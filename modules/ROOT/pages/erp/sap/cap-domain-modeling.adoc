:description: Model business data in CAP with CDS: entities, keys, the reuse aspects cuid and managed, associations versus compositions, localized texts and named aspects, with the SQL and OData metadata the compiler produces, for CAP Node.js 10.2 and CAP Java 5.2.
:keywords: CAP, CDS, domain model, entity, cuid, managed, Association, Composition of many, aspect, localized, sap/cds/common, deep insert, cascaded delete, cds compile, EDMX, SQL, SAP BTP

include::partial$ai-disclaimer.adoc[]

Before an application can show an expense claim, it has to know what a claim is: which fields it has, who owns it, and
that its items belong to it and disappear with it. In CAP this description is called the domain model, and it is the
most important file of a project, because the database tables, the web service and the interface metadata are all
produced from it. This page teaches how to write that model with the CAP modeling language CDS. It covers entities and
keys, the ready-made building blocks `cuid` and `managed`, the difference between an association (a reference) and a
composition (a part-of relationship), translated texts with `localized`, and aspects, which let you add to an entity
from another file. A small teaching model for the expense claims of Example Trading Co. (EX01) is built and run for real
in a scratch folder on 2026-11-13: the SQL and OData metadata that the compiler generates, the seed data and the web
requests with `$expand` shown below are real output. The page is written against CAP Node.js 10.2 (`@sap/cds` 10.2.2,
command line tools `@sap/cds-dk` 10.2.1, Node.js 22.12 or newer) and CAP Java 5.2 (Java 21 or newer, Java 25
recommended). The model is plain CDS, so the same files serve both runtimes, and it can be run on a developer machine
without an account. Deploying it to SAP BTP, on the Cloud Foundry or the Kyma runtime, needs an SAP BTP account and is
not run here. SAP BTP is still the documented name, and SAP now presents the SAP BTP capabilities as part of SAP
Business AI Platform.

== Key terms

* xref:erp/sap/glossary.adoc#cds[CDS (Core Data Services)]: the text language in which CAP models data and services.
* xref:erp/sap/glossary.adoc#entity[Entity]: a named structure of typed elements with a primary key; in a relational
  database it becomes a table.
* xref:erp/sap/glossary.adoc#association[Association]: a reference from one entity to another that does not make the
  target depend on the source.
* xref:erp/sap/glossary.adoc#composition[Composition]: a contained-in relationship in which the child entries belong to
  one parent and are created, read and deleted together with it.
* xref:erp/sap/glossary.adoc#aspect[Aspect]: a reusable bundle of elements or annotations that can be included in an
  entity or added to it with `extend`.
* xref:erp/sap/glossary.adoc#deep-insert[Deep insert]: one request that creates a parent entry together with its
  child entries.
* xref:erp/sap/glossary.adoc#generic-provider[Generic provider]: the built-in CAP code that serves, validates and fills
  in data from the model alone.

== The running example

The teaching model describes what a clerk at Example Trading Co. (EX01) handles every week: an employee files an expense
claim, a claim holds several items (a train ticket, a dinner) and a few free-text notes, and every item has a category
that is shown in the user's language. It reuses the namespace and the entity name of the lab project of this site
(`sap.guide.expenses`, `Claims`) but is larger: it adds employees, categories, items and notes. It is a teaching model,
not SAP software, and the page shows all of its files.

CAP can draw a class diagram of a model. The command `cds compile db/schema.cds --to mermaid` writes Mermaid text, and
the environment variables `CDS_MERMAID_MIN`, `CDS_MERMAID_NAMESPACES` and `CDS_MERMAID_ASSOCNAMES` make it show only the
used entities and the names of the relations. The text below is the real output of that command on the model of this
page. An arrow with a filled diamond marks a composition, a plain arrow an association, and the label is the name of the
element.

[source,shell]

== Entities, keys and types

An entity is declared with the keyword `entity`, a name and a list of elements, each with a name and a type. The domain
modeling guide describes entities as the data of a domain that become tables in relational persistence models, and its
naming conventions are worth following from the first file: entity and type names start with a capital letter, elements
with a lowercase letter, entities are plural (`Claims`) and types singular, and a name does not repeat its context
(`Claims.title`, not `Claims.claimTitle`).

[source,cds]
----
entity Employees : cuid {
  name   : String(60);
  claims : Association to many Claims on claims.employee = $self;
}
----

Source: excerpt of the model of this page, naming conventions from https://cap.cloud.sap/docs/guides/domain/[CAP: Domain Modeling]

The built-in types the guide lists include `UUID`, `Boolean`, `Date`, `Time`, `DateTime`, `Timestamp`, `Integer`,
`Int32`, `Double`, `Decimal`, `String`, `LargeString`, `Binary` and `LargeBinary`. The model uses `String(80)` for a
title and `Decimal(9,2)` for an amount with two decimal places. A project that has many fields of the same kind can name
a type with `type`, but the guide asks for restraint: custom types pay off only when they are reused.

The guide recommends simple, technical, immutable primary keys, and prefers UUIDs for them. Its reasons: a UUID is unique
across systems, a client can create one before saving, and a parent and its children can be inserted in one transaction
without waiting for a database sequence to hand out the parent's number. It adds that the generic service providers of
both runtimes fill an `UUID` key in automatically on insert, and that a UUID must be treated as an opaque value, never
parsed or validated for its format.

== The building blocks of @sap/cds/common

CDS ships a small prebuilt model, `@sap/cds/common`, of reusable types and aspects. The guide on common types describes
three aspects there: `cuid`, `managed` and `temporal`. Importing them is one line:

[source,cds]
----
using { cuid, managed, Currency } from '@sap/cds/common';
----

Source: first line of `db/schema.cds` in the model below, https://cap.cloud.sap/docs/cds/common[CAP: Common Types and Aspects]

=== cuid: a canonical key

`entity Claims : cuid` is the short form of an entity that starts with `key ID : UUID`. The compiler writes the unfolded
result like this (the whole model of the page is compiled with `cds compile db --to cdl`, and the output is shortened to
the entity `Employees`):

[source,text]
----
$ cds compile db --to cdl
...
entity sap.guide.expenses.Employees : cuid {
  key ID : UUID;
  name : String(60);
  claims : Association to many sap.guide.expenses.Claims on claims.employee = $self;
};
----

Source: real output of `cds compile db --to cdl` (shortened to one entity), https://cap.cloud.sap/docs/cds/common#aspect-cuid[CAP: Common Types and Aspects, aspect cuid]

The output keeps the include `: cuid` and also lists the key it added, so one entity is both written the short way and
shown in full. The same command shows what `managed` adds to `Claims`.

=== managed: who changed it and when

`managed` adds four elements, `createdAt`, `createdBy`, `modifiedAt` and `modifiedBy`, and annotates them so that the
generic provider fills them in. The guide describes the rule: data of this kind is filled in automatically and cannot
be written by an external client, and the payload of a request is cleansed. The deep insert request in the section on
compositions sends the field `createdBy` with the value `mallory` on purpose, and the response shows what the server did with it:

[source,json]
----
    "createdAt": "2026-11-13T14:25:17.610Z",
    "createdBy": "anonymous",
    "modifiedAt": "2026-11-13T14:25:17.610Z",
    "modifiedBy": "anonymous",
----

Source: real response of the deep insert request below (shortened to the four managed fields), rule from https://cap.cloud.sap/docs/guides/domain/[CAP: Domain Modeling, Managed Data]

The server stored `anonymous`, the user of the development setup with mocked authentication, and not `mallory`. In a
deployed application the value is the authenticated user. The guide adds that the same behavior can be written for
single elements with the annotations `@cds.on.insert` and `@cds.on.update` and the pseudo variables `$now` and `$user`,
which is what `managed` does internally.

=== Currency, Country and Language

The same shared model offers the types `Country`, `Currency` and `Language`, each a reference to a code list entity
(`sap.common.Currencies` and so on) that also holds translated names. In the model below `currency : Currency` therefore
becomes a column `currency_code` and an association to `sap.common.Currencies`, which is why that entity appears in the
diagram above although the model never declared it.

== The model, in full

This is the whole teaching model. The first file defines the data, the second adds to it from outside (the aspects
section explains why), the third is the service that makes `Claims`, `Employees` and `Categories` visible. The lab file
`modules/ROOT/examples/sap-lab/expenses/db/schema.cds` is smaller: it has only `Claims` with `title`, `status` and
`amount`.

[source,cds]
----
using { cuid, managed, Currency } from '@sap/cds/common';
namespace sap.guide.expenses;

aspect Described {
  remarks : String(200);
}

entity Employees : cuid {
  name   : String(60);
  claims : Association to many Claims on claims.employee = $self;
}

entity Categories : cuid {
  name : localized String(40);
}

entity Claims : cuid, managed, Described {
  title    : String(80);
  status   : String(1) default 'N';
  amount   : Decimal(9,2);
  currency : Currency;
  employee : Association to Employees;
  items    : Composition of many ClaimItems on items.claim = $self;
  notes    : Composition of many {
    key pos : Integer;
    text    : String(200);
  };
}

entity ClaimItems : cuid {
  claim       : Association to Claims;
  category    : Association to Categories;
  description : String(80);
  amount      : Decimal(9,2);
}
----

Source: `db/schema.cds` of the teaching model, written for this page from the syntax of https://cap.cloud.sap/docs/guides/domain/[CAP: Domain Modeling]

== Associations: a reference to another entity

An association says that an entry points at an entry of another entity. `employee : Association to Employees` is the
simplest form: a managed to-one association. The guide's word "managed" means that CAP adds the foreign key column and
the join condition for you, and it recommends managed associations for every to-one relation. The generated column in
the SQL below is `employee_ID`.

A to-many association needs the backlink written down, because the compiler cannot guess it. In `Employees` the element
`claims : Association to many Claims on claims.employee = $self` reads: the claims whose `employee` is this employee.
The guide notes that the condition can compare a backlink association to `$self`, or a backlink foreign key to the own
key. An association is read with `$expand`. The employees and their claims, the second employee has none:

[source,shell]
----
curl -s 'http://localhost:4118/odata/v4/expense/Employees?$expand=claims($select=title,amount)' | python3 -m json.tool
----

[source,json]
----
{
    "@odata.context": "$metadata#Employees",
    "value": [
        {
            "ID": "e1111111-1111-1111-1111-111111111111",
            "name": "Ana Torres",
            "claims": [
                {
                    "title": "Customer visit Chicago",
                    "amount": "128.50",
                    "ID": "a1111111-1111-1111-1111-111111111111"
                }
            ]
        },
        {
            "ID": "e2222222-2222-2222-2222-222222222222",
            "name": "Ben Carter",
            "claims": []
        }
    ]
}
----

Source: real response (JSON pretty-printed with `python3 -m json.tool`), https://cap.cloud.sap/docs/guides/domain/[CAP: Domain Modeling, Associations]

The key `ID` is added to each expanded entry although `$select` did not name it; the response always carries the key.

CDS has no dedicated many-to-many association. The guide resolves it with a link entity that holds two to-one
associations, and notes that a composition of an inline aspect (shown below) removes some of the noise. The model of
this page has no many-to-many relation.

== Compositions: parts that belong to one parent

A composition is an association with a promise: the target entries are parts of the source entry. The reference
documentation puts it as "contained-in", and the domain guide lists the three things the runtimes do for it out of the
box: a deep insert or update fills in whole document structures, deleting the root deletes the parts (a cascaded
delete), and composition targets are exposed in the service automatically. In `Claims`, the line
`items : Composition of many ClaimItems on items.claim = $self` says that the items of a claim are parts of it. The
`on` condition uses the backlink `claim`, which is an ordinary association in `ClaimItems`.

=== Auto-exposure and the entity you cannot call directly

The service of this page lists `Claims`, `Employees` and `Categories`. The compiler still produced `ClaimItems` and
`Claims.notes` in the service, as the metadata further below shows. They were exposed because they are composition
targets. The service lets a client reach them only through their parent. A direct request is refused with this answer:

[source,shell]
----
curl -s -i 'http://localhost:4118/odata/v4/expense/ClaimItems'
----

[source,text]
----
HTTP/1.1 405 Method Not Allowed
{"error":{"message":"Entity \"ExpenseService.ClaimItems\" is not explicitly exposed as part of the service","code":"ENTITY_IS_AUTOEXPOSED","@Common.numericSeverity":4}}
----

Source: real response (shortened to the status line and the body), auto-exposure rule from https://cap.cloud.sap/docs/guides/domain/[CAP: Domain Modeling, Compositions]

The message says that the entity is not explicitly exposed. An entity line of its own in the service is the way to expose
it explicitly; this page did not run that variant.

=== Compositions of aspects: the inline form

The element `+notes : Composition of many { key pos : Integer; text : String(200); }+` has no entity behind it. The guide
calls this a composition of aspects, and the language reference explains the result: the compiler adds an entity whose
name is the name of the parent entity followed by the name of the element, here `Claims.notes`, with a backlink named
`up_`. The unfolded entity, as `cds compile db --to cdl` prints it:

[source,text]
----
entity sap.guide.expenses.Claims.notes {
  key up_ : Association[1..1] to sap.guide.expenses.Claims not null;
  key pos : Integer;
  text : String(200);
};
----

Source: real output of `cds compile db --to cdl` (shortened to one entity), https://cap.cloud.sap/docs/cds/cdl#managed-compositions[CAP: CDL, Managed Compositions of Aspects]

The generated entity has two keys, the backlink and `pos`, which is why the table below has the primary key `+up__ID, pos+` and why the seed file needs both columns. A named aspect can be used instead of an inline one:
`Items : Composition of many OrderItems` with `+aspect OrderItems { ... }+` is unfolded the same way, according to the
language reference. The reference also warns about compositions of one: they are discouraged for entities, with very
limited draft support and no extensive modification over paths.

=== Cascaded delete

Deleting a composition root deletes its parts, and the compiler records that in the service metadata (below). The
service does not expose the items, so the count of rows was made with a small test script using the CAP test helper,
`cds.test`, started in the same project. The script deletes the seeded claim through the service and counts the rows of
the two child tables through the database service before and after:

[source,javascript]
----
import cds from '@sap/cds'
import { test } from 'node:test'
const { DELETE } = cds.test(import.meta.dirname)
const out = (...a) => process.stderr.write(a.join(' ') + '\n')
const count = async e => (await cds.db.run(SELECT.one.from(e).columns('count(*) as n'))).n
const items = 'sap.guide.expenses.ClaimItems', notes = 'sap.guide.expenses.Claims.notes'
test('cascade', async () => {
  out('before: items', await count(items), 'notes', await count(notes))
  const res = await DELETE('/odata/v4/expense/Claims(a1111111-1111-1111-1111-111111111111)')
  out('DELETE Claims', res.status)
  out('after:  items', await count(items), 'notes', await count(notes))
})
----

[source,text]
----
$ node --test check-cascade.test.mjs
before: items 2 notes 1
DELETE Claims 204
after:  items 0 notes 0
----

Source: `check-cascade.test.mjs` of the teaching model and its real output (shortened to the three lines the script prints), cascaded delete rule from https://cap.cloud.sap/docs/guides/domain/[CAP: Domain Modeling, Compositions]; the helper `cds.test` is the one the lab test `test/service.test.js` uses

=== An association does not cascade

An association has no such promise. The employee Ben Carter owns the new claim "Workshop Boston". Deleting the employee
through the service is accepted, and the claim keeps its foreign key; reading the claim with `$expand=employee` finds no
target:

[source,shell]
----
curl -s -o /dev/null -w "DELETE employee %{http_code}\n" -X DELETE 'http://localhost:4118/odata/v4/expense/Employees(e2222222-2222-2222-2222-222222222222)'
curl -s 'http://localhost:4118/odata/v4/expense/Claims?$filter=title%20eq%20%27Workshop%20Boston%27&$expand=employee($select=name)&$select=title,employee_ID'
----

[source,text]
----
DELETE employee 204
{"@odata.context":"$metadata#Claims","value":[{"title":"Workshop Boston","employee_ID":"e2222222-2222-2222-2222-222222222222","employee":null,"ID":"abe6731c-9c71-4656-ad18-d0afb5c573e2"}]}
----

Source: real output of the two requests, run on a fresh server after a new deep insert of the same body (so the claim has a new generated key, unlike the deep insert response above), semantics from https://cap.cloud.sap/docs/guides/domain/[CAP: Domain Modeling, Associations and Compositions]

The generated SQL, shown further down, contains no foreign key constraint, so the database did not object either. The
language reference points to a section on database constraints in the CAP database guide for projects that want to add
them. Which relation is which is therefore a modeling decision with a runtime
effect: a claim item makes no sense without its claim, so it is a composition; a claim only refers to the employee who
filed it, so it is an association.

== Association or composition

[cols="1,2,2",options="header"]
|===
|Question |Association |Composition

|What does it mean?
|The entry refers to an entry that lives on its own.
|The target entries are parts of the source entry.

|Deep insert and update
|Not done: the target must exist, and its key is given as a foreign key (`employee_ID`).
|Done: the parts are sent inside the parent's body, and their keys and backlinks are filled in.

|Delete of the source
|Does not touch the target (shown above).
|Deletes the parts (shown above); the metadata says `+OnDelete Action="Cascade"+`.

|Exposure in a service
|The target must be exposed with its own entity line in the service.
|The target is exposed automatically, and is reachable through its parent.

|Typical use
|Employee of a claim, category of an item, currency.
|Items of a claim, lines of an order, notes of a claim.
|===

Source: the three runtime rules of compositions in https://cap.cloud.sap/docs/guides/domain/[CAP: Domain Modeling, Compositions] and the runs above

The ABAP page xref:programming-languages/abap/cds-associations.adoc[CDS Associations and Compositions] describes the
same split in ABAP CDS: a composition makes a child entity depend on its parent, with a to-parent association pointing
back.

== Localized data: texts in the user's language

The category names are the example. In the model, `name : localized String(40)` is the whole declaration. CAP unfolds it
into a second entity `Categories.texts` that holds the translations, plus two associations on the base entity, as the
localized data guide shows. The unfolded text entity, as the compiler printed it for this model:

[source,text]
----
entity sap.guide.expenses.Categories.texts : sap.common.TextsAspect {
  @title : '{i18n>LanguageCode}'
  key locale : sap.common.Locale(14);
  @odata.containment.ignore : true
  key ID : UUID;
  name : String(40);
};
----

Source: real output of `cds compile db --to cdl` (shortened to one entity), https://cap.cloud.sap/docs/guides/uis/localized-data[CAP: Localized Data]

The base entity keeps the original text (the guide: all original texts stay in the source entity, which saves a join
when a translation is missing), and the texts table holds one row per entry and language. The generated SQL below has
both tables and a view that reads them with a fallback.

The runtime picks the language from the request. The guide says that the preferred locale is taken from request
parameters, user settings or the `Accept-Language` header, and that the pseudo variable `$user.locale` carries it into
the query. The `$expand` of a claim with its items and their categories, sent with the header:

curl -s -H 'Accept-Language: de' 'http://localhost:4118/odata/v4/expense/Claims?$select=title&$expand=items($select=description;$expand=category($select=name))' | python3 -m json.tool
----

Reading the categories directly gave the English names `Travel` and `Meals` from the base entity without the header and
`Reisen` and `Verpflegung` with it (request `Categories?$select=name`). The translated rows are also readable as a

The guide states two limits worth knowing: the keys of an entity with `localized` elements must not be associations, and
`localized` inside structured elements is ignored.

== Aspects: adding to an entity from another place

An aspect is a named or anonymous bundle of elements or annotations. The reference calls CDS aspects a mechanism for the
separation of concerns, with `extend` and `annotate` as the two directives, and says that consumers always see the
effective model, so the separation is invisible outside the model files.

The model uses all three forms. The named aspect `Described` holds one element, `remarks`, and `Claims` includes it
the way it includes `cuid` and `managed`: `entity Claims : cuid, managed, Described`. The unfolded `Claims` table below
has the column `remarks` right after the four managed columns. The file `db/extensions.cds` shows the other two:
`+extend db.Claims with { project : String(20); }+` adds an element to an entity defined elsewhere, and
`+annotate db.Claims with { title @title : 'Claim title'; }+` attaches an annotation. Both took effect in the generated
output: the SQL table has a column `project`, and the metadata has a label for `title`.

The domain guide recommends this for secondary concerns, for authorization annotations that a security team maintains
in its own file, and for user interface annotations that belong in the frontend model, so that the core domain model
stays short and readable. A later page of this section covers the authorization annotations, and the Fiori annotations
belong with the user interface pages.

== Common modeling mistakes

[cols="2,3",options="header"]
|===
|Mistake |What happens and what to do

|A composition used for a plain reference, such as an employee of a claim
|Deleting the claim would delete the employee's data if the target were really part of it, and a service would expose the
target automatically. Use an association when the target lives on its own.

|An association used for the items of a claim
|Deep insert and cascaded delete are not done for it, so the items stay behind when the claim is deleted. Use a
composition.

|A to-many association without an `on` condition on a database model
|The domain guide says the condition is needed when targeting a database; write the backlink as `on items.claim = $self`.

|A client sends `createdBy` or `modifiedAt`
|The generic provider overwrites managed fields; the request of this page shows `mallory` replaced by `anonymous`.

|Composite or business keys everywhere
|The guide prefers a single simple technical key, a UUID, because keys are used in every join; keep business numbers as
ordinary elements.

|`localized` on an entity whose key is an association
|The localized data guide lists this as a restriction.
|===

Source: rules from https://cap.cloud.sap/docs/guides/domain/[CAP: Domain Modeling] and https://cap.cloud.sap/docs/guides/uis/localized-data[CAP: Localized Data], consequences as shown by the runs above

== Summary

* A CAP domain model is CDS: entities with typed elements and a key, written the short way with `cuid` for a UUID key
  and `managed` for the four change-tracking fields that the generic provider fills in and clients cannot write.
* An association is a reference (`employee_ID`), a composition is a part-of relationship: deep insert, cascaded delete
  and automatic exposure apply to compositions only, as the runs on this page showed, and a composition target can be
  read only through its parent unless the service names it.
* `+Composition of many { ... }+` with an inline aspect generates an entity named after the parent and the element
  (`Claims.notes`) with a backlink `up_`; a named aspect included in an entity adds its elements.
* `localized` generates a `.texts` entity and a view with fallback; the language comes from the request, for example
  the `Accept-Language` header.
* `extend` and `annotate` add to an entity from another file, so core models stay clean.
* `cds compile --to sql` and `--to edmx` show exactly what the database and the OData service receive; the dialect
  option changes the database types, not the model.
