= SAP Guide: Test a CAP Service and a UI5 App
:description: Step-by-step guide to automated tests for CAP Node.js 10.2 and OpenUI5 1.154: test a service with cds.test and node --test, check a UI5 app with the UI5 linter, QUnit and OPA5 in a local headless Chrome, and run all checks with one command that ends with an exit code.
:keywords: SAP, CAP, cds.test, node --test, UI5, OpenUI5, QUnit, OPA5, ui5lint, UI5 linter, headless Chrome, exit code, CI, testing, step by step, guide

include::partial$ai-disclaimer.adoc[]

Checked on 2026-11-13 against CAP Node.js 10.2 (`@sap/cds` 10.2.2, `@sap/cds-dk` 10.2.1, `@cap-js/cds-test` 1.0.2), UI5 Tooling 4.0.73 with the UI5 linter 1.23.8, OpenUI5 1.154.0, Node.js 24.21 and Google Chrome in headless mode.

== What you build

This is a teaching model built with CAP. It is not SAP S/4HANA or SAP SuccessFactors and does not reproduce their screens.

You build a small expense claims service and a small UI5 app, and then you write the tests that a pipeline would run after every change. The service gets four tests that start it, send HTTP requests to it and check the answers. One of them is written first and fails, so you see what a failing test looks like, and then you add the code that makes it pass. The UI5 app gets a static check with the UI5 linter, a QUnit unit test and an OPA5 test that presses a button in the running app. A script runs the browser tests in a local headless Chrome. At the end, one command runs everything and reports success or failure as an exit code, which is what a CI server reads.

== Before you start

* No account is needed: the CAP tools, UI5 Tooling and OpenUI5 install from the public npm registry without signing in, and the tests run in a Chrome on your own computer. Installing `@sap/cds-dk` and `@sap/cds` means accepting the SAP Developer License Agreement, version 3.2, which the packages state themselves; the lab README names it. UI5 Tooling, OpenUI5, the UI5 linter and `@cap-js/cds-test` are Apache-2.0 licensed.
* Install Node.js 22.12 or newer and the CAP command line tools (`npm install --global @sap/cds-dk`, as in the guide xref:erp/sap/guide-first-cap-service.adoc[Your First CAP Service]). `node -v` and `cds version` print the versions.
* Install Google Chrome. The browser tests run it without a window (headless mode). The script in step 16 looks for Chrome in the usual places of macOS and Linux; if yours is elsewhere, set the environment variable `CHROME_BIN` to its path.
* Read xref:erp/sap/ci-cd-and-testing.adoc[CI/CD and Testing] first, or at least know what a test and a pipeline are. The guide xref:erp/sap/guide-first-cap-service.adoc[Your First CAP Service] builds a similar project; this guide starts a new one, so nothing from it is needed.
* A passing test prints a check mark, a failing test prints a cross. An exit code is the number a command leaves behind when it ends: 0 means success and any other number means failure.
* The figures are drawings of the editor and the terminal, not screenshots. A highlighted box with a number marks the file or the command of the step with the same number. The terminal text is the real output of the commands, without blank lines and without the lines that npm prints about installed packages; times such as 144.195291ms differ from run to run.

== Check the result

* `npm test` in the project folder prints four check marks, `pass 4` and `fail 0`.
* In `ui5app`, `npm run lint` prints `Success! No findings detected.` and `npm test` prints `unit/Main: 2 tests, 0 failed, 2 of 2 assertions passed` and `integration/opaTests: 1 tests, 0 failed, 1 of 1 assertions passed`.
* `npm run ci` in the project folder runs all of them, and `echo $?` right afterward prints `0`.

== Variations

* Break a test on purpose. In `ui5app/webapp/test/unit/Main.qunit.js`, change the expected total `165.5` to `165` and run `npm test` in `ui5app`. The script prints `unit/Main: 2 tests, 1 failed, 1 of 2 assertions passed` and exits with 1. Change it back.
* Make the linter find something. In `Main.controller.js`, replace `this.byId("total")` with `sap.ui.getCore().byId("total")`. `npm run lint` prints three errors on that line, for the access of the global `sap` (rule `no-globals`) and for the deprecated calls `getCore` and `byId` (rule `no-deprecated-api`), and exits with 1. Change it back.
* Look at the tests in a browser. In `ui5app`, run `npm start` and open http://localhost:8767/test/testsuite.qunit.html. The page lists `unit/Main` and `integration/opaTests` with a button to run all of them. Press `Ctrl+C` in the terminal to stop the server.

== What can go wrong

[cols="2,3,3",options="header"]
|===
|Symptom
|Cause
|Fix

|`npm test` in the project folder prints `ReferenceError: sap is not defined` for files such as `ui5app/webapp/test/integration/MainJourney.js` and ends with a cross
|The script is a plain `node --test`. Without a pattern, Node's runner runs every file in any folder named `test`, including the browser tests of the UI5 app, and Node has no `sap` object.
|Use `node --test "test/*.test.js"` as in step 3.

|`rejects a negative amount` fails with `Missing expected rejection`
|The service accepted the claim, because the handler does not exist yet or is not found.
|Create `srv/claim-service.js` next to `srv/claim-service.cds`, with the same name.

|`npm test` in `ui5app` prints `Duplicate framework dependency definition(s) found for project guide.claims: sap.ui.core, sap.ui.layout, sap.ui.unified, sap.m.` and `ui5 serve did not start`
|An OpenUI5 library, here `@openui5/sap.m`, was added to `package.json` as well as to `ui5.yaml`.
|List the framework libraries only in `ui5.yaml` and remove them from `package.json`.

|`npm test` in `ui5app` prints `EADDRINUSE: Port 8767 is already in use.` and `ui5 serve did not start`
|Another program, for example an earlier `npm start`, still listens on port 8767.
|Stop that program, or change the port in `run-tests.mjs` and in the `start` script.

|`npm run lint` prints errors such as `Access of global variable 'sap' (sap.ui.getCore)  no-globals`
|The app uses a global or a deprecated API that the UI5 linter reports.
|Use the module that the report names instead; the exit code is 1 until the report is clean.

|`unit/Main: 2 tests, 1 failed, 1 of 2 assertions passed`
|A QUnit assertion failed.
|Open `testsuite.qunit.html` in a browser (see the third variation) and read the failed assertion.
|===

== Clean up

The tests create nothing outside the project folders, except the OpenUI5 libraries that UI5 Tooling downloaded into `~/.ui5` and the `node_modules` folders. Delete the folder `claims-tested` when you no longer need it. The next steps of your own app build on it.
