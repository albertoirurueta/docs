= SAP Guide: Secure a CAP Service with Roles
:description: Step-by-step guide to CAP Node.js 10.2 security: close a claims service with requires and restrict, call it with the built-in mocked users alice and bob, read the 401 and 403 answers, test the rules, and learn how XSUAA replaces the mocked users after deployment.
:keywords: SAP, CAP, security, authorization, requires, restrict, mocked users, authenticated-user, admin role, 401, 403, XSUAA, xs-security.json, cds.test, step by step, guide

Checked on 2026-11-13 against CAP Node.js 10.2 (`@sap/cds` 10.2.2, `@sap/cds-dk` 10.2.1, `@cap-js/cds-test` 1.0.2), curl and Node.js 24.21.

== What you build

This is a teaching model built with CAP. It is not SAP S/4HANA or SAP SuccessFactors and does not reproduce their screens.

You build a small service for expense claims that anybody can read and change, and then you close it. Two short annotations say that every caller must be logged in, that every logged-in user may read the claims, and that only a user with the role `admin` may create, change or delete a claim or approve it. You then call the service as the users that CAP ships for development: `alice`, who has the role `admin`, and `bob`, who has not. You see the answers 401 (not logged in), 200 (allowed), 403 (logged in but not allowed) and 204 (an action ran), and you write four tests that keep the rules in place. Nothing is deployed and no real user is involved. How the same roles reach a service in production is explained in the text after the steps.

== Before you start

* No account is needed: the CAP tools install from the public npm registry without signing in, and the users in this guide are test users that CAP carries inside the runtime. Installing `@sap/cds-dk` and `@sap/cds` means accepting the SAP Developer License Agreement, version 3.2, which the packages state themselves; the lab README names it. No password is typed anywhere: the built-in users have none.
* Install Node.js 22.12 or newer and the CAP command line tools (`npm install --global @sap/cds-dk`). Use a code editor and two terminals, one for the server and one for the calls. The `curl` command comes with macOS and current versions of Windows and Linux.
* The guide xref:erp/sap/guide-first-cap-service.adoc[Your First CAP Service] builds the same kind of project with the same commands. If you have not done it, read its steps first or at least know what an entity, a service and `cds watch` are. The project here is new, so you need nothing from that guide.
* Read xref:erp/sap/cap-security.adoc[CAP Security] for the full story of `@requires`, `@restrict` and `where` conditions; this guide only uses the simplest rules. xref:erp/sap/btp-security-xsuaa-and-identity.adoc[Security: XSUAA and Cloud Identity Services] covers what happens after deployment.
* The figures are drawings of the editor and the terminal, not screenshots. A highlighted box with a number marks the file or the command of the step with the same number. The server runs on port 4004 in the figures and in the text; if another program already uses that port, `cds watch` tells you which port it took, and you use that port in the addresses.
* The names are the lab's own: the entity `Claims`, the service `ClaimsService`, the action `approve` and the claim `Train ticket` are made up for this guide. The role `admin` and the users `alice` and `bob` come from CAP.

=== Run the service without rules

[start=6]
. In the first terminal, in the project folder, start the server:
+
[source,bash]
----
cds watch
----
+
The log ends with `server listening on { url: 'http://localhost:4004' }`. Read the line `using auth strategy { kind: 'mocked' }`: the server is in the development profile, where CAP checks logins against a built-in list of test users instead of a real identity service. The service is served at `/odata/v4/claims`.
+
image::sap-general-guide-secure-a-cap-service-02-cds-watch.svg["Terminal after cds watch: the log lists the model files srv/claims-service.cds, db/schema.cds and the common.cds of CAP, connects to an in-memory SQLite database, initializes it from db/data/sap.guide.secured-Claims.csv, shows the line using auth strategy kind mocked, serves ClaimsService at /odata/v4/claims with the implementation srv/claims-service.js and ends with server listening on http://localhost:4004; callout 6 marks the command",width=900]
+
The figure leaves out the banner that `cds watch` prints before the first line.
. In the second terminal, store the two addresses that the next calls use, then read one claim without any credentials. The `$` in `$top` and `$select` is escaped with a backslash so that the shell does not read it as a variable.
+
[source,bash]
----
BASE=http://localhost:4004/odata/v4/claims/Claims
CLAIM="$BASE(11111111-1111-1111-1111-111111111111)"
curl -s -w '\nHTTP %{http_code}\n' "$BASE?\$top=1&\$select=title"
----
+
The answer is the claim and `HTTP 200`.
. Now change the claim, again without credentials. The `-X PATCH` option sends an update and `-d` carries the new amount.
+
[source,bash]
----
curl -s -o /dev/null -w 'HTTP %{http_code}\n' -X PATCH \
  -H 'Content-Type: application/json' -d '{"amount":50}' "$CLAIM"
----
+
The answer is `HTTP 200` again: anyone who can reach the service can change the data. CAP's authorization guide says that services have no access control unless you model it, and in development it does not even ask for a login. That is the state the next steps fix.
+
image::sap-general-guide-secure-a-cap-service-03-open-service.svg["Terminal with two curl calls to the service before any rule exists: the first, a read without credentials, answers HTTP 200 with the claim Train ticket; the second, a PATCH that sets the amount to 50 without credentials, also answers HTTP 200; callout 7 marks the read and callout 8 the write",width=900]
+
The figure shows each command on one line; the page wraps the long one with a backslash.

=== Call the service as mocked users

CAP ships a list of test users for the development profile. In this guide only two matter: `alice` has the role `admin`, and `bob` has no role that the rules know. You can print the list with `cds env get requires.auth`. The users have no password. `curl -u bob:` sends the name and an empty password, and the colon after the name is what tells curl not to ask for one.

[start=11]
. Read the claims without credentials, and print only the status line and the header that asks for a login.
+
[source,bash]
----
curl -s -i "$BASE" | grep -iE '^(HTTP|www-authenticate)'
----
+
The answer is `HTTP/1.1 401 Unauthorized` and `WWW-Authenticate: Basic realm="Users"`. 401 means "I do not know who you are". The service rule `authenticated-user` needs a user, and there is none.
. Read as `bob`:
+
[source,bash]
----
curl -s -w '\nHTTP %{http_code}\n' -u bob: "$BASE?\$top=1&\$select=title"
----
+
The answer is `HTTP 200` with the claim. `bob` is logged in, and the first privilege admits every logged-in user to read.
. Change a claim as `bob`:
+
[source,bash]
----
curl -s -w '\nHTTP %{http_code}\n' -u bob: -X PATCH \
  -H 'Content-Type: application/json' -d '{"amount":50}' "$CLAIM"
----
+
The answer is the error `Forbidden` with the code 403 and `HTTP 403`. 403 means "I know who you are, and you may not do this". `bob` has no role for the event `UPDATE`.
+
image::sap-general-guide-secure-a-cap-service-05-read-and-refuse.svg["Terminal with three curl calls after the rules: a read without credentials answers HTTP/1.1 401 Unauthorized and a WWW-Authenticate header for Basic realm Users; a read as bob answers HTTP 200 with the claim Train ticket; a PATCH as bob answers the error Forbidden with code 403 and HTTP 403; callout 11 marks the first call, callout 12 the second and callout 13 the third",width=900]
. Make the same change as `alice`:
+
[source,bash]
----
curl -s -o /dev/null -w 'HTTP %{http_code}\n' -u alice: -X PATCH \
  -H 'Content-Type: application/json' -d '{"amount":50}' "$CLAIM"
----
+
The answer is `HTTP 200`. The role `admin` is named in the privilege for `UPDATE`.
. Call the action as `bob`. The path is the claim, a slash, the service name and the action name.
+
[source,bash]
----
curl -s -w '\nHTTP %{http_code}\n' -u bob: -X POST \
  -H 'Content-Type: application/json' -d '{}' \
  "$CLAIM/ClaimsService.approve"
----
+
The answer is `Forbidden`, code 403: the action is in the same privilege as the writing events, so it is for `admin` only.
. Call the same action as `alice`:
+
[source,bash]
----
curl -s -o /dev/null -w 'HTTP %{http_code}\n' -u alice: -X POST \
  -H 'Content-Type: application/json' -d '{}' \
  "$CLAIM/ClaimsService.approve"
----
+
The answer is `HTTP 204`: the action ran and returns no content.
. Read the claim again to see what the handler and the aspect `managed` did:
+
[source,bash]
----
curl -s -u alice: "$CLAIM?\$select=title,status,amount"
----
+
The status is now `A` and the amount is `50.00`. Asking for `modifiedBy` shows `alice`, because CAP filled the field from the logged-in user.
+
image::sap-general-guide-secure-a-cap-service-06-admin-writes.svg["Terminal with four curl calls: a PATCH as alice answers HTTP 200; an approve call as bob answers the error Forbidden with code 403 and HTTP 403; the same approve call as alice answers HTTP 204; a read as alice shows the claim Train ticket with the status A and the amount 50.00; callouts 14 to 17 mark the four calls in order",width=900]

The figure shows the long commands with only the end of the address wrapped; in the terminal they are one command each.

== Check the result

* A request without credentials answers 401, as `bob` and as `alice` it can read, and `bob` gets 403 for an update and for the action `approve`.
* As `alice` the update answers 200 and the action answers 204; reading the claim afterward shows the status `A`.
* `npm test` ends with `pass 4` and `fail 0`.

== From mocked users to production

The rules you wrote do not change when the service is deployed. What changes is the answer to "who is calling", and it changes by configuration, not by code. In the development profile the authentication strategy is `mocked`: a list of fixed users inside the runtime, with names, roles and no password. In the production profile CAP reads the strategy `jwt` instead, which `cds env get requires.auth --profile production` printed in the lab. There the caller sends a signed token, the JSON Web Token (JWT), in the `Authorization` header, and CAP builds its user from the token: the name, and the roles from the scopes in the token. This is the part that XSUAA, the SAP Authorization and Trust Management service, plays on SAP BTP Cloud Foundry. It issues the tokens, and an administrator of the subaccount decides which user gets which scopes.

A role such as `admin` in your annotation therefore becomes a scope with the same name. `npx cds compile srv --to xsuaa` prints the descriptor that CAP generates from the roles in the model (see the first variation below), and `cds add xsuaa` writes it into the project as `xs-security.json`. At deployment the descriptor creates the XSUAA service instance. An administrator then bundles the roles into role collections and assigns the collections to users. The users `alice` and `bob` do not exist there: a person is `admin` only if a role collection that holds that role was assigned to the person. SAP now recommends Identity Authentication with the Authorization Management Service for new projects; the reference page names the choice. This guide does none of this, because it needs a deployed application and an SAP BTP account, and the guide needs neither. The full explanation, with the generated file and the role collections, is in xref:erp/sap/btp-security-xsuaa-and-identity.adoc[Security: XSUAA and Cloud Identity Services].

== Variations

* Print what CAP would generate for XSUAA from the roles of your model. The command only reads the model and prints; it contacts nothing:
+
[source,bash]
----
npx cds compile srv --to xsuaa
----
+
The answer lists one scope, `$XSAPPNAME.admin`, and one role template `admin` that references it. The role `authenticated-user` is not a scope, because the runtime adds it after any successful login.
* Let only the owner change a claim. In `claims-access.cds` an `UPDATE` privilege can carry a `where` condition such as `createdBy = $user`, which the reference page xref:erp/sap/cap-security.adoc[CAP Security] explains.

== What can go wrong

[cols="2,3,3",options="header"]
|===
|Symptom
|Cause
|Fix

|`alice` gets `Forbidden` with code 403 on an update after you changed the role in the file to `Admin`
|Role names are case sensitive. `Admin` is a different role from `admin`, and the user `alice` has only `admin`.
|Write the role exactly as the user has it, here `admin`, and save; `cds watch` restarts.

|A `PATCH` answers `Unsupported Media Type` with code 415
|The call has no `Content-Type: application/json` header.
|Add `-H 'Content-Type: application/json'` to the `curl` command.

|The address answers `Invalid resource path "ClaimsService.Claim"` with code 404
|The entity name in the address has a typo (`Claim` for `Claims`).
|Copy the address from the variable `CLAIM`.

|A call as `alice` with a wrong password still answers 200
|The built-in users have no password, so the mocked login accepts any password for them. It tests roles, not passwords.
|Do not read a 200 here as proof that a password is checked. Real logins come with the production strategy.

|Every call answers 401 after the rules were added
|The call has no `-u` option, so there is no user.
|Add `-u alice:` or `-u bob:`, with the colon.
|===

== Clean up

Press `Ctrl+C` in the first terminal to stop `cds watch`. The database lived only in memory, so the changed claim is gone at the next start. The project folder is yours to keep.
