= API Management

When a company opens its systems to other programs, such as a mobile app, a partner's web shop or a script written by a
colleague, it does not want each of them to talk straight to the SAP S/4HANA system. It wants one controlled front door
that checks who is calling, limits how often they call and records what happens. In SAP's cloud portfolio that front
door is API Management, one capability of SAP Integration Suite. This page explains the vocabulary (API proxy, policy,
API product, Developer Hub), follows a single request through the policies that guard an API, and shows the policy
configuration of a small example. It describes the service as documented by SAP in November 2026 for the Cloud Foundry
environment of SAP Business Technology Platform (SAP BTP); the hands-on parts need an SAP BTP account, so the listings
are labeled as not run here. After reading, you can say what an API proxy protects, in which order a typical proxy
checks a request, and how a developer gets a key to call it.

== Key terms

* xref:erp/sap/glossary.adoc#api-management[API Management]: the capability of SAP Integration Suite to publish, secure,
  monitor and promote APIs.
* xref:erp/sap/glossary.adoc#api-proxy[API proxy]: a public representation of a backend API, made of endpoints and
  policies, that hides the backend from its callers.
* xref:erp/sap/glossary.adoc#api-policy[Policy]: a small configured program that does one job on a request or a
  response, such as checking a key or limiting traffic.
* xref:erp/sap/glossary.adoc#api-product[API product]: a bundle of API proxies, with a quota, that developers can
  subscribe to.
* xref:erp/sap/glossary.adoc#developer-hub[Developer Hub]: the self-service portal where application developers find
  APIs, create applications and get keys.
* xref:erp/sap/glossary.adoc#sap-integration-suite[SAP Integration Suite]: the SAP BTP service that bundles
  integration flows, API Management, event handling and related tools.

== Where API Management sits

SAP Integration Suite is the umbrella service for connecting systems. SAP's Integration Suite documentation describes
the API Management capability as the part that lets you publish, promote and oversee APIs in a secure and scalable
environment. It lists what you can do with it: proxify APIs under your own domain, secure them against unauthorized
access, control traffic with quotas and spike limits, govern their life cycle, get business insights from usage
analytics, transform headers and payloads, and engage developers through a portal.

The neighboring capability, Cloud Integration, moves messages between systems along integration flows. API Management
instead stands in front of an interface and decides who may call it and how often. The two are often combined: an
integration flow exposes a service, and an API proxy in front of it adds the access rules. SAP documents this
combination too (the API provider type for SAP Cloud Integration), but this page stays with the proxy itself.

Source: https://github.com/SAP-docs/btp-integration-suite/blob/main/docs/apim/API-Management/what-is-api-management-0aef763.md[What is API Management (SAP Integration Suite documentation source)]

The documentation divides the service into five components, which the rest of this page uses.

[cols="1,3"]
|===
|Component |What it does

|API Runtime
|Runs the deployed API proxies; applications call it and are authenticated there.

|API Portal
|The place where an administrator creates, secures and publishes API proxies, defines products and rate plans.

|Developer Hub
|The self-service site where application developers discover APIs, subscribe to plans and build applications.

|API Analytics
|Collects information about calls, such as URL, user, and latency, and shows it in dashboards.

|API Designer
|Lets API developers define, implement and document an API, with support for the OpenAPI standard.
|===

Source: https://github.com/SAP-docs/btp-integration-suite/blob/main/docs/apim/API-Management/components-of-api-management-24f1af0.md[Components of API Management]

Older material uses older names. The Developer Hub is what earlier generations of the product called the developer

under partly different names and, being from 2019, cannot show the current Integration Suite packaging, so check
screen labels against the current documentation before following an older tutorial.

== The API proxy

An API is exposed as an API proxy. SAP describes it as a discrete representation of an API, implemented as a set of
configuration files, policies and code snippets. Its main value is decoupling: callers keep using the same address while
the backend behind it changes. A proxy can expose a REST service, an OData service (as an OData API or as a REST API) or
a SOAP service as a pass-through. The documentation lists what a proxy can enforce: security (authentication, rate
limiting), scalability (caching, spreading requests), flexibility (changing requests and responses), monitoring and
analytics, and versioning.

A proxy has two kinds of endpoint, and both matter for the rest of the page.

* The *ProxyEndpoint* defines the inbound side: how client applications call the proxy. Every proxy has one.
* The *TargetEndpoint* defines the outbound side: how the proxy calls the real backend service on behalf of the client.
  A proxy can have zero or several.

The backend itself is described by an API provider, which holds the connection details (host, port, and for systems in a
private network the way to reach them) of the system where the actual service lives, such as an SAP S/4HANA system or
any other server that hosts a REST service.

Source: https://github.com/SAP-docs/btp-integration-suite/blob/main/docs/apim/API-Management/api-proxy-8962643.md[API Proxy] and https://github.com/SAP-docs/btp-integration-suite/blob/main/docs/apim/API-Management/concepts-of-api-management-ae66eba.md[Concepts of API Management]

== Flows and policies

Both endpoints process a message as a pipeline called a flow, with a request stream and a response stream. SAP divides
each flow into a PreFlow, optional conditional flows, a PostFlow and, for the response of a ProxyEndpoint, an optional
PostClientFlow. The PreFlow always runs first. SAP's documentation says to use the PreFlow of the ProxyEndpoint when a
call that has exceeded its quota must not be routed to the backend, or when users must be authenticated, so quota and
security policies usually go there. A conditional flow runs only when its condition matches, for example to convert XML
to JSON only for some callers. The PostFlow always runs last, which makes it a fit for logging.

A policy is the unit of behavior placed into a flow. The documentation defines it as a program that executes a specific
function at runtime, so that common functions need not be coded again for each API. You choose the flow segment,
configure the policy in the policy designer, and give it a condition if it should run only sometimes. Policies in a flow
run in the order in which they were applied. Every policy shares three attributes: `enabled` switches it on or off,
`continueOnError` decides whether processing goes on when the policy fails (for quota policies SAP says to set it to
`false`), and `async` runs it in a separate thread.

The prebuilt policy list falls into groups. This table follows the names SAP gives in the policy types topic.

[cols="1,3"]
|===
|Group |Policies from the documented list

|Security
|Verify API Key, OAuth v2.0 (with its GET and SET variants), Basic Authentication, SAML Assertion Policy, Access Control, XML Threat Protection, JSON Threat Protection, Regular Expression Protection

|Traffic management
|Spike Arrest, Quota, Reset Quota, Response Cache, Populate Cache, Lookup Cache, Invalidate Cache

|Mediation (changing messages)
|Assign Message, Extract Variables, JSON to XML, XML to JSON, XSL Transform, Service Callout, Raise Fault

|Extension and logging
|JavaScript, Python Script, Key Value Map Operations, Message Logging Policy, Statistics Collector Policy
|===

Source: https://github.com/SAP-docs/btp-integration-suite/blob/main/docs/apim/API-Management/policy-types-c918e28.md[Policy Types], https://github.com/SAP-docs/btp-integration-suite/blob/main/docs/apim/API-Management/policies-7e4f3e5.md[Policies] and https://github.com/SAP-docs/btp-integration-suite/blob/main/docs/apim/API-Management/flow-08b40d9.md[Flow]

The grouping into four rows is this page's own reading aid; SAP lists the policies in one alphabetical list.

== A request through the proxy

The figure follows a call to a proxy that carries three policies in the ProxyEndpoint PreFlow, in this order: Verify
API Key, Spike Arrest, Quota. Putting the key check first means that an unknown caller is rejected before it uses up
any rate or quota allowance. That order is a design choice made for this example; SAP's pages do not prescribe it, but
they say the policies of a flow run in the order applied and that security and quota policies belong in the PreFlow.

[mermaid]
----
flowchart LR
    C["Client app sends a request with an API key"] --> V["PreFlow: Verify API Key"]
    V -- "key unknown" --> E1["Error response, backend never called"]
    V -- "key valid" --> S["PreFlow: Spike Arrest"]
    S -- "too fast" --> E2["Error response"]
    S -- "rate ok" --> Q["PreFlow: Quota"]
    Q -- "limit used up" --> E3["Error response"]
    Q -- "allowed" --> T["TargetEndpoint calls the backend"]
    T --> B[("Backend service")]
    B --> R["Response flow and PostFlow, for example logging"]
    R --> C
----

Source: https://github.com/SAP-docs/btp-integration-suite/blob/main/docs/apim/API-Management/flow-08b40d9.md[Flow] and https://github.com/SAP-docs/btp-integration-suite/blob/main/docs/apim/API-Management/api-proxy-8962643.md[API Proxy]

In words: the client's request enters the ProxyEndpoint, where each PreFlow policy gets a turn. A failing policy
produces an error response and the request stops there, so the backend never sees a rejected call. Only a request that
passes all three reaches the TargetEndpoint, which forwards it to the backend. The answer travels back through the
response flow, where a PostFlow policy can write a log entry.

== Securing an API

Security policies decide who gets in. The documentation describes the Verify API Key policy as one mechanism to prevent
unauthorized access to APIs exposed over the internet. API Management generates API keys on behalf of applications and
lets providers view and approve them; the policy then checks the key at runtime, so no application reaches the protected
API without a valid one. Its one required setting is where to find the key, given as a reference to a flow variable, for
example `request.header.apikey` for a key sent in an HTTP header or `request.queryparam.key` for a key in the query
string.

An API key identifies an application but does not prove which user is behind it. For that, the OAuth v2.0 policies check
and issue access tokens, and Basic Authentication checks a user name and password. SAP's grant types page lists the
grant types that the service supports, and the designing OAuth v2.0 policies topic describes the policy set. This page
does not repeat them; the token flows themselves are explained in the OAuth section of this site, and what an access
token carries is covered in xref:erp/sap/btp-security-xsuaa-and-identity.adoc[BTP Security: XSUAA and Identity].

Source: https://github.com/SAP-docs/btp-integration-suite/blob/main/docs/apim/API-Management/verify-api-key-4d15a04.md[Verify API Key], https://github.com/SAP-docs/btp-integration-suite/blob/main/docs/apim/API-Management/security-f1f997c.md[Security] and https://github.com/SAP-docs/btp-integration-suite/blob/main/docs/apim/API-Management/oauth-2-0-grant-types-308a18a.md[OAuth 2.0 Grant Types]

== Controlling traffic: Spike Arrest and Quota

Two policies limit how much traffic reaches the backend, and they answer different questions.

*Spike Arrest* protects the backend from bursts. SAP describes it as a rate limit based on the time the last matching
message was processed, not a count. Its own example: a rate of 6 messages per minute means requests can only be
submitted at one per 10 seconds, and a second request within those 10 seconds on the same API Management server is
rejected. The documentation adds that the policy is not distributed, so you may see small differences from the expected
result, and recommends using it to throttle traffic to what the backend can handle, not to limit individual clients.
The rate is written as a number with a unit, such as `30pm` for 30 per minute in SAP's sample.

*Quota* limits how many calls an application may make over a longer period. SAP's definition is the number of request
messages an application can submit to an API over a given period such as an hour, a day or a month. API Management keeps
a counter; when it reaches the limit, further calls are rejected with an error until the counter resets after the
period (or earlier through the Reset Quota policy). The time unit is one of minute, hour, day, week or month, and the
quota type is one of `default`, `calendar`, `flexi` or `rollingwindow`.

A rule of thumb that follows from the two definitions: Spike Arrest answers "how fast", Quota answers "how many in
total", and Spike Arrest is for the backend's protection while Quota is for fairness among consumers.

Source: https://github.com/SAP-docs/btp-integration-suite/blob/main/docs/apim/API-Management/spike-arrest-bf441dc.md[Spike Arrest] and https://github.com/SAP-docs/btp-integration-suite/blob/main/docs/apim/API-Management/quota-1f742c1.md[Quota]

== Example: the three policies of the figure

The XML below is the configuration of the three policies, written from the sample payloads in SAP's topics. Each is
one policy file that you create in the policy designer and attach to the ProxyEndpoint PreFlow, in the order of the
figure. The Quota policy takes its identifier from the Verify API Key policy, which here is assumed to be named `vap1`,
the name used in SAP's own sample.

[source,xml]
----
<?xml version="1.0" encoding="UTF-8" standalone="yes"?>
<VerifyAPIKey async="true" continueOnError="false" enabled="true" xmlns="http://www.sap.com/apimgmt">
    <APIKey ref="request.header.apikey"/>
</VerifyAPIKey>

<?xml version="1.0" encoding="UTF-8" standalone="yes"?>
<SpikeArrest async="true" continueOnError="false" enabled="true" xmlns="http://www.sap.com/apimgmt">
    <Rate>30pm</Rate>
</SpikeArrest>

<?xml version="1.0" encoding="UTF-8" standalone="yes"?>
<Quota async="false" continueOnError="false" enabled="true" type="calendar" xmlns="http://www.sap.com/apimgmt">
    <Identifier ref="verifyapikey.vap1.client_id"/>
    <Allow count="100"/>
    <Interval>1</Interval>
    <TimeUnit>day</TimeUnit>
    <StartTime>2026-11-13 00:00:00</StartTime>
</Quota>
----

Source: https://github.com/SAP-docs/btp-integration-suite/blob/main/docs/apim/API-Management/verify-api-key-4d15a04.md[Verify API Key], https://github.com/SAP-docs/btp-integration-suite/blob/main/docs/apim/API-Management/spike-arrest-bf441dc.md[Spike Arrest] and https://github.com/SAP-docs/btp-integration-suite/blob/main/docs/apim/API-Management/types-of-quota-3e32f19.md[Types of Quota]. Requires an SAP BTP account; not run here.

Reading the Quota policy: up to 100 calls per day per application key, counted from the start time of the `calendar`
type, which SAP says is explicit (the `StartTime` element is only valid for that type). The three policies are
separate files, so a real configuration has three separate policy definitions, not one document.

The caller then sends its key in the header the Verify API Key policy looks at. The host name and the base path of the
proxy are values that API Management shows after deployment; the placeholders below stand for them.

[source,shell]
----
curl -H "apikey: <your-application-key>" "https://<api-host>/<proxy-base-path>/<resource>"
----

Source: https://github.com/SAP-docs/btp-integration-suite/blob/main/docs/apim/API-Management/verify-api-key-4d15a04.md[Verify API Key]. Requires an SAP BTP account; not run here.

If the header is missing or holds an unknown key, the Verify API Key policy fails and the request ends in an error
response before the backend is called. SAP's topic states that the policy sets the flow variable `failed` to `true`
when validation fails.

== From proxy to product to developer

A proxy alone is not yet something a developer can use. SAP's model adds three more layers.

. An *API product* bundles one or more API proxies. An administrator creates it in the API Portal and can set quota
  limits on it. SAP points out that a quota on a product is not enforced by itself: the API must also carry Verify API
  Key and Quota policies, and the Quota policy then reads the product's limit through the flow variables that Verify API
  Key fills in (such as `apiproduct.developer.quota.limit`). That is why different products can allow different volumes
  through the same policy.
. An *application* is created by a developer in the Developer Hub. The developer adds products to it and receives the key
  that the Verify API Key policy checks.
. A *subscription* connects the application to a product (and to a rate plan, if the product has one).

The Developer Hub is the self-service front of this chain. SAP describes it as a feature-rich, themed and customizable
portal with API documentation and code snippets, where developers discover, subscribe to and consume APIs. A separate
administrator role approves access requests where that is configured.

Source: https://github.com/SAP-docs/btp-integration-suite/blob/main/docs/apim/API-Management/create-a-product-d769622.md[Create a Product] and https://github.com/SAP-docs/btp-integration-suite/blob/main/docs/apim/API-Management/concepts-of-api-management-ae66eba.md[Concepts of API Management]

== Analytics and monetization

API Analytics collects information on each call, such as the URL, the user identifier, and latency, and presents it in
dashboards, so an administrator sees which APIs and applications are used and how fast they answer. The Statistics
Collector policy is the documented way to record extra values from a message for the analysis.

Monetization lets an API provider earn money for use of the APIs. The administrator creates a rate plan, attaches it to a
product and publishes the product in the Developer Hub; developers add the product to an application and, depending on
usage, see their bill details. SAP delivers this through a Rate Plan Service and a Billing Service.

Source: https://github.com/SAP-docs/btp-integration-suite/blob/main/docs/apim/API-Management/monetize-apis-fcdc89b.md[Monetize APIs] and https://github.com/SAP-docs/btp-integration-suite/blob/main/docs/apim/API-Management/components-of-api-management-24f1af0.md[Components of API Management]

== Summary

* API Management is the SAP Integration Suite capability that puts a controlled front door, the API proxy, in front of a
  backend service, so callers never reach the backend directly.
* A proxy has a ProxyEndpoint for inbound calls and a TargetEndpoint for the call to the backend; policies sit in flows
  such as the PreFlow, which always runs first, and they run in the order applied.
* Verify API Key and the OAuth policies answer who may call; Spike Arrest limits the rate to protect the backend; Quota
  limits the total number of calls per period.
* An API product bundles proxies, a developer creates an application in the Developer Hub to get a key, and analytics
  and monetization build on the recorded calls.
* The policy XML and the call on this page need an SAP BTP account, so they are shown with their documentation
  sources and were not run here.
