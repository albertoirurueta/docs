= SAP HR Guide: Build an Organizational Structure Model
:description: Step-by-step guide to a small CAP teaching model (CAP Node.js 10.2) of the organizational structure of SAP HR: objects of the types O, S, C and P, relationships stored from both ends (002, 003, 007, 008, 012), an evaluation path query O-S-P, a tree page and a Fiori elements object page.
:keywords: SAP, HR, HCM, Organizational Management, OM, object type, organizational unit, position, job, person, relationship, infotype 1001, evaluation path, O-S-P, chief position, org chart, CAP, Fiori elements, step by step, guide

include::partial$ai-disclaimer.adoc[]

Checked on 2026-11-13 against CAP Node.js 10.2 (`@sap/cds` 10.2.2, `@sap/cds-dk` 10.2.1), the Fiori elements preview of `cds watch` (SAPUI5 1.145.0), curl 8.7 and Node.js 24.21.

== What you build

This is a teaching model built with CAP. It is not SAP S/4HANA or SAP SuccessFactors and does not reproduce their screens.

You build a small model of the structure that SAP Organizational Management stores: *objects* of four types (`O` organizational unit, `S` position, `C` job and `P` person) that are linked by *relationships*. Every relationship is stored twice, once from each end, as SAP does: `A003` "belongs to" from a position to its unit and `B003` "incorporates" from the unit to the position. The model checks each new relationship against its definition, refuses a second chief position for a unit and refuses a loop in the tree of units. You then ask the structure a question with an *evaluation path*, the path `O-S-P` that collects the units below a start unit, their positions and the persons who hold them, and you read the structure as a tree on a web page and as a Fiori elements object page. The model leaves out what a real system adds: validity periods for objects and relationships (the guide xref:erp/sap/human-resources/guide-model-employee-records-with-validity-periods.adoc[Model Employee Records with Validity Periods] shows that idea), tasks, the changing and deleting of objects, and every infotype of an object except its name.

image::sap-hr-guide-build-an-org-structure-model-08-result.svg["Browser page Organizational structure that draws the tree of the unit Example Trading Co.: the unit Sales with its chief position Sales Manager held by Ana Torres, the position Sales Clerk held by Ben Okoye and the position Sales Assistant marked vacant, and the unit Warehouse with the position Warehouse Clerk held by Chloe Martin",width=900]

== Before you start

* No account is needed: the CAP tools and curl install without signing in. Installing `@sap/cds-dk` means accepting the SAP Developer License Agreement, version 3.2, which the lab README names.
* Do the guides xref:erp/sap/guide-first-cap-service.adoc[Your First CAP Service] and xref:erp/sap/guide-cap-fiori-elements-app.adoc[Add a Fiori Elements App to a CAP Service] first (they explain `cds init`, CDS files, CSV data, `cds watch` and the Fiori preview). The guide xref:erp/sap/human-resources/guide-model-employee-records-with-validity-periods.adoc[Model Employee Records with Validity Periods] is the model for the style of this one.
* Read xref:erp/sap/human-resources/organizational-management.adoc[Organizational Management] for the ideas that the model copies, and xref:erp/sap/human-resources/enterprise-and-personnel-structure.adoc[Enterprise and Personnel Structure] for the other picture of a company that OM is not.
* You need curl 7.82 or newer, which has the option `--json`. `curl --version` prints the version.
* The example is the one of the HR pages: Example Trading Co. with the units `50000001` Example Trading Co., `50000002` Sales and `50000003` Warehouse, the jobs `52000001` Manager and `52000002` Clerk, the positions `51000001` Sales Manager, `51000002` Sales Clerk and `51000003` Warehouse Clerk, and the persons Ana Torres `00001234`, Ben Okoye `00001235` and Chloe Martin `00001236`, who hold those three positions in that order. The Sales Manager is the chief position of Sales. All numbers and names are invented example values, not values delivered by SAP.
* Which names come from an SAP page and which are the model's own: the object types `O`, `S`, `C` and `P`, the relationship numbers 002, 003, 007, 008 and 012, the names Reports to, Is line supervisor of, Belongs to, Incorporates, Holder and Manages, the direction letters `B002`, `A003`, `B003`, `A008` and `A012`, and the three rows of the path `O-S-P` come from the SAP Help pages Organizational Unit, Position, Subtypes of Relationships Infotype (1001) and Structural Profiles, which are listed under Sources. The direction letters `A002`, `A007` and `B007` and the names Has job, Is job of, Holds and Is managed by for the other end of 007, 008 and 012 are the model's own. So are the two rules (one chief position per unit and no loop of units), the extra position `51000004` Sales Assistant, the path `O-S-C` of the variation and the tree page. The Sales Assistant extends the example: it is a position without a holder.
* The figures are drawings of the editor, the terminal, the browser and the Fiori page, not screenshots. A highlighted box with a number marks the file, the line or the page part of the step with the same number.

== Steps

=== Create the project and model the structure

. Create a CAP project named `org-structure` and install it, as in the first guide:
+
[source,bash]
----
cds init org-structure --nodejs
cd org-structure
npm install
----
. Create `db/schema.cds`. `Objects` holds every object, told apart by its type and its ID. `RelationshipTypes` is the list of kinds of relationship: the direction letter and the number, a meaning, the object types at the two ends and the relationship that is the same link read from the other end. `Relationships` holds the links: one record per relationship and direction, as the infotype Relationships (1001) of SAP does. `EvaluationPaths` and `EvaluationSteps` hold the rows of an evaluation path.

=== Write the rules and the queries

[start=4]
. Create `srv/org-service.cds`. It exposes the five entities as an OData service and declares two functions: `evaluate` collects the objects of an evaluation path from a start object, and `tree` returns the tree of a unit.
+
[source,cds]
----
include::example$sap-lab/org-structure/srv/org-service.cds[]
----
. Create `srv/org-service.js`. The first part checks a new relationship before it is stored: the relationship must be defined, the object types must be the ones of its definition, both objects must exist, the same record must not exist already, a unit must not report to itself or to a unit below it, and a unit gets one chief position. After the record is stored, the second handler writes the same link from the other end, with the relationship that the definition names as its inverse. The second part holds the two functions. `evaluate` applies row 1 of the path to the start object and every next row to what the row before found; a row from a type to the same type, such as `O B002 O`, is followed until nothing new turns up. `tree` walks the units from the start unit, lists the positions of each unit with their holders and then the units below.

=== Start the service and read the structure

[start=6]
. In the terminal, in the project folder, start the server. The log shows the five CSV files loaded and `OrgService` served at `/odata/v4/org` with the implementation `srv/org-service.js`. If it stops with `[EADDRINUSE] - port 4004 is already in use by another server process.`, another server runs: see What can go wrong.
+
[source,bash]
----
cds watch
----
. Read the relationships that leave the unit Sales. Open http://localhost:4004/odata/v4/org/Relationships?$filter=SourceId eq '50000002'&$select=Relationship,TargetType,TargetId in the browser. There are four records: `A002` to the unit `50000001` (Sales reports to Example Trading Co.), `B003` to the positions `51000001` and `51000002` (Sales incorporates them) and `B012` to the position `51000001` (Sales is managed by the Sales Manager). OData adds `SourceType` and `SourceId`, which are part of the key. The links that point the other way, for example `A003` from the position to Sales, are records of their own, and you find them by filtering for the position.
+
image::sap-hr-guide-build-an-org-structure-model-03-sales-relationships.svg["Browser with the address of the relationships that leave the unit 50000002, marked by callout 7: the JSON response holds four records, A002 to the unit 50000001, B003 to the positions 51000001 and 51000002 and B012 to the position 51000001, so the same links that point down from Sales are stored at the other end as well",width=900]
. Ask the structure a question with the evaluation path `O-S-P`. Open a second terminal in the project folder and evaluate the path from the top unit, then from Sales and from Warehouse:
+
[source,bash]
----
curl -s "http://localhost:4004/odata/v4/org/evaluate(startType='O',startId='50000001',path='O-S-P')"
curl -s "http://localhost:4004/odata/v4/org/evaluate(startType='O',startId='50000002',path='O-S-P')"
curl -s "http://localhost:4004/odata/v4/org/evaluate(startType='O',startId='50000003',path='O-S-P')"
----
+
Each object in the answer has the number of the row that collected it in `Step`. From the top unit the answer has 9 objects: the three units in step 1 (row 1 keeps its start unit and follows `B002` down), the three positions in step 2 and the three persons in step 3. From Sales it has 5 objects (Sales, two positions, two persons) and from Warehouse 3. These are the counts that the reference page Organizational Management gives for the same example.
+
image::sap-hr-guide-build-an-org-structure-model-04-evaluate.svg["Terminal with three curl commands that evaluate the path O-S-P from the units 50000001, 50000002 and 50000003: the first answer lists 9 objects, three units in step 1, three positions in step 2 and three persons in step 3 (callout 8), the second lists 5 objects and the third 3 objects",width=900]

[start=9]

== Check the result

* The evaluation path of step 8 collects 9 objects from the top unit, 5 from Sales and 3 from Warehouse.
* Step 10 answers `HTTP/1.1 201 Created` with the message that `A003` was stored with its inverse `B003`.
* Steps 11 and 12 answer HTTP 400 with the two messages, and the evaluation of step 13 collects 6 objects from Sales.
* The object page of Sales shows *Relationships (5)*.
* The tree page shows the Sales Manager as the chief position and the Sales Assistant as vacant.

== Variations

* Define an evaluation path of your own. A path is a record, so no code changes. Create `http/new-path.json`, the path `O-S-C` with two rows, from `O` along `B003` to `S` and from `S` along `A007` to `C`, and post it. It answers `HTTP/1.1 201 Created`. Then evaluate it from Sales.
+
[source,json]
----
include::example$sap-lab/org-structure/http/new-path.json[]
----
+
[source,bash]
----
curl -s -i --json @http/new-path.json http://localhost:4004/odata/v4/org/EvaluationPaths | grep -E "^HTTP"
curl -s "http://localhost:4004/odata/v4/org/evaluate(startType='O',startId='50000002',path='O-S-C')"
----
+
The answer has 5 objects: the three positions of Sales in step 1 and the two jobs Manager and Clerk in step 2. The start unit is not in the answer, because row 1 goes from `O` to `S`, a different type, and only a row from a type to the same type keeps its start objects.
* Add `?unit=50000002` to the address of the tree page, `http://localhost:4004/tree/index.html?unit=50000002`. The page draws the tree of Sales only.

== What can go wrong

[cols="2,3,3",options="header"]
|===
|Symptom
|Cause
|Fix

|`[EADDRINUSE] - port 4004 is already in use by another server process.` when `cds watch` starts
|A server of an earlier guide still runs on port 4004.
|Press `Ctrl+C` in the terminal of that server, or start this one with `cds watch --port 4005` and use 4005 in every address of this guide.

|`Relationship A009 is not defined` and HTTP 400
|The relationship is not in `RelationshipTypes`.
|Use one of the ten kinds of the CSV file, for example `A003`.

|`Relationship A003 links S to O, not S to P` and HTTP 400
|The types of the two objects are not the ones of the definition: `A003` runs from a position to a unit.
|Use the types of the definition, or another relationship such as `A008` for a person.

|`Object S 51000099 does not exist` and HTTP 400
|One end of the relationship is not an object yet.
|Create the object first, as in step 9.

|`Relationship A003 from S 51000004 to O 50000002 already exists` and HTTP 400
|You posted the same relationship twice, for example step 10 a second time.
|The record is stored already. Start `cds watch` again to get the starting data back.

|`Entity "Objects" is not deletable` and HTTP 405
|You sent a DELETE (a PATCH gets HTTP 405 as well). The model only adds objects and relationships.
|Leave the structure as it is, or restart `cds watch` to get the starting data back.

|`The evaluation path O-S-X is not defined` and HTTP 404
|The path name is not in `EvaluationPaths`.
|Use `O-S-P`, or create the path as in the variation.

|`The path O-S-P starts at O objects, not at S objects` and HTTP 400
|The start object is a position, but row 1 of the path starts at units.
|Start the path at a unit.

|`Object O 59999999 does not exist` and HTTP 404
|The start object of `evaluate` does not exist.
|Use a unit of the example, for example `50000001`.
|===

== Clean up

Press `Ctrl+C` in the terminal that runs `cds watch`. The database lives only in memory, so the position and the relationships of steps 9 and 10 are gone at the next start; the CSV files bring back the starting data.
