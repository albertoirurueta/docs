= Employee Central to SAP S/4HANA Integration
:description: How employee data and the organizational structure travel from SAP SuccessFactors Employee Central to SAP S/4HANA in the core hybrid model (the ECS4HCM add-on with SAP Cloud Integration for on premise and Private Edition, SAP Master Data Integration for Public Edition), for SAP SuccessFactors 2H 2026 and SAP S/4HANA 2025 FPS02.
:keywords: Employee Central, SAP S/4HANA, core hybrid, ECS4HCM, SFSF EC S4 HCM INTEGRATION, SAP Cloud Integration, integration flow, staging area, Data Replication Monitor, Compound Employee API, organizational assignment, organizational object, Business Integration Builder, transformation template group, full transmission start date, push replication, SAP Master Data Integration

include::partial$ai-disclaimer.adoc[]

In a company that keeps its people data in the cloud (SAP SuccessFactors Employee Central) but still runs payroll or time
management in SAP S/4HANA, the two systems must agree on who works there. This page explains how SAP copies the data
across: which pieces take part, what each piece does, how a change made by an HR administrator in the cloud ends up in a
personnel record in SAP S/4HANA, and how an administrator checks that it worked. After reading it you can follow a
replication from start to finish and name the monitor to open when something fails. It is written against SAP SuccessFactors
release 2H 2026 (2611) and SAP S/4HANA 2025 FPS02. It applies to SAP S/4HANA on premise and Private Edition with the
add-on described here. For SAP S/4HANA Cloud Public Edition the documentation points to a different service, SAP Master
Data Integration, which the last sections explain.

Every step in this page that touches Employee Central needs a tenant (a company's own SAP SuccessFactors instance) and an
account on it, and every step in SAP S/4HANA needs an SAP system with the add-on. Nothing on this page was run: it is
read from the SAP Help Portal and described.

== Key terms

* xref:erp/sap/human-resources/glossary.adoc#core-hybrid[Core hybrid]: Employee Central holds the core HR data while SAP S/4HANA runs payroll or time management.
* xref:erp/sap/human-resources/glossary.adoc#employee-central[Employee Central]: the core HR application of SAP SuccessFactors, here the source of the data.
* xref:erp/sap/human-resources/glossary.adoc#system-of-record[System of record]: the system whose copy of a fact is the one to trust and to change.
* xref:erp/sap/human-resources/glossary.adoc#replication[Replication]: copying data from one system to another, here regularly and in one direction.
* xref:erp/sap/human-resources/glossary.adoc#middleware[Middleware]: software between two systems that receives messages from one, transforms them and hands them to the other.
* xref:erp/sap/glossary.adoc#cloud-integration[Cloud Integration]: the capability of SAP Integration Suite that runs the integration flows used here.
* xref:erp/sap/human-resources/glossary.adoc#compound-employee-api[Compound Employee API]: the SOAP interface of Employee Central that returns an employee's data bundled in one message.
* xref:erp/sap/human-resources/glossary.adoc#staging-area[Staging area]: a holding table in SAP S/4HANA where received data waits before it is written into infotypes.
* xref:erp/sap/human-resources/glossary.adoc#replication-request[Replication request]: one entry in the staging area, created for one employee when a run brings new or changed data.
* xref:erp/sap/human-resources/glossary.adoc#organizational-assignment[Organizational assignment]: the fact that an employee belongs to a position, a department, a cost center or a manager.
* xref:erp/sap/human-resources/glossary.adoc#organizational-object[Organizational object]: a unit, job or position of the company structure, as opposed to an employee.
* xref:erp/sap/human-resources/glossary.adoc#business-integration-builder[Business Integration Builder]: the Customizing area where the field mapping between Employee Central and SAP S/4HANA is defined.
* xref:erp/sap/human-resources/glossary.adoc#transformation-template-group[Transformation template group]: a named bundle of the field mappings used by one replication scenario.
* xref:erp/sap/human-resources/glossary.adoc#full-transmission-start-date[Full transmission start date]: the date from which data is replicated.
* xref:erp/sap/human-resources/glossary.adoc#personnel-number[Personnel number]: the number under which SAP S/4HANA stores one employment.

== The example used on this page

The page follows the made-up business of this section, Example Trading Co. (company code `EX01`). Ana Torres (personnel
number `00001234`, Sales Manager, hired 01.03.2024) is maintained in Employee Central. Ben Okoye (`00001235`, Sales Clerk,
hired 01.09.2024) works in her department. SAP S/4HANA needs both of them to run payroll, as in the March 2026 payslip of
Ana in the xref:erp/sap/human-resources/payroll-process.adoc[payroll process]. All codes and values are invented for this
site; none is an SAP-delivered value. The question the page answers is: Ana is hired in Employee Central, so how does her
record, with her position, department and manager, reach SAP S/4HANA?

== Where the integration sits: deployment options

SAP's integration guide names two deployment options for companies that keep SAP S/4HANA next to SAP SuccessFactors.

[cols="1,3,3",options="header"]
|===
|Option |What runs where |Data that must be copied

|Core Hybrid HCM
|Employee Central is the system of record for HR data. Processes such as payroll, time management or custom processes still run in SAP S/4HANA.
|The HR data kept in Employee Central must be replicated to SAP S/4HANA to support those local processes.

|Full Cloud HCM
|All HR processes run in SAP SuccessFactors, which is the system of record for all HR data. Processes that are not HR, such as financials or project management, stay in SAP S/4HANA.
|Some of those processes need HR data, so part of it, for example the so-called mini master, is replicated to SAP S/4HANA.
|===

Source: https://help.sap.com/docs/SAP_SUCCESSFACTORS_EC_S4_HCM_INTEGRATION/ff6b495d894a4685accf7e4bfa75da1b/c56c1ce862a24829a7fe9ef74f9790d1.html[Deployment Options Available for Integration with SAP S/4HANA (SAP Help Portal)]

The rest of this page is about the first row. The guide says that the core hybrid option covers data integration between
Employee Central and SAP S/4HANA and supports processes that span both systems, such as a new hire, an international
transfer or a global assignment. In the core hybrid option the guide lets you keep payroll and time management in SAP
S/4HANA, use Employee Central as the system of record for employee master data and organizational data, replicate the
employee data (and the organizational structure when it is needed in SAP S/4HANA, for example to run payroll), and show
SAP S/4HANA screens such as the salary statement in the Employee Central user interface.

== The parts and the figure

The replication has steps in three systems: SAP S/4HANA, the cloud middleware SAP Cloud Integration, and Employee Central.
The middleware is described in xref:erp/sap/integration-suite-and-business-accelerator-hub.adoc[SAP Integration Suite and the Business Accelerator Hub]:
an integration flow (often shortened to iFlow) is the unit that receives a message, transforms it and sends it on.
SAP delivers the flows used here in integration packages, which an administrator copies from the catalog into the
customer's own workspace in SAP Cloud Integration and then configures.

Read the figure from the right. SAP S/4HANA starts a replication: a query program asks the middleware for data (a pull).
The middleware calls an interface of Employee Central, receives the data and passes it back to SAP S/4HANA, which stores

== The employee replication step by step

The following steps are those of the guide's process flow for employee master data and employee organizational
assignments, in plain words, with the names the guide uses. Everything happens on a schedule that the SAP S/4HANA
administrator defines, and requires an SAP SuccessFactors tenant and an SAP S/4HANA system with the add-on; not run here.

. The query program Create and Execute Employee Master Data and Org. Assignment Query (`ECPAO_EE_ORG_REPL_QUERY`) calls the outbound web service `getEmployeeMasterDataAndOrgAssignmentBundleReplicationQuery`. It reads the parameters set in Customizing and updates the query administration table `ECPAO_QRY_ADM`.
. The web service sends the query to the middleware, which asks Employee Central for the data through the Compound Employee API (SOAP).
. The middleware calls the inbound web service `EmployeeMasterDataAndOrgAssignmentBundleReplicationRequest` in SAP S/4HANA and passes the data in packages.
. That service stores the data as replication requests in the employee staging area. For each new request, SAP S/4HANA calls the outbound service `EmployeeMasterDataReplicationConfirmation_Out`, so that the Data Replication Monitor in Employee Central shows that requests are waiting.
. When the last package has arrived, the middleware sends a final notification. The inbound service updates the query administration tables and triggers the event `SAP_SFIOM_EE_ORGAS_RPPQ_CREATED`.
. The program Process Employee Replication Requests (`ECPAO_RPRQ_EE_PROCESSING`), scheduled with that event as its start condition, reads the staging area and creates or updates infotype records in Personnel Administration and Organizational Management, using the key mapping and the settings made in the Business Integration Builder.
. The program updates the key mapping and the application log, raises the event `SAP_ECPAO_EE_REPLICATED`, and reports for each employee whether the transfer was successful, has errors, or is still pending. The confirmation travels through the middleware to the Data Replication Monitor.

For Ana, step 3 delivers one bundle with her employment, her personal data, her job information and her organizational
assignments. Step 6 turns it into infotype records for her personnel number, for example her Organizational Assignment
(0001) record, as taught in xref:erp/sap/human-resources/infotypes.adoc[Infotypes].

Source: https://help.sap.com/docs/SAP_SUCCESSFACTORS_EC_S4_HCM_INTEGRATION/ff6b495d894a4685accf7e4bfa75da1b/c0543e190a3b4d138e89afbbb6dd17aa.html[Process Flow of Employee Data Replication from Employee Central (SAP Help Portal)]

=== Employment and personnel number

In Employee Central, a person's period of work for a legal entity is an employment. The guide says the personnel number
in SAP S/4HANA serves the same purpose. Only regular employments (type ST, standard) and global assignments (type GA)
are considered. A new employment in Employee Central results in a new personnel number in SAP S/4HANA. The guide gives
three consequences. SAP S/4HANA keeps a personnel number that a failed replication run generated, so that its limited
number ranges are not wasted. SAP recommends setting up Employee Central so that a change of legal entity is a
termination followed by a rehire with a new employment, which lets SAP S/4HANA create the matching new number. And for
an international transfer a new employment record should be created rather than reusing the old one. If Ana moved to a
second legal entity of the group, she would therefore get a second personnel number there.

Source: https://help.sap.com/docs/SAP_SUCCESSFACTORS_EC_S4_HCM_INTEGRATION/ff6b495d894a4685accf7e4bfa75da1b/402fdf343dc5416693e2d13ac944691c.html[Employment in Employee Central Compared to Personnel Number in SAP S/4HANA (SAP Help Portal)]

=== The staging area and the status of a request

The staging area separates receiving from processing, so that two different users can do the two tasks: a technical
data replication user who maintains no HR data, and a processing user who needs the authorization to edit personnel data.
SAP delivers template roles to copy for them, `SAP_HR_ECPAO_WEBSERVICES` for replication and `SAP_HR_ECPAO_PROCESSING`
for processing (see xref:erp/sap/users-roles-and-authorizations.adoc[Users, Roles and Authorizations] for roles in
general). Writing requests to the staging area triggers an event. The processing program is scheduled as a background job
registered on that event, and a periodic job picks up what event-based processing misses. During setup the staging area
is used directly: the View Employee Replication Requests transaction `ECPAO_EE_VIEWER` shows details, errors and payloads
and can simulate or run the processing of selected requests, and the Delete Employee Replication Requests transaction
`ECPAO_EE_DELETION` cleans up requests the automatic deletion does not cover.

The status of a replication request changes as follows.

[cols="3,1,1,3",options="header"]
|===
|Situation |From |To |Meaning

|A new request is stored
|none
|Open
|Waiting to be processed.

|Processing succeeds
|Open
|Successful
|The infotype records were written.

|Processing fails for a temporary reason, such as the employee's manager not yet being replicated
|Open
|Pending
|The request is retried at once; if nothing has changed it is stored as Pending.

|Processing fails for a data or configuration reason, such as an employee having more than one position or a cost center that cannot be determined
|Open
|Failed
|Someone must fix the data or the settings.

|A Pending request is not processed within three days
|Pending
|Failed
|The temporary problem did not go away.

|A new request arrives for the same employee while the old one is not yet Successful
|Open, Pending or Failed
|Outdated
|The newer request replaces it.
|===

Sources: https://help.sap.com/docs/SAP_SUCCESSFACTORS_EC_S4_HCM_INTEGRATION/ff6b495d894a4685accf7e4bfa75da1b/e61940912cfc4411b8933fbce33f9d6c.html[Using the Staging Area for Employee Replication Requests (SAP Help Portal)] and https://help.sap.com/docs/SAP_SUCCESSFACTORS_EC_S4_HCM_INTEGRATION/ff6b495d894a4685accf7e4bfa75da1b/711d47532a5b4a559c50d55369197969.html[Status Transition of Employee Replication Requests (SAP Help Portal)]

The pending case in the table is the one a newcomer meets first. For example, Ben's request would be Pending if Ben is
replicated before Ana, because his position reports to her position and her personnel number does not exist yet. Once Ana's request
is Successful, the retry succeeds.

== Organizational assignments

An employee's organizational assignments say where the employee fits in the company: which position, department, cost
center and manager. In Employee Central they are stored with the employee's employment information. In SAP S/4HANA they
are relationships between objects of Organizational Management, and the position is the central object. The guide gives
this correspondence.

[cols="2,3",options="header"]
|===
|Employee Central |SAP S/4HANA

|Position assignment
|Relationship of the employee's personnel number (object type P) to the position (object type S).

|Business unit, division and department assignments
|Relationship of the position (S) to an organizational unit (object type O).

|Job classification assignment
|Relationship of the position (S) to a job (object type C).

|Cost center assignment
|Relationship of the position (S) to a cost center (object type K).

|Supervisor assignment
|Relationship of the position (S) to the manager's position (S).
|===

By default the position is linked in the Relationships (1001) infotype with the following relationships. The guide says
that other relationships can be configured, and then their names and IDs differ.

For the example, the position Sales Clerk (`51000002`, job `52000002` Clerk, in the organizational unit `50000002` Sales) gets
the holder Ben (`00001235`), belongs to the unit Sales, is described by the job Clerk, and reports to the position Sales
Manager (`51000001`), whose holder is Ana (`00001234`). The structure itself is taught in
xref:erp/sap/human-resources/organizational-management.adoc[Organizational Management]. The example leaves out cost
centers, which the human resources part of this site does not define.

The guide adds that SAP S/4HANA can reuse position assignments when Position Management is enabled in Employee

=== Organizational objects, and which replication creates the relationships

The positions, organizational units and jobs themselves can be replicated on their own, as organizational objects. That
flow is the second row of the figure: the query program Create and Execute Organizational Object Replication Query
(`RH_SFIOM_ORG_OBJ_REPL_QUERY`) calls the outbound web service `getOrganizationalObjectReplicationQuery`, the middleware
asks Employee Central through OData APIs, the inbound services `OrganizationalObjectReplicationNotification` and
`OrganizationalObjectReplicationResponse` receive the status and the data, the data goes to a separate staging area for
organizational objects (with the key mapping applied), and the program Process Organizational Object Replication Requests
(`RH_SFIOM_PROC_ORG_STRUC_RPRQ`) writes the Organizational Management infotypes after the event
`SAP_SFIOM_ORG_STRUC_RPRQ_CREATED`.

A position relationship such as Ben's link to Sales can therefore be created by either replication. The guide says the
settings may complement each other but must never duplicate each other. Organizational assignment replication builds
the relationships from the employee's Job Information, and organizational object replication builds them from Position
Management. The guide lists as advantages of the assignment route that Job Information does not have to be synchronized to Position
Management and that the organizational hierarchy is easier to configure, and as a disadvantage that the mapping is less flexible. A mixed approach (staffed positions from Job Information, vacant ones
from Position Management) exists, but the guide does not recommend it and says it does not work for shared positions.

Sources: https://help.sap.com/docs/SAP_SUCCESSFACTORS_EC_S4_HCM_INTEGRATION/ff6b495d894a4685accf7e4bfa75da1b/1f79b036d42a4be8afdde50a249c11e8.html[Process Flow of Organizational Object Replication from Employee Central (SAP Help Portal)] and https://help.sap.com/docs/SAP_SUCCESSFACTORS_EC_S4_HCM_INTEGRATION/ff6b495d894a4685accf7e4bfa75da1b/61217f9878e84abd9a0babaff9499c1f.html[Deciding Between Organizational Assignment Replication and Organizational Object Replication (SAP Help Portal)]

== Mapping and configuration in SAP S/4HANA

The field mapping lives in Customizing for the Business Integration Builder. A transformation template group bundles the
field mappings of one scenario. To create one for employee data, the guide sends the administrator to Customizing for
the Business Integration Builder, Employee Data, Field Mapping for Employee Data Replication from Employee Central,
Define Transformation Template Group for Employee Data (view `V_ECPAO_TTG_EE`). There the group is assigned to an Employee
Central instance and given a replication direction, and the next activity, Define Field Mapping for Employee Data (view
`VC_ECPAO_MAP`), holds the mappings. The group offers the communication channels CSV file-based transfer and web
service transfer, and SAP delivers sample content for different use cases. The program Import of Metadata from Employee
Central Using XML File (`ECPAO_ECTMPL_METADATA_WRITER`) makes Employee Central fields available for mapping. Before a
go-live, the Business Integration Builder Inspection Tool (transaction `ECPAO_CHECK_TOOL`) lists configuration gaps in an
ALV list: transformation template validations, locale mappings, mandatory fields and relationships among others. All of
this requires an SAP system; not run here.

=== The full transmission start date

The full transmission start date (FTSD) is the date from which data is replicated. The guide calls the decision
important and recommends making it early in a project. It is entered as the earliest transfer date of the
transformation template groups used for employee data and for organizational objects. A country-specific FTSD (for a phased go-live)
and an assignment-specific FTSD for selected employees are optional. SAP S/4HANA always uses the general FTSD when it
queries Employee Central; if a country-specific and an assignment-specific date exist for the same personnel number, the
latest of the three dates is used for processing.

Example with made-up dates: the general FTSD is 01.01.2026, no country-specific date exists, and Ben has an
assignment-specific date of 01.03.2026. For Ben the latest of 01.01.2026 and 01.03.2026 is 01.03.2026, so records of Ben
before that date are not processed. For Ana only the general date applies, 01.01.2026.

If the date is moved into the past after data was replicated, the guide requires a full load: run both query programs
with the option Initiate Full Load selected. If it moves into the future, no full load is needed, but all changes before
the new date must have been replicated successfully.

Source: https://help.sap.com/docs/SAP_SUCCESSFACTORS_EC_S4_HCM_INTEGRATION/ff6b495d894a4685accf7e4bfa75da1b/4f679a1ade4541a08f01689c6538d866.html[Deciding on the Full Transmission Start Date for Data Replication from Employee Central (SAP Help Portal)]

== Push replication for hire, rehire and termination

Regular replication runs at the intervals the administrator schedules. For some events a wait is too long: a new hire
who needs a payroll record now. The guide offers push replication, with preconfigured content for the job events Hire,
Rehire and Termination. Employee Central sends a push notification to the middleware, the middleware calls an inbound
web service for the push notification in SAP S/4HANA with the list of employees and the template
group, and SAP S/4HANA starts the same query program as in regular replication. The remaining steps are the regular
ones. Because regular replication is based on the last modified date, pushed employees are found again by the next run,
but their data is written again only if it changed in between. Push replication needs the Push Notification package
deployed in the middleware and settings in both systems. When Ana is hired in Employee Central, a push brings her to
SAP S/4HANA without waiting for the night run. Requires a tenant and an SAP system; not run here.

Source: https://help.sap.com/docs/SAP_SUCCESSFACTORS_EC_S4_HCM_INTEGRATION/ff6b495d894a4685accf7e4bfa75da1b/a50a7edaf7f140258fba63645938d4b2.html[Push Replication of Employee Master Data and Organizational Assignments from Employee Central (SAP Help Portal)] and https://help.sap.com/docs/SAP_SUCCESSFACTORS_EC_S4_HCM_INTEGRATION/ff6b495d894a4685accf7e4bfa75da1b/0ee56d28d5ee42b2894f7f376fb28d8e.html[Push Replication Process (SAP Help Portal)]

== Replication in the other direction

The packaged integrations also include one-time data migration into Employee Central: employee data, organizational
objects and employee organizational assignments, and foundational data such as pay group, company code, pay calendar or
work schedule rules, all migrated from SAP S/4HANA. Cost centers can be replicated from SAP S/4HANA to Employee Central.
The guide says to migrate core HR data to Employee Central before regular replication to SAP S/4HANA begins. A further
package supports cross-system workflow, visualized in a worklist based on SAP BTP.

== What older books show, and what has changed

The book SAP ERP HCM: Technical Principles and Programming, 1st edition (2013), ends with a chapter on SuccessFactors
integration. It shows the Integration add-on for SAP ERP HCM and SuccessFactors BizX (version 2.0), which could be
installed on SAP ERP 6.0 or higher. Its employee data scenario copies personnel and organizational data in one direction,
from SAP ERP HCM to SuccessFactors, to support talent management, so SAP ERP HCM is the system of record. Its other
scenarios cover compensation (both directions) and recruiting. It builds the scenarios as integration flows designed with
the Eclipse tools of SAP NetWeaver PI 7.31 and lists four technical options: PI, SAP HANA Cloud Integration, custom
point-to-point solutions on the APIs, and third-party middleware.

What has changed since is the direction and the technology of the main scenario. The current integration guide for the
core hybrid model makes Employee Central the system of record and replicates from the cloud into SAP S/4HANA. It names
SAP Cloud Integration as the middleware, uses the Compound Employee API (SOAP) and OData APIs, and adds the staging area,
the Business Integration Builder and monitors that the 2013 book does not know. SAP's documentation of SAP HCM for SAP
S/4HANA still describes integration scenarios for recruiting, employee and organizational, compensation and variable pay
data in which, depending on the scenario, either system can be the system of record. Treat the 2013 chapter as history,
and read the current guides for any project.

Source: https://www.sap-press.com/sap-erp-hcm-technical-principles-and-programming_3698/[SAP ERP HCM: Technical Principles and Programming (SAP PRESS, publisher page; the consulted copy is the 1st edition)], https://help.sap.com/docs/SAP_S4HANA_ON-PREMISE/0a09147b661744fc81907d489d68a1e6/74f77a093f634e959dc5d8d5945c9dbc.html[Integration for SAP HCM for SAP S/4HANA and SuccessFactors HCM Suite (SAP Help Portal)]

== Summary

* In the core hybrid model Employee Central is the system of record and SAP S/4HANA receives a copy to run payroll or time management.
* For SAP S/4HANA on premise and Private Edition the add-on ECS4HCM and SAP Cloud Integration do the replication; for Public Edition SAP points to SAP Master Data Integration, which replicates only the workforce person.
* SAP S/4HANA pulls the data: a query program asks the middleware, the middleware reads Employee Central, and the data lands in a staging area before a processing program writes the infotypes.
* A replication request is Open, then Successful, Pending (retried, Failed after three days), Failed or Outdated.
* Organizational assignments become relationships of the position in Organizational Management; organizational objects have their own replication and the two must not create the same relationship twice.
* The full transmission start date, the personnel number per employment and the monitors (Data Replication Monitor, staging area viewer, application log) are the practical points of a project.
