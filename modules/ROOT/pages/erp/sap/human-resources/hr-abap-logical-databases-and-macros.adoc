:description: How classic ABAP reports read HR master data through the logical databases PNP and PNPCE with NODES, INFOTYPES, GET PERAS, PROVIDE and the HR macros, with a complete report that lists the basic pay of Ana Torres, for SAP S/4HANA 2025 FPS02 on premise and Private Edition with SAP HCM for SAP S/4HANA.

include::partial$ai-disclaimer.adoc[]

Most programming in modern ABAP reads data with a SELECT statement. HR reports are different. For decades the standard way
to write a report on employee data has been to attach the report to a logical database, a ready-made program owned by SAP
that picks the employees, checks the authorizations of the user, reads the infotype records and then hands one employee at
a time to your report. Your report mainly says which infotypes it wants and what to do with each employee. A newcomer
meets this the first time somebody asks for "a small report on salaries" and the existing HR reports turn out to read
their data with a `GET` statement instead of a `SELECT`. This page explains the two HR logical databases PNP and PNPCE, the
statements `NODES`, `INFOTYPES`, `GET` and `PROVIDE`, the HR macros, and then builds one complete report that lists the
basic pay of Ana Torres, the featured employee of Example Trading Co. Later pages of this section reuse that report. The
page is written for classic ABAP in SAP S/4HANA 2025 FPS02 on premise and Private Edition with SAP HCM for SAP S/4HANA
(H4S4), a separately licensed component. It covers classic ABAP only, and SAP SuccessFactors has a different data model
that other pages cover.

== Key terms

* xref:erp/sap/human-resources/glossary.adoc#logical-database[Logical database]: a program owned by SAP that reads a tree of tables and passes the rows to a report one by one; obsolete in general ABAP, still the standard way of reading HR master data in reports.
* xref:erp/sap/human-resources/glossary.adoc#pnp[PNP]: the logical database for HR master data, time data and payroll, which raises one event per personnel number.
* xref:erp/sap/human-resources/glossary.adoc#pnpce[PNPCE]: the enhanced version of PNP that also understands concurrent employment, one person with several personnel numbers.
* xref:erp/sap/human-resources/glossary.adoc#concurrent-employment[Concurrent employment]: one person who holds several employment contracts at the same time, each with its own personnel number.
* xref:erp/sap/human-resources/glossary.adoc#personnel-assignment[Personnel assignment]: one employment of a person, identified by a personnel number.
* xref:erp/sap/human-resources/glossary.adoc#evaluation-period[Evaluation period]: the date range on the selection screen that says which records the report is interested in, held in the fields `PN-BEGDA` and `PN-ENDDA`.
* xref:erp/sap/human-resources/glossary.adoc#infotype[Infotype]: a record type of the HR master data, such as Basic Pay (0008).
* xref:erp/sap/human-resources/glossary.adoc#personnel-number[Personnel number]: the number that identifies one employee and under which all infotype records are stored.
* xref:erp/sap/human-resources/glossary.adoc#time-constraint[Time constraint]: the rule that says how many records of an infotype may be valid at one time.
* xref:erp/sap/human-resources/glossary.adoc#hr-macro[HR macro]: a piece of ABAP code that SAP defines once and that expands in each report that uses it, such as `RP_PROVIDE_FROM_LAST`.

== Why HR reports still use logical databases

The ABAP Keyword Documentation says that logical databases should no longer be used, because they rely on global data
shared between programs, on implicit calls of subroutines and on event control, which does not fit modern concepts. It
adds that no new logical database should be created and that a global class that provides a service should be used
instead. The same documentation says that the function module `LDB_PROCESS` can access existing logical databases, also
from a method. For general ABAP that settles the matter, and the page on xref:programming-languages/abap/obsolete-language-elements.adoc[obsolete language elements] of this site lists the
statements involved.

HR is the exception that the same documentation names. It says that in executable programs associated with the special
logical databases PAP, PCH, PNP and PNPCE of the HR component, the statement `INFOTYPES` is still required, and that
PNPCE is by far the most important of the four. The documentation does not give a reason for the exception, and this page
does not guess one. What the SAP Help pages for HR do show is what the logical database does for the report:

* It reads the personnel numbers that match the selection screen and hands them over one by one.
* It performs the standard authorization checks for every infotype record that the report requests with the `INFOTYPES`
  statement, namely the authorization objects HR: Master Data (`P_ORGIN`) and HR: Master Data - Extended Check
  (`P_ORGXX`), and the structural authorization check.
* It provides the standard HR selection screen, which a report category can extend with more fields, and the same
  logical database underlies the reports of SAP Query for HR.

A report on employee data therefore gets selection, authorization and reading without writing any of it. The price is
the event style of programming that the next sections explain. Everything below is classic ABAP: `INFOTYPES` is
forbidden in classes, so these reports are executable programs and not class-based code.

== PNP and PNPCE

SAP Help says that the general logic of PNPCE corresponds to the logic of PNP, and that PNPCE can also process the concept
of concurrent employment. In a system in which concurrent employment is active, reports are executed by the PNPCE logical
database. The two databases therefore share the idea and differ in how far they look:

[cols="2,3,3",options="header"]
|===
| | PNP | PNPCE

| Unit of processing
| One personnel number at a time, with the event `GET PERNR`.
| One personnel number at a time inside a person, with the event `GET PERAS`. Two more events exist for a whole person
(`GET PERSON`) and for a group of personnel numbers (`GET GROUP`).

| Records provided by default
| All records of the infotype, whatever their dates.
| Only the records that fall into the evaluation period of the selection screen.

| Selection screen
| The standard HR selection screen.
| Corresponds to the PNP screen only in a few fields; it adds the fields that concurrent employment needs and offers
selection IDs, which only PNPCE has.

| Used for
| Reports in systems without concurrent employment, and payroll evaluation reports, which SAP Help sets up on PNP with
the payroll selection screen (version 900).
| Reports in systems with concurrent employment, and the logical database of SAP Query for such systems.
|===

Two statements of this table come from different pages and need a word. The keyword documentation says that the table
declared by `INFOTYPES` is filled with the event `GET pernr` when no addition is given, and does not mention `GET PERAS`.
The sample report that SAP publishes on the SAP Help Portal for reading payroll results with PNPCE, and the book
described later on this page, declare the node `PERAS` and use `GET PERAS`. This page follows the sample, and the reader
confirms the node names of the logical database in the structure view of the Logical Database Builder, transaction `SE36`,
before relying on them, because the nodes of a logical database are defined there.

In the Ana example the three events nest like this:

[mermaid]
----
flowchart TD
    SEL["Selection screen: personnel number, evaluation period"] --> RD["Logical database selects and authorizes the personnel numbers"]
    RD --> PERSON["GET PERSON, once per person (optional)"]
    PERSON --> GROUP["GET GROUP, once per group of personnel numbers (optional)"]
    GROUP --> PERAS["GET PERAS, once per personnel number: infotype tables are filled"]
    PERAS --> CODE["Your code: PROVIDE, WRITE and so on"]
    CODE -->|"next personnel number"| PERAS
    CODE -->|"no more personnel numbers"| END["END-OF-SELECTION"]
----

The flow of events GET PERSON and GET GROUP is drawn from the concept coverage of the book, because the keyword
documentation names only the events and the additions that trigger them. Source for the events and additions:
https://help.sap.com/doc/abapdocu_751_index_htm/7.51/en-us/abapinfotypes.htm[INFOTYPES (ABAP Keyword Documentation 7.51)];
for PNPCE in S/4HANA:
https://help.sap.com/docs/SAP_S4HANA_ON-PREMISE/c6c3ffd90792427a9fee1a19df5b0925/bc2ee153038a424de10000000a174cb4.html[Reporting for Concurrent Employment (SAP Help)];
for the node and event names in a PNPCE report:
https://help.sap.com/docs/SUPPORT_CONTENT/abap/3353526376.html[Payroll Results Using Classes (SAP Help Portal, sample report)].

== Declaring the data: TABLES, NODES and INFOTYPES

A report attached to a logical database has four declarations in its global part.

. The logical database is chosen in the attributes of the report. SAP Help says to enter PNPCE in the Logical Database
  field when you create a program for concurrent employment mode.
. `TABLES pernr.` declares the interface structure `PERNR` of the HR logical database. Only the field `PERNR-PERNR` should
  be read from it: SAP Help says that the other fields are meant for internal use.
. `NODES peras.` declares the work area of a node of the logical database. The keyword documentation says that `NODES`
  is allowed only in the global part of executable programs associated with a logical database, and that you should use
  `NODES`, not `TABLES`, for the nodes of a logical database. The sample report mentioned above declares
  `NODES: PERSON, PERAS.` together with `TABLES: PERNR.`
. `INFOTYPES 0008.` declares one infotype. The statement creates an internal table with the structure `P0008` and a
  header line, and, by default, it tells the logical database to fill that table for every personnel number. It is
  forbidden in classes and must stand in the global part before the first operational statement.

The `INFOTYPES` statement has additions, and the keyword documentation describes them as follows:

[cols="2,5",options="header"]
|===
| Addition | Effect

| `NAME name`
| Uses a name of up to 20 characters for the table instead of `P0008`.

| `OCCURS n`
| Sets the initial memory of the table to `n` rows instead of ten.

| `MODE N`
| The table is not tied to the logical database and is not filled by the `GET` events, so the report reads the data itself.

| `AS PERSON TABLE`
| PNPCE only. The table is filled at the event `GET group`, with the records of all personnel numbers of the group.

| `AS PERSON TABLE` with `MODE P`
| PNPCE only. The table is filled at the event `GET person`; no authorization check is made and the evaluation period is
ignored.

| `VALID FROM intlim1 TO intlim2`
| Uses other fields of the infotype as the implicit interval limits of the short form of `PROVIDE`, instead of `BEGDA`
and `ENDDA`.
|===

The table of an infotype may hold several rows, one per record, because an infotype keeps its history. For Ana, `P0008`
holds her records for the evaluation period, so the report needs a way to look at the records one validity period at a
time. That is the job of `PROVIDE` and of the macros later on this page.

== The PNPCE selection screen and the evaluation period

A report on PNPCE shows the standard HR selection screen. SAP Help describes it as a screen with selection fields arranged
in group boxes by content, with the same structure for all HR reports, so that the reports look alike and offer similar
functions:

* Further selections, to add fields that the screen does not show, or to remove fields that you do not need.
* Search helps, to find employees when you know only some data.
* Sort, to set the order of the output list before the run.
* Org. structure, to run the report for employees of chosen organizational units and the units below them.
* Multiple selection and selection options, to enter several values, ranges or exclusions, for example a personnel
  number greater than 1000.
* Selection IDs, available for PNPCE only, which call selections for persons that were defined in Customizing.
* Report variants, which store the values you entered so that you can reuse them.

For Ana, the selection is the personnel number `00001234` and the evaluation period 01.03.2026 to 31.03.2026, March 2026,
the month of her example payslip. The selection screen puts the two dates into the fields `PN-BEGDA` and `PN-ENDDA`, and
the report reads them in `PROVIDE` and in the macros.

Which records the logical database hands over depends on the database and on the macros of the report:

* PNP provides all records of an infotype by default. PNPCE provides only the records that fall into the evaluation
  period.
* The keyword documentation names the macros `RP_SET_DATA_INTERVAL`, `RP_SET_DATA_INTERVAL_INFTY` and
  `RP_SET_DATA_INTERVAL_ALL` for setting the validity period of the records to provide, and, for PNPCE,
  `PNP_SET_INFTY_MODE_BY_NAME` and `PNP_SET_INFTY_MODE_BY_NUMBER` for changing the mode of an infotype table while the
  program runs.
* SAP Help describes `RP_SET_DATA_INTERVAL` with three input parameters, the infotype, the start and the end of the time
  interval, and no output. Its page says to use the macro at the event `INITIALIZATION`, while another page on the
  authorization check describes it for the time of `START-OF-SELECTION`, so the event is confirmed in the system
  before use.

== Looking at one record: PROVIDE and the macros

After `GET PERAS`, the table `P0008` holds the records of one personnel number. Three tools turn those rows into one
record at a time.

=== PROVIDE

`PROVIDE` is a loop over intervals. The keyword documentation describes the long form as a table iteration across several
internal tables, controlled by the interval limits of their rows. Every table needs two columns of the same data type
that hold the lower and upper limit of a closed interval, intervals within a table must not overlap and must be sorted
in ascending order, and the loop runs once for every interval that results when the limits of all involved tables divide
the interval given after `BETWEEN`. In each pass the work area holds the row that is valid in that interval, and the
interval limits of the work area are set to the limits of the current interval. If two neighboring intervals of one table
touch without a gap and the listed components have the same content, they are merged into one. The long form is allowed
in classes and raises the handleable exceptions `CX_SY_PROVIDE_INTERVAL_OVERLAP` and `CX_SY_PROVIDE_TABLE_NOT_SORTED`.

For HR reports the interesting form is the obsolete short form, which the documentation says is intended exclusively for
internal tables of HR infotypes declared with `INFOTYPES`. It uses the header line of the table as work area, takes the
interval columns from the declaration (for an infotype, `BEGDA` and `ENDDA`), creates a flag named `P0008_VALID` for each
table, and does not fill `sy-subrc` or `sy-tabix`. The keyword documentation says that no condition can be specified in
the short form, while the SAP Help pages for HR show a `WHERE` condition on `PROVIDE` for infotype tables, as the join
below does. The example report of this page uses no condition. The short form looks like this:

[source,abap]
----
PROVIDE * FROM p0008 BETWEEN pn-begda AND pn-endda.
  " one pass per interval in which a record of infotype 0008 is valid
ENDPROVIDE.
----

Requires an SAP system; not run here. The fragment shows the syntax of the HR short form as it appears in the SAP Help
examples; it is not a report by itself.

Source:
https://help.sap.com/doc/abapdocu_751_index_htm/7.51/en-us/abapprovide_obsolete.htm[PROVIDE - Short Form (ABAP Keyword Documentation 7.51)],
https://help.sap.com/doc/abapdocu_751_index_htm/7.51/en-us/abapprovide.htm[PROVIDE (ABAP Keyword Documentation 7.51)],
https://help.sap.com/docs/SAP_S4HANA_ON-PREMISE/c6c3ffd90792427a9fee1a19df5b0925/cca1e2539c70424de10000000a174cb4.html[Report Structure (PA-PAD) (SAP Help)]

SAP Help also shows a join of two infotypes: with `+PROVIDE * FROM P0001 * FROM P0006 BETWEEN PN-BEGDA AND PN-ENDDA+` you get
one pass for each partial period in which both records are valid, and the flags `P0001_VALID` and `P0006_VALID` tell you
which infotype has data in the current pass. SAP Help adds two rules: infotypes with time constraint 3 cannot take part,
because their records overlap, and an infotype with subtypes must be limited to one subtype with a `WHERE` condition,
because the records of the subtypes overlap. For the Basic Pay infotype this is a reminder rather than a problem in the
example, because Ana has only one valid record at a time.

=== RP_PROVIDE_FROM_LAST and RP_PROVIDE_FROM_FIRST

Often a report needs only the newest record of the period, not every interval. SAP Help offers a macro for it. The macro
`RP_PROVIDE_FROM_LAST` is called with four parameters and, in SAP Help's words, places the last entry of the period in
the header line of the infotype table:

[cols="1,4",options="header"]
|===
| Parameter | Meaning

| `inftytab`
| The infotype table, for example `P0008`.

| `subty`
| The subtype you want, or `SPACE` for none.

| `beg`
| The start of the period, usually `PN-BEGDA`.

| `end`
| The end of the period, usually `PN-ENDDA`.
|===

After the call, `PNP-SW-FOUND` is `1` if a matching record was found and `0` if not; in the second case the header line is
cleared. SAP Help states the prerequisites: the start of the period is not after its end, the table is sorted ascending,
and the macro is helpful only for an infotype or subtype with time constraint 1 or 2, because it returns just one record.
For the first record of the period, SAP Help describes `RP_PROVIDE_FROM_FIRST` on a page that titles the macro
`RP_PROVIDE_FROM_FRST`. Two spellings therefore occur in SAP Help, and the one that exists in your system is found by
looking it up in the system. The macro pages speak of the logical databases PNP and PAP, while the PNPCE logic corresponds
to that of PNP, so a report that uses the macro under PNPCE is tested once in the system.

An official example reads the Organizational Assignment (0001) and rejects the personnel number when it is missing:

[source,abap]
----
TABLES pernr.
NODES peras.
INFOTYPES 0001.

GET peras.
  rp_provide_from_last p0001 space pn-begda pn-endda.
  IF pnp-sw-found = '1'.
    WRITE: / peras-pernr, p0001-stell, pn-begda, pn-endda.
  ELSE.
    REJECT.
  ENDIF.
----

Requires an SAP system; not run here. The example follows RPDEMO02 of SAP Help, which uses `GET PERNR` and `PERNR-PERNR`
with PNP, and is adapted to the PNPCE event and node. `REJECT` leaves the current event block and makes the logical
database continue with the next personnel number. The keyword documentation marks it as part of the obsolete logical
database statements.

Source:
https://help.sap.com/docs/SAP_S4HANA_ON-PREMISE/c6c3ffd90792427a9fee1a19df5b0925/d5a1e2539c70424de10000000a174cb4.html[Processing a Specific Infotype Record (PA-PAD) (SAP Help)],
https://help.sap.com/docs/SAP_S4HANA_ON-PREMISE/c6c3ffd90792427a9fee1a19df5b0925/75a5e2539c70424de10000000a174cb4.html[Provide the Last Entry in the Period (SAP Help)],
https://help.sap.com/docs/SAP_S4HANA_ON-PREMISE/c6c3ffd90792427a9fee1a19df5b0925/72a5e2539c70424de10000000a174cb4.html[Provide the First Entry in the Period (SAP Help)],

=== Wage types in a repeated structure

An infotype such as Basic Pay stores its wage types as a table that is built into one record: SAP Help explains that the
line of the wage type exists as numbered fields in the structure `P0008`, so the fields are named with the numbers one to
twenty in its example. A loop evaluates one line each time, using a structure that mirrors one line, and the example in
SAP Help reads one line through the five fields `LGA`, `BET`, `ANZ`, `EIN` and `OPK`, and it writes the first two, which
hold the wage type and the amount of the line:

[source,abap]
----
DATA: BEGIN OF wagetypes,
        lga LIKE p0008-lga01,
        bet LIKE p0008-bet01,
        anz LIKE p0008-anz01,
        ein LIKE p0008-ein01,
        opk LIKE p0008-opk01,
      END OF wagetypes.

DO 20 TIMES VARYING wagetypes FROM p0008-lga01 NEXT p0008-lga02.
  IF wagetypes-lga IS INITIAL.
    EXIT.
  ENDIF.
  WRITE: / wagetypes-lga, wagetypes-bet.
ENDDO.
----

Requires an SAP system; not run here. The listing comes from the example RPABAP06 of SAP Help, shortened. The statement
`+DO ... VARYING+` is itself marked obsolete in the keyword documentation, which recommends `ASSIGN` with the addition
`INCREMENT` instead. The bound of 20 is the number in the SAP Help example. The Basic Pay page states that up to 40 wage
types can be stored for an employee, set by the feature Planned Compensation Specification (`LGMST`), so a report that must
see every line first checks how many lines the structure has in the system.

https://help.sap.com/docs/SAP_S4HANA_ON-PREMISE/c6c3ffd90792427a9fee1a19df5b0925/dea1e2539c70424de10000000a174cb4.html[Repetitive Structures (PA-PAD) (SAP Help)],
https://help.sap.com/docs/SAP_S4HANA_ON-PREMISE/4890f6fdb74a48339baba97ef3d921f0/119bc2531bb9b44ce10000000a174cb4.html[Basic Pay (Infotype 0008) (SAP Help)],

== A complete report: the basic pay of Ana

The pieces fit into one small report. It lists, for every selected personnel number, one line for each wage type of the
Basic Pay records in the evaluation period. The report name `ZEXP_BASIC_PAY_LIST` is invented for this site; the logical
database PNPCE is entered in the attributes of the program, not in the source. The listing needs an infotype, a node, an
event, `PROVIDE` and a loop, the five things the previous sections introduced.

[source,abap]
----
REPORT zexp_basic_pay_list.

TABLES pernr.
NODES peras.
INFOTYPES 0008.

DATA: BEGIN OF wagetypes,
        lga LIKE p0008-lga01,
        bet LIKE p0008-bet01,
        anz LIKE p0008-anz01,
        ein LIKE p0008-ein01,
        opk LIKE p0008-opk01,
      END OF wagetypes.

DATA line_count TYPE i.

START-OF-SELECTION.
  WRITE: / 'Personnel number', 'Valid from', 'Valid to', 'Wage type', 'Amount'.

GET peras.
  PROVIDE * FROM p0008 BETWEEN pn-begda AND pn-endda.
    DO 20 TIMES VARYING wagetypes FROM p0008-lga01 NEXT p0008-lga02.
      IF wagetypes-lga IS INITIAL.
        EXIT.
      ENDIF.
      line_count = line_count + 1.
      WRITE: / peras-pernr, p0008-begda, p0008-endda,
               wagetypes-lga, wagetypes-bet.
    ENDDO.
  ENDPROVIDE.

END-OF-SELECTION.
  WRITE: / line_count, 'wage type lines listed'.
----

Requires an SAP system; not run here. The statement forms come from the SAP Help pages named below, and the node and
event from the SAP sample for PNPCE. The currency of the amount belongs to the same record, but the page does not name its
field because no page read for it names the field, so the listing shows only the amount.

How it works, step by step:

. The logical database PNPCE reads the selection screen. The user enters the personnel number `00001234` and the
  evaluation period 01.03.2026 to 31.03.2026.
. `START-OF-SELECTION` runs once and writes the column titles. The event comes before the first `GET` event.
. For the personnel number, the logical database raises `GET peras`, after checking the authorizations of the user for the
  infotype 0008, and fills the table `P0008` with the records in the evaluation period.
. `PROVIDE` loops over the intervals. Ana's single record is valid from 01.03.2024 to 31.12.9999, and the loop passes once
  for the interval 01.03.2026 to 31.03.2026, which is the evaluation period inside the record. In the pass, the work area
  `P0008` holds the record and its `BEGDA` and `ENDDA` hold the limits of the current interval.
. The `DO` loop reads the wage type lines. The first line holds wage type `1000` with 4,000.00. The next line is empty, so
  the wage type is initial and the loop ends.
. After all personnel numbers, `END-OF-SELECTION` writes the count.

The result that follows from these rules, derived by hand and not produced by a system, is this list for the selection of
Ana alone:

[cols="2,2,2,1,1",options="header"]
|===
| Personnel number | Valid from | Valid to | Wage type | Amount

| 00001234 | 01.03.2026 | 31.03.2026 | 1000 | 4,000.00
|===

and `1 wage type lines listed` at the end. If the user selects all three personnel numbers, the same logic gives three
lines for the evaluation period March 2026: Ben with wage type `1000` and 2,400.00, and Chloe with wage type `2000` and
14.00, which is her hourly rate in the example, each valid from 01.03.2026 to 31.03.2026, and the closing line says
`3 wage type lines listed`. The first column is the personnel number of the node `PERAS`, and the amounts and dates follow
the number format and date format of the user. The count is one line for Ana plus one each for Ben and Chloe, 3 in all.

=== The same report over a longer period: history

This section extends the example. Suppose Ana receives a raise to 4,200.00 EUR from 01.01.2027, as the page xref:erp/sap/human-resources/hr-data-structures-and-tables.adoc[HR Data Structures and Tables] also supposes a raise on that date without an amount. The system would end her first Basic Pay record on
31.12.2026 and add a second record that starts on 01.01.2027 and has no planned end. If the evaluation period on the
selection screen is 01.01.2026 to 31.12.2027, the same report is correct without any change, and `PROVIDE` shows its
purpose: it cuts the records to the evaluation period.

[cols="2,2,2,1,1",options="header"]
|===
| Personnel number | Valid from | Valid to | Wage type | Amount

| 00001234 | 01.01.2026 | 31.12.2026 | 1000 | 4,000.00
| 00001234 | 01.01.2027 | 31.12.2027 | 1000 | 4,200.00
|===

The first record is valid from 01.03.2024 to 31.12.2026, and its part inside the evaluation period is 01.01.2026 to
31.12.2026. The second is valid from 01.01.2027 to 31.12.9999, and its part inside the period is 01.01.2027 to
31.12.2027. The loop passes twice, once for each of the two intervals, and the last line of the report says
`2 wage type lines listed`. The table is derived by hand from the interval rule of the `PROVIDE` page and not produced
by a system. A report that calls `RP_PROVIDE_FROM_LAST` instead of `PROVIDE` would list only the later record, as it is stored
in the table, with its dates 01.01.2027 to 31.12.9999, because the macro returns one whole record and does not cut it.
That is the difference to remember when you choose between the two tools.

== Authorization and skipped personnel numbers

An HR report does not see data that the user may not read. SAP Help says that when a report cannot read some personnel
data because of missing authorization, the data of those persons is not processed at the event `GET PERNR`, and that a
note at the end of the list states the number of persons skipped. Another page describes the reason for care: when a user
may read all records of a personnel number except one, the database skips the personnel number completely, unless the
code says otherwise. Three options for reports based on PNP are described there:

* Set the variable `PNP_SW_SKIP_PERNR` to `N` at the event `INITIALIZATION`, so that the database does not skip the personnel
  number. The data that the user may not read is still not passed to the report, and the report cannot reach it.
* Use the macro `RP_SET_DATA_INTERVAL` for the time of `START-OF-SELECTION`, so that only data of the selection period is read
  and checked. SAP Help spells the macro name with two L here and `RP_SET_DATA_INTERVAL` elsewhere, so check the spelling in
  the system.
* Declare the infotype with `MODE N` and read and check the data in the report, using a function module for reading and the
  function module `HR_CHECK_AUTHORITY_INFTY` from the function group HRAC. SAP Help says this third option is always
  available and is the only way if a report needs just one subtype of an infotype and the user must not see the others.

SAP Help says that the first two options exist for PNP and are not supported for PAP, and the third option always exists. It does not say that they are
documented for PNPCE, so a PNPCE report confirms them in the system.

For the time dependency of authorizations, SAP Help describes a newer behavior for PNP and PNPCE. A new export parameter
`IS_NOT_AUTHORIZED_BY_TIME` of the standard interface of the HCM authorization check says that the user has no authorization
for a record because of the time logic of data blocking. Your own BAdI implementation sets it, and in the sample coding
delivered by SAP it is `FALSE`. If it is `TRUE`, the logical database uses a new `SUBRC` value 8. The personnel number is not
skipped unless another record has the value 4, which means no authorization to read for another reason. The record with
`SUBRC` 8 is not passed to the report, so results may be incomplete or even incorrect, which SAP Help says behaves like a
record that does not exist. The Customizing path named on that page is Personnel Management, Personnel Administration,
Tools, Data Privacy, Blocking, Employee Data, Time-Dependent Authorization Check, Applicability of Time-dependent
Authorization for HCM Reports. The simple summary for Ana: if her record in a period is blocked for the user by time logic,
the report may print fewer lines than the table `PA0008` holds, and no error appears.

== What changed with S/4HANA and H4S4

* SAP HCM for SAP S/4HANA (H4S4) needs a separate license. From SAP S/4HANA 2025 the business function for H4S4 is active
  by default, and SAP Help states that it is no longer possible to run SAP HCM in SAP S/4HANA in compatibility mode. The
  logical databases PNP and PNPCE, the `INFOTYPES` statement and the macros of this page are documented in the same SAP
  Help deliverable, so they are part of the H4S4 documentation for 2025 FPS02.
* In a system in which concurrent employment is active, SAP Help says that reports are executed by PNPCE. Whether your
  system has concurrent employment active is a setting of the system that this page does not cover.
* The time-dependent authorization check described above is a change for the logical databases PNP and PNPCE that SAP Help
  lists as a change in the logical databases.
* The keyword documentation lists logical databases as obsolete for ABAP in general and says that no new one should be
  created, while `INFOTYPES` stays required for HR reports on the special logical databases. Later pages of this
  section show how to read and write infotypes without a logical database and how to write custom HR reports.

== What older books show, and what has changed

The book SAP ERP HCM: Technical Principles and Programming, 1st edition (2013), by Dirk Liepold and Steve Ritter, covers the same ground in its chapter on reading and processing HR data. It shows a world before H4S4:

* It teaches PNP first and treats PNPCE as the enhanced logical database for systems with Management of Global Employee
  or Concurrent Employment, with the nodes `PERSON`, `GROUP` and `PERAS` and the events `GET PERSON`, `GET GROUP` and
  `GET PERAS`. This page keeps that concept and confirms the node and event with the SAP sample.
* It says that a report on PNPCE uses `GET PERAS` instead of `GET PERNR`, and that the reports run in PNP mode if the
  new events are not used. This page does not repeat the second statement because no SAP Help page read for it confirms it.
* It recommends PNPCE for new custom programs even when concurrent employment is not active. The SAP Help page for
  S/4HANA names PNPCE as the database of reports when concurrent employment is active, and does not repeat the
  recommendation, so treat it as the author's advice.
* It describes a world in which SAP ERP HCM is the HR product of the SAP Business Suite. What changed is the product:
  the same infotype and logical database concepts now belong to H4S4, which is licensed separately and no longer has a
  compatibility mode from SAP S/4HANA 2025. Another change is SuccessFactors, which is a different data model and not
  covered by these statements.

== Summary

* An HR report is usually attached to a logical database. PNPCE is the enhanced version of PNP, and the keyword
  documentation calls it by far the most important of the HR logical databases.
* The report declares `TABLES pernr`, a node with `NODES peras`, and each infotype with `INFOTYPES`, and it processes the
  records in an event block such as `GET peras`.
* `PROVIDE` loops over the intervals of an infotype within the evaluation period `PN-BEGDA` to `PN-ENDDA` and cuts the
  records to it; the macro `RP_PROVIDE_FROM_LAST` returns one whole record and suits infotypes with time constraint 1 or 2.
* The complete report of this page lists the basic pay of Ana Torres: wage type `1000` with 4,000.00 for March 2026. It
  requires an SAP system and was not run here.
* The logical database applies the HR authorization checks and may skip a personnel number, and a time-dependent blocking
  can make a record disappear without an error message.
* Logical databases are obsolete in general ABAP, and the HR reports of this page are classic ABAP.
