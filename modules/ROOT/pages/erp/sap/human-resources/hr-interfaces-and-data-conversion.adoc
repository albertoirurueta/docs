Few companies run everything in one system. A payroll provider outside the company wants the employee data, a finance system in
another client wants to check that a personnel number exists, a shop-floor tool sends hours or new hires, and a project has to
move ten years of employee history out of an old HR tool before the first payroll in SAP. Each of these is an interface or a
data conversion, and SAP HR offers a separate toolset for each. This page explains the toolsets one by one: the Interface
Toolbox, which builds export programs for a third-party system; business objects and BAPIs, which let other programs call HR
functions; Application Link Enabling (ALE) with the message type `HRMD_A`, which copies master data to another SAP system; the
interface for external HR master data, which brings data in; and the techniques of data conversion for the one-time load of
legacy data. It follows Example Trading Co. and its three employees. It is written against SAP S/4HANA 2025 FPS02 on premise
and Private Edition, where the HR functions come from SAP HCM for SAP S/4HANA (H4S4), a separately licensed component. SAP
SuccessFactors integrates through other means, which the last sections mention. After reading, you can pick the right
technique for an HR data exchange, describe how each one works, and plan the conversion order of an initial load.

== Key terms

* xref:erp/sap/human-resources/glossary.adoc#interface-toolbox[Interface Toolbox]: the HR tool, started with transaction
  `PU12`, that generates an export program and a file format for sending HR data to a third-party system.
* xref:erp/sap/human-resources/glossary.adoc#interface-format[Interface format]: the hierarchy of database, cluster, table and
  field objects that defines what the Interface Toolbox exports.
* xref:erp/sap/human-resources/glossary.adoc#change-validation[Change validation]: a function of the Interface Toolbox that
  exports only the data that changed since the last export.
* xref:erp/sap/human-resources/glossary.adoc#ale[ALE]: Application Link Enabling, SAP's technique for distributing data
  between systems with IDocs according to a distribution model.
* xref:erp/sap/human-resources/glossary.adoc#idoc[IDoc]: the structured data container, with a message type, in which ALE
  sends data from one system to another.
* xref:erp/sap/human-resources/glossary.adoc#hrmd-a[HRMD_A]: the ALE message type for HR master data and organizational data.
* xref:erp/sap/human-resources/glossary.adoc#change-pointer[Change pointer]: a log entry that records a change so that a
  periodic job can distribute it.
* xref:erp/sap/human-resources/glossary.adoc#bapi[BAPI]: a business object method meant for use from outside the system,
  implemented as a remote-enabled function module.
* xref:erp/sap/human-resources/glossary.adoc#data-conversion[Data conversion]: the one-time transfer of legacy data into the
  SAP system, as opposed to an interface that runs again and again.
* xref:erp/sap/human-resources/glossary.adoc#migration-object[Migration object]: the description, used by the SAP S/4HANA
  migration cockpit, of how one kind of business data is migrated.

== The running example: what has to move

All HR pages on this site use one fictitious business, Example Trading Co. All keys, names, numbers and dates are invented
example values chosen for this site. They are not values delivered by SAP, and a real system defines its own. Dates are
written DD.MM.YYYY, as an SAP screen shows them, and the high date is 31.12.9999.

The three employees are `00001234` Ana Torres (Sales Manager, hired 01.03.2024, employee subgroup `AA`, personnel subarea
`0001`, basic pay 4,000.00 EUR a month), `00001235` Ben Okoye (Sales Clerk, hired 01.09.2024, `AA`, `0001`, 2,400.00 EUR) and
`00001236` Chloe Martin (Warehouse Clerk, hired 15.01.2025, employee subgroup `AB`, personnel subarea `0002`, 14.00 EUR an
hour). All three belong to personnel area `EX01` and employee group `1` "Active", and the monthly payroll area is `E1`. Their
positions are `51000001`, `51000002` and `51000003` in the organizational units `50000002` Sales and `50000003` Warehouse.

This page extends the example with four stories, and says so here once. Each story uses an invented party or date:

* Example Trading Co. sends payroll data to an external provider, called Example Payroll Services, which calculates net pay. This
  is the Interface Toolbox story.
* A separate system, called here the finance client, needs to know that `00001234`, `00001235` and `00001236` exist. This is the
  ALE story.
* A small branch system records new hires and sends them to the HR system. This is the external master data story.
* Before the first payroll in SAP, the company loads its three employees from a spreadsheet kept by the old HR tool, with the
  go-live date 01.01.2026. This is the data conversion story.

== Choosing a technique

SAP Help has a page that compares the methods by task. The table rewrites its main rows in plain words.

[cols="3,3,4"]
|===
| Task | Method | What to know

| Send HR master data from SAP to an external system
| Interface Toolbox
| Any infotype, including customer infotypes. The data is converted to a file format that the receiver expects.

| Send HR master data to another SAP system
| ALE
| The standard system contains an ALE business process for some infotypes, and you can add more. The data travels in the SAP format only, without conversion.

| Bring HR master data in from an external system
| ALE or BAPIs; batch input
| SAP Help lists ALE with BAPIs and the batch input technology for this direction.

| Send payroll results to an external system
| Interface Toolbox
| You can select the tables of payroll, with extra options for wage types, for example retroactive accounting.

| Send master data and payroll results together
| Toolbox and ALE combined
| The Toolbox fills the IDocs and ALE distributes them. IDoc types that begin with `HROT` exist for North America.

| Bring wage types in from an external system
| A customer program or a BAPI, then a payroll run
| The BAPI named in SAP Help belongs to the business object `BUS7023` "Manager for External Payroll", method `InsertOutsourcer`.

| Export only what changed
| Change validation of the Toolbox, or the change display technique of ALE
| The Toolbox can compare single fields or whole records; ALE works at the level of the complete infotype record.
|===

== HR business objects and BAPIs

SAP describes its business data as business objects. A business object has methods, and a BAPI is a method that is meant to be
called from outside, from another SAP system or from a program that is not SAP software. It is implemented as a
remote-enabled function module, so it can be called with RFC. The general mechanism, including the Business Object Repository
and the commit rule, is taught on xref:programming-languages/abap/rfc-bapis-and-idocs.adoc[RFC, BAPIs and IDocs]; this
section only adds what is specific to HR.

HR has business objects of its own. The SAP Help page that compares the interface methods names one: the business object
`BUS7023` "Manager for External Payroll", whose method `InsertOutsourcer` transfers wage types from an external payroll
system into interface tables, from where a payroll run moves them into the payroll result. The ALE QuickStart for distributed
HR in the same documentation shows a second use of a BAPI: a check in a remote system. When someone saves a Cost Distribution
record (infotype 0027) for an employee in the HR system, a BAPI call to the system that owns the cost centers confirms that the
cost center exists. If the cost center is unknown there, the HR system shows an error message. For Example Trading Co., this
is how a finance client could stop Ben Okoye from being assigned a cost center that finance has never created.

Two details matter. First, the BAPI is a synchronous call: the HR system waits for the answer, which is different from an
IDoc that is sent and processed later. Second, a business object method has a fixed interface that SAP keeps stable, so an
interface that calls it survives upgrades better than one that reads HR tables directly. To find the BAPIs of an HR business
object in your system, use the Business Object Repository and the BAPI Explorer of your release; the in-system
documentation of each function module lists its parameters, and the function modules for reading and writing infotypes
from a program are in the page on xref:erp/sap/human-resources/reading-and-writing-infotypes.adoc[reading and writing infotypes]. No BAPI name is listed here except `InsertOutsourcer`,
because the names must come from the system you work in.

== The Interface Toolbox (PU12)

Suppose Example Payroll Services wants a monthly file with the employee's name, employee group and the hours and wage types
that were calculated. Nobody wants to write the extraction by hand and rewrite it when the provider changes the file layout.
The Interface Toolbox is SAP's answer: you describe what you want in a tool, and the tool generates the ABAP program that
exports it.

=== What the Toolbox does

SAP Help states that you use the Interface Toolbox to retrieve data from Human Resources for further processing in a
third-party system. That system can be an external payroll system, for example when the company runs gross payroll in SAP and
net payroll outside. The Toolbox can also work in the other direction: it can import results based on personnel numbers from
the third-party system and use them for payroll in SAP. The data comes from Personnel Administration (PA-PA), Payroll (PY),
Time Management or all three. You start the Toolbox with transaction `PU12`. In Time Management you reach it through the menu
path Time Management, Administration, Environment, Third-party payroll. In Payroll the menu path is Human resources, Payroll,
Tools, Maintenance tools, Interface Toolbox.

SAP Help gives three example scenarios: exporting master data to a third-party system, exporting master data and payroll
results, and running gross payroll in SAP with net payroll in a third-party system.

=== The interface format

The core of the Toolbox is the interface format. It is a hierarchy of objects with four levels, and the documentation gives
examples for each level.

[cols="1,2,4"]
|===
| Level | Objects | Examples from SAP Help

| 1
| Database objects
| `MDTA` for HR master data, `PCL2` for payroll

| 2
| Cluster objects
| `RX` and `RD` for payroll results, `B2` for time evaluation results

| 3
| Table objects
| `WPBP` for work center and basic pay, `P0002` for personal data

| 4
| Field objects
| `PERSK` for employee group, `ANZHL` for number
|===

In the Example Trading Co. story, the provider only needs the data of Ana, Ben and Chloe that is needed for a net calculation,
so the interface format picks the table object `P0002` (personal data) and the field object `PERSK` (employee group, which is
`1` for all three) from the master data, and the payroll tables that the provider needs from the results. SAP Help says that
you can select only the infotypes you need, or only particular fields of an infotype. The same page says that the objects of the
interface format exactly match the definition of the data exported later, so the set of export data should be arranged in the
best possible way for performance. Each object has characteristics, for example a conversion for a field object, that are
entered by the user, assigned implicitly by the Toolbox or set by the SAP system.

=== The setup steps

SAP Help splits the setup of an export interface into steps, in this order.

. Create the interface format: select the data and define how it is converted.
. Optionally define change validation, if only changed data is to be exported.
. Generate the export program from the interface format and the change validation.
. Define the file layout, which is the format of the export file, with blocks, structures and fields.
. Generate the conversion program from the file layout.

The result is an interface that you start to export and convert the data into the file format. A routine export, according to
the same documentation, is then split into three actions. You start the generated export program from the Toolbox, you
download the export files from the TemSe file to your PC or to an application server, and, if the system administrator
agrees, you transfer the data to the third-party system.

These are steps in an SAP system with HR data and the authorization to use `PU12`. Requires an SAP system; not run here.

=== Change validation

Most employee data is the same from one payroll period to the next. Ana's name does not change in March, April and May.
Sending it again every month makes the file larger and leaves the receiver to find out for itself what is new. SAP Help lists
these disadvantages of exporting everything each time: more redundancy, more transfer load, more processing, and a higher
probability of errors during export and processing at the receiver. Change validation avoids this by exporting only the data
that changed since the last export. It works on the objects of the interface format, which are table objects (internal
tables, field strings and infotypes) and field objects. Its functions are creating objects, delimiting objects, validating
single fields, key fields, relations, wage types and user-defined change validation. Wage types have special rules in change
validation.

The comparison with ALE is worth remembering. Change validation of the Toolbox can compare single fields or complete
infotype records, and it works by importing all data and comparing it with the old data, so the documentation tells you to
check performance. ALE works only at the level of the complete infotype record.

=== Converting and enriching the file

Not every receiver accepts the standard file layout. The Toolbox converts the file format of the export file to a user-defined
file format. SAP Help says you create a file layout from blocks, structures and fields, generate it together with the export
program, and then convert the file. Complicated layouts can call your own form routines. The documentation states two
conditions for such a routine: it must contain 16 parameters, and parameter 16 is the return value for the Toolbox. You can set
the first 15 parameters as input, from constants, from values of the interface format or from interface variables, and a
parameter without an entry is passed as `SPACE`. The Toolbox also has an export history for the results of earlier exports.

=== Importing wage types

When the third-party system calculates, for example, a net amount and returns results, the Toolbox offers the function Import
wage types to transfer wage types from an external system into the payroll results of the SAP system. SAP Help says the wage
types first reach interface tables, either through a customer program or through the BAPI `InsertOutsourcer` of the business
object `BUS7023`, and that a payroll run then transfers them to the payroll result. The configuration lives in the
Customizing of Cross Application Components under Predefined ALE Business Processes, Human Resources, HR External Systems,
Connection With an External Payroll System, Import Payroll Results. The wage type concept itself is explained on
the page about xref:erp/sap/human-resources/wage-types-and-payroll-results.adoc[wage types and payroll results].

== ALE with the message type HRMD_A

The finance client of Example Trading Co. wants a copy of the HR master data of its employees, so that it can check personnel
numbers, or create vendors for them. ALE is built for this: one SAP system sends an IDoc to another, according to a
distribution model that says which messages go where. The general technique is explained in
xref:programming-languages/abap/rfc-bapis-and-idocs.adoc[RFC, BAPIs and IDocs]. For HR, the message type is `HRMD_A`, and SAP
Help says it covers both HR master data and organizational data.

=== What is distributed

SAP Help sets these rules for the distribution of HR master data.

* An infotype is distributed completely, with all its fields. Texts on HR master data infotypes are not distributed.
* Filters in the distribution model decide which data goes. The message type `HRMD_A` needs a filter of the type object type
  with the value `P` (person), and one filter of the type infotype for every infotype, with the infotype number as the value.
* Entries in the table `T77TR` set an import lock for objects in the target system.
* There are two modes. In insert mode, the objects are transported completely. In update mode, which uses change pointers,
  the transported data replaces the data in the target system completely.
* The infotypes 0000, 0001, 0002 and 0003 must be distributed if HR master data infotypes are distributed at all. Infotype
  0003 is distributed by change pointers only if it changed together with one of the other supported HR master data infotypes.

SAP Help gives examples of which infotypes the receiving application needs. To check a personnel number against the HR master
record, distribute object type `P` and the infotypes 0000, 0001, 0002 and 0003. To create vendors in finance, add 0006, 0009
and 0017. To identify the sales employee, add 0006 and 0900 to the first four. For the finance client of Example Trading Co.,
which only has to confirm that a personnel number exists, the first set is enough: object type `P` and the infotypes 0000,
0001, 0002 and 0003 for each of `00001234`, `00001235` and `00001236`.

The same message type distributes Organizational Management data. All object types are distributed except those that start with
X, and the documentation names exceptions for several others, such as tasks. All Organizational Management infotypes can be
distributed except those for roles and workflow. In a distributed setup, SAP Help describes a global system that holds the
organizational structure (object types O, C and S with infotypes 1000 and 1001) and regional systems that hold the persons
(object type P with infotypes 0000, 0001, 0002, 0003 and 1001). For Example Trading Co. that would mean the units
`50000001` to `50000003`, the jobs and the positions live in the global system, and Ana, Ben and Chloe live in a regional one.

=== Rules and limits

SAP Help states several constraints that shape the design of any HR distribution.

* HR has one central SAP HR system in which all HR components are integrated. HR master data and organizational data must
  not be changed in the receiving system. The page suggests profiles with read authorization to enforce this.
* The receiving system creates the data with the same plan version as the sending system.
* If more HR master data is maintained in the receiving system, its number range intervals must differ from those of the
  sending system.
* In update mode, local Organizational Management relationships are kept in the target system.
* If you delete an object while change pointers are not active, you must also delete it manually in the target system.
* Data is saved in the target system without a dialog check.

In update mode, the target keeps replicated or locally maintained infotypes that were not changed in the sending system.
Insert mode replaces an entire object: if the target already holds a replication of it, the replication is deleted completely,
with all its infotypes, and locally maintained infotypes are lost. The documentation also describes a report, `RHALEORIGLIST`,
to find out which systems are the original systems of objects, and an `ALE_ORIGSYSTEM` column that shows the original system
in Organizational Management transactions. These belong to distributed Organizational Management, where each object has an
original system and replicas elsewhere.

== External HR master data coming in

A retail company in the SAP documentation connects stores to its headquarters: the store system records a new hire's name and
address, and the headquarters HR system receives it. SAP offers a dedicated interface for this case, and the story of Example
Trading Co. borrows it for a small branch system that records new hires. The interface consists of IDocs for the transfer,
interface tables that hold the transferred data temporarily, and a transaction for post-processing, with functions for
manual or automatic retransfer after processing and for error handling. The process works like this:

. The branch system sends an IDoc of the message type `HRSM_A`, and inbound processing saves the data in an interface table.
. The data is processed in personnel actions, according to a Customizing setting, either automatically in the background or
  manually, one employee after another. An error leaves the employee's data unsaved and writes a message in the interface
  table. In automatic mode the system goes on with the next employee.
. After a personnel action is processed, the HR system sends a confirmation of the processing status through an IDoc of the
  message type `HRSM_B`.
. Completely transferred data and defective data that cannot be processed can be removed from the interface table with the
  reorganization function.

The same validations as for online entry apply. The actions that can be run this way include hiring, organizational changes,
leaving and re-entry, and data verification and changes of basic pay. The infotypes saved automatically are Actions (0000),
Organizational Assignment (0001), Personal Data (0002), Addresses (0006) and Bank Details (0009). A hiring from a branch
system is rarely complete, because the branch does not know contract elements, so a person in HR finishes the record. You can
enhance the IDoc with customer segments whose names begin with `Z1` and process them with the enhancement `PRSM0001`.
Manual transfer starts from the menu path Tools, External human resources master data in Personnel Administration; the
screen shows the records in a tree by personnel area, with a status icon for each. SAP Help says explicitly: do not use this

== XML, files and middleware

Not every receiver speaks IDoc. Many outsourcing providers expect a plain file, and web-based partners expect XML. The Interface
Toolbox produces files, as shown above. The book SAP ERP HCM: Technical Principles and Programming, 1st edition (2013), also
shows that several of the standard HR export programs can write an XML file as an option on their selection screen, and that
a function module can be turned into a web service from the function builder, so that an external partner can call it over
the internet. The book names the programs and the menu steps; these export programs and the XML option have no topic on
help.sap.com that was found for this page, so they are in-system documentation territory. Check the selection screen and the
program documentation in your release before you plan around them.

For connections between SuccessFactors and SAP S/4HANA, the current documentation takes another route. SAP's integration guide
describes the integration of SAP SuccessFactors Employee Central with SAP HCM for SAP S/4HANA, in which employee data and
organizational objects are replicated from Employee Central to the S/4HANA system through middleware, SAP Cloud Integration.
The add-on SFSF EC S4 HCM INTEGRATION is meant for SAP S/4HANA on premise or SAP S/4HANA Cloud Private Edition, not for the
Public Edition, for which SAP points to SAP Master Data Integration. That integration replicates only the workforce person,
which is not sufficient for HR processes such as payroll. This is the core hybrid model of the
xref:erp/sap/human-resources/hr-landscape-hcm-h4s4-and-successfactors.adoc[HR landscape page].

== Data conversion: loading legacy employees

An interface runs again and again. A conversion runs once: it takes the data of an old HR tool and creates the employee
records in the new system before go-live. Because the data is personal and later drives payroll, a conversion is more careful
work than its size suggests. The book SAP ERP HCM: Technical Principles and Programming, 1st edition (2013), devotes a section
to techniques for HCM data conversion, and its advice is the basis of the order below. The concepts are old and still hold;
the tools around them have changed.

=== The tools

[cols="2,4,4"]
|===
| Tool | What it does | Status and notes

| Batch input
| Feeds the screens of an HR transaction, such as the personnel actions, with prepared values, so that every screen check runs.
| Classic technology, explained on xref:programming-languages/abap/batch-input-and-data-migration.adoc[Batch Input, Direct Input and Data Migration]. Dynamic actions that need dialog input are not processed in batch input, according to the book, so the follow-up infotypes must be loaded separately.

| Legacy System Migration Workbench (LSMW)
| A guided tool that reads, converts and imports legacy data, using batch input, direct input, BAPIs or IDocs.
| Legacy. Its documentation describes one-time transfers and only a restricted form of permanent interfaces.

| Function module from a custom program
| A program reads the legacy file and writes records through a function module that runs the checks, such as `HR_INFOTYPE_OPERATION`, around a lock of the employee.
| Documented in the system, not on SAP Help; see the page on xref:erp/sap/human-resources/reading-and-writing-infotypes.adoc[reading and writing infotypes]. Requires an SAP system; not run here.

| Mass update, transaction `HRFE_MASS_UPDATE`
| Maintains one infotype for many employees in one session, from direct entry or from an uploaded Excel file, as a direct save or as a job with an application log.
| Fits corrections after the load and repeated mass changes. It works per infotype, subtype and period, so it does not replace the hiring sequence.

| SAP S/4HANA migration cockpit
| Moves business data with predefined migration objects, from staging tables or directly from an SAP system.
| The available migration objects list contains the objects HCM - Employee, HCM - Object and HCM - Relationship, in the component `PA-PA-XX-MIG`, for the staging table approach and for direct transfer from an ERP system. Check which of them appear in your system, because the objects shown depend on the activated scope and the approach.
|===

The migration cockpit is designed for an initial load for a new implementation. SAP Help says it is not designed to keep data
in sync between systems or to establish an integration scenario. It also carries a data protection warning that applies
strongly to HR: data protection law can require that personal data is deleted once its purpose is over, and migrating
data that should have been deleted could count as processing without a legal purpose, so such data must not be migrated.
The pages xref:erp/sap/human-resources/hr-authorizations.adoc[HR Authorizations] and xref:erp/sap/human-resources/data-privacy-blocking-and-destruction.adoc[Data Privacy: Blocking and Destruction] describe the surrounding controls. Which of the classic tools a given S/4HANA release still allows is stated
in SAP Notes that need an S-user login and were not read for this page.

Source: https://help.sap.com/docs/SAP_S4HANA_ON-PREMISE/29193bf0ebdd4583930b2176cb993268/8dd142b479f9481891fa8b3f86648df3.html[Available Migration Objects], https://help.sap.com/docs/SAP_S4HANA_ON-PREMISE/29193bf0ebdd4583930b2176cb993268/7a62b59726ce42e7a10770b06940f934.html[Migrate Data Directly from SAP System], https://help.sap.com/docs/SAP_S4HANA_ON-PREMISE/29193bf0ebdd4583930b2176cb993268/87ffdbfebd504116b497c02d51ce5b58.html[Migrate Data Using Staging Tables], https://help.sap.com/docs/SAP_S4HANA_ON-PREMISE/c6c3ffd90792427a9fee1a19df5b0925/c03e5516701449cfb2e678cdb1a77125.html[Mass Update of Employee Master Data] and https://help.sap.com/docs/ABAP_PLATFORM_NEW/f6a2c35cb0dd4900ad16d735f1415331/4dafeb6ad8f66d57e10000000a42189e.html[Legacy System Migration Workbench]

=== The order of the conversion

The book's advice, restated in plain words, is to convert in dependency order: the organizational structure first, then the
employees, then the payroll history. The reason is that an employee record points at a position and a position sits in an
organizational unit, so the pointed-at objects must exist before the pointer. The table applies this order to Example Trading
Co. The go-live date 01.01.2026 is an invented example value.

[cols="1,3,5"]
|===
| Step | What is loaded | In the example

| 1
| Number ranges and Customizing checked
| External number ranges for personnel numbers and for the organizational objects are ready, the Organizational Management and Personnel Administration integration is switched on, and cost centers exist.

| 2
| Organizational structure
| Units `50000001`, `50000002`, `50000003`; jobs `52000001` Manager and `52000002` Clerk; positions `51000001`, `51000002`, `51000003`; the relationships between them, and Sales Manager as chief position of Sales.

| 3
| Employees as of their original hire date
| `00001234` Ana from 01.03.2024, `00001235` Ben from 01.09.2024, `00001236` Chloe from 15.01.2025, each through a hiring action.

| 4
| Assignment as of go-live
| Each employee is placed in the position and personnel subarea valid on 01.01.2026: Ana `51000001`, Ben `51000002`, Chloe `51000003`.

| 5
| Pay and time data
| Basic pay 4,000.00 EUR for Ana and 2,400.00 EUR for Ben; hourly rate 14.00 EUR for Chloe; planned working time and vacation entitlement of 30, 30 and 28 days.

| 6
| Payroll history and balances
| Cumulated amounts that payroll needs as of the start of the first SAP payroll period, loaded as agreed with payroll.

| 7
| Checks and test cycles
| Counts and totals compared with the legacy file, then repeated trial loads before the production load.
|===

Two points deserve attention. The book says the initial entry of an employee must be made through an action that sets the
employment status in the Actions infotype (0000), even for an employee that has left, and it proposes four customer-defined
conversion actions for hire, position assignment, inactive and termination, which are names a project chooses, not delivered
values. The book also advises disabling audit logging, called document retention in the system, for the load and enabling it
again afterward, and it advises catching the cases where dynamic actions would normally add records. Take these as project
checklist items and verify them in your release, because the book is of the 2013 edition.

A control total gives a first check that nothing was lost. The three employees give two monthly salaries: 4,000.00 EUR for Ana
and 2,400.00 EUR for Ben, a total of 6,400.00 EUR, and Chloe has an hourly rate and no monthly amount. The legacy file must
therefore show three employees and 6,400.00 EUR of monthly basic pay for the salaried staff, and the loaded data must show the
same. The sum was checked by hand and by a small script; no SAP system was involved. A real project compares many more
fields, and compares them per employee rather than only in total.

Source: https://www.sap-press.com/sap-erp-hcm-technical-principles-and-programming_3698/[SAP ERP HCM: Technical Principles and Programming (SAP PRESS, publisher page; the consulted copy is the 1st edition, the page lists the 2nd)] and https://help.sap.com/docs/SAP_S4HANA_ON-PREMISE/e1ba50d0264949f4b54e42a59ede8a5b/0b8ce0535e56424de10000000a174cb4.html[Distributed HR Master Data Procedure] (the integration of Organizational Management and Personnel Administration)

== Common mistakes

[cols="2,3,3"]
|===
| Mistake | Why it hurts | What to do

| Using the external master data interface for a legacy load
| SAP Help says not to use it for legacy data; it is built for a running connection with confirmations.
| Use the conversion tools above.

| Changing replicated data in the receiving system
| Update mode replaces transported data, and insert mode deletes the replication together with local infotypes.
| Keep the receiving system read-only for distributed HR data, with read-only authorization profiles.

| Forgetting infotypes 0000 to 0003 in the filter
| The distribution of HR master data requires them.
| Add a filter entry for each, plus object type `P`.

| Forgetting to activate change pointers
| Later changes are then not distributed, and a deleted object stays in the target.
| Activate them generally and for `HRMD_A`, and schedule `RBDMIDOC`.

| Exporting everything every month
| Larger files, more processing and a higher chance of errors at the receiver.
| Define change validation in the Interface Toolbox.

| Taking BAPI or function module names from memory or from an old book
| Names and parameters differ between releases and between the book's own listings.
| Read the interface in the system of your release.

| Loading employees before the organizational structure
| A position that does not exist cannot be assigned.
| Convert in dependency order and test with trial loads.
|===

== What older books show, and what has changed

The book SAP ERP HCM: Technical Principles and Programming, 1st edition (2013), covers this topic in two chapters, one on the
HCM interface tools and one on data conversion. The first chapter shows business objects, the Business Object Repository
browser, the BAPI Explorer, testing and calling BAPIs locally and remotely, the Interface Toolbox with its configuration,
export, export history and file layout enhancement, ALE with IDocs, and XML data interchange. The second chapter shows batch
input, recordings, the Legacy System Migration Workbench, and strategies for converting organizational and personnel data and
payroll balances. The concepts it teaches are the same in the current documentation: describe what to export, convert to the
receiver's format, send complete infotype records through ALE and convert in dependency order.

What has changed is the product and the tools around the concepts. The book describes SAP ERP HCM, not SAP HCM for SAP S/4HANA
(H4S4), which SAP says needs a separate license and which, since SAP S/4HANA 2025, can no longer run in compatibility mode.
The conversion chapter relies on batch input and LSMW, while the SAP S/4HANA documentation names the migration cockpit as the
tool for data migration, with HCM migration objects. The book's XML and web service examples predate the middleware of SAP
Cloud Integration, which the current Employee Central integration uses, and several of its export programs and menu paths are the ones for United States payroll. Instead of reading off menu paths and program names from the book, take them from the documentation and the system of
your release. SAP SuccessFactors is now a cloud alternative with different interfaces.

== Summary

* SAP HR has one toolset for each kind of exchange: the Interface Toolbox (`PU12`) generates exports for third-party systems,
  ALE with `HRMD_A` copies master and organizational data to another SAP system, the external HR master data interface
  (`HRSM_A` and `HRSM_B`) brings new-hire data in, and BAPIs give other programs a stable call.
* The Interface Toolbox starts from an interface format of database, cluster, table and field objects, generates the export
  program and the conversion program, and can export only changed data through change validation.
* An ALE distribution of HR data needs a distribution model with filters for object type `P` and for each infotype, with 0000
  to 0003 always included, activated change pointers and a periodic job; the receiving system must not change the data.
* The external HR master data interface is not for legacy data. A one-time load uses data conversion: batch input, a custom
  program, the mass update after the load, or the SAP S/4HANA migration cockpit with its HCM objects.
* Convert in dependency order: organizational structure, employees from their original hire date, assignment as of go-live,
  pay and time data, payroll history, then checks and test cycles. For Example Trading Co. the salaried control total is
  6,400.00 EUR for Ana and Ben.
* Names, menu paths and parameters come from the documentation and the system of the release, not from older books.
