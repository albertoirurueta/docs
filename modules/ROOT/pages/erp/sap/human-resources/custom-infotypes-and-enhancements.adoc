Sooner or later a business asks HR for something the delivered record types do not hold: the laptop an employee was
given, a certificate that expires, a company-specific allowance. SAP's answer is that you can create your own record type,
a customer infotype with a number from 9000 to 9999, and that you can add fields and checks to a delivered infotype
without changing SAP's code. This page explains the choices in plain words: creating an infotype with the transaction
PM01, what the system generates for you, where your own checks go, how to enhance a standard infotype, how dynamic
actions chain follow-up work, which business add-ins (BAdIs) SAP documents for HR, and how customers add their own
functions and operations to payroll and time evaluation. It is written for SAP S/4HANA 2025 FPS02 on premise and Private
Edition with SAP HCM for SAP S/4HANA (H4S4), whose documentation was read for this page. The techniques come from the
classic ABAP-based HR programming model; SAP SuccessFactors has its own extension tools, which other pages cover.

== Key terms

* xref:erp/sap/human-resources/glossary.adoc#customer-infotype[Customer infotype]: an infotype you create yourself, with a
  number from 9000 to 9999, so that an upgrade does not overwrite it.
* xref:erp/sap/human-resources/glossary.adoc#check-class[Check class]: the ABAP Objects class that holds the business
  logic and checks of one decoupled infotype.
* xref:erp/sap/human-resources/glossary.adoc#decoupled-infotype-framework[Decoupled infotype framework]: the way of
  building infotypes in which the business logic lives in classes and not in the screen program.
* xref:erp/sap/human-resources/glossary.adoc#screen-structure[Screen structure]: a dictionary structure with every field
  the user interface of an infotype shows.
* xref:erp/sap/human-resources/glossary.adoc#conversion-class[Conversion class]: a class that converts between the
  stored data and what the screen displays.
* xref:erp/sap/human-resources/glossary.adoc#ci-include[CI include]: the customer include `CI_Pnnnn` that holds your
  additional fields for a standard infotype.
* xref:erp/sap/human-resources/glossary.adoc#dynamic-action[Dynamic action]: a rule, started automatically when an
  infotype record is saved, that leads to follow-up processing.
* xref:erp/sap/human-resources/glossary.adoc#dynamic-processing-rule[Dynamic processing rule]: the successor of dynamic
  actions for the Web Dynpro ABAP master data application.
* xref:erp/sap/human-resources/glossary.adoc#badi[BAdI]: a Business Add-In, a predefined place where a customer
  implementation can replace or extend SAP's logic without modification.
* xref:erp/sap/human-resources/glossary.adoc#personnel-calculation-rule[Personnel calculation rule]: a payroll or time
  evaluation rule made of operations; functions are the building blocks of schemas.

* Personnel number `00001234`, Ana Torres, Sales Manager, hired 01.03.2024, employee subgroup `AA`, personnel subarea

== Where customer code may go

SAP documents several safe places for customer logic in HR. Which one applies depends on what you want to change.

[cols="2,3,3",options="header"]
|===
| You want to | Use | Where SAP describes it

| Store a new kind of employee data
| A customer infotype 9001 to 9999, created with transaction PM01
| SAP Help, Developing an Infotype

| Add fields or checks to a delivered infotype
| The enhancement concept: a customer include `CI_Pnnnn`, the screen structure and the BAdI in the check class
| SAP Help, Enhancing an Infotype Included in the SAP Standard System

| Change the screens of a delivered infotype in ways the enhancement concept does not cover
| A modification with customer name ranges (this is a change to SAP objects, so use it last)
| SAP Help, Modifying an Infotype Included in the SAP Standard System

| Store a new kind of organizational object data
| A customer planning infotype, created with the Personnel Planning Infotype Copier (transaction PPCI)
| SAP Help, Developing a Personnel Planning Infotype

| Start follow-up processing when a record is saved
| A dynamic action (table T588Z) in SAP GUI, or a dynamic processing rule in the Web Dynpro ABAP master data application
| SAP Help, Dynamic Actions; Dynamic Actions and Dynamic Processing Rules

| Replace the HR authorization check
| The BAdIs `HRPAD00AUTH_CHECK` (master data) or `HRBAS00_STRUAUTH` (structural authorization)
| SAP Help, Customer Enhancements

| Add your own function to a payroll schema or operation to a personnel calculation rule
| The function and operation editor
| SAP Help, Editor for Functions and Operations
|===

== Creating a customer infotype with PM01

=== What SAP says you need first

The official topic Developing an Infotype says the transaction Create Infotype (PM01) is used by customers and by SAP to
develop new infotypes. Before you start you should have finished modeling and designing the infotype, you must use
customer development packages (called development classes in the topic) for every subobject so that an upgrade does not
touch them, and you must use the number range 9000 to 9999, which is reserved for customer infotypes. A new infotype is
limited to 1000 positions in its data field structure, because the container structure that carries a record during
processing has that length.

PM01 has no help page of its own on help.sap.com. SAP Help describes it through the topics that name it, which the
references list, and the transaction's own screens and documentation (in-system documentation, transaction PM01) carry the
rest.

=== The steps

The topic Creating an Infotype lists the procedure, which this page condenses.

. Open PM01, choose the tab page Create Infotype, and choose a free number from the customer range, here `9001`.
. Say whether the infotype is for Personnel Administration (an employee infotype), for Recruitment (an applicant infotype)
  or for both. An employee infotype gets the table `PA9001`, an applicant infotype the table `PB9001`.
. Choose Generate Objects. The system offers to create the data field structure `PS9001` and takes you to the ABAP
  Dictionary.
. Enter a short description and the fields. You can type components or copy them from the `PS` structure of a similar
  delivered infotype. The topic gives the example of an emergency telephone number built from the Addresses infotype
  (0006).
. Set the enhancement category to "Can be enhanced (character-type)" (only character-type enhancement is allowed),
  check, save and activate the structure.
. Confirm the object directory entries, including the one for the screen structure, and enter a transport request.
. Write the check class by hand (the next section) and maintain the infotype characteristics (the section after it).

The system confirms that the table entry of view `T582ITVCLAS` (which links the infotype to its check class and container)
still has to be transported. The topic warns that this entry is client-dependent and exists only in the client where it
was created, so you must transport it yourself.

Requires an SAP system; not run here. The steps above are taken from the documentation and were not executed.

The same topics list what PM01 creates, so you do not build the surrounding objects yourself. For infotype 9001 the
pattern gives these objects.

| Structures `PS9001` and `P9001`

| Table `PA9001` (employee) and/or `PB9001` (applicant)

=== Where your own checks go: the check class

Under the decoupled infotype framework, the business logic of an infotype is programmed in ABAP Objects classes and not
in the module pool. The documentation lists five methods of the delivered superclass `CL_HRPA_INFOTYPE_NNNN` that you may
redefine. You must implement your checks in one or more of them, but you do not have to redefine all of them.

[cols="2,3",options="header"]
|===
| Method | Purpose

| `SPECIFIC_INITIAL_COMPUTATIONS`
| Fills default values when a record is created anew.

| `SPECIFIC_READ_COMPUTATIONS`
| Adds values to a record after it is read and before the user sees it.

| `SPECIFIC_MODIFY_COMPUTATIONS`
| Decides whether a record may be changed.

| `SPECIFIC_INSERT_COMPUTATIONS`
| Decides whether a record may be inserted.

| `SPECIFIC_DELETE_COMPUTATIONS`
| Decides whether a record may be deleted.
|===

SAP calls them computations, not checks, because a method may also fill derived values, write further records into the
buffer, or prepare updates of tables outside the `PAnnnn` name range. Three rules from the topics matter in practice.

* Write each method as if an update will be requested and as if the database will not be updated, because the buffer can
  be rolled back at any time. A user who only presses Enter makes the system run all checks and then roll the buffer back.
* Never update a table directly from a check class. Updates of tables outside the `PAnnnn` range go through the so-called
  additional update mechanism.
* The screen's PBO flows into the initial and read methods, and its PAI flows into the insert, modify and delete methods;
  there is no one-to-one mapping between screen events and methods.

For Ana's Work Equipment record, the one example check (the asset tag must not be empty) belongs in the insert and the
modify method. The default for the equipment type, if the business wants one, belongs in the initial method. This page
shows no ABAP listing for the class: the superclass methods have exact signatures that you read in the Class Builder of
your own system (in-system documentation), and a signature taken from memory could be wrong for your release.

Two more details. A simple customer infotype can inherit from `CL_HRPA_INFOTYPE_NNNN`; if the check class must write data
to the buffer, it must inherit from `CL_HRPA_INFTY_NNNN` instead. And a country-specific check class inherits from the
international one, which in turn inherits from `CL_HRPA_INFOTYPE_NNNN`; for that, the international class must not be
marked final.

=== Screen structure and conversion class

The screen structure carries every field the user sees, including fields that are derived and not stored. SAP names two
kinds: MAIN structures with single fields and LINE structures for repeating fields. The conversion class converts input
and output between the stored format and the displayed one and can control screen field attributes; applications such as
the self-service adapter and the HR administrative services call it at runtime. A conversion class uses one of two
interfaces, `IF_HRPA_UI_CONVERT_STANDARD` for the individual infotype structures or `IF_HRPA_UI_CONVERT_ADVANCED` for the
whole container. If no special conversion is needed, the default class `CL_HRPA_UI_CONVERT_BASIC` is assigned. The
assignment is stored in the view `V_T588UICONVCLAS`, and an entry there is mandatory for every screen structure; without
one the screen structure cannot be used. For `9001` the generator creates that entry for you, with the default class.

Source: https://help.sap.com/docs/SAP_S4HANA_ON-PREMISE/c6c3ffd90792427a9fee1a19df5b0925/88a7e2539c70424de10000000a174cb4.html[Structure and Task of the Screen Structure], https://help.sap.com/docs/SAP_S4HANA_ON-PREMISE/c6c3ffd90792427a9fee1a19df5b0925/d99de2539c70424de10000000a174cb4.html[Conversion Class], https://help.sap.com/docs/SAP_S4HANA_ON-PREMISE/c6c3ffd90792427a9fee1a19df5b0925/f49ee2539c70424de10000000a174cb4.html[Assigning Conversion Classes to Screen Structures] (all SAP Help, Human Resources)

=== Decoupled or not

SAP Help describes an old and a new method for creating infotypes. In the old method, the business logic lives in the
module pool next to the screens. In the new, decoupled method, it lives in the check class. PM01 creates decoupled
infotypes. SAP Help states that it is irrelevant for the maintenance transaction PA30 whether an infotype is decoupled,
because both are supported, but that newer applications (it names some self-service scenarios and the HR administrative
services) can only process decoupled infotypes. The recommendation is therefore to always create a decoupled infotype
when you create a new one. Older customer infotypes can be migrated: SAP says it is not mandatory but advisable, and that
the migration generates the screen structure and the table entries, while the infotype-specific logic must be decoupled
by hand. The page on xref:erp/sap/human-resources/reading-and-writing-infotypes.adoc[reading and writing infotypes] explains how the framework reads and writes records.

Source: https://help.sap.com/docs/SAP_S4HANA_ON-PREMISE/c6c3ffd90792427a9fee1a19df5b0925/f037df530404414de10000000a174cb4.html[Decoupling Infotypes], https://help.sap.com/docs/SAP_S4HANA_ON-PREMISE/c6c3ffd90792427a9fee1a19df5b0925/299fe2539c70424de10000000a174cb4.html[Migrating an Infotype], https://help.sap.com/docs/SAP_S4HANA_ON-PREMISE/c6c3ffd90792427a9fee1a19df5b0925/ab2bdd538636424de10000000a174cb4.html[Business Logic Guidelines for Creating and Migrating Infotypes] (all SAP Help, Human Resources)

=== Infotype characteristics

After generation you maintain the infotype characteristics: the time constraint, the subtype table, how the infotype is
selected and displayed, whether a change triggers retroactive accounting for a payroll infotype, and which screens it
uses. SAP lists the tables behind them: `T582A` (basic characteristics such as the screens and the time constraint),
`T582S` (short texts), `T591A` (subtype characteristics, if the infotype has subtypes), `T588G` (field-specific
retroactive accounting), `T588M` (screen control), `T588B` (infotype menus) and `T588Z` (dynamic actions). The tables
`T777D` and `T77ID` are maintained automatically by PM01; the others you maintain yourself, and the Customizing entries
must be transported. For Ana's example, the business picks a time constraint that allows more than one record at a time,
because an employee may hold several devices; the page xref:erp/sap/human-resources/time-constraints-and-validity.adoc[Time
Constraints and Validity Periods] explains the choices.

== Enhancing a delivered infotype

The enhancement concept lets you add fields and your own checks to a standard Personnel Administration or Recruitment
infotype. Added fields behave like SAP's own in reporting, in infotype logs and in dynamic actions. The steps from the
topics are these.

. Create the customer include `CI_Pnnnn` in the dictionary and add your fields. The structure must have an enhancement
  category. Do not put these fields into `CI_Pnnnn` as part of editing subobjects; use the enhancement functions.
. Enhance the single screen (choose Enhance Single Screen, then Generate Objects, and edit the include screen, default
  number 0200, by hand). Optionally enhance the list screen the same way; that creates a structure `ZPLISnnnn` and an
  include in the program `ZPnnnn00`.
. Store the checks for the customer fields in the BAdI `HRPAS00INFTYBL` (reached through the BAdI in the check class).
  Enter the same code in the module pool, as the topic says.
. Enhance the screen structure so that the new fields reach the decoupled framework, and write the conversion class BAdI
  for a standard infotype. After this the enhancement is decoupled.

Limits SAP states: the length of `PSnnnn` together with the include must not exceed 1500 bytes; fields added to
Organizational Assignment (0001) cannot be used as selection fields; and these infotypes are not covered at all: Actions
(0000), Additional Actions (0302), all Time Management infotypes (2nnn), Leave Entitlement (0005), Maternity
Protection/Parental Leave (0080), Military Service (0081), Leave Entitlement Compensation (0083), Time Quota
Compensation (0416), Electronic Data Exchange (0700) and Applicant Actions (4000).

Where the enhancement concept is not enough, SAP lists modification options, such as exchanging a screen or changing the
screen control through table `T588M`. These are changes to SAP objects. SAP names customer ranges so that they survive an
upgrade: single screens 2900 to 2999, list screens 3900 to 3999, and includes `MPnnnn5x`, `MPnnnn6x`, `MPnnnn7x` and
`MPnnnn8x` for data declarations, PBO modules, PAI modules and subroutines. The page
xref:programming-languages/abap/modifications-and-modification-assistant.adoc[Modifications and the Modification Assistant]
explains why modifications cost you at every upgrade.

Requires an SAP system; not run here.

== Custom infotypes for organizational data

Organizational Management infotypes (1000 and up) are not created with PM01. SAP provides the Personnel Planning Infotype
Copier, transaction PPCI, to create customer infotypes for organizational objects and to enhance existing ones. It copies
templates for the repository objects (module pools, IDoc segments, dialog modules), and you then edit them. The
documentation names four kinds: field infotypes and table infotypes, each in a language-dependent and a
language-independent form. For a field infotype you first create a structure `HRI9nnn` in the dictionary and then let the
copier generate the objects; for a customer infotype whose data is not yet in a transparent table, the copier can create the table `HRP9nnn`. A Check
Environment function creates or repairs the repository objects and the entries in the infotype tables. SAP adds that you
can enhance only infotypes that can be maintained directly, and that the standard infotypes 1000 (object) and 1001
(relationships) cannot be enhanced. The documentation also warns that a customer infotype must have at least the
enhancement category of the infotype it was copied from. The practical rule is the same as for PA: customer numbers,
customer packages, and a transport for every generated object.

== Dynamic actions and dynamic processing rules

A dynamic action starts automatically when infotype records are maintained and leads to follow-up processing: when a
change in one infotype affects another, the system brings that infotype up. This differs from a personnel action, which a
person starts. The actions are defined in the table `T588Z` in Customizing of Personnel Administration, and SAP says you
can set up processing chains that fit your company. They run in the SAP GUI transactions PA30 and PA40.

For the Web Dynpro ABAP master data application, SAP describes dynamic processing rules (DPRs) as the successors of
dynamic actions, and a conversion report turns existing dynamic actions into DPRs. A rule is defined in the Customizing
activity under Personnel & Organization, Master Data Application, Dynamic Processing Rules. The documentation compares the
two like this.

[cols="2,3,3",options="header"]
|===
| Idea | Dynamic action | Dynamic processing rule

| Start of a rule
| An implicit logic with the indicator `P`
| The Conditions view

| Maintain infotype records
| Indicators `I` and `W`
| The Operations view and Default Values

| Trigger on a field change
| The field and the indicator `V`
| Two conditions linked by OR, such as the old value differing from the new value

| Value calculation or database update
| A called routine (indicator `F`)
| Calculation methods, or a processing class

| Operations
| Create, Change, Delete
| Create, Change, Delimit

| Country
| A condition on the country grouping
| The version ID of the rule
|===

For Ana's example, a possible rule is "when a Work Equipment record is created for an employee, remind the administrator
to check the Communication infotype". This is an illustration of what a chain looks like, not a rule SAP delivers, and
the page does not show the exact entries because they depend on your release and country. SAP adds that a customer's
rule status can be overridden in the Rule Manager, and that the status of a DPR is stored in a client-dependent view.

Source: https://help.sap.com/docs/SAP_S4HANA_ON-PREMISE/c6c3ffd90792427a9fee1a19df5b0925/df39e153a217424de10000000a174cb4.html[Dynamic Actions], https://help.sap.com/docs/SAP_S4HANA_ON-PREMISE/c6c3ffd90792427a9fee1a19df5b0925/0221a3533039cd46e10000000a44538d.html[Dynamic Actions and Dynamic Processing Rules], https://help.sap.com/docs/SAP_S4HANA_ON-PREMISE/c6c3ffd90792427a9fee1a19df5b0925/6817aa534daad046e10000000a44538d.html[Maintaining Dynamic Processing Rules] (all SAP Help, Human Resources)

== BAdIs that SAP documents for HR authorizations

For authorization checks, SAP Help has a section called Customer Enhancements with three BAdIs.

* `HRPAD00AUTH_CHECK` lets you replace the standard authorization check for HR master data and infotypes without
  modification. The documentation says that as soon as an implementation is active, all HR master data authorization
  checks stop and only the active implementation runs, and that all the methods of the interface must be implemented.
  For one small change, SAP suggests copying the standard class `CL_HRPAD00AUTH_CHECK_STD` and activating the adjusted
  copy.
* `HRBAS00_STRUAUTH` lets you implement a customer test procedure for the structural authorization check.
* `HRBAS00_GET_PROFL` determines the assigned structural profiles.

The IMG nodes sit under Personnel Management, in Personnel Administration, Tools, Authorization Management for the first
and in Organizational Management, Basic Settings, Authorization Management for the structural one. Because an active
implementation replaces SAP's check completely, a mistake opens or closes access for everyone; test it as carefully as a
security change. The page xref:erp/sap/users-roles-and-authorizations.adoc[Users, Roles and Authorizations] and the page
on HR authorizations cover the surrounding model.

== Custom functions and operations for payroll and time

Payroll and time evaluation run on schemas made of functions, and on personnel calculation rules made of operations.
When delivered functions and operations are not enough, a developer writes a new one. The topics describe the steps.

. Write the source text of the form routine in an include and check and save it. SAP names the country-specific include
  `PCBURZxx0` for payroll and `RPTMOZ00` for time management.
. Open the function and operation editor (menu path Payroll, Payroll, the country, Tools, Customizing Tools,
  Function/Operation). The editor has no help page that names a transaction code in its own text; the code PE04 appears in
  the title of an SAP Note that the activation topic refers to, so treat the menu path as the sure way and the code as a
  shortcut to check in your system.
. Enter the name and choose Create. A customer function or operation must contain a special character in its name. By
  default the routine is named `FU<function name>` or `OP<operation name>`; a different name is possible if you mark the
  field as self-defined.
. Maintain the characteristics: country assignment, the parameter list and the parameter values.
. Activate it. The system starts the required reports and generates the indexed `PERFORM`. Only then can schemas and
  rules use it.

Saving creates a transport request. The logical transport objects separate SAP and customer names and the two areas:
`PFCS` and `PFCC` for payroll functions (SAP and customer), `PFTS` and `PFTC` for time functions, `POCS` and `POCC` for
payroll operations, and `POTS` and `POTC` for time operations.

Names follow rules too. Customer personnel calculation rules start with one of the characters `& ( ) / : ; < > =` or the
letter Z; a name starting with a question mark is in the SAP name range. For newly created rules, SAP recommends starting
with a round parenthesis, the digit 9, the letter Z or an exclamation mark. For schemas, SAP recommends changing the name
when you change a schema, so you can see where your system differs from the standard, and recommends parentheses and the
letters Z and Y at the start of a new name. The page xref:erp/sap/human-resources/time-evaluation.adoc[Time Evaluation]
and the page on xref:erp/sap/human-resources/payroll-schemas-and-pcrs.adoc[payroll schemas and personnel calculation rules] show where such functions are used.

Requires an SAP system; not run here.

Source: https://help.sap.com/docs/SAP_S4HANA_ON-PREMISE/c6c3ffd90792427a9fee1a19df5b0925/67b3e0535e56424de10000000a174cb4.html[Editor for Functions and Operations], https://help.sap.com/docs/SAP_S4HANA_ON-PREMISE/c6c3ffd90792427a9fee1a19df5b0925/c7a6e2539c70424de10000000a174cb4.html[Editing Functions and Operations], https://help.sap.com/docs/SAP_S4HANA_ON-PREMISE/c6c3ffd90792427a9fee1a19df5b0925/caa6e2539c70424de10000000a174cb4.html[Creating Functions and Operations], https://help.sap.com/docs/SAP_S4HANA_ON-PREMISE/c6c3ffd90792427a9fee1a19df5b0925/cda6e2539c70424de10000000a174cb4.html[Activating Functions and Operations], https://help.sap.com/docs/SAP_S4HANA_ON-PREMISE/c6c3ffd90792427a9fee1a19df5b0925/d3a6e2539c70424de10000000a174cb4.html[Transport Connections], https://help.sap.com/docs/SAP_S4HANA_ON-PREMISE/c6c3ffd90792427a9fee1a19df5b0925/389fe2539c70424de10000000a174cb4.html[Name Assignment for Standard and Customer Rules], https://help.sap.com/docs/SAP_S4HANA_ON-PREMISE/c6c3ffd90792427a9fee1a19df5b0925/d9a6e2539c70424de10000000a174cb4.html[Assigning Names for Standard and Customer Schemas] (all SAP Help, Human Resources)

== What can go wrong

[cols="3,3",options="header"]
|===
| Problem | What to do

| The infotype number is outside 9000 to 9999.
| Use the customer range. SAP reserves it so that your development survives an upgrade.

| Objects are created in an SAP package.
| Use customer packages for all subobjects.

| The new infotype works in PA30 but not in a newer application.
| Create it decoupled (PM01 does) and keep `NITF_ADM` at its default; SAP says some self-service scenarios and the HR administrative services process only decoupled infotypes.

| The table entry for the check class exists only in the development client.
| Transport the entry of `T582ITVCLAS` and the entries of the Customizing tables by hand.

| A check class updates a table directly.
| Do not. The buffer can roll back; use the additional update mechanism for tables outside the `PAnnnn` range.

| An enhancement field is added to an infotype that is excluded.
| Check the list of excluded infotypes first (for example Actions 0000 and all 2nnn infotypes).

| The PS structure plus the include grows too long.
| Keep `PSnnnn` with `CI_Pnnnn` within 1500 bytes; a new customer infotype is limited to 1000 positions.

| An active `HRPAD00AUTH_CHECK` implementation lets users see too much or too little.
| Remember it replaces the whole HR master data check. Test it, and implement every method.

| A customer function is not found in the schema.
| Activate it in the editor; activation generates the indexed `PERFORM`.
|===

== What older books show, and what has changed

The book SAP ERP HCM: Technical Principles and Programming, 1st edition (2013), covers the same ground in its chapters on
custom enhancements and on enhancing applications: customer exits through the transaction SMOD, BAdIs, enhancement points
and modifications, then PA infotype enhancement, custom PA infotypes with PM01, processing infotypes in the decoupled
infotype framework, dynamic actions through the table `T588Z`, OM infotypes with PPCI, time infotypes and custom payroll
functions and operations. Its concepts are still the ones SAP Help describes. What has changed since 2013 is the
following.

* The decoupled infotype framework, which the book introduces as a newer architecture beside the module-pool method, is now
  the way SAP Help tells you to create every new infotype, because newer applications process only decoupled ones.
* Dynamic actions have a successor for the Web Dynpro ABAP master data application, the dynamic processing rules, with a
  conversion tool; the book describes the route through the table `T588Z`.
* HR is now delivered as SAP HCM for SAP S/4HANA, a separately licensed component that is active by default from SAP
  S/4HANA 2025 and cannot run in compatibility mode, so a 2013 book's ERP context differs from today's S/4HANA one. SAP
  SuccessFactors has its own extension tools, which are outside this page.
* Customer exits are one of the older enhancement techniques; the
  xref:programming-languages/abap/enhancements-and-badis.adoc[Enhancements and BAdIs] page explains how the newer BAdI and
  the enhancement framework compare.

Source: https://www.sap-press.com/sap-erp-hcm-technical-principles-and-programming_3698/[SAP ERP HCM: Technical Principles and Programming (SAP PRESS, publisher page; the consulted copy is the 1st edition, the page lists the 2nd)], https://help.sap.com/docs/SAP_S4HANA_ON-PREMISE/c6c3ffd90792427a9fee1a19df5b0925/18cbddfa5691416d8f004dc97ac98634.html[SAP Human Capital Management for SAP S/4HANA (SAP Help Portal)]

== Summary

* A customer infotype takes a number from 9000 to 9999, is created with transaction PM01, and the system generates the
  structures, tables, module pool, screens, dialog module, screen structure and check class for you; you code the
  check class and maintain the infotype characteristics.
* The business logic of a new infotype goes into five methods of the check class, which must tolerate buffer rollbacks
  and never update a table directly.
* A delivered infotype is enhanced through the customer include `CI_Pnnnn`, the screen structure and the BAdI in the
  check class, with documented limits and a list of excluded infotypes.
* Organizational infotypes are created with transaction PPCI; dynamic actions (table `T588Z`) and dynamic processing
  rules chain follow-up work.
* SAP documents BAdIs for HR authorizations, and the function and operation editor adds customer functions and
  operations to payroll and time evaluation, with SAP and customer transport objects.
* PM01 and the HR check class methods are described by SAP Help topics that name them; their exact screens and method
  signatures are in-system documentation of your own release.
