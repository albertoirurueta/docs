An employee file in paper form is a folder with separate sheets: one for the name and birth date, one for the address, one
for the contract, one for the pay. SAP Human Resources keeps the same file on screen, and each sheet is an infotype. When
something about an employee changes, a new sheet is added with the date it starts, and the old sheet stays in the file
with the date it ended, so the history is never lost. A newcomer meets infotypes the moment an HR administrator opens an
employee: the screens of HR master data are infotypes. This page explains what an infotype is, how
subtypes and validity periods work, which number ranges exist, and then lists the key infotypes with the values that Ana
Torres, the featured employee of Example Trading Co., would have in them. It is written against SAP S/4HANA 2025 FPS02
on premise and Private Edition, where the HR functions come from SAP HCM for SAP S/4HANA (H4S4), a separately licensed
component. The infotype concept is the same in the older SAP ERP HCM, and SAP SuccessFactors uses a different data model
that later pages cover.

== Key terms

* xref:erp/sap/human-resources/glossary.adoc#infotype[Infotype]: a record type of the HR master data, a screen and a data
  structure for one area of information such as personal data or basic pay.
* xref:erp/sap/human-resources/glossary.adoc#subtype[Subtype]: a subdivision of an infotype, such as the address type
  "Permanent residence" inside the Addresses infotype.
* xref:erp/sap/human-resources/glossary.adoc#time-constraint[Time constraint]: the rule that says whether an infotype
  must have a record, how many records may exist at one time and whether they may overlap.
* xref:erp/sap/human-resources/glossary.adoc#delimitation[Delimitation]: ending the validity of an existing record, which
  the system does when a new record starts.
* xref:erp/sap/human-resources/glossary.adoc#personnel-action[Personnel action]: a procedure such as hiring that
  creates or changes several related infotype records in one go.
* xref:erp/sap/human-resources/glossary.adoc#infotype-group[Infotype group]: the sequence of infotypes shown for
  processing while one personnel action runs.
* xref:erp/sap/human-resources/glossary.adoc#customer-infotype[Customer infotype]: an infotype that a customer develops
  in the number range reserved for customers.
* xref:erp/sap/human-resources/glossary.adoc#personnel-number[Personnel number]: the number that identifies one employee
  and under which all infotype records of that employee are stored.

== The running example: Example Trading Co.

All HR pages on this site use one fictitious business, Example Trading Co. All keys, names, numbers and dates are invented
example values chosen for this site. They are not values delivered by SAP, and a real system defines its own. Dates are
written DD.MM.YYYY, as an SAP screen shows them, and the high date, the end date of a record that has no planned end, is
31.12.9999.

* Personnel area `EX01` "Example Trading Co.", personnel subarea `0001` "Head office", employee group `1` "Active",
  employee subgroup `AA` "Salaried staff", payroll area `E1` "Monthly EX01".
* `00001234` Ana Torres, Sales Manager, hired 01.03.2024, basic pay 4,000.00 EUR a month (the featured employee);
  `00001235` Ben Okoye, Sales Clerk, hired 01.09.2024, 2,400.00 EUR a month; `00001236` Chloe Martin, Warehouse Clerk,
  hired 15.01.2025, hourly staff (employee subgroup `AB`, personnel subarea `0002` "Warehouse") paid 14.00 EUR an hour.
* Working time: 40 hours a week, Monday to Friday 08:00 to 16:30 with an unpaid break of 30 minutes, which makes 8 paid
  hours a day (8.5 hours present minus 0.5 hours break) and 5 x 8 = 40 hours a week. Annual leave entitlement is 30 days
  for Ana and Ben and 28 days for Chloe.
* Organizational objects: position `51000001` Sales Manager (job `52000001` Manager) in the organizational unit
  `50000002` Sales, where it is the chief position.

example.

== What an infotype is

SAP Help gives two views of the same thing. For the user, an infotype is a screen for entering data, with checks
programmed into it. The data fields on the screen are grouped by content. From the database side, an infotype is a data
structure, a set of related data records. An infotype record always belongs to exactly one employee (or, in Recruitment,
one applicant), because the data is stored under the personnel number of the employee. Some infotypes are used only in
Personnel Administration, some only in Recruitment, and some in both, for example Personal Data (0002) and Addresses
(0006).

Each infotype has a four-digit number `nnnn` that identifies it uniquely. You can see the pattern in the numbers of the
table later on this page: the master data infotypes of Personnel Administration have numbers such as 0001 and 0008, the
Organizational Management infotypes 1000 and 1001, and the time management infotypes 2001, 2002 and 2006. Each infotype
also has a name, and SAP Help writes the pair together, for example "Basic Pay (Infotype 0008)".

When an administrator saves data, the entries are checked against table entries and for plausibility, and default values
help the entry. The checks and defaults depend on the employee's organizational assignment, which determines the
relevant information for time recording, wage types and the pay scale structure. Authorizations can be assigned
infotype by infotype, and SAP Help also describes a Customizing step that restricts which infotypes appear for which
country, with the example that the Tax Data D infotype (0012) should be shown only for employees in the country grouping
Germany.

== One record per period: validity and history

A paper file keeps the old sheet when it adds a new one. An infotype does the same, and SAP Help calls it time-dependent
storage: when you update data, the legacy data is not lost but kept for evaluations of historical data. Every record has a
validity period, a start date and an end date, and when you update an employee's data the validity of the old record is
delimited automatically. So an employee normally has several records of the same infotype that differ in their validity
periods.

How the records of one infotype may relate in time is set by the time constraint of the infotype. SAP Help lists these
values:

[cols="1,4",options="header"]
|===
| Time constraint | Meaning

| `1` | Exactly one valid record must exist for the entire time the employee works at the enterprise. Records must not
overlap. A new record delimits the old one at its start date. Gaps are allowed only between the entry date and the start
date of the first record.
| `2` | At most one valid record at any time. Records must not overlap, and the existence of a record is not obligatory.
A new record delimits the previous one, with a message.
| `3` | Any number of valid records at the same time, without conflict. A record need not exist.
| `A` | At most one record in total, valid from 01.01.1800 to 31.12.9999, which cannot be subdivided and cannot be deleted.
| `B` | The same as `A`, but the record can be deleted.
| `T` | The time constraint depends on the subtype.
| `Z` | Used by the infotypes for working and absence time, with a special behavior described in the time management
documentation.
|===

SAP Help gives these examples: Organizational Assignment (0001) has time constraint 1 because the system needs its data
for every business process and the data must be unique, and Powers of Attorney (0030) has time constraint 3 because an
employee can hold several powers of attorney at once. Actions (0000), Organizational Assignment (0001) and Personal Data
(0002) all have time constraint 1, so a record must exist for each employee at all times from the hiring. This page covers
only the idea; a later page of this section treats the time constraints and validity periods in detail.

=== Ana's organizational assignment over time

Ana's Organizational Assignment (0001) record was created by the hiring on 01.03.2024 and has no planned end. Suppose, as
an extension of the example, that a personnel action changed her assignment from 01.07.2026. Because the infotype has
time constraint 1, the system delimits the old record and starts a new one without a gap:

[cols="1,2,2,2",options="header"]
|===
| Record | Valid from | Valid to | Status

| 1 | 01.03.2024 | 30.06.2026 | delimited by the system when record 2 was created
| 2 | 01.07.2026 | 31.12.9999 | valid now, no planned end
|===

The old record ends on 30.06.2026, the day before the new one starts, so on every day since the hiring exactly one record
is valid. The step cannot be shown here: it requires an SAP system; not run here.

== Subtypes and object identification

Some infotypes hold data that comes in several kinds, so they are divided into subtypes. Examples from SAP Help: the
Addresses infotype (0006) has subtypes such as Permanent residence, Temporary residence, Home address, Emergency address,
Mailing address and Nursing Address, and the Basic Pay infotype (0008) has Basic Contract, Increase Basic Contract,
Comparable Domestic Pay, Refund of Costs in Foreign Currencies and Local Weighting Allowance. In the time infotypes the
subtype is the type of absence or quota: an absence type is a subtype of Absences (2001), and absence quota types are
subtypes of Absence Quotas (2006). For the payment infotypes, the wage types are the subtypes, for example M110 Vacation
Bonus, M120 Holiday Bonus and M130 Standard Special Payment in Recurring Payments/Deductions (0014) and Additional Payments
(0015). The relationships of Organizational Management are subtypes too, of infotype 1001.

A subtype can have a time constraint of its own, which is what time constraint `T` means. That is how a system makes sure
an employee always has a main address and still lets you enter a temporary residence.

When one subtype needs several parallel histories, SAP Help adds the object identification. It tells apart records that
share the same infotype, subtype, lock indicator and validity dates, and it inherits the time constraint of the subtype.
The example in SAP Help is the Family Member/Dependents infotype (0021): its subtypes Spouse, Child and Legal Guardian
get time constraint 2, but an employee with two children needs overlapping records, so the subtype gets time constraint 3
and the object identification, stored as the child number, gives each child a history of its own.

== Infotype groups: several infotypes in one action

Nobody hires an employee by opening twenty infotypes one after another. SAP solves it with personnel actions, procedures
such as hiring, organizational reassignment or leaving, and each action type has an infotype group, often called an
infogroup: a sequence of related infotypes that the system shows while the action runs, so that all information the
business processes need is stored. An infogroup exists in the standard system for every personnel action type, and you
can tailor it in Customizing and make it depend on the user group. Most actions also create a record in the Actions
infotype (0000), which keeps the overview of the important stages of an employee's history. When Ana was hired on
01.03.2024, the hiring action led the administrator through the infotypes of its infogroup, and the records the
example describes, such as her Organizational Assignment (0001) and Basic Pay (0008), start on that date. Which infotypes
the standard hiring infogroup contains is set in Customizing and is not listed here.

== Where infotype data is stored and how you reach it

SAP Help states that every infotype `nnnn` needs at least three structures and one table in the ABAP Dictionary: the
structure `PSnnnn` with all the data fields of the infotype, the structure `Pnnnn` with the infotype key fields and all the
data fields, and a transparent table `PAnnnn` if the infotype is used in Personnel Administration, or `PBnnnn` if it is used
in Recruitment. So the records of Ana's Basic Pay (0008) are rows of a table named `PA0008`, and each row carries the
validity dates and the personnel number as its key. The Organizational Management infotypes use tables of the `HRPnnnn`
kind, for example `HRP1000` and `HRP1001`, which a later page of this section covers together with the other HR tables.

An administrator reaches infotypes through the transaction PA30 (maintain HR master data), where the most frequently used
infotypes are grouped by subject as infotype menus, shown as tabs. SAP Help adds that a Customizing activity maps a user
group to a country grouping code, so that the infotype menus an administrator sees depend on the country of the employee.
The menu path in SAP Easy Access is Human Resources, Personnel Management, Administration, HR Master Data, Maintain or
Display. Reading and writing infotypes from ABAP programs has a page of its own in this section.

== Customer infotypes

SAP Help says the number range 9000 to 9999 is reserved for customer infotypes, and that you must use it if you want
your own developments to be kept after a release upgrade. The transaction PM01 (Create Infotype) is used to develop
infotypes: you create the data field structure in the ABAP Dictionary, the system then creates the other Dictionary
objects, a supporting program, the dialog module, the conversion class and the check class, and you maintain the
infotype's characteristics. You choose whether the infotype is an employee infotype, an applicant infotype or both, and
the system creates the table `PAnnnn`, `PBnnnn` or both. Objects in the customer name range carry a 9 in the name: the
help text gives the example of an international infotype 9900 for Personnel Administration only, with the structure
`PS9900`, the table `PA9900` and the structure `P9900`. A finished infotype becomes part of the Personnel
Administration and Recruitment transactions and is included in the logical databases PNP and PNPCE.

For Example Trading Co. a customer infotype could hold, for instance, the company's own training record of each employee;
this is an idea, not part of the shared example, and nothing about it is delivered by SAP. Building one requires an SAP
system; not run here. A later page of this section covers custom infotypes and their enhancements.

== What older books show, and what has changed

The book SAP ERP HCM: Technical Principles and Programming, 1st edition (2013), explains infotypes from a developer's
point of view: the four-digit number and the subtypes, the time constraints, the infotype tables, maintaining infotypes
with the master data transactions and building customer infotypes with the Create Infotype transaction. Those concepts
are the same in the current documentation and are what this page teaches.

What has changed is the product around them. The book describes SAP ERP HCM. In SAP S/4HANA the same functions come as SAP
HCM for SAP S/4HANA (H4S4), which SAP says needs a separate license and which, since SAP S/4HANA 2025, can no longer run
in compatibility mode. The current documentation also lists infotypes inside processes and forms of the Personnel &
Organization component, for example the process that creates an organizational unit and names Object (1000) and
Relationships (1001) among its infotypes, which the book does not cover, and SAP SuccessFactors is now a cloud
alternative with a different data model. The screen structures and the object lists of the infotype development help were
not compared with the book, so check object names against the in-system documentation of your release before you build
anything.

== Summary

* An infotype is one record type of HR master data: for the user a screen with checks, for the database a data structure
  whose records belong to one personnel number. Each has a four-digit number and a name, such as Basic Pay (0008).
* Changes never overwrite history. Each record has a validity period, and a new record delimits the old one. The time
  constraint of the infotype sets whether a record must exist and whether records may overlap.
* A subtype divides an infotype into kinds, such as address types, absence types or wage types, and the object
  identification gives parallel histories inside a subtype, as with several children.
* A personnel action such as hiring runs an infotype group, which leads the administrator through the related infotypes.
* The records of an infotype are stored in the table `PAnnnn`, and the number range 9000 to 9999 is reserved for customer
  infotypes created with the Create Infotype transaction (PM01).
* For Ana Torres, the reference table shows the value of each key infotype, and the leave example shows that 30 days minus
  5 days of leave leave 25 days.
