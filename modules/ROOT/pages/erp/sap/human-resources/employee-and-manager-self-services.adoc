= Employee and Manager Self-Services
:description: How employees and managers of SAP HCM for SAP S/4HANA do HR tasks themselves, such as requesting and approving leave, reading a paystub, viewing a team calendar and an organizational chart, with the SAP Fiori apps of SAP S/4HANA 2025 FPS02 on premise and the older Web Dynpro ABAP generation.

Most of the questions an HR department receives are small and repetitive: how many vacation days are left, can this week
of leave be approved, where is last month's payslip. Self-services let the employee or the manager do these tasks
directly, without an HR administrator typing the data in. Employee Self-Service (ESS) is the set of services for
employees, and Manager Self-Service (MSS) is the set for line managers. A newcomer meets them as soon as the first
employee asks for a login, because every service needs a user, a role and an authorization before it shows anything.
This page explains what the current SAP Fiori apps offer, what an administrator has to switch on for one of them, and
how the older Web Dynpro ABAP generation of ESS and MSS differs. It uses the leave request of Ben Okoye and the approval
by Ana Torres as the worked case. It is written against SAP S/4HANA 2025 FPS02 on premise and Private Edition with
SAP HCM for SAP S/4HANA (H4S4). Everything on the page describes on-premise H4S4 documentation. SAP SuccessFactors has
its own employee and manager experience, which is outside this page.

== Key terms

* xref:erp/sap/human-resources/glossary.adoc#employee-self-service[Employee Self-Service]: services with which employees
  display and change their own HR data and send requests such as leave.
* xref:erp/sap/human-resources/glossary.adoc#manager-self-service[Manager Self-Service]: services with which line
  managers see their team and approve or start HR tasks for it.
* xref:erp/sap/human-resources/glossary.adoc#on-behalf[On Behalf]: a function with which a manager carries out an
  employee's self-service for that employee.
* xref:erp/sap/human-resources/glossary.adoc#odata-service[OData service]: the web interface of the back end that a
  Fiori app calls to read and write its data.
* xref:erp/sap/human-resources/glossary.adoc#business-catalog[Business catalog]: a delivered bundle of apps from which
  an administrator builds the role of a user group.
* xref:erp/sap/human-resources/glossary.adoc#web-dynpro-abap[Web Dynpro ABAP]: the older SAP user interface technology on
  which the previous generation of ESS and MSS is built.
* xref:erp/sap/human-resources/glossary.adoc#sap-business-client[SAP Business Client]: the client, desktop or HTML, in
  which the Web Dynpro ABAP self-services run.

== The running example: Example Trading Co.

All HR pages on this site use one fictitious business, Example Trading Co. All keys, names, numbers and dates are invented
example values chosen for this site. They are not values delivered by SAP, and a real system defines its own. Dates are
written DD.MM.YYYY, as an SAP screen shows them.

* `00001235` Ben Okoye, Sales Clerk, hired 01.09.2024, has an annual leave entitlement of 30 days. He is the employee who
  uses the employee apps.
* `00001234` Ana Torres, Sales Manager, is the chief position of the organizational unit Sales (`50000002`), so she is
  the manager who approves Ben's requests and who sees Ben and the other members of Sales in the manager apps.
* `00001236` Chloe Martin, Warehouse Clerk, works in the unit Warehouse (`50000003`) and is not in Ana's team.
* Ana's March 2026 payslip is the one from the payroll pages: gross 4,000.00 EUR, net 2,720.00 EUR. The generic flat
  rates behind it are not any country's real rules.

== What self-service means in SAP HR

Without self-services, an employee who wants leave tells a supervisor, and a time administrator records an absence in
infotype 2001 (see xref:erp/sap/human-resources/time-management.adoc[Time Management Basics]). With self-services, the
employee enters the request, the system finds the approver, the approver decides in an inbox, and the result is
written to the same infotype. The data does not move to a new place. Only the way it gets there changes, and with it
the number of people who touch it.

Two ideas keep the apps understandable.

* The back end owns the data and the rules. The apps are windows onto the same infotypes, quotas, Customizing and
  organizational structure that an HR administrator uses.
* Who may do what is decided by roles. An employee's role contains the employee apps, a manager's role contains the
  manager apps, and the authorization checks in the back end still decide which data a manager may see (see
  xref:erp/sap/users-roles-and-authorizations.adoc[Users, Roles and Authorizations]).

SAP documents two generations. The current one is a set of SAP Fiori apps that run in the Fiori launchpad. The earlier
one is Employee Self-Service (WDA) and Manager Self-Service (WDA), built on Web Dynpro ABAP. Both are described in the
H4S4 documentation, so a system can contain either or both, and the next sections cover each.

The My Paystubs app is listed in a different group of the same documentation. Its description page says that employees
can view a list of the paystubs issued for each payroll period, show the PDF version of a paystub, download it and print it.
That page sits in the group "Fiori 2.0 Apps in SAP Human Capital Management" under the name "My Paystubs (Version
3/Fiori 2.0)". The H4S4 table of contents shows no separate "App Implementation" page for it, so check the SAP Fiori apps
reference library for the release you run before you promise this app to employees.

For Example Trading Co., Ana would open My Paystubs, find the entry for the March 2026 payroll period and see the PDF of
the payslip that payroll issued. The numbers in that PDF come from payroll, not from the app: gross 4,000.00 EUR, employee
social contributions 800.00, income tax 480.00 and net 2,720.00 (see the payroll pages of this section).

== What an administrator switches on for one app

The "App Implementation" pages of My Leave Requests, Approve Leave Requests, My Team, My Reporting, Organizational Chart
and My Team Calendar all begin with the same prerequisite: the enterprise business function for SAP HCM for SAP S/4HANA
must be active. After that, the pages list the same kinds of tasks, and the tasks are the same ones that any Fiori app
needs (see xref:erp/sap/deploying-apps-to-the-fiori-launchpad.adoc[Deploying Apps to the Fiori Launchpad]).

. On the front-end server, activate the OData service from the table, for example `UI_HCMMYLEAVEREQUEST` for My Leave Requests.
. On the front-end server, activate the SAPUI5 application of the app. For My Leave Requests the page names
  `HCM_LEA_MANS1`, served at `/default_host/sap/bc/ui5_ui5/sap/hcm_lea_mans1`.
. Make the app available in the launchpad through a technical catalog, and assign OData service authorizations on both
  servers: in a PFCG role on the back end, and in a role for the launchpad content on the front end.
. Perform the configuration tasks of the app in the back end.

For the roles, the pages name example business catalogs that SAP delivers: `SAP_HCM_BC_EMPLOYEE` for My Leave Requests and
My Team Calendar, `SAP_HCM_BC_MANAGER` for Approve Leave Requests and My Team, and `SAP_HCM_BC_HR_SPECIALIST` together with
`SAP_HCM_BC_MANAGER` for Organizational Chart. The pages say the administrator can use the example catalog or a custom
catalog as the base of the back-end role, with an existing role or a new one. Ben therefore gets a role built from the
employee catalog, and Ana a role built from the manager catalog.

The configuration tasks that the SAP pages list are small in number but easy to forget. Two examples are worth knowing
because they show how an app depends on older back-end objects.

* My Leave Requests needs a document type for attachments. The page has the administrator create document type `LRQ` in
  transaction `DC10`, link it to the object `HCMLEAREQ`, activate the attachment object type `HCMLEAVEREQUEST` in
  transaction `HDM_CUST` and mark `LRQ` as the default type.
* Approve Leave Requests receives its work items from workflow. When the leave requests are kept in the request
  database instead of through workflow, the page has the administrator activate the switch `PTMW FABFI` in table `T77S0`,
  and name the workflow template to use with the switch `PTMW ARQWF`. The delivered template named on the page is
  `40300127`. The page also lists the transaction `SWFVISU` and the Customizing step "Maintain Task Names and Decision
  Options" so that the Approve and Reject buttons appear in the inbox.

These steps need an SAP system; they are not run here. The values come from the SAP pages cited below, and a real system
can differ by release and by whether the customer uses its own workflow.

My Leave Requests also has a Customizing task, "Define Quota KPI", under the Implementation Guide path
Personnel Management, Employee Self-Service (Web Dynpro ABAP/Fiori), Service-Specific Settings, Working Time, Leave
Request, Layout of the Web Application. It defines the leave types for which the app shows a quota figure and whether it
warns about an expiring quota within a set lead time. This is where an administrator decides which leave types, for example
Ben's annual leave, show a remaining-quota figure to the employee.

== Worked case: Ben asks for a week of leave

The case uses the example's own numbers. The leave dates are an invented example, and the calculation assumes that the
public holiday calendar of the example has no holiday in that week and that Ben has taken no other leave in 2026.

Ben wants Monday 15.06.2026 to Friday 19.06.2026. That is five working days, because the work schedule of the example is
Monday to Friday with 8 paid hours a day, so five days are 5 x 8 = 40 hours. A small script confirmed that 15.06.2026 is a
Monday and 19.06.2026 a Friday. Counted in days of the quota:

[stem]
++++
\text{remaining} = \text{entitlement} - \text{requested} = 30 - 5 = 25 \text{ days}
++++

The sequence is the one the SAP descriptions of the two apps give, shown in simplified form.

[mermaid]
----
sequenceDiagram
  actor Ben as Ben Okoye (employee)
  participant ML as My Leave Requests
  participant BE as Back end (leave request, quota)
  participant AI as My Inbox (Approve Leave Requests)
  actor Ana as Ana Torres (manager)
  Ben->>ML: 15.06.2026 to 19.06.2026, note for approver
  ML->>BE: create and submit request
  BE-->>ML: entitlement 30, requested 5, balance 25
  BE->>AI: work item for the approver
  Ana->>AI: open request, check team calendar for overlaps
  Ana->>AI: approve (optional note)
  AI->>BE: decision
  BE-->>ML: status updated
  Ben->>ML: sees the approval status
----

Read the diagram from top to bottom. Ben creates the request and the app shows the entitlement summary that the SAP
description mentions (entitlement, leave taken, available balance). The work item reaches Ana in her inbox. Her view
includes a team calendar that shows overlapping leave, so she can see whether Ben and the other Sales employee are away at
the same time. She approves or rejects, with an optional note, and Ben sees the status. How and when the leave is
written to the absence infotype, and which quota it reduces, depends on the back-end Customizing of the leave types and
on the release. The page therefore does not state that detail for the Fiori generation.

The My Team Calendar app supports the same question outside the approval. Ben, as an employee, can open it to see who
in his organizational unit is absent. The SAP page describes the app as showing colleagues of the same organizational unit, and Chloe belongs to Warehouse, a different unit.

== The Web Dynpro ABAP generation

Before the Fiori apps, ESS and MSS ran on Web Dynpro ABAP. The H4S4 documentation still contains both under the
topic "Shared Services" and calls them Employee Self-Service (WDA) and Manager Self-Service (WDA). The structure is
different from the Fiori apps.

* Employee Self-Service (WDA) lets employees create, display and change their own data in a browser window. It needs the
  business function HCM, ESS on Web Dynpro ABAP (`HCM_ESS_WDA_1`). The page lists services from, among others, HR
  Administrative Services, Payroll, the Cross Application Time Sheet and Personnel Time Management.
* The delivery is a composite role, `SAP_EMPLOYEE_ESS_WDA_3`, which holds one international single role and country-specific
  single roles. The roles carry the menu and the authorizations, and they are maintained with transaction `PFCG`. The
  deployment option the documentation describes is the SAP Business Client for HTML.
* Manager Self-Service (WDA) gives line managers, team leaders and heads of department central access to their
  tasks. It needs the business functions HCM, MSS on Web Dynpro ABAP (`HCM_MSS_WDA_1`) and HCM, MSS on Web Dynpro ABAP 2
  (`HCM_MSS_WDA_2`). Its composite role is `SAP_MANAGER_MSS_NWBC_3`.
* The WDA Leave Request application has three parts: Create Leave Request for employees, Leave Overview, and Approve Leave
  Request for managers. The page says employees can request absences (infotype 2001) and attendances (infotype 2002),
  and that a request is stored in the database of leave requests with a status such as Sent.

The documented process, with the same example, runs differently from the Fiori one. After Ben submits a request, a
background report, `RPTARQEMAIL` ("Leave Requests: Send E-Mails"), runs once a day and sends the approver an e-mail. Ana
opens the Approve Leave Requests service from the personal object worklist (POWL), checks the Team Calendar, and approves
or rejects with a note. The same report mails Ben about the result. SAP Business Workflow can be used for these steps, but
the documentation says it is not required, and that the Web Dynpro application for approval is optional because a simple
back-end report can be used instead.

The WDA documentation lists the technical data of the Approve Leave Request application. It reads the data through RFC
function modules of the back end, among them `PT_ARQ_ACCOUNTS_GET`, `PT_ARQ_CUSTOMIZING_GET`, `PT_ARQ_REQLIST_GET` and
`PT_ARQ_TEAMCALE_GET`. This is shown only to make the point that the same back-end objects serve both generations.

== Differences at a glance

|===
|Question |Fiori apps |Web Dynpro ABAP ESS and MSS

|Where does the user start?
|The SAP Fiori launchpad, with tiles from catalogs.
|A role menu in SAP Business Client for HTML, built from `PFCG` roles.

|How is the user interface delivered?
|SAPUI5 application and OData service on the front-end server.
|Web Dynpro ABAP applications in the back end.

|What does the administrator assign?
|OData service authorizations in a back-end role and launchpad content in a front-end role, from catalogs such as `SAP_HCM_BC_EMPLOYEE`.
|The composite roles `SAP_EMPLOYEE_ESS_WDA_3` and `SAP_MANAGER_MSS_NWBC_3` with their single roles.

|How does a manager approve leave?
|From My Inbox, with a team calendar for overlaps, through workflow items.
|From the Approve Leave Requests service reached through the POWL, with notification by e-mail from a background report.

|Which business function is the prerequisite?
|The business function for SAP HCM for SAP S/4HANA.
|`HCM_ESS_WDA_1` for ESS, `HCM_MSS_WDA_1` and `HCM_MSS_WDA_2` for MSS.
|===

== What older books show, and what has changed

The book SAP ERP HCM: Technical Principles and Programming, 1st edition (2013), has a chapter on ESS and MSS applications.
The chapter shows how those
services are delivered with enhancement packages and the switch framework, how the SAP NetWeaver Business Client for
desktop and for HTML is used, and how ESS and MSS are built on Web Dynpro ABAP, with the Internet Communication Manager
and activated HTTP services behind them. That is the Web Dynpro ABAP generation described above. Several things have
changed since 2013.

* The apps a user meets are now SAP Fiori apps in the launchpad, with an OData service, an SAPUI5 application and a
  catalog for each app.
* In SAP S/4HANA the self-services are part of SAP HCM for SAP S/4HANA, which needs a separate license and is active by
  default from SAP S/4HANA 2025. Compatibility mode is no longer possible (see
  xref:erp/sap/human-resources/hr-landscape-hcm-h4s4-and-successfactors.adoc[SAP HCM, H4S4 and SuccessFactors]).
* The H4S4 documentation lists SAP Business Client for HTML as the deployment option of the WDA generation. The 2013 book
  also discusses portal-based delivery, which this page does not cover.
* The Fiori approval of leave is a workflow item in My Inbox, not a worklist entry and a daily e-mail report.
* SAP SuccessFactors offers its own employee and manager experience for customers who run the cloud suite (see the
  landscape page above). That is a different product and is not described in the book edition used here.

== Summary

* Self-services let employees and managers do routine HR tasks themselves while the back end keeps the same infotypes,
  quotas, workflow and authorizations.
* The current generation is a set of SAP Fiori apps: My Leave Requests and My Team Calendar for employees,
  Approve Leave Requests, My Team, My Reporting and Organizational Chart for managers.
* Each app is switched on with a business function, an OData service, an SAPUI5 application, catalog and role assignments
  on both servers, and back-end Customizing. The example catalogs are `SAP_HCM_BC_EMPLOYEE` and `SAP_HCM_BC_MANAGER`.
* My Paystubs is documented in the Fiori 2.0 group, so check the apps reference library for your release.
* Ben's request for 15.06.2026 to 19.06.2026 is five working days, 40 hours, and leaves 25 of 30 days. The arithmetic was
  checked by hand and with a script, not run in an SAP system.
* The Web Dynpro ABAP generation (Employee Self-Service (WDA) and Manager Self-Service (WDA)) is still documented. It uses
  composite roles in `PFCG`, SAP Business Client for HTML and a daily e-mail report for leave notifications.
