An hourly employee is paid for the hours worked, and the hours come from a time clock: one entry when the person comes in,
one when the person leaves, sometimes several a day. Nobody can pay those raw entries directly. Somebody has to decide
which entries belong together, how many hours they make, which hours are planned work and which are overtime, and what
is left over on the time account. In SAP this decision step is called time evaluation. This page explains how it works
and follows one day of Chloe Martin, the hourly employee of Example Trading Co., from her clock entries to the hours that
payroll multiplies by her rate of 14.00 EUR. After reading it you can name the parts of time evaluation (the report, the
schema, the rules, the internal tables and the results), read a schema outline, and explain how the results reach
payroll. It is written against SAP S/4HANA 2025 FPS02 on premise and Private Edition, where time evaluation comes from SAP
HCM for SAP S/4HANA (H4S4), a separately licensed component. SAP S/4HANA Cloud Public Edition and SAP SuccessFactors are not covered here; the landscape page compares the options.

== Key terms

* xref:erp/sap/human-resources/glossary.adoc#time-evaluation[Time evaluation]: the SAP component that valuates recorded time data and produces balances, time wage types and quota updates.
* xref:erp/sap/human-resources/glossary.adoc#rptime00[RPTIME00]: the time evaluation report, the driver that selects employees, retrieves data, and stores the results.
* xref:erp/sap/human-resources/glossary.adoc#time-evaluation-schema[Schema]: the ordered list of processing steps (functions) that time evaluation runs for each employee and day.
* xref:erp/sap/human-resources/glossary.adoc#personnel-calculation-rule[Personnel calculation rule]: a named set of rules, made of operations, that a function calls to refine a processing step.
* xref:erp/sap/human-resources/glossary.adoc#time-pair[Time pair]: a start time and an end time, for example a clock-in and the matching clock-out.
* xref:erp/sap/human-resources/glossary.adoc#time-type[Time type]: a bucket in which time evaluation collects durations that mean the same thing, such as planned time or overtime.
* xref:erp/sap/human-resources/glossary.adoc#time-wage-type[Time wage type]: a wage type with a number of hours, selected by time evaluation, that payroll later values in money.
* xref:erp/sap/human-resources/glossary.adoc#cluster-b2[Cluster B2]: the database area that stores the results of time evaluation for each employee and period.

== The example used on this page

Every page of this section uses one made-up business, Example Trading Co. All keys, names, numbers and dates are invented
example values for this site, not values delivered by SAP. Dates are written DD.MM.YYYY, as an SAP screen shows them.

* `00001236` Chloe Martin, Warehouse Clerk, hired 15.01.2025, employee subgroup `AB` "Hourly staff", personnel subarea
  `0002` "Warehouse", payroll area `E1` "Monthly EX01", paid 14.00 EUR an hour.
* Planned working time: 8 paid hours a day, 40 hours a week. Chloe works shifts, so her real start and end times vary.
  The example gives her a day shift on Tuesday 10.03.2026 (08:00 to 16:30 with an unpaid break of 30 minutes).
* The rules, schema steps and time-type numbers used below are the ones SAP's documentation shows as examples, applied to
  invented numbers. What a real company customizes (its own schema, rules and time wage types) is different.

== What time evaluation does

SAP's documentation describes time evaluation as the component that valuates time data: it calculates planned times
and overtime, administers time accounts, forms wage types and updates time quotas. It is
documented as the choice when employees record their actual times at time recording terminals, and as optional when time
data is entered in other ways. The documentation names two reasons to run it with the report RPTIME00 rather than only in
payroll: balances can be formed and quotas managed on a daily basis, and time data from terminals can be processed.

Time evaluation has three parts.

* *The report RPTIME00* is the driver. It selects the employees, retrieves the data, determines the evaluation period
  and stores the results. Running it is a normal report start: the menu path is Human Resources, Time Management,
  Administration, Time Evaluation, Time Accounting, and the transaction code is PT60.
* *Schema processing* is the engine. The report starts a function pool (a program unit named SAPFP51T) that reads the
  schema and executes its functions one after the other. How each function works is built into the function pool;
  which functions run, and in which order, is data that the company can change.
* *Customizing* holds the settings that are independent of a schema, such as the time types table.

The point of this design, in SAP's own words, is that the rules used to valuate time data are not hard-coded, so a company
can adapt them to its agreements.

== The schema: ordered functions and rules

A schema is a list of steps, and SAP calls each step a function. A function supplies the data a step needs, processes it
and writes it to internal tables. Some functions are fixed in what they do. Others call a personnel calculation rule, a
named set of operations, which describes a finer step. SAP gives the example of function `PTIP`, which hands every
entry of the day's input table to a rule one entry at a time, and function `ACTIO`, which calls a rule whether or not
the day has any entries.

The documentation groups functions by task:

[cols="2,3,3",options="header"]
|===
| Kind of function | What it does | Example from the documentation
| Sets a switch | Sets an option when the schema is generated, for example whether an administrator receives a message mail | `OPPT`
| Imports data | Fills the internal tables with the day's data: the work schedule, infotype records, time pairs | `P2001` imports the day's absences
| Calls a rule | Runs a personnel calculation rule regardless of table content | `ACTIO` with rule `TE20`
| Processes a table line by line | Hands each line of an internal table to a rule | `PTIP` with rule `TO13`
| Fixed processing | Performs a specific task without a rule | `PBRKS` reads the break specifications of the daily work schedule
|===

Source: https://help.sap.com/docs/SAP_S4HANA_ON-PREMISE/c6c3ffd90792427a9fee1a19df5b0925/d734e153a217424de10000000a174cb4.html[Schemas and Functions in Time Evaluation].

SAP delivers several standard schemas and recommends copying one as a model rather than changing it. The report asks for the
schema on its selection screen. Two of them matter most for hourly staff:

* *TM00* evaluates time events: employees who record actual times at time recording terminals or plant data collection
  systems, or in the Time Events infotype (2011).
* *TM04* evaluates time data entered online, in hours or as clock times, for employees who enter only exceptions to the
  work schedule and for those who record actual times.

The other delivered schemas are TM01 (exceptions to the work schedule, entered as clock times), TM02 (external services)
and TC00, which belongs to payroll. Choose the model by how the time data is entered, how much of it is recorded, and
what results are needed.

To see or change a schema, the documentation gives the menu path Human Resources, Time Management, Administration, Tools,
Maintain Schema. The overview of the personnel calculation rules that TM00 delivers lists them by processing step:
initialization (`MODT`), day processing and data retrieval (`TD10` to `TD90`), error checks (`TE10` to `TE30`), planned
versus actual comparison (`TL10`, `TF10`), overtime (`TO10` to `TO20`), overtime compensation (`TC20`), balance
formation (`TR10` to `TR60`) and final processing (`TS10` to `TS30`).

Sources: https://help.sap.com/docs/SAP_S4HANA_ON-PREMISE/c6c3ffd90792427a9fee1a19df5b0925/1135e153a217424de10000000a174cb4.html[Criteria for Selecting a Schema], https://help.sap.com/docs/SAP_S4HANA_ON-PREMISE/c6c3ffd90792427a9fee1a19df5b0925/8334e153a217424de10000000a174cb4.html[Basic Concepts and Structure of Schema Processing], https://help.sap.com/docs/SAP_S4HANA_ON-PREMISE/c6c3ffd90792427a9fee1a19df5b0925/2335e153a217424de10000000a174cb4.html[Personnel Calculation Rules in Time Evaluation: Overview].

== The pipeline from clock event to payroll

The diagram follows one employee's data from the time clock to payroll. The boxes are the stages, and the labels under a
name are the internal tables or database areas that hold the data at that stage.

[mermaid]
----
flowchart LR
  A["Time events<br/>clock-in 08:00, clock-out 12:30"] --> B["Pair formation<br/>time pairs per day"]
  B --> C["Provide data<br/>work schedule TZP, input table TIP"]
  C --> D["Rules and checks<br/>errors, planned vs actual, overtime"]
  D --> E["Balances<br/>day balances TES, period balances SALDO"]
  D --> F["Time wage types<br/>DZL, overtime ZML"]
  E --> G["Store results<br/>cluster B2"]
  F --> G
  G --> H["Payroll<br/>IMPRT B2 reads table ZL"]
----

The stages in words:

. *Time events are collected.* A time recording terminal, or an administrator in the Time Events infotype (2011), supplies
  clock-in and clock-out entries.
. *Pair formation* turns events into time pairs. SAP describes it as part of time evaluation, in three steps: assign each
  event to the current or previous day, form pairs for each day, and, if plant data collection is used, generate time
  tickets for incentive wages.
. *Data is provided.* The schema reads the planned working time of the employee's daily work schedule into a table of
  planned time points (`TZP`) and puts the day's time pairs and manually entered attendances and absences into the work
  table `TIP`, the day's input.
. *Rules and checks* run function by function. Entries that stay relevant are collected into the output table `TOP`,
  which becomes the new `TIP` for the next step.
. *Balances and time wage types are formed* at the end of day processing. Time types are cumulated into the daily
  balances table `TES`. Time wage types are selected into `DZL`, and overtime wage types into `ZML`.
. *Results are stored* in cluster B2, and the function `CUMBT` moves the daily balances to `ZES`, adds them to `SALDO` and
  moves the wage types from `DZL` to `ZL`.
. *Payroll imports* table `ZL` with function `IMPRT B2` and values it.

Sources: https://help.sap.com/docs/SAP_S4HANA_ON-PREMISE/c6c3ffd90792427a9fee1a19df5b0925/a9f1e0535e56424de10000000a174cb4.html[Pair Formation], https://help.sap.com/docs/SAP_S4HANA_ON-PREMISE/c6c3ffd90792427a9fee1a19df5b0925/1e33e05320a7424de10000000a174cb4.html[Providing Time Data], https://help.sap.com/docs/SAP_S4HANA_ON-PREMISE/c6c3ffd90792427a9fee1a19df5b0925/1b33e05320a7424de10000000a174cb4.html[Processing Using Internal Tables], https://help.sap.com/docs/SAP_S4HANA_ON-PREMISE/c6c3ffd90792427a9fee1a19df5b0925/0635e153a217424de10000000a174cb4.html[Balance Formation in Time Evaluation].

[source,text]
----

OPPT                     * switch: mail the administrator if messages arise
MOD                      * initialization: calls a rule that sets groupings

PTIP   TO13  GEN         * call rule TO13 for each TIP entry: max. daily time

DAYMO                    * set day grouping: workday, Sunday, public holiday

== Time types, balances and time wage types

*Time types* are the calculation tools of time evaluation. Each is a bucket for durations that mean the same thing
to the business: for example overtime hours, productive hours, planned time, a paid or an unpaid break. Time
evaluation adds, subtracts and compares the buckets, and moves hours from one to another. Which time types are stored,
and whether a type goes into the daily balance or the period balance, is set in the time types table (`T555A`, with the
view `V_T555A`).

*Balances* are the stored values of time types. The daily balances are in table `TES` while the day is processed, then
in table `ZES`. The period balances, which accumulate over the evaluation period (the flextime balance is the standard
example), are in table `SALDO`. SAP's example of table `TES` for one day uses time types `0002` (planned time),
`0010` (attendance), `0040` (overtime worked) and `0050` (productive hours).

*Time wage types* are different from time types. A time wage type is a wage type that time evaluation selects for payroll,
and it carries a number, usually hours, but no money. Payroll values it, so the hourly rate is applied only there.
Time evaluation selects them with the time wage type selection rule table (`T510S`, view `V_T510S`), by comparing each
`TIP` entry with the rules for its processing type. For the entries of planned working time (processing type `S`) it writes
to table `DZL`, and for overtime (processing type `M`) to table `ZML`, which holds only overtime wage types so that they
can be processed separately. Each selected time wage type carries an indicator `IFTYP` that tells payroll where it came from:
`S` planned work, `M` overtime and `A` absence.

== Chloe's Tuesday, step by step

Chloe Martin clocks in and out as follows on Tuesday 10.03.2026. The times are invented, and the calculations are done
by hand for this page, not taken from a system run.

[cols="2,2,3",options="header"]
|===
| Stage | What the data looks like | Result
| Time events | 08:00 clock-in, 12:30 clock-out, 13:00 clock-in, 16:30 clock-out | Four events, all assigned to 10.03.2026
| Pair formation | 08:00 to 12:30 and 13:00 to 16:30 | Two time pairs
| Duration of the pairs | 4.50 h + 3.50 h | 8.00 h attendance
| Gap between the pairs | 12:30 to 13:00 | 0.50 h, which is not a pair, so it is not paid (her unpaid break)
| Planned time | 8.00 h from her daily work schedule | Planned equals actual: no flextime change
| Time wage type | Entry with processing type `S` | 8.00 h, `IFTYP` `S`, stored in `ZL`
| Payroll values the hours | 8.00 h x 14.00 EUR | 112.00 EUR for the day
|===

A week of five such days is 5 x 8.00 = 40.00 hours, and 40.00 x 14.00 = 560.00 EUR before any deductions. The deductions
are payroll's job and are not shown here.

Two variations show why the rules matter.

* *A night shift.* If Chloe clocks in at 22:00 on 12.03.2026 and out at 06:00 the next morning, a clock-out in the early
  morning can be assigned to the previous day. SAP's documentation shows the result with 24 hours added to the clock-out
  time, so the time pair is 22:00 to 30:00, which is 8.00 hours, and it belongs to the day the shift started.
  An event is assigned only to the current or the previous day, never to the next.
* *A longer day.* If on 11.03.2026 she works 08:00 to 12:30 and 13:00 to 17:30, the attendance is 9.00 hours against 8.00
  planned. The extra hour is a candidate for overtime. Whether it becomes an overtime wage type (`IFTYP` `M`) or time
  off depends on the overtime rules and the overtime compensation type that the company has set up.

== Who is evaluated: the Time Management status

Not every employee goes through time evaluation. The Time Management status in the Planned Working Time infotype (0007)
decides how an employee is handled. In SAP's documentation:

* Status `0`: the employee is not selected for time evaluation, and payroll determines the time wage types itself.
* Statuses `1` and `2`: the employee's actual times are recorded and evaluated, and the time wage types go to payroll.
* Status `9`: only deviations from the work schedule are recorded, and planned times are the basis.
* Status `7`: time evaluation runs for special accounts, such as accruing absence quotas, without passing results to
  payroll.
* Status `8`: external employees, whose results go to Materials Management.

Chloe, whose actual times are recorded, would have status `1`. Ana Torres, a salaried employee with a monthly basic pay
that does not depend on hours, could be handled without time evaluation (status `0`). These assignments are choices of the
example.

== Running the report and reading the results

You start the report from the menu path given above or with transaction PT60, and a company usually schedules it to run
every night. The selection screen offers these parameters:

* the personnel numbers to evaluate,
* the evaluation schema,
* the time statement variant, which controls how the results are shown,
* the display variant for the log,
* a date for forced recalculation, normally left empty, used to redisplay a day or after retroactive changes to working
  time specifications,
* the date up to which to evaluate, which defaults to the current date,
* program options for technical information in the log.

Each run produces a log of the processing steps, and the results are stored per employee and period in cluster B2.
Cluster B2 holds, among others: `ZES` daily balances, `SALDO` cumulated balances, `ZL` time wage types, `PT` time pairs,
`FEHLER` the messages of the run, and `C1` and `ALP` for cost assignment and for a different rate of payment. You can
view clusters through the menu path Human Resources, Time Management, Administration, Tools, Tool Selection. At the end of
a run the date from which the next run should start is written to the Payroll Status infotype (0003).

Requires an SAP system; not run here.

== The handover to payroll

Table `ZL` of cluster B2, together with `ALP` and `C1`, is the interface between time evaluation and payroll. In payroll,
function `IMPRT B2` imports the time wage types from cluster B2 and values them. Payroll often runs before the end of its
period, so time evaluation has not yet covered every day. SAP's example: payroll runs on the fifteenth and time
evaluation has processed the days up to and including the fourteenth. For the remaining days payroll projects the planned
working time, using schema TC00 or TC04, combined with attendances and absences already recorded.

For Chloe, assume that her March 2026 payroll runs on 15.03.2026 and that her schedule is Monday to Friday in this
illustration. The days 16.03.2026 to 31.03.2026 hold 12 working days, so the projection is 12 x 8.00 = 96.00 hours,
or 96.00 x 14.00 = 1,344.00 EUR for that part of the month. When time evaluation later delivers the real hours, payroll
settles any difference in the next period by retroactive accounting. To trigger that, payroll writes a date into the
field Earliest MD change of the Payroll Status infotype (0003), which requires that the employee takes part in time
evaluation (a Time Management status other than `0`). The same field is set when time infotypes of an already
accounted period are created or changed. If a third-party payroll system is used, table `ZL` is also its interface,
and the report `RPTEZL00` supplies it.

== What older books show, and what has changed

The book SAP ERP HCM: Technical Principles and Programming, 1st edition (2013), describes time evaluation as the core
process of Personnel Time Management: transaction PT60, the driver program RPTIME00, schemas and personnel calculation
rules that turn captured time into wage types and quota accruals, and the cluster tables that store the results. The
concepts on this page are the same, and the documentation for 2025 FPS02 still describes RPTIME00, the schemas and the
tables the same way. What has changed is the product around them. The book was written for SAP ERP HCM. In SAP S/4HANA
2025 these functions come from SAP HCM for SAP S/4HANA, which needs a separate license, and the business function for it
is active by default, so the older compatibility mode is no longer an option. The core hybrid model, in which core HR is held in
SAP SuccessFactors and time management runs in H4S4, is covered on the landscape page.

Source for the H4S4 statements: https://help.sap.com/docs/SAP_S4HANA_ON-PREMISE/c6c3ffd90792427a9fee1a19df5b0925/18cbddfa5691416d8f004dc97ac98634.html[SAP HCM for SAP S/4HANA].

== Summary

* Time evaluation, run with the report RPTIME00 (transaction PT60), turns recorded time into time wage types, balances and
  quota updates.
* A schema is an ordered list of functions, some of which call personnel calculation rules. SAP delivers schemas such as
  TM00 (time events) and TM04 (data recorded in hours or clock times) as models to copy.
* Pair formation makes time pairs from clock events and assigns each event to the current or previous day.
* Time types are buckets for durations and form the balances `TES`, `ZES` and `SALDO`. Time wage types, which carry
  hours only, are selected into `DZL` and `ZML` and stored in table `ZL`.
* Payroll imports `ZL` with `IMPRT B2` and applies the rate: Chloe's 8.00 hours on 10.03.2026 become 8.00 x 14.00 =
  112.00 EUR. The Time Management status of infotype 0007 decides who is evaluated.
