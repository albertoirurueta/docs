A person who has used SAP HR on screen never sees a table: an administrator types a personnel number, opens Basic Pay and
sees fields. Behind each screen the data sits in database tables, and a developer, a report writer or a consultant who
has to find a value, build a report or explain why a number is wrong needs to know which table holds what. SAP HR does
not store everything in the same way. Master data and organizational structures sit in ordinary tables that can be read
with a query, while time evaluation results and payroll results are packed into big binary records called clusters, which
only special functions can open. This page gives the map: which table families exist, how a record is addressed, how the
families relate to each other, and where the example employee Ana Torres of Example Trading Co. would leave her data. It
is written against SAP S/4HANA 2025 FPS02 on premise and Private Edition, where the HR functions come from SAP HCM for SAP
S/4HANA (H4S4). Reading the tables in a real system requires an SAP system; not run here.

== Key terms

* xref:erp/sap/human-resources/glossary.adoc#infotype[Infotype]: a record type of HR master data, stored in a table
  named after its four-digit number.
* xref:erp/sap/human-resources/glossary.adoc#personnel-number[Personnel number]: the number that identifies one employee
  and that is part of the key of almost every HR record.
* xref:erp/sap/human-resources/glossary.adoc#transparent-table[Transparent table]: a database table that can be read
  field by field with an ordinary query.
* xref:erp/sap/human-resources/glossary.adoc#cluster[Cluster]: a group of data objects, such as fields and internal
  tables, that the system packs into one record of a cluster file and reads back as a whole.
* xref:erp/sap/human-resources/glossary.adoc#payroll-result[Payroll result]: the outcome of a payroll run for one
  employee and one period, stored in cluster file PCL2.
* xref:erp/sap/human-resources/glossary.adoc#time-evaluation[Time evaluation]: the program that turns recorded working
  time into time results for payroll, stored in cluster B2 of PCL2.
* xref:erp/sap/human-resources/glossary.adoc#customizing-table[Customizing table]: a table that holds the settings of a
  company, such as the list of personnel areas, instead of employee data.
* xref:erp/sap/human-resources/glossary.adoc#object-type[Object type]: the kind of an Organizational Management object,
  such as organizational unit, job, position or person.

== The running example: Example Trading Co.

All HR pages on this site use one fictitious business, Example Trading Co. All keys, names, numbers and dates are invented
example values chosen for this site. They are not values delivered by SAP, and a real system defines its own. Dates are
written DD.MM.YYYY, as an SAP screen shows them, and the high date, the end date of a record that has no planned end, is
31.12.9999.

* Personnel area `EX01` "Example Trading Co.", personnel subareas `0001` "Head office" and `0002` "Warehouse", employee
  group `1` "Active", employee subgroups `AA` "Salaried staff" and `AB` "Hourly staff", payroll area `E1` "Monthly EX01".
* Organizational units `50000001` Example Trading Co., `50000002` Sales and `50000003` Warehouse; positions `51000001`
  Sales Manager, `51000002` Sales Clerk and `51000003` Warehouse Clerk.
* `00001234` Ana Torres, Sales Manager, hired 01.03.2024, basic pay 4,000.00 EUR a month (the featured employee);
  `00001235` Ben Okoye, Sales Clerk, hired 01.09.2024; `00001236` Chloe Martin, Warehouse Clerk, hired 15.01.2025,
  hourly staff paid 14.00 EUR an hour.
* The illustrative payslip of Ana for March 2026 uses flat example rates, not the rules of any country: gross 4,000.00;
  employee social contributions 20.00% = 800.00; income tax 15.00% of (4,000.00 minus 800.00) = 3,200.00 x 15% = 480.00;
  net 2,720.00 (4,000.00 - 800.00 - 480.00). Employer contributions 21.00% of gross = 840.00, so the total employer cost
  is 4,840.00.

== The map: four families of HR data

SAP HR stores its data in four families, and the quickest way to find a value is to know which family it belongs to.

[cols="2,3,4",options="header"]
|===
| Family | What it holds | Where it is stored

| Master data and time data of employees
| The infotype records of an employee: organizational assignment, basic pay, absences.
| One transparent table `PAnnnn` per infotype, for example `PA0001` and `PA0008`.

| Organizational structure
| The objects of the organizational plan (units, jobs, positions) and the relationships between them.
| Tables `HRPnnnn` per infotype, for example `HRP1000` for objects and `HRP1001` for relationships.

| Derived results
| Time evaluation results, payroll results, generated schemas, change documents.
| Cluster files `PCL1` to `PCL4`, each holding clusters with a two-character name such as `B2` or `RX`.

| Settings and checks
| The values that records may use and what each means: personnel areas, subareas, employee groups, infotype characteristics.
| Customizing tables such as `T500P`, `T001P`, `T503`, `T582A` and `T777D`.
|===

The next sections walk through the families one by one and then show how they connect.

== Master data: the PAnnnn tables

SAP Help describes the storage of HR master data and time data in one sentence: they are stored in the transparent tables
`PAnnnn`, and besides the keys these tables contain the data of the infotype `nnnn`. The keys are the client, the
personnel number, the subtype, the object identification, the lock indicator, the validity period and a sequential number.
Reading that list as a story: the client separates companies on one system, the personnel number says whose record it is,
the subtype and the object identification tell apart parallel records inside one infotype (for example the permanent
residence and the temporary address), the lock indicator marks a record that is locked against changes, the validity
period says from when to when the record applies, and the sequential number separates records that would otherwise have
the same key.

The ABAP Dictionary also contains a structure `Pnnnn` for each infotype. It matches the table `PAnnnn`, except that the
client is missing. A program that wants to use an infotype declares it, and the system then creates an internal table with
the name `Pnnnn` and the structure `Pnnnn` and fills it with all records of the infotype for the personnel number being
processed. The fields `BEGDA` and `ENDDA` of that structure are the start and end of the validity period.

In the example, the Basic Pay infotype (0008) of Ana Torres is read as rows of the table `PA0008`. A row is identified by
the personnel number `00001234` and its validity period, and its data fields carry the amount. The table shows how the
first rows of the three employees would look, with the key written as the SAP Help list describes it and the data
described in words, because this page does not claim field names it did not verify. Showing the rows requires an SAP
system; not run here.

| `PA0001` (Organizational Assignment)
| `00001234`
| 01.03.2024 to 31.12.9999
| Personnel area `EX01`, personnel subarea `0001`, employee group `1`, employee subgroup `AA`, payroll area `E1`.

The validity periods follow the hire dates of the running example, and the high date 31.12.9999 means that no end is
planned. If Ana received a raise on 01.01.2027, the system would end the first `PA0008` record on 31.12.2026 and add a new
record that starts on 01.01.2027, so the table would hold both records and the history stays complete.

Recruitment follows the same pattern with a different prefix: SAP Help states that recruitment data is stored in the
transparent tables `PBnnnn`, keyed by the applicant number instead of the personnel number.

== Customer infotypes and table infotypes

A customer that needs data the delivered infotypes lack creates a customer infotype in the number range 9000 to 9999. SAP
Help documents two ways to do this. With the Create Infotype transaction (PM01) the system creates the table `PA9nnn` and
the structures `PS9nnn` and `P9nnn`; the page on xref:erp/sap/human-resources/infotypes.adoc[infotypes] explains that route. With the Personnel Planning Infotype
Copier, the transaction PPCI, a developer first creates a structure named `HRI9nnn` in the ABAP Dictionary with the
infotype-specific fields, and the copier generates the other repository objects. For an Organizational Management
infotype in the customer range, the help page "Creating Transparent Tables" says that after a customer infotype `9nnn`
exists, the function Create transparent table of PPCI creates the table `HRP9nnn`. The infotype copier also writes entries
into the Customizing tables `T777T` (infotype texts) and `T778T` (infotypes), and the developer maintains the entry in
`T777I` (infotypes per object type) with the function Check environment.

SAP Help separates field infotypes from table infotypes. A table infotype stores a repeating part, such as several lines
of text, beside its fixed fields, and the copier page for table infotypes names the structures `HRI9nnn` and `PT9nnn`. The
archiving documentation shows that Customizing table `T777D` holds two table names for an infotype, `DBTAB` and `TBTAB`,
where the second is the table of the repeating part. This page does not describe the table part further: the exact name
pattern and key fields of the tables that hold it were not confirmed on the help pages used here, so look them up in the
Customizing table `T777D` and the ABAP Dictionary of your own system.

== Organizational Management: the HRPnnnn tables

The organizational plan uses the same infotype idea as master data, but its tables have a different prefix. SAP Help for
the learning component states the pattern in a table of its persistence: objects and their attributes are stored in
`HRPnnnn`, and relationships in `HRP1001`. The archiving documentation names both tables explicitly: `HRP1000` and
`HRP1001` are the two tables with special handling. So the existence of each object of the example, the unit Sales, the job
Manager or the position Sales Manager, is a record of `HRP1000`, and every link between two objects is a record of
`HRP1001`.

The special handling of `HRP1001` shows how the relationships are kept. Every relationship is stored twice, once in each
direction, and the documentation says that the table `HRP1001` contains either both records of a relationship or neither.
For that reason the archiving of OM data uses a helper table `HRP1001_ARCH` for the inverse records of relationships that
have been archived or deleted, so that no record is left without its counterpart.

The table shows the relationship records that tie Ana's world together. The columns are described in plain words, because
the field names were not verified for this page. Each relationship is written with its letter and three-digit subtype as
in the page on xref:erp/sap/human-resources/organizational-management.adoc[Organizational Management], and every row has an inverse record in the table that is not repeated here.

== Cluster files: PCL1 to PCL4

Some HR data is not a set of rows that someone will query one by one. A payroll result for one employee and one month
consists of many internal tables of different shapes, and SAP HR stores that whole bundle as one record. The storage is a
cluster file. SAP Help names four, and all four have the same structure, the same one as the general import and export file
`INDX` that other applications use.

[cols="1,4",options="header"]
|===
| File | What it contains

| `PCL1`
| The basis for the HR work area data: information from time data recording, for example incentive wage time tickets or
infotype supplement texts. The time recording clusters `B1` and `B2` belong to the time area (see below).

| `PCL2`
| Derived information, such as payroll results, and all generated payroll schemas.

| `PCL3`
| Applicant data.

| `PCL4`
| The change documents for HR master data and recruitment.
|===

A record of a cluster file is addressed by the client, by the field `RELID` and by the field `SRTFD`. The `RELID` is the
relation ID, a two-character name that says which kind of cluster the record is, for example `RX` for the payroll result
of country X or `TE` for trip costs data. The field `SRTFD` holds the cluster key, whose structure depends on the cluster
and is defined in an include named `RPCnxxy0`, where `n` is the file number (1 to 4), `xx` the cluster name and `y` a
country indicator, 0 for an international cluster or a country grouping from table `T500L` for a national one. The
personnel number is usually the first component of that key. Forty bytes of `SRTFD` are available for the key.

For the payroll result cluster `RX`, the data definition is in the include `RPC2RX00`, and its key is built from the DDIC
structure `PC200`, which contains the personnel number (`PERNR`) and a sequential number (`SEQNO`). In the example, the
payroll result of Ana Torres for March 2026, whose gross is 4,000.00 and net 2,720.00, would be one record in `PCL2` with
`RELID` `RX` and a key that begins with `00001234`. The result tables that the payroll documentation names among the
tables common to all country versions are `WPBP` (work place and basic pay), `RT` (results table with the result wage
types of the period), `CRT` (cumulative results table) and `BT` (payment information). All of them travel inside that one
record and are not separate database tables.

The time area has its own clusters in the same files. SAP Help states that clusters `B1` and `B2` in `PCL1` and `PCL2` are
relevant to time evaluation, as is cluster `PS`, which stores the generated schema. The results of time evaluation sit in
`PCL2` with `RELID` `B2`. For Chloe Martin (`00001236`, hourly staff), the daily results of a time evaluation run, the
base for the paid hours at 14.00 EUR an hour, would be a record of `B2` with her personnel number in the key. Which
fields the B2 internal tables hold is a matter for the time pages of this section; the declustering documentation lists the
names of 30 internal tables of B2, among them `ZL`, `SALDO`, `ZES` and `WPBP`.

The cluster data is never read with a plain query. SAP Help states that the files are managed with the ABAP commands
`IMPORT` and `EXPORT`, and that programs should use the delivered macros, named `RP-IMP-Cn-xx` for import and
`RP-EXP-Cn-xx` for export, where `n` is the file number and `xx` the cluster. The macros keep the access consistent, and a
change in the way a cluster is stored is then made in one place. In practice a developer uses a delivered function or macro
for the cluster and does not write a select on `PCL2`; the exact function names are in the in-system documentation of the
release. Reading a cluster requires an SAP system; not run here.

== How payroll uses the tables

The page "Payroll-Relevant Files" gives the shortest description of how the families work together. For payroll the
system requires the `Pnnnn` data that has been entered in the infotypes, the file `PCL1` with the primary information from
master data and time recording, and the file `PCL2` with the secondary, derived information. When payroll starts, the
system imports the relevant master data from the `Pnnnn` files, for example basic pay and tax class, and imports the time
data from `PCL1` into the internal table `IT`. It imports the results of previous months from the table `ORT`, for example
to form averages. It processes this data and saves the payroll results and the generated schemas in `PCL2`.

For the March 2026 run of payroll area `E1`, that means the following. The payroll reads the rows of `PA0001` and `PA0008`
for Ana (`00001234`) and finds 4,000.00 EUR of monthly basic pay. It calculates the illustrative figures: gross
4,000.00, social contributions 800.00, tax 480.00, net 2,720.00. It then writes the result as a new record of `PCL2`, and
the source rows of `PA0008` stay unchanged. This is why correcting a payroll result is never a change in a table: the
master data is corrected, and a new run writes a new result.

== Declustering: opening the clusters to queries

Because a cluster is a binary string, the contents of `PCL2` cannot be queried field by field at the database layer. SAP
Help describes a mechanism for this, the business function HCM Declustering Tools: it creates simple transparent tables
in addition to the cluster tables, stores the existing cluster data in them and updates them synchronously, so that
complex queries and aggregations of payroll and time results can run in the database. The documentation describes two
setups, a side-by-side one, where a Business Suite system fills transparent tables on a columnar system such as SAP HANA,
and a one-box one, where the transparent tables are filled in the same system. For time evaluation, the Customizing
activity Maintain Declustering Registry for Time Evaluation Results creates 30 transparent tables for `PCL2` with `RELID`
`B2`, named `P2B2_` followed by the B2 table name, for example `P2B2_ZL` for the table `ZL` and `P2B2_SALDO` for `SALDO`.
An initial load report fills them from existing results, and archiving the cluster data deletes the matching rows of the
transparent tables. SAP Help adds that for payroll one international table is created for a reused international table
such as `RT`, and that an existing transparent table `HRPY_WPBP` for the international table `WPBP` cannot be used for
declustering because it lacks the split, so a new table is created.

Whether declustering is active, and which tables exist, depends on the system, so look in the ABAP Dictionary of your
system before you write a query against a declustered table.

== Check and Customizing tables

The fourth family does not hold employee data but the rules and lists that the other tables are checked against.
Examples from SAP Help are:

* `T500P` holds the personnel areas, `T001P` the personnel areas and subareas, and `T503` the employee groups and
  subgroups. Delivered foreign key checks of an infotype use these three tables: for infotype 0001, the personnel area and
  subarea are checked against `T001P`, the personnel area against `T500P`, and the employee group and subgroup against
  `T503`. In the example, the combination personnel area `EX01` and subarea `0001` must exist in `T001P`, and employee
  group `1` with subgroup `AA` must exist in `T503`, or the system rejects the record.
* The infotype characteristics are determined by Customizing tables: `T582A` holds the basic characteristics (single
  screen, list screen, time constraint), `T582S` the short texts, `T777A` the technical characteristics (database table,
  dialog module), and `T77ID` the name of the data field structure `PSnnnn`. `T591A` holds the subtypes, `T588B` the infotype
  menus and `T588Z` the dynamic actions. The Create Infotype transaction (PM01) maintains the basic characteristics.
* Customizing table `T777D` holds, per infotype, the name of its database table (`DBTAB`) and, for a table infotype, of
  the table of its repeating part (`TBTAB`), and the Customizing table `T777I` lists the infotypes per object type.
* `T500L` holds the country groupings that the national cluster names and key includes refer to.

The delivered classes that read these tables follow the naming convention `CL_HR_<table name>`, for example `CL_HR_T500P`,
`CL_HR_T001P` and `CL_HR_T503`. A program that needs a value from one of these tables should call the class rather than
select from the table, because the class offers central buffering. The Customizing itself is maintained in the Implementation
Guide (IMG), not by editing table rows directly. Showing the entries requires an SAP system; not run here.

== How to find a value: a decision guide

Use the family to choose the access path. Each line names the path and the example it covers.

. Master data of one employee, for example Ana's current basic pay: the infotype `0008`, table `PA0008`, read with the
  delivered infotype reading functions or the infotype declaration of a report. The page on xref:erp/sap/human-resources/infotypes.adoc[infotypes] lists the key
  infotypes and their values.
. Organizational facts, for example who is the holder of Sales Manager: `HRP1001` with the relationship `A008`, read with
  the delivered OM reading functions, as the page on xref:erp/sap/human-resources/organizational-management.adoc[Organizational Management] describes.
. Time results, for example Chloe's evaluated daily hours: cluster `B2` of `PCL2`, through the delivered macros or
  functions, or the declustered transparent tables if declustering is active.
. A payroll result, for example Ana's March 2026 net of 2,720.00: cluster `RX` of `PCL2` (or the cluster of the country
  version) through the delivered macros, or the declustered tables if active.
. What a code in a field means or whether it is allowed, for example employee subgroup `AB`: the Customizing tables
  `T503` and the others of the check family, read with the delivered `CL_HR_` classes.

In all cases, the in-system documentation of the delivered functions, available in the function builder (transaction
SE37), is the reference for their parameters; this page does not name function modules whose existence was not confirmed
in the help pages.

== What older books show, and what has changed

The book SAP ERP HCM: Technical Principles and Programming, 1st edition (2013), has a chapter on the data structures of HR.
It explains the same families as this page: the PA tables and their key, the infotype structures, the organizational
tables with a fixed part and a table part, the personnel planning relationships and the cluster files for time and payroll
with their cluster directories and import and export macros. The concepts are unchanged and remain a good guide.

What has changed is the product and the tools around them. The book describes SAP ERP HCM, while
SAP S/4HANA with SAP HCM for SAP S/4HANA (H4S4) runs on SAP HANA, where SAP documents the declustering tools that make
the cluster results queryable at the database layer; the consulted copy of the book does not mention declustering at all.
SAP SuccessFactors, the cloud alternative, uses a different data model that later pages cover. The book also names the
tables of the repeating part of a table infotype, which this page leaves out because the help pages used here do not
confirm the naming: check them in the Customizing table `T777D` and in the ABAP Dictionary of your own system.

== Summary

* HR data lives in four families: infotype tables `PAnnnn` for employee master data and time data, tables `HRPnnnn` for
  Organizational Management, cluster files `PCL1` to `PCL4` for derived results, and Customizing tables for rules and checks.
* A `PAnnnn` record is keyed by the client, the personnel number, subtype, object identification, lock indicator, validity
  period and a sequential number. The history of Ana's basic pay is several rows with different validity periods.
* Organizational objects are records of `HRP1000` and their links records of `HRP1001`, stored in both directions, and a
  customer infotype in the OM range gets a table `HRP9nnn`.
* Time evaluation results (cluster `B2`) and payroll results (cluster `RX`) are packed into `PCL2` records addressed by the
  `RELID`, the key `SRTFD` and the personnel number, and are read through macros and functions, not by a query.
* The declustering tools fill transparent tables from the clusters so that queries and aggregations can run in the
  database, and the check tables such as `T500P`, `T001P` and `T503` define what the other tables may contain.
