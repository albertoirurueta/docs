= Organizational Management
:description: How SAP Organizational Management stores a company's functional structure as objects (organizational units, jobs, positions, persons) linked by relationships, and how an evaluation path walks that structure, for SAP S/4HANA 2025 FPS02 on premise and Private Edition with HCM for SAP S/4HANA.
:keywords: SAP, HR, Organizational Management, OM, object type, organizational unit, position, job, person, infotype 1000, infotype 1001, relationship, evaluation path, O-S-P, chief position, organizational plan, HRP1000, HRP1001

include::partial$ai-disclaimer.adoc[]

A company is more than a list of employees: it has departments, roles inside those departments, and a boss for each
department. SAP Organizational Management, often shortened to OM, is the part of the Human Resources software where that
picture is stored. It does not describe a person. It describes the structure: which units exist, which positions they
contain, which general kind of work (job) each position is, and who manages whom. A newcomer meets it when an approval
has to find "the manager of this employee", when a report has to list everyone below a department, or when an
authorization has to be limited to one part of the company. After reading this page you will know the four object types
of the structure, how one relationship is stored from both ends, how the chief position of a unit is recorded, and how an
evaluation path collects objects from a starting point. The page is written against SAP S/4HANA 2025 FPS02 (on premise and
Private Edition), where the Human Resources functions come with SAP HCM for SAP S/4HANA. SAP states that this component
needs a separate license, and that from SAP S/4HANA 2025 the business function for it is active by default, so HCM can no
longer run in compatibility mode. SAP SuccessFactors is a different product with its own data model and is not covered.

== Key terms

* xref:erp/sap/human-resources/glossary.adoc#organizational-management[Organizational Management]: the component that
  stores the task-related, functional structure of a company.
* xref:erp/sap/human-resources/glossary.adoc#object-type[Object type]: the kind of an object, written as a letter
  code: `O` organizational unit, `S` position, `C` job, `P` person.
* xref:erp/sap/human-resources/glossary.adoc#organizational-unit[Organizational unit]: a functional unit such as a
  department, a group or a project team.
* xref:erp/sap/human-resources/glossary.adoc#position[Position]: an existing or required place for one employee inside
  an organizational unit.
* xref:erp/sap/human-resources/glossary.adoc#job[Job]: a general classification of a kind of work, shared by many
  positions.
* xref:erp/sap/human-resources/glossary.adoc#relationship[Relationship]: a stored link between two objects, kept in
  infotype 1001.
* xref:erp/sap/human-resources/glossary.adoc#evaluation-path[Evaluation path]: a recipe that says which relationships
  to follow from a start object, and so which objects to collect.
* xref:erp/sap/human-resources/glossary.adoc#chief-position[Chief position]: the position that manages an
  organizational unit.

== The example used on this page

All HR pages on this site use one fictitious business, Example Trading Co., the same company as in the Finance pages
(company code `EX01`). Every number, name and date below is an invented example value, not a value delivered by SAP. This
page adds one thing to the shared example: it assumes the structure below exists from 01.01.2024, before the first hire.

* Organizational units (type `O`): `50000001` Example Trading Co. (the top unit), `50000002` Sales and `50000003`
  Warehouse.
* Jobs (type `C`): `52000001` Manager and `52000002` Clerk.
* Positions (type `S`): `51000001` Sales Manager (job Manager, in Sales), `51000002` Sales Clerk (job Clerk, in Sales)
  and `51000003` Warehouse Clerk (job Clerk, in Warehouse). The Sales Manager is the chief position of Sales.
* Persons (type `P`, shown by personnel number): `00001234` Ana Torres holds the Sales Manager position, `00001235` Ben
  Okoye holds Sales Clerk and `00001236` Chloe Martin holds Warehouse Clerk.

== Functional structure versus enterprise structure

SAP keeps two different pictures of a company. The enterprise structure (client, company code, personnel area, personnel
subarea) is the administrative one: it decides which rules apply to an employee for payroll, time and accounting. The
documentation for Personnel Administration says that the personnel area, for instance, is used only in Personnel
Administration and is assigned exactly one company code. The organizational plan is the other picture. SAP describes it
as the representation of the task-related, functional structure of the enterprise, built with the tools of Organizational
Management, and says that it differs from the administrative structure whose elements matter to payroll or accounting.

The two pictures meet in a person. When a person is assigned to the organizational plan as the holder of a position, and
also to the enterprise structure through a personnel subarea, the functional and the administrative structure touch. In
the example, Ana Torres holds the Sales Manager position (functional) and belongs to personnel area `EX01`, personnel
subarea `0001` (administrative). Neither fact is derived from the other unless the two components are integrated, which
the section on integration below explains.

== Objects and object types

In OM everything in the structure is an object, and every object has an object type, written as a letter code. An
organizational plan is normally built by assigning objects of these types to each other: organizational unit, position,
job and task. The documentation names the codes in several places: organizational unit is `O`, position is `S`, job is
`C` and person is `P`. (A task, which describes work that a position performs, and the objects used for workflow are also
part of the model; this page keeps to the four types of the example.)

* An organizational unit represents a functional unit of the enterprise, such as a marketing department, a group or a
  project team. Assigning units to each other in a hierarchy gives the organizational structure.
* A position represents existing or required personnel capacity in a unit. A position is typically staffed by one
  employee, although more than one employee can be assigned to it.
* A job is a general classification of task areas, a standard description of an activity that a person can perform.
  Many positions can share one job: in the example both Sales Clerk and Warehouse Clerk are positions of the job Clerk.
* A person is the employee. In the structure the person object stands for the personnel master record.

An object is identified by an object ID, a number given when the object is created, that cannot be changed afterwards.
Customizing decides which number ranges are available and whether the system or the user assigns the number. This is why
the example gives each object a number: units start with `+5000...+`, positions with `+5100...+` and jobs with `+5200...+`.
That pattern is an invention of the example, not an SAP rule.

== Infotype 1000: the existence of an object

OM stores the properties of an object in infotypes, just as Personnel Administration does for an employee (the page on
infotypes explains the idea). The basic data of an object, and with it the fact that the object exists, is a record in the
infotype Object (1000). That record carries the object's validity period: when an object is created it receives a start
and an end date, and because the name can change over time there can be several 1000 records for one object, with no time
gaps between them. The start of the first record and the end of the last record give the whole validity of the object, and
every other property of the object must lie inside that period.

In the example, the object `50000002` has one 1000 record named Sales, valid from 01.01.2024 to 31.12.9999 (the high
date, meaning "no end"). If the unit were renamed on 01.01.2027, the system would keep two 1000 records, Sales until
31.12.2026 and the new name from 01.01.2027, with no gap between them.

The same documentation shows that other infotypes hold further properties of an object. The processes that create objects
name some of them: Verbal Description (1002), Department/Staff (1003), Vacancy (1007), Planned Compensation (1005), Work
Schedule (1011) and Employee Group/Subgroup (1013). Infotype 1007 (Vacancy) and 1014 (Obsolete) tell whether a position
is vacant or obsolete.

== Infotype 1001: relationships

A relationship is a link between two objects. It is stored in the infotype Relationships (1001). Structure is nothing but
objects and relationships: the organizational unit "Sales" is below "Example Trading Co." because a relationship says so,
and the Sales Manager is in Sales because another relationship says so.

Each relationship is identified by a three-digit number, the subtype, and by a direction written as a letter in front of
it. The documentation writes `A003` and `B003`. The A and the B record are the same link read from the two ends, and the
documentation lists them with different names: `A003` from a position to its organizational unit reads "belongs to", and
`B003` from the unit to the position reads "incorporates". Likewise `B002` is named "is line supervisor of" and links one
unit to the unit below it, and the same relationship from the lower unit upward is shown on the documentation's
short-profile pages as relationship 002, "Reports To". Another table in the documentation, for Talent Management,
shows the pattern from the other side: subtype `A740` "Is Successor Of" and `B740` "Has Successor" are one pair.

The relationships that this page needs are the following. The short profile pages of the documentation name them, and the
profile page for evaluation paths gives the letter and direction.

[cols="1,2,2,3",options="header"]
|===
| Subtype | Direction listed in the documentation | Meaning | Example
| 002 | `B002`, unit to unit | Reports to (seen from the lower unit), is line supervisor of (seen from the higher unit) | Sales (50000002) reports to Example Trading Co. (50000001)
| 003 | `A003` position to unit, `B003` unit to position | Belongs to, incorporates | Sales Manager (51000001) belongs to Sales (50000002)
| 007 | position to job | The job assigned to the position | Sales Manager has the job Manager (52000001)
| 008 | `A008`, position to person | Holder: the employee who holds the position | Ana Torres (00001234) is the holder of Sales Manager (51000001)
| 012 | `A012`, position to unit | Manages: the position is the manager of the unit | Sales Manager (51000001) manages Sales (50000002)
|===

Subtype 003 is also the one the system writes when you create things. The documentation for the process "Create
Organizational Unit" says that the system assigns the new unit to the unit you selected with relationship 003, and the
process "Create Position" says the same for a new position. The documentation does not give a letter for the direction
of every subtype in one list; where the table above gives only the subtype, read it as "the relationship of this number".

The tables behind these infotypes are named in the documentation too: the objects and their attributes are stored in
tables named `HRPnnnn`, where `nnnn` is the infotype number, and the relationships are stored in the table `HRP1001`.
So infotype 1000 is the table `HRP1000` and infotype 1001 is `HRP1001`. A developer who wants to read the structure
should prefer the delivered reading functions of the system, whose in-system documentation (transaction SE37 for function
modules) lists what they return, rather than a direct select on these tables. This page does not run any such function:
it requires an SAP system; not run here.

== Chief position and the org chart

A unit is managed through one position, the chief position. It is recorded with relationship 012
from the position to the unit. In the example, relationship 012 links the Sales Manager position to the unit Sales. The
documentation's short profile of an organizational unit uses it this way: the field "Managed By" shows the employee who
staffs the position assigned to the unit as the managing position, found through relationship 012 and then the holder
relationship 008, and it shows nothing when no employee holds the managing position. For Sales that field would show Ana
Torres. For Warehouse the example defines no managing position, so a "Managed By" field would be empty.

The same short profile shows what the structure can count without any extra data. For Sales it gives 2 directly
subordinate positions (Sales Manager and Sales Clerk) and 2 employees, because both positions have a holder. The
documentation derives the number of full-time equivalents from the employment percentages of the employees; with Ana and
Ben at 100 percent each, the example would show 2.0. The value of 100 percent is an assumption of the example. Unlike the
chief position, the line of reporting between employees follows from the units: Ben's position belongs to Sales, Sales is
managed by Ana's position, so Ben reports to Ana. The documentation for Talent Management describes exactly this
derivation as the indirect reporting relationship `A742`, built from `A003` and `A012`.

An org chart is a picture of this data: units as boxes, drawn as a tree following relationship 002, and the positions
and holders drawn inside or below each box. The documentation describes representing the organizational structure,
the job architecture and the reporting structure as a tree. Nothing in the chart is stored separately; if the
relationships change, the chart changes.

== Evaluation paths

A structure of objects and links is only useful if a program can ask questions of it, such as "who works below this
department?". An evaluation path answers that. It is a short table that says, starting from a start object, which
relationship to follow to which object type, row by row. The system applies row 1 to the start object, row 2 to everything
row 1 found, and so on, and returns all the objects it collected.

SAP's documentation uses the standard path `O-S-P`, "Staffing Assignments along Organizational Structure", as its
example. It has three rows:

[cols="1,1,2,1",options="header"]
|===
| Object type | Relationship | Meaning | Related object type
| O | B002 | is line supervisor of | O
| O | B003 | incorporates | S
| S | A008 | Holder | P
|===

Row 1 collects the organizational units below the start unit (and the start unit itself). Row 2 collects the positions of
all of them. Row 3 collects the persons who hold those positions. Applied to the example:

* Start object `50000001` (the top unit): row 1 gives the 3 units `50000001`, `50000002` and `50000003`; row 2 gives the 3
  positions `51000001`, `51000002` and `51000003`; row 3 gives the 3 persons `00001234`, `00001235` and `00001236`. In
  total 3 + 3 + 3 = 9 objects.
* Start object `50000002` (Sales): row 1 gives only `50000002`, because Sales has no unit below it; row 2 gives
  `51000001` and `51000002`; row 3 gives `00001234` and `00001235`. In total 1 + 2 + 2 = 5 objects.
* Start object `50000003` (Warehouse): `50000003`, `51000003` and `00001236`, in total 3 objects.

A start object together with an evaluation path is also the basis of a structural profile, one way SAP limits what a user
may see in Human Resources: the user may see exactly the objects the combination returns, and the set changes
automatically when the structure under the start object changes. The documentation adds a performance remark. The
standard path `SBESX` ends with `+S A008 *+`, an unspecified target object type, so the allowed related objects come from
the table of permitted relationships and can include more than persons; a custom path with an explicit target, ending in
`S A008 P`, avoids loading objects that are not needed.

Evaluation paths are Customizing objects. The documentation calls `O-S-P` a standard evaluation path, so the example needs no custom one. This page does not run a function that evaluates a path against a system: requires an SAP system; not run here.
The names and parameters of the structure-reading function modules are in-system documentation (SE37) and are not
repeated here.

== Integration with Personnel Administration

Organizational Management and Personnel Administration can run side by side or integrated. Without integration there is no
technical link between their tables, and the personnel structure (position, job, organizational unit) is set up in
Customizing tables of Personnel Administration. With integration, the structure comes from OM. In that case the position
can carry values for company code, personnel area, personnel subarea, cost center, controlling area, business area,
employee group, employee subgroup, job and organizational unit, and these influence hiring and organizational
reassignment: when you hire a person into a position, the personnel area, employee group and employee subgroup in the
Actions infotype (0000) can be filled from the position, and values typed by hand are checked against the position with a
warning if they disagree.

In the example, the Sales Clerk position could carry personnel area `EX01`, personnel subarea `0001` and employee
subgroup `AA`, so that hiring Ben Okoye into it on 01.09.2024 proposes those values.

The component Personnel & Organization uses a switch to activate the integration: the switch `PLOGI ORGA`, set in
Customizing under Integration, Integration Between Employee Data and Organizational Data, Set Up Integration. SAP's
documentation also says to schedule the report `RHINTE30` as a regular job to keep the data of the two components
consistent, and it offers a "Personnel Only" mode that hides the organizational structures for a company that wants to
manage employees only. Whether to integrate is a design decision made in the implementation project; the system does not
force either choice. Setting the switch requires an SAP system; not run here.

== What older books show, and what has changed

The book SAP ERP HCM: Technical Principles and Programming, 1st edition (2013), covers Organizational Management from a
developer's point of view: the OM tables, reading and changing OM data with delivered function modules and with reports,
maintaining objects with a classic transaction, and defining custom evaluation paths in the implementation guide. The
concepts in it, object types, infotypes 1000 and 1001, relationships in pairs and evaluation paths starting from a root
object, are the same as in the current documentation and are what this page teaches.

What has changed since is the product around them. The book describes SAP ERP HCM. In SAP S/4HANA, Human Resources is
delivered as SAP HCM for SAP S/4HANA (H4S4): SAP states that it needs a separate license and that since SAP S/4HANA 2025
compatibility mode is no longer possible. The current documentation also describes a Personnel & Organization component
with processes and forms for creating organizational units and positions, which this page cites and which the book does
not cover, and SAP SuccessFactors is now a cloud alternative with a different data model. The function module names and listings in the book
were not re-checked against a current system, so treat them as a guide to what exists and look each up in the in-system
documentation of your release.

== Summary

* Organizational Management stores the functional structure of a company, which is a different picture from the
  administrative enterprise structure used for payroll and accounting.
* The structure is made of objects of types `O` (organizational unit), `S` (position), `C` (job) and `P` (person). The
  existence and validity period of an object are a record in infotype 1000.
* Links are records of infotype 1001. Each relationship has a three-digit subtype and an A or B direction, for example
  `A003` "belongs to" and `B003` "incorporates". Subtype 008 links a position to its holder and 012 marks the chief
  position of a unit.
* An evaluation path such as `O-S-P` follows relationships row by row from a start object and returns the collected
  objects: in the example, 9 objects from the top unit and 5 from Sales.
* With integration active, positions pass values such as personnel area and employee subgroup to hiring in Personnel
  Administration.
