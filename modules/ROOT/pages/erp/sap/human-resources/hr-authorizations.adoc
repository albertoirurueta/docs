Human resources data is among the most sensitive data a company holds: salaries, addresses, bank details, performance notes. Nobody
wants every administrator to see all of it, and nobody wants an employee to change their own pay. SAP solves this with
authorizations: before a program shows or changes an employee's record, it asks the system whether the logged-on user
holds a matching permission. HR adds two ideas to the general SAP concept. The first is that permissions can depend on
the data record itself, for example on the employee's personnel area, employee subgroup or the infotype being read. The
second is that permissions can follow the company's organizational structure, so that a manager automatically gets
access to the people below them and loses it when the structure changes. After reading this page you will know which
authorization objects protect HR infotypes, what the main switches do, how the system combines the checks in a fixed
order, how structural profiles are defined, and which BAdIs and reports help. The page is written against SAP S/4HANA
2025 FPS02 (on premise and Private Edition), where the Human Resources functions come with SAP HCM for SAP S/4HANA. SAP
states that this component needs a separate license and that from SAP S/4HANA 2025 the business function for it is active
by default, so HCM can no longer run in compatibility mode. SAP SuccessFactors is a different product with its own
permission model and is not covered.

== Key terms

* xref:erp/sap/human-resources/glossary.adoc#authorization-object[Authorization object]: a named group of up to ten
  authorization fields that are checked together.
* xref:erp/sap/human-resources/glossary.adoc#authorization-level[Authorization level]: the HR field `AUTHC`, which
  stands for the access mode such as read or write.
* xref:erp/sap/human-resources/glossary.adoc#authorization-main-switch[Authorization main switch]: an entry of group
  `AUTSW` in table `T77S0` that turns one part of the HR check on or off.
* xref:erp/sap/human-resources/glossary.adoc#structural-authorization[Structural authorization]: a permission that
  follows the organizational structure instead of listing values.
* xref:erp/sap/human-resources/glossary.adoc#structural-profile[Structural profile]: a start object plus an evaluation
  path (and a few more fields) that returns the set of objects a user may access.
* xref:erp/sap/human-resources/glossary.adoc#period-of-responsibility[Period of responsibility]: the time intervals
  in which a user is responsible for an employee and therefore authorized.
* xref:erp/sap/human-resources/glossary.adoc#time-logic[Time logic]: the rule that compares the period of responsibility
  with the validity dates of the record being accessed.
* xref:erp/sap/human-resources/glossary.adoc#organizational-key[Organizational key]: the field `VDSK1`, a freely
  defined key derived from the Organizational Assignment infotype.

* Organizational units `50000001` Example Trading Co., `50000002` Sales and `50000003` Warehouse. Positions `51000001` Sales

* Ana Torres (`00001234`, Sales Manager, subgroup `AA`), Ben Okoye (`00001235`, Sales Clerk, `AA`) and Chloe Martin
  (`00001236`, Warehouse Clerk, `AB`).

The page extends the example in four places, each marked where it appears: an HR administrator for hourly staff (a role,

== Two layers that are combined

SAP describes two ways to set up authorizations for HR. General authorizations are based on the SAP-wide authorization
concept: authorization objects, roles and profiles, as for any other SAP data. Structural authorizations are specific to
HR: they check, by organizational assignment, whether a user may act on an object. You can use both at the same time.

When you do, SAP states that the user's overall profile is the intersection of the structural and the general profiles. The
structural profile decides which objects of the organizational structure the user can reach. The general profile decides
which data of those objects (infotype, subtype) and which access mode (read, write) the user has. In the example, a
manager whose structural profile covers Sales and whose general profile allows reading infotypes `0000` to `0007` can read
those infotypes for Ana and Ben. Chloe is outside Sales, so the manager cannot read Chloe even though the general profile
would allow it. The manager also needs a `PLOG` authorization for persons, described below, because the structural check
reaches persons through the personnel planning object.

== The general check: authorization objects for HR data

An authorization object groups up to ten fields that are checked in an AND relationship: the check succeeds only if all
field values are covered by the user's authorizations. You display and edit objects with transaction `SU21`; the HR
objects belong to the object class `HR`. The three objects that protect HR master data are listed here.

[cols="1,3,3",options="header"]
|===
| Object | Fields | What it controls

| `P_ORGIN` (HR: Master Data)
| `INFTY` infotype, `SUBTY` subtype, `AUTHC` authorization level, `PERSA` personnel area, `PERSG` employee group, `PERSK` employee subgroup, `VDSK1` organizational key
| Reading and changing infotype records, depending on the employee's organizational assignment. The values of `PERSA`, `PERSG`, `PERSK` and `VDSK1` come from the Organizational Assignment infotype (0001).

| `P_ORGXX` (HR: Master Data, Extended Check)
| `INFTY`, `SUBTY`, `AUTHC`, `SACHA` payroll administrator, `SACHP` master data administrator, `SACHZ` time recording administrator, `SBMOD` administrator group
| An additional check by the administrator fields of infotype 0001. It is evaluated only when its own main switch is on.

| `P_PERNR` (HR: Master Data, Personnel Number Check)
| `AUTHC`, `PSIGN` interpretation of an assigned authorization, `INFTY`, `SUBTY`
| Permissions on the user's own personnel number. The system finds that number through infotype 0105, subtype 0001.
|===

Two more objects deserve a mention. `P_NNNNN` is a name pattern for a customer-specific object that you create yourself
when `P_ORGIN` and `P_ORGXX` cannot express your rule, for example because you want to test an additional, customer-specific
field of infotype 0001. Such an object must contain at least `INFTY`, `SUBTY` and `AUTHC`. `P_PCLX` (HR: Clusters)
protects the PCLx cluster tables of HR, with the fields `RELID`, which names the cluster area, and `AUTHC`. The page
documenting the objects lists many more HR objects, for example `P_APPL` for applicants, `P_ABAP` for reporting, `P_PCR`
for the payroll control record and `P_TCODE`, plus the personnel planning object `PLOG`; this page describes only those
that take part in the order of checks below.

Example Trading Co. can make this concrete. An HR administrator for hourly staff gets a `P_ORGIN` authorization with
personnel area `EX01`, employee group `1`, employee subgroup `AB` and the infotypes and levels needed. Chloe (subgroup
`AB`) is then in scope; Ana and Ben (subgroup `AA`) are not, however many other authorizations the administrator holds.

=== Authorization levels

HR does not use the usual field `ACTVT` for the access mode. SAP explains that the objects with the field `AUTHC` were in
use before the switch to `ACTVT` was decided, and that HR kept `AUTHC` to stay compatible for existing customers. The values
for `P_ORGIN`, `P_ORGXX`, `P_PERNR` and customer-specific objects are these.

[cols="1,4",options="header"]
|===
| Value | Meaning

| `R` | Read access.
| `M` | Read access to entry helps (matchcode).
| `W` | Write access.
| `E` | Write access using the asymmetrical double verification principle; also allows creating and changing locked records.
| `D` | Write access using the asymmetrical double verification principle; also allows changing the lock indicator.
| `S` | Write access using the symmetrical double verification principle.
| `+*+` | All of the above at once.
|===

For `P_PCLX` the field has different values: `R` read, `U` write (update; it includes `S` but not `R`) and `S` write to the
internal buffer but not to the database (simulation).

Two behaviors in dialog transactions for master data surprise newcomers. The check runs from the strongest level down: for a
read the system first tests for write access, then reads, and stops at the first success. As a result a write authorization
also works as a read authorization in the dialog, but special modules that check for read directly then behave
inconsistently, so SAP advises always granting `R` together with `W`, `E`, `D` or `S`. And if a user opens a record without
a subtype, the check uses the blank subtype, so a user who has authorizations for specific subtypes only appears to have no
access. SAP recommends granting an additional authorization for the blank subtype, which does not exist as real data.
SAP also advises against building a concept on the combinations `E`, `D` and `S` for one infotype because the interpretation
order is planned to change.

Source: https://help.sap.com/docs/SAP_S4HANA_ON-PREMISE/c6c3ffd90792427a9fee1a19df5b0925/af04dd5321e8424de10000000a174cb4.html[AUTHC (Authorization Level) (SAP Help Portal)], https://help.sap.com/docs/SAP_S4HANA_ON-PREMISE/c6c3ffd90792427a9fee1a19df5b0925/ac04dd5321e8424de10000000a174cb4.html[Special Features of the Authorization Check in Dialog (Master Data) (SAP Help Portal)]

=== Organizational key

The field `VDSK1` lets you test an additional key that you define yourself. The feature `VDSK1` and the tables `T527`,
`T527A` and `T527O` control how the key is created and validated. For example, a rule can build the key from the first five
places of the cost center of infotype 0001. Example Trading Co. does not define such a key, so the listing above passes a
variable.

=== Checks on the user's own personnel number

`P_PERNR` is evaluated only when the user is assigned to a personnel number and accesses exactly that number. It then
can override all other checks except the test procedures. Employee self-service is the classic case. SAP's example
gives every self-service employee two `P_PERNR` authorizations: read for all infotypes, and all levels for infotype `0006`
(addresses). Ana as self-service user would therefore read all of her own records and change her address, but not her basic
pay. Employees who are not administrators get no `P_ORGIN` authorization, so every other personnel number stays closed.

The field `PSIGN` says how to read an authorization: `I` includes it and `E` excludes it. SAP's second example keeps an
HR administrator from changing the administrator's own Basic Pay: read for all infotypes with `PSIGN = I`, and write levels
`W`, `S`, `D`, `E` for infotype `0008` with `PSIGN = E`. The administrator is a role of the extended example, not one of the three
employees. When both an include and an exclude match, the exclude wins ("when in doubt, no authorization"), except that a
`PSIGN` of `+*+` is treated as `I`, so that users with full authorization can reach their own number. SAP warns that
`P_PERNR` settings never affect personnel numbers that are not assigned to the user, and recommends setting up the
authorizations for other numbers first.

Source: https://help.sap.com/docs/SAP_S4HANA_ON-PREMISE/c6c3ffd90792427a9fee1a19df5b0925/1404dd5321e8424de10000000a174cb4.html[P_PERNR (SAP Help Portal)], https://help.sap.com/docs/SAP_S4HANA_ON-PREMISE/c6c3ffd90792427a9fee1a19df5b0925/fc03dd5321e8424de10000000a174cb4.html[Process of the Authorization Check by Personnel Number (SAP Help Portal)], https://help.sap.com/docs/SAP_S4HANA_ON-PREMISE/c6c3ffd90792427a9fee1a19df5b0925/b403dd5321e8424de10000000a174cb4.html[Example: Employee Self-Service (SAP Help Portal)]

=== Setting up general authorizations

General HR authorizations are set up like other SAP authorizations, in roles with the profile generator (transaction `PFCG`).
Roles delivered by SAP start with the prefix `SAP_`, so you create your own roles in your own namespace. The generated
profile reaches the user master record after a user comparison. HR-specific settings are in the Implementation Guide of
Personnel Administration under Tools > Authorization Management > Maintain Profiles.

== Main switches: which parts of the check are active

The authorization main switches are stored in table `T77S0` under the group name `AUTSW`. They let you tailor the check on HR
infotypes, and because the table is client-specific they can differ by client. The help pages document these values.

[cols="1,4",options="header"]
|===
| Switch | What it does

| `ORGIN`, `ORGXX`, `NNNNN`
| Turn the objects `P_ORGIN`, `P_ORGXX` and your customer-specific object on or off. If the `ORGIN` switch is not active, the check on `P_ORGIN` returns authorized immediately. Check the value in the system: the help page for `ORGIN` states a default of `1` but words the setting that activates the check as `0`.
| `PERNR`
| Controls the check by personnel number. Standard value `1`; set `0` to deactivate it.
| `ORGPD`
| Includes the organizational structure in the check in Personnel Administration. Standard value `0`; `1` to `4` activate it. They differ in two choices, see below.
| `ADAYS`
| Tolerance time in calendar days for time logic. Standard value `15`.
| `APPRO`
| Turns test procedures on (`1`) or off. Standard value `0`.
| `INCON`, `XXCON`, `NNCON`, `DFCON`
| Belong to the context solution and to the check for a person with a default position.
|===

The values of `ORGPD` combine two decisions. For persons who are linked to the default position instead of a real position,
you choose whether the organizational unit stored in infotype 0001 is evaluated, and, if no check by organizational
assignment is possible, whether authorization is denied or granted by default.

[cols="2,1,1",options="header"]
|===
| | Evaluate organizational unit (if available) | Never evaluate organizational unit
| Deny authorization by default | `1` | `2`
| Grant authorization by default | `3` | `4`
|===

SAP's self-service example points out that at least one main switch other than `PERNR` must be active to keep users away from
other personnel numbers, so the example activates `ORGIN` as well.

Source: https://help.sap.com/docs/SAP_S4HANA_ON-PREMISE/c6c3ffd90792427a9fee1a19df5b0925/0504dd5321e8424de10000000a174cb4.html[HR: Authorization Main Switches (SAP Help Portal)], https://help.sap.com/docs/SAP_S4HANA_ON-PREMISE/c6c3ffd90792427a9fee1a19df5b0925/7004dd5321e8424de10000000a174cb4.html[AUTSW ORGPD (SAP Help Portal)], https://help.sap.com/docs/SAP_S4HANA_ON-PREMISE/c6c3ffd90792427a9fee1a19df5b0925/ed03dd5321e8424de10000000a174cb4.html[AUTSW PERNR (SAP Help Portal)], https://help.sap.com/docs/SAP_S4HANA_ON-PREMISE/c6c3ffd90792427a9fee1a19df5b0925/ae03dd5321e8424de10000000a174cb4.html[AUTSW ADAYS (SAP Help Portal)], https://help.sap.com/docs/SAP_S4HANA_ON-PREMISE/c6c3ffd90792427a9fee1a19df5b0925/2b04dd5321e8424de10000000a174cb4.html[AUTSW APPRO (SAP Help Portal)], https://help.sap.com/docs/SAP_S4HANA_ON-PREMISE/c6c3ffd90792427a9fee1a19df5b0925/4604dd5321e8424de10000000a174cb4.html[AUTSW ORGIN (SAP Help Portal)]

== Time: periods of responsibility and time logic

Infotype records are valid for a period, and a user's responsibility is also a period. The system therefore compares
dates. A user's period of responsibility is the set of time intervals in which the user holds the matching authorizations.
For `P_ORGIN` it comes from the organizational assignment: since infotype 0001 changes over time, an authorization can exist
for some intervals only. The setting that tells whether an infotype is checked date-dependently is the field `VALDT` of table
`T582A`.

The time logic then compares the period of responsibility with the begin and end date of the record. The steps, as the help
page lists them, are these. If the period is empty, the result is not authorized. If the infotype is not checked
date-dependently, the result is authorized. Otherwise, for read access, the system opens the period of responsibility up to 31.12.9999 as long as the current date is not
after its end by more than the tolerance time (otherwise it ends where it ended), and it opens the beginning to 01.01.1800.
The record is authorized if it overlaps the resulting period on at least one day. For write access the record must lie completely inside the period.
The tolerance time exists to soften organizational changes.

=== Example: the tolerance time

This scenario extends the example with a second personnel area `EX02`, invented for it. Suppose an administrator is
responsible for personnel area `EX01` only, with read and write access, and date-dependent checks are active. Ben
transfers to `EX02` with effect from 01.04.2026. The administrator's period of responsibility for Ben ends on 31.03.2026.
With `ADAYS` at `15`, write access continues through 15.04.2026 inclusive (31.03.2026 plus 15 calendar days; checked by
script). From 16.04.2026 the administrator loses write access to Ben's records, but can still display records
that began on or before 31.03.2026.

== The structural check

Structural authorizations control access to data that lives in time-dependent hierarchies: the organizational structure,
and the structures of Personnel Development and Training and Event Management. The idea is to keep maintenance small. If
you listed every organizational unit below Sales in a general profile, you would edit the profile whenever a unit is
added. A structural profile names a start object and an evaluation path instead, and so follows the structure.

An evaluation path collects objects from a start object by following the relationships of its definition row by row. SAP
describes the standard path `O-S-P` (staffing assignments along the organizational structure) with three rows: organizational
unit to organizational unit (`B002`), organizational unit to position (`B003`) and position to holder (`A008`). The
combination of a start object and an evaluation path is the structural profile: the objects it returns change as the
structure changes.

In Example Trading Co. the start object `50000001` with the path `O-S-P` returns 9 objects: 3 units, 3 positions and 3
persons. The start object `50000002` Sales returns 5: Sales, the Sales Manager and Sales Clerk positions, Ana and Ben.
Chloe is not among them.

=== Defining and assigning profiles

You define structural profiles in table `T77PR` and assign them to users in table `T77UA`. Customizing offers the following
fields in `T77PR`.

[cols="1,4",options="header"]
|===
| Field | Meaning

| Plan version | The plan version for which the profile is valid; in the integrated scenario SAP says plan version `01` is usually the integrated one.
| Object type | The object types the profile covers. Only types with an 8-digit numeric key can be specified; external types such as cost centers are not checked structurally.
| Object ID | The start object when using an evaluation path.
| Maintenance | Whether display or change authorization is granted.
| Evaluation path | The path that collects the objects; a root object must be specified directly or determined dynamically.
| Status vector | Which relationship statuses count; `12` means active or planned.
| Depth | Up to which level of the hierarchy; `0` means no restriction.
| Sign | A minus sign makes the profile process the structure from bottom to top; blank or plus processes top to bottom.
| Period | Restricts the profile by the validity of the structure: key date, all, current year, current month, and so on.
| Function module | Determines the root object at run time; then Object ID must stay empty.
|===

A function module makes one profile serve many users. SAP delivers two. `RH_GET_MANAGER_ASSIGNMENT` determines the
organizational unit that the user manages through a chief position (relationship `A012`, key date based). `RH_GET_ORG_ASSIGNMENT`
determines the unit the user belongs to. With the first, a single profile gives every manager their own unit as root: Ana gets
Sales, and when she changes department the profile does not change. A profile can also be an exclusion: a branch marked
with the exclusion indicator is checked first, and the user has no authorization for it even if the object appears again
without exclusion.

=== Example: the Period field

The Period field decides which relationships count. This scenario assumes that each holder relationship starts on the hire
date (the example's choice) and uses the profile of Ana's manager role: plan version `01`, object type `O`, path `O-S-P`,
root Sales. Consider a check run on 31.08.2024. Ana's relationship to the Sales Manager position has been valid since
01.03.2024, Ben's relationship to Sales Clerk only starts on 01.09.2024. With Period `D` (key date) the profile returns Sales, the
two positions and Ana: 4 objects. With Period blank (all) it returns Sales, the two positions, Ana and Ben: 5 objects.
Chloe is never returned because her position is in Warehouse.

=== The structural check and the `PLOG` object

`PLOG` (Personnel Planning) is the authorization object of the personnel planning components. Its fields are plan version
`PLVAR`, object type `OTYPE`, infotype `INFOTYP`, subtype `SUBTYP`, planning status `ISTAT` and function code `PPFCODE`. SAP says
that users of those components can reach data only if they hold both a `PLOG` profile and a structural profile, and that a
user who should not be limited structurally still needs a structural profile that covers the whole structure. For Ana's
manager role this means two entries: the structural profile for Sales, and a `PLOG` authorization for object type `P`
(persons) in plan version `01`.

Source: https://help.sap.com/docs/SAP_S4HANA_ON-PREMISE/c6c3ffd90792427a9fee1a19df5b0925/c404dd5321e8424de10000000a174cb4.html[PLOG (Personnel Planning) (SAP Help Portal)]

== The order of the checks

For one request the system works in a fixed order. The parameters are the level, a transaction class that separates an
employee number from an applicant number, the personnel number, infotype, subtype and the begin and end date of the record.
Dates always describe the record, never the period the user asked about, so the time logic decides what part of the record
the user may reach.

[mermaid]
----
flowchart TD
    A["Request: user, personnel number, infotype, subtype, level, record dates"] --> B{"Check by personnel number: user's own number and P_PERNR switch on?"}
    B -- "no or no matching entry: undecided" --> D
    B -- "yes" --> C{"P_PERNR result"}
    C -- "not authorized" --> X["Denied"]
    C -- "authorized: skip all steps except test procedures" --> T
    C -- "undecided" --> D
    D["Structural check used: determine period of responsibility from the structure"] --> E{"Period empty?"}
    E -- "yes" --> X
    E -- "no" --> F["Period from organizational assignment: P_ORGIN, P_ORGXX, customer object"]
    F --> G{"Period empty?"}
    G -- "yes" --> X
    G -- "no" --> H["Intersection of both periods"]
    H --> I{"Time logic: record dates fit the period?"}
    I -- "no" --> X
    I -- "yes" --> T
    T{"Test procedure forbids the change?"} -- "yes" --> X
    T -- "no" --> Y["Authorized"]
----

Two details of the flow matter in practice. When `P_PERNR` answers authorized, everything except the test procedures is
skipped, which is why the self-service permissions of Ana are decided before any `P_ORGIN` check. Test procedures
(main switch `APPRO`) protect data that was checked centrally: a change is allowed only when the record's begin date is after
the date up to which a test procedure forbids changes. They apply to write access and are not applied to applicant numbers or
to infotype 0001.

The structural step takes part only when you use the structural check. Otherwise the period of responsibility from the
organizational assignment alone goes into the time logic.

== The context problem

Because structural and general profiles are added up separately, a user with different roles cannot get a different general
profile for each structure. Suppose Ana manages Sales with read and write for infotypes `0000` to `0007`, and in a second
role is payroll manager for Warehouse with read and write for infotype `0008` only. This second role is an assumption of the
example. The system adds the two structural profiles (Sales and Warehouse) and the two general profiles. Ana then holds
`0000` to `0008` for everyone in both structures, so she could change Ben's Basic Pay, which neither role intended. SAP
names two ways out: a separate user for each role, or the context solution, in which the context variants of the objects
(`P_ORGINCON`, `P_ORGXXCON`, `P_NNNNNCON`) and their switches tie general authorizations to a structural profile. The
details are in the system documentation.

== Authorization checks in reporting

Many HR reports read data through the logical databases `SAPDBPNP` and `SAPDBPAP`, which also run the authorization check.
SAP notes that a personnel number for which one data record cannot be read is skipped completely by default. A report that
only prints addresses can live with partial data; a statistics report would silently omit people. SAP lists three options:
set the skip behavior in the report, restrict reading to the selection period, or read without immediate checking and
check the data in the report with the function module `HR_CHECK_AUTHORITY_INFTY` from the function group `HRAC`. The first
option is a single statement in the `INITIALIZATION` event.

[source,abap]
----
" Requires an SAP system; not run here.
INITIALIZATION.
  pnp_sw_skip_pernr = 'N'.   " do not skip personnel numbers with unreadable records
----

== Customer enhancements: three BAdIs

SAP provides business add-ins for authorizations. Customizing for Personnel Management lists them under Personnel
Administration > Tools > Authorization Management and Organizational Management > Basic Settings > Authorization Management.

[cols="2,3,3",options="header"]
|===
| BAdI | Purpose | Notes from the help page

| `HRPAD00AUTH_CHECK`
| Replace the standard authorization check for HR master data and infotypes without modification.
| As soon as an implementation is active, all HR master data checks stop and only the implementation runs. The interface `IF_EX_HRPAD00AUTH_CHECK` has 13 methods, all of which must be implemented. SAP advises copying the standard class `CL_HRPAD00AUTH_CHECK_STD` and changing the copy when only one sub-function must differ.
| `HRBAS00_STRUAUTH`
| A customer-specific test procedure for the structural check.
| Four methods, all mandatory: `CHECK_AUTHORITY_VIEW`, `FILL_DATE_VIEW`, `FILL_HYPER_VIEW` and `CHECK_AUTH_PLAN1`. Sample code is in the class `CL_EXM_IM_HRBAS00_STRUAUTH`.
| `HRBAS00_GET_PROFL`
| An alternative way to determine a user's structural profiles, which then no longer have to be maintained in `T77UA`.
| One method, `GET_T77PR_TAB`. Described as particularly interesting for the context solution.
|===

The authorization-check BAdI is the most dangerous of the three. Its methods for maximum and minimum authorization are called
by applications as a performance shortcut and are expected to answer well under a second. A maximum check that answers
authorized for a user who should not have access grants access without further checks, so SAP says it must either follow
the main check method or always answer not authorized. Because an active implementation replaces the whole HR master data check, SAP first points to a customer-specific
authorization object for rules that `P_ORGIN` and `P_ORGXX` cannot express, and suggests a BAdI only when that is not enough.

== Performance

Structural checks can be expensive because the system evaluates structures for each user. SAP names three causes in its
constraints: reading large structures (the answer is the `RHBAUS00` indexes), reading objects redundantly, and using an
evaluation path whose target object type is not specified. With an unspecified target type the permitted object types
come from the table of permitted relationships, so the profile can also return other objects linked to positions, which
the requirement did not ask for. A path with a named target type avoids that. Excluding substructures can also help
users with extensive authorizations.

Source: https://help.sap.com/docs/SAP_S4HANA_ON-PREMISE/c6c3ffd90792427a9fee1a19df5b0925/0e04dd5321e8424de10000000a174cb4.html[Evaluation Paths with Non-Specified Target Object Types (SAP Help Portal)], https://help.sap.com/docs/SAP_S4HANA_ON-PREMISE/c6c3ffd90792427a9fee1a19df5b0925/7904dd5321e8424de10000000a174cb4.html[Structural Authorization Check (SAP Help Portal)]

== What older books show, and what has changed

The book SAP ERP HCM: Technical Principles and Programming, 1st edition (2013), has a chapter on authorizations. It shows the
HR authorization objects such as `P_ORGIN` and `P_PERNR`, a read check on `P_ORGIN` for a record opened in the master data
transaction `PA30`, the structural authorization, the interaction of general and structural authorizations, the main
switches and the context-based check with customer-specific objects. The concepts on this page match it. What has changed
since 2013 is the product around them. HR in an S/4HANA system is HCM for SAP S/4HANA, a separately licensed component
that has been active by default since SAP S/4HANA 2025. New tooling appears in the help portal, such as the report
`RHBAUS_PARALLEL` and the BAdI `HRBAS00_STRUAUTH_BAUS`, which the 2013 edition does not cover. The SAP help topics themselves
are older text: several still say SAP Standard Release 4.70 and use the product name mySAP HR, so read them for the
mechanism and check details in your own system.

Source: https://www.sap-press.com/sap-erp-hcm-technical-principles-and-programming_3698/[SAP ERP HCM: Technical Principles and Programming (SAP PRESS, publisher page; the consulted copy is the 1st edition, the page lists the 2nd)]

== Summary

* HR has two authorization layers: general checks on infotype data (`P_ORGIN`, `P_ORGXX`, `P_PERNR`, customer objects) and
  structural checks that follow the organizational structure. When both are used the user gets their intersection.
* The access mode is the field `AUTHC` (`R`, `M`, `W`, `E`, `D`, `S`), not `ACTVT`. Grant `R` together with write levels.
* Main switches of group `AUTSW` in `T77S0` turn each part on or off, so a missing switch means a missing check.
* The check runs in a fixed order: personnel number, structural period, organizational-assignment period, time logic and
  test procedures. Time logic compares the record's dates with the period of responsibility, softened by the tolerance
  time `ADAYS`.
* A structural profile is a start object plus an evaluation path, defined in `T77PR` and assigned in `T77UA`, usually with a
  function module that finds the root object per user. `PLOG` and a structural profile are needed together.
* Adding roles adds profiles, which can grant too much (the context problem). Replacing the check with a BAdI is a last resort.
