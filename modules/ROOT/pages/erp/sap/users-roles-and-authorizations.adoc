= Users, Roles and Authorizations
:description: How people get access in SAP: user master records in SU01, PFCG roles with authorization objects, composite roles and Fiori catalogs in role menus, the analysis tools SU53 and SUIM, and how business roles, business catalogs and restrictions in the Cloud Public Edition and role collections in SAP BTP differ, for S/4HANA 2025 FPS02 on premise and Private Edition and Cloud Public Edition 2608.
:keywords: SAP, user, user master record, SU01, PFCG, role, single role, composite role, derived role, authorization object, authorization, profile, Fiori catalog, role menu, SU53, SUIM, business user, business role, business catalog, IAM app, restriction, restriction type, role template, role collection, SAP BTP, Authorization and Trust Management service, least privilege

include::partial$ai-disclaimer.adoc[]

Every person who works in an SAP system needs two things: an identity that the system knows, and a set of permissions that says what that identity may do. A clerk may display an invoice, a manager may approve it, and only the finance team may post a correction. SAP calls the identity a user and the permission set an authorization, and it hands authorizations to users bundled in roles, so an administrator does not have to tick hundreds of single permissions for every new colleague. The idea is the same in every SAP product, but the tools differ. This page explains the classic model of an ABAP system (S/4HANA 2025 FPS02 on premise and Private Edition): the user master record in transaction SU01, roles in transaction PFCG, and the analysis tools SU53 and SUIM. It then compares that model with the two others a newcomer meets: business users, business roles, business catalogs and restrictions in S/4HANA Cloud Public Edition 2608, and role collections in SAP BTP, which has no release number of its own on its documentation pages. After reading it you can say which model applies to the system in front of you and where to look when somebody says "I have no authorization".

== Key terms

* xref:erp/sap/glossary.adoc#user-master-record[User master record]: the record that makes a person or a technical connection known to an ABAP system; it holds the logon data, the assigned roles and the resulting authorizations.
* xref:erp/sap/glossary.adoc#pfcg-role[Role (PFCG)]: a set of menu entries and authorizations that matches a job, maintained in transaction PFCG and assigned to users.
* xref:erp/sap/glossary.adoc#composite-role[Composite role]: a role that only collects single roles, so one assignment gives a user all of them.
* xref:erp/sap/glossary.adoc#authorization-object[Authorization object]: the repository object that groups authorization fields; every permission is a set of values for the fields of one object.
* xref:erp/sap/glossary.adoc#business-user[Business user]: the user of S/4HANA Cloud Public Edition, who is created for a worker and receives business roles.
* xref:erp/sap/glossary.adoc#business-role[Business role]: in the Public Edition, the access profile of a job function, built from business catalogs and IAM apps plus restriction values.
* xref:erp/sap/glossary.adoc#business-catalog[Business catalog]: a bundle of apps aligned to one task or sub-process, from which business roles are built.
* xref:erp/sap/glossary.adoc#restriction-type[Restriction type]: a group of restriction fields, such as company code or plant, that limits which data a business role may see or change.
* xref:erp/sap/glossary.adoc#role-collection[Role collection]: in SAP BTP, a group of application roles that an administrator assigns to users or user groups.
* xref:erp/sap/glossary.adoc#least-privilege[Least privilege]: the rule that a user gets only the permissions the task needs and nothing more.

== Three models, one question

Before the details, here is the whole picture. Each product answers the same question, "who may do what", with its own vocabulary.

Reading it: in the ABAP system the administrator builds roles from the authorization objects that programs check, and gives the role to the user. In the Public Edition the administrator never touches authorization objects; SAP delivers catalogs and IAM apps, and the administrator picks them and sets restrictions. In SAP BTP the developer of an application defines the authorizations in a security descriptor, and the administrator groups them into role collections.

== Model 1: users and roles in an ABAP system

This model applies to S/4HANA on premise and to the Private Edition, where the customer or SAP's managed service runs a full ABAP system and an administrator has the SAP GUI transactions.

=== The user master record and SU01

Transaction `SU01` (User Maintenance) is where an administrator creates the user master record. Its initial screen offers a few actions, which the documentation lists: create, change, display, delete, copy, lock or unlock, and change password. Locking or unlocking takes effect the next time the user logs on, and a user who is already logged on is not affected. By default the system locks a user after twelve successive failed password logons, and the lock is recorded in the system log. The record has tabs, among them Logon Data, Defaults, Parameters, Roles, Profiles, Groups and License Data.

Not every user is a person. The documentation for creating a technical user names two types for programs. A user of the type System is for internal processes such as background processing, ALE, workflow, the Transport Management System and central user administration; it cannot log on with the SAP GUI, and only an administrator can change its password. A user of the type Communications Data is for dialog-free communication between systems, such as RFC; it cannot log on in dialog either, but it follows the general password rules. The choice matters for security: a technical user that nobody can log on with interactively is a smaller risk than a shared dialog user.

Source: https://help.sap.com/docs/SAP_S4HANA_ON-PREMISE/c6e6d078ab99452db94ed7b3b7bbcccf/4cb5f7ac9cb33c94e10000000a42189c.html[User Administration Functions] and https://help.sap.com/docs/ABAP_PLATFORM_NEW/ad77b44570314f6d8c3a8a807273084c/c548fea2a3784ab39a1ba5b1d69ccdcf.html[Creating a Technical User]. The administration steps happen in the SAP GUI of an ABAP system; this page does not run them.

=== Roles in PFCG

Transaction `PFCG` (Role Maintenance) is where roles are made. The documentation describes a role as a set of transactions that people in a given job need for their daily work, for example a salesperson who adds customers, displays customer details and enters a lead. A role does two jobs at once.

* It defines the user menu: the folders and entries that appear in the SAP Easy Access menu after logon. The Menu tab lists them.
* It carries the authorizations. On the Authorizations tab the administrator chooses Change Authorization Data, maintains the values, saves and then generates the authorization profile. The profile is what enters the user master record.

The administrator assigns the role to users on the User tab of the role, or in the Roles tab of SU01, and a user can have any number of roles. After a role changes, a user comparison updates the user records.

The permissions inside the role are values of authorization fields in authorization objects, exactly the objects that programs ask about with `AUTHORITY-CHECK`. A programmer who wrote a check against an object has made a promise that some role will contain it. xref:programming-languages/abap/authority-checks.adoc[Authorization Checks] explains how the defaults for those values travel from a developer's design (transactions SU22 and SU24) into the role; this page does not repeat it.

Source: https://help.sap.com/docs/ABAP_PLATFORM_NEW/9737050ef01843f19572591b42128f1b/4c5bdc4997817511e10000000a42189b.html[PFCG Overview] and https://help.sap.com/docs/SAP_S4HANA_ON-PREMISE/22bbe89ef68b4d0e98d05f0d56a7f6c8/bec1fdc8e5ca487ebbaf25c293f138f5.html[Assigning Roles to Users on Back End]

=== Single roles, composite roles and derived roles

A role created as a plain role is a single role. A composite role is a role that only collects single roles. The documentation, an older SAP ERP page that still describes the PFCG screens, says composite roles consist of single roles, that users given a composite role receive the single roles automatically after a comparison, and that the composite role holds no authorization data of its own. Two rules follow from it. You cannot put a composite role inside another composite role, and you should change the user assignment in the composite role, because the users of the single roles that come from it are shown grayed out. The system does not distinguish simple and composite roles by name, so the documentation advises a naming convention of your own. A second page recommends creating a composite role for the single roles of a job and assigning only the composite role to the user.

A derived role is the third kind. The Launchpad content manager documentation describes it briefly: a derived role derives its role menu from the role it inherits from. The page does not go further, and this page does not describe the rules of derivation.

Source: https://help.sap.com/docs/SAP_ERP/142f8559883b4c11966ebfb99dd61164/42271d24d86211d2961a0000e82de14a.html[SAP ERP 6.05: Creating Composite Roles (older page)], https://help.sap.com/docs/SAP_ERP/6ce39fbda7a14bfea7058d90dceb6fb6/dfdce4535dd4414de10000000a174cb4.html[SAP ERP: Merging Single Roles into Composite Roles (older page)] and https://help.sap.com/docs/ABAP_PLATFORM_NEW/a7b390faab1140c087b8926571e942b7/4638421502424ab1aa6551ee75e6e2fc.html[SAP Fiori Launchpad: Maintaining Roles in the Launchpad Content Manager]

=== Fiori catalogs inside a role menu

The apps of the SAP Fiori launchpad are not transactions, but they need the same authorizations. SAP's recommendation for SAP S/4HANA 2025 is to treat the catalog as the smallest unit that you assign and authorize, and to keep a catalog and the authorizations its apps need together in the same roles. The mechanism is called the PFCG integration of SAP Fiori tile catalogs.

. In PFCG the administrator creates a role or edits an existing one and opens the Menu tab.
. From the menu of the button that adds objects, the administrator chooses SAP Fiori Launchpad and then Launchpad Catalog. On the back-end server the administrator selects Remote Front-End Server and gives the RFC destination, and selects Include Applications.
. The administrator picks the catalog. The OData services, Web Dynpro applications and SAP GUI for HTML applications of its apps are added as subnodes. Adding them brings the start authorization and the authorization proposals for the business data.
. On the Authorizations tab the administrator maintains the values, saves and generates the profile, as for any role.

The start authorization lets the user open the app or call its OData service. The business authorizations decide which data the user sees inside the app. When a catalog changes in the launchpad designer, for example an app is added, the roles that contain it must be updated. The report `PRGN_COMPARE_ROLE_MENU` finds the roles that need adapting, and PFCG then compares and updates them. The comparison does not cover applications that were added to the role menu by hand.

Source: https://help.sap.com/docs/SAP_S4HANA_ON-PREMISE/22bbe89ef68b4d0e98d05f0d56a7f6c8/6f0e415370107d77e10000000a441470.html[Creating Authorization Roles for Catalogs] and https://help.sap.com/docs/SAP_S4HANA_ON-PREMISE/22bbe89ef68b4d0e98d05f0d56a7f6c8/99bd67fe11234e4e8b7eed52faa242e2.html[Recommendations for Organizing SAP Fiori Launchpad Content and Authorizations]. The steps need a PFCG role and a front-end server; not run here.

=== Finding out why access fails: SU53 and SUIM

Two transactions answer most questions of an administrator who has to explain a missing permission.

* `SU53` displays the last failed authorization check. The documentation says it shows the checked authorization object and the values that were tested, compared with what the user master record holds, and that it works from any of the user's sessions. An administrator can look at the check of another user, but only if that user has already started SU53. Its neighbor `SU56` shows the authorizations that are currently in the user's buffer. If you do not know which authorizations an application needs, the system trace of transaction `ST01` records every checked object with its fields and values. The pages describing these tools belong to an older SAP ERP release, but the SAP Fiori troubleshooting page for S/4HANA 2025 still tells users who see no data to check SU53 first.
* `SUIM`, the User Information System, gives an overview of the users and authorizations in the system. It has reports for users, roles, profiles, authorizations, authorization objects and transactions. The documentation names some of them: `RSUSR002` evaluates users by complex criteria, `RSUSR008_009_NEW` finds users or roles that hold critical authorizations or critical combinations, `RSUSR010` lists the transactions a user can start, and `RSUSR050` compares two users, roles, profiles or authorizations in one or two systems. It also offers where-used lists, so before you change a role you can check which users hold it. SAP recommends defining which authorizations you consider critical and reviewing regularly who has them.

One trap deserves a sentence. SU53 can show nothing even though data is missing. The S/4HANA 2025 troubleshooting page explains that apps that use the Service Adaptation Definition Language or CDS views with access control (DCL) generate a valid query that simply leaves out the rows the user may not see. No check fails, so SU53 stays quiet and the app shows no data or too little. xref:programming-languages/abap/cds-access-control.adoc[CDS Access Control (DCL)] explains that mechanism from the developer's side.

Source: https://help.sap.com/docs/SAP_ERP/142f8559883b4c11966ebfb99dd61164/526716b3439b11d1896f0000e8322d00.html[SAP ERP 6.05: Analyzing Authorization Checks (older page)], https://help.sap.com/docs/SAP_S4HANA_ON-PREMISE/22bbe89ef68b4d0e98d05f0d56a7f6c8/6a779d9b8bb642d3aa55a58b0dcdafe1.html[No Or Too Little Data Is Shown in the App], https://help.sap.com/docs/SAP_S4HANA_ON-PREMISE/c6e6d078ab99452db94ed7b3b7bbcccf/52671261439b11d1896f0000e8322d00.html[User Information System] and https://help.sap.com/docs/SAP_S4HANA_ON-PREMISE/c6e6d078ab99452db94ed7b3b7bbcccf/7384be0ca5a65f4e9ef2b23ad795d34a.html[Reports for Evaluating Users]

== Model 2: business roles, catalogs and restrictions in the Public Edition

In S/4HANA Cloud Public Edition 2608 the customer does not run PFCG, and does not create authorization objects or profiles. SAP's documentation describes an authorization model built from a few entities, and an app called IAM Information System shows how they are assigned to each other.

* A *business user* is the user of the system. It is created in the Maintain Business Users app, and only for a worker that already exists in the system, because the Public Edition is the leading system for users in that onboarding scenario. How workers arrive, by an HR integration or an identity management integration, is a decision of the workforce management scenario.
* A *business catalog* is a semantically meaningful bundle of apps aligned to a task or sub-process. SAP delivers predefined catalogs, which you can extend with custom catalog extensions. The Business Catalogs app lists all of them, including deprecated ones.
* An *IAM app* (app authorization variant) is the smallest unit for fine-grained authorization where it is supported. It attaches to exactly one transaction, which is the app's entry point, and a transaction can have many IAM apps. One app can therefore be offered as display only for auditors and as edit for administrators. The documentation gives Maintain Business Users as the example. Where a catalog does not support IAM apps, the catalog itself remains the smallest unit.
* A *business role* aggregates business catalogs and IAM apps for a job function, a warehouse clerk for example, and carries restriction values. It is created in the Maintain Business Roles app. A leading and derived business role approach lets derived roles inherit baseline assignments and restrictions from a leading role.
* A *restriction type* bundles restriction fields such as company code or plant. Which restriction types a business role can maintain depends on the IAM apps it activates. For each restriction type the administrator chooses an access category: Write, Read or Value Help. The default for Write is No Access, which means display only. The default for Read is Unrestricted. What is granted for Write is inherited by Read and Value Help unless those are explicitly unrestricted.

Two rules of this model surprise people who come from PFCG. First, authorizations are only granted, never denied. If business user receives business role 1, which restricts the sales organization to A, and business role 2, which allows all sales organizations, the user gets all of them. The documentation warns that assigning several business roles with the same restriction types increases the risk of overriding restrictions. Second, SAP delivers business role templates, but recommends them only for testing, for example in fit-to-standard workshops, because a role identical to its template, especially unrestricted, grants more than the actual job needs. For the production system, create business roles for the workplaces you identified.

Business roles are also changes, so they follow the landscape rules. The documentation says they should be created and updated only in the development system, transported to the test system and then to production through software collections, because a change made directly in production puts the productive data at greater risk. See xref:erp/sap/transports-and-change-management.adoc[Transports and Change Management] for how that transport works.

Source: https://help.sap.com/docs/SAP_S4HANA_CLOUD/53e36b5493804bcdb3f6f14de8b487dd/b9fd81647cdf45f5ad462a50222c2caa.html[Authorization Model], https://help.sap.com/docs/SAP_S4HANA_CLOUD/53e36b5493804bcdb3f6f14de8b487dd/c926d691d7144f7dba16f8e12ad81d28.html[How to Define Authorizations Based on Restrictions] and https://help.sap.com/docs/SAP_S4HANA_CLOUD/53e36b5493804bcdb3f6f14de8b487dd/2519632d64f84422b0faaa433d1fe964.html[Onboarding Business Users]. The apps run in a Public Edition tenant; not run here.

The developer's view of the same model is in xref:programming-languages/abap/authority-checks.adoc[Authorization Checks], whose section "What differs in ABAP Cloud" explains how IAM apps and business catalogs reach the authorization objects that custom ABAP Cloud code checks.

== Model 3: role collections in SAP BTP

Applications that run on SAP BTP, in the Cloud Foundry or Kyma environment, do not use PFCG or business roles. They use the SAP Authorization and Trust Management service. The service documentation says it manages user authorizations and trust to identity providers, which are the user base of the applications. SAP ID service is the pre-configured default identity provider, and a corporate or SAP Cloud Identity Services provider can replace it. The authorization terms are these.

* The application developer defines application-specific *role templates* in the application's security descriptor. A *role* is an instance of a role template.
* An administrator groups roles into *role collections*, typically for a type of user such as a sales representative. A collection can contain roles from several applications.
* The administrator assigns a role collection to users or, if the identity provider is a custom one that supplies groups, to user groups. The default identity provider can only provide individual users.

SAP BTP also delivers default role collections that administer the platform itself, for example Global Account Administrator and Subaccount Administrator, and viewer collections that only grant read access. They cannot be changed or deleted. Role collections are specific to an account: those of a global account do not exist in a subaccount, and the other way round. The cockpit marks a collection that contains critical security authorizations with a warning icon, and the documentation asks the administrator to review it before assigning it. A company that runs an ABAP back end and applications on SAP BTP therefore administers more than one of the three models for the same person.

Source: https://help.sap.com/docs/BTP/65de2977205c403bbc107264b8eccf4b/649961f8d4ad463daca33b3a20deba4c.html[What Is the SAP Authorization and Trust Management Service?], https://help.sap.com/docs/BTP/65de2977205c403bbc107264b8eccf4b/393ea0b222754311884123ce564779bd.html[Working with Role Collections], https://help.sap.com/docs/CP_AUTHORIZ_TRUST_MNG/ae8e8427ecdf407790d96dad93b5f723/14a877c6e2f14832999df500ffa6e05e.html[Roles and Role Collections], https://help.sap.com/docs/CP_AUTHORIZ_TRUST_MNG/ae8e8427ecdf407790d96dad93b5f723/31532c77bd61421e9d40d100fd75ef52.html[Assigning Role Collections to Users or User Groups] and https://help.sap.com/docs/BTP/65de2977205c403bbc107264b8eccf4b/0039cf082d3d43eba9200fe15647922a.html[Role Collections and Roles in Global Accounts, Directories, and Subaccounts]. == Comparing the three models

|===
| Question | PFCG roles (ABAP system) | Public Edition business roles | BTP role collections

| Where is it administered?
| SU01 and PFCG in the SAP GUI; SUIM for reports.
| Maintain Business Users and Maintain Business Roles apps in the launchpad.
| SAP BTP cockpit, or the command-line interface.

| Who is the user?
| A user master record in a client of the ABAP system.
| A business user created for an existing worker.
| A user of an identity provider connected to BTP.

| What is granted?
| Values of authorization fields in authorization objects, plus a menu.
| Business catalogs and IAM apps, narrowed by restriction values.
| Application roles, built from role templates in the application's security descriptor.

| How are permissions bundled?
| Single role, composite role, derived role.
| Business role, optionally leading and derived; catalogs and IAM apps inside.
| Role collection that holds roles.

| Can an administrator write authorization objects?
| Yes, in the role's authorization data.
| No. SAP delivers the catalogs and IAM apps that carry the permissions.
| No. The developer defines the application's authorizations.

| Where does the launchpad content come from?
| Catalogs in the role menu, spaces and pages assigned to roles.
| Catalogs inside business roles, spaces assigned to business roles.
| Not part of the role model; see the documentation of the application.

| How does it reach production?
| By transport request.
| Development system, then software collection to test and production.
| Not described on the pages used here.
|===

== Practical advice

* Think in jobs, not people. Make a role per job function, assign several roles to a person who has several jobs, and do not copy a colleague's access.
* Keep least privilege visible. Start from the smallest catalog or role, add what a real task needs, and review critical authorizations regularly with SUIM or the IAM Information System.
* Beware accumulation. In PFCG the effective authorization is the union of all roles; in the Public Edition it is the sum of all active values; two roles with different restrictions give the wider access.
* Never test in production. Create and change roles in development, test with a user who has only that role, and move them as a change.
* Prefer technical users that cannot log on interactively for system-to-system connections, and never share a dialog user between people.

== Summary

* A user is an identity and a role is a bundle of permissions; the same question is answered by three models in different SAP products.
* In an ABAP system (S/4HANA 2025 FPS02 on premise and Private Edition) users are created in SU01, roles in PFCG; roles carry authorization object values and a menu, and composite roles only collect single roles.
* A Fiori catalog is added to a PFCG role menu with Include Applications, which brings the start authorizations and proposals for the business data of its apps.
* SU53 shows the last failed check and SUIM lists users, roles and critical authorizations; neither reports rows that CDS access control silently removed.
* In the Cloud Public Edition 2608 a business user gets business roles made of business catalogs and IAM apps, narrowed by restriction types; authorizations are only granted, and business role templates are for tests.
* In SAP BTP, developers define roles from role templates, administrators group them into role collections and assign these to users or groups.
