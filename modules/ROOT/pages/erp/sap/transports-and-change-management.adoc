= Transports and Change Management
:description: How changes move from development to test to production in SAP landscapes: the Change and Transport System with STMS, CTS+, the Adaptation Transport Organizer in Cloud Public Edition, SAP Cloud Transport Management, and SAP Cloud ALM as the tool that orchestrates them, for S/4HANA 2025 FPS02 and Cloud Public Edition 2608.
:keywords: SAP, transport, transport request, CTS, STMS, TMS, CTS+, Adaptation Transport Organizer, ATO, SAP Cloud Transport Management, cTMS, CTMS, SAP Cloud ALM, SAP Solution Manager, change management, DEV, QAS, PRD

In a company that runs SAP, nobody changes the production system directly. A developer or a consultant changes
something in a development system, the change is recorded in a package of changes called a transport, the transport is
tested in a quality system, and only then is it brought into production. A newcomer meets this process the first day
after being told "put it in a transport". This page explains the idea and the four tools that do the work for different
products: the Change and Transport System with its Transport Management System for ABAP-based systems, the enhanced
variant CTS+ for objects that are not ABAP, the Adaptation Transport Organizer for SAP S/4HANA Cloud Public Edition, and
SAP Cloud Transport Management for cloud content on SAP BTP. It also explains where SAP Cloud ALM fits, the tool SAP
positions as the successor of SAP Solution Manager. It is written against SAP S/4HANA 2025 FPS02 (on premise and Private
Edition) and SAP S/4HANA Cloud Public Edition 2608, and each section says which of them it applies to.

== Key terms

* xref:erp/sap/glossary.adoc#transport-request[Transport request]: a container that records changes so that they can be moved to the next system.
* xref:erp/sap/glossary.adoc#change-and-transport-system[Change and Transport System (CTS)]: the set of tools of an ABAP system that records changes and distributes them in a system landscape.
* xref:erp/sap/glossary.adoc#transport-management-system[Transport Management System (TMS)]: the part of CTS, started with transaction `STMS`, that defines the landscape and runs imports.
* xref:erp/sap/glossary.adoc#adaptation-transport-organizer[Adaptation Transport Organizer (ATO)]: the transport tool of SAP S/4HANA Cloud Public Edition.
* xref:erp/sap/glossary.adoc#sap-cloud-transport-management[SAP Cloud Transport Management]: a service on SAP BTP that moves cloud content between environments along routes that you model.
* xref:erp/sap/glossary.adoc#sap-cloud-alm[SAP Cloud ALM]: SAP's cloud tool for managing implementation and operation, including the deployment of transports.
* xref:erp/sap/glossary.adoc#sap-solution-manager[SAP Solution Manager]: the earlier, on-premise application lifecycle management product that SAP Cloud ALM succeeds.

== Why changes travel in transports

An SAP system holds two kinds of changeable content: development objects, such as programs, tables and CDS views, and
configuration, called Customizing, such as the settings of a company code. Both have to behave the same in every system
of a landscape, otherwise a feature that worked in test fails in production. SAP therefore recommends a landscape of three
systems, development (DEV), quality assurance (QAS) and production (PRD). All changes are made in DEV. They are tested in
QAS, and the same recorded changes are then applied in PRD, never a hand-typed copy of them. The recorded changes are the
transport request, and moving them into the next system is the import.

The process has four stable ideas whichever tool is used.

* Changes are recorded at the moment they are made, in a container that has a name and an owner.
* The container is released in the source system, which makes it importable in the next one.
* The route from system to system is defined once by an administrator, not chosen per change.
* Every import leaves a log that says who moved what and when, which is the audit trail an auditor asks for.

The ABAP-specific details of requests and tasks, such as the locks that stop two developers from editing the same object,
are in xref:programming-languages/abap/transports-packages-and-gcts.adoc[Packages, Transports, gCTS and abapGit].

== The Change and Transport System and STMS

The Change and Transport System (CTS) is, in SAP's words, a tool that helps you organize development projects in
Customizing and in the ABAP development environment and then transport the changes between the SAP systems of your
landscape. The overview page adds that CTS can also transport non-ABAP objects and non-SAP applications, and that its
documentation covers the system and client landscape, the transport strategy and the transactions and tools.

CTS applies to classic ABAP-based systems: SAP S/4HANA on premise and Private Edition (2025 FPS02), and older SAP ERP
systems on SAP NetWeaver Application Server for ABAP. The Transport Organizer (transactions `SE09` and `SE01`) records
requests; the Transport Management System (transaction `STMS`) holds the landscape. In `STMS` one system acts as the
domain controller, and the routes between systems are transport routes: a consolidation route leads from the development
system to the next one and a delivery route continues from there, as the ABAP page describes.

The SAP Cloud ALM setup guide for these systems shows what a well-formed TMS configuration looks like, and it is a
useful checklist even if you do not use SAP Cloud ALM.

* A typical landscape in the guide is a development client, a quality client and a production client, written
  `DEV:100`, `QUA:200` and `PRD:300`, optionally with a pre-production system between quality and production.
* Client-dependent transport routes, the TMS option `CTC=1`, are mandatory from the start. The guide warns that turning
  them on later is a complete landscape change and is not supported while transports are still open.
* The guide strongly recommends a transport target group as the consolidation target, so that the group can change its
  member systems while the consolidation target itself stays the same.
* Imports of released requests go through `STMS`, and the guide checks the client settings in transaction `SCC4`.

A few things are also not supported when SAP Cloud ALM manages the landscape: systems with identical system IDs, TMS
domains with the same name, and switching client-specific routes on or off. The guide says buffer manipulations in CTS for
transports that SAP Cloud ALM manages should be avoided.

Source: https://help.sap.com/docs/CloudALM/08879d094f3b4de3ac67832f4a56a6de/a9ae2e3deb5148829e2381666c27ac0a.html[Configuring your Transport Management System (TMS) on the Managed Systems] and https://help.sap.com/docs/CloudALM/08879d094f3b4de3ac67832f4a56a6de/5aa24f076e3b4b47839f762baa7d089a.html[SAP Cloud ALM: SAP S/4HANA Cloud Private Edition and On-Premise Systems]

=== Who may create and release

Because a release is what makes a change importable, companies restrict it. The SAP Cloud ALM page on transports names the
authorization object `S_TRANSPRT`: removing activity 01 for a request type stops users from creating requests of that
type directly in the managed systems, and removing activities 43 and 75 stops them from releasing. If users also hold the
system-specific authorization `S_SYS_RWBO`, the same activities have to be removed there. The page gives this advice so
that creation and release happen only through SAP Cloud ALM; the same lever works in any landscape that wants to
restrict who can release. Authorizations in general are the topic of the page on xref:erp/sap/users-roles-and-authorizations.adoc[users, roles and authorizations], roles and authorizations.

Source: https://help.sap.com/docs/CloudALM/877c96cf971648b09ee0d0a64f7f4fef/8ca7fc56eace4370962fcc7d0b99d540.html[SAP Cloud ALM: Working with Transports]

== CTS+ for objects that are not ABAP

SAP's support page for the Change and Transport System tells readers who want to transport non-ABAP objects to use the
enhanced Change and Transport System (CTS+), and it points to a page that lists the applications that support CTS+. In
practice CTS+ uses the same TMS routes as a classic ABAP landscape, so a Java application or SAP HANA content can travel
beside the ABAP changes.

Two facts keep CTS+ in proportion today. The ABAP page of this site notes that for HANA content SAP recommends CTS+ over
the older HANA Transport for ABAP. And SAP Cloud ALM states plainly that CTS+ is not supported by its deployment
integration, so a landscape that needs SAP Cloud ALM to orchestrate transports cannot rely on CTS+ for them. The product
list of CTS+ applications is on the SAP page, not repeated here, because it changes with product releases.

Source: https://support.sap.com/en/tools/software-logistics-tools/change-and-transport-system.html[SAP Support: Change and Transport System] and https://help.sap.com/docs/CloudALM/877c96cf971648b09ee0d0a64f7f4fef/eae6f772d11e41b9b3d55515c226120c.html[SAP Cloud ALM: Integration of Deployment Tools]

== The Adaptation Transport Organizer in Cloud Public Edition

In SAP S/4HANA Cloud Public Edition the transport tool described in the sources below is the Adaptation Transport
Organizer (ATO). SAP Cloud ALM documentation names it as the transport
technology for SAP S/4HANA Cloud, and the SAP S/4HANA Cloud administration guide describes the transport of a flavor of
SAP Screen Personas as performed by the ATO. That page shows the cloud-style grouping: objects that are transported belong
to a software collection, an object in one collection cannot be in another, and an object a flavor depends on, such as an
icon or a template, has to be added to the collection before the transport.

The same administration guide says that, within one landscape, for example from development to production, the ATO is
used for the export and import of software collections. It also describes an Export and Import function for reusing
flavors in systems that are not connected through transport mechanisms.

When SAP Cloud ALM manages ATO transports, it works through a communication arrangement. The SAP Cloud ALM page on quality
approval names the arrangement `SAP_COM_0690` on SAP S/4HANA Cloud Public Edition and says that once it is active, the
quality approval is switched on and cannot be switched off. In the Features app of SAP Cloud ALM, setting a feature to
Ready for Production sets the quality status to Approved. SAP Cloud ALM also notes that ATO transports of the types
Central Business Configuration and Key User Extensibility cannot be created from SAP Cloud ALM.

For a developer the consequence is that the clean-core discipline of the Public Edition extends into change management:
the changes of a key user or of ABAP Cloud developers travel as ATO transports along a fixed landscape that SAP
operates, and the customer's job is to organize, approve and schedule them, not to build routes.

Source: https://help.sap.com/docs/SAP_S4HANA_CLOUD/80d510db496a4a41b316dfb4fb5881e4/53c7571722e1417898a8bd84965b2bcf.html[SAP S/4HANA Cloud: Transport a Flavor], https://help.sap.com/docs/SAP_S4HANA_CLOUD/80d510db496a4a41b316dfb4fb5881e4/9ddc7c8de7584219b632b9b7b31b293a.html[SAP S/4HANA Cloud: Assignment Categories] and https://help.sap.com/docs/CloudALM/877c96cf971648b09ee0d0a64f7f4fef/c6812a02200e40a0a801abf40cf3ff11.html[SAP Cloud ALM: Quality Approval for SAP S/4HANA Cloud Public Edition]

== SAP Cloud Transport Management for cloud content

SAP Cloud Transport Management (also written cTMS or CTMS) is a service of SAP Business Technology Platform. SAP
describes it as a service that manages software deliverables between accounts of different environments, such as Cloud
Foundry and ABAP, and that adds transparency to the audit trail so that you know who changed what in production and when.
It supports a separation of duties: a developer can start a transport from the development environment, while the import
into test and production is handled by a central operations team.

The service models a landscape with two ideas.

* A transport node is the source or the target end point of a deployment, for example a development space and a
  production space in a Cloud Foundry subaccount. If you have development and production you need a two-node landscape,
  and a test account makes it a three-node landscape.
* A transport route connects two nodes. The same node can be the source of several routes but the target of only one.
  The Transport Landscape Wizard creates the nodes and routes of a simple landscape from a template.

Each node has an import queue. SAP states that you can import all requests of a queue in one go or only selected ones, and
that full imports can be scheduled to run automatically. The home screen shows, among other things, the nodes with
the most importable requests waiting. The service integrates with the tools that create the content: a developer starts the
transport from the application, and for content that has no export integration, files can be uploaded from a local file
system and imported in a target node. It is available in the Cloud Foundry and Kyma environments, and SAP also
describes it as a complement to CI/CD pipelines.

Cloud Transport Management is the transport tool of SAP BTP content. It is not the tool of SAP S/4HANA Cloud Public Edition
(that is ATO), nor of an ABAP-based on-premise system (that is CTS). SAP's integration page lists the content that uses it,
among them the SAP BTP ABAP environment, SAP Analytics Cloud and SAP Build Apps.

Source: https://help.sap.com/docs/TRANSPORT_MANAGEMENT_SERVICE/7f7160ec0d8546c6b3eab72fb5ad6fd8/5fef9d6b1cb047b2b18d9eb57aa15352.html[What Is SAP Cloud Transport Management], https://help.sap.com/docs/TRANSPORT_MANAGEMENT_SERVICE/7f7160ec0d8546c6b3eab72fb5ad6fd8/dddb74937a014aea8d3d76d740180597.html[Create Transport Routes], https://help.sap.com/docs/TRANSPORT_MANAGEMENT_SERVICE/7f7160ec0d8546c6b3eab72fb5ad6fd8/f14192ede8ac4603955b572537d6bec2.html[Use the Transport Landscape Wizard] and https://help.sap.com/docs/TRANSPORT_MANAGEMENT_SERVICE/7f7160ec0d8546c6b3eab72fb5ad6fd8/ddaa000bc92c43d8bd09f4e2c8ca05eb.html[Integrating SAP Cloud Transport Management with Other SAP Cloud Solutions]

The landscape page for cTMS gives one useful detail. For a product such as SAP Cloud Integration, a two-target landscape
usually becomes a three-system landscape, and the transports are exported from the development system into the buffer of the
test system, which is why a dummy development target is needed. For development outside SAP BTP products, for example in
SAP Business Application Studio, there is no dedicated cloud development system, so a CI/CD upload goes straight to the
first deployment node; SAP Cloud ALM still needs the development system defined so that it knows the order of the systems.

== SAP Cloud ALM as the orchestrator

SAP Cloud ALM does not move a transport itself. Its page on deployment tools says that change and deployment management
does not communicate directly with SAP solutions; it talks only to the deployment tools, namely CTS, the Cloud Transport
Management service and the ATO. The page lists which solutions each integrates: CTS for SAP S/4HANA Cloud Private Edition,
SAP S/4HANA, SAP NetWeaver Application Server for ABAP on premise and SAP SuccessFactors Employee Central Payroll; ATO for
SAP S/4HANA Cloud and SAP Integrated Business Planning for Supply Chain; and the Cloud Transport Management service for the
content types it supports. The actions available depend on the tool.

Transports are assigned to features in the Features app, so that the deployment of a feature's technical content is tracked
beside its business sign-off. Systems are organized in system groups, where each system has a role: Starter, Development,
Quality Assurance, Pre-Production or Production. The Development role is the source system from which a transport can be
created or assigned to a feature. The Deployment Scheduler app then lets you pick target systems from the group for a
planned deployment. A transport that was made outside, in another development system, cannot be assigned directly: SAP
describes repacking its objects into a new transport with transaction `SE09`, or recording it as a manual transport
reference and deploying it in the managed system.

SAP Cloud ALM sets conditions for the landscape it manages. Imports for cTMS nodes that are controlled by SAP Solution
Manager cannot be triggered from it, and for content of the type BTP ABAP the selected-import option is not available, so
the whole import queue up to the chosen request is imported.

== From SAP Solution Manager to SAP Cloud ALM

SAP Solution Manager is the on-premise tool that many companies still use to manage change, testing and operations of
their SAP systems. SAP's transition page for SAP Cloud ALM states that mainstream maintenance for SAP Solution Manager ends
on December 31, 2027, and recommends completing the transition to SAP Cloud ALM before that date. The same page links to
an SAP Note on the mainstream maintenance of SAP Solution Manager 7.2, which needs a login and was not opened for this page,
so the page states the date as the transition page words it. For a newcomer the practical meaning is that a company that
still has a Solution Manager landscape probably has a migration project planned, and that a new project on S/4HANA Cloud
starts directly with SAP Cloud ALM.

Source: https://support.sap.com/en/alm/sap-cloud-alm/transition-to-sap-cloud-alm.html[SAP Support: Transition to SAP Cloud ALM]

| SAP S/4HANA on premise and Private Edition 2025 FPS02
| CTS (Transport Organizer and TMS)
| In `STMS`, by the customer administrator.

| SAP S/4HANA Cloud Public Edition 2608
| Adaptation Transport Organizer (ATO)

== Summary

* Changes reach production only as recorded transports that pass development, quality assurance and production, with a log
  at every import.
* CTS and its Transport Management System (`STMS`) serve ABAP-based systems such as S/4HANA on premise and Private Edition;
  CTS+ extends the same routes to non-ABAP objects but is not supported by SAP Cloud ALM.
* SAP S/4HANA Cloud Public Edition uses the Adaptation Transport Organizer, where objects travel in software collections.
* SAP Cloud Transport Management models nodes and routes for SAP BTP content and keeps an import queue per node.
* SAP Cloud ALM orchestrates deployments through these tools and does not move transports itself.
* SAP states that mainstream maintenance for SAP Solution Manager ends on December 31, 2027 and recommends moving to
  SAP Cloud ALM before then.
