= Key-User Extensibility
:description: What a business expert can change in SAP S/4HANA Cloud Public Edition 2608 without writing a program: custom fields, custom logic, custom CDS views, custom analytical queries and custom business objects, and how the results move to production.
:keywords: key user extensibility, in-app extensibility, Custom Fields app, Custom Logic app, Custom CDS Views app, Custom Analytical Queries, Custom Business Objects, extensibility inventory, software collection, SAP S/4HANA Cloud Public Edition, ABAP for key users, YY1

Most companies want a standard business application to look a little different: one more field on a form, a check that
runs when a document is saved, a report that combines two data sources. SAP calls the way a business expert does this
inside the running system, without developer tools, key-user extensibility. This page explains what the five key-user
tools do, what each one is for, which SAP objects they may touch, and how a finished extension travels from the test
system to production. It is written against the documentation of SAP S/4HANA Cloud Public Edition 2608, the release
named "2608 Latest" on the SAP Help Portal on 2026-11-13. The tools come from the "Extend and Integrate Your SAP
S/4HANA Cloud Public Edition" guide and run in a Public Edition tenant, so nothing here was run: every listing
requires an SAP system and is labeled as not run here. The page does not state which of these apps exist in SAP
S/4HANA on premise or Private Edition, because that was not checked. Developer extensibility and side-by-side
extensibility on SAP BTP are separate options, described in the page on xref:erp/sap/extensibility-and-clean-core.adoc[extensibility and clean core] (a later page of
this section) and in the ABAP section.

== Key terms

* xref:erp/sap/glossary.adoc#key-user-extensibility[Key-user extensibility]: changing and extending SAP applications with built-in apps, by business experts, without a development environment.
* xref:erp/sap/glossary.adoc#extension-item[Extension item]: anything you create with the key-user tools, such as a custom field, a logic implementation or a custom CDS view.
* xref:erp/sap/glossary.adoc#business-context[Business context]: the place in a standard application where a custom field is added.
* xref:erp/sap/glossary.adoc#released-api[Released API]: an SAP object that SAP has marked as stable for a given kind of use.
* xref:erp/sap/glossary.adoc#software-collection[Software collection]: the bundle of extension items that you export from one system and import into the next.
* xref:erp/sap/glossary.adoc#custom-business-object[Custom business object]: a business object that you define yourself, with its database tables, services and screens generated for you.

== Why there is a key-user tier

SAP's page "Extensibility" for the Public Edition lists three options: key-user extensibility "through built-in
capabilities and with extensibility hub", developer extensibility through the SAP S/4HANA Cloud ABAP environment, and
side-by-side extensibility through SAP BTP. Its comparison table describes key-user extensibility as smaller
low-code or no-code extensions that are fully integrated in the SAP S/4HANA Cloud Public Edition stack, aimed at key
users, with BAdIs and CDS views as the released object types. Typical uses are small changes to existing apps, custom
forms and templates (adding new fields, for example) and custom analytics. The same page states why this is safe: the
extensions are "upgrade-proof" because they use only objects that SAP has released, so SAP software updates do not
depend on them.

[cols="1,2,2",options="header"]
|===
|Option |Who and what |Where it runs

|Key-user extensibility
|Key users; smaller low-code or no-code extensions
|Inside the SAP S/4HANA Cloud Public Edition stack

|Developer extensibility
|ABAP developers; tightly coupled, more complex extensions and apps
|SAP S/4HANA Cloud ABAP environment, on the same stack

|Side-by-side extensibility
|Developers; loosely coupled extensions and apps
|SAP BTP
|===

== What the key-user tools are

The page "Key User Extensibility" of the same guide summarizes the toolbox in a few sentences, and this section follows
them. The extensibility apps customize applications and their screens, reports, email templates and form templates, and
they can create database tables for segmentation and design queries. An important limit comes first: you can extend an
application only if SAP made that application extensible.

[cols="2,3,3",options="header"]
|===
|App |What it creates |Typical use

|Custom Fields
|Custom fields, and data source extensions that expose existing fields of predelivered data sources
|One more field on a screen, in a report, in an email or form template

|Custom Logic
|Implementations of released business add-ins (BAdIs) and behavior extensions, written in ABAP for key users
|A check or a derived value that the standard process does not offer

|Custom CDS Views
|CDS views built on released CDS views or on custom content such as custom business objects
|Combine data sources for analytics, or expose data as an OData API

|Custom Analytical Queries
|Queries on the fields of CDS views, with filters, restricted and calculated measures and a preview
|A report that a business user can run and adapt

|Custom Business Objects
|A business object with its database tables, OData services and generated UI, and custom logic on its nodes
|A small application of your own, such as a list of categories or approvals
|===

Source: https://help.sap.com/docs/SAP_S4HANA_CLOUD/0f69f8fb28ac4bf48d2b57b9637e81fa/3ccb50e724b045508fea8b2cf1774b2b.html[Key User Extensibility, SAP S/4HANA Cloud Public Edition 2608]

Two more apps support the work and are covered at the end of the page: Export Software Collection and Import Collection
move extension items between systems, and Extensibility Inventory lists them and their dependencies. SAP's overview also
mentions custom catalog extensions, which this page does not cover.

== Custom fields and data source extensions

The Custom Fields app is used "as a business expert or implementation consultant". It combines two options: custom
fields, and data source extensions. SAP's list of key features for custom fields includes creating a field for a specific
business context, making it available in other languages, enabling its usage in UIs, reports, email templates, form
templates and business scenarios, making its content searchable with free-text search, specifying its aggregation
behavior, publishing it to the test system, editing a published field and deleting fields. A data source extension makes
existing fields of a predelivered data source usable.

The process page "Creating Custom Fields" gives the order of work:

. Open the Custom Fields app, either from the SAP Fiori launchpad or from an extensible application with Add Field in
  the UI adaptation mode of that application.
. Create the field in the business context where it is needed: click Add Business Context, choose one from the value
  help and you land on the custom field itself.
. Edit the field and enable its usage, for example on a screen or in a report.
. Publish the custom field for transport. A field's length cannot be decreased after publishing.
. Export the field with the Export Software Collection app. To see the field in an SAP Fiori app, restart the app and the
  adaptation mode.

A few rules from the same page are worth knowing before you start. A field can be removed from a business context only
if it has not been exported yet. Publishing and deleting a field technically need an ABAP Dictionary activation, which
can run long, so SAP recommends updating fields as needed and then publishing or deleting several at once. Only one
publishing or deletion process can be active at a time, requests wait in a queue, and the affected application can be
unusable while a process runs. The Custom Fields app states that when you delete an already transported field, the
contained data is saved for 18 months, and that no read access logging is provided for custom fields.

Which fields you may add depends on what SAP released. The Key User Extensibility page names three independent types of
release for APIs and data sources such as OData services or CDS views: add custom fields with the key-user app, use
system-internally, and use as remote API. Only an object released for the first type accepts fields from the Custom
Fields app, and SAP keeps those extension points stable. An object released for system-internal use can be called from
ABAP code and used as a base for your own CDS views, and SAP keeps its public interface technically stable, never
removing or changing existing parameters, elements or associations. An API released as a remote API appears in the SAP
Business Accelerator Hub for external access. The page also covers deprecated objects: a deprecated object has a
successor, new custom objects should not be built on it, and the Extensibility Inventory app can show where one is used.

Custom fields can hold personal data in business contexts that support the privacy-relevant master data objects Central
Business Partner, Customer, Supplier, Contract Person and Workforce Person. The Custom Fields app, the Custom Logic app and
the Custom Business Objects app all carry the caution that data in an extension scenario is managed differently from
standard scenarios, and that the owner of the data is responsible for legal requirements such as data protection.

== Custom logic

Not every change is a field. The Custom Logic app implements business add-ins (BAdIs) and behavior extensions of business
objects that SAP released. A BAdI is a place in SAP's code where the standard process calls a method that you may
implement; the page on xref:programming-languages/abap/enhancements-and-badis.adoc[enhancements and BAdIs] in the ABAP section explains the idea. SAP lists the key features: create an
implementation, publish it to your test system, write custom code with "ABAP for key users", test the code with
predefined test variants, compare it with older versions and delete implementations. You can start from the Custom
Logic app or from the UI adaptation of an extensible application.

ABAP for key users is a restricted subset of the language. SAP's overview lists its statements on a page of their own
("Statements in ABAP for Key Users"), so treat the list on that page as the definition and do not assume that a
statement of ABAP Cloud or classic ABAP is allowed. The relation between the layers is spelled out too: by default key-user
objects cannot use developer extensibility objects and the other way round. Two exceptions are documented. Custom
fields and data source extensions can be used by ABAP classes and interfaces, CDS view entities and CDS custom
entities. And a developer can release CDS view entities, CDS custom entities, ABAP classes and interfaces, and ABAP data
types, structures, table types and tables for key users by setting their API state in ABAP Development Tools; the
Custom Logic app and, for CDS view entities, the Custom CDS Views app can then use them.

The code in a custom logic implementation can also work with custom business objects. SAP's code samples page states
that "only BAdIs that contain an importing parameter referencing the ABAP interface type IF_CBO_WRITE can be used to
modify data in custom business objects". The following sketch uses the calls shown on that page, reduced to the smallest
case: read the root node of a custom business object and create it when it does not exist yet. The business object and
data type names carry the prefix `YY1_`, as in SAP's sample. The structure `ls_category` and the key values are
placeholders you would replace with your own.

[source,abap]
----
" requires an SAP system; not run here
" Runs inside a BAdI implementation whose method receives the write API as parameter WRITE.
DATA lv_key TYPE yy1_category.

TRY.
    DATA(lo_category) = write->get_root(
      business_object_id = 'YY1_CATEGORY'
      key                = lv_key ).
  CATCH cx_cbo_write_not_existing.
    lo_category = write->create_root(
      business_object_id = 'YY1_CATEGORY'
      data               = ls_category ).
ENDTRY.
----

Source: adapted from https://help.sap.com/docs/SAP_S4HANA_CLOUD/0f69f8fb28ac4bf48d2b57b9637e81fa/5769d4c3e91546199c3980a5546324d1.html[Code Samples to Write Data from a Custom Logic to Custom Business Objects]; requires an SAP system; not run here

The sample on SAP's page goes further (it gets and updates data, handles child nodes and executes actions with
`execute_action`), and it is the page to open for the full code.

== Custom CDS views

The Custom CDS Views app lets a customer build content on the virtual data model and on other custom content such as
custom business objects. SAP names three purposes: external APIs that define a service consumed externally through OData,
cube or dimension views for analytical scenarios, and general custom CDS views for reuse. In the app you can add fields
from several data sources, create calculated fields, refine field properties, create parameters and add filters to
narrow the result. SAP's overview explains why this is useful: the data of an application sits in many database tables,
and a CDS view merges the data from different sources and rearranges the fields for one purpose. The key-user page says custom
CDS views are based on predelivered data sources and on CDS view entities that a developer released for key users.

Several help pages go with it: modeling rules, creating and editing views, migrating and optimizing them, and exposing a
custom CDS view as an OData API. Open these when you build a view, starting with the modeling rules.

Source: https://help.sap.com/docs/SAP_S4HANA_CLOUD/0f69f8fb28ac4bf48d2b57b9637e81fa/e30de6eae4d24d70b65996ac8ff88848.html[Custom CDS Views]

== Custom analytical queries

A query turns raw business data into a grid that a person can read and filter. The Custom Analytical Queries app hides
the query language: you select fields from a CDS view and set filters. SAP lists these options: search, copy a query from
predefined SAP queries, add dimensions and measures from the data source, add a counter for a distinct count, configure
fields (position, restricted measure, calculated measure), define filters, preview the result, set the maximum
processing effort, zero suppression and runtime extensibility, which adds dimensions or measures at run time that the
query did not predefine. The app page says you cannot create a new query in this app; creating one is done in the Custom
Analytical Queries and Services app, and the pages for the creation steps and for access from SAP Analytics Cloud sit in
the same guide.

Source: https://help.sap.com/docs/SAP_S4HANA_CLOUD/0f69f8fb28ac4bf48d2b57b9637e81fa/33f3a229ecfe438ca6b2053c48b4e1bb.html[Custom Analytical Queries]

== Custom business objects

When no standard application fits, the Custom Business Objects app creates one from your definition. SAP states that you
can create business objects and the corresponding database tables, copy published objects, add fields, generate UIs,
associate objects with each other, track changes with change documents, generate OData services for access from
outside, publish and edit them, add several subnodes to one object and implement custom logic on node level. You can
delete a custom business object only until it has been transported to your production system. The page also states that
no instance-based authorization is provided for custom business objects, which matters for any design that holds
confidential records. A custom application based on an object is then added to the SAP Fiori launchpad, a step described
in the guide's pages on creating custom applications.

Source: https://help.sap.com/docs/SAP_S4HANA_CLOUD/0f69f8fb28ac4bf48d2b57b9637e81fa/b45696ca0d9143cba040797e9c71aa44.html[Custom Business Objects]

== Moving extensions to production and keeping track

Creating an extension item and making it live in production are two steps. The Custom Fields and Custom Logic apps
publish to the test system. For production, you collect the items you want to move in a software collection, check them
for inconsistencies and dependencies, and export the collection with the Export Software Collection app. SAP lists these
abilities of the app: create, add items, merge collections, check items, export a collection and do a hotfix export.
You add the items manually. The Import Collection app then brings the collection into the next system.

[mermaid]
----
flowchart LR
    A["Build in the Custom Fields,<br/>Custom Logic or Custom<br/>Business Objects app"] --> B["Publish to the<br/>test system"]
    B --> C["Add the items to a<br/>software collection"]
    C --> D["Export Software<br/>Collection app"]
    D --> E["Import Collection app<br/>in the next system"]
    E --> F["Items live in production"]
----

The Extensibility Inventory app is the map of everything you built. It shows all extension items, with name, type, date
and person of the last change, and whether the item was deleted, imported or exported. For each item it lists what the
item uses and what uses it, which tells you what an import or export would affect. In the Cloud version it also shows the
change history. Extension items that need rework get tasks with a category (deprecation, security, functionality,
performance, stability, error) and a priority of low, medium or high. You can download the dependencies and open them in
Excel. A related page, "ATC Checks for Key User Extensibility Objects", and an export to abapGit exist in the same guide for
teams that automate quality checks and version control; this page only points to them.

Source: https://help.sap.com/docs/SAP_S4HANA_CLOUD/0f69f8fb28ac4bf48d2b57b9637e81fa/fcf72df4f7c245f1bfea123dbec0613d.html[Extensibility Inventory]

== When to leave the key-user tier

Choose the lightest tool that fits. A new field, a small check, a report on released data: the key-user apps. A tightly
coupled extension with classes, behavior definitions and richer testing: developer extensibility in the ABAP environment,
which is the route of the ABAP Cloud pages of this site. An application for separate users or a different technology
stack: side-by-side extensibility on SAP BTP, for example with the xref:erp/sap/cap-getting-started.adoc[CAP framework].
SAP's own comparison table suggests the same split. The tools of this page cannot go beyond what SAP released: if the
object you need to extend is not released for the type of use you need, raise it through the Extensibility Influence
channel that SAP names, or move to another option.

== Summary

* Key-user extensibility lets business experts extend SAP S/4HANA Cloud Public Edition 2608 inside the system, with
  low-code apps, and only on objects that SAP released, which is why upgrades do not break the extensions.
* There are five tools: Custom Fields (fields and data source extensions), Custom Logic (BAdI implementations in ABAP
  for key users), Custom CDS Views, Custom Analytical Queries and Custom Business Objects.
* A custom field is added to a business context, usage is enabled, the field is published and then exported; a length
  cannot be decreased after publishing and only one publish or delete process runs at a time.
* Key-user and developer objects are separated by default, with documented exceptions in both directions.
* Extensions travel by software collection with Export Software Collection and Import Collection, and the Extensibility
  Inventory shows all items and their dependencies.
* Data in extension scenarios is the customer's responsibility under data protection law, and custom business objects
  have no instance-based authorization.
