= SAP Guide: Model a Domain and Add Custom Logic in CAP
:description: Step-by-step guide to CAP Node.js 10.2: model claims with a composition of items and an association to a reference entity, use cuid and managed, add a validation handler and a bound action submit, and run it all with cds watch and curl.
:keywords: SAP, CAP, CDS, association, composition, cuid, managed, assert.target, event handler, before handler, req.error, bound action, req.subject, deep insert, OData V4, Node.js, step by step, guide

include::partial$ai-disclaimer.adoc[]

Checked on 2026-11-13 against CAP Node.js 10.2 (`@sap/cds` 10.2.2, `@sap/cds-dk` 10.2.1) and Node.js 24.21.

== What you build

This is a teaching model built with CAP. It is not SAP S/4HANA or SAP SuccessFactors and does not reproduce their screens.

You build a small service for expense claims in which a claim is made of parts. A claim has several items, and each item points at a category from a short list. You describe this in CDS with a composition (the items belong to their claim), an association (an item refers to a category that lives on its own) and two ready-made building blocks, `cuid` and `managed`. Then you add two pieces of custom logic in JavaScript: a validation handler that refuses bad claims and sums the total, and an action `submit` that moves a claim from the status `N` (new) to `S` (submitted). You try everything with `curl`.

image::sap-general-guide-cap-domain-model-and-custom-logic-08-result.svg["Terminal with the call of the action submit on the claim Customer visit Chicago: the first call answers HTTP 200 with the claim, whose status is now S and whose total is 128.50, and the second call answers HTTP 409 with the message Claim is already submitted (status S)",width=900]

== Before you start

* No account is needed: the CAP tools install from the public npm registry without signing in. Installing `@sap/cds-dk` and `@sap/cds` means accepting the SAP Developer License Agreement, version 3.2, which the packages state themselves; the lab README names it.
* Install Node.js 22.12 or newer (`node -v` prints the version) and the CAP command line tools (`npm install --global @sap/cds-dk`, as in the guide xref:erp/sap/guide-first-cap-service.adoc[Your First CAP Service]). Use a code editor such as Visual Studio Code and a terminal.
* `curl` must be version 7.82 or newer, because the guide uses its option `--json`. `curl --version` shows it.
* Read xref:erp/sap/cap-domain-modeling.adoc[CAP Domain Modeling] and xref:erp/sap/cap-services-and-handlers-nodejs.adoc[Services and Custom Handlers in Node.js] first, or at least know what an entity, an association and an event handler are. The guide xref:erp/sap/guide-first-cap-service.adoc[Your First CAP Service] builds a smaller project in the same way, and you can do it first.
* The project is built from `cds init`, so nothing from an earlier guide is needed. The names `Categories`, `Claims` and `ClaimItems`, the category codes and the amounts are the model's own and are made up. `cuid`, `managed`, `Composition`, `Association` and `@assert.target` come from the CAP documentation pages listed under Sources. The status codes `N` and `S` are made up as well.
* The figures are drawings of the editor, the terminal and the browser, not screenshots. A highlighted box with a number marks the file, the line or the address of the step with the same number.

== Steps

=== Create the project and the model

. Create the project, install its dependencies and open the folder in your editor (in Visual Studio Code, `code .`):
+
[source,bash]
----
cds init claims --nodejs
cd claims
npm install
----
+
`cds init` prints `Successfully initialized CAP project` and creates the folders `app`, `db` and `srv`.
. Create the file `db/schema.cds`. The first line imports `cuid` and `managed` from CAP. `cuid` adds a key `ID` that CAP fills with a new unique value. `managed` adds the fields `createdAt`, `createdBy`, `modifiedAt` and `modifiedBy`, which CAP fills for you. The file then defines three entities:
+
* `Categories` is a small reference list. Its key is a code that you choose, such as `TRAVEL`.
* `Claims` has a title, a status that starts as `N` and a total. The line `items : Composition of many ClaimItems on items.claim = $self` says that the items are parts of the claim: they are created, read and deleted together with it. The `on` condition names the backlink `claim`, which is the association on the item.
* `ClaimItems` has a description and an amount, an association `claim` back to its claim and an association `category` to the reference entity. The annotation `@assert.target` makes CAP check that the category exists when an item is written.

=== Run the service

[start=5]
. In the terminal, in the project folder, start the server in watch mode. Leave it running: `cds watch` restarts the server whenever you save a file.
+
[source,bash]
----
cds watch
----
. Read the log. CAP loads the model files, connects to a database that lives only in memory and fills it from your three CSV files. The service is served at `/odata/v4/claims` (CAP derives `claims` from the name `ClaimsService`) on `http://localhost:4004`. The line `+using auth strategy { kind: 'mocked' }+` says that no real login is used while you develop.
+
image::sap-general-guide-cap-domain-model-and-custom-logic-03-cds-watch.svg["Terminal after cds watch: the log lists the model files srv/claims-service.cds, db/schema.cds and the common.cds of CAP, connects to an in-memory SQLite database, initializes it from the three CSV files for Claims, ClaimItems and Categories, serves ClaimsService at /odata/v4/claims and ends with server listening on http://localhost:4004; callout 5 marks the command and callout 6 the lines that load the CSV files",width=900]
+
The figure leaves out the banner that `cds watch` prints before the first line, a line about service bindings that your machine may or may not print, and the last line, which names the start time.

=== Read the structure

[start=7]
. Open the claim together with its items and their categories in the browser. The query option `$expand` follows a relation and returns the related rows inside the answer: `items` is the composition and `category` is the association of each item. Open http://localhost:4004/odata/v4/claims/Claims?$top=1&$select=title&$expand=items($select=description;$expand=category). The answer holds the claim `Customer visit Chicago` with its two items, and each item carries its category with the code and the name from the reference list. The key `ID` is always part of an answer.
+
image::sap-general-guide-cap-domain-model-and-custom-logic-04-expand.svg["Browser with the address localhost:4004/odata/v4/claims/Claims with the query options top, select and expand, marked by callout 7: the JSON response holds one claim, Customer visit Chicago, with its two items, the Train ticket in the category TRAVEL named Travel and the Client dinner in the category MEALS named Meals",width=900]
. Ask for the items directly. You did not list `ClaimItems` in the service, and CAP refuses a direct request, because a composition target is reachable only through its parent. The single quotes keep the shell from touching the address.

=== Add a validation handler

The model cannot say that an item must cost something or that a claim needs a title. Such rules go into an event handler, a small function that CAP calls at a defined moment while it processes a request.

[start=9]

The class extends `cds.ApplicationService`, which brings the built-in reading and writing, and attaches the function `validateClaim` for the phase `before` of the events `CREATE` and `UPDATE` on `Claims`. The function reports each broken rule with `req.error`, which records the error and goes on, so that the user sees all of them at once. . Call the action. In OData a bound action is called with a `POST` to the row's address followed by the service name and the action name. The shell treats the parentheses of that address in its own way, so keep the address in single quotes. Put it into a variable, call it, and call it again:
+
[source,bash]
----
URL='localhost:4004/odata/v4/claims/Claims(a1111111-1111-1111-1111-111111111111)/ClaimsService.submit'
curl -s -i --json '{}' "$URL" | grep -E "^(HTTP|\{)"
curl -s -i --json '{}' "$URL" | grep -E "^(HTTP|\{)"
----
+
The first call answers HTTP 200 with the claim, and its `status` is now `S`. The second call answers HTTP 409 with the message `Claim is already submitted (status S)`. The same call for the second claim of the CSV file answers 409 at once, because that claim was submitted from the start. The result is the figure at the top of this guide.

== Check the result

* The log of `cds watch` shows the lines `+impl: 'srv/claims-service.js'+` and `server listening` and no line that starts with `[ERROR]`.
* The expand request returns the claim `Customer visit Chicago` with two items, each with its category.
* A claim with an item amount of zero or less, or with no title or no items, is refused with HTTP 400, and a valid claim answers 201 with the `total` filled in.
* The first `submit` answers 200 and `status` `S`; the second answers 409.

== Variations

* Look at the effect of `@assert.target`. With the annotation in place, post a claim with an item whose `category_code` is `NOPE`: the answer is HTTP 400 with the code `ASSERT_TARGET` and the message `+Target with this key doesn't exist.+` Remove the annotation, save, and post the same request again: it answers 201 Created and stores the item with a category that does not exist. An association alone does not check its target.
* Put the rules under test. Install the test helper with `npm install --save-dev @cap-js/cds-test`, add the script `"test": "node --test"` to `package.json` (`npm pkg set scripts.test="node --test"` does it), create `test/service.test.js` and run `npm test`. == What can go wrong

[cols="2,3,3",options="header"]
|===
|Symptom
|Cause
|Fix

|`zsh: no matches found: localhost:4004/odata/v4/claims/Claims(a1111111-1111-1111-1111-111111111111)/ClaimsService.submit`
|The shell reads the parentheses, and in other addresses the `?` and the `$`, as its own syntax.
|Put the whole address in single quotes, as in step 15.

|The log shows `[EADDRINUSE] - port 4004 is already in use by another server process.`
|Another program already listens on port 4004.
|Stop that program, or press Return to restart with an arbitrary port and use the port that the log names in every address of this guide.

|The claim from `bad-claim.json` is accepted with HTTP 201, and the action answers HTTP 501 with `Service "ClaimsService" has no handler for "submit ClaimsService.Claims".`
|The handler file is not found. Its name differs from the service file (here `claim-service.js` instead of `claims-service.js`), so the log has no `impl:` line and none of your rules run.
|Rename the file to `srv/claims-service.js` and save. `cds watch` restarts, and the `impl:` line appears.

|`cds watch` stops with `Error: in cds.deploy(): table sap_guide_claimsmodel_ClaimItems has no column named category`
|A header in a CSV file names a field that the entity does not have, here `category` instead of `category_code`.
|Correct the first row of the CSV file so that each name is a field of the entity, and save.

|`/odata/v4/claims/ClaimItems` answers HTTP 405 with the code `ENTITY_IS_AUTOEXPOSED`
|`ClaimItems` is a composition target, so CAP exposes it only through its parent.
|Read it with `$expand=items` on `Claims`, or list it explicitly in the service.

|A `GET` on the address of `submit` answers HTTP 405 `Method Not Allowed`
|An action changes data, so OData calls it with `POST`.
|Send the request with `+curl --json '{}' ...+`, which makes it a `POST`.

|A `POST` to `/odata/v4/claims/submit` answers HTTP 404 with `Invalid resource path "ClaimsService.submit"`
|`submit` is bound to `Claims`, so it needs the address of one claim in front of it.
|Use the address of step 15, with the `ID` of the claim.
|===
