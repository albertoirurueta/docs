Real data is rarely ready to analyse. Values are missing or encoded as `-999`, the same customer is spelled three ways, a
number arrives as the text `"1,250.50"`, dates are ambiguous, and one sensor reported a temperature of 4,000 degrees.
Cleaning is the work of turning that raw material into a table in which every column has one meaning, one type and one
set of valid values. It is also where most of the judgement in a project lives, because every cleaning rule is a
decision about what the data means.

This page is concept-first and uses pandas for the mechanics. It targets **Python 3.12 or later**, **pandas 3.1** and
**NumPy 2.5**, as checked against the official documentation in **October 2026**. Every code block was executed on those
versions and the printed output is the real output. The detailed method reference lives in the pandas sub-section, for
example xref:data-science/pandas/missing-data.adoc[Missing Data], xref:data-science/pandas/duplicates.adoc[Duplicate Labels & Rows]
and xref:data-science/pandas/text-data-and-str-dtype.adoc[Text Data & the str Dtype]. For the R equivalents see
xref:programming-languages/r/missing-and-special-values.adoc[missing and special values] and
xref:programming-languages/r/tidyr-purrr-and-stringr.adoc[tidyr, purrr and stringr].

== A cleaning workflow

Cleaning goes faster and is easier to defend when it follows a fixed order. Each step uses the output of the previous one.

[mermaid]
----
flowchart LR
    A["Inspect: shape, dtypes, summaries"] --> B["Fix structure: tidy columns and names"]
    B --> C["Convert types and sentinels"]
    C --> D["Normalise text, units and dates"]
    D --> E["Remove duplicates"]
    E --> F["Handle missing values"]
    F --> G["Investigate outliers"]
    G --> H["Validate with explicit checks"]
    H --> I["Write the cleaned data and the rules"]
----

Three principles apply to every step.

* **Never edit the raw data.** Read it, transform it in code, write the result elsewhere. A cleaning script that can be
  re-run is documentation of every decision.
* **Prefer flagging to deleting.** Adding an `is_imputed` or `is_outlier` column keeps information that deleting rows
  destroys, and lets a later analysis choose.
* **Make each rule explicit and testable.** "Age is between 0 and 120" is a check that can fail loudly; "I looked at the
  ages" is not.

Cleaning that learns something from the data (a mean to fill gaps, a scaling factor, a category list) must be fitted on
the training data only, or the evaluation leaks information from the test set. That boundary is covered in
xref:data-science/feature-engineering.adoc[Feature Engineering] and xref:data-science/model-evaluation.adoc[Model Evaluation & Validation]; deterministic
rules such as removing exact duplicates or fixing a unit can safely run before splitting.

== Tidy data

Hadley Wickham's _Tidy Data_ (Journal of Statistical Software, 2014) gives the structure that most analysis tools expect:

. every variable is a column,
. every observation is a row,
. every type of observational unit is a table.

Messy tables usually break one of these rules: column headers that are values (one column per year), several variables
in one column (`"M_25-34"` holding sex and age group), or variables stored in both rows and columns. The reshaping
functions `melt`, `pivot` and `stack` convert between layouts; this page only needs the idea.

[source,python]
----
import pandas as pd

wide = pd.DataFrame({
    "city": ["Madrid", "Lima"],
    "2025": [3.4, 10.2],
    "2026": [3.6, 10.9],
})
tidy = wide.melt(id_vars="city", var_name="year", value_name="population_m")
tidy["year"] = tidy["year"].astype("int16")
print(tidy)
print(tidy.pivot(index="city", columns="year", values="population_m"))
----

Output on pandas 3.1:

[source,text]
----
     city  year  population_m
0  Madrid  2025           3.4
1    Lima  2025          10.2
2  Madrid  2026           3.6
3    Lima  2026          10.9
year    2025  2026
city              
Lima    10.2  10.9
Madrid   3.4   3.6

Source: https://pandas.pydata.org/docs/user_guide/reshaping.html[pandas user guide, Reshaping and pivot tables]; Wickham,
https://vita.had.co.nz/papers/tidy-data.pdf[Tidy Data]; https://r4ds.hadley.nz/data-tidy.html[R for Data Science, Data tidying].

The wide layout is not wrong. It is convenient for presentation and for some matrix operations. The point is to choose it
deliberately instead of inheriting it, and to keep one tidy version as the source for plotting and modelling.

== Missing values

A missing value is an observation that should exist but was not recorded. How to treat it depends first on **why** it is
missing, and only then on which pandas function to call.

=== How pandas represents missing data

[cols="2,3,3",options="header"]
|===
| Marker | Where it appears | Notes
| `np.nan` (`NaN`) | float columns, the `str` dtype, `object` columns | A floating-point value. `NaN != NaN`, so use `isna()` and never `== np.nan`.
| `NaT` | datetime and timedelta columns | The datetime equivalent.
| `pd.NA` | nullable dtypes: `Int64`, `Float64`, `boolean`, `string` | A single missing value that works in any nullable dtype and keeps integers as integers.
|===

Giving an integer column a missing value used to force it to `float64`. The nullable integer dtype `Int64` keeps the
integers and uses `pd.NA`. With `skipna=True` (the default) pandas reductions ignore missing values, while the NumPy
function `np.mean` does not:

[source,python]
----
import io
import numpy as np
import pandas as pd

s = pd.Series([1, None, 3], dtype="Int64")
print(s)
print(s.isna().tolist())

v = pd.Series([1.0, np.nan, 3.0])
print(v.mean(), v.mean(skipna=False))
----

[source,text]
----
0       1
1    <NA>
2       3
dtype: Int64
[False, True, False]
2.0 nan
----

Source: https://pandas.pydata.org/docs/user_guide/missing_data.html[pandas user guide, Working with missing data].

=== Sentinels hide missing data

The most damaging missing values are the ones that do not look missing: `-999`, `9999`, `0` for "unknown", `"unknown"`,
`"."`, `"?"`, a placeholder date such as `1900-01-01`. A mean computed over a column containing `-999` is wrong without any
warning. Find them in the summaries (a minimum far below the rest, an impossible spike in `value_counts`) and tell the
parser about them when reading:

[source,python]
----
import io
import pandas as pd

csv = "id,score,city\n1,7.5,Madrid\n2,-999,NA\n3,,Lima\n4,n/a,\n"
default = pd.read_csv(io.StringIO(csv))
print(default)

explicit = pd.read_csv(io.StringIO(csv), na_values={"score": ["-999"]})
print(explicit)
----

Source: https://pandas.pydata.org/docs/reference/api/pandas.read_csv.html[pandas.read_csv, na_values and keep_default_na].

`read_csv` already treats a built-in list of strings (the empty string, `NA`, `N/A`, `n/a`, `NaN`, `null`, `None` and a few
more) as missing. Two behaviours trap people. First, a legitimate value such as the country code `NA` (Namibia) or the
surname `Null` is silently turned into a missing value. Set `keep_default_na=False` and list the markers yourself when
that matters. Second, `na_values` accepts a per-column dictionary, so a sentinel that is meaningful in one column is not
removed from another.

=== Why a value is missing

Rubin's classification (1976) is the standard vocabulary and it determines which fixes are defensible.

[cols="1,3,3",options="header"]
|===
| Mechanism | Meaning | Consequence
| MCAR, missing completely at random | The chance of being missing does not depend on any variable, observed or not. A lab sample was dropped. | Dropping rows loses information but does not bias results.
| MAR, missing at random | The chance of being missing depends on *observed* variables. Younger respondents skip the income question more often, and age is recorded. | Dropping rows can bias results; modelling the missingness from the observed variables can correct it.
| MNAR, missing not at random | The chance of being missing depends on the missing value itself. High earners decline to state their income. | No purely statistical fix from the data alone. It needs domain knowledge, a sensitivity analysis or a better data source.
|===

Check for a pattern before choosing a strategy: compare the other variables for rows with and without the missing value
(`df.groupby(df["income"].isna()).mean(numeric_only=True)`), and look at whether missingness clusters in time, in one
source system or in one customer segment. Missingness that follows the data collection process is information, so keep
an indicator column for it.

=== Drop, fill or model

[cols="2,3,3",options="header"]
|===
| Strategy | When it is reasonable | Cost
| `dropna()` rows | Few rows affected and MCAR plausible; the target itself is missing. | Loses data; biases results under MAR or MNAR.
| `dropna(axis=1)` columns | A column that is mostly empty and not important. | Loses a feature that may matter when it is present.
| Constant fill | A missing value has a real meaning, such as "no previous order" meaning 0 orders. | The constant must be justified; an arbitrary 0 distorts statistics.
| Mean, median or mode | Quick baseline for numeric or categorical features. | Shrinks the variance and weakens correlations; use the median for skewed data.
| Forward or backward fill, interpolation | Ordered data (time series, sensor readings) where neighbours are informative. | Invents values; bound the gap with `limit=`.
| Model-based imputation | Missingness depends on other features. | More complex; must be fitted inside the training fold. See xref:data-science/scikit-learn/imputation.adoc[Imputing Missing Values].
|===

[source,python]
----
import numpy as np
import pandas as pd

df = pd.DataFrame({"t": pd.date_range("2026-01-01", periods=6, freq="D"),
                   "v": [1.0, np.nan, np.nan, 4.0, np.nan, 6.0]})
print(df.assign(ffill=df["v"].ffill(limit=1),
                linear=df["v"].interpolate(),
                med=df["v"].fillna(df["v"].median())))
print(df.dropna(subset=["v"]).shape)
----

`ffill(limit=1)` filled only one row of a two-row gap, which is the point of `limit`: do not carry a stale reading across
a long outage. `dropna` also has `how="all"` (drop a row only when every value is missing), `thresh=n` (keep rows with
at least `n` non-missing values) and `subset` (a list of the columns to look at).

Two further rules prevent common errors.

* **Do not impute the target.** Rows with an unknown label cannot teach a supervised model anything; drop them or set
  them aside.
* **Keep an indicator.** `df["income_missing"] = df["income"].isna()` before filling lets a model, or a reviewer, see
  where the data was invented.

== Duplicates

Duplicates come from repeated exports, joins that multiply rows, retries in a data pipeline and manual entry. Decide what
"the same record" means before removing anything: a whole identical row, or the same key with different attributes.

[source,python]
----
print(df.duplicated().sum())                              # fully identical rows
print(df.duplicated(subset="order_id", keep=False).sum()) # every row that shares a key
df = df.drop_duplicates(subset="order_id", keep="first")
----

`duplicated()` marks the second and later occurrences (`keep="first"`, the default); `keep=False` marks all of them, which
is what you want when inspecting conflicts. On the sample orders the first line prints `1` and the second prints `2`.
When the duplicates differ in some columns, `drop_duplicates` keeps whichever comes first, so sort first by the rule that
defines the winner (for example the most recent `updated_at`) and then drop. A key that should be unique can be asserted
afterwards with `df["order_id"].is_unique`. Source:
https://pandas.pydata.org/docs/reference/api/pandas.DataFrame.duplicated.html[DataFrame.duplicated] and
https://pandas.pydata.org/docs/user_guide/duplicates.html[Duplicate Labels].

Near-duplicates (`"Ana López"` and `"Ana Lopez"`) need normalisation first (next sections), and genuinely fuzzy matching
(record linkage) is a separate problem that dedicated libraries address.

== Types and conversion

A column with the wrong dtype hides errors and wastes memory. Convert explicitly, and decide what a failed conversion
means.

[source,python]
----
df["customer"] = df["customer"].str.strip().str.title()
df["country"] = df["country"].str.upper()
df["status"] = df["status"].str.lower().astype("category")
df["amount"] = pd.to_numeric(
    df["amount"].astype("string").str.replace(",", "", regex=False), errors="coerce")
df["ordered_at"] = pd.to_datetime(df["ordered_at"], errors="coerce", format="%Y-%m-%d")
print(df)
print(df.dtypes)
print(df[df["ordered_at"].isna()])
----

Points worth knowing:

* `errors="coerce"` turns anything unparsable into `NaN` or `NaT`. That is convenient and dangerous: it converts data
  errors into missing values without a trace. Count the failures (`df["ordered_at"].isna().sum()` before and after) and
  inspect the rows that failed, as the last line above does. The old `errors="ignore"` option was removed in pandas 3.0.
* Always pass `format=` to `to_datetime` for known layouts. Without it pandas infers a format from the first value and a
  string such as `03/04/2026` is ambiguous between 3 April and 4 March. `dayfirst=True` resolves it for a whole column,
  but only an explicit format makes the intent reviewable.
* Datetimes parse to microsecond resolution (`datetime64[us]`) in pandas 3. Code written for the old nanosecond default,
  for example converting a datetime column to integers and expecting nanoseconds, now gives values 1000 times smaller.
* Low-cardinality text (status, country, plan) is better as a `category`: it saves memory, orders levels explicitly and
  makes a typo visible as an unexpected level. Check `df["status"].cat.categories` after conversion.
* Identifiers that look like numbers (postcodes, phone numbers, product codes with leading zeros) are labels, not
  quantities. Read them as strings (`+dtype={"zip": "string"}+`) or the leading zero is lost.
* Choose the narrowest sufficient type only after cleaning (`int16`, `float32`, `category`); doing it earlier turns the
  cleaning step into an overflow hunt.

== Text, units and encodings

String columns accumulate variants: leading and trailing spaces, mixed case, non-breaking spaces, different Unicode
normal forms, smart quotes, and values with the unit embedded (`"12 kg"`, `"3,5 m"`). Normalise with the `.str` accessor,
in this order: strip whitespace, fold case, replace known variants, then validate against the allowed set.

[source,python]
----
s = pd.Series(["  Madrid", "madrid ", "MADRID", "Madr1d", None], dtype="string")
clean = s.str.strip().str.casefold()
allowed = {"madrid", "lima"}
print(clean.isin(allowed).tolist())
print(clean[~clean.isin(allowed) & clean.notna()].tolist())
----

This prints `[True, True, True, False, False]` and then `+['madr1d']+`: the typo survived the clean-up and is now visible as
a value outside the allowed set. The `.str` methods propagate missing values instead of failing on them. Regular
expressions in `str.replace` are off by default (`regex=False`), so a pattern must opt in with `regex=True`.

Other rules for text and numbers:

* **Units.** Store one unit per column and put it in the column name (`weight_kg`, `duration_s`). Convert at the
  boundary, in one place, and never mix feet and metres in a column. A failed unit conversion is a classic source of
  outliers.
* **Currency and decimals.** `"1.250,50"` (European) and `"1,250.50"` (US) parse differently. Declare `thousands=` and
  `decimal=` in `read_csv` rather than stripping characters by hand.
* **Encodings.** If text contains mojibake such as `"JosÃ©"`, the file was decoded with the wrong encoding. Re-read it
  with `encoding="utf-8"` or the real one (`"latin-1"`, `"cp1252"`), instead of repairing characters afterwards.
* **Unicode.** Normalise with `unicodedata.normalize("NFC", text)` before comparing, so that a composed and a decomposed
  accent compare equal.

== Dates and time zones

Time data fails in predictable ways: mixed formats in one column, two-digit years, local timestamps with no zone, and
daylight-saving transitions. Three habits prevent most of them.

. **Store instants in UTC and convert for display.** A timezone-aware column keeps its zone in the dtype
  (`datetime64[us, Europe/Madrid]`).
. **Localise naive timestamps explicitly** with `tz_localize` (attach a zone) and move between zones with `tz_convert`.
  Never subtract a naive timestamp from an aware one.
. **Decide what to do with the two awkward hours** of each daylight-saving change: one local time that does not exist (spring
  forward) and one that happens twice (fall back).

[source,python]
----
import pandas as pd

naive = pd.Series(pd.to_datetime(["2026-03-29 01:30", "2026-03-29 02:30", "2026-10-25 02:30"]))
try:
    naive.dt.tz_localize("Europe/Madrid")
except ValueError as e:
    print(type(e).__name__)
loc = naive.dt.tz_localize("Europe/Madrid", nonexistent="shift_forward", ambiguous="NaT")
print(loc)
print(loc.dt.tz_convert("UTC"))
----

https://pandas.pydata.org/docs/user_guide/timeseries.html[pandas time series guide] and the

Madrid skipped from 02:00 to 03:00 on 29 March 2026, so `02:30` does not exist; and on 25 October 2026 the clock repeated
the hour from 02:00 to 03:00, so `02:30` is ambiguous. The default is to raise, which is the safe choice. `shift_forward`
moves the nonexistent time to the next valid instant, and `ambiguous="NaT"` marks the repeated hour as missing; when the
data is ordered you can use `ambiguous="infer"`, and otherwise supply a boolean array that says which occurrence each row
is. Time zone data comes from the IANA database through `zoneinfo`; pandas 3 no longer installs `pytz`, so code that
imports it needs a replacement. Period and offset aliases changed too (`M` became `ME`, `H` became `h`), as covered in
xref:data-science/pandas/time-series.adoc[Time Series & Dates].

== Outliers

An outlier is a value far from the bulk of the data. It is not automatically an error. It may be a data-entry mistake, a
unit mix-up, a sensor fault, or the single most interesting observation in the dataset (a fraud, a failure, a rare
disease). Detection is mechanical; the decision is not.

[#fig-iqr]
.The IQR rule draws fences 1.5 interquartile ranges beyond the quartiles; points beyond a fence are flagged for review.
image::data-science-cleaning-iqr-fences.svg["Box plot with the quartile box, whiskers, dashed fences and four flagged points",width=720]

Three common rules, from simplest to most robust:

[cols="2,3,3",options="header"]
|===
| Rule | Definition | Behaviour
| Z-score | `+abs(x - mean) / sd > 3+` is flagged | Quick, but the outlier inflates the mean and standard deviation that are used to detect it (masking). Assumes a roughly normal distribution.
| Tukey IQR fences | Below `Q1 - 1.5 IQR` or above `pass:c[Q3 + 1.5 IQR]` | Uses quartiles, so it is robust to the outliers themselves. The multiplier 1.5 is a convention, and 3 is used for "far out" points.
| Robust (MAD) z-score | `+0.6745 * (x - median) / MAD > 3.5+` is flagged | Uses the median and the median absolute deviation. Preferred for small or skewed samples.
|===

[source,python]
----
import numpy as np
import pandas as pd

rng = np.random.default_rng(42)
x = pd.Series(np.r_[rng.normal(50, 5, 200), [95, 120, -10]], name="x")

q1, q3 = x.quantile([0.25, 0.75])
iqr = q3 - q1
low, high = q1 - 1.5 * iqr, q3 + 1.5 * iqr
print(round(low, 2), round(high, 2), x[(x < low) | (x > high)].round(1).tolist())

med = x.median()
mad = (x - med).abs().median()
robust_z = 0.6745 * (x - med) / mad
print("robust z flags:", int((robust_z.abs() > 3.5).sum()))

z = (x - x.mean()) / x.std()
print("plain z flags:", int((z.abs() > 3).sum()))

clipped = x.clip(lower=low, upper=high)
print(round(x.mean(), 2), round(clipped.mean(), 2), round(x.std(), 2), round(clipped.std(), 2))
----

https://docs.scipy.org/doc/scipy/reference/generated/scipy.stats.median_abs_deviation.html[scipy.stats.median_abs_deviation]
and the NIST/SEMATECH https://www.itl.nist.gov/div898/handbook/prc/section1/prc16.htm[detection of outliers].

The IQR rule flagged four points, including `64.6`, an ordinary draw from the normal part of the sample that lies just
past the upper fence: with 200 normal values a few fall outside the fences by chance, which is why a flag is a prompt to
look, never proof. Both z-score variants flagged three points. Clipping at the fences (winsorising) cut
the standard deviation from 8.44 to 4.59 while the mean barely moved.

What to do with a flagged point, in order of preference:

. **Investigate.** Trace it to the source. A height of 1.8 recorded as 180 is an error; a 10 million transaction in a
  payments table may be real.
. **Correct** it if the right value is known (unit fix, typo), and record the correction.
. **Keep** it and use robust methods (median, rank-based tests, Huber or quantile regression) when it is real.
. **Cap** it (winsorise) or **transform** the variable (logarithm) when extreme values are real but dominate a statistic.
. **Remove** it only with a documented reason, and report results with and without it.

Univariate rules miss points that are only unusual in combination, such as a 2-metre child. For multivariate outliers see
xref:data-science/scikit-learn/outlier-detection.adoc[Outlier & Novelty Detection], and for formal single-outlier tests the
NIST handbook's https://www.itl.nist.gov/div898/handbook/eda/section3/eda35h.htm[Grubbs' test], which assumes normality.

== Validation

After cleaning, turn expectations into checks that fail loudly. A short block of explicit assertions at the end of a
cleaning script catches regressions when the source data changes.

[source,python]
----
import pandas as pd

df = pd.DataFrame({"id": [1, 2, 2], "age": [34, 210, 41], "email": ["a@x.org", "bad", None]})
checks = {
    "id is unique": df["id"].is_unique,
    "age in 0..120": df["age"].between(0, 120).all(),
    "email looks valid": df["email"].str.contains(r"^[^@\s]+@[^@\s]+\.\w+$", na=False).all(),
}
for name, ok in checks.items():
    print(f"{'PASS' if ok else 'FAIL'}  {name}")

df.loc[~df["age"].between(0, 120), "age"] = pd.NA
print(df["age"].dtype, df["age"].tolist())
----

[source,text]
----
FAIL  id is unique
FAIL  age in 0..120
FAIL  email looks valid
float64 [34.0, nan, 41.0]
----

Source: https://pandas.pydata.org/docs/user_guide/missing_data.html[pandas user guide, Working with missing data].

Useful checks: unique keys, allowed value sets, numeric ranges, no missing values in required columns, row counts that
match the source, referential integrity between tables (every `customer_id` in orders exists in customers), and date
logic (`shipped_at >= ordered_at`). In a script, raise on failure (`assert`, or `raise ValueError`) so a pipeline
stops instead of passing bad data downstream. Validation libraries such as Pandera and Great Expectations express the
same checks declaratively and produce reports; they are third-party packages with their own documentation and are not
needed for the concepts on this page. For data that arrives continuously, see the data-quality discussion in
xref:ai/llmops/data-operations.adoc[LLMOps data operations].

== Pitfalls that corrupt data silently

[cols="2,3,3",options="header"]
|===
| Pitfall | What happens in pandas 3.1 | Do this instead
| Chained assignment: `df["a"][mask] = 1` | Never modifies `df`. Copy-on-Write is the only mode, and pandas emits a `ChainedAssignmentError` warning. | `df.loc[mask, "a"] = 1`
| `fillna(method="ffill")` | Removed in 3.0; raises `TypeError`. | `ser.ffill()` or `ser.bfill()`
| `inplace=True` | Deprecated in 3.1 on `drop`, `rename`, `reset_index`, `set_index`, `dropna`, `drop_duplicates`, `sort_values`, `sort_index`, `eval` and `query`; emits a `Pandas4Warning`. It was never faster. | Reassign: `df = df.drop(columns="b")`
| `pd.value_counts(s)` | Removed in 3.0. | `s.value_counts()`
| `applymap` | Removed in 3.0. | `DataFrame.map`
| Growing a frame with `append` in a loop | `DataFrame.append` was removed in 2.0. | Collect rows in a list and call `pd.concat` once.
| `errors="coerce"` without counting | Data errors become missing values without a trace. | Count and inspect the failures.
| Float into an integer column | Upcasting on assignment is rejected (PDEP-6). | Convert the column first, or use a nullable dtype.
| `ser.dtype == object` to find text | False in pandas 3 because text is `str`. | `pd.api.types.is_string_dtype(ser)`
|===

== Where older tutorials and books are outdated

Material written before 2023 (many popular books and blog posts) shows patterns that no longer work or that behave
differently. The table lists the ones that matter for cleaning, with the version in which each changed.

[cols="3,2,3",options="header"]
|===
| Older pattern | Changed | Current practice
| `df.fillna(method="ffill")` | Deprecated in 2.1, removed in 3.0 | `df.ffill()`
| `df.append(row)` | Removed in 2.0 | `pd.concat`
| `df.ix`, `get_value`, `set_value` | Removed in 1.0 | `loc`, `iloc`, `at`, `iat`
| The `errors="ignore"` option of `pd.to_numeric` and `to_datetime` | Removed in 3.0 | `errors="coerce"` plus an explicit check
| `df.applymap(f)` | Removed in 3.0 | `df.map(f)`
| `pytz` time zones | Replaced by `zoneinfo` in 3.0 | `"Europe/Madrid"` strings or `zoneinfo.ZoneInfo`
| `ser.dtype == object` for text | Text defaults to `str` in 3.0 | `pd.api.types.is_string_dtype`
| `inplace=True` everywhere | Deprecated in 3.1 | Reassign the result
| `sklearn.preprocessing.Imputer` | Replaced by `sklearn.impute.SimpleImputer` in 0.20 | See xref:data-science/scikit-learn/imputation.adoc[Imputing Missing Values]
| Frequency alias `"H"` or `"M"` | Removed in 3.0 | `"h"`, `"ME"`
|===

== Checklist

. Raw data is read-only; the cleaning is a script that can be re-run.
. Types are explicit: numbers, dates and categories are parsed, identifiers are text.
. Sentinels are mapped to missing at read time, with `na_values`, per column.
. Duplicates are defined by a key and removed with a deterministic rule.
. Text is stripped, case-folded and checked against allowed values; each column has one unit.
. Timestamps carry a time zone, stored as UTC, and daylight-saving edge cases are handled on purpose.
. Missingness is understood (MCAR, MAR or MNAR) before it is filled, and an indicator column is kept.
. Outliers are investigated, and any change is documented and reversible.
. Anything fitted on the data (imputation values, scalers) is fitted on training data only.
. Explicit checks fail the pipeline when an expectation breaks.
