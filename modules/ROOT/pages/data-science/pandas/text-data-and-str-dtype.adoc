= Text Data & the str Dtype in pandas
:description: Working with strings in pandas 3.1: the default str dtype versus string, ArrowDtype and object, NaN versus pd.NA, the .str accessor (split, extract, replace, contains, cat and more), migration from pandas 2, memory and speed, with real output.
:keywords: pandas, str dtype, string dtype, StringDtype, object dtype, PyArrow, .str accessor, str.contains, str.replace, str.extract, str.split, regex, missing values, future.infer_string, select_dtypes, pandas 3.1

include::partial$data-science-pandas-disclaimer.adoc[]

Since pandas 3.0 text columns are stored in a dedicated `str` dtype instead of Python objects. This page explains what
that dtype is, how it differs from the older `object` columns and from the opt-in `"string"` dtype, how to move code
from pandas 2, and how to use the `.str` accessor to clean and extract text. It targets pandas 3.1 on Python 3.13 or
3.14 and was checked in October 2026. Every example was run with Python 3.13, NumPy 2.5.4, pandas 3.1.0 and PyArrow
26.0.0, and the printed output is the real output. Other string-related pandas topics have their own pages:
xref:data-science/pandas/missing-data.adoc[Missing Data], xref:data-science/pandas/categorical-data.adoc[Categorical Data],
xref:data-science/pandas/nullable-dtypes.adoc[Nullable Integer & Boolean] and
xref:data-science/pandas/pyarrow-backed-data.adoc[PyArrow-Backed Data]. The NumPy view of text is in
xref:data-science/numpy/strings-and-stringdtype.adoc[Strings, Bytes & StringDType], and the Python language itself in
xref:programming-languages/python/strings-and-text.adoc[Strings and Text].

All examples assume the standard imports:

[source,python]
----
import numpy as np
import pandas as pd
----

== The default str dtype

A `Series` built from Python strings now has the dtype `str`:

[source,python]
----
s = pd.Series(["apple", None, "cherry"])
print(s)
print(s.dtype, repr(s.dtype))
print(s.dtype.na_value, s.dtype.storage)
print(pd.api.types.is_string_dtype(s), s.dtype == object, s.dtype == "str")
----

[source,text]
----
0     apple
1       NaN
2    cherry
dtype: str
str <StringDtype(na_value=nan)>
nan pyarrow
True False True
----

Source: https://pandas.pydata.org/docs/user_guide/migration.html#string-migration[pandas user guide: Migration guide for the new string data type (pandas 3.0)].

`str` is an instance of `pd.StringDtype(na_value=np.nan)`, spelled `"str"` as an alias. It is a pandas extension dtype,
not a NumPy dtype, so it cannot be passed to NumPy functions or to `np.issubdtype`. Its missing value is `np.nan`; the
same is true of the `None` in the list above, which pandas converted. Because the dtype is not `object`, the old test
`ser.dtype == object` is now `False`: use `pd.api.types.is_string_dtype` or compare with `"str"`.

=== Storage

When PyArrow is installed the values are stored in Arrow memory. Without PyArrow, pandas falls back to Python objects
internally but keeps the same semantics, so code behaves the same either way; only memory and speed differ. PyArrow
remains an optional dependency of pandas 3.1. The storage is visible on the dtype:

[source,python]
----
print(pd.StringDtype("python", na_value=np.nan))        # str
print(pd.StringDtype("pyarrow"))                          # string
print(pd.StringDtype("pyarrow", na_value=np.nan))         # str
print(pd.Series(["a", None], dtype=pd.StringDtype("python", na_value=np.nan)).array.__class__.__name__)
----

[source,text]
----
str
string
str
StringArray
----

Source: https://pandas.pydata.org/docs/reference/api/pandas.StringDtype.html[pandas.StringDtype].

The `str` dtype only holds valid Unicode text. A lone surrogate such as `"\ud83d"` raises `UnicodeEncodeError` when it is
stored; keep such data in an `object` column.

=== Memory and speed

The Arrow-backed storage is considerably smaller and faster than Python objects. One million values drawn from five
words, on the machine used for this page:

[source,python]
----
import time
rng = np.random.default_rng(0)
words = np.array(["alpha", "beta", "gamma", "delta", "epsilon"])
raw = words[rng.integers(0, 5, 1_000_000)].tolist()

for label, dt in [("object", object), ("str", "str"),
                  ("string[python]", pd.StringDtype("python")), ("string[pyarrow]", pd.StringDtype("pyarrow"))]:
    s = pd.Series(raw, dtype=dt)
    t = time.perf_counter(); s.str.upper(); elapsed = time.perf_counter() - t
    print(f"{label:16} {s.memory_usage(deep=True) / 1e6:7.1f} MB  upper: {elapsed * 1000:6.1f} ms")
----

[source,text]
----
object              54.2 MB  upper:   47.6 ms
str                 13.2 MB  upper:    8.9 ms
string[python]      54.2 MB  upper:   45.4 ms
string[pyarrow]     13.2 MB  upper:    8.9 ms
----

The absolute timings depend on the machine; the ratio (about 4 times less memory and 5 times faster here) is what matters.
Without PyArrow the `str` dtype has the memory profile of `object`.

Source: https://pandas.pydata.org/docs/user_guide/migration.html#string-migration[pandas user guide: Migration guide for the new string data type (pandas 3.0)].

The important consequence is that the missing-value *sentinel* differs. With `str`, operations on missing values return
`NaN` or `False`, exactly like numeric NumPy-backed columns, so code written for pandas 2 object columns keeps working.
With `"string"`, comparisons and string methods propagate `pd.NA` and return nullable result dtypes, which is more
consistent but changes downstream types:

[source,python]
----
a = pd.Series(["x", None], dtype="str")
b = pd.Series(["x", None], dtype="string")
print((a == "x").tolist(), (b == "x").tolist())
print(a.str.len().dtype, b.str.len().dtype, a.str.contains("x").dtype, b.str.contains("x").dtype)
----

[source,text]
----
[True, False] [True, <NA>]
float64 Int64 bool boolean
----

Source: https://pandas.pydata.org/docs/reference/api/pandas.Series.str.len.html[pandas.Series.str.len].

Use `pd.isna` (or `Series.isna()`) to test for missing text rather than comparing with `None` or `np.nan`. The nullable
`"string"` dtype and `ArrowDtype` keep working unchanged in pandas 3; the pandas 3 migration guide describes the new `str`
dtype as the default and the other two as the explicit, `pd.NA`-based choices.

=== Differences from object

* `ser.values` returns an extension array; use `ser.to_numpy()` to get a NumPy array (of `object` dtype for `str`).
* Assigning a non-string raises `TypeError` instead of upcasting; cast to `object` first if you need mixed content.
* `astype(str)` keeps missing values as missing instead of turning `NaN` into the text `"nan"`.
* Reductions that make no sense for text, such as `prod()`, consistently raise `TypeError`.
* `dtype=object` given explicitly is respected: such columns stay `object`.

[source,python]
----
t = pd.Series(["a", "b"], dtype="str")
try:
    t.iloc[0] = 5
except TypeError as err:
    print("TypeError:", err)

print(pd.Series(["a", 1, 2.0]).dtype)                      # mixed data stays object
print(pd.Series([1.5, None]).astype("str").tolist())       # missing stays missing
print(pd.Series([1, 2]).astype("str").dtype)
print(pd.Series(["a", None]).to_numpy())
----

[source,text]
----
TypeError: Invalid value '5' for dtype 'str'. Value should be a string or missing value, got 'int' instead.
object
['1.5', nan]
str
['a' nan]
----

Source: https://pandas.pydata.org/docs/reference/api/pandas.DataFrame.astype.html[pandas.DataFrame.astype].

=== Where str is inferred

pandas infers `str` when it builds a column of strings (constructors, `read_csv`, `read_parquet`, `read_json` and so on),
and a column of only `None` or only `NaN` stays `object` or `float64` because nothing says that it holds text. Index
labels follow the same rule:

[source,python]
----
print(pd.Index(["a", "b"]).dtype)
df = pd.DataFrame({"n": [1], "t": ["a"]})
print(df.dtypes)
print(pd.Series([np.nan, "a"]).dtype, pd.Series([None, None]).dtype)
----

[source,text]
----
str
n    int64
t      str
dtype: object
str object
----

Source: https://pandas.pydata.org/docs/reference/api/pandas.StringDtype.html[pandas.StringDtype].

The columns `Index` of a DataFrame built from string labels is `str` too, as the pivot output on
xref:data-science/pandas/pivot-and-pivot-tables.adoc[Pivot & Pivot Tables] shows.

== Migrating code from pandas 2

The migration guide recommends testing on pandas 2.3 with `pd.options.future.infer_string = True` first. In pandas 3.1
that option still exists but is deprecated and will be removed in pandas 4.0: inferring `str` is the default and can no
longer be turned off. The steps are:

. Replace `dtype == "object"` checks with `pd.api.types.is_string_dtype(ser.dtype)` or `ser.dtype == "str"`.
. Test missing values with `pd.isna` or `Series.isna()`, not with `is None` or `== np.nan`.
. Replace `.values` with `.to_numpy()`.
. Where you assign non-strings into a text column, call `astype(object)` first.
. Review `astype(str)`: use `ser.map(str)` if you need every element stringified, including missing values.
. Keep `dtype=object` where you need arbitrary Python objects or invalid Unicode.
. Select string columns explicitly.

Column selection deserves care. `select_dtypes(include="object")` still returns `str` columns in pandas 3.1 for backward
compatibility, but it emits a deprecation warning (a `Pandas4Warning` in pandas 3.1) because that behaviour will be
removed. The form that works on pandas 2 and 3 is:

[source,python]
----
df = pd.DataFrame({"n": [1], "t": ["a"], "o": pd.Series([object()], dtype=object)})
print(df.select_dtypes(include=["object", "string"]).columns.tolist())
print(df.select_dtypes(include="str").columns.tolist())
----

[source,text]
----
['t', 'o']
['t']
----

Code that targets only pandas 3 should write `include="str"` for text and `include=object` for arbitrary objects.
scikit-learn selectors such as `make_column_selector(dtype_include=object)` are discussed in
xref:data-science/scikit-learn/column-transformer.adoc[ColumnTransformer & Heterogeneous Data]; select text columns by
name or with `dtype_include="str"` on pandas 3.

Source: https://pandas.pydata.org/docs/user_guide/migration.html[pandas user guide: Migration guide for pandas 3.0] and https://pandas.pydata.org/docs/user_guide/text.html[Working with text data].

== The .str accessor

String methods live under `Series.str` and `Index.str`. They are vectorised, skip missing values and mirror the methods
of Python's `str` type, with a few regular-expression extras. The accessor works on `str`, `string`, ArrowDtype strings,
and on `object` columns that hold only strings (and missing values); on other data it raises `AttributeError`:

[source,python]
----
try:
    pd.Series([1, 2]).str.len()
except AttributeError as err:
    print("AttributeError:", err)
----

[source,text]
----
AttributeError: Can only use .str accessor with string values, not integer
----

Source: https://pandas.pydata.org/docs/user_guide/text.html[pandas user guide: Working with text data] and https://pandas.pydata.org/docs/reference/series.html#api-series-str[Series.str reference].

The examples below use this sample:

[source,python]
----
s = pd.Series([" Alice Smith ", "bob.jones@example.org", None, "CAROL  O'Neil", "dave 42"])
----

=== Cleaning and case

[source,python]
----
print(s.str.strip().str.lower().tolist())
print(s.str.len().tolist())
print(pd.Series(["ß", "É"]).str.casefold().tolist())
print(pd.Series(["7", "42", "x"]).str.zfill(4).tolist())
print(pd.Series(["7"]).str.pad(4, side="left", fillchar="*").tolist())
----

representation:

[source,python]

[source,python]

=== Testing: contains, match, startswith

`contains` searches with a regular expression by default; `match` anchors at the start and `fullmatch` at both ends.
`na=` decides what a missing value yields:

[source,python]
----
import re
print(s.str.contains("o", case=False).tolist())
print(s.str.contains("o", na=False).tolist())
print(s.str.startswith("b").tolist(), s.str.endswith("org").tolist())
print(pd.Series(["ab12", "12"]).str.match(r"[a-z]+").tolist(), pd.Series(["ab12", "12"]).str.fullmatch(r"\d+").tolist())
print(pd.Series(["Foo", "foo"]).str.contains("foo", flags=re.IGNORECASE).tolist())
----

[source,text]
----
[False, True, False, True, False]
[False, True, False, False, False]
[False, True, False, False, False] [False, True, False, False, False]
[True, False] [False, True]
[True, True]
----

Source: https://pandas.pydata.org/docs/reference/api/pandas.Series.str.contains.html[pandas.Series.str.contains].

For `str` columns a missing value gives `False` in `contains`; for `"string"` columns it gives `pd.NA`, which cannot be
used directly as a boolean mask. Pass `na=False` (or fill) when you build a filter.

=== Replace

`str.replace` treats the pattern as *literal text* by default (`regex=False`). Older tutorials show regex behaviour by
default, which was the default before pandas 2.0:

[source,python]
----
print(pd.Series(["a.b"]).str.replace(".", "-").tolist())
print(pd.Series(["a.b"]).str.replace(".", "-", regex=True).tolist())
print(s.str.replace(r"\s+", " ", regex=True).tolist())
print(s.str.replace(r"(\w+)@(\w+)", r"\2 at \1", regex=True).tolist())
print(pd.Series(["a1b22"]).str.replace(r"\d+", lambda m: str(int(m.group()) * 2), regex=True).tolist())
----

[source,text]
----

[' Alice Smith ', 'bob.jones@example.org', nan, "CAROL O'Neil", 'dave 42']

Source: https://pandas.pydata.org/docs/reference/api/pandas.Series.str.replace.html[pandas.Series.str.replace].

=== Splitting and joining

`split` returns lists, or with `expand=True` several columns. `partition` always returns three columns (the part before,
the separator and the part after). `cat` concatenates the elements of a Series with a separator, and `get_dummies` turns
delimited tags into indicator columns:

[source,python]
----
print(s.str.split(r"\s+", regex=True, n=1, expand=True))
print(s.str.partition("@"))
print(s.str.cat(sep="|", na_rep="?"))
print(s.str.cat(["1", "2", "3", "4", "5"], sep="-", na_rep="?").tolist())
print(pd.Series(["a|b", "b|c", None, "a"]).str.get_dummies())
----

=== Extracting with regular expressions

`extract` captures the groups of the first match into columns (named groups name the columns). `extractall` returns one
row per match with a `match` level in a `MultiIndex`, and `findall` returns the list of matches:

[source,python]
----
print(s.str.extract(r"(?P<user>[\w.]+)@(?P<domain>[\w.]+)"))
print(s.str.extract(r"(\d+)", expand=False).tolist())
print(s.str.extractall(r"([aeiou])").head(4))
print(s.str.findall(r"[A-Z]").tolist())
print(s.str.count(r"[aeiou]").tolist())
----

=== Behaviour on object and categorical columns

On an `object` column the same methods work and return the same values, with `None` handling that mirrors the older
behaviour:

[source,python]
----
o = pd.Series(["a", None], dtype=object)
print(o.str.upper().tolist(), o.str.len().tolist(), o.str.contains("a").tolist())
c = pd.Series(["a", "b", "a"], dtype="category")
print(c.str.upper().dtype, c.cat.categories.dtype)
----

[source,text]
----
['A', None] [1.0, nan] [True, None]
object str
----

Note the `None` in the object result of `contains`, a reason to convert text columns to `str` early. A categorical column
keeps its categories as `str`, while the result of a `.str` method on it is a plain `object` Series in pandas 3.1; see xref:data-science/pandas/categorical-data.adoc[Categorical Data] for when categoricals pay off with text.

== Other places where text matters

* *Reading files:* `read_csv`, `read_json`, `read_parquet` and the other readers infer `str` for text columns. Pass
  `+dtype={"col": "category"}+` or `dtype_backend="pyarrow"` to choose otherwise; see
  xref:data-science/pandas/io-csv-and-text.adoc[CSV & Text Files].
* *Missing text:* `fillna("")` keeps the `str` dtype, and `isna()` finds missing values; see
  xref:data-science/pandas/missing-data.adoc[Missing Data].
* *Sorting and counting:* `sort_values`, `value_counts` and `unique` work on `str` columns and keep missing values as `NaN`
  (`dropna=False` lists them).
* *Machine learning:* turn text into numbers with scikit-learn's vectorisers; see
  xref:data-science/feature-engineering.adoc[Feature Engineering].
* *Cleaning workflow:* for the wider strategy of fixing inconsistent labels, see
  xref:data-science/data-cleaning.adoc[Data Cleaning & Preparation]. The R counterpart is
  xref:programming-languages/r/tidyr-purrr-and-stringr.adoc[stringr, tidyr and purrr]; for SQL see
  xref:database/sql/functions.adoc[SQL functions].

== Pitfalls

* Mixed types stay `object`, and `.str` on them gives `NaN` for the non-strings. Convert with `astype("str")` after
  checking what the odd values are.
* A text column used as a join key must have the same dtype on both sides; see
  xref:data-science/pandas/merge-and-join.adoc[Merge & Join].
* Comparing `str` and `"string"` columns returns different result dtypes; pick one representation per project.
* `str.replace` is literal by default; pass `regex=True` for patterns.
* `str.contains` with special characters (`.`, `(`, `+`) is a regular expression; pass `regex=False` for literal search.
* Slow row-wise `apply` of Python string functions is rarely needed: the vectorised `.str` method is usually several times
  faster on `str` columns.

|`str.replace` uses regular expressions by default.
|`regex=False` is the default since pandas 2.0.

|`astype(str)` turns `NaN` into the string `"nan"`.
|Missing values are preserved in the `str` dtype.

|PyArrow becomes a required dependency in pandas 3.0.
|PyArrow stays optional in pandas 3.1; `str` falls back to Python storage without it.

|`pd.options.future.infer_string = True` opts in to the new dtype.
|The option is deprecated in 3.1 and will be removed in 4.0; the behaviour is already the default.
