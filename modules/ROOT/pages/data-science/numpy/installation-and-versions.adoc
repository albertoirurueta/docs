= NumPy Installation and Versions
:description: How to install NumPy 2.5 with pip, uv, conda or Miniforge, check the installed version and build configuration, understand the release cadence and supported Python versions, and adapt older code to what NumPy 2.0 to 2.5 renamed, removed or changed, including Ruff rule NPY201.
:keywords: NumPy, install NumPy, pip install numpy, conda, Miniforge, uv, NumPy 2.5, NumPy 2.0 migration, NPY201, Ruff, release cadence, Python support, default_rng, NEP 50, NEP 51, numpy.show_config

include::partial$data-science-numpy-disclaimer.adoc[]

NumPy is the array library that almost all of the scientific Python stack is built on, so getting the installation right
is the first step of every data science project. This page covers how to install NumPy, how to check what you have, how
NumPy is versioned and released, and what changed between NumPy 2.0 and 2.5 so that older code, books and tutorials
can be read critically. It targets NumPy 2.5 (the 2.5.4 patch release, published in October 2026), and every statement
was checked in October 2026. Examples target Python 3.13 or 3.14 and were run on Python 3.13. All the examples were executed with NumPy 2.5.4.

For the general mechanics of virtual environments, pip and lock files see
xref:programming-languages/python/virtual-environments-and-packaging.adoc[Virtual Environments and Packaging] and
xref:programming-languages/python/build-tools/lock-files-and-reproducible-installs.adoc[Lock Files and Reproducible
Installs]. For the data science specific choices (venv or uv or Miniforge, binary wheels, BLAS threads, version policy of
the scientific projects) see xref:data-science/environment-setup.adoc[Setting Up a Data Science Environment]. This page
does not repeat them.

== Installing NumPy

NumPy publishes binary wheels for the mainstream platforms, so a normal installation needs no compiler. Install it into
an isolated environment rather than into the system Python.

=== With pip in a virtual environment

[source,bash]
----
python -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
python -m pip install --upgrade pip
python -m pip install numpy
python -c "import numpy as np; print(np.__version__)"
----

Source: https://numpy.org/install/[NumPy installation instructions].

Use `python -m pip` rather than a bare `pip`, so that the package is installed for the interpreter that you are going to
run. Pin the version when reproducibility matters, for example `python -m pip install "numpy>=2.5,<2.6"`, and record the
whole environment in a lock file (see the lock file page linked above).

=== With uv

[source,bash]
----
uv init analysis && cd analysis
uv add numpy
uv run python -c "import numpy as np; print(np.__version__)"
----

Source: https://numpy.org/install/[NumPy installation instructions] and https://docs.astral.sh/uv/[uv documentation].

`uv add` records NumPy in `pyproject.toml` and in `uv.lock`, which makes the installation reproducible. `uv pip install numpy`
is the drop-in equivalent of pip inside an existing virtual environment. The official install page also mentions Pixi
(`pixi add numpy`) for project based workflows.

=== With conda or Miniforge

[source,bash]
----
conda create -n analysis python=3.13 numpy
conda activate analysis
conda list --show-channel-urls numpy
----

Source: https://numpy.org/install/[NumPy installation instructions] and https://conda-forge.org/docs/user/introduction/[conda-forge documentation].

Conda can also install non-Python dependencies (compilers, CUDA, HDF5), which pip cannot. NumPy is available from the
`defaults` channel and from conda-forge. Mixing the two in one environment causes hard to diagnose conflicts; the
recommended setup is Miniforge, which uses conda-forge only, with strict channel priority. Anaconda's terms of service
(updated on 2025-07-15) require a paid plan for organisations with more than 200 employees or contractors that use
Anaconda's repository; this is not legal advice, so check the current terms. The complete reasoning is on
xref:data-science/environment-setup.adoc[Setting Up a Data Science Environment].

=== System package managers and building from source

The official page lists `brew install numpy`, `sudo apt install python3-numpy` and `choco install numpy` as possible but
not recommended for most users: the package belongs to the system Python, usually lags several releases and cannot be
isolated per project. Building from source is for developers; it needs a C and C++ compiler, Meson and a BLAS/LAPACK
library, and the official documentation recommends binary wheels wherever they exist. Since NumPy 2.5 `numpy.distutils`
no longer exists and builds use Meson.

=== Which tool to choose

[mermaid]
----
flowchart TD
    A[Need NumPy] --> B{Pure Python dependencies only?}
    B -- yes --> C{Want a lock file and one tool?}
    C -- yes --> D[uv add numpy]
    C -- no --> E[python -m venv and python -m pip install numpy]
    B -- no, compilers CUDA HDF5 or a managed Python --> F[Miniforge: conda create with conda-forge only]
    D --> G[Check np.__version__ and numpy.show_config]
    E --> G
    F --> G
----

== Checking what is installed

[source,python]
----
import sys
import numpy as np

print(np.__version__, sys.version_info[:2])
print(np.version.full_version, np.version.release)
np.show_config()   # compiler, BLAS/LAPACK and SIMD information of this build
----

Output of the two `print` calls (the `show_config()` report that follows them is left out here, because its compiler,
BLAS/LAPACK and SIMD details differ per platform):

[source,text]
----
2.5.4 (3, 13)
2.5.4 True
----

Source: https://numpy.org/doc/stable/reference/generated/numpy.show_config.html[numpy.show_config].

`+np.__version__+` is the string you should log with every experiment. `np.version.release` is `False` for development
builds. `np.show_config()` reports which BLAS and LAPACK implementation does the heavy linear algebra (OpenBLAS in the
Linux and Windows wheels, Accelerate on recent macOS builds) and which CPU features are used; install
`pyyaml` for the nicer output format the function prints a warning about otherwise. If `import numpy` fails with an
`ImportError` about C extensions, the usual causes are running the interpreter from inside the NumPy source directory,
or an environment where a package was compiled against a different NumPy than the one now installed; the official
troubleshooting guide for that error is linked in the references.

== Import convention

[source,python]
----
import numpy as np
----

Source: https://numpy.org/doc/stable/user/absolute_beginners.html[NumPy: the absolute basics for beginners].

`import numpy as np` is the universal convention, used by the NumPy documentation, scikit-learn, pandas and virtually
all tutorials. Never use `from numpy import *`: it shadows the built-ins `sum`, `min`, `max`, `abs`, `round` and `any`
with NumPy functions that behave differently on non-array arguments.

== Versions, Python support and release cadence

NumPy uses MAJOR.MINOR.PATCH numbering. Minor releases (2.4, 2.5) appear roughly every six months, around June and
December; they may deprecate and, after at least two minor releases of warning, remove features. Patch releases (2.5.1
to 2.5.4) fix bugs and are published as needed. Each minor release supports a window of Python versions defined by the
community policy SPEC 0, and NumPy drops the oldest Python as the window moves.

[cols="1,2,3",options=header]
|===
| NumPy | Supported Python | Notes

| 2.0 (June 2024)
| 3.9 to 3.12
| First major release since 2006. Many aliases removed, new default promotion rules (NEP 50), new scalar repr (NEP 51), `StringDType`, array API standard support.

| 2.1 and 2.2
| 3.10 to 3.13
| Experimental free-threaded CPython support (2.1), `matvec`/`vecmat` (2.2).

| 2.3
| 3.11 to 3.13
| The mypy plugin is deprecated.

| 2.4
| 3.11 to 3.14
| Removal of `np.trapz`, `np.in1d`, `interpolation=` and `reshape(newshape=)`; setting `strides` deprecated.

| 2.5 (2.5.0 in June 2026; 2.5.4 in October 2026)
| 3.12 to 3.14, with Python 3.15 support starting at its first release candidate
| `numpy.distutils` and `np.row_stack` removed, `sort(descending=True)`, `eig`/`eigvals` always complex, `shape` and `dtype` setters deprecated.

| 2.6 (upcoming)
| not yet released
| Development version 2.6.dev0; the mypy plugin is removed there. Anything listed as 2.6 on this site is upcoming and must not be used in production.
|===

Source: https://numpy.org/doc/stable/release.html[NumPy release notes] and https://numpy.org/doc/stable/release/2.5.0-notes.html[NumPy 2.5.0 release notes].

Two practical consequences follow. First, a project that wants to support several NumPy versions should read the
minimum versions recommended by SPEC 0 (at the end of 2026: Python 3.13 and NumPy 2.3) instead of the oldest version
that happens to import. Second, the stable documentation at `numpy.org/doc/stable` is built from the 2.5.0 tag, so
the notes of the patch releases 2.5.1 to 2.5.4 are published only in the development documentation; the API
described in the stable pages is nevertheless the one you get with 2.5.4. When a statement on the website and the
release notes disagree, follow the release notes: for example the FFT page still says that single precision input is
promoted to double precision, while the 2.0 notes state that FFTs now compute natively in single and long double
precision.

Check your own interpreter before choosing a version: NumPy 2.5 does not install on Python 3.11 or older, and a very new
Python (3.15 at the time of writing) may not have wheels for every library in your stack yet.

== What changed from NumPy 2.0 to 2.5

This is the part that matters when you read older books, blog posts or Stack Overflow answers. Code written for NumPy
1.x mostly still runs, but some of it fails with an `AttributeError`, and some of it silently changes meaning.

=== Removed names and their replacements

NumPy 2.0 cleaned the main namespace. Using a removed name raises an `AttributeError` that names the replacement:

[source,python]
----
import numpy as np

x = np.float_(1)
----

[source,text]
----
AttributeError: `np.float_` was removed in the NumPy 2.0 release. Use `np.float64` instead.
----

Source: https://numpy.org/doc/stable/numpy_2_0_migration_guide.html[NumPy 2.0 migration guide].

[cols="2,2,1",options=header]
|===
| Removed | Use instead | Removed in

| `np.float_`, `np.complex_`, `np.string_`, `np.unicode_`
| `np.float64`, `np.complex128`, `np.bytes_`, `np.str_`
| 2.0

| `np.NaN`, `np.Inf`, `np.infty`, `np.PINF`, `np.NINF`
| `np.nan`, `np.inf`, `-np.inf`
| 2.0

| `np.alltrue`, `np.sometrue`, `np.product`, `np.cumproduct`
| `np.all`, `np.any`, `np.prod`, `np.cumprod`
| 2.0

| `np.round_`, `np.asfarray`, `np.mat`
| `np.round`, `np.asarray` with `dtype=float`, a 2-D array
| 2.0

| `np.cast`, `np.find_common_type`
| `astype`, `np.result_type` or `np.promote_types`
| 2.0

| `np.core`
| the public API; the internals moved to the private `np._core` and importing `numpy.core` only emits a `DeprecationWarning`
| 2.0

| `np.trapz`, `np.in1d`
| `np.trapezoid`, `np.isin`
| 2.4

| `interpolation=` in `percentile` and `quantile`; `newshape=` in `reshape`
| `method=`; `shape=` or a positional argument
| 2.4

| `np.row_stack`, `recfromtxt`, `recfromcsv`, the `+'a'+` dtype alias, `numpy.distutils`
| `np.vstack`, `np.genfromtxt`, `+'S'+`, Meson based builds
| 2.5
|===

Source: https://numpy.org/doc/stable/numpy_2_0_migration_guide.html[NumPy 2.0 migration guide] and the release notes for 2.4 and 2.5.

The 2.0 aliases were removed in a single step, whereas later removals followed one or two minor releases of
`DeprecationWarning`. To see what your own code is about to lose, run it with warnings promoted to errors:
`python -W error::DeprecationWarning script.py`.

=== Ruff rule NPY201

The Ruff linter implements the migration for you. Its `NPY201` rule (NumPy 2.0 deprecation) flags removed names and
fixes most of them automatically:

[source,bash]
----
python -m pip install ruff
ruff check --select NPY201 --fix .
----

Source: https://docs.astral.sh/ruff/rules/numpy2-deprecation/[Ruff rule NPY201] and https://numpy.org/doc/stable/numpy_2_0_migration_guide.html[NumPy 2.0 migration guide].

Review the diff afterwards: the fix cannot know that a library you call still expects the old behaviour, and it does
not rewrite `np.float_` inside strings or generated code.

=== Behaviour changes that do not raise

[source,python]
----
import numpy as np

print(np.float64(3.0))            # 3.0
print(repr(np.float64(3.0)))      # np.float64(3.0)
np.set_printoptions(legacy="1.25")
print(repr(np.float64(3.0)))      # 3.0, the pre-2.0 repr
np.set_printoptions(legacy=False)

print(np.float32(3) + 3.0, (np.float32(3) + 3.0).dtype)   # 6.0 float32
print((np.uint8(1) + 2).dtype)                            # uint8
try:
    np.int8(1) + 1000
except OverflowError as e:
    print("OverflowError:", e)
----

Output:

[source,text]
----
3.0
np.float64(3.0)
3.0
6.0 float32
uint8
OverflowError: Python integer 1000 out of bounds for int8
----

Source: https://numpy.org/neps/nep-0050-scalar-promotion.html[NEP 50] and https://numpy.org/neps/nep-0051-scalar-representation.html[NEP 51].

* **Scalar representation (NEP 51).** `repr` of a NumPy scalar now includes its type, `np.float64(3.0)`. Code or
  doctests that compare printed output with the old `3.0` break; `str()` and `print()` are unchanged.
* **Promotion (NEP 50).** Python scalars are "weak": they adopt the dtype of the NumPy operand instead of forcing a wider
  one, so `np.float32(3) + 3.0` stays `float32` and `np.uint8(1) + 2` stays `uint8`. NumPy scalars are "strong". A Python
  integer that does not fit raises `OverflowError`. See xref:data-science/numpy/type-promotion.adoc[Type Promotion (NEP
  50)] for the full rules.
* **Default integer.** The default integer is now 64-bit on 64-bit Windows as well (it was 32-bit `long` before 2.0), so
  `np.arange(3).dtype` is `int64` on every 64-bit platform.
* **`np.bool`.** `np.bool` is again the canonical name of the boolean dtype (it is `np.bool_`), after being removed in 1.24.

=== `copy=False` now raises

[source,python]
----
import numpy as np

try:
    np.array([1, 2, 3], copy=False, dtype=float)
except ValueError as e:
    print("ValueError:", e)

print(np.asarray([1, 2, 3], dtype=float))              # copy only if needed
print(np.array([1, 2, 3], dtype=float, copy=None))     # same meaning, explicit
----

Output:

[source,text]
----
ValueError: Unable to avoid copy while creating an array as requested.
If using `np.array(obj, copy=False)` replace it with `np.asarray(obj)` to allow a copy when needed (no behavior change in NumPy 1.x).
For more details, see https://numpy.org/devdocs/numpy_2_0_migration_guide.html#adapting-to-changes-in-the-copy-keyword.
[1. 2. 3.]
[1. 2. 3.]
----

Source: https://numpy.org/doc/stable/numpy_2_0_migration_guide.html#adapting-to-changes-in-the-copy-keyword[NumPy 2.0 migration guide: the copy keyword].

In NumPy 1.x, `copy=False` meant "copy only if needed". In NumPy 2 it means "never copy" and raises if a copy is
unavoidable. The old meaning is spelled `copy=None` or, more commonly, `np.asarray`. A class that implements
`+__array__+` must accept `dtype=None, copy=None` arguments.

=== A short list of what 2.1 to 2.5 added or deprecated

* **2.0**: `StringDType` (variable-width UTF-8 strings), `np.strings`, `np.vecdot`, `np.linalg.matrix_norm`, `vector_norm`
  and `svdvals`, `.mT`, `quantile(weights=)`, `sort(stable=True)`, array API standard support, thread-safe and
  context-local `np.errstate`.
* **2.1**: experimental free-threaded Python support.
* **2.2**: `np.matvec` and `np.vecmat`; the NEP 50 escape hatch of 2.0 is removed.
* **2.3**: mypy plugin deprecated.
* **2.4**: `ndmax` argument for `np.array`, `np.round` always copies, `where=` without `out=` warns,
  `casting="same_value"`, removal of `np.trapz`, `np.in1d` and `interpolation=`.
* **2.5**: `sort(descending=True)` and `argsort(descending=True)`, `polyvalnd` family, pattern matching on arrays,
  `np.distutils` gone; deprecations: setting `arr.shape` (use `np.reshape`) and `arr.dtype` (use `arr.view`), `np.fix`
  (use `np.trunc`), `np.char.chararray`, generic-unit `timedelta64`; `eig` and `eigvals` now always return complex arrays
  (use `eigh` or `eigvalsh` for symmetric matrices); `Generator.binomial` and `Generator.multinomial` can return different
  samples for the same seed.

Source: https://numpy.org/doc/stable/release.html[NumPy release notes 2.0 to 2.5].

The full list lives on the dedicated migration and release pages of this section, which are written for reading
end to end: see xref:data-science/numpy/numpy-2-migration.adoc[Migrating to NumPy 2.x] and
xref:data-science/numpy/whats-new.adoc[What's New].

== Making installed versions visible in your work

Record the version in every notebook, report or log, not just in `requirements.txt`:

[source,python]
----
import platform
import numpy as np

print(f"Python {platform.python_version()} on {platform.system()} {platform.machine()}")
print(f"NumPy {np.__version__}")
----

Output on the machine used for this page:

[source,text]
----
Python 3.13.18 on Darwin arm64
NumPy 2.5.4
----

Source: https://numpy.org/doc/stable/reference/generated/numpy.show_config.html[numpy.show_config].

A numerical result can differ between BLAS implementations in the last digits, so the version line is not decoration; it
is part of the evidence needed to reproduce a number. See
xref:data-science/reproducibility-and-mlops-basics.adoc[Reproducibility and MLOps Basics].

== Common installation pitfalls

* **Installing into the system Python** (`sudo pip install`) breaks operating-system tools and is blocked on distributions
  that mark the interpreter as externally managed; use a virtual environment (see
  xref:programming-languages/python/build-tools/environments-and-externally-managed-pythons.adoc[Environments and
  Externally Managed Pythons]).
* **Several interpreters.** Jupyter, an IDE and a terminal can each use a different Python; print
  `sys.executable` and `+np.__file__+` to see which NumPy is imported.
* **Packages built against NumPy 1.x.** A compiled extension built for NumPy 1.x fails to import under NumPy 2 with an
  error such as "A module that was compiled using NumPy 1.x cannot be run in NumPy 2". Upgrade the extension; pinning
  `numpy<2` is a stop gap that conflicts with newer Python versions.
* **Mixing pip and conda** in one environment replaces conda-managed files with pip ones. Install everything possible with
  conda first and use pip last, or use a single tool.
* **Oversubscribed BLAS threads** when several processes each start a full thread pool; limit them with
  `threadpoolctl` or the `OPENBLAS_NUM_THREADS` environment variable.
* **Naming a script `numpy.py`** shadows the library and makes `import numpy` fail in confusing ways.

Source: https://numpy.org/doc/stable/numpy_2_0_migration_guide.html[NumPy 2.0 migration guide] and https://numpy.org/doc/stable/reference/thread_safety.html[NumPy thread safety].
