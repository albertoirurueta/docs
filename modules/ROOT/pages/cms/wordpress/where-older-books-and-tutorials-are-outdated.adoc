= Where Older Books and Tutorials Are Outdated
:description: A reference of claims in older WordPress books and tutorials that no longer hold in WordPress 7.1, grouped by area, with the current behaviour, the version that changed it, the page of this section that covers it and the official source.
:keywords: WordPress, outdated advice, corrections, WordPress All-in-One For Dummies, Pro WordPress, Ultimate WordPress Handbook, block themes, synced patterns, reusable blocks, Customizer, Navigation block, bcrypt, phpass, admin-ajax, REST API, Interactivity API, wp-now, Playground CLI, Vitest, MU Domain Mapping, file permissions, DISALLOW_FILE_MODS, WP_ALLOW_REPAIR, sitemap, Server Push, query cache

include::partial$cms-wordpress-disclaimer.adoc[]

WordPress keeps old code working for a long time, so outdated advice rarely fails loudly: a post type registered
without `show_in_rest` still saves posts, a 777 directory still accepts uploads, and a sitemap ping still returns a
response. This page collects, in one place, the statements in older books and tutorials that the rest of this section
corrects, with the version where the behaviour changed, the page that covers it in depth and the official source. It
is a reference to check advice against before following it, not a substitute for the pages it links.

The page was written against WordPress 7.1.3 (released 2026-10-06), the release the examples in this section were
tested on; WordPress 7.1.4 (released 2026-10-28) is the current security release and should be used in production, and
WordPress 7.2 is in beta, planned for 2026-12-08. Other versions referred to: PHP 7.4 minimum and 8.3+ recommended,
`theme.json` version 3, Gutenberg 24.2.0, `@wordpress/scripts` 37.0.0, `@wordpress/create-block` 5.0.0,
`@wordpress/env` 12.0.0, `@wordpress/interactivity` 8.0.0, WordPress Coding Standards 3.4.1 and WP-CLI 2.12.0.
Everything was checked on 2026-10-28.

== The books compared

Three books published in 2024 were compared with the official documentation. They remain useful for their
operational advice, and much of what they say about writing, publishing, vetting plugins, hosting choices and incident
response still holds. Where they disagree with the official documentation, the official documentation wins. The tables
below refer to them by short title:

[cols="1,3,3",options="header"]
|===
| Short title | Book | Targets and scope

| *All-in-One*
| Lisa Sabin-Wilson, *WordPress All-in-One For Dummies*, 5th edition (Wiley, 2024)
| WordPress 6.3 to 6.4; site owners and administrators; block editor and block themes from the user's side; no plugin,
theme or block development

| *Pro WordPress*
| Sivaraj Selvaraj, *Pro WordPress: Mastering the Techniques for Building, Securing and Scaling Websites* (Apress, 2024)
| No version stated (6.2 is the latest named); classic themes only; hosting, security, performance, SEO, Multisite and
scaling; no block themes, `theme.json`, blocks or REST development

| *Ultimate Handbook*
| Daniel Bisett and Tricia Elizabeth Ulberg, *Ultimate WordPress Handbook* (Orange Education/AVA, 2024)
| WordPress 6.4 to 6.6 and Twenty Twenty-Four; Customizer-centred design with a commercial theme and builder;
troubleshooting runbooks, SEO, analytics and privacy
|===

Rows marked *Tutorials* come from the wider body of blog posts, snippets and handbooks written for WordPress 5.x and
early 6.x. None of the three books covers what arrived between 6.5 and 7.1 (Font Library, Block Bindings, the
Interactivity API, Script Modules, section styles, pattern overrides, PHP-only blocks, the Abilities API, the AI
Client, responsive styles, the always-iframed editor); for those the handbooks, the Make WordPress Core field guides and
developer notes, and the WordPress Developer Blog are the only sources.

== Installation and hosting

[cols="3,3,1,2,2",options="header"]
|===
| Older claim | Current state | Since | Covered in | Official source

| *All-in-One*: `wp-config.php` ends with a closing `?>` tag
| The shipped sample has no closing tag, the PHP convention for code-only files; a stray byte after `?>` causes
"headers already sent" errors
| Always | xref:cms/wordpress/installation.adoc[Installation] | https://developer.wordpress.org/advanced-administration/wordpress/wp-config/[Advanced Administration Handbook: wp-config.php]

| *All-in-One*: check PHP Safe Mode when uploads or installs fail
| Safe Mode was removed from PHP itself in 5.4 (2012); no supported PHP version has it
| PHP 5.4 | xref:cms/wordpress/requirements-and-hosting.adoc[Requirements and Hosting] | https://www.php.net/releases/5_4_0.php[PHP: PHP 5.4.0 Release Announcement]

| *Pro WordPress*: change `ABSPATH` when moving `wp-config.php` one level up
| `wp-load.php` finds the file one level above the WordPress directory on its own; `ABSPATH` must not be edited, and
the security benefit of the move is disputed
| Always | xref:cms/wordpress/wp-config-reference.adoc[wp-config.php Reference] | https://developer.wordpress.org/advanced-administration/security/hardening/[Advanced Administration Handbook: Hardening WordPress]

| *All-in-One*, *Ultimate Handbook*: protect files with `Order`, `Allow` and `Deny`
| Apache 2.4 uses `Require all denied`; the 2.2 directives need `mod_access_compat`, and mixing both styles is
discouraged
| Apache 2.4 | xref:cms/wordpress/web-servers-apache-and-nginx.adoc[Web Servers: Apache and nginx] | https://httpd.apache.org/docs/2.4/upgrading.html[Apache HTTP Server 2.4: Upgrading to 2.4 from 2.2]

| *Tutorials*: pretty permalinks require `mod_rewrite`
| Only on Apache; nginx needs one `try_files` line and no `.htaccess`, and the rules stay in PHP
| Always | xref:cms/wordpress/rewrite-api-and-permalinks.adoc[Rewrite API and Permalinks] | https://developer.wordpress.org/advanced-administration/server/web-server/nginx/[Advanced Administration Handbook: nginx]

| *All-in-One*: a desktop install is a "local staging" site
| Staging runs on the production stack; a laptop differs in web server, PHP build, cache and permissions. Mark each
environment with `WP_ENVIRONMENT_TYPE`
| 5.5 | xref:cms/wordpress/local-development-environments.adoc[Local Development Environments] | https://make.wordpress.org/core/2020/07/24/new-wp_get_environment_type-function-in-wordpress-5-5/[Make WordPress Core: New wp_get_environment_type() function in WordPress 5.5]

| *Tutorials*: run the local site with `wp-now`
| `@wp-now/wp-now` is deprecated; the Playground CLI (`@wp-playground/cli`) has an equivalent for every option
| 2026 | xref:cms/wordpress/playground-and-blueprints.adoc[Playground and Blueprints] | https://developer.wordpress.org/playground/developers/local-development/wp-playground-cli/[Playground documentation: Playground CLI]

| *Tutorials*: Docker Compose files with `version:`, `links:`, `mysql:5.7` and unpinned `wordpress:latest`
| Current Compose ignores `version` and resolves service names without `links`; MySQL 5.7 is end-of-life; pin a

| 2023 | xref:cms/wordpress/containers-docker-and-kubernetes.adoc[Containers, Docker and Kubernetes] | https://hub.docker.com/_/wordpress[Docker Hub: wordpress]

| *Tutorials*: back up the database with `mysqldump`
| On MariaDB 11 the tool is `mariadb-dump` (`mysqldump` is a deprecated alias missing from the container image);

| MariaDB 11 | xref:cms/wordpress/backups-and-disaster-recovery.adoc[Backups and Disaster Recovery] | https://mariadb.com/docs/server/clients-and-utilities/backup-restore-and-import-clients/mariadb-dump[MariaDB Documentation: mariadb-dump]

| Always | xref:cms/wordpress/wp-config-reference.adoc[wp-config.php Reference] | https://developer.wordpress.org/advanced-administration/wordpress/wp-config/[Advanced Administration Handbook: wp-config.php]

| *Tutorials*: turn on `WP_DEBUG` to see errors

| *Tutorials*: a fatal error means a white screen and FTP

| 5.2 | xref:cms/wordpress/debugging-site-health-and-troubleshooting.adoc[Debugging, Site Health and Troubleshooting] | https://make.wordpress.org/core/2019/04/16/fatal-error-recovery-mode-in-5-2/[Make WordPress Core: Fatal Error Recovery Mode in 5.2]

| *Tutorials*: move a site with SQL `REPLACE()` over the database
| Breaks serialized data; `wp search-replace` handles it, and the GUID column is left alone

| *Pro WordPress*: choose the editor in Settings > Writing

| 5.0 | xref:cms/wordpress/block-editor-for-authors.adoc[Block Editor for Authors] | https://wordpress.org/documentation/article/settings-writing-screen/[WordPress.org Documentation: Settings Writing Screen]

| 4.9 | xref:cms/wordpress/dashboard-and-admin-screens.adoc[Dashboard and Admin Screens] | https://wordpress.org/plugins/press-this/[WordPress.org Plugins: Press This]

== Security

[cols="3,3,1,2,2",options="header"]
|===
| Older claim | Current state | Since | Covered in | Official source

| *All-in-One*: set 666 or 777 when uploads or installs fail
| 644 for files, 755 for directories, 440 or 400 for `wp-config.php`; the real fix is ownership, and 777 still fails
the filesystem method test
| Always | xref:cms/wordpress/file-permissions-and-filesystem.adoc[File Permissions and Filesystem] | https://developer.wordpress.org/advanced-administration/security/hardening/#changing-file-permissions[Advanced Administration Handbook: Hardening, Changing file permissions]

| *Tutorials*: passwords are stored as phpass (MD5-based) hashes
| bcrypt with a pre-hash, prefixed `$wp$2y$`; old hashes are rehashed at the next login, and application passwords use
BLAKE2b
| 6.8 | xref:cms/wordpress/authentication-and-login-api.adoc[Authentication and Login API] | https://make.wordpress.org/core/2025/02/17/wordpress-6-8-will-use-bcrypt-for-password-hashing/[Make WordPress Core: WordPress 6.8 will use bcrypt for password hashing]

| *Tutorials*: reset a lost password by writing an MD5 hash in phpMyAdmin
| Still accepted once and rehashed, but legacy; use "Lost your password?", `wp user reset-password` or
`wp user update` with `+--user_pass+`
| 6.8 | xref:cms/wordpress/users-roles-and-profiles.adoc[Users, Roles and Profiles] | https://developer.wordpress.org/cli/commands/user/reset-password/[WP-CLI Commands: wp user reset-password]

| *Tutorials*: WordPress enforces strong passwords
| It shows a strength meter and asks to confirm a weak password; enforcement needs a plugin or SSO
| Always | xref:cms/wordpress/users-roles-and-profiles.adoc[Users, Roles and Profiles] | https://wordpress.org/documentation/article/users-your-profile-screen/[WordPress.org Documentation: Users Your Profile Screen]

| *Tutorials*: scripts and apps need the user's real password or a Basic Auth plugin
| Application passwords are built in: HTTPS-only by default, REST API and XML-RPC only, never `wp-login.php`, revocable
one by one
| 5.6 | xref:cms/wordpress/rest-api-using.adoc[REST API: Using It] | https://make.wordpress.org/core/2020/11/05/application-passwords-integration-guide/[Make WordPress Core: Application Passwords Integration Guide]

| *Tutorials*: `system.multicall` lets one request try hundreds of passwords
| Since 4.4 the first failed login in a request makes the rest fail; disable XML-RPC when unused and rate-limit
`wp-login.php` and `xmlrpc.php` at the server
| 4.4 | xref:cms/wordpress/security-hardening.adoc[Security Hardening] | https://developer.wordpress.org/advanced-administration/security/brute-force/[Advanced Administration Handbook: Brute Force Attacks]

| *Tutorials*: hide or rename the login URL to stop attacks
| Obscurity, not a defense; rate limiting, strong passwords and two-factor login are
| Always | xref:cms/wordpress/security-hardening.adoc[Security Hardening] | https://developer.wordpress.org/advanced-administration/security/brute-force/[Advanced Administration Handbook: Brute Force Attacks]

| *Tutorials*: install iThemes Security
| The same WordPress.org plugin was renamed Solid Security (9.0) and then Kadence Security (10.0)
| Plugin 10.0 | xref:cms/wordpress/security-hardening.adoc[Security Hardening] | https://wordpress.org/plugins/better-wp-security/[WordPress.org Plugins: Kadence Security]

| *Pro WordPress*: an `admin-ajax.php` handler called from jQuery with no nonce
| Any site can make a logged-in browser post to it (CSRF); check `check_ajax_referer()` and `current_user_can()`, or use
a REST route with a `permission_callback`
| Always | xref:cms/wordpress/security-for-developers.adoc[Security for Developers] | https://developer.wordpress.org/plugins/security/nonces/[Plugin Handbook: Nonces]

| *Ultimate Handbook*: a Customizer setting without `sanitize_callback`, printed with `get_theme_mod()` unescaped
| Every setting has a `sanitize_callback`, and output is escaped late with `esc_html()`, `esc_attr()` or `esc_url()`
| Always | xref:cms/wordpress/customizer-api.adoc[Customizer API] | https://developer.wordpress.org/apis/security/escaping/[Common APIs Handbook: Escaping Data]

| *Tutorials*: `is_admin()` checks that the user is an administrator
| It tells whether an admin screen is loading; check a capability with `current_user_can()`
| Always | xref:cms/wordpress/roles-and-capabilities-api.adoc[Roles and Capabilities API] | https://developer.wordpress.org/plugins/security/checking-user-capabilities/[Plugin Handbook: Checking User Capabilities]

| *Tutorials*: `esc_sql()` or `addslashes()` makes a query safe
| `+$wpdb->prepare()+` with unquoted placeholders, `%i` for identifiers, and `esc_like()` for `LIKE`
| 6.2 | xref:cms/wordpress/wp-query-and-the-database-api.adoc[WP_Query and the Database API] | https://developer.wordpress.org/reference/classes/wpdb/prepare/[Code Reference: wpdb::prepare()]

== Performance

[cols="3,3,1,2,2",options="header"]
|===
| Older claim | Current state | Since | Covered in | Official source

| *Pro WordPress*: concatenate CSS and JavaScript and use image sprites
| Under HTTP/2 and HTTP/3 small cached files share one connection; ship minified files from a build step, use

| HTTP/2 | xref:cms/wordpress/performance-and-caching.adoc[Performance and Caching] | https://developer.wordpress.org/advanced-administration/performance/optimization/[Advanced Administration Handbook: Optimization]

== How to read older material

* *Check the version the text targets.* A book or post written for 6.2 to 6.6 predates everything in the 6.7 to 7.1
  rows of xref:cms/wordpress/versions-and-release-cycle.adoc[Versions and Release Cycle].
* *Ask whether the advice is about classic or block themes.* Template files, the Customizer, widgets and
  Appearance > Menus remain correct for classic themes; the equivalents for block themes are in the
  xref:cms/wordpress/themes-overview.adoc[Themes Overview].
* *Treat security snippets with suspicion.* Missing nonces, missing capability checks, unescaped output and
  string-built SQL are the most common defects in copied code; compare them with
  xref:cms/wordpress/security-for-developers.adoc[Security for Developers].
* *Prefer the handbooks, field guides and developer notes.* They are updated with each release; this page and the
  section bibliography in xref:cms/wordpress/index.adoc[WordPress] link the ones used here.
