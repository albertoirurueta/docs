== The release at a glance

image::cms-wordpress-cloud-release-topology.svg["Kubernetes objects of the release: ALB from the Ingress, the Service, pods with nginx and php-fpm containers sharing an EFS uploads volume, configuration from a ConfigMap and External Secrets, and the cron, migrate and install Jobs",width=760]

Each pod of the Deployment `lumenpress-web` runs two containers. *nginx* serves static files and sends `.php` requests to
*PHP-FPM* over FastCGI. Both containers share the pod's network namespace, so nginx reaches FPM at `127.0.0.1:9000` and
there is no Service between them. This is the standard shape for PHP on Kubernetes, and it differs from the Apache image
(`mod_php`) that the single-server page uses in three ways that matter:

* the web server and the PHP runtime are tuned and restarted independently, and PHP-FPM's `pm.max_children` is the
  concurrency knob;
* static files never reach PHP: nginx serves `wp-includes` and `wp-content` assets itself;
* two images are needed, because nginx has to see the same static files that the PHP image carries. The Dockerfile
  builds both from one source tree, so a release is one commit and two tags.

== The image

The Lumen Press repository holds `docker/` (this section), `plugins/lumen-catalog/`, `themes/lumen/` and the chart. The
Composer and Node build stages for the plugin are shown on
xref:cms/wordpress/containers-docker-and-kubernetes.adoc[Containers, Docker and Kubernetes]; here the plugin and theme are
plain folders so the Dockerfile stays readable.

[source,dockerfile]
----
# syntax=docker/dockerfile:1

FROM wordpress:cli-2.12.0-php8.4 AS wpcli

# ---- the Redis Object Cache plugin, downloaded at build time (it also works with Valkey) ----
FROM alpine:3.22 AS redis-cache
ARG REDIS_CACHE_VERSION=3.0.0
RUN set -eux; \
	apk add --no-cache curl unzip; \
	curl -fsSL -o /tmp/redis-cache.zip "https://downloads.wordpress.org/plugin/redis-cache.${REDIS_CACHE_VERSION}.zip"; \
	unzip -q /tmp/redis-cache.zip -d /out; \
	test -f /out/redis-cache/includes/object-cache.php

# ---- target "php": PHP-FPM with WordPress and the Lumen Press code baked in ----------
FROM wordpress:7.1.4-php8.4-fpm AS php

# The official image keeps WordPress in /usr/src/wordpress and copies it into
# /var/www/html when its entrypoint starts. Here the code is part of the image.
RUN set -eux; \
	cp -a /usr/src/wordpress/. /var/www/html/; \
	rm -rf /var/www/html/wp-content/plugins/akismet /var/www/html/wp-content/plugins/hello.php \
		/var/www/html/wp-config-docker.php /var/www/html/wp-config-sample.php; \
	mkdir -p /var/www/html/wp-content/uploads

COPY --from=wpcli /usr/local/bin/wp /usr/local/bin/wp
COPY docker/php/zz-lumen.ini ${PHP_INI_DIR}/conf.d/zz-lumen.ini
COPY docker/php/zz-lumen.conf /usr/local/etc/php-fpm.d/zz-lumen.conf
COPY docker/wp-config.php /var/www/html/wp-config.php
COPY docker/readyz.php /var/www/html/readyz.php
COPY plugins/lumen-catalog /var/www/html/wp-content/plugins/lumen-catalog
COPY themes/lumen /var/www/html/wp-content/themes/lumen
# The plugin folder plus its drop-in: `wp redis enable` cannot copy the drop-in at run time
# on a read-only code tree, so the build does it.
COPY --from=redis-cache /out/redis-cache /var/www/html/wp-content/plugins/redis-cache
RUN cp /var/www/html/wp-content/plugins/redis-cache/includes/object-cache.php /var/www/html/wp-content/object-cache.php

# Code belongs to root and is read-only for the PHP user; only uploads is writable.
RUN set -eux; \
	chown -R root:root /var/www/html; \
	find /var/www/html -type d -exec chmod 0755 {} +; \
	find /var/www/html -type f -exec chmod 0644 {} +; \
	chown www-data:www-data /var/www/html/wp-content/uploads

# Skip the official entrypoint: it would try to copy WordPress and write wp-config.php.
ENTRYPOINT ["docker-php-entrypoint"]
CMD ["php-fpm"]
USER 33:33
EXPOSE 9000

# ---- target "nginx": the static files and the proxy to PHP-FPM ------------------------
FROM nginxinc/nginx-unprivileged:1.29-alpine AS nginx

COPY docker/nginx/default.conf /etc/nginx/conf.d/default.conf
# nginx serves wp-includes, wp-content assets and uploads; PHP files are never executed here.
COPY --from=php --chown=0:0 /var/www/html /var/www/html
EXPOSE 8080
----

Source: https://docs.docker.com/reference/dockerfile/[Dockerfile reference]

The Dockerfile was built with `docker build --target php` and `docker build --target nginx` while writing this page, with
`wordpress:7.1.4-php8.4-fpm` pulled from Docker Hub (verify that the tag exists with `docker pull` when you build; the tag
scheme of the official image is `<version>-php<version>-fpm`). The PHP target came to about 1 GB and the nginx target to
about 170 MB on the test machine. What it does and why:

* *Three stages, two targets.* `wpcli` only provides the `wp` binary, copied pinned from the official CLI image.
  `redis-cache` downloads the object-cache plugin (see
  xref:cms/wordpress/object-cache-sessions-and-cron-in-a-cluster.adoc[Object Cache, Sessions and Cron in a Cluster]). The
  `php` target is the runtime. The `nginx` target copies the finished `/var/www/html` out of the `php` target, so the
  static files can never differ from the code that PHP runs.
* *The code is copied into the image.* The official image keeps WordPress in `/usr/src/wordpress` and copies it into
  `/var/www/html` when its entrypoint runs. That is a convenience for volumes; here it would write to a read-only file
  system. The Dockerfile copies the tree once, and replaces the entrypoint with `docker-php-entrypoint`, so the official
  `docker-entrypoint.sh` (which would copy files and generate a `wp-config.php`) never runs.
* *Own `wp-config.php`.* The image's generated configuration reads `+WORDPRESS_*+` variables and a `WORDPRESS_CONFIG_EXTRA`
  string passed to `eval()`. Lumen Press ships its own file (next section), which reads variables directly, fails loudly
  when a secret is missing and has no `eval()`.
* *Root owns the code.* Files are `root:root` and not writable by the PHP user (UID 33, `www-data`). Even without a
  read-only root file system, a vulnerability in a plugin cannot rewrite code. Only the uploads directory belongs to
  `www-data`, and in the cluster it is a mounted volume.
* *`USER 33:33` and port 9000.* PHP-FPM then runs as a normal user and listens on an unprivileged port. FPM logs a notice
  that its `user` directive is ignored when not running as root; that is harmless and expected.
* *Akismet and Hello Dolly are removed* and `wp-config-sample.php` is deleted: nothing could update them and the sample is
  noise in a production image.
* *nginx-unprivileged.* The `nginxinc/nginx-unprivileged` image runs as UID 101, listens on 8080 and keeps its temporary
  files and PID file under `/tmp`, which makes it work with a read-only root file system and a tmpfs. There is no root
  process in the pod.

=== PHP and FPM settings

[source,ini]
----
; Immutable code: never stat files again.
opcache.enable = 1
opcache.validate_timestamps = 0
opcache.memory_consumption = 192
opcache.interned_strings_buffer = 16
opcache.max_accelerated_files = 20000

memory_limit = 256M
upload_max_filesize = 32M
post_max_size = 32M
expose_php = Off
display_errors = Off
log_errors = On
error_log = /dev/stderr
----

Source: https://www.php.net/manual/en/opcache.configuration.php[PHP Manual: OPcache configuration]

`opcache.validate_timestamps = 0` is the production OPcache setting for immutable code: PHP never checks whether a file
changed, which saves a `stat` per file per request. It is correct here because a code change is a new image and a new
pod, and wrong on any host where files change in place. The 192 MB of OPcache memory and 20 000 accelerated files cover
WordPress core, the theme and a medium plugin set; check `opcache_get_status()` for a full cache before raising traffic.
`log_errors` with `error_log = /dev/stderr` sends PHP errors to the container log, `display_errors` is off, and
`expose_php` hides the PHP version header.

[source,ini]
----
; Loaded after the image's zz-docker.conf, so these values win.
[global]
error_log = /proc/self/fd/2

[www]
; FPM runs as UID 33 (set by the container), so no user or group directives here.
listen = 127.0.0.1:9000
pm = dynamic
pm.max_children = 16
pm.start_servers = 4
pm.min_spare_servers = 2
pm.max_spare_servers = 6
pm.max_requests = 500
request_terminate_timeout = 60s

; Liveness and metrics, reachable only through nginx locations that are not public.
ping.path = /fpm-ping
ping.response = pong
pm.status_path = /fpm-status

catch_workers_output = yes
decorate_workers_output = no
clear_env = no
----

Source: https://www.php.net/manual/en/install.fpm.configuration.php[PHP Manual: FPM configuration]

The pool file loads after the image's `zz-docker.conf` and wins on conflicts. `pm.max_children = 16` is the number that
limits database connections per pod: every busy worker holds one (the arithmetic with replicas is on the
xref:cms/wordpress/managed-database-rds-and-aurora.adoc[database page]). `pm.max_requests = 500` recycles workers to
contain slow memory growth in plugins, `request_terminate_timeout` stops a runaway request, and the status and ping
paths are reachable only through nginx locations that allow `127.0.0.1`. `clear_env = no` is the default of the official
image and is kept explicit because it is what lets the pod's environment variables reach PHP.

=== nginx

[source,nginx]
----
# Pod-local: nginx and PHP-FPM share the pod network namespace, so FPM is on 127.0.0.1.
set_real_ip_from 10.0.0.0/8;
real_ip_header X-Forwarded-For;
real_ip_recursive on;

server {
    listen 8080 default_server;
    server_name _;
    root /var/www/html;
    index index.php;

    client_max_body_size 32m;
    server_tokens off;

    # Kubernetes liveness: answered by nginx itself.
    location = /healthz {
        access_log off;
        default_type text/plain;
        return 200 "ok\n";
    }

    # FPM liveness and status through the pod's own listener only.
    location ~ ^/(fpm-ping|fpm-status)$ {
        allow 127.0.0.1;
        deny all;
        access_log off;
        include fastcgi_params;
        fastcgi_param SCRIPT_FILENAME $document_root$fastcgi_script_name;
        fastcgi_pass 127.0.0.1:9000;
    }

    # Uploads are data: never execute PHP from them.
    location ~* ^/wp-content/uploads/.*\.php$ {
        return 403;
    }

    location ~ /\.(?!well-known) {
        deny all;
    }

    location ~* \.(?:css|js|mjs|woff2?|svg|png|jpe?g|gif|webp|avif|ico)$ {
        expires 30d;
        add_header Cache-Control "public, max-age=2592000";
        try_files $uri =404;
    }

    location / {
        try_files $uri $uri/ /index.php?$args;
    }

    location ~ \.php$ {
        try_files $uri =404;
        include fastcgi_params;
        fastcgi_param SCRIPT_FILENAME $document_root$fastcgi_script_name;
        # X-Forwarded-Proto from the load balancer arrives as HTTP_X_FORWARDED_PROTO.
        fastcgi_read_timeout 60s;
        fastcgi_pass 127.0.0.1:9000;
    }
}
----

Source: https://nginx.org/en/docs/http/ngx_http_core_module.html[nginx: ngx_http_core_module]

Key points: the `realip` directives (nginx's `ngx_http_realip_module`) take the client address from the `X-Forwarded-For`
header that the ALB sets, but only when the connection comes from the VPC range, so a client cannot forge its address.
`/healthz` is answered by nginx itself and is the liveness and load-balancer health check. Uploads can never run PHP (a
`403` for any `.php` below `wp-content/uploads`), dotfiles are denied, and the front controller rule sends unknown paths to
`index.php`. The `fastcgi_params` file makes `HTTP_X_FORWARDED_PROTO` visible to PHP, which `wp-config.php` uses.

The `server_tokens off` directive hides the nginx version. Compression and fine-grained cache headers are left to
CloudFront and the Ingress; the static-asset rule sets a thirty-day lifetime and relies on WordPress's versioned query
strings for cache busting.

=== wp-config.php from environment variables

[source,php]
----
<?php
/**
 * Lumen Press production wp-config.php for Kubernetes.
 * Every value comes from the environment: plain settings from a ConfigMap,
 * secrets from a Secret created by External Secrets Operator.
 */

/** Read an environment variable, with an optional default. */
function lumen_env( string $name, ?string $default = null ): ?string {
	$value = getenv( $name );
	return ( false === $value || '' === $value ) ? $default : $value;
}

/** Like lumen_env() but fail loudly: a pod without its secrets must not start serving. */
function lumen_required( string $name ): string {
	$value = lumen_env( $name );
	if ( null === $value ) {
		http_response_code( 500 );
		error_log( "wp-config: missing environment variable $name" );
		exit( 'Configuration error' );
	}
	return $value;
}

// Database.
define( 'DB_NAME', lumen_required( 'WORDPRESS_DB_NAME' ) );
define( 'DB_USER', lumen_required( 'WORDPRESS_DB_USER' ) );
define( 'DB_PASSWORD', lumen_required( 'DB_PASSWORD' ) );
define( 'DB_HOST', lumen_required( 'WORDPRESS_DB_HOST' ) );
define( 'DB_CHARSET', 'utf8mb4' );
define( 'DB_COLLATE', '' );
// TLS to RDS; certificate verification is covered on the managed database page.
define( 'MYSQL_CLIENT_FLAGS', MYSQLI_CLIENT_SSL );
$table_prefix = lumen_env( 'WORDPRESS_TABLE_PREFIX', 'wp_' );

// The same eight values on every pod, or logins fail on the next request.
foreach ( array(
	'AUTH_KEY', 'SECURE_AUTH_KEY', 'LOGGED_IN_KEY', 'NONCE_KEY',
	'AUTH_SALT', 'SECURE_AUTH_SALT', 'LOGGED_IN_SALT', 'NONCE_SALT',
) as $lumen_constant ) {
	define( $lumen_constant, lumen_required( $lumen_constant ) );
}

// Addresses.
define( 'WP_HOME', lumen_required( 'WP_HOME' ) );
define( 'WP_SITEURL', lumen_required( 'WP_HOME' ) );

// HTTPS: the ALB terminates TLS. Trusting the header is safe only because the
// pods accept traffic from the load balancer and nothing else.
if ( isset( $_SERVER['HTTP_X_FORWARDED_PROTO'] ) && 'https' === $_SERVER['HTTP_X_FORWARDED_PROTO'] ) {
	$_SERVER['HTTPS'] = 'on';
}
define( 'FORCE_SSL_ADMIN', true );

// Immutable code, one scheduler.
define( 'DISALLOW_FILE_MODS', true );
define( 'DISABLE_WP_CRON', true );
define( 'WP_AUTO_UPDATE_CORE', false );
define( 'WP_ENVIRONMENT_TYPE', lumen_env( 'WP_ENVIRONMENT_TYPE', 'production' ) );

// Logs go to stderr, where the container runtime collects them.
define( 'WP_DEBUG', false );
define( 'WP_DEBUG_LOG', '/dev/stderr' );
define( 'WP_DEBUG_DISPLAY', false );

// Object cache: Redis Object Cache plugin settings, pointing at ElastiCache for Valkey.
if ( null !== lumen_env( 'VALKEY_HOST' ) ) {
	define( 'WP_REDIS_HOST', lumen_required( 'VALKEY_HOST' ) );
	define( 'WP_REDIS_PORT', (int) lumen_env( 'VALKEY_PORT', '6379' ) );
	define( 'WP_REDIS_SCHEME', lumen_env( 'VALKEY_SCHEME', 'tls' ) );
	define( 'WP_REDIS_PASSWORD', lumen_required( 'VALKEY_AUTH' ) );
	define( 'WP_REDIS_PREFIX', lumen_env( 'WP_REDIS_PREFIX', 'lumenpress:' ) );
	define( 'WP_REDIS_TIMEOUT', 1 );
	define( 'WP_REDIS_READ_TIMEOUT', 1 );
	define( 'WP_REDIS_GRACEFUL', false );
}

if ( ! defined( 'ABSPATH' ) ) {
	define( 'ABSPATH', __DIR__ . '/' );
}
require_once ABSPATH . 'wp-settings.php';
----

Source: https://developer.wordpress.org/advanced-administration/wordpress/wp-config/[Advanced Administration Handbook: wp-config.php]

The file was checked with `php -l` (PHP 8.4, `No syntax errors detected`) in a `php:8.4-cli` container. Points that deserve
attention:

* *One helper, two behaviours.* `lumen_env()` returns a default when a variable is unset; `lumen_required()` stops the
  request with HTTP 500 and a log line. A pod without its database password or salts must fail its readiness check, not
  serve a login page that cannot work.
* *Secrets come from the environment.* The ConfigMap supplies the plain settings (`WP_HOME`, database host, user, name,
  table prefix), the Secret supplies `DB_PASSWORD`, the eight keys and salts and the Valkey values. An environment
  variable is visible to anyone who can `exec` into the pod or read `/proc`; the alternative is mounting the Secret as files and
  reading them, which the Docker image's `_FILE` convention does. Environment variables are simpler and equal in
  strength for a pod whose access is controlled by RBAC and the Pod Security level.
* *Identical salts everywhere.* All eight constants come from the same Secret. A pod with a different salt rejects every
  login cookie from the others.
* *Database TLS.* RDS for MariaDB 11.8 requires TLS by default (`require_secure_transport` is on from 11.8.3), and
  `MYSQL_CLIENT_FLAGS` set to `MYSQLI_CLIENT_SSL` makes WordPress connect with TLS. It does not verify the server
  certificate; verification with the RDS CA bundle and the corresponding settings are on
  xref:cms/wordpress/managed-database-rds-and-aurora.adoc[Managed Database: RDS and Aurora].
* *HTTPS detection.* The ALB terminates TLS and connects to the pod over HTTP, adding `X-Forwarded-Proto`. Without the
  detection, WordPress builds `http://` URLs, loops on redirects with `FORCE_SSL_ADMIN` and sets non-secure cookies. The
  header is trusted without checking the sender, which is safe only when nothing but the load balancer can reach the pod.
  Keep the Service `ClusterIP`, and add a network policy if other namespaces must not call it directly. The general
  discussion is on xref:cms/wordpress/scaling-and-high-availability.adoc[Scaling and High Availability].
* *Immutable code, one scheduler.* `DISALLOW_FILE_MODS` blocks plugin and core installation and updates from the
  dashboard, automatic core updates are off and `DISABLE_WP_CRON` hands scheduling to the CronJob.
* *Logs to stderr.* `WP_DEBUG_LOG` points at `/dev/stderr`, so the container runtime collects PHP and WordPress log lines
  together with the FPM and nginx logs.

=== Probes: readiness is not liveness

[source,php]
----
<?php
// Readiness: WordPress loads (SHORTINIT skips plugins) and the database answers.
define( 'SHORTINIT', true );
header( 'Content-Type: text/plain' );
header( 'Cache-Control: no-store' );

require __DIR__ . '/wp-load.php';

global $wpdb;
if ( 1 !== (int) $wpdb->get_var( 'SELECT 1' ) ) {
	http_response_code( 503 );
	echo "database unavailable\n";
	exit;
}
echo "ready\n";
----

Source: https://kubernetes.io/docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes/[Kubernetes Documentation: Liveness, readiness and startup probes]

`readyz.php` loads WordPress with `SHORTINIT` (no plugins, no theme) and asks the database one question. It is the
readiness probe: a pod that cannot reach the database leaves the Service endpoints and the ALB target group, and returns
when the database does. The liveness probes are deliberately cheap and independent of dependencies: nginx answers
`/healthz` itself and the FPM container is checked with a TCP connection to port 9000. If liveness depended on the
database, a database outage would restart every pod at once and make recovery slower. The behaviour of `/healthz.php` on a
single host is explained on xref:cms/wordpress/containers-docker-and-kubernetes.adoc[Containers, Docker and Kubernetes].

=== Building, testing and pushing

The script below builds both targets and pushes them to ECR with the short git SHA as the tag. The nginx image gets the
same tag with the suffix `-nginx`. The registry is `lumenpress/wordpress` with immutable tags (OpenTofu page), so a SHA can
be pushed only once:

[source,bash]
----
#!/usr/bin/env bash
# Builds both targets of the Dockerfile and pushes them to ECR with the git SHA as the tag.
set -euo pipefail

account="123456789012"
region="eu-west-1"
repo="${account}.dkr.ecr.${region}.amazonaws.com/lumenpress/wordpress"
sha="$(git rev-parse --short=12 HEAD)"

aws ecr get-login-password --region "$region" \
  | docker login --username AWS --password-stdin "${account}.dkr.ecr.${region}.amazonaws.com"

docker build --target php   -t "${repo}:${sha}" .
docker build --target nginx -t "${repo}:${sha}-nginx" .

docker push "${repo}:${sha}"
docker push "${repo}:${sha}-nginx"
echo "Pushed ${sha}"
----

Source: https://docs.aws.amazon.com/AmazonECR/latest/userguide/docker-push-ecr-image.html[Amazon ECR User Guide: Pushing a Docker image]

In CI the same steps run from GitHub Actions with an OIDC role (see
xref:cms/wordpress/releases-upgrades-and-autoscaling-on-kubernetes.adoc[Releases, Upgrades and Autoscaling on Kubernetes]).
Before pushing, a local smoke test starts both images the way the pod does: read-only root file system, tmpfs for `/tmp`,
UID 33 for PHP, nginx sharing the PHP container's network namespace:

[source,bash]
----
#!/usr/bin/env bash
# Starts the two images the way the pod does (read-only, non-root, one shared network
# namespace) and probes the endpoints the probes use. No database is needed for these.
set -euo pipefail

tag="${1:?usage: smoke-test.sh <image-tag>}"
repo="lumenpress/wordpress"

cleanup() { docker rm -f lp-php lp-nginx >/dev/null 2>&1 || true; }
trap cleanup EXIT

docker run -d --name lp-php --read-only --tmpfs /tmp --user 33:33 "${repo}:${tag}" >/dev/null
docker run -d --name lp-nginx --network container:lp-php --read-only --tmpfs /tmp \
  "${repo}:${tag}-nginx" >/dev/null
sleep 3

probe() {
  docker run --rm --network container:lp-php curlimages/curl:8.15.0 -s -m 5 -o /dev/null \
    -w "$1 -> %{http_code}\n" "http://127.0.0.1:8080$1"
}
probe /healthz
probe /fpm-ping
probe /readyz.php
probe /wp-includes/js/jquery/jquery.min.js
probe /wp-content/uploads/shell.php

docker logs lp-php 2>&1 | tail -n 3
----

Source: https://docs.docker.com/reference/cli/docker/container/run/[Docker Docs: docker container run]

== Cluster prerequisites

Three things are created once per cluster, outside the chart: the namespace (with the restricted Pod Security level, which
the chart's pods satisfy), the `ClusterSecretStore` of External Secrets Operator and the Auto Mode `IngressClass`.

Source: https://external-secrets.io/latest/provider/aws-secrets-manager/[External Secrets Operator: AWS Secrets Manager]

The manifests were checked with `kubeconform -strict -ignore-missing-schemas`; the two custom resources are skipped because
their schemas are not in the default catalog, so a typo in a CRD field is caught only by the cluster. Notes:

* *Pod Identity for the operator.* The `ClusterSecretStore` has no `auth` block, so the operator uses the credentials of its
  own pod, which the Pod Identity association from the OpenTofu page provides for the service account `external-secrets` in the namespace
  `external-secrets`. The operator is installed from its Helm chart (`helm repo add external-secrets
  https://charts.external-secrets.io` and `helm install external-secrets external-secrets/external-secrets -n
  external-secrets --create-namespace`); the exact way the operator picks up Pod Identity credentials is described on its
  AWS authentication page, so check that page for your operator version.
* *Auto Mode `IngressClass`.* With EKS Auto Mode the certificate belongs in `IngressClassParams` (the ARN is the output
  `site_certificate_arn`) and the WAF web ACL is an annotation on the Ingress, because the class parameters do not
  support it. With the self-managed AWS Load Balancer Controller the same class uses the controller name
  `ingress.k8s.aws/alb` and annotations carry the certificate; the comparison is in
  xref:cloud/aws/eks-microservices.adoc[Deploying Microservices on EKS].
* *The `restricted` level.* A pod that runs as a non-root user, drops all capabilities, forbids privilege escalation and
  uses the default seccomp profile satisfies it, which the Deployment does.

The details that make this Deployment production-shaped:

* *Rollout.* `maxUnavailable: 0` with a surge keeps full capacity during a release: a new pod must pass readiness before an old
  one is removed. A `preStop` sleep of ten seconds gives the load balancer time to deregister the pod before nginx stops,
  and `terminationGracePeriodSeconds` covers it plus in-flight requests.
* *Replicas.* `replicas` is omitted when the HPA is enabled, so a `helm upgrade` does not reset the scaled count.
* *Spread.* Two topology spread constraints (zone and node) with `ScheduleAnyway` prefer an even spread without blocking
  scheduling when capacity is short; use `DoNotSchedule` for the zone constraint when a zone outage must never leave the
  site on one zone.
* *Security.* Pod level: `fsGroup: 33` and the default seccomp profile. Container level: non-root user, no privilege escalation,
  read-only root file system and all capabilities dropped. The only writable paths are two `emptyDir` volumes for
  `/tmp` and the uploads volume; the code is not writable.
* *Probes.* The startup probe protects slow starts, the FPM liveness probe is a TCP check on port 9000, nginx liveness is
  `/healthz` and readiness is `/readyz.php`. After a database failover the pods become unready for the duration of the
  failover and rejoin by themselves.
* *Resources.* Requests drive scheduling and the HPA's CPU percentage; the memory limit is the OOM kill line. Size the FPM
  container from `pm.max_children` times the memory a request uses: 16 workers at an assumed 40 MB each is why the limit is 768 MiB; measure your own plugins.
  There is no CPU limit, so a pod can use idle CPU; add one if noisy neighbours are a problem.
* *Config rollout.* The `checksum/config` annotation changes when the ConfigMap changes, which rolls the pods.

Source: https://helm.sh/docs/topics/charts_hooks/[Helm Docs: Chart hooks]

A WordPress update can include a database schema change that `wp core update-db` applies. The hook Job runs it with the new
image before Helm rolls out the new Deployment, so the new pods never see an old schema. The details to know:

* The hook is `pre-upgrade`, not `pre-install`: on the first install the database is empty and the install Job creates the
  schema. The `before-hook-creation` delete policy removes a previous Job of the same name so the hook can run again.
* The Job uses the application database user in this example. The design with a separate `wp_migrate` user that holds the
  schema-altering privileges, and the choice to give the application user data privileges only, is described on
  xref:cms/wordpress/managed-database-rds-and-aurora.adoc[Managed Database: RDS and Aurora]; to use it, point the hook at a second Secret key.
* A pre-upgrade hook runs while the old pods still serve traffic. The migration must therefore be compatible with the
  old code for the duration of the rollout, which is the standard expand-and-contract discipline. WordPress core schema
  changes are, in practice, additive.
* If the Job fails, `helm upgrade` fails and nothing is rolled out. The full sequence and rollback limits are on
  xref:cms/wordpress/releases-upgrades-and-autoscaling-on-kubernetes.adoc[Releases, Upgrades and Autoscaling on Kubernetes].

The first install is a Job, run by a person or a pipeline once per empty database: `wp core is-installed` makes it safe to
run twice, `wp core install` creates the tables, the administrator and the first post, and `wp rewrite structure` stores
pretty permalinks in the database (no `.htaccess` is needed with nginx). The administrator password is read from a
separate secret, `lumenpress/prod/wordpress-install`, and never appears in the values. The shell body of this Job passed
`shellcheck`. The Job is not a Helm hook, so `helm upgrade --wait` waits for it and the release fails if it does. Disable it again
(`install.enabled=false`) once the site exists: a Job's pod template cannot be changed in place, so an upgrade that
changes the image with the Job still enabled is rejected.

== First deployment

The deployment script ties the pieces together. The commands are the ones run for production, once the OpenTofu apply is
done, the secrets are seeded and the image is pushed:

[source,bash]
----
#!/usr/bin/env bash
# First deployment of the chart to lumenpress-prod, then the checks.
set -euo pipefail

sha="${1:?usage: deploy.sh <git-sha>}"
region="eu-west-1"

aws eks update-kubeconfig --name lumenpress-prod --region "$region"

# Once per cluster: the namespace, the ClusterSecretStore and the IngressClass.

  --namespace lumenpress \
  --set image.tag="$sha" \
  --set install.enabled=true \

kubectl -n lumenpress rollout status deployment/lumenpress-web
kubectl -n lumenpress get pods,ingress,hpa,pdb,cronjob
kubectl -n lumenpress logs job/lumenpress-install

# helm upgrade lumenpress ./lumenpress-wordpress -n lumenpress --reuse-values --set install.enabled=false --set image.tag="$sha"

== Common problems

* *Redirect loop on the dashboard.* `X-Forwarded-Proto` is not reaching PHP or `WP_HOME` is `http://`. Check the
  ALB listener (HTTPS to HTTP target) and the value in the ConfigMap.
* *Pods stay `Pending` on the PVC.* The persistent volume has the wrong file system or access point ID, or the EFS add-on is
  not healthy. `kubectl describe pvc` and the events of the CSI driver show the mount error.
* *`CreateContainerConfigError`.* The Secret `lumenpress-secrets` does not exist yet: the ExternalSecret has not synced, for
  example because the secret has no value yet. `kubectl describe externalsecret` shows the provider error.
* *HTTP 500 on every request, `Configuration error` in the logs.* A required environment variable is missing; the log line names
  it.
* *Upload fails with a permission error.* The EFS access point owner is not UID 33, or the volume was mounted without it.
  The access point of the OpenTofu configuration fixes ownership.
* *The migrate hook fails with `Error establishing a database connection`.* The hook runs before the new ConfigMap and
  Secret values reach the pod if they changed in the same upgrade; change them in a separate release.
* *`helm upgrade` fails with an immutable field.* The install Job is still enabled with a new image, or a selector was changed.
  Disable the Job; never change `spec.selector` of a Deployment in place.
* *Admin cannot install plugins.* Intended: `DISALLOW_FILE_MODS`. Plugins arrive through the image.
