= Categories, Tags and Comments
:description: How WordPress 7.1 organizes posts with categories and tags, and how it receives, moderates and stores comments: the default category, the comment lifecycle, the moderation queue, every Discussion setting, moderation and disallowed keys, Akismet, pingbacks and trackbacks, and comment policies.
:keywords: WordPress, categories, tags, default category, taxonomy, comments, comment moderation, moderation queue, Discussion settings, disallowed comment keys, moderation keys, Akismet, pingbacks, trackbacks, XML-RPC, Gravatar, comment policy, WP-CLI, wp term, wp comment, Lumen Press

include::partial$cms-wordpress-disclaimer.adoc[]

Categories and tags are the two taxonomies every WordPress site has for posts, and comments are the built-in
discussion system attached to them. Site owners and editors decide the categories, the tagging conventions and the
discussion policy; administrators decide how much moderation the site needs and whether spam filtering, pingbacks
and avatars are worth their cost. This page covers the screens, the options behind them, the exact rules WordPress
applies to an incoming comment, and the WP-CLI commands that do the same work in bulk.

This page was written against WordPress 7.1.3 (released 2026-10-06; 7.1.4, a security release of 2026-10-28, is the
version to run in production), PHP 7.4 minimum and 8.3+ recommended, WP-CLI 2.12.0 and the Akismet 5.7.2 plugin bundled
with the 7.1.3 download, and checked on 2026-10-28. Every option value,
command output and moderation result below comes from a fresh 7.1.3 installation. WordPress 7.2 (in beta, planned for
2026-12-08) announces no change to categories, tags or comment moderation so far.

== Categories and tags

Both are taxonomies of the `post` post type, stored in the same tables (`wp_terms`, `wp_term_taxonomy`,
`wp_term_relationships`, see xref:cms/wordpress/database-schema.adoc[Database Schema]). They differ in how they are
meant to be used.

[cols="1,2,2",options="header"]
|===
| | Categories (`category`) | Tags (`post_tag`)

| Purpose | A small, planned table of contents of the site: the broad sections a reader browses | Free, specific keywords
  that connect posts across sections
| Hierarchy | Yes: a category can have a parent | No: flat list
| Required | Every post has at least one; a post saved without one gets the default category | Optional; a post can have none
| Editor panel | Checkbox tree in the post sidebar (Categories) | Free-text field with suggestions (Tags)
| Admin screen | Posts > Categories | Posts > Tags (with a "Popular Tags" cloud of the 45 most used)
| Default archive URL | `/category/<slug>/` (base set by the `category_base` option) | `/tag/<slug>/` (base set by `tag_base`)
| Template (block themes) | `category.html`, `category-<slug>.html`, then `archive.html` | `tag.html`, `tag-<slug>.html`, then `archive.html`
| REST collection | `/wp/v2/categories` | `/wp/v2/tags`
|===

A practical rule for Lumen Press: categories describe *what kind* of post it is (News, Events, Book fairs, Reviews),
and tags describe *what it is about* (an imprint such as "Lumen Noir", a genre, an author's name). Pages have neither
by default. The book catalogue does not use categories or tags at all: the `lp_book` post type has its own taxonomies
`lp_genre` (hierarchical) and `lp_series` (flat), registered by the `lumen-catalog` plugin in
xref:cms/wordpress/custom-post-types-and-taxonomies.adoc[Custom Post Types and Taxonomies]. Mixing catalogue terms into
the blog's tags would put "crime fiction" the genre and "crime fiction" the news topic into one archive.

Names and slugs follow two rules that the official screen documentation states more strictly than the code applies
them. A category name must be unique *among its siblings*, not across the whole taxonomy: two categories called
"Reviews" with different parents are accepted, and WordPress gives the second one a slug suffixed with its parent's
slug (`reviews-book-fairs`). Slugs, by contrast, are unique per taxonomy.

=== The default category

Every installation starts with the category "Uncategorized" (term ID 1). The option `default_category` (Settings >
Writing > Default Post Category) names the category given to any post saved without one, including posts created by
WP-CLI, the REST API and importers. Three consequences follow:

* The default category cannot be deleted. Its row on Posts > Categories has no Delete link, `wp_delete_term()` returns
  `0` for it, and the REST API refuses the delete.
* Renaming "Uncategorized" is fine and common; the term ID stays 1, so nothing breaks.
* Deleting any other category does not delete posts: posts whose only category it was are moved to the default
  category. Child categories of a deleted category move up to its parent (or become top-level).

The following session, run against the Compose environment of the next section, sets up the Lumen Press news
categories, makes "News" the default, renames and then deletes "Uncategorized", and shows where the posts end up.

[source,bash]
----
wp term create category News --slug=news --description="Announcements from Lumen Press" --porcelain   # 2
wp term create category Events --slug=events --porcelain                                              # 3
wp term create category "Book fairs" --slug=book-fairs --parent=3 --porcelain                         # 4
wp term update category 1 --name=General --slug=general
wp option update default_category 2

wp post create --post_title="Lumen Noir at the autumn book fair" --post_status=publish \
  --post_category=4 --tags_input="Lumen Noir,crime fiction" --porcelain                                # 4
wp post create --post_title="No category given" --post_status=publish --porcelain                      # 5
wp term list category --fields=term_id,name,slug,parent,count

wp term delete category 1          # "General": its posts move to the default category
wp term delete category 3          # "Events": its child "Book fairs" becomes top-level
wp term list category --fields=term_id,name,parent,count
wp term delete category 2          # the default category: refused
----
Source: https://developer.wordpress.org/cli/commands/term/[WP-CLI: wp term], https://developer.wordpress.org/cli/commands/term/delete/[WP-CLI: wp term delete]

[source,text]
----
term_id	name	slug	parent	count
4	Book fairs	book-fairs	3	1
3	Events	events	0	0
1	General	general	0	1
2	News	news	0	1

term_id	name	parent	count
4	Book fairs	0	1
2	News	0	2

Warning: category 2 doesn't exist.
Success: Term already deleted.
----

The post without a category was filed under News, the sample "Hello world!" post moved from General to News when
General was deleted (count 2), and "Book fairs" lost its deleted parent. The last two lines are misleading: WP-CLI
2.12.0 reports the refused deletion of the default category as "already deleted", although the term is still there.
Change `default_category` first, then delete. The `count` column counts direct assignments only; a parent category's
archive still lists the posts of its children.

=== Assigning terms

In the editor, the post sidebar has a Categories panel (checkboxes, with "Add New Category" for users who can manage
categories) and a Tags panel (type and press Enter or comma). Editors and Administrators have the
`manage_categories` capability; Authors and Contributors can pick existing categories and add new tags, but cannot
create categories. On Posts > All Posts, Bulk Edit adds categories and tags to many posts at once (it never removes
them). With WP-CLI, `wp post term add|set|remove` changes the terms of one post:

[source,bash]
----
wp post term add 4 post_tag "author interviews"
wp post term set 4 category news book-fairs --by=slug     # replaces the post's categories
wp post term list 4 category post_tag --fields=term_id,name,taxonomy
----
Source: https://developer.wordpress.org/cli/commands/post/term/[WP-CLI: wp post term]

=== Converting between categories and tags

Sites often start with too many categories. Converting a category to a tag (or the reverse) keeps its posts:

* `+wp term migrate <term> --from=category --to=post_tag+` moves one term and its relationships to the other taxonomy and
  removes the original.
* In the dashboard, the "Categories and Tags Converter" importer (Tools > Import, installed on demand as the
  `wpcat2tag-importer` plugin) converts several at once.

[source,bash]
----
wp term create post_tag Interviews --porcelain
wp term migrate interviews --by=slug --from=post_tag --to=category
----
Source: https://developer.wordpress.org/cli/commands/term/migrate/[WP-CLI: wp term migrate]

[source,text]
----
Term 'interviews' migrated.
Old instance of term 'interviews' removed from its original taxonomy.
Success: Migrated the term 'interviews' from taxonomy 'post_tag' to taxonomy 'category' for 0 posts.
----

The migrated term gets a new term ID, so links that used `?cat=<id>` break; links by slug keep working. If term
counts look wrong after a migration or a direct database edit, `wp term recount category post_tag` recalculates them.

=== Showing categories and tags

In a block theme the terms appear through blocks, not template tags. The 7.1.3 core blocks are:

[cols="1,1,3",options="header"]
|===
| Block | Name | Shows

| Terms List | `core/categories` | A list or dropdown of the terms of any taxonomy (categories by default; the block name still says `categories`)
| Tag Cloud | `core/tag-cloud` | Terms sized by usage, for any non-hierarchical taxonomy
| Post Terms | `core/post-terms` | The current post's terms of one taxonomy, usually in a Query Loop or single template
| Terms Query, Term Template, Term Name, Term Count, Term Description | `core/terms-query` and its children | A loop over terms with its own layout, the term equivalent of the Query Loop
|===

Archive titles come from the Query Title block, and the archive's description from Term Description. Classic themes use
`the_category()`, `the_tags()`, `get_the_term_list()` and `wp_list_categories()` (see
xref:cms/wordpress/classic-theme-anatomy-and-the-loop.adoc[Classic Theme Anatomy and The Loop]). The URL bases
`category` and `tag` can be renamed on Settings > Permalinks (see
xref:cms/wordpress/settings-screens.adoc[Settings Screens]); renaming them on a live site needs redirects.

== Comments

A comment is a row in `wp_comments` attached to a post (`comment_post_ID`), optionally to a parent comment
(`comment_parent`, for threads) and optionally to a registered user (`user_id`). Anonymous commenters are identified
only by the name, email and URL they typed, plus the IP address and user agent WordPress records.

=== Comment types and statuses

The `comment_type` column distinguishes what the row is:

[cols="1,3",options="header"]
|===
| `comment_type` | Meaning

| `comment` | A reader's comment (stored as an empty string before 5.5)
| `pingback` | An automatic notice that another site linked to a post, verified by fetching the linking page
| `trackback` | A manually sent notice carrying a title and excerpt, not verified
| `note` | An editorial Note left in the block editor (6.9+); never shown on the front end and excluded from comment counts, see xref:cms/wordpress/block-editor-for-authors.adoc[Block Editor for Authors]
|===

The status lives in `comment_approved`:

[cols="1,1,3",options="header"]
|===
| Stored value | Shown as | Meaning

| `1` | Approved | Visible on the site
| `0` | Pending | In the moderation queue, visible only to the commenter (in their browser, through the
  "awaiting moderation" preview) and to moderators
| `spam` | Spam | Hidden; Akismet and moderators put comments here; listed under Comments > Spam
| `trash` | Trash | Hidden; restorable until `EMPTY_TRASH_DAYS` (30 by default) deletes it
| `post-trashed` | (not listed) | The parent post was trashed; restoring the post restores the comment's previous status
|===

=== The lifecycle of a comment

A comment submitted through the comment form goes to `wp-comments-post.php`, which calls
`wp_handle_comment_submission()` and then `wp_new_comment()`. The order of the checks explains most moderation
surprises.

[mermaid]
....
flowchart TD
    A[Comment form submitted] --> B{Comments open, required fields present, logged in if required?}
    B -- no --> X[Rejected with an error page]
    B -- yes --> C[preprocess_comment filter: Akismet checks here]
    C --> D{Duplicate or flood?}
    D -- duplicate --> X2[409 Duplicate comment detected]
    D -- flood --> X3[429 Posting too quickly]
    D -- no --> E{Post author or user with moderate_comments?}
    E -- yes --> TR[Approved, no further checks]
    TR --> H
    E -- no --> F{check_comment passes?}
    F -- yes --> OK[Approved]
    F -- no --> P[Pending]
    OK --> G{Matches Disallowed Comment Keys?}
    P --> G
    G -- yes --> T[Trash]
    T --> H
    G -- no --> H[pre_comment_approved filter: Akismet can return spam]
    H --> I[wp_insert_comment and notification emails]
....

* *Gatekeeping* (`wp_handle_comment_submission()`): the post must exist, be published (or viewable) and have comments
  open; name and email are required when `require_name_email` is on; a login is required when
  `comment_registration` is on. Field lengths are capped (245 characters for the name, 100 for the email, 200 for the
  URL, 65,525 for the content).
* *Duplicate and flood checks* (`wp_allow_comment()`): an identical comment by the same author on the same post is
  rejected with HTTP 409, and a second comment from the same IP address or email within 15 seconds with HTTP 429.
  Users with `moderate_comments` are exempt from the flood check.
* *Trust*: comments by the post's author or by a user with `moderate_comments` (Editors, Administrators) are approved
  without further checks.
* *`check_comment()`* holds a comment (status `0`) if manual approval is on, if it has at least `comment_max_links`
  links, if any moderation key matches, or, when "previously approved" is on, if the same name *and* email have no
  approved comment yet. Since 7.1, a pingback from the same site is approved without moderation.
* *Disallowed Comment Keys* (`wp_check_comment_disallowed_list()`) override everything except the trust rule: a match
  sends the comment to the Trash, or to Spam when `EMPTY_TRASH_DAYS` is `0`. The HTML is stripped first, so splitting a
  word with tags does not bypass it.
* *`pre_comment_approved`* is the last word on the status; Akismet hooks here, and so can a site plugin.
* After insertion, `comments_notify` and `moderation_notify` decide who gets an email (see below).

=== The Comments screen and the moderation queue

Comments (with a bubble showing the pending count, also shown in the admin bar) lists comments newest first, with
filters All, Mine, Pending, Approved, Spam and Trash, and a type filter (Comments or Pings). Editorial Notes are
stored in the same table but never listed here. Hovering a row shows
Approve/Unapprove, Reply, Quick Edit, Edit, Spam and Trash; the bulk actions are Unapprove, Approve, Mark as Spam and
Move to Trash. Clicking an IP address filters all comments from it, which is the quickest way to deal with a burst
from one source. The Spam and Trash views have "Empty Spam" and "Empty Trash" buttons, which delete permanently every
comment in the view, selected or not. The Dashboard's Activity widget shows the latest comments with the same actions.

Who can moderate: Administrators and Editors have `moderate_comments` and can act on every comment. The `edit_comment`
meta capability maps to `edit_post` on the comment's post, so an Author can approve, edit, spam and trash the comments
on *their own* published posts, and receives the "held for moderation" email for them, although the role has no
`moderate_comments`. The official "Comment moderation" article says Authors have no moderation rights and get no
email; WordPress 7.1.3 behaves as described here (checked with `+user_can( $author_id, 'edit_comment', $comment_id )+`).
Contributors cannot edit published posts and therefore cannot moderate.

=== Discussion settings

Settings > Discussion stores every choice as an option. The table gives the option names (useful for WP-CLI, `wp
option get` and deployment scripts) and the defaults of a fresh 7.1.3 installation.

[cols="3,2,1,3",options="header"]
|===
| Setting | Option | Default | Notes

4+| *Default post settings* (copied into each new post; existing posts keep their own values)
| Attempt to notify any blogs linked to from the post | `default_pingback_flag` | `1` | Sends pingbacks on publish
| Allow link notifications from other blogs (pingbacks and trackbacks) | `default_ping_status` | `open` | Becomes the post's `ping_status`
| Allow people to submit comments on new posts | `default_comment_status` | `open` | Becomes the post's `comment_status`; pages and custom post types are created closed unless the type's own default says otherwise
4+| *Other comment settings*
| Comment author must fill out name and email | `require_name_email` | `1` | Nothing is verified
| Users must be registered and logged in to comment | `comment_registration` | `0` | Combine with Membership on Settings > General
| Automatically close comments on old posts / days | `close_comments_for_old_posts`, `close_comments_days_old` | `0`, `14` | Applies to posts only unless filtered
| Show comments cookies opt-in checkbox | `show_comments_cookies_opt_in` | `1` | Since 4.9.6; without consent no commenter cookie is set
| Enable threaded (nested) comments / levels | `thread_comments`, `thread_comments_depth` | `1`, `5` | Up to 10 levels
| Break comments into pages / per page / default page / order | `page_comments`, `comments_per_page`, `default_comments_page`, `comment_order` | `0`, `50`, `newest`, `asc` | Paginated comments create extra URLs (`/comment-page-2/`)

| Anyone posts a note | `wp_notes_notify` | `1` | Editorial Notes (6.9+)
4+| *Before a comment appears*
| Comment must be manually approved | `comment_moderation` | `0` | Every non-trusted comment goes to Pending
| Comment author must have a previously approved comment | `comment_previously_approved` | `1` | Named `comment_whitelist` before 5.5
4+| *Comment Moderation*
| Number of links to allow before holding | `comment_max_links` | `2` | A comment with *this many or more* links is held; `0` disables the check
| Moderation keys (text area) | `moderation_keys` | empty | One word or IP per line
4+| *Disallowed Comment Keys*
| Disallowed keys (text area) | `disallowed_keys` | empty | Named `blacklist_keys` before 5.5; matches go to the Trash
4+| *Avatars*
| Show Avatars | `show_avatars` | `1` |
| Maximum Rating | `avatar_rating` | `G` | G, PG, R or X
| Default Avatar | `avatar_default` | `mystery` | Mystery Person, Blank, Gravatar Logo or a generated image
|===

The two remaining discussion-related options live elsewhere: `default_category` on Settings > Writing, and
`ping_sites` (Update Services, `https://rpc.pingomatic.com/` by default) on Settings > Writing, which only appears when
the site is not discouraging search engines. All of them can be read and set with WP-CLI:

[source,bash]
----
wp option get comment_moderation        # 0
wp option update comment_max_links 2
wp option update moderation_keys "$(printf 'giveaway\nfree download')"
wp option update disallowed_keys "$(printf 'casino\n203.0.113.66')"
wp option update close_comments_for_old_posts 1
wp option update close_comments_days_old 30
wp option update default_pingback_flag 0
wp option update default_ping_status closed
----
Source: https://developer.wordpress.org/cli/commands/option/update/[WP-CLI: wp option update], https://wordpress.org/documentation/article/settings-discussion-screen/[Settings Discussion screen]

The old option names still answer: `+get_option( 'blacklist_keys' )+` returns `disallowed_keys` and
`+get_option( 'comment_whitelist' )+` returns `comment_previously_approved`, with a deprecation notice. Only the new
names exist in `wp_options`, so SQL queries and `+wp option list --search+` must use them.

=== Moderation keys and disallowed keys in practice

The script below submits five comments as anonymous readers, with the settings of the previous section, and prints
the status WordPress gives each one. It calls `wp_new_comment()` directly, the same function the comment form ends in,
so it exercises the real rules without a browser. `pre_wp_mail` short-circuits the notification emails, since the
container has no mail server.

[source,php]
----
<?php
// moderation-check.php: run with "wp eval-file moderation-check.php <post-id>".
add_filter( 'pre_wp_mail', '__return_false' );

$post_id = (int) ( $args[0] ?? 0 );
$cases   = array(
	'first comment'  => array( 'Ana Reader', 'ana@example.org', '198.51.100.1', 'Loved the fair, see you next year.' ),
	'two links'      => array( 'Ben', 'ben@example.org', '198.51.100.2', 'See <a href="https://a.example">a</a> and <a href="https://b.example">b</a>.' ),
	'moderation key' => array( 'Cai', 'cai@example.org', '198.51.100.3', 'Is there a giveaway?' ),
	'disallowed IP'  => array( 'Dee', 'dee@example.org', '203.0.113.66', 'Hello.' ),
	'disallowed key' => array( 'Eve', 'eve@example.org', '198.51.100.5', 'Best <b>cas</b>ino bonus' ),
);

foreach ( $cases as $label => $c ) {
	$id = wp_new_comment(
		wp_slash(
			array(
				'comment_post_ID'      => $post_id,
				'comment_author'       => $c[0],
				'comment_author_email' => $c[1],
				'comment_author_url'   => '',
				'comment_author_IP'    => $c[2],
				'comment_agent'        => 'wp-cli',
				'comment_content'      => $c[3],
				'comment_type'         => 'comment',
			)
		),
		true // Return a WP_Error instead of calling wp_die().
	);
	printf( "%-15s %s\n", $label, is_wp_error( $id ) ? $id->get_error_code() : wp_get_comment_status( $id ) );
}
----
Source: https://developer.wordpress.org/reference/functions/wp_new_comment/[Code Reference: wp_new_comment()], https://developer.wordpress.org/reference/functions/check_comment/[Code Reference: check_comment()]

[source,text]
----
$ wp eval-file moderation-check.php 4
first comment   unapproved
two links       unapproved
moderation key  unapproved
disallowed IP   trash
disallowed key  trash
----

The first comment is held although it is harmless, because "Comment author must have a previously approved comment"
is on by default: a new reader's first comment always waits. Once a moderator approves it, the next comment from the
same name and email is approved immediately (after 15 seconds; sooner it is rejected as a flood, and the same text
again as a duplicate):

[source,bash]
----
wp comment approve "$(wp comment list --status=hold --author_email=ana@example.org --format=ids)"
----
Source: https://developer.wordpress.org/cli/commands/comment/approve/[WP-CLI: wp comment approve]

Three properties of the keys matter when writing them:

* Matching is a case-insensitive *substring* search over the content, author name, email, URL, IP address and user
  agent. "press" matches "WordPress" and "Lumen Press", and an IP line such as `203.0.113.6` also matches
  `203.0.113.66`. Prefer whole, unusual words and full addresses.
* Keys are literal text. WordPress escapes every line with `preg_quote()` before matching, so regular expressions and
  wildcards do not work, although the official "Comment moderation" article still lists regular expressions as an
  option.
* A disallowed match goes to the Trash, not to oblivion: the settings screen says "it will be put in the Trash", while
  the older wording in the official screen documentation ("marked as spam", "deleted without warning") predates the
  current behaviour. Trashed comments still disappear permanently after `EMPTY_TRASH_DAYS`.

The "previously approved" rule trusts a name and email pair that anyone can type. It is a convenience for regular
readers, not an identity check; a site that needs real identities requires registration (`comment_registration`).

=== Managing comments with WP-CLI

`wp comment` covers every status change of the Comments screen, which makes bulk clean-ups and scripted moderation
possible.

[source,bash]
----
wp comment list --status=hold --fields=comment_ID,comment_author,comment_content
wp comment approve 3
wp comment spam 4 && wp comment status 4        # spam
wp comment unspam 4 && wp comment status 4      # unapproved (back to its previous status)
wp comment trash 4 && wp comment untrash 4
wp comment delete $(wp comment list --status=trash --format=ids) --force   # permanent
wp comment create --comment_post_ID=4 --comment_parent=2 --user_id=1 \
  --comment_author="Lumen Press" --comment_content="Thank you, Ana!" --porcelain
wp comment count
----
Source: https://developer.wordpress.org/cli/commands/comment/[WP-CLI: wp comment], https://developer.wordpress.org/cli/commands/comment/count/[WP-CLI: wp comment count]

[source,text]
----
approved:        5
spam:            0
trash:           0
post-trashed:    0
all:             6
moderated:       1
total_comments:  6
----

`wp comment delete` without `+--force+` only trashes. `wp comment create` bypasses every moderation rule (it inserts the
row directly), so it is for imports and tests, not for simulating readers; `wp comment recount <post-id>` fixes a
post's cached `comment_count` after direct database changes.

=== Closing comments

Each post has its own `comment_status` and `ping_status` (the Discussion panel of the post sidebar, or Quick Edit and
Bulk Edit on the posts list). The Discussion setting only provides the value for new posts, so turning comments off
site-wide needs a bulk update as well:

[source,bash]
----
wp post update $(wp post list --post_type=post --format=ids) --comment_status=closed --ping_status=closed
----
Source: https://developer.wordpress.org/cli/commands/post/update/[WP-CLI: wp post update]

"Automatically close comments on old posts" works differently: it changes nothing in the database. The functions
`+_close_comments_for_old_post()+` and `+_close_comments_for_old_posts()+` make `comments_open()` and `pings_open()` return
false at request time when the post's `post_date_gmt` is older than the limit, and only for the post types in the
`close_comments_for_post_types` filter (`post` by default). On the test site, with a 30-day limit and a post dated
January 2025:

[source,bash]
----
wp post update 1 --post_date="2025-01-15 10:00:00" --post_date_gmt="2025-01-15 10:00:00"
wp eval 'var_dump( comments_open( 1 ), get_post( 1 )->comment_status );'
----
Source: https://developer.wordpress.org/reference/functions/comments_open/[Code Reference: comments_open()]

[source,text]
----
bool(false)
string(4) "open"
----

Changing only `+--post_date+` of a published post leaves `post_date_gmt` untouched, and the check uses the GMT date.
Switching the option off reopens every old post instantly, which is the main advantage over a bulk update.

=== Comments in themes, the REST API and privacy

Block themes display comments with the Comments block (`core/comments`), whose inner blocks are the Comments Title,
Comment Template (author name, avatar, date, content, reply and edit links), Comments Pagination and Comments Form
(`core/post-comments-form`). The Latest Comments and Comments Count blocks show comments elsewhere. Threading and
pagination follow the Discussion settings. Classic themes use `comments_template()`, `wp_list_comments()` and
`comment_form()`; the `comment_form_defaults` filter changes the form in both kinds of theme, as the plugin below
does.

The REST API lists approved comments publicly at `/wp/v2/comments` (moderators also see the others with `status`), but
does not accept anonymous comments unless the `rest_allow_anonymous_comments` filter returns true:

[source,bash]
----
curl -s -H 'Content-Type: application/json' \
  -d '{"post":4,"author_name":"Zed","author_email":"zed@example.org","content":"Hi"}' \
  'http://localhost:8080/?rest_route=/wp/v2/comments'
----
Source: https://developer.wordpress.org/rest-api/reference/comments/[REST API Handbook: Comments], https://developer.wordpress.org/reference/hooks/rest_allow_anonymous_comments/[Code Reference: rest_allow_anonymous_comments]

[source,json]
----
{"code":"rest_comment_login_required","message":"Sorry, you must be logged in to comment.","data":{"status":401}}
----

A headless front end such as the Lumen Press reader app (see xref:cms/wordpress/headless-wordpress.adoc[Headless
WordPress]) either posts comments as logged-in users or enables the filter and adds its own spam protection, because
the comment form's Akismet fields and cookies are not involved.

Comments are personal data. Each row stores the commenter's email, IP address and user agent; the opt-in cookies keep
name, email and URL in the browser; and when avatars are shown, every page view sends a hash of each commenter's
email to Gravatar (current core uses SHA-256 hashes). Core's personal-data exporter and eraser (Tools > Export
Personal Data and Erase Personal Data) include comments, and the privacy policy page should name comments, Gravatar
and Akismet. Turning off Show Avatars removes the third-party request entirely. The broader topic is in
xref:cms/wordpress/seo-analytics-and-privacy.adoc[SEO, Analytics and Privacy] and, for plugin authors,
xref:cms/wordpress/privacy-and-personal-data.adoc[Privacy and Personal Data].

== Akismet

Akismet is the anti-spam service run by Automattic. Its plugin ships in the WordPress download (5.7.2 in the 7.1.3
package) but is *inactive*, and it does nothing until it has an API key. The key comes from an Akismet account: the
Personal plan is "name your price" for non-commercial sites, and commercial sites need a paid plan. The plugin sends
each comment's content, author fields, IP address, user agent and referrer to Akismet's servers, which is why it
belongs in the privacy policy.

How it fits the lifecycle: Akismet checks the comment on `preprocess_comment`, before core's rules, and returns its
verdict through `pre_comment_approved`, so a comment that core would approve can still end in Spam. Spam caught by
Akismet is deleted automatically after 15 days (filter `akismet_delete_comment_interval`); the Akismet settings page
can instead discard the most pervasive spam without storing it (`akismet_strictness`). Marking a comment as spam or
not spam on the Comments screen reports it back to Akismet, which trains the service.

[source,bash]
----
wp plugin activate akismet
wp help akismet              # check, recheck_queue, stats
wp akismet recheck_queue     # re-check every Pending comment
----
Source: https://wordpress.org/plugins/akismet/[Akismet Anti-spam plugin]

Without a key, `wp akismet stats` stops with "API key must be set to fetch stats." and `recheck_queue` reports every
comment as "could not be checked". On servers managed as code, the key can be set with
`+define( 'WPCOM_API_KEY', getenv( 'AKISMET_API_KEY' ) );+` in `wp-config.php` instead of the `wordpress_api_key`
option, which keeps it out of database dumps. Akismet is one option, not a requirement: other services and plugins
(challenge-based tools, honeypots, comment forms behind a login) do the same job, and many small sites manage with
moderation alone. Avoid stacking several anti-spam plugins; they hook the same filters and make results hard to
explain.

== Pingbacks and trackbacks

When a post links to another site, WordPress can notify it: a *pingback* is an XML-RPC call (`pingback.ping` to the
endpoint advertised by the target's `X-Pingback` header or `<link rel="pingback">`), and the receiver fetches the
linking page to verify the link before creating a `pingback` comment. A *trackback* is an HTTP POST with a title and
excerpt that the sender types in manually; nothing is verified, and since the block editor there is no Send Trackbacks
field outside the Classic Editor. Outgoing pings run in the background through WP-Cron (`do_all_pings()`), and
`ping_sites` (Update Services) is a separate mechanism that tells ping services about new posts.

Many sites turn both off:

* Trackbacks are almost entirely spam, because anyone can forge them.
* Pingbacks are verified, but the XML-RPC method makes the site fetch arbitrary URLs, which has been used for
  distributed denial-of-service reflection, and incoming pingbacks are mostly low-value link notices.
* Internal links make a site ping itself (a "self-ping"), which adds pingback comments under the site's own older
  posts. Since 7.1, same-site pingbacks are approved automatically instead of filling the moderation queue.

Also since 7.1, pingbacks and trackbacks are switched off automatically, in both directions, whenever the environment
type is not `production` (the `wp_should_disable_pings_for_environment` filter overrides it), so a staging copy no
longer pings the sites it links to. The test site on this page sets no `WP_ENVIRONMENT_TYPE` and therefore counts as
production; see xref:cms/wordpress/security-hardening.adoc[Security Hardening].

The Discussion checkboxes switch off pings for *new* posts only; existing posts keep `ping_status = open`, and the
`X-Pingback` header keeps advertising the endpoint on every single post that allows pings:

[source,bash]
----
curl -sI http://localhost:8080/?p=5 | grep -i x-pingback
----
Source: https://developer.wordpress.org/reference/hooks/wp_headers/[Code Reference: wp_headers]

[source,text]
----
X-Pingback: http://localhost:8080/xmlrpc.php
----

Lumen Press disables them completely with a must-use plugin, which also links the comment form to the comment policy
and extends the automatic closing of comments to pages. A must-use plugin cannot be deactivated from the dashboard,
which suits a site-wide policy (see xref:cms/wordpress/plugin-fundamentals.adoc[Plugin Fundamentals]).

[source,php]
----
<?php
/**
 * Plugin Name: Lumen Discussion
 * Description: Lumen Press discussion policy: no pingbacks or trackbacks, a comment policy link and auto-closing on pages.
 * Version:     1.0.0
 * Requires at least: 7.0
 * Requires PHP: 7.4
 * License:     GPL-2.0-or-later
 */

defined( 'ABSPATH' ) || exit;

// 1. Pingbacks: stop answering them over XML-RPC and stop advertising the endpoint.
add_filter(
	'xmlrpc_methods',
	static function ( array $methods ): array {
		unset( $methods['pingback.ping'], $methods['pingback.extensions.getPingbacks'] );
		return $methods;
	}
);

add_filter(
	'wp_headers',
	static function ( array $headers ): array {
		unset( $headers['X-Pingback'] );
		return $headers;
	}
);

// 2. Pings are closed everywhere, whatever the per-post "Allow pings" checkbox says.
add_filter( 'pings_open', '__return_false' );

// 3. Do not send pingbacks to our own posts when an article links to another one.
add_action(
	'pre_ping',
	static function ( array &$links ): void {
		$home = home_url();
		foreach ( $links as $i => $link ) {
			if ( str_starts_with( $link, $home ) ) {
				unset( $links[ $i ] );
			}
		}
	}
);

// 4. Show the comment policy above every comment form.
add_filter(
	'comment_form_defaults',
	static function ( array $defaults ): array {
		$policy = get_page_by_path( 'comment-policy' );
		if ( $policy instanceof WP_Post ) {
			$defaults['comment_notes_before'] .= sprintf(
				'<p class="comment-policy">%s <a href="%s">%s</a>.</p>',
				esc_html__( 'Comments are moderated according to our', 'lumen-discussion' ),
				esc_url( get_permalink( $policy ) ),
				esc_html__( 'comment policy', 'lumen-discussion' )
			);
		}
		return $defaults;
	}
);

// 5. Auto-close comments on old pages too (core only closes posts).
add_filter(
	'close_comments_for_post_types',
	static function ( array $post_types ): array {
		$post_types[] = 'page';
		return $post_types;
	}
);
----
Source: https://developer.wordpress.org/reference/hooks/xmlrpc_methods/[Code Reference: xmlrpc_methods], https://developer.wordpress.org/reference/hooks/pings_open/[Code Reference: pings_open], https://developer.wordpress.org/reference/hooks/pre_ping/[Code Reference: pre_ping], https://developer.wordpress.org/reference/hooks/comment_form_defaults/[Code Reference: comment_form_defaults], https://developer.wordpress.org/reference/hooks/close_comments_for_post_types/[Code Reference: close_comments_for_post_types]

Saved as `wp-content/mu-plugins/lumen-discussion.php`, it loads on every request. `str_starts_with()` is PHP 8.0,
but WordPress provides a polyfill, so the plugin also runs on PHP 7.4. A check with the test site:

[source,bash]
----
wp plugin list --status=must-use --fields=name,status,version
wp post create --post_type=page --post_title="Comment policy" --post_name=comment-policy --post_status=publish
wp eval 'var_dump( pings_open( 5 ) ); echo implode( ",", apply_filters( "close_comments_for_post_types", array( "post" ) ) ), "\n";'
curl -sI http://localhost:8080/?p=5 | grep -ci x-pingback
----
Source: https://developer.wordpress.org/cli/commands/plugin/list/[WP-CLI: wp plugin list]

[source,text]
----
name	status	version
lumen-discussion	must-use	1.0.0
bool(false)
post,page
0
----

If nothing on the site uses XML-RPC at all (no mobile app, no Jetpack, no remote publishing), disabling the whole
endpoint at the web server is stronger still; see xref:cms/wordpress/security-hardening.adoc[Security Hardening].
Removing the methods with `xmlrpc_methods` is the minimal, application-level step.

== Comment policies

Software settles *how* comments are moderated; a published comment policy settles *what* is accepted, and gives
moderators something to point to. Older books for site owners (*WordPress All-in-One For Dummies* in particular)
rightly recommend writing one. A useful policy for a site like Lumen Press states:

* who moderates, and that comments are moderated before or after they appear;
* what is removed: spam, personal attacks, off-topic promotion, links to unrelated commercial sites, and personal
  data about third parties;
* whether links are allowed (the `comment_max_links` threshold makes it an enforced rule);
* that the site keeps the commenter's name, email and IP address, uses Akismet and Gravatar if it does, and how to
  request export or erasure (linking the privacy policy);
* that comments close after a set time (30 days for Lumen Press) and why.

Publish it as an ordinary page (`comment-policy` on Lumen Press) and link it from the comment form, as the plugin above
does. Applying the policy consistently matters more than its wording: an editor who approves a link-heavy comment one
day and trashes a similar one the next teaches regular readers that the rules are arbitrary.

== Where older books and tutorials are outdated

[cols="2,3",options="header"]
|===
| Older statement | Current behaviour (7.1.3)

| The "Comment Blacklist" and "comment whitelist" settings, `blacklist_keys`, `comment_whitelist` | Renamed in 5.5 to
  Disallowed Comment Keys (`disallowed_keys`) and "previously approved" (`comment_previously_approved`); the old names
  only survive as deprecated aliases in `get_option()`
| Blocklisted comments are deleted, or marked as spam | They go to the Trash (to Spam only when `EMPTY_TRASH_DAYS` is `0`)
| Moderation keys accept regular expressions | Every line is matched literally (escaped with `preg_quote()`), as a substring
| Category names must be unique across the site | Unique among siblings; the slug is what must be unique
| The "Categories" widget and sidebar tag cloud | In block themes, the Terms List and Tag Cloud blocks in templates or
  patterns; widgets remain only in classic themes
| Akismet is free | Free only under the "name your price" personal plan for non-commercial sites; it also needs an
  account and API key
| Send Trackbacks is a standard editor field | Only in the Classic Editor; the block editor has no trackback field
| Self-pingbacks land in the moderation queue | Since 7.1 they are approved automatically; disabling pings removes them altogether
| Gravatar URLs use an MD5 hash of the email | Current core uses SHA-256
|===

The complete list for the whole sub-section is in
xref:cms/wordpress/where-older-books-and-tutorials-are-outdated.adoc[Where Older Books and Tutorials Are Outdated].

== Common errors and pitfalls

* *"Duplicate comment detected" or "You are posting comments too quickly"*: the 409 and 429 checks of
  `wp_allow_comment()`. Testing the form twice in a row triggers them; they are not a server fault.
* *Every first comment is held*: expected with "previously approved" on. Turn it off only if another filter (manual
  approval, Akismet) protects the site.
* *A moderation key catches too much*: substrings match inside words, URLs and user agents. A key like "bot" holds every
  comment whose user agent contains "bot".
* *Comments still open on old posts after changing Discussion settings*: the defaults apply to new posts only; use Bulk
  Edit or `wp post update` for existing ones, or the automatic closing option.
* *Comments missing from a page*: pages and most custom post types are created with comments closed, and the theme's
  template must contain a Comments block. A custom post type also needs `comments` in its `supports`.
* *Moderation emails never arrive*: notifications use `wp_mail()`, which depends on the server's mail setup; see
  xref:cms/wordpress/email-delivery.adoc[Email Delivery].
* *The default category cannot be deleted*: change Settings > Writing > Default Post Category first.
* *Term counts are wrong after an import or SQL edit*: run `wp term recount` and `wp comment recount`.
* *Spam filling the database*: Spam and Trash still occupy `wp_comments` and `wp_commentmeta`; empty them regularly or let
  Akismet's 15-day clean-up run (it needs WP-Cron, see xref:cms/wordpress/wp-cron-and-scheduled-tasks.adoc[WP-Cron and
  Scheduled Tasks]).
