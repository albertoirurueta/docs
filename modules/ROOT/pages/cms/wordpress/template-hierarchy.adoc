= Template Hierarchy
:description: How WordPress chooses the template for every front-end request in block and classic themes: the order of the query conditionals, the candidate list of each request type, block templates versus PHP files, and the template hierarchy and template_include filters, verified on WordPress 7.1.3.

Every front-end request ends with WordPress picking one template to render it: the file (or block template) that
draws a single book, the blog index, a genre archive or the "not found" page. The **template hierarchy** is the rule
that makes that choice. For each kind of request it lists candidate template names from the most specific (this one
book) to the most generic (any single post), takes the first one that exists, and falls back to `index` when nothing
else matches. The same rule serves block themes, whose templates are `+templates/*.html+` files or templates edited in
the Site Editor, and classic themes, whose templates are PHP files. Theme developers need it to know which file to
create; plugin developers need its filters to add candidates or supply templates of their own.

This page was written against WordPress 7.1.3 (released 2026-10-06; 7.1.4, a security release of 2026-10-28, is the
version to run in production), PHP 7.4 minimum and 8.3+ recommended, theme.json version 3 and WP-CLI 2.12.0, and checked
on 2026-10-28. WordPress 7.2 is in beta and due in December 2026; no change to
the hierarchy has been announced for it. Every candidate list on this page was logged from real requests to a 7.1.3
site running the Lumen Press block theme `lumen` and classic theme `lumen-classic` (see
<<_seeing_the_hierarchy_on_a_real_site>>).

The files a block theme ships and the blocks inside them are described in
xref:cms/wordpress/block-theme-templates-and-template-parts.adoc[Templates and Template Parts]; classic template files
and The Loop in xref:cms/wordpress/classic-theme-anatomy-and-the-loop.adoc[Classic Theme Anatomy and The Loop]. This
page covers only how one of them is chosen.

== How the template loader works

`index.php` loads `wp-blog-header.php`, which runs the main query (`wp()`) and then includes
`wp-includes/template-loader.php`. The loader runs in four steps:

. It fires the `template_redirect` action. Redirects belong here (with `wp_safe_redirect()` and `exit`); loading a
  different template here does not, because any `exit` skips later `template_redirect` callbacks.
. Feeds, `robots.txt`, `favicon.ico` and trackbacks are handled and the loader returns; a `HEAD` request exits here too
  (filter `exit_on_http_head`).
. It tests **seventeen conditionals in a fixed order**: `is_embed()`, `is_404()`, `is_search()`, `is_front_page()`,
  `is_home()`, `is_privacy_policy()`, `is_post_type_archive()`, `is_tax()`, `is_attachment()`, `is_single()`,
  `is_page()`, `is_singular()`, `is_category()`, `is_tag()`, `is_author()`, `is_date()`, `is_archive()`. For the
  first that is true it calls the matching getter (`get_embed_template()`, `get_404_template()` and so on; the post
  type archive getter returns nothing unless the post type has `has_archive`). If the getter finds nothing, the loader
  **keeps going down the list**; that is how a front page with no `front-page` template ends up with the `page`
  template. When nothing is found, it calls `get_index_template()`.
. It passes the result through the `template_include` filter, resolves it with `realpath()` and includes it only if
  it is an existing, readable `.php` or `.html` file. The action `wp_before_include_template` (6.9) fires just before
  the include.

Source: https://github.com/WordPress/WordPress/blob/7.1.3/wp-includes/template-loader.php[WordPress 7.1.3: wp-includes/template-loader.php]

Each getter builds an array of candidate file names and hands it to `get_query_template( $type, $templates )`, which:

. strips everything but `a-z`, `0-9` and `-` from the type, which is why the front-page hook is `frontpage` and the
  privacy-policy hook `privacypolicy`;
. applies the `+{type}_template_hierarchy+` filter (4.7) to the candidate list;
. calls `locate_template()`, which returns the first candidate that exists as a PHP file in the child theme, then the
  parent theme, then `wp-includes/theme-compat/` (since 7.1.2 a name containing `..` is only accepted if it resolves
  inside one of those directories);
. calls `locate_block_template()` (5.8), which looks for a block template and, if it finds one, returns
  `wp-includes/template-canvas.php` and stores the block template in globals;
. applies the `+{type}_template+` filter to the resulting path.

The same candidate names serve both kinds of theme: they are always written with a `.php` suffix, and the block
template layer strips it to get a template slug (`single-lp_book.php` becomes the slug `single-lp_book`, matched by
`templates/single-lp_book.html`). The official Theme Handbook writes the hierarchy with `.html` names for block themes;
the order is identical.

Source: https://developer.wordpress.org/reference/functions/get_query_template/[Code Reference: get_query_template()]

Details that the table compresses:

* **Slugs with non-ASCII characters** are tried decoded first and then URL-encoded (`page-über` before
  `page-%c3%bcber`), for categories, tags, terms, pages and single posts (4.7). Taxonomy terms then try the term ID
  (`taxonomy-lp_genre-2`), which 6.9 added; categories and tags have had the ID form for much longer.
* **Custom templates** come first for singular content. For a classic theme it is the file named in the post's
  `+_wp_page_template+` meta, declared with a `Template Name:` header (and `Template Post Type:` since 4.7 for posts
  and custom post types). For a block theme it is a slug declared in the `customTemplates` section of `theme.json`
  (with `postTypes` for anything but pages) or created in the Site Editor. The stored value goes into the list as is:
  a block template slug such as `page-no-title` appears without a `.php` suffix. A value that names a template the
  active theme does not have is skipped silently.
* **`singular`** (4.3) is reached only when no single or page template exists; a theme that wants one template for
  every post, page and book ships `singular` and no `single`/`page`.
* **`home`** is the posts index, not the front page. A site that shows "Your latest posts" on the front page tests
  `front-page`, then `home`, then `index`.
* **Post type archives** go through `get_archive_template()`, so they are logged under the `archive` hook type, not
  a hook of their own. A post type registered without `has_archive` has no archive URL and the getter returns nothing.
* **Author and date archives** fall back to `archive` because `is_archive()` is also true for them; the loader moves
  down the conditional list rather than having a fallback encoded in the getter.
* **Attachment pages** are disabled on installations created since 6.4 (option `wp_attachment_pages_enabled` is `0`),
  and their URLs redirect to the file. The attachment hierarchy applies only where the option is `1`, which upgrades
  from older versions keep. Since 4.3 the MIME candidates run from most to least specific.
* **Embeds** are not supported by the block template system. A custom embed template must be a PHP file in the theme
  root, in a block theme too; without one, WordPress uses `wp-includes/theme-compat/embed.php` instead of `index`.
* **`paged.php`** and **`comments-popup.php`** are no longer part of the hierarchy (`get_paged_template()` is
  deprecated since 4.7). A `+paged_template_hierarchy+` hook is still documented, but the loader never fires it.

== Block templates and PHP files

`locate_block_template()` runs only when the active theme supports `block-templates`: every block theme, and a classic
theme that opts in with `+add_theme_support( 'block-templates' )+` (5.8) so that users can create templates in the
editor. It works like this:

. If `locate_template()` already found a PHP file, the candidate list is **cut after that file**: a block template is
  used only if it is at least as specific. A block theme that ships `single-lp_book.php` in its root and only
  `templates/single.html` renders books with the PHP file; if it also ships `templates/single-lp_book.html`, the block
  template wins the tie.
. `resolve_block_template()` queries every block template whose slug is in the remaining list and sorts them by the
  list's order. For one slug, the sources rank **user-edited template** (a `wp_template` post saved from the Site
  Editor) over the **theme file** (child theme `templates/`, then parent) over a **plugin-registered template**
  (`register_block_template()`, 6.7).
. One child-theme rule: when the child theme has a PHP file and the parent theme a block template with the same slug,
  the child's PHP file is used.
. If a block template is found, its markup is stored in the `+$_wp_current_template_content+` global, its ID in
  `+$_wp_current_template_id+` (6.3; the admin bar's "Edit template" link uses it), and the function returns
  `template-canvas.php`, the file that prints the document around the rendered blocks. An empty template shows a
  warning to logged-in users (6.8).
. If none is found and no PHP file was either, the function returns an empty string and the loader moves on to the
  next conditional; for the `index` type it still returns the canvas, so a block theme's `templates/index.html` is the
  final fallback. That file is what makes a theme a block theme.

Source: https://developer.wordpress.org/reference/functions/locate_block_template/[Code Reference: locate_block_template()]

The default template types the Site Editor offers in "Add template" are `index`, `home`, `front-page`, `singular`,
`single`, `page`, `archive`, `author`, `category`, `taxonomy`, `date`, `tag`, `attachment`, `search`,
`privacy-policy` and `404`, plus per-object variants (a specific book, a specific genre) built from the same patterns.
There is no `embed` entry, consistent with embeds being PHP only.

== The hierarchy filters

Three families of hooks change the result, from the most targeted to the bluntest:

[cols="2,3,1",options="header"]
|===
| Hook | Receives and returns | Since
| `+{type}_template_hierarchy+` | The candidate array, before any lookup. Add, remove or reorder names. Works for block and classic themes alike, because both use the same list. | 4.7
| `+{type}_template+` | The located path (a PHP file or `template-canvas.php`), plus `$type` and `$templates` (4.8). | 1.5
| `template_include` | The final path, for every request type. Return another file to render with it. | 3.0
| `pre_get_block_templates`, `get_block_templates`, `get_block_template` | The block template objects (to supply or alter templates without files) | 5.9
| `template_redirect` | Nothing to return: redirect and exit. Not a place to load templates. | 1.5
|===

Source: https://developer.wordpress.org/reference/hooks/type_template_hierarchy/[Code Reference: \{type}_template_hierarchy]

=== Adding candidates: a template per genre

Lumen Press wants literary fiction titles to look different from children's books without assigning a template to
each book. The `lumen-catalog` plugin inserts `+single-lp_book-{genre}+` names before `single-lp_book`, so the theme
can ship `templates/single-lp_book-literary-fiction.html` (block) or `single-lp_book-literary-fiction.php` (classic),
and both are picked up by the normal lookup.

[source,php]
----
<?php
/**
 * Adds "single-lp_book-{genre}" candidates, so a theme can style each genre's books.
 *
 * File: wp-content/plugins/lumen-catalog/includes/genre-templates.php
 */

defined( 'ABSPATH' ) || exit;

add_filter( 'single_template_hierarchy', 'lumen_catalog_genre_templates' );

function lumen_catalog_genre_templates( $templates ) {
	$book = get_queried_object();
	if ( ! $book instanceof WP_Post || 'lp_book' !== $book->post_type ) {
		return $templates;
	}

	$genres = get_the_terms( $book, 'lp_genre' );
	if ( ! is_array( $genres ) ) {
		return $templates;
	}

	$extra = array();
	foreach ( $genres as $genre ) {
		$extra[] = 'single-lp_book-' . sanitize_file_name( $genre->slug ) . '.php';
	}

	// Insert the genre templates just before "single-lp_book.php".
	$position = array_search( 'single-lp_book.php', $templates, true );
	array_splice( $templates, false === $position ? 0 : $position, 0, $extra );

	return $templates;
}
----
Source: https://developer.wordpress.org/reference/hooks/type_template_hierarchy/[Code Reference: \{type}_template_hierarchy]

The plugin's main file loads it with `+require __DIR__ . '/includes/genre-templates.php';+`. With a template for the
genre in each theme, the logged requests show the new candidate and its winner:

[source,text]
----
lumen /books/the-glass-orchard/
  single        single-lp_book-the-glass-orchard.php single-lp_book-literary-fiction.php single-lp_book.php single.php
  => wp-includes/template-canvas.php
  => block template lumen//single-lp_book-literary-fiction (source: theme)
lumen-classic /books/the-glass-orchard/
  single        single-lp_book-the-glass-orchard.php single-lp_book-literary-fiction.php single-lp_book.php single.php
  => wp-content/themes/lumen-classic/single-lp_book-literary-fiction.php
----
Source: https://developer.wordpress.org/themes/templates/template-hierarchy/[Theme Handbook: Template Hierarchy]

Candidate names become file paths, so anything derived from content goes through `sanitize_file_name()` (or
`sanitize_key()`) first; never build a name from raw request input.

=== Supplying templates from a plugin

A plugin that adds a post type should not depend on every theme shipping a template for it. `lumen-catalog` provides
a default for both kinds of theme: for block themes it registers a block template with `register_block_template()`
(6.7), which a theme file or a user-edited template of the same slug overrides; for classic themes it falls back to its
own PHP file through `template_include` when the theme has no `single-lp_book.php`.

[source,php]
----
<?php
/**
 * Default book templates for themes that do not ship their own.
 *
 * File: wp-content/plugins/lumen-catalog/includes/templates.php
 */

defined( 'ABSPATH' ) || exit;

/*
 * Block themes: register "single-lp_book" in the template registry (WordPress 6.7+).
 * A theme file or a user-edited template with the same slug wins over it.
 */
add_action( 'init', 'lumen_catalog_register_block_templates' );

function lumen_catalog_register_block_templates() {
	if ( ! function_exists( 'register_block_template' ) ) {
		return;
	}

	register_block_template(
		'lumen-catalog//single-lp_book',
		array(
			'title'       => __( 'Single Book', 'lumen-catalog' ),
			'description' => __( 'Displays a single book of the catalogue.', 'lumen-catalog' ),
			'content'     => (string) file_get_contents( dirname( __DIR__ ) . '/templates/single-lp_book.html' ),
			'post_types'  => array( 'lp_book' ),
		)
	);
}

/*
 * Classic themes: use the plugin's PHP template when the theme has no single-lp_book.php.
 */
add_filter( 'template_include', 'lumen_catalog_template_include' );

function lumen_catalog_template_include( $template ) {
	if ( wp_is_block_theme() || ! is_singular( 'lp_book' ) ) {
		return $template;
	}

	if ( '' !== locate_template( array( 'single-lp_book.php' ) ) ) {
		return $template;
	}

	return dirname( __DIR__ ) . '/templates/single-lp_book.php';
}
----
Source: https://developer.wordpress.org/reference/functions/register_block_template/[Code Reference: register_block_template()], https://developer.wordpress.org/reference/hooks/template_include/[Code Reference: template_include]

`the_title()`, `the_terms()` for `lp_genre`, `the_content()`, `get_footer()`), as described in
xref:cms/wordpress/classic-theme-anatomy-and-the-loop.adoc[Classic Theme Anatomy and The Loop].

Two details show in that output. A registered template's ID uses the **active theme's** slug
(`twentytwentyfive//single-lp_book`), not the plugin name; its `source` is `plugin` and its `plugin` property
`lumen-catalog`. And the registry template outranks a PHP file of equal specificity in a block theme exactly as a
theme's `.html` file would: on `lumen` with `single-lp_book.php` in the theme root and no `.html` for books, the
plugin's block template was used until it was unregistered; only then did the PHP file render.

A `template_include` callback must return a path to an existing `.php` or `.html` file: in 7.1 anything else is not
included, and an Administrator sees the theme's errors (if any) instead of a page. Callbacks that load a template from
`template_redirect` and `exit` break every later callback on that action.

== Seeing the hierarchy on a real site

A must-use plugin that hooks every `+{type}_template_hierarchy+` filter at the last priority and `template_include`
records which candidates each request produced and what was finally included. It does nothing unless `WP_DEBUG` is
on, writes to a file under `uploads/` (readable over HTTP on a misconfigured server, so use it only on a local site),
and must not be deployed to production.

[source,php]
----
<?php
/**
 * Plugin Name: Lumen Template Debug
 * Description: Logs the template candidates and the chosen template of every front-end request. Development only.
 *
 * File: wp-content/mu-plugins/lumen-template-debug.php
 */

defined( 'ABSPATH' ) || exit;

if ( ! defined( 'WP_DEBUG' ) || ! WP_DEBUG ) {
	return;
}

/*
 * Every query type that get_query_template() can pass to "{$type}_template_hierarchy".
 */
$lumen_template_types = array(
	'embed', '404', 'search', 'frontpage', 'home', 'privacypolicy', 'taxonomy',
	'attachment', 'single', 'page', 'singular', 'category', 'tag', 'author',
	'date', 'archive', 'paged', 'index',
);

foreach ( $lumen_template_types as $lumen_type ) {
	add_filter(
		"{$lumen_type}_template_hierarchy",
		static function ( $templates ) use ( $lumen_type ) {
			$GLOBALS['lumen_template_trace'][] = sprintf( '  %-13s %s', $lumen_type, implode( ' ', $templates ) );
			return $templates;
		},
		PHP_INT_MAX
	);
}

add_filter(
	'template_include',
	static function ( $template ) {
		global $_wp_current_template_id;

		$lines   = $GLOBALS['lumen_template_trace'] ?? array();
		$lines[] = '  => ' . str_replace( ABSPATH, '', $template );
		if ( ! empty( $_wp_current_template_id ) ) {
			$block_template = get_block_template( $_wp_current_template_id );
			$lines[]        = sprintf(
				'  => block template %s (source: %s)',
				$_wp_current_template_id,
				$block_template ? $block_template->source : 'unknown'
			);
		}

		error_log(
			sprintf( "%s %s\n%s\n", get_stylesheet(), $_SERVER['REQUEST_URI'], implode( "\n", $lines ) ),
			3,
			WP_CONTENT_DIR . '/uploads/lumen-template-debug.log'
		);

		return $template;
	},
	PHP_INT_MAX
);
----
Source: https://developer.wordpress.org/reference/hooks/type_template_hierarchy/[Code Reference: \{type}_template_hierarchy], https://developer.wordpress.org/reference/hooks/template_include/[Code Reference: template_include]

The `source` printed for a block template is `theme` for a file, `custom` for a template saved in the database and
`plugin` for a registered one.

=== The test site

The site runs the official Apache image (so real HTTP requests go through `index.php`) next to a WP-CLI container,
with the plugin, the mu-plugin and the two themes mounted read-only. It extends the standard stack of
xref:cms/wordpress/local-development-environments.adoc[Local Development Environments]; the passwords are
placeholders for a local machine. Inside the Compose network the web container answers as `lumenpress.test` over plain
HTTP, so the site URL is `http://lumenpress.test` rather than the `https://lumenpress.test/` of a full local setup.

== What older books get wrong or leave out

* The classic-theme-only book on professional WordPress development presents the hierarchy as a list of PHP files and
  says nothing of block templates; the same order applies to `+templates/*.html+`, with user-edited and
  plugin-registered templates in front of or behind the theme's files as described above. Its dating of full site
  editing to WordPress 5.4 to 5.6 is also wrong: block themes and the Site Editor shipped in 5.9.
* The *All-in-One For Dummies* and *Ultimate WordPress Handbook* books do not cover the template hierarchy at all;
  site owners meet it as the Site Editor's template list (see
  xref:cms/wordpress/site-editor-and-global-styles.adoc[Site Editor and Global Styles]).
* Older tutorials still list `paged.php` (dropped in 4.7) and `comments-popup.php`, omit `singular` (4.3),
  `+single-{post_type}-{slug}+` (4.4), the decoded-slug variants and `+Template Post Type+` (4.7), the privacy policy
  template (5.2) and `+taxonomy-{taxonomy}-{term_id}+` (6.9), and show attachment pages as always available (new sites
  have them off since 6.4).
* Some tutorials switch templates in `template_redirect` with `include` and `exit`; the supported way is
  `template_include` or the hierarchy filter. Plugins also no longer need to build `WP_Block_Template` objects by hand
  in `get_block_templates` filters: `register_block_template()` (6.7) does it.

== Common errors and pitfalls

[cols="2,3",options="header"]
|===
| Symptom | Cause and fix
| A new `single-lp_book.html` is ignored | A customized `single-lp_book` exists in the database (the Site Editor's version always wins), or the file is in the theme root instead of `templates/`. Reset the template in the Site Editor or delete the `wp_template` post.
| A block theme's PHP file is ignored | A block template of equal or higher specificity exists, including one registered by a plugin.
| The front page uses `page`, not `home` | "A static page" is selected in Settings > Reading; ship `front-page` for a dedicated design.
| `/books/` uses `index` or 404s | The post type lacks `has_archive`, or rewrite rules were not flushed after registering it (Settings > Permalinks > Save, or `wp rewrite flush`).
| `taxonomy-lp_genre.html` not used for a genre | The URL is a category or tag (those use `category`/`tag`), or the term slug differs from the file name; check the logged candidates.
| Attachment URL redirects to the image | Attachment pages are disabled (`wp_attachment_pages_enabled` is `0` on sites installed with 6.4+).
| `embed.html` has no effect | Embeds are PHP only; add `embed-lp_book.php` or `embed.php` to the theme root.
| A hook named `front_page_template_hierarchy` never fires | The type is sanitized: the hooks are `frontpage_…` and `privacypolicy_…`.
| A `template_include` callback yields a blank page | It returned a path that does not exist or does not end in `.php`/`.html`; 7.1 includes nothing in that case.
| A child theme's template is not used | Child files win only by name; a more specific parent file (for example `single-lp_book` in the parent and only `single` in the child) still wins, because specificity is checked before theme.
|===
