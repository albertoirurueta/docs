*Drupal* is a free and open-source content-management framework written in PHP on top of Symfony components. It stores
structured content in entities and fields, keeps site configuration in exportable YAML, renders pages through render
arrays and Twig, and exposes the same content through JSON:API, REST, GraphQL and the Model Context Protocol. It runs
very large sites and small ones from the same code base, and its distinguishing strengths are content modelling,
roles and permissions, multilingual support, a configuration-management workflow and a long security track record. This
sub-section explains it from the first `composer create-project` to a module that syncs museum objects from an API and a
headless kiosk that reads them back.

== Who this sub-section is for

* *Site builders and editors* who model content types, fields, taxonomies, media, menus, blocks, views and layouts, set up
  roles and a moderation workflow, and write content in CKEditor 5 or Canvas without code.
* *Administrators* who install Drupal with Composer and DDEV, configure `settings.php` per environment, manage
  configuration between environments, apply security updates, tune caching and cron, back up and restore, and harden a
  production site.
* *Themers* who generate a theme with Starterkit, write Twig templates, preprocess functions, libraries and Single
  Directory Components, and make the result responsive, accessible and fast.
* *Module developers* who write modules with services, OOP hooks, plugins with PHP attributes, routes, forms, entities,
  queues, the Update and Migrate APIs, tests and Drush commands, and who ship them through CI.
* *Architects and front-end developers* who run Drupal as a headless back end behind Next.js, and teams that connect it
  to AI providers and AI agents.

== The running example: Meridian Museum

Every page uses one fictitious scenario, the *Meridian Museum*, a regional science museum whose site is built step by
step. The figure shows how the parts fit together.

image::cms-drupal-meridian-museum-map.svg["Map of the Meridian Museum site: content model, theme meridian, module meridian_collection, recipe meridian_events, a JSON:API kiosk and AI with MCP",width=760]

* *Content*: exhibitions (content type `exhibition` with dates, gallery and hero media), events (`event`, with a date range
  and ticket link), news, basic pages (Visit, Accessibility, About) and a *collection* of objects, a custom content entity
  `collection_object` with the fields `accession_number`, `period`, `material`, `dimensions` and `on_display`. The
  taxonomies are `topic` and `gallery`, and the media types are image, document and remote video.
* *People*: the roles Administrator, Content Editor, Curator, Reviewer and Member (a logged-in visitor), with a draft,
  review and published moderation workflow.
* *Languages*: English (default) and Spanish, with translated content, configuration and interface.
* *Theme*: `meridian`, generated with Starterkit, with Single Directory Components (`card`, `hero`, `exhibition-teaser`
  and `opening-hours`), responsive images and a Canvas code component, `ticket-banner`.
* *Module*: `meridian_collection`, with the custom entity, routes and a controller, a settings form, a service, an event
  subscriber, OOP hooks, the block plugin "On display now", a field formatter for accession numbers, a queue worker that
  syncs objects from a fictitious collections-management API, the Drush command `meridian:sync`, an Update API
  post-update, a Migrate source for a CSV import and an access policy for curators.
* *Recipe*: `meridian_events` (content type, fields, view and permissions), applied to a fresh site.
* *Operations*: DDEV locally, Docker Compose for CI, staging and production with configuration management, Redis,
  Varnish, cron, Automatic Updates and backups.
* *Headless and AI*: a Next.js gallery kiosk over JSON:API with Simple OAuth, the AI module generating alt text, and the
  MCP Server module exposing collection search to an AI agent.

No real names, tokens or credentials appear anywhere; secrets always come from environment variables or are obvious
placeholders.

== Check date and version baseline

Everything in this sub-section was checked against the official documentation on *2026-10-30*. The state of the platform
on that date is:

[cols="2,3,3",options=header]
|===
|Item |State on 2026-10-30 |What the pages assume

|Drupal 11
|11.4.0 was released on 2026-07-01 and 11.4.x is the current production branch (11.4.11 is its latest patch release). 11.5 is scheduled for December 2026.
|New sites start on Drupal 11.4. Examples are written for 11.4.x.

|Drupal 12
|Scheduled, not released: 12.0.0 is planned for the week of 2026-12-07. It requires PHP 8.5 and Symfony 8, and it refuses to update from 11.2 or earlier.
|Described as an upcoming event. xref:cms/drupal/preparing-for-drupal-12.adoc[Preparing for Drupal 12] explains how to get ready.

|Drupal 10
|End of life is scheduled for 2026-12-09. Its last minor is 10.6, and from 10.6 the upgrade target is 11.3 or later.
|No page recommends starting a new site on Drupal 10. xref:cms/drupal/upgrading-drupal-10-to-11.adoc[Upgrading Drupal 10 to 11] covers the move.

|Drush
|Drush 13 serves Drupal 10.2 and later and 11; Drush 14 serves 11.3 and later and 12.
|Install it per project with `composer require drush/drush`.

|PHP
|Drupal 11.4 runs on PHP 8.3 and later.
|Examples use PHP 8.3 or later syntax.
|===

Drupal uses semantic versioning: a feature minor ships about every six months (June and December), bugfix releases
usually come on the first Wednesday of a month and security releases on the third, and security advisories cover the two
most recent minors only. xref:cms/drupal/versions-release-cycle-and-support.adoc[Drupal Versions, Release Cycle and Support] explains the
cadence, the support windows and where to follow change records. Dates marked "scheduled" or "planned" are plans, not
facts.

Many older books and tutorials describe Drupal 10.0 or 10.1. They show plugin annotations (attributes since 10.2), hooks
only as `.module` functions (OOP hooks since 11.1), module upload from the administration UI (removed in 10.4 and 11.0),
the Article and Page content types created by the Standard profile (no longer created in 11.4), Drush commands
declared with annotations and a `drush.services.yml` file (gone in Drush 13) and Drupal 11 as a future release.
xref:cms/drupal/where-older-books-and-tutorials-are-outdated.adoc[Where Older Books and Tutorials Are Outdated] lists
each point with its correction.
