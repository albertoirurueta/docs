Everything an editor, site builder or administrator does after logging in happens in the _administration interface_: the
side or top menu that leads to the content, structure and configuration screens, and the _administration theme_ that
styles those screens. This page explains the pieces of that interface, how they are chosen and configured, what changes
between Drupal 11 and Drupal 12, and how to tailor the experience for the roles of a real site.

It was written against Drupal 11.4.x, with Drush 13 or 14 and PHP 8.3 or later, and the facts were checked against the
official documentation on 2026-10-30. Drupal 12.0.0 is scheduled for the week of 2026-12-07 and the end of life of
Drupal 10 for 2026-12-09, so both are described as upcoming. The running example is the _Meridian Museum_: the module
`meridian_collection`, the content types `exhibition` and `event`, and the roles Content Editor, Curator and Reviewer.

== The pieces of the administration interface

The administration interface is the sum of several independent parts, each of which can be replaced:

* _The navigation_: the menu that lists administration sections. Core offers two implementations, the older **Toolbar**
  module and the newer **Navigation** module.
* _The administration theme_: the theme used on `+/admin/*+` pages and, optionally, on content forms. Core ships **Claro**
  (the long-time default) and **Default Admin**, a theme based on the contributed Gin theme.
* _Shortcuts_: the **Shortcut** module lets each user keep a personal or shared list of favourite administration links.
* _Dashboards_: a landing page with widgets, provided by the contributed **Dashboard** module rather than by core.
* _The administration menu tree_: the `admin` menu and the menu links declared by modules in their
  `+*.links.menu.yml+` files (see xref:cms/drupal/menus-and-path-aliases.adoc[menus and path aliases]).

Because the parts are independent, changing the navigation does not change the theme and vice versa. A site can run
Navigation with Claro, or Toolbar with Default Admin. The combination of Default Admin and Toolbar has been reported to
need fixes in 11.4 (see the version notes below), which is one reason to treat Navigation as the supported pairing.

== The Navigation module

The Navigation module "provides the administration UI", in the words of its official documentation page. It presents the
administration tasks as a collapsible, vertical sidebar on the left of the screen. Choosing an entry opens a full-height
drawer with the deeper levels, and on small screens the navigation becomes a bar above the content that opens as an
overlay. The default menu is built for fast access to content creation and content management, which is what editors
need most; deeper configuration screens remain reachable through the menu blocks.

=== Versions and status

* It was introduced as an experimental module in the Drupal 10 and early 11 cycles, and became **stable in Drupal 11.3**
  (December 2025). The 11.3.0 announcement describes it as "a superior and more modern experience than the old Toolbar"
  and recommends installing it on all sites, most of all those with a large administration structure.
* On a site created by the Standard profile, or by recipes that follow it, Navigation is the navigation that replaces the
  Toolbar. Reports on the core change place the commit in March 2026, so the exact release in which a fresh Standard
  install starts with Navigation is best confirmed in the release notes of the version in use.
* In **Drupal 12** the Toolbar module (together with Shortcut) leaves core. Navigation is the navigation that remains in
  the core codebase.

=== Customising it

Navigation is built from blocks, so it is customised with the same ideas as the rest of the block system (compare
xref:cms/drupal/blocks-and-block-layout.adoc[blocks and block layout]):

* Site builders can add menu blocks, reorder them and add custom menus through the UI.
* The default logo can be replaced with the site's own, which is how the Meridian Museum shows its logo in the corner
  of the sidebar instead of the stock one.
* A module adds entries by declaring ordinary menu links under an existing administration parent. Entries placed under
  the content or structure parents appear in the corresponding section of the sidebar.

The permissions that control what a role sees are the permissions of the underlying routes, not a navigation-only
setting. A link is rendered only when the current user has access to its route, so a Content Editor never sees
_Configuration_ entries. The pages that appear for a given role can therefore be checked simply by logging in as that role
or with a test account created for that role.

=== Enabling it with Drush

[source,bash]
----
# Install the Navigation module and make it the active navigation.
drush pm:install navigation

# Remove the Toolbar once Navigation works for every role. Uninstalling a module deletes its configuration.
drush pm:uninstall toolbar

drush cache:rebuild
----

Source: https://www.drupal.org/docs/develop/core-modules-and-themes/core-modules/navigation-module[Navigation module]

Uninstalling Toolbar before Navigation is confirmed to work leaves the site without any administration menu; the
administration pages are then reachable only by typing their paths. When both are installed, two navigation systems render
at the same time, which wastes screen space and confuses editors, so one of them should be removed.

=== Adding a menu link for Meridian curators

[source,yaml]
----
# meridian_collection.links.menu.yml
meridian_collection.settings:
  title: 'Collection settings'
  description: 'Sync options and display rules for collection objects.'
  route_name: meridian_collection.settings
  parent: system.admin_config
  weight: 20

meridian_collection.collection_overview:
  title: 'Collection objects'
  route_name: entity.collection_object.collection
  parent: system.admin_content
  weight: 10
----

Source: https://www.drupal.org/docs/develop/creating-modules/defining-menu-links[Creating modules: Defining menu links]

The links show up in whichever navigation is installed, because both read the same menu tree. The route
`entity.collection_object.collection` is the listing route of the custom entity described in
xref:cms/drupal/custom-entity-types.adoc[custom entity types].

== The Toolbar module

The Toolbar module is the classic horizontal administration bar, with a tray that can be shown horizontally or vertically
and that lists the `admin` menu tree. It also hosts the _Shortcuts_ tray and the user links. It is lightweight and well
known, and many contributed modules extend it. The most common extension is **Admin Toolbar**, which turns the tray into a
drop-down menu and adds cache-flush and cron links. Admin Toolbar builds on the core Toolbar, and its project page does not
describe any integration with Navigation or Default Admin, so a site that moves to Navigation should check whether it still
needs the extension at all.

* The permission _Use the toolbar_ decides who sees it.
* In Drupal 12 the module is moved to a contributed project, and the same is true for Shortcut. A site on 11.3 or later that
  still uses them must either uninstall them or require the contributed projects with Composer before it upgrades.
  The 12.0.0 beta release notes warn against uninstalling an extension that is still needed, because that destroys its
  configuration and data.
* Older books such as _Drupal 10 Development Cookbook_ (2023) and _Drupal 10 Masterclass_ (2023) show the Toolbar as the
  administration menu. That is accurate for Drupal 10, but on a new Drupal 11.3 or later site the Navigation module is the
  menu to learn, and on Drupal 12 the Toolbar is no longer in core.

== The administration theme

An _administration theme_ is a normal theme that Drupal selects for administrative routes. Routes opt in with the
`+_admin_route+` option, and the theme negotiator (`system.theme.negotiator.admin_theme`) returns the theme stored in the
`admin` key of the `system.theme` configuration object. The same value is what the Appearance screen at
`/admin/appearance` calls the _Administration theme_.

[source,bash]
----
drush config:get system.theme
drush theme:install default_admin
drush config:set system.theme admin default_admin
drush cache:rebuild
----

Source: https://www.drupal.org/docs/develop/theming-drupal/theme-configuration-and-info-file[Theme configuration and info file]

=== Claro

Claro has been the default administration theme of core since Drupal 9. It is accessibility-focused, has no base theme and
is built from CSS custom properties. It remains in Drupal 11, but it is **not** the long-term choice: Claro is removed from
core in Drupal 12 and may be offered as a contributed theme for sites that want to keep it during an upgrade. The same
removal applies to Olivero and to the deprecated Stable 9 theme (see
xref:cms/drupal/removed-core-modules-and-replacements.adoc[removed core modules and replacements]).

=== Default Admin, the Gin-based theme

The Drupal core blog announced in June 2025 that the contributed **Gin** theme would replace Claro as the default admin
theme. The reasoning given was that Drupal then had two default admin themes, Claro in core and Gin in Drupal CMS, and that
every new administration feature had to work well with both. The approach was to develop a core-ready Gin in a separate branch,
remove its dependency on Claro, cut features that do not belong in core and add test coverage. The announcement targeted the
Drupal 11.3 timeframe, and the work landed later: in Drupal 11.4 (released 1 July 2026) the theme arrived as an
**experimental** core theme named **Default Admin**, with a dark mode option, while Claro stayed the default.

Facts about the theme, taken from its `default_admin.info.yml` in core:

* its machine name is `default_admin` and it has no base theme;
* it declares regions such as `header`, `pre_content`, `breadcrumb`, `highlighted`, `help`, `content`, `page_top`,
  `page_bottom` and `sidebar_first` (the sidebar is hidden by default);
* it overrides the assets of many core components through `libraries-override`, among them tabledrag, the status report,
  vertical tabs, dropbuttons, Field UI, Views UI, the media library and sticky table headers.

Because some sources refer to the theme only as "Admin" (the working name used while it was merged), searches for older
discussions should try both names.

In **Drupal 12** Default Admin is promoted from experimental to stable and replaces Claro as the administration theme.
Sites that stay on Claro until then should plan the change as a normal theme switch, because custom CSS written against
Claro class names and libraries does not carry over automatically.

=== Using the admin theme for content editing

Visitors never see the administration theme, but editors do whenever it is applied to content forms. The
_Administration theme_ section of `/admin/appearance` has a checkbox, "Use the administration theme when editing or
creating content", stored as `use_admin_theme` in the `node.settings` configuration object. It matters for two reasons:
the node form then looks the same as every other administration screen, and the tooling that styles the form (the sticky
action bar, the layout of the revision information) belongs to the administration theme and not to the front-end theme.

[source,yaml]
----
# config/sync/system.theme.yml (excerpt)
default: meridian
admin: default_admin

# config/sync/node.settings.yml (excerpt)
use_admin_theme: true
----

Source: https://www.drupal.org/docs/user_guide/en/extend-theme-admin.html[User Guide: Concept: Administrative Theme]

The permission _View the administration theme_ decides who is shown the administration theme at all. Users without it see
the default front-end theme on administrative pages, which is a frequent source of "my administration looks different for
some roles" reports. Grant it to every role that uses the administration screens. The related permission _Use the
administration pages and help_ (`access administration pages`) controls the overview pages under `/admin`.

== Shortcut

The Shortcut module gives each user a set of shortcut links. Each shortcut set is a configuration entity
(`shortcut.set.default` is the default); users with _Edit current shortcut set_ can add the page they are looking at with
the star icon, and administrators can create sets and assign them to roles. With the Toolbar the shortcuts tray lists them;
with Navigation a shortcut block shows them. In Drupal 12 Shortcut moves to a contributed project, so sites on 11.x that
depend on custom shortcut sets should add `drupal/shortcut` to `composer.json` before the upgrade, and should export the
sets with configuration management (see xref:cms/drupal/configuration-management.adoc[configuration management]) so that
they can be restored.

== Dashboards

Core has no dashboard. The **Dashboard** module, a contributed project that is also part of Drupal CMS, provides a landing
page of widgets and blocks that give each logged-in user a quick overview of the parts of the site that matter to them.
Its stable 2.x series (2.2.1 at the time of writing) works with Drupal ^11.2 and is covered by the Security Team. Several
dashboards can be defined, access to each is controlled by permissions, and users can change the layout and content of a
dashboard. For the Meridian Museum the useful dashboards are:

* one for the Content Editor role: drafts waiting for the editor, recently changed exhibitions and upcoming events;
* one for the Curator role: objects marked `on_display`, objects without an `accession_number` and the queue of items waiting
  to be synced from the collections-management API;
* one for the Reviewer role: content in the _review_ moderation state (see
  xref:cms/drupal/content-moderation-workflows-and-revisions.adoc[content moderation workflows and revisions]).

[source,bash]
----
composer require 'drupal/dashboard:^2.2'
drush pm:install dashboard
----

Source: https://www.drupal.org/project/dashboard[Dashboard project page]

== Customising the editor experience

Navigation and the administration theme are only the frame. The editor experience also depends on the following settings,
each described in more depth on its own page:

* _Roles and permissions_: give each role only the permissions it needs, so its menu stays short
  (xref:cms/drupal/users-roles-and-permissions.adoc[users, roles and permissions]).
* _Form display_: hide fields the role never uses and group the rest, in the content type's form display
  (xref:cms/drupal/content-types-and-fields.adoc[content types and fields]).
* _The text editor_: restrict formats and toolbar buttons per role
  (xref:cms/drupal/text-formats-and-ckeditor-5.adoc[text formats and CKEditor 5]).
* _Media_: use the media library widget so editors pick images instead of uploading them again
  (xref:cms/drupal/media-and-media-library.adoc[media and the media library]).
* _Visual page building_: Drupal CMS 2.x makes Canvas the default editing experience
  (xref:cms/drupal/canvas-visual-page-building.adoc[Canvas]); Layout Builder stays in core
  (xref:cms/drupal/layout-builder.adoc[Layout Builder]).
* _Workflow_: moderation states and transitions shown as buttons on the edit form.

The page xref:cms/drupal/theming-overview-and-render-pipeline.adoc[theming overview and the render pipeline] explains how
the front-end theme and the administration theme coexist.

== Common errors and pitfalls

* _Two navigations at once_: installing Navigation without uninstalling Toolbar shows both. Pick one.
* _Lost menu after uninstalling Toolbar_: the Navigation module must be installed first and checked with an editor account.
* _Default Admin with Toolbar_: in Drupal 11.4 the theme dropped its Toolbar integration and left an override that pointed to
  a missing stylesheet, which was fixed in 11.4.x (core issue 3612540). Maintainers prefer removing the override as part of
  dropping Toolbar support from the theme, so combining the two is unsupported ground. Admin Toolbar was also reported
  to show large top padding under Default Admin 11.4.1 (core issue 3609859), whose resolution was not confirmed.
* _Content forms in the front-end theme_: the _Administration theme when editing or creating content_ box is unchecked, or the
  role lacks _View the administration theme_.
* _Custom CSS that targets Claro_: selectors and libraries written for Claro do not apply to Default Admin; use a
  sub-theme or the `libraries-extend` key of a small custom theme.
* _Removed modules before an upgrade_: uninstalling Toolbar, Shortcut or Claro to "fix" an upgrade check deletes their
  configuration; require the contributed project instead.
* _Caching_: a menu link added by a module appears only after `drush cache:rebuild` because the menu tree is cached.

== Security notes

* The administration theme and navigation hide links but do not grant or deny access. Access is always decided by route
  permissions and entity access, so a hidden link must never be treated as protection.
* Keep `/admin` behind HTTPS, strong passwords and, for privileged roles, a second factor (see
  xref:cms/drupal/security-hardening.adoc[security hardening]).
* Avoid giving the `administer themes` and `administer permissions` permissions to anyone below the Administrator role:
  a theme switch changes every page of the site.
* Contributed navigation add-ons run JavaScript for administrators on every page. Install only supported projects and keep
  them updated (see xref:cms/drupal/updates-composer-and-security-advisories.adoc[updates, Composer and security advisories]).

== Preparing for Drupal 12

Run these checks on a copy of the site while it is on 11.3 or later:

[source,bash]
----
# Which of the affected extensions are installed?
drush pm:list --status=enabled --type=module | grep -E 'toolbar|shortcut|navigation'
drush config:get system.theme admin
drush theme:list --status=enabled
----

Source: https://www.drupal.org/project/drupal/releases/12.0.0-beta1[Drupal 12.0.0-beta1 release notes]

The upgrade path is described in xref:cms/drupal/preparing-for-drupal-12.adoc[preparing for Drupal 12], and the replacement
table in xref:cms/drupal/removed-core-modules-and-replacements.adoc[removed core modules and replacements]. In short:
Toolbar is replaced by Navigation, Claro by Default Admin, and Shortcut and the other moved modules are required from
contrib when still needed.
