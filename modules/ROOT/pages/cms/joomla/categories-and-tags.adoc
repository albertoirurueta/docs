This page was written against *Joomla 6.2.x* (the current release; PHP 8.3 or later) and checked against the official
documentation and the 6.2 source tree on 2026-10-30. The screens and options described are the same in the 5.4
security-only line, and they have not changed in substance since Joomla 4. Joomla 3 and 4 are end of life.

Classification is the first design decision of every Joomla site, because the category tree decides the URLs, the access
rules, the permissions and the menu structure, while tags add a second, free-form dimension on top. The running example
is the *Tallpine Hiking Club*: trail reports live in the categories *Trails > Alpine*, *Trails > Valley* and *News*,
and each report carries tags such as `family-friendly` and `dog-friendly`. The page is for the *site builder* who
designs the structure, the *editor* who files content, and the *developer* who needs to know where the data is stored.
Articles themselves are covered in xref:cms/joomla/articles.adoc[Articles], menu items in
xref:cms/joomla/menus-and-menu-items.adoc[Menus and Menu Items], and custom fields in
xref:cms/joomla/custom-fields.adoc[Custom Fields].

== Categories

=== What a category is

A category is a node in a tree that belongs to exactly one *extension* (the `extension` column of the categories
table): `com_content` for articles, `com_contact` for contacts, `com_banners`, `com_newsfeeds`, and any third-party
component that integrates categories, such as `com_tallpine` in a package built for the club. Categories of different
extensions are managed by the same Categories component (`com_categories`) but never mix: the Contacts category *Board*
cannot hold an article.

Three properties of the model shape everything else:

* An item belongs to *one* category. The User Guide states it plainly: an article can only be in one category of the
  tree. An article about both dogs and cats goes in the parent category, or is tagged, which is the reason tags exist.
* The tree can be as deep as needed. The User Guide suggests three or four levels as typical, and the menu item options
  (shown below) offer depth limits up to five levels.
* A category can hold both items and sub-categories, like a folder in a file system.

Items without a category choice fall into the *Uncategorised* category that every fresh installation creates for
`com_content`. It is an ordinary category that can be renamed, moved or, once empty, deleted.

=== The category tree internally

Categories are stored as a *nested set*: each row of the categories table carries `lft`, `rgt`, `level`, `path` and
`parent_id`, and the table class extends `Joomla\CMS\Table\Nested`. Reading a whole branch is a single range query
(`lft` between the parent's `lft` and `rgt`), which is why Joomla can list "this category and all its descendants"
cheaply. The price is that writes reorder the numbers of the whole tree, so moving a large branch is slower than
editing an article. The `path` column holds the alias path (`trails/alpine`) and is what the SEF router uses to build
URLs.

[source,sql]
----
-- Read-only illustration of the nested set model; run it on a copy of the database.
SELECT c.id, c.title, c.level, c.path
FROM `#__categories` AS c
JOIN `#__categories` AS p ON p.path = 'trails'
WHERE c.extension = 'com_content'
  AND c.lft BETWEEN p.lft AND p.rgt
ORDER BY c.lft;
----

Source: https://github.com/joomla/joomla-cms/blob/6.2-dev/administrator/components/com_categories/forms/category.xml[Joomla CMS source: category form definition]

Developers should never write such queries inside extensions. The `Joomla\CMS\Categories\Categories` service and the
table class keep the numbering consistent; see
xref:cms/joomla/categories-custom-fields-and-workflow-integration.adoc[Categories, Custom Fields and Workflow Integration]
for how a component registers its own category extension.

=== Creating a category: the edit form

*Content > Categories > New* opens the category form. Its tabs and fields, taken from the 6.2 form definition:

[cols="1,3"]
|===
| Field or tab | Purpose

| Title, Alias
| Title is the only mandatory field. The alias is derived from it and becomes a URL segment, so renaming it later
  changes URLs.

| Parent
| *No parent* makes a root category; choosing another makes a sub-category. The list shows only categories of the same
  extension.

| Description
| Editor field. Shown above the item list on the site when the menu item enables it.

| Status
| Published (default), Unpublished, Archived or Trashed.

| Access
| The view access level (Public, Guest, Registered, Special, Super Users by default, plus custom ones such as the club's
  *Trail Warden* level). It decides who may see the category and its items.

| Language
| *All* or one content language; see xref:cms/joomla/multilingual-sites.adoc[Multilingual Sites].

| Tags
| The category itself can carry tags.

| Note, Version Note
| Free-form administrative notes; the version note is attached to the saved version.

| Options tab
| *Layout* (an alternative layout offered by the component or template) and *Image* with its alt text and a "No
  description" checkbox for decorative images.

| Publishing tab
| Created and modified information, hits, and metadata (meta description, meta keywords, author, robots).

| Permissions tab
| The ACL rules for this category; see below.

| Fields tab
| Custom fields assigned to this category or to all categories; see below.
|===

The Save dropdown contains *Save to Menu as List* and *Save to Menu as Blog*, which create a menu item pointing at the
new category in one step. That is the quickest way to give a new category a public URL.

Source: https://guide.joomla.org/user-guide/articles/articles-articles-categories[Joomla User Guide: Articles: Categories]

=== What a category inherits, and what it does not

The word "inheritance" covers three different mechanisms in Joomla, and mixing them up is a frequent source of
mistakes.

* *Permissions inherit down the tree.* A category's ACL entry is an asset whose parent is the parent category's asset,
  which in turn leads up to the component and to the global configuration. A rule set to *Inherited* on the Permissions
  tab is resolved by walking up that chain; *Allowed* and *Denied* are explicit, and a Deny at a higher level wins. The
  full model is in xref:cms/joomla/users-groups-access-levels-and-acl.adoc[Users, Groups, Access Levels and ACL] and
  xref:cms/joomla/acl-in-extensions.adoc[ACL in Extensions].
* *Display options come from the menu item, not from the category.* The category record itself stores only a layout
  and an image in its parameters; the blog and list options (columns, leading articles, show author, ordering) belong to
  the menu item or to the component's global options. Menu item options marked "Use Global" fall back to
  *Content > Articles > Options*, so changing one global value restyles every menu item that did not override it.
* *Status does not copy downward in the form, but it affects what the site shows.* The articles query looks at the
  published state of the item's own category, so unpublishing a category hides its articles in the public views.
  Unpublishing a parent does not rewrite the children's status flags, yet the branch disappears from the parent's
  category views; check the site as a guest after changing a status, because the access level of a category does not
  propagate in the same way and a child can stay reachable by its own URL.

Access levels are the notable exception to inheritance: a sub-category does not automatically take its parent's access
level, so setting *Trails* to the member-only *Trail Warden* level does not protect *Trails > Alpine* unless the child
is set too. Batch processing (below) is the safe way to apply one access level to a branch.

=== Batch operations, trash and deletion

In the category list, selecting rows and choosing *Actions > Batch* offers language, access level, add tag, and
*copy or move to another category*. The model implements them as `batchCopy` and `batchMove` for the tree and
`batchFlipordering` for ordering. Moving or copying carries the branch with it.

A category is deleted in two steps. The 6.2 model refuses deletion unless the record is already in the *Trashed*
state and the user has the `core.delete` permission on that category; so move the items out first. In practice: batch-move the articles, trash the category, then use the *Empty trash* filter
(a user with delete permission only).

=== Category Blog versus Category List

For a category to appear on the site it needs a menu item. `com_content` offers three menu item types for categories:

[cols="1,1,3"]
|===
| Menu item type | Layout file | Typical use

| Category Blog
| `tmpl/category/blog.php`, with `blog_item.php`, `blog_children.php` and `blog_links.php`
| A magazine page: leading articles across the top, intro columns below, then a list of links. The club's home page
  uses it for *News*.

| Category List
| `tmpl/category/default.php`, with `default_articles.php` and `default_children.php`
| A sortable table of titles with optional date, author and hits columns, a filter box and pagination. The club's
  trail-report archive uses it.

| List All Categories
| `tmpl/categories/default.php`
| A page that lists the sub-categories of a base category, to a configurable depth.
|===

Both category types take the category as a request parameter (`id`) and show the same data; they differ in
presentation and in the options they expose.

*Blog options* (in the menu item, "Blog Layout Options"): `num_leading_articles` (full-width articles at the top),
`num_intro_articles`, `num_columns`, `multi_column_order` (across or down), `num_links` (title-only links at the
bottom), `show_featured`, `orderby_pri` and `orderby_sec`, `show_subcategory_content`, and pagination. With
`num_leading_articles` = 1, `num_intro_articles` = 4 and `num_columns` = 2 the News page shows one large story and four
intro texts in two columns.

*List options* ("List Layouts"): `show_pagination_limit`, `filter_field` (hide, title, author, hits or tag) and the
visible columns. The Category List is the better choice when readers look things up, because they can sort and filter;
the Blog is better when readers browse.

Both share the *Category Options*: `show_category_title`, `show_description`, `show_description_image`, `maxLevel` (how
many levels of sub-categories to list: None, 1 to 5 or All), `show_empty_categories`, `show_subcat_desc`,
`show_cat_num_articles` and `show_cat_tags`. For the Blog, `show_subcategory_content` controls whether the articles of
sub-categories appear in the parent's blog, to a chosen depth. This is how a *Trails* blog can show the reports of
*Alpine* and *Valley* together without a menu item of its own for each.

[source,xml]
----
<!-- Sketch of the parameters Joomla stores for a Category Blog menu item. -->
<params>
  {"layout_type":"blog","num_leading_articles":"1","num_intro_articles":"4",
   "num_columns":"2","num_links":"4","show_subcategory_content":"-1",
   "maxLevel":"1","show_cat_tags":"1","show_pagination":"2"}
</params>
----

Source: https://github.com/joomla/joomla-cms/blob/6.2-dev/components/com_content/tmpl/category/blog.xml[Joomla CMS source: Category Blog menu item definition]

Layouts can be replaced from the template without touching core. Copy `blog_item.php` into
`templates/cassiopeia_tallpine/html/com_content/category/` to restyle each teaser; the procedure is in
xref:cms/joomla/template-overrides-and-alternative-layouts.adoc[Template Overrides and Alternative Layouts].

Source: https://guide.joomla.org/user-guide/getting-started/getting-started-articles-and-categories[Joomla User Guide: Articles and Categories]

== Tags

=== What a tag is

A tag is a label that can be attached to *any* taggable content type, across components: articles, contacts, news
feeds, categories, and extension items that opt in. Unlike a category, an item can carry many tags at once, which is
exactly the property the User Guide highlights. Tags are managed under *Components > Tags*.

Tags are themselves a nested set (the table class extends `Joomla\CMS\Table\Nested`), so tags can have parents and
children. Nesting is organisational: a parent tag *Suitable for* with children `family-friendly` and `dog-friendly`
keeps a long tag list readable, and the tag picker can show the hierarchy. It does not make a child automatically
count as its parent on an item; the *include children* option below is what links them at display time.

=== Internals

Tagging is mapped through a join table, so the content tables themselves are untouched:

[source,sql]
----
-- Which tag ids are attached to article 42? (read-only illustration)
SELECT m.tag_id, t.title
FROM `#__contentitem_tag_map` AS m
JOIN `#__tags` AS t ON t.id = m.tag_id
WHERE m.type_alias = 'com_content.article' AND m.content_item_id = 42;
----

Source: https://github.com/joomla/joomla-cms/blob/6.2-dev/libraries/src/Helper/TagsHelper.php[Joomla CMS source: TagsHelper]

`Joomla\CMS\Helper\TagsHelper` is the API: `getItemTags()` for the tags of one item, `getTagIds()` and
`getTagItemsQuery()` for the items carrying given tags, `postStore()` to save the mapping after an item is stored, and
`tagDeleteInstances()`, which removes every mapping when a tag is deleted. Components get the behaviour by adding the
Taggable behaviour to their table (`TagsHelper` is invoked from the table's store and delete events), and the content
type registration in the content types table (`+#__content_types+`) tells the Tags component how to find, title and link each type. Extension
authors integrating this are covered in
xref:cms/joomla/categories-custom-fields-and-workflow-integration.adoc[Categories, Custom Fields and Workflow Integration].

=== The tag edit form

*Components > Tags > New*: Title (mandatory), Alias, Description, Parent (*None* for a root tag), Status, Access,
Language, Note and Version Note. The *Options* tab has the tag *Layout*, a *CSS class* for the tag link (parameter
`tag_link_class`), and two images, an intro image for the tag list and a full image for the tag page. The *Publishing*
tab holds the metadata for the tag's own page. In the list, tags can be searched, reordered by drag and drop, and
processed with *Actions > Batch*, which sets language or access level.

=== Assigning tags to content

The *Tags* field of the article form (and of any form that includes the field) has two input modes, selected by the
global option *Tag Field Mode* in *Components > Tags > Options > Data Entry*:

* *AJAX* (the default, `tag_field_ajax_mode` = 1) searches tags as the editor types, which scales to thousands of
  tags.
* *Nested* shows the whole tree in a list, suitable for a small controlled vocabulary.

In either mode an authorised editor can type a new tag name, and Joomla creates it on save (`createTagsFromField`).
That is convenient and also the reason tag lists decay: `dog-friendly`, `Dog friendly` and `dogs` appear within a month.
Where the vocabulary must stay controlled, remove the `core.create` permission on the Tags component from the editor
group so that editors can pick but not invent tags; permissions are set under *Components > Tags > Options >
Permissions*.

=== Tag global options

*Components > Tags > Options* groups the defaults that tag menu items inherit:

* *Tag* page: show title, image and description, ordering (title, match count, created, modified or published date) and
  direction, headings, date, item image, item description and the maximum characters of the item description.
* *Tag selection*: `min_term_length`, `return_any_or_all` (items matching all or any of several tags),
  `include_children`, `maximum` (number of items), a language filter and `record_hits`.
* *All tags*: ordering, image, description, description length and hit counters.
* *Shared*: filter field and pagination.
* *Integration*: the news feed link.

=== The Tags component views

Tags have their own site views, each created by a menu item:

[cols="1,2,3"]
|===
| Menu item type | Options of interest | What it shows

| Tagged Items
| the tags to match (several allowed, picked in nested mode), the content types, a language filter
| The items carrying the chosen tags, from every selected content type, ordered as configured. The club's
  *Family hikes* page uses it with `family-friendly`.

| Compact list of tagged items
| the same selection (layout `list`)
| A tighter list without teaser images, useful for sidebars and archives.

| List of All Tags
| ordering, image, description
| An index of all published tags with optional counters, for a tag overview or a tag cloud page.
|===

When a tag is chosen on the *Tagged Items* page together with *Include children* set to Include, items tagged with any
descendant also match; with Exclude, only items carrying the exact tag are listed. The matching mode `return_any_or_all`
decides whether an item needs all of the selected tags or just one.

Two modules bring tags into other pages: *Tags - Popular* (`mod_tags_popular`), which displays the most used tags as a
list or cloud, and *Tags - Similar* (`mod_tags_similar`), which shows items that share tags with the article being
viewed. Modules are placed as described in xref:cms/joomla/modules-and-positions.adoc[Modules and Positions]. Tags also
appear on articles when "Show Tags" is on in the article options, and as filter entries in the category list.

Tag URLs are built by the router from the tag path, so renaming a tag alias changes public URLs; redirects are in
xref:cms/joomla/seo-sef-urls-redirects-and-schema-org.adoc[SEO, SEF URLs, Redirects and Schema.org].

Source: https://guide.joomla.org/user-guide/tags/tags-content-tags[Joomla User Guide: Content Tags]

== Categories, tags or custom fields

The three tools overlap, and the right choice depends on what the classification must do.

[mermaid]
----
flowchart TD
  Q[What do you need to record?] --> A{Exactly one value&lt;br/&gt;per item, and it decides&lt;br/&gt;URL, access or permissions?}
  A -- yes --> C[Category]
  A -- no --> B{Free-form labels that&lt;br/&gt;an item can have several of,&lt;br/&gt;shared across components?}
  B -- yes --> T[Tag]
  B -- no --> D{A typed value to edit,&lt;br/&gt;validate and print&lt;br/&gt;in a layout?}
  D -- yes --> F[Custom field]
  D -- no --> C
----

[cols="1,2,2,2"]
|===
| | Categories | Tags | Custom fields

| Cardinality
| One per item
| Many per item
| One or many, depending on the field type

| Structure
| Nested tree
| Optional nesting
| Flat list of typed values

| Drives URLs and menu items
| Yes (category paths, blog and list views)
| Tag pages and the Tags views
| No

| Drives access and permissions
| Yes (ACL assets, access level)
| Access level on the tag only
| Per-field access, no effect on the item

| Spans several components
| No (one extension each)
| Yes
| Per component, with category assignment

| Typed data (number, list, media, date)
| No
| No
| Yes
|===

For the club: the *difficulty* of a trail is a list custom field, because the value is one of a fixed set and is
printed on the report; *distance-km* and *elevation-gain* are numeric fields; the area (*Alpine* or *Valley*) is a
category, since it decides the URL and which Trail Warden group can edit; and `dog-friendly` is a tag, because many
reports have it, contacts and news items can share it, and visitors want a page listing it. Custom fields can also be
restricted to certain categories, so *Trails > Alpine* can show an `elevation-gain` field that *News* does not; that
assignment is on the Fields tab of the category and is explained in
xref:cms/joomla/custom-fields.adoc[Custom Fields]. Where workflow stages should differ per category, see
xref:cms/joomla/workflows.adoc[Workflows].

== Common errors and pitfalls

* *Deep trees without menu items.* A category with no menu item and no parent menu item is reachable only by the
  default router fallback, which yields long, unstable URLs. Create the menu item first, then file content.
* *Changing an alias after launch.* Both category and tag aliases are URL segments. Rename after launch only with a
  redirect in place.
* *Assuming access inherits.* Set the access level on every level of a branch, or batch it.
* *Expecting Delete to work.* Categories must be trashed and then emptied, and must be empty of items.
* *Treating tags as a taxonomy.* Free-text creation produces near-duplicates. Limit creation by permission, review the
  tag list monthly, and merge duplicates by batch re-tagging.
* *Tag cloud performance.* *Tags - Popular* aggregates the mapping table; cache the module (the module's caching
  options) on large sites, see xref:cms/joomla/caching-and-performance.adoc[Caching and Performance].
* *Stale counters.* Hit counters on tags only advance when `record_hits` is on.
* *Sub-categories absent from the parent blog.* The parent's blog shows only its own articles until
  `show_subcategory_content` is raised.

== Security

* Category access levels and permissions are the real protection; hiding a menu item only hides a link. A member-only
  category needs the access level on the category *and* on its menu item.
* Tags display titles and descriptions in public pages and as filter values, and they run through the output filters
  like other content. Do not give untrusted groups the right to create tags, since tag text is visible site-wide.
* Anything stored in the tag map is data; building SQL against it in an extension must use the query builder with
  bound parameters (`+->bind()+`), never string concatenation.
* The Web Services API exposes categories and tags to token holders subject to the same ACL; see
  xref:cms/joomla/web-services-api.adoc[Web Services API].

== Version notes and corrections of older material

The category and tag screens have been stable from Joomla 4 through 6.2. Joomla 6.x changes the surrounding platform
(PHP 8.3 minimum, removed legacy classes available only through the Behaviour - Backward Compatibility 6 plugin) rather
than these screens; extensions that still call removed classes in category code should be checked against the 6.0
removal list in xref:cms/joomla/deprecations-and-preparing-for-joomla-7.adoc[Deprecations and Preparing for Joomla 7].

Older books describe the same concepts but cite older surroundings. *Joomla! 4 Masterclass* (2023) targets Joomla 4,
which reached end of life in October 2025, and links to `docs.joomla.org/J4.x` pages; the current end-user documentation
is the Joomla User Guide at guide.joomla.org, whose pages are cited here. *Developing Extensions for Joomla! 5* (2023)
shows the categories and custom-fields integration for Joomla 5.0; the registration logic is unchanged, but the
surrounding class and event names it uses for older APIs should be checked against the Manual for 6.2. Neither book
covers the Joomla 6 removals.
