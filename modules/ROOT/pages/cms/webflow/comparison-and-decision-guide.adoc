This page helps you decide whether Webflow suits a project. It was checked on 2026-10-28 against the official Webflow
documentation, which is the only source for Webflow's own limits and plans. Webflow is named by tier only (Starter, Basic,
Premium, Team, Enterprise and the Ecommerce tiers) and this page never quotes prices: every product mentioned here changes
its plans often, so compare current plan pages before you commit. Statements about other products are deliberately
general (what kind of tool each is) and should be checked against their own documentation. The running example is
*Fernbrook Gardens*, the fictitious botanical garden: a marketing site with a Plants collection, events, a small
shop, three locales and a developer who wants to import plants from a nursery feed.
For a dated, sourced comparison of Webflow with fifteen other CMSs, see the xref:cms/comparison.adoc[CMS Comparison].

== The five options

* *Webflow* is a hosted visual builder with a built-in CMS, hosting, forms, localization and ecommerce, and a
  developer platform (Data API, Apps, DevLink, Webflow Cloud, MCP). You design visually and Webflow serves the result.
* *WordPress* is open-source software installed on a server with PHP and a database, extended with themes and plugins.
  The sub-section on WordPress is a sibling of this one and is described in prose here; it is compared in more depth
  there once it is published.
* *Other visual builders* such as Framer, Wix Studio and Squarespace are hosted tools in which you design visually.
  They differ in how much of the CMS, layout control, code access and ecommerce each offers.
* *A headless CMS with a web framework* separates the content store (a CMS with an API) from a front end that you code,
  for example in Next.js, and that you host yourself or on a platform. The
  xref:web/frameworks-comparison.adoc[Web Frameworks Comparison] covers the framework side, which excludes CMSs by design.
* *A static site generator* builds pages from files at build time and publishes plain HTML, with content kept in files or
  pulled from an API during the build.

== Hosting, ownership and export

[cols="2,2,2,2,2",options=header]
|===
|Criterion |Webflow |WordPress |Visual builders |Headless CMS plus framework

|Hosting model
|SaaS; Webflow hosts on its CDN and you do not run servers
|You or a managed host runs PHP and a database
|SaaS, hosted by the vendor
|You choose: a platform, your cloud or your servers

|Ownership of content
|You own it, but it lives inside Webflow; export is by CSV, the Data API and code export
|You hold the files and the database
|Inside the vendor, with export options that vary
|You hold the content in the CMS you pick, often with a database export

|Export of the front end
|Static HTML, CSS and JavaScript from code export on paid Workspace plans; the CMS, ecommerce, forms, search, localization and code components do not come with it
|Move files and database to another host
|Varies by product; often limited
|Your code is already yours

|Operating work
|Patching and scaling are done by Webflow
|You patch core, themes and plugins and tune the server
|Done by the vendor
|You operate the front end and the CMS, or pay a host to
|===

== CMS capacity and content modeling

[cols="2,3,3",options=header]
|===
|Criterion |Webflow |Alternatives

|Content types
|Collections with 16 field types, references and multi-references; up to 60 fields per Collection
|WordPress has post types and custom fields; headless CMSs usually allow flexible models, often with fewer fixed ceilings
|Item and Collection ceilings
|Premium includes 20,000 CMS items and 40 Collections; Team 100 Collections; Enterprise is negotiated and has the next-generation CMS
|A self-hosted or headless CMS is bounded by your database and hosting rather than by a plan tier
|Display limits
|A Collection list shows 100 items unless pagination is on; 20 lists per page on standard plans
|A front end you code can paginate and query without such limits
|Editing
|Edit on the canvas with a role on a seat; scheduling and drafts at the item level
|WordPress has a block editor and roles; headless CMSs provide their own admin UI
|===

See xref:cms/webflow/cms-limits-and-scaling.adoc[CMS Limits and Scaling] for the numbers and their sources.

== Extensibility and the developer platform

[cols="2,3,3",options=header]
|===
|Criterion |Webflow |Alternatives

|Server-side code
|None on a Webflow page; use Webflow Cloud (Next.js, Astro or Vite apps on Cloudflare Workers) or your own backend
|WordPress runs PHP in the site; a framework runs wherever you deploy it
|Extending the editor
|Designer Extensions and the Designer API, Apps with OAuth, marketplace apps, custom code of 50,000 characters per box
|WordPress plugins can change anything; visual builders offer apps and embeds
|APIs
|Data API v2 (REST), Content Delivery API, webhooks, the CLI, SDKs for Node.js and Python and an MCP server
|WordPress has a REST API; headless CMSs are API-first
|Code in your own stack
|DevLink exports components as React, and code components import React into the Designer
|A headless approach lets you code the whole front end
|AI agents
|A first-party MCP server and AI features with credits
|Varies; most tools now add AI features of their own
|===

== Team workflow, localization and cost model

[cols="2,3,3",options=header]
|===
|Criterion |Webflow |Alternatives

|Team workflow
|Seats and roles, comments, an activity log, page branching, releases and approvals on higher tiers
|WordPress relies on roles and plugins; a code-first team uses Git, pull requests and CI
|Localization
|Built-in Localization with secondary locales and automatic routing, sold as an add-on; Team includes two locales
|WordPress uses plugins; frameworks use i18n libraries
|Cost model (no prices)
|A Workspace plan for people and tools, a Site plan per site, add-ons (Localize, Analyze, Optimize) and AI credits
|WordPress costs shift to hosting, plugins and maintenance; a headless stack costs CMS, hosting and developer time
|Lock-in
|Moderate to high: the design, interactions, forms, search and CMS pages are tied to Webflow; content leaves by CSV and API
|WordPress is portable but plugin-dependent; a code-first stack is most portable
|===

== When Webflow is the right tool

* A marketing or content site where designers should ship layouts and interactions without developers.
* A site that needs a CMS of tens of thousands of items at most, with editors working on the canvas.
* A team that wants hosting, security patches, forms, localization and analytics from one vendor.
* A project where a developer adds automation (the Data API and webhooks) or custom code to an otherwise visual site.

== When it is not

* Content in the millions of records, or logic that has to run on every request inside the site: use a headless CMS and a
  framework, or put the logic in a Webflow Cloud app or a separate service.
* A need to run your own server software, a custom database or fine control of the HTTP layer: self-host WordPress or a
  framework; xref:cms/webflow/reverse-proxy-and-custom-hosting.adoc[Reverse Proxy and Custom Hosting] covers the limited
  cases where Webflow can sit behind your own proxy.
* A requirement to keep all content, design and code in your own Git repository with no vendor service.
* A very large shop with complex catalog and checkout needs: compare the dedicated ecommerce platforms first.

== Hybrid architectures

* *Webflow for marketing pages, a framework for the application.* Put the app on its own subdomain or, with Webflow Cloud,
  mount it under a path of the site. See xref:cms/webflow/webflow-cloud.adoc[Webflow Cloud] and
  xref:cms/webflow/hybrid-apps.adoc[Hybrid Apps].
* *Webflow as the CMS, a coded front end as the site.* Read published content through the Content Delivery API and
  publish the front end yourself. See xref:cms/webflow/content-delivery-api-and-headless.adoc[Content Delivery API and Headless].
* *Webflow design, React components in an app.* Use DevLink to export components. See
  xref:cms/webflow/devlink-export.adoc[DevLink Export].
* *Webflow plus a WordPress or ecommerce back end.* Keep each tool for what it does best and link them with the APIs or
  a reverse proxy; the WordPress sibling sub-section will describe its side once it is published.

For the backend half of any hybrid, see the xref:backend/frameworks-comparison.adoc[Backend Frameworks Comparison].
