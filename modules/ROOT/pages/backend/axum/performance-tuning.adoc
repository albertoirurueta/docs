This page is written against axum 0.8.9 with tokio 1.53, hyper-util 0.1.21, mimalloc 0.1.52 and oha 1.16 on Rust 1.99
(edition 2024), checked on 2026-10-06. axum adds very little overhead on top of hyper, so the performance of a
*Bookshelf* service is decided by what handlers do: blocking calls on async workers, database round trips, allocation
and serialisation. General Rust optimisation (build settings, allocation avoidance, profilers, benchmarks) is in the Rust
Reference's xref:programming-languages/rust/performance-and-profiling.adoc[Performance & Profiling]; this page covers the
server side.

== Measure first

* Benchmark a *release* build on hardware close to production; debug builds of Rust can be an order of magnitude slower or
  more and tell nothing about production.
* Report *latency percentiles* (p50, p99, p99.9) at a given request rate, not only requests per second. A service that
  does 20 000 req/s with a p99 of 2 s is not fast.
* `oha` (Rust, a terminal UI) and `k6` (JavaScript scenarios, thresholds for CI) generate load; run them from another
  machine for real numbers so the generator does not compete for CPU.
* Change one thing at a time and keep the before and after numbers.

== Release profile

[source,toml]
----
[profile.release]
lto = "thin"                 # cross-crate inlining; "fat" squeezes a little more for much longer links
codegen-units = 1            # better optimisation, slower compile
debug = "line-tables-only"   # symbols for flamegraphs and panic backtraces, small binary cost
# panic = "abort"            # do NOT use in servers: one panicking handler would kill the whole process
----

* Keep `+panic = "unwind"+` (the default) for a server. With unwinding, a panic in a handler aborts that one request's task
  (and `CatchPanicLayer` can turn it into a `500`); with `abort` every in-flight request dies with it.
* `opt-level = 3` is already the release default. `target-cpu=native` is only safe when the build machine and the
  production CPUs match, which is rarely true for container images.

== Never block the async workers

Tokio runs every task on a few worker threads (one per core by default). A handler that does CPU-heavy work or blocking
I/O without yielding holds its worker, and every other task scheduled there -- including unrelated, cheap requests --
waits. Password hashing, image resizing, large JSON serialisation, compression of big files, `std::fs` and synchronous
database drivers all qualify:

[source,rust]
----
use argon2::{Argon2, password_hash::PasswordHasher};
use axum::{
    Router,
    body::Bytes,
    extract::State,
    http::{StatusCode, header},
    response::IntoResponse,
    routing::{get, post},
};
use tracing::{Span, info_span, instrument};

// a faster general-purpose allocator for allocation-heavy services (measure before and after)
#[global_allocator]
static GLOBAL: mimalloc::MiMalloc = mimalloc::MiMalloc;

#[derive(Clone)]
struct AppState {
    cover: Bytes, // reference-counted: cloning shares the buffer instead of copying it
}

/// Anti-pattern: CPU-bound work (tens of milliseconds of Argon2) blocks the worker thread it runs on.
async fn hash_inline(body: String) -> Result<String, StatusCode> {
    Argon2::default()
        .hash_password(body.as_bytes())
        .map(|h| h.to_string())
        .map_err(|_| StatusCode::INTERNAL_SERVER_ERROR)
}

/// The same work on the blocking pool, keeping the request span as the parent.
#[instrument(skip_all)]
async fn hash_offloaded(body: String) -> Result<String, StatusCode> {
    let span = Span::current();
    tokio::task::spawn_blocking(move || {
        let _guard = info_span!(parent: &span, "argon2_hash").entered();
        Argon2::default().hash_password(body.as_bytes()).map(|h| h.to_string())
    })
    .await
    .map_err(|_| StatusCode::INTERNAL_SERVER_ERROR)?
    .map_err(|_| StatusCode::INTERNAL_SERVER_ERROR)
}

async fn cover(State(state): State<AppState>) -> impl IntoResponse {
    ([(header::CONTENT_TYPE, "image/png")], state.cover.clone()) // no copy of the bytes
}

async fn ping() -> &'static str {
    "pong\n"
}

#[tokio::main]
async fn main() {
    tracing_subscriber::fmt().with_env_filter("warn").init();
    let state = AppState { cover: Bytes::from(vec![0u8; 64 * 1024]) };

    let app = Router::new()
        .route("/hash/inline", post(hash_inline))
        .route("/hash", post(hash_offloaded))
        .route("/cover", get(cover))
        .route("/ping", get(ping))
        .with_state(state);

    let listener = tokio::net::TcpListener::bind("127.0.0.1:3000").await.unwrap();
    axum::serve(listener, app).await.unwrap();
}
----

Source: https://docs.rs/tokio/1.53.2/tokio/task/fn.spawn_blocking.html[tokio: spawn_blocking], https://ryhl.io/blog/async-what-is-blocking/[Alice Ryhl: Async: What is blocking?] and https://docs.rs/mimalloc/0.1.52/mimalloc/[mimalloc]

Measured on 4 cores: 8 concurrent clients hash passwords for 10 s while a single client sends `/ping` requests.

[source,bash]
----
$ oha -z 10s -c 8 -m POST -d 'correct horse battery staple' http://127.0.0.1:3000/hash/inline &
$ oha -n 200 -c 1 http://127.0.0.1:3000/ping
  Average:      26.2290 ms           # /ping waits for a worker that is busy hashing
  50.00% in     26.2437 ms
  99.00% in     63.1279 ms

$ oha -z 10s -c 8 -m POST -d 'correct horse battery staple' http://127.0.0.1:3000/hash &
$ oha -n 200 -c 1 http://127.0.0.1:3000/ping
  Average:       0.0438 ms           # workers stay free; hashing runs on the blocking pool
  50.00% in      0.0124 ms
  99.00% in      1.7052 ms
----

* The hashing throughput is about the same either way (the CPU is the limit); what changes is that `spawn_blocking`
  keeps the latency of *everything else* unaffected -- a median of 26 ms against 0.01 ms for `/ping` here.
* `spawn_blocking` runs the closure on a separate pool (up to 512 threads by default). For CPU-bound work, bound the
  concurrency with a `Semaphore` or use a dedicated Rayon pool, so a burst cannot start hundreds of threads competing
  for the same cores.
* The closure runs outside the request's span. Capture `Span::current()` before spawning and enter a child span inside,
  as above, so logs and traces from the blocking code stay attached to the request (Gangappa & Rangaraj, *Mastering
  Distributed Observability in Rust*, chapter 10).
* Use `tokio::fs`, async database drivers (sqlx) and async HTTP clients; `tokio::task::block_in_place` is an escape hatch
  for code that cannot be moved, on the multi-threaded runtime only.
* *Allocator*: the `+#[global_allocator]+` line swaps the system allocator for mimalloc (or `tikv-jemallocator`, which also
  offers heap profiling). Allocation-heavy services often gain throughput and suffer less fragmentation; on musl
  targets, whose allocator is slow, the gain is much larger. Measure it -- the effect depends on the workload.

== Finding blocked and starved tasks with tokio-console

tokio-console shows every task, how long it was busy versus idle, how often it was polled, and warns about tasks that
hold a worker for too long:

[source,bash]
----
$ cargo add console-subscriber            # then call console_subscriber::init() in main (development builds only)
$ RUSTFLAGS="--cfg tokio_unstable" cargo run
$ cargo install --locked tokio-console && tokio-console   # connects to 127.0.0.1:6669
----

* A task with a long *busy* time and few polls is blocking its worker. Many tasks with long *scheduled* times
  (waiting to run) mean the runtime is starved -- usually by such a blocker.
* `tokio_unstable` and the console layer add overhead; enable them in development or a staging build, not in the
  production binary.

== CPU flamegraphs

[source,bash]
----
$ cargo install flamegraph
$ cargo flamegraph --release --bin bookshelf-web    # run load with oha meanwhile, then Ctrl+C
$ samply record ./target/release/bookshelf-web      # alternative with an interactive Firefox Profiler view
----

Wide frames are where the CPU time goes. Typical findings in axum services: JSON serialisation of large responses,
regex compilation inside handlers (compile once, store in a `LazyLock`), cloning large state instead of sharing it in an
`Arc`, logging at `debug` level in production, and TLS handshakes when clients do not reuse connections. `debug =
"line-tables-only"` in the release profile gives readable frames.

== Database and pools

* Pool size is a throughput limit, not a knob to turn up: every connection costs memory and CPU on the database. Start
  from the database's capacity (see xref:backend/axum/databases-with-sqlx.adoc[Databases with sqlx]) and divide by the
  number of replicas.
* Watch the time spent *waiting* for a connection (see xref:backend/axum/metrics-and-slos.adoc[Metrics & SLOs]). If it
  grows, look for slow queries, N+1 patterns and long transactions before adding connections.
* Set `acquire_timeout` so requests fail fast instead of queuing behind an exhausted pool, and bound the whole request
  with `TimeoutLayer`.

== Responses, compression and connections

* *`Bytes` and zero-copy*: `Bytes` is reference counted, so serving a cached image or a pre-rendered page from state
  clones a pointer, not the data (`/cover` above). Stream large files with `ServeFile` or a body stream instead of
  reading them into memory (see xref:backend/axum/static-files-and-spas.adoc[Static Files & SPAs]).
* *Compression* costs CPU on every response. Compress text (JSON, HTML) above a size threshold, skip already compressed
  formats (images, video), prefer pre-compressed static files (`ServeDir::precompressed_br`), and use a lower level for
  dynamic content (see xref:backend/axum/cors-and-compression.adoc[CORS & Compression]). Behind a CDN or a proxy that
  compresses, do not compress twice.
* *Keep-alive*: hyper keeps HTTP/1.1 connections open by default; make sure clients and proxies reuse them, since a new
  TCP plus TLS handshake per request dominates the cost of small requests.
* *HTTP/2*: with the `http2` feature, `axum::serve` also accepts cleartext HTTP/2 (prior knowledge); HTTP/2 over TLS
  is negotiated by the TLS acceptor (see xref:backend/axum/tls-and-https.adoc[TLS & HTTPS]).
  Many requests share one connection, which helps browsers and gRPC; behind a load balancer, HTTP/2 between proxy and
  service is mostly about fewer connections.
* *Per-connection settings*: `axum::serve` exposes few knobs. For a header-read timeout, HTTP/2 stream limits or
  keep-alive intervals, drive connections with hyper-util's `auto::Builder` as shown in
  xref:backend/axum/request-limits-and-timeouts.adoc[Request Limits & Timeouts] (axum's `serve-with-hyper` example).
  `serve::ListenerExt::tap_io` sets `TCP_NODELAY` on accepted sockets.

== Load testing

[source,javascript]
----
// k6 run books.js -- fails the run (non-zero exit) when the thresholds are missed, so it can gate a release
import http from 'k6/http';

export const options = {
  scenarios: { steady: { executor: 'constant-arrival-rate', rate: 500, timeUnit: '1s', duration: '2m',
                         preAllocatedVUs: 50 } },
  thresholds: { http_req_failed: ['rate<0.001'], http_req_duration: ['p(99)<300'] },
};

export default function () {
  http.get('http://staging.bookshelf.internal/books/9781718503106');
}
----

Source: https://grafana.com/docs/k6/latest/[k6 documentation] and https://github.com/hatoo/oha[oha]

* A *constant arrival rate* keeps sending requests when the service slows down, which reveals queueing; a fixed number
  of looping virtual users backs off and hides it (coordinated omission).
* The thresholds mirror the SLOs from xref:backend/axum/metrics-and-slos.adoc[Metrics & SLOs].

== Where the books are outdated

Gangappa & Rangaraj (chapters 9-10) profile with flamegraphs, jemalloc and tokio-console; the approach is current,
and tokio-console still needs the `tokio_unstable` cfg. Material that recommends
`+panic = "abort"+` for smaller, faster binaries applies to CLIs, not servers.
