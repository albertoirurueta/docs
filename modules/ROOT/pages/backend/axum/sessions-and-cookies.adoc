axum 0.8.9 on Rust 1.99 (edition 2024), checked on 2026-10-06. *Bookshelf*'s server-rendered pages sign users in with

== Version pairing first

tower-sessions 0.15 is the newest release, but at the time of writing its ecosystem has not caught up:

* `axum-login` 0.18 requires tower-sessions **0.14**;
* `tower-sessions-redis-store` 0.16 requires tower-sessions **0.14**;
* `tower-sessions-sqlx-store` 0.15 requires tower-sessions **0.14** *and* sqlx **0.8**, so it cannot share a `PgPool`
  with an application on sqlx 0.9 (Cargo builds both sqlx versions, and the two pool types are unrelated).

*Bookshelf* therefore pins tower-sessions 0.14 and stores sessions in Redis. Check `cargo tree -d` after every
upgrade: two copies of tower-sessions in the build mean a layer from one version and an extractor from the other, and
the `Session` extractor then fails at runtime with a missing-extension `500`.

[source,toml]
----
[dependencies]
tower-sessions = "0.14.0"               # not 0.15: axum-login 0.18 and the stores need 0.14
tower-sessions-redis-store = "0.16.0"
time = "0.3"                            # Expiry uses time::Duration
----

== A session layer and the `Session` extractor

[source,rust]
----
use axum::{
    Form, Router,
    response::{Html, IntoResponse, Redirect},
    routing::{get, post},
};
use serde::Deserialize;
use tower_sessions::{
    Expiry, Session, SessionManagerLayer,
    cookie::{SameSite, time::Duration},
};
use tower_sessions_redis_store::{RedisStore, fred::prelude::*};

const USER_KEY: &str = "user_id";

#[derive(Deserialize)]
struct Login {
    username: String,
    password: String,
}

async fn login(session: Session, Form(form): Form<Login>) -> impl IntoResponse {
    // verify the password here (see the Password Authentication page)
    let user_id: i64 = match (form.username.as_str(), form.password.as_str()) {
        ("ursula", "correct horse battery staple") => 42,
        _ => return Redirect::to("/login?error=1"),
    };
    // Rotate the session ID on privilege change: defeats session fixation.
    if session.cycle_id().await.is_err() || session.insert(USER_KEY, user_id).await.is_err() {
        return Redirect::to("/login?error=2");
    }
    Redirect::to("/account")
}

async fn account(session: Session) -> impl IntoResponse {
    match session.get::<i64>(USER_KEY).await {
        Ok(Some(id)) => Html(format!("<p>signed in as user {id}</p>")).into_response(),
        _ => Redirect::to("/login").into_response(),
    }
}

async fn logout(session: Session) -> Redirect {
    // delete the server-side record AND the cookie
    let _ = session.flush().await;
    Redirect::to("/")
}

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    let config = Config::from_url(&std::env::var("REDIS_URL").unwrap_or_else(|_| "redis://127.0.0.1:6379".into()))?;
    let pool = Pool::new(config, None, None, None, 4)?;
    let _connection_task = pool.connect();
    pool.wait_for_connect().await?;

    let sessions = SessionManagerLayer::new(RedisStore::new(pool))
        .with_name("__Host-bookshelf")      // __Host-: Secure, Path=/, no Domain enforced by browsers
        .with_secure(true)
        .with_http_only(true)               // the default; JavaScript cannot read the cookie
        .with_same_site(SameSite::Lax)      // sent on top-level navigation, not on cross-site POSTs
        .with_path("/")
        .with_expiry(Expiry::OnInactivity(Duration::hours(8)));

    let app = Router::new()
        .route("/login", post(login))
        .route("/account", get(account))
        .route("/logout", post(logout))
        .layer(sessions);
    let listener = tokio::net::TcpListener::bind("127.0.0.1:3000").await?;
    axum::serve(listener, app).await?;
    Ok(())
}
----

----
$ curl -si -d 'username=ursula&password=correct horse battery staple' localhost:3000/login | grep -i -E '^HTTP|location|set-cookie'
HTTP/1.1 303 See Other
location: /account
set-cookie: __Host-bookshelf=CvnGyttAULOyvLg_x_0biw; HttpOnly; SameSite=Lax; Secure; Path=/; Max-Age=28800
----

How it works:

* `SessionManagerLayer` reads the session ID from the cookie, and the `Session` extractor loads the record from the
  store *lazily* -- only when a handler calls `get` or `insert`. Requests that never touch the session cost nothing.
* At the end of the request the layer saves modified sessions and sets the cookie; unmodified sessions are not
  rewritten unless `with_always_save(true)` (useful to slide the expiry on every request).
* The cookie contains only a random 128-bit ID; all data stays in Redis, so it can hold more than a cookie and can be
  revoked server-side (delete the record).
* `Expiry::OnInactivity(d)` expires the session after `d` without activity; `Expiry::AtDateTime` sets an absolute
  deadline; `Expiry::OnSessionEnd` makes a browser-session cookie. Stores expire records too (Redis uses its TTL).

== Cookie attributes

[cols="1,3",options="header"]
|===
|Attribute |Why
|`HttpOnly` |JavaScript cannot read the cookie, so an XSS bug cannot steal the session
|`Secure` |sent only over HTTPS; required for `SameSite=None` and for `+__Host-+` cookies
|`SameSite=Lax` |not sent on cross-site sub-requests or cross-site ``POST``s -- the main CSRF defence for cookie
sessions. `Strict` also drops it on cross-site links (users arriving from a link look signed out); `None` sends it
everywhere and needs other CSRF protection
|`+__Host-+` name prefix |browsers only accept the cookie if it is `Secure`, has `Path=/` and no `Domain`, so a
compromised subdomain cannot overwrite it
|`Max-Age` / `Expires` |persistence; omit for a cookie that dies with the browser session
|===

For local development over plain HTTP, `+__Host-+` and `Secure` cookies are rejected by browsers except on
`http://localhost` in most of them; drive both settings from configuration rather than commenting them out.

== Session fixation and logout

In a *session fixation* attack, the attacker plants a known session ID in the victim's browser (through a subdomain or
a URL parameter) and waits for the victim to log in, after which the attacker's copy of the ID is authenticated.
Calling `session.cycle_id()` when privileges change -- login, logout, role change, password change -- issues a new ID
and keeps the data, which defeats it. `session.flush()` deletes the record and clears the cookie; use it on logout
rather than just removing the user key. `axum-login` does both automatically (see
xref:backend/axum/password-authentication.adoc[Password Authentication]).

== Client-side state: signed and private cookie jars

For small, non-sensitive state that does not justify a store -- the last visited shelf, a "dismissed banner" flag, the
OAuth `state` parameter during a login redirect -- axum-extra's `SignedCookieJar` (tamper-evident) and
`PrivateCookieJar` (encrypted) keep it in the cookie itself. They are shown on xref:backend/axum/axum-extra.adoc[axum-extra]
and used for the PKCE verifier on xref:backend/axum/oauth2-and-openid-connect.adoc[OAuth2 & OpenID Connect]. Cookie
state cannot be revoked server-side and is limited to about 4 KB, so authentication sessions belong in a store.

== Where the books are outdated

Yoon (*Beginning Axum*, chapter 4) authenticates with JWTs only and does not cover server-side sessions. Material
written for tower-sessions 0.9 or earlier enables stores through feature flags of the main crate; since 0.10 the
stores are separate crates (`tower-sessions-memory-store`, `-redis-store`, `-sqlx-store`).
And as noted above, the newest tower-sessions (0.15) is not yet usable with axum-login or the official stores.
