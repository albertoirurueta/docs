[#why]
== Why streams exist

Reading a file with `fs.promises.readFile()` allocates one buffer as big as the file before your code sees the first byte; reading it with a
stream hands you 64 KiB at a time. The next two programs count the lines of a generated catalogue of 6 million rows (about 255 MiB), first
by loading the whole file and then by streaming it. They were run on macOS (arm64) after generating the file with a short script that itself
respects backpressure.

.Loading the whole file into memory
[source,javascript]
----
import { readFile } from 'node:fs/promises';

const data = await readFile('big.csv');          // the whole file in one Buffer
let lines = 0;
for (const byte of data) if (byte === 0x0a) lines++;
console.log({ lines, rssMiB: Math.round(process.memoryUsage().rss / 2 ** 20) });
----

.Streaming the same file in chunks
[source,javascript]
----
import { createReadStream } from 'node:fs';

let lines = 0;
let peak = 0;
for await (const chunk of createReadStream('big.csv')) {   // one 64 KiB chunk at a time
  for (const byte of chunk) if (byte === 0x0a) lines++;
  peak = Math.max(peak, process.memoryUsage().rss);
}
console.log({ lines, peakRssMiB: Math.round(peak / 2 ** 20) });
----

Source: https://nodejs.org/learn/modules/how-to-use-streams[Node.js Learn: How to use streams], https://nodejs.org/docs/latest/api/fs.html#fscreatereadstreampath-options[Node.js API: fs.createReadStream()]

.Observed resident set size (RSS) for the 255 MiB file
[cols="2,2,2"]
|===
|Node.js line |`readFile()` (final RSS) |`createReadStream()` (peak RSS)

|26.10.0 |314 MiB |107 MiB
|24.21.0 |307 MiB |74 MiB
|22.23.3 |302 MiB |79 MiB
|===

An empty Node.js process already uses about 48 MiB, so the whole-file read costs roughly the file size on top of that, while the streaming
version stays near a constant: reading a file twice as large (510 MiB) peaked at 112 MiB against 107 MiB. The exact numbers depend on the
machine and the garbage collector; the shape does not. The advantages of streams, in the order the Node.js Learn guide lists them, are:

* *Memory efficiency.* Memory is proportional to the chunk size, not to the data size. `fs.readFile()` additionally has a hard ceiling:
  a file above 2 GiB fails with `ERR_FS_FILE_TOO_LARGE`, an internal I/O constraint rather than a `Buffer` limit (see
  xref:backend/nodejs/file-system.adoc[File System]).
* *Time to first byte.* The first chunk can be processed, compressed or sent to a client while the rest is still being read.
* *Composition.* Small stages (read, decompress, parse, validate, write) connect with the same few primitives, and the runtime handles the
  flow control between them.

Streams are not free: the documentation warns that when all the data is already in memory, streams only add overhead and complexity. Use them
when the data is large, unbounded (a socket, standard input, a log tail) or when latency matters, and use plain buffers for small values such
as a JSON configuration file.

[#how-it-works]
== How Node.js implements streams

Everything on this page is JavaScript: the `node:stream` module lives in the Node.js core library (the documentation links to
`lib/stream.js`, and error stack traces show frames under `node:internal/streams/`). What makes a stream useful is what is underneath it. An
`fs.ReadStream` asks the libuv thread pool to read a file (see xref:backend/nodejs/event-loop.adoc[The Event Loop]); a `net.Socket` is
a Duplex wrapper around a libuv handle that the operating system's poller (epoll, kqueue or IOCP) watches; a `zlib` stream hands each chunk
to a native compressor running on the thread pool. In every case the JavaScript layer adds the same three things: an internal _buffer_ per
direction, a small state machine (flowing, paused, ended, destroyed) and an `EventEmitter` interface, because all streams are instances of
`EventEmitter`. Their events therefore follow the ordering rules described in
xref:backend/nodejs/events-and-eventemitter.adoc[Events & EventEmitter], including the one that matters most here: an `'error'` event with no
listener throws and, if nothing catches it, terminates the process.

Streams normally carry strings, `Buffer`, `TypedArray` and `DataView` values (see xref:backend/nodejs/buffers-and-binary-data.adoc[Buffers &
Binary Data]). A stream created with the `objectMode` option can carry any JavaScript value except `null`, which is reserved to mean "no more
data". Object mode is a property of the stream and is independent of flowing or paused mode; switching an existing stream into object mode is
not safe, so decide when you create it.

[#types]
== The four stream types

There are four fundamental types, plus one convenience subclass.

.The stream types and where Node.js uses them
[cols="2,4,4"]
|===
|Type |Meaning |Built-in examples

|`Readable`
|A _source_ you consume data from.
|`fs.createReadStream()`, `process.stdin`, the `http.IncomingMessage` (a request on the server, a response on the client), child process `stdout` and `stderr`, `zlib` and `crypto` streams, `net.Socket`

|`Writable`
|A _destination_ you write data to.
|`fs.createWriteStream()`, `process.stdout` and `process.stderr`, `http.ServerResponse` (and the client request), child process `stdin`, `net.Socket`

|`Duplex`
|Both at once, with two independent channels and two independent buffers.
|`net.Socket`, `zlib` and `crypto` streams, the pair returned by `stream.duplexPair()`

|`Transform`
|A `Duplex` whose output is computed from its input.
|`zlib.createGzip()`, `zlib.createGunzip()`, `crypto` ciphers

|`PassThrough`
|A `Transform` that returns its input unchanged; useful as a tap, a placeholder or an adapter.
|Your own code
|===

Source: https://nodejs.org/docs/latest/api/stream.html#types-of-streams[Node.js API: Types of streams]

.A Duplex pair, an echo exchange and a PassThrough tap
[source,javascript]
----
import { PassThrough, duplexPair } from 'node:stream';

const tap = new PassThrough();
let seen = 0;
tap.on('data', (chunk) => { seen += chunk.length; });

// duplexPair() returns two connected Duplex streams, like the two ends of a socket
const [client, server] = duplexPair();
server.on('data', (chunk) => server.write(`echo: ${chunk}`));
client.on('data', (chunk) => console.log(String(chunk)));
client.write('hello');

setTimeout(() => {
  tap.write('abcdef');
  tap.end();
  console.log('PassThrough saw', seen, 'bytes');
  client.destroy();
  server.destroy();
}, 20);
----

[source,text]
----
echo: hello
PassThrough saw 6 bytes
----

Source: https://nodejs.org/docs/latest/api/stream.html#streamduplexpairoptions[Node.js API: stream.duplexPair()]

A `Duplex` is not a `Transform`. A socket reads what the remote peer sent and writes what you send; the two directions are unrelated. A
`Transform` is a `Duplex` where what you read is derived from what you wrote. Because both sides keep a separate buffer, each side applies
backpressure on its own. `stream.duplexPair()` is available since v22.6.0 and v20.17.0 and is mostly useful in tests, where it replaces a real
network connection. The classes you extend to build your own types are covered in
xref:backend/nodejs/implementing-custom-streams.adoc[Implementing Custom Streams].

[#flowing-paused]
== Readable streams: flowing and paused

A `Readable` is always in one of two modes, separate from object mode. In _flowing_ mode data is read from the underlying source automatically
and delivered as fast as possible through `'data'` events. In _paused_ mode nothing is delivered until you call `stream.read()` explicitly. Every
Readable starts paused, and the documentation stresses a rule that explains most surprises: a Readable does not generate data until a
mechanism for consuming or ignoring that data is provided.

Internally the "two modes" are three states, visible in `readable.readableFlowing`: `null` (nobody consumes the stream yet, no data is
produced), `true` (flowing) and `false` (explicitly paused, or halted by backpressure). Data keeps accumulating in the buffer while the value
is `false`; what stops is the delivery of events.

.The three states of a Readable and what moves it between them
[mermaid]
----
stateDiagram-v2
    direction LR
    [*] --> Initial
    Initial: readableFlowing is null
    Flowing: readableFlowing is true
    Paused: readableFlowing is false
    Initial --> Flowing: data listener, pipe() or resume()
    Initial --> Paused: pause() or a readable listener
    Flowing --> Paused: pause(), unpipe() or backpressure
    Paused --> Flowing: resume(), when no readable listener exists
    Flowing --> Ended: end event
    Paused --> Ended: end event, after read() drains the buffer
    Ended --> [*]
----

The transitions in the diagram can be observed directly.

.Watching readableFlowing change
[source,javascript]
----
import { Readable } from 'node:stream';

const r = Readable.from(['a', 'b', 'c', 'd']);
console.log('new            ', r.readableFlowing);          // null: nothing consumes it yet

r.on('data', (chunk) => console.log('data', chunk));
console.log('after on(data) ', r.readableFlowing);          // true: flowing

r.pause();
console.log('after pause()  ', r.readableFlowing, r.isPaused()); // false true

r.on('end', () => console.log('end'));
setTimeout(() => {
  r.resume();
  console.log('after resume() ', r.readableFlowing);        // true again
}, 10);
----

[source,text]
----

after on(data)  true
after pause()   false true
after resume()  true
data a
data b
data c
data d
end
----

Source: https://nodejs.org/docs/latest/api/stream.html#three-states[Node.js API: Three states]

There are four ways to consume a Readable, and the documentation's advice is to pick one per stream and never mix them: combining
`on('data')`, `on('readable')`, `pipe()` and async iteration "could lead to unintuitive behavior".

.Ways to consume a Readable
[cols="2,4,3"]
|===
|Style |How it works |Use it when

|`'data'` event
|Adding a listener switches the stream to flowing mode; chunks are pushed to you as fast as they arrive. If there is no listener, `resume()` makes the data vanish.
|Simple consumers that cannot get ahead of themselves; remember a `'data'` handler has no flow control of its own.

|`'readable'` event and `read()`
|Adding a listener stops flowing mode; you call `read()` in a loop until it returns `null`. While a `'readable'` listener exists `resume()` has no effect.
|Fine control over how much is read (`read(size)`), parsers that need a fixed number of bytes.

|`pipe()` or `pipeline()`
|The runtime connects the Readable to a Writable and applies backpressure.
|Moving data between streams. Prefer `pipeline()` (see below).

|`for await ... of`
|The stream is an async iterable; each loop iteration pulls the next chunk.
|Most application code: backpressure and error propagation come for free.
|===

.Reading with the readable event
[source,javascript]
----
import { Readable } from 'node:stream';

const r = Readable.from(['one', 'two', 'three'], { objectMode: true });

r.on('readable', () => {
  let chunk;
  while ((chunk = r.read()) !== null) console.log('read', chunk);
});
r.on('end', () => console.log('end, readableFlowing =', r.readableFlowing)); // false
----

[source,text]
----
read one
read two
read three
end, readableFlowing = false
----

Source: https://nodejs.org/learn/modules/how-to-use-streams[Node.js Learn: How to use streams]

Two details trip people up. First, for backward compatibility, removing the `'data'` listeners does not pause a stream; call `pause()`
explicitly, and note that even `pause()` does not guarantee the stream stays paused if it has pipe destinations that drain and ask for more.
Second, once a `'readable'` listener has been added, a `'data'` listener added afterwards does not switch the stream back to flowing (in the
check run for this page `readableFlowing` stayed `false`). A stream that is switched to flowing mode with no `'data'` consumer loses its
data.

.Choosing how to consume a Readable
[mermaid]
----
flowchart TD
    start(["I have a Readable"]) --> dest{"Is the data going into a Writable or Transform?"}
    dest -- "yes" --> pipeline["pipeline() from node:stream/promises"]
    dest -- "no, I process it in my code" --> iter{"Do I need exact byte counts from read(size)?"}
    iter -- "no" --> forawait["for await ... of"]
    iter -- "yes" --> readable["readable event and read(size) loop"]
    forawait --> note1["break, return or throw destroys the stream unless readable.iterator with destroyOnReturn false"]
----

[#events-methods]
== Events and methods

Both directions follow the `EventEmitter` API to announce their state. The tables list what you will use daily; every item is Stable.

.Readable events
[cols="2,5"]
|===
|Event |When it fires

|`'data'`
|A chunk is available (flowing mode). With `setEncoding()` the chunk is a string, otherwise a `Buffer`.

|`'readable'`
|Data can be read with `read()`, or the end of the stream was reached. Since v10.0.0 it is always emitted on the next tick after `push()`, and using it requires calling `read()`.

|`'end'`
|There is no more data to consume. It fires only after all the data has been consumed.

|`'pause'`, `'resume'`
|`pause()` or `resume()` changed the flowing state.

|`'error'`
|The implementation failed, or pushed an invalid chunk. It may be emitted at any time.

|`'close'`
|The stream and its underlying resources (a file descriptor, for example) are closed. Nothing is emitted afterwards.
|===

.Writable events
[cols="2,5"]
|===
|Event |When it fires

|`'drain'`
|After `write()` returned `false`: it is appropriate to write again.

|`'finish'`
|After `end()` was called and all data was flushed to the underlying system.

|`'pipe'`, `'unpipe'`
|A Readable started or stopped piping into this Writable; `'unpipe'` is also emitted when this Writable errors while piped.

|`'error'`
|An error occurred while writing or piping. The stream is destroyed unless `autoDestroy` is `false`; after `'error'` only `'close'` should follow.

|`'close'`
|The stream and its resources are closed; always emitted when `emitClose` is on (the default).
|===

.The methods and properties worth knowing
[cols="3,5"]
|===
|Member |Purpose

|`readable.read([size])`, `readable.unshift(chunk)`
|Pull data in paused mode; push a chunk back (useful for parsers that read too far).

|`readable.pause()`, `resume()`, `isPaused()`, `readableFlowing`
|Flow control and the state shown in the diagram above.

|`readable.pipe(destination[, options])`, `unpipe()`
|Connect to a Writable. Returns the destination, so Duplex and Transform streams can be chained. `{ end: false }` keeps the destination open.

|`readable.setEncoding(encoding)`
|Decode chunks to strings correctly, even when a multi-byte character straddles two chunks.

|`readable.readableHighWaterMark`, `readableLength`, `readableEnded`, `readableObjectMode`
|Inspection of the buffer and state.

|`writable.write(chunk[, encoding][, callback])`
|Queue a chunk. Returns `false` when the buffer reached `highWaterMark`. The `chunk` may be a `TypedArray` or `DataView` since v22.0.0.

|`writable.end([chunk])`
|Signal that no more data follows; `'finish'` fires once everything is flushed.

|`writable.cork()`, `uncork()`
|Group several small writes so they reach `_writev()` together, avoiding a stream of tiny system calls.

|`writable.writableNeedDrain`, `writableLength`, `writableHighWaterMark`, `writableEnded`, `writableFinished`
|The write side of the state, used to implement flow control by hand.

|`readable.destroy([error])`, `writable.destroy([error])`
|Immediate teardown; see error handling below.
|===

Source: https://nodejs.org/docs/latest/api/stream.html#api-for-stream-consumers[Node.js API: API for stream consumers]

The event order at the end of a stream is easy to get wrong. For a Readable that ends normally it is `'end'` then `'close'`; for a failure it
is `'error'` then `'close'`; `'close'` is always last.

.Event order, observed
[source,javascript]
----
import { Readable } from 'node:stream';

const r = new Readable({ read() {} });
for (const e of ['pause', 'resume', 'data', 'end', 'error', 'close']) r.on(e, (v) => console.log(e, v ?? ''));

r.push('hello');
r.push(null);                                        // end of data

const f = new Readable({ read() { this.destroy(new Error('boom')); } });
f.on('error', (e) => console.log('f error:', e.message));
f.on('close', () => console.log('f close, destroyed =', f.destroyed));  // 'close' always comes last
f.resume();
----

[source,text]
----
resume
data <Buffer 68 65 6c 6c 6f>
end
f error: boom
f close, destroyed = true
close
----

Source: https://nodejs.org/docs/latest/api/stream.html#event-close[Node.js API: Event: 'close']

Strings are a classic source of silent corruption. When a stream delivers `Buffer` chunks and you convert each one with `toString()`, a chunk
boundary that falls inside a multi-byte UTF-8 character produces replacement characters. `setEncoding()` keeps the incomplete bytes until the rest
arrives.

.Chunk boundaries and multi-byte characters
[source,javascript]
----
import { Readable } from 'node:stream';

const bytes = Buffer.from('café ☕');                      // "☕" takes 3 bytes in UTF-8
const chunks = () => [bytes.subarray(0, bytes.length - 2), bytes.subarray(bytes.length - 2)]; // cut inside it

// Wrong: converting each Buffer on its own can cut a character in two
let wrong = '';
for await (const chunk of Readable.from(chunks(), { objectMode: false })) wrong += chunk.toString();
console.log(JSON.stringify(wrong));                         // "café " followed by replacement characters

// Right: setEncoding() holds back an incomplete character until the rest arrives
const r = Readable.from(chunks(), { objectMode: false });
r.setEncoding('utf8');
let right = '';
for await (const chunk of r) right += chunk;
console.log(JSON.stringify(right));                         // "café ☕"
----

Source: https://nodejs.org/docs/latest/api/stream.html#readablesetencodingencoding[Node.js API: readable.setEncoding()]

`cork()` and `uncork()` exist for writers that produce many tiny chunks. Corked chunks are delivered together to `_writev()` if the stream
implements it; without `_writev()` corking can reduce throughput instead.

.Corking three writes
[source,javascript]
----
import { Writable } from 'node:stream';

const sink = new Writable({
  writev(chunks, callback) {                         // receives every corked chunk at once
    console.log('writev got', chunks.length, 'chunks');
    callback();
  },
  write(chunk, encoding, callback) { console.log('write got 1 chunk'); callback(); },
});

sink.cork();
sink.write('a'); sink.write('b'); sink.write('c');
process.nextTick(() => sink.uncork());               // flush the three chunks together
----

[source,text]
----
writev got 3 chunks
----

Source: https://nodejs.org/docs/latest/api/stream.html#writablecork[Node.js API: writable.cork()]

single chunk, not a sequence of characters.

.Readable.from() and strings

----
import { Readable } from 'node:stream';

console.log(await Readable.from('abc').toArray());              // [ 'abc' ]: a string is ONE chunk

[#backpressure]
== Backpressure and highWaterMark

Backpressure is what makes the memory numbers at the top of this page possible. Whenever a destination is slower than its source (a disk
versus a read, a network client versus a file, gzip versus a disk), data piles up behind the slow part. Without a control, the pile grows
until the process runs out of memory, the garbage collector works harder and harder and everything else on the machine slows down. The
mechanism in Node.js is a feedback signal: a Writable tells its producer when its buffer is full, and the producer stops until the Writable
says it is ready again.

.A pipeline whose destination is slower than its source: how the stop signal travels upstream and how data resumes
image::nodejs-stream-pipeline.svg[Diagram of a stream pipeline with backpressure. A Readable source (fs.createReadStream), a Transform (zlib.createGzip) and a Writable destination (fs.createWriteStream) are connected left to right by arrows labelled chunks. Each stream has an internal buffer drawn as six slots. The destination buffer is completely full because the disk is slower than the reader, so write returns false. Dashed arrows run from right to left: the destination tells the transform to stop writing and wait for drain, and the transform pauses the source so that read is not called again. A legend and five numbered steps describe a cycle: chunks flow, the destination buffer reaches the highWaterMark, upstream stages stop, memory stays bounded, and drain restarts the flow. A footer notes that pipeline and pipe implement the cycle automatically.,width=920]

[#hwm]
=== highWaterMark is a threshold, not a limit

Both `Readable` and `Writable` buffer data internally, and the `highWaterMark` constructor option says when to stop. It is expressed in
bytes for ordinary streams, in UTF-16 code units for streams that work on (but do not decode) strings, and in objects for streams in object
mode. Once the buffered amount reaches the mark, a Readable stops calling its internal `_read()`, and a Writable's `write()` starts returning
`false`. The documentation is explicit that this is a threshold and not a limit: `write()` still accepts the chunk, and nothing enforces a
strict memory ceiling unless an implementation chooses to.

.Default highWaterMark values
[cols="3,2,4"]
|===

[#manual-backpressure]
=== Respecting backpressure by hand

`pipeline()` and `pipe()` implement the whole cycle. When you call `write()` yourself you must do it: if it returns `false`, stop and wait for
`'drain'`. The following Writable is deliberately slow (it needs 5 ms per chunk) and has a 16 KiB threshold, so with 4 KiB writes the
fourth call reports that the buffer is full.

.Waiting for drain
[source,javascript]
----
import { Writable } from 'node:stream';
import { once } from 'node:events';

// A deliberately slow destination: it takes 5 ms to "store" a chunk.
const slow = new Writable({
  highWaterMark: 16 * 1024,                       // 16 KiB threshold (the default is 64 KiB)
  write(chunk, encoding, callback) {
    setTimeout(callback, 5);
  },
});

const chunk = Buffer.alloc(4 * 1024, 'x');        // 4 KiB per write
let drains = 0;

for (let i = 0; i < 20; i++) {
  const ok = slow.write(chunk);
  console.log(`write #${i + 1}: returned ${ok}, buffered ${slow.writableLength} B`);
  if (!ok) {
    await once(slow, 'drain');                    // stop until the buffer has emptied
    drains++;
  }
}
slow.end();
await once(slow, 'finish');
console.log('drain events waited for:', drains);
----

[source,text]
----
write #1: returned true, buffered 4096 B
write #2: returned true, buffered 8192 B
write #3: returned true, buffered 12288 B
write #4: returned false, buffered 16384 B
write #5: returned true, buffered 4096 B
...
write #20: returned false, buffered 16384 B
drain events waited for: 5
----

Source: https://nodejs.org/docs/latest/api/stream.html#event-drain[Node.js API: Event: 'drain'], https://nodejs.org/learn/modules/backpressuring-in-streams[Node.js Learn: Backpressuring in Streams]

`events.once()` returns a promise that settles on the next `'drain'` and rejects if the stream emits `'error'` in the meantime, which is why
the `await` form is safer than registering `once('drain', ...)` yourself. Contrast that with ignoring the return value.

.What happens when write() is ignored
[source,javascript]
----
import { Writable } from 'node:stream';

const slow = new Writable({
  highWaterMark: 16 * 1024,
  write(chunk, encoding, callback) { setTimeout(callback, 5); },
});

const chunk = Buffer.alloc(4 * 1024, 'x');
for (let i = 0; i < 1000; i++) slow.write(chunk);        // ignores the return value

console.log('queued bytes:', slow.writableLength);        // about 4 MB, 250 times the threshold
console.log('needs drain :', slow.writableNeedDrain);     // true
----

[source,text]
----
queued bytes: 4096000
needs drain : true
----

Source: https://nodejs.org/docs/latest/api/stream.html#writablewritechunk-encoding-callback[Node.js API: writable.write()]

Everything was accepted and nothing was lost, but 4 MB is now queued in memory for a 16 KiB-threshold stream. The documentation warns that
writing to a stream that is not draining buffers every chunk until memory is exhausted and Node.js aborts, that high memory usage hurts garbage
collection performance, and that, because a TCP socket may never drain if the remote peer does not read, writing to a socket that is not
draining may lead to a remotely exploitable vulnerability. The same applies to a Transform, which is paused by default until it is piped or has
a `'data'` or `'readable'` listener.

The rules of thumb from the Learn guide, restated:

* If you produce data on demand, wrap it in a Readable and `pipe()` or `pipeline()` it instead of calling `write()` in a loop.
* When you must call `write()`, stop on `false` and resume on `'drain'`.
* In a custom `Readable`, stop calling `push()` as soon as it returns `false`, and wait for the next `_read()` (see
  xref:backend/nodejs/implementing-custom-streams.adoc[Implementing Custom Streams]).
* Never disable backpressure by always returning `true` from `write()`; the Learn guide demonstrates that it makes memory grow and the
  garbage collector work harder.

[#connecting]
== Connecting streams: pipe, pipeline and finished

`readable.pipe(destination)` connects a Readable to a Writable, switches the Readable to flowing mode and applies backpressure. It returns the
destination, so `r.pipe(gzip).pipe(w)` chains. Its weakness is error handling: if the Readable fails, the destination is _not_ closed
automatically, and the documentation says you must close each stream manually to avoid leaks. The next program breaks a source on purpose and
compares both styles.

.pipe() leaves the destination open, pipeline() cleans up
[source,javascript]
----
import { Readable, Writable, pipeline } from 'node:stream';

const failingSource = () => new Readable({
  read() { this.destroy(new Error('disk failure')); },
});
const sink = () => new Writable({ write(chunk, enc, cb) { cb(); } });

// 1. pipe(): the error is NOT propagated, the destination is left open
const a = failingSource();
const aSink = sink();
a.on('error', () => {});                  // without this the process would crash
a.pipe(aSink);
setTimeout(() => console.log('pipe():     destination destroyed =', aSink.destroyed)); // false

// 2. pipeline(): every stream is destroyed and the callback gets the error
const b = failingSource();
const bSink = sink();
pipeline(b, bSink, (err) => {
  console.log('pipeline(): callback error =', err.message);
  console.log('pipeline(): destination destroyed =', bSink.destroyed);          // true
});
----

[source,text]
----
pipeline(): callback error = disk failure
pipeline(): destination destroyed = true
pipe():     destination destroyed = false
----

Source: https://nodejs.org/docs/latest/api/stream.html#readablepipedestination-options[Node.js API: readable.pipe()], https://nodejs.org/docs/latest/api/stream.html#streampipelinestreams-callback[Node.js API: stream.pipeline(), callback form]

`stream.pipeline()` is the recommended way to connect streams (it replaced the third-party `pump` package on Node.js 10 and later). It
forwards errors, destroys every stream when one fails or closes early, and tells you when the whole chain is done. The promise form in
`node:stream/promises` is the one to reach for in modern code.

.Gzip a file with the promise form of pipeline()
[source,javascript]
----
import { createReadStream, createWriteStream } from 'node:fs';
import { createGzip } from 'node:zlib';
import { pipeline } from 'node:stream/promises';

try {
  await pipeline(
    createReadStream('big.csv'),
    createGzip(),
    createWriteStream('big.csv.gz'),
  );
  console.log('compressed');
} catch (err) {
  console.error('failed, and every stream was destroyed:', err.code ?? err.message);
}

try {
  await pipeline(
    createReadStream('does-not-exist.csv'),
    createGzip(),
    createWriteStream('never-created.gz'),
  );
} catch (err) {
  console.error('missing input:', err.code);                  // ENOENT
}
----

[source,text]
----
compressed
missing input: ENOENT
----

Source: https://nodejs.org/docs/latest/api/stream.html#streampipelinesource-transforms-destination-options[Node.js API: stream.pipeline(), promise form], https://nodejs.org/learn/modules/backpressuring-in-streams[Node.js Learn: Backpressuring in Streams]

In the second call the input does not exist, `pipeline()` rejects with `ENOENT` and destroys the gzip and the write streams. Observed: the empty
file `never-created.gz` was still left on disk, because `fs.createWriteStream()` opens its file as soon as it is created. `pipeline()` closes
streams; it does not undo their side effects. For output that must be all-or-nothing, write to a temporary name and rename it after the promise
resolves.

[#pipeline-forms]
=== The forms of pipeline()

.Equivalent ways to run a pipeline
[cols="3,4,3"]
|===
|Form |Notes |Import

|`await pipeline(a, b, c)`
|Resolves when the chain is complete, rejects on the first error. Accepts a last `{ signal }` options object and `{ end: false }`.
|`node:stream/promises`

|`pipeline(a, b, c, callback)`
|Callback form. Since v14.0.0 it waits for `'close'` before calling back, so the underlying file descriptors are released.
|`node:stream`

|`pipeline([a, b, c], callback)`
|Same as above with an array of stages.
|`node:stream`

|`a.pipe(b).pipe(c)`
|No error propagation, no cleanup. Keep it for code that wants to manage that itself.
|(method)
|===

Each stage can be a stream, an iterable or async iterable, a function, or a web stream (since v19.7.0). A function stage receives the previous
stage as an async iterable, and an async generator is the most readable way to write one. The first stage may be a generator without a source
argument; if a source stage does long-running work, honour the `signal` it receives, or the pipeline may never finish.

.An async generator as a transform stage
[source,javascript]
----
import { createReadStream, createWriteStream } from 'node:fs';
import { pipeline } from 'node:stream/promises';

// An async generator is a transform stage: it receives the previous stage as an async iterable.
async function* upperCase(source) {
  for await (const chunk of source) yield chunk.toString().toUpperCase();
}

await pipeline(
  createReadStream('../bookshelf/data/books.csv'),
  upperCase,
  createWriteStream('books-upper.csv'),
);
----

[source,text]
----
TITLE,AUTHOR
DUNE,HERBERT
EMMA,AUSTEN
----

Source: https://nodejs.org/docs/latest/api/stream.html#streampipelinesource-transforms-destination-options[Node.js API: stream.pipeline()]

The `chunk.toString()` call above is safe only for ASCII data. For arbitrary text, call `source.setEncoding('utf8')` first, as the Bookshelf
import below does. The `signal` option cancels the whole chain; when the signal aborts, every stream is destroyed with an `AbortError`.

.Cancelling a pipeline with a timeout, and waiting with finished()
[source,javascript]
----
import { Readable, Writable } from 'node:stream';
import { pipeline, finished } from 'node:stream/promises';

const endless = Readable.from((async function* () {
  let i = 0;
  while (true) { yield `row ${i++}\n`; await new Promise((r) => setTimeout(r, 10)); }
})());
const sink = new Writable({ write(chunk, enc, cb) { cb(); } });

try {
  await pipeline(endless, sink, { signal: AbortSignal.timeout(100) });
} catch (err) {
  console.log(err.name, err.code, err.cause?.name);   // AbortError ABORT_ERR TimeoutError
  console.log('source destroyed:', endless.destroyed, ' sink destroyed:', sink.destroyed);
}

// finished(): wait for a stream whose pipeline you do not own
const r = Readable.from(['x', 'y']);
r.resume();                                         // drain it, otherwise it never finishes
await finished(r);
console.log('finished() resolved, readable ended =', r.readableEnded);
----

[source,text]
----

source destroyed: true  sink destroyed: true
finished() resolved, readable ended = true
----

Source: https://nodejs.org/docs/latest/api/stream.html#streamfinishedstream-options[Node.js API: stream.finished()], https://nodejs.org/docs/latest/api/stream.html#streampipelinesource-transforms-destination-options[Node.js API: stream.pipeline()]

`finished(stream)` resolves when the stream is no longer readable or writable (or has had an error or a premature close, in which case it
rejects). It is the tool for a stream that you did not create and cannot put in a pipeline, such as a request body you only observe. By
default it leaves its `'error'`, `'end'`, `'finish'` and `'close'` listeners attached, on purpose, so that an unexpected late error does not
crash the process; pass `{ cleanup: true }` (v19.1.0 and later) if you reuse the stream afterwards and want them removed.

[#errors-cleanup]
== Error handling and cleanup

Streams make failure handling subtle because a pipeline has several resources (file descriptors, sockets, native compressors) that must all be
released. The rules are short.

* *Every stream that can emit `'error'` needs a handler, or a pipeline that owns it.* An `'error'` event without a listener is thrown as an
  uncaught exception. `pipeline()` and `finished()` attach listeners for you.
* *`destroy(err)` is the teardown primitive.* It releases resources, emits `'error'` (when given an error) and then `'close'`, and is a no-op on
  an already destroyed stream (since v14.0.0). After a Writable is destroyed, `write()` and `end()` produce `ERR_STREAM_DESTROYED`. `end()`
  flushes pending writes; `destroy()` abandons them, so use `end()` when the data matters.
* *`pipeline()` destroys everything except what already finished*: Readable streams that emitted `'end'` or `'close'`, and Writable streams
  that emitted `'finish'` or `'close'`.
* *`autoDestroy` and `emitClose` default to on* for the built-in classes, so a stream destroys itself after `'error'`, `'end'` or `'finish'`
  and then emits `'close'`.

The most common error codes are easy to provoke, which is the best way to learn to recognise them.

.The error codes of misuse and early close
[source,javascript]
----
import { Writable, Readable } from 'node:stream';
import { finished } from 'node:stream/promises';

const w = new Writable({ write(chunk, enc, cb) { cb(); } });
w.on('error', (e) => console.log('writable error:', e.code));
w.end();
w.write('too late');                                  // ERR_STREAM_WRITE_AFTER_END

const w2 = new Writable({ write(chunk, enc, cb) { cb(); } });
w2.destroy();
w2.write('after destroy', (e) => console.log('write callback:', e.code));   // ERR_STREAM_DESTROYED

// A stream closed before it finished: finished() rejects
const r = new Readable({ read() {} });
r.push('partial');
setTimeout(() => r.destroy(), 10);                    // 'close' without 'end'
await finished(r.resume()).catch((e) => console.log('finished rejected:', e.code)); // ERR_STREAM_PREMATURE_CLOSE
----

[source,text]
----
writable error: ERR_STREAM_WRITE_AFTER_END
write callback: ERR_STREAM_DESTROYED
finished rejected: ERR_STREAM_PREMATURE_CLOSE
----

Source: https://nodejs.org/docs/latest/api/errors.html#err_stream_premature_close[Node.js API: ERR_STREAM_PREMATURE_CLOSE], https://nodejs.org/docs/latest/api/stream.html#writabledestroyerror[Node.js API: writable.destroy()]

`ERR_STREAM_PREMATURE_CLOSE` is the code a pipeline reports when one side went away early; the classic case is an HTTP client that disconnects
while you are sending it a file. The general error taxonomy (operational against programmer errors, `cause`) is in
xref:backend/nodejs/errors-and-error-handling.adoc[Errors & Error Handling].

An HTTP response is a Writable, which makes `pipeline()` the natural way to serve a file, with one caveat that the documentation spells out:
when a pipeline fails, it destroys the response and therefore the socket, so you cannot send a nicely formed error afterwards. Decide the status
first. The example opens the file, waits for the `'open'` event (or an error) and only then commits to a status line.

.Serving a file with pipeline(), deciding the status before streaming
[source,javascript]
----
import { createServer } from 'node:http';
import { createReadStream } from 'node:fs';
import { pipeline } from 'node:stream/promises';

const server = createServer(async (req, res) => {
  const file = createReadStream(req.url === '/books' ? '../bookshelf/data/books.csv' : 'missing.csv');
  // Check that the file opens BEFORE the status line is sent, otherwise pipeline()
  // can only destroy the socket if the stream fails later.
  try {
    await new Promise((resolve, reject) => file.once('open', resolve).once('error', reject));
  } catch {
    res.statusCode = 404;
    return res.end('not found');
  }
  res.setHeader('Content-Type', 'text/csv');
  try {
    await pipeline(file, res);                       // res is a Writable: backpressure toward the client
  } catch (err) {
    console.error('transfer aborted:', err.code);    // e.g. ERR_STREAM_PREMATURE_CLOSE when the client leaves
  }
});

server.listen(0, '127.0.0.1', async () => {
  const { port } = server.address();
  for (const path of ['/books', '/nothing']) {
    const r = await fetch(`http://127.0.0.1:${port}${path}`);
    console.log(path, r.status, JSON.stringify(await r.text()));
  }
  server.close();
});
----

[source,text]
----
/books 200 "title,author\nDune,Herbert\nEmma,Austen\n"
/nothing 404 "not found"
----

Source: https://nodejs.org/docs/latest/api/stream.html#streampipelinesource-transforms-destination-callback[Node.js API: stream.pipeline() and IncomingRequest], https://nodejs.org/docs/latest/api/http.html#class-httpincomingmessage[Node.js API: http.IncomingMessage]

Request bodies are Readable streams, response bodies are Writable streams; reading a JSON body by concatenating `'data'` chunks is the
classic way to buffer a request and enforce a size limit. The server side of HTTP is the subject of
xref:backend/nodejs/http-server-fundamentals.adoc[HTTP Server Fundamentals]; the same mechanics in a framework are in
xref:backend/nestjs/file-upload-and-streaming.adoc[File Upload & Streaming in NestJS].

Since v24.2.0 both `readable[Symbol.asyncDispose]()` and `writable[Symbol.asyncDispose]()` are stable. They call `destroy()` with an
`AbortError` and return a promise that fulfils when the stream is finished, so on runtimes that support explicit resource management a stream
can be released by an `await using` declaration. That is also the direction of the deprecation of `stream.addAbortSignal()` for long-lived
resources (DEP0209, documentation only since v26.8.2): prefer `using` for resource cleanup, and keep the `signal` option of `pipeline()` for
cancelling a bounded operation. Cancellation across a whole application is covered in
xref:backend/nodejs/async-context-and-cancellation.adoc[Async Context & Cancellation].

[#async-iteration]
== Async iteration

Every Readable is an async iterable (`Symbol.asyncIterator`, stable since v11.14.0). `for await ... of` pulls one chunk per iteration, applies
backpressure automatically (the stream is read in chunks of `highWaterMark` bytes) and turns a stream error into an exception that a `try`
statement catches. It is the simplest correct way to consume a stream in application code.

.Iterating, and what break does to the stream
[source,javascript]
----
import { createReadStream } from 'node:fs';
import { Readable } from 'node:stream';

const input = createReadStream('../bookshelf/data/books.csv', { encoding: 'utf8' });
let text = '';
for await (const chunk of input) text += chunk;     // backpressure is automatic
console.log(JSON.stringify(text));

// break (or throw, or return) destroys the stream...
const a = Readable.from([1, 2, 3]);
for await (const n of a) { console.log('a', n); break; }
console.log('destroyed after break:', a.destroyed);               // true

// ...unless you ask for an iterator that does not
const b = Readable.from([1, 2, 3]);
for await (const n of b.iterator({ destroyOnReturn: false })) { console.log('b', n); break; }
console.log('destroyed after break:', b.destroyed);               // false
for await (const n of b.iterator({ destroyOnReturn: false })) console.log('b again', n);
----

[source,text]
----
"title,author\nDune,Herbert\nEmma,Austen\n"
a 1
destroyed after break: true
b 1
destroyed after break: false
b again 2
b again 3
----

Source: https://nodejs.org/docs/latest/api/stream.html#readablesymbolasynciterator[Node.js API: readable[Symbol.asyncIterator]()], https://nodejs.org/docs/latest/api/stream.html#readableiteratoroptions[Node.js API: readable.iterator()]

Leaving the loop early destroys the stream, which is what you want for a file you stop reading and a trap if you intended to continue
later. `readable.iterator({ destroyOnReturn: false })` (stable since v24.0.0 and v22.17.0) keeps the stream alive so that a second loop can
resume. The same loop works on async generators, on `readline` interfaces (see
xref:backend/nodejs/console-readline-and-terminal-io.adoc[Console, Readline & Terminal I/O]) and on web streams, and the language-level
mechanics of async iterators are in
xref:programming-languages/javascript/async-javascript.adoc[Asynchronous JavaScript]. The batch iterator protocol of the experimental
`stream/iter` module is a faster variant for byte streams and is previewed in
xref:backend/nodejs/implementing-custom-streams.adoc[Implementing Custom Streams].

[#operators-compose]
== Readable operators and compose

Readable streams have array-like helper methods that return new Readable streams: `map()`, `filter()`, `flatMap()`, `drop()` and `take()`
(stream results, lazy) and `forEach()`, `toArray()`, `some()`, `find()`, `every()` and `reduce()` (promise results, which consume the stream).
All of them are Stability 1 (Experimental) on Node.js 26. They accept an `options` object with `signal` and, for the callbacks of `map()`,
`filter()` and `forEach()`, `concurrency`: an `async` mapper is invoked up to that many times in parallel while the output order is kept.

.Operators: filter, map, take and a concurrent async map
[source,javascript]
----
import { Readable } from 'node:stream';

const titles = await Readable.from(['dune', 'emma', 'ulysses', 'walden', 'beloved'])
  .filter((t) => t.length > 4)
  .map((t) => t.toUpperCase())
  .take(2)
  .toArray();
console.log(titles);                                // [ 'ULYSSES', 'WALDEN' ]

// async functions run concurrently (concurrency option), the output order is kept
const doubled = await Readable.from([1, 2, 3, 4])
  .map(async (n) => n * 2, { concurrency: 2 })
  .toArray();
console.log(doubled);
console.log(await Readable.from([1, 2, 3, 4]).reduce((sum, n) => sum + n, 0));
----

[source,text]
----
[ 'ULYSSES', 'WALDEN' ]
[ 2, 4, 6, 8 ]
10
----

Source: https://nodejs.org/docs/latest/api/stream.html#readablemapfn-options[Node.js API: readable.map()], https://nodejs.org/docs/latest/api/stream.html#readabletakelimit-options[Node.js API: readable.take()]

Two cautions apply. `toArray()` collects every chunk in memory, so it defeats the purpose of streaming on large inputs (the documentation warns
of this); use it for short streams and tests. And `take()` stops the pipeline early, which is the right tool for "give me the first N":
combined with `filter()` it reads only as much of a large source as needed.

`stream.compose()` joins several stages into a single `Duplex`: it writes into the first stage and reads from the last, each stage is piped into
the next through `pipeline()`, and an error in any stage destroys them all, including the outer Duplex. Unlike `pipeline()`, whose first stage is a
Readable and last stage a Writable, forming a closed circuit, the result of `compose()` can be reused and piped further, which makes it the
tool for building a named, reusable processing step. A function passed to it is converted into a stream: an async generator function becomes a
transform, an async iterable a readable, an async function a writable. `readable.compose(stream)` is the method form of
`stream.compose(readable, stream)`.

.Composing a reusable step
[source,javascript]
----
import { compose, Transform, Readable } from 'node:stream';

async function* toUpper(source) {
  for await (const chunk of source) yield String(chunk).toUpperCase();
}
const trim = () => new Transform({
  transform(chunk, encoding, callback) { callback(null, String(chunk).trim()); },
});

// stream.compose(): several stages become ONE Duplex (writes into the first, reads from the last)
const shout = compose(trim(), toUpper);
console.log(await Readable.from(['  dune ', ' emma  ']).pipe(shout).toArray()); // [ 'DUNE', 'EMMA' ]

// readable.compose(): the same idea, starting from a Readable
console.log(await Readable.from(['  dune ', ' emma  ']).compose(toUpper).toArray());
----

[source,text]
----
[ 'DUNE', 'EMMA' ]
[ '  DUNE ', ' EMMA  ' ]
----

Source: https://nodejs.org/docs/latest/api/stream.html#streamcomposestreams[Node.js API: stream.compose()], https://nodejs.org/docs/latest/api/stream.html#readablecomposestream-options[Node.js API: readable.compose()]

A composed Duplex is single-use: build a fresh one (here with a factory function) for every run, because its streams are consumed by the first.
On Node.js 24 and 22 the documentation does not yet mark `stream.compose()` as stable (it became stable in v26.2.0), but in the runs for this
page it behaved identically on all three lines and printed no warning; the observed behaviour is not a stability guarantee.

[#bookshelf]
== Bookshelf: a streaming export and import

Bookshelf stores its catalogue as CSV. The program below exports the 6 million row file gzip-compressed, then imports it again: it decompresses,
splits the bytes into lines in an async generator stage, turns each line into an array in an object mode `Transform`, and finally consumes the
rows in an async function stage. At no point does more than a few chunks of data exist in memory, and a failure in any stage destroys all the
others. Writing your own `Transform` and `Readable` classes, such as a full CSV parser, is the topic of
xref:backend/nodejs/implementing-custom-streams.adoc[Implementing Custom Streams]; the compression side is covered in
xref:backend/nodejs/compression-with-zlib.adoc[Compression with zlib].

.A streaming export and import pipeline
[source,javascript]
----
import { createReadStream, createWriteStream } from 'node:fs';
import { createGzip, createGunzip } from 'node:zlib';
import { pipeline } from 'node:stream/promises';
import { Transform } from 'node:stream';

// Bookshelf: export the catalogue gzip-compressed, then import it back without
// ever holding more than a few chunks in memory.
await pipeline(
  createReadStream('big.csv'),
  createGzip(),
  createWriteStream('catalogue.csv.gz'),
);

let rows = 0;
let largestYear = 0;
await pipeline(
  createReadStream('catalogue.csv.gz'),
  createGunzip(),
  async function* splitLines(source) {                // generator stage: bytes in, lines out
    source.setEncoding('utf8');                       // decode safely across chunk boundaries
    let rest = '';
    for await (const chunk of source) {
      const lines = (rest + chunk).split('\n');
      rest = lines.pop();
      yield* lines;
    }
    if (rest) yield rest;
  },
  new Transform({                                     // classic Transform stage: line in, row out
    readableObjectMode: true,
    transform(line, encoding, callback) { callback(null, String(line).split(',')); },
  }),
  async function (rowsStream) {                       // final stage: consume the rows
    for await (const [, , , year] of rowsStream) {
      rows++;
      largestYear = Math.max(largestYear, Number(year));
    }
  },
);
console.log({ rows, largestYear });
----

[source,text]
----
{ rows: 6000000, largestYear: 2025 }
----

[#books]
== Where the books are outdated

The streams chapter of _Efficient Node.js_ (Samer Buna, O'Reilly 2025) is a good conceptual tour: stream types, the memory comparison between reading
a file whole and streaming it, `pipeline` in both its callback and promise forms, events and methods, paused and flowing modes, backpressure
and `drain`, implementing Readable, Writable, Duplex and Transform, `Readable.from()` with generators, object mode and compression. It is
worth reading next to this page, with these updates and corrections applied:

.Points to check when following the book
[cols="3,5"]
|===
|Topic |Current behaviour

|Module name
|The promise API is `node:stream/promises`, with `stream` in the singular; the book's pipeline listing has a typo in that import path.

|Pausing a stream
|Removing `'data'` listeners does not pause a stream; call `pause()`, and remember pipe destinations can resume it.

|Large-file generators
|A generator or loop that writes a big file must honour the `write()` return value and wait for `'drain'`, as the example earlier on this page does.

|Operators and newer APIs
|The Readable operators are Experimental, `readable.compose()` and `readable.iterator()` are stable since v24.0.0 and v22.17.0, `stream.compose()` since v26.2.0. The book does not cover the Web Streams interop functions, `stream.duplexPair()` or the experimental `stream/iter` module, and DEP0209 is newer than the book.

|Default highWaterMark
|Do not hard-code sizes from any text, including this page: the default changed in v22.0.0 and differs on Windows, so read it with `stream.getDefaultHighWaterMark()`.

|Cipher streams
|Use authenticated encryption (such as AES-256-GCM) rather than an unauthenticated stream mode; see xref:backend/nodejs/crypto-passwords-and-secrets.adoc[Crypto, Passwords & Secrets].
|===

_Node.js Projects_ (Jonathan Wexler, O'Reilly 2025) touches streams only in concept, in its setup chapters, so the Learn guides and the API
reference cited below are the primary sources for this topic.

[#pitfalls]
== Pitfalls and good practice

.Common stream mistakes
[cols="3,4"]
|===
|Mistake |What to do instead

|Reading a big file with `readFile()` and processing it afterwards
|Stream it; remember the 2 GiB `fs.readFile()` ceiling.

|`a.pipe(b).pipe(c)` in production code
|`pipeline()`; it handles errors, cleanup and completion.

|Ignoring the return value of `write()` in a loop
|Wait for `'drain'` (`events.once()`), or build a Readable and `pipeline()` it.

|No `'error'` listener on a stream outside a pipeline
|Attach one, or move the stream into `pipeline()` / `finished()`; an unhandled `'error'` event terminates the process.

|Mixing `'data'`, `'readable'`, `pipe()` and `for await` on one stream
|Choose one consumption style per stream.

|`chunk.toString()` on every chunk of text
|`setEncoding('utf8')` or a `StringDecoder`, because characters can straddle chunk boundaries.

|`toArray()` on a large stream
|Process chunk by chunk; `toArray()` buffers everything.

|`break` out of `for await` and then reusing the stream
|`readable.iterator({ destroyOnReturn: false })`.

|Sending an error page after `pipeline()` failed on a response
|Check the resource opens before the status line is sent, then stream.

|Treating `highWaterMark` as a hard cap
|It is a threshold for pausing; use limits at the application level (maximum body sizes) for hard guarantees.

|Assuming `fs.createWriteStream()` leaves nothing behind after a failure
|It creates the file immediately; write to a temporary path and rename on success.

|Forgetting that streams are single-use
|Create a new stream (or composed Duplex) for every run.
|===
