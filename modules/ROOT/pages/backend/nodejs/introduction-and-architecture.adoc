[#what-node-is]
== What Node.js is

Node.js is an open-source, cross-platform *JavaScript runtime environment*. A runtime is a program that executes code written
in a language and gives that code access to the world outside the language: files, sockets, processes, timers and the
operating system. JavaScript itself has no such access; it only defines values, functions and control flow. Node.js supplies
the missing part, so the same language that animates a web page can also read a file, listen on a port or run a command-line
tool.

Two points are worth fixing early because they are the most common misconceptions:

* *Node.js is not a language.* The code you write is JavaScript (or TypeScript, see
  xref:backend/nodejs/typescript-in-nodejs.adoc[TypeScript in Node.js]); Node.js is the program that runs it.
* *Node.js is not a framework.* It ships low-level building blocks (`node:http`, `node:fs`, `node:stream`, a test runner,
  a package manager client) but no opinion about routing, validation, dependency injection or project layout. Frameworks
  such as Express and Fastify (see xref:backend/nodejs/web-frameworks-express-and-fastify.adoc[Web Frameworks: Express and Fastify])
  or NestJS (see xref:backend/nestjs/introduction-and-architecture.adoc[NestJS Introduction & Architecture]) are libraries
  that run _on_ Node.js.

[#history]
== A short history

[cols="1,3", options="header"]
|===
| When | What happened

| 2008
| Google open-sources V8 on 2 September 2008, the day Chrome launches. V8 compiled JavaScript to machine code instead of
  interpreting it, which is what made server-side JavaScript fast enough to be practical.

| 2009
| Ryan Dahl starts Node.js (the first commit in the `nodejs/node` repository is dated 16 February 2009; version 0.1.0 follows
  on 30 June 2009). The idea is to combine V8 with an event loop so that a server can handle many connections without a

| 2011

| A community fork called io.js moves faster than Node.js. The two code bases are merged under the Node.js Foundation, and

  (LTS) plan with a new major every six months.

| 2018 and later

  and the JS Foundation merge into the OpenJS Foundation, which governs the project today.

| 2026
| Node.js 26 is the last line on the old two-releases-a-year cadence. From Node.js 27 there is one major release per year
  and every line becomes LTS (see xref:backend/nodejs/release-lines-and-lts.adoc[Release Lines & LTS]).
|===

[#architecture]
== Architecture

A running Node.js process is a single executable that links several components together. Knowing which component does what
explains most of Node.js's behaviour, including why it is fast at I/O, why a long loop freezes it, and which problems come
from JavaScript and which from the operating system.

.The Node.js layer stack: your code at the top, the operating system at the bottom
image::nodejs-layer-stack.svg[Layer diagram of Node.js. From top to bottom: your code, the Node.js core library written in JavaScript, C++ bindings and Node-API, V8 and libuv side by side, and the operating system. A side note says one main thread runs all JavaScript while libuv pool threads and workers handle blocking and parallel work.,width=720]

[#v8]
=== V8

V8 is Google's open-source JavaScript and WebAssembly engine, written in C++. It parses JavaScript, compiles it to machine
code with a just-in-time (JIT) compiler, runs it, and manages memory with a garbage collector. V8 implements the ECMAScript
language (syntax, `Promise`, `Map`, classes, `async`/`await`, and so on) but nothing about files or networks. Chrome and
Node.js embed the same engine; the engine version Node.js ships determines which language features are available. Node.js 26
bundles V8 14.6, Node.js 24 bundles V8 13.6 and Node.js 22 bundles V8 12.4 (see the example below), so new syntax usually
reaches Node.js shortly after it reaches Chrome and is not tied to a Node.js release.

[#libuv]
=== libuv

libuv is a C library, originally written for Node.js, that provides the event loop and cross-platform asynchronous I/O. On
Linux it wraps `epoll`, on macOS and BSD `kqueue`, and on Windows I/O completion ports, so Node.js code looks the same on all
of them. libuv also provides timers, TCP/UDP sockets, child-process handling, file-system operations and a *thread pool*
for work that the operating system cannot do asynchronously. The event loop itself is covered in
xref:backend/nodejs/event-loop.adoc[The Event Loop]; here it is enough to know that libuv owns it.

[#bindings]
=== C++ bindings

Between JavaScript and the C and C++ libraries sit the _bindings_: C++ code that exposes native functionality to JavaScript
through V8's embedding API. When `node:fs` calls into the file system, a binding converts the JavaScript arguments, hands the
request to libuv, and later converts the result back into a JavaScript value and schedules your callback or resolves your
promise. These internal bindings are an implementation detail and are not public API. Native addons that need to reach
native code use *Node-API* (Stable), a C interface that stays binary-compatible across Node.js versions (see
xref:backend/nodejs/native-addons-webassembly-and-ffi.adoc[Native Addons, WebAssembly & FFI]).

[#core-library]
=== The JavaScript core library

Most of what you import with the `node:` prefix is written in JavaScript and compiled into the executable: `node:fs`,
`node:http`, `node:stream`, `node:events`, `node:path`, `node:util`, `node:test` and many more. This layer validates
arguments, implements the public API shape (callbacks, promises, streams, events) and delegates the heavy lifting to bindings.
It is also where the Web-platform globals that Node.js adopted live: `URL`, `TextEncoder`, `AbortController`, `EventTarget`,
`structuredClone`, `fetch`, and others (see xref:backend/nodejs/globals-and-web-platform-apis.adoc[Globals & Web Platform APIs]).

[#undici-llhttp]
=== Undici and llhttp

Two HTTP-related components deserve a name because they appear in error messages and version tables:

* *llhttp* is the HTTP/1.x parser used by `node:http` and by Undici. It is a small, generated C parser that replaced the older
  `http-parser` library; its strictness is part of the defence against request-smuggling attacks (see
  xref:backend/nodejs/server-timeouts-limits-and-hardening.adoc[Server Timeouts, Limits & Hardening]).
* *Undici* is the HTTP client that implements the global `fetch`, `Request`, `Response`, `Headers`, `FormData` and `WebSocket`
  (the client class), and which is also published on npm for direct use (see
  xref:backend/nodejs/fetch-and-http-clients.adoc[Fetch & HTTP Clients]). `node:http` and `node:https` are a separate, older
  implementation that shares the llhttp parser.

Other native dependencies bundled in the executable include OpenSSL (TLS and `node:crypto`), zlib (`node:zlib`), c-ares
(asynchronous DNS), ICU (internationalisation) and SQLite (`node:sqlite`).

[#hello-server]
=== A first program that touches every layer

The classic first program is a web server. The listener below is JavaScript (your code), `node:http` is the core library,
the socket is created through a binding and libuv, and the request line is parsed by llhttp. The client side uses the
global `fetch`, which is Undici.

.A server and a client in one file (port 0 asks the operating system for a free port)
[source,javascript]
----
// hello.mjs
import { createServer } from 'node:http';

const server = createServer((req, res) => {
  res.writeHead(200, { 'content-type': 'text/plain; charset=utf-8' });
  res.end('Hello from the Bookshelf\n');
});

server.listen(0, '127.0.0.1', async () => {
  const { port } = server.address();
  const response = await fetch(`http://127.0.0.1:${port}/`);
  console.log(response.status, await response.text());
  server.close();
});
----

.Output (identical on Node.js 26, 24 and 22)
[source,text]
----
200 Hello from the Bookshelf
----

[#io-model]
== The non-blocking I/O model and the single main thread

Node.js runs your JavaScript on *one main thread*. There is no parallel execution of your callbacks: while one function runs,
no other JavaScript function in the same thread can. That sounds like a limitation, and for CPU-heavy work it is, but it
removes a whole class of problems (data races, locks, deadlocks on shared JavaScript objects) and makes server code easy to
reason about.

The model that makes one thread useful is *non-blocking I/O*. A request to read a file, query a database or fetch a URL does
not make the thread wait. Node.js hands the operation to the operating system or to libuv, registers a callback (or a promise),
and returns to the event loop, which keeps running other callbacks. When the operation finishes, the callback is queued and the
loop runs it. Waiting is therefore done by the operating system in parallel, and the single thread is only busy when it is
actually executing JavaScript. A server spends nearly all its time waiting for the network and the disk, which is why one
process can keep thousands of connections open.

[#thread-pool]
=== The libuv thread pool

Not every operation has a non-blocking operating-system interface. File-system calls, `dns.lookup()` (which uses
`getaddrinfo`), and CPU-bound native work in `node:crypto` (`pbkdf2`, `scrypt`, `randomBytes` with a callback) and `node:zlib`
are executed by libuv on a pool of worker threads, four by default. The size is set with the `UV_THREADPOOL_SIZE` environment
variable, which must be set before the pool is first used. The JavaScript you wrote still runs on the main thread: only the
blocking system call is moved off it.

The example below starts eight password-hash computations. With the default pool of four, they complete in two waves.

.Eight PBKDF2 computations on the default pool of four threads
[source,javascript]
----
// pool.mjs
import { pbkdf2 } from 'node:crypto';

const started = performance.now();
let done = 0;
for (let i = 0; i < 8; i++) {
  pbkdf2('password', 'salt', 400_000, 64, 'sha512', () => {
    console.log(`hash ${i} finished after ${Math.round(performance.now() - started)} ms`);
    if (++done === 8) console.log('threadpool size:', process.env.UV_THREADPOOL_SIZE ?? '4 (default)');
  });
}
----

.Output on Node.js 26 (an Apple-silicon laptop; absolute times vary by machine)
[source,text]
----
hash 3 finished after 68 ms
hash 2 finished after 69 ms
hash 0 finished after 69 ms
hash 1 finished after 70 ms
hash 4 finished after 135 ms
hash 5 finished after 137 ms
hash 6 finished after 137 ms
hash 7 finished after 137 ms
threadpool size: 4 (default)
----

The two clusters, about 70 ms and about 137 ms, are the two waves of four. Running the same file with
`UV_THREADPOOL_SIZE=8 node pool.mjs` lets all eight run together (the measured finish times were then all between roughly 80
and 110 ms). Note that the hashing happens on pool threads in true parallel, while the callbacks are delivered one at a time
on the main thread.

[#ordering]
=== Who runs when: the order of callbacks

Because everything is queued, the order of output is determined by the event loop rather than by the order of lines. The
example mixes synchronous code, `process.nextTick`, a promise microtask, a file-read callback, `setImmediate` and a zero-delay
timer.

.Ordering of synchronous code, microtasks and event-loop callbacks
[source,javascript]
----
// order.mjs
import { readFile } from 'node:fs';

console.log('1 main script starts');
readFile(import.meta.filename, () => {
  console.log('5 file read finished (callback runs on the main thread)');
  setTimeout(() => console.log('7 timer (0 ms)'), 0);
  setImmediate(() => console.log('6 setImmediate'));
});
Promise.resolve().then(() => console.log('4 promise microtask'));
process.nextTick(() => console.log('3 process.nextTick'));
console.log('2 main script ends');
----

.Output (identical on Node.js 26, 24 and 22, repeated runs)
[source,text]
----
1 main script starts
2 main script ends
4 promise microtask
3 process.nextTick
5 file read finished (callback runs on the main thread)
6 setImmediate
7 timer (0 ms)
----

The synchronous lines run first. Then the microtask queues are drained; in an ES module the promise microtask ran before the
`nextTick` callback, which is a property of how the module is evaluated, so do not rely on that relative order and prefer
`queueMicrotask()` (`process.nextTick` is Legacy since Node.js 22.7 and 20.18). Finally the loop moves on to I/O callbacks.
Inside an I/O callback `setImmediate` always runs before a zero-delay timer, whereas from the main script their order is not
guaranteed, which is why the example calls them from the file callback. The loop phases are explained in
xref:backend/nodejs/event-loop.adoc[The Event Loop].

Source: https://nodejs.org/learn/asynchronous-work/event-loop-timers-and-nexttick[The Node.js Event Loop]

[#blocking]
=== What blocking costs

The flip side of a single thread is that synchronous CPU work stops everything else. Timers do not fire, sockets are not
serviced and no request gets a response until the function returns.

.A busy loop starves a timer
[source,javascript]
----
// blocking.mjs
const tick = setInterval(() => console.log('tick'), 100);
setTimeout(() => {
  const end = Date.now() + 350;
  while (Date.now() < end) { /* busy loop blocks the only main thread */ }
  console.log('blocked ~350 ms, no tick could run meanwhile');
}, 150);
setTimeout(() => clearInterval(tick), 600);
----

.Output (the timings, not the text, are the lesson)
[source,text]
----
tick
blocked ~350 ms, no tick could run meanwhile
tick
----

Without the busy loop the interval would have fired five times in 600 ms; with it, only two ticks appear. See
xref:backend/nodejs/dont-block-the-event-loop.adoc[Don't Block the Event Loop] for the practical rules.

Source: https://nodejs.org/learn/asynchronous-work/overview-of-blocking-vs-non-blocking[Overview of Blocking vs Non-Blocking]

[#workers]
=== Adding threads: worker threads

When CPU-bound JavaScript is unavoidable, `node:worker_threads` (Stable) runs additional JavaScript threads, each with its own
V8 isolate and event loop. Workers do not share JavaScript objects; they exchange messages (copied or transferred), and can
share raw memory through `SharedArrayBuffer`. The main thread stays free to serve requests.

.A worker computes while the main thread stays responsive
[source,javascript]
----
// worker.mjs
import { Worker, isMainThread, threadId, parentPort, workerData } from 'node:worker_threads';

if (isMainThread) {
  const worker = new Worker(import.meta.filename, { workerData: { n: 40 } });
  worker.on('message', (value) => console.log(`main thread ${threadId} received`, value));
  worker.on('exit', (code) => console.log('worker exited with code', code));
} else {
  const fib = (n) => (n < 2 ? n : fib(n - 1) + fib(n - 2));
  parentPort.postMessage({ threadId, fib: fib(workerData.n) });
}
----

.Output (identical on Node.js 26 and 22)
[source,text]
----
main thread 0 received { threadId: 1, fib: 102334155 }
worker exited with code 0
----

Source: https://nodejs.org/learn/asynchronous-work/dont-block-the-event-loop[Don't Block the Event Loop]

The other ways to use more CPU cores are `node:child_process` (separate processes) and `node:cluster` (several processes
sharing a listening port); all three are compared in xref:backend/nodejs/concurrency-models.adoc[Concurrency Models] and
detailed in xref:backend/nodejs/worker-threads.adoc[Worker Threads] and xref:backend/nodejs/cluster-and-scaling.adoc[Cluster & Scaling].

[#stack-in-action]
=== Following one call down the stack

An `await readFile(...)` crosses every layer of the diagram. The JavaScript core library validates the path, a binding submits
a request to libuv, a pool thread performs the blocking `read` system call, and the result climbs back up to resolve the promise
on the main thread.

.A file read and a DNS lookup, both served by the libuv pool
[source,javascript]
----
// stack.mjs
import { readFile } from 'node:fs/promises';
import { lookup } from 'node:dns/promises';

const started = performance.now();
const text = await readFile(import.meta.filename, 'utf8'); // fs binding, read(2) on the pool
const address = await lookup('localhost');                   // getaddrinfo on the pool
console.log({ characters: text.length, address: address.address, ms: Math.round(performance.now() - started) });
----

.Output on Node.js 26 (the same shape on 24 and 22; the address depends on the host's resolver)
[source,text]
----
{ characters: 494, address: '::1', ms: 4 }
----

Source: https://nodejs.org/learn/getting-started/introduction-to-nodejs[Introduction to Node.js]

[#tracing-a-call]
=== Tracing a file read and a socket through the layers

The same path can be followed in more detail. Take the callback form of `fs.readFile()`:

. *Your code* calls `readFile(path, callback)`.
. *The JavaScript core library* (`lib/fs.js`) validates the arguments, converts the flags, and creates a _request object_
  (`FSReqCallback`, or the request type used by a newer implementation) that holds the callback.
. *A C++ binding* (`src/node_file.cc`) receives the request, converts the JavaScript values into C values and calls a libuv
  function such as `uv_fs_open()` or `uv_fs_read()`.
. *libuv* cannot read a regular file without blocking, so it queues the work on its thread pool. A pool thread performs the
  blocking system call (`open`, `fstat`, `read`, `close`) while the main thread keeps running other JavaScript.
. *The operating system* completes the call. libuv notices the finished work during the event loop's poll phase.
. *Back up the stack*: the binding converts the result to a `Buffer` or an error and calls the request's completion
  function, which runs your callback on the main thread.

A socket takes a different route at step 4. Network I/O has non-blocking operating-system interfaces, so libuv registers the
socket with `epoll`, `kqueue` or an I/O completion port and the pool is not involved; the thread pool is only for work that
the operating system cannot do asynchronously.

[mermaid]
....
sequenceDiagram
    participant JS as Your code (main thread)
    participant Lib as lib/fs.js (core library)
    participant B as C++ binding (node_file.cc)
    participant UV as libuv event loop
    participant Pool as libuv thread pool
    participant OS as Operating system
    JS->>Lib: readFile(path, callback)
    Lib->>B: request object + arguments
    B->>UV: uv_fs_* request
    UV->>Pool: queue blocking work
    Note over JS,UV: main thread returns to the event loop and runs other callbacks
    Pool->>OS: open / fstat / read / close
    OS-->>Pool: bytes or error
    Pool-->>UV: work done
    UV-->>B: completion during the poll phase
    B-->>Lib: Buffer or Error
    Lib-->>JS: callback(err, data) on the main thread
....

The objects that cross the binding layer can be observed. `async_hooks.createHook()` reports every native request and handle
that the C++ layer creates (its type names, such as `FSREQCALLBACK`, `TCPWRAP` and `TCPSERVERWRAP`, are the binding classes).
The API is Stability 1, Experimental, and the documentation asks you to migrate away from it for application code, but it
is the clearest window into this layer for a learning exercise.

.Recording the native resources created by a file read and a TCP round trip
[source,javascript]
----
// trace.mjs
import { createHook } from 'node:async_hooks';
import { readFile } from 'node:fs';
import { createServer, connect } from 'node:net';

// Record the native request and handle objects (the C++ binding layer) that each step creates.
// TickObject (process.nextTick) and PROMISE entries are JavaScript-level and are left out.
let created = [];
const hook = createHook({
  init(asyncId, type) { if (type !== 'TickObject' && type !== 'PROMISE') created.push(type); },
});
hook.enable();
const report = (step) => { console.log(step.padEnd(28), created.join(' → ')); created = []; };

readFile(import.meta.filename, () => {
  report('fs.readFile:');
  const server = createServer((socket) => socket.end('hi\n'));
  server.listen(0, '127.0.0.1', () => {
    report('net server.listen:');
    const client = connect(server.address().port, '127.0.0.1');
    client.on('data', () => report('net connect + accept + data:'));
    client.on('close', () => { report('net close:'); hook.disable(); server.close(); });
  });
});
----

.Output (Node.js 26.10.0, then 24.21.0 and 22.23.3)
[source,text]
----
fs.readFile:                 FSREQCALLBACK
net server.listen:           DNSCHANNEL → TCPSERVERWRAP
net connect + accept + data: TCPWRAP → TCPCONNECTWRAP → TCPWRAP → SHUTDOWNWRAP
net close:                   SHUTDOWNWRAP

fs.readFile:                 FSREQCALLBACK → FSREQCALLBACK → FSREQCALLBACK → FSREQCALLBACK
net server.listen:           DNSCHANNEL → TCPSERVERWRAP
net connect + accept + data: TCPWRAP → TCPCONNECTWRAP → TCPWRAP → SHUTDOWNWRAP
net close:                   SHUTDOWNWRAP
----

Reading the trace:

* On Node.js 24 and 22 the callback `readFile()` makes four separate trips to the thread pool, one request each for open, fstat,
  read and close. On Node.js 26.10.0 the source of `lib/fs.js` performs open, fstat, read and close "in one thread pool
  round trip" for files that fit in one chunk, so the trace shows a single request. The public API did not change; this is
  why the internal bindings are not a contract you should depend on.
* `TCPSERVERWRAP` is the listening socket and each `TCPWRAP` is one end of a connection (the client's, then the accepted
  one on the server). `TCPCONNECTWRAP` is the pending `connect()` request and `SHUTDOWNWRAP` the half-close sent by
  `socket.end()`. None of them involves the thread pool.
* `DNSCHANNEL` is a c-ares resolver channel, created as the DNS machinery is first loaded; the trace shows it is created, not
  that a lookup took place (both addresses in the example are literal IPs).

[#vs-browser]
== Node.js versus the browser

Both environments run JavaScript on V8 (or, in Firefox and Safari, on another engine) and share the language, but the
environment around the language is different.

[cols="2,3,3", options="header"]
|===
| Aspect | Browser | Node.js

| Global object
| `window` (also `self`, `globalThis`)
| `globalThis` (also `global`); there is no `window`

| Page APIs
| DOM, `document`, CSS, `alert`, `localStorage`, canvas
| None. No DOM, no rendering. Web Storage and `navigator` exist but are Release Candidate and Active development; `localStorage` needs `--localstorage-file`

| System access
| Sandboxed: no free file or process access
| Full access to files, processes, network and environment (restrictable with the permission model)

| Module system
| ES modules only (`<script type="module">`)
| ES modules and CommonJS; `require(esm)` is Stable (see xref:backend/nodejs/esm-cjs-interop.adoc[ESM & CommonJS Interop])

| Version control
| You cannot choose the user's browser; you transpile and polyfill for the oldest target
| You choose the Node.js version, so you can use the newest language features your version supports

| Networking
| `fetch`, `WebSocket`, subject to CORS and same-origin rules
| `fetch`, `WebSocket`, plus raw TCP, UDP, HTTP servers, TLS; no CORS (that is a browser policy)

| Concurrency
| Main thread (UI) plus Web Workers
| Main thread plus `worker_threads`, child processes and the libuv pool

| Lifetime
| Lives as long as the page
| Exits when the event loop has nothing left to do, or on `process.exit()`
|===

The difference that matters most for the programmer is control. A browser app must run on whatever the visitor has; a Node.js
app runs on the version you install, so you can use new syntax without a build step. The same simplicity means Node.js code
cannot assume a DOM: libraries that touch `window` or `document` fail on import.

[#behaviour-differences]
=== Behaviour that differs, not only APIs

Some differences do not show up in a feature check because the name exists in both environments but behaves differently.
The example runs four of them in Node.js; the comments say what a browser would do instead.

.Timers, module URLs, binary data and the absence of a same-origin policy
[source,javascript]
----
// env-diff.mjs: the same lines behave differently in Node.js and in a browser
import { createServer } from 'node:http';

// 1. Timers: a browser returns a number, Node.js returns a Timeout object with extra methods.
const t = setTimeout(() => {}, 1000);
console.log('setTimeout returns:', t.constructor.name, '| hasRef():', t.hasRef(), '| as a number:', typeof +t);
t.unref(); // Node.js only: this timer no longer keeps the process alive
clearTimeout(t);

// 2. Module scope: import.meta.url is a file: URL, not an https: URL of a page.
console.log('import.meta.url scheme:', new URL(import.meta.url).protocol);

// 3. Binary data: Buffer is a Node.js subclass of the standard Uint8Array.
const buf = Buffer.from('Bookshelf');
console.log('Buffer extends Uint8Array:', buf instanceof Uint8Array, '| base64:', buf.toString('base64'));

// 4. No same-origin policy: a cross-origin response without CORS headers is fully readable.
const server = createServer((req, res) => res.end(JSON.stringify({ origin: req.headers.origin ?? null })));
server.listen(0, '127.0.0.1', async () => {
  const res = await fetch(`http://127.0.0.1:${server.address().port}/`);
  console.log('cross-origin read without CORS:', res.status, await res.text(),
    '| access-control-allow-origin:', res.headers.get('access-control-allow-origin'));
  server.close();
});
----

.Output (identical on Node.js 26, 24 and 22)
[source,text]
----
setTimeout returns: Timeout | hasRef(): true | as a number: number
import.meta.url scheme: file:
Buffer extends Uint8Array: true | base64: Qm9va3NoZWxm
cross-origin read without CORS: 200 {"origin":null} | access-control-allow-origin: null
----

* *Timers.* In a browser `setTimeout()` returns an integer id. In Node.js it returns a `Timeout` object with `ref()`,
  `unref()`, `hasRef()` and `refresh()`; it still converts to a number, so `clearTimeout(Number(id))` works. An `unref()`-ed
  timer does not keep the process alive, a concept that has no meaning in a page.
* *Module URLs.* `import.meta.url` is a `file:` URL in Node.js, so resolve files with `import.meta.dirname` or
  `new URL('./data.json', import.meta.url)` rather than with string concatenation.
* *Binary data.* Node.js APIs return `Buffer`, a subclass of the standard `Uint8Array`, so browser code that expects a
  `Uint8Array` accepts it, while code that calls `Buffer` methods does not run in a browser.
* *No same-origin policy.* The response is readable even though the server sent no `Access-Control-Allow-Origin`
  header, and Node.js's `fetch` sent no `Origin` header. CORS protects the browser's user; a server-side client is not
  that user, so the check does not apply. The flip side is that your server must not rely on CORS to keep non-browser
  clients out.
* *Failure.* In a browser an uncaught error is logged and the page keeps running. In Node.js an uncaught exception or an
  unhandled rejection terminates the process (see <<criticisms>>).

Code meant to run in both places should feature-detect (`typeof process`, `typeof document`) and stick to the shared
web-standard APIs: `fetch`, `URL`, `TextEncoder`, `crypto.getRandomValues()`, `structuredClone()`, `AbortController`, Web
Streams and `EventTarget`.

Source: https://nodejs.org/docs/latest/api/timers.html#class-timeout[Node.js API: Timers, class Timeout], https://nodejs.org/docs/latest/api/esm.html#importmetaurl[Node.js API: import.meta.url], https://nodejs.org/docs/latest/api/buffer.html#buffers-and-typedarrays[Node.js API: Buffers and TypedArrays] and https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CORS[MDN: Cross-Origin Resource Sharing (CORS)]

[#how-much-js]
=== How much JavaScript you need

The official guidance is that Node.js is an excellent place to learn JavaScript's modern features, because the runtime is
current and you are not limited by browser support. You should be comfortable with variables, functions, objects, arrays,
callbacks, promises and `async`/`await`, and with classes and modules; you do not need to know the DOM. The existing JavaScript
reference in this repository covers the language (for example
xref:programming-languages/javascript/async-javascript.adoc[Asynchronous JavaScript]); this section covers the runtime.

[#vs-deno-bun]
== Node.js versus Deno and Bun

Node.js is no longer the only server-side JavaScript runtime. Two alternatives matter in practice.

[cols="1,2,2,2", options="header"]
|===
| | Node.js | Deno | Bun

| Engine
| V8
| V8
| JavaScriptCore (the engine of Safari)

| Implemented in
| C++ and JavaScript, with libuv
| Rust, with Tokio for asynchronous I/O
| Zig until 1.3; rewritten in Rust for Bun 1.4 (August 2026)

| Origin
| 2009, Ryan Dahl
| Repository created in May 2018 by the same author to redesign the runtime; Deno 1.0 in May 2020
| Started by Jarred Sumner; first public release (v0.1) in July 2022; Bun 1.0 in September 2023

| Defaults
| Full access; opt-in restriction with the permission model (`--permission`, Stable)
| Secure by default: permission flags required for files, network and environment
| Full access, like Node.js

| TypeScript
| Type stripping of erasable syntax (Stable); no type checking
| Runs TypeScript directly, with built-in tooling
| Runs TypeScript directly

| Packages
| npm registry, `node_modules`, `package.json`
| URL and JSR imports as well as npm specifiers
| npm-compatible, with its own fast installer

| Built-in tooling
| Test runner, `--watch`, `--run`, `--env-file`; separate linters and formatters
| Linter, formatter, test runner, benchmarking and more in one binary
| Package manager (`bun install`), bundler (`bun build`), Jest-compatible test runner (`bun test`) in one binary

| Ecosystem and stability
| The largest ecosystem and the longest track record; a defined LTS programme
| Smaller ecosystem; `node:` built-in modules and `npm:` specifiers are supported, with a published compatibility table
| Smaller ecosystem; designed as "a drop-in replacement for Node.js", with a published compatibility status per module
|===

Source: https://docs.deno.com/runtime/[Deno documentation], https://docs.deno.com/runtime/fundamentals/security/[Deno: Security and permissions], https://docs.deno.com/runtime/fundamentals/node/[Deno: Node and npm compatibility], https://deno.com/blog/v1[Deno blog: Deno 1.0], https://bun.sh/docs[Bun documentation], https://bun.com/docs/runtime/nodejs-compat[Bun: Node.js compatibility], https://bun.com/blog/bun-v1.0[Bun blog: Bun 1.0], https://bun.com/blog/bun-v0.1.1[Bun blog: Bun v0.1.1] and https://bun.com/blog/bun-in-rust[Bun blog: Rewriting Bun in Rust]

The table is a snapshot of design choices, not a ranking. All three can run the same ES-module code that uses web-standard
APIs, which is one reason Node.js has steadily adopted web standards (`fetch`, `URL`, Web Streams, `AbortController`,
`WebSocket`). The practical reasons to choose Node.js are the ecosystem, the LTS guarantees, the depth of production tooling
(diagnostics, profilers, APM agents, container images) and the number of engineers who know it. Compatibility claims of other
runtimes change quickly, so test your dependencies on the runtime you intend to deploy rather than assuming parity.

[#portable-code]
=== Writing code that runs on all three

The common subset is large: ES modules, the web-standard globals, and `node:` built-in modules, which both Deno and Bun
implement. Code that sticks to it can be tested on each runtime. The example identifies the runtime through each one's
documented global (`Deno.version`, `Bun.version`, `process.release`) and otherwise uses only shared APIs.

.Runtime detection plus shared APIs
[source,javascript]
----
// runtime.mjs: portable code that uses only web-standard APIs and node: built-ins
import { createHash } from 'node:crypto';   // Deno and Bun both implement node: specifiers

function detectRuntime() {
  if (typeof globalThis.Deno !== 'undefined') return `Deno ${globalThis.Deno.version.deno}`;
  if (typeof globalThis.Bun !== 'undefined') return `Bun ${globalThis.Bun.version}`;
  if (typeof process !== 'undefined' && process.release?.name === 'node') return `Node.js ${process.versions.node}`;
  return 'unknown';
}

const body = JSON.stringify({ title: 'Dune', rating: 5 });
const digest = createHash('sha256').update(body).digest('hex').slice(0, 16);
const url = new URL('/books?sort=title', 'https://bookshelf.example');
console.log(detectRuntime(), '| navigator.userAgent:', navigator.userAgent);
console.log('sha256:', digest, '| URL:', url.searchParams.get('sort'), '| structuredClone:', structuredClone({ a: [1] }).a[0]);
----

.Output (Node.js 26.10.0, then 24.21.0 and 22.23.3)
[source,text]
----
Node.js 26.10.0 | navigator.userAgent: Node.js/26
sha256: 5e6bd6bf64ecbf22 | URL: title | structuredClone: 1
Node.js 24.21.0 | navigator.userAgent: Node.js/24
sha256: 5e6bd6bf64ecbf22 | URL: title | structuredClone: 1
Node.js 22.23.3 | navigator.userAgent: Node.js/22
sha256: 5e6bd6bf64ecbf22 | URL: title | structuredClone: 1

[#use-cases]
== Typical use cases

* *Web servers and APIs.* HTTP and JSON services, GraphQL gateways and backends for single-page and mobile apps (see
  xref:backend/nodejs/http-server-fundamentals.adoc[HTTP Server Fundamentals]).
* *Real-time applications.* WebSockets and server-sent events for chat, dashboards and notifications.
* *Command-line tools and scripts.* Build tools, code generators, linters and automation; a Node.js script starts quickly and
  can use any npm package (see xref:backend/nodejs/building-cli-tools.adoc[Building CLI Tools]).
* *Streaming and data pipelines.* Backpressure-aware streams for files, uploads and transformation.
* *Backends for frontends and proxies.* Aggregating several upstream APIs for a user interface.
* *Tooling for the frontend.* Bundlers, test runners and dev servers run on Node.js even in projects that never deploy it.
* *Serverless functions and microservices.* Fast start-up and small memory footprints.
* *Desktop and embedded hosts.* Electron-style applications and single executable applications (see
  xref:backend/nodejs/single-executable-applications.adoc[Single Executable Applications]); the Model Context Protocol
  servers in xref:ai/mcp/nodejs-servers.adoc[MCP Node.js Servers] are a recent example.

Two of these in miniature. A data pipeline streams rows through compression with backpressure, so memory use stays flat
however many rows there are:

.Streaming one million generated rows through gzip
[source,javascript]
----
// pipeline.mjs: a data pipeline with backpressure, compressing 1,000,000 generated CSV rows
import { pipeline } from 'node:stream/promises';
import { Readable, Writable } from 'node:stream';
import { createGzip } from 'node:zlib';

async function* rows() {
  yield 'id,title,rating\n';
  for (let i = 1; i <= 1_000_000; i++) yield `${i},Book ${i},${(i % 5) + 1}\n`;
}

let raw = 0, compressed = 0;
await pipeline(
  Readable.from(rows()),
  async function* (source) { for await (const chunk of source) { raw += chunk.length; yield chunk; } },
  createGzip(),
  new Writable({ write(chunk, _enc, cb) { compressed += chunk.length; cb(); } }),
);
const mb = (n) => `${(n / 1024 / 1024).toFixed(1)} MiB`;
console.log('rows streamed:', mb(raw), '→ gzip:', mb(compressed));
----

.Output (identical on Node.js 26, 24 and 22)
[source,text]
----

----

[#criticisms]
== Criticisms and limitations

A balanced view of Node.js includes its weak points, most of which follow from the architecture above.

[cols="2,4", options="header"]
|===
| Criticism | Reality today

| CPU-bound work blocks the single main thread
| True. Use worker threads, child processes, or a different technology for heavy computation (see the blocking example above).

| Callback nesting ("callback hell")
| Largely solved by promises and `async`/`await`; modern APIs return promises (`node:fs/promises`, `node:timers/promises`).

| A tiny standard library leads to huge dependency trees
| Better than it was: the core now includes a test runner, `fetch`, `--env-file`, `util.parseArgs`, `util.styleText`,
  `fs.glob` and `node:sqlite`, but supply-chain hygiene remains essential (see
  xref:backend/nodejs/security-best-practices.adoc[Security Best Practices]).

| Unhandled errors crash the process
| By design, for uncaught exceptions and unhandled rejections; handle errors and let a supervisor restart the process (see
  xref:backend/nodejs/errors-and-error-handling.adoc[Errors & Error Handling]).

| Fragmentation between CommonJS and ES modules
| The friction is much reduced by `require(esm)` (Stable) and syntax detection (see
  xref:backend/nodejs/esm-cjs-interop.adoc[ESM & CommonJS Interop]).

| Dynamic typing
| Optional static typing through TypeScript; Node.js runs erasable TypeScript natively but does not type-check it.

| Frequent breaking changes between majors
| Mitigated by the LTS programme, deprecation cycles and codemods (see
  xref:backend/nodejs/upgrading-and-whats-changed.adoc[Upgrading & What Changed]).

| Not the best fit for heavy numeric or machine-learning workloads
| Correct for training; Node.js is more often the orchestration layer around such services.
|===

Source: https://nodejs.org/learn/asynchronous-work/dont-block-the-event-loop[Node.js Learn: Don't Block the Event Loop] and https://nodejs.org/docs/latest/api/process.html#event-uncaughtexception[Node.js API: process, 'uncaughtException']

[source,javascript]
----
// perm.mjs: full access by default, denied under --permission
import { readFileSync } from 'node:fs';
try {
  console.log('read /etc/hosts:', readFileSync('/etc/hosts', 'utf8').length > 0);
} catch (err) {
  console.log(err.code, err.permission, err.resource);
}
----

.Running it (identical on Node.js 26, 24 and 22)
[source,bash]
----
node perm.mjs
node --permission --allow-fs-read="$PWD/perm.mjs" perm.mjs
----

.Output
[source,text]
----
read /etc/hosts: true
ERR_ACCESS_DENIED FileSystemRead /etc/hosts
----

The permission model is a seat belt for trusted code, not a sandbox for hostile code; the details are in
xref:backend/nodejs/permission-model.adoc[The Permission Model].

Source: https://nodejs.org/docs/latest/api/permissions.html#permission-model[Node.js API: Permission Model] and https://nodejs.org/docs/latest/api/errors.html#err_access_denied[Node.js API: ERR_ACCESS_DENIED]

[#what-changed-recently]
== What changed recently

[cols="2,3", options="header"]
|===
| Change | Version and status

| Release model
| Node.js 26 is the last line on the six-month cadence; Node.js 27 starts one major per year with every line becoming LTS.

| Node.js 26 LTS date
| Becomes LTS on 2026-10-28, maintenance from 2027-10-20, end of life 2029-04-30. Node.js 24 moves to Maintenance on
  2026-10-20; Node.js 22 is Maintenance until 2027-04-30; Node.js 20, 23 and 25 are end of life.

| Bundled engine
| V8 12.4 (Node.js 22), 13.6 (24) and 14.6 (26); see the version table above.

| `Temporal`
| Available without flags on Node.js 26 only (measured: object on 26, undefined on 24 and 22).

| `URLPattern`
| Global since Node.js 24, Stability 1 Experimental; undefined on Node.js 22.

| `require(esm)`
| No flag since 22.12; Stable, no longer experimental, in 25.4.

| Type stripping
| Enabled by default in 23.6 and 22.18; Stable in 24.12 and 25.2; `--experimental-transform-types` removed in 26.0.0.

| Permission model
| Added in 20.0.0 as experimental; Stable since 23.5.0 and 22.13.0 for file system, child process and worker
  restrictions. The network flag `--allow-net`, added in 25.0.0, is still Active development (Stability 1.1).

| `process.nextTick`
| Marked Legacy (Stability 3) since 22.7.0 and 20.18.0; prefer `queueMicrotask()`.

| Built-in SQLite
| `node:sqlite` is a Release Candidate (Stability 1.2) since 25.7.0 and needs no flag since 23.4 and 22.13.

| Single executable applications
| Stability 1.1 Active development; `--build-sea` added in 25.5.0.
|===

A fuller per-major summary is in xref:backend/nodejs/upgrading-and-whats-changed.adoc[Upgrading & What Changed].

[#books-outdated]
== Where the books are outdated

Two O'Reilly books were consulted while preparing this section: _Efficient Node.js_ by Samer Buna (2025) and
_Node.js Projects_ by Jonathan Wexler (2025). They are good introductions, but some statements in their opening chapters
have aged since publication:

* Both books assume a baseline of Node.js 18 or 20. Those lines are end of life, so install a current LTS (26, or 24) and
  use `node:26-slim` or `node:24-slim` style images when containerising (see
  xref:backend/nodejs/docker-and-containers.adoc[Docker & Containers]).
* The description of Node.js as having a single thread is correct for JavaScript execution but incomplete; this page names the
  libuv thread pool and `worker_threads`, and the book's coverage of workers is thin compared with the official documentation.
* The permission model is described as being introduced, and experimental. It was added in 20.0.0 as experimental and has
  been Stable since 23.5.0 and 22.13.0 for file system, child process and worker restrictions; the network flag
  `--allow-net` (25.0.0) is still Active development (Stability 1.1).
* Tools the books install from npm now have built-in equivalents: `nodemon` becomes `node --watch`, `dotenv` becomes
  `--env-file`, and a test library can be replaced by `node:test`.
* Corepack is no longer bundled from Node.js 25, contrary to Wexler's appendix on package managers.
* Running TypeScript no longer needs a compile step for erasable syntax, and the experimental transform flag was removed in 26.
* The comparison with Deno and Bun reflects the state of those runtimes at publication time, so treat any feature matrix with
  caution and check the runtimes' own documentation.

Collected book corrections for the whole section are in
xref:backend/nodejs/upgrading-and-whats-changed.adoc[Upgrading & What Changed].
