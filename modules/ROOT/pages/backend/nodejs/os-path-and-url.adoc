[#os]
== node:os: the machine you run on

`node:os` exposes facts about the operating system and the hardware. Most functions are thin wrappers around libuv or around the C library, so
the values are the ones the kernel reports, not something Node.js computes. Two of them deserve a decision rule; the rest are lookups.

.The os functions and properties used most often
[cols="3,4,3"]
|===
|API |What it returns |Use it for

|`os.availableParallelism()`
|An estimate of the default amount of parallelism a program should use; always greater than zero. A wrapper around libuv's `uv_available_parallelism()`.
|Sizing worker pools and cluster forks.

|`os.cpus()`
|One object per logical CPU with `model`, `speed` (MHz) and cumulative `times` in milliseconds (`user`, `nice`, `sys`, `idle`, `irq`). The array is empty when the information is unavailable, for example when `/proc` is missing.
|Reporting hardware and computing CPU load from two samples. Not for sizing pools.

|`os.homedir()`
|The home directory. On POSIX it uses `$HOME` if defined, otherwise it looks up the effective user; on Windows it uses `USERPROFILE` if defined.
|Per-user config and caches. Not a trust boundary: the environment variable wins.

|`os.userInfo()`
|`username`, `uid`, `gid`, `shell`, `homedir` from the operating system itself (`uid` and `gid` are -1 on Windows). Its `homedir` ignores `$HOME`.
|When you need the account's real home regardless of the environment.

|`os.tmpdir()`
|The default directory for temporary files, with no trailing slash. On POSIX it checks `TMPDIR`, `TMP` and `TEMP` in that order and falls back to `/tmp`; on Windows `TEMP` wins over `TMP`.
|Scratch files; combine with `fs.mkdtemp()` for a private directory.

|`os.EOL`
|`"\n"` on POSIX, `"\r\n"` on Windows.
|Writing text files meant for people on the current platform.

|`os.devNull`
|`/dev/null` on POSIX, `\\.\nul` on Windows.
|Discarding output of a child process portably.

|`os.constants`
|Objects `signals`, `errno`, `priority` and `dlopen`, plus the libuv flag `UV_UDP_REUSEADDR`. Not every constant exists on every platform.
|Mapping between numbers and names (`SIGTERM` is 15, `ENOENT` is 2 on Linux and macOS).

|`os.platform()`, `os.arch()`, `os.type()`, `os.release()`, `os.version()`, `os.machine()`
|Strings identifying the OS and CPU architecture the binary was built for.
|Choosing a native binary or reporting diagnostics.

|`os.totalmem()`, `os.freemem()`, `os.uptime()`, `os.loadavg()`, `os.hostname()`, `os.networkInterfaces()`
|Host-level numbers; `loadavg()` is always `[0, 0, 0]` on Windows.
|Health endpoints and diagnostics.

|`os.getPriority()`, `os.setPriority()`
|Scheduling priority of a process, expressed with the `os.constants.priority` values (a nice value on POSIX, a priority class on Windows).
|Lowering the priority of a background batch job.
|===

.A tour of node:os

[#parallelism]
=== availableParallelism() versus cpus().length

The Node.js documentation says plainly that `os.cpus().length` should not be used to calculate the amount of parallelism available to an
application, and gives `os.availableParallelism()` as the replacement. The difference shows up as soon as the process does not own the
whole machine. A container limited with `--cpus=2` on a ten-CPU host still lists ten processors, because `cpus()` describes the host as the kernel
reports it, while `availableParallelism()` asks libuv for what this process may use. Observed on Node.js 26 in the official `node:26` image under
Docker Desktop (ten CPUs in the VM):

.Observed in a container limited to two CPUs (Node.js 26, Docker Desktop)
[source,bash]
----
docker run --rm --cpus=2 node:26 node -e \
  "const os=require('node:os');console.log(os.availableParallelism(), os.cpus().length)"
----

.Output (observed; the second number is the host, the first is what the process may use)
[source,text]
----
2 10
----

Source: https://nodejs.org/docs/latest/api/os.html#osavailableparallelism[Node.js API: os.availableParallelism()]

The decision rule for the _Bookshelf_ worker pool is therefore short: take `availableParallelism()`, cap it at what the work justifies, never go
below one, and let an environment variable override it when an operator knows better. The example starts that many worker threads and joins their
output with `os.EOL`; the worker pool itself is developed in xref:backend/nodejs/worker-threads.adoc[Worker Threads], and the cluster module's use of the same
number in xref:backend/nodejs/cluster-and-scaling.adoc[Cluster & Scaling].

.Sizing a pool of workers from availableParallelism()
[source,javascript]
----
import os from 'node:os';
import { Worker, isMainThread, parentPort, workerData } from 'node:worker_threads';

if (isMainThread) {
  const size = Math.max(1, Math.min(os.availableParallelism(), 4));
  const lines = os.EOL;
  const results = await Promise.all(
    Array.from({ length: size }, (_, i) => new Promise((resolve, reject) => {
      const w = new Worker(new URL(import.meta.url), { workerData: { id: i } });
      w.once('message', resolve).once('error', reject);
    })),
  );
  process.stdout.write(`pool of ${size} workers${lines}${results.join(lines)}${lines}`);
} else {
  parentPort.postMessage(`worker ${workerData.id} ready`);
}
----

.Output on Node.js 26, 24 and 22
[source,text]
----
pool of 4 workers
worker 0 ready
worker 1 ready
worker 2 ready
worker 3 ready
----

Source: https://nodejs.org/docs/latest/api/os.html#osavailableparallelism[Node.js API: os.availableParallelism()], https://nodejs.org/docs/latest/api/worker_threads.html[Node.js API: Worker threads]

[#tmpdir]
=== Where temporary files go

`os.tmpdir()` is not a constant, it is a function of the environment, and that is a feature: an operator can redirect all temporary files of a
process by setting `TMPDIR` (POSIX) or `TEMP` (Windows) without touching the code. The same applies to `os.homedir()`, which is why neither is
a security boundary. A predictable file name directly inside a shared temporary directory is also a classic attack surface, so create a fresh private
directory with `fs.mkdtemp(path.join(os.tmpdir(), 'bookshelf-'))` (see xref:backend/nodejs/directories-glob-and-watch.adoc[Directories, Glob & Watch]) instead of writing `os.tmpdir() + '/cache.json'`.

.Overriding the temporary directory from the environment
[source,javascript]
----
import os from 'node:os';
console.log(os.tmpdir());
console.log(os.userInfo().homedir === os.homedir());
----

.Run with TMPDIR=/var/tmp/bookshelf (identical on Node.js 26, 24 and 22)
[source,text]
----

true
----

Source: https://nodejs.org/docs/latest/api/os.html#ostmpdir[Node.js API: os.tmpdir()]

[#path]
== node:path: building and taking apart file paths

A path is just a string until the file system gets it, and `node:path` is the module that manipulates those strings the way the current platform expects.
It never checks that a file exists, never follows symbolic links, and never touches the disk; that is why its functions are synchronous and why the
Learn article on file paths points out that neither `resolve()` nor `normalize()` verify that the result exists. The default flavour follows the operating
system the code runs on, so the same call can give different answers on Linux and Windows. Two properties expose both flavours at once:
`path.posix` and `path.win32` always behave like the platform they are named after, and `path.posix.posix` and `path.win32.win32` point back to themselves.

.The path functions and what they decide
[cols="2,5,3"]
|===
|Function |Behaviour |Watch out for

|`path.join(...segments)`
|Joins the segments with the platform separator and normalizes the result. Zero-length segments are ignored; an empty result is `'.'`.
|`join()` keeps a leading `..` and never anchors to the working directory, so it does not make a path absolute.

|`path.resolve(...segments)`
|Processes the segments from right to left until an absolute path is built, then falls back to the current working directory. The result is normalized and has no trailing slash (except the root).
|A later absolute segment discards everything before it. The result depends on `process.cwd()`.

|`path.relative(from, to)`
|The relative path that leads from `from` to `to`, both resolved first. Returns an empty string for equal paths.
|On Windows, two different drives have no relative path, so `to` is returned absolute.

|`path.parse()` and `path.format()`
|Split a path into `root`, `dir`, `base`, `name` and `ext`, and build it back. In `format()`, `dir` wins over `root`, and `base` wins over `name` and `ext`.
|`ext` includes the dot, and only the last one: `cover.final.png` has name `cover.final`.

|`path.basename()`, `path.dirname()`, `path.extname()`
|The last segment (optionally without a suffix), the parent directory, the extension of the last segment.
|`extname('c.tar.gz')` is `'.gz'`, and `extname('.bashrc')` is the empty string.

|`path.normalize()`
|Collapses `.`, `..` and repeated separators.
|It does not check the result stays inside any directory.

|`path.isAbsolute()`, `path.sep`, `path.delimiter`
|Whether a path is absolute; the segment separator (`/` or `\`); the `PATH`-style list delimiter (`:` or `;`).
|`delimiter` is what splits environment variables such as `PATH`.

|`path.toNamespacedPath()`
|On Windows returns the `\\?\` form for long paths; a no-op on POSIX.
|Rarely needed by application code.
|===

.The core path functions on Bookshelf paths
[source,javascript]
----

console.log(path.join('a', '', 'b', '.'));
console.log(path.join(''));
console.log(path.resolve('/srv/bookshelf', './uploads'));
console.log(path.resolve('/srv/bookshelf', '/tmp/file/'));
console.log(path.resolve('a', 'b') === path.join(process.cwd(), 'a', 'b'));
console.log(path.relative('/srv/bookshelf/data', '/srv/bookshelf/uploads/a.png'));
console.log(path.normalize('/users/joe/..//test.txt'));
console.log(path.parse('/srv/bookshelf/uploads/cover.final.png'));
console.log(path.format({ dir: '/srv/bookshelf', name: 'catalog', ext: 'json' }));
console.log(path.basename('/a/b/c.txt'), path.basename('/a/b/c.txt', '.txt'), path.dirname('/a/b/c.txt'), path.extname('c.tar.gz'), path.extname('.bashrc'));
console.log(path.isAbsolute('/a'), path.isAbsolute('a'), path.sep, path.delimiter);
----

The difference between the first two functions is the one people trip over. `join()` is concatenation plus cleanup and works on any strings, even
if the first one is relative; `resolve()` is "what absolute path would the shell reach by `cd`-ing through these arguments", so a segment that
starts with `/` restarts the walk, and a relative result is anchored to the working directory. Use `join()` to assemble a path below a known base, and
`resolve()` when you need an absolute path or want to compare two paths.

[#posix-win32]
=== path.posix and path.win32

Because the default flavour depends on the host, a program that parses Windows paths on Linux (a build tool reading a manifest, a log analyser) or builds
POSIX paths on Windows (the keys of an object store, the entries of a ZIP archive, the paths inside a URL) must say which rules it wants. The documentation's own example
is `basename('C:\\temp\\myfile.html')`, which returns the whole string on POSIX because a backslash is an ordinary character there. On Windows Node.js also follows
the per-drive working directory concept: `path.resolve('C:\\')` and `path.resolve('C:')` can differ.

.Forcing a path flavour regardless of the host
[source,javascript]
----
import path from 'node:path';

console.log(path.win32.basename('C:\\temp\\myfile.html'));
console.log(path.posix.basename('C:\\temp\\myfile.html'));
console.log(path.win32.join('C:\\', 'Users', 'ana', '..', 'bob'));
console.log(path.win32.resolve('C:\\data', '..\\logs', 'app.log'));
console.log(path.win32.parse('C:\\Users\\ana\\notes.txt'));
console.log(path.win32.relative('C:\\data\\a', 'C:\\data\\b\\c'));
console.log(path.win32.relative('C:\\data', 'D:\\data'));
console.log(path.win32.sep, path.posix.sep, path.win32.delimiter, path.posix.delimiter);
console.log(path.win32.toNamespacedPath('C:\\temp\\file.txt'));
console.log(path.posix.toNamespacedPath('/tmp/file.txt'));
console.log(path.posix === path.posix.posix, path.win32.win32 === path.win32);
----

A practical rule: paths that name something on the local disk use the default `path`; paths that name something elsewhere (an object key, a path inside a URL,
a path inside an archive) use `path.posix`, so they look the same on every developer machine.

[#matches-glob]
=== path.matchesGlob()

`path.matchesGlob(path, pattern)` answers "does this path match this glob?" without touching the disk, which is the half of globbing that `fs.glob()` does not need a file system for.
It is useful for ignore lists, routing of file-change events and test-file selection. Both arguments must be strings, otherwise a `TypeError`
(code `ERR_INVALID_ARG_TYPE`) is thrown. The function is Stability 2 (Stable) from v24.8.0 and v22.20.0; on earlier releases of the 22 and 20 lines it was experimental.
The matching directory-walking counterpart, `fs.glob()`, is covered in xref:backend/nodejs/directories-glob-and-watch.adoc[Directories, Glob & Watch].

[#traversal]
=== Joining untrusted input: the traversal check

`path.join(root, name)` does exactly what its name says, so when `name` comes from a request, `'../secret.txt'` or `'/etc/passwd'` walks right out of `root`.
The last line of the example below shows the escape. The safe pattern has three steps: resolve the candidate against the base, compute the relative path from the base back to
the candidate, and reject anything that starts by climbing out (`..` as the whole result or followed by a separator) or that is absolute. Testing
`rel.startsWith('..')` alone also rejects a legitimate file named `..notes`, which is why the example checks for `..` followed by the separator.

.A traversal-safe join for the Bookshelf uploads directory
[source,javascript]
----
import path from 'node:path';

const root = path.resolve('/srv/bookshelf/uploads');

function safeJoin(base, untrusted) {
  const target = path.resolve(base, untrusted);
  const rel = path.relative(base, target);
  if (rel === '' || rel === '..' || rel.startsWith(`..${path.sep}`) || path.isAbsolute(rel)) {
    throw new RangeError(`path escapes ${base}: ${untrusted}`);
  }
  return target;
}

for (const name of ['cover.png', 'a/b.txt', '../secret.txt', '/etc/passwd', 'x/../../uploads-evil/a']) {
  try { console.log('ok  ', safeJoin(root, name)); }
  catch (e) { console.log('deny', e.message); }
}
console.log(path.join(root, '../secret.txt'));
----

.Output on Node.js 26, 24 and 22 (POSIX)
[source,text]
----
ok   /srv/bookshelf/uploads/cover.png
ok   /srv/bookshelf/uploads/a/b.txt
deny path escapes /srv/bookshelf/uploads: ../secret.txt
deny path escapes /srv/bookshelf/uploads: /etc/passwd
deny path escapes /srv/bookshelf/uploads: x/../../uploads-evil/a
/srv/bookshelf/secret.txt
----

Source: https://nodejs.org/docs/latest/api/path.html#pathresolvepaths[Node.js API: path.resolve()], https://nodejs.org/docs/latest/api/path.html#pathrelativefrom-to[Node.js API: path.relative()]

This check is purely lexical. It does not see symbolic links, so a symlink inside `uploads/` that points elsewhere still passes; if that matters, resolve the final path with
`fs.realpath()` and run the same comparison on it. Generated names (a random identifier plus a fixed extension, never the client's file name) remove the problem at the source,
and the opt-in permission model, which confines file system access for the whole process, is the second layer (see xref:backend/nodejs/permission-model.adoc[Permission Model]).

[#url]
== URLs: the WHATWG URL API

Node.js implements the WHATWG URL Standard, the same one browsers implement, and exposes it as the global classes `URL` and `URLSearchParams` (and, experimentally, `URLPattern`).
The classes are also importable from `node:url`, where `URL === globalThis.URL` is true. Code written for Node.js therefore runs unchanged in a browser, a service worker or another runtime.
Every property of a `URL` is a getter and setter on the prototype rather than a data property, so `Object.keys(url)` is empty and `delete url.protocol` has no effect; use
`url.href`, `url.toString()` or `url.toJSON()` (all identical) to get the whole string, and `JSON.stringify()` calls `toJSON()` for you.

.The parts of a URL and the property that reads or writes each
[cols="2,3,4"]
|===
|Property |Example value for `https://ana:example-only@api.bookshelf.test:8443/v1/books/42?tag=node#reviews` |Notes

|`protocol`
|`https:`
|Includes the colon. Invalid values assigned to it are ignored.

|`username`, `password`
|`ana`, `example-only`
|They are part of `href`, so a URL with credentials in it must never be logged or put in an error message.

|`host`, `hostname`, `port`
|`api.bookshelf.test:8443`, `api.bookshelf.test`, `8443`
|`port` is the empty string when it equals the scheme default, so a port equal to the default of the current scheme is dropped (the example shows it).

|`origin`
|`https://api.bookshelf.test:8443`
|Read-only. It is the string `'null'` for schemes without an origin such as `data:` and `file:`.

|`pathname`
|`/v1/books/42`
|Setting it percent-encodes what needs encoding.

|`search`, `searchParams`
|`?tag=node`, a live `URLSearchParams`
|Changes to `searchParams` update `search` and `href`, and the other way round.

|`hash`
|`#reviews`
|Never sent to a server; the browser keeps it.
|===

Parsing is strict. `new URL(input, base)` throws a `TypeError` with `code` `ERR_INVALID_URL` when `input` cannot be parsed, and `input` is the offending string. Relative references need
a base. Two helpers avoid the `try`/`catch` when you only want to know: `URL.canParse(input, base)` returns a boolean, and `URL.parse(input, base)` (added in v22.1.0) returns a `URL` or `null`.

[#search-params]
=== URLSearchParams

`URLSearchParams` is the query string as a list of name and value pairs, in order, with duplicates allowed. It is reachable as `url.searchParams` (live) or constructible from a string, a plain object or an array
of pairs. It percent-encodes on output (with `+` for spaces, the `application/x-www-form-urlencoded` convention), decodes on input, is iterable, and has `size`, `has(name, value)`, `delete(name, value)`
and `sort()`. Values are always strings: an array value in an object is joined with commas and `undefined` becomes the text `undefined`, so build repeated keys with `append()`.

.Building, reading and encoding query strings
[source,javascript]

params.delete('tag', 'cjs');
params.sort();
console.log([...params], Object.fromEntries(params));
console.log(new URLSearchParams('a=1&a=2&b=%20x+y&c').toString());
console.log(new URLSearchParams([['x', '1'], ['y', 'ü']]).toString());

const url = new URL('https://api.bookshelf.test/books');

[#url-pattern]
=== URLPattern: routing without a framework

`URLPattern` matches URLs, or parts of URLs, against a pattern, using the syntax of the URL Pattern Standard (named groups such as `:id`, an optional regular expression in parentheses, wildcards,
optional groups in braces). It was added as a class in v23.8.0 and became a global in v24.0.0. The documentation marks it Stability 1 (Experimental), but on the lines tested here it printed no experimental warning:
it is `'function'` on Node.js 26 and 24 and not defined on Node.js 22, so code that must run on 22 needs a fallback (a small hand-written matcher, or a router library).
`new URLPattern(init, options)` accepts a URL string or an object with `protocol`, `username`, `password`, `hostname`, `port`, `pathname`, `search`, `hash` and `baseURL`; the only option listed in the Node.js documentation is `ignoreCase`.
`pattern.test(input)` returns a boolean and `pattern.exec(input)` returns, for every component, an object with the matched `input` and the named `groups` (unnamed wildcards get numeric group names).
A pattern that omits a component matches anything in it, so a pattern with only `pathname` matches any host.

.Matching and extracting groups with URLPattern
[source,javascript]

The same class makes the Bookshelf API's router small: a table of patterns, each tried against `new URL(req.url, base).pathname`. Two details matter. The base is a constant,

full REST API is built in xref:backend/nodejs/building-a-rest-api.adoc[Building a REST API].

.A tiny router for node:http built on URLPattern (Node.js 26 and 24)
[source,javascript]
----
import http from 'node:http';

const BASE = 'http://bookshelf.invalid';          // never trust the Host header for this
const routes = [
  ['GET', new URLPattern({ pathname: '/books/:id(\\d+)' }), (m, url) => ({ id: Number(m.pathname.groups.id), fields: url.searchParams.get('fields') })],
  ['GET', new URLPattern({ pathname: '/books' }), (m, url) => ({ page: Number(url.searchParams.get('page') ?? 1) })],
];

const server = http.createServer((req, res) => {
  const url = new URL(req.url, BASE);
  for (const [method, pattern, handler] of routes) {
    const match = req.method === method && pattern.exec({ pathname: url.pathname });
    if (match) {
      res.setHeader('content-type', 'application/json');
      return res.end(JSON.stringify(handler(match, url)));
    }
  }
  res.statusCode = 404;
  res.end('not found');
});

server.listen(0, '127.0.0.1', async () => {
  const { port } = server.address();
  for (const p of ['/books/42?fields=title', '/books?page=3', '/books/abc', '/books/..%2f..%2fetc']) {
    const r = await fetch(`http://127.0.0.1:${port}${p}`);
    console.log(r.status, p, await r.text());
  }
  server.close();
});
----

[#file-urls]
== File URLs and file paths

A module's identity in ESM is a URL, not a path: `import.meta.url` is a `file:` URL such as `file:///srv/bookshelf/src/server.js`. Converting between the two worlds is the job of two functions
in `node:url`, and doing it by hand (`new URL(...).pathname`, string slicing) is wrong in ways that only show up on some platforms: the pathname of a file URL is still percent-encoded
(`/hello%20world`), and on Windows it carries a leading slash before the drive letter (`/C:/path/`). `fileURLToPath(url)` decodes it and returns a valid absolute path for the platform, `pathToFileURL(path)`
resolves the path to absolute and encodes characters that are special in URLs (`#`, `%`, `?`, spaces). Both accept a `windows` option (v22.1.0 and v20.13.0) to force the Windows or POSIX interpretation, which is how the
example below can show Windows results on any platform. `fileURLToPath()` throws for non-`file:` URLs (`ERR_INVALID_URL_SCHEME`), for URLs with a host on POSIX (`ERR_INVALID_FILE_URL_HOST`) and for
encoded slashes (`ERR_INVALID_FILE_URL_PATH`). `url.fileURLToPathBuffer()` (v24.3.0 and v22.18.0) returns a `Buffer` for names that are not valid UTF-8.

In ESM you rarely need the conversion for the current module: `import.meta.filename` and `import.meta.dirname` already give the path of the current file and its directory (see
xref:backend/nodejs/ecmascript-modules.adoc[ECMAScript Modules]); CommonJS has `__filename` and `__dirname` (see xref:backend/nodejs/commonjs-modules.adoc[CommonJS Modules]).
Use `new URL('./data/catalog.json', import.meta.url)` to build a URL relative to the module, which `fs` functions also accept.

.Converting between file paths and file URLs

console.log(new URL('file:///hello world').pathname, fileURLToPath('file:///hello world'));
console.log(new URL('./data/catalog.json', import.meta.url).pathname.endsWith('/data/catalog.json'));

[#legacy]
== Why url.parse() and querystring are legacy

Before the WHATWG classes existed, Node.js had its own URL API, now called the legacy API: `url.parse()`, `url.format(urlObject)`, `url.resolve()` and the plain `urlObject` they use, together with the
`node:querystring` module. The two have different statuses, and the difference is worth knowing.

.Status of the old APIs (Node.js 26 documentation)
[cols="3,3,5"]
|===
|API |Status |Why and what to use instead

|Legacy URL API section (`urlObject`, `url.format(urlObject)`)
|3 Legacy
|The deprecation announced in v11.0.0 was revoked in v15.13.0 and v14.17.0 and the API was labelled Legacy: it is kept for compatibility. Use the WHATWG classes in new code.

|`url.parse()`, `url.format(urlString)`, `url.resolve()`
|0 Deprecated; DEP0169 is an application deprecation since v24.0.0
|`url.parse()` uses a lenient, non-standard algorithm that is prone to host-name spoofing and to wrong handling of user names and passwords, and CVEs are not issued for its vulnerabilities. `format(urlString)` and `resolve()` call it internally. Use `new URL()` and `URL.parse()`.

|`node:querystring`
|2 Stable (not deprecated)
|It is not standardized and has behaviour of its own (see the example). The documentation says it is faster than `URLSearchParams`, which should be preferred unless performance is critical or browser compatibility matters.
|===

.What the two modules do differently from the WHATWG classes
[source,javascript]
----
import url from 'node:url';

// 1. The legacy result shape
const input = 'https://user:pw@example.com:8080/p/a/t/h?query=string#hash';

  const l = url.parse(s);
  let w;
  try { w = new URL(s).href; } catch (e) { w = e.code; }
  console.log(JSON.stringify(s), '\n  legacy  :', l.hostname, l.port, l.pathname, '\n  WHATWG  :', w);
}

// 3. Relative and format helpers
console.log(url.resolve('https://a.test/one/two', '../three'), new URL('../three', 'https://a.test/one/two').href);
console.log(url.format({ protocol: 'https', hostname: 'a.test', pathname: '/x', query: { a: 1 } }));
console.log(url.format(new URL('https://u:p@a.test/x?y=1#z'), { auth: false, fragment: false }));

as `URLSearchParams` does, and encodes a space as `%20` where `URLSearchParams` writes `+`. If you keep using `querystring`, keep it for the
server-side cases it was written for and put an allow-list of known keys on its output; for everything that shares code with a browser, use `URLSearchParams`.

.Common legacy idioms and their replacements
[cols="3,4"]
|===
|Legacy |Replacement

|`url.parse(req.url, true)` in a server
|`new URL(req.url, 'http://bookshelf.invalid')` with a constant base, then `url.searchParams`; never build the base from the `Host` header or from `x-forwarded-*` headers unless a trusted proxy sets them.

|`url.parse(s).query` as an object
|`Object.fromEntries(url.searchParams)` (last value wins) or `url.searchParams.getAll(name)`.

|`url.resolve(from, to)`
|`new URL(to, from).href`.

|`+url.format({ protocol, hostname, pathname, query })+`
|Set `protocol`, `hostname`, `pathname` and `searchParams` on a `URL`, or use `url.format(urlInstance, options)` (still current) to leave out parts such as credentials or the fragment.

|`url.parse(s).hostname` to validate a host
|`URL.parse(s)?.hostname` (returns `null` on bad input instead of guessing), compared against an allow-list.

[#pitfalls]
== Pitfalls

.Mistakes that recur with these modules
[cols="3,5"]
|===
|Mistake |What to do instead

|Using `os.cpus().length` to size a pool
|Use `os.availableParallelism()`; it respects the CPUs the process may use, which matters in containers.

|Assuming `os.tmpdir()` or `os.homedir()` are fixed
|They follow environment variables. Create private subdirectories with `fs.mkdtemp()` and do not trust them as a security boundary.

|Joining untrusted names onto a base with `path.join()`
|Resolve, compute the relative path and reject `..` and absolute results; use generated names where you can; add `realpath()` if symbolic links are possible.

|Hardcoding `/` or `\` in a path
|Build paths with `path.join()` or `path.resolve()`; use `path.posix` for keys and URL paths.

|Parsing a Windows path on Linux (or the reverse) with the default `path`
|Use `path.win32` or `path.posix` explicitly.

|Reading `new URL('file:///...').pathname` as a path
|Use `fileURLToPath()`. The pathname is still percent-encoded and, on Windows, begins with a slash before the drive letter.

|Trusting `fileURLToPath()` to stay inside a directory
|Check the converted path with the same traversal test you use for any path.

|Concatenating strings into URLs and query strings
|Use `new URL(relative, base)` and `searchParams.set()` or `append()`.

|Logging `url.href` of a URL that may contain credentials
|Log `url.origin + url.pathname`, or clear `username` and `password` first.

|Building the base URL of a request from the `Host` header
|Use a configured constant, or a trusted proxy's header only when you control the proxy.

|Using `URLPattern` on Node.js 22 without a check
|Test `typeof URLPattern` first, or require Node.js 24 or later. Remember it is still Experimental.

|Using `url.parse()` or `url.resolve()` in new code
|Use `URL` and `URL.parse()`. DEP0169 warns on 24 and later.
|===

[#books]
== Where the books are outdated or incomplete

_Efficient Node.js_ (Samer Buna, O'Reilly 2025) lists `node:os`, `node:path` and `node:url` in a one-line-each table of built-in modules and then uses them only in passing. Its cluster example sizes the number of
workers with `os.availableParallelism()`, which is the current API, but it describes the result as a number up to what `os.cpus().length` reports; as the container example above shows, the two can differ,
and the point of the newer function is exactly that it does not report the host. Several of its HTTP examples route by comparing `req.url` with literal strings in a `switch`; that value includes the query string, so `/compute?n=5` would not
match `/compute`, and the page-level fix is to parse `req.url` with `new URL()` against a constant base and compare `pathname`, or to use `URLPattern` on Node.js 24 and later. The book treats
`__dirname` and `import.meta.dirname` as alternatives, which is right, but it does not cover `fileURLToPath()` and `pathToFileURL()`, which are what ESM needs for everything that is not the current file, and it says nothing about `path.matchesGlob()`,
`URLPattern` or the legacy status of `url.parse()` (an application deprecation since Node.js 24.0.0).

_Node.js Projects_ (Jonathan Wexler, O'Reilly 2025) builds its projects on frameworks and does not teach these modules. Where it needs a path it resolves a relative file name with `path.resolve()`, which is correct, and where it composes
HTTP addresses for the peers of its blockchain project and for API calls it concatenates strings with template literals. That works while every piece is trusted; once a piece
comes from a user, use `new URL()` and `searchParams` so that the encoding is done for you.

.Quick corrections for older tutorials and books
[cols="3,4"]
|===
|Statement you may meet |Current situation

|"Use `os.cpus().length` to decide how many workers to start"
|Use `os.availableParallelism()`; the documentation warns against `cpus().length` for this purpose.

|"`path.join()` makes a path safe"
|It only normalizes. Untrusted names need a resolve, relative and prefix check, and symbolic links need `realpath()`.

|"`__dirname` does not exist in ESM, so use `path.dirname(new URL(import.meta.url).pathname)`"
|Use `import.meta.dirname` and `import.meta.filename`, or `fileURLToPath(import.meta.url)`. The `.pathname` shortcut breaks on spaces and on Windows.

|"`url.parse()` is the standard way to read a query string"
|It is deprecated; `new URL()` and `URLSearchParams` are the standard replacement.

|"`querystring` is deprecated"
|It is not; it is Stable but non-standard. Prefer `URLSearchParams` for new code.

|"You need a router package to match URL patterns"
|`URLPattern` is built in from Node.js 24 (Experimental); on 22 use a package or your own matcher.

|"`fs.glob` is the only built-in glob"
|`path.matchesGlob()` tests a path against a glob without reading the disk and is stable from v24.8.0 and v22.20.0.
|===
