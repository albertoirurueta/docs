Two facts shape every upgrade plan. First, from Node.js 27 the project moves to one major release per year, every line becomes LTS, and an alpha
channel opens in October for early testing (the announcement is
https://nodejs.org/en/blog/announcements/evolving-the-nodejs-release-schedule[Evolving the Node.js Release Schedule]); the "even numbers are
production" rule ends with Node.js 26. Second, npm 12 exists (npm `latest` was 12.2.0 on 2026-10-03) but no Node.js line bundles it: Node.js 26.10.0
ships npm 11.19.1, so the npm version is an upgrade you control separately, covered in
xref:backend/nodejs/npm-and-package-management.adoc[npm & Package Management].

[#upgrade-process]
== Upgrading across majors

A Node.js major is the only release type that is allowed to break documented behaviour; minor and patch releases of a line keep the stability index
promises (see the stability index in xref:backend/nodejs/globals-and-web-platform-apis.adoc[Globals & Web Platform APIs]). Breaking changes are
announced in three places, and the upgrade workflow below uses all of them.

.The three sources that announce breaking changes
[cols="2,4,3",options="header"]
|===
|Source |What it tells you |How to use it

|Release blog post of the `X.0.0` release
|The notable changes, the deprecations and removals, and every commit labelled `SEMVER-MAJOR`.
|Read it for each major you skip, in order: the posts for 22.0.0 through 26.0.0 are the "per-major highlights" below.

|Migration guides (blog category "migrations")
|A curated list of platform changes (supported platforms, OpenSSL, behaviour changes) plus matching codemods. Guides exist for v20 to v22 and v22 to v24; none existed yet for v24 to v26 on 2026-10-04.
|Use them as the checklist, then fall back to the release posts for the newer lines.

|The deprecations page of the API docs
|Each DEP code with its type, the version where it changed type, and the replacement.
|Search for the code printed in a warning; see the table in this page for the codes that matter most.
|===
Source: https://nodejs.org/en/blog/migrations/v22-to-v24[Node.js v22 to v24, nodejs.org migration guide]

The workflow that keeps surprises small is the same for a service and for a library:

. Move one LTS to the next LTS at a time (22 to 24, then 24 to 26) while the service still has tests, and read the release post of every major in between,
including the odd one that was skipped: Node.js 23 and 25 ended their lives as Current lines, but their `SEMVER-MAJOR` changes are part of the
jump from 22 to 24 and from 24 to 26.
. Declare the supported range in `package.json` `engines` and run the test suite on every line you promise to support, locally with a version manager
and in CI with a matrix; add the next Current line (or, from 27, the alpha channel) as an allowed-to-fail job so a breaking change shows up months
before it reaches LTS.
. Make deprecations visible and fatal in the test run (the next section), upgrade dependencies that print them, and run codemods for the rest.
. Rebuild native add-ons: an add-on compiled against V8 or OpenSSL internals needs a rebuild for each major, while Node-API add-ons keep the same
ABI across majors (see xref:backend/nodejs/native-addons-webassembly-and-ffi.adoc[Native Add-ons, WebAssembly & FFI]).
. Update the base image, the `.nvmrc` or `.node-version` file, and the `engines` field last, once the suite is green, and check the new
line's bundled npm (npm 10.9.9 on 22, 11.19.x on 24 and 26) against the lockfile version your team expects.

The matrix part of that workflow is a plain loop when a version manager is installed. This script runs a project's strict test script on each line
and reports the exit code; the project is a tiny Bookshelf check with one test that calls the legacy `url.parse()`.

.A local line-by-line test matrix with nvm
[source,bash]
----
#!/usr/bin/env bash
source ~/.nvm/nvm.sh
for v in 22 24 26; do
  nvm use "$v" >/dev/null
  npm run --silent test:strict >/dev/null 2>&1
  status=$?
  echo "$(node -v): npm run test:strict exits with $status"
done
----

.package.json of the checked project
[source,json]
----
{
  "name": "upgrade-check",
  "type": "module",
  "engines": { "node": ">=22.12" },
  "scripts": {
    "test": "node --test",
    "test:strict": "node --throw-deprecation --test"
  }
}
----

.Output of the matrix script
[source,text]
----
v22.23.3: npm run test:strict exits with 0
v24.21.0: npm run test:strict exits with 1
v26.10.0: npm run test:strict exits with 1
----
Source: https://nodejs.org/docs/latest/api/cli.html#--throw-deprecation[Node.js CLI: --throw-deprecation]

The same test passes with plain `npm test` on all three lines (observed), and `test:strict` is the only script that fails on 24 and 26. The reason is
in the next section: `url.parse()` is a documentation-only deprecation on 22 and a warning-printing one on 24 and 26.

[#find-deprecations]
== Making Node.js show what will break

Node.js has four kinds of deprecation, and they differ in what you see:

.The four deprecation types
[cols="2,4,3",options="header"]
|===
|Type |Behaviour |How to surface it

|Documentation-only
|Appears only in the API docs and generates nothing at run time.
|Some are marked as supporting `--pending-deprecation`; with that flag (or `NODE_PENDING_DEPRECATION=1`) they emit a warning like a runtime deprecation.

|Application (non-`node_modules` code only)
|A process warning printed once, the first time the API is used from code that is not under `node_modules`.
|With `--pending-deprecation` it also warns for code loaded from `node_modules`.

|Runtime (all code)
|A process warning printed once for any caller, including dependencies.
|`--throw-deprecation` turns it into a thrown error; `--trace-deprecation` adds a stack trace.

|End-of-Life
|The API was removed or now throws; the code needs a replacement before the upgrade.
|Look for `ERR_` codes, `undefined` functions and `ERR_UNKNOWN_BUILTIN_MODULE`.
|===
Source: https://nodejs.org/api/deprecations.html[Node.js API: Deprecated APIs]

The flags that control all of this are Stable command-line options: `--trace-deprecation`, `--throw-deprecation`, `--pending-deprecation` and
`--no-deprecation` (and their `NODE_OPTIONS` forms), and `--disable-warning=code-or-type`, which became Stable in v26.7.0 and v24.20.0 (it was added
in v21.3.0). The script below calls two APIs that are deprecated differently, and prints the stack of each warning with `--trace-deprecation`:

.A script that triggers a runtime and an application deprecation
[source,javascript]
----
import { isArray } from 'node:util';   // DEP0044, runtime since v22.0.0
import { parse } from 'node:url';      // DEP0169, application since v24.0.0

console.log('isArray:', isArray([]));
console.log('host:', parse('https://example.com:8080/a?b=1').host);
----

.Default run on Node.js 22.23.3: only the runtime deprecation warns
[source,text]
----

(node:88840) [DEP0044] DeprecationWarning: The `util.isArray` API is deprecated. Please use `Array.isArray()` instead.
(Use `node --trace-deprecation ...` to show where the warning was created)
----

.Default run on Node.js 24.21.0 and 26.10.0: both warn
[source,text]

With `--throw-deprecation` the first warning is thrown as an exception whose `code` is `DEP0044`, so a CI job fails at the offending line; with
`--disable-warning=DEP0044 --disable-warning=DEP0169` or `--no-deprecation` the run is silent (all four variants were run on 26.10.0). Silencing is a
tool for a dependency you cannot change yet, not a way to finish an upgrade.

Process warnings are also delivered to the `'warning'` event on `process`, which makes a deprecation audit a small script that works even when the output is
silenced (the `--no-warnings` flag below only hides the printing, not the event):

.Collecting deprecation codes with the process warning event
[source,javascript]
----
import { createHash } from 'node:crypto';
import { parse } from 'node:url';

const codes = new Set();
process.on('warning', (warning) => {
  if (warning.name === 'DeprecationWarning') codes.add(warning.code);
});

createHash('shake128').update('bookshelf').digest('hex'); // DEP0198
parse('https://example.com/books?id=1');                  // DEP0169
new Buffer(4);                                            // DEP0005

process.on('exit', () => {
  console.log([...codes].sort().join(' ') || 'no deprecations');
  process.exitCode = codes.size > 0 ? 1 : 0;
});
----

|22.23.3
|`DEP0005`
|`DEP0005 DEP0169 DEP0198`

|24.21.0
|`DEP0005 DEP0169`
|`DEP0005 DEP0169 DEP0198`

|26.10.0
|`DEP0005 DEP0169 DEP0198`

Source: https://nodejs.org/api/deprecations.html#dep0198-creating-shake-128-and-shake-256-digests-without-an-explicit-optionsoutputlength[Node.js API: DEP0198]

Read that table as a forecast: the code that is silent on the line you run today is the code that warns on the next one, so running the suite
with `--pending-deprecation` on Node.js 22 already shows the deprecations that 24 and 26 will print. (`new Buffer()` is an application
deprecation that has been printing for years; the SHAKE example became a runtime deprecation in v25.0.0.)

[#codemods]
== Userland Migrations and codemods

Node.js maintains official codemods for "userland" code, the code outside the `node` executable. They are published under the `@nodejs` scope of the
Codemod registry, are reviewed or written by Node.js members, and cover the end-of-life deprecations and breaking changes that have a mechanical
fix. The Learn page recommends running them on a separate branch, reviewing the diff, running the tests, and formatting or linting afterwards.
Migration guides list per-major codemods; for example, the guides name `@nodejs/import-assertions-to-attributes` for v20 to v22, and
`@nodejs/crypto-rsa-pss-update`, `@nodejs/dirent-path-to-parent-path`, `@nodejs/fs-access-mode-constants`, `@nodejs/fs-truncate-fd-deprecation`,
`@nodejs/http2-priority-signaling`, `@nodejs/process-assert-to-node-assert` and `@nodejs/tls-create-secure-pair-to-tls-socket` for v22 to v24.
The deprecations page also prints the command next to the DEP codes that have one (for example DEP0044 and DEP0030). The Learn section additionally
ships guides that replace third-party packages with built-ins: `chalk`, `kleur` and `ansi-colors` to `util.styleText()`, `axios` to the WHATWG
`fetch`, and `mocha` to the Node.js test runner, plus one that corrects TypeScript import specifiers.

The Bookshelf scratch project had a file that still used the removed import-assertion syntax and one that used `util.isArray()`:

.Before running the codemods
[source,javascript]
----
// old.mjs
import data from './data.json' assert { type: 'json' };
console.log(data.name);

// legacy2.mjs
import { isArray } from 'node:util';

console.log(isArray([1, 2]));
----

.Running two official codemods on a clean git tree (codemod CLI 1.18.3)
[source,bash]
----
npx codemod@latest run @nodejs/import-assertions-to-attributes --no-interactive --disable-analytics
npx codemod@latest run @nodejs/util-is --no-interactive --disable-analytics
----

.After the codemods
[source,javascript]
----
// old.mjs
import data from './data.json' with { type: 'json' };
console.log(data.name);

// legacy2.mjs
console.log(Array.isArray([1, 2]));
----
Source: https://nodejs.org/learn/getting-started/userland-migrations[Node.js Learn: Introduction to Userland Migrations]

Three observations from running them, labelled as observed behaviour of that day's CLI and registry packages and not as a promise. The Learn page
shows `npx codemod <codemod-name>`; the CLI version used here needed the `run` subcommand, and without `--no-interactive` it stopped with "The
input device is not a TTY". It refuses to run on a dirty git tree unless you add `--allow-dirty`, and `--dry-run` reports "Would modify 1 file"
without writing. Finally, when a file had two separate `node:util` import lines (one for `isArray`, one for `_extend`), both the `util-is` and the
`util-extend-to-object-assign` codemods removed both imports and left the other identifier unresolved. That is why the Learn page insists on
reviewing every diff and running the tests after a codemod.

[#deprecations]
== The deprecations that matter

The full list has more than two hundred entries, most of them old end-of-life ones. The table below keeps the codes that an application written for
Node.js 18 to 22 is most likely to meet when moving to 24 and 26, in the state recorded by the 26.x API documentation. "Since" gives the version where
the entry reached its current type; the history column shows the earlier steps.

.Deprecations that changed type between Node.js 22 and 26
[cols="2,3,2,3",options="header"]
|===
|Code |API |Current type and since |Earlier steps and replacement

|DEP0005
|`Buffer()` / `new Buffer()`
|Application, since v10.0.0
|Use `Buffer.alloc()`, `Buffer.allocUnsafe()` or `Buffer.from()`; still prints on every line.

|DEP0030
|`SlowBuffer`
|End-of-Life, v25.0.0
|Runtime in v24.0.0 (prints on 24). Use `Buffer.allocUnsafeSlow()`.

|DEP0040
|`node:punycode`
|Application, v23.7.0 / v22.14.0
|Runtime in v21.0.0, then relaxed to application scope. Use a userland alternative.

|DEP0044
|`util.isArray()`
|Runtime, v22.0.0
|Use `Array.isArray()`. Codemod: `@nodejs/util-is`.

|DEP0045 to DEP0059
|`util.isBoolean()`, `isBuffer()`, `isDate()`, `isError()`, `isFunction()`, `isNull()`, `isNullOrUndefined()`, `isNumber()`, `isObject()`, `isPrimitive()`, `isRegExp()`, `isString()`, `isSymbol()`, `isUndefined()`, `util.log()`
|End-of-Life, v23.0.0
|Runtime on 22.0.0. Replace with `typeof`, `Array.isArray()`, `instanceof` or a logger; `util.isArray()` is the only one that was not removed.

|DEP0060
|`util._extend()`
|Runtime, v22.0.0
|Use `Object.assign()`. Codemod: `@nodejs/util-extend-to-object-assign`.

|DEP0063
|`ServerResponse.prototype.writeHeader()`
|End-of-Life, v26.0.0
|Runtime in v25.0.0. Use `writeHead()`.

|DEP0147
|`fs.rmdir(path, { recursive: true })`
|End-of-Life, v25.0.0
|Use `fs.rm(path, { recursive: true, force: true })`. Codemod: `@nodejs/rmdir`.

|DEP0169
|`url.parse()` (and `url.format(string)`, `url.resolve()`)
|Application, v24.0.0
|Documentation-only since v19.9.0 / v18.17.0, with `--pending-deprecation` support. Use the WHATWG `URL`. Application scope means it warns only in code outside `node_modules`.

|DEP0176
|`fs.F_OK`, `fs.R_OK`, `fs.W_OK`, `fs.X_OK`
|End-of-Life, v25.0.0
|Runtime in v24.0.0. Use `fs.constants.F_OK` and the others. Codemod: `@nodejs/fs-access-mode-constants`.

|DEP0182
|Short GCM authentication tags without an explicit `authTagLength`
|End-of-Life, v26.0.0
|Runtime in v23.0.0. Pass `authTagLength`, and keep the default 16-byte tag.

|DEP0184
|`node:zlib` classes called without `new`
|Runtime, v24.0.0
|Documentation-only in v22.9.0. Use `new`.

|DEP0185
|`node:repl` classes called without `new`
|End-of-Life, v25.0.0
|Runtime in v24.0.0.

|DEP0187
|Invalid argument types to `fs.existsSync()`
|Runtime, v24.0.0
|Documentation-only in v23.4.0 / v22.13.0; it will throw in a future version.

|DEP0190
|An `args` array together with `shell: true` in `execFile()` / `spawn()`
|Runtime, v24.0.0
|Documentation-only in v23.11.0 / v22.15.0. Arguments are only space-joined, so they are not escaped; drop the shell and keep the array.

|DEP0193
|`require('node:_stream_*')`
|End-of-Life, v26.0.0
|Runtime in v24.2.0. Use `node:stream`. (DEP0125 for `_stream_wrap` ended in v26.0.0 too.)

|DEP0195
|`node:http` classes called without `new`
|Documentation-only, v24.2.0 / v22.17.0
|Codemod: `@nodejs/http-classes-with-new`.

|DEP0197
|`util.types.isNativeError()`
|Documentation-only, v24.2.0
|Use `Error.isError()`.

|DEP0198
|SHAKE-128 and SHAKE-256 without `outputLength`
|Runtime, v25.0.0
|Documentation-only with `--pending-deprecation` in v24.4.0 / v22.18.0. Pass `outputLength`.

|DEP0201
|`options.type` in `Duplex.toWeb()`
|Runtime, v26.0.0
|Documentation-only in v25.7.0. Use `readableType`.

|DEP0203 and DEP0204
|Passing a `CryptoKey` to `node:crypto` APIs; `KeyObject.from()` with a non-extractable `CryptoKey`
|Runtime, v26.0.0
|Documentation-only in v25.9.0; both will throw in a future version.

|DEP0205
|`module.register()`
|Runtime, v26.0.0
|Documentation-only in v25.9.0. Use `module.registerHooks()` (Stability 1.2, Release candidate).

|DEP0206
|`hmac.digest()` on an already-finalized `Hmac`
|Documentation-only, v26.2.0
|Today it returns an empty buffer; it will throw in a future version.

|DEP0209
|Using `AbortSignal` to dispose of long-lived resources
|Documentation-only, v26.8.2
|Prefer `using` / `await using`; `AbortSignal` remains the right tool for cancellation and timeouts.
|===
Source: https://nodejs.org/api/deprecations.html[Node.js API: Deprecated APIs]

Two of those entries have a nuance that older summaries get wrong. DEP0169 is an _application_ deprecation, not a runtime one (a blog post for 24.0.0
calls it a runtime deprecation, but the API documentation, which is authoritative, lists the type as application); that is why a dependency in
`node_modules` can call `url.parse()` silently unless `--pending-deprecation` is set. And DEP0190 has been a runtime deprecation since v24.0.0,
which is the first time the warning is visible without a flag. Two entries were revoked and are safe to keep using: DEP0033, `EventEmitter.listenerCount()`
(revoked in v25.4.0), and DEP0163, `channel.subscribe(onMessage)` (revoked in v24.8.0); DEP0116, the legacy URL API as a whole, was revoked earlier
and its remaining parts are covered by DEP0169.

The script that follows checks, on each line, which of the removed members are still there. It was run with `--no-warnings` so that only the table is printed,
which is why Node.js 22 and 24 show them as present although most of them print a warning there.

.Probing removed APIs
[source,javascript]
----
import buffer from 'node:buffer';
import fs from 'node:fs';
import http from 'node:http';
import { mkdtempSync, mkdirSync } from 'node:fs';
import { tmpdir } from 'node:os';
import { join } from 'node:path';

const results = {};
results['buffer.SlowBuffer'] = typeof buffer.SlowBuffer;
results['fs.F_OK'] = typeof fs.F_OK;
results['ServerResponse#writeHeader'] = typeof http.ServerResponse.prototype.writeHeader;
results['fs.constants.F_OK'] = typeof fs.constants.F_OK;

const dir = mkdtempSync(join(tmpdir(), 'rm-'));
mkdirSync(join(dir, 'a', 'b'), { recursive: true });
try {
  fs.rmdirSync(join(dir, 'a'), { recursive: true });
  results['rmdirSync recursive'] = 'removed the tree';
} catch (err) {
  results['rmdirSync recursive'] = err.code;
}
fs.rmSync(dir, { recursive: true, force: true });

for (const name of ['node:_stream_readable', 'node:_stream_wrap']) {
  try { await import(name); results[name] = 'loads'; }
  catch (err) { results[name] = err.code; }
}
console.table(results);
----

[#replacements]
== Worked replacements

Four changes cause most upgrade failures in real projects: customization hooks, import syntax, TypeScript syntax and shell-based child processes.

=== module.register() becomes module.registerHooks()

`module.register()` registered asynchronous hooks that ran in a separate thread; it is Deprecated (Stability 0), became documentation-only deprecated in
v25.9.0 and warns at run time since v26.0.0. `module.registerHooks()` is synchronous, runs in the same thread, works for every module type, and
is Stability 1.2 (Release candidate) since v25.4.0 and v24.13.1; it was added in v23.5.0 and v22.15.0.

.The old and the new registration
[source,javascript]
----
// hooks-old.mjs
import { register } from 'node:module';
register('./loader-hooks.mjs', import.meta.url);
console.log('registered with module.register()');

// hooks-new.mjs
import { registerHooks } from 'node:module';

registerHooks({
  resolve(specifier, context, nextResolve) {
    return nextResolve(specifier, context);
  },
});
console.log('registered with module.registerHooks()');
----

.Result: only Node.js 26.10.0 warns about the old form
[source,text]
----
registered with module.register()
(node:97226) [DEP0205] DeprecationWarning: `module.register()` is deprecated. Use `module.registerHooks()` instead.
registered with module.registerHooks()
----
Source: https://nodejs.org/api/deprecations.html#dep0205-moduleregister[Node.js API: DEP0205]; https://nodejs.org/api/module.html#moduleregisterhooksoptions[Node.js API: module.registerHooks()]

The warning appeared only on 26; both forms ran silently on 24.21.0 and 22.23.3. The details of writing hooks are in
xref:backend/nodejs/esm-cjs-interop.adoc[ESM & CommonJS Interoperability].

=== Import assertions become import attributes

The `assert { type: 'json' }` form was standardised as `with { type: 'json' }`; Node.js dropped support for assertions in 22.0.0 (it had accepted
attributes since v21.0.0, v20.10.0 and v18.20.0). Every line from 22 to 26 reports a `SyntaxError` for the old keyword, and the codemod shown above
does the rewrite.

.The same file with the old and the new keyword
[source,javascript]
----
// assert.mjs: SyntaxError: Unexpected identifier 'assert' on 22, 24 and 26
import data from './data.json' assert { type: 'json' };

// with.mjs: prints "bookshelf" on 22, 24 and 26
import data from './data.json' with { type: 'json' };
console.log(data.name);
----
Source: https://nodejs.org/api/esm.html#import-attributes[Node.js API: Import attributes]

=== Enums and other non-erasable TypeScript syntax

Type stripping runs `.ts` files directly by erasing types; it was added in v22.6.0, is on by default since v23.6.0 and v22.18.0, prints no
experimental warning since v24.3.0 and v22.18.0, and is Stable since v25.2.0 and v24.12.0. The flag that used to transform enums, namespaces and
parameter properties, `--experimental-transform-types`, was removed in v26.0.0. On 26 there is no flag to fall back on, so the code must use
erasable syntax. Run on each line with the default settings, an `enum` file fails with `ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX` ("TypeScript enum is not supported in
strip-only mode"), and with `--experimental-transform-types` it ran on 22.23.3 and 24.21.0 (with an `ExperimentalWarning`) but is "bad option" on 26.10.0.

.An enum and its erasable equivalent
[source,typescript]
----
// ts.ts: fails in strip-only mode on 22, 24 and 26
enum Color { Red, Green }
console.log(Color.Green);

// ts-erasable.ts: prints 1 on 22.23.3, 24.21.0 and 26.10.0
const Color = { Red: 0, Green: 1 } as const;
type Color = (typeof Color)[keyof typeof Color];
const c: Color = Color.Green;
console.log(c);
----
Source: https://nodejs.org/api/typescript.html#type-stripping[Node.js API: Type stripping]

More on what strip-only mode accepts, and the `tsconfig` options that enforce it, is in
xref:backend/nodejs/typescript-in-nodejs.adoc[TypeScript in Node.js].

=== An args array with a shell

Passing an arguments array together with `shell: true` does not escape the arguments; they are only joined with spaces, which is a shell-injection hazard
(DEP0190). It prints a runtime warning from v24.0.0. The safe form is to keep the array and drop the shell.

.The deprecated and the safe call
[source,javascript]
----
import { execFileSync } from 'node:child_process';

// Deprecated since 24.0.0 (DEP0190): an args array together with shell: true
console.log(execFileSync('echo', ['hello', 'world'], { shell: true, encoding: 'utf8' }).trim());

// Replacement: no shell, arguments stay separate array items
console.log(execFileSync('echo', ['hello', 'world'], { encoding: 'utf8' }).trim());
----

Both lines printed `hello world` on all three lines, and `[DEP0190] DeprecationWarning: Passing args to a child process with shell option true can lead to security
vulnerabilities, as the arguments are not escaped, only concatenated.` appeared only on 24.21.0 and 26.10.0.
Source: https://nodejs.org/api/deprecations.html#dep0190-passing-args-to-nodechild_process-execfile--spawn-with-shell-option[Node.js API: DEP0190]

On Windows, `.bat` and `.cmd` files cannot be launched with `execFile()` because they need a terminal; the child-process documentation lists `exec()`,
or spawning `cmd.exe` explicitly, as the ways to run them, and marks `spawn()` with the shell option as not recommended because of DEP0190. See
xref:backend/nodejs/child-processes.adoc[Child Processes] for the argument-array rules.

.Modules, TypeScript and the permission model
[cols="2,3,3",options="header"]
|===
|Area |What the older material assumes |Current approach

|Module detection
|A `"type": "module"` field or `.mjs` extension for every ES module.
|Syntax detection is on by default since v22.7.0 for ambiguous files; `"type"` remains the explicit, recommended setting.

|`require(esm)`
|ES modules cannot be loaded from CommonJS.
|`require()` loads a synchronous ES module graph without a flag on every supported line (v22.12.0+); it throws `ERR_REQUIRE_ASYNC_MODULE` for top-level await.

|Import assertions
|`assert { type: 'json' }`.
|`with { type: 'json' }`; assertions were dropped in 22.0.0.

|Customization hooks
|`module.register()`.
|`module.registerHooks()`; `register()` warns since v26.0.0 (DEP0205).

|`import.meta`
|`__dirname` and `__filename` workarounds.
|`import.meta.dirname` and `import.meta.filename` are stable; `import.meta.main` exists since v24.2.0 and v22.18.0.

|TypeScript
|A compile step with `tsc` before running; the idea that `tsc` refuses to emit on type errors.
|Node runs erasable-syntax `.ts` files directly (Stable since v24.12.0 and v25.2.0); `--experimental-transform-types` was removed in v26.0.0; use `tsc --noEmit` for checking. `tsc` emits despite type errors unless `noEmitOnError` is set.

|Permission model
|Mentioned only as an upcoming feature.
|Stable for filesystem, child-process and worker scopes (`--permission`, `--allow-fs-read`, `--allow-fs-write`, `--allow-child-process`, `--allow-worker`); `--allow-net` is Active development.

|===
|Area |What the older material assumes |Current approach

|Production installs
|`--production`, or a `prune` followed by `install` before tests.
|`npm ci` and `--omit=dev`; `--production` is deprecated.

|Publishing credentials
|Classic npm tokens.
|Classic tokens were revoked on 2025-12-09; use granular tokens or trusted publishing with provenance (https://docs.npmjs.com/trusted-publishers/[trusted publishers]).

|Install scripts always run.
|npm 12.0.0 blocks dependency scripts unless allowed with `allowScripts`, and removes `npm shrinkwrap` and `npm adduser`; `min-release-age` (added in npm 11.10.0) adds a dependency cooldown.

|Even-numbered lines are the production lines.

=== Insecure practices that the projects should not copy

Some sample projects in _Node.js Projects_ (Jonathan Wexler) are teaching code, not production code, and a reader who copies them inherits their
weaknesses. The safe form for each:

.Insecure practices and the safe form
[cols="2,3,4",options="header"]
|===
|Area |Weakness in the sample projects |Safe form

|Stored secrets
|A password manager that keeps the managed passwords readable.
|Derive a key with scrypt or Argon2id and encrypt each secret with AES-256-GCM, storing the IV and auth tag with the ciphertext (see xref:backend/nodejs/crypto-passwords-and-secrets.adoc[Crypto, Passwords & Secrets]).

|Password hashing
|A low-iteration, synchronous PBKDF2 whose hashes are compared with `===`.
|Use at least 210,000 iterations for PBKDF2-HMAC-SHA512 (OWASP), or better Argon2id or scrypt, the asynchronous API and `crypto.timingSafeEqual()`.

|Configuration
|Hard-coded secrets and JWT secrets that fall back to a fixed string.
|Fail fast at start-up when a secret is missing, and read it from `process.env` through `--env-file`.

|Tokens
|JWTs issued without an expiry and verified without pinned algorithms; session cookies without `secure`, `httpOnly` and `sameSite`.
|Set `expiresIn`, pass `algorithms` when verifying, and set all three cookie attributes (see xref:backend/nodejs/authentication-and-sessions.adoc[Authentication & Sessions]).

|Request protection
|No CSRF protection, no rate limiting, and an email address placed in a verification URL.
|Add CSRF defences and rate limits, and verify email with a random single-use token.

|Scraping and templates
|A scraper that spoofs its user agent and ignores robots.txt; a vulnerable version of the `ejs` template engine (CVE-2022-29078).
|Respect robots.txt and site terms, identify your client, and keep template engines up to date (see xref:backend/nodejs/email-feeds-and-web-scraping.adoc[Email, Feeds & Web Scraping]).

|Cloud database access
|A MongoDB Atlas network access list open to every address.
|Restrict access to the addresses that need it, and use credentials from the environment.
|===
Source: https://nodejs.org/learn/getting-started/security-best-practices[Node.js Learn: Security Best Practices]; https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html[OWASP: Password Storage Cheat Sheet]

=== Errors in the books worth knowing

Typos and slips are normal in technical books, and the page that covers each concept already shows the right form; the ones below are collected so
that a reader following either book can check them in one place. The correct form is given, not the passage.

.Corrections for _Efficient Node.js_ (Samer Buna)
[cols="2,4",options="header"]
|===
|Topic |Correct form

|Promise helper module
|The module is `node:stream/promises` (singular `stream`).

|Awaiting several promises
|`await [p1, p2]` does not wait for both; use `Promise.all()`, `Promise.allSettled()` or another combinator.

|Per-request child processes
|A child forked per request must exit, or each request leaks a process; a request or response object cannot be sent to a worker (it is not serialisable).

|Client IP hashing
|An address-hashing sketch for sticky balancing must handle IPv6 as well as IPv4.

|ES modules
|Use `export` and `export default` in ES modules; `exports` and `module.exports` are CommonJS.

|`NODE_PATH`
|The separator is `:` on Unix and `;` on Windows, not a comma, and the variable applies to CommonJS only.

|`assert.doesNotMatch()`
|It passes when the string does not match the pattern and throws when it does.

|`ENOTFOUND`
|A DNS lookup failure, not "entity not found".

|Pausing a stream
|Removing `'data'` listeners does not pause a stream; call `pause()` or use `pipeline()`.

|Backpressure
|Large generators must respect backpressure by honouring the result of `write()` and waiting for `'drain'`.

|Encryption
|`aes-256-ctr` has no integrity protection; use `aes-256-gcm` and check the authentication tag.
|===
Source: https://nodejs.org/learn/modules/backpressuring-in-streams[Node.js Learn: Backpressuring in Streams]; https://nodejs.org/docs/latest/api/stream.html[Node.js API: Stream]; https://nodejs.org/docs/latest/api/assert.html[Node.js API: Assert]; https://nodejs.org/docs/latest/api/errors.html[Node.js API: Errors]; https://nodejs.org/docs/latest/api/cli.html[Node.js API: Command-line API (NODE_PATH)]

.Corrections for _Node.js Projects_ (Jonathan Wexler)
[cols="2,4",options="header"]
|===
|Topic |Correct form

|`promisify` example
|The readline interface used in the example must be created before it is used.

|`npm start`
|It needs a `start` script in `package.json`; without one `npm start` runs `node server.js` only if that file exists.

|Not-found handlers
|A Fastify `setNotFoundHandler` should reply with 404, not 500, and `reply.send()` must be called once.

|Sequelize `sync()`
|`sync({ force: true })` drops and recreates tables; it is not change detection (use migrations).

|Schedulers and queues
|Use the documented `node-schedule` rule keys, declare every queue you use, and treat Redis Pub/Sub as at-most-once messaging, not a durable queue; acknowledge a RabbitMQ message only after the work is done.

|Blockchain project
|A transaction needs its own class, and a proof-of-work nonce must be bound to the block it signs.

|LLM errors
|An error object returned by the API is not an answer; check the status and the error field first.

|MongoDB connection strings
|`mongodb://localhost` can fail where `localhost` resolves to IPv6 first; use `127.0.0.1` or `[::1]` explicitly.
|===
Source: https://fastify.dev/docs/latest/Reference/Server/[Fastify: Server]; https://redis.io/docs/latest/develop/pubsub/[Redis: Pub/Sub]; https://sequelize.org/docs/v6/core-concepts/model-basics/[Sequelize: Model basics]; https://nodejs.org/docs/latest/api/dns.html[Node.js API: DNS]
