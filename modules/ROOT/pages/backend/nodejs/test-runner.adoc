[#model]
== How `node --test` works

Running `node --test` does not simply load your files. The process you start is the _runner_: it finds the test files, decides which of them this process should run, starts each file in
its own child Node.js process (the default, called process isolation), listens to what the children report, and feeds one stream of events to the reporters. A file does not have to use
`node:test` at all; the runner treats it as a script and counts exit code 0 as a pass. Inside a file that does use `node:test`, every test runs on the same single application thread,
whatever the `concurrency` option says, because concurrency there means interleaving asynchronous work on the event loop, not parallel threads (see
xref:backend/nodejs/event-loop.adoc[Event Loop] for why).

.From `node --test` to the exit code
[mermaid]
----
flowchart TD
    cli["node --test with flags and optional glob arguments"] --> find["find test files: default patterns or the globs you passed"]
    find --> shard{"--test-shard set?"}
    shard -- "yes" --> slice["keep only this shard's files"]
    shard -- "no" --> mode{"isolation mode"}
    slice --> mode
    mode -- "process (default)" --> children["one child process per file, at most --test-concurrency at a time"]
    mode -- "none" --> inproc["import every file into the runner process, one at a time"]
    children --> events["test events from every file"]
    inproc --> events
    events --> stream["TestsStream: the single ordered event stream"]
    stream --> reporters["reporters: spec, dot, tap, junit, lcov or your own"]
    reporters --> dest["stdout, stderr or a file"]
    stream --> code["exit code: 1 if a test failed, 0 otherwise"]
----

Because every file is a separate process by default, a crash, a global variable, or an open handle in one file cannot affect another, and the files can run in parallel on several cores. The cost is
the start-up time of one Node.js process per file. The Node.js 26 documentation also says that child processes inherit Node.js options from the parent, including options from environment
variables such as `NODE_OPTIONS` and from configuration files, except for the options the runner manages itself (`--test`, the coverage and reporter flags, `--watch`, the randomization flags
and the tag filter). That is how a `--import` setup file reaches every test file.

Source: https://nodejs.org/docs/latest/api/test.html#test-runner-execution-model[Node.js API: Test runner execution model]; https://nodejs.org/docs/latest/api/test.html#child-process-option-inheritance[Node.js API: Child process option inheritance]

[#discovery]
== Finding the test files

With no arguments, `node --test` searches the current directory tree (skipping `node_modules`) and runs every file whose path matches one of these patterns.

.Default test file patterns on Node.js 26
[cols="3,3,4"]
|===
|Pattern |Matches |Does not match

|`+**/*.test.{cjs,mjs,js}+`
|`src/isbn.test.js`
|`src/isbn.spec.js`

|`+**/*-test.{cjs,mjs,js}+`
|`src/isbn-test.js`
|`src/isbn-tests.js`

|`+**/*_test.{cjs,mjs,js}+`
|`src/isbn_test.js`
|`src/helper.js`

|`+**/test-*.{cjs,mjs,js}+`
|`src/test-isbn.js`
|`src/mytest-isbn.js`

|`+**/test.{cjs,mjs,js}+`
|`src/test.js`
|`src/tests.js`

|`+**/test/**/*.{cjs,mjs,js}+`
|`test/a.js`, `test/nested/b.mjs`, `test/c.cjs`
|`tests/a.js` (the directory must be named `test`)
|===

Unless you pass `--no-strip-types`, the same six patterns are also matched for `cts`, `mts` and `ts`, so a `*.test.ts` file runs directly through Node.js type stripping (see
xref:backend/nodejs/typescript-in-nodejs.adoc[TypeScript in Node.js]). A file that merely matches a pattern is executed even if it never imports `node:test`; that is why a helper placed
under a `test/` directory is run as a test file too. Put shared helpers outside `test/` or give them a name that no pattern matches.

To pick files yourself, pass one or more glob patterns as the final arguments, in double quotes so that the shell does not expand them (the quotes also keep the command portable). In
the following scratch project, which holds one file per pattern plus decoys, the commands show the difference.

.Default discovery versus explicit globs
[source,bash]
----
node --test                                      # the default patterns
node --test "src/**/*.spec.js" "lib/*.js"        # only what the globs select
node --test "test/**/*.{js,mjs,cjs}"             # a directory is not walked: use a glob
----

.Files executed by the plain `node --test` run (output sorted)
[source,text]
----
src/math-test.js    src/math.test.js    src/math_test.js    src/test-math.js    src/test.js
src/z.test.ts       test/a.js           test/c.cjs          test/nested/b.mjs   test/types.ts
(not run: src/helper.js, src/math.spec.js, lib/utils.js, node_modules/pkg/index.test.js)
----

Source: https://nodejs.org/docs/latest/api/test.html#running-tests-from-the-command-line[Node.js API: Running tests from the command line]

Passing a directory name is a common mistake. In my runs (observed, not documented), `node --test test` ran zero tests and printed a summary of zero on Node.js 26, while on Node.js 24 and 22 the name was
treated as a file to execute and failed with `MODULE_NOT_FOUND`. Use a glob such as `"test/**/*.js"` instead. A related trap: `node --test "test/**"` also matches the directories themselves, which
then fail. The command normally goes in `package.json`, where `npm test` runs it and any extra arguments go after `--`.

.Wiring the runner into npm scripts
[source,json]
----
{
  "type": "module",
  "scripts": {
    "test": "node --test",
    "test:watch": "node --test --watch",
    "test:ci": "node --test --test-reporter=spec --test-reporter=junit --test-reporter-destination=stdout --test-reporter-destination=junit.xml"
  }
}
----

Source: https://nodejs.org/learn/test-runner/using-test-runner[Node.js Learn: Using Node.js's test runner]

A failing test sets the process exit code to 1, so any CI system can tell success from failure without parsing output. Setup that every test file needs (registering a loader, adding a global polyfill) goes into a
module that you preload for the children with `node --import ./test/setup.mjs --test`, a pattern the Learn guide recommends keeping in small, purpose-specific setup files so that cheap unit tests do not pay for
expensive environment mocks.

[#first-test]
== Your first tests: `test`, `describe` and `it`

A test is one function. It passes when it returns normally (or its returned promise fulfills) and fails when it throws (or the promise rejects). A third style gives the function a callback as the
second argument: calling it with a truthy first argument fails the test, and a test that takes a callback and also returns a promise fails. `describe()` groups tests into a suite and `it()` is
the test function with the name you would expect there; `describe` is an alias of `suite` and `it` is an alias of `test`. The three styles are equivalent, so choose by taste and stay consistent in a codebase.
The first example tests the ISBN check that the _Bookshelf_ uses to reject malformed books.

.The function under test: an ISBN-13 validator
[source,javascript]
----
// Validates an ISBN-13: 13 digits (hyphens/spaces allowed) whose weighted sum is divisible by 10.
export function isValidIsbn13(input) {
  if (typeof input !== 'string') throw new TypeError('ISBN must be a string');
  const digits = input.replace(/[-\s]/g, '');
  if (!/^\d{13}$/.test(digits)) return false;
  const sum = [...digits].reduce((acc, d, i) => acc + Number(d) * (i % 2 === 0 ? 1 : 3), 0);
  return sum % 10 === 0;
}
----

.test/isbn.test.js: a suite with three tests
[source,javascript]
----
import { describe, it } from 'node:test';
import assert from 'node:assert/strict';
import { isValidIsbn13 } from '../src/isbn.js';

describe('isValidIsbn13', () => {
  it('accepts a valid ISBN with hyphens', () => {
    assert.equal(isValidIsbn13('978-0-306-40615-7'), true);
  });

  it('rejects a wrong check digit', () => {
    assert.equal(isValidIsbn13('978-0-306-40615-8'), false);
  });

  it('throws a TypeError for non-strings', () => {
    assert.throws(() => isValidIsbn13(42), { name: 'TypeError', message: 'ISBN must be a string' });
  });
});
----

The tests inside one `describe()` run one after another in the order they were declared, unless you ask for concurrency. The suite function itself should declare tests and hooks synchronously; the runner awaits the
tests created inside a suite for you.

[#hooks]
== Hooks: `before`, `after`, `beforeEach` and `afterEach`

Hooks are functions the runner calls around your tests. `before()` runs once before the first test of its suite and `after()` runs once after the last one; the Node.js documentation guarantees that `after()` runs
even when tests in the suite fail, which makes it the right place to close servers and delete temporary files. `beforeEach()` and `afterEach()` run around every test of the suite, including the tests of nested suites.
Hooks take the same options as tests (`timeout`, `signal`) and may be written with a callback. Declared at the top level of a file, outside any `describe()`, they apply to every test in that file.

.test/hooks.test.js: the order in which hooks and tests run
[source,javascript]
----
import { describe, it, before, after, beforeEach, afterEach } from 'node:test';
import assert from 'node:assert/strict';

describe('hook order', () => {
  const log = [];

  before(() => log.push('before'));
  after(() => {
    log.push('after');
    assert.deepStrictEqual(log, [
      'before',
      'beforeEach', 'test A', 'afterEach',
      'beforeEach', 'test B', 'afterEach',
      'after',
    ]);
  });
  beforeEach(() => log.push('beforeEach'));
  afterEach(() => log.push('afterEach'));

  it('A', () => log.push('test A'));
  it('B', () => log.push('test B'));
});
----

Source: https://nodejs.org/docs/latest/api/test.html#beforefn-options[Node.js API: before(), after(), beforeEach() and afterEach()]

The next file, also run on all three lines, pins down how hooks nest: suite hooks run once and outermost first, and the each-test hooks of every enclosing scope run before a test, outermost first.

.test/hooks-scope.test.js: hooks at the file level and in nested suites
[source,javascript]
----
import { describe, it, before, beforeEach, after, test } from 'node:test';
import assert from 'node:assert/strict';

const log = [];
beforeEach(() => log.push('root beforeEach'));   // file level: applies to every test in the file
after(() => assert.deepStrictEqual(log, [
  'root beforeEach', 'top-level test',
  'outer before', 'inner before',                 // suite hooks run once, outermost first
  'root beforeEach', 'outer beforeEach',          // each-test hooks run outermost first
  'inner test',
]));

test('top-level test', () => log.push('top-level test'));

describe('outer', () => {
  before(() => log.push('outer before'));
  beforeEach(() => log.push('outer beforeEach'));

  describe('inner', () => {
    before(() => log.push('inner before'));
    it('inner test', () => log.push('inner test'));
  });
});
----

Source: https://nodejs.org/docs/latest/api/test.html#beforefn-options[Node.js API: Hooks]

A hook that throws fails the tests it guards: in an experiment where a `beforeEach()` threw, the test it guarded was reported as failed and never ran. Keep hooks small and deterministic, and keep their work proportional to what every
test needs; an expensive `beforeEach()` multiplies by the number of tests.

[#subtests]
== Subtests

The context object `t` that the runner passes to every test function has a `t.test()` method that creates a subtest. This builds hierarchies inside a test, shares setup between the subtests (the parent's code runs once), and
lets you generate cases in a loop. The context also has its own hooks, `t.before()`, `t.beforeEach()`, `t.after()` and `t.afterEach()`, which apply to the subtests of that one test.

.test/nesting.test.js: a parent test, its hooks and two subtests
[source,javascript]
----
import { test } from 'node:test';
import assert from 'node:assert/strict';

test('parent', async (t) => {
  const seen = [];
  t.before(() => seen.push('parent before'));
  t.beforeEach((sub) => seen.push(`beforeEach for ${sub.name}`));
  t.after(() => assert.deepStrictEqual(seen, [
    'parent before',
    'beforeEach for first',
    'beforeEach for second',
  ]));

  await t.test('first', () => {});
  await t.test('second', () => {});
});
----

Source: https://nodejs.org/docs/latest/api/test.html#subtests[Node.js API: Subtests]

The documentation says to `await` every subtest, because a parent does not wait for its subtests (unlike tests declared inside a suite) and cancels the ones still pending when it finishes; a failing subtest also fails its parent.
That is what happens on Node.js 22: in my run of a test that called `t.test()` without `await`, Node.js 22.23.3 reported the subtest as cancelled with the message `test did not finish before its parent and was cancelled`.
On Node.js 24.21 and 26.10 the same file passed, because newer lines wait for outstanding subtests (the Learn guide dates this change to v23.8.0). Do not depend on that: write `await t.test(...)` and the code works on every line.

.test/table.test.js: one subtest per data row
[source,javascript]
----
import test from 'node:test';
import assert from 'node:assert/strict';
import { isValidIsbn13 } from '../src/isbn.js';

const cases = [
  ['978-0-306-40615-7', true],
  ['978 0 306 40615 7', true],
  ['9780306406158', false],
  ['not an isbn', false],
];

test('isValidIsbn13 table', async (t) => {
  for (const [input, expected] of cases) {
    // t.test, not test: the subtest belongs to this parent
    await t.test(`isValidIsbn13(${JSON.stringify(input)})`, () => {
      assert.equal(isValidIsbn13(input), expected);
    });
  }
});
----

Source: https://nodejs.org/learn/test-runner/using-test-runner[Node.js Learn: Using Node.js's test runner (dynamically generating test cases)]

[#plan]
== Counting assertions: `t.plan()` and `t.assert`

`t.plan(count)` declares how many assertions and subtests the test must run; the test fails if the number differs. It exists for code where an assertion sits in a callback or event handler that might never fire, which would
otherwise leave the test green. Plans count only assertions made through `t.assert`, the object that exposes the functions of `node:assert` bound to the current test; the plain imported `assert` is invisible to the plan. The
`wait` option controls whether the check happens at once (the default, `false`), waits as long as needed (`true`), or waits up to a number of milliseconds.

.A plan that counts `t.assert` calls
[source,javascript]
----
import test from 'node:test';
import { Readable } from 'node:stream';

test('every chunk is checked', (t, done) => {
  const chunks = ['a', 'b', 'c'];
  const expected = [...chunks];
  t.plan(chunks.length); // the test fails unless exactly three t.assert calls happen

  Readable.from(chunks)
    .on('data', (chunk) => t.assert.strictEqual(chunk, expected.shift()))
    .on('end', done);
});

test('a plan can wait for late assertions', (t) => {
  t.plan(1, { wait: 1_000 }); // wait up to one second for the assertion
  setTimeout(() => t.assert.ok(true), 50);
});
----

.Mixing the imported `assert` into a plan does not count (files named `*.demo.js` match no default pattern, so they run only when you name them)
[source,javascript]
----
import test from 'node:test';
import assert from 'node:assert/strict';

test('plan ignores the imported assert', (t) => {
  t.plan(1);
  assert.ok(true); // not tracked: only t.assert.* counts
});
----

.Result on Node.js 26
[source,text]
----
✖ plan ignores the imported assert (0.30ms)

----

[#async-tests]
== Asynchronous tests, timeouts and polling

An `async` function, a function that returns a promise, and a function that takes a callback are all valid. Each test can also be bounded: the `timeout` option fails the test after a number of milliseconds (the default is
`Infinity`), `--test-timeout` sets a default for all tests, and `t.signal` is an `AbortSignal` that aborts when the test is cancelled or times out, so pass it to anything cancellable. The documentation is explicit that a timeout is not a
reliable cancellation mechanism: a test that blocks the thread in a synchronous loop prevents the scheduled cancellation from running. For eventual conditions, `t.waitFor()` polls an assertion function until it stops
throwing (default `interval` 50 ms, default `timeout` 1000 ms) and returns its value; prefer it to a hand-written `sleep()` followed by an assertion.

.test timeouts, `t.signal` and `t.waitFor()` (demo/timeouts.demo.js)
[source,javascript]
----
import { test } from 'node:test';
import assert from 'node:assert/strict';
import { setTimeout as sleep } from 'node:timers/promises';

test('hangs past its timeout', { timeout: 100 }, async (t) => {
  // t.signal aborts when the test times out, so the timer is cancelled too
  await sleep(5_000, undefined, { signal: t.signal });
});

test('polls until an eventual condition holds', async (t) => {
  let ready = false;
  setTimeout(() => { ready = true; }, 120);
  await t.waitFor(() => assert.equal(ready, true), { interval: 20, timeout: 1_000 });
});
----

Source: https://nodejs.org/docs/latest/api/test.html#testname-options-fn[Node.js API: test() options]; https://nodejs.org/docs/latest/api/test.html#contextwaitforcondition-options[Node.js API: context.waitFor()]

A timed-out test is counted as _cancelled_, not _failed_, in the summary, yet the run still ends with exit code 1. Work that outlives its test is another source of confusion: once a test function returns, the result is reported
at once, a subtest created afterwards fails, and an `uncaughtException` from a finished test is attributed to it and reported as a diagnostic. The documentation calls this _extraneous asynchronous activity_; the cure is to await
everything a test starts, and to close what it opens in `t.after()`.

Source: https://nodejs.org/docs/latest/api/test.html#extraneous-asynchronous-activity[Node.js API: Extraneous asynchronous activity]

[#assert]
== Assertions with `node:assert/strict`

The test runner has no `expect()`. Assertions come from `node:assert`, and the module should be imported in its strict form, `node:assert/strict`: in strict assertion mode the loosely named methods behave like their
strict counterparts (`assert.equal()` is `assert.strictEqual()`, `assert.deepEqual()` is `assert.deepStrictEqual()`), failure messages for objects include a colored diff, and the coercion surprises of legacy mode disappear. The legacy mode (`import assert from 'node:assert'`)
compares with `==` in `equal()`, `deepEqual()`, `notEqual()` and `notDeepEqual()`, and the Node.js documentation marks those four Stability 3 (Legacy) and points to the strict names.

.The assertions you will use every day
[cols="3,5"]
|===
|Assertion |What it checks

|`assert.strictEqual(actual, expected)`
|Primitives or identity, compared with `Object.is()`.

|`assert.deepStrictEqual(actual, expected)`
|Recursive equality of enumerable own properties, including the prototypes' identity, `Map` and `Set` contents, `Error` names, messages and causes. Property order does not matter; array order does.

|`assert.partialDeepStrictEqual(actual, expected)`
|Only the properties present in `expected` are compared (a superset of `deepStrictEqual`'s rules). Handy for API responses with generated ids and timestamps.

|`assert.ok(value)`, `assert.match(string, regexp)`, `assert.doesNotMatch(string, regexp)`
|Truthiness; a regular expression must match; a regular expression must not match.

|`assert.throws(fn, expected)`, `assert.doesNotThrow(fn)`
|`expected` may be an error class, a `RegExp`, an object of properties to compare, or a validation function.

|`assert.rejects(promiseOrFn, expected)`, `assert.doesNotReject(promiseOrFn)`
|The asynchronous twins: always `await` them, otherwise a failure becomes an unhandled rejection after the test is over.
|===

.test/assertions.test.js (Node.js 26: the function message in the last test needs v26.0.0)
[source,javascript]
----
import { test } from 'node:test';
import assert from 'node:assert/strict'; // strict mode: equal() means strictEqual(), deepEqual() means deepStrictEqual()
import { Shelf } from '../src/shelf.js';

test('assertion tour', async () => {
  assert.strictEqual(1 + 1, 2);                          // Object.is() comparison
  assert.deepStrictEqual({ a: [1, { b: 2 }] }, { a: [1, { b: 2 }] });
  assert.notDeepStrictEqual([1, 2], [2, 1]);             // order matters in arrays
  assert.partialDeepStrictEqual({ id: 7, title: 'Dune', tags: ['sf', 'classic'] }, { title: 'Dune', tags: ['sf'] });
  assert.ok('non-empty strings are truthy');
  assert.match('978-0-306-40615-7', /^\d{3}(-\d+){4}$/);
  assert.doesNotMatch('Dune', /\d/);                     // passes when the string does NOT match
  assert.throws(() => new Shelf().add(null), TypeError); // class, regexp, object or validation function
  await assert.rejects(Promise.reject(new RangeError('page out of range')), { name: 'RangeError' });
  await assert.doesNotReject(Promise.resolve('fine'));
});

test('strict mode rejects coercion that legacy mode accepts', async () => {
  const legacy = await import('node:assert'); // the legacy-mode default export
  legacy.default.equal(1, '1');                          // passes: 1 == '1'
  assert.throws(() => assert.equal(1, '1'), { code: 'ERR_ASSERTION' });
  legacy.default.deepEqual({ n: 1 }, { n: '1' });        // passes: deepEqual() compares leaves with ==
  assert.throws(() => assert.deepEqual({ n: 1 }, { n: '1' }), { code: 'ERR_ASSERTION' });
});

test('a custom message can be a function evaluated only on failure', () => {
  assert.throws(
    () => assert.strictEqual(1, 2, (actual, expected) => `wanted ${expected}, got ${actual}`),
    { message: /^wanted 2, got 1/ },  // the generated diff is appended after your text
  );
});
----

Source: https://nodejs.org/docs/latest/api/assert.html#strict-assertion-mode[Node.js API: Strict assertion mode]; https://nodejs.org/docs/latest/api/assert.html#assertpartialdeepstrictequalactual-expected-message[Node.js API: assert.partialDeepStrictEqual()]; https://nodejs.org/docs/latest/api/assert.html#assertrejectsasyncfn-error-message[Node.js API: assert.rejects()]

Two version notes from running that file. First, the first two tests passed on Node.js 26, 24 and 22. Second, the last test passed only on Node.js 26: on 24.21 and 22.23 `assert.strictEqual()` did not accept a function as its message
(the documentation lists the printf-style and function forms as added to `deepStrictEqual()` in v25.1.0 and to `equal()` in v26.0.0), so I treat that form as Node.js 26 only. Also notice that a custom message does not replace the generated diff: in my
run the text was followed by the usual `1 !== 2` comparison, so match the start of the message rather than the whole string. The Node.js 26 documentation warns, in its legacy-mode section, that `assert.deepEqual(/a/gi, new Date())` does not throw; in my runs on

[#selecting]
== Skipping, todo, only, expected failures and name patterns

While a feature is unfinished, or a test is known to be broken, you need to keep the suite green without deleting the test. The runner has four markers, all available as options on `test()` and `describe()` and as shorthand methods (`it.skip()`, `it.todo()`, `it.only()`, `it.expectFailure()`), and as methods on the context (`t.skip()`, `t.todo()`).

.The markers and what each one does to the run
[cols="2,5,3"]
|===
|Marker |Behaviour |Effect on the exit code

|`skip` (option, `it.skip()`, `t.skip()`)
|The test is not run. A string is shown as the reason. `t.skip()` does not stop the function, so `return` after calling it.
|None.

|`todo` (option, `it.todo()`, `t.todo()`)
|The test runs, but a failure is not counted as a failure. If a test is both TODO and skipped, the TODO is ignored.
|None: a failing TODO test leaves the exit code at 0, though its error text is still printed.

|`expectFailure` (option, `it.expectFailure()`)
|The test must throw to pass and fails if it does not. A `RegExp`, function, object or error restricts which failure is accepted, and `{ label, match }` supplies both a reason and a matcher. Added in v25.5.0 and v24.14.0.
|A test that unexpectedly succeeds fails the run. `skip` beats it, and `todo` beats it too.

|`only` (option, `it.only()`, `describe.only()`)
|With `--test-only` (or with isolation off), only tests marked `only` run. Everything below a marked suite runs unless a descendant is marked too.
|Unselected tests are omitted from the output.
|===

.test/markers.test.js: skip, todo, expectFailure and a todo test without a body
[source,javascript]
----
import { describe, it, test } from 'node:test';
import assert from 'node:assert/strict';

test('runs normally', () => {});

test('skipped by option', { skip: 'no network in CI' }, () => {
  throw new Error('never executed');
});

test('skipped at runtime', (t) => {
  t.skip('feature flag is off');
  // skip() does not stop the function; return yourself
});

test('todo still executes but cannot fail the run', { todo: 'ISBN-10 support' }, () => {
  assert.equal(1 + 1, 3);
});

it.expectFailure('known bug: trims too much', () => {
  assert.equal(' a '.trim().length, 2);
});

describe('search', () => {
  it('finds by title', () => {});
  it('finds by author', () => {});
  it.todo('finds by ISBN');
});
----

=== Name patterns

`--test-name-pattern` runs only tests whose name matches a JavaScript regular expression, and `--test-skip-pattern` skips matching tests. Both can be repeated, `"/.../flags"` syntax gives you flags such as `i`, and when both are given a test has to
satisfy both. A pattern is tested against the test's own name; to select one test among several with the same name, prefix it with its ancestors' names, separated by spaces. The hooks of the selected tests still run, tests that are filtered out
are omitted from the output, and the set of files that the runner executes does not change: the filter applies after the files are loaded, so a pattern does not make a run cheaper to start.

.test/names.test.js
[source,javascript]
----
import { describe, it } from 'node:test';

describe('isbn', () => {
  it('accepts hyphens', () => {});
  it('rejects letters', () => {});
});
describe('shelf', () => {
  it('accepts duplicates?', () => {});
  it('rejects duplicates', () => {});
});
----

.Selecting by name (Node.js 26; only the matching lines are shown)
[source,bash]
----
node --test --test-name-pattern="^isbn" test/names.test.js
# runs the whole isbn suite: accepts hyphens, rejects letters

node --test --test-name-pattern="/REJECTS/i" test/names.test.js
# case-insensitive: isbn "rejects letters" and shelf "rejects duplicates"

node --test --test-name-pattern="shelf rejects duplicates" test/names.test.js
# ancestor names make the match unique: one test

node --test --test-skip-pattern="rejects" test/names.test.js
# everything except the two "rejects ..." tests

node --test --test-name-pattern="shelf" --test-skip-pattern="accepts" test/names.test.js
# both must hold: only shelf "rejects duplicates"
----

Source: https://nodejs.org/docs/latest/api/test.html#filtering-tests-by-name[Node.js API: Filtering tests by name]

=== Tags (Early development)

Names encode metadata badly, so Node.js 26.2.0 (and 24.19.0) added _tags_: an array of labels on a test or suite, inherited by union from enclosing suites, and a filter flag that selects tests with a boolean expression using `and`/`&&`, `or`/`||`, `not`/`!`, parentheses and `*` wildcards.
Tags are lowercase, may not contain whitespace or the operator characters, and untagged tests behave as if they had an empty tag set, so `not flaky` selects them. The Node.js 26 flag is `--experimental-test-tag-filter='<expression>'`, and the feature is Stability 1.0 (Early development), which printed an `ExperimentalWarning` in my run. The Node.js 24
documentation describes a simpler form of the flag that takes one tag, so do not copy expression syntax into a project that runs on 24.

.test/tags.test.js
[source,javascript]
----
import { describe, it } from 'node:test';

describe('database', { tags: ['db'] }, () => {
  it('reads a row');
  it('writes a row', { tags: ['integration'] });
  it('reconnects after disconnect', { tags: ['flaky'] });
});
it('pure function', { tags: ['unit'] }, () => {});
it('untagged', () => {});
----

.Filtering by tag (Node.js 26)
[source,bash]
----
node --test --experimental-test-tag-filter='db and not flaky' test/tags.test.js
# runs: reads a row, writes a row        (2 tests)

node --test --experimental-test-tag-filter='not flaky' test/tags.test.js
# runs the two db tests, "pure function" and "untagged"   (4 tests)
----

Most behaviour of a run is set with command-line flags, which are mirrored as options of the `run()` function (see below). The list below groups the flags you will use; every flag is Stable unless the table says otherwise.

=== Concurrency and isolation

The cost of process isolation is start-up time; the benefit is that files run in parallel. In the scratch experiment each of six files sleeps 300 ms. The numbers show that `--test-concurrency` bounds file-level parallelism, and that
turning isolation off made the run slower (all six files ran in the same process, one worker, one after another).

.Six files that each take 300 ms, on a machine with `availableParallelism()` of 10 (Node.js 26)
[cols="3,2"]
|===
|Command |Run time (the `duration_ms` line)

|`node --test --test-concurrency=1`
|about 2.1 s

|`node --test --test-concurrency=2`
|about 1.1 s

|`node --test --test-concurrency=6`
|about 0.35 s

|`node --test --test-isolation=none`
|about 1.8 s
|===

Isolation `none` also lets tests influence each other. The following pair of files shows it: one writes a global, the other expects a clean global scope.

.iso/a-writes.test.js and iso/b-reads.test.js
[source,javascript]
----
import { test } from 'node:test';

test('writes a global', () => {
  globalThis.currentUser = 'alice';
});

import { test } from 'node:test';
import assert from 'node:assert/strict';

test('expects a clean global scope', () => {
  assert.equal(globalThis.currentUser, undefined);
});
----

.Same files, two modes (Node.js 26, 24 and 22 behaved the same)
[source,text]
----

✔ writes a global
✔ expects a clean global scope

$ node --test --test-isolation=none        (--experimental-test-isolation=none on Node.js 22)
✔ writes a global
✖ expects a clean global scope

=== Sharding across CI machines

`--test-shard=1/3` divides the matching files into three parts and runs the first; the same command on three CI jobs with `2/3` and `3/3` runs everything exactly once. Sharding divides _files_, not tests, so a suite with one giant file does not benefit.

.Six files, three shards (Node.js 26)
[source,text]
----
$ node --test --test-shard=1/3      runs: file a, file d
$ node --test --test-shard=2/3      runs: file b, file e
$ node --test --test-shard=3/3      runs: file c, file f
----

.A GitHub Actions matrix that runs one shard per job
[source,yaml]
----
jobs:
  test:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        shard: [1, 2, 3]
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-node@v7
        with:
          node-version: 26
      - run: npm ci
      - run: node --test --test-shard=${{ matrix.shard }}/3

=== Rerunning only what failed

With `--test-rerun-failures=state.json`, the runner writes a JSON file listing the tests that passed on each attempt and, on the next run, executes only the tests that have not yet passed. Inside a test, `t.attempt` is the zero-based attempt number. The documentation warns
that keys are the file path with the line and column of the definition, so changing the order of tests or moving them between runs makes the runner believe tests passed that did not: use it with tests that run in a deterministic order. In my runs `t.attempt` was also
available on 24.21 and 22.23 although the 26 documentation dates it to v25.0.0; the flag itself is v24.7.0 and later and is not recognised on 22.

.rerun/flaky.test.js
[source,javascript]
----
import { test } from 'node:test';
import assert from 'node:assert/strict';
import { existsSync, writeFileSync } from 'node:fs';

test('always passes', () => {});

test('fails on the first attempt only', (t) => {
  // t.attempt is zero-based and counts runs recorded in the state file
  t.diagnostic(`attempt ${t.attempt}`);
  assert.ok(t.attempt > 0, 'transient failure');
});
----

.Two runs against the same state file (Node.js 26)
[source,text]
----
$ node --test --test-rerun-failures=state.json
✔ always passes (0.23ms)
✖ fails on the first attempt only (0.26ms)
ℹ attempt 0
ℹ pass 1
ℹ fail 1

$ node --test --test-rerun-failures=state.json
✔ always passes (0.23ms) (passed on attempt 0)
✔ fails on the first attempt only (0.09ms)
ℹ attempt 1
ℹ pass 2
ℹ fail 0
----

That is a tool for working through a failing suite on a developer machine or for a CI "re-run failed tests" button; do not use it to hide flaky tests, and note that it does not retry inside one run. Mocha-style `retries` have no equivalent in `node:test`.

=== Randomized order and global setup

Order-dependent tests are found by shuffling. `--test-randomize` (Early development, v26.1.0 and v24.16.0) randomizes both the order of files and of queued tests inside a file, and prints the seed so a failure can be replayed with `--test-random-seed=n`. Subtests that are awaited one after another keep their declaration order, because each starts only after the previous one finished; suites created with `describe()` stay eligible.

.Randomization and replay (Node.js 26; the first seed is random)
[source,text]
----

$ node --test --test-random-seed=12345 test/order.test.js

----

`--test-global-setup` (Early development, v24.0.0) names a module whose exported `globalSetup()` runs once before all tests and `globalTeardown()` once after them; if setup throws, no test runs and teardown is not called. In my run, an environment variable set inside `globalSetup()` was visible in the test file, which is enough to hand every file a shared temporary directory; the documentation only promises that setup runs once before all tests, so treat anything beyond that as observed behaviour.

.global-setup.js and a test that uses it
[source,javascript]
----
import { mkdtemp, rm } from 'node:fs/promises';
import { tmpdir } from 'node:os';
import { join } from 'node:path';

let dir;

export async function globalSetup() {
  dir = await mkdtemp(join(tmpdir(), 'bookshelf-'));
  process.env.BOOKSHELF_DATA_DIR = dir; // inherited by the per-file child processes
}

export async function globalTeardown() {
  await rm(dir, { recursive: true, force: true });
}

import test from 'node:test';
import assert from 'node:assert/strict';

test('sees the directory created by global setup', () => {
  assert.match(process.env.BOOKSHELF_DATA_DIR ?? '', /bookshelf-/);
});
----

=== Watch mode

`node --test --watch` runs the tests, then waits for changes to the test files and to the modules they import, and reruns the affected tests; it runs until you terminate it. The `--test --watch` combination is Stability 1 (Experimental), while plain `node --watch` for scripts is Stable (see
xref:backend/nodejs/running-scripts-cli-and-repl.adoc[Running Scripts, the CLI & the REPL] and xref:backend/nodejs/directories-glob-and-watch.adoc[Directories, glob & watch]). The recorded session below changed the code under test twice: the first change broke it, the second repaired it. `--test-shard`, `--test-randomize` and `--test-random-seed` are not supported in watch mode.
`--watch-path` cannot be combined with `--test`, so there is no way to narrow the watched paths through that flag.

== Reporters, `run()` and the event stream

The reporter turns the stream of test events into text. You choose one with `--test-reporter`, and the output goes to stdout unless you give `--test-reporter-destination`. The exact output of the built-in reporters is not an API: the documentation says it may change between versions and tells you to consume the events if you need to process results programmatically.

[cols="1,4,3"]

|Reporter |Output |Typical use

|`tap`
|The Test Anything Protocol. The default for non-TTY output before v23.0.0, so on Node.js 22.23.3 the output of `node --test \| cat` is TAP, which I observed.

=== A custom reporter

A custom reporter is a module whose default export is something `stream.compose()` accepts: a `Transform` in object mode or, simplest, an async generator function that receives the event stream and yields text. Pass its path to `--test-reporter`, the way you would pass a specifier to `import()` (a relative path needs `./`).

.reporters/one-line.js
[source,javascript]
----
// A custom reporter: an async generator that turns TestsStream events into lines.
export default async function* oneLine(source) {
  for await (const event of source) {
    const { type, data } = event;
    if (type === 'test:pass' && data.details.type !== 'suite') {
      yield `${data.skip === undefined ? 'PASS' : 'SKIP'} ${data.name}\n`;
    } else if (type === 'test:fail') {
      const error = data.details.error.cause ?? data.details.error;
      yield `FAIL ${data.name}: ${error.message.split('\n')[0]}\n`;
    } else if (type === 'test:summary' && data.file === undefined) {
      const { passed, failed, skipped } = data.counts;
      yield `${passed} passed, ${failed} failed, ${skipped} skipped\n`;
    }
  }
}
----

.demo/mixed.demo.js
[source,javascript]
----
import { test } from 'node:test';
import assert from 'node:assert/strict';

test('adds up', () => assert.equal(1 + 1, 2));
test('breaks', () => assert.equal(1 + 1, 3));
test('is skipped', { skip: true }, () => {});
----

=== Running tests from code with `run()`

`run(options)` from `node:test` starts a run programmatically and returns the `TestsStream`. It takes the same ideas as the flags: `files` or `globPatterns`, `concurrency`, `isolation`, `timeout`, `only`, `testNamePatterns` and `testSkipPatterns`, `shard`, `watch`, `rerunFailuresFilePath`, coverage options and thresholds, `execArgv`, `argv`, `env` (v25.6.0 and v24.14.0), `cwd`, `forceExit`, `signal` to abort, and a `setup` function that receives the stream before any test runs. Use it to build custom test scripts, to run tests from a tool, or to attach your own listeners.

.scripts/run-tests.js: a runner script with a summary and an exit code (identical on Node.js 26, 24 and 22)
[source,javascript]
----
import { run } from 'node:test';
import { spec } from 'node:test/reporters';
import { fileURLToPath } from 'node:url';

const files = [
  fileURLToPath(new URL('../test/isbn.test.js', import.meta.url)),
  fileURLToPath(new URL('../test/shelf.test.js', import.meta.url)),
];

const stream = run({ files, concurrency: true, timeout: 10_000 });

let failed = 0;
stream.on('test:fail', () => { failed++; });
stream.on('test:summary', ({ counts, file }) => {
  if (file === undefined) console.error(`summary: ${counts.passed} passed, ${counts.failed} failed`);
});

stream.compose(spec).pipe(process.stdout);
await new Promise((resolve) => stream.on('end', resolve));
process.exitCode = failed > 0 ? 1 : 0;
----

[source,text]

  ✔ starts empty (0.31ms)
  ...
summary: 14 passed, 0 failed
----

[cols="2,5"]
|===
|Event |When it is emitted

|`'test:enqueue'`, `'test:dequeue'`

|`'test:start'`, `'test:pass'`, `'test:fail'`

[#test-types]
== Kinds of tests, test doubles and TDD

`node:test` does not care what kind of test you write; the kind decides what you set up and how fast it is. A good split puts each assertion at the lowest layer that can make it.

.Kinds of tests and how they look with the Node.js runner
[cols="2,4,4"]
|===
|Kind |What it exercises |In _Bookshelf_

|Unit
|One function or class, with its collaborators replaced by test doubles. Milliseconds, no I/O.
|`isValidIsbn13()`, `Shelf`, the notifier with a fake mailer.

|Integration
|Several real parts together: code and a real database, a router and its handlers.
|The API with an in-memory `node:sqlite` database (see xref:backend/nodejs/sqlite-builtin.adoc[SQLite from Node.js]).

|Functional
|One feature end to end through its public interface, usually without the network.
|"Adding a book makes it appear in the list", through the HTTP handler.

|End-to-end
|The deployed shape: a real server process, real HTTP, real dependencies.
|The server listening on a port, driven with `fetch()`; later, the same tests against a container (see xref:backend/nodejs/production-deployment.adoc[Production Deployment]).
|===

=== Test doubles

A _test double_ replaces a collaborator so the unit under test can be exercised in isolation. The vocabulary is older than any framework; this is how it maps onto `node:test`.

.Test doubles and the Node.js tools that build them
[cols="1,4,4"]
|===
|Double |Purpose |With `node:test`

|Dummy
|Fills a parameter that is never used.
|A plain `{}` or `null`.

|Stub
|Returns canned answers (or errors) to drive the code down a path.
|`mock.fn(impl)` or `mockImplementationOnce()` on the mock's `mock` property.

|Spy
|Records how it was called while the real behaviour stays.
|`mock.fn()` and `mock.method(object, 'name')`; inspect `.mock.calls` and `.mock.callCount()`.

|Fake
|A small working substitute (an in-memory store, a recording mailer).
|Ordinary objects you write.

|Mock
|A double with built-in expectations about calls.
|Spy plus assertions on `.mock.calls`; there is no expectation DSL.
|===

The `mock` object that comes from `node:test` and its twin `t.mock` do the heavy lifting. Prefer `t.mock`: it is the same API, but the runner restores everything when the test ends, so a failed assertion cannot leave a replaced method behind for the next test. Replacing methods, getters and properties, mock timers, module mocks and snapshots are covered on
xref:backend/nodejs/mocking-snapshots-and-coverage.adoc[Mocking, Snapshots & Coverage]; here is what a unit test needs. The code under test receives its mailer as a parameter (dependency injection by function argument), which is what makes it testable without any module mocking.

.src/notifier.js
[source,javascript]
----
// Sends a reminder for every overdue loan; the mailer is injected, so tests can replace it.
export async function remindOverdue(loans, mailer, now = new Date()) {
  const overdue = loans.filter((loan) => loan.dueDate < now);
  for (const loan of overdue) {
    await mailer.send(loan.member, `"${loan.title}" is overdue`);
  }
  return overdue.length;
}
----

.test/doubles.test.js: a spy, a stub, a fake and an auto-restored method spy
[source,javascript]
----
import { test } from 'node:test';
import assert from 'node:assert/strict';
import { remindOverdue } from '../src/notifier.js';
import { Shelf } from '../src/shelf.js';

const loans = [
  { member: 'ana', title: 'Dune', dueDate: new Date('2026-01-10') },
  { member: 'bo', title: 'Emma', dueDate: new Date('2026-03-01') },
];

test('spy: records calls without changing behaviour', async (t) => {
  const send = t.mock.fn(async () => {});          // a fake function that also records calls
  const count = await remindOverdue(loans, { send }, new Date('2026-02-01'));

  assert.equal(count, 1);
  assert.equal(send.mock.callCount(), 1);
  assert.deepStrictEqual(send.mock.calls[0].arguments, ['ana', '"Dune" is overdue']);
});

test('stub: canned answers, including failures', async (t) => {
  const send = t.mock.fn(async () => {});
  send.mock.mockImplementationOnce(async () => { throw new Error('smtp down'); });

  await assert.rejects(remindOverdue(loans, { send }, new Date('2026-12-31')), /smtp down/);
  assert.equal(send.mock.callCount(), 1); // the loop stopped at the first failure
});

test('fake: a small working replacement', async () => {
  const outbox = [];
  const fakeMailer = { send: async (to, text) => { outbox.push({ to, text }); } };

  await remindOverdue(loans, fakeMailer, new Date('2026-12-31'));
  assert.deepStrictEqual(outbox.map((m) => m.to), ['ana', 'bo']);
});

test('t.mock.method is restored automatically', async (t) => {
  const shelf = new Shelf();
  t.mock.method(shelf, 'add');                      // wraps the real method and records calls
  await shelf.loadFrom({ fetchAll: async () => [{ isbn: '1', title: 'A' }] });
  assert.equal(shelf.add.mock.callCount(), 1);
});
----

Source: https://nodejs.org/docs/latest/api/test.html#mocking[Node.js API: Mocking]; https://nodejs.org/learn/test-runner/mocking[Node.js Learn: Mocking in tests]

All four tests passed on Node.js 26, 24 and 22. In the second one, `mockImplementationOnce()` changes only the first call; the assertion that `callCount()` is 1 documents that the loop aborts at the first failed send, which may or may not be what you want, and the test is the place where that decision becomes explicit.

=== Test-driven development

TDD is a discipline of tiny cycles: write one failing test (red), write the least code that passes (green), then clean up with the tests as a safety net (refactor). The test runner suits it because a run costs tens of milliseconds, and `node --test --watch` reruns the affected tests on every save. The example drives a `slugify()` function used to build URLs from titles: the test file comes first.

.slug.test.js, written before the code
[source,javascript]
----
import { describe, it } from 'node:test';
import assert from 'node:assert/strict';
import { slugify } from './slug.js';

describe('slugify', () => {
  it('lowercases and joins words with hyphens', () => {
    assert.equal(slugify('Efficient Node'), 'efficient-node');
  });
  it('drops punctuation', () => {
    assert.equal(slugify('Dune: Messiah!'), 'dune-messiah');
  });
});
----

.Red: a first implementation that only lowercases (Node.js 26)
[source,text]
----
✖ lowercases and joins words with hyphens (0.53ms)
  + 'efficient node'
  - 'efficient-node'
✖ drops punctuation (0.43ms)
ℹ pass 0
ℹ fail 2
----

.Green: the least code that satisfies both tests
[source,javascript]
----

  return title.toLowerCase().replace(/[^a-z0-9]+/g, '-').replace(/^-|-$/g, '');
}
----

.Green (Node.js 26)
[source,text]
----
✔ lowercases and joins words with hyphens (0.29ms)
✔ drops punctuation (0.05ms)
ℹ pass 2
ℹ fail 0

[#http-testing]
== Testing an HTTP server

An HTTP service is tested by starting the real server on a random port, calling it with the global `fetch()`, and shutting it down. The pieces: listen on port 0 so the operating system picks a free port (no clash between the test files that run in parallel, and no dependency on port 3000 being free), read the actual port from `server.address()`, create and close the server in `before()` and `after()`, and do not leave keep-alive sockets behind, or the process will not exit.
The _Bookshelf_ server is the one used elsewhere in this section; `createApp()` returns a `node:http` server and an in-memory SQLite database, so each test file has its own clean data.

.test/server.test.js
[source,javascript]
----
import { describe, it, before, after } from 'node:test';
import assert from 'node:assert/strict';
import { once } from 'node:events';
import { createApp } from '../src/server.js';

describe('books API', () => {
  let server;
  let base;

  before(async () => {
    ({ server } = createApp()); // in-memory SQLite database
    server.listen(0, '127.0.0.1'); // port 0: the OS picks a free port
    await once(server, 'listening');
    base = `http://127.0.0.1:${server.address().port}`;
  });

  after(async () => {
    server.close();
    server.closeAllConnections(); // do not wait for keep-alive sockets
    await once(server, 'close');
  });

  it('starts with an empty list', async () => {
    const res = await fetch(`${base}/books`);
    assert.equal(res.status, 200);
    assert.match(res.headers.get('content-type'), /^application\/json/);
    assert.deepStrictEqual(await res.json(), []);
  });

  it('creates a book and lists it', async () => {
    const created = await fetch(`${base}/books`, {
      method: 'POST',
      headers: { 'content-type': 'application/json' },
      body: JSON.stringify({ title: 'Dune', author: 'Herbert' }),
    });
    assert.equal(created.status, 201);
    assert.partialDeepStrictEqual(await created.json(), { title: 'Dune', author: 'Herbert' });

    const list = await (await fetch(`${base}/books`)).json();
    assert.equal(list.length, 1);
  });

  it('answers 400 to a malformed body', async () => {
    const res = await fetch(`${base}/books`, { method: 'POST', body: '{not json' });
    assert.equal(res.status, 400);
    assert.ok((await res.json()).error);
  });

  it('answers 404 to an unknown path', async () => {
    const res = await fetch(`${base}/nope`);
    assert.equal(res.status, 404);
    await res.body?.cancel();
  });
});
----

.Result (identical on Node.js 26, 24 and 22)
[source,text]
----
  ✔ starts with an empty list (8.15ms)
  ✔ creates a book and lists it (2.65ms)
  ✔ answers 400 to a malformed body (0.81ms)
  ✔ answers 404 to an unknown path (0.66ms)
✔ books API (16.57ms)
ℹ pass 4
ℹ fail 0
----

Four details in that file matter. `partialDeepStrictEqual` ignores the generated `id`, so the test does not depend on database order. The 404 test cancels the unread response body (`res.body?.cancel()`), because an unread body keeps the connection busy. `server.closeAllConnections()` closes idle keep-alive connections that `fetch()` leaves open, which otherwise makes `close()` wait. And binding to `127.0.0.1` explicitly avoids the IPv4 versus IPv6 resolution mismatch that a `localhost` base URL can produce on machines where the name resolves to `::1` first.
A test that needs a database, a queue or another service is an integration test and should say so in its name and its folder; the sibling pages on databases and queues show how to start those dependencies in containers. Frameworks bring their own shortcuts (Fastify's `inject()` injects a request without opening a socket, described on
xref:backend/nodejs/web-frameworks-express-and-fastify.adoc[Web Frameworks: Express & Fastify]), and the NestJS and Next.js sections have their own testing pages, which use Jest or Vitest (see
xref:backend/nestjs/testing.adoc[Testing in NestJS] and xref:web/nextjs/testing.adoc[Testing in Next.js]). The same test shape applies to a server you build in
xref:backend/nodejs/building-a-rest-api.adoc[Building a REST API] and to the lower-level API of xref:backend/nodejs/http-server-fundamentals.adoc[HTTP Server Fundamentals].

Source: https://nodejs.org/docs/latest/api/test.html#testname-options-fn[Node.js API: test()]; https://nodejs.org/docs/latest/api/assert.html#assertpartialdeepstrictequalactual-expected-message[Node.js API: assert.partialDeepStrictEqual()]

[#comparison]
== `node:test` versus Jest, Vitest and Mocha

Pick the built-in runner for a new Node.js library or service whose tests are plain JavaScript or erasable TypeScript; Vitest for a project that already builds with Vite or tests UI components; Jest where you already have a large Jest suite (including React Native) and the migration is not worth the churn. The Jest runner, matchers and mocking are described in
xref:programming-languages/javascript/tooling-jest.adoc[Unit Testing with Jest], and are not repeated here.

=== Migrating from Mocha

Mocha and `node:test` have almost the same `describe`/`it`/hook shape, so migration is mostly mechanical. The Node.js project publishes a codemod, `@nodejs/mocha-to-node-test-runner`, that targets Mocha 8.x suites and `node:test` on Node.js 22 and 24. It adds the `node:test` imports for the globals a file uses, turns `done` callbacks into the `(t, done)` signature, rewrites `this.skip()` to `t.skip()` and `this.timeout(n)` to a `{ timeout: n }` option, keeps your function style, supports both CommonJS and ESM files, and removes `mocha` and `@types/mocha` from `package.json`. Its documented limitation is that `node:test` has no equivalent of Mocha's `retry` option.

.Running the codemod
[source,bash]
----
npx codemod @nodejs/mocha-to-node-test-runner
----

I tried that command in the scratch project. It downloaded the codemod and then asked for interactive permission for file-system and child-process access, and it exited because the shell had no TTY, so it did not modify anything. I did not work around that prompt; the "after" listing below was written by hand to follow the documented rules, and then run on Node.js 26, 24 and 22 (all three tests passed, and the third was skipped when `CI` was set).

.A Mocha test before migration
[source,javascript]
----
import assert from 'node:assert/strict';
import { Shelf } from '../src/shelf.js';

describe('Shelf', function () {
  this.timeout(500);
  let shelf;

  beforeEach(function () {
    shelf = new Shelf();
  });

  it('adds a book', function () {
    shelf.add({ isbn: '1', title: 'A' });
    assert.equal(shelf.size, 1);
  });

  it('loads asynchronously (done style)', function (done) {
    shelf.loadFrom({ fetchAll: async () => [{ isbn: '2', title: 'B' }] }).then((n) => {
      assert.equal(n, 1);
      done();
    }, done);
  });

  it('skips on CI', function () {
    if (process.env.CI) this.skip();
  });
});
----

.The same test after applying the documented transformations
[source,javascript]
----
import assert from 'node:assert/strict';
import { describe, it, beforeEach } from 'node:test';
import { Shelf } from '../src/shelf.js';

describe('Shelf', { timeout: 500 }, function () {
  let shelf;

  beforeEach(function () {
    shelf = new Shelf();
  });

  it('adds a book', function () {
    shelf.add({ isbn: '1', title: 'A' });
    assert.equal(shelf.size, 1);
  });

  it('loads asynchronously (done style)', function (t, done) {
    shelf.loadFrom({ fetchAll: async () => [{ isbn: '2', title: 'B' }] }).then((n) => {
      assert.equal(n, 1);
      done();
    }, done);
  });

  it('skips on CI', function (t) {
    if (process.env.CI) t.skip();
  });
});
----

Beyond what the codemod does, a migration checklist covers the rest of the Mocha ecosystem: a Chai or `should.js` assertion is rewritten with `node:assert/strict`; Sinon spies and stubs become `mock.fn()` and `mock.method()`; `.mocharc` options become command-line flags or an npm script (`--grep` is `--test-name-pattern`, `--reporter` is `--test-reporter`, `--exit` roughly corresponds to `--test-force-exit`, `--require` is `--import`, `--watch` is `--watch`); and a `done`-style test that also returns a promise has to pick one, because `node:test` fails a test that does both.

Source: https://nodejs.org/learn/userland-migrations/mocha-to-node-test-runner[Node.js Learn: Mocha to Node.js Test Runner]

[#books]
== Where the books are outdated

Testing is one of the clearest places where print falls behind, because the runner went from experimental to stable in v20.0.0 and has gained features in nearly every release since. Samer Buna's _Efficient Node.js_ (O'Reilly, 2025) has a chapter on testing Node that does cover `node:test` and `node:assert`, test doubles, TDD, `--watch` and coverage gates, and a later chapter that surveys Mocha, Chai and Jest as the tools of the trade. What it cannot cover are the later additions: `partialDeepStrictEqual()` as a stable assertion, awaited-by-default subtests, `t.waitFor()`, `expectFailure`, tags, randomized order and replayable seeds, `--test-rerun-failures`, JUnit and custom reporters as first-class output, the `Experimental`-to-`Stable` changes for snapshots and `t.plan()`, and the removal of `assert.CallTracker` in Node.js 25. Where a flag or option differs from this page, trust this page and the Node.js documentation. Jonathan Wexler's _Node.js Projects_ (O'Reilly, 2025) is organised around applications rather than around testing; its appendix on tools reaches for `nodemon` to restart a server, which `node --watch` (Stable since v22.0.0) now does, and `node --test --watch` does for tests. If you follow either book, use `node:assert/strict` rather than the legacy `assert`, import `describe`, `it` and the hooks explicitly (the runner has no globals), and prefer `t.mock` over `mock` so that doubles restore themselves.

A last reading note on one assertion helper, because it is easy to invert in your head: `assert.doesNotMatch(string, regexp)` passes when the string does _not_ match the pattern (it is the negation of `assert.match()`), as the run of `test/assertions.test.js` above confirms.

Source: https://www.oreilly.com/library/view/efficient-node-js/9781098145187[O'Reilly: Efficient Node.js, Samer Buna]; https://www.oreilly.com/library/view/node-js-projects/9781098173135/[O'Reilly: Node.js Projects, Jonathan Wexler]

[#pitfalls]
== Pitfalls

.Common mistakes with the Node.js test runner
[cols="3,5"]
|===
|Mistake |Fix

|Forgetting `await` on `t.test()`
|Await every subtest; Node.js 22 cancels the ones still running when the parent finishes.

|Using the imported `assert` with `t.plan()`
|Use `t.assert.*`; the plan counts only assertions made through the context.

|Importing `node:assert` instead of `node:assert/strict`
|Legacy `equal()` and `deepEqual()` coerce with `==`; use the strict import.

|Passing a directory to `node --test`
|Pass a glob (`"test/**/*.js"`) or rely on the default patterns; a directory name ran zero tests on Node.js 26 and failed on 24 and 22.

|Putting helpers in `test/`
|Every file under `test/` is run as a test; keep helpers elsewhere or name them so no pattern matches.

|Committing `.only`
|Run with `--test-only` locally and let CI run without it, so a stray `only` fails loudly instead of silently narrowing the run.

|Expecting `todo` to fail the build
|A failing TODO test never changes the exit code; use `expectFailure` (Node.js 24.14 or later) to make a known failure self-checking.

|A hard-coded port in server tests
|Listen on port 0 and read `server.address().port`.

|Not closing servers and handles
|Close in `after()` or `t.after()`; `--test-force-exit` hides the leak rather than fixing it.

|Tests that share state under `--test-isolation=none`
|Keep the default process isolation unless you have measured a start-up problem.

|Using `retries` as a flakiness cure
|`node:test` has none; fix the race, or use `--test-rerun-failures` knowingly.

|A test that cannot fail
|Make sure the assertion would fail if the code were wrong: write the failing test first (TDD) and watch it fail for the reason you expect.

|Relying on the exact text of a reporter
|The output of built-in reporters is not stable; consume events through `run()` or a custom reporter.

|Treating Early development features as stable
|Tags, global setup, randomization and module mocks may change in minor releases; pin your Node.js version and re-test when upgrading.
|===
