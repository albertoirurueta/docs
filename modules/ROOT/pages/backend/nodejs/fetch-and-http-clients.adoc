[#test-server]
== The test server used by the examples

To keep every example runnable offline, they call a tiny Bookshelf API started on port 0 (the operating system picks a free port). It exposes a
JSON list, a POST endpoint, a 404, a slow endpoint, a flaky endpoint that fails twice with `503` and `Retry-After: 1` and then succeeds, an NDJSON
stream, an echo of the request content type and size, a redirect and a short unit of "work". The files in this page share one directory, with
`"type": "module"` in `package.json`.

.server.js: the Bookshelf API used by the examples
[source,javascript]
----
import { createServer } from 'node:http';
import { once } from 'node:events';

// A tiny Bookshelf API used by the client examples. Port 0 = the OS picks a free port.
export async function startServer() {
  let flaky = 0;
  const server = createServer(async (req, res) => {
    const url = new URL(req.url, 'http://localhost');
    if (url.pathname === '/books' && req.method === 'GET') {
      res.setHeader('content-type', 'application/json');
      res.end(JSON.stringify([{ id: 1, title: 'Dune' }, { id: 2, title: 'Emma' }]));
    } else if (url.pathname === '/books' && req.method === 'POST') {
      let body = '';
      for await (const chunk of req) body += chunk;
      res.writeHead(201, { 'content-type': 'application/json' });
      res.end(JSON.stringify({ id: 3, ...JSON.parse(body) }));
    } else if (url.pathname === '/missing') {
      res.writeHead(404, { 'content-type': 'application/json' });
      res.end(JSON.stringify({ error: 'not found' }));
    } else if (url.pathname === '/slow') {
      setTimeout(() => res.end('finally'), 2000).unref();
    } else if (url.pathname === '/flaky') {
      // Fails twice with 503 + Retry-After, then succeeds.
      if (flaky++ < 2) {
        res.writeHead(503, { 'retry-after': '1' });
        res.end('try later');
      } else {
        res.end('ok after ' + flaky + ' attempts');
      }
    } else if (url.pathname === '/lines') {
      res.setHeader('content-type', 'application/x-ndjson');
      for (let i = 1; i <= 5; i++) res.write(JSON.stringify({ n: i }) + '\n');
      res.end();
    } else if (url.pathname === '/old') {
      res.writeHead(301, { location: '/books' }).end();
    } else if (url.pathname === '/echo') {
      let length = 0;
      for await (const chunk of req) length += chunk.length;
      res.setHeader('content-type', 'application/json');
      res.end(JSON.stringify({ type: req.headers['content-type']?.split(';')[0], length }));
    } else if (url.pathname === '/work') {
      await new Promise((r) => setTimeout(r, 50));
      res.end('done');
    } else {
      res.writeHead(404).end();
    }
  });
  server.listen(0, '127.0.0.1');
  await once(server, 'listening');
  return { base: `http://127.0.0.1:${server.address().port}`, server, close: () => server.close() };
}
----

Source: https://nodejs.org/docs/latest/api/http.html#httpcreateserveroptions-requestlistener[Node.js API: http.createServer()]

[#fetch-basics]
== Global fetch: requests, JSON and errors

`fetch(input, init)` returns a promise for a `Response` as soon as the status line and headers have arrived; the body is still on its way.
`input` is a string, a `URL` or a `Request`. `init` carries `method`, `headers`, `body`, `signal`, `redirect` and a few more. The response gives you
`status`, `ok` (true for 200 to 299), `headers`, `url`, `redirected` and body readers: `json()`, `text()`, `arrayBuffer()`, `blob()`
and the raw `body`, a web `ReadableStream`. Two behaviours surprise people coming from other clients, and both are in the next listing: a
`404` or `500` is a _successful_ fetch (you must check `res.ok` yourself), and a network failure rejects with a bare `TypeError: fetch failed`
whose real reason is on `err.cause`.

.Basic GET, JSON POST, the HTTP error trap and a network error
[source,javascript]
----
import { createServer } from 'node:http';
import { once } from 'node:events';
import { startServer } from './server.js';

const { base, close } = await startServer();

const res = await fetch(`${base}/books`);
if (!res.ok) throw new Error(`HTTP ${res.status}`);          // fetch does NOT reject on 4xx/5xx
console.log(res.status, res.headers.get('content-type'), await res.json());

const created = await fetch(`${base}/books`, {
  method: 'POST',
  headers: { 'content-type': 'application/json' },
  body: JSON.stringify({ title: 'Ulysses' }),
});
console.log(created.status, await created.json());

const missing = await fetch(`${base}/missing`);
console.log('a 404 is a normal response:', missing.status, missing.ok, await missing.json());

// A network failure rejects with TypeError; the real reason is in err.cause
const probe = createServer().listen(0, '127.0.0.1');          // find a free port, then free it again
await once(probe, 'listening');
const { port } = probe.address();
probe.close();
await once(probe, 'close');
try {
  await fetch(`http://127.0.0.1:${port}/`);
} catch (err) {
  console.log(err.name, '-', err.message, '| cause:', err.cause.code);
}
try { await fetch('/books'); } catch (err) { console.log(err.name, '-', err.message, '|', err.cause.code); }

console.log('bundled undici', process.versions.undici, 'on Node.js', process.version);
close();
----

Source: https://nodejs.org/learn/getting-started/fetch[Node.js Learn: Fetching data with Node.js], https://nodejs.org/docs/latest/api/globals.html#fetch[Node.js API: fetch]

Unlike a browser, Node.js has no page origin, so a relative URL such as `/books` is an error, and `fetch` has no `baseURL` option: build absolute URLs with
`new URL(path, base)` (the migration section wraps this in a small client).

.What fetch does and does not reject on
[cols="3,3"]
|===
|Situation |Result

|The server answers `404`, `429`, `500` or any other status
|The promise _resolves_. Check `res.ok` or `res.status`; read the body for the server's message.

|DNS failure, refused connection, TLS error, reset socket
|Rejects with `TypeError: fetch failed`; `err.cause` carries the Node.js error (`ECONNREFUSED`, `ENOTFOUND`, `UNABLE_TO_VERIFY_LEAF_SIGNATURE`).

|A relative URL, or a blocked "bad port" such as 1
|Rejects with `TypeError` before any network traffic (observed: `Failed to parse URL from /books`, `bad port`).

|The `AbortSignal` fires
|Rejects with the signal's `reason`: `TimeoutError` for `AbortSignal.timeout()`, `AbortError` for `controller.abort()` with no reason.

|`res.json()` on a body that is not JSON
|Rejects with `SyntaxError`; check the `content-type` first when the server may return HTML error pages.
|===

[#bodies]
== Request bodies, Response helpers and redirects

`fetch` accepts several body types and sets the `content-type` header for the ones that carry their own type: a `URLSearchParams` becomes
`application/x-www-form-urlencoded`, a `FormData` becomes `multipart/form-data` with a generated boundary, a string becomes
`text/plain;charset=UTF-8`, and a `Blob` uses its own type. For JSON you serialise yourself and set the header, as in the previous listing.
A body is single-use: reading it twice rejects with `TypeError: Body is unusable`, so `clone()` the response first when you need two readers.
By default redirects are followed (`redirect: 'follow'`); `'manual'` hands you the 3xx response and `'error'` rejects.

.URLSearchParams, FormData, Blob, clone() and redirect modes
[source,javascript]
----
import { startServer } from './server.js';

const { base, close } = await startServer();

// URLSearchParams -> application/x-www-form-urlencoded, set automatically
const form = await fetch(`${base}/echo`, { method: 'POST', body: new URLSearchParams({ q: 'dune', page: '1' }) });
console.log(await form.json());

// FormData with a Blob -> multipart/form-data with a generated boundary
const data = new FormData();
data.set('title', 'Dune');
data.set('cover', new Blob(['fake image bytes'], { type: 'image/png' }), 'cover.png');
console.log(await (await fetch(`${base}/echo`, { method: 'POST', body: data })).json());

// A string body is sent as text/plain;charset=UTF-8
console.log(await (await fetch(`${base}/echo`, { method: 'POST', body: 'hello' })).json());

// A body can be read once; clone() before reading when you need it twice
const res = await fetch(`${base}/books`);
const copy = res.clone();
console.log((await res.json()).length, (await copy.text()).length);
console.log(await res.json().catch((e) => `${e.name}: ${e.message}`));

// Redirects are followed unless you say otherwise
const followed = await fetch(`${base}/old`);
console.log('follow:', followed.status, followed.redirected, new URL(followed.url).pathname);
const manual = await fetch(`${base}/old`, { redirect: 'manual' });
console.log('manual:', manual.status, manual.headers.get('location'));
await fetch(`${base}/old`, { redirect: 'error' }).catch((e) => console.log('error: ', e.name, '-', e.cause.message));
close();
----

[#timeouts]
== Deadlines and cancellation

A `fetch` without a deadline can wait a very long time. Undici's own socket-level defaults (per its documentation: 300 seconds for response headers
and for each gap between body chunks, 10 seconds to connect) are far too generous for a request that a user is waiting on, so give every
outbound call an `AbortSignal`. `AbortSignal.timeout(ms)` is a signal that aborts itself after the delay with a `TimeoutError`, and the deadline covers
the _whole_ exchange: in a test where the server sent the headers and then stalled, `res.text()` still rejected with `TimeoutError` after the deadline.
To let the caller cancel as well (a user navigating away, a parent request being aborted), combine signals with `AbortSignal.any()`; the
reason of whichever signal fired first is what the promise rejects with. The same signals work with `fs`, timers, events and child processes, as
described in xref:backend/nodejs/async-context-and-cancellation.adoc[Async Context & Cancellation].

.A deadline, and a deadline combined with a cancel signal
[source,javascript]
----
import { startServer } from './server.js';

const { base, close } = await startServer();

// A deadline for the whole exchange, including reading the body
try {
  const res = await fetch(`${base}/slow`, { signal: AbortSignal.timeout(300) });
  console.log(await res.text());
} catch (err) {
  console.log(err.name, '-', err.message);       // TimeoutError
}

// A deadline plus a cancel button that the caller controls
const user = new AbortController();
setTimeout(() => user.abort(), 100);
try {
  await fetch(`${base}/slow`, { signal: AbortSignal.any([user.signal, AbortSignal.timeout(5000)]) });
} catch (err) {
  console.log(err.name, '-', err.message);       // AbortError: the user's signal fired first
}
close();
----

Source: https://nodejs.org/docs/latest/api/globals.html#static-method-abortsignaltimeoutdelay[Node.js API: AbortSignal.timeout()], https://nodejs.org/docs/latest/api/globals.html#static-method-abortsignalanysignals[Node.js API: AbortSignal.any()]

.Output (Node.js 26.10.0; identical on 24 and 22)
[source,text]
----
TimeoutError - The operation was aborted due to timeout
AbortError - This operation was aborted
----

Always distinguish the two reasons in `catch`: a `TimeoutError` is usually worth a retry or a clear "upstream is slow" error, while an `AbortError`
is somebody else's decision and should not be retried or logged as a failure.

[#streaming]
== Streaming bodies

`res.body` is a web `ReadableStream` of `Uint8Array` chunks. That is what makes `fetch` suitable for large downloads, newline-delimited JSON,
server-sent events and LLM token streams: you process data as it arrives and memory stays flat. A web stream is async-iterable, so `for await`
works, and `pipeThrough(new TextDecoderStream())` turns bytes into text without splitting multi-byte characters. To connect it to the classic
`node:stream` world (files, `zlib`, `pipeline()`), use `Readable.fromWeb(res.body)`; to send a streaming _request_ body, pass a `Readable`, an async
generator wrapped in `Readable.from()` or a `ReadableStream`, and set `duplex: 'half'`. Without `duplex` the call rejects (observed:
`TypeError: RequestInit: duplex option is required when sending a body`). Conversions are covered in
xref:backend/nodejs/web-streams-and-interop.adoc[Web Streams & Interop] and backpressure in xref:backend/nodejs/streams.adoc[Streams].

If you do not need the body, say so. An unread body keeps the connection busy, and a connection that is neither drained nor cancelled cannot return
to the pool; call `await res.body.cancel()` (or read it) on every response you stop caring about.

.NDJSON line by line, download to a file with backpressure, streaming upload, and cancelling an unread body
[source,javascript]
----
import { startServer } from './server.js';
import { Readable } from 'node:stream';
import { pipeline } from 'node:stream/promises';
import { createWriteStream } from 'node:fs';
import { tmpdir } from 'node:os';
import { join } from 'node:path';
const { base, close } = await startServer();

// Read an NDJSON response line by line, as the bytes arrive
const res = await fetch(`${base}/lines`);
const lines = res.body.pipeThrough(new TextDecoderStream());
let pending = '';
for await (const text of lines) {
  pending += text;
  const parts = pending.split('\n');
  pending = parts.pop();                       // keep an incomplete last line
  for (const line of parts) console.log(JSON.parse(line));
}

// Save a response straight to disk with backpressure
const dest = join(tmpdir(), 'books.json');
const res2 = await fetch(`${base}/books`);
await pipeline(Readable.fromWeb(res2.body), createWriteStream(dest));
console.log('saved', dest);

// Stream a request body from an async generator (needs duplex: 'half')
async function* chunks() {
  yield '{"title":';
  yield '"Streamed"}';
}
const up = await fetch(`${base}/books`, {
  method: 'POST',
  headers: { 'content-type': 'application/json' },
  body: Readable.from(chunks()),
  duplex: 'half',
});
console.log(up.status, await up.json());

// Not reading the body: cancel it so the connection can be reused
const unread = await fetch(`${base}/books`);
console.log('status only:', unread.status);
await unread.body.cancel();
close();
----

[#retries]
== Retries with backoff and Retry-After

Networks and upstream services fail transiently: a connection reset, a `503` during a deploy, a `429` when you exceed a rate limit. A small retry
policy turns many of those into non-events, but a careless one multiplies load on a service that is already struggling. The rules in the helper
below are the usual ones, and each is a line in the code:

.Retry policy implemented below
[cols="2,4"]
|===
|Rule |Why

|Retry only idempotent methods (`GET`, `HEAD`, `OPTIONS`, `PUT`, `DELETE`)
|Repeating a `POST` can create two orders. Retry it only when the API supports an idempotency key and you send one.

|Retry network errors and the statuses `408`, `429`, `500`, `502`, `503`, `504`
|These usually mean "try again"; a `400`, `401` or `404` will not get better.

|Exponential backoff with full jitter
|The delay is a random value between zero and `base * 2^attempt`, capped; the randomness keeps many clients from retrying in lockstep.

|Honour `Retry-After`
|The header is either a number of seconds or an HTTP date (RFC 9110). When the server says when to come back, obey it instead of guessing; the cap still protects you from an absurd value.

|Bound the attempts and respect the caller's signal
|The sleep uses `timers/promises` with the same `AbortSignal`, so cancelling or timing out the call stops the retry loop immediately.

|Cancel the failed response body before waiting
|An unread body would hold its connection for the whole backoff.
|===

.retry.js: fetchWithRetry() and retryAfterMs()
[source,javascript]
----
import { setTimeout as sleep } from 'node:timers/promises';

const RETRYABLE_STATUS = new Set([408, 429, 500, 502, 503, 504]);
const IDEMPOTENT = new Set(['GET', 'HEAD', 'OPTIONS', 'PUT', 'DELETE']);

// Retry-After is either delta-seconds or an HTTP-date.
export function retryAfterMs(value, now = Date.now()) {
  if (!value) return null;
  if (/^\d+$/.test(value)) return Number(value) * 1000;
  const at = Date.parse(value);
  return Number.isNaN(at) ? null : Math.max(0, at - now);
}

export async function fetchWithRetry(url, init = {}, { retries = 3, baseMs = 200, capMs = 10_000 } = {}) {
  const method = (init.method ?? 'GET').toUpperCase();
  const canRetry = IDEMPOTENT.has(method);               // never blindly retry POST
  for (let attempt = 0; ; attempt++) {
    let res;
    try {
      res = await fetch(url, init);
    } catch (err) {
      if (init.signal?.aborted || !canRetry || attempt >= retries) throw err;
      await sleep(Math.random() * Math.min(capMs, baseMs * 2 ** attempt), undefined, { signal: init.signal });
      continue;                                           // network error: back off and retry
    }
    if (!RETRYABLE_STATUS.has(res.status) || !canRetry || attempt >= retries) return res;
    const hinted = retryAfterMs(res.headers.get('retry-after'));
    const backoff = Math.random() * Math.min(capMs, baseMs * 2 ** attempt);   // "full jitter"
    await res.body?.cancel();                             // release the connection before waiting
    await sleep(Math.min(capMs, hinted ?? backoff), undefined, { signal: init.signal });
  }
}
----

Source: https://nodejs.org/docs/latest/api/globals.html#fetch[Node.js API: fetch], https://nodejs.org/docs/latest/api/timers.html#timerspromisessettimeoutdelay-value-options[Node.js API: timers/promises setTimeout()]

The signal passed to `fetchWithRetry()` is shared by all attempts, so `AbortSignal.timeout(10_000)` above is a budget for the _whole_ operation,
not per attempt. If you want a per-attempt limit as well, build it inside the loop and combine both with `AbortSignal.any()`. For production traffic
consider a circuit breaker so that a dead dependency fails fast instead of absorbing every request's full retry budget.

[#concurrency]
== Concurrency limits

`Promise.all(items.map(fetchOne))` starts every request at once. With 16 items that is 16 sockets (measured in the next sections: global `fetch` opened
all 16 connections); with 10,000 items it exhausts file descriptors, trips the remote rate limit or overwhelms your own event loop. Bound the
fan-out. The helper below keeps at most `limit` calls in flight with a shared iterator and `limit` worker loops, and preserves the input order of the
results. Libraries such as `p-limit` do the same with more features, but the pattern is short enough to own.

.mapLimit.js: a bounded Promise.all()
[source,javascript]
----
// Run fn over items with at most `limit` calls in flight; results keep input order.
export async function mapLimit(items, limit, fn) {
  const results = new Array(items.length);
  const entries = items.entries();                        // one shared iterator
  async function worker() {
    for (const [i, item] of entries) results[i] = await fn(item, i);
  }
  await Promise.all(Array.from({ length: Math.min(limit, items.length) }, worker));
  return results;
}
----

Source: https://nodejs.org/docs/latest/api/globals.html#fetch[Node.js API: fetch]

.Twenty requests, at most four at a time
[source,javascript]
----
import { startServer } from './server.js';
import { mapLimit } from './mapLimit.js';

const { base, close } = await startServer();

let inFlight = 0;
let peak = 0;
const ids = Array.from({ length: 20 }, (_, i) => i);
const out = await mapLimit(ids, 4, async (i) => {
  inFlight++;
  peak = Math.max(peak, inFlight);
  const res = await fetch(`${base}/work`);
  const text = await res.text();                      // always consume the body
  inFlight--;
  return `${i}:${text}`;
});
console.log(out.length, out[0], out.at(-1), '| peak in flight =', peak);
close();
----

Source: https://nodejs.org/docs/latest/api/globals.html#fetch[Node.js API: fetch]

[source,text]

An application-level limit and a connection-level limit are different tools. `mapLimit()` bounds how much _work_ you start; an agent's `maxSockets`
(next section) or an Undici dispatcher's `connections` bounds how many _sockets_ are opened per origin. Use the first to protect yourself and the
remote API, and the second to keep the connection count predictable.

[#http-request]
== node:http clients: http.request(), agents and keep-alive

`node:http` is the original client, and it is still what `https`, many SDKs and older libraries use. `http.request(url, options, callback)` returns a
`ClientRequest` (a writable stream: you must call `req.end()`), and the callback receives an `IncomingMessage` (a readable stream). `http.get()` is
the same call with the method fixed to `GET` and `end()` called for you. It is lower level than `fetch`: no JSON helpers, no automatic redirect
following, no promise. Errors arrive as the request's `'error'` event, a stalled socket as `'timeout'` (and the request must be destroyed by hand),
and cancellation through the `signal` option. The wrapper below turns a request into a promise using `events.once()`, whose rejection on `'error'`
removes the boilerplate.

.httpclient.js: a promise wrapper around http.request()
[source,javascript]
----
import http from 'node:http';
import { once } from 'node:events';

// Minimal promise wrapper around http.request(): resolves with { status, headers, body }.
export async function request(url, { method = 'GET', headers, body, agent, signal, timeout } = {}) {
  const req = http.request(url, { method, headers, agent, signal, timeout });
  req.on('timeout', () => req.destroy(new Error(`socket idle for ${timeout} ms`)));
  req.end(body);
  const [res] = await once(req, 'response');            // 'error' rejects once() automatically
  const chunks = [];
  for await (const chunk of res) chunks.push(chunk);     // IncomingMessage is a Readable
  return { status: res.statusCode, headers: res.headers, body: Buffer.concat(chunks).toString() };
}
----

Source: https://nodejs.org/docs/latest/api/http.html#httprequesturl-options-callback[Node.js API: http.request()], https://nodejs.org/docs/latest/api/http.html#class-httpagent[Node.js API: http.Agent], https://nodejs.org/docs/latest/api/events.html#eventsonceemitter-name-options[Node.js API: events.once()]

An `http.Agent` decides what happens to a socket after a request: pool it for the next request to the same host and port, or close it. Opening a TCP
connection (and a TLS handshake for `https`) costs round trips, so reuse matters for chatty clients. The facts that matter in practice:

.http.Agent behaviour and options
[cols="2,4"]
|===
|Option or object |Meaning

|`http.globalAgent`
|Used when you pass no `agent`. Since v19.0.0 it has keep-alive enabled and a 5 second timeout; before that it closed the socket after every request.

|`new http.Agent()`
|A fresh agent has `keepAlive: false` by default: one connection per request, then close. Pass `keepAlive: true` to pool connections.

|`agent: false`
|A throwaway agent with default options for one request: no reuse.

|`keepAlive`, `keepAliveMsecs`
|Keep idle sockets for reuse; `keepAliveMsecs` is the initial delay of TCP keep-alive probes (default 1000).

|`agentKeepAliveTimeoutBuffer`
|Milliseconds subtracted from the server's `keep-alive: timeout=` hint when deciding when to drop an idle socket (default 1000, added in v24.7.0 and v22.20.0), so the client closes first and does not send on a socket the server is about to close.

|`maxSockets`, `maxTotalSockets`
|Per-host and overall caps on open sockets (default `Infinity`); extra requests wait in `agent.requests`.

|`maxFreeSockets`
|Idle sockets kept per host when `keepAlive` is on (default 256).

|`scheduling`
|`'lifo'` (default since v15.6.0) reuses the most recently used socket; `'fifo'` the least recently used.

|`timeout`
|Socket timeout in milliseconds, applied when the socket is created.

|`proxyEnv`
|Per-agent proxy settings (see <<proxies,Proxies>>).
|===

The next program counts server-side TCP connections for five sequential requests under each configuration, shows that `maxSockets` caps parallel
connections, and exercises both timeout styles.

Three practical consequences. First, if you create your own `Agent`, set `keepAlive: true` and `destroy()` it on shutdown; unused pooled sockets are
unreferenced, so they do not keep the process alive, but they do consume file descriptors. Second, pooled connections can be closed by the
server while idle, so a request can occasionally fail on a reused socket; that is another reason to retry idempotent calls. Third, the
socket `timeout` option is an _idle_ timeout (no bytes), not a deadline: use `signal: AbortSignal.timeout(ms)` for a total deadline. The server side
of these limits is in xref:backend/nodejs/server-timeouts-limits-and-hardening.adoc[Server Timeouts, Limits & Hardening].

[#undici]
== Undici beyond fetch: dispatchers and the version trap

Global `fetch` has no connection options of its own, because Undici's connection management lives in a _dispatcher_. A dispatcher decides how many
connections are opened, their timeouts and TLS settings, and where proxy traffic goes. Node.js gives you two ways to customise it, both from the
API page for `fetch`: pass `{ dispatcher }` in the options of one call, or install a global dispatcher with `setGlobalDispatcher()` from the `undici`
package. The bundled Undici is internal, so you install the npm package (`npm install undici`) to get `Agent`, `Pool`, `request()`, `MockAgent` and
friends.

The catch, observed while preparing this page: a dispatcher is only guaranteed to work with the `fetch` of the _same_ Undici version. With the current
npm release (8.11.2 at the time of writing) a dispatcher passed to the global `fetch` worked on Node.js 26 (bundled 8.10.2), but on Node.js 24
(bundled 7.29.1) and Node.js 22 (bundled 6.28.1) the call rejected with `InvalidArgumentError: invalid onRequestStart method` as the cause. The
robust pattern is to import `fetch` from the same package as the dispatcher, as the example does, or to pin the `undici` major that matches
`process.versions.undici` of your oldest supported Node.js line.

.Limiting connections with an Undici Agent, and Undici's lower-level request()
[source,javascript]
----
import { Agent, fetch as undiciFetch, request } from 'undici';
import { startServer } from './server.js';

let sockets = 0;
server.on('connection', () => sockets++);

  sockets = 0;
  await Promise.all(Array.from({ length: 16 }, () => doFetch(`${base}/work`, init).then((r) => r.text())));
  console.log(label.padEnd(40), 'connections opened:', sockets);
}
await burst('global fetch, defaults', fetch);

// Use the SAME package for the dispatcher and for fetch: the Agent must match the fetch implementation
const dispatcher = new Agent({ connections: 4, connect: { timeout: 2000 } });
await burst('undici fetch + Agent({ connections: 4 })', undiciFetch, { dispatcher });

const { statusCode, headers, body } = await request(`${base}/books`, { dispatcher });
console.log(statusCode, headers['content-type'], (await body.json()).length, 'books');
await dispatcher.close();
close();
----

`request()` from the package skips the `Response` object and the Fetch-standard layer for raw speed and control. It requires you to consume or `dump()` the body of every response, which is the same discipline as with `fetch`. Undici's
`fetch` is documented by Node.js as an HTTP/1.1 client; Undici's `Client` has an opt-in `allowH2` option for HTTP/2, and for HTTP/2 in general see
xref:backend/nodejs/https-tls-and-http2.adoc[HTTPS, TLS & HTTP/2].

[#proxies]
== Proxies

Corporate networks often allow outbound traffic only through an HTTP(S) proxy, announced to tools through the conventional environment variables
`HTTP_PROXY`, `HTTPS_PROXY` and `NO_PROXY` (and their lowercase forms). Historically Node.js ignored them, and every library implemented proxy
support on its own: `https-proxy-agent` for `http`, an Undici `ProxyAgent` or `EnvHttpProxyAgent` for `fetch`. Node.js now has built-in support,
Stability 1.1 (Active development), switched on explicitly:

.Ways to enable built-in proxy support
[cols="3,3"]
|===
|Mechanism |What it does

|`NODE_USE_ENV_PROXY=1` (environment variable)
|Reads `HTTP_PROXY`, `HTTPS_PROXY` and `NO_PROXY` at startup and routes `fetch()`, `http` and `https` requests through the proxy by default.

|`node --use-env-proxy app.js`
|The same, as a flag; the flag takes precedence if both are set. The variables can come from `--env-file`.

|`http.setGlobalProxyFromEnv([proxyEnv])`
|Turns support on at runtime (v25.4.0, v24.14.0), reading `process.env` or the object you pass, and returns a function that restores the previous global agent and dispatcher. Call it before any request is in flight.

|`new http.Agent({ proxyEnv })` or `new https.Agent({ proxyEnv })`
|Proxy settings for one agent only (v24.5.0, v22.21.0): `proxyEnv` is an object with `HTTP_PROXY`, `HTTPS_PROXY`, `NO_PROXY` (and lowercase forms, which win if both are present).
|===

A proxy URL may be `http://` or `https://`, with optional `user:password@` credentials. `NO_PROXY` takes a comma-separated list: `*` for every host,
an exact host name, a `.suffix` or `*.suffix` domain match, an exact IP, an IP range such as `192.168.1.1-192.168.1.100`, or `host:port`. Overriding
`http.globalAgent` or `https.globalAgent` by hand affects `http`/`https` requests but does not affect `fetch()`; for `fetch` use the environment
variable, `setGlobalProxyFromEnv()` or a dispatcher.

The next two programs use a small forward proxy defined below. It maps every host name to 127.0.0.1, so a request for the invented name
`books.internal.test` can only succeed if it really goes through the proxy.

.proxy.js and run-proxy.mjs: a forward proxy for experiments (not for production)
[source,javascript]
----
import http from 'node:http';
import net from 'node:net';
import { once } from 'node:events';

// A tiny forward proxy for experiments. It handles plain HTTP forwarding and CONNECT tunnels,
// and maps every host name to 127.0.0.1 so that invented names such as books.internal.test work.
export async function startProxy() {
  const proxy = http.createServer((req, res) => {
    console.log('[proxy]', req.method, req.url);                // absolute-form target: GET http://host:port/path
    const target = new URL(req.url);
    const upstream = http.request(
      { host: '127.0.0.1', port: target.port, path: target.pathname + target.search, method: req.method, headers: req.headers },
      (up) => { res.writeHead(up.statusCode, up.headers); up.pipe(res); },
    );
    req.pipe(upstream);
  });
  proxy.on('connect', (req, client, head) => {
    console.log('[proxy] CONNECT', req.url);                    // used for tunnels, e.g. HTTPS through a proxy
    const upstream = net.connect(Number(req.url.split(':')[1]), '127.0.0.1', () => {
      client.write('HTTP/1.1 200 Connection Established\r\n\r\n');
      upstream.write(head);
      upstream.pipe(client);
      client.pipe(upstream);
    });
    upstream.on('error', () => client.destroy());
    client.on('error', () => upstream.destroy());
  });
  proxy.listen(0, '127.0.0.1');
  await once(proxy, 'listening');
  return { url: `http://127.0.0.1:${proxy.address().port}`, close: () => proxy.close() };
}

// run-proxy.mjs
import { startProxy } from './proxy.js';

const proxy = await startProxy();
console.log(proxy.url);       // the first line is the proxy URL; the process keeps running
----

[#enterprise-ca]
== Enterprise certificate authorities

Inside a company, internal services are often signed by a private CA that is installed in the operating system's trust store, which Node.js
does not consult by default: it uses its own bundle of Mozilla roots. The symptom is an error such as `self signed certificate in certificate chain`
or `UNABLE_TO_VERIFY_LEAF_SIGNATURE`. There are four correct fixes, and one tempting wrong one.

.Ways to trust a private CA
[cols="3,3,2"]
|===
|Mechanism |Scope |Versions

|`NODE_USE_SYSTEM_CA=1` or `--use-system-ca`
|Whole process: bundled roots plus the system store (Windows certificate store, macOS keychain, on Linux the OpenSSL default locations)
|v22.19.0 and v24.6.0 for the variable; the flag since v23.8.0

|`NODE_EXTRA_CA_CERTS=/path/ca.pem`
|Whole process: bundled roots plus the PEM file; read once at startup; ignored when node runs as setuid root or with Linux file capabilities
|v7.3.0

|`tls.setDefaultCACertificates([...])` (with `tls.getCACertificates('default' \| 'system' \| 'bundled' \| 'extra')` for the lists)
|Whole thread, at runtime; call it before the first TLS connection
|v22.19.0 and v24.5.0 (`getCACertificates` since v22.15.0 and v23.10.0)

|The `ca` option of `https.request()`, `tls.connect()`, or an Undici dispatcher's `connect: { ca }`
|One request or one dispatcher; _replaces_ the default roots instead of adding to them
|All lines
|===

The wrong fix is `NODE_TLS_REJECT_UNAUTHORIZED=0` (or `rejectUnauthorized: false`), which turns certificate validation off; the CLI documentation says plainly
that it makes TLS insecure and is strongly discouraged. It also silences exactly the attacker who would present a forged certificate.

[#axios]
== Migrating from axios

axios was the default HTTP client for a decade because browsers and old Node.js lacked a good one. Today `fetch` covers the common cases without a
dependency, and the Node.js project ships a codemod for the mechanical part of the move: `npx codemod @nodejs/axios-to-whatwg-fetch` (documented in
the Node.js Learn "Userland Migrations" series). It rewrites `axios.request()`, `get()`, `delete()`, `head()`, `options()`, `post()`, `put()`, `patch()`
and the `postForm()`, `putForm()` and `patchForm()` helpers, in ESM imports, aliased imports, CommonJS `require()` and dynamic `import()`, and removes
`axios` and `@types/axios` from `package.json` once every call site is converted. It was not run for this page; its documented behaviour is what the
following paragraphs describe.

The codemod keeps `response.data` working by wrapping each call as `fetch(url).then(async (res) => Object.assign(res, { data: await res.json() }))`
and appends `.catch(() => null)`, so a failed request resolves to `null` instead of rejecting. Two more points from the documentation matter for review:
`fetch` does not reject on 4xx and 5xx statuses, so code that relied on axios rejecting needs manual attention, and if any call in a file uses a
configuration option that has no direct equivalent, the whole file is left untouched with a warning. The options on that list include `timeout`,
`signal`, `validateStatus`, `maxRedirects`, `maxContentLength`, `httpAgent`, `httpsAgent`, `transformRequest`, `transformResponse`,
`paramsSerializer`, `withCredentials`, `cancelToken`, `socketPath`, `decompress` and `beforeRedirect`; interceptors, cancel tokens and
`axios.create()` instances are outside its scope. That is most real-world axios code, which is why the sensible approach is to migrate by hand around a small client
of your own, not to expect the codemod to finish the job.

.Where axios and fetch differ
[cols="2,3,3"]
|===
|Concern |axios |fetch (and what to write)

|Status errors
|Rejects on non-2xx (`AxiosError`, `error.response.status`, `error.response.data`).
|Resolves. Check `res.ok`; throw your own `HttpError` with status and parsed body.

|Response body
|Parsed into `response.data`.
|Call `res.json()` or `res.text()`; a `Response` body is single-use.

|Request JSON
|Object `data` is serialised and `content-type` set.
|`JSON.stringify()` the body and set `content-type: application/json`.

|Query string
|`params` option, `paramsSerializer`.
|`new URL()` plus `url.searchParams.set()`, or `new URLSearchParams(obj)`.

|Base URL
|`baseURL` on the instance.
|`new URL(path, base)`; note that a leading slash in `path` replaces any path in `base`.

|Timeout
|`timeout` option (`ECONNABORTED`).
|`signal: AbortSignal.timeout(ms)`, rejecting with `TimeoutError`.

|Cancellation
|`signal` (and the deprecated cancel token).
|`signal` with `AbortController`, `AbortSignal.any()`.

|Interceptors
|`interceptors.request` and `interceptors.response`.
|A wrapper function around `fetch`, or an Undici interceptor on a dispatcher.

|Connection pooling and proxy
|`httpAgent`, `httpsAgent`, `proxy` option.
|Undici dispatcher, `NODE_USE_ENV_PROXY`, `proxyEnv`.

|Upload and download progress
|`onUploadProgress`, `onDownloadProgress`.
|Stream the body and count bytes yourself.

|Automatic retries
|Not built in (plugins).
|Your own helper, as in <<retries,Retries>>.
|===

The wrapper below is a replacement for the `axios.create()` pattern in about thirty lines: base URL, default headers, query parameters, JSON in and out, a
per-call deadline that can be combined with a caller signal, and an `HttpError` that carries the status and parsed body like `error.response` did. The
program then runs the same calls through axios (installed only in the scratch project) and through the wrapper to compare results.

.client.js: an axios.create() replacement built on fetch
[source,javascript]
----
export class HttpError extends Error {
  constructor(res, body) {
    super(`HTTP ${res.status} ${res.statusText} for ${res.url}`);
    this.name = 'HttpError';
    this.status = res.status;
    this.body = body;                 // parsed JSON or text, like axios's error.response.data
    this.headers = res.headers;
  }
}

// A small axios.create() replacement: base URL, default headers, query params,
// JSON in/out, a per-request timeout and throwing on non-2xx statuses.
export function createClient({ baseUrl, headers = {}, timeoutMs = 10_000 } = {}) {
  const root = baseUrl.endsWith('/') ? baseUrl : `${baseUrl}/`;
  async function send(method, path, { params, json, signal, headers: extra } = {}) {
    const url = new URL(path.replace(/^\//, ''), root);            // 'books', not '/books': a leading slash resets the path
    for (const [k, v] of Object.entries(params ?? {})) url.searchParams.set(k, String(v));
    const res = await fetch(url, {
      method,
      headers: { accept: 'application/json', ...(json !== undefined && { 'content-type': 'application/json' }), ...headers, ...extra },
      body: json === undefined ? undefined : JSON.stringify(json),
      signal: signal ? AbortSignal.any([signal, AbortSignal.timeout(timeoutMs)]) : AbortSignal.timeout(timeoutMs),
    });
    const text = await res.text();
    const data = text && res.headers.get('content-type')?.includes('json') ? JSON.parse(text) : text;
    if (!res.ok) throw new HttpError(res, data);                   // axios rejects here; fetch does not
    return { status: res.status, headers: res.headers, data };
  }
  return {
    get: (path, opts) => send('GET', path, opts),
    post: (path, json, opts) => send('POST', path, { ...opts, json }),
    put: (path, json, opts) => send('PUT', path, { ...opts, json }),
    delete: (path, opts) => send('DELETE', path, opts),
  };
}
----

Source: https://nodejs.org/learn/userland-migrations/axios-to-whatwg-fetch[Node.js Learn: Axios to WHATWG Fetch], https://nodejs.org/docs/latest/api/globals.html#fetch[Node.js API: fetch]

A migration checklist that follows from this: grep for `validateStatus`, interceptors and `error.response` first, because they are the places where
behaviour changes silently; move the timeout to a signal next, since a request that used to be bounded by axios's `timeout` is unbounded with a bare `fetch`;
then replace the remaining call sites with the client above; finally remove the dependency and run the tests. Compare with the effort of keeping the
dependency honestly: axios is maintained and works, so the migration is about fewer dependencies and one HTTP stack to configure, not about a defect.

[#practices]
== Practical guidance

* Give every outbound request a deadline (`AbortSignal.timeout()`), and a status check (`res.ok`); those two lines prevent most outage stories.
* Always consume or cancel the body, including on error paths, so connections return to the pool.
* Retry idempotent requests only, with jittered backoff, a cap and `Retry-After`; make a retried `POST` safe with an idempotency key.
* Bound concurrency (`mapLimit()` or a dispatcher's `connections`) before you fan out.
* Build URLs with `URL` and `searchParams`; never concatenate user input into a URL. When the target host comes from user input, validate it against an
  allow-list to avoid server-side request forgery, because `fetch` will happily call `http://169.254.169.254/` or an internal address for you.
* Keep secrets out of URLs and logs; send them in headers, read them from `process.env` (loaded with `--env-file`), and never log full request headers.
* Reuse connections: rely on the global agent and the global `fetch` pool, or keep one long-lived `Agent` or dispatcher per process, not one per request.
* In tests, avoid real network calls: point the code at a local server on port 0 as in this page, or use Undici's `MockAgent`; see
  xref:backend/nodejs/mocking-snapshots-and-coverage.adoc[Mocking, Snapshots & Coverage].
* Where the call is to an LLM provider, the same rules (deadline, streaming, retry on `429` with `Retry-After`) apply; see
  xref:backend/nodejs/integrating-llm-apis.adoc[Integrating LLM APIs].

[#books]
== Where the books are outdated

This section compares the page with two O'Reilly books consulted while preparing this guide: _Efficient Node.js_ by Samer Buna and _Node.js Projects_ by
Jonathan Wexler. Both are published in 2025 and mostly current; the points below are about habits worth updating, not mistakes of the authors.

* _Node.js Projects_ (Wexler) uses the axios package for server-to-server calls, including a peer-to-peer example and a call to an AI model API, and
  tells readers on older Node.js lines to install `node-fetch`. Both pieces of advice are now unnecessary: global `fetch` is in every supported
  line (Node.js 18 reached end of life on 2025-04-30), and the Node.js project documents a codemod from axios to fetch. When you adapt those
  projects, remember that `fetch` does not reject on error statuses and has no `timeout` option, as the migration section shows. The same
  book's API keys in a `.env` file loaded by a package are better served today by `--env-file`, covered in
  xref:backend/nodejs/cli-options-environment-and-config-file.adoc[CLI Options, Environment & Config File].
* _Efficient Node.js_ (Buna) uses `fetch` in short examples, such as one that feeds several API responses into a stream. Like most book
  examples they omit what production code needs: an `res.ok` check, a deadline, retries, and a concurrency limit. Use the helpers above for those.
* Neither book covers the built-in proxy and system-CA support added in the Node.js 22.19 to 22.21 and 24 lines, the Undici-versus-npm dispatcher
  compatibility issue, or the `http.globalAgent` keep-alive default introduced in v19.0.0, so older advice to create a keep-alive agent for every
  `http` client is partly obsolete: the global agent already pools connections.
