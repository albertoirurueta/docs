Oracle Database is one of the databases that Quartz has supported through its JDBC job store from the beginning, and the Quartz jar still contains a delegate class named after it
and two DDL scripts for it. A Spring Boot service that already runs on Oracle can therefore keep its triggers, job definitions and cluster state next to its business data. What makes
Oracle different from the other SQL pages of this section is not the locking (it is plain `SELECT ... FOR UPDATE`, the same statement every other engine receives) but a
driver and script combination: since the Oracle JDBC driver moved to the 23 line, the script that Spring Boot picks for Oracle by default stops working, and the symptom is a
database error on the very first job that is stored. This page explains why, shows the matrix of what was run, and then goes through the setup in the order in which a reader
needs it: dependencies, the delegate, the two scripts, a schema user, migrations, `application.yml`, locking, clustering and a Testcontainers test. Every statement
about what works or fails was produced by running it.

The generic concepts (what the `QRTZ_` tables are, `initialize-schema`, `@QuartzDataSource`, pool sizing) are on
xref:backend/scheduling/job-stores-and-persistence.adoc[Job Stores & Persistence]; the reference database page is
xref:backend/scheduling/database-postgresql.adoc[Quartz on PostgreSQL]; clustering in general is on xref:backend/scheduling/clustering.adoc[Clustering]. The sibling page with the
same template for another engine that needs script edits is xref:backend/scheduling/database-sql-server.adoc[Quartz on SQL Server].

It was written against Quartz 2.5.2, Spring Boot 4.1.1, Spring Framework 7.0.9 and Java 21 and verified on 5 October 2026 on an Apple Silicon (arm64) Mac with the Docker image
`gvenzl/oracle-free:slim-faststart`, which started natively on arm64 and whose server reported `Oracle AI Database 26ai Free Release 23.26.3.0.0` (version 23.26.3.0.0, the
release line that was called Oracle Database 23ai; this page says "23ai" for the BOOLEAN-capable generation and quotes the banner for the exact build) with the pluggable database `FREEPDB1`.
The JDBC driver was `ojdbc11` 23.26.3.0.0 (the version Spring Boot 4.1.1 manages), and the matrix was repeated with `ojdbc11` 21.9.0.0 and 23.7.0.25.01 by overriding the Boot property
`oracle-database.version`. The other versions in play were Flyway 12.4.0, Liquibase 5.0.3 (both Boot-managed) and Testcontainers 2.0.5. The projects were compiled for Java 21 and
run on JDK 26.0.1. Only Oracle Database Free 23ai was available: a 19c or 21c server was not run, and everything the page says about those releases is labelled as not run. Spring Boot 3.5.16
manages the same Quartz 2.5.2, so everything about Quartz is identical there; only the package of `@QuartzDataSource` and `SchedulerFactoryBeanCustomizer` differs
(`org.springframework.boot.autoconfigure.quartz` instead of `org.springframework.boot.quartz.autoconfigure`), Spring Framework is 6.2.19, and the Boot-managed driver is
`ojdbc11` 23.7.0.25.01, which was also run (it fails the same way as 23.26.3.0.0 with the old script, see the matrix).

== Status and dependencies

Status: official. The JDBC job store, the `OracleDelegate` and the two DDL scripts are part of Quartz itself and are maintained with it, unlike the MongoDB and Redis stores.
Quartz's own tutorial lists Oracle among the databases the JDBC job store "has been used widely with".

[#delegate]
== The delegate: what OracleDelegate changes

`org.quartz.impl.jdbcjobstore.oracle.OracleDelegate` lives in an `oracle` sub-package, which is the most common way to misspell it: there is no `org.quartz.impl.jdbcjobstore.OracleDelegate`
class in the jar, and a `driverDelegateClass` without the sub-package fails with a class-not-found error at startup. Its Javadoc calls it "a driver delegate for the Oracle 10 and 11 database".
It extends `StdJDBCDelegate` and overrides the code that writes and reads `BLOB` columns, nothing else:

.What OracleDelegate overrides (read from the 2.5.2 source)
[cols="3,6",options="header"]
|===
|Method |What it does differently from `StdJDBCDelegate`

|`insertJobDetail`, `updateJobDetail`, `updateJobData`
|Inserts or updates the row with `EMPTY_BLOB()` in `JOB_DATA`, selects that row with `SELECT ... FOR UPDATE`, writes the serialised `JobDataMap` into the returned locator and runs a second
 `UPDATE` with `setBlob`. The standard delegate binds the bytes in one statement with `PreparedStatement.setBytes`.

|`insertTrigger`, `updateTrigger`
|The same three-step write for the trigger's own `JOB_DATA` (only when the trigger has data; `updateTrigger` skips it when the map is not dirty).

|`insertCalendar`, `updateCalendar`
|The same for the `CALENDAR` column of `QRTZ_CALENDARS`.

|`writeDataToBlob`
|Casts the locator to `oracle.sql.BLOB`, calls `putBytes` and `trim`, and throws `SQLException("Driver's Blob representation is of an unsupported type: ...")` for any other `Blob` implementation.

|`getObjectFromBlob`, `getJobDataFromBlob`
|Reads with `ResultSet.getBinaryStream`; with `useProperties=true` it returns the stream itself so the properties loader reads it.
|===

Source: https://github.com/quartz-scheduler/quartz/blob/v2.5.2/quartz/src/main/java/org/quartz/impl/jdbcjobstore/oracle/OracleDelegate.java[OracleDelegate.java (v2.5.2)] and
https://www.quartz-scheduler.org/api/2.5.x/org/quartz/impl/jdbcjobstore/oracle/OracleDelegate.html[Quartz Javadoc: OracleDelegate].

The class also depends on Oracle's own `oracle.sql.BLOB`, so it needs the Oracle driver on the classpath to load, and it is the reason the delegate is tied to Oracle's driver and not to
any wrapper that hands out another `Blob` type. The sibling `oracle.weblogic.WebLogicOracleDelegate` exists for Oracle drivers used inside a WebLogic server; the
Quartz configuration page lists it as `org.quartz.impl.jdbcjobstore.oracle.WebLogicOracleDelegate`, which is not in the jar (the class is in the `oracle.weblogic` sub-package).

What matters in practice is that the extra machinery is no longer needed with a current driver. The Bookshelf jobs were run twice on Oracle Database Free with `ojdbc11` 23.26.3.0.0, once with
no `driverDelegateClass` (the scheduler then reports no delegate class and Quartz uses `StdJDBCDelegate`) and once with `OracleDelegate`, and a second test stored data of hundreds of kilobytes:

The recommendation that follows is conservative. Leaving the delegate unset is what was tested most (it is also what Boot does when you set nothing), and `OracleDelegate` is accepted and worked in

[#scripts]
== Two schema scripts: tables_oracle.sql and tables_oracle23.sql

The 2.5.2 jar carries two Oracle scripts under `org/quartz/impl/jdbcjobstore/`, and the 2.3.2 and 2.4.1 jars carry only the first one (read from the jar listings).
They differ in one thing, the type of the boolean flags:

.The only differences between the two scripts (`diff tables_oracle.sql tables_oracle23.sql`)
[cols="3,3,3",options="header"]
|===
|Column |`tables_oracle.sql` |`tables_oracle23.sql`

|`QRTZ_JOB_DETAILS.IS_DURABLE`, `IS_NONCONCURRENT`, `IS_UPDATE_DATA`, `REQUESTS_RECOVERY`
|`VARCHAR2(1) NOT NULL`
|`BOOLEAN NOT NULL`

|`QRTZ_SIMPROP_TRIGGERS.BOOL_PROP_1`, `BOOL_PROP_2`
|`VARCHAR2(1) NULL`
|`BOOLEAN NULL`

|`QRTZ_FIRED_TRIGGERS.IS_NONCONCURRENT`, `REQUESTS_RECOVERY`
|`VARCHAR2(1) NULL`
|`BOOLEAN NULL`
|===

Source: https://github.com/quartz-scheduler/quartz/blob/v2.5.2/quartz/src/main/resources/org/quartz/impl/jdbcjobstore/tables_oracle23.sql[tables_oracle23.sql (v2.5.2)] and
https://github.com/quartz-scheduler/quartz/blob/v2.5.2/quartz/src/main/resources/org/quartz/impl/jdbcjobstore/tables_oracle.sql[tables_oracle.sql (v2.5.2)]; the table is the output of `diff` on the two files from the jar, plus a trailing blank line that only the old script has.

Everything else is shared: eleven `CREATE TABLE` statements and twenty `CREATE INDEX` statements (counted in the file and confirmed with `user_tables` and `user_indexes` after a run), `VARCHAR2` names of 120 characters
for the scheduler name and 200 for the job and trigger names, `NUMBER(13)` columns for every time (epoch milliseconds, so the database time zone never matters), `BLOB` columns for the job data, the trigger data, the
calendars and the blob triggers, and unquoted lower-case identifiers, which Oracle folds to upper case. The script's comment says Oracle "MUST be created as shared" with `job_queue_processes` above 2 and then
immediately says other users have run in dedicated mode; the hint dates from the first Quartz releases and it is not needed for the JDBC job store as measured here (the Free image ran in its default mode).

Three conclusions follow from the matrix.

* The `ORA-12899` is a driver behaviour, not a Quartz bug and not an Oracle delegate bug. `StdJDBCDelegate.setBoolean` calls `PreparedStatement.setBoolean`, and the 23.x driver sends a four-character value for it (the error says "actual: 4"), which does
 not fit into a `VARCHAR2(1)` column. The 21.9 driver stores `1` and `0` instead (the stock delegate left `1` and `0` in the `VARCHAR2(1)` columns when it was run, and the `BOOLEAN` columns of
 `tables_oracle23.sql` also accept it). `OracleDelegate` does not change this, because it calls the same `setBoolean`.
* `tables_oracle23.sql` worked with all three drivers on the 23ai server, so on a 23ai database it is the script to use whatever the driver, and it removes the dependency on the driver's boolean binding.
* The `BOOLEAN` SQL column type exists from Oracle Database 23ai. A 19c or 21c server cannot create `tables_oracle23.sql`; that was not run here because no such server was available. For those releases the two
 options below keep `VARCHAR2(1)` columns and make the driver store `1` and `0`.

=== Choosing the script in Spring Boot

Boot's `spring.quartz.jdbc.schema` property names the script, and `spring.quartz.jdbc.platform` is the value that replaces `@@platform@@` in its default path. Both ways of selecting the 23 script were run and
created the tables:

.application.yml: two equivalent ways to select tables_oracle23.sql
[source,yaml]
----
spring:
  quartz:
    jdbc:
      # either name the script ...
      schema: classpath:org/quartz/impl/jdbcjobstore/tables_oracle23.sql
      # ... or change the platform id that Boot substitutes into tables_@@platform@@.sql
      # platform: oracle23
----

Source: https://docs.spring.io/spring-boot/reference/io/quartz.html[Spring Boot: Quartz Scheduler]. Each variant was run alone (`schema`, and `platform: oracle23` with no `schema`), with `initialize-schema=always`, and both passed the Bookshelf scenario with `ojdbc11` 23.26.3.0.0.

=== Keeping tables_oracle.sql: pin the driver or bind the flags yourself

If the server is older than 23ai the `VARCHAR2(1)` script is the only option, and with a 23.x driver the flags must be bound as text. Option A is to pin `ojdbc11` to a 21.x release (the property override shown above); with
`ojdbc11` 21.9.0.0 and `tables_oracle.sql` the stock delegate and `OracleDelegate` both worked, against the 23ai server. Option B keeps the 23.x driver and overrides the two protected methods that `StdJDBCDelegate` uses for
booleans (`setBoolean` for writing, and the two `getBoolean` overloads for reading):

.Varchar2FlagOracleDelegate.java: store the flags as '1' and '0' in VARCHAR2(1) columns
[source,java]
----
package bookshelf;

import org.quartz.impl.jdbcjobstore.oracle.OracleDelegate;

import java.sql.PreparedStatement;
import java.sql.ResultSet;
import java.sql.SQLException;

public class Varchar2FlagOracleDelegate extends OracleDelegate {

    @Override
    protected void setBoolean(PreparedStatement ps, int index, boolean val) throws SQLException {
        ps.setString(index, val ? "1" : "0");
    }

    @Override
    protected boolean getBoolean(ResultSet rs, String columnName) throws SQLException {
        return "1".equals(rs.getString(columnName));
    }

    @Override
    protected boolean getBoolean(ResultSet rs, int columnIndex) throws SQLException {
        return "1".equals(rs.getString(columnIndex));
    }
}
----

Source: https://www.quartz-scheduler.org/api/2.5.x/org/quartz/impl/jdbcjobstore/StdJDBCDelegate.html[Quartz Javadoc: StdJDBCDelegate] and
https://github.com/quartz-scheduler/quartz/blob/v2.5.2/quartz/src/main/java/org/quartz/impl/jdbcjobstore/StdJDBCDelegate.java[StdJDBCDelegate.java (v2.5.2)]. The class compiled and was run as `driverDelegateClass` against `tables_oracle.sql` (without its leading statements) with `ojdbc11` 23.26.3.0.0 and with 21.9.0.0 on the 23ai server: the Bookshelf scenario passed and the
`IS_DURABLE` column held `1` for the four stored jobs. It was not run on a 19c or 21c server, so test it there before relying on it.

[#head]
== The leading delete and drop statements

Every Oracle script starts with eleven `delete from qrtz_...` statements and eleven `drop table qrtz_...` statements, with no `IF EXISTS`, before the first `CREATE TABLE`. On a schema that has no Quartz
tables yet each of them fails with `ORA-00942` (table or view does not exist). That has three consequences, each measured:

* With Boot's default `continue-on-error: true` the initializer logs the failures, skips them and runs the `CREATE` statements, so the first start works. The failure is silent, which is how the `ORA-12899` of the previous section
 is the first error a reader sees.
* With `continue-on-error: false` startup fails at statement 1, whichever script and driver (the first two rows of the matrix).
* With `initialize-schema: always` the head also does its job on an existing schema, and that is a data-loss trap: the application was started with the development profile of this page, stored jobs, restarted, and the `runs` counter that
 the nightly job keeps in its `JobDataMap` had gone from 4 back to 1, because the second start deleted and recreated every table. Never use `always` against a database whose triggers matter.

A migration tool must not receive those lines: Flyway and Liquibase stop at the first failing statement, and a migration is supposed to run exactly once on an empty schema. The edit is to delete them and keep
every `CREATE`:

.One command: tables_oracle23.sql from the jar without the delete and drop statements
[source,bash]
----
unzip -p quartz-2.5.2.jar org/quartz/impl/jdbcjobstore/tables_oracle23.sql \
  | sed -e '/^delete from /d' -e '/^drop table /d' > V1__quartz_tables.sql
----

Source: https://github.com/quartz-scheduler/quartz/blob/v2.5.2/quartz/src/main/resources/org/quartz/impl/jdbcjobstore/tables_oracle23.sql[tables_oracle23.sql (v2.5.2)]. The result has 11 `CREATE TABLE` and 20 `CREATE INDEX` statements and is byte-identical to the file used in every Flyway, Liquibase and strict (`continue-on-error: false`) run below.

The same `sed` on `tables_oracle.sql` gives the VARCHAR2 variant. Both were run through Boot's initializer with `continue-on-error: false` as the schema user `QUARTZ` described next, and the
Bookshelf scenario passed with the 23 script on `ojdbc11` 23.26.3.0.0, and with the old script on `ojdbc11` 21.9.0.0 (and failed with `ORA-12899` on 23.26.3.0.0, as the matrix says).

[#user]
== A schema user on a pluggable database

Quartz needs a schema of its own, or at least its own set of tables: a user that owns the eleven tables is the simplest arrangement. The Free image is a container database whose application data lives in the pluggable
database `FREEPDB1`, so the connection uses that service name, not the container root. The commands were run as `SYSTEM` against `FREEPDB1`:

.create-quartz-user.sql: a user that can connect and create its own tables, nothing else
[source,sql]
----
CREATE USER quartz IDENTIFIED BY "<choose-a-strong-password>"
  DEFAULT TABLESPACE users
  TEMPORARY TABLESPACE temp
  QUOTA UNLIMITED ON users;

GRANT CREATE SESSION, CREATE TABLE TO quartz;
----

Source: https://docs.oracle.com/en/database/oracle/oracle-database/23/sqlrf/CREATE-USER.html[Oracle Database SQL Language Reference: CREATE USER]. Executed through JDBC against `jdbc:oracle:thin:@//localhost:<mapped-port>/FREEPDB1` as `SYSTEM`; a test password that is not shown here was used. Querying `session_privs` as the new user returned exactly `CREATE SESSION` and `CREATE TABLE`.

The user created that way ran the whole Bookshelf scenario: Boot's initializer created the eleven tables and the twenty indexes in the `QUARTZ` schema, Quartz fired the jobs and stored a serialised `JobDataMap`, and Flyway and Liquibase (next sections) used the same
user to create their own bookkeeping tables. No privilege was granted on any other schema and no role was needed. The quota is what lets the user store the table, index and `BLOB` segments; the `CREATE TABLE`
privilege also covers the indexes the owner creates in its own schema. In production, run the creation script as an administrator once, keep the password in a secret store, and give the application only
`$\{DB_PASSWORD}` (see <<yaml>>).

The convenient alternative in tests is to let the Testcontainers module create the user: `new OracleContainer(image).withUsername("quartz").withPassword("...")` makes the image create an application user with that name, and
querying it showed far more than Quartz needs: 29 session privileges (including `CREATE TABLE`, `CREATE VIEW`, `CREATE PROCEDURE`, `CREATE JOB` and `CREATE MATERIALIZED VIEW`) and the roles `DB_DEVELOPER_ROLE`, `RESOURCE` and `SODA_APP`. That is fine for a
throw-away container and wrong as a model for a real database.

Two Oracle facts worth keeping next to the setup. If the Quartz tables must live in another schema than the connecting user's, Quartz substitutes `org.quartz.jobStore.tablePrefix` verbatim into every statement (the default is `QRTZ_`), so a
schema-qualified prefix such as `QUARTZ.QRTZ_` is the mechanism; that variant was not run here. And because Oracle treats an empty string as `NULL`, a job described with `""` reads back with a `null` description (measured above), which is harmless but shows up in comparisons.

== Transactions and locking

Under Spring Boot the job store is `LocalDataSourceJobStore`, a `JobStoreCMT` subclass, and `JobStoreCMT.initialize` forces database locks on unless the data source is HSQL (the Spring class switches to an in-memory semaphore only for HSQL). So on Oracle every
Quartz scheduler uses `StdRowLockSemaphore`, even a single non-clustered node, and a clustered one needs it by definition. The semaphore takes a row lock with exactly this statement (the constant `SELECT_FOR_LOCK`, with the table prefix and scheduler name filled in):

.The lock statement, as Oracle received it (from V$SQL while a clustered scheduler was running)
[source,sql]
----
SELECT * FROM QRTZ_LOCKS WHERE SCHED_NAME = 'BookshelfCluster' AND LOCK_NAME = :1 FOR UPDATE
----

Source: https://github.com/quartz-scheduler/quartz/blob/v2.5.2/quartz/src/main/java/org/quartz/impl/jdbcjobstore/StdRowLockSemaphore.java[StdRowLockSemaphore.java (v2.5.2)] and https://docs.oracle.com/en/database/oracle/oracle-database/23/sqlrf/SELECT.html[Oracle Database SQL Language Reference: SELECT, the FOR UPDATE clause]. The statement text and its execution count (9 in an eight second run with a two second check-in) come from `V$SQL`; the same view also showed the `INSERT INTO QRTZ_LOCKS(SCHED_NAME, LOCK_NAME) VALUES (...)` that creates a lock row on first use (twice, once for `STATE_ACCESS` and once for `TRIGGER_ACCESS`; the script inserts none).

That is plain Oracle SQL, so no `selectWithLockSQL` override is needed (unlike SQL Server, where Quartz substitutes lock hints). The two lock names matter: `TRIGGER_ACCESS` guards every change of trigger state that must not interleave between nodes, and `STATE_ACCESS` guards the cluster check-in and the
recovery of a failed node. By default `acquireNextTriggers` does not take `TRIGGER_ACCESS` at all (`acquireTriggersWithinLock` is false and the batch size is 1): it moves a trigger from `WAITING` to `ACQUIRED` with a conditional `UPDATE` and checks that one row changed,
and only the following `triggersFired` call, which turns the acquired trigger into a fired one, runs inside the lock.

[mermaid]
....
sequenceDiagram
    participant A as Node A
    participant DB as Oracle QRTZ tables
    participant B as Node B
    A->>DB: UPDATE trigger WAITING to ACQUIRED where state is WAITING
    B->>DB: same UPDATE for the same trigger
    DB-->>A: 1 row updated, A owns the trigger
    DB-->>B: 0 rows updated, B moves on
    A->>DB: SELECT FOR UPDATE on TRIGGER_ACCESS lock row
    Note over A,DB: the row stays locked until A commits
    A->>DB: triggersFired inserts QRTZ_FIRED_TRIGGERS and updates the trigger
    A->>DB: COMMIT releases the lock
    B->>DB: SELECT FOR UPDATE on TRIGGER_ACCESS for its own triggersFired
    Note over B,DB: waits only while another node holds the row
....

Source: https://github.com/quartz-scheduler/quartz/blob/v2.5.2/quartz/src/main/java/org/quartz/impl/jdbcjobstore/JobStoreSupport.java[JobStoreSupport.java (v2.5.2)], methods `acquireNextTriggers` and `triggersFired`. The two statements are drawn from the source; the lock behaviour of the row itself is the measurement below.

Oracle's behaviour on that row was measured with two JDBC sessions on a schema with a clustered scheduler stopped in standby: the first session ran the statement above and kept its transaction open, and the second session tried to lock the same row:

|===
|Second session's statement |Result

|`... FOR UPDATE` (what Quartz sends)
|blocked: still waiting after 2000 ms; it returned `TRIGGER_ACCESS` right after the first session rolled back (2008 ms after it started)

|`... FOR UPDATE NOWAIT`

Source: https://docs.oracle.com/en/database/oracle/oracle-database/23/cncpt/data-concurrency-and-consistency.html[Oracle Database Concepts: Data Concurrency and Consistency]. The measurements are from a test run with two connections to `QRTZ_LOCKS`.

Two practical consequences. A session that runs `SELECT ... FOR UPDATE` on `QRTZ_LOCKS` for inspection and is left open in a SQL client freezes the firing of every node until it ends: use plain `SELECT` statements (as in the queries above, which Oracle answers
without locking, because readers do not block writers). And Oracle's undo-based concurrency means the tables do not need a `VACUUM`-style routine for the constant insert and delete churn of `QRTZ_FIRED_TRIGGERS` (the PostgreSQL page has to deal with bloat there).
That second point is Oracle's documented behaviour and was not measured.

The isolation level is the Oracle default. A connection from the Hikari pool reported `Connection.TRANSACTION_READ_COMMITTED` (2) with auto-commit on; `LocalDataSourceJobStore` sets `dontSetAutoCommitFalse` because Spring manages the transaction around the Quartz calls
(see xref:backend/springboot/transaction-isolation-and-locking.adoc[Transaction Isolation & Locking] for the Spring side). Quartz has an opt-in `org.quartz.jobStore.txIsolationLevelSerializable` (default false in `JobStoreSupport`); the Oracle documentation says that a serializable transaction raises
an error instead of waiting when it meets a concurrent change, so leave it off on Oracle. That behaviour is documented, not measured here. According to the Oracle documentation the database offers only `READ COMMITTED`, `SERIALIZABLE` and read-only transactions, which is why the Quartz option offers no other level.
If a lock attempt fails, `StdRowLockSemaphore` retries up to 3 times one second apart before it throws (`maxRetry` and `retryPeriod`, read from the source).

[#testcontainers]
== A Testcontainers test for the Bookshelf jobs

The test below starts Oracle Database Free in a container, lets Boot create the schema from the headless `tables_oracle23.sql` with `continue-on-error=false` (so any script error fails the test; the property exists on Spring Boot 4.x only, on 3.5.16 the initializer hard-codes `true`), and checks that the Bookshelf triggers are rows in Oracle and that the cache refresh fired
and persisted its previous fire time. The image is large (4.81 GB) but started natively on the Apple Silicon Mac that ran the tests: the container was ready in 6 to 9 seconds and the whole test class took 17 seconds.

.src/test/java/bookshelf/BookshelfOracleTest.java
[source,java]
----
package bookshelf;

import org.junit.jupiter.api.Test;
import org.quartz.Scheduler;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.jdbc.core.JdbcTemplate;
import org.springframework.test.context.DynamicPropertyRegistry;
import org.springframework.test.context.DynamicPropertySource;
import org.testcontainers.junit.jupiter.Container;
import org.testcontainers.junit.jupiter.Testcontainers;
import org.testcontainers.oracle.OracleContainer;

import java.time.Duration;

import static org.assertj.core.api.Assertions.assertThat;
import static org.awaitility.Awaitility.await;

@SpringBootTest(classes = BookshelfApplication.class, properties = {
        "spring.quartz.job-store-type=jdbc",
        "spring.quartz.jdbc.initialize-schema=always",
        "spring.quartz.jdbc.continue-on-error=false",
        "spring.quartz.jdbc.schema=classpath:db/quartz/tables_oracle23_nohead.sql",
        "spring.quartz.scheduler-name=bookshelf"
})
@Testcontainers
class BookshelfOracleTest {

    @Container
    static final OracleContainer ORACLE = new OracleContainer("gvenzl/oracle-free:slim-faststart")
            .withUsername("quartz")
            .withPassword("quartz-test-only");

    @DynamicPropertySource
    static void datasource(DynamicPropertyRegistry registry) {
        registry.add("spring.datasource.url", ORACLE::getJdbcUrl);
        registry.add("spring.datasource.username", ORACLE::getUsername);
        registry.add("spring.datasource.password", ORACLE::getPassword);
    }

    @Autowired Scheduler scheduler;
    @Autowired JdbcTemplate jdbc;

    @Test
    void storesTheBookshelfJobsInOracleAndFiresThem() throws Exception {
        assertThat(scheduler.getMetaData().isJobStoreSupportsPersistence()).isTrue();
        assertThat(scheduler.getMetaData().getJobStoreClass().getSimpleName()).isEqualTo("LocalDataSourceJobStore");

        // the schema script created the 11 QRTZ_ tables in the QUARTZ schema
        assertThat(jdbc.queryForObject(
                "SELECT COUNT(*) FROM user_tables WHERE table_name LIKE 'QRTZ\\_%' ESCAPE '\\'", Integer.class)).isEqualTo(11);

        // the Bookshelf triggers are rows, not memory
        assertThat(jdbc.queryForObject("SELECT COUNT(*) FROM qrtz_triggers", Integer.class)).isEqualTo(4);

        // the cache refresh fired at least once and its previous fire time was persisted
        await().atMost(Duration.ofSeconds(30)).untilAsserted(() ->
                assertThat(jdbc.queryForObject(
                        "SELECT prev_fire_time FROM qrtz_triggers WHERE trigger_name = 'cacheRefreshTrigger'", Long.class))
                        .isGreaterThan(0L));

        // flags are real booleans in the 23ai script
        assertThat(jdbc.queryForObject(
                "SELECT COUNT(*) FROM qrtz_job_details WHERE is_durable = TRUE", Integer.class)).isEqualTo(4);
    }
}

|Pitfall |What to do

|Running the default Boot configuration against Oracle with a 23.x driver
|Boot's default script for Oracle is `tables_oracle.sql`, and with `ojdbc11` 23.26.3.0.0 (and 23.7.0.25.01) the first stored job fails with `ORA-12899` on `IS_DURABLE` (actual 4, maximum 1). On a 23ai server use `tables_oracle23.sql` through `spring.quartz.jdbc.schema` or `platform: oracle23`; on an older server pin the driver to 21.x or bind the flags as text (see <<scripts>>).

|Expecting `OracleDelegate` to fix the flag-column error
|It calls the same `setBoolean` as the standard delegate and fails identically with the old script and a 23.x driver (measured). The delegate only changes how the `BLOB` columns are written.

|Misspelling the delegate
|The class is `org.quartz.impl.jdbcjobstore.oracle.OracleDelegate`. There is no `org.quartz.impl.jdbcjobstore.OracleDelegate`, and the `WebLogicOracleDelegate` that the configuration page lists in the `oracle` package is in `oracle.weblogic`.

|The `ORA-00942` from the script's `delete from` and `drop table` lines
|Silent while `continue-on-error` is `true`; fatal with `false`, with Flyway and with Liquibase. Delete those lines for every migration (the `sed` command above).

|`initialize-schema: always` on a real database
|The script deletes and drops the tables first, so every restart wipes jobs, triggers and counters (a `JobDataMap` counter went from 4 back to 1 in the Oracle run). Use it for tests only.

|Reading the `ORA-12899` as a Quartz bug and downgrading Quartz
|The cause is the driver's `setBoolean` against `VARCHAR2(1)`; Quartz 2.3.2 and 2.4.1 ship only the old script. Change the script (or the driver), not the Quartz version.

|`BOOLEAN` columns on an older server
|`tables_oracle23.sql` needs the BOOLEAN column type of 23ai. A 19c or 21c server needs `tables_oracle.sql` with a driver or delegate that stores `1` and `0`; that combination was run only against a 23ai server.

|Connecting with the wrong service name
|Use the service of the pluggable database in the form `@//host:port/service` (`FREEPDB1` for the Free image). The Testcontainers `getJdbcUrl()` already returns a URL with that service (`jdbc:oracle:thin:@localhost:<port>/freepdb1` was measured). A SID-style URL (`host:port:SID`) was not run.

|Giving the application the powerful user of a test container
|`withUsername` creates a user whose session holds 29 system privileges (directly or through the roles `RESOURCE`, `DB_DEVELOPER_ROLE` and `SODA_APP`). The Quartz schema owner ran with `CREATE SESSION` and `CREATE TABLE` plus a quota.

|Leaving `SELECT ... FOR UPDATE` open on `QRTZ_LOCKS` in a SQL client
|The row lock blocks every node's `triggersFired` until the session ends (measured: a second `FOR UPDATE` stayed blocked). Inspect with plain `SELECT`.

|Enabling `txIsolationLevelSerializable` to be safe
|Oracle's serializable mode raises an error on concurrent changes instead of waiting (Oracle documentation, not measured here). The default `READ COMMITTED` plus the row locks is what Quartz expects.

|Comparing descriptions with `""`
|Oracle stores the empty string as `NULL` (measured: a job described with `""` reads back `null`). Treat `null` and empty as the same.

|Writing directly to the `QRTZ_` tables from SQL clients
|Quartz keeps cross-table invariants (trigger state, fired triggers, lock rows) that a manual `UPDATE` breaks; use the `Scheduler` API, and see the production page for the rule.

|`OracleDelegate` behind a pool or proxy that wraps `Blob`
|`writeDataToBlob` accepts only `oracle.sql.BLOB` and throws "Driver's Blob representation is of an unsupported type" otherwise (read from the source; not provoked here). The default delegate has no such cast.

|Assuming the Free image tells you its version
|The image has no version label; query `v$version` (`Oracle AI Database 26ai Free Release 23.26.3.0.0` for the image used here) and pin the tag in your tests.
|===

=== What changed

* Quartz 2.5.2's jar adds `tables_oracle23.sql` (BOOLEAN flags, Oracle 23ai). The jars of Quartz 2.3.2 and 2.4.1 contain only `tables_oracle.sql`; `OracleDelegate` and `WebLogicOracleDelegate` are in all three. The jar grows from 22 DDL scripts to 25 overall, as listed on the xref:backend/scheduling/job-stores-and-persistence.adoc[job stores page].
* Spring Boot 4.1.1 manages `ojdbc11` 23.26.3.0.0; Boot 3.5.16 manages 23.7.0.25.01. Under Boot 4.1.1 both versions fail on `tables_oracle.sql` (measured by overriding `oracle-database.version`); the Boot 3.5.16 build itself was not run. The Boot 3.5 property names, including `spring.quartz.jdbc.*`, are unchanged in Boot 4; the types moved to `org.springframework.boot.quartz.autoconfigure`.
* Boot still maps Oracle to the unchanged platform id `oracle`, so the default script is the old one; it does not select the 23 script by itself.
* Testcontainers 2.x moved the Oracle module to `testcontainers-oracle-free` and `org.testcontainers.oracle.OracleContainer`.
* The Quartz configuration page still lists a `WebLogicOracleDelegate` in the `oracle` package, which the 2.5.2 jar does not contain; the class is in `oracle.weblogic`. This is collected with the other documentation discrepancies on xref:backend/scheduling/migration-and-whats-changed.adoc[Migration & What's Changed].
