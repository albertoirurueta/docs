SQL Server is one of the databases that Quartz supports through its official JDBC job store, so a Spring Boot service that already runs on SQL Server
(or on Azure SQL) can keep its triggers, job definitions and cluster state in the same engine as its business data. Of the databases covered in this
section it is the one whose DDL script needs the most attention: the script that ships in the Quartz jar is written for a client tool such as `sqlcmd`, not
for a JDBC driver, and a Quartz scheduler that uses the default delegate fails at startup because of the way it locks rows. This page walks through
the setup in the order in which a reader hits the problems, and every statement about what works or fails was produced by running it.
The generic concepts (what the `QRTZ_` tables are, `initialize-schema`, `@QuartzDataSource`, pool sizing) are on
xref:backend/scheduling/job-stores-and-persistence.adoc[Job Stores & Persistence]; the reference database page is
xref:backend/scheduling/database-postgresql.adoc[Quartz on PostgreSQL], and clustering in general is on
xref:backend/scheduling/clustering.adoc[Clustering].

It was written against Quartz 2.5.2, Spring Boot 4.1.1, Spring Framework 7.0.9 and Java 21 and verified on 5 October 2026 with the Microsoft JDBC driver
`mssql-jdbc` 13.4.0.jre11 (the version Spring Boot 4.1.1 manages), Flyway 12.4.0, Liquibase 5.0.3, Testcontainers 2.0.5 and the Docker image
`mcr.microsoft.com/mssql/server:2022-latest`, which reported SQL Server 2022 (RTM-CU27) 16.0.4295.3, Developer edition, on Linux, with the server collation
`SQL_Latin1_General_CP1_CI_AS`. That image is published for amd64 only; the tests ran on an Apple Silicon (arm64) machine, where Docker Desktop runs it
under Rosetta emulation, and every result below comes from that emulated server. Azure SQL Database was not available and was not tested: everything on this page
about Azure is taken from Microsoft's documentation and is labelled that way. Spring Boot 3.5.16 manages the same Quartz 2.5.2, so everything about Quartz is identical there;
only the package of `@QuartzDataSource` and `SchedulerFactoryBeanCustomizer` differs (`org.springframework.boot.autoconfigure.quartz` instead of
`org.springframework.boot.quartz.autoconfigure`), Spring Framework is 6.2.19 and the Boot-managed `mssql-jdbc`, Flyway and Liquibase versions are older.

== Status and dependencies

Status: official. The JDBC job store, the `MSSQLDelegate` and the DDL script are part of Quartz itself and are maintained with it. Nothing about the job store is community
code, unlike the MongoDB and Redis stores.

== The delegate: MSSQLDelegate

A *driver delegate* is the class that issues the SQL for one database. The default, `StdJDBCDelegate`, uses plain JDBC and works on several databases (MySQL and MariaDB
among them); engines with a different dialect or a different way of handling binary columns need their own subclass. `org.quartz.impl.jdbcjobstore.MSSQLDelegate` is the one for SQL Server.
Reading its 2.5.2 source, it extends `StdJDBCDelegate` and overrides exactly three methods:

.What MSSQLDelegate overrides in Quartz 2.5.2
[cols="3,6",options="header"]
|===
|Method |Why

|`getObjectFromBlob(ResultSet, String)`
|Reads a serialised object from a `VARBINARY(max)` column with `getBinaryStream` instead of `java.sql.Blob`, and returns `null` for an empty stream.

|`getJobDataFromBlob(ResultSet, String)`
|The same for `JOB_DATA`; when `useProperties` is on it hands back the raw stream so that the `JobDataMap` can be read as properties.

|`selectTriggerToAcquire(Connection, long, long, int)`
|Rewrites the "next trigger to acquire" query as `SELECT TOP n ...` because T-SQL has no `LIMIT` clause, and sets `maxRows` and `fetchSize` to `n`.
|===

Source: https://github.com/quartz-scheduler/quartz/blob/v2.5.2/quartz/src/main/java/org/quartz/impl/jdbcjobstore/MSSQLDelegate.java[MSSQLDelegate.java (v2.5.2)] and
https://www.quartz-scheduler.org/api/2.5.x/org/quartz/impl/jdbcjobstore/MSSQLDelegate.html[MSSQLDelegate Javadoc].

The delegate does not change the lock statement. That belongs to the job store: `JobStoreSupport.initialize` looks at the configured `driverDelegateClass`, and if its name contains
the text `MSSQLDelegate` and `selectWithLockSQL` is not set, it installs an SQL Server specific one (see <<locking>>). The consequence is that the delegate is *mandatory*, not an
optimisation. Spring Boot does not set a delegate (the property is not part of `spring.quartz.*`), so the effective delegate is `StdJDBCDelegate` unless you name another one in
`spring.quartz.properties`. The measured behaviour on SQL Server 2022 with the schema in place:

.Delegate choice on SQL Server, measured with the edited script of the next section
[cols="3,3,6",options="header"]
|===
|Delegate |Result |Evidence

|none set (Boot's default, `StdJDBCDelegate`)
|*fails at startup*
|`SQLServerException: Line 1: FOR UPDATE clause allowed only for DECLARE CURSOR.`, reported by Quartz as `Failure obtaining db row lock`; the scheduler bean is never created

|`org.quartz.impl.jdbcjobstore.MSSQLDelegate`
|works
|the Bookshelf jobs fire, a dynamically scheduled job with a serialised `JobDataMap` fires, and after a restart the stored jobs are found
|===

The failure message is worth recognising, because it does not mention Quartz, a delegate or SQL Server's locking: it comes from the default lock statement, `SELECT * FROM QRTZ_LOCKS WHERE ... FOR UPDATE`,
which is valid on PostgreSQL, MySQL and Oracle but not in T-SQL, where `FOR UPDATE` exists only for cursors.

== The DDL script and the edits it needs

Quartz ships `org/quartz/impl/jdbcjobstore/tables_sqlServer.sql` in the `quartz-2.5.2.jar`. Reading it from the jar gives this anatomy:

.Anatomy of tables_sqlServer.sql in the Quartz 2.5.2 jar
[cols="3,6",options="header"]
|===
|Part |What it is

|Comment header
|Lines starting with `--#`: it tells you to set the `MSSQLDelegate`, to replace the database name on the first line, and quotes an old tip about `SelectMethod=cursor` and the jTDS driver for a Microsoft driver of the SQL Server 2000 era.
 Neither tip is needed with `mssql-jdbc` 13.

|`USE [enter_db_name_here]`
|A placeholder: the database the script is meant to run in. It fails if executed as is (below).

|47 lines containing only `GO`
|The batch separator of `sqlcmd`, SSMS and similar tools. `GO` is not a Transact-SQL statement and SQL Server itself does not understand it.

|`IF EXISTS (...) ALTER TABLE ... DROP CONSTRAINT` and `IF EXISTS (...) DROP TABLE`
|The script drops every foreign key and every `QRTZ_` table before creating them. It is a bootstrap script, not a migration.

|`CREATE TABLE [dbo].[QRTZ_...]` (11 tables)
|`NVARCHAR` for every name and flag column (`SCHED_NAME` 120, `TRIGGER_NAME` and `TRIGGER_GROUP` 200, `JOB_CLASS_NAME` 250, flags `NVARCHAR(1)`), `BIGINT` for times, `VARBINARY (max)` for `JOB_DATA`, `CALENDAR` and `BLOB_DATA`. The schema `[dbo]` is hard-coded.

|Primary keys, foreign keys, indexes
|Clustered primary keys on each table, `ON DELETE CASCADE` foreign keys from the trigger sub-tables to `QRTZ_TRIGGERS`, and non-clustered indexes on the four child tables. It has no `INSERT` statements: the two `QRTZ_LOCKS` rows are inserted by Quartz on first use.
|===

Source: https://github.com/quartz-scheduler/quartz/blob/v2.5.2/quartz/src/main/resources/org/quartz/impl/jdbcjobstore/tables_sqlServer.sql[tables_sqlServer.sql (v2.5.2)] and
the Spring Boot reference, which says that "the SQL Server, Azure SQL and Sybase scripts may need editing" without saying how (https://docs.spring.io/spring-boot/reference/io/quartz.html[Spring Boot: Quartz Scheduler]).

=== The two edits

.Three ways to load the script, and what each needs
image::scheduling-sqlserver-schema-routes.svg["Three routes from tables_sqlServer.sql in the Quartz 2.5.2 jar to a SQL Server database. The script has a USE line with a placeholder database name, 47 GO batch separators, drop guards and 11 CREATE TABLE statements. Route 1, Flyway for production: delete the USE line, keep every GO, measured to work because Flyway splits on GO itself. Route 2, Liquibase for production: delete the USE line and use sqlFile with the GO lines kept, or the bundled liquibase.quartz.init.xml, which creates VARCHAR and BIT columns; both measured to work. Route 3, Boot's initializer for development and tests only: sed deletes the USE line and turns GO into semicolons; it works but the script drops the tables on every start. All three end in the same 11 QRTZ tables, and the database is chosen by the JDBC URL. On every route the driverDelegateClass must be MSSQLDelegate, otherwise the lock statement ends in FOR UPDATE and SQL Server rejects it",width=950,role=text-center]

Two lines of the script are a problem for anything that is not a SQL client: the `USE` line and the `GO` lines. What each one does depends on who runs the script, and these are the measured results on the SQL Server 2022 container.
Every row used a fresh database, `MSSQLDelegate` and `spring.quartz.jdbc.initialize-schema=always` where Boot ran the script.

.Running tables_sqlServer.sql through different tools, measured
[cols="4,2,6",options="header"]
|===
|Who runs it, and how |Result |What happened

|Boot's initializer, the script untouched, `continue-on-error=false`
|fails
|`Failed to execute SQL script statement #1`, caused by `Database 'enter_db_name_here' does not exist`

|Boot's initializer, the script untouched, `continue-on-error` left at its default (`true`)
|fails later, and misleadingly
|Boot silently skips the failing statements, so *no table is created*. The scheduler bean then fails with `Invalid object name 'QRTZ_JOB_DETAILS'` -- the real cause is far away in the log

|Boot's initializer, only the `USE` line removed, `GO` kept
|fails
|`Could not find stored procedure 'GO'`: Spring's script runner sends `GO` to the server

|Flyway 12.4.0, the script untouched
|fails
|`Database 'enter_db_name_here' does not exist` (Flyway reports the script, line 27 and SQL State S0001)

|Flyway 12.4.0, the `USE` line removed, `GO` kept
|*works*
|Flyway understands `GO` for SQL Server by itself; `flyway_schema_history` shows version 1 as successful and the 11 `QRTZ_` tables exist

|Liquibase 5.0.3 `sqlFile`, the `USE` line removed, `GO` kept, default attributes
|*works*
|13 tables: the 11 `QRTZ_` tables plus Liquibase's own `DATABASECHANGELOG` and `DATABASECHANGELOGLOCK`

|Liquibase 5.0.3 `sqlFile` with `splitStatements="true" endDelimiter="\nGO"`
|*works*
|the same 13 tables

|Liquibase 5.0.3 `sqlFile`, `GO` replaced by `;`
|*works*
|the same 13 tables

|Boot's initializer, the `USE` line removed and every `GO` line replaced by `;`
|*works*
|see the `sed` command below
|===

Two conclusions follow. The `USE` line must always go, because the database is selected by the connection (see <<jdbc-url>> and, for Azure SQL, <<azure>>), not by the script. And
the `GO` lines are a problem only for tools that do not know them: Flyway and Liquibase each cope on their own, while Spring Boot's own script runner needs them converted. The reason for
that last point is a property of the file: it contains no semicolons outside comments, so Spring's `ScriptUtils`, which splits on `;` and falls back to newlines when it finds none, would cut each multi-line `CREATE TABLE`
into fragments, and a `GO` line would still be sent as if it were a statement.

.The tested edit for Boot's initializer (development and tests)
[source,bash]
----
# extract the script from the jar, delete the USE line and turn every GO line into a semicolon
unzip -p quartz-2.5.2.jar org/quartz/impl/jdbcjobstore/tables_sqlServer.sql \
  | sed -e '/^USE \[/d' -e 's/^GO$/;/' > src/main/resources/quartz/tables_sqlServer_boot.sql
----

Source: https://docs.spring.io/spring-boot/reference/io/quartz.html[Spring Boot: Quartz Scheduler]. The command reproduces, byte for byte, the file used in the tests (checked with `diff`).

.application-dev.yml: Boot creates the tables from the edited script (development and tests only)
[source,yaml]
----
spring:
  quartz:
    job-store-type: jdbc
    jdbc:
      initialize-schema: always          # the script DROPS the tables first: never in production
      continue-on-error: false           # surface script errors instead of hiding them
      schema: classpath:quartz/tables_sqlServer_boot.sql
    properties:
      org.quartz.jobStore.driverDelegateClass: org.quartz.impl.jdbcjobstore.MSSQLDelegate
----

Source: https://docs.spring.io/spring-boot/reference/io/quartz.html[Spring Boot: Quartz Scheduler]. Property names and defaults were read from `QuartzProperties` and the initializer in the 4.1.1 sources.

The script's first block drops all `QRTZ_` tables, so with `initialize-schema=always` every restart deletes every stored job and trigger (the same pitfall as on every database,
measured on PostgreSQL and described on xref:backend/scheduling/job-stores-and-persistence.adoc[Job Stores & Persistence]). Setting `continue-on-error: false` is the
sensible choice when Boot runs this script, because the default of `true` produced the misleading failure in the table above. (On Spring Boot 3.5.16 the property does not exist and the initializer hard-codes `true`, so run the script with Flyway or Liquibase there.)

=== NVARCHAR in 2.5.2, and the fix that is not released

The columns are `NVARCHAR` in the Quartz 2.5.2 jar: reading `tables_sqlServer.sql` from the released jar shows `[NVARCHAR]` for every name and flag column. That change is commit `b9e92c33` of 29 November 2025
("Change SQL Server DDL to use NVARCHAR instead of VARCHAR for perf reasons, see #1422"), and it is included in 2.5.2. Some summaries describe it as a coming 2.5.3 change; that is not accurate, and no 2.5.3 release exists as of this writing
(the latest release is 2.5.2).

What is *not* released yet is a separate fix in the delegate. Pull request #1515, "Bind MSSQL scheduler-state instance name as NVARCHAR", was merged into the Quartz `main` branch on 28 September 2026. It overrides
`MSSQLDelegate.updateSchedulerState` so that the instance name is bound with `PreparedStatement.setNString`, and it fixes issue #1514, in which a user reported frequent deadlocks on `QRTZ_SCHEDULER_STATE` in a cluster:
the cluster check-in update binds `INSTANCE_NAME` with `setString`, which the reporter says SQL Server then treats as `VARCHAR`, so the clustered primary key on the `NVARCHAR(200)` column cannot be used. The override is for SQL Server only.

What was and was not verified here, stated precisely:

* The 2.5.2 jar contains the `NVARCHAR` DDL and an `MSSQLDelegate` without the `updateSchedulerState` override (read from the sources).
* The 2.5.2 behaviour in a short cluster test is described in <<clustering>>: no deadlock was observed. The deadlock in #1514 is *reported, not reproduced* here.
* The `mssql-jdbc` documentation says that the driver sends `String` parameters as Unicode by default (`sendStringParametersAsUnicode=true`), which would make the reported mismatch depend on the connection settings.
  That is documentation-derived; the report does not say which settings the reporter used, and this page does not claim to know.
* Until a release that contains #1515 exists, a deployment that sees check-in deadlocks has two options: check the driver settings, and move to the release when it is published. Do not copy the fix into a custom delegate unless you can test it under load.

Source: https://github.com/quartz-scheduler/quartz/pull/1515[Quartz pull request #1515], https://github.com/quartz-scheduler/quartz/issues/1514[Quartz issue #1514],
https://github.com/quartz-scheduler/quartz/commit/b9e92c33[commit b9e92c33] and https://learn.microsoft.com/en-us/sql/connect/jdbc/setting-the-connection-properties[Microsoft: Setting the connection properties]. The state of the pull request was read from the GitHub API on 5 October 2026.

== Flyway: the production route

In production the schema should be created by a migration tool, run once and recorded, not by the application's initializer. With Flyway the edit is one line: delete the `USE` line, keep everything else, and name the file by Flyway's convention.

.src/main/resources/db/migration/V1__quartz_tables.sql: produced by one command
[source,bash]
----
unzip -p quartz-2.5.2.jar org/quartz/impl/jdbcjobstore/tables_sqlServer.sql \
  | sed -e '/^USE \[/d' > src/main/resources/db/migration/V1__quartz_tables.sql
----

Source: https://docs.spring.io/spring-boot/how-to/data-initialization.html[Spring Boot: Database Initialization]. The result was run through Flyway 12.4.0 on SQL Server 2022 and created the 11 tables.

.application.yml: Flyway creates the tables, Quartz only uses them
[source,yaml]
----
spring:
  datasource:
    url: jdbc:sqlserver://${DB_HOST}:1433;databaseName=bookshelf;encrypt=true
    username: ${DB_USER}
    password: ${DB_PASSWORD}
  flyway:
    enabled: true
    locations: classpath:db/migration
  quartz:
    job-store-type: jdbc
    jdbc:
      initialize-schema: never           # Flyway owns the schema
    properties:
      org.quartz.jobStore.driverDelegateClass: org.quartz.impl.jdbcjobstore.MSSQLDelegate
----

Source: https://docs.spring.io/spring-boot/reference/io/quartz.html[Spring Boot: Quartz Scheduler]. The keys were run with these values, with the container's URL and credentials in place of the placeholders.

Boot orders the scheduler after the database initializers, so on startup Flyway runs before Quartz reads its tables; that was visible in the tests, where Quartz started on a database that Flyway had just migrated.
Three remarks on the migration itself:

* The script still contains the `DROP TABLE` guards. They are harmless in a migration that runs once on an empty database, and Flyway never re-runs a versioned migration. If you prefer, delete the guard block; it is plain `IF EXISTS` statements before the first `CREATE TABLE`.
* Do not edit the migration after it was applied. A later change to the Quartz tables, for example when upgrading Quartz, is a new `V2__` migration.
* A Flyway run needs the right to create tables, a Quartz run does not (see <<dedicated>>).

== Liquibase: the other production route

Liquibase handles the same script through `sqlFile`. All three variants in the measured table worked; the shortest one keeps the `GO` lines and sets no attribute at all.

.src/main/resources/db/changelog/db.changelog-master.xml: the Quartz tables as a Liquibase changeset
[source,xml]
----
<?xml version="1.0" encoding="UTF-8"?>
<databaseChangeLog xmlns="http://www.liquibase.org/xml/ns/dbchangelog"
                   xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
                   xsi:schemaLocation="http://www.liquibase.org/xml/ns/dbchangelog https://www.liquibase.org/xml/ns/dbchangelog/dbchangelog-latest.xsd">
  <changeSet id="quartz-tables" author="bookshelf">
    <sqlFile path="quartz/tables_sqlServer.sql" relativeToChangelogFile="true"
             splitStatements="true" endDelimiter="\nGO"/>
  </changeSet>
</databaseChangeLog>
----

Source: https://docs.liquibase.com/concepts/changelogs/sql-format.html[Liquibase: SQL changelogs] and https://docs.spring.io/spring-boot/how-to/data-initialization.html[Spring Boot: Database Initialization]. The `quartz/tables_sqlServer.sql` file is the jar script with the `USE` line removed.
This exact changelog, with the file next to it, created the 11 tables on SQL Server 2022 under Liquibase 5.0.3 and the application then ran the Bookshelf jobs.

Liquibase's documentation says that statements are split on `;` or on a `go` at the end of a line by default, and the measurement agrees: the variant without `splitStatements` and `endDelimiter`, and the variant with the `GO` lines replaced by semicolons, both worked too.
`splitStatements="true"` with `endDelimiter="\nGO"` is shown above because it states the intent, and it behaves the same. Setting `spring.liquibase.change-log` is only needed when the changelog is not at Boot's default `classpath:/db/changelog/db.changelog-master.yaml`; with the XML name above, set it to `classpath:db/changelog/db.changelog-master.xml`.
The general Liquibase workflow is on xref:database/schema-evolution/liquibase-getting-started.adoc[Liquibase: Getting Started], and the choice between the tools is on xref:database/schema-evolution/choosing-a-migration-tool.adoc[Choosing a Migration Tool].

=== The bundled liquibase.quartz.init.xml

The Quartz 2.5.2 jar also contains `org/quartz/impl/jdbcjobstore/liquibase.quartz.init.xml`, a database-neutral Liquibase changelog (a single changeset, `quartz-init`, that creates the same 11 tables and uses a `blob_type` property that is `BYTEA` on PostgreSQL and `BLOB` elsewhere).
It can be included from a master changelog with `<include file="org/quartz/impl/jdbcjobstore/liquibase.quartz.init.xml"/>`, and it was run on SQL Server 2022 with `MSSQLDelegate`: it works, the Bookshelf jobs fired and the stored state survived a restart. It produces a different schema from the T-SQL script, though.
Querying the catalogue afterwards showed `VARCHAR(200)` for `INSTANCE_NAME` (not `NVARCHAR`), `BIT` for `IS_DURABLE` and `VARBINARY(max)` for `JOB_DATA`. It also has no `[dbo]` hard-coding. Choose it when you want one changelog for every database in the fleet, and the T-SQL script when you want the schema that Quartz's SQL Server maintainers
describe and test; do not mix them in one environment.

Source: https://github.com/quartz-scheduler/quartz/blob/v2.5.2/quartz/src/main/resources/org/quartz/impl/jdbcjobstore/liquibase.quartz.init.xml[liquibase.quartz.init.xml (v2.5.2)]. The column types are from `INFORMATION_SCHEMA.COLUMNS` of a database created by this file.

== A dedicated database, schema and users

Like the PostgreSQL page, this one recommends that Quartz's tables are kept apart from the business tables and that the runtime user can do less than the migration user. On SQL Server there are two levels of separation: a database of its own (selected by `databaseName` in the URL, no script change) or a schema of its own in the application's database.
The second needs one more edit, because the script hard-codes `[dbo]`.

.Setup run once by an administrator: a schema and two users
[source,sql]
----
-- run in the application's database
CREATE LOGIN quartz_migrator WITH PASSWORD = '<migrator-password>';
CREATE LOGIN quartz_app      WITH PASSWORD = '<runtime-password>';

CREATE USER quartz_migrator FOR LOGIN quartz_migrator;
ALTER ROLE db_owner ADD MEMBER quartz_migrator;       -- creates tables, schema and grants

CREATE USER quartz_app FOR LOGIN quartz_app WITH DEFAULT_SCHEMA = quartz;
----

Source: https://learn.microsoft.com/en-us/sql/t-sql/statements/create-user-transact-sql[Microsoft: CREATE USER]. The passwords in the test were random values generated per run; use secrets from your vault.

.The migrations: V1 creates the schema, V2 is the script with [dbo] replaced, V3 grants DML only
[source,bash]
----
printf 'CREATE SCHEMA [quartz]\nGO\n' > V1__quartz_schema.sql
unzip -p quartz-2.5.2.jar org/quartz/impl/jdbcjobstore/tables_sqlServer.sql \
  | sed -e '/^USE \[/d' -e 's/\[dbo\]/[quartz]/g' > V2__quartz_tables.sql
printf 'GRANT SELECT, INSERT, UPDATE, DELETE ON SCHEMA::[quartz] TO [quartz_app]\nGO\n' > V3__grant_runtime_user.sql
----

Source: https://learn.microsoft.com/en-us/sql/t-sql/statements/grant-schema-permissions-transact-sql[Microsoft: GRANT Schema Permissions]. The three files ran under Flyway 12.4.0; the replacement touches only the bracketed `[dbo]`, so the `dbo.sysobjects` catalogue view in the drop guards stays as it is.

.application.yml: Flyway runs as the migration user, Quartz as the runtime user, and the table prefix names the schema
[source,yaml]
----
spring:
  datasource:

`tablePrefix` is the property that carries the schema: Quartz substitutes it into every statement, so `quartz.QRTZ_` produces `quartz.QRTZ_JOB_DETAILS` and so on, and with the user's `DEFAULT_SCHEMA` set to `quartz` as well, the unqualified names used by monitoring queries resolve too.
The runtime user needs no DDL rights. It does need `INSERT` as well as `SELECT`, `UPDATE` and `DELETE`, because the `QRTZ_LOCKS` rows are inserted by Quartz itself on first use.

[#locking]
== Locking: selectWithLockSQL, UPDLOCK and ROWLOCK

Quartz uses a lock table, `QRTZ_LOCKS`, with two rows per scheduler name (`TRIGGER_ACCESS` and `STATE_ACCESS`), and takes a lock by selecting one of them with a row lock inside a transaction. The statement is `selectWithLockSQL`, and the code default in `StdRowLockSemaphore` is
`SELECT * FROM \{0}LOCKS WHERE SCHED_NAME = \{1} AND LOCK_NAME = ? FOR UPDATE`, in which `\{0}` is the table prefix and `\{1}` the scheduler name. SQL Server rejects `FOR UPDATE`, which is the failure of the delegate table above. Instead, `JobStoreSupport.initialize` contains this block (at line 671 of the 2.5.2 source):

.JobStoreSupport.initialize in Quartz 2.5.2: the SQL Server default
[source,java]
----
if (getDriverDelegateClass() != null && getDriverDelegateClass().contains(MSSQLDelegate.class.getSimpleName())) {
    if (getSelectWithLockSQL() == null) {
        String msSqlDflt = "SELECT * FROM {0}LOCKS WITH (UPDLOCK,ROWLOCK) WHERE " + COL_SCHEDULER_NAME + " = {1} AND LOCK_NAME = ?";
        getLog().info("Detected usage of MSSQLDelegate class - defaulting 'selectWithLockSQL' to '{}'.", msSqlDflt);
        setSelectWithLockSQL(msSqlDflt);
    }
}
----

Source: https://github.com/quartz-scheduler/quartz/blob/v2.5.2/quartz/src/main/java/org/quartz/impl/jdbcjobstore/JobStoreSupport.java[JobStoreSupport.java (v2.5.2)]. The code is quoted from the 2.5.2 sources.

The block runs only when the job store uses database locks, which Spring Boot's `LocalDataSourceJobStore` (a `JobStoreCMT` subclass) always does, and it also runs when the scheduler is not clustered. The INFO message is logged by the job store class, so its logger is `org.springframework.scheduling.quartz.LocalDataSourceJobStore`, not a `org.quartz` logger. Setting
`logging.level.org.springframework.scheduling.quartz=INFO` produced exactly this line in the test log:

[source,text]
----
Detected usage of MSSQLDelegate class - defaulting 'selectWithLockSQL' to 'SELECT * FROM {0}LOCKS WITH (UPDLOCK,ROWLOCK) WHERE SCHED_NAME = {1} AND LOCK_NAME = ?'.
Using db table-based data access locking (synchronization).
----

Source: https://www.quartz-scheduler.org/documentation/quartz-2.5.x/configuration/ConfigJDBCJobStoreClustering.html[Quartz: Configure Clustering with JDBC-JobStore]. The two lines are copied from the log of the test run.

The hints do what their names say: `UPDLOCK` takes an update lock that other `UPDLOCK` readers wait for (and keeps it until the end of the transaction), and `ROWLOCK` asks for a row-level lock rather than a page or table lock, so that the two lock rows do not block each other at a coarser level.
Because the default is installed only when `selectWithLockSQL` is null, a property of your own wins. The hints were observed with two plain JDBC connections against the real server:

.Two connections and the lock row, measured on SQL Server 2022
[cols="5,5",options="header"]
|===
|Step |Result

|Connection A runs the Quartz default `... FOR UPDATE` statement
|`FOR UPDATE clause allowed only for DECLARE CURSOR.`

|Connection A runs the `WITH (UPDLOCK,ROWLOCK)` statement in a transaction and reads the row
|`sys.dm_tran_locks` shows a `U` lock on a `KEY` resource, an `IU` lock on the `PAGE` and an `IX` lock on the `OBJECT`: a key-level (row) update lock under the intent locks that SQL Server always takes

|Connection B runs the same statement and reads the row (lock timeout 1000 ms)
|`Lock request time out period exceeded.` after 1014 ms: B waits for A

|A commits, B runs the statement again
|B gets the row
|===

Source: https://learn.microsoft.com/en-us/sql/t-sql/queries/hints-transact-sql-table[Microsoft: Table hints (Transact-SQL)]. The test read the first row of each result, because the driver returns from `executeQuery` before the row lock is requested.
It is worth knowing when writing such a probe yourself: a statement that is blocked on the lock reports it when the result is read, not when it is sent.

By default, trigger acquisition takes no row lock: `JobStoreSupport.acquireNextTriggers` claims each trigger with a conditional `UPDATE` from `WAITING` to `ACQUIRED`, and a node whose `UPDATE` affects 0 rows simply moves on.
The `WITH (UPDLOCK,ROWLOCK)` statement on the `TRIGGER_ACCESS` row is taken afterwards, in `triggersFired` and `triggeredJobComplete`, and that is where a second node waits.
Acquisition runs inside the same lock only when `org.quartz.jobStore.acquireTriggersWithinLock=true` or `org.quartz.scheduler.batchTriggerAcquisitionMaxCount` is greater than 1.

=== Isolation level and READ_COMMITTED_SNAPSHOT

Quartz does not change the isolation level unless asked. The job store has two switches, `org.quartz.jobStore.txIsolationLevelSerializable` (default false, in `JobStoreSupport`) and `txIsolationLevelReadCommitted` (default false, in `JobStoreCMT`), and with Spring's data source neither is set, so connections run at the driver's default.
On SQL Server that is `READ COMMITTED`: a new session on the test server reported level 2 (`READ COMMITTED`) and a plain JDBC connection reported `Connection.TRANSACTION_READ_COMMITTED`. The correctness of Quartz's locking does not depend on a higher level, because the lock row serialises the critical sections.
The `SERIALIZABLE` switch exists for engines where that is not true, and on SQL Server it only adds range locks and deadlock risk.

One database option does interact with it: `READ_COMMITTED_SNAPSHOT`. With it on, plain reads under `READ COMMITTED` use row versions instead of shared locks, while a statement with `UPDLOCK` still takes update locks. It is off by default on SQL Server and on by default in Azure SQL Database (Microsoft's documentation). A two-node cluster test on a database with
the option turned on (`is_read_committed_snapshot_on` was 1) ran for 10 seconds with no duplicate execution and both nodes firing jobs, the same result as with it off. Microsoft's guide also warns that `UPDLOCK` under `SNAPSHOT` isolation (not `READ_COMMITTED_SNAPSHOT`) can raise error 3960, an update conflict; Quartz does not use snapshot isolation, so avoid setting it as the default isolation of the Quartz connections.

Source: https://learn.microsoft.com/en-us/sql/relational-databases/sql-server-transaction-locking-and-row-versioning-guide[Microsoft: Transaction locking and row versioning guide] and https://github.com/quartz-scheduler/quartz/blob/v2.5.2/quartz/src/main/java/org/quartz/impl/jdbcjobstore/JobStoreSupport.java[JobStoreSupport.java (v2.5.2)].
For Spring-managed transactions and isolation levels in general, see xref:backend/springboot/transaction-isolation-and-locking.adoc[Transaction Isolation & Locking].

[#azure]
== Azure SQL Database

Azure SQL Database was not available for the tests, so this section is derived from Microsoft's documentation and from what the script and the delegate do; it is not a measurement.

* *No `USE`.* In Azure SQL Database the `USE` statement can name only the current database; any other database gives error 40508, and "to change databases, you must directly connect to the database" (Microsoft's `USE` page). The script's `USE [enter_db_name_here]` line must be deleted exactly as above, and the database is part of the connection (`databaseName=...`).
* *Same T-SQL, same delegate.* The script is plain T-SQL (`NVARCHAR`, `VARBINARY(max)`, `IF EXISTS` guards, `sysobjects`) and `MSSQLDelegate` is used unchanged; the Spring Boot reference lists Azure SQL together with SQL Server as needing the script edited, and the edits are the same.
* *`READ_COMMITTED_SNAPSHOT` is on by default*, so the two notes in the previous section apply from the first day: the update lock is still taken, and nothing needs to change.
* *Connections need `encrypt=true`* (the driver's default, see <<jdbc-url>>) and a certificate the JVM trusts; do not use `trustServerCertificate=true` against Azure.

Source: https://learn.microsoft.com/en-us/sql/t-sql/language-elements/use-transact-sql[Microsoft: USE (Transact-SQL)] and
https://learn.microsoft.com/en-us/azure/azure-sql/database/transact-sql-tsql-differences-sql-server[Microsoft: T-SQL differences between SQL Server and Azure SQL Database]. These statements were not run against Azure SQL.

[#jdbc-url]
== JDBC URL options

Version 10.2 of the Microsoft driver changed the default of `encrypt` to `true` (and since 11.2 the property is a string that also accepts `strict`), and `trustServerCertificate` defaults to `false`. A server with a valid certificate therefore needs no option at all. The Docker image generates a self-signed certificate,
so a container needs either `encrypt=false` or `trustServerCertificate=true`.

.JDBC URLs for production and for the test container
[source,properties]
----
# production: a server with a certificate the JVM trusts
spring.datasource.url=jdbc:sqlserver://${DB_HOST}:1433;databaseName=bookshelf;encrypt=true

# Testcontainers only: a self-signed certificate (this is what MSSQLServerContainer#getJdbcUrl() returns)
# jdbc:sqlserver://localhost:54430;encrypt=false
# alternatively: jdbc:sqlserver://localhost:54430;databaseName=bookshelf;encrypt=false;trustServerCertificate=true
----

Source: https://learn.microsoft.com/en-us/sql/connect/jdbc/setting-the-connection-properties[Microsoft: Setting the connection properties]. The container URL is the one Testcontainers 2.0.5 returned in the run; the port is random per run.

Do not copy `trustServerCertificate=true` or `encrypt=false` into a deployed configuration; they turn off the server authentication that TLS exists for. Two tips in the script's old header were not needed in any test: `SelectMethod=cursor` was advice for the SQL Server 2000 driver, and the jTDS driver it mentions is not the Microsoft driver used here.
`sendStringParametersAsUnicode` is `true` by default; the Microsoft documentation recommends `false` for `VARCHAR` columns, but Quartz's columns are `NVARCHAR`, so leave it alone unless you have measured a reason (it is also the one setting connected to #1514 above).

== A Testcontainers test for the Bookshelf jobs

The test starts SQL Server, lets Flyway create the tables from `V1__quartz_tables.sql` (the script with the `USE` line removed), starts the Bookshelf service with the JDBC job store and checks that the jobs were stored and that one of them fires.
The Bookshelf schedule is the one from xref:backend/scheduling/getting-started-with-spring-boot.adoc[Getting Started with Spring Boot], with a property that makes the cache refresh fire every second.

.BookshelfSqlServerIT.java: the Bookshelf jobs on a real SQL Server
[source,java]
----
package bookshelf;

import static org.assertj.core.api.Assertions.assertThat;
import static org.awaitility.Awaitility.await;

import java.time.Duration;

import org.junit.jupiter.api.Test;
import org.quartz.Scheduler;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.boot.testcontainers.service.connection.ServiceConnection;
import org.springframework.jdbc.core.JdbcTemplate;
import org.testcontainers.junit.jupiter.Container;
import org.testcontainers.junit.jupiter.Testcontainers;
import org.testcontainers.mssqlserver.MSSQLServerContainer;

@SpringBootTest(properties = {
        "bookshelf.fast=true",
        "spring.quartz.job-store-type=jdbc",
        "spring.quartz.jdbc.initialize-schema=never",
        "spring.quartz.scheduler-name=BookshelfScheduler",
        "spring.quartz.properties.org.quartz.scheduler.instanceId=AUTO",
        "spring.quartz.properties.org.quartz.jobStore.isClustered=true",
        "spring.quartz.properties.org.quartz.jobStore.driverDelegateClass=org.quartz.impl.jdbcjobstore.MSSQLDelegate"
})
@Testcontainers
class BookshelfSqlServerIT {

    @Container
    @ServiceConnection
    static final MSSQLServerContainer SQL_SERVER =
            new MSSQLServerContainer("mcr.microsoft.com/mssql/server:2022-latest").acceptLicense();

    @Autowired
    Scheduler scheduler;

    @Autowired
    JdbcTemplate jdbc;

    @Test
    void bookshelfJobsAreStoredInSqlServerAndFire() throws Exception {
        assertThat(scheduler.getMetaData().getJobStoreClass().getSimpleName()).isEqualTo("LocalDataSourceJobStore");
        assertThat(scheduler.getMetaData().isJobStoreSupportsPersistence()).isTrue();
        assertThat(scheduler.getMetaData().isJobStoreClustered()).isTrue();

        // Flyway created the tables, Boot's initializer did nothing, the Bookshelf beans were stored on startup
        assertThat(jdbc.queryForObject("SELECT COUNT(*) FROM QRTZ_JOB_DETAILS", Integer.class)).isEqualTo(4);
        assertThat(jdbc.queryForObject("SELECT COUNT(*) FROM QRTZ_TRIGGERS", Integer.class)).isEqualTo(4);

        // the one-second cache refresh fires and the store records it (PREV_FIRE_TIME is -1, not NULL, until the first fire)
        await().atMost(Duration.ofSeconds(30)).untilAsserted(() ->
                assertThat(jdbc.queryForObject(
                        "SELECT COUNT(*) FROM QRTZ_TRIGGERS WHERE TRIGGER_NAME = 'cacheRefreshTrigger' AND PREV_FIRE_TIME > 0",
                        Integer.class)).isEqualTo(1));

        // this node checked in to the cluster table
        assertThat(jdbc.queryForObject("SELECT COUNT(*) FROM QRTZ_SCHEDULER_STATE WHERE SCHED_NAME = 'BookshelfScheduler'",
                Integer.class)).isEqualTo(1);
    }
}
----

Source: https://java.testcontainers.org/modules/databases/mssqlserver/[Testcontainers: Microsoft SQL Server Module] and
https://docs.spring.io/spring-boot/reference/testing/testcontainers.html[Spring Boot: Testcontainers]. The test was run on 5 October 2026 and passed (1 test, 0 failures, about 50 seconds including the image start).

What the run established, stated plainly because the page is the only place it is written down:

* The container is `mcr.microsoft.com/mssql/server:2022-latest`, an amd64 image, run under Rosetta emulation on an arm64 Mac. It started in about eight seconds, the 47 batches of the migration ran, and the test passed. On an amd64 CI runner no emulation is involved; the image is amd64 only, so an arm64 host needs an emulation layer.
* `@ServiceConnection` works with the 2.x `MSSQLServerContainer`: it supplied the connection details of the container to the Boot data source, so no `@DynamicPropertySource` is needed.
* The container's default database is `master` and the user is `sa`; that is acceptable for a throw-away container, and the test therefore does not need a `databaseName`. A test for the dedicated-schema setup above creates a database and users first, with a plain JDBC connection to the container, and that variant was also run.
* The same Bookshelf scenario (the four stored jobs and triggers, a dynamically scheduled job whose `JobDataMap` holds a serialisable record, and a restart with `initialize-schema=never` in which the job's persisted counter kept growing) passed on SQL Server with each route in the table of edits that is marked as working.

== Business data and Quartz data on SQL Server

If the business data is also on SQL Server, the simplest layout is one Hikari data source, which Boot shares with Quartz: a single `DataSource` bean is picked up for the job store automatically. With a second data source you need `@QuartzDataSource` (and `@QuartzTransactionManager` when the Quartz data source has its own transaction manager),
exactly as on the xref:backend/scheduling/job-stores-and-persistence.adoc[Job Stores & Persistence] page, and the pitfall measured there applies here too: two data sources with no `@Primary` make Boot silently fall back to the RAM store, and `@QuartzDataSource` does not rescue that (mark the application's data source `@Primary` and Quartz's `@QuartzDataSource`). Entities and repositories are covered on
xref:backend/springboot/spring-data-jpa.adoc[Spring Data JPA]; the general SQL material of this site is under xref:database/sql/index.adoc[SQL].

Collation can matter on SQL Server, and it was tested: a database created with the case-sensitive collation `Latin1_General_100_CS_AS` ran the Bookshelf jobs and the restart check without any change, because Quartz addresses its tables and columns in upper case, as the script creates them.
The pitfall is on your side: monitoring queries and any code that writes `qrtz_triggers` in lower case would fail on such a database.

== Pitfalls

.SQL Server pitfalls, each from a run or from the sources
[cols="4,5,5",options="header"]
|===
|Symptom |Cause |Fix

|`Database 'enter_db_name_here' does not exist`
|the script's first statement is `USE [enter_db_name_here]`
|delete that line (`sed -e '/^USE \[/d'`); the database comes from the JDBC URL

|`Could not find stored procedure 'GO'`
|Spring's script runner sent a `GO` line to the server
|for Boot's initializer, convert `GO` lines to `;`; Flyway and Liquibase need no conversion

|`FOR UPDATE clause allowed only for DECLARE CURSOR` and `Failure obtaining db row lock`
|the default `StdJDBCDelegate` is in use, so the lock statement ends with `FOR UPDATE`
|set `org.quartz.jobStore.driverDelegateClass` to `org.quartz.impl.jdbcjobstore.MSSQLDelegate`

|`Invalid object name 'QRTZ_JOB_DETAILS'` after startup
|Boot's initializer ran the script, `continue-on-error` is `true` by default and the script's failing statements were skipped, so no table exists
|set `continue-on-error: false` while debugging, and create the tables with Flyway or Liquibase

|Stored jobs and triggers vanish after every restart
|`initialize-schema=always` re-runs a script that drops the tables first
|`initialize-schema=never` outside development; migrations create the schema

|A schema other than `dbo` is ignored or fails
|the script hard-codes `[dbo]`
|replace `[dbo]` in the script and set `org.quartz.jobStore.tablePrefix` to `schema.QRTZ_`

|A dedicated runtime user cannot start the scheduler
|the user lacks `INSERT` (Quartz inserts the `QRTZ_LOCKS` rows) or `UPDATE` and `DELETE` on the tables
|grant `SELECT, INSERT, UPDATE, DELETE` on the schema; no DDL rights are needed

|Connection fails with a certificate or TLS error against a container
|`mssql-jdbc` encrypts by default (since 10.2) and the image has a self-signed certificate
|`encrypt=false` or `trustServerCertificate=true`, for the container only

|Two `DataSource` beans and no persistence at all
|neither is `@Primary`, so Boot silently uses the RAM store (a `@QuartzDataSource` does not change that)
|mark the application's data source `@Primary` and the Quartz one with `@QuartzDataSource`

|Check-in deadlocks on `QRTZ_SCHEDULER_STATE` under load
|reported in #1514; fixed on Quartz `main` by #1515, unreleased; not reproduced in the tests on this page
|check the driver and connection settings and move to a release that contains #1515 when one exists

|The Docker image does not start on an arm64 machine without emulation
|`mssql/server:2022-latest` is amd64 only
|enable Rosetta (Docker Desktop on Apple Silicon) or run the tests on amd64 CI

|The same schema script is applied to Azure SQL Database and fails on `USE`
|`USE` cannot switch databases there (error 40508)
|remove the line, as everywhere
