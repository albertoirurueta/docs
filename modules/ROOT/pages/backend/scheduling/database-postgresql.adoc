[[delegate]]
== The delegate: PostgreSQLDelegate, and why it is mandatory

A JDBC job store talks to the database through a *driver delegate*, the class that holds the SQL and the JDBC calls. Quartz chooses nothing for you: if `org.quartz.jobStore.driverDelegateClass` is not set, Quartz uses `StdJDBCDelegate`
(measured under Boot: the job store reported a `null` delegate class and used the standard one). `StdJDBCDelegate` is written for databases whose BLOB columns behave like JDBC BLOBs, and it reads every serialized column
(the `JobDataMap` of a job, the `JobDataMap` of a trigger, a calendar) with `ResultSet.getBlob`. PostgreSQL's script declares those columns as `BYTEA`, a plain byte string, and pgJDBC maps `getBlob` only to PostgreSQL's separate *large object*
facility (columns of type `oid`), so on a `BYTEA` column it fails.

.What the standard delegate does with a BLOB, and what PostgreSQLDelegate does instead (Quartz 2.5.2 sources, abridged)
[source,java]
----
// StdJDBCDelegate.getObjectFromBlob (line 3410)
Blob blobLocator = rs.getBlob(colName);
if (blobLocator != null && blobLocator.length() != 0) {
    InputStream binaryInput = blobLocator.getBinaryStream();
    // ... ObjectInputStream.readObject()
}

// PostgreSQLDelegate.getObjectFromBlob (overrides it; getJobDataFromBlob is overridden the same way)
byte[] bytes = rs.getBytes(colName);
if (bytes != null && bytes.length != 0) {
    try (ObjectInputStream in = new ObjectInputStream(new ByteArrayInputStream(bytes))) {
        obj = in.readObject();
    }
}
----
Source: https://github.com/quartz-scheduler/quartz/blob/v2.5.2/quartz/src/main/java/org/quartz/impl/jdbcjobstore/PostgreSQLDelegate.java[`PostgreSQLDelegate` source at v2.5.2] and
https://github.com/quartz-scheduler/quartz/blob/v2.5.2/quartz/src/main/java/org/quartz/impl/jdbcjobstore/StdJDBCDelegate.java[`StdJDBCDelegate` source at v2.5.2]

The asymmetry is what makes the mistake easy to make: the *write* side of `StdJDBCDelegate` uses `setBytes`, which works on `BYTEA`, so the first symptom is not at the first insert but at the first read. On the Bookshelf service, with
`initialize-schema: always` and no delegate, the application context did not start. The chain of causes, measured on `postgres:17` with pgJDBC 42.7.13:

[source,text]

The text after `Bad value for type long` is the stored value itself: the hexadecimal `aced0005` is the header of Java serialization (`ObjectOutputStream`), the first four bytes of every job and trigger data column (measured with `encode(substring(job_data from 1 for 4), 'hex')`
on all four Bookshelf jobs). pgJDBC tried to read a `BYTEA` value as the numeric object id of a large object and complained that it is not a number.

The fix is one property, written under `spring.quartz.properties` because Boot passes that map straight to Quartz:

.Selecting the delegate (application.yml)
[source,yaml]
----
spring:
  quartz:
    job-store-type: jdbc
    properties:
      org.quartz.jobStore.driverDelegateClass: org.quartz.impl.jdbcjobstore.PostgreSQLDelegate
----
Source: https://www.quartz-scheduler.org/documentation/quartz-2.5.x/configuration/ConfigJobStoreTX.html[Quartz documentation: Configure JDBCJobStoreTX] and
https://docs.spring.io/spring-boot/reference/io/quartz.html[Spring Boot: Quartz Scheduler]

With it, the same service started, stored and fired the Bookshelf jobs and restarted with the state intact (the persisted `runs` counter of the overdue-loan job kept growing across a restart). This is the opposite of MySQL and MariaDB, where the standard delegate
is the right one, and of Oracle and SQL Server, which need their own; the choice per database is in the support matrix of the generic page. A `BYTEA` column also means that a `JobDataMap` is stored as a Java-serialized blob, so every value must be
`Serializable` and a class rename or a field change can make old rows unreadable; xref:backend/scheduling/jobs-and-job-data.adoc[Jobs & Job Data] explains the consequences and the `useProperties` alternative, which was not run on PostgreSQL.

[[ddl]]
== tables_postgres.sql

The script is inside the Quartz jar at `org/quartz/impl/jdbcjobstore/tables_postgres.sql` (7205 bytes in 2.5.2). It creates the eleven `QRTZ_` tables, their foreign keys and twenty secondary indexes, and it *starts* by dropping every table
(`DROP TABLE IF EXISTS`, eleven statements, in dependency order) and ends with `COMMIT;`. Everything in the first statement list is what makes the script safe for a demo and dangerous for a database that holds a schedule:
Boot's `initialize-schema: always` runs it on every start and therefore deletes every stored job and trigger on every restart (measured: a job scheduled at runtime survived a restart with `never` and was gone after a restart with `always`).

.The tables, their rows after the Bookshelf run, and the PostgreSQL types that matter
[cols="3,5,5",options="header"]
|===
|Table |What it holds |Notes

|`QRTZ_JOB_DETAILS`
|One row per `JobDetail`: class name, durable, non-concurrent, update-data, requests-recovery, `JOB_DATA`
|`JOB_DATA` is `BYTEA`; the four flags are `BOOL`. Four rows after the Bookshelf start.

|`QRTZ_TRIGGERS`
|One row per trigger: state, next and previous fire time, priority, misfire instruction, calendar name, `JOB_DATA`
|Times are `BIGINT` epoch milliseconds, `-1` meaning none. `MISFIRE_INSTR` is `SMALLINT`. Foreign key to the job.

|`QRTZ_SIMPLE_TRIGGERS`, `QRTZ_CRON_TRIGGERS`, `QRTZ_SIMPROP_TRIGGERS`, `QRTZ_BLOB_TRIGGERS`
|The type-specific part of a trigger
|Declared foreign keys to `QRTZ_TRIGGERS`. `CRON_EXPRESSION` is `VARCHAR(120)`, `TIME_ZONE_ID` `VARCHAR(80)`.

|`QRTZ_CALENDARS`, `QRTZ_PAUSED_TRIGGER_GRPS`
|Serialized calendars (`BYTEA NOT NULL`) and the names of paused groups
|

|`QRTZ_FIRED_TRIGGERS`
|One row per trigger that is acquired or executing, with the node that owns it
|The churn table. `ENTRY_ID` is `VARCHAR(95)`. No foreign keys.

|`QRTZ_SCHEDULER_STATE`
|One row per live cluster node and its last check-in
|Written only when clustered.

|`QRTZ_LOCKS`
|The row locks (`TRIGGER_ACCESS`, `STATE_ACCESS`)
|Two rows per scheduler name, created by Quartz on first use, not by the script (see <<locking>>).
|===
Source: https://www.quartz-scheduler.org/documentation/quartz-2.5.x/tutorials/tutorial-lesson-09.html[Quartz Tutorial: Lesson 9, JobStores] and
https://github.com/quartz-scheduler/quartz/blob/v2.5.2/quartz/src/main/resources/org/quartz/impl/jdbcjobstore/tables_postgres.sql[`tables_postgres.sql` at v2.5.2]

Every primary key starts with `SCHED_NAME` (`VARCHAR(120)`), which is how several schedulers, or several clusters, share one set of tables: the *scheduler name* (`spring.quartz.scheduler-name`) is part of every key and every `WHERE` clause. The
entity-relationship picture is on the generic page. Three PostgreSQL details deserve a sentence each:

* *Case.* The script uses unquoted upper-case identifiers, which PostgreSQL folds to lower case, so the tables are `qrtz_job_details` and so on (the monitoring queries below use lower case). Quartz's own SQL is also unquoted, so the two agree. A tool that
creates the tables with quoted upper-case names produces tables Quartz cannot find.
* *Indexes.* There are twenty secondary indexes (two on `QRTZ_JOB_DETAILS`, twelve on `QRTZ_TRIGGERS` and six on `QRTZ_FIRED_TRIGGERS`) besides the eleven primary keys. The acquisition query filters on `SCHED_NAME`, `TRIGGER_STATE` and `NEXT_FIRE_TIME`, for which the script has
`IDX_QRTZ_T_NFT_ST` and `IDX_QRTZ_T_NEXT_FIRE_TIME`. Which one the planner picks depends on statistics: on the four-row Bookshelf table with sequential scans disabled it chose `IDX_QRTZ_T_NEXT_FIRE_TIME` (an `EXPLAIN` on a table this small
proves nothing about a table with a million triggers). Each index is also something that every trigger update must maintain, which matters for the vacuum section below.
* *Booleans.* `BOOL` is PostgreSQL's `boolean`; Quartz binds it with `setBoolean`, so unlike Oracle with a 23.x driver there is no driver trap here.

[[schema]]
== A dedicated schema and role

Quartz's tables do not have to live next to the business tables. A separate *schema* and a separate *role* give three things for free: the tables stay out of the application's namespace (and of its migrations and its ORM), the privileges can be
narrower than the application's, and role-level settings such as `search_path` or session timeouts apply to Quartz connections only. The SQL below was run on `postgres:17` as an administrator; the role name `quartz` and the password
placeholder are examples (use a secret store; the placeholder is not a credential).

.01-quartz-role-and-schema.sql: a schema owned by its own role
[source,sql]
----
-- Run once as an administrator, connected to the application database (here: "bookshelf").
CREATE ROLE quartz LOGIN PASSWORD 'change-me-from-a-secret-store';

CREATE SCHEMA quartz AUTHORIZATION quartz;

-- Unqualified QRTZ_* names resolve through the search_path of the quartz role.
ALTER ROLE quartz IN DATABASE bookshelf SET search_path = quartz;

-- Nobody but the owner can see or touch the tables.
REVOKE ALL ON SCHEMA quartz FROM PUBLIC;
----
Source: https://www.postgresql.org/docs/current/sql-createrole.html[PostgreSQL: CREATE ROLE], https://www.postgresql.org/docs/current/sql-createschema.html[CREATE SCHEMA] and
https://www.postgresql.org/docs/current/ddl-schemas.html[Schemas]

Connecting as `quartz` showed `show search_path` = `quartz` and `current_schema()` = `quartz`. There are three ways to make Quartz's unqualified names land in that schema, all of which were run:

.Three ways to point Quartz at the schema (all measured on PostgreSQL 17)
[cols="3,5,4",options="header"]
|===
|Mechanism |How |Result

|The role's `search_path` (above)
|Nothing in Quartz or Spring: the role setting applies to every session of `quartz`
|Works. Needs the role to be the one the application uses.

|`currentSchema` in the JDBC URL
|`jdbc:postgresql://host:5432/bookshelf?currentSchema=quartz`, a pgJDBC connection parameter
|Works with any role. The Flyway and Liquibase connections that use the same URL create their tables and history table in that schema too.

|A schema-qualified `tablePrefix`
|`spring.quartz.properties.org.quartz.jobStore.tablePrefix: quartz.QRTZ_` with the default `search_path`
|Works: the job store read and wrote `quartz.qrtz_*` from a connection whose `search_path` was `public`. The Boot initializer and the Quartz scripts still create unqualified names, so use it only with tables created by a migration.
|===
Source: https://jdbc.postgresql.org/documentation/use/[pgJDBC: Connecting to the database] and
https://www.quartz-scheduler.org/documentation/quartz-2.5.x/configuration/ConfigJobStoreTX.html[Quartz documentation: Configure JDBCJobStoreTX]

The page uses `currentSchema` in the URL (it is visible in the configuration, which `search_path` is not) together with the role setting as a safety net. A bare `tablePrefix` such as `BKS_QRTZ_` is a different feature, for several applications in one schema;
it is described on the generic page.

=== Separating the migration role from the runtime role

The role that creates the tables does not need to be the role the service runs as. A runtime role that can only read and write rows cannot drop the schedule by mistake, and it cannot be used to change the table definitions. The second script was run
with Flyway connecting as `quartz` (the schema owner, through `spring.flyway.user`) and the application connecting as `quartz_app`:

.02-quartz-runtime-role.sql: a role that can only use the rows
[source,sql]
----
CREATE ROLE quartz_app LOGIN PASSWORD 'change-me-as-well';

GRANT USAGE ON SCHEMA quartz TO quartz_app;

-- Tables created later by role quartz (Flyway) become usable by quartz_app automatically.
ALTER DEFAULT PRIVILEGES FOR ROLE quartz IN SCHEMA quartz
    GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO quartz_app;

ALTER ROLE quartz_app IN DATABASE bookshelf SET search_path = quartz;
----
Source: https://www.postgresql.org/docs/current/sql-alterdefaultprivileges.html[PostgreSQL: ALTER DEFAULT PRIVILEGES]

.The runtime role in application.yml (the migration connection is separate)
[source,yaml]
----
spring:
  datasource:
    url: jdbc:postgresql://${DB_HOST:localhost}:5432/bookshelf?currentSchema=quartz
    username: quartz_app
    password: ${DB_PASSWORD}
  flyway:
    user: quartz
    password: ${DB_MIGRATION_PASSWORD}
----
Source: https://docs.spring.io/spring-boot/how-to/data-initialization.html[Spring Boot: Database Initialization]

Measured: with the schema recreated, the default privileges set and the service started like this, Flyway created eleven tables plus `flyway_schema_history`, all twelve owned by `quartz`, the service ran as `quartz_app` and the Bookshelf jobs fired. `UPDATE` is what
`SELECT ... FOR UPDATE` needs, so the four DML privileges are enough. Order matters: `ALTER DEFAULT PRIVILEGES ... IN SCHEMA` belongs to the schema, so it disappears with `DROP SCHEMA` and must be repeated after the schema is recreated (a first run
that forgot it failed with `permission denied for table qrtz_job_details`).

[[config]]
== application.yml for production

The configuration below is the one run for the single-node check of this page: it was started as a separate JVM with the YAML as its only configuration file and the four `DB_*` environment variables set, against the container, with an empty schema.
It created the tables through Flyway (`flyway_schema_history` held version 1, `quartz tables`), registered one node in `QRTZ_SCHEDULER_STATE` with `CHECKIN_INTERVAL` 5000, fired the cache refresh, and
`pg_stat_activity` showed sixteen connections whose `application_name` was `bookshelf-service`.

.application.yml of the Bookshelf service on PostgreSQL
[source,yaml]
----
spring:
  application:
    name: bookshelf-service
  datasource:
    url: jdbc:postgresql://${DB_HOST:localhost}:${DB_PORT:5432}/bookshelf?currentSchema=quartz&ApplicationName=bookshelf-service
    username: ${DB_USER}
    password: ${DB_PASSWORD}
    hikari:
      maximum-pool-size: 16            # Quartz threads + 3 (documented rule) plus the application's own needs
      connection-timeout: 10000
  flyway:
    enabled: true                      # V1__quartz_tables.sql lives in classpath:db/migration
  quartz:
    job-store-type: jdbc
    scheduler-name: BookshelfScheduler
    wait-for-jobs-to-complete-on-shutdown: true
    overwrite-existing-jobs: false
    jdbc:
      initialize-schema: never         # the migration tool owns the tables
    properties:
      org.quartz.scheduler.instanceId: AUTO
      org.quartz.jobStore.driverDelegateClass: org.quartz.impl.jdbcjobstore.PostgreSQLDelegate
      org.quartz.jobStore.isClustered: "true"
      org.quartz.jobStore.clusterCheckinInterval: "5000"   # default 7500; a dead node is noticed after interval + 7500 ms
      org.quartz.threadPool.threadCount: "10"
----
Source: https://docs.spring.io/spring-boot/reference/io/quartz.html[Spring Boot: Quartz Scheduler] and
https://www.quartz-scheduler.org/documentation/quartz-2.5.x/configuration/ConfigJDBCJobStoreClustering.html[Quartz documentation: Configure Clustering with JDBC-JobStore]

What each line is for, and where the page treats it:

* `ApplicationName=bookshelf-service` is a pgJDBC parameter. Without it the driver reports `PostgreSQL JDBC Driver` for every session (the statement `SET application_name = 'PostgreSQL JDBC Driver'` shows in the server log), which makes
`pg_stat_activity` useless for telling the service from a console. With it, `select application_name, count(*) from pg_stat_activity` showed the sixteen Quartz-pool connections under the service's name.
* `maximum-pool-size: 16` -- Hikari opens the *whole* pool at start unless `minimum-idle` is lowered: the measured count above was sixteen connections for one idle node. See <<connections>> for the budget of a cluster.
* `scheduler-name` is part of every key in the tables; all nodes of one cluster must share it, and two different applications that share tables must not.
* `initialize-schema: never` hands the tables to the migration tool; <<flyway>> and <<liquibase>> follow.
* `wait-for-jobs-to-complete-on-shutdown: true` lets a node finish what it is running on a graceful stop, so only a crash needs the recovery described in <<cluster-test>>.
* `overwrite-existing-jobs: false` keeps operator changes (a paused trigger) across a deployment, as on the generic page.
* `instanceId: AUTO` makes Quartz build the id from the host name and the epoch milliseconds (so two nodes started in the same millisecond on one host could collide, an unlikely event that the generic clustering page discusses).
* The delegate and `isClustered` need no further explanation; every other `spring.quartz.*` property is on xref:backend/scheduling/spring-boot-configuration.adoc[Spring Boot Configuration].

[[flyway]]
== Flyway

A Flyway migration is the Quartz script without its `DROP TABLE` lines. The `COMMIT;` at the end of the script is also removed (Flyway runs each migration in a transaction of its own). The whole pipeline, run against the 2.5.2 jar, produces a file that is byte-for-byte
the migration used by every test on this page:

.Producing the migration from the Quartz jar
[source,bash]
----
mkdir -p src/main/resources/db/migration
unzip -p quartz-2.5.2.jar org/quartz/impl/jdbcjobstore/tables_postgres.sql \
  | sed -e '/^DROP TABLE/d' -e '/^COMMIT;/d' > src/main/resources/db/migration/V1__quartz_tables.sql
----
Source: https://www.quartz-scheduler.org/documentation/quartz-2.5.x/configuration/ConfigJobStoreTX.html[Quartz documentation: Configure JDBCJobStoreTX]

The YAML of the previous section is the whole Boot configuration: `spring.flyway.enabled` defaults to true and the default location is `classpath:db/migration`. Boot starts the scheduler *after* Flyway (the scheduler bean depends on database initialization,
which includes Flyway and Liquibase): with an empty schema and `initialize-schema: never` the migration ran first and the jobs fired from the tables it had just created, with no `@DependsOn`. Measured with the dedicated `quartz` role and
`currentSchema=quartz`: eleven `qrtz_*` tables, `flyway_schema_history` in the same schema (one row, version 1, `quartz tables`, success true), and the Bookshelf jobs firing. Which tool to choose is on
xref:database/schema-evolution/choosing-a-migration-tool.adoc[Choosing a Migration Tool]; Flyway has no page of its own in that section, see xref:database/schema-evolution/index.adoc[Schema Evolution] for the concepts.

When a Quartz upgrade changes the DDL, you write `V2__...` yourself. Nothing in Quartz or Boot will ever alter the tables of a database it did not create: that is the reason to own the migration.

[[liquibase]]
== Liquibase

Liquibase offers two routes, both run on `postgres:17` with Liquibase 5.0.3 and `currentSchema=quartz`. Boot looks for `classpath:/db/changelog/db.changelog-master.yaml` by default and needs `spring.liquibase.change-log` for any other file, and both Flyway and Liquibase
start automatically when on the classpath, so the measured runs switched the other one off with `spring.flyway.enabled=false` or `spring.liquibase.enabled=false`.

.Route 1: the script as a change set (db/changelog/db.changelog-master.yaml)
[source,yaml]
----
databaseChangeLog:
  - changeSet:
      id: quartz-tables
      author: bookshelf
      changes:
        - sqlFile:
            path: db/changelog/quartz-tables.sql      # the same file as V1__quartz_tables.sql
            splitStatements: true
            endDelimiter: ;
            stripComments: true
----
Source: https://docs.liquibase.com/concepts/changelogs/sql-format.html[Liquibase: SQL changelogs]

.Route 2: the changelog that ships inside the Quartz jar (db/changelog/db.changelog-master.xml)

[[quartz-datasource]]
== A second data source: @QuartzDataSource and @QuartzTransactionManager

When the business data is elsewhere (another PostgreSQL database, or MongoDB as on xref:backend/scheduling/database-mongodb.adoc[Quartz with MongoDB]), Quartz gets its own data source. Boot's rule has two steps: `job-store-type: jdbc` is honoured only when there is exactly one candidate `DataSource` (a single bean, or one marked `@Primary`), and
then the job store uses the `DataSource` annotated `@QuartzDataSource` if there is one, else that candidate. The first listing configures an application database as the primary data source and a dedicated `quartzdb` database for Quartz; both were PostgreSQL 17 databases in
one container, with a `quartz` role that owns `quartzdb`.

.Two data sources: the application's is primary, Quartz's is marked @QuartzDataSource (Boot 4.1)
[source,java]

=== The transaction the data source does not give you

A second data source changes what a Spring transaction covers. A `@Transactional` method of the application is bound to the *primary* transaction manager, which manages the application's data source; Quartz's connections come from another pool, so
the application's transaction does not include them. Boot's counterpart of `@QuartzDataSource` is `@QuartzTransactionManager`. I measured what each setup sends to the database when a `loan-A` reminder is scheduled inside a `TransactionTemplate` (statements read from the
server log with `log_statement = all`):

.Scheduling a reminder inside a transaction, with the Quartz connection in autocommit or in a transaction (measured)

|Setup |Statements Quartz sent

|`TransactionTemplate` on the *application's* transaction manager, Quartz on `@QuartzDataSource`

import org.springframework.boot.quartz.autoconfigure.QuartzDataSource;
import org.springframework.boot.quartz.autoconfigure.QuartzTransactionManager;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.context.annotation.Primary;
import org.springframework.jdbc.datasource.DataSourceTransactionManager;
import org.springframework.transaction.PlatformTransactionManager;

import javax.sql.DataSource;

    @Bean @Primary
    PlatformTransactionManager appTransactionManager(DataSource appDataSource) {
        return new DataSourceTransactionManager(appDataSource);
    }

    PlatformTransactionManager quartzTransactionManager(@QuartzDataSource DataSource quartzDataSource) {
        return new DataSourceTransactionManager(quartzDataSource);
    }

single data source this matters, as the next section shows.

[[locking]]
== Locking: SELECT ... FOR UPDATE on QRTZ_LOCKS

Quartz protects its tables with two *named locks*, implemented as rows of `QRTZ_LOCKS` that a transaction locks with `SELECT ... FOR UPDATE`. The class is `StdRowLockSemaphore`; the statement is a constant in its source:

.The lock statement and the insert of a missing lock row (StdRowLockSemaphore, Quartz 2.5.2)
[source,java]
----
public static final String SELECT_FOR_LOCK = "SELECT * FROM "
        + TABLE_PREFIX_SUBST + TABLE_LOCKS + " WHERE " + COL_SCHEDULER_NAME + " = " + SCHED_NAME_SUBST
        + " AND " + COL_LOCK_NAME + " = ? FOR UPDATE";

public static final String INSERT_LOCK = "INSERT INTO "
    + TABLE_PREFIX_SUBST + TABLE_LOCKS + "(" + COL_SCHEDULER_NAME + ", " + COL_LOCK_NAME + ") VALUES ("
    + SCHED_NAME_SUBST + ", ?)";
----
Source: https://github.com/quartz-scheduler/quartz/blob/v2.5.2/quartz/src/main/java/org/quartz/impl/jdbcjobstore/StdRowLockSemaphore.java[`StdRowLockSemaphore` source at v2.5.2]

Three properties of this mechanism follow from the source and were all observed:

* *The rows are created on demand.* If the `SELECT` finds no row, `StdRowLockSemaphore` inserts it (the log shows `INSERT INTO QRTZ_LOCKS(SCHED_NAME, LOCK_NAME) VALUES ('BookshelfCluster', $1)` right after the first `FOR UPDATE`).
The script does not insert them, so a freshly migrated database has an empty `QRTZ_LOCKS`, and after a Bookshelf run it held exactly `TRIGGER_ACCESS` and `STATE_ACCESS` for the scheduler name (`STATE_ACCESS` only when clustered). If two nodes race on the very first insert, the loser retries: `maxRetry` is 3 and
`retryPeriod` 1000 ms by default (three attempts in all, a second apart).
* *The rows are never updated.* After 975 firings on a busy single node, `QRTZ_LOCKS` had one live tuple (`TRIGGER_ACCESS`; two in a clustered run), zero updates and zero dead tuples (`pg_stat_user_tables`). A row lock of this kind writes the locking transaction's id into the existing row version instead of creating a new one,
so the lock table does not bloat and needs no tuning (see <<vacuum>>).
* *A failure to get the lock is retried, then thrown.* On a `SQLException` the semaphore rolls the connection back, sleeps `retryPeriod` and tries again, for `maxRetry` attempts in all, and finally throws `LockException: Failure obtaining db row lock`.

=== Which operation takes which lock

The two lock names are the constants `LOCK_TRIGGER_ACCESS` (`TRIGGER_ACCESS`) and `LOCK_STATE_ACCESS` (`STATE_ACCESS`) in `JobStoreSupport`. `TRIGGER_ACCESS` protects the scheduling tables; `STATE_ACCESS` protects the cluster state.

.Where Quartz 2.5.2 takes the locks (JobStoreSupport source, confirmed by statement logs)
[cols="4,3,6",options="header"]
|===
|Operation |Lock |Detail

|`acquireNextTriggers` (scheduler thread)
|*none by default*
|Locks `TRIGGER_ACCESS` only when `acquireTriggersWithinLock` is true or the batch size is above one (the source: `isAcquireTriggersWithinLock() \|\| maxCount > 1`). The default is false and the batch size is 1, and the log of such a run shows no `FOR UPDATE` during acquisition.

|`triggersFired` (scheduler thread, after the wait)
|`TRIGGER_ACCESS`
|Re-checks that the trigger is still `ACQUIRED`, marks the fired row `EXECUTING`, computes the next fire time.

|`triggeredJobComplete` (worker thread, after the job)
|`TRIGGER_ACCESS`
|Updates the job data when `@PersistJobDataAfterExecution` is set, frees blocked triggers of a `@DisallowConcurrentExecution` job, deletes the fired row.

|Storing jobs and triggers, `scheduleJob`, `rescheduleJob`, `deleteJob`, pause and resume
|`TRIGGER_ACCESS`
|For plain inserts only when `lockOnInsert` is true (the default); replacing or updating always locks.

|Misfire handling (`MisfireHandler` thread)
|`TRIGGER_ACCESS`, only if something misfired
|It first counts misfired triggers without a lock and skips the lock when the count is zero.

|Cluster check-in, normal case
|*none*
|`SELECT * FROM QRTZ_SCHEDULER_STATE` and an `UPDATE` of `LAST_CHECKIN_TIME`, no lock.

|First check-in of a node, and recovery of a failed node
|`STATE_ACCESS`, then `TRIGGER_ACCESS` for the recovery
|Recovery needs both because it rewrites trigger and fired-trigger rows.
|===
Source: https://github.com/quartz-scheduler/quartz/blob/v2.5.2/quartz/src/main/java/org/quartz/impl/jdbcjobstore/JobStoreSupport.java[`JobStoreSupport` source at v2.5.2] and
https://www.quartz-scheduler.org/documentation/quartz-2.5.x/configuration/ConfigJobStoreTX.html[Quartz documentation: Configure JDBCJobStoreTX]

The same source says why acquisition can do without a lock: the update that claims a trigger is conditional (it only succeeds while the state is still `WAITING`). The Javadoc of `setAcquireTriggersWithinLock` calls the lock the behaviour before Quartz 1.6.3, considers it superfluous for most databases because of that update,
and says that with batch acquisition it must be used for every database. With the defaults, the lock-free path is also what makes a cluster scale: only the short fire and complete transactions serialize.

=== The three settings that change the picture

* `acquireTriggersWithinLock` (default false): described above. Leave it false unless you raise `org.quartz.scheduler.batchTriggerAcquisitionMaxCount` above 1, in which case the source locks anyway.
* `lockOnInsert` (default true): measured with the same `scheduleJob` call twice. With the default, the insert transaction began with the `FOR UPDATE` on `TRIGGER_ACCESS`; with `org.quartz.jobStore.lockOnInsert: "false"` it began directly with the `SELECT JOB_NAME FROM QRTZ_JOB_DETAILS`.
The Javadoc of the property calls true the safest value, says that some databases (SQL Server is named) need it to avoid deadlocks under load, and warns that with false the isolation between scheduling and trigger acquisition is left entirely to the database and may give unusual scheduling behaviour; the same Javadoc advertises a significant speed-up of adding jobs and triggers. Leave it true unless you have measured a problem with job insertion.
* `selectWithLockSQL` (default none): the statement above is used. Only SQL Server needs a replacement (`WITH (UPDLOCK, ROWLOCK)`), which the source sets for `MSSQLDelegate`; PostgreSQL does not.

=== Isolation level

Quartz does not set an isolation level by default, so a Quartz connection runs at the server's default, which on PostgreSQL is `READ COMMITTED` (the log of the run above contains no `SET SESSION CHARACTERISTICS` statement). That is the level the row-lock design assumes:
a transaction that waits on `FOR UPDATE` re-reads the row after the lock is granted and proceeds. Two properties exist to change it, and I ran both on the busy Bookshelf workload (twenty seconds each) to see what they do:

.The isolation properties under Boot's LocalDataSourceJobStore (measured)
[cols="4,6",options="header"]
|===
|Property |What the server log showed

|`org.quartz.jobStore.txIsolationLevelReadCommitted: "true"`
|No `SET` statement (the connection was already `READ COMMITTED`), but one extra `SHOW TRANSACTION ISOLATION LEVEL` round trip per Quartz transaction: 1957 of them in twenty seconds. A cost with no effect on PostgreSQL.

|`org.quartz.jobStore.txIsolationLevelSerializable: "true"`
|Ten `SET SESSION CHARACTERISTICS AS TRANSACTION ISOLATION LEVEL SERIALIZABLE` statements, each restored afterwards, and none for the scheduler thread's transactions. Under Boot, `JobStoreCMT` honours only the read-committed flag for the connections of its scheduler threads, so this property reaches
only the connections obtained through Spring for the scheduler API calls. No `could not serialize access` error occurred, but the run was a single node.
|===

=== Scheduler calls outside a transaction

The lock only protects what happens while the transaction that took it is open. Spring's `LocalDataSourceJobStore` sets `dontSetAutoCommitFalse`, and the connections it hands out for scheduler API calls come from Spring's transaction handling: inside a Spring-managed transaction they take part in it, outside one
they are plain autocommit connections. The same `scheduleJob` call, measured twice in one JVM on a quiet scheduler:

In the first form the `FOR UPDATE` lock is released before the insert, and the job and its trigger are two commits: a crash between them leaves a job without a trigger. PostgreSQL does not complain. Spring's own Javadoc says to perform all scheduler operations inside Spring-managed
transactions, and mentions Oracle as a database where the lock without a transaction fails outright. In the Bookshelf service, the method that creates the per-member reminder when a loan is made should therefore be `@Transactional` (with `@QuartzTransactionManager` named explicitly when Quartz has its own data
source, see the previous section), which also lets the reminder commit or roll back together with the loan row when both are in the same database. The scheduler API is covered on xref:backend/scheduling/dynamic-scheduling-and-management.adoc[Dynamic Scheduling & Management].

Two role-level settings, both applied with `ALTER ROLE quartz IN DATABASE bookshelf SET ...` (which is one more reason for a dedicated role), react to a stuck holder, and the measurements disagree with the intuition:

* `lock_timeout = '1500ms'` made waiters give up. With a *sixteen*-second hold the retries ran out, the scheduler thread logged

is consistent with the job store's `dbRetryInterval` (15000 ms), the period its retry loops sleep for after a failure (`retryExecuteInNonManagedTXLock` in `JobStoreSupport`). A short `lock_timeout` therefore turns a long stall into a longer one; if you set it, set it well above the longest stall you tolerate.
* `idle_in_transaction_session_timeout` ends the session of a client that opened a transaction and stopped (`FATAL: terminating connection due to idle-in-transaction timeout`, measured with a two-second value on a test session that held the lock row). It is the setting that frees a lock held by a forgotten transaction and the one that keeps a
stuck transaction from pinning the vacuum horizon (next section). Because it applies per role it affects Quartz's own sessions too, so choose a value above the longest transaction your *application* keeps open around scheduler calls.

[[vacuum]]
== Vacuuming and bloat of the churn tables

PostgreSQL never updates a row in place: an `UPDATE` writes a new row version and leaves the old one for `VACUUM` to reclaim, and a `DELETE` leaves a dead version too. Quartz's access pattern is a stream of tiny updates and deletes on a few tiny tables, so the interesting question is how many dead
versions it produces and whether autovacuum keeps up. I measured it with a deliberately busy scheduler: eight simple triggers firing every 250 ms each, on one node with ten worker threads and instantly finishing jobs, in a fresh schema, for sixty seconds, reading `pg_stat_user_tables` and the table sizes every twenty seconds.
The container ran `autovacuum_naptime = 5s` (the default is one minute) so that the effect of autovacuum shows within the run. The number of executions differed from run to run (between 962 and 1377 in sixty seconds, on a laptop doing other work), so compare dead tuples per execution, not absolute rates.

Autovacuum *ran* (eleven times) and removed nothing, because the idle transaction held the horizon: the dead-tuple counts kept growing, almost as in the run with autovacuum switched off, and the tables reached about three times the largest size of any run without the old transaction (1528 KiB against 464 KiB for `qrtz_triggers`).
After the transaction ended the dead-tuple counts started to fall (they are cumulative statistics and lag a little) but the files did not shrink: `VACUUM`
makes the space reusable and only truncates empty pages at the end of a table. In a real database the transaction that holds the horizon is rarely idle by accident: a long report, a forgotten console session, a logical replication slot that nobody consumes, a standby with `hot_standby_feedback`. Quartz is the first to suffer, because it
rewrites the same few rows continuously. The defences, in order of strength:

* Set `idle_in_transaction_session_timeout` for application roles (see <<locking>> for its interaction with Quartz) and `statement_timeout` or a read replica for reports.
* Monitor the age of the oldest transaction (`pg_stat_activity.xact_start`) and the dead-tuple counts above; alert when `n_dead_tup` of `qrtz_fired_triggers` or `qrtz_triggers` keeps growing while `autovacuum_count` keeps increasing.
* Keep Quartz in its own *database* when other workloads run long transactions: the vacuum horizon is per database, so a separate schema is cosmetic here and a separate database (the `@QuartzDataSource` section) is real isolation (replication slots and prepared transactions are the exceptions: they hold the horizon of the whole cluster).
* To return the space of an already bloated table: `VACUUM (VERBOSE)` makes it reusable; `VACUUM FULL` or `pg_repack` shrink it but `VACUUM FULL` takes an `ACCESS EXCLUSIVE` lock, which blocks the scheduler until it is done (stated by the PostgreSQL documentation; not run here). Stop the scheduler (`standby()`) or the nodes first.

[[connections]]
== Connections: the budget of a cluster

Each node holds a pool, and the pool of a node that is merely idle is already full: with Hikari's default `minimum-idle` (equal to the maximum) the measured node held sixteen connections for `maximum-pool-size: 16`. A three-node cluster with that configuration holds 48 connections of PostgreSQL's `max_connections`
(100 by default), before the application's own traffic and before a rolling deployment starts new nodes while the old ones still run. The documented sizing rule, stated on the generic page, is the number of worker threads plus three at least. I also measured what a pool really needs when jobs finish instantly: the busy
workload of the vacuum section (ten worker threads, instant jobs) ran as many executions in forty seconds with a pool of four connections as with a pool of twelve (1287 and 1286), with no pool timeout, and the number of Quartz sessions seen in `pg_stat_activity` never exceeded the pool size (12 in the larger run). That shows that Quartz's transactions are short, not that the rule can be ignored: with jobs that use the same
pool as Quartz, or that take a while, the sizing rule is the right default. The production consequences are on xref:backend/scheduling/production-and-best-practices.adoc[Production & Best Practices] and the pool itself on
xref:backend/scheduling/job-stores-and-persistence.adoc[Job Stores & Persistence].

Source: https://www.quartz-scheduler.org/documentation/quartz-2.5.x/configuration/ConfigJDBCJobStoreClustering.html[Quartz documentation: Configure Clustering with JDBC-JobStore] and
https://github.com/quartz-scheduler/quartz/blob/v2.5.2/quartz/src/main/java/org/quartz/impl/jdbcjobstore/JobStoreSupport.java[`JobStoreSupport` source at v2.5.2 (`doCheckin`, `findFailedInstances`, `calcFailedIfAfter`, `clusterRecover`)]

The failure detection rule is in `calcFailedIfAfter`: a node is declared failed when its `LAST_CHECKIN_TIME` plus the larger of its own check-in interval and the time since the *observer's* last check-in, plus a fixed 7500 ms, has passed. With `clusterCheckinInterval` at the default 7500 ms the
worst case is therefore about fifteen seconds plus one check-in cycle; with the 2000 ms of the test below it is about ten. The check-in times are written with each node's own clock, so the nodes' clocks must agree (the clustering documentation warns about unsynchronized clocks); run a time-sync service on every host.

The recovery has two halves, and they differ in what they promise. A trigger that the dead node had *acquired* but not started is freed and fires normally. A job that was *executing* is run again only if it was declared with `requestRecovery(true)`; the recovery trigger carries the original scheduled time and the job sees
`JobExecutionContext.isRecovering()` as true. For everything else the fired-trigger row is cleaned up and the execution is lost. The job must therefore be written to be run twice, which is why the Bookshelf weekly report is the example below.
How a cluster shares work (it does not load-balance) and how to design for it is on xref:backend/scheduling/clustering.adoc[Clustering].

            .withInitScript("db/init-quartz-schema.sql");   // CREATE ROLE quartz, CREATE SCHEMA quartz

    /** A cluster node = a separate JVM running bookshelf.BookshelfNode, so that it can be killed with SIGKILL. */
    static final class Node implements AutoCloseable {
        final Process process;
        final List<String> output = new CopyOnWriteArrayList<>();

        Node(String schedulerName, String... extraArgs) throws Exception {
            List<String> command = new ArrayList<>(List.of(
                    System.getProperty("java.home") + "/bin/java", "-cp", System.getProperty("java.class.path"),
                    "bookshelf.BookshelfNode",
                    "--spring.main.banner-mode=off", "--logging.level.root=WARN",
                    "--logging.level.org.springframework.scheduling.quartz=INFO", // the job store logs under its own class name: shows ClusterManager messages
                    "--bookshelf.fast=true",
                    "--spring.datasource.url=jdbc:postgresql://%s:%d/bookshelf?currentSchema=quartz"
                            .formatted(POSTGRES.getHost(), POSTGRES.getFirstMappedPort()),
                    "--spring.datasource.username=quartz",
                    "--spring.datasource.password=" + QUARTZ_PASSWORD,
                    "--spring.flyway.enabled=true",                       // V1__quartz_tables.sql creates the tables
                    "--spring.quartz.job-store-type=jdbc",
                    "--spring.quartz.jdbc.initialize-schema=never",
                    "--spring.quartz.scheduler-name=" + schedulerName,   // the same name on every node of one cluster
                    "--spring.quartz.properties.org.quartz.scheduler.instanceId=AUTO",
                    "--spring.quartz.properties.org.quartz.jobStore.driverDelegateClass=org.quartz.impl.jdbcjobstore.PostgreSQLDelegate",
                    "--spring.quartz.properties.org.quartz.jobStore.isClustered=true",
                    "--spring.quartz.properties.org.quartz.jobStore.clusterCheckinInterval=2000",
                    "--spring.quartz.properties.org.quartz.threadPool.threadCount=3"));
            command.addAll(List.of(extraArgs));
            process = new ProcessBuilder(command).redirectErrorStream(true).start();
            Thread reader = new Thread(() -> {
                try (BufferedReader in = new BufferedReader(new InputStreamReader(process.getInputStream()))) {
                    String line;
                    while ((line = in.readLine()) != null) output.add(line);
                } catch (Exception ignored) { }
            });
            reader.setDaemon(true);
            reader.start();
            awaitLine(60_000, l -> l.startsWith("NODE-READY"));
        }

        String awaitLine(long millis, Predicate<String> match) throws InterruptedException {
            long end = System.currentTimeMillis() + millis;
            while (System.currentTimeMillis() < end) {
                for (String l : output) if (match.test(l)) return l;
                Thread.sleep(100);
            }
            throw new AssertionError("no matching output within " + millis + " ms:\n" + String.join("\n", output));
        }

        List<String> fires(String job) {
            return output.stream().filter(l -> l.startsWith("FIRE " + job + " ")).toList();
        }

        @Override public void close() { process.destroyForcibly(); }
    }

    static List<Map<String, Object>> query(String sql) throws Exception {
        try (Connection c = DriverManager.getConnection(POSTGRES.getJdbcUrl(), POSTGRES.getUsername(), POSTGRES.getPassword());
             Statement st = c.createStatement(); ResultSet rs = st.executeQuery(sql)) {
            List<Map<String, Object>> rows = new ArrayList<>();
            while (rs.next()) {
                Map<String, Object> row = new TreeMap<>();
                for (int i = 1; i <= rs.getMetaData().getColumnCount(); i++) row.put(rs.getMetaData().getColumnLabel(i), rs.getObject(i));
                rows.add(row);
            }
            return rows;
        }
    }

    @Test
    void threeNodesShareTheWorkAndNeverRunTheSameFireTimeTwice() throws Exception {
        try (Node a = new Node("share"); Node b = new Node("share"); Node c = new Node("share")) {   // a runs Flyway, b and c find the tables
            Thread.sleep(15_000);

            assertThat(query("SELECT instance_name FROM quartz.qrtz_scheduler_state WHERE sched_name = 'share'")).hasSize(3);

            List<String> fires = new ArrayList<>();
            for (Node n : List.of(a, b, c)) { fires.addAll(n.fires("cacheRefresh")); fires.addAll(n.fires("overdueLoanReminders")); }
            assertThat(fires).isNotEmpty();

            // "FIRE <job> node=<id> scheduled=<epoch ms> recovering=<b>": the job plus its scheduled time must be unique
            Map<String, Long> perFireTime = fires.stream().collect(Collectors.groupingBy(
                    l -> l.split(" ")[1] + " " + l.split(" ")[3], Collectors.counting()));
            assertThat(perFireTime.values()).allMatch(count -> count == 1);

            for (String job : List.of("cacheRefresh", "overdueLoanReminders"))
                System.out.println(job + ": a=" + a.fires(job).size() + " b=" + b.fires(job).size() + " c=" + c.fires(job).size());
        }
    }

    @Test
    void aCrashedNodeIsDetectedAndItsRecoverableJobIsRunAgain() throws Exception {
        try (Node x = new Node("crash", "--bookshelf.schedule-weekly-report-now=true")) {
            x.awaitLine(40_000, l -> l.startsWith("FIRE weeklyReport "));   // x is now inside the 25 s report
            try (Node y = new Node("crash")) {                                // y starts after x took the job
                assertThat(query("SELECT state, requests_recovery FROM quartz.qrtz_fired_triggers WHERE sched_name = 'crash' AND job_name = 'weeklyReport'"))
                        .singleElement().satisfies(row -> {
                            assertThat(row.get("state")).isEqualTo("EXECUTING");
                            assertThat(row.get("requests_recovery")).isEqualTo(true);
                        });

                long killedAt = System.currentTimeMillis();
                x.process.destroyForcibly().waitFor();                       // kill -9: no shutdown hook, no clean-up

                String line = y.awaitLine(60_000, l -> l.startsWith("FIRE weeklyReport ") && l.endsWith("recovering=true"));
                System.out.println("recovered after " + (System.currentTimeMillis() - killedAt) + " ms: " + line);
                y.output.stream().filter(l -> l.contains("ClusterManager")).forEach(System.out::println);
                assertThat(query("SELECT instance_name FROM quartz.qrtz_scheduler_state WHERE sched_name = 'crash'")).hasSize(1);
            }
        }
    }
}

Each node gets its own scheduler name per test (`share` and `crash`) so that rows left by a killed node of one test cannot disturb the other, whatever the order the tests run in. `DriverManager` in the helper uses the container's own superuser to read the Quartz tables; the nodes use the `quartz` role.
Every JVM started by `java.class.path` of the test, which works because Surefire runs with a real classpath (`useManifestOnlyJar` false in the pom of the test project).

[[pitfalls]]
== Pitfalls

.Quartz on PostgreSQL: what goes wrong, why, and the fix
[cols="3,4,4",options="header"]
|===
|Symptom |Cause |Fix

|`PSQLException: Bad value for type long : \xaced0005...` when the context starts
|`StdJDBCDelegate` reads `BYTEA` columns with `getBlob`
|`org.quartz.jobStore.driverDelegateClass: org.quartz.impl.jdbcjobstore.PostgreSQLDelegate`

|`relation "qrtz_job_details" does not exist`
|Nothing created the tables: Boot's default `initialize-schema` is `embedded`, which means H2, HSQLDB and Derby only
|Flyway or Liquibase with `initialize-schema: never` (or `always` for a throw-away database)

|Every stored job and trigger disappears after a restart
|`initialize-schema: always` re-runs a script that begins with `DROP TABLE IF EXISTS`
|Never use `always` outside tests; a migration without the `DROP` lines

|The tables appear in `public`, or in the wrong schema
|No `currentSchema`, no role `search_path`
|`currentSchema=quartz` in the URL and `ALTER ROLE ... SET search_path`

|`permission denied for table qrtz_job_details` with a runtime role
|Default privileges were set before the schema was dropped and recreated, or never set for the migration role
|`ALTER DEFAULT PRIVILEGES FOR ROLE quartz IN SCHEMA quartz GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO quartz_app` after every `CREATE SCHEMA`

|Jobs vanish after a restart with two data sources and no error
|Two `DataSource` beans and no `@Primary`: Boot silently uses the RAM store, even when one of them is `@QuartzDataSource`
|Mark the application's data source `@Primary` and the Quartz one `@QuartzDataSource` (or keep a single `DataSource`)

|A job and its trigger are committed separately, or the lock does not protect an insert
|`scheduleJob` called outside a Spring transaction runs in autocommit; with a second data source the application's transaction does not include Quartz's connection
|`@Transactional` around scheduler calls, and a `@QuartzTransactionManager` when Quartz has its own data source

|Nothing fires for a while although the scheduler is running, `wait_event = transactionid` on a Quartz backend
|Another session holds the `TRIGGER_ACCESS` row lock (a long transaction that locked it, or a manual `FOR UPDATE`)
|Find and end the holder; set `idle_in_transaction_session_timeout` for application roles

|Firing resumes 15 seconds late after a long stall
|A short `lock_timeout` made the lock fail; the scheduler thread retries on `dbRetryInterval` (15000 ms)
|Do not set `lock_timeout` below the longest stall you accept

|`txIsolationLevelReadCommitted: "true"` slows the scheduler
|It adds a `SHOW TRANSACTION ISOLATION LEVEL` round trip to every Quartz transaction and changes nothing on PostgreSQL
|Leave the isolation properties unset

|`QRTZ_TRIGGERS` and `QRTZ_FIRED_TRIGGERS` grow although autovacuum runs
|An old transaction (idle, a long report, a replication slot, `hot_standby_feedback`) holds the vacuum horizon
|Find it in `pg_stat_activity` and `pg_replication_slots`; `idle_in_transaction_session_timeout`; Quartz on its own database

|Lookups of a job's triggers are slow with the bundled Liquibase changelog
|`liquibase.quartz.init.xml` does not create `IDX_QRTZ_T_J`
|Add the index in your own change set

|`QRTZ_LOCKS` is empty after migration
|Normal: Quartz inserts the rows on first use
|Do nothing; do not insert them yourself

|Hikari exhausts `max_connections` during a rolling deployment
|Every idle node holds its whole pool (`minimum-idle` defaults to the maximum)
|Budget nodes times pool size, set `minimum-idle`, or use a pooler in session mode

|Duplicate runs of a job after a crash
|The job was re-run on purpose: `requestRecovery(true)` and the crashed node had it `EXECUTING`
|Make the job idempotent, or leave `requestRecovery` false
|===

.Facts about Quartz on PostgreSQL that changed, or that older articles get wrong
[cols="3,3,4",options="header"]
|===
|Topic |Before |Now (Quartz 2.5.2, Boot 4.1.1, pgJDBC 42.7.13, PostgreSQL 17.11)

|Boot package of the Quartz and JDBC types
|`org.springframework.boot.autoconfigure.quartz`, `org.springframework.boot.autoconfigure.jdbc.DataSourceProperties`

|Terracotta clustering
|Documented on the Quartz website
|Removed in 2.4.0: PostgreSQL (or another JDBC database) is the clustering path

|`liquibase.quartz.init.xml`
|Often described as the way to create the schema
|Present in the 2.5.2 jar and identical to `tables_postgres.sql` in columns and keys, but one index (`IDX_QRTZ_T_J`) short; an unreleased Liquibase-related primary-key change (#1489) is on `main`

|Commit validation
|n/a
|The 2.5.2 source retries a failed `COMMIT` by checking whether the acquisition or fire really went through (`TransactionValidator` in `acquireNextTriggers` and `triggersFired`); not exercised here

|Spring Boot 3.5.16
|same Quartz 2.5.2, same pgJDBC 42.7.13
|only package names, the migration-tool starters and Spring Framework 6.2.19 differ; not run on 3.5
