A schedule is code that nobody watches run: the cron expression that is wrong by one day, the job that needs the scheduler's thread to finish before it is visible, the JDBC table that is missing one column on Oracle, the second node that fires the same job again, all of them are found by the customer on the day after the release. [[bookshelf-code]]
== The code under test

The *Bookshelf* service of the section has a nightly overdue-loan reminder and a weekly statistics report. For testing, the reminder job has three collaborators, all injected through its constructor: a `LoanService` that finds overdue loans, a `ReminderSender` that sends one reminder and a `Clock` that says what "today" is. The job data entry `maxReminders` caps one run and reaches the job through a setter, the standard `QuartzJobBean` mechanism of xref:backend/scheduling/getting-started-with-spring-boot.adoc[Getting Started with Spring Boot].

.OverdueReminderJob.java (src/main)
[source,java]
----
package bookshelf;

import java.time.Clock;
import java.time.LocalDate;
import java.time.temporal.ChronoUnit;
import java.util.List;

import org.quartz.DisallowConcurrentExecution;
import org.quartz.JobExecutionContext;
import org.springframework.scheduling.quartz.QuartzJobBean;

@DisallowConcurrentExecution
public class OverdueReminderJob extends QuartzJobBean {

    private final LoanService loans;
    private final ReminderSender sender;
    private final Clock clock;

    private int maxReminders = 100;          // set from the JobDataMap entry "maxReminders"

    public OverdueReminderJob(LoanService loans, ReminderSender sender, Clock clock) {
        this.loans = loans;
        this.sender = sender;
        this.clock = clock;
    }

    public void setMaxReminders(int maxReminders) {
        this.maxReminders = maxReminders;
    }

    @Override
    protected void executeInternal(JobExecutionContext context) {
        LocalDate today = LocalDate.now(clock);
        List<OverdueLoan> overdue = loans.overdueBefore(today);
        int sent = 0;
        for (OverdueLoan loan : overdue) {
            if (sent == maxReminders) {
                break;
            }
            sender.send(loan.memberId(), loan.loanId(), ChronoUnit.DAYS.between(loan.dueDate(), today));
            sent++;
        }
        context.setResult(sent);
    }
}
----
Source: https://docs.spring.io/spring-framework/docs/7.0.x/javadoc-api/org/springframework/scheduling/quartz/QuartzJobBean.html[Spring Framework API: QuartzJobBean]

.BookshelfTriggers.java (src/main)
[source,java]

package bookshelf;

import java.time.ZoneId;
import java.util.TimeZone;

import org.quartz.CronScheduleBuilder;
import org.quartz.JobDetail;
import org.quartz.Trigger;
import org.quartz.TriggerBuilder;

/** Trigger definitions as plain static methods, so tests can build them without Spring. */
public final class BookshelfTriggers {
    private BookshelfTriggers() { }

    public static Trigger overdueReminders(JobDetail job, String cron, ZoneId zone) {
        return TriggerBuilder.newTrigger().forJob(job).withIdentity("overdueLoanRemindersTrigger", "bookshelf")
                .withSchedule(CronScheduleBuilder.cronSchedule(cron)
                        .inTimeZone(TimeZone.getTimeZone(zone))
                        .withMisfireHandlingInstructionFireAndProceed())
                .build();
    }

    public static Trigger weeklyStatistics(JobDetail job, ZoneId zone) {
        return TriggerBuilder.newTrigger().forJob(job).withIdentity("weeklyStatisticsTrigger", "bookshelf")
                .withSchedule(CronScheduleBuilder.cronSchedule("0 0 6 ? * MON")
                        .inTimeZone(TimeZone.getTimeZone(zone)))
                .build();
    }
}

[[unit-tests]]
== Unit-testing job logic without a scheduler

A job is a class with one method. If the logic sits in `executeInternal` and its collaborators are constructor parameters, a test needs a mock of `JobExecutionContext` and nothing else: no scheduler, no Spring, no thread pool. `executeInternal` is `protected` in `QuartzJobBean`, which is reachable from a test in the same package; the public `execute` is `final` and does one more thing before it calls `executeInternal`: it copies the scheduler context and the merged `JobDataMap` onto the job's setters. A second test therefore calls `execute` to check that binding, and has to stub `getScheduler()`, `getContext()` and `getMergedJobDataMap()` for it.

.OverdueReminderJobTest.java
[source,java]
----
package bookshelf;

import static org.assertj.core.api.Assertions.assertThat;
import static org.mockito.ArgumentMatchers.anyLong;
import static org.mockito.Mockito.mock;
import static org.mockito.Mockito.never;
import static org.mockito.Mockito.verify;
import static org.mockito.Mockito.when;

import java.time.Clock;
import java.time.Instant;
import java.time.LocalDate;
import java.time.ZoneId;
import java.util.List;

import org.junit.jupiter.api.Test;
import org.quartz.JobDataMap;
import org.quartz.JobExecutionContext;
import org.quartz.Scheduler;
import org.quartz.SchedulerContext;

class OverdueReminderJobTest {

    private static final ZoneId MADRID = ZoneId.of("Europe/Madrid");
    // 5 October 2026, 02:00 in Madrid: the moment the real trigger fires
    private static final Clock CLOCK = Clock.fixed(Instant.parse("2026-10-05T00:00:00Z"), MADRID);

    private final LoanService loans = mock(LoanService.class);
    private final ReminderSender sender = mock(ReminderSender.class);
    private final OverdueReminderJob job = new OverdueReminderJob(loans, sender, CLOCK);

    @Test
    void remindsEveryMemberWithAnOverdueLoan() {
        LocalDate today = LocalDate.of(2026, 10, 5);
        when(loans.overdueBefore(today)).thenReturn(List.of(
                new OverdueLoan(1, 10, today.minusDays(3)), new OverdueLoan(2, 11, today.minusDays(1))));
        JobExecutionContext context = mock(JobExecutionContext.class);

        job.executeInternal(context);                 // protected, reachable from the same package

        verify(sender).send(10, 1, 3);
        verify(sender).send(11, 2, 1);
        verify(context).setResult(2);
    }

    @Test
    void jobDataMapEntryReachesTheSetterAndCapsTheRun() throws Exception {
        LocalDate today = LocalDate.of(2026, 10, 5);
        when(loans.overdueBefore(today)).thenReturn(List.of(
                new OverdueLoan(1, 10, today.minusDays(3)), new OverdueLoan(2, 11, today.minusDays(1))));
        JobExecutionContext context = mock(JobExecutionContext.class);
        Scheduler scheduler = mock(Scheduler.class);
        when(context.getScheduler()).thenReturn(scheduler);
        when(scheduler.getContext()).thenReturn(new SchedulerContext());
        when(context.getMergedJobDataMap()).thenReturn(new JobDataMap(java.util.Map.of("maxReminders", 1)));

        job.execute(context);                         // the public entry point: binds the data, then executeInternal

        verify(sender).send(10, 1, 3);
        verify(sender, never()).send(11, 2, 1);
        verify(context).setResult(1);
    }

    @Test
    void nothingOverdueSendsNothing() {
        when(loans.overdueBefore(LocalDate.of(2026, 10, 5))).thenReturn(List.of());
        JobExecutionContext context = mock(JobExecutionContext.class);

        job.executeInternal(context);

        verify(sender, never()).send(anyLong(), anyLong(), anyLong());
        assertThat(CLOCK.instant()).isEqualTo(Instant.parse("2026-10-05T00:00:00Z"));
    }

    @Test
    void executeNeedsTheSchedulerOfTheContextToBeStubbed() {
        JobExecutionContext context = mock(JobExecutionContext.class);      // getScheduler() returns null
        org.junit.jupiter.api.Assertions.assertThrows(NullPointerException.class, () -> job.execute(context));
    }
}
----
Source: https://docs.spring.io/spring-framework/docs/7.0.x/javadoc-api/org/springframework/scheduling/quartz/QuartzJobBean.html[Spring Framework API: QuartzJobBean] and https://site.mockito.org/[Mockito]

All four tests passed (0.2 s). The fourth test, `executeNeedsTheSchedulerOfTheContextToBeStubbed`, records a measured trap: calling `execute` with a bare mock fails with a `NullPointerException`, because `QuartzJobBean.execute` calls `context.getScheduler().getContext()` and a mock returns `null` for `getScheduler()`. Calling `executeInternal` avoids the trap, at the price of not testing the setter binding, which is why the page has both.

=== Deterministic time with an injectable Clock

The job asks the `Clock` for "today" (`LocalDate.now(clock)`), and the test hands it `Clock.fixed(Instant.parse("2026-10-05T00:00:00Z"), MADRID)`, so that "three days late" is 3 on any day the test runs. That is the whole technique: a `java.time.Clock` is a constructor parameter, production gets `Clock.system(zone)`, the test gets a fixed or a hand-moved one. Three limits are worth knowing:

* *Quartz itself does not use your clock.* In 2.5.2 the scheduler thread reads `System.currentTimeMillis()` (`QuartzSchedulerThread`), and the `org.quartz.spi.TimeBroker` interface that looks like a hook is documented as "not currently used in the Quartz code base". A test cannot make Quartz believe it is 02:00; it can only (a) test the job with a fixed clock, as above, and (b) test the trigger's arithmetic without waiting, as in the next section.
* The fixed clock has to be the one the job reads. A job that calls `LocalDate.now()` or `Instant.now()` directly cannot be made deterministic; this is why `OverdueReminderJob` takes the clock in the constructor.
* For `@Scheduled`, Spring's `ThreadPoolTaskScheduler` has a `setClock(Clock)`, but the delays are still waited out by a real executor; the practical test is the one at the end of this page, which calls the method directly and tests the lock separately.

[[trigger-tests]]
== Testing trigger definitions

Whether a cron expression means what the ticket said is arithmetic, and Quartz can do it without starting anything. `TriggerUtils.computeFireTimes(OperableTrigger, Calendar, int)` clones the trigger and returns its next fire times; `computeFireTimesBetween` does the same for a date range; a `CronExpression` answers `getNextValidTimeAfter` on its own. Two details matter for a deterministic test. First, the builder defaults the start time to "now", so the expected dates would move every day: a test pins the start with `trigger.getTriggerBuilder().startAt(start).build()`. Second, `computeFireTimes` needs an `OperableTrigger`, the SPI interface that every trigger implementation also implements; the test casts the built trigger to it, and passes `null` for the calendar unless it tests one.

.BookshelfTriggersTest.java
[source,java]
----
package bookshelf;

import static org.assertj.core.api.Assertions.assertThat;

import java.time.Duration;
import java.time.Instant;
import java.time.ZoneId;
import java.time.ZonedDateTime;
import java.util.Date;
import java.util.List;

import org.junit.jupiter.api.Test;
import org.quartz.CronExpression;
import org.quartz.CronTrigger;
import org.quartz.JobBuilder;
import org.quartz.JobDetail;
import org.quartz.Trigger;
import org.quartz.TriggerUtils;
import org.quartz.impl.calendar.HolidayCalendar;
import org.quartz.spi.OperableTrigger;

class BookshelfTriggersTest {

    private static final ZoneId MADRID = ZoneId.of("Europe/Madrid");
    private final JobDetail job = JobBuilder.newJob(WeeklyStatisticsJob.class).withIdentity("weeklyStatistics", "bookshelf")
            .storeDurably().build();

    private static Date at(int year, int month, int day, int hour, int minute) {
        return Date.from(ZonedDateTime.of(year, month, day, hour, minute, 0, 0, MADRID).toInstant());
    }

All seven tests passed (0.04 s) on the first run. What they pin down, each of them a real incident when it goes wrong:

* The weekly report fires on Mondays at 06:00 Madrid time, and the fire time follows the clock change rather than the UTC offset: 06:00 is 04:00Z until 25 October 2026 and 05:00Z after it (the assertions use `2026-10-26T05:00:00Z`).
* A `HolidayCalendar` removes a Monday from the list of fire times; the calendar is passed as the second argument of `computeFireTimes`.
* The reminder trigger is a `CronTrigger` in `Europe/Madrid` whose misfire instruction is `MISFIRE_INSTRUCTION_FIRE_ONCE_NOW`, which is what `withMisfireHandlingInstructionFireAndProceed()` selects.
* `CronExpression.isValidExpression` rejects `0 0 2 * * *` (both day fields set) before the application is started; this is the cheapest guard against a typo in a YAML property.
* On the spring-forward day, Sunday 29 March 2026, `0 0 2 * * ?` in Madrid does not fire: the fire times from 27 March are the 28th, the 30th, the 31st and 1 April, all at 02:00. That is the measured behaviour on 2.5.2; the cron page explains the rule and the fall-back day.

The DST test is the pattern for every "what does this do on the night the clocks change" question: write the date range into the test, run it, read what Quartz did, and then assert it, so that a Quartz upgrade that changes it is noticed.

[[spring-tests]]
== Testing the Spring wiring with @SpringBootTest

`@SpringBootTest` starts the real application with Boot's Quartz auto-configuration, the real YAML and the real `JobDetail` and `Trigger` beans. With the default memory store this costs a few seconds and needs no database. Three techniques make it a good test instead of a slow one.

*Start the scheduler stopped.* `spring.quartz.auto-startup=false` makes Boot register every job and trigger and leave the scheduler in standby, so nothing fires behind the test's back. A test asserts on what was registered, and starts the scheduler (`scheduler.start()`) only for the test that needs jobs to run. Measured on 4.1.1: `triggerJob` on a stopped scheduler does *not* run the job (the first test below waits two seconds and asserts that the mock was never called), the job waits in the store, and it runs as soon as the scheduler starts.

*Replace the collaborators with `@MockitoBean`.* Boot creates job instances at fire time through the application context (the `SpringBeanJobFactory` of xref:backend/scheduling/getting-started-with-spring-boot.adoc[Getting Started with Spring Boot]), so a bean that the test replaces is the bean the job receives. `@MockitoBean` is Spring Framework's annotation (`org.springframework.test.context.bean.override.mockito.MockitoBean`); it replaced Boot's own `@MockBean`, which is gone in Boot 4.

*Wait for the effect with Awaitility, not `Thread.sleep`.* The job runs on a Quartz worker thread, so the test polls an assertion until it holds or a timeout expires; `await().atMost(...).untilAsserted(...)` is the form, and `await().during(...)` asserts that something stays true for a period, which is how the first test proves that nothing ran. The official smoke test of Boot's Quartz sample waits the same way (the page on xref:backend/scheduling/getting-started-with-spring-boot.adoc[Getting Started with Spring Boot] shows it).

.BookshelfSchedulerTest.java
[source,java]
----
package bookshelf;

import static org.assertj.core.api.Assertions.assertThat;
import static org.awaitility.Awaitility.await;
import static org.mockito.ArgumentMatchers.anyLong;
import static org.mockito.Mockito.never;
import static org.mockito.Mockito.verify;

import java.time.Duration;

import org.junit.jupiter.api.Test;
import org.quartz.JobDataMap;
import org.quartz.JobKey;
import org.quartz.Scheduler;
import org.quartz.SchedulerException;
import org.quartz.Trigger.TriggerState;
import org.quartz.TriggerKey;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.test.context.bean.override.mockito.MockitoBean;

@SpringBootTest(properties = {
        "spring.quartz.auto-startup=false",            // register everything, fire nothing until the test says so
        "bookshelf.reminders.max-per-run=5"
})
class BookshelfSchedulerTest {

    private static final JobKey REMINDERS = JobKey.jobKey("overdueLoanReminders", "bookshelf");

    @Autowired
    Scheduler scheduler;

    @MockitoBean
    ReminderSender sender;                             // replaces the real bean; the job gets the mock injected

    @Test
    void theScheduleIsRegisteredButTheSchedulerIsInStandby() throws SchedulerException {
        assertThat(scheduler.isInStandbyMode()).isTrue();
        assertThat(scheduler.checkExists(REMINDERS)).isTrue();
        assertThat(scheduler.getJobDetail(REMINDERS).getJobDataMap().getInt("maxReminders")).isEqualTo(5);
        assertThat(scheduler.getTriggerState(TriggerKey.triggerKey("overdueLoanRemindersTrigger", "bookshelf")))
                .isEqualTo(TriggerState.NORMAL);
    }

    @Test
    void aTriggeredJobWaitsInStandbyAndRunsOnceTheSchedulerStarts() throws SchedulerException {
        scheduler.triggerJob(REMINDERS);

        // nothing runs while the scheduler is in standby
        await().during(Duration.ofSeconds(2)).atMost(Duration.ofSeconds(3))
                .untilAsserted(() -> verify(sender, never()).send(anyLong(), anyLong(), anyLong()));

        scheduler.start();
        try {
            await().atMost(Duration.ofSeconds(5)).untilAsserted(() -> verify(sender).send(10, 1, 3));
        } finally {
            scheduler.standby();                       // leave the shared context the way the next test found it
        }
    }

    @Test
    void jobDataPassedToTriggerJobOverridesTheStoredValueForThatRunOnly() throws SchedulerException {
        scheduler.start();
        try {
            scheduler.triggerJob(REMINDERS, new JobDataMap(java.util.Map.of("maxReminders", 1)));

            await().atMost(Duration.ofSeconds(5)).untilAsserted(() -> verify(sender).send(10, 1, 3));
            verify(sender, never()).send(11, 2, 1);
            assertThat(scheduler.getJobDetail(REMINDERS).getJobDataMap().getInt("maxReminders")).isEqualTo(5);
        } finally {
            scheduler.standby();
        }
    }
}

The third test shows the other way to run a job on demand: `scheduler.triggerJob(JobKey, JobDataMap)` with a data map that overrides `maxReminders` for that run only; the stored job data still says 5 afterwards. Each test that starts the scheduler stops it again in a `finally` block, because the Spring context (and its scheduler) is shared by the test methods of the class and, as the pitfalls table shows, by other classes with the same configuration.

*Other ways to know that a job ran.* A mock is the best evidence when the job has a collaborator whose call is the effect. When it has none, a job listener registered on the scheduler (`scheduler.getListenerManager().addJobListener(...)`, with `org.quartz.listeners.JobListenerSupport` as a base class) can count down a `CountDownLatch` in `jobWasExecuted`, as the database test below does, and a global listener registered through a `SchedulerFactoryBeanCustomizer` bean can record every execution, as the cluster test does. Listeners are covered on xref:backend/scheduling/listeners-and-plugins.adoc[Listeners & Plugins].

[[jdbc-tests]]
== A Testcontainers test for the JDBC store, parameterized over the databases

A memory-store test cannot find the bugs that matter on a database: a column type, a missing delegate, a script that fails on an empty schema, a `JobDataMap` that cannot be serialized. The test below runs the same scenario on every database page of the section. A JUnit `@ParameterizedTest` with an `@EnumSource` receives one enum constant per database; the constant carries the container and the two settings that differ between databases, the Quartz delegate and the schema script. The scenario starts a container, starts the Bookshelf application against it with the JDBC store (the `always` schema mode is acceptable in a test, because the container is empty and thrown away), checks that the jobs and triggers are in the tables, runs a job from the stored definition, and then starts a second application with `initialize-schema=never` to prove that the stored schedule is found again.

Credentials are the ones the container generates (`getJdbcUrl()`, `getUsername()`, `getPassword()`), passed to the application as `--` arguments of `run`, so nothing is typed into the test. Arguments are used instead of the builder's `properties(...)` because those are *default* properties, which `application.yml` overrides.

.JdbcJobStoreIT.java
[source,java]
----
package bookshelf;

import static org.assertj.core.api.Assertions.assertThat;

import java.util.ArrayList;
import java.util.List;
import java.util.concurrent.CountDownLatch;
import java.util.concurrent.TimeUnit;
import java.util.function.Supplier;

import javax.sql.DataSource;

import org.junit.jupiter.params.ParameterizedTest;
import org.junit.jupiter.params.provider.EnumSource;
import org.quartz.JobExecutionContext;
import org.quartz.JobExecutionException;
import org.quartz.JobKey;
import org.quartz.Scheduler;
import org.quartz.listeners.JobListenerSupport;
import org.springframework.boot.WebApplicationType;
import org.springframework.boot.builder.SpringApplicationBuilder;
import org.springframework.context.ConfigurableApplicationContext;
import org.springframework.jdbc.core.JdbcTemplate;
import org.testcontainers.containers.JdbcDatabaseContainer;
import org.testcontainers.mariadb.MariaDBContainer;
import org.testcontainers.mssqlserver.MSSQLServerContainer;
import org.testcontainers.mysql.MySQLContainer;
import org.testcontainers.oracle.OracleContainer;
import org.testcontainers.postgresql.PostgreSQLContainer;

class JdbcJobStoreIT {

    private static final String QUARTZ = "spring.quartz.properties.org.quartz.";
    private static final JobKey REMINDERS = JobKey.jobKey("overdueLoanReminders", "bookshelf");

    /** One row per database page of the section: the container and the two settings that differ. */
    enum StoreDatabase {
        POSTGRESQL(() -> new PostgreSQLContainer("postgres:17"), "org.quartz.impl.jdbcjobstore.PostgreSQLDelegate", null, false),
        MYSQL(() -> new MySQLContainer("mysql:9"), null, null, false),
        MARIADB(() -> new MariaDBContainer("mariadb:11"), null, null, false),
        ORACLE(() -> new OracleContainer("gvenzl/oracle-free:slim-faststart"), null,
                "classpath:org/quartz/impl/jdbcjobstore/tables_oracle23.sql", true),
        SQL_SERVER(() -> new MSSQLServerContainer("mcr.microsoft.com/mssql/server:2022-latest").acceptLicense(),
                "org.quartz.impl.jdbcjobstore.MSSQLDelegate", "classpath:tables_sqlServer_boot.sql", false);

        final Supplier<JdbcDatabaseContainer<?>> container;
        final String delegate;                  // null = Quartz's StdJDBCDelegate
        final String schemaScript;              // null = the script Boot picks for the platform
        final boolean tolerateScriptErrors;     // the Oracle script starts with DELETE/DROP of tables that do not exist yet

        StoreDatabase(Supplier<JdbcDatabaseContainer<?>> container, String delegate, String schemaScript, boolean tolerate) {
            this.container = container;
            this.delegate = delegate;
            this.schemaScript = schemaScript;
            this.tolerateScriptErrors = tolerate;
        }
    }

    private ConfigurableApplicationContext start(StoreDatabase db, JdbcDatabaseContainer<?> c, String initializeSchema) {
        List<String> props = new ArrayList<>(List.of(
                "spring.datasource.url=" + c.getJdbcUrl(),
                "spring.datasource.username=" + c.getUsername(),
                "spring.datasource.password=" + c.getPassword(),         // supplied by the container, never typed by us
                "spring.quartz.job-store-type=jdbc",
                "spring.quartz.jdbc.initialize-schema=" + initializeSchema,
                "spring.quartz.scheduler-name=BookshelfTest"));
        if (!db.tolerateScriptErrors) {
            props.add("spring.quartz.jdbc.continue-on-error=false");     // make a broken script fail the test
        }
        if (db.delegate != null) {
            props.add(QUARTZ + "jobStore.driverDelegateClass=" + db.delegate);
        }
        if (db.schemaScript != null) {
            props.add("spring.quartz.jdbc.schema=" + db.schemaScript);
        }
        // run(args) beats application.yml; properties(...) on the builder would not
        return new SpringApplicationBuilder(BookshelfApplication.class).web(WebApplicationType.NONE)
                .run(props.stream().map(p -> "--" + p).toArray(String[]::new));
    }

    @ParameterizedTest(name = "{0}")
    @EnumSource(StoreDatabase.class)
    void theBookshelfScheduleLivesInTheDatabaseAndSurvivesARestart(StoreDatabase db) throws Exception {
        try (JdbcDatabaseContainer<?> database = db.container.get()) {
            database.start();

            try (ConfigurableApplicationContext first = start(db, database, "always")) {
                Scheduler scheduler = first.getBean(Scheduler.class);
                assertThat(scheduler.getMetaData().isJobStoreSupportsPersistence()).isTrue();

                JdbcTemplate jdbc = new JdbcTemplate(first.getBean(DataSource.class));
                assertThat(jdbc.queryForObject("SELECT COUNT(*) FROM QRTZ_JOB_DETAILS", Integer.class)).isEqualTo(2);
                assertThat(jdbc.queryForObject("SELECT COUNT(*) FROM QRTZ_CRON_TRIGGERS", Integer.class)).isEqualTo(2);

                CountDownLatch executed = new CountDownLatch(1);
                scheduler.getListenerManager().addJobListener(new JobListenerSupport() {
                    @Override
                    public String getName() {
                        return "test-latch";
                    }

                    @Override
                    public void jobWasExecuted(JobExecutionContext context, JobExecutionException exception) {
                        executed.countDown();
                    }
                });
                scheduler.triggerJob(REMINDERS);                         // a job really runs from the stored definition
                assertThat(executed.await(15, TimeUnit.SECONDS)).isTrue();
            }

            // a second application start must find the jobs without creating the tables again
            try (ConfigurableApplicationContext second = start(db, database, "never")) {
                assertThat(second.getBean(Scheduler.class).checkExists(REMINDERS)).isTrue();
            }
        }
    }
}

== A two-scheduler cluster test

The questions a cluster test answers are two: does each fire time run on exactly one node, and does a surviving node run the job of a node that died. Both can be answered in automation, with one design decision that the clustering page already explains: the two schedulers may live in one JVM as long as nobody has to be killed, because Spring registers the data source under the scheduler name and both nodes use the same database; the node that has to be killed with `kill -9` must be its own JVM.

The test needs a way to see who ran what. A global `JobListener` registered through a `SchedulerFactoryBeanCustomizer` bean (Boot registers no listener beans by itself) appends an `Execution` for every job that is about to run: the instance id of the scheduler, the job name, the scheduled fire time and whether Quartz says it is a recovery run.

.Executions.java (src/test): a global listener that records every execution
[source,java]
----
package bookshelf;

import java.time.Instant;
import java.util.List;
import java.util.concurrent.CopyOnWriteArrayList;

import org.quartz.JobExecutionContext;
import org.quartz.listeners.JobListenerSupport;
import org.springframework.boot.quartz.autoconfigure.SchedulerFactoryBeanCustomizer;
import org.springframework.boot.test.context.TestConfiguration;
import org.springframework.context.annotation.Bean;

/** Records which node started which scheduled fire time; registered as a global job listener. */
public final class Executions {

    public record Execution(String node, String job, Instant scheduledFireTime, boolean recovering) { }

    public static final List<Execution> ALL = new CopyOnWriteArrayList<>();

    private Executions() { }

    @TestConfiguration(proxyBeanMethods = false)
    public static class Recording {
        @Bean
        SchedulerFactoryBeanCustomizer executionRecorder() {
            return factory -> factory.setGlobalJobListeners(new JobListenerSupport() {
                @Override
                public String getName() {
                    return "execution-recorder";
                }

                @Override
                public void jobToBeExecuted(JobExecutionContext context) {
                    try {
                        ALL.add(new Execution(context.getScheduler().getSchedulerInstanceId(),
                                context.getJobDetail().getKey().getName(),
                                context.getScheduledFireTime().toInstant(), context.isRecovering()));
                    } catch (Exception e) {
                        throw new IllegalStateException(e);
                    }
                }
            });
        }
    }
}

package bookshelf;

import org.quartz.JobExecutionContext;
import org.springframework.scheduling.quartz.QuartzJobBean;

/** A long job that asks Quartz to run it again if its node dies; the second run is quick. */
public class SlowReportJob extends QuartzJobBean {
    @Override
    protected void executeInternal(JobExecutionContext context) {
        System.out.println("SLOW-STARTED recovering=" + context.isRecovering());
        System.out.flush();
        try {
            Thread.sleep(context.isRecovering() ? 100 : 60_000);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
    }
}

Reading them correctly matters. In the first test five consecutive fire times each ran on exactly one node, which is the assertion; that all five ran on the *same* node is not a bug of the test but the behaviour documented on the clustering page: Quartz does not balance load, the first node to acquire a trigger keeps getting it. A test must therefore never assert that work is shared. In the second test the survivor started the job again with `recovering=true` 10.60 seconds after the `kill -9`, inside the window the clustering page derives from the check-in interval (the 7.5 s grace plus the check-in cycles); a fail-over test needs a timeout comfortably above that window, here 60 s, and a short `clusterCheckinInterval` of its own, here 2 s. The survivor is put in standby before the victim starts so that it cannot take the job first, and is started right after the kill.

Rules the cluster tests of this section follow, all of them learned from runs:

* *One scheduler name per test class, or a database per class.* All nodes of one test must share the scheduler name, but a different test class that uses the same name against the same tables would see this one's rows; a non-clustered scheduler with that name would delete the fired-trigger rows of running nodes (see xref:backend/scheduling/clustering.adoc[Clustering]). With a container per class (`static` `@Container`) the problem does not arise.
* *Build cluster nodes by hand,* as `ClusterIT` does with `SpringApplicationBuilder`, rather than as a shared `@SpringBootTest` context: a cluster node is not something to leave in the test context cache (a `@SpringBootTest` class that must start one marks itself `@DirtiesContext`).
* *Only the first node gets `initialize-schema=always`;* the others use `never`, otherwise the second node's script drops the tables under the first.
* *Never assert how the work was shared,* only that no fire time ran twice and that recovery happened.
* The victim JVM is started with the `java.class.path` of the test JVM; the test project sets Surefire's `useManifestOnlyJar` to `false` so that this property lists the real classpath entries.

[[shedlock-tests]]
== Testing @Scheduled with ShedLock, for comparison

The standard alternative to Quartz clustering, `@Scheduled` plus ShedLock, is covered on xref:backend/springboot/scheduling-and-shedlock.adoc[Scheduling & ShedLock] and compared in xref:backend/scheduling/standard-scheduling-vs-quartz.adoc[Standard Scheduling vs Quartz]. Its tests are lighter, because there is no scheduler to configure, and they split in three: the method is plain Java, the lock is a `LockProvider` that can be exercised directly, and the combination is two application contexts that share one lock table.

.RetentionCleanup.java (src/main): a @Scheduled method guarded by ShedLock
[source,java]
----
package bookshelf;

import java.time.Instant;
import java.util.List;
import java.util.concurrent.CopyOnWriteArrayList;

import net.javacrumbs.shedlock.core.LockAssert;
import net.javacrumbs.shedlock.spring.annotation.SchedulerLock;
import org.springframework.scheduling.annotation.Scheduled;
import org.springframework.stereotype.Component;

/** The standard-scheduling counterpart: @Scheduled guarded by ShedLock. */
@Component
public class RetentionCleanup {

    private final List<Instant> runs = new CopyOnWriteArrayList<>();

    @Scheduled(fixedRateString = "${bookshelf.retention.rate:PT1S}")
    @SchedulerLock(name = "retentionCleanup", lockAtMostFor = "PT30S", lockAtLeastFor = "PT3S")
    public void purgeOldLoans() {
        LockAssert.assertLocked();      // fails if the method is ever called without the lock
        runs.add(Instant.now());
    }

    public List<Instant> runs() {
        return runs;
    }
}
----
Source: https://github.com/lukas-krecan/ShedLock[ShedLock]

`LockAssert.assertLocked()` makes the method fail if it is ever called without the lock, which is its value in production and its nuisance in a unit test; `LockAssert.TestHelper.makeAllAssertsPass(true)` switches the assertion off for a test, and `makeAllAssertsPass(false)` puts it back.

                        + "locked_at TIMESTAMP(3) NOT NULL, locked_by VARCHAR(255) NOT NULL, PRIMARY KEY (name))");

Source: https://docs.spring.io/spring-framework/reference/testing/testcontext-framework/ctx-management/context-pausing.html[Spring Framework: Context Pausing]

Surefire ran the classes in name order (`junit-platform.properties` sets `junit.jupiter.testclass.order.default` to `org.junit.jupiter.api.ClassOrderer$ClassName`). With the default settings `LeakBTest` passed: the scheduler of `LeakATest`, which fires every second, was `started=true standby=true shutdown=false` and its executed-jobs counter stayed at `1 -> 1` over three seconds, because Spring Framework paused the inactive cached context when the next class used a different one. With `-Dspring.test.context.cache.pause=never` the same measurement printed `standby=false` and `jobsExecuted 3 -> 6`: the scheduler of a finished test class kept firing for the rest of the build. The property is read by Spring's `SpringProperties`, so it can also be set in a `spring.properties` file on the test classpath.

The second trap is the transaction of the test method. `@Transactional` on a test method wraps the method in a transaction that is rolled back at the end, and a Quartz worker thread is not part of it:

.TransactionalTestTest.java
[source,java]
----
package bookshelf;

import static org.assertj.core.api.Assertions.assertThat;
import static org.awaitility.Awaitility.await;

import java.time.Duration;
import java.util.concurrent.atomic.AtomicInteger;

import org.junit.jupiter.api.Test;
import org.quartz.JobBuilder;
import org.quartz.JobExecutionContext;
import org.quartz.Scheduler;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.jdbc.core.JdbcTemplate;
import org.springframework.scheduling.quartz.QuartzJobBean;
import org.springframework.transaction.annotation.Transactional;

@SpringBootTest
class TransactionalTestTest {

    static final AtomicInteger SEEN_BY_JOB = new AtomicInteger(-1);

    public static class CountLoansJob extends QuartzJobBean {
        private final JdbcTemplate jdbc;
        public CountLoansJob(JdbcTemplate jdbc) { this.jdbc = jdbc; }
        @Override
        protected void executeInternal(JobExecutionContext context) {
            SEEN_BY_JOB.set(jdbc.queryForObject("SELECT COUNT(*) FROM loan_probe", Integer.class));
        }
    }

    @Autowired Scheduler scheduler;
    @Autowired JdbcTemplate jdbc;

    @Test
    @Transactional
    void aJobDoesNotSeeTheRowsOfTheTestTransaction() throws Exception {
        jdbc.execute("CREATE TABLE IF NOT EXISTS loan_probe(id INT)");
        jdbc.execute("DELETE FROM loan_probe");
        jdbc.update("INSERT INTO loan_probe VALUES (1)");          // uncommitted: rolled back when the test ends
        assertThat(jdbc.queryForObject("SELECT COUNT(*) FROM loan_probe", Integer.class)).isEqualTo(1);

        scheduler.addJob(JobBuilder.newJob(CountLoansJob.class).withIdentity("probe", "bookshelf").storeDurably().build(), true);
        scheduler.triggerJob(org.quartz.JobKey.jobKey("probe", "bookshelf"));

        await().atMost(Duration.ofSeconds(5)).until(() -> SEEN_BY_JOB.get() >= 0);
        System.out.println("TX test sees 1 row, job sees " + SEEN_BY_JOB.get());
        assertThat(SEEN_BY_JOB.get()).isZero();
    }
}
----
Source: https://docs.spring.io/spring-framework/reference/testing/testcontext-framework.html[Spring Framework: TestContext Framework]

The test passed with the output `TX test sees 1 row, job sees 0`: the test thread read its own uncommitted row, the job, on its own connection and transaction, read none. A job test that prepares data therefore commits it first (a `TransactionTemplate`, or no `@Transactional` on the test) and removes it afterwards.

[[pitfalls]]
== Pitfalls

.Testing pitfalls and what actually happens (measured on Quartz 2.5.2, Boot 4.1.1, Spring Framework 7.0.9)
[cols="3,6,5",options="header"]
|===
|Mistake |What happens |What to do

|`triggerJob` on a scheduler started with `spring.quartz.auto-startup=false`
|Nothing runs: the test waited two seconds and the mock was never called; the job runs as soon as the scheduler is started
|Call `scheduler.start()` in the test that needs execution, and stop it again

|Calling `QuartzJobBean.execute` with a bare mock context
|`NullPointerException`, because `execute` reads `context.getScheduler().getContext()`
|Call `executeInternal` for logic, or stub `getScheduler()`, `getContext()` and `getMergedJobDataMap()` to test the setter binding

|Building a trigger in a test and asserting fire times without pinning the start
|The builder starts the trigger "now", so the expected dates are right only on the day the test was written
|`trigger.getTriggerBuilder().startAt(fixedDate).build()` before `computeFireTimes`

|Expecting the cached context of an earlier test class to keep running
|Spring Framework 7.0.3 and later pause an inactive cached context when the next test uses a different one: after a class with a one-second cron finished, its scheduler was in standby and its job-executed counter did not move over a three-second wait (1 to 1)
|Rely on it, but know that with `spring.test.context.cache.pause=never` (a system property or `spring.properties` entry) the same scheduler kept running (counter 3 to 6 in three seconds) and fires into your other tests

|A `@Transactional` test method that inserts rows and then triggers a job
|The job runs on a Quartz thread in its own transaction and does not see the uncommitted rows: the test saw 1 row and the job counted 0
|Commit the data before triggering the job (a `TransactionTemplate`, or no `@Transactional` on the test), and clean up in `@AfterEach`

|Asserting that the nodes of a cluster shared the work
|Quartz is first come, first served: five consecutive fire times all ran on the first node
|Assert that each fire time ran once, not where

|Running the node to be killed in the test JVM
|Nothing can be killed without killing the test; a clean `close()` is not a crash and leaves nothing to recover
|Start the victim as a second JVM with `ProcessBuilder` and `destroyForcibly`

|A fail-over timeout of a few seconds
|Detection takes the 7.5 s grace plus the check-in cycles; the measured recovery with a 2 s interval was 10.60 s
|Wait up to a minute with Awaitility, and shorten `clusterCheckinInterval` in tests only

|Passing test properties with `SpringApplicationBuilder.properties(...)` while `application.yml` sets the same key
|The builder's properties are default properties with the lowest precedence, so the YAML wins and the test silently runs on the memory store (`isJobStoreSupportsPersistence` was false)
|Pass `run("--key=value")` arguments, or use `@SpringBootTest(properties = ...)`

|Leaving Boot's `continue-on-error=true` in a schema test
|A script that fails halfway is skipped and the failure shows up later as a missing table
|Set `spring.quartz.jdbc.continue-on-error=false` and tolerate errors only where the script is known to fail harmlessly (Oracle)

|`@MockBean` or `@SpyBean` on Boot 4
|The annotations are gone from `spring-boot-test` 4.1.1; the code does not compile
|`@MockitoBean` and `@MockitoSpyBean` from `org.springframework.test.context.bean.override.mockito`

|`thread.sleep(5000)` instead of Awaitility
|The test is slow when the job is quick and flaky when the machine is busy
|`await().atMost(...).untilAsserted(...)`, and `during(...)` to prove that something does not happen

|Passing a real password through a command line or a checked-in file
|Visible in the process list, in logs and in version control
|Use the container's generated credentials, as the tests above do, or an environment variable; never a real secret in a test

|Expecting `spring-boot-starter-quartz-test` to add test utilities
|The JAR contains no classes; the starter only brings `spring-boot-starter-quartz` and `spring-boot-starter-test`
|Use it as a naming convention, and write the helpers (listener, recorder) yourself
|===
Source: this page's measured results, https://docs.spring.io/spring-framework/reference/testing/testcontext-framework/ctx-management/context-pausing.html[Spring Framework: Context Pausing] and https://www.quartz-scheduler.org/documentation/quartz-2.5.x/best-practices.html[Quartz Best Practices].

== What changed since Spring Boot 3.5

Most of the page is unchanged between Boot 3.5 and 4: Quartz is 2.5.2 on both, and `QuartzJobBean`, `TriggerUtils`, `CronExpression` and the Quartz API are identical. What moved is the test infrastructure around them. The 3.5 column below was checked against the published Boot 3.5.16, Spring Framework 6.2.19 and Testcontainers 1.21.4 artifacts and BOMs, not by re-running the tests.

.Test-related differences between Spring Boot 3.5.16 and 4.1.1
[cols="3,4,4",options="header"]
|===
|Topic |Boot 3.5.16 (Spring Framework 6.2.19) |Boot 4.1.1 (Spring Framework 7.0.9)

|Test starter for Quartz
|None; `spring-boot-starter-test` plus `spring-boot-starter-quartz`. The artifact `spring-boot-starter-quartz-test` has no 3.x version
|`spring-boot-starter-quartz-test` (empty JAR, brings `spring-boot-starter-quartz` and `spring-boot-starter-test`)

|`@AutoConfigureMockMvc`
|`org.springframework.boot.test.autoconfigure.web.servlet.AutoConfigureMockMvc` in `spring-boot-test-autoconfigure`; `@SpringBootTest` provides `MockMvc` support without it
|`org.springframework.boot.webmvc.test.autoconfigure.AutoConfigureMockMvc` in `spring-boot-webmvc-test` (starter `spring-boot-starter-webmvc-test`); `@SpringBootTest` alone no longer provides `MockMvc`, and `MockMvcTester` is available in Spring Test

|Replacing a bean with a mock
|`@MockBean` and `@SpyBean` (`org.springframework.boot.test.mock.mockito`, still present in `spring-boot-test` 3.5.16) or `@MockitoBean` (present in Spring Framework 6.2.19)
|`@MockitoBean` and `@MockitoSpyBean` only; `@MockBean` and `@SpyBean` were removed

|Quartz Boot types used in tests
|`org.springframework.boot.autoconfigure.quartz.SchedulerFactoryBeanCustomizer`, `QuartzDataSource`; endpoint class `org.springframework.boot.actuate.quartz.QuartzEndpoint`
|`org.springframework.boot.quartz.autoconfigure.SchedulerFactoryBeanCustomizer`, `QuartzDataSource`; endpoint class `org.springframework.boot.quartz.actuate.endpoint.QuartzEndpoint`

|Test context cache
|Inactive cached contexts keep running, so the scheduler of an earlier test class keeps firing
|Contexts are paused when the next test uses a different one (Spring Framework 7.0.3 and later); controlled by `spring.test.context.cache.pause` with `always`, `on_context_switch` (the default) and `never`

|JUnit
|JUnit Jupiter 5.12.2
|JUnit Jupiter 6.0.3 (the `org.junit.jupiter.api` and `org.junit.jupiter.params` annotations used here are unchanged)

|Testcontainers
|1.21.4: artifacts `org.testcontainers:postgresql`, `org.testcontainers:junit-jupiter`; classes `org.testcontainers.containers.PostgreSQLContainer<?>` (generic)
|2.0.5: artifacts `org.testcontainers:testcontainers-postgresql`, `testcontainers-junit-jupiter`; class `org.testcontainers.postgresql.PostgreSQLContainer` (not generic); the old `org.testcontainers.containers` names remain as deprecated aliases in the module JARs. The same applies to MySQL (`org.testcontainers.mysql`), MariaDB (`org.testcontainers.mariadb`), Oracle Free (`org.testcontainers.oracle.OracleContainer`, artifact `testcontainers-oracle-free`) and SQL Server (`org.testcontainers.mssqlserver.MSSQLServerContainer`)

|Awaitility, Mockito
|4.2.2, 5.17.0
|4.3.0, 5.23.0
|===
Source: https://github.com/spring-projects/spring-boot/wiki/Spring-Boot-4.0-Migration-Guide[Spring Boot 4.0 Migration Guide], https://github.com/testcontainers/testcontainers-java/releases/tag/2.0.0[Testcontainers 2.0.0 release notes], https://docs.junit.org/6.0.3/release-notes/[JUnit 6.0.3 release notes] and the Maven Central artifacts and BOMs named in the table.

For a migrating project the mechanical edits are: change the `AutoConfigureMockMvc` import and add `spring-boot-starter-webmvc-test`; replace `@MockBean` with `@MockitoBean` (and the import); rename the Testcontainers artifacts and imports; add `spring-boot-starter-quartz-test` if the build follows the new naming; and check whether any test relied on a cached context's scheduler still running, since that no longer holds by default. The migration of production code and configuration is on xref:backend/scheduling/migration-and-whats-changed.adoc[Migration & What's Changed].
