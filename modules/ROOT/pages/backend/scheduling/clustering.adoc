Quartz clustering is the feature that lets several copies of one service share one schedule: every job still runs once per fire time, and if the node that was running a job dies, a survivor can run it again. It is built on nothing but the job store's database, which is why it appears here after the generic ideas of xref:backend/scheduling/job-stores-and-persistence.adoc[Job Stores & Persistence] and the reference database page xref:backend/scheduling/database-postgresql.adoc[Quartz on PostgreSQL]. This page collects what is common to all databases and everything that is only about the cluster: the mechanics (locks, check-ins, instance ids), who fires what (nobody balances the load), what happens when a node dies and how long it takes, the clock requirement, the one setup mistake that corrupts a cluster, the three acquisition tuning properties, the scaling limit, the community stores that claim to cluster, running it on Kubernetes, Terracotta (gone), the official Example 13, and a three-node *Bookshelf* cluster with a weekly report that survives a `kill -9`.

It was written against Quartz 2.5.2, Spring Boot 4.1.1, Spring Framework 7.0.9 and Java 21 (bytecode level; the build ran on JDK 25.0.2 with Maven 3.9.16) and verified on 5 October 2026. Every default and name below was read from the Quartz 2.5.2 sources (`JobStoreSupport`, `StdRowLockSemaphore`, `StdSchedulerFactory`, `QuartzSchedulerThread`, the instance id generators) and every behaviour that the page states as measured was run against PostgreSQL 17 (`postgres:17`, 17.11, native arm64) with Testcontainers 2.0.5 on one Apple Silicon laptop, with the nodes either as threads of one JVM or, where a node had to be killed or signalled, as separate JVMs. Those numbers show that a mechanism works and how its timing is composed; they are not a benchmark. Two-node cluster runs on MySQL 9, MariaDB 11, Oracle Free and SQL Server 2022 (no duplicate executions, work shared) are reported on the pages of those databases. *Spring Boot 3.5.16* manages the same Quartz 2.5.2, so every statement about Quartz is identical; only the package of the Boot types (`org.springframework.boot.autoconfigure.quartz` instead of `org.springframework.boot.quartz.autoconfigure`) and Spring Framework 6.2.19 differ, and the page was not re-run on Boot 3.5. The Kubernetes manifests are illustrative: they were *not applied to a cluster* in this verification (no cluster was available); the application-side configuration inside them was run with plain JVMs and environment variables.

[[how-it-works]]
== How JDBC clustering works

Nodes of a cluster never talk to each other. Each node is a normal scheduler that uses the same tables, the same scheduler name (the `SCHED_NAME` column of every table) and the same configuration, and the database is the only coordinator. Three things make that safe: two row locks, a heartbeat row per node, and an instance id that is unique per node.

=== The two row locks in QRTZ_LOCKS

`QRTZ_LOCKS` holds two rows per scheduler name, `TRIGGER_ACCESS` and `STATE_ACCESS` (the constants `LOCK_TRIGGER_ACCESS` and `LOCK_STATE_ACCESS` in `JobStoreSupport`). A lock is taken by `StdRowLockSemaphore` with a `SELECT * FROM QRTZ_LOCKS WHERE SCHED_NAME = ? AND LOCK_NAME = ? FOR UPDATE` inside the transaction that does the work; it is released when that transaction commits or rolls back. If the row does not exist yet Quartz inserts it and tries again; if the lock attempt fails the semaphore retries up to `maxRetry` = 3 times, `retryPeriod` = 1000 ms apart. As soon as `org.quartz.jobStore.isClustered` is true the store forces `useDBLocks` on, so the row locks are always the mechanism in a cluster. Without clustering, a plain `JobStoreTX` uses a JVM monitor instead; `JobStoreCMT`, and therefore Boot's `LocalDataSourceJobStore`, always uses the database row locks, clustered or not (except on HSQLDB, where Spring installs a JVM-local `SimpleSemaphore`). The statements PostgreSQL actually logged are on xref:backend/scheduling/database-postgresql.adoc[Quartz on PostgreSQL]; SQL Server needs `WITH (UPDLOCK,ROWLOCK)`, which `JobStoreSupport` defaults in for `MSSQLDelegate` (see xref:backend/scheduling/database-sql-server.adoc[Quartz on SQL Server]).

=== Check-ins in QRTZ_SCHEDULER_STATE

Every node runs a `ClusterManager` thread (an inner class of `JobStoreSupport`, started when the scheduler starts, only in clustered mode). Every `clusterCheckinInterval` milliseconds it updates the node's row in `QRTZ_SCHEDULER_STATE` (`INSTANCE_NAME`, `LAST_CHECKIN_TIME`, `CHECKIN_INTERVAL`), inserting the row the first time, and at the same time it reads all rows to see whether another node is late. The default is *7500 ms* in the source. The Quartz configuration page for `JobStoreTX` says 15000; the source wins, and the value the page documents is not the one the code uses. A late node is handled by the rule in the <<failover,fail-over>> section.

A clean shutdown does *not* delete the node's row: `JobStoreSupport.shutdown()` stops the `ClusterManager` and the misfire thread and releases the connections, and that is all. The row of a node that stopped cleanly therefore stays until a survivor declares it failed and removes it (measured below: about ten seconds later).

[[load-balancing]]
== Who fires: there is no load balancing

When a trigger is due, the first node to acquire it fires it; every fire time runs on exactly one node. "Acquire" is a state change in the database, not a lock held for the whole wait: in the default configuration a node selects the due triggers, issues `UPDATE QRTZ_TRIGGERS SET TRIGGER_STATE = 'ACQUIRED' WHERE ... AND TRIGGER_STATE = 'WAITING'` for the one it wants, and inserts a `QRTZ_FIRED_TRIGGERS` row with its own instance id. The node whose update matches a row owns the trigger; the other node's update matches nothing (it waits for the winner's commit, then sees `ACQUIRED`) and it moves to the next trigger. Only when the node actually fires the trigger does it take `TRIGGER_ACCESS` (`triggersFired`), re-check that the state is still `ACQUIRED`, mark the fired row `EXECUTING` and compute the next fire time.

The Quartz documentation adds that clustering works best for scaling out long-running or CPU-intensive jobs; for thousands of short jobs it recommends partitioning the jobs over several distinct schedulers (see <<scaling,Scaling limits>>).

[[failover]]
== Fail-over and recovery

A node that dies (a crash, `kill -9`, a lost host, an evicted pod) leaves three kinds of evidence in the database: its row in `QRTZ_SCHEDULER_STATE` stops being refreshed, its `QRTZ_FIRED_TRIGGERS` rows stay, and the triggers it had acquired stay `ACQUIRED` or `BLOCKED`. Every surviving node's `ClusterManager` looks for exactly that at each check-in.

=== How a failed node is detected

A node is declared failed when `lastCheckin + max(checkinInterval, now - ownLastCheckin) + 7500 ms` is in the past (`calcFailedIfAfter`). `lastCheckin` and `checkinInterval` are the dead node's own row; `now` is the observer's clock and `ownLastCheckin` is the observer's previous check-in, so the second term is about one check-in interval. The 7500 ms is a fixed grace period that cannot be configured. Checks happen once per interval, so, with *I* the check-in interval and the kill at a random moment after the dead node's last check-in:

The range is "the interval plus the grace, plus the wait for the next check-in of the observer", which is why a short interval buys faster fail-over at the price of more check-in traffic (each check-in is a select of all rows and an update of the node's own row, with the locks taken only when there is work). The same rule bounds how long a job that is merely slow can run without being mistaken for a dead node: the check-in is done by the `ClusterManager`, not by the job threads, so a long job does not stop a node from checking in. A node that is paused (a long stop-the-world garbage collection, a stopped container, a database outage longer than the grace) *does* stop checking in and will be declared failed while still alive; the node's own next check-in then logs a warning that the instance is still active but was recovered by another instance in the cluster.

The consequence for job design is the whole point of the weekly report in the worked example: a recoverable job runs *at least once*, and possibly twice if the crash came after it had done most of its work but before its fired row was deleted. A job declared with `requestRecovery(true)` must therefore be written so that running it twice is harmless, which is a statement about the job and not about Quartz. The job data model of xref:backend/scheduling/jobs-and-job-data.adoc[Jobs & Job Data] and the way a held-back (`BLOCKED`) trigger turns into a misfire on xref:backend/scheduling/misfires.adoc[Misfires] decide what a recovered run sees.

=== Restarting with the same instance id

=== Stopping a node cleanly

[[clock-sync]]
== Clock synchronisation

Quartz states the requirement bluntly: never run a cluster on separate machines unless their clocks are synchronised by a time-service daemon that runs very regularly, and the clocks must be within one second of each other. The reason is visible in the source. The check-in time written to `QRTZ_SCHEDULER_STATE` is the node's own `System.currentTimeMillis()`, and the failure rule compares *that* value with the observer's own clock. Fire times are computed by each node from its own clock too. Reasoned from the source, not run (the clocks of a laptop cannot be skewed safely), the effects are:

.What clock skew does to a cluster (derived from JobStoreSupport and QuartzSchedulerThread 2.5.2)
[cols="3,6",options="header"]
|===
|Skew between two nodes |Effect

|An observer whose clock is *ahead* of the dead node's by *s*
|Failed nodes are detected *s* earlier than the rule above; once *s* exceeds the 7500 ms grace, a *live* node that checks in on time looks late and is "recovered" while it is still running its jobs, so a recoverable job can run twice

|An observer whose clock is *behind*
|Detection is later by *s*; fail-over takes longer, nothing is wrong otherwise

|A node whose clock is ahead
|It considers triggers due earlier and wins the race for them more often, which makes the uneven distribution worse; its jobs run early by the skew
|===
Source: https://www.quartz-scheduler.org/documentation/quartz-2.5.x/configuration/ConfigJDBCJobStoreClustering.html[Quartz documentation: Configure Clustering with JDBC-JobStore] and https://github.com/quartz-scheduler/quartz/blob/v2.5.2/quartz/src/main/java/org/quartz/impl/jdbcjobstore/JobStoreSupport.java[`JobStoreSupport` source at v2.5.2 (`calcFailedIfAfter`, `clusterCheckIn`)]

In practice this means one time service (NTP or chrony) on every host or Kubernetes node, a monitor on the offset, and the same `TZ` in every container. Cluster nodes on one host or in one Kubernetes node share a clock and cannot disagree. The clocks of the database host do not matter to Quartz in the way the nodes' do, because the timestamps are written by the nodes, not by `now()` in SQL.

[[no-mixing]]
== Never mix clustered and non-clustered nodes

Quartz warns never to start a non-clustered scheduler against tables that another scheduler is using, and predicts serious data corruption and erratic behaviour. The source shows the mechanism. A non-clustered job store runs `recoverJobs()` when the scheduler starts; it assumes it is alone, so it resets the world: every `ACQUIRED` and `BLOCKED` trigger of the scheduler name goes back to `WAITING`, `COMPLETE` triggers are removed, and *every* row of `QRTZ_FIRED_TRIGGERS` of that scheduler name is deleted, whichever node it belonged to. It recovers only the fired rows that carry its *own* instance id, which is `NON_CLUSTERED`. This was run: a clustered node was executing the 25-second recoverable job, a second JVM with the same scheduler name and `isClustered=false` was started, and then the first node was killed.

.A non-clustered scheduler started against a running cluster (measured, PostgreSQL 17)
[cols="3,6",options="header"]
|===
|Step |Observed

|Before the second JVM starts
|`QRTZ_FIRED_TRIGGERS`: one row, instance of the clustered node, job `slow`, state `EXECUTING`, `REQUESTS_RECOVERY` true

|After it started (`instanceId` `NON_CLUSTERED`)
|`QRTZ_FIRED_TRIGGERS`: *no rows*. The running job was erased from the bookkeeping; nothing logged an error

|The clustered node is killed with `kill -9` and a surviving clustered node waits 40 s
|The survivor removed the dead node's check-in row, found no fired rows to recover, and *never re-ran the job*. The recoverable job was silently lost
|===
Source: https://www.quartz-scheduler.org/documentation/quartz-2.5.x/configuration/ConfigJDBCJobStoreClustering.html[Quartz documentation: Configure Clustering with JDBC-JobStore] and https://github.com/quartz-scheduler/quartz/blob/v2.5.2/quartz/src/main/java/org/quartz/impl/jdbcjobstore/JobStoreSupport.java[`JobStoreSupport` source at v2.5.2 (`schedulerStarted`, `recoverJobs`)]

The same reset also moves the blocked triggers of a `@DisallowConcurrentExecution` job back to `WAITING` (the guard against a second concurrent run lives in those trigger states), so the cluster-wide "never overlaps" rule of xref:backend/scheduling/jobs-and-job-data.adoc[Jobs & Job Data] stops holding for as long as the damage lasts. The practical rules are: every process that starts a scheduler with a given scheduler name on shared tables must set `isClustered=true`; a one-off script, an integration test or a developer's laptop must use another scheduler name, another table prefix or another database; and the Boot default of `spring.quartz.job-store-type=memory` (a RAM store never touches the tables) is the safe setting for processes that must not schedule. Giving a *different* scheduler name to a non-clustered scheduler is safe because every table carries `SCHED_NAME`; two clustered schedulers with different names simply form two independent logical clusters.

Three properties shape how triggers are acquired. They are all documented on the configuration pages, and all verified in `QuartzSchedulerThread` and `JobStoreSupport`:

[[scaling]]
== Scaling limits

Every acquisition-to-completion cycle of every fire passes through `TRIGGER_ACCESS` (at the latest at `triggersFired` and `triggeredJobComplete`), so the lock is a single serialisation point for the whole cluster. The Quartz documentation says that a cluster-wide lock of this kind degrades performance as nodes are added, beyond about three nodes and depending on the database. Nothing here was benchmarked; the figure is Quartz's, not a measurement of this section. What follows from it:

* Add nodes for availability, not for throughput: two or three nodes is the sweet spot, and the fire rate a cluster can sustain is bounded by the database's row-lock throughput rather than by the number of worker threads.
* Add threads and nodes for *long-running and CPU-heavy* jobs, where the time is in the job and the lock is touched twice per execution.
* For thousands of short jobs, partition: run several *distinct* schedulers (distinct scheduler names, each possibly itself a small cluster for availability) and give each its own share of the jobs. The `SCHED_NAME` column means they can share tables; the locks are per scheduler name, so partitions do not contend with each other.
* If the only requirement is "run this on one node at a time", with no job store, no fail-over of running jobs and no dynamic scheduling, a `@Scheduled` method plus a lock is much lighter: see xref:backend/springboot/scheduling-and-shedlock.adoc[Scheduling & ShedLock] and the comparison on xref:backend/scheduling/standard-scheduling-vs-quartz.adoc[Standard Scheduling vs Quartz].
* The connection pool has to cover the worker threads plus Quartz's housekeeping threads on every node (the pool arithmetic is on xref:backend/scheduling/job-stores-and-persistence.adoc[Job Stores & Persistence] and xref:backend/scheduling/production-and-best-practices.adoc[Production & Best Practices]).

== Terracotta clustering is gone

Quartz once clustered through the `TerracottaJobStore`. It was removed in Quartz 2.4.0: the 2.3.2 jar contains eight Terracotta classes, the 2.4.1 and 2.5.2 jars none (the comparison is on xref:backend/scheduling/job-stores-and-persistence.adoc[Job Stores & Persistence]), so *JDBC is the only clustering mechanism in 2.5.2*. Some pages of the official 2.5.x documentation still describe it (the Lesson 11 text that this page cites says clustering "currently works with the JDBC-Jobstore ... and the TerracottaJobStore", and the configuration index still lists a Terracotta page); that is stale text, not a feature. The `StdSchedulerFactory` of 2.5.2 still contains a branch for job stores whose class name starts with `org.terracotta.quartz`, which can never be taken without that class. If you meet `org.terracotta.quartz.TerracottaJobStore` in an old configuration, the migration is to a JDBC job store: see xref:backend/scheduling/migration-and-whats-changed.adoc[Migration & What's Changed].

[[kubernetes]]
== Running the cluster on Kubernetes

A cluster on Kubernetes is a Deployment (or StatefulSet) of several replicas of the service, all pointing at one database. Nothing about Quartz needs to know about Kubernetes except two things: the instance id must be unique per pod, and a pod must be given time to finish its jobs. The workload objects themselves are on xref:backend/kubernetes/replicasets-and-deployments.adoc[ReplicaSets & Deployments] and xref:backend/kubernetes/statefulsets.adoc[StatefulSets], the termination sequence on xref:backend/kubernetes/health-probes-and-lifecycle.adoc[Health Probes & Lifecycle]. Whether the work should be a Quartz cluster at all, or a Kubernetes `CronJob`, is the question of xref:backend/kubernetes/jobs-and-cronjobs.adoc[Jobs & CronJobs]: the CronJob is the better answer for a job that is a separate batch process; a Quartz cluster is the better answer for dynamic schedules, persistence in the application's own database, and job code that is part of the service.

=== Pod names as instance ids

The hostname of a pod defaults to its name (see xref:backend/kubernetes/pods.adoc[Pods]), so plain `AUTO` already produces `<pod name><epoch millis>`: unique, and different at every restart. A stable, readable id needs one of three things, all run:

.A custom InstanceIdGenerator that returns the pod name
[source,java]
----
package bookshelf;

import org.quartz.SchedulerException;
import org.quartz.spi.InstanceIdGenerator;

/** Uses the pod name (env POD_NAME from the downward API, else the HOSTNAME that Kubernetes sets to the pod name) as the Quartz instance id. */
public class PodNameInstanceIdGenerator implements InstanceIdGenerator {

    @Override
    public String generateInstanceId() throws SchedulerException {
        String id = System.getenv("POD_NAME");
        if (id == null || id.isBlank()) {
            id = System.getenv("HOSTNAME");
        }
        if (id == null || id.isBlank()) {
            throw new SchedulerException("Neither POD_NAME nor HOSTNAME is set; cannot derive a unique instance id");
        }
        return id.trim();
    }
}
----
Source: https://www.quartz-scheduler.org/api/2.5.x/org/quartz/spi/InstanceIdGenerator.html[Quartz API: InstanceIdGenerator] and https://kubernetes.io/docs/tasks/inject-data-application/environment-variable-expose-pod-information/[Kubernetes: Expose Pod Information to Containers Through Environment Variables]

The generator is switched on by `AUTO` together with the `instanceIdGenerator.class` property. This block was run with the environment variables `POD_NAME`, `DB_URL`, `DB_USER` and `DB_PASSWORD` set and nothing else, as two JVMs (their ids were `bookshelf-0` and `bookshelf-1`, and both rows were in `QRTZ_SCHEDULER_STATE`):

=== Deployment or StatefulSet

The choice is a trade between two behaviours that were measured above:

.Instance ids of a Deployment against a StatefulSet
[cols="2,4,4",options="header"]
|===
|Workload |Ids |Consequence for the cluster

|Deployment
|Random pod names; a replaced pod gets a new name
|A killed pod is recovered by *another* node after the 7.5 s grace plus the check-in cycle (9.7 s measured with a 2 s interval); every rollout leaves one stale `QRTZ_SCHEDULER_STATE` row per old pod for about ten seconds

|StatefulSet
|Stable ordinals `bookshelf-0`, `bookshelf-1`, and a pod is never run twice at once
|A restarted pod recovers its *own* jobs at its first check-in (1.9 s measured); the stale rows do not accumulate. The price is a StatefulSet's ordered rollout and slower scaling, and that a pod that stays down keeps its row until another node declares it failed
|===
Source: https://kubernetes.io/docs/concepts/workloads/controllers/statefulset/[Kubernetes: StatefulSets] and https://kubernetes.io/docs/concepts/workloads/controllers/deployment/[Kubernetes: Deployments]

A Deployment is the right default, because the stateless service that happens to schedule work stays a Deployment and the recovery by a neighbour is fast enough for jobs that take minutes. A StatefulSet is worth it only for fail-over of short, frequent recoverable jobs, where waiting ten seconds for a neighbour matters.

=== Graceful shutdown

When a pod is deleted Kubernetes sends SIGTERM, waits up to `terminationGracePeriodSeconds` (default 30), and then sends SIGKILL. Spring closes the context on SIGTERM and the scheduler is shut down as described above. Three rules follow, each backed by the measurements of the shutdown table:

* Set `spring.quartz.wait-for-jobs-to-complete-on-shutdown: true`, otherwise a SIGTERM cuts the running job off at once (63 ms in the measurement). With `true` the JVM stayed up for the whole 25 seconds of the job and the job was recorded as complete, so no recovery was needed. The YAML above was run with a pod-name node and a 25-second job: the node exited 25.0 s after SIGTERM. This holds for Quartz's own `SimpleThreadPool`: with a Spring `TaskExecutor` as the thread pool the flag is not honoured, and `spring.task.execution.shutdown.await-termination=true` keeps the JVM alive until the job ends but Quartz has already shut its job store down, so the completion is not recorded, the fired row stays `EXECUTING` and a surviving node re-runs a `requestsRecovery` job (see xref:backend/scheduling/production-and-best-practices.adoc#shutdown[Production & Best Practices: Graceful shutdown] and xref:backend/scheduling/spring-boot-configuration.adoc[Spring Boot Configuration]).
* Set `terminationGracePeriodSeconds` above the longest job plus the Spring shutdown time, or Kubernetes sends SIGKILL in the middle of it and you are back to the crash case of the fail-over section. A job that is longer than any grace period you are willing to give must be a recoverable, idempotent job, or must be split.
* While a node is shutting down, it stops acquiring new triggers at once (the scheduler thread halts first) and only the running jobs continue; the other replicas keep firing. A rolling update therefore never stops the schedule, and the old pod's stale row is removed by a neighbour roughly ten seconds later.

The rest of the termination sequence (the `preStop` hook, endpoint removal and why a short `sleep` helps HTTP traffic) concerns the web side and is on xref:backend/kubernetes/health-probes-and-lifecycle.adoc[Health Probes & Lifecycle]. Rolling update tuning is on xref:backend/kubernetes/deployment-strategies.adoc[Deployment Strategies], and scaling replicas on xref:backend/kubernetes/autoscaling.adoc[Autoscaling]: do not let a horizontal autoscaler add replicas to a Quartz cluster to gain throughput, because of the scaling limit above; scale the worker threads and keep three nodes.

[[example-13]]
== Quartz Example 13

Quartz ships a clustering example in the repository under `examples/src/main/java/org/quartz/examples/example13` (read at tag v2.5.2, not run as it stands because it needs a prepared database and two terminals). It is the closest thing to an official reference and worth reading next to this page:

* `ClusterExample` is a `main` class. It creates a scheduler with `new StdSchedulerFactory()`, which reads `quartz.properties` from the classpath or from the file named by the `org.quartz.properties` system property (the example's resources are called `instance1.properties` and `instance2.properties`, so each node is pointed at one of them). With the argument `clearJobs` it first calls `sched.clear()`, and with `dontScheduleJobs` it only starts the scheduler, which is how the second node is started. Otherwise it schedules five jobs (`job_1` to `job_5`), each in a *group named after the node's instance id*, each with `requestRecovery()` and a trigger that repeats 20 times (every 5, 5, 3, 4 and 4.5 seconds), starts the scheduler and sleeps for an hour.
* `SimpleRecoveryJob` logs whether it is `RECOVERING` or starting, sleeps ten seconds so there is time to kill the node, and increments a counter in its `JobDataMap`. `SimpleRecoveryStatefulJob` extends it with `@PersistJobDataAfterExecution` and `@DisallowConcurrentExecution`, so the counter survives and the job never overlaps with itself.
* `instance1.properties` and `instance2.properties` configure the two nodes: scheduler name `TestScheduler`, fixed instance ids `instance_one` and `instance_two` (not `AUTO`), five threads, `JobStoreTX` with `PostgreSQLDelegate`, a named data source with its own pool, and `isClustered=true`; the check-in interval is left at its default. The credentials in the file are the example's own placeholders for a local database; use your own, and never ship them.

It teaches the operational experiment: start both nodes, watch which node logs each job, kill one while a job sleeps, and watch the other log `RECOVERING` after the detection time. It differs from this page's setup in three ways: plain Quartz instead of Spring (so the pool, the transactions and the job factory are configured by hand), fixed ids set per properties file instead of `AUTO`, and a job store (`JobStoreTX`) that manages its own transactions instead of Boot's `LocalDataSourceJobStore`. The cluster behaviour is the same, and so is the lesson: mark the jobs that must survive a crash with `requestRecovery`.
Source: https://github.com/quartz-scheduler/quartz/blob/v2.5.2/examples/src/main/java/org/quartz/examples/example13/ClusterExample.java[`ClusterExample.java` at v2.5.2], https://github.com/quartz-scheduler/quartz/tree/v2.5.2/examples/src/main/resources/org/quartz/examples/example13[the example13 resources at v2.5.2] and https://www.quartz-scheduler.org/documentation/quartz-2.5.x/configuration/ConfigJDBCJobStoreClustering.html[Quartz documentation: Configure Clustering with JDBC-JobStore]

[[worked-example]]
== Worked example: the three-node Bookshelf cluster

The weekly statistics report of *Bookshelf* is the job that most needs clustering: it takes a long time, must not run twice at once, and must be re-run if its node dies. Three Bookshelf nodes share one PostgreSQL database with the configuration of the Kubernetes section. The job is written so that a second run is harmless:

.WeeklyReportJob.java: a recoverable job that is safe to run twice
[source,java]
----
package bookshelf;

import java.time.DayOfWeek;
import java.time.LocalDate;
import java.time.ZoneOffset;
import java.time.temporal.TemporalAdjusters;

import org.quartz.DisallowConcurrentExecution;
import org.quartz.JobExecutionContext;
import org.quartz.JobExecutionException;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.jdbc.core.JdbcTemplate;
import org.springframework.scheduling.quartz.QuartzJobBean;

@DisallowConcurrentExecution
public class WeeklyReportJob extends QuartzJobBean {

    private static final Logger log = LoggerFactory.getLogger(WeeklyReportJob.class);

    private final JdbcTemplate jdbc;

    public WeeklyReportJob(JdbcTemplate jdbc) {
        this.jdbc = jdbc;
    }

    @Override
    protected void executeInternal(JobExecutionContext context) throws JobExecutionException {
        // keyed by the week of the SCHEDULED time: a recovery run has the same scheduled time and hits the same row
        LocalDate week = context.getScheduledFireTime().toInstant().atZone(ZoneOffset.UTC).toLocalDate()
                .with(TemporalAdjusters.previousOrSame(DayOfWeek.MONDAY));
        String node = instanceId(context);

        String status = jdbc.query("SELECT status FROM weekly_report WHERE week_start = ?",
                rs -> rs.next() ? rs.getString(1) : null, week);
        if ("DONE".equals(status)) {
            log.info("Report for week {} is already DONE, nothing to do", week);
            return;
        }

        jdbc.update("""
                INSERT INTO weekly_report (week_start, status, attempts, node) VALUES (?, 'RUNNING', 1, ?)
                ON CONFLICT (week_start) DO UPDATE
                   SET status = 'RUNNING', attempts = weekly_report.attempts + 1, node = EXCLUDED.node
                """, week, node);

        generateStatistics(context.getMergedJobDataMap().getLongValueFromString("workMillis"));   // the long part

        jdbc.update("UPDATE weekly_report SET status = 'DONE', finished_at = now() WHERE week_start = ?", week);
    }

    private void generateStatistics(long workMillis) {
        try {
            Thread.sleep(workMillis);       // stands in for the real queries
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
    }

    private static String instanceId(JobExecutionContext context) {
        try {
            return context.getScheduler().getSchedulerInstanceId();
        } catch (org.quartz.SchedulerException e) {
            return "unknown";
        }
    }
}
----
Source: https://www.quartz-scheduler.org/api/2.5.x/org/quartz/JobExecutionContext.html[Quartz API: JobExecutionContext] and https://docs.spring.io/spring-framework/reference/integration/scheduling.html[Spring Framework: Task Execution and Scheduling]

The table is `weekly_report (week_start date PRIMARY KEY, status varchar(10), attempts int, node varchar(200), finished_at timestamptz)`. The job is declared with `requestRecovery(true)`:

.Scheduling the report as a recoverable job
[source,java]
----
JobDetail report = JobBuilder.newJob(WeeklyReportJob.class)
        .withIdentity("weeklyReport", "bookshelf")
        .usingJobData("workMillis", "20000")
        .requestRecovery(true)                  // re-run if the node dies while it executes
        .storeDurably()
        .build();
Trigger sundayNight = TriggerBuilder.newTrigger()
        .forJob(report)
        .withIdentity("weeklyReportTrigger", "bookshelf")
        .withSchedule(CronScheduleBuilder.cronSchedule("0 0 3 ? * SUN"))
        .build();
scheduler.scheduleJob(report, sundayNight);
----
Source: https://www.quartz-scheduler.org/documentation/quartz-2.5.x/tutorials/tutorial-lesson-03.html[Quartz Tutorial: Lesson 3, More About Jobs and Job Details]

[[pitfalls]]
== Pitfalls

.Clustering pitfalls (measured unless marked source)
[cols="3,4,4",options="header"]
|===
|Pitfall |What happens |What to do

|A non-clustered scheduler with the same name on the tables
|Its start-up recovery deletes every fired-trigger row, so a running recoverable job is never re-run after a crash (measured), and it frees blocked triggers (source)
|`isClustered=true` everywhere, or another scheduler name, prefix or database for scripts and tests

|`isClustered=true` but the same instance id on two live nodes
|The second node recovers the first one's running jobs at its first check-in (source)
|`AUTO`, a pod name, or a unique `SYS_PROP`; never a literal copied between configurations

|Expecting the cluster to share the load
|One node fires most or all of the work in the runs measured here
|Create several jobs or triggers, or partition by scheduler name; use the cluster for availability

|A recoverable job that is not idempotent
|After a crash it runs again from the beginning, possibly after partial side effects (measured: the report ran twice)
|Key the work on the scheduled time, upsert, check a completion marker

|A job without `requestsRecovery`
|It is silently lost when its node dies; only the next fire time runs
|Declare it with `requestRecovery(true)` if the run matters

|Unsynchronised clocks
|Late or false fail-over (a skew above the 7.5 s grace can make a live node look dead), early or late fires (source)
|One time service on every host or Kubernetes node; monitor the offset

|Waiting for the 15000 ms default
|The documentation lists 15000, the code uses 7500, and the observed fail-over is 7.5 s to 22.5 s with the code's default
|Set `clusterCheckinInterval` explicitly and size the application's tolerance to the range

|`wait-for-jobs-to-complete-on-shutdown` left `false`, or a grace period shorter than the job
|The pod is cut off in the middle of a job (63 ms in the measurement)
|`true` plus `terminationGracePeriodSeconds` longer than the longest job; recoverable jobs for the rest. With a Spring `TaskExecutor` the flag is not honoured and `await-termination` does not make Quartz record completion (xref:backend/scheduling/production-and-best-practices.adoc#shutdown[Production & Best Practices: Graceful shutdown], xref:backend/scheduling/spring-boot-configuration.adoc[Spring Boot Configuration])

|Batch acquisition or a fire-ahead window "for performance"
|One node takes all the due triggers, triggers fire seconds early (3.3 s early measured)
|Leave `batchTriggerAcquisitionMaxCount` at 1 and the window at 0 unless thousands of triggers are due together

|Adding nodes to scale throughput
|The shared `TRIGGER_ACCESS` lock serialises every fire; Quartz documents the degradation beyond about three nodes
|Add threads for long jobs; partition into several schedulers for many short ones

|A community NoSQL store as the cluster's store
|MongoDB: nothing fires and nothing is reported; Redis: start-up failure (measured on 2.5.2)
|Quartz on SQL, MongoDB or Redis for the data, or ShedLock

|Three schedulers of one name in one JVM outside a test
|Spring registers the data source under the scheduler name, so the second overwrites the first (see the PostgreSQL page)
|One scheduler per JVM in production; separate JVMs when a test needs `kill -9`

|Looking for `TerracottaJobStore`
|It was removed in 2.4.0 although some documentation pages still mention it
|Migrate to JDBC
|===
Source: this page's measured results and the https://www.quartz-scheduler.org/documentation/quartz-2.5.x/best-practices.html[Quartz Best Practices].

[[what-changed]]
== What changed

.Changes that touch clustering
[cols="2,5",options="header"]
|===
|Release |Change

|Quartz 2.4.0
|`TerracottaJobStore` removed: clustering is JDBC-only. HikariCP and c3p0 became `provided` dependencies. The documentation of 2.5.x still mentions Terracotta in Lesson 11.

|Quartz 2.5.0
|Jakarta namespace and Java 11; `JobDetail.isConcurrentExectionDisallowed()` (the misspelling) removed, which silently breaks `quartz-mongodb` compiled against 2.4 and earlier (measured: the scheduler starts, nothing fires, because the scheduler thread dies with a `NoSuchMethodError` on `isConcurrentExectionDisallowed`). The Redis store fails loudly instead: with the Boot-managed Jedis 7.4.1 it stops at startup with a `NoSuchMethodError` on `JedisCommands.del(String)`, and with Jedis 3.3.0 on Quartz 2.5.2 it fails on the JSON (de)serialization of `JobDetailImpl` (Jackson `UnrecognizedPropertyException` on `concurrentExecutionDisallowed`) and with an `AbstractMethodError` on `getAcquireRetryDelay` (measured). The JDBC store itself was not affected.

|Quartz 2.5.x scripts
|`tables_oracle23.sql` and two GaussDB scripts are added; the SQL Server script uses `NVARCHAR` columns (in the released 2.5.2). The cluster tables and lock names did not change.

|After Quartz 2.5.2 (unreleased on `main`)
|`MSSQLDelegate` binds the scheduler-state instance name as `NVARCHAR` (the fix for clustered check-in deadlocks on SQL Server, issue 1514, pull request 1515); a two-node SQL Server run on 2.5.2 did not deadlock in a ten-second test, so the issue is real but was not reproduced here.

|Quartz 2.5.2 versus the documentation
|The `clusterCheckinInterval` default is 7500 ms in the code and 15000 in the `JobStoreTX` page; Lesson 11 still lists the Terracotta store; the same pages tell you to set `acquireTriggersWithinLock` for batch acquisition, which the code does for you.

|Spring Boot 3.5 to 4.x
|The Quartz auto-configuration moved to `org.springframework.boot.quartz.autoconfigure` in the new `spring-boot-quartz` module; the `spring.quartz.*` property names are unchanged, so the cluster configuration of this page is the same on Boot 3.5.16 (which also manages Quartz 2.5.2). Boot 4.1.1 registers no Quartz health indicator or metrics (measured; Boot 3.5 was not run).

|Spring Framework 6.2 to 7.0
|`LocalDataSourceJobStore` and `SchedulerFactoryBean` keep their behaviour, including the use of `waitForJobsToCompleteOnShutdown` on context close.
|===
