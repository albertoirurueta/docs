== What a job store is

Quartz separates *running* a job from *remembering* it. The scheduler thread, the worker pool and the listeners are the same whatever you
choose; everything that has to be remembered goes through one interface, `org.quartz.spi.JobStore`, and the scheduler is created with exactly one
implementation of it. Reading the 2.5.2 interface, its methods fall into five groups.

.The groups of methods in the JobStore SPI (Quartz 2.5.2)
[cols="2,4,4",options="header"]
|===
|Group |Methods (abbreviated) |What the store must guarantee

|Lifecycle
|`initialize(ClassLoadHelper, SchedulerSignaler)`, `schedulerStarted()`, `schedulerPaused()`, `schedulerResumed()`, `shutdown()`, `setInstanceId`, `setInstanceName`, `setThreadPoolSize`
|It is told the scheduler's name and instance id before `initialize`, and gets a `SchedulerSignaler` to wake the scheduler thread when something changes (a new trigger that fires earlier than the one it sleeps on).
 `schedulerStarted()` is where a JDBC store recovers jobs after a crash (non-clustered) or starts the cluster manager thread (clustered).

|Capabilities
|`supportsPersistence()`, `isClustered()`, `getEstimatedTimeToReleaseAndAcquireTrigger()`, `getAcquireRetryDelay(int)`
|What the scheduler may assume. `getAcquireRetryDelay` is how long the scheduler thread sleeps after repeated failures to talk to the store; the JDBC store returns `dbRetryInterval` (15000 ms by default).

|Definitions

|===

=== The three obligations

Whatever the technology behind it, a store that is correct for Quartz does three things.

*Atomic trigger acquisition.* The scheduler thread asks `acquireNextTriggers` for the triggers whose next fire time is within the next moments, in
order of fire time and priority. The store must hand each trigger to exactly one caller and mark it as reserved. The `RAMJobStore` does
this under a `synchronized` block around an in-memory sorted set of triggers (`TreeSet<TriggerWrapper>` in the source). The JDBC store has no
shared memory to lock, so it uses the database: it selects the due trigger keys (`SELECT_NEXT_TRIGGER_TO_ACQUIRE`), then flips the trigger row from
`WAITING` to `ACQUIRED` with an `UPDATE ... WHERE TRIGGER_STATE = 'WAITING'` (`updateTriggerStateFromOtherState`) and inserts a row in
`QRTZ_FIRED_TRIGGERS`. If the update touches no row, another node got there first and the store moves on to the next candidate. By default this
runs without any lock (the code takes the `TRIGGER_ACCESS` lock only when `org.quartz.jobStore.acquireTriggersWithinLock` is true or the scheduler
acquires more than one trigger per call, `org.quartz.scheduler.batchTriggerAcquisitionMaxCount` greater than 1), and a validator re-reads
`QRTZ_FIRED_TRIGGERS` to confirm that the acquisition really was committed.

*Misfire scan.* A trigger whose fire time is far enough in the past must be handled according to its misfire instruction rather than fired
blindly. The RAM store applies this while it hands out triggers. The JDBC store runs a dedicated `MisfireHandler` thread that wakes up every
`misfireThreshold` milliseconds, selects waiting triggers older than the threshold (`hasMisfiredTriggersInState`), handles at most
`maxMisfiresToHandleAtATime` (20 by default) per pass, and signals the scheduler thread. The policies themselves are on
xref:backend/scheduling/misfires.adoc[Misfires].

*Cluster locking.* A store that several scheduler instances share needs a mutual exclusion primitive and a way to notice that an instance died.
The JDBC store provides both with ordinary rows: the locks are rows of `QRTZ_LOCKS` taken with `SELECT ... FOR UPDATE`
(`TRIGGER_ACCESS` and `STATE_ACCESS`), and each instance writes a heartbeat row into `QRTZ_SCHEDULER_STATE`; an instance whose heartbeat is
older than its check-in interval plus a grace period is declared dead and its `QRTZ_FIRED_TRIGGERS` rows are recovered by a surviving node.
The detail of that protocol, with the measured fail-over time, is on xref:backend/scheduling/clustering.adoc[Clustering]. The RAM store is
never clustered (`RAMJobStore.isClustered()` returns false).

== The built-in job stores

Quartz 2.5.2 ships `org.quartz.simpl.RAMJobStore` and three JDBC-based stores in `org.quartz.impl.jdbcjobstore`, of which one is Spring's. (`TerracottaJobStore`
was removed in 2.4.0, the 2.5.2 jar contains no Terracotta class, and what the Quartz website still says about it is obsolete.)

.The job stores you can choose between on Spring Boot 4.1
[cols="2,3,3,3",options="header"]
|===
|Store |Who manages the connection and the transaction |Locking and clustering |Typical use

|`RAMJobStore`
|Nobody: there is no database
|`synchronized`; never clustered
|Tests, caches, anything that is rebuilt from code on every start. Boot's default (`spring.quartz.job-store-type=memory`).

|`JobStoreTX` (`org.quartz.impl.jdbcjobstore`)
|Quartz itself: it obtains a connection from a Quartz-managed `org.quartz.dataSource.NAME.*` pool, sets auto-commit to false and commits or rolls back each operation
|`SimpleSemaphore` (a JVM monitor) unless clustered or `useDBLocks` is true, otherwise row locks in `QRTZ_LOCKS`
|Plain Quartz outside Spring, with its own pool

|`JobStoreCMT`
|The container: API calls join an existing (JTA) transaction; the scheduler's own housekeeping uses a second, non-XA data source (`nonManagedTXDataSource`) with auto-commit off
|Always database row locks (`initialize` forces `useDBLocks`)
|Application servers with JTA

|`LocalDataSourceJobStore` (`org.springframework.scheduling.quartz`)
|Spring: it extends `JobStoreCMT` and borrows connections from the Spring-managed `DataSource` through `DataSourceUtils`, so API calls take part in Spring transactions
|Database row locks, except that it switches to the in-JVM `SimpleSemaphore` when the product name contains `hsql`
|What Spring Boot installs when `job-store-type=jdbc`
|===
Source: https://www.quartz-scheduler.org/documentation/quartz-2.5.x/configuration/ConfigJobStoreCMT.html[Quartz documentation: Configure JDBCJobStoreCMT] and the
https://github.com/spring-projects/spring-framework/blob/v7.0.9/spring-context-support/src/main/java/org/springframework/scheduling/quartz/LocalDataSourceJobStore.java[Spring Framework 7.0.9 `LocalDataSourceJobStore` source].

Two details of `LocalDataSourceJobStore` explain behaviour you will otherwise find puzzling. First, it registers two connection providers with Quartz's
`DBConnectionManager`, named `springTxDataSource.<scheduler instance name>` and `springNonTxDataSource.<scheduler instance name>`: the
transactional one hands out the connection bound to the current Spring transaction (so `scheduler.scheduleJob(...)` inside a `@Transactional` method commits
or rolls back with your business data), the non-transactional one always opens a fresh connection (used by the scheduler thread, the misfire handler and the cluster
manager, which manage their own commits). With an XA `DataSource` you pass a second, non-XA one through `SchedulerFactoryBean.setNonTransactionalDataSource`.
Second, it calls `setDontSetAutoCommitFalse(true)`, so Quartz does not touch the auto-commit flag of the connections it borrows from your pool.

=== Choosing the store from Spring Boot

Spring Boot exposes the choice as one property, `spring.quartz.job-store-type`, an enum with two values, `memory` (the default) and `jdbc`.

.Selecting the JDBC store
[source,yaml]
----
spring:
  datasource:
    url: jdbc:postgresql://localhost:5432/bookshelf
    username: ${DB_USER}
    password: ${DB_PASSWORD}
  quartz:
    job-store-type: jdbc
    properties:
      org.quartz.jobStore.driverDelegateClass: org.quartz.impl.jdbcjobstore.PostgreSQLDelegate
----
Source: https://docs.spring.io/spring-boot/reference/io/quartz.html[Spring Boot: Quartz Scheduler]

What `job-store-type=jdbc` does, read from `QuartzAutoConfiguration`: the JDBC configuration class is active only when the property is `jdbc` *and* the context has a
single candidate `DataSource` (`@ConditionalOnSingleCandidate`, so one bean, or one marked `@Primary`); it then calls `schedulerFactoryBean.setDataSource(...)`, and Spring's
`SchedulerFactoryBean` responds by putting `org.quartz.jobStore.class=org.springframework.scheduling.quartz.LocalDataSourceJobStore` into the Quartz properties unless one is already there.
It also creates the schema initializer described below and imports `DatabaseInitializationDependencyConfigurer`. Three measured consequences:

== The QRTZ_ tables

The JDBC stores use eleven tables. All of them are prefixed with `QRTZ_` (configurable), and every primary key starts with `SCHED_NAME`, the scheduler name
(`spring.quartz.scheduler-name`, bean name `quartzScheduler` when unset), which is what lets several logical schedulers share one set of tables.

.The main QRTZ_ tables and how they relate (declared foreign keys solid, logical references dashed)

In the middle, QRTZ_TRIGGERS has a declared foreign key to the job and a logical reference by name to QRTZ_CALENDARS. === tablePrefix and SCHED_NAME

`org.quartz.jobStore.tablePrefix` (default `QRTZ_`) lets several applications keep separate Quartz tables in one database without separate schemas. The prefix is a Quartz property,
so under Boot it goes through `spring.quartz.properties`, and *the DDL has to be edited to match*, because the scripts and the Boot initializer know only `QRTZ_`. Both directions
were run on PostgreSQL 17:

=== useProperties

By default the `JobDataMap` of a job and of a trigger is stored as a serialized Java object. `org.quartz.jobStore.useProperties=true` switches the format: the map is stored
as the text of a `java.util.Properties` file, which makes the column readable and survives class changes, at the price that *every key and value must be a `String`*. Quartz enforces it:
with `useProperties=true` and the code-defined Integer value `runs`, the startup of the Bookshelf service failed with

.Measured: the useProperties restriction
....

....
Source: https://www.quartz-scheduler.org/documentation/quartz-2.5.x/configuration/ConfigJobStoreTX.html[Quartz documentation: Configure JDBCJobStoreTX] and `StdJDBCDelegate` in the 2.5.2 source.

Use it when the map holds only strings and you want to evolve job classes freely; keep the default when jobs carry records or numbers (the Bookshelf `MemberReminderJob` stores `memberId` and
`loanId` as `Long`). The trade-offs of putting data in a `JobDataMap` at all are on xref:backend/scheduling/jobs-and-job-data.adoc[Jobs & Job Data].

== Managing the schema

The tables must exist before the scheduler starts. Spring Boot can create them for you, and a migration tool can create them better.

=== spring.quartz.jdbc.initialize-schema

`spring.quartz.jdbc.initialize-schema` takes the Spring `DatabaseInitializationMode` values `embedded` (the default), `always` and `never`. The initializer is the bean
`QuartzDataSourceScriptDatabaseInitializer`, created only when the property is not `never`; it runs the script selected by `spring.quartz.jdbc.schema` before the scheduler is created.

.The three initialization modes, measured on PostgreSQL 17 and H2 (Boot 4.1.1)
[cols="2,5,5",options="header"]
|===
|Mode |Embedded database (H2) |Real database (PostgreSQL)

|`embedded` (default)
|The eleven tables are created (`qrtz tables=11`)
|*Nothing is created.* Startup fails with `PSQLException: ERROR: relation "qrtz_job_details" does not exist` wrapped in `Couldn't retrieve job`

|`always`
|Script runs on every start
|The script runs on every start. Because it begins with `DROP TABLE IF EXISTS`, *every stored job and trigger is deleted at every restart*: a job named `survivor` scheduled at runtime existed after a restart with `never` and did not exist after a restart with `always`

|`never`
|Nothing runs; on an empty database `Table "QRTZ_JOB_DETAILS" not found`
|Nothing runs; on an empty database the same `relation ... does not exist` failure
|===
Source: https://docs.spring.io/spring-boot/how-to/data-initialization.html[Spring Boot: Database Initialization] and
https://docs.spring.io/spring-boot/reference/io/quartz.html[Spring Boot: Quartz Scheduler]

*Why `always` destroys triggers.* The scripts are *installers*, not migrations: the first thing they do is drop every `QRTZ_` table so that they can create it afresh. Spring Boot does not
know that, it simply runs the script again at each startup. The result is a service that works perfectly in development (where an empty schedule at every start is what you
want) and silently loses every runtime-created reminder, every paused trigger and every `@PersistJobDataAfterExecution` counter in production. The code-defined jobs reappear because
the beans re-register them, which hides the problem until someone notices that the per-member reminders are gone. Use `always` for throwaway tests and demos, `embedded` (the default)
for an in-memory H2, and `never` with Flyway or Liquibase for anything that has data worth keeping. Note the opposite trap of the default: `embedded` on a real database is not
"create if missing", it is "do nothing", and the failure message is the missing table.

A good habit while developing a schema script or a new database page is to set `continue-on-error: false` so every error is visible, and to leave the default for the unavoidable case of the Oracle scripts
that Boot runs. In production none of this applies, because Boot should not run the script at all.

On Spring Boot 3.5.16 `spring.quartz.jdbc.continue-on-error` does not exist: the `jdbc` settings are a nested class with four properties (`initialize-schema`, `schema`, `platform`, `comment-prefix`) and the initializer hard-codes `continue-on-error=true`, so script errors are always skipped there and a `continue-on-error: false` line is not an error but has no effect. The property was added in Spring Boot 4.0.

[[ordering]]
=== The scheduler waits for the schema

Whatever creates the tables, it has to finish before the scheduler asks for a trigger. Spring Boot guarantees that with its database-initialization ordering:
`QuartzAutoConfiguration` imports `DatabaseInitializationDependencyConfigurer`, and the class `SchedulerDependsOnDatabaseInitializationDetector` declares that beans of type `Scheduler` and
`SchedulerFactoryBean` depend on database initialization. The initializers it recognizes include Boot's own script initializers (Quartz's, `spring.sql.init`), Flyway and Liquibase. The effect is
visible in the measured runs of the next two sections: with `initialize-schema=never` and an empty database, the Flyway or Liquibase migration ran first and the scheduler started on the
tables it had just created, with no `@DependsOn` anywhere.
Source: https://github.com/spring-projects/spring-boot/blob/v4.1.1/module/spring-boot-quartz/src/main/java/org/springframework/boot/quartz/autoconfigure/SchedulerDependsOnDatabaseInitializationDetector.java[4.1.1 `SchedulerDependsOnDatabaseInitializationDetector` source].

=== Flyway

For anything beyond a demo the schema is a versioned migration, like the rest of the database (the reasoning, and how to choose a tool, are on
xref:database/schema-evolution/index.adoc[Schema Evolution] and xref:database/schema-evolution/choosing-a-migration-tool.adoc[Choosing a Migration Tool]; Flyway has no page of its own there).
Take the Quartz script for your database from the jar, *delete the `DROP TABLE` lines*, and keep it as a migration.

.Dependencies for Flyway on Spring Boot 4.1 (Maven)
[source,xml]
----
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-flyway</artifactId>
</dependency>
<dependency>
    <groupId>org.flywaydb</groupId>
    <artifactId>flyway-database-postgresql</artifactId>
</dependency>
----

.Producing the migration from the Quartz jar
[source,bash]
----

  | sed '/^DROP TABLE/d' > src/main/resources/db/migration/V1__quartz_tables.sql
----

.Letting Flyway own the schema (application.yml)
[source,yaml]
----
spring:
  flyway:
    enabled: true            # default; locations default to classpath:db/migration
  quartz:
    job-store-type: jdbc
    jdbc:
      initialize-schema: never
    properties:
      org.quartz.jobStore.driverDelegateClass: org.quartz.impl.jdbcjobstore.PostgreSQLDelegate
----
Source: https://docs.spring.io/spring-boot/how-to/data-initialization.html[Spring Boot: Database Initialization]

Measured on `postgres:17` with Flyway 12.4.0 and the file above named `V1__quartz_tables.sql`: on an empty database the start created the eleven `qrtz_*` tables plus `flyway_schema_history` (one row, version 1, description
`quartz tables`, success true), the four Bookshelf jobs fired (`cacheRefresh` three times, `overdueLoanReminders` twice) and the job store was `LocalDataSourceJobStore` with `PostgreSQLDelegate`. A second start on the migrated database found
nothing to do (still one history row) and ran the jobs again. The control run, with nothing managing the schema and `initialize-schema=never`, failed with `relation "qrtz_job_details" does not exist`.

The Flyway starter appeared in Spring Boot 4.0 (the 4.0.0 milestone releases are the first versions of `spring-boot-starter-flyway` on Maven Central); on Spring Boot 3.5.16 add `flyway-core` and the database module directly. The property names
under `spring.flyway.*` are the same.

A Quartz upgrade that changes the DDL (2.5.2 changed the SQL Server script to `NVARCHAR` columns, see <<what-changed>>) becomes a new `V2__...` migration written by you, which is the point of owning the schema: the Quartz jar changes
whenever Boot does, and you decide when the tables change.

=== Liquibase

The Quartz jar also contains a Liquibase changelog, `org/quartz/impl/jdbcjobstore/liquibase.quartz.init.xml`. It is *inside the Quartz jar* (`org.quartz-scheduler:quartz`, present in the 2.3.2, 2.4.1 and 2.5.2 jars: measured), not

[[dedicated-datasource]]
== A dedicated Quartz database

Quartz does not have to share the application's database. Two reasons are common: the business data lives in a database Quartz cannot use (MongoDB, Redis, Elasticsearch: none of them has a Quartz job store that works on the
Quartz 2.5.2 that Boot manages, see <<non-jdbc>>), or the team wants the high-churn trigger tables, their locking and their vacuuming out of the business database. Spring Boot supports this with two qualifier annotations
in `org.springframework.boot.quartz.autoconfigure`.

* `@QuartzDataSource` marks the `DataSource` bean Quartz must use. It is honoured in two places in `QuartzAutoConfiguration`: the data source passed to `SchedulerFactoryBean.setDataSource`, and the data source the
  schema initializer runs the script against. Without it Boot uses the single (or `@Primary`) `DataSource`.
* `@QuartzTransactionManager` marks the `PlatformTransactionManager` bean that Boot sets on the `SchedulerFactoryBean` with `setTransactionManager`. It exists in Spring Boot 4.1.1 (the source carries `@since 4.0.0` for the new package; the 3.5.16 jar also contains it, in the old package: measured by listing the jar). Its Javadoc says it is meant for a secondary transaction manager when another one is marked `@Primary`. Without it Boot takes the one transaction manager it can find
  (`ObjectProvider.getIfUnique()`, so the `@Primary` one if there are several), and none at all if there is no unique candidate.

What the transaction manager is used for: `SchedulerFactoryBean` registers the `JobDetail`, `Calendar` and `Trigger` beans in a single transaction when it starts. The transaction is only meaningful if the transaction manager
manages the *Quartz* data source. This was measured: the registration was made to fail halfway (two durable `JobDetail`s and a `Trigger` that names a calendar that does not exist, which makes `scheduleJob` throw
`SchedulerException: Calendar not found: doesNotExist` after both jobs were stored), with the business `DataSource` (H2) `@Primary` and Quartz on PostgreSQL 17.

.Which transaction manager Quartz registers its beans with (measured)
[cols="4,3,3",options="header"]
|===
|Configuration |Transactions begun |Rows left in `QRTZ_JOB_DETAILS` after the failed start

|`@QuartzDataSource` and `@QuartzTransactionManager` (the application's manager is `@Primary`)
|Quartz manager 1, application manager 0
|*0*: the registration was rolled back

|`@QuartzDataSource` only; the `@Primary` manager belongs to the application data source
|Application manager 1, Quartz manager 0
|*2*: the manager used is for a different database, so nothing is rolled back
|===
Source: https://docs.spring.io/spring-boot/reference/io/quartz.html[Spring Boot: Quartz Scheduler] and the 4.1.1 `QuartzTransactionManager` and `QuartzAutoConfiguration` sources.

The second row is the pitfall: a half-registered schedule after a failed start is not catastrophic, but the same mismatch applies to every `scheduler.scheduleJob(...)` you call from a `@Transactional` service: the
application transaction does not include the Quartz tables, so a rollback of the business transaction leaves the trigger in place. If you want the two to commit together they must be in the *same* database (use one `DataSource`),
and if they cannot be, treat the scheduler call as a separate step (see the consistency discussion on xref:backend/scheduling/database-mongodb.adoc[the MongoDB page]).

.Business data in one database, Quartz in another (Bookshelf, compiled and run)
[source,java]

    @ConfigurationProperties("bookshelf.datasource")

        return new DataSourceProperties();

    @Bean @Primary

    HikariDataSource appDataSource(@Qualifier("appDataSourceProperties") DataSourceProperties properties) {
        return properties.initializeDataSourceBuilder().type(HikariDataSource.class).build();
    }

    @Bean @Primary
    PlatformTransactionManager appTransactionManager(DataSource appDataSource) {
        return new DataSourceTransactionManager(appDataSource);
    }

    // Quartz tables
    @Bean
    @ConfigurationProperties("bookshelf.quartz.datasource")
    DataSourceProperties quartzDataSourceProperties() {
        return new DataSourceProperties();
    }

    @Bean @QuartzDataSource
    @ConfigurationProperties("bookshelf.quartz.datasource.hikari")
    HikariDataSource quartzDataSource(@Qualifier("quartzDataSourceProperties") DataSourceProperties properties) {
        return properties.initializeDataSourceBuilder().type(HikariDataSource.class).build();
    }

    @Bean @QuartzTransactionManager
    PlatformTransactionManager quartzTransactionManager(@QuartzDataSource DataSource quartzDataSource) {
        return new DataSourceTransactionManager(quartzDataSource);
    }
}

annotations live in `org.springframework.boot.autoconfigure.quartz`.

== Sizing the connection pool

Quartz needs more connections than people expect. The scheduler thread, the misfire handler and the cluster manager each use the database, and every worker thread uses a connection when its job completes
(`triggeredJobComplete` updates the trigger and deletes the fired row). The Quartz documentation states the rule on both the data sources page and the best-practices page: configure the data source's maximum connections to at least the number
of worker threads in the pool plus three, more if the application calls the scheduler API often, and at least four for the non-managed data source of a `JobStoreCMT`. The extra three match the three housekeeping threads; the page you are reading verified the *rule* against the documentation, not by
exhausting a pool. (An earlier outline of this section said "threads plus two"; the official text says plus three, which is what to use.)

The default makes it matter. Quartz's thread pool defaults to 10 threads (measured 10 under Boot) and Hikari's default pool is 10 connections, shared with the application, so a busy 10-thread scheduler on the application's default pool is
already under the recommendation. Raise the pool, or give Quartz its own, as in the previous section:

.Pool sizing for the default ten threads (application.yml)
[source,yaml]
----
spring:
  datasource:
    hikari:
      maximum-pool-size: 20     # application traffic (about 7) plus Quartz (10 threads + 3)
  quartz:
    properties:
      org.quartz.threadPool.threadCount: "10"
----
Source: https://www.quartz-scheduler.org/documentation/quartz-2.5.x/configuration/ConfigDataSources.html[Quartz documentation: Configure DataSources] and
https://www.quartz-scheduler.org/documentation/quartz-2.5.x/best-practices.html[Quartz documentation: Best Practices]

When Quartz manages its own pool (plain Quartz, or a `JobStoreTX` set up by hand) the pool is configured with `org.quartz.dataSource.NAME.*`; the documented property that selects HikariCP is `provider = hikaricp`, not the
`driver = hikaricp` that an example on the same page uses, and since Quartz 2.4.0 HikariCP and c3p0 are `provided` dependencies you have to add yourself. The production consequences, including the one scheduler per database
connection budget of a cluster, are on xref:backend/scheduling/production-and-best-practices.adoc[Production & Best Practices].

== Code-defined jobs and stored jobs: overwrite-existing-jobs

With a persistent store there are now two sources of truth for a job: the `JobDetail` and `Trigger` beans in the code and the rows the database already has. Spring's `SchedulerFactoryBean` reconciles them when it
starts, in `SchedulerAccessor.registerJobsAndTriggers`, controlled by one switch, `spring.quartz.overwrite-existing-jobs` (default false). The flow, read from the source:

.How a code-defined JobDetail bean reaches the job store on startup (`SchedulerAccessor`, Spring Framework 7.0.9)
[mermaid]
....
flowchart TD
    S[Context refresh: SchedulerFactoryBean.afterPropertiesSet creates the scheduler and its job store] --> T{Transaction manager set?}
    T -- yes --> TB[Begin one transaction]
    T -- no --> J
    TB --> J[For each JobDetail bean]
    J --> J1{overwrite-existing-jobs true or job not stored yet?}
    J1 -- yes --> J2[addJob with replace true]
    J1 -- no --> J3[Skip: the stored job and its data stay]
    J2 --> C
    J3 --> C[For each Calendar bean: addCalendar with replace and updateTriggers, always]
    C --> R[For each Trigger bean]
    R --> R1{Trigger stored already?}
    R1 -- no --> R2[scheduleJob: store the trigger, with its job if that is not stored]
    R1 -- yes, overwrite false --> R3[Skip: stored trigger, state and next fire time stay]
    R1 -- yes, overwrite true --> R4[rescheduleJob: replace the stored trigger by the bean]
    R2 --> E
    R3 --> E
    R4 --> E{Any exception?}
    E -- no --> OK[Commit; the scheduler is started later by the SmartLifecycle]
    E -- yes --> KO[Roll back, shut the scheduler down, the context fails to start]
....

Source: https://docs.spring.io/spring-framework/reference/integration/scheduling.html[Spring Framework: Task Execution and Scheduling] and the
https://github.com/spring-projects/spring-framework/blob/v7.0.9/spring-context-support/src/main/java/org/springframework/scheduling/quartz/SchedulerAccessor.java[7.0.9 `SchedulerAccessor` source].

Registration happens in `afterPropertiesSet`, before `start`; a scheduler that registers the same beans on every node (a cluster) is protected by the store: a race on the same trigger key ends in an
`ObjectAlreadyExistsException` that Spring logs at debug level and ignores ("assumably due to cluster race condition"). What the flow does *not* do matters as much: it never deletes anything. A job whose bean you removed from the
code stays in the database and keeps firing; a job created at runtime is never touched.

The effect was measured with the Bookshelf overdue-loan reminders on PostgreSQL 17 and the JDBC store: a first deployment (version 1 of the beans), then the same kind of changes production makes by itself (the job incremented its persisted
counter to 7, an operator paused the trigger, a reminder `reminders.loan-501` was scheduled at runtime), then a redeployment with version 2 of the beans (a different description, job data, cron expression and calendar, a new
`newsletter` job and the `retiredJob` bean removed), once with `overwrite-existing-jobs=false` and once with `true`.

The practical rules that follow from the table:

* With the default (`false`) the code is only the *initial* definition: a changed cron expression, misfire instruction or job data in the code does *not* reach an already deployed environment. This is what you want when operators
  edit schedules at runtime (pause, reschedule) and a restart must not undo it; it is a trap when you change a cron in a pull request and nothing changes in production. The Boot reference says the same: a restart does not re-create
  or change jobs that already exist.
* With `true` every start resets every code-defined job and trigger to the code's version, including state: paused triggers resume, and `@PersistJobDataAfterExecution` counters go back to the bean's value. It is the right setting for
  schedules that are code-only and where the code is the truth; it is wrong for any job whose data the job itself maintains.
* Neither setting removes a job. Remove obsolete jobs explicitly, through a one-off migration or an administrative call (`Scheduler.deleteJob`), or accept that they keep firing.
* The calendar is always replaced, even with `false`, and `updateTriggers=true` makes the stored triggers that use it recompute their next fire time.
* A middle road that keeps both properties is to leave `overwrite-existing-jobs` false and update specific jobs from code at startup (a `SchedulerFactoryBeanCustomizer` or an `ApplicationRunner` that calls
  `rescheduleJob` for the triggers whose definition you changed, compare first, replace only on difference). The dynamic management of schedules is the subject of
  xref:backend/scheduling/dynamic-scheduling-and-management.adoc[Dynamic Scheduling & Management].

== Never write to the QRTZ tables yourself

The tables look like an ordinary schema, and a `UPDATE QRTZ_TRIGGERS SET TRIGGER_STATE = 'PAUSED'` is tempting during an incident. The Quartz best-practices page has a section titled "Never Write Directly To Quartz's Tables", and warns
that doing so can corrupt data, make jobs vanish without running or appear stuck, and cause deadlocks. The reason is visible in the structure above: a trigger's state, its next fire time, the fired-trigger
row of its current execution, the row locks and the in-memory view of the scheduler thread all have to agree, and Quartz maintains that agreement in code under locks, in several tables at once, with the serialized
`JobDataMap` and calendar blobs in binary form. Read the tables freely (the queries above are safe, a read-only reporting user is a good idea), and change them only through the `Scheduler` API, the Actuator
`quartz` endpoint (trigger-now only) or your own management endpoints. Everything you do through the API is also correct for every other node of a cluster at once, because it goes through the store.
Source: https://www.quartz-scheduler.org/documentation/quartz-2.5.x/best-practices.html[Quartz documentation: Best Practices]

== Pitfalls

.Job store and persistence pitfalls (all measured unless marked source)
[cols="3,4,4",options="header"]
|===
|Pitfall |What happens |What to do

|`initialize-schema=always` against a database you care about
|The script drops every `QRTZ_` table first, so every runtime job, pause and persisted counter is deleted at each restart
|`never` plus Flyway or Liquibase; keep `always` for tests

|The default `embedded` on a real database
|Nothing is created; startup fails with `relation "qrtz_job_details" does not exist`
|Let a migration tool create the schema, or use `always` once in development

|`continue-on-error=true` (the default) hides script errors
|A wrong platform or an unrunnable script (SQL Server, a mismatched `platform`) creates nothing and the failure shows later as a missing table
|Set it to `false` while developing the script

|No `driverDelegateClass` on PostgreSQL or SQL Server
|`Bad value for type long : \xaced...` (PostgreSQL) or `FOR UPDATE clause allowed only for DECLARE CURSOR` (SQL Server) at the first trigger store
|Set `PostgreSQLDelegate` or `MSSQLDelegate`

|Two `DataSource` beans, none `@Primary` (with or without a `@QuartzDataSource`)
|No error: Boot silently uses `RAMJobStore`; the schedule is lost at restart
|Mark the application's data source `@Primary` and the Quartz one `@QuartzDataSource`; assert `isJobStoreSupportsPersistence()` in a test

|`@QuartzDataSource` without `@QuartzTransactionManager` while a `@Primary` manager exists for another database
|Registration runs in the wrong transaction (two job rows left after a failed start); API calls from `@Transactional` code do not commit with the business data
|Add `@QuartzTransactionManager`, or keep Quartz and business data in one database

|Overriding `org.quartz.jobStore.class` with `jdbc`
|`DataSource name not set.`
|Leave the class to Boot; custom stores need `job-store-type: memory`

|`overwrite-existing-jobs=false` and a changed cron in the code
|The deployed environment keeps the old cron and job data
|Redeploy with `true` once, update the trigger with `rescheduleJob`, or change it through the management endpoint

|`overwrite-existing-jobs=true` with a counter kept in the `JobDataMap`
|Every restart resets the counter, resumes paused triggers and resets the description
|Keep it `false` for jobs that maintain their own data

|Removing a job bean
|The stored job and trigger remain and keep firing
|Delete it explicitly with `Scheduler.deleteJob`

|Writing to `QRTZ_` tables by hand
|Corrupt state, vanished or stuck jobs, deadlocks (Quartz best practices)
|Use the `Scheduler` API

|Pool smaller than threads plus three
|Worker threads and the housekeeping threads wait for connections (the Quartz guidance; not exhausted in a test here)
|Size the pool for the thread count, or give Quartz its own pool

|`useProperties=true` with non-String job data
|Startup or `addJob` fails with `JobDataMap values must be Strings...`
|Keep strings only, or leave the default

|A `tablePrefix` the script does not use
|`relation "bks_qrtz_job_details" does not exist`
|Edit the script and set `spring.quartz.jdbc.schema` with the same prefix

|A community NoSQL store on Quartz 2.5
|MongoDB: scheduler "started", no job ever fires. Redis: startup failure
|Quartz on SQL plus MongoDB or Redis for data, or ShedLock
|===

[[what-changed]]
== What changed

.Changes that touch job stores and persistence
[cols="2,5",options="header"]
|===
|Release |Change

|Quartz 2.4.0
|`TerracottaJobStore` removed (the 2.3.2 jar contains eight Terracotta classes, the 2.4.1 and 2.5.2 jars none); clustering is JDBC-only. HikariCP and c3p0 become `provided` dependencies, so a Quartz-managed pool needs them added.

|Quartz 2.5.0
|Jakarta namespace (`jakarta.transaction` in `JobStoreCMT`) and Java 11; the misspelled `JobDetail.isConcurrentExectionDisallowed()` is gone, which breaks community stores compiled against 2.4 and earlier.

|Quartz 2.5.x scripts
|The jar grows from 22 DDL scripts (2.3.2 and 2.4.1) to 25 in 2.5.2: `tables_oracle23.sql` (Oracle 23ai, `BOOLEAN` columns) and two GaussDB scripts. The SQL Server script uses `NVARCHAR` columns (commit of 29 November 2025, in the released 2.5.2).

|After Quartz 2.5.2 (unreleased on `main`)
|Pull request 1515 binds the scheduler-state instance name as `NVARCHAR` in `MSSQLDelegate` (the fix for clustered check-in deadlocks on SQL Server); not part of 2.5.2 or of any released version.

|Spring Boot 3.5 to 4.x
|The Quartz auto-configuration moved to `org.springframework.boot.quartz.autoconfigure` in the new `spring-boot-quartz` module: `@QuartzDataSource`, `@QuartzTransactionManager`, `SchedulerFactoryBeanCustomizer` and `QuartzProperties` change package, the property names (`spring.quartz.job-store-type`, `spring.quartz.jdbc.*`, `spring.quartz.overwrite-existing-jobs`) do not. The Flyway and Liquibase starters appear in 4.0.

|Spring Framework 6.2 to 7.0
|`LocalDataSourceJobStore` and `SchedulerAccessor` keep their behaviour; the 7.0 sources add JSpecify nullness annotations.

|Documentation versus code
|The Quartz configuration page says the RAM store's `misfireThreshold` is 60000 (it is 5000, 60000 is the JDBC store and the bundled `quartz.properties`); lists `CloudscapeDelegate` (not in 2.5.2); and uses `driver = hikaricp` (the property is `provider`). The Boot reference says the SQL Server script "may need" edits (it cannot run through Boot unedited). The collected list is on xref:backend/scheduling/migration-and-whats-changed.adoc[Migration & What's Changed].
|===
