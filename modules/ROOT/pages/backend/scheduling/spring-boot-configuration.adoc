Spring Boot turns Quartz into a handful of `spring.quartz.*` properties, a hook for code (`SchedulerFactoryBeanCustomizer`) and a
pass-through for every raw Quartz key. This page is the reference for all three: which property does what and what it defaults to,
which layer wins when two of them say different things, and what Boot does _not_ do for you (read `quartz.properties`, register
listener beans, use your `Executor` bean, run two schedulers). The first steps with the starter are on
xref:backend/scheduling/getting-started-with-spring-boot.adoc[Getting Started with Spring Boot], the store-specific properties are
treated in depth on xref:backend/scheduling/job-stores-and-persistence.adoc[Job Stores & Persistence], and the general Spring Boot
mechanics (property sources, profiles, relaxed binding) are on xref:backend/springboot/configuration-and-profiles.adoc[Configuration and Profiles].

It was written against Quartz 2.5.2, Spring Boot 4.1.1, Spring Framework 7.0.9 and Java 21, and verified on 5 October 2026: every
default below was read from the 4.1.1 sources and every behaviour was run in a test project on exactly those versions (macOS, JDK 25
running Java 21 bytecode, Maven 3.9, PostgreSQL 17 in Docker), and the outputs are quoted, not assumed. *Spring Boot 3.5.16* manages
the same Quartz 2.5.2 and uses the same property names, with these differences: the auto-configuration classes live in
`org.springframework.boot.autoconfigure.quartz` instead of `org.springframework.boot.quartz.autoconfigure`, the `jdbc.*` settings are
a nested class of `QuartzProperties` that has no `continue-on-error` property, and Spring Framework is 6.2.19. They are collected in
<<_what_changed,What changed>>.

== Where a setting comes from

A Quartz scheduler under Boot is configured in layers, and knowing the order explains most surprises. Boot reads `spring.quartz.*`
into `QuartzProperties` and `QuartzJdbcProperties`, creates one `SchedulerFactoryBean` from them, lets every
`SchedulerFactoryBeanCustomizer` bean change it, and Spring's `SchedulerFactoryBean` finally merges all Quartz keys into one
`java.util.Properties` object that it hands to Quartz's `StdSchedulerFactory`.

.How the configuration reaches Quartz (QuartzAutoConfiguration and SchedulerFactoryBean, read from the 4.1.1 and 7.0.9 sources)
[mermaid]
....
flowchart TD
    A["application.yml, profile files, environment: spring.quartz.*"] --> B["QuartzProperties and QuartzJdbcProperties"]
    B --> C["QuartzAutoConfiguration builds ONE SchedulerFactoryBean: name, auto-startup, startup-delay, shutdown wait, overwrite flag, SpringBeanJobFactory, JobDetail, Trigger and Calendar beans"]
    A2["spring.quartz.properties.org.quartz.*, raw keys"] --> C
    C --> D["SchedulerFactoryBeanCustomizer beans in Order: Boot's own JDBC customizer at order 0, yours after it"]
    D --> E["SchedulerFactoryBean merges the keys: Spring defaults first, then the configLocation file if one was set, then quartzProperties on top"]
    E --> F["StdSchedulerFactory initialize with the merged Properties"]
    F --> G["Scheduler: job store, thread pool, plugins, global listeners"]
....

The layers, from the weakest to the strongest, are these. Each row was checked in `SchedulerFactoryBean.initSchedulerFactory`.

.Who wins when two layers set the same key
[cols="1,3,5",options="header"]
|===
|Rank |Layer |What it contributes

|1
|Quartz's code defaults
|Used only for keys nobody set: a `RAMJobStore`, instance id `NON_CLUSTERED`, `idleWaitTime` 30000 ms and so on. The `quartz.properties` file inside the Quartz jar is *not* a layer: it is read only by `new StdSchedulerFactory()` without arguments, and Spring always passes properties.

|2
|Spring's defaults
|`org.quartz.threadPool.class=org.quartz.simpl.SimpleThreadPool` and `org.quartz.threadPool.threadCount=10`, set by `SchedulerFactoryBean` itself (or `LocalTaskExecutorThreadPool` when a task executor is set). `ResourceLoaderClassLoadHelper` is added as class loading helper.

|3
|A properties file given to `setConfigLocation`
|Only when a customizer sets it. Boot never does, so a `quartz.properties` on the classpath is ignored (see <<_quartz_properties_files,below>>).

|4
|`spring.quartz.properties.*`
|Every entry overrides the same key from layers 1 to 3. Passed through only when the map is not empty.

|5
|Typed `spring.quartz.*` properties and `setSchedulerName`
|`scheduler-name` replaces `org.quartz.scheduler.instanceName` even when both are set (measured: both set gives the Boot name).

|6
|Customizers
|Run last, in `@Order`, on the `SchedulerFactoryBean` itself, so they can overwrite anything above (`setQuartzProperties`, `setConfigLocation`, `setTaskExecutor`, `setJobFactory`, ...).
|===

One special case follows from `putIfAbsent`: with a `DataSource` set, `org.quartz.jobStore.class` defaults to
`LocalDataSourceJobStore` unless a raw property already names a class, so a raw `jobStore.class` *replaces* the
Spring-aware store (measured in <<_overriding_org_quartz_jobstore_class,Overriding org.quartz.jobStore.class>>). Note also that a
customizer's `setQuartzProperties` replaces Boot's whole map; it does not add to it.

== Every spring.quartz property

Reading the defaults from the source is one thing; asking the running Boot is better, because it is the code that decides. This
test binds both property classes from an empty `Environment`, which is exactly what Boot does when nothing is configured.

.QuartzDefaultsTest.java: the defaults, bound from nothing (Boot 4.1.1)
[source,java]
----
import org.springframework.boot.context.properties.bind.Binder;
import org.springframework.boot.context.properties.source.ConfigurationPropertySources;
import org.springframework.boot.quartz.autoconfigure.QuartzJdbcProperties;
import org.springframework.boot.quartz.autoconfigure.QuartzProperties;
import org.springframework.core.env.StandardEnvironment;

class QuartzDefaultsTest {

    static String dump() {
        Binder binder = new Binder(ConfigurationPropertySources.get(new StandardEnvironment()));
        QuartzProperties q = binder.bindOrCreate("spring.quartz", QuartzProperties.class);
        QuartzJdbcProperties j = binder.bindOrCreate("spring.quartz.jdbc", QuartzJdbcProperties.class);
        return "job-store-type=" + q.getJobStoreType() + "\nscheduler-name=" + q.getSchedulerName()
                + "\nauto-startup=" + q.isAutoStartup() + "\nstartup-delay=" + q.getStartupDelay()
                + "\nwait-for-jobs-to-complete-on-shutdown=" + q.isWaitForJobsToCompleteOnShutdown()
                + "\noverwrite-existing-jobs=" + q.isOverwriteExistingJobs() + "\nproperties=" + q.getProperties()
                + "\njdbc.initialize-schema=" + j.getInitializeSchema() + "\njdbc.schema=" + j.getSchema()
                + "\njdbc.platform=" + j.getPlatform() + "\njdbc.continue-on-error=" + j.isContinueOnError()
                + "\njdbc.comment-prefix=" + j.getCommentPrefix();
    }
}
----

What each property does, with the measurements that are not obvious from its name:

=== job-store-type

`memory` (the default) leaves Quartz on its `RAMJobStore`; `jdbc` makes Boot pass the `DataSource` to Spring's `LocalDataSourceJobStore`
and create the schema if asked to. The enum is `JobStoreType` with exactly these two values. The conditions under which `jdbc`
silently turns back into `memory` are the second diagram of this page, in <<_which_job_store_boot_selects,Which job store Boot selects>>.
A store from a library (a MongoDB or Redis store) is not a third value: it is plugged in with `job-store-type` left at `memory` and
`spring.quartz.properties.org.quartz.jobStore.class` (measured with a `RAMJobStore` subclass, which Boot honoured).

=== scheduler-name

No default. When it is not set the scheduler is named after the `SchedulerFactoryBean` bean, `quartzScheduler` (measured). The name is
part of every key in a JDBC job store (`SCHED_NAME` is the first column of every primary key), so all nodes of one cluster must share
it and two applications that share tables must not. When both `spring.quartz.scheduler-name` and
`spring.quartz.properties.org.quartz.scheduler.instanceName` are set, the first wins (measured: the scheduler was named `FromBoot`).
Setting only the raw `instanceName` is the third route in `SchedulerFactoryBean` (read from the source; the cluster and Actuator
pages use `scheduler-name`).

=== auto-startup, startup-delay and the lifecycle

`auto-startup` is a `SchedulerFactoryBean` `SmartLifecycle` flag. With `false` the scheduler is created, jobs and triggers are
stored, and nothing fires until somebody calls `scheduler.start()`: this is how tests and "migrate then start" deployments hold
the scheduler back. `startup-delay` is a `Duration`, but Boot passes it as `(int) getSeconds()`, so the sub-second part is cut
off. All of this was measured by reading `isStarted()` and `isInStandbyMode()` right after the context was ready:

.What auto-startup and startup-delay do (Boot 4.1.1, memory store)
[cols="3,4,4",options="header"]
|===
|Setting |Right after startup |Later

|`startup-delay: 3s`
|`isStarted()` false, in standby
|3.5 seconds later: started, not in standby

|`startup-delay: 1500ms`
|`isStarted()` false (the delay is 1 second)
|1.5 seconds later: started

|`startup-delay: 500ms`
|`isStarted()` *true*: the delay is 0 seconds
|

|`auto-startup: false`
|`isStarted()` false, in standby, 4 jobs stored
|after `scheduler.start()`: started
|===
Source: https://github.com/spring-projects/spring-boot/blob/v4.1.1/module/spring-boot-quartz/src/main/java/org/springframework/boot/quartz/autoconfigure/QuartzAutoConfiguration.java[QuartzAutoConfiguration.java (v4.1.1)]
(`setStartupDelay((int) properties.getStartupDelay().getSeconds())`); the times are the output of the run.

=== wait-for-jobs-to-complete-on-shutdown

With `true`, closing the context calls `scheduler.shutdown(true)` and the thread pool waits for running jobs. With the default
`false` it does not. Measured with a job that sleeps 4 seconds, closing the context while it ran:

.Closing the context with a 4-second job running (memory store, default SimpleThreadPool)
[cols="3,2,3",options="header"]
|===
|`wait-for-jobs-to-complete-on-shutdown` |`close()` took |Job after `close()` returned

|`false`
|3 ms
|still running, abandoned
|`true`
|3902 ms
|finished
|===
Source: output of the run; the mechanism is `QuartzScheduler.shutdown(boolean)` in the Quartz 2.5.2 sources, which ends in
`getThreadPool().shutdown(waitForJobsToComplete)`.

That last call is why the setting has a catch with a Spring `TaskExecutor` as thread pool, described in
<<_a_spring_taskexecutor_instead_of_the_thread_pool,A Spring TaskExecutor instead of the thread pool>>.

=== overwrite-existing-jobs, properties and jdbc

`overwrite-existing-jobs` decides who wins when a `JobDetail` or `Trigger` bean meets the same key in a persistent store; the
decision tree and its measurement are in the "job-registration decision" section of
xref:backend/scheduling/getting-started-with-spring-boot.adoc[Getting Started with Spring Boot]. `properties` is the raw pass-through,
the next section. The five `jdbc.*` properties (`initialize-schema`, `schema`, `platform`, `continue-on-error`, `comment-prefix`) are
explained with their failure modes on xref:backend/scheduling/job-stores-and-persistence.adoc[Job Stores & Persistence]; only their
defaults are repeated in the reference table at the end of this page.

== Raw Quartz properties: spring.quartz.properties

Everything under `spring.quartz.properties` is copied unchanged into the Quartz configuration, so any key from the Quartz
configuration reference is available. The map has string values, so numbers and booleans are quoted in YAML.

.The keys most often set (application.yml fragment)
[source,yaml]
----
spring:
  quartz:
    properties:
      org.quartz.scheduler.instanceId: AUTO                       # cluster nodes: a generated id
      org.quartz.scheduler.idleWaitTime: "30000"                  # maximum sleep of the scheduler thread, ms
      org.quartz.threadPool.threadCount: "10"                     # SimpleThreadPool size (Spring's default is 10)
      org.quartz.jobStore.misfireThreshold: "60000"               # how late a trigger may be before it is a misfire
      org.quartz.jobStore.isClustered: "true"                     # JDBC store only
      org.quartz.jobStore.clusterCheckinInterval: "5000"          # JDBC store only
      org.quartz.jobStore.driverDelegateClass: org.quartz.impl.jdbcjobstore.PostgreSQLDelegate   # JDBC store only
----
Source: https://www.quartz-scheduler.org/documentation/quartz-2.5.x/configuration/ConfigMain.html[Quartz documentation: Main Configuration]
and https://docs.spring.io/spring-boot/reference/io/quartz.html[Spring Boot: Quartz Scheduler].

=== Overriding org.quartz.jobStore.class

`SchedulerFactoryBean` sets the store class only when no raw key names one. That is the door for a store from a library, and a trap for
everyone else. All five cases were run (results taken from the verification run of this section):

[cols="5,5",options="header"]
|===
|Configuration |Result

|`memory` and `org.quartz.simpl.RAMJobStore`

=== A key for the wrong store fails at startup

The same property map goes to whichever store is active, and a store rejects keys it has no setter for. That is why a `prod` profile
copied onto a `memory` store does not run quietly: it does not start. Measured with `RAMJobStore`, one key at a time:

.Setting a JDBC-store key while the store is RAMJobStore (measured)
[cols="4,6",options="header"]

|Key |Result at startup

|`org.quartz.jobStore.misfireThreshold`
|accepted
|`org.quartz.jobStore.isClustered`

=== Environment variables lose the key's case

Quartz keys are case sensitive and mixed case (`org.quartz.threadPool.threadCount`). Spring Boot maps an environment variable
such as `SPRING_QUARTZ_PROPERTIES_ORG_QUARTZ_THREADPOOL_THREADCOUNT` to the lower-case key `org.quartz.threadpool.threadcount`, which
Quartz does not know. It is not an error; the setting just does nothing. Measured:

.Setting the thread count through the environment (Boot 4.1.1, default 10 threads)
[cols="5,2,3",options="header"]
|===
|How the value 4 was supplied |Pool size |Effective key seen by Boot

|nothing
|10
|

|environment variable `SPRING_QUARTZ_PROPERTIES_ORG_QUARTZ_THREADPOOL_THREADCOUNT=4`
|*10*, silently ignored
|`org.quartz.threadpool.threadcount`

|environment variable `SPRING_APPLICATION_JSON` with the full key (below)
|4
|`org.quartz.threadPool.threadCount`
|===
Source: https://docs.spring.io/spring-boot/reference/features/external-config.html[Spring Boot: Externalized Configuration]
(environment variable binding and `SPRING_APPLICATION_JSON`); the pool sizes are read back from the running scheduler.

.The variant that works: the key travels inside a JSON value, case intact
[source,bash]
----
SPRING_APPLICATION_JSON='{"spring.quartz.properties.org.quartz.threadPool.threadCount":"4"}' java -jar bookshelf.jar
----
Source: https://docs.spring.io/spring-boot/reference/features/external-config.html[Spring Boot: Externalized Configuration] (JSON application properties).

In Kubernetes, put raw Quartz keys in a mounted `application.yml` or in `SPRING_APPLICATION_JSON`, never in individual environment
variables. Typed properties such as `SPRING_QUARTZ_JOB_STORE_TYPE` are fine.

== SchedulerFactoryBeanCustomizer

`SchedulerFactoryBeanCustomizer` is a one-method functional interface (`void customize(SchedulerFactoryBean)`). Boot collects every bean
of that type, orders them with `@Order` (an unordered bean sorts last) and applies them to the factory bean just before it is
returned. Boot's own JDBC customizer, which sets the `DataSource` and the transaction manager, is registered at order 0, so yours run
after it and can override it. It is the one supported extension point; the properties cover about half of what
`SchedulerFactoryBean` can do, and the customizer covers the rest:

.SchedulerFactoryBean settings that only a customizer can change (verified setters, Spring Framework 7.0.9)
[cols="4,6",options="header"]
|===
|Setter |What it is for

|`setGlobalJobListeners`, `setGlobalTriggerListeners`, `setSchedulerListeners`
|Register listeners. Boot does *not* pick up listener beans (measured below).

|`setTaskExecutor`
|Use a Spring `Executor` as the thread pool instead of `SimpleThreadPool`.

|`setJobFactory`
|Replace the `SpringBeanJobFactory` that Boot installed, for example to add MDC context or counters.

|`setSchedulerContextAsMap`, `setApplicationContextSchedulerContextKey`
|Global data every job can read from the `SchedulerContext`, and the `ApplicationContext` itself.

|`setConfigLocation`, `setQuartzProperties`
|Load a file or add keys in code.

|`setDataSource`, `setNonTransactionalDataSource`, `setTransactionManager`
|What Boot's own JDBC customizer does; change it only when `@QuartzDataSource` and `@QuartzTransactionManager` are not enough.

|`setPhase`, `setAutoStartup`, `setStartupDelay`, `setExposeSchedulerInRepository`, `setWaitForJobsToCompleteOnShutdown`
|Lifecycle: the `SmartLifecycle` phase, and the properties that have a typed `spring.quartz` twin.
|===
Source: https://docs.spring.io/spring-framework/docs/current/javadoc-api/org/springframework/scheduling/quartz/SchedulerFactoryBean.html[SchedulerFactoryBean Javadoc]
and https://docs.spring.io/spring-boot/api/java/org/springframework/boot/quartz/autoconfigure/SchedulerFactoryBeanCustomizer.html[SchedulerFactoryBeanCustomizer API (Boot 4.1)].

=== Listeners are not registered for you

A `JobListener` or `TriggerListener` that is a Spring bean is not attached to the scheduler by Boot (`QuartzAutoConfiguration`
collects `JobDetail`, `Trigger`, `Calendar` and customizer beans, nothing else). Measured: a context with one `JobListener` bean and

=== Replacing the job factory

`setJobFactory` swaps the factory that creates job instances. Extend `SpringBeanJobFactory` (which is what Boot installs, with the
`ApplicationContext` set) and call `super`, so that constructor injection keeps working:

.A JobFactory that counts the jobs it creates
[source,java]
----
import org.quartz.spi.TriggerFiredBundle;
import org.springframework.boot.quartz.autoconfigure.SchedulerFactoryBeanCustomizer;
import org.springframework.context.ApplicationContext;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.scheduling.quartz.SpringBeanJobFactory;

import java.util.concurrent.atomic.AtomicInteger;

@Configuration(proxyBeanMethods = false)
class JobFactoryConfiguration {

    static final AtomicInteger CREATED = new AtomicInteger();

    static class CountingJobFactory extends SpringBeanJobFactory {
        @Override
        protected Object createJobInstance(TriggerFiredBundle bundle) throws Exception {
            CREATED.incrementAndGet();
            return super.createJobInstance(bundle);
        }
    }

    @Bean
    SchedulerFactoryBeanCustomizer countingJobFactory(ApplicationContext context) {
        CountingJobFactory jobFactory = new CountingJobFactory();
        jobFactory.setApplicationContext(context);
        return factory -> factory.setJobFactory(jobFactory);
    }
}
----
Source: https://docs.spring.io/spring-framework/docs/current/javadoc-api/org/springframework/scheduling/quartz/SpringBeanJobFactory.html[SpringBeanJobFactory Javadoc].
Run with the Bookshelf jobs firing every second: the factory created 3 job instances and the overdue-loan job fired 2 times, so autowiring still worked.

== The thread pool and why an Executor bean is not used

Boot's Quartz auto-configuration never looks for an `Executor`, `TaskExecutor` or `TaskScheduler` bean. The only way a Spring executor
reaches Quartz is `SchedulerFactoryBean.setTaskExecutor`, and Boot does not call it. The scheduler's threads are the
`SimpleThreadPool` that Quartz creates itself (`<scheduler name>_Worker-N`), ten of them unless configured. A common mistake is to
declare a tuned `ThreadPoolTaskExecutor` and expect Quartz jobs to run on it.

.ExecutorBeanConfiguration.java: an Executor bean that Quartz ignores
[source,java]
----
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.scheduling.concurrent.ThreadPoolTaskExecutor;

@Configuration(proxyBeanMethods = false)
class ExecutorBeanConfiguration {

    @Bean(name = "myExecutor")
    ThreadPoolTaskExecutor myExecutor() {
        ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
        executor.setThreadNamePrefix("my-exec-");
        executor.setCorePoolSize(2);
        executor.setMaxPoolSize(2);
        return executor;
    }
}
----
Source: https://docs.spring.io/spring-boot/reference/features/task-execution-and-scheduling.html[Spring Boot: Task Execution and Scheduling]
and https://docs.spring.io/spring-boot/reference/io/quartz.html[Spring Boot: Quartz Scheduler].

Measured with that bean and `spring.threads.virtual.enabled=true`, three jobs fired: the thread pool was `SimpleThreadPool` with 10 threads
and the jobs ran on platform threads named `BookshelfScheduler_Worker-N`, none on `my-exec-N`. A side effect worth knowing: declaring
any `Executor` bean made Boot's own `applicationTaskExecutor` back off (`applicationTaskExecutor present=false`), because
Boot creates it only `@ConditionalOnMissingBean(Executor.class)`. That affects `@Async` and the web layer, not just Quartz.

=== A Spring TaskExecutor instead of the thread pool

To run jobs on a Spring executor, hand it over explicitly. The class that makes it work is
`org.springframework.scheduling.quartz.LocalTaskExecutorThreadPool` (it exists in Spring Framework 7.0.9; `SchedulerFactoryBean` selects it
by itself when a task executor is set). It adapts the executor to Quartz's `ThreadPool` interface, and the adaptation is thin:
`getPoolSize()` returns -1, `blockForAvailableThreads()` always returns 1, `shutdown` does nothing and `runInThread` calls
`executor.execute`, returning `false` if the executor rejects the task. Those four facts are the rows of the table, each measured with
six jobs of 1.5 seconds triggered at the same moment:

.SimpleThreadPool against Spring executors (measured, Boot 4.1.1, six simultaneous 1.5-second jobs)
[cols="3,3,4",options="header"]
|===
|Thread pool |Result |Why it matters

|`SimpleThreadPool`, `threadCount=2`
|max 2 concurrent, three waves at 0, 1.5 and 3.0 s, `Worker-N` platform threads
|The scheduler thread waits for a free worker, so the pool size is a real cap.

|virtual `SimpleAsyncTaskExecutor`
|max *6* concurrent, all done after 1.55 s, virtual threads
|No cap at all: `blockForAvailableThreads()` always says one thread is free.

|`ThreadPoolTaskExecutor`, core = max = 2, unbounded queue
|max 2 concurrent, all six done after 4.6 s, platform threads
|Jobs queue inside the executor. Quartz thinks they have started, and the queue grows without limit if jobs are slow.

|`ThreadPoolTaskExecutor`, core = max = 2, `queueCapacity=0`
|only 2 of 6 ran; the other four triggers ended in state *ERROR*
|A rejected task makes `runInThread` return `false`; Quartz then sets the job's triggers to ERROR and does not fire them again. With a recurring trigger, one burst takes the job out of service until `Scheduler.resetTriggerFromErrorState(TriggerKey)` is called for it.

|`SimpleAsyncTaskExecutor`, virtual threads, `concurrency-limit=2`, blocking
|max 2 concurrent, six done after 4.6 s
|A real cap: the executor blocks the scheduler thread when the limit is reached.

|same, `reject-tasks-when-limit-reached=true`
|only 2 of 6 ran; four triggers in state *ERROR*
|The rejection case again.
|===
Source: https://github.com/spring-projects/spring-framework/blob/v7.0.9/spring-context-support/src/main/java/org/springframework/scheduling/quartz/LocalTaskExecutorThreadPool.java[LocalTaskExecutorThreadPool.java (v7.0.9)];
the durations and states are measured.

Three more consequences, two measured and one read from the source:

* *`threadCount` is not valid any more.* With a task executor set and `spring.quartz.properties.org.quartz.threadPool.threadCount`
  still present, startup fails with `ThreadPool class 'org.springframework.scheduling.quartz.LocalTaskExecutorThreadPool' props could not be
  configured`, caused by `NoSuchMethodException: No setter for property 'threadCount'`. Remove every `org.quartz.threadPool.*` key (Spring's default of 10 is
  a `SimpleThreadPool` setting).
* *Quartz no longer waits for running jobs.* `shutdown(true)` waits through `getThreadPool().shutdown(true)`, which is a no-op for this pool.
  With a virtual `SimpleAsyncTaskExecutor` and `wait-for-jobs-to-complete-on-shutdown=true`, `close()` took 1 ms and the 4-second job was
  still running afterwards. The executor has to do the waiting (next section).
* *A rejection is a one-way street.* When `runInThread` returns `false`, `QuartzSchedulerThread` logs "ThreadPool.runInThread() return false!"
  and calls `triggeredJobComplete(..., SET_ALL_JOB_TRIGGERS_ERROR)`: every trigger of that job goes to ERROR (the four rows above), and the
  application keeps running without that job (Quartz 2.5.2 source and the measured states).

=== Virtual threads

Quartz does not use virtual threads on its own: `spring.threads.virtual.enabled=true` changes Boot's `applicationTaskExecutor`, `@Async`, the
web server and `@Scheduled`, but the Quartz `SimpleThreadPool` keeps its platform threads (measured above). To run jobs on virtual threads,
give Quartz Boot's executor. The configuration below is switched on by a property and added by the `virtual` profile in
<<_the_complete_bookshelf_configuration,the complete configuration>>.

.A customizer that runs jobs on Boot's applicationTaskExecutor
[source,java]
----
import org.springframework.beans.factory.annotation.Qualifier;
import org.springframework.boot.autoconfigure.condition.ConditionalOnProperty;
import org.springframework.boot.quartz.autoconfigure.SchedulerFactoryBeanCustomizer;
import org.springframework.context.annotation.Bean;
import org.springframework.core.annotation.Order;
import org.springframework.core.task.AsyncTaskExecutor;

// inside BookshelfQuartzConfiguration
@Bean
@Order(20)
@ConditionalOnProperty(name = "bookshelf.quartz.use-application-task-executor", havingValue = "true")
SchedulerFactoryBeanCustomizer applicationTaskExecutorForJobs(
        @Qualifier("applicationTaskExecutor") AsyncTaskExecutor executor) {
    return factory -> factory.setTaskExecutor(executor);
}
----
Source: https://docs.spring.io/spring-boot/reference/features/task-execution-and-scheduling.html[Spring Boot: Task Execution and Scheduling].

.application-virtual.yml: virtual threads, a cap and a graceful shutdown
[source,yaml]
----
spring:
  threads:
    virtual:
      enabled: true                    # applicationTaskExecutor becomes a virtual-thread SimpleAsyncTaskExecutor
  task:
    execution:
      simple:
        concurrency-limit: 20          # the cap SimpleThreadPool's threadCount used to give; the scheduler thread blocks at 20
      shutdown:
        await-termination: true        # without it a running job is abandoned at shutdown
        await-termination-period: 30s

bookshelf:
  quartz:
    use-application-task-executor: true
----
Source: https://docs.spring.io/spring-boot/appendix/application-properties/index.html[Spring Boot: Common Application Properties (spring.task.execution)].

The Bookshelf service ran with the profiles `prod,virtual` against PostgreSQL: the scheduler reported "Using thread pool
`LocalTaskExecutorThreadPool` - with -1 threads", jobs ran on threads `task-1`, `task-2`, ... (virtual), and the cluster still worked. The

Three rules keep the split honest. First, profile-specific *keys* must be valid for the store they sit with (the `isClustered` failure above). Second,
`application.yml` should contain only keys that are valid for both stores (`scheduler-name`, the shutdown flag, `misfireThreshold` is
accepted by both). Third, the production tables are created by a migration tool, never by `initialize-schema`
(see xref:backend/scheduling/database-postgresql.adoc[PostgreSQL]), which is why `prod` says `never` and the other profiles do not need to say anything: the memory store has no tables. The
`test` profile leaves the scheduler stopped so that a test starts it, or triggers a job by hand, when it wants to
(see xref:backend/scheduling/testing.adoc[Testing]).

== Several schedulers in one application

Boot auto-configures exactly one scheduler, as one `SchedulerFactoryBean` created `@ConditionalOnMissingBean`. A second scheduler is
therefore possible, but Boot's convenience is not shared with it, and the first thing that goes is Boot's own scheduler. All variants were run with
the Bookshelf application and the Actuator `quartz` endpoint exposed:

.What Boot does when there is more than one scheduler (measured)
[cols="4,6",options="header"]
|===
|Configuration |Result

|your own `SchedulerFactoryBean reportsScheduler` bean, nothing else
|*Boot's scheduler is not created* (`@ConditionalOnMissingBean` backs off for any `SchedulerFactoryBean`). The only scheduler is yours, named `reportsScheduler`, with *0 jobs*: the `JobDetail` and `Trigger` beans, `spring.quartz.*` and Boot's `DataSource` customizer are applied only inside Boot's factory method, so none of them reaches your bean.

The two shapes that work are below. Keep Boot's scheduler as the main one and add a hidden plain scheduler when the second one is rare and
simple (for example a RAM scheduler for a single reporting job); take over both with `@Primary` when each needs a data source or

.TwoSchedulers.java: the first shape, Boot's scheduler plus a hidden RAM scheduler
[source,java]
----
import java.util.Properties;

import org.quartz.Scheduler;
import org.quartz.SchedulerException;
import org.quartz.impl.StdSchedulerFactory;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

@Configuration(proxyBeanMethods = false)
class ReportsSchedulerConfiguration {

    /** Not an autowire candidate: injecting Scheduler keeps getting Boot's scheduler. Look this one up by name. */
    @Bean(destroyMethod = "shutdown", autowireCandidate = false)
    Scheduler reportsScheduler() throws SchedulerException {
        Properties properties = new Properties();
        properties.setProperty("org.quartz.scheduler.instanceName", "ReportsScheduler");
        properties.setProperty("org.quartz.threadPool.threadCount", "2");
        Scheduler scheduler = new StdSchedulerFactory(properties).getScheduler();
        scheduler.start();
        return scheduler;
    }
}
----
Source: https://www.quartz-scheduler.org/documentation/quartz-2.5.x/quick-start.html[Quartz Quick Start Guide] and
https://docs.spring.io/spring-framework/reference/core/beans/dependencies/factory-autowire.html[Spring Framework: Autowiring Collaborators].

.TwoFactoryBeans.java: the second shape, two SchedulerFactoryBeans and a primary one
[source,java]
----
import java.util.List;

import org.quartz.JobDetail;
import org.quartz.Trigger;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.context.annotation.Primary;
import org.springframework.scheduling.quartz.SchedulerFactoryBean;

@Configuration(proxyBeanMethods = false)
class TwoFactoryBeans {

    @Bean
    @Primary
    SchedulerFactoryBean bookshelfScheduler(List<JobDetail> jobs, List<Trigger> triggers) {
        SchedulerFactoryBean factory = new SchedulerFactoryBean();   // Boot's customizers do not run for this one
        factory.setJobDetails(jobs.toArray(new JobDetail[0]));
        factory.setTriggers(triggers.toArray(new Trigger[0]));
        return factory;
    }

    @Bean
    SchedulerFactoryBean reportsScheduler() {
        return new SchedulerFactoryBean();
    }
}
----
Source: https://docs.spring.io/spring-framework/docs/current/javadoc-api/org/springframework/scheduling/quartz/SchedulerFactoryBean.html[SchedulerFactoryBean Javadoc].
Both beans started, and `GET /actuator/quartz` returned the Bookshelf group of the primary scheduler.

When both schedulers use a JDBC store, give each its own `SchedulerFactoryBean.setSchedulerName`: every Quartz table is keyed by `SCHED_NAME`, so two
names on one set of tables are two independent schedulers. With your own factory beans you also set the `DataSource`, the transaction
manager and `org.quartz.jobStore.*` keys yourself. For work that needs different queues rather than different stores, one scheduler with different
job groups is usually enough, and clustering is the better answer to "more capacity" (xref:backend/scheduling/clustering.adoc[Clustering]).

== The complete Bookshelf configuration

The Bookshelf service, configured for development, tests and production, as it was run. The five jobs are the Bookshelf jobs of the other pages (`QuartzJobBean`
subclasses; here they only log). What this page adds is the configuration around them, so that the schedule is
data and the environment is a profile.

.ScheduleProperties.java: the schedule's settings as a record
[source,java]
----
package bookshelf;

import java.time.Duration;
import java.util.TimeZone;

import org.springframework.boot.context.properties.ConfigurationProperties;

@ConfigurationProperties("bookshelf.schedule")
public record ScheduleProperties(TimeZone zone, Duration cacheRefreshInterval, String overdueCron,
        String weeklyCron, String retentionCron) {
}
----

.BookshelfSchedule.java: the five jobs and their triggers, driven by ScheduleProperties
[source,java]
----
package bookshelf;

import org.quartz.CronScheduleBuilder;
import org.quartz.JobBuilder;
import org.quartz.JobDetail;
import org.quartz.SimpleScheduleBuilder;
import org.quartz.Trigger;
import org.quartz.TriggerBuilder;
import org.springframework.boot.context.properties.EnableConfigurationProperties;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

@Configuration(proxyBeanMethods = false)
@EnableConfigurationProperties(ScheduleProperties.class)
class BookshelfSchedule {

    @Bean JobDetail cacheRefreshJob() {
        return JobBuilder.newJob(CacheRefreshJob.class).withIdentity("cacheRefresh", "bookshelf").storeDurably().build();
    }

    @Bean Trigger cacheRefreshTrigger(JobDetail cacheRefreshJob, ScheduleProperties p) {
        return TriggerBuilder.newTrigger().forJob(cacheRefreshJob).withIdentity("cacheRefreshTrigger", "bookshelf")
                .withSchedule(SimpleScheduleBuilder.simpleSchedule()
                        .withIntervalInMilliseconds(p.cacheRefreshInterval().toMillis()).repeatForever()
                        .withMisfireHandlingInstructionNextWithRemainingCount()).build();
    }

    @Bean JobDetail overdueLoanRemindersJob() {
        return JobBuilder.newJob(OverdueLoanRemindersJob.class).withIdentity("overdueLoanReminders", "bookshelf")
                .usingJobData("runs", 0).storeDurably().build();
    }

    @Bean Trigger overdueLoanRemindersTrigger(JobDetail overdueLoanRemindersJob, ScheduleProperties p) {
        return cron(overdueLoanRemindersJob, "overdueLoanRemindersTrigger", p.overdueCron(), p);
    }

    @Bean JobDetail weeklyStatisticsJob() {
        return JobBuilder.newJob(WeeklyStatisticsJob.class).withIdentity("weeklyStatistics", "bookshelf").storeDurably().build();
    }

    @Bean Trigger weeklyStatisticsTrigger(JobDetail weeklyStatisticsJob, ScheduleProperties p) {
        return cron(weeklyStatisticsJob, "weeklyStatisticsTrigger", p.weeklyCron(), p);
    }

    @Bean JobDetail retentionCleanupJob() {
        return JobBuilder.newJob(RetentionCleanupJob.class).withIdentity("retentionCleanup", "bookshelf").storeDurably().build();
    }

    @Bean Trigger retentionCleanupTrigger(JobDetail retentionCleanupJob, ScheduleProperties p) {
        return cron(retentionCleanupJob, "retentionCleanupTrigger", p.retentionCron(), p);
    }

    private static Trigger cron(JobDetail job, String name, String expression, ScheduleProperties p) {
        return TriggerBuilder.newTrigger().forJob(job).withIdentity(name, "bookshelf")
                .withSchedule(CronScheduleBuilder.cronSchedule(expression).inTimeZone(p.zone())).build();
    }
}
----
Source: https://www.quartz-scheduler.org/documentation/quartz-2.5.x/tutorials/tutorial-lesson-06.html[Quartz Tutorial: Lesson 6, CronTrigger] and
https://docs.spring.io/spring-boot/reference/features/external-config.html[Spring Boot: Externalized Configuration] (`@ConfigurationProperties` records).

The listener and the customizer are the `BookshelfQuartzConfiguration` shown above, plus the virtual-thread customizer; the listener is a plain component:

.JobAuditListener.java: a global JobListener bean
[source,java]
----
package bookshelf;

import org.quartz.JobExecutionContext;
import org.quartz.JobExecutionException;
import org.quartz.JobListener;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.stereotype.Component;

@Component
class JobAuditListener implements JobListener {

    private static final Logger log = LoggerFactory.getLogger(JobAuditListener.class);

    @Override public String getName() { return "bookshelf-audit"; }

    @Override public void jobToBeExecuted(JobExecutionContext context) {
        log.info("starting {} on {}", context.getJobDetail().getKey(), Thread.currentThread().getName());
    }

    @Override public void jobExecutionVetoed(JobExecutionContext context) { }

    @Override public void jobWasExecuted(JobExecutionContext context, JobExecutionException error) {
        log.info("finished {} in {} ms{}", context.getJobDetail().getKey(), context.getJobRunTime(),
                error == null ? "" : " with " + error.getMessage());
    }
}
----
Source: https://www.quartz-scheduler.org/documentation/quartz-2.5.x/tutorials/tutorial-lesson-07.html[Quartz Tutorial: Lesson 7, TriggerListeners and JobListeners].

== Worked example: asking the running scheduler what is configured

With this many layers, the useful habit is to ask the running scheduler, not the files. The Actuator endpoint shows jobs and triggers,
`SchedulerMetaData` shows the engine. This is the check used throughout this page:

.EffectiveConfiguration.java: what the scheduler is really running
[source,java]
----
import org.quartz.Scheduler;
import org.quartz.SchedulerMetaData;

static String describe(Scheduler scheduler) throws Exception {
    SchedulerMetaData md = scheduler.getMetaData();
    return "schedulerName=" + md.getSchedulerName()
            + "\ninstanceId=" + md.getSchedulerInstanceId()
            + "\njobStoreClass=" + md.getJobStoreClass().getName()
            + "\nthreadPoolClass=" + md.getThreadPoolClass().getName()
            + "\nthreadPoolSize=" + md.getThreadPoolSize()
            + "\nsupportsPersistence=" + md.isJobStoreSupportsPersistence()
            + "\nclustered=" + md.isJobStoreClustered();
}
----
Source: https://www.quartz-scheduler.org/api/2.5.x/org/quartz/SchedulerMetaData.html[SchedulerMetaData Javadoc].

== Pitfalls

.Spring Boot configuration of Quartz: what goes wrong, why, and the fix
[cols="3,4,4",options="header"]
|===
|Symptom |Cause |Fix

|A `quartz.properties` on the classpath has no effect
|`SchedulerFactoryBean` reads a file only through `setConfigLocation`; Boot never sets it
|Use `spring.quartz.properties.*`, or a customizer with `setConfigLocation`

|`org.quartz.threadPool.threadCount` set through an environment variable stays at 10
|The environment variable binds to the lower-case key, which Quartz ignores
|Put raw keys in `application.yml` or in `SPRING_APPLICATION_JSON`

|`NoSuchMethodException: No setter for property 'isClustered'` at startup
|A JDBC-store key reached `RAMJobStore`: `job-store-type: memory`, or profiles `prod,dev` in the wrong order
|Keep store keys in the profile that selects the store; order profiles so the store's profile is last

|`job-store-type: jdbc` and the jobs vanish at every restart, no error
|Zero `DataSource` beans, or several without `@Primary`: Boot falls back to `RAMJobStore`
|One `DataSource`, or `@Primary` on the application's and `@QuartzDataSource` on Quartz's; check `getMetaData().getJobStoreClass()`

|`@QuartzDataSource` is ignored and the store is RAM
|The `jdbc` configuration needs a single `DataSource` candidate; two beans without `@Primary` are not one
|Add `@Primary` to the application's data source

|`ThreadPool class ... LocalTaskExecutorThreadPool props could not be configured`
|`org.quartz.threadPool.threadCount` (or another pool key) with a task executor set
|Remove every `org.quartz.threadPool.*` key

|Jobs do not run on the `Executor` bean
|Boot never passes an `Executor` to Quartz
|`setTaskExecutor` in a customizer; remember it also removes `applicationTaskExecutor` when you declare any `Executor` bean

|Four of six triggers in state ERROR after a burst
|A bounded executor rejected the tasks; `LocalTaskExecutorThreadPool` returns `false` and Quartz errors the trigger
|Unbounded queue with care, or a blocking `concurrency-limit`; never `queueCapacity=0` or `reject-tasks-when-limit-reached`

|A running job is abandoned at shutdown although `wait-for-jobs-to-complete-on-shutdown` is `true`
|With a Spring executor `ThreadPool.shutdown` is a no-op
|`spring.task.execution.shutdown.await-termination=true` with a period

|A second `SchedulerFactoryBean` makes Boot's scheduler disappear
|Boot's is `@ConditionalOnMissingBean(SchedulerFactoryBean)`
|Define both yourself with one `@Primary`, or add a plain `Scheduler` with `autowireCandidate = false`

|`NoUniqueBeanDefinitionException` for `Scheduler`, also from the Actuator
|Two `Scheduler` beans, none primary
|`@Primary`, or hide the second one

|Listener beans never run
|Boot does not register listener beans
|Customizer with `setGlobalJobListeners` / `setGlobalTriggerListeners`

|A cron change in `application.yml` does nothing after the redeploy
|JDBC store plus `overwrite-existing-jobs: false`
|Set it to `true`, or change the trigger through the `Scheduler` API

|A sub-second `startup-delay` starts the scheduler at once
|`(int) getSeconds()` cuts the fraction off
|Use whole seconds
|===
Source: output of the runs on this page; the failure messages are quoted.

== What changed

.Facts about configuring Quartz under Boot that changed, or that the documentation gets wrong
[cols="3,3,4",options="header"]
|===
|Topic |Before |Now (Quartz 2.5.2, Boot 4.1.1, Spring Framework 7.0.9)

|Packages of the Quartz types
|`org.springframework.boot.autoconfigure.quartz` (3.5.16)
