Most of what is written about JMeter, including the three books this section draws on, describes JMeter 2.11, 2.12 or
3.0. The test-plan model has not changed since then: thread groups, samplers, config elements, timers, extractors,
assertions and listeners still run in the same order and with the same scoping rules. What changed is almost
everything around that model: the scripting language, the JSON and XML tooling, the way plugins are installed, how
results are reported and monitored, how distributed runs are secured, and the Java version underneath. This page
collects those changes in one place. It gives a timeline, a release-by-release summary, a table that maps each book
idiom to its current replacement, a measured procedure for migrating an old `.jmx` file and a checklist for the next
major version. The topic pages linked from each row carry the detail.

The page was written against Apache JMeter 5.6.3 (released 2024-01-07), the latest release on 2026-10-14. JMeter 6.0
is **not released**. On that date the download page offered 5.6.3, the newest tag in the `apache/jmeter` repository
was `v5.6.3-rc2`, and the newest `ApacheJMeter_core` artifact on Maven Central was 5.6.3. The master branch declares
version 6.0.0, and its `xdocs/changes.xml` lists what 6.0 is planned to contain. Everything said here about 6.0 is
planned, not released behaviour, and may change before the release. Other versions used on this page are Java 17 or
later (21 recommended; 5.6.3 itself runs on Java 8 or later), Groovy 3.0.20 as bundled with 5.6.3, JMeter Plugins
Manager 2.0, jmeter-maven-plugin 3.8.0, the gRPC Request plugin 2.0.x and JMeter Java DSL 2.3. The legacy-plan runs
shown below were made on a real 5.6.3 installation with Java 21.

== Version timeline

The books cover the top of the timeline: _JMeter Cookbook_ uses 2.11, _Performance Testing with JMeter_ (2nd ed.)
uses 2.12 and _Pro Apache JMeter_ uses 3.0. Everything below 3.0 in the timeline is newer than all three books.

----

    section Books era

        2015 : 2.13 adds the Backend Listener with Graphite
        2016 : 3.0 adds the HTML dashboard, bundles Groovy and is used by Pro Apache JMeter : 3.1 deprecates BSF and makes Groovy the JSR223 default
    section Modernisation
        2017 : 3.2 requires Java 8, moves to Log4j 2, removes SOAP/XML-RPC Request and Monitor Results, adds InfluxDB : 3.3 adds InfluxDB over UDP and TCP latency

        2019 : 5.1 renames non-GUI mode to CLI mode and adds Import from cURL : 5.2 adds Same user on each iteration, JMESPath, XPath2 Assertion and Bolt

        2021 : 5.4.2 and 5.4.3 fix Log4j vulnerabilities

        2023 : 5.6 adds the experimental DSL and ServiceLoader plugins : 5.6.1 makes UTF-8 the HTTP default

        6.0 unreleased : Java 17 minimum, MongoDB removed, expired cookies dropped, 307 and 308 keep the method, Groovy 5

== Release by release

The tables below keep only the changes that alter how a plan is written, run or read. Each change links to the page
that explains the element today. Dependency bumps and bug fixes are left out unless they change behaviour.

=== The books' baseline: 2.11 to 3.0

[cols="1,1,5",options="header"]
|===
|Version |Released |Changes that matter for plans written today

|2.11
|January 2014
|The version of _JMeter Cookbook_. The summariser is on by default in non-GUI mode. New Transaction Controllers
exclude timer and pre/post-processor time by default (see
xref:backend/jmeter/logic-controllers-and-transactions.adoc[Logic Controllers & Transactions]).

|2.12
|November 2014
|The version of _Performance Testing with JMeter_. Adds the Critical Section Controller, JMS Priority and Expiration,
SMTP timeouts and the Synchronizing Timer timeout.

|2.13
|March 2015
|Adds the asynchronous Backend Listener with a Graphite client, the ancestor of today's real-time monitoring (see
xref:backend/jmeter/real-time-monitoring-with-backend-listener.adoc[Real-time Monitoring with Backend Listener]). Test
Fragments are disabled by default. The WebService(SOAP) Request is deprecated.

|3.0
|May 2016
|The version of _Pro Apache JMeter_. Requires Java 7. Adds the HTML dashboard report (`-e -o`, `-g`), bundles Groovy
2.4.6 in `lib`, adds the JSON Path PostProcessor (renamed JSON Extractor in 3.1), moves to HttpClient 4.5.2 with SNI,
changes the recorder's default port to 8888 and adds *Validate* for thread groups. Deprecates the MongoDB elements
(hidden from the menus) and the HttpClient 3.1 implementation, and removes the WebService(SOAP) Request.
|===

=== 3.1 to 3.3: Groovy first, Java 8, Log4j 2

[cols="1,1,5",options="header"]
|===
|Version |Released |Changes

|3.1
|November 2016
|Groovy becomes the default JSR223 language and the `+__groovy+` function is added. The six BSF elements (Sampler,
Listener, Assertion, Timer, PreProcessor, PostProcessor) are deprecated in favour of JSR223. The `+__jexl+` function is
dropped (use `+__jexl3+`). The dashboard gains new graphs and ignores empty transaction samples, and the summariser
ignores Transaction Controller samples. `timer.factor` scales the random timers. The Distribution Graph and Spline
Visualizer listeners are removed.

|3.2
|April 2017
|Requires Java 8 (Java 7 support dropped). Logging moves to SLF4J and Log4j 2 with `log4j2.xml`. Adds the InfluxDB
client for the Backend Listener. Removes the SOAP/XML-RPC Request ("Use HTTP Request element as a replacement"), the
Monitor Results listener and the HttpClient 3.1 implementation and its jar. Basic authentication becomes pre-emptive
with HttpClient4. View Results Tree is capped at 500 entries.

|3.3
|September 2017
|InfluxDB over UDP and error counts per response code, TCP Sampler latency, JDBC driver and validation-query
drop-downs, the `+__timeShift+` and `+__RandomDate+` functions. `+_StringFromFile+` (one underscore) stops working.
|===

=== 4.0: the WorkBench goes, SSL comes

Released February 2018. This is the release that breaks the most book instructions.

[cols="2,5",options="header"]
|===
|Change |Detail

|WorkBench removed
|Non-test elements (the HTTP(S) Test Script Recorder, Mirror Server, Property Display) become direct children of the
Test Plan. When an old plan is loaded, JMeter moves those three elements under the Test Plan and puts any other
WorkBench content in a Test Fragment called *Workbench Test Fragment*. Recording starts from the *Recording* template
(see xref:backend/jmeter/recording-and-curl-import.adoc[Recording & cURL Import]).

|RMI over SSL by default
|"Since JMeter 4.0 the default transport mechanism for RMI will use SSL": create a keystore with
`create-rmi-keystore.sh` and copy it to every node, or set `server.rmi.ssl.disable=true` on a trusted network. The
`Hold` sample sender mode is removed. Distributed testing is covered later in this section, in the distributed testing
page.

|New core elements
|Boundary Extractor, JSON Assertion (the AtlantBH JSON Path Assertion migrated from jmeter-plugins) and Precise
Throughput Timer (Poisson arrivals at a constant throughput). See
xref:backend/jmeter/correlation-and-extractors.adoc[Correlation & Extractors],
xref:backend/jmeter/assertions.adoc[Assertions] and
xref:backend/jmeter/open-model-and-throughput-control.adoc[Open Model & Throughput Control].

|Safer defaults
|New If Controllers interpret the condition as a variable expression, new JSR223 elements cache compiled scripts, and
Loop and ForEach Controllers expose `+__jm__<Name>__idx+`.

|Thread Group scheduler
|The absolute *Start Time* and *End Time* fields are removed; only *Duration* and *Startup delay* remain (see
xref:backend/jmeter/thread-groups-concurrent-users-and-ramp-up.adoc[Thread Groups: Concurrent Users & Ramp-up]).

|Other
|Java 9 support, the Darcula look and feel by default, `bin/setenv.sh` for JVM settings, tearDown Thread Groups run
after stop and shutdown by default, the plan is saved before each run, and the `+__digest+`, `+__dateTimeConvert+`,
`+__changeCase+`, `+__isVarDefined+` and `+__isPropDefined+` functions.
|===

=== 5.0 to 5.4

[cols="1,1,5",options="header"]
|===
|Version |Released |Changes

|5.0
|September 2018
|XPath2 Extractor. Test Action renamed *Flow Control Action* and CSS/JQuery Extractor renamed *CSS Selector
Extractor*. *Go to next iteration of Current Loop* and *Break Current Loop* added to the Flow Control Action and the
Result Status Action Handler. HTTP state (connections and SSL) is reset on each thread-group iteration with HttpClient4.
Sub-results are written to CSV results files and renamed with `-N` suffixes. Multipart works for `PUT` and `DELETE`, and
JMeter no longer adds a form `Content-Type` to a `POST` that has none (Bug 60190). The dashboard gains Total
Transactions Per Second and custom graphs. Distributed runs prefix thread names with the engine host and port.

|5.1
|February 2019
|The documentation renames non-GUI mode to *CLI mode* (the option is still `-n`). *Tools → Import from cURL*,
*Tools → Compile JSR223 Test Elements*, template parameters (used by the Recording template), `statistics.json` next to
the dashboard. 5.1.1 adds *Tools → Generate HTML report*.

|5.2
|October 2019
|*Same user on each iteration* on the Thread Group (drives the Cookie Manager, Cache Manager and HTTP state reset).
JMESPath Extractor and Assertion, XPath2 Assertion, empty Boundary Extractor boundaries, InfluxDB 2 support, the Bolt
Request for Neo4j, PKCS11 keystores, *Preinit Pool* in the JDBC Connection Configuration. XML parsing refuses insecure
XML.

|5.3
|May 2020
|Groovy 3.0.3, listed as an incompatible change: "The update to Groovy 3 might break some old Groovy code". The
default `httpclient4.time_to_live` goes from 2000 to 60000 ms. The dashboard gains a Median column and decimal
percentiles.

|5.4
|November 2020
|GraphQL HTTP Request (see xref:backend/jmeter/rest-json-graphql-and-soap-apis.adoc[REST, JSON, GraphQL & SOAP APIs]).
A Backend Listener client that sends raw results to InfluxDB. The dashboard says PASS and FAIL instead of OK and KO.
cURL import handles backslash line continuations and `PUT` with data.

|5.4.1, 5.4.2, 5.4.3
|January and December 2021
|5.4.2 is a fix release for CVE-2021-44228 (Log4j 2 JNDI lookups) and 5.4.3 for CVE-2021-45105. Any installation older
than 5.4.3 ships a vulnerable Log4j 2 and should not be kept around for "compatibility".
|===

=== 5.5: the open model

Released June 2022. Adds the **Open Model Thread Group** (experimental), which drives arrivals from a schedule such as
`+rate(0/sec) random_arrivals(1 min) rate(10/sec)+` instead of a thread count, and the experimental
`jmeter.regex.engine=java` switch from Jakarta ORO to the JDK regular expression engine (ORO remains the default in
5.6.3). JMeter now supports Java 17, ships Log4j 2.17.2 and starts using Kotlin in core classes. The GraphQL HTTP
Request accepts variables, the JSON Assertion fails on an indefinite path with an empty result, and the dashboard's
percentile estimator becomes configurable. See
xref:backend/jmeter/open-model-and-throughput-control.adoc[Open Model & Throughput Control].

=== 5.6 to 5.6.3: the current line

[cols="1,1,5",options="header"]
|===
|Version |Released |Changes

|5.6
|June 2023
|Plugins are found through Java's `ServiceLoader` instead of classpath scanning, for faster start-up (see
xref:backend/jmeter/plugins-and-plugins-manager.adoc[Plugins & Plugins Manager]). An experimental Kotlin and Java DSL for

|5.6.2
|July 2023

|5.6.3
|January 2024

== Outdated book idiom → current practice

The books' methodology still holds; their tooling often does not. Each row names the idiom, where the books use it, its
status in 5.6.3 and what to do instead. Chapters refer to _JMeter Cookbook_ (Cookbook), _Performance Testing with
JMeter_ 2nd ed. (PTwJ) and _Pro Apache JMeter_ (Pro).

[cols="3,3,4,3",options="header"]
|===
|Book idiom (chapter) |Status in 5.6.3 (and 6.0) |Current practice |Detail

|BeanShell pre/post-processors (Pro ch. 3) and the BSF PostProcessor (PTwJ ch. 3)
|BeanShell is discouraged by the best-practices page. The BSF elements were deprecated in 3.1; they still ship but are
listed in `not_in_menu`, and a BSF element set to Groovy loads but does not run (measured below).
|JSR223 elements with Groovy and *Cache compiled script if available*; no `+${...}+` inside cached scripts, pass values
through *Parameters* or `vars`.
|xref:backend/jmeter/scripting-with-jsr223-and-groovy.adoc[Scripting with JSR223 & Groovy]

|SOAP/XML-RPC Request and WebService(SOAP) Request samplers (Cookbook ch. 4; PTwJ ch. 7)
|WebService(SOAP) removed in 3.0, SOAP/XML-RPC removed in 3.2. An old SOAP/XML-RPC Request is converted to an empty
config element on load, so it silently sends nothing (measured below).
|HTTP Request with the envelope in *Body Data*, `Content-Type` and `SOAPAction` in a Header Manager, or the *Building a
SOAP WebService Test Plan* template.
|xref:backend/jmeter/rest-json-graphql-and-soap-apis.adoc[REST, JSON, GraphQL & SOAP APIs]

|`jp@gc` JSON Path Extractor and JSON Path Assertion plugins (Cookbook ch. 2; PTwJ ch. 7)
|The `jpgc-json` catalogue entry is "Deprecated in favor of core JMeter 4.0+". Without the plugin, a plan that uses it
fails to load.
|Core JSON Extractor (3.0, renamed in 3.1), JSON Assertion (4.0), JMESPath Extractor and Assertion (5.2), Boundary

|xref:backend/jmeter/correlation-and-extractors.adoc[Correlation & Extractors], xref:backend/jmeter/assertions.adoc[Assertions]

|Monitor Results listener for Tomcat, and PerfMon with ServerAgent (PTwJ ch. 5; Pro ch. 9)
|Monitor Results removed in 3.2 (an old one loads as an obsolete element). PerfMon is a legacy community plugin.
|Backend Listener to InfluxDB or Graphite for JMeter's own metrics, and Prometheus (Actuator, Micrometer, exporters)
for the server, side by side in Grafana.
|xref:backend/jmeter/real-time-monitoring-with-backend-listener.adoc[Real-time Monitoring with Backend Listener], xref:backend/jmeter/analyzing-results-and-finding-bottlenecks.adoc[Analyzing Results & Finding Bottlenecks]

|Stepping Thread Group (Cookbook ch. 6)
|Still in `jpgc-casutg` 3.1.1; its wiki page points to the Concurrency Thread Group as the "better alternative".

for arrival rates.
|xref:backend/jmeter/custom-thread-groups-and-load-shaping.adoc[Custom Thread Groups & Load Shaping]

|Recording into the WorkBench with the HTTP Proxy Server (Pro ch. 4)
|WorkBench removed in 4.0; old plans are migrated on load.
|*File → Templates → Recording*, the HTTP(S) Test Script Recorder on port 8888 with the `ApacheJMeterTemporaryRootCA`

|xref:backend/jmeter/recording-and-curl-import.adoc[Recording & cURL Import]

|"Non-GUI mode" (Pro ch. 3)
|Called CLI mode since the 5.1 documentation; same `-n` option. GUI mode "should only be used for creating the test

|`jmeter -n -t plan.jmx -l results.jtl -e -o report`, with load parameters passed as `-J` properties.
|xref:backend/jmeter/running-tests-in-cli-mode.adoc[Running Tests in CLI Mode]

|Unzipping the jmeter-plugins Standard and Extras sets (Cookbook appendix)
|The sets are virtual packages in the catalogue today; plugins are installed one by one.
|Plugins Manager 2.0 from *Options → Plugins Manager*, or `PluginsManagerCMD.sh install` and `install-for-jmx` in CI.
|xref:backend/jmeter/plugins-and-plugins-manager.adoc[Plugins & Plugins Manager]

|jmeter-maven-plugin 1.10 with plugins declared as Maven plugin dependencies (Cookbook ch. 8; Pro ch. 7)
|1.10.0 added JMeter 2.11 support. 2.0.0 introduced `<jmeterExtensions>` and `<jmeterVersion>`; 3.0.0 made the

|jmeter-maven-plugin 3.8.0 with `configure`, `jmeter` and `results` executions and an explicit

|Covered later in this section, in the CI/CD page; see also xref:backend/springboot/performance-testing-jmeter.adoc[Performance Testing with Apache JMeter]

|Removed in 3.2; an old HttpClient 3.1 sampler loads as an obsolete element.
|Leave *Implementation* empty (HttpClient4) or choose `Java`.

|xref:backend/jmeter/thread-groups-concurrent-users-and-ramp-up.adoc[Thread Groups: Concurrent Users & Ramp-up]

|GUI listeners are for debugging; View Results Tree is capped at 500 entries.
|The HTML dashboard (`-e -o` or `-g`), `statistics.json` and APDEX.
|xref:backend/jmeter/html-dashboard-report.adoc[HTML Dashboard Report]

|Plain RMI between master and slaves (Pro ch. 6; Cookbook ch. 5)
|RMI over SSL by default since 4.0; `Hold` mode removed; default sender `StrippedBatch`.
|A shared RMI keystore on every node, data files copied to every node, same JMeter and Java versions everywhere.
|Covered later in this section, in the distributed testing page

|MongoDB Script sampler (Cookbook ch. 4; PTwJ ch. 7)
|Deprecated in 3.0 and hidden; bundled driver 2.14.3. Planned 6.0: removed, plans no longer load.
|JSR223 Sampler with a current MongoDB Java driver in `lib`.
|xref:backend/jmeter/other-samplers.adoc[Other Samplers]

|Typing non-ASCII data with an explicit encoding (Cookbook; Pro)
|UTF-8 is the HTTP default since 5.6.1.
|Leave *Content encoding* empty unless the server needs something else.
|xref:backend/jmeter/http-requests.adoc[HTTP Requests]

== Migrating a book-era plan to 5.6.3

A plan saved by JMeter 2.x or 3.0 usually opens in 5.6.3, which is exactly the problem: some obsolete elements load
without any error and then do nothing. The procedure below finds them before a test result is trusted.

=== What happens when 5.6.3 loads old elements

=== Step 1: inventory the plans

Because the `.jmx` format is XML with one element per test element, a plain text search finds the obsolete ones. The
script below reports every match with its line number and the replacement, and exits with 1 when it finds any, so it
can also run in CI before the load test:

[source,bash]
----
#!/usr/bin/env bash
# jmx-legacy-scan.sh: report elements in .jmx files that current JMeter removed, hides or discourages,
# or that JMeter 6.0 plans to remove or change. Usage: jmx-legacy-scan.sh plan.jmx...
set -u
rules='testclass="BSF|BSF element: deprecated in 3.1, hidden from menus; use JSR223 + Groovy
testclass="BeanShell|BeanShell element: discouraged; use JSR223 + Groovy
testclass="SoapSampler"|SOAP/XML-RPC Request: removed in 3.2, loads as an empty element; use HTTP Request
testclass="WebServiceSampler"|WebService(SOAP) Request: removed in 3.0; use HTTP Request
testclass="HTTPSampler2"|HttpClient 3.1 sampler: removed in 3.2; use HTTP Request (HttpClient4)
>HttpClient3.1<|HttpClient3.1 implementation: removed in 3.2; leave the implementation empty or HttpClient4
guiclass="MonitorHealthVisualizer"|Monitor Results listener: removed in 3.2; use Backend Listener + server metrics
testclass="WorkBench"|WorkBench: dropped in 4.0; use a Test Fragment or the Recording template
testclass="Mongo|MongoDB element: deprecated in 3.0, removal planned for 6.0; use JSR223 + MongoDB driver
testclass="com.atlantbh.jmeter.plugins.jsonutils|jp@gc JSON plugin: deprecated; use core JSON Extractor / JSON Assertion
testclass="kg.apc.jmeter.threads.SteppingThreadGroup"|Stepping Thread Group: use the Concurrency Thread Group
testclass="kg.apc.jmeter.perfmon.PerfMonCollector"|PerfMon: use Backend Listener + Prometheus/Grafana
com.mysql.jdbc.Driver|old MySQL driver class: 6.0 references com.mysql.cj.jdbc.Driver'
status=0
for plan in "$@"; do
  while IFS='|' read -r pattern advice; do
    grep -n -F -- "$pattern" "$plan" | while IFS=: read -r line _; do
      printf '%s:%s: %s\n' "$plan" "$line" "$advice"
    done
    grep -q -F -- "$pattern" "$plan" && status=1
  done <<< "$rules"
done
exit "$status"
----

Run against four book-era Bookshelf plans:

[source,bash]
----
./jmx-legacy-scan.sh legacy-*.jmx; echo "exit=$?"
----

=== Step 2: open, fix and re-save in 5.6.3

. Install the plugins the plan needs first, with *Options → Plugins Manager* or with
  `PluginsManagerCMD.sh install-for-jmx plan.jmx`, so the plan can load at all (see
  xref:backend/jmeter/plugins-and-plugins-manager.adoc[Plugins & Plugins Manager]).
. Open the plan with *File → Open*. A WorkBench is converted on load: the recorder moves under the Test Plan and other
  content into *Workbench Test Fragment*. Delete what is no longer needed.
. Replace each element reported by the scan, using the table above. The scripting case is the most common; it is
  shown next.
. Run *Validate* on each thread group (right-click the Thread Group) to execute one iteration with one thread and no
  pauses, and check the results in a View Results Tree that you disable again afterwards.
. *File → Save* writes the plan in the 5.6.3 format (`jmeter="5.6.3"` in the root element). Commit the result so the
  diff shows exactly what changed.

=== Step 3: align the toolchain

* **Java.** Run 5.6.3 on Java 17 or 21. That is also what 6.0 will need, so the upgrade does not change the runtime
  twice.
* **Every node, same versions.** Distributed runs need the same JMeter, Java and plugin versions on the controller and
  every worker.
* **Maven builds.** jmeter-maven-plugin 3.8.0 defaults to JMeter 5.6.2 (its changelog: "Default to JMeter 5.6.2"), so
  pin the version explicitly:

[source,xml]
----
<plugin>
  <groupId>com.lazerycode.jmeter</groupId>
  <artifactId>jmeter-maven-plugin</artifactId>
  <version>3.8.0</version>
  <executions>
    <execution>
      <id>configuration</id>
      <goals>
        <goal>configure</goal>
      </goals>
    </execution>
    <execution>
      <id>jmeter-tests</id>
      <goals>
        <goal>jmeter</goal>
      </goals>
    </execution>
    <execution>
      <id>jmeter-check-results</id>
      <goals>
        <goal>results</goal>
      </goals>
    </execution>
  </executions>
  <configuration>
    <jmeterVersion>5.6.3</jmeterVersion>

=== Step 4: re-baseline

A migrated plan is a new measuring instrument. Before comparing it with any old result, run the Bookshelf baseline
profile on 5.6.3 and keep it as the new reference:

[source,bash]
----
bin/jmeter -n -t bookshelf-load.jmx -Jthreads=50 -Jrampup=60 -Jduration=660 \
  -l baseline-5.6.3.jtl -e -o baseline-5.6.3-report
----

With 50 threads, a 60 s ramp-up and a 660 s duration, the hold at full load lasts 10 minutes. With the Bookshelf think
time of 3 s and a typical response time of 0.2 s, each thread completes one request every 3.2 s, about 0.31 requests
per second, so the plan settles near 50 / 3.2 ≈ 15.6 requests per second. If the migrated plan lands far from that
number against the same build of the API, look for an element that no longer does what it did (a missing timer, a
script that no longer runs) before blaming the server. Even a correct migration changes some numbers on purpose: since
5.0 HTTP state is reset on each thread-group iteration unless *Same user on each iteration* is ticked, and since 3.1
transaction samples are excluded from the summariser and empty ones from the dashboard.

Source: https://jmeter.apache.org/usermanual/get-started.html#non_gui[Getting Started: CLI mode (User Manual)] and https://jmeter.apache.org/usermanual/component_reference.html#Thread_Group[Thread Group (Component Reference)]

== Preparing for 6.0

None of the following needs to wait for the release. Each item can be checked on 5.6.3 today, so that the upgrade
becomes a version bump plus a re-run.

[cols="3,4,4",options="header"]
|===
|Planned change |What can break |What to do on 5.6.3 now

|Java 17 minimum
|Generators, CI images and Docker images still on Java 8 or 11.
|Move every node to Java 17 or 21 now; 5.6.3 runs on both.

|MongoDB elements removed (PR 6573)
|Plans with a MongoDB Script sampler or MongoDB Source Config no longer load.
|Run the inventory script; rewrite those steps as a JSR223 Sampler with a current MongoDB driver in `lib`.

|Expired cookies no longer sent (issue 6428)
|Long soak tests whose session cookie expires mid-run start failing with authentication or session errors.
|Check the cookie lifetimes of the system under test against the test duration; add a re-login path (for Bookshelf,
repeat `POST /api/auth/login` when the token or session is rejected).

|307 and 308 keep the method (issue 6080)
|A `POST` that is redirected with 307 or 308 is repeated as a `POST` at the new location, so a write can happen twice
where 5.6.3 sent a `GET`.
|Find redirects in the responses (View Results Tree during *Validate*, or the response codes in the JTL) and decide
whether the test should follow them.

|No automatic `charset` on `multipart/form-data` (issue 6250)
|A server that relied on the `charset` parameter in the header.
|Check multipart uploads against the server; set the header explicitly if it needs one.

|Open Model and Precise Throughput Timer delays from the Thread Group start (issue 6352)
|Schedules of thread groups that start after the test starts.
|See the worked example below; avoid workarounds you will have to remove.

|`com.mysql.cj.jdbc.Driver` (PR 6274)
|Plans and templates that still name `com.mysql.jdbc.Driver`.
|Use `com.mysql.cj.jdbc.Driver` with a current Connector/J jar now (see
xref:backend/jmeter/database-testing-with-jdbc.adoc[Database Testing with JDBC]).

|Groovy 5.1.3
|Groovy 3 scripts that use APIs removed in Groovy 4 or 5, such as `+groovy.util.XmlSlurper+`.
|Use `+groovy.xml.XmlSlurper+`, keep scripts to `vars`, `props`, `prev`, the JDK and `+groovy.json+`, and run *Tools →
Compile JSR223 Test Elements* after the upgrade.

|json-path 3.0.0, Saxon-HE 13, Tika 4.x, Rhino 1.9.1, Neo4j driver 6.x
|Edge cases in JSONPath and XPath expressions, *Document (text)* assertions, JavaScript conditions, Bolt requests.
|Keep a functional smoke plan with assertions on extracted values, to run on 6.0 before any load test.

|Numeric properties trimmed
|Nothing should break; the change log says the trimming is there "so accidental spaces do not silently change
configuration values".
|Keep property values clean anyway, so that runs behave the same on 5.6.3 and 6.0.

|Plugins
|Plugins compiled against the old libraries, or bundling their own copies, may fail; Kotlin 1.9 or later is required.
|Pin plugin versions (Plugins Manager or `<jmeterExtensions>`) and re-run the smoke plan with each plugin on 6.0
before upgrading generators. The gRPC Request plugin's compatibility with 6.0 cannot be checked until 6.0 exists.
|===

=== Worked example: the Open Model timing change

Bookshelf seeds its test data in a setUp Thread Group that takes about 30 s, then an Open Model Thread Group runs the
schedule `+rate(20/sec) random_arrivals(10 min)+`.

* **On 5.6.3** arrival times are offsets from the start of the test. When the Open Model Thread Group starts at 30 s,
  the arrivals planned for the first 30 s are already overdue and are released at once: 20 arrivals per second × 30 s
  ≈ 600 iterations in a burst, then the schedule continues at 20 per second. The burst is not a property of the system
  under test, and it distorts the first minute of the dashboard.
* **The 5.6.3 workaround** is to start the schedule with a pause that covers the setUp phase:
  `+pause(30 sec) rate(20/sec) random_arrivals(10 min)+`.
* **On 6.0 (planned)** delays are measured from the start of the Thread Group, so the burst disappears without a
  workaround, and the same workaround then delays the real load by an extra 30 s. Remove the leading pause when
  upgrading, and keep the schedule in a property (`+${__P(schedule,...)}+`) so that it is changed in one place.

Source: https://jmeter.apache.org/usermanual/component_reference.html#Open_Model_Thread_Group[Open Model Thread Group (Component Reference)] and https://github.com/apache/jmeter/blob/master/xdocs/changes.xml[changes.xml on master (planned 6.0)]

== Related tools that changed too

* **JMeter Plugins Manager**: version 2.0 is the one this section uses; `cmdrunner` 2.3 for the command-line installer.
  The catalogue at jmeter-plugins.org is a community project, not part of Apache JMeter.
* **gRPC Request plugin**: the original `zalopay-oss/jmeter-grpc-request` repository was archived in April 2024 after
  1.2.6; the catalogue now points to the bakthava continuation (2.0.0 to 2.0.2, 2026, with mTLS and Java 21 support).
  It supports unary calls only. See xref:backend/jmeter/grpc-load-testing.adoc[gRPC Load Testing].
* **Programmatic plans**: the experimental Kotlin and Java DSL in core 5.6 is different from JMeter Java DSL 2.3, a
  third-party library from Abstracta. Both are covered later in this section, in the programmatic test plans page.
* **Docker and Gradle**: there is still no official Apache JMeter Docker image and no official Gradle plugin; book
  recipes based on Vagrant, Flood.io or specific cloud images are dated.

== Pitfalls when upgrading

* **Trusting the exit code.** JMeter exits with 0 even when a converted element produced no samples or every sample
  failed (see xref:backend/jmeter/running-tests-in-cli-mode.adoc[Running Tests in CLI Mode]); check the sample count
  and the error rate in `statistics.json` or the JTL.
* **Comparing across versions without a new baseline.** Changes such as the 5.0 HTTP state reset or the 3.1
  transaction handling in reports alter numbers by design.
* **Mixing versions in a distributed run.** The controller and the workers must run the same JMeter, Java and plugins.
* **Keeping an old copy of Groovy.** Since 3.0 Groovy is bundled in `lib`; a copy in `search_paths` or
  `user.classpath` left over from a 2.x setup conflicts with it.
* **Editing `jmeter.properties` to restore old behaviour.** Put overrides in `user.properties` so that the next upgrade
  does not discard them (see xref:backend/jmeter/installation-and-configuration.adoc[Installation & Configuration]).
* **Treating master-branch behaviour as released.** Anything described as 6.0 on this page comes from the development
  branch and may still change.
