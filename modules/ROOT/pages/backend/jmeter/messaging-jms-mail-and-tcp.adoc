== What these samplers measure

A JMeter sampler measures one interaction from the client's point of view. For HTTP that is obvious: request out,
response back. For messaging it depends on the style of interaction, and the choice decides what the numbers mean.

[cols="1,2,2",options="header"]
|===
|Sampler and mode |One sample is... |What its elapsed time means

|JMS Point-to-Point, *Request Only*
|Sending one message to a queue
|How long the broker takes to accept the message (for persistent delivery, including the broker's store write). Says
nothing about when, or whether, it is consumed.

|JMS Point-to-Point, *Request Response*
|Sending a request and waiting for the matching reply
|End-to-end round trip through the broker and the service that consumes the request and replies. The only JMS mode that
measures a service's response time.

|JMS Publisher
|Publishing *Number of samples to aggregate* messages to a topic or queue
|Time to publish that batch.

|JMS Subscriber
|Receiving *Number of samples to aggregate* messages from a topic or queue
|Mostly the time spent *waiting* for messages to arrive. It is a throughput and delivery check, not a latency
measurement of any server.

|SMTP Sampler
|One complete SMTP session that sends one message
|Connect, optional TLS and authentication, and the transfer of one message to the mail server.

|Mail Reader Sampler
|One complete POP3 or IMAP session that reads some or all messages of a folder
|Connect, log in, open the folder, fetch the messages (and optionally delete them).

|TCP Sampler
|Sending a block of bytes on a socket and reading one response
|Time until the response is considered complete, which depends on how the client implementation detects the end of a
response.
|===

The rest of the page goes through the samplers in that order. All of them are added with *Add -> Sampler -> ...* on a
Thread Group or a controller, and follow the usual scoping and execution order described on
xref:backend/jmeter/test-plan-elements-execution-order-and-scoping.adoc[Test Plan Elements, Execution Order & Scoping]:
config elements, pre-processors and timers in scope run before the sampler, post-processors and assertions after it.

== A local test bed

Load tests are only ever aimed at the reader's own systems. The test bed below runs a JMS broker and a mail server on
the developer machine, bound to `127.0.0.1` so nothing is exposed on the network. Both images are official or
project-published images: `apache/activemq-classic` is published by the ActiveMQ project, and `greenmail/standalone`
by the GreenMail project.

[source,yaml]
----
# compose.yaml -- local brokers for the JMeter messaging examples
services:
  activemq:
    image: apache/activemq-classic:5.19.2
    environment:
      # Enables authentication on the broker's transport connectors.
      # Placeholder values: replace them, and never commit real ones.
      ACTIVEMQ_CONNECTION_USER: loadtest
      ACTIVEMQ_CONNECTION_PASSWORD: change-me
    ports:
      - "127.0.0.1:61616:61616"   # OpenWire (JMS clients)
      - "127.0.0.1:8161:8161"     # web console, to watch queue depths
  greenmail:
    image: greenmail/standalone:2.1.14
    environment:
      GREENMAIL_OPTS: >-
        -Dgreenmail.setup.test.all
        -Dgreenmail.hostname=0.0.0.0
        -Dgreenmail.users=reader1:change-me@bookshelf.test
        -Dgreenmail.users.login=email
    ports:
      - "127.0.0.1:3025:3025"     # SMTP
      - "127.0.0.1:3110:3110"     # POP3
      - "127.0.0.1:3143:3143"     # IMAP
----

----
docker compose up -d

----

`ACTIVEMQ_CONNECTION_USER` and `ACTIVEMQ_CONNECTION_PASSWORD` switch on authentication for JMS clients (without them,
the image accepts anonymous connections); `GREENMAIL_OPTS` configures one mailbox, `reader1@bookshelf.test`, whose login
is the full e-mail address because of `greenmail.users.login=email`. The TCP examples need a third, even smaller server,
started later on this page.

The credentials reach JMeter as run properties, never as literals in the `.jmx` file. The JMS and mail samplers all
store their password fields **unencrypted** in the test plan (the component reference says so for each of them), so a
literal password in a committed plan is a leaked password:

[source,properties]
----
# messaging.properties -- passed with -q messaging.properties (placeholder values)
jms_url=tcp://localhost:61616
jms_user=loadtest
jms_password=change-me
mail_user=reader1@bookshelf.test
mail_password=change-me
tcp_host=localhost
tcp_port=7000
----

== JMS in JMeter

JMS (Java Message Service, now Jakarta Messaging) is a Java *API*, not a protocol: every broker ships its own client
library that implements the API and speaks the broker's wire protocol. JMeter's three JMS samplers are written against
the API only, so they work with any broker whose JMS client jar is on JMeter's classpath, and they find the broker's
objects (connection factory, queues, topics) through JNDI.

[cols="1,3",options="header"]
|===
|Sampler |Use it for

|*JMS Point-to-Point*
|Queues. Sends messages and, optionally, waits for replies: request only (fire and forget), request/response with
correlation, plus *Read*, *Browse* and *Clear* utilities.

|*JMS Publisher*
|Sending messages to a topic (publish/subscribe) or a queue, from inline text, a file or a random file from a folder;
text, map, object or bytes messages.

|*JMS Subscriber*
|Receiving messages from a topic or a queue, with an optional durable subscription and message selector.
|===

The official tutorials build one plan of each kind: the point-to-point tutorial uses one Thread Group of 5 threads, each
sending 4 messages through a request queue and waiting on a fixed reply queue; the topic tutorial uses a *Subscribers*
Thread Group of 5 threads and a *Publisher* Thread Group of 1 thread, 10 iterations each. The Bookshelf examples below
follow the same shapes with the Bookshelf loan flow.

=== Provider jars in `lib`

JMeter includes the JMS API jar, but no JMS client implementation. The provider's jars go in JMeter's `lib` directory,
not in `lib/ext` (which is for plugins), or in a directory listed in the `user.classpath` property; JMeter must be
restarted after adding them. Setting the `CLASSPATH` environment variable has no effect, because JMeter is started with
`java -jar`. For ActiveMQ the getting-started guide asks for the single `activemq-all-X.X.X.jar`.

The *version* of the client jar matters more than the guide suggests, because the JMS API changed package name:

[cols="1,2,2",options="header"]
|===
|JMeter |JMS API it is compiled against |Compatible client jars

|5.6.3 (current)
|`javax.jms` (the Apache Geronimo JMS 1.1 spec jar shipped in `lib`)
|Clients that implement `javax.jms`: ActiveMQ Classic 5.x (for example `activemq-all-5.19.2.jar`), the ActiveMQ
Artemis "JMS" client (not the "Jakarta" one), IBM MQ's `javax.jms` client, and so on.

|6.0 (planned)
|`jakarta.jms` (Jakarta Messaging 3.1) in the master-branch source
|Clients that implement `jakarta.jms`: ActiveMQ Classic 6.x, the Artemis Jakarta client, and so on.
|===

The 5.6.3 column is from the 5.6.3 build files (`geronimo-jms_1.1_spec`); ActiveMQ Classic 6.x moved its client to the
Jakarta Messaging API, so a 6.x client jar dropped into JMeter 5.6.3 does not provide the `javax.jms` classes the
samplers call. The broker version is a separate question: a 5.19 *client* talks OpenWire to a 5.19 or 6.x *broker*
alike. The 6.0 column is from the master branch, whose JMS module now depends on `jakarta.jms-api` 3.1.0 and imports
`+jakarta.jms.*+`; at the time of writing this is not yet listed in `changes.xml`, so treat it as planned and re-check
the 6.0 release notes before upgrading. A plan written for 5.6.3 keeps working on 6.0 as far as the `.jmx` file is
concerned; it is the jars in `lib` that will need replacing.

[source,bash]
----
# Install the ActiveMQ Classic 5.19.x all-in-one client into JMeter 5.6.3 (download it from the ActiveMQ site
# or Maven Central and verify its checksum first)
cp activemq-all-5.19.2.jar "$JMETER_HOME/lib/"
ls "$JMETER_HOME/lib" | grep -i -E 'jms|activemq'
----

=== JNDI: how the samplers find the broker

All three samplers look up a connection factory and destinations through a JNDI `InitialContext`. They can build it in
two ways:

* **From fields in the sampler**: an *Initial Context Factory* class name, a *Provider URL*, and (Point-to-Point only)
  a table of extra *JNDI Properties*.
* **From a `jndi.properties` file** (Publisher and Subscriber only, through the *Use jndi.properties file* checkbox):
  the file must be on the classpath, for example in a directory added to `user.classpath`; the context-factory and
  provider-URL fields are then disabled.

For ActiveMQ Classic, the component reference gives these values:

[cols="1,2,2",options="header"]
|===
|Item |Value |Comment

|Context factory
|`org.apache.activemq.jndi.ActiveMQInitialContextFactory`
|

|Provider URL
|`vm://localhost`, or `tcp://localhost:61616` for a separate broker
|`vm://` starts an embedded broker inside JMeter; the tutorials use `tcp://localhost:61616`.

|Provider URL
|`vm:(broker:(vm://localhost)?persistent=false)`
|Embedded broker with persistence disabled

|Queue reference
|`dynamicQueues/QUEUENAME`
|Defines the queue in JNDI dynamically, without configuration

|Topic reference
|`dynamicTopics/TOPICNAME`
|Defines the topic in JNDI dynamically, without configuration
|===

The default connection factory name in ActiveMQ's JNDI context is `ConnectionFactory`. Fixed JNDI names are defined
with `queue.<jndiName>=<physicalName>` and `topic.<jndiName>=<physicalName>` entries, which is what the point-to-point
tutorial does (`queue.Q.REQ=example.A`, `queue.Q.RPL=example.B`). An embedded `vm://` broker is handy for a quick
experiment, but it runs inside the load generator and competes with it for CPU and heap; a load test should always use
a separate broker.

The Bookshelf `jndi.properties`, for the Publisher and Subscriber when the checkbox is used:

[source,properties]
----
# jndi.properties -- in a directory listed in user.classpath
java.naming.factory.initial=org.apache.activemq.jndi.ActiveMQInitialContextFactory
java.naming.provider.url=tcp://localhost:61616
queue.LoanRequests=bookshelf.loan.requests
queue.LoanReplies=bookshelf.loan.replies
topic.LoanEvents=bookshelf.loan.events
----

[source,properties]
----
# user.properties
user.classpath=../lib;/opt/bookshelf-loadtest/jndi
----

For ActiveMQ Artemis the equivalent JNDI factory is `org.apache.activemq.artemis.jndi.ActiveMQInitialContextFactory`,
and connection factories are declared as `connectionFactory.<name>=tcp://host:port` entries, with the same `queue.`
and `topic.` prefixes for destinations; with JMeter 5.6.3 use Artemis's `javax.jms` client, not its Jakarta client.

https://jmeter.apache.org/usermanual/build-jms-point-to-point-test-plan.html[Building a JMS Point-to-Point Test Plan (User Manual)],
https://activemq.apache.org/components/classic/documentation/jndi-support[ActiveMQ Classic JNDI Support] and

== JMS Point-to-Point

The JMS Point-to-Point sampler sends, and optionally receives, messages through queues. The component reference sums up
its modes: *request only* typically puts load on a JMS system, while *request/reply* is used to test the response time
of a JMS service that processes messages from the request queue, because it waits for the response on the reply queue.

=== Communication styles

[cols="1,1,3",options="header"]
|===
|Style |JMX value (`JMSSampler.communicationStyle`) |Behaviour

|*Request Only*
|`0`
|Sends messages and does not monitor replies ("fire and forget"). Use it to load a broker or a consumer service.

|*Request Response*
|`1`
|Sends a message and waits for the matching reply. If *JNDI name Receive queue* has a value, that fixed queue is
monitored and the reply is matched to the request through message and correlation IDs. If it is empty, JMeter uses a
*temporary queue*, and the sending thread blocks until the reply arrives. Either way a server must listen on the request
queue and send replies to the queue in the message's `JMSReplyTo` header.

|*Read*
|`2`
|Reads a message from a queue that has no listener attached (useful in tests). Combined with *Number of samples to
aggregate*, it reads several.

|*Browse*
|`3`
|Returns the current queue depth without removing messages.

|*Clear*
|`4`
|Removes all messages from the queue.
|===

The numeric values are the 5.6.3 source's `JMS_COMMUNICATION_STYLE` enum; older plans contain a
`JMSSampler.isFireAndForget` boolean from before *Read*, *Browse* and *Clear* existed (they arrived in JMeter 4.0).

Source: https://jmeter.apache.org/usermanual/component_reference.html#JMS_Point-to-Point[JMS Point-to-Point (Component Reference)]

=== Correlation: matching a reply to its request

With a fixed reply queue, many threads wait on the same queue, so JMeter must know which reply belongs to which request.
Two checkboxes under *Use alternate fields for message correlation* decide which header fields are compared:

* *Use Request Message Id*: if selected, the request's `JMSMessageID` is used, otherwise the request's
  `JMSCorrelationID` (which then has to be set on the request, through the *JMS Properties* table).
* *Use Response Message Id*: if selected, the response's `JMSMessageID` is used, otherwise the response's
  `JMSCorrelationID`.

[cols="1,1,1,2",options="header"]
|===
|Pattern |Use Request Message Id |Use Response Message Id |The service must...

|*JMS Message ID pattern* (most common)
|selected
|cleared
|copy the request's `JMSMessageID` into the reply's `JMSCorrelationID`.

|*JMS Correlation ID pattern*
|cleared
|cleared
|copy the request's `JMSCorrelationID` into the reply's `JMSCorrelationID`; the plan sets a unique correlation ID on
each request.

|Same queue for request and reply (raw broker throughput)
|selected
|selected
|nothing: the "reply" is the request message itself, so both message IDs match.
|===

In both real patterns the application is responsible for populating the correlation ID. A correlation ID can be set on
the request by adding a row named `JMSCorrelationID` to the *JMS Properties* table (the name is matched case
insensitively in the 5.6.3 source, which also treats a `JMSType` row as the `JMSType` header since JMeter 5.4).

[mermaid]
----
sequenceDiagram
    participant T as JMeter thread
    participant RQ as bookshelf.loan.requests
    participant W as Loan worker
    participant RP as bookshelf.loan.replies
    T->>RQ: send request, JMSReplyTo = replies queue
    Note over T: message ID ID:42 recorded, timer started
    RQ->>W: deliver request
    W->>RP: reply with JMSCorrelationID = ID:42
    RP->>T: shared receiver matches ID:42 to the waiting thread
    Note over T: sample ends, elapsed = round trip
----

With the *Request Response* style and a reply queue, the sampler sets the request's `JMSReplyTo` to that queue; one
receiver per reply queue hands each reply to the thread waiting for its ID. Replies that arrive after the *Timeout* are
discarded and the sample fails with the response message `No reply message received`.

Source: https://jmeter.apache.org/usermanual/component_reference.html#JMS_Point-to-Point[JMS Point-to-Point (Component Reference)]

The JMX property names are from the 5.6.3 source (`JMSSampler.java`); the field labels and descriptions are from the

|*Name*
|`testname` attribute

|`JMSSampler.isNonPersistent`
|Sends with `DeliveryMode.NON_PERSISTENT`.

|*Content*
|`HTTPSamper.xml_data` (sic)
|The message body (a text message). JMeter functions and variables are evaluated.

|*JMS Properties*
|`arguments` (a `JMSProperties` element)

|*Initial Context Factory*
|`JMSSampler.initialContextFactory`
|Class of the JNDI context factory.

|*JNDI Properties*
|`JMSSampler.jndiProperties`

|*Provider URL*

=== Example 1: raw broker throughput on one queue

The smallest runnable JMS test needs nothing but the broker: request and reply on the *same* queue, with both
correlation checkboxes selected, so every request comes back to its own thread as its "reply". It measures the broker's
send-plus-receive cost, which is a useful baseline before a service is involved.

. Copy the client jar into `lib` as shown above and start JMeter.
. *Add -> Threads (Users) -> Thread Group*: name `Broker baseline`, *Number of Threads*
  `+${__P(threads,1)}+`, *Ramp-up period* `+${__P(rampup,1)}+`, *Loop Count* *Infinite*, *Specify Thread lifetime*
  with *Duration* `+${__P(duration,60)}+`.
. *Add -> Sampler -> JMS Point-to-Point* on it, and fill in:
** *QueueConnection Factory*: `ConnectionFactory`
** *JNDI name Request queue* and *JNDI name Receive queue*: `dynamicQueues/bookshelf.baseline`
** *Communication style*: *Request Response*; both *Use Request Message Id* and *Use Response Message Id* selected
** *Timeout (ms)*: `5000`; *Content*: `ping`
** *Initial Context Factory*: `org.apache.activemq.jndi.ActiveMQInitialContextFactory`
** *Provider URL*: `+${__P(jms_url,tcp://localhost:61616)}+`
** *JNDI Properties*: `java.naming.security.principal` = `+${__P(jms_user,)}+` and
   `java.naming.security.credentials` = `+${__P(jms_password,)}+`
. *Add -> Assertions -> Response Assertion* below the sampler, *Text Response* *Contains* `ping`.

[source,xml]
----

  <stringProp name="JMSSampler.ReceiveQueue">dynamicQueues/bookshelf.baseline</stringProp>

  <boolProp name="JMSSampler.useResMsgIdAsCorrelId">true</boolProp>
  <boolProp name="JMSSampler.isNonPersistent">false</boolProp>
  <stringProp name="JMSSampler.timeout">5000</stringProp>
  <stringProp name="HTTPSamper.xml_data">ping</stringProp>

  <elementProp name="JMSSampler.jndiProperties" elementType="Arguments" guiclass="ArgumentsPanel"

        <stringProp name="Argument.name">java.naming.security.principal</stringProp>

=== Temporary reply queues

Leaving *JNDI name Receive queue* empty switches *Request Response* to temporary queues: JMeter sets `JMSReplyTo` to a
temporary queue and the sending thread blocks until the reply arrives. The component reference stresses that this is
very different from a fixed reply queue. The service under test sees the same `JMSReplyTo` contract, so it needs no
change, but the broker now creates and deletes temporary destinations, which is extra load that production may not
have. Use the same reply mechanism as the real clients.

=== Read, Browse and Clear

The three utility styles make queue housekeeping part of the plan rather than a manual step:

* a *Clear* sample in a *setUp Thread Group* empties `bookshelf.loan.requests` before the run, so leftover messages
  from a previous run do not distort the first minutes;
* a *Browse* sample in a *tearDown Thread Group* records the final queue depth (response message
  `N messages available on the queue`), and an assertion can fail the run when it is not zero;
* a *Read* sample takes messages from a queue nobody consumes, for example to check what a *Request Only* run left
  behind.

Source: https://jmeter.apache.org/usermanual/component_reference.html#JMS_Point-to-Point[JMS Point-to-Point (Component Reference)]

== JMS Publisher and JMS Subscriber

The JMS Publisher publishes messages to a destination (topic or queue) and the JMS Subscriber subscribes to messages
from one. They are independent samplers, usually in different Thread Groups, as in the topic tutorial: one group of
subscribers and one group of publishers.

=== Why messages are aggregated

The topic tutorial explains *Number of samples to aggregate* by performance: small messages arrive very quickly, and if
the sampler did not aggregate them JMeter would not be able to keep up. Each sample costs a result object, listener
work and a line in the JTL file; at thousands of messages per second, one sample per message turns the load generator
into the bottleneck. Aggregating 10 or 100 messages per sample divides that overhead accordingly. The flip side is that
one sample's elapsed time covers the whole batch, so per-message latency is not visible; when it matters, put a
timestamp in the message body and compute it on the consumer side, or use request/reply.

The tutorial also notes that the two subscriber client implementations exist because some providers show zombie
threads with one of them: if that happens, try the other.

== JMS on the load generator and common pitfalls

* **Connections per thread.** The JMS samplers open their connections per thread, so 200 threads mean about 200 broker
  connections, each with its sessions and, for subscribers, buffers of prefetched messages. That load on the broker is
  part of the test; on the generator it costs memory and threads.
* **One shared reply matcher.** With a fixed reply queue, the 5.6.3 source matches every reply through one shared,
  synchronized registry; at very high request rates that becomes a point of contention inside JMeter, which shows up as
  a rising round trip that the broker's own metrics do not confirm. Spread such load over more JMeter instances.
* **Stored responses.** *Store Response* on a subscriber, and View Results Tree anywhere, keep message bodies in memory.
  Clear it for load runs.
* **Object messages.** XStream serialization and deserialization cost CPU per message; prefer text or bytes messages
  unless the system really uses object messages.
* **Persistent versus non-persistent.** Persistent delivery is the default and costs the broker a store write per
  message, so it is usually noticeably slower. Match production, and state the mode in the test report.
* **Leftover messages.** A queue that still holds messages from an earlier run makes the first minutes of a
  request/response test meaningless (replies to old requests, a worker busy with stale work). Clear queues in a setUp
  Thread Group.
* **Timeouts that hide failures.** A Point-to-Point *Timeout* of `0` waits forever: a lost reply freezes the thread and
  silently lowers the offered load. Always set a finite timeout above the SLA.
* **Wrong jar generation.** `NoClassDefFoundError` for a `javax.jms` or `jakarta.jms` class in `jmeter.log` almost
  always means a client jar of the other API generation (see the table above).

Source: https://jmeter.apache.org/usermanual/best-practices.html[Best Practices (User Manual)] and
https://jmeter.apache.org/usermanual/component_reference.html#JMS_Subscriber[JMS Subscriber (Component Reference)]

== SMTP Sampler

The SMTP Sampler sends mail messages using SMTP or SMTPS. It supports SSL and StartTLS, user authentication, CC, BCC
and Reply-To addresses, extra headers, attachments, and sending a ready-made `.eml` file. Every sample is a complete
SMTP session: the 5.6.3 source connects, authenticates if asked, sends one message and closes the connection. Its
purpose in a load test is to load a *mail server*, typically the relay the application sends through; to test how the
Bookshelf API behaves when it sends confirmation e-mails, load the API and point it at a test mail server instead.

Load tests must never send mail through a third-party or production mail service: besides the risk of spamming real
addresses, providers rate-limit and block such traffic. Use a local test server such as GreenMail.

== TCP Sampler

The TCP Sampler opens a TCP/IP connection to a server, sends text and waits for a response. It speaks no protocol of
its own: the bytes it sends are exactly the *Text to send* (after variable substitution), and a pluggable *TCPClient*
class decides how the text is encoded and, crucially, how the end of the response is detected. That makes it the
sampler for line-based legacy services, simple binary protocols and anything else without a dedicated sampler.

=== Connections

* With *Re-use connection* selected, connections are shared between TCP Samplers **of the same thread** that use
  exactly the same host name string and port. Different host/port combinations and different threads use different
  connections.
* With both *Re-use connection* and *Close connection* selected, the socket is closed after the sampler runs and a new
  one is created by the next sampler, which is a way to close the socket at the end of each thread loop.
* When an error is detected, or *Re-use connection* is not selected, the socket is closed and another one is opened on
  the next sample.
* Sockets are disconnected at the end of the test run.

=== The client implementations

The class is chosen by the *TCPClient classname* field, failing that by the `tcp.handler` property; a short name is
looked up in the package `org.apache.jmeter.protocol.tcp.sampler`. Users can provide their own class, which must extend
`org.apache.jmeter.protocol.tcp.sampler.TCPClient`.

[cols="1,2,2",options="header"]
|===
|Class |Request |End of the response

|`TCPClientImpl` (default)
|The text, encoded with `tcp.charset` (default: the platform's default encoding).
|The end-of-line byte, if `tcp.eolByte` (or the GUI field) is set; otherwise the end of the input stream.

|`BinaryTCPClientImpl`
|The text must be a hex-encoded string, converted to binary (and the response converted back to hex).
|The end-of-message byte, if `tcp.BinaryTCPClient.eomByte` is set; otherwise the end of the input stream.

|`LengthPrefixedBinaryTCPClientImpl`
|As `BinaryTCPClientImpl`, prefixed with a binary length.
|The number of bytes given by the response's length prefix; the prefix is 2 bytes unless
`tcp.binarylength.prefix.length` says otherwise.
|===

**The most common TCP Sampler bug** follows from that table: with `TCPClientImpl`, no EOL byte and a server that keeps
the connection open, "end of the input stream" never comes, so every sample waits for the *Response Timeout* (or
forever, if none is set). Define how a response ends: an EOL byte, an EOM byte, a length prefix, or a server that
closes the connection. And if an EOL or EOM byte is used, the *Response Timeout* must be long enough, because the read
is cut off when it expires.

=== Properties

[cols="2,1,3",options="header"]
|===
|Property |Default |Meaning

|`tcp.handler`
|`TCPClientImpl`
|Client class when the GUI field is empty.

|`tcp.eolByte`
|`1000` (disabled)
|End-of-line byte for `TCPClientImpl`; a value outside -128 to +127 disables EOL checking. The GUI field wins over the
property.

|`tcp.charset`
|platform default
|Charset of `TCPClientImpl`.

|`tcp.BinaryTCPClient.eomByte`
|not set
|End-of-message byte for `BinaryTCPClientImpl`.

|`tcp.binarylength.prefix.length`
|`2`
|Length-prefix size, in bytes, for `LengthPrefixedBinaryTCPClientImpl`.

|`tcp.status.prefix`, `tcp.status.suffix`
|not set
|Text before and after a status code in the response.

|`tcp.status.properties`
|not set
|Properties file that maps status codes to response messages.
|===

When `tcp.status.prefix` is defined, the response is searched for the text between prefix and suffix, which becomes the
response code, and the message comes from the properties file if given. With prefix `[` and suffix `]`, the response
`[J28] XI123,23,GBP,CR` has response code `J28`. Response codes from 400 to 499 and 500 to 599 count as failures;
everything else is a success.

=== Example 2: a length-prefixed binary message

Binary protocols often frame messages with a length prefix. `LengthPrefixedBinaryTCPClientImpl` adds the 2-byte prefix
to the request and reads exactly as many bytes as the response's prefix announces, so it works on a connection that
stays open. Against the same echo server, the response is the request itself:

* *TCPClient classname*: `LengthPrefixedBinaryTCPClientImpl`
* *Text to send*: `0102002A`, the hex encoding of 4 bytes (for example a message type `01`, a version `02` and a book
  ID `0x002A` = 42)
* *Response Assertion*: *Text Response* *Equals* `0102002A`

On the wire JMeter sends `0004 0102002A` (the prefix 4 in two bytes, then the data) and expects the same framing back.
If the real protocol uses a 4-byte prefix, set `tcp.binarylength.prefix.length=4`. With plain `BinaryTCPClientImpl`,
the same request would need `tcp.BinaryTCPClient.eomByte` or a server that closes the connection.

Source: https://jmeter.apache.org/usermanual/component_reference.html#TCP_Sampler[TCP Sampler (Component Reference)]

=== Connection reuse, `TIME_WAIT` and the load generator

The TCP Sampler is light on CPU; its cost is sockets. *Worked numbers* for the stock lookup with 50 threads, a 1 s think
time and a 5 ms response:

* each thread makes about 1 / 1.005 ≈ 0.995 requests per second, so the plan offers ≈ 50 requests per second;
* with *Re-use connection*, that is 50 long-lived sockets in total, one per thread;
* without it, every sample opens and closes a connection: 50 new connections per second. The side that closes first
  keeps each closed socket in `TIME_WAIT`, on Linux for 60 s, so about 50 × 60 = 3000 sockets sit in `TIME_WAIT` on
  the load generator. At 500 requests per second that becomes 30 000, above the 28 232 ephemeral ports of the usual
  Linux default range (32768 to 60999), and new connections start failing with errors that look like a server problem.

Reuse connections when the real clients do, and close them per sample only when the real clients do too. *SO_LINGER*
`0` makes the close abortive and avoids `TIME_WAIT`, as the component reference notes, at the price of a reset instead
of an orderly close; use it only when the server tolerates that. *Set NoDelay* matters for small request/response
messages: with Nagle's algorithm on, a small write can be delayed waiting for an acknowledgement, which inflates
response times for reasons that have nothing to do with the server.

Source: https://jmeter.apache.org/usermanual/component_reference.html#TCP_Sampler[TCP Sampler (Component Reference)]

|Java 17+; the master-branch JMS module uses `jakarta.jms` (Jakarta Messaging 3.1), so provider jars must be Jakarta
