== gRPC basics for load testers

gRPC is a remote procedure call framework. A service is described in a `.proto` file written in the Protocol Buffers
language: messages (typed records with numbered fields) and services (named methods taking one message type and
returning another). Code generators turn the file into client stubs and server skeletons for many languages. On the
wire, the points that matter for load testing are:

* **HTTP/2 transport.** Every call is an HTTP/2 request with `POST` to the path `/<package>.<Service>/<Method>`, for
  example `/bookshelf.v1.LoanService/CreateLoan`, and content type `application/grpc`. HTTP/2 multiplexes many
  concurrent calls (streams) over **one TCP connection**, so a gRPC client normally keeps a long-lived connection
  (a *channel*) and does not open a connection per call.
* **Protobuf payloads.** Messages are binary-encoded Protocol Buffers, not text. A tester cannot type a request body by
  hand without a tool that knows the message schema; that is why every gRPC load tool needs either the `.proto` files,
  a compiled descriptor set or generated code.
* **Four call types.** *Unary* (one request, one response), *server streaming* (one request, a stream of responses),
  *client streaming* (a stream of requests, one response) and *bidirectional streaming*. The type is declared in the
  `.proto` with the `stream` keyword.
* **Deadlines.** The client states how long it is willing to wait for the call. If the deadline passes, the call ends
  with the status `DEADLINE_EXCEEDED` on the client, and well-behaved servers stop working on it. In a load test the
  deadline acts as the timeout and defines what counts as "too slow".
* **Metadata.** Key/value pairs sent as HTTP/2 headers with the call (and returned as headers and trailers). It carries
  authentication (`+authorization: Bearer ...+`), tracing ids and tenant ids. Keys are case-insensitive ASCII; keys
  ending in `-bin` carry binary values.
* **Status codes.** The result of a call is a gRPC status, sent in the `grpc-status` trailer, not the HTTP status
  (which is `200` even for most failed calls). The codes are:

[cols="1,3,5",options="header"]
|===
|Code |Name |Typical meaning in a load test

|0 |`OK` |Success.
|1 |`CANCELLED` |The client cancelled the call.
|2 |`UNKNOWN` |An unexpected server error, often an exception not mapped to a status.
|3 |`INVALID_ARGUMENT` |The request is invalid regardless of system state: usually a test-data problem.
|4 |`DEADLINE_EXCEEDED` |The deadline expired before the call completed: the service is too slow for the deadline you set.
|5 |`NOT_FOUND` |The requested entity does not exist, for example an unknown loan id after a failed correlation.
|6 |`ALREADY_EXISTS` |A create conflicted with an existing entity: often non-unique test data.
|7 |`PERMISSION_DENIED` |The caller is authenticated but not allowed.
|8 |`RESOURCE_EXHAUSTED` |A quota or limit was hit (rate limiting, message too large, server out of resources).
|9 |`FAILED_PRECONDITION` |The system is not in the state required, for example the book is already on loan.
|10 |`ABORTED` |A concurrency conflict, typically a transaction abort.
|11 |`OUT_OF_RANGE` |A value past the valid range.
|12 |`UNIMPLEMENTED` |The method is not implemented by this server: usually a wrong full method name or a stale `.proto`.
|13 |`INTERNAL` |An internal invariant was broken.
|14 |`UNAVAILABLE` |The service is currently unavailable: connection refused or reset, server overloaded or shutting down.
|15 |`DATA_LOSS` |Unrecoverable data loss or corruption.
|16 |`UNAUTHENTICATED` |Missing or invalid credentials: an absent or expired bearer token in the metadata.
|===

Source: https://grpc.io/docs/what-is-grpc/core-concepts/[Core concepts, architecture and lifecycle (gRPC)], https://grpc.io/docs/guides/status-codes/[Status Codes (gRPC)], https://grpc.io/docs/guides/deadlines/[Deadlines (gRPC)] and https://grpc.io/docs/guides/metadata/[Metadata (gRPC)]

Two consequences shape every gRPC load test:

* **Connections are few and long-lived.** A load test that opens a fresh connection per call measures connection setup
  (and the TLS handshake), not the service. Conversely, because one connection carries all calls of a client, a load
  balancer that balances connections (layer 4) sends all calls of one client to the same backend. The gRPC project
  describes this as the reason for proxy (layer 7) or client-side load balancing. If the test uses few connections
  against a scaled-out service behind a layer-4 balancer, some backends may receive no load at all.
* **Success is not the HTTP status.** A tool that only checks "the HTTP exchange worked" reports `NOT_FOUND` or
  `UNAUTHENTICATED` calls as successes. The sampler must turn the gRPC status into a JMeter success flag and the test
  must assert on it.

Source: https://grpc.io/blog/grpc-load-balancing/[gRPC Load Balancing (gRPC blog)] and https://grpc.io/docs/guides/performance/[Performance Best Practices (gRPC)]

== What core JMeter offers: no gRPC

Apache JMeter 5.6.3 has no gRPC sampler, and none is planned in `changes.xml` for 6.0. The HTTP Request sampler cannot
stand in for one: its implementations (`HttpClient4` and `Java`) speak HTTP/1.1, while gRPC requires HTTP/2 framing,
binary protobuf bodies and trailers carrying the status. The component reference lists no HTTP/2 or gRPC element.

The options are therefore:

[cols="2,3,3,2",options="header"]
|===
|Option |How it builds the request |What you need |Status (2026-10-14)

|*JMeter gRPC Request* plugin (`jmeter-grpc-request`) |Compiles the `.proto` files at run time and builds the message from JSON. No code generation. |The plugin jar in `lib/ext` and the `.proto` files (or a descriptor set). |Original repository archived on 2024-04-04 (last release 1.2.6, 2022-12-10). Continued as 2.0.0 to 2.0.2 (April 2026) by a different maintainer; served by the Plugins Manager.
|*JMeter gRPC Plugin* (`zalopay-oss/jmeter-grpc-plugin`) |Java code you write against stubs generated from your protos. |A jar of generated classes plus the plugin jar in `lib/ext`. |One release, 0.1.0 (2020-03-15); last commit 2023-06; not archived, not in the Plugins Manager catalogue.
|JSR223 Sampler + grpc-java stubs |A Groovy script calls a generated blocking stub. |Generated stubs and the grpc-java libraries on the classpath. |An unofficial pattern, not a product: you maintain it.
|Tools outside JMeter |Their own gRPC clients. |A second tool and report format. |Named in prose only, at the end of this page.

The JMeter Java DSL (Abstracta) has no gRPC support either: its user guide does not mention gRPC. The rest of this page
uses the first option and returns to the others under <<alternatives>>.

=== How the plugin works

The README summarises the design: no generated classes and no compiled protos are needed; you give it the host and
port, the method, the folder with the `.proto` files and the request as JSON, and it "parses proto files at runtime".
It supports blocking unary calls, plaintext and TLS connections, authentication through metadata and JSON request
data. The 2.0.2 source (`GRPCSampler.java`, `ClientCaller.java`, `ProtocInvoker.java`, `ChannelFactory.java`) shows
the sequence in more detail:

[mermaid]
----
sequenceDiagram
    participant T as JMeter thread
    participant S as GRPC Request sampler
    participant P as protoc and descriptors
    participant C as Netty channel over HTTP/2
    participant G as LoanService server
    participant X as Extractors and assertions
    opt first sample of this sampler in this thread
        S->>P: compile every .proto under Proto Root Directory
        P-->>S: descriptor set, resolve package.Service/Method
        S->>C: build channel: plaintext, TLS or mTLS
    end
    loop every iteration
        T->>S: sample
        S->>S: substitute variables, JSON to dynamic protobuf message, parse metadata
        S->>C: blocking unary call with deadline and metadata
        C->>G: HTTP/2 POST /bookshelf.v1.LoanService/CreateLoan
        G-->>C: response message and grpc-status trailer
        alt status OK
            C-->>S: Loan message
            S-->>T: sample result 200, body is the response printed as JSON
        else any other status
            C-->>S: status exception
            S-->>T: sample result 500, message is the status code and name
        end
        T->>X: JSON Extractor sets loanId, assertions check code and payload
    end
----

The important details, read from the 2.0.2 source:

* **Compilation happens once per sampler per thread, at its first sample.** JMeter gives every thread its own copy of
  each sampler. On the first sample, the copy runs the bundled `protoc` over every `.proto` file under *Proto Root
  Directory* (with *Library Directory* and the protobuf well-known types on the include path), resolves the full
  method, and creates its channel. This preparation happens before the sample's timer starts, so it is not in the
  measured time, but it costs CPU and a few temporary files on the load generator. A 50-thread plan with two gRPC
  samplers runs `protoc` 100 times during the ramp-up.
* **One channel per sampler copy.** Each thread's sampler keeps its own Netty channel, reused for every iteration of
  that thread. Fifty threads with two samplers hold up to 100 HTTP/2 connections, which is closer to "100 independent
  clients" than to one service client multiplexing many calls on one connection.
* **The request and metadata are re-evaluated on every sample.** Variables and functions in the JSON request and the
  metadata are substituted per iteration, so `+${loanId}+` and `+${token}+` work as expected. Host, port, method, protos
  and TLS settings are read once per thread, at the first sample.
* **Only the unary path is used.** The client code contains server-, client- and bidirectional-streaming methods, but
  the sampler only ever calls the blocking unary path.

Source: https://github.com/bakthava/jmeter-grpc-request[bakthava/jmeter-grpc-request README and source at v2.0.2 (GitHub)]

=== Installing the plugin

The plugin is a single jar that must end up in `lib/ext` of every JMeter installation that runs the plan, followed by a
restart. There are four ways to put it there.

image::jmeter-grpc-plugin-setup.svg["The files involved in a gRPC test: the project folder with bookshelf-grpc.jmx, protos and data, the JMeter installation with the plugin jar in lib/ext, and the Bookshelf gRPC LoanService",width=720]

**1. Plugins Manager GUI.** With the Plugins Manager installed (see
xref:backend/jmeter/plugins-and-plugins-manager.adoc[Plugins & Plugins Manager]):

. *Options → Plugins Manager*, tab *Available Plugins*.
. Type `grpc` in the search box and tick *JMeter gRPC Request*. The right-hand panel shows the description and a
  version selector; choose the version (2.0.2 here, or 1.2.6 for the archived original).
. Click *Apply Changes and Restart JMeter*.
. After the restart, right-click a Thread Group: *Add → Sampler → GRPC Request* is available.

**2. Plugins Manager command line**, for Docker images and CI agents, with `cmdrunner-2.3.jar` in `lib` (the version the
Plugins Manager 2.0 script runs) and the `PluginsManagerCMD` scripts in `bin`:

[source,bash]
----
cd apache-jmeter-5.6.3
bin/PluginsManagerCMD.sh install jmeter-grpc-request=2.0.2
bin/PluginsManagerCMD.sh status
----

The `status` command prints the installed plugins with their versions; the list now includes
`jmeter-grpc-request=2.0.2`. Without `=2.0.2` the latest catalogue version is installed. The `install-for-jmx` command
detects plugins from the class names in a saved plan; the catalogue entry lists this plugin's component class as
`vn.zalopay.benchmarkGRPCSampler` (a dot is missing), so installing it explicitly by id, as above, is the reliable
route.

Source: https://jmeter-plugins.org/wiki/PluginsManagerAutomated/[Plugins Manager from Command-Line (JMeter Plugins)]

**3. Manual jar.** Download `jmeter-grpc-request.2.0.2.jar` from the continuation's releases page (the 1.x jars are on
the original repository's releases page), copy it to `lib/ext` and restart JMeter. Remove any older
`+jmeter-grpc-request*.jar+` first: two copies of the same classes in `lib/ext` make the loaded version unpredictable.

[source,bash]
----
cp ~/Downloads/jmeter-grpc-request.2.0.2.jar apache-jmeter-5.6.3/lib/ext/
ls apache-jmeter-5.6.3/lib/ext | grep grpc
----

[source,text]
----
jmeter-grpc-request.2.0.2.jar
----

Source: https://github.com/bakthava/jmeter-grpc-request/releases[bakthava/jmeter-grpc-request releases (GitHub)]

**4. jmeter-maven-plugin `<jmeterExtensions>`.** The plugin copies each listed artifact into `lib/ext` of the JMeter
it provisions. The coordinate `vn.zalopay.benchmark:jmeter-grpc-request` (the `groupId` and `artifactId` in the
plugin's `pom.xml`) is **not published on Maven Central** (checked 2026-10-14), so the jar must first be installed in
the local repository or deployed to an internal repository:

[source,bash]
----
mvn install:install-file -Dfile=jmeter-grpc-request.2.0.2.jar \
  -DgroupId=vn.zalopay.benchmark -DartifactId=jmeter-grpc-request \
  -Dversion=2.0.2 -Dpackaging=jar
----

[source,xml]
----
<plugin>
  <groupId>com.lazerycode.jmeter</groupId>
  <artifactId>jmeter-maven-plugin</artifactId>
  <version>3.8.0</version>
  <configuration>
    <jmeterVersion>5.6.3</jmeterVersion>
    <jmeterExtensions>
      <artifact>vn.zalopay.benchmark:jmeter-grpc-request:2.0.2</artifact>
    </jmeterExtensions>
    <!-- the jar is shaded and already contains its dependencies -->
    <downloadExtensionDependencies>false</downloadExtensionDependencies>
  </configuration>
  <executions>
    <execution>
      <id>configuration</id>
      <goals><goal>configure</goal></goals>
    </execution>
    <execution>
      <id>jmeter-tests</id>
      <goals><goal>jmeter</goal></goals>
    </execution>
    <execution>
      <id>jmeter-check-results</id>
      <goals><goal>results</goal></goals>
    </execution>
  </executions>
</plugin>
----

The repository's `iru-java-springboot-performance-tests` skill, which generates JMeter projects for Spring Boot
services, adds this same `vn.zalopay.benchmark:jmeter-grpc-request` extension for gRPC use cases, so a project
generated by it also needs the artifact to be resolvable as above. The skill notes that the sampler is a third-party
plugin with a slower release cadence than JMeter itself; the status table above is the current detail behind that note.

Source: https://github.com/jmeter-maven-plugin/jmeter-maven-plugin/wiki/Adding-Excluding-libraries-to-from-the-classpath[Adding Excluding libraries to from the classpath (jmeter-maven-plugin wiki)] and https://maven.apache.org/plugins/maven-install-plugin/install-file-mojo.html[install:install-file (Apache Maven Install Plugin)]

**Classpath conflicts.** Because the jar bundles unrelocated grpc-java 1.38.0, Netty and protobuf-java classes, do not
put other grpc-java, Netty or protobuf jars in `lib` or `lib/ext` of the same installation (for example for the JSR223
pattern below, or another plugin that ships them). Whichever copy the class loader finds first wins, and mixed versions
fail with `NoSuchMethodError` or `ClassNotFoundException` at the first call. Use a separate JMeter installation for each
approach.

=== The GRPC Request sampler: every field

Menu path: right-click a Thread Group (or a controller), *Add → Sampler → GRPC Request*. The GUI of release 2.0.2 has
five panels. The README lists ten fields; the table below lists every field in the 2.0.2 GUI
(`GRPCSamplerGui.java`), with the property name saved in the `.jmx` (`GRPCSampler.java`) and the default the GUI fills
in for a new sampler. Every text field accepts JMeter variables and functions.

==== Name and comments

The standard *Name* and *Comments* fields of every sampler. The name becomes the sample label in listeners, the JTL
and the dashboard, so name samplers after the method (`gRPC CreateLoan`).

==== Web Server panel

[cols="2,2,1,5",options="header"]
|===
|Field |Property |Default |Meaning

|Server Name or IP |`GRPCSampler.host` |empty |Host name or IP address of the gRPC server. No scheme and no port. Use `+${__P(host,localhost)}+` to set it from the command line.
|Port Number |`GRPCSampler.port` |empty |The server's gRPC port, `9090` for the Bookshelf service (the port used on the Spring Boot gRPC page). The README mentions `80` or `443` for servers behind a gateway. Host and port are joined as `host:port`.
|SSL/TLS |`GRPCSampler.tls` |off |Off: plaintext HTTP/2 (often called h2c). On: TLS with HTTP/2 negotiated through ALPN. It must match the server; a TLS client against a plaintext port (or the reverse) fails with `UNAVAILABLE`.
|Disable SSL/TLS Cert Verification |`GRPCSampler.tlsDisableVerification` |off |Trusts any server certificate (an insecure trust manager). For self-signed certificates in a local environment only. When ticked, the *CA Certificate File* below is ignored.
|===

==== Mutual TLS (mTLS) - Optional panel (2.0.0 and later)

These fields were added in 2.0.0 and are not described in the README; the names and behaviour below come from the 2.0.2
GUI and `ChannelFactory.java`. They only take effect when *SSL/TLS* is ticked.

[cols="2,2,1,5",options="header"]
|===
|Field |Property |Default |Meaning

|Client Certificate File |`GRPCSampler.clientCertFile` |empty |Path to the client certificate chain presented to the server, with a *Browse...* button. Used only if the client key is also set.
|Client Key File |`GRPCSampler.clientKeyFile` |empty |Path to the client's private key. Both files are handed to Netty's `SslContextBuilder.keyManager(File, File)`, whose documentation asks for an X.509 certificate chain in PEM format and a PKCS#8 private key in PEM format.
|CA Certificate File (Optional) |`GRPCSampler.caCertFile` |empty |A PEM file with the CA certificates used to verify the server, for a private CA. If empty, the JVM's default trust store is used. Ignored when *Disable SSL/TLS Cert Verification* is ticked.
|===

The certificate files are read once per thread when the channel is built. Keep test certificates out of the repository
(or use throw-away ones issued only for the test environment) and point the fields at them with properties, for example
`+${__P(grpc_client_cert)}+`.

Source: https://netty.io/4.1/api/io/netty/handler/ssl/SslContextBuilder.html[SslContextBuilder (Netty API)] and https://github.com/bakthava/jmeter-grpc-request/releases/tag/v2.0.0[v2.0.0 release notes (GitHub)]

[[request-json]]
=== The request as JSON

The JSON in the request panel is parsed with protobuf's `JsonFormat` into a message of the method's input type. The
rules are those of the proto3 JSON mapping, plus two behaviours of the plugin:

* **Field names**: both the `.proto` name (`book_id`) and the JSON name (`bookId`, lowerCamelCase) are accepted in the
  request.
* **Unknown fields are ignored**, not rejected: the parser is created with `ignoringUnknownFields()`. A typo such as
  `"bookid"` is dropped silently and the server receives an empty `book_id`. Check the *Request* tab of View Results
  Tree, which shows the message that was actually sent, printed back as JSON with all default values.
* **64-bit integers** (`int64`, `uint64`, `fixed64`) are written as JSON strings in proto3 JSON, though numbers are
  accepted on input. **Enums** are written by name (`"LOAN_STATUS_ACTIVE"`). **`google.protobuf.Timestamp`** is an RFC
  3339 string (`"2026-10-28T00:00:00Z"`); `Duration` a string such as `"1.5s"`; `bytes` base64.
* **The response** is printed with `preservingProtoFieldNames()` and `includingDefaultValueFields()`: it uses the
  `.proto` names (`loan_id`, not `loanId`) and shows fields that hold default values. Write JSONPath expressions
  against those names.
* **Variables inside JSON strings** need the quotes around them: `+"book_id": "${bookId}"+`. A numeric field can take
  an unquoted variable (`+"days": ${days}+`), but if the variable is missing the literal `+${days}+` makes the JSON
  invalid and the sample fails before the call (see the result mapping below).

Source: https://protobuf.dev/programming-guides/json/[ProtoJSON Format (Protocol Buffers)]

[[metadata]]
=== Metadata, including a bearer token

The *Metadata* field accepts two formats:

* `key1:value1,key2:value2`: entries separated by commas, key and value separated by the **first** colon, and each
  value **URL-decoded** as UTF-8. A value that contains a comma, or a `pass:c[+]` or `%` that must stay literal, has to be
  URL-encoded (`%2C`, `%2B`, `%25`).
* A JSON object, recognised when the field starts with `+{+` and ends with `+}+`: `+{"authorization":"Bearer ${token}"}+`.
  The README says nested JSON values are sent as a JSON string, but in the 2.0.2 source any value that is not a JSON
  string (a number, a boolean or a nested object) is rejected with "Metadata entry must be valid JSON String or in
  key1:value1,key2:value2 format", so quote every value.

The JSON form is the safer choice for tokens, because no URL decoding is applied to it. For the Bookshelf service the
JWT obtained by the HTTP login goes into `+{"authorization":"Bearer ${token}"}+`. The metadata keys are sent through
grpc-java's ASCII marshaller, so binary metadata (keys ending in `-bin`) cannot be sent with this plugin. The metadata
of each sample is shown on the *Request* tab of View Results Tree as request headers.

Source: https://github.com/bakthava/jmeter-grpc-request#configurations[Configurations (jmeter-grpc-request README)] and https://grpc.io/docs/guides/metadata/[Metadata (gRPC)]

[[results]]
=== What the sampler records: results and the error-code mapping

The README says the plugin "counts the failed request in the report" but does not document the values. The mapping
below is what `GRPCSampler.java` writes in 2.0.2:

[cols="3,1,1,3,3",options="header"]
|===
|Outcome |Success |Response code |Response message |Response data

|The call returned status `OK` |true |`200` |`success` (with a leading space) |The response message printed as JSON (proto field names, default values included).
|The call ended with any other gRPC status (`INVALID_ARGUMENT`, `NOT_FOUND`, `DEADLINE_EXCEEDED`, `UNAVAILABLE`, `UNAUTHENTICATED` and the others) |false |`500` (with a leading space) |The numeric code and the name, for example `4 DEADLINE_EXCEEDED` or `16 UNAUTHENTICATED` (each preceded by a space) |The status description sent by the server (often empty).
|Another exception during the call |false |`500` (with a leading space) |The exception text |The exception text.
|The request could not be prepared: proto compilation error, unknown method, invalid request JSON, malformed metadata, missing proto folder |false |`400` (with a leading space) |`+GRPCSampler parsing exception: An unknown exception occurred before the GRPC request was initiated...+` |The stack trace. The sample is not timed (its elapsed time is close to zero).
|===

So the "HTTP-like" codes are synthetic: `200` means gRPC `OK`, `500` means "the server or transport answered with an
error status", `400` means "the plan is wrong". The real gRPC code is in the **response message**. Three consequences:

* Assert success with a Response Assertion on the response code *Equals* `200`. The sampler already marks non-OK calls
  as failed, so the assertion adds a clear failure message rather than detection.
* To count a specific gRPC failure (for example to tolerate `ALREADY_EXISTS` from a seeding step), test the **response
  message** with *Substring* `ALREADY_EXISTS`, not the code: the code is `500` with a leading space for every failure, and that space
  makes an *Equals* `500` fail.
* In the JTL and in the dashboard's error tables, failures are grouped by response code and message, so the gRPC
  status names appear there directly; a run with expired tokens shows a row with `16 UNAUTHENTICATED`.

Source: https://github.com/bakthava/jmeter-grpc-request[GRPCSampler.java at v2.0.2 (jmeter-grpc-request)] and https://grpc.io/docs/guides/status-codes/[Status Codes (gRPC)]

**A failed call closes the thread's channel.** In the 2.0.2 source (`ClientCaller.call`), any non-OK status shuts the
channel down, and the sampler does not build a new one while the thread lives. Later calls from that thread then fail
with `UNAVAILABLE` (the channel has been shut down) until the thread ends. A single `NOT_FOUND` can therefore turn into a
long run of `UNAVAILABLE` errors in a closed-model test. The README does not document this; verify it in a smoke run
with a deliberately unknown id or a 1 ms deadline, and design the plan so that expected business errors do not occur
in the load mix. Under the Open Model Thread Group every arrival is a new thread with a new channel, so the effect is
limited to one iteration.

=== Cost on the load generator

The sampler is heavier than an HTTP Request in four ways:

* **Start-up CPU.** `protoc` runs once per sampler per thread (100 runs for 50 threads and two gRPC samplers), plus
  descriptor parsing. During a 60 s ramp-up that is under two runs a second, which a modern machine absorbs; under an
  Open Model Thread Group, where each arrival is a new thread, it is two runs **per arrival** (see the arrival-rate
  profile below). A <<descriptor-set,pre-built descriptor set>> removes the `protoc` runs entirely.
* **Connections and memory.** One Netty channel per sampler per thread, each with its own HTTP/2 connection and
  buffers. Count connections as `threads × gRPC samplers` when sizing the generator and the server's connection limits.
* **Per-call work.** JSON parsing into a dynamic message, protobuf encoding, decoding and printing the response back to
  JSON. For small messages this is a fraction of a millisecond; for multi-megabyte responses it dominates, and the
  response text is kept in each sample result.
* **Heap.** The usual rules apply: no View Results Tree in load runs, CSV JTL output, few assertions. The 32 MB jar adds a
  little metaspace. See the best practices of the user manual.

Source: https://jmeter.apache.org/usermanual/best-practices.html[Best Practices (User Manual)]

[[descriptor-set]]
=== Pre-compiled descriptor sets

Since 1.2.6 the *Proto Root Directory* field may point at a `FileDescriptorSet` file whose name ends in `.bin`. The
sampler then reads it instead of running `protoc`. Generate it once, with `--include_imports` so that imported files
(including well-known types) are inside:

[source,bash]
----
protoc --proto_path=protos --include_imports \
  --descriptor_set_out=descriptors/bookshelf.bin \
  protos/bookshelf/v1/bookshelf.proto
ls -l descriptors/bookshelf.bin
----

[source,text]
----
-rw-r--r--  1 tester  staff  7342 Oct 14 10:00 descriptors/bookshelf.bin
----

In the 2.0.2 source a `.bin` path is used as given, **without** the "relative to the `.jmx` folder" resolution applied
to folders, so pass an absolute path, for example `+${__P(proto_dir,/opt/bookshelf-perf/descriptors/bookshelf.bin)}+`.
The descriptor set must be rebuilt whenever the `.proto` changes, or the test silently runs against an old contract
(new fields are ignored, removed methods fail with `UNIMPLEMENTED`). Build it in the same CI step that builds the
service.

Source: https://github.com/zalopay-oss/jmeter-grpc-request/releases/tag/v1.2.6[v1.2.6 release notes, "support for bin descriptors" (GitHub)] and https://protobuf.dev/programming-guides/techniques/#self-description[Self-describing Messages (Protocol Buffers)]

== Worked example: the Bookshelf LoanService

The companion plan `bookshelf-grpc.jmx` simulates borrowers who log in once over HTTP and then repeatedly create a loan
and read it back over gRPC. It reuses the conventions of the section: run properties `threads`, `rampup`, `duration`,
`host` and `port` (HTTP), plus `grpc_port`, `grpc_deadline_ms` and `proto_dir` for this plan; data from `users.csv`;
the token in `token`, the book in `bookId` and the new loan in `loanId`.

=== The contract: bookshelf.proto

[source,protobuf]
----
syntax = "proto3";

package bookshelf.v1;

import "google/protobuf/timestamp.proto";

option java_multiple_files = true;
option java_package = "com.example.bookshelf.grpc.v1";

// Loans of books to registered users. Both methods are unary.
service LoanService {
  // Creates a loan for the caller identified by the bearer token in the metadata.
  rpc CreateLoan(CreateLoanRequest) returns (Loan);
  // Returns an existing loan.
  rpc GetLoan(GetLoanRequest) returns (Loan);
}

message CreateLoanRequest {
  string book_id = 1;
  string username = 2;
  int32 days = 3;
}

message GetLoanRequest {
  string loan_id = 1;
}

enum LoanStatus {
  LOAN_STATUS_UNSPECIFIED = 0;
  LOAN_STATUS_ACTIVE = 1;
  LOAN_STATUS_RETURNED = 2;
}

message Loan {
  string loan_id = 1;
  string book_id = 2;
  string username = 3;
  LoanStatus status = 4;
  google.protobuf.Timestamp due_date = 5;
}
----

A successful `CreateLoan` is printed by the sampler as:

[source,json]
----
{
  "loan_id": "c0a8012e-5f1b-4f7e-9d0b-2b8f3c6e1a47",
  "book_id": "b-1042",
  "username": "reader01",
  "status": "LOAN_STATUS_ACTIVE",
  "due_date": "2026-10-28T10:00:00Z"
}
----

How a Spring Boot service implements this contract, including mapping exceptions to the status codes above, is covered
by xref:backend/springboot/grpc-apis.adoc[gRPC APIs with Spring Boot]; keeping the `.proto` as the single source for
both the service and the test is the contract-first approach of
xref:backend/springboot/api-first-rest-and-grpc.adoc[API-First Development: REST and gRPC].

Source: https://protobuf.dev/programming-guides/proto3/[Language Guide (proto 3) (Protocol Buffers)]

Two design choices protect the run from the channel behaviour described in <<results>>:

* The `GetLoan` request uses the loan just created by the same thread, so a correlation failure is the only way to
  send an unknown id. If the extractor falls back to `LOAN_NOT_FOUND`, the `GetLoan` call fails with `NOT_FOUND` and the
  thread's `GetLoan` channel closes. To avoid that cascade, wrap `gRPC GetLoan` in an *If Controller* with the
  condition `+${__groovy(vars.get("loanId") != "LOAN_NOT_FOUND")}+`, see
  xref:backend/jmeter/logic-controllers-and-transactions.adoc[Logic Controllers & Transactions].
* The token is obtained once per thread, so its lifetime must exceed the run (11 minutes for the load profile).
  Otherwise the calls fail with `UNAUTHENTICATED` once it expires, and each failure closes the channel.

=== Load profiles with worked numbers

**Closed load profile: 50 threads, 60 s ramp-up, 10-minute hold.** One iteration takes the two think times plus the two
response times. With `CreateLoan` at about 20 ms and `GetLoan` at about 10 ms on a local service:

* iteration time ≈ 3 + 0.020 + 3 + 0.010 = 6.03 s;
* by Little's Law each thread completes 1 / 6.03 ≈ 0.166 iterations per second, so 50 threads give
  50 / 6.03 ≈ 8.3 loans per second, that is ≈ 16.6 gRPC calls per second at full load;
* the ramp-up starts 50 / 60 ≈ 0.83 threads per second; each new thread compiles the protos twice (two samplers), so
  ≈ 1.7 `protoc` runs per second during the first minute and none afterwards;
* the generator holds up to 100 HTTP/2 connections to port 9090 (two samplers × 50 threads) plus 50 HTTP connections
  for the logins;
* the scheduler duration 660 s covers 60 s of ramp-up and a 10-minute hold.

Because think time dominates, a slower service lowers the throughput only slightly: at 200 ms per call the iteration
takes 6.4 s and the rate drops to 7.8 loans per second. That is the closed-model effect explained on
xref:backend/jmeter/performance-testing-fundamentals.adoc[Performance Testing Fundamentals]; for a fixed arrival rate
use the next profile.

**Arrival-rate profile: 10 loans per second.** The section's arrival-rate profiles use the Open Model Thread Group.
With this plugin that element has a specific cost: every arrival is a new thread, so every arrival compiles the protos
(once per gRPC sampler), opens new connections and logs in. At 10 arrivals per second that is 20 `protoc` runs and 20
new HTTP/2 connections per second, and the first call of each arrival includes the connection set-up in its measured
time. Two ways to keep the target rate without that cost:

* **A fixed pool paced by a Precise Throughput Timer** (recommended for gRPC). Keep the Thread Group above with
  `threads=100`, add a *Flow Control Action* dummy sampler (pause 0) as the first child of the loop, and under it a
  *Precise Throughput Timer* with target throughput `10` per `1` second and test duration `660`. Each thread logs in
  once and keeps its channels. The pool must be larger than the rate times the iteration time: 10 × 6.03 ≈ 61 threads
  at nominal latency, and 10 × 8 = 80 if both calls degrade to 1 s; 100 leaves head-room. If the pool is too small the
  timer cannot reach the rate and the shortfall is visible in the throughput graph. The fields and placement are
  described on xref:backend/jmeter/open-model-and-throughput-control.adoc[Open Model & Throughput Control].
* **An Open Model Thread Group with a descriptor set**, when independent short-lived clients are what the service
  really sees: point *Proto Root Directory* at an absolute `bookshelf.bin` to remove the `protoc` runs, and accept that
  every arrival pays the connection set-up (and the login). The schedule
  `+rate(0) random_arrivals(1 min) rate(10/sec) random_arrivals(10 min) pause(30 sec)+` ramps to 10 arrivals per
  second in a minute and holds it for ten.

The Concurrency and Arrivals thread groups and the Throughput Shaping Timer from the Custom Thread Groups plugin are
alternatives for stepped and shaped profiles, see
xref:backend/jmeter/custom-thread-groups-and-load-shaping.adoc[Custom Thread Groups & Load Shaping].

Source: https://jmeter.apache.org/usermanual/component_reference.html#Precise_Throughput_Timer[Precise Throughput Timer] and https://jmeter.apache.org/usermanual/component_reference.html#Open_Model_Thread_Group[Open Model Thread Group (Component Reference)]

=== Distributed runs

In a distributed test every server runs the **whole** plan, so the load is threads × servers, and data files are not
sent from the client: they must exist on every node. For a gRPC plan this list grows to:

* the **same plugin jar** (same version) in `lib/ext` of every JMeter server, installed with the same command line as
  above;
* the **protos** (or the descriptor set) and the CSV files at the same path on every node;
* the same JMeter and Java versions everywhere.

Use absolute paths passed as global properties, so every server resolves the same location regardless of how the
server process was started:

[source,bash]
----
jmeter -n -t bookshelf-grpc.jmx -R gen1.internal,gen2.internal -l results/grpc-dist.jtl \
  -Gthreads=25 -Grampup=60 -Gduration=660 -Ghost=bookshelf.internal -Ggrpc_port=9090 \
  -Gproto_dir=/opt/bookshelf-perf/descriptors/bookshelf.bin
----

Two servers with `threads=25` produce the same 50 threads in total as the single-machine run. The setup of the
servers (RMI ports and the RMI SSL keystore) is covered later in this guide, in the distributed testing page.

Source: https://jmeter.apache.org/usermanual/remote-test.html[Remote Testing (User Manual)]

== Limits of the plugin

* **Unary calls only.** No server, client or bidirectional streaming; a streaming method cannot be load-tested with this
  sampler.
* **No grpc-web.** It is listed as an open to-do in the README; gRPC-Web endpoints (HTTP/1.1 through a proxy) cannot be
  called.
* **No server reflection.** The plugin needs the `.proto` files or a descriptor set; it cannot discover methods from a
  server with reflection enabled.
* **No binary metadata** (`-bin` keys), and metadata values must be strings.
* **No channel tuning** beyond the two size limits and the shutdown wait: no keep-alive, compression, load-balancing
  policy or connection sharing between threads. Each sampler copy is one client with one connection.
* **Synthetic response codes.** `200`, `500` and `400` (the last two with a leading space) stand for OK, gRPC error and plan error; the gRPC status is in
  the response message, and only the status description (not the error details) is kept.
* **A failed call closes the thread's channel** in 2.0.2, as described above.
* **Old bundled libraries** (grpc-java 1.38.0) and a single-maintainer continuation.

Source: https://github.com/bakthava/jmeter-grpc-request#features[Features (jmeter-grpc-request README)]

== Alternatives

=== jmeter-grpc-plugin: generated code

`zalopay-oss/jmeter-grpc-plugin` (the "GRPC Client Sampler", class package `vn.zalopay.jmeter.grpc`) takes the opposite
approach: you generate Java classes from your protos, package them in a jar in `lib/ext`, build the plugin from source
(`mvn clean install`, then copy `target/jmeter-grpc-client-sampler.jar` to `lib/ext`) and supply the request as Java
code. The sampler is added with *Add → Sampler → GRPC Client Sampler*. Its documented fields are `hostname`, `port`,
`useSsl`, `keepAliveTime`, `keepAliveTimeout`, `keepAliveWithoutCalls`, `maxInboundMessageSize`, `packageN`, `service`,
`method`, `request` (the request class name), `timeout` (ms), `metaData` (a JSON map) and `requestBuilderCode`: a class
implementing the plugin's `MessageBuilder` interface whose `buildMessage(JMeterContext ctx)` returns the message,
reading JMeter variables from `ctx.getVariables()`. It offers keep-alive settings that the JSON plugin lacks, but it
needs a code-generation step for every contract change, has had a single release (0.1.0, March 2020) and is not in the
Plugins Manager catalogue. Its README points to `jmeter-grpc-request` for working with plain JSON.

Source: https://github.com/zalopay-oss/jmeter-grpc-plugin[zalopay-oss/jmeter-grpc-plugin README and docs/description.md (GitHub)]

=== JSR223 Groovy with grpc-java stubs (unofficial pattern)

**This is an unofficial pattern, not a JMeter or plugin feature**: JMeter only provides the JSR223 Sampler; the gRPC
part is ordinary grpc-java client code that you maintain. It is useful when a contract needs something the plugin
cannot do (a client-side load-balancing policy, keep-alive settings, a newer grpc-java), and only for unary or
server-streaming calls whose result fits one sample.

Prerequisites: generate the Java classes for `bookshelf.proto` with the protobuf and grpc-java Maven or Gradle plugins,
package them as `bookshelf-grpc-stubs.jar`, and copy it with its runtime dependencies (`grpc-netty-shaded`,
`grpc-protobuf`, `grpc-stub`, `protobuf-java` and their transitive dependencies, in matching versions) into `lib` of a
JMeter installation **without** the `jmeter-grpc-request` plugin (see the classpath warning above). Then, *Add →
Sampler → JSR223 Sampler*, language `groovy`, *Cache compiled script if available* ticked, script:

[source,groovy]
----
import com.example.bookshelf.grpc.v1.CreateLoanRequest
import com.example.bookshelf.grpc.v1.LoanServiceGrpc
import io.grpc.ManagedChannel
import io.grpc.ManagedChannelBuilder
import io.grpc.Metadata
import io.grpc.StatusRuntimeException
import io.grpc.stub.MetadataUtils
import java.util.concurrent.TimeUnit

// One channel per thread, created on the first iteration and reused afterwards.
ManagedChannel channel = vars.getObject('grpcChannel') as ManagedChannel
if (channel == null) {
    channel = ManagedChannelBuilder
            .forAddress(props.getProperty('host', 'localhost'), props.getProperty('grpc_port', '9090') as int)
            .usePlaintext()
            .build()
    vars.putObject('grpcChannel', channel)
}

Metadata headers = new Metadata()
headers.put(Metadata.Key.of('authorization', Metadata.ASCII_STRING_MARSHALLER), 'Bearer ' + vars.get('token'))

def stub = LoanServiceGrpc.newBlockingStub(channel)
        .withInterceptors(MetadataUtils.newAttachHeadersInterceptor(headers))
        .withDeadlineAfter(props.getProperty('grpc_deadline_ms', '2000') as long, TimeUnit.MILLISECONDS)

def request = CreateLoanRequest.newBuilder()
        .setBookId(vars.get('bookId'))
        .setUsername(vars.get('username'))
        .setDays(14)
        .build()

try {
    def loan = stub.createLoan(request)
    vars.put('loanId', loan.getLoanId())
    SampleResult.setResponseCodeOK()
    SampleResult.setResponseMessage('OK')
    SampleResult.setResponseData(loan.toString(), 'UTF-8')
} catch (StatusRuntimeException e) {
    SampleResult.setSuccessful(false)
    SampleResult.setResponseCode(String.valueOf(e.status.code.value()))
    SampleResult.setResponseMessage(e.status.code.name())
    SampleResult.setResponseData(String.valueOf(e.status.description), 'UTF-8')
}
----

The JSR223 Sampler times the whole script, so the first iteration of each thread includes building the channel. The
script takes all inputs from `vars` and `props` instead of `+${...}+` references, which keeps the compiled script
cacheable (see xref:backend/jmeter/scripting-with-jsr223-and-groovy.adoc[Scripting with JSR223 & Groovy]). Unlike the
plugin, this script keeps the channel after an error and puts the real gRPC code in the response code. Channels are
not shut down explicitly; they close when the JMeter process exits, which is acceptable for a test run but would
leak connections in a long-lived process.

Source: https://jmeter.apache.org/usermanual/component_reference.html#JSR223_Sampler[JSR223 Sampler (Component Reference)] and https://grpc.io/docs/languages/java/basics/[Basics tutorial: Java (gRPC)]

Dedicated gRPC benchmarking tools exist, such as `ghz`, the gRPC module of k6 and gRPC plugins for Gatling. They

== Pitfalls checklist

* **Everything fails with `400` and a parsing exception**: the proto root is wrong, a `.proto` under it does not
  compile, an import needs a *Library Directory*, the full method is misspelled, or the request JSON is invalid (often
  an unquoted empty variable). The response data holds the stack trace; `protoc` messages are in `jmeter.log`.
* **`UNIMPLEMENTED`**: the server does not know the method. The package, service or method name differs from the
  server's contract, or the test uses an older or newer `.proto` than the deployed service.
* **`UNAVAILABLE` on every call**: wrong port, TLS on one side only, the server is down, or an earlier failure closed
  this thread's channel.
* **`DEADLINE_EXCEEDED` under load but not in the smoke run**: the deadline is the timeout. Keep it at the service's
  real client deadline rather than the GUI default of 1000 ms, and report deadline failures as errors, not as slow
  successes.
* **`UNAUTHENTICATED`**: the metadata does not carry the token (check the *Request* tab), the token expired during a
  long run, or the key is not `authorization`.
* **Fields silently empty on the server**: a misspelled JSON field name, ignored by the plugin's parser.
* **Unexpectedly even or uneven load across replicas**: each sampler copy has its own connection. With few threads
  behind a layer-4 balancer, some replicas get no traffic.
* **The plugin worked in the GUI but not on a load generator**: the jar, the protos or the CSV files are missing there,
  or a relative descriptor-set path was used.

== What changed: from the books to 5.6.3 and 6.0

* **The books** (JMeter 2.11 to 3.0, 2014 to 2017) do not cover gRPC: gRPC 1.0 was released in 2016 and the two
  plugins covered here appeared in 2020. Their methodology for think time, data and correlation applies unchanged.
* **Plugin history:** 1.0.0 (September 2020), 1.1.x (metadata authentication, method listing, failure counting, TLS
  ALPN fixes), 1.2.0 (request skeleton from the proto), 1.2.6 (December 2022, descriptor sets, Apple Silicon support);
  original repository archived in April 2024; 2.0.0 to 2.0.2 in April 2026 (mTLS, CVE fixes, Java 21).
* **JMeter 5.6.3:** the plugin is built against the JMeter 5.5 API (its `pom.xml`), and its catalogue entry declares
  only a dependency on `jmeter-core`, without an upper version bound. This page uses it on 5.6.3; run the GUI smoke
  test after any JMeter upgrade.
* **JMeter 6.0 (planned):** still no gRPC sampler in `changes.xml`, Java 17 or later required, and Groovy 5 for JSR223
  scripts. Whether the 2.0.x plugin works with 6.0 cannot be verified until 6.0 is released; test it before upgrading.
