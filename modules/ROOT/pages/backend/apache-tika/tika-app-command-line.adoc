the `--help` output and the source of *4.1.0*. Run `--help` on your own version before you copy a command into a
script, and pin the tika-app version in any script you keep.

== What tika-app is

`tika-app` is a Maven module and a release artifact. Its main class, `org.apache.tika.cli.TikaCLI`, wraps the same
components the Java pages of this section use: a `TikaLoader` built from a configuration file, an `AutoDetectParser`, a
`ParseContext` and a content handler chosen by an option. Since Tika 4.0 it also wraps `PipesForkParser` (fork mode) and
the Tika Pipes `AsyncProcessor` (pipes mode). In short, it is a convenient way to see what Tika will do with a file before
you write code, to script one-off extractions and, in pipes mode, to run a batch.

It runs in three modes. The official page names them standard, GUI and Tika Pipes. Fork mode is an option of the
standard mode.

[cols="1,3,3",options="header"]
|===
|Mode |What it does |How you get it

|Standard |Parses one or more files, URLs or standard input in the CLI JVM and writes the result to standard output. |A file, a URL, `-` or nothing on standard input, with output options.
|Standard + fork |Same output, but the parse runs in a forked JVM through `PipesForkParser`, so a crash, an `OutOfMemoryError` or a hang cannot take the CLI down. |Add `-f` or `--fork`.
|GUI |A Swing window. Drop a file on it and look at its metadata, text, XHTML and recursive JSON. |`-g` or `--gui`, or no arguments and nothing on standard input.
|Tika Pipes |Processes every file under a directory (or a file list, or any configured pipes iterator) in forked JVMs and writes one output file per input. |Two directories, `-i` / `-o`, `-z` / `-Z`, `--fileList`, `-a`, or a single `.json` pipes configuration.
|===

The mode is picked from the arguments before any option is applied. The following flow is how `TikaCLI.main` in 4.1.0
decides (help first, then the pipes test, then the standard per-argument loop).

[mermaid]
....
flowchart TD
    A[java -jar tika-app.jar args] --> B{-? or --help anywhere?}
    B -- yes --> H[print usage and exit]
    B -- no --> C{pipes trigger?}
    C -- "two dirs, a single .json, -i, -o, -z, -Z, --extract, --fileList, -a" --> P[Tika Pipes mode: banner on stderr, AsyncProcessor, forked JVMs]
    C -- no --> D{any arguments?}
    D -- none --> E{data on stdin within 0.1 s?}
    E -- yes --> S[standard mode on stdin]
    E -- no --> G[GUI]
    D -- yes --> L[standard mode: options and files processed left to right]
    L --> F{-f or --fork set?}
    F -- yes --> K[parse in a forked JVM through PipesForkParser]
    F -- no --> I[parse in the CLI JVM]
....

Source: https://tika.apache.org/docs/4.1.x/using-tika/cli/index.html[Apache Tika 4.1.x, Tika Command Line Interface]
and the 4.1.0 source of https://github.com/apache/tika/blob/4.1.0/tika-app/src/main/java/org/apache/tika/cli/TikaCLI.java[`TikaCLI.java`].

== Installing the zip distribution

Tika 4.x ships `tika-app` as a zip, not as the single fat jar of the 1.x to 3.x lines. The jar inside the zip is a thin
launcher: its manifest has a `Class-Path` that lists the jars in the adjacent `lib/` directory, and pipes mode loads its
fetcher and emitter plugins from the adjacent `plugins/` directory. The zip has no top-level directory, so unzip it into
one.

[source,bash]
----
curl -O https://archive.apache.org/dist/tika/4.1.0/tika-app-4.1.0.zip
curl -O https://archive.apache.org/dist/tika/4.1.0/tika-app-4.1.0.zip.sha512
shasum -a 512 tika-app-4.1.0.zip    # compare with the content of the .sha512 file
cat tika-app-4.1.0.zip.sha512

unzip -q -d tika-app-4.1.0 tika-app-4.1.0.zip
ls tika-app-4.1.0
----

Output (the two checksum lines were identical and are shortened here):

[source,text]
----
e8ffd4b85f08b2c9...25487c8745d  tika-app-4.1.0.zip
e8ffd4b85f08b2c9...25487c8745d
LICENSE  NOTICE  lib  plugins  tika-app-4.1.0.jar
----

What is inside (4.1.0):

[cols="2,5",options="header"]
|===
|Entry |Content

|`tika-app-4.1.0.jar` |`TikaCLI`, the GUI, the default single-file configuration and a `log4j2.xml`. Its manifest declares `Java-Version: 17` and a `Class-Path` of `+lib/...+` entries.
|`lib/` |110 jars, about 57 MB: `tika-core`, every module of the standard parser package, `tika-langdetect-charsoup`, `tika-vlm`, `tika-inference`, `tika-async-cli`, the pipes core, POI, PDFBox, Bouncy Castle and the rest.
|`plugins/` |The file-system pipes plugin (`tika-pipes-file-system-4.1.0.zip` and its unpacked directory), which pipes mode uses to read the input directory and write the output directory.
|`LICENSE`, `NOTICE` |The Apache license and notices.
|===

The `Class-Path` entries are resolved relative to the jar, not to the current directory, so `java -jar
/opt/tika-app-4.1.0/tika-app-4.1.0.jar` works from any working directory. All the examples on this page were run that way
from a directory that held the sample files. The jar on its own does not work. Copied out of the distribution it fails
before reading any argument:

[source,bash]
----
cp tika-app-4.1.0/tika-app-4.1.0.jar /some/other/dir/
java -jar /some/other/dir/tika-app-4.1.0.jar --version
----

Output:

[source,text]
----
Error: Unable to initialize main class org.apache.tika.cli.TikaCLI
Caused by: java.lang.NoClassDefFoundError: org/apache/tika/mime/MimeTypeException
----

This is the `NoClassDefFoundError` the 4.x FAQ and the CLI page describe. If pipes mode is started from an incomplete
distribution, `TikaCLI` catches the error and prints an explanation (download the zip, run the jar from inside it); the
standard mode fails in the JVM launcher, as above. The `tika-app` artifact on Maven Central is the same thin jar plus a
POM with the dependencies, which is how the earlier pages of this section ran `TikaCLI` on a Maven-built classpath.

A shell alias keeps the commands short. The rest of the page writes `tika` for it:

[source,bash]
----
alias tika='java -jar /opt/tika-app-4.1.0/tika-app-4.1.0.jar'
tika --version
----

Output:

[source,text]
----
Apache Tika 4.1.0
----

The JVM options go before `-jar`, as for any Java program: `+java -Xmx2g -jar tika-app-4.1.0.jar ...+` sets the heap of
the CLI JVM in standard mode. The forked JVMs of fork mode and pipes mode get their own options through
`--fork-jvm-args` and `--Xmx`, described below.

Source: https://tika.apache.org/download.html[Apache Tika, Download],
https://tika.apache.org/docs/4.1.x/using-tika/cli/index.html[Apache Tika 4.1.x, Tika Command Line Interface, Installation]
and https://tika.apache.org/docs/4.1.x/faq.html[Apache Tika 4.1.x, FAQ].

=== Logging and the convenience-defaults banner

Log lines go to standard error through Log4j 2, so standard output stays clean for redirection and pipes. The bundled
`log4j2.xml` logs at `INFO`, and every standard-mode run without `--config` logs this notice first:

[source,text]
----
INFO  [main] 22:53:16,719 org.apache.tika.cli.TikaCLI As a convenience, TikaCLI has turned on several non-default features
as specified in tika-app/src/main/resources/tika-config-default-single-file.json.
See: TIKA-2374, TIKA-4017, TIKA-4354 and TIKA-4472).
This is not the default behavior in Tika generally or in tika-server.
----

The notice is accurate and worth reading. Without `--config`, tika-app loads a bundled configuration that turns on
features the library and tika-server leave off. The file in the 4.1.0 jar is:

[source,json]
----
{
  "parsers": [
    { "default-parser": {} },
    { "pdf-parser": {
        "extractActions": true,
        "extractInlineImages": true,
        "accessCheckMode": "ALLOW_EXTRACTION_FOR_ACCESSIBILITY",
        "extractIncrementalUpdateInfo": true,
        "parseIncrementalUpdates": true } },
    { "ooxml-parser": {
        "includeDeletedContent": true,
        "includeMoveFromContent": true,
        "extractMacros": true } },
    { "office-parser": { "extractMacros": true } }
  ]
}
----

So tika-app shows PDF actions, inline images and incremental updates, and Word's deleted and moved text and macros, by
default. That is useful when you are inspecting a file, and it is the reason the same file can give a little more output
in tika-app than in your own `AutoDetectParser` code. Pass `--config=` with your production configuration when you want
to see exactly what your service will see. The pipes mode template has the same parser settings (see
<<pipes-defaults,Defaults of pipes mode>>).

To keep only warnings and errors, point Log4j at your own file:

[source,xml]
----
<?xml version="1.0" encoding="UTF-8"?>
<!-- quiet-log4j2.xml: only WARN and above, on standard error -->
<Configuration status="WARN">
  <Appenders>
    <Console name="stderr" target="SYSTEM_ERR">
      <PatternLayout pattern="%-5p %c{1} %m%n"/>
    </Console>
  </Appenders>
  <Loggers>
    <Root level="warn"><AppenderRef ref="stderr"/></Root>
  </Loggers>
</Configuration>
----

[source,bash]
----
java -Dlog4j.configurationFile=quiet-log4j2.xml -jar tika-app-4.1.0.jar -t catalogue.pdf
----

Output (standard error was empty):

[source,text]
----
Bookshelf spring catalogue
Forty titles from independent publishers.
----

`-v` / `--verbose` does the opposite and raises the root logger to `DEBUG` (a `-j -v` run on `manuscript.docx` printed
43 `DEBUG` lines on standard error).

Source: https://tika.apache.org/docs/4.1.x/advanced/integration-testing/tika-app.html[Apache Tika 4.1.x, Tika-App Integration Testing]
(its known issue "INFO message on every default-config command") and https://logging.apache.org/log4j/2.x/manual/configuration.html[Apache Log4j 2, Configuration].

Three things in this text need reading with care, and the official page says so too:

* *`-T` has two meanings.* In standard mode it is `--text-main`. In pipes mode it is `--timeoutMillis`. `-c` and `-p`
  exist only in pipes mode; in standard mode the configuration is `--config=<file>`.
* *`-z` and `--extract` are listed with the standard options but switch to pipes mode.* Their description ("into
  current directory") is the 3.x wording; in 4.1.0 they always run through Tika Pipes (see <<unpacking,Unpacking
  attachments>>).
* *The pipes section is a summary.* The pipes-mode options are parsed by `TikaAsyncCLI` with Apache Commons CLI, so
  `--handler t` and `--handler=t` both work, and `--fileList` takes a value.

== Standard mode

In standard mode `TikaCLI` processes its arguments left to right. An option changes the state (the output type, the
configuration, the password), and a file name, a URL or `-` parses that input with the current state and writes the
result to standard output. Several inputs in one command are parsed one after the other and their outputs are
concatenated.

The order matters in two ways. An option placed after the file name does not apply to it, and `--config=` must come
before the first input (and before `-g` or `-f`, as the help says), because the configuration is loaded when the first
input is parsed:

[source,bash]
----
tika -d manuscript.docx -t novel.epub   # -d applies to the first file, -t to the second
tika novel.epub -t                      # -t comes too late: the default Markdown is printed
----

Output:

[source,text]
----
application/vnd.openxmlformats-officedocument.wordprocessingml.document
Chapter one
It begins at dusk.
# Chapter one

It begins at dusk.
----

Long options take two dashes and short options are one letter. In 4.1.0 an unknown option fails fast with exit status 1
and a hint, instead of being taken as a URL:

[source,bash]
----
tika -input catalogue.pdf
----

Output (standard error, stack trace omitted):

[source,text]
----
Exception in thread "main" java.lang.IllegalArgumentException: Unknown option '-input'. Long-form flags require two dashes (try '--input' instead of '-input'). Run with --help for the full option list.
----

A missing file is still reported in an unhelpful way, because a name that is not an existing file is tried as a URL. The
official integration-test page lists this as a known issue:

[source,text]
----
Exception in thread "main" java.net.MalformedURLException: no protocol: missing.pdf
----

Source: https://tika.apache.org/docs/4.1.x/using-tika/cli/index.html[Apache Tika 4.1.x, Tika Command Line Interface, Standard-mode Options]
and https://tika.apache.org/docs/4.1.x/advanced/integration-testing/tika-app.html[Apache Tika 4.1.x, Tika-App Integration Testing].

=== Help, version and configuration options

[cols="2,5",options="header"]
|===
|Option |Effect in 4.1.0

|`-?`, `--help` |Prints the usage above. If it appears anywhere on the command line, nothing else runs.
|`-V`, `--version` |Prints `Apache Tika 4.1.0`.
|`-v`, `--verbose` |Raises the Log4j root level to `DEBUG`.
|`--config=<tika-config.json>` |Loads this JSON configuration with `TikaLoader` instead of the bundled convenience defaults. Its `parsers`, `detectors` and `parse-context` sections apply, so for example `parse-context.exception-reporting` bounds the exception values of `-j` and `-J` output. A 3.x XML file is rejected; convert it first.
|`--convert-config-xml-to-json=<input.xml>` |Converts the `parsers` section of a 3.x `tika-config.xml` to 4.x JSON on standard output, then exits. The xref:backend/apache-tika/configuration.adoc[Configuration] page shows a full conversion and what it does not cover.
|===

With `--config=`, the parse uses your configuration instead of the convenience defaults. The _Bookshelf_ desk keeps one
`tika-config.json` for the intake service and for its batch runs:

[source,json]
----
{
  // Bookshelf intake: shared by the desk CLI and the batch runs
  "parsers": [
    { "pdf-parser": { "sortByPosition": true, "extractInlineImages": false } },
    { "default-parser": { "exclude": ["executable-parser"] } }
  ],
  "metadata-filters": [
    { "include-field-metadata-filter": {
        "include": ["Content-Type", "dc:title", "dc:creator", "tk:content"] } }
  ],
  "parse-context": {
    "embedded-limits": { "maxDepth": 5, "maxCount": 200 },
    "timeout-limits":  { "totalTaskTimeoutMillis": 120000, "progressTimeoutMillis": 30000 }
  },
  "pipes": {
    "numClients": 2,
    "forkedJvmArgs": ["-Xmx768m"]
  }
}
----

[source,bash]
----
tika --config=tika-config.json -j -r manuscript.docx
----

Output:

[source,json]
----
{
  "Content-Length" : "1418",

=== Output formats

One option chooses what is written for each input. The last one given before the input wins.

[cols="2,4,3",options="header"]

inside the Word file. `jq` keeps the output readable:

[source,bash]
----
tika -J -t publisher-email.eml \

----

[source,bash]

[source,text]

model behind `-J` (the "list of metadata" of `RecursiveParserWrapper`, the same JSON as tika-server's `/rmeta`) is

=== Detection, language and digests

`-d` runs only the detector and prints the media type. It reads the bytes, so a renamed file is reported as what it is:

[source,bash]
----
tika -d manuscript.docx novel.epub renamed-invoice.png book-cover.jpg
----

Output:

[source,text]
----
application/vnd.openxmlformats-officedocument.wordprocessingml.document
application/epub+zip
application/pdf
image/jpeg
----

`renamed-invoice.png` is a PDF, and Tika says so. That is the check the intake desk runs before it trusts a file
extension (the xref:backend/apache-tika/media-types-and-detection.adoc[Media Types & Detection] page explains the magic,
glob and container steps behind it).

`-l` parses the text and prints only the detected language. tika-app 4.1.0 bundles the CharSoup detector
(`tika-langdetect-charsoup`), which reports ISO 639-3 codes:

[source,bash]
----
tika -l reviews-es.html
tika -l reseñas-fr.txt
----

Output:

[source,text]
----
spa
fra
----

These are three-letter codes, not the two-letter `es` and `fr` that the 2.x and 3.x Optimaize detector usually returned. Map them
before comparing with stored values. The xref:backend/apache-tika/language-detection-and-translation.adoc[Language Detection & Translation]
page covers CharSoup and the short-text pitfalls.

`--digest=X` adds a digest of the input bytes to the metadata. The accepted values are `md2`, `md5`, `sha1`, `sha256`,
`sha384` and `sha512` (case-insensitive). It uses the Commons Codec digester, which has no SHA-3; for SHA3-256 and the
other SHA-3 variants, configure the Bouncy Castle digester in `tika-config.json` instead. The digest is a metadata key,
so combine it with `-j`, `-m` or `-J`:

[source,bash]
----
tika -j --digest=sha256 catalogue.pdf | jq -r '."tk:digest:SHA-256"'
shasum -a 256 catalogue.pdf
----

Output:

[source,text]
----
775dabd42ebe9c7c1ea7cc6c3164a41fcafc51d3541db835f34d1e9a21135385
775dabd42ebe9c7c1ea7cc6c3164a41fcafc51d3541db835f34d1e9a21135385  catalogue.pdf
----

The key is `tk:digest:SHA-256` in 4.x (`X-TIKA:digest:SHA256` in 3.x). The intake desk stores it to spot duplicate
submissions.

Source: https://tika.apache.org/docs/4.1.x/using-tika/cli/index.html[Apache Tika 4.1.x, Tika Command Line Interface, Detection, Language and Content]
and https://tika.apache.org/docs/4.1.x/configuration/digesters.html[Apache Tika 4.1.x, Digesters].

=== Passwords

`--password=X` supplies a password for encrypted PDF and Office files. Without it, the members-only catalogue fails with
exit status 1:

[source,bash]
----
tika -t members-only.pdf
----

Output (standard error, stack traces omitted):

[source,text]
----
Exception in thread "main" org.apache.tika.exception.EncryptedDocumentException: Unable to process: document is encrypted
Caused by: org.apache.pdfbox.pdmodel.encryption.InvalidPasswordException: Cannot decrypt PDF, the password is incorrect
----

A password on the command line is visible to other users of the machine (in `ps` output and the shell history). The
4.1.0 source also reads the environment variable `TIKA_PASSWORD` as the default password, which keeps it off the command
line. `TIKA_PASSWORD` is not mentioned in `--help` or on the CLI page; it was found in the `TikaCLI` source and tested:

[source,bash]
----
# the test password of the sample file; in real use read it from a secret store
export TIKA_PASSWORD='reader-pw'
tika -t members-only.pdf
----

Output:

[source,text]
----
Bookshelf spring catalogue
Forty titles from independent publishers.
----

`--password=X` on the command line overrides the environment variable. The password applies to every encrypted document
of the run, including embedded ones; for per-file passwords write a `PasswordProvider` in Java (see
xref:backend/apache-tika/parser-api-and-autodetectparser.adoc[Parser API & AutoDetectParser]).

Source: https://tika.apache.org/docs/4.1.x/using-tika/cli/index.html[Apache Tika 4.1.x, Tika Command Line Interface]
and the 4.1.0 https://github.com/apache/tika/blob/4.1.0/tika-app/src/main/java/org/apache/tika/cli/TikaCLI.java[`TikaCLI` source]
(the `TIKA_PASSWORD` default).

=== Standard input and URLs

With `-` or no input, and data waiting on standard input, tika-app parses standard input. With a name that is not an
existing file it tries a URL, so `file:`, `http:` and `https:` URLs work:

[source,bash]
----
cat catalogue.pdf | tika -t
cat renamed-invoice.png | tika -d
tika -d "file://$PWD/novel.epub"
----

Output:

[source,text]
----

Bookshelf spring catalogue
Forty titles from independent publishers.

application/pdf
application/epub+zip
----

Standard input has no file name, so detection relies on the bytes alone, which is enough for the renamed PDF. For text
formats that need a name hint, pass a file instead. Fetching a URL makes the CLI an HTTP client: run it only on URLs
you trust, never on URLs taken from an untrusted document or request (the xref:backend/apache-tika/security.adoc[Security]
page explains the server-side request forgery risk).

Source: the `Description` section of `--help` above.

== Fork mode

`-f` / `--fork` keeps the standard-mode command line but runs the parse in a separate JVM through `PipesForkParser`, the
4.x replacement of the removed `ForkParser`. If the parser crashes the JVM, runs out of memory or hangs, the forked JVM
dies or is killed and the CLI reports it instead of dying itself. That is the right way to look at a file you do not
trust, such as an attachment that has already crashed a worker.

[cols="2,2,4",options="header"]
|===
|Option |Default |Meaning

|`-f`, `--fork` |off |Parse in a forked JVM.
|`--task-timeout=<ms>` |3600000 (1 hour) |Total budget per file. The fork is killed when it runs out. Same default as `TimeoutLimits` in the library and in pipes.
|`--progress-timeout=<ms>` |120000 (2 minutes) |Stall detector: the fork is killed as hung if it makes no progress for this long.
|`--fork-jvm-args=<args>` |none (heap auto-sized) |Comma-separated JVM arguments for the fork, for example `--fork-jvm-args=-Xmx512m,-Dsome.prop=value`.
|`--fork-plugins-dir=<dir>` |the distribution's `plugins/` |Directory with plugin zips for the fork.
|`--fork-timeout=<ms>` |removed |Removed in 4.0. Using it is an error that names the two replacements.
|===

[source,bash]
----
tika -f -t catalogue.pdf
----

Output (the 35 empty lines before the title are shortened to one):

[source,text]
----

Spring catalogue


Bookshelf spring catalogue
Forty titles from independent publishers.
----

The run took about 12.7 seconds of wall time against 6.3 seconds without `-f`, because a second JVM starts and loads the
parsers again. The log on standard error shows the fork being sized and started:

[source,text]
----
INFO  [main] 22:53:22,064 org.apache.tika.pipes.core.PipesParser Using per-client server mode with 1 clients
INFO  [main] 22:53:22,066 org.apache.tika.pipes.core.PerClientServerManager pipes-cpu-sizing: hostCores=8, numClients=1, parentReserved=2, autoCap=slice=6, heap=MaxRAMPercentage=60

Without `--fork-jvm-args`, the fork's heap is auto-sized to 60 % of the machine's memory (`MaxRAMPercentage=60`); on a

Fork mode is not a drop-in copy of standard mode in 4.1.0. Reading the source and running it showed these differences:

* The output comes from a `PipesForkParser` result in `CONCATENATE` parse mode (or `RMETA` with `-J`), so `-t` uses the
  full text handler: the title from the `<head>` appears, with the blank lines, as above.
* `-T` maps to the `BODY` handler, not to boilerpipe. `-A`, `-d`, `-l` and `-y` map to the `IGNORE` handler and print
  nothing useful; use them without `-f`.
* `--password=` and `TIKA_PASSWORD` were not passed to the fork: `-f --password=reader-pw -t members-only.pdf` printed
  nothing, and `-f -j` showed `tk:exception:container-exception` with the "password is incorrect" error. The parse
  inside the fork also used its own defaults rather than the parsers of `--config=`, as far as the source shows (the
  fork configuration is built from the timeouts, JVM arguments, plugin directory and embedded limits only).
* The result metadata includes `tk:source-path` with the absolute path of the input and `tk:content-handler-type`.

So use fork mode for what it is for (looking safely at one dangerous file) and pipes mode for batches. For production
isolation inside a service, use `PipesForkParser` from Java (see xref:backend/apache-tika/tika-pipes.adoc[Tika Pipes])
or tika-server, whose parsing endpoints always fork.

Source: https://tika.apache.org/docs/4.1.x/using-tika/cli/index.html[Apache Tika 4.1.x, Tika Command Line Interface, Fork Mode],
https://tika.apache.org/docs/4.1.x/pipes/timeouts.html[Apache Tika 4.1.x, Pipes, Timeouts],
https://tika.apache.org/docs/4.1.x/pipes/cpu-sizing.html[Apache Tika 4.1.x, Forked-JVM CPU and Heap Sizing] and the
4.1.0 `TikaCLI` source (`processWithFork`).

== Tika Pipes mode

Pipes mode is the batch mode of 4.x. It replaces the 1.x to 3.x tika-batch mode of tika-app (`-bc`, `-numConsumers`,
`-maxRestarts` and the rest), which was removed with the tika-batch module. tika-app hands the arguments to the
`tika-async-cli` module (`TikaAsyncCLI`), which writes a temporary `tika-config.json` from a template, merges your
`--config` into it, applies the command-line overrides and runs an `AsyncProcessor`: a file-system pipes iterator lists
the input files, a pool of forked JVMs parses them, and a file-system emitter writes one output file per input. The
xref:backend/apache-tika/tika-pipes.adoc[Tika Pipes] page explains those roles; this section covers the command line.

=== How pipes mode is activated

tika-app 4.1.0 enters pipes mode when any of these holds (checked before anything else, except `--help`):

* exactly two arguments and the first is an existing directory (`tika in/ out/`);
* the last two arguments are an existing directory followed by a directory or a path that does not exist yet, with
  options in front;
* a single argument ending in `.json`, which is read as a complete pipes configuration;
* any of `-i`, `--inputDir` (in fact any argument starting with `--input`), `-o`, `--outputDir` (any argument starting
  with `--output`), `--fileList`, `-z`, `-Z`, `--extract`, `--extract-dir`, `-a` or `--async`.

When it switches, it prints a one-line banner on standard error, so you can tell which path ran:

[source,text]
----
tika-app: running in Tika Pipes mode (async dispatch via -a/--async); use --help for options.
----

Source: https://tika.apache.org/docs/4.1.x/using-tika/cli/index.html[Apache Tika 4.1.x, Tika Command Line Interface, How Pipes mode is activated]
and the 4.1.0 `TikaCLI.testForAsync` source.

=== Pipes-mode options

[cols="2,2,4",options="header"]
|===
|Option |Default |Meaning

|`-i`, `--inputDir=<dir>` |none |Input directory; a single file also works (its parent becomes the base path). The long form is `--inputDir`, not `--input`.
|`-o`, `--outputDir=<dir>` |`./output` (or `.` for a single input file) |Output directory. The long form is `--outputDir`.
|`--fileList=<file>` |none |Text file with one path per line, relative to `--inputDir` or absolute. Only those files are processed.
|`--handler=<X>` |`m` |Content handler: `t` text, `h` HTML, `x` XHTML, `m` Markdown, `b` body, `i` ignore (metadata only).
|`--concatenate` |off |Parse mode `CONCATENATE`: one metadata object per input, with the content of all embedded documents joined into its `tk:content`.
|`--content-only` |off |Parse mode `CONTENT_ONLY`: write only the content, no JSON wrapper and no metadata; the output extension follows the handler (`.txt`, `.md`, `.html`, `.xml`). Implies `--concatenate`.
|`--on-exists=<mode>` |`exception` |What to do when an output file exists: `exception`, `replace` or `skip`. Also applied to a configured `file-system-jsonl-reporter` (`skip` becomes `APPEND` there).
|`-n`, `--numClients=<N>` |2 (1 in the bare two-directory form) |Number of forked JVMs that parse in parallel. A `pipes.numClients` in `--config` is kept when `-n` is not given.
|`--Xmx=<size>` |unset: heap auto-sized (`-Xmx1g` in the bare form) |`-Xmx` of each forked JVM, for example `--Xmx=1g`. Merged into `pipes.forkedJvmArgs`, replacing an existing `-Xmx` and keeping the other arguments. A long flag despite its look; there is no `-X` option.
|`-T`, `--timeoutMillis=<ms>` |config or library default (30000 in the bare form) |Total task timeout per input. Sets `parse-context.timeout-limits.totalTaskTimeoutMillis`, merged into any `timeout-limits` of the config.
|`-c`, `--config=<file>` |the built-in template |A `tika-config.json` merged over the template. Its top-level sections replace the template's.
|`-p`, `--pluginsDir=<dir>` |the distribution's `plugins/` |Where the pipes plugins (fetchers, emitters, iterators) are loaded from.
|`-a`, `--async` |n/a |Forces pipes mode. Redundant with any of the triggers above.
|`-z`, `--extract`, `-Z`, `--extract-dir=<dir>`, `--unpack-format`, `--unpack-mode`, `--unpack-include-metadata` |off |Unpacking, see <<unpacking,Unpacking attachments>>.
|===

The bare-form defaults (one client, `-Xmx1g`, a 30-second task timeout) were read from the 4.1.0 `TikaAsyncCLI`
source; the "1 workers" in the log above confirms the client count. The other defaults are from the official CLI page
and were confirmed by the runs below.

=== Re-runs, --on-exists and the exit status

Run the same command again and every emit fails, because the output files exist and the default is `exception`:

[source,bash]
----
tika -i intake -o text-out --handler t --content-only
echo "exit status: $?"
----

Output (standard error, one of six messages shown, stack traces and paths shortened):

[source,text]
----
WARN  [pool-2-thread-1] 22:55:20,790 [fork] pipesClientId=0 org.apache.tika.pipes.core.server.EmitHandler emit exception
java.io.IOException: Output already exists (onExists=EXCEPTION, not overwritten): .../text-out/manuscript.docx.txt. Use an empty output dir, delete the file, or set onExists to REPLACE or SKIP.
INFO  [main] 22:55:22,047 tika.pipes Successfully finished processing 6 files in 9213 ms
exit status: 0
----

Two lessons. First, choose the policy: `--on-exists skip` resumes an interrupted batch (only missing outputs are
written), `--on-exists replace` reprocesses everything. Second, *the exit status is 0 and the summary says
"Successfully finished" even though nothing was written*. In pipes mode a per-file failure (a parse exception, a
timeout, a crash of a fork, an emit failure) is recorded for that file and the batch continues; the command only fails
for configuration and startup errors. A script must check the outputs, the log, or a configured reporter (the
`file-system-jsonl-reporter` writes one status line per file), not just `$?`.

This run also shows that `-n` defaults to 2 outside the bare form: the warnings came from `pipesClientId=0` and
`pipesClientId=1` without any `-n`.

Source: https://tika.apache.org/docs/4.1.x/pipes/reporters.html[Apache Tika 4.1.x, Pipes, Reporters] and
https://tika.apache.org/docs/4.1.x/pipes/troubleshooting.html[Apache Tika 4.1.x, Pipes, Troubleshooting].

=== A file list and a configuration file

`--fileList` processes only the listed files, which suits a "reprocess these two" request from the editors:

[source,bash]
----
printf 'manuscript.docx\nnovel.epub\n' > batch.txt
tika -i intake --fileList batch.txt -o listed --handler t

----

Output:

[source,text]
----

----

`-c` (or `--config=`) merges the _Bookshelf_ `tika-config.json` shown earlier into the pipes template. Its `pipes`
section sets two clients and `-Xmx768m`; the `--Xmx=1g` on the command line replaces the `-Xmx` and keeps the rest:

[source,bash]
----

jq . cfg-out/manuscript.docx.json
----

Output (standard error shortened):

[source,text]
----
INFO  [main] 22:57:03,054 org.apache.tika.pipes.core.async.AsyncProcessor Using per-client server mode with 2 workers
INFO  [main] 22:57:10,207 tika.pipes Successfully finished processing 6 files in 7193 ms

----
[
  {
    "dc:title": "The Lighthouse Keeper",
    "dc:creator": "Ana Torres",

Here the `include-field-metadata-filter` of the file was applied: only the four listed keys remain. The merge is

{
  "content-handler-factory": {

  },

    { "office-parser": { "extractMacros": true } }
  ],
  "fetchers": { "fsf": { "file-system-fetcher": { "basePath": "FETCHER_BASE_PATH", "extractFileSystemMetadata": false } } },
  "emitters": { "fse": { "file-system-emitter": { "basePath": "EMITTER_BASE_PATH", "fileExtension": "json", "onExists": "EXCEPTION" } } },
  "pipes-iterator": { "file-system-pipes-iterator": { "basePath": "FETCHER_BASE_PATH", "countTotal": true, "fetcherId": "fsf", "emitterId": "fse" } },

(The JSON was reformatted to fit; the placeholders are replaced at run time by the `-i`, `-o` and plugin paths.) The

configuration with an `output-limits` section and the limits of the

[#unpacking]
=== Unpacking attachments

`-z` and `-Z` write the embedded files' bytes, not their text. Both run in pipes mode (parse mode `UNPACK`) and accept a
directory or a single file. `-Z` extracts recursively; `-z` is documented as "direct attachments (depth 1)" and is
implemented as an embedded depth limit of 2.

[cols="2,4",options="header"]
|===
|Option |Meaning

|`-z`, `--extract` |Extract direct attachments.
|`-Z` |Extract all attachments recursively.
|`--extract-dir=<dir>` |Output directory for the bytes; the same as `-o`.
|`--unpack-format=<format>` |`REGULAR` (default) or `FRICTIONLESS` (a Frictionless Data Package with `datapackage.json`).
|`--unpack-mode=<mode>` |`ZIPPED` or `DIRECTORY`. `DIRECTORY` when `--unpack-format=FRICTIONLESS` is given without a mode.
|`--unpack-include-metadata` |Metadata for every extracted file: a Frictionless package carries `metadata.json` anyway; this adds a `.metadata.json` sidecar per file to `REGULAR` zip output.
|===

The publisher's e-mail, recursively:

[source,bash]
----
mkdir mail && cp intake/publisher-email.eml mail/
tika -Z -i mail -o unpacked
find unpacked -type f | sort
----

Output:

[source,text]
----
unpacked/publisher-email.eml-embed/00000001.zip
unpacked/publisher-email.eml-embed/00000002.docx
unpacked/publisher-email.eml-embed/00000003.png
unpacked/publisher-email.eml-embed/00000004.pdf
unpacked/publisher-email.eml-embed/00000005.bin
unpacked/publisher-email.eml.json
----

The files are named `<input>-embed/<8-digit id>.<suffix>`, with the suffix chosen from the detected type, and the
`.json` next to them is the usual list of metadata that maps each id to its original name. `00000001.zip` is
`samples.zip` itself, and `00000005.bin` is `notes/cover-note.txt`, a windows-1252 text file that received `.bin` in
this run. Read the names from the metadata, not from the suffixes. The CLI keeps this naming whatever
`unpack-config` your `--config` sets for `suffixStrategy`, `zeroPadName`, `embeddedIdPrefix` or `keyBaseStrategy`; the
other `unpack-config` settings apply, and `+"includeOriginal": true+` there is the only way to also copy the source
document into the output.

`-z` with a single file. The options go *before* the file: `--extract-dir` is rewritten to `-o`, and Commons CLI stops
reading options at the first positional argument, so `tika -z mail/publisher-email.eml --extract-dir=shallow` fails with
`+TikaConfigException: Can't have more than 2 unknown args+`.

[source,bash]
----
tika -z --extract-dir=shallow mail/publisher-email.eml
find shallow -type f | sort
----

Output:

[source,text]
----
shallow/publisher-email.eml-embed/00000001.zip
shallow/publisher-email.eml-embed/00000002.docx
shallow/publisher-email.eml-embed/00000003.pdf
shallow/publisher-email.eml-embed/00000004.bin
shallow/publisher-email.eml.json
----

In 4.1.0, `-z` on the e-mail wrote the zip _and_ the three files inside it, and left out only the image inside the Word
file. The zip's entries are one level deeper than "direct attachments of the e-mail", so the depth accounting counts
differently from what the description suggests. Check with your own files when the depth matters, or set
`parse-context.embedded-limits.maxDepth` explicitly.

{ "path": "unpacked/00000001.zip", "mediatype": "application/zip", "name": "samples.zip" }
----

Each resource in `datapackage.json` also has `bytes` and a `hash` (`+sha256:...+`), so a consumer can verify what it
reads. The `name` is the original name from the e-mail or the archive; it is _untrusted input_. Never use it as a path
on disk without sanitizing it (a name such as `../../etc/cron.d/x` is a classic "zip slip"). The 8-digit file names
Tika writes are safe; that is one reason it writes them. The official home page says the Frictionless format is planned
to become the default in 4.2.0.

== Removed and changed options

The command line changed more between 3.x and 4.x than in any earlier release. 4.1.0 rejects the removed options with an
error (exit status 1) instead of misreading them.

[cols="2,2,4",options="header"]
|===
|Old option |Removed in |What to use / what 4.1.0 does

|`-s`, `--server`, `-p`, `--port` (server mode) |2.0 (3.x printed an error naming the wiki page) |Run tika-server (see xref:backend/apache-tika/tika-server-rest-api.adoc[Tika Server (REST API)]). 4.1.0: `Unknown option '--server'`. In 4.x `-p` exists only in pipes mode, as `--pluginsDir`.
|`-c<uri>`, `--client=<uri>` (network client, `NetworkParser`) |4.0 |Call tika-server over HTTP. The official page explains that it sent raw sockets, including a bare `telnet:` scheme, to any user-supplied host with no authentication or TLS. 4.1.0: `+Unknown option '--client=...'+`. In 4.x `-c` is the pipes-mode `--config`.
|`-eX` (inline encoding) |4.0 |`--encoding=X`. 4.1.0: `+Unknown option '-eUTF-8'. Long-form flags require two dashes ...+`
|`-pX` (inline password) |4.0 |`--password=X` or `TIKA_PASSWORD`. Same error as `-eX`.
|Batch mode (`-bc`, `-numConsumers`, `-maxRestarts`, `-timeoutThresholdMillis`, `-includeFilePat`, `-excludeFilePat`, `-maxFileSizeBytes`, `-JXmx4g`, `+-JD...+`) |4.0, with tika-batch |Pipes mode: `-n`, `--Xmx`, `-T`, `--fileList`, `--config` with `pipes` and `parse-context`. |`--fork-timeout=<ms>` |4.0 |`--task-timeout=<ms>` and `--progress-timeout=<ms>`. The error message says so.
|`--config=<tika-config.xml>` |4.0 (format) |`--config=<tika-config.json>`; convert with `--convert-config-xml-to-json=`.
|`--dump-minimal-config`, `--dump-current-config`, `--dump-static-config`, `--dump-static-full-config` |4.0 |Not implemented in 4.x (commented out in the source, listed as a known issue on the integration-test page). Keep your `tika-config.json` under version control instead.
|`--container-aware`, `--container-aware-detector` |earlier |Accepted and ignored: container-aware detection is always on.
|`-x` as the default output |4.0 |The default is `--md`. Add `-x` to scripts that expect XHTML.
|`-f` through `ForkParser` |4.0 |`-f` now uses `PipesForkParser`, with the new timeout flags and the differences listed under fork mode.
|`-a` with an XML async config |4.0 |`-a` forces pipes mode; a JSON pipes config is passed with `-c` or as the only argument.

[cols="2,4",options="header"]

|Check what your service will see |Standard mode with `--config=` set to the service's file (and remember the fork-mode and metadata-filter differences above).

== Memory, performance and robustness

* *JVM start-up dominates.* Every standard-mode call starts a JVM and loads more than a hundred parsers: about 6 seconds
  for a tiny PDF here. Put several files in one call (`tika -t a.pdf b.docx`) or use pipes mode, which starts its forks
  once and reuses them.
* *Standard mode has no isolation.* A parser bug, a zip bomb or an endless loop affects the CLI JVM itself. Set `-Xmx`
  before `-jar`, use `-f` for unknown files, and do not run standard mode on untrusted input in a loop.
* *Fork and pipes heap.* Without `--Xmx` / `--fork-jvm-args`, each fork's heap is sized from the machine's memory (60 %
  in the fork-mode run above). With `-n 4` on a shared host, set `--Xmx` so that `n` times the heap plus the parent fits.
* *Timeouts.* Fork mode: `--task-timeout` and `--progress-timeout`. Pipes mode: `-T` for the total budget, and
  `progressTimeoutMillis` in the configuration for the stall detector.
* *Limits.* The CLI defaults do not cap the output size (`writeLimit: -1` in the pipes template, and unlimited embedded
  depth and count). Add `output-limits` and `embedded-limits` to your configuration, as described on the
  xref:backend/apache-tika/robustness-limits-and-timeouts.adoc[Robustness, Limits & Timeouts] page.
* *Temporary files.* Spooling and per-fork temp directories go to `java.io.tmpdir` (logged at start-up); point it at a
  volume with enough space for large batches with `+-Djava.io.tmpdir=...+` before `-jar` and in `--fork-jvm-args`.

Source: https://tika.apache.org/docs/4.1.x/pipes/performance.html[Apache Tika 4.1.x, Pipes, Performance and Isolation Trade-offs]
and https://tika.apache.org/docs/4.1.x/advanced/robustness.html[Apache Tika 4.1.x, Robustness].

== Pitfalls and security

* *Pinning.* The CLI is in flux for 4.x. Pin the version (`tika-app-4.1.0`) in scripts and re-read `--help` when you
  upgrade.
* *Exit status in pipes mode.* 0 even when every file failed; check outputs or a reporter.
* *Option order.* `--config=` before the first file; pipes options before a positional input.
* *`-T` and `-c` mean different things in the two modes.*
* *Convenience defaults.* Standard mode and the pipes template turn on macro extraction, deleted Word text, PDF actions
  and incremental updates. That is right for inspection and forensics; for a public index, deleted text and macros may be
  content you do not want to publish. Use your own configuration.
* *Passwords on the command line* are visible in process lists and shell history; prefer `TIKA_PASSWORD` from a secret
  store, and remember that fork mode did not pass it in 4.1.0.
* *URLs.* Passing a URL makes tika-app fetch it. Do not build tika-app command lines from untrusted strings, and quote
  file names (a file named `-input` is taken as an option unless it exists).
* *Extracted names are untrusted.* Original names in `-J` output and `datapackage.json` come from the documents.
* *Hostile files.* The CLI parses with the same parsers as the library and has the same exposure to parser
  vulnerabilities (for example CVE-2025-54988 / CVE-2025-66516 in the PDF module before 3.2.2). Keep the distribution
  current; the xref:backend/apache-tika/security.adoc[Security] page covers the threat model.

Source: https://tika.apache.org/docs/4.1.x/security.html[Apache Tika 4.1.x, Security] and
https://tika.apache.org/security.html[Apache Tika, Security].

== What was verified and what was not

Verified by running the official 4.1.0 zip distribution on Java 25 (macOS): the `--help` and `--version` output, every
standard-mode output format shown, `-d`, `-l`, `--digest`, `--password` and `TIKA_PASSWORD`, standard input and
`file:` URLs, the listing options, `--maxEmbeddedDepth`, fork mode (including the password and handler differences),
the removed-option errors, pipes mode with two directories, `-i` / `-o` with `--handler`, `--content-only`, `-n`,
`--Xmx`, `-T`, `--fileList`, `-c`, `--on-exists` (default and `skip`), a single `.json` pipes configuration (with and
without `plugin-roots`), and `-z`, `-Z` and `--unpack-format=FRICTIONLESS`.

Read from the 4.1.0 source but not exercised: the bare-form timeout (30 s) and heap (`-Xmx1g`), `--unpack-mode`,

`--progress-timeout` and `--task-timeout` actually killing a fork, the GUI and its menus, and pipes plugins other than
the file system. Not checked at all: Windows behavior, and the 1.x / 2.x command lines (read from source only).
