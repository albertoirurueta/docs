A document intake service receives files it does not control: a Word manuscript, a scanned PDF, an e-mail with a ZIP
attachment, a text file in an old encoding, a PDF renamed to `.png`. Apache Tika answers the two questions every such
service asks first: what is this file, and what is in it. It detects the media type of more than a thousand formats and
extracts text, metadata, embedded documents and the language through a single interface. This section is a practical,
example-driven guide to using it from Java, from the command line, as a REST or gRPC service and as a scalable Tika
Pipes pipeline that feeds search indexes and RAG systems. Versions and dates are re-verified when each page is written
and stated as of the date checked.

== Running scenario: Bookshelf

Every page uses the same example, the document intake service of the Bookshelf store used by other sections, so
readers can compare approaches. It receives files from publishers and readers, then extracts text and metadata for
search and RAG. The sample files are original and were created for this section:

* `manuscript.docx`: headings, tables, an embedded image and author metadata.
* `catalogue.pdf`: a tagged PDF with bookmarks, a form and a PDF attachment.
* `scanned-loan-form.pdf` and `book-cover.jpg`: OCR and EXIF and XMP metadata.
* `publisher-email.eml` with a `samples.zip` attachment that contains more documents: embedded and recursive parsing.
* `novel.epub`, `reviews-es.html` and `reseñas-fr.txt`: other formats, HTML and language detection.
* `legacy-catalogue.txt`, saved in windows-1252: charset detection.
* `renamed-invoice.png`, a PDF renamed to `.png`: detection by content, not by name.

No example uses real secrets, passwords or personal data; examples that need credentials (cloud fetchers, VLM and
inference services) read them from environment variables.

== Library path and service path

The section is organised around two ways of running Tika, and most real systems end up using both.

* *Library path.* The Tika classes run inside your own JVM: the `Tika` facade, `AutoDetectParser`, content handlers,
  `Metadata` and the configuration loaded with `TikaLoader`. It is the simplest and the fastest route, but a parser that
  runs in-process shares the fate of your application: an out-of-memory error, an infinite loop or a crash caused by a
  hostile file is then your problem, not Tika's.
* *Service and pipeline path.* Parsing happens in a separate process: `PipesForkParser`, the `tika-app` command line,
  `tika-server` (REST), `tika-grpc` or a full Tika Pipes pipeline with fetchers and emitters. Process isolation is
  Tika's own sandbox model, and it is what the official documentation recommends for untrusted input. `tika-server` and
  `tika-grpc` are not security boundaries themselves: expose them only to trusted callers.

The foundations and core concepts pages teach the library path. The running and integration pages add the service path
and show how both are tied together in Spring Boot, search indexing and RAG ingestion.

page that depends on it says so; check both pages before planning a migration. Version 2.x (Java 8) reached end of
life in April 2025 (last release 2.9.4) and 1.x in September 2022.

== The book and the official documentation

_Tika in Action_ by Chris A. Mattmann and Jukka L. Zitting (Manning, 2011) was written for Tika 1.0. Its concepts are
still valid: media types and detection, the `Parser` and `ContentHandler` model, XHTML output, metadata and language
detection. Its code is not, because the API has changed in 2.0, 3.0 and 4.0. The pages of this section teach the
concepts the book introduced and show every API in its current form, with the book chapter cited where it helps and an
"outdated idiom to current code" table on the xref:backend/apache-tika/whats-changed-and-migration.adoc[What's Changed & Migration] page.

The official documentation also has gaps that the pages state honestly instead of inventing APIs:

* There is no official Spring Boot starter or Spring integration for Tika; the Spring page builds the wiring itself.
* The `tika-app` command line is still described as in flux for 4.x.
* The facade, `RecursiveParserWrapper` from Java, encrypted documents, custom media types, translation and logging have
  little or no 4.x narrative; those pages cite the Javadoc, the 3.x guides, the wiki and the official `tika-example`
  module.
* The 4.1.x documentation site says it was generated with AI assistance and needs human review, so facts are
  cross-checked against the Javadoc, `CHANGES.txt` and the source.
* Tika does not recover layout (reading order across columns, table structure) as layout models do.
* Many wiki pages describe 3.x behaviour and are labelled as such.
