== The Bookshelf scenario: publisher-email.eml

The _Bookshelf_ intake service receives `publisher-email.eml`, a message from a publisher with one attachment,
`samples.zip`. Inside the archive are three files: a chapter, `chapter-one.docx`, which itself contains the picture
`figure1.png`; the catalogue `catalogue.pdf`; and a text note stored as `notes/cover-note.txt` in windows-1252. The
sample files used here are small stand-ins that were generated for this page (the `.eml` is 4 KB, the ZIP 2,975 bytes).

[source,text]
----
publisher-email.eml                  message/rfc822, the container
└── samples.zip                      the attachment
    ├── chapter-one.docx             Word document
    │   └── figure1.png              picture inside the .docx
    ├── catalogue.pdf
    └── notes/cover-note.txt         windows-1252 text
----

== What counts as embedded

Tika treats a document as embedded when a parser finds another complete file inside the one it is parsing and hands that
inner file back to Tika for its own detection and parse. The container parser decides what is worth handing back, so the
list below describes what the standard parsers do in 4.1.x, not a guarantee of the format.

[cols="2,5",options="header"]
|===
|Container |Embedded documents

|ZIP, TAR, 7z, gzip and other archives |Every entry (a gzip has one). The entry path becomes the resource name.
|E-mail (`.eml`, `.msg`, mbox, PST) |The attachments, with the parts' file names where the message gives them.
|Word, Excel and PowerPoint (OOXML and OLE2) |Pictures, embedded OLE objects (a spreadsheet pasted into a document) and attached files.
|PDF |File attachments and, when enabled, inline images; the `METADATA` resource type exists for streams such as XMP and XFA.
|OpenDocument, iWork, EPUB |Pictures and other package parts, depending on the parser.
|===

The category of an embedded document is recorded in `tk:embedded-resource-type` when the parser knows it. In the
Bookshelf tree above the ZIP carries `ATTACHMENT` (it was attached to an e-mail) and the picture carries `INLINE` (it
is shown in the page). The values are the constants of the `TikaCoreProperties.EmbeddedResourceType` enum in 4.1.0:
`INLINE`, `ATTACHMENT`, `MACRO`, `METADATA`, `FONT`, `THUMBNAIL`, `RENDERING`, `VERSION` and
`ALTERNATE_FORMAT_CHUNK`. Not every parser sets it: in the run on this page the DOCX, PDF and text entries of the ZIP
have no `tk:embedded-resource-type` at all, because the ZIP parser does not classify its entries.

Source: https://tika.apache.org/docs/4.1.x/advanced/embedded-documents.html[Embedded Document Metadata, Tika 4.1.x docs],
https://tika.apache.org/4.1.0/api/org/apache/tika/metadata/TikaCoreProperties.html[`TikaCoreProperties`, Javadoc 4.1.0]
and https://tika.apache.org/docs/4.1.x/formats.html[Supported formats, 4.1.x].

== What the default parse does with embedded documents

If you parse with `AutoDetectParser` and a `BodyContentHandler`, embedded documents are parsed, but the result is one
merged stream. Their text is appended to the container's text in document order, their metadata is not returned per
document, and there is no way to tell which words came from which file.

[source,java]
----
import java.nio.file.Path;

import org.apache.tika.io.TikaInputStream;
import org.apache.tika.metadata.Metadata;
import org.apache.tika.parser.AutoDetectParser;
import org.apache.tika.parser.ParseContext;
import org.apache.tika.sax.BodyContentHandler;

public class FlatVersusList {
    public static void main(String[] args) throws Exception {
        AutoDetectParser parser = new AutoDetectParser();
        BodyContentHandler handler = new BodyContentHandler(-1);
        Metadata metadata = new Metadata();
        try (TikaInputStream tis = TikaInputStream.get(Path.of(args[0]))) {
            parser.parse(tis, handler, metadata, new ParseContext());
        }
        System.out.println(handler);
    }
}
----

Source: https://tika.apache.org/4.1.0/api/org/apache/tika/parser/AutoDetectParser.html[`AutoDetectParser`, Javadoc 4.1.0]
and https://github.com/apache/tika/blob/main/tika-example/src/main/java/org/apache/tika/example/ParsingExample.java[`ParsingExample`, tika-example].

Output for `publisher-email.eml` (blank lines collapsed, so the line breaks are approximate):

[source,text]
----
Hello,
Please find the spring samples in the attached archive.
Marta
chapter-one.docx
Chapter one
The lamp was lit at dusk.
figure1.png
catalogue.pdf
Bookshelf spring catalogue
Forty titles from independent publishers.
notes/cover-note.txt
Cover note for the Bookshelf intake team.
Two samples attached: a chapter with one figure and the spring catalogue.
----

This is good enough for a search index that only needs words, and it is what the Tika facade returns. It is not good
enough for the intake service, which wants to file the catalogue under _Catalogues_, the manuscript under _Submissions_
and the note under _Correspondence_, and which wants the author of the DOCX and the producer of the PDF, not the
sender of the e-mail. The file names that appear in the output above (`chapter-one.docx`, `catalogue.pdf`) are written
into the text by `ParsingEmbeddedDocumentExtractor`, which emits the resource name as a heading before each embedded
document unless `SAXOutputConfig.isWriteFileNameToContent()` says otherwise. For per-document text and metadata you use
the recursive parser.

Two behaviours of the default parse are worth knowing before you rely on it:

* `AutoDetectParser.parse` puts itself into the `ParseContext` as the `Parser` that embedded documents are delegated to,
  unless you already set one, and does the same for the `Detector`. In 4.1.0 this is done by a private method that
  documents why: the stock extractors read `Parser.class` from the context, so a missing entry would silently drop
  embedded content. The book's recipe, `context.set(Parser.class, parser)`, is therefore needed only when you use a
  parser that is not an `AutoDetectParser`, such as a bare `CompositeParser`.
* Embedded recursion is on by default and is not bounded unless you configure `EmbeddedLimits` (see
  <<embedded-limits,Embedded limits>>). The default `maxDepth` and `maxCount` are `-1`, unlimited.

== RecursiveParserWrapper and the list of metadata

`RecursiveParserWrapper` (package `org.apache.tika.parser`) decorates another parser. It parses the container with that
parser and intercepts every embedded document on the way: it gives each one its own `Metadata` object and its own
content handler, and reports the result to a `RecursiveParserWrapperHandler`. The handler's `getMetadataList()` returns
the _list of metadata_: one `Metadata` per document, the container first, with the extracted text stored in each object
under `tk:content`.

[source,java]
----
import java.io.IOException;
import java.io.StringWriter;
import java.nio.file.Path;
import java.util.List;

import org.apache.tika.exception.TikaException;
import org.apache.tika.io.TikaInputStream;
import org.apache.tika.metadata.Metadata;
import org.apache.tika.metadata.TikaCoreProperties;
import org.apache.tika.parser.AutoDetectParser;
import org.apache.tika.parser.ParseContext;
import org.apache.tika.parser.RecursiveParserWrapper;
import org.apache.tika.sax.BasicContentHandlerFactory;
import org.apache.tika.sax.RecursiveParserWrapperHandler;
import org.apache.tika.serialization.JsonMetadataList;
import org.xml.sax.SAXException;

public class IntakeTree {

    public static void main(String[] args) throws IOException, SAXException, TikaException {
        RecursiveParserWrapper wrapper = new RecursiveParserWrapper(new AutoDetectParser());
        RecursiveParserWrapperHandler handler = new RecursiveParserWrapperHandler(
                new BasicContentHandlerFactory(BasicContentHandlerFactory.HANDLER_TYPE.TEXT, -1));

        try (TikaInputStream tis = TikaInputStream.get(Path.of(args[0]))) {
            wrapper.parse(tis, handler, new Metadata(), new ParseContext());
        }

        List<Metadata> list = handler.getMetadataList();
        System.out.println(list.size() + " metadata objects");
        for (Metadata m : list) {
            System.out.printf("%-6s %-10s %-24s %-44s %s%n",
                    m.get(TikaCoreProperties.EMBEDDED_ID),
                    m.get(TikaCoreProperties.EMBEDDED_ID_PATH),
                    m.get(TikaCoreProperties.RESOURCE_NAME_KEY),
                    m.get(TikaCoreProperties.EMBEDDED_RESOURCE_PATH),
                    m.get("Content-Type"));
        }

        StringWriter json = new StringWriter();
        JsonMetadataList.toJson(list, json, true);   // the same JSON that /rmeta and -J return
        System.out.println(json);
    }
}
----

Source: https://tika.apache.org/4.1.0/api/org/apache/tika/parser/RecursiveParserWrapper.html[`RecursiveParserWrapper`, Javadoc 4.1.0],
https://tika.apache.org/4.1.0/api/org/apache/tika/sax/RecursiveParserWrapperHandler.html[`RecursiveParserWrapperHandler`, Javadoc 4.1.0],
https://cwiki.apache.org/confluence/display/TIKA/RecursiveParserWrapper[RecursiveParserWrapper, Tika wiki] (written
for 2.x and 3.x) and the `tika-example` `ParsingExample` class.

Read the table carefully, because it shows the three properties of the model that surprise people.

* *The container is first, then the embedded documents in the order their parse finished.* `RecursiveParserWrapperHandler`
  appends each embedded document's metadata when `endEmbeddedDocument` fires, which is after all of that document's
  children, and inserts the container at index 0 in `endDocument`. So `figure1.png` (`/1/2/3`) comes before the
  `chapter-one.docx` (`/1/2`) that contains it, and `samples.zip` (`/1`) comes last. This is a post-order traversal.
  Never treat the list as a pre-order tree dump; rebuild the tree from `tk:embedded-id-path`.
* *Every object has its own text.* The `tk:content` value of the DOCX is only the Word text; the ZIP's is only the list
  of entry names. That is what makes it possible to classify and index the documents separately.
* *The container's own metadata is not polluted by the attachments.* In the real output above, the e-mail's object has
  `message:from`, `dc:subject` and `dcterms:created` of the message, and `tk:parsed-by-full-set` lists every parser that
  touched any document in the tree (`RFC822Parser`, `ZipParser`, `OOXMLParser`, `ImageParser`, `PDFParser`,
  `TextAndCSVParser`), while `tk:parsed-by` lists only the parsers of the container itself.

=== Constructor, handler type and memory

`new RecursiveParserWrapper(parser)` catches and records exceptions thrown by embedded documents so one bad attachment
does not lose the others. `new RecursiveParserWrapper(parser, false)` rethrows them instead, which stops the parse
(see <<failures-in-embedded-documents,Failures inside embedded documents>>).

The text handler is chosen by the `ContentHandlerFactory` you give the handler. `BasicContentHandlerFactory` offers the
handler types `TEXT`, `HTML`, `XML`, `BODY`, `MARKDOWN` and `IGNORE`, and a write limit, covered in
xref:backend/apache-tika/content-handlers-and-output-formats.adoc[Content Handlers & Output Formats]. The 4.x default
for tika-app and tika-server is Markdown; the factory you build in code is whatever you pass, as above. `IGNORE`
(metadata only) is the cheap option for a classification pass that does not need the text.

The default `RecursiveParserWrapperHandler` keeps every document's metadata and content in memory until you drop the
list, because it stores the text in `tk:content`. A 4,000-entry mailbox export therefore holds all 4,000 documents'
text at once. Two ways to bound that are a write limit on the factory and a streaming handler.

The write limit is shared. Reading `RecursiveParserWrapper` in 4.1.0, the counter that enforces `writeLimit` is created
once per top-level parse and passed to every embedded document's handler, so the limit is a budget for the whole
container, not per attachment. A large first attachment can therefore starve the rest. This was read from the source,
not measured.

=== A streaming handler

When you do not want a list at all, subclass `AbstractRecursiveParserWrapperHandler`, the base class of the default
handler, and act on each document as soon as it ends. The base class tracks the nesting depth in
`tk:embedded-depth`, so the overrides must call `super`.

[source,java]
----
import java.io.IOException;
import java.nio.file.Path;

import org.apache.tika.exception.TikaException;
import org.apache.tika.io.TikaInputStream;
import org.apache.tika.metadata.Metadata;
import org.apache.tika.metadata.TikaCoreProperties;
import org.apache.tika.parser.AutoDetectParser;
import org.apache.tika.parser.ParseContext;
import org.apache.tika.parser.RecursiveParserWrapper;
import org.apache.tika.sax.AbstractRecursiveParserWrapperHandler;
import org.apache.tika.sax.BasicContentHandlerFactory;
import org.xml.sax.ContentHandler;
import org.xml.sax.SAXException;

/** Handles each document as soon as it ends; nothing is kept in a list. */
public class StreamingHandler extends AbstractRecursiveParserWrapperHandler {

    public StreamingHandler() {
        super(new BasicContentHandlerFactory(BasicContentHandlerFactory.HANDLER_TYPE.TEXT, 100_000));
    }

    @Override
    public void endEmbeddedDocument(ContentHandler contentHandler, Metadata metadata)
            throws SAXException {
        super.endEmbeddedDocument(contentHandler, metadata);   // keeps the depth counter right
        report(contentHandler, metadata);
    }

    @Override
    public void endDocument(ContentHandler contentHandler, Metadata metadata) throws SAXException {
        super.endDocument(contentHandler, metadata);
        report(contentHandler, metadata);
    }

    private void report(ContentHandler contentHandler, Metadata metadata) {
        String text = contentHandler.toString();
        String idPath = metadata.get(TikaCoreProperties.EMBEDDED_ID_PATH);
        System.out.printf("%-10s depth=%s chars=%d%n", idPath == null ? "(root)" : idPath,
                metadata.get(TikaCoreProperties.EMBEDDED_DEPTH), text.length());
        // index or store the document here, then let it be garbage collected
    }

    public static void main(String[] args) throws IOException, SAXException, TikaException {
        RecursiveParserWrapper wrapper = new RecursiveParserWrapper(new AutoDetectParser());
        try (TikaInputStream tis = TikaInputStream.get(Path.of(args[0]))) {
            wrapper.parse(tis, new StreamingHandler(), new Metadata(), new ParseContext());
        }
    }
}
----

Source: https://tika.apache.org/4.1.0/api/org/apache/tika/sax/AbstractRecursiveParserWrapperHandler.html[`AbstractRecursiveParserWrapperHandler`, Javadoc 4.1.0].

Output:

[source,text]
----
/1/2/3     depth=3 chars=36
/1/2       depth=2 chars=105
/1/4       depth=2 chars=136
/1/5       depth=2 chars=144
/1         depth=1 chars=77
(root)     depth=0 chars=134
----

Here the root is reported last because `endDocument` fires when the whole parse is over; the default handler reorders it
to the front, a streaming handler does not. Create one handler per parse; handlers keep per-parse state (the depth
counter, the list), and the source of `RecursiveParserWrapper` itself says its per-call state is a step towards making
the wrapper thread safe in a future version, so treat wrapper and handler as one unit per parse. The wrapper is cheap
to create.

== Containment metadata

Tika writes a small family of keys to describe where each embedded document sits and what the container called it. The
4.1.x docs split them into two groups that are easy to confuse.

*Containment structure (written by Tika).* These answer "which document contained this one?".

[cols="3,3,3,5",options="header"]
|===
|`TikaCoreProperties` constant |4.x key |3.x key |Meaning

|`EMBEDDED_ID` |`tk:embedded-id` |`X-TIKA:embedded_id` |A 1-based counter assigned in the order the wrapper meets documents. Not set on the root.
|`EMBEDDED_ID_PATH` |`tk:embedded-id-path` |`X-TIKA:embedded_id_path` |The chain of ids from the root, such as `/1/2/3`. This is the field to use for tracking containment: it is unique and has no characters from a file name.
|`EMBEDDED_RESOURCE_PATH` |`tk:embedded-resource-path` |`X-TIKA:embedded_resource_path` |A synthetic, human-readable path built from the resource names at each level, such as `/samples.zip/chapter-one.docx/figure1.png`. Path separators inside a name are stripped.
|`FINAL_EMBEDDED_RESOURCE_PATH` |`tk:final-embedded-resource-path` |`X-TIKA:final_embedded_resource_path` |The same, computed at the end of the parse by `RecursiveParserWrapperHandler`, so it knows names that were only discovered after an object's children were parsed.
|`EMBEDDED_DEPTH` |`tk:embedded-depth` |`X-TIKA:embedded_depth` |0 for the root, 1 for its attachments, and so on. Set by the handler base class.
|`RESOURCE_NAME_KEY` |`tk:resource-name` |`resourceName` |The name a parser recorded. For archive entries this is the whole entry path, `notes/cover-note.txt`; elsewhere a bare file name. If nothing is known Tika invents `embedded-1.jpg`-style names.
|`EMBEDDED_RESOURCE_TYPE` |`tk:embedded-resource-type` |`embeddedResourceType` |`INLINE`, `ATTACHMENT` and the rest of the enum above, when the parser classifies.
|===

*Container metadata (what the file itself says).* These answer "where did the container store this?".

[cols="3,3,3,5",options="header"]
|===
|`TikaCoreProperties` constant |4.x key |3.x key |Meaning

|`INTERNAL_PATH` |`tk:internal-path` |`X-TIKA:internalPath` |The path as literally stored inside the immediate container: the ZIP entry (`notes/cover-note.txt`), the OOXML part name (`/word/media/figure1.png`), a PST folder and message name. It starts over at every container boundary.
|`ORIGINAL_RESOURCE_NAME` |`tk:orig-resource-name` |`X-TIKA:origResourceName` |For some formats, the path where a document was last saved on its author's machine, or the original name an attachment recorded.
|`EMBEDDED_RELATIONSHIP_ID` |`tk:embedded-relationship-id` |`embeddedRelationshipId` |The relationship id in an Office Open XML package, such as `rId10` for the picture above.
|===

The 3.x spellings of the keys in both tables were read from the `tika-core-3.3.0` sources (`X-TIKA:` prefix, snake_case
or camelCase words) and the 4.x spellings from the 4.1.0 sources, where `TIKA_META_PREFIX` is `tk:` and words are separated by hyphens.
The complete 3.x to 4.x key mapping is the subject of xref:backend/apache-tika/metadata.adoc[Metadata].

Source: https://tika.apache.org/docs/4.1.x/advanced/embedded-documents.html[Embedded Document Metadata, 4.1.x docs] and
https://tika.apache.org/docs/4.1.x/migration-to-4x/metadata-changes-4x.html[Metadata Changes in Tika 4.x].

|`figure1.png` |`/1/2/3` |`figure1.png` |`/word/media/figure1.png` |`/samples.zip/chapter-one.docx/figure1.png`
|`catalogue.pdf` |`/1/4` |`catalogue.pdf` |`catalogue.pdf` |`/samples.zip/catalogue.pdf`
|`notes/cover-note.txt` |`/1/5` |`notes/cover-note.txt` |`notes/cover-note.txt` |`/samples.zip/cover-note.txt`
|===

Notice three things. The root has no `tk:internal-path` because nothing contains it, and its `tk:resource-name` is a
display name the e-mail parser built from the subject, not a file name on disk. The text note has the entry path in
`tk:resource-name`, with the folder `notes/`, but `tk:embedded-resource-path` drops the folder: Tika keeps one path
component per nesting level. And the picture's `tk:internal-path` is the OOXML part name, which no longer mentions
`samples.zip`: each container only knows its own layout.

[WARNING]
====
Never build a file-system path from `tk:embedded-resource-path`, `tk:resource-name` or `tk:internal-path`. They come from
the file, so two entries can have the same name, a name can contain characters illegal on your file system, and an
archive entry can be called `../../etc/cron.d/job` (zip slip). The 4.1.x docs say the same about the synthetic path and
recommend `tk:embedded-id-path`. In the extractor below the output file name is a counter plus an extension that is
checked against a pattern, never the name from the file.
====

== The stateless EmbeddedDocumentExtractor

When a container parser (the ZIP parser, the PDF parser, the OOXML parser) finds an embedded document it does not parse
it itself. It asks the `ParseContext` for an `EmbeddedDocumentExtractor` and calls it twice: `shouldParseEmbedded` to
ask whether to bother, and `parseEmbedded` to do the work. The default implementation,
`ParsingEmbeddedDocumentExtractor`, delegates to the `Parser` that is in the context (that is what lets
`RecursiveParserWrapper` interpose its own decorator).

[source,java]
----
public interface EmbeddedDocumentExtractor {
    boolean shouldParseEmbedded(Metadata metadata, ParseContext parseContext);

    void parseEmbedded(TikaInputStream stream, ContentHandler handler, Metadata metadata,
                       ParseContext parseContext, boolean outputHtml) throws SAXException, IOException;
}
----

Source: https://tika.apache.org/4.1.0/api/org/apache/tika/extractor/EmbeddedDocumentExtractor.html[`EmbeddedDocumentExtractor`, Javadoc 4.1.0].

In Tika 4.x this interface is *stateless*. Every method receives the `ParseContext` of the enclosing parse, one shared
instance (`ParsingEmbeddedDocumentExtractor.INSTANCE`) serves every parse on every thread, and the interface's Javadoc
tells implementors not to cache per-parse state on `this`. In 3.x the extractor was created per parse by an
`EmbeddedDocumentExtractorFactory` that received the metadata and context, so implementations kept the per-parse state
(a counter, an output directory) in fields.

[cols="3,4,4",options="header"]
|===
|Aspect |3.x (3.3.0 sources) |4.x (4.1.0 sources)

|`shouldParseEmbedded` |`shouldParseEmbedded(Metadata)` |`shouldParseEmbedded(Metadata, ParseContext)`
|`parseEmbedded` |`parseEmbedded(InputStream, ContentHandler, Metadata, boolean)` |`parseEmbedded(TikaInputStream, ContentHandler, Metadata, ParseContext, boolean)`
|Lifecycle |`EmbeddedDocumentExtractorFactory.newInstance(Metadata, ParseContext)` made one per parse |No factory class in the 4.1.0 `tika-core` sources (searched for it and found no reference). Bind one shared instance with `+context.set(EmbeddedDocumentExtractor.class, ...)+`.
|Per-parse state |Fields on the extractor |A holder object in the `ParseContext`
|Limits |`RecursiveParserWrapperHandler(factory, maxEmbeddedResources)` |`EmbeddedLimits` in the `ParseContext`
|===

=== What the default extractor checks

`ParsingEmbeddedDocumentExtractor.shouldParseEmbedded` and `parseEmbedded` apply, in this order, using the `ParseRecord`
and other objects that the parse put in the context:

[mermaid]
....
flowchart TD
    A["Container parser found an embedded document"] --> B{"Task deadline reached?<br/>(timeout-limits)"}
    B -->|yes| X["Skip it. Throw EmbeddedLimitReachedException<br/>only if throwOnDeadline"]
    B -->|no| C{"embedded count >= maxCount?"}
    C -->|yes| X2["Skip it and every later one<br/>tk:exception:embedded-resource-limit-reached"]
    C -->|no| D{"depth + 1 > maxDepth?"}
    D -->|yes| X3["Skip it, siblings still parse<br/>tk:exception:embedded-depth-limit-reached"]
    D -->|no| E{"DocumentSelector in context<br/>and select(metadata) false?"}
    E -->|yes| X4["Skip it"]
    E -->|no| F{"FilenameFilter in context<br/>and name rejected?"}
    F -->|yes| X5["Skip it"]
    F -->|no| G["Parse with the Parser in the context<br/>output a div class package-entry if outputHtml"]
....

The selection hooks are therefore ordinary context entries:

* `DocumentSelector` (`org.apache.tika.extractor`) is a one-method interface, `boolean select(Metadata metadata)`.
  It sees the metadata the container parser has gathered so far, usually the resource name and, sometimes, the media
  type. It is the right place to skip images or executables, and it is what the example below uses.
* `java.io.FilenameFilter` is consulted when no `DocumentSelector` is present; Tika calls it with an empty `File` and
  the resource name.
* The 4.1.0 source comment says subclasses that override `parseEmbedded` should call `checkEmbeddedLimits`, so a custom
  extractor does not accidentally disable limits.

When the embedded parse itself fails, `parseEmbedded` records the exception in the `ParseRecord`, which the wrapper
copies to the document's metadata, and moves on. `CorruptedFileException` is the exception to that rule: it is wrapped
in an `IOException` and stops the whole parse, "to avoid infinite loops on corrupt sqlite3 files", as a source comment
puts it.

=== Skipping documents: DocumentSelector and limits in action

The program below parses `publisher-email.eml` five times: with no limit, with `maxDepth=2`, with `maxCount=3`, with a
`DocumentSelector` that refuses images, and with a throwing count limit. It prints the id path and the final resource
path of each object.

[source,java]
----
import java.io.IOException;
import java.nio.file.Path;
import java.util.List;

import org.apache.tika.config.EmbeddedLimits;
import org.apache.tika.exception.TikaException;
import org.apache.tika.extractor.DocumentSelector;
import org.apache.tika.io.TikaInputStream;
import org.apache.tika.metadata.Metadata;
import org.apache.tika.metadata.TikaCoreProperties;
import org.apache.tika.parser.AutoDetectParser;
import org.apache.tika.parser.ParseContext;
import org.apache.tika.parser.RecursiveParserWrapper;
import org.apache.tika.sax.BasicContentHandlerFactory;
import org.apache.tika.sax.RecursiveParserWrapperHandler;
import org.xml.sax.SAXException;

public class LimitsAndSelection {

    static List<Metadata> parse(Path file, ParseContext context)
            throws IOException, SAXException, TikaException {
        RecursiveParserWrapper wrapper = new RecursiveParserWrapper(new AutoDetectParser());
        RecursiveParserWrapperHandler handler = new RecursiveParserWrapperHandler(
                new BasicContentHandlerFactory(BasicContentHandlerFactory.HANDLER_TYPE.IGNORE, -1));
        try (TikaInputStream tis = TikaInputStream.get(file)) {
            wrapper.parse(tis, handler, new Metadata(), context);
        }
        return handler.getMetadataList();
    }

    public static void main(String[] args) throws Exception {
        Path eml = Path.of(args[0]);

        ParseContext depth = new ParseContext();
        depth.set(EmbeddedLimits.class, new EmbeddedLimits(2, false, -1, false));   // maxDepth 2

        ParseContext count = new ParseContext();
        count.set(EmbeddedLimits.class, new EmbeddedLimits(-1, false, 3, false));   // maxCount 3

        ParseContext select = new ParseContext();
        select.set(DocumentSelector.class, metadata -> {
            String type = metadata.get("Content-Type");
            return type == null || !type.startsWith("image/");
        });

        ParseContext strict = new ParseContext();
        strict.set(EmbeddedLimits.class, new EmbeddedLimits(-1, false, 2, true));   // throw at the 3rd

        for (ParseContext context : List.of(new ParseContext(), depth, count, select)) {
            for (Metadata m : parse(eml, context)) {
                System.out.printf("   %-10s %s%n", m.get(TikaCoreProperties.EMBEDDED_ID_PATH),
                        m.get(TikaCoreProperties.FINAL_EMBEDDED_RESOURCE_PATH));
            }
            System.out.println();
        }
        try {
            parse(eml, strict);
        } catch (Exception e) {
            System.out.println(e.getClass().getName() + ": " + e.getMessage());
        }
    }
}
----

Source: https://tika.apache.org/docs/4.1.x/advanced/setting-limits.html[Setting Limits, 4.1.x docs],
https://tika.apache.org/4.1.0/api/org/apache/tika/config/EmbeddedLimits.html[`EmbeddedLimits`, Javadoc 4.1.0] and
https://tika.apache.org/4.1.0/api/org/apache/tika/extractor/DocumentSelector.html[`DocumentSelector`, Javadoc 4.1.0].

The real results (the first line of each group is the root, which has no paths):

[[embedded-limits]]
== Embedded limits

Untrusted containers can be nested thousands of levels deep or hold millions of tiny entries. In 4.x the bounds are
configured in the `parse-context` section of the JSON configuration (`TikaLoader`) or, in code, as an `EmbeddedLimits`
object in the `ParseContext`.

[cols="2,2,6",options="header"]
|===
|`embedded-limits` key |Default |Meaning

|`maxDepth` |`-1`, unlimited |The deepest nesting that is parsed. Recursion stops at the limit; siblings at the current level still parse. With `maxDepth` 1 the children of a depth-1 document are not parsed, but its depth-1 siblings are.
|`throwOnMaxDepth` |`false` |Throw `EmbeddedLimitReachedException` at `maxDepth` instead of continuing and setting `tk:exception:embedded-depth-limit-reached` to `true`.
|`maxCount` |`-1`, unlimited |The maximum total number of embedded documents. Processing stops immediately when it is reached, including siblings.
|`throwOnMaxCount` |`false` |Throw at `maxCount` instead of continuing and setting `tk:exception:embedded-resource-limit-reached` to `true`.
|===

[source,json]
----
{
  "parsers": [
    { "default-parser": {} }
  ],
  "parse-context": {
    "embedded-limits": {
      "maxDepth": 2,
      "throwOnMaxDepth": false,
      "maxCount": 100,
      "throwOnMaxCount": false
    }
  }
}
----

[source,java]
----

        ParseContext context = loader.loadParseContext();               // carries EmbeddedLimits
        RecursiveParserWrapper wrapper = new RecursiveParserWrapper(loader.loadAutoDetectParser());

                new BasicContentHandlerFactory(BasicContentHandlerFactory.HANDLER_TYPE.IGNORE, -1));

Other bounds that apply to a container and its children, all covered in
xref:backend/apache-tika/introduction-and-architecture.adoc[Introduction & Architecture] and elsewhere in this
section:

* `output-limits` (`writeLimit`, `zipBombThreshold`, `zipBombRatio`, `maxPackageEntryDepth`, `maxXmlDepth`): the 4.1.x
  docs list these, with defaults, as bounds on the extracted characters and on structural expansion. They are not run
  on this page.
* `timeout-limits` (`totalTaskTimeoutMillis`, one hour by default, and `progressTimeoutMillis`, two minutes by default):
  the total budget covers the container and every embedded document. When it is spent, the remaining embedded documents
  are skipped and reported as partial rather than failing the parse, unless `throwOnDeadline` is true. The stall
  detector kills a task only in a forked JVM (Tika Pipes or tika-app `--fork`).
* `unpack-config.maxUnpackBytes`, bounding the bytes written when you extract the embedded files, below.

== Extracting the embedded bytes

Parsing an attachment is not the same as getting the attachment back. The intake service wants to store the original
`catalogue.pdf` so a reviewer can open it. In 4.x there are four routes, from lowest to highest level.

=== A custom extractor in Java

The extractor is the place to write the bytes, because it receives the `TikaInputStream` of each embedded document
before it is parsed. This one saves every embedded document under a counter-based name, then lets Tika parse it as
usual. Note how the per-parse state (the output directory and the counter) lives in a record placed in the
`ParseContext`, not in the extractor, to respect the stateless contract.

[source,java]
----
import java.io.IOException;
import java.nio.file.Files;
import java.nio.file.Path;
import java.nio.file.StandardCopyOption;
import java.util.concurrent.atomic.AtomicInteger;
import java.util.regex.Pattern;

import org.apache.tika.exception.TikaException;
import org.apache.tika.extractor.EmbeddedDocumentExtractor;
import org.apache.tika.extractor.ParsingEmbeddedDocumentExtractor;
import org.apache.tika.io.TikaInputStream;
import org.apache.tika.metadata.Metadata;
import org.apache.tika.metadata.TikaCoreProperties;
import org.apache.tika.parser.AutoDetectParser;
import org.apache.tika.parser.ParseContext;
import org.apache.tika.parser.RecursiveParserWrapper;
import org.apache.tika.sax.BasicContentHandlerFactory;
import org.apache.tika.sax.RecursiveParserWrapperHandler;
import org.xml.sax.ContentHandler;
import org.xml.sax.SAXException;

/** Saves the bytes of every embedded document, then lets Tika parse it as usual. */
public class SaveAttachments {

    /** Per-parse state lives in the ParseContext, never in the (shared) extractor. */
    record SaveState(Path outDir, AtomicInteger counter) { }

    /** Stateless: one instance can serve every parse on every thread. */
    static class SavingExtractor implements EmbeddedDocumentExtractor {
        private static final Pattern SAFE_EXTENSION = Pattern.compile("[A-Za-z0-9]{1,8}");

        @Override
        public boolean shouldParseEmbedded(Metadata metadata, ParseContext context) {
            return ParsingEmbeddedDocumentExtractor.INSTANCE.shouldParseEmbedded(metadata, context);
        }

        @Override
        public void parseEmbedded(TikaInputStream stream, ContentHandler handler, Metadata metadata,
                                  ParseContext context, boolean outputHtml)
                throws SAXException, IOException {
            SaveState state = context.get(SaveState.class);
            if (state != null) {
                String target = String.format("%03d%s", state.counter().incrementAndGet(),
                        extensionOf(metadata.get(TikaCoreProperties.RESOURCE_NAME_KEY)));
                // getPath() spools the stream to a temporary file when needed;
                // the stream stays usable for the parse that follows
                Files.copy(stream.getPath(), state.outDir().resolve(target),
                        StandardCopyOption.REPLACE_EXISTING);
            }
            ParsingEmbeddedDocumentExtractor.INSTANCE.parseEmbedded(
                    stream, handler, metadata, context, outputHtml);
        }

        private static String extensionOf(String resourceName) {
            if (resourceName == null) {
                return ".bin";
            }
            int dot = resourceName.lastIndexOf('.');
            String ext = dot < 0 ? "" : resourceName.substring(dot + 1);
            return SAFE_EXTENSION.matcher(ext).matches() ? "." + ext.toLowerCase() : ".bin";
        }
    }

    public static void main(String[] args) throws IOException, SAXException, TikaException {
        Path outDir = Files.createDirectories(Path.of(args[1]));

        ParseContext context = new ParseContext();
        context.set(EmbeddedDocumentExtractor.class, new SavingExtractor());
        context.set(SaveState.class, new SaveState(outDir, new AtomicInteger()));

        RecursiveParserWrapper wrapper = new RecursiveParserWrapper(new AutoDetectParser());
        RecursiveParserWrapperHandler handler = new RecursiveParserWrapperHandler(
                new BasicContentHandlerFactory(BasicContentHandlerFactory.HANDLER_TYPE.IGNORE, -1));

        try (TikaInputStream tis = TikaInputStream.get(Path.of(args[0]))) {
            wrapper.parse(tis, handler, new Metadata(), context);
        }
    }
}
----

Source: https://github.com/apache/tika/blob/main/tika-example/src/main/java/org/apache/tika/example/ExtractEmbeddedFiles.java[`ExtractEmbeddedFiles`, tika-example]
(the official example this one is modelled on, written for the pre-4.x extractor),
https://tika.apache.org/4.1.0/api/org/apache/tika/extractor/ParsingEmbeddedDocumentExtractor.html[`ParsingEmbeddedDocumentExtractor`, Javadoc 4.1.0]
and _Tika in Action_, chapter 5 (recursive parsing and extracting embedded documents).

Output (listing the output directory):

Four details of this extractor are choices, not requirements:

* It names files with its own counter. In this run the counter matches `tk:embedded-id` (`003.png` is `/1/2/3`), but
  the extractor runs before the wrapper assigns the id, so the two counters are separate and agree only because both
  follow the same depth-first order. If you must link a saved file to its list entry, record the `tk:embedded-id-path`
  after the parse, or use one of the built-in routes below.
* It saves every embedded document, including the intermediate `samples.zip` and the `chapter-one.docx`. Add a
  `tk:embedded-resource-type` or media-type check to save only the leaf attachments you need.
* `getPath()` on the stream makes Tika spool a one-way stream to a temporary file. When the stream is already a file,
  or was already spooled for detection, it costs nothing; otherwise you pay one disk copy per embedded document.
* The extension comes from the resource name, checked against a small pattern. `notes/cover-note.txt` becomes `.txt`;
  a name without a safe extension becomes `.bin`.

=== tika-app -J, -z and -Z

The tika-app command line covers the common cases without code. `-J` (`--jsonRecursive`) prints the same list of metadata
as JSON, with content, to standard output. `-z` extracts the direct attachments (depth 1) and `-Z` every level. In 4.x
both of those run in Tika Pipes, so they use forked JVMs, and they take an input _directory_ (or file) and an output

https://tika.apache.org/docs/4.1.x/pipes/unpack-config.html[unpack-config, 4.1.x docs]. The excerpt keeps two of the
five resources.

The `-z` and `-Z` flag table, from the 4.1.x CLI page:

[cols="3,6",options="header"]
|===
|Flag |Meaning

|`-z`, `--extract` |Extract direct attachments (depth 1).
|`-Z` |Extract all attachments recursively.
|`--extract-dir=<dir>` |Output directory for the bytes; equivalent to `-o`.
|`--unpack-format=<format>` |`REGULAR` (default) or `FRICTIONLESS`.

=== unpack-config and the UNPACK parse mode

In Tika Pipes (and so in tika-server `/pipes` and `/async`, and in tika-app with a configuration file) extraction is
switched on by the parse mode and tuned by an `unpack-config` block. This is from the 4.1.x docs; it was not run on
this page, only its CLI counterparts were.

[source,json]
----
{
  "pipes": {
    "parseMode": "UNPACK"
  },
  "parse-context": {
    "unpack-config": {
      "maxUnpackBytes": 104857600,
      "zipEmbeddedFiles": true,
      "includeMetadata": true,
      "suffixStrategy": "DETECTED"
    }
  }
}
----

Source: https://tika.apache.org/docs/4.1.x/pipes/unpack-config.html[unpack-config: Extracting Embedded Document Bytes, 4.1.x docs].

[cols="3,3,2,6",options="header"]
|===
|`unpack-config` field |Type |Default |Meaning

|`emitter` |String |from the `FetchEmitTuple` |Emitter name for the embedded bytes.
|`maxUnpackBytes` |long |10 GiB |Total bytes extracted per file. `-1` is unlimited, not recommended; `0` means zero bytes, not unlimited.
|`includeOriginal` |boolean |`false` |Also emit the container itself.
|`zipEmbeddedFiles` |boolean |`false` |Collect the embedded files in one ZIP emitted at the container's key plus `-embedded.zip`.
|`includeMetadata` |boolean |on for Frictionless, off for REGULAR |Metadata for every extracted file: one `metadata.json` (Frictionless) or a `.metadata.json` sidecar per file (REGULAR zip output). The older names `includeMetadataInZip` and `includeFullMetadata` are deprecated aliases, to be removed in 5.0.
|`zeroPadName` |int |0 |Zero-pad ids in names; `8` gives `00000001`.
|`suffixStrategy` |`NONE`, `EXISTING`, `DETECTED` |`NONE` |How extensions are decided: none, from the embedded resource name, or from the detected media type.
|`keyBaseStrategy` |`DEFAULT`, `CUSTOM` |`DEFAULT` |`DEFAULT` writes `<containerKey>-embed/<id><suffix>`; `CUSTOM` writes `<emitKeyBase><embeddedIdPrefix><id><suffix>`.
|`emitKeyBase`, `embeddedIdPrefix` |String |empty, `-` |Used only by `CUSTOM`.
|`outputFormat` |`REGULAR`, `FRICTIONLESS` |`REGULAR` |Frictionless adds `datapackage.json` with SHA-256 hashes and media types. The 4.x home page says the default is planned to change to Frictionless in 4.2.0.
|`outputMode` |`ZIPPED`, `DIRECTORY` |`ZIPPED` |One archive, or each file emitted as its own item. `DIRECTORY` is refused on tika-server `/unpack`.
|===

Hitting `maxUnpackBytes` is quiet: the file being written is truncated at the remaining budget, later embedded files are
skipped, a `WARN` is logged, and nothing is stamped on the metadata or the result status. Watch the log, not the status.
Those are the 4.1.x docs' words, and they matter for untrusted input, where you should lower the 10 GiB default.

=== tika-server /unpack and /rmeta

tika-server exposes the same two views over HTTP. These endpoints were not run for this page, since no server was
started; they are listed in the 4.1.x server and FAQ pages.

[source,bash]
----
# the list of metadata, as JSON; Markdown content by default in 4.x
curl -T publisher-email.eml http://localhost:9998/rmeta

# the same with plain text content
curl -T publisher-email.eml http://localhost:9998/rmeta/text

# the embedded files as one zip, and with the metadata and the original
curl -T publisher-email.eml http://localhost:9998/unpack -o unpacked.zip
curl -T publisher-email.eml http://localhost:9998/unpack/all -o unpacked-all.zip
----

Source: https://tika.apache.org/docs/4.1.x/using-tika/server/index.html[tika-server, 4.1.x docs] and
https://tika.apache.org/docs/4.1.x/migration-to-4x/migrating-to-4x.html[Migrating to Tika 4.x]. The `/rmeta` and
`/unpack` endpoints, with their 429 and 503 behaviour, are the subject of the
xref:backend/apache-tika/tika-server-rest-api.adoc[Tika Server (REST API)] page of
this section; the `/rmeta/text`
and `/unpack/all` forms above are taken from the 4.1.x docs' descriptions and have not been executed here.

In 4.x `/rmeta`, `/tika`, `/meta` and `/unpack` parse in a fixed pool of forked JVMs, so a saturated pool answers 429
and a crashed fork 503. The old 3.x endpoints `/tika/main` and `/tika/form` and the translate endpoint were removed.

[[failures-in-embedded-documents]]
== Failures inside embedded documents

A damaged attachment should not cost you the e-mail. With `catchEmbeddedExceptions` true, the default,
`RecursiveParserWrapper` catches the `TikaException` or `SAXException` that an embedded parse throws, records it in the
document's metadata and carries on. The error ends up in `tk:exception:embedded-exception`, a multi-valued key on that
document's own object; the container's exception, if any, is in `tk:exception:container-exception`.

[source,java]
----
for (Metadata m : handler.getMetadataList()) {
    String error = m.get(TikaCoreProperties.EMBEDDED_EXCEPTION);
    if (error == null) {
        error = m.get(TikaCoreProperties.CONTAINER_EXCEPTION);
    }
    System.out.printf("%-8s %-14s %s%n", m.get(TikaCoreProperties.EMBEDDED_ID_PATH),
            m.get(TikaCoreProperties.RESOURCE_NAME_KEY),
            error == null ? "ok" : error.lines().findFirst().orElse(""));
}
----

Source: https://tika.apache.org/4.1.0/api/org/apache/tika/metadata/TikaCoreProperties.html[`TikaCoreProperties`, Javadoc 4.1.0].

Run against a ZIP built for the purpose, with a good PDF, a DOCX cut in half and a PDF with an `/Encrypt` entry but no
real encryption dictionary:

[source,text]
----
null     null           ok
/1       good.pdf       ok
/2       truncated.docx org.apache.tika.exception.TikaException: No OOXML extractor found for content type: null
/3       locked.pdf     org.apache.tika.exception.TikaException: TIKA-198: Illegal IOException from org.apache.tika.parser.pdf.PDFParser@49601f82
----

The first row is the ZIP root, which parsed correctly; the second and third rows carry the embedded exceptions; the
good PDF was unaffected. The run also logged a long XML parser stack trace to the error stream for the truncated DOCX,
which comes from the POI detector's attempt to open the damaged package and not from your code. Two further points:

* A mere warning goes in `tk:exception:embedded-warning`, and an exception while saving the embedded _bytes_ (the
  `unpack` routes) goes in `tk:exception:embedded-bytes-exception`.
* `new RecursiveParserWrapper(parser, false)` rethrows embedded exceptions and stops the parse. The javadoc of that
  constructor says `CorruptedFileException` and runtime exceptions are never swallowed in either mode. Use it in a test
  suite that must fail loudly, not in an intake service.
* An encrypted attachment sets `tk:encrypted` to `true`; password handling is its own topic, with a
  `PasswordProvider` in the parse context.

== The 4.1 hooks for components that enrich embedded documents

Two small classes were added in 4.1 so that a component which writes results *after* a document has ended, such as the
inference engines that tag pictures, can find the right metadata object:

* `ParentMetadata` is put in the `ParseContext` for the duration of a child's parse. It holds the metadata of the
  document the child belongs to, so a picture's result can be written on the page it appears on.
* `EmbeddedMetadataLookup` is set for the duration of the top-level parse. Its `kept(idPath)` returns the metadata the
  handler kept for an embedded document, using `AbstractRecursiveParserWrapperHandler.getEmbeddedMetadata(idPath)`,
  which the default handler implements and a custom streaming handler may leave returning `null`.

You do not need either to use embedded documents; they matter if you write a parser or filter that annotates
embedded documents late. Both are marked `@since Apache Tika 4.1` in the 4.1.0 sources.

== Performance, memory and robustness

* *Memory.* The default handler holds all text. Use `IGNORE` where you only need metadata, a `writeLimit`, a streaming
  handler, or the Pipes route that emits each document as it finishes.
* *Disk.* Container formats are random access, so embedded streams may be spooled to a temporary file. The 4.1.0 release
  notes say 4.1 spools to disk less often; the extractor above forces a spool through `getPath()`.
* *Time.* The embedded parse time is part of the container's. The ZIP above took 365 ms in total, of which about 187 ms
  was the DOCX and 177 ms the PDF; the first parse in a JVM also loads the parser classes, so measure on a warm JVM.
* *Isolation.* An OOM or native crash in an embedded parser kills the in-process parse of everything. Containers from
  outside are the main reason to run Tika in forked JVMs (Tika Pipes, tika-server). This is the subject of
  xref:backend/apache-tika/introduction-and-architecture.adoc[Introduction & Architecture] and later pages.
* *Quines and bombs.* A ZIP that contains itself, or a 42 KB file that expands to gigabytes, is exactly what
  `maxDepth`, `maxCount`, `output-limits` and `unpack-config.maxUnpackBytes` are for. Set all four for untrusted input,
  not just one.

== Pitfalls

* *Assuming the list is a pre-order tree.* It is the container first and then post-order; rebuild the tree from
  `tk:embedded-id-path`.
* *Treating ids as stable.* They depend on limits and selectors (see the `maxDepth=2` run, where the PDF changed from
  `/1/4` to `/1/3`). Do not use them as database keys across configurations.
* *Writing files under `tk:embedded-resource-path` or `tk:resource-name`.* Zip slip and name collisions; use the id,
  as in the extractor above.
* *Using `BodyContentHandler` and expecting attachments to be separate.* They are merged into the text and the metadata
  of the container only.
* *Setting no limits on untrusted input.* The defaults are unlimited depth and count.
* *Forgetting that the write limit is shared.* One large attachment may use the whole budget for every sibling after it.
* *Ignoring the `+tk:exception:*+` keys.* A parse that returns normally can still have skipped or failed documents. Check
  the keys, or count the objects against what you expected.
* *Keeping per-parse state in an extractor field.* In 4.x the instance is shared across threads. Use the `ParseContext`.
* *Reusing 3.x code.* `EmbeddedDocumentExtractorFactory`, the 4-argument `+parseEmbedded(InputStream, ...)+` and
  `RecursiveParserWrapperHandler(factory, maxEmbeddedResources)` are 3.x idioms.

== What changed from the book to 4.x

[cols="3,3,3,4",options="header"]
|===
|Topic |_Tika in Action_ (1.x, 2011) |3.x |4.x

|Recursion |`context.set(Parser.class, parser)` in the book's recipe; embedded text is merged |`RecursiveParserWrapper` and `RecursiveParserWrapperHandler` |Same classes; `AutoDetectParser` sets `Parser` itself; the wrapper also sets `ParentMetadata` and `EmbeddedMetadataLookup` (4.1)
|Choosing what to parse |a custom `EmbeddedDocumentExtractor` |`EmbeddedDocumentExtractorFactory`, `DocumentSelector`, `FilenameFilter` |Shared stateless extractor in the context; `DocumentSelector`, `FilenameFilter`; no factory class
|Limits |not covered |`maxEmbeddedResources` on the handler |`EmbeddedLimits` (`maxDepth`, `maxCount`, throw flags) in the `ParseContext`, JSON `embedded-limits`
|Keys |not covered, a counter in your own code |`X-TIKA:embedded_id_path`, `X-TIKA:embedded_resource_path`, `resourceName` |`tk:embedded-id-path`, `tk:embedded-resource-path`, `tk:resource-name` (`LegacyKeyMigrationFilter` restores the old names)
|Extraction of bytes |your own extractor |your own extractor, tika-app and tika-server `/unpack` |`unpack-config`, `ParseMode.UNPACK`, `-z` and `-Z` through Pipes, Frictionless output
|Server and CLI |not covered |`/rmeta` returned XML content by default; `-J` on tika-app |`/rmeta` returns Markdown by default and parses in forked JVMs (429 and 503); `-J`, `-z` and `-Z` as above
|===

== What the docs do not provide

* The 4.1.x docs describe embedded metadata keys and the unpack configuration in detail but have no prose on using
