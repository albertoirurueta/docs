A vision-language model (VLM) reads an image and answers in text. Tika 4.x uses one in two ways. As a **text
recognizer**, a VLM takes Tesseract's place: it transcribes a scanned page or an embedded picture into Markdown, which
Tika turns into XHTML and adds to the document text. As an **inference engine**, a model produces something other than
text, today an embedding vector, for the extracted text, the pictures, the rendered pages or the audio and video of a
document tree; the vectors land in the `tk:chunks` metadata field, ready for a vector index. This page covers both, for
the _Bookshelf_ intake service that receives manuscripts, catalogues, scanned loan forms and book covers.

xref:backend/apache-tika/pdf-parsing.adoc[PDF Parsing] (the `pages` block that decides when a page is rendered),

== Where VLMs and inference fit

The two features answer different questions, and 4.1 configures them in different sections of `tika-config.json`:

[cols="2,3,3",options="header"]
|===
| |Text recognizer (OCR by a VLM) |Inference (embeddings)

|Question |What does this picture _say_? |What is this text, picture, page or clip _like_?
|Output |Text, merged into the document's content (`tk:content` in recursive output) |A vector per unit, in `tk:chunks`
|Config sections |`engines` + `text-recognizers` |`engines` + `inference` (+ `pages.inference` for PDFs)
|Engine types |`openai-vlm-parser`, `claude-vlm-parser`, `gemini-vlm-parser` (and `tesseract-ocr-parser`, `tess4j-parser`) |`openai-embedding-engine`
|Who calls it |The image parser and the PDF parser, as they meet an image or render a page |One dispatcher, after the parse of the whole document tree
|Module |`tika-vlm` |`tika-inference` (dispatcher and SPI in `tika-core`)
|Status in 4.1.0 |Experimental classes; the `text-recognizers` list is stable |Experimental
|===

Both start from the same `engines` map: a name you choose, mapped to one engine type and its settings. An engine knows
nothing about documents. A `text-recognizers` entry or an `inference` binding names the engine and says what it is fed.
Two names may point at the same endpoint with different models, and secrets live only in the engine entry.

The flow, from a _Bookshelf_ document to text and vectors:

[mermaid]
....
flowchart LR
    doc["Document<br/>(scanned-loan-form.pdf, manuscript.docx, book-cover.jpg)"] --> parse["AutoDetectParser<br/>parses the tree"]
    parse --> units{"Units released"}
    units -->|"rendered pages<br/>(pages.text = AUTO or OCR)"| rec["Text recognizer engine<br/>openai / claude / gemini VLM"]
    units -->|"embedded and top-level images"| rec
    units -->|"PAGES (pages.inference)"| emb["Inference engine<br/>openai-embedding-engine"]
    units -->|"IMAGES, MEDIA segments"| emb
    parse -->|"after parse: tk:content of every document"| chunk["markdown-chunker<br/>(TEXT binding)"]
    chunk --> emb
    rec -->|"Markdown answer to XHTML"| text["Text<br/>tk:content, vlm:* keys"]
    emb -->|"one vector per unit"| vec["Vectors<br/>tk:chunks with locators"]
    text --> out["Metadata list<br/>(-J, /rmeta, Pipes RMETA)"]
    vec --> out
....

The diagram shows the order that matters. A recognizer runs _during_ the parse, as the PDF or image parser meets each
page or picture, so its text is part of the document text. Inference runs _after_ the walk of the tree: images, pages
and media are flushed at the end of the top-level parse, and the TEXT stage runs over the finished metadata list. That
is why text vectors are computed from the text the recognizer produced.

Source: https://tika.apache.org/docs/4.1.x/configuration/index.html[Configuration, 4.1.x docs] (the `text-recognizers`
list) and https://tika.apache.org/docs/4.1.x/configuration/inference.html[Inference: engines and bindings, 4.1.x docs].

== Modules and dependencies

`tika-vlm` holds the three VLM parsers and the Markdown-to-XHTML emitter. `tika-inference` holds the embedding engine,
the Markdown chunker and the deprecated 4.0 embedding filters. Both live under `tika-parsers-ml` and are **not** part of
`tika-parsers-standard-package`, so a library user adds them explicitly. Both depend on `tika-http-jdk`, Tika's small
client over the JDK `HttpClient`; no vendor SDK is pulled in. `tika-vlm` also brings commonmark-java (with the GFM tables
and strikethrough extensions) and jsoup for the Markdown and HTML conversion.

== The three VLM parsers

All three extend `AbstractVLMParser`, share one configuration class (`VLMOCRConfig`) and implement `TextRecognizer`.
They differ in the wire format, the authentication and the media types they accept.

[cols="2,3,3,3",options="header"]
|===
| |`OpenAIVLMParser` |`ClaudeVLMParser` |`GeminiVLMParser`

|Config key |`openai-vlm-parser` |`claude-vlm-parser` |`gemini-vlm-parser`
|Endpoint |Any OpenAI-compatible chat completions API: vLLM, Ollama, LiteLLM, a FastAPI wrapper, OpenAI, Azure OpenAI |Anthropic Messages API (`/v1/messages`) |Google Gemini `generateContent` (`+/v1beta/models/{model}:generateContent+`)
|Default `baseUrl` |`http://127.0.0.1:8000` |`https://api.anthropic.com` |`https://generativelanguage.googleapis.com`
|Default `model` |`jinaai/jina-vlm` |`claude-sonnet-4-20250514` |`gemini-2.5-flash`
|Authentication |`Authorization: Bearer <apiKey>`; no header when `apiKey` is empty |`x-api-key` header, plus `anthropic-version: 2023-06-01` |`key` query parameter on the URL
|Startup health check |`+GET {baseUrl}/v1/models+`, skipped when `completionsPath` is not the default |None |`+GET {baseUrl}/v1beta/models?key=...+`
|Image types |png, jpeg, tiff, bmp, gif, jp2, jpx, x-portable-pixmap, webp |png, jpeg, gif, webp |png, jpeg, tiff, bmp, gif, jp2, jpx, x-portable-pixmap, webp, heic, heif
|PDF |No |`application/pdf` as a `document` block (deprecated route, below) |`application/pdf` (deprecated route, below)
|Token counts read from |`usage.prompt_tokens`, `usage.completion_tokens` |`usage.input_tokens`, `usage.output_tokens` |`usageMetadata.promptTokenCount`, `candidatesTokenCount`
|===

Source: the `OpenAIVLMParser`, `ClaudeVLMParser` and `GeminiVLMParser` 4.1.0 sources and
https://tika.apache.org/4.1.0/api/org/apache/tika/parser/vlm/AbstractVLMParser.html[`AbstractVLMParser` Javadoc]. The
defaults are the values in the constructors; the model names are whatever the project chose for 4.1.0 and are not a
recommendation. Set `model` explicitly, because vendors retire model identifiers on their own schedule.

Every parse writes three metadata keys, all in the `vlm:` namespace (`AbstractVLMParser.VLM_META`):

[cols="2,2,4",options="header"]
|===
|Key |Type |Meaning
|`vlm:model` |text |The `model` the request used.
|`vlm:prompt-tokens` |integer |Input tokens the endpoint reported (the image counts here).
|`vlm:completion-tokens` |integer |Output tokens the endpoint reported.
|===

The token counts are the only cost signal Tika gives you. Aggregate them per document and per day; see
<<cost-privacy-residency>>.

== Configuring a VLM as a text recognizer

The 4.1 shape names the engine once under `engines` and lists it in `text-recognizers`. Every default parser stays
loaded; the image parser and the PDF parser call the recognizer for the bytes they have already parsed.

=== A local OpenAI-compatible model (run)

This is the configuration the intake service uses on a workstation, against a model served on the same machine. The
key is optional for a local server; it is shown read from the environment because a shared vLLM or LiteLLM gateway
usually wants one.

[source,json]
----
{
  "engines": {
    "local-vlm": {
      "openai-vlm-parser": {
        "baseUrl": "http://127.0.0.1:8000",
        "model": "mock-vlm",
        "apiKey": "${env:BOOKSHELF_VLM_KEY}",
        "timeoutMillis": 600000,
        "maxTokens": 4096
      }
    }
  },
  "text-recognizers": [ { "engine": "local-vlm" } ]
}
----

`+${env:NAME}+` is the 4.1 environment interpolation: the loader replaces it with the variable's value when the file is
read. Only that exact form is touched (`+${NAME}+`, `$NAME` and `+${sys:...}+` stay literal), the forked workers of
tika-server and Pipes inherit the variable, and per-request configuration can never read the server's environment. A
missing variable stops the load with its name and JSON path, never a value. The run without the variable failed with:

[source,text]
----
org.apache.tika.exception.TikaConfigException: environment variable BOOKSHELF_VLM_KEY is not set;
referenced at /engines/local-vlm/openai-vlm-parser/apiKey
----

The Java program loads that file, parses the cover and prints what the recognizer added:

[source,java]
----
import java.nio.file.Path;

import org.apache.tika.config.loader.TikaLoader;
import org.apache.tika.io.TikaInputStream;
import org.apache.tika.metadata.Metadata;
import org.apache.tika.parser.ParseContext;
import org.apache.tika.parser.RecursiveParserWrapper;
import org.apache.tika.sax.BasicContentHandlerFactory;
import org.apache.tika.sax.RecursiveParserWrapperHandler;

public class VlmIntake {
    public static void main(String[] args) throws Exception {
        TikaLoader loader = TikaLoader.load(Path.of(args[0]));              // tika-config.json
        RecursiveParserWrapper parser = new RecursiveParserWrapper(loader.loadAutoDetectParser());
        ParseContext context = loader.loadParseContext();
        RecursiveParserWrapperHandler handler = new RecursiveParserWrapperHandler(
                new BasicContentHandlerFactory(BasicContentHandlerFactory.HANDLER_TYPE.MARKDOWN, -1));
        try (TikaInputStream tis = TikaInputStream.get(Path.of(args[1]))) {  // book-cover.jpg
            parser.parse(tis, handler, new Metadata(), context);
        }
        for (Metadata m : handler.getMetadataList()) {
            System.out.println("Content-Type          : " + m.get("Content-Type"));
            System.out.println("tk:parsed-by          : " + String.join(", ", m.getValues("tk:parsed-by")));
            System.out.println("vlm:model             : " + m.get("vlm:model"));
            System.out.println("vlm:prompt-tokens     : " + m.get("vlm:prompt-tokens"));
            System.out.println("vlm:completion-tokens : " + m.get("vlm:completion-tokens"));
            System.out.println("tk:content            :\n" + m.get("tk:content"));
        }
    }
}
----

=== Azure OpenAI and custom paths

`OpenAIVLMParser` has a `completionsPath` (default `/v1/chat/completions`) for endpoints whose path differs, such as an
Azure deployment (`+/openai/deployments/{deployment}/chat/completions?api-version=...+`). A non-default path also turns
the `/v1/models` probe off. Azure wants the key in an `api-key` header with no `Bearer` prefix. The Java class has
`setApiKeyHeaderName` and `setApiKeyPrefix` for that, but in 4.1.0 those two are **not** JSON keys: adding them to the
engine entry failed the load with

[source,text]
----
Unrecognized field "apiKeyHeaderName" (class org.apache.tika.parser.vlm.VLMOCRConfig), not marked as ignorable
(15 known properties: "inlineContent", "maxRetries", "prompt", "apiKey", "timeoutMillis", "model", "textRecognizer",
"allowRuntimePrompt", "minFileSizeToOcr", "completionsPath", "baseUrl", "skipOcr", "maxFileSizeToOcr",
"maxImagePixels", "maxTokens")
----

So from `tika-config.json` the VLM parser always sends `Authorization: Bearer`. For Azure, either construct
`OpenAIVLMParser` in Java and call the setters, or put an OpenAI-shaped gateway (LiteLLM, for instance) in front. The
embedding engine is different: `openai-embedding-engine` does accept `apiKeyHeaderName` and `apiKeyPrefix` in JSON (see
<<vendor-keys>>). The error message above is also the most reliable list of the VLM keys in 4.1.0.

Source: the `OpenAIVLMParser` 4.1.0 source and its Javadoc, and a load of that configuration on 4.1.0.

=== VLMOCRConfig options

[cols="2,2,5",options="header"]
|===
|Key |Default |Meaning and cost

|`baseUrl` |per parser (table above) |Endpoint root, no trailing slash. Cannot be changed per request.
|`model` |per parser |Model identifier sent in the request and written to `vlm:model`. Cannot be changed per request; configure a second engine for a second model.
|`prompt` |"Extract all visible text from this image. ..." (Markdown transcription prompt) |The instruction sent with the image. Changing it per request needs `allowRuntimePrompt`.
|`maxTokens` |`4096` |Ceiling on generated tokens, and so on output cost per call. Per request it may be lowered, never raised.
|`timeoutMillis` |`120000` |HTTP read timeout, also used for the startup probe. Local models need far more (the docs suggest 600000 for a laptop).
|`maxRetries` |`4` |Retries of a 429, 502, 503 or 504 with a jittered backoff inside the parse's time budget; `0` fails at once. Blocked per request.
|`apiKey` |`+""+` |Sent as described in the parser table. Use `+${env:NAME}+`. Blocked per request.
|`completionsPath` |`/v1/chat/completions` |OpenAI-compatible parser only; Claude and Gemini ignore it.
|`inlineContent` |`true` |For an image embedded inline (embedded resource type `INLINE`), also write the recognized text into the parent document's content, as Tesseract does.
|`skipOcr` |`false` |Kill switch. The parser advertises no types and does nothing. Allowed per request.
|`textRecognizer` |`true` |Says the prompt transcribes. Set `false` for a captioning or tagging prompt: the engine still runs, but the PDF parser's `AUTO` strategy never replaces a page's extracted text with its answer.
|`minFileSizeToOcr` |`0` |Smaller inputs are skipped, in bytes.
|`maxFileSizeToOcr` |`52428800` (50 MB) |Larger inputs are skipped, in bytes.
|`maxImagePixels` |`100000000` |Images with a larger decoded area are skipped before any request (decompression-bomb and cost guard); `-1` disables. Blocked per request.
|`allowRuntimePrompt` |`false` |Whether a caller-supplied JSON config may change `prompt` and `textRecognizer`. Security-relevant, see <<per-request>>.
|===

Source: https://tika.apache.org/docs/4.1.x/configuration/parsers/vlm-parsers.html#_configuration_options_reference[VLM
Parsers, configuration options reference, 4.1.x docs], cross-checked with the field initializers in `VLMOCRConfig`
4.1.0 and the
https://tika.apache.org/4.1.0/api/org/apache/tika/parser/vlm/VLMOCRConfig.html[`VLMOCRConfig` Javadoc].

On top of the engine's own gates, a `text-recognizers` entry takes `engine`, `_mime-include`, `_mime-exclude`,

2 x 2 pixels never reaches any engine.

=== Startup behaviour

What happens when the engine cannot be reached is a frequent surprise, so it is worth spelling out:

* `AbstractVLMParser.initialize()` probes the health URL (OpenAI-compatible and Gemini only). If the probe fails, it
  logs a warning and the parser advertises **no media types** for the rest of the run. It does not retry later.
* The `text-recognizers` loader then refuses an engine with no types. The run against a closed port failed the load
  with: `Text recognizer engine "local-vlm" advertises no media types (a _mime-include list does not count). Is the
  engine unavailable (missing native binary, unreachable inference server) or configured to skip enrichment?`
* So: **start the model server before Tika**, and in Docker Compose or Kubernetes make Tika wait for the model's
  readiness. A tika-server that restarts on failure (`restart: on-failure`) recovers once the model is up.
* The OpenAI probe calls `/v1/models`. A home-made server that only implements `/v1/chat/completions` fails the probe;
  add the `/v1/models` route (the 4.1.x local-server guide does) or use a non-default `completionsPath`.
* Claude has no probe, and the Gemini probe only proves that the model list is readable. A wrong key or a model your
  key cannot use fails at the first parse.

Source: the `AbstractVLMParser` 4.1.0 source and the
https://tika.apache.org/docs/4.1.x/advanced/local-vlm-server.html[Running a Local VLM Server, 4.1.x docs] page. Both
failure messages above are from runs on 4.1.0.

=== Scanned PDFs: the pages block decides

The PDF parser asks the recognizer for text only when its `pages.text` policy says so. The default is `AUTO`: pages
whose extracted text is poor are rendered and sent. `scanned-loan-form.pdf` has no text layer, so `AUTO` sends every
page; `OCR` sends every page of every PDF, which is what this run forced on the one-page `catalogue.pdf` to show the
output shape:

embedded images in every other format too. The 4.2-compatible shape is `+"pages": {"text": "OCR"}+` with the VLM in
`text-recognizers`, as above; it sends page images, not the file. There is no 4.2 shape yet for sending the PDF file
itself.

== Markdown-to-XHTML conversion

A model answers in Markdown, and Tika does not paste that answer as plain text. `MarkdownToXHTMLEmitter` parses it with
commonmark-java and emits real XHTML elements: headings, paragraphs, `<b>`/`<i>`, lists and tables (GFM tables and
strikethrough are enabled). The run above shows a Markdown pipe table becoming `<table>`, `<thead>`, `<th>` and `<td>`,
wrapped in `+<div class="ocr">+`. Because the result is XHTML, every Tika output format sees structure: the Markdown
handler writes the pipe table back (as in the `tk:content` above), the XML handler writes the `<table>`, the text
handler writes the cell text.

Document-OCR models (the docs name jina-ocr-v1 and DeepSeek-OCR) write tables as raw HTML inside the Markdown whatever
the prompt says. Tika parses such an HTML block leniently with jsoup and re-emits only the structural elements (`table`,
`tr`, `th`, `td`, `p`, lists, headings), dropping every attribute except `colspan` and `rowspan`. Other elements give
their text; `script` and `style` give nothing. Inline HTML tags are dropped and their text kept, except `<br>`. That is a
safety property as well as a convenience: a model that echoes markup from a hostile image cannot inject scripts or
event attributes into Tika's XHTML.

The conversion is also why a VLM's output is better than raw OCR for the RAG pipeline downstream: headings survive as
headings, so the Markdown chunker can split on them (see <<why-markdown>>). It does not make the model correct. A VLM
can misread, skip or invent text, and nothing in Tika checks the transcription against the image.

Source: https://tika.apache.org/docs/4.1.x/configuration/parsers/vlm-parsers.html#_markdown_to_xhtml_conversion[Markdown-to-XHTML
conversion, 4.1.x docs] and the `MarkdownToXHTMLEmitter` 4.1.0 source.

== Per-request configuration

There are two paths with different trust.

=== In-process Java: trusted

Code that builds the `ParseContext` is trusted by construction. Put a `VLMOCRConfig` in it and every field applies:

[source,java]
----
import org.apache.tika.exception.TikaConfigException;
import org.apache.tika.parser.ParseContext;
import org.apache.tika.parser.vlm.VLMOCRConfig;

public final class CoverCaptionContext {
    private CoverCaptionContext() {
    }

    /** A captioning prompt for the cover workflow: not a transcription, so textRecognizer is false. */
    public static ParseContext forCovers() throws TikaConfigException {
        VLMOCRConfig override = new VLMOCRConfig();
        override.setBaseUrl("http://127.0.0.1:8000");
        override.setModel("mock-vlm");
        override.setPrompt("Describe this book cover in one sentence. Return Markdown.");
        override.setTextRecognizer(false);
        override.setMaxTokens(256);
        ParseContext context = new ParseContext();
        context.set(VLMOCRConfig.class, override);
        return context;
    }
}
----

Source: https://tika.apache.org/docs/4.1.x/configuration/parsers/vlm-parsers.html#_per_request_configuration[Per-request
configuration, 4.1.x docs] and the `VLMOCRConfig` 4.1.0 setters. Compiled and run against the mock. The object
_replaces_ the engine's configuration for that parse (it is not merged): in the run, the request carried no
`Authorization` header, because the override's empty `apiKey` replaced the engine's. Set every field you rely on,
including `baseUrl`, `model` and, for a hosted endpoint, `apiKey` (read it from the environment, never a literal).

=== Caller-supplied JSON: restricted

JSON that arrives with a request, through the tika-server `/config` endpoints or gRPC `parse_context_json` (each gated by
its own `allowPerRequestConfig`), goes through `VLMOCRConfig.RuntimeConfig`, which refuses cost- and security-sensitive
changes. In Java the same untrusted path is `ParseContext.setJsonConfig(key, json)`, which this program used to try five
overrides against the engine above (`maxTokens` 4096 at load):

[source,java]
----
import java.nio.file.Path;

import org.apache.tika.config.loader.TikaLoader;
import org.apache.tika.io.TikaInputStream;
import org.apache.tika.metadata.Metadata;
import org.apache.tika.parser.ParseContext;
import org.apache.tika.parser.Parser;
import org.apache.tika.sax.ToMarkdownContentHandler;

public class PerRequest {
    public static void main(String[] args) throws Exception {
        TikaLoader loader = TikaLoader.load(Path.of(args[0]));
        Parser parser = loader.loadAutoDetectParser();
        String[] overrides = {
            "{\"maxTokens\": 1024}", "{\"maxTokens\": 9000}", "{\"model\": \"another-model\"}",
            "{\"prompt\": \"Describe the cover.\"}", "{\"skipOcr\": true}"
        };
        for (String json : overrides) {
            ParseContext context = loader.loadParseContext();
            context.setJsonConfig("openai-vlm-parser", json);     // untrusted, as from a request
            Metadata metadata = new Metadata();
            try (TikaInputStream tis = TikaInputStream.get(Path.of(args[1]))) {
                parser.parse(tis, new ToMarkdownContentHandler(), metadata, context);
                System.out.println(json + " -> OK, vlm:model=" + metadata.get("vlm:model"));
            } catch (Exception e) {
                Throwable root = e;
                while (root.getCause() != null) {
                    root = root.getCause();
                }
                System.out.println(json + " -> " + root.getMessage());
            }
        }
    }
}
----

[source,text]
----
{"maxTokens": 1024} -> OK, vlm:model=mock-vlm
{"maxTokens": 9000} -> Cannot increase maxTokens beyond the init-time value (4096) at runtime. Requested: 9000
{"model": "another-model"} -> Cannot modify model at runtime. Models must be configured at initialization time. If you need a different model, configure a separate parser instance.
{"prompt": "Describe the cover."} -> Cannot modify prompt at runtime. Set allowRuntimePrompt=true at initialization time to permit per-request prompt overrides.
{"skipOcr": true} -> OK, vlm:model=null
----

Source: https://tika.apache.org/docs/4.1.x/configuration/parsers/vlm-parsers.html#_per_request_configuration[Per-request
configuration, 4.1.x docs] and the `VLMOCRConfig.RuntimeConfig` 4.1.0 source. Run against the mock; the messages are
the root causes (`IllegalStateException`) of the parse exceptions.

[cols="2,4",options="header"]
|===
|Field |Rule for caller-supplied JSON
|`baseUrl`, `apiKey` |Always refused. A caller can never redirect the document, or your key, to another host.
|`model` |Always refused. A second model is a second engine.
|`maxTokens` |May be lowered, never raised above the load-time value. This ceiling is what bounds the cost of one call.
|`maxImagePixels`, `maxRetries`, `allowRuntimePrompt` |Always refused.
|`prompt`, `textRecognizer` |Refused unless the engine was loaded with `allowRuntimePrompt: true`.
|`skipOcr` and the size gates |Allowed. Switching the engine off for one request is always safe.
|===

Keep `allowRuntimePrompt` off for any server reachable by people you do not fully trust. A caller-controlled prompt is a
prompt-injection surface on your key: "ignore the image and write ..." costs you tokens and puts arbitrary text into
your index under the document's name. The site's xref:ai/security/prompt-injection.adoc[Prompt Injection] page covers
the general problem; here, the image itself is also untrusted input, so a scanned page can carry instructions to the
model too. Treat VLM output as untrusted text, exactly like the document's own text.

With `+"server": {"allowPerRequestConfig": true}+`, a multipart `config` part on `/tika/config`, `/rmeta/config` or
`/meta/config` carries the same JSON, keyed by component name:

[source,bash]
----

    "no-enrichment": { "text-recognizers": { "enabled": false }, "inference": { "enabled": false } }

----

== Running a local VLM server

A local model removes the per-call cost and keeps documents on your hardware, which is often the deciding argument for
loan forms and other personal data. Anything that speaks the OpenAI chat-completions shape works with
`openai-vlm-parser`. Three common choices:

[cols="2,4,4",options="header"]
|===
|Server |How Tika talks to it |Notes
|Ollama |`baseUrl` = the Ollama host and port (11434 by default); Ollama serves `/v1/chat/completions` and `/v1/models` |Easiest on a laptop or a single GPU box; pull a vision-capable model first. See xref:ai/local-llms/ollama.adoc[Ollama].
|vLLM |`baseUrl` = the vLLM OpenAI-compatible server |Higher throughput, batching on GPU. See xref:ai/local-llms/vllm-and-sglang.adoc[vLLM and SGLang].
|A FastAPI wrapper around a Hugging Face model |Must implement `/v1/chat/completions` _and_ `/v1/models` |The 4.1.x guide ships one for `jinaai/jina-vlm` and `Qwen/Qwen2-VL-2B-Instruct` on Apple Silicon or CUDA.

Practical notes for local models:

* **Timeouts.** The 4.1.x guide measures 15 to 30 seconds per page image for a 2.4B model on an M3 Max, and 20 to 30
  seconds to load the model. Set `timeoutMillis` to 600000 or more, and size the parse's own `timeout-limits` (one hour
  total, two minutes without progress by default) so a 40-page scan fits; the wait on the model counts as progress.
* **Throughput.** A single local model is a queue. More Tika workers than the model can serve only lengthen the queue;
  keep `numClients` (tika-server, Pipes) near the number of concurrent requests the model server handles.
* **Licences.** Model weights carry their own licence. The guide notes that `jinaai/jina-vlm` (the default model name
  in `VLMOCRConfig`) is CC BY-NC 4.0, non-commercial, while `Qwen/Qwen2-VL-2B-Instruct` is Apache 2.0. Check before a
  commercial deployment.
* **Bind locally.** The guide's server binds `127.0.0.1` only. A model server has no notion of Tika's trust model; keep
  it off public interfaces.

== Inference: engines and bindings

Inference in 4.1 has three parts, each answering one question:

* `engines`: _what can be called_. Name, engine type, endpoint, model, key.
* `inference`: _what runs on what_. A list of bindings; each names an engine, an input kind and the tasks.
* `pages.inference` on the PDF parser: _what a rendering parser releases_ (`TEXT`, the default, and/or `PAGES`).

The only engine type in 4.1.0 is `openai-embedding-engine`, which posts to an OpenAI-shaped `/v1/embeddings` endpoint,
and the only task is `embed`. A chat task on a chat engine (a caption or tags per picture) is listed by the project as
4.2 work.

=== The embedding engine

[cols="2,2,5",options="header"]
|===
|Key |Default |Meaning
|`baseUrl` |`http://localhost:8000` |Endpoint root; the engine appends `embeddingsPath`.
|`model` |`+""+` |Model identifier.
|`apiKey` |`+""+` |Use `+${env:NAME}+`.
|`timeoutMillis` |`120000` |Per request.
|`maxBatchSize` |`32` |Inputs per request. A document tree's units are sent in batches of this size.
|`maxRetries` |`4` |Retries of 429/502/503/504 (see <<concurrency>>).
|`embeddingsPath` |`/v1/embeddings` |For Azure deployments and gateways.
|`apiKeyHeaderName` |`Authorization` |`api-key` for Azure.
|`apiKeyPrefix` |`Bearer ` (with a space) |`+""+` for Azure.
|`requestParameters` |empty map |Vendor keys copied into every request body (see <<vendor-keys>>).
|`imageInput` |`object` |How an image goes into `input`: `object` sends `+{"image": "data:..."}+` (Jina's form); `data-uri` sends a bare data URI (LiteLLM's form).
|`mediaInput` |none |`object` sends audio and video as `+{"audio": ...}+` / `+{"video": ...}+`; required for MEDIA bindings.
|===

Source: https://tika.apache.org/docs/4.1.x/configuration/inference.html[Inference: engines and bindings, 4.1.x docs]
and the field initializers in `OpenAIEmbeddingEngine` 4.1.0
(https://tika.apache.org/4.1.0/api/org/apache/tika/inference/OpenAIEmbeddingEngine.html[Javadoc]).

=== Bindings

[cols="2,5",options="header"]
|===
|Key |Meaning
|`id` |Names the binding; defaults to `<engine>-<input>`. Unique in the list; it is the `producer` of every chunk it writes.
|`engine` |A name from `engines`. An unknown name fails the load.
|`input` |`TEXT`, `IMAGES`, `PAGES` or `MEDIA` (table below).
|`modality` |`text`, `visual` or `audio`. Implied for TEXT, IMAGES and PAGES; a MEDIA binding must say `visual` or `audio`.
|`tasks` |`+["embed"]+` (the default and the only task in 4.1.0). `embed` on a recognizer such as Tesseract fails the load.
|`maxChunks` |Units one tree may send: pages of one document for PAGES, chunks of the tree for TEXT, segments of one file for MEDIA (480 unless set). `-1` for no limit. This is the cost cap per document.
|`maxBytes` |Largest unit accepted (20 MB unless set, `-1` for none); larger units are skipped and counted in a warning.
|`chunker` |TEXT only: `+{"markdown-chunker": {"maxChunkChars": 1500, "overlapChars": 200}}+`. Without one, a document's whole text is one chunk.
|`minWidth`, `minHeight` |IMAGES only: smaller recorded images are not offered (2 unless set, so spacers never are).
|`enabled` |`false` keeps the binding idle until a request selects it.
|`_mime-include`, `_mime-exclude` |Narrow by media type. With neither, an IMAGES binding skips vector and CAD image types (SVG, EMF, DWG) that no embedding endpoint takes.
|===

[cols="1,4,3",options="header"]
|===
|Input |Units |Where the vector lands
|`TEXT` |The `tk:content` of every document in the tree, cut by the chunker, after the parse |On the document the text came from, with a `text` locator (character offsets)
|`IMAGES` |Every image document: inline pictures, image attachments, a top-level image file (not page renders) |In recursive output, on the containing document with an `embedded` locator naming the picture; an attachment keeps its own
|`PAGES` |One render per page, from a parser that releases pages (the PDF parser with `+pages.inference: ["PAGES"]+`) |On the PDF, with a `paginated` locator naming the page
|`MEDIA` |Audio and video cut by ffmpeg into segments (25 s windows, 5 s overlap by default) |On the media document, with a `temporal` locator and a `correlator` shared by a segment's audio and visual chunks
|===

Source: https://tika.apache.org/docs/4.1.x/configuration/inference.html[Inference: engines and bindings, 4.1.x docs]
and the `InferenceBinding` 4.1.0 source
(https://tika.apache.org/4.1.0/api/org/apache/tika/parser/inference/InferenceBinding.html[Javadoc]).

=== How it runs

Parsers do not call embedding engines. Every image, audio or video document the parse meets, however deep, is offered to
one `InferenceDispatcher` after its own parser has run. The dispatcher keeps the units of the whole tree, as files it
owns, until the top-level parse ends, then sends each binding's units to its engine in requests of up to
`maxBatchSize`. A `.docx` with twelve pictures is one embeddings request, not twelve; if the endpoint rejects one image
in a batch, the rest are retried one by one. This flush is still inside `parse()`, under the parse's timeout, and the
unit files are deleted when it ends. A failed request marks the top-level document with a warning; it never fails the
parse.

The TEXT stage is separate: it runs **after** `parse()` returns, over the finished metadata list and **before** the
metadata filters. tika-app, tika-server and Pipes call it for you. In the Java API you call it yourself, as `TikaCLI`
does in 4.1.0; otherwise TEXT bindings silently do nothing. This was the first thing the run below found: with a plain
`RecursiveParserWrapper`, the page vectors appeared and the text vectors did not.

[source,java]
----
import java.nio.file.Path;
import java.util.List;

import org.apache.tika.config.loader.TikaLoader;
import org.apache.tika.io.TikaInputStream;
import org.apache.tika.metadata.Metadata;
import org.apache.tika.parser.ParseContext;
import org.apache.tika.parser.RecursiveParserWrapper;
import org.apache.tika.parser.inference.EngineRegistry;
import org.apache.tika.parser.inference.InferenceDispatcher;
import org.apache.tika.sax.BasicContentHandlerFactory;
import org.apache.tika.sax.RecursiveParserWrapperHandler;

public class BookshelfVectors {
    public static void main(String[] args) throws Exception {
        TikaLoader loader = TikaLoader.load(Path.of(args[0]));               // tika-config.json
        try (EngineRegistry engines = loader.get(EngineRegistry.class)) {     // closes the HTTP clients
            RecursiveParserWrapper parser = new RecursiveParserWrapper(loader.loadAutoDetectParser());
            ParseContext context = loader.loadParseContext();
            RecursiveParserWrapperHandler handler = new RecursiveParserWrapperHandler(
                    new BasicContentHandlerFactory(BasicContentHandlerFactory.HANDLER_TYPE.MARKDOWN, -1));
            try (TikaInputStream tis = TikaInputStream.get(Path.of(args[1]))) {
                parser.parse(tis, handler, new Metadata(), context);          // IMAGES, PAGES, MEDIA flush here
            }
            List<Metadata> metadataList = handler.getMetadataList();
            InferenceDispatcher inference = loader.get(InferenceDispatcher.class);
            if (inference != null) {
                inference.text(metadataList, context);                        // the TEXT stage
            }
            loader.loadMetadataFilters().filter(metadataList);                // filters run last
            for (Metadata m : metadataList) {
                System.out.println(m.get("Content-Type") + " -> tk:chunks = " + m.get("tk:chunks"));
            }
        }
    }
}

wrapped here). `EngineRegistry` and `InferenceDispatcher` are in `tika-core`
(`org.apache.tika.parser.inference`); the docs ask library users to close the registry themselves.

What the run showed:

* `tk:chunks` is one metadata value holding a JSON array. Each chunk has `vector`, `producer` (the binding `id`),
  `modality` and `locators`; text chunks also carry their `text`. The `vector` is base64 of big-endian float32 values:
  the mock's `[0.1, 0.2, 0.3, 0.4]` decodes from `PczMzT5MzM0+mZmaPszMzQ==` exactly. Decode it with
  `ByteBuffer.wrap(bytes).asFloatBuffer()` in Java (big-endian is the `ByteBuffer` default).
* `tk:inference-released` was `TEXT` and `PAGES` on the PDF. With `+["PAGES"]+` alone the TEXT stage skips the PDF, so it
  is embedded once, by its pages.
* `requestParameters` arrived in the request body: the mock logged the keys `dimensions`, `input` and `model`.
* For `publisher-email.eml` (an email with a zip holding a `.docx`, a PDF and a text note) the TEXT stage sent **one** request with
  eight chunks for the whole tree, and each chunk landed on the document its text came from: the email, the `.docx`,
  the PDF, a plain-text note and the zip.

$ java -jar tika-app-4.1.0.jar --config=tika-config.json -J catalogue.pdf
----

The run (with the tika-app 4.1.0 classes on the class path) produced the same `tk:chunks` value, plus
`+"tk:inference-released": ["TEXT", "PAGES"]+` and `+"tk:content-handler-type": "MARKDOWN"+`. The CLI is still described as

[#concurrency]
=== Hosted engines and concurrency

A hosted engine limits requests in flight per key and answers the excess with 429 at once, usually without
`Retry-After`; a saturated one answers 502, 503 or 504. Tika retries those four, `maxRetries` times, with a jittered
backoff from 250 ms doubling to 4 s (or the server's `Retry-After`), and never past the time the parse granted the call.
A 400 or 401 fails at once. The VLM parsers use the same policy.

The retries absorb collisions between a few workers; they do not create capacity. The rule from the docs: keep
`numClients` (tika-server, Pipes) at or below the key's concurrency, counting **every** engine the workers call (a VLM
recognizer and an embedding engine on the same vendor share the key), and raise the key's tier before raising the
workers. As an example of the scale, the docs quote Jina's limits as two requests in flight on a free key, 50 on a paid
key and 500 on premium.

[#vendor-keys]
=== Vendor keys: requestParameters

Most embedding services accept the OpenAI shape plus keys of their own. `requestParameters` is copied verbatim into
every request body next to `model` and `input`; the engine neither knows nor checks the names, so use your vendor's.
Three kinds recur: a Matryoshka dimension (`dimensions`, `output_dimension`), a query-versus-document hint (`task`,
`input_type`, `task_type`; use the document or passage value, since Tika indexes) and normalize/truncate flags. Two
rules are enforced: `model` and `input` are refused, and so is any key that changes the response away from float
vectors by index (`encoding_format`, `embedding_type`, `output_type`, `output_dtype`, `return_multivector`).

=== Media, in one paragraph

A MEDIA binding embeds audio or video. Tika cuts the file with ffmpeg (found on the `PATH` at load; the `-full` image
ships it) into 25-second windows starting every 20 seconds, as 360p H.264 silent clips for `visual` and mono Opus for
`audio`, under the parse's time budget. Each segment's chunks carry a `temporal` locator (`start_ms`, `end_ms`) and a
`correlator` such as `t:20000-45000`, so the audio and visual vectors of one segment can be grouped. The engine needs
`+"mediaInput": "object"+`, and the segment grid is set per request in `+{"parse-context": {"media": {"segment": {...}}}}+`.
The Bookshelf intake has no audio, so this page does not go further; the 4.1.x Inference page covers the limits.

=== Per request

[source,json]
----
{ "parse-context": { "inference": { "bindings": ["page-vectors"], "enabled": true } } }
----

`enabled: false` runs nothing for the request; `bindings` names the bindings that run (every enabled binding when
absent). A name that is not configured fails the request. Engines can never be defined or changed per request, and the
block carries names only, so it is safe in a preset or on a Pipes tuple.

Source: https://tika.apache.org/docs/4.1.x/configuration/inference.html[Inference: engines and bindings, 4.1.x docs].
Not run.

[#why-markdown]
== Why Markdown is required for inference

The TEXT stage, and the 4.0 embedding filters before it, chunk `tk:content` with `MarkdownChunker`. The chunker looks
for boundaries in priority order:

. Headings (`+#+` to `+######+`): the strongest boundary, and the only split made when a section already fits in
  `maxChunkChars`.
. Blank lines: paragraph boundaries, to subdivide an oversized section.
. A hard split at `maxChunkChars`: the last resort for a single paragraph that is still too long.

Each chunk overlaps the previous one by `overlapChars` (200 by default; it must be smaller than `maxChunkChars`, or the
load fails). Plain text has no headings, so a ten-page report chunks at arbitrary paragraph breaks instead of its
sections, the heading text that tells the embedding model what a chunk is about is lost, and tables and lists lose their
structure. Nothing fails; the chunks are only worse.

Two mechanisms keep this right in 4.x:

* **The default handler is Markdown.** `BasicContentHandlerFactory` defaults to `HANDLER_TYPE.MARKDOWN`, and tika-server
  and tika-app default to Markdown output, so an unconfigured setup already chunks well. In Java, pass
  `HANDLER_TYPE.MARKDOWN` explicitly, as the programs above do.
* **A runtime warning when it is overridden.** The handler factory records its type in `tk:content-handler-type` (the
  CLI run above shows `MARKDOWN`), and the embedding code logs a `WARN` when it is anything else. It is a check on a
  recorded value, not a guess about the content.

The project considered failing the load, or silently switching the handler, and rejected both: the first would make
deliberate plain-text chunking impossible, the second would change `tk:content` under consumers that asked for `TEXT`.

For Pipes, use the `CONCATENATE` or `RMETA` parse mode with inference. `CONTENT_ONLY` emits only the raw `tk:content`
string, so the chunks and vectors are dropped at emit time. The Elasticsearch and OpenSearch emitters have a
`chunkStrategy` option for writing chunks as their own documents.

Source: https://tika.apache.org/docs/4.1.x/migration-to-4x/inference-handler-requirements.html[Content Handler
Requirements for Inference, 4.1.x docs], https://tika.apache.org/docs/4.1.x/migration-to-4x/chunk-strategies.html[Chunk
Strategies, 4.1.x docs] and the `MarkdownChunker` 4.1.0 source
(https://tika.apache.org/4.1.0/api/org/apache/tika/inference/MarkdownChunker.html[Javadoc]).

The site's xref:database/vector-rag/document-ingestion-and-chunking.adoc[Document Ingestion & Chunking] page compares
chunking strategies in general; Tika's chunker is a structural one with a fixed overlap.

== The 4.0 shapes and their deprecation

Tika 4.0.0 shipped embeddings as metadata filters and an image parser. 4.1.0 keeps them working, with a `WARN` at
startup, and the project states they are removed in 4.2.0:

[cols="2,3,3",options="header"]
|===
|4.0 shape |What it did |4.1 replacement
|`openai-embedding-filter` in `metadata-filters` |Chunked and embedded each document's `tk:content`, one document per request |An engine plus a TEXT binding, which batches the whole tree
|`jina-embedding-filter` |The same against Jina, with a `task` option (default `retrieval.passage`) |`openai-embedding-engine` with Jina's keys in `requestParameters`
|`openai-image-embedding-parser` as a recognizer |Embedded one image per request |An engine plus an IMAGES binding
|A VLM or OCR engine under `parsers` |Configured the engine and made it a parser for unclaimed types |`engines` + `text-recognizers`; fails the load in 4.2.0
|===

A 4.0 filter configuration, kept here only to recognise it when migrating:

{
  "content-handler-factory": {
    "basic-content-handler-factory": { "type": "MARKDOWN", "writeLimit": -1 }
  },
  "metadata-filters": [
    { "openai-embedding-filter": {
        "baseUrl": "https://api.openai.com",
        "model": "text-embedding-3-small",
        "apiKey": "${env:OPENAI_API_KEY}",
        "maxChunkChars": 1500,
        "overlapChars": 200 } }
  ]
}
----

[#cost-privacy-residency]
== Cost, privacy and data residency

A VLM or embedding engine is the one place where Tika sends **document content to another system**. Everything in
Tika's security model about untrusted input still applies, and the following comes on top. The
xref:ai/llmops/cost-management.adoc[Cost Management] and
xref:ai/security/sensitive-information-and-hidden-context.adoc[Sensitive Information] pages cover the general practice.

Cost:

* **Every page and every picture is a call.** With `AUTO`, a 40-page scanned loan form is 40 VLM calls; an email with a
  signature logo in every reply is one call per logo unless `_min-width`/`_min-height` or `minWidth`/`minHeight` keep it
  out. Set `ocr.maxPages` in the PDF parser's `pages` block, `maxChunks` on bindings and `maxTokens` on VLM engines.
* **Retries cost too.** A 502 that succeeds on the fourth retry may have been billed four times, depending on the
  vendor.
* **Measure.** Sum `vlm:prompt-tokens` and `vlm:completion-tokens` from the output. Embedding engines report no usage in
  Tika's metadata, so count units (chunks) instead.
* **Re-parsing is not free.** Re-indexing a corpus re-runs every model call. Store the vectors with the document
  version, and use a no-enrichment preset for re-parses that only need metadata.

Privacy and residency:

* **The bytes leave your network.** The image or page render is sent base64-encoded in the request body. A hosted
  vendor's retention, training-use and logging terms then apply, along with the region its endpoint runs in. These
  terms are vendor contracts, not Tika settings, and this page does not describe any vendor's; read them before sending
  personal data.
* **Choose the region with the endpoint.** Residency is decided by `baseUrl`: a regional endpoint, a private cloud
  deployment (an Azure resource in your region, a Vertex endpoint behind a gateway) or a local model. Tika has no
  routing of its own, and a caller can never change `baseUrl` per request.
* **Local is the default answer for sensitive files.** For the loan forms, a model on your own hardware (Ollama, vLLM)
  keeps the data in place. Use separate engines, and if needed separate tika-server instances, for files that may go to
  a hosted model and files that may not; presets select the configuration per workflow.
* **Keys.** Read keys with `+${env:NAME}+`, inject them from your secret store (Kubernetes Secret, Docker secret, Vault)
  and never commit them. Note the limit the docs state: with a persistent config store (`configStoreType` `file` or
  Ignite), resolved fetcher and emitter configurations are written to that store. Gemini's key travels in the URL.
* **Output is untrusted.** A model can hallucinate text that was not on the page, and a hostile image can carry prompt
  injection. Never let VLM text drive actions (routing, approvals) without a check, and keep `allowRuntimePrompt` off.

Source: https://tika.apache.org/docs/4.1.x/configuration/parsers/vlm-parsers.html[VLM Parsers, 4.1.x docs],
https://tika.apache.org/docs/4.1.x/configuration/index.html#env[Secrets from the environment, 4.1.x docs] and
https://tika.apache.org/security-model.html[Apache Tika security model].

== Memory, performance and robustness

* **The whole input is held in memory.** `AbstractVLMParser.parse` reads the file fully and base64-encodes it, so a
  50 MB input (the default `maxFileSizeToOcr`) is about 50 MB of bytes plus about 67 MB of base64 text plus the JSON
  body, per concurrent parse. Lower `maxFileSizeToOcr` and keep page renders small.
* **The model dominates latency.** Seconds per page for a hosted model, tens of seconds for a laptop model. The
  progress timeout counts the wait as progress, but the total task timeout still applies; size it for your longest
  document.
* **Use the forked paths for untrusted files.** In tika-server and Pipes the parse runs in a forked JVM, so a stuck
  model call ends with the fork, not with your application. The engines' HTTP clients are closed when the pipes server
  shuts down; in a library, close the `EngineRegistry`.
* **Failures are contained.** A failed recognizer is reported through the parser's normal exception handling and does
  not stop other recognizers; a failed embedding request becomes a warning on the root document. Check
  `tk:exception:warn` (and the other `+tk:exception:*+` keys) in your intake reports.
* **Two recognizers on one type both run.** If you list Tesseract and a VLM for the same images, both run and their text
  is concatenated (a startup `WARN` names them). Choose one per media type with `_mime-include`/`_mime-exclude`.

== Pitfalls

* **TEXT bindings do nothing from a bare `RecursiveParserWrapper`.** Call `+InferenceDispatcher.text(...)+` after the
  parse, or use tika-app, tika-server or Pipes.
* **Unreachable model at startup fails the load** for OpenAI-compatible and Gemini engines. Order your containers and
  retry the start.
* **A wrong Claude or Jina key passes startup** and fails on the first document.
* **`apiKeyHeaderName`/`apiKeyPrefix` are not JSON keys for the VLM parser** in 4.1.0 (they are for the embedding
  engine).
* **The default model names are not a recommendation.** `jinaai/jina-vlm` is non-commercial; the Claude and Gemini
  defaults will be retired by their vendors.
* **A captioning prompt with `textRecognizer: true`** lets `AUTO` replace a page's real text with a description. Set
  `textRecognizer: false` for anything that is not a transcription.
* **A non-Markdown handler** degrades chunking silently except for a `WARN`.
* **`CONTENT_ONLY` in Pipes** discards the vectors.
* **Engine entries under `parsers`** stop loading in 4.2.0. Migrate now.
* **Everything here is experimental.** Re-read the release notes before every Tika upgrade and pin the version.

== Checklist

* Add `tika-vlm` and/or `tika-inference` (library) or use the tika-app / tika-server distributions, which include both.
* Configure engines under `engines`, recognizers in `text-recognizers`, embeddings in `inference`.
* Read every key with `+${env:NAME}+`; never put a key in `tika-config.json` or in source control.
* Set `model`, `maxTokens`, `timeoutMillis`, `maxFileSizeToOcr`, `maxImagePixels` and the minimum image size explicitly.
* Cap pages and chunks (`ocr.maxPages`, `maxChunks`) and keep `numClients` within the key's concurrency.
* Use `textRecognizer: false` for non-transcription prompts and keep `allowRuntimePrompt: false`.
* Use the Markdown handler, and `CONCATENATE` or `RMETA` in Pipes.
* In Java: run the TEXT stage, then the metadata filters, and close the `EngineRegistry`.
* Decide per document class whether it may leave your network; use a local model or a regional endpoint where not.
* Record `+vlm:*+` token counts and the chunk counts for cost tracking.
