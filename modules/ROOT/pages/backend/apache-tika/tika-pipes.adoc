== What Tika Pipes is

Parsing a file you did not write is risky. A crafted or merely broken PDF can make PDFBox allocate gigabytes, a ZIP can
expand without end, a parser can loop forever, and a native library can crash the JVM. When the parser runs inside your
application, all of that happens to your application. Tika's security model says so plainly: calling parsers in-process
opts out of the sandbox, and an out-of-memory error or an infinite loop is then the caller's problem, not a Tika
vulnerability. Process isolation is the sandbox, and Tika Pipes is how Tika provides it.

Tika Pipes splits the work between two kinds of process:

* The *parent* (the driver) is your application, tika-app in batch mode, tika-server or tika-grpc. It lists the
  documents, hands them out, writes the results and keeps the books. It never parses.
* The *forks* are child JVMs (class `PipesServer`) that the parent starts, feeds over a local socket and restarts when
  they die. Each fork fetches one document, parses it and either sends the result back or writes it itself.

`numClients` sets how many forks run at once. When a fork runs out of memory, times out or crashes, the parent records the
failure for that one document, starts a fresh fork and carries on with the next document.

image::apache-tika-pipes.svg["Tika Pipes: an iterator in the parent JVM lists documents, a queue feeds a pool of PipesClients, each forked JVM fetches and parses one document, the emitter writes the result directly or after passback and batching, and the reporter in the parent records each status",width=960]

=== The four roles

A pipeline is assembled from four kinds of pluggable component. Each is named in `tika-config.json` and each is a PF4J
plugin, so a source or a destination Tika does not ship can be added without rebuilding Tika.

[cols="1,2,2,2",options="header"]
|===
|Role |What it does |Where it runs |Configured under
|Pipes iterator |Enumerates the work: walks a folder, lists a bucket, reads a CSV or a JDBC result set, drains a Kafka
topic. It produces one `FetchEmitTuple` per document. |Parent, on its own thread |`pipes-iterator` (singular, one per
pipeline), keyed by component name
|Fetcher |Turns a fetch key (a relative path, an object key, a URL) into the document bytes. |Fork |`fetchers`, keyed by
an instance id you choose, then the component name
|Emitter |Writes the parse result to a destination keyed by the emit key: a file, an object, a search document, a row,
a Kafka record. |Fork (direct emit) or parent (after passback) |`emitters`, keyed by instance id, then component name
|Reporter |Records the outcome (`PipesResult` status) of every document: counters, a JSON-lines ledger, a table, an
index. Observational only. |Parent |`pipes-reporters` (plural, several allowed), keyed by component name
|===

The `FetchEmitTuple` is the unit of work. It carries an `id` (yours, echoed in logs and reports), a `FetchKey` (fetcher
id plus key), an `EmitKey` (emitter id plus key), optional `Metadata` to seed the parse (a content-type hint, a resource
name, or business fields such as a shelf code), an optional per-document `ParseContext` (parse mode, limits, emit
strategy) and an `onParseException` choice (`EMIT` or `SKIP`). The iterator builds the tuples; with the Java API you can
build them yourself.

Source: https://tika.apache.org/docs/4.1.x/pipes/index.html[Apache Tika 4.1.x, Tika Pipes] (The four roles),
https://tika.apache.org/docs/4.1.x/pipes/iterators.html[Pipes Iterators] and the 4.1.0 `FetchEmitTuple` source.

=== Ways in

The same machinery is reachable at six levels. Pick the highest one that does the job.

[cols="2,2,3",options="header"]
|===
|Entry point |Module / artifact |Use it when
|`tika-app -i <in> -o <out>` |tika-app zip (`TikaAsyncCLI`) |A folder of files to a folder of JSON, Markdown or text,
from a shell or a cron job. No code.
|`tika-app -a -c tika-config.json` |tika-app zip |The same, with any iterator, fetcher, emitter and reporter from a config
file.
|tika-server `/tika`, `/rmeta`, `/pipes`, `/async` |tika-server-standard zip, `apache/tika` image |Other services send
documents (or fetch keys) over HTTP. Parsing endpoints always run in forks in 4.x.
|tika-grpc |`apache/tika-grpc` image |The same over gRPC, with fetcher management calls. Trusted networks only.
|`PipesForkParser` |`tika-pipes-fork-parser` |Your Java code has a file or a stream and wants text and metadata back,
crash-isolated. Local files and in-memory bytes only.
|`PipesParser` |`tika-pipes-core` |One document at a time through a full pipes config: any fetcher, any emitter, result
written by the fork or passed back.
|`AsyncProcessor` |`tika-pipes-core` |The whole pipeline inside your JVM: queue, fork pool, emitter threads, reporters.
This is what `tika-app -i/-o` runs.
|===

`PipesClient` is the per-fork socket client wrapped by the last three; it is not a user-facing API.

Source: https://tika.apache.org/docs/4.1.x/using-tika/java-api/pipes.html[Apache Tika 4.1.x, Tika Pipes from Java]
and https://tika.apache.org/docs/4.1.x/pipes/index.html[Tika Pipes] (Overview).

== The forked-JVM model

Each `PipesClient` in the parent owns one fork in the default *per-client* mode. The life of a fork:

. *Lazy start.* No fork starts when the pipeline is built. The first request that needs a client starts its fork, which
  loads the config and the plugins and then reports READY. Starting a fork costs seconds (about five seconds on the
  test machine for the first parse, with the standard parser package); that is why a `PipesForkParser` or a
  `PipesParser` must be created once and reused.
. *Request and heartbeat.* The parent sends the tuple over the socket; small in-memory documents travel inside the
  request (up to `maxInlineBytes`, 10 MB by default), anything larger is written to a file first. While parsing, the
  fork sends a heartbeat every `heartbeatIntervalMillis` (1000 ms). If nothing arrives for `socketTimeoutMillis` (60 s),
  the parent treats the fork as hung.
. *Result.* The fork returns a `PipesResult` with a status, a message and, when the result is passed back, the list of
  `Metadata` objects.
. *Death and restart.* An `OutOfMemoryError`, a timeout or a native crash ends the fork. The parent records `OOM`,
  `TIMEOUT` or `UNSPECIFIED_CRASH` for that document and starts a new fork on the next request. The fork is also
  recycled after `maxFilesProcessedPerProcess` documents (10 000), which bounds slow leaks in parser libraries.
. *Reuse and idle shutdown.* The client pool hands out the most recently used client first, so light traffic stays on
  warm forks. A fork that gets no work for `socketTimeoutMillis` exits on its own and is restarted transparently.
. *Parent death.* The parent passes its process id in `TIKA_PIPES_PARENT_PID`; each fork watches it and exits within
  milliseconds if the parent dies, so killed services do not leave orphaned forks (or orphaned `tesseract` processes).

Every fork has its own heap and its own temporary directory: a `+pipes-server-*+` subdirectory of the parent's
`java.io.tmpdir`, which the parent removes when the fork goes away. The first lines a fork logs show both, plus its cache
budget (from the `PipesForkParser` run below, with `-Xmx512m`):

[source,text]
----

INFO  [main] 22:47:55,966 [fork] pipesClientId=0 o.a.t.pipes.core.server.PipesServer watching parent pid 5900 for exit
INFO  [main] 22:47:56,105 [fork] pipesClientId=0 o.a.t.config.loader.TikaLoader temporary files go to java.io.tmpdir=/var/folders/.../T/pipes-server-0-16529982140448677553

=== How many forks, how much CPU and heap

The default `numClients` is derived from the host: `max(1, min((cores - 2) / 2, 4))`, so roughly half the cores,
never more than four (`PipesConfig.defaultNumClients()` in the source). The batch CLIs (`tika-app -i/-o`,
`tika-async-cli`) use 2 when neither `-n` nor a config value is given, and `PipesForkParser` uses 1.

Each JVM sizes its garbage collector, JIT and fork-join pools from the host CPU count, so four forks on a 16-core host
would otherwise start about 64 GC threads. Unless you pass your own, Tika injects `-XX:ActiveProcessorCount` (a fair
slice of the cores, never below 2, with 2 cores reserved for the parent) and `-XX:MaxRAMPercentage` (so the forks'
combined heap stays under the host's memory) into each fork. The tika-app run on an 8-core laptop logged:

[source,text]
----
INFO  [main] 22:50:27,910 org.apache.tika.pipes.core.async.AsyncProcessor Using per-client server mode with 2 workers
INFO  [main] 22:50:27,914 org.apache.tika.pipes.core.PerClientServerManager pipes-cpu-sizing: hostCores=8, numClients=2, parentReserved=2, autoCap=slice=3, heap=MaxRAMPercentage=37
----

The documented rule of thumb: pick the largest `numClients` for which twice that number plus two cores still fits on the
host; beyond it, more forks reduce throughput. Size `-Xmx` per fork so that three quarters of it covers the parsing
working set, because a quarter is the default in-memory cache budget (`tika.pipes.cacheMemoryBudgetBytes`, a fork-side
system property). The xref:backend/apache-tika/docker-and-kubernetes-deployment.adoc[Docker & Kubernetes Deployment]
page applies this to container limits.

Source: https://tika.apache.org/docs/4.1.x/pipes/cpu-sizing.html[Apache Tika 4.1.x, Forked-JVM CPU and Heap Sizing]
and https://tika.apache.org/docs/4.1.x/pipes/configuration.html[Pipes Configuration] (Process Management, Embedded-object
cache memory budget).

=== Result statuses

Every document ends in one `PipesResult.RESULT_STATUS`, grouped into five categories. `PipesResult` and
`PipesForkResult` have one predicate per category.

[cols="1,3,3",options="header"]
|===
|Predicate (category) |Statuses |What to do
|`isSuccess()` (`SUCCESS`) |`PARSE_SUCCESS`, `PARSE_SUCCESS_WITH_EXCEPTION`, `PARSE_EXCEPTION_NO_EMIT`, `EMIT_SUCCESS`,
`EMIT_SUCCESS_PARSE_EXCEPTION`, `EMIT_SUCCESS_PASSBACK`, `PARTIAL_TIMEOUT`, `EMPTY_OUTPUT` |Use the output. The
`pass:c[*_EXCEPTION]` variants carry a partial parse with the stack trace in the message and in the container metadata;
`PARTIAL_TIMEOUT` means the task deadline cut the parse short.
|`isTaskException()` (`TASK_EXCEPTION`) |`FETCH_EXCEPTION`, `EMIT_EXCEPTION`, `FETCHER_NOT_FOUND`, `EMITTER_NOT_FOUND`,
`PRESET_NOT_FOUND`, `PAYLOAD_LIMIT_EXCEEDED` |This document failed; the fork is fine. Log it and move on.
|`isProcessCrash()` (`PROCESS_CRASH`) |`OOM`, `TIMEOUT`, `UNSPECIFIED_CRASH` |The fork died on this document and is
restarted before the next one. Record the document; do not retry it with the same settings.
|`isInitializationFailure()` (`INITIALIZATION_FAILURE`) |`FETCHER_INITIALIZATION_EXCEPTION`,
`EMITTER_INITIALIZATION_EXCEPTION`, `CLIENT_UNAVAILABLE_WITHIN_MS` |Possibly transient: a backend is down or every fork
was busy for `maxWaitForClientMillis`. Retry later.
|`isFatal()` (`FATAL`) |`FAILED_TO_INITIALIZE` |The fork cannot start at all: bad config, bad class path, bad
`javaPath`. Stop and fix it.
|===

Source: the 4.1.0 `PipesResult` source and
https://tika.apache.org/docs/4.1.x/using-tika/java-api/pipes.html[Tika Pipes from Java] (Reading a result).

== Getting started with tika-app

The quickest pipeline needs no configuration file. tika-app 4.x ships as a zip: unzip it and run the jar from inside,
because the jar is a thin launcher that loads `lib/` and `plugins/` from beside itself. Given an input folder and an
output folder, tika-app switches to Tika Pipes mode, walks the input recursively and writes one JSON file per document.

[source,bash]
----
cd tika-app-4.1.0
java -jar tika-app-4.1.0.jar -i /srv/bookshelf/inbox -o /srv/bookshelf/extracts -n 2
----

[source,text]
----
tika-app: running in Tika Pipes mode (async dispatch via -a/--async); use --help for options.
INFO  [main] 22:50:27,910 org.apache.tika.pipes.core.async.AsyncProcessor Using per-client server mode with 2 workers
INFO  [pool-2-thread-3] 22:50:35,216 org.apache.tika.pipes.core.PipesClient clientId=0: server successfully started
INFO  [pool-2-thread-2] 22:50:35,382 org.apache.tika.pipes.core.PipesClient clientId=1: server successfully started
INFO  [main] 22:50:37,635 tika.pipes Successfully finished processing 9 files in 9765 ms
----

The output folder then holds `catalogue.pdf.json`, `legacy-catalogue.txt.json`, `manuscript.docx.json`,
`novel.epub.json`, `publisher-email.eml.json`, `renamed-invoice.png.json`, `reviews-es.html.json`, `samples.zip.json`
and `scanned-loan-form.pdf.json`. The emit key is the input's relative path and the emitter appends `.json`. Each file
is the RMETA list: the container first, then one object per embedded document, with the text in `tk:content` as
Markdown (the 4.x default handler). For `samples.zip` that is three objects: the ZIP itself (whose content is the two
headings `# manuscript.docx` and `# catalogue.pdf`), then `/manuscript.docx` and `/catalogue.pdf` with their own
`dc:title`, `dc:creator` and text.

Source: https://tika.apache.org/docs/4.1.x/pipes/getting-started.html[Apache Tika 4.1.x, Getting Started with Tika
Pipes] (Quick Start with tika-app).

=== Pipes-mode options

|===
|Option |Meaning
|`-i`, `--inputDir` |Input folder, walked recursively by the file-system iterator.
|`-o`, `--outputDir` |Output folder for the file-system emitter.
|`-n`, `--numClients` |Number of forks (default 2 for the CLI).

== The pipes configuration

A pipeline is configured in the same `tika-config.json` that configures parsers, detectors and limits (see
xref:backend/apache-tika/configuration.adoc[Configuration]). Five top-level keys belong to Pipes.

[cols="1,3",options="header"]
|===
|Key |Contents
|`plugin-roots` |A folder (or an array of folders) of plugin zips. Mandatory for `PipesParser` and `AsyncProcessor`,
even if the folder is empty; tika-app, tika-server and `PipesForkParser` fill it in for you.
|`fetchers` |Map of fetcher id to one component: `+{ "inbox": { "file-system-fetcher": { ... } } }+`.
|`emitters` |Map of emitter id to one component, same shape.
|`pipes-iterator` |One iterator, keyed by component name, with `fetcherId` and `emitterId` naming the fetcher and the
emitter bound to every tuple it produces.
|`pipes-reporters` |Reporters keyed by component name; several may run together.
|`pipes` |The pipeline itself: forks, timeouts, parse mode, batching, emit strategy (table below).
|===

The text format comes from the top-level `content-handler-factory` and the per-document limits from `parse-context`
(`timeout-limits`, `embedded-limits`, `output-limits`, `unpack-config`, digesters), exactly as for the library.

=== The Bookshelf intake configuration

The _Bookshelf_ intake service receives manuscripts, catalogues, scans and publisher e-mails into an inbox folder and
needs one JSON extract per document plus a record of anything that failed. This is the file used for the
`AsyncProcessor` run later on this page.

[source,json]
----
{
  "plugin-roots": "/srv/bookshelf/plugins",

Notes on the file:

* `inbox` and `extracts` are instance ids you choose: letters, digits, `.`, `_` and `-` only. Ids beginning with two
  underscores are reserved for components the hosts wire up themselves (tika-server's upload fetcher,
  ``PipesForkParser``'s internal fetcher, the inline-bytes fetcher) and a file that defines one fails at startup.
* `file-system-fetcher`, `file-system-emitter` and `file-system-pipes-iterator` are component names, the `getName()` of
  each plugin factory. An unknown name fails the load and lists the names available.
* `basePath` on the fetcher and the emitter is the sandbox: keys that resolve outside it, including absolute paths and
  `../` traversal, are rejected.
* `extractFileSystemMetadata` adds `fs:created`, `fs:modified` and `fs:accessed` to each document's metadata; the
  iterator adds `tk:source-path`.
* `onParseException` is set per tuple (the iterators set `EMIT`); the 4.1.x configuration page notes that nothing reads
  it from the `pipes` section, although the key is accepted there.
* Secrets in other components (an S3 key, an Elasticsearch API key) belong in environment variables referenced as
  `+${env:NAME}+`, which `TikaJsonConfig` resolves at load time since 4.1.0; see
  xref:backend/apache-tika/configuration.adoc[Configuration] for the exact syntax and its limits.

Source: https://tika.apache.org/docs/4.1.x/pipes/configuration.html[Apache Tika 4.1.x, Pipes Configuration] (Complete
examples), https://tika.apache.org/docs/4.1.x/pipes/fetchers.html[Fetchers] (Reserved IDs) and
https://tika.apache.org/docs/4.1.x/pipes/plugins/filesystem.html[File System Plugin].

=== Parse modes

The parse mode decides how embedded documents are handled and what the emitter writes. It is set as `parseMode` in the
`pipes` section and can be overridden per document by putting a `ParseMode` into the tuple's `ParseContext`.

[cols="1,4,2",options="header"]
|===
|Mode |What happens |Equivalent elsewhere
|`RMETA` (default) |Recursive parse; one `Metadata` per document, container first, each embedded document with its own
metadata, text and `tk:embedded-exception`. |`/rmeta`, `tika-app -J`, `RecursiveParserWrapper`
|`CONCATENATE` |Same parse, but all text is merged into the container's `tk:content` and the embedded documents' own
metadata is dropped. Container failures land in `tk:exception:container-exception`. |`/tika`, the classic tika-app output
|`CONTENT_ONLY` |Parsed like `CONCATENATE`, but a metadata filter keeps only `tk:content` and
`tk:exception:container-exception`, and a stream emitter (file system, S3) writes the raw text with no JSON. |`tika-app
--content-only`
|`NO_PARSE` |No parser runs. Detection and any configured digester still run on the raw bytes, so you get
`Content-Type` and, for example, `tk:digest:SHA-256`. |MIME triage and hash inventories
|`UNPACK` |Parsed like `RMETA` and the raw bytes of embedded documents are written through an emitter. |`/unpack`,
`tika-app -z` / `-Z`
|===

The content format is independent of the mode: the top-level `content-handler-factory` (`TEXT`, `HTML`, `XML`,
`MARKDOWN`, `BODY`, `IGNORE`; `MARKDOWN` when unset) applies to every mode that produces content. With `CONTENT_ONLY` set
the emitter's `fileExtension` to match the handler (`md`, `txt`, `html`, `xml`). The handlers themselves are described in
xref:backend/apache-tika/content-handlers-and-output-formats.adoc[Content Handlers & Output Formats] and the RMETA list in
xref:backend/apache-tika/embedded-documents-and-recursive-parsing.adoc[Embedded Documents & Recursive Parsing].

[source,json]
----
{
  "content-handler-factory": { "basic-content-handler-factory": { "type": "MARKDOWN" } },
  "emitters": {
    "markdown": {
      "file-system-emitter": { "basePath": "/srv/bookshelf/markdown", "fileExtension": "md" }
    }
  },
  "pipes": { "parseMode": "CONTENT_ONLY" }
}
----

Source: https://tika.apache.org/docs/4.1.x/pipes/parse-modes.html[Apache Tika 4.1.x, Parse Modes] and the 4.1.0
`ParseMode` source.

[[_emit_strategy_and_batching]]
=== Emit strategy and batching

When a fork finishes a document, someone has to call the emitter. `emitStrategy` decides who:

* `PASSBACK_ALL`: the fork sends the metadata list back over the socket and the parent emits. The parent knows exactly
  what was written, and a fork crash means "not emitted". The cost is carrying every extract across the IPC link and
  holding it in the parent's heap.
* `EMIT_ALL`: the fork emits directly and only reports success. Cheap for the parent, but the emitter's dependencies
  and credentials must work inside the fork, and batching is per document.
* `DYNAMIC` (default): extracts above `thresholdBytes` (100 000) are emitted by the fork, smaller ones are passed back
  and batched. The right choice for `AsyncProcessor` and tika-app.

Passed-back extracts wait in the parent until a batch is flushed by size (`emitMaxEstimatedBytes`) or by time
(`emitWithinMillis`), then the `numEmitters` threads write them. Batching matters for the search emitters, which send
bulk requests.

`emitIntermediateResults` decides what happens to documents whose parse did not succeed. Two runs of the Bookshelf
CSV pipeline with an absurd five-millisecond `progressTimeoutMillis`, so that every document timed out, showed the
difference: with `false` (the default) the output folder stayed empty and only the reporter knew about the three
documents; with `true` the emitter wrote one file per document, each containing just
`+[{"tk:pipes-result":"TIMEOUT"}]+`. Use `true` when the destination itself must hold a record of every attempt, and a
JSON-lines reporter otherwise.

Source: https://tika.apache.org/docs/4.1.x/pipes/configuration.html[Apache Tika 4.1.x, Pipes Configuration] (Emit
Strategy, Async / Emit Batching) and the 4.1.0 `EmitStrategy` source.

=== Timeouts in one paragraph

Two limits in `parse-context.timeout-limits` bound each document: `totalTaskTimeoutMillis` (end to end, default one
hour) and `progressTimeoutMillis` (how long the parse may go silent). When the total deadline passes, the fork first
tries to stop cleanly and return what it has as `PARTIAL_TIMEOUT` (or an error, with `throwOnDeadline`); a hard
watchdog in the parent kills the fork if that does not happen within the progress window, which yields `TIMEOUT`. The
progress timeout produced this result in the failure run below:
`Server-side progress timeout: no progress for 11ms (limit: 5ms)`. The complete model, the 3.x renames and the sizing
advice are on xref:backend/apache-tika/robustness-limits-and-timeouts.adoc[Robustness, Limits & Timeouts].

Source: https://tika.apache.org/docs/4.1.x/pipes/timeouts.html[Apache Tika 4.1.x, Timeouts].

=== Reporters

Reporters are called once per document by the parent, with the tuple, the `PipesResult` and the elapsed time. Because
they run in the parent, they see crashes that never reach an emitter. Every configured reporter receives every call;
the first exception any of them throws is rethrown afterwards and stops the run.

The `file-system-reporter` rewrites a status file every `reportUpdateMs` (always set it: the value is the writer
thread's sleep, so leaving it at 0 rewrites the file in a tight loop). After the Bookshelf run:

[source,json]
----
{"started":"2026-10-12T20:50:08.097221Z","lastUpdate":"2026-10-12T20:50:16.378513Z","totalCountResult":{"totalCount":9,"status":"COMPLETED"},"statusCounts":{"PARSE_SUCCESS":9},"asyncStatus":"COMPLETED","crashMessage":""}
----

The write is not atomic, so a watcher (a dashboard, the Tika GUI) must treat a JSON parse error as a stale read and try
again on the next poll.

The `file-system-jsonl-reporter` (new in 4.1.0) appends one line per document and flushes it before returning, so it
survives the death of the parent too. With `includes` you can turn it into a crash ledger for a dead-letter process or for
tika-eval. Lines from the successful run and from the timeout run:

[source,json]
----
{"id":"manuscript.docx","status":"PARSE_SUCCESS","category":"SUCCESS","message":null,"elapsedMs":118,"timestamp":"2026-10-12T20:50:15.381116Z"}
{"id":"BK-0002","status":"TIMEOUT","category":"PROCESS_CRASH","message":"java.lang.RuntimeException: Server-side progress timeout: no progress for 9ms (limit: 5ms)\n\tat org.apache.tika.pipes.core.server.PipesServer.checkProgressTimeout(PipesServer.java:699)\n\tat org.apache.t[stack trace shortened here]","elapsedMs":5985,"timestamp":"2026-10-12T20:56:08.179382Z"}
----

[cols="1,1,3",options="header"]
|===
|`file-system-jsonl-reporter` key |Default |Meaning
|`path` |required |The JSONL file; parent folders are created.
|`onExists` |`EXCEPTION` |`EXCEPTION` refuses to start, `APPEND` continues an old ledger, `REPLACE` truncates it.
|`includes` / `excludes` |all statuses |Mutually exclusive sets of status names, for example
`+["OOM", "TIMEOUT", "UNSPECIFIED_CRASH", "FETCH_EXCEPTION", "EMIT_EXCEPTION"]+`.
|`maxMessageLength` |10000 |Characters of the message (stack trace) to keep.
|===

The other reporters are `jdbc-reporter` (rows in a table), `opensearch-pipes-reporter` and `es-pipes-reporter` (status
documents in an index).

Source: https://tika.apache.org/docs/4.1.x/pipes/reporters.html[Apache Tika 4.1.x, Pipes Reporters] and
https://tika.apache.org/docs/4.1.x/pipes/plugins/filesystem.html[File System Plugin] (File System Reporter, File System
JSONL Reporter).

== Plugins

=== How plugins are loaded

Every fetcher, emitter, iterator and reporter in 4.x is a https://pf4j.org/[PF4J] plugin. A plugin contributes one
factory per component, each annotated with `@org.pf4j.Extension` and listed in `META-INF/extensions.idx`. The
configuration never names a class: it names the factory's `getName()`, such as `file-system-fetcher`.

Plugins reach a Tika host in one of two ways:

* *As zips in a plugins folder.* This is the distribution layout. The tika-app and tika-server zips ship a `plugins/`
  folder and `plugin-roots` points at it. Tika unzips each plugin into a sibling folder named after the zip and writes a
  completion marker; a folder without the marker is treated as a failed extraction and deleted, so unpacking a plugin
  there by hand does not work. In the Docker images extra plugins go into `/tika-extras` (see
  xref:backend/apache-tika/docker-and-kubernetes-deployment.adoc[Docker & Kubernetes Deployment]).
* *As jars on the class path.* For an embedding application, add the plugin jar (`tika-pipes-s3`,
  `tika-pipes-opensearch`, `tika-pipes-csv` and so on) as an ordinary Maven dependency. Forks are launched with the
  parent's class path, so they see the same plugins. `tika-pipes-fork-parser` already depends on
  `tika-pipes-file-system`. A zip plugin of the same name takes precedence over a class-path plugin.

The plugin zips come from the distribution zips on the download page; they are not on Maven Central, the jars are.
When `plugin-roots` points at a folder that does not exist, PF4J logs a warning and Tika carries on with the class-path
plugins, which is what the runs on this page did:

[source,text]
----
WARN  [main] 22:47:56,199 [fork] pipesClientId=0 org.pf4j.AbstractPluginManager No '/srv/bookshelf/plugins' root
INFO  [main] 22:47:56,200 [fork] pipesClientId=0 org.pf4j.AbstractPluginManager No plugins
----

For plugin development, `-Dtika.plugin.dev.mode=true` (or `TIKA_PLUGIN_DEV_MODE=true`) treats each `plugin-roots`
entry as one already exploded plugin folder, so you can point it at a module's `target/classes`.

Source: https://tika.apache.org/docs/4.1.x/using-tika/java-api/pipes.html[Apache Tika 4.1.x, Tika Pipes from Java]
(Where plugins come from) and https://tika.apache.org/docs/4.1.x/pipes/plugins/writing-a-plugin.html[Writing a Pipes
Plugin].

=== HTTP, Google Drive and Microsoft Graph

These are fetcher-only plugins; pair them with an iterator that produces the right keys (a CSV of URLs, a JSON-lines
work list, your own code) and any emitter. For `http-fetcher` the fetch key is the URL itself; it supports basic and JWT
authentication, connection and timeout settings, extra headers and `maxSpoolSize`, and since 4.0 it verifies TLS
certificates and host names by default (`verifySsl: false` opts out, which you should not do outside a test).

=== Work lists: CSV, JSON lines and JDBC

When the list of documents comes from a system rather than a folder, use a work-list iterator. The Bookshelf intake
desk exports the day's submissions as a CSV, with business fields that should end up in each extract:

`2026/BK-0001.json`, `2026/BK-0002.json` and `2026/BK-0003.json`, the ledger used the CSV ids
(`+{"id":"BK-0001","status":"PARSE_SUCCESS",...}+`), and every column not consumed as a key became metadata: the

`fetcher`, `fetchKey`, `emitter`, `emitKey`, and optionally `metadata`, `parse-context`, `onParseException`, `preset`),
so each line names its own fetcher and emitter; unknown fields are rejected. The `jdbc-pipes-iterator` walks a `SELECT`
(`select`, `idColumn`, `fetchKeyColumn`, `emitKeyColumn`, `fetchSize`), and the `jdbc-emitter` writes chosen metadata
keys into a table through an `insert` template with typed `keys`.

=== Search emitters: Solr, Elasticsearch and OpenSearch

The three search emitters send bulk requests, so they benefit from passback batching. Each takes the index or collection
URL, an `idField` (the emit key becomes the document id), an `attachmentStrategy` for embedded documents
(the 4.1.x examples use `PARENT_CHILD`) and an `updateStrategy` (`ADD` for Solr, `OVERWRITE` for the other two). The Elasticsearch and
OpenSearch emitters also take a `chunkStrategy` for `tk:chunks`.

[source,json]
----
{
  "emitters": {
    "catalogue-index": {
      "es-emitter": {
        "esUrl": "https://search.bookshelf.internal:9200/bookshelf-docs",
        "idField": "doc_id",
        "attachmentStrategy": "PARENT_CHILD",
        "updateStrategy": "OVERWRITE",
        "apiKey": "${env:BOOKSHELF_ES_API_KEY}",
        "httpClientConfig": { "connectionTimeoutMillis": 10000, "socketTimeoutMillis": 60000 }
      }
    },
    "solr": {
      "solr-emitter": {
        "solrCollection": "bookshelf",
        "solrUrls": ["http://solr1.bookshelf.internal:8983/solr"],
        "idField": "id",
        "commitWithin": 1000,
        "attachmentStrategy": "PARENT_CHILD",
        "updateStrategy": "ADD"

Restrict what reaches the index with a metadata filter (see xref:backend/apache-tika/metadata.adoc[Metadata]) instead of

supports Solr 8. For the index side see xref:database/solr/indexing-and-updates.adoc[Solr indexing & updates] and
xref:database/elasticsearch/ingest-pipelines.adoc[Elasticsearch ingest pipelines]. Not run for this page.

Source: https://tika.apache.org/docs/4.1.x/pipes/plugins/elasticsearch.html[Apache Tika 4.1.x, Elasticsearch Plugin],

=== Kafka

The Kafka plugin has two halves with different standing.

The `kafka-emitter` is a plain producer and a good fit for streaming extracts to downstream indexers. Its keys map onto
the standard producer settings (`topic`, `bootstrapServers`, `acks`, `lingerMs`, `batchSize`, `compressionType`,
`enableIdempotence`, `maxRequestSize`, `deliveryTimeoutMs`, `transactionalId`, and so on); Tika sets no values of its
own, so an absent key means the Kafka client default. Read from the 4.1.0 `KafkaEmitter` source: the emitter sends *one
record per `Metadata` object*, so an RMETA extract of `publisher-email.eml` becomes six records with the same key (the
emit key). The value is a JSON object of the metadata fields, and only the first value of a multi-valued key is kept
(with a warning in the log). Use `CONCATENATE` when downstream consumers expect one record per document.

[source,json]
----
{
  "emitters": {
    "extract-topic": {
      "kafka-emitter": {
        "topic": "bookshelf.extracts",
        "bootstrapServers": "kafka1.bookshelf.internal:9092,kafka2.bookshelf.internal:9092",
        "acks": "all",
        "enableIdempotence": true,
        "compressionType": "lz4",
        "maxRequestSize": 1048576,
        "clientId": "bookshelf-tika-pipes"
      }
    }
  },
  "pipes": { "parseMode": "CONCATENATE" }
}
----

The `kafka-pipes-iterator` is documented as a worked example rather than a supported production integration. In
4.1.0 it uses each record's *key* as the tuple id, the fetch key and the emit key (the record value is not read). It
leaves `enable.auto.commit` at Kafka's default, so offsets are committed when records are polled, before Tika has parsed
or emitted them: a crash in between loses those documents, which is at-most-once delivery. It drains the topic and
stops after `drainIdleMs` (1000 ms) of quiet, so it suits a periodic batch run, not a long-running consumer. And a slow
document holds up its partition. For long-running or OCR-heavy work, write your own consumer that commits after a
successful result and drives tika-server, tika-grpc or `PipesParser` (see the `AsyncProcessor` section), and keep the
Kafka emitter for the results.

The Kafka side of these trade-offs is covered in xref:backend/messaging/kafka-consumers.adoc[Kafka Consumers],
xref:backend/messaging/kafka-producers.adoc[Kafka Producers],
xref:backend/messaging/delivery-guarantees.adoc[Delivery Guarantees] and
xref:backend/messaging/kafka-reliability-and-exactly-once.adoc[Kafka Reliability and Exactly-Once Semantics]. Not run for
this page.

Source: https://tika.apache.org/docs/4.1.x/pipes/plugins/kafka.html[Apache Tika 4.1.x, Apache Kafka Plugin] and the
4.1.0 `KafkaEmitter` and `KafkaPipesIterator` sources.

=== Writing a plugin

A plugin is three kinds of class, one `plugin.properties` and a zip with a fixed layout. Using a Bookshelf fetcher for a
supplier portal as the example:

. A `org.pf4j.Plugin` subclass with a `(PluginWrapper)` constructor, one per zip.
. One factory per component, annotated with `@Extension` (on the factory, never on the fetcher) and implementing the
  matching interface from `org.apache.tika.pipes.api`: `fetcher.FetcherFactory`, `emitter.EmitterFactory`,
  `pipesiterator.PipesIteratorFactory` or `reporter.PipesReporterFactory`. `getName()` is the name users write in
  `tika-config.json` and must be unique among all loaded plugins.
. The component itself, extending `org.apache.tika.plugins.AbstractTikaExtension` (or `PipesIteratorBase` from
  `tika-pipes-iterator-commons`, whose only abstract method is `enqueue()`, or `PipesReporterBase`). Its configuration
  arrives as a JSON string in `ExtensionConfig.json()`. Fetchers and emitters must be thread-safe: one instance serves
  every concurrent request for its id.

[source,java]
----
package org.bookshelf.tika;

import java.io.IOException;

import org.apache.tika.exception.TikaConfigException;
import org.apache.tika.pipes.api.fetcher.Fetcher;
import org.apache.tika.pipes.api.fetcher.FetcherFactory;
import org.apache.tika.plugins.ExtensionConfig;
import org.pf4j.Extension;

@Extension
public class SupplierPortalFetcherFactory implements FetcherFactory {

    @Override
    public String getName() {
        return "bookshelf-supplier-fetcher";
    }

    @Override
    public Fetcher buildExtension(ExtensionConfig extensionConfig)
            throws IOException, TikaConfigException {
        return new SupplierPortalFetcher(extensionConfig);
    }

    @Override
    public Class<?> getConfigClass() {
        return SupplierPortalFetcherConfig.class;
    }
}
----

[source,properties]
----
plugin.id=bookshelf-supplier-plugin
plugin.class=org.bookshelf.tika.BookshelfPipesPlugin
plugin.version=${project.version}
plugin.provider=Bookshelf
plugin.description=Fetches publisher files from the Bookshelf supplier portal
----

The zip holds `plugin.properties` at its root, `classes/META-INF/extensions.idx`, and `lib/` with the plugin's own jar
and its runtime dependencies. Everything on the boundary between host and plugin is declared `provided` and must not be
in `lib/`: `pf4j`, `tika-core`, `tika-plugins-core`, `tika-pipes-api`, `tika-serialization`, the logging API and,
unless you deliberately bundle your own, Jackson. A plugin that ships its own `tika-core` loads cleanly and then finds
no extensions or fails with a `ClassCastException`, because its `FetcherFactory` is a different class from the host's.
Follow the logging convention of the bundled plugins: literal fetch and emit keys only at TRACE.

The factory above was written from the 4.1.x guide and not compiled for this page. The parser-side extension points are
on xref:backend/apache-tika/extending-tika.adoc[Extending Tika].

Source: https://tika.apache.org/docs/4.1.x/pipes/plugins/writing-a-plugin.html[Apache Tika 4.1.x, Writing a Pipes
Plugin] and https://github.com/apache/tika/tree/main/tika-pipes/tika-pipes-plugins/tika-pipes-file-system[tika-pipes-file-system]
(the reference plugin).

== The Java API

=== PipesForkParser: crash-isolated parsing for your own code

`PipesForkParser` (module `tika-pipes-fork-parser`) is the 4.x replacement for the removed `ForkParser`. It is the
simplest way to give an application process isolation: you pass a `Path` or a `TikaInputStream`, a fork parses it and
the text and metadata come back in a `PipesForkResult`. Internally it writes a temporary `tika-config.json` with an
internal file-system fetcher (UUID-named, `allowAbsolutePaths: true`), the `PASSBACK_ALL` emit strategy and your
settings, and loads a `PipesParser` from it.

The Bookshelf intake check below parses every file in the inbox in Markdown and RMETA mode, lists embedded documents and
handles the three outcome classes. It also parses a stream with no file behind it, which travels inline to the fork.

[source,java]
----
package org.bookshelf.intake;

import java.io.InputStream;
import java.nio.file.Files;
import java.nio.file.Path;
import java.util.List;
import java.util.stream.Stream;

import org.apache.tika.config.TimeoutLimits;
import org.apache.tika.io.TikaInputStream;
import org.apache.tika.metadata.HttpHeaders;
import org.apache.tika.metadata.Metadata;
import org.apache.tika.metadata.TikaCoreProperties;
import org.apache.tika.pipes.api.ParseMode;
import org.apache.tika.pipes.fork.PipesForkParser;
import org.apache.tika.pipes.fork.PipesForkParserConfig;
import org.apache.tika.pipes.fork.PipesForkParserException;
import org.apache.tika.pipes.fork.PipesForkResult;
import org.apache.tika.sax.BasicContentHandlerFactory;

public class IntakeFork {

    public static void main(String[] args) throws Exception {
        Path inbox = Path.of(args.length > 0 ? args[0] : "/srv/bookshelf/inbox");
        PipesForkParserConfig config = new PipesForkParserConfig()
                .setHandlerType(BasicContentHandlerFactory.HANDLER_TYPE.MARKDOWN)
                .setParseMode(ParseMode.RMETA)
                .setTimeoutLimits(new TimeoutLimits(
                        TimeoutLimits.DEFAULT_TOTAL_TASK_TIMEOUT_MILLIS, 30_000))
                .addJvmArg("-Xmx512m")
                .setMaxFilesPerProcess(500)
                .setNumClients(2);

        List<Path> files;
        try (Stream<Path> s = Files.list(inbox)) {
            files = s.filter(Files::isRegularFile).sorted().toList();
        }

        // create once, reuse: each instance owns a pool of forked JVMs
        try (PipesForkParser parser = new PipesForkParser(config)) {
            for (Path file : files) {
                report(file.getFileName().toString(), parser.parse(file));
            }
            // a stream without a file behind it: up to maxInlineBytes travels inside the request
            try (InputStream in = Files.newInputStream(inbox.resolve("catalogue.pdf"));
                 TikaInputStream tis = TikaInputStream.get(in)) {
                Metadata hint = new Metadata();
                hint.set(TikaCoreProperties.RESOURCE_NAME_KEY, "catalogue.pdf");
                report("stream:catalogue.pdf", parser.parse(tis, hint));
            }
        } catch (PipesForkParserException e) {
            // configuration and initialization problems are thrown, not returned
            System.err.println("configuration problem (" + e.getStatus() + "): " + e.getMessage());
        }
    }

    static void report(String name, PipesForkResult result) {
        if (result.isSuccess()) {
            List<Metadata> list = result.getMetadataList();   // container first
            String text = result.getContent();                 // container text only
            System.out.printf("%-24s %-14s docs=%d type=%s chars=%d%n", name, result.getStatus(),
                    list.size(), result.getMetadata().get(HttpHeaders.CONTENT_TYPE),
                    text == null ? 0 : text.length());
            for (int i = 1; i < list.size(); i++) {
                Metadata m = list.get(i);
                System.out.printf("%-24s   embedded %s %s%s%n", "",
                        m.get(TikaCoreProperties.EMBEDDED_RESOURCE_PATH),
                        m.get(HttpHeaders.CONTENT_TYPE),
                        m.get(TikaCoreProperties.EMBEDDED_EXCEPTION) == null ? "" : " EXCEPTION");
            }
        } else if (result.isProcessCrash()) {
            // OOM, TIMEOUT or UNSPECIFIED_CRASH: the fork restarts before the next parse
            System.out.printf("%-24s CRASH %s%n", name, result.getStatus());
        } else {
            // fetch or parse problem with this document only
            System.out.printf("%-24s FAILED %s %s%n", name, result.getStatus(), result.getMessage());
        }
    }
}

==== Failures, observed

Two deliberate failures show the split between results and exceptions. A five-millisecond progress timeout makes every
parse a process crash, which `parse` returns; a non-existent `javaPath` makes the fork impossible to start, which `parse`
throws as a `PipesForkParserException`:

[source,java]
----
PipesForkParserConfig tight = new PipesForkParserConfig()
        .setTimeoutLimits(new TimeoutLimits(5, 5));
try (PipesForkParser parser = new PipesForkParser(tight)) {
    PipesForkResult r = parser.parse(Path.of("/srv/bookshelf/inbox/scanned-loan-form.pdf"));
    System.out.println(r.getStatus() + " crash=" + r.isProcessCrash() + " msg=" + r.getMessage().lines().findFirst().orElse(""));
}

PipesForkParserConfig badJava = new PipesForkParserConfig().setJavaPath("/opt/no-such-jdk/bin/java");
try (PipesForkParser parser = new PipesForkParser(badJava)) {
    parser.parse(Path.of("/srv/bookshelf/inbox/catalogue.pdf"));
} catch (PipesForkParserException e) {
    System.out.println(e.getStatus() + " initFailure=" + e.isInitializationFailure());

=== PipesParser: one document, any fetcher, any emitter

`PipesParser` (in `tika-pipes-core`) takes a `FetchEmitTuple` and returns a `PipesResult`, with everything else coming
from a config file. The same code reads from a folder today and from a bucket tomorrow. It is thread-safe: each call
borrows one of the `numClients` forks and waits up to `maxWaitForClientMillis` for one to free up.

Against the Bookshelf file (fetcher `inbox`, emitter `extracts`), this program writes one extract from the fork, gets
one back instead, and asks for a file that is not there:

[source,java]
----
package org.bookshelf.intake;

import java.nio.file.Path;

import org.apache.tika.metadata.Metadata;
import org.apache.tika.metadata.TikaCoreProperties;
import org.apache.tika.parser.ParseContext;
import org.apache.tika.pipes.api.FetchEmitTuple;
import org.apache.tika.pipes.api.PipesResult;
import org.apache.tika.pipes.api.emitter.EmitKey;
import org.apache.tika.pipes.api.fetcher.FetchKey;
import org.apache.tika.pipes.core.EmitStrategy;
import org.apache.tika.pipes.core.EmitStrategyConfig;
import org.apache.tika.pipes.core.PipesParser;

public class OneDoc {
    public static void main(String[] args) throws Exception {
        try (PipesParser parser = PipesParser.load(Path.of("/srv/bookshelf/tika-config.json"))) {
            // 1. the fork writes the extract itself
            ParseContext emitAll = new ParseContext();
            emitAll.set(EmitStrategyConfig.class, new EmitStrategyConfig(EmitStrategy.EMIT_ALL));
            PipesResult written = parser.parse(new FetchEmitTuple("manuscript-001",
                    new FetchKey("inbox", "manuscript.docx"),
                    new EmitKey("extracts", "single/manuscript"), new Metadata(), emitAll));
            System.out.println("emit:     " + written.status());

            // 2. the result comes back instead
            ParseContext passback = new ParseContext();
            passback.set(EmitStrategyConfig.class, new EmitStrategyConfig(EmitStrategy.PASSBACK_ALL));
            PipesResult returned = parser.parse(new FetchEmitTuple("email-001",
                    new FetchKey("inbox", "publisher-email.eml"), EmitKey.NO_EMIT,
                    new Metadata(), passback));
            System.out.println("passback: " + returned.status());
            if (returned.isSuccess() && returned.emitData() != null) {
                for (Metadata m : returned.emitData().getMetadataList()) {
                    System.out.println("  " + m.get(TikaCoreProperties.EMBEDDED_RESOURCE_PATH)
                            + " | " + m.get("Content-Type"));
                }
            }

            // 3. a key that is not there
            PipesResult missing = parser.parse(new FetchEmitTuple("missing-001",
                    new FetchKey("inbox", "no-such-file.pdf"), new EmitKey("extracts", "missing")));
            System.out.println("missing:  " + missing.status() + " taskException=" + missing.isTaskException());
        }
    }
}

=== AsyncProcessor: the whole pipeline

`AsyncProcessor` adds the queue, the worker threads that feed the forks, the emitter threads and the reporters. You
offer tuples; it does the rest. With an iterator in the config, the tuples come from the config too:

[source,java]
----
package org.bookshelf.intake;

import java.nio.file.Path;
import java.util.concurrent.TimeoutException;

import org.apache.tika.config.loader.TikaJsonConfig;
import org.apache.tika.pipes.api.FetchEmitTuple;
import org.apache.tika.pipes.api.pipesiterator.PipesIterator;
import org.apache.tika.pipes.core.async.AsyncProcessor;
import org.apache.tika.pipes.core.pipesiterator.PipesIteratorManager;
import org.apache.tika.plugins.TikaPluginManager;

public class Intake {
    public static void main(String[] args) throws Exception {
        Path configPath = Path.of(args[0]);
        TikaJsonConfig jsonConfig = TikaJsonConfig.load(configPath);
        PipesIterator iterator = PipesIteratorManager
                .load(TikaPluginManager.load(jsonConfig), jsonConfig)
                .orElseThrow(() -> new IllegalStateException("no pipes-iterator configured"));
        long start = System.currentTimeMillis();
        try (AsyncProcessor processor = AsyncProcessor.load(configPath, iterator)) {
            for (FetchEmitTuple tuple : iterator) {
                if (!processor.offer(tuple, 120_000)) {
                    throw new TimeoutException("queue stayed full for two minutes");
                }
            }
            processor.finished();                // no more input
            while (processor.checkActive()) {    // rethrows the first worker or emitter failure
                Thread.sleep(500);
            }
            System.out.println("processed " + processor.getTotalProcessed() + " documents in "
                    + (System.currentTimeMillis() - start) + " ms");
        }
    }
}
----

[source,bash]
----
java -cp "intake.jar:lib/*" org.bookshelf.intake.Intake /srv/bookshelf/tika-config.json
----

[source,text]
----
processed 9 documents in 8313 ms
----

The extracts folder then held the nine `.json` files, `status.json` showed `+"statusCounts":{"PARSE_SUCCESS":9}+` and the
JSONL ledger had nine lines (shown in the Reporters section). Swapping the iterator for the CSV one produced the
`2026/BK-000n.json` extracts described there.

An iterator is optional. Pass `null` as the second argument of `AsyncProcessor.load` and offer tuples you build
yourself, from a Kafka consumer, a database cursor or an upload queue. `offer` blocks while the queue (`queueSize`) is
full and returns `false` if it never drains. Per-document outcomes go to the reporters, not back to the caller;
`checkActive` only surfaces failures that stop the pipeline. Because `AsyncProcessor` emits passed-back extracts itself,
the default `DYNAMIC` strategy is the right one here.

Source: https://tika.apache.org/docs/4.1.x/using-tika/java-api/pipes.html[Apache Tika 4.1.x, Tika Pipes from Java]
(AsyncProcessor: the whole pipeline).

=== Lifecycle

* `PipesForkParser`, `PipesParser` and `AsyncProcessor` are `Closeable`. Closing kills the forks and deletes the
  temporary files the parent created for them (for `PipesForkParser`, the generated config file). Use
  try-with-resources, or a container-managed bean with a destroy method.
* Create each once and share it; they are thread-safe. A new instance per document starts a JVM per document.
* Close every `TikaInputStream` you pass in: a stream without a file is spooled to a temporary file when it is larger
  than `maxInlineBytes`, and that file is removed only on close. Prefer `parse(Path)` when the document is already on
  disk; random-access formats (ZIP, OLE2, PDF) are then read in place.
* The forks inherit the parent's class path. A dependency you add to the application is visible to the forks; a
  `-cp` override in `forkedJvmArgs` that points at a different Tika version is unsupported (the IPC format is
  same-version only).

The xref:backend/apache-tika/spring-boot-integration.adoc[Spring Boot Integration] page of this section covers
`PipesForkParser` as a Spring bean with a matching shutdown.

[[_shared_server_yolo_mode]]
== Shared server ("YOLO") mode

By default every client has its own fork, so a crash can only take down the document that caused it.
`+"useSharedServer": true+` connects all clients to *one* forked JVM with several connection handlers. That saves the
memory of `numClients - 1` JVMs and is often faster: one warm JIT profile and one larger heap. The 4.1.x documentation
reports one benchmark in which shared mode came within about 5 to 15 percent of in-process parsing while per-client
mode was 20 to 35 percent slower.

[source,json]
----
{
  "pipes": {
    "numClients": 4,
    "useSharedServer": true,
    "forkedJvmArgs": ["-Xmx4g"],
    "emitStrategy": { "type": "PASSBACK_ALL" }
  },
  "parse-context": {
    "timeout-limits": { "progressTimeoutMillis": 60000 }
  }
}
----

The price is isolation, which is the reason Tika Pipes exists:

* Any OOM, timeout or crash kills the shared process and *every* in-flight document, not only the bad one. The server is
  restarted and the clients reconnect, but retrying the lost requests is up to you.
* With `EMIT_ALL`, or `DYNAMIC` for large extracts, a client whose document was emitted just before another document
  crashed the process sees only "crash" and cannot tell whether its extract reached the destination. `PASSBACK_ALL`, as
  above, removes that ambiguity.
* All parses share one heap, so size it for `numClients` times the worst document, plus headroom.
* Parsers run concurrently in one JVM, which can expose thread-safety bugs that per-client mode hides.

The project marks it experimental and not recommended for production. Consider it only for well-behaved corpora under
hard memory limits, after testing with your own documents. Not run for this page.

Source: https://tika.apache.org/docs/4.1.x/pipes/shared-server-mode.html[Apache Tika 4.1.x, Shared Server Mode (YOLO
Mode)].

== Troubleshooting and logging

=== Telling fork lines from parent lines

Forks inherit the parent's stdout and stderr, which suits containers: everything reaches the container log. The bundled
fork logging configuration (`pipes-fork-server-default-log4j2.xml`) marks fork lines with `[fork]`, and both sides
print `pipesClientId=N`, so you can follow one fork across the boundary:

[source,text]
----
INFO  [main] 22:47:56,180 [fork] pipesClientId=0 org.apache.tika.pipes.core.server.PipesServer forked JVM max heap: 512 MB
INFO  [pool-2-thread-3] 22:50:35,216 org.apache.tika.pipes.core.PipesClient clientId=0: server successfully started
----

The 4.1.0 forks in these runs also logged one `WORKER_TIMING` line per document at INFO, with the deserialization,
fetch, parse and emit times in microseconds and the tuple id. For `PipesForkParser` the id is the absolute file path, so
treat these lines as containing file names:

[source,text]
----
INFO  [main] 22:48:01,909 [fork] pipesClientId=0 org.apache.tika.pipes.timing.worker WORKER_TIMING id=/srv/bookshelf/inbox/samples.zip req_deser_us=535 ctx_merge_us=495 intermediate_wait_us=2540 handoff_us=472 fetch_us=997 parse_us=14872 emit_us=9 worker_wall_us=15896 intermediate_us=130 resp_ser_us=362 resp_write_us=138 resp_ack_us=1120 resp_bytes=3152
----

=== Knobs

[cols="2,1,3",options="header"]
|===
|Setting |Read by |Effect
|`-Dtika.pipes.server.stdio=discard` |parent |Drop all fork stdout and stderr (used for the runs on this page to keep the
console readable). Default: inherit.
|`+-Dlog4j.configurationFile=...+` in `forkedJvmArgs` |fork |Your own fork logging config instead of the bundled one.
|`+-Dtika.pipes.cacheMemoryBudgetBytes=...+` in `forkedJvmArgs` |fork |In-memory cache budget per fork; 0 or less
disables it.
|`+-Djava.io.tmpdir=...+` |parent (and inherited) |Where spooled input, unpacked files and fork folders go. Never on
tmpfs.
|`tika-app -v` |tika-app |Root logger at DEBUG for one run.
|`TIKA_PIPES_PARENT_PID` |fork (set automatically) |Parent-death watch.
|===

A property that "does nothing" is usually set on the wrong JVM: fork-side properties belong in `forkedJvmArgs`, and set
on the parent (`+java -D...+`, `MAVEN_OPTS`, Surefire `argLine`) they are silently ignored by the forks.

Logging levels follow a convention: ERROR and WARN never contain literal fetch or emit keys (documents are identified by
the tuple id), INFO is lifecycle, DEBUG is per-document progress and counts, TRACE adds the literal keys (paths, URLs,
object keys). HTTP fetchers may still include response bytes in exception messages, limited by `maxErrMsgSize`.

=== Common problems

[cols="2,3",options="header"]
|===
|Symptom |Cause and fix
|`Process exited with code 1 before connecting to socket` |The fork died during start-up: a bad `forkedJvmArgs` flag, a
missing class, too little heap. Read the lines tagged `[fork]` just before it.
|`FAILED_TO_INITIALIZE`, `+Cannot run program ...+` |`javaPath` wrong (see the run above), or the fork cannot load the
config. Fatal: fix and restart.
|A JVM crash log in the parent's output |A native crash in a fork. Tika points `-XX:ErrorFile=` at the fork's temp folder
and copies the `hs_err_pid` file into the parent's log before cleaning up.
|`+WARN ... No '<dir>' root+`, `No plugins` |`plugin-roots` folder missing. Harmless if the plugins are on the class path;
otherwise unzip the distribution or set `plugin-roots` / `setPluginsDir`.
|Unknown component name at load |Typo, or the plugin is not loaded. The error lists the names that are available.
|`CLIENT_UNAVAILABLE_WITHIN_MS` |Every fork busy for `maxWaitForClientMillis`. Raise `numClients` (within the CPU rule),
lower the load, or retry later.
|`PAYLOAD_LIMIT_EXCEEDED`, or `UNSPECIFIED_CRASH` on large documents |The result or request exceeded
`maxIpcPayloadBytes`. Raise it together with the fork heap, lower the write limit, or use `EMIT_ALL` for large extracts.
|Crashed documents missing from the output |Expected with `emitIntermediateResults: false`. Add a
`file-system-jsonl-reporter` with crash `includes`, or set `emitIntermediateResults: true`.
|Leftover `pass:c[pipes-server-*]` folders or `.tmp` files |The whole process group was killed at once (container stop,
SIGKILL), or a worker died mid-write with `atomicWrites`. Apply your own retention; tell crawlers to ignore
`pass:c[*.tmp]`.
|Host runs out of memory while spooling |`java.io.tmpdir` on tmpfs (`/dev/shm`). Move it to a disk-backed volume.
|===

== Memory, performance and robustness

* *Every fork is a JVM.* Memory is roughly `numClients` times (fork heap plus JVM overhead) plus the parent. Start-up
  takes seconds, so short-lived pipelines and per-request construction waste most of their time starting forks.
* *Throughput* scales with forks until the CPU rule (two cores per fork plus two for the parent) is exceeded. Shared
  mode trades isolation for throughput and memory.
* *IPC cost.* `PASSBACK_ALL` and small-extract passback serialize every metadata list across the socket and hold it in
  the parent; `EMIT_ALL` avoids that but loses batching. Large documents are what `DYNAMIC` exists for.
* *Disk.* Inputs larger than `maxInlineBytes`, streams from remote fetchers with `spoolToTemp`, unpacked embedded files
  and random-access parsers all use the temporary folder. 4.1.0 reduced spooling noticeably; budget the volume anyway.
* *Bounding the work.* Write limits, embedded limits, `maxUnpackBytes` and the timeouts belong in `parse-context` (see
  xref:backend/apache-tika/robustness-limits-and-timeouts.adoc[Robustness, Limits & Timeouts]). The fork protects the
  parent; the limits protect the fork's time and your destination.
* *Leaks.* `maxFilesProcessedPerProcess` recycles forks; lower it for parsers known to leak (OCR, some image libraries).

== Pitfalls and security

* *Pipes is the sandbox, not an authentication layer.* tika-server and tika-grpc run every parse in forks, but they are
  not security boundaries: whoever can reach `/pipes`, `/async` or the gRPC fetcher calls can make the server read any
  path or URL its fetchers allow. Keep them on trusted networks, behind authentication, with `allowPipes` off unless you
  need it. See xref:backend/apache-tika/security.adoc[Security] and
  xref:backend/apache-tika/tika-server-rest-api.adoc[Tika Server].
* *`basePath` is the only containment for the file-system components.* Never combine `allowAbsolutePaths: true` with keys
  from callers. Do not rely on symbolic-link containment on the emitter side.
* *Credentials* go in environment variables (`+${env:NAME}+`) or the cloud SDKs' own credential chains, never in the file.
  The forks inherit the parent's environment.
* *Do not retry crashes blindly.* A document that produced `OOM` or `TIMEOUT` will usually do so again; route it to a
  dead-letter list (the JSONL ledger) and retry it with different limits, if at all.
* *Defaults differ by entry point.* Markdown for tika-app and the pipes config, plain text for `PipesForkParser`;
  `numClients` from the CPU count, 2 for the CLIs, 1 for `PipesForkParser`. Set what you depend on.
* *`getContent()` is the container only* in RMETA mode. Embedded text is in the other list elements.
* *Kafka iterator delivery is at most once.* Use your own consumer when a lost document matters.
* *Fork-side settings on the parent are ignored.* Heap, cache budget and fork logging go into `forkedJvmArgs`.
* *Keep parent and forks on the same Tika version.* The IPC protocol is internal and same-version only.

Source: https://tika.apache.org/security-model.html[Apache Tika Security Model] and
https://tika.apache.org/docs/4.1.x/security.html[Apache Tika 4.1.x, Security].

== From 1.x to 4.x

*Tika in Action* (2011, Tika 1.x) handles robustness in chapter 9 with the `ForkParser`, which streamed SAX events
from a child process, and with careful thread and memory management in the caller. Batch processing meant your own
loops, or later the `tika-batch` module behind tika-app's `-bc` batch mode.

[cols="1,3",options="header"]
|===
|Version |What changed for Pipes
|1.x (the book) |`ForkParser` for isolation; `tika-batch` for directory runs; no fetchers or emitters.
|2.0 (July 2021) |Tika Pipes arrives: `PipesClient` and `PipesServer`, fetchers (a `FileSystemFetcher` replaces
tika-server's `enableFileUrl`), emitters and pipes iterators, configured in `tika-config.xml`. 2.x adds GCS, OpenSearch and Solr components and a JDBC reporter.
|3.x |Same model on Java 11, configured by class name in `tika-config.xml` (`<fetchers>`, `<emitters>`,
`<pipesIterator>`, `<pipes>`, `<async>`), with defaults such as `numClients` 4 and a 60 s `timeoutMillis`. 3.3.0 adds
per-file timeouts; 3.3.2 gates `/pipes`, `/async` and `/status` behind `enableUnsecureFeatures`. `ForkParser` and
`tika-batch` still exist.
|4.0 (August 2026) |Pipes becomes the engine of every service: tika-server's parsing endpoints and tika-grpc run in
forks. JSON configuration; components become PF4J plugins in `+tika-pipes-*+` modules, with `tika-pipes-core` and a
separate `tika-pipes-file-system` plugin. `PipesForkParser` replaces the removed `ForkParser`; `tika-batch` and
tika-app's `-bc` mode are removed in favour of `-a`. New parse modes `NO_PARSE`, `CONTENT_ONLY` and `UNPACK`; new
plugins (Elasticsearch, Google Drive, Microsoft Graph, Azure Blob, JSON, HTTP, Atlassian JWT, Ignite config store);
unified timeout model; `staleFetcherTimeoutSeconds` and `staleFetcherDelaySeconds` removed; the tuple JSON key
`parseContext` renamed `parse-context`; `http-fetcher` verifies TLS by default.
|4.1 (September 2026) |`file-system-jsonl-reporter`, less spooling and a fork cache budget, environment-variable
interpolation in `tika-config.json`, `PipesForkParser` honouring `javaPath` and `socketTimeoutMillis`, plugins no longer
bundling Jackson, `tempDirectory` deprecated, a Kafka iterator that no longer stops on the first empty poll.
|===
