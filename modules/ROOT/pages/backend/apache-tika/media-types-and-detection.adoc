== Media types in one page

A _media type_ (formerly called a MIME type) is the label that says what kind of data a byte sequence is. It is
registered with IANA and written `type/subtype`, optionally followed by parameters:

[source,text]
----
text/html; charset=UTF-8
application/vnd.openxmlformats-officedocument.wordprocessingml.document
application/epub+zip
----

[cols="2,5",options="header"]
|===
|Part |Meaning

|`type` |One of the top-level registries: `application`, `audio`, `font`, `image`, `message`, `model`, `multipart`, `text`, `video`.
|`subtype` |The format. A `vnd.` prefix marks a vendor tree (`application/vnd.ms-excel`), `x-` marks an unregistered, historical name (`application/x-tika-ooxml`), and a `+suffix` names the underlying syntax (`image/svg+xml`, `application/epub+zip`).
|parameters |`name=value` pairs after a semicolon. The one that matters most is `charset` on `text/*`. Parameters do not change the format: `text/html` and `text/html; charset=UTF-8` are the same type for choosing a parser.
|alias |A second name for the same format that real software produces, such as `application/x-pdf` for `application/pdf`. Tika keeps one canonical name and lists the others as aliases.
|===

Source: https://www.iana.org/assignments/media-types/media-types.xhtml[IANA media types registry] and
https://tika.apache.org/4.1.0/api/org/apache/tika/mime/MediaType.html[`MediaType`, Javadoc 4.1.0].

== MediaType and MediaTypeRegistry

`org.apache.tika.mime.MediaType` is an immutable, comparable value object. `MediaTypeRegistry` knows how types relate to
each other. Both are in `tika-core`.

[source,java]
----
import org.apache.tika.mime.MediaType;
import org.apache.tika.mime.MediaTypeRegistry;

public class TypesAndHierarchy {

    public static void main(String[] args) {
        MediaType html = MediaType.parse("text/html; charset=UTF-8");
        System.out.println(html + " | base=" + html.getBaseType()
                + " | type=" + html.getType() + " subtype=" + html.getSubtype()
                + " | params=" + html.getParameters());

        MediaTypeRegistry registry = MediaTypeRegistry.getDefaultRegistry();
        MediaType docx = MediaType.parse(
                "application/vnd.openxmlformats-officedocument.wordprocessingml.document");

        System.out.println(docx.getSubtype() + " -> " + registry.getSupertype(docx));
        System.out.println("epub -> " + registry.getSupertype(MediaType.parse("application/epub+zip")));
        System.out.println("html -> " + registry.getSupertype(MediaType.parse("text/html")));
        System.out.println("rss  -> " + registry.getSupertype(MediaType.parse("application/rss+xml")));
        System.out.println("pdf  -> " + registry.getSupertype(MediaType.parse("application/pdf")));
        System.out.println("docx is a zip? " + registry.isInstanceOf(docx, MediaType.APPLICATION_ZIP));

        System.out.println("aliases of pdf: " + registry.getAliases(MediaType.application("pdf")));
        System.out.println("normalize(application/x-pdf) = "
                + registry.normalize(MediaType.parse("application/x-pdf")));
        System.out.println("known types: " + registry.getTypes().size());
    }
}
----

Output on Tika 4.1.0:

[source,text]
----
text/html; charset=UTF-8 | base=text/html | type=text subtype=html | params={charset=UTF-8}
vnd.openxmlformats-officedocument.wordprocessingml.document -> application/x-tika-ooxml
epub -> application/zip
html -> text/plain
rss  -> application/xml
pdf  -> application/octet-stream
docx is a zip? true
aliases of pdf: [application/x-pdf]
normalize(application/x-pdf) = application/pdf
known types: 1687
----

What the output teaches:

* *The hierarchy is the reason detection can be layered.* A `.docx` file is "a kind of `application/x-tika-ooxml`, which
  is a kind of `application/zip`". When one detector says `application/zip` and another says the DOCX type, the registry
  tells Tika that the DOCX answer is the more specific one and should win.
* *Built-in heuristics fill the gaps.* If the XML registry gives no explicit parent, a `text/\*` type falls back to
  `text/plain`, a `+xml` type to `application/xml` and anything else to `application/octet-stream`, the root of the tree.
* *Always normalise before comparing.* `application/x-pdf` is an alias; compare `registry.normalize(type)` against the
  canonical name, or use `registry.isInstanceOf(type, canonical)`. Comparing strings misses aliases and parameters.
* *Parameters stay on the type.* `getBaseType()` drops them. Use it when you only care about the format.

The most useful methods:

[cols="2,4",options="header"]
|===
|Method |Use

|`MediaType.parse(String)` |Parses `type/subtype; a=b`; returns `null` for malformed input, so check for `null` on untrusted headers.
|`MediaType.application("pdf")`, `image("png")`, `+text(...)+`, `+audio(...)+`, `+video(...)+` |Factories for the common top-level types. Constants exist for `OCTET_STREAM`, `TEXT_PLAIN`, `TEXT_HTML`, `APPLICATION_XML` and `APPLICATION_ZIP`.
|`registry.getSupertype(type)` |The parent in the hierarchy.
|`registry.isSpecializationOf(a, b)` |`true` if `a` is a strict descendant of `b`.
|`registry.isInstanceOf(a, b)` |`true` if `a` equals `b` or descends from it. A `String` overload parses and normalises first.
|`registry.getChildTypes(type)` |Direct children; `application/zip` has 40 in 4.1.0.
|`registry.getAliases(type)`, `normalize(type)` |Alias handling.
|`registry.addType`, `addAlias`, `addSuperType` |Programmatic changes to a registry you own. For the shared registry, use `custom-mimetypes.xml` instead.
|===

`MediaTypeRegistry.getDefaultRegistry()` is the registry that Tika's own detectors use. `TikaLoader.getMediaTypeRegistry()`
returns the one that a loaded configuration works with.

Source: https://tika.apache.org/4.1.0/api/org/apache/tika/mime/MediaTypeRegistry.html[`MediaTypeRegistry`, Javadoc 4.1.0]
and https://tika.apache.org/3.3.2/detection.html[Apache Tika 3.3.2, Content detection].

== Where the types come from: tika-mimetypes.xml

Tika's knowledge of formats is data, not code. The file `org/apache/tika/mime/tika-mimetypes.xml` inside `tika-core`
declares 1,699 `mime-type` elements in 4.1.0 (the registry reports 1,687 distinct types after aliases are folded). Its
format is derived from the freedesktop.org shared-mime-info specification, with Tika extensions for richer magic.
The element names below were checked against the reader's constants (`MimeTypesReaderMetKeys`).

[cols="2,5",options="header"]
|===
|Element |Meaning

|`+<mime-type type="...">+` |One type. May be empty (a name that exists but has no rules).
|`+<alias type="..."/>+` |Another name for this type.
|`<acronym>`, `<_comment>`, `<tika:link>`, `<tika:uti>` |Human-readable description, specification links and the Apple UTI. Not used for detection.
|`+<glob pattern="*.pdf"/>+` |A file-name rule. `isregex="true"` makes the pattern a regular expression. Patterns must be unique across the file; when a name clashes, the most popular format gets it.
|`<magic priority="50">` |A group of byte rules. The priority orders groups: higher runs first, and lower-priority groups are skipped once a higher one matched. In 4.1.0 most groups use 50 and 60, a few go up to 80.
|`+<match value="..." type="..." offset="..."/>+` |One byte test. `type` is `string`, `stringignorecase`, `regex`, `big16`, `little16`, `host16`, `big32`, `little32`, `host32` or `unicodeLE`. `offset` is a position (`0`) or a range (`0:8192`). `mask` applies a bit mask first. Nested `match` elements are AND clauses; sibling elements are OR clauses; `minShouldMatch` requires N of several.
|`+<root-XML localName="..." namespaceURI="..."/>+` |For XML formats, identify by the root element when the generic magic says `application/xml` or `text/html`.
|`+<sub-class-of type="..."/>+` |The parent in the hierarchy.
|===

The PDF entry shows several features at once (abridged from 4.1.0):

[source,xml]
----
<mime-type type="application/pdf">
  <alias type="application/x-pdf"/>
  <acronym>PDF</acronym>
  <_comment>Portable Document Format</_comment>
  <tika:uti>com.adobe.pdf</tika:uti>
  <magic priority="50">
    <!-- Normally just %PDF- -->
    <match value="%PDF-" type="string" offset="0"/>
    <!-- Sometimes has a UTF-8 Byte Order Mark first -->
    <match value="\xef\xbb\xbf%PDF-" type="string" offset="0"/>
  </magic>
  <magic priority="40">
    <!-- a lower-priority match for %PDF-#.# near the start of the file -->
    ...
  </magic>
  <glob pattern="*.pdf"/>
</mime-type>
----

Source: https://tika.apache.org/4.1.x/api/org/apache/tika/mime/package-summary.html[`org.apache.tika.mime`] (Javadoc 4.1.0 is under `https://tika.apache.org/4.1.0/api/`),
https://github.com/apache/tika/blob/main/tika-core/src/main/resources/org/apache/tika/mime/tika-mimetypes.xml[`tika-mimetypes.xml` on GitHub]
and https://specifications.freedesktop.org/shared-mime-info-spec/latest/[freedesktop.org Shared MIME-info specification].

Two facts about the magic engine matter for performance and correctness:

* *Magic reads at most 64 KiB.* `MimeTypes.getMinLength()` returns 65,536 in 4.1.0. Rules must match inside that prefix,
  and the detector marks and resets the stream around the read, so it does not consume it. A rule with an offset beyond
  64 KiB never matches.
* *Highly specific rules get high priorities, generic ones low.* Containers need higher priorities than the things they
  contain, or a ZIP of images would be reported as an image. The file's own header comment says so.

== The pipeline: DefaultDetector

`DefaultDetector` is what `new Tika()`, `AutoDetectParser` and `TikaLoader.loadDetectors()` give you unless you
configure otherwise. In 4.1.0 its `detect` method (read from the source) does this:

image::apache-tika-detection-pipeline.svg["The 4.x detection pipeline: input, override, MimeTypes with magic, name and header hints, container detectors, text fallback, most specific type wins, result",width=900]

. *Override.* If the metadata has `tk:content-type-override` (set by you, `TikaCoreProperties.CONTENT_TYPE_USER_OVERRIDE`)
  or `tk:content-type-parser-override` (set by a parser for an embedded file), that value is the answer and nothing else
  runs.
. *`MimeTypes` (magic, name and header hints).* The first 64 KiB are matched against the magic rules. Then the name in
  `tk:resource-name` is looked up in the glob rules, and the `Content-Type` header value, if present, is looked up as a
  type. Each hint only *refines* the magic result: it replaces the magic answer only when it is the same type or a
  more specific one in the registry. When magic found nothing, the hint is used as is. The result is stored in
  `tk:content-type-magic-detected`.
. *Container detectors.* Detectors loaded through the service-provider mechanism look inside the file: ZIP (OOXML,
  ODF, EPUB, JAR, IPA, KMZ, Frictionless Data Package and others), OLE2 (Word `.doc`, Excel `.xls`, Outlook `.msg`),
  gzip specialisations, Ogg, Matroska, binary property lists, raw TIFF. They run in name order and the registry keeps
  the most specific answer.
. *Text fallback.* Only if steps 2 and 3 both said `application/octet-stream`, `TextDetector` scans the first 512 bytes
  for control characters and returns `text/plain` if there are none (or very few).
. *Most specific wins.* The result is the most specific of the magic answer, the container answer and the text answer;
  for unrelated types the container answer is preferred.

The detectors that `new DefaultDetector().getDetectors()` lists in a 4.1.0 project with `tika-parsers-standard-package`
(the magic `MimeTypes` and the text fallback are built into `DefaultDetector` itself and are not in this list):

[cols="3,4",options="header"]
|===
|Class |Recognises

|`org.apache.tika.detect.zip.DefaultZipContainerDetector` |ZIP-based formats: OOXML (via `OPCPackageDetector`), OpenDocument, EPUB, JAR, IPA, KMZ, StarOffice, Frictionless Data Package, GeoGebra.
|`org.apache.tika.detect.microsoft.POIFSContainerDetector` |OLE2 containers: Word, Excel, PowerPoint, Visio, Outlook and others.
|`org.apache.tika.detect.ole.MiscOLEDetector` |Further OLE2 formats from the miscellaneous office module.
|`org.apache.tika.detect.gzip.GZipSpecializationDetector` |Specialisations of gzip.
|`org.apache.tika.detect.apple.BPListDetector` |Binary property lists and the Apple formats that use them.
|`org.apache.tika.detect.image.RawTiffDetector` |Raw TIFF variants.
|`org.apache.tika.detect.mkv.MatroskaDetector`, `org.apache.tika.detect.ogg.OggDetector` |Matroska/WebM and Ogg families.
|===

A project with fewer modules sees fewer detectors: the list is whatever is on the classpath.

=== Running the pipeline by hand

The 4.x `Detector` interface has one method:

[source,java]
----
public interface Detector extends Serializable, SelfConfiguring {
    MediaType detect(TikaInputStream tis, Metadata metadata, ParseContext parseContext)
            throws IOException;
}
----

The stream may be `null` when only the name and headers are known. The next program calls the detector directly with
the _Bookshelf_ files, each time passing the name through `Metadata`:

[source,java]
----
import java.nio.file.Path;
import org.apache.tika.config.loader.TikaLoader;
import org.apache.tika.detect.Detector;
import org.apache.tika.io.TikaInputStream;
import org.apache.tika.metadata.HttpHeaders;
import org.apache.tika.metadata.Metadata;
import org.apache.tika.metadata.TikaCoreProperties;
import org.apache.tika.parser.ParseContext;

public class DetectByHand {

    public static void main(String[] args) throws Exception {
        Detector detector = TikaLoader.loadDefault().loadDetectors();

        for (String f : new String[] {"manuscript.docx", "catalogue.pdf", "renamed-invoice.png"}) {
            Metadata md = new Metadata();
            // TikaInputStream.get(path, metadata) puts the file name into tk:resource-name
            try (TikaInputStream tis = TikaInputStream.get(Path.of(f), md)) {
                System.out.println(f + " -> " + detector.detect(tis, md, new ParseContext())
                        + "  (tk:resource-name=" + md.get(TikaCoreProperties.RESOURCE_NAME_KEY) + ")");
            }
        }

        // name only: no stream
        Metadata nameOnly = new Metadata();
        nameOnly.set(TikaCoreProperties.RESOURCE_NAME_KEY, "novel.epub");
        System.out.println("name only novel.epub -> " + detector.detect(null, nameOnly, new ParseContext()));

        // PDF bytes with a PNG name: the bytes win
        Metadata lying = new Metadata();
        lying.set(TikaCoreProperties.RESOURCE_NAME_KEY, "renamed-invoice.png");
        try (TikaInputStream tis = TikaInputStream.get(Path.of("catalogue.pdf"))) {
            System.out.println("pdf bytes + png name -> " + detector.detect(tis, lying, new ParseContext()));
        }

        // PDF bytes with a Content-Type header of text/plain: the bytes win again
        Metadata header = new Metadata();
        header.set(HttpHeaders.CONTENT_TYPE, "text/plain");
        try (TikaInputStream tis = TikaInputStream.get(Path.of("catalogue.pdf"))) {
            System.out.println("pdf bytes + text/plain header -> " + detector.detect(tis, header, new ParseContext()));
        }

        // The user override is absolute
        Metadata forced = new Metadata();
        forced.set(TikaCoreProperties.CONTENT_TYPE_USER_OVERRIDE, "image/png");
        try (TikaInputStream tis = TikaInputStream.get(Path.of("catalogue.pdf"))) {
            System.out.println("user override -> " + detector.detect(tis, forced, new ParseContext()));
        }
    }
}
----

Output:

----

catalogue.pdf -> application/pdf  (tk:resource-name=catalogue.pdf)

[source,text]
----

=== Which hint wins

[cols="3,2,4",options="header"]
|===
|Input signal |Strength |Behaviour

|`tk:content-type-override`, `tk:content-type-parser-override` |Absolute |Returned unchanged. Use only for values you control. The user override is checked first, the parser override second.
|Magic bytes |Strong |Beat any name or header that contradicts them.
|Container structure (ZIP entries, OLE2 streams) |Strong |Refines a generic magic answer to the exact format.
|`tk:resource-name` (file name or URL path) |Hint |Applied only if it equals the magic type or specialises it. Ignored for server-side script extensions when the name is an HTTP URL.
|`Content-Type` (`HttpHeaders.CONTENT_TYPE`) |Hint |The same rule as the name.
|`tk:content-type-hint` |Hint for charset only |Read by the charset detectors, not by media type detection; see xref:backend/apache-tika/character-encoding-detection.adoc[Character Encoding Detection].
|===

=== What 4.x changed in the detector API

[cols="2,3",options="header"]
|===
|Book (1.x) and 3.x |4.x

|`Detector.detect(InputStream, Metadata)` |`detect(TikaInputStream, Metadata, ParseContext)`. The stream may be `null`.
|`TikaConfig` builds the default detector and reads `tika-config.xml` |`TikaConfig` was removed. Use `TikaLoader.loadDefault().loadDetectors()` or `TikaLoader.load(path).loadDetectors()` with a JSON file.
|Detectors read their configuration from constructor arguments or XML `<param>` elements |A detector implements the marker `SelfConfiguring`, and its JSON is resolved by `TikaLoader`; the detector names are kebab-case (`pkcs-7-detector`, `ogg-detector`).
|Container detectors in `tika-parsers`, one class per container |Container detectors live in the format modules and in `tika-parser-zip-commons`. The ZIP ones are chosen by `DefaultZipContainerDetector`, which has a ZIP file opened or salvaged for them.
|Stream left at its start by `detect(InputStream)` if it supported `mark` |`Tika.detect(InputStream)` consumes the stream; see xref:backend/apache-tika/getting-started-with-the-tika-facade.adoc[Getting Started with the Tika Facade]. With `TikaInputStream` use `rewind()` or reopen.
|`MimeTypes.getMimeType(String name)` |Deprecated; use `Tika.detect(String)` or `Detector.detect` with a `tk:resource-name`.
|`Metadata.RESOURCE_NAME_KEY` |`TikaCoreProperties.RESOURCE_NAME_KEY`, value `tk:resource-name`; the 3.x key was `resourceName`.
|===

Source: https://tika.apache.org/docs/4.1.x/migration-to-4x/migrating-to-4x.html[Migrating to Tika 4.x],

== TikaInputStream and detection

Detection needs two things from the stream: a way to peek at the first bytes and put them back, and, for container
formats, random access to the whole file. `TikaInputStream` supplies both.

* `TikaInputStream.get(Path)` or `get(Path, Metadata)` wraps a file and sets `tk:resource-name` to the file name. No
  spooling is needed because the file already exists.
* `TikaInputStream.get(byte[])` and `get(InputStream)` wrap memory or a one-way stream. When a container detector calls
  `getPath()` on a one-way stream, Tika *spools* it to a temporary file that is deleted when the stream closes.
* `rewind()` repositions the stream at its beginning for the parser that follows detection, while `mark` and `reset`
  protect the short peeks.
* `getOpenContainer()` and `setOpenContainer(Object)` let a container detector hand an already opened `ZipFile` or
  POIFS file system to the parser, so the file is opened once. The `zip:detector-zip-file-opened` metadata key says
  whether that happened.

Always put `TikaInputStream` in a try-with-resources block: closing it deletes any temporary file. The cost model is
simple: files and byte arrays are free to detect; a network stream of a ZIP-based format is copied to disk once,
whatever you do. See the spooling chapter of the 4.1.x documentation for the limits that govern it.

Source: https://tika.apache.org/4.1.0/api/org/apache/tika/io/TikaInputStream.html[`TikaInputStream`, Javadoc 4.1.0]
and https://tika.apache.org/docs/4.1.x/advanced/spooling.html[Apache Tika 4.1.x, Spooling].

== Container detection and salvaging

OOXML (`.docx`, `.xlsx`, `.pptx`), OpenDocument, EPUB and plain archives all begin with the ZIP signature, so magic can
only say `application/zip`. `DefaultZipContainerDetector` opens the archive and looks at its entries and manifest to name
the real format: `[Content_Types].xml` for OOXML, `mimetype` for ODF and EPUB, and so on. OLE2 formats (the old `.doc`
and `.xls`, Outlook `.msg`) are handled the same way by `POIFSContainerDetector` and `MiscOLEDetector`, which read the
directory of streams inside the compound file.

When the central directory of a ZIP is damaged or missing, for example because the upload was cut off, Tika tries to
_salvage_ the file: it reads the local file headers at the start of the archive and rebuilds a directory. Salvaging
happens only when `DefaultZipContainerDetector` is used, the `ParseContext` carries `ParsingIntent.WILL_PARSE`
(`AutoDetectParser` sets it) and the file cannot be opened normally. A salvaged file gets the metadata key
`zip:salvaged=true`.

The next program truncates the `manuscript.docx` stand-in to several lengths and detects each prefix with the intent set:

[source,java]
----
import java.nio.file.Files;
import java.nio.file.Path;
import java.util.Arrays;
import org.apache.tika.detect.DefaultDetector;
import org.apache.tika.io.TikaInputStream;
import org.apache.tika.metadata.Metadata;
import org.apache.tika.parser.ParseContext;
import org.apache.tika.parser.ParsingIntent;

public class TruncatedUpload {

    public static void main(String[] args) throws Exception {
        byte[] docx = Files.readAllBytes(Path.of("manuscript.docx"));
        for (double fraction : new double[] {1.0, 0.9, 0.6, 0.1}) {
            Path cut = Files.createTempFile("cut", ".bin");
            Files.write(cut, Arrays.copyOf(docx, (int) (docx.length * fraction)));

            Metadata md = new Metadata();
            ParseContext context = new ParseContext();
            context.set(ParsingIntent.class, ParsingIntent.WILL_PARSE);
            try (TikaInputStream tis = TikaInputStream.get(cut, md)) {
                System.out.println(fraction + " -> " + new DefaultDetector().detect(tis, md, context)
                        + ", zip:salvaged=" + md.get("zip:salvaged"));
            }
        }
    }
}
----

middle of an attribute):

[source,text]
----
1.0 -> application/vnd.openxmlformats-officedocument.wordprocessingml.document, zip:salvaged=null
0.9 -> application/vnd.openxmlformats-officedocument.wordprocessingml.document, zip:salvaged=true
0.6 -> application/vnd.openxmlformats-officedocument.wordprocessingml.document, zip:salvaged=true
0.1 -> application/x-tika-ooxml, zip:salvaged=true
----

A cut file that still holds the content-types entry keeps its exact type; one that does not degrades to the generic
`application/x-tika-ooxml`, and is then unparseable. The practical rule: truncated uploads are not always reported as
errors by detection, so decide acceptance on a successful parse, not on the detected type alone. These figures come
from a 1.9 KB stand-in file; the thresholds in a real manuscript differ.

Source: https://tika.apache.org/docs/4.1.x/advanced/zip-detection.html[Apache Tika 4.1.x, ZIP detection and salvaging].

== Adding your own types: custom-mimetypes.xml

To teach Tika a type of your own, write a `custom-mimetypes.xml` in the same format as `tika-mimetypes.xml` and put it on
the classpath. `MimeTypesFactory` loads `tika-mimetypes.xml` first, then every `custom-mimetypes.xml` found at the root
of any classpath entry, then, if the system property `tika.custom-mimetypes` is set, that external file. Later
definitions are added to the registry, so a custom file can add types and rules and set parents. The Bookshelf intake
service has three formats of its own:

[source,xml]
----
<?xml version="1.0" encoding="UTF-8"?>
<mime-info>

  <!-- A purchase order: a text file whose first bytes identify it. -->
  <mime-type type="application/vnd.bookshelf.order">
    <_comment>Bookshelf purchase order</_comment>
    <glob pattern="*.bso"/>
    <magic priority="60">
      <match value="BSHELF-ORDER/1" type="string" offset="0"/>
    </magic>
    <sub-class-of type="text/plain"/>
  </mime-type>

  <!-- An XML manifest recognised by its root element and namespace. -->
  <mime-type type="application/vnd.bookshelf.manifest+xml">
    <root-XML localName="manifest" namespaceURI="urn:bookshelf:manifest:1"/>
    <glob pattern="*.bsm"/>
    <sub-class-of type="application/xml"/>
  </mime-type>

  <!-- A batch of manuscripts: a ZIP that a custom Detector recognises (next section). -->
  <mime-type type="application/vnd.bookshelf.batch+zip">
    <glob pattern="*.bsb"/>
    <sub-class-of type="application/zip"/>
  </mime-type>

</mime-info>
----

Save it as `src/main/resources/custom-mimetypes.xml`. With the file on the classpath the facade needs no changes:

[source,java]
----
Tika tika = new Tika();
System.out.println(tika.detect(Path.of("order-0042.bso")));   // application/vnd.bookshelf.order
System.out.println(tika.detect(Path.of("order-0042.txt")));   // same bytes, wrong name: still the order type
System.out.println(tika.detect(Path.of("intake.bsm")));       // application/vnd.bookshelf.manifest+xml
System.out.println(tika.detect(Path.of("other.xml")));        // application/xml
----

Output:

[source,text]
----
order-0042.bso -> application/vnd.bookshelf.order
order-0042.txt -> application/vnd.bookshelf.order
intake.bsm -> application/vnd.bookshelf.manifest+xml
other.xml -> application/xml
----

The `.txt` copy is typed by its magic, because a type that is a specialisation of `text/plain` outranks the name's
`text/plain`. A custom type only gets a parser if one is registered for it: until then `AutoDetectParser` falls back to the
parent's parser (here, the text parser for the order, the XML parser for the manifest), which is usually what you want.

Notes on custom types:

* *Classpath, not working directory.* The file must be at the root of a jar or directory on the classpath of the JVM
  that does the detection. For the CLI or the server, put the jar in the extras directory described in the setup and
  Docker pages, or use `-Dtika.custom-mimetypes=/path/to/custom-mimetypes.xml` (the property name comes from the 4.1.0
  source; not run here).
* *Use `sub-class-of`.* Without a parent, a new type derives from `application/octet-stream` and cannot refine anything.
* *Pick priorities deliberately.* The default Tika groups sit mostly at 50 and 60; give a strict container rule more, a
  loose rule less.
* *Glob clashes.* Two types claiming `*.bso` give an unpredictable winner. Prefix vendor types with `vnd.`.
* *3.x location.* The 3.x guide describes the same file under `org/apache/tika/mime/custom-mimetypes.xml`; in 4.1.0 the
  loader searches the classpath root, which is where this example placed it. Keep to the root in new code.

Source: https://tika.apache.org/3.3.2/detection.html[Apache Tika 3.3.2, Content detection (custom mime types)] and
https://tika.apache.org/4.1.0/api/org/apache/tika/mime/MimeTypesFactory.html[`MimeTypesFactory`, Javadoc 4.1.0].

== A custom Detector

Some formats cannot be expressed as bytes at an offset: a ZIP that contains `bookshelf-batch.json` needs the archive's
directory. That is a job for a `Detector`. This one returns the batch type only for such ZIPs and otherwise says nothing
(`application/octet-stream`), which, as in the composite, never overrides another detector's answer:

[source,java]
----
package demo;

import java.io.IOException;
import java.util.zip.ZipFile;
import org.apache.tika.detect.Detector;
import org.apache.tika.io.TikaInputStream;
import org.apache.tika.metadata.Metadata;
import org.apache.tika.mime.MediaType;
import org.apache.tika.parser.ParseContext;

/** Recognises a ZIP that carries a bookshelf-batch.json entry. */
public class BatchZipDetector implements Detector {

    public static final MediaType BATCH = MediaType.application("vnd.bookshelf.batch+zip");

    @Override
    public MediaType detect(TikaInputStream tis, Metadata metadata, ParseContext context)
            throws IOException {
        if (tis == null) {
            return MediaType.OCTET_STREAM;
        }
        // Cheap guard first: a ZIP starts with PK\003\004.
        tis.mark(4);
        byte[] head = new byte[4];
        int n = tis.read(head);
        tis.reset();
        if (n < 4 || head[0] != 'P' || head[1] != 'K' || head[2] != 3 || head[3] != 4) {
            return MediaType.OCTET_STREAM;
        }
        // Random access needs a file; TikaInputStream spools to disk only if necessary.
        try (ZipFile zip = new ZipFile(tis.getPath().toFile())) {
            if (zip.getEntry("bookshelf-batch.json") != null) {
                return BATCH;
            }
        } catch (IOException e) {
            // not a readable ZIP: say nothing
        }
        return MediaType.OCTET_STREAM;
    }
}
----

Register it with the standard Java service mechanism, in
`src/main/resources/META-INF/services/org.apache.tika.detect.Detector`:

[source,text]
----
demo.BatchZipDetector
----

`DefaultDetector` loads service-registered detectors, sorts them by class name and runs them after magic. Because the
custom file above declared `application/vnd.bookshelf.batch+zip` as a child of `application/zip`, the composite accepts
the detector's answer as more specific than the ZIP one:

[source,text]
----
batch.zip -> application/vnd.bookshelf.batch+zip
plain.zip -> application/zip
batch isInstanceOf zip = true
----

Rules for custom detectors:

* *Do not consume the stream.* Peek with `mark` and `reset`, or use `getPath()`/`rewind()`. The parser reads the same
  stream afterwards.
* *Return `application/octet-stream` for "I do not know".* Never throw for foreign data.
* *Be cheap or be late.* A detector runs for every file of every type. Test a signature first, as above, and open the
  file only when it matters.
* *Register the type in the registry.* A detector that returns a type the registry does not know as a descendant of
  what the earlier detectors returned loses to the earlier answer.
* *The class is yours to keep serialisable.* `Detector` extends `Serializable`; keep state out of it or make it
  `transient`.
* *Order.* Service-loaded detectors run in class-name order after the built-in ones. To control order or to wrap
  `DefaultDetector`, build your own `CompositeDetector` and pass it to `new Tika(detector, parser)`.

The `@TikaComponent` annotation that Tika's own detectors carry is used by its build to generate the component index that
JSON configuration reads; this page used the plain service file, which `DefaultDetector` loads without it. How a
custom detector is addressed by name in `tika-config.json` was not verified here.

Source: https://tika.apache.org/3.3.2/detection.html[Apache Tika 3.3.2, Content detection (custom detector)],
https://tika.apache.org/4.1.0/api/org/apache/tika/detect/CompositeDetector.html[`CompositeDetector`, Javadoc 4.1.0] and
the https://github.com/apache/tika/tree/main/tika-example[`tika-example` module].

== Configuring detectors in tika-config.json

In 4.x, detectors are configured in the `detectors` array of the JSON file, loaded with `TikaLoader`. A list names
*only* the detectors it contains; to keep the defaults add a `default-detector` entry.

.Keep the defaults, drop two families (`tika-config.json`)
[source,json]
----
{
  "detectors": [
    {
      "default-detector": {
        "exclude": ["ogg-detector", "matroska-detector"]
      }
    }
  ]
}
----

Loading it and listing what is left:

[source,java]
----
TikaLoader loader = TikaLoader.load(Path.of("tika-config.json"));
Detector detector = loader.loadDetectors();
Tika tika = new Tika(detector, loader.loadAutoDetectParser());
----

Result in the scratch project: the `DefaultDetector` listed `BatchZipDetector`, `BPListDetector`,
`GZipSpecializationDetector`, `RawTiffDetector`, `POIFSContainerDetector`, `MiscOLEDetector` and
`DefaultZipContainerDetector`; the Ogg and Matroska detectors were gone, and `catalogue.pdf` still detected as
`application/pdf`. Excluding detectors you never need saves a little work per file and shrinks the attack surface.

=== The PKCS7 / CMS detector

By default a CMS (PKCS7) message is typed by magic only, as `application/pkcs7-signature`; the parser refines the subtype
later. The opt-in `pkcs-7-detector` types it earlier, for example as `application/pkcs7-mime; smime-type=signed-data`.
Because its answer is a sibling of the magic answer, not a specialisation, the composite keeps the first of two siblings,
so it must be listed *before* `default-detector`:

[source,json]
----
{
  "detectors": [
    { "pkcs-7-detector": {} },
    { "default-detector": {} }
  ]
}
----

Loading this file in the scratch project produced a `CompositeDetector` of `org.apache.tika.detect.crypto.Pkcs7Detector`
followed by `DefaultDetector`, which verifies the names and the order. The detection of a real CMS file was not run (no
signed sample is part of the Bookshelf set); enable it only if routing depends on the CMS subtype before parsing.

[NOTE]
====
In 3.x the same configuration was XML (`+<detectors><detector class="..."/></detectors>+`) read by `TikaConfig`. That class
no longer exists in 4.x, so there is no `TikaConfig` equivalent of the examples above; migrate to JSON.
====

Source: https://tika.apache.org/docs/4.1.x/configuration/detectors.html[Apache Tika 4.1.x, Detectors configuration]
and https://tika.apache.org/docs/4.1.x/migration-to-4x/migrating-to-4x.html[Migrating to Tika 4.x].

== Applied: validating uploads by content

The _Bookshelf_ intake service receives `renamed-invoice.png`, a PDF whose extension says PNG. The OWASP File Upload
Cheat Sheet is explicit that the `Content-Type` header and the extension come from the client and can be forged, and
that content should be validated on the server. Tika gives a direct way: detect from the bytes, compare with the name,
accept only an allow-list.

[source,java]
----
import java.io.IOException;
import java.nio.file.Path;
import java.util.Set;
import org.apache.tika.config.loader.TikaLoader;
import org.apache.tika.detect.Detector;
import org.apache.tika.io.TikaInputStream;
import org.apache.tika.metadata.Metadata;
import org.apache.tika.metadata.TikaCoreProperties;
import org.apache.tika.mime.MediaType;
import org.apache.tika.mime.MediaTypeRegistry;
import org.apache.tika.mime.MimeTypes;
import org.apache.tika.parser.ParseContext;

public class UploadGuard {

    /** Types Bookshelf accepts from publishers. */
    private static final Set<MediaType> ALLOWED = Set.of(
            MediaType.application("pdf"),
            MediaType.application("vnd.openxmlformats-officedocument.wordprocessingml.document"),
            MediaType.application("epub+zip"),
            MediaType.image("png"),
            MediaType.image("jpeg"));

    private final Detector detector;
    private final MediaTypeRegistry registry =
            MimeTypes.getDefaultMimeTypes().getMediaTypeRegistry();

    public UploadGuard() throws Exception {
        this.detector = TikaLoader.loadDefault().loadDetectors();
    }

    public String check(Path file, String claimedName) throws IOException {
        Metadata nameOnly = new Metadata();
        nameOnly.set(TikaCoreProperties.RESOURCE_NAME_KEY, claimedName);

        MediaType byName;
        MediaType byContent;
        try (TikaInputStream tis = TikaInputStream.get(file)) {
            byName = detector.detect(null, nameOnly, new ParseContext());
            byContent = registry.normalize(detector.detect(tis, new Metadata(), new ParseContext()));
        }
        if (!ALLOWED.contains(byContent)) {
            return "REJECT " + claimedName + ": content is " + byContent;
        }
        if (!byContent.equals(byName)) {
            return "REJECT " + claimedName + ": name says " + byName + " but content is " + byContent;
        }
        return "ACCEPT " + claimedName + " as " + byContent;
    }

    public static void main(String[] args) throws Exception {
        UploadGuard guard = new UploadGuard();
        System.out.println(guard.check(Path.of("manuscript.docx"), "manuscript.docx"));
        System.out.println(guard.check(Path.of("catalogue.pdf"), "catalogue.pdf"));
        System.out.println(guard.check(Path.of("renamed-invoice.png"), "renamed-invoice.png"));
    }
}
----

Output:

[source,text]
----
ACCEPT manuscript.docx as application/vnd.openxmlformats-officedocument.wordprocessingml.document
ACCEPT catalogue.pdf as application/pdf
REJECT renamed-invoice.png: name says image/png but content is application/pdf
----

The same check belongs in a web layer. The JSF pages of this site show how a Faces application receives uploaded files,
including the `Part` and the declared content type that must not be trusted:
xref:web/jsf/file-upload-and-download.adoc[File Upload and Download] and
xref:web/jsf/primefaces-files-media-charts-and-drag-drop.adoc[PrimeFaces: Files, Media, Charts and Drag and Drop].
Call the guard from the backing bean or from a validator, with the stream of the `Part`, before anything is stored or
handed to a parser.

What detection does and does not give you:

* *It is classification, not validation.* A file typed `application/pdf` has the PDF signature; it can still be
  malformed, huge, encrypted or hostile. Parse untrusted files in a forked or isolated process (see
  xref:backend/apache-tika/tika-pipes.adoc[Tika Pipes] and
  xref:backend/apache-tika/robustness-limits-and-timeouts.adoc[Robustness, Limits & Timeouts]) and apply size, time and depth limits.
* *Polyglots exist.* A file can be valid in two formats. Tika returns one answer; deny-lists of dangerous types are
  weaker than allow-lists of expected ones.
* *Compare, then decide.* The mismatch between name and content is itself a useful signal: log it, reject it or store the
  file under a name derived from the detected type, never the client's.
* *Rename on storage.* Store uploads under a generated name outside any web-served directory, with the extension taken
  from the detected type (`+MimeTypes.forName(...).getExtension()+` gives `.pdf` for PDF), as the OWASP sheet advises.
* *Keep the allow-list in the registry's terms.* Use `registry.isInstanceOf(type, canonical)` if a family is acceptable
  (for example any `image/*` you can render), and normalise aliases first.
* *Header limits.* A web server that sets `Content-Length` lies about size no better than about type; enforce the real byte
  count while reading.

Source: https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html[OWASP File Upload Cheat Sheet] and
https://tika.apache.org/security-model.html[Apache Tika, Security model].

== Pitfalls

* *Detecting by name only.* `Tika.detect(String)` and `detect(Path)` without stream access are guesses from the extension.
* *Reading a stream twice.* In 4.x `Tika.detect(InputStream)` leaves the stream advanced. Use a `TikaInputStream` and
  `rewind()`, or detect from the `Path`.
* *Comparing type strings.* Use the registry; aliases and parameters make plain equality unreliable.
* *`application/octet-stream` is a result, not an error.* It means "nothing matched". Treat it as unknown, and note that
  empty files are also `application/octet-stream`.
* *The 64 KiB limit.* Magic placed deeper in a file is invisible to `MimeTypes`; write a `Detector` for such formats.
* *Parameters in comparisons.* `text/html; charset=UTF-8` is not equal to `text/html`; use `getBaseType()`.
* *Custom files in the wrong place.* A `custom-mimetypes.xml` inside a directory that is not on the classpath of the process
  that detects (the server, a forked JVM) is silently ignored.
* *Trusting the `Content-Type` header of an upload.* It is a hint at best, and any client can set it.
* *Parsers disagree with detectors after a custom type.* A type with no registered parser is parsed by its parent's
  parser; check the result on real files.

== Checklist

* Detect from the bytes with a `TikaInputStream`; give the name and headers as hints only.
* Normalise types through `MediaTypeRegistry` before comparing; use `isInstanceOf` for families.
* Treat `application/octet-stream` as unknown and decide what the intake does with it.
* Put custom types in `custom-mimetypes.xml` at the classpath root, with a `sub-class-of`, and verify with `Tika.detect`.
* Write a `Detector` only for what byte rules cannot express, keep it cheap and non-consuming, register it by service file.
* Exclude detectors you do not need in `tika-config.json`, and add `pkcs-7-detector` first only if you need the CMS subtype.
* Validate uploads against an allow-list of detected types and compare with the client's name; never trust the header.
* Decide acceptance of truncated archives on a successful parse, not on the detected type.
