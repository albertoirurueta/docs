== The deployment at a glance

In 4.x every parsing endpoint of `tika-server` (`/tika`, `/rmeta`, `/meta`, `/unpack`, `/detect`) runs its work in a
forked JVM managed by Tika Pipes. So one container is not one JVM: it is a light _parent_ JVM that owns the HTTP ports,
and up to `pipes.numClients` _forked_ JVMs that parse one document each at a time. A document that crashes, exhausts
memory or times out kills one fork; the request gets a `503`, the fork is restarted, and the parent stays up. That model
drives most of this page: the container memory and CPU limits must cover the forks, not just the parent.

image::apache-tika-deployment.svg["The Bookshelf intake service calls a Kubernetes Service that routes to a tika-server pod. Inside the pod, the parent JVM owns ports 9998 and 9404 and drives three forked JVMs over IPC; the pod mounts tika-config.json from a ConfigMap, an emptyDir at /tmp, the image's /opt/tika-server and optional /tika-extras jars; Prometheus scrapes port 9404 and the kubelet probes port 9998",width=960]

The figure shows the Kubernetes deployment built at the end of the page: two replicas of a pod with 8 CPUs and 8 GiB,
each running three forks with a 1.5 GB heap. The same shape applies to a single `docker run` on a laptop, with the
container limits playing the role of the pod limits.

[cols="2,3,3",options="header"]
|===
|Line |Container process model |Consequence for sizing

|4.x (`apache/tika:4.1.0-1`)
|Parent JVM plus up to `pipes.numClients` forked JVMs, started lazily and reused. Default `numClients` is derived from the
CPU count (1 to 4).
|Memory and CPU limits must cover the parent and every fork. Tika divides the heap and the CPUs between the forks
automatically unless you set them.

|3.x (`apache/tika:3.3.1.0`)
|Parent watchdog plus a single forked server process by default (`-noFork` ran it in-process, the legacy 1.x mode).
|One child heap to size, set with `forkedJvmArgs` in `tika-config.xml`.

|1.x
|One JVM.
|One heap. 1.x images still exist on Docker Hub but the line has been unsupported since 30 September 2022.
|===

== Choosing an image

The project publishes two repositories on Docker Hub: `apache/tika` (the REST server, port 9998, in a minimal and a
`-full` variant) and `apache/tika-grpc` (the gRPC server, port 9090). Since 4.0.0-alpha-1 the Dockerfiles live in the
main source tree, under `tika-server/docker-build/` and `tika-grpc/docker-build/`; the older `apache/tika-docker`
repository still builds 3.x patch images and its README still describes the pre-4.x tags.

[cols="2,4,2,2",options="header"]
|===
|Image |Contents (from the 4.1.0 Dockerfiles) |Port and platforms |Compressed size of `4.1.0-1` on amd64

|`apache/tika:4.1.0-1` (minimal)
|Ubuntu 26.04 (resolute, pinned by digest), `openjdk-25-jre-headless`, `ca-certificates`, and the unzipped
`tika-server-standard-4.1.0.zip`. Every pure-Java parser, no external tools, no `curl` or `wget`.
|9998; `linux/amd64`, `linux/arm64`, `linux/s390x`
|about 190 MB (189,787,970 bytes)

|`apache/tika:4.1.0-1-full`
|The minimal content plus Tesseract OCR with the `eng`, `ita`, `fra`, `spa`, `deu` and `jpn` language packs, GDAL,
ImageMagick, ffmpeg, the Liberation, FreeFont, Noto CJK and Microsoft core fonts, `wget` and `cabextract`. Sets
`OMP_THREAD_LIMIT=1`.
|9998; `linux/amd64`, `linux/arm64`, `linux/s390x`
|about 589 MB (589,425,668 bytes)

|`apache/tika-grpc:4.1.0-1`
|Ubuntu 26.04, a JRE (the Dockerfile's default `JRE` argument is `openjdk-21-jre-headless`), Tesseract with `eng`, `ita`,
`fra`, `spa`, `deu`, GDAL, the same font sets, the `tika-grpc` jar, its libraries and the pipes plugins under
`/tika/plugins`. No ImageMagick or ffmpeg.
|9090; `linux/amd64`, `linux/arm64`
|about 1.03 GB (1,033,715,238 bytes)
|===

Which one for Bookshelf? The intake service receives `scanned-loan-form.pdf` and `book-cover.jpg`, which need OCR, so it
runs `-full`. A deployment that only receives born-digital files (`manuscript.docx`, `catalogue.pdf`, `novel.epub`,
`reviews-es.html`) should take the minimal image: a third of the size, a smaller attack surface, and nothing that shells
out to native programs. Choose `-full` when you OCR scanned documents, parse geospatial rasters with GDAL, or feed audio
and video to a MEDIA inference binding (ffmpeg); see xref:backend/apache-tika/ocr-with-tesseract.adoc[OCR with
Tesseract] and xref:backend/apache-tika/vlm-parsers-and-inference.adoc[VLM Parsers & Inference]. Choose
`apache/tika-grpc` only when your clients speak gRPC; it is a different server with its own configuration, covered in
xref:backend/apache-tika/tika-grpc.adoc[Tika gRPC].

`OMP_THREAD_LIMIT=1` in the `-full` and gRPC images stops each Tesseract process from starting one OpenMP thread per
core. With several forks each running OCR, unlimited OpenMP threads would oversubscribe the CPU the same way unlimited
GC threads do (see <<memory-and-cpu,Memory and CPU inside a container>>). Keep it unless you have measured a reason not
to.

If none of the variants fits (for example you need Tesseract language packs the `-full` image does not install), build
your own image `FROM` one of them rather than from scratch. The `full/Dockerfile` accepts a `LANGUAGES` build argument
for the Tesseract packs, but it downloads the signed release zip from an Apache mirror and verifies it against the
project `KEYS` file, so it builds only released versions, never your working tree.

[source,dockerfile]
----
# Bookshelf variant of the full image with Portuguese and Dutch OCR packs added.
FROM apache/tika:4.1.0-1-full
USER root
RUN apt-get update \
 && DEBIAN_FRONTEND=noninteractive apt-get install --yes --no-install-recommends \
      tesseract-ocr-por tesseract-ocr-nld \
 && apt-get clean && rm -rf /var/lib/apt/lists/*
USER 35002:35002
----

The `USER root` / `USER 35002:35002` pair matters: the base image ends with `USER 35002:35002`, so `apt-get` would fail
without switching, and forgetting to switch back would run your image as root. This Dockerfile was not built for this
page; the package names are the Ubuntu ones the official `full/Dockerfile` composes from its
`LANGUAGES` argument.

Source: https://tika.apache.org/docs/4.1.x/using-tika/docker.html[Apache Tika 4.1.x, Running Tika in Docker],
https://github.com/apache/tika/tree/4.1.0/tika-server/docker-build[`tika-server/docker-build` at 4.1.0],
https://github.com/apache/tika/tree/4.1.0/tika-grpc/docker-build[`tika-grpc/docker-build` at 4.1.0] and

== Tags, digests and platforms

Starting with 4.0.0-alpha-1 every image is published under three kinds of tag:

[cols="2,2,4",options="header"]
|===
|Tag form |Example |Behaviour

|`+<version>+`
|`4.1.0`, `4.1.0-full`
|Rolling. Moves when the image is rebuilt for the same Tika release (for example for a base-image security fix).

|`+<version>-<N>+`
|`4.1.0-1`, `4.1.0-1-full`
|Immutable, never reassigned. `N` counts rebuilds from 1. **Pin this in production.**

|`latest`, `latest-full`
|`latest`
|Rolling, newest stable release only. Pre-releases never move it. Never deploy it.
|===

Snapshot tags (`4.2.0-SNAPSHOT`, `4.1.1-SNAPSHOT` and their `-full` twins) are rebuilt from development branches and
must not be deployed either.

On the baseline date Docker Hub showed these tags for 4.1.0, all published on 29 September 2026:

[cols="2,4",options="header"]
|===
|Tags |Image index digest

|`4.1.0-1`, `4.1.0`, `latest`
|`sha256:06bcdbd09aca073293e5a171ad161418cc93c91d58d9e4e205064eade84889d4`

|`4.1.0-1-full`, `4.1.0-full`, `latest-full`
|`sha256:ab9cc988828c594d32d6409e1850d1c8d83152ea793ef5fe0e7862ac0f9e5891`
|===

So `latest` now points at 4.1.0. The README of the old `apache/tika-docker` repository still says `latest` tracks the 3.x
line; that text predates 4.0.0 and is no longer true.

For a reproducible deployment pin the immutable tag _and_ the digest. The tag documents intent for humans, the digest is
what the runtime actually checks:

[source,bash]
----
docker pull apache/tika:4.1.0-1-full@sha256:ab9cc988828c594d32d6409e1850d1c8d83152ea793ef5fe0e7862ac0f9e5891
----

To read the same metadata without pulling, ask the registry for the manifest. `docker buildx imagetools inspect` prints
the platforms and digests; the configuration (user, entry point, environment) is in the image config:

[source,bash]
----
docker buildx imagetools inspect apache/tika:4.1.0-1-full
docker buildx imagetools inspect --format '{{json .Image}}' apache/tika:4.1.0-1-full
----

These two commands were not run here; the values on this page were read with plain HTTP calls to the Docker Hub tag API
and to `registry-1.docker.io` (token, image index, manifest, config blob), which is what those commands do.

Platforms. `apache/tika` 4.x is published for `linux/amd64`, `linux/arm64` and `linux/s390x`, and `docker pull` picks the
right one, so the same tag works on an x86 build server, an Apple Silicon laptop and an AWS Graviton node.
`apache/tika-grpc` is published for `linux/amd64` and `linux/arm64` only. 32-bit ARM (`linux/arm/v7`) was dropped: on
Docker Hub the last tag that carries it is `3.3.0.0`.

The 3.x line uses a different scheme: four-part tags `<tika-version>.<docker-build>` such as `3.3.1.0` and
`3.3.1.0-full`, still built from `apache/tika-docker`. On the baseline date the newest 3.x image was `3.3.1.0` (27 May
2026); there was no image for 3.3.2 on Docker Hub, although 3.3.2 was released on 16 July 2026. If you must stay on 3.x,
build your own image from the 3.3.2 zip or accept 3.3.1, and read
xref:backend/apache-tika/security.adoc[Security] before choosing.

== What is inside the image

Everything you mount or override has to fit this layout. The values below come from the `apache/tika:4.1.0-1` and
`4.1.0-1-full` image configurations and from the `tika-server-standard-4.1.0.zip` that the Dockerfile unzips:

[cols="2,5",options="header"]
|===
|Path or setting |Value

|`/opt/tika-server`
|The unzipped distribution: `tika-server-standard-4.1.0.jar` (a thin launcher), `lib/` (147 jars in 4.1.0), `plugins/`
(only `tika-pipes-file-system` is bundled), `bin/` (the service scripts of the zip, unused by the image), `LICENSE` and
`NOTICE`. Copied in owned by root, so the server cannot write into it.

|Working directory
|`/opt/tika-server`. tika-server falls back to `plugins/` relative to the working directory when it looks for pipes
plugins, which is why the Dockerfile sets it.

|`/tika-extras`
|On the classpath, absent from the image until you mount or copy something there. Extra jars go here.

|User
|`35002:35002` (UID and GID), not root, no name in `/etc/passwd`. The Dockerfile comment calls it a random UID chosen to be
unused elsewhere.

|Entry point
|`+/bin/sh -c 'exec java -cp "/opt/tika-server/*:/opt/tika-server/lib/*:/tika-extras/*" org.apache.tika.server.core.TikaServerCli -h 0.0.0.0 $0 $@'+`

|Command
|None. Whatever you put after the image name (`docker run`), in `command:` (Compose) or in `args:` (Kubernetes) is
appended to the entry point.

|Environment
|`TIKA_VERSION=4.1.0`; the `-full` image adds `OMP_THREAD_LIMIT=1`. No `JAVA_OPTS` hook: the entry point does not read one.

|Exposed port
|`9998/tcp`. The metrics port is not exposed in the image; publish it yourself when you enable it.

|Writable paths
|Only the JVM temp directory, `/tmp`. tika-server creates `+tika-server-input-*+` (spooled request bodies),
`+tika-server-unpack-*+` and one `+pipes-server-*+` directory per fork there.
|===

Three consequences:

* **Do not pass `-h` again.** The entry point already binds to `0.0.0.0` inside the container; network exposure is decided
  by how you publish the port, not by `-h`. Pass `-c`, `-p`, `-i` and `--metricsPort` as needed.
* **In Kubernetes use `args:`, not `command:`.** `command:` replaces the image's entry point, and with it the classpath
  that includes `/tika-extras` and `lib/`. The official Compose example for custom OCR overrides the entry point only
  because it adds a directory to the classpath, and it copies the whole `+java -cp ...+` line to do so.
* **Anything you mount must be readable by UID 35002.** A bind-mounted `tika-config.json` with mode `0600` owned by your
  user fails at startup with a permission error. Directories the server writes to must be writable by that UID; in
  practice that is only `/tmp`.

What a container actually runs looks like this. The process list below comes from the local run that reproduced the
entry point, with the paths rewritten to the container layout; the forked JVMs read most of their arguments from an
`@`-file in their temp directory:

[source,text]
----
java -cp /opt/tika-server/*:/opt/tika-server/lib/*:/tika-extras/* org.apache.tika.server.core.TikaServerCli -h 0.0.0.0 -c /config/tika-config.json
java @/tmp/pipes-server-0-17241709522081129930/jvm-args.txt -Djava.awt.headless=true -Dlog4j.configurationFile=classpath:pipes-fork-server-default-log4j2.xml -DpipesClientId=0 -Xmx1g -XX:ErrorFile=...
java @/tmp/pipes-server-0-8531678959168089369/jvm-args.txt -Djava.awt.headless=true ... -Xmx1g ...
----

Source: https://tika.apache.org/docs/4.1.x/using-tika/docker.html[Apache Tika 4.1.x, Running Tika in Docker, What is
inside], the
https://github.com/apache/tika/blob/4.1.0/tika-server/docker-build/minimal/Dockerfile[minimal Dockerfile at 4.1.0] and

== Running a container

The smallest useful run publishes the port on the loopback interface only:

[source,bash]
----
docker run -d --name tika -p 127.0.0.1:9998:9998 apache/tika:4.1.0-1
curl -s http://localhost:9998/version
curl -s -T catalogue.pdf http://localhost:9998/tika/text
----

Output (from the local run of the same 4.1.0 distribution with the image's classpath, no configuration file):

[source,text]
----
Apache Tika 4.1.0
Bookshelf spring catalogue
Forty titles from independent publishers.
----

In 4.x the output format is chosen by the path (`/tika/text`, `/tika/md`, `/tika/xml`), not by an `Accept` header; see
xref:backend/apache-tika/tika-server-rest-api.adoc[Tika Server (REST API)].

The startup log shows what the server decided, which is the first thing to check after deploying:

[source,text]
----
INFO  org.apache.tika.server.core.TikaServerProcess Starting Apache Tika 4.1.0 server
INFO  org.apache.tika.pipes.core.PipesParser Using per-client server mode with 3 clients
INFO  org.apache.tika.pipes.core.PerClientServerManager pipes-cpu-sizing: hostCores=8, numClients=3, parentReserved=2, autoCap=slice=2, heap=MaxRAMPercentage=25
INFO  org.apache.tika.server.core.TikaServerProcess Pipes-based parsing enabled for /tika, /rmeta, /unpack, /meta, /detect, and /pipes endpoints
----

On a host with 8 cores and no configuration, the server chose three forks, gave each fork a view of 2 CPUs, and
capped each fork's heap at 25% of the memory the JVM can see. Inside a container "the memory the JVM can see" is the
container limit; without a limit it is the whole host, which is how three forks plus the parent can each believe they may
take a quarter of a 64 GB node. **Always set `--memory` and `--cpus`** (or the Compose and Kubernetes equivalents):

[source,bash]
----
docker run -d --name tika \
  --memory 4g --cpus 4 \
  --read-only --tmpfs /tmp:size=1g \
  --cap-drop ALL --security-opt no-new-privileges \
  -p 127.0.0.1:9998:9998 \
  apache/tika:4.1.0-1
----

`--read-only` with a `tmpfs` at `/tmp` works because `/tmp` is the only place the server writes. A tmpfs lives in RAM and
counts towards the container memory, so size it to the uploads you accept (`maxRequestSizeBytes`) times the requests in
flight, or mount a volume at `/tmp` instead.

Source: https://tika.apache.org/docs/4.1.x/using-tika/docker.html[Apache Tika 4.1.x, Running Tika in Docker] and
https://tika.apache.org/docs/4.1.x/using-tika/server/index.html[Apache Tika 4.1.x, Tika Server, Basic Usage]. For the
`docker run` flags, see xref:backend/docker/running-containers.adoc[Running Containers] and
xref:backend/docker/security.adoc[Docker Security].

== Mounting tika-config.json

Mount the file read-only and point the server at it with `-c`, after the image name:

[source,bash]
----
docker run -d --name tika --memory 6g --cpus 6 \
  -v "$(pwd)/tika/tika-config.json:/config/tika-config.json:ro" \
  -p 127.0.0.1:9998:9998 \
  apache/tika:4.1.0-1-full -c /config/tika-config.json
----

The Bookshelf intake configuration used by the Compose file below:

[source,json]
----
{
  "server": {
    "port": 9998,
    "metricsPort": 9404,
    "endpoints": ["tika", "rmeta", "meta", "detect", "unpack", "version", "status"],
    "maxRequestSizeBytes": 104857600
  },
  "pipes": {
    "numClients": 2,
    "forkedJvmArgs": ["-Xmx1500m"],
    "maxWaitForClientMillis": 30000,
    "maxFilesProcessedPerProcess": 5000
  },
  "parse-context": {
    "timeout-limits": {
      "totalTaskTimeoutMillis": 300000,
      "progressTimeoutMillis": 60000
    }
  },
  "parsers": [
    { "default-parser": {} }
  ]
}
----

What each part does in a container:

[cols="2,5",options="header"]
|===
|Key |Why it is there

|`server.metricsPort`
|Turns on the Prometheus endpoint on a second port. Off by default.

|`server.endpoints`
|Only what the intake service calls, plus `version` and `status` for health checks. `status` is opt-in. Leaving out
`language` keeps the one endpoint that runs in the parent JVM (outside fork isolation) switched off; `pipes` and `async`
are not served anyway without `allowPipes`.

|`server.maxRequestSizeBytes`
|100 MB instead of the 1 GiB default. Bodies above `pipes.maxInlineBytes` (10 MB by default) are spooled to `/tmp`, so this
also bounds how much one request can write there.

|`pipes.numClients`
|Two forks: on 6 CPUs that leaves 2 for the parent and 2 per fork (see <<memory-and-cpu,Memory and CPU inside a
container>>).

|`pipes.forkedJvmArgs`
|An explicit heap per fork, which also switches off the automatic heap division.

|`pipes.maxWaitForClientMillis`
|How long a request waits for a free fork before it gets `429` with `Retry-After`. Default 60000.

|`pipes.maxFilesProcessedPerProcess`
|Recycle each fork after 5,000 documents (default 10,000), which bounds slow leaks in native libraries.

|`parse-context.timeout-limits`
|The per-document deadlines; see xref:backend/apache-tika/robustness-limits-and-timeouts.adoc[Robustness, Limits &
Timeouts].
|===

This file was loaded by the local 4.1.0 server, which parsed `catalogue.pdf` and `manuscript.docx` through `/tika`,
`/rmeta/text` and `/meta` with it, and logged:

[source,text]
----
pipes-cpu-sizing: hostCores=8, numClients=2, parentReserved=2, autoCap=slice=3, heap=user-set in forkedJvmArgs
----

(`slice=3` because the test host had 8 cores, not the 6 the Compose file grants.)

Points that bite in containers:

* **A server configuration needs a `server` section.** A `tika-config.json` with only `pipes` and `parsers` makes the
  4.1.0 server refuse to start with `+TikaConfigException: Couldn't find 'server' element+`. An empty `+"server": {}+` is
  enough.
* **The command line wins for host, port, id and metrics port.** `-h`, `-p`, `-i` and `--metricsPort` override the JSON;
  everything else (`allowPipes`, `allowPerRequestConfig`, CORS, TLS, timeouts) is JSON-only. The image always passes
  `-h 0.0.0.0`, so `server.host` in the file has no effect in a container.
* **Secrets come from the environment.** Since 4.1.0 any string value may reference `+${env:NAME}+`, so a fetcher key or
  a VLM API key is passed with `+-e NAME=...+` (or a Kubernetes Secret) instead of being written into the file. See
  xref:backend/apache-tika/configuration.adoc[Configuration] for the rules.
* **Restart to reload.** The file is read once at startup. A changed ConfigMap or bind mount takes effect only after the
  container restarts.

    <taskTimeoutMillis>300000</taskTimeoutMillis>
    <maxFiles>5000</maxFiles>
    <forkedJvmArgs>
      <arg>-Xmx1500m</arg>
    </forkedJvmArgs>

      <endpoint>tika</endpoint>

== Extra jars: /tika-extras

Mount a directory of jars at `/tika-extras`. It is already on the parent's classpath, and Tika forwards it to the forked
JVMs:

[source,bash]
----
docker run -d --name tika -p 127.0.0.1:9998:9998 \
  -v "$(pwd)/bookshelf-extras:/tika-extras:ro" \
  apache/tika:4.1.0-1 -c /config/tika-config.json
----

Typical contents are an optional component that the standard package leaves out (a tika-eval metadata filter, an extra
parser module), an optional dependency such as `jai-imageio-jpeg2000` (check its licence first), or your own component,
for example the Bookshelf shelf-code metadata filter written in
xref:backend/apache-tika/configuration.adoc[Configuration] and the custom parsers of
xref:backend/apache-tika/extending-tika.adoc[Extending Tika]. Components registered through SPI or `@TikaComponent` are
found the same way as on the plain zip, where the equivalent is the `tika.extras.dir` system property.

For production, bake the jars into your own image instead of mounting them, so the code that runs is versioned with the
image digest:

[source,dockerfile]
----
FROM apache/tika:4.1.0-1@sha256:06bcdbd09aca073293e5a171ad161418cc93c91d58d9e4e205064eade84889d4
COPY bookshelf-extras/*.jar /tika-extras/
----

`COPY` creates `/tika-extras` owned by root with world-readable files, which is what you want: UID 35002 can read the jars
but not replace them. Treat this directory as trusted code: anything in it runs with the full privileges of the Tika
process, in the parent and in every fork. Never make it writable by the server, by request handling, or by a less
trusted team.

Jars on `/tika-extras` share one classpath with `lib/`. A jar that brings its own copy of POI, PDFBox, Jackson or Log4j
will clash with the versions in `lib/`; ship only the component and the dependencies that `lib/` does not already
contain. See xref:backend/apache-tika/setup-and-installation.adoc[Setup & Installation] for the dependency-clash
discussion.

This page did not mount a real extras directory; the forwarding to forks is stated by the 4.1.x Docker page.

Source: https://tika.apache.org/docs/4.1.x/using-tika/docker.html[Apache Tika 4.1.x, Running Tika in Docker, Extra jars]
and https://tika.apache.org/docs/4.1.x/configuration/index.html[Apache Tika 4.1.x, Configuration].

== Memory and CPU inside a container

On JDK 17 and later the JVM reads the cgroup limits of its container: `Runtime.availableProcessors()` returns the CPU
limit (`--cpus`, `resources.limits.cpu`) and the default heap is a fraction of the memory limit. Tika builds on that and
sizes the forks from the same numbers. The rules, verified in the 4.1.0 source (`PipesConfig`, `PerClientServerManager`)
and in the local runs:

[cols="2,4,3",options="header"]
|===
|Setting |Rule in 4.1.0 |Observed on an 8-core host

|Default `pipes.numClients`
|`(cores - 2) / 2`, clamped to between 1 and 4. Two cores are reserved for the parent; each fork wants two (one for the
parser thread, one for GC, JIT and I/O).
|`numClients=3`

|Fork CPU view
|`-XX:ActiveProcessorCount=` the fair share `(cores - 2) / numClients`, never below 2, injected unless you set
`-XX:ActiveProcessorCount` in `forkedJvmArgs`.
|`slice=2` with 3 forks, `slice=3` with 2

|Fork heap
|`-XX:MaxRAMPercentage=75/numClients` (60 for a single fork), injected unless `forkedJvmArgs` already sets `-Xmx`,
`-XX:MaxRAMPercentage` or `-XX:MaxRAMFraction`. Each fork logs a `WARN` if its heap came up under 256 MB.
|`heap=MaxRAMPercentage=25` with 3 forks, `37` with 2

|Parent heap
|The JVM default, about 25% of the container memory. Tika does not change it.
|25%
|===

The arithmetic, then, for a container with memory `M` and `n` forks:

* **CPU:** give the container at least two cores per fork plus two for the parent. Pick the largest `numClients` for which
  two cores per fork plus two still fit in the CPU limit. The official table shows 8 cores with 3 forks and 16 cores with 4
  forks as the sweet spots; past that, more forks slow the server down.
* **Heap:** `n` times the fork heap must stay under 75% of `M` (Tika warns at startup when an explicit `-Xmx` breaks this),
  and the parent's own heap comes on top.
* **Native memory:** each JVM also needs metaspace, thread stacks, direct buffers and code cache, and the `-full` image
  runs Tesseract, ImageMagick and ffmpeg as separate native processes whose memory the JVM never sees. Plan a few hundred
  MB per fork on top of its heap, more with OCR.
* **tmpfs:** a RAM-backed `/tmp` counts towards `M` as well.

A worked budget for the Bookshelf Kubernetes pod (8 CPUs, 8 GiB):

[cols="3,2,4",options="header"]
|===
|Item |Amount |Notes

|Parent heap |about 1 GB |`-XX:MaxRAMPercentage=12` through `JAVA_TOOL_OPTIONS` (see below)
|Three fork heaps |4.5 GB |`-Xmx1500m` each; under the 6 GB (75%) ceiling Tika checks
|Native overhead of four JVMs |about 1 to 1.5 GB |metaspace, threads, buffers; measure with Native Memory Tracking
|Tesseract and other tools |the rest, about 1 GB |`OMP_THREAD_LIMIT=1` keeps each OCR run to one thread
|`/tmp` |0 |disk-backed `emptyDir`, counted as ephemeral storage, not memory
|===

The official guidance suggests about 2 GB of heap per fork as a starting point for mixed corpora with pathological PDFs;
Bookshelf uses 1.5 GB because its intake rejects files over 100 MB. Measure the post-GC live heap of your own corpus with
`+-Xlog:gc*+` and set `-Xmx` to about 1.5 times that.

=== Setting the parent heap: JAVA_TOOL_OPTIONS and its trap

The image's entry point offers no `JAVA_OPTS` variable. The only way to pass JVM options to the parent without replacing
the entry point is `JAVA_TOOL_OPTIONS`, which every JVM reads at startup. That includes the forks: the environment is
inherited by the processes the parent starts. The local 4.1.0 tests showed what that means:

[cols="3,3,3",options="header"]
|===
|`JAVA_TOOL_OPTIONS` |`forkedJvmArgs` |Resulting fork heap

|`-XX:MaxRAMPercentage=10`
|none
|The injected `-XX:MaxRAMPercentage=37` wins (it comes later on the command line). Parent at 10%. **Safe.**

|`-Xmx300m`
|none
|**300 MB.** `-Xmx` beats the injected percentage, so every fork silently gets the parent's heap. The sizing log still
reports `heap=MaxRAMPercentage=37`.

|`-Xmx300m`
|`["-Xmx1g"]`
|1 GB. An explicit `-Xmx` on the fork command line wins over the inherited one.
|===

So: **never put `-Xmx` in `JAVA_TOOL_OPTIONS`.** Size the parent with `-XX:MaxRAMPercentage` there, and size the forks
with `-Xmx` in `pipes.forkedJvmArgs`. The same applies to any other heap or GC flag you set this way.

=== CPU limits matter more than requests

If a container or pod has no CPU _limit_, `availableProcessors()` returns the node's CPU count, and the auto-sizer plans
forks for a 64-core node inside a pod that was promised 2. Always set an explicit CPU limit on tika-server containers,
and in Kubernetes set requests equal to limits so the pod gets the Guaranteed QoS class. Recent JDKs ignore CPU shares
(requests) when computing the processor count; only the quota (the limit) counts.

When both the synchronous endpoints and `/async` are enabled, the server runs two independent fork pools, each sized with
`numClients` as if it owned the host. Either keep `/async` in a separate deployment (recommended, and the Bookshelf
configuration does not enable it), or set `-XX:ActiveProcessorCount` in `forkedJvmArgs` with the combined total in mind.

Source: https://tika.apache.org/docs/4.1.x/pipes/cpu-sizing.html[Apache Tika 4.1.x, Forked-JVM CPU and Heap Sizing],
https://tika.apache.org/docs/4.1.x/using-tika/docker.html[Apache Tika 4.1.x, Running Tika in Docker, Memory],
https://tika.apache.org/docs/4.1.x/using-tika/server/index.html[Apache Tika 4.1.x, Tika Server, Endpoints and
Forked-Process Groups] and the `PipesConfig` and `PerClientServerManager` classes in the 4.1.0 source. For cgroups and
JVM ergonomics in general, see xref:backend/docker/java-and-spring-boot-images.adoc[Java and Spring Boot Images] and
xref:backend/docker/resources-logging-and-monitoring.adoc[Resources, Logging and Monitoring].

== Binding to 127.0.0.1 and keeping the server private

tika-server has no authentication. Anyone who can reach port 9998 can make it parse arbitrary bytes, and Tika parses
untrusted input by design. Keep it reachable only by the services that need it.

* **Publish on the loopback interface.** `-p 127.0.0.1:9998:9998`, not `-p 9998:9998`. Docker writes its own iptables
  rules for published ports, which bypass a host firewall such as `ufw`, so a plain `-p 9998:9998` can expose the server
  to the internet on a cloud VM.
* **Better, do not publish at all.** Containers on the same user-defined network reach each other by service name
  (`http://tika:9998`) without any published port. The Compose file below publishes `127.0.0.1:9998` only so a developer
  can `curl` the server.
* **Keep metrics apart.** The metrics listener serves only `/metrics` (every parse endpoint answers `404` there, and
  `/metrics` answers `404` on the parse port, which the local run confirmed). It binds to the same host as the server,
  so in a container it listens on all interfaces; restrict who can reach it with network rules, not with `-h`.
* **No egress unless needed.** A plain parse needs no outbound network. Only fetchers, emitters, VLM parsers and remote
  inference do. Denying egress turns a parser exploit that tries to phone home into a failed connection.
* **TLS where traffic leaves the host.** tika-server supports TLS and mutual TLS through `server.tlsConfig`; the metrics
  port stays plain HTTP. See xref:backend/apache-tika/security.adoc[Security] and
  xref:backend/apache-tika/tika-server-rest-api.adoc[Tika Server (REST API)].

Source: https://tika.apache.org/docs/4.1.x/using-tika/docker.html[Apache Tika 4.1.x, Running Tika in Docker],
https://tika.apache.org/docs/4.1.x/using-tika/server/monitoring.html[Apache Tika 4.1.x, Monitoring with Prometheus] and
https://tika.apache.org/docs/4.1.x/security.html[Apache Tika 4.1.x, Security]. For Docker networking itself, see
xref:backend/docker/networking.adoc[Networking].

== Docker Compose for the Bookshelf intake service

The intake service (a Spring Boot 4 application, built from its own Dockerfile) talks to tika-server over a private
network. The layout:

[source,text]
----
bookshelf-intake/
├── compose.yaml
├── intake/            # the Spring Boot service and its Dockerfile
└── tika/
    └── tika-config.json   # the file from "Mounting tika-config.json"
----

`compose.yaml`:

[source,yaml]
----
name: bookshelf-intake

services:
  tika:
    image: apache/tika:4.1.0-1-full
    command: ["-c", "/config/tika-config.json"]
    read_only: true
    tmpfs:
      - /tmp:size=1g,mode=1777
    volumes:
      - ./tika/tika-config.json:/config/tika-config.json:ro
    cap_drop: [ALL]
    security_opt:
      - no-new-privileges:true
    deploy:
      resources:
        limits:
          cpus: "6"
          memory: 6g
    ports:
      - "127.0.0.1:9998:9998"
    healthcheck:
      test: ["CMD", "wget", "-q", "-O", "/dev/null", "http://127.0.0.1:9998/version"]
      interval: 15s
      timeout: 5s
      retries: 3
      start_period: 30s
    restart: on-failure
    networks: [intake]

  intake:
    build: ./intake
    image: bookshelf/intake:1.0.0
    environment:
      TIKA_URL: http://tika:9998
    depends_on:
      tika:
        condition: service_healthy
    ports:
      - "127.0.0.1:8080:8080"
    networks: [intake]

networks:
  intake: {}
----

Notes on the choices:

* `command:` is appended to the image's entry point, so it carries only the server arguments.
* `read_only` plus a `tmpfs` at `/tmp` gives the server the one writable directory it needs. The 1 GB tmpfs counts towards
  the 6 GB limit: ten concurrent 100 MB uploads would fill it. If uploads are large, replace the tmpfs with a named volume.
* `deploy.resources.limits` is applied by `docker compose up` (Compose v2), not only by Swarm. With 6 CPUs and
  `numClients: 2` the parent keeps 2 cores and each fork gets 2.
* The health check uses `wget` because the `-full` image installs it. **The minimal image contains neither `wget` nor
  `curl`**, so with it either drop the container health check and let the intake service retry, or build a small image
  `FROM apache/tika:4.1.0-1` that installs `curl` (switching to `USER root` and back to `USER 35002:35002`, as in
  <<_choosing_an_image,Choosing an image>>).
* `/version` is answered by the parent without touching a fork, so it says the HTTP layer is alive, not that a parse
  will succeed. That is the right meaning for a liveness check; readiness is discussed in the Kubernetes section.
* The metrics port 9404 is not published. Compose services on the `intake` network (a Prometheus container, for example)
  can scrape `tika:9404` directly.

[source,bash]
----
docker compose config -q && echo "compose.yaml is valid"
docker compose up -d
docker compose ps
curl -s -T catalogue.pdf http://127.0.0.1:9998/tika/text
----

==== Sizing: CPU and heap per fork

* **Requests equal limits.** `+cpu: "8"+` as a _limit_ is what makes the JVM see 8 processors; with requests equal to
  limits the pod is in the Guaranteed QoS class and is the last to be evicted under node pressure. The auto-sizer then
  logs `hostCores=8, numClients=3, parentReserved=2, autoCap=slice=2, heap=user-set in forkedJvmArgs`.
* **Heap per fork** is set explicitly to 1.5 GB in the ConfigMap; three forks commit 4.5 GB, under the 6 GB (75%) that Tika
  checks. The parent is held to about 1 GB with `JAVA_TOOL_OPTIONS=-XX:MaxRAMPercentage=12`, which does not leak into the
  forks because their explicit `-Xmx` wins.
* **Ephemeral storage.** `/tmp` is a disk-backed `emptyDir` with a 4 GiB `sizeLimit`; the kubelet evicts the pod if it
  grows past that, and the ephemeral-storage request makes the scheduler account for it. Do not use `medium: Memory` here
  unless you add its size to the memory limit.
* **More pods or bigger pods?** Throughput scales with the total number of forks. Many 4-CPU pods with `numClients: 1`
  waste half their CPU on parents; one 32-CPU pod puts every request behind one parent and one failure domain. Pods of 8
  to 16 CPUs with 3 to 4 forks match the official sizing table and keep a lost pod cheap.

==== Probes

[cols="1,2,4",options="header"]
|===
|Probe |Endpoint |Why

|startup
|`GET /version`, up to 2 minutes
|The parent loads its resources and starts Jetty in a few seconds (about 4 seconds in the local run), but a cold node may
be slower. The startup probe keeps liveness from killing a pod that is still starting. Forks start lazily, so the first
parse after startup pays an extra fork start.

|readiness
|`GET /status`
|Enabled because `status` is listed in `server.endpoints`. Returns `+{"status" : "OPERATING", ...}+`. If you do not enable
`status`, use `/version` here too.

|liveness
|`GET /version`
|Answered by the parent. A crashing fork does not fail it, which is correct: the parent restarts forks on its own, and
killing the pod would only abort the other requests in flight.
|===

Never point a probe at `/metrics` on port 9404: the metrics listener stays up while parsing is broken, and a metrics
problem must not take a healthy pod out of rotation. Do not make readiness fail when all forks are busy either; the
server already answers `429` with `Retry-After` for that, which is a better signal than dropping the pod from the
Service.

The `/status` output in the local run, after four parses:

[source,json]
----
{
  "status" : "OPERATING",
  "active_tasks" : 0,
  "millis_since_last_parse_started" : 124,
  "files_processed" : 4
}
----

==== Shutdown and rolling updates

In the local run, `SIGTERM` stopped the 4.1.0 server (Jetty, the metrics listener and the forks) within about a second;
the logs showed no draining of requests in flight, and the documentation describes none. Plan for that:

* the `preStop` sleep of 10 seconds lets the endpoints controller and the kube-proxies remove the pod from the Service
  before `SIGTERM` arrives, so no _new_ requests reach a stopping pod;
* `terminationGracePeriodSeconds: 30` covers the sleep and the quick shutdown; a longer grace period does not help
  because the server does not wait for in-flight parses;
* the client must retry requests whose connection is reset, exactly as it retries `429`, and the rolling update uses
  `maxUnavailable: 0` so capacity never drops below two pods.

See xref:backend/kubernetes/health-probes-and-lifecycle.adoc[Health Probes and Container Lifecycle] and
xref:backend/kubernetes/deployment-strategies.adoc[Deployment Strategies].

==== Security context

The image already runs as UID 35002; the pod spec makes that a requirement (`runAsNonRoot`, `runAsUser`), so a
mistakenly rebuilt image that runs as root is refused. `readOnlyRootFilesystem` works because the server only writes to
`/tmp`, which the `emptyDir` provides; `emptyDir` volumes are world-writable, so no `fsGroup` is needed. Dropping all
capabilities, disallowing privilege escalation and the `RuntimeDefault` seccomp profile satisfy the `restricted` Pod
Security Standard. `automountServiceAccountToken: false` keeps a Kubernetes API token out of a process that parses
hostile files. See xref:backend/kubernetes/pod-security.adoc[Pod Security].

Source: https://tika.apache.org/docs/4.1.x/pipes/cpu-sizing.html[Apache Tika 4.1.x, Forked-JVM CPU and Heap Sizing,
Container & cgroup behavior], https://tika.apache.org/docs/4.1.x/using-tika/server/monitoring.html[Apache Tika 4.1.x,
Monitoring with Prometheus, Probes] and
https://tika.apache.org/docs/4.1.x/using-tika/server/index.html[Apache Tika 4.1.x, Tika Server, Best practices]. For the
Kubernetes objects, see xref:backend/kubernetes/replicasets-and-deployments.adoc[ReplicaSets and Deployments],
xref:backend/kubernetes/resource-management.adoc[Resource Management] and
xref:backend/kubernetes/volumes-and-ephemeral-storage.adoc[Volumes and Ephemeral Storage].

=== Service and PodDisruptionBudget

[source,yaml]
----
apiVersion: v1
kind: Service
metadata:
  name: tika-server
  namespace: bookshelf
  labels:
    app.kubernetes.io/name: tika-server
spec:
  type: ClusterIP
  selector:
    app.kubernetes.io/name: tika-server
  ports:
    - name: http
      port: 9998
      targetPort: http
    - name: metrics
      port: 9404
      targetPort: metrics
---
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: tika-server
  namespace: bookshelf
spec:
  minAvailable: 1
  selector:
    matchLabels:
      app.kubernetes.io/name: tika-server
----

A `ClusterIP` Service keeps the server inside the cluster; never expose tika-server through an Ingress or a `LoadBalancer`
Service to the internet. The intake service reaches it as `http://tika-server.bookshelf.svc:9998`. The PDB keeps one pod
running through node drains. Connections are balanced per connection, not per request, so a client with a long-lived
keep-alive pool can pin itself to one pod; let the HTTP client recycle connections (a maximum connection lifetime) if load
is visibly uneven. See xref:backend/kubernetes/services.adoc[Services] and
xref:backend/kubernetes/scheduling-and-disruptions.adoc[Scheduling and Disruptions].

=== NetworkPolicy

[source,yaml]
----
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: tika-server
  namespace: bookshelf
spec:
  podSelector:
    matchLabels:
      app.kubernetes.io/name: tika-server
  policyTypes: ["Ingress", "Egress"]
  ingress:
    - from:
        - podSelector:
            matchLabels:
              app.kubernetes.io/name: bookshelf-intake
      ports:
        - port: 9998
    - from:
        - namespaceSelector:
            matchLabels:
              kubernetes.io/metadata.name: monitoring
      ports:
        - port: 9404
  egress: []
----

Only the intake pods may call the parse port, only the `monitoring` namespace may scrape the metrics port, and the pods
may not open any outbound connection, not even DNS, because a synchronous parse of an uploaded body needs none. Add
egress rules when you enable something that does: a VLM parser calling an inference endpoint, or fetchers and emitters on
a pipes deployment. Kubelet probes are not subject to NetworkPolicy on the common CNI plugins, but check yours. See
xref:backend/kubernetes/network-policies.adoc[Network Policies].

=== Metrics, alerts and autoscaling

With `server.metricsPort` set, tika-server serves Micrometer metrics in Prometheus format on port 9404. With the
Prometheus Operator, a ServiceMonitor selects the Service port:

[source,yaml]
----
apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: tika-server
  namespace: bookshelf
spec:
  selector:
    matchLabels:
      app.kubernetes.io/name: tika-server
  endpoints:
    - port: metrics
      path: /metrics
      interval: 30s
----

The Tika-specific series, from the local run after a few requests (excerpt):

[source,text]
----
tika_pipes_worker_restarts_total{pool="sync",reason="oom"} 0.0
tika_pipes_worker_restarts_total{pool="sync",reason="timeout"} 0.0
tika_pipes_worker_restarts_total{pool="sync",reason="crash"} 0.0
tika_pipes_workers{pool="sync",state="busy"} 0.0
tika_pipes_workers{pool="sync",state="idle"} 2.0
tika_server_requests_seconds_count{endpoint="tika",method="PUT",status="2xx"} 1
tika_server_requests_seconds_count{endpoint="meta",method="PUT",status="2xx"} 1
tika_server_requests_seconds_count{endpoint="detect",method="PUT",status="2xx"} 1
tika_server_requests_seconds_count{endpoint="language",method="PUT",status="4xx"} 1
tika_server_tasks_active 0.0
----

(The `language` request returned `404` because that endpoint is not in `server.endpoints`.) The `+jvm_*+` and `+process_*+`
series describe the parent JVM only, which does not parse; a near-idle parent heap is not evidence of headroom. For CPU
and memory of the whole pod, forks included, use the container metrics your cluster already collects (cAdvisor).

What to watch:

[source,promql]
----
# Saturation: share of busy forks, per pod (scale on this, not on CPU)
sum by (pod) (tika_pipes_workers{state="busy"})
  / sum by (pod) (tika_pipes_workers)

# Backpressure: requests refused because no fork was free in time
sum(rate(tika_server_rejected_total{reason="busy_429"}[5m]))

# Failures: forks killed by documents (alert on these)
sum by (reason) (rate(tika_pipes_worker_restarts_total{reason=~"oom|timeout|crash"}[5m]))
sum(rate(tika_server_rejected_total{reason="crash_503"}[5m]))

# Latency per endpoint
histogram_quantile(0.95, sum by (le, endpoint) (rate(tika_server_requests_seconds_bucket[5m])))
----

CPU is a poor autoscaling signal for tika-server: a pod whose forks are all busy on OCR may show high CPU, but a pod whose
forks are waiting on slow I/O or a remote VLM is saturated at low CPU. Scale on the busy-fork ratio or the `429` rate
instead: expose the first query above as a per-pod custom metric with `prometheus-adapter` (or use KEDA's Prometheus
scaler) and give the HorizontalPodAutoscaler a target such as an average busy ratio of 0.7, with a long scale-down
stabilization window (ten minutes or more) so pods, and their in-flight parses, are not removed every time a batch
finishes. Tika exports no ready-made ratio series, and this autoscaling setup was not tested for this page.

Source: https://tika.apache.org/docs/4.1.x/using-tika/server/monitoring.html[Apache Tika 4.1.x, Monitoring with
Prometheus]. See also xref:backend/kubernetes/observability-logging-and-metrics.adoc[Observability: Logging, Metrics and
Tracing], xref:backend/kubernetes/autoscaling.adoc[Autoscaling], and the site's
xref:database/prometheus/containers-and-kubernetes-monitoring.adoc[Containers & Kubernetes Monitoring] and
xref:database/prometheus/recording-and-alerting-rules.adoc[Recording & Alerting Rules] pages of the Prometheus section.

`apache/tika-grpc` differs from `apache/tika` in ways that matter for a manifest:

|9998 (`-p` to change)

|HTTP on 9998
|The 4.1.0 jar registers the standard gRPC health service, so a native `grpc:` probe on port 9090 should work

The same sizing rules apply: tika-grpc parses through Tika Pipes forks too. See
xref:backend/apache-tika/tika-grpc.adoc[Tika gRPC] for the service and its configuration.

configuration of `apache/tika-grpc:4.1.0-1` on Docker Hub.

== Pitfalls

* **Deploying `latest` or a rolling tag.** `latest` jumped from 3.x to 4.x, which changed the configuration format, the
  endpoints and the metadata keys. Pin `+<version>-<N>+`, ideally with the digest.
* **No memory or CPU limit.** The JVM then sizes the parent and every fork from the whole host, and the kernel OOM killer,
  not Tika, decides which process dies.
* **Sizing for the parent only.** A 2 GB container is enough for the parent and nothing else. Budget each fork's heap and
  native memory, plus OCR tools, plus a RAM-backed `/tmp`.
* **`-Xmx` in `JAVA_TOOL_OPTIONS`.** It is inherited by the forks and silently overrides their heap.
* **`command:` instead of `args:` in Kubernetes.** It replaces the entry point, losing `/tika-extras` and the classpath.
* **A configuration without `+"server"+`.** The server refuses to start.
* **Unreadable mounts.** UID 35002 must be able to read the configuration file, the extras and the plugin directories.
* **Expecting the zip of a plugin to work.** Plugins must be unzipped into a directory under `/opt/tika-server/plugins/`.
* **Health checks with `curl` on the minimal image.** It has neither `curl` nor `wget`.
* **Probing `/metrics`, or failing readiness when busy.** Use `/version` or `/status`; let `429` express saturation.
* **`-p 9998:9998` on a cloud VM.** Docker's iptables rules can bypass the host firewall.
* **Enabling `/async` next to the synchronous endpoints in the same pod.** Two fork pools, each sized for the whole pod.
* **Expecting a 3.3.2 image.** There is none on Docker Hub; the newest 3.x image is `3.3.1.0`.
* **`linux/arm/v7` hosts.** 4.x images do not support them.

== Security checklist

* Pin the image by immutable tag and digest; rebuild or bump `N` for base-image fixes; scan the image in CI (see
  xref:backend/docker/image-best-practices-and-security.adoc[Image Best Practices and Supply-Chain Security]).
* Run as UID 35002 (the default), non-root enforced, read-only root filesystem, all capabilities dropped, no privilege
  escalation, `RuntimeDefault` seccomp, no service-account token.
* No published port on public interfaces; `ClusterIP` only; NetworkPolicy allowing only the callers and the scraper; no
  egress unless a feature needs it.
* Metrics on their own port, reachable only by Prometheus.
* Leave `allowPerRequestConfig` and `allowPipes` off on a server that receives uploads; run pipes in a separate deployment
  with its own policy.
* `maxRequestSizeBytes` and the timeout limits set for your intake, so one request cannot fill `/tmp` or hold a fork for
  an hour.
* `/tika-extras` and plugin directories baked into the image, never writable at runtime.
* Secrets only through environment variables and `+${env:NAME}+`, never in the ConfigMap.

The threat model behind these items (why a parser is an attack surface, the XXE CVEs of 2025, what the forks do and do
not protect against) is in xref:backend/apache-tika/security.adoc[Security].
