= Fault tolerance: skip & retry
:description: Making a chunk step survive bad data and transient failures -- faultTolerant(), skip with skipLimit, SkipPolicy, LimitCheckingExceptionHierarchySkipPolicy, SkipListener and noSkip; retry with retryLimit, RetryPolicy built on Spring Framework 7's retry support rather than the Spring Retry library, BackOffPolicy and RetryListener; noRollback; and the read/process/write replay semantics that require an idempotent ItemProcessor.
:keywords: faultTolerant, skip, skipLimit, SkipPolicy, LimitCheckingExceptionHierarchySkipPolicy, AlwaysSkipItemSkipPolicy, SkipListener, noSkip, retry, retryLimit, RetryPolicy, BackOffPolicy, ExponentialBackOffPolicy, RetryListener, Spring Framework 7 retry, noRollback, chunk replay, scan mode, idempotent ItemProcessor

include::partial$ai-disclaimer.adoc[]

Two different failures need two different answers. A *bad record* is permanent -- retrying will not fix it, so
skip it and carry on. A *transient failure* -- a deadlock, a timeout, a briefly unavailable service -- will
probably succeed on the next attempt, so retry it. Spring Batch expresses both declaratively.

== Turning on fault tolerance

`.faultTolerant()` switches the chunk step into the fault-tolerant implementation, which is what makes the
skip and retry options available:

[source,java]
----
@Bean
public Step loadTradesStep(JobRepository jobRepository, PlatformTransactionManager tx,
                           ItemReader<TradeCsv> reader,
                           ItemProcessor<TradeCsv, Trade> processor,
                           ItemWriter<Trade> writer) {
    return new StepBuilder("loadTradesStep", jobRepository)
            .<TradeCsv, Trade>chunk(500, tx)
            .reader(reader)
            .processor(processor)
            .writer(writer)
            .faultTolerant()
            .skip(FlatFileParseException.class)
            .skip(ValidationException.class)
            .skipLimit(50)
            .retry(DeadlockLoserDataAccessException.class)
            .retry(TransientDataAccessException.class)
            .retryLimit(3)
            .build();
}
----

Fault tolerance is not free: it changes how the chunk is executed (see *Replay semantics* below) and adds
bookkeeping per item. Turn it on where it is needed, not everywhere.

== Skip

Skipping discards the offending *item* and lets the chunk continue. It applies to exceptions thrown by the
reader, the processor or the writer, and each is counted separately (`readSkipCount`, `processSkipCount`,
`writeSkipCount`).

[source,java]
----
.faultTolerant()
.skip(FlatFileParseException.class)      // a malformed line
.skip(ValidationException.class)         // a record that fails business validation
.noSkip(FileNotFoundException.class)     // but never skip a missing input file
.skipLimit(100)                          // fail the step after 100 skips
----

`.skipLimit(n)` is a *safety valve*, not a target: exceeding it fails the step with
`SkipLimitExceededException`, which is the correct outcome when a feed is broadly corrupt rather than
occasionally imperfect. `+.noSkip(...)+` carves exceptions out of a broader `+.skip(...)+` declaration -- the
exception hierarchy is evaluated most-specific-first.

=== `SkipPolicy`

When the decision depends on more than the exception type, implement `SkipPolicy`:

[source,java]
----
public class BusinessHoursSkipPolicy implements SkipPolicy {

    @Override
    public boolean shouldSkip(Throwable throwable, long skipCount) throws SkipLimitExceededException {
        if (throwable instanceof FileNotFoundException) {
            return false;                                  // never skip
        }
        if (throwable instanceof ValidationException && skipCount < 500) {
            return true;                                   // tolerate many bad records
        }
        if (throwable instanceof FlatFileParseException && skipCount < 10) {
            return true;                                   // tolerate few parse errors
        }
        return false;
    }
}
----

[source,java]
----
.faultTolerant()
.skipPolicy(new BusinessHoursSkipPolicy())
----

`LimitCheckingExceptionHierarchySkipPolicy` is the built-in policy behind the `+.skip(...)+`/`+.skipLimit(...)+`
shorthand: it takes a map of exception class to "skippable?" and a limit, walking the exception hierarchy to
find the most specific entry. `AlwaysSkipItemSkipPolicy` and `NeverSkipItemSkipPolicy` are the degenerate
cases, useful in tests.

=== `SkipListener`

A skipped item that nobody records is data silently lost. A `SkipListener` is the place to write it to a
rejects file or a quarantine table:

[source,java]
----
@Component
public class RejectedItemListener implements SkipListener<TradeCsv, Trade> {

    private static final Logger log = LoggerFactory.getLogger(RejectedItemListener.class);

    private final RejectRepository rejectRepository;

    public RejectedItemListener(RejectRepository rejectRepository) {
        this.rejectRepository = rejectRepository;
    }

    @Override
    public void onSkipInRead(Throwable throwable) {
        log.warn("unparseable input line", throwable);
        rejectRepository.saveReadFailure(throwable.getMessage());
    }

    @Override
    public void onSkipInProcess(TradeCsv item, Throwable throwable) {
        rejectRepository.save(item.getExternalId(), "process", throwable.getMessage());
    }

    @Override
    public void onSkipInWrite(Trade item, Throwable throwable) {
        rejectRepository.save(item.getId(), "write", throwable.getMessage());
    }
}
----

Register it with `.listener(rejectedItemListener)` on the fault-tolerant builder. Note that
`onSkipInWrite` runs *after* the chunk's transaction rolled back, so the listener's own writes need their own
transaction (`REQUIRES_NEW`) or a non-transactional sink.

== Retry

Retry re-attempts the *operation*, transparently, before any skip decision is made (for retry outside a batch step, see
xref:backend/resilience/retry.adoc[Retry] in the Resilience section):

[source,java]
----
.faultTolerant()
.retry(DeadlockLoserDataAccessException.class)
.retry(OptimisticLockingFailureException.class)
.retryLimit(3)
.backOffPolicy(exponentialBackOff())
.noRetry(DataIntegrityViolationException.class)   // a constraint violation will not fix itself
----

**Which retry API applies depends on which step builder is used, and the two cannot be mixed.**

* The `.faultTolerant()` builder shown above is `FaultTolerantStepBuilder`, which is still built on the
  **Spring Retry** library: its `+.retryPolicy(...)+` and `+.listener(...)+` take
  `org.springframework.retry.RetryPolicy`, `org.springframework.retry.backoff.BackOffPolicy` and
  `org.springframework.retry.RetryListener`. Spring Batch 6.0 still declares a `spring-retry` dependency.
* The newer `ChunkOrientedStepBuilder` (see
  xref:backend/spring-batch/chunk-oriented-processing.adoc[Chunk-oriented processing]) uses **Spring Framework
  7's own retry support** in `org.springframework.core.retry` instead.

So a `RetryListener` written against `org.springframework.core.retry` cannot be attached to a
`.faultTolerant()` step, and vice versa -- match the imports to the builder in use.

The two builders also differ in what the limit means and in which methods exist:

[cols="2,3,3",options="header"]
|===
| | `.faultTolerant()` on `.chunk(size, tx)` | `ChunkOrientedStepBuilder`

| Skip
| `.skip(Class)` and `.noSkip(Class)`, `.skipLimit(int)`, `+.skipPolicy(...)+`
| `+.skip(Class...)+`, `.skipLimit(long)`, `+.skipPolicy(...)+`; no `noSkip`

| Retry
| `.retry(Class)` and `.noRetry(Class)`, `.retryLimit(int)`, `+.retryPolicy(...)+` and `+.backOffPolicy(...)+` from Spring Retry
| `+.retry(Class...)+`, `.retryLimit(long)`, `+.retryPolicy(...)+` from `org.springframework.core.retry`; the back-off is part of that policy

| Listeners
| `+.listener(...)+` for skip, retry and chunk listeners
| `+.skipListener(...)+` and `+.retryListener(...)+`

| Roll-back control
| `.noRollback(Class)`, `.processorNonTransactional()`
| `.processorNonTransactional()` only

| What `retryLimit(3)` allows
| three attempts in all
| the first attempt and three retries
|===

The last row matters when porting a step: with a processor that fails three times in a row before succeeding, the
classic step was configured with `retryLimit(3)` and failed, while the `ChunkOrientedStepBuilder` step with the same
number completed (see the worked example).

=== `RetryPolicy` and `BackOffPolicy`

[source,java]
----
@Bean
public BackOffPolicy exponentialBackOff() {
    ExponentialBackOffPolicy policy = new ExponentialBackOffPolicy();
    policy.setInitialInterval(200L);     // ms before the first retry
    policy.setMultiplier(2.0);           // 200, 400, 800 ...
    policy.setMaxInterval(5_000L);
    return policy;
}
----

Back-off matters: retrying a contended row three times without pausing usually reproduces the same deadlock.
For a policy that cannot be expressed as "these exception types, n times", supply a `RetryPolicy` directly with
`+.retryPolicy(...)+`; the interface and the standalone `RetryTemplate` are covered in
xref:backend/spring-batch/repeat-and-retry-internals.adoc[Repeat & retry internals].

=== `RetryListener`

The listener below implements the Spring Framework 7 `org.springframework.core.retry.RetryListener`, so it
attaches to a `ChunkOrientedStepBuilder` step with `+.retryListener(...)+`. Its callbacks take the `RetryPolicy` and the
`Retryable` being executed, not an execution object:

[source,java]
----
@Component
public class RetryLoggingListener implements RetryListener {

    private static final Logger log = LoggerFactory.getLogger(RetryLoggingListener.class);

    @Override
    public void onRetryFailure(RetryPolicy policy, Retryable<?> retryable, Throwable throwable) {
        log.warn("retrying after failure", throwable);
    }

    @Override
    public void onRetryPolicyExhaustion(RetryPolicy policy, Retryable<?> retryable, RetryException exception) {
        log.error("retries exhausted", exception);
    }
}
----

A `.faultTolerant()` step needs the Spring Retry equivalent instead, passed to `+.listener(...)+`:

[source,java]
----
static class SpringRetryLogger extends org.springframework.retry.listener.RetryListenerSupport {
    @Override
    public <T, E extends Throwable> void onError(RetryContext context, RetryCallback<T, E> callback, Throwable t) {
        log.info("attempt {} failed: {}", context.getRetryCount(), t.getMessage());
    }
}
----

Both listeners are told about *every* failure that reaches the retry machinery, including exceptions the policy never
retries: a malformed line, a validation error or a duplicate key all produce an `onError` call on the Spring Retry
listener and an `onRetryPolicyExhaustion` call on the framework one, with no retry having happened. A counter of
"retries exhausted" therefore also counts plain skippable errors; filter on the exception type before counting.

Retry listeners are the natural place for a metric -- a counter of retried operations is an early warning that
a downstream system is degrading. See xref:backend/spring-batch/observability.adoc[Observability].

== `noRollback`

By default any exception rolls the chunk's transaction back. `+.noRollback(...)+` declares exceptions that
should not:

[source,java]
----
.faultTolerant()
.noRollback(DuplicateKeyIgnoredException.class)
----

Use it only when the exception genuinely leaves the transaction usable -- typically a business-level signal
thrown after the writer already handled the situation. A database that has marked the transaction
rollback-only will not honour the request no matter what the step says.

== Replay semantics, and why the processor must be idempotent

This is the part that surprises people. When a chunk fails and skipping is enabled, the framework cannot know
*which* item caused the failure -- the writer was handed the whole list. So it:

. rolls the transaction back;
. **replays the chunk**, re-reading the items from its internal cache and re-processing them;
. re-writes them **one at a time** (the "scan" pass), so the failing item can be identified;
. skips that one item and commits the rest.

The consequences:

* the `ItemProcessor` runs **more than once** for the same item. If it has side effects -- sending an e-mail,
  incrementing a counter, calling a payment API -- those side effects happen repeatedly. **The processor must
  be idempotent**, which is why side effects belong in the writer, not the processor. See
  xref:backend/spring-batch/item-processors.adoc[ItemProcessors].
* the `ItemWriter` may be called with single-item lists during the scan, so it must handle a list of any size;
* `rollbackCount` rises and throughput drops sharply while a chunk is being scanned -- frequent skipping is
  expensive, which is another reason `skipLimit` should be modest.

If a processor genuinely cannot be made idempotent, `.processorNonTransactional()` tells the step to cache
processed items rather than re-process them on replay -- at the cost of holding the outputs in memory:

[source,java]
----
.faultTolerant()
.skip(ValidationException.class)
.skipLimit(20)
.processorNonTransactional()
----

== Worked example: loading a dirty feed

The running example is the trade load again, now over a feed with one defect of every kind. Twelve rows, loaded
in chunks of 4 into a `trade` table whose primary key is `external_id`:

[cols="1,2,3",options="header"]
|===
| Row | Content | Fate

| 1, 2 | `T-0001`, `T-0002` | written
| 3 | `T-0003`, quantity 0 | filtered by the processor
| 4 | `T-0004`, price `not-a-number` | read skip: `FlatFileParseException`
| 5 | `T-0005` | written
| 6 | `T-0006`, ISIN `BADISIN` | process skip: `ValidationException`
| 7 | `T-0007` | the processor throws a transient exception twice, then succeeds: retried
| 8 | `T-0008` | written
| 9 | `T-0002` again | write skip: `DuplicateKeyException`
| 10 | `T-0005` again | write skip: `DuplicateKeyException`
| 11, 12 | `T-0011`, `T-0012` | written
|===

The step is the one from the top of the page, with an exponential back-off starting at 200 ms, and with a skip
listener and a retry listener that log what they see:

[source,java]
----
Step step = new StepBuilder("faultClassicStep", jobRepository).<TradeCsv, Trade>chunk(4, tx)
        .reader(tradeReader).processor(flakyProcessor).writer(tradeWriter)
        .faultTolerant()
        .skip(FlatFileParseException.class).skip(ValidationException.class)
        .skip(DataIntegrityViolationException.class).skipLimit(10)
        .retry(TransientDataAccessException.class).retryLimit(3).backOffPolicy(backoff)
        .listener(new Rejects()).listener(new SpringRetryLogger())
        .build();
----

On Spring Batch 6.0.6 it ends with seven rows written and every defect accounted for:

----
step faultClassicStep: status=COMPLETED read=11 filter=1 write=7 readSkip=1 processSkip=1 writeSkip=2 commit=6 rollback=7
----

`readCount` is 11, not 12, because the malformed line never produced an item, and the counters of the three skips
match the three table rows that are skipped. The skip listener printed

----
  skip in READ: Parsing error at line: 5 in resource=[URL [file:data/trades-dirty.csv]], input=[T-0004,DE0007164600,75,not-a-number,2026-03-02]
  skip in PROCESS: T-0006 (invalid ISIN BADISIN in T-0006)
  skip in WRITE: T-0002 (DuplicateKeyException)
  skip in WRITE: T-0005 (DuplicateKeyException)
----

and the retry listener the timing of the retries of `T-0007`:

----
  retry: attempt 1 failed at 20906 ms: downstream timeout (attempt 1)
  retry: attempt 2 failed at 21108 ms: downstream timeout (attempt 2)
----

The 202 ms between the two failures is the 200 ms initial interval; a third failure would have waited 406 ms.

=== The scan, in the log

The second chunk holds `T-0006`, `T-0007`, `T-0008` and the duplicate `T-0002`. The writer is called with the three
items that survived processing, fails on the duplicate, and the chunk is replayed:

----
  writer called with 3 item(s): [Trade[T-0007], Trade[T-0008], Trade[T-0002]]
  retry: attempt 1 failed ...: ... Key (external_id)=(T-0002) already exists.
  processor: T-0007 processed again (call #2)
  writer called with 1 item(s): [Trade[T-0007]]
  skip in PROCESS: T-0006 (invalid ISIN BADISIN in T-0006)
  processor: T-0008 processed again (call #2)
  writer called with 1 item(s): [Trade[T-0008]]
  processor: T-0002 processed again (call #2)
  writer called with 1 item(s): [Trade[T-0002]]
  skip in WRITE: T-0002 (DuplicateKeyException)
----

[mermaid]
....
sequenceDiagram
    participant S as Step
    participant P as ItemProcessor
    participant W as ItemWriter
    participant D as Database
    S->>P: process the chunk
    S->>W: write 3 items
    W->>D: batch insert
    D-->>W: duplicate key
    Note over S,D: rollback, nothing committed
    loop for each item of the cached chunk
        S->>P: process the item again
        S->>W: write 1 item
        W->>D: insert
    end
    Note over S,D: the item that fails is skipped, SkipListener notified,<br/>the others are committed
....

Every item of the failed chunk was processed again and written alone; the process and write skip callbacks of the
listener fire only during that scan. A fault-tolerant step with `.processorNonTransactional()` caches the processed outputs
instead: the same run showed *no* "processed again" line (six without it) and identical counters.

[cols="2,1,1,1",options="header"]
|===
| Configuration | Processor calls repeated | `rollbackCount` | `commitCount`

| `.faultTolerant()` as above | 6 | 7 | 6
| plus `.processorNonTransactional()` | 0 | 7 | 6
| plus `.noRollback(ValidationException.class)` | 6 | 6 | 6
|===

`noRollback` lowered the roll-back count by one (7 to 6) and changed nothing else in the counters.

=== The same feed with the 6.0 builder

`ChunkOrientedStepBuilder` accepts the same declarations with its own method names:

[source,java]
----
Step step = new ChunkOrientedStepBuilder<TradeCsv, Trade>("faultCosStep", jobRepository, 4)
        .reader(tradeReader).processor(flakyProcessor).writer(tradeWriter)
        .transactionManager(tx)
        .faultTolerant()
        .skip(FlatFileParseException.class, ValidationException.class, DataIntegrityViolationException.class)
        .skipLimit(10)
        .retry(TransientDataAccessException.class).retryLimit(3)
        .skipListener(new Rejects())
        .retryListener(retryLoggingListener)
        .build();
----

The totals are the same -- `read=11 filter=1 write=7 readSkip=1 processSkip=1 writeSkip=2` -- but the transaction
accounting differs: `commit=3 rollback=3`, against `commit=6 rollback=7`. The chunks also differ: a skipped read
occupies a slot of the chunk, so the first chunk wrote two items, and the last chunk, `T-0002`, `T-0005`, `T-0011`
and `T-0012`, hit both duplicates and was scanned in one go:

----
  writer called with 2 item(s): [Trade[T-0001], Trade[T-0002]]
  writer called with 3 item(s): [Trade[T-0005], Trade[T-0007], Trade[T-0008]]
  writer called with 4 item(s): [Trade[T-0002], Trade[T-0005], Trade[T-0011], Trade[T-0012]]
  processor: T-0002 processed again (call #2)
  writer called with 1 item(s): [Trade[T-0002]]
  skip in WRITE: T-0002 (DuplicateKeyException)
  ...
----

The scan is the same one-item-at-a-time replay with the processor called again (four repeated calls here). The
back-off of a `ChunkOrientedStepBuilder` step belongs to its `RetryPolicy`; the following replaces `+.retry(...)+`
and `+.retryLimit(...)+` above with 200 ms doubling to at most five seconds:

[source,java]
----
RetryPolicy policy = RetryPolicy.builder()
        .includes(TransientDataAccessException.class)
        .maxRetries(3)
        .delay(Duration.ofMillis(200))
        .multiplier(2.0)
        .maxDelay(Duration.ofSeconds(5))
        .build();

.retryPolicy(policy)
----

With a processor that fails the first three or four times, the retry listener printed the failures of the *retries*
(the first failure is not reported to it) at 400 ms and 800 ms intervals, and the outcome depends on the limit:

----
failures = 3, maxRetries(3):  retry failed at 28683 ms: ... (attempt 2)
                              retry failed at 29083 ms: ... (attempt 3)      -> the fourth attempt succeeds
failures = 4, maxRetries(3):  ... attempts 2, 3 and 4 fail, then
                              NonSkippableProcessException: Skip policy rejected skipping item
                              Caused by: TransientDataAccessResourceException: downstream timeout (attempt 4)
----

Exhausted retries are an ordinary failure of the operation. Whether it is then skipped is decided by the skip policy,
and a transient exception that is not in the skip list fails the step.

=== Failing on purpose: the skip limit

With `.skipLimit(1)` instead of 10, the same feed fails after the second skip:

----
org.springframework.batch.core.step.skip.SkipLimitExceededException: Skip limit of '1' exceeded
Caused by: org.springframework.batch.infrastructure.item.validator.ValidationException: invalid ISIN BADISIN in T-0006
step skipLimitStep: status=FAILED read=8 filter=1 write=3 readSkip=1 processSkip=0 writeSkip=0 commit=1 rollback=2
----

The read skip of row 4 used the whole budget, so the validation failure of row 6 exceeded it. The first chunk stays
committed -- `commit=1`, `write=3`.
