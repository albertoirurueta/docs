= Observability
:description: Seeing what a Spring Batch job is doing -- the Micrometer meters published under the spring.batch prefix (job, job.active, step, item.read, item.process, chunk.write), tracing through the Observation API with observations for job launches, jobs, steps and (on the 6.0 chunk step) items and chunk writes, wiring a MeterRegistry and ObservationRegistry, the 6.0 Java Flight Recorder events, and what Spring Boot Actuator adds.

include::partial$ai-disclaimer.adoc[]

A batch job that runs at 02:00 is only as good as what it reports. Spring Batch instruments itself with
Micrometer and the Observation API, so job, step and chunk timings reach the same monitoring stack as the rest
of the application.

== Micrometer meters

Spring Batch publishes these meters under the `spring.batch` prefix. Each is produced by an *Observation* (see below)
and is therefore a `Timer`, with a matching `LongTaskTimer` named `<meter>.active` while the work is running:

[cols="1,1,2",options="header"]
|===
| Meter | Type | Records

| `spring.batch.job` | Timer | Duration of a whole job execution. Tags: `spring.batch.job.name`, `spring.batch.job.status`, `error`.
| `spring.batch.job.active` | LongTaskTimer | Currently running job executions and how long each has been running -- the meter that answers "is last night's job still going?".
| `spring.batch.job.launch.count` | Timer | One observation per launch through the `JobOperator`, with `spring.batch.job.launch.count.active` for launches in flight. Despite the name it is a timer, so its `_count` is the launch counter.
| `spring.batch.step` | Timer | Duration of a step execution. Tags: `spring.batch.step.name`, `spring.batch.step.job.name`, `spring.batch.step.type` (the step class), `spring.batch.step.status`, `error`.
| `spring.batch.step.active` | LongTaskTimer | Step executions in flight, per step name.
| `spring.batch.item.read` | Timer | Duration of a single `read()`. Tags: `spring.batch.item.read.job.name`, `.step.name`, `.status`.
| `spring.batch.item.process` | Timer | Duration of a single `process()`. Tags as for `item.read`.
| `spring.batch.chunk.write` | Timer | Duration of one `write(chunk)` -- per chunk, not per item. Tags as for `item.read`.
|===

Two details of that table matter in practice. The item and chunk meters carry the step and job name in
*meter-specific* tag keys (`spring.batch.item.read.step.name`, not a shared `step.name`), so a dashboard variable
has to be written per meter. And the `status` of a call is `SUCCESS` or `FAILURE`; the one failed `process()` of a
failing run shows up in a separate series.

The split between item-level and chunk-level timers is what makes a slow step diagnosable: if
`spring.batch.item.process` dominates, the processor is the problem; if `spring.batch.chunk.write` dominates,
the writer or the database is. That is the same question
xref:backend/spring-batch/profiling-and-tuning.adoc[Profiling & tuning] starts from, answered continuously
instead of in a profiling session.

Under Spring Boot, a `MeterRegistry` on the classpath is enough -- the meters are registered automatically:

[source,xml]
----
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-actuator</artifactId>
</dependency>
<dependency>
    <groupId>io.micrometer</groupId>
    <artifactId>micrometer-registry-prometheus</artifactId>
</dependency>
----

[source,yaml]
----
management:
  endpoints:
    web:
      exposure:
        include: health,info,metrics,prometheus
  metrics:
    tags:
      application: batch-app
----

Outside Spring Boot, register a global registry explicitly:

[source,java]
----
@Configuration
public class MetricsConfiguration {

    @Bean
    public MeterRegistry meterRegistry() {
        PrometheusMeterRegistry registry =
                new PrometheusMeterRegistry(PrometheusConfig.DEFAULT);
        Metrics.addRegistry(registry);      // Spring Batch publishes to the global registry
        return registry;
    }
}
----

Business-level counters belong alongside them -- a rejected-record counter incremented from a `SkipListener`
(xref:backend/spring-batch/fault-tolerance-skip-and-retry.adoc[Fault tolerance: skip & retry]) is often the
most actionable metric a batch job has:

[source,java]
----
@Component
public class MeteredSkipListener implements SkipListener<TradeCsv, Trade> {

    private final Counter rejected;

    public MeteredSkipListener(MeterRegistry registry) {
        this.rejected = Counter.builder("batch.trades.rejected")
                .description("trades skipped during the load step")
                .register(registry);
    }

    @Override
    public void onSkipInProcess(TradeCsv item, Throwable throwable) {
        rejected.increment();
    }
}
----

A useful alerting rule set: job duration above its usual band, `spring.batch.job.active` still non-zero past a
deadline, any execution with `status=FAILED`, and a rejection counter above a threshold.

== Tracing with the Observation API

Every meter above is produced by an *Observation*, so the same instrumentation also emits spans when a tracer
is present: one observation per job launch and per job execution, one per step execution and -- on the 6.0
`ChunkOrientedStep` -- one per item read, item process and chunk write. A job that calls downstream services
therefore appears in a trace as a job span containing step spans containing the outgoing HTTP or messaging spans.
The classic `SimpleChunkProcessor` step records the item and chunk timers directly (without observations), so it
produces no spans below the step level.

[source,java]
----
@Configuration
public class ObservabilityConfiguration {

    @Bean
    public ObservationRegistry observationRegistry(MeterRegistry meterRegistry) {
        ObservationRegistry registry = ObservationRegistry.create();
        registry.observationConfig()
                .observationHandler(new DefaultMeterObservationHandler(meterRegistry));
        return registry;
    }
}
----

Under Spring Boot, `spring-boot-starter-actuator` plus a tracer bridge (`micrometer-tracing-bridge-otel` and
an exporter) is all that is needed; the general Micrometer / OpenTelemetry / Prometheus / Grafana setup is
covered on xref:backend/springboot/metrics-and-observability.adoc[Metrics & Observability] and is not restated
here.

Sampling deserves a thought for batch: a chunk observation per 500 items is fine, but item-level spans on a
ten-million-row job are not -- and the 6.0 chunk step creates exactly those item observations. Sample
aggressively, or rely on the timers rather than on spans for item-level detail.

*Where the `ObservationRegistry` comes from.* Spring Batch does not read it from a global: a bean post-processor
(`BatchObservabilityBeanPostProcessor`) injects the application's `ObservationRegistry` into every `Job` and `Step`
*bean*. A step that is built inline and never exposed as a bean gets no registry, and its `spring.batch.step`
meters and spans silently never appear (its jobs still do). Either declare the steps as beans, or hand the
registry to the builder explicitly: `+new StepBuilder(...).observationRegistry(registry)+` or
`+new ChunkOrientedStepBuilder<...>(...).observationRegistry(registry)+`.

== Java Flight Recorder events

Spring Batch 6.0 emits *JFR events* for job, step and chunk execution. Because JFR is built into the JVM and
cheap enough to leave on, this gives a full picture of a production run -- framework phases interleaved with
GC, allocation, JDBC and thread activity -- without attaching anything:

[source,bash]
----
java -XX:StartFlightRecording=filename=endofday.jfr,settings=profile,dumponexit=true \
     -jar batch-app.jar --spring.batch.job.name=endOfDayJob run.date=2026-01-31
----

The events are named after their classes in `org.springframework.batch.core.observability.jfr.events` -- there is no
short `+SpringBatch...+` name to filter on:

[cols="2,3",options="header"]
|===
| Event class | Emitted by

| `job.JobLaunchEvent`, `job.JobExecutionEvent` | every job launch and execution
| `step.StepExecutionEvent` | every step
| `step.tasklet.TaskletExecutionEvent` | classic chunk steps and tasklet steps (one event for the whole step)
| `step.chunk.ItemReadEvent`, `ItemProcessEvent`, `ChunkWriteEvent`, `ChunkTransactionEvent`, `ChunkScanEvent` | the 6.0 `ChunkOrientedStep` only
| `step.partition.PartitionSplitEvent`, `PartitionAggregateEvent` | partitioned steps
|===

[source,bash]
----
jfr summary endofday.jfr
jfr print --events org.springframework.batch.core.observability.jfr.events.job.JobExecutionEvent endofday.jfr
jfr print --events org.springframework.batch.core.observability.jfr.events.step.chunk.ChunkWriteEvent endofday.jfr
----

This is the tool of choice for "the job took three hours last night and nobody was watching": the recording is
written by the run itself and analysed afterwards in JDK Mission Control. The `jfr` command ships in the JDK's
`bin` directory (it is not on the `PATH` of every installation).

== Worked example: the settlement job, instrumented

The running example of this section -- 1000 trades settled in chunks of 50 -- was run on Spring Batch 6.0.6 and Spring
Boot 4.1.2 with `spring-boot-starter-actuator` and `micrometer-registry-prometheus` on the classpath, the step
declared as a `@Bean` built with `ChunkOrientedStepBuilder`. Listing the meters whose name starts with `spring.batch`
gives (with `_count` of each timer):

[source,text]
----
TIMER spring.batch.chunk.write   [job.name=observedChunkJob, status=SUCCESS, step.name=observedChunkStep] count=20
TIMER spring.batch.item.process  [job.name=observedChunkJob, status=SUCCESS, step.name=observedChunkStep] count=1000
TIMER spring.batch.item.read     [job.name=observedChunkJob, status=SUCCESS, step.name=observedChunkStep] count=1001
TIMER spring.batch.job           [name=observedChunkJob, status=COMPLETED] count=1
TIMER spring.batch.job.launch.count [] count=1
TIMER spring.batch.step          [job.name=observedChunkJob, name=observedChunkStep, status=COMPLETED, type=...ChunkOrientedStep] count=1
(and a LONG_TASK_TIMER spring.batch.<x>.active for each of them)
----

The numbers tell the story of the chunk loop: 1000 processed items, 20 chunk writes (1000 divided by 50), and
1001 reads -- the last one is the `read()` that returned `null` and ended the step. The same run as seen by the
Prometheus registry (tag keys have their dots turned into underscores, timers gain the `_seconds` suffix and the
`_count`/`_sum`/`_max` series):

[source,text]
----
spring_batch_chunk_write_seconds_count{error="none",spring_batch_chunk_write_job_name="observedChunkJob",spring_batch_chunk_write_status="SUCCESS",spring_batch_chunk_write_step_name="observedChunkStep"} 20
spring_batch_chunk_write_seconds_sum{...} 0.058124753
spring_batch_chunk_write_seconds_max{...} 0.012620417
spring_batch_item_process_seconds_count{...} 1000
spring_batch_item_process_seconds_sum{...} 0.015611871
spring_batch_job_seconds_count{error="none",spring_batch_job_name="observedChunkJob",spring_batch_job_status="COMPLETED"} 1
spring_batch_job_seconds_sum{...} 0.248160125
spring_batch_job_active_seconds_count{spring_batch_job_name="observedChunkJob"} 0
----

Dividing `_sum` by `_count` gives the mean cost: about 58 ms of writing for 20 chunks (2.9 ms each, 12.6 ms for the
slowest) against 16 ms of processing for 1000 items. In this run the writer, not the processor, is where the time
goes, which is exactly the diagnosis the item-versus-chunk split exists to make. The `.active` series are all 0
after the run; during it, `spring_batch_job_active_seconds_count` is 1, and that is the series behind an alert such
as "the job is still active at 06:00".

With the failure switch armed (trade 600 throws), the same job produces a different set of series:

[source,text]
----
TIMER spring.batch.chunk.write  [job.name=observedChunkJob, status=SUCCESS, step.name=observedChunkStep] count=11
TIMER spring.batch.item.process [job.name=observedChunkJob, status=SUCCESS, step.name=observedChunkStep] count=599
TIMER spring.batch.item.process [job.name=observedChunkJob, step.name=observedChunkStep] count=1
TIMER spring.batch.item.read    [job.name=observedChunkJob, status=SUCCESS, step.name=observedChunkStep] count=600
TIMER spring.batch.job          [name=observedChunkJob, status=FAILED] count=1
TIMER spring.batch.step         [job.name=observedChunkJob, name=observedChunkStep, status=FAILED, error=IllegalStateException, ...] count=1
----

The failed step carries `status=FAILED` and the exception class as its `error` tag, the job carries
`status=FAILED`, and the progress made before the failure is visible too (600 reads, 599 successful processes, 11
chunk writes: ten full chunks plus the one cut short). An alert on `+spring_batch_job_seconds_count{spring_batch_job_status="FAILED"}+`
increasing is the cheapest possible "last night's job failed" page.

....
flowchart LR
    J["JobOperator.start"] --> L["spring.batch.job.launch.count"]
    L --> JB["spring.batch.job (and job.active)"]
    JB --> ST["spring.batch.step (and step.active)"]
    ST --> R["spring.batch.item.read, once per read"]

=== Seeing the observations

A custom `ObservationHandler` shows exactly which observations a run creates. Registered on the
`ObservationRegistry` bean, with `supportsContext` always true and `onStop` collecting `context.getName()`, it
prints for the 6.0 chunk step:

[source,text]
----
spring.batch.chunk.write, spring.batch.item.process, spring.batch.item.read,
spring.batch.job, spring.batch.job.launch.count, spring.batch.step
----

and for the same job built on the classic `StepBuilder` (steps declared as beans): `spring.batch.job`,
`spring.batch.job.launch.count` and `spring.batch.step` only, with the item and chunk timers recorded directly.

[source,java]
----
@Component
public class ObservationLogger implements ObservationHandler<Observation.Context> {

    @Override
    public boolean supportsContext(Observation.Context context) {
        return true;
    }

    @Override
    public void onStop(Observation.Context context) {
        log.debug("observation {} {}", context.getName(), context.getLowCardinalityKeyValues());
    }
}
----

Boot registers every `ObservationHandler` bean on the registry, which makes this the quickest way to feed
custom reporting (an audit log of job outcomes, for instance) from the same instrumentation.

=== JFR on the same run

Running the 6.0 step with `-XX:StartFlightRecording` and `jfr summary` lists exactly the events described above,
with counts that match the meters:

[source,text]
----
 org.springframework.batch.core.observability.jfr.events.step.chunk.ItemReadEvent              1001
 org.springframework.batch.core.observability.jfr.events.step.chunk.ItemProcessEvent           1000
 org.springframework.batch.core.observability.jfr.events.step.chunk.ChunkTransactionEvent        21
 org.springframework.batch.core.observability.jfr.events.step.chunk.ChunkWriteEvent              20
 org.springframework.batch.core.observability.jfr.events.step.StepExecutionEvent                  1
 org.springframework.batch.core.observability.jfr.events.job.JobLaunchEvent                       1
 org.springframework.batch.core.observability.jfr.events.job.JobExecutionEvent                    1
----

One `ChunkTransactionEvent` per transaction (21: twenty chunks plus the final empty one) lets a recording separate
transaction overhead from write time. `jfr print` of a `ChunkWriteEvent` shows the step name, the step execution id,
the `chunkWriteStatus`, the `itemCount` (50) and the duration, with the Java stack trace of the writing thread. The
same job built with the classic `StepBuilder` produces only `StepExecutionEvent`, `TaskletExecutionEvent`,
`JobLaunchEvent` and `JobExecutionEvent`: item- and chunk-level events are a feature of the new chunk step.

== What Actuator adds

With `spring-boot-starter-actuator` on the classpath, a batch application also gets:

* `/actuator/metrics/spring.batch.job` and the other meters, browsable per tag;
* `/actuator/prometheus` for scraping;
* `/actuator/health` -- worth extending with a custom indicator that reports the last execution's status, so an
  orchestrator can tell a *failed* job from a *finished* one;
* `/actuator/loggers` to raise a package's log level on a running job without restarting it.

(`HealthIndicator` and `Health` live in `org.springframework.boot.health.contributor` since Spring Boot 4.)

[source,java]
----
@Component
public class LastRunHealthIndicator implements HealthIndicator {

    private final JobRepository jobRepository;

    public LastRunHealthIndicator(JobRepository jobRepository) {
        this.jobRepository = jobRepository;
    }

    @Override
    public Health health() {
        JobInstance instance = jobRepository.getLastJobInstance("endOfDayJob");
        if (instance == null) {
            return Health.unknown().withDetail("reason", "never run").build();
        }
        JobExecution execution = jobRepository.getLastJobExecution(instance);
        return (execution.getStatus() == BatchStatus.COMPLETED ? Health.up() : Health.down())
                .withDetail("executionId", execution.getId())
                .withDetail("status", execution.getStatus())
                .withDetail("endTime", execution.getEndTime())
                .build();
    }
}
----

The metadata tables remain the durable record behind all of this -- see
xref:backend/spring-batch/job-repository-and-metadata-schema.adoc[The job repository & metadata schema].
