= Stopping, restart & recovery
:description: How a Spring Batch job ends and how it comes back -- natural completion versus a programmatic stop, StepExecution.setTerminateOnly and the 6.0 StoppableStep that makes external stop work for every step type, job failure and ExitStatus, controlling restart with preventRestart, startLimit and allowStartIfComplete, the 6.0 JobOperator.recover for executions stranded by a crash, and failing a step that read nothing with NoWorkFoundStepExecutionListener.
:keywords: stop, STOPPING, STOPPED, setTerminateOnly, StoppableStep, JobOperator.stop, restart, restartable, startLimit, allowStartIfComplete, ABANDONED, abandon, recover, stranded execution, crash recovery, NoWorkFoundStepExecutionListener, ExitStatus, BatchStatus, rerun a completed step

include::partial$ai-disclaimer.adoc[]

Batch jobs are long-running, so they get interrupted: an operator stops one, a pod is evicted, a database goes
away. What separates a batch framework from a loop is what happens next.

== Natural completion vs. a programmatic stop

A job ends *naturally* when its last step completes -- `BatchStatus.COMPLETED`, `ExitStatus.COMPLETED` -- or
when a step fails and no transition handles the failure, giving `FAILED`.

A *stop* is different: it is a request, honoured at the next safe checkpoint, that leaves the execution
restartable.

=== Stopping from outside

`JobOperator.stop(jobExecution)` sets the execution to `STOPPING`. The running step notices at its next chunk
boundary, finishes the in-flight transaction, and the execution becomes `STOPPED`:

[source,java]
----
@Service
public class BatchControlService {

    private final JobOperator jobOperator;
    private final JobRepository jobRepository;

    public BatchControlService(JobOperator jobOperator, JobRepository jobRepository) {
        this.jobOperator = jobOperator;
        this.jobRepository = jobRepository;
    }

    public void stopAll(String jobName) throws Exception {
        for (JobExecution execution : jobRepository.findRunningJobExecutions(jobName)) {
            jobOperator.stop(execution);
        }
    }
}
----

The stop is *cooperative*, not immediate: the current chunk is allowed to commit, so no work is lost and no
partial chunk is written.

In Spring Batch 6.0 a stop request reaches *every* step type, through `StoppableStep` (it extends `Step`, and every
`AbstractStep` implements it). Its default `stop(StepExecution)` marks the step execution as terminate-only and sets
its status to `STOPPED`; the step ends after the work it is doing, and the job ends `STOPPED` without starting the
next step. What differs between step types is *how soon*:

* a chunk step checks at every chunk boundary, so it stops after the chunk in flight commits;
* a plain tasklet cannot be interrupted in the middle of `execute()`: a 1.5-second tasklet ran to the end of that call,
  committed, and only then was the step recorded `STOPPED` (`COMMIT_COUNT` 1) and the following step skipped -- stopped
  *late*, not ignored;
* a tasklet that wants to stop sooner opts in with `StoppableTasklet`. Its callback `stop()` is called from the stopping
  thread, so the flag it sets must be `volatile`. The no-argument `stop()` is deprecated for removal since 6.0 -- the
  default `stop(StepExecution)` delegates to it, and it is still the abstract method to implement -- and
  `stop(StepExecution)` is the new hook.

[source,java]
----
public class LongRunningTasklet implements StoppableTasklet, StepExecutionListener {

    private static final int UNITS = 20;
    private volatile boolean stopping;

    @Override
    public void beforeStep(StepExecution stepExecution) {
        this.stopping = false;     // the bean is reused by every execution
    }

    @Override
    public RepeatStatus execute(StepContribution contribution, ChunkContext chunkContext) throws Exception {
        ExecutionContext context = chunkContext.getStepContext().getStepExecution().getExecutionContext();
        int done = context.getInt("units.done", 0);        // restart: resume from here
        while (!stopping && done < UNITS) {
            Thread.sleep(100);                              // one unit of work
            done++;
            context.putInt("units.done", done);
        }
        // CONTINUABLE when stopped with work left, so the step is not recorded as
        // COMPLETED and the remaining work is picked up on restart
        return stopping && done < UNITS ? RepeatStatus.CONTINUABLE : RepeatStatus.FINISHED;
    }

    @Override
    public void stop() {
        this.stopping = true;      // called by the framework when a stop is requested
    }
}
----

The `beforeStep` reset is not decoration. The tasklet is a singleton bean, so `stopping` outlives the execution that
was stopped: the first version of this example, without the reset, was restarted with the flag still `true` and
returned `CONTINUABLE` on every call -- an endless tight loop that only ended when the process was killed. A tasklet
that implements `StepExecutionListener` is registered as a listener of its step automatically.

Run with a stop requested after 0.7 s, the tasklet had done seven of its twenty units; the stop left the execution
`STOPPED`, the step context persisted `units.done=7`, and the restart (a second `JobExecution` of the same instance)
did the remaining thirteen:

[source,text]
----
leaving execute() with units.done=7 stopping=true      -> execution 1 STOPPED / STOPPED
leaving execute() with units.done=20 stopping=false    -> execution 2 COMPLETED / COMPLETED

STEP_EXECUTION_ID JOB_EXECUTION_ID STEP_NAME STATUS    COMMIT_COUNT
1                 1                longStep  STOPPED   1
2                 2                longStep  COMPLETED 1
----

=== Stopping from inside

Business logic can stop the job itself by flagging the current step execution. The step finishes its chunk and
the job stops:

[source,java]
----
@Bean
public Step guardedStep(JobRepository jobRepository, PlatformTransactionManager tx) {
    return new StepBuilder("guardedStep", jobRepository)
            .tasklet((contribution, chunkContext) -> {
                if (marketDataService.isStale()) {
                    chunkContext.getStepContext().getStepExecution().setTerminateOnly();
                }
                return RepeatStatus.FINISHED;
            }, tx)
            .build();
}
----

`setTerminateOnly()` results in a `JobInterruptedException` and a `STOPPED` execution -- which, unlike a
failure, reads as "deliberately halted" in the metadata.

A flow can also be told to stop declaratively, with `.stopAndRestart(step)` naming where a restart should pick
up -- see xref:backend/spring-batch/step-flow-and-listeners.adoc[Step flow & listeners].

== Failure and `ExitStatus`

When a step throws an exception that is not skipped, not retried and not caught by a transition, the step is
`FAILED` and, by default, so is the job. The failing throwables are recorded on the execution:

[source,java]
----
JobExecution execution = jobRepository.getJobExecution(executionId);
if (execution.getStatus() == BatchStatus.FAILED) {
    execution.getAllFailureExceptions().forEach(throwable -> log.error("job failed", throwable));
    log.error("exit code {} / {}", execution.getExitStatus().getExitCode(),
                                   execution.getExitStatus().getExitDescription());
}
----

`ExitStatus` is the outward-facing outcome: `COMPLETED`, `FAILED`, `STOPPED`, `NOOP`, `UNKNOWN`, or any custom
code a listener sets. Callers -- a shell script's exit code, a flow transition, a monitoring probe -- key on
that string.

== Restart

Restarting means launching the *same* `JobInstance` again, which the framework recognises by the identifying
parameters (xref:backend/spring-batch/jobs-instances-and-parameters.adoc[Jobs, instances & parameters]).
Spring Batch then:

. finds the previous `JobExecution` for that instance;
. skips steps that already ended `COMPLETED` -- unless `allowStartIfComplete(true)` says otherwise;
. resumes the first incomplete step, restoring its step-scoped `ExecutionContext` so a restartable reader
  continues where it stopped.

[source,java]
----
// restart the instance whose previous execution is this one
JobExecution failedExecution = jobRepository.getJobExecution(failedExecutionId);
JobExecution restarted = jobOperator.restart(failedExecution);
----

Three switches shape this behaviour:

[cols="1,3",options="header"]
|===
| Setting | Effect

| `.preventRestart()` on the job | The instance may never be restarted; a second launch throws `JobRestartException`.
| `.startLimit(n)` on a step | The step may be started at most `n` times across all executions of the instance; exceeding it fails the job with `StartLimitExceededException`.
| `.allowStartIfComplete(true)` on a step | The step runs again on restart even though it completed -- for validation, staging or clean-up steps that must always execute.
|===

=== Rerunning a completed step

A step that already succeeded is normally skipped on restart. `allowStartIfComplete(true)` is the supported
way to force it:

[source,java]
----
@Bean
public Step stageInputStep(JobRepository jobRepository, PlatformTransactionManager tx) {
    return new StepBuilder("stageInputStep", jobRepository)
            .tasklet(new CopyInputFileTasklet(), tx)
            .allowStartIfComplete(true)
            .build();
}
----

Note the constraint this places on the step: it will run more than once for one instance, so it must be
idempotent.

A *completed job instance* cannot be rerun at all. If the same logical work must run twice, give it different
identifying parameters -- an incrementer is the tidy way
(xref:backend/spring-batch/configuring-a-job.adoc[Configuring a job]).

== Recovering stranded executions

If the JVM dies mid-run, nobody updates the metadata: the execution stays `STARTED` (or `STOPPING`) forever,
and because Spring Batch believes it is still running, a restart is refused. Historically this was fixed by
hand with an `UPDATE` statement.

Spring Batch 6.0 adds `JobOperator.recover()`, which finds such executions and marks them appropriately so
they can be restarted:

[source,java]
----
@Component
public class StartupRecovery implements ApplicationRunner {

    private final JobOperator jobOperator;
    private final JobRepository jobRepository;

    public StartupRecovery(JobOperator jobOperator, JobRepository jobRepository) {
        this.jobOperator = jobOperator;
        this.jobRepository = jobRepository;
    }

    @Override
    public void run(ApplicationArguments args) throws Exception {
        for (JobExecution stranded : jobRepository.findRunningJobExecutions("endOfDayJob")) {
            // nothing can genuinely be running: this process has just started
            jobOperator.recover(stranded);
        }
    }
}
----

`abandon(jobExecution)` remains available for the opposite decision: mark a stopped or crashed execution
`ABANDONED` so that restart logic ignores it entirely and the instance is considered closed (the `long` overload is
deprecated for removal). After `abandon` on a failed execution, `start` with the same parameters threw
`JobInstanceAlreadyCompleteException` and `restart` threw `JobRestartException` with the same message.

== Failing a step that found no work

An empty input is usually a bug in the upstream feed, not a success. `NoWorkFoundStepExecutionListener` turns
"read nothing" into a failure:

[source,java]
----
@Bean
public Step loadTradesStep(JobRepository jobRepository, PlatformTransactionManager tx,
                           ItemReader<Trade> reader, ItemWriter<Trade> writer) {
    return new StepBuilder("loadTradesStep", jobRepository)
            .<Trade, Trade>chunk(500, tx)
            .reader(reader)
            .writer(writer)
            .listener(new NoWorkFoundStepExecutionListener())
            .build();
}
----

The listener inspects `readCount` in `afterStep` and returns `ExitStatus.FAILED` when it is zero. Run on an empty
file, the step ended with `BatchStatus` `COMPLETED` and exit code `FAILED`, and so did the job: the *exit* status is
`FAILED` (what a flow transition, an exit code or a monitoring probe sees) but the *batch* status is `COMPLETED`, so the
instance is complete and cannot be restarted. When an
empty input is legitimate, route on it instead -- return a custom `NO_DATA` exit code from a listener and add
a `+.on("NO_DATA").to(alertStep)+` transition, as in
xref:backend/spring-batch/step-flow-and-listeners.adoc[Step flow & listeners]. This and related recipes are in
https://docs.spring.io/spring-batch/reference/common-patterns.html[Common batch patterns].

== Worked example: stopping the load and restarting it

The end-of-day load, with a 200 ms processor to give a stop time to arrive, was launched on a separate thread and a
stop requested after 0.8 s. While it ran, the persisted state showed one chunk done
(`READ_COUNT 3`, `COMMIT_COUNT 1`, `tradeReader.read.count=3`). The stop moved the execution through `STOPPING` to
`STOPPED` at the next chunk boundary. (The numbers below are from the variant of the job with a singleton reader, whose
step is named `slowFixedStep`; the step-scoped reader, which behaved differently, follows.)

[mermaid]
....
sequenceDiagram
    participant Op as JobOperator
    participant Repo as JobRepository
    participant Step as chunk step
    Note over Step: processing chunk 2
    Op->>Repo: execution STOPPING, end time set
    Op->>Step: StoppableStep.stop(stepExecution)
    Note over Step: terminate-only is set, the chunk is not cut short
    Step->>Step: chunk 2 commits
    Step->>Step: boundary check: terminate-only seen
    Step->>Repo: step STOPPED, job STOPPED
....

[source,text]
----
stop() returned true
result: execution 1 STOPPED / STOPPED

STEP_NAME    STATUS  READ_COUNT FILTER_COUNT WRITE_COUNT COMMIT_COUNT ROLLBACK_COUNT
slowFixedStep STOPPED 6          1            5            2            0

TRADE: ids 1, 2, 3, 4, 6
----

Six items read, two chunks committed, five rows written (the filtered trade 5 is the difference) and no rollback: the
chunk in flight was allowed to finish, so no *partial* chunk exists. With the reader declared as an ordinary singleton
bean, the persisted context was `fixedReader.read.count=6`, the restart read only the remaining four items
(`READ_COUNT 4`, two commits) and the table ended with nine rows.

[IMPORTANT]
====
The same run with the reader declared `@StepScope` -- as the end-of-day reader is, to bind `input.file` -- behaved
differently on Spring Batch 6.0.6. The step was `STOPPED` with the same counters, but the persisted context read
`tradeReader.read.count=0` instead of `6`, so the *restart read the file from the first line* and its first insert
failed on the primary key of trade 1 (`DuplicateKeyException`, execution `FAILED`). A failure in a chunk (the file with a bad record in the next
section) kept `read.count=6` for the same step-scoped reader; only the operator-driven stop lost it. The stop path registers the step execution on the stopping thread and releases it afterwards, and the
step-scoped reader was closed in the process, which resets the position the reader had saved. Until that is fixed,
treat a stopped execution of a step with a step-scoped reader as *replayable from the start*: make the writes
idempotent (an upsert, or a `MERGE` keyed on the trade id), or keep the reader a singleton and bind the parameter by
another means.
====

== Worked example: failure, correction and restart

A failure, unlike an operator stop, restarts correctly even with the step-scoped reader. The input has a record the
processor rejects (trade 8, quantity 0). The first execution failed in the third chunk; the
operator fixed the file and called `jobOperator.restart(failedExecution)`:

[source,text]
----
committed chunk 1: read=3 write=3
committed chunk 2: read=6 write=5
ERROR Encountered an error executing step loadStep in job endOfDayJob
java.lang.IllegalArgumentException: trade 8 has quantity 0
endOfDayJob finished as FAILED in 202ms
...
step loadStep starting
committed chunk 1: read=3 write=3
committed chunk 2: read=4 write=4
staged=10 loaded=9 for 2026-01-30
endOfDayJob finished as COMPLETED in 76ms
----

Three observations tie the restart rules to the numbers. `stageStep` did not run again (it had completed). The restarted
`loadStep` read four items, not ten: its `ExecutionContext` handed `tradeReader.read.count=6` back to the reader's
`open()`. And the first chunk of the restart is *items 7 to 9*, which includes the trade that had failed -- the
transaction of the failed chunk had rolled back, so none of its rows existed. The full tables of that run are listed
in xref:backend/spring-batch/job-repository-and-metadata-schema.adoc[The job repository & metadata schema].

The programmatic stop from inside, `setTerminateOnly()` in a guard tasklet followed by another step, was run too: the
tasklet's step ended `STOPPED`, the job `STOPPED`, the next step never started, and `getAllFailureExceptions()` listed
two ``JobInterruptedException``s (`Job interrupted by step execution` and `Job interrupted status detected`).

== Worked example: a crash and `recover()`

To see a stranded execution, the same load was started and the JVM then killed with `Runtime.halt(137)` while the
second chunk was in flight -- no `finally`, no shutdown hook, nothing updated. The next process found:

[source,text]
----
-- BATCH_JOB_EXECUTION
JOB_EXECUTION_ID JOB_INSTANCE_ID STATUS  EXIT_CODE
1                1               STARTED UNKNOWN

-- BATCH_STEP_EXECUTION
STEP_EXECUTION_ID JOB_EXECUTION_ID STEP_NAME    STATUS  READ_COUNT WRITE_COUNT COMMIT_COUNT
1                 1                slowLoadStep STARTED 3          3           1

TRADE: ids 1, 2, 3
----

The execution is `STARTED` and will stay so: one chunk was committed (`TRADE` has three rows), and the repository
believes the job is still running. A restart is refused:

[source,text]
----
JobRestartException: Illegal state (only happens on a race condition): job execution already running with name=slowLoadJob and parameters={...}
----

After `jobOperator.recover(stranded)` the same row read `FAILED` with exit code `UNKNOWN`, and the step row `FAILED`; the
restart then completed:

[source,text]
----
after recover(): status FAILED exit exitCode=UNKNOWN
result: execution 33 COMPLETED / COMPLETED

STEP_EXECUTION_ID STEP_NAME    STATUS    READ_COUNT FILTER_COUNT WRITE_COUNT COMMIT_COUNT
1                 slowLoadStep FAILED    3          0            3           1
33                slowLoadStep COMPLETED 7          1            6           3

TRADE: ids 1, 2, 3, 4, 6, 7, 8, 9, 10
----

Seven items read by the restart -- items 4 to 10, resuming after the committed first chunk -- and nine rows in the
end, trades 1 to 3 from before the crash and the rest after it. (The restart's execution id is 33 rather than 2: on
the file-based H2 database the id sequence jumped when the process was killed.)
