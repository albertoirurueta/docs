= Architecture & processing strategies
:description: The three-layer Spring Batch architecture (application, core, infrastructure), the batch stereotypes, general batch principles and guidelines, and the processing strategies available -- the normal batch window, concurrent batch and online access with logical locking, parallel processing, and partitioning with its six break-up approaches.
:keywords: spring batch architecture, application layer, batch core, batch infrastructure, batch stereotypes, batch principles, batch window, concurrent batch and online, logical locking, parallel processing, partitioning, fixed-length break-up, range break-up, list break-up, hashing, modulus, custom partitioning, idempotency, restartability

include::partial$ai-disclaimer.adoc[]

Spring Batch is layered so that business logic, batch runtime and reusable plumbing stay separate, and it
leaves the *processing strategy* -- how a workload is split up in time and across processes -- as an explicit
design decision. This page covers both.

== The three layers

[mermaid]
....
flowchart TB
    App["Application layer<br/>your Job/Step configuration, ItemProcessors, Tasklets, business services"]
    Core["Batch core<br/>Job, Step, JobRepository, JobOperator, builders, flows, listeners, partitioning"]
    Infra["Batch infrastructure<br/>ItemReaders, ItemWriters, RepeatTemplate, RetryTemplate, ItemStream"]
    App --> Core
    App --> Infra
    Core --> Infra
....

*Application* is the code written for a particular business problem: the job and step definitions, the
processors, any tasklets, and the services they call. It is the only layer that changes per project.

*Batch core* (`spring-batch-core`) is the runtime that launches and controls a job: the domain classes, the
`JobRepository` that records executions, the `JobOperator` that starts and stops them, the builders, flow
handling, listeners and partitioning.

*Batch infrastructure* (`spring-batch-infrastructure`) holds the reusable, problem-agnostic pieces -- the
readers and writers, `RepeatOperations`, retry support, and the `ItemStream` contract. Both the application
and the core layer build on it, and it can be used without the core layer at all.

The stereotypes that populate these layers -- `Job`, `Step`, `JobRepository`, `JobOperator`,
`ItemReader`/`ItemProcessor`/`ItemWriter` -- are introduced in
xref:backend/spring-batch/jobs-instances-and-parameters.adoc[Jobs, instances & parameters] and
xref:backend/spring-batch/steps-executions-and-context.adoc[Steps, executions & the ExecutionContext]. The
layering itself is described in
https://docs.spring.io/spring-batch/reference/spring-batch-architecture.html[Batch processing and Spring
Batch's architecture].

A minimal job touches all three layers without naming them:

[source,java]
----
@Bean
public Step loadCustomers(JobRepository jobRepository, PlatformTransactionManager tx,
                          ItemReader<CustomerCsv> reader,      // infrastructure
                          ItemProcessor<CustomerCsv, Customer> processor,  // application
                          ItemWriter<Customer> writer) {       // infrastructure
    return new StepBuilder("loadCustomers", jobRepository)     // core
            .<CustomerCsv, Customer>chunk(500, tx)
            .reader(reader)
            .processor(processor)
            .writer(writer)
            .build();
}
----

== General batch principles and guidelines

These are the design rules that make a batch program survivable in production:

* *Make steps idempotent.* A step that is rerun after a crash must not double-count. Prefer writes that can be
  replayed -- upserts keyed on a natural key, or a watermark that advances only on commit.
* *Keep each step small and single-purpose.* One step should do one thing: stage a file, load it, aggregate it,
  archive it. Small steps restart cheaply and fail informatively.
* *Simplify aggressively.* Batch code is read at 3 a.m. Complex conditional flows are harder to reason about
  than three sequential steps.
* *Minimise system I/O.* Read and write in chunks, not per item. Avoid re-reading the same data in several
  steps; stage it once.
* *Do not do in a batch what a database does better.* Set-based updates, sorting and aggregation are usually
  cheaper in SQL than row-by-row in Java -- see
  xref:backend/spring-batch/tasklet-steps.adoc[Tasklet steps] for wrapping such a statement in a step.
* *Log liberally, and count.* Every `StepExecution` already records read/write/skip counts; add business-level
  logging at chunk boundaries, not per item.
* *Allocate enough memory to avoid re-reads, but no more.* Large in-memory caches defeat chunking.
* *Validate input at the boundary* and assume nothing downstream -- see
  xref:backend/spring-batch/item-processors.adoc[ItemProcessors].
* *Plan and execute stress tests early* with production-scale volumes; batch problems are volume problems.
* *Build checks into the job*, not into a runbook: row counts, control totals and reconciliation as steps that
  fail the job.

== Processing strategies

=== The normal batch window

The simplest arrangement: online access is closed (or quiescent), and the batch owns the data for a fixed
window. There is no contention, so no locking strategy is needed and jobs can use the fastest bulk techniques.
The design constraint is purely the clock -- the work must fit the window, which is what makes the scaling
options in xref:backend/spring-batch/scaling-and-parallel-processing.adoc[Scaling & parallel processing]
relevant.

=== Concurrent batch and online processing

When the online system stays available, batch and online transactions contend for the same rows. Options, in
increasing order of intrusiveness:

* keep batch transactions *short* (a small commit interval) so locks are held briefly;
* use *optimistic locking* -- a version column checked on update, so a conflicting online change fails the item
  rather than blocking it;
* use *pessimistic locking* on a narrow set of rows for the duration of one chunk;
* use a *logical lock*: a dedicated lock-flag column or lock table that both the online application and the
  batch respect, so the batch marks a record as "being processed" and the online path refuses or defers.

The transaction-isolation trade-offs behind these are covered in
xref:database/sql/transactions.adoc[SQL Transactions] and
xref:backend/springboot/transaction-isolation-and-locking.adoc[Transaction Isolation & Locking].

=== Parallel processing

Independent jobs, or independent steps within a job, run at the same time. This is the cheapest speed-up when
the workloads do not touch the same data: split flows inside one job
(xref:backend/spring-batch/step-flow-and-listeners.adoc[Step flow & listeners]) or simply schedule separate
jobs concurrently. The prerequisite is that the parallel units share no mutable state and no contended table.

=== Partitioning

One logically identical step is run many times over *disjoint slices* of the input. Partitioning is the
strategy that scales a single large step, and it is described in detail -- with the `Partitioner`,
`PartitionHandler` and worker-step machinery -- in
xref:backend/spring-batch/scaling-and-parallel-processing.adoc[Scaling & parallel processing].

The strategic question is how to break the input up. The classic approaches:

[cols="1,3",options="header"]
|===
| Approach | How the input is split

| *Fixed-length* (record count)
| Each partition gets a fixed number of records -- partition 1 takes records 1..10 000, partition 2 takes
  10 001..20 000. Simple; assumes uniform per-record cost.

| *Range* (key range)
| Each partition owns a contiguous key range -- customer IDs `+A--F+`, `+G--M+`, `+N--Z+`, or a date range. Natural
  for indexed keys; can skew badly if the key distribution is uneven.

| *List* (explicit breakdown)
| A separate control table or file lists the partitions explicitly -- one per branch, region, or file. Gives
  full control and allows an operator to add or remove partitions without code changes.

| *Hashing*
| A hash of the key modulo the grid size decides the partition. Distributes evenly regardless of key skew, but
  destroys locality, so each partition's reads scatter across the table.

| *Modulus*
| A numeric key modulo the grid size (`id % 8`). The cheapest even split when keys are dense integers; adding a
  partition re-shuffles every assignment.

| *Custom*
| Any project-specific rule -- one partition per input file, per tenant, per upstream feed -- implemented by
  writing a `Partitioner`.
|===

A `Partitioner` returning a per-partition `ExecutionContext` is the code form of whichever approach is chosen:

[source,java]
----
public class ModulusPartitioner implements Partitioner {

    @Override
    public Map<String, ExecutionContext> partition(int gridSize) {
        Map<String, ExecutionContext> partitions = new HashMap<>();
        for (int i = 0; i < gridSize; i++) {
            ExecutionContext context = new ExecutionContext();
            context.putInt("remainder", i);
            context.putInt("divisor", gridSize);
            partitions.put("partition" + i, context);
        }
        return partitions;
    }
}
----

Whichever strategy is chosen, decide it *before* writing the step: partitioned steps need a restartable,
stateless reader and a writer that tolerates concurrency, which constrains the choices made in
xref:backend/spring-batch/item-readers-databases.adoc[ItemReaders: databases].

== Choosing a strategy

The four strategies are not exclusive, and the order below is also the order in which to try them: each step costs
more design effort than the one before.

[mermaid]
....
flowchart TD
    Q1{"Does the work fit the window<br/>with one thread?"}
    Q1 -->|"yes"| Plain["Normal batch window:<br/>one job, chunk steps, nothing more"]
    Q1 -->|"no"| Q2{"Are there independent<br/>jobs or steps?"}
    Q2 -->|"yes"| Par["Parallel processing:<br/>split flows or concurrent jobs"]
    Q2 -->|"no"| Q3{"Does one large step<br/>dominate the run time?"}
    Q3 -->|"yes"| Part["Partitioning:<br/>one step over disjoint slices"]
    Q3 -->|"no"| Prof["Profile first:<br/>chunk size, reader and writer cost"]
    Online{"Does online traffic hit<br/>the same rows?"} -->|"yes"| Lock["Concurrent batch:<br/>short chunks, version column or logical lock"]
    Online -->|"no"| Plain
....

Two questions sit beside that chain rather than in it: whether online traffic touches the same rows (the lock
strategies of
xref:backend/spring-batch/architecture-and-processing-strategies.adoc#_concurrent_batch_and_online_processing[concurrent batch]
apply to every branch), and whether the work has to be restartable, which rules out any design whose steps
cannot be replayed. Profiling comes before every "scale it" decision, because the first bottleneck is rarely
the one assumed
(xref:backend/spring-batch/profiling-and-tuning.adoc[Profiling & tuning]).

== Partitioning worked through: a modulus split of the trade load

The `ModulusPartitioner` above is only half of a partitioned step. The other half is a worker step whose reader
reads *only its own slice* from the `ExecutionContext` the partitioner prepared. In the end-of-day example, after
the load has put the nine non-filtered trades into the `TRADE` table, a second job copies them to `TRADE_ARCHIVE`
in three partitions. The reader is step-scoped so that each worker execution gets its own slice:

[source,java]
----
@Bean
@StepScope
public JdbcPagingItemReader<Trade> modulusReader(DataSource dataSource,
        @Value("#{stepExecutionContext['remainder']}") Integer remainder,
        @Value("#{stepExecutionContext['divisor']}") Integer divisor) throws Exception {
    return new JdbcPagingItemReaderBuilder<Trade>()
            .name("modulusReader")
            .dataSource(dataSource)
            .selectClause("SELECT ID, ISIN, QUANTITY, PRICE, RUN_DATE")
            .fromClause("FROM TRADE")
            .whereClause("WHERE MOD(ID, :divisor) = :remainder")
            .parameterValues(Map.of("divisor", divisor, "remainder", remainder))
            .sortKeys(Map.of("ID", Order.ASCENDING))
            .pageSize(2)
            .rowMapper(new DataClassRowMapper<>(Trade.class))
            .build();
}

@Bean
public Step managerStep(JobRepository jobRepository, Step workerStep) {
    return new StepBuilder("managerStep", jobRepository)
            .partitioner("workerStep", new ModulusPartitioner())
            .step(workerStep)
            .gridSize(3)
            .taskExecutor(new SimpleAsyncTaskExecutor("part-"))
            .build();
}
----

`workerStep` is an ordinary chunk step (chunk size 2) from `modulusReader` to a `JdbcBatchItemWriter` into
`TRADE_ARCHIVE`. `Order` is `org.springframework.batch.infrastructure.item.database.Order`, and the builder's
`build()` declares `throws Exception`, so the bean method has to as well.

[mermaid]
....
flowchart TB
    Manager["managerStep<br/>PartitionStep, gridSize 3"] --> Splitter["ModulusPartitioner.partition(3)"]
    Splitter --> P0["workerStep:partition0<br/>remainder 0"]
    Splitter --> P1["workerStep:partition1<br/>remainder 1"]
    Splitter --> P2["workerStep:partition2<br/>remainder 2"]
    P0 --> Agg["aggregate counters into managerStep"]
    P1 --> Agg
    P2 --> Agg
....

The run logs which thread handled which trade -- three workers named after the task executor's prefix, working
concurrently on interleaved ids:

[source,text]
----
trade 1 handled on part-2
trade 4 handled on part-2
trade 3 handled on part-1
trade 6 handled on part-1
trade 2 handled on part-3
trade 8 handled on part-3
trade 9 handled on part-1
trade 7 handled on part-2
trade 10 handled on part-2
----

The metadata then holds four step executions for the one logical step: the manager and one per partition, named
`<worker step>:partition<n>` after the keys of the map the partitioner returned.

[source,text]
----
STEP_EXECUTION_ID STEP_NAME             STATUS    READ_COUNT WRITE_COUNT COMMIT_COUNT
4                 managerStep           COMPLETED 9          9           7
5                 workerStep:partition2 COMPLETED 2          2           2
6                 workerStep:partition1 COMPLETED 4          4           3
7                 workerStep:partition0 COMPLETED 3          3           2
----

The manager's counters are the sums of the workers' (`2 + 4 + 3 = 9` items, `2 + 3 + 2 = 7` commits). The
distribution is not even: trades `3, 6, 9` fall in partition 0, `1, 4, 7, 10` in partition 1 and only `2, 8` in
partition 2, because trade 5 -- the filtered one -- would have belonged to partition 2 and leaves a gap. That is
the "adding a partition re-shuffles every assignment, gaps skew the split" trade-off of the modulus approach in
miniature. Each partition also keeps its own restart state: the stored `ExecutionContext` of `partition2` holds
`remainder=2`, `divisor=3`, `modulusReader.read.count=3` and `+modulusReader.start.after={ID=8}+`, so a failed
partition restarts after its last committed key without touching the other two.

[NOTE]
====
This is a *local* partition: the workers are threads of one JVM. Remote partitioning keeps the same `Partitioner`
and worker step and only changes who executes the workers, as described in
xref:backend/spring-batch/scaling-and-parallel-processing.adoc[Scaling & parallel processing].
====

== Idempotency and the commit interval

The first principle above -- make steps idempotent -- is not abstract. The end-of-day load commits every three
items. When the input contains a bad record (trade 8 with quantity 0) the processor throws inside the third chunk;
the transaction rolls back, and the metadata of that first execution records exactly where the safe point is:

[source,text]
----
STEP_NAME  STATUS READ_COUNT FILTER_COUNT WRITE_COUNT COMMIT_COUNT ROLLBACK_COUNT
loadStep   FAILED 9          1            5           2            1
----

Nine items were read, but only the two committed chunks counted: five rows are in `TRADE` (trades 1 to 4 and 6)
and the reader's saved position is `tradeReader.read.count=6`. After the file is corrected and the same instance
restarted, the new execution reads only four items (`READ_COUNT` 4), inserts trades 7 to 10 and ends with nine
rows in the table -- no duplicates, because the restart resumed after the last commit rather than from the top. The
full walk-through is on
xref:backend/spring-batch/stopping-restart-and-recovery.adoc[Stopping, restart & recovery]. The contrasting case, in
which the saved position is lost and a plain `INSERT` fails on the primary key of a row loaded by the first attempt,
is described there too, and is the practical argument for upserts keyed on a natural key.
