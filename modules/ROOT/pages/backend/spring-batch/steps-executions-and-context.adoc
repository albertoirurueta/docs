= Steps, executions & the `ExecutionContext`
:description: The step side of the Spring Batch domain language -- Step as an independent sequential phase, StepExecution and its read/write/commit/rollback/filter/skip counters, the job- and step-scoped ExecutionContext and when each is persisted, the Serializable constraint on stored values, and passing data between steps by promoting keys with an ExecutionContextPromotionListener.

include::partial$ai-disclaimer.adoc[]

A `Step` is one independent, sequential phase of a job. Its runtime counterpart, the `StepExecution`, carries
the counters that tell you what actually happened, and the `ExecutionContext` is the small key/value store that
makes restart -- and passing data between steps -- possible.

== Step

Every `Job` is made of ``Step``s, and each step encapsulates one phase: stage a file, load it, aggregate it,
send a report. Steps come in two shapes -- *chunk-oriented* steps
(xref:backend/spring-batch/chunk-oriented-processing.adoc[Chunk-oriented processing]) and *tasklet* steps
(xref:backend/spring-batch/tasklet-steps.adoc[Tasklet steps]) -- but both are built the same way:

[source,java]
----
@Bean
public Step archiveStep(JobRepository jobRepository, PlatformTransactionManager tx) {
    return new StepBuilder("archiveStep", jobRepository)
            .tasklet(new FileArchivingTasklet(), tx)
            .build();
}
----

Keeping steps small is what makes a failure informative and a restart cheap: the job resumes at the first
step that did not complete, so a five-step job that fails in step four repeats only step four.

== StepExecution and its counters

A `StepExecution` is one attempt at one step within one `JobExecution`. Besides `BatchStatus`, `ExitStatus`,
timings and `failureExceptions`, it maintains the counters that are the primary operational signal of a batch
run:

[cols="1,3",options="header"]
|===
| Counter | Meaning

| `readCount` | Items successfully returned by the `ItemReader`.
| `filterCount` | Items the `ItemProcessor` filtered out by returning `null` -- read, but deliberately not written.
| `writeCount` | Items handed to the `ItemWriter` and committed.
| `commitCount` | Transactions committed -- one per chunk, so roughly `readCount / chunkSize`.
| `rollbackCount` | Transactions rolled back, including those replayed after a skip.
| `readSkipCount` | Items skipped because the *reader* threw a skippable exception.
| `processSkipCount` | Items skipped because the *processor* threw a skippable exception.
| `writeSkipCount` | Items skipped because the *writer* threw a skippable exception.
|===

`readCount = writeCount + filterCount + processSkipCount + writeSkipCount` is the identity worth remembering
when reconciling a run. The skip counters only move in a fault-tolerant step -- see
xref:backend/spring-batch/fault-tolerance-skip-and-retry.adoc[Fault tolerance: skip & retry].

Business code contributes to these counters through the `StepContribution` handed to a tasklet:

[source,java]
----
@Bean
public Step purgeStep(JobRepository jobRepository, PlatformTransactionManager tx, PurgeService purgeService) {
    return new StepBuilder("purgeStep", jobRepository)
            .tasklet((contribution, chunkContext) -> {
                int deleted = purgeService.purgeExpired();
                contribution.incrementWriteCount(deleted);
                return RepeatStatus.FINISHED;
            }, tx)
            .build();
}
----

The counters are persisted with the execution, so they are queryable long after the run -- see
xref:backend/spring-batch/job-repository-and-metadata-schema.adoc[The job repository & metadata schema].

== The `ExecutionContext`

An `ExecutionContext` is a `Map`-like bag of key/value pairs that Spring Batch persists on the caller's
behalf. There are two of them, with different lifetimes:

[cols="1,3",options="header"]
|===
| Context | Lifetime and persistence

| *Step-scoped* (`StepExecution.getExecutionContext()`)
| One per `StepExecution`. Persisted at *every commit point* -- that is, once per chunk. This is what makes
  restart work: a reader saves its position here, and on restart reads it back and resumes.

| *Job-scoped* (`JobExecution.getExecutionContext()`)
| One per `JobExecution`. Persisted *between steps*. Use it to hand values from one step to the next.
|===

Because both are written to the metadata tables, every stored value must be serializable by the configured
serializer (`Serializable` for the default one) and should be *small*. The context is not a cache: putting a collection of ten thousand IDs in it bloats every commit and
slows the whole step. Keep it to positions, counts and identifiers -- and note the tuning consequence in
xref:backend/spring-batch/profiling-and-tuning.adoc[Profiling & tuning].

=== Reading and writing the context

Framework components use it automatically -- `FlatFileItemReader` stores the line count, paging readers store
the page and offset -- and application code can use it too, most simply from a listener or tasklet:

[source,java]
----
@Bean
public Step countingStep(JobRepository jobRepository, PlatformTransactionManager tx) {
    return new StepBuilder("countingStep", jobRepository)
            .tasklet((contribution, chunkContext) -> {
                ExecutionContext stepContext = chunkContext.getStepContext()
                        .getStepExecution()
                        .getExecutionContext();
                long processed = stepContext.getLong("processed", 0L);
                stepContext.putLong("processed", processed + 1);
                return RepeatStatus.FINISHED;
            }, tx)
            .build();
}
----

A reader or writer that keeps its own state implements `ItemStream` so the framework calls `open`, `update`
and `close` around it:

[source,java]
----
public class WatermarkReader implements ItemStreamReader<Trade> {

    private static final String KEY = "watermark.id";
    private long lastId;

    @Override
    public void open(ExecutionContext executionContext) {
        this.lastId = executionContext.getLong(KEY, 0L);   // resume, or start at 0
    }

    @Override
    public void update(ExecutionContext executionContext) {
        executionContext.putLong(KEY, this.lastId);        // called at each commit point
    }

    @Override
    public Trade read() {
        Trade next = tradeDao.findFirstAfter(lastId);
        if (next != null) {
            this.lastId = next.getId();
        }
        return next;
    }

    @Override
    public void close() {
        // release resources
    }
}
----

Registering that stream with the step is described in
xref:backend/spring-batch/chunk-oriented-processing.adoc[Chunk-oriented processing].

== Passing data between steps

Step contexts are *not* shared: step two cannot see step one's step-scoped context. The supported way to hand
a value forward is to *promote* it to the job-scoped context with an `ExecutionContextPromotionListener`.

Step one puts the value in its own step context:

[source,java]
----
@Bean
public Step extractStep(JobRepository jobRepository, PlatformTransactionManager tx,
                        ExecutionContextPromotionListener promotionListener) {
    return new StepBuilder("extractStep", jobRepository)
            .tasklet((contribution, chunkContext) -> {
                String fileName = extractService.writeExtract();
                chunkContext.getStepContext()
                        .getStepExecution()
                        .getExecutionContext()
                        .putString("extract.file", fileName);
                return RepeatStatus.FINISHED;
            }, tx)
            .listener(promotionListener)
            .build();
}

@Bean
public ExecutionContextPromotionListener promotionListener() {
    ExecutionContextPromotionListener listener = new ExecutionContextPromotionListener();
    listener.setKeys(new String[] { "extract.file" });
    // optionally: only promote when the step ended with these exit codes
    listener.setStatuses(new String[] { ExitStatus.COMPLETED.getExitCode() });
    return listener;
}
----

The listener copies the named keys from the step context to the *job* context after the step completes. Step
two then reads them back -- most conveniently by late binding, since the job context is exposed to SpEL:

[source,java]
----
@Bean
@StepScope
public FlatFileItemReader<Trade> extractReader(
        @Value("#{jobExecutionContext['extract.file']}") String fileName) {
    return new FlatFileItemReaderBuilder<Trade>()
            .name("extractReader")
            .resource(new FileSystemResource(fileName))
            .delimited()
            .names("id", "isin", "quantity", "price")
            .targetType(Trade.class)
            .build();
}
----

Late binding with `@StepScope` and the `jobExecutionContext` / `stepExecutionContext` / `jobParameters` SpEL
roots is covered in xref:backend/spring-batch/step-flow-and-listeners.adoc[Step flow & listeners]. Note that
these expressions belong inside code, where the braces are literal; in ordinary prose an expression such as
`+#{jobExecutionContext['extract.file']}+` has to be written with the brace escaped.

For the pattern in the reference itself see
https://docs.spring.io/spring-batch/reference/common-patterns.html[Common batch patterns].

== Counters in a run that skips

The counters are easiest to trust after seeing them on an input that exercises all of them. The `loadSkipStep` is the
end-of-day load made fault tolerant (`.faultTolerant().skip(Exception.class).skipLimit(10)`, see
xref:backend/spring-batch/fault-tolerance-skip-and-retry.adoc[Fault tolerance: skip & retry]), run over the trade file
with four deliberate defects:

[cols="1,3,2",options="header"]
|===
| Line | Content | What happens to it

| 3 | quantity `0` | the processor throws: a *process skip*
| 5 | ISIN `XX0000000001` | the processor returns `null`: *filtered*
| 7 | quantity `abc` | the reader cannot parse the line: a *read skip*
| 10 | id `2` again | the writer hits the primary key: a *write skip*
|===

The `BATCH_STEP_EXECUTION` row, and the rows that reached the table:

[source,text]
----
STEP_NAME    STATUS    READ_COUNT FILTER_COUNT WRITE_COUNT COMMIT_COUNT ROLLBACK_COUNT READ_SKIP_COUNT PROCESS_SKIP_COUNT WRITE_SKIP_COUNT
loadSkipStep COMPLETED 9          1            6           6            3              1               1                  1

TRADE ids: 1, 2, 4, 6, 8, 9
----

Ten lines went in; `READ_COUNT` is 9 because the unparseable line was never *returned* by the reader -- it counts
as a read skip instead. The identity from the table above then holds exactly:

[source,text]
----
readCount (9) = writeCount (6) + filterCount (1) + processSkipCount (1) + writeSkipCount (1)
----

and `readSkipCount` stands outside the equation, since those items were never read. The step's exit status was
`COMPLETED WITH SKIPS` -- set by the `@AfterStep` listener of the step-flow page -- and the job's conditional flow
therefore went to the `reconcileStep` instead of the summary step. Without any defective line the same step ended with
`READ_COUNT` 10, `WRITE_COUNT` 9, `FILTER_COUNT` 1, four commits and no rollback.

[mermaid]
....
flowchart LR
    File["input file<br/>10 lines"] --> Reader{"reader"}
    Reader -->|"unparseable"| RS["readSkipCount 1"]
    Reader -->|"item returned"| RC["readCount 9"]
    RC --> Proc{"processor"}
    Proc -->|"throws"| PS["processSkipCount 1"]
    Proc -->|"returns null"| FC["filterCount 1"]
    Proc -->|"item"| Writer{"writer"}
    Writer -->|"constraint violation"| WS["writeSkipCount 1"]
    Writer -->|"committed"| WC["writeCount 6"]
....

== What the `ExecutionContext` really contains

The step's context is not only what application code puts in it. After the first end-of-day run, reading the persisted
contexts back through the repository gave:

[source,text]
----
stageStep  {staged.rows=10, batch.version=6.0.6, batch.stepType=...TaskletStep, batch.taskletType=...}
loadStep   {tradeReader.read.count=11, batch.version=6.0.6, batch.stepType=...TaskletStep,
            batch.taskletType=org.springframework.batch.core.step.item.ChunkOrientedTasklet}
reportStep {batch.version=6.0.6, batch.stepType=...TaskletStep, batch.taskletType=...}

job context {staged.rows=10, batch.version=6.0.6}
----

Three things to read off it. The reader contributed `tradeReader.read.count` -- the key is the reader's `name` plus a
suffix, which is why every restartable reader needs a unique name -- and its value, 11, is one more than the ten lines
because the final read that detected the end of the file is counted too. The framework itself writes `batch.version`,
`batch.stepType` and `batch.taskletType`, which also confirms that a chunk step is a `TaskletStep` running a
`ChunkOrientedTasklet`. And `staged.rows` appears in *both* the step context of `stageStep` and the job context: the
promotion listener copied it, and `reportStep` read it back through
`+@Value("#{jobExecutionContext['staged.rows']}")+` to log `staged=10 loaded=9`.

The persisted form depends on the serializer. By default the `SHORT_CONTEXT` column holds a Base64 string of the
Java-serialized map (it starts `+rO0ABXNy...+`), which cannot be read in a SQL client. With a
`JacksonExecutionContextStringSerializer` registered through `@EnableJdbcJobRepository` with an `executionContextSerializerRef` -- it needs the Jackson 3 `tools.jackson.core:jackson-databind` on the classpath -- the same column holds JSON:

[source,text]
----
{"staged.rows":["java.lang.Long",10],"batch.taskletType":"com.example.infra.HelloJob$HelloTasklet","batch.version":"6.0.6","batch.stepType":"org.springframework.batch.core.step.tasklet.TaskletStep"}
----

The JSON form records the Java type of each value (`["java.lang.Long",10]`), which is what lets a `Long` come back as a
`Long`.

== When the context is written

Both contexts are rewritten at defined moments, not continuously. The sequence for a chunk step with the end-of-day
reader, as observed through the repository while the job was running, is:

[mermaid]
....
sequenceDiagram
    participant Step as TaskletStep
    participant Reader as FlatFileItemReader
    participant Repo as JobRepository
    Step->>Reader: open(executionContext)
    Note over Reader: read.count restored, 0 on a first run
    Step->>Repo: persist the initial context
    loop each chunk
        Step->>Reader: read and process three items
        Step->>Step: write the chunk
        Step->>Reader: update(executionContext)
        Step->>Repo: persist the context, then commit
    end
    Step->>Repo: persist the final context
    Step->>Reader: close()
....

A snapshot taken between chunks, while a slow variant of the job ran, showed `tradeReader.read.count=3` in the
persisted context and one commit in the step's counters; after the second chunk the same row read `6`. That is the
whole mechanism behind restart granularity: the persisted position can lag the real position by at most the chunk that
was in flight. After a failure in the third chunk the persisted value was `6` and, once restarted, the reader skipped
those six items and read the remaining four.
