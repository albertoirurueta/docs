= Infrastructure configuration
:description: Configuring the Spring Batch infrastructure -- why @EnableBatchProcessing is left off under Spring Boot, the 6.0 split into @EnableBatchProcessing plus @EnableJdbcJobRepository and @EnableMongoJobRepository, DefaultBatchConfiguration for full manual control, the resourceless job repository and transaction manager defaults, and the 6.0 interface unification of JobRepository/JobExplorer and JobOperator/JobLauncher.
:keywords: EnableBatchProcessing, EnableJdbcJobRepository, EnableMongoJobRepository, DefaultBatchConfiguration, BatchConfigurer, ResourcelessJobRepository, ResourcelessTransactionManager, JobRepository, JobExplorer, JobOperator, JobLauncher, JobRegistry, taskExecutorRef, batch auto-configuration, spring boot batch

include::partial$ai-disclaimer.adoc[]

Before a job can run, three infrastructure beans must exist: a `JobRepository`, a `PlatformTransactionManager`
and a `JobOperator`. Under Spring Boot they are auto-configured; this page covers what they are, how to take
manual control, and what changed in 6.0.

== Leave `@EnableBatchProcessing` off under Spring Boot

`@EnableBatchProcessing` is the annotation that bootstraps the batch infrastructure *by hand*. Adding it to a
Spring Boot application **switches Boot's batch auto-configuration off**: Boot's own configuration is declared
`+@ConditionalOnMissingBean(value = DefaultBatchConfiguration.class, annotation = EnableBatchProcessing.class)+`, so
it backs off as soon as the annotation (or a `DefaultBatchConfiguration` subclass) is present. What is left is the
framework's own default, which in 6.0 is the *resourceless* repository. Running the same `helloWorldJob` with the
JDBC starter and an H2 data source on the classpath, with and without the annotation, prints:

[source,text]
----
without @EnableBatchProcessing:  repository: jdk.proxy2.$Proxy54   (the JDBC repository)  rows in BATCH_JOB_INSTANCE: 1
with    @EnableBatchProcessing:  repository: ResourcelessJobRepository                     BATCH_JOB_INSTANCE query failed (table does not exist)
----

So the annotation does not break the application -- the job still runs and the startup runner
(`JobLauncherApplicationRunner`) still launches it -- but the metadata tables are never created, `+spring.batch.jdbc.*+`
is ignored and nothing is persisted. That silent downgrade from "restartable" to "nothing remembered" is the reason
to leave the annotation off.

So, under Spring Boot:

[source,java]
----
@SpringBootApplication          // no @EnableBatchProcessing here
public class BatchApplication {
    public static void main(String[] args) {
        SpringApplication.run(BatchApplication.class, args);
    }
}
----

Boot's own documentation states the rule at
https://docs.spring.io/spring-boot/reference/io/spring-batch.html[Batch Applications]; the concrete
walk-through of what the starter auto-configures is on
xref:backend/springboot/spring-batch.adoc[Spring Batch (SpringBoot Reference)] and is not restated here.

=== What the annotation does in 6.0

Outside Spring Boot -- a plain Spring application, or a Boot application that genuinely wants to assemble the
infrastructure itself -- `@EnableBatchProcessing` is still the entry point, and 6.0 splits its
responsibilities:

* `@EnableBatchProcessing` now carries the *common* attributes only: `modular`, `taskExecutorRef`,
  `jobRegistryRef`, `observationRegistryRef`, `transactionManagerRef` and `jobParametersConverterRef` (there is no
  `jobRepositoryRef` any more);
* the store-specific configuration moved to dedicated annotations -- `@EnableJdbcJobRepository` (`dataSourceRef`,
  `transactionManagerRef`, `tablePrefix`, `isolationLevelForCreate`, `databaseType`, `executionContextSerializerRef`
  and more) and `@EnableMongoJobRepository` (`mongoOperationsRef`, `transactionManagerRef`,
  `isolationLevelForCreate` and others). Without one of them, `@EnableBatchProcessing` produces the resourceless
  repository.

[source,java]
----
@Configuration
@EnableBatchProcessing(taskExecutorRef = "batchTaskExecutor")
@EnableJdbcJobRepository(dataSourceRef = "batchDataSource", tablePrefix = "BATCH_")
public class ManualBatchInfrastructure {

    @Bean
    public TaskExecutor batchTaskExecutor() {
        return new SimpleAsyncTaskExecutor("batch-");
    }
}
----

[source,java]
----
@Configuration
@EnableBatchProcessing
@EnableMongoJobRepository(mongoOperationsRef = "mongoTemplate")
public class MongoBatchInfrastructure {
}
----

== `DefaultBatchConfiguration` for full control

When individual beans must be replaced rather than merely parameterised, extend
`DefaultBatchConfiguration` and override the factory methods. This is the replacement for the removed
`BatchConfigurer` interface -- code that implemented `BatchConfigurer` in 4.x has no equivalent in 6.0 and
must be migrated to this style.

The hooks the class exposes are `getJobRegistry()`, `getObservationRegistry()`, `getTransactionManager()`,
`getTaskExecutor()` and `getJobParametersConverter()`, plus the two `@Bean` methods `jobRepository()` and
`jobOperator(JobRepository)`. The important detail is what `jobRepository()` returns by default: a
`ResourcelessJobRepository`. Putting `@EnableJdbcJobRepository` on a `DefaultBatchConfiguration` subclass does *not*
change that -- the annotation is for the `@EnableBatchProcessing` style, and the subclass's own `jobRepository()`
bean wins. Running that combination prints `repository: ResourcelessJobRepository` and leaves the metadata tables
empty. To persist, override `jobRepository()` and build the JDBC repository explicitly:

[source,java]
----
@Configuration
public class BatchInfrastructure extends DefaultBatchConfiguration {

    @Override
    @Bean
    public JobRepository jobRepository() {
        try {
            JdbcJobRepositoryFactoryBean factory = new JdbcJobRepositoryFactoryBean();
            factory.setDataSource(batchDataSource());
            factory.setTransactionManager(getTransactionManager());
            factory.setTablePrefix("BATCH_");
            factory.setIsolationLevelForCreateEnum(Isolation.READ_COMMITTED);   // relax SERIALIZABLE deliberately
            factory.afterPropertiesSet();
            return factory.getObject();
        } catch (Exception e) {
            throw new IllegalStateException(e);
        }
    }

    @Override
    protected PlatformTransactionManager getTransactionManager() {
        return new DataSourceTransactionManager(batchDataSource());
    }

    @Bean
    public DataSource batchDataSource() {
        return DataSourceBuilder.create()
                .url("jdbc:postgresql://localhost:5432/batchmeta")
                .username("batch")
                .build();
    }
}
----

With the embedded-H2 equivalent of this class (and the `schema-h2.sql` script from `spring-batch-core`), a job ran
to `COMPLETED` through a repository proxy, the six tables and three sequences existed, and a second launch with the
same parameters threw `JobInstanceAlreadyCompleteException` -- the persisted behaviour. Extending
`DefaultBatchConfiguration` is *also* mutually exclusive with Boot's auto-configuration for the beans it defines --
which is the point: it is chosen when the defaults are not wanted.

== The resourceless default

Spring Batch 6.0 makes the infrastructure work with *no database at all*. The resourceless repository is also what
the framework's own defaults produce -- `DefaultBatchConfiguration`, and `@EnableBatchProcessing` without
`@EnableJdbcJobRepository`, give it even when a `DataSource` bean exists; a persistent repository has to be asked
for. With no `DataSource` at all, the `ResourcelessJobRepository` and `ResourcelessTransactionManager` are used, so a job can be written, run and
demonstrated with nothing but the framework on the classpath. The repository remembers what *this JVM* did -- a
second `start` with the same parameters in the same process throws `JobInstanceAlreadyCompleteException` -- but
nothing survives the process: two separate launches of the same job with the same parameters both ended with exit
code `0`.

[source,java]
----
@Configuration
public class ResourcelessInfrastructure {

    @Bean
    public JobRepository jobRepository() {
        return new ResourcelessJobRepository();
    }

    @Bean
    public PlatformTransactionManager transactionManager() {
        return new ResourcelessTransactionManager();
    }
}
----

This is excellent for samples, prototypes and unit tests, and it is what makes a "hello world" job runnable
without provisioning anything. It is *not* suitable for production: with no persisted metadata there is no
restart, no history and no audit trail. Anything that must survive a crash needs the JDBC or MongoDB
repository described in
xref:backend/spring-batch/job-repository-and-metadata-schema.adoc[The job repository & metadata schema].

== The 6.0 interface unification

Three long-standing sources of confusion were removed in 6.0:

[cols="1,3",options="header"]
|===
| Change | What it means in code

| `JobRepository` extends `JobExplorer`
| The read operations that used to require a separate `JobExplorer` bean are now on the repository itself.
  Inject `JobRepository` and call `getJobInstances`, `getJobExecutions`, `getLastJobExecution` directly. A
  separate `JobExplorer` is no longer needed.

| `JobOperator` extends `JobLauncher`
| `JobOperator` is now the single launching *and* controlling interface: `start`, `stop`, `restart`,
  `startNextInstance`, `abandon`, `recover`. `TaskExecutorJobOperator` is the standard implementation. Code
  that injected a `JobLauncher` can inject a `JobOperator` instead.

| `JobRegistry` is optional
| Jobs defined as beans are registered automatically for `start(Job, JobParameters)`, so the old `JobRegistry` plus
  `JobRegistryBeanPostProcessor` wiring is no longer required. Declare a `JobRegistry` bean (a `MapJobRegistry`)
  when something looks jobs up *by name*: the `CommandLineJobOperator` entry point fails with `No qualifying bean of
  type JobRegistry` without one, and works once the bean exists.
|===

[source,java]
----
@Service
public class BatchAdminService {

    private final JobOperator jobOperator;     // launching AND control
    private final JobRepository jobRepository; // launching metadata AND queries

    public BatchAdminService(JobOperator jobOperator, JobRepository jobRepository) {
        this.jobOperator = jobOperator;
        this.jobRepository = jobRepository;
    }

    public JobExecution lastRunOf(String jobName) {
        JobInstance instance = jobRepository.getLastJobInstance(jobName);
        return instance == null ? null : jobRepository.getLastJobExecution(instance);
    }
}
----

Using these interfaces to launch and control jobs is covered in
xref:backend/spring-batch/running-a-job.adoc[Running a job] and
xref:backend/spring-batch/stopping-restart-and-recovery.adoc[Stopping, restart & recovery]. The full list of
6.0 changes is at https://docs.spring.io/spring-batch/reference/whatsnew.html[What's new in Spring Batch 6.0].

== Wiring it up: what each style actually produces

The three ways to assemble the infrastructure above were each run against the same `helloWorldJob`, in a plain
Spring context (no Boot), with an embedded H2 data source. What they produced:

[cols="2,3,3",options="header"]
|===
| Configuration | Repository and operator | Behaviour observed

| `@EnableBatchProcessing` with a `taskExecutorRef`, plus `@EnableJdbcJobRepository` with a `dataSourceRef`
| A JDBC repository and a `JobOperator`, both transactional proxies
| `start()` returned at once with the execution in `STARTING`; a second `start()` while it still ran threw
  `JobExecutionAlreadyRunningException`. Six tables and the sequences `BATCH_JOB_INSTANCE_SEQ`,
  `BATCH_JOB_EXECUTION_SEQ` and `BATCH_STEP_EXECUTION_SEQ` existed.

| The same, without `taskExecutorRef`
| The same
| `start()` blocked and returned `COMPLETED`; a second `start()` with the same parameters threw
  `JobInstanceAlreadyCompleteException`.

| `DefaultBatchConfiguration` subclass, `@EnableJdbcJobRepository` on it
| `ResourcelessJobRepository`
| The job ran, the tables stayed empty (`BATCH_JOB_INSTANCE` held 0 rows).

| `DefaultBatchConfiguration` subclass overriding `jobRepository()` with `JdbcJobRepositoryFactoryBean`
| A JDBC repository
| The job ran and one `BATCH_JOB_INSTANCE` row was written.

| `ResourcelessJobRepository` and `ResourcelessTransactionManager` beans, a `JobOperatorFactoryBean`
| `ResourcelessJobRepository`
| The job ran; a second `start()` in the same process threw `JobInstanceAlreadyCompleteException`; no tables.
|===

Under Spring Boot the same knobs are exposed as *qualifier annotations* on ordinary beans, so Boot's configuration
can stay in charge: a `TaskExecutor` bean annotated `@BatchTaskExecutor` (from
`org.springframework.boot.batch.autoconfigure`) makes the auto-configured `JobOperator` asynchronous, and
`@BatchTransactionManager` and `@BatchDataSource` dedicate a transaction manager or a data source to batch when the
application has several. With `@BatchTaskExecutor` on a `SimpleAsyncTaskExecutor`, a `POST` to a controller that
calls `start` on the `JobOperator` returned `202` with `"status":"STARTED"` and the execution later read `COMPLETED`.

[source,java]
----
@Bean
@BatchTaskExecutor
public TaskExecutor batchTaskExecutor() {
    return new SimpleAsyncTaskExecutor("batch-");
}
----

Outside the annotations, the operator is assembled with `JobOperatorFactoryBean`, which wires the transaction manager
and returns a transactional proxy. `TaskExecutorJobOperator` itself has no `setTransactionManager`:

[source,java]
----
@Bean
public JobOperator jobOperator(JobRepository jobRepository, JobRegistry jobRegistry,
                               PlatformTransactionManager transactionManager) throws Exception {
    JobOperatorFactoryBean factory = new JobOperatorFactoryBean();
    factory.setJobRepository(jobRepository);
    factory.setJobRegistry(jobRegistry);
    factory.setTransactionManager(transactionManager);
    factory.setTaskExecutor(new SimpleAsyncTaskExecutor("batch-"));   // omit for synchronous launching
    factory.afterPropertiesSet();
    return factory.getObject();
}
----
