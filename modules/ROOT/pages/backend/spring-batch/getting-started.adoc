Spring Batch is a lightweight framework for *finite, bounded bulk processing*: reading a large but known
quantity of input, doing something to each item, and writing the result -- restartably, transactionally, and
with a full audit trail. This page places the framework, lists its modules, and walks through a first runnable
job.

== A framework for finite, bounded processing

A batch job has a beginning and an end. It processes a *finite* input -- yesterday's transactions, a delivered
file, the rows added since the last watermark -- and then terminates. That boundedness is what lets Spring
Batch offer the guarantees it does: a job that will end is a job whose progress can be recorded, whose failure
can be resumed from the last commit point, and whose outcome can be reported.

Spring Batch supplies the parts that every such program otherwise re-invents:

* a *domain language* -- `Job`, `Step`, `ItemReader`, `ItemProcessor`, `ItemWriter` -- so the structure of a
  batch program is explicit rather than buried in a `main()` method;
* a *`JobRepository`* that persists what ran, with which parameters, how far it got, and how it ended;
* *chunk-oriented processing*, which turns "read a million rows" into "read, process and write N rows per
  transaction", bounding memory and giving restart a granularity;
* *fault tolerance* -- skip, retry and rollback policies applied declaratively rather than hand-coded;
* *scaling* strategies (multi-threaded steps, parallel flows, partitioning, remote chunking) that leave the
  business logic untouched.

For the framework's own overview see
https://docs.spring.io/spring-batch/reference/spring-batch-intro.html[Spring Batch Introduction].

=== What Spring Batch is not

Spring Batch is *not a scheduler*. It has no cron table, no calendar, no concept of "run this at 02:00". It
provides the machinery to *run* a job and to know what happened; deciding *when* to run it is somebody else's
job -- Unix `cron`, Quartz, Control-M, an enterprise scheduler, a Kubernetes `CronJob`, or a message arriving
on a queue. Pairing the two is covered in
xref:backend/spring-batch/running-a-job.adoc[Running a job] and
xref:backend/spring-batch/cloud-native-batch.adoc[Cloud-native batch].

It is also not a streaming framework: an unbounded, never-ending source of events is a different problem with
different tools. And it is not an ETL product with a graphical designer -- jobs are ordinary Spring beans
written in Java.

=== A short history

Spring Batch began in 2007 as a collaboration between Accenture, which contributed decades of in-house batch
architecture experience, and SpringSource (then Interface21), which contributed the Spring programming model.
Accenture donated its batch frameworks; the result was released as an open-source project and has been part of
the Spring portfolio ever since.

The JSR-352 (`jakarta.batch`, "Batch Applications for the Java Platform") specification was later standardised
with heavy influence from Spring Batch, and Dave Syer -- Spring Batch's original lead -- was on the expert
group. Spring Batch's own API remains the richer of the two; JSR-352 is *linked, not documented in depth*
here.

== Module layout

Spring Batch ships as a small set of artifacts:

[cols="1,3",options="header"]
|===
| Module | Contains

| `spring-batch-core`
| The domain and its runtime: `Job`, `Step`, `JobRepository`, `JobOperator`, the builders, listeners, flows,
  partitioning, and the metadata schema.

| `spring-batch-infrastructure`
| The reusable plumbing: the `ItemReader`/`ItemProcessor`/`ItemWriter` implementations, `RepeatOperations`,
  retry support, and the item-level utilities. Usable on its own, without the core runtime.

| `spring-batch-test`
| Test support: `@SpringBatchTest`, `JobOperatorTestUtils`, `JobRepositoryTestUtils`,
  `MetaDataInstanceFactory`, and the step/job scope test listeners.

| `spring-batch-integration`
| The bridge to Spring Integration: launching jobs from messages, async processing, remote chunking and remote
  partitioning.

| `spring-boot-starter-batch`
| The Spring Boot starter that pulls in `spring-batch-core` and triggers Boot's batch auto-configuration, without
  any persistence.

| `spring-boot-starter-batch-jdbc`
| `spring-boot-starter-batch` plus the JDBC job repository auto-configuration (`+spring.batch.jdbc.*+`).
|===

Under Spring Boot, one starter is normally all that is declared -- Boot's dependency management supplies the
version:

[source,xml]
----
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-batch-jdbc</artifactId>
</dependency>
<dependency>
    <groupId>com.h2database</groupId>
    <artifactId>h2</artifactId>
    <scope>runtime</scope>
</dependency>
<dependency>
    <groupId>org.springframework.batch</groupId>
    <artifactId>spring-batch-test</artifactId>
    <scope>test</scope>
</dependency>
----

In Spring Boot 4 the batch support is split in two starters. `spring-boot-starter-batch` brings `spring-batch-core`
and the batch auto-configuration but *no* persistence: the job repository is the resourceless one and no
`PlatformTransactionManager` bean exists, so the first job below does not start with it alone (the context fails
with "required a bean of type `PlatformTransactionManager` that could not be found"). `spring-boot-starter-batch-jdbc`
adds `spring-boot-batch-jdbc`, the JDBC job repository and the data source support, which is what a restartable
application wants; H2 stands in for the real database in the examples.

=== The release line

These pages track *Spring Batch 6.0.x*, which runs on *Spring Framework 7* and is the line shipped by *Spring
Boot 4.1.x*, with a *Java 17+* baseline. The headline changes relative to the previous generation are
summarised in https://docs.spring.io/spring-batch/reference/whatsnew.html[What's new in Spring Batch 6.0] and
noted on the individual pages where they matter:

* `JobBuilderFactory` and `StepBuilderFactory` are gone -- construct `new JobBuilder(name, jobRepository)` and
  `new StepBuilder(name, jobRepository)` directly;
* `BatchConfigurer` is gone -- extend `DefaultBatchConfiguration` instead
  (xref:backend/spring-batch/batch-infrastructure-configuration.adoc[Infrastructure configuration]);
* `+javax.*+` became `+jakarta.*+`;
* the infrastructure defaults are now *resourceless* -- no database is required to run a job;
* `JobRepository` absorbed `JobExplorer`, and `JobOperator` absorbed `JobLauncher`;
* retry is built on Spring Framework 7's core retry support rather than the separate Spring Retry library
  (xref:backend/spring-batch/fault-tolerance-skip-and-retry.adoc[Fault tolerance: skip & retry]);
* `CommandLineJobRunner` is deprecated for removal in favour of `CommandLineJobOperator`;
* the infrastructure types moved to `+org.springframework.batch.infrastructure.*+` -- `ItemReader`, `ItemProcessor`,
  `ItemWriter`, `ExecutionContext` and `RepeatStatus` are imported from there, which is the first thing to fix when
  porting 5.x code;
* `JobParametersInvalidException` was renamed `InvalidJobParametersException`
  (`org.springframework.batch.core.job.parameters`);
* JUnit 4 support was dropped -- tests are JUnit Jupiter only
  (xref:backend/spring-batch/testing.adoc[Testing batch jobs]).

== A first runnable job

The smallest useful job is a single *tasklet* step: one unit of work that runs inside one transaction and
reports that it is finished. The `JobRepository` is auto-configured by Spring Boot, so it can simply be
injected into the configuration class.

[source,java]
----
package com.example.batch;

import org.springframework.batch.core.job.Job;
import org.springframework.batch.core.job.builder.JobBuilder;
import org.springframework.batch.core.repository.JobRepository;
import org.springframework.batch.core.step.Step;
import org.springframework.batch.core.step.builder.StepBuilder;
import org.springframework.batch.infrastructure.repeat.RepeatStatus;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.transaction.PlatformTransactionManager;

@Configuration
public class HelloWorldJobConfiguration {

    @Bean
    public Step helloStep(JobRepository jobRepository, PlatformTransactionManager transactionManager) {
        return new StepBuilder("helloStep", jobRepository)
                .tasklet((contribution, chunkContext) -> {
                    System.out.println("Hello, Spring Batch!");
                    return RepeatStatus.FINISHED;
                }, transactionManager)
                .build();
    }

    @Bean
    public Job helloWorldJob(JobRepository jobRepository, Step helloStep) {
        return new JobBuilder("helloWorldJob", jobRepository)
                .start(helloStep)
                .build();
    }
}
----

Nothing else is required: no `@EnableBatchProcessing`. Under Spring Boot that annotation actively *disables*
the batch auto-configuration, which is why it is left off here -- see
xref:backend/spring-batch/batch-infrastructure-configuration.adoc[Infrastructure configuration].

=== Running it

Spring Boot registers a `JobLauncherApplicationRunner` that runs jobs at startup. Name the job to run and pass
parameters as `+--key=value+` arguments:

[source,yaml]
----
spring:
  batch:
    job:
      name: helloWorldJob
----

[source,properties]
----
# equivalent, and the switch that turns startup execution off entirely
spring.batch.job.name=helloWorldJob
spring.batch.job.enabled=true
----

[source,bash]
----
java -jar batch-app.jar --spring.batch.job.name=helloWorldJob run.date=2026-01-31
----

For an application that should *not* run a job on startup -- one that launches jobs on demand from an
endpoint, a scheduler, or a message -- set `spring.batch.job.enabled=false` and launch through the
`JobOperator`; both styles are covered in xref:backend/spring-batch/running-a-job.adoc[Running a job].

The Spring Boot side of this -- the starter, the auto-configured job repository and data source, the
`+spring.batch.*+` properties -- is documented at
https://docs.spring.io/spring-boot/reference/io/spring-batch.html[Batch Applications] and, in this site, on the
shorter xref:backend/springboot/spring-batch.adoc[Spring Batch (SpringBoot Reference)] page.

== The running example of this section

Every page of this section uses the same small program, so that the metadata tables, logs and numbers quoted on
one page can be compared with the next: the *end-of-day trade load*. A file of trades arrives each business day;
the job stages it, loads it into a `TRADE` table and reports what it loaded.

[source,text]
----
1,US0378331005,100,189.25
2,US5949181045,250,412.10
3,US0231351067,75,178.90
4,US88160R1014,40,248.50
5,XX0000000001,10,1.00
6,US30303M1027,300,501.75
7,US67066G1040,125,131.20
8,US4592001014,60,169.40
9,US0079031078,500,125.05
10,US7134481081,210,170.35
----

Ten lines, one of which (`XX0000000001`, a test ISIN) the processor will filter out. The two value types are records, and
the job has three steps:

[source,java]
----
public record TradeCsv(long id, String isin, int quantity, BigDecimal price) {}

public record Trade(long id, String isin, int quantity, BigDecimal price, LocalDate runDate) {}
----

[mermaid]
....
flowchart LR
    Start(["run.date = 2026-01-30"]) --> Stage["stageStep<br/>tasklet: count the rows"]
    Stage --> Load["loadStep<br/>chunk of 3: read, process, write"]
    Load --> Report["reportStep<br/>tasklet: compare staged and loaded"]
    Report --> End(["COMPLETED"])
....

The configuration is built up page by page; the finished job is assembled in
xref:backend/spring-batch/configuring-a-job.adoc[Configuring a job] and the chunk step in
xref:backend/spring-batch/chunk-oriented-processing.adoc[Chunk-oriented processing]. Run once against H2, it prints
(timestamps, logger names and the details of the parameter list trimmed):

[source,text]
----
starting endOfDayJob execution 1 with {JobParameter{name='run.date', value=2026-01-30, ...},JobParameter{name='input.file', ...}}
staged 10 rows from data/in/trades-2026-01-30.csv
committed chunk 1: read=3 write=3
committed chunk 2: read=6 write=5
committed chunk 3: read=9 write=8
committed chunk 4: read=10 write=9
staged=10 loaded=9 for 2026-01-30
endOfDayJob finished as COMPLETED in 86ms
----

Ten rows read, nine written: `write` falls one behind at the second chunk because trade 5 was filtered. The same
numbers are in the `BATCH_STEP_EXECUTION` row of the `loadStep` (`READ_COUNT` 10, `FILTER_COUNT` 1, `WRITE_COUNT`
9, `COMMIT_COUNT` 4), which is how
xref:backend/spring-batch/steps-executions-and-context.adoc[Steps, executions & the ExecutionContext] reads them back.

== What happens when the job runs

The first job above looks like one method call, but between the `main` method and the `Hello, Spring Batch!` line
the framework does the bookkeeping that justifies using it:

[mermaid]
....
sequenceDiagram
    participant Boot as SpringApplication
    participant Runner as JobLauncherApplicationRunner
    participant Op as JobOperator
    participant Repo as JobRepository
    participant Job as Job
    participant Step as TaskletStep
    Boot->>Runner: context refreshed
    Runner->>Op: start(helloWorldJob, parameters)
    Op->>Repo: create or find JobInstance, create JobExecution
    Op->>Job: execute(jobExecution)
    Job->>Repo: update status STARTED
    Job->>Step: execute(stepExecution)
    Step->>Repo: create StepExecution
    Step->>Step: Tasklet.execute() in one transaction
    Step->>Repo: update counters and ExecutionContext
    Job->>Repo: update status COMPLETED
    Op-->>Runner: JobExecution
....

With the JDBC starter and a command line of `run.date=2026-01-30,java.time.LocalDate chunk.size=500,java.lang.Long
output.dir=/tmp/out`, the run logs the parameters it converted from the arguments (the type suffix pins the Java
type), runs the step and reports the outcome:

[source,text]
----
Running default command line with: [run.date=2026-01-30,java.time.LocalDate, chunk.size=500,java.lang.Long, output.dir=/tmp/out]
Job: [SimpleJob: [name=helloWorldJob]] launched with the following parameters: [{JobParameter{name='output.dir', value=/tmp/out, type=class java.lang.String, identifying=true}, ...}]
Executing step: [helloStep]
Hello, Spring Batch!
Step: [helloStep] executed in 13ms
Job: [SimpleJob: [name=helloWorldJob]] completed with the following parameters: [...] and the following status: [COMPLETED]
----

A parameter without a type suffix is a `String` and, like every command-line parameter, *identifying* unless a third
suffix says otherwise (`output.dir=/tmp/out,java.lang.String,false`). Parameters and identity are the subject of
xref:backend/spring-batch/jobs-instances-and-parameters.adoc[Jobs, instances & parameters].

== With and without a database

Whether anything is remembered between runs depends only on the job repository behind the starter. Running the same
application twice with the same parameters shows the difference:

[cols="2,2,3",options="header"]
|===
| Setup | Process exit codes | Why

| `spring-boot-starter-batch` only, with a `ResourcelessTransactionManager` bean
| `0`, then `0` again
| The resourceless repository persists nothing: the second process sees no history, so the "completed" instance is
  simply run again.

| `spring-boot-starter-batch-jdbc` with a file-based H2 database, a job that fails on its first attempt
| `5` (job `FAILED`), `0` (the second launch restarted the failed instance and completed it), `1` (a third launch:
  `JobInstanceAlreadyCompleteException`)
| The metadata tables remember the instance, so the failed run is resumed and the completed one refused.
|===

The exit codes come from running the application with
`+System.exit(SpringApplication.exit(SpringApplication.run(App.class, args)))+`, as in the
xref:backend/spring-batch/running-a-job.adoc[Running a job] page. Everything else about the production behaviour of
batch -- restart, history, audit -- is the JDBC column of that table; the resourceless setup is for demos and tests
(see xref:backend/spring-batch/batch-infrastructure-configuration.adoc[Infrastructure configuration]).
