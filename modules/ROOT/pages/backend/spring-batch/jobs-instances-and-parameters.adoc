:keywords: Job, JobInstance, JobExecution, JobParameters, JobParameter, identifying parameters, non-identifying parameters, JobParametersBuilder, JobParametersIncrementer, RunIdIncrementer, BatchStatus, ExitStatus, restart, rerun, job lifecycle, state machine, JobRepository

Four types carry the whole job-side vocabulary of Spring Batch: `Job`, `JobInstance`, `JobParameters` and
`JobExecution`. Getting the relationship between them right is what makes restart behave the way you expect.

== Job

A `Job` is a container for an ordered sequence of ``Step``s plus the configuration that applies to the run as a
whole -- restartability, a parameter validator, an incrementer, and job-level listeners. It is a *definition*,
a singleton bean, and it holds no runtime state:

[source,java]
----
@Bean
public Job endOfDayJob(JobRepository jobRepository, Step loadStep, Step reportStep) {
    return new JobBuilder("endOfDayJob", jobRepository)
            .start(loadStep)
            .next(reportStep)
            .build();
}
----

The job's *name* is its identity in the `JobRepository`; renaming a job starts its history over.

== JobInstance: a job plus its identifying parameters

A `JobInstance` is a *logical run* of a job: the combination of the job name and its **identifying**
`JobParameters`. "The end-of-day job for 2026-01-31" is one `JobInstance`. Running it again on the same date
resumes *that* instance; running it with `2026-02-01` creates a new one.

This is the rule that surprises newcomers: Spring Batch refuses to start a `JobInstance` that has already
*completed*. A completed instance cannot be rerun -- only a failed or stopped one can be restarted. If the
same logical work must genuinely run twice, it needs different identifying parameters (which is exactly what a
`JobParametersIncrementer` provides, below).

== JobParameters

`JobParameters` is a typed map passed in at launch. Each `JobParameter` carries a value, its Java type, and an
*identifying* flag:

[source,java]
----
JobParameters parameters = new JobParametersBuilder()
        .addLocalDate("run.date", LocalDate.of(2026, 1, 31))   // identifying by default
        .addLong("run.id", 1L)                                  // identifying by default
        .addString("output.dir", "/tmp/out", false)             // false => NOT identifying
        .toJobParameters();
----

* *Typed*: `addString`, `addLong`, `addDouble`, `addDate`, `addLocalDate`, `addLocalDateTime`, and the generic
  `addJobParameter(key, value, Class<T>, identifying)`. Types are preserved in the metadata tables, so a
  parameter read back later is still a `LocalDate`, not a string.
* *Identifying* (the default) means the parameter takes part in deciding which `JobInstance` this is. Change
  it and you get a new instance -- "start fresh".
* *Non-identifying* parameters are recorded and available to the job but do not affect instance identity.
  Output directories, verbosity flags and retry limits belong here, so that changing one on a restart does not
  accidentally create a new instance.

That distinction is precisely the difference between the two things an operator might mean by "run it again":

[cols="1,2",options="header"]
|===
| Intent | What to do

| *Resume where you left off* -- the previous run failed halfway
| Launch with the **same identifying parameters**. Spring Batch finds the existing `JobInstance`, creates a new
  `JobExecution` for it, and steps that already completed are skipped (see
  xref:backend/spring-batch/stopping-restart-and-recovery.adoc[Stopping, restart & recovery]).

| *Start fresh* -- process a new period, or reprocess from scratch
| Launch with **different identifying parameters** (a new business date, or a new `run.id` from an
  incrementer). A brand-new `JobInstance` is created with an empty `ExecutionContext`.
|===

Parameters are read inside a step through late binding, which is covered in
xref:backend/spring-batch/step-flow-and-listeners.adoc[Step flow & listeners], and validated as described in
xref:backend/spring-batch/configuring-a-job.adoc[Configuring a job].

== JobExecution

A `JobExecution` is one *attempt* at running a `JobInstance`. One instance may have many executions -- one per
restart. It records:

* `BatchStatus` -- the framework's own enum for where the execution stands;
* `ExitStatus` -- the outcome as a code plus description, used by flow transitions and by callers such as a
  shell script;
* `startTime`, `endTime`, `createTime`, `lastUpdated`;
* `failureExceptions` -- the throwables that ended it;
* the job-level `ExecutionContext`
  (xref:backend/spring-batch/steps-executions-and-context.adoc[Steps, executions & the ExecutionContext]);
* the ``StepExecution``s it produced.

=== BatchStatus lifecycle

[mermaid]
....
stateDiagram-v2
    [*] --> STARTING
    STARTING --> STARTED
    STARTED --> COMPLETED : all steps completed
    STARTED --> FAILED : unhandled exception
    STARTED --> STOPPING : stop() requested
    STOPPING --> STOPPED
    STOPPED --> STARTING : restart
    FAILED --> STARTING : restart
    FAILED --> ABANDONED : abandon()
    STOPPED --> ABANDONED : abandon()
    COMPLETED --> [*]
    ABANDONED --> [*]
....

`UNKNOWN` is the remaining value: an execution whose fate could not be determined, typically after a process
crash. Recovering those is what the 6.0 `JobOperator.recover()` is for -- see
xref:backend/spring-batch/stopping-restart-and-recovery.adoc[Stopping, restart & recovery].

=== BatchStatus vs. ExitStatus

`BatchStatus` is a fixed enum owned by the framework. `ExitStatus` is an open, extensible pair of an exit
*code* (a `String`) and a description; a step or a listener may set any code it likes, and flow transitions
match on it:

[source,java]
----
@Bean
public StepExecutionListener classifyingListener() {
    return new StepExecutionListener() {
        @Override
        public ExitStatus afterStep(StepExecution stepExecution) {
            if (stepExecution.getWriteCount() == 0) {
                return new ExitStatus("NO_DATA", "the input contained no rows to write");
            }
            return stepExecution.getExitStatus();   // leave COMPLETED as-is
        }
    };
}
----

`.on("NO_DATA")` in a job flow then routes on that code, as shown in
xref:backend/spring-batch/step-flow-and-listeners.adoc[Step flow & listeners].

== Two executions of one instance

The following job is deliberately fragile: it fails the first time and succeeds the second, so the same
`JobInstance` accumulates two ``JobExecution``s.

[source,java]
----
@Configuration
public class RestartDemoConfiguration {

    @Bean
    public Step flakyStep(JobRepository jobRepository, PlatformTransactionManager tx) {
        return new StepBuilder("flakyStep", jobRepository)
                .tasklet((contribution, chunkContext) -> {
                    Path marker = Path.of("target", "already-ran");
                    if (!Files.exists(marker)) {
                        Files.createDirectories(marker.getParent());
                        Files.createFile(marker);
                        throw new IllegalStateException("first attempt always fails");
                    }
                    return RepeatStatus.FINISHED;
                }, tx)
                .build();
    }

    @Bean
    public Job restartDemoJob(JobRepository jobRepository, Step flakyStep) {
        return new JobBuilder("restartDemoJob", jobRepository)
                .validator(new DefaultJobParametersValidator(
                        new String[] { "run.date" },      // required
                        new String[] { "output.dir" }))   // optional
                .start(flakyStep)
                .build();
    }
}
----

Launching it twice with the *same* identifying parameters produces two executions of one instance:

[source,java]
----
JobParameters parameters = new JobParametersBuilder()
        .addLocalDate("run.date", LocalDate.of(2026, 1, 31))
        .toJobParameters();

JobExecution first  = jobOperator.start(restartDemoJob, parameters);   // FAILED
JobExecution second = jobOperator.start(restartDemoJob, parameters);   // COMPLETED

assert first.getJobInstance().equals(second.getJobInstance());
----

=== Forcing a new instance with an incrementer

When a job should be runnable repeatedly with otherwise identical parameters -- a nightly job whose only
distinguishing feature is "another run" -- attach a `JobParametersIncrementer`. `RunIdIncrementer` adds (or
bumps) a `run.id` parameter, so every launch through `startNextInstance` gets a fresh `JobInstance`:

[source,java]
----
@Bean
public Job nightlyJob(JobRepository jobRepository, Step flakyStep) {
    return new JobBuilder("nightlyJob", jobRepository)
            .incrementer(new RunIdIncrementer())
            .start(flakyStep)
            .build();
}
----

[source,java]
----
// each call creates the NEXT JobInstance rather than restarting the last one
jobOperator.startNextInstance(nightlyJob);   // the Job bean, not its name
----

Custom incrementers -- for example one that advances a business date -- are shown in
xref:backend/spring-batch/configuring-a-job.adoc[Configuring a job]. Note that in 6.0 a plain `start(job, parameters)`
on a job that *has* an incrementer also starts the next instance and discards the parameters passed in.

== Instance identity in the metadata

A `JobInstance` is stored as one row of `BATCH_JOB_INSTANCE`, and its identity is the pair `JOB_NAME` plus `JOB_KEY`,
a 32-character hash of the *identifying* parameters only. Because the hash ignores the job name, the same parameters
give the same key for different jobs, and a non-identifying parameter never changes it. The runs of this section
produced:

[cols="3,3,2",options="header"]
|===
| Job and parameters | `JOB_KEY` | Identifying?

| `endOfDayJob`, `run.date=2026-01-30` and `input.file=data/in/trades-2026-01-30.csv` (identifying)
| `d54c13dc69c1f13ece5a796ee67ee5af`
| both

| `endOfDayJob`, the same two, `input.file` declared non-identifying
| `df0352cc1b533043a1cc787fb8d0052a`
| `run.date` only

| `restartDemoJob`, `run.date=2026-01-30`
| `df0352cc1b533043a1cc787fb8d0052a`
| `run.date` only

| `restartDemoJob`, `run.date=2026-01-31`
| `7ae102b4d894243a2d1c7037f80d99a4`
| `run.date` only
|===

The second and third rows show the rule at work: dropping `input.file` from the identity gave a different key from
the first row, and the key then matched another job launched with the same single parameter. The parameters
themselves are stored per execution in `BATCH_JOB_EXECUTION_PARAMS`, with their type as a class name and a `Y`/`N`
identifying flag:

[source,text]
----
JOB_EXECUTION_ID PARAMETER_NAME PARAMETER_TYPE      PARAMETER_VALUE               IDENTIFYING
1                input.file     java.lang.String    data/in/trades-2026-01-30.csv N
1                run.date       java.time.LocalDate 2026-01-30                    Y
----

Which row of `BATCH_JOB_INSTANCE` a launch lands on, and whether it is allowed to run at all, follows one decision:

[mermaid]
....
flowchart TD
    L["start(job, parameters)"] --> I{"Instance for the job name<br/>and the identifying parameters?"}
    I -->|"no"| N["create the instance<br/>and its first execution"]
    I -->|"yes"| E{"Status of its last execution"}
    E -->|"COMPLETED or ABANDONED"| X1["JobInstanceAlreadyCompleteException"]
    E -->|"STARTED"| X2["JobExecutionAlreadyRunningException"]
    E -->|"FAILED or STOPPED"| R{"Job restartable?"}
    R -->|"yes"| N2["new execution of the same instance"]
    R -->|"no"| X3["JobRestartException"]
....

Every box of the diagram was reached in a run: a repeated completed launch and a launch after `abandon()` both threw
`JobInstanceAlreadyCompleteException`; an asynchronous launch repeated while it ran threw
`JobExecutionAlreadyRunningException`; a failed instance of a `.preventRestart()` job threw `JobRestartException`; and
a failed instance of an ordinary job was restarted, as the next section shows.

== Worked example: one instance, two executions

The `restartDemoJob` above fails on its first launch and succeeds on the second. After `start` was called twice with
`run.date=2026-01-31`, the repository held:

[source,text]
----
-- BATCH_JOB_INSTANCE
JOB_INSTANCE_ID JOB_NAME       JOB_KEY
1               restartDemoJob 7ae102b4d894243a2d1c7037f80d99a4
-- BATCH_JOB_EXECUTION
JOB_EXECUTION_ID JOB_INSTANCE_ID STATUS    EXIT_CODE EXIT_MESSAGE
1                1               FAILED    FAILED    java.lang.IllegalStateException: first a...
2                1               COMPLETED COMPLETED
-- BATCH_STEP_EXECUTION
STEP_EXECUTION_ID JOB_EXECUTION_ID STEP_NAME STATUS    READ_COUNT WRITE_COUNT COMMIT_COUNT ROLLBACK_COUNT
1                 1                flakyStep FAILED    0          0           0            1
2                 2                flakyStep COMPLETED 0          0           1            0
----

One instance, two executions, one step execution per attempt. The failed step shows `ROLLBACK_COUNT` 1 and
`COMMIT_COUNT` 0 -- its single transaction was rolled back -- and the successful one `COMMIT_COUNT` 1. The
assertion `first.getJobInstance().equals(second.getJobInstance())` of the snippet above holds for exactly that
reason: both executions point at `JOB_INSTANCE_ID` 1. The same pattern with a chunk step, where the restart does not
begin from the top, is walked through in
xref:backend/spring-batch/stopping-restart-and-recovery.adoc[Stopping, restart & recovery].

== `BatchStatus` and `ExitStatus` in practice

The two statuses of an execution usually agree, but the cases in which they do not are the ones that matter to a
caller:

[cols="3,2,2,3",options="header"]
|===
| Situation | `BatchStatus` | `ExitStatus` code | Observed consequence

| a step throws and nothing handles it
| `FAILED`
| `FAILED`
| the instance can be restarted

| `JobOperator.stop()` or `setTerminateOnly()`
| `STOPPED`
| `STOPPED`
| the instance can be restarted; the failure list holds `JobInterruptedException`

| `JobOperator.abandon()` on a failed execution
| `ABANDONED`
| `FAILED`
| the instance is then treated as complete: `start` and `restart` both refuse it

| `JobOperator.recover()` on a stranded execution
| `FAILED`
| `UNKNOWN`
| the instance can be restarted

| the `NoWorkFoundStepExecutionListener` runs on an empty input
| `COMPLETED`
| `FAILED`
| the step and job are *complete* (not restartable) although the outcome says failed

| a listener returns a custom code such as `NO_DATA` and a transition handles it
| `COMPLETED`
| `COMPLETED`
| the flow followed the matching transition (a `+.on("NO_DATA")+` run went to the alert step)
|===

The fifth row deserves emphasis: a failed *exit* status is not a failed *batch* status. A flow transition, a shell
exit code or a monitoring probe sees `FAILED`; the repository, and therefore restart, sees a completed step. The
sixth row was run with the `classifyingListener` shown above on an empty input file.
