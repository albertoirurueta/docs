= Repeat & retry internals
:description: The lower-level abstractions the chunk loop is built on -- RepeatOperations and RepeatTemplate with a CompletionPolicy and an ExceptionHandler, and RetryOperations and RetryTemplate on Spring Framework 7's retry support with RetryPolicy, BackOffPolicy and RetryListener -- plus stateless versus stateful retry and how a fault-tolerant step's skip and retry settings map onto them.
:keywords: RepeatOperations, RepeatTemplate, RepeatCallback, RepeatStatus, RepeatContext, CompletionPolicy, SimpleCompletionPolicy, TimeoutTerminationPolicy, CompositeCompletionPolicy, ExceptionHandler, SimpleLimitExceptionHandler, RetryOperations, RetryTemplate, RetryPolicy, MaxAttemptsRetryPolicy, BackOffPolicy, ExponentialBackOffPolicy, RetryListener, stateless retry, stateful retry, Spring Framework 7 retry

include::partial$ai-disclaimer.adoc[]

The chunk loop and the fault-tolerance options are conveniences over two general-purpose abstractions:
`RepeatOperations`, which runs something repeatedly until a policy says stop, and `RetryOperations`, which
runs something again after a failure. Both are usable on their own.

== `RepeatOperations`

[source,java]
----
public interface RepeatOperations {
    RepeatStatus iterate(RepeatCallback callback) throws RepeatException;
}
----

`RepeatTemplate` is the implementation. It calls the callback in a loop, passing a `RepeatContext`, and stops
when the callback returns `RepeatStatus.FINISHED` or the `CompletionPolicy` says the batch is complete:

[source,java]
----
RepeatTemplate template = new RepeatTemplate();
template.setCompletionPolicy(new SimpleCompletionPolicy(100));   // at most 100 iterations

SimpleLimitExceptionHandler handler = new SimpleLimitExceptionHandler(5);
handler.setUseParent(true);        // count across iterations, not per iteration
handler.afterPropertiesSet();      // builds the thresholds; the container does this for a bean
template.setExceptionHandler(handler);   // tolerate 5 failures, rethrow the sixth

template.iterate(context -> {
    Trade trade = tradeQueue.poll();
    if (trade == null) {
        return RepeatStatus.FINISHED;
    }
    tradeService.settle(trade);
    return RepeatStatus.CONTINUABLE;
});
----

With a limit of 2 and a callback that fails on every second call, this template rethrows the third failure and
not the first (the run in the worked example below prints `rethrown after iteration 6`). Two details matter
outside a container: `SimpleLimitExceptionHandler` builds its thresholds in `afterPropertiesSet()`, so a handler
created with `new` and never initialised rethrows the very first exception; and by default it counts per
iteration context, so a limit never trips across iterations unless `setUseParent(true)` is set.

This is exactly the shape of the chunk loop in
xref:backend/spring-batch/chunk-oriented-processing.adoc[Chunk-oriented processing]: "read and process until
the completion policy says the chunk is full".

[mermaid]
....
flowchart TD
    A["RepeatTemplate.iterate(callback)"] --> B["policy.update(context)"]
    B --> C["callback.doInIteration(context)"]
    C --> D{"threw?"}
    D -- yes --> E["ExceptionHandler.handleException"]
    E -- rethrows --> X["leave the loop, throw"]
    E -- swallows --> F
    D -- no --> F{"FINISHED, or policy.isComplete(context, status), or completeOnly?"}
    F -- no --> B
    F -- yes --> G["return the RepeatStatus"]
....

Note the order inside the loop: `CompletionPolicy.update(context)` runs *before* the callback, and
`isComplete(context, status)` runs *after* it. A policy that needs to look at the item it just consumed must
therefore read it in `isComplete`, not in `update`.

=== `CompletionPolicy`

[cols="1,3",options="header"]
|===
| Policy | Stops the batch when

| `SimpleCompletionPolicy` | A fixed number of iterations has run. This is what an integer chunk size creates.
| `TimeoutTerminationPolicy` | A wall-clock budget has elapsed -- the last iteration is allowed to finish.
| `CountingCompletionPolicy` | A counter derived from the result (bytes, records, cost) reaches a limit. It is an abstract base class; a subclass supplies how much each iteration counts.
| `CompositeCompletionPolicy` | Any of several policies is satisfied (set with `+setPolicies(...)+`); a loop with `SimpleCompletionPolicy(1000)` and a 30 ms timeout ends at the timeout.
|===

A custom policy is a small class, and it is how "commit whenever the business key changes" is expressed. Because
`update(context)` runs before each iteration (see the flow above), the policy decides in `isComplete(context,
status)`, after the iteration, by peeking at the key of the *next* item:

[source,java]
----
public class KeyBoundaryCompletionPolicy extends CompletionPolicySupport {

    private final Supplier<String> nextKey;     // key of the next item, or null when the input is exhausted

    public KeyBoundaryCompletionPolicy(Supplier<String> nextKey) {
        this.nextKey = nextKey;
    }

    @Override
    public boolean isComplete(RepeatContext context, RepeatStatus status) {
        if (status == RepeatStatus.FINISHED) {
            return true;
        }
        // the callback stored the key of the item it just consumed
        return !Objects.equals(context.getAttribute("isin"), nextKey.get());
    }
}
----

Fed with six trades whose instruments are `A, A, A, B, B, C`, a loop that gives each chunk a fresh
`+iterate(...)+` call closes the chunks at `[1, 2, 3]`, `[4, 5]` and `[6]` -- one chunk per instrument. A policy
that looked at the key in `+update(...)+` would lag one item behind and put the first `B` into the `A` chunk.
In a real step the "peek" is a `SingleItemPeekableItemReader`.

=== `ExceptionHandler`

The `ExceptionHandler` decides whether an exception thrown inside an iteration ends the loop.
`SimpleLimitExceptionHandler` rethrows only after the limit has been exceeded, and
`LogOrRethrowExceptionHandler` classifies exceptions into "log and continue" and "rethrow". In a chunk step the
handler sits on the *step-level* `RepeatTemplate` (see below); the skip limit of a fault-tolerant step is a
different mechanism, `LimitCheckingItemSkipPolicy`, not an `ExceptionHandler`.

`TaskExecutorRepeatTemplate` runs iterations concurrently (default throttle limit 4) and is what a classic
`+.taskExecutor(...)+` step uses -- the basis of the multi-threaded step in
xref:backend/spring-batch/scaling-and-parallel-processing.adoc[Scaling & parallel processing]. It is deprecated
and scheduled for removal in Spring Batch 7.

== `RetryOperations`

Retry is the other half, and there are *two* libraries. **Spring Framework 7 ships its own core retry support**
-- the types live in `org.springframework.core.retry`, and it is what `ChunkOrientedStepBuilder` uses. The classic
`.faultTolerant()` builder of `StepBuilder` is still on the Spring Retry library (`org.springframework.retry`,
see xref:backend/spring-batch/fault-tolerance-skip-and-retry.adoc[Fault tolerance: skip & retry]); both jars are on
the classpath of a Spring Batch 6.0 application, and their types are not interchangeable. The code below uses
the Framework 7 types:

[source,java]
----
RetryTemplate retryTemplate = new RetryTemplate(RetryPolicy.builder()
        .maxRetries(3)                       // retries after the first attempt: four attempts in all
        .includes(TransientDataAccessException.class, RemoteAccessException.class)
        .excludes(DataIntegrityViolationException.class)
        .delay(Duration.ofMillis(200))
        .multiplier(2.0)
        .maxDelay(Duration.ofSeconds(5))
        .jitter(Duration.ofMillis(50))
        .build());

// unchecked variant: rethrows the last original exception once the policy is exhausted
Trade settled = retryTemplate.invoke(() -> settlementClient.settle(trade));

// checked variant: wraps the exhaustion in a RetryException
Trade checked = retryTemplate.execute(() -> settlementClient.settle(trade));
----

The pieces:

* *`RetryPolicy`* -- how many retries (`maxRetries`, not an attempt count), which exceptions qualify
  (`includes`/`excludes`/`predicate`), a `timeout`, and the delay between attempts. The builder is a front end to
  a `BackOff`.
* *`BackOff`* (`org.springframework.util.backoff`) -- `FixedBackOff` or `ExponentialBackOff`, derived from
  `delay`, `multiplier`, `maxDelay` and `jitter`. This is the Framework 7 name; `BackOffPolicy` belongs to Spring
  Retry and is what the classic `+.backOffPolicy(...)+` takes. Retrying a contended resource without back-off
  usually reproduces the same failure; jitter additionally prevents a thundering herd when many workers fail
  together.
* *`RetryListener`* -- callbacks such as `beforeRetry`, `onRetryFailure`, `onRetrySuccess` and
  `onRetryPolicyExhaustion`; the natural place for logging and metrics
  (xref:backend/spring-batch/observability.adoc[Observability]).
* *No recovery callback.* Framework 7 has no `RecoveryCallback`: when the policy is exhausted, `+execute(...)+`
  throws a checked `RetryException` (it carries `getRetryCount()`, `getExceptions()` and the last exception as its
  cause), and the caller decides what the fallback is. `invoke(Supplier)` and `invoke(Runnable)` are the
  unchecked variants and rethrow the *last original exception* instead.

=== Stateless vs. stateful retry

[cols="1,3",options="header"]
|===
| | Behaviour

| *Stateless*
| All attempts happen inside one call, in a loop, on the same thread and inside the *same* transaction. Right
  for a failure that does not poison the transaction -- a flaky remote call, a read timeout. This is the only
  kind the Framework 7 `RetryTemplate` offers.

| *Stateful*
| The failure aborts the transaction; the retry happens on a *subsequent* call, with the attempt count keyed
  by an item identity and stored in a retry context. Right for a database failure that marks the transaction
  rollback-only, such as a deadlock -- there is no point retrying inside a transaction that can no longer
  commit. Only the Spring Retry template supports it (`RetryState`).
|===

The classic fault-tolerant chunk step is the stateful case: because the chunk's transaction has already rolled
back, the framework replays the chunk in a *new* transaction and keys the retry state by item. The 6.0
`ChunkOrientedStepBuilder` instead retries *inside* the chunk transaction -- the worked example below shows the
observable difference.

== How a step maps onto these

[cols="1,2",options="header"]
|===
| Step-level setting | Underlying mechanism

| `.chunk(500, tx)` | Two nested `RepeatTemplate` instances: a *step* template whose every iteration is one transactional chunk, and a *chunk* template with `SimpleCompletionPolicy(500)` whose every iteration reads and processes one item.
| `.chunk(policy, tx)` | The same, with the supplied `CompletionPolicy` on the inner template.
| `+.exceptionHandler(...)+` | The `ExceptionHandler` of the step-level template; the default rethrows everything.
| `+.taskExecutor(...)+` | A `TaskExecutorRepeatTemplate` at the step level (deprecated for removal in 7).
| `.faultTolerant().retry(X.class).retryLimit(3)` | A Spring Retry `SimpleRetryPolicy` with a *maximum of three attempts*, inside a `BatchRetryTemplate` that retries statefully around the write.
| `+.faultTolerant().backOffPolicy(...)+` | The Spring Retry `BackOffPolicy` handed to that template.
| `.faultTolerant().skip(X.class).skipLimit(50)` | A `LimitCheckingItemSkipPolicy`: 50 skips of a skippable type are tolerated, the next failure fails the step.
| `.faultTolerant().noRollback(X.class)` | A rollback classifier consulted before the transaction is marked rollback-only.
| `ChunkOrientedStepBuilder.faultTolerant().retry(X.class).retryLimit(3)` | A Framework 7 `RetryPolicy` with *three retries* (four attempts), applied inside the chunk transaction.
|===

Note the two meanings of `retryLimit(3)`: three attempts on the classic builder, three retries on the 6.0
builder.

Nearly all batch code should stay at the step level -- `+.faultTolerant().skip(...).retry(...)+` as described in
xref:backend/spring-batch/fault-tolerance-skip-and-retry.adoc[Fault tolerance: skip & retry]. Reach for
`RetryTemplate` or `RepeatTemplate` directly only inside a tasklet, a custom reader or writer, or a service
that is called from batch and online code alike.

== Worked example: observing the loops

The settlement running example of this section feeds every experiment below. The runs use Spring Batch 6.0.6 on
Spring Boot 4.1.2 (Spring Framework 7.0.10, Spring Retry 2.0.13), Java 17.

=== A repeat loop, three completion policies

A `RepeatTemplate` over a queue of 25 trades, with `SimpleCompletionPolicy(10)`, stops after ten calls and leaves
fifteen trades behind, returning `CONTINUABLE` -- the policy ended the batch, not the input. A
`TimeoutTerminationPolicy(50)` around a callback that sleeps 20 ms runs three iterations (the policy is checked
after an iteration, so the budget is exceeded by the last one). The composite of a 1000-iteration count and a
30 ms timeout ends with whichever fires first:

[source,text]
----
simple(10): status=CONTINUABLE calls=10 left=15
limit(2): rethrown after iteration 6 -> IllegalStateException: bad trade #6
timeout(50ms): iterations=3
composite(1000 | 30ms): iterations=3
keyed chunk 1: ids=[1, 2, 3]
keyed chunk 2: ids=[4, 5]
keyed chunk 3: ids=[6]
----

The `limit(2)` line is the handler from the first example, failing on iterations 2, 4 and 6: the third failure is
the one that is rethrown. The three `keyed` lines are the `KeyBoundaryCompletionPolicy` above.

=== A retry loop, with the back-off visible

The policy `maxRetries(3)`, `delay(100ms)`, `multiplier(2.0)`, `jitter(0)` attached to a flaky settlement call that
succeeds on its third attempt, with a `RetryListener` that prints what it sees:

[source,text]
----
  beforeRetry after 107 ms
  onRetryFailure: settlement gateway busy #2
  beforeRetry after 206 ms
  onRetrySuccess: settled
recovered result=settled attempts=3
----

and the same policy against a call that never succeeds:

[source,text]
----
  beforeRetry after 105 ms
  onRetryFailure: down #2
  beforeRetry after 203 ms
  onRetryFailure: down #3
  beforeRetry after 400 ms
  onRetryFailure: down #4
  onRetryPolicyExhaustion after 3 retries
exhausted: retryCount=3 exceptions=4 cause=down #4
invoke exhausted: down #4
----

The delays are 100, 200 and 400 ms: the exponential multiplier at work, plus a few milliseconds of scheduling.
`getExceptions()` holds all four failures, one more than the retry count. Two behaviours worth knowing: an
exception matched by `+excludes(...)+` is *not* retried (one attempt), but it still comes out of `+execute(...)+` wrapped
in a `RetryException` whose `getRetryCount()` is 0; and `+invoke(...)+` unwraps and rethrows the original
exception type, which is why it is the convenient variant for code that does not want a checked exception.

[mermaid]
....

    participant C as Caller
    participant T as RetryTemplate
    participant S as Settlement gateway
    C->>T: execute(settle trade)
    T->>S: attempt 1
    S-->>T: IllegalStateException
    Note over T: back off 100 ms
    T->>S: attempt 2
    S-->>T: IllegalStateException
    Note over T: back off 200 ms
    T->>S: attempt 3
    S-->>T: settled
    T-->>C: result (onRetrySuccess)
....

=== Stateful retry, across calls

The Spring Retry template makes the difference between the two kinds concrete. With a `SimpleRetryPolicy` of three
attempts and a `DefaultRetryState` keyed by the trade, each call performs *one* attempt and lets the exception
escape -- in a step that exception is what rolls the transaction back -- and the state is picked up again on the next
call. The fourth call goes to the recovery callback:

[source,text]
----
stateful call 1: exception propagates (transaction rolls back), callbacks=1
stateful call 2: exception propagates (transaction rolls back), callbacks=2
stateful call 3: exception propagates (transaction rolls back), callbacks=3
stateful call 4: recovered after 3 attempts
----

[mermaid]
....
sequenceDiagram
    participant L as Chunk loop
    participant R as Retry template with RetryState
    participant W as Writer
    L->>R: execute(callback, recovery, state key trade-42)
    R->>W: attempt 1
    W-->>R: deadlock
    R-->>L: rethrow, transaction rolls back
    L->>R: execute again (new transaction)
    R->>W: attempt 2
    W-->>R: deadlock
    R-->>L: rethrow, transaction rolls back
    L->>R: execute again (new transaction)
    R->>W: attempt 3
    W-->>R: deadlock
    R-->>L: rethrow, transaction rolls back
    L->>R: execute again (new transaction)
    R-->>L: recovery callback result
....

=== The same flaky writer in both step builders

A step settles the trades in chunks of 50, and the writer throws a transient `deadlock` error the first N times
it is given the second chunk (trade ids 51 to 100), configured with `+retry(...)+` and `retryLimit(3)` on each builder:

[cols="2,1,1,2,1,1",options="header"]
|===
| Builder | Failures injected | Outcome | Writer calls | Commits | Rollbacks

| Classic `.faultTolerant()` | 2 | `COMPLETED` | 22 | 21 | 2
| 6.0 `ChunkOrientedStepBuilder` | 2 | `COMPLETED` | 22 | 20 | 0
| Classic `.faultTolerant()` | 3 | `FAILED` | 4 | 1 | 4
| 6.0 `ChunkOrientedStepBuilder` | 3 | `COMPLETED` | 23 | 20 | 0
|===

With two failures both builders succeed on the third attempt, but the classic step rolled back twice (and counts 21
commits to the other step's 20), while the 6.0 step retried inside the open chunk transaction with no rollback. With
three failures the classic builder ran out of its three *attempts* and failed the step with
`ExhaustedRetryException: Retry exhausted after last attempt in recovery path, but exception is not skippable`
(the message points at the missing `+skip(...)+` for that exception type), while the 6.0 builder still had a fourth
attempt (three *retries*) and completed. Both runs write all 1000 rows when they complete.
