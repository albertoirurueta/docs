= Testing batch jobs
:description: Testing Spring Batch jobs with the spring-batch-test module -- @SpringBatchTest and @SpringJUnitConfig, JobOperatorTestUtils for starting a whole job or a single step, JobRepositoryTestUtils for cleaning metadata between tests, MetaDataInstanceFactory for building domain objects in isolation, testing @StepScope and @JobScope beans, end-to-end assertions on JobExecution and ExitStatus, validating output, and mocking with Mockito -- noting that JUnit 4 support was removed in 6.0.
:keywords: spring-batch-test, SpringBatchTest, SpringJUnitConfig, SpringBootTest, JobOperatorTestUtils, startJob, startStep, JobRepositoryTestUtils, MetaDataInstanceFactory, StepScopeTestExecutionListener, StepScopeTestUtils, JobScopeTestExecutionListener, getStepExecution, JUnit Jupiter, JUnit 5, Mockito, Testcontainers, assertions, ExitStatus

include::partial$ai-disclaimer.adoc[]

Batch jobs are testable at three levels: a component in isolation, a single step, and the whole job. The
`spring-batch-test` module supplies the fixtures for all three.

**JUnit 4 support was removed in Spring Batch 6.0 -- tests use JUnit Jupiter (JUnit 5) only.** `JobLauncherTestUtils`
is deprecated for removal since 6.0 in favour of `JobOperatorTestUtils` (which still extends it), matching the unified
`JobOperator` (xref:backend/spring-batch/batch-infrastructure-configuration.adoc[Infrastructure
configuration]).

[source,xml]
----
<dependency>
    <groupId>org.springframework.batch</groupId>
    <artifactId>spring-batch-test</artifactId>
    <scope>test</scope>
</dependency>
----

== `@SpringBatchTest`

`@SpringBatchTest` registers the test utilities as beans and adds the scope test listeners, so a test class
can inject them directly. Combine it with `@SpringJUnitConfig` (plain Spring) or `@SpringBootTest` (Boot):

[source,java]
----
@SpringBatchTest
@SpringJUnitConfig({ BatchTestConfiguration.class, EndOfDayJobConfiguration.class })
class EndOfDayJobTests {

    @Autowired
    private JobOperatorTestUtils jobOperatorTestUtils;

    @Autowired
    private JobRepositoryTestUtils jobRepositoryTestUtils;

    @AfterEach
    void clearMetadata() {
        jobRepositoryTestUtils.removeJobExecutions();   // a clean repository per test
    }
}
----

A test configuration that uses the resourceless infrastructure needs no database at all, which keeps unit
tests fast; an in-memory H2 (or Testcontainers) is used when the metadata itself is under test.

`JobOperatorTestUtils` needs to know *which* job it starts. With a single `Job` bean it finds it; an application
with several jobs (the usual case under Spring Boot) must pick one in the test, or `startJob()` has nothing to run:

[source,java]
----
@Autowired
private Job partitionedJob;

@BeforeEach
void selectJob() {
    jobOperatorTestUtils.setJob(partitionedJob);
}
----

== `JobOperatorTestUtils`

=== Running a whole job

[source,java]
----
@Test
void loadsEveryTradeAndCompletes() throws Exception {
    JobParameters parameters = new JobParametersBuilder()
            .addString("input.file", "src/test/resources/trades.csv")
            .addLocalDate("run.date", LocalDate.of(2026, 1, 31))
            .toJobParameters();

    JobExecution execution = jobOperatorTestUtils.startJob(parameters);

    assertEquals(BatchStatus.COMPLETED, execution.getStatus());
    assertEquals(ExitStatus.COMPLETED.getExitCode(), execution.getExitStatus().getExitCode());

    StepExecution loadStep = execution.getStepExecutions().stream()
            .filter(step -> step.getStepName().equals("loadTradesStep"))
            .findFirst()
            .orElseThrow();

    assertEquals(1_000, loadStep.getReadCount());
    assertEquals(998, loadStep.getWriteCount());
    assertEquals(2, loadStep.getFilterCount());
    assertEquals(0, loadStep.getSkipCount());
}
----

Asserting on the *counters* is what makes a batch test meaningful -- "it completed" says nothing about whether
it processed anything (xref:backend/spring-batch/steps-executions-and-context.adoc[Steps, executions & the
`ExecutionContext`]).

=== Running a single step

`startStep(name)` runs one step in isolation, which keeps a test focused and fast. The name is resolved
through the selected job, so it finds steps the job *contains* -- a partition worker step, which only the
partition handler knows about, is not found (`IllegalStateException: No Step found with name`); pass the `Step`
bean itself with the `startStep(Step)` overloads instead:

[source,java]
----
@Test
void rejectsRowsWithANegativePrice() {
    JobExecution execution = jobOperatorTestUtils.startStep("loadTradesStep");

    StepExecution stepExecution = execution.getStepExecutions().iterator().next();
    assertEquals(BatchStatus.COMPLETED, stepExecution.getStatus());
    assertEquals(3, stepExecution.getProcessSkipCount());
}
----

`startStep(name, jobParameters, executionContext)` supplies parameters and a seeded `ExecutionContext` -- but
note that this third argument seeds the **job** execution context (the parameter is named `jobExecutionContext`,
and the entries are copied in a `beforeJob` listener), not the step's. A reader bound to
`+#{stepExecutionContext['minId']}+` therefore sees nothing:

[source,java]
----
@Test
void workerStepReadsTheSliceFromTheJobContext() {
    ExecutionContext context = new ExecutionContext();
    context.putLong("minId", 1L);
    context.putLong("maxId", 100L);

    JobExecution execution = jobOperatorTestUtils.startStep(
            workerStep, new JobParameters(), context);      // the Step bean, not its name

    assertEquals(100, execution.getStepExecutions().iterator().next().getReadCount());
}
----

This works only if the worker binds `+#{jobExecutionContext['minId']}+`; with the usual
`+#{stepExecutionContext['minId']}+` binding the step fails and writes nothing (on the settlement example the
execution ends `FAILED` with zero rows in `settled_trade`). To test a *partition worker* that binds
`+#{stepExecutionContext['minId']}+` -- the usual case -- seed a `StepExecution` instead and drive the reader
inside step scope with `+StepScopeTestUtils.doInStepScope(...)+`, shown under
<<_testing_step_scoped_and_job_scoped_beans>> below.

=== `JobRepositoryTestUtils`

Tests that run the same job repeatedly hit the "instance already completed" rule
(xref:backend/spring-batch/jobs-instances-and-parameters.adoc[Jobs, instances & parameters]).
`JobRepositoryTestUtils` clears the metadata between tests, and can also create executions for tests that
exercise restart:

[source,java]
----
@BeforeEach
void reset() {
    jobRepositoryTestUtils.removeJobExecutions();
}

@Test
void resumesAfterAFailure() throws Exception {
    JobExecution seeded = jobRepositoryTestUtils
            .createJobExecutions("endOfDayJob", new String[] { "loadTradesStep" }, 1)
            .get(0);
    // ... arrange a failed first execution, then restart and assert the completed steps were skipped
}
----

== `MetaDataInstanceFactory`

For a *unit* test of a listener, a partitioner or a tasklet, a real job run is overkill.
`MetaDataInstanceFactory` builds domain objects without a repository:

[source,java]
----
@Test
void listenerFlagsAStepThatSkippedItems() {
    StepExecution stepExecution = MetaDataInstanceFactory.createStepExecution();
    stepExecution.setReadCount(100);
    stepExecution.setWriteCount(95);
    stepExecution.setProcessSkipCount(5);

    ExitStatus exitStatus = new StepAuditListener().after(stepExecution);

    assertEquals("COMPLETED WITH SKIPS", exitStatus.getExitCode());
}
----

`createJobExecution()`, `createJobInstance()` and `createStepExecution(jobParameters, executionContext)` cover
the other shapes.

== Testing step-scoped and job-scoped beans

A `@StepScope` bean cannot be instantiated outside a running step -- the SpEL expressions in its `@Value`
arguments have nothing to bind to. `@SpringBatchTest` registers `StepScopeTestExecutionListener`, which looks
for a `getStepExecution()` method on the test class and uses it as the ambient step execution. The lookup is by
*return type*, preferring that name: *any* method of the test class returning a `StepExecution` qualifies,
including a private helper or a compiler-generated lambda such as `Collectors.toMap(StepExecution::getStepName,
s -> s)`. A stray one makes every test fail in `prepareTestInstance` with "Could not create step execution from
method: lambda$...", so use `Function.identity()` there and keep helpers out of the test class:

[source,java]
----
@SpringBatchTest
@SpringJUnitConfig(ReaderTestConfiguration.class)
class TradeReaderTests {

    @Autowired
    private FlatFileItemReader<TradeCsv> tradeReader;

    /** Supplies the StepExecution that step-scoped beans bind to. */
    StepExecution getStepExecution() {
        JobParameters parameters = new JobParametersBuilder()
                .addString("input.file", "src/test/resources/trades.csv")
                .toJobParameters();
        return MetaDataInstanceFactory.createStepExecution(parameters);
    }

    @Test
    void readsEveryRow() throws Exception {
        tradeReader.open(new ExecutionContext());
        int count = 0;
        while (tradeReader.read() != null) {
            count++;
        }
        tradeReader.close();
        assertEquals(1_000, count);
    }
}
----

`+StepScopeTestUtils.doInStepScope(...)+` does the same for one block. Without `@SpringBatchTest` that is all you
need. *Inside* a `@SpringBatchTest` class the listener has already registered a step execution built with the
factory's default id, and a second default-id execution reuses that scope -- the slice is then not bound and the
reader's construction fails with a `NullPointerException`. Give the execution of the block its own id:

[source,java]
----
@Test
void readsTheSliceItWasGiven() throws Exception {
    StepExecution stepExecution =
            MetaDataInstanceFactory.createStepExecution("workerStep:partition0", 4242L);   // not the default id
    stepExecution.getExecutionContext().putLong("minId", 1L);
    stepExecution.getExecutionContext().putLong("maxId", 50L);

    int count = StepScopeTestUtils.doInStepScope(stepExecution, () -> {
        partitionedReader.open(stepExecution.getExecutionContext());
        int read = 0;
        while (partitionedReader.read() != null) {
            read++;
        }
        partitionedReader.close();
        return read;
    });

    assertEquals(50, count);
}
----

`JobScopeTestExecutionListener` and `JobScopeTestUtils` are the `@JobScope` equivalents.

== Validating output, and mocking

An end-to-end test should assert on what the job *produced*, not only on how it ended:

[source,java]
----
@Test
void writesTheExpectedOutputFile() throws Exception {
    JobExecution execution = jobOperatorTestUtils.startJob(parameters);
    assertEquals(BatchStatus.COMPLETED, execution.getStatus());

    List<String> lines = Files.readAllLines(Path.of("target/out/trades.csv"));
    assertEquals(999, lines.size());                       // 998 rows plus a header
    assertEquals("externalId,isin,quantity,price,notional", lines.get(0));
    assertTrue(lines.get(1).startsWith("T-0001,"));
}
----

[source,java]
----
@Test
void skipsTradesThePricingServiceRejects() throws Exception {
    // register the general stub FIRST: a later broader stubbing would
    // override the specific one and the exception would never be thrown
    when(pricingClient.price(anyString()))
            .thenReturn(new BigDecimal("12.34"));
    when(pricingClient.price("XX0000000000"))
            .thenThrow(new UnknownInstrumentException("not priced"));

    JobExecution execution = jobOperatorTestUtils.startStep("priceTradesStep");

    StepExecution stepExecution = execution.getStepExecutions().iterator().next();
    assertEquals(1, stepExecution.getProcessSkipCount());
    verify(pricingClient, times(1_000)).price(anyString());
}
----

A pragmatic split:

* *unit-test* processors, `FieldSetMapper` and `Partitioner` implementations and listeners as plain objects -- no Spring context
  needed;
* *step-test* readers and writers with `startStep` or `doInStepScope`, against a small fixture file or an
  in-memory database;
* *job-test* the flow -- that steps run in the right order, that a failure routes where it should, that a
  restart resumes -- with `startJob`, sparingly, because these are the slow ones.

Mocking a *remote* dependency is right; mocking the *database* usually is not, since half of what a batch step
does is SQL. Testcontainers against the real engine is the better trade -- see
xref:backend/springboot/unit-and-integration-testing.adoc[Unit & Integration Testing].

== Worked example: testing the partitioned settlement job

The tests below belong to the running example of this section -- the 1000-trade settlement job split into four
partitions (see xref:backend/spring-batch/scaling-and-parallel-processing.adoc[Scaling & parallel processing]).
They run on Spring Boot 4.1.2 with `spring-boot-starter-batch-test` (Spring Batch 6.0.6, JUnit Jupiter 6.0.3, in-memory
H2). The class is `@SpringBootTest` plus `@SpringBatchTest`; before each test the job is selected, the output table
is emptied and the failure switch (a bean that makes the processor fail on trade 600) is disarmed, and after each
test the metadata is removed:

[source,java]
----
@SpringBootTest
@SpringBatchTest
class PartitionedJobTests {

    @Autowired private JobOperatorTestUtils jobOperatorTestUtils;
    @Autowired private JobRepositoryTestUtils jobRepositoryTestUtils;
    @Autowired private JobOperator jobOperator;
    @Autowired private Job partitionedJob;
    @Autowired private Step workerStep;
    @Autowired private Partitioner tradeIdRangePartitioner;
    @Autowired private JdbcPagingItemReader<Trade> partitionedReader;
    @Autowired private JdbcTemplate jdbc;
    @Autowired private FailureSwitch failureSwitch;

    @BeforeEach
    void setUp() {
        jobOperatorTestUtils.setJob(partitionedJob);
        jdbc.update("delete from settled_trade");
        failureSwitch.arm(false);
    }

    @AfterEach
    void clearMetadata() {
        jobRepositoryTestUtils.removeJobExecutions();
    }

    @Test
    void settlesEveryTradeAcrossFourPartitions() throws Exception {
        JobExecution execution = jobOperatorTestUtils.startJob(jobOperatorTestUtils.getUniqueJobParameters());

        assertEquals(BatchStatus.COMPLETED, execution.getStatus());
        Map<String, StepExecution> steps = execution.getStepExecutions().stream()
                .collect(Collectors.toMap(StepExecution::getStepName, Function.identity()));
        assertEquals(Set.of("partitionedLoadStep", "workerStep:partition0", "workerStep:partition1",
                "workerStep:partition2", "workerStep:partition3"), steps.keySet());
        assertEquals(1000, steps.get("partitionedLoadStep").getReadCount());
        for (int i = 0; i < 4; i++) {
            assertEquals(250, steps.get("workerStep:partition" + i).getWriteCount());
        }
        assertEquals(1000, jdbc.queryForObject("select count(*) from settled_trade", Long.class));
    }

    @Test
    void partitionerCoversTheKeyRangeWithoutOverlap() {
        Map<String, ExecutionContext> partitions = tradeIdRangePartitioner.partition(4);

        assertEquals(4, partitions.size());
        List<long[]> ranges = partitions.values().stream()
                .map(c -> new long[] { c.getLong("minId"), c.getLong("maxId") })
                .sorted((a, b) -> Long.compare(a[0], b[0]))
                .toList();
        assertEquals(1L, ranges.get(0)[0]);
        assertEquals(1000L, ranges.get(3)[1]);
        for (int i = 1; i < ranges.size(); i++) {
            assertEquals(ranges.get(i - 1)[1] + 1, ranges.get(i)[0]);   // adjacent, never overlapping
        }
    }

    @Test
    void aFailedPartitionIsTheOnlyOneRerunOnRestart() throws Exception {
        failureSwitch.arm(true);
        JobParameters parameters = new JobParametersBuilder().addLong("run.id", 7L).toJobParameters();

        JobExecution first = jobOperator.start(partitionedJob, parameters);
        assertEquals(BatchStatus.FAILED, first.getStatus());

        failureSwitch.arm(false);
        JobExecution second = jobOperator.restart(first);

        assertEquals(BatchStatus.COMPLETED, second.getStatus());
        assertEquals(Set.of("partitionedLoadStep", "workerStep:partition2"),
                second.getStepExecutions().stream().map(StepExecution::getStepName).collect(Collectors.toSet()));
        assertEquals(1000, jdbc.queryForObject("select count(*) from settled_trade", Long.class));
    }
}
----

The class also holds the `doInStepScope` test (a reader bound to ids 1 to 50 reads 50 trades) and the `startStep`
test shown earlier. Maven reports all five passing:

[source,text]
----
Tests run: 5, Failures: 0, Errors: 0, Skipped: 0
  partitionerCoversTheKeyRangeWithoutOverlap          0.587 s
  aFailedPartitionIsTheOnlyOneRerunOnRestart          0.345 s
  readerReadsOnlyTheSliceOfItsStepExecution           0.027 s
  startStepSeedsTheJobContextNotTheStepContext        0.051 s
  settlesEveryTradeAcrossFourPartitions               0.118 s
----

Three habits in it are worth copying. The job parameters come from `getUniqueJobParameters()` (or a fixed `run.id`
in the restart test, which *needs* the same parameters twice), so a test never trips over a completed instance
left by another test. The restart test drives `+JobOperator.restart(...)+` directly, because restart is the property
that justifies partitioning, and asserts both *which* step executions the second run created and the final row
count. And the partitioner is tested as a plain object, with no Spring context involved, because its contract
(four adjacent, non-overlapping key ranges covering 1 to 1000) is pure logic.

[mermaid]
....
flowchart TD
    U["Unit tests: Partitioner, processor, listener. No Spring context, milliseconds"] --> S["Step tests: reader or writer in doInStepScope, startStep with the Step bean"]
    S --> J["Job tests: startJob, restart, counters and rows. Full context, real SQL, slowest"]
....

The pyramid, narrowing from top to bottom, is the practical split for batch: many unit tests of the logic, a few step tests per reader
and writer against a small fixture, and a handful of job tests for the flow, the restart and the end-to-end
counts.
