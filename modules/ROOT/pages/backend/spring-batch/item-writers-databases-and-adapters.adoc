= ``ItemWriter``s: databases & alternative destinations
:description: Writing a chunk to a database or another destination -- JdbcBatchItemWriter with bean-mapped parameters, an ItemPreparedStatementSetter or an ItemSqlParameterSourceProvider, JpaItemWriter and its persist/merge and flush/clear semantics, the Spring Data writers RepositoryItemWriter and MongoItemWriter, and the alternative-destination adapters ItemWriterAdapter and PropertyExtractingDelegatingItemWriter.
:keywords: JdbcBatchItemWriter, JdbcBatchItemWriterBuilder, beanMapped, columnMapped, ItemPreparedStatementSetter, ItemSqlParameterSourceProvider, assertUpdates, JpaItemWriter, flush, clear, RepositoryItemWriter, MongoItemWriter, ItemWriterAdapter, PropertyExtractingDelegatingItemWriter, upsert, batch insert, messaging writer

include::partial$ai-disclaimer.adoc[]

The database is the usual destination for a chunk, and it is where the "whole chunk at once" contract pays
off: one `PreparedStatement` executed as a JDBC batch instead of 500 round-trips.

== `JdbcBatchItemWriter`

The workhorse. It takes one SQL statement and executes it as a batch over the chunk.

=== Bean-mapped

Named parameters are resolved from the item's properties:

[source,java]
----
@Bean
public JdbcBatchItemWriter<Trade> tradeWriter(DataSource dataSource) {
    return new JdbcBatchItemWriterBuilder<Trade>()
            .dataSource(dataSource)
            .sql("""
                 INSERT INTO trade (external_id, isin, quantity, price, trade_date)
                 VALUES (:externalId, :isin, :quantity, :price, :tradeDate)
                 """)
            .beanMapped()          // :externalId <- item.getExternalId()
            .assertUpdates(true)   // fail if any statement affects no rows
            .build();
}
----

`assertUpdates(true)` (the default) throws `EmptyResultDataAccessException` when a statement updates zero rows
-- exactly what you want for an `UPDATE` that must match, and exactly what you must turn *off* for an
idempotent upsert that may legitimately do nothing.

=== Column-mapped

When the items are ``Map``s rather than beans, `.columnMapped()` binds by map key.

=== `ItemPreparedStatementSetter`

For positional `?` parameters, or when values must be computed or converted:

[source,java]
----
@Bean
public JdbcBatchItemWriter<Trade> positionalTradeWriter(DataSource dataSource) {
    return new JdbcBatchItemWriterBuilder<Trade>()
            .dataSource(dataSource)
            .sql("INSERT INTO trade (external_id, isin, quantity, notional) VALUES (?, ?, ?, ?)")
            .itemPreparedStatementSetter((trade, statement) -> {
                statement.setString(1, trade.getExternalId());
                statement.setString(2, trade.getInstrument().getIsin());
                statement.setLong(3, trade.getQuantity());
                statement.setBigDecimal(4, trade.getQuantity().multiply(trade.getPrice()));
            })
            .build();
}
----

=== `ItemSqlParameterSourceProvider`

The named-parameter equivalent, and the right hook when the parameter set is not a one-to-one map of the
item's properties:

[source,java]
----
@Bean
public JdbcBatchItemWriter<Trade> providerTradeWriter(DataSource dataSource) {
    return new JdbcBatchItemWriterBuilder<Trade>()
            .dataSource(dataSource)
            .sql("""
                 INSERT INTO trade (external_id, isin, notional, loaded_at)
                 VALUES (:externalId, :isin, :notional, :loadedAt)
                 ON CONFLICT (external_id) DO UPDATE SET notional = EXCLUDED.notional
                 """)
            .itemSqlParameterSourceProvider(trade -> new MapSqlParameterSource()
                    .addValue("externalId", trade.getExternalId())
                    .addValue("isin", trade.getInstrument().getIsin())
                    .addValue("notional", trade.getQuantity().multiply(trade.getPrice()))
                    .addValue("loadedAt", Timestamp.from(Instant.now())))
            .assertUpdates(false)   // an upsert may legitimately update nothing
            .build();
}
----

An upsert like this is what makes a step *restartable without duplicates*, which is the practical form of the
idempotency requirement discussed in
xref:backend/spring-batch/architecture-and-processing-strategies.adoc[Architecture & processing strategies].
The statement syntax itself is covered in xref:database/sql/dml-modifications.adoc[SQL Modifications].

== JPA writers

`JpaItemWriter` merges (or persists) each item and flushes once per chunk:

[source,java]
----
@Bean
public JpaItemWriter<Trade> jpaTradeWriter(EntityManagerFactory entityManagerFactory) {
    return new JpaItemWriterBuilder<Trade>()
            .entityManagerFactory(entityManagerFactory)
            .usePersist(true)                   // persist() for new entities instead of merge()
            .clearPersistenceContext(true)      // the default: clear the context after each chunk
            .build();
}
----

`HibernateItemWriter` is not part of Spring Batch 6.0 -- nor are the Hibernate readers -- so `JpaItemWriter` is the
ORM writer.

Two batch-specific cautions:

* the persistence context must be *cleared* per chunk, otherwise it accumulates every entity written by the step and
  eventually exhausts the heap. `JpaItemWriter` does so by default (`clearPersistenceContext` is `true`); the
  setting matters only if it is turned off;
* JDBC batching only happens if the provider is configured for it -- `hibernate.jdbc.batch_size`, plus an
  identifier strategy that does not force a round-trip per row (`IDENTITY` defeats batching).

Both are covered in xref:backend/hibernate/index.adoc[Hibernate Reference] and
xref:backend/springboot/spring-data-jpa.adoc[Spring Data JPA] and are not restated here. For pure bulk
loading, `JdbcBatchItemWriter` is usually the faster choice.

== Spring Data writers

`RepositoryItemWriter` calls a repository method per item -- convenient, and the natural fit when the
repository already encapsulates the save logic:

[source,java]
----
@Bean
public RepositoryItemWriter<Trade> repositoryTradeWriter(TradeRepository tradeRepository) {
    return new RepositoryItemWriterBuilder<Trade>()
            .repository(tradeRepository)
            .methodName("save")
            .build();
}
----

`MongoItemWriter` writes a chunk to a collection, either inserting or upserting:

[source,java]
----
@Bean
public MongoItemWriter<Trade> mongoTradeWriter(MongoTemplate mongoTemplate) {
    return new MongoItemWriterBuilder<Trade>()
            .template(mongoTemplate)
            .collection("trade")
            .mode(MongoItemWriter.Mode.UPSERT)
            .build();
}
----

`MongoItemWriter.Mode.REMOVE` deletes the chunk's items instead, which makes a purge step trivial.

== Alternative-destination adapters

`ItemWriterAdapter` turns an existing service method into a writer -- one call per item:

[source,java]
----
@Bean
public ItemWriterAdapter<Trade> serviceWriter(TradeService tradeService) {
    ItemWriterAdapter<Trade> adapter = new ItemWriterAdapter<>();
    adapter.setTargetObject(tradeService);
    adapter.setTargetMethod("record");     // void record(Trade trade)
    adapter.afterPropertiesSet();
    return adapter;
}
----

Note the cost: per-item calls give up the batching that makes a chunk writer fast. It is the right adapter for
a service that genuinely takes one item, and the wrong one for anything that could accept a list.

`PropertyExtractingDelegatingItemWriter` calls a method whose *arguments* are extracted from the item's
properties, which suits a legacy service signature:

[source,java]
----
@Bean
public PropertyExtractingDelegatingItemWriter<Trade> extractingWriter(LedgerService ledgerService) {
    PropertyExtractingDelegatingItemWriter<Trade> writer =
            new PropertyExtractingDelegatingItemWriter<>();
    writer.setTargetObject(ledgerService);
    writer.setTargetMethod("post");                                  // post(String isin, BigDecimal notional)
    writer.setFieldsUsedAsTargetMethodArguments(
            new String[] { "instrument.isin", "notional" });          // nested paths are allowed
    writer.afterPropertiesSet();
    return writer;
}
----

=== Messaging and mail destinations

Writers for the common messaging and mail destinations are in `spring-batch-infrastructure` itself, with their own
builders: `JmsItemWriter`, `AmqpItemWriter`, `KafkaItemWriter`, `RedisItemWriter`, `SimpleMailMessageItemWriter` and
`MimeMessageItemWriter`. The Spring Integration bridge adds the writers that need a `MessageChannel` -- the
asynchronous writer used to overlap slow remote calls with processing and the remote-chunking writer -- see
xref:backend/spring-batch/spring-batch-integration.adoc[Spring Batch Integration].

Whatever the destination, remember that a *non-transactional* writer -- a message broker, an HTTP call, a
file with `transactional(false)` -- will not be rolled back with the chunk. Either make the operation
idempotent and keyed on the item, or move it into a separate step that runs after the data is safely
committed.

== Worked example: loading the trades

The running example of this section loads the trades of a CSV file into the `trade` table in chunks of 4, on
PostgreSQL 17. The reader and processor are those of the file-reader page: twelve rows are read, the zero-quantity
row is filtered, eleven trades reach the writer. Every writer variant below sits behind the same step, so the
counters are the same unless stated:

----
step writeJdbcPositionalStep: status=COMPLETED read=12 filter=1 write=11 ... commit=4 rollback=0
----

=== `assertUpdates` and idempotent loads

The upsert from the `ItemSqlParameterSourceProvider` section uses `ON CONFLICT (external_id) DO UPDATE`. Run twice
against the same table it completes both times and the table keeps eleven rows:

----
step writeJdbcUpsertStep: status=COMPLETED read=12 filter=1 write=11 ... commit=4 rollback=0
step writeJdbcUpsertStep: status=COMPLETED read=12 filter=1 write=11 ... commit=4 rollback=0
select count(*) from trade   ->   11
----

With `ON CONFLICT (external_id) DO NOTHING` and the default `assertUpdates(true)` the second run fails on the first
chunk, because every statement affects zero rows:

----
org.springframework.dao.EmptyResultDataAccessException: Item 0 of 3 did not update any rows: [Trade[T-0001]]
step writeJdbcDoNothingStep: status=FAILED read=4 filter=1 write=0 ... commit=0 rollback=1
----

The message names the item index inside the chunk and the item itself. A `DO NOTHING` insert needs
`assertUpdates(false)`; a `DO UPDATE` upsert always affects a row and passes either way.

An upsert statement that lists only some of the columns must still satisfy the table's `NOT NULL` constraints; one
that omitted `quantity` and `price` failed with `+null value in column "quantity" ... violates not-null constraint+`
until the full column list was used.

=== What `JpaItemWriter` sends

[mermaid]
....
flowchart TB
    Chunk["write(chunk)"] --> Each["for each item"]
    Each --> Mode{"usePersist?"}
    Mode -->|true| Persist["entityManager.persist(item)"]
    Mode -->|false| Merge["entityManager.merge(item)<br/>SELECT by id, then INSERT or UPDATE"]
    Persist --> Next{"more items?"}
    Merge --> Next
    Next -->|yes| Each
    Next -->|no| Flush["flush, then clear the persistence context<br/>(clearPersistenceContext, default true)"]
....

Counting the statements Hibernate logs (`logging.level.org.hibernate.SQL=DEBUG`) for the eleven new trades:

[cols="2,1,1",options="header"]
|===
| Writer | `insert` | `select` before the insert

| `JpaItemWriter` with `usePersist(true)` | 11 | 0
| `JpaItemWriter` default (`merge`) | 11 | 11
|===

`merge` has to look each row up to decide between insert and update, so for new entities `usePersist(true)` saves one
query per item. It is the right choice only when the items are known to be new: `persist` on an existing identifier
fails. The `RepositoryItemWriter` with `methodName("save")` completed the same load with the same counters.

=== Per-item adapters

`ItemWriterAdapter` calls `TradeService.record(Trade)` once per item, so a chunk of 4 becomes four calls:

----
  TradeService.record(T-0001)
  TradeService.record(T-0002)
  TradeService.record(T-0004)
  ...
----

`PropertyExtractingDelegatingItemWriter` with `fieldsUsedAsTargetMethodArguments` set to `isin` and `notional`
calls `LedgerService.post(String, BigDecimal)` with the extracted values:

----
  LedgerService.post(US0378331005, 18995.00)
  LedgerService.post(US5949181045, 103775.00)
  LedgerService.post(DE0007164600, 9105.00)
----

Both give up the single batched statement of the JDBC writer, and neither is transactional with the chunk unless the
target service takes part in the step's transaction.
