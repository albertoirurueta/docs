= ``ItemProcessor``s

:keywords: ItemProcessor, transform, type change, filtering, return null, filterCount, CompositeItemProcessor, ClassifierCompositeItemProcessor, ItemProcessorAdapter, ValidatingItemProcessor, BeanValidatingItemProcessor, Jakarta Bean Validation, ValidationException, ScriptItemProcessor, idempotency, side effects, replay semantics

The `ItemProcessor` sits between the reader and the writer and is where business logic belongs: transform the
item, change its type, or drop it.

== The contract

[source,java]
----
public interface ItemProcessor<I, O> {
    O process(I item) throws Exception;   // return the output, or null to filter the item out
}
----

The two type parameters are the step's input and output types -- they are allowed to differ, and usually
should. A step that reads a flat-file DTO and writes a domain entity does its mapping here:

[source,java]
----
@Component
public class TradeItemProcessor implements ItemProcessor<TradeCsv, Trade> {

    private final InstrumentService instrumentService;

    public TradeItemProcessor(InstrumentService instrumentService) {
        this.instrumentService = instrumentService;
    }

    @Override
    public Trade process(TradeCsv item) {
        Instrument instrument = instrumentService.byIsin(item.getIsin());   // read-only lookup
        return new Trade(
                item.getExternalId(),
                instrument,
                item.getQuantity(),
                item.getPrice(),
                item.getQuantity().multiply(item.getPrice()));
    }
}
----

[source,java]
----
@Bean
public Step loadTradesStep(JobRepository jobRepository, PlatformTransactionManager tx,
                           ItemReader<TradeCsv> reader,
                           TradeItemProcessor processor,
                           ItemWriter<Trade> writer) {
    return new StepBuilder("loadTradesStep", jobRepository)
            .<TradeCsv, Trade>chunk(500, tx)
            .reader(reader)
            .processor(processor)
            .writer(writer)
            .build();
}
----

A step with no processor simply passes items through; the input and output types are then the same.

== Filtering vs. skipping

Returning `null` *filters* the item: it is not passed to the writer, the step continues normally, and
`filterCount` increases. This is the way to express "this record is valid but not interesting":

[source,java]
----
@Override
public Trade process(TradeCsv item) {
    if (item.getQuantity().signum() == 0) {
        return null;             // a zero-quantity trade is nothing to load -- filtered, not an error
    }
    return map(item);
}
----

Throwing an exception is different: it is an *error*, and what happens next depends on whether the step is
fault-tolerant and whether the exception is skippable -- see
xref:backend/spring-batch/fault-tolerance-skip-and-retry.adoc[Fault tolerance: skip & retry]. It increments
`processSkipCount`, not `filterCount`.

[cols="1,3",options="header"]
|===
| | Meaning

| *Filter* (`return null`) | Expected, routine, part of the business rules. Counted in `filterCount`.
| *Skip* (throw a skippable exception) | Unexpected but tolerable -- a bad record. Counted in `processSkipCount`, capped by `skipLimit`, and reportable through a `SkipListener`.
|===

Using an exception for routine filtering makes the skip limit meaningless and the counters misleading.

== Composing processors

`CompositeItemProcessor` chains processors, feeding each one's output into the next; the delegates are constructor
arguments in 6.0 (a varargs or a `List` constructor). The chain's input type is
the first processor's, its output type the last one's; if any link returns `null`, the item is filtered and the
rest of the chain is skipped:

[source,java]
----
@Bean
public CompositeItemProcessor<TradeCsv, Trade> tradeProcessingChain(
        BeanValidatingItemProcessor<TradeCsv> validator,
        TradeEnrichingProcessor enricher,
        TradeMappingProcessor mapper) {

    return new CompositeItemProcessor<>(validator, enricher, mapper);
}
----

`ClassifierCompositeItemProcessor` *routes* instead of chaining -- one processor per item category:

[source,java]
----
@Bean
public ClassifierCompositeItemProcessor<Transaction, Posting> routingProcessor(
        PurchaseProcessor purchaseProcessor,
        RefundProcessor refundProcessor,
        FeeProcessor feeProcessor) {

    ClassifierCompositeItemProcessor<Transaction, Posting> processor =
            new ClassifierCompositeItemProcessor<>();
    processor.setClassifier(transaction -> switch (transaction.getType()) {
        case PURCHASE -> purchaseProcessor;
        case REFUND   -> refundProcessor;
        case FEE      -> feeProcessor;
    });
    return processor;
}
----

== Wrapping an existing service

`ItemProcessorAdapter` turns any bean method into a processor, which avoids writing a class whose only job is
to delegate:

[source,java]
----
@Bean
public ItemProcessorAdapter<TradeCsv, Trade> serviceProcessor(TradeMappingService mappingService) {
    ItemProcessorAdapter<TradeCsv, Trade> adapter = new ItemProcessorAdapter<>();
    adapter.setTargetObject(mappingService);
    adapter.setTargetMethod("toTrade");
    adapter.afterPropertiesSet();
    return adapter;
}
----

A method reference does the same thing with less ceremony when the signature already matches:

[source,java]
----
@Bean
public ItemProcessor<TradeCsv, Trade> lambdaProcessor(TradeMappingService mappingService) {
    return mappingService::toTrade;
}
----

== Validation

`ValidatingItemProcessor` runs a `Validator` and passes the item through unchanged when it is valid:

[source,java]
----
@Bean
public ValidatingItemProcessor<TradeCsv> customValidatingProcessor() {
    ValidatingItemProcessor<TradeCsv> processor = new ValidatingItemProcessor<>(item -> {
        if (item.getPrice().signum() <= 0) {
            throw new ValidationException("price must be positive: " + item.getExternalId());
        }
    });
    processor.setFilter(false);   // true => filter invalid items instead of throwing
    return processor;
}
----

`setFilter(true)` is the switch between "an invalid record is an error" (throw, and let skip handle it) and
"an invalid record is uninteresting" (filter it out silently).

`BeanValidatingItemProcessor` applies Jakarta Bean Validation annotations, so the rules live on the item type:

[source,java]
----
public class TradeCsv {

    @NotBlank
    private String externalId;

    @Pattern(regexp = "[A-Z]{2}[A-Z0-9]{9}[0-9]")
    private String isin;

    @NotNull @Positive
    private BigDecimal price;

    // getters and setters
}
----

[source,java]
----
@Bean
public BeanValidatingItemProcessor<TradeCsv> beanValidatingProcessor() throws Exception {
    BeanValidatingItemProcessor<TradeCsv> processor = new BeanValidatingItemProcessor<>();
    processor.setFilter(false);
    processor.afterPropertiesSet();
    return processor;
}
----

Pair it with `.skip(ValidationException.class)` and a `SkipListener` that writes rejects to a quarantine table,
and the job gains a complete, auditable data-quality gate.

`ScriptItemProcessor` evaluates a JSR-223 script (Groovy, JavaScript, and so on) as the processing logic --
useful when a rule must be changed without redeploying:

[source,java]
----
@Bean
@StepScope
public ScriptItemProcessor<Trade, Trade> scriptProcessor(
        @Value("#{jobParameters['rules.script']}") Resource script) throws Exception {
    ScriptItemProcessor<Trade, Trade> processor = new ScriptItemProcessor<>();
    processor.setScript(script);   // setScriptSource(String, String) is the inline alternative
    processor.afterPropertiesSet();
    return processor;
}
----

A JSR-223 engine must be on the classpath: the JDK has shipped no JavaScript engine since JDK 15, so a Groovy
script needs `org.apache.groovy:groovy-jsr223`. The item is bound to the variable `item` (configurable with
`setItemBindingVariableName`), the script's last expression is the result, and a script that evaluates to `null`
filters the item. With an inline script over the `TradeCsv` rows of the running example,

[source,java]
----
ScriptItemProcessor<TradeCsv, String> script = new ScriptItemProcessor<>();
script.setScriptSource(
        "item.quantity() == 0 ? null : item.externalId() + ' -> ' + (item.price() * item.quantity())", "groovy");
script.afterPropertiesSet();
----

the step wrote eleven strings such as `+T-0001 -> 18995.00+` and filtered the zero-quantity row
(`read=12 filter=1 write=11`).

Treat the script as code: version it, review it, and never load it from a location an untrusted party can
write to.

== Three outcomes of one call

[mermaid]
....
flowchart LR
    In["item from the reader"] --> Call["process(item)"]
    Call -->|"returns an item"| Out["goes into the chunk,<br/>then to the writer"]
    Call -->|"returns null"| Filter["dropped, filterCount + 1,<br/>the step goes on"]
    Call -->|"throws"| Err{"fault-tolerant and<br/>skippable?"}
    Err -->|yes| Skip["skipped, processSkipCount + 1,<br/>SkipListener notified"]
    Err -->|no| Fail["step fails,<br/>the chunk rolls back"]
....

== Worked example: validating the trade file

The running example of this section is the trade feed of the file pages. The processors below run behind a
`FlatFileItemReader<TradeCsv>` and a logging writer, with chunks of 4, on Spring Batch 6.0.6. `TradeCsv` is a record
carrying Bean Validation constraints:

[source,java]
----
public record TradeCsv(
        @NotBlank String externalId,
        @Pattern(regexp = "[A-Z]{2}[A-Z0-9]{9}[0-9]") String isin,
        @NotNull @PositiveOrZero BigDecimal quantity,
        @NotNull @Positive BigDecimal price,
        LocalDate tradeDate) { }
----

The input has five rows: `T-0002` has the ISIN `BADISIN`, `T-0003` has a quantity of zero and `T-0004` has a price of
`-1.00`. The mapping processor returns `null` for a zero quantity and builds a `Trade` otherwise.

=== Filter mode

A chain of `BeanValidatingItemProcessor` with `setFilter(true)` and the mapping processor drops the invalid rows
silently:

[source,java]
----
BeanValidatingItemProcessor<TradeCsv> validator = new BeanValidatingItemProcessor<>();
validator.setFilter(true);
validator.afterPropertiesSet();
CompositeItemProcessor<TradeCsv, Trade> chain = new CompositeItemProcessor<>(validator, new TradeProcessor());
----

----
  [filter-mode] chunk of 1: [Trade[T-0001]]
  [filter-mode] chunk of 1: [Trade[T-0005]]
step filterModeStep: status=COMPLETED read=5 filter=3 write=2 readSkip=0 processSkip=0 writeSkip=0 commit=2 rollback=0
----

Three rows are counted as filtered -- the two invalid ones and the zero-quantity one -- and nothing records *why*.
That is acceptable for "not interesting" rows and wrong for bad data.

=== Throw mode

With `setFilter(false)` the validator throws `org.springframework.batch.infrastructure.item.validator.ValidationException`
for the same two rows; making the step fault-tolerant with `.skip(ValidationException.class)` turns them into
counted, reportable skips:

----
  skip in PROCESS: T-0002 (Validation failed for TradeCsv[externalId=T-0002, isin=BADISIN, ...]: ...)
  skip in PROCESS: T-0004 (Validation failed for TradeCsv[externalId=T-0004, ..., price=-1.00, ...]: ...)
  [throw-mode] chunk of 1: [Trade[T-0001]]
  [throw-mode] chunk of 1: [Trade[T-0005]]
step throwModeStep: status=COMPLETED read=5 filter=1 write=2 readSkip=0 processSkip=2 writeSkip=0 commit=2 rollback=2
----

The result differs from filter mode only in the counters -- `filter=1` for the zero-quantity row, `processSkip=2` for the
rejects -- and in the skip listener calls, which is where a quarantine table or a rejects file is written. Note
`rollback=2`: each process skip rolled the chunk back and re-processed it, see the idempotency section.

=== Routing

A `ClassifierCompositeItemProcessor` that sends `US` instruments to a mapping method and every other instrument to
the same mapping followed by an illustrative 1.08 conversion factor on the notional produces, for the twelve-row
file (the zero-quantity row maps to a zero notional there, because this processor does not filter):

----
  T-0001 US0378331005 notional=18995.00
  T-0004 DE0007164600 notional=9833.4000
  T-0009 NL0010273215 notional=379296.0000
  ...
step classifierStep: status=COMPLETED read=12 filter=0 write=12 ...
----

The foreign notionals carry the extra scale of the multiplication: a processor that changes a value's representation
should also fix its scale, or downstream columns will see `9833.4000`.

=== Adapters and predicates

`ItemProcessorAdapter` over `TradeMappingService.toTrade`, chained with a `PredicateFilteringItemProcessor` whose
predicate is "notional below 10000", keeps only the larger trades. The predicate names what to *drop*:

[source,java]
----
PredicateFilteringItemProcessor<Trade> small =
        new PredicateFilteringItemProcessor<>(t -> t.getNotional().compareTo(new BigDecimal("10000")) < 0);
CompositeItemProcessor<TradeCsv, Trade> chain = new CompositeItemProcessor<>(adapter, small);
----

----
  [big-trades] chunk of 2: [Trade[T-0001], Trade[T-0002]]
  [big-trades] chunk of 3: [Trade[T-0008], Trade[T-0009], Trade[T-0011]]
step adapterStep: status=COMPLETED read=12 filter=7 write=5 ...
----

== Idempotency

A processor may be called **more than once for the same item**. When a chunk is rolled back and replayed --
which is exactly what a fault-tolerant step does on a skip or a retry -- every item in that chunk is
re-processed from the framework's cache.

Consequences, drawn out in
xref:backend/spring-batch/fault-tolerance-skip-and-retry.adoc[Fault tolerance: skip & retry]:

* a processor that sends an e-mail, charges a card, posts to a queue or increments a shared counter will do it
  *again* on replay;
* a processor that mutates the item in place and depends on its previous state will compute a different result
  the second time;
* a processor that writes to the database is doing the writer's job, and its write is not covered by the
  writer's batching or ordering guarantees.

The rule that follows: *keep the processor pure*. Read-only lookups, computation and mapping belong here; all
side effects belong in the `ItemWriter`
(xref:backend/spring-batch/item-writers-databases-and-adapters.adoc[ItemWriters: databases & alternative
destinations]). When a side effect genuinely cannot move, either make it idempotent (key it on the item's
identity, so a second attempt is a no-op) or enable `.processorNonTransactional()` so processed outputs are
cached instead of recomputed.

=== Replays, counted

The idempotency rule is visible by counting calls. A processor that logs a line whenever it sees the same item object a
second time, run in a fault-tolerant step over a twelve-row feed with one malformed line, one invalid ISIN, one
transient failure and two duplicate keys at write time, was called again for six items in the ordinary
configuration and for none with `.processorNonTransactional()`; the step counters were identical:

----
faultClassicBaseline:   processed again = 6   write=7 readSkip=1 processSkip=1 writeSkip=2
faultClassicNonTx:      processed again = 0   write=7 readSkip=1 processSkip=1 writeSkip=2
----

The earlier throw-mode run shows the same effect from a processor skip: `T-0001`, processed before `T-0002` failed
validation, was processed a second and a third time when the chunk was replayed after each of the two skips: the
chunk's input items come from the framework's cache, but the processor is called again for each of them.
