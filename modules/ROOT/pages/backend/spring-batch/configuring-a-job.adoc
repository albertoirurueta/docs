= Configuring a job
:description: Building a Job with JobBuilder -- ordering steps with start, next and flow, controlling restartability with preventRestart and start limits, validating input with DefaultJobParametersValidator or a custom JobParametersValidator, generating fresh parameters with RunIdIncrementer or a custom date-based JobParametersIncrementer, and reacting to the run with a JobExecutionListener.
:keywords: JobBuilder, start, next, flow, preventRestart, restartable, start limit, JobParametersValidator, DefaultJobParametersValidator, InvalidJobParametersException, JobParametersIncrementer, RunIdIncrementer, JobExecutionListener, BeforeJob, AfterJob, job configuration

include::partial$ai-disclaimer.adoc[]

A `Job` bean is assembled with a `JobBuilder`: the steps in order, plus the cross-cutting configuration --
restartability, parameter validation, an incrementer and listeners.

== `JobBuilder` and step ordering

Since the removal of `JobBuilderFactory`, the builder is constructed directly with the job name and the
`JobRepository`:

[source,java]
----
@Bean
public Job endOfDayJob(JobRepository jobRepository,
                       Step stageFileStep, Step loadStep, Step reportStep) {
    return new JobBuilder("endOfDayJob", jobRepository)
            .start(stageFileStep)
            .next(loadStep)
            .next(reportStep)
            .build();
}
----

`.start(step)` fixes the first step and returns a `SimpleJobBuilder`; `.next(step)` appends the next one.
Steps run sequentially, and the job stops at the first step that fails.

`+.flow(...)+` switches to the flow builder, which is what conditional transitions, splits and deciders need:

[source,java]
----
@Bean
public Job conditionalJob(JobRepository jobRepository, Flow mainFlow) {
    return new JobBuilder("conditionalJob", jobRepository)
            .start(mainFlow)
            .end()
            .build();
}
----

Everything that can be expressed inside a flow -- `+.on(...)+`, `+.to(...)+`, `+.from(...)+`, splits, deciders --
is covered in xref:backend/spring-batch/step-flow-and-listeners.adoc[Step flow & listeners].

== Restartability and start limits

By default a failed or stopped `JobInstance` can be restarted, and completed steps are skipped on the retry.
Two switches change that.

`.preventRestart()` marks the job non-restartable: if an execution fails, that `JobInstance` is finished for
good, and attempting to launch it again throws `JobRestartException`. Use it when a partial run leaves the
system in a state that only a fresh instance can safely process:

[source,java]
----
@Bean
public Job oneShotJob(JobRepository jobRepository, Step transferStep) {
    return new JobBuilder("oneShotJob", jobRepository)
            .preventRestart()
            .start(transferStep)
            .build();
}
----

At the *step* level, `startLimit` caps how many times a given step may be started across all executions of one
instance -- a guard against a step being retried indefinitely by repeated restarts -- and
`allowStartIfComplete(true)` forces a step to run again on restart even though it already completed (useful for
validation or clean-up steps that must always run):

[source,java]
----
@Bean
public Step validateStep(JobRepository jobRepository, PlatformTransactionManager tx) {
    return new StepBuilder("validateStep", jobRepository)
            .tasklet(new ValidateInputTasklet(), tx)
            .startLimit(3)              // at most 3 attempts across restarts
            .allowStartIfComplete(true) // re-run even if it completed previously
            .build();
}
----

The restart semantics themselves -- what is skipped, what is replayed -- are in
xref:backend/spring-batch/stopping-restart-and-recovery.adoc[Stopping, restart & recovery].

== Validating parameters

A job that requires a business date should refuse to start without one, rather than failing three steps in.
`DefaultJobParametersValidator` takes the required and optional key names:

[source,java]
----
@Bean
public JobParametersValidator endOfDayValidator() {
    DefaultJobParametersValidator validator = new DefaultJobParametersValidator(
            new String[] { "run.date" },                    // required keys
            new String[] { "output.dir", "dry.run" });      // optional keys
    validator.afterPropertiesSet();
    return validator;
}

@Bean
public Job endOfDayJob(JobRepository jobRepository, Step loadStep,
                       JobParametersValidator endOfDayValidator) {
    return new JobBuilder("endOfDayJob", jobRepository)
            .validator(endOfDayValidator)
            .start(loadStep)
            .build();
}
----

A key that is neither required nor optional is only *logged*, not rejected: with the validator above, a launch
carrying a misspelled `dry.runn` printed a warning (`The JobParameters contains keys that are not explicitly optional or required: [dry.runn]`) and
then ran to `COMPLETED`. Missing *required* keys do fail the launch, before any
step runs, with `InvalidJobParametersException: The JobParameters do not contain required keys: [run.date]`. To reject
unknown keys outright, write a `JobParametersValidator` that throws, and combine it with the default one.

For rules the default validator cannot express -- a value range, a relationship between two parameters, a
readable file -- implement `JobParametersValidator`:

[source,java]
----
public class RunDateValidator implements JobParametersValidator {

    @Override
    public void validate(JobParameters parameters) throws InvalidJobParametersException {
        LocalDate runDate = parameters.getLocalDate("run.date");
        if (runDate == null) {
            throw new InvalidJobParametersException("run.date is required");
        }
        if (runDate.isAfter(LocalDate.now())) {
            throw new InvalidJobParametersException(
                    "run.date must not be in the future, was " + runDate);
        }
        if (runDate.getDayOfWeek() == DayOfWeek.SUNDAY) {
            throw new InvalidJobParametersException("no settlement run on Sundays");
        }
    }
}
----

Several validators can be combined with `CompositeJobParametersValidator`.

== Incrementers

A `JobParametersIncrementer` computes the *next* parameter set from the previous one, so an operator can say
"run the next instance" without composing parameters by hand. `RunIdIncrementer` bumps a `run.id` counter:

[source,java]
----
@Bean
public Job nightlyJob(JobRepository jobRepository, Step loadStep) {
    return new JobBuilder("nightlyJob", jobRepository)
            .incrementer(new RunIdIncrementer())
            .start(loadStep)
            .build();
}
----

A date-based incrementer is often more meaningful, because the resulting instance identity carries business
sense:

[source,java]
----
public class NextBusinessDateIncrementer implements JobParametersIncrementer {

    private final LocalDate firstRunDate;

    public NextBusinessDateIncrementer(LocalDate firstRunDate) {
        this.firstRunDate = firstRunDate;
    }

    @Override
    public JobParameters getNext(JobParameters parameters) {
        LocalDate previous = (parameters == null) ? null : parameters.getLocalDate("run.date");
        LocalDate next = (previous == null) ? firstRunDate : previous.plusDays(1);
        while (next.getDayOfWeek() == DayOfWeek.SATURDAY || next.getDayOfWeek() == DayOfWeek.SUNDAY) {
            next = next.plusDays(1);
        }
        return new JobParametersBuilder(parameters == null ? new JobParameters() : parameters)
                .addLocalDate("run.date", next)
                .toJobParameters();
    }
}
----

The incrementer is applied by `JobOperator.startNextInstance(job)` -- see
xref:backend/spring-batch/running-a-job.adoc[Running a job]. In 6.0 it is applied by a plain
`start(job, parameters)` as well: *when the job defines an incrementer, `start` ignores the parameters it was given*
and starts the next instance. The call logs a warning and carries on, as the worked example below shows, so a job
that is meant to be launched with explicit parameters (a `run.date` chosen by the caller) must not have an
incrementer.

== `JobExecutionListener`

Job-level listeners run before the first step and after the last one, regardless of outcome. Implement the
interface, or use the annotations:

[source,java]
----
@Component
public class JobTimingListener {

    private static final Logger log = LoggerFactory.getLogger(JobTimingListener.class);

    @BeforeJob
    public void before(JobExecution jobExecution) {
        log.info("starting {} execution {} with {}",
                jobExecution.getJobInstance().getJobName(),
                jobExecution.getId(),
                jobExecution.getJobParameters());
    }

    @AfterJob
    public void after(JobExecution jobExecution) {
        Duration duration = Duration.between(jobExecution.getStartTime(), jobExecution.getEndTime());
        log.info("{} finished as {} in {}s",
                jobExecution.getJobInstance().getJobName(),
                jobExecution.getStatus(),
                duration.toSeconds());
        if (jobExecution.getStatus() == BatchStatus.FAILED) {
            jobExecution.getAllFailureExceptions()
                    .forEach(throwable -> log.error("failure", throwable));
        }
    }
}
----

[source,java]
----
@Bean
public Job endOfDayJob(JobRepository jobRepository, Step loadStep, JobTimingListener timingListener) {
    return new JobBuilder("endOfDayJob", jobRepository)
            .listener(timingListener)
            .start(loadStep)
            .build();
}
----

`@AfterJob` runs even when the job failed, which makes it the right place for notifications and clean-up.
Step-level and item-level listeners are covered in
xref:backend/spring-batch/step-flow-and-listeners.adoc[Step flow & listeners].

Under Spring Boot, the concrete auto-configuration around all of this -- the repository, the datasource, the
startup runner -- is described on
xref:backend/springboot/spring-batch.adoc[Spring Batch (SpringBoot Reference)].

== The life of a launch

Validation, the incrementer, restart rules and listeners all act at fixed points of one launch. Reading the
diagram from top to bottom gives the order in which the settings of this page take effect:

[mermaid]
....
sequenceDiagram
    participant Caller
    participant Op as JobOperator
    participant Val as JobParametersValidator
    participant Repo as JobRepository
    participant L as JobExecutionListener
    participant S as Steps
    Caller->>Op: start(job, parameters)
    Note over Op: job has an incrementer?<br/>then the parameters are replaced
    Op->>Repo: find or create the JobInstance
    Op->>Repo: check restart rules against the last execution
    Repo-->>Op: ok, or JobRestartException
    Op->>Val: validate(parameters)
    Val-->>Op: ok, or InvalidJobParametersException
    Op->>Repo: create the JobExecution
    Repo-->>Op: JobExecution
    Op->>L: beforeJob
    Op->>S: run the steps in order
    S-->>Op: statuses
    Op->>L: afterJob
    Op->>Repo: update JobExecution
    Op-->>Caller: JobExecution
....

The consequence worth remembering is the *order*, which the source of the launcher and a run both confirm. The
instance is looked up or created first, the restart rules are checked next, and only then are the parameters
validated and the execution created. A launch refused by the validator therefore leaves no `JobExecution` -- no listener
runs and no step starts -- but the `JobInstance` row for the refused parameters has already been inserted. After the
five launches of the example below, of which four were rejected, `BATCH_JOB_INSTANCE` held five rows and
`BATCH_JOB_EXECUTION` one. And since the restart checks come before validation, a completed instance is refused with
`JobInstanceAlreadyCompleteException` even if the new parameters would not have passed the validator.

== Worked example: the end-of-day job under validation

The `endOfDayJob` of this section requires `run.date` and `input.file` and treats `output.dir` and `dry.run` as
optional. Launching it with the parameters of the table gave:

[cols="3,4",options="header"]
|===
| Launch | Outcome

| `input.file` only
| `InvalidJobParametersException: The JobParameters do not contain required keys: [run.date]`; an instance row, no execution.

| `run.date`, `input.file` and the misspelled `dry.runn`
| `WARN` about the unknown key, then a normal run to `COMPLETED`.
|===

A second job, `settlementJob`, uses the `RunDateValidator` above and a single no-op step. The three launches below
were all refused before any step ran (each left an instance row and no execution):

[source,text]
----
InvalidJobParametersException: run.date is required
InvalidJobParametersException: no settlement run on Sundays                  (run.date 2026-02-01)
InvalidJobParametersException: run.date must not be in the future, was 2026-11-13
----

Three more behaviours of the same builder, each observed:

* *Incrementers.* `nightlyJob` with `RunIdIncrementer` and three calls of `startNextInstance` created instances 1,
  2 and 3 with `run.id` 1, 2 and 3 -- the first of them `FAILED`, and the second call did *not* restart it but
  created a new instance. The business-day incrementer, started at `2026-01-29` (a Thursday) with
  `new NextBusinessDateIncrementer(LocalDate.of(2026, 1, 29))`, produced `2026-01-29`, `2026-01-30`, `2026-02-02` and
  `2026-02-03`: the weekend is skipped.
* *`start` with an incrementer.* Calling `start` on that same job with `run.date=2026-03-13` logged `+Attempting to
  launch job: [businessDayJob] which defines an incrementer with additional parameters: [...]. Additional parameters
  will be ignored.+` and ran with `2026-02-04` -- the next date in the sequence.
* *Restart switches.* After `oneShotJob` (`.preventRestart()`) failed once, launching its instance again threw
  `JobRestartException: JobInstance already exists and is not restartable`. For a step with `.startLimit(2)` that
  always fails, the first two launches ended `FAILED` with the step's own exception and the third with
  `StartLimitExceededException: Maximum start limit exceeded for step: alwaysFailsStepStartMax: 2` -- recorded as a
  failed `JobExecution` that has no step execution of its own.

== The listener in the log

The `JobTimingListener` above, attached to the `endOfDayJob`, wraps every run. A failed run followed by a
successful restart, as in
xref:backend/spring-batch/stopping-restart-and-recovery.adoc[Stopping, restart & recovery], logs:

[source,text]
----
starting endOfDayJob execution 1 with {JobParameter{name='run.date', value=2026-01-30, ...},JobParameter{name='input.file', ...}}
endOfDayJob finished as FAILED in 202ms
failure: java.lang.IllegalArgumentException: trade 8 has quantity 0
starting endOfDayJob execution 2 with {JobParameter{name='run.date', value=2026-01-30, ...},JobParameter{name='input.file', ...}}
endOfDayJob finished as COMPLETED in 76ms
----

(The parameter lists are abbreviated; the real `JobParameters.toString()` spells out name, value, type and the
identifying flag of each parameter.)

Both calls were made for the same `JobInstance`: `@BeforeJob` ran once per *execution*, not once per instance, and
`@AfterJob` ran for the failed execution as well, which is why it is the place for notifications. The 6.0
`getStartTime()`/`getEndTime()` are `LocalDateTime` values, so `Duration.between` applies directly.
