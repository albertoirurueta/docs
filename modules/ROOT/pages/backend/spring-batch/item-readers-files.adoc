include::partial$ai-disclaimer.adoc[]

Most batch input arrives as a file. Spring Batch supplies readers for delimited and fixed-length flat files,
XML and JSON, and a contract for writing your own.

== The `ItemReader` contract

[source,java]
----
public interface ItemReader<T> {
    T read() throws Exception;   // returns the next item, or null when exhausted
}
----

`read()` returns *one* item per call and `null` exactly once, to signal the end of input -- that `null` ends
the step. Returning `null` early therefore truncates the job, which is a common bug in hand-written readers.

`ItemStreamReader<T>` adds the `ItemStream` callbacks (`open`, `update`, `close`) that make a reader
*restartable*: `update` writes the current position into the step `ExecutionContext` at every commit point, and
`open` reads it back on restart. Every framework reader implements it. See
xref:backend/spring-batch/steps-executions-and-context.adoc[Steps, executions & the `ExecutionContext`] for the
contract and for registering delegate streams.

== `FlatFileItemReader`

Reading a flat file is a chain of four responsibilities:

[mermaid]
....
flowchart LR
    File["Resource<br/>one line of text"] --> LM["LineMapper"]
    LM --> LT["LineTokenizer<br/>split the line"]
    LT --> FS["FieldSet<br/>typed positional/named access"]
    FS --> FSM["FieldSetMapper<br/>build the domain object"]
    FSM --> Item["item"]
....

`FlatFileItemReaderBuilder` assembles all four for the common cases:

[source,java]
----
@Bean
@StepScope
public FlatFileItemReader<TradeCsv> tradeReader(
        @Value("#{jobParameters['input.file']}") Resource inputFile) {
    return new FlatFileItemReaderBuilder<TradeCsv>()
            .name("tradeReader")            // required: the ExecutionContext key prefix
            .resource(inputFile)
            .linesToSkip(1)                 // a header row
            .delimited()
            .delimiter(",")
            .quoteCharacter('"')
            .names("externalId", "isin", "quantity", "price", "tradeDate")
            .targetType(TradeCsv.class)     // maps by property name
            .strict(true)                   // fail if the resource is missing
            .build();
}
----

`+.name(...)+` is mandatory for a restartable reader -- it is the key under which the line count is saved.

A fixed-length file uses column ranges instead of a delimiter:

[source,java]
----
@Bean
public FlatFileItemReader<Customer> fixedWidthCustomerReader() {
    return new FlatFileItemReaderBuilder<Customer>()
            .name("fixedWidthCustomerReader")
            .resource(new ClassPathResource("customers.txt"))
            .fixedLength()
            .columns(new Range(1, 10), new Range(11, 40), new Range(41, 42), new Range(43, 52))
            .names("customerId", "name", "countryCode", "balance")
            .targetType(Customer.class)
            .build();
}
----

=== A custom `FieldSetMapper`

`+targetType(...)+` uses a `BeanWrapperFieldSetMapper` under the covers, which needs a no-argument constructor
and setters (a record is handled by a `RecordFieldSetMapper` instead). For conversion, validation or an immutable
type, write the mapper:

[source,java]
----
public class TradeFieldSetMapper implements FieldSetMapper<Trade> {

    @Override
    public Trade mapFieldSet(FieldSet fieldSet) {
        return new Trade(
                fieldSet.readString("isin"),
                fieldSet.readLong("quantity"),
                fieldSet.readBigDecimal("price"),
                LocalDate.parse(fieldSet.readString("tradeDate")));
    }
}
----

[source,java]
----
.delimited()
.names("isin", "quantity", "price", "tradeDate")
.fieldSetMapper(new TradeFieldSetMapper())
----

`FieldSet` is the typed accessor over the tokenized line: `readString`, `readInt`, `readLong`,
`readBigDecimal`, `readBoolean`, `readDate`, each by name or index.

=== Files with several record formats

A file that mixes header, detail and trailer records needs a `LineMapper` that chooses a tokenizer per line
prefix:

[source,java]
----
@Bean
public FlatFileItemReader<Object> mixedRecordReader() {
    PatternMatchingCompositeLineMapper<Object> lineMapper = new PatternMatchingCompositeLineMapper<>(
            Map.of("HDR*", headerTokenizer(),
                   "DTL*", detailTokenizer(),
                   "TRL*", trailerTokenizer()),
            Map.of("HDR*", new HeaderFieldSetMapper(),
                   "DTL*", new DetailFieldSetMapper(),
                   "TRL*", new TrailerFieldSetMapper()));

    return new FlatFileItemReaderBuilder<Object>()
            .name("mixedRecordReader")
            .resource(new FileSystemResource("/data/in/mixed.txt"))
            .lineMapper(lineMapper)
            .build();
}
----

In 6.0 the two maps are constructor arguments of `PatternMatchingCompositeLineMapper`; the setters remain, but there
is no no-argument constructor to call them on. The mapper's generic type is the common type of what the three
``FieldSetMapper``s return.

The patterns use the same `+*+`/`?` wildcards as flow transitions.

=== Multi-line records

When one logical item spans several physical lines, wrap the flat-file reader in a reader that assembles them.
The typical shape is a delegate plus a loop that reads until the record's terminator:

[source,java]
----
public class TradeGroupReader implements ItemStreamReader<TradeGroup> {

    private final FlatFileItemReader<Object> delegate;

    public TradeGroupReader(FlatFileItemReader<Object> delegate) {
        this.delegate = delegate;
    }

    @Override
    public TradeGroup read() throws Exception {
        TradeGroup group = null;
        for (Object line = delegate.read(); line != null; line = delegate.read()) {
            if (line instanceof Header header) {
                group = new TradeGroup(header);
            } else if (line instanceof Detail detail && group != null) {
                group.add(detail);
            } else if (line instanceof Trailer && group != null) {
                return group;            // record complete
            }
        }
        return group;                     // last record, or null at end of file
    }

    @Override public void open(ExecutionContext context) { delegate.open(context); }
    @Override public void update(ExecutionContext context) { delegate.update(context); }
    @Override public void close() { delegate.close(); }
}
----

Delegating `open`/`update`/`close` is what keeps the composite restartable.

=== Reading a directory of files

`MultiResourceItemReader` runs one delegate over many resources, tracking which file and which line it is on. The
delegate is a constructor argument in 6.0 and must be a `ResourceAwareItemReaderItemStream` (a `FlatFileItemReader`
built without a `+resource(...)+` is the usual choice, because the multi-resource reader assigns each file in turn):

[source,java]
----
@Bean
@StepScope
public MultiResourceItemReader<TradeCsv> multiFileReader(
        @Value("#{jobParameters['input.dir']}") String inputDir,
        FlatFileItemReader<TradeCsv> tradeReader) throws IOException {

    Resource[] resources = new PathMatchingResourcePatternResolver()
            .getResources("file:" + inputDir + "/trades-*.csv");

    MultiResourceItemReader<TradeCsv> reader = new MultiResourceItemReader<>(tradeReader);
    reader.setName("multiFileReader");
    reader.setResources(resources);
    reader.setStrict(true);
    return reader;
}
----

Sort the resources deterministically (the default comparator is by filename) so a restart sees the same order.

== Worked example: the trade file

The running example of this section loads a delimited file of trades. The input has a header row and twelve
trades; the third has a quantity of zero:

----
externalId,isin,quantity,price,tradeDate
T-0001,US0378331005,100,189.95,2026-03-02
T-0002,US5949181045,250,415.10,2026-03-02
T-0003,GB0002634946,0,98.20,2026-03-02
...
T-0012,JP3633400001,300,15.50,2026-03-04
----

The item type is a record, with a date as one of its components:

[source,java]
----
public record TradeCsv(String externalId, String isin, BigDecimal quantity, BigDecimal price, LocalDate tradeDate) { }
----

The obvious reader -- `+.names(...)+` plus `.targetType(TradeCsv.class)` -- fails on the first line, both for a bean
with setters and for a record, because neither mapper registers a conversion from `String` to `LocalDate`. For the
bean the failure reads:

----
Caused by: org.springframework.validation.BindException: ...
Field error in object 'target' on field 'tradeDate': rejected value [2026-03-02]; ... Cannot convert value of type
'java.lang.String' to required type 'java.time.LocalDate' for property 'tradeDate': no matching editors or
conversion strategy found
----

The `FieldSetMapper` shown above fixes it, and with it the reader runs. The step reads from the file, a processor
maps each row to a `Trade` (the zero-quantity row is filtered) and a `JdbcBatchItemWriter` inserts the result:

----
=== job csvToJdbc ===
step loadTradesStep: status=COMPLETED read=12 filter=1 write=11 readSkip=0 processSkip=0 writeSkip=0 commit=4 rollback=0
----

If the resource does not exist, `.strict(true)` fails the step before any item is read:

----
org.springframework.batch.infrastructure.item.ItemStreamException: Failed to initialize the reader
Caused by: java.lang.IllegalStateException: Input resource must exist (reader is in 'strict' mode): URL [file:data/missing.csv]
step loadTradesStep: status=FAILED read=0 filter=0 write=0 ...
----

=== A malformed line

When a field cannot be converted -- a price of `not-a-number` on the fourth data row -- the mapper throws and the
reader wraps the failure in a `FlatFileParseException` that names the file, the physical line number (the header
is line 1) and the raw text. Under a fault-tolerant step that exception is the usual candidate for a read skip
(xref:backend/spring-batch/fault-tolerance-skip-and-retry.adoc[Fault tolerance: skip & retry]), and a skip listener
receives this message:

----
Parsing error at line: 5 in resource=[URL [file:data/trades-dirty.csv]], input=[T-0004,DE0007164600,75,not-a-number,2026-03-02]
----

=== What the reader saves for a restart

A `FlatFileItemReader` is an `ItemStreamReader` whose state is one number, the count of items read so far. It is
stored in the step's `ExecutionContext` under a key built from the reader's `name`, and that key is why `+.name(...)+`
is mandatory when `saveState` is on (the default):

[mermaid]
....
flowchart TB
    Open["open(executionContext)"] --> Has{"context contains<br/>tradeReader.read.count?"}
    Has -->|no| First["start at the first line<br/>(after linesToSkip)"]
    Has -->|yes| Skip["read and discard that many items"]
    First --> Read
    Skip --> Read["read() returns the next item<br/>and increments the count"]
    Read --> Update["update(executionContext)<br/>at every commit: put the count"]
    Update --> Read
....

After a run that committed its first chunk of four items and failed in the second, the persisted step context
contains `tradeReader.read.count=4`; restarting the execution skips four items and carries on with the fifth
(the run is in
xref:backend/spring-batch/chunk-oriented-processing.adoc[Chunk-oriented processing]). The counter counts items,
not lines, so it stays correct for multi-line records, but it makes a restart *replay the input* up to that point:
reading is cheap, yet a very large file restarts slower than a database reader that can seek.

=== Fixed-length columns are not trimmed by `targetType`

The fixed-length reader above, run against a two-line file with padded columns, returns the padding when the item
is a record built by the `targetType` mapper:

----
Customer[customerId=C000000001, name=Alice Martin                  , countryCode=ES, balance=12.50]
----

`+FieldSet.readString(...)+` trims, so a mapper written with it returns clean values:

[source,java]
----
.fieldSetMapper(fs -> new Customer(fs.readString("customerId"), fs.readString("name"),
        fs.readString("countryCode"), fs.readBigDecimal("balance")))
----

----
Customer[customerId=C000000001, name=Alice Martin, countryCode=ES, balance=12.50]
----

`+readRawString(...)+` is the untrimmed accessor, for formats where the padding is significant.

=== Header, detail and trailer records, run

The mixed-format reader and the wrapper that assembles one group per header-to-trailer block, run against

----
HDR|B-100|2026-03-02
DTL|T-0001|US0378331005|100
DTL|T-0002|US5949181045|250
TRL|2
HDR|B-101|2026-03-03
DTL|T-0005|FR0000120271|40
TRL|1
----

produce two items, one per block, with the step counting groups rather than lines:

----
  [groups] chunk of 2: [Group[B-100 [T-0001:100, T-0002:250]], Group[B-101 [T-0005:40]]]
step mixedStep: status=COMPLETED read=2 filter=0 write=2 ...
----

=== Several files, one step

`MultiResourceItemReader` presents the files as a single stream, so chunk boundaries ignore file boundaries. With
the twelve trades split over `trades-1.csv` (six rows) and `trades-2.csv` (six rows) and a chunk size of 4, the
second chunk takes its first two items from the first file and its last two from the second, and the step reports
`read=12 write=12 commit=4`.

== XML with `StaxEventItemReader`

StAX-based, so the document is streamed rather than loaded. The fragment root element names the item boundary,
and an `Unmarshaller` (JAXB here) turns each fragment into an object:

[source,java]
----
@Bean
public StaxEventItemReader<Trade> xmlTradeReader() {
    Jaxb2Marshaller marshaller = new Jaxb2Marshaller();
    marshaller.setClassesToBeBound(Trade.class);

    return new StaxEventItemReaderBuilder<Trade>()
            .name("xmlTradeReader")
            .resource(new FileSystemResource("/data/in/trades.xml"))
            .addFragmentRootElements("trade")
            .unmarshaller(marshaller)
            .build();
}
----

== JSON with `JsonItemReader`

`JsonItemReader` streams a JSON *array of objects* through a `JsonObjectReader`. The Jackson-backed
implementation is `JacksonJsonObjectReader`, which in the current line uses Jackson 3:

[source,java]
----
@Bean
public JsonItemReader<Trade> jsonTradeReader() {
    return new JsonItemReaderBuilder<Trade>()
            .name("jsonTradeReader")
            .resource(new FileSystemResource("/data/in/trades.json"))
            .jsonObjectReader(new JacksonJsonObjectReader<>(Trade.class))
            .build();
}
----

A newline-delimited JSON file is not a JSON array; read it with a `FlatFileItemReader` whose `LineMapper`
deserialises each line instead.

=== XML and JSON, read back

The item type must be mapped for the unmarshaller. JAXB has no built-in mapping for `java.time.LocalDate`, so the
trade class carries an adapter for its date:

[source,java]
----
@XmlRootElement(name = "trade")
@XmlAccessorType(XmlAccessType.FIELD)
public class Trade {
    private String externalId;
    private String isin;
    private BigDecimal quantity;
    private BigDecimal price;
    private BigDecimal notional;
    @XmlJavaTypeAdapter(LocalDateAdapter.class)    // XmlAdapter<String, LocalDate> using LocalDate.parse
    private LocalDate tradeDate;
    // constructors, getters and setters
}
----

`Jaxb2Marshaller` needs `spring-oxm` and a JAXB runtime (`org.glassfish.jaxb:jaxb-runtime`) on the classpath, which
the Spring Boot starters do not bring. Reading back the eleven-trade XML file written by the writer page, and a
three-element JSON array, with chunks of 4:

----
  [xml] chunk of 4: [Trade[T-0001], Trade[T-0002], Trade[T-0004], Trade[T-0005]]
  [xml] chunk of 4: [Trade[T-0006], Trade[T-0007], Trade[T-0008], Trade[T-0009]]
  [xml] chunk of 3: [Trade[T-0010], Trade[T-0011], Trade[T-0012]]
  [json] chunk of 3: [Trade[T-0001], Trade[T-0002], Trade[T-0003]]
step xmlStep: status=COMPLETED read=11 ... commit=3 rollback=0
step jsonStep: status=COMPLETED read=3 ... commit=1 rollback=0
----

The JSON reader worked with `JacksonJsonObjectReader<>(Trade.class)` and the Jackson 3 artifact
(`tools.jackson.core:jackson-databind`), which understands `LocalDate` and `BigDecimal` without further
configuration.

== Custom readers

Implement `ItemStreamReader` when the source is neither a file nor a database -- a REST endpoint, a queue
drain, a proprietary API. Two rules cover most mistakes: return `null` only at true end of input, and save
enough state in `update` to resume. The watermark example in
xref:backend/spring-batch/steps-executions-and-context.adoc[Steps, executions & the `ExecutionContext`] is a
complete template.

== Dealing with no input

A reader that returns `null` on the first call produces a step that completes with `readCount = 0`. Whether
that is success or failure is a business decision -- attach a `NoWorkFoundStepExecutionListener` to fail it, or
return a custom exit code and branch on it. Both are covered in
xref:backend/spring-batch/stopping-restart-and-recovery.adoc[Stopping, restart & recovery].

For reading and writing Excel files in a step with Apache POI, see xref:backend/office-files/batch-import-export-with-spring-batch.adoc[Batch Import & Export with Spring Batch].
