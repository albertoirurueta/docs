= Chunk-oriented processing
:description: The chunk-oriented step -- the read-one/process-one/accumulate/write-chunk loop, the commit interval as chunk size and transaction boundary, dynamic chunk sizing with a CompletionPolicy, the classic StepBuilder chunk(size, transactionManager) idiom alongside the 6.0 ChunkOrientedStep and ChunkOrientedStepBuilder, transaction attributes (propagation, isolation, timeout, noRollback) and registering an ItemStream with the step.
:keywords: chunk-oriented processing, commit interval, chunk size, transaction boundary, ItemReader, ItemProcessor, ItemWriter, StepBuilder.chunk, ChunkOrientedStep, ChunkOrientedStepBuilder, CompletionPolicy, SimpleCompletionPolicy, TimeoutTerminationPolicy, CompositeCompletionPolicy, transaction attributes, propagation, isolation, timeout, noRollback, ItemStream, stream registration

include::partial$ai-disclaimer.adoc[]

Chunk-oriented processing is what Spring Batch is for: read items one at a time, transform each one,
accumulate them until a chunk is full, then write the whole chunk inside a single transaction.

== The loop

[mermaid]
....
flowchart TB
    Start(["step starts"]) --> Tx["begin transaction"]
    Tx --> Read["ItemReader.read()<br/>repeated until the chunk is full<br/>or the input is exhausted"]
    Read --> Process["ItemProcessor.process(item)<br/>once per item read<br/>(null means filtered)"]
    Process --> Write["ItemWriter.write(chunk)<br/>the whole list at once"]
    Write --> Update["update the StepExecution,<br/>persist the ExecutionContext"]
    Update --> Commit["commit transaction"]
    Commit --> More{"input exhausted?"}
    More -->|no| Tx
    More -->|yes| Done(["step ends"])
....

Four properties of that picture matter:

* the *reader* and *processor* see one item at a time, so memory is bounded by the chunk, not by the input;
* a chunk is *read completely before it is processed*: the reader is called until the chunk is full (or returns
  `null`), then the processor runs over the items that were read, then the writer receives what is left. The
  worked example below prints the order;
* the *writer* sees the whole chunk, so it can issue one batched statement instead of N;
* the *commit interval is the chunk size is the transaction boundary* -- these are three names for one number.
  A chunk of 500 means one transaction per 500 items, one `ExecutionContext` save per 500 items, and a restart
  granularity of 500 items.

The chunk size counts items *read*, not items written: an item the processor filters still occupies a slot. With
a chunk size of 3 and a zero-quantity trade among the first three rows, the first transaction writes two items,
not three.

If anything in the chunk fails, the whole transaction rolls back -- all 500 items -- and the framework's
fault-tolerance machinery decides whether to retry, skip or fail
(xref:backend/spring-batch/fault-tolerance-skip-and-retry.adoc[Fault tolerance: skip & retry]).

== Building a chunk step

The current idiom constructs the builder directly and passes the chunk size and the transaction manager:

[source,java]
----
@Bean
public Step loadTradesStep(JobRepository jobRepository,
                           PlatformTransactionManager transactionManager,
                           ItemReader<TradeCsv> reader,
                           ItemProcessor<TradeCsv, Trade> processor,
                           ItemWriter<Trade> writer) {
    return new StepBuilder("loadTradesStep", jobRepository)
            .<TradeCsv, Trade>chunk(500, transactionManager)
            .reader(reader)
            .processor(processor)
            .writer(writer)
            .build();
}
----

The two type parameters are the *input* type (what the reader returns) and the *output* type (what the
processor produces and the writer consumes). They may differ -- that type change is the processor's main job.
A step without a processor uses the same type twice.

=== The 6.0 `ChunkOrientedStep`

Spring Batch 6.0 introduces `ChunkOrientedStep` and its `ChunkOrientedStepBuilder`, which take the chunk size
as a constructor argument and expose the new concurrency model (see
xref:backend/spring-batch/scaling-and-parallel-processing.adoc[Scaling & parallel processing]):

[source,java]
----
@Bean
public Step loadTradesStep(JobRepository jobRepository,
                           PlatformTransactionManager transactionManager,
                           ItemReader<TradeCsv> reader,
                           ItemProcessor<TradeCsv, Trade> processor,
                           ItemWriter<Trade> writer) {
    return new ChunkOrientedStepBuilder<TradeCsv, Trade>("loadTradesStep", jobRepository, 500)
            .reader(reader)
            .processor(processor)
            .writer(writer)
            .transactionManager(transactionManager)
            .build();
}
----

The two forms are not equal in status. `StepBuilder.chunk(int, PlatformTransactionManager)` and
`chunk(CompletionPolicy, PlatformTransactionManager)` -- along with the `SimpleStepBuilder` and
`FaultTolerantStepBuilder` they return -- are annotated `@Deprecated(since = "6.0", forRemoval = true)`. The
non-deprecated entry point is `StepBuilder.chunk(int)`, which returns a `ChunkOrientedStepBuilder`.

The `.chunk(size, transactionManager)` form is still what most existing code and most published examples use,
and it is what the other pages in this section show, so it is worth recognising -- but new code should prefer
`ChunkOrientedStepBuilder`, and code being migrated should plan to move off the deprecated form.

== Dynamic chunk sizes with a `CompletionPolicy`

A fixed chunk size is a fixed *count*. When "how much is a chunk" depends on something else -- elapsed time, a
change of business key, a memory budget -- supply a `CompletionPolicy` instead:

[source,java]
----
@Bean
public Step timeBoundedStep(JobRepository jobRepository, PlatformTransactionManager tx,
                            ItemReader<Trade> reader, ItemWriter<Trade> writer) {
    CompositeCompletionPolicy policy = new CompositeCompletionPolicy();
    policy.setPolicies(new CompletionPolicy[] {
            new SimpleCompletionPolicy(1000),          // at most 1000 items ...
            new TimeoutTerminationPolicy(5_000L)       // ... or 5 seconds, whichever comes first
    });

    return new StepBuilder("timeBoundedStep", jobRepository)
            .<Trade, Trade>chunk(policy, tx)
            .reader(reader)
            .writer(writer)
            .build();
}
----

`SimpleCompletionPolicy` is what a plain integer chunk size creates internally. A custom policy implements
`CompletionPolicy` (usually by extending `CompletionPolicySupport`) and is consulted after every item to decide
whether the chunk is finished. It receives only the `RepeatContext`, not the item, so a rule that depends on the
data needs the reader's state: see *Chunk boundaries driven by data* below for a policy that closes the chunk
whenever the trade date changes.

The underlying `RepeatOperations` abstraction that runs this loop is described in
xref:backend/spring-batch/repeat-and-retry-internals.adoc[Repeat & retry internals].

== Transaction attributes

The chunk transaction is a normal Spring transaction, and its attributes are configurable per step:

[source,java]
----
@Bean
public Step isolatedStep(JobRepository jobRepository, PlatformTransactionManager tx,
                         ItemReader<Trade> reader, ItemWriter<Trade> writer) {
    DefaultTransactionAttribute attribute = new DefaultTransactionAttribute();
    attribute.setPropagationBehavior(Propagation.REQUIRES_NEW.value());
    attribute.setIsolationLevel(Isolation.READ_COMMITTED.value());
    attribute.setTimeout(120);   // seconds; fail the chunk rather than hold locks forever

    return new StepBuilder("isolatedStep", jobRepository)
            .<Trade, Trade>chunk(200, tx)
            .reader(reader)
            .writer(writer)
            .transactionAttribute(attribute)
            .build();
}
----

* *Propagation* -- `REQUIRED` by default. `REQUIRES_NEW` isolates the chunk from any surrounding transaction;
  `NOT_SUPPORTED` runs the chunk without one, which only makes sense for a read-only step.
* *Isolation* -- the default is the database's. Raising it increases contention; see
  xref:database/sql/transactions.adoc[SQL Transactions].
* *Timeout* -- an upper bound on one chunk. A long timeout plus a large chunk is the classic recipe for lock
  contention with the online system.

`.noRollback(SomeException.class)` -- available on the fault-tolerant builder returned by `.faultTolerant()`, and
not on `ChunkOrientedStepBuilder` -- declares exceptions that must *not* roll the chunk back -- typically a
business exception thrown by a writer that has already handled the failure itself:

[source,java]
----
return new StepBuilder("tolerantStep", jobRepository)
        .<Trade, Trade>chunk(200, tx)
        .reader(reader)
        .writer(writer)
        .faultTolerant()
        .noRollback(DuplicateTradeException.class)
        .build();
----

== Registering an `ItemStream`

Readers and writers that hold restart state implement `ItemStream`, and the step must know about them so that
`open`, `update` and `close` are called at the right moments. A reader or writer passed to `+.reader(...)+` or
`+.writer(...)+` is registered automatically. A *delegate* hidden inside another component is registered only if
that component passes the callbacks on:

* `CompositeItemWriter` is itself an `ItemStreamWriter` and opens, updates and closes every delegate that is an
  `ItemStream` (unless `setIgnoreItemStream(true)` is set), so its delegates need no extra registration. In
  6.0 the delegates are constructor arguments;
* `ClassifierCompositeItemWriter` is a plain `ItemWriter`, so its delegates are invisible to the step and must be
  registered with `+.stream(...)+`.

[source,java]
----
@Bean
public Step routingStep(JobRepository jobRepository, PlatformTransactionManager tx,
                        ItemReader<Trade> reader,
                        FlatFileItemWriter<Trade> domesticWriter,
                        FlatFileItemWriter<Trade> foreignWriter) {

    ClassifierCompositeItemWriter<Trade> routing = new ClassifierCompositeItemWriter<>();
    routing.setClassifier(trade -> trade.isDomestic() ? domesticWriter : foreignWriter);

    return new StepBuilder("routingStep", jobRepository)
            .<Trade, Trade>chunk(500, tx)
            .reader(reader)
            .writer(routing)
            .stream(domesticWriter)    // the delegates need open/update/close
            .stream(foreignWriter)
            .build();
}
----

Forgetting a needed registration is the usual cause of a failing step with this message:

----
org.springframework.batch.infrastructure.item.WriterNotOpenException: Writer must be open before it can be written to
----

or, for a reader, of "restart started from the beginning of the file".

== Worked example: tracing one chunk

The running example of this section loads trade files into a `trade` table. The step below is the one from the
top of the page with a chunk size of 3; a listener registered for the read, process, write and chunk callbacks
prints what happens, and the input is a 12-row file in which the third row has a quantity of zero:

[source,java]
----
static class Tracer implements ItemReadListener<TradeCsv>, ItemProcessListener<TradeCsv, Trade>,
        ItemWriteListener<Trade>, ChunkListener<TradeCsv, Trade> {

    @Override public void beforeChunk(ChunkContext context) { log.info("--- chunk begins (transaction opened)"); }
    @Override public void afterRead(TradeCsv item) { log.info("read    {}", item.externalId()); }
    @Override public void afterProcess(TradeCsv item, Trade result) {
        log.info("process {} -> {}", item.externalId(), result == null ? "null (filtered)" : "Trade");
    }
    @Override public void beforeWrite(Chunk<? extends Trade> items) { log.info("write   {} item(s)", items.size()); }
    @Override public void afterChunk(ChunkContext context) { log.info("--- chunk ends (committed)"); }
}

Step step = new StepBuilder("traceStep", jobRepository)
        .<TradeCsv, Trade>chunk(3, transactionManager)
        .reader(tradeReader).processor(tradeProcessor).writer(tradeWriter)
        .listener((ItemReadListener<TradeCsv>) tracer)
        .listener((ItemProcessListener<TradeCsv, Trade>) tracer)
        .listener((ItemWriteListener<Trade>) tracer)
        .listener((ChunkListener) tracer)
        .build();
----

The first two chunks and the end of the step print:

----
--- chunk begins (transaction opened)
read    T-0001
read    T-0002
read    T-0003
process T-0001 -> Trade
process T-0002 -> Trade
process T-0003 -> null (filtered)
write   2 item(s)
--- chunk ends (committed)
--- chunk begins (transaction opened)
read    T-0004
read    T-0005
read    T-0006
process T-0004 -> Trade
...
write   3 item(s)
--- chunk ends (committed)
--- chunk begins (transaction opened)
--- chunk ends (committed)
step traceStep: status=COMPLETED read=12 filter=1 write=11 readSkip=0 processSkip=0 writeSkip=0 commit=5 rollback=0
----

Three things are visible in that output:

* all reads of a chunk happen before its first `process` call, and the single `write` call comes last;
* the filtered item occupied a slot in the first chunk, so it wrote two items; the other chunks wrote three;
* the last chunk is empty -- the reader returned `null` straight away -- yet it still opens and commits a
  transaction, which is why twelve items in chunks of three give a `commitCount` of 5, not 4.

The `ChunkListener` callbacks that take a `ChunkContext` are the ones the classic builder invokes; the 6.0
interface also has overloads that receive the `Chunk` itself, which the `ChunkOrientedStep` calls instead.

== Chunk boundaries driven by data

A `CompletionPolicy` is consulted after every item with only the `RepeatContext`, so a boundary based on the data
has to be fed by the reader. The example closes the chunk whenever the trade date changes, so that all trades of
one day commit together. A `SingleItemPeekableItemReader` looks one row ahead; the date of the item just read is
remembered by an `ItemReadListener`:

[source,java]
----
static class DateChangePolicy extends CompletionPolicySupport {

    private final SingleItemPeekableItemReader<TradeCsv> reader;
    volatile LocalDate last;                  // date of the item read most recently

    DateChangePolicy(SingleItemPeekableItemReader<TradeCsv> reader) { this.reader = reader; }

    @Override
    public boolean isComplete(RepeatContext context) {
        try {
            TradeCsv next = reader.peek();    // the row that would start the next chunk
            return next == null || !next.tradeDate().equals(last);
        } catch (Exception e) {
            throw new IllegalStateException(e);
        }
    }

    @Override
    public boolean isComplete(RepeatContext context, RepeatStatus result) {
        return result == RepeatStatus.FINISHED || isComplete(context);
    }
}

SingleItemPeekableItemReader<TradeCsv> peekable = new SingleItemPeekableItemReader<>(tradeReader);
DateChangePolicy policy = new DateChangePolicy(peekable);
ItemReadListener<TradeCsv> remember = new ItemReadListener<>() {
    @Override public void afterRead(TradeCsv item) { policy.last = item.tradeDate(); }
};

Step step = new StepBuilder("byDateStep", jobRepository)
        .<TradeCsv, Trade>chunk(policy, transactionManager)
        .reader(peekable)
        .processor(tradeProcessor)
        .writer(tradeWriter)
        .listener(remember)
        .build();
----

With a writer that logs each call, the 12-row file produces one write per trade date:

----
  writing 3 trades for 2026-03-02
  writing 4 trades for 2026-03-03
  writing 4 trades for 2026-03-04
step byDateStep: status=COMPLETED read=12 filter=1 write=11 ... commit=4 rollback=0
----

The first date has four rows and one of them is filtered, hence three writes. Because chunk boundaries now depend
on the data, the peekable reader must also be the reader the step registers, so that its state is saved at each
commit.

== The commit interval is the restart granularity

A restart resumes from the last *committed* chunk, so the chunk size is also the most work that can be repeated
after a failure. The example makes the writer fail once for the chunk that contains `T-0007`, then restarts the
failed execution:

[mermaid]
....
sequenceDiagram
    participant S as Step
    participant R as FlatFileItemReader
    participant D as Database
    participant J as JobRepository
    Note over S,J: first execution, chunk size 4
    S->>R: read T-0001 .. T-0004
    S->>D: write 3 items, commit
    S->>J: save context, tradeReader.read.count=4
    S->>R: read T-0005 .. T-0008
    S->>D: write fails, rollback
    Note over S,J: FAILED, the second chunk is not saved
    Note over S,J: restart of the same execution
    S->>J: load the saved context
    S->>R: open, skip the 4 rows already read
    S->>R: read T-0005 .. T-0012
    S->>D: write 8 items, commit
....

The step execution and the persisted context of the failed run print:

----
java.lang.IllegalStateException: simulated outage while writing [Trade[T-0005], Trade[T-0006], Trade[T-0007], Trade[T-0008]]
step restartStep: status=FAILED read=8 filter=1 write=3 readSkip=0 processSkip=0 writeSkip=0 commit=1 rollback=1
  persisted context of restartStep: [batch.version=6.0.6, ..., tradeReader.read.count=4, batch.executed=true]
=== restarting restartDemo ===
step restartStep: status=COMPLETED read=8 filter=0 write=8 commit=3 rollback=0
----

The failed run had read eight items, but only the first chunk was committed, so the saved `read.count` is 4 and
the restart processes `T-0005` to `T-0012` -- eight items, none of the four committed ones. A chunk size of 500
would have repeated up to 500 items of work after a failure; the trade-off against throughput is discussed in
xref:backend/spring-batch/profiling-and-tuning.adoc[Profiling & tuning].

== The two builders side by side

The same step, built with `ChunkOrientedStepBuilder` and with the `StepBuilder.chunk(int)` entry point, behaves
like the classic one for reads, filters and writes; the difference visible in the counters is the empty final
transaction:

[cols="2,1,1,1,1",options="header"]
|===
| Builder (12 rows, chunk of 4) | `readCount` | `filterCount` | `writeCount` | `commitCount`

| `.chunk(4, transactionManager)` (deprecated)
| 12 | 1 | 11 | 4

| `new ChunkOrientedStepBuilder<>(name, jobRepository, 4)`
| 12 | 1 | 11 | 3
|===

`.chunk(int)` returns a `ChunkOrientedStepBuilder` too, so
`+new StepBuilder("entryPointStep", jobRepository).<TradeCsv, Trade>chunk(4).reader(...).writer(...).transactionManager(tx).build()+`
is the non-deprecated spelling of the classic idiom. Transaction attributes (`REQUIRES_NEW`, `READ_COMMITTED` and a
120-second timeout in the example above) are accepted by both builders through `+.transactionAttribute(...)+`.
