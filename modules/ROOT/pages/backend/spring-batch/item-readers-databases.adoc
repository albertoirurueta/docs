= ``ItemReader``s: databases
:description: Reading from a database in a Spring Batch step -- JdbcCursorItemReader versus JdbcPagingItemReader with a PagingQueryProvider, the cursor-versus-paging trade-off, the JPA cursor and paging readers (the Hibernate readers are gone in 6.0), StoredProcedureItemReader, the Spring Data readers RepositoryItemReader and MongoPagingItemReader, and the driving-query pattern.
:keywords: JdbcCursorItemReader, JdbcPagingItemReader, PagingQueryProvider, SqlPagingQueryProviderFactoryBean, cursor vs paging, fetchSize, sortKeys, JpaCursorItemReader, JpaPagingItemReader, StoredProcedureItemReader, RepositoryItemReader, MongoPagingItemReader, driving query pattern, thread safety, SynchronizedItemStreamReader

include::partial$ai-disclaimer.adoc[]

Database input comes in two shapes: hold a *cursor* open and stream rows from it, or issue a *page* query
repeatedly. The choice determines restartability, thread-safety and how long a transaction stays open.

== Cursor vs. paging

[cols="1,2,2",options="header"]
|===
| | *Cursor* | *Paging*

| How it works
| One `SELECT`; the `ResultSet` stays open and rows are streamed as `read()` is called.
| Repeated ``SELECT``s with a sort key and an offset or a key predicate; each page is a separate round-trip.

| Transaction / connection
| One long-lived connection and result set for the whole step.
| Short queries; nothing is held between pages.

| Restart
| Re-executes the query and *skips* forward to the saved row number.
| Re-executes from the saved page -- naturally stateless.

| Threads
| Bound to one thread: a `ResultSet` is not thread-safe.
| Safe to use from several threads if the sort key is unique and deterministic.

| Cost
| Cheapest per row; no repeated query planning.
| More round-trips; deep offsets degrade unless the sort key is indexed.

| Use it when
| A single-threaded step reads a large, stable table.
| The step is multi-threaded or partitioned, or the source changes under a long transaction.
|===

The sort key is what makes paging correct: it must be *unique* and *stable*, otherwise pages overlap or skip
rows.

== `JdbcCursorItemReader`

[source,java]
----
@Bean
public JdbcCursorItemReader<Trade> cursorTradeReader(DataSource dataSource) {
    return new JdbcCursorItemReaderBuilder<Trade>()
            .name("cursorTradeReader")
            .dataSource(dataSource)
            .sql("SELECT id, isin, quantity, price FROM trade WHERE trade_date = ?")
            .preparedStatementSetter(new ArgumentPreparedStatementSetter(
                    new Object[] { Date.valueOf(LocalDate.now().minusDays(1)) }))
            .rowMapper(new TradeRowMapper())
            .fetchSize(1000)       // JDBC driver hint: rows per network round-trip
            .verifyCursorPosition(false)
            .build();
}
----

`fetchSize` is the single most valuable setting here -- the default of many drivers is to fetch a handful of
rows at a time, or (on some) to buffer the entire result set in memory.

== `JdbcPagingItemReader`

The reader needs a `PagingQueryProvider`, which builds the per-page SQL for the specific database.
`SqlPagingQueryProviderFactoryBean` detects the dialect from the `DataSource`:

[source,java]
----
@Bean
public PagingQueryProvider tradeQueryProvider(DataSource dataSource) throws Exception {
    SqlPagingQueryProviderFactoryBean factory = new SqlPagingQueryProviderFactoryBean();
    factory.setDataSource(dataSource);
    factory.setSelectClause("SELECT id, isin, quantity, price");
    factory.setFromClause("FROM trade");
    factory.setWhereClause("WHERE trade_date = :tradeDate");
    factory.setSortKey("id");
    return factory.getObject();
}

@Bean
@StepScope
public JdbcPagingItemReader<Trade> pagingTradeReader(
        DataSource dataSource, PagingQueryProvider tradeQueryProvider,
        @Value("#{jobParameters['run.date']}") LocalDate runDate) {
    return new JdbcPagingItemReaderBuilder<Trade>()
            .name("pagingTradeReader")
            .dataSource(dataSource)
            .queryProvider(tradeQueryProvider)
            .parameterValues(Map.of("tradeDate", Date.valueOf(runDate)))
            .pageSize(1000)
            .rowMapper(new TradeRowMapper())
            .build();
}
----

A good default is `pageSize` equal to the chunk size, so one page fills one chunk.

== JPA readers

`JpaCursorItemReader` streams a JPQL query; `JpaPagingItemReader` pages it. Both need an
`EntityManagerFactory`:

[source,java]
----
@Bean
public JpaPagingItemReader<Trade> jpaTradeReader(EntityManagerFactory entityManagerFactory) {
    return new JpaPagingItemReaderBuilder<Trade>()
            .name("jpaTradeReader")
            .entityManagerFactory(entityManagerFactory)
            .queryString("SELECT t FROM Trade t WHERE t.tradeDate = :tradeDate ORDER BY t.externalId")
            .parameterValues(Map.of("tradeDate", LocalDate.of(2026, 3, 3)))
            .pageSize(500)
            .build();
}
----

`JpaCursorItemReaderBuilder` takes the same `queryString`/`parameterValues` (and `hintValues`) without a page size.
The Hibernate-specific `HibernateCursorItemReader` and `HibernatePagingItemReader`, and `HibernateItemWriter` on the
writer side, are not part of Spring Batch 6.0: the JPA readers and writers replace them, and a Hibernate
`StatelessSession` is reachable only through a custom reader.

Two persistence-specific hazards, both amplified by batch volumes:

* the *first-level cache* grows with every entity that stays managed, so a long-running JPA step can leak memory
  unless the persistence context is cleared per chunk -- the JPA writer clears it by default, see
  xref:backend/spring-batch/item-writers-databases-and-adapters.adoc[``ItemWriter``s: databases & alternative
  destinations];
* *lazy associations* turn one query into N. Fetch what the processor needs in the query itself.

Both are covered in depth in xref:backend/hibernate/index.adoc[Hibernate Reference]; the Spring Data JPA side
is xref:backend/springboot/spring-data-jpa.adoc[Spring Data JPA] -- neither is restated here.

== `StoredProcedureItemReader`

When the query is a procedure returning a cursor:

[source,java]
----
@Bean
public StoredProcedureItemReader<Trade> procedureTradeReader(DataSource dataSource) {
    return new StoredProcedureItemReaderBuilder<Trade>()
            .name("procedureTradeReader")
            .dataSource(dataSource)
            .procedureName("read_trades_for_date")
            .parameters(new SqlParameter[] { new SqlParameter("p_trade_date", Types.DATE) })
            .preparedStatementSetter(new ArgumentPreparedStatementSetter(
                    new Object[] { Date.valueOf(LocalDate.now().minusDays(1)) }))
            .refCursorPosition(2)          // for databases that return a REF CURSOR out parameter
            .rowMapper(new TradeRowMapper())
            .build();
}
----

== Spring Data readers

`RepositoryItemReader` calls a paging repository method, which keeps the query definition next to the domain
model:

[source,java]
----
@Bean
public RepositoryItemReader<Trade> repositoryTradeReader(TradeRepository tradeRepository) {
    return new RepositoryItemReaderBuilder<Trade>()
            .name("repositoryTradeReader")
            .repository(tradeRepository)
            .methodName("findByTradeDate")
            .arguments(List.of(LocalDate.now().minusDays(1)))
            .sorts(Map.of("id", Sort.Direction.ASC))
            .pageSize(500)
            .build();
}
----

`MongoPagingItemReader` (and its cursor sibling) does the same over a `MongoTemplate`:

[source,java]
----
@Bean
public MongoPagingItemReader<Trade> mongoTradeReader(MongoTemplate mongoTemplate) {
    return new MongoPagingItemReaderBuilder<Trade>()
            .name("mongoTradeReader")
            .template(mongoTemplate)
            .collection("trade")
            .jsonQuery("{ 'tradeDate': ?0 }")
            .parameterValues(List.of(LocalDate.now().minusDays(1)))
            .sorts(Map.of("_id", Sort.Direction.ASC))
            .pageSize(500)
            .targetType(Trade.class)
            .build();
}
----

== The driving-query pattern

Instead of selecting whole rows with all their joins, select only the *keys*, and let the processor hydrate
each one. The reader's query stays small and index-only, the transaction stays short, and the work of
assembling an object graph moves to a place where it can be parallelised:

[source,java]
----
@Bean
public JdbcPagingItemReader<Long> tradeIdReader(DataSource dataSource,
                                                PagingQueryProvider tradeIdQueryProvider) {
    return new JdbcPagingItemReaderBuilder<Long>()
            .name("tradeIdReader")
            .dataSource(dataSource)
            .queryProvider(tradeIdQueryProvider)     // SELECT id FROM trade WHERE ... ORDER BY id
            .pageSize(1000)
            .rowMapper((resultSet, rowNumber) -> resultSet.getLong("id"))
            .build();
}

@Bean
public ItemProcessor<Long, Trade> hydratingProcessor(TradeRepository tradeRepository) {
    return tradeRepository::loadWithPositions;       // one keyed lookup per item
}
----

The trade-off is one extra query per item, so it pays off when the hydration is selective or the driving query
would otherwise be an expensive multi-way join. The pattern is described in
https://docs.spring.io/spring-batch/reference/common-patterns.html[Common batch patterns]; the query technique
itself is in xref:database/sql/dml-queries.adoc[SQL Queries].

== Worked example: the same four trades through five readers

The running example is a `trade` table holding the eleven trades loaded by the file pages. Every reader below
selects the trades of 2026-03-03 -- four rows, `T-0005` to `T-0008` -- with a page size or chunk size of 3, and a
logging writer prints each chunk. The run, on PostgreSQL 17 with Spring Batch 6.0.6, reports the same figures for
the JDBC cursor, JDBC paging, JPA paging, JPA cursor and Spring Data repository readers:

----
  [cursor] chunk of 3: [Trade[T-0005], Trade[T-0006], Trade[T-0007]]
  [cursor] chunk of 1: [Trade[T-0008]]
step cursorStep: status=COMPLETED read=4 filter=0 write=4 ... commit=2 rollback=0
step pagingStep: status=COMPLETED read=4 filter=0 write=4 ... commit=2 rollback=0
step jpaPagingStep: ... read=4 ... commit=2
step jpaCursorStep: ... read=4 ... commit=2
step repositoryStep: ... read=4 ... commit=2
----

What differs is the SQL each reader sends, which is visible with `logging.level.org.springframework.jdbc.core.JdbcTemplate=DEBUG`
and `logging.level.org.hibernate.SQL=DEBUG`:

[cols="1,3",options="header"]
|===
| Reader | Statements for the four rows with a page size of 3

| `JdbcCursorItemReader`
| One `+SELECT ... WHERE trade_date = ? ORDER BY external_id+`; the `ResultSet` stays open for the whole step.

| `JdbcPagingItemReader`
| `+SELECT ... ORDER BY external_id ASC LIMIT 3+`, then `+SELECT ... WHERE (trade_date = ?) AND ((external_id > ?)) ORDER BY external_id ASC LIMIT 3+`.

| `JpaPagingItemReader`
| `+... order by t1_0.external_id offset ? rows fetch first ? rows only+`, once per page.

| `JpaCursorItemReader`
| One query, `+... order by t1_0.external_id+`, streamed.

| `RepositoryItemReader`
| The same offset/fetch query per page, plus a `+select count(*)+` per page for the `Page` result.
|===

The JDBC paging reader is therefore a *keyset* pager: the second query does not use an offset, it asks for rows
whose sort key is greater than the last one returned, which is why the sort key must be unique and why deep pages
cost the same as the first. The JPA and Spring Data readers use offsets, which degrade on deep pages.

[mermaid]
....
sequenceDiagram
    participant S as Step
    participant R as JdbcPagingItemReader
    participant D as Database
    S->>R: read() three times
    R->>D: first page: ORDER BY external_id LIMIT 3
    D-->>R: T-0005, T-0006, T-0007
    Note over R: remembers the last sort key T-0007
    S->>R: read(), buffer empty
    R->>D: next page: external_id greater than T-0007, LIMIT 3
    D-->>R: T-0008
    S->>R: read(), buffer empty
    Note over R: the second page held fewer rows than the page size,<br/>so no further query is issued
    R-->>S: null, end of input
....

A page shorter than the page size tells the reader that the input is exhausted, so the four rows cost two queries,
not three.

=== The driving-query pattern, run

With the id reader and the hydrating processor from the previous section, the logged SQL is one keyset query for
ids per page and one keyed lookup per item:

----
SELECT external_id FROM trade WHERE trade_date = ? ORDER BY external_id ASC LIMIT 3
select t1_0.external_id,... from trade t1_0 where t1_0.external_id=?    (three times)
  [driving] chunk of 3: [Trade[T-0005], Trade[T-0006], Trade[T-0007]]
SELECT external_id FROM trade WHERE (trade_date = ?) AND ((external_id > ?)) ORDER BY external_id ASC LIMIT 3
select t1_0.external_id,... from trade t1_0 where t1_0.external_id=?    (once)
  [driving] chunk of 1: [Trade[T-0008]]
----

The hydration lookups run inside the chunk's transaction, so they see a consistent snapshot, and they are the
part to parallelise or batch when the per-item query dominates.

== Thread safety

No stateful reader is thread-safe. In a multi-threaded step, either use a paging reader with a unique sort key
or wrap the reader in a `SynchronizedItemStreamReader` -- see
xref:backend/spring-batch/scaling-and-parallel-processing.adoc[Scaling & parallel processing], which also
covers giving each partition its own key range instead of sharing one reader.
