= Putting It All Together: The Place Order Flow
:description: Assembles every pattern in this section into one worked example -- the happy path and the payment-failure path through the Place Order Saga, end to end from an HTTP request to the CQRS read model, plus a checklist of what to test at each layer.
:keywords: domain-driven design, DDD, worked example, place order saga, transactional outbox, saga orchestration, CQRS, aggregate, end to end, compensating transaction, idempotent consumer

include::partial$ddd-microservices-disclaimer.adoc[]

Every other page in this section builds one piece of the running e-commerce domain in isolation: an aggregate, an
event, an outbox row, a saga step, a read model. None of them, on its own, shows what actually happens when a
single HTTP request comes in and the whole machine has to turn it into a delivered order. This page does exactly
that: it assembles the `Order`, `Inventory`, `Payment`, and `Shipping` bounded contexts, the transactional outbox,
the `PlaceOrderSaga` orchestrator, and the `OrderHistoryView` CQRS read model into one continuous walkthrough, twice
-- once for the happy path, once for the path where payment authorization fails -- on the same Java 21 / Spring
Boot 4.1.x / Spring Data JPA / Spring Modulith 2.x / Spring for Apache Kafka 4.1.x baseline as the rest of this
section. No new pattern is introduced here and no class is redefined; every name below is exactly the one its
originating page already established, cross-referenced rather than repeated.

== The running domain, assembled

xref:backend/ddd-microservices/strategic-design.adoc[Strategic Design]'s context map names five contexts:
**Order** as the core domain driving the checkout process, **Inventory**, **Payment**, and **Shipping** as
supporting subdomains it depends on as a customer depends on suppliers, and **Customer** as a generic subdomain
referenced only by `CustomerId` and never implemented. This page's two walkthroughs exercise all four implemented
contexts together, coordinated by the `PlaceOrderSaga` orchestrator
xref:backend/ddd-microservices/sagas.adoc[Sagas] already builds in full.

image::ddd-worked-example-system.svg[Diagram of the Place Order Saga assembled end to end: the Order Service's Order aggregate and PlaceOrderService write through a local transaction into an outbox table, which a polling relay forwards to the order-events broker topic; PlaceOrderSaga orchestrates Inventory as a compensatable step, Payment as the pivot step with a dashed ReleaseInventoryCommand compensation path, and Shipping as a retriable step; the same order-events topic also feeds OrderHistoryProjector, which maintains the OrderHistoryView CQRS read model,width=760,role=text-center]

`PlaceOrderSagaCommandHandler` is the one name on that tree not spelled out in full anywhere else -- it is the
inbound adapter xref:backend/ddd-microservices/structuring-the-code.adoc[Structuring the Code]'s hexagon figure
already names alongside `OrderController`, and both walkthroughs below use it for exactly the job that figure
already assigns it: receiving `ApproveOrderCommand`/`RejectOrderCommand` from `PlaceOrderSaga` and calling
`order.approve()`/`order.reject(reason)` through the same `OrderRepository` and `DomainEventPublisher` ports
`PlaceOrderService` already depends on, never a new port of its own.

== The happy path, end to end

Placing an order that succeeds all the way through touches every layer this section has built, in the order the
sequence below lays out. `PlaceOrderController` here is the plain, synchronous shape -- validate, call
`PlaceOrderService`, return `201 Created` with a `PlacedOrderResponse`
(xref:backend/ddd-microservices/cqrs.adoc[CQRS]) -- not the publish-first variant of the same controller name
xref:backend/ddd-microservices/listen-to-yourself.adoc[Listen to Yourself] shows for contrast; a service picks one
shape for `PlaceOrderController`, not both.

. **`PlaceOrderController` -> `PlaceOrderService`.** The controller builds a `PlaceOrderCommand` from the request
  body and calls `PlaceOrderService.placeOrder(command)`
  (xref:backend/ddd-microservices/structuring-the-code.adoc[Structuring the Code]).
. **`Order.place(command)`.** The static factory
  (xref:backend/ddd-microservices/entities.adoc[Entities], xref:backend/ddd-microservices/aggregates.adoc[Aggregates])
  builds the new `Order` in `APPROVAL_PENDING`, enforces the minimum-order-amount invariant, and returns an
  `OrderCreation(order, List.of(new OrderPlaced(...)))`.
. **Outbox insert, same local transaction.** `PlaceOrderService` saves the `Order` row through `OrderRepository`
  and hands `OrderPlaced` to `OutboxDomainEventPublisher`, which inserts one `outbox` row
  (xref:backend/ddd-microservices/transactional-outbox.adoc[Transactional Outbox]) -- the `Order` row and the
  outbox row commit or roll back together, so there is no window where one exists without the other.
. **Relay.** `OutboxPollingRelay`'s `@Scheduled` sweep reads the unpublished row, publishes it to the
  `order-events` topic keyed by `orderId`, and only then marks it published -- the same at-least-once relay
  xref:backend/ddd-microservices/transactional-outbox.adoc[Transactional Outbox] already walks through in full.
. **`PlaceOrderSaga` starts.** The orchestrator reacts to `OrderPlaced`, persists a `SagaState` in
  `RESERVING_INVENTORY`, and sends `ReserveInventoryCommand` to Inventory
  (xref:backend/ddd-microservices/sagas.adoc[Sagas]).
. **Inventory, Payment, Shipping, in sequence.** `InventoryService.reserve(...)` commits its own local
  transaction and replies `InventoryReserved`; the saga advances to `AUTHORIZING_PAYMENT` and sends
  `AuthorizePaymentCommand`; Payment's own handler (the same shape as `InventoryService`, not repeated on this
  page) replies `PaymentAuthorized`, the saga's pivot; the saga advances to `SCHEDULING_SHIPPING` and sends
  `ScheduleShippingCommand`; Shipping replies `ShippingScheduled`.
. **`Order.approve()`.** The saga advances to `ORDER_APPROVED` and sends `ApproveOrderCommand` to
  `PlaceOrderSagaCommandHandler`, which loads `Order` via `OrderRepository`, calls `order.approve()`
  (xref:backend/ddd-microservices/entities.adoc[Entities]), saves the now-`APPROVED` order, and publishes
  `OrderApproved` through the same outbox as step 3.
. **`OrderHistoryProjector` updates the CQRS view.** The relay forwards `OrderApproved` the same way it forwarded
  `OrderPlaced`; `OrderHistoryProjector` dedups on the envelope's `eventId` and applies
  `OrderHistoryView.applyStatusChange("APPROVED", ...)`
  (xref:backend/ddd-microservices/cqrs.adoc[CQRS]) -- a client polling `GET /order-history/\{orderId}` eventually
  observes `status = "APPROVED"`, once the projector has caught up.

== The payment-failure path: compensating and rejecting

The failure walkthrough shares everything up through inventory reservation with the happy path above -- the
divergence starts the moment Payment replies `PaymentAuthorizationFailed` instead of `PaymentAuthorized`.

. Steps 1-5 above run unchanged: the order is placed, the outbox relays `OrderPlaced`, and `PlaceOrderSaga`
  reserves inventory successfully, advancing to `AUTHORIZING_PAYMENT`.
. **`PaymentAuthorizationFailed`.** Payment's own local transaction determines the charge cannot be authorized
  (an insufficient-funds decline, a fraud hold) and replies `PaymentAuthorizationFailed(orderId, reason)`
  (xref:backend/ddd-microservices/sagas.adoc[Sagas]) instead of committing an authorization.
. **The saga's `REJECTING_INVENTORY` compensation.** `PlaceOrderSaga.handle(PaymentAuthorizationFailed)` loads the
  persisted `SagaState`, calls `state.onPaymentAuthorizationFailed(reply)`, which moves the state machine to
  `REJECTING_INVENTORY` and returns `List.of(new ReleaseInventoryCommand(orderId))` -- inventory reservation was a
  **compensatable** step, so committing it earlier is exactly what makes an explicit compensation necessary now;
  payment was never reached as a committed fact, so nothing about *it* needs undoing.
. **Inventory releases its hold.** `InventoryService.release(command)` runs its own local transaction, releases
  the reservation made in step 6 of the happy path, and replies `InventoryReleased`
  (xref:backend/ddd-microservices/sagas.adoc[Sagas]).
. **`Order.reject(reason)`.** The saga advances to `ORDER_REJECTED` and sends `RejectOrderCommand(orderId, reason)`
  to `PlaceOrderSagaCommandHandler`, which loads `Order`, calls `order.reject(reason)`
  (xref:backend/ddd-microservices/entities.adoc[Entities]) -- moving `Order` from `APPROVAL_PENDING` straight to
  `REJECTED`, the same state-machine transition xref:backend/ddd-microservices/entities.adoc[Entities]'s
  `OrderStatus` diagram already draws -- saves the now-`REJECTED` order, and publishes `OrderRejected` through the
  outbox.
. **The CQRS view reflects `REJECTED`.** `OrderHistoryProjector` applies the same
  `applyStatusChange(...)` path as the happy path's `OrderApproved`, this time setting `status = "REJECTED"` --
  the read model needs no separate code path for a rejected order, because both outcomes are just a status
  transition applied to the same `OrderHistoryView` row.

Notice what does *not* appear anywhere in that diagram: no distributed transaction spans Payment's decline and
Order's rejection, and no step ever blocks waiting for another service's lock --
xref:backend/ddd-microservices/why-not-distributed-transactions.adoc[Why Not Distributed Transactions]'s whole
argument is exactly why this compensating sequence, not a rolled-back cross-service transaction, is what a
multi-step failure looks like once each bounded context owns its own database.

== What to test, and where it is already sketched

Testing this assembled flow does not mean standing up all four services and a broker for every test -- each layer
already has a narrow, fast test sketched on its own page, and the checklist below is where to find it rather than
a new suite to write from scratch.

[cols="2,3,3"]
|===
|Level |What the test verifies |Already sketched on

|Aggregate unit tests (`Order`)
|`Order.approve()`/`reject(reason)`/`cancel()` only fire from `APPROVAL_PENDING`; `removeLine` enforces the
minimum-order-amount invariant; two `Order` instances sharing an `OrderId` are equal regardless of `status`.
|`OrderEqualityTest` on xref:backend/ddd-microservices/entities.adoc[Entities], exercised against the invariant
xref:backend/ddd-microservices/aggregates.adoc[Aggregates]' fuzzy-boundary scenario motivates.

|Saga state-machine tests (`PlaceOrderSaga` / `SagaState`)
|Given a starting `SagaStatus`, a specific reply transitions the state machine to the expected next status and
returns the expected next command or compensation -- no broker, no database, no real participant needed.
|`paymentFailureTriggersInventoryReleaseThenRejection` on xref:backend/ddd-microservices/sagas.adoc[Sagas], the
exact given/when/then this page's own failure-path walkthrough follows.

|Outbox / consumer idempotency tests
|A redelivered envelope (the same `eventId` twice) is a safe no-op, not a duplicate row or a double-applied effect
-- the `INSERT ... ON CONFLICT DO NOTHING` dedup guard returns zero affected rows on the second delivery and the
handler returns immediately.
|The dedup guard and `OutboxPollingRelay`'s at-least-once relay on
xref:backend/ddd-microservices/transactional-outbox.adoc[Transactional Outbox], and the `processed_events` guard
on xref:backend/ddd-microservices/domain-events.adoc[Domain Events].

|CQRS projection tests
|`OrderHistoryProjector.on(...)` dispatches each event type to the right `OrderHistoryView` update, is idempotent
under redelivery, and a query against a not-yet-caught-up view returns `409` rather than stale data.
|`OrderHistoryProjector`'s dedup-then-`switch` body and `OrderHistoryQueryService.byId`'s `minVersion` check on
xref:backend/ddd-microservices/cqrs.adoc[CQRS].
|===

Reading the table top to bottom also reads as the order in which a change to this flow is cheapest to verify:
an aggregate-level regression is caught by the fastest, most isolated test in the list, and only a change to how
the pieces are wired together -- the saga's sequencing, the outbox's relay timing, the projector's dispatch --
needs a test that spans more than one class, never all of them running live at once for an ordinary unit-level
check.
