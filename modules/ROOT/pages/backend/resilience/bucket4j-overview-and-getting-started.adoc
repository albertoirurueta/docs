Bucket4j is a Java library that limits how fast something may happen. A *bucket* holds tokens, every operation takes
some of them, and a *refill* puts them back at a fixed speed. When the bucket is empty the operation is refused, or it
waits. That is the whole model, and it is the token-bucket algorithm that the
xref:backend/resilience/bucket4j-token-bucket-and-bandwidths.adoc[next page] explains in detail. This page introduces the
library, lists what it ships, and builds a first working limiter for the *Bookshelf* API.

It was written against Bucket4j 8.21.0 (released on 2 October 2026), Spring Boot 4.1.x, Spring Framework 7.0.x and Java 21,
and verified on 4 October 2026. The `bucket4j-spring-boot-starter` that appears in the ecosystem section is a community
project; the version it needs is stated where it is used.

== What Bucket4j is

Bucket4j describes itself as a library, not a framework: it has no container, no annotations of its own and no
configuration files. You add a jar, build a `Bucket` object with a fluent builder, and call `tryConsume` before the work
you want to limit. Everything else, such as where requests come from, what a rejection looks like and where to keep the
buckets, is your code. The library does four things well:

* *A precise, allocation-light algorithm.* A bucket keeps a few `long` values. The reference says it takes no more
  than about 40 bytes however many requests arrive, and the arithmetic is integer-only, so there is no floating-point drift.
* *Local and distributed buckets with the same API.* A local bucket lives in the JVM. A distributed bucket lives in Redis, a
  database or a data grid and is reached through a `ProxyManager`, so that every replica of a service sees the same
  tokens. Application code does not change between the two.
* *Several limits per bucket.* One bucket can enforce an hourly quota and a per-second burst guard at once; see
  xref:backend/resilience/bucket4j-token-bucket-and-bandwidths.adoc[token bucket and bandwidths].
* *Many consumption styles.* Non-blocking (`tryConsume`), blocking (`asBlocking()`), scheduled (`asScheduler()`), probing
  (`tryConsumeAndReturnRemaining`) and diagnostic (`asVerbose()`); see
  xref:backend/resilience/bucket4j-bucket-api.adoc[the Bucket API].

It is a rate limiter, not a resilience toolkit. It does not retry, break circuits or isolate threads; Resilience4j does that,
and the section explains how the two fit together on xref:backend/resilience/resilience4j-vs-bucket4j.adoc[Resilience4j vs Bucket4j].

== When to use it

* *API quotas by plan.* The free plan of the *Bookshelf* API gets 20 requests per minute per API key, a pro plan 200 and a
  partner plan 2000. One bucket per key, with a configuration chosen by plan.
* *Abuse and DoS mitigation.* Per-IP or per-account buckets on login, password reset and search endpoints.
* *A shared third-party quota.* The ISBN-metadata provider allows a fixed number of calls per day for the whole
  company. A bucket in Redis, shared by every replica, keeps the sum under that number, which an in-process limiter cannot
  do.
* *Notification throttling.* At most so many e-mails or push messages per user per hour.
* *Billing plans and fair use.* Heavy operations cost more tokens: a search costs five tokens, a lookup costs one.

When the limit must hold per JVM only, and the only goal is to protect one call from overload, the Resilience4j
`RateLimiter` described in xref:backend/resilience/rate-limiter.adoc[RateLimiter] is enough. Bucket4j is the right tool when the limit
is per key, shared between instances, or needs a real token-bucket shape.

== The 8.21.0 modules

Bucket4j is published under the group id `com.bucket4j`; the Java package is `io.github.bucket4j`. Since 8.11.1 every
artifact name carries the minimum Java version, `bucket4j_jdk17-*`. The table lists everything that 8.21.0 publishes
for Java 17 and later. A distributed bucket needs the core module plus one backend module. Redis needs two: `redis-common`
and one client module.

The BOM manages the core, `redis-common`, the five Redis clients, the JDBC modules, `jcache`, `ignite`, `ignite3`,

(`redis`, `hazelcast-all`, `infinispan-all`) stop at 8.14.0 and are not part of 8.21.0. The backend table, with each
builder entry point and its atomicity model, is on xref:backend/resilience/bucket4j-backends.adoc[Bucket4j backends].

== Adding the dependency

Import the BOM once and declare the modules without versions. Spring Boot does not manage Bucket4j, so there is no
other place that pins the version.

.pom.xml with the BOM and the core module
[source,xml]
----
<dependencyManagement>
    <dependencies>
        <dependency>
            <groupId>com.bucket4j</groupId>
            <artifactId>bucket4j_jdk17-bom</artifactId>
            <version>8.21.0</version>
            <type>pom</type>
            <scope>import</scope>
        </dependency>
    </dependencies>
</dependencyManagement>

<dependencies>
    <dependency>
        <groupId>com.bucket4j</groupId>
        <artifactId>bucket4j_jdk17-core</artifactId>
    </dependency>
</dependencies>
----

Source: https://bucket4j.com/8.21.0/toc.html#adding-the-bucket4j-dependency[Bucket4j reference: Adding the Bucket4j dependency].
The reference shows a plain dependency with a version and does not mention the BOM, which first appeared in 8.21.0; the
module list is in the https://github.com/bucket4j/bucket4j/tree/8.21.0/bucket4j-bom[`bucket4j-bom` module of the 8.21.0 tag].

.build.gradle.kts with the BOM and the core module
[source,kotlin]
----
dependencies {
    implementation(platform("com.bucket4j:bucket4j_jdk17-bom:8.21.0"))
    implementation("com.bucket4j:bucket4j_jdk17-core")
}
----

Source: https://bucket4j.com/8.21.0/toc.html#adding-the-bucket4j-dependency[Bucket4j reference: Adding the Bucket4j dependency].

A distributed *Bookshelf* adds the backend modules. The Maven form for Redis with the Lettuce client, which Spring Boot
already brings, is:

.Backend modules for a Redis-backed bucket
[source,xml]
----
<dependency>
    <groupId>com.bucket4j</groupId>
    <artifactId>bucket4j_jdk17-redis-common</artifactId>
</dependency>
<dependency>
    <groupId>com.bucket4j</groupId>
    <artifactId>bucket4j_jdk17-lettuce</artifactId>
</dependency>
----

Source: https://bucket4j.com/8.21.0/toc.html#bucket4j-lettuce[Bucket4j reference: bucket4j-lettuce].

== A first local bucket for the Bookshelf API

The smallest useful limiter keeps one bucket per API key in a `ConcurrentHashMap`. This is a local limiter: every instance of the
service has its own map, so a client that talks to three replicas gets three times the quota. The distributed version
is the subject of xref:backend/resilience/bucket4j-distributed-rate-limiting.adoc[distributed rate limiting].

.A local per-key limiter
[source,java]
----
import io.github.bucket4j.Bucket;

import java.time.Duration;
import java.util.concurrent.ConcurrentHashMap;
import java.util.concurrent.ConcurrentMap;

public class LocalPlanLimiter {

    private final ConcurrentMap<String, Bucket> buckets = new ConcurrentHashMap<>();

    public boolean allow(String apiKey, long requestsPerMinute) {
        Bucket bucket = buckets.computeIfAbsent(apiKey, key -> Bucket.builder()
                .addLimit(limit -> limit.capacity(requestsPerMinute)
                        .refillGreedy(requestsPerMinute, Duration.ofMinutes(1)))
                .build());
        return bucket.tryConsume(1);
    }
}
----

Source: https://bucket4j.com/8.21.0/toc.html#bucket[Bucket4j reference: Bucket] and
https://bucket4j.com/8.21.0/toc.html#local-bucket-builder[Local bucket builder].

Running the class with the free plan (20 per minute) and 25 calls in a row for one key lets exactly 20 through and
refuses 5; a second key starts with its own full bucket. Three details are worth reading closely:

* `capacity` is the bucket size, and a new bucket starts full. A client may therefore send 20 requests at once, not 20
  spread over the minute. Spreading is the job of the refill and of a second bandwidth, covered on the next page.
* `refillGreedy(20, Duration.ofMinutes(1))` adds one token every three seconds, not 20 tokens once a minute.
* The map never forgets a key. With millions of anonymous callers it is a memory leak, which is one of the reasons the
  production setup keeps buckets in a bounded cache or in Redis, with an expiration.

Refusing with a hint about when to retry needs the probe variant. A rejected probe tells how long to wait:

.Reading the wait time of a rejected request
[source,java]
----
Bucket bucket = Bucket.builder()
        .addLimit(limit -> limit.capacity(20).refillGreedy(20, Duration.ofMinutes(1)))
        .build();
bucket.tryConsume(20);

ConsumptionProbe probe = bucket.tryConsumeAndReturnRemaining(1);
// probe.isConsumed() is false, getNanosToWaitForRefill() is 3_000_000_000 (3 seconds)
----

Source: https://bucket4j.com/8.21.0/toc.html#limiting-the-rate-of-access-to-a-rest-api[Bucket4j reference: Limiting the rate of access to a REST API].
Turning that value into an HTTP 429 with `Retry-After` is shown in the sequence diagram on xref:backend/resilience/bucket4j-bucket-api.adoc[the Bucket API page].

The diagram reads left to right. The core module gives you both worlds; the backends only appear once you need a
bucket that lives outside the JVM. The Spring integrations at the right are three ways to put those buckets in front of
HTTP traffic: your own filter, the community starter that generates the filter from YAML, and the Spring Cloud Gateway
filters, which keep their buckets in an `AsyncProxyManager` (typically Caffeine for a single gateway, or a Redis-backed
manager for several).

== The ecosystem

*The Spring Boot starter.* `bucket4j-spring-boot-starter`, with the group id `com.giffing.bucket4j.spring.boot.starter`,
wraps Bucket4j in Spring Boot auto-configuration: you declare filters and bandwidths in `application.yml` and the starter
builds the servlet or WebFlux filter. It is a *community project* maintained under the `MarcGiffing` GitHub account, not by the Bucket4j
project or by Spring, and its release cadence and Spring Boot support are its own. Bucket4j's README recommends it in its
Spring Boot starter section. The starter has two relevant lines at the time of writing: 0.14.0 (2026-02-28, Spring
Boot 4.0.3, Bucket4j 8.15.0) and the pre-release 0.20.0-RC1 (2026-09-11, Spring Boot 4.1.1, Bucket4j 8.17.0),
which is published to Maven Central only and changes the module layout. Both are covered on
xref:backend/resilience/bucket4j-spring-boot-starter.adoc[the starter page], which also says which one the examples use. The alternative
that needs no third-party starter, a filter you write yourself, is on
xref:backend/resilience/bucket4j-spring-boot-manual-integration.adoc[manual Spring Boot integration].

*Spring Cloud Gateway.* Spring Cloud Gateway 5.0.x ships a Bucket4j rate limiter for the Web MVC server
(`Bucket4jFilterFunctions.rateLimit`) and for the WebFlux server (an argument to `RequestRateLimiter`). Bucket4j is an
optional dependency there: you add it yourself, and the gateway build uses 8.15.0, so import the 8.21.0 BOM to align it.
See xref:backend/resilience/bucket4j-spring-cloud-gateway.adoc[Bucket4j in Spring Cloud Gateway].

*Commercial Java 8 builds.* The open-source artifacts for Java 8 stop at 8.10.1. The project offers later Java 8
builds commercially; see the "Java compatibility" page linked in the references. Nothing in this section needs them.

*Version 9.* A 9.x line has open milestones on GitHub but is not released. Under the project's backward-compatibility policy,
deprecated API is removed only in a major release, so everything in this section that avoids deprecated API should carry
over. The deprecations that exist today, and the discrepancies between the reference and the 8.21.0 code, are collected on
xref:backend/resilience/bucket4j-migration-and-whats-changed.adoc[migration and what's changed].
