Every Resilience4j instance in a Spring Boot service is described in `application.yml`, under a handful of `resilience4j.*`
prefixes: a `default` configuration, optional named configurations, and one entry per instance. This page is the reference
for that file. It covers the complete structure, every property of every module with its default, how an instance's
effective configuration is resolved, the settings that exist only in Spring Boot, how `XxxConfigCustomizer` beans override
the YAML, and how profiles, SpEL names and `@RefreshScope` interact with it. It closes with the complete *Bookshelf*
configuration. The semantics of each property are on the module pages
(xref:backend/resilience/circuit-breaker.adoc[CircuitBreaker],
xref:backend/resilience/retry.adoc[Retry],
xref:backend/resilience/rate-limiter.adoc[RateLimiter],
xref:backend/resilience/bulkhead.adoc[Bulkhead] and
xref:backend/resilience/time-limiter.adoc[TimeLimiter]); the registry model behind the file is in
xref:backend/resilience/registries-configuration-and-decorators.adoc[Registries, Configuration & Decorators].

The page was written against Resilience4j 2.4.0 (released 14 March 2026), Spring Boot 4.1.1, Spring Framework 7.0.x and Java 21
and verified on 4 October 2026. Every YAML file and Java class below was bound and run in a sample project, and the same
suite was repeated on Spring Boot 3.5.16 with `resilience4j-spring-boot3` 2.4.0. The property keys and their behaviour are the
same on both lines. Two things differ and are called out where they matter: the Java package of the property classes
(`io.github.resilience4j.springboot` on Boot 4, `io.github.resilience4j.springboot3` on Boot 3), and the `@RefreshScope`
registries, which only the Boot 4 starter ships.

== How the starter reads the configuration

The starter registers one `@ConfigurationProperties` bean per prefix. Each is a thin class in `resilience4j-spring-boot4`
that extends a class in `resilience4j-spring6` (which adds the aspect order) that extends a `Common...ConfigurationProperties`
class in `resilience4j-framework-common`. The common class holds everything interesting: the two maps `configs` and
`instances`, the validation in the setters, the inheritance rules and the code that turns properties into a `XxxConfig`.
That is why the Boot 3 and Boot 4 starters behave identically.

The prefixes were read from the `@ConfigurationProperties` annotations and from the `spring-configuration-metadata.json` inside
the published `resilience4j-spring-boot4-2.4.0.jar`.

At startup the module's `XxxConfiguration` in `resilience4j-spring6` turns those properties into a registry, in this order:

* every entry under `configs` is built into a `XxxConfig` and added to the registry as a *named configuration*; the entry called
  `default` becomes the registry's default configuration;
* every entry under `instances` is built into a `XxxConfig` and the instance is created in the registry under its name;
* every `XxxConfigCustomizer` bean whose name is not already a configuration and not already created gets an instance of its
  own (see <<_customizers,Customizers>>);
* each instance is wired to an event consumer whose buffer holds `eventConsumerBufferSize` events (default 100).

An instance that appears in no YAML and no customizer is created later, on its first use by an annotation, from a named
configuration or the default one. The diagram follows one instance through both paths.

Read the first chain as the startup path and the second as the runtime path. The YAML path is a pipeline of layers, each
overriding only the keys it sets. The runtime path never reads `instances`; it asks the registry, which is why an annotation
with a new name (or a SpEL-computed one) silently gets the `default` configuration and never an `instances` entry that you
forgot to rename. Source: https://github.com/resilience4j/resilience4j/blob/v2.4.0/resilience4j-spring6/src/main/java/io/github/resilience4j/spring6/circuitbreaker/configure/CircuitBreakerConfiguration.java[`CircuitBreakerConfiguration`]
(startup) and the https://github.com/resilience4j/resilience4j/blob/v2.4.0/resilience4j-spring6/src/main/java/io/github/resilience4j/spring6/circuitbreaker/configure/CircuitBreakerAspect.java[`CircuitBreakerAspect`]
(runtime) at v2.4.0; the other modules follow the same pattern.

=== Where an instance starts from

The common classes differ in one important place, and the readme.io page does not say so. Each row below was confirmed by
running a YAML file and reading the effective configuration back from the registry.

[cols="2,4,4",options="header"]
.What an instance inherits, per module
|===
|Module |No `baseConfig` on the instance |`baseConfig` names a configuration

|CircuitBreaker
|Starts from `configs.default` if it exists, otherwise from the builder defaults. An instance whose name is also the name of a configuration starts from that configuration.
|Starts from *that configuration only*. `configs.default` is not applied to it, nor to the configuration it names (in the run below, `minimumNumberOfCalls: 10`, set only in `default`, did not reach `pricing`). A named configuration may itself name a `baseConfig`.

|Retry, RateLimiter, Bulkhead, ThreadPoolBulkhead, TimeLimiter, Timer
|Starts from `configs.default` if it exists, otherwise from the builder defaults.
|Starts from that configuration, which is itself built on top of `configs.default`. The default is always the root of the chain (an instance with `baseConfig: slow` took `limitForPeriod` from `default` and `limitRefreshPeriod` from `slow`).
|===

Source: https://github.com/resilience4j/resilience4j/blob/v2.4.0/resilience4j-framework-common/src/main/java/io/github/resilience4j/common/circuitbreaker/configuration/CommonCircuitBreakerConfigurationProperties.java[`CommonCircuitBreakerConfigurationProperties.createCircuitBreakerConfig`]
and https://github.com/resilience4j/resilience4j/blob/v2.4.0/resilience4j-framework-common/src/main/java/io/github/resilience4j/common/retry/configuration/CommonRetryConfigurationProperties.java[`CommonRetryConfigurationProperties.createRetryConfig`]

The next file makes the difference concrete. It has one `default`, one named configuration `critical`, and instances that use
them in the three ways.

.layers.yml: the same shape, resolved differently for each instance
[source,yaml]
----
resilience4j:
  circuitbreaker:
    configs:
      default:                                  # the base of every breaker that names no baseConfig
        slidingWindowSize: 20
        minimumNumberOfCalls: 10
        failureRateThreshold: 50
        waitDurationInOpenState: 30s
        registerHealthIndicator: true           # Boot only
      critical:                                 # a shared, named configuration
        slidingWindowSize: 10
        failureRateThreshold: 25
        waitDurationInOpenState: 10s
        enableExponentialBackoff: true
        exponentialBackoffMultiplier: 2
    instances:
      pricing:
        baseConfig: critical
        failureRateThreshold: 20                # wins over critical
      isbn:
        baseConfig: critical
        waitDurationInOpenState: 15s            # replaces the wait of critical, and drops its backoff
      reviews: {}                               # no baseConfig: starts from default
  retry:
    configs:
      default:
        maxAttempts: 3
        waitDuration: 200ms
        enableExponentialBackoff: true
        exponentialBackoffMultiplier: 2
      patient:
        maxAttempts: 5
    instances:
      isbn:
        baseConfig: patient                     # patient is built on top of default
        waitDuration: 1s
----

syntax) and the common classes above. Bound and run on Spring Boot 4.1.1 (JDK 21); the effective values read back from the
registries are in the table.

[cols="2,3,3,3",options="header"]
.Effective configuration read back from the registries
|===
|Instance |Window / minimum calls / failure rate |Open-state waits (1st, 2nd, 3rd) |Why

|`pricing`
|10 / *100* / 20
|10 s, 20 s, 40 s
|Starts from `critical`: its window, wait and exponential backoff apply, the instance's `failureRateThreshold: 20` wins. `minimumNumberOfCalls: 10` from `default` is *not* applied, so the built-in 100 stays.

|`isbn`
|10 / *100* / 25
|15 s, 15 s, 15 s
|Overriding `waitDurationInOpenState` replaces the wait of `critical` and, because the CircuitBreaker's backoff flags are not inherited, also drops its exponential backoff.

|`reviews`, and any instance not in the file
|20 / 10 / 50
|30 s, 30 s, 30 s
|No `baseConfig`: `default` applies.
|===

Two further observations from the same run. First, the *Boot-only* property `registerHealthIndicator: true` that sits in
`default` reached all four breakers, including `pricing` and `isbn`, which do not inherit `default`'s other keys: Boot-only
properties are merged separately (see <<_boot_only_properties,Boot-only properties>>). Second, the Retry module behaves the
other way round on backoff. In the same file, the Retry instance `isbn` that sets only `waitDuration: 1s` and
`baseConfig: patient` waited 1 s, 2 s and 4 s and made five attempts: `maxAttempts` came from `patient`, and the exponential
flags came from `default`, which Retry always merges in. The Retry merge carries `enableExponentialBackoff`,
`enableRandomizedWait`, `exponentialBackoffMultiplier` and `exponentialMaxWaitDuration`; the CircuitBreaker merge carries none of
them. The Retry merge has one gap: `randomizedWaitFactor` is not carried. With a default of `waitDuration: 100ms`,
`enableRandomizedWait: true` and `randomizedWaitFactor: 0.1`, an instance that inherited all three drew waits between 90 ms and
110 ms, and an instance that overrode only `waitDuration: 1000ms` drew waits between 500 ms and 1500 ms, that is the built-in
factor of 0.5.

A `baseConfig` that names no configuration fails the startup with `ConfigurationNotFoundException: Configuration with name 'x'
does not exist`. An instance that names itself fails with `IllegalStateException: Circular reference detected in instance
config`. A longer cycle, a configuration naming another that names the first, is not detected and ends in a `StackOverflowError`
(reproduced for CircuitBreaker and Retry), so keep `baseConfig` chains short and acyclic.

== The complete YAML structure

read, not a file to copy: the defaults are what you get without it. Keys that are Boot-only carry a comment. A few values are
illustrative because they have no fixed default: the two thread-pool sizes (they depend on the number of CPUs), the class names,
the `team` tag and the scheduled executor's `corePoolSize`. The three `reference-*` instances show the keys that only make sense
in combination (exponential backoff, randomized wait, predicate classes). Binding this exact file and reading the effective
configuration back gave the same values as the `ofDefaults()` of `CircuitBreakerConfig`, `RetryConfig`, `RateLimiterConfig`,
`BulkheadConfig`, `TimeLimiterConfig` and `TimerConfig`, and for the thread-pool bulkhead the same queue capacity and keep-alive.

Three details of the structure are worth knowing before you write your own.

* *Property names are relaxed.* `slidingWindowSize`, `sliding-window-size` and `SLIDING_WINDOW_SIZE` (as an environment
  variable) are the same key. The examples use camelCase because that is how the Resilience4j documentation writes the
  keys; the run also bound the kebab-case spelling given as a command-line argument over the camelCase one in the file.
* *Instance and configuration names are map keys.* Keep them lower-case with hyphens (`isbn-metadata`) or camelCase
  (`pricingFail`) in YAML, but see <<_names_in_environment_variables,environment variables>> for what happens to them there.
* *Legacy aliases still bind.* `resilience4j.circuitbreaker.backends`, `resilience4j.retry.backends`,
  `resilience4j.bulkhead.backends`, `resilience4j.thread-pool-bulkhead.backends` and `resilience4j.ratelimiter.limiters` are
  the same map as `instances` (the `getBackends()` and `getLimiters()` getters return it). The TimeLimiter and Timer prefixes
  have no alias. Use `instances` in new files.

=== Names in environment variables

Environment variables are upper-cased and cannot contain hyphens, so they address the *lower-case* key. In a run with
`RESILIENCE4J_CIRCUITBREAKER_INSTANCES_PRICING_FAILURERATETHRESHOLD=55` the `pricing` instance took the value. An instance
called `pricingFail` in the YAML, set through `RESILIENCE4J_CIRCUITBREAKER_INSTANCES_PRICINGFAIL_SLIDINGWINDOWSIZE`, took the
value *and* an extra instance called `pricingfail` appeared in the registry. A variable for the hyphenated instance
`isbn-metadata` (`..._ISBN_METADATA_SLIDINGWINDOWSIZE`) was ignored. The practical rules are to give instances single-word
lower-case names when they must be overridable from the environment, and to override long-lived values in the YAML or through
a configuration server rather than through the process environment. Source:
https://docs.spring.io/spring-boot/reference/features/external-config.html[Spring Boot reference: Externalized Configuration].

=== Unknown keys are ignored

Spring Boot ignores keys it cannot bind, and Resilience4j adds no validation. A misspelled key (`failureRateTreshold`), a
misspelled prefix (`resilience4j.circuitbreakr`) and a key that does not exist in the starter all start the application and
leave the default in place. The run printed `rate=50.0` for an instance configured with `failureRateTreshold=10`. Section
<<_property_reference,Property reference>> lists the keys that exist; the next section lists the ones that people expect and
that do not.

=== Settings that have no YAML key

Several builder settings have no Spring Boot property in 2.4.0, and setting them in YAML does nothing. Use a customizer

== Durations

Every duration property is a `java.time.Duration` converted by Spring Boot, so the usual formats work, and the unit of a bare
number is *milliseconds*. The table lists what was bound for `resilience4j.retry.instances.x.waitDuration` and read back from
the interval function; the same converter serves every duration key.

[cols="2,3,4",options="header"]
.Duration formats accepted by the binder
|===
|Value in YAML |Result |Note

|`500ms`, `5s`, `2m`, `1h`, `1d`
|500 ms, 5 s, 2 min, 1 h, 1 day
|The simple style: a number and one of `ns`, `us`, `ms`, `s`, `m`, `h`, `d`. Case does not matter (`500MS` worked).

|`PT0.5S`, `PT1M30S`
|500 ms, 90 s
|The ISO-8601 style.

|`5000`
|5000 ms, that is 5 s
|A bare number is milliseconds. The readme.io example `waitDurationInOpenState: 10000` therefore means 10 seconds. Prefer a suffix.

|`0`
|0
|Valid where zero makes sense: RateLimiter `timeoutDuration`, Bulkhead `maxWaitDuration`, `maxWaitDurationInHalfOpenState`, Retry `waitDuration`.

|`1.5s`, `5 s`
|Startup failure: `'1.5s' is not a valid duration`
|No fractions in the simple style (use `1500ms`) and no spaces.

|`100us`, `1500000ns`
|0 ms and 1 ms for Retry
|Retry and the open-state waits keep milliseconds, so finer values are truncated. RateLimiter keeps nanoseconds: its default `limitRefreshPeriod` is 500 ns.

== Exception, predicate and other class names

Seven kinds of property hold a class name. YAML gives them as fully qualified names, a list for the arrays, and Spring Boot's
`Class` conversion loads them at startup.

[cols="3,3,4",options="header"]
.Properties that take a class
|===
|Property |Type the class must have |Requirements

|`recordExceptions`, `ignoreExceptions` (CircuitBreaker), `retryExceptions`, `ignoreExceptions` (Retry)
|a list of `Throwable` subclasses
|Fully qualified names. `Outer$Inner` and `Outer.Inner` both resolved for a nested class. The class must exist: a typo fails the startup with `ClassNotFoundException`. The type is not checked: `java.lang.String` was accepted, and simply never matches.

|`recordFailurePredicate`, `ignoreExceptionPredicate` (CircuitBreaker), `retryExceptionPredicate` (Retry)
|`Predicate<Throwable>`
|A *public* class with a *public no-argument constructor*. It is created by reflection, not by Spring: it is not a bean, nothing is injected into it, and it is shared by every call.

|`recordResultPredicate` (CircuitBreaker), `resultPredicate` (Retry)
|`Predicate<Object>`
|The same requirements.

|`consumeResultBeforeRetryAttempt` (Retry)
|`BiConsumer<Integer, Object>`
|The same requirements. The attempt number comes first, then the result.

|`intervalBiFunction` (Retry)
|`IntervalBiFunction<Object>`
|The same requirements. It overrides the backoff keys.

|`contextPropagators` (ThreadPoolBulkhead, and `resilience4j.scheduled.executor`)
|a list of `ContextPropagator`
|A no-argument constructor. YAML entries and `ThreadPoolBulkheadConfigCustomizer` entries are added together.

|`onFailureTagResolver` (Timer)
|`Function<Throwable, String>`
|The same requirements as a predicate.
|===

(`getConstructor().newInstance()`) and the `InstanceProperties` types. Each outcome in the table was produced on Spring Boot

A wrong class fails fast, and with different messages: a class that does not exist gives `ClassNotFoundException`; a predicate
without a public no-argument constructor gives `NoSuchMethodException: ...<init>()` (a package-private class is the same);
a class that is not a `Predicate` gives `ClassCastException`. The `ignoreClassBindingExceptions` property does *not* soften the
first of them in 2.4.0 (see <<_boot_only_properties,Boot-only properties>>). Because a predicate is built from a class name,
logic that needs a Spring bean, a feature flag or the request has to move to a customizer (next section) or into the
decorated method itself.

[source,java]

== Boot-only properties

A few properties do not belong to any `XxxConfig`. They configure what the starter builds *around* an instance: health
indicators, event buffers, tags, metrics, aspect order. They live in the same `instances` and `configs` entries (the per-instance
ones) or next to them (the per-prefix ones).

[cols="3,2,2,5",options="header"]

|===
|Property |Where |Default |Effect

|`registerHealthIndicator`
|CircuitBreaker, RateLimiter instances
|`false`

|`allowHealthIndicatorToFail`
|CircuitBreaker, RateLimiter instances
|`false`

How these properties are inherited is different from the builder properties, and it is implemented in `mergePropertiesIfAny`.
That method copies a Boot-only value into the instance when the instance does not set it, first from the `baseConfig`'s entry
and then from `configs.default`. It is the reason `registerHealthIndicator: true` in `default` reached every breaker in the

`allowHealthIndicatorToFail`, `eventConsumerBufferSize` and `ignoreClassBindingExceptions`; for RateLimiter the same plus
`subscribeForEvents`; for Retry `eventConsumerBufferSize` and the four backoff keys; and `eventConsumerBufferSize` only for

(`resilience4j.circuitbreaker.instances` and `.configs` are listed as `Map<String, InstanceProperties>`), the per-prefix keys and
the Actuator `access` and `cache.time-to-live` keys, but a map value type is not expanded into per-key completion, so
`slidingWindowSize` under an instance is not offered. Use the tables on this page.

== Customizers

YAML cannot express everything: a `Clock`, a lambda, a bean from the application context, or one of the settings in the
<<_settings_that_have_no_yaml_key,table above>>. For those the starter looks for beans of the module's customizer type and calls
them with the `Builder` while it builds the configuration. There is one interface per module:
`CircuitBreakerConfigCustomizer`, `RetryConfigCustomizer`, `RateLimiterConfigCustomizer`, `BulkheadConfigCustomizer`,
`ThreadPoolBulkheadConfigCustomizer`, `TimeLimiterConfigCustomizer` and `TimerConfigCustomizer`. Each has a `name()` and a
`customize(Builder)` method, and a static `of(name, consumer)` factory for the common case. The readme.io page lists six of the
seven; the Timer one exists in 2.4.0.

.A customizer that gives the pricing breaker the application's clock
[source,java]
----
package com.example.bookshelf;

import io.github.resilience4j.common.circuitbreaker.configuration.CircuitBreakerConfigCustomizer;
import java.time.Clock;
import org.springframework.boot.autoconfigure.condition.ConditionalOnMissingBean;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

@Configuration(proxyBeanMethods = false)
public class BookshelfResilienceConfig {

    @Bean
    @ConditionalOnMissingBean
    Clock clock() {
        return Clock.systemUTC();
    }

    @Bean
    CircuitBreakerConfigCustomizer pricingBreakerClock(Clock clock) {
        // the TIME_BASED window of "pricing" now reads the application's Clock bean,
        // which a test replaces with a fixed or manually advanced clock
        return CircuitBreakerConfigCustomizer.of("pricing", builder -> builder.clock(clock));
    }
}
----

Source: https://resilience4j.readme.io/docs/getting-started-3[Resilience4j: Spring Boot 2 & 3] (the customizer example) and
https://github.com/resilience4j/resilience4j/blob/v2.4.0/resilience4j-framework-common/src/main/java/io/github/resilience4j/common/circuitbreaker/configuration/CircuitBreakerConfigCustomizer.java[`CircuitBreakerConfigCustomizer` at v2.4.0].
Compiled and run on Spring Boot 4.1.1 and 3.5.16: with a fixed `Clock` bean in a test, the breaker read back from the registry
held that clock. Spring Boot defines no `Clock` bean, hence the `@ConditionalOnMissingBean` default.

The rules, each verified by a run:

* *The name selects what is customized.* The name is an instance name *or a configuration name*. A customizer named `default`
  changes the default configuration and therefore every instance that inherits it; one named like a `configs` entry changes that
  configuration for the instances that use it. In a run, a customizer named `default` set `minimumNumberOfCalls(8)` and both an
  instance with `baseConfig: default` and an unlisted instance reported 8; a customizer for the configuration `strict` reached an
  instance with `baseConfig: strict`.
* *The customizer runs last and wins.* It receives the builder after the YAML values were applied. With the YAML saying
  `failureRateThreshold: 45`, a command-line argument saying 60 and the customizer saying 20, the effective value was 20.
* *A customizer can create an instance.* If its name is neither a configuration nor an instance already created, the starter
  creates an instance of that name at startup (a customizer for `ghost` made `registry.find("ghost")` non-empty before any call).
* *One customizer per name and module.* Two beans for the same name fail the startup with `IllegalStateException: It is not
  possible to define more than one customizer per instance name pricing`. Put all the changes for a name in one bean.
* *Lists add up.* `ThreadPoolBulkheadConfigCustomizer` appends to the `contextPropagators` from YAML; it does not replace them.

Source: https://github.com/resilience4j/resilience4j/blob/v2.4.0/resilience4j-framework-common/src/main/java/io/github/resilience4j/common/CompositeCustomizer.java[`CompositeCustomizer`]
(one per name), the `buildConfig` methods (the customizer runs after the property keys), and `initCircuitBreakerRegistry` in
https://github.com/resilience4j/resilience4j/blob/v2.4.0/resilience4j-spring6/src/main/java/io/github/resilience4j/spring6/circuitbreaker/configure/CircuitBreakerConfiguration.java[`CircuitBreakerConfiguration`]
at v2.4.0. The 2.4.0 release includes the fix to the order in which customizers are applied in the Boot 3 starter (PR 2321,
a port of an older Boot 2 fix).

The customizers below set what has no YAML key. They are compiled and applied in the same run: the circuit breaker read back
`LOCK_FREE`, the retry read back waits of 100 ms and 200 ms, the bulkhead read back a non-fair strategy.

A customizer is an ordinary bean, so a profile can switch it (`@Profile("test")`) and it can take collaborators as constructor
or method arguments, which a class named in YAML cannot. The registry is built from the customizers,
so a customizer cannot inject the registry: the run failed with `BeanCurrentlyInCreationException` (an unresolvable circular
reference).

== Precedence

Two separate orderings apply, and it helps not to mix them. The first is Spring Boot's: which *property source* provides the
value of a key. The second is Resilience4j's: which *layer* of a configuration provides a setting once the keys are known.

=== Which property source wins

Spring Boot merges every source into one environment before the starter reads it, so the usual order applies, from weakest to
strongest: the packaged `application.yml`, the packaged profile files, `application.yml` files outside the jar and their
profile files, OS environment variables, JVM system properties, `SPRING_APPLICATION_JSON` and command-line arguments. A value
imported with `spring.config.import` (a Spring Cloud Config Server, a mounted file, a config tree) takes the position of the
file that imports it, with its own profile variants after it. The runs confirmed that a command-line argument beats the YAML
(`--...failure-rate-threshold=60` over `failureRateThreshold: 45`, even in a different spelling), that a system property beats
the YAML, and that an environment variable beats the YAML. Source:
https://docs.spring.io/spring-boot/reference/features/external-config.html#features.external-config.order[Spring Boot reference: Externalized Configuration, order].

=== Which layer wins

[cols="1,3,4",options="header"]
.Layers of one instance's configuration, weakest first
|===
|Layer |Source |Notes

|1
|The builder defaults of the module (`XxxConfig.custom()`)
|For example a 100-call window and a 5 s limiter timeout. The table in <<_property_reference,Property reference>> lists them.

|2
|`configs.default`
|Applies to every instance of the module that does not name a `baseConfig` (and, except for the CircuitBreaker, as the root of every `baseConfig` chain).

|3
|`configs.<baseConfig>`, following its own `baseConfig` chain
|Replaces `configs.default` for the CircuitBreaker.

|4
|`instances.<name>`
|Only the keys that are present.

|5
|The `XxxConfigCustomizer` named after the instance, applied after each level
|The customizer for `default` runs when the default is built, the one for a `baseConfig` when that configuration is built, and the one for the instance last. A command-line value does not beat it.

|6
|`@CircuitBreaker(configuration = "x")` and the other annotations' `configuration` attribute
|Not a layer of the YAML: it chooses *which registry configuration* a not-yet-existing instance is created from. It never changes an existing instance.
|===

Source: the `buildConfig` and `createXxxConfig` methods of the `Common...ConfigurationProperties` classes at v2.4.0, the six
aspects (`configKey = annotation.configuration().isEmpty() ? name : annotation.configuration()`), and the runs described in this
page. Registering a configuration for an instance that already exists does nothing: `registry.circuitBreaker(name, config)`
returns the existing instance and ignores the new configuration, as shown on the
xref:backend/resilience/registries-configuration-and-decorators.adoc[Registries, Configuration & Decorators] page.

== Profiles

Profiles are a Spring Boot feature, and Resilience4j needs nothing special: a profile-specific file or a profile-activated
document is one more property source, merged before the starter reads the properties. The general mechanics are on the
xref:backend/springboot/configuration-and-profiles.adoc[Configuration & Profiles] page; what follows is the Resilience4j side
of it. The practical use is to keep the production values in `application.yml` and to override only what a test or a laptop
needs: tiny windows and waits so a test can open a breaker with four calls (see
xref:backend/resilience/testing.adoc[Testing Resilience]), or breakers that never open while you debug.

The multi-document form keeps the profile in the same file. This file was run with and without the `test` profile: the wait
was 200 ms, then 1 ms.

.One file, two documents: the second applies only with the test profile
[source,yaml]
----
resilience4j:
  retry:
    configs:
      default:
        maxAttempts: 3
        waitDuration: 200ms
---
spring:
  config:
    activate:
      on-profile: test
resilience4j:
  retry:
    configs:
      default:
        waitDuration: 1ms
----

Source: https://docs.spring.io/spring-boot/reference/features/profiles.html[Spring Boot reference: Profiles] and
https://docs.spring.io/spring-boot/reference/features/external-config.html#features.external-config.files.multi-document[Multi-document files].
Run on Spring Boot 4.1.1 with `--spring.profiles.active=test`.

Four things go wrong in practice, and each one was reproduced.

* *An instance value beats a profile's `default`.* A test profile that shortens `configs.default.waitDurationInOpenState` does
  not reach an instance that sets its own wait. In the Bookshelf run, `isbn` kept its jittered 10 s wait under a profile that
  had set `default` to 100 ms, until the profile also overrode the instance. Override at the same level the production file
  sets the value.
* *A list replaces the whole list.* A profile that sets `recordExceptions` for `pricing` to one class made the breaker stop
  recording the two classes of the base file (the run showed `IOException` recorded without the profile and not recorded with it).
  Repeat every element you want to keep.
* *The `access` or exposure keys travel with the profile too.* Keep `management.endpoint.circuitbreakers.access: read-only`
  in the base file so that no profile can quietly re-enable the write operation.
* *Do not branch on the profile in Java.* A customizer that checks `environment.acceptsProfiles("test")` hides the difference
  from the YAML. Make the difference a property.

The two profile files of the Bookshelf configuration are in <<_the_bookshelf_configuration,the last section>>.

== SpEL instance names

The `name` of every Resilience4j annotation can be computed. The aspect passes the string to a `SpelResolver` before it asks
the registry, and the resolver recognizes three shapes; anything else is used literally. The same resolver also handles the
`fallbackMethod` attribute, so a fallback name can be a placeholder too.

[cols="3,3,4",options="header"]
.Name expressions, as run
|===
|Expression in `name` |Resolved to |Rule

|`${bookshelf.resilience.pricing-instance:pricing}`
|`pricing-v2` (the value in the Environment)
|A whole-string placeholder (also `#{...}`) is resolved through the embedded value resolver, which supports `${key:default}`. The key does not have to be in the Resilience4j prefix.

|`#tenant.tier`, `#isbn`, `#p0`, `#root.args[0]`
|`gold`, the ISBN, the first argument, the first argument
|A string that starts with `#` is evaluated as SpEL against the method arguments. Parameter names need the `-parameters` compiler flag (Spring Boot's Maven parent and Gradle plugin set it); `#p0` and `#root.args[0]` do not.

|`#root.methodName`, `#root.className`
|`search`, `com.example.bookshelf.SpelNames`
|`#root` exposes `methodName`, `className` and `args`.

|`@instanceNames.forIsbn(#isbn)`
|`isbn-978`
|A string that starts with `@` is a SpEL expression that can call a bean, with the method arguments available.

|`'literal-' + #isbn`
|`'literal-' + #isbn`, literally
|An expression must *start* with `#` or `@` to be evaluated. This one became the instance name, quotes and all.

|`#isbn.length()`
|`ClassCastException` on every call
|The expression must return a `String`.
|===

.Annotations that compute their instance name
[source,java]
----
package com.example.bookshelf;

import io.github.resilience4j.circuitbreaker.annotation.CircuitBreaker;
import io.github.resilience4j.ratelimiter.annotation.RateLimiter;
import org.springframework.stereotype.Component;

@Component
public class SpelNames {

    public record Tenant(String id, String tier) {}

    // placeholder, resolved from the Environment: the instance name lives in application.yml
    @CircuitBreaker(name = "${bookshelf.resilience.pricing-instance:pricing}")
    public String price(String isbn) {
        return "9.99";
    }

    // a method argument, by parameter name: one breaker per tenant tier, all created
    // from the "tier" configuration instead of from configs.default
    @CircuitBreaker(name = "#tenant.tier", configuration = "tier")
    public String catalogue(Tenant tenant) {
        return "catalogue";
    }

    // the method name: the limiter is called "search", like the instance in application.yml
    @RateLimiter(name = "#root.methodName")
    public String search(String query) {
        return "results";
    }

    // a bean method that receives the argument; the bean is called instanceNames
    @CircuitBreaker(name = "@instanceNames.forIsbn(#isbn)", configuration = "tier")
    public String metadata(String isbn) {
        return "metadata";
    }
}
----

Source: https://resilience4j.readme.io/docs/getting-started-3[Resilience4j: Spring Boot 2 & 3] (SpEL in annotation names) and the
resolver above. In the run, the calls created the instances `pricing-v2`, `gold`, `silver` and `isbn-978`, and the limiter
`search`.
The bean called `instanceNames` is a component with one method, `forIsbn(String isbn)`, that returns `"isbn-"` plus the first
three characters.

The consequence of a computed name is on the *configuration* side. The registry knows no configuration called `gold`, so the
instance is created from `configs.default`, which is almost never what you meant. The `configuration` attribute fixes
that: `@CircuitBreaker(name = "#tenant.tier", configuration = "tier")` created `gold` and `silver` from the `tier` configuration
(window 7 and rate 30 in the run) instead of the default (window 20 and rate 50). The attribute was added in 2.4.0 under the
release note "Provide key for components using SpEL for names" (PR 2329). Two warnings follow. First, a computed name creates an
instance per distinct value, and each has its own state, window and Micrometer series, so never compute a name from unbounded
input such as an ID or a URL. Second, the instance is not in `instances`, so it has no entry of its own: its `registerHealthIndicator`
and `eventConsumerBufferSize` come from `configs.default`.

== `@RefreshScope` registries

With Spring Cloud's `RefreshScope` available, the *Boot 4* starter makes the six registries refresh-scoped: changing the
properties and refreshing the context rebuilds them from the new values. This works for the CircuitBreaker, Retry, RateLimiter,
Bulkhead, ThreadPoolBulkhead and TimeLimiter registries; the Timer registry and the aspects are not refresh-scoped.

[mermaid]
....
sequenceDiagram
    participant Src as Config source (Git, Config Server, file)
    participant Ep as POST /actuator/refresh
    participant CR as ContextRefresher
    participant Reg as CircuitBreakerRegistry (refresh-scoped proxy)
    participant Asp as CircuitBreakerAspect
    Src->>Ep: value changed, operator or webhook calls refresh
    Ep->>CR: refresh()
    CR->>CR: reload the environment, rebind the properties beans
    CR-->>Ep: names of the changed keys
    CR->>Reg: destroy the scoped target
    Note over Reg: every instance, its state and its window are dropped
    Asp->>Reg: next annotated call
    Reg->>Reg: rebuild from the rebound properties, customizers applied
    Reg-->>Asp: a new CircuitBreaker, CLOSED, with the new configuration
....

The sequence is what a run on Spring Boot 4.1.1 showed. The scoped target was `scopedTarget.circuitBreakerRegistry` (and the
five siblings), the bean seen by the application was a proxy, and an annotated call after the refresh went through a *new*
breaker.

.Refreshing the circuit breaker thresholds through the Actuator endpoint
[source,bash]
----
# application.yml points at the file that the platform mounts or a config server serves
#   spring.config.import: optional:file:/etc/bookshelf/resilience.yml
#   management.endpoints.web.exposure.include: refresh,circuitbreakers

# after the file changed
curl -s -X POST http://localhost:8080/actuator/refresh
# ["resilience4j.circuitbreaker.instances.pricing.failureRateThreshold"]

curl -s http://localhost:8080/actuator/circuitbreakers
# {"circuitBreakers":{"pricing":{"failureRateThreshold":"20.0%","state":"CLOSED", ...}}}
----

Source: https://docs.spring.io/spring-cloud-commons/reference/spring-cloud-commons/application-context-services.html#refresh-scope[Spring Cloud Commons: Refresh Scope].
The responses are from the run: the refresh returned the changed key, and `/actuator/circuitbreakers` then showed the new
threshold of 20 where the file had said 50.

The behaviour to plan for:

* *State is lost.* The refreshed registry is a new object. A breaker that was `OPEN` is `CLOSED` again, with an empty window
  (the run went from `OPEN` to `CLOSED`), and a limiter or bulkhead starts full. Refreshing during an incident re-closes a
  breaker that was protecting a failing dependency.
* *Held references go stale.* An instance fetched earlier (`CircuitBreaker cb = registry.circuitBreaker("pricing")` stored in a
  field) is detached: in the run the old instance stayed `OPEN` and nothing called through it any more. Fetch instances from
  the registry for each use, or use the annotations, which do.
* *Metrics follow the new registry.* After the refresh the `resilience4j.circuitbreaker.state` gauge for `pricing` reported the
  new instance (`open` back to 0) and the series count was unchanged.
* *The endpoint is a write operation.* `POST /actuator/refresh` changes the running configuration. Do not expose it on the
  public port; protect it like the `circuitbreakers` write operation (a management port, or Spring Security rules on
  `/actuator/**`).
* *Prefer a rolling restart for incident-time changes.* Refresh is useful for tuning thresholds in a calm system; it is a poor
  tool for changes that must not reset state.

*Spring Boot 3 differs.* The `resilience4j-spring-boot3` 2.4.0 jar contains no refresh-scoped registry auto-configuration. On
Spring Boot 3.5.16 with `spring-cloud-context` 4.3.0, `POST /actuator/refresh` reported the changed key and rebound the
properties bean, but the registry was a plain `InMemoryCircuitBreakerRegistry`, still held the old instance and still reported
the old threshold. If you need it on Boot 3, define the registry bean yourself: it backs the auto-configuration off, and this is
the same wiring the Boot 4 starter ships. With this bean the Boot 3 run behaved like the Boot 4 one (rate changed from 50 to 20,
state `CLOSED`).

== Pitfalls

[cols="3,5",options="header"]
.Configuration pitfalls, all reproduced on 2.4.0
|===
|Pitfall |What happens and what to do

|A misspelled key or prefix
|It is ignored and the default applies, silently. Check the effective configuration through the registry (or `/actuator/circuitbreakers`) after a change, and use the tables above.

|Setting a key that has no Boot property (`ignoreExceptionsPrecedenceEnabled`, `fairCallHandlingEnabled`, `rejectedExecutionHandler`, `slidingWindowSynchronizationStrategy`, `drainPermissionsOnResult`)
|Accepted and ignored. Use a customizer.

|Relying on `ignoreClassBindingExceptions`
|It has no effect in the Boot 3 and Boot 4 starters. A class name that does not exist always fails the startup.

|Assuming `baseConfig` stacks on `configs.default`
|For the circuit breaker it replaces it: a key that only `default` sets does not reach an instance with a `baseConfig`. For the other modules `default` is always the root. Repeat the key in the named configuration, or avoid `baseConfig` on breakers.

|Overriding only the wait of an instance that inherits an exponential breaker
|The circuit breaker drops the exponential backoff (its flags are not inherited). The retry keeps the flags, but loses an inherited `randomizedWaitFactor` and falls back to 0.5. Repeat the flags and the factor on the instance.

|A profile that changes `configs.default` while instances set the same key
|The instance value wins. Override at the same level, or leave the key out of the instance.

|A profile that changes a list
|The list is replaced as a whole. Repeat the elements you keep.

|Overriding an instance with an environment variable
|The key is lower-cased: `pricingFail` gains a second instance `pricingfail`, and a hyphenated name cannot be addressed. Use lower-case single-word names, or do not override through the environment.

|`recordExceptions` with a typo, a predicate class with constructor arguments, a class that is not a `Predicate`
|The application stops at startup (`ClassNotFoundException`, `NoSuchMethodException`, `ClassCastException`). A class that is not a `Throwable` is accepted and never matches.

|Expecting injection into a predicate, interval function or propagator class
|They are created by reflection, not by Spring. Use a customizer bean when a collaborator is needed.

|Two customizers for the same name, or a customizer that injects the registry
|Startup failure (`IllegalStateException`, `BeanCurrentlyInCreationException`). One customizer per name; no registry dependency.

|Expecting a command-line argument to override a customizer
|The customizer runs last and wins. Take the value from `@Value` or a properties bean inside the customizer if it must be overridable.

|A bare number as a duration
|It is milliseconds: `waitDurationInOpenState: 10000` is 10 s and `limitRefreshPeriod: 1` is 1 ms. Write the unit.

|A `baseConfig` cycle
|Only a direct self-reference is reported; a longer cycle ends in a `StackOverflowError`.

|A SpEL name that does not start with `#` or `@`, or does not return a `String`
|The text is used literally, or every call throws `ClassCastException`. Computed names also bypass `instances`: add `configuration = "..."`, and keep the set of names small.

|`registerHealthIndicator: true` and nothing in `/actuator/health`
|The indicator needs `management.health.circuitbreakers.enabled` (or `ratelimiters`) set to `true`; the default is `false`.

|`@RefreshScope` on Spring Boot 3
|The Boot 3 starter does not make the registries refreshable; the properties rebind but the registry keeps its values. Define a refresh-scoped registry yourself, as shown above, or restart.

|Refreshing during an incident
|The new registry starts `CLOSED` with empty windows. Do not refresh while a breaker is open, and protect `POST /actuator/refresh`.

|Exposing the `circuitbreakers` endpoint with its write operation
|One unauthenticated `POST` can force a breaker open or disable it. Set `management.endpoint.circuitbreakers.access: read-only` in the base file and keep management on a protected port.
|===

Source: the runs and source references of the sections above, on Spring Boot 4.1.1 and 3.5.16 with Resilience4j 2.4.0.

== What changed recently

* *Boot 2 to Boot 3 to Boot 4.* The `resilience4j.*` keys are the same on all three. What changed is the starter
  (`resilience4j-spring-boot3`, then `resilience4j-spring-boot4`, which is not in the BOM), the AspectJ starter, and the
  Actuator health package; `resilience4j-spring-boot2` and `resilience4j-spring-cloud2` stopped at 2.3.0. See
  xref:backend/resilience/getting-started.adoc[Getting Started] and
  xref:backend/resilience/migration-and-whats-changed.adoc[Migration & What's Changed].
* *2.3.0.* The `ignoreClassBindingExceptions` setter appeared in the properties class (comparing the 2.2.0 and 2.3.0 jars), and
  the circular-reference `StackOverflowError` in `baseConfig` handling was fixed for the self-reference case only.
* *2.4.0, new keys.* `initialState` and `transitionToStateAfterWaitDuration` on the circuit breaker (PRs 2268 and 2290), and the
  `configuration` attribute on the annotations, for SpEL names (PR 2329). None of these exist in the 2.3.0 properties classes
  or annotations (confirmed by comparing the jars).
* *2.4.0, fixes that touch configuration.* `bulkheadAspectOrder` became bindable from YAML, because the setter was added
  (PR 2386); in 2.3.0 the key was silently ignored. The Retry `eventConsumerBufferSize` is now inherited from the base
  configuration (PR 2344). Customizers are applied in the right order in the Boot 3 starter (PR 2321). SpEL regular expressions
  are compiled once (PR 2398).
* *2.4.0, the Boot 4 starter.* `resilience4j-spring-boot4` ships the `@RefreshScope` registry auto-configurations (PR 2384).
  The Boot 3 starter does not.
* *Endpoint access.* `management.endpoint.<id>.access` (`none`, `read-only`, `unrestricted`) works on both Spring Boot lines
  that were run, 3.5.16 and 4.1.1, and `read-only` removes the circuit breaker write operation.
* *The documentation.* The readme.io Spring Boot page predates all of this. It shows a duration as bare milliseconds (`waitDurationInOpenState: 10000`), lists six
  customizer types (not `TimerConfigCustomizer`), says customizers are for instance names (they also accept configuration
  names), and does not mention the Boot-only keys listed above, the aspect order keys, `initialState`, the precedence rules or
  `@RefreshScope`. The 2.4.0 notes are only in the
  https://github.com/resilience4j/resilience4j/releases/tag/v2.4.0[GitHub release]: `RELEASENOTES.adoc` stops at 2.3.0.
