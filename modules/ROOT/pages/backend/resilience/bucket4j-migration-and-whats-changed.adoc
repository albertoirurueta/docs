Bucket4j keeps its API stable inside the 8.x line, so most upgrades are mechanical, but four things have moved enough to deserve
a page of their own: the *bandwidth builder* that replaced `Bandwidth.simple` and `Refill` in 8.5.0, the *artifact names* that
changed to `bucket4j_jdk17-*` in 8.11.x, the *builder entry points* (`Bucket4jLettuce.casBasedBuilder` and its relatives) that
replaced direct constructors, and the *community Spring Boot starter*, whose coordinates and supported modes changed between
its versions 0.13.0, 0.14.0 and 0.20.0-RC1. The page ends with every place where the official documentation disagrees with the code, gathered
from the whole Bucket4j part of this section so that you can see them in one table.

This is the one page of the section where deprecated API appears, and only as the "before" side of a migration. It was written
against Bucket4j 8.21.0 (released on 2 October 2026), Spring Boot 4.1.x (4.1.1), Spring Framework 7.0.x and Java 21, with the
community starter at 0.14.0 and 0.20.0-RC1 and Spring Cloud Gateway 5.0.3, and verified on 5 October 2026. Every Java example on
this page, in its old and in its new form, was compiled and run against Bucket4j 8.21.0 in a scratch project, and a test proved
that each old form behaves identically to its replacement on a manual clock. The vocabulary (capacity, refill, bandwidth) is in
xref:backend/resilience/bucket4j-token-bucket-and-bandwidths.adoc[Token Bucket and Bandwidths]; the Resilience4j counterpart of
this page is xref:backend/resilience/migration-and-whats-changed.adoc[Migration & What's Changed].

== 7.x to 8.x

Bucket4j 7.0.0 was the release that redesigned the distributed facilities (a `ProxyManager` per backend, rolling upgrades,
non-JCache backends such as Redis and relational databases), and its release notes announce that the API it deprecated would be
removed "in 2023". The 8.x line then changed the platform rather than the model. The notes of 8.0.1 (31 July 2022) list the
migration to JDK 11 and the change of the Maven *groupId* to `com.bucket4j`; the Spring Boot starter's own README dates the JDK 11
move to 8.0.0 and adds that the project then published dedicated Java 8 artifacts. Maven Central confirms the groupId move: the
7.x artifacts live under `com.github.vladimir-bukhtoyarov`, and the group `com.bucket4j` starts with 7.6.1 and 8.0.0.

== The 8.5.0 bandwidth builder

Until 8.4.0 a bandwidth was created with a static factory: `Bandwidth.simple(capacity, period)` for a bucket that refills
completely every period, and `Bandwidth.classic(capacity, Refill...)` for everything else, with `withInitialTokens` and `withId`
as wither methods on the result. The factories are named after implementation details ("classic", "simple") rather than after the
two numbers of the token-bucket algorithm, and which `Refill` was greedy or intervally was a question of memorising factory names.
Release 8.5.0 (issue #401, "making the builder API to be more close with token-bucket description") added a staged builder:
`Bandwidth.builder()` then `capacity`, then one of four refill methods, then the optional `id` and `initialTokens`, then
`build()`. On a `BucketConfiguration` or `Bucket` builder, `addLimit(limit -> ...)` takes the same stages as a lambda. The old
factories, the `withInitialTokens` and `withId` methods and the whole `Refill` class were marked `@Deprecated` in 8.5.0; they still
work in 8.21.0, and under the project's backward-compatibility policy deprecated API is removed only in a major release, so not
before 9.0.0. Version 9 has open milestones on GitHub and is not released.

.From the deprecated API to the builder (all of it still compiles on 8.21.0)
[cols="3,4",options="header"]
|===
|Before 8.5.0 (deprecated) |8.5.0 and later

|`Bandwidth.simple(100, Duration.ofMinutes(1))`
|`Bandwidth.builder().capacity(100).refillGreedy(100, Duration.ofMinutes(1)).build()`

|`Bandwidth.classic(100, Refill.greedy(10, Duration.ofMinutes(1)))`
|`Bandwidth.builder().capacity(100).refillGreedy(10, Duration.ofMinutes(1)).build()`

|`Refill.of(...)`, `Refill.smooth(...)` (aliases of `Refill.greedy`)
|`refillGreedy(tokens, period)`

|`Bandwidth.classic(100, Refill.intervally(10, Duration.ofMinutes(1)))`
|`Bandwidth.builder().capacity(100).refillIntervally(10, Duration.ofMinutes(1)).build()`

|`Refill.intervallyAligned(tokens, period, first, false)`
|`refillIntervallyAligned(tokens, period, first)`

|`Refill.intervallyAligned(tokens, period, first, true)`
|`refillIntervallyAlignedWithAdaptiveInitialTokens(tokens, period, first)`

|`bandwidth.withInitialTokens(20)`
|`...initialTokens(20)` before `build()`

|`bandwidth.withId("plan")`
|`...id("plan")` before `build()`

|`Bucket.builder().addLimit(bandwidth)` with a prebuilt `Bandwidth`
|Still valid; or `addLimit(limit -> limit.capacity(...).refillGreedy(...))`
|===

The same mapping appears, next to the algorithm it describes, on
xref:backend/resilience/bucket4j-token-bucket-and-bandwidths.adoc#_from_the_deprecated_api_to_the_builder[Token Bucket and
Bandwidths]. The code below shows the two forms side by side. The first method is the "before"; it still compiles, with
deprecation warnings.

.Before: deprecated factories, Refill and the withers (compiles on 8.21.0 with warnings)
[source,java]
----
Instant firstRefill = Instant.parse("2026-01-01T00:00:00Z");

Bandwidth[] before = {
    Bandwidth.simple(100, Duration.ofMinutes(1)),
    Bandwidth.classic(100, Refill.greedy(10, Duration.ofMinutes(1))),
    Bandwidth.classic(100, Refill.intervally(10, Duration.ofMinutes(1))),
    Bandwidth.classic(100, Refill.intervallyAligned(10, Duration.ofMinutes(1), firstRefill, false)),
    Bandwidth.classic(100, Refill.intervallyAligned(10, Duration.ofMinutes(1), firstRefill, true)),
    Bandwidth.classic(100, Refill.of(10, Duration.ofMinutes(1))).withInitialTokens(20).withId("plan")
};

Bucket bucket = Bucket.builder()
    .addLimit(Bandwidth.classic(10, Refill.greedy(10, Duration.ofMinutes(1))))
    .build();
----

.After: the staged builder (Bucket4j 8.5.0 and later)
[source,java]
----
Instant firstRefill = Instant.parse("2026-01-01T00:00:00Z");

Bandwidth[] after = {
    Bandwidth.builder().capacity(100).refillGreedy(100, Duration.ofMinutes(1)).build(),
    Bandwidth.builder().capacity(100).refillGreedy(10, Duration.ofMinutes(1)).build(),
    Bandwidth.builder().capacity(100).refillIntervally(10, Duration.ofMinutes(1)).build(),
    Bandwidth.builder().capacity(100).refillIntervallyAligned(10, Duration.ofMinutes(1), firstRefill).build(),
    Bandwidth.builder().capacity(100)
        .refillIntervallyAlignedWithAdaptiveInitialTokens(10, Duration.ofMinutes(1), firstRefill).build(),
    Bandwidth.builder().capacity(100).refillGreedy(10, Duration.ofMinutes(1)).initialTokens(20).id("plan").build()
};

Bucket bucket = Bucket.builder()
    .addLimit(limit -> limit.capacity(10).refillGreedy(10, Duration.ofMinutes(1)))
    .build();
----

The test that accompanies this page asserted that each of the six `before` bandwidths is `equals` to the corresponding `after`
one, field by field (capacity, refill tokens and period, greedy or intervally, aligned time, adaptive initial tokens, initial
tokens and id), and that the two buckets give the same answers on a manual clock: with a capacity of 10 refilled 10 per minute,
the exhausted bucket reported exactly 6 seconds to wait, 5 tokens were back after 30 seconds, and 10 after five minutes, for both.
The intervally variant gave 0 tokens after 59 seconds and 10 after 60, for both.

Source: https://bucket4j.com/8.21.0/toc.html#bandwidth[Bucket4j reference: Bandwidth],
https://bucket4j.com/8.21.0/toc.html#refill-types[Bucket4j reference: Refill types] and the 8.21.0 source of
https://github.com/bucket4j/bucket4j/blob/8.21.0/bucket4j-core/src/main/java/io/github/bucket4j/Bandwidth.java[`Bandwidth`] and
https://github.com/bucket4j/bucket4j/blob/8.21.0/bucket4j-core/src/main/java/io/github/bucket4j/Refill.java[`Refill`], whose
`@Deprecated` tags are where the migration is announced. The 8.21.0 reference no longer shows the old factories at all (a search of
its page and of its AsciiDoc sources found no `Bandwidth.simple`, `Bandwidth.classic` or `Refill.`), so the deprecation is visible
only in the Javadoc and in your compiler's warnings.

Two details of the builder are worth knowing before you convert code in bulk. `initialTokens` cannot be combined with
`refillIntervallyAlignedWithAdaptiveInitialTokens` (the builder throws), exactly as `withInitialTokens` could not be combined with
an adaptive `Refill`. And `withNanosecondPrecision()` belongs to the *local bucket builder*, not to the `Bandwidth` builder;
the aligned refills need a wall-clock time meter and refuse the nanosecond one.

=== Ids change what a replacement means

The builder makes it easy to add `id("...")` while you are converting. Do not add ids to an existing live configuration on the way:
`replaceConfiguration` with `TokensInheritanceStrategy.PROPORTIONALLY` matches the old and the new bandwidth by id (or by position
when neither has one). A run in the scratch project replaced `capacity(20)` (no id) by `capacity(40)...id("plan")` and the bucket
ended with 40 tokens, not the 30 that proportional inheritance gives, because the new bandwidth had an id the old one lacked and
was treated as a different bandwidth. With both ids unset the same replacement gave 30. See
xref:backend/resilience/bucket4j-bucket-api.adoc#_bandwidth_ids_decide_which_old_bandwidth_is_which[Bandwidth ids decide which old
bandwidth is which].

=== MathType.IEEE_754 was removed in 8.6

Before 8.6 the `MathType` enum had a second, experimental value, `IEEE_754`, intended for testing backends written in Lua or
JavaScript that lack 64-bit integer arithmetic. The 8.5.0 source still has it and the 8.6.0 source does not (commit "#410 remove
experimental code", 24 October 2023, which the 8.6.0 tag contains). The 8.6.0 release notes do not mention it. On 8.21.0 `MathType`
is `@Experimental` and has one value, `INTEGER_64_BITS`, which a test of the scratch project asserted. Code that referred to
`MathType.IEEE_754` has to be deleted; there is no replacement, and nothing in the 8.21.0 reference documents `MathType`.

Source: https://github.com/bucket4j/bucket4j/blob/8.21.0/bucket4j-core/src/main/java/io/github/bucket4j/MathType.java[`MathType` at 8.21.0]
and https://bucket4j.com/8.6.0/release-notes.html[Bucket4j 8.6.0 release notes].

== The distributed side: build(key, supplier) and the builder entry points

A `ProxyManager` hands out a `BucketProxy` for a key. The older way to pass the configuration was the `BucketConfiguration` itself:
`proxyManager.builder().build(key, configuration)`. In 8.21.0 that overload is `@Deprecated` ("use `build(Object, Supplier)`
instead. This method will be removed soon" in the source). The replacement takes a `Supplier<BucketConfiguration>` that the
manager calls only when the bucket does not exist yet, which saves building a configuration on every request. The other change is
how the managers are created. The classes with public constructors (`CaffeineProxyManager`, `InfinispanProxyManager` and the JDBC
`SQLProxyConfiguration` family) are deprecated in favour of entry-point classes named `Bucket4j<Backend>`, whose static methods
return a builder that carries the client-side settings (`clientClock`, `expirationAfterWrite`, `requestTimeout`, `maxRetries`,
`retryStrategy`, `executionStrategy` and the others). The 8.11.1 release notes list "unified style builders for all ProxyManagers"
(#467).

The example uses the Caffeine backend because it needs no server: the old constructor keeps the buckets in a local cache, and its
`keepAfterRefillDuration` argument means "keep an entry for that long after the bucket has refilled completely", which is
`ExpirationAfterWriteStrategy.basedOnTimeForRefillingBucketUpToMax(duration)` in the new API.

.Before: public constructor and build(key, config) (deprecated, compiles on 8.21.0 with warnings)
[source,java]
----
ProxyManager<String> proxyManager = new CaffeineProxyManager<>(
    Caffeine.newBuilder().maximumSize(10_000),
    Duration.ofMinutes(1),                                   // keep after refill
    ClientSideConfig.getDefault().withClientClock(clock));

BucketConfiguration configuration = BucketConfiguration.builder()
    .addLimit(Bandwidth.simple(100, Duration.ofMinutes(1)))
    .build();

BucketProxy bucket = proxyManager.builder().build("client-1", configuration);
----

.After: Bucket4jCaffeine.builderFor and build(key, supplier)
[source,java]
----
ProxyManager<String> proxyManager = Bucket4jCaffeine
    .<String>builderFor(Caffeine.newBuilder().maximumSize(10_000))
    .expirationAfterWrite(ExpirationAfterWriteStrategy
        .basedOnTimeForRefillingBucketUpToMax(Duration.ofMinutes(1)))
    .clientClock(clock)
    .build();

BucketConfiguration configuration = BucketConfiguration.builder()
    .addLimit(limit -> limit.capacity(100).refillGreedy(100, Duration.ofMinutes(1)))
    .build();

BucketProxy bucket = proxyManager.builder().build("client-1", () -> configuration);
// or, when the supplier is all you need:
BucketProxy same = proxyManager.getProxy("client-1", () -> configuration);
----

In the test both managers were given a manual `TimeMeter` as `clock`. After consuming 70 of 100 tokens both proxies reported 30
available, and after 30 simulated seconds both reported 80. `getProxy(key, supplier)` returned a proxy over the same bucket as
`builder().build(key, supplier)`: a second proxy for the same key was refused a token that the first had taken. The constructors
are `@Deprecated` in the 8.21.0 source (a reflection check in the test confirmed it for the two-argument `CaffeineProxyManager`
constructor and for `RemoteBucketBuilder.build(Object, BucketConfiguration)`).

Source: https://bucket4j.com/8.21.0/toc.html#proxy-manager[Bucket4j reference: ProxyManager] and the 8.21.0 source of
https://github.com/bucket4j/bucket4j/blob/8.21.0/bucket4j-caffeine/src/main/java/io/github/bucket4j/caffeine/Bucket4jCaffeine.java[`Bucket4jCaffeine`],
https://github.com/bucket4j/bucket4j/blob/8.21.0/bucket4j-core/src/main/java/io/github/bucket4j/distributed/proxy/RemoteBucketBuilder.java[`RemoteBucketBuilder`]
and https://github.com/bucket4j/bucket4j/blob/8.21.0/bucket4j-core/src/main/java/io/github/bucket4j/distributed/proxy/AbstractProxyManagerBuilder.java[`AbstractProxyManagerBuilder`].

== 8.11.1: JDK 17 and the artifact rename

The 8.11.1 release notes list three items: split Redis support into individual Maven modules (#466), unified builders (#467) and
the migration to JDK 17 (#474). Under "Backward incompatible changes" they say that the *target JDK is now part of the artifact
name*: `com.bucket4j:bucket4j-core` became `com.bucket4j:bucket4j_jdk17-core`, and that the Redis dependencies were split into
the Jedis, Lettuce and Redisson modules. On Maven Central `bucket4j_jdk17-*` starts at 8.11.0 (the GitHub release 8.11.0 is dated 24 April 2024)
and the notes are filed under 8.11.1. Because the *artifactId changes*, a dependency bot that follows
`bucket4j-core` never sees the new releases: the legacy `bucket4j-core` ends at 8.10.1 on Maven Central.

== From 8.16 to 8.21: new entry points and modules

Since 8.16 the releases have added backends and one build tool, not new concepts. Every new module follows the entry-point rule of
the previous section: a `Bucket4j<Backend>` class with static builder methods, no public constructor to learn. The versions below
are the first on Maven Central, cross-checked against the release notes.

.Entry points and modules added in 8.16 to 8.21 (8.21.0 signatures)
[cols="1,3,5",options="header"]
|===
|Release |Module (artifact `bucket4j_jdk17-...`) |Entry point and notes

|8.16.x
|`glide` (Valkey GLIDE)
|`Bucket4jGlide.casBasedBuilder(BaseClient)`. The 8.16.1 notes also list a retry strategy for compare-and-swap (#560) and OSGi metadata (#561).

|8.17.0
|`vertx` (Redis through Vert.x)
|`Bucket4jVertx.casBasedBuilder(Redis)`, key type `byte[]`; a fix for an Infinispan end-of-file error on a missing key.

|8.18.0
|`couchbase`
|`Bucket4jCouchbase.compareAndSwapBasedBuilder(Collection)` or `(AsyncCollection)`, key type `String`, with `Mapper<K>` overloads.

|8.19.0

|8.20.0
|`geode` (Gemfire)
|`Bucket4jGeode.compareAndSwapBasedBuilder(Region)` and `functionBasedBuilder(Region)`. Redis Sentinel through Lettuce (#588); stack-trace generation disabled in `BucketExecutionException` (#595); a fix of MySQL gap-lock deadlocks (#606).

|8.21.0

|8.21.0
|`infinispan-15`, `coherence-21`

|8.21.0
|core
|Serialization moved from byte-array streams to `ByteBuffer` (#625) and `reset()` skips a needless token recalculation (#634).

Two facts from this list matter at upgrade time. The `redis`, `hazelcast-all` and `infinispan-all` aggregator artifacts have no
8.21.0 build, so a dependency on one of them freezes at 8.14.0; use the individual modules. And the release notes of 8.20.0
and 8.21.0 repeat the items of earlier releases (#580, #588, #615, #595 and #606 appear in both), so read them as a running list and
not as a per-release diff; the Maven Central versions are the reliable record of which module arrived when.

The following code shows what a new-style entry point looks like in a service and compiles on 8.21.0 with only the Caffeine
module on the classpath; the other entry points above have the same shape and differ in the client object they take.

.An 8.21.0 proxy manager and a bucket through the supplier form
[source,java]
----
ProxyManager<String> proxyManager = Bucket4jCaffeine
    .<String>builderFor(Caffeine.newBuilder().maximumSize(10_000))
    .expirationAfterWrite(ExpirationAfterWriteStrategy
        .basedOnTimeForRefillingBucketUpToMax(Duration.ofMinutes(5)))
    .build();

Supplier<BucketConfiguration> freePlan = () -> BucketConfiguration.builder()
    .addLimit(limit -> limit.capacity(20).refillGreedy(20, Duration.ofMinutes(1)))
    .build();

BucketProxy bucket = proxyManager.getProxy("api:alice", freePlan);
boolean allowed = bucket.tryConsume(1);
----

=== YAML: what changes and what does not

The property model is stable across the three Boot-4-era versions. The same filter YAML bound and limited identically on 0.14.0
(Spring Boot 4.0.3) and on 0.20.0-RC1 (Spring Boot 4.1.1) in the scratch project of this section, and the property classes of the
two tags have the same keys and defaults for `bucket4j.filters[]`, `rate-limits[]` and `bandwidths[]`. What changes is a mode that
disappears and one property that was removed earlier.

.Before: a 0.14.0 Gateway filter (the only filter-method value that disappears)
[source,yaml]
----
bucket4j:
  enabled: true
  filters:
    - id: gateway-books
      cache-name: buckets
      filter-method: gateway          # FilterMethod.GATEWAY exists in 0.13.0 and 0.14.0
      url: /api/.*
      rate-limits:
        - cache-key: "getRemoteAddr()"
          bandwidths:
            - capacity: 100
              time: 1
              unit: minutes
----

.After: the servlet filter on 0.20.0-RC1 (the same keys, a supported filter-method)
[source,yaml]
----
bucket4j:
  enabled: true
  cache-to-use: jcache
  filters:
    - id: servlet-books
      cache-name: buckets
      filter-method: servlet          # SERVLET, WEBFLUX and JMS are the values left
      url: /api/.*
      rate-limits:
        - cache-key: "getRemoteAddr()"
          bandwidths:
            - capacity: 100
              time: 1
              unit: minutes
----

On a Spring Cloud Gateway application there is no replacement inside the starter: `filter-method: gateway` no longer binds on
the 0.20.0-RC1 tag and the Gateway filter factory is gone. The supported route is the gateway's own limiter, which uses Bucket4j directly,
described on xref:backend/resilience/bucket4j-spring-cloud-gateway.adoc[Bucket4j in Spring Cloud Gateway]. And the removed
`expression` property, which the README's 0.12 entry names, is a plain rename:

.Before and after: the 0.12 rename of expression to cache-key
[source,yaml]
----
# before 0.12 (the property is removed, not just deprecated)
bucket4j:
  filters:
    - cache-name: buckets
      url: /api/.*
      rate-limits:
        - expression: "getRemoteAddr()"
          bandwidths:
            - capacity: 100
              time: 1
              unit: minutes

# 0.12 and later
bucket4j:
  filters:
    - cache-name: buckets
      url: /api/.*
      rate-limits:
        - cache-key: "getRemoteAddr()"
          bandwidths:
            - capacity: 100
              time: 1
              unit: minutes
----

All key names in these three YAML blocks were checked against the property classes of the 0.20.0-RC1 tag
(`Bucket4JConfiguration`, `RateLimit`, `BandWidth`) and, for `filter-method: gateway`, against the `FilterMethod` enum of 0.14.0,
which has `SERVLET`, `WEBFLUX`, `GATEWAY` and `JMS`, where the 0.20.0-RC1 enum has no `GATEWAY`. A neighbouring `expression`
exists only on the metric tags (`MetricTag`), a different property. The starter also needs a Bean Validation provider
(`spring-boot-starter-validation`), because it validates its properties at startup.

Source: https://github.com/MarcGiffing/bucket4j-spring-boot-starter#bucket4j_complete_properties[starter README: Bucket4j complete properties]
and the `FilterMethod`, `Bucket4JConfiguration` and `RateLimit` classes of the
https://github.com/MarcGiffing/bucket4j-spring-boot-starter/tree/0.20.0-RC1[0.20.0-RC1 tag].

== Pitfalls

.Pitfalls when migrating
[cols="3,4,4",options="header"]
|===
|Pitfall |What happens |What to do

|A dependency bot that follows `bucket4j-core`
|It never proposes anything newer than 8.10.1, because the artifact id changed in 8.11.x
|Switch to `bucket4j_jdk17-*` explicitly and import `bucket4j_jdk17-bom`

|Both `bucket4j-core` and `bucket4j_jdk17-core` on the classpath
|Duplicate `io.github.bucket4j` classes, and whichever comes first wins
|Exclude the legacy artifact from every transitive dependency (an old starter, an internal library)

|Staying on Java 11 and bumping to 8.21.0
|The jars need Java 17
|Stay on `bucket4j_jdk11-*` 8.15.0 until the runtime moves, or upgrade the JDK

|`Bucket4j.builder()` after the upgrade
|The class is gone since 8.5.0: a compile error
|`Bucket.builder()` and `BucketConfiguration.builder()`

|Converting `Bandwidth.simple(100, 1 min)` to a refill of 10
|`simple` refills the whole capacity every period; the two are not the same bucket
|Use `refillGreedy(100, period)` for the equivalent of `simple`, as in the mapping table

|Adding `id(...)` while converting a live distributed bucket
|`replaceConfiguration` or implicit replacement treats the bandwidth as a different one and loses the inherited tokens
|Give both the old and the new bandwidth the same id, or none

|Declaring the aggregators `bucket4j_jdk17-redis`, `-hazelcast-all` or `-infinispan-all`
|The newest build is 8.14.0, with no 8.21.0
|Use the individual modules and the BOM

|Starter 0.20.0-RC1 keeps Bucket4j 8.17.0
|Fixes and modules of 8.18 to 8.21 are missing
|Import `bucket4j_jdk17-bom` 8.21.0 before the starter

|`starter-servlet` and `starter-webflux` together
|They cannot share a classpath
|One feature module per application

|`filter-method: gateway` on 0.20.0-RC1
|The value no longer binds and the Gateway filter is gone
|Use the gateway's native Bucket4j limiter

|Following a reference example that does not compile
|`withClientSideConfig`, `Bandwidth.builder(limit -> ...)`, a `TimeMeter` without `isWallClockBased()`, `javax.servlet`
|Use the discrepancy table above
|===

== What changed

* *7.x to 8.0*: JDK 11 baseline, groupId `com.bucket4j`, dedicated `bucket4j_jdk8-*` artifacts for Java 8.
* *8.5.0*: the `Bandwidth.builder()` and `addLimit(limit -> ...)` API; `Bandwidth.simple`, `Bandwidth.classic`, `withInitialTokens`,
  `withId` and the `Refill` class are deprecated; the `Bucket4j` factory class is gone.
* *8.6.0*: `MathType.IEEE_754` removed.
* *8.7.0*: Amazon DynamoDB support removed.
* *8.11.x*: `bucket4j_jdk17-*` artifacts, Redis split into `redis-common` plus a client, unified builders for every `ProxyManager`.
* *8.15.0*: the last `bucket4j_jdk11-*` release.
* *8.16 to 8.21*: GLIDE, Vert.x, Couchbase, Geode, Memcached, Cassandra, Ignite 3, `infinispan-15` and `coherence-21`, the
  compare-and-swap retry mechanism, Redis Sentinel through Lettuce, and in 8.21.0 the `bucket4j_jdk17-bom`.
* *Starter*: 0.13.0 on the `jdk17` artifacts, 0.14.0 on Spring Boot 4, 0.20.0-RC1 on the new module layout without the Gateway
  filter; no GA 0.20.0 yet.
* *Version 9*: not released; the policy removes deprecated API only in a major release, so everything on this page that avoids
  deprecated API should carry over. The state of the line is on https://bucket4j.com/previous-releases.html[the previous-releases
  page].
