A resilience library that nobody can see working is a liability: a breaker that stays open for an hour, a retry that quietly
triples the load on a dependency, or a bulkhead that is always full all look like "the service is slow" until somebody
reads the right number. Resilience4j reports through four channels: *Actuator endpoints* (JSON, for a person with `curl`),
*health indicators* (for the platform), *Micrometer meters* (for Prometheus and Grafana) and *events* (for logs and your own
code). This page covers all four for every module, shows what each one looks like in a running service, and ends with alert
rules and the tracing-context question that the thread-pool bulkhead raises. It was written against Resilience4j 2.4.0,
Spring Boot 4.1.x, Spring Framework 7.0.x and Java 21 and verified on 4 October 2026. Every sample on the page is output from
a sample Spring Boot 4.1.1 application running on JDK 21, and the same run was repeated on Spring Boot 3.5.16 with
`resilience4j-spring-boot3`: the endpoint JSON, the HTTP status codes and every Prometheus metric name were identical. The
Boot 3 differences are in the section <<what-changed,What changed recently>>.

The base setup of Actuator, Micrometer, the Prometheus registry and Micrometer Tracing is not repeated here; it is in
xref:backend/springboot/metrics-and-observability.adoc[Metrics and Observability]. This page adds only what is specific to
Resilience4j. The running example is *Bookshelf* in the package `com.example.bookshelf`: a `pricing` circuit breaker, an
`isbn` retry, rate limiter and semaphore bulkhead, a `reviews` time limiter, a `recommendations` thread-pool bulkhead and a
`search` timer. The sample outputs use the same instance names, and the code in the sample application was identical apart
from the package name.

The Bucket4j counterpart of this page (bucket listeners, Micrometer meters and backend health) is xref:backend/resilience/bucket4j-observability.adoc[Bucket4j: Observability].

== The four channels

[cols="1,2,2,2",options="header"]
|===
|Channel |What you get |Who reads it |Switched on by

|Actuator endpoints
|The current state of every instance and the last 100 events per instance, as JSON.
|A person debugging, a script, a runbook.
|`management.endpoints.web.exposure.include` plus the module on the classpath.

|Health indicators
|`circuitBreakers` and `rateLimiters` components in `/actuator/health`.
|A load balancer, a Kubernetes readiness probe, a status page.
|`management.health.circuitbreakers.enabled` and `management.health.ratelimiters.enabled`, plus `registerHealthIndicator` per instance.

|Micrometer meters
|Gauges, counters and timers per instance, with the tags `name` and `kind` or `state`.
|Prometheus, Grafana, alerting.
|On by default when a `MeterRegistry` bean exists; `resilience4j.<module>.metrics.enabled` switches a module off.

|Events
|One object per call outcome, state transition or rejection, delivered to a listener.
|Logs, audit trails, your own counters.
|Always available on every instance through `getEventPublisher()`.
|===

The figure shows how the first three channels connect. Metrics flow from the instances through the module's metrics publisher
into the `MeterRegistry`, over the Actuator Prometheus endpoint to Prometheus, and from there to Grafana and Alertmanager.
Events and health take their own route and do not go through Micrometer at all.

.The metrics pipeline, and the channels that bypass it
image::resilience-metrics-pipeline.svg["A left-to-right pipeline of six boxes. Resilience4j instances (CircuitBreaker, Retry, RateLimiter, Bulkhead, ThreadPoolBulkhead, TimeLimiter and Timer) feed a Tagged...MetricsPublisher in resilience4j-micrometer, which binds each instance when it is created and tags it with name, kind or state. The publisher writes to a Micrometer MeterRegistry backed by Prometheus, which turns dots into underscores, adds _seconds to timers and _total to counters. The Actuator endpoint /actuator/prometheus serves the text format, Prometheus scrapes it, stores the series and evaluates alerting rules, and feeds a Grafana dashboard and Alertmanager. Below the pipeline four boxes show the channels that do not use Micrometer: the EventPublisher feeding log lines and the /actuator/*events ring buffers, the HealthIndicator feeding /actuator/health and a custom health group that must never be the liveness group, tracing context copied onto thread-pool bulkhead threads by a ContextPropagator, and the circuitbreakers write operation that must be locked down",width=900,role=text-center]

== Dependencies and the minimum configuration

With the starter from xref:backend/resilience/getting-started.adoc[Getting Started] in place, observability needs
two more things: the Actuator starter, which also brings Micrometer, and a Micrometer registry for the monitoring system. For
Prometheus that is `micrometer-registry-prometheus`.

.The two dependencies that turn the endpoints and the meters on
[source,xml]
----
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-actuator</artifactId>
</dependency>
<dependency>
    <groupId>io.micrometer</groupId>
    <artifactId>micrometer-registry-prometheus</artifactId>
</dependency>
----

Source: https://docs.spring.io/spring-boot/reference/actuator/metrics.html[Spring Boot: Metrics] and
https://docs.micrometer.io/micrometer/reference/implementations/prometheus.html[Micrometer: Prometheus]. The Actuator starter
is not a transitive dependency of the Resilience4j starters (their POMs pull in Micrometer and Spring only at runtime scope),
so it has to be added explicitly. Without it the application starts, the annotations work and there are no
endpoints and no meters.

Actuator endpoints are not exposed over HTTP by default, apart from `health`. The next block exposes the twelve
Resilience4j endpoints that this page walks through, the Prometheus scrape endpoint and `health`, shows health details, and
moves the whole management API onto its own port. The samples below were produced with the same endpoints, but on the
application port, with `show-details: always` and without the `access` line, so that every request could be made without
credentials.

.The Bookshelf monitoring configuration (application.yml)
[source,yaml]
----
management:
  server:
    port: 8081                       # management API on its own port, not reachable through the gateway
  endpoints:
    web:
      exposure:
        include: >-
          health,prometheus,
          circuitbreakers,circuitbreakerevents,
          retries,retryevents,
          ratelimiters,ratelimiterevents,
          bulkheads,bulkheadevents,
          timelimiters,timelimiterevents,
          timers,timerevents
  endpoint:
    health:
      show-details: when-authorized
    circuitbreakers:
      access: read-only              # no write operation unless an ops profile turns it on
  health:
    circuitbreakers:
      enabled: true
    ratelimiters:
      enabled: true
  metrics:
    tags:
      application: bookshelf         # the Grafana dashboard filters on this label
----

Source: https://docs.spring.io/spring-boot/reference/actuator/endpoints.html[Spring Boot: Endpoints]. Putting the management
API on its own port was run: with `management.server.port=0` and the same endpoints exposed, `/actuator/circuitbreakers`
answered `404` on the application port and `200` on the management port. The `access` property is explained in the section
<<write-operation,The circuitbreakers write operation>>, and the individual keys of `resilience4j.*` are in
xref:backend/resilience/spring-boot-configuration.adoc[Spring Boot Configuration].

== The Actuator endpoints

Each module that is on the classpath contributes a pair of endpoints: one that lists the instances and one that returns the
buffered events. Every endpoint id below is the literal `@Endpoint(id = ...)` of the v2.4.0 `resilience4j-spring-boot4`
sources, and an endpoint exists only when it is exposed (`@ConditionalOnAvailableEndpoint`).

[cols="2,3,3",options="header"]
|===
|Endpoint id |Paths under `/actuator` |What it returns

|`circuitbreakers`
|`GET /circuitbreakers`, `POST /circuitbreakers/<name>`
|Every breaker with its state, rates and counters. The POST is the write operation.

|`circuitbreakerevents`
|`GET /circuitbreakerevents`, `/circuitbreakerevents/<name>`, `/circuitbreakerevents/<name>/<type>`
|Buffered events of all breakers, of one breaker, or of one breaker filtered by event type.

|`retries`, `retryevents`
|`GET /retries`, `GET /retryevents[/<name>[/<type>]]`
|The names of the retries, and their buffered events.

|`ratelimiters`, `ratelimiterevents`
|`GET /ratelimiters`, `GET /ratelimiterevents[/<name>[/<type>]]`
|The names of the rate limiters, and their buffered events.

|`bulkheads`, `bulkheadevents`
|`GET /bulkheads`, `GET /bulkheadevents[/<name>[/<type>]]`
|The names of the semaphore and the thread-pool bulkheads, and their buffered events.

|`timelimiters`, `timelimiterevents`
|`GET /timelimiters`, `GET /timelimiterevents[/<name>[/<type>]]`
|The names of the time limiters, and their buffered events.

|`timers`, `timerevents`
|`GET /timers`, `GET /timerevents[/<name>[/<type>]]`
|The names of the `@Timer` instances, and their buffered events.

|`streamcircuitbreakerevents`, `hystrixstreamcircuitbreakerevents`
|`GET /streamcircuitbreakerevents[/<name>[/<type>]]`
|A server-sent-events stream of breaker events. Needs Reactor on the classpath. See below.
|===

Only `circuitbreakers` shows details. The other `...s` endpoints return the instance names, because the interesting numbers
for those modules are meters, not endpoint fields. The `...events` endpoints return what the instance's *event consumer
buffer* holds: a ring buffer per instance whose size is `eventConsumerBufferSize` (default `100`). Old events are
overwritten, so these endpoints answer "what just happened", not "what happened last night", and an unknown instance name
returns an empty list rather than an error.

The samples come from this sequence: three successful `pricing` price calls, one `isbn` lookup that failed twice and then
succeeded on the third attempt (so the retry was used) next to one that succeeded at once, a fast `reviews` call and one that
timed out after 200 ms, a `recommendations` call on the thread pool, and two `search` calls, one of which threw. JSON is
reformatted for reading and lists are trimmed where noted; the values are as returned.

----

Source: the output of the sample run and the
https://github.com/resilience4j/resilience4j/blob/v2.4.0/resilience4j-circuitbreaker/src/main/java/io/github/resilience4j/circuitbreaker/event/CircuitBreakerEvent.java[`CircuitBreakerEvent.Type` at v2.4.0].
The type segment is case-insensitive (`state_transition` is converted with `toUpperCase()`); the types are `ERROR`,
`IGNORED_ERROR`, `SUCCESS`, `NOT_PERMITTED`, `STATE_TRANSITION`, `RESET`, `FORCED_OPEN`, `DISABLED`, `FAILURE_RATE_EXCEEDED`
and `SLOW_CALL_RATE_EXCEEDED`. A `SUCCESS` event looks like the one above with `"type": "SUCCESS"`, a `durationInMs` and no
`stateTransition`. Only `STATE_TRANSITION` and `RESET` are published in every state; the other types are published only while
the breaker is `CLOSED`, `OPEN`, `HALF_OPEN` or `METRICS_ONLY` (`CircuitBreakerEvent.Type.forcePublish` and
`CircuitBreaker.State.allowPublish`), so a breaker in `FORCED_OPEN` or `DISABLED` adds nothing to the buffer except the
transitions themselves, as noted on xref:backend/resilience/circuit-breaker.adoc[CircuitBreaker]. The state
transition string is the `toString()` of the `StateTransition` enum on Spring Boot 4.1.1 (Jackson 3), as above, while the same
request on Spring Boot 3.5.16 (Jackson 2) returned the enum name `CLOSED_TO_OPEN`; do not parse that field in a script that has
to run on both.

=== The event stream endpoint

`streamcircuitbreakerevents` (and the Hystrix-format `hystrixstreamcircuitbreakerevents`) are Actuator endpoints that
return `Flux<ServerSentEvent<String>>` with the content type `text/event-stream`, merged with a one-second heartbeat. They
are registered only when Reactor is on the classpath. In the sample application, which runs on Spring MVC, a request to
`/actuator/streamcircuitbreakerevents/pricing` did not produce a stream: it answered `503` without an `Accept` header and
`404` with `Accept: text/event-stream`. The endpoint was therefore not verified on the servlet stack and the page does not
recommend it; the Javadoc in the source also still shows the old path `stream-circuitbreaker-events`. For a live feed on
Spring MVC, use the `EventPublisher` listeners described in the section <<event-logging,Logging the event streams>> or poll
`circuitbreakerevents`.

[[write-operation]]
== The circuitbreakers write operation

The `circuitbreakers` endpoint is the only Resilience4j endpoint with a write operation. `POST /actuator/circuitbreakers/<name>`
with a JSON body `{"updateState": "<value>"}` changes the state of that breaker. The operation accepts exactly three values:
`CLOSE` (`transitionToClosedState()`), `FORCE_OPEN` (`transitionToForcedOpenState()`) and `DISABLE`
(`transitionToDisabledState()`). The state machine side of these transitions is on
xref:backend/resilience/circuit-breaker.adoc[CircuitBreaker].

.Forcing a breaker open during an incident, then closing it again
[source,bash]
----
curl -s -X POST http://localhost:8081/actuator/circuitbreakers/pricing \
     -H 'Content-Type: application/json' \
     -d '{"updateState":"FORCE_OPEN"}'
curl -s -X POST http://localhost:8081/actuator/circuitbreakers/pricing \
     -H 'Content-Type: application/json' \
     -d '{"updateState":"CLOSE"}'
----

[source,json]
----
{"circuitBreakerName":"pricing","currentState":"FORCED_OPEN","message":"pricing state has been changed successfully"}
----

[source,json]
----
{"circuitBreakerName":"pricing","currentState":"CLOSED","message":"pricing state has been changed successfully"}
----

Source: the output of the sample run and the
https://github.com/resilience4j/resilience4j/blob/v2.4.0/resilience4j-spring-boot4/src/main/java/io/github/resilience4j/springboot/circuitbreaker/monitoring/endpoint/CircuitBreakerEndpoint.java[`CircuitBreakerEndpoint` at v2.4.0].
`DISABLE` answered `"currentState":"DISABLED"`. Three things about the operation surprised in the run, and each is a
reason to treat it carefully:

* Any other value is rejected before the method runs: `OPEN` and `HALF_OPEN` both returned `400 Bad Request`, because the
  body is bound to an enum with only those three constants. There is no way to open a breaker "naturally" or to force it
  half-open over HTTP.
* The name is not checked. Posting `{"updateState":"CLOSE"}` to `/actuator/circuitbreakers/nosuch` returned `200` with
  `"currentState":"CLOSED"` and *created* a breaker named `nosuch` with the default configuration, which then appeared in
  `/actuator/circuitbreakers`, in the health indicator if the default config registers it, and as a new set of series in
  Prometheus. A typo in a runbook command creates a permanent, empty instance.
* A body-less request is rejected with `415 Unsupported Media Type`; the `Content-Type: application/json` header is required.

`FORCE_OPEN` and `DISABLE` change production behaviour with one request: a forced-open breaker rejects every call until
somebody posts `CLOSE`, and a disabled breaker lets everything through and stops recording. That makes the endpoint a
control plane and not a monitoring page, so it needs three layers of protection.

=== Layer 1: take the write operation away

Since Spring Boot 3.4 the access level of an endpoint is set with `management.endpoint.<id>.access`, which replaces the
older `enabled` property. The values are `none`, `read-only` and `unrestricted`. With `read-only`, the `GET` stays and the
`POST` is not registered.

.Making the circuitbreakers endpoint read-only
[source,yaml]
----
management:
  endpoint:
    circuitbreakers:
      access: read-only
----

Source: https://docs.spring.io/spring-boot/reference/actuator/endpoints.html[Spring Boot: Endpoints] (endpoint access). In
the run, with `access=read-only`, `GET /actuator/circuitbreakers` returned `200` and the same `POST` returned `404`: the
write operation does not exist at all. Keep `read-only` as the default, and turn it to `unrestricted` only in a profile that
operators use, if at all.

=== Layer 2: keep the management API off the public network

`management.server.port` (shown earlier) moves every endpoint to a second port, and `management.server.address` binds it to
one interface. In the run the application port answered `404` for `/actuator/circuitbreakers` and the management port
answered `200`. The gateway, the ingress and the public load balancer should route only to the application port; reach the
management port through a `Service` that is not exposed, a port-forward, or a network policy that admits only the monitoring
namespace.

=== Layer 3: authenticate and authorize

Even on a private port the write operation should need a role, and a monitoring user (Prometheus, Grafana) should not have
it. A Spring Security filter chain that matches the Actuator endpoints can express "everybody authenticated reads, only ops
writes". The password comes from the environment and is never in the file.

.Security rules for the Actuator endpoints (Spring Security 7, Spring Boot 4)
[source,java]
----
package com.example.bookshelf.config;

import org.springframework.beans.factory.annotation.Value;
import org.springframework.boot.security.autoconfigure.actuate.web.servlet.EndpointRequest;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.core.annotation.Order;
import org.springframework.http.HttpMethod;
import org.springframework.security.config.Customizer;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.config.http.SessionCreationPolicy;
import org.springframework.security.core.userdetails.User;
import org.springframework.security.core.userdetails.UserDetailsService;
import org.springframework.security.crypto.factory.PasswordEncoderFactories;
import org.springframework.security.provisioning.InMemoryUserDetailsManager;
import org.springframework.security.web.SecurityFilterChain;

@Configuration
class ActuatorSecurityConfig {

    @Bean
    @Order(1)
    SecurityFilterChain actuatorSecurity(HttpSecurity http) throws Exception {
        return http
            .securityMatcher(EndpointRequest.toAnyEndpoint())
            .authorizeHttpRequests(auth -> auth
                .requestMatchers(EndpointRequest.to("health")).permitAll()
                .requestMatchers(HttpMethod.POST, "/actuator/circuitbreakers/**").hasRole("OPS")
                .anyRequest().hasAnyRole("OPS", "OBSERVER"))
            .httpBasic(Customizer.withDefaults())
            .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
            .csrf(csrf -> csrf.disable())      // stateless, header-authenticated management API
            .build();
    }

    @Bean
    UserDetailsService actuatorUsers(@Value("${ACTUATOR_PASSWORD}") String password) {
        var encoder = PasswordEncoderFactories.createDelegatingPasswordEncoder();
        return new InMemoryUserDetailsManager(
            User.withUsername("ops").password(encoder.encode(password)).roles("OPS").build(),
            User.withUsername("grafana").password(encoder.encode(password)).roles("OBSERVER").build());
    }
}
----

Source: https://docs.spring.io/spring-boot/reference/actuator/endpoints.html[Spring Boot: Endpoints] (securing HTTP endpoints). In
the run, with `ACTUATOR_PASSWORD` supplied as a system property: `/actuator/health` was reachable without credentials,
`/actuator/circuitbreakers` returned `401` without them, the `grafana` user got `200` for `GET /actuator/circuitbreakers`,
`/actuator/retries` and `/actuator/prometheus`, the same user got `403` for the `POST`, and the `ops` user got `200` with
`"currentState":"FORCED_OPEN"`. Two details matter. The `POST` rule has to be written with `HttpMethod.POST` and a path
matcher, because `EndpointRequest.to("circuitbreakers")` matches the endpoint for every method. And the example uses one
shared secret for two users only to stay short; in production give each consumer its own credential, from a secret store,
and prefer a token-based scheme (OAuth2 resource server, mutual TLS) over basic authentication. The Prometheus scrape
configuration later on this page shows the monitoring user's password being read from a mounted file.

On Spring Boot 3 the matcher class is `org.springframework.boot.actuate.autoconfigure.security.servlet.EndpointRequest`; the
rest of the example is unchanged.

== Health indicators

Resilience4j contributes two health indicators to `/actuator/health`: `circuitBreakers` and `rateLimiters`. There is no
bulkhead, retry or time limiter indicator: those modules have no "unhealthy" condition that a health check could
meaningfully report. A health indicator has to be enabled twice: once for the indicator as a whole and once for each
instance that should appear in it.

.Enabling the health indicators
[source,yaml]
----
management:
  health:
    circuitbreakers:
      enabled: true
    ratelimiters:
      enabled: true
resilience4j:
  circuitbreaker:
    configs:
      default:
        registerHealthIndicator: true
    instances:
      pricing:
        baseConfig: default
      pricingStrict:
        baseConfig: default
        allowHealthIndicatorToFail: true
  ratelimiter:
    instances:
      isbn:
        registerHealthIndicator: true
----

Source: https://resilience4j.readme.io/docs/getting-started-3[Resilience4j: Spring Boot 2 & 3] and the
https://github.com/resilience4j/resilience4j/blob/v2.4.0/resilience4j-spring-boot4/src/main/java/io/github/resilience4j/springboot/circuitbreaker/autoconfigure/CircuitBreakersHealthIndicatorAutoConfiguration.java[`CircuitBreakersHealthIndicatorAutoConfiguration` at v2.4.0].
The `management.health.circuitbreakers.enabled` and `management.health.ratelimiters.enabled` properties are
`@ConditionalOnProperty` without a default: if they are absent, the indicator bean does not exist and nothing appears in the
health response, whatever `registerHealthIndicator` says. `registerHealthIndicator` defaults to `false` per instance, and the
indicator lists only instances where it is `true`; putting it in `configs.default` makes every instance that inherits the
default configuration, including breakers created later by name, appear. The `pricingStrict` instance in the sample is a
second breaker with `allowHealthIndicatorToFail: true`, to show the difference below.

=== What each state reports

For the circuit breaker the mapping is in `CircuitBreakersHealthIndicator.mapBackendMonitorState`. `CLOSED` is `UP`. `OPEN`
is the custom status `CIRCUIT_OPEN`, or `DOWN` when the instance has `allowHealthIndicatorToFail: true`. `HALF_OPEN` is the
custom status `CIRCUIT_HALF_OPEN`, and `allowHealthIndicatorToFail` does not change it. Every other state (`DISABLED`,
`METRICS_ONLY`, `FORCED_OPEN`) is `UNKNOWN`. The details of each instance are the numbers of the `circuitbreakers` endpoint.
The rate limiter indicator reports `UP` while a permission is available or nobody is waiting, `RATE_LIMITED` (or `DOWN` with
`allowHealthIndicatorToFail`) when no permission is available and the wait would exceed `timeoutDuration`, and `UNKNOWN`
otherwise; its details are `availablePermissions` and `numberOfWaitingThreads`.

service with one broken dependency and a working fallback is degraded, not dead. Use `allowHealthIndicatorToFail: true` only
for a breaker whose dependency the service cannot do its job without.

`management.endpoints.web.exposure.include` set to `circuitbreakers` only and
`management.health.circuitbreakers.enabled=true` failed with a missing bean of type
`org.springframework.boot.health.actuate.endpoint.StatusAggregator`, because the health endpoint's configuration, which
provides that bean, is conditional on the endpoint being available. Expose `health` whenever the indicator is enabled.

=== Health groups, and keeping the indicators out of liveness

Spring Boot health *groups* select which indicators answer a given URL: `/actuator/health/<group>`. They are the right way to
use Resilience4j's indicators. A custom group gives an operator or a status page the dependency view without touching what
the platform probes.

.A dependency group, and the probe groups left alone
[source,yaml]
----
management:
  endpoint:
    health:
      group:
        dependencies:
          include: circuitBreakers,rateLimiters
          show-details: never
        readiness:
          include: readinessState
----

Source: https://docs.spring.io/spring-boot/reference/actuator/endpoints.html[Spring Boot: Health groups]. In the run,
`/actuator/health/dependencies` with `pricingStrict` open answered `503 {"status":"DOWN"}` and the readiness group
answered `200`.

The liveness probe answers one question: "is this process stuck so badly that restarting it is the cure?" An open breaker
means that a *dependency* is unhealthy, and restarting the caller does not fix a dependency. Worse, every replica of
`bookshelf-service` sees the same open breaker at about the same time, so a liveness probe that includes `circuitBreakers`
makes Kubernetes restart the whole deployment, which empties the breaker state, reconnects every pool at once and adds a
thundering herd to the outage. In the run, a configuration that added `circuitBreakers` to the `liveness` group made
`/actuator/health/liveness` answer `503` as soon as a strict breaker opened. Keep `circuitBreakers` and `rateLimiters` out of
`liveness`, leave `readiness` with `readinessState`, and add the indicators to readiness only for a dependency that the
service genuinely cannot serve without (and then with `allowHealthIndicatorToFail`), accepting that the instance leaves the
load balancer while the breaker is open. The probe mechanics, timings and the Spring Boot group configuration are covered in
xref:backend/kubernetes/health-probes-and-lifecycle.adoc[Health Probes and Lifecycle].

== Micrometer meters

When a `MeterRegistry` bean exists, every module's auto-configuration registers a `Tagged...MetricsPublisher` that binds the
meters of each instance as it is created, so breakers created later by name get meters too. All the meter names below are the
constants of the `...MetricNames` classes in `resilience4j-micrometer` at v2.4.0, and each tag was checked against
`/actuator/prometheus` in the sample run. Micrometer names use dots; the Prometheus registry rewrites them:

* dots become underscores;
* a `Timer` becomes a `summary` with `_seconds_count`, `_seconds_sum` and a separate `_seconds_max` gauge (and `_bucket`
  series when histograms are switched on);
* a counter, including the `FunctionCounter` that the retry module uses, gets the suffix `_total`;
* a gauge keeps its name.

Every meter carries the tag `name` (the instance name), any registry tags, and the per-module tags in the tables. A tag that
is a *label* of every series in Prometheus is also what `by (name)` aggregations in the alert rules use.

=== Controlling the meters

* *Switch a module's meters off:* `resilience4j.circuitbreaker.metrics.enabled=false` (likewise `retry`, `ratelimiter`,
  `bulkhead`, `thread-pool-bulkhead`, `timelimiter`). In the run, `resilience4j.retry.metrics.enabled=false` removed every
  `resilience4j_retry_*` series and left the others.
* *Add tags to every instance of a module:* `resilience4j.<module>.tags.<key>: <value>`. `resilience4j.circuitbreaker.tags.team=checkout`
  produced `resilience4j_circuitbreaker_state{application="bookshelf",name="pricing",state="closed",team="checkout"}`. The
  `application` label in that line comes from `management.metrics.tags.application`.
* *Turn on histograms or service-level objectives:* these are standard Micrometer distribution settings addressed by the
  Micrometer meter name. `management.metrics.distribution.percentiles-histogram.resilience4j.circuitbreaker.calls=true` added
  `resilience4j_circuitbreaker_calls_seconds_bucket{...,le="0.001"}` series in the run, and
  `management.metrics.distribution.slo.resilience4j.circuitbreaker.calls=100ms,500ms` adds fixed buckets. Histograms multiply
  the series count by the number of buckets, so enable them for the call timers you will actually query.
* *Rename a meter:* declare your own publisher bean with a names object; the auto-configured one is
  `@ConditionalOnMissingBean` and backs off.

.Renaming the circuit breaker state meter
[source,java]
----
@Configuration
class BreakerMetricNames {

    @Bean
    TaggedCircuitBreakerMetricsPublisher breakerMetrics(MeterRegistry registry) {
        return new TaggedCircuitBreakerMetricsPublisher(
            CircuitBreakerMetricNames.custom().stateMetricName("bookshelf.breaker.state").build(),
            registry);
    }
}
----

Source: the
https://github.com/resilience4j/resilience4j/blob/v2.4.0/resilience4j-micrometer/src/main/java/io/github/resilience4j/micrometer/tagged/CircuitBreakerMetricNames.java[`CircuitBreakerMetricNames` at v2.4.0].
In the run the series was exposed as `bookshelf_breaker_state{name="pricing",state="closed"}`, the default
`resilience4j_circuitbreaker_state` was gone, and `resilience4j_circuitbreaker_calls_seconds_count` was untouched, because only
the state name had been overridden. Renaming breaks every dashboard and alert that uses the default name, including the
official Grafana dashboard, so do it only when a naming convention forces it.

* *Legacy binders:* `resilience4j.<module>.metrics.legacy.enabled=true` registers the older `Tagged...Metrics` `MeterBinder`
  instead of the publisher. The publisher is the default and the right choice.

The meters are updated by the instance itself, not by the annotation: a breaker used from `Decorators`, from a Reactor
operator or from a Feign interceptor is measured exactly like an annotated one, as long as the instance comes from the
registry. An instance built with `CircuitBreaker.ofDefaults("x")` outside the registry has no meters at all.

|Counts of closed, open (`open\|forced_open`) and half-open breakers from `resilience4j_circuitbreaker_state`, and a time series of the states.

|CircuitBreaker

Source: https://resilience4j.readme.io/docs/grafana-1[Resilience4j: Grafana] and the dashboard file. Four things to know before
relying on it:

* It filters on labels that the application must provide. The `Application` variable is
  `label_values(jvm_info, application)`, so the service needs the common tag `management.metrics.tags.application`, which the
  configuration above sets, and the `Instance` variable uses the `instance` label that Prometheus adds. Without the
  `application` tag the retry and bulkhead panels are empty.
* Its buffered-calls panel also queries `resilience4j_circuitbreaker_max_buffered_calls`. That meter does not exist in 2.4.0
  (it is in the readme.io Micrometer table, which describes 2.2.0, but not in the source); the panel shows the buffered calls
  and an empty second series.
* It has no panels for rate limiters, time limiters, thread-pool bulkheads, `@Timer` meters, or the not-permitted counter.
  Everything those modules expose is a meter in the tables above, so add panels from them. The thread-pool saturation view is
  `resilience4j_bulkhead_queue_depth` against `resilience4j_bulkhead_queue_capacity`, and the not-permitted rate is
  `rate(resilience4j_circuitbreaker_not_permitted_calls_total[5m])`.
* The readme.io Grafana page was last updated years before Resilience4j 2.x and shows screenshots of the old layout. The file in
  the repository is the reference.

== Logging the event streams

Every instance has an `EventPublisher`: `circuitBreaker.getEventPublisher()`, and the same on `Retry`, `RateLimiter`, `Bulkhead`,

`onStateTransition`, `onCallNotPermitted`, `onRetry`, `onFailedAcquire`, `onCallRejected` and so on) and a catch-all
`onEvent`. The listener runs synchronously on the thread that produced the event, so it must be fast and must not throw.

=== Registering listeners for every instance

A listener on an instance has to be attached before the first event, and breakers created by name at runtime would be missed
by a loop over `getAllCircuitBreakers()` at start-up. The registry's own event consumer solves both: a `RegistryEventConsumer`
bean is called each time an instance is added, and the Boot auto-configuration collects every such bean.

.Logging every state transition and rejection of every breaker, including ones created later
[source,java]
----
package com.example.bookshelf.config;

import io.github.resilience4j.circuitbreaker.CircuitBreaker;
import io.github.resilience4j.core.registry.EntryAddedEvent;
import io.github.resilience4j.core.registry.EntryRemovedEvent;
import io.github.resilience4j.core.registry.EntryReplacedEvent;
import io.github.resilience4j.core.registry.RegistryEventConsumer;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

@Configuration
class ResilienceEventLogging {

    private static final Logger LOG = LoggerFactory.getLogger("bookshelf.resilience.events");

    @Bean
    RegistryEventConsumer<CircuitBreaker> circuitBreakerLogging() {
        return new RegistryEventConsumer<>() {
            @Override
            public void onEntryAddedEvent(EntryAddedEvent<CircuitBreaker> added) {
                added.getAddedEntry().getEventPublisher()
                    .onStateTransition(e -> LOG.warn("circuit breaker '{}' {}",
                        e.getCircuitBreakerName(), e.getStateTransition()))
                    .onCallNotPermitted(e -> LOG.warn("circuit breaker '{}' rejected a call",
                        e.getCircuitBreakerName()));
            }

            @Override
            public void onEntryRemovedEvent(EntryRemovedEvent<CircuitBreaker> removed) { }

            @Override
            public void onEntryReplacedEvent(EntryReplacedEvent<CircuitBreaker> replaced) { }
        };
    }
}
----

Source: https://resilience4j.readme.io/docs/getting-started-3[Resilience4j: Spring Boot 2 & 3] (event consumer registry) and the
https://github.com/resilience4j/resilience4j/blob/v2.4.0/resilience4j-core/src/main/java/io/github/resilience4j/core/registry/RegistryEventConsumer.java[`RegistryEventConsumer` at v2.4.0].

== Alerting rules

Alerts should fire on symptoms the team can act on, and every rule below uses a meter from the tables above. The rules were
checked by extracting every `resilience4j_*` name from the expressions and looking each one up in the real scrape of the
sample run; all of them are present, and every label value used in a selector (`state="open"`, `kind="failed_with_retry"`,
`kind="timeout"`) appears in that scrape. The expressions were not evaluated by a Prometheus server, because none was
available; run `promtool check rules` on the file before loading it.

.Prometheus alerting rules for the Bookshelf resilience meters
[source,yaml]
----
groups:
  - name: bookshelf-resilience
    rules:
      - alert: BookshelfCircuitBreakerOpen
        expr: max by (application, instance, name) (resilience4j_circuitbreaker_state{state=~"open|forced_open"}) == 1
        for: 2m
        labels:
          severity: page
        annotations:
          summary: "Circuit breaker {{ $labels.name }} on {{ $labels.instance }} has been open for 2 minutes"

      - alert: BookshelfCircuitBreakerRejectingCalls
        expr: sum by (application, name) (rate(resilience4j_circuitbreaker_not_permitted_calls_total[5m])) > 0
        for: 5m
        labels:
          severity: ticket
        annotations:
          summary: "Breaker {{ $labels.name }} is rejecting {{ $value | humanize }} calls per second"

      - alert: BookshelfHighRetryRate
        expr: |
          sum by (application, name) (rate(resilience4j_retry_calls_total{kind=~"successful_with_retry|failed_with_retry"}[5m]))
            /
          sum by (application, name) (rate(resilience4j_retry_calls_total[5m]))
            > 0.2
        for: 10m
        labels:
          severity: ticket
        annotations:
          summary: "More than 20% of calls through retry {{ $labels.name }} needed a retry"

      - alert: BookshelfRetriesExhausted
        expr: sum by (application, name) (rate(resilience4j_retry_calls_total{kind="failed_with_retry"}[5m])) > 0
        for: 5m
        labels:
          severity: page
        annotations:
          summary: "Retry {{ $labels.name }} keeps giving up after its last attempt"

      - alert: BookshelfBulkheadSaturated
        expr: |
          resilience4j_bulkhead_available_concurrent_calls
            /
          resilience4j_bulkhead_max_allowed_concurrent_calls
            < 0.1
        for: 5m
        labels:
          severity: ticket
        annotations:
          summary: "Bulkhead {{ $labels.name }} has had less than 10% of its permits free for 5 minutes"

      - alert: BookshelfThreadPoolQueueFilling
        expr: |
          resilience4j_bulkhead_queue_capacity > 0
            and
          resilience4j_bulkhead_queue_depth / resilience4j_bulkhead_queue_capacity > 0.8
        for: 5m
        labels:
          severity: ticket
        annotations:
          summary: "Thread-pool bulkhead {{ $labels.name }} queue is more than 80% full"

      - alert: BookshelfTimeLimiterTimeouts
        expr: sum by (application, name) (rate(resilience4j_timelimiter_calls_total{kind="timeout"}[5m])) > 0.1
        for: 5m
        labels:
          severity: ticket
        annotations:
          summary: "TimeLimiter {{ $labels.name }} is cutting off calls"
----

Source: https://prometheus.io/docs/prometheus/latest/configuration/alerting_rules/[Prometheus: Alerting rules] for the rule
format, and the meters of the sample run. How to read them:

* *Open breaker.* The state gauge is `1.0` for exactly one `state` label per breaker, so selecting `open` and `forced_open` and
  comparing with `1` finds breakers in either condition. The `for: 2m` keeps a breaker that opens and recovers in one
  `waitDurationInOpenState` cycle from paging anybody. A breaker you forced open on purpose will page too, which is usually
  what you want.
* *Retry rate.* The counter counts calls, so the ratio is "the share of calls that needed at least one retry". A steady 5 percent
  can be normal; a jump to 20 percent means the dependency is flaky even if users still get answers, which is exactly when
  retries hide an outage. `failed_with_retry` is the share that did not recover, which is the actionable one. Remember that
  retries multiply load, so a rising retry rate is also a rising load on the dependency.
* *Bulkhead saturation.* The semaphore ratio uses the two gauges; a `maxWaitDuration` of zero makes a full bulkhead reject at
  once, so the ratio near `0` for minutes means users are being rejected. For the thread pool the signal is the queue filling
  up, and the extra `queue_capacity > 0` selector keeps a pool configured with `queueCapacity: 0` (a `SynchronousQueue`, always
  empty by design) from dividing zero by zero. Neither bulkhead kind has a rejection counter, so count the rejections from the
  fallback or from `CALL_REJECTED` events when you need a rate.
* *Everything uses `by (application, name)`.* Remove the `application` label from the aggregations if the service does not set
  the common tag.

Prometheus has to be allowed to scrape the secured endpoint. The scrape job below reads the password of the monitoring user
from a file mounted from a secret, which keeps it out of the configuration.

== Tracing context through bulkhead threads

A call that goes through a `ThreadPoolBulkhead` runs on a pool thread, and every `ThreadLocal` of the caller is invisible
there: the logging MDC, the Spring Security context, the current Micrometer observation and, with it, the trace and span. A
trace that stops at the bulkhead, or log lines on the pool thread without a `traceId`, are the symptoms. The semaphore
bulkhead, the circuit breaker, the retry and the rate limiter run on the caller's thread and have no such problem. The
mechanism and the MDC and security-context propagators are described in
xref:backend/resilience/bulkhead.adoc[Bulkhead]; this section is about the Micrometer side.

.How a ContextPropagator carries the observation to the pool thread
[mermaid]
....
sequenceDiagram
    participant R as Request thread
    participant B as ThreadPoolBulkhead
    participant P as bulkhead-recommendations-1
    R->>R: Observation started, traceId in MDC
    R->>B: submit the call
    B->>R: retrieve() captures a ContextSnapshot
    B->>P: hand the task to a pool thread
    P->>P: copy() restores every registered ThreadLocal
    P->>P: the task runs with the observation, span and MDC
    P->>P: clear() closes the scope in a finally block
    P-->>R: CompletableFuture completes
....

The bridge is one `ContextPropagator` that takes a `ContextSnapshot` from Micrometer's `context-propagation` library on the
caller thread and restores it on the pool thread. It is the propagator from the Bulkhead page, shown again here because the
tracing behaviour needs it.

.A ContextPropagator for every ThreadLocal registered in Micrometer's ContextRegistry
[source,java]
----
public class SnapshotContextPropagator implements ContextPropagator<ContextSnapshot> {

    private static final ContextSnapshotFactory FACTORY = ContextSnapshotFactory.builder().build();
    private static final ThreadLocal<ContextSnapshot.Scope> SCOPE = new ThreadLocal<>();

    @Override
    public Supplier<Optional<ContextSnapshot>> retrieve() {
        return () -> Optional.of(FACTORY.captureAll());
    }

    @Override
    public Consumer<Optional<ContextSnapshot>> copy() {
        return snapshot -> snapshot.ifPresent(s -> SCOPE.set(s.setThreadLocals()));
    }

    @Override
    public Consumer<Optional<ContextSnapshot>> clear() {
        return snapshot -> {
            ContextSnapshot.Scope scope = SCOPE.get();
            if (scope != null) {
                scope.close();
                SCOPE.remove();
            }
        };
    }
}
----

[source,yaml]
----
resilience4j:
  thread-pool-bulkhead:
    instances:
      recommendations:
        coreThreadPoolSize: 2
        maxThreadPoolSize: 4
        queueCapacity: 10
        contextPropagators:
          - com.example.bookshelf.SnapshotContextPropagator
----

Source: https://docs.micrometer.io/context-propagation/reference/[Micrometer Context Propagation],
https://docs.micrometer.io/micrometer/reference/observation.html[Micrometer Observation] and
https://docs.spring.io/spring-boot/reference/actuator/tracing.html[Spring Boot: Tracing]. The class must be on the classpath
with a no-argument constructor (`contextPropagators` takes class names), and `io.micrometer:context-propagation` must be a
dependency. The run used Spring Boot's Brave tracing bridge (`micrometer-tracing-bridge-brave` and
`spring-boot-micrometer-tracing-brave`) with `management.tracing.sampling.probability=1.0`, and a `recommendations` method
annotated `@Bulkhead(name = "recommendations", type = Bulkhead.Type.THREADPOOL)` that records what it sees on its pool thread.
The results were not what a quick read of the documentation suggests:

[cols="3,2,3,2",options="header"]
|===
|What the caller had open |Propagator |What the pool thread saw |Verdict

|A span from `tracer.nextSpan().start()` and an MDC entry `requestId`
|`SnapshotContextPropagator`, no MDC accessor registered
|`requestId=null`, `traceId=none`, `mdcTraceId=null`
|Nothing carried over.

|The same, after `ContextRegistry.getInstance().registerThreadLocalAccessor(new Slf4jThreadLocalAccessor("requestId", "traceId", "spanId"))`
|`SnapshotContextPropagator`
|`requestId=req-42`, MDC `traceId` equal to the caller's, but `tracer.currentSpan()` is `null`
|The log context arrived; the span did not.

|An `Observation` started with `Observation.start("bookshelf.request", observationRegistry)` and made current
|`SnapshotContextPropagator`
|The same `traceId` from `tracer.currentSpan()`, the MDC `traceId`, and the observation `bookshelf.request` from `observationRegistry.getCurrentObservation()`
|The whole context arrived.
|===

Source: the output of the sample run (three calls through the same bulkhead, with the pool thread names
`bulkhead-recommendations-1` and `-2`). What follows from it:

* The snapshot carries the ``ThreadLocal``s that are *registered in the `ContextRegistry`*. The Observation accessor is
  registered by `micrometer-observation` itself, so an observation, and the span that the tracing handler binds to it, crosses
  the thread boundary with this one propagator. A bare tracer span that is not part of an observation does not.
* The MDC is not registered by default. `Slf4jThreadLocalAccessor` exists in `io.micrometer.context.integration`, but it has to
  be registered, once, for the keys you want (the accessor takes the key names). Spring Boot's tracing support puts `traceId`
  and `spanId` in the MDC of the thread where the span is current, which is why the MDC `traceId` arrived in the second row once
  the accessor was registered.
* Code that creates its own spans with the bare `Tracer` API loses them at the pool. Wrap the work in an observation
  (`Observation.createNotStarted(...)` and `start()`) so that the span is bound to something the snapshot carries.
* The propagator runs for `ThreadPoolBulkhead` only. A semaphore bulkhead, a retry or a breaker needs none.

== A worked example: Bookshelf in an outage

The pieces above come together in one scenario: the `pricing-service` starts answering `503`, and the on-call engineer sees it.
The configuration is the monitoring YAML and the health block earlier on this page, the security configuration, the logging
consumer and the alert rules. The `pricing` call is the one from the first page of the section:

.The instrumented pricing call
[source,java]
----
package com.example.bookshelf.pricing;

@Component
public class PricingClient {

    private final RestClient http;

    public PricingClient(RestClient.Builder builder,
                         @Value("${bookshelf.pricing.url}") String baseUrl) {
        this.http = builder.baseUrl(baseUrl).build();
    }

    @CircuitBreaker(name = "pricing", fallbackMethod = "lastKnownPrice")
    public Money price(String isbn) {
        return http.get().uri("/prices/{isbn}", isbn).retrieve().body(Money.class);
    }

    Money lastKnownPrice(String isbn, Throwable t) {
        return new Money(isbn, 0, true);       // stale marker, no exception for the caller
    }
}
----

Source: https://resilience4j.readme.io/docs/getting-started-3[Resilience4j: Spring Boot 2 & 3] (annotations with a fallback). The
sample run replayed an outage against a version of this class whose body threw when a switch was set. The breaker has a
four-call window (`slidingWindowSize: 4`, `minimumNumberOfCalls: 4`, threshold 50 percent). After three good calls the switch
was set and eight more calls were made. Each signal shows it in its own way:

|Callers

|`GET /actuator/circuitbreakerevents/pricing`

|`GET /actuator/health`

|`/actuator/prometheus`

never fails would not open it; the `slowCallRate` field of the endpoint and `resilience4j_circuitbreaker_slow_call_rate` would

each logical call once. Read the two together before you decide that "the breaker saw three failures".

== Common pitfalls

[cols="2,3",options="header"]
|===
|Pitfall |What to do instead

|Exposing `*` or the circuitbreakers endpoint on the public port
|Expose the endpoints by name, on `management.server.port`, behind authentication, with `management.endpoint.circuitbreakers.access=read-only` unless an operator profile needs the write operation.

|Posting a state change with a typo in the name
|The endpoint creates a new default breaker. Check the name against `GET /actuator/circuitbreakers` first, and delete nothing in a hurry: the instance stays until the JVM restarts.

|Enabling `management.health.circuitbreakers.enabled` and not exposing `health`
|The application fails to start for lack of a `StatusAggregator` bean. Expose `health` whenever the indicator is enabled.

|Setting `registerHealthIndicator` but not `management.health.circuitbreakers.enabled`
|The indicator bean is `@ConditionalOnProperty` with no default, so nothing appears. Set both.

|Adding `circuitBreakers` to the liveness group
|A dependency outage restarts every replica. Keep the indicators in a custom group, and out of liveness.

|Using `allowHealthIndicatorToFail` on a breaker with a good fallback
|It turns a degraded service `DOWN` and removes it from the load balancer. Use it only for a dependency the service cannot work without.

|Expecting `CIRCUIT_OPEN` to turn the service `DOWN`
|It is a custom status that the default `StatusAggregator` does not rank; it never worsens the aggregate. Alert on the meters, not the top-level health.

|Reading the endpoint failure rate as a percentage of all calls
|It is the rate over the current window, `-1.0%` until `minimumNumberOfCalls`. Do not alert on it directly; alert on the state gauge.

|Alerting on a missing counter for bulkhead rejections
|There is none. Bulkheads expose gauges and `CALL_REJECTED` events, so alert on saturation or count the fallback.

|Querying `rate()` on the breaker `state` gauge, or `sum` of `state` without a selector
|The gauge is one series per state with `1.0` on the current one. Select the state, then `max by (name)`.

|Importing the Grafana dashboard without the `application` tag
|The variables and the retry and bulkhead panels are empty. Set `management.metrics.tags.application`.

|High-cardinality tags
|The `failure` tag of `@Timer` is the exception class name, and registry tags are added to every series. Keep tag values bounded, and never tag with an ISBN or a user id.

|Pool threads without a propagator
|A trace that ends at the bulkhead and log lines without `traceId`. Use the `ContextSnapshot` propagator, register the MDC accessor, and use an observation rather than a bare span.

|Logging every success event
|One log line per call. Log transitions and rejections, and count the rest with meters.
|===

== What changed recently

* *Resilience4j 2.4.0.* The Spring Boot 4 starter (`resilience4j-spring-boot4`) moved the autoconfiguration to the Boot 4
  health and Actuator packages. The meter names, the tags, the endpoint ids and the endpoint JSON described on this page are
  the same as on 2.3.0 and Boot 3. Two details to know when reading the older docs: the readme.io Micrometer page (written for
  2.2.0) still lists `resilience4j.circuitbreaker.max.buffered.calls`, which the 2.4.0 source does not register, shows the retry
  meter as a gauge with dotted `kind` values such as `successful.without.retry` where the source has a `FunctionCounter` named
  `resilience4j_retry_calls_total` with underscored kinds, and its Grafana page is unchanged for years.
* *Spring Boot 4.* `HealthIndicator` and `Health` moved to `org.springframework.boot.health.contributor` and `StatusAggregator`
  to `org.springframework.boot.health.actuate.endpoint` (Boot 3: `org.springframework.boot.actuate.health`). The
  Actuator security matcher `EndpointRequest` is in `org.springframework.boot.security.autoconfigure.actuate.web.servlet`
  (Boot 3: `org.springframework.boot.actuate.autoconfigure.security.servlet`). Applications that only use properties are
  unaffected. In the sample run the liveness and readiness groups were present without configuration on Boot 4.1.1, while on
  Boot 3.5.16 outside Kubernetes a `liveness` group that included `livenessState` failed at start-up until
  `management.endpoint.health.probes.enabled=true` was set.
* *Spring Boot 3.4 and later.* `management.endpoint.<id>.access` (`none`, `read-only`, `unrestricted`) replaces
  `management.endpoint.<id>.enabled`; use it to remove the circuit breaker write operation.
* *Spring Boot tests.* On Spring Boot 3.5.16 a `@SpringBootTest` does not export metrics unless the test class is annotated
  with `@AutoConfigureObservability`; without it the `/actuator/prometheus` response in the test had no `resilience4j_` series.
  The Boot 4.1.1 sample tests produced the series without the annotation.
* *Micrometer 1.17 and the Prometheus client 1.x.* Timers are exposed as summaries with `_seconds_count`, `_seconds_sum` and a
  separate `_seconds_max` gauge, and counters carry `_total`, as shown in the scrape above; dashboards built for the old
  `_count` and `_sum` names of Resilience4j 1.x on Micrometer 1.5 need those names updated.
* *Migration.* The full Resilience4j and Spring Boot version changes are collected in
  xref:backend/resilience/migration-and-whats-changed.adoc[Migration & What's Changed].
