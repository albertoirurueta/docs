[#overview]
== SQLModel: SQLAlchemy 2.0 and Pydantic in One Class

SQLModel is a library by the author of FastAPI, built to be the natural fit for FastAPI applications that need a
relational database. It adds almost no machinery of its own; it fuses two libraries you already know:

[cols="1,2,2",options="header"]
|===
| Layer | Provides | Where you meet it
| SQLAlchemy 2.0 | Engine, connection pool, Core SQL expressions, the ORM (mapped classes, relationships, the unit of work), dialects for PostgreSQL, MySQL, SQLite, Oracle, SQL Server | `create_engine`, `Session`, `select`, `Relationship`, every database error (`sqlalchemy.exc`)
| Pydantic v2 | Validation, parsing, serialization, JSON Schema | Field constraints, `model_validate`, `model_dump`, the OpenAPI schemas FastAPI generates
| SQLModel | One class that is both: a `SQLModel` subclass with `table=True` is an ORM-mapped table _and_ a Pydantic model; without `table=True` it is a plain Pydantic data model | `Field(primary_key=True, foreign_key=..., index=True)`, `Relationship`, `session.exec()`, `sqlmodel_update()`
|===

`sqlmodel` provides its own `Field`, `Relationship`, `Session`, `AsyncSession` (in `sqlmodel.ext.asyncio.session`), a typed `select` and
`col`, and re-exports SQLAlchemy's `create_engine` and `func` unchanged (verified: they are the same objects). A typical
import line is `from sqlmodel import Field, Session, SQLModel, create_engine, select`. Everything
else on the SQLAlchemy side (exceptions, `selectinload`, `event`, pool classes, the async extension) is imported from
`sqlalchemy` directly. That is intentional: SQLModel is a thin layer, and the SQLAlchemy documentation remains the reference
for anything relational.

Install it with the project tool of your choice (the official tutorial uses `uv add sqlmodel`; `pip install sqlmodel`
works the same). A driver is needed for anything other than SQLite, which ships with Python:

[source,bash]
----
uv add sqlmodel                    # SQLModel pulls in SQLAlchemy 2.0 and Pydantic v2
uv add "psycopg[binary]"           # PostgreSQL, synchronous (psycopg 3)
uv add asyncpg                     # PostgreSQL, asynchronous
uv add aiosqlite                   # SQLite, asynchronous (handy for tests)
uv add alembic                     # migrations
----

Source: https://fastapi.tiangolo.com/tutorial/sql-databases/[FastAPI: SQL (Relational) Databases]

SQLModel is still 0.0.x, like FastAPI is still 0.x: pin both. When should you reach for something else?

[cols="1,2,2",options="header"]
|===
| Choice | Pick it when | Cost
| SQLModel | You want one set of classes for table, validation and OpenAPI, and the official FastAPI tutorial's approach | Table models and data models are two different jobs (below); the SQLModel release line is 0.0.x and lags SQLAlchemy 2.1
| Plain SQLAlchemy 2.0 ORM with Pydantic schemas | You want full SQLAlchemy typing (`Mapped[...]`), no SQLModel version coupling, or an existing SQLAlchemy codebase | You write the Pydantic schemas yourself and convert with `from_attributes`
| SQLAlchemy Core or raw DB-API | Reporting queries, bulk operations, tiny services, or a team that prefers SQL text | You manage mapping, transactions and thread-safety yourself
| A non-relational store | The data is documents, a cache, search or vectors rather than related rows | See the NoSQL page of this section and xref:database/index.adoc[Databases]
|===

The relational background (keys, joins, normalization, transactions) is on this site: xref:database/sql/index.adoc[SQL],
xref:database/sql/relations.adoc[relations], xref:database/sql/normalization.adoc[normalization] and
xref:database/sql/transactions.adoc[transactions]. For the same ORM ideas on the JVM, compare
xref:backend/hibernate/index.adoc[Hibernate Reference]. For choosing a store at all, see
xref:database/choosing-the-right-database.adoc[Choosing the Right Database].

[#engine-and-session]
== Engine, Session Dependency and Table Creation

Three objects do all the plumbing, and each has a clear lifetime:

[cols="1,2,2",options="header"]
|===
| Object | Lifetime | Job
| `engine` | One per process, created at import time | Holds the connection pool and the dialect. Creating it does not connect.
| `Session` | One per request | The unit of work: tracks the objects you loaded or added and flushes them in a transaction. Not thread-safe, never shared.
| Tables | Created once | `SQLModel.metadata.create_all(engine)` for a prototype, Alembic for anything that must evolve (below)
|===

The engine is built from a URL. The official tutorial uses a SQLite file so that the code runs as it is. The session is
a dependency with `yield`: it opens a `Session`, hands it to the path operation, and closes it afterwards, which is
the pattern described on xref:backend/fastapi/dependencies-with-yield.adoc[Dependencies with yield]. The `SessionDep`
alias keeps every route signature short. Table creation moves into the lifespan, the modern replacement for the
deprecated `startup` and `shutdown` events (FastAPI 0.93.0, 2023-03-07), whose full treatment is on
xref:backend/fastapi/settings-lifespan-and-background-tasks.adoc[Settings, Lifespan & Background Tasks].

[source,python]
----
import os
import secrets
from collections.abc import AsyncIterator, Iterator
from contextlib import asynccontextmanager
from typing import Annotated

from fastapi import Depends, FastAPI, Header, HTTPException, Query, Response
from pydantic import field_validator
from sqlalchemy.exc import IntegrityError
from sqlmodel import Field, Session, SQLModel, create_engine, func, select


DATABASE_URL = os.environ.get("DATABASE_URL", "sqlite:///bookshelf.db")
connect_args = {"check_same_thread": False} if DATABASE_URL.startswith("sqlite") else {}
engine = create_engine(DATABASE_URL, connect_args=connect_args)


def get_session() -> Iterator[Session]:
    with Session(engine) as session:
        yield session


SessionDep = Annotated[Session, Depends(get_session)]


@asynccontextmanager
async def lifespan(app: FastAPI) -> AsyncIterator[None]:
    SQLModel.metadata.create_all(engine)
    yield
    engine.dispose()


app = FastAPI(title="Bookshelf API", lifespan=lifespan)


def require_admin(x_admin_key: Annotated[str | None, Header()] = None) -> None:
    expected = os.environ.get("BOOKSHELF_ADMIN_KEY", "")
    if not expected or not x_admin_key or not secrets.compare_digest(x_admin_key, expected):
        raise HTTPException(status_code=401, detail="Admin key required")
----

Source: https://fastapi.tiangolo.com/tutorial/sql-databases/[FastAPI: SQL (Relational) Databases]

This is the top of `bookshelf_db.py`; the models and the routes follow in the next sections. Points to take from it:

* `connect_args={"check_same_thread": False}` is for SQLite only and is explained in the pooling section: FastAPI may use
  one connection from different threads. It is not passed for other databases.
* The URL comes from the environment (`DATABASE_URL`), with a SQLite file as the local default. Never hard-code a
  server URL with a password; a settings class that reads a secret file is shown in the PostgreSQL section.
* `get_session` is a generator function declared with `def`, so FastAPI runs it in the threadpool, exactly like a
  `def` path operation. A `with Session(engine) as session` block guarantees `close()` runs, which returns the
  connection to the pool.
* `create_all` creates only tables that do not exist. It never alters an existing table, so changing a model later
  needs a migration. It is also blocking, which is acceptable once at startup. In the lifespan it runs before the
  first request is served; the `engine.dispose()` after `yield` closes the pooled connections on shutdown.
* The `require_admin` dependency protects the destructive route below: the key comes from the environment, is
  compared with `secrets.compare_digest` (constant-time), and an unset key rejects everybody. Real applications use
  the OAuth2 machinery from xref:backend/fastapi/security-fundamentals.adoc[Security Fundamentals] instead.
* The official tutorial page still shows `@app.on_event("startup")` for table creation. Prefer the lifespan form.

[#model-family]
== Table Models and Data Models

A single class that is the table, the request body and the response is tempting and wrong: the client could set the
`id`, the response would expose columns that must stay private, and a PATCH would need every field to be optional.
The documented answer is a small family of classes. Only one of them has `table=True`:

[cols="1,1,3",options="header"]
|===
| Class | `table=True` | Role
| `BookBase` | no | The fields shared by all the others (title, ISBN, year) with their validation rules, written once
| `Book` | yes | The table: `BookBase` plus the database-only columns (`id`, `internal_notes`). Never used as a request body, and never returned as is.
| `BookCreate` | no | The POST body: the shared fields, no `id`
| `BookPublic` | no | The response: shared fields plus the `id`, which is always present once the row exists
| `BookUpdate` | no | The PATCH body: every field optional, so a client sends only what changes
|===

[source,python]
----
class BookBase(SQLModel):
    title: str = Field(index=True, min_length=1, max_length=200)
    isbn: str = Field(unique=True, min_length=10, max_length=17)
    year: int | None = Field(default=None, ge=1400, le=2100)


class Book(BookBase, table=True):
    id: int | None = Field(default=None, primary_key=True)
    internal_notes: str | None = None  # never leaves the server


class BookCreate(BookBase):
    pass


class BookPublic(BookBase):
    id: int


class BookUpdate(SQLModel):
    title: str | None = Field(default=None, min_length=1, max_length=200)
    isbn: str | None = Field(default=None, min_length=10, max_length=17)
    year: int | None = Field(default=None, ge=1400, le=2100)

    @field_validator("title", "isbn")
    @classmethod
    def not_null(cls, value: str | None) -> str:
        if value is None:  # sent explicitly as null, not merely omitted
            raise ValueError("must not be null")
        return value


class BooksPage(SQLModel):
    items: list[BookPublic]
    total: int
    offset: int
    limit: int
----

Source: https://fastapi.tiangolo.com/tutorial/sql-databases/#update-the-app-with-multiple-models[FastAPI: SQL Databases, multiple models]

What each detail does:

* *`Field(...)` carries both worlds.* `min_length`, `max_length`, `ge` and `le` are Pydantic constraints (validated in the
  request, and published in the OpenAPI schema); `index=True`, `unique=True` and `primary_key=True` are database
  settings. One declaration, both effects. `int | None` makes a column nullable.
* *`id: int | None = Field(default=None, primary_key=True)`.* The `None` default is for the moment before the row is
  inserted. In `BookPublic` the `id` is a plain `int`, so the OpenAPI response schema marks it required.
* *`BookUpdate` and explicit nulls.* All fields default to `None`, which makes a missing field and `"title": null`
  indistinguishable by value. `exclude_unset=True` (below) tells them apart, but an explicit `null` for a NOT NULL
  column would reach the database. The `field_validator` rejects it with a 422. Validators run only for values that
  were sent, so omitted fields are untouched.
* *Table models skip validation on construction.* `Book(title="", isbn="1")` is created without complaint (verified): that is
  how SQLAlchemy mapped classes behave. Validation comes from `Book.model_validate(book_create)`, which does validate
  (and also copies the data into a table object). That is why the POST route validates the body model first and then
  converts, rather than building `Book(**data)` by hand.
* *Never return the table model.* Declaring `-> Book` alone returns every column, including the private one: a verified
  run returned `internal_notes` to the client, and the OpenAPI schema grew a `Book` component. Setting
  `response_model=BookPublic` filters the output and documents the right schema. The return annotation alone is also
  enough since FastAPI 0.89.0 (2023-01-07) when it is itself a data model such as `-> BookPublic`; the routes here keep
  `response_model=` because they return a different class (the table object) than the one they document. See
  xref:backend/fastapi/response-models-and-return-types.adoc[Response Models & Return Types].
* *Pydantic v2 vocabulary.* SQLModel 0.0.47 needs Pydantic 2.11 or newer: `model_validate` and `model_dump`, not the
  v1 `parse_obj` and `.dict()`, and `from_attributes` (set by SQLModel for you) instead of `orm_mode`. Pydantic
  basics are on xref:backend/fastapi/pydantic-v2-essentials.adoc[Pydantic v2 Essentials] and body models on
  xref:backend/fastapi/request-body-and-models.adoc[Request Body & Models].
* *`session.exec()`, not `session.execute()` or `session.query()`.* `exec` is SQLModel's own method: for a
  `select(Book)` it returns the `Book` objects directly (a scalar result), where SQLAlchemy's `execute` returns rows
  you must unpack. `session.query()` still works but emits a `DeprecationWarning` that points back to `exec()` (verified).

[#crud]
== Full CRUD with PATCH

The routes below are the rest of `bookshelf_db.py`, in file order. Create first:

[source,python]
----
@app.post("/books", response_model=BookPublic, status_code=201)
def create_book(book: BookCreate, session: SessionDep) -> Book:
    db_book = Book.model_validate(book)
    session.add(db_book)
    try:
        session.commit()
    except IntegrityError:
        session.rollback()
        raise HTTPException(status_code=409, detail="ISBN already exists")
    session.refresh(db_book)
    return db_book
----

Source: https://fastapi.tiangolo.com/tutorial/sql-databases/#create-a-hero[FastAPI: SQL Databases, create a hero]

`Book.model_validate(book)` validates and converts; `session.add` stages the INSERT; `session.commit` writes it. The unique
ISBN constraint is enforced by the database, so a duplicate surfaces as `IntegrityError` at commit time. The handler
rolls back (the session would otherwise be unusable until `rollback()`) and answers `409 Conflict`. After the commit,
`session.refresh(db_book)` reloads the row so the generated `id` is available: SQLAlchemy expires every attribute on
commit, and `refresh` is the explicit way to repopulate them. (The status-code and error-handling side of this is on
xref:backend/fastapi/status-codes-and-error-handling.adoc[Status Codes & Error Handling].)

Read one, update and delete (listing is covered under pagination below):

[source,python]
----
@app.get("/books/{book_id}", response_model=BookPublic)
def read_book(book_id: int, session: SessionDep) -> Book:
    book = session.get(Book, book_id)
    if book is None:
        raise HTTPException(status_code=404, detail="Book not found")
    return book


@app.patch("/books/{book_id}", response_model=BookPublic)
def update_book(book_id: int, changes: BookUpdate, session: SessionDep) -> Book:
    book = session.get(Book, book_id)
    if book is None:
        raise HTTPException(status_code=404, detail="Book not found")
    book.sqlmodel_update(changes.model_dump(exclude_unset=True))
    session.add(book)
    try:
        session.commit()
    except IntegrityError:
        session.rollback()
        raise HTTPException(status_code=409, detail="ISBN already exists")
    session.refresh(book)
    return book
----

Source: https://fastapi.tiangolo.com/tutorial/sql-databases/#read-one-hero[FastAPI: SQL Databases, read one hero]

[source,python]
----
@app.delete("/books/{book_id}", status_code=204, dependencies=[Depends(require_admin)])
def delete_book(book_id: int, session: SessionDep) -> Response:
    book = session.get(Book, book_id)
    if book is None:
        raise HTTPException(status_code=404, detail="Book not found")
    session.delete(book)
    session.commit()
    return Response(status_code=204)
----

Source: https://fastapi.tiangolo.com/tutorial/sql-databases/#update-a-hero-with-heroupdate[FastAPI: SQL Databases, update with HeroUpdate]

The PATCH route is the heart of this page:

. `changes.model_dump(exclude_unset=True)` returns a dictionary containing _only the fields the client actually sent_.
  Fields that merely hold their default `None` are excluded. Without `exclude_unset`, a request that sends only
  `{"year": 1966}` would overwrite the title and ISBN with `None`.
. `book.sqlmodel_update(data)` copies those keys onto the table object. It accepts a dictionary or a Pydantic model
  and an optional `update=` dictionary for extra values.
. `commit()` writes only what changed (SQLAlchemy's unit of work diffs the attributes), and `refresh()` returns the
  final state.

PUT and PATCH differ in what an omitted field means. PUT replaces the resource, so omitted fields are reset; PATCH leaves
them alone. This route is a PATCH, so `{"year": null}` _does_ clear the year (sent, and nullable), while
`{"title": null}` is rejected. The generic partial-update discussion is in the official
https://fastapi.tiangolo.com/tutorial/body-updates/[Body - Updates] page.

Delete answers `204 No Content`; the empty body is why the handler returns a bare `Response`. Deleting is destructive,
so the route requires the admin key (without it: `401`). A real service would check a user's role instead.

[#pagination]
== Pagination with offset and limit

An unbounded `GET /books` is a denial-of-service waiting to happen. The list route takes `offset` and `limit` query
parameters, bounds both, and orders the result so pages are stable:

[source,python]
----
@app.get("/books", response_model=BooksPage)
def list_books(
    session: SessionDep,
    offset: Annotated[int, Query(ge=0)] = 0,
    limit: Annotated[int, Query(ge=1, le=100)] = 20,
) -> BooksPage:
    total = session.exec(select(func.count()).select_from(Book)).one()
    books = session.exec(select(Book).order_by(Book.id).offset(offset).limit(limit)).all()
    items = [BookPublic.model_validate(book) for book in books]
    return BooksPage(items=items, total=total, offset=offset, limit=limit)
----

Source: https://fastapi.tiangolo.com/tutorial/sql-databases/#read-heroes[FastAPI: SQL Databases, read heroes]

* `Query(ge=0)` and `Query(ge=1, le=100)` validate in the request: asking for `limit=1000` is a `422`
  (`Input should be less than or equal to 100`, verified), not a surprise query. This is the same constraint style as
  the official tutorial's `Query(le=100)`; see xref:backend/fastapi/query-parameters.adoc[Query Parameters].
* `order_by(Book.id)` is not optional. Without an `ORDER BY`, the database may return rows in any order and the same row
  can appear on two pages (or on none). Order by a unique, indexed column.
* `select(func.count()).select_from(Book)` runs a second query for the total. Counting is a full scan on large tables;
  drop the `total` when the client does not need it.
* Offset pagination gets slower as `offset` grows, because the database still walks past the skipped rows, and it
  can skip or repeat rows when data changes between requests. Keyset (cursor) pagination avoids both; the trade-offs
  are on xref:database/pagination-strategies.adoc[Pagination: Offset vs. Keyset].
* Build the envelope with `BookPublic.model_validate(book)` for every item. Passing table objects straight into an
  envelope model happened to drop the `authors` of a nested response in a verified run on the relationships version below.

[source,bash]
----
curl 'localhost:8000/books?offset=1&limit=1'
----

[source,json]
----
{"items":[{"title":"Neuromancer","isbn":"978-0441569595","year":1984,"id":2}],"total":2,"offset":1,"limit":1}
----

[#relationships]
== Relationships: Authors and Books

A book has several authors and an author several books: a many-to-many relationship, which needs the link table from the
ER diagram. SQLModel expresses it with a link model (a table with two foreign keys that form its primary key) and two
`Relationship` attributes that point at each other with `back_populates`. Reviews are one-to-many: each review has one
book, and `cascade_delete=True` on the parent side removes the reviews when the book is deleted.

The full file below replaces `bookshelf_db.py`. Models first:

[source,python]
----
import os
import secrets
from collections.abc import AsyncIterator, Iterator
from contextlib import asynccontextmanager
from typing import Annotated, Generic, TypeVar

from fastapi import Depends, FastAPI, Header, HTTPException, Query, Response
from pydantic import field_validator
from sqlalchemy import event
from sqlalchemy.exc import IntegrityError
from sqlalchemy.orm import selectinload
from sqlmodel import Field, Relationship, Session, SQLModel, col, create_engine, func, select


class BookAuthorLink(SQLModel, table=True):
    book_id: int | None = Field(default=None, foreign_key="book.id", primary_key=True, ondelete="CASCADE")
    author_id: int | None = Field(default=None, foreign_key="author.id", primary_key=True, ondelete="CASCADE")


class AuthorBase(SQLModel):
    name: str = Field(index=True, min_length=1, max_length=120)
    born: int | None = None


class Author(AuthorBase, table=True):
    id: int | None = Field(default=None, primary_key=True)
    books: list["Book"] = Relationship(back_populates="authors", link_model=BookAuthorLink)


class BookBase(SQLModel):
    title: str = Field(index=True, min_length=1, max_length=200)
    isbn: str = Field(unique=True, min_length=10, max_length=17)
    year: int | None = Field(default=None, ge=1400, le=2100)


class Book(BookBase, table=True):
    id: int | None = Field(default=None, primary_key=True)
    authors: list[Author] = Relationship(back_populates="books", link_model=BookAuthorLink)
    reviews: list["Review"] = Relationship(back_populates="book", cascade_delete=True)


class ReviewBase(SQLModel):
    rating: int = Field(ge=1, le=5)

Details worth knowing:

* *`Relationship` attributes are not columns and not Pydantic fields on the table model's database side.* `Book.authors`
  is a Python list the ORM loads from the database. `back_populates` keeps both sides in sync when you modify one.
* *`link_model=BookAuthorLink`* tells SQLAlchemy to use that table to join `Author` and `Book`. The link table has
  no `id`; its two foreign keys are the composite primary key, which also prevents duplicate pairs.
* *`ondelete="CASCADE"` versus `cascade_delete=True`.* The first is the database foreign-key action
  (`ON DELETE CASCADE` in the DDL, visible in the migration below); the second makes the ORM delete the children it has
  loaded. They solve the same problem at two levels, and this schema declares both. The
  database action only fires if the database enforces foreign keys, which brings up the SQLite pragma below.
* *Data models stay flat.* `AuthorPublic` has no `books` and `BookPublic` has no `authors`; the nested variants
  (`BookWithAuthors`, `AuthorWithBooks`) each go one level deep. If both pointed at each other, serialization would
  recurse forever. Decide the direction per endpoint.
* *`Page` is a generic Pydantic model* (`Generic[T]`), so one envelope serves books and reviews, and OpenAPI gets
  the specific names `Page_BookWithAuthors_` and `Page_ReviewPublic_`.

How the routes use the relationship API:

* *Attaching authors at creation.* `load_authors` fetches the requested authors with `col(Author.id).in_(...)` (`col()` tells
  type checkers that this attribute is a column) and answers `404` for unknown ids. `Book.model_validate(book,
  update={"authors": authors})` validates the body and injects the loaded `Author` objects into the relationship;
  the link rows are written at commit.
* *Replacing authors with PATCH.* `author_ids` is popped from the update dictionary before `sqlmodel_update` (it is not a
  `Book` column) and assigned as `book.authors = ...`; SQLAlchemy computes which link rows to insert and delete.
* *Filtering through the link.* `?author_id=2` joins `BookAuthorLink`; the join condition is inferred from the foreign keys.
* *Eager loading.* `selectinload(Book.authors)` loads the authors of all returned books with one extra query. Without
  it, building each `BookWithAuthors` touches `book.authors` and triggers one lazy query per book: the N+1 problem
  (explained for the JVM on xref:backend/hibernate/fetching-and-n-plus-1.adoc[Fetching and the N+1 Problem]; the
  mechanics are the same). A counted run of `GET /books` with five books issued 3 statements with `selectinload` (count,
  books, authors) and 7 with lazy loading (count, books, then one per book).
* *Lazy loading works in `read_book` only because the session is still open and the driver is synchronous.* The lazy
  access runs in the threadpool inside the open session. In the async variant it fails, as shown next.
* *Deleting.* `session.delete(book)` removes the book, its link rows and its reviews. In the verified run the review
  list of a deleted book was empty afterwards and the author survived with an empty `books` list.

[#session-lifecycle]
== Session Lifecycle, Transactions and `def` versus `async def`

A session is a transaction scope. The rules that avoid most database bugs in FastAPI:

* *One session per request, created by the dependency.* Never a module-level session, and never one shared between
  threads or tasks.
* *Commit in the path operation.* Since FastAPI 0.118.0 (2025-09-29) the teardown of a default-scope `yield` dependency
  runs after the response has been sent, so a commit placed after `yield` cannot change the status code and the
  client may see `201` for a write that failed. Commit before returning, and let the dependency only close the
  session (see xref:backend/fastapi/dependencies-with-yield.adoc[Dependencies with yield] for `scope="function"`).
* *Roll back on failure.* After an exception inside a transaction (for example the `IntegrityError` above) call
  `session.rollback()` before the session is reused. Closing the session also discards uncommitted work.
* *`expire_on_commit` and `refresh`.* By default a commit expires all loaded attributes, so the next access reloads
  the row (a lazy query). That is why the routes call `refresh()` before returning, and why the async session below sets
  `expire_on_commit=False`. The relational model of transactions is on xref:database/sql/transactions.adoc[Transactions].
* *`def` routes with a synchronous driver.* FastAPI runs `def` dependencies and routes in a threadpool (40 worker
  threads by default in AnyIO, verified), so a blocking driver such as `psycopg` or `sqlite3` is fine and does not block
  the event loop. Do not call a synchronous session from an `async def` route: the call blocks the loop. See
  xref:backend/fastapi/async-and-concurrency.adoc[Async & Concurrency], in particular its sections on blocking calls and
  tuning.
* *The pool must be sized with the threadpool in mind.* Up to 40 threads can ask for a connection at once, while the default
  SQLAlchemy pool offers 5 plus 10 overflow (below).

[#testing]

The session dependency is the single seam through which every route reaches the database, which makes it the thing to
override in tests: `app.dependency_overrides[get_session]` swaps in a session bound to a throwaway in-memory database.
The in-memory URL (`sqlite://`) with `StaticPool` and `check_same_thread=False` gives every thread the same single
connection, and therefore the same tables. This keeps tests fast and independent of a server; run a small set of
tests against real PostgreSQL as well, because SQLite is more lenient (types, foreign keys, `ILIKE`, concurrency).

[#async]
== Async Sessions: AsyncSession with asyncpg

A synchronous session in a threadpool scales well enough for many services. The alternative is an async stack:
`create_async_engine`, `AsyncSession` and an async driver, with `async def` dependencies and routes, so database
waits do not occupy a thread. SQLAlchemy 2.0 ships the asyncio extension; SQLModel adds a subclass,
`sqlmodel.ext.asyncio.session.AsyncSession`, whose `exec()` is awaitable and returns the same scalar results as the
synchronous one. (Plain SQLAlchemy's `AsyncSession` has no `exec`; use `execute()` plus `scalars()` there.)

The driver changes with the URL. For PostgreSQL: a `postgresql+asyncpg://` URL (user, secret password, host, port and database name), built from
settings, never typed into source. For SQLite in tests: `sqlite+aiosqlite:///file.db`. The example runs unchanged on both
by reading `DATABASE_URL`; it was executed with `aiosqlite` only, because no PostgreSQL server was available. Creating the
`asyncpg` engine (no connection is made at that point) succeeds and uses an `AsyncAdaptedQueuePool`.

What changes compared with the synchronous version:

* *Everything that touches the database is awaited:* `await session.commit()`, `await session.refresh(...)`,
  `await session.get(...)`, `await session.exec(...)`. Forgetting an `await` returns a coroutine and a
  `RuntimeWarning: coroutine ... was never awaited`.
* *`create_all` is synchronous DDL*, so it runs through `conn.run_sync(SQLModel.metadata.create_all)` inside
  `engine.begin()`, and the shutdown awaits `engine.dispose()`.
* *`expire_on_commit=False` on the session.* After `await session.commit()`, reading an expired attribute would require
  I/O, which an async session cannot do implicitly. With `False`, the committed object stays readable (as in
  `create_review`, which returns it without a refresh). The trade-off: the object can be stale if the database changed
  it (defaults, triggers); `await session.refresh(obj)` reloads it explicitly when that matters.
* *No implicit lazy loading.* Eager-load every relationship you will serialize (`selectinload`, `joinedload`). The
  deliberately wrong `lazy-mistake` route fails in a verified run with a `ResponseValidationError` wrapping
  `MissingGreenlet: greenlet_spawn has not been called; can't call await_only() here. Was IO attempted in an unexpected
  place?`. That message always means "lazy load in async code": fix the query, not the exception.
* *`pool_pre_ping=True`.* The pool tests each connection with a cheap ping when it is checked out, so connections
  dropped by the server or a firewall are replaced silently. It costs a round trip per checkout.
* *Do not mix.* An `async def` route with a synchronous `Session` blocks the event loop; a `def` route with an
  `AsyncSession` cannot await. Pick one style per application, or per router.

Choose async when the application is already async end to end (WebSockets, streaming, many concurrent slow calls). The
simpler synchronous stack is a completely valid choice that the official tutorial uses.

[#alembic]
== Alembic Migrations

`create_all` cannot change an existing table: add a column to `Book` and the database keeps the old shape. Alembic is
SQLAlchemy's migration tool: it compares your models with the database, writes a versioned script, and applies scripts
in order. SQLModel's metadata is SQLAlchemy metadata, so Alembic works with it directly. The general question of
choosing a migration tool across languages is on xref:database/schema-evolution/index.adoc[Schema Evolution].

[source,bash]
----
alembic init migrations                                   # creates alembic.ini and migrations/
# edit migrations/env.py and script.py.mako as below
export DATABASE_URL=sqlite:///migrated.db                 # or the PostgreSQL URL
alembic revision --autogenerate -m "create bookshelf tables"
alembic upgrade head
----

Notes on the edits:

* `compare_type=True` makes autogenerate notice changed column types, not just added and removed columns and tables.
* `render_as_batch` is turned on for SQLite only: SQLite cannot alter most column properties in place, and Alembic's
  batch mode recreates the table. PostgreSQL does not need it.
* `url.replace("%", "%%")` is required because Alembic stores the URL in a `ConfigParser`, where `%` introduces an

  (reproduced).

  runtime, as long as a synchronous driver (`psycopg`) is installed for the migration URL. Alembic also ships an `async`

[#postgresql-compose]
== PostgreSQL in Docker Compose

SQLite is for tests and prototypes; production is a server database. Compose runs PostgreSQL next to the API for local
development. The credential rule is the same as everywhere: the password lives in a file that is not committed and
that Compose mounts as a secret, never in the YAML. Create it with a generated value, for example
`mkdir -p secrets && openssl rand -hex 24 > secrets/bookshelf_db_password.txt`, and git-ignore `secrets/`.

the URL with `URL.create`, which percent-escapes special characters in the password for you, and the password type is
`SecretStr`, so it never appears in a log or a `repr`.

[source,python]
----
from functools import lru_cache

from pydantic_settings import BaseSettings, SettingsConfigDict
from sqlalchemy import URL

    port: int = 5432
    user: str = "bookshelf"
    name: str = "bookshelf"

            "postgresql+psycopg",
            username=self.user,
            password=self.password.get_secret_value(),
            host=self.host,
            port=self.port,
            database=self.name,
        )


@lru_cache
def get_db_settings() -> DatabaseSettings:
    return DatabaseSettings()

[#plain-sqlalchemy]
== Plain SQLAlchemy or Raw DB-API Instead

SQLModel is optional. Everything above (session per request through a `yield` dependency, explicit commit, Pydantic
schemas at the edge) works with the libraries underneath.

*SQLAlchemy 2.0 ORM with separate Pydantic schemas.* The table is a typed `Mapped` class; the API models are ordinary Pydantic models.
`ConfigDict(from_attributes=True)` lets a response model read attributes from an ORM object, replacing Pydantic v1's
`orm_mode`:

[source,python]
----
import os
from collections.abc import AsyncIterator, Iterator
from contextlib import asynccontextmanager
from typing import Annotated

from fastapi import Depends, FastAPI, HTTPException
from pydantic import BaseModel, ConfigDict, Field
from sqlalchemy import String, create_engine, select
from sqlalchemy.exc import IntegrityError
from sqlalchemy.orm import DeclarativeBase, Mapped, Session, mapped_column, sessionmaker


class Base(DeclarativeBase):
    pass


class BookRow(Base):
    __tablename__ = "book"

    id: Mapped[int] = mapped_column(primary_key=True)
    title: Mapped[str] = mapped_column(String(200), index=True)
    isbn: Mapped[str] = mapped_column(String(17), unique=True)
    year: Mapped[int | None]


class BookIn(BaseModel):
    title: str = Field(min_length=1, max_length=200)
    isbn: str = Field(min_length=10, max_length=17)
    year: int | None = None


class BookOut(BookIn):
    model_config = ConfigDict(from_attributes=True)  # read attributes from ORM objects
    id: int


engine = create_engine(os.environ.get("DATABASE_URL", "sqlite:///plain.db"))
SessionLocal = sessionmaker(engine, expire_on_commit=False)


def get_session() -> Iterator[Session]:
    with SessionLocal() as session:
        yield session


SessionDep = Annotated[Session, Depends(get_session)]


@asynccontextmanager
async def lifespan(app: FastAPI) -> AsyncIterator[None]:
    Base.metadata.create_all(engine)
    yield
    engine.dispose()


app = FastAPI(lifespan=lifespan)


@app.post("/books", response_model=BookOut, status_code=201)
def create_book(book: BookIn, session: SessionDep) -> BookRow:
    row = BookRow(**book.model_dump())
    session.add(row)
    try:
        session.commit()
    except IntegrityError:
        session.rollback()
        raise HTTPException(status_code=409, detail="ISBN already exists")
    return row


@app.get("/books", response_model=list[BookOut])
def list_books(session: SessionDep, offset: int = 0, limit: int = 20):
    return session.scalars(select(BookRow).order_by(BookRow.id).offset(offset).limit(limit)).all()
----

Source: https://docs.sqlalchemy.org/en/20/orm/quickstart.html[SQLAlchemy: ORM Quick Start]

The routes are the same as in the SQLModel version, except `session.scalars(select(...))` replaces `session.exec`. A
run returned `201` for the first book, `409 {"detail":"ISBN already exists"}` for the duplicate, and the list with the
one book. `sessionmaker(engine, expire_on_commit=False)` is a factory that keeps committed objects readable, so the
POST route needs no refresh.

*SQLAlchemy Core.* No ORM and no mapped classes: tables, SQL expressions and result rows. Useful for bulk and reporting
queries:

[source,python]
----
from sqlalchemy import Column, Integer, MetaData, String, Table, create_engine, insert, select

metadata = MetaData()  # note the capital D: sqlalchemy.MetaData
books = Table(
    "book",
    metadata,
    Column("id", Integer, primary_key=True),
    Column("title", String(200), nullable=False),
    Column("isbn", String(17), nullable=False, unique=True),
)

engine = create_engine("sqlite://")
metadata.create_all(engine)

with engine.begin() as conn:  # begin() commits on success, rolls back on error
    conn.execute(insert(books), [{"title": "Dune", "isbn": "978-0441172719"},
                                 {"title": "Neuromancer", "isbn": "978-0441569595"}])
    rows = conn.execute(select(books.c.id, books.c.title).order_by(books.c.id)).mappings().all()

print([dict(r) for r in rows])
----

Source: https://docs.sqlalchemy.org/en/20/tutorial/index.html[SQLAlchemy: Unified Tutorial]

The output was `[{'id': 1, 'title': 'Dune'}, {'id': 2, 'title': 'Neuromancer'}]`. `engine.begin()` opens a transaction and
commits on success or rolls back on error. The class is `MetaData` with a capital D: a widely copied older example
imports a non-existent `Metadata` from SQLAlchemy and fails with `ImportError` (reproduced; the error message even
suggests `MetaData`).

*Raw DB-API (`sqlite3`, `psycopg`).* You write the SQL yourself (the statements are covered on
xref:database/sql/dml-queries.adoc[DML: Queries] and xref:database/sql/dml-modifications.adoc[DML: Modifications], the
schema on xref:database/sql/ddl.adoc[DDL]). The standard is PEP 249: connections, cursors, `execute`, `commit`, parameter
placeholders. In FastAPI the same rules apply: a connection per request from a `yield` dependency, parameters passed
separately, no global connection. Older guides commonly open one module-level `sqlite3` connection and share it
across all requests; a shared connection serializes (or breaks) concurrent requests and cannot be used from the
threadpool without disabling SQLite's thread check. The corrected version:

[source,python]
----
import os
import sqlite3
from collections.abc import Iterator
from typing import Annotated

from fastapi import Depends, FastAPI, HTTPException
from pydantic import BaseModel, Field

DB_PATH = os.environ.get("BOOKSHELF_DB", "raw.db")

SCHEMA = """
CREATE TABLE IF NOT EXISTS book (
    id INTEGER PRIMARY KEY,
    title TEXT NOT NULL,
    isbn TEXT NOT NULL UNIQUE
)
"""


def get_connection() -> Iterator[sqlite3.Connection]:
    # One connection per request, never a module-level global.
    # check_same_thread=False: a def dependency and a def path operation can run in different worker threads.
    conn = sqlite3.connect(DB_PATH, check_same_thread=False)
    conn.row_factory = sqlite3.Row
    try:
        yield conn  # path operations commit explicitly, before the response is sent
    finally:
        conn.close()


ConnDep = Annotated[sqlite3.Connection, Depends(get_connection)]
app = FastAPI()

with sqlite3.connect(DB_PATH) as _setup:  # simple bootstrap; use migrations in real projects
    _setup.execute(SCHEMA)


class BookIn(BaseModel):
    title: str = Field(min_length=1, max_length=200)
    isbn: str = Field(min_length=10, max_length=17)


class BookOut(BookIn):
    id: int


@app.post("/books", status_code=201)
def create_book(book: BookIn, conn: ConnDep) -> BookOut:
    try:
        cur = conn.execute("INSERT INTO book (title, isbn) VALUES (?, ?)", (book.title, book.isbn))
    except sqlite3.IntegrityError:
        raise HTTPException(status_code=409, detail="ISBN already exists")
    conn.commit()
    return BookOut(id=cur.lastrowid, **book.model_dump())


@app.get("/books/search")
def search_books(title: str, conn: ConnDep) -> list[BookOut]:
    # Parameters travel separately from the SQL text: never build SQL with f-strings.
    rows = conn.execute("SELECT id, title, isbn FROM book WHERE title LIKE ?", (f"%{title}%",)).fetchall()
    return [BookOut(**dict(row)) for row in rows]
----

Source: https://docs.python.org/3/library/sqlite3.html[Python: sqlite3]

* *Parameters, never string building.* `WHERE title LIKE ?` with a separate tuple lets the driver escape values.
  The verified request `title=' OR 1=1 --` returned an empty list, not the table. `f"... \{title}"` is SQL injection.
* *`check_same_thread=False` is deliberate here* (next section): a `def` dependency and a `def` path operation can run in
  different worker threads, and `sqlite3` refuses to use a connection in a thread other than the one that created it.
  Because each request owns its own connection, nothing is shared concurrently, so turning the check off is safe.
* *Commit in the route,* for the same teardown-timing reason as with sessions.
* *PostgreSQL's DB-API drivers* use `%s` placeholders (`psycopg`) instead of `?` and offer their own pools; the shape of the
  dependency is identical.

[#pooling]
== Connection Pooling and check_same_thread

Opening a database connection is slow (a network round trip, authentication, TLS). SQLAlchemy's engine keeps connections in
a pool and lends one to each session until it closes. The pool class depends on the database, as observed:

[cols="2,2,3",options="header"]
|===
| URL | Pool class | Notes
| `postgresql+psycopg://...` | `QueuePool` | Defaults: `pool_size=5`, `max_overflow=10`, `pool_timeout=30`, `pool_recycle=-1` (never), `pool_pre_ping=False`
| `postgresql+asyncpg://...` | `AsyncAdaptedQueuePool` | The same options, used with `create_async_engine`
| `sqlite:///file.db` | `QueuePool` | A file database pools like any other (SQLAlchemy 2.0)
| `sqlite://` (in memory) | `SingletonThreadPool` | One connection per thread, so each thread sees a different empty database
|===

Tune with `create_engine` arguments: `pool_size` (connections kept), `max_overflow` (temporary extra connections),
`pool_timeout` (seconds a request waits), `pool_recycle` (retire old connections, useful behind firewalls or proxies
that drop idle ones), `pool_pre_ping` (detect dead connections at checkout). The total across all processes must stay below
the server's `max_connections`: with 4 worker processes and `pool_size=10, max_overflow=5` the API can open up to 60
connections. When the pool is exhausted, new requests wait `pool_timeout` seconds and then fail:

[source,python]
----
from sqlalchemy import create_engine
from sqlalchemy.exc import TimeoutError as PoolTimeout

# Rarely what you want in production; tiny numbers make the limit visible.
engine = create_engine("sqlite:///pool_demo.db", pool_size=1, max_overflow=0, pool_timeout=1)

first = engine.connect()  # takes the only pooled connection
try:
    engine.connect()  # a second request waits pool_timeout seconds, then gives up
except PoolTimeout as exc:
    print(str(exc).split(" (Background")[0])
finally:
    first.close()

# Defaults for QueuePool: pool_size=5, max_overflow=10, pool_timeout=30, pool_recycle=-1, pool_pre_ping=False
default = create_engine("sqlite:///pool_demo.db")
print(type(default.pool).__name__, default.pool.size())
print(type(create_engine("sqlite://").pool).__name__)  # in-memory SQLite
----

Source: https://docs.sqlalchemy.org/en/20/core/pooling.html[SQLAlchemy: Connection Pooling]

The output was `QueuePool limit of size 1 overflow 0 reached, connection timed out, timeout 1.00`, then `QueuePool 5` and
`SingletonThreadPool`. In FastAPI this appears as `500` errors under load when sessions are held too long (a slow
call inside the session, a streaming response, or a leaked session). Close sessions promptly, keep the pool at least
as large as the number of concurrent requests that need the database, and size it against the server limit. Use `NullPool` (no pooling)
for migration commands and short-lived scripts.

*`check_same_thread` explained.* The `sqlite3` module raises `ProgrammingError: SQLite objects created in a thread can only be
used in that same thread` when a connection crosses threads. FastAPI crosses threads routinely: it runs `def` dependencies and
`def` routes in a worker threadpool, so the thread that opened the connection may not be the one that uses it. A verified
reproduction: an `async def` dependency (event-loop thread) opens a raw connection and a `def` route (worker thread) uses it,
which returned `500` with exactly that error. The official tutorial passes `connect_args={"check_same_thread": False}`
for this reason.

Two facts refine that advice, both observed with SQLAlchemy 2.0.54:

* For a SQLite _file_ database, SQLAlchemy 2.0's `QueuePool` already hands connections across threads without the
  argument (the cross-thread query in a test returned a normal result). The tutorial's argument is harmless and
  keeps older versions and in-memory setups working.
* For the in-memory test database (`StaticPool`), the argument is required: without it, a second thread failed with
  `ProgrammingError`; with it, the query returned `1`. That is why the test fixture above sets it.

Only SQLite takes this argument; it is passed conditionally in the examples so that the same code works against PostgreSQL.
Disabling the check is safe when no two threads use the same connection at the same time, which the pool and the
per-request session guarantee.

[#changes]
== Where Older Guides Are Outdated, and What Changed Recently

* *The official SQL tutorial now uses SQLModel (0.115.1, 2024-10-12).* Older tutorials and books show SQLAlchemy models,
  Pydantic schemas and a global connection or `scoped_session`. They still work, but the documented approach is a
  session dependency with `yield` and SQLModel with SQLAlchemy 2.0 underneath.
* *SQLAlchemy 1.x idioms.* `declarative_base()`, `Column(...)` annotations, `session.query(...)` and `engine.execute(...)`
  are the 1.x style. The 2.0 style uses `DeclarativeBase`, `Mapped`/`mapped_column`, `select()` with
  `session.scalars()` or `session.exec()`, and `Connection.execute()` inside `engine.begin()`.
* *Pydantic v1 names.* `orm_mode` is `from_attributes`, `.dict()` is `model_dump()`, `parse_obj` is `model_validate`.
  FastAPI dropped Pydantic v1 in 0.126.0 (2025-12-20) and `pydantic.v1` in 0.128.0 (2025-12-27).
* *Startup and shutdown events.* Table creation in `@app.on_event("startup")` is the older form (even the official tutorial page
  still shows it). Lifespan context managers have been the supported way since 0.93.0 (2023-03-07).
* *Yield dependency timing.* Guides that commit in the teardown, or assume the session stays open for background tasks,
  predate 0.106.0 (2023-12-25) and 0.118.0 (2025-09-29), which changed when the teardown runs; 0.121.0 (2025-11-03) added
  `Depends(scope="function")`. Commit in the route.
* *A global `sqlite3` connection and environment-variable switching of storage modules.* Replaced by a per-request
  connection or session from a dependency, with `dependency_overrides` for tests.
* *Incorrect imports.* `sqlalchemy.Metadata` does not exist (it is `MetaData`); copy-paste from sources that were not
  executed is where such errors come from.
* *Python 3.14 and SQLModel.* SQLModel 0.0.47 declares Python 3.10 and later; the examples here ran on 3.13 only.
* *SQLAlchemy 2.1.* It is released, but SQLModel 0.0.47 pins `<2.1`; stay on 2.0 until SQLModel lifts the pin. The
  release history of FastAPI itself is collected on
  xref:backend/fastapi/whats-changed-and-migration.adoc[What's Changed & Migration].

[#pitfalls]
== Pitfalls

* *Returning the table model.* It exposes every column and publishes a `Book` schema. Always use a data model as the
  `response_model`.
* *Trusting validation on a table model.* `Book(...)` does not validate. Validate a data model, then convert with
  `model_validate`.
* *`exclude_unset` forgotten in PATCH.* Every omitted field becomes `None` and wipes data. Also reject explicit `null` for
  NOT NULL columns.
* *Catching every `IntegrityError` as "ISBN exists".* NOT NULL and foreign-key violations raise the same exception.
  Inspect the constraint name, or check the condition explicitly (the author lookup above returns `404` before the
  commit for that reason).
* *Forgetting `rollback()`.* After a failed flush the session is in a failed state and the next use raises
  `PendingRollbackError`.
* *Committing in the dependency teardown.* After 0.118.0 it runs after the response is sent.
* *Accessing a lazy relationship or an expired attribute after the session closes.* `DetachedInstanceError`: eager-load what you
  serialize, and serialize inside the route.
* *Lazy loading in a loop (N+1).* Three statements became seven for five books. `selectinload` for collections, `joinedload`
  for single-valued relationships.
* *Lazy loading in async code.* `MissingGreenlet`; eager-load.
* *A blocking driver inside `async def`.* It freezes the event loop; use `def` routes or an async driver.
* *An unbounded list endpoint, or `OFFSET` on huge tables.* Bound `limit`, order by a unique column, consider keyset.
* *SQLite foreign keys are off by default.* Add the `PRAGMA foreign_keys=ON` listener, or tests will accept data PostgreSQL
  rejects.
* *`create_all` as a migration tool.* It never alters tables; use Alembic and review autogenerated scripts.
* *`%` in the Alembic URL.* Double it before `set_main_option`.
* *Passwords in code, YAML or the image.* Use secret files or the platform's secret store, and `SecretStr` in settings.
* *Exhausting the pool or the server's `max_connections`.* Size `pool_size`, `max_overflow` and worker count together.
* *Mixing SQLModel with an unpinned SQLAlchemy.* Let SQLModel's requirement choose the SQLAlchemy version.
