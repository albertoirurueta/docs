== What Apache POI is

Apache POI is a pure Java library, published by the Apache Software Foundation under the Apache License 2.0, that reads
and writes the file formats of Microsoft Office. It needs no Office installation, no native code and no COM bridge, so it
runs on any server, in a container and in a unit test. It works on the files themselves: it parses the binary or XML
structures, gives you an object model over them, and serialises the model back. It is not a rendering engine: it never
lays out pages, never calculates what a Word document looks like on paper and never opens a user interface.

The project started in the early 2000s as a Jakarta subproject and later became a top-level Apache project. Its history
explains the odd class names:

* The name POI is a joke on _Poor Obfuscation Implementation_, a nod to the deliberately obscure Microsoft file formats
  that the first contributors had to reverse engineer.
* The first two components were named with the same humour. *HSSF* is the _Horrible Spreadsheet Format_ (Excel
  `.xls`) and *HWPF* the _Horrible Word Processor Format_ (Word `.doc`). The official documentation still uses the
  expansions.
* When OOXML support arrived (POI 3.5), the new components were named by analogy: *XSSF* is the _XML Spreadsheet Format_
  (`.xlsx`), *XWPF* the _XML Word Processor Format_ (`.docx`), *XSLF* the _XML Slide Layout Format_ (`.pptx`). The
  first letter tells the generation: *H* means a binary OLE2 format, *X* means an XML (OOXML) format.
* POI follows semantic versioning since 4.0.0: an API is deprecated in one major release and removed in the next, which
  is why 6.0 is announced as the release that removes the deprecated code of the 5.x line.

Do not confuse POI with the Java `org.apache.poi` packages of older tutorials. Code written for POI 3.x uses
integer cell types such as `HSSFCell.CELL_TYPE_STRING`, `Cell.getCellTypeEnum()` and `XSSFWorkbook(InputStream)`
everywhere. Those idioms were removed or discouraged by 4.0 and 5.x; every example in this section uses the current API.

The consequences for a server project are practical:

* Everything you need for `.xlsx` and `.docx` is in `poi-ooxml`, which depends on `poi`. Add `poi-scratchpad` only if you
  must read `.doc`, `.ppt`, `.msg`, `.vsd` or `.pub`.
* OOXML parts are mapped to Java objects by Apache XMLBeans, generated from the ECMA-376 schemas. Those generated classes
  are large, so the schemas are shipped in two jars: `poi-ooxml-lite` (about 6 MB, the commonly used schemas) and
  `poi-ooxml-full` (about 16 MB, all of them). Code that reaches into the raw `CT*` beans, or that signs documents, may
  need the full jar. The choice is explained in the setup page.
* POI 5.0 renamed and re-split the jars (the former `ooxml-schemas` jars became lite and full), so a 4.x build file does
  not carry over unchanged. See the xref:backend/office-files/whats-changed-and-migration.adoc[migration page] of this section for the history.

== OLE2 versus OOXML

Every format in the table is one of two physical containers, and most POI behaviour follows from that.

[cols="1,2,2",options="header"]
|===
|Aspect |OLE2 (binary, "H" components) |OOXML (XML in a ZIP, "X" components)

|Typical extensions |`.xls`, `.doc`, `.ppt`, `.msg`, `.vsd`, `.pub` |`.xlsx`, `.xlsm`, `.docx`, `.pptx`, `.vsdx`
|Container |A compound file: sectors, a FAT and a directory of streams (POIFS) |A ZIP archive of XML parts and relationship files (OpenXML4J)
|Specification |Microsoft binary format documents (MS-XLS, MS-DOC) |ECMA-376 and ISO/IEC 29500
|Limits |Excel: 65,536 rows by 256 columns, 4,000 cell styles |Excel: 1,048,576 rows by 16,384 columns, 64,000 cell styles
|Read model |Whole file loaded in memory (or record events for HSSF) |Parts parsed on demand to XMLBeans; XSSF keeps the model in memory; SAX is available for sheets
|Typical risks |Malformed records, oversized streams |Zip bombs, XML external entities, oversized parts
|Status |Legacy, kept for compatibility |The default for new files
|===

The practical rule: produce `.xlsx` and `.docx`, and accept `.xls` and `.doc` only when users still send them. An
encrypted OOXML file is, surprisingly, an OLE2 file: the encrypted package is stored as a stream inside a compound
file, which is why detection by file extension or by the ZIP signature alone is not enough. The two formats are
described in depth in xref:backend/office-files/file-formats-ooxml-and-ole2.adoc[File Formats: OOXML & OLE2].

== Three API levels

For spreadsheets, POI exposes the same data through three kinds of API. Choosing among them is the most important design
decision of a report or import feature; the xref:backend/office-files/performance-memory-and-threading.adoc[performance page] of this section revisits it with measurements.

[mermaid]
....
flowchart TD
    A["Need to work with a spreadsheet"] --> B{"Read or write?"}
    B -->|"Write"| C{"More than about 100k rows?"}
    B -->|"Read"| D{"Whole file needed at once?"}
    C -->|"No"| E["Usermodel: XSSFWorkbook"]
    C -->|"Yes"| F["Streaming write: SXSSFWorkbook"]
    D -->|"Yes, small file"| G["Usermodel: WorkbookFactory"]
    D -->|"No, large file"| H["Event API: XSSFReader and SAX"]
    E --> I["Common ss.usermodel interfaces"]
    F --> I
    G --> I
    H --> J["Raw cell events, no object model"]
....

[cols="2,3,3,3",options="header"]
|===
|API level |Packages and classes |Memory |Use it for

|Usermodel (read and write)
|`org.apache.poi.ss.usermodel` interfaces; `HSSFWorkbook`, `XSSFWorkbook`, `XWPFDocument`
|The whole workbook or document is a tree of objects in memory, typically many times the file size
|Reports up to some tens of thousands of rows, files you edit in place, anything needing styles, formulas and random access

|Event model (read only)
|`XSSFReader`, `XSSFSheetXMLHandler` and a SAX parser for `.xlsx`; `org.apache.poi.hssf.eventusermodel` for `.xls`
|Constant, a few megabytes regardless of the file size
|Importing very large sheets row by row, extracting text, validation passes that do not need the object model

|Streaming write (write only)
|`org.apache.poi.xssf.streaming.SXSSFWorkbook`, `SXSSFSheet`, `SXSSFRow`
|Only a window of rows (100 by default) is kept; older rows are flushed to a temporary file
|Exporting hundreds of thousands of rows, such as the `loans-report.xlsx` of the scenario
|===

Word has only the usermodel level: `XWPFDocument` loads the whole document. There is no streaming writer and no SAX
reader for `.docx` in POI itself, which is one more reason to keep generated documents small and to cap upload sizes.

=== Usermodel in practice

The first example creates the catalogue workbook of the scenario through the usermodel API. The variable type is the
interface `Workbook`; only the constructor names the format.

[source,java]
----
import java.io.IOException;
import java.io.OutputStream;
import java.nio.file.Files;
import java.nio.file.Path;
import org.apache.poi.ss.usermodel.Row;
import org.apache.poi.ss.usermodel.Sheet;
import org.apache.poi.ss.usermodel.Workbook;
import org.apache.poi.xssf.usermodel.XSSFWorkbook;

public class CreateInventory {

    public static void main(String[] args) throws IOException {
        try (Workbook workbook = new XSSFWorkbook()) {
            Sheet sheet = workbook.createSheet("Books");

            Row header = sheet.createRow(0);
            header.createCell(0).setCellValue("ISBN");
            header.createCell(1).setCellValue("Title");
            header.createCell(2).setCellValue("Price");

            Row row = sheet.createRow(1);
            row.createCell(0).setCellValue("9780140449136");
            row.createCell(1).setCellValue("The Odyssey");
            row.createCell(2).setCellValue(12.5);

            try (OutputStream out = Files.newOutputStream(Path.of("books-inventory.xlsx"))) {
                workbook.write(out);
            }
        }
    }
}
----

Source: https://poi.apache.org/components/spreadsheet/quick-guide.html#NewWorkbook[POI Quick Guide, New Workbook]

The try-with-resources block matters: since POI 3.x `Workbook` is `Closeable`, and closing releases the underlying
package (and, for SXSSF, deletes temporary files). Writing the file never closes the workbook.

=== Reading with the common interfaces

Because `Workbook`, `Sheet`, `Row` and `Cell` are interfaces, the same code reads `.xls` and `.xlsx`.
`WorkbookFactory` inspects the file header and returns the matching implementation. Pass a `File` rather than an
`InputStream` whenever you have one: POI can then open the file lazily and avoids copying the whole stream into memory.

[source,java]
----
import java.io.File;
import java.io.IOException;
import org.apache.poi.ss.usermodel.Cell;
import org.apache.poi.ss.usermodel.DataFormatter;
import org.apache.poi.ss.usermodel.Row;
import org.apache.poi.ss.usermodel.Sheet;
import org.apache.poi.ss.usermodel.Workbook;
import org.apache.poi.ss.usermodel.WorkbookFactory;

public class ReadInventory {

    public static void main(String[] args) throws IOException {
        DataFormatter formatter = new DataFormatter();
        try (Workbook workbook = WorkbookFactory.create(new File("books-inventory.xlsx"))) {
            Sheet sheet = workbook.getSheetAt(0);
            for (Row row : sheet) {
                StringBuilder line = new StringBuilder();
                for (Cell cell : row) {
                    line.append(formatter.formatCellValue(cell)).append(" | ");
                }
                System.out.println(line);
            }
        }
    }
}
----

Source: https://poi.apache.org/components/spreadsheet/quick-guide.html#Iterator[POI Quick Guide, Iterate over rows and cells]
and https://poi.apache.org/apidocs/dev/org/apache/poi/ss/usermodel/WorkbookFactory.html[WorkbookFactory Javadoc]

=== The event model in practice

The event API gives up the object model: you receive callbacks as the XML is parsed, so memory stays flat. The skeleton
below only opens the package and lists the sheets. Reading cell contents with `XSSFSheetXMLHandler` is the subject of the
large-file import page.

[source,java]
----
import java.io.File;
import java.io.InputStream;
import org.apache.poi.openxml4j.opc.OPCPackage;
import org.apache.poi.openxml4j.opc.PackageAccess;
import org.apache.poi.xssf.eventusermodel.XSSFReader;

public class ListSheets {

    public static void main(String[] args) throws Exception {
        try (OPCPackage pkg = OPCPackage.open(new File("loans-report.xlsx"), PackageAccess.READ)) {
            XSSFReader reader = new XSSFReader(pkg);
            XSSFReader.SheetIterator sheets = (XSSFReader.SheetIterator) reader.getSheetsData();
            while (sheets.hasNext()) {
                try (InputStream sheetXml = sheets.next()) {
                    // sheetXml is the raw SpreadsheetML of one sheet, ready for a SAX parser
                    System.out.println(sheets.getSheetName());
                }
            }
        }
    }
}
----

Source: https://poi.apache.org/components/spreadsheet/how-to.html#xssf_sax_api[POI How-To, XSSF and SAX (Event API)]
and the official example
https://github.com/apache/poi/blob/trunk/poi-examples/src/main/java/org/apache/poi/examples/xssf/eventusermodel/XLSX2CSV.java[XLSX2CSV]

== The common ss.usermodel interfaces

The package `org.apache.poi.ss.usermodel` (jar `poi`) defines the interfaces that both Excel implementations share. They
are what your service code should depend on, so that the choice between `.xls`, `.xlsx` and the streaming writer is made
in one place.

[cols="2,3,3",options="header"]
|===
|Interface |Role |Implementations

|`Workbook`
|The document: sheets, styles, fonts, named ranges, properties, `write`
|`HSSFWorkbook`, `XSSFWorkbook`, `SXSSFWorkbook`

|`Sheet`
|A sheet: rows, merged regions, column widths, freeze panes, print setup, drawing
|`HSSFSheet`, `XSSFSheet`, `SXSSFSheet`

|`Row`
|A row of cells, row height, hidden state
|`HSSFRow`, `XSSFRow`, `SXSSFRow`

|`Cell`
|A value, a `CellType` (`NUMERIC`, `STRING`, `BOOLEAN`, `FORMULA`, `BLANK`, `ERROR`), a style, a comment, a hyperlink
|`HSSFCell`, `XSSFCell`, `SXSSFCell`

|`CellStyle`, `Font`, `DataFormat`
|Formatting objects, owned by the workbook and shared by cells
|`HSSFCellStyle`, `XSSFCellStyle` and so on

|`CreationHelper`
|Factory for hyperlinks, rich text, date and formula evaluator objects without naming the implementation
|`HSSFCreationHelper`, `XSSFCreationHelper`, `SXSSFCreationHelper`

|`FormulaEvaluator`
|Computes formulas on demand and can cache results
|`HSSFFormulaEvaluator`, `XSSFFormulaEvaluator`, `SXSSFFormulaEvaluator`
|===

A hierarchy sketch, as a Mermaid class diagram:

[mermaid]
....

Two cautions apply to this abstraction:

* The interface does not make the formats equivalent. A style count, a row limit or a feature (tables, pivot tables,
  some conditional-format options) exists only in XSSF, and the limits of `.xls` apply when you pick HSSF. Code that
  casts to `XSSFSheet` for those features is normal and fine; keep the cast in one helper.
* `SXSSFWorkbook` implements the interfaces but with write-only semantics: once a row leaves the window you cannot read
  or change it, and `getRow` returns `null` for it.

`HSSFWorkbook`, `XSSFWorkbook` and `SXSSFWorkbook` are not thread safe. Use one workbook per request or per job, never a
shared static instance.

== There is no common Word interface

The spreadsheet world has `ss.usermodel`; the Word world has nothing comparable. `XWPFDocument` (for `.docx`) and
`HWPFDocument` (for `.doc`) are unrelated classes with different object models: XWPF exposes `XWPFParagraph`, `XWPFRun`,
`XWPFTable`, `XWPFPicture` and `XWPFHeader`; HWPF exposes `Range`, `Paragraph` and `CharacterRun`. The official overview
page says so explicitly, and it adds that HWPF is orphaned and in early development, with only partial write support and
no thread safety.

The practical advice for a server:

* Generate and edit only `.docx`, through XWPF.
* Read `.doc` only to extract text or simple tables, through `WordExtractor` or the HWPF `Range`, and convert it to your
  internal model immediately.
* Where you only need the text of either format, use the text-extraction classes (or Apache Tika), which hide the
  difference. This is covered in the xref:backend/office-files/text-extraction-and-apache-tika.adoc[text extraction page] of the section.
* XWPF is described as fairly stable but incomplete: some tasks (a table of contents, custom styles, content controls)
  need the low-level `CT*` XMLBeans objects behind the high-level classes. Those beans need the schema jar named in the
  setup page.

The next example creates the first paragraph of `loan-letter.docx`.

[source,java]
----
import java.io.IOException;
import java.io.OutputStream;
import java.nio.file.Files;
import java.nio.file.Path;
import org.apache.poi.xwpf.usermodel.XWPFDocument;
import org.apache.poi.xwpf.usermodel.XWPFParagraph;
import org.apache.poi.xwpf.usermodel.XWPFRun;

public class CreateLoanLetter {

    public static void main(String[] args) throws IOException {
        try (XWPFDocument document = new XWPFDocument()) {
            XWPFParagraph paragraph = document.createParagraph();

            XWPFRun title = paragraph.createRun();
            title.setBold(true);
            title.setFontSize(16);
            title.setText("Loan confirmation");

            XWPFParagraph body = document.createParagraph();
            XWPFRun text = body.createRun();
            text.setText("You have borrowed \"The Odyssey\" until 30 October 2026.");

            try (OutputStream out = Files.newOutputStream(Path.of("loan-letter.docx"))) {
                document.write(out);
            }
        }
    }
}
----

Source: https://poi.apache.org/components/document/quick-guide-xwpf.html[POI XWPF Quick Guide]
and https://github.com/apache/poi/blob/trunk/poi-examples/src/main/java/org/apache/poi/examples/xwpf/usermodel/SimpleDocument.java[SimpleDocument example]

== Other components and related projects

The official component overview lists more formats than this section uses. They share the OLE2 and OPC infrastructure
described above, and a server that accepts arbitrary uploads may meet any of them, so it is useful to know the names.

[cols="2,2,3",options="header"]
|===
|Component |File type |Notes

|HSLF
|PowerPoint `.ppt`
|Binary slides; reading text and shapes, limited writing. Jar `poi-scratchpad`.

|XSLF
|PowerPoint `.pptx`
|Slides, shapes, text, pictures; can render a slide to an image with Java 2D. Jar `poi-ooxml`.

|HSMF
|Outlook `.msg`
|Read messages, recipients and attachments. Jar `poi-scratchpad`.

|HMEF
|TNEF `winmail.dat`
|Extract the attachments that some mail clients wrap in this format. Jar `poi-scratchpad`.

|HDGF and XDGF
|Visio `.vsd` and `.vsdx`
|Read diagram shapes and text. Jars `poi-scratchpad` and `poi-ooxml`.

|HPBF
|Publisher `.pub`
|Read text. Jar `poi-scratchpad`.
|===

POI also has a few neighbours that are often confused with it:

[cols="2,4",options="header"]
|===
|Project |Relationship to POI

|Apache Tika
|Content detection and text extraction for many formats, using POI underneath for Office files. The POI documentation
"strongly advises" Tika for extraction when you do not need Office-specific details.

|poi-tl and XDocReport
|Template engines built on POI (listed on the official related-projects page) that fill a `.docx` template. POI itself
has no template API, as explained below.

|NPOI
|A .NET port of POI. It is a separate project with its own release cycle; it is mentioned here because teams that work in
both Java and .NET often compare the two.

|Apache FOP
|A formatting-objects processor that renders XSL-FO to PDF. The HWPF `converter` package can produce XSL-FO from a `.doc`,
which FOP can then render. It is the only official route from POI to PDF.
|===

== What POI does not do

A frequent source of disappointment is looking in POI for features that it deliberately or practically does not provide.
Stating them up front saves a week of searching.

* *No PDF output.* POI cannot convert `.docx` or `.xlsx` to PDF. The only official path is HWPF to XSL-FO to Apache FOP,
  which is limited to `.doc`. For PDF generation see the xref:backend/pdf-generation/index.adoc[PDF Generation] section,
  or run a converter such as LibreOffice in headless mode as a separate service.
* *No Word template or mail-merge API.* XWPF has no `replace placeholder` function. Placeholders can be split across
  several `XWPFRun` objects, so a correct replacement must handle that. Template engines (poi-tl, XDocReport) exist on top
  of POI, and the Word pages of this section show a hand-written approach.
* *No rendering.* POI does not calculate page breaks, page counts, table of contents entries or the visual result of a
  formula's number format. A table of contents field is inserted as a field and filled in by Word when the user opens the
  file.
* *No complete chart guide.* Charts are created through the XDDF classes in `poi-ooxml`; the website has no narrative guide
  for them, so chart code in this section derives from the official examples and the Javadoc.
* *Not every Excel function.* The formula evaluator implements most, but not all, built-in functions, and macros (VBA)
  are neither executed nor created. User-defined functions can be added.
* *Not a database.* The usermodel API is an in-memory document model. For a million rows, use SXSSF to write and the SAX
  API to read.
