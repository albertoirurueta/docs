= Architectural Patterns
:description: Landing page for the Architectural Patterns reference -- domain-driven design patterns for structuring a microservice's code and, above all, why the data-consistency toolbox changes once every service owns its own database: strategic design, tactical building blocks, sagas, domain events, the transactional outbox, listen to yourself, CQRS, event sourcing, and a worked example that ties them all together, plus a downloadable cheat sheet.

Welcome to the Architectural Patterns reference. This section applies **domain-driven design** (DDD) to
microservice architectures: it shows how to structure a single service's code around its domain model, and,
above all, why the data-consistency toolbox a monolith takes for granted -- one ACID transaction spanning
everything it touches -- stops working the moment every service owns its own database. From there it builds up,
pattern by pattern, the toolbox that replaces it: **sagas** coordinating local transactions with compensations,
**domain events** as the currency those sagas exchange, the **transactional outbox** and **listen-to-yourself**
patterns for publishing those events reliably, **CQRS** for the queries a decomposed data model can no longer
answer directly, and **event sourcing** as an alternative persistence model built entirely out of events. The
tactical DDD building blocks -- **entities**, **value objects**, **aggregates**, repositories, factories and
domain services -- are what make "one transaction, one aggregate" possible in the first place, so this section
covers them in depth too. Deciding whether to split a system into services in the first place, and the
strangler-style migration that gets you there, was previously left out of scope here; that material now lives in
xref:backend/architecture/decisions-and-migrations/index.adoc[the Architecture Decisions and Migration Paths reference], the other half of the
xref:backend/architecture/index.adoc[Architecture] reference.

Every code example in this section shares one running domain -- an e-commerce *Order* / *Inventory* / *Payment*
/ *Shipping* set of bounded contexts -- and is written and verified against **Java 21**, **Spring Boot 4.1.x**
(Spring Framework 7.0.x), **Spring Data JPA**, **Spring Modulith 2.x** and **Spring for Apache Kafka 4.1.x**. The
domain model itself stays plain Java -- records, sealed interfaces, no framework -- and Spring only appears in
the application and infrastructure layers.

== What's covered

=== Foundations

* xref:backend/architecture/architectural-patterns/strategic-design.adoc[Strategic Design for Microservices] -- domains and
  subdomains, the ubiquitous language, the bounded context as the unit that owns both a model and a database, the
  context map's relationship patterns, and the three integration styles between contexts.
* xref:backend/architecture/architectural-patterns/structuring-the-code.adoc[Structuring a DDD Microservice's Code] -- transaction
  script vs. domain model, application services as the transaction boundary, inbound/outbound adapters, and the
  Maven module and Java package layout the running example follows throughout this section.

=== Tactical building blocks

* xref:backend/architecture/architectural-patterns/entities.adoc[Entities] -- identity over attributes, rich behavior instead of
  getters/setters, a state-machine view of `OrderStatus`, and JPA mapping of a typed identifier.
* xref:backend/architecture/architectural-patterns/value-objects.adoc[Value Objects] -- value objects defined by the absence of
  identity, equality by attributes, immutability, self-validation, when to promote a primitive to a value object,
  and their JPA persistence as `@Embeddable`, `@ElementCollection`, or JSON columns.
* xref:backend/architecture/architectural-patterns/aggregates.adoc[Aggregates] -- the tactical DDD building block that ties
  entities and value objects to a transactional consistency boundary -- fuzzy boundaries, Richardson's and
  Vernon's rules, granularity trade-offs, optimistic locking, and eventual consistency between aggregates.
* xref:backend/architecture/architectural-patterns/repositories-factories-and-domain-services.adoc[Repositories, Factories, and
  Domain Services] -- the collection-like Repository port and its Spring Data JPA adapter, static-factory vs.
  dedicated-factory construction, domain services vs. application-service orchestration, and modules as the
  coarsest-grained building block.

=== Consistency across services

* xref:backend/architecture/architectural-patterns/why-not-distributed-transactions.adoc[Why Distributed Transactions Don't Work
  Across Microservices] -- why the ACID transaction a monolith takes for granted stops at the service boundary --
  two-phase commit's mechanics and real failure modes, the availability-product and CAP-theorem arguments against
  it, and the three strategies that replace it in practice.
* xref:backend/architecture/architectural-patterns/sagas.adoc[Sagas] -- message-driven sequences of local transactions coordinating
  the Place Order Saga across bounded contexts -- compensating transactions, choreography vs. orchestration, the
  ACD lack of isolation and its countermeasures.
* xref:backend/architecture/architectural-patterns/domain-events.adoc[Domain Events] -- past-tense facts about an aggregate --
  naming, the envelope and its metadata, minimal vs. enriched payloads, how the aggregate hands events off,
  in-process and out-of-process consumption, and event versioning.
* xref:backend/architecture/architectural-patterns/event-storming.adoc[Event Storming] -- the collaborative workshop that
  discovers domain events, commands, and aggregates before any code is written, and how the running domain's own
  board maps onto the pages this section already covers.
* xref:backend/architecture/architectural-patterns/transactional-outbox.adoc[The Transactional Outbox Pattern] -- how a service
  publishes a domain event reliably in the same local transaction as the state change it describes -- the
  dual-write problem, the outbox table, polling publishers vs. transaction-log tailing, Spring Modulith's event
  publication registry, and idempotent consumers on the receiving end.
* xref:backend/architecture/architectural-patterns/listen-to-yourself.adoc[Listen to Yourself] -- publishing a domain event before
  applying it to the publisher's own database, and consuming that same event as the one code path that updates
  local state, contrasted with the transactional outbox and event sourcing.
* xref:backend/architecture/architectural-patterns/cqrs.adoc[CQRS] -- why cross-service queries need a different answer than the
  write model, the command side vs. query side split, designing a view module, idempotent projections,
  replication lag, and the canonical `OrderHistoryView` read model.
* xref:backend/architecture/architectural-patterns/event-sourcing.adoc[Event Sourcing] -- the trouble with state-based persistence,
  the append-only event store, reconstituting state by replay, snapshots and evolving events, and the canonical
  `EventSourcedOrder` decide/apply split.

=== Putting it all together

* xref:backend/architecture/architectural-patterns/worked-example.adoc[Putting It All Together: The Place Order Flow] -- assembles
  every pattern in this section into one worked example -- the happy path and the payment-failure path through
  the Place Order Saga, end to end from an HTTP request to the CQRS read model, plus a checklist of what to test
