Architecture is the set of decisions about how a backend system is divided and how its parts stay consistent. This subsection groups the two halves of that work, which read best in this order: first *whether and how to split* a system, then *how a split system stays consistent*. Both are written for backend developers and architects who have to choose between a monolith, a modular monolith and microservices, migrate a system one safe step at a time, and keep data consistent once every service owns its own database.

* xref:backend/architecture/decisions-and-migrations/index.adoc[Architecture Decisions and Migration Paths] covers what a monolith, a modular monolith and microservices are, the benefits and drawbacks of microservices, when a monolith is still the right call, how to isolate backend and frontend behind an API gateway or backends for frontends, the migration paths (legacy stack, monolith to modular monolith, monolith to microservices, single-tenant to multi-tenant SaaS) and how to start a new project.
* xref:backend/architecture/architectural-patterns/index.adoc[Architectural Patterns] covers domain-driven design applied to microservices: strategic design, the tactical building blocks (entities, value objects, aggregates, repositories), why distributed transactions do not work across services, sagas, domain events and event storming, the transactional outbox, CQRS and event sourcing, assembled into one worked example.

Both halves share one vocabulary (bounded contexts, business capabilities, database per service) and link into each other wherever a decision on one side has consequences on the other: every migration path that ends with "and now that transaction spans two services" hands over to the saga, outbox and CQRS pages, and every pattern page assumes the split it builds on was made for the reasons the decisions pages lay out.

== Version baseline

The code in the pattern pages is written and verified against *Java 21*, *Spring Boot 4.1.x* (Spring Framework 7.0.x), *Spring Data JPA*, *Spring Modulith 2.x* and *Spring for Apache Kafka 4.1.x*; the domain model itself stays plain Java (records and sealed interfaces) and Spring appears only in the application and infrastructure layers. The decision and migration pages are mostly technology-neutral, and name a technology only where they show a Spring Boot or Quarkus realisation of a step.

== Running example

The two halves use different running domains. The decision and migration pages follow *Bookshop*, a fictional online bookstore shown first as a legacy Java EE and Struts monolith, then as a healthy Spring Boot monolith with five business capabilities (catalogue, orders, payments, shipping, customer accounts), and finally strangled into a modular monolith, a set of microservices and a multi-tenant SaaS product. The pattern pages follow an e-commerce *Order*, *Inventory*, *Payment* and *Shipping* set of bounded contexts, which the worked example assembles into the place-order flow.

=== Books

* Chris Richardson, _Microservices Patterns: With Examples in Java_, Manning, 2019, ISBN 978-1-61729-454-9: https://www.manning.com/books/microservices-patterns[publisher page]. The main narrative source for the decomposition, migration, saga, domain-event, outbox, CQRS and event-sourcing pages.
