[#in-a-hurry]
== In a Hurry: The Short Version

.The container recipe in eight rules
[cols="2,5",options="header"]
|===
| Decision | Recommendation

| Server
| Gunicorn (or another production WSGI server), never `flask run` or `app.run()`. The development server and the debugger are
for your laptop; see <<dev-server>>.

| Base image
| The official `python` image, `-slim` variant, pinned to a minor version (`python:3.14-slim`). Pin a digest when builds must
be bit-for-bit repeatable.

| Build
| Multi-stage: install locked dependencies into a virtual environment in a builder stage, copy only that environment into the
runtime stage.

| User
| A non-root user with a numeric UID in the image (`USER 10001:10001`), so Kubernetes can verify `runAsNonRoot`.

| Start command
| Exec form, `CMD ["gunicorn", "bookshelf:create_app()"]`, with a `gunicorn.conf.py` next to it. Never the shell form.

| Processes
| A few Gunicorn workers per container (2 to 4), and scale with replicas. Do not derive the worker count from the machine's
CPU count inside a container.

| Configuration
| Environment variables read with `from_prefixed_env()`; secrets from a Secret or a secret manager, never from an `ENV`
line or an `ARG`. One `SECRET_KEY` shared by every replica.

| Platform contract
| `/healthz` (the process is alive) and `/readyz` (it can serve) endpoints, SIGTERM handled by Gunicorn, logs on
standard output and standard error, migrations as a separate step run once.
|===

[#project]
== The Project Inside the Container

The Bookshelf project is the installable package described in
xref:backend/flask/application-factory-and-project-layout.adoc[Application Factory & Project Layout]: a `pyproject.toml`,
a `src/bookshelf` package whose `create_app()` builds the application, and a lock file. The container needs three things
from the application that a laptop run does not: configuration that arrives through environment variables, endpoints the
platform can probe, and a trusted-proxy setting that matches the load balancer in front. The factory below has all three.
It reads every `+BOOKSHELF_*+` variable with `Config.from_prefixed_env()` (the mechanism of
xref:backend/flask/configuration.adoc[Configuration]), refuses to start without a `SECRET_KEY`, wraps the WSGI application in
`ProxyFix` only when told how many proxies exist, and exposes the two probe endpoints.

[source,python]
----
from flask import Flask, jsonify
from werkzeug.middleware.proxy_fix import ProxyFix


def create_app(test_config=None, readiness_checks=()):
    app = Flask(__name__)
    app.config.from_prefixed_env("BOOKSHELF")        # BOOKSHELF_SECRET_KEY -> SECRET_KEY, and so on
    if test_config:
        app.config.from_mapping(test_config)
    if not app.config.get("SECRET_KEY"):
        raise RuntimeError("set BOOKSHELF_SECRET_KEY")   # fail at start-up, not at the first login

    hops = app.config.get("PROXY_HOPS", 0)               # BOOKSHELF_PROXY_HOPS=1 behind one ingress
    if hops:
        app.wsgi_app = ProxyFix(app.wsgi_app, x_for=hops, x_proto=hops, x_host=hops)

    @app.get("/healthz")
    def healthz():
        """Liveness: the process answers. Never touch the database here."""
        return jsonify(status="ok"), 200, {"Cache-Control": "no-store"}

    @app.get("/readyz")
    def readyz():
        """Readiness: every dependency the application needs to serve is reachable."""
        failed = []
        for check in readiness_checks:
            try:
                check()
            except Exception as exc:
                failed.append(f"{check.__name__}: {type(exc).__name__}")
        if failed:
            return jsonify(status="unavailable", failed=failed), 503, {"Cache-Control": "no-store"}
        return jsonify(status="ready"), 200, {"Cache-Control": "no-store"}

    return app
----
Source: https://flask.palletsprojects.com/en/stable/config/#configuring-from-environment-variables[Flask: Configuration Handling, Configuring from Environment Variables]

The probe endpoints return the names of the failed checks, not their messages, so a probe cannot be used to read a
connection string out of an exception. `Cache-Control: no-store` stops a proxy from caching a readiness answer. The
readiness view runs inside a request, and therefore inside an application context, so a check can use
`db.session` directly, as shown next. Everything is exercised with the test client, with the environment patched the way a
container's environment would be:

[source,python]
----
import os
import secrets
from unittest import mock

from flask import request
from flask_sqlalchemy import SQLAlchemy
from sqlalchemy import text

db = SQLAlchemy()


def database():
    db.session.execute(text("SELECT 1"))     # a real check: one round trip to the database


# 1. Configuration arrives as environment variables, exactly as in a container
env = {"BOOKSHELF_SECRET_KEY": secrets.token_hex(32), "BOOKSHELF_PROXY_HOPS": "1"}
with mock.patch.dict(os.environ, env):
    app = create_app({"SQLALCHEMY_DATABASE_URI": "sqlite://"}, readiness_checks=[database])
db.init_app(app)
app.add_url_rule("/scheme", "scheme", lambda: request.scheme)
client = app.test_client()

assert app.config["PROXY_HOPS"] == 1                       # "1" was parsed as JSON, so it is an int
assert client.get("/healthz").get_json() == {"status": "ok"}
assert client.get("/readyz").get_json() == {"status": "ready"}

# 2. One trusted proxy: X-Forwarded-Proto is honoured, so Flask knows the client used HTTPS
assert client.get("/scheme", headers={"X-Forwarded-Proto": "https"}).text == "https"

# 3. A failing dependency turns readiness into 503 while liveness stays 200
broken = create_app(
    {"SECRET_KEY": "x", "SQLALCHEMY_DATABASE_URI": "sqlite:////nonexistent-dir/bookshelf.db"},
    readiness_checks=[database],
)
db.init_app(broken)
response = broken.test_client().get("/readyz")
assert response.status_code == 503 and response.get_json()["failed"] == ["database: OperationalError"]
assert broken.test_client().get("/healthz").status_code == 200

# 4. No secret key, no application
try:
    create_app()
except RuntimeError as exc:
    print("refused to start:", exc)
----
Source: https://flask.palletsprojects.com/en/stable/testing/[Flask: Testing Flask Applications]

The second assertion is the reason `ProxyFix` appears in the factory: behind a TLS-terminating ingress the application
itself sees plain HTTP, and without the forwarded headers `request.scheme`, `+url_for(..., _external=True)+` and secure cookie
decisions are wrong. <<proxy>> explains how many hops to trust.

[#dev-server]
== Why Not `flask run` in a Container

The `flask run` command and `app.run()` start the Werkzeug development server. The Flask documentation says plainly not to
use it in production: it is single-purpose, not hardened, and not tested for load. Starting the debugger there, which the
older books do with `app.run(debug=True)` or `FLASK_ENV=development` in a Dockerfile, is worse: the interactive debugger
allows arbitrary code execution to anyone who can reach the port and guess or learn its PIN. `FLASK_ENV`, `ENV` and
`app.env` were removed in Flask 2.3 and do nothing in 3.x, so a Dockerfile that still sets them gives no development
behaviour and a false sense of configuration. In a container the production server is the process you run, and the debugger
has no place in the image or in the Compose file that runs it. For local debugging, run the application on the host, outside
the container, as in xref:backend/flask/debugging-logging-and-profiling.adoc[Debugging, Logging & Profiling], pointing at the
Compose-managed database and Redis.

[#gunicorn]
== Gunicorn as the Container's Process

Gunicorn is a pre-fork WSGI server: a master process starts worker processes and replaces them when they die or stall.
The Flask documentation's Gunicorn page shows the minimal form, and the factory is named in quotes with parentheses so that
Gunicorn calls it:

[source,bash]
----
gunicorn "bookshelf:create_app()"
----
Source: https://flask.palletsprojects.com/en/stable/deploying/gunicorn/[Flask: Deploying with Gunicorn]

Everything else goes into `gunicorn.conf.py`, which Gunicorn loads from the working directory by default
(the `--config` setting defaults to `./gunicorn.conf.py`). A file keeps the command line stable and lets values come from
environment variables with sensible defaults:

[source,python]
----
import os

# Gunicorn reads ./gunicorn.conf.py on its own; every name below is a setting
bind = f"0.0.0.0:{os.environ.get('PORT', '8000')}"
workers = int(os.environ.get("WEB_CONCURRENCY", "2"))
threads = int(os.environ.get("GUNICORN_THREADS", "4"))   # threads > 1 selects the gthread worker
worker_tmp_dir = "/dev/shm"        # heartbeat files in memory, not on the container's disk
timeout = 30                       # a silent worker is killed and replaced after this many seconds
graceful_timeout = 25              # time to finish requests after SIGTERM, below the Pod's grace period
keepalive = 5
max_requests = 1000                # recycle workers to bound memory growth ...
max_requests_jitter = 100          # ... without restarting them all at once
accesslog = "-"                    # stdout
errorlog = "-"                     # stderr
loglevel = os.environ.get("GUNICORN_LOG_LEVEL", "info")
----
Source: https://gunicorn.org/reference/settings/[Gunicorn: Settings]

A typo in a setting name is silently a plain variable in a Python file, so it is worth checking once that every name is
a real setting. Gunicorn's own `Config` object rejects unknown ones:

[source,python]
----
from gunicorn.config import Config

cfg = Config()
names = ["bind", "workers", "threads", "worker_tmp_dir", "timeout", "graceful_timeout", "keepalive",
         "max_requests", "max_requests_jitter", "accesslog", "errorlog", "loglevel"]
for name in names:
    cfg.set(name, globals()[name])

assert cfg.bind == ["0.0.0.0:8000"] and cfg.workers == 2 and cfg.threads == 4
assert cfg.worker_class_str == "gthread"          # threads > 1 switched the worker type
try:
    cfg.set("gracefull_timeout", 25)               # the typo is rejected
except AttributeError as exc:
    print("rejected:", exc)
----
Source: https://gunicorn.org/reference/settings/#threads[Gunicorn: Settings, threads]

.The Gunicorn settings that matter in a container
[cols="2,2,5",options="header"]
|===
| Setting | Value used | Why

| `bind`
| `0.0.0.0:$PORT`
| Inside a container the server must listen on all interfaces, or the published port reaches nothing. Platforms such as Cloud Run
tell the container which port to use through `PORT`; publish the port to `127.0.0.1` only when it is for local use.

| `workers`
| `WEB_CONCURRENCY`, default 2
| Gunicorn already defaults to that variable (or 1). Set it explicitly per environment.

| `threads`
| 4
| More than one thread per worker switches to the `gthread` worker, which serves several requests per process and tolerates slow
clients and I/O waits better than the default `sync` worker. Code must be thread-safe, which Flask's context locals are.

| `worker_tmp_dir`
| `/dev/shm`
| Workers write heartbeat files so the master can see they are alive. Gunicorn's documentation warns that disk-backed
filesystems can make that write block; a memory-backed directory avoids it. It also works with a read-only root filesystem.

| `timeout`
| 30
| A worker that does not report for this long is killed and replaced. It is not a request timeout for `gthread` workers
that keep reporting; long work belongs in a queue (see xref:backend/flask/background-jobs-celery-and-email.adoc[Background
Jobs, Celery & E-mail]).

| `graceful_timeout`
| 25
| Time workers get to finish requests after a stop or restart signal. Keep it below the platform's grace period, see <<shutdown>>.

| `max_requests`, `max_requests_jitter`
| 1000, 100
| Recycle workers to contain slow memory leaks in application or extension code; the jitter staggers the restarts.

| `accesslog`, `errorlog`
| `-`
| Standard output and standard error, where the container runtime collects logs. No log files inside the image.

| `forwarded_allow_ips`
| default (`FORWARDED_ALLOW_IPS`)
| Which proxies Gunicorn trusts for scheme headers. See <<proxy>>.

| `preload_app`
| off
| Loads the application in the master before forking, which saves memory through copy-on-write but shares anything created
at import time, such as open database connections, across workers. Leave it off unless startup memory is a measured problem.
|===

*How many workers.* The tempting formula of two times the CPU count plus one assumes the process sees the machine it runs on.
Inside a container, `multiprocessing.cpu_count()` reports the host's CPUs, not the Kubernetes CPU limit or a cgroup quota, so
a pod limited to one CPU on a 64-core node would start 129 workers and be throttled to a crawl. Choose a small, explicit number
(2 to 4), give the container a matching CPU request, and scale out with replicas, which the orchestrator can schedule,
restart and balance. Compare the one-process-per-container reasoning on
xref:backend/fastapi/docker-and-kubernetes.adoc[FastAPI's Docker & Kubernetes page]; Flask differs only in that a
synchronous WSGI process serves one request at a time, so threads (or gevent workers, see
xref:backend/flask/async-gevent-and-quart.adoc[Async, gevent & Quart]) are how a worker serves more than one.

[#proxy]
=== Behind an Ingress: Trusting the Proxy

An ingress controller or load balancer terminates TLS and adds `X-Forwarded-For`, `X-Forwarded-Proto` and
`X-Forwarded-Host`. Two layers can interpret them, and they should not fight. Werkzeug's `ProxyFix` rewrites the WSGI
environment for Flask, and Flask's documentation says to give it exactly the number of proxies you have, because every
`+x_*+` value trusts that many entries from the right of the header, and a client can prepend its own. Gunicorn itself decides the
request scheme from `secure_scheme_headers` for connections from addresses in `forwarded_allow_ips`, which defaults to the
`FORWARDED_ALLOW_IPS` environment variable and, when unset, to loopback only. The usual arrangement in Kubernetes is
`ProxyFix` with the real hop count (one for a single ingress, two with a CDN in front) and no widening of
`forwarded_allow_ips` to `+*+`. Setting `TRUSTED_HOSTS` (Flask 3.1) to the public host names makes Flask reject requests with
another `Host` header, a cheap defence against host-header poisoning that matters once the application builds absolute URLs;
the details are in xref:backend/flask/security-considerations.adoc[Security Considerations]. The nginx and Apache
configurations in front of Gunicorn are covered by the xref:backend/flask/deployment-wsgi-servers-and-proxies.adoc[deployment] page of this section.

Source: https://flask.palletsprojects.com/en/stable/deploying/proxy_fix/[Flask: Tell Flask it is Behind a Proxy]

If a Flask application is mounted inside a FastAPI application with `WSGIMiddleware`, the container runs the ASGI server and
the Flask code shares its process; that arrangement and its limits are in
xref:backend/fastapi/sub-applications-wsgi-and-graphql.adoc[FastAPI: Sub-applications, WSGI & GraphQL]. Everything on this
page then applies to the ASGI server's command instead of Gunicorn's.

[#dockerfile]
== A Production Dockerfile

The Dockerfile below is a two-stage build. The builder stage creates a virtual environment in `/opt/venv` and installs the
locked, hash-checked dependencies, then the project itself without dependencies. The runtime stage starts again from the same
slim image, adds a non-root user, copies the finished environment, and starts Gunicorn. Compilers, pip caches and the source
tree stay in the builder.

[source,dockerfile]
----
# syntax=docker/dockerfile:1
FROM python:3.14-slim AS builder
ENV PIP_NO_CACHE_DIR=1 PIP_DISABLE_PIP_VERSION_CHECK=1
RUN python -m venv /opt/venv
ENV PATH="/opt/venv/bin:$PATH"
WORKDIR /build
# Dependencies first: this layer is rebuilt only when the lock file changes
COPY requirements.lock ./
RUN pip install --require-hashes -r requirements.lock
COPY pyproject.toml ./
COPY src ./src
RUN pip install --no-deps .

FROM python:3.14-slim AS runtime
ENV PYTHONUNBUFFERED=1 \
    PYTHONDONTWRITEBYTECODE=1 \
    PATH="/opt/venv/bin:$PATH"
RUN groupadd --system --gid 10001 app \
 && useradd --system --uid 10001 --gid app --no-create-home --shell /usr/sbin/nologin app
COPY --from=builder /opt/venv /opt/venv
WORKDIR /app
COPY gunicorn.conf.py healthcheck.py ./
USER 10001:10001
EXPOSE 8000
HEALTHCHECK --interval=30s --timeout=3s --start-period=10s --retries=3 \
  CMD ["python", "-c", "import sys, healthcheck; sys.exit(healthcheck.main())"]
CMD ["gunicorn", "bookshelf:create_app()"]
----
Source: https://docs.docker.com/reference/dockerfile/[Docker: Dockerfile reference]

The lock file comes from the project's own tooling. With uv, `uv pip compile pyproject.toml --universal --generate-hashes
-o requirements.lock` writes pinned versions with hashes for every platform, and `--require-hashes` makes pip refuse
anything that does not match, which is the reproducibility and supply-chain property that a bare
`pip install flask` in a Dockerfile lacks. The built image was 245 MB in the run behind this page.

.The decisions in the Dockerfile
[cols="2,5",options="header"]
|===
| Line | What it does and why

| `python:3.14-slim`
| The official image on Debian slim: small, with the usual `python` and `pip`. Pin the minor version so a rebuild does not
jump to a new Python, and use the same tag in both stages so the virtual environment's interpreter path exists in the
runtime. The images the books use (`python:3.8`, `python:3.9`, buster-based tags) are out of support.

| `python -m venv /opt/venv` and `PATH`
| An environment outside the source directory that can be copied whole between stages. Putting it first on `PATH` makes
`gunicorn` and `flask` resolve to it.

| `COPY requirements.lock` before the source
| Layer caching: the install layer is rebuilt only when dependencies change, not on every edit of a view. See
xref:backend/docker/build-cache-and-multi-stage-builds.adoc[Build Cache & Multi-stage Builds].

| `PYTHONUNBUFFERED=1`
| Log lines reach the container runtime immediately instead of waiting in a buffer.

| `PYTHONDONTWRITEBYTECODE=1`
| The environment was byte-compiled at install time, and a read-only filesystem could not take new files anyway.

| `groupadd` / `useradd` with a numeric ID, `USER 10001:10001`
| The process runs without root. A numeric `USER` lets Kubernetes check `runAsNonRoot` (it cannot map a name to an ID).
The user has no home and no login shell.

| `COPY gunicorn.conf.py healthcheck.py`
| Only the two small files that sit beside the package; the application code is in the installed environment, not in
`/app`.

| `HEALTHCHECK`
| Docker and Compose use it; Kubernetes ignores it and uses its own probes (<<kubernetes>>). The slim image has no `curl`, so
the check is a tiny Python script (<<healthcheck>>).

| Exec-form `CMD`
| Gunicorn is PID 1 and receives `SIGTERM` directly. The shell form (`+CMD gunicorn ...+`) runs under `/bin/sh -c`, which does
not forward signals, so `docker stop` waits ten seconds and then kills the container without a graceful shutdown.
|===

A `.dockerignore` keeps the build context small and, more important, keeps secrets and local state out of the image, because
`COPY` and `COPY . .` take everything that is not excluded:

[source,text]
----
.git
.venv
__pycache__
*.pyc
.pytest_cache
.env
.env.*
instance/
tests/
docs/
compose*.yaml
Dockerfile*
----
Source: https://docs.docker.com/build/concepts/context/#dockerignore-files[Docker: Build context, .dockerignore files]

The `instance/` folder holds the instance configuration of
xref:backend/flask/application-factory-and-project-layout.adoc[Application Factory & Project Layout], often a local SQLite file
and a `config.py` with secrets, and must never be baked into an image. Build and run it, passing the secret at run time:

[source,bash]
----
docker build -t bookshelf:1.0.0 .
docker run --rm -p 127.0.0.1:8000:8000 \
  -e BOOKSHELF_SECRET_KEY="$(python -c 'import secrets; print(secrets.token_hex(32))')" \
  bookshelf:1.0.0
----
Source: https://docs.docker.com/reference/cli/docker/container/run/[Docker: docker container run]

[source,bash]
----
$ curl -s localhost:8000/healthz
{"status":"ok"}
$ docker exec <container> id
uid=10001(app) gid=10001(app) groups=10001(app)
----
Source: https://docs.docker.com/reference/cli/docker/container/exec/[Docker: docker container exec]

More on layers, tags and hardening is in xref:backend/docker/dockerfile-fundamentals.adoc[Dockerfile Fundamentals] and
xref:backend/docker/image-best-practices-and-security.adoc[Image Best Practices & Security].

[#uv]
=== A uv-Based Image

If the project is managed with uv, the lock file is `uv.lock` and the builder stage uses `uv sync`. The shape follows uv's own
Docker guide: copy the uv binary from its official image at a pinned version, compile bytecode, use copy link mode because the
cache and the target are different filesystems, install dependencies in their own layer, then the project, and copy only
`.venv` into the final stage:

[source,dockerfile]
----
# syntax=docker/dockerfile:1
FROM python:3.14-slim AS builder
COPY --from=ghcr.io/astral-sh/uv:0.12.23 /uv /uvx /bin/
ENV UV_COMPILE_BYTECODE=1 \
    UV_LINK_MODE=copy \
    UV_PYTHON_DOWNLOADS=never
WORKDIR /app
RUN --mount=type=cache,target=/root/.cache/uv \
    --mount=type=bind,source=uv.lock,target=uv.lock \
    --mount=type=bind,source=pyproject.toml,target=pyproject.toml \
    uv sync --locked --no-install-project --no-dev
COPY pyproject.toml uv.lock ./
COPY src ./src
RUN --mount=type=cache,target=/root/.cache/uv \
    uv sync --locked --no-dev --no-editable

FROM python:3.14-slim AS runtime
ENV PYTHONUNBUFFERED=1 \
    PYTHONDONTWRITEBYTECODE=1 \
    PATH="/app/.venv/bin:$PATH"
RUN groupadd --system --gid 10001 app \
 && useradd --system --uid 10001 --gid app --no-create-home --shell /usr/sbin/nologin app
COPY --from=builder /app/.venv /app/.venv
WORKDIR /app
COPY gunicorn.conf.py healthcheck.py ./
USER 10001:10001
EXPOSE 8000
CMD ["gunicorn", "bookshelf:create_app()"]
----
Source: https://docs.astral.sh/uv/guides/integration/docker/[uv: Using uv in Docker]

`--locked` fails the build when `uv.lock` is out of date with `pyproject.toml`, `--no-dev` leaves test tools out of the image,
and `--no-editable` installs the package into the environment instead of linking to the source tree, so the runtime stage
needs only `.venv`. `UV_PYTHON_DOWNLOADS=never` makes uv use the image's interpreter, and the virtual environment must keep the
same absolute path (`/app/.venv`) in both stages because environments are not relocatable. This image was 234 MB and ran
identically to the pip one. It omits the `HEALTHCHECK` for brevity; add the same lines as above.

[#healthcheck]
=== A Health Check Without curl

The `HEALTHCHECK` command runs inside the container, and the slim image does not ship `curl` or `wget`. A short script from
the standard library does the job and returns the exit code Docker expects (0 healthy, 1 unhealthy):

[source,python]
----
import sys
import urllib.error
import urllib.request


def main(url="http://127.0.0.1:8000/healthz", timeout=2.0):
    try:
        with urllib.request.urlopen(url, timeout=timeout) as response:
            return 0 if response.status == 200 else 1
    except (urllib.error.URLError, OSError):
        return 1
----
Source: https://docs.docker.com/reference/dockerfile/#healthcheck[Docker: Dockerfile reference, HEALTHCHECK]

The function is tested against a real server on an ephemeral port, started with Werkzeug, using both probe endpoints of the
factory:

[source,python]
----
import threading
from werkzeug.serving import make_server

server = make_server("127.0.0.1", 0, app)               # port 0: the OS picks a free port
thread = threading.Thread(target=server.serve_forever, daemon=True)
thread.start()
base = f"http://127.0.0.1:{server.server_port}"
try:
    assert main(base + "/healthz") == 0                  # healthy
    assert main(base + "/readyz") == 0                   # the SQLite check passes
    assert main(base + "/missing") == 1                  # 404 becomes unhealthy
finally:
    server.shutdown()
assert main(base + "/healthz", timeout=0.5) == 1         # nothing is listening any more
----
Source: https://werkzeug.palletsprojects.com/en/stable/serving/[Werkzeug: Serving WSGI Applications]

[#config-secrets]
== Configuration and Secrets in a Container

A container image must be the same in every environment, so everything that differs travels in the environment. With
`from_prefixed_env("BOOKSHELF")` every `+BOOKSHELF_*+` variable becomes a config key; values are parsed as JSON where they can
be (so `"1"` is an integer and `"false"` a boolean) and stay strings otherwise, and `+BOOKSHELF_CELERY__broker_url+` sets
the nested key `broker_url` of the `CELERY` dictionary, which is what the Celery pattern of
xref:backend/flask/background-jobs-celery-and-email.adoc[Background Jobs, Celery & E-mail] reads. Flask itself supports the
`FLASK_` prefix by default.

* *Secrets stay out of the image.* No `+ENV BOOKSHELF_SECRET_KEY=...+` and no `ARG` carrying a password: both are recorded in
the image's metadata and layers, and anyone who can pull the image can read them. Pass them at run time, from a Kubernetes
Secret, a Compose `.env` file that is git-ignored, or a secret manager. This is also why `.env` is in `.dockerignore`.
* *One key for every replica.* Flask signs the session cookie, CSRF tokens and `itsdangerous` tokens with `SECRET_KEY`. If each
replica generates its own at start-up, a user's session fails whenever the load balancer picks another Pod. Generate the key
once (`secrets.token_hex(32)`), store it in the Secret, and rotate with `SECRET_KEY_FALLBACKS` (Flask 3.1), the list of old keys
still accepted for verification, as described in
xref:backend/flask/security-considerations.adoc[Security Considerations].
* *Database URLs with special characters.* A password containing `@`, `/` or `:` breaks a URL built by string formatting. Use a
password that is URL-safe (hexadecimal output of `secrets.token_hex` is) or build the URL with SQLAlchemy's `URL.create()`.
* *Read-only root filesystem.* Run the container with `read_only: true` (Compose) or `readOnlyRootFilesystem: true`
(Kubernetes) and give it a writable `/tmp`. Python's `tempfile` needs one: Werkzeug spools large uploads there (see
xref:backend/flask/file-uploads.adoc[File Uploads]) and Celery's worker, as a test for this page showed, fails with "No usable
temporary directory" without it.

A Kubernetes Secret can be created without writing a key into any file, using a command that generates it on the spot:

[source,bash]
----
kubectl create namespace bookshelf
kubectl --namespace bookshelf create secret generic bookshelf-secrets \
  --from-literal=BOOKSHELF_SECRET_KEY="$(python -c 'import secrets; print(secrets.token_hex(32))')" \
  --from-literal=BOOKSHELF_SQLALCHEMY_DATABASE_URI="$DATABASE_URL"
----
Source: https://kubernetes.io/docs/tasks/configmap-secret/managing-secret-using-kubectl/[Kubernetes: Managing Secrets using kubectl]

Run it once: executing it again would generate a different key and invalidate every session. In a real cluster the Secret is
usually produced from a secret manager by an operator or by sealed or encrypted manifests; see
xref:backend/kubernetes/secrets.adoc[Kubernetes Secrets] for the options and for the fact that a Secret is only base64, not
encryption, unless encryption at rest is configured.

== Docker Compose: Web, PostgreSQL, Redis and a Worker

Compose describes the whole stack for a single host, which is the right tool for local development and small deployments.
This file runs the web application, a one-shot migration service, PostgreSQL 18, Redis 8 and a Celery worker built from the same
image. It has no `version:` key (the Compose Specification ignores it) and is run with `docker compose`, the plugin that
replaced the old `docker-compose` v1 binary, which is end of life.

[source,yaml]
----
name: bookshelf

x-app-env: &app-env

  BOOKSHELF_SQLALCHEMY_DATABASE_URI: postgresql+psycopg://bookshelf:${POSTGRES_PASSWORD:?set it in the .env file}@db:5432/bookshelf
  BOOKSHELF_CELERY__broker_url: redis://redis:6379/0

services:
  db:
    image: postgres:18
    environment:
      POSTGRES_USER: bookshelf
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD:?set it in the .env file}
      POSTGRES_DB: bookshelf
    volumes:
      - pgdata:/var/lib/postgresql
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U bookshelf -d bookshelf"]
      interval: 5s
      timeout: 3s
      retries: 10

  redis:
    image: redis:8
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 5s
      timeout: 3s
      retries: 10

  migrate:
    build: .
    command: ["flask", "--app", "bookshelf:create_app", "db", "upgrade"]
    environment: *app-env
    depends_on:
      db:
        condition: service_healthy
    restart: "no"

  web:
    build: .
    ports:
      - "127.0.0.1:8000:8000"
    environment:
      <<: *app-env
      WEB_CONCURRENCY: "2"
    depends_on:
      migrate:
        condition: service_completed_successfully
      redis:
        condition: service_healthy
    stop_grace_period: 30s
    read_only: true
    tmpfs:
      - /tmp
    cap_drop: [ALL]
    security_opt: ["no-new-privileges:true"]

  worker:
    build: .
    command: ["celery", "--app", "bookshelf.tasks:celery_app", "worker", "--loglevel", "INFO", "--concurrency", "2"]
    environment: *app-env
    depends_on:
      migrate:
        condition: service_completed_successfully
      redis:
        condition: service_healthy
    healthcheck:

      timeout: 10s
      retries: 3

      - /tmp

The secrets live in a git-ignored `.env` file that Compose reads automatically, created once with generated values (and the
`:?` forms make Compose stop with a message if either is missing):

[source,bash]
----
printf 'BOOKSHELF_SECRET_KEY=%s\nPOSTGRES_PASSWORD=%s\n' \
  "$(python -c 'import secrets; print(secrets.token_hex(32))')" \
  "$(python -c 'import secrets; print(secrets.token_hex(16))')" > .env
docker compose config --quiet && docker compose up --build
----
Source: https://docs.docker.com/compose/how-tos/environment-variables/set-environment-variables/[Docker Compose: Set environment variables]

In the run behind this page (with the migration command replaced by a no-op, because the sample project has no migration
folder), `docker compose ps` showed `db` and `redis` healthy, `web` healthy through the image's `HEALTHCHECK`, and the worker
healthy through `celery inspect ping`, and `curl localhost:8000/readyz` answered `+{"status":"ready"}+`.

What the file shows, point by point:

* *Order comes from health, not from the order of lines.* `depends_on` with `condition: service_healthy` waits for the database
to accept connections, and `service_completed_successfully` makes `web` and `worker` wait for the `migrate` service to exit
with status 0. A plain `depends_on` only waits for the container to start, which is the mistake behind the "connection
refused" errors of older tutorials.
* *Migrations are a service, not part of the web command.* With two web replicas a start-up migration races itself; the
dedicated service runs once. The same idea in Kubernetes is a Job, <<migrations>>.
* *The hardening options work for Flask.* `read_only` with a `tmpfs` for `/tmp`, `cap_drop: [ALL]` and `no-new-privileges` ran
the application and the worker without trouble. Gunicorn's heartbeat directory is `/dev/shm`, which Docker mounts as a
memory filesystem.
* *`stop_grace_period: 30s`* gives Gunicorn's 25-second `graceful_timeout` room, because Compose's default is ten seconds
(<<shutdown>>).
* *The port is published on `127.0.0.1`.* `"8000:8000"` would expose the service on every interface of the host.
* *`$$HOSTNAME`* escapes the dollar sign so that Compose passes it to the container's shell, which expands it to the worker's
name for `inspect ping`.
* *The worker reuses the image.* It differs only by `command`. Its Celery application lives in a module of the package
(`bookshelf.tasks`), built as described in xref:backend/flask/background-jobs-celery-and-email.adoc[Background Jobs, Celery &
E-mail]. Running it as a separate service lets you scale it independently with `docker compose up --scale worker=3`.

For development on the host, `docker compose up db redis` starts only the dependencies, and `flask --app bookshelf run
--debug` on the host connects to them; that keeps the debugger out of every container. See
xref:backend/docker/compose-in-practice.adoc[Compose in Practice] for profiles, overrides and watch mode.

Source: https://docs.docker.com/reference/compose-file/services/[Docker Compose: Services reference]

[#shutdown]
== Health Endpoints and Graceful Shutdown

*Two probes, two questions.* Liveness asks "should this process be restarted?", readiness asks "should it receive traffic?".
`/healthz` therefore does nothing but answer, and `/readyz` checks what a request needs. The mistake to avoid is a
liveness probe that calls the database: when the database is down every Pod then fails liveness, Kubernetes restarts all of
them, and a recoverable outage becomes a restart storm. A readiness failure only removes the Pod from the Service, which is
the right reaction. Keep readiness checks cheap and bounded by timeouts (for PostgreSQL put `connect_timeout` in the `connect_args` of
`SQLALCHEMY_ENGINE_OPTIONS` so a hung database cannot hold a probe for minutes), and do not check optional dependencies that the
application can live without. The generic probe mechanics are in
xref:backend/kubernetes/health-probes-and-lifecycle.adoc[Health Probes & Lifecycle].

*What happens at shutdown.* When a container is stopped, the runtime sends `SIGTERM` to PID 1 and, after the grace period,
`SIGKILL`. Gunicorn's master reacts to `SIGTERM` by stopping the acceptance of connections and giving the workers
`graceful_timeout` seconds to finish their requests. The log of the stopped container in this page's run:

[source,text]
----
[2026-10-07 14:52:49 +0000] [1] [INFO] Handling signal: term
[2026-10-07 14:52:49 +0000] [7] [INFO] Worker exiting (pid: 7)
[2026-10-07 14:52:49 +0000] [8] [INFO] Worker exiting (pid: 8)
[2026-10-07 14:52:49 +0000] [1] [INFO] Shutting down: Master
----
Source: https://gunicorn.org/guides/docker/[Gunicorn: Docker guide]

The process is PID 1 (`[1]`) because of the exec-form `CMD`; the whole stop took well under a second with idle workers.
Three timers have to be ordered correctly, from the shortest:

.Shutdown timers, shortest first
[cols="2,2,5",options="header"]
|===
| Timer | Value used | Rule

| Kubernetes `preStop` sleep
| 5 s
| Endpoint removal and `SIGTERM` happen at the same time, and some load balancers keep sending requests for a moment. A short
sleep before `SIGTERM` lets in-flight routing settle.

| Gunicorn `graceful_timeout`
| 25 s
| Longer than your slowest legitimate request, shorter than the grace period minus the `preStop` sleep.

| `terminationGracePeriodSeconds` (Pod), `stop_grace_period` (Compose)
| 40 s, 30 s
| After this the runtime sends `SIGKILL` whatever the workers are doing. The default of 30 s in Kubernetes and 10 s in Compose is
shorter than many `graceful_timeout` values.
|===

Source: https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/#pod-termination[Kubernetes: Pod Lifecycle, Termination of Pods]

[#migrations]
== Running Migrations

Migrations change the schema every replica depends on, so they run exactly once per release, before the new version serves
traffic, and with a database account allowed to change the schema (the application's own account should not be). Flask-Migrate's
`flask db upgrade` is the command, as explained in
xref:backend/flask/database-migrations.adoc[Database Migrations]: that page also covers backward-compatible
(expand and contract) changes, which you need because during a rolling update the old and new versions run side by side
against the new schema. In containers there are three ways to run it:

* *A separate Compose service or `docker compose run --rm migrate`* on a single host, as in the Compose file above.
* *A Kubernetes Job* that uses the same image and the migrator's credentials, applied before the Deployment is updated
(<<job>>). An init container on the web Pods is the tempting shortcut and the wrong one: it runs in every Pod, so three
replicas race to migrate.
* *A release or pre-deploy hook* of the platform or the pipeline (a Helm hook, an Argo CD pre-sync hook, Cloud Run jobs),
which is the same Job with scheduling done for you.

Do not put `+flask db upgrade && gunicorn ...+` in the image's `CMD` unless there is exactly one container; the shell form that
requires also loses signal handling.

[#deployment]
=== Deployment

The Deployment runs three replicas with a rolling update that never removes a Pod before its replacement is ready
(`maxUnavailable: 0`, `maxSurge: 1`). The container runs as the image's numeric user, without privilege escalation or
capabilities, with a read-only root filesystem and an in-memory-limited `emptyDir` for `/tmp`. Requests size the scheduling
decision (and the Horizontal Pod Autoscaler's percentage); a memory limit stops a leak from taking the node, and there is no
CPU limit, which avoids throttling a request-heavy Gunicorn worker.

[source,yaml]
----
apiVersion: apps/v1
kind: Deployment
metadata:
  name: bookshelf-web
  namespace: bookshelf
  labels:
    app.kubernetes.io/name: bookshelf
    app.kubernetes.io/component: web
spec:
  replicas: 3
  revisionHistoryLimit: 5
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 0
      maxSurge: 1
  selector:
    matchLabels:
      app.kubernetes.io/name: bookshelf
      app.kubernetes.io/component: web
  template:
    metadata:
      labels:
        app.kubernetes.io/name: bookshelf
        app.kubernetes.io/component: web
    spec:
      terminationGracePeriodSeconds: 40
      securityContext:
        runAsNonRoot: true
        runAsUser: 10001
        runAsGroup: 10001
        seccompProfile:
          type: RuntimeDefault
      containers:
        - name: web
          image: registry.example.com/bookshelf:1.0.0
          ports:
            - name: http
              containerPort: 8000
          envFrom:
            - configMapRef:
                name: bookshelf-config
            - secretRef:
                name: bookshelf-secrets
          resources:
            requests:
              cpu: 250m
              memory: 256Mi
            limits:
              memory: 512Mi
          startupProbe:
            httpGet:
              path: /healthz
              port: http
            periodSeconds: 2
            failureThreshold: 30
          readinessProbe:
            httpGet:
              path: /readyz
              port: http
            periodSeconds: 5
            timeoutSeconds: 3
            failureThreshold: 2
          livenessProbe:
            httpGet:
              path: /healthz
              port: http
            periodSeconds: 10
            timeoutSeconds: 3
            failureThreshold: 3
          lifecycle:
            preStop:
              sleep:
                seconds: 5
          securityContext:
            allowPrivilegeEscalation: false
            readOnlyRootFilesystem: true
            capabilities:
              drop: ["ALL"]
          volumeMounts:
            - name: tmp
              mountPath: /tmp
      volumes:
        - name: tmp
          emptyDir:
            sizeLimit: 256Mi
----
Source: https://kubernetes.io/docs/concepts/workloads/controllers/deployment/[Kubernetes: Deployments]

* *Three probes.* The startup probe gives the application up to a minute to boot before liveness starts counting; readiness
uses `/readyz` and liveness `/healthz`, for the reasons in <<shutdown>>. Probes address the port by name (`http`), so a
port change is made in one place.
* *`runAsUser: 10001`* matches the image. With `runAsNonRoot: true`, Kubernetes refuses to start an image whose `USER` is root
or a name it cannot resolve to a numeric ID.
* *The `/tmp` volume* is what lets `readOnlyRootFilesystem: true` coexist with uploads and Celery; the Gunicorn heartbeat
directory `/dev/shm` is provided by the container runtime.
* *Replicas of a synchronous app are cheap protection.* Two Gunicorn workers per Pod and three Pods give six concurrent
request-processing processes (times four threads) and survive the loss of a node.
* *The Celery worker* is a second Deployment with the same Pod template, `command: ["celery", "--app",
"bookshelf.tasks:celery_app", "worker"]`, no Service and no HTTP probes (an `exec` probe running `celery inspect ping` works,
as in the Compose file). Scale it on queue length, not CPU, for instance with KEDA; the generic pieces are in
xref:backend/kubernetes/replicasets-and-deployments.adoc[ReplicaSets & Deployments] and
xref:backend/kubernetes/autoscaling.adoc[Autoscaling].

[#service-ingress]
=== Service and Ingress

The Service gives the Pods one stable address and balances across the ready ones. The Ingress publishes it with TLS. The
`ingressClassName` must name the IngressClass of a controller that is installed in the cluster; the example uses a
placeholder because the Kubernetes project retired the widely used ingress-nginx controller and the Ingress API is frozen in
favour of the Gateway API, both discussed on xref:backend/kubernetes/ingress.adoc[Ingress] and
xref:backend/kubernetes/gateway-api.adoc[Gateway API]. Whichever you use, the controller is the proxy that
`BOOKSHELF_PROXY_HOPS` counts.

[source,yaml]
----
apiVersion: v1
kind: Service
metadata:
  name: bookshelf-web
  namespace: bookshelf
spec:
  type: ClusterIP
  selector:
    app.kubernetes.io/name: bookshelf
    app.kubernetes.io/component: web
  ports:
    - name: http
      port: 80
      targetPort: http
---
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: bookshelf
  namespace: bookshelf
spec:
  ingressClassName: example-class     # the IngressClass of the controller installed in the cluster
  tls:
    - hosts: ["bookshelf.example.com"]
      secretName: bookshelf-tls
  rules:
    - host: bookshelf.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: bookshelf-web
                port:
                  name: http
----
Source: https://kubernetes.io/docs/concepts/services-networking/ingress/[Kubernetes: Ingress]

Static files (see xref:backend/flask/static-files-and-assets.adoc[Static Files & Assets]) should not make Gunicorn busier than
necessary: build them into the image and serve them from a CDN or an object store when traffic is real, or add a caching
layer at the ingress; Flask can serve them with correct cache headers, but a worker that streams a large file is a worker
that does not run Python.

[#job]
=== A Migration Job

The Job runs the same image with a different command and the migrator's credentials. `backoffLimit: 0` makes a failed
migration stop the pipeline instead of retrying a half-applied revision; `activeDeadlineSeconds` bounds a stuck one;
`ttlSecondsAfterFinished` removes the finished Job; the name carries the version, so the next release creates a new Job:

[source,yaml]
----
apiVersion: batch/v1
kind: Job
metadata:
  name: bookshelf-migrate-1-0-0
  namespace: bookshelf
spec:
  backoffLimit: 0
  activeDeadlineSeconds: 600
  ttlSecondsAfterFinished: 86400
  template:
    spec:
      restartPolicy: Never
      securityContext:
        runAsNonRoot: true
        runAsUser: 10001
        seccompProfile:
          type: RuntimeDefault
      containers:
        - name: migrate
          image: registry.example.com/bookshelf:1.0.0
          command: ["flask", "--app", "bookshelf:create_app", "db", "upgrade"]
          envFrom:
            - configMapRef:
                name: bookshelf-config
            - secretRef:
                name: bookshelf-migrator
          securityContext:
            allowPrivilegeEscalation: false
            readOnlyRootFilesystem: true
            capabilities:
              drop: ["ALL"]
          volumeMounts:
            - name: tmp
              mountPath: /tmp
      volumes:
        - name: tmp
          emptyDir: {}
----
Source: https://kubernetes.io/docs/concepts/workloads/controllers/job/[Kubernetes: Jobs]

The pipeline applies the Job, waits for it (`kubectl wait --for=condition=complete job/bookshelf-migrate-1-0-0 --timeout=10m`),
and only then updates the Deployment image. The same pattern for scheduled maintenance commands (the `flask` CLI commands of
xref:backend/flask/cli-and-shell.adoc[CLI & Shell]) is a CronJob, see
xref:backend/kubernetes/jobs-and-cronjobs.adoc[Jobs & CronJobs].

[#scaling]
=== Autoscaling and Disruption Budgets

A HorizontalPodAutoscaler adds replicas when average CPU utilisation (relative to the request) passes 70 percent, and a
PodDisruptionBudget keeps node drains from taking every Pod at once:

[source,yaml]
----
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: bookshelf-web
  namespace: bookshelf
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: bookshelf-web
  minReplicas: 3
  maxReplicas: 10
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70
---
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: bookshelf-web
  namespace: bookshelf
spec:
  maxUnavailable: 1
  selector:
    matchLabels:
      app.kubernetes.io/name: bookshelf
      app.kubernetes.io/component: web
----
Source: https://kubernetes.io/docs/tasks/run-application/horizontal-pod-autoscale/[Kubernetes: Horizontal Pod Autoscaling]

CPU is a fair signal for a CPU-bound Flask application and a poor one for a service that mostly waits on a database; there,
scale on request concurrency or latency from your metrics system. Details of both objects are in
xref:backend/kubernetes/autoscaling.adoc[Autoscaling] and xref:backend/kubernetes/scheduling-and-disruptions.adoc[Scheduling &
Disruptions].

[#managed]
== Managed Container Platforms

The same image runs on platforms that take a container and give back a URL; what changes is the contract. Google Cloud Run
starts the container with a `PORT` environment variable (the `bind` line of `gunicorn.conf.py` already honours it), scales
to zero, and bills per request, so keep start-up fast and put background work in jobs or Cloud Tasks
(xref:cloud/google-cloud/cloud-run.adoc[Cloud Run]). AWS ECS on Fargate takes the same image from ECR with a task
definition and a load balancer health check pointing at `/healthz`
(xref:cloud/aws/ecs-and-fargate.adoc[ECS & Fargate]). The platform-by-platform Flask specifics (PythonAnywhere, App Engine,
Elastic Beanstalk, Azure App Service) and the monitoring that goes with them are in
xref:backend/flask/cloud-platforms-and-monitoring.adoc[Cloud Platforms & Monitoring]. The books' Cloud Run chapter built the image
with the now retired Container Registry and deployed by hand; today the image lives in Artifact Registry (or ECR) and the
pipeline below pushes it.

[#cicd]
== CI/CD with GitHub Actions

The pipeline has one job to test, one to build and push the image, and a deployment step that is yours (a `kubectl set image`,
a GitOps commit, a Cloud Run deploy). Images are tagged with the commit and, for releases, the version; a pull request
builds but does not push.

.Test, build, authenticate with a short-lived token and push; the deployment pulls by tag
[mermaid]
----
flowchart LR
    Push["Push or tag"] --> Test["Test job: pytest"]
    Test --> Build["Image job: build with Buildx"]
    Build --> OIDC["Request OIDC token from GitHub"]
    OIDC --> Cloud["Cloud provider checks repository and branch"]
    Cloud --> Token["Short-lived registry credentials"]
    Token --> Reg[("Artifact Registry or ECR")]
    Reg --> Deploy["Deploy: migration Job, then Deployment image update"]
----

*Why OIDC.* The books store a JSON service-account key (or AWS access keys) as a repository secret. A key is long-lived, can be
copied out of a log or a fork, and has to be rotated by hand. With OpenID Connect, GitHub issues each job a signed token
describing the repository, the branch and the workflow; the cloud provider is configured to trust tokens that match a
condition and exchanges them for credentials that live for an hour. Nothing secret is stored in GitHub, which is why the
workflows below contain only identifiers (stored as repository variables, not secrets) and the `id-token: write` permission,
which lets the job request a token but grants nothing by itself. The provider side must restrict the trust: a Google
workload identity pool needs an attribute condition (for instance on the repository owner), an AWS role a trust policy on the
`sub` claim naming the repository and branch, otherwise any repository on GitHub could assume it.

The first workflow pushes to *Google Artifact Registry* with the `google-github-actions/auth` action. Images are named
`REGION-docker.pkg.dev/PROJECT/REPOSITORY/IMAGE`, and the service account needs the Artifact Registry Writer role. (The
`gcr.io` hostnames of Container Registry, shut down in 2025, are gone: use Artifact Registry.)

[source,yaml]
----
name: Image to Artifact Registry

on:
  push:
    branches: [main]
    tags: ["v*"]
  pull_request:

permissions:
  contents: read

env:
  IMAGE: ${{ vars.GCP_REGION }}-docker.pkg.dev/${{ vars.GCP_PROJECT_ID }}/bookshelf/web

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-python@v7
        with:
          python-version: "3.14"
          cache: pip
      - run: |
          pip install --require-hashes -r requirements.lock
          pip install --no-deps . pytest
          pytest

  image:
    needs: test
    runs-on: ubuntu-latest
    permissions:
      contents: read
      id-token: write          # lets the job request an OIDC token, nothing more
    steps:
      - uses: actions/checkout@v7
      - id: auth
        if: github.event_name != 'pull_request'
        uses: google-github-actions/auth@v3
        with:
          workload_identity_provider: ${{ vars.GCP_WORKLOAD_IDENTITY_PROVIDER }}
          service_account: ${{ vars.GCP_PUSH_SERVICE_ACCOUNT }}
          token_format: access_token
      - if: github.event_name != 'pull_request'
        uses: docker/login-action@v4
        with:
          registry: ${{ vars.GCP_REGION }}-docker.pkg.dev
          username: oauth2accesstoken
          password: ${{ steps.auth.outputs.access_token }}
      - id: meta
        uses: docker/metadata-action@v6
        with:
          images: ${{ env.IMAGE }}
          tags: |
            type=sha
            type=semver,pattern={{version}}
      - uses: docker/setup-buildx-action@v4
      - uses: docker/build-push-action@v7
        with:
          context: .
          push: ${{ github.event_name != 'pull_request' }}
          tags: ${{ steps.meta.outputs.tags }}
          labels: ${{ steps.meta.outputs.labels }}
          cache-from: type=gha
          cache-to: type=gha,mode=max
----
Source: https://github.com/google-github-actions/auth[google-github-actions/auth: Authenticate to Google Cloud from GitHub Actions]

The second pushes to *Amazon ECR*: `configure-aws-credentials` assumes an IAM role through OIDC (`role-to-assume`, with
`id-token: write`), `amazon-ecr-login` logs Docker in and reports the registry host, and the rest is identical:

[source,yaml]
----
name: Image to Amazon ECR

on:
  push:
    branches: [main]
    tags: ["v*"]

permissions:
  contents: read

jobs:
  image:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      id-token: write
    steps:
      - uses: actions/checkout@v7
      - uses: aws-actions/configure-aws-credentials@v6
        with:
          role-to-assume: ${{ vars.AWS_PUSH_ROLE_ARN }}
          aws-region: ${{ vars.AWS_REGION }}
      - id: ecr
        uses: aws-actions/amazon-ecr-login@v2
      - id: meta
        uses: docker/metadata-action@v6
        with:
          images: ${{ steps.ecr.outputs.registry }}/bookshelf-web
          tags: |
            type=sha
            type=semver,pattern={{version}}
      - uses: docker/setup-buildx-action@v4
      - uses: docker/build-push-action@v7
        with:
          context: .
          push: true
          tags: ${{ steps.meta.outputs.tags }}
          labels: ${{ steps.meta.outputs.labels }}
          cache-from: type=gha
          cache-to: type=gha,mode=max
----
Source: https://github.com/aws-actions/configure-aws-credentials[aws-actions/configure-aws-credentials: OIDC with GitHub Actions]

Notes that apply to both:

* *Test before you build.* The `image` job `needs: test`, so a red build never produces an image. Run the container-level
checks too (start the image, probe `/readyz`), as the xref:backend/docker/index.adoc[Docker pages] show in
xref:backend/docker/ci-cd-with-github-actions.adoc[Docker CI/CD with GitHub Actions], together with the tag and label
conventions of `docker/metadata-action`, Buildx caching and image scanning.
* *Pull requests get no credentials.* The authentication and login steps are skipped for `pull_request`, so a fork's workflow
never obtains registry access and the build still verifies that the Dockerfile works.
* *Pin the actions.* Major-version tags are shown for readability; for a supply-chain-hardened pipeline pin each third-party
action to a commit SHA and let Dependabot keep them current.
* *Deploy by immutable tag.* Deploy `bookshelf:sha-<commit>` or the version tag, never `latest`, so a rollback is
`kubectl rollout undo` or the previous tag. Registry and cloud specifics are in
xref:cloud/google-cloud/container-registry-and-builds.adoc[Artifact Registry & Cloud Build] and
xref:cloud/aws/container-registry.adoc[Amazon ECR]; GitOps delivery is in
xref:backend/kubernetes/gitops-and-ci-cd.adoc[GitOps & CI/CD].

[#pitfalls]
== Pitfalls and Security

[cols="2,5",options="header"]
|===
| Pitfall | What to do

| `CMD python app.py` or `flask run --host 0.0.0.0` in the image
| The development server in production, and with `debug=True` a remote-code-execution endpoint. Use Gunicorn.

| `FLASK_ENV=development` in the Dockerfile
| Removed in Flask 2.3, ignored in 3.x. Delete it; there is no environment switch, only `FLASK_DEBUG` and `--debug`, which do not
belong in an image.

| Shell-form `CMD` or an `ENTRYPOINT` script that does not `exec`
| `SIGTERM` never reaches Gunicorn and every stop becomes a kill after the grace period. Use exec form, or end a wrapper script
with `+exec gunicorn ...+`.

| Worker count from `cpu_count()`
| A container sees the host's CPUs. Set `WEB_CONCURRENCY` explicitly.

| Different `SECRET_KEY` in each replica
| Sessions and CSRF tokens fail at random. One key from one Secret.

| Secrets in `ENV`, `ARG`, a copied `.env` or `instance/` folder
| They are readable from the image. Inject at run time and keep them in `.dockerignore`.

| Container running as root
| Add a numeric non-root `USER`; set `runAsNonRoot`, drop capabilities, use a read-only root filesystem with a `/tmp` volume.

| Liveness probe that checks the database
| A database outage restarts every Pod. Liveness only proves the process answers; readiness holds the dependency checks.

| `ProxyFix` with too many hops, or Gunicorn `+forwarded_allow_ips="*"+`
| Clients can forge their address and scheme. Trust the number of proxies you have.

| Grace period shorter than `graceful_timeout`
| Requests are cut off during a deployment. Order the timers as in <<shutdown>>.

| Migrations in the web container's start command
| They race between replicas. Run a Job or a release step once, then roll out.

| `:latest` images and unpinned `FROM`
| Builds drift and rollbacks are impossible. Pin the Python minor version, lock dependencies with hashes, and tag by version
or digest.

| Long-lived cloud keys as repository secrets
| Use OIDC federation with a narrow trust condition and `id-token: write` only on the job that needs it.

| Using the container for scheduled or heavy work
| Move it to a Celery worker or a CronJob; do not run it inside a web worker, where `timeout` will kill it.
|===

[#books]
== What the Books Show and What Changed

The books' deployment chapters (the cookbook chapters on microservices and containers, the API book's chapter on dockerizing
microservice APIs, and the unit-testing book's containerization and deployment chapter) were written between 2018 and 2023
and need these corrections before reuse:

* *Dockerfiles built on `python:3.8`, `python:3.9` or buster-based images* use end-of-life Python versions and an old Debian
release. Start from `python:3.14-slim` (or the minor version your dependencies support) and rebuild regularly to pick up
patches.
* *`FLASK_ENV` in Dockerfiles and `.flaskenv` files* was removed in Flask 2.3, the very version one of the books targets. Remove
it; use `--debug` locally, never in an image.
* *`CMD ["python", "app.py"]` with `app.run(debug=True)`* is the development server and the debugger inside a container. Use
Gunicorn with a configuration file, as shown here. The Flask documentation says the development server must not be used in
production.
* *Single-stage images with a bare `pip install -r requirements.txt`* work but are larger and not reproducible. A multi-stage
build with hash-locked dependencies (or `uv sync --locked`) is the current practice, with a non-root user.
* *`version: "3"` at the top of `docker-compose.yml` and the `docker-compose` command* belong to Compose v1, which is
discontinued. Compose V2 (`docker compose`) follows the Compose Specification, where `version` is obsolete and ignored.
* *Pushing to `gcr.io` (Container Registry)* no longer works for new projects: the service was shut down in 2025 in favour of
Artifact Registry, with `REGION-docker.pkg.dev` addresses.
* *A JSON service-account key in a GitHub secret* is the old way to authenticate a pipeline. Workload Identity Federation (Google)
or an OIDC role (AWS) removes the stored key.
* *Heroku's free tier, Zappa on AWS Lambda and Aurora Serverless v1* appear in the books' deployment chapters; the free tier is gone,
Zappa is not part of Flask's documented deployment options, and Aurora Serverless v1 reached end of life in March 2025. The
current choices are in xref:backend/flask/cloud-platforms-and-monitoring.adoc[Cloud Platforms & Monitoring].
* *Kubernetes on minikube* in the books shows a Deployment and a NodePort Service. That still works for learning;
the manifests above add probes, a security context, resource requests, a Job for migrations and an Ingress, which is what a
real service needs.
* *Postgres in a container with an anonymous volume* was fine for a tutorial; use a named volume (as in the Compose file; note
that the official `postgres:18` image keeps its data under `/var/lib/postgresql`, one level above where older images
did) or, better, a managed database.

== Recent Changes

.Versions that matter on this page
[cols="2,5",options="header"]
|===
| Version | Change

| Flask 3.1 (2024-11)
| `SECRET_KEY_FALLBACKS` for key rotation and `TRUSTED_HOSTS` for host validation, both useful behind an ingress.

| Flask 3.1 and 3.0
| Flask 3.1 requires Python 3.9 or newer (3.0 dropped 3.7); `flask.Markup` and `flask.escape` were removed in 3.0, which matters when upgrading old images.

| Flask 2.3 (2023-04)
| `FLASK_ENV`, `ENV` and `app.env` removed; `--debug` and `FLASK_DEBUG` are the only switches.

| Flask 2.2 (2022-08)
| `flask --app <module> run --debug` becomes the documented form; `FLASK_APP` still works.

| Gunicorn 26.2.0
| Current on 2026-10-07; reads `./gunicorn.conf.py` by default, and `threads` above 1 selects the `gthread` worker.

| Python 3.14
| Current stable; `python:3.14-slim` is the base used here. The binary wheels used (for example `psycopg-binary`) are published
for it.

| Docker Compose V2
| `version:` is obsolete; `docker compose` is the command; `depends_on` conditions such as `service_completed_successfully`.

| Kubernetes 1.34
| The version of the schemas used to validate the manifests; the lifecycle `sleep` action is available for `preStop`.

| Flask 3.2 (unreleased)
| No change to containerization. The merge of the application and request contexts does not affect Gunicorn, probes or
configuration; see the xref:backend/flask/database-migrations.adoc[migration] page of this section once published.
|===

[#summary]
== Summary

Run Flask in a container as a production server, not the development one: Gunicorn in exec form, configured by
`gunicorn.conf.py` with a few workers and threads, `/dev/shm` for heartbeats and a `graceful_timeout` shorter than the
platform's grace period. Build the image in two stages from a pinned slim base with hash-locked dependencies, run it as a
numeric non-root user, and keep secrets and the `instance/` folder out of it. Read configuration with `from_prefixed_env()`,
share one `SECRET_KEY`, and trust exactly the proxies you have with `ProxyFix`. Expose `/healthz` and `/readyz`, with
dependency checks only in readiness. Use Compose with health-based ordering and a migrate service on one host, and on
Kubernetes a Deployment with probes, a hardened security context and a writable `/tmp`, a Service and Ingress, a Job for
migrations, and an autoscaler with a disruption budget. Let GitHub Actions test, build and push by OIDC to Artifact Registry or
ECR, and deploy by immutable tag.
