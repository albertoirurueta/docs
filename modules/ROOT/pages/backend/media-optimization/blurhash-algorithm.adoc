= BlurHash: The Algorithm
:description: How BlurHash turns an image into a 20 to 30 character string and back: sRGB to linear conversion, the DCT-like component equation, size flag, maximum AC quantisation, DC and AC packing, the base83 alphabet, decoding and the punch parameter, with a worked example, guidance and implementations per language.
:keywords: BlurHash, ThumbHash, placeholder, DCT, cosine basis, base83, sRGB, linear light, punch, image placeholder, woltapp, blurha.sh
:stem: latexmath

include::partial$ai-disclaimer.adoc[]

Baseline date: 2026-10-07. This page follows the reference implementation in the
https://github.com/woltapp/blurhash[woltapp/blurhash] repository: its
https://github.com/woltapp/blurhash/blob/master/Algorithm.md[Algorithm.md] and the
https://github.com/woltapp/blurhash/tree/master/TypeScript/src[reference TypeScript code]. The numbers in the worked
example were produced with the `blurhash` npm package (version 2.0.5) and cross-checked against a Python port. The cover examples further down were run with that package,
blurhash-java 1.0.0, `blurhash-python` 1.2.2, `blurhash` 1.1.5 (the other Python package) and `thumbhash` 0.1.1.

A BlurHash is a short string, usually 20 to 30 characters, that describes a blurry version of an image. The backend
stores it next to the image and returns it in the API response. The frontend decodes it to a few pixels in a few
milliseconds, scales it up and shows it while the real image downloads, see
xref:web/media-optimization/blurhash-in-the-browser.adoc[BlurHash in the browser]. Compared with a tiny JPEG or a solid
colour, it is smaller than any image file, needs no extra request, and looks like the image.

The string is the image's lowest few frequencies. It is a coarse DCT (discrete cosine transform), the same idea as JPEG
but with a handful of components for the whole image instead of 8 by 8 blocks.

== Colour space

BlurHash averages colours, and averaging must be done in linear light, not in the gamma-encoded sRGB bytes. Each sRGB
byte latexmath:[b] is converted to a linear value before encoding and back after decoding.

With latexmath:[v = b / 255], the linear value is

[stem]
++++
\mathrm{sRGBToLinear}(b) = \begin{cases} v / 12.92 & v \le 0.04045 \\ \left(\dfrac{v + 0.055}{1.055}\right)^{2.4} & \text{otherwise} \end{cases}
++++

The inverse takes a linear value latexmath:[v] clamped to latexmath:[[0, 1\]], and gives a byte

[stem]
++++
\mathrm{linearToSRGB}(v) = \mathrm{round}\left(255 \cdot \begin{cases} 12.92\,v & v \le 0.0031308 \\ 1.055\,v^{1/2.4} - 0.055 & \text{otherwise} \end{cases}\right)
++++

The reference code rounds by adding 0.5 and truncating.

== Encoding

The encoder runs a DCT-like transform with latexmath:[n_x \times n_y] components, where latexmath:[1 \le n_x, n_y \le 9]. 4 by 3 is the
usual choice. For an image of width latexmath:[W] and height latexmath:[H], with latexmath:[L(x, y)] the linear value of one colour channel, each
component is computed separately for the R, G and B channels:

[stem]
++++
C_{ij} = \frac{N_{ij}}{W\,H}\sum_{x=0}^{W-1}\sum_{y=0}^{H-1}\cos\left(\frac{\pi i x}{W}\right)\cos\left(\frac{\pi j y}{H}\right) L(x,y)
++++

latexmath:[C_{00}] is the average colour, the *DC* component. The other latexmath:[n_x n_y - 1] components are the *AC* components, which
describe how the colour varies across the image. The normalisation factor latexmath:[N_{ij}] is 1 for latexmath:[(i, j) = (0, 0)] and 2 for every other component.

=== Quantisation and packing

The string is written in base 83 with this alphabet, in this order:

[source,text]
----
0123456789ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz#$%*+,-.:;=?@[]^_{|}~
----

A value is written most significant digit first, with a fixed number of digits. The fields appear in this order:

. *Size flag*, 1 character: latexmath:[(n_x - 1) + 9\,(n_y - 1)].
. *Maximum AC value*, 1 character: latexmath:[q_{max} = \mathrm{clamp}(\lfloor 166\,A_{max} - 0.5 \rfloor, 0, 82)], where latexmath:[A_{max}] is
  the largest AC value. The decoder reads it back as latexmath:[M = (q_{max} + 1) / 166]. If there are no AC components, the
  reference writes 0 and uses latexmath:[M = 1].
. *DC*, 4 characters: the 24-bit sRGB average colour, latexmath:[(R \ll 16) + (G \ll 8) + B], after converting each linear channel back
  with latexmath:[\mathrm{linearToSRGB}].
. *Each AC component*, 2 characters. Each channel is quantised to 19 levels,
  latexmath:[q = \mathrm{clamp}(\lfloor 9\,\mathrm{signPow}(c / M,\ 0.5) + 9.5 \rfloor, 0, 18)], where
  latexmath:[\mathrm{signPow}(v, e) = \mathrm{sign}(v)\,|v|^{e}], and the three channels are packed as
  latexmath:[19^2 q_R + 19\,q_G + q_B]. This fits in two base 83 digits because latexmath:[83^2 = 6889 \ge 19^3 = 6859].

The total length is latexmath:[4 + 2\,n_x n_y], which gives 28 characters for 4 by 3.

A detail worth knowing: in the TypeScript reference the maximum is taken as the plain maximum of the AC values, not of their absolute
values, and implementations differ on this detail. Both produce valid strings. Compare the output of two
implementations by decoding, not by comparing strings.

== Decoding

The decoder reads latexmath:[n_x] and latexmath:[n_y] from the size flag, latexmath:[M] from the second character, and the DC and AC values.
Each AC channel value is

[stem]
++++
c = \mathrm{signPow}\!\left(\frac{q - 9}{9},\ 2\right) \cdot M \cdot \mathrm{punch}
++++

The DC value is converted from sRGB to linear. For an output of latexmath:[w \times h] pixels, each pixel of each channel is

[stem]
++++
L(x,y)=\sum_{j=0}^{n_y-1}\sum_{i=0}^{n_x-1} C_{ij}\cos\left(\frac{\pi i x}{w}\right)\cos\left(\frac{\pi j y}{h}\right)
++++

and is converted back to sRGB with latexmath:[\mathrm{linearToSRGB}]. The output size does not have to match the original, which
is why decoding at 32 pixels and scaling up with the UI works.

*punch* is a contrast knob. In the formula, values above 1 exaggerate the AC components (more contrast) and values
below 1 soften them. The reference TypeScript decoder, however, sets `punch = punch | 1`. That bitwise OR first
truncates the value to an integer and then sets its lowest bit, so `0.5` and `1.5` become `1`, `2` becomes `3` and `4`
becomes `5`. With that decoder only odd integers (1, 3, 5, ...) take effect as given, and nothing below 1 is possible. If
you need another punch in JavaScript, scale the AC values yourself, or use an implementation that does not apply the
OR. The cost of decoding is
latexmath:[O(w\,h\,n_x\,n_y)], which is trivial at 32 by 32.

== Worked example

Take a 2 by 2 image where the left column is red latexmath:[(255, 0, 0)] and the right column is blue latexmath:[(0, 0, 255)], and
encode it with latexmath:[n_x = 2], latexmath:[n_y = 1].

. *Linear values.* latexmath:[255 \to 1] and latexmath:[0 \to 0], so the left pixels are latexmath:[(1, 0, 0)] and the right pixels are
  latexmath:[(0, 0, 1)].
. *DC, latexmath:[C_{00}].* All cosines are 1 and latexmath:[N_{00} = 1], so the DC is the average of the four pixels:
  latexmath:[(0.5, 0, 0.5)].
. *AC, latexmath:[C_{10}].* latexmath:[N_{10} = 2], and latexmath:[\cos(\pi x / 2)] is 1 for latexmath:[x = 0] and 0 for latexmath:[x = 1]. Only the left column
  contributes, with weight 2 for each of its two pixels, so the red channel is latexmath:[2 \cdot 2 \cdot 1 / 4 = 1]. Green is 0,
  and blue is zero up to floating point noise (about latexmath:[6 \times 10^{-17}]). So latexmath:[C_{10} = (1, 0, 0)].
. *Size flag.* latexmath:[(2 - 1) + 9\,(1 - 1) = 1], the character `1`.
. *Maximum AC.* latexmath:[A_{max} = 1], so latexmath:[q_{max} = \min(82, \lfloor 166 - 0.5 \rfloor) = 82], the character `+~+`, and
  latexmath:[M = 83 / 166 = 0.5].
. *DC.* latexmath:[\mathrm{linearToSRGB}(0.5) = 188], so the colour is latexmath:[(188, 0, 188)] and the value is
  latexmath:[188 \cdot 65536 + 188 = 12320956], which is `LjfL` in four base 83 digits.
. *AC.* latexmath:[c / M = (2, 0, 0)]. latexmath:[\mathrm{signPow}(2, 0.5) = 1.41], so latexmath:[\lfloor 9 \cdot 1.41 + 9.5 \rfloor = 22], which is
  clamped to 18. For zero, latexmath:[\lfloor 0 + 9.5 \rfloor = 9]. So latexmath:[q = (18, 9, 9)] and the packed value is
  latexmath:[361 \cdot 18 + 19 \cdot 9 + 9 = 6678], which is `|c`.

The result is `+1~LjfL|c+`: 8 characters, as expected from latexmath:[4 + 2 \cdot 2 \cdot 1]. Decoding it at 2 by 2 gives these pixels
in every row:

[source,text]
----
x=0: 255,0,188   x=1: 188,0,188
----

At latexmath:[x = 0] the AC term is added to the DC; at latexmath:[x = 1] the cosine is zero, so only the DC shows. The decoded image is only a rough hint of the original, which is all two components can represent. This is also what you see on real photos: very few components give a smooth blob of the dominant
colours.

== A real hash, field by field

The running example is the Moby-Dick cover with id `b81f`, a 2400 by 3600 image. Its API record carries a BlurHash made from a 64 by 96 pixel reduction (exactly 2:3) with 3 columns and 4 rows of components.
The reference TypeScript encoder returns `TIAxG?R,4pm#f8WB01t6?aN2j[t6` for those pixels. The function below unpacks the string with nothing but the rules of the previous sections:

[source,python]
----
ALPHABET = "0123456789ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz#$%*+,-.:;=?@[]^_{|}~"

def b83(chars: str) -> int:
    value = 0
    for ch in chars:
        value = value * 83 + ALPHABET.index(ch)
    return value

def linear_to_srgb(v: float) -> int:
    v = max(0.0, min(1.0, v))
    return int((12.92 * v if v <= 0.0031308 else 1.055 * v ** (1 / 2.4) - 0.055) * 255 + 0.5)

def sign_pow(v: float, e: float) -> float:
    return abs(v) ** e * (1 if v >= 0 else -1)

def fields(blurhash: str) -> None:
    size = b83(blurhash[0])
    nx, ny = size % 9 + 1, size // 9 + 1
    assert len(blurhash) == 4 + 2 * nx * ny, "length does not match the size flag"
    maximum = (b83(blurhash[1]) + 1) / 166
    dc = b83(blurhash[2:6])
    print(f"size flag {size} -> {nx} x {ny} components, {len(blurhash)} characters")
    print(f"maximum AC value M = (q + 1) / 166 = {maximum:.4f}")
    print(f"DC = {dc} -> sRGB ({dc >> 16}, {(dc >> 8) & 255}, {dc & 255})")
    for index in range(1, nx * ny):
        value = b83(blurhash[4 + 2 * index: 6 + 2 * index])
        q = (value // 361, (value // 19) % 19, value % 19)
        ac = tuple(round(sign_pow((x - 9) / 9, 2) * maximum, 4) for x in q)
        i, j = index % nx, index // nx
        print(f"AC({i},{j}) = {blurhash[4 + 2 * index: 6 + 2 * index]!r:5} -> q {q} -> {ac}")
----

Called on that string it prints:

[source,text]
----
size flag 29 -> 3 x 4 components, 28 characters
maximum AC value M = (q + 1) / 166 = 0.1145
DC = 6125722 -> sRGB (93, 120, 154)
AC(1,0) = 'R,'  -> q (6, 7, 9) -> (-0.0127, -0.0057, 0.0)
AC(2,0) = '4p'  -> q (1, 1, 3) -> (-0.0904, -0.0904, -0.0509)
AC(0,1) = 'm#'  -> q (11, 3, 18) -> (0.0057, -0.0509, 0.1145)
AC(1,1) = 'f8'  -> q (9, 8, 10) -> (0.0, -0.0014, 0.0014)
AC(2,1) = 'WB'  -> q (7, 7, 7) -> (-0.0057, -0.0057, -0.0057)
AC(0,2) = '01'  -> q (0, 0, 1) -> (-0.1145, -0.1145, -0.0904)
AC(1,2) = 't6'  -> q (12, 12, 11) -> (0.0127, 0.0127, 0.0057)
AC(2,2) = '?a'  -> q (16, 16, 15) -> (0.0692, 0.0692, 0.0509)
AC(0,3) = 'N2'  -> q (5, 5, 11) -> (-0.0226, -0.0226, 0.0057)
AC(1,3) = 'j['  -> q (10, 10, 10) -> (0.0014, 0.0014, 0.0014)
AC(2,3) = 't6'  -> q (12, 12, 11) -> (0.0127, 0.0127, 0.0057)
----

Reading it:

* The first character `T` is 29 in the alphabet, so the grid is (29 mod 9) + 1 = 3 columns by (29 div 9) + 1 = 4 rows, and 4 + 2 * 12 = 28 characters, as the length check requires.
* The DC colour (93, 120, 154) is the average of the cover, a muted blue: the sea gradient dominates the picture. This single value is what a client sees before anything else is decoded.
* Component `(0, 1)` is a vertical variation (half a cosine period over the height), and its blue value 0.1145 is the maximum M: blue changes strongly between the top and the bottom of the cover.
  Components `(2, 0)` and `(0, 2)` are the strongest negative terms. The encoder took M from the largest signed value, the positive blue of `(0, 1)`, so the larger negative red of `(0, 2)` could not be
  represented: it is at the lowest of the 19 levels (q = 0) and is stored as -M. The next section shows that its true size is about -0.1265.
* The 11 two-character AC values use only 22 of the 28 characters. The other six are the size flag, the maximum and the four DC characters. That is the whole image.

== Same pixels, different strings

The clipped `(0, 2)` component is not a bug in the hash, it is a consequence of how the maximum is chosen, and it is where implementations disagree. The same 64 by 96 pixels and the same 3 by 4 grid, encoded by four libraries:

[cols="2,3,1", options="header"]
|===
| Implementation | String | Second character

| `blurhash` 2.0.5 (TypeScript reference)
| `TIAxG?R,4pm#f8WB01t6?aN2j[t6`
| `I`

| blurhash-java 1.0.0
| `TIAxG?R,4pm#f8WB01t6?aN2j[t6`
| `I`

| `blurhash-python` 1.2.2 (wraps the C reference)
| `TKAxG?R,9Gm#f8WC0Lt6?GN1j[t6`
| `K`

| `blurhash` 1.1.5 (the other Python package)
| `TKAxG?R,9Gm#f8WC0Lt6?GN1j[t6`
| `K`
|===

The TypeScript and Java encoders agree character for character, and so do the two Python packages, but the two pairs differ in the maximum AC character (`I` is M = 0.1145, `K` is M = 0.1265). The first pair takes the largest signed AC value, so a strong
negative component is quantised against a maximum that it exceeds and is clipped: the C-based encoders' M of 0.1265 is the size of the red channel of `(0, 2)`, which the TypeScript encoder stored as -0.1145 (the same
`fields` function applied to the second string shows `(0, 2)` as `(-0.1265, -0.1, -0.0765)`, against `(-0.1145, -0.1145, -0.0904)` above). The second pair takes the largest absolute value, which leaves headroom for it. Decoded at 32 by 48 pixels, the two
pictures differ by 4.6 on a 0 to 255 scale on average (largest difference 45 in one channel), and both are about as far from the cover itself (a mean error of 37.5 against a box-reduced 32 by 48 copy of the cover) as each other. Both strings are valid and
every decoder reads either. What follows from it:

* Never compare or deduplicate images by BlurHash string across services in different languages. Compare by decoding, or store the string with the implementation that wrote it.
* Do not "fix" one side to match the other. The cost of clipping a component is below what the eye sees in a blurred placeholder.
* Pick one encoder per platform and keep it for the lifetime of the stored strings, so a backfill produces strings that match the ones already stored.

== Cost of encoding and decoding

Encoding costs time in proportion to the pixels, so encode from the reduction. In Node, the encoder took 2.3 ms for the 64 by 96 thumbnail with 3 by 4 components, and the Python wrapper took 2 ms for the same input, 300 ms for a 600 by 900 copy and 5.1 seconds for the
2400 by 3600 original, see xref:backend/media-optimization/python-image-and-video-libraries.adoc[the Python page]. Decoding costs time in proportion to the output pixels times the number of components, so decode small and let the browser scale.
The TypeScript decoder on the same string:

[cols="1,1", options="header"]
|===
| Output size | Time per decode

| 32 x 48
| 0.29 ms

| 64 x 96
| 0.71 ms

| 320 x 480
| 17 ms

| 640 x 960
| 69 ms
|===

Decoding at the size of the final image is 240 times slower than at 32 by 48 and gains nothing, since the result is blurry anyway.

== Choosing the grid

The grid should follow the aspect ratio, so the hash does not spend its few components on a direction that has no detail. A function that matches the rule used on
xref:web/media-optimization/blurhash-in-the-browser.adoc[the browser page]:

[source,python]
----
def components_for(width: int, height: int, maximum: int = 4) -> tuple[int, int]:
    ratio = width / height
    if ratio >= 1:
        return maximum, max(1, min(maximum, round(maximum / ratio)))
    return max(1, min(maximum, round(maximum * ratio))), maximum
----

It returns `(3, 4)` for the 640 by 960 and the 2400 by 3600 cover (28 characters), `(4, 2)` for a 1920 by 1080 video cover (20 characters), `(4, 4)` for a square avatar (36 characters), and `(4, 1)` and `(1, 4)` for a 1200 by 300 banner and its
transpose (12 characters each). Python's `round` rounds halves to even and JavaScript's `Math.round` rounds them up, so inputs whose product is exactly a half can differ between a Python backend and the
JavaScript function. A bigger grid helps slowly: on the cover, a 1 by 1 hash had a mean error of 44.8, 3 by 4 had 37.3, 6 by 9 had 28.0 and 9 by 9 (166 characters) 27.9, see the table on the Python page.

== Practical guidance

* *Components.* 4 by 3 is the default and gives 28 characters. Adapt it to the aspect ratio: portrait covers do well with
  3 by 4, banner images with 5 by 2. More components mean a longer string, a slower encode and a decode that
  looks closer to the image but costs more. Past 6 by 6 the benefit is small.
* *Encode from a downscaled image.* The encoder is latexmath:[O(W\,H\,n_x n_y)], so run it on a thumbnail of about 64 to 100
  pixels wide, not on a 24-megapixel original. The result is practically the same.
* *Store and return the string.* It is 20 to 30 characters. Keep it next to the image in the database and return it
  with the image in API JSON, see
  xref:backend/media-optimization/responsive-images-and-thumbnails.adoc[responsive images and thumbnails].
* *Decode small.* Decode to about 20 to 32 pixels wide and let the UI scale it up with smooth interpolation (canvas
  CSS scaling or a blurred `<img>`). Never decode to the full image size.
* *Validate.* A decoder should check that the length equals latexmath:[4 + 2 n_x n_y], as the reference does, before trusting
  user-supplied strings.
* *Cover images of videos.* Run the same encode on the extracted frame, see
  xref:backend/media-optimization/video-covers-and-thumbnails.adoc[video covers].

=== ThumbHash

https://github.com/evanw/thumbhash[ThumbHash] by Evan Wallace is a similar placeholder format. It also encodes the
alpha channel, keeps the aspect ratio of the image inside the hash, and stores colour in a different colour space (it
uses a perceptual space and gives a slightly more detailed result in about 25 bytes). Its encoded form is binary, and is
usually written as base64. Use it when you need transparency, or when the frontend library you use supports it, for
example https://docs.expo.dev/versions/latest/sdk/image/[expo-image] and
https://github.com/johannschopplich/unlazy[unlazy]. Use BlurHash when you need the widest set of implementations. Measured on the cover (a 43 by 64 reduction, because ThumbHash takes at most 100 by 100 pixels),
`thumbhash` 0.1.1 produced 21 bytes, which is the 28 characters `2aUFNQQnh3Z3F7hoiH+EF2eAdvRo` in base64: the same text length as the 3 by 4 BlurHash of the same pixels (`TJAe8iWF4:iXa#WB02t6?aN2j[t6`, also 28 characters), and
a base64 string can be stored in a `bytea` column at 21 bytes. It decoded to a 23 by 32 image, because the aspect ratio is recovered from the hash (approximately, 0.714 for a true 0.672 here) rather than being carried by the client, and
that is the practical advantage: a client needs no extra width and height to size the placeholder.
