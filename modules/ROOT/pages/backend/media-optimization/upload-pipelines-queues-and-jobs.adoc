= Upload Pipelines, Queues and Jobs
:description: The reference architecture for media processing: never transcode inside the HTTP request, upload straight to object storage with a pre-signed URL, trigger work from a storage event or API call, queue jobs, run idempotent workers with retries, backoff and dead-letter queues, track status, and notify clients; linked to the messaging, scheduling, batch, Docker and Kubernetes pages.
:keywords: upload pipeline, pre-signed URL, direct upload, queue, job, worker, idempotency, retry, backoff, dead-letter queue, status, webhook, Kubernetes Job, Spring Batch, messaging, media processing architecture

include::partial$media-optimization-backend-disclaimer.adoc[]

Baseline date: 2026-10-07. Image resizing takes tens of milliseconds to seconds, AVIF encoding takes seconds and video
transcoding takes minutes to hours. None of it can happen in the request that receives the upload. The request would
time out, hold a thread and memory for the whole duration, and make the upload fail when the work fails. The fix is the
same for every stack: accept the file, record a job, answer immediately, and process in the background.

=== Direct upload with a pre-signed URL

The client asks the API for an upload slot. The API creates a database row in the state `awaiting_upload`, signs a short-lived PUT URL for a specific key, content type and
maximum length, and returns the URL and the media id. The client then uploads straight to object storage, and the
bytes never pass through your servers. For files above a few tens of megabytes, use multipart or resumable uploads
(S3 multipart upload, Google Cloud Storage resumable upload, Azure Blob block upload). The details per cloud are in
xref:cloud/aws/s3-object-storage.adoc[S3], xref:cloud/google-cloud/cloud-storage.adoc[Cloud Storage] and
xref:cloud/azure/blob-storage.adoc[Blob Storage].

Upload to a *private* `uploads/` prefix that no CDN serves, and write results to a different prefix (or bucket). That
separation means an unprocessed or malicious file is never public.

=== Trigger: storage event or API call

* *Storage event.* The bucket publishes an event when the object is created (S3 event notifications, Cloud Storage
  Pub/Sub notifications or Eventarc, Azure Event Grid). No client cooperation is needed, so a client that crashes after
  the upload does not leave an orphan. Events are delivered at least once, so the consumer must be idempotent.
* *API call.* The client calls `+POST /media/{id}/complete+`, and the API verifies that the object exists and has the
  expected size before it enqueues the job. It is simple, easy to test and works with any storage. A client that
  never calls it leaves an orphan, so a scheduled cleanup should delete expired `awaiting_upload` rows and their
  objects, see xref:backend/scheduling/index.adoc[scheduling].

Many platforms use both: the event as the trigger, the API call as a fast path.

== Queues and jobs

== Worker design

Idempotency::
A job can be delivered twice, and a worker can crash after producing half the output. Make every step safe to repeat:
write outputs to deterministic keys (`media/<id>/w640.avif`), overwrite on retry, and set the final status last. Skip
the job when the row is already `ready` for the same recipe version. Use the job id or media id as a dedup key where the
queue supports it.

Retries and backoff::
Retry transient failures (storage timeouts, a busy encoder) with exponential backoff and jitter, and a cap on attempts.
Do not retry permanent failures (unsupported or corrupt file): mark them `failed` with a reason at once.

Dead-letter queues::
After the maximum attempts, the message moves to a dead-letter queue. Alert on its depth, keep the messages for
inspection, and provide a way to replay them after a fix.

Timeouts and resource limits::
Put a hard time limit on every FFmpeg or libvips call, and a memory and CPU limit on the container (see
xref:backend/kubernetes/resource-management.adoc[Kubernetes resource management]). A single corrupt file must not stall
a worker for hours. Size the limit from the duration of the video.

Concurrency control::
FFmpeg already uses several cores, so run one or two transcodes per worker. Image jobs can run in parallel up to the CPU
count. Scale the number of workers on queue depth (KEDA, or the queue-based autoscaling of the platform) rather than
on CPU of the web tier.

Visibility timeout::
For queues that hide a message while it is processed (SQS, Azure Service Bus), set the visibility timeout above the
longest job, or extend it with a heartbeat, so that a running job is not delivered a second time.

Separate queues::
Keep images and videos on different queues, so a backlog of long transcodes cannot delay thumbnails.

== Status and notifications

[mermaid]
....
stateDiagram-v2
    [*] --> awaiting_upload
    awaiting_upload --> uploaded: file arrived
    uploaded --> queued: job published
    queued --> processing: worker picked it up
    processing --> ready: all outputs written
    processing --> queued: transient error, retry
    processing --> failed: permanent error or retries exhausted
    awaiting_upload --> expired: never uploaded
    ready --> [*]
    failed --> [*]
....

Store the state in the database, with the failure reason, the number of attempts and, for video, a progress percentage that
the worker updates (FFmpeg prints progress with `-progress pipe:1`). The client sees the status in one of three ways:

* *Polling.* `+GET /media/{id}+` returns the status and, once `ready`, the variants and BlurHash. Simple, works
  everywhere, and fine with a backoff on the client.
* *Webhook.* The platform calls a URL registered by another system when a job finishes. Sign the payload, and retry
  deliveries.
* *Push.* Server-sent events, WebSockets, or a mobile push notification for apps, where a user waits for a video.
  See xref:apps/media-optimization/device-side-compression-and-uploads.adoc[device-side compression and uploads].

Return `202 Accepted` with a `Location` header from the endpoint that starts the work, and make the API describe the
`processing` state so that the UI can show the BlurHash or a placeholder in the meantime, see
xref:backend/media-optimization/blurhash-algorithm.adoc[BlurHash].
