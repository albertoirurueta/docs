== What Tornado is

Tornado is a Python web framework and asynchronous networking library that started life at FriendFeed. It bundles four
things that other stacks keep in separate projects: a web framework (`tornado.web`: `Application`, `RequestHandler`,
templates, cookies, XSRF protection, WebSockets), an HTTP server and client (`HTTPServer`, `AsyncHTTPClient`), a
non-blocking networking layer (`IOLoop` and `IOStream`, now thin wrappers around `asyncio`), and coroutine tools
(`tornado.gen`, `tornado.queues`, `tornado.locks`).

The defining design choice is that Tornado is *not* a WSGI framework. It brings its own HTTP server and runs every
request of a process on one thread and one event loop. A handler that waits (for a database, a remote service or a
client) does so with `await` and lets the loop serve other connections meanwhile. That makes Tornado a good fit for
workloads with many long-lived or idle connections, such as WebSockets, long polling and Server-Sent Events, and for
services that spend their time calling other services. It is a poor fit for CPU-heavy handlers and for code built on
blocking libraries, unless that work is moved off the loop.

This section is for developers who:

* know Python and want to build real-time or high-concurrency services without a second framework for the networking
  layer
* are coming from Flask, Django, FastAPI or Pyramid and want to understand what a single-threaded, single-loop server
  changes about handlers, databases, tests and deployment
* maintain Tornado 4.x or 5.x code (callbacks, `@gen.coroutine`, `IOLoop.instance()`) and need the current
  `async def` idioms and the upgrade path
* need one coherent path from a first handler to WebSockets, security, testing and a multi-process deployment behind
  nginx

== The Bookshelf Live scenario

Every example builds one small original service, _Bookshelf Live_, so the pages fit together instead of being isolated
snippets. It is the real-time companion of the Flask _Bookshelf_ and the FastAPI _Bookshelf API_, and it shows what
Tornado is for:

* a JSON API for books and reviews backed by an async driver
* a WebSocket chat room per book, and a "new reviews" feed over long polling and Server-Sent Events
* cover metadata fetched concurrently from an external service with `AsyncHTTPClient`, driven by a bounded queue of
  workers (a local fake service in tests)
* signed-cookie login, XSRF and cross-origin protection, and Google OAuth 2.0 sign-in
* tests with `AsyncHTTPTestCase`, and deployment as one process per CPU behind nginx

.Bookshelf Live: clients, nginx, Tornado processes and the services they talk to
image::tornado-architecture.svg["Diagram of Bookshelf Live. Clients such as browsers, curl, WebSocket chat, EventSource and long-poll loops reach nginx, which terminates TLS and forwards upgrade headers. nginx balances requests across Tornado processes, one per CPU, each a single thread running one asyncio event loop. A process contains a JSON API, authentication with signed cookies and XSRF, a WebSocket chat per book, a new-reviews feed over long polling and SSE, a cover fetcher built from a bounded queue and workers, and the Application and IOLoop. The processes talk to PostgreSQL through an async driver pool, to Redis for publish and subscribe fan-out, to an external metadata API, and to Google for OAuth 2.0 sign-in.",width=100%]

== Reading path

The pages are ordered so that each one builds on the previous ones. Read them in this order the first time, then use
them as a reference:

. *Foundations*: what Tornado is made of, a first running app, why blocking the event loop is the cardinal sin,
  coroutines, and the queue and lock primitives.
. *The web framework*: applications and handlers, routing, error pages, templates and UI modules, static files and
  translations.
. *Security*: signed cookies and login, XSRF and cross-origin protection, and sign-in with third-party providers.
. *HTTP clients, real-time and networking*: `AsyncHTTPClient`, WebSockets, streaming with long polling and SSE, and the
  low-level TCP layer.
. *Data, configuration and testing*: async database drivers, options and logging, and `AsyncHTTPTestCase`.
. *Production*: one process per CPU, nginx, graceful shutdown, serving WSGI apps next to Tornado handlers, and what
  changed between releases.

for quick lookup.
