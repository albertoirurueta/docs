== The persistence context: identity map + first-level cache

The persistence context is the set of entity instances one `EntityManager`/`Session` is currently managing. It
serves two roles simultaneously:

* *Identity map* -- within one persistence context, asking for the same primary key twice (by `find`, by a
  query that returns that row, by navigating an association) always returns the *same Java object instance*.
  This is what lets `equals()`-by-reference work correctly for entities loaded through the same context, and
  why xref:backend/hibernate/entities-and-identifiers.adoc[Entities and Identifiers]' equality guidance matters
  once entities cross contexts.
* *First-level cache* -- a `find(Book.class, id)` for an id already present in the context returns the cached
  instance without hitting the database at all. Always on, never configurable, and never shared between
  `EntityManager` instances -- distinct from the optional, shared xref:backend/hibernate/second-level-cache.adoc[
  second-level cache].

== The four entity states

[mermaid]
....
stateDiagram-v2
    [*] --> Transient: new Entity()
    Transient --> Managed: persist(e)
    [*] --> Managed: find(id) / getReference(id) / query result
    Managed --> Managed: setters (tracked by dirty checking)
    Managed --> Removed: remove(e)
    Removed --> Managed: persist(e) again before flush
    Removed --> [*]: flush/commit issues DELETE
    Managed --> Detached: detach(e) / clear() / close()
    Detached --> Managed: merge(e) returns a NEW managed copy
    Transient --> [*]: never persisted, garbage collected
    Detached --> [*]: garbage collected
....

* *Transient* -- a plain `new Foo()`. No database identity, unknown to any persistence context. Never
  synchronized to the database unless it becomes managed.
* *Managed (persistent)* -- associated with a context, has a database identity, every field change is tracked
  by dirty checking (see xref:backend/hibernate/flushing-and-dirty-checking.adoc[Flushing & Dirty Checking]) and
  eventually flushed as `UPDATE` SQL.
* *Detached* -- was managed; the context closed, or the entity was explicitly evicted. Still carries an
  identity, but changes to it are no longer tracked or synchronized -- it is a plain, disconnected Java object
  until reattached (via `merge`) or discarded.
* *Removed* -- scheduled for deletion. The `DELETE` is issued at the next flush, but from the application's
  side the entity is already gone: `contains()` returns `false` and `find()` returns `null` for its identifier.
  After the flush the instance has left the persistence context entirely.

== `EntityManager` operations

[cols="1,3"]
|===
| Operation | Effect

| `persist(entity)`
| Transient -> managed. Schedules an `INSERT`. With `GenerationType.IDENTITY`, the `INSERT` fires immediately
  (the id is needed right away); with `SEQUENCE`/`TABLE`, it can be deferred to flush time.

| `find(Class, id)`
| Returns the managed instance for `id`, hitting the first-level cache first, then a `SELECT` if not already
  present. Returns `null` if no row exists.

| `getReference(Class, id)`
| Returns a lazy proxy *without* querying the database -- the proxy resolves its state only when a
  non-identifier method is first called (and throws `EntityNotFoundException` then, not immediately, if the row
  turns out not to exist). Useful for setting a `@ManyToOne` by id alone, avoiding a `SELECT` that is thrown
  away anyway.

| `merge(entity)`
| See the dedicated section below -- returns a *different*, managed instance; does not attach the argument.

| `remove(entity)`
| Managed -> removed. The entity must already be managed -- `remove()` on a detached instance throws
  `IllegalArgumentException` (merge it first).

| `refresh(entity)`
| Discards the entity's in-memory state and reloads it from the database, overwriting any unflushed changes --
  the inverse of dirty checking, used when the database is known to have changed underneath the current
  transaction (e.g. after a native bulk update).

| `detach(entity)`
| Managed -> detached, for that one instance, without ending the whole persistence context.

| `clear()`
| Detaches *every* managed entity in the context at once -- more common than one-at-a-time `detach()`, notably
  in batch-processing loops (see xref:backend/hibernate/bulk-operations-and-batching.adoc[Bulk Operations &
  Batching]).
|===

== `merge()` semantics, in depth

`merge(detachedEntity)` is the operation most often used incorrectly. It does **not** attach the argument you
pass to the persistence context. Instead it:

1. Looks up (or loads) the managed entity with the same identifier.
2. Copies the *state* of the detached argument onto that managed instance.
3. Returns the managed instance -- a **different object** from the one passed in.

[source,java]
----
Book detached = someCacheOrClientPayload();  // has an id, but from a closed context
Book managed = em.merge(detached);           // NOT detached itself -- a different, managed instance
// detached is still detached and untracked; only `managed`'s changes will be persisted
----

A common bug is continuing to mutate the argument (`detached`) after calling `merge`, expecting those changes
to be tracked -- they are not; only `managed` is. If the detached entity has no id yet (was never persisted),
`merge` behaves like `persist` and creates a new row.

== Cascading and exception handling

Cascading state transitions across an association is controlled per-association by `cascade` (see
xref:backend/hibernate/associations.adoc[Associations]) -- `persist`, `merge`, and `remove` do **not**
automatically propagate to associated entities unless the association declares the matching `CascadeType`.

Exceptions specific to state mismanagement:

* `OptimisticLockException` (JPA) / `StaleObjectStateException` (native) -- a flush detected that the row's
  `@Version` (or state, for versionless optimistic locking) no longer matches what was loaded -- someone else
  committed a conflicting change first. See xref:backend/hibernate/locking.adoc[Locking].
* `LazyInitializationException` -- a lazy association or proxy was accessed after its owning persistence
  context closed; there is no session left to issue the `SELECT`. See
  xref:backend/hibernate/fetching-and-n-plus-1.adoc[Fetching & N+1] for the fetch strategies that prevent it.
* `EntityNotFoundException` -- a `getReference()` proxy was accessed but the underlying row no longer exists,
  or a non-nullable `@ManyToOne` points at a deleted row.

== The identity map, observed

The library running example again: a `Book` with a lazy `@ManyToOne Author`, persisted once and then loaded
in fresh `EntityManager` instances (Hibernate ORM 7.4 on H2, SQL printed as issued).

[source,java]
----
try (EntityManager em = emf.createEntityManager()) {
    Book b1 = em.find(Book.class, id);              // select
    Book b2 = em.find(Book.class, id);              // no SQL: first-level cache
    Book b3 = em.createQuery("select b from Book b where b.id = :id", Book.class)
                .setParameter("id", id).getSingleResult();   // a select, but the SAME object comes back
    // b1 == b2 and b1 == b3
    try (EntityManager other = emf.createEntityManager()) {
        // other.find(Book.class, id) != b1 : a different context holds a different instance
    }
}
----

The program printed `same instance: true` for the second `find`, `query result is the same instance: true` for
the query -- which *did* issue SQL, because a query always goes to the database; what the identity map decides
is which Java object represents each returned row -- and `same across contexts: false` for the second
`EntityManager`. That last line is the practical reason entity equality has to be designed with
xref:backend/hibernate/entities-and-identifiers.adoc[business keys]: the guarantee ends at the persistence
context boundary.

[mermaid]
....
flowchart TD
    A["em.find Book, id"] --> B{"id in the persistence context?"}
    B -->|"yes"| C["return the cached instance, no SQL"]
    B -->|"no"| D["select from book where id = ?"]
    D --> E{"row found?"}
    E -->|"yes"| F["hydrate, store in the context, take a snapshot, return"]
    E -->|"no"| G["return null"]
....

A query result does *not* refresh an instance that is already in the context: if another transaction has
changed the row since it was loaded, the query returns the existing, possibly stale, instance. `refresh`
(below) is the explicit remedy.

== `getReference` and proxies

`getReference` hands back a generated subclass of the entity (a `HibernateProxy`; its class name ends in
`$HibernateProxy`) that holds only the identifier:

[source,java]
----
Book ref = em.getReference(Book.class, id);
Hibernate.isInitialized(ref);        // false -- no SQL yet
ref.getTitle();                      // select issued now
Hibernate.isInitialized(ref);        // true

Book missing = em.getReference(Book.class, 9999L);   // no SQL
missing.getTitle();                  // EntityNotFoundException
----

The failure for the absent row was an `EntityNotFoundException` ("No row with the given identifier exists
for entity" followed by the entity name and id `9999`), raised at the first non-identifier call, not at `getReference`. Use `getReference`
only when the association needs the key and nothing else; for ordinary loading, `find` returns `null` for an
absent row, which is easier to handle than an exception from an unrelated line.

== `merge` in action

[source,java]
----
Book detached;
try (EntityManager em = emf.createEntityManager()) { detached = em.find(Book.class, id); }
detached.setTitle("Edited while detached");

try (EntityManager em = emf.createEntityManager()) {
    em.getTransaction().begin();
    Book managed = em.merge(detached);                 // select, then copy state onto the managed copy
    // managed != detached ; em.contains(detached) == false ; em.contains(managed) == true
    detached.setTitle("Edited after merge (lost)");    // not tracked
    em.getTransaction().commit();                      // update book set author_id=?,title=? where id=?
}
----

The program confirmed each comment: `merge returned a different instance: true, argument managed: false,
result managed: true`, one `update` was issued at commit, and a later `find` returned `Edited while detached`
-- the edit made after the merge never reached the database.

[mermaid]
....
sequenceDiagram
    participant App as Application
    participant PC as Persistence context
    participant DB as Database
    App->>PC: merge detached copy
    PC->>DB: select by identifier
    DB-->>PC: current row
    PC->>PC: copy detached state onto the managed instance
    PC-->>App: the managed instance, a different object
    App->>PC: commit
    PC->>DB: update changed columns
....

== Operations on the wrong state

The state diagram says which transitions exist; these are the errors raised for the ones that do not:

[cols="2,3"]
|===
| Call | Observed result

| `persist(detached)`
| `+EntityExistsException: Detached entity passed to persist: ...Book+` -- a detached entity already has an
  identity, so `persist` refuses it and `merge` is the right call.

| `remove(detached)`
| `IllegalArgumentException` wrapping `org.hibernate.DetachedObjectException: Given entity is not associated
  with the persistence context`.

| `remove(managed)`, then `contains` and `find`
| `contains` returned `false` and `find` returned `null` for the same identifier, although the row still
  exists until the flush -- from the application's point of view a removed entity is already gone.

| `persist(removed)` before the flush
| Allowed: `contains` is `true` again and no `DELETE` is issued -- the transition drawn in the diagram.

| `refresh(managed)` after `setTitle("unflushed")`
| The title printed afterwards was the stored `Edited while detached`: the unflushed change was discarded.

| Reading the lazy `author` of a `Book` loaded in a closed context
| `+LazyInitializationException: Could not initialize proxy [...Author#1] - no session+`.
|===

`clear()` then `contains(book)` returned `false`, confirming that `clear` detaches every instance at once.
