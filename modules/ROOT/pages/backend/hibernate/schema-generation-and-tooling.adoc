= Schema Generation and Tooling

:keywords: hibernate.hbm2ddl.auto, jakarta.persistence.schema-generation, import.sql, @Check, @ColumnDefault, @Index, @UniqueConstraint, bytecode enhancement plugin, static metamodel generation, Hibernate Tools

include::partial$ai-disclaimer.adoc[]

xref:backend/springboot/hibernate.adoc#schema-generation-vs-migrations[Hibernate (JPA & ORM)] already states the
core rule: schema generation is a development convenience, migrations own production schema. This page covers
the generation settings and mapping annotations in full, plus the build tooling around Hibernate.

== `hibernate.hbm2ddl.auto` and the `+jakarta.persistence.schema-generation.*+` settings

[cols="1,3"]
|===
| Value | Behavior

| `none`
| Hibernate never touches the schema.

| `validate`
| Compares the mappings against the existing schema at startup and fails fast if they disagree -- catches drift
  between code and a migration-tool-owned schema before the first query does.

| `update`
| Attempts to alter the existing schema to match the mappings. Never drops or renames anything (so a renamed
  column becomes an orphaned old column plus a new one), and its inference is not always correct for complex
  changes -- development convenience only.

| `create` / `create-drop`
| Drops (if present) and recreates the schema at startup / also drops it again at shutdown. For a fresh local
  database or a test run only.
|===

The portable JPA equivalent is the `+jakarta.persistence.schema-generation.*+` property family
(`jakarta.persistence.schema-generation.database.action`, `.scripts.action` to instead emit DDL to a file rather
than run it) -- functionally overlapping with `hibernate.hbm2ddl.auto` but standardized across providers; most
Hibernate-specific documentation and this section's examples use the native property.

== `import.sql` and ordered init scripts

A file named `import.sql` on the classpath (or a location set via `jakarta.persistence.sql-load-script-source`)
is executed automatically after schema generation -- handy for seeding lookup/reference data in a dev/test
database created with `create`/`create-drop`. For anything beyond a handful of seed rows, or anything that must
run in production, prefer the migration tool's own seed-data mechanism instead (see
xref:database/schema-evolution/index.adoc[Evolving the Database Model]) -- `import.sql` has no concept of
"already ran" and simply re-executes every time the schema is (re)created.

== `@Check`, `@ColumnDefault`, `@Index`, `@UniqueConstraint`

Mapping-level annotations that schema-generation tooling honors when producing DDL:

[source,java]
----
@Entity
@Table(
    name = "book",
    uniqueConstraints = @UniqueConstraint(columnNames = "isbn"),
    indexes = @Index(name = "idx_book_published_year", columnList = "published_year"))
public class Book {
    @Check(constraints = "price >= 0")
    private BigDecimal price;

    @ColumnDefault("true")
    private boolean active;
}
----

All four are DDL-generation hints only -- they influence what `create`/`update` emit, but Hibernate never
enforces `@Check`/`@UniqueConstraint` itself at runtime (a `CHECK`/`UNIQUE` violation surfaces only as a
database-level `SQLException` translated by the JDBC driver, not caught earlier by Hibernate). On a
migration-owned schema (`hibernate.hbm2ddl.auto=validate`), these annotations play no generation role at all --
the actual constraints live in the migration scripts, and only Hibernate's own runtime queries/writes are
affected.

== Gradle/Maven plugins

* *Bytecode enhancement plugin* -- rewrites compiled entity classes to support lazy loading of basic attributes
  and collections without a proxy subclass (see
  xref:backend/hibernate/fetching-and-n-plus-1.adoc[Fetching & N+1]), and dirty-checking without a snapshot
  comparison. Configured as a build-time bytecode transformation step, not a runtime dependency; for Maven the
  `org.hibernate.orm:hibernate-maven-plugin` provides an `enhance` goal (see the worked example below).
* *Static metamodel generation* -- the `hibernate-processor` annotation processor (formerly published as
  `hibernate-jpamodelgen`) generates the `Book_`-style
  metamodel classes xref:backend/hibernate/criteria-api.adoc[Criteria API] uses, as a normal
  `annotationProcessorPath`/`provided`-scope dependency, no separate plugin needed on most build setups.
* *Schema management* -- the same `hbm2ddl` machinery is available programmatically as
  `SessionFactory.getSchemaManager()` (`exportMappedObjects`, `validateMappedObjects`,
  `truncateMappedObjects`, `dropMappedObjects`) and, through the `+jakarta.persistence.schema-generation.scripts.*+`
  properties, for writing a DDL script file for review without running it against a database.

== Hibernate Tools reverse engineering

*Hibernate Tools* can generate entity classes and mappings *from* an existing database schema (reverse
engineering) -- the inverse direction from everything else on this page, useful when onboarding Hibernate onto
a database that already exists and was not designed alongside the entity model. It ships as an Ant task, a
Gradle plugin, and an Eclipse plugin; for Maven, the descriptor of `org.hibernate.orm:hibernate-maven-plugin`
7.4.15 lists, besides `enhance`, the reverse-engineering goals `generateHbm`, `hbm2dao`, `hbm2ddl`, `hbm2java`
and `transformHbm` (backed by the `hibernate-reveng` library; only `enhance` was run for this page). Output is a starting point to review and
refine by hand, not a finished mapping -- reverse-engineered associations, inheritance, and identifier
strategies rarely match what a hand-designed mapping would choose.

== Worked example: what the generator emits and how each mode reacts

The mapping used throughout is the page's `Book` with `@Table(uniqueConstraints, indexes)`, `@Check` on `price`,
`@ColumnDefault("true")` on `active`, `nullable = false, length = 20` on `isbn` and a `precision = 8, scale = 2`
price. Hibernate ORM 7.4.15 on H2.

=== The DDL for that mapping

With `hibernate.hbm2ddl.auto=create` the log shows these statements (the same text is written to a file by the
`scripts` action below):

[source,sql]
----
create sequence book_seq start with 1 increment by 50;
create table book (active boolean default true not null, price numeric(8,2) check ((price >= 0)),
    published_year integer not null, id bigint not null, isbn varchar(20) not null, title varchar(255),
    primary key (id), unique (isbn));
create index idx_book_published_year on book (published_year);
----

Every annotation turned into DDL as described: the column-level `check`, `default true`, `not null` from
`nullable = false`, `varchar(20)` from `length`, `numeric(8,2)` from precision and scale, the `unique` constraint
and the named index. The primitive `int` and `boolean` fields became `not null`; use wrapper types where null is
meaningful.

=== Writing the script instead of running it

[source,java]
----
Configuration cfg = new Configuration().addAnnotatedClass(Book.class)
    .setProperty("hibernate.hbm2ddl.auto", "none")
    .setProperty("jakarta.persistence.schema-generation.scripts.action", "create")
    .setProperty("jakarta.persistence.schema-generation.scripts.create-target", "target/create-book.sql");
cfg.buildSessionFactory().close();   // the file now holds the three statements above
----

The file is appended to if it already exists, so delete it before regenerating in a build.

=== `validate` and `update`, side by side

* `validate` against an empty database failed the startup with
  `SchemaManagementException: Schema validation: missing table [book]`. Against a table that existed but had no
  sequence it failed with `Schema validation: missing sequence [book_seq]`: validation covers sequences, not
  only tables.
* `update` against an existing `book` table that had a column `name` where the mapping says `title` ran
  `alter table if exists book add column title varchar(255)`, created the index, added the unique constraint and
  created the sequence. The column list afterwards was `ID, ISBN, NAME, PUBLISHED_YEAR, PRICE, ACTIVE, TITLE`:
  the old `name` column was left in place and the renamed attribute got a new column, exactly the orphaned
  column the table above warns about.

=== The `SchemaManager` API

`SessionFactory.getSchemaManager()` exposes the same operations programmatically, which is useful in tests:

[source,java]
----
SchemaManager schema = sessionFactory.getSchemaManager();
schema.exportMappedObjects(true);     // drop then create the mapped tables and sequences
schema.validateMappedObjects();       // throws on drift
schema.truncateMappedObjects();       // empty every mapped table, keep the structure
----

A row inserted before `truncateMappedObjects` was gone afterwards (count 1, then 0), with the tables still in
place.

=== Constraints are enforced by the database

Inserting a book with `price = -1.00` through a native statement failed with a `ConstraintViolationException`
caused by H2's check-constraint violation (error code 23513): Hibernate generated the constraint but did
nothing at runtime to prevent the write. Bean Validation (see
xref:backend/hibernate/validation-with-hibernate-validator.adoc[Validation with Hibernate Validator]) is the layer
that rejects bad values before they reach the database; `@Check` remains the last line of defense.

=== Seeding with a load script

Pointing `jakarta.persistence.sql-load-script-source` at a SQL file with
`+insert into book (id, isbn, title, published_year, price, active) values (100, 'seed-1', 'Seeded', 2001, 9.99, true);+`
and creating the schema with `create` left one row, `[Seeded]`, after startup. The script runs after the schema
is created and again on every `create`, which is why it stays a development and test tool.

=== Build-time enhancement with Maven

`org.hibernate.orm:hibernate-maven-plugin` 7.4.15 was bound to the `compile` phase with its `enhance` goal and
lazy initialization and dirty tracking enabled (the run also enabled association management, see the end of
this section):

[source,xml]
----
<plugin>
  <groupId>org.hibernate.orm</groupId>
  <artifactId>hibernate-maven-plugin</artifactId>
  <version>${hibernate.version}</version>
  <executions>
    <execution>
      <phase>compile</phase>
      <goals><goal>enhance</goal></goals>
      <configuration>
        <enableLazyInitialization>true</enableLazyInitialization>
        <enableDirtyTracking>true</enableDirtyTracking>
      </configuration>
    </execution>
  </executions>
</plugin>
----

With an `Article` entity declaring `@Basic(fetch = FetchType.LAZY) @Lob String body`, `find` ran
`select a1_0.id,a1_0.title from article a1_0 where a1_0.id=?`, reported
`Hibernate.isPropertyInitialized(article, "body")` as `false`, and the first `getBody()` issued a second
statement, `select a1_0.body from article a1_0 where a1_0.id=?`. Without enhancement the `body` column is
selected with the entity and the lazy hint is ignored. The association-management option logged
`HHH90000029` stating that it is deprecated and will be removed, so leave it off unless an existing code base
relies on it.
