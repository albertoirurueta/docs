= Criteria API
:description: The JPA Criteria API with Hibernate -- CriteriaBuilder/CriteriaQuery/Root, the static metamodel, joins and fetch joins, predicates, SelectionSpecification/MutationSpecification, and composing queries from runtime conditions.
:keywords: Criteria API, CriteriaBuilder, CriteriaQuery, Root, JPA static metamodel, metamodel annotation processor, SelectionSpecification, MutationSpecification, HibernateCriteriaBuilder

include::partial$ai-disclaimer.adoc[]

Where xref:backend/hibernate/hql-jpql.adoc[HQL/JPQL] queries are strings, the *Criteria API* builds a query as
a tree of typed Java objects -- verbose, but type-checked at compile time and naturally suited to a query whose
shape depends on runtime conditions.

== `CriteriaBuilder`, `CriteriaQuery`, `Root`

[source,java]
----
CriteriaBuilder cb = em.getCriteriaBuilder();
CriteriaQuery<Book> cq = cb.createQuery(Book.class);
Root<Book> root = cq.from(Book.class);

cq.select(root)
  .where(cb.equal(root.get("title"), "Effective Java"));

List<Book> results = em.createQuery(cq).getResultList();
----

`CriteriaBuilder` is the factory for predicates, expressions, and the query object itself; `CriteriaQuery<T>` is
the query being built; `Root<T>` is the query's `FROM` entity, the starting point for navigating attributes and
joins.

== The static metamodel

`root.get("title")` above is a string, losing the compile-time safety the Criteria API is otherwise known for.
The *JPA static metamodel* -- generated at compile time by an annotation processor
(`hibernate-jpamodelgen`) from each `@Entity` -- provides typed attribute references instead:

[source,xml]
----
<dependency>
    <groupId>org.hibernate.orm</groupId>
    <artifactId>hibernate-jpamodelgen</artifactId>
    <scope>provided</scope>
</dependency>
----

[source,java]
----
// generated: Book_.title, Book_.author (in package com.example, class Book_)
cq.where(cb.equal(root.get(Book_.title), "Effective Java"));
----

The generated `Book_` class mirrors ``Book``'s attributes as typed `SingularAttribute`/`ListAttribute`/...
fields, so `root.get(Book_.title)` is checked against ``Book``'s actual `title` type at compile time, and a
renamed/removed field breaks the build immediately instead of failing at runtime with a string typo.

== Joins and fetch joins

[source,java]
----
Root<Book> root = cq.from(Book.class);
Join<Book, Author> authorJoin = root.join(Book_.author); // INNER JOIN by default
authorJoin = root.join(Book_.author, JoinType.LEFT);

cq.select(root).where(cb.equal(authorJoin.get(Author_.name), "King"));

// fetch join -- see fetching-and-n-plus-1.adoc
root.fetch(Book_.author, JoinType.LEFT);
----

`join()` and `fetch()` are separate calls -- `fetch()` controls whether the association is eagerly loaded in this
query's result, `join()` controls whether it can be referenced in `WHERE`/`ORDER BY`. Calling both for the same
association is allowed but produces **two** SQL joins (one for the fetch, one for the filter): the run printed
`+join author a1_0 ... join author a2_0 ...+` for that shape. To filter on a fetched association, use the object
returned by `fetch()` as a join -- in Hibernate it is a `Join` and can be cast:

[source,java]
----
@SuppressWarnings("unchecked")
Join<Book, Author> author = (Join<Book, Author>) root.fetch(Book_.author);
cq.select(root).where(cb.equal(author.get(Author_.name), "Author 2"));
// one join: select b1_0.id,a1_0.id,a1_0.name,... from book b1_0 join author a1_0 on a1_0.id=b1_0.author_id where a1_0.name=?
----

== Parameters and predicates

[source,java]
----
ParameterExpression<String> namePar = cb.parameter(String.class, "name");
cq.where(cb.equal(authorJoin.get(Author_.name), namePar));

TypedQuery<Book> query = em.createQuery(cq);
query.setParameter("name", "King");
----

Predicate combinators: `+cb.and(...)+`, `+cb.or(...)+`, `+cb.not(...)+`, plus the same comparison/`LIKE`/`BETWEEN`/
`IN` predicates JPQL exposes, built as method calls on `CriteriaBuilder` rather than parsed from a string.

== `SelectionSpecification`/`MutationSpecification`

Hibernate-specific APIs (in `org.hibernate.query.specification`, not part of Jakarta Persistence) for building a
query *programmatically from a base query*, rather than from scratch -- particularly convenient for composing
optional filters. `restrict` takes a `Restriction` built from the static metamodel; for anything a `Restriction`
cannot express, `augment` hands over the underlying `CriteriaQuery` and `Root`:

[source,java]
----
SelectionSpecification<Book> spec = SelectionSpecification.create(Book.class)
        .restrict(Restriction.equal(Book_.outOfPrint, false))
        .sort(Order.asc(Book_.publishedYear));

if (minYear != null) {
    spec = spec.restrict(Restriction.greaterThanOrEqual(Book_.publishedYear, minYear));
}

List<Book> books = spec.createQuery(session).getResultList();   // also accepts an EntityManager or StatelessSession
----

`MutationSpecification` is the equivalent for bulk `UPDATE`/`DELETE` statements (see
xref:backend/hibernate/bulk-operations-and-batching.adoc[Bulk Operations & Batching]), composed the same way.
Hibernate's own `HibernateCriteriaBuilder` (obtained via `session.getCriteriaBuilder()`) extends the standard
`CriteriaBuilder` with HQL-only capabilities not exposed by the portable JPA interface -- insert-select
criteria queries, additional function support, and criteria-based bulk mutation queries predating
`MutationSpecification`.

== Composing a query from runtime conditions

The Criteria API's main practical advantage over string-based HQL/JPQL is exactly this: building up a `WHERE`
clause whose shape depends on which filters the caller actually supplied, without string concatenation:

[source,java]
----
public List<Book> search(String titleContains, Integer minYear, String authorName) {
    CriteriaBuilder cb = em.getCriteriaBuilder();
    CriteriaQuery<Book> cq = cb.createQuery(Book.class);
    Root<Book> root = cq.from(Book.class);

    List<Predicate> predicates = new ArrayList<>();
    if (titleContains != null) {
        predicates.add(cb.like(root.get(Book_.title), "%" + titleContains + "%"));
    }
    if (minYear != null) {
        predicates.add(cb.ge(root.get(Book_.publishedYear), minYear));
    }
    if (authorName != null) {
        predicates.add(cb.equal(root.join(Book_.author).get(Author_.name), authorName));
    }

    cq.select(root).where(predicates.toArray(new Predicate[0]));
    return em.createQuery(cq).getResultList();
}
----

Compare with xref:backend/springboot/spring-data-jpa.adoc#specifications-and-querydsl-for-dynamic-queries[Spring
Data JPA's Specifications], which wrap this exact pattern behind `JpaSpecificationExecutor` so a repository
method can accept a composable `Specification<T>` instead of building `CriteriaQuery` by hand.

== Worked example: the criteria tree and what it produces

A `CriteriaQuery` is a tree of nodes -- one `Root` per `FROM` entity, `Join` and `Fetch` children, a predicate
tree for `WHERE`, expressions for the selection and ordering -- that Hibernate converts to the same semantic
query model HQL strings are parsed into. The two front ends therefore share the SQL generation stage and give
the same statements for the same logical query:

[mermaid]
....
flowchart TB
    CB["CriteriaBuilder"] --> CQ["CriteriaQuery"]
    CQ --> R["Root of Book"]
    R --> J["Join to Author"]
    CQ --> W["Predicate tree"]
    CQ --> S["Selection:<br/>entity, scalars or construct"]
    CQ --> O["Order list"]
    CQ --> SQM["SQM, shared with HQL"]
    W --> SQM
    S --> SQM
    O --> SQM
    SQM --> SQL["SQL AST and SQL"]
....

The metamodel classes used below (`Book_`, `Author_`) are generated by `hibernate-processor` (the current name of
the artifact formerly published as `hibernate-jpamodelgen`; the examples were compiled with it as an
annotation-processor path on version 7.4.15):

[source,xml]
----
<plugin>
  <groupId>org.apache.maven.plugins</groupId>
  <artifactId>maven-compiler-plugin</artifactId>
  <configuration>
    <annotationProcessorPaths>
      <path>
        <groupId>org.hibernate.orm</groupId>
        <artifactId>hibernate-processor</artifactId>
        <version>${hibernate.version}</version>
      </path>
    </annotationProcessorPaths>
  </configuration>
</plugin>
----

=== Dynamic search, measured

With the `search(titleContains, minYear, authorName)` method shown above, calling it with all arguments `null`
returned all 36 books from `+select ... from book b1_0 order by b1_0.id+` -- no `WHERE` at all, because
`where(new Predicate[0])` adds no restriction. Calling it with `("Book 1", 1990, "Author 1")` added the join and
all three predicates in one statement:

[source,sql]
----
select b1_0.id,... from book b1_0
  join author a1_0 on a1_0.id=b1_0.author_id
  where b1_0.title like ? escape '' and b1_0.published_year>=? and a1_0.name=?
  order by b1_0.id
----

The author join is only created when `authorName` is supplied, which is the property string-built HQL needs
extra care to reproduce.

=== Constructor results, grouping and subqueries

`cb.construct` builds a DTO from expressions, so grouping queries stay typed. For authors with at least three
books the run returned `AuthorStat[name=Author 1, books=3, avgPrice=20.0]` and its neighbours:

[source,java]
----
record AuthorStat(String name, Long books, Double avgPrice) {}

CriteriaQuery<AuthorStat> cq = cb.createQuery(AuthorStat.class);
Root<Book> book = cq.from(Book.class);
Join<Book, Author> author = book.join(Book_.author);
cq.select(cb.construct(AuthorStat.class,
        author.get(Author_.name), cb.count(book), cb.avg(book.get(Book_.price))))
  .groupBy(author.get(Author_.name))
  .having(cb.ge(cb.count(book), 3L))
  .orderBy(cb.asc(author.get(Author_.name)));
----

A correlated or uncorrelated subquery is built from the outer query:

[source,java]
----
CriteriaQuery<Long> cq = cb.createQuery(Long.class);
Root<Book> outer = cq.from(Book.class);
Subquery<Double> average = cq.subquery(Double.class);
Root<Book> inner = average.from(Book.class);
average.select(cb.avg(inner.get(Book_.price)));
cq.select(cb.count(outer)).where(cb.gt(outer.get(Book_.price), average));
// select count(b1_0.id) from book b1_0 where b1_0.price>(select avg(b2_0.price) from book b2_0)
----

=== Specifications: restrictions, sorting, fetch, count and mutation

The specification API composes the same ingredients without creating the tree by hand. Each call below was run
against the same data; the SQL quoted is the statement Hibernate printed:

[source,java]
----
SelectionSpecification<Book> spec = SelectionSpecification.create(Book.class)
        .restrict(Restriction.equal(Book_.outOfPrint, false))
        .sort(Order.asc(Book_.publishedYear))
        .restrict(Restriction.greaterThanOrEqual(Book_.publishedYear, 2000))
        .restrict(Restriction.contains(Book_.title, "Book 1"));
spec.createQuery(session).getResultList();
// where b1_0.out_of_print=? and b1_0.published_year>=? and b1_0.title like ? escape '\'
// order by b1_0.published_year

SelectionSpecification.create(Book.class)
        .fetch(Path.from(Book.class).to(Book_.author))          // adds: left join author a1_0 ...
        .createQuery(session).getResultList();

SelectionSpecification.create(Book.class)
        .restrict(Restriction.lessThan(Book_.price, new BigDecimal("20")))
        .createCountProjection().createQuery(session).getSingleResult();   // select count(b1_0.id) ... where price<?

MutationSpecification.create(Review.class, "delete from Review")
        .restrict(Restriction.equal(Review_.rating, 3))
        .createQuery(session).executeUpdate();                  // delete from review r1_0 where r1_0.rating=?
----

Two details are easy to miss. `Restriction.contains` escapes `%` and `_` in the search text (note the
`+escape '\'+` in the SQL) while the `pass:c[cb.like(..., "%" + text + "%")]` used in the hand-built search above does not,
so a user typing `50%` matches differently in the two. And `+fetch(...)+` through the specification API produces a
`left join`, where a hand-written `JOIN FETCH` in HQL is an inner join unless written `LEFT JOIN FETCH`.

=== `CriteriaUpdate` and `CriteriaDelete`

The standard bulk interfaces work through `createMutationQuery` on a `Session` or `EntityManager`:

[source,java]
----
CriteriaUpdate<Book> update = cb.createCriteriaUpdate(Book.class);
Root<Book> root = update.from(Book.class);
update.set(root.get(Book_.outOfPrint), true).where(cb.lt(root.get(Book_.publishedYear), 1985));
int updated = session.createMutationQuery(update).executeUpdate();
// update book b1_0 set out_of_print=? where b1_0.published_year<?
----
