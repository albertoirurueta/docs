xref:backend/hibernate/integration-testing.adoc[Integration Testing with Hibernate] covers testing Hibernate ORM
itself -- bootstrapping a test `SessionFactory`, in-memory databases, and Testcontainers for the *database*.
This page covers the analogous ground for *Hibernate Search*: mapping annotations, analyzers, queries, faceting
and projections all deserve their own tests, independent of whether the underlying entities are also
database-tested. The Docker side of the Elasticsearch/OpenSearch containers used below is covered in
xref:backend/docker/testcontainers-fundamentals.adoc[Testcontainers Fundamentals].

== The Lucene backend's in-memory directory -- the H2 equivalent for search

xref:backend/hibernate/hibernate-search-backends.adoc[Hibernate Search Backends] covers the Lucene backend's
production limitation (it does not scale across application instances). For a test suite, that same embedded
Lucene backend is exactly the right tool -- and setting `hibernate.search.backend.directory.type=local-heap`
keeps the index entirely in the JVM heap, with no filesystem directory left behind between test runs, the same
role H2 plays for the database side:

[source,yaml]
----
hibernate:
  search:
    backend:
      directory:
        type: local-heap    # index lives in the JVM heap; gone when the JVM exits -- no cleanup needed
----

As with H2 (xref:backend/hibernate/integration-testing.adoc[Integration Testing with Hibernate]'s own
"in-memory databases" caveat), this is a fast smoke test of mapping and query *shape*, not a guarantee of
production parity -- the Lucene backend's own analysis chain and query execution differ in some respects from
running the same mapping against a real Elasticsearch/OpenSearch cluster (see
xref:backend/hibernate/hibernate-search-backends.adoc[Hibernate Search Backends] for how the two backends
differ). Treat Lucene-backed tests as the fast, default layer, and reach for Testcontainers (below) for the
smaller set of tests that must prove behavior against the actual production backend.

== Testing custom analyzers

xref:backend/hibernate/hibernate-search-analyzers.adoc[Hibernate Search Analyzers] shows defining a
language-specific stemming analyzer and an n-gram-based autocomplete analyzer. The `SearchSession` API has no "show me the tokens" call, so an analyzer can be tested in two ways.
The *behavioral* way, shown first, indexes a small, targeted set of documents built specifically to exercise the
analyzer's behavior, then asserts on which queries do and do not match (the Lucene backend also lets a test read the
token stream directly; see the section on token-level assertions below):

[source,java]
----
@Test
void englishStemmingAnalyzer_matchesAcrossInflections() {
    SearchSession searchSession = Search.session(entityManager);

    entityManager.getTransaction().begin();
    entityManager.persist(new Book("Effective Java", "Running a JVM smoothly", "en"));
    entityManager.getTransaction().commit();

    List<Book> hits = searchSession.search(Book.class)
            .where(f -> f.match().field("description").matching("runs"))   // stemmed query term
            .fetchHits(20);

    assertThat(hits).extracting(Book::getTitle).containsExactly("Effective Java");  // matched via "run" stem
}

@Test
void autocompleteAnalyzer_matchesPartialPrefix() {
    // same shape: index a document through the "autocomplete" analyzer's field,
    // then assert a partial query term ("hiber") matches "Hibernate" but "xyz" does not
}
----

This treats the analyzer as a black box exercised through the same `SearchSession` API application code uses --
the right level for asserting that a user-visible search keeps working.

== Testing queries, faceting, and projections

The same in-memory-backed `SearchSession` verifies the query DSL, aggregation, and projection behavior covered
on xref:backend/hibernate/hibernate-search-fundamentals.adoc[Hibernate Search Fundamentals]:

[source,java]
----
@Test
void termsAggregation_countsHitsPerGenre() {
    seedBooks();   // persists a handful of Book entities across a few genre values

    AggregationKey<Map<String, Long>> countsByGenre = AggregationKey.of("countsByGenre");

    SearchResult<Book> result = searchSession.search(Book.class)
            .where(f -> f.matchAll())
            .aggregation(countsByGenre, f -> f.terms().field("genre", String.class))
            .fetch(20);

    assertThat(result.aggregation(countsByGenre))
            .containsEntry("Fiction", 2L)
            .containsEntry("Non-Fiction", 1L);
}

@Test
void idProjection_returnsOnlyMatchingIdentifiers() {
    seedBooks();

    List<Long> ids = searchSession.search(Book.class)
            .select(f -> f.id(Long.class))
            .where(f -> f.match().field("title").matching("persistence"))
            .fetchHits(20);

    assertThat(ids).containsExactly(persistenceBookId);
}
----

Because indexing runs synchronously by default against the Lucene backend in a single-threaded test (see
xref:backend/hibernate/hibernate-search-backends.adoc[Hibernate Search Backends]'s "Sync vs. async index
writes"), a search immediately after `persist`/commit sees the just-indexed documents without needing to poll or
sleep -- a real convenience for tests that would otherwise need to wait for asynchronous indexing to settle.

== A complete Lucene-backed test fixture

The fixture below is what the tests on this page share. It was run with Hibernate ORM 7.4.15.Final, Hibernate Search 8.4.1.Final (Lucene backend, `local-heap`), H2 2.4.240 and JUnit 5. Each test starts from an empty database *and* an empty index, because the two stores do not roll back together:

[source,java]
----
class SearchFundamentalsTest {
    static EntityManagerFactory emf;
    EntityManager em;
    SearchSession searchSession;

    @BeforeAll static void boot() { emf = Persistence.createEntityManagerFactory("test"); }
    @AfterAll  static void stop() { emf.close(); }

    @BeforeEach
    void seed() {
        em = emf.createEntityManager();
        em.getTransaction().begin();
        em.createQuery("delete from Book").executeUpdate();
        em.createQuery("delete from Author").executeUpdate();
        em.getTransaction().commit();
        em.clear();

        searchSession = Search.session(em);
        searchSession.workspace().purge();          // bulk deletes bypass indexing, so empty the index too

        Fixtures.seed(em);                          // persists 3 authors and 3 books, then clears the context
    }

    @AfterEach void close() { em.close(); }
}
----

Three details earn their place. The bulk `delete` statements run through HQL, so Hibernate Search never sees them and `workspace().purge()` is what empties the index. `Fixtures.seed` ends with `em.clear()`, so a later rename of an `Author` loads fresh entities whose `books` collection reflects the database, which keeps `@IndexedEmbedded` reindexing tests honest (see the stale-collection scenario on xref:backend/hibernate/hibernate-search-fundamentals.adoc[Hibernate Search Fundamentals]). And the persistence unit sets `hibernate.search.backend.type=lucene`, `hibernate.search.backend.directory.type=local-heap` and `hibernate.search.backend.analysis.configurer`, the same configurer class production uses, so the analyzers under test are the real ones.

== Token-level assertions with the Lucene backend

When a test should pin the analysis chain itself (a stemmer upgrade, a changed `minGramSize`), read the configured Lucene `Analyzer` from the running mapping and assert on its token stream. This needs no entity and no index:

[source,java]
----
LuceneBackend backend = Search.mapping(emf).backend().unwrap(LuceneBackend.class);

List<String> tokens(String analyzerName, String text) throws IOException {
    List<String> out = new ArrayList<>();
    try (TokenStream ts = backend.analyzer(analyzerName).orElseThrow().tokenStream("f", text)) {
        CharTermAttribute term = ts.addAttribute(CharTermAttribute.class);
        ts.reset();
        while (ts.incrementToken()) out.add(term.toString());
        ts.end();
    }
    return out;
}

assertThat(tokens("english", "Running Hibernate Persistence")).containsExactly("run", "hibern", "persist");
assertThat(tokens("autocomplete_search", "Running Hibernate Persistence"))
        .containsExactly("running", "hibernate", "persistence");
----

Those exact token lists are what the analyzers from xref:backend/hibernate/hibernate-search-analyzers.adoc[Hibernate Search Analyzers] printed when run. The `autocomplete_indexing` chain makes the strongest regression test, because a changed gram size silently changes which partial queries work: for the three titles _Hibernate Recipes_, _Hibernating Bears_ and _Hidden Figures_, the queries `hiber` and `hib` matched the first two and `hi` matched none. The Elasticsearch backend has no such in-process accessor, so on that backend the behavioral style above is the only option (or a call to the index's `_analyze` endpoint).

== Testing the failure modes, not only the happy path

Search tests that only assert hits miss the errors that bite in production. Two cheap tests worth keeping:

* *A mapping capability that the query needs.* A sort on a field without `sortable = Sortable.YES`, or a terms aggregation on a field without `aggregable = Aggregable.YES`, fails with `HSEARCH000604` when the query runs, not at startup. A test that executes each query shape used by the application once catches a mapping change that silently removed a capability.
* *Index drift after a bulk statement.* After `+delete from Book where genre = 'Persistence'+`, the table held one book while a `matchAll()` search still returned three. A test that documents this, and then proves that `massIndexer(Book.class).purgeAllOnStart(true).startAndWait()` restores agreement (the index held one document afterwards), pins down the repair procedure that an operations runbook will rely on.

== Testcontainers with a real Elasticsearch/OpenSearch image

When a test must prove behavior against the actual production backend -- an Elasticsearch-specific relevance
tuning detail (see xref:backend/springboot/elasticsearch.adoc[Elasticsearch] for the query DSL and relevance
concepts this backend runs), a coordination-strategy interaction, or simply a pre-release confidence check --
https://java.testcontainers.org/modules/elasticsearch/[Testcontainers' Elasticsearch module] starts a real
cluster as a disposable Docker container, the same pattern
xref:backend/hibernate/integration-testing.adoc[Integration Testing with Hibernate] uses for the database:

[source,java]
----
@Testcontainers
class BookSearchElasticsearchIT {

    @Container
    static ElasticsearchContainer elasticsearch =
            new ElasticsearchContainer("docker.elastic.co/elasticsearch/elasticsearch:9.0.0")
                    .withEnv("xpack.security.enabled", "false");   // no TLS or password in the test cluster

    static EntityManagerFactory emf;

    @BeforeAll
    static void bootstrap() {
        emf = Persistence.createEntityManagerFactory("test", Map.of(
                "hibernate.search.backend.type", "elasticsearch",
                "hibernate.search.backend.hosts", elasticsearch.getHttpHostAddress(),
                "hibernate.search.backend.protocol", "http",
                "hibernate.search.indexing.plan.synchronization.strategy", "sync",
                "hibernate.search.schema_management.strategy", "drop-and-create-and-drop"));
    }

    // test methods as above, unchanged -- the SearchSession/query DSL calls are backend-agnostic
}
----

The `sync` synchronization strategy in that bootstrap is not optional for tests. With the default (`write-sync`), twenty
`matchAll()` searches issued right after a commit all missed the freshly stored books on Elasticsearch 9, while
with `sync` none did (details on xref:backend/hibernate/hibernate-search-backends.adoc[Hibernate Search Backends]).
The class names are those of Testcontainers 2 (`org.testcontainers.elasticsearch.ElasticsearchContainer` from the
`testcontainers-elasticsearch` artifact, JUnit support from `testcontainers-junit-jupiter`); Testcontainers 1.x ships
the same container as the `elasticsearch` artifact.

`elasticsearch.getHttpHostAddress()` reads the running container's actual `host:port`, the same role
`postgres.getJdbcUrl()` plays for a database container on
xref:backend/hibernate/integration-testing.adoc[Integration Testing with Hibernate]. Test methods written
against the query DSL, aggregations, and projections do not need to change between the Lucene-backed and
Elasticsearch-backed variants -- only the `EntityManagerFactory` bootstrap properties differ -- so it is common
to run the fast Lucene-backed suite on every build and the Elasticsearch-backed variant on a smaller, slower CI
job or before a release.
