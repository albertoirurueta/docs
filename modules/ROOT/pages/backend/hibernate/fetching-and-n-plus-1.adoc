xref:backend/springboot/hibernate.adoc[Hibernate (JPA & ORM)] already introduces the N+1 problem briefly. This
page goes deeper on every fetch strategy available to prevent it and the trade-offs between them.

== Lazy vs. eager, and the JPA defaults

* `@ManyToOne` / `@OneToOne` default to `FetchType.EAGER`.
* `@OneToMany` / `@ManyToMany` default to `FetchType.LAZY`.

The JPA-mandated defaults are a poor fit for most applications: an eager `@ManyToOne` fetches the associated
row on *every* load of the owning entity whether or not that use case needs it, which itself is a source of
unnecessary joins and, transitively, its own N+1 risk when the eagerly-loaded association has further lazy
associations. The common house rule: **default every association to `FetchType.LAZY`** (explicitly, on
`@ManyToOne`/`@OneToOne` too) and load eagerly only per-query, using one of the mechanisms below, for the
specific associations a given use case actually needs.

== Proxies, bytecode enhancement, and `LazyInitializationException`

A lazy `@ManyToOne`/`@OneToOne` is represented by a runtime-generated proxy subclass that holds only the
identifier until a non-identifier method is first called, at which point it triggers a `SELECT` -- this needs
the entity class to be non-`final` with a non-private no-arg constructor. Lazy *basic* attributes and lazy
*collections* work differently: they need build-time bytecode enhancement (the Hibernate Gradle/Maven
enhancement plugin) to intercept field access, since there is no proxy object to substitute for a `String` or a
`List`.

`LazyInitializationException` fires when a lazy association/collection/attribute is accessed after its
persistence context has already closed -- there is no session left to run the `SELECT`. *Open-session-in-view*
(`spring.jpa.open-in-view=true`, Spring Boot's default) works around this by keeping the persistence context
open for the whole HTTP request, so lazy access from the view/serialization layer still succeeds -- at the cost
of holding a database connection for the request's full duration and hiding N+1 problems that surface only in
that layer. See xref:backend/springboot/hibernate.adoc#spring-boot-integration[Hibernate (JPA & ORM) -- Spring
Boot integration] for the trade-off in full; the fetch strategies below are the alternative that avoids needing
OSIV at all.

== `JOIN FETCH`

The most direct fix: ask for the association in the same query, as a real SQL join, instead of a separate
lazy-triggered `SELECT`.

[source,java]
----
List<Order> orders = em.createQuery("""
            SELECT DISTINCT o FROM Order o
            JOIN FETCH o.customer
            WHERE o.status = :status
            """, Order.class)
        .setParameter("status", OrderStatus.PENDING)
        .getResultList();
----

Since Hibernate 6, entities returned through a to-many `JOIN FETCH` are de-duplicated in the Java result list
automatically, so `DISTINCT` is no longer needed for that purpose: on ORM 7.4.15 a query of this shape over 12
stored authors, each with three books, returns 12 authors both with and without it, in one statement. If `DISTINCT` is written anyway, it is
also passed to the database (the generated statement starts with `select distinct`), which costs a sort or hash
step without changing the result. Only one to-many association can be ``JOIN FETCH``ed per query without risking a Cartesian-product
explosion (or, for two *bag*-typed to-many associations specifically, an outright
`MultipleBagFetchException` -- see xref:backend/hibernate/collections.adoc[Collections]).

== Entity graphs

An `@EntityGraph` or named fetch profile declares, independently of any specific query's JPQL, which
associations should be loaded eagerly *for this fetch only* -- reusable across several queries without
duplicating join syntax in each:

[source,java]
----
@Entity
@NamedEntityGraph(
    name = "Order.withCustomerAndLines",
    attributeNodes = {
        @NamedAttributeNode("customer"),
        @NamedAttributeNode("lines")
    })
public class Order { /* ... */ }

// ...
EntityGraph<?> graph = em.getEntityGraph("Order.withCustomerAndLines");
Order order = em.find(Order.class, id, Map.of("jakarta.persistence.fetchgraph", graph));
----

`jakarta.persistence.fetchgraph` loads exactly the named attributes eagerly and everything else per its mapped
default; `jakarta.persistence.loadgraph` loads the named attributes eagerly *in addition to* whatever is
already mapped eager, rather than instead of it.

== `@BatchSize` and subselect fetching

For associations that will be lazily initialized anyway (rather than fetch-joined up front), batching turns N
follow-up ``SELECT``s into a handful of `IN`-batched ones:

[source,java]
----
@Entity
public class Author {
    @OneToMany(mappedBy = "author")
    @BatchSize(size = 20)
    private List<Book> books;
}
----

`hibernate.default_batch_fetch_size` sets the same behavior globally instead of per-association.
`@Fetch(FetchMode.SUBSELECT)` takes a different approach: when the *owning* collection is lazily initialized for
one of several already-loaded parent entities, it re-runs the *original query that loaded the parents* as a
subselect to fetch every parent's collection in one extra query, rather than batching by id -- a good fit when
the parents were loaded by a complex query and their ids alone would not reproduce the same set.

== `@Fetch(SELECT | JOIN | SUBSELECT)`

`@Fetch` on an association picks the SQL strategy Hibernate uses when it does decide to load that lazy
association: `FetchMode.SELECT` (one `SELECT` per parent -- the N+1-prone default), `FetchMode.JOIN` (always
join-fetch it, effectively forcing eager loading regardless of the declared `FetchType`), or
`FetchMode.SUBSELECT` (as above). `@BatchSize` and `@Fetch(FetchMode.SELECT)` compose; `@Fetch(FetchMode.JOIN)`
overrides batching for that association.

== DTO projections to avoid loading entities at all

The most direct way to avoid N+1 (and the overhead of loading full managed entities) for a read-only view is to
not load entities at all -- project straight into a DTO:

[source,java]
----
public record BookSummary(Long id, String title, String authorName) {}

List<BookSummary> summaries = em.createQuery("""
            SELECT new com.example.BookSummary(b.id, b.title, a.name)
            FROM Book b JOIN b.author a
            """, BookSummary.class)
        .getResultList();
----

`+SELECT new ...+` DTO projections are covered fully in xref:backend/hibernate/hql-jpql.adoc[HQL/JPQL]; they
sidestep fetching strategy entirely since there are no lazy associations on a projection.

== The N+1 blow-up and its fix

[mermaid]
....
sequenceDiagram
    participant App
    participant DB as Database
    App->>DB: SELECT * FROM orders WHERE status = 'PENDING'  (1 query, 100 rows)
    DB-->>App: 100 Order rows
    loop for each of the 100 orders (naive lazy access)
        App->>DB: SELECT * FROM customer WHERE id = ?
        DB-->>App: 1 Customer row
    end
    Note over App,DB: 1 + 100 queries total -- the N+1 problem

    App->>DB: SELECT o.*, c.* FROM orders o JOIN customer c ON ... WHERE o.status = 'PENDING'
    Note over App,DB: JOIN FETCH -- 1 query total
    App->>DB: SELECT * FROM customer WHERE id IN (?, ?, ..., ?)
    Note over App,DB: @BatchSize alternative -- 1 (orders) + ceil(100/batchSize) queries
....

See also xref:database/diagnosing-slow-queries.adoc[] for how an N+1 fetch shows up in a slow-query log or
profiler and how to confirm it as the root cause.

== Worked example: measuring the strategies

The examples below use the section's running model -- `Author` owns many ``Book``s, and each `Book` owns many
``Review``s, with every association declared `FetchType.LAZY`. The data set is 12 authors, 3 books each and 2
reviews per book. Every number was read from `Statistics.getPrepareStatementCount()` on Hibernate ORM 7.4.15
against an in-memory H2 database, so it counts real JDBC statements, not queries as the application sees them:

[source,java]
----
Statistics stats = sessionFactory.getStatistics();
stats.clear();
try (Session session = sessionFactory.openSession()) {
    for (Author author : session.createQuery("from Author", Author.class).getResultList()) {
        author.getBooks().size();   // touches the lazy collection of every author
    }
}
System.out.println(stats.getPrepareStatementCount() + " SQL statements");
----

[cols="3,1,3"]
|===
| Strategy | Statements | Why

| Naive lazy loop
| 13
| One query for the authors, then one `SELECT` per author to initialize its `books` collection.

| `JOIN FETCH a.books`
| 1
| One join returns every author with its books; both are materialized from the same result set.

| `hibernate.default_batch_fetch_size=5`
| 4
| One query for the authors, then three `IN` queries of five author ids each (12 authors need three batches).

| `@Fetch(FetchMode.SUBSELECT)`
| 2
| The parents query is re-used as a subselect: one extra statement initializes the collections of all parents.

| Entity graph (`find` or query)
| 1
| Equivalent to a fetch join, declared outside the query text.

| DTO projection
| 1
| No managed entities, so there is nothing lazy to trigger.
|===

The batch-fetch statements show how Hibernate rewrites each lazy initialization into an `IN` list; the last
batch is padded to the same number of placeholders so the database can re-use one prepared statement:

[source,sql]
----
select a1_0.id,a1_0.name from author a1_0
select b1_0.author_id,b1_0.id,b1_0.isbn,b1_0.out_of_print,b1_0.price,b1_0.published_year,b1_0.stock,b1_0.title
  from book b1_0 where b1_0.author_id in (?,?,?,?,?)     -- repeated three times
----

The subselect variant, on a `Series` entity with `@Fetch(FetchMode.SUBSELECT)` on its `volumes` collection,
re-runs the original `WHERE` clause inside the second statement:

[source,sql]
----
select s1_0.id,s1_0.name from series s1_0 where s1_0.name like 'Series%'
select v1_0.series_id,v1_0.id,v1_0.number from volume v1_0
  where v1_0.series_id in (select s1_0.id from series s1_0 where s1_0.name like 'Series%')
----

=== The eager `@ManyToOne` default is an N+1 too

`Volume.series` is a plain `@ManyToOne`, which is `EAGER` by the JPA default. Loading four volumes of four series
with `from Volume` prepared five statements: the volume query plus one `+select ... from series where id=?+` per
distinct series. HQL does not honor the mapped eager fetch inside the query itself, so Hibernate fixes the
association up afterwards with immediate secondary selects. Declaring the association `LAZY` and fetching it
per use case is the only way to keep this predictable.

=== Entity graphs in practice

All four ways of applying a graph produced exactly one statement in the same run:

[source,java]
----
EntityGraph<Author> graph = session.createEntityGraph(Author.class);
graph.addAttributeNodes("books");

// 1. JPA hint on find (what the example above uses)
session.find(Author.class, id, Map.of("jakarta.persistence.fetchgraph", graph));
// 2. Jakarta Persistence 3.2 / Hibernate 7: pass the graph itself
session.find(graph, id);
// 3. JPA hint on a query
session.createQuery("from Author", Author.class).setHint("jakarta.persistence.fetchgraph", graph);
// 4. Hibernate selection query API
session.createSelectionQuery("from Author", Author.class).setEntityGraph(graph, GraphSemantic.FETCH);
----

An entity graph is applied as a left outer join, so authors without books are still returned -- unlike
`JOIN FETCH`, which is an inner join unless written as `LEFT JOIN FETCH`.

=== Two collections: `MultipleBagFetchException`

Fetching two `List` collections at once is rejected at query-compilation time. The run produced:

[source,text]
----
IllegalArgumentException: MultipleBagFetchException: cannot simultaneously fetch multiple bags:
  [demo.Book.reviews, demo.Author.books]
----

Switching one of the collections to a `Set` (or adding `@OrderColumn`) avoids the exception but multiplies the
result rows (books times reviews per author). The fix that keeps the row count linear is two queries in the
same persistence context: the second query's managed entities fill the collections left uninitialized by the
first one.

[source,java]
----
List<Author> authors = session.createQuery(
        "select a from Author a join fetch a.books", Author.class).getResultList();
session.createQuery(
        "select b from Book b join fetch b.reviews where b.author in :authors", Book.class)
    .setParameter("authors", authors)
    .getResultList();
// 2 statements in total; all 72 reviews are now reachable without further SQL
----

=== `LazyInitializationException`, reproduced

Reading a lazy collection after its session closed fails with a message that names the role and the key:

[source,text]
----
Cannot lazily initialize collection of role 'demo.Author.books' with key '1' (no session)
----
