== The performance checklist, distilled

* Default every association to `FetchType.LAZY`; load eagerly per-query via `JOIN FETCH`/entity graphs only for
  what a specific use case needs.
* Set `spring.jpa.open-in-view=false` (or the equivalent for a non-Spring bootstrap) and fetch exactly what a
  response needs inside the transactional service method.
* Use `SEQUENCE` (not `IDENTITY`) generation where the database supports it, to keep JDBC batching intact.
* Set `hibernate.jdbc.batch_size` and `hibernate.order_inserts`/`order_updates` for any workload doing more
  than a handful of writes per transaction.
* Project read-only views as DTOs (`SELECT new`) instead of loading full managed entities.
* Reach for `StatelessSession` or the `flush()`/`clear()` loop for large batch/ETL work.
* Cache only what is actually re-read often and rarely changes; verify with the `Statistics` API rather than
  assuming a cache region is paying for itself (see xref:backend/hibernate/second-level-cache.adoc[Second-Level
  Cache]'s query-cache pitfall).

== The `Statistics` API and `hibernate.generate_statistics`

[source,java]
----
Statistics stats = sessionFactory.getStatistics();
stats.setStatisticsEnabled(true); // also settable via hibernate.generate_statistics=true

long queries = stats.getQueryExecutionCount();
long slowest = stats.getQueryExecutionMaxTime();
String slowestQuery = stats.getQueryExecutionMaxTimeQueryString();

CacheRegionStatistics bookCache = stats.getCacheRegionStatistics("book");
double hitRatio = (double) bookCache.getHitCount()
        / (bookCache.getHitCount() + bookCache.getMissCount());
----

`Statistics` exposes per-entity, per-collection, per-query, and per-cache-region counters (load/fetch/update/
insert/delete counts, cache hit/miss/put counts, query execution counts and timings) -- the direct way to
confirm a suspected N+1 pattern, a cold cache region, or a slow query, rather than guessing from application
behavior alone.

== The slow-query log

`hibernate.log_slow_query` (a threshold in milliseconds, must be at least 1) logs, at `INFO` level on the
`org.hibernate.SQL_SLOW` logger category, any single SQL statement whose execution exceeds the threshold,
including the SQL text and its duration -- a low-overhead, always-on way to catch performance regressions in
production without enabling full statistics collection or `hibernate.show_sql`. With the property set to `1`
the run printed lines of this shape:

[source,text]
----
INFO: Slow query took 3 milliseconds [select next value for author_seq]
INFO: Slow query took 2 milliseconds [insert into book (author_id,isbn,out_of_print,price,published_year,stock,title,id) values (?,?,?,?,?,?,?,?)]
----

A value of `0` disables the log rather than logging everything. Because the logger category is `SQL_SLOW`,
the application's logging configuration must allow `INFO` for `org.hibernate.SQL_SLOW`.

== Java Flight Recorder events

The `org.hibernate.orm:hibernate-jfr` module emits JFR (Java Flight Recorder) events for key persistence
operations (session open/close, flushes, JDBC statement creation and execution, batch execution, cache gets and
puts, entity and collection events) when it is on the classpath of a JVM that is recording -- lets Hibernate-level
activity be correlated, in one recording, with the rest of the JVM's own GC/allocation/lock-contention events
already captured by JFR, without adding a separate Hibernate-specific profiling agent. The module is separate
from `hibernate-core`; without it no `+org.hibernate.orm.*+` events are recorded.

== Connection-pool tuning

Hibernate's own performance is frequently bottlenecked by the connection pool underneath it rather than
anything Hibernate itself does: a pool sized too small serializes otherwise-parallel requests waiting for a
connection; a pool sized too large can overwhelm the database's own max-connections limit. HikariCP (the
Spring Boot default) exposes `maximum-pool-size`, `minimum-idle`, `connection-timeout`, and `leak-detection-
threshold` as the settings worth tuning first; see also
xref:backend/springboot/metrics-and-observability.adoc[Metrics & Observability] for exposing pool metrics via
Micrometer/Actuator.

== Common anti-patterns

* *Open-session-in-view left on by default* -- hides N+1 problems in the serialization layer and holds a
  database connection for the whole request; see
  xref:backend/hibernate/fetching-and-n-plus-1.adoc[Fetching & N+1].
* *Eager fetching everywhere* -- loading associations that most call sites never use, on every load of the
  owning entity.
* *Entity-instead-of-DTO for read-only views* -- pays persistence-context and dirty-checking overhead for data
  that is never going to be written back.
* *`@OneToMany` with no `@BatchSize`* -- lazily-initialized collections default to one `SELECT` per parent,
  the textbook N+1 shape, unless batched.

See also xref:database/diagnosing-slow-queries.adoc[] for a vendor-neutral workflow to turn what the slow-query
log and Statistics API surface into a confirmed root cause.

== Worked example: proving an N+1 with the Statistics API

The scenario is the running model (12 authors, 3 books each, 2 reviews per book) and a service method that lists
every author with its books' titles. With `hibernate.generate_statistics=true`, ORM 7.4.15 reported this after
running the lazy version once:

[source,text]
----
statements prepared : 13
queries executed    : 1
entities loaded     : 48
collections fetched : 12
collections loaded  : 12
slowest query       : select a from Author a
Book: loads=36 fetches=0
Author.books: loads=12 fetches=12
query [select a from Author a] count=1 rows=12
----

Read the numbers together. `queries executed` counts what the *application* issued through the query API (one);
`statements prepared` counts what reached JDBC (13). The 12-statement gap is the signature of lazy loading, and
it is attributed precisely: `Author.books` was fetched 12 times, `fetches` being the lazy, on-demand loads, while
`Book` shows 36 `loads` and 0 `fetches` because the books came in as part of those collection loads. The
`logSummary()` output labels the counters `Entities fetched` and `Collections fetched` with `(minimize this)` for
exactly this reason.

Repeating the work with `select a from Author a join fetch a.books` changed the picture to `statements
prepared : 1, collections fetched: 0`. The same assertion can protect a test suite against regressions:

[source,java]
----
Statistics stats = sessionFactory.getStatistics();
stats.clear();
service.listAuthorsWithBookTitles();
assertThat(stats.getPrepareStatementCount()).isLessThanOrEqualTo(2);
----

=== Java Flight Recorder in practice

Adding `hibernate-jfr` and starting the JVM with `-XX:StartFlightRecording=filename=run.jfr,settings=profile`
recorded, for the same program, events named `+org.hibernate.orm.*+` that the standard `jfr` tool reads:

[source,bash]
----
jfr summary run.jfr                                   # event counts, including org.hibernate.orm.*
jfr print --events org.hibernate.orm.FlushEvent run.jfr
----

The summary of one run listed `JdbcPreparedStatementCreation` and `JdbcPreparedStatementExecution` (141 each),
`EntityInsertEvent` (120), `CachePut` and `CacheGet`, `FlushEvent` (3), `SessionOpen`/`SessionClosed` (3) and
`JdbcBatchExecution`, among others. A single event carries its payload; a flush event printed
`duration = 131 ms`, `numberOfEntitiesProcessed = 120`, `numberOfCollectionsProcessed = 48` and
`isAutoFlush = false`, and a statement-execution event carries the SQL text, for example
`sql = "select next value for author_seq"` with its duration.

[source,text]
----
org.hibernate.orm.FlushEvent {
  duration = 131 ms
  numberOfEntitiesProcessed = 120
  numberOfCollectionsProcessed = 48
  isAutoFlush = false
  ...
}
----

Flush events with a large `numberOfEntitiesProcessed` are the JFR-side view of the dirty-checking cost that the
`flush()`/`clear()` loop in xref:backend/hibernate/bulk-operations-and-batching.adoc[Bulk Operations and Batching]
exists to bound.
