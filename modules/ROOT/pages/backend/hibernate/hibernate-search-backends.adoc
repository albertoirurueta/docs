== Lucene backend -- embedded, per-node

The Lucene backend runs Apache Lucene directly inside the application's own JVM, writing its index to the
local filesystem of whichever node the application instance runs on. No separate service to deploy or operate
-- the simplest possible setup, and adequate for a single-instance deployment.

It does **not** scale horizontally: each application instance keeps its **own**, independently-maintained index
on its own local disk. Running three instances of the same application means three separate, drifting copies of
the index, each reflecting only the writes that particular instance's own Hibernate Search integration happened
to apply -- there is no shared, near-real-time refresh across instances, and a full reindex has to run
separately, per node. This makes the Lucene backend a poor fit the moment a deployment needs more than one
application instance for availability or load.

== Elasticsearch/OpenSearch backend -- shared, recommended for scale-out

The Elasticsearch/OpenSearch backend talks to a genuinely separate, shared search cluster over HTTP -- every
application instance indexes into, and searches, the *same* cluster. This is the recommended backend for any
multi-instance/scaled-out deployment: the index is consistent regardless of which application instance served
a given write or read, and the search cluster scales independently of the application tier (add Elasticsearch
nodes without touching application instance count, or vice versa).

[source,xml]
----
<dependency>
    <groupId>org.hibernate.search</groupId>
    <artifactId>hibernate-search-backend-elasticsearch</artifactId>
</dependency>
----

[source,yaml]
----
hibernate:
  search:
    backend:
      hosts: elasticsearch:9200
      version: "9"
----

The sharding/replica configuration on the Elasticsearch side (see
xref:backend/springboot/elasticsearch.adoc[Elasticsearch]'s own shard/replica coverage) applies to Hibernate
Search's indexes exactly as it would to any other Elasticsearch index -- Hibernate Search creates and manages
the index's mapping, but the cluster-level distribution characteristics are ordinary Elasticsearch concerns.

== Coordination strategies for multi-node automatic indexing

Even with a shared Elasticsearch backend, something has to decide *when* an application instance's entity
change gets pushed to the index, and coordinate that across instances without duplicate or lost updates:

[cols="1,3"]
|===
| Strategy | Behavior

| `none`
| Each application instance indexes its own changes directly and synchronously (or asynchronously per the sync
  strategy below) as they happen, with no cross-instance coordination layer. Simplest, adequate when index
  updates do not need to survive an application-instance crash between the database commit and the index write.

| `outbox-polling`
| Entity changes are first written to a database "outbox" table within the same transaction as the entity
  change itself (transactionally consistent with it), then a background process polls that table and applies
  the corresponding index updates. Survives an application-instance crash between commit and indexing (the
  outbox row is still there to process after restart, by this or another instance), and coordinates multiple
  application instances without them stepping on each other -- the recommended strategy for a multi-node
  deployment that needs indexing to be reliable across restarts.
|===

== Sync vs. async index writes

Independent of coordination strategy, an indexing operation can be *synchronous* (the entity-change transaction
does not complete until the index write is acknowledged -- index and database are never observably out of sync,
at the cost of added write latency) or *asynchronous* (the index write happens after the transaction commits,
in the background -- lower write latency, with a brief window where the database has the new state but the
index does not yet). Read-after-write consistency requirements on the search results should drive this choice;
most applications tolerate a short async indexing lag in exchange for not blocking the write path on the search
cluster's own latency.

== Spring Boot configuration

Hibernate Search's own properties are set the same way as any other Hibernate property, via
`+spring.jpa.properties.hibernate.search.*+`:

[source,yaml]
----
spring:
  jpa:
    properties:
      hibernate:
        search:
          backend:
            hosts: elasticsearch:9200
          coordination:
            strategy: outbox-polling
----

== Choosing the backend in the build

A backend is a classpath decision plus one property. Adding `hibernate-search-backend-lucene` or `hibernate-search-backend-elasticsearch` next to `hibernate-search-mapper-orm` is enough when only one is present. When both are on the classpath (as in a project that runs fast Lucene tests and an Elasticsearch deployment), Hibernate Search cannot guess, so set `hibernate.search.backend.type` to `lucene` or `elasticsearch` explicitly. Properties that belong to the other backend are reported as unused, not rejected: with `type=elasticsearch`, a leftover `hibernate.search.backend.directory.type` logged `HSEARCH000568` ("some properties in the given configuration are not used"), which is a useful misspelling detector and also the sign of a configuration meant for the wrong backend.

The `outbox-polling` coordination strategy is a separate artifact, `org.hibernate.search:hibernate-search-mapper-orm-coordination-outbox-polling`, and it adds its own tables (`HSEARCH_OUTBOX_EVENT` and an agent table) to the schema Hibernate manages.

== Worked example: the same save, three ways of reaching the index

The running example is the library's three books and three authors from xref:backend/hibernate/hibernate-search-fundamentals.adoc[Hibernate Search Fundamentals], stored through an `EntityManager` and then searched immediately with `matchAll()` and `fetchTotalHitCount()`. The Elasticsearch runs used a Testcontainers `ElasticsearchContainer` (Elasticsearch 9.5.6, security off), Hibernate ORM 7.4.15.Final and Hibernate Search 8.4.1.Final. Hibernate Search 8.4.1 logged `HSEARCH400085` ("Unknown Elasticsearch version running on the cluster") for that server version and worked anyway, which is the expected behavior when a cluster is newer than the Hibernate Search release; pin `hibernate.search.backend.version` to a version the release documents to avoid the warning in production.

*Default synchronization strategy, Elasticsearch.* Twenty `matchAll()` searches in a loop right after the commit that stored three books all reported fewer than three hits (20 out of 20 missed the books), and a `match` on `description` for `runs` returned nothing. The documents were written and acknowledged, but Elasticsearch had not refreshed the index yet. The default strategy, `write-sync`, waits for the write to be committed and replicated, not for it to become searchable.

*`sync` synchronization strategy, Elasticsearch.* After `hibernate.search.indexing.plan.synchronization.strategy=sync`, the same twenty searches saw all three books (0 out of 20 missed) and the `runs` query returned _Effective Java_. `sync` waits for the write and for the refresh that makes it searchable, which costs write latency in exchange for read-your-writes.

*Lucene, default strategy.* On the Lucene backend the same immediate search saw all three books with no extra setting. That is a property of the embedded backend (its default `hibernate.search.backend.io.refresh_interval` of `0` makes a search refresh the reader first), not a property of the default strategy, so it must not be generalized to Elasticsearch.

[cols="1,3,2"]
|===
|Strategy |When the transaction returns |Searchable right after commit?

|`write-sync` (default)
|After the index write is committed and acknowledged.
|Lucene: yes (refresh interval 0). Elasticsearch: no, until the next refresh.

|`read-sync`
|After the changes are searchable (the index is refreshed), without waiting for them to be durably committed.
|Yes.

|`sync`
|After the write is committed and the index is refreshed.
|Yes, on both backends.

|`async`
|Immediately, indexing continues in the background.
|Not guaranteed; the lowest write latency.
|===

The strategy can be set globally (`hibernate.search.indexing.plan.synchronization.strategy`) or overridden for one session with `searchSession.indexingPlanSynchronizationStrategy(IndexingPlanSynchronizationStrategy.sync())`, for example `sync` only for the one request that must read its own writes.

*Outbox polling.* With `hibernate.search.coordination.strategy=outbox-polling` (and Elasticsearch, with H2 as the database in the run), the same save left six rows in `HSEARCH_OUTBOX_EVENT` (three authors and three books) immediately after commit and the immediate search found 0 indexed hits. Polling the search every 100 milliseconds, all three books became searchable after about 785 milliseconds, and the outbox table was empty again afterwards. The synchronization strategy no longer applies in this mode: indexing is always asynchronous with respect to the transaction, because the transaction's only job is to write the events.

[mermaid]
....
sequenceDiagram
    participant App as Application instance A
    participant DB as Database
    participant Poller as Outbox poller (any instance)
    participant ES as Elasticsearch
    App->>DB: BEGIN, UPDATE book, INSERT outbox event, COMMIT
    Note over App,DB: entity change and event commit atomically
    loop every polling interval
        Poller->>DB: claim unprocessed events (row locks)
        DB-->>Poller: events
        Poller->>ES: bulk index or delete
        ES-->>Poller: acknowledged
        Poller->>DB: delete processed events
    end
    App->>ES: search (may not see the change yet)
....

The crash-safety argument for the outbox is visible in the sequence: if instance A dies after its `COMMIT`, the event row is already in the database and any other instance's poller will process it, whereas with the `none` strategy the in-memory indexing plan of a crashed instance is simply lost, and the only recovery is a `MassIndexer` run.
