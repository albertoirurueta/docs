xref:backend/springboot/hibernate.adoc[Hibernate (JPA & ORM)] already introduces the object/relational paradigm
mismatch briefly. This page goes deeper into each friction point and lays out where Hibernate's runtime objects
sit relative to JDBC.

== The paradigm mismatch, in depth

* *Granularity* -- an `Address` or `Money` class is naturally its own type in Java, but rarely its own table;
  it typically maps onto a handful of columns of the owning entity's table (`@Embeddable`, see
  xref:backend/hibernate/basic-and-embeddable-types.adoc[Basic & Embeddable Types]).
* *Inheritance* -- Java's single-inheritance class hierarchies and interfaces have no direct SQL counterpart.
  A `Payment` / `CardPayment` / `BankTransferPayment` hierarchy has to be flattened onto one of three table
  shapes -- see xref:backend/hibernate/inheritance-mapping.adoc[Inheritance Mapping].
* *Identity* -- Java has three notions of "sameness": reference identity (`==`), `equals()`-defined equality,
  and database identity (same primary key value). Two separately loaded `EntityManager` instances can each hold
  a distinct Java object for the same row; a single persistence context, by contrast, guarantees one Java
  instance per row (the identity map, see
  xref:backend/hibernate/persistence-context-and-lifecycle.adoc[Persistence Context & Lifecycle]).
* *Associations* -- a Java reference is directional and single-ended; a foreign key is undirected column data
  navigable from either table. A `@ManyToMany` needs a join table that has no object-model counterpart at all.
  See xref:backend/hibernate/associations.adoc[Associations].
* *Data navigation* -- walking `order.getCustomer().getAddress().getCity()` one reference at a time is natural
  in Java and disastrous against a database unless the right join (or fetch strategy) accompanies it -- the
  root cause of the N+1 problem, see xref:backend/hibernate/fetching-and-n-plus-1.adoc[Fetching & N+1].

Hibernate's job is to let you program against the object model while it works out the SQL, joins, and identity
bookkeeping needed to reconcile it with the relational model underneath.

== Layered architecture

[mermaid]
....
flowchart TB
    App["Application code"] --> API["JPA API (EntityManager) or native Hibernate API (Session)"]
    API --> PC["Persistence context\n(identity map + first-level cache + dirty checking)"]
    PC --> SQLGen["SQL generation / HQL-JPQL-Criteria translation"]
    SQLGen --> JDBC["JDBC driver"]
    JDBC --> DB[("Relational database")]
    API -.optional, no dirty checking / caching.-> Stateless["StatelessSession"]
    Stateless --> JDBC
....

Application code talks to either the standard JPA API (`EntityManager`) or Hibernate's own native API
(`Session`, a superset of `EntityManager`); both sit on top of the same persistence-context machinery, which in
turn generates SQL and delegates to a plain JDBC `Connection`. Hibernate never talks to the database except
through JDBC -- there is no proprietary wire protocol.

== `SessionFactory`/`Session` vs. `EntityManagerFactory`/`EntityManager`

Hibernate's native API predates JPA and remains richer than it:

[cols="1,1,2"]
|===
| Native type | JPA equivalent | Notes

| `SessionFactory`
| `EntityManagerFactory`
| One per persistence unit, thread-safe, application-scoped. `sessionFactory` is obtainable from
  `entityManagerFactory.unwrap(SessionFactory.class)`.

| `Session`
| `EntityManager`
| `Session` extends `EntityManager` and exposes extra operations JPA does not standardize:
  `Session.lock()` variants, HQL-specific query options, `Session.getStatistics()`, `Filter` activation, and
  `StatelessSession` access.

| `Query` (Hibernate)
| `TypedQuery`/`Query` (JPA)
| Hibernate's `org.hibernate.query.Query` extends the JPA one with scrolling, insertion order, and
  cache-region hints.
|===

A JPA-only application never needs to see `+org.hibernate.*+` types; reaching for `Session` (via
`entityManager.unwrap(Session.class)`) is a deliberate opt-in to Hibernate-specific capability, and ties that
code to Hibernate as the provider.

== `StatelessSession`

`StatelessSession` is a command-oriented alternative to `Session`: no persistence context, no first-level
cache, no automatic dirty checking, no cascading, no interceptors/events by default. Every operation
(`insert`/`update`/`delete`/`get`) is issued immediately as its own SQL statement, and returned entities are
detached the moment they are loaded. It trades away Hibernate's automation for predictable, low-overhead
behavior -- exactly what large batch/ETL jobs want; see
xref:backend/hibernate/bulk-operations-and-batching.adoc[Bulk Operations & Batching].

== Persistence units and dialects

A *persistence unit* names a set of managed classes, a data source, and a bag of properties -- the unit of
configuration an `EntityManagerFactory` is built from (one unit per `persistence.xml` `<persistence-unit>`
element, or the equivalent Spring Boot auto-configuration). A *dialect* (`org.hibernate.dialect.Dialect` and
its subclasses -- `PostgreSQLDialect`, `MySQLDialect`, `SQLServerDialect`, ...) tells Hibernate the SQL variant,
pagination syntax, identity/sequence support, and type mappings for one specific database product; since
Hibernate 6 the dialect is auto-detected from the JDBC connection metadata in the overwhelming majority of
cases, so `hibernate.dialect` rarely needs to be set explicitly.

== The API objects are the same objects

The table above pairs the native and the standard types. In Hibernate ORM 7 the pairing is literally
inheritance, and a short program against the library example (an `Author` with a `Book` collection, H2,
Hibernate ORM 7.4) confirms it:

[mermaid]
....
classDiagram
    EntityManagerFactory <|-- SessionFactory
    EntityManager <|-- Session
    Session <.. SessionFactory : openSession
    StatelessSession <.. SessionFactory : openStatelessSession
    class SessionFactory {
        getStatistics()
        inTransaction()
    }
    class Session {
        byNaturalId()
        setHibernateFlushMode()
    }
    class StatelessSession {
        get()
        insert()
        update()
    }
....

[source,java]
----
SessionFactory sf = emf.unwrap(SessionFactory.class);
sf instanceof EntityManagerFactory;                 // true

try (EntityManager em = emf.createEntityManager()) {
    Session s = em.unwrap(Session.class);
    s == em;                                        // true: same object
    s instanceof EntityManager;                     // true
}

emf.getMetamodel().getEntities();                   // [Author, Book]
----

`unwrap(Session.class)` does not wrap or copy: it returns the very object that `createEntityManager()` gave
back. That is why using native-only features costs nothing at runtime; it only costs portability. The
`Metamodel` (the standard `jakarta.persistence.metamodel` API) is built once, when the factory is built, and
is what HQL and Criteria queries are validated against -- an unknown entity name fails at query creation, not
when SQL runs.

== The data-navigation mismatch, measured

The paradigm-mismatch list claims that walking an object graph one reference at a time is "disastrous"
against a database. With three authors of two books each, with statistics enabled (`hibernate.generate_statistics`),
the same traversal was written two ways:

[source,java]
----
// one reference at a time
for (Author a : em.createQuery("select a from Author a", Author.class).getResultList()) {
    total += a.getBooks().size();            // lazy collection: one select per author
}

// one query with the join the traversal needs
for (Author a : em.createQuery("select distinct a from Author a join fetch a.books", Author.class).getResultList()) {
    total += a.getBooks().size();
}
----

Both counted six books. The first prepared **4** statements (the authors query plus one collection select
for each of the three authors, the N+1 pattern), the second **1**. The mismatch is not that Hibernate is
slow; it is that nothing in the Java code looks different between the two, so the cost is invisible until it
is measured. Statistics (`SessionFactory.getStatistics().getPrepareStatementCount()`) is the cheapest
way to put a number on it; see xref:backend/hibernate/performance-and-statistics.adoc[Performance and
Statistics] and xref:backend/hibernate/fetching-and-n-plus-1.adoc[Fetching and N+1].

== `Session` versus `StatelessSession`, side by side

The earlier paragraph describes `StatelessSession` in prose. The same operations on both, on the same
database:

[source,java]
----
try (Session s = sf.openSession()) {
    Book b1 = s.find(Book.class, 1L);
    Book b2 = s.find(Book.class, 1L);
    // b1 == b2 : true -- one select, identity map
}

try (StatelessSession ss = sf.openStatelessSession()) {
    Book b1 = ss.get(Book.class, 1L);
    Book b2 = ss.get(Book.class, 1L);
    // b1 == b2 : false -- two selects, two objects

    ss.getTransaction().begin();
    b1.setTitle("changed");
    ss.getTransaction().commit();       // no UPDATE: nothing tracks the change

    ss.getTransaction().begin();
    ss.update(b1);                      // explicit command
    ss.getTransaction().commit();       // UPDATE issued
}
----

The statistics agreed: after the explicit `update` the entity-update counter was `1`, and `0` before it.
`StatelessSession` is therefore the right tool when the code *wants* to say exactly which SQL runs
(ETL, bulk loads), and the wrong one the moment a dirty-checked, cascading object graph is expected.

== Dialect detection in the startup log

Hibernate reports the dialect it resolved from the connection metadata at startup. For the H2 database used
throughout these pages the line was `Database dialect: H2Dialect` together with `Database version: 2.3.232`,
read from the JDBC connection with no `hibernate.dialect` property set. The same detection chooses
PostgreSQL's `PostgreSQLDialect` from a `jdbc:postgresql:` connection, which is how the lock SQL in
xref:backend/hibernate/locking.adoc[Locking] differs between the two databases without any change in
mapping or application code.
