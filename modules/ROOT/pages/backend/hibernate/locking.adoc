= Locking
:description: Optimistic and pessimistic locking with Hibernate -- @Version, OPTIMISTIC/OPTIMISTIC_FORCE_INCREMENT, @OptimisticLocking dirty-vs-all, versionless locking, PESSIMISTIC_READ/WRITE/FORCE_INCREMENT, LockModeType, and lock scope/timeout hints.
:keywords: Hibernate locking, @Version, optimistic locking, OPTIMISTIC_FORCE_INCREMENT, @OptimisticLocking, versionless optimistic locking, pessimistic locking, PESSIMISTIC_READ, PESSIMISTIC_WRITE, LockModeType, lock timeout

include::partial$ai-disclaimer.adoc[]

Concurrent writers to the same row need a strategy for who wins. This page covers Hibernate's optimistic and
pessimistic locking mechanisms in depth; for how Spring layers `@Transactional` isolation and `@Lock` on top of
these, see xref:backend/springboot/transaction-isolation-and-locking.adoc[Transaction Isolation & Locking].

== Optimistic locking with `@Version`

[source,java]
----
@Entity
public class Account {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Version
    private Long version;

    private BigDecimal balance;
}
----

Every `UPDATE` Hibernate generates for a `@Version`-annotated entity includes `WHERE id = ? AND version = ?`
and increments the version column. If zero rows match (because another transaction already updated -- and
incremented the version of -- that row first), Hibernate throws `OptimisticLockException` (JPA) /
`StaleObjectStateException` (native) instead of silently overwriting the concurrent change. This needs no
database-level locking at all -- the conflict is only ever detected at write time, which is why it is called
*optimistic*: it assumes conflicts are rare and pays the cost only when one actually occurs.

`OptimisticLockType`/`LockModeType` variants:

[cols="1,3"]
|===
| Mode | Behavior

| `OPTIMISTIC` (JPA `LockModeType.OPTIMISTIC`)
| Standard `@Version` check as above for modified entities; additionally re-reads the version at commit, so
  an entity that was only read fails the commit if it changed meanwhile.

| `OPTIMISTIC_FORCE_INCREMENT`
| Forces a version increment even when the entity's own state did not change -- used when a change to an
  *associated* entity should still be treated as a conflict-relevant change to this entity (e.g. incrementing
  the version of an `Order` when an `OrderLine` is added, so a concurrent edit to the order sees the line addition
  as a conflict too).

| Versionless optimistic locking (`@OptimisticLocking(type = OptimisticLockType.ALL)`)
| No `@Version` column at all -- the `WHERE` clause instead compares *every* mapped column against the values
  loaded, detecting a conflict on any changed column. Works without a schema change and requires
  `@DynamicUpdate`, but raises a conflict even for concurrent edits of *unrelated* columns, because every
  column is compared -- `@Version` is the generally preferred approach when a schema change is possible.
|===

The `OPTIMISTIC_FORCE_INCREMENT` case above is really *aggregate versioning* in disguise -- the root's version
stands in for the whole cluster's consistency, not just its own columns; see
xref:backend/architecture/architectural-patterns/aggregates.adoc[] for the full treatment.

== `@OptimisticLocking`: dirty vs. all

`@OptimisticLocking(type = OptimisticLockType.DIRTY)` narrows the versionless comparison (or, combined with
`@DynamicUpdate`, the `@Version`-based one) to only the columns that actually changed in this flush, rather
than every mapped column -- reduces the chance of a false conflict against a concurrent change to an unrelated
column, at the cost of needing `@DynamicUpdate` (see
xref:backend/hibernate/flushing-and-dirty-checking.adoc[Flushing & Dirty Checking]) since the generated SQL now
varies per flush.

== Pessimistic locking

Pessimistic locking asks the database to hold a row lock for the duration of the current transaction, blocking
(or failing) other transactions that want a conflicting lock on the same row -- suited to high-contention
scenarios where an optimistic conflict would be common and retrying is expensive (e.g. decrementing a limited
inventory count).

[cols="1,3"]
|===
| `LockModeType` | Behavior

| `PESSIMISTIC_READ`
| A shared lock -- blocks other transactions from acquiring a conflicting write lock, but not from also reading.
  Maps to `+SELECT ... FOR SHARE+` or the dialect's equivalent (`for update` on H2, `for share` on PostgreSQL).

| `PESSIMISTIC_WRITE`
| An exclusive lock -- blocks any other transaction from reading-for-update or writing the row until this
  transaction ends. Maps to `+SELECT ... FOR UPDATE+` (`for no key update` on PostgreSQL).

| `PESSIMISTIC_FORCE_INCREMENT`
| Combines a pessimistic write lock with an immediate `@Version` increment, for when a concurrently-running
  optimistic reader elsewhere should also see this as a conflict once it later tries to commit.
|===

[source,java]
----
Account account = em.find(Account.class, id, LockModeType.PESSIMISTIC_WRITE);
// or, explicitly against an already-loaded managed entity:
em.lock(account, LockModeType.PESSIMISTIC_WRITE);

Map<String, Object> hints = Map.of("jakarta.persistence.lock.timeout", 3000); // milliseconds
Account locked = em.find(Account.class, id, LockModeType.PESSIMISTIC_WRITE, hints);
----

Hibernate's native `Session.lock(entity, LockMode)` and
`Session.find(Class, id, LockMode, Timeout, PessimisticLockScope)` offer the same capability (`LockOptions` and
`Session.get(Class, id, LockOptions)` are deprecated for removal since Hibernate 7; see below).

== Lock scope and timeout hints

`jakarta.persistence.lock.timeout` (milliseconds; `0` = no wait/fail-fast, `-1` = wait indefinitely per the
database's default, `-2` = skip locked rows) controls how long a pessimistic-lock acquisition waits before the database raises a lock
-- wait -- timeout error, translated by Hibernate into `jakarta.persistence.PessimisticLockException` /
`LockTimeoutException`. `jakarta.persistence.lock.scope = PessimisticLockScope.EXTENDED` extends a pessimistic
lock on an entity to also lock rows in its owned collection tables, not just the entity's own row.

== Optimistic vs. pessimistic: choosing

`xref:backend/springboot/transaction-isolation-and-locking.adoc#optimistic-vs-pessimistic-choosing[Transaction
Isolation & Locking]` already lays out the general decision (contention frequency, retry cost, UX for
conflicts). At the Hibernate-mapping level specifically: optimistic locking needs no schema change beyond a
`@Version` column and scales better under low contention (no lock held across a possibly-slow transaction);
pessimistic locking avoids retries entirely under high contention but holds a real database lock for as long
as the transaction runs, directly limiting throughput on that row.

== Optimistic locking, observed

The `Account` entity from the example above (`@Version Long version`, a `balance`, an `owner`) was loaded by
two `EntityManager` instances, each changed `balance`, and both committed. Hibernate ORM 7.4 on H2 printed:

[source,text]
----
select a1_0.id,a1_0.balance,a1_0.owner,a1_0.version from account a1_0 where a1_0.id=?
select a1_0.id,a1_0.balance,a1_0.owner,a1_0.version from account a1_0 where a1_0.id=?
update account set balance=?,owner=?,version=? where id=? and version=?     -- first commit: 1 row
update account set balance=?,owner=?,version=? where id=? and version=?     -- second commit: 0 rows
----

and the second commit failed with this chain, from the outermost exception inward:
`RollbackException` -> `OptimisticLockException` -> `StaleObjectStateException` -> `StaleStateException`,
whose message is `Unexpected row count (expected row count 1 but was 0)` followed by the statement. (When
the conflict is detected by an explicit `flush()` instead of a commit, the `OptimisticLockException` is thrown
directly, without the `RollbackException` wrapper.) The handling is always the same: abandon the
`EntityManager`, reload, and either retry the whole unit of work or report the conflict.

=== The lock modes that touch an unmodified entity

`LockModeType.OPTIMISTIC` is not just a version check at flush time. Loading an `Account` with
`em.find(Account.class, id, LockModeType.OPTIMISTIC)`, changing nothing and committing issued, at commit time:

[source,text]
----
select version as version_ from account where id=?
----

That is the *read check*: the version is re-read and compared when the transaction ends, so a transaction
that only *read* an entity still fails if someone changed it meanwhile. It is the cheap way to say "my
decision was based on this row and it must not have changed". `OPTIMISTIC_FORCE_INCREMENT` with no state
change instead issued `update account set version=? where id=? and version=?`: a write that exists only to
bump the version.

=== Versionless locking: `ALL` and `DIRTY`

`@OptimisticLocking(type = OptimisticLockType.ALL)` and `DIRTY` both require `@DynamicUpdate`: without it the
factory failed to build with a `MappingException` stating that the entity "has 'OptimisticLockType.ALL' but
is not annotated '@DynamicUpdate'". With it, two transactions that changed *different* columns of one row
behaved differently under the two types:

[source,text]
----
-- ALL: first writer changes balance, second writer changes owner
update all_acc set balance=? where id=? and balance=? and owner=?
update all_acc set owner=?   where id=? and balance=? and owner=?      -- 0 rows: conflict

-- DIRTY: the same two edits
update dirty_acc set balance=? where id=? and balance=?
update dirty_acc set owner=?   where id=? and owner=?                  -- 1 row: no conflict
----

`ALL` raised a conflict even though the two transactions had edited unrelated columns, because the second
`WHERE` clause compares the *original* `balance` as well, and the first writer had changed it. So it is `ALL` that
produces false conflicts between unrelated columns, and `DIRTY` that avoids them. `DIRTY` still detected a genuine conflict when both writers changed `balance`
(`update dirty_acc set balance=? where id=? and balance=?` matched 0 rows for the second). A `@Version`
column remains the more explicit and cheaper choice when a column can be added.

== Pessimistic locking, per database

What `PESSIMISTIC_READ` and `PESSIMISTIC_WRITE` become in SQL depends on the dialect. The same
`em.find(Account.class, id, mode)` was run on H2 2.3 and on PostgreSQL 17 (Docker image `postgres:17-alpine`):

[cols="2,2,3"]
|===
| Request | H2 | PostgreSQL

| `PESSIMISTIC_READ`
| `+... where a1_0.id=? for update+`
| `+... where a1_0.id=? for share of a1_0+`

| `PESSIMISTIC_WRITE`
| `+... where a1_0.id=? for update+`
| `+... where a1_0.id=? for no key update of a1_0+`

| `PESSIMISTIC_WRITE`, `lock.timeout` `0`
| not run
| `+... for no key update of a1_0 nowait+`

| `PESSIMISTIC_WRITE`, `lock.timeout` `300`
| `+... for update wait 1+` (H2 takes whole seconds)
| `set local lock_timeout = 300`, the select, then `set local lock_timeout = 0` to restore the old value

| `PESSIMISTIC_WRITE`, `lock.timeout` `-2`
| not run
| `+... for no key update of a1_0 skip locked+`

| `PESSIMISTIC_FORCE_INCREMENT`
| `+... for update+`, then `update account set version=? where id=? and version=?`
| not run
|===

Two consequences. First, `FOR UPDATE` is only the generic picture: on PostgreSQL Hibernate asks for the weaker `for no key update`, which does not block
inserts of child rows that reference the locked row, and `PESSIMISTIC_READ` is `for share`. Second, a timeout
of `-2` is Jakarta Persistence 3.2's `SKIP_LOCKED`, which is what a worker-queue loop wants: rows already
locked by another worker are skipped instead of waited for.

With one transaction holding the row, a second `find` with `jakarta.persistence.lock.timeout` of `300` on H2
failed with `LockTimeoutException` after about one second (H2 rounds the timeout up); on PostgreSQL the
`nowait` variant failed immediately with `PessimisticLockException`. Which of the two exception types a
database produces varies, so handle both (they share the `PersistenceException` parent; per the specification
`PessimisticLockException` marks the transaction for rollback while `LockTimeoutException` does not).

`em.lock(account, LockModeType.PESSIMISTIC_WRITE)` on an already loaded `Account` re-reads *and version-checks*
the row while locking it:

[source,text]
----
select a1_0.id from account a1_0 where a1_0.id=? and a1_0.version=? for update
----

so if another transaction committed a change after the load, the lock attempt itself fails with an
optimistic-lock error rather than silently locking stale state.

=== Lock scope

`jakarta.persistence.lock.scope` set to `PessimisticLockScope.EXTENDED` on an entity with an
`@ElementCollection` produced a second locking statement for the collection table, on PostgreSQL:

[source,text]
----
select a1_0.id,a1_0.version from account2 a1_0 where a1_0.id=? for no key update of a1_0
select tbl.Account2_id from Account2_tags tbl where tbl.Account2_id in (?) for no key update of tbl
----

== The native locking API in Hibernate 7

`LockOptions` and `Session.get(Class, Object, LockOptions)` are deprecated for removal since Hibernate ORM
7 (the compiler reports it on 7.4.15). The replacement is the Jakarta
Persistence 3.2 vocabulary that Hibernate's `Session` now accepts directly:

[source,java]
----
session.lock(account, LockMode.PESSIMISTIC_WRITE);

Account a = session.find(Account.class, id,
        LockMode.PESSIMISTIC_WRITE,
        Timeout.ms(250),                       // jakarta.persistence.Timeout
        PessimisticLockScope.EXTENDED);
----

On PostgreSQL the `find` above issued the `set local lock_timeout = 250` statement, the two locking selects
(entity row, then collection rows) and the restoring `set local lock_timeout = 0`.
