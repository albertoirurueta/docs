= HQL and JPQL
:description: Hibernate Query Language as a superset of JPQL -- statement types, joins, functions, DTO projections, set operations, aggregation, the Query API, pagination, @NamedQuery, and scrolling/streaming.
:keywords: HQL, JPQL, Hibernate Query Language, SELECT new, JOIN FETCH, WITH ON, setFirstResult, setMaxResults, key-based pagination, @NamedQuery, ScrollableResults, scroll, stream

include::partial$ai-disclaimer.adoc[]

*HQL* (Hibernate Query Language) is Hibernate's own object-oriented query language; *JPQL* (the JPA-standard
query language) is a strict subset of it -- any valid JPQL query is valid HQL, but HQL adds syntax JPQL does
not define. This page covers HQL/JPQL syntax and the `Query` API in depth; for how Spring Data wires `@Query`
strings into repository methods, see xref:backend/springboot/spring-data-jpa.adoc[Spring Data JPA] -- this page
stays one layer below that, on the language itself.

== Statement types

HQL supports `SELECT`, `UPDATE`, `DELETE`, and `+INSERT ... SELECT+` statements, all operating over entity names
and their fields rather than table and column names:

[source,java]
----
// SELECT
em.createQuery("SELECT b FROM Book b WHERE b.title LIKE :pattern", Book.class);

// bulk UPDATE / DELETE -- see bulk-operations-and-batching.adoc for why these bypass the persistence context
em.createQuery("UPDATE Book b SET b.outOfPrint = true WHERE b.publishedYear < :year")
        .setParameter("year", 1990)
        .executeUpdate();
----

== `FROM`/`JOIN`: explicit, implicit, `WITH`/`ON`

[source,java]
----
// explicit join
"SELECT b FROM Book b JOIN b.author a WHERE a.name = :name"

// join fetch -- see fetching-and-n-plus-1.adoc
"SELECT b FROM Book b JOIN FETCH b.author"

// implicit join via path expression (equivalent inner join, no alias for author)
"SELECT b FROM Book b WHERE b.author.name = :name"

// WITH / ON -- extra join-time predicate beyond the association's own mapping
"SELECT a FROM Author a LEFT JOIN a.books b WITH b.publishedYear > :year"
----

`WITH` (HQL) and JPQL's standardized `ON` are equivalent for this purpose in modern Hibernate -- both add a
join-time condition beyond the association's own foreign key, most useful for a `LEFT JOIN` where filtering in
the main `WHERE` clause instead would incorrectly turn it into an inner join.

== Functions, predicates, and projections

Standard JPQL functions (`LOWER`, `UPPER`, `LENGTH`, `CONCAT`, `SUBSTRING`, `TRIM`, arithmetic, `COALESCE`,
`NULLIF`, `CASE WHEN`) plus HQL extensions (`FORMAT`, date/time component extraction, `CAST`); predicates
include `BETWEEN`, `IN`, `LIKE`, `IS NULL`, `EXISTS`, and JPQL's `MEMBER OF` for collection membership.

`SELECT new` projects query results directly into a DTO constructor instead of full entities -- the recommended
shape for read-only views (see xref:backend/hibernate/fetching-and-n-plus-1.adoc[Fetching & N+1]):

[source,java]
----
public record BookSummary(Long id, String title, String authorName) {}

List<BookSummary> summaries = em.createQuery(
        "SELECT new com.example.BookSummary(b.id, b.title, a.name) FROM Book b JOIN b.author a",
        BookSummary.class).getResultList();
----

== Set operations: `UNION`/`INTERSECT`/`EXCEPT`

HQL supports combining the results of several `SELECT` queries with the same JPQL-level set operators SQL
offers, translated to the target database's own syntax (or emulated where unsupported):

[source,java]
----
em.createQuery("""
        SELECT b.title FROM Book b WHERE b.publishedYear > 2020
        UNION
        SELECT b.title FROM Book b WHERE b.author.name = :name
        """, String.class);
----

== Aggregation and grouping

`COUNT`, `SUM`, `AVG`, `MIN`, `MAX`, `GROUP BY`, `HAVING` -- standard SQL-style aggregation, over entity paths:

[source,java]
----
em.createQuery("""
        SELECT a.name, COUNT(b), AVG(b.price)
        FROM Book b JOIN b.author a
        GROUP BY a.name
        HAVING COUNT(b) > 5
        """, Object[].class);
----

== The `Query` API, parameters, and pagination

[source,java]
----
TypedQuery<Book> query = em.createQuery("FROM Book b WHERE b.publishedYear = :year", Book.class);
query.setParameter("year", 2024);          // named parameter
query.setFirstResult(20);                  // offset
query.setMaxResults(10);                   // page size
List<Book> page = query.getResultList();

// Hibernate's own Limit/Page API (alternative to setFirstResult/setMaxResults)
Query<Book> hquery = session.createQuery("FROM Book", Book.class);
hquery.setPage(Page.first(10));
----

Offset-based pagination (`setFirstResult`/`setMaxResults`) gets slower as the offset grows, since the database
still has to scan and discard every skipped row. *Key-based (seek) pagination* avoids this by filtering on the
last-seen sort key instead of an offset:

[source,java]
----
// page N+1: everything after the last id seen on the previous page, same order
"FROM Book b WHERE b.id > :lastSeenId ORDER BY b.id ASC"
----

== `@NamedQuery`

[source,java]
----
@Entity
@NamedQuery(
    name = "Book.findByAuthorName",
    query = "SELECT b FROM Book b JOIN b.author a WHERE a.name = :name")
public class Book { /* ... */ }

// ...
em.createNamedQuery("Book.findByAuthorName", Book.class).setParameter("name", "King").getResultList();
----

Named queries are validated and their query plan is prepared at `EntityManagerFactory` bootstrap rather than
the first time they run, catching a typo at startup instead of at request time.

== Scrolling and streaming

For result sets too large to materialize as a `List` at once:

[source,java]
----
// Hibernate native scrolling -- a server-side cursor
try (ScrollableResults<Book> results = session.createQuery("FROM Book", Book.class)
        .scroll(ScrollMode.FORWARD_ONLY)) {
    while (results.next()) {
        Book book = results.get();
        // process one at a time; periodically clear() the session, see bulk-operations-and-batching.adoc
    }
}

// JPA streaming
try (Stream<Book> stream = em.createQuery("FROM Book", Book.class).getResultStream()) {
    stream.forEach(this::process);
}
----

Both still hold one JDBC `ResultSet` open for the duration; they bound *heap* usage (no giant `List` materialized
at once), not the database-side or persistence-context cost of processing many rows -- pair with periodic
`session.clear()` for very large scans.

== `+hibernate.query.*+` settings

`hibernate.query.plan_cache_max_size` bounds how many parsed-and-translated query plans Hibernate keeps cached
(a cache miss re-parses the JPQL/HQL string, so highly dynamic query strings can thrash this cache -- prefer
parameters over string-concatenated literals for exactly this reason, in addition to avoiding SQL injection).
`hibernate.query.fail_on_pagination_over_collection_fetch` catches, at query-plan time, the specific mistake of
combining `setFirstResult`/`setMaxResults` with a `JOIN FETCH` of a to-many collection in the cases where
Hibernate has to apply the limit to the joined (denormalized) rows in memory instead of in SQL -- there the page
is computed over the whole fetched result, which can be very large. Whether a given query falls into that case
depends on the Hibernate version and the query shape (see the measured example below), so the setting is a
guard rail rather than a description of default behavior.

== From string to SQL: what Hibernate does with a query

[mermaid]
....
flowchart LR
    A["HQL or JPQL string"] --> B["ANTLR parser"]
    B --> C["SQM<br/>semantic query model"]
    C --> D["Type checking and<br/>implicit-join resolution"]
    D --> E["SQL AST<br/>per dialect"]
    E --> F["SQL string and<br/>JDBC parameters"]
    F --> G["ResultSet"]
    G --> H["Row mapping:<br/>entities, DTOs, scalars"]
....

The parse and translation work is cached per query string (see `hibernate.query.plan_cache_max_size` below), and
a malformed query -- unknown attribute, wrong operand type -- is rejected in the first two stages, before any SQL
is produced. The fragments that follow all run against the section's `Author`/`Book` model (12 authors, three
books each); the SQL quoted is what Hibernate ORM 7.4.15 printed for the H2 dialect with the Spring-Boot-style
naming strategy, so table and column names are snake case.

=== Implicit joins and `ON`

A path through a to-one association in the `WHERE` clause becomes a real inner join, with no alias in the HQL:

[source,sql]
----
-- from: select b from Book b where b.author.name = :n
select b1_0.id,b1_0.author_id,b1_0.isbn,... from book b1_0
  join author a1_0 on a1_0.id=b1_0.author_id where a1_0.name=?
----

A condition in `ON` stays inside the join, so the outer join is preserved. For authors 1 and 2 and a threshold of
1985, `select a.name, b.title from Author a left join a.books b on b.publishedYear > :y where a.id < 3`
returned one row for author 1 and three for author 2 in the run, and the predicate was rendered as
`left join book b1_0 on a1_0.id=b1_0.author_id and b1_0.published_year>?`. Moving the same predicate to
`WHERE` would drop every author without a matching book.

=== Projections: `new`, records and constructor matching

A `select new` expression and a plain select list whose shape matches the target record's constructor produced
identical SQL and results in 7.4.15, so a result type can be given directly:

[source,java]
----
public record BookRow(String title, String authorName, BigDecimal price) {}

List<BookRow> rows = session.createQuery("""
        select b.title, a.name, b.price
        from Book b join b.author a
        where a.id = 1
        order by b.title
        """, BookRow.class).getResultList();
// BookRow[title=Book 1.1, authorName=Author 1, price=15.00], BookRow[title=Book 1.2, ...]
----

=== Aggregates, window functions and common table expressions

HQL 7 accepts window functions and `WITH` clauses, translated to the dialect's own syntax:

[source,java]
----
session.createQuery("""
        select b.title, b.price,
               rank() over (partition by b.author order by b.price desc)
        from Book b where b.author.id = 1 order by b.title
        """, Object[].class);
// [Book 1.1, 15.00, 3]   [Book 1.2, 20.00, 2]   [Book 1.3, 25.00, 1]

session.createQuery("""
        with recent as (select b.id as id, b.title as title from Book b where b.publishedYear > 2015)
        select r.title from recent r order by r.title
        """, String.class);
----

The second statement became
`+select r1_0.title from (select b1_0.id,b1_0.title from book b1_0 where b1_0.published_year>2015) r1_0(id,title) ...+`
on H2: the CTE was inlined as a derived table, because the
dialect does not need a real `WITH` for it.

=== Pagination, offset and keyset

`setFirstResult`/`setMaxResults` and `setPage(Page.page(5, 2))` both produced the standard
`offset ? rows fetch first ? rows only`. For a stable sort, Hibernate 6.5 and later can also build the seek
predicate itself:

[source,java]
----
KeyedPage<Book> page = Page.first(5).keyedBy(List.of(Order.asc(Book_.publishedYear), Order.asc(Book_.id)));
KeyedResultList<Book> first = session.createSelectionQuery("from Book", Book.class)
        .getKeyedResultList(page);
KeyedResultList<Book> second = session.createSelectionQuery("from Book", Book.class)
        .getKeyedResultList(first.getNextPage());
----

The first page returned ids 1 to 5 and the second 6 to 10. The first statement used `order by 6,1 offset ?
rows fetch first ? rows only`; the second replaced the offset with
`where published_year>? or id>? and published_year=?`, i.e. a keyset predicate computed from the last row of the
previous page, with no offset scan. The query text must not contain its own `ORDER BY`, because the key
definition supplies the ordering.

=== Pagination over a collection fetch

Combining `setMaxResults(2)` with `join fetch a.books` returned two authors, each with all of their books, in
7.4.15. The statement shows why: the limit is applied to a subquery over the parents, then the books are
joined, so no rows are discarded in memory:

[source,sql]
----
select a1_0.id,b1_0.author_id,b1_0.id,...,a1_0.name
from (select a1_0.id,a1_0.name from author a1_0
      where exists(select 1 from book b1_0 where a1_0.id=b1_0.author_id)
      order by a1_0.id offset ? rows fetch first ? rows only) a1_0(id,name)
join book b1_0 on a1_0.id=b1_0.author_id order by a1_0.id
----

Older Hibernate versions applied the limit in memory after fetching every joined row and logged a warning
(`HHH90003004`); `hibernate.query.fail_on_pagination_over_collection_fetch`, described above, turns that
situation into an error.

=== Bulk statements

`createMutationQuery` is the type-safe entry point for `UPDATE`/`DELETE`/`INSERT`; running
`+update Book b set b.price = b.price * 1.1 where b.publishedYear < :y+` produced
`+update book b1_0 set price=(b1_0.price*1.1) where b1_0.published_year<?+` and returned the affected row count
(6 in the run). See xref:backend/hibernate/bulk-operations-and-batching.adoc[Bulk Operations and Batching] for
the persistence-context consequences.
