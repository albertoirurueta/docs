= Hibernate & Spring Boot Integration
:description: How spring-boot-starter-data-jpa wires Hibernate in as the JPA provider, whether Spring Data JPA supersedes Hibernate (it doesn't -- a comparison table of what each layer is responsible for), Hibernate's own limitations inside a Spring Boot application, and where to track database model evolution.
:keywords: spring-boot-starter-data-jpa, HibernateJpaVendorAdapter, Spring Data JPA vs Hibernate, JpaRepository, EntityManager, open-in-view, hibernate.properties, spring.jpa.properties.hibernate, N+1, second-level cache, reactive Hibernate

include::partial$ai-disclaimer.adoc[]

Every other page in this section documents Hibernate on its own terms -- plain Jakarta Persistence, independent
of any framework. This page is the deliberate exception: it answers the question every reader arriving from
xref:backend/springboot/index.adoc[the SpringBoot Reference] eventually asks -- *what, exactly, is Spring Data
JPA adding on top of Hibernate, and where does Hibernate stop and Spring start?*

== Two layers, not two competing choices

*Spring Data JPA does not replace Hibernate -- it sits on top of it.* Spring Boot's
`spring-boot-starter-data-jpa` pulls in Hibernate ORM as the default *Jakarta Persistence provider*, Spring ORM,
and a connection pool (HikariCP), then auto-configures an `EntityManagerFactory` from `+spring.datasource.*+` and
`+spring.jpa.*+` -- `HibernateJpaVendorAdapter` is the adapter Boot uses to plug Hibernate in as that provider and
translate common settings (dialect detection, DDL mode) into Hibernate properties. Every entity mapping
annotation (`@Entity`, `@ManyToOne`, `@Id`), every flush, every piece of dirty-checking and every SQL statement
Spring Data JPA ultimately issues is Hibernate doing the actual ORM work -- see
xref:backend/springboot/hibernate.adoc#spring-boot-integration[Hibernate (JPA & ORM) -- Spring Boot
integration] for that wiring in full, and xref:backend/hibernate/getting-started.adoc[Getting Started] for
Hibernate's own bootstrap outside of Spring entirely.

*Spring Data JPA*, covered in depth in xref:backend/springboot/spring-data-jpa.adoc[Spring Data JPA], is a
*repository-generation layer*: it takes an interface (`JpaRepository<Book, Long>`) and generates an
implementation at startup, backed by an `EntityManager` obtained from that same Hibernate-provided
`EntityManagerFactory`. Nothing about Hibernate's own model -- the persistence context, entity states, dirty
checking, caching, HQL -- changes underneath it; Spring Data JPA just removes the boilerplate of writing a DAO
class by hand.

[cols="1,2,2"]
|===
| |Hibernate (native / plain JPA) |Spring Data JPA

|What it is
|The ORM engine and Jakarta Persistence provider -- entity mapping, the persistence context, dirty checking,
caching, query execution.
|A repository-generation layer built on top of a JPA provider (Hibernate, by default in Spring Boot).

|How you use it
|Inject/obtain an `EntityManager` (or a native `Session`) and call `persist`/`find`/`createQuery` yourself.
|Declare a repository interface; Spring Data generates the CRUD/query implementation at startup.

|Boilerplate for common CRUD
|You write the `EntityManager` calls for every operation.
|None -- `save`/`findById`/`findAll`/`delete` come from `CrudRepository`/`JpaRepository` for free.

|Deriving a query from intent
|Not built in -- write HQL/JPQL, Criteria, or native SQL by hand (xref:backend/hibernate/hql-jpql.adoc[HQL/JPQL],
xref:backend/hibernate/criteria-api.adoc[Criteria API]).
|Derived query methods parse a query straight out of a method name/`@Query` annotation -- see
xref:backend/springboot/spring-data-jpa.adoc[Spring Data JPA] and
xref:backend/springboot/spring-data-overview.adoc[Spring Data Overview].

|Type-safe, runtime-composed queries
|The JPA Criteria API / `SelectionSpecification` (xref:backend/hibernate/criteria-api.adoc[Criteria API]).
|Specifications, built on the same Criteria API underneath -- no separate query engine.

|Transaction demarcation
|Programmatic (`EntityTransaction`/`Session` transaction API) unless something else (Spring) supplies
declarative `@Transactional`.
|`@Transactional` on repository/service methods, backed by Spring's `PlatformTransactionManager` --
Hibernate still executes the actual SQL underneath.

|Auditing (`created_at`/`updated_at`/etc.)
|Manual, via lifecycle callbacks (xref:backend/hibernate/events-interceptors-and-filters.adoc[Events,
Interceptors & Filters]) or Envers for full history (xref:backend/hibernate/envers-auditing.adoc[Envers
Auditing]).
|`@CreatedDate`/`@LastModifiedDate`/`@CreatedBy`/`@LastModifiedBy` with `@EnableJpaAuditing` -- Hibernate's
lifecycle callbacks are what Spring Data hooks to implement this.

|Testing without a framework
|Bootstrap a `SessionFactory`/`EntityManagerFactory` directly --
xref:backend/hibernate/integration-testing.adoc[Integration Testing with Hibernate].
|Needs Spring's test support (`@DataJpaTest`, `TestEntityManager`) --
xref:backend/springboot/unit-and-integration-testing.adoc[Unit & Integration Testing].

|Escape hatch for what the abstraction doesn't cover
|None needed -- you already have the full session/`EntityManager` API.
|Inject a raw `EntityManager` (`@PersistenceContext`), or drop to `JdbcClient`/`JdbcTemplate` -- both covered on
xref:backend/springboot/spring-data-jpa.adoc[Spring Data JPA].

|Reactive (non-blocking) support
|Only via the separate *Hibernate Reactive* project, with a fundamentally different session/transaction model
-- xref:backend/hibernate/reactive-and-data-repositories.adoc[Reactive & Data Repositories].
|None -- Spring Data JPA is JDBC-based and always blocking; Spring's reactive stack uses R2DBC instead, with no
Hibernate involved at all.
|===

The practical guidance: reach for Spring Data JPA's repositories for the large majority of CRUD and
query-by-intent use cases -- it is the lower-friction default this repo's own
xref:backend/springboot/spring-data-jpa.adoc[Spring Data JPA] page assumes. Drop to the Hibernate/JPA APIs this
section documents in depth (a raw `EntityManager`, `StatelessSession`, HQL written by hand, `@EntityGraph`
tuning) whenever a repository method can't express what's needed -- Spring Data JPA never hides or blocks that
escape hatch, since the `EntityManager` it hands your custom repository methods is the very same Hibernate
`Session` underneath.

== Hibernate's limitations inside a Spring Boot application

These are constraints that come from *Hibernate itself*, not from Spring Data JPA's repository layer -- they
apply equally whether the code in front of them is a hand-written `EntityManager` call or a generated
repository method:

* *`spring.jpa.open-in-view` hides N+1 problems until production load.* It defaults to `true`, keeping the
  persistence context open for the whole HTTP request so lazy associations still resolve in the
  view/serializer -- convenient, but it holds a database connection for longer than the service method and
  masks N+1 query patterns that only show up as latency under real traffic. See
  xref:backend/hibernate/fetching-and-n-plus-1.adoc[Fetching & N+1] and
  xref:backend/springboot/hibernate.adoc#spring-boot-integration[Hibernate (JPA & ORM) -- Spring Boot
  integration].
* *Hibernate is fundamentally blocking.* It is built on JDBC, which is a synchronous, thread-blocking API --
  there is no non-blocking code path through `spring-boot-starter-data-jpa`/Hibernate ORM at all. A Spring
  WebFlux application cannot call a `JpaRepository` (or a plain `EntityManager`) from a reactive pipeline
  without blocking the calling thread; the only genuinely non-blocking path to a JPA-mapped domain model is the
  separate *Hibernate Reactive* project, whose session/transaction model does **not** ride the same Reactor
  `Context` Spring's own reactive transactions use -- see
  xref:backend/hibernate/reactive-and-data-repositories.adoc[Reactive & Data Repositories] and
  xref:backend/springboot/reactive-programming.adoc[Reactive Programming with Project Reactor] for the two
  context-propagation models side by side, and why bridging between them is not automatic.
* *The second-level cache is opt-in and easy to leave misconfigured.* Unlike Spring's own `@Cacheable`
  abstraction, Hibernate's own entity/collection/query cache (xref:backend/hibernate/second-level-cache.adoc[
  Second-Level Cache]) needs a provider dependency and per-entity `@Cache` annotations; adding
  `spring-boot-starter-cache` alone does nothing for it. The two caching layers solve different problems and are
  easy to conflate -- see the cross-reference on that page and
  xref:backend/springboot/caching.adoc[Caching] for Spring's own abstraction.
* *Not every Hibernate setting has a first-class Spring Boot property.* `HibernateJpaVendorAdapter` only
  translates the common ones (dialect detection, DDL mode); anything else -- batch size, statistics, a
  Hibernate-specific interceptor -- goes through the `+spring.jpa.properties.hibernate.*+` prefix
  (e.g. `spring.jpa.properties.hibernate.jdbc.batch_size`), which is a raw pass-through with no Boot-side
  validation or IDE autocompletion.
* *Schema generation is a Hibernate-only development convenience, never a Spring Boot feature.*
  `spring.jpa.hibernate.ddl-auto` (Boot's property for Hibernate's `hbm2ddl.auto`) is documented in full,
  including why `validate` is the only production-safe value, on
  xref:backend/hibernate/schema-generation-and-tooling.adoc[Schema Generation and Tooling]. Real schema
  change belongs to a migration tool instead -- see xref:database/schema-evolution/index.adoc[Evolving the
  Database Model] for tracking the database model's evolution with Liquibase, Mongock, or Flamingock, applied
  the same way regardless of whether Hibernate is used through Spring Data JPA or on its own.

== What the starter assembles, bean by bean

Spring Boot does not hide a different persistence stack behind `spring-boot-starter-data-jpa`; it builds the same objects a hand-written bootstrap would, and exposes them as beans:

[mermaid]
....
flowchart LR
    props["spring.datasource.* and spring.jpa.*"] --> ds["DataSource (HikariCP)"]
    props --> vendor["HibernateJpaVendorAdapter"]
    ds --> lcemfb["LocalContainerEntityManagerFactoryBean"]
    vendor --> lcemfb
    lcemfb --> emf["EntityManagerFactory = Hibernate SessionFactory"]
    emf --> tm["JpaTransactionManager"]
    emf --> shared["Shared EntityManager proxy (@PersistenceContext)"]
    shared --> repos["Generated Spring Data repositories"]
    tm --> tx["@Transactional boundaries"]
    tx --> repos
....

Three observations about that wiring, each checked against a running Spring Boot 4.1.2 application (which manages Hibernate ORM 7.4.13.Final):

* *The injected `EntityManager` is a thread-aware proxy, not a session.* `em.unwrap(Session.class)` on the injected instance returns a JDK proxy (its class name starts with `$Proxy`) that delegates to whichever Hibernate `Session` the current transaction owns. Outside a transaction it opens a short-lived one per call. That is why a repository method can be called from any thread without sharing state, and why holding on to an entity across transactions leaves it detached.
* *`+spring.jpa.properties.*+` is a raw pass-through.* With `spring.jpa.properties.hibernate.jdbc.batch_size=25` in `application.properties`, `session.getSessionFactory().getProperties().get("hibernate.jdbc.batch_size")` returns `25`. Nothing validates the key, so a misspelled one is silently ignored.
* *Slice tests rebuild the database.* Under `@DataJpaTest` the same entities run against an embedded H2 whose JDBC URL contains a random identifier, and each test method runs in a transaction that is rolled back. Boot 4 moved the annotation to `org.springframework.boot.data.jpa.test.autoconfigure.DataJpaTest`, shipped by the `spring-boot-starter-data-jpa-test` test starter.

The mapping from the most-used Spring Boot property to the Hibernate setting it feeds:

[cols="2,2,3"]
|===
|Spring Boot property |Hibernate setting |Notes

|`spring.jpa.hibernate.ddl-auto`
|`hibernate.hbm2ddl.auto`
|Embedded databases default to `create-drop`, everything else to `none`. Use `validate` or a migration tool for real schemas.

|`spring.jpa.show-sql`
|`hibernate.show_sql`
|Prints SQL to standard output. Prefer the `org.hibernate.SQL` logger category, which goes through the logging framework.

|`spring.jpa.open-in-view`
|none (a Spring MVC interceptor)
|Controls whether the `EntityManager` stays open for the whole web request. Not a Hibernate setting at all.

|`+spring.jpa.properties.hibernate.*+`
|the same key without the prefix
|Everything Boot does not model, such as `jdbc.batch_size`, `generate_statistics` or `default_batch_fetch_size`.
|===

== Worked example: the same endpoint with open-in-view on, off, and fixed

The running example is a library: `Book` has a lazy `@ManyToOne` `Author`, and a controller returns a list of `title`/`author` pairs. Five books, five authors, and `spring.jpa.properties.hibernate.generate_statistics=true` so the number of JDBC statements can be read back from `SessionFactory.getStatistics()`.

[source,java]
----
@Entity
public class Book {
    @Id @GeneratedValue private Long id;
    private String title;
    @ManyToOne(fetch = FetchType.LAZY) private Author author;
    // constructors and getters omitted
}

public interface BookRepository extends JpaRepository<Book, Long> {
    List<Book> findByTitleContaining(String fragment);

    @EntityGraph(attributePaths = "author")
    List<Book> findWithAuthorByTitleContaining(String fragment);
}

@RestController
public class BookController {
    record BookDto(String title, String author) {}

    private final BookRepository books;

    public BookController(BookRepository books) { this.books = books; }

    @GetMapping("/books")
    List<BookDto> all() {       // no @Transactional on purpose
        return books.findByTitleContaining("").stream()
                .map(b -> new BookDto(b.getTitle(), b.getAuthor().getName())).toList();
    }

    @GetMapping("/books-graph")
    List<BookDto> allGraph() {
        return books.findWithAuthorByTitleContaining("").stream()
                .map(b -> new BookDto(b.getTitle(), b.getAuthor().getName())).toList();
    }
}
----

Calling both endpoints through `MockMvc` and reading `Statistics.getPrepareStatementCount()` after each call gave:

[cols="2,1,3"]
|===
|Endpoint and setting |Statements |What happened

|`/books`, `open-in-view` left at its default (`true`)
|6
|One `select` for the books, then one lazy `select` per author (the N+1 pattern). The response is fine, and the startup log carries a warning that `spring.jpa.open-in-view` is enabled by default.

|`/books`, `spring.jpa.open-in-view=false`
|1
|`LazyInitializationException: Could not initialize proxy [lab.Author#1] - no session`. The persistence context closed when the repository's own transaction ended.

|`/books-graph` (either setting)
|1
|The `@EntityGraph` turns the association into a join, so the author is already loaded when the mapping lambda touches it.
|===

[mermaid]
....
sequenceDiagram
    participant C as Client
    participant F as OpenEntityManagerInViewInterceptor
    participant H as BookController
    participant R as BookRepository
    participant S as Hibernate Session
    C->>F: GET /books
    F->>S: open EntityManager for the whole request
    F->>H: handler invoked
    H->>R: findByTitleContaining
    R->>S: select books (own short transaction)
    S-->>H: Book entities, author proxies still attached
    H->>S: getAuthor().getName() x5 (5 more selects)
    H-->>F: DTO list
    F->>S: close EntityManager
    F-->>C: 200 OK
....

The lesson is that `open-in-view=true` did not make the code correct, it made the failure invisible: the five extra statements ran while the request still held a connection. Setting it to `false` turns the hidden N+1 into an exception in development, and the fix belongs in the repository (an `@EntityGraph`, a `JOIN FETCH` query or a DTO projection, see xref:backend/hibernate/fetching-and-n-plus-1.adoc[Fetching and N+1]), not in a wider session.

== Reading the Hibernate session from Spring-managed code

When a repository method is not enough, inject the `EntityManager` and unwrap Hibernate's own API from it; `Session`, `StatelessSession` (opened from the `SessionFactory` obtained with `emf.unwrap(SessionFactory.class)`) and `Statistics` are all reachable this way:

[source,java]
----
@Service
class LibraryStats {
    private final EntityManagerFactory emf;

    LibraryStats(EntityManagerFactory emf) { this.emf = emf; }

    long statements() {
        return emf.unwrap(SessionFactory.class).getStatistics().getPrepareStatementCount();
    }
}
----

The same unwrapping is what the test above used to read the statement counts, and it is the bridge to every Hibernate-only feature in this section: filters, `StatelessSession` batch jobs, second-level cache statistics and Envers.
