include::partial$ai-disclaimer.adoc[]

xref:backend/hibernate/persistence-context-and-lifecycle.adoc[Persistence Context & Lifecycle] covers the
always-on first-level cache. This page covers the optional, shared second-level cache -- what it holds, the
providers, and the concurrency strategies that decide what happens under concurrent access.

== First-level cache recap

The first-level cache is the persistence context itself: mandatory, in-memory only, scoped to one
`EntityManager`, gone the moment that `EntityManager` closes. The second-level cache is everything the
first-level cache is not: optional, potentially off-heap/distributed, shared across every `EntityManager`
created from one `EntityManagerFactory`, and outlives any single unit of work.

== Second-level cache architecture

Hibernate does not implement caching itself -- it defines an SPI (`org.hibernate.cache.spi.RegionFactory`) and
delegates to a pluggable provider:

[cols="1,2"]
|===
| Provider | Notes

| JCache (`javax.cache`) + Caffeine
| The lightweight, in-process default choice for a single-instance deployment -- Caffeine as the JCache
  implementation behind Hibernate's JCache region factory (`hibernate.cache.region.factory_class=jcache`; the class lives in the
  `hibernate-jcache` module, as `org.hibernate.cache.jcache.internal.JCacheRegionFactory` in ORM 7).

| Infinispan
| A distributed, embeddable or client-server cache -- the JBoss/Red Hat ecosystem's own second-level cache
  provider, supports clustering out of the box.

| Ehcache
| Another long-standing JCache-compatible provider, with optional clustering (Terracotta).

| Redis
| Not a native Hibernate second-level cache provider by default, but reachable via a JCache-compliant Redis
  client or a community region-factory adapter -- worth choosing when the application already runs Redis for
  other caching (see xref:backend/springboot/caching.adoc[Caching]) and wants one shared cache layer instead of
  two; see the xref:database/redis/use-cases-and-patterns.adoc[Redis Use Cases & Patterns] page for this kind of
  caching pattern.
|===

A multi-instance deployment sharing an in-process (Caffeine) second-level cache is a correctness trap: each
instance's cache can silently diverge from what the others just wrote, since there is no cross-instance
invalidation. Prefer a genuinely distributed provider (Infinispan, a shared Redis, Ehcache with clustering) once
more than one application instance is in play.

== `@Cache` and `CacheConcurrencyStrategy`

An entity opts in explicitly -- nothing is cached by default:

[source,java]
----
@Entity
@Cache(usage = CacheConcurrencyStrategy.READ_WRITE, region = "book")
public class Book {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    // ...
}
----

[cols="1,3"]
|===
| Strategy | Behavior

| `READ_ONLY`
| Assumes the entity is never updated after insert -- the simplest, fastest, and safest strategy, since there
  is no update-time invalidation race to reason about. Attempting to update a `READ_ONLY`-cached entity fails
  with `+UnsupportedOperationException: Can't update read-only object+` (reproduced on 7.4.15), and Hibernate
  logs `HHH90001003` at startup when the entity is mapped as mutable; pair `READ_ONLY` with `@Immutable`.

| `NONSTRICT_READ_WRITE`
| Updates evict (rather than update) the cache entry, and there is a small window where a concurrent reader can
  see stale cached data right after an update commits, before eviction is visible everywhere. Acceptable when
  occasional staleness for a brief window is tolerable.

| `READ_WRITE`
| Uses soft locks around updates to prevent readers from ever seeing a stale value across a commit, at the cost
  of more bookkeeping than `NONSTRICT_READ_WRITE`. The right default for entities that are both cached and
  updated with any regularity.

| `TRANSACTIONAL`
| Fully transactional cache semantics (cache changes commit/rollback with the surrounding JTA transaction) --
  needs a cache provider that supports it (Infinispan does); the strongest guarantee, also the most demanding
  on the provider.
|===

`@Cache` also applies to a `@OneToMany`/`@ManyToMany` collection (caching the association's *identifiers*, not
the associated entities' own state, which is cached separately per its own `@Cache` if present), and to
`@NaturalId` lookups via `@NaturalIdCache`.

== The query cache and its pitfalls

The *query cache* caches the *result set of identifiers* a specific query+parameters combination returned, not
the entity data itself (which still comes from the entity/collection second-level cache, or the database if not
cached there). It requires `hibernate.cache.use_query_cache=true` and an explicit
`query.setCacheable(true)`/`@QueryHints(@QueryHint(name = "org.hibernate.cacheable", value = "true"))` per
query -- nothing is query-cached implicitly. The known pitfall: **every query cache region is invalidated
whenever *any* row of *any* table the query touches changes**, regardless of whether that specific change would
have affected this specific query's result -- a query cache region for a frequently-updated table can end up
with a near-zero effective hit rate despite being "enabled," making it a net loss (cache-maintenance overhead
without a corresponding hit-rate benefit). Reserve the query cache for queries against tables that change
rarely.

== `CacheMode` and `SharedCacheMode`

`CacheMode` (per-`Session`, or per-operation) controls how that session's operations interact with the
second-level cache: `NORMAL` (read and write, the default), `GET` (read but never write), `PUT` (write but
never read -- useful for a bulk-loading pass that should populate the cache without being slowed down by
reading it first), `IGNORE` (bypass entirely). `SharedCacheMode` (JPA, set at the persistence-unit level) sets
the default caching *policy* for entities that carry no explicit annotation:
`ENABLE_SELECTIVE` (only `@Cacheable`-annotated entities are cached -- the default and generally the clearest),
`DISABLE_SELECTIVE` (cache everything except entities explicitly marked `@Cacheable(false)`), `ALL`, or `NONE`.

== Cache regions and statistics

Every cached entity/collection/query lives in a named *region* (defaulting to the entity's fully-qualified
class name, overridable via `+@Cache(region = "...")+`), which is also the unit of eviction
(`SessionFactory.getCache().evictEntityData(Book.class)`, `evictRegion("book")`). `hibernate.generate_statistics`
plus `SessionFactory.getStatistics()` exposes hit/miss/put counts per region -- the direct way to check whether
a given cache region is actually earning its keep before assuming it is, per the query-cache pitfall above; see
also xref:backend/hibernate/performance-and-statistics.adoc[Performance & Statistics].

== Worked example: counting hits, misses and invalidation

The experiment uses the section's model: `Book` and `Author` annotated `@Cacheable` with
`@Cache(usage = CacheConcurrencyStrategy.READ_WRITE)`, and `Author.books` cached as a collection. The provider is
Ehcache 3.10.8 through `hibernate-jcache` on Hibernate ORM 7.4.15:

[source,java]
----
Configuration cfg = new Configuration()
    .setProperty("hibernate.cache.use_second_level_cache", "true")
    .setProperty("hibernate.cache.use_query_cache", "true")
    .setProperty("hibernate.cache.region.factory_class", "jcache")
    .setProperty("hibernate.javax.cache.provider", "org.ehcache.jsr107.EhcacheCachingProvider")
    .setProperty("hibernate.javax.cache.missing_cache_strategy", "create")
    .setProperty("hibernate.generate_statistics", "true");
----

Each line below is read from `Statistics` after one unit of work, each in a new session. Without the
`missing_cache_strategy` setting Hibernate logs `HHH90001006` once per region and creates it with the provider's
default policy; the `create` value silences that on purpose, and production setups should instead declare each
region with its own size and expiry.

[cols="3,3,2"]
|===
| Unit of work | Second-level cache | SQL statements

| `find(Book.class, 1L)`, first session
| 1 miss, 1 put
| 1

| the same `find`, second and third session
| 1 hit each
| 0

| `find(Author.class, 1L).getBooks().size()`, first time
| 2 misses (entity, collection)
| 2

| the same call in a new session
| 5 hits (author, collection, three books)
| 0

| cacheable query `from Book b where b.publishedYear > :y`, run three times
| first run: query-cache miss and put; runs two and three: query-cache hit
| 1, then 0, 0
|===

=== How a cached read flows

[mermaid]
....
sequenceDiagram
    participant App
    participant S1 as Session (L1)
    participant L2 as Second-level cache
    participant DB as Database
    App->>S1: find(Book, 1)
    S1->>S1: persistence context lookup
    S1->>L2: get Book#1
    alt hit
        L2-->>S1: dehydrated state
    else miss
        S1->>DB: select ... where id=?
        DB-->>S1: row
        S1->>L2: put Book#1
    end
    S1-->>App: managed Book
....

The cache stores *dehydrated state* (the column values), not entity instances, which is why every hit still
creates a fresh managed object per session.

=== What invalidates what

An entity update commits the new state through the cache strategy: after `s.find(Book.class, 2L).setTitle("Renamed")`
in a transaction, the next execution of the cacheable query was a *miss* and went to the database
(`query cache hits=0 misses=1 puts=1`), even though the renamed book's year had not changed -- the query cache
only knows that the `book` table was touched after its result was cached. This is the pitfall described above,
reproduced.

Bulk statements invalidate regions rather than entries. After each of the following updates of all `book` rows,
the table below shows what the next `find` of `Book#1` and `Author#1` did (both had been cached before):

[cols="3,2,2"]
|===
| Statement | `find(Book, 1)` | `find(Author, 1)`

| HQL `update Book set stock = stock + 1`
| miss, reloaded
| hit

| Native `+update book ...+`, no table declared
| miss, reloaded
| miss, reloaded

| Native update with `addSynchronizedEntityClass(Book.class)`
| miss, reloaded
| hit

| Native update with `addSynchronizedEntityClass(Review.class)` (wrong table declared)
| hit -- *stale data served*
| hit
|===

The last row is the danger: declaring the wrong query space leaves the `Book` region untouched, so the next
read returns the pre-update value from the cache while the database holds the new one.

=== `CacheMode` and the JPA find options

`CacheMode` is honored by queries: with `+session.setCacheMode(...)+` or `+query.setCacheMode(...)+` an HQL query
that loads `Book#3` produced `puts=1` under `NORMAL` and `PUT`, and no put under `IGNORE` and `GET`. A plain
`session.find` in the same run ignored the session's `CacheMode` (it still read and wrote the cache under every
mode). For `find`, use the Jakarta Persistence 3.2 options: `find(Book.class, 3L, CacheStoreMode.BYPASS)`
produced a miss without a put, and `find(Book.class, 3L, CacheRetrieveMode.BYPASS)` skipped the cache read
entirely (no hit, no miss, no put recorded).

=== Reading region statistics

Four reads of the same book, with the region emptied first, left the `demo.Book` region at 3 hits, 1 miss and
1 put:

[source,java]
----
CacheRegionStatistics region = sessionFactory.getStatistics()
        .getDomainDataRegionStatistics("demo.Book");   // region name defaults to the entity name
long hits = region.getHitCount(), misses = region.getMissCount(), puts = region.getPutCount();
sessionFactory.getCache().evictEntityData(Book.class);   // next find is a miss again
boolean cached = sessionFactory.getCache().containsEntity(Book.class, 3L);
----

The run listed these region names: `demo.Author`, `demo.Author.books`, `demo.Book`, `demo.Genre` and
`default-query-results-region` -- one per cached entity and collection plus the shared query-results region.
