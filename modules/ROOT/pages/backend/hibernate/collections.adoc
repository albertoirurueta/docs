= Collections
:description: Mapping collection-valued state with Hibernate -- List/Set/Map/sorted collections, @ElementCollection, ordering annotations, bag vs. list semantics, SQL array columns, and @SortNatural/@SortComparator.
:keywords: Hibernate collections, @ElementCollection, @OrderColumn, @OrderBy, @MapKeyColumn, bag semantics, PersistentBag, SQL array column, @SortNatural, @SortComparator

include::partial$ai-disclaimer.adoc[]

Hibernate wraps every mapped collection field in its own persistent collection implementation
(`PersistentBag`, `PersistentList`, `PersistentSet`, `PersistentMap`) that tracks additions/removals for dirty
checking. This page covers the collection interfaces Hibernate supports, `@ElementCollection` for collections
of non-entity values, and the bag-semantics trade-off that trips up more people than any other collection
detail.

== `List`, `Set`, `Map`, and sorted collections

[cols="1,2"]
|===
| Declared type | Hibernate behavior

| `List<T>` (no `@OrderColumn`)
| Treated as a *bag* -- see below -- unless `@OrderColumn` is present, in which case insertion order is
  persisted in a dedicated index column.

| `Set<T>`
| No duplicates, no defined order (unless `@OrderBy` is added); backed by a `HashSet` (needs correct
  `equals()`/`hashCode()` on the element type) or, with `@SortNatural`/`@SortComparator`, a `TreeSet`.

| `Map<K, V>`
| A key/value association; the key column is declared with `@MapKeyColumn` (a basic key) or `@MapKey` (using
  another entity attribute as the key) or `@MapKeyJoinColumn` (an entity key).

| `SortedSet<T>` / `SortedMap<K, V>`
| Ordered in memory via `@SortNatural` (the elements'/keys' natural ordering) or
  `@SortComparator(MyComparator.class)`. This is *in-memory* Java-side sorting via a `TreeSet`/`TreeMap`, distinct
  from `@OrderBy`, which asks the *database* to `ORDER BY` on select.
|===

== `@ElementCollection`

For a collection of basic values or embeddables that have no identity of their own -- no `@Entity`, just a
value stored in its own table keyed by the owner's foreign key:

[source,java]
----
@Entity
public class Book {
    @ElementCollection
    @CollectionTable(name = "book_tag", joinColumns = @JoinColumn(name = "book_id"))
    @Column(name = "tag")
    private Set<String> tags = new HashSet<>();

    @ElementCollection
    @CollectionTable(name = "book_translation", joinColumns = @JoinColumn(name = "book_id"))
    @MapKeyColumn(name = "locale")
    private Map<String, String> translatedTitles = new HashMap<>();

    @ElementCollection
    @CollectionTable(name = "book_review", joinColumns = @JoinColumn(name = "book_id"))
    private List<Review> reviews = new ArrayList<>();   // Review is an @Embeddable class
}
----

An `@ElementCollection` has no cascading options to configure -- the contained values are always fully owned by
the parent entity (they cannot be shared, referenced from elsewhere, or outlive their owner), so every add/
remove is unconditionally reflected as an `INSERT`/`DELETE` on the collection table.

== `@OrderColumn`, `@OrderBy`, and `+@MapKey*+`

* `@OrderColumn` -- persists a dedicated integer index column and reconstructs a `List` in exactly that order,
  supporting index-based operations (`+list.set(3, ...)+`) without reordering the rest of the table.
* `@OrderBy("title ASC")` -- asks the database to sort on `SELECT`, referencing entity attribute names (not
  column names); the order is not stored anywhere, only applied at read time. Cheaper to write (no index
  column to maintain) but list index operations are not meaningful, since re-fetching can reorder elements if
  the sort key changes.
* `@MapKeyColumn` / `@MapKey` / `@MapKeyJoinColumn` -- the three ways to say what the key of a `Map` comes from: a
  dedicated column value, another attribute of the value entity, or a to-one association used as the key.

== Bag vs. list semantics -- the performance trade-off

A plain `List<T>` with no `@OrderColumn` is a *bag*: an unordered collection that permits duplicates,
represented internally as `PersistentBag`. Bags are the cause of a specific, easy-to-hit runtime error: **a
query cannot `JOIN FETCH` two bags of the same root entity in one query** -- Hibernate cannot tell which rows
of the Cartesian product belong to which parent-collection element once two unordered bags are combined, and
throws `MultipleBagFetchException`. The fixes, in order of preference:

* Change one of the two collections to a `Set` (if duplicates genuinely cannot occur) -- the most common fix.
* Add `@OrderColumn` to make it a true ordered list instead of a bag.
* Fetch the two collections in separate queries (or via `@BatchSize`, see
  xref:backend/hibernate/fetching-and-n-plus-1.adoc[Fetching & N+1]) instead of both in one `JOIN FETCH`.

A `Set` also avoids a related, subtler bag cost: removing one element from a bag that has its own table (a `@ManyToMany` join table or an
`@ElementCollection`) forces Hibernate to delete and re-insert the *entire* collection's rows to preserve
correctness, because a bag has no identity per row to delete selectively -- another reason `Set` (or an ordered
`List` via `@OrderColumn`) is generally the safer default over a bare `List`. An inverse
`+@OneToMany(mappedBy = ...)+` bag has no table of its own and is not affected.

== Mapping to SQL arrays

Where the database and dialect support a native array column type (PostgreSQL's `text[]`, `integer[]`, ...), a
basic collection of a simple element type can map directly to it via `@JdbcTypeCode(SqlTypes.ARRAY)` on a
`String[]`/`Integer[]` field, avoiding a separate `@ElementCollection` table entirely for small, denormalized,
rarely-queried-by-element lists.

== One `Book`, every collection kind, measured

To compare collection mappings on equal terms, a single `Book` entity was given one of each kind and run on
H2 with Hibernate ORM 7.4. The mappings are those of the sections above, plus `@OrderColumn` and a
`@SortNatural` set:

[source,java]
----
@Embeddable
public class Review { String reviewer; int stars; }

@Entity
public class Book {
    @Id @GeneratedValue Long id;
    String title;

    @OneToMany(cascade = CascadeType.ALL) @JoinColumn(name = "book_id")
    List<Chapter> chapters = new ArrayList<>();                        // entity bag

    @OneToMany(cascade = CascadeType.ALL) @JoinColumn(name = "book_ed_id")
    List<Edition> editions = new ArrayList<>();                        // second entity bag

    @ElementCollection @CollectionTable(name = "book_tag", joinColumns = @JoinColumn(name = "book_id"))
    @Column(name = "tag")
    Set<String> tags = new HashSet<>();

    @ElementCollection @CollectionTable(name = "book_keyword", joinColumns = @JoinColumn(name = "book_id"))
    @Column(name = "keyword")
    List<String> keywords = new ArrayList<>();                         // value bag

    @ElementCollection @CollectionTable(name = "book_note", joinColumns = @JoinColumn(name = "book_id"))
    @OrderColumn(name = "pos") @Column(name = "note")
    List<String> notes = new ArrayList<>();                            // true list

    @ElementCollection @CollectionTable(name = "book_review", joinColumns = @JoinColumn(name = "book_id"))
    List<Review> reviews = new ArrayList<>();                          // embeddables

    @ElementCollection @CollectionTable(name = "book_translation", joinColumns = @JoinColumn(name = "book_id"))
    @MapKeyColumn(name = "locale") @Column(name = "translated_title")
    Map<String, String> translatedTitles = new HashMap<>();

    @ElementCollection @CollectionTable(name = "book_sorted_tag", joinColumns = @JoinColumn(name = "book_id"))
    @Column(name = "tag") @SortNatural
    SortedSet<String> sortedTags = new TreeSet<>();

    @JdbcTypeCode(SqlTypes.ARRAY)
    String[] labels;
}
----

The element type of a collection of embeddables is written plainly, `List<Review>`, with `@Embeddable` on
the `Review` class; `@Embeddable` cannot annotate a type argument.

Hibernate replaced each collection field with its own implementation on load:

[source,text]
----
tags     -> PersistentSet
keywords -> PersistentBag
notes    -> PersistentList
sortedTags -> PersistentSortedSet
----

and generated these collection tables (abridged):

[source,text]
----
create table book_keyword (book_id bigint not null, keyword varchar(255))
create table book_tag (book_id bigint not null, tag varchar(255), unique (book_id, tag))
create table book_note (pos integer not null check ((pos>=0)), book_id bigint not null, note varchar(255),
                        primary key (pos, book_id))
create table book_review (stars integer, book_id bigint not null, reviewer varchar(255))
create table book_translation (book_id bigint not null, locale varchar(255) not null,
                               translated_title varchar(255), primary key (book_id, locale))
create table book (id bigint not null, title varchar(255), labels varchar(255) array, primary key (id))
----

The shape of the key is the whole story of collection cost. A `Set` of values gets a `unique` constraint, a
`List` with `@OrderColumn` gets a primary key that includes the position, a `Map` gets one that includes the
key -- and a bag (`keywords`, `reviews`) gets *no key at all*, so Hibernate has no way to address one of its
rows. The `labels` array is a single column, with no collection table.

== What removing one element costs

Starting from three keywords, three tags, three notes and two reviews, removing a single element from each
collection in its own transaction issued:

[cols="2,3"]
|===
| Collection | SQL issued

| `Set<String> tags`, remove `"jpa"`
| `delete from book_tag where book_id=? and tag=?` -- one row.

| `List<String> keywords` (bag), remove the first
| `delete from book_keyword where book_id=?`, then an `insert` for each of the two survivors.

| `List<Review> reviews` (bag of embeddables), remove one of two
| `delete from book_review where book_id=?`, then one `insert` for the survivor.

| `List<String> notes` with `@OrderColumn`, remove the first
| `delete from book_note where book_id=? and pos=?` for the *last* position, then
  `update book_note set note=? where book_id=? and pos=?` for each shifted element.
|===

The ordered list is not free either -- removing near the head shifts every later element with an `update` --
but it never deletes the whole collection. For a large value collection that is edited often, a `Set` (or a
link entity with its own key, see xref:backend/hibernate/associations.adoc[Associations]) is the right
choice; a bag is appropriate only when the collection is small or written once.

== `MultipleBagFetchException`, reproduced

With the two entity bags `chapters` and `editions` on the same root, the query

[source,java]
----
em.createQuery("select b from Book b join fetch b.chapters join fetch b.editions", Book.class)
  .getResultList();
----

failed at query-creation time with `IllegalArgumentException` wrapping
`org.hibernate.loader.MultipleBagFetchException: cannot simultaneously fetch multiple bags`, followed by
the fully qualified names of `Book.chapters` and `Book.editions`. The exception names both collections, and it is raised before any
SQL runs. Switching either collection to a `Set` or adding `@OrderColumn` to it makes the same query legal,
at the price of a Cartesian product between the two collections in the result set; for two large collections
the better answer is two queries (one `join fetch` each) inside the same persistence context, as described in
xref:backend/hibernate/fetching-and-n-plus-1.adoc[Fetching and N+1].

== Maps, sorting and arrays, verified

`translatedTitles` round-tripped as `+{es=Hibernate en la práctica}+` with accented text intact (the key
column `locale` is part of the composite key). `sortedTags`, stored as `z`, `a`, `m`, came back as `[a, m, z]`:
the sorting is done in memory by a `TreeSet`, not by `order by`, so it costs nothing in SQL but requires the
whole collection to be loaded. `labels` came back from the single `varchar array` column as `[x, y]`, which
is why an array column is attractive for small, rarely queried lists and unattractive for anything that must
be filtered by element in SQL.
