= Hibernate Reactive and Data Repositories
:description: Hibernate Reactive's Mutiny.SessionFactory, Vert.x Context binding vs. Reactor Context, transaction handling, bridging Uni/Multi to Mono/Flux, running under Spring WebFlux, Hibernate Data Repositories, and why Hibernate Search does not support Hibernate Reactive.
:keywords: Hibernate Reactive, Mutiny.SessionFactory, Mutiny.Session, withSession, withTransaction, Vert.x Context, Vert.x reactive SQL client, mutiny-reactor, UniReactorConverters, Hibernate Data Repositories, Jakarta Data, HSEARCH-4922

include::partial$ai-disclaimer.adoc[]

Everything else in this section documents blocking Hibernate ORM. This page covers *Hibernate Reactive* -- a
genuinely different, non-blocking execution model -- and *Hibernate Data Repositories*, the Jakarta Data
implementation built on blocking Hibernate ORM. The two are easy to conflate by name; they are unrelated to
each other beyond sharing the Hibernate project.

== Hibernate Reactive fundamentals

Hibernate Reactive offers two async APIs: the recommended, Mutiny-based `Mutiny.SessionFactory`/
`Mutiny.Session`, and a legacy `CompletionStage`-based `Stage.SessionFactory`/`Stage.Session`. This page uses
the Mutiny API throughout, as the reference documentation itself recommends.

Two facts shape everything else on this page:

* Hibernate Reactive requires a genuinely non-blocking **Vert.x reactive SQL client** per database (dedicated
  clients exist for PostgreSQL, MySQL, DB2, SQL Server, Oracle, and CockroachDB) **instead of a JDBC driver** --
  there is no JDBC `DataSource` underneath at all, so none of the connection-pool/`DataSource` configuration
  used elsewhere in this section applies.
* **Spring Data does not support Hibernate Reactive** -- there is no `ReactiveCrudRepository`-style repository
  abstraction for it. Every reactive interaction with Hibernate Reactive goes through the
  `Mutiny.SessionFactory` API directly.

Obtaining the `Mutiny.SessionFactory`: unwrap it from a JPA `EntityManagerFactory` built with the
`org.hibernate.reactive.provider.ReactivePersistenceProvider` persistence provider, then expose it as a Spring
`@Bean`:

[source,java]
----
@Configuration
public class HibernateReactiveConfig {

    @Bean
    public Mutiny.SessionFactory sessionFactory() {
        EntityManagerFactory emf = Persistence.createEntityManagerFactory("library-reactive");
        return emf.unwrap(Mutiny.SessionFactory.class);
    }
}
----

== Accessing the session/entity manager reactively

`Mutiny.SessionFactory` has no standalone "get me a session" call the way blocking Hibernate's
`@PersistenceContext EntityManager em` does. Instead, the session exists only for the duration of a callback's
`Uni`:

[source,java]
----
// read / non-transactional work
public Uni<Book> findBook(Long id) {
    return sessionFactory.withSession(session -> session.find(Book.class, id));
}

// transactional work -- see "Transaction handling" below
public Uni<Order> placeOrder(Order order) {
    return sessionFactory.withTransaction((session, tx) ->
            session.persist(order).chain(session::flush).replaceWith(order));
}
----

`withSession(Function<Mutiny.Session, Uni<T>> work)` opens (or reuses) a `Mutiny.Session` for the duration of
`work`, returning the `Uni<T>` the callback produces. `withTransaction(BiFunction<Mutiny.Session,
Mutiny.Transaction, Uni<T>> work)` does the same within a transaction. A nested `withSession`/`withTransaction`
call made from inside an already-open one reuses the same session rather than opening a second one -- calling
`withTransaction` again inside an outer `withTransaction` block joins the existing transaction/session instead
of nesting a new one.

== How the session is bound to the current unit of work -- and why this differs from Reactor

This is the detail every other page in this section's cross-linked
xref:backend/springboot/reactive-programming.adoc[Reactive Programming] page does **not** prepare you for.
Per https://docs.hibernate.org/reactive/[the Hibernate Reactive reference documentation], `withSession()`/
`withTransaction()` associate the reactive session with **the current Vert.x (duplicated) `Context`** -- *not*
a Reactor `Context`, and *not* a `ThreadLocal`. Every operation on an open session then runs on the event-loop
thread that context belongs to. Called from a thread that is not an event loop (a JUnit `main` thread, a Reactor
scheduler thread), `withSession()`, `withTransaction()` and `openSession()` hop onto a Vert.x context themselves:
a `withSession` callback invoked from `main` reported `vert.x-eventloop-thread-0` as its thread when run against
Hibernate Reactive 4.5.14, so the entry points are safe to call from anywhere. What is *not* safe is handing an
already-open `Mutiny.Session` to another thread. Using a session from a thread other than the one that opened it
fails fast with:

[source]
----
HR000069: Detected use of the reactive Session from a different Thread than the one which was used to open
the reactive Session - this suggests an invalid integration
----

(`HR000068`, "This method should exclusively be invoked from a Vert.x EventLoop thread", is the companion check
that guards session operations and connection acquisition. Both checks can be switched off with the system
property `org.hibernate.reactive.common.InternalStateAssertions.ENFORCE=false`; with it set, the cross-thread
call above succeeded, which makes it a debugging aid for a suspected false positive, not a fix for a real
threading mistake.)

Contrast this directly with
xref:backend/springboot/reactive-programming.adoc#reactive-transactions-and-thread-affinity[Reactive
transactions and thread affinity], which documents how Spring's own `ReactiveTransactionManager` rides the
**Reactor** `Context` instead -- state that survives thread hops, scoped to one unit of work rather than one
thread. The two mechanisms *look* similar at that level of description, but they are two entirely independent
context-propagation systems that share no state whatsoever. A Reactor pipeline calling into Hibernate Reactive
crosses a real context boundary at that call, even though no explicit `.subscribe()` is written there -- the
"don't break the chain" rules on that page are about *Reactor's own* `Context` and say nothing, by themselves,
about the *Vert.x* `Context` Hibernate Reactive needs to already be present.

== Transaction handling

`+withTransaction((session, tx) -> ...)+` demarcates the transaction **programmatically, not declaratively**: it
begins a transaction, runs the callback, and commits when the returned `Uni` completes successfully, or rolls
back if it completes with a failure -- including an exception thrown synchronously inside the callback.
Conceptually this is the Mutiny counterpart of `+TransactionalOperator.transactional(...)+`
(xref:backend/springboot/reactive-programming.adoc#reactive-transactions-and-thread-affinity[Reactive
transactions and thread affinity]), but **there is no `ReactiveTransactionManager` implementation for Hibernate
Reactive**, and Spring's declarative `@Transactional` on a method returning a `Publisher` does **not** apply to
it -- `withTransaction` is the only transaction-demarcation mechanism available.

[source,java]
----
public Uni<Order> placeOrder(Order order) {
    return sessionFactory.withTransaction((session, tx) ->
            session.persist(order).chain(session::flush).replaceWith(order));
}
----

== Bridging `Uni`/`Multi` to `Mono`/`Flux`

The `io.smallrye.reactive:mutiny-reactor` Maven artifact (see
https://smallrye.io/smallrye-mutiny/guides/converters/[the SmallRye Mutiny "Using other reactive programming
libraries" guide]) provides `UniReactorConverters`/`MultiReactorConverters` for the Hibernate-Reactive-to-Spring
direction:

[source,java]
----
public Mono<Book> findBookReactor(Long id) {
    Uni<Book> uni = sessionFactory.withSession(session -> session.find(Book.class, id));
    return uni.convert().with(UniReactorConverters.toMono());
}

public Flux<Book> allBooksReactor() {
    return sessionFactory.withSession(session ->
                    session.createSelectionQuery("from Book", Book.class).getResultList())
            .convert().with(UniReactorConverters.<List<Book>>toMono())
            .flatMapMany(Flux::fromIterable);
}
----

Convert the single `Uni<List<Book>>` with `toMono()` and fan it out with `flatMapMany`. The alternative of turning
the `Uni` into a `Multi` with `+onItem().transformToMulti(...)+` inside the same chain and calling
`MultiReactorConverters.toFlux()` looks equivalent, but in a run against Hibernate Reactive 4.5.14 and
PostgreSQL 17 it failed with error `HR000088` ("Expected to use the object `SqlClientConnection` on context X but was Y")
as soon as a pooled connection had been used by an earlier call, whereas the `Mono`-based form succeeded in the
same circumstances.

For the reverse direction (Reactor to Mutiny), plain Reactive-Streams interop needs no extra dependency:
`Uni.createFrom().publisher(mono)` / `Multi.createFrom().publisher(flux)`.

**The bridge converts only the *value* stream** -- it does **not** carry Reactor `Context` into the Mutiny side
or vice versa (per the context-boundary point above). Anything read from Reactor `Context` upstream of the
conversion must be passed into the Hibernate Reactive call explicitly, as a method parameter -- never assumed
to cross the bridge implicitly.

== Running under Spring WebFlux specifically

The Vert.x `Context` requirement is independent of which HTTP server WebFlux uses. Spring WebFlux's default
Reactor Netty server does not itself provide a Vert.x event loop. When Hibernate Reactive finds no Vert.x instance
it starts its own (it logs `HR000002: Vert.x not detected, creating a new instance`), and `withSession`/
`withTransaction` hop onto it, so a WebFlux application works without any Vert.x code of its own. Embedding an
explicit `io.vertx.core.Vertx` bean (and running calls with `vertx.getOrCreateContext()` /
`+Vertx.currentContext().runOnContext(...)+`) is still the better choice in production, because it makes the
number of event loops, the shutdown order and the metrics of that Vert.x instance the application's decision
instead of a hidden default.

https://quarkus.io/guides/hibernate-reactive[Quarkus's Hibernate Reactive guide] is worth mentioning only as a
contrast: Quarkus wires this automatically because it runs on Vert.x natively. This section does not use
Quarkus as part of its own stack -- owning the Vert.x instance explicitly, as described above, is a choice a
Spring WebFlux application makes for itself, where a Quarkus application gets it from the framework.

== Hibernate Data Repositories

Separately from Hibernate Reactive, Hibernate ORM 7 implements the *Jakarta Data* `@Repository` model:
implementations generated at compile time by `HibernateProcessor`, using `@Find`/`@Query`/`@HQL`/`@SQL`
annotated methods, backed by `StatelessSession`.

[source,java]
----
@Repository
public interface BookRepository {
    @Find
    List<Book> findByAuthorName(String authorName);

    @HQL("from Book where publishedYear > :year")
    List<Book> recentBooks(int year);
}
----

State plainly: **this is the blocking-Hibernate-ORM Jakarta Data implementation, not Hibernate Reactive** -- it
runs on `StatelessSession` over a normal JDBC connection, with none of the Vert.x-Context requirements above.
It differs in intent from Spring Data JPA in that Jakarta Data is a specification-level, provider-agnostic
repository model (any Jakarta Data provider could implement `BookRepository` above), whereas Spring Data JPA's
`JpaRepository` is Spring-specific and Hibernate/JPA-specific by design.

== Hibernate Search does not support Hibernate Reactive

Per the Hibernate team, `hibernate-search-mapper-orm` does not work with Hibernate Reactive, and there is no
officially supported or planned reactive Hibernate Search integration -- tracked as the still-open feature
request https://hibernate.atlassian.net/browse/HSEARCH-4922[HSEARCH-4922], with no committed timeline (see also
https://discourse.hibernate.org/t/integration-with-hibernate-reactive/6868[the Hibernate team's own confirmation
on the Hibernate community forum]).

For full-text search from a Hibernate-Reactive-based service, call Elasticsearch/OpenSearch **directly** with a
non-blocking client instead of going through Hibernate Search's ORM mapper -- see
xref:backend/hibernate/hibernate-search-backends.adoc[Hibernate Search Backends] (explicitly noting it is
blocking-Hibernate-only) and xref:backend/springboot/elasticsearch.adoc[Elasticsearch] for the reactive
Elasticsearch client / Spring Data Elasticsearch reactive path.

== Worked example: Book and Author on PostgreSQL with Hibernate Reactive

The following was run against **Hibernate Reactive 4.5.14.Final** (which resolves Hibernate ORM 7.4.14.Final and Vert.x 5.1.10 transitively), the Vert.x PostgreSQL client in the same 5.1.10 line, and a `postgres:17-alpine` container. The Vert.x client version must match the `vertx-core` that Hibernate Reactive resolves: pairing `vertx-pg-client` 5.2.x with `vertx-core` 5.1.x failed at startup with `ServiceConfiguration io.vertx.sqlclient.spi.Driver: io.vertx.pgclient.spi.PgDriver Unable to get public no-arg constructor`.

[source,xml]
----
<dependency>
    <groupId>org.hibernate.reactive</groupId>
    <artifactId>hibernate-reactive-core</artifactId>
    <version>4.5.14.Final</version>
</dependency>
<dependency>
    <groupId>io.vertx</groupId>
    <artifactId>vertx-pg-client</artifactId>
    <version>5.1.10</version>
</dependency>
<dependency>
    <groupId>io.smallrye.reactive</groupId>
    <artifactId>mutiny-reactor</artifactId>
    <version>3.3.1</version>
</dependency>
----

The persistence unit names the reactive provider and keeps the standard `+jakarta.persistence.jdbc.*+` keys. Hibernate Reactive never opens a JDBC connection: the URL is only parsed to configure the Vert.x client:

[source,xml]
----
<persistence-unit name="library-reactive">
  <provider>org.hibernate.reactive.provider.ReactivePersistenceProvider</provider>
  <class>lab.Author</class>
  <class>lab.Book</class>
  <properties>
    <property name="jakarta.persistence.jdbc.url" value="jdbc:postgresql://localhost:5432/library"/>
    <property name="jakarta.persistence.jdbc.user" value="library"/>
    <property name="jakarta.persistence.jdbc.password" value="changeit"/>
    <property name="jakarta.persistence.schema-generation.database.action" value="drop-and-create"/>
  </properties>
</persistence-unit>
----

The entities are the blocking pages' `Book` and `Author` (a lazy `@ManyToOne` from book to author, no Hibernate Search annotations, since Hibernate Search does not run on Hibernate Reactive). A small helper runs a `Uni`-returning block on a Vert.x context and waits for it, which is how a plain JUnit test stands in for a Vert.x handler:

[source,java]
----
static Vertx vertx = Vertx.vertx();
static Context ctx = vertx.getOrCreateContext();

static <T> T onVertx(Supplier<Uni<T>> work) throws Exception {
    CompletableFuture<T> f = new CompletableFuture<>();
    ctx.runOnContext(v -> work.get().subscribe().with(f::complete, f::completeExceptionally));
    return f.get(30, TimeUnit.SECONDS);
}
----

Then the interesting cases, each followed by what it printed:

[source,java]
----
// 1. write in a transaction, read in a session
Long id = onVertx(() -> sf.withTransaction((s, tx) -> {
    Author a = new Author("Joshua Bloch");
    Book b = new Book("Effective Java", a);
    return s.persist(a).chain(() -> s.persist(b)).replaceWith(b);
}).map(Book::getId));                                   // persisted book id=1

// 2. a lazy association must be fetched explicitly, inside the session
String author = onVertx(() -> sf.withSession(s -> s.find(Book.class, id)
        .chain(b -> Mutiny.fetch(b.getAuthor()))).map(Author::getName));   // Joshua Bloch

// 3. touching the proxy after the session closed
onVertx(() -> sf.withSession(s -> s.find(Book.class, id)).map(b -> b.getAuthor().getName()));
// LazyInitializationException: Could not initialize proxy [lab.Author#1] - no session

// 4. failure inside withTransaction rolls everything back
onVertx(() -> sf.withTransaction((s, tx) -> s.persist(new Book("Rolled back", null))
        .chain(s::flush).chain(() -> Uni.createFrom().failure(new IllegalStateException("boom")))));
// afterwards: select count(b) from Book b where b.title = 'Rolled back'  ->  0

// 5. a nested withTransaction joins the outer one
onVertx(() -> sf.withTransaction((outer, tx) ->
        sf.withTransaction((inner, tx2) -> Uni.createFrom().item(outer == inner))));   // true
----

Case 3 is the reactive version of the classic lazy-loading mistake, and the cure is the one blocking Hibernate uses (fetch inside the unit of work), spelled `+Mutiny.fetch(...)+` instead of an implicit proxy load, since a lazy load cannot block an event loop. Case 4 shows the all-or-nothing contract: the persist was flushed (the `INSERT` really ran) and the later failure still left no row behind.

== Hibernate Data Repositories in practice

A Jakarta Data repository is an interface: the Hibernate Processor annotation processor generates its implementation at compile time as `BookRepository_`, and the generated class takes a `StatelessSession` in its constructor. The example below was compiled and run with `org.hibernate.orm:hibernate-processor` 7.4.15.Final configured as an annotation processor and `jakarta.data:jakarta.data-api` 1.0.1 on H2 2.4.240:

[source,xml]
----
<plugin>
    <groupId>org.apache.maven.plugins</groupId>
    <artifactId>maven-compiler-plugin</artifactId>
    <configuration>
        <annotationProcessorPaths>
            <path>
                <groupId>org.hibernate.orm</groupId>
                <artifactId>hibernate-processor</artifactId>
                <version>7.4.15.Final</version>
            </path>
        </annotationProcessorPaths>
    </configuration>
</plugin>
----

[source,java]
----
@Repository
public interface BookRepository extends CrudRepository<Book, Long> {

    @Find
    List<Book> byAuthor(String authorName);                 // parameter name must match an entity attribute

    @Find
    Page<Book> byAuthorPaged(String authorName, PageRequest pageRequest, Order<Book> order);

    @Find
    Optional<Book> byTitle(String title);

    @Query("where publishedYear > :year order by title")    // Jakarta Data Query Language
    List<Book> recentBooks(int year);

    @Query("select count(this) from Book where authorName = :author")
    long countByAuthor(String author);
}
----

[source,java]
----
try (StatelessSession ss = sessionFactory.openStatelessSession()) {
    BookRepository repo = new BookRepository_(ss);
    ss.getTransaction().begin();
    repo.insert(new Book("Effective Java", "Joshua Bloch", 2018));
    repo.insert(new Book("Java Puzzlers", "Joshua Bloch", 2005));
    repo.insert(new Book("Java Concurrency in Practice", "Brian Goetz", 2006));
    repo.insert(new Book("Hibernate in Action", "Joshua Bloch", 2004));
    ss.getTransaction().commit();

    repo.byAuthor("Joshua Bloch");   // [Effective Java, Java Puzzlers, Hibernate in Action]
    repo.recentBooks(2005);          // [Effective Java, Java Concurrency in Practice]
    repo.countByAuthor("Joshua Bloch");   // 3

    Page<Book> page1 = repo.byAuthorPaged("Joshua Bloch", PageRequest.ofSize(2), Order.by(Sort.asc("title")));
    // [Effective Java, Hibernate in Action], hasNext = true
    Page<Book> page2 = repo.byAuthorPaged("Joshua Bloch", page1.nextPageRequest(), Order.by(Sort.asc("title")));
    // [Java Puzzlers]
}
----

Three details are worth knowing. The repository methods run inside whatever transaction the `StatelessSession` has open, so transaction demarcation stays the caller's job (a container or Spring would supply it). Because the session is stateless there is no persistence context: no dirty checking, no first-level cache, and lazy associations on returned entities are not initialized. And `Page`/`PageRequest`/`Order`/`Sort` are Jakarta Data types, so the same method signature compiles against any other Jakarta Data provider; the Hibernate-specific `@HQL` and `@SQL` annotations shown earlier trade that portability for HQL features the portable query language does not have.
