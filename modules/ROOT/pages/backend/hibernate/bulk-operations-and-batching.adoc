= Bulk Operations and Batching
:description: JDBC statement batching with Hibernate, StatelessSession for ETL-style work, bulk HQL UPDATE/DELETE/INSERT-SELECT, the flush/clear loop pattern for large imports, and why bulk HQL bypasses the persistence context.
:keywords: Hibernate batching, hibernate.jdbc.batch_size, ordered inserts, StatelessSession, bulk HQL update delete, INSERT SELECT, flush clear loop, second-level cache bypass

include::partial$ai-disclaimer.adoc[]

Loading, mutating, and flushing entities one at a time through the persistence context does not scale to
imports/exports touching thousands or millions of rows. This page covers the mechanisms built for that case.

== JDBC batching

`hibernate.jdbc.batch_size` groups consecutive, same-shape `INSERT`/`UPDATE`/`DELETE` statements into a single
JDBC batch round-trip instead of one round-trip per statement:

[source,yaml]
----
hibernate.jdbc.batch_size: 50
hibernate.order_inserts: true    # groups same-table inserts together even if interleaved with other entities
hibernate.order_updates: true    # same, for updates
----

One condition silently disables insert batching for an entity even with `batch_size` set:
`GenerationType.IDENTITY` (the id must come back from the database right after each insert, so each row is sent
on its own -- see xref:backend/hibernate/entities-and-identifiers.adoc[Entities and Identifiers]). Versioned
entities (`@Version`) are batched by default; `hibernate.jdbc.batch_versioned_data` (default `true`) exists only
for old JDBC drivers whose batch update counts are unreliable and can be switched off for those. `order_inserts`/
`order_updates` matter because Hibernate can only batch *consecutive* same-table statements -- interleaving
inserts to two different tables (one `Book`, one `Author`, one `Book`, ...) defeats batching unless reordered
first.

== `StatelessSession` for ETL-style work

xref:backend/hibernate/architecture.adoc[Architecture] introduces `StatelessSession`: no persistence context,
no first-level cache, no automatic dirty checking, no cascading. Every operation is an immediate, individual
statement, and entities it returns are already detached:

[source,java]
----
try (StatelessSession session = sessionFactory.openStatelessSession()) {
    Transaction tx = session.beginTransaction();
    try (ScrollableResults<Book> results = session.createQuery("FROM Book", Book.class)
            .scroll(ScrollMode.FORWARD_ONLY)) {
        while (results.next()) {
            Book book = results.get();
            book.setOutOfPrint(true);
            session.update(book); // explicit -- no dirty checking to rely on
        }
    }
    tx.commit();
}
----

`StatelessSession` trades away every convenience a normal `Session` provides in exchange for predictable,
constant-memory behavior regardless of how many rows are processed -- exactly the profile a large batch job
wants, and the reason it, rather than a regular `Session` with periodic `clear()` calls, is often the first
choice for genuinely large (multi-million-row) jobs.

== Bulk HQL `UPDATE`/`DELETE`/`+INSERT ... SELECT+`

For a single mass mutation, a bulk HQL statement is far cheaper than loading every row into the persistence
context to mutate it there:

[source,java]
----
int updated = em.createQuery("UPDATE Book b SET b.outOfPrint = true WHERE b.publishedYear < :year")
        .setParameter("year", 1990)
        .executeUpdate();

int deleted = em.createQuery("DELETE FROM Book b WHERE b.outOfPrint = true AND b.stock = 0")
        .executeUpdate();

int inserted = em.createQuery("""
        INSERT INTO ArchivedBook (id, title)
        SELECT b.id, b.title FROM Book b WHERE b.outOfPrint = true
        """).executeUpdate();
----

== Why bulk HQL bypasses the persistence context and second-level cache

A bulk `UPDATE`/`DELETE` is translated directly into one SQL statement and executed against the database --
**it never loads, touches, or updates any already-managed entity instance's in-memory state**, and it cannot
update second-level cache entries row by row because it does not know which rows matched. Two consequences that
surprise people:

* If an entity matching the bulk statement's `WHERE` clause is *already managed* in the current persistence
  context, that in-memory instance now silently disagrees with the database -- its fields still hold the
  pre-bulk-update values until something re-reads it (`refresh()`, or a fresh `find()` after `clear()`).
* If second-level caching is enabled for the affected entity (see
  xref:backend/hibernate/second-level-cache.adoc[Second-Level Cache]), Hibernate invalidates the affected
  entity's cache regions after a bulk HQL statement, so the next `find` goes to the database and re-populates
  the cache. A native SQL mutation is opaque: unless the tables are declared with
  `addSynchronizedEntityClass`/`addSynchronizedQuerySpace`, Hibernate invalidates *every* region (measured on
  7.4.15: with no declaration the `Author` region was emptied by an update of `book`; with the `Book` space
  declared it was not).

For this reason, run a bulk statement at the start of a unit of work (before anything relevant has been
loaded) or immediately `clear()` the persistence context afterward if related entities might already be
managed.

== The `flush()`/`clear()` loop pattern

For a large import processed through a normal, stateful `Session` (rather than `StatelessSession`), the
standard pattern periodically flushes and clears to bound memory and keep dirty-checking cost from growing
without limit as the persistence context accumulates entities:

[source,java]
----
int batchSize = 50;
for (int i = 0; i < records.size(); i++) {
    Book book = mapToEntity(records.get(i));
    em.persist(book);

    if (i % batchSize == 0 && i > 0) {
        em.flush(); // send pending INSERTs to the database
        em.clear(); // detach everything -- release memory, reset dirty-checking cost to zero
    }
}
----

Without periodic `clear()`, the persistence context grows by one entity per iteration for the whole import,
and every later flush has to dirty-check the entire, ever-growing set of managed entities -- a quadratic cost
in the number of records processed that `StatelessSession` sidesteps entirely by never accumulating state in
the first place.

== Worked example: 200 inserts, counted

All figures come from `Statistics.getPrepareStatementCount()` on Hibernate ORM 7.4.15 and H2, loading 200 `Book`
rows for one `Author` in a single transaction. Sequence-based ids (the default `@GeneratedValue` on this
model) are used except where noted.

[cols="3,1,3"]
|===
| Configuration | Prepared statements | Notes

| No batching (`hibernate.jdbc.batch_size` unset)
| 207
| Essentially one prepared statement per inserted row (201 entity inserts).

| `batch_size=50`, `order_inserts=true`
| 8
| Inserts are sent in batches of 50 rows, so the statement count no longer grows with the row count.

| `batch_size=50` with `GenerationType.IDENTITY` ids (separate `LogEntry` entity, 200 rows)
| 200
| Batching is defeated: each insert must return its generated key immediately.

| `StatelessSession.insertMultiple(200 books)` with `batch_size=50`
| 10
| One batched statement per 50 rows, no persistence context involved.
|===

[mermaid]
....
sequenceDiagram
    participant App
    participant PC as Persistence context
    participant Act as ActionQueue
    participant JDBC
    App->>PC: persist(book 1..50)
    PC->>Act: queue 50 inserts
    App->>PC: flush()
    Act->>JDBC: addBatch x 50, then executeBatch
    App->>PC: clear()
    Note over PC: managed entities back to 0
    App->>PC: persist(book 51..100)
....

=== The flush/clear loop bounds memory

Persisting 120 books in a loop with `flush(); clear();` every 50 inserts ended with 20 managed entities in the
persistence context (the books since the last clear); the same 120 persists without `clear()` ended with all 120
managed. In a real import the second number grows with the file, and so does the cost of every flush. After
`clear()`, any entity reference you still hold (the `Author` in the loop above) is detached; re-attach it with
`session.getReference(Author.class, id)` instead of reading it again.

=== `StatelessSession` in detail

`StatelessSession` batches only the multi-row operations. Updating 200 books by scrolling and calling
`update(book)` on each prepared 201 statements (one select plus 200 updates, none batched), while loading the
same books into a list and calling `updateMultiple(books)` prepared 1 statement. Prefer the `+*Multiple+`
variants (`insertMultiple`, `updateMultiple`, `deleteMultiple`, `upsertMultiple`) whenever the entities fit in
memory in chunks:

[source,java]
----
try (StatelessSession session = sessionFactory.openStatelessSession()) {
    session.beginTransaction();
    List<Book> chunk = session.createQuery("from Book where publishedYear = 1999", Book.class).getResultList();
    for (Book book : chunk) {
        book.setOutOfPrint(false);
    }
    session.updateMultiple(chunk);      // 1 prepared statement for 200 rows
    session.getTransaction().commit();
}
----

Because there is no persistence context, changing a loaded entity does nothing until it is handed to
`update`/`updateMultiple`, and lazy associations cannot be initialized later: fetch what you need in the query.

=== The stale-instance trap, observed

Loading a book, running `+update Book set outOfPrint = true where isbn = 'sl-1'+` and reading the book again in the
same session still reported `outOfPrint = false`; `refresh(book)` then reported `true`. The same sequence with
the update run before the book is loaded needs no `refresh`.

=== `+INSERT ... SELECT+`

`insert into ArchivedBook (id, title) select b.id, b.title from Book b where b.outOfPrint = true` copied the
six matching rows in one statement and returned `6`; nothing was loaded into the persistence context. The target
entity must be a mapped entity; both sides of the statement are written in terms of entity attributes, not
columns.
