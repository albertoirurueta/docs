= What Changed and Migration
:description: A consolidated list of what changed in Terraform and its ecosystem since the books of the 2024 and 2025 era: Terraform minor releases 1.10 to 1.17 with their deprecations and upgrade notes, provider majors (AWS 6, Google 7 and 8, AzureRM 4 and 5, Docker 4, Kubernetes 3, Helm 3), Terraform Cloud becoming HCP Terraform, the CDK for Terraform archival, DynamoDB locking giving way to use_lockfile, tfsec moving to Trivy, GitHub Actions majors, and the licensing timeline, with a migration checklist.
:keywords: Terraform, OpenTofu, upgrade, migration, deprecation, removal, changelog, 1.10, 1.11, 1.12, 1.13, 1.14, 1.15, 1.16, 1.17, AWS provider 6, Google provider 8, AzureRM 5, HCP Terraform, CDKTF, use_lockfile, DynamoDB, tfsec, Trivy, BSL, MPL-2.0, setup-terraform, Terraform Policy, Bookshelf

include::partial$terraform-disclaimer.adoc[]

Infrastructure code outlives the tutorials it was copied from. A configuration written from a book published in 2024 or
early 2025 still mostly works, but the tool around it has moved on: the language gained ephemeral values and actions, the
S3 backend stopped needing a lock table, the providers shipped new major versions, Terraform Cloud changed its name, a
whole alternative interface was archived and the free security scanner was folded into another product. This page
collects those changes in one place, with the version or date at which each happened, and says what to do about each.

The baseline is **Terraform 1.17** (1.17.0 was released on 2026-10-21) and **OpenTofu 1.13** (1.13.0 was released on
2026-09-30). The two books the section draws on were written against Terraform about 1.9 and OpenTofu about 1.8 (Hafner,
2025, with `hashicorp/aws` at `+~> 5.0+`) and against Terraform 1.4 to 1.8 with `hashicorp/google` pinned to exactly 5.38.0
(Wang, 2024); both eras therefore end just before the 1.10 release of 2024-11-27. Every date below was checked on the
official release pages, changelogs or registry on 2026-10-24, and what could not be confirmed is worded cautiously. The
page is the last stop of the reading path: each row links to the page of this section that explains the topic in depth,
for example xref:backend/terraform/state.adoc[State], xref:backend/terraform/backends-and-remote-state.adoc[Backends and Remote State]
and xref:backend/terraform/opentofu.adoc[OpenTofu].

| 1.13
| 2025-08-20

| 1.14
| 2025-11-19

| 1.15

| 1.16
| 2026-08-26
| `import` blocks inside modules. The `store` block of `terraform_data`. Action triggers get `on_failure` (`halt`, `taint` or `continue`) and actions get `before_destroy` and `after_destroy`. `state show -json`. `bastion_host_key` is now correctly applied by provisioners, so review the configured key before upgrading.

== Migrating S3 locking from DynamoDB to use_lockfile

The Bookshelf state lives in an S3 bucket. A book-era backend declares a DynamoDB table; the current one uses a lock
file next to the state object. The migration is done in two steps so that both lock sources protect the state during the
transition.

[source,hcl]
----
terraform {
  required_version = ">= 1.11"

  backend "s3" {
    bucket       = "bookshelf-tfstate-example"
    key          = "prod/network/terraform.tfstate"
    region       = "eu-west-1"
    encrypt      = true
    use_lockfile = true

    # Step 1: keep the old table while every pipeline moves to the new CLI.
    # dynamodb_table = "bookshelf-tf-locks"
  }
}
----

Source: https://developer.hashicorp.com/terraform/language/backend/s3[Terraform Docs -- S3 backend].

Run `terraform init -reconfigure` after changing the backend block; the state itself does not move. Once every runner uses
a version that supports `use_lockfile`, remove the `dynamodb_table` argument and, later, the table. The changelog states
that while both are configured locks are taken from both sources. Native locking needs conditional writes on the bucket;
whether an S3-compatible store such as a local emulator supports them is not documented in the pages consulted, so test
before relying on it. OpenTofu added native S3 locking in its 1.10 line; see
xref:backend/terraform/opentofu.adoc[OpenTofu].

The safe upgrade procedure is the same for every provider. First upgrade to the last release of the previous major and
run a plan with no unexpected changes and no deprecation warnings; then raise the constraint, run
`terraform init -upgrade`, and review the plan before applying. The dependency lock file records the chosen version, so
commit the resulting `.terraform.lock.hcl` change on its own.

[source,hcl]
----
terraform {
  required_version = ">= 1.17"

  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 6.0"
    }
    google = {
      source  = "hashicorp/google"
      version = "~> 8.0"
    }
    azurerm = {
      source  = "hashicorp/azurerm"
      version = "~> 5.0"
    }
    docker = {
      source  = "kreuzwerker/docker"
      version = "~> 4.0"
    }
  }
}
----

== Terraform Cloud becomes HCP Terraform

Both books say "Terraform Cloud". HashiCorp renamed it HCP Terraform on 2024-04-22. The CLI block that connects to it is
still called `cloud`, the environment variables keep their `TF_CLOUD_` prefix, and the provider is still `hashicorp/tfe`
(0.82.0 on 2026-10-23). What did change is commercial: the legacy member-based Free plan ended on 2026-03-31, and
organizations moved to the enhanced Free tier, which allows up to 500 managed resources at no charge and is billed per
managed resource beyond that. Hafner's chapter 8 pricing and limits are therefore outdated. Terraform Enterprise moved to
semantic versions: the monthly scheme ended at `v202507-1`, and the 2.0.x line is the newest, with 2.0.8
(2026-09-23) as its latest patch release.

Source: https://developer.hashicorp.com/terraform/cloud-docs[Terraform Docs -- HCP Terraform],
https://www.hashicorp.com/blog/continuing-hcp-terraform-s-enhanced-free-tier-experience[HashiCorp -- Continuing HCP Terraform's enhanced Free tier experience] and
https://registry.terraform.io/providers/hashicorp/tfe/latest[hashicorp/tfe on the Registry] and
https://developer.hashicorp.com/terraform/enterprise/releases/2.0.x[Terraform Enterprise 2.0.x releases].

See xref:backend/terraform/hcp-terraform-and-enterprise.adoc[HCP Terraform and Enterprise] and
xref:backend/terraform/terraform-stacks.adoc[Terraform Stacks].

== CDK for Terraform

The README of the `hashicorp/terraform-cdk` repository announced that CDKTF would sunset and be archived on
2025-12-10, after which HashiCorp would no longer maintain or develop it. The repository is archived on GitHub today (last
push 2025-12-10). The precise wording is therefore "sunset and archived", not merely "deprecated": the code stays
available read-only under the MPL, with no further fixes or compatibility updates, and the README suggests community
forks. The documented migration path is to generate HCL from the project:

[source,bash]
----
cdktf synth --hcl
terraform init
terraform plan
----

Source: https://github.com/hashicorp/terraform-cdk[hashicorp/terraform-cdk on GitHub].

The generated files need review and tidying before they are good HCL. For programmatic access to Terraform, the
supported route is the JSON output and the machine-readable UI described in
xref:backend/terraform/machine-readable-output-and-integrations.adoc[Machine-Readable Output and Integrations].

== tfsec to Trivy

The README of `aquasecurity/tfsec` announces a migration to Trivy: Trivy natively supports Terraform scanning with the
engine tfsec laid the foundations for, and the project encourages tfsec users to move. It also says tfsec "will continue
to remain available for the time being" while engineering attention goes to Trivy; the repository is not archived as of
2026-10-24. In a pipeline, replace the tfsec step by `trivy config`, and review severity filters and ignore comments,
because the rule identifiers and ignore syntax are not guaranteed to be identical. See
xref:backend/terraform/code-quality-and-security-scanning.adoc[Code Quality and Security Scanning].

Source: https://github.com/aquasecurity/tfsec[aquasecurity/tfsec on GitHub].

== Terraform Policy maturity

Terraform Policy is a case where two official sources differ, and both statements are accurate as of 2026-10-24. The
1.17.0 changelog (2026-10-21) says Terraform Policy is now generally available and that the `-policies` flag for `plan`,
`apply` and `query` no longer requires an experimental build or the `-allow-experimental-features` flag. The
documentation pages of the policy reference still carried a beta label and the usual warning against using beta features
in production when the section was written. Until the documentation catches up, treat the CLI behaviour as generally
available, the documentation as the more cautious statement, and verify the status on the policy documentation before
making it a gate in production. See xref:backend/terraform/policy-as-code.adoc[Policy as Code].

Source: https://github.com/hashicorp/terraform/blob/v1.17/CHANGELOG.md[Terraform v1.17 CHANGELOG] and

== GitHub Actions majors

The CI examples of this section use `actions/checkout@v7` and `hashicorp/setup-terraform@v4`, and
`opentofu/setup-opentofu@v2`. These are the majors shown in the READMEs of those repositories on 2026-10-24
(latest releases: checkout v7.0.1 on 2026-07-20, setup-terraform v4.0.1 on 2026-05-12, setup-opentofu v2.0.2 on
2026-06-29). Some tutorials still use `setup-terraform@v3` and older checkout majors; those still run, but
the maintained majors are newer. Pin a major (or a full commit hash) and let Dependabot propose bumps.

[source,yaml]
----
steps:
  - uses: actions/checkout@v7
  - uses: hashicorp/setup-terraform@v4
    with:
      terraform_version: "1.17.0"
  - run: terraform fmt -check -recursive
  - run: terraform init -input=false
  - run: terraform validate
----

Source: https://github.com/hashicorp/setup-terraform[hashicorp/setup-terraform on GitHub] and
https://github.com/actions/checkout[actions/checkout on GitHub].

== Migration checklist

For a Bookshelf repository written from a book of this era, work through the changes in this order, one commit each:

* Pin the CLI with `required_version` and move CI to the current action majors.
* Run `terraform init -upgrade` on the newest 1.x minor you can adopt, reading the upgrade note of each minor from 1.10.
* Replace `-state` and `-state-out` by the `path` of the `local` backend, and `refresh` and `taint` by `-refresh-only` and `-replace`.
* Switch the S3 backend to `use_lockfile`, keep the DynamoDB table for one release cycle, then drop it.
* Upgrade providers one major at a time, starting with the last release of the current major, and review the lock file.
* Move secrets out of state with ephemeral values and write-only arguments where the provider offers them.
* Replace `template_file` with `templatefile()`, and tfsec with Trivy.
* Update references to Terraform Cloud and re-check plan limits against the HCP Terraform pricing page.
* Decide whether OpenTofu is an alternative for your team; the migration notes are on the OpenTofu page.

Reading order after this page: xref:backend/terraform/best-practices-and-troubleshooting.adoc[Best Practices and Troubleshooting].
