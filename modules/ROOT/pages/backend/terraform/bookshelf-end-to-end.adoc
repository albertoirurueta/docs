= Bookshelf End to End
:description: A capstone that provisions the whole Bookshelf scenario with Terraform from an empty repository: network, database, service and covers modules, dev and prod root modules, an S3 state backend with native locking on LocalStack, ephemeral and write-only secrets, checks and variable validation, mock-provider tests, TFLint and Checkov, GitHub Actions with OIDC, a real AWS variant, an import of a pre-existing bucket and a moved refactor, with the final repository layout.
:keywords: Terraform, OpenTofu, Bookshelf, end to end, capstone, modules, dev, prod, LocalStack, S3 backend, use_lockfile, tfbackend, ephemeral, write-only, secret_string_wo, check block, terraform test, mock_provider, TFLint, Checkov, GitHub Actions, OIDC, import block, moved block, AWS, Docker provider

include::partial$terraform-disclaimer.adoc[]

The earlier pages of this section each explain one idea in isolation. This page puts them in one repository and walks
through the order in which a team would actually build it: state first, then modules, then two environments, then the
safety net (checks, tests, linters, scanners), then the pipeline, and finally the two maintenance operations every
long-lived repository needs, adopting an object that already exists and renaming something that is already deployed. It
assumes the baseline of the rest of the section: Terraform 1.17 (OpenTofu 1.13 runs the same code, see the last
sections), `hashicorp/aws` 6.x and `kreuzwerker/docker` 4.x. It is the last page of the reading path and it links back to
the page that explains each part instead of repeating the explanation.

The scenario is *Bookshelf*: `catalog-api`, `reviews-api` and `web` containers, PostgreSQL, a covers bucket, a private
network, and a secret shared by the services. Everything runs on a laptop with Docker and LocalStack, so no cloud account
is needed. A later section shows what changes when the same repository targets a real AWS account. Bucket names, tokens,
role ARNs and registries are placeholders. Commands and console output are illustrative and abbreviated: no Terraform
binary was run to produce this page, so treat every transcript as the shape of the output, not as captured text.

== What is built, and in which order

The order matters because each step needs the previous one:

* *A state bucket.* Nothing else can be managed remotely until a place for the state exists. It is the one object
  that is created outside the configuration it serves (the chicken-and-egg problem described in
  xref:backend/terraform/backends-and-remote-state.adoc[Backends and Remote State]).
* *Modules.* `network`, `database` and `service` are the modules built in
  xref:backend/terraform/module-development-and-publishing.adoc[Module Development and Publishing]; this page adds a
  fourth, `covers`, for the object storage.
* *Two root modules.* `envs/dev` and `envs/prod` are thin: a backend, providers, variables and calls to the modules, as
  recommended in
  xref:backend/terraform/workspaces-environments-and-project-structure.adoc[Workspaces, Environments and Project Structure].
* *Secrets, checks and validation.* Rules that keep bad inputs and leaked secrets out
  (xref:backend/terraform/sensitive-data-ephemeral-and-write-only.adoc[Sensitive Data, Ephemeral Values and Write-Only Arguments]
  and xref:backend/terraform/lifecycle-validation-and-checks.adoc[Lifecycle, Validation and Checks]).
* *Tests and static analysis.* `terraform test` with a mocked provider, TFLint and Checkov
  (xref:backend/terraform/testing.adoc[Testing] and
  xref:backend/terraform/code-quality-and-security-scanning.adoc[Code Quality and Security Scanning]).
* *The pipeline.* GitHub Actions authenticating with OIDC, so no cloud key is stored
  (xref:backend/terraform/ci-cd-and-automation.adoc[CI/CD and Automation]).
* *Day-two operations.* An `import` block and a `moved` block
  (xref:backend/terraform/import-and-query.adoc[Import and Query] and
  xref:backend/terraform/refactoring-moved-and-removed.adoc[Refactoring: moved and removed]).

== Step 1: LocalStack and the state bucket

The state bucket is created by a script, not by Terraform. Terraform could create it, but then it would need a state to
record it, which is the bootstrap loop; the script keeps the loop outside. The credentials are the conventional dummy
values that LocalStack accepts; none of them is a secret.

[source,bash]
----
#!/usr/bin/env bash
# bootstrap/localstack.sh -- run once per machine
set -euo pipefail

docker run --rm -d --name localstack -p 127.0.0.1:4566:4566 localstack/localstack

export AWS_ACCESS_KEY_ID=test
export AWS_SECRET_ACCESS_KEY=test
export AWS_DEFAULT_REGION=us-east-1
endpoint=http://localhost:4566

# wait until the edge port answers
until curl -fsS "$endpoint/_localstack/health" >/dev/null; do sleep 2; done

aws --endpoint-url "$endpoint" s3 mb s3://bookshelf-tfstate
aws --endpoint-url "$endpoint" s3api put-bucket-versioning \
  --bucket bookshelf-tfstate --versioning-configuration Status=Enabled

# a bucket somebody created by hand before Terraform existed (adopted in a later step)
aws --endpoint-url "$endpoint" s3 mb s3://bookshelf-dev-covers
----

Source: https://docs.localstack.cloud/aws/connecting/infrastructure-as-code/terraform/[LocalStack Docs -- Terraform] and
https://developer.hashicorp.com/terraform/language/backend/s3[Terraform Docs -- Backend type: s3]

Versioning on the state bucket lets you recover an earlier snapshot after a bad write. The last command creates the
pre-existing object that the import step adopts later. Stopping the container (`docker stop localstack`) discards
everything unless persistence is enabled, so rerun the script after a restart and remember that the state is gone too.

== Step 2: the modules

Three modules already exist in
xref:backend/terraform/module-development-and-publishing.adoc[Module Development and Publishing] and are used here
unchanged apart from the provider constraint. Their interfaces are what the root modules rely on:

[cols="1,4,4",options="header"]
|===
| Module | Inputs the root module passes | Outputs the root module reads
| `network` | `name`, `cidr_block`, optional `tiers` | `network_names` (by tier), `cidr_blocks`
| `database` | `name`, `network_name`, `image_tag`, optional `password`, `resources` | `host`, `port`, `database_name`, `connection_url` (sensitive)
| `service` | `name`, `image`, `networks`, `replicas`, `env`, `secret_env`, `ports`, `healthcheck` | `internal_urls`
| `covers` (new here) | `name_prefix`, `force_destroy`, `versioned` | `bucket_name`, `bucket_arn`
|===

For a new repository set the Docker provider constraint in each module's `versions.tf` to `+version = "~> 4.6"+` (the
module page uses a wider `>= 3.0` for compatibility). A module should declare what it needs, not configure it, so none of
the four contains a `provider` block.

=== The covers module

Covers (book cover images) live in an S3-compatible bucket. The module is small on purpose, and it carries the rules that
must hold in every environment: no public access, versioning on, server-side encryption on, and a name that follows the
convention.

[source,hcl]
----
# modules/covers/versions.tf
terraform {
  required_version = ">= 1.11"

  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 6.0"
    }
  }
}
----

[source,hcl]
----
# modules/covers/variables.tf
variable "name_prefix" {
  type        = string
  description = "Prefix of the bucket name, for example bookshelf-dev. The module appends -covers."

  validation {
    condition     = can(regex("^[a-z][a-z0-9-]{2,40}$", var.name_prefix))
    error_message = "The name_prefix must start with a letter and contain 3 to 41 lowercase letters, digits or hyphens."
  }
}

variable "force_destroy" {
  type        = bool
  description = "Allow destroying a bucket that still holds objects. Keep false in production."
  default     = false
}

variable "versioned" {
  type        = bool
  description = "Keep previous versions of every cover."
  default     = true
}
----

[source,hcl]
----
# modules/covers/main.tf
resource "aws_s3_bucket" "this" {
  # checkov:skip=CKV_AWS_144:Cross-region replication is not needed for re-creatable covers
  # checkov:skip=CKV_AWS_18:Access logging is configured at account level in this scenario
  bucket        = "${var.name_prefix}-covers"
  force_destroy = var.force_destroy
}

resource "aws_s3_bucket_public_access_block" "this" {
  bucket = aws_s3_bucket.this.id

  block_public_acls       = true
  block_public_policy     = true
  ignore_public_acls      = true
  restrict_public_buckets = true
}

resource "aws_s3_bucket_versioning" "this" {
  bucket = aws_s3_bucket.this.id

  versioning_configuration {
    status = var.versioned ? "Enabled" : "Suspended"
  }
}

resource "aws_s3_bucket_server_side_encryption_configuration" "this" {
  bucket = aws_s3_bucket.this.id

  rule {
    apply_server_side_encryption_by_default {
      sse_algorithm = "AES256"
    }
  }
}
----

[source,hcl]
----
# modules/covers/outputs.tf
output "bucket_name" {
  description = "Name of the covers bucket."
  value       = aws_s3_bucket.this.bucket
}

output "bucket_arn" {
  description = "ARN of the covers bucket, for IAM policies."
  value       = aws_s3_bucket.this.arn
}
----

Source: https://registry.terraform.io/providers/hashicorp/aws/latest/docs/resources/s3_bucket[AWS provider -- aws_s3_bucket],
https://registry.terraform.io/providers/hashicorp/aws/latest/docs/resources/s3_bucket_public_access_block[aws_s3_bucket_public_access_block],
https://registry.terraform.io/providers/hashicorp/aws/latest/docs/resources/s3_bucket_versioning[aws_s3_bucket_versioning]
and https://registry.terraform.io/providers/hashicorp/aws/latest/docs/resources/s3_bucket_server_side_encryption_configuration[aws_s3_bucket_server_side_encryption_configuration]

The two `checkov:skip` comments travel with the resource and appear in the scan as skipped checks with a reason, which is
how a reviewer sees a deliberate exception. The longer discussion of the S3 resources is in
xref:backend/terraform/terraform-on-aws.adoc[Terraform on AWS].

== Step 3: the backend, one partial file per environment

Backend blocks cannot use variables, so the block is empty and each environment supplies the settings with
`-backend-config` (partial configuration). Two environments share the bucket and differ only in the key, which is the
design the workspaces page recommends when separate accounts are not available.

[source,hcl]
----
# envs/dev/backend.tf
terraform {
  required_version = ">= 1.11"

  backend "s3" {}
}
----

[source,hcl]
----
# envs/dev/dev.s3.tfbackend
bucket = "bookshelf-tfstate"
key    = "bookshelf/dev/terraform.tfstate"
region = "us-east-1"

# LocalStack, not AWS: remove these lines for a real bucket
endpoints = {
  s3 = "http://localhost:4566"
}
use_path_style              = true
skip_credentials_validation = true
skip_requesting_account_id  = true
skip_metadata_api_check     = true
skip_region_validation      = true
skip_s3_checksum            = true

# native locking: a .tflock object next to the state object
use_lockfile = true
----

Source: https://developer.hashicorp.com/terraform/language/backend#partial-configuration[Terraform Docs -- Partial configuration]
and https://developer.hashicorp.com/terraform/language/backend/s3[Terraform Docs -- Backend type: s3]

`envs/prod/prod.s3.tfbackend` is identical except for `+key = "bookshelf/prod/terraform.tfstate"+`. The file holds no
secret: the dummy credentials come from `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY` in the environment. As the
backends page notes, LocalStack's documentation does not state that it enforces the `.tflock` object, so verify locking
yourself in step 5 before relying on it.

== Step 4: the dev root module

The root module is the only place that knows how the modules fit together and where the providers point. The same code
serves `prod`; only the values change.

[source,hcl]
----
# envs/dev/providers.tf
terraform {
  required_providers {
    docker = {
      source  = "kreuzwerker/docker"
      version = "~> 4.6"
    }
    aws = {
      source  = "hashicorp/aws"
      version = "~> 6.0"
    }
    random = {
      source  = "hashicorp/random"
      version = "~> 3.9"
    }
    http = {
      source  = "hashicorp/http"
      version = "~> 3.4"
    }
  }
}

provider "docker" {}

# LocalStack endpoints. For a real account these arguments are removed (see the variant section).
provider "aws" {
  region                      = var.region
  access_key                  = "test"
  secret_key                  = "test"
  skip_credentials_validation = true
  skip_metadata_api_check     = true
  skip_requesting_account_id  = true
  s3_use_path_style           = true

  endpoints {
    s3             = "http://localhost:4566"
    secretsmanager = "http://localhost:4566"
  }
}
----

----

variable "environment" {
  type        = string
  description = "Environment name, used in resource names."

  validation {
    condition     = contains(["dev", "prod"], var.environment)
    error_message = "The environment must be dev or prod."

  type    = string
  default = "us-east-1"
}

variable "vpc_cidr" {
  type    = string

}

variable "catalog_api_image" {
  type        = string

}

variable "reviews_api_image" {
  type        = string
  description = "reviews-api image with an explicit tag. Placeholder registry."

  type    = number
  default = 1

  type        = number

    module.network.network_names["backend"],

Points worth noticing:

* Every container and network name includes the environment, so the dev and prod root modules can run on the same Docker
  engine without colliding. The prod CIDR differs for the same reason (Docker networks cannot overlap).
* `module.catalog_api` has two replicas in prod, so its published port stays internal; only `web` publishes a host port,
  which is the cross-variable rule of the `service` module at work.
* There is no `depends_on`. References such as `module.database.connection_url` and `module.network.network_names`
  produce the dependency graph, as explained in
  xref:backend/terraform/dependency-graph-and-plan.adoc[Dependency Graph and Plan].
* The password is not in any file. The variable is `sensitive`, has no default, and receives its value from
  `TF_VAR_db_password` (step 5). In the Docker variant the value still reaches the container's `env` argument and is
  recorded in state, which is why the state bucket is private and versioned; the Docker provider page describes the
  limitation, and the real-cloud variant removes it.
* `prod.tfvars` sets `covers_force_destroy = false`, so a `terraform destroy` of production cannot silently delete a bucket
  that still holds covers.

=== Secrets: ephemeral generation, write-only storage

The services need a shared token. It is generated ephemerally, written once to Secrets Manager through a write-only
argument, and fetched by the containers at start-up with their own identity. Terraform never stores it, and it is not an
output.

[source,hcl]
----
# envs/dev/secrets.tf
ephemeral "random_password" "service_token" {
  length  = 48
  special = false
}

resource "aws_secretsmanager_secret" "service_token" {
  name                    = "bookshelf/${var.environment}/service-token"
  recovery_window_in_days = 0 # allow immediate re-creation after destroy; use 7 to 30 for production
}

resource "aws_secretsmanager_secret_version" "service_token" {
  secret_id                = aws_secretsmanager_secret.service_token.id
  secret_string_wo         = ephemeral.random_password.service_token.result
  secret_string_wo_version = var.service_token_version
}
----

Source: https://developer.hashicorp.com/terraform/language/manage-sensitive-data/ephemeral[Terraform Docs -- Ephemerality],
https://registry.terraform.io/providers/hashicorp/aws/latest/docs/resources/secretsmanager_secret_version[AWS provider -- aws_secretsmanager_secret_version]
and https://registry.terraform.io/providers/hashicorp/random/latest/docs/ephemeral-resources/password[random provider -- random_password ephemeral resource]

A write-only argument is sent to the provider and never saved, so Terraform cannot tell by itself that the value should
change. The companion `secret_string_wo_version` is the trigger: raising `service_token_version` in the tfvars file makes
the next apply generate and write a fresh token. Set `recovery_window_in_days` to a real window in production; zero is a
convenience for a disposable local environment. This pattern, the alternatives and the places where an ephemeral value is
not allowed are explained in
xref:backend/terraform/sensitive-data-ephemeral-and-write-only.adoc[Sensitive Data, Ephemeral Values and Write-Only Arguments].
LocalStack's coverage of write-only secret versions was not verified for this page; if your emulator version rejects the
call, test this file against a real account or keep the pattern and mock it in tests.

=== A check for the running system

A `check` block validates the world after the apply without failing it. Here it asks the published `web` port for a
response. It warns, rather than errors, which is the right severity for a health probe that depends on container start-up.

[source,hcl]
----
# envs/dev/checks.tf
check "web_responds" {
  data "http" "web" {
    url = "http://localhost:${var.web_port}/"

    # Without this the first plan, before the container exists, would warn.
    depends_on = [module.web]
  }

  assert {
    condition     = data.http.web.status_code == 200
    error_message = "web answered ${data.http.web.status_code} on port ${var.web_port}."
  }
}
----

Source: https://developer.hashicorp.com/terraform/language/block/check[Terraform Docs -- check block reference]

Variable `validation` blocks (the password length, the port range, the environment name) fail at plan time; the `check`
fails softly after the apply. The page
xref:backend/terraform/lifecycle-validation-and-checks.adoc[Lifecycle, Validation and Checks] has the full comparison,
including when to prefer a `precondition`.

=== Verifying that the lock works

Run two applies at the same time and confirm that the second is refused.

[source,bash]
----
terraform apply -var-file=dev.tfvars -auto-approve &
sleep 2
terraform apply -var-file=dev.tfvars -auto-approve -lock-timeout=0s
wait
aws --endpoint-url http://localhost:4566 s3 ls s3://bookshelf-tfstate/bookshelf/dev/
----

Source: https://developer.hashicorp.com/terraform/language/state/locking[Terraform Docs -- State locking]

When the lock is enforced, the second command reports that the state is locked and the listing briefly shows a
`terraform.tfstate.tflock` object next to the state object. If both applies proceed, your LocalStack version does not
implement the conditional writes that `use_lockfile` needs: keep the setting in the repository (it is correct for real
S3) and treat the local environment as single-user. After an interrupted run, `terraform force-unlock <LOCK_ID>` releases
the lock, but only when you are sure that nobody is still running.

== Step 6: adopt an object that already exists

The bootstrap script created `bookshelf-dev-covers` by hand, as a team often does before it adopts Terraform. Terraform
would otherwise try to create a bucket that already exists and fail. An `import` block makes the adoption reviewable: it is
a plan item, not a command typed once on one laptop.

[source,hcl]
----
# envs/dev/imports.tf
import {
  to = module.covers.aws_s3_bucket.this
  id = "bookshelf-dev-covers"
}
----

[source,console]
----
$ terraform plan -var-file=dev.tfvars
# abbreviated and illustrative
  # module.covers.aws_s3_bucket.this will be imported
  # module.covers.aws_s3_bucket_versioning.this will be created
  # module.covers.aws_s3_bucket_public_access_block.this will be created
  # module.covers.aws_s3_bucket_server_side_encryption_configuration.this will be created

Plan: 1 to import, 3 to add, 0 to change, 0 to destroy.
----

Source: https://developer.hashicorp.com/terraform/language/import/single-resource[Terraform Docs -- Import a single resource]

The plan shows what the module will do to the bucket besides adopting it: the three configuration resources are new
because the hand-made bucket had no versioning, encryption or public access block. That is the value of importing through
the module, since the bucket is brought up to the standard in the same review. Once the apply finishes, the `import` block
is finished work and can stay (it is idempotent) or be removed in a later change. The `import` block belongs to the root
module, and its `to` address reaches into the module; the import page lists the cases, including
`-generate-config-out` for objects with many arguments.

== Step 7: a rename that must not recreate anything

During review the name `reviews` for the second API is judged too vague, and the module call is renamed to
`reviews_api`. Without help, Terraform sees one module disappear and another appear, and plans to destroy and recreate its
containers. A `moved` block records the rename instead.

[source,hcl]
----
# envs/dev/refactor.tf -- history of address changes; keep until every environment has applied them
moved {
  from = module.reviews
  to   = module.reviews_api
}
----

[source,console]
----
$ terraform plan -var-file=dev.tfvars
# abbreviated and illustrative
  # module.reviews has moved to module.reviews_api
...
Plan: 0 to add, 0 to change, 0 to destroy.
----

Source: https://developer.hashicorp.com/terraform/language/modules/develop/refactoring[Terraform Docs -- Refactor modules]

Copy the same `moved` block to `envs/prod/refactor.tf`: each environment has its own state and must apply the move
separately. A module test or a CI step that asserts the plan contains no `delete` or `replace` actions turns this into a
guard rail. Retiring an object without destroying it uses the sibling `removed` block with `destroy = false`; both are
covered in
xref:backend/terraform/refactoring-moved-and-removed.adoc[Refactoring: moved and removed].

=== One entry point for developers and CI

[source,makefile]
----
# Makefile
ENVS := dev prod

.PHONY: check fmt validate test lint scan
check: fmt validate test lint scan

fmt:
	terraform fmt -check -recursive -diff

validate:
	for e in $(ENVS); do \
	  terraform -chdir=envs/$$e init -backend=false -input=false && \
	  terraform -chdir=envs/$$e validate || exit 1; \
	done

test:
	for m in network database service covers; do \
	  terraform -chdir=modules/$$m init -backend=false -input=false && \
	  terraform -chdir=modules/$$m test || exit 1; \
	done

lint:
	tflint --init
	tflint --recursive --format compact

scan:
	checkov -d . --framework terraform --quiet --compact
----

Source: https://developer.hashicorp.com/terraform/cli/commands/validate[Terraform Docs -- validate],

== Step 9: GitHub Actions with OIDC

Two workflows split read from write. The checks workflow needs no credentials and runs for every pull request, including
forks. The deploy workflow assumes an AWS role through OpenID Connect, so there is no stored access key. It targets the
real-cloud variant of the next section, because GitHub-hosted runners cannot reach the LocalStack on your laptop (the
same workflow can run against a LocalStack service container if you want a full local rehearsal in CI).

[source,yaml]
----
# .github/workflows/terraform-checks.yml
name: terraform-checks

on:
  pull_request:
    paths:
      - "modules/**"
      - "envs/**"
      - ".github/workflows/terraform-*.yml"

permissions:
  contents: read

env:
  TF_IN_AUTOMATION: "true"
  TF_INPUT: "false"

jobs:
  checks:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7

      - uses: hashicorp/setup-terraform@v4
        with:
          terraform_wrapper: false

      - uses: terraform-linters/setup-tflint@v6

      - name: install Checkov
        run: pip install checkov==3.3.30

      - name: make check
        run: make check
----

Source: https://github.com/hashicorp/setup-terraform[hashicorp/setup-terraform README],
https://github.com/terraform-linters/setup-tflint[terraform-linters/setup-tflint README]
and https://github.com/actions/checkout[actions/checkout README]

[source,yaml]
----
# .github/workflows/terraform-deploy.yml
name: terraform-deploy

on:
  push:
    branches: [main]
    paths:
      - "modules/**"
      - "envs/**"

permissions:
  contents: read

env:
  TF_IN_AUTOMATION: "true"
  TF_INPUT: "false"

jobs:
  dev:
    runs-on: ubuntu-latest
    environment: dev
    concurrency:
      group: terraform-dev
      cancel-in-progress: false
    permissions:
      contents: read
      id-token: write          # request the GitHub OIDC token
    steps:
      - uses: actions/checkout@v7
      - uses: hashicorp/setup-terraform@v4
        with:
          terraform_wrapper: false
      - uses: aws-actions/configure-aws-credentials@v6
        with:
          role-to-assume: ${{ vars.AWS_ROLE_ARN }}      # an environment variable of "dev"
          aws-region: ${{ vars.AWS_REGION }}
      - name: apply dev
        working-directory: envs/dev
        run: |
          terraform init -backend-config=dev.aws.s3.tfbackend
          terraform apply -auto-approve -lock-timeout=5m -var-file=dev.aws.tfvars
        env:
          TF_VAR_db_password: ${{ secrets.DEV_DB_PASSWORD }}

  prod:
    needs: dev
    runs-on: ubuntu-latest
    environment: production        # required reviewers are enforced here
    concurrency:
      group: terraform-prod
      cancel-in-progress: false
    permissions:
      contents: read
      id-token: write
    steps:
      - uses: actions/checkout@v7
      - uses: hashicorp/setup-terraform@v4
        with:
          terraform_wrapper: false
      - uses: aws-actions/configure-aws-credentials@v6
        with:
          role-to-assume: ${{ vars.AWS_ROLE_ARN }}      # an environment variable of "production"
          aws-region: ${{ vars.AWS_REGION }}
      - name: plan prod
        working-directory: envs/prod
        run: |
          terraform init -backend-config=prod.aws.s3.tfbackend
          terraform plan -lock-timeout=5m -var-file=prod.aws.tfvars -out=tfplan
      - name: apply prod
        working-directory: envs/prod
        run: terraform apply -lock-timeout=5m tfplan
----

Source: https://developer.hashicorp.com/terraform/tutorials/automation/github-actions[HashiCorp Developer -- Automate Terraform with GitHub Actions],
https://github.com/aws-actions/configure-aws-credentials[aws-actions/configure-aws-credentials README]
and https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments[GitHub Docs -- Managing environments for deployment]

Notes on the pipeline:

* The majors in the workflow (`actions/checkout` v7, `hashicorp/setup-terraform` v4, `terraform-linters/setup-tflint` v6,
  `aws-actions/configure-aws-credentials` v6) are the ones the CI page verified. The `hashicorp/setup-terraform` README
  shows v4, not the v3 mentioned in the original issue for this section.
* `id-token: write` is what lets the job request a GitHub OIDC token. The role's trust policy must accept only this
  repository and the matching environment as subject (`repo:ORG/REPO:environment:production`), as in the Terraform
  snippet of the CI page. The role ARN is an identifier, not a secret, and lives in an environment variable.
* The database password still comes from a repository environment secret in this simplified file. Where the cloud supports
  it, replace it with a write-only argument and a generated password (next section) so that even that secret disappears.
* The production job waits for the `production` environment's required reviewers. The CI page shows the stricter variant
  that saves the reviewed plan as an artifact and applies exactly that file; use it for production.

== Step 10: the real-cloud variant

The structure does not change. What changes is below the module interfaces and in the provider and backend files.

[cols="2,3,3",options="header"]
|===
| Piece | Local (this page) | Real AWS
| Backend file | `dev.s3.tfbackend` with `endpoints`, `use_path_style` and `+skip_*+` | `dev.aws.s3.tfbackend` with `bucket`, `key`, `region`, `encrypt = true`, `use_lockfile = true` only
| `aws` provider | dummy keys, `endpoints` block, `+skip_*+` | no credentials in code: OIDC in CI, SSO or a profile on a laptop; `default_tags`
| `network` | Docker networks cut with `cidrsubnet` | `terraform-aws-modules/vpc/aws` or an equivalent module with the same outputs shape
| `database` | PostgreSQL container, password from `TF_VAR_db_password` | `aws_db_instance` with a write-only password
| `service` | Docker containers | ECS services on Fargate behind a load balancer
| `covers` | unchanged | unchanged
| Secrets | LocalStack Secrets Manager | AWS Secrets Manager, same `secrets.tf`
|===

use_lockfile = true

== Using OpenTofu instead

The configuration uses only features that exist in both tools at the versions shown: partial backend configuration, S3
`use_lockfile`, ephemeral resources and write-only arguments (OpenTofu 1.11 and later), `check` blocks, `import`, `moved`
and mock providers. Replace `terraform` with `tofu` in the Makefile and the workflows, install it with
`opentofu/setup-opentofu` (v2 as verified in the CI page) and run the checks as a matrix to prove the compatibility, as
that page shows. OpenTofu's own state encryption and early evaluation are not used here; adopting them would make the
repository OpenTofu-only. See xref:backend/terraform/opentofu.adoc[OpenTofu] for the differences.

== Pitfalls collected from the build

* *Applying prod from a laptop.* The pipeline should be the only identity that can write production state. Give laptops
  read-only roles.
* *Sharing one state key.* Dev and prod must use different keys (and ideally different buckets and accounts). A wrong key
  makes `plan` propose destroying the other environment.
* *Forgetting the password variable.* An unset `TF_VAR_db_password` prompts in a terminal and fails in CI with
  `TF_INPUT=false`; that failure is deliberate.
* *Committing plan files or tfvars with secrets.* Saved plans can contain sensitive values. Keep `+*.tfplan+` and secret
  tfvars out of Git.
* *Expecting a write-only argument to track changes.* Without a version bump the secret never rotates.
* *Moving without moved.* Renaming a module call or resource without a `moved` block plans a destroy and create.
* *Trusting a local lock.* Verify locking on every backend you use before relying on it, as in step 5.
* *Emulator settings in production code.* Keep `endpoints`, `+skip_*+` and dummy keys out of the real provider and backend
  files; the table in the variant section lists what to remove.

== What this page could not verify

* LocalStack's enforcement of the `.tflock` lock object and its support for write-only Secrets Manager versions are not
  documented by LocalStack; both are marked as "verify on your version".
* Resource counts and console output in the transcripts are illustrative.
* The AWS ruleset version for TFLint and the Checkov pin are examples taken from the scanning and CI pages.
