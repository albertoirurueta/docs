Welcome to the Terraform reference. *Terraform* is a tool for describing infrastructure -- networks, databases,
containers, buckets, DNS records, identities and permissions -- as declarative text files, and for making a real
environment match that description. You write the desired end state in HashiCorp Configuration Language (HCL);
Terraform compares it with a record of what it created before (the state) and with what actually exists, shows a
plan of the differences, and applies only the changes you approve. The same files can be reviewed in a pull
request, versioned in Git and run again to rebuild an environment from scratch. *OpenTofu* is the open-source fork
of Terraform that is maintained under the Linux Foundation; it reads the same language and uses the same providers,
and this section treats the two tools as peers and marks every place where they differ.

This section is for backend developers and platform engineers who build and ship services, such as those in the
xref:backend/docker/index.adoc[Docker] and xref:backend/kubernetes/index.adoc[Kubernetes] references, and now
need to create the infrastructure underneath them in a repeatable way. It starts from the problem that manual
provisioning creates, builds up the language and the workflow, and ends with a complete repository that provisions
the whole example application. It explains the concepts, the commands and the configuration, and it links every
example to the official documentation that backs it. The core pages need no cloud account: they run on a laptop
against the Docker provider, the utility providers and LocalStack.

== Version baseline and release cadence

The examples are written and checked against Terraform 1.17 (1.17.0 was released on 2026-10-21), OpenTofu 1.13 (the
latest patch at the time of writing is 1.13.2, published on 2026-10-21), the `hashicorp/aws` provider 6.x, the
`hashicorp/azurerm` provider 5.x, the `hashicorp/google` provider 8.x and the `hashicorp/setup-terraform` GitHub
Action v4. Both projects publish a new minor version several times a year and keep publishing patch releases for
earlier minor lines after a new minor appears: when 1.17.0 shipped, the 1.16 line was still receiving fixes with
1.16.7, and OpenTofu published the 1.12.9 and 1.13.2 patches on the same day. Provider releases follow their own
schedule, independent of the core, and a provider major version can change resource arguments in breaking ways, so
`required_providers` constraints and the dependency lock file matter in practice. The changelogs and upgrade
guides are the authority for what changed in a given release; xref:backend/terraform/whats-changed-and-migration.adoc[What Changed and Migration]
collects the changes since the 2024 and 2025 era of the books listed in the <<_bibliography,bibliography>>, and
xref:backend/terraform/opentofu.adoc[OpenTofu] maps OpenTofu versions to Terraform versions. Always read the
https://developer.hashicorp.com/terraform/language/upgrade-guides[upgrade guides] and the
https://github.com/hashicorp/terraform/blob/main/CHANGELOG.md[Terraform changelog] before moving to a new minor
version.

== The Bookshelf scenario

Every example in this section provisions the infrastructure of the same small application, *Bookshelf*, which the
Docker, Kubernetes, AWS, Azure and Google Cloud sections of this site also use: a `catalog-api`, a `reviews-api` and
a `web` front end, PostgreSQL and Redis, an object-storage bucket for book covers, and the networking, DNS, secrets
and IAM that connect them. Names, images and account identifiers are neutral placeholders, so nothing depends on a
real account or a published image. The scenario grows page by page: the early pages create a container, a network
and a volume with the Docker provider, the middle pages add a state backend, modules, tests and a pipeline, the
cloud pages rebuild the same infrastructure on AWS, Azure and Google Cloud with a clean-up section each, and
xref:backend/terraform/bookshelf-end-to-end.adoc[Bookshelf End to End] assembles everything into one repository
with `modules/network`, `modules/database`, `modules/service`, `envs/dev`, `envs/prod`, `tests/` and a GitHub
Actions workflow.
