= Debugging Containers
:description: A practical toolbox for debugging containers in the order you reach for it -- docker logs, docker ps -a and exit codes, docker inspect with Go templates, docker exec, docker debug for shell-less images, top, diff, cp, image history, events -- namespace-sharing debug sidecars, daemon logs and dockerd --debug, and a table of common failures with their fixes.
:keywords: debugging Docker containers, docker logs, docker ps -a, exit code, docker inspect --format, Go templates, docker exec, docker debug, distroless debugging, docker top, docker diff, docker cp, docker image history, docker events, --pid=container, --network=container, debug sidecar, nicolaka/netshoot, nsenter, daemon logs, dockerd --debug, port is already allocated, permission denied docker.sock, no space left on device, DNS inside containers, exec format error, OOMKilled, unhealthy healthcheck, bind mount not updating

include::partial$docker-disclaimer.adoc[]

Most container problems are ordinary application problems seen through an extra layer of indirection. Chapter 8 of
_Docker: Up & Running_ and chapter 10 of _Learning Docker_ teach the same method -- look at the process, the
network, the image history and the filesystem from the outside -- and it still works. What has changed is the
tooling: `docker exec` and `docker debug` replace `nsenter`, and Go templates make `docker inspect` precise. This
page describes that toolbox for Docker Engine 29.8.x and Docker Desktop 4.91 or later, followed by a table of the
failures you will actually meet.

== The toolbox, in the order you reach for it

[mermaid]
....
flowchart TD
  s(["Container misbehaves"]) --> r{"Is it running?"}
  r -->|No| ps["docker ps -a: status and exit code"]
  ps --> code{"Exit code"}
  code -->|137| oom["docker inspect .State.OOMKilled<br/>raise --memory or fix the leak"]
  code -->|125 / 126 / 127| cmd["Wrong command, entrypoint<br/>or permissions: check CMD/ENTRYPOINT"]
  code -->|other| logs["docker logs: application error"]
  r -->|Yes| h{"Healthy and reachable?"}
  h -->|Unhealthy| hc["docker inspect .State.Health.Log<br/>run the probe by hand with exec"]
  h -->|Not reachable| net["docker port, network inspect,<br/>netshoot sidecar on its network"]
  h -->|Slow or wrong output| inside["docker exec or docker debug:<br/>inspect files, env, processes"]
  logs --> fix(["Fix, rebuild, re-run"])
  oom --> fix
  cmd --> fix
  hc --> fix
  net --> fix
  inside --> fix
....

=== 1. Logs

[source,shell]
----
docker logs --tail 200 orders
docker logs -f --since 5m --timestamps orders
----

Everything the main process writes to stdout/stderr is here -- provided the application logs to the console (see
xref:backend/docker/resources-logging-and-monitoring.adoc[Resources, Logging and Monitoring]). Derived from
https://docs.docker.com/reference/cli/docker/container/logs/[`docker container logs`].

=== 2. Status and exit code

[source,shell]
----
docker ps -a --filter name=orders --format 'table {{.Names}}\t{{.Status}}\t{{.Image}}'
docker inspect --format '{{.State.Status}} exit={{.State.ExitCode}} oom={{.State.OOMKilled}} error={{.State.Error}}' orders
----

The exit codes are explained on
xref:backend/docker/running-containers.adoc#_signals_exit_codes_and_graceful_shutdown[Running Containers]: `137` is
`SIGKILL` (often the OOM killer), `143` is `SIGTERM`, `125`-`127` mean the command could not be started.

=== 3. `docker inspect` with Go templates

`docker inspect` prints the full JSON for any object; `--format` extracts exactly what you need:

[source,shell]
----
docker inspect --format '{{json .Config.Env}}' orders | jq .
docker inspect --format '{{range .Mounts}}{{.Type}} {{.Source}} -> {{.Destination}}{{"\n"}}{{end}}' orders
docker inspect --format '{{range $net, $cfg := .NetworkSettings.Networks}}{{$net}} {{$cfg.IPAddress}}{{"\n"}}{{end}}' orders
docker inspect --format '{{json .State.Health}}' orders | jq '.Log[-1]'
docker inspect --format '{{.Config.Entrypoint}} {{.Config.Cmd}} user={{.Config.User}}' orders-service:1.4.0
----

Derived from https://docs.docker.com/reference/cli/docker/inspect/[`docker inspect`] and
https://docs.docker.com/engine/cli/formatting/[Format command and log output].

=== 4. Get inside: `docker exec`

[source,shell]
----
docker exec -it orders sh                          # a shell, if the image has one
docker exec orders env                             # the actual environment
docker exec -u 0 -it orders sh                     # as root, e.g. to install a tool temporarily
docker exec orders cat /proc/1/status | grep -E 'Name|VmRSS|Threads'
----

Derived from https://docs.docker.com/reference/cli/docker/container/exec/[`docker container exec`].

=== 5. Images without a shell: `docker debug`

Distroless and hardened runtime images deliberately ship no shell, so `docker exec -it ... sh` fails. `docker debug`
(bundled with Docker Desktop, free for all users) attaches a toolbox shell -- with `vim`, `curl`, `htop`, `strace`
and an `install` command for more -- to a running container or even to an image, without modifying it:

[source,shell]
----
docker debug orders                   # a debug shell sharing the container's filesystem, processes and network
docker debug orders-service:1.4.0     # explore an image that has no shell
----

Derived from https://docs.docker.com/reference/cli/docker/debug/[`docker debug`].

=== 6. Processes, filesystem changes, files and history

[source,shell]
----
docker top orders -eo pid,ppid,user,rss,args      # processes, with host PIDs
docker diff orders                                # files added (A), changed (C), deleted (D) since start
docker cp orders:/tmp/heapdump.hprof ./           # copy artifacts out -- works on stopped containers too
docker image history --no-trunc orders-service:1.4.0   # how each layer was produced
docker events --filter container=orders --since 30m    # start, die, oom, health_status transitions
----

Derived from https://docs.docker.com/reference/cli/docker/container/top/[`docker container top`],
https://docs.docker.com/reference/cli/docker/container/diff/[`docker container diff`] and
https://docs.docker.com/reference/cli/docker/system/events/[`docker system events`].

== Debug sidecars: sharing namespaces

When the tool you need is not in the image and `docker debug` is not available (for example on a server with plain
Docker Engine), start a second container that *joins the target's namespaces* and brings its own tools:

image::docker-debug-sidecar.svg[A debug sidecar container joining the PID and network namespaces of a target container so that its tools see the target processes and sockets,width=700]

[source,shell]
----
# See and trace the target's processes (same PID namespace)
docker run --rm -it --pid=container:orders --cap-add SYS_PTRACE busybox:1.37 sh -c 'ps aux'

# Debug its network from inside (same network namespace: same IP, same localhost, same ports)
docker run --rm -it --network=container:orders nicolaka/netshoot:v0.16 \
  sh -c 'ss -ltnp; curl -s localhost:8080/actuator/health; dig orders-db'
----

Derived from https://docs.docker.com/reference/cli/docker/container/run/#pid[`--pid`] and
https://docs.docker.com/reference/cli/docker/container/run/#network[`--network`].

Both books use `nsenter` (from `util-linux`, run on the host with the container's PID) to enter a container's
namespaces. That technique is historical: it needs root on the host and does not work on Docker Desktop, where the
containers live inside a VM. `docker exec`, `docker debug` and namespace-sharing sidecars replace it.

== When the daemon is the problem

[source,shell]
----
docker info                                     # warnings at the bottom: no cgroup v2, storage driver issues, ...
journalctl -u docker.service --since "1 hour ago"     # daemon logs on systemd Linux hosts
sudo dockerd --debug                            # run in the foreground with debug logging (stop the service first)
----

Set `"debug": true` in `/etc/docker/daemon.json` and send `SIGHUP` to `dockerd` to switch debug logging on without a
restart. On Docker Desktop, use *Troubleshoot > Gather diagnostics*. Derived from
https://docs.docker.com/engine/daemon/logs/[Read the daemon logs] and
https://docs.docker.com/engine/daemon/troubleshoot/[Troubleshooting the Docker daemon].

== Common failures and fixes

[cols="2,3,3",options="header"]
|===
| Symptom | Cause | Fix

| `Bind for 0.0.0.0:8080 failed: port is already allocated`
| Another container or host process owns the host port.
| `docker ps --filter publish=8080`; stop it, or publish a different host port (`-p 8081:8080`).

| `permission denied while trying to connect to the Docker daemon socket at unix:///var/run/docker.sock`
| Your user is not in the `docker` group (or the new group membership is not active yet).
| Add the user to the group and log in again, use rootless mode, or `sudo` (see
  xref:backend/docker/getting-started.adoc#_post_install_steps_on_linux[post-install steps]).

| `no space left on device`
| Images, stopped containers, volumes and build cache filled `/var/lib/docker` (or the Desktop VM disk).
| `docker system df`, then `docker system prune` / `docker builder prune`; configure log rotation.

| Name resolution fails inside a container
| Container on the default bridge (no DNS by name), a host resolver on `127.0.0.53` that containers cannot use, or
  a VPN changing DNS.
| Use a user-defined network; set `--dns` or daemon-wide `"dns"`; test with `docker run --rm --network <net>
  busybox:1.37 nslookup <name>`.

| `exec /app/start.sh: exec format error`
| Image built for another architecture (for example `linux/amd64` on Apple silicon), or a script with Windows line
  endings or no shebang.
| Build a multi-platform image or pass `--platform`; fix line endings and add `#!/bin/sh`.

| Container exits with `137`, `OOMKilled=true`
| The process exceeded `--memory`.
| Raise the limit, or size the JVM with `-XX:MaxRAMPercentage` (see
  xref:backend/docker/resources-logging-and-monitoring.adoc#_what_the_jvm_sees[What the JVM sees]).

| Health check stays `starting` or becomes `unhealthy`
| The probe command is missing from the image (`curl` in a JRE-only image), wrong port or path, or a too-short
  `--start-period`.
| Read `.State.Health.Log`; run the probe with `docker exec`; use a tool the image contains.

| Edits to bind-mounted files are not visible
| The application caches files, the editor replaced the file (new inode) under a single-file bind mount, or Desktop
  file sharing is not configured for that path.
| Bind-mount the directory rather than the file; check *Settings > Resources > File sharing*; consider Compose
  Watch.

| `docker stop` always takes 10 seconds
| The process is not PID 1 in exec form, or ignores `SIGTERM`.
| Use exec-form `ENTRYPOINT`, `exec` in wrapper scripts, or `--init`.
|===

The error texts are those printed by Docker Engine 29 and are described across
https://docs.docker.com/engine/daemon/troubleshoot/[Troubleshooting the Docker daemon],
https://docs.docker.com/engine/network/port-publishing/[Port publishing and mapping] and
https://docs.docker.com/engine/install/linux-postinstall/[Linux post-installation steps].
