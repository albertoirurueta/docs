Since Docker Engine 23.0 every `docker build` runs on BuildKit through the Buildx client. The defaults are enough for
a laptop, but CI pipelines, multi-architecture images and supply-chain metadata all depend on features that need a
little configuration: builders and drivers, exporters, remote caches, attestations and Bake. This page covers them
for Buildx 0.37.x and BuildKit 0.33.x with the `docker/dockerfile:1` frontend under Docker Engine 29.8.x; how to
use them from GitHub Actions is on xref:backend/docker/ci-cd-with-github-actions.adoc[Docker CI/CD with GitHub
Actions].

== BuildKit in one paragraph

BuildKit turns a build definition into a graph (LLB, "low-level build") and solves it. A *frontend* -- the Dockerfile
frontend selected by `# syntax=docker/dockerfile:1`, or another one -- produces the graph; the *solver* runs
independent vertices in parallel, skips any stage the requested target does not depend on, and caches every vertex
by content. Compared with the legacy builder this gives parallel multi-stage builds, `RUN --mount`, secrets that
never touch a layer, multi-platform output, pluggable exporters and caches, and build attestations. Derived from
https://docs.docker.com/build/buildkit/[BuildKit].

== Builders and drivers

A *builder* is a BuildKit instance that Buildx sends builds to. How that instance runs is its *driver*:

image::docker-buildx-drivers.svg[Buildx client sending builds to builders using the docker driver inside dockerd or the docker-container driver in a container or the kubernetes driver in pods or the remote driver or the cloud driver,width=700]

[cols="1,3,2",options="header"]
|===
| Driver | Where BuildKit runs | Use it for

| `docker`
| Inside `dockerd` (the default builder, named after the context)
| Local builds whose result goes straight into the Engine's image store

| `docker-container`
| In a dedicated container managed by Buildx
| Multi-platform builds with the classic image store, remote cache export (`gha`, `registry` with `mode=max`), a
  pinned BuildKit version

| `kubernetes`
| In pods of a Kubernetes cluster
| Shared, scalable builders; native nodes per architecture

| `remote`
| An existing BuildKit daemon you manage (TCP or Unix socket)
| Self-hosted build farms

| `cloud`
| Docker Build Cloud
| Managed builders with native amd64/arm64 and a shared cache (a Docker subscription feature)
|===

[source,shell]
----
docker buildx ls                                        # builders and their platforms
docker buildx create --name ci --driver docker-container --use --bootstrap
docker buildx inspect ci
docker buildx build --builder ci -t myorg/orders:dev --load .
docker buildx rm ci
----

Derived from https://docs.docker.com/build/builders/[Builders] and
https://docs.docker.com/build/builders/drivers/[Build drivers]. With the containerd image store (the Engine 29
default on fresh installs) the `docker` driver can itself build and store multi-platform images and attestations,
which removes the most common reason for a `docker-container` builder on a laptop.

== Multi-platform builds

A multi-platform image is an image index with one manifest per platform (see
xref:backend/docker/images-layers-and-tags.adoc#_manifests_manifest_lists_and_multi_platform_images[Images,
Layers and Tags]). Buildx builds all platforms in one command:

[source,shell]
----
docker buildx build --platform linux/amd64,linux/arm64 -t registry.example.com/myorg/orders:1.4.0 --push .
docker buildx imagetools inspect registry.example.com/myorg/orders:1.4.0
----

[mermaid]
....
flowchart LR
  df["Dockerfile + context"] --> bx["docker buildx build<br/>--platform linux/amd64,linux/arm64"]
  bx --> a["linux/amd64 build<br/>(native or emulated)"]
  bx --> b["linux/arm64 build<br/>(native or emulated)"]
  a --> ma["amd64 manifest"]
  b --> mb["arm64 manifest"]
  ma --> idx["Image index (manifest list)"]
  mb --> idx
  idx --> reg["Registry tag orders:1.4.0"]
....

There are three ways to produce the non-native platforms:

* *Emulation with QEMU* -- BuildKit runs foreign binaries through `binfmt_misc` handlers. Docker Desktop has them
  preinstalled; on Linux run `docker run --privileged --rm tonistiigi/binfmt --install all` (or
  `docker/setup-qemu-action` in CI). Simple, but compiling under emulation is several times slower.
* *Native nodes* -- a builder with one node per architecture (`docker buildx create --append`), or Docker Build
  Cloud.
* *Cross-compilation* -- run the compiler on the build platform and target the other one. The predefined arguments
  `BUILDPLATFORM`, `TARGETPLATFORM`, `TARGETOS` and `TARGETARCH` make this explicit:

[source,dockerfile]
----
# syntax=docker/dockerfile:1
# The JDK stage always runs natively; Java bytecode is platform-independent
FROM --platform=$BUILDPLATFORM eclipse-temurin:25-jdk AS build
WORKDIR /src
COPY . .
RUN --mount=type=cache,target=/root/.m2 ./mvnw -B -ntp package -DskipTests

# The runtime stage is resolved per target platform (amd64 and arm64 JRE variants)
FROM eclipse-temurin:25-jre
ARG TARGETARCH
RUN echo "building the runtime layer for ${TARGETARCH}"
COPY --from=build /src/target/*.jar /app/app.jar
ENTRYPOINT ["java", "-jar", "/app/app.jar"]
----

Derived from https://docs.docker.com/build/building/multi-platform/[Multi-platform builds]. For JVM applications
this is the ideal case: Maven runs once, natively, and only the JRE base differs per platform.

== Exporters: where the result goes

[cols="1,3",options="header"]
|===
| Output | Meaning

| `--load` (`type=docker`)
| Load the image into the local Docker image store (default for the `docker` driver)

| `--push` (`type=registry`)
| Push the image, its index and attestations to a registry

| `type=image`
| An image in the builder, optionally pushed (`push=true`, `name=...`, `compression=zstd`, ...)

| `type=oci` / `type=docker` with `dest=file.tar`
| An OCI layout or Docker tarball on disk

| `type=local,dest=./out` / `type=tar`
| The final stage's filesystem as files -- useful to extract build artifacts such as a JAR or test reports
|===

[source,shell]
----
docker buildx build --target test --output type=local,dest=./test-reports .   # copy a stage's files out
docker buildx build --output type=oci,dest=orders.oci.tar -t orders:1.4.0 .
----

Derived from https://docs.docker.com/build/exporters/[Exporters overview].

== Remote cache backends

A builder's local cache is lost when an ephemeral CI runner disappears. Cache backends export it and import it on
the next run:

[cols="1,3",options="header"]
|===
| Backend | Stores the cache in

| `inline`
| The image itself (only `mode=min`); simplest, works with the `docker` driver

| `registry`
| A separate cache image in a registry (`ref=registry.example.com/myorg/orders:buildcache`)

| `local`
| A directory -- combine with `actions/cache` or a shared volume

| `gha`
| The GitHub Actions cache service; the recommended choice inside GitHub Actions workflows

| `s3` / `azblob`
| An S3-compatible bucket or Azure Blob Storage
|===

`mode=min` (the default) exports only the layers of the final image; `mode=max` also exports intermediate stages,
which is what makes the dependency stage of a multi-stage build hit the cache next time.

[source,shell]
----
docker buildx build --push -t registry.example.com/myorg/orders:1.4.0 \
  --cache-from type=registry,ref=registry.example.com/myorg/orders:buildcache \
  --cache-to type=registry,ref=registry.example.com/myorg/orders:buildcache,mode=max .
----

Derived from https://docs.docker.com/build/cache/backends/[Cache storage backends] and
https://docs.docker.com/build/cache/backends/registry/[Registry cache]. The `gha` backend is not supported by the
default `docker` driver; `docker/setup-buildx-action` creates a `docker-container` builder for exactly this reason
(see https://docs.docker.com/build/cache/backends/gha/[GitHub Actions cache]).

== Build checks

`docker build --check` evaluates the Dockerfile against rules such as `JSONArgsRecommended` (shell-form
`CMD`/`ENTRYPOINT`), `FromAsCasing`, `SecretsUsedInArgOrEnv`, `UndefinedVar` and `WorkdirRelativePath` without
building anything; a normal build prints the same warnings at the end.

[source,shell]
----
docker build --check .
docker build --check --build-arg "BUILDKIT_DOCKERFILE_CHECK=error=true" .     # fail on any violation
----

The same can be declared in the Dockerfile with `# check=error=true` or `# check=skip=<rules>`. Derived from
https://docs.docker.com/build/checks/[Checking your build configuration]; every rule is listed in the
https://docs.docker.com/reference/build-checks/[build checks reference].

== Attestations: SBOM and SLSA provenance

BuildKit can attach two kinds of attestations to an image, stored as extra manifests in its image index:

* an *SBOM* (SPDX) listing the packages in the image, generated by a scanner during the build;
* *SLSA provenance* describing how it was built -- the source, the build arguments, the builder, timestamps.

[source,shell]
----
docker buildx build --sbom=true --provenance=mode=max \
  -t registry.example.com/myorg/orders:1.4.0 --push .
docker buildx imagetools inspect registry.example.com/myorg/orders:1.4.0 --format '{{ json .SBOM.SPDX }}'
docker buildx imagetools inspect registry.example.com/myorg/orders:1.4.0 --format '{{ json .Provenance.SLSA }}'
----

Derived from https://docs.docker.com/build/metadata/attestations/[Build attestations],
https://docs.docker.com/build/metadata/attestations/sbom/[SBOM attestations] and
https://docs.docker.com/build/metadata/attestations/slsa-provenance/[Provenance attestations]. A minimal
provenance attestation is added by default when pushing; attestations need an exporter that can store an image
index (a registry push, or the containerd image store locally). Annotations -- OCI metadata on manifests and
indexes -- are covered on xref:backend/docker/images-layers-and-tags.adoc#_labels_and_annotations[Images, Layers
and Tags].

== Bake: builds as code

When a repository builds several images, or the same image with several variants, a long `docker buildx build`
command line becomes a *Bake* file. Bake reads HCL (or JSON, or a Compose file) describing targets, groups,
variables and matrices, and builds them in parallel:

[source,hcl]
----
# docker-bake.hcl
variable "TAG" {
  default = "dev"
}

group "default" {
  targets = ["orders", "billing"]
}

target "_common" {
  platforms  = ["linux/amd64", "linux/arm64"]
  cache-from = ["type=gha"]
  cache-to   = ["type=gha,mode=max"]
  labels = {
    "org.opencontainers.image.source" = "https://github.com/myorg/services"
  }
}

target "orders" {
  inherits = ["_common"]
  context  = "orders-service"
  tags     = ["ghcr.io/myorg/orders:${TAG}"]
}

target "billing" {
  inherits = ["_common"]
  context  = "billing-service"
  tags     = ["ghcr.io/myorg/billing:${TAG}"]
}
----

[source,shell]
----
docker buildx bake --print                 # resolved configuration, nothing built
TAG=1.4.0 docker buildx bake --push        # build and push both targets
docker buildx bake -f compose.yaml         # use the build sections of a Compose file as targets
----

Derived from https://docs.docker.com/build/bake/[Bake], https://docs.docker.com/build/bake/targets/[Bake targets],
https://docs.docker.com/build/bake/matrices/[Matrix targets] and
https://docs.docker.com/build/bake/compose-file/[Building with Bake from a Compose file]. `docker/bake-action`
runs the same file in GitHub Actions.

== Build policies (introduction only)

*Build policies* validate a build's inputs -- base images, Git sources, downloaded files -- against rules written in
Rego (Open Policy Agent), for example "base images must come from approved registries and carry provenance". They
are experimental (Buildx 0.31 or later, BuildKit 0.27 or later) and go beyond `ADD --checksum`, which only verifies
content. See https://docs.docker.com/build/policies/[Validating build inputs with policies].

== Remote builders

Two managed alternatives to running BuildKit yourself are named here for completeness:
https://docs.docker.com/build-cloud/[Docker Build Cloud] (the `cloud` driver: native amd64 and arm64 builders with a
shared cache) and the https://docs.docker.com/build/ci/github-actions/github-builder/[Docker GitHub Builder]
(reusable GitHub Actions workflows maintained by Docker that encapsulate runner selection, caching, provenance,
signing and multi-platform manifests).
