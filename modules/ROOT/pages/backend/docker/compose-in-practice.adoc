== Multiple Compose files

Compose can assemble one project from several files. There are three mechanisms:

image::docker-compose-merge.svg[A base compose.yaml merged with compose.override.yaml and a profile-gated service producing the effective configuration,width=700]

* *Merge* -- pass several files with `-f`; later files override earlier ones. Without `-f`, Compose reads
  `compose.yaml` *and* `compose.override.yaml` automatically. Single values (`image`, `command`) are replaced;
  `ports`, `expose`, `dns` and similar lists are concatenated; `environment`, `labels` and `volumes` are merged by
  key or mount path.
* *`extends`* -- a service inherits another service's configuration, from the same or another file.
* *`include`* -- imports another Compose file (local, Git or `oci://`) as a self-contained sub-project with its own
  relative paths; conflicts are errors rather than silent overrides.

[source,yaml]
----
# compose.yaml -- the base, committed
services:
  api:
    image: ghcr.io/myorg/orders-service:1.4.0
    environment:
      LOGGING_LEVEL_ROOT: INFO
----

[source,yaml]
----
# compose.override.yaml -- applied automatically in development
services:
  api:
    build: .
    ports:
      - "127.0.0.1:5005:5005"
    environment:
      LOGGING_LEVEL_ROOT: DEBUG
      JAVA_TOOL_OPTIONS: -agentlib:jdwp=transport=dt_socket,server=y,suspend=n,address=*:5005
----

[source,yaml]
----
# compose.yaml of a service that reuses a shared infrastructure definition
include:
  - path: ../platform/infra.compose.yaml
services:
  api:
    image: ghcr.io/myorg/orders-service:1.4.0
    depends_on: [kafka]
----

[source,shell]
----
docker compose config                                         # base + override, merged
docker compose -f compose.yaml -f compose.ci.yaml config      # an explicit set (no automatic override)
----

Derived from https://docs.docker.com/compose/how-tos/multiple-compose-files/[Use multiple Compose files],
https://docs.docker.com/compose/how-tos/multiple-compose-files/merge/[Merge],
https://docs.docker.com/compose/how-tos/multiple-compose-files/extends/[Extend] and
https://docs.docker.com/compose/how-tos/multiple-compose-files/include/[Include].

== Profiles

A service with `profiles: [...]` starts only when one of its profiles is active; services without `profiles` always
start. This keeps optional tooling in the same file:

[source,yaml]
----
services:
  prometheus:
    image: prom/prometheus:v3.6.0
    profiles: ["observability"]
  grafana:
    image: grafana/grafana:12.2.0
    profiles: ["observability"]
----

[source,shell]
----
docker compose --profile observability up -d
COMPOSE_PROFILES=observability,tools docker compose up -d
docker compose up -d grafana          # naming a service activates its profile implicitly
----

Derived from https://docs.docker.com/compose/how-tos/profiles/[Use service profiles].

== Compose Watch

Compose Watch updates running services as you edit files, without bind mounts: `sync` copies changed files into the
container, `rebuild` rebuilds the image and recreates the container, `sync+restart` copies and then restarts the
container, and `sync+exec` copies and runs a command.

[source,yaml]
----
services:
  web:
    build: .
    develop:
      watch:
        - action: sync
          path: ./src/main/resources/static
          target: /app/static
        - action: sync+restart
          path: ./config/application.yaml
          target: /app/config/application.yaml
        - action: rebuild
          path: pom.xml
        - action: rebuild
          path: ./src/main/java
----

[source,shell]
----
docker compose watch          # or: docker compose up --watch
----

[mermaid]
....
flowchart TD
  e(["File changed on the host"]) --> m{"Matches a watch rule path?"}
  m -->|No or ignored| n["Nothing happens"]
  m -->|action sync| s["Copy file into the running container"]
  m -->|action sync+restart| sr["Copy file, then restart the container"]
  m -->|action sync+exec| se["Copy file, then run the configured command"]
  m -->|action rebuild| r["docker compose build for the service"]
  r --> rc["Recreate the container from the new image"]
....

Derived from https://docs.docker.com/compose/how-tos/file-watch/[Use Compose Watch] and the
https://docs.docker.com/reference/compose-file/develop/[Compose Develop Specification] (which documents
`sync+exec`, available since Compose 2.32). For Java, a `rebuild` rule on
sources is the simple, reliable choice; for faster reloads combine `sync` of compiled classes with Spring Boot
DevTools. Watch needs the image to contain the files' target directories and, for `sync`, a user that may write
them.

== Lifecycle hooks and init containers

Hooks run commands in a service's container around its lifecycle: `post_start` after it starts, `pre_stop` before
Compose stops it (not when it exits by itself). `pre_start` runs *before* the main container starts -- either a
command in the service's own image or a separate image -- which is how Compose expresses init containers:

[source,yaml]
----
services:
  api:
    image: ghcr.io/myorg/orders-service:1.4.0
    user: "10001:10001"
    volumes:
      - uploads:/data/uploads
    pre_start:
      - image: busybox:1.37
        user: root
        command: ["chown", "-R", "10001:10001", "/data/uploads"]   # fix ownership before the app starts
    post_start:
      - command: ["/bin/sh", "-c", "echo started > /tmp/started"]
    pre_stop:
      - command: ["/bin/sh", "-c", "echo draining > /tmp/stopping"]
volumes:
  uploads:
----

Derived from https://docs.docker.com/compose/how-tos/lifecycle/[Use lifecycle hooks] and
https://docs.docker.com/compose/how-tos/init-containers/[Use init containers]. Database migrations are the classic
init step; for Spring Boot services Flyway or Liquibase usually run inside the application instead.

== Secrets and configs

Compose secrets are files mounted read-only at `/run/secrets/<name>` inside the services that request them. Unlike
`environment:`, they do not appear in `docker inspect`, in the process environment inherited by child processes,
or in logs that dump the environment:

[source,yaml]
----
services:
  api:
    image: ghcr.io/myorg/orders-service:1.4.0
    secrets:
      - db_password
    environment:
      SPRING_DATASOURCE_PASSWORD_FILE: /run/secrets/db_password   # read by the app or an entrypoint script
    configs:
      - source: app_config
        target: /app/config/application.yaml

secrets:
  db_password:
    file: ./secrets/db_password.txt      # not committed; or environment: DB_PASSWORD to take it from a variable
configs:
  app_config:
    file: ./config/application.yaml
----

Derived from https://docs.docker.com/compose/how-tos/use-secrets/[Manage secrets securely in Docker Compose] and
the https://docs.docker.com/reference/compose-file/configs/[configs] reference. Spring Boot can read such files
directly with a config tree: `spring.config.import=optional:configtree:/run/secrets/`.

== Provider services, GPUs and models

*Provider services* let Compose delegate a service to an external provider plugin instead of running a container
-- for example a managed database or a tunnel -- while other services still depend on it by name:

[source,yaml]
----
services:
  database:
    provider:
      type: awesomecloud          # a Compose provider plugin available on the PATH
      options:
        type: mysql
  app:
    image: myapp:1.0
    depends_on:
      - database
----

*GPU access* is requested as a device reservation:

[source,yaml]
----
services:
  trainer:
    image: nvidia/cuda:13.0.1-base-ubuntu24.04
    command: nvidia-smi
    deploy:
      resources:
        reservations:
          devices:
            - driver: nvidia
              count: 1
              capabilities: [gpu]
----

*Models* declare AI models that Docker Model Runner serves to a service, which receives the endpoint and model name
as environment variables:

[source,yaml]
----
services:
  chat-app:
    image: my-chat-app:1.0
    models:
      - llm
models:
  llm:
    model: ai/smollm2
----

Derived from https://docs.docker.com/compose/how-tos/provider-services/[Use provider services],
https://docs.docker.com/compose/how-tos/gpu-support/[Enable GPU support] and
https://docs.docker.com/ai/compose/models-and-compose/[Define AI models in Docker Compose applications]. Docker
Model Runner itself is out of scope for this section.

== Compose Bridge: from Compose to Kubernetes

Compose Bridge converts a Compose file into Kubernetes manifests (and a Kustomize overlay) using templates you can
customise, which is a practical first step when a Compose-defined application has to move to Kubernetes:

[source,shell]
----
docker compose bridge convert                # writes ./out with Kubernetes manifests
kubectl apply -k out/overlays/desktop        # deploy to Docker Desktop's Kubernetes cluster
----

Derived from https://docs.docker.com/compose/bridge/[Overview of Compose Bridge] and
https://docs.docker.com/compose/bridge/usage/[Use the default Compose Bridge transformation]. See also
xref:backend/docker/orchestration-swarm-and-kubernetes.adoc[Orchestration: Swarm Mode and Kubernetes].

== Compose applications as OCI artifacts

A Compose application can be published to any OCI registry and run from there without cloning a repository:

[source,shell]
----
docker compose publish myorg/orders-stack:1.4.0
docker compose -f oci://docker.io/myorg/orders-stack:1.4.0 up -d
----

Derived from https://docs.docker.com/compose/how-tos/oci-artifact/[Package and deploy Docker Compose applications
as OCI artifacts]. Environment variables are left out unless you pass `--with-env`, and Compose scans the
configuration for sensitive data and asks for confirmation before publishing anything that looks like a secret.

== Compose in production -- and the trust model

Compose runs happily on a single production host: keep a base `compose.yaml` and a `compose.production.yaml`
override that removes development bind mounts, sets `restart: always`, pins image digests and adds resource
limits, then deploy with `docker compose -f compose.yaml -f compose.production.yaml up -d`. Multi-host scheduling,
rolling updates and self-healing across machines are orchestrator territory (see
xref:backend/docker/orchestration-swarm-and-kubernetes.adoc[Orchestration]). Derived from
https://docs.docker.com/compose/how-tos/production/[Use Compose in production].

Compose treats every Compose file as *trusted input*: a file can request `privileged: true`, bind-mount `/`, or
mount the Docker socket, and Compose applies it exactly as `docker run` would. That also holds for files pulled in
through `include` or `extends` from Git or `oci://` references. Review remote Compose files like code, pin remote
references to digests, and prefer local copies for anything that runs with privileges. Derived from
https://docs.docker.com/compose/trust-model/[Compose trust model].
