= Java and Spring Boot Images
:description: Three ways to containerize a Spring Boot 4.1 / Java 25 service and how to choose -- a multi-stage Dockerfile with a cached Maven repository and Spring Boot's layered jar extraction (java -Djarmode=tools extract --layers), Cloud Native Buildpacks via spring-boot:build-image, and Jib -- plus docker init for Java, a .dockerignore for Maven, JVM memory settings, health checks, graceful shutdown and Docker Hardened Images.

include::partial$docker-disclaimer.adoc[]

This page turns a Spring Boot 4.1.x service on Java 25 into a container image, three ways: a hand-written
multi-stage Dockerfile, Cloud Native Buildpacks through `spring-boot:build-image`, and Jib. It builds on the generic
material in xref:backend/docker/build-cache-and-multi-stage-builds.adoc[Build Cache and Multi-Stage Builds] and
targets Docker Engine 29.8.x with BuildKit 0.33.x and the `docker/dockerfile:1` frontend. The Quarkus counterpart --
Quarkus's own Jib, Docker, Buildpacks and OpenShift extensions -- is on
xref:backend/quarkus/container-images.adoc[Quarkus: Container Images].

== Path 1: a multi-stage Dockerfile with layered extraction

A Spring Boot executable jar contains a `layers.idx` index that groups its content by how often it changes:
`dependencies`, `spring-boot-loader`, `snapshot-dependencies` and `application`. The `tools` jar mode extracts the
jar into one directory per layer, so each can become a separate image layer and a code change re-ships only the
small `application` layer:

image::docker-spring-boot-layered-jar.svg[Layered Spring Boot image with separate dependencies and loader and snapshot and application layers compared with a fat jar copied as a single layer,width=700]

[source,dockerfile]
----
# syntax=docker/dockerfile:1

# ---- build: compile with the Maven wrapper, caching ~/.m2 across builds; runs on the builder's own platform
FROM --platform=$BUILDPLATFORM eclipse-temurin:25-jdk AS build
WORKDIR /src
COPY mvnw pom.xml ./
COPY .mvn/ .mvn/
RUN --mount=type=cache,target=/root/.m2 ./mvnw -B -ntp dependency:go-offline
COPY src/ src/
RUN --mount=type=cache,target=/root/.m2 ./mvnw -B -ntp package -DskipTests \
 && cp target/*.jar /tmp/application.jar

# ---- extract: split the jar into its layers
FROM eclipse-temurin:25-jre AS extract
WORKDIR /builder
COPY --from=build /tmp/application.jar application.jar
RUN java -Djarmode=tools -jar application.jar extract --layers --destination extracted

# ---- runtime: JRE, non-root, one COPY per layer (least to most frequently changed)
FROM eclipse-temurin:25-jre AS runtime
RUN apt-get update \
 && apt-get install -y --no-install-recommends curl \
 && rm -rf /var/lib/apt/lists/* \
 && groupadd --system --gid 10001 app \
 && useradd --system --uid 10001 --gid app --no-create-home app
WORKDIR /application
COPY --from=extract /builder/extracted/dependencies/ ./
COPY --from=extract /builder/extracted/spring-boot-loader/ ./
COPY --from=extract /builder/extracted/snapshot-dependencies/ ./
COPY --from=extract /builder/extracted/application/ ./
USER 10001:10001
EXPOSE 8080
ENV MANAGEMENT_ENDPOINT_HEALTH_PROBES_ENABLED=true
HEALTHCHECK --interval=15s --timeout=3s --start-period=60s --retries=3 \
  CMD ["curl", "-fsS", "http://localhost:8080/actuator/health/readiness"]
STOPSIGNAL SIGTERM
ENTRYPOINT ["java", "-XX:MaxRAMPercentage=75", "-jar", "application.jar"]
----

[source,shell]
----
docker build -t orders-service:1.4.0 .
docker run --rm -p 127.0.0.1:8080:8080 --memory 768m orders-service:1.4.0
docker image history orders-service:1.4.0     # the application layer is only a few hundred KB
----

Derived from Spring Boot's https://docs.spring.io/spring-boot/reference/packaging/container-images/efficient-images.html[Efficient
Container Images] and
https://docs.spring.io/spring-boot/reference/packaging/container-images/dockerfiles.html[Dockerfiles] pages (the
`extract --layers --destination extracted` command and one `COPY` per layer are taken from there) and Docker's
https://docs.docker.com/guides/java/#containerize-a-java-application[Java guide]. Notes on the choices:

* *`--platform=$BUILDPLATFORM` on the build stage*: the jar it produces is platform-independent bytecode, so in a
  multi-platform build (`--platform linux/amd64,linux/arm64`) Maven runs once, natively on the builder, instead of
  once per target under QEMU emulation. The `extract` and `runtime` stages keep the default target platform, so each
  image gets a JRE (and `curl`) for its own architecture; only `application.jar` crosses from the build stage. See
  xref:backend/docker/buildkit-and-buildx.adoc#_multi_platform_builds[BuildKit and Buildx].

* *`eclipse-temurin:25-jre`* is the Eclipse Temurin JRE on Ubuntu. It ships neither `curl` nor `wget`, hence the
  explicit install for the `HEALTHCHECK`; drop both if your platform probes the endpoint itself (Kubernetes,
  ECS), which is the more common production setup.
* *Readiness probe*: `/actuator/health/readiness` requires Spring Boot Actuator; probe groups are enabled
  automatically on Kubernetes and elsewhere with `management.endpoint.health.probes.enabled=true` (set here through
  the environment).
* *Memory*: `-XX:MaxRAMPercentage=75` sizes the heap from the container limit (see
  xref:backend/docker/resources-logging-and-monitoring.adoc#_what_the_jvm_sees[What the JVM sees]).
* *Graceful shutdown*: the JVM is PID 1 in exec form, so `SIGTERM` triggers Spring Boot's graceful shutdown
  (enabled by default); keep the orchestrator's stop timeout above `spring.lifecycle.timeout-per-shutdown-phase`
  (30 seconds by default).
* *AOT cache*: on Java 25 Spring Boot documents an extra training-run step
  (`java -XX:AOTCacheOutput=app.aot -Dspring.context.exit=onRefresh -jar application.jar`) and
  `-XX:AOTCache=app.aot` at start-up for faster start times; see the Dockerfiles page linked above.

=== `.dockerignore` for a Maven project

[source,text]
----
.git
.github
.idea
.vscode
*.iml
target/
**/*.log
.env
compose*.yaml
----

The Dockerfile above builds inside Docker, so `target/` is excluded entirely. Derived from
https://docs.docker.com/build/concepts/context/#dockerignore-files[.dockerignore files].

=== Docker Hardened Images instead of Temurin

Swap the `FROM` lines for a Docker Hardened Image pair -- a `-dev` Maven/JDK image for the build stage and a
distroless JRE image for the runtime stage -- following Docker's
https://docs.docker.com/dhi/migration/examples/java/[Java migration example]. The runtime variant has no shell or
package manager, so remove the `apt-get` step and the `HEALTHCHECK` and probe from the platform instead.

=== `docker init` for Java

`docker init` asks a few questions and writes a `Dockerfile`, `compose.yaml`, `.dockerignore` and `README.Docker.md`
for a Maven project packaged as an uber jar -- a reasonable starting point to adapt to the layered layout above:

[source,shell]
----
docker init        # choose "Java", the source directory, the Java version and the port
----

Derived from https://docs.docker.com/reference/cli/docker/init/[`docker init`].

== Path 2: Cloud Native Buildpacks with `spring-boot:build-image`

The Spring Boot Maven plugin can build an OCI image without a Dockerfile, using a Cloud Native Buildpacks builder
(Paketo's `paketobuildpacks/builder-noble-java-tiny` by default). The Java buildpack installs a JRE matching the
project's Java version, applies the jar's layer index, and computes memory flags at container start from the
container limit.

[source,shell]
----
./mvnw spring-boot:build-image \
  -Dspring-boot.build-image.imageName=ghcr.io/myorg/orders-service:1.4.0
docker run --rm -p 127.0.0.1:8080:8080 ghcr.io/myorg/orders-service:1.4.0
----

[source,xml]
----
<plugin>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-maven-plugin</artifactId>
  <configuration>
    <image>
      <name>ghcr.io/myorg/${project.artifactId}:${project.version}</name>
      <env>
        <BP_JVM_VERSION>25</BP_JVM_VERSION>
        <BPE_DELIM_JAVA_TOOL_OPTIONS xml:space="preserve"> </BPE_DELIM_JAVA_TOOL_OPTIONS>
        <BPE_APPEND_JAVA_TOOL_OPTIONS>-XX:+HeapDumpOnOutOfMemoryError</BPE_APPEND_JAVA_TOOL_OPTIONS>
      </env>
    </image>
    <docker>
      <publishRegistry>
        <url>${docker.publishRegistry.url}</url>
        <username>${docker.publishRegistry.username}</username>
        <password>${docker.publishRegistry.password}</password>
      </publishRegistry>
    </docker>
  </configuration>
</plugin>
----

With that configuration a CI job can build and push in one step, passing credentials as properties -- this is the
command the house `deploy.yml` uses (see xref:backend/docker/ci-cd-with-github-actions.adoc#_the_house_deploy_yml_variant[Docker
CI/CD with GitHub Actions]):

[source,shell]
----
./mvnw -B -ntp spring-boot:build-image -DskipTests \
  -Dspring-boot.build-image.imageName=ghcr.io/myorg/orders-service:1.4.0 \
  -Dspring-boot.build-image.publish=true \
  -Ddocker.publishRegistry.url=ghcr.io \
  -Ddocker.publishRegistry.username="$REGISTRY_USERNAME" \
  -Ddocker.publishRegistry.password="$REGISTRY_PASSWORD"
----

Derived from the Spring Boot Maven plugin's https://docs.spring.io/spring-boot/maven-plugin/build-image.html[Packaging
OCI Images] page (image name, builder, `env`, `publish` and `docker.publishRegistry` parameters, and the
runtime-JVM-configuration example), https://buildpacks.io/[Cloud Native Buildpacks] and
https://paketo.io/[Paketo Buildpacks]. Without `docker.publishRegistry` credentials the plugin falls back to the
credential helpers and `~/.docker/config.json`. Buildpacks also work with Podman or Colima by pointing the
plugin's `docker.host` at their socket.

== Path 3: Jib

Jib builds images from the Maven project directly -- no Dockerfile and no Docker daemon -- with layers for
dependencies, resources and classes, and reproducible timestamps by default:

[source,shell]
----
./mvnw compile com.google.cloud.tools:jib-maven-plugin:3.5.2:build \
  -Djib.from.image=eclipse-temurin:25-jre \
  -Dimage=ghcr.io/myorg/orders-service:1.4.0
./mvnw compile com.google.cloud.tools:jib-maven-plugin:3.5.2:dockerBuild -Dimage=orders-service:dev   # into the local daemon
----

Derived from the https://github.com/GoogleContainerTools/jib/tree/master/jib-maven-plugin[Jib Maven plugin
documentation]. The Quarkus page covers Jib in more depth (it is Quarkus's default container-image extension); see
xref:backend/quarkus/container-images.adoc[Quarkus: Container Images].

== Native images

A GraalVM native executable (`./mvnw -Pnative spring-boot:build-image` or `native:compile`) starts in milliseconds
and uses far less memory, at the cost of build time and reflection configuration. It is out of scope here; see
Spring Boot's https://docs.spring.io/spring-boot/reference/packaging/native-image/index.html[GraalVM Native Image
Support].
