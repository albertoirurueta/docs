A Dockerfile is a text file of instructions that BuildKit executes, top to bottom, to produce an image. Chapter 3 of
_Learning Docker_ surveys every instruction as it existed in Docker 1.5; this page does the same for the current
Dockerfile frontend (`docker/dockerfile:1`, executed by BuildKit 0.33.x under Docker Engine 29.8.x and Buildx
0.37.x), flags which parts of that survey are obsolete, and adds everything introduced since -- parser directives,
`RUN --mount`, `COPY --link`/`--parents`/`--exclude`, here-documents and build checks. The build cache and
multi-stage builds, which shape how a Dockerfile should be ordered, get their own page:
xref:backend/docker/build-cache-and-multi-stage-builds.adoc[Build Cache and Multi-Stage Builds].

== A first Dockerfile

[source,dockerfile]
----
# syntax=docker/dockerfile:1
FROM eclipse-temurin:25-jre
WORKDIR /app
COPY target/orders-service.jar app.jar
EXPOSE 8080
USER 10001
ENTRYPOINT ["java", "-jar", "/app/app.jar"]
----

[source,shell]
----
./mvnw -q package -DskipTests
docker build -t orders-service:dev .
docker run --rm -p 8080:8080 orders-service:dev
----

Derived from https://docs.docker.com/build/concepts/dockerfile/[Dockerfile overview]. This works, but it re-copies a
fat JAR as one layer and builds the JAR outside Docker; the production-grade version is on
xref:backend/docker/java-and-spring-boot-images.adoc[Java and Spring Boot Images].

== How a build works

[mermaid]
....
flowchart LR
  ctx["Build context<br/>(directory minus .dockerignore)"] --> cli["docker build<br/>(Buildx client)"]
  df["Dockerfile"] --> cli
  cli -->|"sends context and definition"| bk["BuildKit"]
  bk --> fe["Dockerfile frontend<br/>syntax=docker/dockerfile:1"]
  fe --> llb["LLB build graph"]
  llb --> solver["Solver: cache lookup,<br/>parallel steps"]
  solver --> l1["Layer: FROM base"]
  solver --> l2["Layer: RUN / COPY / ADD"]
  solver --> cfg["Config: CMD, ENV, USER,<br/>EXPOSE, LABEL"]
  l1 --> img["Image (manifest + config + layers)"]
  l2 --> img
  cfg --> img
....

Only `RUN`, `COPY` and `ADD` create filesystem layers; every other instruction only changes the image
configuration. Derived from https://docs.docker.com/build/concepts/overview/[Docker Build overview].

== Parser directives

Parser directives are special comments that must appear at the very top of the file, before any instruction or
blank line.

[cols="1,3",options="header"]
|===
| Directive | Purpose

| `# syntax=docker/dockerfile:1`
| Selects the Dockerfile *frontend* image. `docker/dockerfile:1` always resolves to the latest stable 1.x release,
  so new instructions and flags become available without upgrading Docker itself. Put it in every Dockerfile.

| `# escape=\``
| Changes the escape character from `\` to a backtick -- useful for Windows paths.

| `# check=skip=<checks>` / `# check=error=true`
| Configures build checks: skip named rules (`JSONArgsRecommended,StageNameCasing`) or fail the build on any
  violation. See xref:backend/docker/buildkit-and-buildx.adoc#_build_checks[Build checks].
|===

== Instruction reference

=== `FROM`

`FROM [--platform=<platform>] <image>[:<tag>|@<digest>] [AS <name>]` starts a build stage. A Dockerfile can have
several `FROM` lines -- each begins a new stage, and `AS` names it for `COPY --from` and `--target` (see
xref:backend/docker/build-cache-and-multi-stage-builds.adoc[multi-stage builds]). `FROM scratch` starts from an
empty filesystem. `ARG` is the only instruction allowed before the first `FROM`, to parameterise the base image:

[source,dockerfile]
----
# syntax=docker/dockerfile:1
ARG JAVA_VERSION=25
FROM eclipse-temurin:${JAVA_VERSION}-jre
----

Derived from https://docs.docker.com/reference/dockerfile/#understand-how-arg-and-from-interact[Understand how ARG
and FROM interact].

`--platform=$BUILDPLATFORM` pins a stage to the machine doing the build, which is how cross-compilation works in
multi-platform builds (see xref:backend/docker/buildkit-and-buildx.adoc[BuildKit and Buildx]).

=== `RUN`

`RUN` executes a command in a new layer on top of the current image. It has two forms:

* *Shell form* -- `RUN apt-get update && apt-get install -y curl` -- runs through `/bin/sh -c`, so variables,
  pipes and `&&` work.
* *Exec form* -- `RUN ["/usr/bin/mvn", "-B", "package"]` -- a JSON array executed directly, with no shell
  processing.

The options that make `RUN` powerful are BuildKit additions:

[cols="1,3",options="header"]
|===
| Option | Effect

| `--mount=type=cache,target=<path>`
| A persistent cache directory across builds (Maven's `~/.m2`, npm's cache), not stored in the image.

| `--mount=type=bind`
| Bind-mounts files from the context or another stage without copying them into a layer.

| `--mount=type=secret,id=<id>`
| Exposes a secret as a file (default `/run/secrets/<id>`) or environment variable for this one step only.

| `--mount=type=ssh`
| Forwards the host's SSH agent, for example to clone private Git repositories.

| `--mount=type=tmpfs,target=<path>`
| A scratch in-memory filesystem for this step.

| `--network=default\|none\|host`
| Controls network access for the step (`host` needs the `network.host` entitlement).

| `--security=insecure\|sandbox`
| Runs the step without the sandbox (needs the `security.insecure` entitlement); rarely needed.

| `--device`
| Gives the step access to a CDI device, for example a GPU (Dockerfile 1.27 or later).
|===

[source,dockerfile]
----
# syntax=docker/dockerfile:1
FROM eclipse-temurin:25-jdk AS build
WORKDIR /src
COPY . .
RUN --mount=type=cache,target=/root/.m2 ./mvnw -B -ntp package -DskipTests
----

Derived from https://docs.docker.com/reference/dockerfile/#run[`RUN`] and
https://docs.docker.com/reference/dockerfile/#run---mount[`RUN --mount`]. Every mount type is explained with
examples on xref:backend/docker/build-cache-and-multi-stage-builds.adoc[Build Cache and Multi-Stage Builds].

=== Here-documents

`RUN`, `COPY` and `ADD` accept here-documents, which replace long `&& \` chains with a readable script that still
produces one layer:

[source,dockerfile]
----
# syntax=docker/dockerfile:1
FROM debian:trixie-slim
RUN <<EOF
set -eu
apt-get update
apt-get install -y --no-install-recommends curl ca-certificates
rm -rf /var/lib/apt/lists/*
EOF
COPY <<EOF /etc/app/defaults.properties
server.port=8080
EOF
----

Derived from https://docs.docker.com/reference/dockerfile/#here-documents[Here-documents].

=== `CMD` and `ENTRYPOINT`

`ENTRYPOINT` is the executable the container runs; `CMD` provides default arguments to it -- or, when there is no
`ENTRYPOINT`, the default command itself. `docker run <image> <args>` replaces `CMD`; `docker run --entrypoint`
replaces `ENTRYPOINT`. Both have a shell form and an exec form, and the combination decides what actually runs:

image::docker-cmd-entrypoint-matrix.svg[CMD and ENTRYPOINT interaction matrix showing the command executed for each combination of exec form and shell form,width=700]

[cols="2,2,2,3",options="header"]
|===
| | No `ENTRYPOINT` | `ENTRYPOINT exec_entry p1_entry` | `ENTRYPOINT ["exec_entry", "p1_entry"]`

| *No `CMD`*
| error, not allowed
| `/bin/sh -c exec_entry p1_entry`
| `exec_entry p1_entry`

| *`CMD ["exec_cmd", "p1_cmd"]`*
| `exec_cmd p1_cmd`
| `/bin/sh -c exec_entry p1_entry`
| `exec_entry p1_entry exec_cmd p1_cmd`

| *`CMD exec_cmd p1_cmd`*
| `/bin/sh -c exec_cmd p1_cmd`
| `/bin/sh -c exec_entry p1_entry`
| `exec_entry p1_entry /bin/sh -c exec_cmd p1_cmd`
|===

Derived from https://docs.docker.com/reference/dockerfile/#understand-how-cmd-and-entrypoint-interact[Understand how
CMD and ENTRYPOINT interact]. The practical rules:

* Use the *exec form* for `ENTRYPOINT` and `CMD`. In shell form the process is `/bin/sh`, which becomes PID 1 and
  does not forward `SIGTERM` to your application, so `docker stop` waits for the timeout and then kills it (see
  xref:backend/docker/running-containers.adoc#_signals_exit_codes_and_graceful_shutdown[graceful shutdown]).
* A shell-form `ENTRYPOINT` ignores `CMD` and any `docker run` arguments entirely.
* For an image that behaves like a command, put the program in `ENTRYPOINT` and its default flags in `CMD`.

=== `COPY` and `ADD`

`COPY` copies files from the build context, another stage (`--from=<stage>`) or an image
(`--from=<image>`) into the image. `ADD` does the same and can also fetch remote URLs and Git repositories and
auto-extract local tar archives. Prefer `COPY`; use `ADD` only when you need its extra behaviour, and then verify
remote content with `--checksum`.

[cols="1,3",options="header"]
|===
| Flag | Effect

| `--chown=<user>:<group>`
| Sets ownership of the copied files (otherwise root).

| `--chmod=<perms>`
| Sets permissions, octal or symbolic.

| `--link`
| Copies into an independent layer that does not depend on previous layers, so changing the base image does not
  invalidate it and the layer can be rebased without re-copying.

| `--parents`
| Preserves the parent directories of the source paths (`COPY --parents ./services/*/pom.xml /src/`).

| `--exclude=<pattern>`
| Excludes matching paths from the copy.

| `ADD --checksum=<hash>`
| Verifies a remote HTTP artifact (`sha256:...`) or Git commit.

| `ADD --keep-git-dir` / `ADD --unpack`
| Keep `.git` when adding a Git repository; control tar extraction explicitly.
|===

[source,dockerfile]
----
# syntax=docker/dockerfile:1
FROM eclipse-temurin:25-jre
ADD --checksum=sha256:bbf83c151b6400709e2f225bdd07a04f839d9d13b8b93464241333fd25d3e3ba \
    https://repo1.maven.org/maven2/io/opentelemetry/javaagent/opentelemetry-javaagent/2.31.1/opentelemetry-javaagent-2.31.1.jar \
    /opt/otel/opentelemetry-javaagent.jar
COPY --link --chown=10001:10001 --exclude=*.md target/app/ /app/
----

Derived from https://docs.docker.com/reference/dockerfile/#copy[`COPY`] and
https://docs.docker.com/reference/dockerfile/#add[`ADD`].

=== `WORKDIR`

Sets the working directory for subsequent `RUN`, `CMD`, `ENTRYPOINT`, `COPY` and `ADD`, creating it if needed.
Always use it instead of `RUN cd ... && ...`; relative `WORKDIR`s are resolved against the previous one.

=== `ENV` and `ARG`

[cols="1,2,2",options="header"]
|===
| | `ARG` | `ENV`

| Available during the build
| Yes, from its declaration to the end of the stage
| Yes, from its declaration

| Present in the running container
| No
| Yes -- persisted in the image configuration

| Set from outside
| `docker build --build-arg NAME=value`
| `docker run -e NAME=value` (runtime only)

| Scope
| Per stage; an `ARG` before `FROM` must be re-declared (`ARG NAME`) inside a stage to be used there
| Inherited by later stages built `FROM` this one
|===

Changing a build argument's value invalidates the cache from the first instruction that uses it. BuildKit
predefines platform arguments (`TARGETPLATFORM`, `TARGETOS`, `TARGETARCH`, `BUILDPLATFORM`, ...), proxy arguments
(`HTTP_PROXY`, `NO_PROXY`, ...) that are exempt from the cache, and `BUILDKIT_*` arguments that tune the build.
Never pass credentials through `ARG` or `ENV`. `ENV` values are stored in the image, and `ARG` values appear in
the build history. Use `RUN --mount=type=secret` (see
xref:backend/docker/image-best-practices-and-security.adoc[Image Best Practices and Supply-Chain Security]).
Derived from https://docs.docker.com/build/building/variables/[Build variables].

=== `EXPOSE`

`EXPOSE 8080/tcp` documents which ports the application listens on. It does *not* publish anything; publishing is
done at run time with `-p` (or `-P`, which publishes every exposed port to a random host port). See
xref:backend/docker/networking.adoc[Networking].

=== `USER`

Sets the user (and optionally group) for subsequent `RUN` instructions and for the running container. Use a
numeric UID, create it if the base image does not have one, and switch to it before `ENTRYPOINT`:

[source,dockerfile]
----
# syntax=docker/dockerfile:1
FROM eclipse-temurin:25-jre
RUN groupadd --system --gid 10001 app && useradd --system --uid 10001 --gid app --no-create-home app
USER 10001:10001
----

Derived from https://docs.docker.com/reference/dockerfile/#user[`USER`].

=== `VOLUME`

`VOLUME /var/lib/data` marks a path whose data should live outside the container's writable layer; Docker creates
an anonymous volume there if none is mounted. Changes made to that path by later `RUN` instructions are discarded.
Declaring volumes in the image surprises users more often than it helps; prefer documenting the path and letting
the operator mount a named volume (see xref:backend/docker/storage-volumes-and-bind-mounts.adoc[Storage]).

=== `LABEL` (and the deprecated `MAINTAINER`)

`LABEL key="value" ...` adds metadata to the image configuration; use the `org.opencontainers.image.*` keys (see
xref:backend/docker/images-layers-and-tags.adoc#_labels_and_annotations[labels and annotations]). `MAINTAINER`,
which _Learning Docker_ still uses, is deprecated -- write `LABEL org.opencontainers.image.authors="..."` instead.

=== `HEALTHCHECK`

[source,dockerfile]
----
# syntax=docker/dockerfile:1
FROM eclipse-temurin:25-jre
# the JRE image does not ship curl, so install it for the check
RUN apt-get update \
 && apt-get install -y --no-install-recommends curl \
 && rm -rf /var/lib/apt/lists/*
COPY target/app.jar /app/app.jar
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "/app/app.jar"]
HEALTHCHECK --interval=30s --timeout=3s --start-period=30s --start-interval=2s --retries=3 \
  CMD ["curl", "-fsS", "http://localhost:8080/actuator/health/readiness"]
----

Docker runs the command periodically inside the container and reports `starting`, `healthy` or `unhealthy` in
`docker ps`; Compose's `condition: service_healthy` and Testcontainers' `Wait.forHealthcheck()` rely on it. The
command must exist in the image (a JRE-only or distroless image may not ship `curl`). `HEALTHCHECK NONE` disables a
check inherited from the base image. Derived from https://docs.docker.com/reference/dockerfile/#healthcheck[`HEALTHCHECK`].

=== `STOPSIGNAL`, `SHELL` and `ONBUILD`

* `STOPSIGNAL SIGTERM` sets the signal `docker stop` sends first (the default is `SIGTERM`; some servers want
  `SIGQUIT` or `SIGINT` for a graceful stop).
* `SHELL ["/bin/bash", "-o", "pipefail", "-c"]` changes the shell used by shell-form instructions -- useful to make
  pipelines fail properly, and on Windows images to switch to PowerShell.
* `ONBUILD <instruction>` registers an instruction to run when another image uses this one as its base. It hides
  behaviour from the downstream Dockerfile; avoid it in new images.

== The build context and `.dockerignore`

`docker build <context>` sends the context -- a local directory, a Git URL or a tarball -- to BuildKit. Only files in
the context can be copied, and BuildKit transfers only the files a build actually references. A `.dockerignore`
file at the context root excludes paths up front, keeping builds fast and secrets out of the image:

[source,text]
----
# .dockerignore for a Maven project
.git
.idea
*.iml
target/
!target/*.jar
**/*.log
.env
compose.yaml
----

Derived from https://docs.docker.com/build/concepts/context/[Build context]. A Dockerfile-specific ignore file
(`Dockerfile.dockerignore`, next to `Dockerfile`) takes precedence when present.

== `docker build` essentials

[source,shell]
----
docker build -t orders-service:1.4.0 .                    # context = current directory, ./Dockerfile
docker build -f docker/Dockerfile.native -t orders:native .   # a different Dockerfile
docker build --target build -t orders:build .             # stop at the stage named "build"
docker build --build-arg JAVA_VERSION=25 -t orders .      # set an ARG
docker build --no-cache -t orders .                       # ignore the cache for every step
docker build --progress=plain -t orders . 2>&1 | tee build.log   # full, unfolded step output
docker build --check .                                    # run build checks only, do not build
----

Derived from https://docs.docker.com/reference/cli/docker/buildx/build/[`docker buildx build`], which `docker
build` aliases. `--progress=plain` is invaluable when a `RUN` step fails: the default TTY output folds each step's
log.

== What changed since the 2015 books

[cols="2,3",options="header"]
|===
| 2015 practice | Current practice

| `MAINTAINER` instruction
| `LABEL org.opencontainers.image.authors=...`

| No `# syntax` directive; features tied to the Docker release
| `# syntax=docker/dockerfile:1` selects the frontend independently of the Engine

| Long `&& \` chains, secrets passed as `ARG`
| Here-documents, `RUN --mount=type=secret`

| One stage per Dockerfile, separate "build" images
| Multi-stage builds (Docker 17.05 and later)

| The legacy builder
| BuildKit (default since Docker 23.0), with build checks
|===
