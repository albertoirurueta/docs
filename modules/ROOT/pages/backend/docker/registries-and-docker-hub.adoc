A registry is where images live between `docker build` and `docker run`. _Learning Docker_ (chapters 4 and 5)
covers Docker Hub and the Python `docker-registry` of 2015; since then registries have been standardised by the
OCI distribution specification, Docker Hub has added access tokens, immutable tags and pull limits, and every
cloud provider runs an OCI registry. This page describes that landscape for Docker Engine 29.8.x and Buildx 0.37.x.

== How a registry works

A registry is an HTTP API (the OCI distribution specification, derived from Docker's Registry HTTP API V2) that
stores two kinds of objects per repository:

* *blobs* -- layers and image configurations, addressed by digest (`sha256:...`) and uploaded once;
* *manifests* (and image indexes) -- small JSON documents listing blobs, addressed by digest and optionally by one
  or more *tags*.

image::docker-registry-push-pull.svg[Push and pull between a client and a registry: blobs are checked and uploaded first then the manifest is put under a tag and a pull resolves the tag to a manifest and downloads missing blobs,width=700]

A *push* checks which blobs the registry already has (`HEAD /v2/<name>/blobs/<digest>`), uploads the missing ones,
then `PUT`s the manifest under a tag. A *pull* `GET`s the manifest by tag or digest, then downloads only the blobs
that are not already local. Pulling by digest skips the tag lookup and verifies content, which is why it is the
reproducible choice (see xref:backend/docker/images-layers-and-tags.adoc[Images, Layers and Tags]). Derived from
the https://github.com/opencontainers/distribution-spec/blob/main/spec.md[OCI distribution specification].

== Docker Hub

Docker Hub (`docker.io`) is the default registry for every unqualified image name.

* *Repositories* are `<namespace>/<name>`: your user or organisation namespace, or `library/` for Docker Official
  Images.
* *Docker Official Images* (`nginx`, `postgres`, `eclipse-temurin`) are curated, rebuilt for security fixes and
  documented; *Verified Publisher* images come from commercial vendors; both are "trusted content".
* *Immutable tags* can be enabled per repository so a pushed tag can never be overwritten.
* *Access tokens* replace passwords for the CLI and CI: *personal access tokens* (scoped read, read/write or
  read/write/delete) and *organisation access tokens*. Docker Hub also accepts OIDC connections from CI providers.

[source,shell]
----
docker login -u myuser                   # prompts; paste a personal access token, not the account password
echo "$DOCKERHUB_TOKEN" | docker login -u myuser --password-stdin    # non-interactive, e.g. CI
docker tag orders-service:1.4.0 myuser/orders-service:1.4.0
docker push myuser/orders-service:1.4.0
docker logout
----

Derived from https://docs.docker.com/docker-hub/quickstart/[Docker Hub quickstart],
https://docs.docker.com/docker-hub/repos/[Repositories] and
https://docs.docker.com/security/access-tokens/[Access tokens]. Credentials are stored in the OS keychain through a
credential helper when one is configured, otherwise base64-encoded in `~/.docker/config.json`.

=== Pull limits, and staying under them in CI

Docker Hub limits pulls per 6 hours: 100 for unauthenticated clients (per IPv4 address or IPv6 /64), 200 for
authenticated Personal accounts, unlimited for Pro, Team and Business. Shared CI runners hit the unauthenticated
limit quickly because many jobs share an address. The remedies:

[mermaid]
....
flowchart LR
  job["CI job: docker pull / Testcontainers"] --> auth{"Authenticated<br/>to Docker Hub?"}
  auth -->|No| lim["Shared IP limit<br/>100 pulls per 6 h"]
  auth -->|Yes| q{"Registry mirror or<br/>pull-through cache?"}
  q -->|Yes| mirror["Mirror / cache<br/>(Distribution proxy, Artifactory, ECR pull-through)"]
  q -->|No| hub["Docker Hub with the<br/>account's allowance"]
  mirror -->|cache miss only| hub
  mirror --> ok["Image served from cache"]
  hub --> ok
....

* *Authenticate every pull* with an access token (`docker/login-action` in GitHub Actions).
* *Use a mirror or pull-through cache* (`"registry-mirrors"` in `daemon.json` for Docker Hub, or a cloud
  registry's pull-through cache).
* *Mirror the few images you use* into GHCR or your cloud registry and reference them there.

Derived from https://docs.docker.com/docker-hub/usage/pulls/[Docker Hub pull usage and limits] and
https://docs.docker.com/docker-hub/image-library/mirror/[Mirror the Docker Hub library]. The Testcontainers side of
this, including image-name substitution, is on
xref:backend/docker/spring-boot-integration-tests-with-testcontainers.adoc[Spring Boot Integration Tests with
Testcontainers].

== Pushing images

[source,shell]
----
# Single platform: build, tag, push
docker build -t ghcr.io/myorg/orders-service:1.4.0 .
docker push ghcr.io/myorg/orders-service:1.4.0

# Multi-platform: build and push the image index in one step
docker buildx build --platform linux/amd64,linux/arm64 \
  -t ghcr.io/myorg/orders-service:1.4.0 -t ghcr.io/myorg/orders-service:1.4 --push .

# Copy an image (all platforms, attestations) between registries without pulling it locally
docker buildx imagetools create -t registry.example.com/mirror/orders-service:1.4.0 ghcr.io/myorg/orders-service:1.4.0
----

Derived from https://docs.docker.com/reference/cli/docker/image/push/[`docker image push`],
https://docs.docker.com/build/building/multi-platform/[Multi-platform builds] and
https://docs.docker.com/reference/cli/docker/buildx/imagetools/create/[`docker buildx imagetools create`].

== Other registries

[cols="1,2,2",options="header"]
|===
| Registry | Address | Authentication from CI

| GitHub Container Registry
| `ghcr.io/<owner>/<image>`
| `GITHUB_TOKEN` with `packages: write` in GitHub Actions

| Amazon ECR
| `<account>.dkr.ecr.<region>.amazonaws.com/<repo>`
| OIDC role via `aws-actions/configure-aws-credentials`, then `aws-actions/amazon-ecr-login`

| Google Artifact Registry
| `<region>-docker.pkg.dev/<project>/<repo>/<image>`
| Workload Identity Federation (OIDC) via `google-github-actions/auth`

| Azure Container Registry
| `<name>.azurecr.io/<image>`
| Federated credentials (OIDC) via `azure/login`
|===

All of them speak the OCI distribution API, so `docker push`/`pull` work unchanged once logged in; prefer keyless
OIDC over long-lived passwords. GitHub's own guide is
https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-container-registry[Working
with the Container registry]; the login action's README documents each provider
(https://github.com/docker/login-action[docker/login-action]).

== A private registry with CNCF Distribution

The registry Docker open-sourced became https://distribution.github.io/distribution/[CNCF Distribution] and ships as
the `registry` image. A minimal authenticated registry with TLS:

[source,shell]
----
mkdir -p auth certs
docker run --rm --entrypoint htpasswd httpd:2.4 -Bbn ci-user "$REGISTRY_PASSWORD" > auth/htpasswd
# certs/registry.crt and certs/registry.key issued for registry.example.com
docker run -d --name registry --restart always -p 443:5000 \
  -v "$(pwd)/auth":/auth -v "$(pwd)/certs":/certs -v registry-data:/var/lib/registry \
  -e REGISTRY_AUTH=htpasswd -e REGISTRY_AUTH_HTPASSWD_REALM=registry-realm \
  -e REGISTRY_AUTH_HTPASSWD_PATH=/auth/htpasswd \
  -e REGISTRY_HTTP_TLS_CERTIFICATE=/certs/registry.crt -e REGISTRY_HTTP_TLS_KEY=/certs/registry.key \
  registry:3
docker login registry.example.com
----

To run it as a *pull-through cache* for Docker Hub instead, set `REGISTRY_PROXY_REMOTEURL=https://registry-1.docker.io`
(plus credentials for authenticated upstream pulls) and point the daemon's `"registry-mirrors"` at it. Derived from
the https://distribution.github.io/distribution/about/deploying/[Distribution deployment guide] and
https://distribution.github.io/distribution/recipes/mirror/[Registry as a pull through cache].

== OCI artifacts and webhooks

Because the distribution API stores arbitrary manifests and blobs, registries also hold *OCI artifacts* that are not
container images: Helm charts, SBOMs and signatures, Compose applications (`docker compose publish`, see
xref:backend/docker/compose-in-practice.adoc[Compose in Practice]) and AI models. Docker Hub *webhooks* notify a URL
when an image is pushed to a repository, which can trigger a deployment. Derived from
https://docs.docker.com/docker-hub/repos/manage/hub-images/oci-artifacts/[OCI artifacts on Docker Hub] and
https://docs.docker.com/docker-hub/repos/manage/webhooks/[Webhooks].

== Superseded: automated builds and the Python registry

* *Docker Hub automated builds* (build on every Git push, _Learning Docker_ chapter 4) are a legacy feature,
  deprecated and scheduled for removal on 1 April 2027. Build in CI instead -- see
  xref:backend/docker/ci-cd-with-github-actions.adoc[Docker CI/CD with GitHub Actions] and Docker's
  https://docs.docker.com/docker-hub/repos/manage/builds/migrate/[migration guide].
* The *Python `docker-registry`* of _Learning Docker_ chapter 5 implemented the long-retired v1 protocol. Its
  replacement is CNCF Distribution and the OCI distribution API, as above.
