MongoDB stores JSON-like documents (see xref:database/mongodb/documents-and-bson.adoc[Documents and BSON]) and Nest offers two ways to use it: the MongoDB connector of TypeORM (see xref:backend/nestjs/data-overview-and-typeorm.adoc[Data Overview & TypeORM]) or Mongoose, the most popular object modelling library for MongoDB, wrapped by the first-party `@nestjs/mongoose` package. This page covers the second. In the _Bookshelf_ application that grows across this section, MongoDB holds the activity feed: an append-only stream of "book viewed" and "review posted" events, a per-book counter, and an audit log in a second database. Relational data (books, authors, users) stays in PostgreSQL; the MongoDB design questions (embed or reference, indexes, shard keys) are covered in xref:database/mongodb/data-modeling.adoc[Data Modeling] and xref:database/mongodb/indexes.adoc[Indexes].

== What @nestjs/mongoose adds to Mongoose

Mongoose itself is plain JavaScript with TypeScript typings. `@nestjs/mongoose` adds four things on top:

* `MongooseModule`, a dynamic module (see xref:backend/nestjs/dynamic-modules.adoc[Dynamic Modules]) with `forRoot()`/`forRootAsync()` to open connections and `forFeature()`/`forFeatureAsync()` to register models per feature module.
* Decorators (`@Schema()`, `@Prop()`, `@Virtual()`) and `SchemaFactory` that build a Mongoose `Schema` from a TypeScript class, using the metadata that `emitDecoratorMetadata` emits (see xref:backend/nestjs/typescript-for-nestjs.adoc[TypeScript for NestJS]).
* Injection tokens for models and connections: `@InjectModel()`, `@InjectConnection()` and the helper functions `getModelToken()` and `getConnectionToken()`.
* Lifecycle integration: connections are opened when the module is initialised and closed when the application shuts down.

Install both packages:

[source,bash]
----
npm i @nestjs/mongoose mongoose
----

Source: https://docs.nestjs.com/data/mongodb

Mongoose 9 needs Node.js 20.19 or later, which matches the Node.js floor of Nest 12. The examples use `.js` import extensions, as the current ESM template does. Nothing else about the module is specific to the HTTP adapter: the Express and Fastify platforms behave identically because MongoDB access never touches the request object.

== Connecting: forRoot() and forRootAsync()

`MongooseModule.forRoot()` takes a connection string and the same options object as `mongoose.connect()`. A connection string is configuration, so it belongs in the environment rather than in source; prefer `forRootAsync()` with `ConfigService` (see xref:backend/nestjs/configuration.adoc[Configuration]):

.mongodb.module.ts (default connection)
[source,typescript]
----
import { Module } from '@nestjs/common';
import { ConfigModule, ConfigService } from '@nestjs/config';
import { MongooseModule } from '@nestjs/mongoose';
import { hideVersionKey } from './plugins.js';

@Module({
  imports: [
    ConfigModule.forRoot({ isGlobal: true }),
    MongooseModule.forRootAsync({
      imports: [ConfigModule],
      inject: [ConfigService],
      useFactory: (config: ConfigService) => ({
        // Throws at startup if the variable is missing.
        uri: config.getOrThrow<string>('MONGODB_URI'),
        connectionFactory: (connection) => {
          connection.plugin(hideVersionKey); // see "Plugins" below
          return connection;
        },
      }),
    }),
  ],
})
export class MongodbModule {}
----

Source: https://docs.nestjs.com/data/mongodb#async-configuration

`useFactory` may be `async` and may `inject` providers. Two other styles exist for the same options object, and both work:

* `useClass` instantiates a class inside `MongooseModule`; the class implements `MongooseOptionsFactory` and returns the options from `createMongooseOptions()`.
* `useExisting` reuses a provider that already implements `MongooseOptionsFactory` instead of creating a private copy.

.mongoose-config.service.ts
[source,typescript]
----
import { Injectable } from '@nestjs/common';
import { ConfigService } from '@nestjs/config';
import { MongooseModuleOptions, MongooseOptionsFactory } from '@nestjs/mongoose';

@Injectable()
export class MongooseConfigService implements MongooseOptionsFactory {
  constructor(private readonly config: ConfigService) {}

  createMongooseOptions(): MongooseModuleOptions {
    return { uri: this.config.getOrThrow<string>('MONGODB_URI'), autoIndex: false };
  }
}

// In a module:
// MongooseModule.forRootAsync({ useClass: MongooseConfigService })
----

Source: https://docs.nestjs.com/data/mongodb#async-configuration

Setting `autoIndex: false` is the production-minded choice: with the default (`true`) Mongoose calls `createIndexes()` for every model when the application starts, which on a large collection is a heavyweight operation you may not want to run on every deploy. Create indexes through a migration step instead (see xref:database/mongodb/indexes.adoc[Indexes]).

Note that `forRoot()` waits for the first connection attempt: if MongoDB is unreachable the application fails to start after the driver's server-selection timeout (30 seconds by default). In containers where the database starts later, that surfaces as a slow crash loop; set `serverSelectionTimeoutMS` in the options to fail faster.

== Defining schemas with decorators

A Mongoose schema describes the shape of the documents in one collection; a model compiled from it creates and queries documents. `@nestjs/mongoose` lets a class carry the schema definition:

.activity.schema.ts (excerpt)
[source,typescript]
----
import { Prop, Schema, SchemaFactory } from '@nestjs/mongoose';
import { HydratedDocument } from 'mongoose';

@Schema({ timestamps: true })
export class BookCounter {
  @Prop({ required: true, unique: true })
  bookId: string;

  @Prop({ default: 0 })
  reviews: number;
}

export type BookCounterDocument = HydratedDocument<BookCounter>;
export const BookCounterSchema = SchemaFactory.createForClass(BookCounter);
----

Source: https://docs.nestjs.com/data/mongodb#model-injection

* `@Schema(options)` marks the class. Its optional argument is the second argument of `new mongoose.Schema(definition, options)`; for example `timestamps`, `collection`, `discriminatorKey` or `toJSON`. Mongoose names the collection after the model, lower-cased and pluralised (`BookCounter` becomes `bookcounters`); set `collection` to choose a name explicitly.
* `@Prop(options)` declares a property. Simple types (`string`, `number`, `boolean`, `Date`) are inferred from the TypeScript metadata. Arrays, unions, `Map`s and nested objects cannot be reflected, so they need an explicit type: `@Prop([String])` or `@Prop({ type: [String], default: [] })`. The options object accepts the usual schema-type options such as `required`, `default`, `immutable`, `enum`, `min`, `max`, `index` and `unique`.
* `SchemaFactory.createForClass(Class)` turns the metadata into a `Schema` instance. Do this once, in the schema file, and export the result next to the class.
* A schema can also be written without decorators, as `new mongoose.Schema({ ... })`; both styles register the same way. `DefinitionsFactory.createForClass()` returns the raw definition object when you need to modify the generated definition before building the schema.

=== HydratedDocument, not extends Document

Older tutorials declare `export type CatDocument = Cat & Document` or write `class Cat extends Document`. Both are outdated: extending Mongoose's `Document` pulls its runtime class into your schema class (its properties, `_id` typing and methods leak into `@Prop()` metadata) and the intersection type does not model hydrated documents accurately. The current pattern, shown in the Nest documentation, keeps the schema class a plain class and derives the document type from it:

[source,typescript]
----
import { HydratedDocument } from 'mongoose';

export type BookCounterDocument = HydratedDocument<BookCounter>;
----

Source: https://docs.nestjs.com/data/mongodb#model-injection

`Model<BookCounter>` is the type of an injected model; documents returned by `create()` or `find()` are `HydratedDocument<BookCounter>` (a `BookCounter` plus Mongoose's document methods such as `save()`, `toJSON()` and `populate()`). Queries with `.lean()` return plain `BookCounter` objects without those methods and are cheaper to produce.

=== References, populate and raw()

References between collections are `ObjectId` properties with a `ref` to the target _model name_. Type the property as `Types.ObjectId` and populate on demand with an explicit type for the populated shape, so the field is never mistaken for a loaded document:

.extras.ts (excerpt)
[source,typescript]
----
import { Injectable } from '@nestjs/common';
import { InjectModel, Prop, raw, Schema } from '@nestjs/mongoose';
import mongoose, { Model, Types } from 'mongoose';

@Schema()
export class Reader {
  // A nested object that is not a class: pass a raw definition.
  @Prop(raw({ firstName: { type: String }, lastName: { type: String } }))
  details: Record<string, any>;
}

@Schema()
export class Shelf {
  @Prop({ required: true })
  label: string;

  @Prop({ type: mongoose.Schema.Types.ObjectId, ref: Reader.name })
  owner: Types.ObjectId;
}

@Injectable()
export class ShelfRepository {
  constructor(@InjectModel(Shelf.name) private readonly shelves: Model<Shelf>) {}

  findAllPopulated() {
    return this.shelves.find().populate<{ owner: Reader }>('owner').exec();
  }
}
----

Source: https://docs.nestjs.com/data/mongodb#model-injection

The populate call returns `owner` as the full `Reader` document (for a reader saved with `details: { firstName: 'Ada', lastName: 'L' }`, `owner.details.firstName` is `'Ada'`). Populating is a second query issued by Mongoose, not a join; for relationships that are always read together, embedding (see <<_subdocuments,Subdocuments>>) is usually better.

== Registering and injecting models

Models are registered per feature module with `forFeature()`, using the schema class name as the model name (`Class.name`), and injected with `@InjectModel()`:

.activity.module.ts (excerpt) and service
[source,typescript]
----
import { Module } from '@nestjs/common';
import { MongooseModule } from '@nestjs/mongoose';

@Module({
  imports: [
    MongooseModule.forFeature([{ name: BookCounter.name, schema: BookCounterSchema }]),
  ],
  providers: [ActivityService],
  // Export MongooseModule to let importing modules inject these models too.
  exports: [MongooseModule],
})
export class ActivityModule {}

// activity.service.ts
@Injectable()
export class ActivityService {
  constructor(@InjectModel(BookCounter.name) private readonly counters: Model<BookCounter>) {}

  counterFor(bookId: string) {
    return this.counters.findOne({ bookId }).lean().exec();
  }
}
----

Source: https://docs.nestjs.com/data/mongodb#model-injection

Three details are worth knowing. The token behind `@InjectModel(name)` is a string derived from the model name (`getModelToken(name)`), so the name given to `forFeature()` and to `@InjectModel()` must match exactly. `.exec()` returns a real `Promise` with a useful stack trace; the bare query object is only "thenable". And model registration is per connection: if the module should use a named connection, `forFeature()` and `@InjectModel()` both need its name (next sections).

Documents get an `_id` of type `ObjectId`; when a controller returns a Mongoose document, Nest serialises it with `JSON.stringify`, which calls the document's `toJSON()`. Control the output with the `toJSON` schema option or, for DTO-style filtering, with `class-transformer` (see xref:backend/nestjs/serialization.adoc[Serialization]); note that a hydrated document is not an instance of your schema class, so `ClassSerializerInterceptor` and `@Exclude()` do not apply to it directly unless you convert it to a plain object first.

== Injecting the connection

For native driver access, `.collection()`, or sessions, inject the Mongoose `Connection`:

[source,typescript]
----
import { Injectable } from '@nestjs/common';
import { InjectConnection } from '@nestjs/mongoose';
import { Connection } from 'mongoose';

@Injectable()
export class ActivityService {
  constructor(@InjectConnection() private readonly connection: Connection) {}
}
----

Source: https://docs.nestjs.com/data/mongodb#connection

The bound `connection.name` is the database name from the URI (`bookshelf` for the URI used on this page), which is also what `connection.db.databaseName` reports once connected.

== Sessions and transactions

A single-document write in MongoDB is already atomic. When an invariant spans several documents, for example "the feed entry and the per-book counter change together", use a transaction (see xref:database/mongodb/transactions.adoc[Multi-document ACID transactions] for the database-side semantics). With Mongoose you start a session from the connection that Nest manages, which is why the docs recommend `@InjectConnection()` over calling `mongoose.startSession()` directly:

.activity.service.ts (transaction)
[source,typescript]
----
async recordReview(input: ReviewInput) {
  const session = await this.connection.startSession();
  try {
    return await session.withTransaction(async () => {
      const [review] = await this.reviews.create(
        [{
          bookId: input.bookId,
          rating: input.rating,
          tags: input.tags ?? [],
          actor: { userId: input.userId, displayName: input.displayName },
        }],
        { session }, // every operation must be given the session explicitly
      );
      await this.counters.updateOne(
        { bookId: input.bookId },
        { $inc: { reviews: 1 } },
        { upsert: true, session },
      );
      return review;
    });
  } finally {
    await session.endSession();
  }
}

// The helper form: commits, aborts on error and retries transient errors.
recordReviewWithHelper(input: ReviewInput) {
  return this.connection.transaction(async (session) => {
    const [review] = await this.reviews.create(
      [{ bookId: input.bookId, rating: input.rating, actor: { userId: input.userId, displayName: input.displayName } }],
      { session },
    );
    await this.counters.updateOne({ bookId: input.bookId }, { $inc: { reviews: 1 } }, { upsert: true, session });
    return review;
  });
}
----

Source: https://docs.nestjs.com/data/mongodb#sessions

Throwing an error after both writes inside the callback and then reading the data back gives:

.Output
[source,text]
----
counter 2 feed 2
----

Two transactions committed (one with each form) and the third, which threw after writing, left neither a feed entry nor a counter increment. The pitfalls are all about the session:

* **Pass the session to every operation.** Nothing is implicit: an operation without `{ session }` runs outside the transaction and is not rolled back. `Model.create()` takes an array when you pass options, which is why the example destructures `[review]`.
* **Use `withTransaction()` or `connection.transaction()` rather than manual `startTransaction()`/`commitTransaction()`** unless you need the control: the helpers retry on transient transaction errors and on unknown commit results, so the callback must be safe to run more than once (no external side effects such as sending e-mail inside it).
* **Always end the session** (`finally`), also after an abort, or the server keeps it until it times out.
* **Do not use `Promise.all` inside a transaction.** Operations in one transaction on one session are not meant to run concurrently; run them sequentially.
* **Keep transactions short.** The default `transactionLifetimeLimit` is 60 seconds and long transactions hold locks and cache pressure.

=== Transactions need a replica set

Multi-document transactions work only on a replica set or a sharded cluster, not on a standalone `mongod`. On a standalone server the same code fails, for instance with this message from the test (the exact text can vary between drivers and server versions):

.Output
[source,text]
----
This MongoDB deployment does not support retryable writes. Please add retryWrites=false to your connection string.
----

(Following that advice would only hide the real problem: the deployment must be a replica set. See xref:database/mongodb/replication.adoc[Replication].) Practical consequences:

* Local development: run MongoDB as a single-node replica set (for example `mongod --replSet rs0` plus `rs.initiate()`, or a Docker image that does it for you).
* Atlas and any managed cluster are replica sets already.
* In tests, `mongodb-memory-server` can start a replica set: use `MongoMemoryReplSet` instead of `MongoMemoryServer`. The test file in this page does exactly this (see <<_testing_with_getmodeltoken,Testing>>), and it is also how you can run transaction code against Testcontainers (see xref:backend/docker/testcontainers-fundamentals.adoc[Testcontainers Fundamentals]).

Calling into the transaction from a request handler is not special: the session is a local variable of the service method, so there is nothing request-scoped to manage. Do not store a session in a singleton provider's field, since concurrent requests would share it.

== Multiple connections

A second database, or a second cluster, needs a second named connection. Naming is mandatory: unnamed or equally named connections override each other.

.mongodb.module.ts (second connection)
[source,typescript]
----
MongooseModule.forRootAsync({
  connectionName: 'audit',
  imports: [ConfigModule],
  inject: [ConfigService],
  useFactory: (config: ConfigService) => ({
    uri: config.getOrThrow<string>('MONGODB_AUDIT_URI'),
  }),
}),
----

Source: https://docs.nestjs.com/data/mongodb#multiple-databases

Then pass the connection name everywhere a connection or model is chosen:

[source,typescript]
----
// Register the model on the named connection (second argument of forFeature).
MongooseModule.forFeature([{ name: AuditEntry.name, schema: AuditEntrySchema }], 'audit'),

// Inject the model (second argument of @InjectModel) and the connection.
constructor(
  @InjectModel(AuditEntry.name, 'audit') private readonly audit: Model<AuditEntry>,
  @InjectConnection('audit') private readonly auditConnection: Connection,
) {}
----

Source: https://docs.nestjs.com/data/mongodb#multiple-databases

The default connection reports the database `bookshelf` and the `audit` connection `bookshelf_audit`, and writes made through the audit model land in the second database only:

.Output
[source,text]
----
dbs ["bookshelf","bookshelf_audit"]
----

For a custom provider, use `getConnectionToken(name)` (and `getModelToken(name, connectionName)` for models). A factory provider that receives a connection looks like this (shown with the default connection; pass the name for a named one):

.extras.ts (excerpt)
[source,typescript]
----
import { getConnectionToken } from '@nestjs/mongoose';
import { Connection } from 'mongoose';

export const connectionAwareProvider = {
  provide: ConnectionAware,
  useFactory: (connection: Connection) => new ConnectionAware(connection),
  inject: [getConnectionToken()], // getConnectionToken('audit') for a named one
};
----

Source: https://docs.nestjs.com/data/mongodb#multiple-databases

A transaction cannot span two connections created this way, since each has its own client and its own sessions. If two databases must change atomically they have to live in the same cluster and be accessed through one connection (use `connection.useDb()` or fully qualified collection names), otherwise accept eventual consistency (see xref:backend/nestjs/events-scheduling-and-queues.adoc[Events, Scheduling & Queues] for outbox-style approaches).

== Hooks (middleware)

Mongoose _middleware_ (called hooks in this page to avoid confusion with HTTP middleware) are functions that run before or after operations such as `save`, `updateOne`, `find` or `deleteOne`. They are defined on the schema, and a hook defined after the model has been compiled has no effect. That is why `@nestjs/mongoose` offers `forFeatureAsync()`: its factory receives the schema before the model is compiled and can inject providers such as `ConfigService`:

.activity.module.ts (hook)
[source,typescript]
----
MongooseModule.forFeatureAsync([
  {
    name: Activity.name,
    imports: [ConfigModule],
    inject: [ConfigService],
    useFactory: (config: ConfigService) => {
      // clone(): the module-level schema object stays untouched.
      const schema = ActivitySchema.clone();
      const maxTags = config.get<number>('ACTIVITY_MAX_TAGS', 5);
      schema.pre('save', function () {
        this.tags = [...new Set(this.tags.map((t) => t.toLowerCase()))].slice(0, maxTags);
      });
      return schema;
    },
  },
]),
----

Source: https://docs.nestjs.com/data/mongodb#hooks-middleware

Saving a review with the tags `['Great', 'GREAT', 'Scifi']` stored `["great","scifi"]`. Notes:

* Use `function`, not an arrow function, when you need `this`: for document hooks (`save`, `validate`) `this` is the document; for query hooks (`find`, `updateOne`) it is the query.
* Write hooks as plain or `async` functions, as above; Mongoose 9 does not pass a `next` callback at all: a `pre('save')` hook that calls `next()` fails with `next is not a function`, so older examples need adjusting.
* Mutating the shared `ActivitySchema` constant instead of cloning it is the usual bug: each call of the factory (every test module, every application restart in watch mode inside one process) would register the hook again on the same object. Clone, or build the schema inside the factory.
* `save` hooks do not run for `updateOne()`, `findOneAndUpdate()` or `insertMany()`; those have their own hook points (`pre('updateOne')`, `pre('insertMany')`), and `bulkWrite()` bypasses most of them.

== Plugins

A plugin is a function that receives a schema and extends it (fields, methods, hooks, options). Register one for a single schema in the same `forFeatureAsync()` factory with `schema.plugin(fn)` (the Nest docs show `mongoose-autopopulate` this way), or for every schema of a connection from `connectionFactory`, which runs before any model is compiled:

.plugins.ts and the connectionFactory (see the connection module above)
[source,typescript]
----
import { Schema } from 'mongoose';

// A global plugin: hides the Mongoose version key from JSON output.
export function hideVersionKey(schema: Schema): void {
  schema.set('toJSON', { versionKey: false });
}

// MongooseModule.forRootAsync({
//   useFactory: (config: ConfigService) => ({
//     uri: config.getOrThrow<string>('MONGODB_URI'),
//     connectionFactory: (connection) => {
//       connection.plugin(hideVersionKey);
//       return connection;
//     },
//   }),
// })
----

Source: https://docs.nestjs.com/data/mongodb#plugins

With the plugin installed, the JSON of a created review has no `__v` field, although the stored document still has one. Plugins registered on the connection apply to the models registered on that connection only, so a named connection needs its own `connectionFactory`.

== Discriminators

Discriminators are schema inheritance for MongoDB: several models with overlapping schemas share one collection, and Mongoose stores a key in every document to say which model it belongs to. They fit the activity feed, where events differ in a few fields but are read as one time-ordered stream (the "single collection with a type field" pattern from xref:database/mongodb/data-modeling.adoc[Data Modeling]).

.activity.schema.ts
[source,typescript]
----
import { Prop, Schema, SchemaFactory } from '@nestjs/mongoose';
import { Actor, ActorSchema } from './actor.schema.js';

export const BOOK_VIEWED = 'BookViewed';
export const REVIEW_POSTED = 'ReviewPosted';

// `discriminatorKey` names the path that identifies the model (default: __t).
@Schema({ discriminatorKey: 'kind', timestamps: true })
export class Activity {
  @Prop({ type: String, required: true, enum: [BOOK_VIEWED, REVIEW_POSTED] })
  kind: string;

  @Prop({ required: true, index: true })
  bookId: string;

  @Prop({ type: ActorSchema, required: true })
  actor: Actor;

  @Prop({ type: [String], default: [] })
  tags: string[];
}
export const ActivitySchema = SchemaFactory.createForClass(Activity);

@Schema()
export class BookViewed {
  // Inherited paths are declared WITHOUT @Prop(): the base schema already has them.
  kind: string;
  bookId: string;
  actor: Actor;
  tags: string[];

  @Prop({ required: true })
  referrer: string;
}
export const BookViewedSchema = SchemaFactory.createForClass(BookViewed);

@Schema()
export class ReviewPosted {
  kind: string;
  bookId: string;
  actor: Actor;
  tags: string[];

  @Prop({ required: true, min: 1, max: 5 })
  rating: number;
}
export const ReviewPostedSchema = SchemaFactory.createForClass(ReviewPosted);
----

Register them with the `discriminators` option of `forFeature()` (or `forFeatureAsync()`, as in the hook example above, where the option sits next to `useFactory`):

.activity.module.ts (discriminators)
[source,typescript]
----
MongooseModule.forFeature([
  {
    name: Activity.name,
    schema: ActivitySchema,
    discriminators: [
      { name: BOOK_VIEWED, schema: BookViewedSchema, value: BOOK_VIEWED },
      { name: REVIEW_POSTED, schema: ReviewPostedSchema, value: REVIEW_POSTED },
    ],
  },
]),
----

Source: https://docs.nestjs.com/data/mongodb#discriminators

Each discriminator is a model of its own, injected with `@InjectModel(BOOK_VIEWED)`, while the base model reads all kinds. One view and one review go to a single `activities` collection:

.Output (the review document as stored)
[source,json]
----
{
  "_id": "6abf...",
  "kind": "ReviewPosted",
  "bookId": "b1",
  "actor": { "userId": "u1", "displayName": "Ada" },
  "tags": ["great", "scifi"],
  "rating": 5,
  "createdAt": "2026-10-02T15:58:25.608Z",
  "updatedAt": "2026-10-02T15:58:25.608Z",
  "__v": 0
}
----

The pitfall that the examples above work around: if `BookViewed` simply `extends Activity`, `SchemaFactory` also collects the inherited `@Prop()` metadata, the discriminator schema then declares `kind` itself, and Mongoose refuses to register it with `Discriminator "BookViewed" cannot have field with name "kind"`. Declare the inherited fields as plain TypeScript properties without `@Prop()` (this is what the Nest docs do) and the types stay accurate. Mongoose also requires the discriminator key not to be redefined, the same collection and connection for the base and its discriminators, and a unique `value` per discriminator (it defaults to the model name).

== Subdocuments

Embedded documents have their own schema but live inside the parent document, with no collection of their own. Give a subdocument class `@Schema({ _id: false })` when it does not need an identifier, create its schema, and reference that schema in the parent:

.actor.schema.ts and its use in Activity
[source,typescript]
----
@Schema({ _id: false })
export class Actor {
  @Prop({ required: true })
  userId: string;

  @Prop({ required: true })
  displayName: string;
}
export const ActorSchema = SchemaFactory.createForClass(Actor);

// In the parent schema class:
@Prop({ type: ActorSchema, required: true })
actor: Actor;

// The hydrated document type is overridden so that TypeScript knows `actor` is a subdocument:
export type ActivityDocument = HydratedDocument<
  Activity,
  { actor: Types.Subdocument<Types.ObjectId> & Actor }
>;
----

Source: https://docs.nestjs.com/data/mongodb#subdocuments

For many subdocuments use an array of the schema, and override the property with `Types.DocumentArray`:

.author.schema.ts
[source,typescript]
----
@Schema({ _id: false })
export class Name {
  @Prop({ required: true })
  firstName: string;

  @Prop({ required: true })
  lastName: string;
}
export const NameSchema = SchemaFactory.createForClass(Name);

@Schema()
export class Author {
  @Prop([NameSchema])
  names: Name[];
}

export type AuthorDocument = HydratedDocument<Author, { names: Types.DocumentArray<Name> }>;
export const AuthorSchema = SchemaFactory.createForClass(Author);
----

Source: https://docs.nestjs.com/data/mongodb#subdocuments

The nested schema's validators apply to the subdocument, and its fields can be queried with dot notation, for example `find({ 'actor.userId': 'u1' })`. The MongoDB maximum document size (16 MiB) and unbounded arrays are the practical limits of embedding; see xref:database/mongodb/data-modeling.adoc[Data Modeling].

== Virtuals

A virtual is a property computed on access and never stored. `@Virtual()` from `@nestjs/mongoose` declares one on the schema class:

.author.schema.ts and activity.schema.ts (virtuals)
[source,typescript]
----
import { Virtual } from '@nestjs/mongoose';

// in Author
@Virtual({
  get: function (this: Author) {
    const [first] = this.names ?? [];
    return first ? `${first.firstName} ${first.lastName}` : '';
  },
})
fullName: string;

// in Activity
@Virtual({
  get: function (this: Activity) {
    return `${this.actor?.displayName ?? 'someone'} -> ${this.kind} on ${this.bookId}`;
  },
})
summary: string;
----

Source: https://docs.nestjs.com/data/mongodb#virtuals

For an author created with `names: [{ firstName: 'Ursula', lastName: 'Le Guin' }]`, `fullName` is `Ursula Le Guin` while the stored and serialised document contains only `names`. Remember that:

* Virtuals are not in the database, so they cannot be used in queries, indexes or `.lean()` results (lean returns the stored data only).
* Virtuals are left out of `toJSON()` and `toObject()` unless the schema option `toJSON: { virtuals: true }` is set; the example controller therefore adds `summary` by hand. Setting it globally with a plugin is convenient but exposes every virtual.
* Use `function`, not an arrow function, in `get`/`set`, so that `this` is the document.

== Connection events

`onConnectionCreate` receives each connection as soon as it exists and before it opens, so listeners cannot miss the first events (`connected`, `open`, `disconnected`, `reconnected`, `disconnecting`). It works in `forRoot()` and in the object returned by the `forRootAsync()` factory:

.connection-events.ts
[source,typescript]
----
import { Logger } from '@nestjs/common';
import { Connection } from 'mongoose';

export const CONNECTION_EVENTS = ['connected', 'open', 'disconnected', 'reconnected', 'disconnecting'] as const;

export function logConnectionEvents(name: string) {
  const logger = new Logger(`mongoose:${name}`);
  return (connection: Connection): Connection => {
    for (const event of CONNECTION_EVENTS) {
      connection.on(event, () => logger.log(event));
    }
    return connection;
  };
}

// MongooseModule.forRootAsync({
//   useFactory: (config: ConfigService) => ({
//     uri: config.getOrThrow<string>('MONGODB_URI'),
//     onConnectionCreate: logConnectionEvents('default'),
//   }),
//   inject: [ConfigService],
// })
----

Source: https://docs.nestjs.com/data/mongodb#connection-events

Use these events for logging and metrics; for a liveness check on the database use a health indicator (see the health-checks page of this section) rather than reading the events.

== Testing with getModelToken

Unit tests of a service should not need a database. Because models are ordinary providers with a deterministic token, replace them with `getModelToken()`, and connections with `getConnectionToken()`:

.activity.service.spec.ts
[source,typescript]
----
import { Test } from '@nestjs/testing';
import { getConnectionToken, getModelToken } from '@nestjs/mongoose';

it('uses mock models', async () => {
  const find = vi.fn().mockReturnValue({ sort: () => ({ exec: async () => [{ kind: 'BookViewed' }] }) });
  const moduleRef = await Test.createTestingModule({
    providers: [
      ActivityService,
      { provide: getModelToken(Activity.name), useValue: { find } },
      { provide: getModelToken('BookViewed'), useValue: {} },
      { provide: getModelToken('ReviewPosted'), useValue: {} },
      { provide: getModelToken('BookCounter'), useValue: {} },
      { provide: getModelToken('AuditEntry', 'audit'), useValue: {} },
      { provide: getConnectionToken(), useValue: { name: 'fake' } },
      { provide: getConnectionToken('audit'), useValue: { name: 'fake-audit' } },
    ],
  }).compile();

  const service = moduleRef.get(ActivityService);
  expect(await service.findForBook('b1')).toEqual([{ kind: 'BookViewed' }]);
  expect(find).toHaveBeenCalledWith({ bookId: 'b1' });
});
----

Source: https://docs.nestjs.com/data/mongodb#testing

(`vi.fn()` is Vitest; use `jest.fn()` in the CommonJS/Jest template.) A mock proves the service calls the model as intended; it does not prove the query, the hooks, the discriminators or the transactions work. For those, run against a real MongoDB: `mongodb-memory-server` downloads and starts a real `mongod` for the test run, and `MongoMemoryReplSet` provides the replica set that transactions require:

.activity.e2e-spec.ts (excerpt)
[source,typescript]
----
import { MongoMemoryReplSet } from 'mongodb-memory-server';

let replSet: MongoMemoryReplSet;
let app: INestApplication;

beforeAll(async () => {
  replSet = await MongoMemoryReplSet.create({ replSet: { count: 1 } });
  // The application reads these through ConfigService.
  process.env.MONGODB_URI = replSet.getUri('bookshelf');
  process.env.MONGODB_AUDIT_URI = replSet.getUri('bookshelf_audit');
  const moduleRef = await Test.createTestingModule({
    imports: [MongodbModule, ActivityModule],
  }).compile();
  app = moduleRef.createNestApplication();
  await app.init();
});

afterAll(async () => {
  await app.close();      // closes the Mongoose connections
  await replSet.stop();
});
----

== Where older material is outdated, and what changed recently

* **Nest 10 and `extends Document` tutorials.** Material written for Nest 10 (including the book this section consulted, which targets Nest 10) types documents as `Cat & Document`. Use `HydratedDocument<Cat>`. The book's GraphQL case study also reuses Mongoose classes as GraphQL types without `@ObjectType()`: that does not work, because GraphQL needs its own decorated type; keep schema classes and GraphQL types separate (or deliberately decorate one class for both, accepting the coupling).
* **Connection options.** Options such as `useNewUrlParser` and `useUnifiedTopology`, still common in older tutorials, belong to old driver versions; do not copy them. Use a plain URI plus the options you actually need.
* **Hooks.** Mongoose 9 hooks are plain or async functions without `next`; tutorials written for Mongoose 5 to 8 call `next()`.
* **Mongoose queries are thenables, not Promises.** `await model.find()` works, but `.exec()` gives better stack traces and a real `Promise` for `Promise.all`.

== Express and Fastify

Nothing in `@nestjs/mongoose` depends on the HTTP platform. The one place the platform shows is around it: ObjectId strings arrive as route parameters on both adapters, so validate them with a pipe before they reach a query (see xref:backend/nestjs/pipes-and-validation.adoc[Pipes & Validation]); an invalid id otherwise surfaces as a Mongoose `CastError` and a 500 response.
