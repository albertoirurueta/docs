[#what-it-is]
== What middleware is, and where it runs

By default a Nest middleware is an Express middleware: a function `(req, res, next)` that can run code, change the
request and response objects, end the request-response cycle, or call `next()` to pass control on. A middleware that
neither responds nor calls `next()` leaves the request hanging.

[mermaid]
....
flowchart LR
  A["Incoming request"] --> B["Global middleware<br/>app.use()"]
  B --> C["Module middleware<br/>consumer.apply()"]
  C --> D["Guards, interceptors,<br/>pipes, handler"]
  C -. "next(err) or throw" .-> E["Exceptions layer<br/>global filters only"]
  D --> F["Response"]
  E --> F
....

Because middleware runs before the router has chosen a handler, it knows nothing about the controller, the method or the
`ExecutionContext`. That is the key difference from guards and interceptors, and the reason to prefer those when the
decision depends on _which handler_ is about to run. Typical middleware jobs are the ones that are indifferent to the
handler: request identifiers, logging, CORS, `helmet`, cookie and body parsing, compression.

Source: https://docs.nestjs.com/middleware[NestJS: Middleware]

[#class-middleware]
== Class middleware

A class middleware is an `@Injectable()` class implementing the `NestMiddleware` interface (from `@nestjs/common`),
with a `use(req, res, next)` method. Because it is a normal provider-style class, it takes part in dependency
injection: its constructor can receive any provider that is available in the module that binds it.

.logger.middleware.ts
[source,typescript]
----
import { Injectable, NestMiddleware } from '@nestjs/common';
import type { NextFunction, Request, Response } from 'express';
import { TraceService } from './trace.service.js';

@Injectable()
export class LoggerMiddleware implements NestMiddleware {
  // Class middleware takes part in dependency injection like any provider.
  constructor(private readonly trace: TraceService) {}

  use(req: Request, res: Response, next: NextFunction): void {
    this.trace.record(`logger ${req.method} ${req.originalUrl}`);
    next();
  }
}
----
Source: https://docs.nestjs.com/middleware#dependency-injection[NestJS: Middleware - Dependency injection]

The `Request`, `Response` and `NextFunction` types come from `express` (a transitive dependency of
`@nestjs/platform-express`; add `@types/express` if you do not have it). `req.originalUrl` is used because it keeps the full
requested path, whereas `req.url` can be relative to the mount point of the middleware.

[#applying]
== Applying middleware: `NestModule.configure()`

Middleware is not listed in the `@Module()` decorator. A module that uses middleware implements the `NestModule`
interface and its `configure(consumer: MiddlewareConsumer)` method. The method may be `async`; Nest awaits it, which is
handy when the setup depends on an asynchronous lookup.

[cols="2,3",options="header"]
|===
| `MiddlewareConsumer` method | Purpose

| `apply(...middleware)`
| Takes one or several class or functional middleware (executed in the order given) and returns a configuration object. Further `apply()` calls on the consumer start another binding.

| `exclude(...routes)`
| Routes the middleware must _not_ run for: strings or `RouteInfo` objects (`{ path, method }`), wildcards allowed.

| `forRoutes(...routes)`
| Where it runs: a string path, several strings, a `RouteInfo` object, a controller class or several controller classes. This call finishes the binding, so `exclude()` must come before it.
|===

.app.module.ts: binding by controller, with exclusions
[source,typescript]
----
import {
  MiddlewareConsumer,
  Module,
  NestModule,
  RequestMethod,
} from '@nestjs/common';
import { LoggerMiddleware } from './logger.middleware.js';
import { requestId } from './functional.middleware.js';
import {
  BooksController,
  FilesController,
  HealthController,
} from './books.controller.js';
import { TraceService } from './trace.service.js';

@Module({
  controllers: [BooksController, FilesController, HealthController],
  providers: [TraceService],
})
export class AppModule implements NestModule {
  configure(consumer: MiddlewareConsumer) {
    consumer
      .apply(LoggerMiddleware)
      .exclude(
        { path: 'books', method: RequestMethod.POST },
        'books/{*splat}',
      )
      .forRoutes(BooksController);

    consumer
      .apply(LoggerMiddleware)
      .forRoutes({ path: 'files/abcd/{*splat}', method: RequestMethod.GET });

    consumer.apply(requestId).forRoutes('*splat');
  }
}
----

Requesting `GET /books`, `GET /books/7`, `POST /books`, `GET /health`, `GET /files/abcd/xyz` and `GET /files/abcd` in
that order produced this trace from `LoggerMiddleware`: only `GET /books` (the controller's routes minus the excluded
ones) and `GET /files/abcd/xyz` (the wildcard binding) were logged.

.Observed trace
[source,json]
----
["logger GET /books", "logger GET /files/abcd/xyz"]
----

`forRoutes(BooksController)` binds the middleware to every route the controller declares, including its global prefix
and any version segment. Binding to a controller class is the form to prefer, because it survives route renames.

Source: https://docs.nestjs.com/middleware#applying-middleware[NestJS: Middleware - Applying middleware], https://docs.nestjs.com/middleware#middleware-consumer[Middleware consumer] and https://docs.nestjs.com/middleware#excluding-routes[Excluding routes]

[#request-method]
== Restricting by HTTP method: `RouteInfo` and `RequestMethod`

To limit a binding to one verb, pass a `RouteInfo` object to `forRoutes()` or `exclude()`: `{ path, method }`, where
`method` is a member of the `RequestMethod` enum (`GET`, `POST`, `PUT`, `DELETE`, `PATCH`, `ALL`, `OPTIONS`, `HEAD`,
and so on). A bare string path is the same as `RequestMethod.ALL`.

[source,typescript]
----
consumer
  .apply(LoggerMiddleware)
  .forRoutes({ path: 'books', method: RequestMethod.GET });
----

In the first `configure()` above, `{ path: 'books', method: RequestMethod.POST }` inside `exclude()` is what kept
`POST /books` out of the log while `GET /books` stayed in it.

Source: https://docs.nestjs.com/middleware#applying-middleware[NestJS: Middleware - Applying middleware]

[#wildcards]
== Named wildcards

Paths in `forRoutes()` and `exclude()` are patterns. Express 5 (and Nest 11 onward with it) uses `path-to-regexp` v8,
which has no bare `*`: a wildcard must be _named_, written `*name`. The name (`splat` in the docs) has no special
meaning; `*wildcard` works the same. Two forms matter:

[cols="2,3,3",options="header"]
|===
| Pattern | Matches | Does not match

| `abcd/*splat`
| `abcd/1`, `abcd/123`, `abcd/abc`: anything after `abcd/`
| `abcd/` and `abcd`: at least one character must follow

| `abcd/\{*splat}`
| everything above, and `abcd/` too, because the braces make the wildcard optional
| no exceptions: everything under `abcd` matches
|===

String paths treat the hyphen and the dot literally. The scratch test confirms the first row: with the binding
`files/abcd/{*splat}`, `GET /files/abcd/xyz` was logged, and `GET /files/abcd` was not (it matched the controller route
but not the middleware pattern, because the pattern requires a `/` after `abcd`).

[source,typescript]
----
consumer.apply(requestId).forRoutes({ path: 'abcd/*splat', method: RequestMethod.ALL });
consumer.apply(requestId).forRoutes({ path: 'abcd/{*splat}', method: RequestMethod.ALL });
----

For "every route" in a module, `forRoutes('*splat')` is the form to use (it ran in the example above). The legacy
`forRoutes('*')` string also ran in the scratch project, and the official docs still use it in one hint, but writing
the named form avoids depending on that compatibility.

Source: https://docs.nestjs.com/middleware#route-wildcards[NestJS: Middleware - Route wildcards]

[#functional]
== Functional middleware

A class with no state and no dependencies is boilerplate. A plain function with the signature `(req, res, next)` is
accepted anywhere a class is, and has no `@Injectable()` and no interface to implement. A function that _returns_ a
middleware function is the usual way to configure one.

.functional.middleware.ts
[source,typescript]
----
import type { NextFunction, Request, Response } from 'express';

// Functional middleware: no class, no DI, just (req, res, next).
export function requestId(req: Request, res: Response, next: NextFunction): void {
  const id = req.header('x-request-id') ?? crypto.randomUUID();
  res.setHeader('x-request-id', id);
  next();
}

// A factory returns a configured middleware function.
export function stamp(label: string, sink: string[]) {
  return (_req: Request, _res: Response, next: NextFunction): void => {
    sink.push(label);
    next();
  };
}
----

Used from `configure()` with `consumer.apply(requestId).forRoutes('*splat')`, every response in the scratch test carried
an `x-request-id` header (the incoming value, or a generated UUID). Functional middleware cannot inject providers; when
you need one, write a class.

Source: https://docs.nestjs.com/middleware#functional-middleware[NestJS: Middleware - Functional middleware]

[#multiple]
== Multiple middleware

`apply()` takes a comma-separated list; the middleware run in that order, then the next binding runs. This is also how
third-party Express middleware such as `helmet` or `cors` is attached to a subset of routes:

[source,typescript]
----
consumer.apply(cors(), helmet(), logger).forRoutes(CatsController);
----

Within one module, bindings run in the order of the `configure()` calls. Across modules the order is described in
<<ordering>>.

Source: https://docs.nestjs.com/middleware#multiple-middleware[NestJS: Middleware - Multiple middleware]

[#global]
== Global middleware and the DI caveat

To bind a middleware to every route of the application at once, call `app.use()` on the `INestApplication` in
`main.ts`:

.main.ts
[source,typescript]
----
const app = await NestFactory.create(AppModule);
app.use(requestId);
await app.listen(process.env.PORT ?? 3000);
----

`app.use()` hands the function straight to the underlying platform (Express or Fastify); Nest's module system, and
therefore the dependency injection container, is not involved. This is the caveat: a middleware registered with
`app.use()` cannot receive providers in a constructor, and there is no module to resolve them from. There are two
workarounds:

* Use functional middleware with `app.use()`, and read configuration from the environment or the closure.
* Keep the class middleware and bind it in a module with `forRoutes('*splat')` (or the controller classes), where DI works.

In the scratch project a global `app.use(stamp('app.use', order))` ran _before_ every module-level middleware:

.Observed order with app.use() plus module middleware
[source,json]
----
["app.use", "global-module", "root-a", "root-b", "leaf"]
----

Two more consequences of `app.use()` are worth knowing. Errors raised there are handled by the platform, not by Nest's
exceptions layer, so prefer `throw` or `next(err)` from middleware bound with the consumer. And with the Express
adapter Nest registers the `json` and `urlencoded` body parsers by default; to customize them through
`MiddlewareConsumer`, create the application with `bodyParser: false`. In the scratch test that option made a
`POST /books` with a JSON body reach the handler with an empty body (`{}` came back), because nothing parsed it:

[source,typescript]
----
const app = await NestFactory.create<NestExpressApplication>(AppModule, {
  bodyParser: false,
});
----

Source: https://docs.nestjs.com/middleware#global-middleware[NestJS: Middleware - Global middleware] and https://docs.nestjs.com/middleware#applying-middleware[Applying middleware]

[#ordering]
== Ordering across modules

Middleware runs sequentially in the order it is bound, exactly as in Express. For middleware bound in several modules
the official lifecycle page gives the order:

. Middleware from `app.use()` (global).
. Middleware from global modules (`@Global()`).
. Middleware bound in the root module.
. Middleware from the other modules, ordered by their distance from the root module in the import graph.

Nest 11 made this order deterministic, with middleware from global modules first (module resolution switched to
object-reference keys in the same release). The example registers a stamp from a `@Global()` module, from the root
module (two middleware in one `apply()`) and from a leaf module that the root imports:

.order.module.ts
[source,typescript]
----
export const order: string[] = [];

@Global()
@Module({})
export class GlobalFeatureModule implements NestModule {
  configure(consumer: MiddlewareConsumer) {
    consumer.apply(stamp('global-module', order)).forRoutes('*splat');
  }
}

@Module({})
export class LeafModule implements NestModule {
  configure(consumer: MiddlewareConsumer) {
    consumer.apply(stamp('leaf', order)).forRoutes('*splat');
  }
}

@Module({
  imports: [LeafModule, GlobalFeatureModule],
  controllers: [BooksController],
})
export class OrderModule implements NestModule {
  configure(consumer: MiddlewareConsumer) {
    consumer
      .apply(stamp('root-a', order), stamp('root-b', order))
      .forRoutes('*splat');
  }
}
----

Note that the root module imports `LeafModule` _first_, yet the leaf's middleware runs last:

.Observed order for GET /books
[source,json]
----
["global-module", "root-a", "root-b", "leaf"]
----

Do not depend on the relative order of two unrelated feature modules; if one middleware must precede another, bind them
in the same `apply()` call.

Source: https://docs.nestjs.com/faq/request-lifecycle#middleware[NestJS: Request lifecycle - Middleware] and https://docs.nestjs.com/migration-guide[Migration guide]

[#errors]
== Errors thrown from middleware

When middleware bound with the consumer throws, Nest's exceptions layer handles it as it would an error from a handler.
Throw an `HttpException` (or a built-in subclass such as `UnauthorizedException`); an asynchronous middleware must
return its promise (declare `use()` as `async`) so a rejection is forwarded. You can also hand the error to `next()`,
which is the right shape when wrapping Express-style code that reports failures through the callback.

.auth.middleware.ts
[source,typescript]
----
import {
  Injectable,
  NestMiddleware,
  UnauthorizedException,
} from '@nestjs/common';
import type { NextFunction, Request, Response } from 'express';

@Injectable()
export class AuthMiddleware implements NestMiddleware {
  use(req: Request, res: Response, next: NextFunction): void {
    if (!req.headers.authorization) {
      throw new UnauthorizedException();
    }
    next();
  }
}

@Injectable()
export class AsyncAuthMiddleware implements NestMiddleware {
  async use(req: Request, res: Response, next: NextFunction): Promise<void> {
    await Promise.resolve(); // e.g. verify a session in a store
    if (!req.headers.authorization) {
      return next(new UnauthorizedException('Missing credentials'));
    }
    next();
  }
}
----

Both variants, bound with `consumer.apply(...).forRoutes(BooksController)`, answered an unauthenticated request with
401:

[source,bash]
----
curl -i http://localhost:3000/books
----

[source,json]
----
{"message":"Unauthorized","statusCode":401}
----

and, for `AsyncAuthMiddleware`, `{"message":"Missing credentials","error":"Unauthorized","statusCode":401}`. With an
`Authorization` header both continued to the handler and returned 200.

Only *global* exception filters can see these errors (`app.useGlobalFilters()` or an `APP_FILTER` provider), because no
route handler, and therefore no controller or method scope, has been selected yet; `@UseFilters()` on a middleware class
is not supported. The scratch project proved it with an `APP_FILTER` filter that replaced the body, which turned the
401 into `{"filtered":true}` for a middleware error, while `LoggerMiddleware`, the first middleware in the same `apply()`, still ran before `AuthMiddleware` threw.

[source,typescript]
----
@Module({
  controllers: [BooksController],
  providers: [TraceService, { provide: APP_FILTER, useClass: TaggingFilter }],
})
export class FilterModule implements NestModule {
  configure(consumer: MiddlewareConsumer) {
    consumer.apply(LoggerMiddleware, AuthMiddleware).forRoutes('*splat');
  }
}
----

Filters themselves are covered in xref:backend/nestjs/exception-filters-and-error-handling.adoc[Exception Filters &
Error Handling].

Source: https://docs.nestjs.com/middleware#error-handling[NestJS: Middleware - Error handling] and https://docs.nestjs.com/exception-filters[Exception filters]

[#fastify]
== Express versus Fastify

The consumer API is identical on both platforms; what differs is the signature of the middleware. With the Fastify
adapter Nest installs `@fastify/middie` (already a dependency of `@nestjs/platform-fastify`), which runs
Connect-style middleware on Fastify's request cycle. These functions receive the *raw* Node.js request and response
objects, not Fastify's wrappers, so type them with `FastifyRequest['raw']` and `FastifyReply['raw']`, and `next` is a
plain `() => void`.

.raw.middleware.ts
[source,typescript]
----
import { Injectable, NestMiddleware } from '@nestjs/common';
import type { FastifyReply, FastifyRequest } from 'fastify';

@Injectable()
export class RawLoggerMiddleware implements NestMiddleware {
  // @fastify/middie hands over the raw Node.js objects, not Fastify's wrappers.
  use(req: FastifyRequest['raw'], res: FastifyReply['raw'], next: () => void) {
    res.setHeader('x-raw', `${req.method} ${req.url}`);
    next();
  }
}
----

Bound with `consumer.apply(RawLoggerMiddleware).forRoutes(BooksController)` on a `FastifyAdapter` application, this ran
for `/books` and `/books/7`. One pitfall appeared in the test: the raw `req.url` seen by the middleware was `/` for
both, because middie strips the mount path from `req.url`. Do not use `req.url` for routing decisions in Fastify
middleware; Express-specific helpers such as `req.originalUrl`, `req.header()` and `res.json()` are likewise not
available on the raw objects.

[cols="2,3,3",options="header"]
|===
| | Express adapter | Fastify adapter

| Engine
| Express 5 middleware stack
| `@fastify/middie`
| Arguments of `use()`
| Express `Request` / `Response` / `NextFunction`
| raw `IncomingMessage` / `ServerResponse`, `next: () => void`
| Third-party ecosystem
| any Express middleware (`helmet`, `cors`, `cookie-parser`, ...)
| Fastify plugins (`@fastify/helmet`, `@fastify/cors`) are the better fit; register them with `app.register()`
| Default body parsers
| `json` and `urlencoded` registered by Nest; disable with `bodyParser: false`
| Fastify's own content-type parsers
|===

Source: https://docs.nestjs.com/http/performance#middleware[NestJS: Performance (Fastify) - Middleware] and https://fastify.dev/docs/latest/Reference/Middleware/[Fastify: Middleware]

[#vs-guards]
== Middleware versus guards, interceptors and pipes

[cols="2,2,3",options="header"]
|===
| Use | When | Why

| Middleware
| the work is independent of the handler: request ids, logging, CORS, security headers, parsers
| runs first, works on the raw request, can come from the Express/Fastify ecosystem
| Guard
| allow or deny based on the handler (roles, metadata)
| has the `ExecutionContext`, so it can read decorators and the target class
| Interceptor
| code around the handler (timing, response mapping, caching)
| sees both the incoming request and the response stream
| Pipe
| validate or transform a handler argument
| runs after guards, per parameter
|===

Authentication that merely _identifies_ the caller (attach `req.user`) can live in either place, but authorization
decisions belong in guards: a middleware cannot tell whether the route it is about to forward to is public.

[#book]
== What changed recently, and where the book is outdated

* *Express 5 wildcards (Nest 11 onward).* Bare `*` in route patterns is gone; use `*splat` and `{*splat}` as shown above. Patterns copied from older articles or the book (`forRoutes('abcd/*')`) need updating.
* *Global-module ordering (Nest 11).* Middleware from `@Global()` modules runs first, then the root module, then the others by distance from the root.
* *Express 5 and Fastify 5.* Nest 12 targets both; the Fastify raw-object signature above is unchanged.
* *Imports end in `.js` in ESM projects,* the current default template. Nest 12 packages are ESM-only.
* *The book* (published January 2025) shows class and functional middleware with `MiddlewareConsumer.apply().exclude().forRoutes()` correctly, but its wildcard paths predate Express 5's named wildcards, and it does not warn that only global filters catch middleware errors.

Source: https://docs.nestjs.com/migration-guide[Migration guide] and https://docs.nestjs.com/faq/request-lifecycle[Request lifecycle]
