This page is written against NestJS 12.1 (npm `12.1.2`), TypeScript 6 (`6.0.3`), Node.js 20.19+ or 22.12+, Express 5 (`5.2.1`) and Fastify 5 (`5.12.5`), and was checked on 2026-10-02. The running scenario is the *Bookshelf* application used throughout this section.

A *controller* is the class that receives incoming HTTP requests and returns responses. It owns no routing code itself: decorators attach metadata (a path, an HTTP method, parameter sources) and Nest reads that metadata at bootstrap to register routes on the underlying HTTP adapter (Express or Fastify). Everything else a request touches before and after the handler (middleware, guards, interceptors, pipes, filters) is covered on its own page; the order is summarised in xref:backend/nestjs/request-lifecycle.adoc[Request Lifecycle].

== Controllers and the route map

A controller is a class decorated with `@Controller()` and registered in the `controllers` array of a module (see xref:backend/nestjs/modules.adoc[Modules]). A class that is not listed there is never instantiated and none of its routes exist.

.books.controller.ts (shortened)
[source,typescript]
----
import { Body, Controller, Get, Post } from '@nestjs/common';
import { CreateBookDto } from './dto.js';

@Controller('books')
export class BooksController {
  private readonly books = new Map<number, Book>();
  private nextId = 1;

  @Post()
  create(@Body() dto: CreateBookDto): Book {
    const book = { id: this.nextId++, ...dto };
    this.books.set(book.id, book);
    return book; // 201 Created: the default for POST
  }

  @Get()
  findAll(): Book[] {
    return [...this.books.values()];
  }
}
----

The route of a handler is the controller prefix joined with the path given to the method decorator: `@Controller('books')` plus `@Get('latest')` maps `GET /books/latest`. The method name is irrelevant to Nest. You can generate a controller with `nest g controller books` or a full CRUD resource (controller, service, DTOs and a module) with `nest g resource books`; see xref:backend/nestjs/getting-started-and-cli.adoc[Getting Started and the CLI].

Source: https://docs.nestjs.com/controllers#routing[Controllers, "Routing"].

=== `@Controller()` options

`@Controller()` has three call signatures: no argument, a prefix (`string` or `string[]`) or an options object.

[cols="1,3",options="header"]
|===
| Option | Meaning

| `path`
| The route prefix, a `string` or an array of strings. With an array, every handler is registered under each prefix.

| `host`
| A `string`, a `RegExp` or an array of them that the request's host name must match (<<sub-domain-routing>>).

| `version`
| A version (or array of versions) for the whole controller when versioning is enabled. Versioning is a separate feature, see the https://docs.nestjs.com/http/versioning[Versioning] documentation.

| `scope`
| The injection scope of the controller (`Scope.DEFAULT`, `Scope.REQUEST`, `Scope.TRANSIENT`). Controllers are singletons by default, which is safe because Node.js does not use one thread per request.

| `durable`
| Marks a request-scoped controller as durable (shared across requests of the same tenant). Meaningful only together with a request scope.
|===

Source: https://docs.nestjs.com/controllers#state-sharing[Controllers, "State sharing"] and the `ControllerOptions` interface in `@nestjs/common` (checked in the installed package types).

An array of prefixes produces one route per prefix:

.extras.controller.ts (excerpt)
[source,typescript]
----
@Controller(['library', 'shelf'])
export class ExtrasController {
  @Get('page')
  page() { /* ... */ }
}
----

In the scratch project this answered both `GET /library/page` and `GET /shelf/page`.

Source: https://docs.nestjs.com/controllers#routing[Controllers, "Routing"] (array form verified in the scratch project).

=== The global prefix

`app.setGlobalPrefix('api/v1')` prepends a prefix to every route of the application; `exclude` takes route strings (any method) or `{ path, method }` objects.

.main.ts (excerpt)
[source,typescript]
----
import { RequestMethod } from '@nestjs/common';

app.setGlobalPrefix('api/v1', {
  exclude: [{ path: 'shelf/page', method: RequestMethod.GET }],
});
----

With this setting `GET /api/v1/library/page` and `GET /shelf/page` answered `200`, while `GET /library/page` answered `404`.

Source: https://docs.nestjs.com/faq/global-prefix[Global prefix].

== HTTP method decorators

Nest provides a decorator for each HTTP method. All take an optional path, or an array of paths to serve the same handler on several routes.

[cols="2,3",options="header"]
|===
| Decorator | HTTP method

| `@Get()`, `@Post()`, `@Put()`, `@Patch()`, `@Delete()`, `@Options()`, `@Head()`
| The standard methods of the same name.

| `@All()`
| Every method.

| `@Search()`
| `SEARCH`. It is exported by `@nestjs/common`, but the official controllers chapter does not list it; treat it as a less documented API.

| `@QueryMethod()`
| The `QUERY` method (a safe request that carries a body). It is named `QueryMethod` to avoid a clash with the `@Query()` parameter decorator. Added in Nest 11.2.0 (https://github.com/nestjs/nest/pull/17162[PR 17162]).

| `@Propfind()`, `@Proppatch()`, `@Mkcol()`, `@Copy()`, `@Move()`, `@Lock()`, `@Unlock()`
| WebDAV methods. They exist in `@nestjs/common` (verified in the installed package types) but are not described in the official controllers chapter.
|===

.routes.controller.ts (excerpt)
[source,typescript]
----
@Controller('routes')
export class RoutesController {
  // Several paths for one handler
  @Get(['ping', 'health-check'])
  multiPath() {
    return 'pong';
  }

  @Search('books')
  search(@Query('q') q?: string) {
    return { method: 'SEARCH', q };
  }

  @QueryMethod('books')
  queryMethod(@Query('q') q?: string) {
    return { method: 'QUERY', q };
  }

  @All('echo')
  echo(@Req() req: Request) {
    return { method: req.method };
  }
}
----

Calling these routes from a Node.js script:

[source,typescript]
----
const r = await fetch(`${base}/routes/books?q=x`, { method: 'QUERY' });
----

[source,json]
----
{ "method": "QUERY", "q": "x" }
----

`SEARCH` returned `{"method":"SEARCH","q":"x"}`, and `PUT`, `PATCH` and `GET` on `/routes/echo` each returned their own method name. On Express a `QUERY` request with a JSON body was handled without extra configuration. On Fastify, the same request needs a `Content-Type` header: a bare `QUERY` was answered with `400` and the message `Method 'QUERY' must provide a 'Content-Type' header.`, while one with `content-type: application/json` returned `200` and the parsed body.

Source: https://docs.nestjs.com/controllers#resources[Controllers, "Resources"]; release notes https://github.com/nestjs/nest/releases/tag/v11.2.0[v11.2.0].

== Route paths and Express 5 syntax

Nest builds routes with the adapter's own matcher. Express 5 uses path-to-regexp v8, which made the syntax stricter: a wildcard must have a name, optional parts use braces, and the old `?`, `+` and regular-expression characters in strings are gone. Nest adds a compatibility layer so that the common unnamed trailing `*` still works, and the official docs describe the rules this way:

* An asterisk at the *end* of a string path is a wildcard. In string paths the hyphen (`-`) and the dot (`.`) are literal.
* In plain Express 5 a wildcard must be named, such as `+abcd/{*splat}+`; `splat` is an arbitrary name with no special meaning. Nest still accepts an unnamed `*`.
* An asterisk in the *middle* of a path requires a named wildcard on Express (for example `+ab{*splat}cd+`), and Fastify does not support it at all.

[cols="2,3,3",options="header"]
|===
| Syntax | Meaning (path-to-regexp v8) | Result in the scratch project (Express)

| `+abcd/*+`
| Legacy unnamed trailing wildcard, rewritten by Nest.
| Matched `/routes/abcd/`, `/routes/abcd/123/x`.

| `+files/*path+`
| Named wildcard: one or more segments, captured as an array.
| `/routes/files/a/b/c` gave `{"path":["a","b","c"]}`; `/routes/files` was a `404`.

| `+docs{/*rest}+`
| Braces make a part optional; so the wildcard now matches zero or more segments.
| `/routes/docs` gave `{"rest":[]}`; `/routes/docs/a/b` gave `{"rest":["a","b"]}`.

| `catalog{/:lang}/books`
| An optional parameter segment.
| `/routes/catalog/books` gave `{"lang":"default"}`; `/routes/catalog/en/books` gave `{"lang":"en"}`.
|===

.routes.controller.ts (excerpt)
[source,typescript]
----
// Unnamed trailing wildcard: Nest's compatibility layer rewrites it
@Get('abcd/*')
legacyWildcard(@Req() req: Request) {
  return { url: req.url };
}

// Named wildcard (path-to-regexp v8): one or more segments
@Get('files/*path')
namedWildcard(@Param('path') path: string[] | string) {
  return { path };
}

// {/*rest}: zero or more segments
@Get('docs{/*rest}')
optionalWildcard(@Param('rest') rest?: string[]) {
  return { rest: rest ?? [] };
}

// {...}: an optional segment
@Get('catalog{/:lang}/books')
optionalSegment(@Param('lang') lang?: string) {
  return { lang: lang ?? 'default' };
}
----

Source: https://docs.nestjs.com/controllers#route-wildcards[Controllers, "Route wildcards"] and https://docs.nestjs.com/migration-guide[Migration guide].

Note the type of a wildcard parameter: it is captured as an array of segments, not as a slash-separated string.

=== Fastify differences

Fastify's router (`find-my-way`) has its own, smaller syntax. In the scratch project, with the default `FastifyAdapter`:

* `+abcd/*+` (trailing asterisk) and `:a/x/:b` (parameters) worked.
* `+files/*path+`, `+docs{/*rest}+`, `+ab*cd+` and `+ab{*splat}cd+` made `NestFactory.create()` fail at registration with `Wildcard must be the last character in the route`.
* `catalog{/:lang}/books` was accepted but did not match `/catalog/books` or `/catalog/en/books` (both `404`), so the Express optional-segment syntax is not portable.

If an application must run on both adapters, restrict itself to literal segments, `:param` tokens and a single trailing `*`, or declare two explicit routes with an array of paths (`@Get(['docs', 'docs/:page'])`).

Source: https://docs.nestjs.com/controllers#route-wildcards[Controllers, "Route wildcards"]; Express migration notes at https://expressjs.com/en/guide/migrating-5/[Migrating to Express 5]; adapter behaviour verified in the scratch project.

== Route conflicts and resolution order

Nest registers routes in declaration order. On an order-sensitive adapter, such as the default Express adapter, a parametric route declared first silently shadows a more specific one declared later, and the application boots without a warning:

.users.controller.ts
[source,typescript]
----
@Controller('users')
export class UsersController {
  @Get(':id')
  findOne() {
    return { handler: 'findOne' };
  }

  @Get('me') // shadowed by ':id' with the default 'declaration' strategy
  findMe() {
    return { handler: 'findMe' };
  }
}
----

`GET /users/me` returned `{"handler":"findOne"}` on Express. Pipes such as `ParseIntPipe` cannot help: routing chooses the handler before any pipe runs. The classical fix is to declare static routes before parametric ones.

Nest 12 adds two opt-in `NestApplicationOptions` properties. Both default to the previous behaviour.

[cols="2,3",options="header"]
|===
| Option | Values and effect

| `routeConflictPolicy`
| An object with a severity per conflict kind, each `'off'` (default), `'warn'` or `'error'`. `duplicate`: two routes with the same method, path, host and version. `shadow`: two patterns that can match the same request (`/users/me` and `/users/:id`). With `'error'`, all offending pairs are reported together in one `RouteConflictException` thrown from `app.init()` (or from `app.listen()` if you never call `init()`).

| `routeResolutionStrategy`
| `'declaration'` (default) or `'specificity'`. With `'specificity'` the most specific routes are registered first: literal segments beat parametric segments, which beat wildcards.
|===

.main.ts (excerpt)
[source,typescript]
----
const app = await NestFactory.create(AppModule, {
  routeConflictPolicy: { duplicate: 'error', shadow: 'error' },
});
----

[source,text]
----
RouteConflictException: Conflicting HTTP routes detected:
  - Route GET /users/me (UsersController#findMe) is shadowed by GET /users/:id (UsersController#findOne). The first-registered route will match all matching requests on order-sensitive adapters.
Adjust route declarations or relax the 'routeConflictPolicy' option passed to NestFactory.create() to allow the application to start.
----

With `routeResolutionStrategy: 'specificity'` the same controller answered `GET /users/me` with `{"handler":"findMe"}`:

[source,typescript]
----
const app = await NestFactory.create(AppModule, {
  routeResolutionStrategy: 'specificity',
});
----

Express is order-sensitive; Fastify is not, because `find-my-way` already ranks routes by specificity (on Fastify `GET /users/me` returned `findMe` with the default settings, and `shadow` and `'specificity'` are no-ops there). The `duplicate` policy works on both adapters. The `RouteConflictPolicy`, `RouteConflictPolicyLevel` and `RouteResolutionStrategy` types are exported from `@nestjs/common`. Use `shadow: 'error'` in CI or in tests to catch the mistake early, and keep `'specificity'` for codebases where reordering handlers is impractical.

Source: https://docs.nestjs.com/controllers#route-conflicts-and-resolution-order[Controllers, "Route conflicts and resolution order"] and https://docs.nestjs.com/migration-guide[Migration guide, "Route conflict diagnostics"].

== Request data: parameter decorators

Handlers receive request data through parameter decorators. Each one reads from the platform request object, so you rarely need `@Req()`.

[cols="2,3",options="header"]
|===
| Decorator | Value

| `@Request()`, `@Req()`
| `req`

| `@Response()`, `@Res()`
| `res`; switches the handler to library-specific mode (<<library-specific-responses>>)

| `@Next()`
| `next`; also library-specific mode

| `@Session()`
| `req.session`

| `@Param(key?)`
| `req.params` or `req.params[key]`

| `@Body(key?)`
| `req.body` or `req.body[key]`

| `@Query(key?)`
| `req.query` or `req.query[key]`

| `@Headers(name?)`
| `req.headers` or `req.headers[name]`

| `@Cookies(name?)`, `@SignedCookies(name?)`
| Request cookies or verified signed cookies (the HTTP cookies feature)

| `@Ip()`
| `req.ip`

| `@HostParam()`
| `req.hosts` (parameters of the controller `host` option)
|===

`@Body()`, `@Query()`, `@Param()` and `@RawBody()` also accept an options object with `schema` and `pipes` properties, which attaches a Standard Schema (Zod, Valibot, ArkType) to the parameter. The decorator only stores the schema as metadata; validation happens when the `StandardSchemaValidationPipe` (or a custom pipe that reads `metadata.schema`) is registered, as in xref:backend/nestjs/pipes-and-validation.adoc[Pipes & Validation].

Source: https://docs.nestjs.com/controllers#request-object[Controllers, "Request object"].

=== Route parameters, query, headers and the request object

.books.controller.ts (excerpt)
[source,typescript]
----
@Get(':id')
findOne(@Param('id', ParseIntPipe) id: number): Book {
  const book = this.books.get(id);
  if (!book) {
    throw new NotFoundException(`Book ${id} not found`);
  }
  return book;
}

@Get('debug/request')
inspect(
  @Req() request: Request,
  @Ip() ip: string,
  @Headers('user-agent') userAgent: string,
  @Headers() headers: Record<string, string>,
) {
  return { method: request.method, ip, userAgent, hasHeaders: Object.keys(headers).length > 0 };
}
----

[source,bash]
----
curl -i localhost:3000/books/abc
----

[source,json]
----
{ "message": "Validation failed (numeric string is expected)", "error": "Bad Request", "statusCode": 400 }
----

`GET /books/9` for a missing book returned `404` with `{"message":"Book 9 not found","error":"Not Found","statusCode":404}`. Route parameters (like query values) arrive as strings. The `number` annotation on `id` converts nothing; `ParseIntPipe` does, and rejects `abc` with a `400`. To use `Request` as a type with Express install `@types/express` and import it with `import type`.

Source: https://docs.nestjs.com/controllers#route-parameters[Controllers, "Route parameters"].

=== Request payloads and DTOs

A *DTO* (data transfer object) describes the shape of data sent over the network. Declare DTOs as classes, not interfaces: classes survive compilation, so pipes such as `ValidationPipe` can read their metatype at runtime, while interfaces are erased (see xref:backend/nestjs/typescript-for-nestjs.adoc[TypeScript for NestJS]).

.dto.ts
[source,typescript]
----
export class CreateBookDto {
  title: string;
  isbn: string;
  pages: number;
}

export class ListBooksQuery {
  limit?: string;
  offset?: string;
  author?: string;
}
----

[source,bash]
----
curl -i -X POST localhost:3000/books \
  -H 'content-type: application/json' \
  -d '{"title":"Dune","isbn":"978-0441172719","pages":412}'
----

[source,json]
----
{ "id": 1, "title": "Dune", "isbn": "978-0441172719", "pages": 412 }
----

The response status was `201` and a `Cache-Control: no-store` header (set with `@Header()`, below). A class DTO on its own validates nothing: add a `ValidationPipe` with class-validator decorators, or a Standard Schema, to enforce the shape. With `whitelist: true` the `ValidationPipe` also strips properties not declared in the DTO.

Source: https://docs.nestjs.com/controllers#request-payloads[Controllers, "Request payloads"].

=== Query parameters

`@Query()` returns the parsed query string, either as a whole object or one key at a time. Values are strings until a pipe converts them.

.extras.controller.ts (excerpt)
[source,typescript]
----
@Get('page')
page(
  @Query('limit', new DefaultValuePipe(10), ParseIntPipe) limit: number,
  @Query('offset', new DefaultValuePipe(0), ParseIntPipe) offset: number,
) {
  return { limit, offset, types: [typeof limit, typeof offset] };
}
----

`GET /library/page` returned `{"limit":10,"offset":0,"types":["number","number"]}`, and `?limit=x` returned the same `400` `ParseIntPipe` error as above.

A schema can replace the pipes. With `StandardSchemaValidationPipe` registered through `app.useGlobalPipes(new StandardSchemaValidationPipe())` and Zod 4:

.extras.controller.ts (excerpt)
[source,typescript]
----
import { z } from 'zod';

const createBookSchema = z.object({
  title: z.string().min(1),
  pages: z.number().int().positive(),
});
type CreateBook = z.infer<typeof createBookSchema>;

@Post('validated')
create(@Body({ schema: createBookSchema }) body: CreateBook) {
  return body;
}

@Get('typed/:id')
typed(@Param('id', { schema: z.coerce.number().int().positive() }) id: number) {
  return { id, type: typeof id };
}
----

A valid body returned `201` and the parsed value; `{"title":"","pages":-1}` returned `400` with `"message":["title: Too small: expected string to have >=1 characters","pages: Too small: expected number to be >0"]`; `GET /library/typed/7` returned `{"id":7,"type":"number"}` and `/typed/abc` a `400`.

Source: https://docs.nestjs.com/controllers#query-parameters[Controllers, "Query parameters"] and https://docs.nestjs.com/controllers#request-object[Controllers, "Request object"].

=== The Express `simple` and `extended` query parsers

Express 5 changed the default query parser from `extended` to `simple`. Nested objects (`filter[where][name]=John`) and bracket arrays (`item[]=1`) are therefore not parsed unless you switch parser. Both parsers were tried on `/qp?filter[where][name]=John&item[]=1&item[]=2&tag=a&tag=b`:

.main.ts (excerpt, Express)
[source,typescript]
----
const app = await NestFactory.create<NestExpressApplication>(AppModule);
app.set('query parser', 'extended');
----

[cols="1,3",options="header"]
|===
| Parser | `@Query()` value

| `simple` (Express 5 default)
| `{"filter[where][name]":"John","item[]":["1","2"],"tag":["a","b"]}`

| `extended`
| `{"filter":{"where":{"name":"John"}},"item":["1","2"],"tag":["a","b"]}`
|===

Repeated keys (`tag=a&tag=b`) become an array in both. On Fastify there is no such switch; pass a `querystringParser` to the adapter, for example with `qs` (`npm install qs`):

.main.ts (excerpt, Fastify)
[source,typescript]
----
import qs from 'qs';

const app = await NestFactory.create<NestFastifyApplication>(
  AppModule,
  new FastifyAdapter({ querystringParser: (str) => qs.parse(str) }),
);
----

On Fastify this produced `{"filter":{"where":{"name":"John"}},"item":["1","2"]}`. Fastify 5.12 printed a deprecation warning (`FSTDEP022`) saying that router options such as `querystringParser` are to be passed in `routerOptions` of the Fastify instance; the Nest docs still show the form above, so check the adapter documentation when you upgrade.

Source: https://docs.nestjs.com/controllers#query-parameters[Controllers, "Query parameters"].

== Responses

=== Status codes

The default status is `200`, and `201` for `POST`. `@HttpCode()` overrides it for a handler; for a status that depends on runtime data, throw an exception (see xref:backend/nestjs/exception-filters-and-error-handling.adoc[Exception Filters & Error Handling]) or use library-specific mode.

.books.controller.ts (excerpt)
[source,typescript]
----
@Delete(':id')
@HttpCode(HttpStatus.NO_CONTENT)
remove(@Param('id', ParseIntPipe) id: number): void {
  this.books.delete(id);
}
----

`DELETE /books/1` answered `204` with an empty body. A real delete endpoint also needs authorisation (see xref:backend/nestjs/guards.adoc[Guards]); this example omits it to stay focused on routing.

Source: https://docs.nestjs.com/controllers#status-code[Controllers, "Status code"].

=== Response headers

`@Header(name, value)` sets a static response header; use `res.header()` in library-specific mode for dynamic ones.

.books.controller.ts (excerpt)
[source,typescript]
----
@Post()
@Header('Cache-Control', 'no-store')
create(@Body() dto: CreateBookDto): Book { /* ... */ }
----

Source: https://docs.nestjs.com/controllers#response-headers[Controllers, "Response headers"].

=== Redirects

`@Redirect(url?, statusCode?)` redirects the response; the status defaults to `302`. A handler may return an object that follows the `HttpRedirectResponse` interface (`url` and optionally `statusCode`) to override the decorator values at runtime.

.redirect.controller.ts
[source,typescript]
----
@Controller('redirects')
export class RedirectController {
  @Get('static')
  @Redirect('https://nestjs.com', 301)
  staticRedirect() {}

  @Get('docs')
  @Redirect('https://docs.nestjs.com', 302)
  getDocs(@Query('version') version?: string) {
    if (version === '5') {
      return { url: 'https://docs.nestjs.com/v5/' };
    }
  }

  @Get('moved')
  @Redirect()
  moved() {
    return { url: '/books', statusCode: 308 };
  }
}
----

The observed answers were `301` to `https://nestjs.com`, `302` to `https://docs.nestjs.com` (and to `.../v5/` with `?version=5`) and `308` to `/books`. Never build the redirect target from unvalidated user input (an open redirect); validate it against an allow-list first.

Source: https://docs.nestjs.com/controllers#redirection[Controllers, "Redirection"].

=== Async handlers and Observables

A handler may be an `async` function (the returned promise is awaited) or return an RxJS `Observable`; Nest subscribes and sends the last value emitted when the stream completes.

.books.controller.ts (excerpt)
[source,typescript]
----
@Get('count')
async count(): Promise<{ count: number }> {
  return { count: this.books.size };
}

@Get('latest')
latest(): Observable<Book | undefined> {
  const all = [...this.books.values()];
  return of(all[all.length - 1]);
}
----

Both returned the expected JSON. Streams that must keep sending events use Server-Sent Events (`@Sse()`), which is a different mechanism: a handler that returns an `Observable` normally responds once. Interceptors can also run RxJS operators on this stream (see xref:backend/nestjs/interceptors.adoc[Interceptors]).

Source: https://docs.nestjs.com/controllers#asynchronicity[Controllers, "Asynchronicity"].

[[sub-domain-routing]]
== Sub-domain routing

The `host` option of `@Controller()` restricts a controller to requests whose `Host` header matches. Tokens such as `:account` capture the dynamic part, readable with `@HostParam()`.

.host.controller.ts
[source,typescript]
----
@Controller({ host: 'admin.example.com' })
export class AdminController {
  @Get()
  index(): string {
    return 'Admin page';
  }
}

@Controller({ host: ':account.example.com' })
export class AccountController {
  @Get()
  getInfo(@HostParam('account') account: string) {
    return { account };
  }
}
----

[source,bash]
----
curl localhost:3000/ -H 'Host: acme.example.com'
----

[source,json]
----
{ "account": "acme" }
----

`Host: admin.example.com` answered `Admin page`, `acme.example.com` answered the account object, and `example.com` answered `404`. The controllers are matched in registration order, and `:account.example.com` also matches `admin.example.com`, so declare the specific host first (as in the module of the scratch project). The official docs warn that Fastify does not support nested routers and tell you to use the Express adapter if you rely on sub-domain routing; in the scratch project a `host` controller with `@HostParam()` did answer on Fastify (`inject()` with a `host` header), but the officially supported path remains Express, so test your own setup before depending on it.

Source: https://docs.nestjs.com/controllers#sub-domain-routing[Controllers, "Sub-domain routing"].

[[library-specific-responses]]
== Library-specific responses with `@Res()`

The standard approach is to return a value and let Nest send it: objects and arrays become JSON, primitives are sent as they are. The alternative is to inject the platform response with `@Res()` (alias `@Response()`) and call its methods. Nest detects `@Res()` or `@Next()` in the signature and switches the handler to *library-specific mode*, in which you are responsible for sending the response; if you do not, the request hangs.

[mermaid]
----
flowchart LR
  H[Handler runs] --> Q{"@Res() or @Next() injected?"}
  Q -- no --> S["Nest sends the returned value: serialization, status, headers, interceptor results"]
  Q -- yes, passthrough --> S
  Q -- yes, no passthrough --> M["You must send the response yourself"]
  M -- forgot --> X[Request hangs]
----

.response.controller.ts
[source,typescript]
----
@Controller('response')
export class ResponseController {
  // Library-specific mode: Nest hands over the response completely
  @Post('manual')
  manual(@Res() res: Response) {
    res.status(HttpStatus.CREATED).send({ mode: 'manual' });
  }

  // passthrough: set cookies/headers, still return the value
  @Get('passthrough')
  @HttpCode(202)
  passthrough(@Res({ passthrough: true }) res: Response) {
    res.cookie('seen', '1', { httpOnly: true, sameSite: 'lax' });
    return { mode: 'passthrough' };
  }

  // Forgetting to send: the request hangs
  @Get('hang')
  hang(@Res() _res: Response) {
    // intentionally nothing
  }
}
----

Observed results: `POST /response/manual` returned `201` and the JSON body; `GET /response/passthrough` returned `202`, the JSON body and a `Set-Cookie: seen=1; Path=/; HttpOnly; SameSite=Lax` header; `GET /response/hang` never answered (a client with a 500 ms timeout aborted).

What `@Res()` costs, measured with a controller-level interceptor that wraps every result in `{ data: ... }`:

[cols="2,3",options="header"]
|===
| Handler | Response body
| standard: returns `{ x: 1 }`
| `{"data":{"x":1}}`
| `@Res()` calling `res.send({ x: 1 })`
| `{"x":1}` (interceptor mapping lost)
| `@Res({ passthrough: true })` returning `{ x: 1 }`
| `{"data":{"x":1}}`
|===

The official chapter says library-specific mode loses compatibility with features that depend on standard response handling, such as interceptors and the `@HttpCode()` / `@Header()` decorators. In 12.1.2 `@HttpCode(202)` and `@Header('X-A', '1')` were in fact still applied to a `@Res()` handler on both Express and Fastify (the status and header are set before the handler runs), but interceptors were not, so the guidance is: prefer returning values, and use `@Res({ passthrough: true })` when you only need the response object to set a cookie or a header. Beyond interceptors, `@Res()` ties code to the platform (an Express `Response` is not a Fastify reply) and makes unit tests harder because the response must be mocked.

Source: https://docs.nestjs.com/controllers#library-specific-approach[Controllers, "Library-specific approach"].

== Where it sits in the request lifecycle

Routing is the first step. The adapter matches the method and path (and host) to a handler; middleware registered for the route runs next, then guards, interceptors (before the handler), pipes on the parameters (including the ones attached with `@Param('id', ParseIntPipe)`), the handler itself, interceptors (after) and finally exception filters if anything threw. Because the handler is selected first, a pipe can never fix a route conflict (see <<route-conflicts-and-resolution-order>>). Controllers are singletons by default: state held in a field of the controller is shared by every request, and per-request state belongs in a request-scoped provider (see xref:backend/nestjs/providers-and-dependency-injection.adoc[Providers & Dependency Injection]). The complete order and the binding scopes are in xref:backend/nestjs/request-lifecycle.adoc[Request Lifecycle].

== Pitfalls

* *Not registering the controller.* A controller missing from a module's `controllers` array yields `404` for all its routes, with no error at boot.
* *Parametric before static.* `@Get(':id')` above `@Get('me')` shadows `me` on Express; reorder, or enable `routeConflictPolicy` and `routeResolutionStrategy`.
* *Expecting numbers from `@Param()` and `@Query()`.* They are strings; add `ParseIntPipe`, `DefaultValuePipe` or a schema.
* *Interfaces as DTOs.* They are erased at compile time and cannot be validated by pipes; use classes or Standard Schemas.
* *Old wildcard syntax.* `'*'` in the middle of a path and string patterns with `?`, `+` or `()` were Express 4 features; on Express 5 use named wildcards and braces, and avoid them on Fastify.
* *Nested query objects returning flat keys.* Express 5's default `simple` parser does not nest `a[b]=1`; switch to `extended` (Express) or a `querystringParser` (Fastify).
* *`@Res()` without sending.* The request hangs; use `passthrough: true` or return the value.
* *Business logic in the controller.* Keep controllers thin: parse, delegate to a provider, return.

== What changed recently

* *Nest 12.0:* `routeConflictPolicy` and `routeResolutionStrategy`; the `schema` option on `@Body()`, `@Query()`, `@Param()` and `@RawBody()`; the built-in `StandardSchemaValidationPipe`.
* *Nest 11.2.0:* `@QueryMethod()` for the `QUERY` method, and the `@SseSignal()` decorator for SSE handlers.
* *Nest 11:* Express 5 became the default platform, bringing path-to-regexp v8 syntax and the `simple` query parser default.

Source: https://docs.nestjs.com/migration-guide[Migration guide]; https://github.com/nestjs/nest/releases/tag/v12.0.0[v12.0.0] and https://github.com/nestjs/nest/releases/tag/v11.2.0[v11.2.0] release notes.

== Where the book is outdated

The reference book (January 2025, see the xref:backend/nestjs/index.adoc#_bibliography[section bibliography]) predates Nest 12 and the later 11.x releases, so it does not cover the route-conflict options, `QUERY` support or the `schema` option on parameter decorators. Its routing examples follow the Express 4 era; on Express 5 apply the path syntax and query-parser rules above. Where an example returns an error object with HTTP 200, use an HTTP exception or `@HttpCode()` instead so clients can rely on the status code.
