== SWC in depth

SWC is a compiler written in Rust. In a Nest project it replaces the part of `nest build` that turns TypeScript into JavaScript, which makes the compile step itself much faster. The price is that it only _strips types_: it does not check them. The basics (installing `@swc/cli` and `@swc/core`, `nest start -b swc`, the comparison with `tsc` and Rspack) are in xref:backend/nestjs/getting-started-and-cli.adoc#builder-swc[Getting Started & CLI]; this section covers the options, the output, and the places where SWC behaves differently from `tsc`.

=== Options at a glance

[cols="2,3,4",options="header"]
|===
| Where | Option | Effect

| `nest-cli.json` `compilerOptions`
| `builder`
| `"swc"`, or an object `{ "type": "swc", "options": { ... } }`. The options object takes `swcrcPath` (the `.swcrc` file to use, exercised below) and `extensions` (the file extensions to compile; the recipe's example adds `.tsx` and `.jsx`, which Nest applications do not normally need, so it was not run).

| `nest-cli.json` `compilerOptions`
| `typeCheck`
| `true` runs `tsc` in `noEmit` mode next to SWC and fails the build on type errors. Default `false`.

| `nest-cli.json` `compilerOptions`
| `emitDeclarations`
| `true` also writes `.d.ts` files. Default `false`.

| `nest build` and `nest start`
| `-b swc`, `--type-check`, `--no-type-check`, `--emit-declarations`
| The same switches on the command line. Both options are ignored (the CLI prints an `Info` line) when the builder is not `swc`.

| `.swcrc` in the project root, or the file named by `swcrcPath`
| SWC's own configuration
| Parser, decorator and module settings. The builder is preconfigured for Nest, so a `.swcrc` is only needed to change something.
|===

Source: https://docs.nestjs.com/recipes/swc[NestJS: SWC], https://docs.nestjs.com/cli/usages#nest-build[NestJS: CLI usage - nest build]

=== Type checking and declaration files

A build with both options on looks like this:

.nest-cli.json
[source,json]
----
{
  "$schema": "https://json.schemastore.org/nest-cli",
  "collection": "@nestjs/schematics",
  "sourceRoot": "src",
  "compilerOptions": {
    "deleteOutDir": true,
    "builder": "swc",
    "typeCheck": true,
    "emitDeclarations": true
  }
}
----

[source,bash]
----
npx nest build
----

.Output
[source,text]
----
-  TSC  Initializing type checker...
✔  TSC  Initializing type checker...
>  TSC  Found 0 issues.
>  SWC  Running...
Successfully compiled: 2 files with swc (21.09ms)
>  SWC  Emitting declaration files...
----

`dist` then held `app.module.js`, `app.module.js.map`, `main.js`, their `.d.ts` files and a `tsconfig.build.tsbuildinfo`. The declaration for the small module of the scratch project was what `tsc` would have written:

.dist/app.module.d.ts
[source,typescript]
----
export declare class AppController {
    hello(): string;
}
export declare class AppModule {
}
----

Source: https://docs.nestjs.com/cli/monorepo#global-compiler-options[NestJS: CLI workspaces - Global compiler options], https://docs.nestjs.com/recipes/swc#type-checking[NestJS: SWC - Type checking]

Declaration files matter when the project is a library that other packages import (see xref:backend/nestjs/project-structure-and-workspaces.adoc[Project Structure & Workspaces]); an application does not need them, so leave `emitDeclarations` off. Type checking matters always: without it a type error compiles and ships (the demonstration is in the xref:backend/nestjs/getting-started-and-cli.adoc#swc-type-checking[CLI page]). In watch mode the check runs asynchronously, so the process restarts quickly and the errors appear next to it. A CI job should build with `typeCheck` on, or run `tsc --noEmit` as a separate step.

On speed: the documentation claims SWC is about 20 times faster than the TypeScript compiler on its recipe page, and about 10 times on the CLI overview page. On the six-file scratch project here the difference was not visible: `nest build -b tsc` took 0.72 s and `nest build -b swc --no-type-check` 0.76 s wall time, although SWC itself reported 22 ms for the compile, because starting the CLI dominates a build that small. The factor depends on the project size and on whether type checking is on (it is the slow part), so measure your own project before promising a number.

=== The .swcrc file and the module format

Without a `.swcrc` the builder emits the module format that `tsc` would: ES modules when `package.json` has `"type": "module"` (the default of new projects) and CommonJS otherwise. A `.swcrc` that sets `module` overrides that choice, which is a common way to break an ESM project. This `.swcrc` in the root of the ESM scratch project made `nest build` succeed and the application crash at start-up:

.Do not copy: a CommonJS `module` setting in an ESM project
[source,json]
----
{ "module": { "type": "commonjs" } }
----

.Output of node dist/main.js
[source,text]
----
ReferenceError: Cannot determine intended module format because both 'exports' and top-level await are present. If the code is intended to be CommonJS, wrap await in an async function. If the code is intended to be an ES module, use export instead of module.exports/exports.
----

The fix is to leave `module` out of `.swcrc` in ESM projects. In a CommonJS project, the setting `"module": { "type": "commonjs" }` is what Jest needs (below).

To keep the SWC configuration somewhere other than the root, point the builder at it:

.nest-cli.json
[source,json]
----
{
  "$schema": "https://json.schemastore.org/nest-cli",
  "collection": "@nestjs/schematics",
  "sourceRoot": "src",
  "compilerOptions": {
    "deleteOutDir": true,
    "builder": { "type": "swc", "options": { "swcrcPath": "infrastructure/.swcrc" } },
    "typeCheck": true
  }
}
----

.infrastructure/.swcrc
[source,json]
----
{
  "$schema": "https://swc.rs/schema.json",
  "sourceMaps": false,
  "jsc": {
    "parser": { "syntax": "typescript", "decorators": true, "dynamicImport": true },
    "transform": { "legacyDecorator": true, "decoratorMetadata": true },
    "baseUrl": "./"
  },
  "minify": false
}
----

The build succeeded, wrote no `.js.map` files (the file asked for none), and `dist/main.js` was still an ES module. The settings in the file are merged over the builder's Nest defaults rather than replacing them: a second run with an `infrastructure/.swcrc` that contained only `{ "sourceMaps": false }` still emitted the decorator and metadata helpers (`_ts_decorate`, `_ts_metadata`) and the application started and served requests. That is different from Jest with `@swc/jest` (below), which does not use the builder's defaults and needs the decorator settings spelled out in its own `.swcrc`.

Source: https://docs.nestjs.com/recipes/swc#getting-started[NestJS: SWC - Getting started], https://docs.nestjs.com/recipes/swc#swc-configuration[NestJS: SWC - SWC configuration]

=== Decorator metadata and circular imports

Nest resolves constructor parameters from the metadata that `emitDecoratorMetadata` writes, and SWC writes it too (`decoratorMetadata` in `.swcrc`, preconfigured by the builder). The metadata of a decorated property refers to the property's class _by name_ at class-definition time. With two entities that import each other, that reference is read while the other module is still being initialised, and in ES modules the result is a `ReferenceError`. The recipe calls this out for SWC, but it is not specific to it: the same pair compiled with `tsc` in the ESM project failed identically.

.src/entities/user.entity.ts and profile.entity.ts (each imports the other)
[source,typescript]
----
// user.entity.ts
import { Column, Entity, OneToOne, PrimaryGeneratedColumn } from 'typeorm';
import { Profile } from './profile.entity.js';

@Entity()
export class User {
  @PrimaryGeneratedColumn()
  id!: number;

  @Column()
  name!: string;

  @OneToOne(() => Profile, (profile) => profile.user)
  profile!: Profile; // design:type metadata references Profile at definition time
}

// profile.entity.ts has the mirror-image `user!: User` property with @JoinColumn().
----

.Output of node dist/check.js
[source,text]
----
ReferenceError: Cannot access 'Profile' before initialization
----

The fix is the wrapper type from the recipe: `Relation<T>` from TypeORM, which is just `T` to the type checker but a type that has no runtime value, so the metadata falls back to `Object`. One detail the recipe omits matters with the current templates: because `isolatedModules` and `emitDecoratorMetadata` are both on, TypeScript 6 rejects a plain import of `Relation` in a decorated signature with error TS1272, and it must be imported with `import type`:

.src/entities/user.entity.ts after the fix
[source,typescript]
----
import { Column, Entity, OneToOne, PrimaryGeneratedColumn } from 'typeorm';
import type { Relation } from 'typeorm';
import { Profile } from './profile.entity.js';

@Entity()
export class User {
  @PrimaryGeneratedColumn()
  id!: number;

  @Column()
  name!: string;

  @OneToOne(() => Profile, (profile) => profile.user)
  profile!: Relation<Profile>;
}
----

With both entities changed, `nest build` reported `Found 0 issues`, and a script that created a `DataSource` over `better-sqlite3`, saved a user and a profile and loaded the profile with its user printed the saved rows. For ORMs without such a type, declare your own `type WrapperType<T> = T` and use it the same way, including for `@Inject(forwardRef(() => OtherService))` constructor parameters (see xref:backend/nestjs/module-ref-circular-dependencies-and-lazy-loading.adoc[ModuleRef, Circular Dependencies & Lazy Loading]).

Source: https://docs.nestjs.com/recipes/swc#common-pitfalls[NestJS: SWC - Common pitfalls]

=== CLI plugins, monorepos and Rspack

The Swagger and GraphQL CLI plugins are TypeScript compiler transformers, so a builder that does not run `tsc` does not run them. With the SWC builder, `--type-check` (or `typeCheck: true`) is what runs the plugins and writes a serialised metadata file that the application loads at start-up. The exact setup, with `PluginMetadataGenerator`, is on the xref:backend/nestjs/openapi-and-swagger.adoc#plugin-swc[OpenAPI page].

Monorepos compile with Rspack by default since NestJS 12, and the recipe says Rspack already compiles TypeScript with SWC through its built-in loader, so the `swc-loader` and `webpack.config.js` setup that the recipe still shows applies only to the deprecated webpack builder. Those projects get a single bundled file rather than one file per source file (see xref:backend/nestjs/project-structure-and-workspaces.adoc[Project Structure & Workspaces]).

Source: https://docs.nestjs.com/recipes/swc#cli-plugins-swc[NestJS: SWC - CLI Plugins], https://docs.nestjs.com/recipes/swc#monorepo[NestJS: SWC - Monorepo]

=== Tests: Vitest and Jest with SWC

Tests do not go through `nest build`, so the test runner needs its own SWC integration to emit decorator metadata. For Vitest, `unplugin-swc` is a plugin in `vitest.config.e2e.ts`:

.vitest.config.e2e.ts
[source,typescript]
----
import swc from 'unplugin-swc';
import { defineConfig } from 'vitest/config';

export default defineConfig({
  test: {
    include: ['**/*.e2e-spec.ts'],
    globals: true,
    root: './',
  },
  plugins: [
    // Builds the test files with SWC, which emits the decorator metadata Nest needs.
    swc.vite({ module: { type: 'es6' } }),
  ],
});
----

For Jest (CommonJS projects), the transform is `@swc/jest`, with the decorator settings in the project's `.swcrc`:

.jest.config.js
[source,javascript]
----
module.exports = {
  rootDir: '.',
  testRegex: '.*\\.spec\\.ts$',
  testEnvironment: 'node',
  transform: {
    '^.+\\.(t|j)s?$': ['@swc/jest'],
  },
};
----

.A .swcrc that works with @swc/jest (CommonJS)
[source,json]
----
{
  "$schema": "https://swc.rs/schema.json",
  "sourceMaps": true,
  "jsc": {
    "parser": { "syntax": "typescript", "decorators": true, "dynamicImport": true },
    "transform": { "legacyDecorator": true, "decoratorMetadata": true },
    "baseUrl": "./"
  },
  "module": { "type": "commonjs" },
  "minify": false
}
----

A test that injects a service by type and calls an endpoint with supertest (a `BooksController` that takes a `BooksService`) passed with the Vitest configuration above, and, in the CommonJS project, with Jest started as `node --experimental-vm-modules ./node_modules/jest/bin/jest.js`, which is how the scaffolded `test` script runs it. The same Vitest test also passed with a configuration that had no SWC plugin at all: Vitest 4.1 runs on Vite 8, which transforms TypeScript with Oxc and emitted the metadata from `tsconfig.json`. That is why the book-era advice "Vitest needs SWC for decorators" is no longer universally true; the plugin remains the recipe's recommendation because it keeps the behaviour independent of the Vite version and compiles tests the way production is compiled. The details, including the failure on older Vitest, are on xref:backend/nestjs/testing.adoc[Testing]. Remember that supertest 7 needs the default import (`import request from 'supertest'`), and that SWC does not type-check the tests either.

Source: https://docs.nestjs.com/recipes/swc#vitest[NestJS: SWC - Vitest], https://docs.nestjs.com/recipes/swc#jest-swc[NestJS: SWC - Jest + SWC]

== Hot reload

There are two different things called hot reload in Nest, and it helps to keep them apart:

* _Watch mode_ (`nest start --watch`, with `tsc` or SWC) recompiles on change and _restarts the process_. It works with every builder and with ESM and CommonJS projects. See xref:backend/nestjs/getting-started-and-cli.adoc#hot-reload[Getting Started & CLI].
* _Hot-module replacement_ (HMR) keeps the process running, swaps only the changed modules and re-creates the application inside the same process. It is the technique of the documentation's hot-reload recipe. It saves the start-up time of the process, which for large applications is dominated by TypeScript compilation and module loading.

[mermaid]
....
flowchart LR
  A["Edit a .ts file"] --> B{"Which loop?"}
  B -- "watch mode" --> C["Recompile the changed files"]
  C --> D["Kill the process<br/>start a new one"]
  B -- "HMR" --> E["Bundler rebuilds the<br/>changed modules only"]
  E --> F["Same process:<br/>app.close() then new application"]
  D --> G["New code serves requests"]
  F --> G
....

=== HMR with webpack (the documented recipe)

The recipe targets CommonJS projects and the Nest CLI's webpack builder. In NestJS 12 that builder is deprecated (the CLI prints a deprecation notice) and the recipe's own warning says new projects should prefer Rspack, but it still worked in the throwaway CommonJS project with `@nestjs/cli` 12.0.8. Install the packages the CLI asks for (it names them when one is missing, including `fork-ts-checker-webpack-plugin`):

[source,bash]
----
npm i --save-dev webpack webpack-node-externals run-script-webpack-plugin ts-loader fork-ts-checker-webpack-plugin tsconfig-paths-webpack-plugin
----

Add `webpack-hmr.config.js` to the project root. The CLI calls the function with its default webpack options and the `webpack` module, and the function returns the extended configuration:

.webpack-hmr.config.js
[source,javascript]
----
const nodeExternals = require('webpack-node-externals');
const { RunScriptWebpackPlugin } = require('run-script-webpack-plugin');

module.exports = function (options, webpack) {
  return {
    ...options,
    entry: ['webpack/hot/poll?100', options.entry],
    externals: [
      nodeExternals({
        allowlist: ['webpack/hot/poll?100'],
      }),
    ],
    plugins: [
      ...options.plugins,
      new webpack.HotModuleReplacementPlugin(),
      new webpack.WatchIgnorePlugin({
        paths: [/\.js$/, /\.d\.ts$/],
      }),
      new RunScriptWebpackPlugin({ name: options.output.filename, autoRestart: false }),
    ],
  };
};
----

`webpack/hot/poll?100` is the HMR runtime that polls for updates every 100 ms, `nodeExternals` keeps `node_modules` out of the bundle (except that runtime), and `RunScriptWebpackPlugin` starts the bundle once and lets HMR do the rest, hence `autoRestart: false`. Then the entry file registers the hot-module callbacks:

.src/main.ts
[source,typescript]
----
import { NestFactory } from '@nestjs/core';
import { AppModule } from './app.module';

declare const module: any;

async function bootstrap() {
  if (module.hot?.data?.closePromise) {
    // wait for the previous application instance to fully shut down
    await module.hot.data.closePromise;
  }

  const app = await NestFactory.create(AppModule, {
    forceCloseConnections: !!module.hot,
  });
  await app.listen(process.env.PORT ?? 3000);

  if (module.hot) {
    module.hot.accept();
    module.hot.dispose((data: any) => {
      data.closePromise = app.close();
    });
  }
}
bootstrap();
----

The two details that look unnecessary are what prevent `EADDRINUSE` on reload: `app.close()` is asynchronous but webpack does not await the `dispose` callback, so the promise is stashed on `module.hot.data` and awaited by the next instance, and `forceCloseConnections` makes the old server drop keep-alive connections. Run it with the CLI's webpack flags:

[source,bash]
----
nest build --webpack --webpackPath webpack-hmr.config.js --watch
----

With a controller that returned `{ message: 'v1', pid: process.pid }`, changing the string to `v2` while the watcher ran produced this, and the next `curl` returned `{"message":"v2","pid":26162}`, the same process id as before the edit:

.Output
[source,text]
----
Entrypoint main 45.9 KiB = main.js 44 KiB 0.4ca1a00cdb5cd7964f9b.hot-update.js 1.87 KiB
webpack 5.111.1 compiled successfully in 34 ms
[HMR] Updated modules:
[HMR]  - 5
[HMR]  - 3
[HMR] Update applied.
[Nest] 26162  - 10/02/2026, 7:46:11 PM     LOG [NestFactory] Starting Nest application...
----

=== HMR with Rspack

The Rspack builder is the supported direction, and its configuration function has the same shape, except that the second argument is the `@rspack/core` module. The recipe has no Rspack variant; this one was assembled from the webpack recipe and verified in the same CommonJS project. Two differences: Rspack's own HMR runtime lives at `@rspack/core/hot/poll`, and Rspack has no `WatchIgnorePlugin` (`new rspack.WatchIgnorePlugin(...)` throws "is not a constructor"), so the output directory is excluded through `watchOptions.ignored` instead.

.rspack-hmr.config.js
[source,javascript]
----
const nodeExternals = require('webpack-node-externals');
const { RunScriptWebpackPlugin } = require('run-script-webpack-plugin');

// The CLI calls this function with its default Rspack options and the `@rspack/core` module.
module.exports = function (options, rspack) {
  return {
    ...options,
    entry: ['@rspack/core/hot/poll?100', options.entry],
    externals: [
      nodeExternals({
        allowlist: ['@rspack/core/hot/poll?100'],
      }),
    ],
    // Rspack has no WatchIgnorePlugin; keep the emitted output out of the watcher instead.
    watchOptions: { ignored: ['**/dist/**', '**/node_modules/**'] },
    plugins: [
      ...(options.plugins ?? []),
      new rspack.HotModuleReplacementPlugin(),
      new RunScriptWebpackPlugin({ name: options.output.filename, autoRestart: false }),
    ],
  };
};
----

The `main.ts` is the same as above. Select the builder and the configuration on the command line, or in `nest-cli.json` with the object form of `builder` (the CLI documentation names `builder.options.configPath` as the replacement for the deprecated `webpackConfigPath`):

[source,bash]
----
nest build --builder rspack --rspackPath rspack-hmr.config.js --watch
----

.nest-cli.json
[source,json]
----
{
  "$schema": "https://json.schemastore.org/nest-cli",
  "collection": "@nestjs/schematics",
  "sourceRoot": "src",
  "compilerOptions": {
    "deleteOutDir": true,
    "builder": { "type": "rspack", "options": { "configPath": "rspack-hmr.config.js" } }
  }
}
----

Both forms were run. After the same `v1` to `v2` edit the process kept its id (`26726` with the flags, `27826` with the object form), the response changed, and the log showed `Rspack 2.2.8 compiled successfully in 27 ms` followed by `[HMR] Update applied.`

Source: https://docs.nestjs.com/recipes/hot-reload[NestJS: Hot reload], https://docs.nestjs.com/cli/usages#nest-build[NestJS: CLI usage - nest build]

=== ESM projects, limits and pitfalls

New projects are ESM, and this is where HMR is awkward. In the ESM scratch project (`"type": "module"`), the webpack variant did not start at all; the CLI refused with `The webpack compiler does not support ESM projects ("type": "module" in package.json). Please use rspack instead by setting "builder": "rspack" in your nest-cli.json compilerOptions, or use --builder rspack on the command line.` The Nest repository contains an ESM hot-reload sample (`sample/34-hmr-esm`, see the samples table below) whose script uses the same webpack flags and a `.cjs` configuration; it was only read, not run, so check it against your CLI version.

An attempt to run Rspack HMR in the ESM project (an `import.meta.webpackHot` check in `main.ts`, the HMR runtime kept out of the externals, `output.publicPath` set to `./`) started the application and compiled an update in 31 ms, but the update itself failed in Node.js with `[HMR] Update failed: Error [ERR_MODULE_NOT_FOUND]: Cannot find module '.../dist/main.<hash>.hot-update.json.mjs'` and the old code kept serving. The attempt is not a recommendation: for ESM projects use watch mode with the SWC builder, (its restart loop is shown on the xref:backend/nestjs/getting-started-and-cli.adoc#hot-reload[CLI page]), and use HMR where a CommonJS project with webpack or Rspack already exists.

The recipe's own warnings apply too. A bundler does not copy assets (such as `.graphql` files) to `dist`, and a bundle does not support static glob paths such as the `entities` property of `TypeOrmModule`, so list classes explicitly. Application state (caches, in-memory sessions) is lost on every HMR cycle, as with a restart. And a configuration that works for `nest build --watch` is a development tool only: build production artefacts without the HMR entries.

Source: https://docs.nestjs.com/recipes/hot-reload[NestJS: Hot reload]

== AsyncLocalStorage and nestjs-cls

A recurring need in a web application is _request context_: the authenticated user, the tenant, a correlation id, a database transaction. Nest's default answer, request-scoped providers (see xref:backend/nestjs/injection-scopes.adoc[Injection Scopes]), makes every provider that depends on one request-scoped too and costs performance. The alternative that the documentation now prefers for the common case is Node's `AsyncLocalStorage`: wrap the handling of a request in `als.run(store, ...)`, and any code that runs inside that call, however many `await`s deep, can read the same store with `als.getStore()`. It is the equivalent of thread-local storage in other languages, and providers stay singletons.

[mermaid]
....
flowchart TD
  Q["Need per-request state<br/>in singleton providers?"] --> A{"Entry points?"}
  A -- "HTTP only,<br/>one or two values" --> M["Plain AsyncLocalStorage<br/>in a middleware"]
  A -- "HTTP plus jobs,<br/>messages, GraphQL" --> C["nestjs-cls<br/>ClsModule and ClsService"]
  A -- "Already using<br/>NestJS Observe" --> O["TracerService<br/>setAttribute / getAttribute"]
  Q --> R{"Needs a different<br/>instance per request?"}
  R -- "yes" --> S["Request-scoped provider"]
....

The same mechanism is used for log correlation on the xref:backend/nestjs/logging.adoc[Logging] page; this section is the general treatment.

=== A custom implementation

Nest has no built-in abstraction for it, so the recipe builds one with three parts: a module that provides one `AsyncLocalStorage` instance, a middleware that opens the context, and any service that reads it. Middleware is the first thing a request reaches, so the store is visible in guards, pipes, interceptors, controllers and exception filters (see xref:backend/nestjs/middleware.adoc[Middleware] and xref:backend/nestjs/request-lifecycle.adoc[Request Lifecycle]):

.als.module.ts
[source,typescript]
----
import { AsyncLocalStorage } from 'node:async_hooks';
import { Controller, Get, Injectable, MiddlewareConsumer, Module, NestModule } from '@nestjs/common';

export interface RequestStore {
  userId: string;
}

@Module({
  providers: [{ provide: AsyncLocalStorage, useValue: new AsyncLocalStorage<RequestStore>() }],
  exports: [AsyncLocalStorage],
})
export class AlsModule {}

@Injectable()
export class ShelfService {
  constructor(private readonly als: AsyncLocalStorage<RequestStore>) {}

  // A plain singleton that reads per-request state without a request-scoped provider.
  async shelfFor(): Promise<{ userId: string; books: string[] }> {
    await new Promise((resolve) => setTimeout(resolve, Math.random() * 20)); // let requests interleave
    const userId = this.als.getStore()?.userId ?? 'anonymous';
    return { userId, books: [`Dune (shelved by ${userId})`] };
  }
}

@Controller('shelf')
export class ShelfController {
  constructor(private readonly shelf: ShelfService) {}

  @Get()
  find() {
    return this.shelf.shelfFor();
  }
}

@Module({
  imports: [AlsModule],
  providers: [ShelfService],
  controllers: [ShelfController],
})
export class ShelfModule implements NestModule {
  constructor(private readonly als: AsyncLocalStorage<RequestStore>) {}

  configure(consumer: MiddlewareConsumer) {
    consumer
      .apply((req: { headers: Record<string, string | undefined> }, _res: unknown, next: () => void) => {
        const store: RequestStore = { userId: req.headers['x-user-id'] ?? 'anonymous' };
        // Everything the rest of the request does runs inside this callback's async context.
        this.als.run(store, () => next());
      })
      .forRoutes('*path');
  }
}
----

A test sent 20 concurrent requests, each with its own `x-user-id`, through the module; the artificial random delay makes them interleave, and every response carried the id of its own request:

.Output
[source,json]
----
{"userId":"u3","books":["Dune (shelved by u3)"]}
{"userId":"anonymous","books":["Dune (shelved by anonymous)"]}
----

The first line is the response to the request with `x-user-id: u3`, the second the response to a request without the header. On the Fastify adapter the same module returned `{"userId":"fast-1","books":["Dune (shelved by fast-1)"]}` for `x-user-id: fast-1`; the middleware receives the underlying request object on both platforms, so only the types in its signature differ. The pattern was introduced in xref:backend/nestjs/injection-scopes.adoc[Injection Scopes] and the request-id variant appears in xref:backend/nestjs/logging.adoc[Logging].

Source: https://docs.nestjs.com/recipes/async-local-storage#custom-implementation[NestJS: Async local storage - Custom implementation], https://nodejs.org/api/async_context.html#class-asynclocalstorage[Node.js: AsyncLocalStorage]

The limits are the ones the documentation warns about. It hides the data flow (a service now depends on something the constructor does not show), so keep the store small and avoid a catch-all object. It covers only the entry points you wrap: a cron job, a queue consumer or a message handler runs outside the request's `run()` call and sees `undefined`. And outside any context `als.getStore()` returns `undefined`, so code that can run both ways must handle that (the example above falls back to `'anonymous'`).

=== nestjs-cls

`nestjs-cls` (a third-party package maintained outside the Nest core team; "CLS" stands for continuation-local storage) removes the boilerplate: a `ClsModule` that opens the context for you, an injectable and typed `ClsService`, request ids, and initialisers for transports other than HTTP. The package version here is 7.0.1, which supports NestJS 10 to 12. The first example uses four of its features at once: a typed store, a context opened by an _interceptor_ instead of a middleware, a proxy provider, and a request id.

.cls.module.ts (the module and the controller)
[source,typescript]
----
import { randomUUID } from 'node:crypto';
import { CanActivate, Controller, ExecutionContext, Get, Injectable, Module, UseGuards } from '@nestjs/common';
import { ClsModule, ClsService, ClsStore, InjectableProxy } from 'nestjs-cls';

// A typed store: keys and value types are checked by ClsService<BookshelfStore>.
export interface BookshelfStore extends ClsStore {
  userId: string;
  tenant: string;
}

// A guard that authenticates; the interceptor-mounted setup runs after it, so it can see request.user.
@Injectable()
export class DemoAuthGuard implements CanActivate {
  canActivate(context: ExecutionContext): boolean {
    const req = context.switchToHttp().getRequest();
    req.user = { id: req.headers['x-user-id'] ?? 'anonymous' };
    return true;
  }
}

@Injectable()
export class AuditService {
  constructor(private readonly cls: ClsService<BookshelfStore>) {}

  describe() {
    return { id: this.cls.getId(), userId: this.cls.get('userId'), tenant: this.cls.get('tenant') };
  }
}

// A proxy provider: a request-aware object that is still injected like a singleton.
@InjectableProxy()
@Injectable()
export class CurrentUser {
  constructor(public readonly cls: ClsService<BookshelfStore>) {}
  get id(): string {
    return this.cls.get('userId');
  }
}

@Controller('audit')
@UseGuards(DemoAuthGuard)
export class AuditController {
  constructor(
    private readonly audit: AuditService,
    private readonly user: CurrentUser,
  ) {}

  @Get()
  find() {
    return { ...this.audit.describe(), proxyUserId: this.user.id };
  }
}

@Module({
  imports: [
    ClsModule.forRoot({
      global: true,
      // Mount an interceptor instead of the middleware so setup() runs after the guards.
      interceptor: {
        mount: true,
        generateId: true,
        idGenerator: () => randomUUID(),
        setup: (cls, context) => {
          const req = context.switchToHttp().getRequest();
          cls.set('userId', req.user?.id ?? 'anonymous');
          cls.set('tenant', req.headers['x-tenant'] ?? 'public');
        },
      },
    }),
    ClsModule.forFeature(CurrentUser),
  ],
  controllers: [AuditController],
  providers: [AuditService],
})
export class AuditModule {}
----

A request with `x-user-id: ann` and `x-tenant: acme` returned the following (with a fresh UUID each time), on both Express and Fastify:

.Output
[source,json]
----
{"id":"698c86cc-0834-4bf3-addf-f779158b3faf","userId":"ann","tenant":"acme","proxyUserId":"ann"}
----

The choices in this module are worth explaining:

* *Where the context opens.* `ClsModule.forRoot()` can mount a _middleware_ (the recipe's choice, it is the earliest point), a _guard_ or an _interceptor_ (each with `mount`, `setup`, `generateId` and `idGenerator`). Middleware runs before guards, so it cannot see what a guard attaches to the request (such as `request.user`); a guard or interceptor opens the context later but with the full execution context, which also works for GraphQL and other transports. Setting `middleware.setup`, as the official recipe does, is the simplest form when nothing from the guards is needed.
* *Typing.* `ClsService<BookshelfStore>` makes `get('userId')` return `string` and rejects unknown keys, and `ClsStore` is the base interface (a plain `interface` extending it works here, unlike the typing of the Observe store below).
* *Proxy providers.* A class decorated with `@InjectableProxy()` and registered with `ClsModule.forFeature(CurrentUser)` is injected like a singleton, but its properties and methods are resolved against the current context on each access, so business classes can depend on `CurrentUser` without knowing about CLS. Factory proxies (`forFeatureAsync()`) are the variant for values that need other providers to construct.
* *Ids.* `generateId: true` makes `cls.getId()` return an id per context, and the `idGenerator` option replaces the generator. The package can also keep the request itself in the store (the `saveReq` option and the `CLS_REQ` key, per the recipe); check the package documentation for the defaults before relying on them.

Source: https://docs.nestjs.com/recipes/async-local-storage#nestjs-cls[NestJS: Async local storage - NestJS CLS], https://github.com/Papooch/nestjs-cls[nestjs-cls repository]

Beyond HTTP, a background job or a message handler can open its own context with the `@UseCls()` decorator on an async method:

.The job (in cls.module.ts)
[source,typescript]
----
import { randomUUID } from 'node:crypto';
import { Injectable } from '@nestjs/common';
import { ClsService, UseCls } from 'nestjs-cls';
import { BookshelfStore } from './cls.module.js';

@Injectable()
export class ReindexJob {
  constructor(private readonly cls: ClsService<BookshelfStore>) {}

  @UseCls<[string]>({
    generateId: true,
    idGenerator: () => `job-${randomUUID()}`,
    setup: (cls, tenant) => cls.set('tenant', tenant),
  })
  async run(tenant: string): Promise<{ id: string; tenant: string }> {
    await Promise.resolve();
    return { id: this.cls.getId(), tenant: this.cls.get('tenant') };
  }
}
----

Calling `run('acme')` returned `{"id":"job-f3585543-2d67-45cd-8265-513314256281","tenant":"acme"}`. The decorator needs the module to be initialised (in a test, `await moduleRef.init()` after `compile()`); without that, the first call failed with `this.beforeSetupHooks is not iterable`, because the plugin hooks are registered during module initialisation.

In unit tests the `ClsService` is an ordinary provider, so it can be mocked. To use the real one, import the static `ClsModule` (which provides only the service) and wrap the call under test in `runWith()`, passing a hand-made store:

.Unit test with a hand-made store
[source,typescript]
----
const mod = await Test.createTestingModule({ imports: [ClsModule], providers: [AuditService] }).compile();
const cls = mod.get<ClsService<BookshelfStore>>(ClsService);
const audit = mod.get(AuditService);

const out = cls.runWith({ userId: 'u42', tenant: 't1' }, () => audit.describe());
// out: { id: undefined, userId: 'u42', tenant: 't1' }
----

Calling `ClsService` outside any context did not throw: `cls.isActive()` was `false` and `get('tenant')` and `getId()` returned `undefined`.

Source: https://docs.nestjs.com/recipes/async-local-storage#testing[NestJS: Async local storage - Testing]

=== NestJS Observe

If the application is instrumented with NestJS Observe (the pre-1.0 `@nestjs/observe` package, set up on the xref:backend/nestjs/health-checks-and-observability.adoc[Health Checks & Observability] page), it already maintains an `AsyncLocalStorage` store for every request, job and message it traces, and `TracerService` exposes it through `setAttribute()` and `getAttribute()`. There is no module or middleware to write, and the store exists wherever Observe traces an operation, not only on HTTP:

.observe.module.ts
[source,typescript]
----
import { Controller, Get, Injectable, Module, Req } from '@nestjs/common';
import { ConfigModule, ConfigService } from '@nestjs/config';
import { createObserveModule, TracerService } from '@nestjs/observe';

export const { ObserveModule, ObserveInstrument } = createObserveModule();

// A type alias (not an interface) satisfies the store constraint.
type RequestStore = { userId: string };

@Injectable()
export class CatalogService {
  constructor(private readonly tracer: TracerService<RequestStore>) {}

  forCurrentUser() {
    // Written by the controller, read here, with no module or middleware of our own.
    return { userId: this.tracer.getAttribute('userId'), traceId: this.tracer.currentTraceId() };
  }
}

@Controller('catalog')
export class CatalogController {
  constructor(
    private readonly tracer: TracerService<RequestStore>,
    private readonly catalog: CatalogService,
  ) {}

  @Get()
  find(@Req() req: { headers: Record<string, string> }) {
    this.tracer.setAttribute('userId', req.headers['x-user-id'] ?? 'anonymous');
    return this.catalog.forCurrentUser();
  }
}

@Module({
  imports: [
    ConfigModule.forRoot({ isGlobal: true }),
    ObserveModule.forRootAsync({
      imports: [ConfigModule],
      inject: [ConfigService],
      useFactory: (config: ConfigService) => ({
        appKey: config.getOrThrow<string>('OBSERVE_APP_KEY'),
        appSecret: config.getOrThrow<string>('OBSERVE_APP_SECRET'),
        serviceId: 'bookshelf-api',
      }),
    }),
  ],
  controllers: [CatalogController],
  providers: [CatalogService],
})
export class CatalogModule {}
----

The application was created with `NestFactory.create(CatalogModule, { instrument: ObserveInstrument })`. Two concurrent requests with different `x-user-id` headers returned `{"userId":"ann","traceId":"01a0fdb6-ed38-7b21-a7c4-acfa9344bff6"}` and `{"userId":"bob","traceId":"01a0fdb6-ed3c-740a-a24f-9cf87050cd3b"}`: each saw its own value and its own trace id (a stand-in HTTP server received the telemetry; the hosted dashboard was not used). The API key pair comes from configuration, never from source. `getAttribute()` and `setAttribute()` throw outside a traced context, while `currentTraceId()` returns `null`; and as noted on the observability page, `TracerService<Store>` needs the store type to be a `type` alias, because an `interface` has no index signature and TypeScript 6 rejects it.

Source: https://docs.nestjs.com/recipes/async-local-storage#nestjs-observe[NestJS: Async local storage - NestJS Observe], https://docs.nestjs.com/observability/manual-instrumentation[NestJS: Observability - Manual instrumentation]

=== Choosing

[cols="2,3,3",options="header"]
|===
| Approach | Use it when | Watch out for

| Plain `AsyncLocalStorage` in a middleware
| HTTP only, one or two values, no extra dependency.
| You write the module, the types and the non-HTTP entry points yourself.

| `nestjs-cls`
| HTTP plus GraphQL, queue consumers, scheduled jobs or messages; typed store; proxy providers; testing helpers.
| A third-party dependency with its own release cycle; open the context in a guard or interceptor if `setup` needs authentication results.

| `TracerService` of `@nestjs/observe`
| The application already uses the hosted observability service.
| Pre-1.0 package; throws outside a traced context.

| Request-scoped providers
| A provider genuinely needs a new instance per request.
| The scope bubbles up the dependency graph and costs performance (see xref:backend/nestjs/injection-scopes.adoc[Injection Scopes]).
|===

== Where the book is outdated

The reference book (see the xref:backend/nestjs/index.adoc#_bibliography[section bibliography]) was published in January 2025, before NestJS 12, so it cannot describe the tooling of this page as it is today:

* SWC is now a first-class builder with `typeCheck` and `emitDeclarations` options, Rspack replaced webpack as the bundler (webpack is deprecated, and CLI 12.0.8 refuses it in ESM projects), and new projects are ESM, which changes how decorator metadata, circular imports and HMR behave.
* New projects test with Vitest on ESM (Jest remains for CommonJS), and the SWC plugin for Vitest is optional on current Vitest, as shown above.
* The documentation now presents `AsyncLocalStorage` (or the store of NestJS Observe) as the default for request context and request scope as the exception, so older material that reaches for request-scoped providers first predates that guidance.
* Links to documentation pages from before the September 2026 restructure (the `/techniques/` URLs, for instance) no longer match the current sidebar.

== What changed recently

* NestJS 12 (2026-08-27): Rspack became the default builder for monorepos, `--webpack` and `--webpackPath` were deprecated in favour of `--builder rspack` and `--rspackPath`, and `nest build` gained `--emit-declarations`, `--no-type-check` and `--silent`. The hot-reload and SWC recipes carry warnings to that effect, and CLI 12.0.8 refused the webpack builder in an ESM project. See the https://docs.nestjs.com/migration-guide[migration guide].
* The async-local-storage recipe gained the NestJS Observe section (`@nestjs/observe` 0.x, pre-1.0), and the observability chapter is new in the September 2026 documentation restructure.
* `nestjs-cls` is at 7.0 with support for NestJS 10 to 12; its `ClsModule` options (`middleware`, `guard`, `interceptor`, `plugins`, `proxyProviders`) are unchanged in spirit from the versions older tutorials describe.
* The samples repository lists 37 applications on 2026-10-02; the highest numbers (`34-hmr-esm`, `35-zod-validation`, `36-valibot-serializer`, `37-outbox`) match features the 12.x line added or emphasises (ESM, Standard Schema, the outbox).
* Vite 8 (Oxc) made decorator metadata work in Vitest without SWC; `unplugin-swc` 2 remains supported.
