  no numbers were

== How the Vapor ecosystem is organised

Four groups publish packages that a Vapor application uses:

* *vapor* (https://github.com/vapor) -- the framework itself and the packages that the Vapor team maintains:
  vapor/vapor, the
  Fluent family, Leaf, Redis, Queues, JWT, APNS and their kits. The versions are in the closing section of each page
  of this
  section.
* *vapor-community* (https://github.com/vapor-community) -- an organisation for packages that the community maintains
  under the Vapor
  name. It holds a lot of repositories that have not been touched for years (Vapor 1 to 3 providers), so every package
  taken from
  there needs the date check this page performs.
* *Swift Server Workgroup (SSWG) and Apple packages* -- SwiftNIO, swift-log, swift-metrics, swift-distributed-tracing,
  AsyncHTTPClient, swift-service-lifecycle, swift-configuration, swift-openapi-generator and swift-crypto. Vapor
  builds on these and
  they are shared with every other Swift server framework; see
  xref:backend/vapor/introduction-and-architecture.adoc[Introduction & Architecture].
* *Independent maintainers* -- Soto, MongoKitten, Graphiti, APNSwift, VaporSecurityHeaders and similar. Vapor
  documents some of them,
  but a Vapor release does not wait for them.

A Fluent or Leaf package that is not yet compatible with Vapor 5 will not resolve next to it, and several community
packages declare a
dependency on Vapor 4; check the dependency range before planning a move, as described in
xref:backend/vapor/whats-new-upgrading-and-vapor-5.adoc[What's New, Upgrading and Vapor 5].

== Vapor and Hummingbird 2

Hummingbird is the main alternative among Swift server frameworks. On 2026-10-17
https://github.com/hummingbird-project/hummingbird[hummingbird-project/hummingbird]
was not archived, its latest release was 2.28.0 (2026-10-13), the previous ones 2.27.1 (2026-10-09) and 2.27.0
(2026-09-21), and its
`Package.swift` declared `swift-tools-version:6.2`. Two companion packages in the same organisation were also active:
hummingbird-auth 2.5.0 (2026-09-27) and hummingbird-fluent 2.0.0 (2025-01-10, which lets Hummingbird use Fluent).

[cols="2,3,3",options="header"]
|===
|Aspect |Vapor 4.122 |Hummingbird 2.28

|Shape
|Batteries included: routing, Content, validation, sessions, authentication helpers, commands, a test helper and an application lifecycle in the one package, with Fluent, Leaf, Queues and Redis as sibling packages.
|A small core (router, middleware, server, request context) and separate packages for authentication, Fluent, WebSocket, and so on. You assemble what you need.

|Concurrency
|SwiftNIO under an async/await API; `EventLoopFuture` remains in the public API for legacy code.
|SwiftNIO and structured concurrency; the HTTP server is built to run as a swift-service-lifecycle service.

|Per-request state
|The `Request` object, `req.storage`, `req.application`.
|A generic request context type that you define, with the data a handler needs.

|Data access
|Fluent, with SQLKit underneath, is the default and is documented as part of the framework.
|You choose: hummingbird-fluent, or a database driver such as PostgresNIO, directly.

|Documentation and books
|The most documentation, books (the three consulted for this section) and community packages in Swift server development.
|Its own official documentation; fewer books were found and fewer third-party integrations are listed in this section.

|Next major
|5.0.0-beta.4, not generally available (see xref:backend/vapor/whats-new-upgrading-and-vapor-5.adoc[What's New, Upgrading and Vapor 5]).
|Version 2 is the current major.
|===

The rows describe design as documented by the two projects and as seen in their repositories; no benchmark was run.
Both are built on
SwiftNIO and the SSWG libraries, so many packages (AsyncHTTPClient, swift-log, swift-otel, Soto, MongoKitten,
swift-openapi-generator,
APNSwift) work with either. Choose Vapor for an integrated stack with a large body of tutorials; consider Hummingbird
for a small
service or when you want to choose each piece. Neither choice is irreversible: handlers written against `Content`,
services behind
protocols and a separate data layer move more easily, as discussed in
xref:backend/vapor/services-storage-and-dependency-injection.adoc[Services, Storage and Dependency Injection].

When Vapor is a good fit: you want one language across an iOS or macOS client and the backend and can share model
types (see
xref:backend/vapor/full-stack-swift-with-ios-clients.adoc[Full-Stack Swift with iOS Clients]); you want strong typing
with a compiler that checks data-race
safety; the team already writes Swift. When it is not: you need the larger hiring pool, library choice and operational
experience that
the Java, JavaScript and Python ecosystems offer, or integrations that only have a Java, PHP or Node client. These are
judgements,
not measurements.

A broader comparison of backend and web frameworks across all the languages of this site is planned in issue #263;
this table covers
only the five frameworks named above.

== A checklist for adding a dependency

. Open the repository and note whether it is archived and the date of the latest release; a package that has not
  changed in three years
  may still be fine if it is small, but you own that decision.
. Read `Package.swift` for the swift-tools-version and the platforms. A tools version of 5.x compiles as Swift 5 code,
  which does not get
  the Swift 6 data-race checks in your build for that target.
. Check which Vapor major it depends on. A dependency on Vapor 4 will not resolve with Vapor 5.
. Pin it with `from:` or `exact:` and let Dependabot or a manual `swift package update` review the changes; see
  xref:backend/vapor/security-hardening.adoc[Security Hardening].
. Put it behind a protocol of your own when it is a service you may replace (email, push, storage), as the pages for
  email and Apple
  push notifications do.

== What could not be verified

* Whether the packages marked "not evaluated" work with Vapor 4.122.2 on Swift 6. Only their GitHub status was read.
* The GitHub status of repositories whose exact names could not be found (see "Not found or not recommended").
* No benchmark and no feature count of the other frameworks was taken; the framework table reflects design, not
  measured behaviour.
* The Kitura and Perfect dates come from the GitHub API on 2026-10-17 and may differ on other branches.
