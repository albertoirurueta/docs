== Upgrading from Vapor 2 and Vapor 3 to Vapor 4

Vapor 4 is a rewrite, not a rename. The official guide https://docs.vapor.codes/upgrading/[Upgrading to 4.0] covers
Vapor 3 to 4.0 only, and it is itself frozen at Swift 5.2 and Xcode 11.4: its `main.swift` example still uses the
`Application(env)` initializer that 4.113 deprecated, it chains `EventLoopFuture` values with `flatMapThrowing`, and it
predates `async`/`await`. Use it for the mapping of concepts, and apply the current forms from the tables below. The
current documentation has no Vapor 2 to 3 guide; the Vapor 2 entries below describe what the Patel book teaches.

Upgrade in the order of the tables: the project and the process first (nothing else compiles until they are right), then
services and configuration, routing and requests, concurrency, Fluent, Leaf and authentication, and the tests last.

=== The project and the process

[cols="2,4,5",options="header"]
|===
|Area |Vapor 2 and 3 (the books) |Vapor 4.122.2 (this section)

|Targets and layout
|V3: `+Sources/App/{app,boot,configure,routes}.swift+` plus a `Sources/Run/main.swift` target, `swift-tools-version:4.0`. V2: a `Droplet` configured from `+Config/*.json+`.
|One executable target `App` with `entrypoint.swift`, `configure.swift` and `routes.swift`, `swift-tools-version:6.3` in the template (6.0 is the minimum), automatic test discovery, and `DTOs/`, `Models/` and `Controllers/` folders. See xref:backend/vapor/project-structure-and-swiftpm.adoc[Project structure and SwiftPM].

|Entrypoint
|V3: `app(env).run()`. V2: `Droplet()` then `drop.run()`. Early Vapor 4 and the official upgrade guide: `Application(env)`, `+defer { app.shutdown() }+`, `try app.run()`.
|`@main enum Entrypoint` with `Environment.detect()`, `LoggingSystem.bootstrap(from:)`, `Application.make(env)`, `configure(app)`, `app.execute()` and `app.asyncShutdown()`. See xref:backend/vapor/application-lifecycle-and-entrypoint.adoc[Application lifecycle and entrypoint].

|Toolchain
|Swift 4 or 5.x, Xcode 9 to 11, Ubuntu 14.04 to 18.04, the Vapor APT repository, `check.vapor.sh`, `vapor build`, `vapor run`, `vapor xcode`, `vapor cloud`, `vapor heroku` and `swift package generate-xcodeproj`.
|Swift 6.x through Swiftly, Xcode or a Docker image. Toolbox 20 only creates projects (`vapor new`); open `Package.swift` directly in Xcode or VS Code. See xref:backend/vapor/installation-and-toolchain.adoc[Installation and toolchain].

|Dependencies
|V3: `vapor/auth`, `vapor/core`, `vapor/crypto`, `vapor/multipart`, `vapor/url-encoded-form`, and database packages such as `fluent-postgresql`.
|Authentication, SwiftCrypto, multipart and URL-encoded forms are part of `vapor`; `fluent` is a separate dependency and every database package is named `fluent-<database>-driver`. See xref:backend/vapor/fluent-overview-and-drivers.adoc[Fluent overview and drivers].
|===

The entrypoint that replaces all of the first three rows. It is the template's `entrypoint.swift` without the
commented-out executor takeover, and `configure` and `routes` are the two functions of the next listings:

[source,swift]
----
import Logging
import Vapor

@main
enum Entrypoint {
    static func main() async throws {
        var env = try Environment.detect()
        try LoggingSystem.bootstrap(from: &env)

        let app = try await Application.make(env)

        do {
            try await configure(app)
            try await app.execute()
        } catch {
            app.logger.report(error: error)
            try? await app.asyncShutdown()
            throw error
        }
        try await app.asyncShutdown()
    }
}
----

Source: https://github.com/vapor/template/blob/main/Sources/App/entrypoint.swift[vapor/template: entrypoint.swift]

The forms that the books and early Vapor 4 projects use still compile in 4.122.2, but they are deprecated. A scratch
target containing the official upgrade guide's `main.swift`:

[source,swift]
----
import Vapor

var env = try Environment.detect()
let app = Application(env)
defer { app.shutdown() }
try app.run()
----

produced this diagnostic (and no other) with `swift build`:

----
Sources/Legacy/main.swift:5:11: warning: 'init(_:_:)' is deprecated: Migrate to using the async APIs. Use use Application.make(_:_:) instead
----

The synchronous `shutdown()` is marked `noasync` since 4.99.0, so it is flagged inside an `async` function but not in
top-level code like the listing. Vapor 3's `app(env)` function, the `Run` target and `main.swift` have no counterpart
that compiles.

=== Services, configuration and providers

[cols="2,4,5",options="header"]
|===
|Area |Vapor 2 and 3 (the books) |Vapor 4.122.2 (this section)

|Configuration function
|V3: `configure(_ config: inout Config, _ env: inout Environment, _ services: inout Services)` and a separate `boot.swift`. V2: JSON files under `Config/`, with per-environment subfolders and `$PORT:8080` style environment references.
|`func configure(_ app: Application) async throws`; `boot.swift` content moves into it. Settings are properties of `app`. See xref:backend/vapor/configuration-and-environment.adoc[Configuration and environment].

|Services and providers
|V3: `+services.register(...)+`, `+config.prefer(...)+`, `try req.make(Client.self)`, `Container`, `Service`, `ServiceType`. V2: Providers added to the `Droplet`.
|Services are properties and methods of `Application` and `Request` (`req.client`, `req.db`, `req.view`), added with extensions. Stored properties use `app.storage` and a `StorageKey`; startup and shutdown hooks use `LifecycleHandler`. See xref:backend/vapor/services-storage-and-dependency-injection.adoc[Services, storage and dependency injection].

|Server settings
|V3: `services.register(NIOServerConfig.default(port: 8281))`.
|`app.http.server.configuration.port = 8281`. See xref:backend/vapor/server-configuration.adoc[Server configuration].

|Middleware
|V3: `MiddlewareConfig`, `middlewares.use(ErrorMiddleware.self)` by type, `services.register(middlewares)`.
|`+app.middleware.use(...)+` with an instance (`ErrorMiddleware.default(environment: app.environment)`), at `.beginning` or `.end`, and `+grouped(...)+` on routes. See xref:backend/vapor/middleware.adoc[Middleware].

|Environment
|V3: `Environment.get`. V2: `Config/secrets` and `$VAR:default`.
|`Environment.get`, `Environment.process`, `.env` and `.env.<environment>` files, `Environment.secret(key:)`, `app.environment`. See xref:backend/vapor/configuration-and-environment.adoc[Configuration and environment].

|Commands and console
|V3: `CommandConfig` registered in `configure` and the separate `Console` package.
|ConsoleKit commands with `Signature`, registered on `app.asyncCommands`; `AsyncCommand` is the current protocol. See xref:backend/vapor/commands.adoc[Commands].

|Logging
|V3: `LoggerAPI` (IBM) or Vapor's own `Logger` service.
|swift-log, bootstrapped with `LoggingSystem.bootstrap(from:)`, `req.logger` and `app.logger`. See xref:backend/vapor/logging.adoc[Logging].
|===

=== Routing, requests and content

[cols="2,4,5",options="header"]
|===
|Area |Vapor 2 and 3 (the books) |Vapor 4.122.2 (this section)

|Registering routes
|V3: `routes(_ router: Router, _ container: Container)` and `router.get("books", Int.parameter)`. V2: `drop.get`, `drop.resource("books", BookController())` with `ResourceRepresentable`.
|`routes(_ app: Application)` and `app.get("books", ":bookID")`. Resource controllers are `RouteCollection` values. Paths are comma separated and never contain a slash inside a component. See xref:backend/vapor/routing.adoc[Routing] and xref:backend/vapor/controllers-and-route-collections.adoc[Controllers and route collections].

|Path parameters
|V3: `try req.parameters.next(Book.self)`; the `Parameter` protocol, and models as path components.
|`req.parameters.get("bookID", as: UUID.self)` or `require`; look the model up with `Book.find(_:on:)`.

|Request bodies
|V2: `request.json`, `Node`, `JSONConvertible`, `makeJSON()`. V3: `req.content.decode(User.self)` returned a `Future` and `req.http` wrapped `HTTPRequest`.
|`let user = try req.content.decode(User.self)` is synchronous and throwing in 4.x, because the body is collected first; `req.http` is gone. Large bodies use `body: .stream`. See xref:backend/vapor/content-and-codable.adoc[Content and Codable] and xref:backend/vapor/request-and-response.adoc[Request and response].

|Validation
|V3: a different `Validatable` with `validations()` returning an array.
|`static func validations(_ validations: inout Validations)` and `req.content.decode` followed by `validate(content:)`. See xref:backend/vapor/validation.adoc[Validation].

|Errors
|V2 and V3: `Abort` plus `Debuggable` in a separate package.
|`Abort`, `AbortError` and `DebuggableError` in Vapor, and `ErrorMiddleware`. See xref:backend/vapor/error-handling.adoc[Error handling].

|Files and uploads
|V3: `DirectoryConfig`, `req.streamFile`, `FileMiddleware` registered through `MiddlewareConfig`.
|`app.directory`, `req.fileio`, `FileMiddleware(publicDirectory:)` added with `app.middleware.use`, `File` in a `Content` struct. See xref:backend/vapor/static-files-and-file-io.adoc[Static files and file I/O] and xref:backend/vapor/file-uploads-and-streaming.adoc[File uploads and streaming].

|Sessions and caching
|V3: `KeyedCache`, `MemoryKeyedCache`, `SessionsMiddleware` registered through services; a Redis provider with `jsonSet` and `jsonGet`.
|`app.sessions`, `app.caches.use(.memory)`, `.fluent` or `.redis`, and `req.cache`. See xref:backend/vapor/sessions.adoc[Sessions] and xref:backend/vapor/redis-and-caching.adoc[Redis and caching].

|HTTP client
|V3: `try req.make(Client.self).get(url)`.
|`req.client.get(url)`. See xref:backend/vapor/http-client.adoc[HTTP client].
|===

=== Concurrency: from futures to async/await

Vapor 3 had its own `Future<T>` type with `map(to:)` labels and global `flatMap` helpers. Vapor 4.0 dropped it and
exposed SwiftNIO's `EventLoopFuture` directly (`map`, `flatMap`, `flatMapThrowing`, `and`, `makePromise(of:)`). Vapor
4.50.0 (2021-10-26) added `async`/`await` APIs, and since then the recommended handler is an `async throws` function
that returns its value.

[cols="1,3",options="header"]
|===
|Era |What to expect in code and in books
|Vapor 3 |`Future<Response>`, `+req.content.decode(User.self).flatMap { ... }+`, `+req.parameters.next(...)+`, `wait()` in tests.
|Vapor 4.0 to 4.49 |`EventLoopFuture<Response>` return types; synchronous `req.content.decode`; `app.autoMigrate().wait()` in `configure`.
|Vapor 4.50 and later |`async throws` handlers, `AsyncMiddleware`, `AsyncMigration`, `AsyncCommand`, `AsyncJob`, `AsyncBasicAuthenticator`; futures bridged with `.get()`.
|Vapor 4.99 to 4.122 |`Sendable` everywhere: `Application` and `Request` are `Sendable`, route closures are `@Sendable`, storage values must be `Sendable`, models are `+final class ...: Model, @unchecked Sendable+`.
|Vapor 5 beta |No `EventLoopFuture` API at all; structured concurrency throughout. See <<_vapor_5_beta_4>>.
|===

The legacy operators, the bridges and the Swift 6 rules are on xref:backend/vapor/swift-concurrency-in-vapor.adoc[Swift
concurrency in Vapor]. The future-returning handler of a book still compiles in 4.122.2, which is why a half-upgraded
project can build and still be wrong about `Sendable`.

=== Fluent, migrations, Leaf and authentication

[cols="2,4,5",options="header"]
|===
|Area |Vapor 2 and 3 (the books) |Vapor 4.122.2 (this section)

|Models
|V2: `Model` with `Node`, `Entity`, `Row` and `Preparation`. V3: `PostgreSQLModel`, `SQLiteModel` or `MySQLModel` structs with `var id: Int?`, `static let entity` and `Migration` conformance on the model; the `Parameter` protocol.
|`final class Book: Model, @unchecked Sendable` with `static let schema`, `@ID(key: .id)` (the template now writes `@ID`), `@Field(key:)`, `@Timestamp(key:on:)`, an empty `init()`, and key paths like `+\.$title+`. See xref:backend/vapor/fluent-models.adoc[Fluent models].

|Relations
|V3: computed `+parent(\.authorID)+`, `+children(\.authorID)+`, `siblings()`.
|`@Parent`, `@Children(for:)`, `@Siblings(through:from:to:)`, `@OptionalChild`, pivots as ordinary models, `+with(\.$author)+` for eager loading. See xref:backend/vapor/fluent-relations.adoc[Fluent relations].

|Migrations
|V3: `+extension Todo: Migration {}+` with reflection-based auto migration, `static func prepare(on conn:)`, `Database.create(Todo.self, on: conn)` and `MigrationConfig`.
|A separate `AsyncMigration` value with `prepare(on:)` and `revert(on:)`, `+database.schema("books")...create()+`, registered with `app.migrations.add` and run by the `migrate` command or `try await app.autoMigrate()`. See xref:backend/vapor/migrations-and-schema.adoc[Migrations and schema].

|Database configuration
|V3: `DatabasesConfig`, `FluentPostgreSQLProvider`, `services.register`.
|`+app.databases.use(.postgres(configuration: SQLPostgresConfiguration(...)), as: .psql)+` with explicit TLS. There is no provider registration step.

|Queries and raw SQL
|V3: `Planet.query(on: req)`, `+filter(\.foo == x)+`, `withPooledConnection`, `deletedAtKey`, `alsoDecode`.
|`Planet.query(on: req.db)`, `+filter(\.$foo == x)+`, `@Timestamp(on: .delete)` soft delete, `paginate`, SQLKit for raw SQL with bound interpolation. See xref:backend/vapor/fluent-queries-and-pagination.adoc[Fluent queries and pagination] and xref:backend/vapor/sql-kit-and-raw-sql.adoc[SQLKit and raw SQL].

|Leaf
|Leaf 2 and 3: `+#embed+`, `+#set+` and `+#get+`, `+#loop+`, brace blocks, `LeafProvider`, `req.make(LeafRenderer.self)`.
|Leaf 4: `+#extend+`, `+#export+` and `+#import+`, `+#if(...):+` with `+#endif+`, `+#for(...):+` with `+#endfor+`, `app.views.use(.leaf)`, `req.view.render`. See xref:backend/vapor/leaf-templates.adoc[Leaf templates].

|Authentication
|V2: `auth-provider`. V3: `vapor/auth` with `PasswordAuthenticatable`, `TokenAuthenticatable`, `BCryptDigest`, `AuthenticationSessionsMiddleware`, `PersistMiddleware`.
|Built in: `Authenticatable`, `AsyncBasicAuthenticator`, `AsyncBearerAuthenticator`, `ModelAuthenticatable`, `ModelTokenAuthenticatable`, `ModelSessionAuthenticatable`, `req.auth`, `app.passwords`, `Bcrypt`. JWT 5 (`app.jwt.keys`, `req.jwt.verify`) is covered by none of the books. See xref:backend/vapor/authentication.adoc[Authentication] and xref:backend/vapor/jwt.adoc[JWT].

|OAuth and email
|Imperial 0.7 (Vapor 3); the Vapor 3 SendGrid provider.
|Imperial 2.x; `sendgrid-kit`, Mailgun 6 or an SMTP package; Sign in with Apple through `req.jwt.apple`. See xref:backend/vapor/oauth-and-sign-in-with-apple.adoc[OAuth and Sign in with Apple].
|===

Repositories deserve a note, because the pattern is in the official upgrade guide and in the books. In Vapor 3 a
repository was a `final class` registered as a `ServiceType`. In Vapor 4 it is a protocol, a `struct` that takes the
database, a factory stored in `app.storage` and an accessor on `Request`; with `async`/`await` the protocol methods are
`async throws`. xref:backend/vapor/services-storage-and-dependency-injection.adoc[Services, Storage and Dependency
Injection] builds it step by step.

=== Testing

[cols="2,4,5",options="header"]
|===
|Era |Tool |Shape
|Vapor 2 and 3 |XCTest with `Droplet.testable()` or a hand-built `Request(http:using:)` and `wait()` |Futures and explicit event-loop handling.
|Vapor 4.0 to 4.109 |XCTVapor, `+app.test(.GET, "path") { res in ... }+` |Synchronous test method; `XCTAssertEqual`.

The test below compiles and passes against 4.122.2. It is the whole test of the `books` route used in this page's
scratch package:

[source,swift]
----
import Testing
import VaporTesting

@testable import App

@Suite struct AppTests {
    @Test func listBooks() async throws {
        try await withApp(configure: configure) { app in
            try await app.testing().test(.GET, "books") { res async throws in
                #expect(res.status == .ok)
                let books = try res.content.decode([BookDTO].self)
                #expect(books.first?.title == "Swift for Servers")
            }
        }
    }
}
----

Source: https://docs.vapor.codes/advanced/testing/[Vapor docs: Testing] and
https://github.com/vapor/vapor/releases/tag/4.110.0[vapor/vapor release 4.110.0]

`XCTVapor` still works, with one change from the books' examples. Calling the synchronous `+app.test(...)+` from an
`async` test method is a compile error in 4.122.2
(`+instance method 'test' is unavailable from asynchronous contexts; Use the async method instead+`), so the XCTest form
is `+try await app.test(.GET, "books/7") { res async in ... }+`. Vapor 5's `VaporTesting` has new APIs again (see
below). xref:backend/vapor/testing.adoc[Testing] covers the details.

The 4.x handlers and the controller the tests exercise are below. The `list` and `show` handlers are the current form;
`legacyList` is the `EventLoopFuture` shape of the books, which still compiles in 4.122.2 and is shown only so that you
can recognise it.

[source,swift]
----
import Vapor

struct BookDTO: Content {
    var id: Int
    var title: String
}

struct BookController: RouteCollection {
    func boot(routes: any RoutesBuilder) throws {
        let books = routes.grouped("books")
        books.get(use: list)
        books.get(":bookID", use: show)
        books.get("legacy", use: legacyList)
    }

    @Sendable
    func list(req: Request) async throws -> [BookDTO] {
        [BookDTO(id: 1, title: "Swift for Servers")]
    }

    @Sendable
    func show(req: Request) async throws -> BookDTO {
        let id = try req.parameters.require("bookID", as: Int.self)
        return BookDTO(id: id, title: "Book \(id)")
    }

    // Legacy shape: still compiles in 4.122.2, returns an EventLoopFuture.
    @Sendable
    func legacyList(req: Request) -> EventLoopFuture<[BookDTO]> {
        req.eventLoop.makeSucceededFuture([BookDTO(id: 1, title: "Swift for Servers")])
    }
}

func routes(_ app: Application) throws {
    app.get("hello") { _ async in "Hello, Vapor 4" }
    try app.register(collection: BookController())
}
----

Source: https://docs.vapor.codes/basics/controllers/[Vapor docs: Controllers]

$ curl -s localhost:8088/books/legacy

== Notable 4.x releases

The table lists the releases that changed how an application is written, with the dates and the change as stated in the
GitHub release notes. The full history is in the https://github.com/vapor/vapor/releases[release list]; exact release
numbers for several earlier changes (for example the first `Sendable` conformances) are in the blog post _Upcoming
Sendable changes_ rather than in one release.

[cols="1,1,5",options="header"]
|===
|Release |Date |Change for application code
|4.0.0 |2020-04-09 |The rewrite: services on `Application` and `Request`, SwiftNIO types exposed directly, Fluent 4 with property wrappers.
|4.50.0 |2021-10-26 |`async`/`await` APIs for `Client`, routes, `ResponseEncodable`, `Middleware` (`AsyncMiddleware`), password hashing, `Cache` and views.
|4.89.0 |2023-12-06 |Fully async entrypoints: use `execute()` instead of `run()` and `startup()` instead of `start()`.
|4.99.0 |2024-05-10 |`asyncShutdown()`; the synchronous `shutdown()` becomes `noasync`.
|4.100.0 |2024-05-15 |Async `LifecycleHandler` methods, needed by packages such as Redis whose shutdown used to call `wait()`.
|4.110.0 |2024-12-21 |The `VaporTesting` module for Swift Testing, with `app.testing()`.
|4.113.0 |2025-02-10 |`Application.init` deprecated in favour of the `async` `Application.make`.
|4.116.0 |2025-09-09 |`Application.make` accepts a `Logger`.
|4.121.0 |2026-01-05 |`RouteNotFound`, the error thrown when no route matches, is public, so a middleware can handle 404s for every method.
|4.122.0 |2026-07-01 |`idleTimeout` on `HTTPServer.Configuration` (not in the official documentation yet).
|4.122.1 |2026-08-25 |Fix for multiple response-stream callbacks.
|4.122.2 |2026-09-17 |Sends `Accept-Ranges` instead of `Accept` on file responses.
|===

Swift 6 adoption in Vapor 4 happened in steps rather than in one release: a large `Sendable` annotation effort in 2023
(using locks inside `Application` and `Request`), async streaming bodies for requests and responses, and by 2026 a
package that builds with strict concurrency and no warnings in the Swift 6 language mode. The template of the 4.121 line
enables the upcoming features `ExistentialAny`, `InternalImportsByDefault`, `MemberImportVisibility`,
`InferIsolatedConformances` and `ImmutableWeakCaptures`. Two practical consequences for code copied from older material:
route closures and handler methods should be `@Sendable` when the enclosing type could gain non-`Sendable` state, and a
value stored under a `StorageKey` must be `Sendable`.

== 4.122.2 behaviour that differs from the documentation

Verifying this section against the source of 4.122.2 and the libraries it resolves turned up statements in the official
documentation that no longer match the code, and a few defects. They are collected here with the page that proves each
one. A row is a statement about the checked version, not a documented guarantee: re-test when you upgrade.

[cols="3,4,4,2",options="header"]
|===
|Topic |What the documentation (or an older article) says |What 4.122.2 and its libraries do |Page

|Request decompression
|The server configuration page says the default is `.disabled` with `.ratio(10)`.
|The initializer in the source defaults to `.enabled` with `.ratio(25)`.
|xref:backend/vapor/server-configuration.adoc[Server configuration]

|Idle timeout
|Not documented.
|`HTTPServer.Configuration.idleTimeout` exists since 4.122.0 (pull request 3473).
|xref:backend/vapor/server-configuration.adoc[Server configuration]

|Session cookie name
|The sessions page says the default cookie is `vapor_session`.
|The source sets `vapor-session` with a hyphen. Do not hard-code either spelling in a client.

== Vapor 5 beta.4

Vapor 5 is a major overhaul of Vapor's internals. The summary below is what the `5.0.0-beta.4` tag contains; it was
compiled and run, but the APIs are explicitly not frozen. The release notes from the alphas to beta.4 are the best
change log there is.

=== What changes for application code

Everything in the "Vapor 5 beta.4" column was read from the sources of the tag. "Removed" means that the file or the
public API is not in the tree of `5.0.0-beta.4`; it may come back in another form.

[cols="2,4,5",options="header"]
|===
|Area |Vapor 4.122.2 |Vapor 5.0.0-beta.4

|Server
|Vapor's own NIO pipeline, `app.http.server.configuration` (`HTTPServer.Configuration`), `serve` flags `-H`, `-p`, `-b`.
|`swift-http-server`; `app.serverConfiguration` is a `ServerConfiguration` (`address`, `tlsConfiguration`, `httpVersions` that defaults to HTTP/1.1 only, `eTagHashCacheCapacity`, `maxDrainBytes` of 16 KB). HTTP/2 needs TLS. mTLS and certificate reloading are in. The configuration is frozen once the application starts.

|Application
|`Application.make(env)` (async), `execute()`, `asyncShutdown()`; `Application` is a `Sendable` class holding its services in `app.storage`.
|`try Application(configReader:)` is a throwing synchronous initializer on a `final class Application: Sendable, Service`. `run()` runs it as a service without signal handling, so that you can place it in your own `ServiceGroup`; `start()` runs it with SIGTERM and SIGINT handlers; `shutdown()` is `async throws` and not calling it before `deinit` trips an assertion. There is a `state` property.

|Services
|Extensions on `Application`, `app.storage` with `StorageKey`, `app.locks`, `+app.lifecycle.use(...)+`, `app.clients.use`, `app.caches.use`, `app.views.use`, `app.sessions.use`.
|The view renderer, cache, responder, server, client and session driver are chosen once, through `Application.ServiceConfiguration` passed to `init`. Extra services are added with `+addService(_:)+` (any `ServiceLifecycle.Service`) and `+addLifecycleHandler(_:)+`. `StorageKey`, `app.storage` and `app.locks` are not in the tree.

|Configuration
|`Environment.get`, `.env` files (`DotEnv`), `Environment.secret`, `--env` and `VAPOR_ENV`.
|`swift-configuration`: `Environment.detect(from:)` reads the `vapor.env` key of a `ConfigReader` whose default providers are the command-line arguments and the process environment. The address keys are `hostname`, `port`, `bind` (`"hostname:port"`) and `unix-socket`. `DotEnv`, `Environment+Process` and `Environment+Secret` are gone. How `.env` files and secrets are replaced was not verified.

|Request and response
|`Request` and `Response` are classes with NIO types (`HTTPMethod`, `HTTPHeaders`, `ByteBuffer`) in their public API.
|`Request`, `Response` and `Route` are `Sendable` structs. Method, status and headers use `swift-http-types` (`HTTPRequest.Method`, `HTTPResponse.Status`, `HTTPFields`). `ResponseEncodable` is a single `async throws` protocol. NIO types are not in the public `Response` API.

|Bodies
|Collected by default (`.collect(maxSize:)`, 16 KB), `.stream` per route.
|Streaming by default: `+try await req.body.forEachChunk { ... }+`, a single-consumer body (two tasks reading it at once throw `RequestBodyAlreadyBeingRead`, and collecting what is left after a partial read throws `RequestBodyPartiallyConsumed`), `maxBodySize:` per route, `+Response(body: .init(stream: { writer in ... }))+` with an awaiting writer that gives back-pressure.

|Content
|`try req.content.decode(T.self)`, synchronous.
|`try await req.content.decode(T.self)`; `validate(content:)` becomes `async throws`.

|Middleware
|`AsyncMiddleware.respond(to:chainingTo: any AsyncResponder)`.
|`Middleware: Sendable` with `+respond(to:chainingTo: any Responder) async throws -> Response+`; the `Async` prefix is gone. The default stack is still `RouteLoggingMiddleware` then `ErrorMiddleware`. The `Middlewares` type keeps `use(_:at:)` with `.beginning` and `.end`.

|Routing
|`app.get`, `grouped`, `RouteCollection`, `PathComponent`.
|The same, plus macro routing with the `MacroRouting` trait (below), and router methods for `QUERY`.

|Authentication
|`AsyncBasicAuthenticator`, `AsyncBearerAuthenticator`, `AsyncCredentialsAuthenticator`, `ChallengeMiddleware`.
|Async-only protocols without the prefix; `Authenticatable` refines `Sendable`; basic and bearer authenticators add a `WWW-Authenticate` challenge on a 401. Guard and redirect middleware keep their names. Fluent's `+Model*Authenticatable+` protocols are not part of `vapor`.

|Passwords, OTP and crypto
|`app.passwords`, `req.password`, `Bcrypt`, `OTP.swift` (HOTP, TOTP).
|The `Passwords`, `Bcrypt` and `Security` directories and OTP are not in the tree; `swift-crypto` is still a dependency, and `Base32`, `Base64` and `secureCompare` helpers remain. Where Vapor 5 puts password hashing is unverified: keep hashing behind a small protocol of your own.

|Files
|`req.fileio` with `readFile`, `writeFile`, `collectFile`, `streamFile`; `FileMiddleware(publicDirectory:)`.
|Removed in 5.0.0-beta.1 (pull request 3553): `FileIO` is reached through `app.fileio` and its only public method is `streamFile(at:for:chunkSize:mediaType:advancedETagComparison:onCompleted:)`. Read and write files with Foundation, swift-system or NIOFileSystem. The file middleware is created with `+app.makeFileMiddleware(...)+`.

|Cache, sessions, views
|`Cache` with futures and `for(_:)`; `SessionDriver` with futures; `ViewRenderer` returning a future.
|`Cache` is `Sendable` with two `async throws` requirements (`get` and `set`) and a `MemoryCache` default; the session driver is fixed at `init` (`MemorySessions` by default); `ViewRenderer` has one `async throws` requirement and the default is a `PlaintextRenderer`.

|HTTP client
|`Client` over AsyncHTTPClient with futures and async overloads.
|One requirement, `send(_:) async throws`; a `Duration` timeout (30 seconds default), `maxResponseBodySize` of 10 MB, a body type shared with `Response.Body`.

|Commands, logging, tracing
|ConsoleKit 4 `AsyncCommand`, `LoggingSystem.bootstrap(from:)`.
|ConsoleKit 5 (beta), the `ConsoleLogger` module (`bootstrapWithConfigReader(config:)`), a task-local logger (`withLogger`, `Logger.current`).

|Testing
|`Application.make(.testing)`, `+app.testing().test(...)+`, promises available.
|New `VaporTesting` APIs; the promise type is removed.
|===

=== A Vapor 5 application

The scratch package below builds against `5.0.0-beta.4` with no warnings. The entrypoint is the shape of the
repository's own `Development` target (it has no `Environment.detect()` or `Application.make`), the controller uses the
`@Controller` macro, and the plain route reads the request body as a stream.

`Package.swift`:

[source,swift]
----
// swift-tools-version:6.4
import PackageDescription

let package = Package(
    name: "bookshelf-v5",
    platforms: [.macOS("26.2")],
    dependencies: [
        .package(url: "https://github.com/vapor/vapor.git", exact: "5.0.0-beta.4"),
        .package(url: "https://github.com/apple/swift-configuration.git", from: "1.0.0", traits: ["CommandLineArguments"]),
    ],
    targets: [
        .executableTarget(
            name: "App",
            dependencies: [
                .product(name: "Vapor", package: "vapor"),
                .product(name: "VaporMacros", package: "vapor"),
                .product(name: "Configuration", package: "swift-configuration"),
            ]
        )
    ]
)
----

`entrypoint.swift`:

[source,swift]
----
import Configuration
import ConsoleLogger
import Logging
import Vapor

@main
struct Entrypoint {
    static func main() async throws {
        let config = ConfigReader(providers: [
            CommandLineArgumentsProvider(),
            EnvironmentVariablesProvider(),
        ])
        ConsoleLogger.bootstrapWithConfigReader(config: config)
        let logger = Logger(label: "codes.vapor.bookshelf")
        try await withLogger(logger) { _ in
            let app = try Application(configReader: config)
            do {
                try await configure(app)
                try await app.run()
                try await app.shutdown()
            } catch {
                try? await app.shutdown()
                throw error
            }
        }
    }
}
----

`configure.swift`:

[source,swift]
----
import Vapor

func configure(_ app: Application) async throws {
    app.serverConfiguration.address = .hostname("127.0.0.1", port: 8089)
    try await routes(app)
}
----

`routes.swift`:

[source,swift]
----
import HTTPTypes
import Vapor
import VaporMacros

struct BookDTO: Content {
    var id: Int
    var title: String
}

@Controller
struct BookController {
    @GET("books")
    func list(req: Request) async throws -> [BookDTO] {
        [BookDTO(id: 1, title: "Swift for Servers")]
    }

    @GET("books", Int.self)
    func show(req: Request, bookID: Int) async throws -> BookDTO {
        BookDTO(id: bookID, title: "Book \(bookID)")
    }
}

func routes(_ app: Application) async throws {
    app.get("hello") { _ in "Hello, Vapor 5" }

    app.on(.post, "echo") { req -> String in
        var total = 0
        try await req.body.forEachChunk { chunk in
            total += chunk.count
        }
        return "received \(total) bytes"
    }

    try await app.register(collection: BookController())
}
----

Sources/Development] (the entrypoint, the route registration and the macro controller are adapted from it)

== Migration advice

Moving within Vapor 4:

. Move the entrypoint to `Application.make`, `execute()` and `asyncShutdown()`, and remove `Application(env)`, `run()`
  and `shutdown()` (4.113 deprecation).
. Convert handlers, middleware, migrations and commands to their `async` protocols; keep `EventLoopFuture` only inside
  third-party code, bridged with `.get()`.
. Turn on the Swift 6 language mode with `swift-tools-version:6.3` and fix `Sendable` problems at the source:
  `@unchecked Sendable` on Fluent models, `Sendable` storage values, `@Sendable` handlers.
. Replace XCTest with `VaporTesting` and Swift Testing (4.110), using `withApp` so that `asyncShutdown()` always runs.
. Move `.sql(raw:)` and `+\(raw:)+` to `unsafeRaw:` and read the other deprecation warnings that a Swift 6.4 build
  prints.

Preparing for Vapor 5 without waiting for it:

. Keep the application's own code behind small protocols: a configuration type (`AppConfig`) that is the only reader of
  `Environment`, a password hasher, a file store, and repositories over Fluent. These are the parts that Vapor 5 changes
  or removes.
. Return DTOs, not Fluent models, and keep `Content` types independent of `Request`.
. Write streaming code with `async` bodies (`req.body`, `Response.Body(managedAsyncStream:)`) rather than collecting
  everything.
. Do not depend on `app.storage`, `app.locks`, `Environment.get`, `req.fileio.writeFile`, `.env` files or OTP in code
  you expect to carry over.
. Try the beta in a branch with a throwaway service to learn the new application shape, and re-run it on every beta.

Moving to Vapor 5, once it is released and the packages you use have Vapor 5 releases: read the
https://docs.vapor.codes/upgrading/[official upgrade guide] (it covers only Vapor 3 to 4 today) and the release notes of
5.0.0, rewrite the entrypoint and `configure` around `ConfigReader`, pass the services in `ServiceConfiguration`, change
`AsyncMiddleware` conformances to `Middleware`, `await` content decoding and validation, replace NIO types by
swift-http-types and Foundation types, and register routes with the macros if you want type-safe parameters.

All three books are outdated: Patel (2018) is written for Vapor 2, Yeung (2018) for Vapor 3.0 and Swift 4.2, and the
Kodeco book of Condon and others is the early-access build whose chapters 1 to 13 use Vapor 4.0 on Swift 5.2 and whose
chapters 14 to 36 still show Vapor 3. The books are consulted references for concepts and narrative; no text, code or
figure is copied from them, and none of their code compiles against Vapor 4.122 as printed. Their ISBNs, publishers and
companion repositories are in xref:backend/vapor/index.adoc#_bibliography[the section bibliography].

=== Errata and bad practices not to reproduce

The books contain code that is wrong or unsafe independently of their age. This section's pages do not reproduce it, and
say the correct form where the topic comes up.

[cols="2,4,5",options="header"]
|===
|Category |What the books do |The correct form here

|Secrets and credentials
|Hard-coded fallback database credentials such as `?? "vapor_password"` (Condon ch. 6, 11; Yeung ch. 8); a seeded admin with the password "password" (Condon ch. 18); bcrypt hashes published for seeding (Yeung ch. 9); OAuth secrets set on the command line (Condon ch. 31); default `crypto.json` keys (Patel ch. 3 and 4).
|Read secrets from the environment and fail fast in production; create the admin with a command that takes the password from the operator's environment and hashes it at run time. See xref:backend/vapor/configuration-and-environment.adoc[Configuration and environment].

|TLS
|`certificateVerification: .none` for MySQL (Condon ch. 6); global ATS "Allow Arbitrary Loads" (Patel ch. 6, Yeung ch. 13); service-to-service credentials over plain HTTP (Condon ch. 36).
|Keep certificate verification on (turn it off only for a local container, never through a downgraded URL); narrow ATS exceptions in Debug builds; TLS between services you do not run on a trusted network. See xref:backend/vapor/server-configuration.adoc[Server configuration] and xref:backend/vapor/http-client.adoc[HTTP client].

|Tokens and passwords
|Bearer and password-reset tokens stored in plaintext with no expiry (Condon ch. 18, 24, 35; Patel ch. 10); SHA-256 password hashing shown before bcrypt (Patel ch. 10); a `Content`-conforming user model leaking the hash to JSON and templates (Yeung ch. 9); tokens in `UserDefaults` (Condon ch. 19, Patel ch. 10).
|Store a digest of the token with an expiry; use `req.password`; return a public DTO; use the Keychain. See xref:backend/vapor/fluent-authentication-and-tokens.adoc[Fluent authentication and tokens] and xref:backend/vapor/passwords-and-crypto.adoc[Passwords and crypto].

|Authorization
|A profile-picture upload taking the user ID from the URL with no ownership check and no size or type validation (Condon ch. 25); an unauthenticated admin API (Yeung ch. 11); an unauthenticated `DELETE` that wipes a table (Patel ch. 5); a shared-secret header compared with `==` (Condon ch. 28).
|Derive the owner from the authenticated user; guard every admin route; compare secrets with `secureCompare` or an HMAC. See xref:backend/vapor/authorization.adoc[Authorization].

|Web security
|Forms without CSRF protection, or with a token on only one form (Condon ch. 16, 20; Yeung ch. 9; Patel ch. 7); logout and deletes over `GET` (Yeung ch. 6, 9; Patel ch. 10); validation messages reflected through the query string (Condon ch. 21); a template name taken from the URL (Patel ch. 7); a static file server allowing path traversal (Patel ch. 3).
|A CSRF token, `SameSite` and an origin check on every cookie-authenticated form; `POST` for state changes; messages kept in the session; templates chosen in code. See xref:backend/vapor/security-hardening.adoc[Security hardening] and xref:backend/vapor/server-rendered-web-apps-and-forms.adoc[Server-rendered web apps and forms].

|Concurrency
|A mutable in-memory array in a controller shared across event loops (Yeung ch. 5); a global mutable WebSocket registry (Condon ch. 29); `autoMigrate().wait()` on an event loop (Condon ch. 5).
|An actor for shared state; `try await app.autoMigrate()`. See xref:backend/vapor/swift-concurrency-in-vapor.adoc[Swift concurrency in Vapor] and xref:backend/vapor/websockets.adoc[WebSockets].

|HTTP semantics
|400 for not found and 200 for creation (Yeung ch. 5, 11; Patel ch. 5); "HTTP UPDATE" (Yeung ch. 5); N+1 queries in serialisation (Patel ch. 5); no cascade on parent delete (Patel ch. 5).
|404 for a missing record, 201 with `Location` for creation, 204 for a successful delete; eager loading with `with`; `onDelete: .cascade`. See xref:backend/vapor/error-handling.adoc[Error handling].

|Operations
|`sudo su -` and `wget \| apt-key add` (Condon ch. 33); `pass:c[sudo chmod -R a+rx /usr/]` in CI (Patel ch. 8); MongoDB with access control disabled (Patel ch. 4).
|A non-root service user, signed repositories, least privilege in CI, and authentication enabled on every database. See xref:backend/vapor/deployment-with-docker.adoc[Deployment with Docker].

|Typos and broken code
|`hotname:`, extra parentheses and wrong module names (Yeung ch. 8); a stored property in an extension and non-public package API (Patel ch. 1, 4); `+#if TARGET_OS_IOS+`, always false in Swift (Patel ch. 11); a "ttps://" source-code link and the word "releational" (Condon).
|Compiling examples; `+#if os(iOS)+`.

== Common errors when upgrading

[cols="2,3",options="header"]
|===
|Symptom |Cause and fix
|`+'init(_:_:)' is deprecated: Migrate to using the async APIs+` |`Application(env)` in an entrypoint copied from a book or the upgrade guide. Use `try await Application.make(env)`.
|`+instance method 'test' is unavailable from asynchronous contexts+` |The synchronous XCTVapor `app.test` called in an `async` test. Use `+try await app.test(...)+` or VaporTesting.
|`+.unknownCommand("boot", ...)+` |There is no `boot` command in 4.122.2. Use `routes` or a custom command (see xref:backend/vapor/commands.adoc[Commands]).
|Warnings about `Sendable` after switching to tools 6.3 |Models without `@unchecked Sendable`, a non-`Sendable` value under a `StorageKey`, a non-`@Sendable` closure that captures `req`. Fix them; do not switch back to the Swift 5 mode.
|`+expression is 'async' but is not marked with 'await'+` on `app.register(collection:)` |Vapor 5 beta only: registration is `async` there.
|Package resolution fails for `5.0.0-beta.4` |The beta needs tools 6.4 and 26.2 Apple platforms, and dependencies that are themselves prereleases; pin `exact:` and build with a Swift 6.4 toolchain.
|A Fluent or Leaf package will not resolve next to Vapor 5 |Those packages still depend on Vapor 4; see <<_ecosystem_readiness>>.
|===
