== Two jobs: serving files and doing file I/O

Vapor touches the file system in two different ways, and they use different APIs:

[cols="2,3,3",options="header"]
|===
|Job |API |Typical use
|Serve files that ship with the application unchanged |`FileMiddleware` and the `Public/` directory |CSS, JavaScript, images, fonts, a single-page application build, `robots.txt`
|Read or write files from inside a route handler |`req.fileio` (`FileIO`) |Download endpoints, generated exports, reading a template or a data file, saving a small upload
|Find the right directory |`app.directory` (`DirectoryConfiguration`) |Locate `Public/`, `Resources/` and the working directory regardless of how the process was started
|===

Both are built on SwiftNIO's non-blocking file I/O: reads and writes run off the event loop on a thread pool, so a slow
disk does not stall unrelated requests. The Vapor 4.122 implementation uses `NIOFileSystem` (the underscored
`_NIOFileSystem` module) for the asynchronous API, which is why the API is `async` and the older future-returning
methods are deprecated.

== The working directory and app.directory

`app.directory` is a `DirectoryConfiguration`. Created by `DirectoryConfiguration.detect()` when the application starts,
it takes the process's *current working directory* (`getcwd`) and derives the others from it:

[cols="2,3,3",options="header"]
|===
|Property |Value (working directory `/app`) |Used by
|`workingDirectory` |`/app/` (a trailing slash is always added) |everything else
|`publicDirectory` |`/app/Public/` |`FileMiddleware` when you pass it explicitly
|`resourcesDirectory` |`/app/Resources/` |your own data files, templates
|`viewsDirectory` |`/app/Resources/Views/` |Leaf (see the Leaf page of this section)
|===

All four are plain `String` values that end in `/`, and all are `var`, so they can be changed in `configure`:

[source,swift]
----
app.directory = DirectoryConfiguration(workingDirectory: "/srv/bookshelf")
// or change one directory only
app.directory.publicDirectory = "/srv/bookshelf/static/"
----

The detail that causes most of the "works in Xcode, not in production" reports: the directories are computed from where
the process was *started*, not from where the executable lives. `swift run` and `.build/debug/App serve` started in the
package root find `Public/` next to `Package.swift`. Xcode starts the app in `DerivedData`, so the scheme needs a custom
working directory (Edit Scheme, Run, Options, "Use custom working directory"); Vapor logs a warning when it detects the
`DerivedData` path under Xcode. A systemd unit needs `WorkingDirectory=`, and a container needs `WORKDIR` (or the
files copied next to the executable, as shown in the Docker section and in
xref:backend/vapor/deployment-with-docker.adoc[Deployment with Docker]). Resources bundled with SwiftPM
(`+resources: [.process(...)]+`) live in a `<package>_<target>.resources` bundle next to the executable and are read
with `Bundle.module`, not through `app.directory`. A writable data directory for `req.fileio` belongs in configuration;
see xref:backend/vapor/configuration-and-environment.adoc[Configuration and Environment].

== FileMiddleware and the Public directory

`FileMiddleware` is an `AsyncMiddleware` that maps the request path onto a file below a *public directory* and, when the
file exists, answers with the file instead of calling the rest of the chain. The official template does *not* register
it (an API service has nothing to serve); you add it in `configure` when the service also serves assets.

=== The initializer

[source,swift]
----
// Vapor 4.122.2, signature of the main initializer
public init(
    publicDirectory: String,
    defaultFile: String? = nil,
    directoryAction: DirectoryAction = .none,
    advancedETagComparison: Bool = false,
    cachePolicy: CachePolicy = .browserDefault
)
----

[cols="2,5",options="header"]
|===
|Parameter |Meaning
|`publicDirectory` |The directory files are served from. A trailing slash is added if missing. Pass `app.directory.publicDirectory`; a relative path is resolved from the working directory
|`defaultFile` |File served when the request is for a directory (a URL ending in `/`). `"index.html"` is relative to that directory, so `/docs/` serves `Public/docs/index.html`. A value starting with `/` (`"/index.html"`) is absolute from the root of the public directory, which makes every directory URL serve the same file. `nil` (the default) serves no default file
|`directoryAction` |What to do when the URL names a directory but has *no* trailing slash. `.none` (default) passes the request on; `.redirect` answers `301 Moved Permanently` with the same URL plus `/`
|`advancedETagComparison` |`false` (default): the `ETag` is built from the file's modification time and size. `true`: the `ETag` is the SHA-256 of the file's content, cached per path and recomputed when the modification time changes. Needed when the same content has different timestamps on several servers
|`cachePolicy` |A `FileMiddleware.CachePolicy` applied to every response the middleware produces (see below)
|===

There is also a `+init(bundle:publicDirectory:defaultFile:directoryAction:cachePolicy:)+` that serves a `Public` folder
copied into an app bundle, for servers embedded in an Xcode project; it throws `BundleSetupError` when the bundle has no
resource URL or no such folder.

=== What happens to a request

image::vapor-static-files-and-file-io-filemiddleware-decision.svg["Decision flow of FileMiddleware: reject bad paths, stream files, apply defaultFile and directoryAction, otherwise call the next responder",width=900]

The steps in `respond(to:chainingTo:)` (Vapor 4.122.2, `Sources/Vapor/Middleware/FileMiddleware.swift`) are:

. The path is percent-decoded. Invalid encoding throws `Abort(.badRequest)`.
. Leading slashes are removed, and a path that contains `../` throws `Abort(.forbidden)`. Because decoding happens
  first, `..%2f` and `%2e%2e/` are caught too (verified below).
. The absolute path is `publicDirectory` plus the request path. If nothing exists there, the request goes to
  `next.respond`, so a missing file is not a 404 from the middleware: the router gets the chance to handle it, and
  an unknown route yields the normal not-found error.
. If it is a regular file, it is streamed with `req.fileio.asyncStreamFile`, whatever the HTTP method, and the
  cache policy is applied.
. If it is a directory and the URL ends in `/`, the `defaultFile` (if any) is streamed when it exists.
. If it is a directory and the URL has no trailing slash, `.redirect` answers `301`; otherwise the request goes to the
  next responder.

Two consequences follow from step 3. A file under `Public/` *shadows* a route with the same path, since the middleware
runs before the router. And `FileMiddleware` is a GET-style server only in practice: nothing in it checks the method, so
`HEAD`, `POST` and the rest are answered with the file too. Put method-specific rules in an outer middleware if the
distinction matters.

=== Registering it

[source,swift]
----
import Vapor

func configure(_ app: Application) async throws {
    // L1: serve Public/ with defaults
    app.middleware.use(ImmutableAssetsMiddleware(prefix: "/assets/"))
    app.middleware.use(FileMiddleware(
        publicDirectory: app.directory.publicDirectory,
        defaultFile: "index.html",
        directoryAction: .redirect,
        advancedETagComparison: false,
        cachePolicy: .cacheUpToDuration(.minutes(5))
    ))
    app.middleware.use(SPAFallbackMiddleware(publicDirectory: app.directory.publicDirectory))
    try routes(app)
}
----

Source: https://docs.vapor.codes/advanced/middleware/[Vapor docs: Middleware, FileMiddleware]

The registration order matters (the first middleware registered is the outermost one):
`ImmutableAssetsMiddleware` wraps the file middleware so it can adjust the response on the way out, and
`SPAFallbackMiddleware` sits inside it so it only sees requests no file satisfied. Both are shown in the next sections.
`RouteLoggingMiddleware` and `ErrorMiddleware` are already registered ahead of all three by default.

Result of calling the service with `Public/` containing `index.html`, `docs/index.html` and
`assets/app.3f9a1c.js`:

[source,bash]
----
$ curl -I localhost:8080/
HTTP/1.1 200 OK
last-modified: Sat, 17 Oct 2026 14:43:23 GMT
etag: "1792248203-19"
accept-ranges: bytes
content-type: text/html; charset=utf-8
content-length: 19
cache-control: max-age=300
age: 0

$ curl -I localhost:8080/docs
HTTP/1.1 301 Moved Permanently
location: /docs/

$ curl -I localhost:8080/docs/
HTTP/1.1 200 OK
content-type: text/html; charset=utf-8

----

The `Content-Type` comes from the file extension (`HTTPMediaType.fileExtension(_:)`); an unknown extension gets no
`Content-Type`, and an extension-less file is served without one. Pass `mediaType:` to `asyncStreamFile` when you stream
such a file from a handler.

=== Conditional and range requests

Because the middleware delegates to `asyncStreamFile`, every file response is conditional and resumable:

* `ETag` is sent with `Last-Modified`. When the request carries an identical `If-None-Match`, the answer is `304 Not
  Modified` with the `ETag` and a `Content-Length` equal to the file's, and no body. Only `If-None-Match` is compared;
  `If-Modified-Since` is ignored.
* `Accept-Ranges: bytes` is advertised. A single `+Range: bytes=...+` request is answered with `206 Partial Content` and
  a `Content-Range`; a multi-range request is answered with the whole file.
* A range that cannot be satisfied, or a `Range` header that cannot be parsed, is answered with `400 Bad Request`
  (Vapor throws `Abort(.badRequest)`), not with the `416 Range Not Satisfiable` that RFC 9110 prescribes.

[source,bash]
----
$ curl -s -i -H 'Range: bytes=0-3' localhost:8080/index.html
HTTP/1.1 206 Partial Content
etag: "1792248203-19"
accept-ranges: bytes
content-range: bytes 0-3/19
content-type: text/html; charset=utf-8
content-length: 4

<h1>

$ curl -s -i -H 'If-None-Match: "1792248203-19"' localhost:8080/index.html
HTTP/1.1 304 Not Modified
etag: "1792248203-19"
cache-control: max-age=300

$ curl -s -i -H 'Range: bytes=99-120' localhost:8080/index.html
HTTP/1.1 400 Bad Request
----

The default `ETag` is `"<modification time in seconds>-<size>"`. It is cheap (one `stat`), but it changes whenever a
deployment rewrites the file even with identical bytes, and it differs between servers behind a load balancer if the
files were copied at different times. `advancedETagComparison: true` reads each file once and caches the SHA-256 in
`app.storage`, keyed by path and invalidated by the modification time; it costs memory proportional to the number of
distinct files and a full read of each file the first time it is requested.

=== Caching headers

`FileMiddleware.CachePolicy` controls the `Cache-Control` and `Age` headers of every file the middleware serves:

[cols="3,5",options="header"]
|===
|Policy |Effect
|`.browserDefault` (default) |No `Cache-Control`. Browsers cache heuristically, based on `Last-Modified`, and revalidate with the `ETag`; you do not control when
|`.noCache` |`Cache-Control: no-cache`: the browser may store the file but must revalidate before every use. Good in development
|`.cacheUpToDuration(.minutes(5))` |`Cache-Control: max-age=300` and `Age: 0`
|`.custom(cacheControlHeader:ageHeader:)` |Any `HTTPHeaders.CacheControl` value and an optional `Age`
|===

One policy applies to *all* files, which is rarely what a real front end needs. HTML entry points should be revalidated
on every load (so a deployment is visible immediately), while build output whose file name contains a content hash
(`app.3f9a1c.js`) can be cached for a year and marked `immutable`. The reliable pattern is a small outer middleware that
rewrites the header for the fingerprinted prefix, as in the first listing below; because the headers are already set
when the response comes back, assigning `cacheControl` replaces the policy value.

[source,swift]
----
import Vapor

/// Marks fingerprinted build output (for example /assets/app.3f9a1c.js) as cacheable for a year.
/// Registered before FileMiddleware so it sees the response on the way out.
struct ImmutableAssetsMiddleware: AsyncMiddleware {
    let prefix: String

    func respond(to request: Request, chainingTo next: any AsyncResponder) async throws -> Response {
        let response = try await next.respond(to: request)
        if request.url.path.hasPrefix(prefix), response.status == .ok {
            response.headers.cacheControl = .init(isPublic: true, immutable: true, maxAge: 31_536_000)
        }
        return response
    }
}

/// Serves index.html for unknown browser navigations so client-side routing works.
/// Registered after FileMiddleware, so real files win.
struct SPAFallbackMiddleware: AsyncMiddleware {
    let publicDirectory: String

    func respond(to request: Request, chainingTo next: any AsyncResponder) async throws -> Response {
        do {
            return try await next.respond(to: request)
        } catch let error as any AbortError where error.status == .notFound {
            let path = request.url.path
            let wantsHTML = request.headers[.accept].contains { $0.contains("text/html") }
            let hasExtension = path.split(separator: "/").last?.contains(".") ?? false
            guard request.method == .GET, wantsHTML, !hasExtension, !path.hasPrefix("/api/") else { throw error }
            return try await request.fileio.asyncStreamFile(at: publicDirectory + "index.html")
        }
    }
}
----

Source: https://api.vapor.codes[Vapor API documentation: FileMiddleware and HTTPHeaders.CacheControl]

The output for the fingerprinted asset (the five-minute policy of the middleware is overridden, and `immutable` is
honoured by browsers that implement it; Firefox only on HTTPS):

[source,bash]
----
$ curl -I localhost:8080/assets/app.3f9a1c.js
HTTP/1.1 200 OK
etag: "1792248203-15"
accept-ranges: bytes
content-type: application/javascript
content-length: 15
age: 0
cache-control: immutable, public, max-age=31536000
----

Note that `FileMiddleware` leaves an `Age: 0` header behind when a duration policy is used; it is harmless here but
confusing if a CDN in front computes its own `Age`.

=== Serving a single-page application build

A single-page application (a React, Vue or Angular build, or a Swift/WASM front end) is a folder of static files plus
one rule: any URL that is a client-side route must answer with `index.html`. With `FileMiddleware` that is two pieces:

. copy the build output into `Public/` (or point `publicDirectory` at the build folder), with
  `defaultFile: "index.html"` so `/` works;
. add a fallback that serves `index.html` for navigations nothing else answered.

The `SPAFallbackMiddleware` above is that fallback. Its conditions are what keep it from hiding real errors: only `GET`,
only when the client accepts HTML, only for paths whose last component has no file extension (a missing `/app.js` must
stay a 404, not an HTML page that the browser fails to parse as JavaScript), and never under `/api/`. It catches
`any AbortError` with status `.notFound` rather than `Abort`, because since 4.121 the router's miss is the public
`RouteNotFound` type, not an `Abort` (an `as Abort` pattern silently never matches; this was found while testing the
listing).

[source,bash]
----
$ curl -s -i -H 'Accept: text/html' localhost:8080/books/42
HTTP/1.1 200 OK
etag: "1792248203-19"
content-type: text/html; charset=utf-8
content-length: 19

$ curl -s -i -H 'Accept: application/json' localhost:8080/books/42
HTTP/1.1 404 Not Found

$ curl -s -i -H 'Accept: text/html' localhost:8080/api/nope
HTTP/1.1 404 Not Found

$ curl -s -i -H 'Accept: text/html' localhost:8080/x.png
HTTP/1.1 404 Not Found
----

An application mounted at a sub-path (`+/app/...+`) can instead use a catch-all route, `+app.get("app", "**")+`, whose
handler streams `index.html`. The middleware version has the advantage of not interfering with the route table.

=== Not-found responses are not special

When no file, no route and no fallback match, the response is the normal JSON `+{"error":true,"reason":"Not Found"}+`
from `ErrorMiddleware`. A site that serves HTML needs its own error page (the page for an unknown URL included); see the
xref:backend/vapor/error-handling.adoc[Error Handling] page for the rendering hooks, and
xref:backend/vapor/leaf-templates.adoc[Leaf Templates] for the `viewsDirectory` that holds the templates.

== File I/O with req.fileio

`req.fileio` returns a `FileIO` value bound to the request (it holds the application's `NonBlockingFileIO`, the
allocator and the request, whose logger and event loop it uses). It is `Sendable` and cheap to create; you do not
store it. The async methods of Vapor 4.122.2 are:

[cols="3,3,4",options="header"]
|===
|Method |Returns |Notes
|`collectFile(at:)` |`ByteBuffer` |Reads the whole file into memory. Throws `Abort(.internalServerError)` if the file does not exist
|`readFile(at:chunkSize:offset:byteCount:)` |`FileIO.FileChunks`, an `AsyncSequence` of `ByteBuffer` |Reads in chunks (default `NonBlockingFileIO.defaultChunkSize`, 128 KiB), optionally from an offset and for a number of bytes. The handle closes when iteration reaches the end; closing it after an error is the caller's job, with `closeHandle()`
|`writeFile(_:at:)` |`Void` |Writes a `ByteBuffer`, *replacing* an existing file and creating a missing one. The parent directory must exist
|`asyncStreamFile(at:chunkSize:mediaType:advancedETagComparison:onCompleted:)` |`Response` |A streaming response with `ETag`, `Last-Modified`, `Accept-Ranges`, `Content-Type`, range and `304` handling. The same code `FileMiddleware` uses
|===

The `Source:` for the whole table is the official page, which documents the older names:

Source: https://docs.vapor.codes/advanced/files/[Vapor docs: Files]

=== A controller using all four

[source,swift]
----
import Vapor
import NIOCore

func routes(_ app: Application) throws {
    app.get("api", "health") { _ in "ok" }
    try app.register(collection: FileController())
}

struct FileController: RouteCollection {
    func boot(routes: any RoutesBuilder) throws {
        let files = routes.grouped("files")
        files.get("size", ":name", use: size)
        files.get("lines", ":name", use: lineCount)
        files.get("notes", ":name", use: readWhole)
        files.put("notes", ":name", use: write)
        files.get("export", ":name", use: download)
        files.get("report", use: report)
    }

    private func notesPath(_ req: Request) throws -> String {
        guard let name = req.parameters.get("name") else { throw Abort(.badRequest) }
        return try SafePath.resolve(name: name, in: req.application.directory.resourcesDirectory + "notes/")
    }

    /// Same as notesPath, but answers 404 instead of letting FileIO throw a 500 for a missing file.
    private func existingNotesPath(_ req: Request) async throws -> String {
        let path = try notesPath(req)
        let exists = try await req.application.threadPool.runIfActive {
            var isDirectory: ObjCBool = false
            return FileManager.default.fileExists(atPath: path, isDirectory: &isDirectory) && !isDirectory.boolValue
        }
        guard exists else { throw Abort(.notFound) }
        return path
    }

    /// readFile: chunked read; the handle is closed at EOF, and on error by the caller.
    @Sendable func lineCount(_ req: Request) async throws -> String {
        let chunks = try await req.fileio.readFile(at: try await existingNotesPath(req), chunkSize: 8 * 1024)
        var lines = 0
        do {
            for try await chunk in chunks {
                lines += chunk.readableBytesView.reduce(0) { $1 == UInt8(ascii: "\n") ? $0 + 1 : $0 }
            }
        } catch {
            try? await chunks.closeHandle()
            throw error
        }
        return "\(lines)"
    }

    /// collectFile: the whole file in memory. Only for small files.
    @Sendable func readWhole(_ req: Request) async throws -> String {
        let buffer = try await req.fileio.collectFile(at: try await existingNotesPath(req))
        return String(buffer: buffer)
    }

    @Sendable func size(_ req: Request) async throws -> String {
        let buffer = try await req.fileio.collectFile(at: try await existingNotesPath(req))
        return "\(buffer.readableBytes)"
    }

    /// writeFile: replaces the file; body limited by the route's collect limit.
    @Sendable func write(_ req: Request) async throws -> HTTPStatus {
        guard let body = req.body.data, body.readableBytes <= 64 * 1024 else { throw Abort(.payloadTooLarge) }
        try await req.fileio.writeFile(body, at: try notesPath(req))
        return .noContent
    }

    /// asyncStreamFile: ETag, Last-Modified, Range and Content-Type are handled for you.
    @Sendable func download(_ req: Request) async throws -> Response {
        let path = try await existingNotesPath(req)
        let response = try await req.fileio.asyncStreamFile(at: path, mediaType: .plainText)
        response.headers.contentDisposition = .init(.attachment, filename: "notes.txt")
        return response
    }

    /// Copy of a stream with a completion callback.
    @Sendable func report(_ req: Request) async throws -> Response {
        let path = req.application.directory.resourcesDirectory + "notes/a.txt"
        let logger = req.logger
        return try await req.fileio.asyncStreamFile(at: path, chunkSize: 4096) { result in
            switch result {
            case .success: logger.info("file sent")
            case .failure(let error): logger.warning("file send failed", metadata: ["error": "\(error)"])
            }
        }
    }
}

enum SafePath {
    /// Resolves a client-supplied file name below `base`, or throws 400/404.
    static func resolve(name: String, in base: String) throws -> String {
        guard !name.isEmpty, !name.contains("/"), !name.contains("\\"), !name.contains("\0"),
              name != ".", name != ".." else {
            throw Abort(.badRequest, reason: "Invalid file name.")
        }
        let baseURL = URL(fileURLWithPath: base, isDirectory: true).resolvingSymlinksInPath()
        let candidate = baseURL.appendingPathComponent(name).resolvingSymlinksInPath()
        guard candidate.path.hasPrefix(baseURL.path + "/") else {
            throw Abort(.notFound)
        }
        return candidate.path
    }
}
----

Source: https://docs.vapor.codes/advanced/files/[Vapor docs: Files]

What each handler shows:

* `lineCount` iterates `readFile` with a small chunk size. The file is never fully in memory, so it works for a file
  of any size; the `do`/`catch` closes the handle when an error stops the iteration early.
* `readWhole` and `size` use `collectFile`, appropriate for small files only. The official documentation warns that
  the whole file has to fit in memory at once.
* `write` uses `writeFile` after checking the size of the body Vapor already collected (the default limit of a collected
  body is 16 KiB; larger bodies are rejected with `413 Payload Too Large` before the handler runs; the limits and
  streaming alternatives are covered on xref:backend/vapor/file-uploads-and-streaming.adoc[File Uploads and Streaming]).
* `download` and `report` use `asyncStreamFile`; `download` sets `Content-Disposition: attachment` through
  `HTTPHeaders.ContentDisposition`, and `report` shows the completion callback, which receives `.success` once the last
  chunk is written and `.failure` if streaming broke (a client disconnect, for example).
* `existingNotesPath` turns a missing file into a `404`. `collectFile`, `readFile` and `asyncStreamFile` report a
  missing path as a generic `500 Internal Server Error` (or, for `readFile`, a thrown file-system error), which is the
  wrong status for a client asking for something that does not exist. The `stat` is done on `app.threadPool` because
  `FileManager` is blocking and must not run on an event loop thread.

=== Memory, streaming and back-pressure

`asyncStreamFile` builds a `Response.Body(asyncStream:count:)` that reads the file chunk by chunk and writes each one to
the response stream, awaiting the write, so a slow client slows the disk reads instead of filling memory. The
`Content-Length` is known up front (the `count:` argument), so the response is not chunked-encoded. A handler that
returns the file's bytes as `Data` or a `ByteBuffer` instead (for example after `collectFile`) holds the whole file in
memory for every concurrent request: fine for a 2 KiB template, a memory incident for a 2 GiB export. Streaming request
bodies to disk and proxying downloads from another service with AsyncHTTPClient are covered in
xref:backend/vapor/file-uploads-and-streaming.adoc[File Uploads and Streaming] and
xref:backend/vapor/http-client.adoc[HTTP Client].

=== The legacy future API

The futures API from Vapor 4's first years still exists, now deprecated with "Migrate to async API":
`+collectFile(at:) -> EventLoopFuture<ByteBuffer>+`, `+readFile(at:chunkSize:onRead:) -> EventLoopFuture<Void>+`,
`+streamFile(at:chunkSize:mediaType:onCompleted:) -> Response+`, `+writeFile(_:at:) -> EventLoopFuture<Void>+`, plus the
non-deprecated `+streamFile(at:chunkSize:mediaType:advancedETagComparison:onCompleted:) -> EventLoopFuture<Response>+`.
Code written in the Vapor 3 style (`req.streamFile(at:)`, `DirectoryConfig.detect()`, `Environment.get`) does not
compile any more: `DirectoryConfig` became `DirectoryConfiguration`, and `req.streamFile` became `req.fileio.streamFile`
and then `asyncStreamFile`. `app.fileio` still exposes SwiftNIO's `NonBlockingFileIO` (`openFile(path:eventLoop:)`,
chunked reads, writes at offsets) for operations Vapor does not wrap, such as appending or writing at an offset; the
official page points to it for those cases.

== Path-traversal safety

`FileMiddleware` rejects `../` after percent-decoding, and Vapor 4.122.2 behaves as follows (all calls with
`--path-as-is` so `curl` does not normalise them):

[source,bash]
----
$ curl -i --path-as-is localhost:8080/../Package.swift
HTTP/1.1 403 Forbidden
$ curl -i --path-as-is localhost:8080/..%2f..%2fPackage.swift
HTTP/1.1 403 Forbidden
$ curl -i --path-as-is localhost:8080/%2e%2e/Package.swift
HTTP/1.1 403 Forbidden
$ curl -i --path-as-is localhost:8080/assets/..%2findex.html
HTTP/1.1 403 Forbidden
$ curl -i --path-as-is localhost:8080/..
HTTP/1.1 301 Moved Permanently
location: /../
----

The built-in protection is a string check, so know its limits. It does not resolve *symbolic links*: a symlink inside
`Public/` pointing at `/etc` is served, which is the usual deployment mistake (a `Public/uploads` link to a data volume
that also holds other files). The `/..` request above is redirected to `/../`, which the next request rejects with
`403`; it leaks nothing but shows the check is purely textual. Do not rely on the middleware's check for paths your own
handlers build: it only covers requests the middleware itself serves.

The real exposure is in *your* handlers. Any route that builds a path from a URL parameter, a JSON field or an upload's
file name and passes it to `req.fileio` has the vulnerability that book-era static servers had (one consulted book's
static server concatenated the request path onto the public directory without a check, which the book's erratum
describes). Rules for such handlers:

. Prefer an indirection. Store files under a generated name (a UUID) and look the real name up in a database row the
  user is authorised to see; never build the path from user input at all.
. When a client-supplied name must be used, accept only a single path component (no `/`, `\`, NUL, `.` or `..`),
  resolve it against the base directory *and resolve symbolic links*, and verify that the resolved path still starts
  with the resolved base plus `/`.
. Use an allow-list of extensions when the extension decides the `Content-Type`.
. Never serve the working directory itself; keep `Public/` for files that are meant to be public, and keep secrets,
  `.env` files and `Package.swift` outside it.

`SafePath.resolve(name:in:)` in the controller above implements rule 2. The check on the symbolic link in the sample
tree (`Resources/notes/link.txt` pointing to `../secret.txt`) shows it:

[source,bash]
----
$ curl -i localhost:8080/files/notes/link.txt
HTTP/1.1 404 Not Found
$ curl -i localhost:8080/files/notes/..
HTTP/1.1 400 Bad Request
----

Source: https://owasp.org/www-community/attacks/Path_Traversal[OWASP: Path Traversal]

== Resources and Public in Docker images

The official template's Dockerfile builds in a `swift:6.3-noble` stage, then copies the executable and the folders the
server reads at run time into a staging directory, and the final stage copies the staging directory into `/app`, which
is also the container's working directory (see xref:backend/vapor/deployment-with-docker.adoc[Deployment with Docker]
for the complete image):

[source,dockerfile]
----
WORKDIR /staging

# ... the executable and the SwiftPM resource bundles are copied here first ...

RUN [ -d /build/Public ] && { mv /build/Public ./Public && chmod -R a-w ./Public; } || true
RUN [ -d /build/Resources ] && { mv /build/Resources ./Resources && chmod -R a-w ./Resources; } || true

FROM ubuntu:noble

RUN useradd --user-group --create-home --system --skel /dev/null --home-dir /app vapor
WORKDIR /app
COPY --from=build --chown=vapor:vapor /staging /app
USER vapor:vapor
EXPOSE 8080
CMD ["serve", "--env", "production", "--hostname", "0.0.0.0", "--port", "8080"]
----

Source: https://github.com/vapor/template/blob/main/Dockerfile[vapor/template: Dockerfile]

What this means for the APIs on this page:

* `Public/` and `Resources/` are copied *only if they exist* in the build context, so a typo in the folder name produces
  an image that builds and then serves nothing. Check with `docker run --rm --entrypoint ls <image> /app`.
* They are made read-only (`chmod -R a-w`), and the runtime user `vapor` owns the files but cannot write to them.
  `writeFile` into `Resources/` therefore fails with a permission error in the container even though it works on a
  developer machine. Writable data (uploads, generated reports) belongs on a mounted volume, or in object storage,
  with its own directory: `/data` created in the image with the right owner, or a path from configuration.
* The process starts in `/app`, so `app.directory.publicDirectory` is `/app/Public/` with no configuration.
* A multi-instance deployment cannot keep user uploads on the container's disk; each replica would see different
  files. Static assets baked into the image are fine (every replica has the same ones); user content goes to a
  shared volume or an object store.
* Keep a `.dockerignore` so `.build/`, `.git/` and local `.env` files do not enter the build context.

== Who should serve static files

`FileMiddleware` is correct and convenient, and it is one more thing the Swift process does. Compare:

[cols="2,3,3",options="header"]
|===
|Where |Strengths |Weaknesses
|`FileMiddleware` in the Vapor app |One deployable. Same host and origin as the API. Conditional requests and ranges work. Easy in development |Every asset request occupies the app's thread pool and connections. No compression of files (`responseCompression` applies to dynamic responses; see xref:backend/vapor/server-configuration.adoc[Server Configuration]). No tuned static-file cache. Redeploying the app also redeploys the assets
|A reverse proxy (nginx, Caddy) serving `Public/` itself |sendfile, OS page cache, gzip/brotli, per-location `Cache-Control`, a separate `try_files` rule for the SPA fallback. The app only sees API traffic |The proxy needs the same files (a shared volume or an image layer), and a second configuration to keep in sync
|A CDN or object storage (S3, R2, Cloud Storage) in front of the app or instead of it |Edge caching, global latency, offloads bandwidth completely. Fingerprinted assets with `immutable` are cached forever |A build and upload step, cache invalidation for non-fingerprinted files, CORS and cookie considerations for a different origin
|===

A sound default for production: keep `FileMiddleware` for development and small sites, and in production put a reverse
proxy or CDN in front, with fingerprinted assets cached `immutable` and HTML revalidated. The nginx fragment below does
the same job as the Vapor registration above, with the application only receiving requests it must handle:

[source,nginx]
----
server {
    listen 80;
    server_name bookshelf.example.com;
    root /srv/bookshelf/Public;

    location /assets/ {
        add_header Cache-Control "public, max-age=31536000, immutable";
        try_files $uri =404;
    }

    location /api/ {
        proxy_pass http://127.0.0.1:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    location / {
        add_header Cache-Control "no-cache";
        try_files $uri $uri/ /index.html;
    }
}
----

Source: https://nginx.org/en/docs/http/ngx_http_core_module.html#try_files[nginx: try_files]

This configuration is illustrative: check it against the nginx documentation and your TLS setup before using it.
Whichever layer serves the files, keep user-generated content on a different origin or with
`Content-Disposition: attachment` and a restrictive `Content-Type`, so an uploaded HTML or SVG file cannot run script
in your site's origin.

== Testing static files

VaporTesting (see xref:backend/vapor/testing.adoc[Testing]) calls the whole middleware chain without a socket, so
file-serving rules can be tested like any route. The test needs a working directory that contains `Public/`: the package
root, when `swift test` is run from it.

[source,swift]
----
import VaporTesting
import Testing
@testable import App

@Suite struct StaticFileTests {
    @Test func servesIndexAndRevalidates() async throws {
        let app = try await Application.make(.testing)
        do {
            try await configure(app)
            try await app.testing().test(.GET, "/") { res async in
                #expect(res.status == .ok)
                let etag = res.headers.first(name: .eTag)
                #expect(etag != nil)
            }
            try await app.testing().test(.GET, "/..%2fPackage.swift") { res async in
                #expect(res.status == .forbidden)
            }
        } catch { try await app.asyncShutdown(); throw error }
        try await app.asyncShutdown()
    }
}
----

Source: https://docs.vapor.codes/advanced/testing/[Vapor docs: Testing]

== Common errors and pitfalls

[cols="3,3,3",options="header"]
|===
|Symptom |Cause |Fix
|Every file under `Public/` answers 404 |`FileMiddleware` not registered, or the process started in another working directory |register it; check `app.directory.publicDirectory`; set the Xcode working directory or `WORKDIR`
|A file exists but a route of the same path is never reached |the middleware serves the file first |rename one of them
|`/docs` is a 404 while `/docs/` works |`directoryAction` is the default `.none` |use `.redirect`
|`/` is a 404 |no `defaultFile` |pass `defaultFile: "index.html"`
|A deployment is not visible in browsers |a long `max-age` on HTML |revalidate HTML (`.noCache`); long caching only for fingerprinted files
|A missing file gives 500 |`collectFile`, `asyncStreamFile` throw `Abort(.internalServerError)` for a missing path |check existence and answer 404 yourself
|`Abort.403` for a legitimate URL |the path contains `../` after decoding |fix the link; do not disable the check
|The SPA fallback never triggers |catching `Abort` instead of `any AbortError`, or a client that does not send `Accept: text/html` |catch `any AbortError`; check the headers actually sent
|`Range` request returns 400 |unsatisfiable or malformed range (Vapor does not use 416) |request a valid range; do not rely on 416
|Out-of-memory with large downloads |`collectFile` or `Data` for big files |`asyncStreamFile` or `readFile`
|Write fails with a permission error in the container |`Resources/` and `Public/` are read-only in the official image |write to a dedicated volume
|The same file has a different `ETag` on each replica |the default `ETag` uses the modification time |`advancedETagComparison: true`, or one shared volume
|A symlink under `Public/` exposes other files |no symlink resolution in `FileMiddleware` |do not link to shared directories
|Swift 6 error about a non-`Sendable` capture in a stream callback |`onCompleted` is `@Sendable` |capture a copy of the `Logger`, as `report` does, not the request
|===

== Version notes and outdated material

* The `Public/` directory convention and `FileMiddleware` predate Vapor 4. Vapor 3 registered the middleware through
  `MiddlewareConfig`, `DirectoryConfig` and `+services.register(...)+`, none of which exist in Vapor 4. The Vapor 4
  version is the one-line `app.middleware.use(FileMiddleware(publicDirectory:))` shown above.
* The consulted books register `FileMiddleware` to serve CSS and Bootstrap for Leaf pages and show it with only
  `publicDirectory`. The `defaultFile`, `directoryAction`, `advancedETagComparison` and `cachePolicy` parameters,
  `ETag`/`Range` handling and the async `asyncStreamFile` are later additions.
* One consulted book's static server concatenated the request path to the public directory without a traversal check
  (the erratum for chapter 3); current Vapor rejects `../`, but not symbolic links.
* The futures API of `FileIO` (`collectFile`, `readFile` with a callback, `writeFile` returning a future, `streamFile`)
  is deprecated in 4.122.2. `req.fileio.readFile(at:)` now returns an `AsyncSequence`, which the old books cannot show.
* Swift 6 language mode makes the `Sendable` requirements of `onCompleted` and of middleware properties compile-time
  errors; code that captures a `Request` in a completion closure needs the capture of a `Logger` or value instead.
* *Vapor 5* (5.0.0-beta.4, not released). Read from the `5.0.0-beta.4` tag on 2026-10-17; the official 5.0 documentation
  was still a placeholder, so nothing below is documented officially and every signature may change before the release.
  The static-file pieces survive but are reshaped, and the general-purpose file operations are gone:
  `FileMiddleware` is created with
  `app.makeFileMiddleware(publicDirectory:defaultFile:directoryAction:advancedETagComparison:cachePolicy:)`, which
  defaults the directory to `app.directoryConfiguration.publicDirectory` (a `let` property, so the directory layout is
  fixed at startup) and shares an ETag hash cache with `app.fileio`. `FileIO` is now reached through `app.fileio` and
  its only public method is `streamFile(at:for:chunkSize:mediaType:advancedETagComparison:onCompleted:)`, which takes
  the `Request` as an argument and keeps the `ETag`, `Range` and `304` behaviour. `collectFile`, `readFile` and
  `writeFile` are not in the beta's public API, consistent with the removal of NIO types (`ByteBuffer`,
  `EventLoopFuture`) from the public API. A Vapor 5 service reads and writes files with Foundation, swift-system or
  NIOFileSystem directly, and `FileIO` stays a response-streaming helper. For Vapor 4 code, keeping file access behind a
  small protocol of your own (the repository pattern, described in
  xref:backend/vapor/services-storage-and-dependency-injection.adoc[Services, Storage and Dependency Injection]) makes
  that move a one-file change. xref:backend/vapor/whats-new-upgrading-and-vapor-5.adoc[What's New, Upgrading and Vapor
  5] lists the other Vapor 5 changes.
* Vapor 4.121 made `RouteNotFound` public: error handling that matched `Abort` for 404s needs `any AbortError`.
