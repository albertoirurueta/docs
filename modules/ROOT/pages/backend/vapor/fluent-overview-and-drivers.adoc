== What Fluent is

Fluent is Vapor's ORM: it maps Swift types (models) to rows or documents and Swift expressions (query builders) to the
database's own query language, and it runs the migrations that create and evolve the schema. It is deliberately split
into layers, and knowing which layer a type or an error comes from is most of what you need to read its documentation
and its stack traces.

image::vapor-fluent-overview-and-drivers-stack.svg["The Fluent stack: your app, Fluent, FluentKit, the four driver packages, SQLKit shared by the three SQL drivers, the per-database kits and the NIO libraries",width=900]

[cols="2,2,5",options="header"]
|===
|Layer |Package |What it does
|Fluent |`vapor/fluent` 4.13.0 |The Vapor integration and nothing else: `req.db` and `app.db`, `app.databases`, `app.migrations`, the `migrate` command with `--auto-migrate` and `--auto-revert`, sessions storage, `paginate(for:)`, the Authenticatable helpers. It depends on Vapor and FluentKit.
|FluentKit |`vapor/fluent-kit` 1.57.0 |The database-agnostic core with no Vapor dependency: `Model`, the property wrappers, relations, `QueryBuilder`, the `Database` and `DatabaseDriver` protocols, `DatabaseID`, `Databases`, migrations and `SchemaBuilder`. It is what a driver implements.
|SQLKit |`vapor/sql-kit` 3.36.0 |A Swift AST for SQL plus a serializer with per-dialect hooks. The three SQL drivers translate Fluent queries into SQLKit expressions; `FluentSQL` (shipped with FluentKit) is the glue.
|Fluent drivers |`fluent-*-driver` |One package per database. Each exposes a `DatabaseConfigurationFactory` (`.postgres`, `.mysql`, `.sqlite`, `.mongo`), a `DatabaseID` constant, and the implementation of `DatabaseDriver`.
|Kits |PostgresKit, MySQLKit, SQLiteKit, MongoKitten |Dialect and connection-pool code. The first three sit on SQLKit and AsyncKit's connection pool; MongoKitten is a standalone MongoDB client that also covers BSON.
|NIO libraries |PostgresNIO, MySQLNIO, SQLiteNIO, MongoKitten's core |The wire protocols over SwiftNIO (SQLiteNIO runs `libsqlite3` on a thread pool because SQLite has no network protocol).
|===

Two consequences are used throughout the page. First, a Fluent model is portable between the SQL drivers but not free of
database differences (column types, enum support, JSON); the schema layer is where those differences show up. Second,
MongoDB is not an SQL dialect: the driver reuses Fluent's model and query API, but it has no SQLKit underneath and needs
its own `ID` type for the best fit (see <<_mongodb>>).

== Where it sits in the application

Fluent is not part of the request pipeline in the way middleware and the router are. It is a service that lives on the
`Application`, is configured once during boot, and is used by handlers through the request.

[source]
----
configure(app)                               boot                         request                      shutdown
  app.databases.use(config, as: id)    -->   --auto-migrate? runs   -->   req.db / req.db(id)   -->  databases.shutdownAsync()
  app.migrations.add(...)                    app.autoMigrate()            Model.query(on: req.db)      closes every pool and driver
----

* `+app.databases.use(...)+` stores a *configuration* under a `DatabaseID`. It does not open a connection and it does
  not validate that the server is reachable. The driver, and its connection pool, are created lazily the first time that
  database is requested through `+app.databases.database(...)+`, which is what `req.db` and `app.db` call.
* The `migrate` command and the `--auto-migrate` / `--auto-revert` flags are registered by Fluent the first time
  anything touches `app.databases` or `app.migrations`. With `app.autoMigrate()` in `configure`, a wrong password or an
  unreachable host is reported at boot; without it, the first request that touches the database reports it.
* `req.db` returns a lightweight `any Database` value bound to the request's event loop and logger; it is not a
  connection. Each query or transaction borrows a pooled connection for its own duration and returns it.
* On shutdown, Fluent's lifecycle handler calls `+databases.shutdownAsync()+`, which closes every driver that was
  created. The entrypoint in the official template already awaits `app.asyncShutdown()`; see
  xref:backend/vapor/application-lifecycle-and-entrypoint.adoc[Application Lifecycle and Entrypoint].

`app.databases.use` call for you. Written by hand, the dependencies are:

The package versions are an example: the official documentation shows `from: "2.0.0"`, `"4.0.0"`, `"4.0.0"` and
`"1.0.0"` as minimums for the drivers, which is the lowest version that works with Vapor 4, not the version you should
deploy. Commit `Package.resolved` for an application so every build uses the versions you tested.

A pitfall with the template's upcoming-feature flags: with `MemberImportVisibility` on, a file that writes `.sqlite` or
`+.postgres(...)+` must itself `import` the driver module that declares the member, even though another file of the
target already imports it. The compiler says exactly that (see <<_common_errors>>). `Fluent` does not re-export the
drivers, so `configure.swift` imports `Fluent` and each driver it uses.

== Registering a database: app.databases.use

[source,swift]
----
public func use(_ configuration: DatabaseConfigurationFactory, as id: DatabaseID, isDefault: Bool? = nil)
----

Source: https://github.com/vapor/fluent-kit/blob/1.57.0/Sources/FluentKit/Database/Databases.swift[vapor/fluent-kit 1.57.0: Databases.swift]

* The factory is what `+.postgres(...)+`, `+.mysql(...)+`, `+.sqlite(...)+` and `+.mongo(...)+` return. It captures the
  configuration values and builds the driver later, when `Databases` needs it.
* `as:` names the database. Names are global to the application, and registering twice under the same id replaces the
  earlier configuration.
* `isDefault` decides which database `req.db` and `Model.query(on: req.db)` use when no id is given. The first database
  registered becomes the default unless you pass `isDefault: false`; `isDefault: true` takes the default over from an
  earlier one. `+app.databases.default(to:)+` changes the default later.
* `+app.databases.ids()+` returns the registered ids, and `+app.databases.configuration(for:)+` the stored
  configuration.

Registration order matters in one more place: migrations. `+app.migrations.add(_:to:)+` takes a database id and defaults
to the default database, so decide the default before adding migrations (see <<_several_databases_at_once>>).

== PostgreSQL

fluent-postgres-driver is built on PostgresKit and PostgresNIO. PostgreSQL is the database the official documentation
recommends and the one the template offers first. There are three ways to build the configuration, and all of them end
in a `SQLPostgresConfiguration`.

=== From a URL

A URL carries the host, port, credentials, database name and the TLS mode in one string, which suits a `DATABASE_URL`
environment variable (the pattern used by Heroku, Fly.io, Render and most container platforms):

[source,swift]
----
import Vapor
import Fluent
import FluentPostgresDriver

/// PostgreSQL from a URL: the TLS mode travels in the query string.
func usePostgresFromURL(_ app: Application) throws {
    let url = Environment.get("DATABASE_URL") ?? "postgres://bookshelf:replace-me@localhost:5432/bookshelf?tlsmode=require"
    app.databases.use(
        try .postgres(url: url, maxConnectionsPerEventLoop: 4, connectionPoolTimeout: .seconds(10), sqlLogLevel: .debug),
        as: .psql
    )
}
----

Source: https://docs.vapor.codes/fluent/overview/#configuration[Vapor docs: Fluent overview, configuration] and https://github.com/vapor/postgres-kit/blob/2.17.0/Sources/PostgresKit/SQLPostgresConfiguration.swift[vapor/postgres-kit 2.17.0: SQLPostgresConfiguration.swift]

The accepted shapes, from the PostgresKit source, are `postgres://user:password@host:port/database?tlsmode=mode`,
`+postgres+tcp://...+` (an alias of the first), and `postgres+uds://user:password@localhost/path?tlsmode=mode#database`
for a UNIX domain socket. Only host and user are required for TCP. The password is part of a URL, so percent-encode any
character that is not URL-safe (`@`, `:`, `/`, `#`, `?`, `%`).

The `tlsmode` values are:

[cols="1,4",options="header"]
|===
|Value |Behaviour
|`disable` |Do not use TLS, even if the server offers it.
|`prefer` |Use TLS if the server supports it, fall back to plaintext if it does not. This is the default for TCP URLs (and `disable` is the default for UNIX sockets).
|`require` |Use TLS and fail the connection if the server does not support it.
|===

`sslmode`, `tls` and `ssl` are accepted as aliases of `tlsmode`, for compatibility with `libpq`, and several spellings
exist for each value. The documentation comment states the rule that matters: whenever a TLS connection is made, full
certificate verification (chain of trust *and* host name) is always enforced, whatever the mode. So `prefer` still
verifies the certificate when the server offers TLS; what it permits is the *downgrade to plaintext* when the server
does not. That makes `prefer` the wrong choice for anything that crosses a network you do not control: an attacker who
strips TLS support from the negotiation gets plaintext. Use `require` outside local development.

=== From parts, with TLS decided in code

[source,swift]
----
import Vapor
import Fluent
import FluentPostgresDriver
import NIOSSL

/// PostgreSQL from parts, with TLS decided in code (NIOSSL verifies the chain and the host name by default).
func usePostgresExplicit(_ app: Application) throws {
    let tls = try NIOSSLContext(configuration: .makeClientConfiguration())
    let configuration = SQLPostgresConfiguration(
        hostname: Environment.get("DB_HOST") ?? "localhost",
        port: SQLPostgresConfiguration.ianaPortNumber,
        username: Environment.get("DB_USER") ?? "bookshelf",
        password: Environment.get("DB_PASSWORD"),
        database: Environment.get("DB_NAME") ?? "bookshelf",
        tls: .require(tls)   // .disable for a local container, .prefer(tls) to fall back to plaintext
    )
    app.databases.use(.postgres(configuration: configuration), as: .psql)
}
----

Source: https://docs.vapor.codes/fluent/overview/#configuration[Vapor docs: Fluent overview, configuration]

`tls:` is a `PostgresConnection.Configuration.TLS`, which has exactly three forms: `.disable`, `.prefer(NIOSSLContext)`
and `.require(NIOSSLContext)`. The context carries the trust roots and the verification settings; to trust a private CA,
build the `TLSConfiguration` first (`var config = TLSConfiguration.makeClientConfiguration(); config.trustRoots =
.file("/etc/ssl/db-ca.pem")`) and pass it to `NIOSSLContext(configuration:)`. The official documentation's own example
uses `tls: .disable` because it targets a local container. There is also an initialiser for UNIX domain sockets
(`SQLPostgresConfiguration(unixDomainSocketPath:username:password:database:)`) and one for a pre-established `Channel`,
for tunnelling.

=== Options common to the factory methods

[cols="2,2,5",options="header"]
|===
|Parameter |Default |Meaning
|`maxConnectionsPerEventLoop` |`1` |Upper bound of pooled connections *per event loop*, so the total is this times the number of event loops (see <<_connection_pools>>).
|`connectionPoolTimeout` |`.seconds(10)` |How long a query may wait for a free connection before failing.
|`pruneInterval` |`nil` (no pruning) |How often idle connections are checked, in the overloads that take it. Together with `maxIdleTimeBeforePruning` (default 120 seconds) it closes connections that sat idle, which helps behind a load balancer that drops idle TCP connections.
|`encodingContext`, `decodingContext` |`.default` |The JSON encoder and decoder used for `jsonb` columns (`@Field` values that are `Codable` structs).
|`sqlLogLevel` |`.debug` |The log level at which the generated SQL is logged (see <<_logging_the_sql>>).
|===

== MySQL and MariaDB

fluent-mysql-driver is built on MySQLKit and MySQLNIO and works with MariaDB too.

[source,swift]
----
import Vapor
import Fluent
import FluentMySQLDriver

/// MySQL or MariaDB: certificate verification stays on, except for the local Docker case.
func useMySQL(_ app: Application, localDocker: Bool) {
    var tls = TLSConfiguration.makeClientConfiguration()   // verifies chain and host name
    if localDocker {
        tls.certificateVerification = .none                // local development only
    }
    app.databases.use(
        .mysql(
            hostname: Environment.get("DB_HOST") ?? "localhost",
            username: Environment.get("DB_USER") ?? "bookshelf",
            password: Environment.get("DB_PASSWORD") ?? "replace-me",
            database: Environment.get("DB_NAME") ?? "bookshelf",
            tlsConfiguration: tls
        ),
        as: .mysql
    )
}
----

Source: https://docs.vapor.codes/fluent/overview/#configuration[Vapor docs: Fluent overview, configuration] and https://github.com/vapor/mysql-kit/blob/4.10.1/Sources/MySQLKit/MySQLConfiguration.swift[vapor/mysql-kit 4.10.1: MySQLConfiguration.swift]

TLS is where MySQL setups most often go wrong, and the defaults are now the safe ones:

* `tlsConfiguration` defaults to `TLSConfiguration.makeClientConfiguration()`, which verifies the server certificate
  chain and the host name. Pass `nil` for plaintext; do not pass a configuration with verification off to a server you
  do not control. The official documentation shows `certificateVerification = .none` only for MySQL 8 in a local Docker
  container, where the server has a self-signed certificate, and says not to do it in production. The listing above
  makes that a conscious switch.
* For a server with a private CA, keep verification on and add the CA: `tls.trustRoots = .file("/etc/ssl/db-ca.pem")`.
* The URL form (`+.mysql(url:)+`) takes `ssl-mode=DISABLED|PREFERRED|REQUIRED` (aliases `tls-mode`, `tls`, `ssl`;
  `VERIFY_CA` and `VERIFY_IDENTITY` are accepted as aliases of `REQUIRED`). If none is given, the default is `REQUIRED`
  for TCP and `DISABLED` for UNIX sockets. In MySQLKit 4.10.1 `PREFERRED` behaves exactly like `REQUIRED` (the source
  documents this as a limitation of the underlying implementation), so a URL cannot downgrade to plaintext by accident.
  Full certificate verification is enforced whenever TLS is used; emulating the non-verifying `REQUIRED` of
  `libmysqlclient` needs the explicit `TLSConfiguration` form shown above.
* The factory has `maxConnectionsPerEventLoop`, `connectionPoolTimeout`, pruning options and `sqlLogLevel` with the same
  meaning and defaults as the PostgreSQL ones. `sqlLogLevel` is optional here (`nil` turns query logging off).

== SQLite

fluent-sqlite-driver is built on SQLiteKit and SQLiteNIO. SQLite has no server: the "connection" is a file (or memory),
and every call runs `libsqlite3` on the application's `NIOThreadPool`.

[source,swift]
----
import Vapor
import Fluent
import FluentSQLiteDriver

/// SQLite: a file for development, memory for tests.
func useSQLite(_ app: Application, path: String?) {
    if let path {
        app.databases.use(.sqlite(.file(path)), as: .sqlite)
    } else {
        app.databases.use(.sqlite(.memory), as: .sqlite)
    }
}
----

Source: https://docs.vapor.codes/fluent/overview/#configuration[Vapor docs: Fluent overview, configuration]

* `.file(path)` stores the database in a file. A relative path is relative to the process's working directory, so it
  moves when the application is started from another directory (the launch directory of an Xcode scheme is not the
  package directory); an absolute path avoids that.
* `.memory` keeps the database in memory under a random identifier, generated each time `.memory` is evaluated. The data
  lives only until the last connection to it closes; a later connection, even with the same identifier, starts empty.
  Use it for tests and throw-away demos. The identifier form (`SQLiteConfiguration.Storage.memory(identifier:)`) lets
  several connections share one in-memory database on purpose.
* The pool of a SQLite database has one connection per event loop whatever `maxConnectionsPerEventLoop` says (the
  parameter is documented as ignored). SQLite serialises writers anyway.
* SQLite does not enforce foreign keys unless asked to, and SQLiteKit asks: `SQLiteConfiguration.enableForeignKeys`
  defaults to `true` and issues `PRAGMA foreign_keys = ON` on every connection, so the `references` and `onDelete:
  .cascade` of the Bookshelf migrations are enforced. The `.file` and `.memory` shorthands use that default.

== MongoDB

The xref:backend/vapor/mongodb.adoc[MongoDB] page of this section goes beyond the connection setup shown here.

fluent-mongo-driver integrates Fluent with MongoKitten, an independent, community-maintained client
(github.com/orlandos-nl/MongoKitten) that covers BSON, the wire protocol and the connection cluster.

[source,swift]
----
import Vapor
import Fluent
import FluentMongoDriver

/// MongoDB: the connection string names the target database.
func useMongo(_ app: Application) throws {
    let uri = Environment.get("MONGO_URL") ?? "mongodb://bookshelf:replace-me@localhost:27017/bookshelf"
    try app.databases.use(.mongo(connectionString: uri), as: .mongo)
}
----

Source: https://docs.vapor.codes/fluent/overview/#configuration[Vapor docs: Fluent overview, configuration] and https://github.com/vapor/fluent-mongo-driver/blob/1.4.0/Sources/FluentMongoDriver/MongoDB.swift[vapor/fluent-mongo-driver 1.4.0: MongoDB.swift]

The connection string is the standard MongoDB URI (`mongodb://` or `mongodb+srv://`, with options such as `tls`,
`authSource` and `replicaSet` parsed by MongoKitten's `ConnectionSettings`). Two things follow from the driver's source:

* The string must name a database in its path. Without one, `.mongo(connectionString:)` throws
  `FluentMongoError.noTargetDatabaseSpecified`, and an empty host list throws `FluentMongoError.missingHosts`; both
  happen at configuration time, which is why the call is `try`.
* The connection is *lazy*: `MongoCluster(lazyConnectingTo:)` is called when the driver is created, and a malformed
  specification at that point stops the process with `fatalError("The MongoDB connection specification was malformed")`.
  There is no `sqlLogLevel`, no SQL and no SQLKit underneath. Mongo's log lines come from MongoKitten.

MongoDB differs from the SQL drivers in what the model looks like. The official documentation says to declare the
identifier as `@ID(custom: .id)` with an `ObjectId` when a model is Mongo-only, and to keep `UUID` (the *Bookshelf*
models of this section) if the same models must also work with SQL; it also recommends nesting data and arrays of ids
over join tables, a `Document` field for free-form data, and `.custom` queries for features Fluent cannot express
(regular expressions). Migrations are mostly no-ops for Mongo, because collections are created on first write; the
xref:backend/vapor/migrations-and-schema.adoc[Migrations & Schema] page covers what `SchemaBuilder` does and does not do
there.

== Choosing the database from the environment

A service usually runs on SQLite or in-memory in development and tests, and on PostgreSQL in production. The decision
belongs in `configure.swift`, driven by the `Environment`, never by a compile-time flag, so the same binary runs
everywhere. The variable names are yours; the pattern is:

[source,swift]
----
import Vapor
import Fluent
import FluentPostgresDriver
import FluentSQLiteDriver

func configureDatabase(_ app: Application) throws {
    if let url = Environment.get("DATABASE_URL") {
        app.databases.use(try .postgres(url: url), as: .psql)
    } else if app.environment == .testing {
        app.databases.use(.sqlite(.memory), as: .sqlite)
    } else {
        app.databases.use(.sqlite(.file("bookshelf.sqlite")), as: .sqlite)
    }
}
----

Because `req.db` resolves the *default* database, the handlers and models of the rest of the application do not change
between the two branches. Where `DATABASE_URL` comes from (the process environment, a `.env` file loaded by Vapor, or a
secret store) is the subject of xref:backend/vapor/configuration-and-environment.adoc[Configuration and Environment].
Never commit a URL with a real password.

Source: https://docs.vapor.codes/basics/environment/[Vapor docs: Environment]

== Several databases at once

A `DatabaseID` per database lets one application talk to several, of the same or different kinds: an OLTP primary and a
read-only reporting copy, PostgreSQL for the domain and SQLite for a local cache, or a legacy MySQL beside a new
PostgreSQL. This listing is the one that was run (two SQLite databases, so it needs no server):

[source,swift]
----
import Vapor
import Fluent
import FluentSQLiteDriver
import SQLKit

extension DatabaseID {
    /// A second database for reporting; DatabaseID is just a string wrapper.
    static var reporting: DatabaseID { DatabaseID(string: "reporting") }
}

func configureMultipleDatabases(_ app: Application) async throws {
    // The first database registered becomes the default unless isDefault says otherwise.
    app.databases.use(.sqlite(.file("bookshelf.sqlite"), sqlLogLevel: .debug), as: .sqlite)
    app.databases.use(.sqlite(.memory, sqlLogLevel: .info), as: .reporting, isDefault: false)
    app.logger.logLevel = .debug

    app.migrations.add(CreateBookshelf())                 // runs on the default database
    app.migrations.add(CreateBookshelf(), to: .reporting) // and again on the reporting one
    try await app.autoMigrate()
}

func registerDatabaseRoutes(_ app: Application) {
    app.get("databases") { req async throws -> [String] in
        req.application.databases.ids().map(\.string).sorted()
    }

    app.get("count", ":which") { req async throws -> String in
        let which = req.parameters.get("which") ?? "default"
        let db: any Database = which == "reporting" ? req.db(.reporting) : req.db
        let n = try await Author.query(on: db).count()
        return "\(which): \(n) authors"
    }

    app.get("sql-version") { req async throws -> String in
        guard let sql = req.db as? any SQLDatabase else {
            throw Abort(.internalServerError, reason: "Default database is not an SQL database.")
        }
        let row = try await sql.raw("SELECT sqlite_version() AS v").first()
        return try row?.decode(column: "v", as: String.self) ?? "unknown"
    }
}
----

Source: https://docs.vapor.codes/fluent/overview/[Vapor docs: Fluent overview] and https://docs.vapor.codes/fluent/migration/[Vapor docs: Fluent migrations]

`CreateBookshelf` is the migration of the Bookshelf tables from the
xref:backend/vapor/migrations-and-schema.adoc[Migrations & Schema] page. Started with `App serve --hostname 127.0.0.1
--port 8089`, the three routes answer:

[source,bash]
----
$ curl -s localhost:8089/databases
["reporting","sqlite"]
$ curl -s localhost:8089/count/default
default: 0 authors
$ curl -s localhost:8089/count/reporting
reporting: 0 authors
$ curl -s localhost:8089/sql-version
3.54.1
----

What the listing shows, and the traps around it:

* `req.db` is the default database; `+req.db(.reporting)+` is another. `Model.query(on:)` and `model.save(on:)` take
  whichever `any Database` you hand them, so *every* query names its database through the value it is given. A model has
  no built-in home database. Reading `Author` from the reporting database and saving it into the default one is a normal
  two-line operation, and it is a normal source of mistakes: pass the same `db` value through a function instead of
  re-reading `req.db` in the middle of it.
* `app.migrations.add(_:to:)` is per database. Without `to:` the migration runs on the default only. The migration
  table (`_fluent_migrations`) and the enum table (`_fluent_enums`, which SQLite uses to emulate enum types) are created
  in each database that is migrated.
* `req.application.databases.ids()` is what the first route returns, and the log lines of every query carry
  `database-id` as metadata.
* The cast `req.db as? any SQLDatabase` works only for the SQL drivers, and that is why the route has a guard. See
  <<_dropping_down_to_sqlkit_and_mongokitten>>.
* Transactions are per database and per connection: `+req.db.transaction { ... }+` cannot span two `DatabaseID` values.
  Cross-database consistency is a design problem (outbox, saga), not a Fluent feature.

== Connection pools

Every SQL driver keeps connection pools from AsyncKit (`EventLoopGroupConnectionPool`): one pool per event loop of the
application's `EventLoopGroup`, each holding at most `maxConnectionsPerEventLoop` connections. A query made from a
request runs on the request's event loop, so it uses that loop's pool; connections never migrate between loops. Vapor
creates one event loop per CPU core by default (`System.coreCount`), so:

[source]
----
maximum connections to one database = cores x maxConnectionsPerEventLoop
----

A 4-core container with the PostgreSQL defaults opens up to 4 connections, an 8-core one 8, and a 16-core one with
`maxConnectionsPerEventLoop: 4` up to 64 per replica. Multiply by the number of replicas and compare with the server's
`max_connections` (100 by default in PostgreSQL) and with any connection pooler in between (PgBouncer, RDS Proxy). This
is the most common reason a scaled-out Vapor service starts failing with "too many connections". The
xref:backend/vapor/production-and-performance.adoc#connection-pools[Production and Performance] page works through the
pool arithmetic for replicas and poolers.

Behaviour worth knowing, all from the AsyncKit and driver sources:

* Connections are opened *on demand*, one per concurrent query, up to the limit. A connection is held for the duration
  of a query or of a whole `transaction { }` closure, and returned afterwards. A handler that holds a transaction open
  while it awaits a slow HTTP call ties up a connection for that long.
* When every connection of the loop's pool is busy, the next query waits in a queue. It fails with AsyncKit's
  `ConnectionPoolTimeoutError.connectionRequestTimeout` after `connectionPoolTimeout` (10 seconds by default). A small
  timeout turns a stall into fast errors, which is usually what an API wants.
* Idle connections are pruned only when `pruneInterval` is set (the PostgreSQL and MySQL factories offer it). Behind a
  firewall that silently drops idle connections, set it; I did not verify how a pool recovers from a connection that
  died while idle.
* SQLite is the exception: one connection per event loop, always.
* MongoKitten manages its own connection cluster; the settings that bound it (pool size, timeouts, replica set options)
  are options of the connection string, not parameters of the Fluent factory.

== Logging the SQL

Fluent logs every query twice, at different layers and levels. FluentKit logs `Running query` at debug level with the
query's structure (action, fields, filters, limits); the driver logs `Executing query` with the final SQL and its bound
parameters at `sqlLogLevel`, which is `.debug` by default for PostgreSQL, MySQL and SQLite. Both carry the `database-id`
and, inside a request, the `request-id`, because `req.db` is built with the request's logger.

[source,bash]
----
[ INFO ] GET /count/default [request-id: 670AB4B9-8DB2-4E43-B663-3DEA70F053BA]
[ DEBUG ] Running query [action: aggregate(count(authors[id])), database-id: sqlite, request-id: 670AB4B9-..., schema: authors, ...]
[ DEBUG ] Executing query [binds: [], database-id: sqlite, request-id: 670AB4B9-..., sql: SELECT COUNT("authors"."id") AS "aggregate" FROM "authors"]
[ INFO ] GET /count/reporting [request-id: 20EE7DA3-BEFF-442D-BA29-B9228EA06C0E]
[ INFO ] Executing query [binds: [], database-id: reporting, request-id: 20EE7DA3-..., sql: SELECT COUNT("authors"."id") AS "aggregate" FROM "authors"]
----

(The log lines are shortened with `+...+`; the `sqlLogLevel: .debug` of the first database and the `.info` of the
reporting one are what make the same statement appear at different levels.) To see the SQL in development, lower the
application's log level in `configure` (`app.logger.logLevel = .debug`, or run with `--log debug` or the `LOG_LEVEL`
environment variable; see the xref:backend/vapor/logging.adoc[Logging] page) and leave `sqlLogLevel` at its default. In
production keep the application at `.info` and leave `sqlLogLevel` at `.debug` so the SQL is not logged; raising
`sqlLogLevel` to `.info` there would log every statement and, with it, every bound value, including emails and password
hashes. Treat query logs as sensitive.

Source: https://docs.vapor.codes/fluent/overview/#logging[Vapor docs: Fluent overview, logging]

== Dropping down to SQLKit and MongoKitten

Fluent covers the common queries, and the official documentation names the escape hatches for the rest:

* *Raw SQL* (see xref:backend/vapor/sql-kit-and-raw-sql.adoc[SQLKit and Raw SQL]). Every SQL driver's `any Database` can
  be cast to `any SQLDatabase` (`import FluentSQL`, or `import SQLKit` as in the listing above). `+sql.raw("...")+` and
  the SQLKit query builders then run on the same pooled connection, in the same transaction if you are inside one.
  Interpolate values into `raw` with `\(bind:)`, never with plain string interpolation, so they are sent as bound
  parameters and not spliced into the SQL.
* *The driver's own type.* Cast to `any PostgresDatabase`, `any MySQLDatabase` or `any SQLiteDatabase` (after importing
  the driver) for what the driver's own API offers beyond SQL.
* *`.custom` and `.sql(raw:)`.* Most query and schema value types have a `.custom` case that takes a string or a
  `SQLExpression`, and a `.sql(raw:)` convenience works in both queries and schemas (for example a MySQL-specific column
  type).
* *MongoDB.* Cast to `any MongoDatabaseRepresentable` and read its `raw` property to get the MongoKitten
  `MongoDatabase`, with the whole MongoKitten API (aggregation pipelines, change streams, GridFS).

Source: https://docs.vapor.codes/fluent/advanced/[Vapor docs: Fluent advanced]

== Databases in Docker for development

A throw-away database in a container is the usual way to develop against PostgreSQL, MySQL or MongoDB without installing
a server. The values are placeholders for local development only (the password, user and database names are not secrets,
and no real instance should use them; running the service itself in a container is the subject of
xref:backend/vapor/deployment-with-docker.adoc[Deployment with Docker]). These commands and the Compose file were *not*
run while writing this page, because no container runtime was running there; they use the official images' documented
environment variables.

[source,bash]
----
docker run --name bookshelf-postgres -e POSTGRES_USER=bookshelf -e POSTGRES_PASSWORD=replace-me \
  -e POSTGRES_DB=bookshelf -p 5432:5432 -d postgres:17

docker run --name bookshelf-mysql -e MYSQL_USER=bookshelf -e MYSQL_PASSWORD=replace-me \
  -e MYSQL_DATABASE=bookshelf -e MYSQL_RANDOM_ROOT_PASSWORD=yes -p 3306:3306 -d mysql:8

docker run --name bookshelf-mongo -e MONGO_INITDB_ROOT_USERNAME=bookshelf -e MONGO_INITDB_ROOT_PASSWORD=replace-me \
  -p 27017:27017 -d mongo:8
----

The same as a Compose file, with a volume so the data survives `docker compose down` and a health check so scripts can
wait for the database:

[source,yaml]
----
services:
  db:
    image: postgres:17
    environment:
      POSTGRES_USER: bookshelf
      POSTGRES_PASSWORD: replace-me
      POSTGRES_DB: bookshelf
    ports:
      - "5432:5432"
    volumes:
      - bookshelf-data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U bookshelf -d bookshelf"]
      interval: 5s
      timeout: 3s
      retries: 10

volumes:
  bookshelf-data:
----

Then point the service at it:

[source,bash]
----
DATABASE_URL='postgres://bookshelf:replace-me@localhost:5432/bookshelf?tlsmode=disable' swift run App serve
----

Notes: the stock PostgreSQL image does not enable TLS, so a `require` URL fails against it with a TLS error: use
`tlsmode=disable` locally and `require` in the deployed environment. MySQL 8 in a container creates a self-signed
certificate, which is why the MySQL listing above has a `localDocker` switch. Inside a Compose network the host is the
service name (`db`), not `localhost`.

Source: https://docs.vapor.codes/fluent/overview/[Vapor docs: Fluent overview] and https://hub.docker.com/_/postgres[Docker Hub: postgres image]

== Swift 6 concurrency notes

* `DatabaseConfigurationFactory` is `Sendable` (its `make` closure is `@Sendable`), and so are the configuration structs
  of the drivers, so a factory can be built anywhere. `Databases` is `@unchecked Sendable` with its mutable state behind
  a lock, which is why `app.databases.use` can be called from `configure` on any thread; do it before the server starts
  anyway, since replacing a configuration does not replace a driver that has already been created (use
  `+databases.reinitialize(_:)+` for that).
* `any Database` is not `Sendable`: it is bound to an event loop and a logger. Do not store `req.db` in a long-lived
  object or capture it in a `Task` that outlives the request; pass the *id* (`DatabaseID` is `Sendable`) and ask for
  `app.db(id)` where you need it. In background work use `app.db`, not a stored request's.
* The `async` API (`try await Author.query(on: db).all()`) is the one to use; the `EventLoopFuture` API still exists in
  FluentKit, but it is the legacy form and this section does not use it. `autoMigrate()` and `autoRevert()` have `async`
  overloads, and the older future versions are what Vapor's lifecycle calls from non-async code paths.
* Models are classes with mutable state, which is why they are declared `@unchecked Sendable`; the
  xref:backend/vapor/fluent-models.adoc[Fluent Models] page explains the trade-off, and
  xref:backend/vapor/swift-concurrency-in-vapor.adoc[Swift Concurrency in Vapor] the general rules.
* With `NIOSingletons.unsafeTryInstallSingletonPosixEventLoopGroupAsConcurrencyGlobalExecutor()`, the commented-out
  option in the official template's entrypoint, calls into `.wait()`-style legacy code can deadlock; the template warns
  about it. Fluent's synchronous `shutdown()` is marked unavailable from async contexts for the same reason.

== Version notes

* *Vapor 3 to Vapor 4.* Vapor 3 used `FluentPostgreSQL` and friends as *providers*
  (`services.register(FluentPostgreSQLProvider())`, `DatabasesConfig`) and `Model` subclasses with `PostgreSQLModel`. In
  Vapor 4, drivers are plain factories registered with `app.databases.use`, models conform to `Model` with property
  wrappers, and the migrations are `Migration`/`AsyncMigration` values. There is no provider registration step.
* *Fluent releases.* The versions used are the latest releases on 2026-10-17: Fluent 4.13.0, FluentKit 1.57.0,
  fluent-postgres-driver 2.14.0, fluent-mysql-driver 4.8.0, fluent-sqlite-driver 4.9.0, fluent-mongo-driver 1.4.0. The
  `postgres(configuration:)` factory takes `SQLPostgresConfiguration`; the older `PostgresConfiguration`-based
  initialisers are deprecated in 2.x of the driver.
* *Vapor 5.* Vapor 5 is at 5.0.0-beta.4. The Fluent repository's `main` branch still declares a dependency on `vapor`
  from 4.117.0 in its `Package.swift`, and I did not find a Fluent release that targets Vapor 5; I could not verify how
  Fluent will be integrated with Vapor 5. Treat the Fluent integration as unchanged for Vapor 4 projects, and re-check
  the Fluent release notes before moving a Fluent application to Vapor 5.
* *Tools versions.* fluent 4.13.0 needs tools version 6.0 on `main`, fluent-postgres-driver `main` tools 6.2. The
  application's own tools version can be lower than the template's 6.3 as long as it is at least what the dependencies
  need.

== Where the books are outdated

* Condon et al. (_Server-Side Swift with Vapor_, Kodeco) introduces the drivers in chapters 5 to 7 (SQLite, MySQL,
  PostgreSQL and MongoDB, with Docker) and a Vapor 3 and early Vapor 4 style: `DatabaseConfigurationFactory` calls
  without `isDefault`, futures, and a MySQL setup for a local container. The book was not available where this page was
  written, so its chapter-6 MySQL TLS snippet could not be checked line by line; the outline of this section calls for
  correcting it, and the correction is what the MySQL section above states: keep certificate verification on by default
  (the 4.8 driver does), turn it off only for a local container, and never through a URL that downgrades the connection.
* Yeung (Packt) installs PostgreSQL, SQLite and MySQL and registers the Fluent drivers in Vapor 4 style, with
  completion-handler and future-based code around the connection; the `async` forms of this page replace the futures,
  and `+req.db+` is used the same way.
* Patel (Packt) uses Vapor 2's Fluent with `Droplet` and `Preparation`, and a `fluent.json` configuration file. None of
  that exists any more: drivers are registered in code, and `Preparation` became `Migration`.
