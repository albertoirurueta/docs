== Why a queue, and what Vapor Queues is

A handler that sends an e-mail (see xref:backend/vapor/email.adoc[Sending Email]), resizes an image or calls a slow
partner API makes the client wait, and loses the work if the request
fails half way. Moving that work out of the request has three effects: the response returns fast, the work can be
retried when it
fails, and the amount of work in flight is limited by the number of workers instead of by the number of requests. The
price is a second
moving part (the store and the workers) and a different failure model: a job runs later, in another process, possibly
more than once.

*Vapor Queues* (the `vapor/queues` package) is a small job queue written in Swift on top of SwiftNIO. It gives you:

* a `Job` and an `AsyncJob` protocol, with a typed `Codable` payload;
* `dispatch`, to store a job and put it in a named queue, optionally delayed and with a retry budget;
* workers that poll the queue, run the job and retry it on failure, as a separate process (`swift run App queues`) or
  inside the web
  process (`startInProcessJobs`);
* a hook protocol (`AsyncJobEventDelegate`) and `swift-metrics` instrumentation;
* a `QueuesDriver` protocol, so that the storage is replaceable, and a test driver.

What it is not: a message broker. There is no routing, no priorities inside a queue, no dead-letter queue and no
exactly-once
delivery. When you need those, use a broker (see xref:backend/messaging/index.adoc[Messaging] and
xref:backend/messaging/delivery-guarantees.adoc[Delivery Guarantees]) and consume from it in a Vapor service.

[cols="2,3,3",options="header"]
|===
|Need |Use |Why
|Work for this request, result needed in the response |`async let` or a task group inside the handler |The client waits anyway; no queue needed
|Work that can happen after the response, may be lost on a crash (a cache warm-up) |A detached `Task`, with care |No retry and no record; the task dies with the process
|Work that must happen, may take seconds, may fail (welcome e-mail, push, webhook, image resize) |A queued job |Stored before the response, retried, run by workers you size
|Work on a clock (nightly overdue scan) |A scheduled job, or a Kubernetes CronJob |The xref:backend/vapor/scheduled-jobs.adoc[Scheduled Jobs] page and the xref:backend/scheduling/index.adoc[Scheduling] section
|Work shared with other services, fan-out, replay |A broker (Kafka, RabbitMQ) |xref:backend/messaging/index.adoc[Messaging]
|===

== Choosing and configuring the driver

The driver is chosen once, in `configure`, with `app.queues.use(_:)`. `QueuesRedisDriver` adds `.redis(url:)`, which
throws if the
string is not a valid Redis URL (`redis://` or `rediss://`, optionally with a password and a database number in the
URL). Everything
else that tunes Queues is on `app.queues.configuration`:

[cols="2,2,4",options="header"]
|===
|Setting |Default |Meaning
|`refreshInterval` |`.seconds(1)` |Pause between two polling passes of a worker. The next pass starts this long after the previous one *finished*. An idle queue therefore adds up to this much latency to a job.
|`workerCount` |`.default`, one per event loop |Number of concurrent workers (each is a loop on one event loop that runs one job at a time). `.default` is the number of event loops of the application, normally the number of CPU cores. An integer literal means `.custom(n)`.
|`persistenceKey` |`"vapor_queues"` |Prefix of the Redis list names. A queue called `emails` with the key `bookshelf` is the list `bookshelf[emails]`. Give each application its own key when applications share a Redis.
|===

The complete `configure` of the Bookshelf scratch project, used by the rest of this page:

[source,swift]
----
import Queues
import QueuesRedisDriver
import Vapor

func configure(_ app: Application, retryBaseSeconds: Int = 30) async throws {
    // 1. Driver. Tests choose their own driver, so the production one is skipped there.
    if app.environment != .testing {
        let url = Environment.get("REDIS_URL") ?? "redis://127.0.0.1:6379"
        try app.queues.use(.redis(url: url))
    }

    // 2. Tuning.
    app.queues.configuration.refreshInterval = .seconds(1)
    app.queues.configuration.persistenceKey = "bookshelf"
    app.queues.configuration.workerCount = 2

    // 3. Every job type must be registered, in the web process and in the worker process.
    app.queues.add(WelcomeEmailJob(retryBaseSeconds: retryBaseSeconds))
    app.queues.add(LoanReminderJob())

    // 4. Monitoring.
    app.queues.add(JobAuditDelegate(logger: app.logger, stats: app.jobStats))

    // 5. Optional in-process workers, for small deployments and local development.
    if Environment.get("QUEUES_IN_PROCESS") == "true" {
        try app.queues.startInProcessJobs(on: .emails)
        try app.queues.startInProcessJobs(on: .reminders)
    }

    try routes(app)
}

extension Application {
    private struct JobStatsKey: StorageKey { typealias Value = JobStats }

    var jobStats: JobStats {
        if let existing = storage[JobStatsKey.self] { return existing }
        let stats = JobStats()
        storage[JobStatsKey.self] = stats
        return stats
    }
}
----

Source: https://docs.vapor.codes/advanced/queues/[Vapor docs: Queues, Getting started],
https://github.com/vapor/queues/blob/1.18.0/Sources/Queues/QueuesConfiguration.swift[vapor/queues 1.18.0:
QueuesConfiguration.swift]

Three details of that listing matter:

* *Register every job in every process.* The job registry lives in memory. The web process only needs the types it
  dispatches, but the
  worker process, which is the same binary started with a different command, must know every job that can reach it.
  Putting
  `app.queues.add` in `configure` does both.
* *Tests skip the production driver.* `app.environment != .testing` leaves the choice to the test (see
  <<_testing_jobs>>); without
  that, the tests would try to reach Redis.
* *The Redis URL is configuration, not code.* Read it from the environment (see
  xref:backend/vapor/configuration-and-environment.adoc[Configuration & Environment]). A `rediss://` URL turns on TLS,
  and a password goes in
  the URL or in the `RedisConfiguration`, never in the source.

The Redis driver opens one connection pool and shares it between all its workers. The default of `vapor/redis` is at
most two
simultaneous connections (`.maximumActiveConnections(2)`), and `connectionRetryTimeout` is `nil` by default. With the
default
`workerCount` on a many-core machine, size the pool and set a timeout (so that an unreachable Redis fails instead of
waiting) with the
`RedisConfiguration` overload:

[source,swift]
----
import Queues
import QueuesRedisDriver
import Vapor

/// The same driver with an explicit pool, a connection timeout and TLS taken from a `rediss://` URL.
func makeRedisQueuesProvider() throws -> Application.Queues.Provider {
    let url = Environment.get("REDIS_URL") ?? "redis://127.0.0.1:6379"
    let configuration = try RedisConfiguration(
        url: url,
        pool: .init(
            maximumConnectionCount: .maximumActiveConnections(8),
            minimumConnectionCount: 1,
            connectionRetryTimeout: .seconds(5)))
    return .redis(configuration)
}
----

Source:
https://github.com/vapor/queues-redis-driver/blob/1.1.2/Sources/QueuesRedisDriver/JobsRedisDriver.swift[queues-redis-driver 1.1.2: JobsRedisDriver.swift], https://github.com/vapor/redis/blob/4.14.0/Sources/Redis/RedisConfiguration.swift[vapor/redis 4.14.0: RedisConfiguration.swift]

Use it as `try app.queues.use(makeRedisQueuesProvider())`. The Queues driver and the `app.redis` client of the Redis
package are separate
pools, even when they point at the same server.

=== The Fluent driver

If the service already has a SQL database and no Redis, jobs can live in a table. The listing below is the whole
configuration of the
scratch project in which the Fluent driver was run (SQLite for the scratch project; use Postgres or MySQL for real
work):

[source,swift]
----
import Fluent
import FluentSQLiteDriver
import Queues
import QueuesFluentDriver
import Vapor

struct PingPayload: Codable, Sendable {
    let message: String
}

struct PingJob: AsyncJob {
    typealias Payload = PingPayload

    func dequeue(_ context: QueueContext, _ payload: PingPayload) async throws {
        context.logger.info("PingJob ran", metadata: ["message": "\(payload.message)"])
    }
}

func configure(_ app: Application) async throws {
    // The database must be registered before the queues driver.
    app.databases.use(.sqlite(app.environment == .testing ? .memory : .file("queues.sqlite")), as: .sqlite)

    // The jobs table, created by `migrate` like any other table.
    app.migrations.add(JobModelMigration())

    app.queues.use(.fluent(preservesCompletedJobs: true))
    app.queues.configuration.workerCount = 1
    app.queues.configuration.refreshInterval = .milliseconds(200)
    app.queues.add(PingJob())

    app.post("ping") { req async throws -> HTTPStatus in
        try await req.queue.dispatch(PingJob.self, PingPayload(message: "hello from the web process"))
        return .accepted
    }
}
----

Source: https://github.com/vapor-community/vapor-queues-fluent-driver[vapor-community/vapor-queues-fluent-driver 3.2.0]

The driver needs the database registered before `app.queues.use(.fluent())`, and a migration for the jobs table (see
xref:backend/vapor/migrations-and-schema.adoc[Migrations & Schema]). `swift run App migrate --auto-migrate` created this
table:

[source,sql]
----
CREATE TABLE "_jobs_meta" ("id" TEXT PRIMARY KEY, "queue_name" TEXT NOT NULL, "job_name" TEXT NOT NULL,
  "queued_at" TIMESTAMP NOT NULL, "delay_until" TIMESTAMP DEFAULT NULL, "state" varchar(16) NOT NULL,
  "max_retry_count" INTEGER NOT NULL, "attempts" INTEGER NOT NULL, "payload" BLOB NOT NULL, "updated_at" TIMESTAMP NOT NULL);
----

The web process and the worker were then started as two processes against the same file, with one `curl` in between:

[source,bash]
----
$ swift run App serve --port 8091 &
$ curl -i -X POST localhost:8091/ping
HTTP/1.1 202 Accepted
$ sqlite3 queues.sqlite "select state, job_name, queue_name from _jobs_meta"
pending|PingJob|default
$ swift run App queues
[ INFO ] Starting jobs worker [queue: default]
[ INFO ] Dequeing and running job [attempt: 1, job-id: BFDD4B83-D248-465C-8E47-4BD5D6865013, job-name: PingJob, queue: default, retries-left: 0]
[ INFO ] PingJob ran [job_id: BFDD4B83-D248-465C-8E47-4BD5D6865013, message: hello from the web process, queue: default]
$ sqlite3 queues.sqlite "select state, job_name from _jobs_meta"
completed|PingJob
----

Compared with Redis, the table gives you something to query and to repair by hand (a job is a row with a `state`), jobs
that survive
a Redis flush, and the same backup as the rest of your data. It costs a polling query per worker per `refreshInterval`
on your primary
database, so raise `refreshInterval` and lower `workerCount` for it. `preservesCompletedJobs: true` keeps finished rows
(nothing
deletes them afterwards, so add a clean-up). The driver is a community package: its Vapor 5 status is unknown, and it is
a dependency
to review before adopting.

== Defining a job

A job is a value (a struct, usually without stored state) that conforms to `AsyncJob`, with a `Payload` type that is
`Codable` and
`Sendable`:

[cols="2,4",options="header"]
|===
|Member |Role
|`associatedtype Payload` |The data of one run, serialised to JSON by default (`serializePayload` and `parsePayload` are overridable for other formats). Must be `Sendable`, and `Codable` unless you write the two functions.
|`func dequeue(_ context: QueueContext, _ payload: Payload) async throws` |The work. Returning means success; throwing means failure.
|`func error(_ context: QueueContext, _ error: any Error, _ payload: Payload) async throws` |Called once, after the last attempt has failed. Optional; the default does nothing.
|`+func nextRetryIn(attempt: Int) -> Int+` |Seconds to wait before the next try after a failure; `0` (the default) means immediately. `attempt` is the number of failures so far, so `1` after the first failure.
|`static var name: String` |The identifier stored with every job; the default is `String(describing: Self.self)`, the Swift type name.
|===

`Job` is the older, `EventLoopFuture`-returning protocol, and `AsyncJob` refines it with `async` versions of `dequeue`
and `error`
(the futures versions are forwarded to them). Use `AsyncJob`; `Job` remains for code that predates async/await and is
not shown here.

`QueueContext` is what a job gets instead of a `Request`, because there is no request: it carries the `application` (and
through it
every service, database and client), a `logger` already tagged with the queue name and the job id, the `queueName`, the
`configuration`,
and the `eventLoop`. It also gives `context.queue` and `context.queues(_:)`, so a job can dispatch a follow-up job.

[source,swift]
----
import Foundation
import Queues
import Vapor

struct WelcomeEmail: Codable, Sendable {
    let memberID: UUID
    let email: String
    let name: String
}

struct WelcomeEmailJob: AsyncJob {
    typealias Payload = WelcomeEmail

    /// A stable name: renaming the Swift type must not orphan jobs already waiting in Redis.
    static var name: String { "welcome-email" }

    /// Seconds before the first retry; each further retry doubles it (capped at 15 minutes).
    var retryBaseSeconds = 30

    func dequeue(_ context: QueueContext, _ payload: WelcomeEmail) async throws {
        let key = "welcome-\(payload.memberID)"
        let ledger = context.application.sentLedger
        guard await !ledger.contains(key) else {
            context.logger.info("Welcome email already sent, skipping", metadata: ["key": "\(key)"])
            return
        }
        try await context.application.emailSender.send(OutgoingEmail(
            to: payload.email,
            subject: "Welcome to Bookshelf, \(payload.name)",
            body: "Your account is ready.",
            idempotencyKey: key))
        await ledger.record(key)
    }

    func error(_ context: QueueContext, _ error: any Error, _ payload: WelcomeEmail) async throws {
        // Called once, after the last attempt failed. Park it where a human or a repair job will look.
        context.logger.error("Welcome email gave up", metadata: [
            "member": "\(payload.memberID)", "error": "\(error)",
        ])
    }

    func nextRetryIn(attempt: Int) -> Int {
        guard retryBaseSeconds > 0 else { return 0 }
        return min(retryBaseSeconds << (attempt - 1), 15 * 60)
    }
}

struct LoanReminder: Codable, Sendable {
    let loanID: UUID
    let email: String
    let title: String
}

struct LoanReminderJob: AsyncJob {
    typealias Payload = LoanReminder

    func dequeue(_ context: QueueContext, _ payload: LoanReminder) async throws {
        try await context.application.emailSender.send(OutgoingEmail(
            to: payload.email,
            subject: "\"\(payload.title)\" is due tomorrow",
            body: "Please return it or renew the loan.",
            idempotencyKey: "reminder-\(payload.loanID)"))
    }
}

extension QueueName {
    /// Everything that sends mail: its own queue, so a backlog never delays the others.
    static let emails = QueueName(string: "emails")
    /// Reminders are processed strictly one at a time.
    static let reminders = QueueName(string: "reminders", workerCount: 1)
}
----

Source: https://docs.vapor.codes/advanced/queues/[Vapor docs: Queues, The Job protocol],
https://github.com/vapor/queues/blob/1.18.0/Sources/Queues/AsyncJob.swift[vapor/queues 1.18.0: AsyncJob.swift]

Points worth stating about that listing:

* *The payload holds identifiers and the minimum to act on, not objects.* `WelcomeEmail` carries the member id, the
  address and the name
  rather than a `Member` model. The payload is stored as plain JSON in Redis (or in a table), so anything you put there
  is readable
  by anyone with access to the store: no passwords, tokens or other secrets, and think twice about personal data (the
  e-mail address
  here is the minimum needed). When the data may have changed by the time the job runs, carry the id and load the row in
  `dequeue`.
* *The Swift 6 constraints are enforced by the compiler.* `AnyJob` is `Sendable`, so a job struct cannot hold mutable
  state, and
  `Payload` must be `Sendable`. A job reaches shared services through `context.application` (the pattern of
  xref:backend/vapor/services-storage-and-dependency-injection.adoc[Services, Storage & Dependency Injection]) and keeps
  cross-run state in
  an `actor` or a database, never in a stored `var`.
* *`static var name` is a decision you should make explicitly.* The name is written into every stored job, and the
  worker looks the
  job up by it. Renaming the Swift type without pinning the name makes jobs already in the queue unrunnable: the worker
  logs
  `No job with the desired name is registered, discarding` and deletes them.
* *The `error` hook is the only place to record a permanent failure.* The queue has no dead-letter list: after the last
  failed attempt
  the job data is deleted. The hook (and the event delegate below) is where a row in a `failed_jobs` table, a log line
  with the member
  id, or an alert belongs.
* *The `nextRetryIn` shown is exponential backoff*: with a base of 30 seconds the delays are 30, 60, 120, 240 and so on,
  capped at
  fifteen minutes. A `retryBaseSeconds` of zero means no delay, which tests use.

When the payload is not `Sendable` or not `Codable` the compiler says so (messages from the scratch project):

[source,text]
----
error: type 'ResizeJob.Payload' (aka 'ResizePayload') does not conform to the 'Sendable' protocol
error: type 'ResizePayload' does not conform to protocol 'Decodable'
error: type 'PlainJob' does not conform to protocol 'Job'
----

The first is a payload that holds a class (`final class Cover { var path = "" }`); the last is a payload that is not
`Codable`
without custom `serializePayload`/`parsePayload`.

== Registering and dispatching

`app.queues.add(_:)` registers a job instance and must run for each job type before the application starts (the listing
does it in
`configure`). Registering the same name twice replaces the first and logs a warning. *Dispatching a job that is not
registered does
not fail*: the job is stored, and the worker discards it with the warning above, so a typo in the registration shows up
as jobs that
silently vanish.

`dispatch` stores the job data and then pushes its id onto the queue. Its signature, copied from the source:

[source,swift]
----
func dispatch<J: Job>(
    _ job: J.Type,
    _ payload: J.Payload,
    maxRetryCount: Int = 0,
    delayUntil: Date? = nil,
    id: JobIdentifier = .init()
) async throws
----

You reach a queue from a request with `req.queue` (the default queue) or `+req.queues(_:)+` (a named one), and from
anywhere else with
`app.queues.queue` and `app.queues.queue(_:)`, for instance in a command or in another job. The routes of the scratch
project:

[source,swift]
----
import Queues
import Vapor

struct RegisterMember: Content {
    let email: String
    let name: String
}

struct LoanRequest: Content {
    let email: String
    let title: String
    let dueDate: Date
}

func routes(_ app: Application) throws {
    app.post("members") { req async throws -> HTTPStatus in
        let input = try req.content.decode(RegisterMember.self)
        let memberID = UUID()
        // ... save the member with Fluent first; dispatch only after the row is committed.
        try await req.queues(.emails).dispatch(
            WelcomeEmailJob.self,
            WelcomeEmail(memberID: memberID, email: input.email, name: input.name),
            maxRetryCount: 5,
            id: JobIdentifier(string: "welcome-\(memberID)"))
        return .accepted
    }

    app.post("loans") { req async throws -> HTTPStatus in
        let input = try req.content.decode(LoanRequest.self)
        let reminderAt = input.dueDate.addingTimeInterval(-24 * 60 * 60)
        try await req.queues(.reminders).dispatch(
            LoanReminderJob.self,
            LoanReminder(loanID: UUID(), email: input.email, title: input.title),
            maxRetryCount: 3,
            delayUntil: reminderAt)
        return .accepted
    }
}
----

Source: https://docs.vapor.codes/advanced/queues/[Vapor docs: Queues, Dispatching jobs],
https://github.com/vapor/queues/blob/1.18.0/Sources/Queues/AsyncQueue.swift[vapor/queues 1.18.0: AsyncQueue.swift]

Behaviour that the handlers rely on, each verified in the test suite:

* `dispatch` returns as soon as the job is stored, so the handler answers `202 Accepted` while the e-mail has not been
  sent yet. The
  test asserts exactly that: after the request, `app.queues.asyncTest.contains(WelcomeEmailJob.self)` is true and the
  fake sender has
  recorded nothing.
* *Dispatch after the data is committed.* If the handler dispatches inside a database transaction that later rolls back,
  the job runs
  for a member that does not exist; if it dispatches before the commit, a fast worker can run before the row is visible.
  Do the
  dispatch after the commit (see
  xref:backend/vapor/transactions-model-middleware-and-soft-delete.adoc[Transactions, Model Middleware & Soft Delete]);
  the reverse
  failure (committed, then the dispatch fails) is the case the retry and the idempotency below cannot cover, so a
  reliable system adds
  a periodic repair job that finds rows without their e-mail. That is the cost of having two stores, a database and a
  queue, with no
  shared transaction.
* *A custom `id` is not a deduplication key.* The listing uses `+JobIdentifier(string: "welcome-\(memberID)")+` so that
  logs and
  metrics can be matched to the member. Dispatching twice with the same id stores the data once (the second write
  overwrites the
  first) but pushes the id twice. The test shows the consequence: the queue holds two entries and one data record, the
  first pop
  runs the job and deletes the record, and the second pop throws (`NoSuchJobError` on the test driver; the Redis driver
  throws its
  `missingJob` error, per its source). Dedupe with a unique database constraint instead.
* `maxRetryCount` is the number of *retries*, so `maxRetryCount: 2` is three attempts in total (tested: three calls to
  the sender,
  then `error`). The default `0` means a failure is final.
* *Dispatching from a request needs an `await`.* The official page shows some examples without `try await`, but the
  `async` overload
  returns a value that must be awaited, and the compiler will tell you.

== Named queues and priorities

A `QueueName` is a string that selects a separate list in the store. There are no priorities *inside* a queue: it is
first in, first
out. What the documentation calls priorities is the ability to route different kinds of work to different queues and
give each its own
workers:

[source,swift]
----
extension QueueName {
    /// Everything that sends mail: its own queue, so a backlog never delays the others.
    static let emails = QueueName(string: "emails")
    /// Reminders are processed strictly one at a time.
    static let reminders = QueueName(string: "reminders", workerCount: 1)
}
----

Source: https://docs.vapor.codes/advanced/queues/[Vapor docs: Queues, Specify a priority]

The optional `workerCount` caps the number of workers *for that queue*, whatever the global setting: the effective
number is the
smaller of the two, and `1` makes the queue strictly sequential (useful when order matters, or when the job talks to
something that
cannot take parallel callers). A queue name without a count uses the global one. Queues and workers are matched when you
start the
worker, not when you dispatch: a job sent to a queue nobody serves waits there forever, and Queues does not warn about
it.

[cols="2,3",options="header"]
|===
|Goal |How
|Keep e-mail from blocking image processing |Two queues, a worker process per queue
|Give urgent work precedence |A separate queue with its own workers (more of them, or a lower `refreshInterval`); the queue does not reorder
|Process one account's jobs in order |Not provided; use a queue with `workerCount: 1`, or a broker with partitions
|Limit parallel calls to a rate-limited API |A queue with a small `workerCount`
|===

== Running workers

Dispatching only stores jobs. Nothing runs them until a worker is started, and `Queues` does not tell you when none is:
the official
page carries a warning that jobs do not run unless you start a worker, on the command line or in process.

=== As a separate process

The `queues` command is registered by Queues itself, and works with the same binary and the same `configure` as the web
server:

[source,bash]
----
swift run App queues                      # the default queue
swift run App queues --queue emails       # one named queue
swift run App queues --scheduled          # the scheduler instead (scheduled-jobs page)
----

`swift run App queues --help` prints (the path in the first line shortened):

[source,text]
----
Usage: App queues [--queue] [--scheduled] 

Starts the Vapor Queues worker

Options:
      queue Specifies a single queue to run

Flags:
  scheduled Runs the scheduled queue jobs
----

One worker process serves one queue: to serve `emails` and `reminders` you start two processes (or use the in-process
option below). In
production the command is a long-running service, run like the web server by systemd, a container or a Kubernetes
Deployment
(see <<_deployment_shapes>>). It handles `SIGTERM` and `SIGINT`: the scratch worker, sent `SIGTERM`, stopped polling and
exited. What happens to a job that is
running at that moment was not verified, so write jobs that can safely run again (see
<<_retries_failures_and_idempotency>>).

=== Inside the web process

For a small deployment, or while developing, workers can run in the server process:

[source,swift]
----
try app.queues.startInProcessJobs(on: .emails)
try app.queues.startInProcessJobs(on: .reminders)
----

Call it once per queue; each call starts the number of workers that queue is configured for. The listing in `configure`
does it
when `QUEUES_IN_PROCESS` is `true`. The test suite runs the same call against the test driver.

[cols="2,3,3",options="header"]
|===
| |Separate `queues` process |In-process (`startInProcessJobs`)
|Scale |Workers and web servers scale independently |Every web replica also runs workers
|Isolation |A slow or crashing job cannot take the web server down; a deployment can restart workers alone |Jobs share the event loops, memory and fate of the web server
|CPU-heavy jobs |Run them on a dedicated, larger or smaller machine |Compete with request handling
|Operations |One more service to run and monitor |Nothing extra
|Good for |Production |Development, tests, and small single-instance services
|===

A worker is a loop pinned to one event loop that runs `refreshInterval` after the previous pass finished: it pops jobs
one at a time
until the queue is empty, then sleeps. So a worker runs one job at a time, `dequeue` is `async` and does not block the
event loop while
it awaits, and the concurrency of a queue is its worker count. A long job occupies a worker for its whole duration; do
not run
thread-blocking work (a synchronous library call) in `dequeue` without moving it off the event loop.

=== Delayed jobs and the head of the queue

`delayUntil` is implemented by the worker, not by the store. When a worker pops a job whose time has not come, it pushes
the id back
onto the queue *and ends the pass*. Two consequences, both measured in the test suite, which dispatched three jobs
delayed by an hour
followed by one ready job:

[source,text]
----
the ready job ran on pass 4
----

* *Delayed jobs are polled, not parked.* A job delayed by two weeks is popped and re-pushed on every pass of every
  worker for two weeks.
* *Delayed jobs ahead of ready ones slow them down.* Each pass gets past one delayed job, so a ready job behind three
  delayed ones
  waits for four passes, which at the default `refreshInterval` is four seconds, and a hundred delayed reminders would
  hold ready
  jobs up for minutes.

Use `delayUntil` for short delays (a retry, "in five minutes"). For "remind the member the day before the loan is due",
do not queue a
job fourteen days ahead as the `/loans` route above does for illustration: store the due date in the database and let a
scheduled job
find the loans due tomorrow once a day (the xref:backend/vapor/scheduled-jobs.adoc[Scheduled Jobs] page), which also
survives a Redis flush and lets a
returned book cancel its reminder.

== Retries, failures and idempotency

The worker's behaviour when `dequeue` throws, read from `QueueWorker.swift` and confirmed by the tests:

[cols="2,4",options="header"]
|===
|Situation |What happens
|`dequeue` returns |The job data is deleted, the id leaves the queue, delegates get `success`
|`dequeue` throws, retries left |`nextRetryIn(attempt:)` is called; the job data is rewritten with the attempt count and `delayUntil` (if the delay is above zero) and the id is pushed back. `error` is *not* called and delegates are *not* told. The next attempt runs on any worker.
|`dequeue` throws, none left |The job's `error` hook runs, then delegates get `error(jobId:error:)`, then the job is deleted
|The job's name is not registered |Warning in the log, job deleted
|Delay not over |Id pushed back, the pass ends (see above)
|The worker process dies during `dequeue` |See below
|===

Because a job can run more than once, make it *idempotent*: running it twice must have the effect of running it once.
Retries cause
the repeat when `dequeue` does part of its work and then throws (the e-mail was sent, then the database write failed),
and an
operator who requeues a stuck job causes it too. The usual tools, in order of strength:

. *A natural key*: the operation is itself idempotent (`UPDATE loans SET reminded = true`, an upsert).
. *A record of completion*, checked before and written after: the listing keeps a `SentLedger`, an in-memory `actor` in
  the scratch
  project, so the second run logs `Welcome email already sent, skipping` and sends nothing (tested: two identical jobs,
  one e-mail). In
  a real service the ledger is a table with a unique constraint on the key, written in the same transaction as the side
  effect when
  the side effect is a database change.
. *The provider's idempotency key*: pass the same key (the listing passes `idempotencyKey` in `OutgoingEmail`) on every
  attempt, for
  providers that support one, so the provider deduplicates what a ledger cannot (the crash between "sent" and
  "recorded").

The remaining gap, between sending and recording, is inherent: you can choose to risk a duplicate (check, send, record:
what the
listing does) or a loss (record, send), and for e-mail a duplicate is the safer error.

=== What a crash does (Redis driver, from the source)

The Redis driver's `pop` is `RPOPLPUSH`: it atomically moves the id from the queue list `bookshelf[emails]` to a second
list,
`bookshelf[emails]-processing`, and `clear` removes it from there when the job finishes or fails for good. This is the
"reliable
queue" pattern, and it means a worker that dies between the pop and the clear leaves the id in the processing list. I
searched
`queues` 1.18.0 and `queues-redis-driver` 1.1.2 for anything that reads the processing list back and found only the
three places
that write to or remove from it, so *a job that was running when its worker was killed is not retried automatically*:
its data stays
in Redis under `job:<id>` and its id stays in the processing list until someone moves it back. (This was not run against
a Redis
server; if you depend on it, test it with a real one.) The recovery, with no worker running on that queue, is to look at
the list
and move the ids back to the queue, one `LMOVE` per id (`LMOVE` replaces the deprecated `RPOPLPUSH`):

[source,bash]
----
redis-cli LRANGE 'bookshelf[emails]-processing' 0 -1
redis-cli LMOVE 'bookshelf[emails]-processing' 'bookshelf[emails]' RIGHT LEFT
----

The job data key is `job:<id>`, not prefixed by `persistenceKey`, and dates in it are written as seconds since 1970. The
Fluent driver
keeps the state of each job in a row, which makes the same situation visible with a query.

This is why a queue like this one gives you at-least-once behaviour for failures it can see (an exception) and no
guarantee for a
process that disappears. Anything needing stronger delivery guarantees belongs on a broker; the
xref:backend/messaging/delivery-guarantees.adoc[Delivery Guarantees]
page has the vocabulary.

== Monitoring jobs

`AsyncJobEventDelegate` receives four events, all optional (the defaults do nothing). Register one with
`app.queues.add(_:)`:

[source,swift]
----
import Queues
import Vapor

/// Counters kept by the delegate (an actor, because delegates are called from several event loops).
actor JobStats {
    private(set) var dispatched = 0
    private(set) var dequeued = 0
    private(set) var succeeded = 0
    private(set) var failed = 0

    func didDispatch() { dispatched += 1 }
    func didDequeue() { dequeued += 1 }
    func didSucceed() { succeeded += 1 }
    func didFail() { failed += 1 }
}

struct JobAuditDelegate: AsyncJobEventDelegate {
    let logger: Logger
    let stats: JobStats

    func dispatched(job: JobEventData) async throws {
        await stats.didDispatch()
        logger.info("job dispatched", metadata: [
            "job": "\(job.jobName)", "id": "\(job.id)", "queue": "\(job.queueName)",
        ])
    }

    func didDequeue(jobId: String) async throws {
        await stats.didDequeue()
    }

    func success(jobId: String) async throws {
        await stats.didSucceed()
        logger.info("job succeeded", metadata: ["id": "\(jobId)"])
    }

    func error(jobId: String, error: any Error) async throws {
        await stats.didFail()
        logger.error("job failed for good", metadata: ["id": "\(jobId)", "error": "\(error)"])
    }
}
----

Source: https://github.com/vapor/queues/blob/1.18.0/Sources/Queues/AsyncJobEventDelegate.swift[vapor/queues 1.18.0:
AsyncJobEventDelegate.swift]

[cols="2,4",options="header"]
|===
|Callback |Called
|`dispatched(job:)` |By `dispatch`, with `JobEventData`: id, queue name, payload bytes, retry budget, delay, queue time and job name
|`didDequeue(jobId:)` |Each time a worker picks the job up, so once per attempt (tested: three for a job that failed twice and then succeeded)
|`success(jobId:)` |When `dequeue` returns
|`error(jobId:error:)` |Once, after the last failed attempt; not on a retry
|===

A delegate that throws is logged as `Failed to send notification` and otherwise ignored, so monitoring cannot break job
processing.
The delegate must be `Sendable` and is called from whichever event loop runs the job, hence the `actor` for the
counters.

Queues also reports to `swift-metrics`, so any metrics backend you have bootstrapped (Prometheus, OpenTelemetry)
receives these from
the source of `QueueWorker` and `dispatch` (see xref:backend/vapor/tracing-metrics-and-opentelemetry.adoc[Tracing,
Metrics & OpenTelemetry] for bootstrapping a backend; queues do not propagate trace context, so carry a `traceparent`
value in the payload if you need it):

[cols="3,2,3",options="header"]
|===
|Metric |Kind |Dimensions
|`dispatched.jobs.counter` |counter |`queueName`, `jobName`
|`success.completed.jobs.counter` |counter |`queueName`
|`error.completed.jobs.counter` |counter |`queueName`
|`jobs.in.progress.meter` |meter |`queueName`
|`<jobName>.jobDurationTimer` |timer |`success`, `jobName`
|===

The most useful alerts are the age of the oldest job in each queue (how late the work is) and the length of each queue,
which Queues
does not export: read them from Redis (`+LLEN 'bookshelf[emails]'+`) or the jobs table with a small scheduled probe.

== Testing jobs

The general test setup is on the xref:backend/vapor/testing.adoc[Testing] page. `XCTQueues` provides `.asyncTest` (and
`.test` for the futures-based `Job`), a driver that keeps jobs in memory. The name `XCTQueues`
is historical: it works with Swift Testing. Two rules make queue tests deterministic: select the driver *before*
`configure`, and do not
start any worker; call `app.queues.queue.worker.run()` yourself to run everything that is ready, in the test's own task.

[source,swift]
----
import Foundation
import Queues
import Testing
import VaporTesting
import XCTQueues
@testable import App

/// Fake provider: fails the first `failures` calls, records the rest.
actor RecordingEmailSender: EmailSender {
    private(set) var sent: [OutgoingEmail] = []
    private(set) var attempts = 0
    private var failuresLeft: Int

    struct Outage: Error {}

    init(failures: Int = 0) { failuresLeft = failures }

    func send(_ message: OutgoingEmail) async throws {
        attempts += 1
        if failuresLeft > 0 {
            failuresLeft -= 1
            throw Outage()
        }
        sent.append(message)
    }
}

func withApp(
    sender: RecordingEmailSender = RecordingEmailSender(),
    retryBaseSeconds: Int = 0,
    _ body: (Application) async throws -> Void
) async throws {
    let app = try await Application.make(.testing)
    do {
        app.queues.use(.asyncTest)
        app.emailSender = sender
        try await configure(app, retryBaseSeconds: retryBaseSeconds)
        try await body(app)
    } catch {
        try await app.asyncShutdown()
        throw error
    }
    try await app.asyncShutdown()
}

@Suite struct QueueTests {
    @Test func registrationDispatchesAJobWithoutSendingMail() async throws {
        let sender = RecordingEmailSender()
        try await withApp(sender: sender) { app in
            try await app.testing().test(.POST, "members", beforeRequest: { req in
                try req.content.encode(RegisterMember(email: "ada@example.com", name: "Ada"))
            }, afterResponse: { res async in
                #expect(res.status == .accepted)
            })

            // The handler only enqueued the job.
            #expect(app.queues.asyncTest.contains(WelcomeEmailJob.self))
            let payload = try #require(app.queues.asyncTest.first(WelcomeEmailJob.self))
            #expect(payload.email == "ada@example.com")
            #expect(await sender.sent.isEmpty)

            // Drain the queue the way a worker does.
            try await app.queues.queue.worker.run()
            #expect(await sender.sent.count == 1)
            #expect(app.queues.asyncTest.queue.isEmpty)
        }
    }

    @Test func aTransientFailureIsRetried() async throws {
        let sender = RecordingEmailSender(failures: 2)
        try await withApp(sender: sender) { app in
            let payload = WelcomeEmail(memberID: UUID(), email: "ada@example.com", name: "Ada")
            try await app.queues.queue.dispatch(WelcomeEmailJob.self, payload, maxRetryCount: 3)
            try await app.queues.queue.worker.run()

            #expect(await sender.attempts == 3)
            #expect(await sender.sent.count == 1)
            #expect(await app.jobStats.dequeued == 3)
            #expect(await app.jobStats.succeeded == 1)
            #expect(await app.jobStats.failed == 0)
        }
    }

    @Test func delayedJobsAtTheFrontBlockReadyJobs() async throws {
        let sender = RecordingEmailSender()
        try await withApp(sender: sender) { app in
            let later = Date(timeIntervalSinceNow: 3600)
            for n in 1...3 {
                try await app.queues.queue.dispatch(
                    LoanReminderJob.self,
                    LoanReminder(loanID: UUID(), email: "d\(n)@example.com", title: "Later"),
                    delayUntil: later)
            }
            try await app.queues.queue.dispatch(
                LoanReminderJob.self,
                LoanReminder(loanID: UUID(), email: "ready@example.com", title: "Now"))

            var passes = 0
            while await sender.sent.isEmpty {
                passes += 1
                try await app.queues.queue.worker.run()
            }
            print("the ready job ran on pass \(passes)")
            #expect(passes == 4)
        }
    }
}
----

Source: https://github.com/vapor/queues/blob/1.18.0/Sources/XCTQueues/TestQueueDriver.swift[vapor/queues 1.18.0:
TestQueueDriver.swift], https://docs.vapor.codes/advanced/testing/[Vapor docs: Testing]

== Deployment shapes

A typical Compose file runs the same image three ways, differing in the arguments (the template's Dockerfile makes the
binary the
entrypoint, so `command` holds only the arguments). This file was not run (no Docker daemon was available); it follows
the template's
own `docker-compose.yml`:

[source,yaml]
----
x-shared_environment: &shared_environment
  LOG_LEVEL: ${LOG_LEVEL:-info}
  REDIS_URL: redis://redis:6379

services:
  app:
    image: bookshelf:latest
    environment:
      <<: *shared_environment
    ports:
      - '8080:8080'
    command: ["serve", "--env", "production", "--hostname", "0.0.0.0", "--port", "8080"]
  worker-emails:
    image: bookshelf:latest
    environment:
      <<: *shared_environment
    command: ["queues", "--queue", "emails"]
  worker-reminders:
    image: bookshelf:latest
    environment:
      <<: *shared_environment
    command: ["queues", "--queue", "reminders"]
  redis:
    image: redis:7
    command: ["redis-server", "--appendonly", "yes"]
----

The same split maps onto Kubernetes as one Deployment per command. Practical points:

* *Scale workers by queue depth, not by CPU.* Add replicas of `worker-emails` when the e-mail backlog grows; each
  replica runs
  `workerCount` workers.
* *Persist Redis.* Jobs live only in Redis: without persistence (`--appendonly yes`, or a managed service with
  persistence), a restart
  empties the queue. With the Fluent driver they live in the database.
* *Protect Redis.* Anyone who can reach it can read every payload and enqueue jobs of any registered type. Use a
  password and TLS
  (`rediss://`), keep it on a private network, and see xref:backend/vapor/security-hardening.adoc[Security Hardening].
* *One scheduler.* If you also run scheduled jobs, run exactly one process with `--scheduled`, or every replica fires
  every schedule;
  the xref:backend/vapor/scheduled-jobs.adoc[Scheduled Jobs] page covers it.
* *Give workers their own readiness story.* A worker has no HTTP port. Use the process state, or expose a probe from a
  small `serve`
  alongside it; deployment of Vapor in general is covered by xref:backend/vapor/deployment-with-docker.adoc[Deployment
  with Docker] and
  xref:backend/vapor/deployment-targets.adoc[Deployment Targets].

== Common errors

[cols="3,4",options="header"]
|===
|Symptom |Cause and fix
|`+Fatal error: No Queues driver configured. Configure with app.queues.use(...)+` |`app.queues.queue`, `req.queue` or a worker was used before a driver was selected (or in a test that skipped `.asyncTest`). Call `+app.queues.use(...)+` in `configure`.
|Jobs are dispatched but never run |No worker is running for that queue: start `swift run App queues --queue <name>` for each queue, or `startInProcessJobs`.
|`+No job with the desired name is registered, discarding+` in the worker log |The job type was never passed to `app.queues.add` in the *worker* process, or its `name` changed since the job was queued. Pin `static var name`.
|`Job type is already registered` (warning) |`app.queues.add` was called twice for the same name; the second replaces the first.
|`+Job run failed [error: RediStack.RedisConnectionPoolError(... timedOutWaitingForConnection)]+` repeated, with `failed to create connection for pool [error: connection reset (error set): Connection refused) (errno: 61)` |Observed with `REDIS_URL=redis://127.0.0.1:6390` and nothing listening. The worker keeps retrying every `refreshInterval`; fix the address or start Redis. In a web process the same condition fails `dispatch` with the pool error.
|A `500` from a handler when dispatching |The driver is down (above), or the payload failed to encode: `dispatch` rethrows the driver's or the encoder's error.
|`NoSuchJobError` (test driver) or a `missingJob` error (Redis driver) from `worker.run()` or in the worker log |An id is in the queue whose data is gone: the same custom `id` was dispatched twice, or the data key was deleted.
|compile error `+type '...' does not conform to the 'Sendable' protocol+` on a job |The payload (or the job) holds a non-`Sendable` type. Make the payload a struct of `Sendable` values.
|compile error `+type '...' does not conform to protocol 'Job'+` |The payload is not `Codable`. Conform it, or implement `serializePayload` and `parsePayload`.
|Delayed jobs run late, ready jobs wait behind them |See <<_delayed_jobs_and_the_head_of_the_queue>>.
|A job runs twice |Retry after a partial success, or an operator requeue: make the job idempotent.
|The same job runs on every web replica's worker |Workers are meant to share one queue; if work is duplicated, check that the queue key (`persistenceKey`) and the queue name are the same on all and that the jobs are not also scheduled in several places.
|===

== Version notes

* *Vapor 3 to 4*: this page documents the Vapor 4 API (`app.queues`, `req.queue`, `QueueContext`); the Vapor 3 job API
  was not
  checked. When `AsyncJob` and the async `dispatch` were added to 1.x was not checked.
* *`queues` 1.18.0* needs Vapor 4.104.0 or later; `queues-redis-driver` 1.1.2 is from September 2024, so the Redis
  driver changes
  slowly, and the processing-list behaviour above is what ships today.
* *Vapor 5* (5.0.0-beta.4, not generally available): I found no Vapor 5 release or branch of `vapor/queues` (its default
  branch
  is the 1.x line and its manifest requires Vapor 4), so treat Queues on Vapor 5 as unconfirmed and check the package
  before
  planning a Vapor 5 migration. `vapor/redis` has a 5.0.0-alpha.2.2 tag and a `v5-dev` branch that were not verified
  here. Code that
  uses only `AsyncJob`, `req.queue.dispatch` and `QueueContext` will be the easiest to move.
* *Swift 6*: `AnyJob` and `Payload` are `Sendable` in 1.18.0, which is what gives the diagnostics shown above; the
  delegate protocol
  is `Sendable` too.

== Where the books are outdated

* None of the three books in this section's bibliography covers a job queue: the section's concept table maps no chapter
  to
  `vapor/queues`, and the Kodeco book's transactional e-mail chapter (Condon et al., chapter 24, written for Vapor 3 and
  futures) is
  the nearest topic. The advice there to send an e-mail is correct in intent; today the send belongs in an `AsyncJob`,
  dispatched
  from the handler with `req.queue.dispatch`, with the retry and idempotency rules of this page.
* Anything in the books built on Vapor 3 services (`Config`, `Services`, `req.make`) has no counterpart here: Queues is
  configured
  through `app.queues` and reached through `req.queue`.
* Yeung and Patel (Packt) predate Vapor 4 (Vapor 3 and Vapor 2); for background work, use the pattern on this page
  rather than a
  detached `DispatchQueue` or an unstructured `Task` started from a handler.
