Most services that need this page arrive from one of four places: a Hystrix command that still runs in production, a
Resilience4j 1.x dependency that was never upgraded, a Spring Boot 2 or 3 application that is moving to Boot 4, or a
`@Retryable` method that is still on the archived Spring Retry project. Each has a section below with a mapping table, a
before and after example and the traps found while running it. The page ends with the list of places where the official
readme.io documentation disagrees with the code, collected from the whole section so that you can see them in one place.

The page was written against Resilience4j 2.4.0, Spring Boot 4.1.x (4.1.1), Spring Framework 7.0.x (7.0.9) and Java 21,
and every example was compiled and run on exactly those versions on 4 October 2026. Where the old stack is shown it is the
version that was current for it: Hystrix 1.5.18, Spring Boot 2.7.18 with Resilience4j 2.3.0, Spring Boot 3.5.16 with
Resilience4j 2.4.0, and Spring Retry 2.0.13. The vocabulary (breaker, bulkhead, retry storm) is in
xref:backend/springboot/resilience/resilience-fundamentals.adoc[Resilience Fundamentals].

The order matters. Hystrix and Resilience4j 1.x are *library* migrations that you can do on the Spring Boot version you

== Hystrix to Resilience4j

*Hystrix* is in maintenance mode, with 1.5.18 as its last release, and its Spring integration (Spring Cloud Netflix
Hystrix) is not part of the current Spring Cloud release train, whose circuit breaker support is
xref:backend/springboot/resilience/spring-cloud-circuitbreaker.adoc[Spring Cloud CircuitBreaker]. The history and the design
differences are in xref:backend/springboot/resilience/resilience-fundamentals.adoc[Resilience Fundamentals]; this section is
the mapping. The mapping is conceptual first: Hystrix is one command object that bundles a circuit breaker, an isolation
strategy, a timeout and a fallback, and Resilience4j is five separate decorators that you combine.

=== Concepts

[cols="3,4,4",options="header"]
|===
|Hystrix |Resilience4j |Where it is covered

|A decorated function or an annotated method. `run()` is the body of the method, or the `Supplier` that you decorate.
|xref:backend/springboot/resilience/programmatic-usage.adoc[Programmatic Usage], xref:backend/springboot/resilience/annotations-and-aspect-order.adoc[Annotations & Aspect Order]

|`@CircuitBreaker`, `@Retry`, `@RateLimiter`, `@Bulkhead` and `@TimeLimiter` on the method, each with its own `name`

|The *instance name*: one `CircuitBreaker` per remote dependency, created from `resilience4j.circuitbreaker.instances.<name>`
|xref:backend/springboot/resilience/registries-configuration-and-decorators.adoc[Registries, Configuration & Decorators]

|A `ThreadPoolBulkhead` (`@Bulkhead(type = THREADPOOL)`), plus a `TimeLimiter` for the timeout

The defaults are not the same, and that is where a migration changes behaviour without anyone touching the code. A Hystrix
circuit with 20 requests in ten seconds is a Resilience4j breaker that, left on its defaults, needs 100 calls and stays open
for 60 seconds. Set the Hystrix values explicitly to keep the old behaviour, as the example does, and then decide what you
really want.

=== Behavioural differences that bite

* *Fallbacks.* Hystrix runs the fallback on any failure, a timeout or a rejection. Resilience4j runs the
  `fallbackMethod` of *each annotation* when that decorator throws, so a fallback on the inner decorator hides the failure
  from the outer one. See xref:backend/springboot/resilience/fallbacks-and-composition.adoc[Fallbacks & Composition].
* *Timeouts need a future.* There is no blocking-method timeout in `@TimeLimiter`; a Hystrix command timed out a blocking
  call by running it on another thread, and Resilience4j gives that to the thread-pool bulkhead plus the time limiter.
* *Half-open.* Hystrix lets one request through after the sleep window; Resilience4j lets
  `permittedNumberOfCallsInHalfOpenState` calls through (10 by default) and compares their failure rate with the threshold.
* *Slow calls.* A Resilience4j breaker can open on slow calls (`slowCallDurationThreshold`, default 60 s) even when nothing
  fails; Hystrix reacts only to errors and timeouts.
* *Nothing is global.* There is no `hystrix.command.default` that every call inherits unless you define
  `configs.default`, and an instance name that is not configured takes `configs.default`, not Resilience4j's built-in
  defaults (see xref:backend/springboot/resilience/spring-boot-configuration.adoc[Spring Boot Configuration]).
* *Metrics changed names.* The Hystrix stream and the Hystrix dashboard have no counterpart; the meters and endpoints are in
  xref:backend/springboot/resilience/observability.adoc[Observability].

=== The Bookshelf pricing call, before and after

The first block is a Hystrix command with the values of the table set explicitly. The second is the Resilience4j version of
the same dependency protection: one annotated method, with the breaker and a semaphore bulkhead, and the configuration in
YAML. Both were run against a gateway that fails every call.

.Before: a Hystrix command (Hystrix 1.5.18)
[source,java]
----
package com.example.bookshelf;

class PriceCommand extends HystrixCommand<Long> {
    private final String isbn;

    PriceCommand(String isbn) {
        super(Setter.withGroupKey(HystrixCommandGroupKey.Factory.asKey("pricing"))
            .andCommandKey(HystrixCommandKey.Factory.asKey("price"))
            .andCommandPropertiesDefaults(HystrixCommandProperties.Setter()
                .withExecutionIsolationStrategy(HystrixCommandProperties.ExecutionIsolationStrategy.SEMAPHORE)
                .withExecutionIsolationSemaphoreMaxConcurrentRequests(10)
                .withExecutionTimeoutInMilliseconds(1000)
                .withCircuitBreakerRequestVolumeThreshold(20)
                .withCircuitBreakerErrorThresholdPercentage(50)
                .withCircuitBreakerSleepWindowInMilliseconds(5000)
                .withMetricsRollingStatisticalWindowInMilliseconds(10000)));
        this.isbn = isbn;
    }

    @Override protected Long run() { return pricing.priceCents(isbn); }

    @Override protected Long getFallback() { return 0L; }
}

long cents = new PriceCommand("978-0-13-468599-1").execute();
----

Source: https://github.com/Netflix/Hystrix/wiki/Configuration[Hystrix: Configuration] and the `HystrixCommand` API of 1.5.18.
Run: the first call returned the fallback `0`; after 20 failed calls `isCircuitBreakerOpen()` was `true`, the next call was
short-circuited, and the backend had been invoked 21 times in total.

.After: an annotated method (Resilience4j 2.4.0)
[source,java]
----
package com.example.bookshelf;

import io.github.resilience4j.bulkhead.annotation.Bulkhead;
import io.github.resilience4j.circuitbreaker.annotation.CircuitBreaker;
import org.springframework.stereotype.Service;

@Service
public class PricingService {
    private final PricingGateway gateway;

    public PricingService(PricingGateway gateway) {
        this.gateway = gateway;
    }

    @CircuitBreaker(name = "pricing", fallbackMethod = "noPrice")
    @Bulkhead(name = "pricing")
    public long priceCents(String isbn) {
        return gateway.priceCents(isbn);
    }

    long noPrice(String isbn, Throwable cause) {
        return 0L;
    }
}
----

.After: the Hystrix values as Resilience4j properties
[source,yaml]
----
resilience4j:
  circuitbreaker:
    instances:
      pricing:
        failureRateThreshold: 50        # errorThresholdPercentage
        minimumNumberOfCalls: 20        # requestVolumeThreshold
        slidingWindowType: TIME_BASED   # rollingStats.timeInMilliseconds
        slidingWindowSize: 10           # seconds
        waitDurationInOpenState: 5s     # sleepWindowInMilliseconds
  bulkhead:
    instances:
      pricing:
        maxConcurrentCalls: 10          # semaphore maxConcurrentRequests
----

Source: https://resilience4j.readme.io/docs/getting-started-3[Resilience4j: Spring Boot 2 & 3] for the annotations and the
property names, checked against the v2.4.0 `CircuitBreakerConfigurationProperties` and `BulkheadConfigurationProperties`.
Run on Spring Boot 4.1.1: the first call returned the fallback `0`, after 20 failed calls the breaker was `OPEN` with a
failure rate of 100.0 and the backend had been invoked 20 times, and the next call returned the fallback without invoking
the backend. A second test read the configuration back (20 calls, 50 percent, `TIME_BASED`, a window of 10, 10 permitted
half-open calls, 10 concurrent calls). Note that the half-open value stayed at the Resilience4j default of 10, as the table says.

The timeout is the part that moved: Hystrix applied `executionTimeoutInMilliseconds` to every command, and the annotated
method above has none. Put the timeout on the HTTP client (`spring.http.clients.connect-timeout` and `read-timeout` on Spring
Boot 4), or make the method return a `CompletionStage` and add `@TimeLimiter`; both are shown in
xref:backend/springboot/resilience/time-limiter.adoc[TimeLimiter].

== Resilience4j 1.x to 2.x

Resilience4j 2.0.0 was a deliberate break; its release notes list four things: Vavr removed as a dependency, Java 17 as the
baseline, Kotlin 1.7.20 and Spring Boot 2.7. 2.0.1 added Spring Boot 3 and removed the deprecated configuration keys.

[cols="3,5,4",options="header"]
|===
|Change |What to do |Version

|*Java 17 baseline*
|Build and run on Java 17 or later. The 2.4.0 jars read back as class-file major version 61, which is Java 17, so Java 21
and virtual threads are fine, and Java 11 and 8 are not.
|2.0.0

|*Vavr removed from the core modules*
|Remove `io.vavr` imports from the decorator code. `Try` and `Function1` based helpers are gone; the checked function types
are in `io.github.resilience4j.core.functions` (`CheckedFunction`, `CheckedSupplier`, `Either`). Use plain `try`/`catch`,
`Optional` or the `Decorators` builder. An optional `resilience4j-vavr` module is still listed in the 2.4.0 BOM for code
that wants Vavr types.
|2.0.0

|`ringBufferSizeInClosedState` removed
|Use `slidingWindowSize`
|2.0.1

|`ringBufferSizeInHalfOpenState` removed
|Use `permittedNumberOfCallsInHalfOpenState`
|2.0.1

|Retry `maxRetryAttempts` removed
|Use `maxAttempts` (it counts the first call too)
|2.0.1

|Bulkhead `contextPropagator` (list) removed
|Use `contextPropagators`
|2.0.1

|`resilience4j-spring-boot3` and `resilience4j-spring6` added
|Use them for Spring Boot 3 and Spring Framework 6
|2.0.1

|`recordResultPredicate` configurable from Boot properties
|Available from YAML
|2.1.0

|Apache Commons Configuration registries
|`resilience4j-commons-configuration`
|2.2.0
|===

Source: https://github.com/resilience4j/resilience4j/blob/v2.4.0/RELEASENOTES.adoc[`RELEASENOTES.adoc` at v2.4.0], sections 2.0.0, 2.0.1,
2.1.0 and 2.2.0, and the bytecode version of the 2.4.0 jars.

== Spring Retry to Spring Framework 7

*Spring Retry* (`org.springframework.retry:spring-retry`) is archived at
https://github.com/spring-attic/spring-retry[spring-attic/spring-retry]; the last release is 2.0.13 (8 June 2026). Spring
Framework 7 replaced its core with `@Retryable`, `@EnableResilientMethods`, `RetryTemplate` and `RetryPolicy`.
Spring Boot 3.5.16 still manages Spring Retry 2.0.13, Spring Boot 4.1.1 no longer does, and Framework 6.2 has no native
API at all, so this migration belongs to the Boot 4 step. The complete attribute-by-attribute table, the behaviour of
`RetryTemplate`, `RetryListener` and `MethodRetryEvent`, and the comparison with Resilience4j are in
xref:backend/springboot/resilience/spring-framework-native-resilience.adoc[Spring Framework Native Resilience]; this is the part
you need to start.

[cols="3,3,5",options="header"]
|===
|Spring Retry |Spring Framework 7 |What to watch

|`@EnableRetry`
|`@EnableResilientMethods`
|Without it, `@Retryable` is a silent no-op on Boot 4.1.1: nothing enables it automatically.

|`maxAttempts = 3` (total invocations)
|`maxRetries = 2` (retries after the first call)
|The default of 3 is 3 invocations in Spring Retry and 4 in the Framework.

|`retryFor`, `noRetryFor`
|`includes`, `excludes`
|Empty means every exception in both.

|`@Backoff(delay, multiplier, maxDelay)`
|`delay`, `multiplier`, `maxDelay` on the annotation
|Default fixed one second in both; the multiplier of 1.0 is fixed.

|`@Backoff(random = true)`
|`jitter`
|The Framework jitter is an absolute duration added to the delay.

|`@Recover`
|nothing
|Catch the exception at the call site, or use a Resilience4j `fallbackMethod`. The Framework rethrows the original exception.

|`RetryTemplate.execute(callback, recoveryCallback)`
|`RetryTemplate.invoke(...)` or `execute(Retryable)`
|`execute` always throws `RetryException` on failure; `invoke` rethrows the original.

|`@CircuitBreaker`, `stateful = true`
|nothing in core
|Resilience4j `CircuitBreaker`, or the Framework Retry implementation of Spring Cloud CircuitBreaker.
|===

Source: https://github.com/spring-attic/spring-retry[Spring Retry (archived)] and the
https://docs.spring.io/spring-framework/reference/core/resilience.html[Spring Framework reference: Resilience features].
The full table was checked against the Spring Retry 2.0.13 and Spring Framework 7.0.9 sources, and the two annotations below
were run again for this page.

.The same retry before and after
[source,java]
----
// Spring Retry 2.0.13: three invocations in total, then @Recover answers
@Configuration
@EnableRetry
class OldConfig { }

class OldCovers {
    @org.springframework.retry.annotation.Retryable(retryFor = IOException.class, maxAttempts = 3,
                                                    backoff = @Backoff(delay = 10))
    String fetch(String isbn) throws IOException { return http.fetch(isbn); }

    @Recover
    String fallback(IOException e, String isbn) { return "no-cover"; }
}

// Spring Framework 7: maxRetries = maxAttempts - 1, the recovery moves to the caller
@Configuration
@EnableResilientMethods
class NewConfig { }

class NewCovers {
    @org.springframework.resilience.annotation.Retryable(includes = IOException.class, maxRetries = 2, delay = 10)
    String fetch(String isbn) throws IOException { return http.fetch(isbn); }
}
----

Source: https://docs.spring.io/spring-framework/reference/core/resilience.html[Spring Framework reference: Resilience features] and
https://github.com/spring-attic/spring-retry[Spring Retry (archived)]. Run on Spring Boot 4.1.1 with `@EnableRetry` and
`@EnableResilientMethods` in the same context: each processed its own annotation, the old bean was invoked 3 times and
answered from `@Recover` with `no-cover`, and the new bean was invoked 3 times and threw the original `IOException`. Because
both can be active together, the migration can be done one bean at a time.

When a retry is the only thing you use, the Framework annotation is enough and removes a dependency. When you also need a
circuit breaker, back-off with jitter caps, a retry on a result, or metrics, move to the Resilience4j `Retry` instead, which
is described in xref:backend/springboot/resilience/retry.adoc[Retry]; do not mix both on one method, because native
`@Retryable` and Resilience4j `@Retry` multiply (3 by 3 gives 9 invocations).

|`OPEN` maps to the custom status `CIRCUIT_OPEN` (`DOWN` only with `allowHealthIndicatorToFail: true`), `HALF_OPEN` to `CIRCUIT_HALF_OPEN`; the default aggregator leaves the top-level status `UP`; the indicators are off unless `management.health.circuitbreakers.enabled` is set
|xref:backend/springboot/resilience/observability.adoc[Observability]

|Micrometer metric names
|The Micrometer page (written for 2.2.0) lists `resilience4j.circuitbreaker.max.buffered.calls` and a retry gauge with dotted kinds such as `successful.without.retry`
|`max.buffered.calls` is not registered; the retry meter is a `FunctionCounter` named `resilience4j_retry_calls_total` with underscored kinds; Micrometer 1.17 adds `_seconds_*` suffixes for timers
|xref:backend/springboot/resilience/observability.adoc[Observability]

|Grafana dashboard
|Old screenshots; the official JSON is the reference
|The JSON queries the missing `max_buffered_calls`, needs the `application` tag, and covers only the circuit breaker, retry and the semaphore bulkhead
|xref:backend/springboot/resilience/observability.adoc[Observability]

|Kotlin `TimeLimiter`
|A `TimeoutCancellationException` "rather than a `TimeoutException`"
|The extension converts it and the runs show `java.util.concurrent.TimeoutException`
|xref:backend/springboot/resilience/reactive-kotlin-and-rxjava.adoc[Reactive, Kotlin & RxJava]

== Migration pitfalls

[cols="3,4,4",options="header"]
|===
|Mistake |What you see |Fix

|Migrating to Boot 4 with `spring-boot-starter-aop`
|The application starts; `@CircuitBreaker` and `@Retry` do nothing
|Use `spring-boot-starter-aspectj`

|`resilience4j-spring-boot3` on Boot 4
|"Module 'io.github.resilience4j:resilience4j-spring-boot3' is only compatible with Spring Boot 3.x"
|Use `resilience4j-spring-boot4`; with Spring Cloud CircuitBreaker 5.0.3, exclude the Boot 3 starter and import the BOM first

|Importing the BOM and leaving the starter without a version
|`'dependencies.dependency.version' ... is missing`
|Pin `resilience4j-spring-boot4` (and `-hedge`) with `${resilience4j.version}`

|Keeping the 1.x keys
|The breaker uses 100 calls and a window of 100; no error
|Rename to `slidingWindowSize`, `permittedNumberOfCallsInHalfOpenState`, `maxAttempts`, `contextPropagators`

|Copying Hystrix numbers without setting them
|The breaker needs 100 calls and stays open for 60 seconds
|Set `minimumNumberOfCalls`, `waitDurationInOpenState` and the window explicitly

|`@Retryable` without `@EnableResilientMethods` on Boot 4
|No retry, no error
|Add the annotation, or use Resilience4j `@Retry`

|`maxAttempts = 3` copied to `maxRetries = 3`
|Four invocations instead of three
|`maxRetries = maxAttempts - 1`

|Native `@Retryable` and Resilience4j `@Retry` on one method
|Three times three, nine invocations
|Use one retry layer per call

|Trusting the readme.io aspect-order sentence
|The breaker records one failure per retried call instead of three
|Follow `Ordered`: lower is outer, and leave the defaults when you want Retry outside the breaker
|===
