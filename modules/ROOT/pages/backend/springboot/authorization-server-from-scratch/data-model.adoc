= Authorization Server from Scratch: Data Model and Schema
:description: The PostgreSQL schema of the irurueta-auth-server example after its walking skeleton: users, authorities and passwords, the three Spring Authorization Server tables, the Flyway migration layout and version ranges, and the tables that later pages add.
:keywords: Flyway, PostgreSQL, schema, migrations, V100, V101, users, user_authorities, user_passwords, oauth2_registered_client, oauth2_authorization, oauth2_authorization_consent, Spring Authorization Server, JDBC, entity relationship diagram, erDiagram, classpath:db/migration, Spring Session JDBC

include::partial$springboot-disclaimer.adoc[]

`auth-server` keeps its state in PostgreSQL, and every table is created by a Flyway migration, never by the
framework. This page covers the tables that exist after the example's walking skeleton: three *custom* tables for
the users, and the three tables that *Spring Authorization Server* defines for registered clients, authorizations and
consents. Later pages add the rest, and the last section lists them. The two databases of the
xref:backend/springboot/authorization-server-from-scratch/architecture.adoc[architecture] are separate: the
authorization server owns the `authserver` database and the BFF owns the `bff` database.

== Entity relationship diagram

A solid line is a real foreign key declared in a migration. A dashed line is a *logical link with no foreign key*:
Spring Authorization Server copies a client id or a principal name into its tables by value, so deleting a user or a
client does not cascade to those rows. Entities marked *custom* are defined by this project; entities marked
*Spring* use the schema of the framework.

[mermaid]
....

The shape of the three custom tables follows the schema that Spring Security documents for JDBC authentication, split
so a user without a password (for example one that only signs in with a passkey, added by a later page) is just a
user with no row in `user_passwords`.

----

These tables derive from the schema in https://docs.spring.io/spring-security/reference/servlet/authentication/passwords/jdbc.html[the JDBC authentication section of the Spring Security reference], with the password moved to a table of its own.

The `users` table is the account:

[cols="2,2,3",options="header"]
|===
|Column
|Type
|Notes

|`id`
|`uuid`
|Primary key, generated by the application.

|`username`
|`varchar(100)`
|Not null, unique (`uq_users_username`). The principal name that Spring Authorization Server stores in its tables.

|`enabled`
|`boolean`
|Not null, default `TRUE`. A disabled account cannot sign in.

|`created_at`, `updated_at`
|`timestamp with time zone`
|Not null, default the current timestamp.
|===

The `user_authorities` table holds one row per granted authority:

[cols="2,2,3",options="header"]
|===
|Column
|Type
|Notes

|`user_id`
|`uuid`
|Part of the primary key. Foreign key to `users(id)` with `ON DELETE CASCADE`.

|`authority`
|`varchar(100)`
|Part of the primary key. A role or authority name.
|===

The `user_passwords` table holds the encoded password, one row per user:

[cols="2,2,3",options="header"]
|===
|Column
|Type
|Notes

|`user_id`
|`uuid`
|Primary key. Foreign key to `users(id)` with `ON DELETE CASCADE`.

|`encoded_password`
|`varchar(255)`
|Not null. The output of a `PasswordEncoder`, never a clear text password.

|`updated_at`
|`timestamp with time zone`
|Not null, default the current timestamp.
|===

== Flyway layout

Flyway runs at application start (`spring.flyway.enabled: true`) and reads the scripts from `classpath:db/migration`,
so each migration lives in the `src/main/resources/db/migration` folder of the module that owns the data. Each
application has its own database and its own migrations, and `flyway-database-postgresql` provides the PostgreSQL
support:

[cols="2,3,2",options="header"]
|===
|Database
|Module and folder
|Versions

|`authserver`
|`auth-server/infrastructure/persistence`, `src/main/resources/db/migration`
|`V100` to `V899`

|`bff`
|`bff/infrastructure/session`, `src/main/resources/db/migration`
|`V300`
|===

Inside the authorization server each code issue owns a range of version numbers, so features developed in parallel
never collide, and a migration is never written outside the range of the issue that adds it:

[cols="1,3,3",options="header"]
|===
|Range
|Owner
|Content

|`V1xx`
|Walking skeleton (issue 1)
|The Spring Authorization Server tables (`V100`) and the users, authorities and passwords (`V101`).

|`V2xx`
|Credentials and token core (issue 2)
|Account data and tokens, signing keys, refresh token reuse detection.

|`V3xx`
|Login pages and BFF (issue 3)
|The Spring Session tables, in the `bff` database.

|`V4xx`
|Multi-factor authentication (issue 4)
|Security events, second factor lockout, TOTP, recovery codes and trusted devices.

|`V5xx`
|Passkeys (issue 5)
|Spring Security's WebAuthn tables.

|`V6xx`
|One-time tokens and SMS (issue 6)
|Magic-link tokens, e-mail and SMS codes, phone numbers and the SMS cost ledger.

|`V7xx`
|Social login, X.509 and the device grant (issue 7)
|Linked external identities, generated passwords and certificate bindings.

|`V8xx`
|Client authentication, token exchange and PAR (issue 8)
|Used client assertion identifiers.
|===

The issue numbers are those of the example repository. See
https://docs.spring.io/spring-boot/how-to/data-initialization.html#howto.data-initialization.migration-tool.flyway[the Spring Boot Flyway how-to] for the properties used above.
