== What you build

A client is the application that asks the authorization server for tokens. This page builds the part of the
example that decides *which* clients exist and *how* each one may behave: a small set of clients seeded at start-up,
an administration REST API to create, change, rotate and delete clients, and, optionally, the OpenID Connect dynamic
client registration endpoint. The protocol theory (what a client is, public versus confidential clients, client
authentication methods) lives in the OAuth Reference, in
xref:backend/oauth/client-credentials-and-client-authentication.adoc[Client Credentials and Client Authentication]
and in xref:backend/oauth/discovery-metadata-and-client-registration.adoc[Discovery, Metadata and Client Registration].
For the framework's own description of the model see the
xref:backend/springboot/spring-security-authorization-server.adoc#_registered_clients[Registered Clients] section of
the Spring Security Authorization Server guide.

The design has three layers, in line with the hexagonal layout of the
xref:backend/springboot/authorization-server-from-scratch/architecture.adoc[architecture] page:

* The *domain* record `ClientRegistration` holds the definition of a client in plain Java and validates it (a public
  client must require PKCE, `tls_client_auth` needs a subject DN, `private_key_jwt` needs a JWK set).
* The *application* layer creates and seeds clients (`CreateClientUseCase`, `SeedRegisteredClientsUseCase`) through a
  repository port. It never sees a Spring Security type.
* The *persistence* adapter maps a `ClientRegistration` to Spring's `RegisteredClient` (`RegisteredClientMapper`) and
  stores it with `JdbcRegisteredClientRepository` in the `oauth2_registered_client` table described in
  xref:backend/springboot/authorization-server-from-scratch/data-model.adoc[Data Model and Schema].

== How it works

An administrator calls the REST API with a bearer token that has the `admin` scope and the API audience. The use
case refuses the implicit grant and an already used client id, generates a secret only for clients that use a
`client_secret_*` authentication method, stores it *encoded*, and returns the clear text exactly once.

[mermaid]
....
sequenceDiagram
    autonumber
    actor A as Administrator
    participant API as ApiSecurityConfig (/api/**)
    participant UC as CreateClientUseCase
    participant H as PasswordHasher
    participant R as ClientRegistrationRepository
    participant M as RegisteredClientMapper
    participant J as JdbcRegisteredClientRepository
    A->>API: POST /api/admin/clients (Bearer, scope admin)
    API->>API: validate signature, issuer, expiry and audience
    API->>UC: execute(ClientRegistration)
    UC->>UC: refuse the implicit grant
    UC->>R: findByClientId(clientId)
    R-->>UC: empty, or ClientAlreadyExistsException (409)
    alt client uses client_secret_basic or client_secret_post
        UC->>UC: generate secret
        UC->>H: encode(secret)
        H-->>UC: encoded secret
    end
    UC->>R: save(registration, encoded secret or null)
    R->>M: toRegisteredClient(registration, id, issuedAt, secret)
    M-->>R: RegisteredClient
    R->>J: save(registeredClient)
    UC-->>A: 201 with the client and the clear secret, once
....

At start-up a second path creates the default clients: `ClientSeeder` (an `ApplicationRunner`) builds the
definitions of `DefaultClientDefinitions` for every client whose redirect URIs are configured, and
`SeedRegisteredClientsUseCase` stores the ones that do not exist yet. Running it again changes nothing.

Three points are worth noticing:

* A client is seeded *only* when its redirect URIs are configured. Nothing is seeded by default, and no `localhost`
  URI exists outside the `dev` profile, so a fresh deployment starts with no usable client.
* The secret of the confidential client comes from the environment and never from the source. The seed tag below
  shows definitions, not values.
* The `dev` profile adds a `device-client` (public, device authorization grant) and a demo user through
  `DevDataInitializer`. It is a local development convenience and is inert without that profile.

The table of token lifetimes and formats is used again on
xref:backend/springboot/authorization-server-from-scratch/access-refresh-and-id-tokens.adoc[Access, Refresh & ID Tokens].

== Data

Clients live in the `oauth2_registered_client` table, whose columns (`client_authentication_methods`,
`authorization_grant_types`, `redirect_uris`, `scopes`, `client_settings`, `token_settings`) are the schema that
Spring defines. The settings columns hold JSON. The project's own additions (`audiences`, `mfa_required`, the registered
JWK set) are stored as custom keys *inside* `client_settings`, so no migration was needed. The full table is on the
xref:backend/springboot/authorization-server-from-scratch/data-model.adoc[data model] page.

== API

The administration API lives under `/api/admin/clients`. It is served by the stateless `/api/**` chain: the bearer
token must be issued by this server, list the API audience and carry the `admin` scope. A token issued only for the
resource server is refused with `401`, and a valid token without the scope with `403`. The examples assume a token in
`$ADMIN_TOKEN` and the server on its development port.

Create a confidential client. The response contains the generated secret *once*:

[source,bash]
----
curl -s -X POST http://localhost:9000/api/admin/clients \
  -H "Authorization: Bearer $ADMIN_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "clientId": "reports",
    "name": "Reports service",
    "confidential": true,
    "authMethods": ["client_secret_basic"],
    "grantTypes": ["client_credentials"],
    "redirectUris": [],
    "scopes": ["documents.read"],
    "audiences": ["resource-server"],
    "accessTokenTtl": "PT5M",
    "refreshTokenTtl": "PT1H"
  }'
----

The answer is `201` with `client` (without any secret) and `clientSecret`. A second `POST` with the same `clientId`
answers `409`; a client with the implicit grant or a `jwks` that holds a private key answers `400`.

List, read, replace and delete:

[source,bash]
----
curl -s http://localhost:9000/api/admin/clients -H "Authorization: Bearer $ADMIN_TOKEN"
curl -s http://localhost:9000/api/admin/clients/reports -H "Authorization: Bearer $ADMIN_TOKEN"
curl -s -X PUT http://localhost:9000/api/admin/clients/reports \
  -H "Authorization: Bearer $ADMIN_TOKEN" -H "Content-Type: application/json" \
  -d '{ "...": "the whole definition again; clientId must equal the path" }'
curl -s -X DELETE http://localhost:9000/api/admin/clients/reports -H "Authorization: Bearer $ADMIN_TOKEN"
----

`PUT` replaces the definition but never touches the secret, and it answers `400` when the `clientId` of the body
differs from the path. `DELETE` answers `204` and also removes the client's authorizations and consents. Unknown
clients answer `404`.

Rotate the secret of a confidential client. The old secret stops working immediately; a public client answers `400`:

[source,bash]
----
curl -s -X POST http://localhost:9000/api/admin/clients/reports/secret \
  -H "Authorization: Bearer $ADMIN_TOKEN"
----

Register a client dynamically (only when enabled). The answer contains `client_id` and `client_secret`:

[source,bash]
----
curl -s -X POST http://localhost:9000/connect/register \
  -H "Authorization: Bearer $INITIAL_ACCESS_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"client_name": "Dynamic", "redirect_uris": ["https://app.example.test/callback"], "grant_types": ["authorization_code"], "token_endpoint_auth_method": "client_secret_basic"}'
----

The request and response schemas (`ClientRequest`, `ClientResponse`, `CreatedClientResponse`, `ClientSecretResponse`)
are in the OpenAPI file of the example under `apis/auth-server/rest-server/`.

== Security notes and pitfalls

* *Exact redirect URIs.* The authorization server compares redirect URIs exactly. Never register wildcards or a
  broad prefix; an open redirect on a registered URI is how authorization codes are stolen
  (https://www.rfc-editor.org/rfc/rfc9700[RFC 9700, OAuth 2.0 Security Best Current Practice]).
* *Secrets are stored encoded.* Only the encoded secret is in `oauth2_registered_client`; the clear text is shown once
  at creation or rotation and is never logged. Losing it means rotating it.
* *Public clients need PKCE.* `ClientRegistration` refuses a public client that does not require PKCE, and both seeded
  clients require it (https://www.rfc-editor.org/rfc/rfc7636[RFC 7636]).
* *Prefer asymmetric client authentication* for high-value service clients: nothing secret is stored on the server,
  only a public JWK set.
* *Who may call the admin API.* Only a token with the `admin` scope *and* the API audience. A role alone never grants
  access, and a token issued for the resource server is useless against the administration API.
* *No implicit grant.* The API refuses it. Only an opt-in demo profile seeds such a client; see the legacy-implicit
  profile of the example.
* *Dynamic registration is off by default.* Enable it only with an initial access token that is hard to obtain, and
  review what registered clients may request. Open registration lets anyone create a client.
* *Seeding is create-only.* Changing the seed configuration after the first start does not update existing clients:
  use the API.
