== What you build

The earlier pages built the features. This page asks a different question: if you put this server in front of real users, what is already
hardened, what is only partly done, and what is missing? It is not a new feature. It is a checklist written after reading the configuration and the code
of the example, so each row says what the example *does*, not what a server should do.

The example is a teaching project and is *never deployed*. Its CI builds and tests it and nothing more. Treat the second part of this page as
the list of work a production deployment still owes, not as a statement that the example is production ready.

The reasons behind each control are in the OAuth Reference, mainly xref:backend/oauth/security-best-practices.adoc[] and
xref:backend/oauth/par-jar-and-hardened-profiles.adoc[]. This page links each row to the page of the example where the control is built.

== Checklist against RFC 9700 and OWASP ASVS

The standards are https://datatracker.ietf.org/doc/html/rfc9700[RFC 9700, Best Current Practice for OAuth 2.0 Security], the chapters of the
https://owasp.org/www-project-application-security-verification-standard/[OWASP Application Security Verification Standard] 5.0 (V3 Web Frontend Security, V6 Authentication,
V7 Session Management, V9 Self-contained Tokens, V10 OAuth and OIDC, V11 Cryptography, V12 Secure Communication, V13 Configuration, V16 Security Logging and Error Handling) and
https://pages.nist.gov/800-63-4/sp800-63b.html[NIST SP 800-63B-4]. The status column is one of *Implemented*, *Partly* or *Not implemented*.

|===
|Control
|Why
|In the example
|Standard

|TLS and HSTS
|Tokens, codes and cookies must never cross the network in clear text, and a browser should refuse to downgrade
|*Not implemented* in the application. The example listens on plain HTTP in the `dev` profile and expects TLS to end in front of it. It sets no explicit HSTS header; Spring Security's default header is written only on HTTPS requests. See xref:backend/springboot/authorization-server-from-scratch/project-setup.adoc[Project Setup]
|ASVS V12; RFC 9700 section 4.13 for TLS-terminating proxies

|Cookie attributes
|A session or device cookie that scripts can read, or that any site can overwrite, is a takeover
|*Partly.* The BFF session cookie (`+__Host-SESSION+`) and the trusted-device cookie (`+__Host-TRUSTED-DEVICE+`) are `Secure`, `HttpOnly` and `SameSite=Lax`, with the `+__Host-+` prefix. The authorization server's own session cookie keeps the container's defaults, with no explicit settings. See xref:backend/springboot/authorization-server-from-scratch/backend-for-frontend.adoc#_the_session_cookie[BFF, The session cookie]
|ASVS V3 and V7

|Content-Security-Policy and headers
|Limits what an injected script or a framing page can do on the login and consent pages
|*Implemented* for the server-rendered pages: `default-src 'self'`, `frame-ancestors 'none'`, `nosniff` and `Referrer-Policy: no-referrer`; the BFF sends `default-src 'self'; frame-ancestors 'none'`. See xref:backend/springboot/authorization-server-from-scratch/login-and-consent-pages.adoc#_security_headers_and_the_content_security_policy[Security headers and the Content-Security-Policy]
|ASVS V3

|CSRF protection
|A form post or a state-changing call made by another site with the user's cookie
|*Implemented.* The login chain keeps Spring Security's CSRF protection. The BFF uses a cookie token that the SPA echoes in `X-XSRF-TOKEN`. The `/api/**` chain turns CSRF off because it is stateless and bearer-only, and a browser never sends a bearer token by itself
|RFC 9700 section 4.7; ASVS V3

|Exact redirect URIs
|A loose match lets an attacker receive the authorization code
|*Implemented.* Spring Authorization Server compares registered redirect URIs exactly (loopback ports excepted), and the example seeds a client only when its URIs are configured, with none by default. See xref:backend/springboot/authorization-server-from-scratch/registered-clients.adoc[Registered Clients]
|RFC 9700 sections 2.1 and 4.1; ASVS V10

|PKCE
|Binds the code to the client that asked for it, and stops code injection and interception
|*Implemented.* A registration of a public client without PKCE is refused by the domain, and the authorization code flow of the examples uses `S256`. See xref:backend/springboot/authorization-server-from-scratch/registered-clients.adoc[Registered Clients]
|RFC 9700 section 2.1.1; ASVS V10

|Implicit and password grants
|Tokens in the URL, and passwords handled by clients
|*Implemented.* The framework has no password grant. The implicit flow does not exist unless the `legacy-implicit` profile is on, and a request with `response_type=token` is refused otherwise. See xref:backend/springboot/authorization-server-from-scratch/implicit-flow-legacy-and-migration.adoc[Implicit Flow: Legacy Demo & Migration]
|RFC 9700 sections 2.1.2 and 2.4

|Token lifetimes
|A stolen token is useful only until it expires
|*Implemented.* The seeded clients get 10-minute access tokens and 8-hour refresh tokens; ID tokens last 30 minutes. E-mail and SMS codes last 10 minutes (`authserver.ott.code-ttl`), magic links 15 minutes, password-reset links 30 minutes and verification links 24 hours. See xref:backend/springboot/authorization-server-from-scratch/access-refresh-and-id-tokens.adoc[Access, Refresh & ID Tokens]
|RFC 9700 section 2.2; ASVS V9

|Refresh-token rotation
|A leaked refresh token is detected the moment both parties use it
|*Implemented.* Refresh tokens are not reused, and a rotated-out token that is presented again revokes the authorization it belonged to, from the `consumed_refresh_tokens` table. See xref:backend/springboot/authorization-server-from-scratch/access-refresh-and-id-tokens.adoc[Access, Refresh & ID Tokens]
|RFC 9700 section 2.2.2

|Audience and scope restriction
|A token for one API must not work at another
|*Implemented.* Each client has audiences and scopes, the resource server and the account API validate the audience, and token exchange narrows it. Sender-constrained tokens (DPoP, mutual TLS) are available per client but not required. See xref:backend/springboot/authorization-server-from-scratch/client-credentials-and-service-to-service.adoc[Client Credentials & Service-to-Service]
|RFC 9700 sections 2.3 and 4.10

|Signing-key rotation
|A key that never changes is a key that cannot be recovered from a leak
|*Implemented.* The keys rotate every 30 days (`authserver.keys.rotation-interval`), a retired key stays published for at least two hours and as long as a token it signed can still be valid, and an administrator can rotate on demand. See xref:backend/springboot/authorization-server-from-scratch/signing-keys-jws-and-jwt.adoc#_rotating[Signing Keys, Rotating]
|ASVS V9 and V11

|Private keys at rest, KMS
|A database dump must not hand over the signing keys
|*Partly.* Private keys and TOTP secrets are encrypted with AES-GCM under a key derived from `authserver.keys.encryption.password` and `.salt`, and the application refuses to start without them. There is no KMS or HSM; the page lists the alternatives. See xref:backend/springboot/authorization-server-from-scratch/signing-keys-jws-and-jwt.adoc#_alternatives_kms_and_hsm[Signing Keys, Alternatives: KMS and HSM]
|ASVS V11 and V13

|Secret management
|Secrets in a repository or a log are public
|*Partly.* No client secret, password or key is in the repository: every secret comes from the environment, and the `dev` profile generates throwaway values. Nothing integrates with a secrets manager, so rotating a secret means a restart with a new value
|ASVS V13

|Password storage
|A leaked table of hashes should be expensive to crack
|*Implemented.* A delegating encoder that upgrades the hash on sign-in, a compromised-password check that sends only a hash prefix, a policy with a length cap. There is no pepper. See xref:backend/springboot/authorization-server-from-scratch/password-storage.adoc[Storing Passwords Securely]
|NIST SP 800-63B-4, Memorized Secrets; ASVS V6

|Rate limiting and lockout
|Online guessing of passwords, codes and e-mail addresses
|*Partly.* Bucket4j limits the account endpoints, the one-time-token endpoints, SMS sending (with cost caps) and the device user code, per client address and per identifier. A second-factor lockout counts failures per user in the database. The buckets live in the memory of one instance, and failed password sign-ins are recorded as `LOGIN_FAILURE` events but not counted into a lockout. no limiter covers `/oauth2/token`
|NIST SP 800-63B-4, Rate Limiting (Throttling); ASVS V6

|Enumeration resistance
|Telling which accounts exist is the first step of most attacks
|*Implemented.* Registration, reset request and sign-in answer alike for known and unknown identifiers, with equal work, and the one-time-token flow is covered by its own test. See xref:backend/springboot/authorization-server-from-scratch/password-storage.adoc#_security_notes_and_pitfalls[Storing Passwords Securely, Security notes]
|ASVS V6

|Phishing-resistant sign-in
|Codes can be relayed by a fake site, a passkey cannot
|*Implemented as an option.* Passkeys are a first or second factor, and a step-up demands a recent multi-factor sign-in. Nothing forces passkeys for every user. See xref:backend/springboot/authorization-server-from-scratch/passkeys.adoc[Passkeys (WebAuthn)]
|NIST SP 800-63B-4, Phishing Resistance; RFC 9470

|Audit logging
|After an incident you need to know who did what, and when
|*Partly.* The `security_events` table records sign-in success and failure, second-factor outcomes and lockouts, and changes to trusted devices, passkeys, the phone number, bound certificates, linked identities and the authenticator app. Application logs use SLF4J. Token issuance and the client and key administration API write no audit event. See xref:backend/springboot/authorization-server-from-scratch/data-model.adoc#_security_events_and_second_factor_lockout_v400[Data Model, Security events], and for the logging setup xref:backend/springboot/logging.adoc[]
|ASVS V16

|Metrics and alerting
|An attack shows first as a change in a rate
|*Not implemented.* The actuator exposes only `health` and `info`, and the application defines no meters. See xref:backend/springboot/metrics-and-observability.adoc[]
|ASVS V16
|===

== What running it for real would add

The example is built to teach one mechanism at a time. Putting it in production means closing these gaps.

=== High availability

The authorizations, consents, registered clients, signing keys, passkeys, codes and security events are all in PostgreSQL, so several instances of the
authorization server can share them. Three things are *not* shared:

* *The HTTP session of the authorization server* is in the memory of one instance (only the BFF uses Spring Session JDBC). Use Spring Session or sticky sessions, or a sign-in in progress is lost when the next request reaches another instance.
* *The rate-limit buckets* are per instance, so the effective limit grows with the number of instances. Keep the counters in a shared store.
* *The pending state of a few flows* (such as a social link waiting for confirmation) lives in the session too, and follows the first point.

Signing-key rotation is already safe with several instances: `JdbcSigningKeyRepository` takes a row lock so that two instances do not rotate at once. The other
scheduled jobs are described next.

=== Scheduled jobs and ShedLock

Four jobs clean up: expired one-time codes, phone verifications and SMS ledger entries (hourly), expired authorizations (hourly), expired account tokens (hourly) and used
client-assertion identifiers (hourly), next to the key-rotation job. They are plain `@Scheduled` methods with no distributed lock. Every instance runs each of them, which is wasteful but harmless,
because each one is an idempotent `DELETE` of expired rows. If a job later does something that must happen once (sending a digest, calling a billing API), guard it with ShedLock.
The pattern is on xref:backend/springboot/scheduling-and-shedlock.adoc[].

=== The issuer behind a proxy

The issuer is a configured value, `spring.security.oauth2.authorizationserver.issuer` (`AUTHSERVER_ISSUER_URL`), not derived from the request, so it never changes with a spoofed `Host` header.
In production it must be the public `https` URL, and so must the `authserver.mail.base-url` that goes into e-mailed links. Behind a reverse proxy also set `server.forward-headers-strategy`
so that the client address, the scheme and the host that Spring sees are the real ones: the rate limits are per client address, and every request looks like it comes from the proxy otherwise.
The X.509 feature goes the other way and refuses to start with a forwarded certificate header and a strategy that rewrites the client address, see
xref:backend/springboot/authorization-server-from-scratch/other-passwordless-methods.adoc[Other Passwordless Methods]. The Spring Boot reference describes
https://docs.spring.io/spring-boot/how-to/webserver.html#howto.webserver.use-behind-a-proxy-server[running behind a proxy server].

=== Container images and deployment

The example builds executable jars with `spring-boot-maven-plugin` and has no Dockerfile, no image build and no deployment manifest. For a real deployment you add an image per application,
configuration and secrets injected as environment variables, readiness and liveness probes on the actuator health endpoints, and a database migration step. The Docker and Kubernetes sections of this site cover those steps:
xref:backend/docker/java-and-spring-boot-images.adoc[], xref:backend/docker/image-best-practices-and-security.adoc[] and
xref:backend/docker/orchestration-swarm-and-kubernetes.adoc[], with xref:backend/docker/compose-for-local-development.adoc[] for the local services.

=== Conformance and the hardened profiles

* The *OpenID conformance suite* tests an OpenID Provider against the specification, including the certification profiles. The example has never been run against it, so its claims about
  OpenID Connect are those of Spring Authorization Server and of the tests in the repository, not a certification.
* *PAR* (RFC 9126) is in the example but off by default (`authserver.par.enabled`). A hardened deployment enables it and requires it for the clients that can use it.
* *DPoP* and *mutual TLS* sender-constrained tokens are available per client, and the resource server enforces them for bound tokens, but no client is required to use them.
  The theory and the trade-offs are on xref:backend/oauth/par-jar-and-hardened-profiles.adoc[] and xref:backend/oauth/sender-constrained-tokens-dpop-and-mtls.adoc[].

=== Things a production server also needs

* *Account recovery policy and support tooling*: a human way back in when the recovery codes are lost, with its own audit trail.
* *Backups and key escrow* that include the encryption secret of the signing keys: a restored database is useless without it.
* *Dependency and image scanning*, and a way to roll out a patched Spring release quickly. The example's CI runs static analysis and SonarCloud, not a vulnerability scan of the images.
* *Load and abuse testing*, because the password hash is deliberately expensive and a sign-in flood is a denial of service on its own. See xref:backend/springboot/performance-testing-jmeter.adoc[].
