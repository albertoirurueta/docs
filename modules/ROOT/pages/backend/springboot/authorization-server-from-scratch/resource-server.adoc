= Authorization Server from Scratch: Protecting APIs, the Resource Server
:description: The resource-server application of the irurueta-auth-server example: validating bearer JWTs (signature through JWKS, issuer, expiry, audience), mapping scope and roles claims to authorities, method security, ownership checks, DPoP and certificate-bound tokens, and the RFC 9470 step-up challenge.

include::partial$springboot-disclaimer.adoc[]

The `resource-server` application of the example (port 8081) is the smallest of the four: it owns no database, it
serves a documents API from memory and its only job is to decide, for every request, whether the bearer token in the
`Authorization` header is acceptable and what it allows. This page walks through that decision. How the tokens are
issued is the subject of the authorization server pages; the protocol background of the token itself is in
xref:backend/oauth/jwt-and-jose.adoc[JWT and JOSE] and xref:backend/oauth/access-and-refresh-tokens.adoc[Access and Refresh Tokens].

== What you build

A Spring Security *resource server* with these properties:

* It validates self-contained JWT access tokens: the signature against the authorization server's JWKS, the issuer, the
  expiry and the `aud` claim. A token without an accepted audience is refused even when its signature is valid.
* It turns the `scope` claim into `SCOPE_*` authorities and the `roles` claim into `ROLE_*` authorities.
* It protects `GET /api/documents` with the scope `documents.read` and `+DELETE /api/documents/{id}+` with the scope
  `documents.delete`, in two places (the filter chain and method security).
* It restricts every user to their own documents (ownership check), with `ROLE_ADMIN` as the only exception.
* Deleting also requires a *recent strong authentication* (RFC 9470 step-up): the token must carry an accepted `acr`
  and a recent `auth_time`, otherwise the answer is a `401` with an `insufficient_user_authentication` challenge.
* It accepts sender-constrained tokens (DPoP, RFC 9449, and certificate-bound, RFC 8705). Those mechanisms are
  explained on a later page of the guide; this page only shows the single line of configuration that enables them.
* A second filter chain, active under the `opaque` Spring profile, validates reference tokens through introspection
  instead. It is mentioned where it differs and is not listed here; see
  xref:backend/oauth/opaque-tokens-introspection-and-revocation.adoc[Opaque Tokens, Introspection and Revocation].

The generic Spring Security mechanics (the `SecurityContext` built from a JWT, `JwtDecoder`, authorities) are in
xref:backend/springboot/spring-security.adoc#_building_the_securitycontext_from_a_jwt[Building the SecurityContext from a JWT];
this page shows how the example configures them.

== How it works

The Mermaid flow below follows one `+DELETE /api/documents/{id}+` request, the most demanding one, through the chain.

[mermaid]
....
flowchart TD
    REQ["Request with Authorization: Bearer token"] --> BT{"Token present and well formed?"}
    BT -- no --> E401["401, WWW-Authenticate: Bearer (BearerTokenAuthenticationEntryPoint)"]
    BT -- yes --> SIG{"Signature valid against the JWKS of the issuer?"}
    SIG -- no --> E401I["401, error=invalid_token"]
    SIG -- yes --> CLAIMS{"iss, exp and aud accepted?"}
    CLAIMS -- no --> E401I
    CLAIMS -- yes --> CONV["JwtAuthenticationConverter: scope to SCOPE_*, roles to ROLE_*"]
    CONV --> HAS{"Has SCOPE_documents.delete?"}
    HAS -- no --> E403["403, error=insufficient_scope"]
    HAS -- yes --> STEP{"StepUpAuthorizationManager: acr accepted and auth_time recent?"}
    STEP -- no --> E401S["401, error=insufficient_user_authentication, acr_values, max_age"]
    STEP -- yes --> MS{"@PreAuthorize hasAuthority SCOPE_documents.delete"}
    MS -- no --> E403
    MS -- yes --> OWN{"DeleteDocumentUseCase: owner is the caller, or ROLE_ADMIN?"}
    OWN -- no --> E404["404, as if the document did not exist"]
    OWN -- yes --> OK["204 No Content"]
....

The signature check needs the public keys of the authorization server. Spring Boot builds the `JwtDecoder` from the
`issuer-uri` property: on the first request it reads the issuer's OpenID Connect discovery document, finds the
`jwks_uri` (`/oauth2/jwks`), downloads the keys and caches them, refetching when it meets an unknown `kid`. The
decoder validates `iss` and `exp` on its own and, because the example sets `audiences`, `aud` too. Nothing in the
example code writes a decoder: that is the reason the `JwtDecoder` bean is absent from the table below.

== Data

The resource server has no database. The documents live in memory (`resource-server/infrastructure/memory`) and the
only configuration it needs is the issuer, the accepted audience and the step-up policy, all in its `application.yml`.
The `documents` it serves are plain records with an `id`, an `owner` (the token's `sub`), a `title` and a `content`.

== Code

=== The filter chain

The chain requires a token for everything except the health endpoint and the OpenAPI document, checks the scope per
route and configures how failures are answered. The helper that declares the routes is private and is not part of the
listing; in short, `GET /api/documents` needs `SCOPE_documents.read`, `DELETE /api/documents/*` goes through the
step-up manager, and any other request only needs to be authenticated. The chain refuses to start without a configured
audience, so a missing property can never mean "accept every token".

=== Authorities from the token

The framework's default converter maps only `scope` (or `scp`) to `SCOPE_*`. The example wraps it so that the `roles`
claim of the access token also yields `ROLE_*` authorities (the prefix is added when missing). Scopes say what the
client application may do on behalf of the user; roles say who the user is, and the two are checked separately, which
is why `ROLE_ADMIN` alone never grants `documents.delete`.

=== Sender-constrained tokens

One call in the chain enables DPoP. A token bound to a key (`cnf.jkt`) is then accepted only with a matching proof,
and the framework already refuses such a token when it arrives as a plain `Bearer`. A token bound to a client
certificate (`cnf.x5t#S256`) is checked against the TLS client certificate by the validator of the decoder Spring Boot
builds. The mechanism and its threats are the subject of a later page of this guide, on sender-constrained tokens; here
it is enough to know that a stolen bound token is useless without the key or the certificate.

=== The ownership check

Scopes are coarse: `documents.delete` says the client may delete documents, not whose. The ownership rule is business
logic and lives in the use case of the application layer, not in an annotation: the caller deletes the document only
when its `owner` equals the token's subject, or when the caller is an administrator. When the rule fails the use case
returns the same result as for a missing document, which the controller turns into `404`, so the API never reveals that
someone else's document exists.

=== Step-up: the decision

`StepUpAuthorizationManager` first requires the delete authority (a caller without it gets an ordinary denial, answered
`403 insufficient_scope`). A caller that has it passes when the policy is disabled, or when the token's `acr` is one of
the configured values and its `auth_time` is not older than `max-age`. Otherwise it returns a dedicated
`StepUpRequiredDecision`, so the handler can tell this denial from any other. The claims are read from the token
attributes, which is why the same class serves JWTs and introspected opaque tokens. An `acr` is matched against the
members of the configured space-separated list, never against the list as a whole, and a missing or malformed
`auth_time` fails closed.

----

----

See https://www.rfc-editor.org/rfc/rfc9470[RFC 9470: OAuth 2.0 Step Up Authentication Challenge Protocol].

=== Step-up: the challenge

The handler turns that decision into the RFC 9470 response: `401` (not `403`, because the token is acceptable but
insufficient for this request), with the `acr_values` and `max_age` the client must ask for when it sends the user back
to the authorization server. Every other denial goes to the framework's RFC 6750 handler, which answers
`403 insufficient_scope`.

----

The policy is bound from `resourceserver.step-up.*` and validated at startup. The defaults are `urn:irurueta:acr:mfa`
and five minutes, the values also set in `application.yml`. The authorization server side of the exchange (how a
challenged client obtains the new token) is covered by the multi-factor authentication page of this guide.

== API

The contract is `resource-server-api-v1.yaml`:

[source,yaml]
----
include::irurueta-auth-server::example$apis/resource-server/rest-server/resource-server-api-v1.yaml[tag=resource-server-documents-api]
----

See the https://spec.openapis.org/oas/latest.html[OpenAPI Specification]. The following `curl` calls match it; `$TOKEN`
is an access token for the audience `resource-server` obtained through the authorization server (the BFF obtains it
for the SPA).

[source,bash]
----
# 200 with the caller's documents (scope documents.read)
curl -i -H "Authorization: Bearer $TOKEN" http://localhost:8081/api/documents

# 401 with: WWW-Authenticate: Bearer   (no token)
curl -i http://localhost:8081/api/documents

# 401 with: WWW-Authenticate: Bearer error="invalid_token"   (bad signature, expired, or wrong audience)
curl -i -H "Authorization: Bearer not-a-valid-token" http://localhost:8081/api/documents

# 403 with: WWW-Authenticate: Bearer error="insufficient_scope"   (token without documents.delete)
curl -i -X DELETE -H "Authorization: Bearer $TOKEN" http://localhost:8081/api/documents/42

# 401 with: WWW-Authenticate: Bearer error="insufficient_user_authentication",
#           acr_values="urn:irurueta:acr:mfa", max_age="300"
#   (token has documents.delete but a password-only acr, or a stale auth_time)
curl -i -X DELETE -H "Authorization: Bearer $TOKEN" http://localhost:8081/api/documents/42

# 204 (token with documents.delete, acr urn:irurueta:acr:mfa and auth_time within the last 5 minutes)
curl -i -X DELETE -H "Authorization: Bearer $STEPPED_UP_TOKEN" http://localhost:8081/api/documents/42
----

A client that receives the step-up challenge must not retry with the same token: it sends the user through the
authorization endpoint again with the advertised `acr_values` and `max_age`, then repeats the call with the new
token. The `404` for a document that is missing or owned by someone else is deliberately the same answer.

== Tests

No test of this module carries a tagged region, so none is pasted. The integration tests run the real filter chain
with JWTs signed by a key generated at run time (never committed):

* `SecurityConfigIT` covers the validation matrix: no token, an invalid token, an accepted audience, another audience
  and no audience at all, the read and delete scopes, the ownership rules (own document, someone else's, an
  administrator), and the step-up cases (password `acr`, missing claims, old `auth_time`).
* `StepUpDeletionIT` follows the whole story a user goes through: a password-only token is challenged, the same user
  with a multi-factor token and a recent `auth_time` deletes the document, and a stale multi-factor authentication is
  challenged again.
* `BoundTokenIT` runs over a real TLS handshake and proves that certificate-bound and DPoP-bound tokens are accepted
  only with their certificate or proof, and that a DPoP token sent as a plain bearer is refused.
* `OpaqueTokenSecurityIT` does the same for the `opaque` profile against a stub introspection endpoint.
* `OpenApiDriftIT` fails when the running API drifts from the OpenAPI contract, and unit tests such as
  `StepUpAuthorizationManagerTest` and `StepUpAccessDeniedHandlerTest` cover the step-up classes in isolation.

== Security notes and pitfalls

* *Always check the audience.* A signature proves who issued the token, not for whom. Without an `aud` check, a token
  issued for another API of the same issuer works here. The chain refuses to start when no audience is configured, and
  the integration tests cover a token with another audience and with none. See
  https://www.rfc-editor.org/rfc/rfc8725[RFC 8725, JWT Best Current Practices].
* *Clock skew.* `exp` and `nbf` are checked with the framework's default tolerance of sixty seconds. Keep the clocks of
  the servers synchronised rather than widening it, and keep access token lifetimes short, because a JWT cannot be
  revoked before it expires (use reference tokens when you need that).
* *JWKS caching.* The decoder caches the keys and refetches when it meets an unknown `kid`, which is what makes key
  rotation work without a restart. The authorization server publishes the retired key during an overlap window, as
  explained on the signing keys page. A resource server that pins one key breaks at the first rotation.
* *The issuer must be exactly what the tokens say.* `issuer-uri` is both where the discovery document is read from and
  the value `iss` must have. A mismatch (a trailing slash, another host name) makes every token invalid.
* *Do not authorize by role alone.* Use scopes for what the client may do and ownership checks for whose data it is;
  `ROLE_ADMIN` widens the ownership check and nothing else.
* *Do not leak existence.* Answering `404` for someone else's document avoids an enumeration oracle that `403` would
  create.
* *Step-up needs a fresh claim, not a remembered one.* The rule compares `auth_time` with the clock on every request,
  so an old token cannot be reused after the window. Keep `max-age` as short as the operation deserves, and note that
  disabling `resourceserver.step-up.enabled` lets every caller through.
* *Failures carry no body.* The answers expose only the RFC 6750 challenge, so error text never reveals why a
  signature failed. Log the reason on the server instead.
* *Mind the transport.* Bearer tokens are credentials: send them only over TLS, never in a URL, and never log the
  `Authorization` header. See https://www.rfc-editor.org/rfc/rfc6750[RFC 6750].
