== What you build

This page lets users sign in to the authorization server with an account they already have at *Google*, *Microsoft
Entra ID*, *Apple* or *GitHub*. The server does not forward the upstream tokens to anyone: it *brokers* the sign-in.
It consumes the provider's answer, finds or creates a local account, links the two, and from then on issues its own
tokens. The pieces are:

* one `oauth2Login()` configuration in the login chain, with a client registration per enabled provider, the server's
  own `/login` page and the framework endpoints `+/oauth2/authorization/*+` and `+/login/oauth2/code/*+`;
* two user services (one for the OpenID Connect providers, one for GitHub, which is plain OAuth 2.0) that turn the
  provider's user into a *local* principal after the account has been resolved;
* the *linking rules*: an identity already linked signs in its account, a verified e-mail address links an existing
  account that verified it too, an unverified address never links, and an unknown person gets a new account;
* the *provider quirks* that Spring does not cover: the issuer of a multi-tenant Entra ID token, Apple's signed
  client secret and form post callback, and GitHub's verified e-mail address;
* a `federated` authentication factor, an `idp` claim in the tokens, and a page and an API to list, link and unlink
  identities that never let an account lose its last way to sign in.

The protocol side (account linking, the verified-email trap, provider quirks, the broker pattern) lives in the OAuth
Reference at xref:backend/oauth/social-login-and-federation.adoc[Social Login and Federation], and the place of
federation among the authentication methods in
xref:backend/oauth/authentication-methods-2fa-and-passwordless.adoc#_federated_social_login_as_passwordless_by_delegation[Federated / social login as passwordless by delegation].
This page does not repeat that theory; it shows the code.

=== How this differs from social login in a client application

The Spring Boot guide has a section on
xref:backend/springboot/spring-security-authorization-server.adoc#_social_login_google_microsoft_apple[social login (Google, Microsoft, Apple)]
where the *application* is the OAuth client of the identity provider. Here the roles move one level up:

[cols="2,3,3",options="header"]
|===
|
|Client application with social login
|This page: authorization server that brokers

|OAuth client of the provider
|The application
|The authorization server

|Who holds the local account
|The application
|The authorization server

|What downstream clients receive
|Not applicable: the application is the end of the chain
|Only tokens issued by this server, with its own `sub`, plus `amr` and `idp`; the provider's tokens are never exposed

|Where the provider is configured
|In each application
|Once, in the server; every client gets every provider
|===

Because every downstream client sees only the server's tokens, a client does not need to know which provider the user
chose, and adding a provider changes nothing for them. The cost is that the server becomes responsible for what the
upstream answer *means*: how strong it was (see the `amr` discussion below), and which local account it belongs to.

== How it works

=== Brokered sign-in

A user who is sent to `/login` by an interrupted `/oauth2/authorize` request clicks a provider link on the login page.
The framework runs the authorization code flow against the provider, and the two user services described below take
over when the provider's answer has been validated.

[mermaid]
....
sequenceDiagram
    autonumber
    actor U as User
    participant B as Browser
    participant A as Authorization server (login chain)
    participant P as Provider (Google, Entra, Apple, GitHub)
    participant S as FederatedOidcUserService / FederatedOAuth2UserService
    participant R as FederatedAccountResolver
    participant H as FederatedAuthenticationSuccessHandler
    B->>A: GET /oauth2/authorize (not signed in)
    A-->>B: 302 to /login (request saved)
    U->>B: Clicks "Sign in with Google"
    B->>A: GET /oauth2/authorization/google
    A-->>B: 302 to the provider, with state and nonce
    B->>P: Authorization request, user authenticates
    P-->>B: 302 to /login/oauth2/code/google with code and state
    B->>A: GET /login/oauth2/code/google
    A->>P: Token request, ID token validated
    A->>S: loadUser
    S->>R: resolve provider, subject, e-mail, verified
    alt Identity already linked
        R-->>S: Linked account, last_login_at updated
    else Verified e-mail matches an account that verified it too
        R-->>S: Identity linked to that account
    else E-mail unverified, or the account never verified it
        R-->>S: access_denied, generic failure
    else Unknown person with a verified e-mail
        R-->>S: New account provisioned, identity linked
    end
    S-->>A: Local principal named after the account
    A->>H: onAuthenticationSuccess
    H->>H: Grant FACTOR_FEDERATED, save the security context
    H-->>B: 302 to the saved request /oauth2/authorize
    B->>A: GET /oauth2/authorize (signed in)
    A-->>B: Authorization code for the client
....

The explicit link that a signed-in user starts from the account page takes a different branch inside
`FederatedAccountResolver`: the identity is attached to the signed-in account without looking at e-mail addresses at
all, and nobody is signed in. It is described under <<_the_account_page>>.

=== Which account does a sign-in reach

The rules live in a pure domain class, `FederatedLinkingPolicy`, and are applied by `ResolveFederatedLoginUseCase` in
this order. The provider's *stable subject*, never its e-mail address, identifies the person; an e-mail address is used
only once, to decide whether a first sign-in may be attached to an account that already exists.

[mermaid]
....
flowchart TD
    IN["Provider, subject, e-mail, e-mail verified?"] --> LOCK["Lock the identity: advisory lock on provider and subject"]
    LOCK --> FOUND{"Identity (provider, subject) already linked?"}
    FOUND -- yes --> DIS1{"Account enabled?"}
    DIS1 -- yes --> SIGN["Sign in that account, update e-mail and last_login_at"]
    DIS1 -- no --> REF["Refused: access_denied"]
    FOUND -- no --> VER{"Provider vouches for a usable e-mail?"}
    VER -- no --> REF
    VER -- yes --> SAME{"Account with that e-mail exists?"}
    SAME -- no --> PROV["Provision a new enabled account with a generated password, link the identity"]
    SAME -- yes --> BOTH{"Account verified that e-mail too?"}
    BOTH -- no --> REF
    BOTH -- yes --> DIS2{"Account enabled?"}
    DIS2 -- no --> REF
    DIS2 -- yes --> LINK["Link the identity to the account"]
    PROV --> OK["Account status check, then sign-in"]
    LINK --> OK
    SIGN --> OK
....

Three of these branches are security decisions rather than conveniences:

* *Both sides must vouch for the e-mail.* The provider says the address is verified *and* the existing local account
  verified it too. Otherwise an attacker could register an account with a victim's address, never verify it, and wait
  for the victim to sign in with a provider.
* *An unverified address never provisions.* A person whose provider does not vouch for an address gets no account
  rather than a half-trusted one.
* *The identity is locked first.* Two first sign-ins of the same person (two tabs, a double click) are serialized by a
  PostgreSQL advisory lock on provider and subject, so the second one finds the link of the first instead of failing on
  the unique constraint.

=== Provider differences that matter

[cols="1,2,3",options="header"]
|===
|Provider
|Protocol and registration
|What the example has to handle

|Google
|OpenID Connect, Spring's `CommonOAuth2Provider.GOOGLE` defaults
|Nothing special: the ID token carries `email` and `email_verified`.

|Microsoft Entra ID
|OpenID Connect, registered by hand, *without* an issuer
|The issuer of a multi-tenant token is the issuer of the user's tenant, so the framework's single issuer comparison would reject every token. A custom validator checks the issuer against the token's own `tid`. Its default tokens carry no `email_verified`, so only the optional `xms_edov` claim counts as verification.

|Apple
|OpenID Connect, registered by hand, no UserInfo endpoint
|The client secret is a short-lived ES256 JWT signed with the key Apple issued. The authorization request asks for `response_mode=form_post`, so the callback arrives as a cross-site POST.

|GitHub
|Plain OAuth 2.0 (no ID token), `CommonOAuth2Provider.GITHUB` with the `user:email` and `read:user` scopes
|The profile is not trusted for the e-mail address. The verified primary address is read from `GET /user/emails`, and the stable subject is GitHub's numeric id, not the login name.
|===

=== The factor and the claims

The framework's authentication carries no factor authority, so the success handler grants one through `FactorGrantor`,
saves the security context again, and lets the usual handler resume the saved request. When the answer completed an
explicit link, nobody signs in: the previous authentication is put back and no factor is granted.

[source,java]
----
include::irurueta-auth-server::example$auth-server/api/web/src/main/java/com/irurueta/authserver/authorization/api/web/social/FederatedAuthenticationSuccessHandler.java[tag=social-success-handler]
----

Reference: https://docs.spring.io/spring-security/reference/api/java/org/springframework/security/web/authentication/AuthenticationSuccessHandler.html[`AuthenticationSuccessHandler` Javadoc].

Two factors are declared, both reporting the RFC 8176 `amr` value `fed` and never held by one session. The ordinary
one is a *primary* factor, so the normal second-factor and step-up policy still applies. The strong one is
multi-factor on its own, like a passkey that proves several things at once.

[source,java]
----
include::irurueta-auth-server::example$auth-server/api/web/src/main/java/com/irurueta/authserver/authorization/api/web/social/FederatedFactor.java[tag=social-factor]
----

Reference: https://www.rfc-editor.org/rfc/rfc8176[RFC 8176, Authentication Method Reference Values], and the
https://docs.spring.io/spring-security/reference/servlet/authentication/mfa.html[Spring Security multi-factor authentication reference] for `FactorGrantedAuthority`.

The strong factor is chosen only when the provider is marked `trust-mfa` *and* its upstream `amr` contains `mfa`. An
upstream claim the server was not told to trust is never believed:

[source,java]
----
include::irurueta-auth-server::example$auth-server/api/web/src/main/java/com/irurueta/authserver/authorization/api/web/social/FederatedFactorSelector.java[tag=social-factor-selector]
----

Reference: https://www.rfc-editor.org/rfc/rfc8176[RFC 8176].

Finally the token customizer adds `idp` (the registration id of the provider). The token's `sub` is the *local*
account's username, because the principal's name is, so a token of a federated sign-in is indistinguishable from any
other in what it says about the user. Only for the strong factor are the upstream `amr` values merged into `amr`; the
`acr` is not set here, because the multi-factor contributor already derives it from the same rule the step-up check
uses.

[source,java]
----
include::irurueta-auth-server::example$auth-server/api/web/src/main/java/com/irurueta/authserver/authorization/api/web/social/IdpClaimsContributor.java[tag=social-claims]
----

=== Provider quirks

==== Microsoft Entra ID: multi-tenant issuer

With the `common` or `organizations` endpoint, the discovery document advertises a `+{tenantid}+` placeholder as the
issuer, while a real token is issued by the user's own tenant, `+https://login.microsoftonline.com/{tid}/v2.0+`. The
framework compares `iss` with one fixed issuer, so the registration has no issuer and this validator takes the tenant

== Tests

None of the tests of this feature is tagged for inclusion, so they are described in prose. They run against fake
providers that answer over HTTP, with every client id, secret, signing key and Apple key generated at run time, so
nothing leaves the process and CI never calls a real provider.

* `SocialLoginIT` checks the whole sign-in as the application wires it, with fake Google (an OpenID Connect provider
  that does not vouch for multi-factor authentication), GitHub (plain OAuth 2.0) and Apple (with the client secret the
  application signs): the first sign-in provisions an account, a verified e-mail address links an existing account, an
  unverified one never does, the tokens carry the local `sub`, `idp` and `amr`, a provider that is not trusted still
  leads to the second-factor step, identities are removed through the API under step-up, a disabled account is never
  linked, and a signed-in user links an identity from the identities page without the session changing its user.
* `SocialLoginConfigurationIT` checks the wiring with Google, Apple and GitHub configured: the login page lists exactly
  the configured providers, each authorization redirect carries what the provider needs (Apple's form post response
  mode, GitHub's e-mail scope), only Apple's callback is exempt from CSRF, and an unconfigured provider is never a way
  in.
* `SocialEntraSingleTenantIT` checks that a single-tenant application accepts only its own tenant, and
  `SocialEntraMultiTenantIT` that a multi-tenant one restricted to a list refuses a tenant that is not allowed, refuses
  a token whose issuer is another tenant's, refuses an address Entra does not vouch for, and accepts one that either
  `email_verified` or `xms_edov` vouches for.
* `SocialTrustedProviderIT` checks what `trust-mfa` changes: the provider's multi-factor sign-in counts only when the ID
  token really reports `mfa` in its `amr`, and then the user with an authenticator app is not asked for a code again
  and the tokens list the upstream factors, while a trusted provider that reports no `mfa` (or no `amr` at all) is an
  ordinary primary factor.
* `JdbcFederatedIdentityRepositoryIT` checks the repository against PostgreSQL: the round trip of a link, the unique
  constraint across accounts, listing and deleting only an owner's links, the cascade on account deletion, and that the
  advisory lock is held until the transaction ends.
* `JdbcGeneratedPasswordRepositoryIT` checks that a generated password is flagged, and that changing the password or
  saving the account again clears the flag.
* `JdbcSignInMethodsLockIT` checks that the lock of an account is held until the transaction ends, blocks another
  connection for the same account only, and is free once the transaction is over.

These are Spring Boot integration tests with Testcontainers PostgreSQL; see the
https://docs.spring.io/spring-boot/reference/testing/index.html[Spring Boot testing reference].

== Security notes and pitfalls

* *Account takeover through e-mail matching.* Matching by e-mail address alone lets an attacker who controls a
  provider account with someone else's address take over the local account. The example links by e-mail only when the
  provider *and* the local account both verified the address, never links an unverified address, and never provisions
  over an existing one. The subject, not the address, identifies a returning user. See
  https://www.rfc-editor.org/rfc/rfc9700[RFC 9700, OAuth 2.0 Security Best Current Practice] and the
  xref:backend/oauth/social-login-and-federation.adoc[Social Login and Federation] page for the verified-email trap.
* *What counts as verified depends on the provider.* Google and Apple send `email_verified`. Entra's default tokens do
  not, and a tenant administrator can set its `email` to any value, so only the optional `xms_edov` claim counts. GitHub's
  profile e-mail is not verified, which is why the verified primary address is read from `/user/emails`.
* *Entra multi-tenant issuer validation.* Skipping the issuer check to make `common` work accepts a token from any
  issuer. The validator requires `iss` to be the issuer of the token's own `tid`, and the optional list of allowed
  tenants limits who may sign in. A single-tenant application is limited to its own tenant even with no list.
* *Apple's relay address and secret.* Apple may hand over a private relay e-mail address instead of the real one; it
  still arrives as a verified address for that provider, so an account created from it carries the relay address.
  The client secret is a JWT, so the key is a secret like any private key: it comes from the environment, the
  secret has a short lifetime (five minutes by default, six months at most) and is cached for half of it. Because
  Apple answers with a cross-site POST, only its callback is exempt from CSRF, and the session cookie has to be sent on
  that cross-site request (`SameSite=None; Secure`), which a deployment must configure.
* *Unlinking the last sign-in method.* Removing an identity, a certificate or a passkey must never leave an account
  with no way in. The methods are counted under a per-account lock, and a generated password does not count as one.
  A user who signed up with a provider and unlinks it must first set a password or add another method.
* *Trusting a provider's MFA.* `trust-mfa` is off by default. A federated sign-in is a primary factor, and the
  local second factor still applies. Only a trusted provider that reports `mfa` in its `amr` counts as multi-factor
  alone, and its upstream `amr` is copied to the tokens only then; an upstream claim from an untrusted provider would
  claim a strength the server did not accept. Delegating authentication also delegates its assurance (see
  xref:backend/oauth/authentication-methods-2fa-and-passwordless.adoc#_federated_social_login_as_passwordless_by_delegation[the OAuth Reference]).
* *`amr` and `idp` to clients.* Downstream clients see `fed`, and for a strong sign-in the provider's values and `mfa`,
  plus `idp`. The `sub` is the local username, so a client cannot tell the account came from a provider except through
  these claims. Do not use `idp` for authorization decisions that the server itself did not make.
* *Uniform refusals.* Every refused sign-in is the same `access_denied`, shown as the generic login failure, so the
  page never says whether an account exists or why it was refused.
* *Stale links.* A link marker lives five minutes, is used once, and is honoured only while the session is still signed
  in as the account that asked, so an abandoned link attempt cannot be completed by someone else.
* *Secrets.* No client secret, Apple key or tenant secret is committed. The example reads them from the environment and
  fails at startup when an enabled provider lacks one.

For the references behind these notes see https://openid.net/specs/openid-connect-core-1_0.html#IDTokenValidation[ID Token Validation in OpenID Connect Core 1.0],
https://www.rfc-editor.org/rfc/rfc8176[RFC 8176], https://www.rfc-editor.org/rfc/rfc9700[RFC 9700] and the
https://cheatsheetseries.owasp.org/cheatsheets/OAuth2_Cheat_Sheet.html[OWASP OAuth 2.0 Cheat Sheet].
