= Authorization Server from Scratch: Other Passwordless Methods
:description: Three more ways to prove who is signing in to the irurueta-auth-server example: X.509 client certificates (directly on a dedicated TLS port or forwarded by a trusted proxy, bound by SHA-256 fingerprint), the OAuth 2.0 device authorization grant of RFC 8628 for input-constrained devices, and a design, not an implementation, of push approval with number matching.
:keywords: X.509, client certificate, mTLS, smart card, x509(), X509PrincipalExtractor, X509AuthenticationFilter, forwarded certificate header, trusted proxies, device authorization grant, RFC 8628, device_code, user_code, device verification, OAuth2DeviceVerificationEndpointConfigurer, push approval, number matching, MFA fatigue, FACTOR_X509, amr sc hwk, Spring Security, Spring Authorization Server

== What you build

The earlier pages of this guide cover the password, passkeys, one-time codes and social login. This page adds three
methods that do not fit those pages, each with its own short treatment:

* *X.509 client-certificate login*: a user whose browser or smart card holds a certificate signs in with it. The
  certificate reaches the server either through a dedicated TLS port that asks for it, or in a header forwarded by a
  reverse proxy that terminated TLS. A certificate is *bound* to an account by its SHA-256 fingerprint.
* The *device authorization grant* (RFC 8628): a television, a command-line tool or any device without a usable
  keyboard shows a short code, and the user approves it on a phone or a laptop, where signing in is easy.
* *Push approval with number matching*: a design only. The example does not implement it.

NOTE: Push approval is *not implemented* in the example. Its section below is a design sketch, written so that the
method could be added through the same extension points as the other factors. There is no code for it, here or in the
example repository.

The theory lives in the OAuth Reference:
xref:backend/oauth/authentication-methods-2fa-and-passwordless.adoc#_certificate_smart_card_mtls_authentication[certificate and smart-card authentication],
xref:backend/oauth/authentication-methods-2fa-and-passwordless.adoc#_push_approval_as_a_primary_factor[push approval],
xref:backend/oauth/device-authorization-grant.adoc[the device authorization grant] and, for the Spring side of the
grant, xref:backend/oauth/spring-boot-flow-recipes.adoc[Spring Boot flow recipes] (see its device-code section).
This page does not repeat them. How a factor is *required* (per user, per client, step-up) is the subject of the
Multi-Factor Authentication & Step-Up page of this guide.

== How it works

=== X.509 client-certificate login

The login page shows a button only while `authserver.x509.enabled` is true. It posts, with the CSRF token, to
`POST /login/x509`. In front of that request sits one of two transports, both off by default.

[mermaid]
....
sequenceDiagram
    autonumber
    actor U as User
    participant B as Browser
    participant T as TLS port or trusted proxy
    participant FF as ForwardedCertificateFilter
    participant X as X509LoginFilter
    participant E as CertificatePrincipalExtractor
    participant S as X509UserDetailsService
    participant H as X509AuthenticationSuccessHandler
    U->>B: Presses Use my certificate
    B->>T: POST /login/x509 with the CSRF token, TLS handshake with the client certificate
    alt Dedicated TLS port
        T->>X: Container leaves the certificate in the jakarta.servlet.request.X509Certificate attribute
    else Reverse proxy
        T->>FF: Request with the certificate header, from a trusted address
        FF->>X: Parses the header and sets the same request attribute
    end
    X->>E: extractPrincipal(certificate)
    E-->>X: SHA-256 fingerprint, or an empty principal when expired
    X->>S: loadUserDetails(fingerprint)
    S->>S: Resolve the binding in x509_certificates, load the account
    S-->>X: UserDetails, or UsernameNotFoundException
    X->>H: Authentication succeeded
    H->>H: Replace the pre-authenticated token, grant FACTOR_X509, change the session id
    H-->>B: 302 to the interrupted request, for example /oauth2/authorize
....

The same filter and the same extractor serve both transports, because both leave the certificate where a servlet
container leaves one. Three decisions matter:

* *The fingerprint, not the subject, identifies the certificate.* Whoever controls a certificate authority can issue a
  certificate with any subject name, and none with a given fingerprint. The principal is the SHA-256 digest of the
  DER form, and the account is found by a lookup in the bindings table.
* *The server does not validate the chain on the dedicated port.* The connector asks for a certificate without
  requiring or validating one (`optionalNoCA`): the handshake proves that the client holds the private key, and the
  binding proves that this particular certificate was registered by the account's owner. Validity dates are still
  checked, by the extractor.
* *The certificate is a strong primary factor.* The factor reports the `sc` (smart card) value of `amr` by default,
  or `hwk` when the deployment says that its keys are bound to hardware, and satisfies the multi-factor policy on its
  own.

=== The device authorization grant

The grant is defined by RFC 8628. The device never sees the user's credentials: it gets two codes, shows one of them,
and polls for the result while the user signs in elsewhere.

[mermaid]
....
sequenceDiagram
    autonumber
    participant D as Device or CLI
    participant AS as Authorization server
    actor U as User
    participant B as Browser on another device
    D->>AS: POST /oauth2/device_authorization (client_id)
    AS-->>D: device_code, user_code, verification_uri, expires_in, interval
    D->>U: Shows the user code and the verification URI
    loop Every interval seconds
        D->>AS: POST /oauth2/token (grant_type device_code, device_code, client_id)
        AS-->>D: authorization_pending (or slow_down)
    end
    U->>B: Opens the verification URI
    B->>AS: GET /oauth2/device_verification
    AS-->>B: Sign-in if needed, then the page with the code form
    U->>B: Types the user code
    B->>AS: POST /oauth2/device_verification (user_code, CSRF token)
    AS->>AS: Guard counts the attempt and applies the multi-factor policy
    AS-->>B: 302 to /oauth2/consent
    U->>B: Approves the scopes
    B->>AS: POST /oauth2/device_verification (consent decision)
    AS-->>B: 302 to /oauth2/device_verification?success
    D->>AS: POST /oauth2/token (grant_type device_code, device_code, client_id)
    AS-->>D: access_token, refresh_token
....

The example changes four things around the framework's defaults. The device is a *public client* that cannot keep a
secret and, unlike a browser app, has no PKCE verifier, so the example gives it its own client authentication, by
`client_id` alone. The verification endpoint is *guarded* before the framework's converters run: every request that
carries a user code is counted against a limit per address and per user, and the multi-factor policy of the account
and of the client is applied (the client is the one that the stored authorization names for the typed code, so a
client that requires a second factor is enforced even if it skips consent). The user *consents* on the same consent
page as the authorization code flow. And the verification page is an ordinary Thymeleaf page rendered by a controller
that implements the generated pages interface.

=== Push approval with number matching (design)

A push approval asks an already enrolled phone to approve a sign-in. Plain approve or deny prompts are easy to abuse:
an attacker who knows a password can trigger prompts until a tired user taps Approve (MFA fatigue or prompt bombing).
*Number matching* removes that: the sign-in page shows a number, the phone shows several candidates, and the user must
pick the one on the screen, which proves that the person holding the phone is looking at the sign-in being approved.

[mermaid]
....
sequenceDiagram
    autonumber
    actor U as User
    participant W as Sign-in page
    participant AS as Authorization server
    participant P as Push provider, APNs or FCM
    participant A as Phone app with an enrolled device key
    U->>W: Starts a sign-in
    W->>AS: Create a challenge for this session and authorization request
    AS-->>W: Shows a two-digit number, waits for the approval
    AS->>P: Notification carrying only an opaque challenge id
    P->>A: Delivers the notification
    A->>AS: Fetch the challenge context
    AS-->>A: Application name, scopes, three candidate numbers
    U->>A: Picks the number shown on the sign-in page, or denies
    A->>AS: Response signed with the device key over challenge, number, client, scope and expiry
    AS->>AS: Verify the signature with the enrolled public key, consume the challenge
    AS-->>W: Approved, the page continues the authorization
....

The design, in the terms of the extension points that the example already uses for the other factors:

* *Enrolment.* A device key pair is created on the phone, the private key stays in the secure enclave or keystore,
  and the public key is stored for the account. Enrolling needs a recent multi-factor sign-in, as binding a
  certificate or a passkey does.
* *Registration in the framework.* A second factor with its own authority and an `amr` value, a fragment of the
  second-factor page that says "waiting for approval", a query that says that a user with an enrolled device must use
  it, and an `AuthenticationProvider` that reuses the shared lockout and security-event machinery.
* *Challenge.* Each attempt creates a single-use challenge bound to the session and to the pending authorization
  request, with a lifetime of about 60 seconds, a small cap of pending challenges per user and a rate limit. The
  page polls or listens for the result and falls back to another factor on expiry.
* *No secret in the push.* The notification carries only a challenge id. The approval is a signature, so a stolen
  notification cannot approve anything.
* *Relation to the device grant.* The two are unrelated approvals. A device-grant verification already runs the
  multi-factor policy, so a user whose second factor is a push approval would approve it while signing in on the
  verification page; the consent screen of the device flow stays a plain click.
* *Relation to step-up.* An approved push is a second factor, so it would produce `amr` and satisfy the step-up check
  of RFC 9470 as the other factors do; a sensitive operation sends the user to a fresh challenge.

Risks to review before building it: device loss (recovery through other factors or recovery codes, and revoking the
device), notification availability (an offline fallback), and the push provider as a third party (hence the opaque
payload).

them, so a private authority's certificate would never be presented.

=== X.509: from certificate to account

described here: it checks the validity dates and returns the lower-case SHA-256 of the DER form, or an empty string

sign-in fails like any unknown certificate.

=== Certificates

The account API binds, lists and unbinds certificates. All operations need a bearer token of the account, and binding
and unbinding need a recent multi-factor sign-in when the account has a confirmed second factor.

[source,yaml]
----
include::irurueta-auth-server::example$apis/auth-server/rest-server/auth-server-api-v1.yaml[tag=certificates-schemas]
----

The schemas follow the https://spec.openapis.org/oas/v3.1.0#schema-object[OpenAPI 3.1 Schema Object] rules.

Bind a certificate by sending its public part in PEM form. The answer is `201` with the binding, or the existing
binding when the account already has it; `409` means that another account has it, and `400` that the value is not a
single valid certificate:

[source,bash]
----
curl -s -X POST http://localhost:9000/api/account/certificates \
  -H "Authorization: Bearer ${TOKEN}" \
  -H "Content-Type: application/json" \
  -d "$(jq -n --rawfile pem client.crt '{certificate: $pem}')"
----

List and unbind:

[source,bash]
----
curl -s http://localhost:9000/api/account/certificates \
  -H "Authorization: Bearer ${TOKEN}"

curl -s -X DELETE http://localhost:9000/api/account/certificates/${BINDING_ID} \
  -H "Authorization: Bearer ${TOKEN}"
----

Unbinding the last way to sign in is refused. The sign-in itself is the form of the login page; there is no JSON API
for it, because the credential is the TLS handshake.

=== Device verification page

The device endpoints are framework endpoints, so their request and response shapes are those of RFC 8628. The only
operation of the example's pages contract is the verification page:

[source,yaml]
----
include::irurueta-auth-server::example$apis/auth-server/web-pages/auth-server-pages-v1.yaml[tag=device-verification-page-api]
----

See the https://spec.openapis.org/oas/v3.1.0#path-item-object[OpenAPI path item object] for the structure of a path.

The device requests its codes with its `client_id` alone (use the identifier of a client that has the
`urn:ietf:params:oauth:grant-type:device_code` grant; the development profile seeds one named `device-client`):

[source,bash]
----
curl -s -X POST http://localhost:9000/oauth2/device_authorization \
  -d "client_id=device-client"
----

The answer carries `device_code`, `user_code`, `verification_uri`, `verification_uri_complete`, `expires_in` and
`interval`. The device then polls the token endpoint every `interval` seconds until the user has approved it:

[source,bash]
----
curl -s -X POST http://localhost:9000/oauth2/token \
  -d "grant_type=urn:ietf:params:oauth:grant-type:device_code" \
  -d "device_code=${DEVICE_CODE}" \
  -d "client_id=device-client"
----

Until then the answer is `400` with `authorization_pending`, or `slow_down` when the device polls too fast, and
`expired_token` once the codes have expired. After approval it is a token response.

== Tests

All of these are integration tests of the example. None of them has a tagged region, so they are described here.

* *`X509LoginIT`* (Spring MockMvc). A bound certificate signs in and the tokens report `sc`. An unbound certificate,
  no certificate, an expired certificate, a removed binding and a disabled account are all sent back to the login
  page. A forwarded header from an untrusted address is ignored. A certificate issued by a certificate authority
  works like a self-signed one. A GET never signs anybody in, and a request without the CSRF token is refused.
* *`X509TlsLoginIT`*. A real TLS handshake on the dedicated port, with certificates generated by `keytool` at run
  time: bound, unbound, no certificate, binding removed and expired.
* *`X509ForwardedHeadersGuardIT`*. The application refuses to start with a forwarded header and a strategy that
  rewrites the client address.
* *`CertificateApiIT`* and *`JdbcCertificateBindingRepositoryIT`*. The account API (binding, listing, the step-up
  challenge, conflicts, the last sign-in method) and the repository against PostgreSQL in a container.
* *`DeviceVerificationPageIT`*. The verification page for an anonymous and a signed-in user, the error and success
  messages, the full flow to tokens, a link that carries the code, and redirects to the second-factor page when the
  account or the client requires one.
* *`DeviceVerificationRateLimitIT`*. Attempts beyond the per-address and per-user limits are refused.
* *`DeviceFlowEndToEndIT`*, in the `e2e-tests` module. The packaged `DeviceFlowCli` obtains tokens after the user
  approves in a real browser driven by Playwright, and ends with a non-zero exit when the user denies.

Two production defects were found by these tests while the example was written, which is what they are for: an
expired bound certificate used to sign in on both transports, and the dedicated TLS port used to advertise the JVM's
authorities, so a private authority's certificate was never offered.

== Security notes and pitfalls

* *Trust forwarded certificate headers only from the proxy.* Anybody can send a header. The filter reads it only when
  the direct network peer is in `authserver.x509.trusted-proxies`, and the guard refuses a forwarded-header strategy
  that would let a client choose that address. The proxy must also overwrite or remove a header of that name sent by
  the client, and must verify the certificate.
* *Revocation is not checked.* On the dedicated port no authority validates the chain, and behind a proxy the proxy
  does. What revokes access is deleting the binding. If you rely on a PKI, check revocation (CRL or OCSP) at the proxy
  and remove bindings when a certificate is revoked.
* *Expiry is checked.* The extractor yields no usable principal for a certificate outside its validity period.
* *Bind only public certificates.* The reader refuses anything that mentions a private key, so a user who pastes the
  wrong file does not send the key to the server.
* *Do not lock yourself out.* Unbinding the last way to sign in is refused, and binding or unbinding need a recent
  multi-factor sign-in.
* *Browser prompts.* A certificate prompt on the main port would affect every user. A dedicated port keeps it to the
  people who choose the button.
* *User-code brute force and phishing in the device flow.* A user code is short, so the example limits attempts per
  address and per user, makes the code expire with the device code, and never says why a code failed. The user is
  still asked to approve a code that an attacker's device may have started: show the client name and scopes on the
  consent page and tell the user to approve only a code that their own device showed. RFC 8628 discusses both in its
  sections on brute forcing and remote phishing.
* *The device is a public client.* Its identifier is not a secret. Give it only the scopes a device needs and prefer
  short-lived tokens.
* *Push fatigue.* A plain approve or deny prompt can be spammed until a user approves. Number matching defeats that,
  because the attacker cannot see the number that the real sign-in page shows. Limit pending challenges per user and
  keep the challenge short-lived.

For the full reference see https://www.rfc-editor.org/rfc/rfc8628[RFC 8628], the
https://docs.spring.io/spring-security/reference/servlet/authentication/x509.html[Spring Security X.509 reference],
the https://docs.spring.io/spring-authorization-server/reference/protocol-endpoints.html[Spring Authorization Server protocol endpoints]
and https://pages.nist.gov/800-63-4/sp800-63b.html[NIST SP 800-63B-4] for authenticator policy.
