== What you build

This page adds two ways to prove the possession of a mailbox: a *one-time code* (six digits typed into the login page) and a
*magic link* (a single-use URL that the user opens from the e-mail). Each works in two roles:

* as a *primary* login method, offered on the login page next to the password and the passkey, for a user who has a verified
  e-mail address;
* as a *second factor*, offered on the second-factor page to a user who already signed in with a primary factor and has no
  stronger factor of their own.

The theory (what each mechanism proves, why a mailbox is only as strong as the way the password is reset) lives in the OAuth
Reference sections xref:backend/oauth/authentication-methods-2fa-and-passwordless.adoc#_e_mail_one_time_code_otp[],
xref:backend/oauth/authentication-methods-2fa-and-passwordless.adoc#_e_mail_magic_link_single_use_token[] and
xref:backend/oauth/authentication-methods-2fa-and-passwordless.adoc#_e_mail_or_sms_otp_as_a_second_factor[], and this page does not repeat it.
Rate limiting is the subject of xref:backend/resilience/bucket4j-spring-boot-manual-integration.adoc[]; here only the way the
example applies it to these endpoints is shown. The SMS channel shares all the machinery of this page and is described in
xref:backend/springboot/authorization-server-from-scratch/sms-otp.adoc[].

=== What Spring gives and what the example adds

Spring Security 7.1 provides the *one-time token login*: `HttpSecurity.oneTimeTokenLogin()` registers a filter that answers
`POST /ott/generate` (it asks a `OneTimeTokenService` for a token and hands it to a `OneTimeTokenGenerationSuccessHandler`) and a
filter that answers `POST /login/ott` (it turns the posted `token` into an authentication and calls an `AuthenticationProvider`).
`JdbcOneTimeTokenService` stores the tokens in a `one_time_tokens` table. The framework leaves the *delivery* of the token to the
application, and its tokens are UUIDs.

The example keeps all of that for the magic link and adds what a production login needs:

* *numeric codes*. The stock service always generates a UUID and keys its table by that value alone, so six digits would
  collide across users. A code is stored in the example's own table, `ott_codes` (migration `V610`), as a hash, bound to the
  user name and to a *binding id* held in the session of the browser that asked for it;
* a *confirm page* for the link: the e-mail opens `GET /login/ott/confirm`, which only renders a button, and the button's `POST`
  consumes the token;
* *delivery through a listener*, after the database transaction commits and off the request thread;
* *rate limiting* per client address and per identifier;
* *enumeration safety*: the same redirect, whatever the identifier is;
* *factors* that register the method in the multi-factor framework of the
  xref:backend/springboot/authorization-server-from-scratch/multi-factor-authentication.adoc[Multi-Factor Authentication & Step-Up] page.

== How it works

=== The code variant

The browser posts the identifier to `/ott/generate`. Spring's filter asks the example's resolver for the token to generate
and the stock service stores it; the example's success handler then *discards* that token (a code does not use the stock store),
stores a code of its own and requests its delivery.

[mermaid]
....
sequenceDiagram
    autonumber
    actor U as User
    participant B as Browser
    participant RL as OttRateLimitFilter
    participant G as GenerateOneTimeTokenFilter
    participant H as OttGenerationSuccessHandler
    participant UC as RequestOneTimeCodeUseCase
    participant DB as ott_codes
    participant L as OttDeliveryListener
    participant M as ThymeleafOttMailer
    U->>B: Types the user name, chooses e-mail and code
    B->>RL: POST /ott/generate (username, channel=email, kind=code)
    RL->>G: Within the per-client and per-identifier limits
    G->>H: A token from the resolver, stored by JdbcOneTimeTokenService
    H->>H: Consume and discard the stock token
    H->>UC: execute(identifier, EMAIL, LOGIN, bindingId)
    UC->>DB: Save the hash of the code, with the binding id (only if the account has a verified address)
    UC-->>L: EmailCodeRequested, published inside the transaction
    H->>B: 302 to /login/ott, binding id kept in the session
    L->>M: After commit, off the request thread: deliverCode
    M-->>U: E-mail with the code
    U->>B: Types the code
    B->>RL: POST /login/ott (token=code)
    RL->>B: The converter reads identifier and binding id from the session
    B->>DB: OttCodeAuthenticationProvider and VerifyOneTimeCodeUseCase: attempts, hash, consume
    DB-->>B: Authentication with FACTOR_OTT, then the saved request resumes
....

Two details make a code safe to be six digits. It is checked only in the browser that asked for it, because the converter reads
the identifier and binding id from the session (`PendingOtt`), never from the form. And it is checked at most a few times: the
attempt counter is incremented atomically before the comparison, and the code is burnt after the last wrong attempt.

=== The link variant

[mermaid]
....
sequenceDiagram
    autonumber
    actor U as User
    participant B as Browser
    participant S as Mail scanner
    participant H as OttGenerationSuccessHandler
    participant T as JdbcOneTimeTokenService
    participant C as GET /login/ott/confirm
    participant P as POST /login/ott
    U->>B: Types the user name, chooses e-mail and link
    B->>H: POST /ott/generate (kind=link)
    H->>T: Token (UUID) stored by the framework, kept
    H-->>U: E-mail with the link to /login/ott/confirm, token in the query
    S->>C: GET the link to scan it
    C-->>S: A page with one button, nothing consumed
    U->>C: Opens the link
    C-->>U: The confirm page, no-store, no referrer
    U->>P: Clicks the button: POST token
    P->>T: OttLinkAuthenticationProvider: consume(token)
    T-->>P: The token and its user name, deleted
    P-->>U: Authentication with FACTOR_OTT, then the saved request resumes
....

The link points at a *page*, never at an endpoint that consumes the token. Mail clients, security gateways and link
previews fetch URLs with `GET` before the user ever sees the message; a link that signed the user in on `GET` would be spent by
the scanner and fail for the person. Here a `GET` changes nothing and only the click, a `POST` with the CSRF token of the page,
consumes it. The page is sent with `Cache-Control: no-store` and `Referrer-Policy: no-referrer`, because the token is in its
address.

|`ott_codes.username`, `ott_codes.channel`, `ott_codes.purpose`

|`ott_codes.code_hash`
|`varchar(128)`
|SHA-256 of the code in lower-case hex, compared in constant time.

|`ott_codes.binding_id`
|`varchar(128)`
|Random id held in the session of the browser that requested the code. A code only verifies together with it.

|`ott_codes.attempts`
|`integer`
|Wrong submissions so far, never negative. Past the limit the code is burnt.

|`ott_codes.expires_at`, `ott_codes.created_at`
|`timestamp with time zone`
|Expiry and creation time.
|===

A plain hash of a six-digit code can be brute-forced instantly if the table leaks. That is acceptable only because a code is single use, lives for
minutes and is burnt after a few wrong attempts; never reuse that hasher for a long-lived secret. The table definitions also appear, with the
rest of the schema, in xref:backend/springboot/authorization-server-from-scratch/data-model.adoc[Data Model and Schema].

=== Delivery

The success handler of the framework's filter is where the example takes over, and `OttGenerationSuccessHandler` always ends in the same redirect to
`/login/ott`. For a link it asks `RequestMagicLinkUseCase` to e-mail the confirm link, whose host is the configured issuer, never the `Host` header of the
request (which an attacker controls). For a code it discards the stock token and asks `RequestOneTimeCodeUseCase` to store a code of its own. Both use cases
resolve the destination (a verified address of an enabled account) and *publish an event* instead of sending anything. The listener sends it:

[source,java]
----
include::irurueta-auth-server::example$auth-server/api/web/src/main/java/com/irurueta/authserver/authorization/api/web/ott/OttDeliveryListener.java[tag=ott-delivery-listener]
----

Reference: https://docs.spring.io/spring-framework/reference/data-access/transaction/event.html[Transaction-bound events].

Because the send happens after commit and off the request thread, no mail server is called inside a transaction, a slow one holds no database connection, a rolled-back
request sends nothing, and the time a request takes is the same whether or not something is sent. A failure is logged without the address, the number or the token.

The mailer renders a text and an HTML body from Thymeleaf templates, with the locale of the mail settings and never the platform's. Any failure becomes an
`OttDeliveryException` that carries neither the address nor the token.

[source,java]
----

=== Rate limits

Token requests and submissions are limited separately, and each twice: per client address and per identifier. The identifier is limited whether or not it belongs to
an account, so the limit never tells which ones exist. The limiter uses the same Bucket4j and Caffeine pattern as the account endpoints; see
xref:backend/resilience/bucket4j-spring-boot-manual-integration.adoc[] for the technique.

[source,java]
----
include::irurueta-auth-server::example$auth-server/api/web/src/main/java/com/irurueta/authserver/authorization/api/web/ott/OttRateLimiter.java[tag=ott-rate-limit]
----

Reference: https://bucket4j.com/[Bucket4j].

The limiter is applied by `OttRateLimitFilter`. Spring's one-time token filters are Spring Security filters, so no controller advice sees their failures; the filter answers
`429` as `application/problem+json` with a `Retry-After` header, before any token is stored or any code is checked. The buckets live in the memory of one instance, so several
instances each apply the limits on their own, and the client address is `request.getRemoteAddr()`: behind a proxy `server.forward-headers-strategy` must be set for it to be the real client.

=== Factors

One authority cannot carry two strengths, and the registry refuses two factors with the same authority. So each use of each channel is a factor of its own. A code or link
that signs the user in proves the possession of a mailbox, which is as strong as a password and no more (`PRIMARY`); the same mailbox as the second factor of a user who already signed in is `SECOND`.
The `amr` values are those of https://www.rfc-editor.org/rfc/rfc8176[RFC 8176]: `otp` for the e-mail code or link and `sms` for the SMS code.

== API

The flow is made of form posts and two HTML pages, not of a JSON API, so it has no OpenAPI operation for the generate and sign-in posts: they are the framework's endpoints.

[cols="3,2,5",options="header"]
|===
|Endpoint
|Who
|What it does

|`POST /ott/generate`
|Anyone (CSRF token required)
|Fields `username`, `channel` (`email` or `sms`, default `email`), `kind` (`code` or `link`, default `code`) and `purpose` (`login` or `second-factor`, default `login`). Always answers a redirect to `/login/ott`; a second factor needs a signed-in user. A link is sent by e-mail only.

|`GET /login/ott`
|Anyone
|The page that says to check the inbox and, for a code, shows the form to type it.

|`POST /login/ott`
|Anyone (CSRF token required)
|Field `token`: the UUID of a magic link or the numeric code. Success resumes the saved request, usually `/oauth2/authorize`.

|`GET /login/ott/confirm`
|Anyone
|Query `token`. The page a magic link opens; it renders one button and consumes nothing.

|`POST /login/second-factor/ott`
|Signed-in user
|Field `code`: the second-factor code.
|===

== Tests

The example covers this feature at four levels. They are described in prose, since none of the test classes carries a tag for inclusion:

* *Unit tests* of every class of the package, the use cases (attempt counter, burn on the last failed attempt, lockout and audit for the second factor), the providers, the converter, the resolver, the success handler, the listener, the mailer and the rate limiter.
* *Persistence*: `JdbcOneTimeCodeRepositoryIT` runs the code repository against PostgreSQL (one active code per binding and user, atomic attempt counting, single consumption, expiry).
* *Integration tests of the sign-in*, with a real SMTP relay: `OttEmailCodeIT` and `OttMagicLinkIT` sign in with a code and with a link, as primary and as second factor, reading the message through the Mailpit HTTP API (Testcontainers, `axllent/mailpit`).
  `OttPagesIT` renders the login fragment, the second-factor offer (e-mail only for a user without another factor), the code page and the confirm page, whose button posts the token.
  `OttRateLimitIT` checks the limits per identifier and per client, and `OttEnumerationIT` that status, body and delivery are identical for a known and an unknown identifier.
* *End to end*: `OttEndToEndIT` drives the packaged jar with Playwright, signs in with an e-mail code read from Mailpit and with a magic link, and checks that a scanner's `GET` does not consume the link.

Writing the rate-limit test found a real bug: the limiter was first registered before `UsernamePasswordAuthenticationFilter`, but Spring's generate filter sits earlier and answers the request itself, so generation was never limited. The customizer shown above adds it before `GenerateOneTimeTokenFilter`.

== Security notes and pitfalls

* *Enumeration.* The response to `POST /ott/generate` is the same redirect whether the identifier exists, is disabled or has no verified address. The use cases still generate and hash a code in the unhappy case, and
  delivery happens after commit and off the request thread, so neither the body nor the latency tells. Only the e-mail of a real account differs.
* *Rate limiting.* Limit per address *and* per identifier: the first stops one client flooding mailboxes, the second stops many clients aiming at one account. Both are applied before any token is stored. Behind a proxy,
  configure forwarded headers or every client shares one address.
* *Single use and expiry.* A link is consumed by the `POST` that uses it and a code by the first correct submission, with the conditional consume deciding which of two concurrent submissions wins. Codes live ten minutes and links fifteen
  by default; short lifetimes shrink the window for a stolen message. Expired rows are removed by a scheduled clean-up.
* *Link prefetching.* A mail scanner or preview fetches the URL with `GET`. The confirm page makes that harmless; never make the link itself sign the user in.
* *Where the link points.* The link is built from the configured issuer, never from the `Host` header, so a forged request cannot make the server mail a valid token for the wrong host. The application refuses to start without an issuer.
* *Cross-device use.* A numeric code works only in the browser that requested it, through the binding id kept in the session. A user who requests a code on a laptop and types it on a phone is refused, by design; a magic link has no such
  binding for a sign-in, which is the convenience and the risk of links: whoever opens the e-mail can complete the login. A *second-factor* link is accepted only in the session that already holds the primary factor.
* *Mailbox strength.* The factor is as strong as the mailbox and as the password reset. This is why the example never lets the same mailbox be both the sign-in and the second factor, and withholds the e-mail second factor from users
  who enrolled a stronger one.
* *Phishing.* A code typed into a fake page is lost to the attacker in real time; a magic link is no better against a user who is tricked into confirming. Neither is phishing-resistant: use a passkey where that matters.
* *Development.* The compose file starts Mailpit, a local SMTP sink with a web UI, and the dev profile points the mail relay at it, so no real e-mail is ever sent; see
  xref:backend/springboot/authorization-server-from-scratch/project-setup.adoc#_local_services_with_docker_compose[Local services with Docker Compose].
* *Logging.* Never log the code, the token, the address or a message body. Failures are logged by type only.

https://pages.nist.gov/800-63-4/sp800-63b.html[NIST SP 800-63B-4] guidance on out-of-band and look-up authenticators and the
https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html[OWASP Forgot Password Cheat Sheet], whose enumeration advice applies to every flow that sends a message to an address.
