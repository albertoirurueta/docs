== What you build

The earlier pages added the endpoints one feature at a time. This page is the map: every URL the example serves, who defines it,
which Spring component answers it, and where its page is. It has four groups:

* the *protocol endpoints*, defined by RFCs and OpenID Connect specifications and answered by Spring Authorization Server;
* the *Spring Security authentication endpoints* behind the login page, answered by Spring Security itself;
* the *custom APIs*, defined by the OpenAPI contracts under `apis/` of the example and answered by the controllers of the example;
* the *error model* shared by all of them.

The theory of each protocol endpoint is in the OAuth Reference, starting at xref:backend/oauth/discovery-metadata-and-client-registration.adoc[]
and xref:backend/oauth/opaque-tokens-introspection-and-revocation.adoc[]. This page lists what the example does with them. All
examples assume the authorization server on `+http://localhost:9000+` (the `dev` profile), the BFF on `+http://localhost:8080+` and the
resource server on `+http://localhost:8081+`. `+${...}+` values are placeholders, and none is a real secret.

=== The discovery document

The discovery document is the only URL a client needs to know: it lists every other endpoint, so a Spring client configured with an `issuer-uri` finds the rest.
The listing below keeps the fields that name the endpoints of this example and the algorithms and methods it supports. The field names are those of
OpenID Connect Discovery and RFC 8414, and the endpoint values follow the issuer `+http://localhost:9000+` and the paths in the table above.

NOTE: This trimmed listing was assembled from the example's configuration and the specifications, not captured from a running instance. The `PAR` and registration
endpoints appear only when their features are enabled. Run the `curl` command below against your own instance and treat its output as the truth.

[source,json]
----
{
  "issuer": "http://localhost:9000",
  "authorization_endpoint": "http://localhost:9000/oauth2/authorize",
  "token_endpoint": "http://localhost:9000/oauth2/token",
  "jwks_uri": "http://localhost:9000/oauth2/jwks",
  "revocation_endpoint": "http://localhost:9000/oauth2/revoke",
  "introspection_endpoint": "http://localhost:9000/oauth2/introspect",
  "device_authorization_endpoint": "http://localhost:9000/oauth2/device_authorization",
  "userinfo_endpoint": "http://localhost:9000/userinfo",
  "end_session_endpoint": "http://localhost:9000/connect/logout",
  "response_types_supported": ["code"],
  "subject_types_supported": ["public"],
  "id_token_signing_alg_values_supported": ["RS256"],
  "code_challenge_methods_supported": ["S256"]
}
----

The metadata format is defined in https://openid.net/specs/openid-connect-discovery-1_0.html#ProviderMetadata[OpenID Connect Discovery, Provider Metadata] and https://datatracker.ietf.org/doc/html/rfc8414#section-2[RFC 8414, Authorization Server Metadata].

=== Requests you can make with curl

These endpoints need no browser. The ones that need a signed-in user (`/oauth2/authorize`, consent and the second factor) are HTML pages, so `curl` stops at the redirect to `/login`.

*Discovery and keys.* Both are public:

[source,bash]
----
curl -s http://localhost:9000/.well-known/openid-configuration
curl -s http://localhost:9000/oauth2/jwks
----

The JWK set lists the `ACTIVE`, the `NEXT` and the still-retained `RETIRED` keys, with no private part. See xref:backend/springboot/authorization-server-from-scratch/signing-keys-jws-and-jwt.adoc#_publishing_keys_and_signing_with_the_active_one[Publishing keys and signing with the active one].

*Client credentials token.* The client authenticates with HTTP Basic (`client_secret_basic`) and gets an access token whose subject is the client:

[source,bash]
----
curl -s -u "${CLIENT_ID}:${CLIENT_SECRET}" http://localhost:9000/oauth2/token \
  -d grant_type=client_credentials \
  -d scope=documents.read
----

The answer has `access_token`, `token_type` (`Bearer`), `expires_in` and `scope`, and no refresh token. Other client authentication methods (`private_key_jwt`, mutual TLS) and token exchange are shown in
xref:backend/springboot/authorization-server-from-scratch/client-credentials-and-service-to-service.adoc#_api[Client Credentials & Service-to-Service, API].

*Introspection and revocation.* Both need client authentication. Introspection answers `+{"active":false}+` for a token that is revoked, expired or unknown:

[source,bash]
----
curl -s -u "${CLIENT_ID}:${CLIENT_SECRET}" http://localhost:9000/oauth2/introspect \
  -d token="${ACCESS_TOKEN}"

curl -s -u "${CLIENT_ID}:${CLIENT_SECRET}" http://localhost:9000/oauth2/revoke \
  -d token="${REFRESH_TOKEN}" -d token_type_hint=refresh_token
----

*Device authorization.* The device sends only its `client_id` and polls the token endpoint with the `device_code` it gets back:

[source,bash]
----
curl -s -X POST http://localhost:9000/oauth2/device_authorization \
  -d client_id=device-client
----

The `dev` profile seeds `device-client`. The full poll loop and its errors are on xref:backend/springboot/authorization-server-from-scratch/other-passwordless-methods.adoc[Other Passwordless Methods].

*UserInfo.* The access token of a signed-in user is the credential:

[source,bash]
----
curl -s -H "Authorization: Bearer ${ACCESS_TOKEN}" http://localhost:9000/userinfo
----

The answer always has `sub`; the `profile` and `email` scopes add the claims listed on xref:backend/springboot/authorization-server-from-scratch/access-refresh-and-id-tokens.adoc#_api[Access, Refresh & ID Tokens, API].

These requests are the ones of https://datatracker.ietf.org/doc/html/rfc6749#section-4.4[RFC 6749, Client Credentials Grant], https://datatracker.ietf.org/doc/html/rfc7662#section-2.1[RFC 7662, Introspection Request],
https://datatracker.ietf.org/doc/html/rfc7009#section-2.1[RFC 7009, Revocation Request], https://datatracker.ietf.org/doc/html/rfc8628#section-3.1[RFC 8628, Device Authorization Request] and
https://openid.net/specs/openid-connect-core-1_0.html#UserInfo[OpenID Connect Core, UserInfo].

== Custom APIs

The REST APIs of the example are contract first: the OpenAPI documents under `apis/` are the source, and the controllers implement interfaces generated from them. The `OpenApiDriftIT` test of each application
fails when the running application serves something different (see xref:backend/springboot/authorization-server-from-scratch/testing.adoc#_testing_tricks[Testing tricks]).
The documents are `apis/auth-server/rest-server/auth-server-api-v1.yaml`, `apis/auth-server/web-pages/auth-server-pages-v1.yaml`, `apis/bff/rest-server/bff-api-v1.yaml`,
`apis/resource-server/rest-server/resource-server-api-v1.yaml` and `apis/github/rest-server/github-api-v1.yaml` (the GitHub calls the server makes, not an API it serves).
Each is in https://github.com/albertoirurueta/irurueta-auth-server/tree/main/apis[the `apis` folder of the repository].

=== How the account and administration APIs are secured

`+/api/**+` has its own chain, ahead of the protocol chain. It is stateless, validates a bearer JWT issued by this server, requires the audience `authserver.api.audience` (default `auth-server`),
refuses the purpose-bound account tokens that are signed by the server but never meant as bearer tokens, and answers `+/api/admin/**+` only to a token with the scope `admin`.
Registration, e-mail verification and the two password-reset endpoints are the only anonymous ones.

== Error model

=== Protocol errors (RFC 6749)

The token, revocation and introspection endpoints answer failures with the JSON object of https://datatracker.ietf.org/doc/html/rfc6749#section-5.2[RFC 6749, section 5.2]:
an `error` code, and optionally `error_description` and `error_uri`. Spring Authorization Server writes them, so the example does not change their shape.

[cols="2,1,4",options="header"]
|===
|`error`
|Status
|Typical cause in the example

|`invalid_request`
|400
|A required parameter is missing or repeated

|`invalid_client`
|401
|Wrong secret, an unknown client, or a replayed client assertion

|`invalid_grant`
|400
|A used, expired or rotated code or refresh token (presenting a rotated refresh token again also revokes the authorization it belonged to)

|`unauthorized_client`
|400
|The client has no registration for that grant type

|`unsupported_grant_type`
|400
|The grant type is not implemented or not enabled

|`invalid_scope`
|400
|A scope the client is not registered for

|`invalid_target`
|400
|A token exchange asked for an audience the client may not have

|`authorization_pending`, `slow_down`, `expired_token`, `access_denied`
|400
|Device flow polling states (RFC 8628 section 3.5)
|===

The authorization endpoint cannot always answer with JSON. A request with `response_type=token` is refused with `unsupported_response_type`, because the implicit flow is off by default. When the redirect URI is trusted it redirects back with `error` and `state` in the query, and otherwise it shows an error page.
See xref:backend/oauth/security-best-practices.adoc[] for why the redirect URI is validated before anything is sent to it.

=== Problem details on the custom APIs (RFC 9457)

Every failure of the account, administration, BFF and resource-server REST APIs is `application/problem+json` (https://datatracker.ietf.org/doc/html/rfc9457[RFC 9457]) with `type`, `title`, `status` and `detail`.
`type` is a URN of the form `+urn:problem:<area>:<name>+`. The areas are `account`, `client`, `mfa`, `passkeys`, `phone`, `identity`, `certificate` and `ott` on the authorization server, and `documents` on the BFF.
Request validation failures use `about:blank`. A rate-limited answer carries `Retry-After`. The step-up handler of the account API shows the shape: it builds a `ProblemDetail` with its `type` and `title`, and returns it through `problemResponse`, a helper of the handlers' base class `ProblemJsonExceptionHandler` that sets the `application/problem+json` media type:

=== Challenges (RFC 6750, RFC 9470 and RFC 9449)

A resource that rejects a token sets a `WWW-Authenticate` header, and the client acts on it:

[cols="3,3,4",options="header"]
|===
|Header
|Meaning
|Where it comes from

|`+Bearer error="invalid_token"+`
|The token is missing, expired, badly signed or has the wrong audience (RFC 6750 section 3.1)
|`BearerTokenAuthenticationEntryPoint` on the resource server and on the account API chain

|`+Bearer error="insufficient_scope"+`
|The token is valid but lacks the scope (`403`)
|Spring Security's bearer token access denied handling

|`+Bearer error="insufficient_user_authentication", acr_values="...", max_age="..."+`
|The sign-in is too old or too weak; sign the user in again with these parameters (RFC 9470)
|`StepUpAccessDeniedHandler` on the resource server and `MfaExceptionHandler` on the account API

|`+DPoP error=...+`
|A DPoP-bound token was sent as `Bearer`, or the proof is missing or invalid (RFC 9449 section 7)
|The framework's DPoP support, enabled in the resource server chain
|===
