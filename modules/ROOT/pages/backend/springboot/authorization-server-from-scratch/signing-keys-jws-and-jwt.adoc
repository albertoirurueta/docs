= Authorization Server from Scratch: Signing Keys, JWS & JWT
:description: How the irurueta-auth-server example creates, stores, rotates and publishes its JWT signing keys: RSA keys encrypted at rest with AES-GCM, a database-backed JWKSource with separate signing and public views, a lock-protected NEXT, ACTIVE and RETIRED rotation with a retention window, the JwtEncoder, and the KMS and HSM alternatives.
:keywords: JWS, JWT, JWK, JWKS, kid, RS256, signing keys, key rotation, retention, JWKSource, JwtEncoder, NimbusJwtEncoder, NimbusJwtDecoder, BytesEncryptor, Encryptors.stronger, AES-GCM, PBKDF2, advisory lock, KMS, HSM, PKCS#11, RFC 7515, RFC 7517, RFC 7519, Spring Authorization Server, Mermaid

include::partial$ai-disclaimer.adoc[]

Every token the authorization server signs is only as trustworthy as the key that signed it, and a key that never
changes is a key that is eventually leaked. This page builds the part of the example that owns those keys: how an RSA
key pair is generated, how its private half is stored encrypted, how the public half is published at `/oauth2/jwks`, how
a new key replaces an old one without invalidating a single token that is still alive, and how the `JwtEncoder` that
signs the tokens is wired to all of it.

== What you build

* A `signing_keys` table that holds every key with a lifecycle `status` of `NEXT`, `ACTIVE` or `RETIRED`, and a
  database rule that allows at most one `ACTIVE` key.
* An RS256 key generator whose private half leaves the generator already encrypted with AES-256-GCM, with a key derived
  from a passphrase and a salt that never appear in logs.
* Two views of the same keys: the public JWKS (active, next and still-valid retired keys, public halves only) and the
  signing set (the single active key, with its private half, which only the `JwtEncoder` sees).
* A rotation use case, run at startup, on a schedule and on demand, that is safe to run on several instances at once.
* A signed-token service that issues and verifies the example's own purpose-bound tokens (for example the
  e-mail verification token), pinned to RS256.

The theory (what `kid`, `alg` and a JWKS are, the classic attacks and why keys must rotate) is in the OAuth Reference:
read xref:backend/oauth/jwt-and-jose.adoc[JWT and the JOSE Family] first, in particular its sections on signing
algorithms and on JWKS, `kid`, key rotation and caching. This page is the Spring Boot implementation of that
checklist. The decoded structure of the token that these keys sign is the one in the figure below.

image::oauth-jwt-anatomy.svg["A decoded JWT: the dot-separated compact form with the header, payload and signature, each decoded below it",width=700,role=text-center]

The access tokens, ID tokens and refresh tokens themselves, and the claims the example puts in them, are built on the
Access, Refresh and ID Tokens page of this guide; the key store is the common ground.

== How it works

Three entry points trigger the same `RotateSigningKeysUseCase`, all through a thin `SigningKeyRotator`
component that publishes an event afterwards so the caches refresh at once:

* `SigningKeyBootstrapRunner` runs at startup, so a fresh database gets an `ACTIVE` key and a `NEXT` key before the
  first request.
* `SigningKeyRotationJob` runs on a schedule (`authserver.keys.rotation.cron`, hourly by default) and only rotates a
  key that has been active for the whole `authserver.keys.rotation-interval`.
* `POST /api/admin/keys/rotate` forces a rotation whatever the age of the key, for example after a suspected
  compromise.

== Data

A key is one row. The private half is stored as `private_jwk_encrypted` (Base64 text of the AES-GCM ciphertext) and the
public half as a plain JWK, so listing the keys or publishing the JWKS never needs the passphrase.

The three states are enforced by the `ck_signing_keys_status` check, and the partial unique index
`uq_signing_keys_single_active` is the database's guarantee that two instances can never both have an active key. See

=== Encrypting the private key at rest

pair is created once in the owner-only file `.irurueta-auth-server/key-encryption` under the user's home directory, and
a warning is logged). The properties record refuses to be created without them and never prints them.

`AesGcmKeyCipher` wraps Spring Security's `Encryptors.stronger`, which derives an AES-256 key from the passphrase and the
salt and uses GCM, so a modified ciphertext fails to decrypt instead of decrypting to garbage.

=== One secret, one key per purpose

The same passphrase is also the root of other, unrelated secrets (the trusted-device cookie signature and the TOTP
secrets). `PurposeKeyDerivation` gives each purpose its own salt and key so that no two uses share a key. The signing-key
cipher keeps the configured salt itself, so keys that are already stored still decrypt.

[source,java]
----
include::irurueta-auth-server::example$auth-server/infrastructure/keys/src/main/java/com/irurueta/authserver/authorization/infrastructure/keys/PurposeKeyDerivation.java[tag=keys-purpose-derivation]

The derivation is PBKDF2 with HMAC-SHA-256, specified in https://www.rfc-editor.org/rfc/rfc8018[RFC 8018]; see also the

=== Rotating

The use case applies three transitions in one pass: retire the active key if it is due (or if the rotation is forced),
promote the `NEXT` key to `ACTIVE` (generating one first if there is none), and make sure a new `NEXT` key exists.
Finally it deletes the retired keys whose retention has passed. Everything runs inside `withRotationLock`, so two
instances that start their schedule at the same instant cannot both create an active key.

[source,java]
----
include::irurueta-auth-server::example$auth-server/application/src/main/java/com/irurueta/authserver/authorization/application/keys/RotateSigningKeysUseCase.java[tag=keys-rotation]
----

The scheduling is Spring's `@Scheduled`; see the https://docs.spring.io/spring-framework/reference/integration/scheduling.html[Task Execution and Scheduling]
reference.

The lock is a PostgreSQL transaction-scoped advisory lock, taken as the first statement of a transaction and released
when it ends, which also means a crashed instance cannot leave it held.

[source,java]

See https://www.postgresql.org/docs/current/explicit-locking.html#ADVISORY-LOCKS[Advisory Locks] in the PostgreSQL documentation.

=== Retention

How long a retired key stays published is derived, not guessed. The effective retention is the longer of the configured
`authserver.keys.retention` (two hours by default) and the longest lifetime of any token the server signs plus
`authserver.keys.clock-skew` (60 seconds by default). The lifetimes come from the registered clients (the seeded clients issue
10-minute self-contained access tokens, and the ID token lifetime is 30 minutes) and from the 24-hour e-mail
verification token. In the example as shipped the verification token is the longest, so a retired key is in practice
kept for a little over a day. Registering a client with longer-lived tokens lengthens the window automatically.

[source,java]
----
include::irurueta-auth-server::example$auth-server/application/src/main/java/com/irurueta/authserver/authorization/application/keys/SigningKeyRetention.java[tag=keys-retention]
----

The rule is the one RFC 8725 and the OAuth Reference ask for: a verifier must be able to find the key of any token it may
still be handed. See https://www.rfc-editor.org/rfc/rfc8725[RFC 8725: JSON Web Token Best Current Practices].

=== Signing and verifying with the encoder

`NimbusSignedTokenService` is the example's own use of the encoder and the decoder, for tokens that are not OAuth tokens
(for instance the e-mail verification link). It signs a JWT with the issuer, subject, issued-at, expiry and a
`purpose` claim, always with the RS256 header; and it verifies with a decoder over the public keys, with the algorithm
pinned to RS256, the issuer and the timestamps validated, and then the purpose compared. Every failure (expired,
tampered, other issuer, other purpose, malformed) is the same empty result, so a caller cannot tell why a token was refused.

[source,java]
----
include::irurueta-auth-server::example$auth-server/infrastructure/keys/src/main/java/com/irurueta/authserver/authorization/infrastructure/keys/NimbusSignedTokenService.java[tag=jwt-service]
----

See the https://docs.spring.io/spring-security/reference/servlet/oauth2/resource-server/jwt.html[Spring Security JWT resource server reference]
and https://www.rfc-editor.org/rfc/rfc7519[RFC 7519: JSON Web Token]. The signature format itself is
https://www.rfc-editor.org/rfc/rfc7515[RFC 7515: JSON Web Signature].

[source,shell]
----

  -H "Authorization: Bearer $ADMIN_TOKEN"
----

Each element of the array has the `kid`, `alg`, `status`, `createdAt`, `activatedAt`, `retiredAt` and `publicJwk` properties
of the `SigningKeyResponse` schema above. Without a token the answer is `401`, and with a token that lacks the `admin`
scope it is `403`.

The public keys are served by Spring Authorization Server at `/oauth2/jwks` and need no authentication. The response is a
JWK Set whose members are the public halves only, one per published key, each with its `kid`:

[source,shell]
----
curl -s http://localhost:9000/oauth2/jwks
----

A resource server reads this document once, caches it, and fetches it again when it meets a `kid` it does not know.

== Alternatives: KMS and HSM

Keeping an encrypted private key in the application database is a deliberate trade-off for a self-contained example: the
passphrase protects the keys at rest, but whoever can read both the database and the passphrase can sign tokens. In
production the usual answer is to keep the private key where it cannot be read at all, and sign by asking a service to do
it. The pieces that change are small, because the example already isolates the keys behind two views:

* The *public* `JWKSource` does not change: the public keys can still be listed from a table or fetched from the key
  service (for example
  https://docs.aws.amazon.com/kms/latest/developerguide/overview.html[AWS Key Management Service]
  can export the public key of an asymmetric KMS key).
* The *signing* side changes. `NimbusJwtEncoder` needs a `JWKSource` that returns a key with a private half, which a
  KMS or an HSM never gives away. Instead you provide a `JwtEncoder` of your own that builds the signing input
  (the Base64url header and payload) and has the service sign it, using Nimbus's `JWSSigner` interface, or you wrap the
  service in a custom `JWSSigner`. The `kid` of the published key must be the identifier of the remote key.
* *Rotation* moves to the service: check in each provider's documentation whether automatic rotation covers asymmetric
  signing keys, and if not, rotate by creating a new key and re-pointing an alias. Versioned keys (as in Google Cloud KMS
  and Azure Key Vault) play the role of the `NEXT`, `ACTIVE` and `RETIRED` states here. The retention-window logic of
  this page applies unchanged.
* A *PKCS#11 HSM* is reached through the JDK's `SunPKCS11` provider, which exposes the key as a `PrivateKey` whose bytes
  cannot be extracted; Nimbus's `RSASSASigner` can be given such a key together with the provider, so only the key loading differs.

Official starting points: https://aws.amazon.com/kms/[AWS KMS], https://cloud.google.com/kms/docs[Google Cloud KMS],
https://learn.microsoft.com/en-us/azure/key-vault/general/overview[Azure Key Vault] and the
https://docs.oracle.com/en/java/javase/21/security/pkcs11-reference-guide1.html[Java PKCS#11 Reference Guide]. The cost
of the remote option is a network call on every signature, which is why signing short-lived tokens in volume is
usually combined with a local cache or with signing only the longer-lived tokens remotely.

== Tests

The behaviour is covered at three levels, described here rather than pasted because these test classes carry no tag in
the example: `RotateSigningKeysUseCaseTest` and `SigningKeyRetentionTest` exercise the transitions and the retention
arithmetic with a fixed clock, `AesGcmKeyCipherTest` shows that encrypting twice gives different text and that a
tampered or wrongly keyed value is rejected, and `KeyRotationIT` runs the whole stack against PostgreSQL. It checks that
a fresh start publishes the active and next keys with no private parts, that a token signed before a rotation validates
until its key is removed, that a key retired longer than the configured retention is kept while its tokens may still
be alive, and that the admin endpoints return no private material and reject a caller without the `admin` scope.

== Security notes and pitfalls

* *Never generate a key at startup in production.* The common tutorial pattern of building a `KeyPair` in a `@Bean`
  method gives each instance its own key and a new one on every restart: tokens stop validating across instances and
  after a deploy. Keys here live in the database and every instance reads the same ones.
* *Always set a `kid`, and let the verifier select by it.* The generator gives every key a random UUID, and the JWKS
  lists several keys at once, which is only workable if tokens carry the `kid` of the key that signed them.
* *Pin the algorithm.* `NimbusSignedTokenService` builds its decoder with RS256 only and the header it issues is always
  RS256, which closes the `alg: none` and the key-confusion attacks that RFC 8725 describes. Never read the algorithm from
  the token to decide how to verify it.
* *Encrypt private keys at rest, and keep the passphrase out of the database.* The passphrase and the salt come from
  configuration or the environment, never from a file in the repository, and `KeyEncryptionProperties` redacts itself
  in logs. Changing the passphrase makes every stored private key undecryptable, so it is a migration, not a setting.
* *Back up the keys and the passphrase together, and test the restore.* A database backup without the passphrase is a
  set of keys that cannot sign: every token issued so far is still verifiable, but nothing new can be issued. One
  rotation is not enough to recover, because it promotes the existing `NEXT` key, whose private half was encrypted
  with the lost passphrase too. Delete the `NEXT` row before forcing the rotation (or force two rotations), so the
  key that becomes `ACTIVE` is generated and encrypted with the new passphrase.
* *Rotate on a schedule and after any suspected compromise,* and remember that a forced rotation stops signing with the
  old key immediately but still publishes it for the retention window so legitimate tokens keep working. If the key
  itself leaked, the tokens it signed must be treated as compromised for that window too: shorten the retention
  or delete the key row.
* *Rotate under a lock.* Without `withRotationLock` two instances can both promote a key and both create a `NEXT`
  key; the unique index would then reject one of them as an error at best.
* *Keep the JWKS cache short and refresh it on rotation.* The 30-second default bounds how long a stale key set can be
  served; verifiers that cache the JWKS for hours need the retention window to cover them as well.
