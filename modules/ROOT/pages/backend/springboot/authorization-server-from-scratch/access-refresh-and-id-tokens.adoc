= Authorization Server from Scratch: Access, Refresh and ID Tokens
:description: How the irurueta-auth-server example issues access, refresh and ID tokens: lifetimes and formats from the seeded clients, the claims that every token carries, refresh token rotation with reuse detection, the UserInfo mapper, and the clean-up of abandoned authorizations.
:keywords: access token, refresh token, ID token, JWT, reference token, opaque token, OAuth2TokenCustomizer, JwtEncodingContext, OAuth2TokenClaimsContext, TokenSettings, OAuth2TokenFormat, refresh token rotation, reuse detection, OAuth2AuthorizationService, UserInfo, introspection, revocation, consumed_refresh_tokens

include::partial$springboot-disclaimer.adoc[]

This page shows how the authorization server *mints* tokens: which formats and lifetimes the seeded clients use, how
the same custom claims reach both self-contained (JWT) and reference (opaque) access tokens, how a refresh token is
rotated and how the replay of a rotated token revokes the whole authorization, and what the UserInfo endpoint returns.
The theory is in the OAuth Reference:
xref:backend/oauth/access-and-refresh-tokens.adoc[Access and Refresh Tokens],
xref:backend/oauth/id-tokens-vs-access-tokens.adoc[ID Tokens vs. Access Tokens] and
xref:backend/oauth/opaque-tokens-introspection-and-revocation.adoc[Opaque Tokens, Introspection and Revocation].
It is not repeated here. How the tokens are *signed* is the subject of the Signing Keys, JWS & JWT page of this
section, and how a resource server *validates* them is the subject of the resource server page.

== What you build

Spring Authorization Server already generates and stores the tokens. The example configures three things on top of it:

* *Token settings per client*, stored with the registered client: format, lifetimes and whether refresh tokens are reused.
* *Claims*: one class, `IssuedTokenClaims`, decides which claims a token gets, and two small customizers apply it, one
  for JWTs and one for reference tokens. Other features add claims through the `JwtClaimsContributor` extension point.
* *Refresh token reuse detection*: a decorator of the `OAuth2AuthorizationService` that remembers rotated-out refresh
  tokens by their hash.

== Formats and lifetimes

The values below are the ones the example *sets*, taken from `DefaultClientDefinitions` (the `clients-seed` region) and
mapped onto Spring's `TokenSettings` by `RegisteredClientMapper` (the `tokens-settings` region), not framework defaults.

[cols="2,3,3,3",options="header"]
|===
|Token
|Format
|Lifetime
|Where it comes from

|Access token
|`self-contained` (a signed JWT) for both seeded clients. A client can be registered with the `reference` format
instead, which makes the token an opaque string that the resource server introspects.
|10 minutes (`bff` and `spa-public`)
|`accessTokenFormat` and `accessTokenTimeToLive` of `TokenSettings`.

|Refresh token
|Opaque random string. Once rotated out, only its SHA-256 hash is kept (see below).
|8 hours (`bff` and `spa-public`)
|`refreshTokenTimeToLive`. `reuseRefreshTokens` is `false`, so *every refresh rotates the token*.

|ID token
|Always a signed JWT (OpenID Connect Core).
|Not set by the example code: Spring Authorization Server fixes the lifetime of the ID tokens it generates.
|Issued only when the `openid` scope is granted. Both seeded clients request `openid`.

|Authorization code
|Opaque, single use.
|Framework default, not changed by the example.
|Consumed at the token endpoint; see the Authorization Code and PKCE guides in the OAuth Reference.
|===

The table of the seeded clients (secret type, scopes, consent) is on the Registered Clients page of this section. The
access token lifetime is deliberately short: a JWT cannot be revoked once issued, so the refresh token, which can be
revoked, carries the session.

== How it works

=== Refresh rotation and reuse detection

With `reuseRefreshTokens` set to `false`, every successful refresh response carries a *new* refresh token and the old
one stops being valid. `ReuseDetectingAuthorizationService` wraps the JDBC `OAuth2AuthorizationService` and records the
SHA-256 hash of every refresh token that a `save` rotates out. If a token that is no longer current is presented again,
`findByToken` cannot find it in the delegate, finds its hash in `consumed_refresh_tokens`, and removes the authorization
the token belonged to: the thief and the legitimate client both lose the session, and the user signs in again.

[mermaid]
....
sequenceDiagram
    autonumber
    participant C as Client
    participant T as Token endpoint
    participant S as ReuseDetectingAuthorizationService
    participant D as Delegate (JDBC) and consumed_refresh_tokens
    C->>T: POST /oauth2/token grant_type=refresh_token, refresh_token=R1
    T->>S: findByToken(R1, refresh_token)
    S->>D: delegate.findByToken(R1)
    D-->>S: authorization (R1 is current)
    T->>S: save(authorization with R2)
    S->>D: findById, then delegate.save
    S->>D: INSERT hash(R1) into consumed_refresh_tokens
    T-->>C: new access token and R2
    Note over C,D: later, the old token R1 is replayed
    C->>T: POST /oauth2/token grant_type=refresh_token, refresh_token=R1
    T->>S: findByToken(R1, refresh_token)
    S->>D: delegate.findByToken(R1)
    D-->>S: null (R1 was rotated out)
    S->>D: SELECT authorization_id WHERE token_hash = hash(R1)
    D-->>S: the authorization id
    S->>D: delegate.remove(authorization): the family is revoked
    S-->>T: null
    T-->>C: 400 invalid_grant
    C->>T: refresh with R2
    T-->>C: 400 invalid_grant (the authorization no longer exists)
....

The `consumed_refresh_tokens` rows reference `oauth2_authorization` with `ON DELETE CASCADE`, so revoking the authorization
also deletes its list of consumed hashes: a *second* replay of `R1` after the revocation finds nothing and is simply
an unknown token (still `invalid_grant`). The `ReuseDetectingAuthorizationServiceIT` and `TokenFlowIT` tests (below)
exercise this exact sequence.

=== Which claims a token gets

[mermaid]
....
flowchart TD
    G[Token being issued] --> K{Token type}
    K -- access token JWT --> J["RolesTenantAudienceTokenCustomizer (JwtEncodingContext)"]
    K -- access token reference --> R["ReferenceTokenClaimsCustomizer (OAuth2TokenClaimsContext)"]
    K -- ID token JWT --> J
    J --> I[IssuedTokenClaims.apply]
    R --> I
    I --> A{Access token?}
    A -- yes --> B["roles, tenant (user grants only), aud from the client setting"]
    A -- no, ID token --> C[no built-in claims]
    B --> X["every JwtClaimsContributor, in order"]
    C --> X
....

A token of the client credentials grant has no user, so it gets no `roles` and no `tenant`, only the audience. `roles`
are the authorities of the user *without* the `FACTOR_` authorities, which record how the user signed in (see the
Multi-Factor Authentication page) and are not permissions.

Two details of the region matter. `save` compares the stored refresh token with the new one and records the hash only
when it *changed*, so saves that do not rotate record nothing. `findByToken` only looks in the consumed list when the
lookup is for a refresh token (or for an unknown token type) and the delegate found nothing.

== API

These endpoints are defined by their specifications, so they are not part of the project's own OpenAPI contract. The
examples assume the authorization server on `http://localhost:9000`; replace the placeholders with your own values.

Refresh with the confidential `bff` client (`client_secret_basic`):

[source,bash]
----
curl -s -u "bff:<client-secret>" http://localhost:9000/oauth2/token \
  -d grant_type=refresh_token \
  -d refresh_token=<refresh-token>
----

The response carries a *new* `refresh_token` and a new `access_token`; the old refresh token is now rotated out. The
public `spa-public` client has no secret and sends `-d client_id=spa-public` instead of `-u`. Presenting a rotated token
again returns `400` with `+{"error":"invalid_grant"}+`.

Revoke a token (RFC 7009) and introspect it (RFC 7662):

[source,bash]
----
curl -s -u "bff:<client-secret>" http://localhost:9000/oauth2/revoke \
  -d token=<refresh-token> -d token_type_hint=refresh_token

curl -s -u "bff:<client-secret>" http://localhost:9000/oauth2/introspect \
  -d token=<access-token>
----

Revocation answers `200` with an empty body even for an unknown token. Introspection returns `+{"active":false}+` for a
revoked, expired or unknown token, and for an active one `active`, `scope`, `client_id`, `exp`, `aud`, `roles` and
`tenant`.

UserInfo, with the access token of a user:

[source,bash]
----
curl -s -H "Authorization: Bearer <access-token>" http://localhost:9000/userinfo
----

The response always has `sub`. With the `profile` scope it adds `preferred_username`, `roles` and `tenant`; with the
`email` scope, `email` and `email_verified`. A missing or invalid token is rejected with `401`.

See https://datatracker.ietf.org/doc/html/rfc6749#section-6[RFC 6749, Refreshing an Access Token],
https://datatracker.ietf.org/doc/html/rfc7009[RFC 7009] and https://datatracker.ietf.org/doc/html/rfc7662[RFC 7662], and the
https://docs.spring.io/spring-security/reference/servlet/oauth2/authorization-server/protocol-endpoints.html[Protocol Endpoints reference].

== Tests

None of the regions below is tagged, so the tests are described, not pasted:

* `TokenFlowIT` (module `auth-server/boot`) runs the real endpoints: a user access token carries audience, roles and
  tenant; a client credentials token has the audience but no user claims; a refresh rotates the token; *a rotated token
  that is reused revokes the authorization, and the current token stops working*; revoking an access or a refresh token
  works; introspection reports active and unknown tokens and returns audience, roles and tenant for a reference token;
  UserInfo contains the profile and email claims for the granted scopes and is rejected without a valid token.
* `ReuseDetectingAuthorizationServiceIT` runs the decorator against a real database: the replay of a rotated token
  revokes the authorization, and a save that does not rotate the token records nothing.
* `CleanExpiredAuthorizationsUseCaseTest` covers the clean-up of expired and abandoned authorizations.

== Security notes and pitfalls

* *Rotation protects public clients.* A SPA cannot keep a secret, so a stolen refresh token is as good as the client.
  Rotation plus reuse detection turns a theft into a forced sign-in instead of a silent, lasting session.
* *Reuse detection is not instant revocation of access tokens.* A JWT access token stays valid until it expires
  (10 minutes here). Short lifetimes, or the `reference` format with introspection, are the levers.
* *A benign replay revokes too.* A client that loses the response to a refresh and retries with the old token revokes
  its own session. The design trades that for security; give clients a retry that falls back to a new sign-in.
* *Clean up abandoned authorizations.* An authorization or consent request that never got a token has no expiry. The
  `created_at` column lets `ExpiredAuthorizationCleanupJob` (cron `authserver.tokens.cleanup.cron`, hourly by default)
  delete those older than `authserver.tokens.cleanup.abandoned-after` (one day by default), together with expired ones.
* *Minimise claims.* Every claim in a JWT is readable by the client and the browser. Put roles and tenant in access
  tokens for resource servers, not in ID tokens, and keep UserInfo scope-limited, as `UserInfoMapper` does.
* *Never log tokens.* The consumed list stores hashes for that reason; the revocation warning logs the authorization id,
  never the token.
* *Use the audience.* `aud` comes from the client setting, so a token minted for one API is not accepted by another;
  the resource server page shows the check.
