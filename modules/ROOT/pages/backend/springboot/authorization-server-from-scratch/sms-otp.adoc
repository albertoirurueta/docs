== What you build

This page adds the *SMS channel* to the one-time-token machinery of the example. A user first *verifies a phone
number*: the server sends a code by SMS, the user types it back and the number is stored as the account's verified
phone. From then on the number can be used in two ways:

* *SMS login*: on the sign-in page the user asks for a code by SMS and posts it, with no password. The sign-in is a
  primary factor that is reported as `amr` `sms`.
* *SMS as a second factor*: after the password, the second-factor page offers "Send me a code by SMS", and the
  tokens then carry `sms`, `otp` and `mfa`.

A verified phone is also a *confirmed second factor*: as soon as an account has one, multi-factor authentication is
required for it, even for clients that do not ask for it (see the Multi-Factor Authentication & Step-Up page of this guide).

The theory is in the OAuth Reference section
xref:backend/oauth/authentication-methods-2fa-and-passwordless.adoc#_sms_one_time_code_otp[SMS one-time code (OTP)] and, for the second
factor, xref:backend/oauth/authentication-methods-2fa-and-passwordless.adoc#_e_mail_or_sms_otp_as_a_second_factor[E-mail or SMS OTP as a second factor].
NIST SP 800-63B classes the public switched telephone network (SMS and voice) as a *restricted authenticator*: it is
still permitted, but the verifier has to offer an alternative, warn the user about its limits and take the risk of
SIM changes and number porting into account. See https://pages.nist.gov/800-63-4/sp800-63b.html[NIST SP 800-63B-4], in
particular the section on authentication using the public switched telephone network. The example treats SMS as a
*fallback with guard rails*, not as a default, which is why most of this page is about limits.

The code generation, hashing, single-use and attempt-counting machinery is the same as for e-mail codes, and it is
explained once in xref:backend/springboot/authorization-server-from-scratch/email-otp-and-magic-links.adoc[E-mail OTP and Magic Links]. This page covers only what SMS adds: the phone
number, the gateway, the cost control and the account page.

== How it works

=== Phone verification

A user adds a number on the account page (`/account/phone`) or through the REST API. The number is normalised to
E.164, the country is checked against an allow-list, a code is hashed and stored as a *pending* verification, and
the SMS is sent *after the transaction commits*. The number only becomes the verified phone when the code is
confirmed.

[mermaid]
....
sequenceDiagram
    autonumber
    actor U as User
    participant P as PhonePageController
    participant S as StartPhoneEnrolmentUseCase
    participant C as SendSmsOneTimeCodeUseCase
    participant L as sms_cost_ledger
    participant E as OttDeliveryListener
    participant G as SmsSender
    participant V as ConfirmPhoneUseCase
    participant DB as user_phones
    U->>P: POST /account/phone (number)
    P->>P: Step-up check, then rate limit per address and per account
    P->>S: execute(userId, number)
    S->>S: Normalise to E.164, check the country allow-list
    S->>DB: Save the pending number with the hashed code
    S->>C: execute(number, message)
    C->>L: tryRecord(country, cost, window cap, daily cap)
    C-->>E: SmsRequested event, after commit
    P-->>U: 303 to /account/phone?status=pending
    E->>G: send(number, text)
    G-->>U: SMS with the code
    U->>P: POST /account/phone/verify (code)
    P->>V: execute(userId, username, code)
    V->>DB: Match the hash, store phone_e164 and verified_at, delete the pending data
    P-->>U: 303 to /account/phone?status=verified
....

Two details are deliberate. The answer is `pending` *whether or not the number already belongs to another
account*, and in that case nothing is sent, so the enrolment endpoint cannot be used to find out which numbers are
registered. And the SMS is handed to the gateway only after the commit, from an `@Async` listener, so a slow or
failing gateway never shows in the response and never holds a database connection.

=== Login with an SMS code

The login and second-factor flows are the one-time-token flows of the e-mail page, with the channel `sms`. The user
names the account, the server looks up its *verified phone*, and a code is sent to it.

[mermaid]
....
sequenceDiagram
    autonumber
    actor U as User
    participant B as Browser
    participant R as POST /ott/generate
    participant Q as RequestOneTimeCodeUseCase
    participant C as SendSmsOneTimeCodeUseCase
    participant E as OttDeliveryListener
    participant G as SmsSender
    participant A as POST /login/ott
    U->>B: Chooses the SMS method and types the username
    B->>R: username, channel sms, kind code, purpose login
    R->>Q: execute(username, SMS, LOGIN)
    Q->>Q: Resolve the verified phone, if there is none do nothing
    Q->>Q: Store the hashed code with its expiry
    Q->>C: execute(phone, message)
    C->>C: Country allowed? Spend within both caps?
    C-->>E: SmsRequested event, after commit
    R-->>B: The same redirect to the code page as for any username
    E->>G: send(phone, text)
    G-->>U: SMS with the code
    U->>B: Types the code
    B->>A: code
    A->>A: Check the hash, attempts and expiry, grant FACTOR_OTT_SMS
    A-->>B: Signed in, asked for a second factor when MFA is required
....

When the user is already signed in with a password and the account requires a second factor, the same flow runs with
the purpose `second-factor`, posts to `/login/second-factor/ott` and grants `FACTOR_OTT_SMS_2FA`. Which channels the
second-factor page offers is decided by one small component, shown in the Code section: SMS is offered only to an
account with a verified phone, and never when SMS itself signed the user in.

== Risks and mitigations

SMS is the weakest of the one-time-code channels, and some of its risks are outside the application. The table
says what the example does about each one and what remains.

[cols="2,4,4",options="header"]
|===
|Risk
|What the example does
|What remains

|*SIM swap* (an attacker ports the victim's number to another SIM)
|A verified phone is a *second* factor next to the password by default. Replacing the verified number requires a
recent multi-factor sign-in (step-up) when the account already has a second factor, and confirming a *different* number
revokes every trusted device of the account and records a `SECOND_FACTOR_REMOVED` security event.
|The application cannot see a SIM change. Offer a stronger factor (a passkey or an authenticator app) and
treat SMS as a fallback, as NIST recommends.

|*SMS pumping and toll fraud* (an attacker triggers many messages to premium or attacker-controlled numbers)
|Only the countries of `authserver.sms.allowed-countries` receive messages. Every message first records its cost in the
`sms_cost_ledger` table through an atomic check against a per-window cap and a per-day cap, kept in the database so a
restart cannot reset them. Requests are also limited per client address and per account or username (the
`authserver.ott.rate-limit` settings).
|The caps are global, not per number or per country: an attack inside an allowed country can still use up the budget
and deny SMS to everyone until the window passes. Add per-country caps and gateway-side fraud protection in production.

|*Interception* (SS7 weaknesses, malware that reads messages, shoulder surfing)
|Codes are short-lived (10 minutes by default), single use, stored only as a hash, and a code is spent after
five wrong attempts. A code is bound to the request that created it.
|A code in transit is readable by the network and the phone. The channel is not phishing resistant:
a real-time phishing site can relay the code at once.

|*Number recycling* (an operator gives a former subscriber's number to someone else)
|A number belongs to *one* account (`uq_user_phones_phone_e164`), and a pending enrolment does not reserve it.
Removing the phone is always possible.
|The application cannot know that a number was reassigned. A stale number is a risk until the user changes it,
so keep an alternative recovery path and expire unused phones by policy.

|*Enumeration* (finding out which usernames or numbers exist)
|The response to a request for a code is the same for an unknown user, a user without a verified phone, a number that
belongs to another account, a country that is not allowed and a spent budget. Nothing is sent in those cases and the
caller cannot tell them apart. The phone page and the API show only the last four digits of the number.
|Timing differences are small but not eliminated: the code is generated and hashed before the destination is
resolved, which keeps the work of the known and the unknown case alike.
|===

The shared limiter keeps four sets of fixed-window buckets (generation and verification, each per client address and per

identifier, so one account cannot request unlimited codes from many addresses.

The schemas follow the https://spec.openapis.org/oas/v3.1.0#schema-object[OpenAPI 3.1 Schema Object] rules.

Start the enrolment. The number may be international or in the national form of the default region; the answer is
`202` and says how long the code is valid:

[source,bash]
----
curl -s -X PUT http://localhost:9000/api/account/phone \
  -H "Authorization: Bearer ${TOKEN}" \
  -H "Content-Type: application/json" \
  -d '{"phone":"+34 600 11 22 33"}'
----

Confirm it with the code from the SMS (four to ten digits). The answer is the masked number and the verification time:

[source,bash]
----
curl -s -X POST http://localhost:9000/api/account/phone/verify \
  -H "Authorization: Bearer ${TOKEN}" \
  -H "Content-Type: application/json" \
  -d '{"code":"123456"}'
----

Read the verified phone, masked so that only the last four digits show, and remove it:

[source,bash]
----
curl -s http://localhost:9000/api/account/phone \
  -H "Authorization: Bearer ${TOKEN}"

curl -s -X DELETE http://localhost:9000/api/account/phone \
  -H "Authorization: Bearer ${TOKEN}"
----

The errors follow the contract: `400` for a number that is not valid (`urn:problem:phone:invalid-phone`), a country that
receives no SMS (`urn:problem:phone:country-not-allowed`) or a wrong, expired or missing code
(`urn:problem:phone:invalid-code`); `401` without a valid token or without the step-up (with the RFC 9470 challenge); `404`
when the account has no verified phone; and `429` over a rate limit. Removing a phone that is not set succeeds with `204`.

== Tests

CI never calls a real SMS gateway: the integration tests run with the logging sender and read the codes from its outbox.
The example covers the feature at three levels, described here in prose because none of these tests carries a tag:

* *Sign-in integration tests*: `OttSmsIT` checks that a user with a verified phone who asks for a code by SMS and posts it
  signs in without a password and is then asked for a second factor (because a verified phone makes MFA required), that
  neither channel that already signed the user in is offered again, that the tokens carry `sms`, `otp` and `mfa`, that a
  code sent as the second factor after the password issues multi-factor tokens, that a wrong code is redirected back with an error,
  and that confirming a code stores the verified phone. `OttSmsLimitsIT` checks that nothing is sent to a country that is not on
  the allow-list, neither as a sign-in code nor as an enrolment code, and that once the spend of the window reaches
  its cap no more messages are sent while every request is still answered the same way.
* *API and configuration integration tests*: `PhoneApiIT` covers the enrolment without a step-up when the account has no second
  factor, the step-up challenge when it has one and the token is password only, the revocation of the trusted devices and the
  audit event when a new number replaces the verified one or the only second factor is removed, and a number that
  another user verified in the meantime. `SmsSenderProfilesIT` proves that the logging sender is the bean under `test` and `dev`,
  that it is not under a gateway profile, and that the application refuses to start with no sender profile and names the
  profiles to choose from.
* *Persistence integration tests* against a real PostgreSQL: `JdbcUserPhoneRepositoryIT`, `JdbcPhoneVerificationRepositoryIT`
  and `JdbcSmsCostLedgerRepositoryIT` check the constraints of `V620` and `V630` and the atomic cap check of the ledger.

The unit tests cover the use cases (normalisation, country check, attempt counting, the replacement of a number), the cost
policy and the adapters with a fake gateway client.

== Security notes and pitfalls

* *SMS is a restricted authenticator.* NIST SP 800-63B still allows it, with an alternative on offer and a warning to the
  user. Offer a passkey or an authenticator app, and use SMS for the users who cannot.
* *The cost cap is a safety net, not a defence.* It limits the money an attack can burn, and it does so for everyone at
  once. Combine it with per-country and per-number limits, a gateway-side fraud filter and an alert when the daily spend
  approaches its cap.
* *Keep the allow-list short.* A country that is not on the list receives nothing, so the premium-rate destinations
  that toll fraud targets are excluded by default. Review the list when the business changes.
* *Same answer, always.* The endpoints answer identically for unknown users, numbers of other accounts, refused countries
  and exhausted budgets. Do not add a helpful error message to any of them.
* *Never log the number or the code.* The logging sender records only the last four digits, and the delivery listener logs only the
  class of an exception. The clear code exists only in the message and in the process memory that sends it.
* *Credentials stay in the environment.* The Twilio and SNS credentials come from environment variables or the default
  AWS credential chain, never from a file in the repository.
* *The dev inbox shows secrets.* `/dev/sms-inbox` lists the text of every message, codes included. It exists only
  under `dev`, and the application refuses to start with no sender profile, so a production deployment can neither
  expose it nor silently keep messages in memory.
* *Changing the number is changing the factor.* Replacing a verified number needs a recent multi-factor sign-in and
  revokes the trusted devices, otherwise a stolen password-only session could redirect the second factor to the attacker's phone.
* *Phones need a recovery path.* A lost phone or a recycled number locks the user out or hands the factor to a stranger.
  Keep recovery codes, as on the xref:backend/springboot/authorization-server-from-scratch/totp-and-recovery-codes.adoc[TOTP and Recovery Codes] page,
  and a documented support process.

For the full reference see https://pages.nist.gov/800-63-4/sp800-63b.html[NIST SP 800-63B-4],
https://www.rfc-editor.org/rfc/rfc9470[RFC 9470] for the step-up challenge and the
https://cheatsheetseries.owasp.org/cheatsheets/Multifactor_Authentication_Cheat_Sheet.html[OWASP Multifactor Authentication Cheat Sheet].
