== What you build

Everything so far authenticated a *person*. This page covers the other caller of an API, a *service* with no browser and
no user at the keyboard. The example has a command line application, `service-client`, that obtains access tokens on its
own, calls `GET /api/documents` on the resource server, and can also call it on behalf of a signed-in user. The page
builds four capabilities:

* the *client credentials* grant: the client authenticates to the token endpoint and receives a short-lived access token
  whose subject is the client itself, cached and renewed shortly before it expires;
* *client authentication without a shared secret*: a signed assertion with `private_key_jwt` (RFC 7523), or a TLS client
  certificate with `tls_client_auth` and `self_signed_tls_client_auth`, which also yield *certificate-bound* access
  tokens (RFC 8705);
* *sender-constrained tokens with DPoP* (RFC 9449): the `service-client` has a code path that sends a proof of possession with every call;
* *token exchange* (RFC 8693): the client trades the access token of a user, plus its own token as actor, for an
  audience-restricted token that names the user as subject and the client in an `act` claim, so a downstream call is made
  as the user, by the service.

The theory lives in the OAuth Reference pages
xref:backend/oauth/client-credentials-and-client-authentication.adoc[],
xref:backend/oauth/sender-constrained-tokens-dpop-and-mtls.adoc[] and
xref:backend/oauth/token-exchange-and-assertion-grants.adoc[], and this page does not repeat it. It shows what Spring
Authorization Server gives out of the box, and the parts the example adds because the framework does not do them:

* *replay protection* for client assertions (the framework neither requires a `jti` nor remembers one);
* *registered public keys* for `private_key_jwt`, stored with the client instead of fetched from a URL;
* a *trust anchor check* for `tls_client_auth` (the TLS port accepts any chain, so the application validates it);
* the *audience restriction* of exchanged tokens (the framework parses `audience` but ignores it).

The settings of a client that uses these methods (a JWK set, a signing algorithm, a certificate subject) are stored and
validated as described in
xref:backend/springboot/authorization-server-from-scratch/registered-clients.adoc#_advanced_client_authentication_settings[Registered Clients, Advanced client authentication settings].
How a resource server validates the resulting tokens, including the thumbprint and proof checks, is on
xref:backend/springboot/authorization-server-from-scratch/resource-server.adoc#_sender_constrained_tokens[Protecting APIs, Sender-constrained tokens].

Only `bff` and `spa-public` are seeded (the `clients-seed` region of
xref:backend/springboot/authorization-server-from-scratch/registered-clients.adoc[Registered Clients & Client Management]).
A service client is not seeded: it is registered through the admin API, so no client identifier, secret or key of a
service is ever part of the source. The rows above that name `service-client` describe how the tool is configured and how
the end-to-end tests register the client.

=== `private_key_jwt`

The client signs a short JWT (the *assertion*) with its private key and sends it in place of a secret. The server finds
the client's public keys, verifies the signature and the claims, and records the `jti` so the same assertion cannot be
used twice (RFC 7523, section 3).

[mermaid]
....
sequenceDiagram
    autonumber
    participant C as service-client
    participant T as POST /oauth2/token
    participant P as JwtClientAssertionAuthenticationProvider
    participant F as RegisteredJwksClientAssertionDecoderFactory
    participant V as ReplayRejectingJwtValidator
    participant DB as client_assertion_jtis
    C->>C: Sign an assertion (iss = sub = client id, aud = token URI, jti, iat, exp)
    C->>T: grant_type=client_credentials, client_assertion_type, client_assertion
    T->>P: Authenticate the client
    P->>F: createDecoder(registered client)
    F-->>P: Decoder over the registered JWK set (cached per client and settings hash)
    P->>P: Verify signature, issuer, subject, audience, expiry
    P->>V: validate(assertion)
    V->>V: jti, iat and exp present, lifetime within the maximum
    V->>DB: Insert (client id, jti) if new
    alt the jti was already used
        DB-->>V: Nothing inserted
        V-->>T: invalid_client, the assertion was already used
        T-->>C: 401
    else first use
        DB-->>V: Inserted
        V-->>P: Success
        P-->>T: Client authenticated
        T-->>C: 200 with the access token
    end
....

The validators run in fail-fast order, so the replay check, which writes, runs only for an assertion that passed every
default check. A refused assertion therefore never consumes its `jti`.

=== A certificate-bound token with mTLS

With `tls_client_auth` the client presents an X.509 certificate during the TLS handshake on a dedicated port (the
`authserver.x509.port` connector that also serves X.509 sign-in) and identifies itself with `client_id`. The server
validates the chain, compares the subject, and, if the client asked for certificate-bound tokens, puts the SHA-256
thumbprint of the certificate in the `cnf` claim of the token. The resource server accepts that token only on a
connection that presents the same certificate.

[mermaid]
....
sequenceDiagram
    autonumber
    participant C as service-client
    participant T as Token endpoint on the TLS port
    participant V as ClientCertificateVerifier
    participant R as Resource server
    C->>T: TLS handshake with the client certificate
    C->>T: grant_type=client_credentials, client_id
    T->>V: accept(context)
    V->>V: PKIX path validation against authserver.mtls.trusted-authorities
    V->>V: Leaf subject DN equals the registered one
    V-->>T: Client authenticated
    T->>T: Framework adds cnf with the x5t S256 thumbprint of the certificate
    T-->>C: Access token, certificate-bound
    C->>R: TLS handshake with the same certificate, then GET /api/documents
    R->>R: Thumbprint in cnf equals the thumbprint of the presented certificate
    R-->>C: 200 with the documents
    Note over C,R: The same token sent without the certificate, or with another one, is refused with invalid_token
....

For `self_signed_tls_client_auth` the check is different: the certificate must be self-signed and its public key must be
one of the keys of the client's registered JWK set. The server also advertises the TLS addresses of its endpoints in the
`mtls_endpoint_aliases` metadata claim (RFC 8705, section 5), so a client can discover which URL to call with a
certificate.

=== Token exchange

The `service-client` receives the access token of a user (in the end-to-end test it is obtained through the BFF) and
wants to call the resource server as that user. It does not forward the user's token; it exchanges it.

[mermaid]
....
sequenceDiagram
    autonumber
    actor U as User
    participant S as service-client
    participant T as POST /oauth2/token
    participant X as TokenExchangeAudienceContributor
    participant R as Resource server
    U->>S: Hands over their access token (the subject token)
    S->>T: client_credentials, to get its own token (the actor token)
    T-->>S: Actor token
    S->>T: grant_type=token-exchange, subject_token, actor_token, audience, scope
    T->>T: The framework checks the grant, the subject and actor tokens, the scopes
    T->>X: contribute(context, claims)
    X->>X: Keep only the requested audiences the client may have
    alt none of the requested audiences is allowed
        X-->>T: invalid_target
        T-->>S: 400
    else
        X-->>T: aud narrowed
        T-->>S: Access token, sub is the user, act names the service-client
    end
    S->>R: GET /api/documents with the exchanged token
    R-->>S: The user's own documents
....

The subject of the exchanged token stays the *user*, so the resource server applies the user's ownership rules; the
`act` claim records that the service-client acted. The framework writes `act` itself from the actor token.

== Data

Spring Authorization Server does not keep a record of used client assertions. The example adds one table, `client_assertion_jtis`
(migration `V800`), keyed by the client and the `jti`. An insert that does not add a row means the assertion was used
before. A scheduled job deletes the rows after they expire, because a row matters only while its assertion could still
be accepted.

=== Finding the keys of a client

The factory has two paths. A client with a registered JWK set is verified against those keys; any other client goes
through the framework's factory. Both end with the default assertion validators (issuer, subject, audience, expiry) and
then the replay validator. The framework's factory caches a decoder per client forever, so this one caches its own
decoders by client identifier and a hash of the settings that decide the keys. When an administrator replaces a client's
keys, the next assertion is verified against the new ones, not the cached old ones.

[source,java]
----

Reference: https://docs.spring.io/spring-security/reference/api/java/org/springframework/security/oauth2/server/authorization/authentication/JwtClientAssertionDecoderFactory.html[JwtClientAssertionDecoderFactory].

The framework's default validators do not require a `jti` and keep no replay store, so this validator fills the gap
(RFC 7523, section 3). It requires `jti`, `iat` and `exp`, refuses an `iat` in the future, limits `exp` minus `iat` to
`authserver.client-assertion.max-lifetime`, and records the use last.

== API

The requests below go to the token endpoint of the example's default local address. They are the requests the Spring
clients of the previous section send, written as `curl` so each parameter is visible. `+${...}+` values are placeholders;
none is a real secret.

*Client credentials with a client assertion.* The assertion is a JWT you sign with the client's private key. Its claims
are `iss` and `sub` equal to the client identifier, `aud` the token endpoint, a fresh `jti`, `iat`, and an `exp` no more
than `authserver.client-assertion.max-lifetime` after `iat`. The client sends no `client_secret`:

[source,bash]
----
curl -s -X POST http://localhost:9000/oauth2/token \
  -d grant_type=client_credentials \
  -d scope=documents.read \
  -d client_assertion_type=urn:ietf:params:oauth:client-assertion-type:jwt-bearer \
  -d client_assertion="${CLIENT_ASSERTION}"
----

Sending the same assertion twice answers `401` with `invalid_client` the second time.

*Client credentials with mutual TLS.* The request goes to the TLS port, with the client certificate and key, and carries
`client_id` as the only identification (RFC 8705, section 2):

[source,bash]
----
curl -s -X POST https://localhost:${MTLS_PORT}/oauth2/token \
  --cacert server-ca.pem --cert client.pem --key client.key \
  -d grant_type=client_credentials \
  -d client_id="${CLIENT_ID}" \
  -d scope=documents.read
----

When the client is registered with certificate-bound tokens, the access token carries `+cnf.x5t#S256+` with the thumbprint
of `client.pem`, and the resource server accepts it only over a connection that presents that certificate.

*Token exchange.* The form parameters are those of RFC 8693, section 2.1. The client authenticates as usual (here with
`client_secret_basic`), and its registration must include the grant type
`urn:ietf:params:oauth:grant-type:token-exchange`:

[source,bash]
----
curl -s -X POST http://localhost:9000/oauth2/token \
  -u "${CLIENT_ID}:${CLIENT_SECRET}" \
  -d grant_type=urn:ietf:params:oauth:grant-type:token-exchange \
  -d subject_token="${USER_ACCESS_TOKEN}" \
  -d subject_token_type=urn:ietf:params:oauth:token-type:access_token \
  -d actor_token="${CLIENT_ACCESS_TOKEN}" \
  -d actor_token_type=urn:ietf:params:oauth:token-type:access_token \
  -d requested_token_type=urn:ietf:params:oauth:token-type:access_token \
  -d audience=resource-server \
  -d scope=documents.read
----

The response is an ordinary token response. Its access token has the user as `sub`, the client in `act`, the audience
narrowed to the requested ones the client may have, and no refresh token. The contract of the client administration API,
which is how these clients are registered, is shown on
xref:backend/springboot/authorization-server-from-scratch/registered-clients.adoc#_api[Registered Clients, API].

== Tests

The example covers this feature at several levels. None of these tests carries a tagged region, so they are described here
and not pasted:

* `ClientAuthenticationIT` (authorization server) runs the real chain against each client authentication method:
  secret (right and wrong), `private_key_jwt` with registered keys and with a `jwkSetUrl`, a replayed `jti`, an assertion
  that lives too long, `tls_client_auth` accepted only for a trusted authority, `self_signed_tls_client_auth` with a
  registered and an unregistered key, the certificate thumbprint in the token, and a DPoP-bound token.
* `TokenExchangeIT` covers the exchange: a valid subject and actor token (the token is the user's and the client is the
  actor), an audience that is not allowed (`invalid_target`), a client without the grant, a token this server did not
  issue, and a `may_act` claim that excludes or names the actor.
* `JdbcClientAssertionReplayRegistryIT` runs the registry against the real database: the same pair twice is a replay,
  the same `jti` of another client is a first use, concurrent registration has exactly one winner, and the purge removes
  only expired rows.
* `ServiceClientApplicationIT` checks that the application starts with no profile and with each of the
  `client-credentials` and `token-exchange` profiles. `ResourceServerAdapterIT` checks that a token is reused across
  calls, that it is renewed when it expires within the margin, that a `private_key_jwt` assertion is signed with the
  configured key, that an exchange uses the client token as actor, that DPoP sends the proof and the scheme, and that
  refusals become a domain exception.
* `ClientCredentialsEndToEndIT` and `TokenExchangeEndToEndIT` start the authorization server and the resource server and
  run the real `service-client` as a process: one client per method (secret, `private_key_jwt`, `tls_client_auth`,
  `self_signed_tls_client_auth`) and DPoP, then the exchange on behalf of a user who signed in through the BFF, ending
  with the resource server returning that user's documents. Keys and certificates are generated at run time; none is
  committed.

== Security notes and pitfalls

* *Rotate client keys without downtime.* A client may register several public keys in its JWK set, so a new key can be
  added before the old one is removed and assertions signed with either verify during the overlap. The decoder cache is
  keyed by a hash of the stored keys, so a change takes effect on the next assertion.
* *Keep the assertion lifetime short.* The default maximum is five minutes (`PT5M`). A short lifetime bounds how long a
  captured assertion could be replayed and how many `jti` rows the table must keep.
* *`jti` replay is enforced in the database.* The record is shared by every instance of the server, so a replay is
  refused even when it lands on another instance. If the table is unreachable, authentication fails, which is the safe
  direction.
* *Restrict the audience of exchanged tokens.* An exchanged token should be usable at one API, not everywhere the
  client may call. The example narrows `aud` and refuses the request with `invalid_target` when nothing requested is
  allowed. Do not rely on the framework to do it.
* *Use least-privilege scopes.* Register a service client with only the scopes it needs, and request only those. The
  framework refuses scopes outside the registration. A token exchange never widens the scopes of the subject token past
  those of the exchanging client.
* *Allow token exchange deliberately.* The grant is explicit in the client's registration. A subject token that carries
  `may_act` limits which client may act on it. Without `may_act` any actor token is accepted, so keep the grant to the
  clients that need it.
* *Pin trust for mutual TLS.* With no trusted authority configured, `tls_client_auth` is refused rather than accepting
  every chain. Revocation is not checked by the example: add a CRL or OCSP check before relying on this in production.
  Terminating TLS at a proxy changes where the certificate is seen, so a forwarded certificate must be trusted only from
  that proxy.
* *Prefer sender-constrained tokens for powerful APIs.* A bearer token works for whoever holds it. A certificate-bound
  or DPoP-bound token is useless to a thief without the certificate or key. The resource server must enforce the binding,
  as shown on the Protecting APIs page.
* *Never ship client secrets or keys in code.* No client identifier of a service, secret, private key or certificate is
  in the repository. The tool reads the secret and the key from the environment or a file, and tests generate theirs at
  run time. Unencrypted PKCS#8 keys in an environment variable are acceptable for a demonstration; in production keep
  the key in a secret store or an HSM and mount it as a file.
* *Prefer `private_key_jwt` or mTLS over a shared secret* for services. The server holds only a public key, so a database
  leak does not let anyone authenticate as the client.
