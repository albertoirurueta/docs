= Authorization Server from Scratch: Storing Passwords Securely
:description: How the irurueta-auth-server example stores and checks passwords: a DelegatingPasswordEncoder with Argon2 as default and bcrypt and PBKDF2 for legacy hashes, upgrade on sign-in, a NIST-style PasswordPolicy, the Have I Been Pwned check, a user-enumeration-safe DaoAuthenticationProvider, and the registration and password-reset flows with their account REST API.
:keywords: password storage, DelegatingPasswordEncoder, Argon2, Argon2PasswordEncoder, bcrypt, PBKDF2, scrypt, UserDetailsPasswordService, upgradeEncoding, DaoAuthenticationProvider, CompromisedPasswordChecker, HaveIBeenPwnedRestApiPasswordChecker, PasswordPolicy, NIST SP 800-63B, OWASP, user enumeration, password reset token, registration, rate limiting, Bucket4j, Spring Security, Spring Boot

include::partial$ai-disclaimer.adoc[]

Storing a password is a one-way operation: the server keeps a salted, deliberately slow hash and never the password
itself, so a leaked database does not hand out working credentials. This page shows how the example does it with
nothing but Spring Security building blocks: which encoder hashes new passwords, how an old hash is replaced the next
time its owner signs in, which rules a new password must follow, how a leaked password is refused, and how the account
endpoints (registration and password reset) avoid revealing which users exist. The protocol-level background, where
passwords are the baseline primary factor that the other methods are compared with, is in
xref:backend/oauth/authentication-methods-2fa-and-passwordless.adoc#_passwords_as_the_baseline_primary_factor[Passwords as the baseline primary factor];
this page is its implementation.

== What you build

* A `PasswordEncoder` bean that is a `DelegatingPasswordEncoder`: every stored hash starts with an `+{id}+` prefix
  naming the algorithm that made it, so the server can verify old hashes and still encode new ones with the current
  default. The example encodes with *Argon2id*, and still verifies *bcrypt* and *PBKDF2* hashes.
* *Upgrade on sign-in*: when a user signs in with a hash made by an older algorithm, the verified clear-text password is
  re-encoded with the default and stored, with no password-reset campaign.
* A `PasswordPolicy` in the style of NIST SP 800-63B (length limits and a username check, no composition rules) applied
  everywhere a password is chosen, and a *compromised-password check* against the Have I Been Pwned range API.
* A `DaoAuthenticationProvider` declared by hand so that a wrong password always gets the same answer, whether the
  account exists, is disabled or does not exist.
* The self-service account flows: registration with e-mail verification, password change and password reset with a
  single-use, hashed, expiring token, all rate limited.

The external references behind the choices are the
https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html[OWASP Password Storage Cheat Sheet],
https://pages.nist.gov/800-63-4/sp800-63b.html[NIST SP 800-63B-4 (Digital Identity Guidelines: Authentication and Authenticator Management)]
and the Spring Security
https://docs.spring.io/spring-security/reference/features/authentication/password-storage.html[Password Storage] reference.

== How it works

A hash is stored as `+{id}encodedPassword+`. `DelegatingPasswordEncoder.encode` always uses the default id;
`matches` reads the prefix of the stored hash and delegates to the encoder registered under that id;
`upgradeEncoding` answers `true` when the prefix is not the default id (or when the delegate itself finds its
parameters outdated). That last method is what makes the upgrade on sign-in possible.

The sequence below is a sign-in through the login form with a stored bcrypt hash. `DaoAuthenticationProvider` calls
`upgradeEncoding` on the stored hash after the password matched, encodes the password it just verified with the default
algorithm and hands the result to the `UserDetailsPasswordService`, which the example implements in the same class
that loads the user.

[mermaid]
....
sequenceDiagram
    autonumber
    actor U as User
    participant F as Login form (POST /login)
    participant P as DaoAuthenticationProvider
    participant S as UserAccountUserDetailsService
    participant E as PasswordEncoder (delegating)
    participant C as UpgradePasswordHashUseCase
    participant R as UserAccountRepository (JDBC)
    U->>F: username and password
    F->>P: authenticate(username, password)
    P->>S: loadUserByUsername(username)
    S->>R: find the account (users, user_passwords, user_authorities)
    R-->>S: account with the stored hash, prefix bcrypt
    S-->>P: UserDetails
    P->>E: matches(password, stored hash)
    E-->>P: true
    P->>P: post-authentication checks (account enabled, not locked)
    P->>E: upgradeEncoding(stored hash)
    E-->>P: true, the id is not the default
    P->>E: encode(password)
    E-->>P: new hash, prefix argon2
    P->>S: updatePassword(user, new hash)
    S->>C: replaceHash(account, new hash)
    C->>R: updatePassword(user id, new hash)
    P-->>F: authenticated
....

If the password did not match, none of the steps from step 9 on runs, so a failed sign-in never touches the stored
hash. The account status is checked only *after* the password, which is a deliberate choice explained in
<<_security_notes_and_pitfalls,Security notes and pitfalls>>.

=== Which algorithm for new hashes

The example registers three encoders in its `DelegatingPasswordEncoder` and uses the defaults of each Spring Security
factory method, so none of the parameters below is a value the example chose: they are the documented defaults of the
`+..._v5_8+` factories (a version label that Spring Security keeps stable so existing hashes still verify). The
`scrypt` and `NoOp` rows are not registered in the example and are listed for comparison.

[cols="2,3,3,3",options="header"]
|===
|Encoder (`+{id}+` prefix)
|Parameters used
|Registered in the example
|When to use it

|`Argon2PasswordEncoder` (`+argon2@SpringSecurity_v5_8+`)
|Argon2id with salt 16 bytes, hash 32 bytes, parallelism 1, memory 2^14 KiB (16 MiB) and 2 iterations
|Yes, the *default* for every new hash
|First choice for new systems: memory-hard, so it resists GPU and ASIC cracking. It needs BouncyCastle on the class
path, which is why `auth-server` declares `bcprov-jdk18on`. The OWASP cheat sheet asks for at least 19 MiB, 2
iterations and parallelism 1, so these defaults are slightly *below* that floor: tune the constructor
(`+new Argon2PasswordEncoder(...)+`) to your hardware, aiming at about one second per verification.

|`BCryptPasswordEncoder` (`bcrypt`)
|Strength 10 (the default of the no-argument constructor)
|Yes, legacy hashes only
|Acceptable when Argon2 is not available. It truncates passwords at 72 bytes and is not memory-hard, so keep it
for verifying old hashes and let the upgrade replace them.

|`Pbkdf2PasswordEncoder` (`+pbkdf2@SpringSecurity_v5_8+`)
|PBKDF2-HMAC-SHA-256 with salt 16 bytes, 310,000 iterations and a 256-bit hash, no extra secret
|Yes, legacy hashes only
|When FIPS 140 validated algorithms are mandatory. OWASP currently recommends 600,000 iterations for
HMAC-SHA-256, so 310,000 is outdated for new hashes.

|`SCryptPasswordEncoder` (`+scrypt@SpringSecurity_v5_8+`)
|CPU cost 65,536, memory cost 8, parallelization 1, key length 32, salt 16 bytes
|No
|The fallback OWASP names when Argon2id is unavailable; the Spring default is weaker than OWASP's minimum
(N = 2^17), so raise it if you choose it.

|`NoOpPasswordEncoder`
|none, the password is stored as typed
|No
|*Never.* It is deprecated and exists only for tests and tutorials.
|===

The prefix gives the migration path between encoders: to move to a new algorithm, register it, make it the default id
and keep the old encoders registered until `upgradeEncoding` has rewritten the hashes of every active user.

xref:backend/springboot/authorization-server-from-scratch/data-model.adoc[Data Model and Schema]: the encoded

This derives from the https://pages.nist.gov/800-63-4/sp800-63b/passwords/[NIST SP 800-63B-4 password requirements], which ask for a minimum length, a generous maximum and no composition rules.

The policy is a plain domain class with no Spring dependency, exposed as a bean by `PasswordPolicyConfiguration` so a
deployment can replace it. The constants are `MIN_LENGTH` 12 and `MAX_LENGTH` 128, counted in code points; the only
content rule is that the password does not contain the username, compared ignoring case. A broken rule is reported as
a `PasswordViolation` (`TOO_SHORT`, `TOO_LONG`, `CONTAINS_USERNAME`), which the use cases turn into a `400` answer.

The check is on by default and is switched off with the property `authserver.password.compromised-check.enabled=false`,
which registers a no-op check instead (useful offline and in tests). The range API
(https://haveibeenpwned.com/API/v3#PwnedPasswords[Pwned Passwords]) only receives the first characters of the

password*; the example does not declare a Spring `CompromisedPasswordChecker` bean, so the sign-in provider below
does not check a password at every login.

=== The authentication provider

[source,java]
----
include::irurueta-auth-server::example$auth-server/api/web/src/main/java/com/irurueta/authserver/authorization/api/web/password/PasswordAuthenticationConfiguration.java[tag=password-authentication-provider]

This derives from the Spring Security https://docs.spring.io/spring-security/reference/servlet/authentication/passwords/dao-authentication-provider.html[DaoAuthenticationProvider] reference, whose provider the bean replaces to change the order of its checks.

`DaoAuthenticationProvider` normally checks the account status (disabled, locked, expired) *before* the password. The
bean sets no pre-authentication checks and an `AccountStatusUserDetailsChecker` as post-authentication check, and it
keeps `hideUserNotFoundExceptions` on, so the answer to a wrong password is the same generic one for a known account,
a disabled account and an unknown username. Because the bean is the only `AuthenticationProvider`, Spring Security
logs a startup warning that the `UserDetailsService` bean is not used to build one; the example silences that
warning on purpose in `application.yml`.

=== Registration

[source,java]
----
include::irurueta-auth-server::example$auth-server/application/src/main/java/com/irurueta/authserver/authorization/application/account/RegisterAccountUseCase.java[tag=account-register]
----

This derives from the https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html#authentication-and-error-messages[OWASP Authentication Cheat Sheet] guidance on uniform messages, which the use case follows for taken addresses and usernames.

The order matters. The policy and the compromised check run first, so a bad password is rejected whatever the account
state is. The password is then hashed *in every case*, before the taken-address check, so a registration costs the
same time whether or not the address or username exists. A registered address receives a neutral "already
registered" e-mail, and a new address with a taken username receives a normal verification message whose token names
no account (it fails like an expired link), so the endpoint reveals no username. The account is created disabled and
unverified, and saving it and sending the message happen in one transaction: if the mail cannot be sent, nothing is
registered.

== API

chain: registration, verification, reset request and reset are public and rate limited, and the password change
needs a bearer token issued by this server.

----

This is a fragment of an https://spec.openapis.org/oas/latest.html[OpenAPI] description; errors use `application/problem+json` as defined by https://www.rfc-editor.org/rfc/rfc9457[RFC 9457].

Against the local development instance (`http://localhost:9000`), with placeholder values:

[source,shell]
----
# register: always 202, whether or not the address or the username is taken
curl -i -X POST http://localhost:9000/api/account/register \
  -H 'Content-Type: application/json' \
  -d '{"username":"alice","email":"alice@example.com","password":"<a passphrase of 12 to 128 characters>"}'

# verify the e-mail address with the token in the message; it works once
curl -i 'http://localhost:9000/api/account/verify?token=<token from the e-mail>'

# request a reset link: always 202
curl -i -X POST http://localhost:9000/api/account/password/reset-request \
  -H 'Content-Type: application/json' \
  -d '{"email":"alice@example.com"}'

# choose a new password with the token from the e-mail: 204, or 400 for a bad token or a rejected password
curl -i -X POST http://localhost:9000/api/account/password/reset \
  -H 'Content-Type: application/json' \
  -d '{"token":"<token from the e-mail>","newPassword":"<a new passphrase>"}'

# change the password of the signed-in account (bearer token issued by this server): 204, 400 or 401
curl -i -X POST http://localhost:9000/api/account/password \
  -H "Authorization: Bearer $ACCESS_TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"currentPassword":"<current>","newPassword":"<new>"}'
----

A rejected password answers `400` with a problem body; a request over the limit answers `429` with a `Retry-After`
header in seconds (https://www.rfc-editor.org/rfc/rfc6585#section-4[RFC 6585]). A registration whose
confirmation e-mail cannot be sent answers `503` and registers nothing.

== Tests

The behaviours above are covered by tests that this page describes and does not paste, because none of them carries
an include tag:

* `PasswordConfigurationTest` encodes with the bean and checks that the hash is Argon2 and matches, that a different
  value does not match, that a bcrypt hash matches and asks for an upgrade, and that a PBKDF2 hash matches.
* `PasswordUpgradeIT` (PostgreSQL container, real login form) stores a bcrypt hash, signs in and checks that the stored
  hash now starts with the Argon2 prefix, still matches and no longer asks for an upgrade; a wrong password leaves the
  hash untouched and a hash that is already current is not rewritten.
* `PasswordAuthenticationIT` checks that a disabled account with a wrong password shows the same page as an unknown
  user, and that only the correct password reveals the "disabled" message.
* `ResetPasswordUseCaseTest` covers an unusable token, a concurrently consumed token, a password that breaks the
  policy, contains the username or is compromised, each without consuming the token.
* `AccountApiIT` drives the endpoints above end to end: e-mail verification enables the account, a taken address
  answers like a new one, a token works once, a rejected password keeps the token usable, a replayed verification
  link does not re-enable a disabled account, and a limit exceeded answers `429`.
* `PasswordPolicyTest` covers the length bounds and the username rule.

== Security notes and pitfalls

* *User enumeration.* Registration, reset request and sign-in answer identically for known and unknown identifiers,
  and the work done is made equal (the password is hashed and a token is generated either way) so timing does not
  leak it either. The only message that depends on the account, "disabled", appears after the correct password.
  Equalising the time of an unknown username at sign-in relies on `DaoAuthenticationProvider` encoding a dummy
  password for it; keep `hideUserNotFoundExceptions` on.
* *Rate limiting.* The unauthenticated account endpoints are limited twice, per client address and per e-mail
  address, with Bucket4j buckets in `AccountRateLimiter`. The limits in `application.yml` are 20 requests per client and
  5 per address in a 15 minute window, with at most 10,000 tracked keys; the buckets live in the memory of one
  instance, so several instances need a shared store. Behind a proxy, `server.forward-headers-strategy` must be set or
  every request appears to come from the proxy.
+
[source,java]
----
include::irurueta-auth-server::example$auth-server/api/web/src/main/java/com/irurueta/authserver/authorization/api/web/account/AccountRateLimiter.java[tag=account-rate-limit]
----
+
This derives from the https://bucket4j.com[Bucket4j] token-bucket library that the class builds on.
* *Token hygiene.* Reset and verification tokens are random, stored only as a hash, expire, and are consumed by one
  atomic statement. A reset also revokes the user's authorizations. The
  https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html[OWASP cheat sheet] explains why the
  link must be single use and short lived.
* *Pepper.* The example does not use a pepper (a secret added to every password before hashing and kept outside the
  database, in a vault or HSM). OWASP describes it as an optional extra layer; if you add one, it must survive a
  migration between encoders, so version it (for example in the encoder id) like the algorithm.
* *Migration between encoders.* Keep every legacy encoder registered until no active user has a hash with its prefix.
  Accounts that never sign in are never upgraded; decide when to expire or force a reset for them.
* *Parameters age.* The Spring factory defaults are a floor for compatibility, not a recommendation for your
  hardware: measure a verification on production-like machines, and raise the Argon2 memory and iterations before the
  next hash rotation.
* *Never log or return a password or a token.* The OpenAPI schemas mark them with the `password` format for that
  reason, and the compromised-password check sends only a hash prefix.
* *Length limit.* The policy caps passwords at 128 characters so a very long input cannot be used to make a hash
  computation expensive.
