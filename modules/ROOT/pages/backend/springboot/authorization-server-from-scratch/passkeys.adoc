== What you build

This page adds *passkeys* to the example: public-key credentials held by an authenticator (a phone, a laptop, a security
key or a password manager) and bound to the host name of the server. A passkey plays two roles:

* a *passwordless primary login*: the user clicks a button on the login page, or picks the passkey that the browser
  offers in the username field, and signs in without typing anything;
* a *second factor* after a password: a user who has at least one passkey is asked for it on the second-factor page
  instead of, or as an alternative to, a TOTP code.

The theory (what a passkey is, why it resists phishing, how synced and device-bound passkeys differ) lives in the OAuth
Reference sections xref:backend/oauth/authentication-methods-2fa-and-passwordless.adoc#_passkeys_webauthn_fido2[]
and xref:backend/oauth/authentication-methods-2fa-and-passwordless.adoc#_hardware_otp_tokens_and_passkeys_used_as_a_second_factor[],
and the Spring Boot options are compared in xref:backend/oauth/spring-boot-authentication-methods.adoc#_passkeys[].
This page does not repeat them. For the protocol itself see the W3C
https://www.w3.org/TR/webauthn-3/[Web Authentication Level 3] specification, and for a practical introduction
https://passkeys.dev/docs/intro/what-are-passkeys/[passkeys.dev].

Spring Security 7.1 does most of the protocol work. Its `webAuthn()` DSL installs the four filters that serve the
registration and authentication ceremonies, verifies the signed assertions with the WebAuthn4J library, and defines the
repositories that store users and credentials. The example adds what a real server needs around them:

* the *factor*: a `PasskeyFactor` that registers the `FACTOR_WEBAUTHN` authority as a strong primary factor, so a
  passkey alone satisfies the multi-factor policy and the tokens report it in `amr` and `acr`;
* the *rules of the chain*: public endpoints, registration only for a session that satisfies the multi-factor policy,
  no framework-owned deletion, a session strategy that changes the session id, and a user service that refuses disabled
  accounts;
* the *pages and the browser script*: a section of the login page, a button on the second-factor page and an account
  page where a passkey is named and registered;
* the *account API*: list, rename and delete passkeys, with a step-up for the deletion;
* the *JSON mapper module* that lets the WebAuthn types be stored in the authorization server's serialized objects.

== How it works

A passkey ceremony has two halves: the *server* produces a random challenge and the options of the ceremony, and the
*authenticator*, reached through the browser's `navigator.credentials` API, signs it. The browser refuses to talk to an
authenticator for a relying party id that does not match the host of the page, which is what makes the credential
phishing resistant. The server then checks the signature, the challenge, the origin and the relying party id.

=== Registration

The user is already signed in and opens the account page. The script of the page asks the framework endpoints for the
creation options, hands them to the authenticator and sends back the new credential together with the name the user chose.

[mermaid]
....
sequenceDiagram
    autonumber
    actor U as User
    participant JS as Browser script passkeys.js
    participant N as navigator.credentials
    participant A as Authenticator
    participant O as POST /webauthn/register/options
    participant R as POST /webauthn/register
    participant DB as user_entities and user_credentials
    U->>JS: Types a name and clicks Register
    JS->>O: POST with the CSRF header
    O->>DB: Find or create the user entity named like the account
    O-->>JS: challenge, rp, user, excludeCredentials
    JS->>JS: Decode challenge, user.id and excludeCredentials from base64url
    JS->>N: create(publicKey)
    N->>A: Create a credential for the relying party id
    A->>U: Asks for user verification
    A-->>N: Attestation object and client data
    N-->>JS: PublicKeyCredential
    JS->>R: POST credential and label
    R->>R: Verify challenge, origin and relying party id
    R->>DB: Save the credential record with its label
    R-->>JS: success true
    JS->>JS: Reload the account page
....

`excludeCredentials` lists the passkeys the account already has, so an authenticator that holds one is not registered a
second time. If the session still has a second factor to complete, the options request is redirected to the
second-factor page, and the script follows that redirect instead of showing an error.

=== Authentication

The same ceremony serves the login page (button or autofill) and the second-factor page. The options request carries no
username: the authenticator picks a discoverable credential and sends its user handle, and the server finds the account
from the stored credential.

[mermaid]
....
sequenceDiagram
    autonumber
    actor U as User
    participant JS as Browser script passkeys.js
    participant N as navigator.credentials
    participant A as Authenticator
    participant O as POST /webauthn/authenticate/options
    participant L as POST /login/webauthn
    participant DB as user_entities and user_credentials
    U->>JS: Clicks Use a passkey, or picks one in the username field
    JS->>O: POST with the CSRF header
    O-->>JS: challenge, rpId, allowCredentials
    JS->>N: get(publicKey), conditional mediation for autofill
    N->>A: Sign the challenge for the relying party id
    A->>U: Asks for user verification
    A-->>N: authenticatorData, clientDataJSON, signature, userHandle
    N-->>JS: PublicKeyCredential
    JS->>L: POST the assertion
    L->>DB: Load the credential by id
    L->>L: Verify signature, challenge, origin, relying party id and counter
    L->>DB: Update signature count and last use
    L->>L: Load the user, refuse a disabled account, grant FACTOR_WEBAUTHN
    L-->>JS: authenticated true and redirectUrl
    JS->>JS: Go to the saved authorization request
....

When the user already signed in with a password, the success keeps the factors of the session: Spring Security merges
the existing factor authorities into the result when the names match, so the user ends with `FACTOR_PASSWORD` and
`FACTOR_WEBAUTHN`. That is why the user entity is named exactly like the username of the account. Multi-factor
requirements, `amr` and `acr` are explained in
xref:backend/springboot/authorization-server-from-scratch/multi-factor-authentication.adoc[Multi-Factor Authentication & Step-Up].

The customizer is where the rules are:

* the options, the sign-in post and the script are public (CSRF stays on, and the script sends the token);
* the framework's `+DELETE /webauthn/register/{id}+` is denied, so a passkey can only be removed through the account API,
  which asks for a recent multi-factor sign-in;
* the registration endpoints and the account page require a session that satisfies the multi-factor policy, so a session
  that only presented a password cannot register a passkey and then sign in with it, skipping the second factor;
* a passkey used as a second factor is refused while the second factor of the user is locked;
* `webAuthn()` receives the relying party and a post-processor that gives its filter the chain's session strategy.

=== The factor

A passkey alone satisfies the policy, because the authenticator proves possession of the key and, with user
verification, the user as well. The tokens report `hwk` (RFC 8176, a key held in hardware or in a platform authenticator)
in `amr`, together with `pwd` and `mfa` when a password came first. A synced passkey is reported the same way; the
backup flags are exposed by the account API.

== API

Spring Security owns four endpoints. All of them are `POST` and need the CSRF token, because the options endpoints change
server state:

[cols="3,3,4",options="header"]
|===
|Endpoint
|Who may call it
|Purpose

|`+POST /webauthn/authenticate/options+`
|Anyone
|Returns the challenge, the relying party id and the allowed credentials of an authentication ceremony.

|`+POST /login/webauthn+`
|Anyone
|Verifies the assertion. The answer is JSON, `+{"authenticated":true,"redirectUrl":"..."}+` on success and `401` on failure.

|`+POST /webauthn/register/options+`
|A session that satisfies the multi-factor policy
|Returns the creation options, including `excludeCredentials`.

|`+POST /webauthn/register+`
|A session that satisfies the multi-factor policy
|Verifies the attestation and stores the credential with its label. The answer is `+{"success":true}+`.
|===

== Tests

None of the passkey tests carries a tag for inclusion, so they are described here.

* `PasskeyConfigurationIT` checks the sign-in as the login chain applies it: the endpoints the chain permits with CSRF on,
  a passkey as the second factor after a password and as the only factor, the merge of the session's factors, the
  resumption of the saved authorization request with a new session id, the claims of the issued tokens (the same as a
  password sign-in), the refusal of a disabled account and of a locked second factor, and the same answer for an
  unknown credential and a rejected assertion. The relying party operations are mocked, so it needs no authenticator.
* `PasskeyRegistrationIT` runs the real operations and repositories: the user entity carries the username, a session
  that only presented a password cannot register a passkey while the account needs a second factor, the framework's
  own removal endpoint and default page are gone, and the authentication options never depend on a username.
* `PasskeyPagesIT` renders the pages: the passkey section of the login page with its external script, the script served
  anonymously, the second-factor page with and without a passkey, and the account page.
* `PasskeyAccountIT` covers the account API: list, rename (including a blank or too long label), deletion, the step-up
  challenge, the revocation of trusted devices, and that an account never sees or touches another account's passkeys.
* `JdbcPasskeyRepositoryIT` runs against PostgreSQL on the `V500` schema: lookups by account, ownership checks on
  rename and delete, the unique user entity name, and the round trip of the instants.
* `PasskeyEndToEndIT` drives a real headless Chromium with a virtual authenticator (CTAP2, internal, resident key, user
  verified) through the Chrome DevTools Protocol, so the script runs the real ceremonies. It registers a passkey and signs in
  through the BFF with it alone, signs in with a password and completes the second-factor page with the passkey, and lets
  the browser offer the passkey in the username field.

These are Spring MockMvc and Testcontainers integration tests plus a browser test; see the
https://docs.spring.io/spring-security/reference/servlet/test/mockmvc/index.html[Spring Security MockMvc testing reference]
and the https://developer.chrome.com/docs/devtools/webauthn[Chrome DevTools WebAuthn emulation].

== Security notes and pitfalls

* *Phishing resistance and the RP ID.* The authenticator signs for a relying party id, and the browser refuses a page
  whose host does not match it. Set `rp-id` to the public host name (or a registrable suffix) and `allowed-origins` to the
  exact origins that run the ceremonies, never to a wildcard. The default `localhost` is for local runs only, and a
  credential registered under one relying party id does not work under another, so changing it later orphans every
  passkey.
* *User verification.* A passkey proves possession of the key; with user verification (a biometric or a PIN) it also
  proves the user. The example treats a passkey as a strong primary factor on that basis, so keep user verification
  required for registrations and sign-ins that stand alone, and check the `uv_initialized` data if a policy needs it.
* *Synced and device-bound passkeys.* A synced passkey survives a lost phone but is only as safe as the account that
  syncs it. The example reports both as `hwk` and exposes `backupEligible` and `backedUp` in the account API, so a client
  can warn about, or a policy can require, a device-bound credential.
* *Registration must not weaken the second factor.* Registering a passkey adds a factor that signs in on its own, so the
  registration endpoints require a session that satisfies the multi-factor policy. Without that rule, a stolen password
  would be enough to enrol a passkey and bypass the second factor.
* *Deletion and the step-up.* The framework's deletion endpoint is denied; removing a passkey goes through the account API,
  which needs a recent multi-factor sign-in and, when it removes the last second factor, revokes the trusted devices.
  Deleting a passkey also removes the credential from the server only: the authenticator may keep its copy.
* *Account status.* Spring's WebAuthn provider trusts the user it loads. The decorated `UserDetailsService` makes a passkey
  sign-in refuse the disabled, locked or expired accounts that a password sign-in refuses.
* *Account recovery.* A lost authenticator is the weak point: keep at least two passkeys or another second factor, and
  remember that a recovery path that bypasses the passkey is the real strength of the account. See
  xref:backend/oauth/authentication-methods-2fa-and-passwordless.adoc#enrolment-and-account-recovery-the-weakest-link[].
* *Attestation.* The example accepts attestation as received and does not restrict authenticator models, which is right
  for a public service. Requiring a specific attestation is only worth the privacy cost and the maintenance of trust
  anchors in a closed fleet of managed security keys.
* *Counters and cloning.* The signature counter is stored and updated, but synced passkeys often report zero, so a counter that does not
  grow is not by itself a sign of cloning.
* *Pitfalls.* The creation and authentication options endpoints are `POST` and need the CSRF token. The script must decode
  `challenge`, `user.id` and every credential id from base64url before calling the browser, and encode the answer back.
  A failure of the automatic autofill sign-in must not redirect to the error page, or the page loads the script again and loops.
