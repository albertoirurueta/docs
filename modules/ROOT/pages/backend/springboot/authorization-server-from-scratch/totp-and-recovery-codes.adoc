== What you build

This page adds the first *second factor* of the example: a time-based one-time password (TOTP) produced by an
authenticator app, plus the *recovery codes* that stand in for it when the phone is lost. A user enrols the app once,
either on the second-factor page during a sign-in or through the REST API, and from then on a code is asked after the
password. The pieces are:

* the *enrolment*: a random shared secret, stored *encrypted*, handed to the app as an `otpauth://` URI and a QR code,
  and activated only when the first code from the app is accepted;
* the *verification*: a six-digit code checked against a small window of time steps, with a step that can be used only
  once and a lockout after repeated failures;
* ten *recovery codes*, shown once, stored hashed and each valid once;
* the Spring Security wiring that turns an accepted code into a `FACTOR_TOTP` authority, which the token customizers
  later report as `amr` `otp` and `acr`, and the Thymeleaf forms that collect the codes.

The theory (what TOTP and HOTP are, why recovery is the weakest link) lives in the OAuth Reference sections
xref:backend/oauth/authentication-methods-2fa-and-passwordless.adoc#_totp_hotp_authenticator_apps[]
and xref:backend/oauth/authentication-methods-2fa-and-passwordless.adoc#enrolment-and-account-recovery-the-weakest-link[],
and this page does not repeat it. How the factor is *required* (per user, per client, step-up, lockout counters and
trusted devices) belongs to the Multi-Factor Authentication & Step-Up page of this guide; this page only shows where
the TOTP code plugs into it.

=== The algorithm in two formulas

RFC 4226 (HOTP) computes a code from a shared secret `K` and a counter `C`, and RFC 6238 (TOTP) makes the counter
the number of time steps since the Unix epoch. With the defaults that authenticator apps use (`SHA1`, 6 digits, a
30-second step), and writing `T` for the counter:

[stem]
++++
T = \left\lfloor \frac{t_{\mathrm{ unix }} - T_0}{ X } \right\rfloor, \qquad T_0 = 0, \; X = 30
++++

[stem]
++++
\mathrm{ TOTP }(K, T) = \bigl( \mathrm{ DT }\bigl(\mathrm{HMAC\text{-}SHA1}(K, T)\bigr) \bmod 10^{ 6 } \bigr), \qquad \mathrm{ DT }(h) = \bigl( h[o \ldots o+3] \,\&\, \mathtt{ 0x7fffffff } \bigr), \; o = h[19] \,\&\, \mathtt{ 0x0f }
++++

`DT` is the *dynamic truncation* of RFC 4226: the low four bits of the last of the 20 hash bytes choose an offset
`o`, the four bytes from there are read as a big-endian integer, and the sign bit is cleared so the result is
positive. Authenticator app and server run the same computation, which is why they agree without talking to each
other, and why a code stays valid only while both clocks are within a step or two.

== How it works

=== Enrolment

The example enrols on the second-factor page during a sign-in (the path below) and through `POST /api/account/totp`
for a client that manages the account over the REST API. Both call the same `EnrollTotpUseCase` and
`ConfirmTotpUseCase`, so the secret is generated and activated the same way.

[mermaid]
....
sequenceDiagram
    autonumber
    actor U as User
    participant B as Browser
    participant P as GET /login/second-factor
    participant F as TotpAuthenticationFilter
    participant C as ConfirmTotpAtSignInUseCase
    participant DB as totp_credentials and recovery_codes
    U->>B: Signs in with the password
    B->>P: GET /login/second-factor
    P->>P: TotpSecondFactorFragment calls EnrollTotpUseCase
    P->>DB: Insert the secret encrypted, confirmed = false
    P-->>B: Page with the QR code and the otpauth URI
    U->>B: Scans it and types the first code
    B->>F: POST /login/second-factor/totp (code, enroll)
    F->>C: TotpCodeVerifier, ENROLMENT kind
    C->>DB: Check the code, advance last_used_step, confirmed = true
    C->>DB: Replace the recovery codes with ten new ones, hashed
    F->>F: PendingRecoveryCodes keeps the clear codes in the session
    F-->>B: 302 to /login/second-factor/recovery-codes
    B->>P: GET the codes page, shown once
    P-->>B: Ten recovery codes and a Continue link
....

The secret is never confirmed by the act of generating it: the row is created with `confirmed = false`, a second
`EnrollTotpUseCase` call replaces a pending secret, and only a code computed from the secret proves that the user
really stored it in an app. A page reload during enrolment therefore shows a *new* QR code, and the old one stops
working.

=== Verification

[mermaid]
....
flowchart TD
    IN["POST /login/second-factor/totp: code, kind"] --> K{"Kind of code"}
    K -- TOTP --> L{"Second factor locked?"}
    L -- yes --> LOCKED["SecondFactorLockedException, mapped to LockedException"]
    L -- no --> CRED["Load the confirmed credential and decrypt the secret"]
    CRED --> WIN["Compute the code for each step in the window, compare in constant time"]
    WIN --> NEW{"Matching step greater than last_used_step?"}
    NEW -- no --> FAIL["Register a failure: BadCredentialsException"]
    NEW -- yes --> ADV{"advanceLastUsedStep updates one row?"}
    ADV -- no --> FAIL
    ADV -- yes --> OK["Reset the failure counter, record SECOND_FACTOR_SUCCESS, grant FACTOR_TOTP"]
    K -- RECOVERY --> RC["Normalise the code, compare with each unused hashed code, markUsed"]
    RC --> OK
    K -- ENROLMENT --> ENR["Confirm the pending credential, see the enrolment diagram"]
    ENR --> OK
    FAIL --> LIM["After the configured number of failures the second factor locks for a period"]
....

Three defences sit in this path. The *window* accepts the previous, the current and the next 30-second step, which
absorbs a phone clock that is up to about a step out. *Replay protection* stores the last accepted step per user and
accepts only a strictly greater one, with the update done as a conditional `+UPDATE ... WHERE last_used_step < ?+` so
two concurrent requests with the same code cannot both succeed. The *lockout* counts failures per user and, after
the configured number (default 5), refuses even a correct code for the configured period (default 15 minutes); both
are `authserver.mfa` properties, described on the Multi-Factor Authentication & Step-Up page.

set the trusted-device cookie when the user ticked "Remember this device".

=== Secrets at rest

A TOTP secret has to be recoverable, because the server needs the clear bytes to compute the expected code, so it
is *encrypted*, not hashed. The example encrypts it with Spring Security Crypto's `Encryptors.stronger`, from a
passphrase and a salt. The signing keys use the configured salt directly (that cipher is the listing below, which the
Signing Keys, JWS & JWT page explains in full); the TOTP cipher, `AesGcmTotpSecretCipher`, is built the same way but
takes a salt *derived for the purpose* `totp-secret` from the same configuration, so a single configured passphrase
yields different keys for the secrets and for the signing keys. This page does not repeat the mechanism.

[source,bash]
----
curl -s -X POST http://localhost:9000/api/account/totp \
  -H "Authorization: Bearer ${TOKEN}"
----

`recoveryCodes` and `remaining`, shown only this once:

[source,bash]
----
curl -s -X POST http://localhost:9000/api/account/totp/confirm \
  -H "Authorization: Bearer ${TOKEN}" \
  -H "Content-Type: application/json" \
  -d '{"code":"123456"}'
----

[source,bash]
----
curl -s -X POST http://localhost:9000/api/account/recovery-codes \
  -H "Authorization: Bearer ${TOKEN}"
----

Disable the factor. The answer is `204`, also when nothing was enabled:

[source,bash]
----
curl -s -X DELETE http://localhost:9000/api/account/totp \
  -H "Authorization: Bearer ${TOKEN}"
----

enrolment in progress, or recovery codes requested without a confirmed factor. The page that shows the codes after a

== Security notes and pitfalls

* *Clock drift.* The window is one step each side (about 30 seconds) of the current step. A wider window helps users
  with bad phone clocks but multiplies the codes an attacker may guess in one attempt, so the example keeps it at one
  step and relies on the lockout for the rest. Keep the server on NTP.
* *Code reuse.* A valid code is a bearer secret for up to about 90 seconds. RFC 6238 requires a verifier to accept
  each code once; the example stores the last accepted step and updates it with a conditional `UPDATE`, so a code
  observed by someone shoulder-surfing or phishing the form cannot be replayed within its window (it does not stop
  a real-time phishing proxy, which uses the code immediately; only a phishing-resistant factor such as a passkey does).
* *Brute force.* Six digits are one million possibilities. The lockout, counted per user in a separate table and
  enforced before the code is looked at, is what makes that safe; rate limiting by address in front of the endpoint
  is a useful second layer.
* *Secret storage.* Encrypt the secret, never log it and never return it after enrolment. The `otpauthUri` and `qrCode`
  fields are marked as secrets in the contract and sent with `Cache-Control: no-store`. The key that protects the
  secrets belongs in a secret store, not in the repository; losing it makes every enrolment unusable.
* *Recovery codes.* They are random (ten characters from a Crockford-style alphabet without look-alike letters),
  hashed like a password, single use through the `used_at` guard, and replaced as a set, so regenerating invalidates
  the old ones. Typed codes are normalised (case, dashes, spaces and look-alike characters) before comparison. Show
  them once, ask the user to store them offline, and warn when few are left, as the page does.
* *Step-up to change the factor.* Disabling the app or regenerating codes through the API requires a token that shows
  a recent multi-factor sign-in (`acr` and `auth_time`, five minutes by default), otherwise a stolen password-only
  session could remove the second factor. Disabling also revokes the trusted devices.
* *The account-recovery weakest link.* Recovery codes, a support desk and an e-mail reset are all ways *around* the
  factor, so the strength of the account is that of the weakest of them: a reset by e-mail that bypasses the app
  turns the second factor into decoration. The OAuth Reference discusses the trade-offs in
  xref:backend/oauth/authentication-methods-2fa-and-passwordless.adoc#enrolment-and-account-recovery-the-weakest-link[].
* *Pending enrolment.* An unconfirmed credential is not a factor: verification and recovery codes ignore it. It can,
  however, be replaced by a reload of the second-factor page, which is why the QR code is not cached.

For the full reference on TOTP see https://www.rfc-editor.org/rfc/rfc6238[RFC 6238], https://www.rfc-editor.org/rfc/rfc4226[RFC 4226]
and https://www.rfc-editor.org/rfc/rfc9470[RFC 9470] for the step-up challenge; the `otpauth://` format is described
in the https://github.com/google/google-authenticator/wiki/Key-Uri-Format[Key URI Format] of Google Authenticator, and the
https://cheatsheetseries.owasp.org/cheatsheets/Multifactor_Authentication_Cheat_Sheet.html[OWASP Multifactor Authentication Cheat Sheet]
and https://pages.nist.gov/800-63-4/sp800-63b.html[NIST SP 800-63B-4] cover the policy side.
