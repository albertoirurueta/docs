This page is the map of the example that the rest of the *Authorization Server from Scratch* guide builds on:
https://github.com/albertoirurueta/irurueta-auth-server[irurueta-auth-server]. It shows which applications exist, who
talks to whom and across which trust boundary, how a user signs in end to end, how the authorization server's
Spring Security filter chains are split, and how a new authentication method plugs in without editing shared files.

The example is a *learning project*: it is built and tested in CI, but it is *never deployed*, so every address,
port and credential in these pages is a local development value. The protocol background lives in the
xref:backend/oauth/index.adoc[OAuth Reference]; this guide is its Spring Boot counterpart, in the same way that
xref:backend/oauth/spring-boot-integration-overview.adoc[Spring Boot and OAuth: Integration Overview] maps each
OAuth role to a Spring Boot starter, and xref:backend/oauth/browser-based-apps.adoc[Browser-Based Apps] explains why
the browser holds a cookie and never a token.

== Components and ports

Four applications and a handful of infrastructure services make up the system. The browser is the only untrusted
party: it talks to the BFF with a session cookie and to the authorization server through redirects, and it never
sees an access, refresh or ID token. The external services (identity providers, mail, SMS) are only ever called by
the authorization server.

image::springboot-authz-architecture.svg["Components and trust boundaries of the example: the browser, the BFF, the authorization server, the resource server, the service client, PostgreSQL and the external identity providers, mail and SMS services",width=900]

[cols="2,1,4",options="header"]
|===
|Module
|Port
|Role

|`auth-server`
|9000
|Spring Authorization Server: the OAuth 2.1 and OpenID Connect protocol endpoints, the Thymeleaf login, consent and
logout pages, the account and administration REST API, the signing keys and the JWKS endpoint. Its state lives in the
`authserver` database.

|`bff`
|8080
|Backend for frontend: an `oauth2Login()` client using the authorization code grant with PKCE. It serves the SPA,
keeps the user's tokens in a server-side session (Spring Session JDBC, cookie `+__Host-SESSION+`, `bff` database) and
relays the API calls of the SPA to the resource server with the user's access token.

|`resource-server`
|8081
|Validates the bearer JWTs issued by the authorization server (signature through its JWKS, issuer, expiry and `aud`)
and serves the documents API. It has no database: the documents are kept in memory.

|`service-client`
|none
|A command-line style application with no HTTP port. It obtains a token with the client credentials grant, calls the
resource server and exits. Its other profiles (device flow, token exchange) belong to later pages.

|PostgreSQL 18
|5432 in the container
|Started from the root `compose.yaml`. One server, one database per application (`authserver`, `bff`,
`resourceserver`, the last one created by `compose/init-databases.sql`). The host port is assigned by Docker Compose.

|Mailpit
|1025 (SMTP), 8025 (web UI)
|Local stand-in for the mail relay that receives the verification and one-time-code e-mails.

|`test-support`, `e2e-tests`, `coverage`
|none
|Root modules outside the applications: the shared Testcontainers base, the Playwright sign-in smoke test and the
aggregated JaCoCo report.
|===

Each application is a Maven sub-reactor split by hexagonal layer (`domain`, `application`, `infrastructure/<adapter>`,
`api/<adapter>` and a `boot` composition root). The layering is enforced twice, by `maven-enforcer-plugin`
`bannedDependencies` rules in each `pom.xml` and by an ArchUnit test in each `boot` module. See
xref:backend/springboot/architectural-patterns.adoc[Architectural Patterns] for the pattern in general.

== End-to-end sign-in

The sequence below is the sign-in of a single-page application through the BFF, the flow recommended for
browser-based apps. Every step is implemented by the example's code: the `/bff/login` endpoint starts the
`/oauth2/authorization/bff` redirect, Spring Security's `oauth2Login()` completes the code exchange at
`/login/oauth2/code/bff`, and the access token only ever travels from the BFF to the resource server.

[mermaid]
....
sequenceDiagram
    autonumber
    actor U as User
    participant S as Browser (SPA)
    participant B as bff :8080
    participant A as auth-server :9000
    participant R as resource-server :8081
    S->>B: GET /bff/login?returnTo=/
    B-->>S: 302 to /oauth2/authorization/bff
    S->>B: GET /oauth2/authorization/bff
    B-->>S: 302 to /oauth2/authorize (client_id, state, PKCE challenge)
    S->>A: GET /oauth2/authorize
    A-->>S: 302 to /login (no session yet)
    U->>A: sign in (and second factor and consent when required)
    A-->>S: 302 to the BFF redirect_uri with the authorization code
    S->>B: GET /login/oauth2/code/bff (code and state)
    B->>A: POST /oauth2/token (code, code_verifier, client_secret_basic)
    A-->>B: access token, refresh token and ID token
    B->>B: store the tokens in the server-side session
    B-->>S: 302 to returnTo with Set-Cookie __Host-SESSION
    S->>B: GET /api/documents (session cookie)
    B->>R: GET /api/documents with Authorization Bearer and the access token
    R->>A: GET /oauth2/jwks (first request, then cached)
    A-->>R: public signing keys
    R->>R: verify signature, issuer, expiry and audience
    R-->>B: 200 documents
    B-->>S: 200 documents
....

The authorization code, the PKCE verifier and the tokens are the standard messages of
https://datatracker.ietf.org/doc/draft-ietf-oauth-v2-1/[the OAuth 2.1 draft]; the one design decision specific to the
BFF pattern is steps 12 and 13, where the session cookie replaces the token in the browser. The page
xref:backend/oauth/authorization-code-and-pkce.adoc[Authorization Code and PKCE] explains each parameter.

== The authorization server's filter chains

`auth-server` defines three `SecurityFilterChain` beans, evaluated in `@Order` order, and the first chain whose matcher
accepts the request handles it:

* `ApiSecurityConfig` (order 0) secures `+/api/**+` statelessly. It accepts only bearer JWTs issued by this server for
  the API audience, with a decoder of its own, keeps registration, e-mail verification and password reset public (rate
  limited) and requires the scope `admin` under `+/api/admin/**+`.
* The protocol chain of `SecurityConfig` (order 1) applies only to the authorization server endpoints
  (`/oauth2/authorize`, `/oauth2/token`, `/oauth2/jwks`, the OpenID Connect discovery and logout endpoints and the
  rest), enables OpenID Connect, hands the configurer to every `ProtocolChainCustomizer` bean and redirects an
  unauthenticated user to the login page.
* The login and UI chain of `SecurityConfig` (order 2) has no matcher, so it catches everything else: the login page,
  the consent page, the account pages and the error page. It enables form login, applies every `LoginChainCustomizer`
  bean and only then adds its catch-all rule.

[mermaid]
....
flowchart TD
    REQ[Incoming request] --> M0{"Path matches /api/** ?"}
    M0 -- yes --> C0["ApiSecurityConfig, @Order(0): stateless, CSRF off, bearer JWT of this server, scope admin under /api/admin/**"]
    M0 -- no --> M1{"Authorization server endpoint?"}
    M1 -- yes --> C1["SecurityConfig, @Order(1): protocol chain, OIDC enabled, anyRequest authenticated, entry point redirects to /login"]
    M1 -- no --> C2["SecurityConfig, @Order(2): login and UI chain, form login, catch-all rule"]
    PC[ProtocolChainCustomizer beans] -.-> C1
    LC[LoginChainCustomizer beans] -.->|applied before the catch-all rule| C2
    C2 --> P["Permitted without login: /login, /error, /actuator/health/**, /v3/api-docs/**"]
    C2 --> AU[Everything else requires authentication]
....

The two chains of `SecurityConfig` are the heart of the server. The protocol chain takes its matcher from the
authorization server configurer, so it never needs a list of endpoint paths; the login chain deliberately lets the
customizers run before its `anyRequest().authenticated()` rule, so a customizer can still permit its own endpoints.

[source,java]
----
include::irurueta-auth-server::example$auth-server/api/web/src/main/java/com/irurueta/authserver/authorization/api/web/SecurityConfig.java[tag=security-chains]
----

This code derives from the https://docs.spring.io/spring-authorization-server/reference/getting-started.html[Spring Authorization Server Getting Started guide], which defines the same two-chain layout for the protocol endpoints and the login page.

The remaining services are plain Spring Security resource servers and an `oauth2Login()` client. The general model
that all of these chains plug into, including how `FilterChainProxy` picks a chain by matcher and order, is described
in https://docs.spring.io/spring-security/reference/servlet/architecture.html[Spring Security Servlet Architecture],
and the role of the authorization server in the larger picture in
https://docs.spring.io/spring-authorization-server/reference/overview.html[the Spring Authorization Server overview].

== Package per feature and the extension points

Inside each layer the code is grouped by feature, and a feature uses the same package name in every layer it spans:
`password` is `+...domain.password+`, `+...application.password+`, `+...infrastructure.persistence.password+` and
`+...api.web.password+`; `passkeys`, `ott`, `social`, `x509`, `mfa`, `clients` and `keys` follow the same rule. Two
developers adding two authentication methods therefore touch disjoint packages. The shared files are closed for
modification and open for extension through a small number of interfaces in `api.web`:

[cols="2,4",options="header"]
|===
|Extension point
|What it does

|`LoginChainCustomizer`
|A functional interface over `HttpSecurity` (deliberately not a `Customizer<HttpSecurity>`, which Spring Security
would apply to every chain). Every bean of this type is applied to the login chain in `@Order` order, before its
catch-all rule.

|`LoginMethodFragment`
|Contributes one Thymeleaf fragment to the login page (`templateName()`, `fragmentName()` and `order()`). The login
template renders one fragment per bean, sorted by order, so adding a sign-in method never edits `login.html`.

|`ProtocolChainCustomizer`
|The same idea for the protocol chain: every bean receives the authorization server configurer, for example to
configure the UserInfo mapper.
|===

A feature that adds a sign-in method ships one bean of each of the first two kinds. Passkeys declare their
`LoginChainCustomizer` in a configuration class, with an explicit order so it runs after the TOTP customizer:

[source,java]
----
include::irurueta-auth-server::example$auth-server/api/web/src/main/java/com/irurueta/authserver/authorization/api/web/passkeys/PasskeyConfiguration.java[tag=passkeys-chain-customizer]
----

This derives from the https://docs.spring.io/spring-security/reference/servlet/authentication/passkeys.html[Spring Security passkeys documentation], whose `+http.webAuthn(...)+` configuration the customizer applies.

Signing in with an X.509 client certificate contributes its button to the login page with a
`LoginMethodFragment`; its `ORDER` constant places it after the social sign-in and before the one-time tokens:

[source,java]
----
include::irurueta-auth-server::example$auth-server/api/web/src/main/java/com/irurueta/authserver/authorization/api/web/x509/X509LoginMethodFragment.java[tag=x509-login-method-fragment]
----

This derives from the https://docs.spring.io/spring-security/reference/servlet/authentication/x509.html[Spring Security X.509 authentication documentation], which describes the certificate sign-in that the fragment's form posts to.

The later pages of the guide add each authentication method as exactly this pair of beans, so reading these two
listings once is enough to follow all of them.
