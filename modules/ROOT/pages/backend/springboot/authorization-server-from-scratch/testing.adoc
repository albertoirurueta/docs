== What you build

An authorization server is mostly behaviour that is easy to break and hard to see: a redirect that must not happen, a claim that must be present, a code that must work once.
The example tests it at four levels, and this page shows what each level proves, which classes to read, and the few tricks that keep the tests fast and honest.
It is a tour of the example's tests, not a testing course: the general techniques are on xref:backend/springboot/unit-and-integration-testing.adoc[] and, for OAuth flows,
on xref:backend/oauth/testing-and-debugging.adoc[].

The example has roughly 560 unit test classes, 94 integration test classes and 9 end-to-end test classes (counted on the `main` branch when this page was written; the numbers move).
Every test of every page of this guide is one of them, which is why the "Tests" section of a feature page can name a class instead of showing code.

The rule that separates the first two levels from the rest is the file name. `+*Test+` classes run in Surefire and start no Spring context; every test that starts Spring or a container is a `+*IT+` class run by Failsafe.
`./mvnw test` is therefore the fast loop, and `./mvnw -B clean verify` runs everything, with the build gates. Note that some `+*IT+` classes are slices, so the suffix says "run with Failsafe", not "needs Docker".

== Unit tests

A unit test builds the class with its collaborators as plain objects and asserts a result. The domain and application modules of the hexagonal layout are written for this: they have no Spring and no I/O,
so a test needs no setup beyond `new`. `TotpAlgorithmTest` is the model: it keeps the shared secret and the eight-digit expected codes of RFC 6238 Appendix B, truncates them to six digits and
asserts that the generator produces them at each Unix time, so a change in the algorithm cannot pass. The filter chain customizers are tested the same way, against a mocked `HttpSecurity`
or a recorded set of calls, and `HexagonalArchitectureTest` (ArchUnit, one per application) fails the build when a layer imports one it should not.

No unit test of the example is a tagged region, so no listing is shown for this level. The classes above are the ones to open.

== Slices with spring-security-test

Spring Security's test support adds *request post-processors* to MockMvc, so a test can arrive already authenticated without signing in:

* `jwt()` puts a `Jwt` authentication in the request, with claims set by the test. The resource server's `SecurityConfigIT` uses it to prove that a missing scope is `403`, a wrong audience is `401` and a password-only sign-in
  needs a step-up to delete. `ApiSecurityConfigIT` does the same for the account API chain, with a probe controller and a `@WebMvcTest` slice.
* `oidcLogin()` is a signed-in user as the BFF sees one, with ID token claims and an authorized client. The BFF's `SecurityConfigIT`, `UserControllerIT` and `DocumentsApiIT` use it for `/bff/user` and the relayed API calls; they run with PostgreSQL, because the BFF keeps its session there.
* `csrf()` adds a valid CSRF token to a state-changing request. The example uses it in dozens of tests of the login chain and of the BFF, and a test of the opposite (a post *without* it is refused) for each page that posts a form.

The documentation of the post-processors is on the Spring Security testing pages linked below. The example does not use `oauth2Client()` or `@WithMockUser`; it needs a synthetic user only where the
code reads an `Authentication`, and `jwt()` and `oidcLogin()` cover those places.

The closest *tagged* example is `TotpApiIT` in the next section. It uses `jwt()` as described here, but it runs with the real database, because the answer depends on stored data.

== Integration tests with Testcontainers

`@PostgresIT` (from the `test-support` module) is one annotation that starts the application with the `test` profile and a PostgreSQL container, runs the Flyway migrations on it and a key-encryption secret made for tests. It is a `@SpringBootTest` that imports the container configuration, so a test class stays small. A test injects `MockMvc`, repositories and a `JdbcClient`,
and uses the fixtures of the module (`AuthServerFixtures`) to create a user, a client and a token. The integration pages of the Spring Boot and Docker sections explain the mechanics:
xref:backend/docker/spring-boot-integration-tests-with-testcontainers.adoc[] and xref:backend/docker/testcontainers-fundamentals.adoc[].

== End-to-end tests

The nine classes of the `e2e-tests` module start the packaged applications as separate processes (`ManagedApp`, `RunningAuthServer`, `RunningResourceServer`) against a PostgreSQL container and talk to them over HTTP. They are the only tests where a
browser runs the JavaScript of the pages and a second JVM calls the API, so each one covers something the others cannot:

* `SignInSmokeIT` signs in through the BFF in headless Chromium, driven by Playwright for Java.
* `PasskeyEndToEndIT` gives the browser a *virtual authenticator* through the Chrome DevTools Protocol (CTAP2, internal transport, resident key, user verified), so the real WebAuthn ceremonies of the pages run: registration, sign-in with the button and
  sign-in with the autofill field.
* `OttEndToEndIT` starts a Mailpit container, requests a code, reads the e-mail from the Mailpit HTTP API and types the code; another scenario follows the magic link, including a mail scanner fetching it first.
* `BffEndToEndIT`, `ResourceServerEndToEndIT`, `ClientCredentialsEndToEndIT`, `TokenExchangeEndToEndIT`, `DeviceFlowEndToEndIT` and `LegacyImplicitEndToEndIT` run the BFF, the resource server, the `service-client` tool and the grants end to end.

None of them is a tagged region, so they are described here instead of shown. They are slow (they start processes and a browser), so they are few and each one tests a journey, not a rule: the rules are checked below them.
See the https://playwright.dev/java/docs/intro[Playwright for Java documentation] for the browser side.

== Testing tricks

=== Clocks and time travel

Time is a dependency here: a code expires in ten minutes, a key rotates every thirty days, a step-up is recent for a few minutes. The application takes a `Clock` bean (`ClockConfiguration`) wherever it needs the time,
and the *unit* tests of those classes pass `+Clock.fixed(...)+` (see `FactorGrantorTest`, `StepUpGuardTest`, `TrustedDeviceCookieWriterTest` and `PendingIdentityLinksTest`), so every boundary is exact.

The integration tests use the real clock of the context and *move the data instead of the clock*:

* *Key rotation.* `KeyRotationIT` forces a rotation through the administration API, then runs `UPDATE signing_keys SET retired_at = now() - interval '2 days'` on the retired key and rotates again, to prove that a key
  outside its retention is removed from the published set while a token it signed was still valid until then.
* *Old sign-ins.* `TotpApiIT` (above) builds its token with an `auth_time` older than the step-up window instead of waiting for it.
* *TOTP steps.* The fixtures of the MFA tests compute the code of a stored credential for the current step or for an offset of steps (`codeNow(userId, 1)` is the next code), with `TotpTools` in `AuthServerFixtures`, so a test never sleeps.

=== The OpenAPI contract as a test

The contracts under `apis/` are the source of the REST APIs, and a test keeps the running application honest to them. `OpenApiContract` in `test-support` reduces a contract and the OpenAPI document that springdoc serves to a sorted summary
(operation ids, tags, security, parameters, bodies, status codes and the properties of every schema) and compares them. `OpenApiContractTest` is the unit test of that comparator, and each application has an `OpenApiDriftIT` that
fails with the exact difference when an endpoint is mapped by hand outside the generated interface, a contract operation has no controller, or a status code or schema differs. The contract of the account and administration API
is on xref:backend/springboot/authorization-server-from-scratch/api-reference.adoc#_custom_apis[API Reference, Custom APIs].

=== Mailpit and the logging SMS sender

E-mail codes and magic links are tested against a real SMTP server that keeps what it receives. `Mailpit` and `MailpitTestConfiguration` start the container and point the application's mail settings at it, and
`MailpitClient` reads the messages from its HTTP API, so `OttEmailCodeIT`, `OttMagicLinkIT` and the end-to-end test read the code or the link exactly as a user would. For local development the same
service is in the example's `compose.yaml`:

----

See the https://mailpit.axllent.org/[Mailpit documentation] for the API and the web interface on port 8025.

SMS never leaves the machine in a test. The default `SmsSender` is `LoggingSmsSender`, which records the message in an in-memory `SmsOutbox` and logs only the masked recipient. The `dev` and `test` profiles select it, and the tests read the code back from
the inbox (see `OttSmsIT`). `SmsSenderProfilesIT` proves that the `test` and `dev` profiles use it and that a gateway profile replaces it; `MissingSmsGatewayConfigurationTest` covers the refusal to start with no sender profile.

=== Generated certificates

No certificate, key or key store is committed. `TestPki` builds a small public key infrastructure at run time with the JDK's `keytool`: a certificate authority and the server and client certificates it signs, in PKCS#12 key stores in a temporary directory that
is deleted on close. `TestCertificates` generates single self-signed client certificates the same way. They back the mutual TLS tests (`X509TlsLoginIT`, `ClientAuthenticationIT`, `BoundTokenIT`) and the certificate tests (`X509LoginIT`, `CertificateApiIT`).
Generating the material in the test also keeps the secret scanner quiet, and expiry tests can ask for a certificate that is already expired.

== Test-only CI

The workflow `.github/workflows/build.yml` of the example runs on pushes to `main`, `develop` and `+release_*+` branches and on pull requests, and it only builds and tests: the example is never deployed, so no workflow releases or deploys anything.
The job sets up JDK 21, restores the Maven and Playwright caches, runs `./mvnw -B -ntp clean verify` (the build gates, the unit tests, the integration tests and the end-to-end tests, with Docker preinstalled on the runner for Testcontainers),
runs the SonarCloud analysis only when a token exists, and always uploads the reports. This is the job:
