= Authorization Server from Scratch: Multi-Factor Authentication & Step-Up
:description: Multi-factor authentication and step-up in the irurueta-auth-server example: how Spring Security 7 factor authorities are turned into an amr, acr and auth_time policy, the second-factor page and its extension point, OIDC max_age and acr_values step-up on the authorization endpoint, the RFC 9470 challenge of the account API, failed-attempt lockout and signed trusted-device cookies.

include::partial$springboot-disclaimer.adoc[]

This page adds a second factor to the authorization server built in the previous pages and makes the result visible to
the rest of the system: the tokens say *how* the user signed in, and an API can demand a stronger or fresher
sign-in than the one a token proves. It covers the policy that decides when a second factor is needed, the
second-factor page, step-up through `acr_values` and `max_age`, the lockout that stops code guessing, and the
signed "remember this device" cookie. The authenticator app itself (TOTP enrolment, verification and recovery codes) is
the subject of the next page, *TOTP Authenticator Apps & Recovery Codes*; here it only appears as the one
second factor that is registered.

== What you build

The theory is in the OAuth Reference: xref:backend/oauth/authentication-methods-2fa-and-passwordless.adoc[Authentication Methods, 2FA and Passwordless] explains the
two axes (how the user proved who they are, and how the client learns it), the RFC 8176 `amr` values and the RFC 9470 step-up
exchange (see its section xref:backend/oauth/authentication-methods-2fa-and-passwordless.adoc#_step_up_mid_session_rfc_9470[Step-up mid-session: RFC 9470]), and
xref:backend/oauth/spring-boot-authentication-methods.adoc#_multi_factor_authentication[Spring Boot Authentication Methods: Multi-factor authentication]
shows the framework's own API. This page is the worked example of both.

*What Spring Security 7 gives you.* Every completed authentication step adds a `FactorGrantedAuthority` (for example
`FACTOR_PASSWORD`) to the `Authentication`, with the instant it was granted. `@EnableMultiFactorAuthentication`
registers the authorization rules and the entry points that send a user who lacks a required factor to the page that
collects it. That is all the framework knows: it has no idea what a "second" factor is, which clients require one, what
goes into a token or how recent a sign-in must be.

*What the example adds* on top of that:

* a registry of `AuthenticationFactor` beans (identifier, `amr` value, authority and a `FactorStrength`) and a pure
  `MfaPolicy` that says when a set of factors is enough, when a second factor is required (the client, or the user's
  account, asks for it) and when an authentication counts as multi-factor;
* a `MfaAuthorizationManager` that applies the policy to the consent page and to `/oauth2/authorize`;
* a `FactorTimeline` that reads the factor authorities once, so the `amr`, `acr` and `auth_time` claims and the step-up
  checks always agree;
* the second-factor page, built from `SecondFactorFragment` beans in the same way as the login page;
* step-up on the authorization endpoint (`max_age`, `acr_values`) and the RFC 9470 challenge on the account API;
* a failed-attempt lockout shared by every second factor, and a signed trusted-device cookie that skips the code on a
  browser the user chose to remember, without ever counting as a real second factor.

== How it works

The sign-in below is the sequence of a user whose account requires a second factor (the administrator forced it, or the
user has a confirmed authenticator app, or the client is registered with `mfaRequired`). The primary factor is the
password of xref:backend/springboot/authorization-server-from-scratch/password-storage.adoc[Storing Passwords Securely]; the code
is verified by the TOTP use case of the next page.

[mermaid]
....
sequenceDiagram
    autonumber
    actor U as User
    participant B as Browser
    participant A as auth-server :9000
    B->>A: GET /oauth2/authorize (client_id, PKCE challenge)
    A-->>B: 302 to /login (no session yet)
    U->>A: POST /login (username and password)
    A->>A: grant FACTOR_PASSWORD with the current instant
    A-->>B: 302 back to /oauth2/authorize (saved request)
    B->>A: GET /oauth2/authorize
    A->>A: MfaAuthorizationManager.evaluate: required, not satisfied
    A-->>B: 302 to /login/second-factor (request saved)
    B->>A: GET /login/second-factor
    A-->>B: 200 second-factor page (one fragment per factor)
    U->>A: POST /login/second-factor/totp (code)
    A->>A: check lockout, verify code, grant FACTOR_TOTP
    A-->>B: 302 back to /oauth2/authorize (resumed)
    B->>A: GET /oauth2/authorize
    A->>A: policy satisfied
    A-->>B: 302 to /oauth2/consent when consent is required
    U->>A: POST /oauth2/consent (approve)
    A-->>B: 302 to redirect_uri with the authorization code
    B->>A: POST /oauth2/token (code, code_verifier)
    A->>A: MfaClaimsContributor adds amr, acr and auth_time
    A-->>B: tokens with amr pwd, otp, mfa and acr urn:irurueta:acr:mfa
....

The policy sits in two places. `MfaLoginChainCustomizer` (a `LoginChainCustomizer` of the extension points described in
xref:backend/springboot/authorization-server-from-scratch/architecture.adoc[Architecture]) puts the manager in front of the consent page and tells Spring Security to send
a user with a missing second-factor authority to the second-factor page. `MfaProtocolChainCustomizer` (a
`ProtocolChainCustomizer`) wraps the authorization-code request validator, so a request that reaches `/oauth2/authorize`
without enough factors is refused with a redirect to the same page instead of getting a code.

=== Factor accumulation

A factor is just an authority with an instant, and the factors a session holds decide what the next token says:

[mermaid]
....
stateDiagram-v2
    [*] --> Anonymous
    Anonymous --> PasswordOnly: password accepted (FACTOR_PASSWORD)
    PasswordOnly --> PasswordAndTrusted: trusted-device cookie valid (FACTOR_TRUSTED_DEVICE)
    PasswordOnly --> MultiFactor: second factor verified (FACTOR_TOTP)
    PasswordAndTrusted --> MultiFactor: step-up asks for acr mfa and a real code is verified
    PasswordOnly: claims amr pwd and the password acr
    PasswordAndTrusted: sign-in policy satisfied but claims stay amr pwd
    MultiFactor: claims amr pwd, otp, mfa and the mfa acr
    MultiFactor --> [*]
....

The four `FactorStrength` values define the rules: `PRIMARY_STRONG` (a passkey) is enough alone, `PRIMARY` (the password)
needs a `SECOND` factor (a TOTP code) or a `REMEMBERED` one (the trusted device), and a `REMEMBERED` factor is never
reported, so it can satisfy the sign-in but not a step-up. A passkey proves one thing, however strongly, so it is
multi-factor only when its factor says so. `auth_time` is the instant of the *primary* factor: adding a second factor
later never makes the sign-in look newer.

=== Step-up

Step-up is the same machinery driven by the client. It has two entry points, an authorization request and an API
call, and they meet in the tokens:

[mermaid]
....
sequenceDiagram
    autonumber
    participant C as Client
    participant R as auth-server /api (resource)
    participant A as auth-server /oauth2/authorize
    C->>R: DELETE /api/account/totp (bearer token, acr pwd)
    R->>R: StepUpGuard: confirmed second factor, token not multi-factor or too old
    R-->>C: 401 WWW-Authenticate insufficient_user_authentication, acr_values, max_age
    C->>A: GET /oauth2/authorize with acr_values and max_age from the challenge
    A->>A: StepUpAuthorizationRequestConverter: max_age exceeded or acr not reached
    A-->>C: sign in again, or ask for a real second factor
    C->>A: POST /oauth2/token
    A-->>C: new token with acr mfa and a fresh auth_time
    C->>R: DELETE /api/account/totp (new token)
    R-->>C: 204
....

== Code

=== The policy: when is a second factor required

All the settings come from one record. A value left out takes its default and an invalid one stops the application at
startup: five consecutive failures lock the second factor for 15 minutes, a trusted device lasts 30 days, and a
multi-factor sign-in must be at most 5 minutes old to disable a factor through the API.

[source,java]
----
include::irurueta-auth-server::example$auth-server/application/src/main/java/com/irurueta/authserver/authorization/application/mfa/MfaProperties.java[tag=mfa-properties]
----

Spring Boot documents constructor binding and `@DefaultValue` in https://docs.spring.io/spring-boot/reference/features/external-config.html#features.external-config.typesafe-configuration-properties.constructor-binding[Constructor Binding].

A second factor is required when *either* the account or the client asks. The account asks when an administrator forced
it or when the user has confirmed a factor, because a factor the user enrolled must protect every sign-in; removing the
last factor lifts the second reason, never the first:

[source,java]
----
include::irurueta-auth-server::example$auth-server/application/src/main/java/com/irurueta/authserver/authorization/application/mfa/IsUserMfaRequiredUseCase.java[tag=mfa-user-required]
----

This is application logic, not framework API; the transaction rules it relies on are in the Spring Framework https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/annotations.html[`@Transactional` reference].

The client asks through its registration flag. How the flag is stored is the business of the clients adapter alone (see
xref:backend/springboot/authorization-server-from-scratch/registered-clients.adoc[Registered Clients & Client Management]):

[source,java]
----
include::irurueta-auth-server::example$auth-server/application/src/main/java/com/irurueta/authserver/authorization/application/mfa/IsClientMfaRequiredUseCase.java[tag=mfa-client-required]

See https://docs.spring.io/spring-security/reference/servlet/oauth2/authorization-server/core-model-components.html[the Authorization Server core model components] for the registered client.

=== Reading the factors: timeline and claims

`FactorTimeline` is the single place that reads the factor authorities. It keeps only the factors the policy reports
(so a trusted device is invisible), orders them by instant, and answers the three questions the rest of the code asks:
which `amr` values, is it multi-factor, and when did the primary factor happen.

[source,java]
----
include::irurueta-auth-server::example$auth-server/api/web/src/main/java/com/irurueta/authserver/authorization/api/web/mfa/FactorTimeline.java[tag=mfa-factor-timeline]
----

The class reads https://docs.spring.io/spring-security/reference/api/java/org/springframework/security/core/authority/FactorGrantedAuthority.html[`FactorGrantedAuthority`], whose `getIssuedAt()` is the instant it works from; the claim names come from https://www.rfc-editor.org/rfc/rfc8176.html[RFC 8176] (`amr`) and https://openid.net/specs/openid-connect-core-1_0.html#IDToken[OpenID Connect Core] (`acr`, `auth_time`).

`MfaClaimsContributor` is a `JwtClaimsContributor` of the token pipeline from
xref:backend/springboot/authorization-server-from-scratch/access-refresh-and-id-tokens.adoc[Access, Refresh & ID Tokens]. It adds `amr` (plus `mfa` when there
are at least two factors), `acr` (the multi-factor or the password class) and `auth_time` (as epoch seconds, on access tokens
only, because the framework sets it itself on ID tokens). A token that carries no counted factor, such as one from the
client credentials grant, gets none of the three.

[source,java]
----
include::irurueta-auth-server::example$auth-server/api/web/src/main/java/com/irurueta/authserver/authorization/api/web/mfa/MfaClaimsContributor.java[tag=mfa-claims]
----

This contributor plugs into https://docs.spring.io/spring-security/reference/servlet/oauth2/authorization-server/core-model-components.html#oauth2AuthorizationServer-oauth2-token-customizer[`OAuth2TokenCustomizer`], the framework hook for custom token claims.

=== Step-up on the authorization endpoint

The converter runs before every other authorization request converter. It only applies to a signed-in user with a
counted factor (otherwise it would loop a user who could never satisfy the request through the login page). It throws
`ReauthenticationRequiredException` when more than `max_age` whole seconds have passed since the primary factor, and a
step-up `SecondFactorRequiredException` when the request asks only for authentication context classes the session has not
reached. Unknown classes are ignored, because `acr_values` is voluntary, and the multi-factor class also satisfies a
request for the password class.

[source,java]
----
include::irurueta-auth-server::example$auth-server/api/web/src/main/java/com/irurueta/authserver/authorization/api/web/mfa/StepUpAuthorizationRequestConverter.java[tag=mfa-step-up-converter]
----

The parameters are defined by https://openid.net/specs/openid-connect-core-1_0.html#AuthRequest[OpenID Connect Core, Authentication Request] (`max_age`, `acr_values`); the hook is the `authorizationRequestConverter` of https://docs.spring.io/spring-security/reference/servlet/oauth2/authorization-server/protocol-endpoints.html#oauth2AuthorizationServer-oauth2-authorization-endpoint[the authorization endpoint configurer].

=== Step-up for the account API

The second half of step-up is the API that decides a token is not good enough. The account endpoints that remove or
weaken a second factor (disable the authenticator app, generate new recovery codes, revoke a trusted device) call
`StepUpGuard` first. If the account has a confirmed second factor, the bearer token must carry `acr`
`urn:irurueta:acr:mfa` and an `auth_time` that is not in the future and not older than `authserver.mfa.step-up-max-age`.
An account without a second factor cannot step up, so it is not asked to. The `+/api/**+` chain itself is unchanged: the check
is a call in the controllers.

[source,java]
----
include::irurueta-auth-server::example$auth-server/api/web/src/main/java/com/irurueta/authserver/authorization/api/web/mfa/StepUpGuard.java[tag=mfa-step-up-guard]
----

This guard reads the claims of the `Jwt` that https://docs.spring.io/spring-security/reference/servlet/oauth2/resource-server/jwt.html[the JWT resource server support] puts in a `JwtAuthenticationToken`.

When the guard throws, the exception handler builds the answer RFC 9470 defines: `401`, error
`insufficient_user_authentication`, and the `acr_values` and `max_age` the client must send when it signs the user in
again, plus a problem-details body:

[source,java]
----
include::irurueta-auth-server::example$auth-server/api/web/src/main/java/com/irurueta/authserver/authorization/api/web/mfa/MfaExceptionHandler.java[tag=mfa-step-up-challenge]
----

The challenge format is https://www.rfc-editor.org/rfc/rfc9470.html#section-3[RFC 9470, section 3]; the body is Spring's https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-ann-rest-exceptions.html[`ProblemDetail`].

=== Lockout

A six-digit code has only a million values, so guessing is stopped by counting failures per user, not per IP address. Every
second-factor verification (the TOTP code, a recovery code, a one-time code) is a transactional use case that starts with
this check. The check *locks the user's attempt row until the end of the transaction*, so two verifications of the same
user run one after the other and neither can pass the check while the other is about to count a failure.

[source,java]
----
include::irurueta-auth-server::example$auth-server/application/src/main/java/com/irurueta/authserver/authorization/application/mfa/CheckSecondFactorLockoutUseCase.java[tag=mfa-lockout-check]
----

The use case is plain Spring transaction management: see https://docs.spring.io/spring-framework/reference/data-access/transaction.html[the Spring Framework transaction support].

The lock itself is a `+SELECT ... FOR UPDATE+`, preceded by an insert that guarantees the row exists. The repository keeps
SQL as text blocks, so these two constants are the whole concurrency story:

[source,java]
----
include::irurueta-auth-server::example$auth-server/infrastructure/persistence/src/main/java/com/irurueta/authserver/authorization/infrastructure/persistence/mfa/JdbcSecondFactorAttemptRepository.java[tag=mfa-lock-attempts]
----

Row locking is documented in https://www.postgresql.org/docs/current/sql-select.html#SQL-FOR-UPDATE-SHARE[the PostgreSQL SELECT locking clause] and `ON CONFLICT DO NOTHING` in https://www.postgresql.org/docs/current/sql-insert.html#SQL-ON-CONFLICT[INSERT ... ON CONFLICT].

Counting a failure is one upsert statement: it increments the counter, sets `locked_until` when the maximum is reached, and
restarts the counter at one when an earlier lock has already ended. Concurrent failures serialize on the row, so none is lost.

[source,java]
----
include::irurueta-auth-server::example$auth-server/infrastructure/persistence/src/main/java/com/irurueta/authserver/authorization/infrastructure/persistence/mfa/JdbcSecondFactorAttemptRepository.java[tag=mfa-record-failure]
----

The statement is run through Spring's https://docs.spring.io/spring-framework/reference/data-access/jdbc/core.html#jdbc-JdbcClient[`JdbcClient`] (named parameters as in `:maxAttempts`); the SQL features are in https://www.postgresql.org/docs/current/sql-insert.html#SQL-ON-CONFLICT[INSERT ... ON CONFLICT].

=== Trusted devices

After a successful second factor the user can tick "remember this device". The server creates a random token, stores only
its hash in `trusted_devices`, and sends the browser the token plus an HMAC signature in the `+__Host-TRUSTED-DEVICE+`
cookie (the `+__Host-+` prefix makes the browser accept it only over HTTPS, from the exact host, with path `/` and no
`Domain`). The design has three parts.

*The factor.* A trusted device is registered as a factor of strength `REMEMBERED`. Together with the password it satisfies
the sign-in policy, so the code is not asked again; but it is excluded from `amr`, `acr` and `auth_time` and never satisfies
a step-up:

[source,java]
----
include::irurueta-auth-server::example$auth-server/api/web/src/main/java/com/irurueta/authserver/authorization/api/web/mfa/TrustedDeviceFactor.java[tag=mfa-trusted-device-factor]
----

This is an ordinary Spring https://docs.spring.io/spring-framework/reference/core/beans/java/bean-annotation.html[`@Bean` method] that declares one more `AuthenticationFactor`; nothing else in the policy is edited.

*The signature.* The cookie value is `token.signature`. The signing port is in the domain and the HMAC-SHA256 adapter sits in
the keys module, with a key derived from the key-encryption secret for this purpose only (see
xref:backend/springboot/authorization-server-from-scratch/signing-keys-jws-and-jwt.adoc[Signing Keys, JWS & JWT] for the derivation), so the cookie key is never the
key that encrypts signing keys:

[source,java]
----
include::irurueta-auth-server::example$auth-server/domain/src/main/java/com/irurueta/authserver/authorization/domain/mfa/TrustedDeviceTokenSigner.java[tag=mfa-trusted-device-signer]
----

The port follows the hexagonal layering described in xref:backend/springboot/authorization-server-from-scratch/architecture.adoc[Architecture]; the technique it hides is the HMAC of https://www.rfc-editor.org/rfc/rfc2104.html[RFC 2104].

[source,java]
----
include::irurueta-auth-server::example$auth-server/infrastructure/keys/src/main/java/com/irurueta/authserver/authorization/infrastructure/keys/HmacTrustedDeviceTokenSigner.java[tag=mfa-trusted-device-signature]
----

This uses the JDK's https://docs.oracle.com/en/java/javase/21/docs/api/java.base/javax/crypto/Mac.html[`javax.crypto.Mac`] and compares with `MessageDigest.isEqual`, which takes the same time whatever the position of the first different byte.

*The lookup.* The use case verifies the signature first, so a forged or unsigned value is rejected before the account or the
database is touched; then it hashes the token and finds a device of *that user* that has neither expired nor been revoked:

[source,java]
----
include::irurueta-auth-server::example$auth-server/application/src/main/java/com/irurueta/authserver/authorization/application/mfa/FindTrustedDeviceUseCase.java[tag=mfa-find-trusted-device]
----

Storing only a hash of the token follows the guidance of the https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html[OWASP Session Management Cheat Sheet] for session identifiers.

The filter is the only place the cookie is read, and only on `GET /login/second-factor`, which every request that owes a
second factor is sent to, so a user is not looked up on every request. On a valid cookie it replaces the authentication with one
that also holds the factor, changes the session id, saves the security context and resumes the interrupted request. While a
step-up is pending the cookie is ignored, because a trusted device cannot satisfy it and resuming would redirect straight
back to the page:

With a bearer token that was issued after a password-only sign-in, disabling the authenticator app is refused, and nothing
is removed:

[source,bash]
----
curl -i -X DELETE http://localhost:9000/api/account/totp \
  -H "Authorization: Bearer $ACCESS_TOKEN"
----

[source,http]
----
HTTP/1.1 401
WWW-Authenticate: Bearer error="insufficient_user_authentication", acr_values="urn:irurueta:acr:mfa", max_age="300"
Content-Type: application/problem+json

{ "type": "urn:problem:mfa:insufficient-user-authentication", "title": "Step-up authentication required", ... }
----

The same `401` is given by `POST /api/account/recovery-codes` and `+DELETE /api/account/trusted-devices/{id}+`. The client
reads the two parameters from the header, starts a new authorization request with them and retries with the new token (here
`$STEPPED_UP_TOKEN`):

[source,bash]
----
# 1. open in a browser, then sign in and enter the second factor
#    http://localhost:9000/oauth2/authorize?response_type=code&client_id=...&redirect_uri=...&scope=...
#      &code_challenge=...&code_challenge_method=S256&acr_values=urn:irurueta:acr:mfa&max_age=300
# 2. exchange the code at /oauth2/token, then retry
curl -i -X DELETE http://localhost:9000/api/account/totp \
  -H "Authorization: Bearer $STEPPED_UP_TOKEN"

== Security notes and pitfalls

*Downgrade attacks.* A second factor is worthless if an attacker can choose not to be asked. Three rules in the code close that door. The
requirement is evaluated on the server, from the account and the client, never from a request parameter (`acr_values` can
only *raise* the bar). The policy is enforced at `/oauth2/authorize`, where the code is issued, and not only on the page the
user happens to be redirected to: a request that skips the page is refused there. And the claims are computed from the
factors the session really holds, so a token never says `mfa` because a client asked for it. Keep the fallbacks honest too:
a user who has no second factor registered yet is sent to enrol (the enrolment test above), not waved through, whenever the
policy requires one. Finally, do not let a weaker path, such as a social login that reports no `amr`, produce an `acr` it
did not earn; the example's `trust-mfa` provider settings are off by default.

*Lockout versus denial of service.* A per-user lockout protects the code and gives an attacker who knows only a username a way
to lock the real user out. The example limits the damage: the lock is short (15 minutes by default), the counter restarts when a
lock ends, the lock applies to the *second* factor after the password has been accepted (so the attacker must know the
password to trigger it), and a lockout is recorded as a security event and shown to the user with its own message. Add the
usual rate limits at the edge for the password step, notify the user on repeated lockouts and decide whether an administrator
can unlock. See the https://cheatsheetseries.owasp.org/cheatsheets/Multifactor_Authentication_Cheat_Sheet.html[OWASP Multifactor Authentication Cheat Sheet].

*Trusted-device token theft.* The cookie is a bearer credential: anyone who copies it gets the second factor skipped for that
account on their own browser, as long as they also have the password. Mitigations in the example are that the cookie is
`HttpOnly`, `Secure` and host-bound, its value is signed (a forged value costs one constant-time comparison, not a
database lookup), the database holds only a hash, the device expires after 30 days, a device can be revoked from the API, removing the
second factor revokes every device, and a trusted device never satisfies a step-up, so the sensitive operations still need a real
code. The stronger design is a device-bound key pair; see
xref:backend/oauth/authentication-methods-2fa-and-passwordless.adoc[the OAuth Reference] on device-bound credentials.

*Step-up replay.* A step-up token is valid for as long as it lives; the guard bounds the *age of the sign-in*, not the number
of uses. Keep `step-up-max-age` short, remember that `auth_time` is the primary factor's instant (adding a code later does not
refresh it, so `max_age` forces a new password entry), and never let a client reuse a stepped-up token for a different
operation than the one the user approved. The guard refuses a token whose `auth_time` is in the future, which covers clock
tampering by an issuer you do not control. Pair it with short access-token lifetimes.

*Other pitfalls.*

* `amr` is information, not authorization: a resource server decides with `acr` and `auth_time`, and only for issuers it trusts.
* The tokens report `amr [pwd]` after a trusted-device sign-in on purpose. Do not "fix" that to show two factors, or a step-up becomes satisfiable by a stolen cookie.
* A session that has no counted factor is left alone by the `max_age` check, because it could never satisfy the request and would loop through the login page.
* Change the session id whenever the level of authentication changes (the filter does), against session fixation.
