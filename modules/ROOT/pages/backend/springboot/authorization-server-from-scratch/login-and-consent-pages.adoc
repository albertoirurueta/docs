== What you build

The authorization server is the only place where the user types a credential, so its pages are part of the protocol
surface: the authorization endpoint redirects the browser to them and expects the browser to come back. This page
builds three of them, all rendered on the server with Thymeleaf and all served from the `auth-server` application
described in xref:backend/springboot/authorization-server-from-scratch/architecture.adoc[Architecture]:

* the *login page* (`/login`), a thin shell that renders one fragment per sign-in method, so the password form is only
  the first of them;
* the *consent page* (`/oauth2/consent`), where the user approves or denies the scopes a client asks for;
* the *logout confirmation page* (`/logout`), which asks before ending the session and posts with a CSRF token.

Around them sit the security headers and the Content-Security-Policy that every page is served with, the branding of the
pages and the `PageRenderer` that turns a template into the `text/html` answer of an operation generated from the pages'
OpenAPI contract. The protocol background is in the OAuth Reference:
xref:backend/oauth/logout-and-session-management.adoc[Logout and Session Management] covers RP-initiated logout, and
xref:web/thymeleaf/spring-security-integration.adoc[Thymeleaf and Spring Security integration] covers the login
template, the CSRF hidden field that `th:action` adds and why logging out is a POST.

The page forms of the *second factor*, passkeys, one-time tokens and social sign-in are not repeated here. Each of them
contributes its own `LoginMethodFragment` or second-factor fragment to the pages below, and the later pages of the guide
describe them one by one. The example contains no custom `AuthenticationSuccessHandler`, no `continue` parameter and no
custom `LogoutSuccessHandler`: the defaults of Spring Security do those jobs, and the sections below say which.

== How it works

=== Login and consent

An application that needs a token redirects the browser to `/oauth2/authorize`. The protocol chain finds no session and
`ExceptionTranslationFilter` saves the request in the session and the chain's entry point (a `LoginUrlAuthenticationEntryPoint`) redirects to `/login`. The form posts to the
login chain, whose default success handler returns to the saved request. If the client was registered with
`requireAuthorizationConsent`, the authorization endpoint then redirects to `/oauth2/consent`, and the user's decision is
posted back to `/oauth2/authorize`, which answers with the authorization code, or with `error=access_denied` when no
scope is posted.

[mermaid]
....
sequenceDiagram
    autonumber
    actor U as User
    participant B as Browser
    participant P as Protocol chain (order 1)
    participant L as Login chain (order 2)
    participant C as ConsentController
    participant R as Client redirect_uri
    B->>P: GET /oauth2/authorize (client_id, scope, state, code_challenge)
    P-->>B: 302 /login (request saved in the session)
    B->>L: GET /login
    L-->>B: 200 login page (one fragment per LoginMethodFragment)
    U->>L: POST /login (username, password, _csrf)
    L-->>B: 302 to the saved request, /oauth2/authorize
    B->>P: GET /oauth2/authorize
    P-->>B: 302 /oauth2/consent (client_id, scope, state)
    B->>C: GET /oauth2/consent
    C-->>B: 200 consent page (scopes as checked boxes)
    U->>P: POST /oauth2/authorize (client_id, state, approved scopes, _csrf)
    P-->>B: 302 to redirect_uri with code and state
    B->>R: GET redirect_uri?code=...
....

The consent page itself never completes anything: it renders a form, and the decision goes to the framework's
authorization endpoint, which owns the state it generated for the consent step (the `state` field is posted back
unchanged). The same page serves the device flow, in which case `user_code` is present and the decision is posted to
the device verification endpoint instead.

=== Logout

There are two ways out, and the example supports both. The *local* logout is the confirmation page: a GET never signs
anybody out, because any page could trigger it, and the confirmation form posts to `/logout` with the CSRF token. The
*RP-initiated* logout is the OpenID Connect endpoint `/connect/logout`, which the default OIDC configuration already
exposes: a client sends the user there with an `id_token_hint`, and the server honours a `post_logout_redirect_uri` only
when the client registered it (the seeded clients register none by default).

[mermaid]
....
sequenceDiagram
    autonumber
    actor U as User
    participant B as Browser
    participant S as Authorization server
    U->>B: choose "Sign out" in the client
    B->>S: GET /connect/logout (id_token_hint, post_logout_redirect_uri, state)
    S->>S: validate the hint, the client and the registered post-logout URI
    S->>S: invalidate the session
    S-->>B: 302 to the registered post_logout_redirect_uri with state
    Note over B,S: local logout without a client
    B->>S: GET /logout
    S-->>B: 200 confirmation page with a CSRF token
    U->>S: POST /logout (_csrf)
    S->>S: invalidate the session and delete JSESSIONID
    S-->>B: 302 /login?logout
....

== Data

The pages keep no table of their own. The login failure lives in the HTTP session under Spring Security's
`WebAttributes.AUTHENTICATION_EXCEPTION` attribute, the saved authorization request in the same session, and the
approved scopes in `oauth2_authorization_consent`, described in
xref:backend/springboot/authorization-server-from-scratch/data-model.adoc[Data Model and Schema]. The text of every page
is in `messages.properties`, so the pages can be translated, and the branding is configuration.

=== Rendering the pages

OpenAPI generator produces. It resolves the view with the application's view resolvers and the request's locale,
renders it against the current request into a `ContentCachingResponseWrapper` and returns the captured HTML. Because the
view is rendered against the real request, the CSRF field, the `+@{...}+` links and the messages keep working. It also
adds the branding to every model.

Fetching the pages by hand (the example listens on port 9000 locally; the consent page needs a session of a signed-in
user and the parameters the authorization endpoint generates, so it is reached through a browser):

[source,bash]
----
curl -i 'http://localhost:9000/login'
curl -i 'http://localhost:9000/login?error'
curl -i 'http://localhost:9000/login?logout'
curl -i 'http://localhost:9000/logout' --cookie 'JSESSIONID=<session of a signed-in user>'
----

The first answers `200` with the login page and the security headers listed in the security notes, the second shows the generic
failure message, and the third says the user has signed out. A `POST /logout` without the CSRF token is answered with
`403` and keeps the session.

== Tests

The behaviour of the pages is covered by tests that carry no tagged region, so they are described rather than pasted:

* `LoginPageIT` renders the login page in a web slice with the real password fragment and checks the layout, the
  autocomplete hints and the CSRF field; that a post without the token is `403`; that an unknown user and a wrong
  password get an identical response; the message of every kind of failure; the signed-out status; and that a successful
  sign-in returns to the authorization request saved before the redirect.
* `LoginContentSecurityPolicyIT` checks that a logo on another origin is rendered and that only its origin is allowed
  as an image source.
* `ConsentPageIT` drives the real authorization endpoint of a client that requires consent up to the consent page, then
  checks that the page lists the scope and both decisions, that denying redirects with `access_denied` and that allowing
  redirects with the authorization code.
* `LogoutIT` checks the confirmation page and its CSRF field, that a confirmed logout invalidates the session and
  returns to `/login?logout`, that a logout without the token is refused, and that `/connect/logout` honours a
  `post_logout_redirect_uri` only when the client registered it.
* The unit tests `LoginControllerTest`, `LoginHeadersCustomizerTest`, `LoginContentSecurityPolicyTest`,
  `BrandingPropertiesTest`, `ConsentControllerTest` and `LogoutChainCustomizerTest` cover each class of this page in
  isolation.

== Security notes and pitfalls

The headers of the pages and what each one stops:

[cols="2,3,3",options="header"]
|===
|Header or directive
|Value in the example
|What it stops

|`Content-Security-Policy: default-src 'self'`
|Same-origin resources only, plus `img-src 'self' data:` and the origin of an absolute logo URL
|Injected scripts, styles, frames and connections to other origins. The templates contain no inline script or style, so nothing needs `unsafe-inline`.

|`frame-ancestors 'none'`
|No page of the server may be framed
|Clickjacking: a hostile page overlaying the consent or login page in an invisible frame to collect clicks. It is the modern replacement for `X-Frame-Options`, which Spring Security also sends by default.

|`X-Content-Type-Options: nosniff`
|Spring Security default
|The browser guessing a script or style type for a response served with another type.

|`Referrer-Policy: no-referrer`
|Set in `LoginHeadersCustomizer`
|The authorization request, with its `state` and PKCE challenge, leaking in the `Referer` header to the logo's host or any link.
|===

* *No `form-action` directive, on purpose.* Browsers also apply `form-action` to the redirect that follows a form
  submission, so `form-action 'self'` would block the redirect from the login or consent form back to the client's
  `redirect_uri`, which is on another origin. The CSRF token and the exact redirect URI registration protect the form
  instead.
* *CSRF on every form.* The login, consent and logout forms use `th:action`, which adds the token, and Spring Security
  rejects a post without it. The consent form matters most: without it a hostile page could approve scopes on behalf of
  the signed-in user. See the https://docs.spring.io/spring-security/reference/servlet/exploits/csrf.html[Spring Security CSRF documentation].
* *Open redirect.* The example has no `continue` or `returnTo` parameter on the server: after login the user returns to
  the request Spring Security saved in the session, which the server itself stored, and the authorization endpoint only
  redirects to a `redirect_uri` that the client registered exactly. The same holds for logout, where a
  `post_logout_redirect_uri` must be registered. A page that accepted a free redirect target would need an allow-list; see the
  https://cheatsheetseries.owasp.org/cheatsheets/Unvalidated_Redirects_and_Forwards_Cheat_Sheet.html[OWASP Unvalidated Redirects and Forwards Cheat Sheet]
  and https://www.rfc-editor.org/rfc/rfc6749#section-10.15[RFC 6749, open redirectors].
* *Clickjacking and consent.* The consent page is the one worth framing, and `frame-ancestors 'none'` is why it cannot be
  framed. See the https://cheatsheetseries.owasp.org/cheatsheets/Clickjacking_Defense_Cheat_Sheet.html[OWASP Clickjacking Defense Cheat Sheet].
* *No account enumeration.* The login page shows a generic message, and an unknown user gets the same response as a
  wrong password (`LoginPageIT`). The distinct messages exist only for states the user already proved they know, such as
  a locked or expired account.
* *GET never logs out.* The confirmation page exists because a logout link that works on GET can be triggered by any
  image tag on any page.
* *Unregistered post-logout URIs are ignored.* An RP-initiated logout that names a `post_logout_redirect_uri` the client
  did not register is not redirected there, and the seeded clients register none.
* *Extension point for later methods.* A new sign-in method contributes a `LoginMethodFragment` for its form and a
  `LoginChainCustomizer` for its filters and permitted paths. Its form must use `th:action`, avoid inline script and style,
  and load only same-origin resources, or the policy above will block it. The passkey and one-time-token pages of the
  guide show the pattern.
