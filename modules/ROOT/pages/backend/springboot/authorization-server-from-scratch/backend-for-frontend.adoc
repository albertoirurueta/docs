= Authorization Server from Scratch: Backend-for-Frontend (BFF)
:description: The BFF of the irurueta-auth-server example: an oauth2Login() client with PKCE that keeps the tokens in a Spring Session JDBC session, a __Host- session cookie, CSRF protection for a single page application, a RestClient that relays API calls with the user's access token, and RP-initiated logout.
:keywords: Spring Security 7.1, Spring Boot 4.1, backend for frontend, BFF, oauth2Login, OAuth2AuthorizedClientManager, OAuth2AuthorizedClientRepository, OAuth2ClientHttpRequestInterceptor, RestClient, Spring Session JDBC, JdbcIndexedSessionRepository, CookieSerializer, __Host- cookie, CSRF, CsrfTokenRequestAttributeHandler, CookieCsrfTokenRepository, OidcClientInitiatedLogoutSuccessHandler, RP-initiated logout, PKCE, SPA, token relay, step-up, Mermaid

include::partial$springboot-disclaimer.adoc[]

This page documents the second application of the example, `bff`: a Spring Boot web application that signs the user in
with the authorization server, keeps the user's tokens on the server and serves a small single page application (SPA).
The browser only ever holds a session cookie. The theory behind this choice, the browser threat model and the
alternatives are in xref:backend/oauth/browser-based-apps.adoc[Browser-Based Apps]; the way a BFF fits among the other
applications is in xref:backend/springboot/authorization-server-from-scratch/architecture.adoc[Architecture].

== What you build

The BFF is a *confidential OAuth 2.0 client* (registration id `bff`) that uses the authorization code grant with PKCE,
and a thin API in front of the resource server:

* `GET /bff/login` validates a `returnTo` path and starts the sign-in.
* `oauth2Login()` completes it: it exchanges the code for tokens and stores them, as an authorized client, in the HTTP
  session. The session lives in PostgreSQL (Spring Session JDBC, `bff` database) and the browser receives only the
  cookie `+__Host-SESSION+`.
* `GET /bff/user` returns the signed-in user as UI-safe claims; `GET /api/documents` and `+DELETE /api/documents/{id}+`
  call the resource server with the access token of the session and return its answer.
* `POST /bff/logout` ends the local session and then the session at the authorization server (RP-initiated logout).
* The SPA (`index.html` and `app.js`, no framework and no build step) is served from the BFF itself, so the browser sees
  a single origin and CORS never comes into play.

The BFF listens on port 8080, the authorization server on 9000 and the resource server on 8081. The topology is the
one the OAuth reference recommends, with the real ports and the real cookie of the example:

[mermaid]
....
flowchart LR
    subgraph Browser["Browser (untrusted)"]
        spa["SPA\nindex.html and app.js"]
    end
    subgraph BFFApp["bff :8080 (confidential client, bff database)"]
        bff["oauth2Login() and the /bff and /api endpoints"]
        sess[("spring_session\n(tokens of the user)")]
        bff --- sess
    end
    as["auth-server :9000"]
    rs["resource-server :8081"]
    spa -->|"cookie __Host-SESSION and X-XSRF-TOKEN"| bff
    spa -.->|"top-level redirects only"| as
    bff -->|"authorization code, PKCE, client_secret_basic"| as
    bff -->|"Authorization Bearer, access token of the user"| rs
....

No arrow that reaches the browser carries an access, refresh or ID token. The browser takes part in the sign-in only
through redirects (dotted arrow), which carry the authorization code and, at logout, the ID token hint, but are
followed by the browser as top-level navigations and are never readable by a script.

== How it works

=== Sign-in

[mermaid]
....
sequenceDiagram
    autonumber
    participant S as Browser (SPA)
    participant L as BffLoginController
    participant F as oauth2Login() filters
    participant A as auth-server :9000
    participant R as HttpSession (Spring Session JDBC)
    S->>L: GET /bff/login?returnTo=/
    L->>L: ReturnToValidator.isAllowed(returnTo)
    L->>R: create session, keep returnTo and the step-up values
    L-->>S: 302 to /oauth2/authorization/bff (Set-Cookie __Host-SESSION)
    S->>F: GET /oauth2/authorization/bff
    F-->>S: 302 to /oauth2/authorize (state, PKCE challenge, acr_values and max_age if any)
    S->>A: GET /oauth2/authorize
    A-->>S: sign in, second factor and consent, then 302 to the redirect_uri with the code
    S->>F: GET /login/oauth2/code/bff (code and state)
    F->>A: POST /oauth2/token (code, code_verifier, client_secret_basic)
    A-->>F: access token, refresh token and ID token
    F->>R: save the authorized client and the OIDC user, change the session id
    F-->>S: 302 to returnTo (ReturnToAuthenticationSuccessHandler)
....

`BffLoginController` runs first, as a plain controller, because the SPA must say where to come back to. It validates the
value, keeps it in the session and redirects to Spring Security's authorization endpoint. Everything after step 4 is
`oauth2Login()`: the authorization request resolver adds PKCE and, if `/bff/login` received `acrValues` or `maxAge` (a
step-up, see below), the `acr_values` and `max_age` parameters; the login filter verifies `state`, exchanges the code and
stores the result. Spring Security's default session fixation protection changes the session id when the authentication
is established (the example does not configure it), so the id issued at step 4 is not the one that ends up
authenticated.

=== Calling the API

[mermaid]
....
sequenceDiagram
    autonumber
    participant S as Browser (SPA)
    participant C as DocumentsController
    participant G as RestDocumentGateway
    participant I as OAuth2ClientHttpRequestInterceptor
    participant M as OAuth2AuthorizedClientManager
    participant R as resource-server :8081
    S->>C: GET /api/documents (cookie)
    C->>G: ListDocumentsUseCase, then the gateway
    G->>I: DocumentsApi call over the RestClient
    I->>M: authorize the client bff for the user of the request
    M-->>I: access token (renewed with the refresh token if it expired)
    I->>R: GET /api/documents with Authorization Bearer
    R-->>G: 200 documents
    G-->>S: 200 documents
....

The SPA never sees the token: it sends its cookie, the BFF finds the session and the authorized client in it, and the
interceptor puts the access token on the outgoing request. When the token cannot be obtained or renewed, the gateway
raises `DocumentsUnauthorizedException`, which is answered `401`, and the SPA restarts the sign-in. When the resource
server answers `401` asking for a stronger or more recent authentication
(https://www.rfc-editor.org/rfc/rfc9470[RFC 9470]), the BFF forwards that as a problem detail with the `acrValues` and
`maxAge` to ask for, and the SPA sends the user to `/bff/login` with them, which is what the optional parameters of the
login endpoint are for. How the resource server decides that is described in the resource server page and in the
multi-factor authentication page of this guide.

=== Logout

[mermaid]
....
sequenceDiagram
    autonumber
    participant S as Browser (SPA)
    participant B as bff :8080
    participant A as auth-server :9000
    S->>B: POST /bff/logout (form, _csrf parameter)
    B->>B: CsrfFilter checks the token
    B->>B: logout handlers clear the XSRF-TOKEN cookie and the security context, and invalidate the session
    B-->>S: 302 to the end_session_endpoint (id_token_hint, post_logout_redirect_uri)
    S->>A: GET /connect/logout
    A-->>S: 302 to the BFF root
    S->>B: GET /
    B-->>S: SPA, signed out
....

The SPA submits a real form so that the browser itself follows the redirect: the URL carries the ID token hint, and a
`fetch` call would hand it to the script. The authorization server's side of the protocol is described in
xref:backend/oauth/logout-and-session-management.adoc[Logout and Session Management].

=== The security filter chain

One `SecurityFilterChain` secures the whole application. It permits the SPA's static files and `/bff/login`, requires
authentication for the rest, enables the CSRF cookie, sets a same-origin content security policy, answers `401` instead
of a redirect to a login page for `+/bff/**+` and `+/api/**+` (the SPA is not a browser navigation there), and configures
`oauth2Login()` and the logout.

[source,java]
----
include::irurueta-auth-server::example$bff/api/web/src/main/java/com/irurueta/authserver/bff/api/web/security/SecurityConfig.java[tag=bff-security]
----

This derives from the https://docs.spring.io/spring-security/reference/servlet/oauth2/login/core.html[Spring Security OAuth2 Login reference] and from its https://docs.spring.io/spring-security/reference/servlet/exploits/csrf.html#csrf-integration-javascript-spa[single-page application CSRF section].

The comments in the listing carry two decisions. First, PKCE is switched on explicitly because the authorization
server requires it and Spring enables it by default only for public clients. Second, the plain
`CsrfTokenRequestAttributeHandler` is used instead of the XOR handler of `csrf.spa()`: masking protects against BREACH
a token that is rendered in a compressed response body, and the BFF only puts it in a cookie; the XOR handler would also
reject the raw cookie value that the sign-out form posts.

=== The session cookie

[source,java]
----
include::irurueta-auth-server::example$bff/infrastructure/session/src/main/java/com/irurueta/authserver/bff/infrastructure/session/SessionConfiguration.java[tag=bff-session]
----

This derives from the https://docs.spring.io/spring-session/reference/http-session.html[Spring Session HTTP session reference], which describes the `CookieSerializer`.

The prefix `+__Host-+` makes the browser accept the cookie only when it is `Secure`, has `Path=/` and has no `Domain`
attribute, so a sibling subdomain cannot overwrite or shadow it. `HttpOnly` hides it from scripts, and `SameSite=Lax`
keeps it off cross-site sub-requests while still allowing the top-level redirects of the sign-in. The class does not
use `@EnableJdbcHttpSession` on purpose: that annotation switches Spring Boot's session auto-configuration off, with
every `+spring.session.*+` property (the schema initialization and the timeout among them). The Boot behavior is described in
https://docs.spring.io/spring-boot/reference/web/spring-session.html[Spring Boot Spring Session support].

=== Relaying calls to the resource server

The example does not use Spring Cloud Gateway's `TokenRelay` filter. The BFF is a servlet application whose `/api/documents`
operations are written as a contract (`bff-api-v1.yaml`) and implemented by ordinary controllers, use cases and a
gateway, so a *hand-written relay* fits: the resource server is called through a client generated from its own
contract, on top of a `RestClient` whose interceptor adds the token. That keeps the BFF's API explicit (the SPA can only
reach the operations the contract lists, not an arbitrary proxied path), lets each failure become a domain exception
and a problem detail, and avoids adding a reactive gateway to a servlet application. A gateway is the better choice when
a BFF has to proxy many routes without an API of its own.

----
include::irurueta-auth-server::example$bff/infrastructure/resourceserver/src/main/java/com/irurueta/authserver/bff/infrastructure/resourceserver/ResourceServerClientConfiguration.java[tag=bff-relay]

This derives from the https://docs.spring.io/spring-security/reference/servlet/oauth2/client/authorized-clients.html#oauth2-client-rest-client[Spring Security RestClient support] and the Javadoc of

[source,js]

include::irurueta-auth-server::example$bff/boot/src/main/resources/static/assets/app.js[tag=bff-spa-js]

This follows the SPA pattern of the https://www.rfc-editor.org/rfc/rfc10017[IETF OAuth 2.0 for Browser-Based Applications (RFC 10017)], section on the BFF: the script only calls same-origin endpoints with
`+credentials: 'same-origin'+`. Four details are worth reading:

* The script cannot see the session cookie (it is `HttpOnly`); the only cookie it reads is `XSRF-TOKEN`.
* A `401` from `/bff/user` means signed out and shows a button; nothing redirects automatically, because right after a
  logout the authorization server sends the browser back to this page and an automatic redirect would sign the user in
  again.
* A `401` from `/api/documents` means the session or its token ended, so the script starts the sign-in again.
* Sign-out is a top-level form `POST` with the CSRF token in the `_csrf` field, since a form cannot set a header.

The page itself is the SPA's whole interface; the sign-in and logout pages belong to the authorization server and are
described in the login and consent pages of this guide.

== Configuration

The `bff` registration comes from `application.yml`. The client secret is read from the environment (`BFF_CLIENT_SECRET`)
and is never committed; the issuer, the resource server and the database follow the same pattern, so the values below
are local development defaults.

[cols="2,3",options="header"]
|===
|Property
|Value in the example

|`spring.security.oauth2.client.registration.bff.authorization-grant-type`
|`authorization_code`

|`+...client-authentication-method+`
|`client_secret_basic`

|`+...redirect-uri+`
|`+{baseUrl}/login/oauth2/code/{registrationId}+`

|`+...scope+`
|`openid,profile,documents.read,documents.delete`

|`spring.security.oauth2.client.provider.auth-server.issuer-uri`
|`pass:c[${AUTH_ISSUER:http://localhost:9000}]`

|`spring.session.jdbc.initialize-schema`
|`never` (Flyway owns the schema)

|`bff.resource-server.base-uri`
|`pass:c[${RESOURCE_SERVER_URI:http://localhost:8081}]`

|`bff.login.allowed-return-paths`
|`/`, `/index.html`

|`server.port`
|`8080`
|===

The scopes `documents.read` and `documents.delete` are asked for at sign-in, and the user grants them on the consent
page; the seeded `bff` client of the authorization server allows both. See
xref:backend/springboot/authorization-server-from-scratch/project-setup.adoc[Project Setup and Running the Example] for the profiles and for how the client secret is obtained at the first development start.

generated from it. A test (`OpenApiDriftIT`) fails when the running application and the contract disagree.

[source,shell]

curl -i http://localhost:8080/bff/user -H 'Cookie: __Host-SESSION=<session id>'

# With a session: the documents of the user, read from the resource server with the user's access token
curl -i http://localhost:8080/api/documents -H 'Cookie: __Host-SESSION=<session id>'

# A state-changing request also needs the CSRF token, copied from the XSRF-TOKEN cookie into the header
curl -i -X DELETE http://localhost:8080/api/documents/<document id> \
  -H 'Cookie: __Host-SESSION=<session id>; XSRF-TOKEN=<token>' -H 'X-XSRF-TOKEN: <token>'
----

A `401` of type `urn:problem:documents:step-up-required` carries the `acrValues` and `maxAge` the SPA must pass to
`/bff/login`; a `403` means the access token of the session lacks `documents.read`, and a `502` that the resource server
could not be reached or answered with an unexpected error.

== Tests

The example has no tagged test for the BFF, so the tests are described here and not shown. Every `+*IT+` runs the whole
application, with a Testcontainers PostgreSQL where it needs a database:

* `BffSessionIT` proves that signing in stores the session in `spring_session`, hands the browser the `+__Host-+`
  cookie with its attributes, and that Spring Boot's session auto-configuration (and so `+spring.session.*+`) is in effect.
* `SecurityConfigIT` exercises the filter chain: PKCE on the authorization request, the step-up parameters (and a `400` for
  invalid ones), the redirect of a failed sign-in, `401` for an anonymous `+/api/**+` call, the readable `XSRF-TOKEN`
  cookie, a `403` for a `POST` without a valid CSRF token, and the logout (`POST` only, from a form with the raw token).
* `UserControllerIT` and `DocumentsApiIT` call `/bff/user` and `/api/documents` through the whole chain; the resource
  server is a `MockRestServiceServer` bound to the `RestClient.Builder`, so the relay, the token handling and the error
  translation are tested without a second application.
* `SpaStaticResourcesIT` checks that the SPA's files are served.
* `OpenApiDriftIT` compares the running application with `bff-api-v1.yaml`.
* The unit tests next to each class cover the `returnTo` validator, the step-up resolver, the CSRF cookie filter and the
  mappers; the Playwright test in `e2e-tests` signs in through the real stack.

The mocking technique is described in the
https://docs.spring.io/spring-framework/reference/testing/spring-mvc-test-client.html[Spring Framework client-side REST test support].

== Security notes and pitfalls

* *Tokens never reach the browser.* The access, refresh and ID tokens stay in the server-side session. The two places
  where a token could leak are the logout redirect (it carries `id_token_hint`, hence the top-level form post instead of
  `fetch`) and the SPA's error handling (the script only ever shows a generic message). XSS is still dangerous in a BFF:
  a script can call `+/api/**+` with the cookie. That is why the content security policy allows same-origin resources only
  (`+default-src 'self'; frame-ancestors 'none'+`) and why the SPA has no inline script and no third-party content.
* *CSRF with a SPA.* Cookie authentication means every state-changing request is a CSRF target. The token is in the
  `XSRF-TOKEN` cookie, readable by the script (not `HttpOnly`, by design), and must come back in the `X-XSRF-TOKEN`
  header or the `_csrf` form field. `SameSite=Lax` is defence in depth, not a replacement. See the
  https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html[OWASP CSRF Prevention Cheat Sheet].
* *Cookie attributes.* `+__Host-+` requires `Secure`, `Path=/` and no `Domain`; the browser rejects a cookie that does
  not meet them. In development a browser treats `localhost` as a secure context for this purpose, but a development
  setup served over plain HTTP on another host name will not keep the cookie. See
  https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie[Set-Cookie on MDN].
* *Session fixation.* The session is created before the user is authenticated (it holds `returnTo`, the PKCE verifier and
  `state`), so the session id must change at login. Spring Security's default does that; do not disable it. See
  https://docs.spring.io/spring-security/reference/servlet/authentication/session-management.html#ns-session-fixation[session fixation protection].
* *Open redirects.* `returnTo` is validated twice (when the login starts and when it completes) against an allow-list.
  Never redirect to a value taken from a request without such a check.
* *Refresh handling.* The `OAuth2AuthorizedClientManager` renews the access token with the refresh token when it
  expires. The authorization server rotates refresh tokens and detects reuse (see the tokens page of this guide), so a
  renewal that fails (for example after a reuse was detected) leaves the session without a usable token: the example
  answers `401` and the SPA signs in again. A failed renewal must end the session's use of the token, never fall back to an unauthenticated call (hence
  the second interceptor).
* *Back-channel and session lifetime.* The BFF session and the authorization server session are independent: ending one
  does not end the other, which is why logout goes through RP-initiated logout. The session timeout is the Boot
  `spring.session.timeout`, and expired rows are removed by Spring Session's cleanup.
* *Secrets.* `BFF_CLIENT_SECRET` comes from the environment and is never committed. The example is never deployed; do not
  reuse its development values.

For the general guidance see the https://www.rfc-editor.org/rfc/rfc10017[IETF OAuth 2.0 for Browser-Based Applications] and the https://www.rfc-editor.org/rfc/rfc9700[OAuth 2.0 Security Best Current Practice].
