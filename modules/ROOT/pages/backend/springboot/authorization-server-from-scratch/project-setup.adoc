== Clone the example

The example is not published as a package, so you build it from source. You need a *JDK between 21 and 25* (the
build enforces `[21,26)` because SpotBugs cannot parse the class files of newer JDKs), and *Docker* for the integration
tests and for the local services. Maven itself is optional: the repository ships the Maven wrapper.

[source,bash]
----
git clone https://github.com/albertoirurueta/irurueta-auth-server.git
cd irurueta-auth-server
./mvnw -v
----

The wrapper downloads the Maven version pinned in `.mvn/wrapper/maven-wrapper.properties` on first use. See
https://maven.apache.org/wrapper/[the Maven Wrapper documentation] for how it works.

== The starters, module by module

The root `pom.xml` uses `spring-boot-starter-parent` 4.1.2, so every Spring Boot starter below is version-managed
and carries its Boot 4.1 name, for example `spring-boot-starter-webmvc` and
`spring-boot-starter-security-oauth2-authorization-server`. Each application is a
reactor of small modules, and a dependency sits in the narrowest module that needs it:

|===
|Module

|Why it is there

|`auth-server/api/web`
|`spring-boot-starter-security-oauth2-authorization-server`

|`auth-server/api/web`

== Profiles

A Spring profile switches a set of beans and property files on or off, as explained in
xref:backend/springboot/configuration-and-profiles.adoc[Configuration and Profiles]. The example uses these:

* `dev` (`auth-server` and `bff`): local development only. It starts the services of `compose.yaml` through
  `spring-boot-docker-compose`, points the mail relay at Mailpit, sets the local redirect URIs of the seeded clients
  and seeds the demo data below. Never activate it outside a developer machine.
* `test`: activated by the integration tests. It selects a logging SMS sender that keeps its messages in memory.
* `legacy-implicit`, `twilio` and `sns`: opt-in profiles used by later pages. `legacy-implicit` enables a demo of the
  removed implicit grant, and `twilio` or `sns` choose the SMS gateway. A deployment always activates one SMS profile,
  because `auth-server` refuses to start without an SMS gateway outside `dev` and `test`.

The profile files are `application-<profile>.yml` in each application's `boot` module. See
https://docs.spring.io/spring-boot/reference/features/profiles.html[the Spring Boot profiles reference] for the
mechanism itself.

== Local services with Docker Compose

The root `compose.yaml` starts PostgreSQL 18 and Mailpit for local development; it holds throwaway development
credentials that must never be reused. The `compose/init-databases.sql` script creates one database per application
next to the `authserver` one. The `dev` profile sets `spring.docker.compose.file` to `../../compose.yaml`, relative
to the `boot` module directory that `spring-boot:run` uses as its working directory, so Spring Boot starts the
containers before the application context, takes the datasource connection details from them (the published
PostgreSQL port is random) and stops them when the application stops. Starting the jar or an IDE configuration from
another directory needs `SPRING_DOCKER_COMPOSE_FILE` to point to the file.

The compose file and the dev profile have no `tag::` regions yet, so they are described here rather than listed. The
mechanism comes from https://docs.spring.io/spring-boot/reference/features/dev-services.html#features.dev-services.docker-compose[the Spring Boot Docker Compose support reference].

== Run order

Start each application in its own terminal, with `auth-server` first, because the other applications resolve its
issuer metadata:

[source,bash]
----
./mvnw -pl auth-server/boot -am spring-boot:run -Dspring-boot.run.profiles=dev
./mvnw -pl resource-server/boot -am spring-boot:run
./mvnw -pl bff/boot -am spring-boot:run -Dspring-boot.run.profiles=dev
----

`auth-server` listens on port 9000, `resource-server` on 8081 and `bff` on 8080. The `dev` profile of `auth-server`
logs the generated secret of the seeded `bff` client once at start; export it as `BFF_CLIENT_SECRET` before starting
the `bff`, which refuses to start without it. Then open http://localhost:8080 and sign in. The `service-client` has no
HTTP port and is started the same way when you want to see the client credentials grant. These are the Maven
commands of https://docs.spring.io/spring-boot/maven-plugin/run.html[the Spring Boot Maven plugin run goal].

== Seeded demo data

Nothing is seeded by default. With the `dev` profile, `auth-server` seeds a user named `demo` whose generated password
is written to the log at start, the confidential `bff` client with a generated secret, and the public `device-client`
of a later page. A client is seeded only when its redirect URIs are configured: the `dev` profile configures the BFF
on port 8080 and a single-page application on port 3000, and the secret of the `bff` client comes from the
environment, never from the file. The definitions of the two default clients are tagged in the code:

[source,java]
----
include::irurueta-auth-server::example$auth-server/application/src/main/java/com/irurueta/authserver/authorization/application/clients/DefaultClientDefinitions.java[tag=clients-seed]
----

These definitions are the `RegisteredClient` of Spring Authorization Server expressed as the application's own
`ClientRegistration`; see https://docs.spring.io/spring-authorization-server/reference/core-model-components.html#registered-client[the registered client section of the core model reference].

The properties that decide which clients are seeded and where they redirect are tagged too:

[source,yaml]
----
include::irurueta-auth-server::example$auth-server/boot/src/main/resources/application.yml[tag=clients-seed-config]
----

The `+${NAME:default}+` placeholders are the externalised configuration of
https://docs.spring.io/spring-boot/reference/features/external-config.html[Spring Boot], where the part after the colon is the default.

== How these pages show code

The pages of this guide never paste application code. Every listing is an `include::` of a tagged region of the example
repository, so the code you read is the code CI compiled and tested. In the example, a region is marked with a
`tag::name[]` and an `end::name[]` comment around the lines to show, and the page includes it with
`include::irurueta-auth-server::example$<path>[tag=name]`. The example repository is an Antora component of its own
(its `docs/antora.yml`), and the Antora Collector extension copies each module's `+src/**+`, the OpenAPI contracts under
`apis/` and the root `pom.xml` and `compose.yaml` into that component's `example$` family at build time, so a path such
as `+example$auth-server/api/web/src/main/java/...+` is the module path inside the repository. Each listing is followed by a link to the
official page it derives from. See https://docs.asciidoctor.org/asciidoc/latest/directives/include-tagged-regions/[the
AsciiDoc tagged regions reference] and https://docs.antora.org/collector-extension/latest/[the Antora Collector extension documentation].

== Run the tests

`./mvnw verify` compiles every module, runs the unit tests (`+*Test+`, Surefire) and the integration tests (`+*IT+`,
Failsafe) and every build gate, and writes the reports. `./mvnw test` is the fast loop: unit tests only, no Spring
context and no Docker. A single class in a single module:

[source,bash]
----
./mvnw verify
./mvnw test
./mvnw -pl auth-server/api/web -am test -Dtest=LoginControllerTest
----

The integration tests do not use `compose.yaml`: they start their own PostgreSQL container through the `test-support`
module. The page xref:backend/springboot/unit-and-integration-testing.adoc[Unit and Integration Testing] explains the
test slices and Testcontainers that the example relies on, and the Spring Boot reference describes
https://docs.spring.io/spring-boot/reference/testing/testcontainers.html[Testcontainers support] and its `@ServiceConnection` wiring.

== Continuous integration

A single workflow, `.github/workflows/build.yml`, builds and tests the example on every push to `main`, `develop` and
`+release_*+` branches and on pull requests. It sets up JDK 21, caches the Playwright browsers, runs
`./mvnw -B -ntp clean verify` (build gates, unit and integration tests and the Playwright sign-in smoke test) and
uploads the reports. It is a test-only pipeline: the example is *never deployed*, so there is no publish or release
job. The workflow is not part of the Collector scan and has no tagged region, so it is described here. See
https://docs.github.com/en/actions/writing-workflows[the GitHub Actions workflow reference].
