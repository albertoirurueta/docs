= Bookshelf End to End
:description: The complete Bookshelf application on a kind cluster, from an empty cluster to a hardened stack -- namespace with Pod Security labels, ConfigMaps and Secrets, a PostgreSQL StatefulSet, three Deployments with probes resources and security contexts, Services, Gateway and HTTPRoutes, NetworkPolicies, RBAC, HPA, PDB and a notifier CronJob -- then packaged with Kustomize overlays and Helm and delivered with Argo CD.
:keywords: Bookshelf, kind, end to end, namespace, Pod Security Admission, ConfigMap, Secret, StatefulSet, Deployment, probes, securityContext, Gateway API, HTTPRoute, NetworkPolicy, RBAC, HorizontalPodAutoscaler, PodDisruptionBudget, CronJob, Kustomize, Helm, Argo CD, Spring Boot, Quarkus, ASP.NET Core, Aspire, FastAPI

include::partial$kubernetes-disclaimer.adoc[]

Every earlier page in this section used one running scenario, the *Bookshelf*, to show a single feature at a time. This
page assembles the pieces into one working stack, on Kubernetes 1.37 (kubectl 1.37) with a kind 0.33 cluster,
and then shows how the same stack is packaged as Kustomize overlays and a Helm chart and delivered by Argo CD. Each
step links back to the page that explains it, so this is the place to read the concepts *in combination*, and the
linked pages are the place to read them in depth. The container images are neutral placeholders
(`ghcr.io/example/bookshelf-catalog-api:1.0.0` and friends) rather than published images; substitute your own.

The stack has three stateless services -- `catalog-api`, `reviews-api` and `web` -- a PostgreSQL StatefulSet, a
Redis cache, and a `notifier` CronJob. The figure below shows the finished result.

image::kubernetes-bookshelf-deployment.svg[The complete Bookshelf deployment on a kind cluster from Gateway and HTTPRoutes through three Deployments to PostgreSQL and Redis with the notifier CronJob,align="center"]

== Step 1: an empty cluster

A kind cluster with one control plane and two workers, and a host port mapped for the Gateway (see
xref:backend/kubernetes/getting-started.adoc[Getting Started] and xref:backend/kubernetes/kubectl-essentials.adoc[kubectl Essentials]):

[source,yaml]
----
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
name: bookshelf
nodes:
  - role: control-plane
    image: kindest/node:v1.37.0
    extraPortMappings:
      - containerPort: 30080
        hostPort: 8080
  - role: worker
    image: kindest/node:v1.37.0
  - role: worker
    image: kindest/node:v1.37.0
----

[source,bash]
----
kind create cluster --config kind.yaml
kubectl cluster-info --context kind-bookshelf
kubectl get nodes
----

Source: https://kind.sigs.k8s.io/docs/user/configuration/[kind Docs -- Configuration]

kind's default CNI does not enforce NetworkPolicies. To exercise step 9, create the cluster with
`networking.disableDefaultCNI: true` and install a policy-capable CNI, as explained in
xref:backend/kubernetes/cluster-networking-and-cni.adoc[Cluster Networking and CNI].

== Step 2: the namespace and its Pod Security labels

The namespace is the unit that policies, quotas and RBAC attach to. Its labels turn on Pod Security Admission at the
`restricted` level, so every Pod in it must already follow the hardening used below
(xref:backend/kubernetes/pod-security.adoc[Pod Security]):

[source,yaml]
----
apiVersion: v1
kind: Namespace
metadata:
  name: bookshelf
  labels:
    pod-security.kubernetes.io/enforce: restricted
    pod-security.kubernetes.io/enforce-version: latest
    pod-security.kubernetes.io/warn: restricted
----

Source: https://kubernetes.io/docs/tasks/configure-pod-container/enforce-standards-namespace-labels/[Kubernetes Docs -- Enforce Pod Security Standards with Namespace Labels]

== Step 3: configuration and credentials

Non-secret settings live in a ConfigMap, credentials in a Secret (see
xref:backend/kubernetes/objects-and-the-api.adoc[Objects and the API], xref:backend/kubernetes/configmaps.adoc[ConfigMaps] and xref:backend/kubernetes/secrets.adoc[Secrets]):

[source,yaml]
----
apiVersion: v1
kind: ConfigMap
metadata:
  name: bookshelf-config
  namespace: bookshelf
data:
  DB_HOST: postgres-0.postgres.bookshelf.svc.cluster.local
  DB_NAME: catalog
  REDIS_HOST: redis.bookshelf.svc.cluster.local
  LOG_LEVEL: info
----

Credentials are generated at creation time and never written into a manifest that is committed:

[source,bash]
----
kubectl -n bookshelf create secret generic postgres-credentials \
  --from-literal=POSTGRES_USER=bookshelf \
  --from-literal=POSTGRES_PASSWORD="$(openssl rand -base64 24)"
----

Source: https://kubernetes.io/docs/tasks/configmap-secret/managing-secret-using-kubectl/[Kubernetes Docs -- Managing Secrets using kubectl]

In a real delivery pipeline the Secret comes from an external secret manager or a sealed secret, as described in
xref:backend/kubernetes/gitops-and-ci-cd.adoc[GitOps and CI/CD].

== Step 4: PostgreSQL as a StatefulSet

A headless Service and a one-replica StatefulSet with a `volumeClaimTemplate`, following
xref:backend/kubernetes/statefulsets.adoc[StatefulSets] and xref:backend/kubernetes/persistent-volumes-and-storage-classes.adoc[Persistent Volumes and Storage Classes]. Production
clusters should prefer an operator or a managed database; see
xref:backend/kubernetes/stateful-applications-in-practice.adoc[Stateful Applications in Practice].

[source,yaml]
----
apiVersion: v1
kind: Service
metadata:
  name: postgres
  namespace: bookshelf
spec:
  clusterIP: None
  selector:
    app.kubernetes.io/name: postgres
  ports:
    - port: 5432
---
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: postgres
  namespace: bookshelf
spec:
  serviceName: postgres
  replicas: 1
  selector:
    matchLabels:
      app.kubernetes.io/name: postgres
  template:
    metadata:
      labels:
        app.kubernetes.io/name: postgres
        app.kubernetes.io/part-of: bookshelf
    spec:
      securityContext:
        runAsNonRoot: true
        runAsUser: 999
        fsGroup: 999
        seccompProfile:
          type: RuntimeDefault
      containers:
        - name: postgres
          image: postgres:18
          ports:
            - containerPort: 5432
          envFrom:
            - secretRef:
                name: postgres-credentials
          env:
            - name: POSTGRES_DB
              valueFrom:
                configMapKeyRef:
                  name: bookshelf-config
                  key: DB_NAME
            - name: PGDATA
              value: /var/lib/postgresql/data/pgdata
          readinessProbe:
            exec:
              command: ["pg_isready", "-U", "bookshelf"]
          resources:
            requests: { cpu: 250m, memory: 512Mi }
            limits: { memory: 512Mi }
          securityContext:
            allowPrivilegeEscalation: false
            capabilities:
              drop: ["ALL"]
          volumeMounts:
            - name: data
              mountPath: /var/lib/postgresql/data
  volumeClaimTemplates:
    - metadata:
        name: data
      spec:
        accessModes: ["ReadWriteOnce"]
        resources:
          requests:
            storage: 10Gi
----

Source: https://kubernetes.io/docs/concepts/workloads/controllers/statefulset/[Kubernetes Docs -- StatefulSets]

== Step 5: the three Deployments

Each service is a Deployment with a rolling update strategy, readiness and liveness probes, resource requests and
limits, and a restricted `securityContext`. `catalog-api` is shown in full; the others differ only in name, image,
port and the environment they receive. See xref:backend/kubernetes/pods.adoc[Pods], xref:backend/kubernetes/replicasets-and-deployments.adoc[ReplicaSets and Deployments],
xref:backend/kubernetes/deployment-strategies.adoc[Deployment Strategies], xref:backend/kubernetes/health-probes-and-lifecycle.adoc[Health Probes and Lifecycle] and
xref:backend/kubernetes/resource-management.adoc[Resource Management].

[source,yaml]
----
apiVersion: apps/v1
kind: Deployment
metadata:
  name: catalog-api
  namespace: bookshelf
  labels:
    app.kubernetes.io/name: catalog-api
    app.kubernetes.io/part-of: bookshelf
spec:
  replicas: 2
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0
  selector:
    matchLabels:
      app.kubernetes.io/name: catalog-api
  template:
    metadata:
      labels:
        app.kubernetes.io/name: catalog-api
        app.kubernetes.io/part-of: bookshelf
    spec:
      automountServiceAccountToken: false
      securityContext:
        runAsNonRoot: true
        seccompProfile:
          type: RuntimeDefault
      containers:
        - name: catalog-api
          image: ghcr.io/example/bookshelf-catalog-api:1.0.0
          ports:
            - name: http
              containerPort: 8080
          envFrom:
            - configMapRef:
                name: bookshelf-config
          env:
            - name: DB_USER
              valueFrom:
                secretKeyRef:
                  name: postgres-credentials
                  key: POSTGRES_USER
          startupProbe:
            httpGet: { path: /health/started, port: http }
            failureThreshold: 30
            periodSeconds: 2
          readinessProbe:
            httpGet: { path: /health/ready, port: http }
            periodSeconds: 5
          livenessProbe:
            httpGet: { path: /health/live, port: http }
            periodSeconds: 10
          resources:
            requests: { cpu: 200m, memory: 256Mi }
            limits: { memory: 384Mi }
          securityContext:
            allowPrivilegeEscalation: false
            readOnlyRootFilesystem: true
            capabilities:
              drop: ["ALL"]
          volumeMounts:
            - name: tmp
              mountPath: /tmp
      volumes:
        - name: tmp
          emptyDir: {}
----

Source: https://kubernetes.io/docs/concepts/workloads/controllers/deployment/[Kubernetes Docs -- Deployments]

The database password is deliberately not passed as an environment variable here; the application reads it from a
mounted Secret file or, better, from a short-lived credential source. The `reviews-api` Deployment listens on port
8081 and `web` on port 8080 with `replicas: 2`.

== Step 6: Services

A ClusterIP Service per Deployment gives each a stable name and virtual IP; the Gateway routes to them (see
xref:backend/kubernetes/services.adoc[Services] and xref:backend/kubernetes/dns-and-service-discovery.adoc[DNS and Service Discovery]):

[source,yaml]
----
apiVersion: v1
kind: Service
metadata:
  name: catalog-api
  namespace: bookshelf
spec:
  selector:
    app.kubernetes.io/name: catalog-api
  ports:
    - name: http
      port: 80
      targetPort: http
----

Source: https://kubernetes.io/docs/concepts/services-networking/service/[Kubernetes Docs -- Service]

== Step 7: Gateway and HTTPRoutes

Gateway API replaces Ingress for the north-south entry point. The GatewayClass and controller installation are in
xref:backend/kubernetes/gateway-api.adoc[Gateway API] (Envoy Gateway on kind); the Bookshelf-specific part is one Gateway and one
HTTPRoute (compare xref:backend/kubernetes/ingress.adoc[Ingress], which the Ingress-NGINX retirement has made a legacy choice):

[source,yaml]
----
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: bookshelf-gateway
  namespace: bookshelf
spec:
  gatewayClassName: envoy-gateway
  listeners:
    - name: http
      protocol: HTTP
      port: 80
      allowedRoutes:
        namespaces:
          from: Same
---
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: bookshelf
  namespace: bookshelf
spec:
  parentRefs:
    - name: bookshelf-gateway
  rules:
    - matches:
        - path: { type: PathPrefix, value: /catalog }
      backendRefs:
        - name: catalog-api
          port: 80
    - matches:
        - path: { type: PathPrefix, value: /reviews }
      backendRefs:
        - name: reviews-api
          port: 80
    - matches:
        - path: { type: PathPrefix, value: / }
      backendRefs:
        - name: web
          port: 80
----

Source: https://gateway-api.sigs.k8s.io/api-types/httproute/[Gateway API Docs -- HTTPRoute]

== Step 8: a Redis cache

The cache is a single-replica Deployment behind a Service named `redis`, following the same shape as the services
above (an image of `redis:8`, port 6379, a `readinessProbe` running `redis-cli ping`). A replicated, Sentinel-managed
Redis is the subject of xref:backend/kubernetes/stateful-applications-in-practice.adoc[Stateful Applications in Practice], and Redis itself is
covered in xref:database/redis/redis-software-cloud-kubernetes-and-valkey.adoc[Redis on Kubernetes].

== Step 9: NetworkPolicies

By default every Pod can reach every other Pod. A default-deny policy plus narrow allows implements
least privilege (xref:backend/kubernetes/network-policies.adoc[Network Policies]):

[source,yaml]
----
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny
  namespace: bookshelf
spec:
  podSelector: {}
  policyTypes: ["Ingress", "Egress"]
---
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-catalog-to-postgres
  namespace: bookshelf
spec:
  podSelector:
    matchLabels:
      app.kubernetes.io/name: postgres
  policyTypes: ["Ingress"]
  ingress:
    - from:
        - podSelector:
            matchLabels:
              app.kubernetes.io/name: catalog-api
      ports:
        - port: 5432
---
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-dns-egress
  namespace: bookshelf
spec:
  podSelector: {}
  policyTypes: ["Egress"]
  egress:
    - to:
        - namespaceSelector:
            matchLabels:
              kubernetes.io/metadata.name: kube-system
      ports:
        - { port: 53, protocol: UDP }
        - { port: 53, protocol: TCP }
----

Source: https://kubernetes.io/docs/concepts/services-networking/network-policies/[Kubernetes Docs -- Network Policies]

Further allow rules admit the Gateway's data plane to the three front-end services, the services to Redis, and
`catalog-api` egress to PostgreSQL on port 5432.

== Step 10: RBAC for the notifier

Pods run as a ServiceAccount, and a Role grants exactly what that account needs
(xref:backend/kubernetes/authentication-authorization-and-rbac.adoc[Authentication, Authorization and RBAC]). The `notifier` reads the ConfigMap and
nothing else:

[source,yaml]
----
apiVersion: v1
kind: ServiceAccount
metadata:
  name: notifier
  namespace: bookshelf
automountServiceAccountToken: false
---
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: notifier-config-reader
  namespace: bookshelf
rules:
  - apiGroups: [""]
    resources: ["configmaps"]
    resourceNames: ["bookshelf-config"]
    verbs: ["get"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: notifier-config-reader
  namespace: bookshelf
subjects:
  - kind: ServiceAccount
    name: notifier
roleRef:
  kind: Role
  name: notifier-config-reader
  apiGroup: rbac.authorization.k8s.io
----

Source: https://kubernetes.io/docs/reference/access-authn-authz/rbac/[Kubernetes Docs -- Using RBAC Authorization]

Verify it with `kubectl auth can-i get configmaps/bookshelf-config --as system:serviceaccount:bookshelf:notifier -n bookshelf`.

== Step 11: autoscaling and disruption budget

An HPA (`autoscaling/v2`) scales `catalog-api` on CPU, and a PodDisruptionBudget keeps at least one replica during
node drains (xref:backend/kubernetes/autoscaling.adoc[Autoscaling], xref:backend/kubernetes/scheduling-and-disruptions.adoc[Scheduling and Disruptions]). The HPA needs
metrics-server, installed as described in xref:backend/kubernetes/observability-logging-and-metrics.adoc[Observability: Logging and Metrics].

[source,yaml]
----
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: catalog-api
  namespace: bookshelf
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: catalog-api
  minReplicas: 2
  maxReplicas: 6
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70
---
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: catalog-api
  namespace: bookshelf
spec:
  minAvailable: 1
  selector:
    matchLabels:
      app.kubernetes.io/name: catalog-api
----

Source: https://kubernetes.io/docs/tasks/run-application/horizontal-pod-autoscale/[Kubernetes Docs -- Horizontal Pod Autoscaling]

== Step 12: the notifier CronJob

The `notifier` sends review digests every fifteen minutes (see xref:backend/kubernetes/jobs-and-cronjobs.adoc[Jobs and CronJobs]):

[source,yaml]
----
apiVersion: batch/v1
kind: CronJob
metadata:
  name: notifier
  namespace: bookshelf
spec:
  schedule: "*/15 * * * *"
  concurrencyPolicy: Forbid
  successfulJobsHistoryLimit: 3
  jobTemplate:
    spec:
      backoffLimit: 2
      activeDeadlineSeconds: 600
      ttlSecondsAfterFinished: 3600
      template:
        spec:
          serviceAccountName: notifier
          restartPolicy: OnFailure
          securityContext:
            runAsNonRoot: true
            seccompProfile:
              type: RuntimeDefault
          containers:
            - name: notifier
              image: ghcr.io/example/bookshelf-notifier:1.0.0
              envFrom:
                - configMapRef:
                    name: bookshelf-config
              resources:
                requests: { cpu: 50m, memory: 64Mi }
                limits: { memory: 128Mi }
              securityContext:
                allowPrivilegeEscalation: false
                capabilities:
                  drop: ["ALL"]
----

Source: https://kubernetes.io/docs/concepts/workloads/controllers/cron-jobs/[Kubernetes Docs -- CronJob]

Then apply everything and check the result:

[source,bash]
----
kubectl apply -f namespace.yaml
kubectl apply -f . --recursive
kubectl -n bookshelf get all,gateway,httproute,hpa,pdb,networkpolicy
kubectl -n bookshelf rollout status deployment/catalog-api
curl -s http://localhost:8080/catalog/
----

When something does not start, the routine in xref:backend/kubernetes/debugging-and-troubleshooting.adoc[Debugging and Troubleshooting] applies:
`kubectl describe`, events, logs and `kubectl debug`. Node-level scheduling rules such as affinity and taints are in
xref:backend/kubernetes/scheduling-and-disruptions.adoc[Scheduling and Disruptions], the wider cluster design in
xref:backend/kubernetes/introduction-and-architecture.adoc[Introduction and Architecture], and namespace quotas and limits in
xref:backend/kubernetes/resource-management.adoc[Resource Management]. Other workload controllers used elsewhere in the section are
xref:backend/kubernetes/daemonsets.adoc[DaemonSets] (per-node agents), and extensions through
xref:backend/kubernetes/custom-resources-and-operators.adoc[Custom Resources and Operators] and
xref:backend/kubernetes/admission-control-and-policy.adoc[Admission Control and Policy].

== Packaged as Kustomize overlays

Fifteen-odd hand-applied files do not scale to several environments. The same objects move into a Kustomize base with
one overlay per environment (xref:backend/kubernetes/kustomize.adoc[Kustomize]):

[source,yaml]
----
# k8s/overlays/prod/kustomization.yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
resources:
  - ../../base
  - hpa.yaml
images:
  - name: ghcr.io/example/bookshelf-catalog-api
    newTag: 1.1.0
patches:
  - path: resources-patch.yaml
----

[source,bash]
----
kubectl kustomize k8s/overlays/prod | less
kubectl apply -k k8s/overlays/prod
----

Source: https://kubernetes.io/docs/tasks/manage-kubernetes-objects/kustomization/[Kubernetes Docs -- Declarative Management of Kubernetes Objects Using Kustomize]

== Packaged as a Helm chart

Where the stack is installed by other teams, with values, upgrades and rollbacks, it becomes a chart
(xref:backend/kubernetes/helm.adoc[Helm]). The environment is then a values file:

[source,bash]
----
helm lint charts/bookshelf
helm upgrade --install bookshelf charts/bookshelf \
  --namespace bookshelf --create-namespace \
  -f charts/bookshelf/values-prod.yaml
helm history bookshelf -n bookshelf
helm rollback bookshelf 1 -n bookshelf
----

Source: https://helm.sh/docs/helm/helm_upgrade/[Helm Docs -- helm upgrade]

Kustomize is simpler when you own the manifests; Helm is better when you distribute them. Both are legitimate
inputs to the next step.

== Delivered with Argo CD

Delivery by hand is replaced with a Git repository and a controller that reconciles the cluster to it
(xref:backend/kubernetes/gitops-and-ci-cd.adoc[GitOps and CI/CD]). An Argo CD `Application` points at the prod overlay:

[source,yaml]
----
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: bookshelf-prod
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/example/bookshelf-deploy.git
    targetRevision: main
    path: k8s/overlays/prod
  destination:
    server: https://kubernetes.default.svc
    namespace: bookshelf
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
----

Source: https://argo-cd.readthedocs.io/en/stable/user-guide/application-specification/[Argo CD Docs -- Application specification]

[mermaid]
....
flowchart LR
  Dev["Developer"] -->|"push"| CI["CI builds image"]
  CI -->|"bump tag"| Git[("Deploy repo")]
  Git -->|"watched by"| Argo["Argo CD"]
  Argo -->|"sync"| K8s["Bookshelf on the cluster"]
  K8s -.->|"drift detected"| Argo
....

The Bookshelf is the same shape as the older teaching examples. Rensin's 2015 book walks through a *Guestbook*
(a front end plus a Redis back end) and a *WordPress plus MySQL* pair (a stateless web tier plus a stateful database
on a persistent volume). Each maps onto steps above: stateless Deployments behind Services, and PostgreSQL and Redis as
stateful back ends with their own storage.

== Application-side notes

The cluster only runs what the application exposes, so each framework has a few obligations. Health endpoints must
exist for the probes, configuration should arrive through environment variables or mounted files, the process
must handle SIGTERM for graceful shutdown, and logs should go to standard output.

* *Spring Boot*: Actuator liveness and readiness groups back the probes, and ConfigMaps and Secrets can be
  imported as configuration; see xref:backend/springboot/configuration-and-profiles.adoc[Spring Boot configuration and profiles] and
  xref:backend/springboot/metrics-and-observability.adoc[Spring Boot metrics and observability].
* *Quarkus*: the Kubernetes extension generates the manifests and the health and metrics extensions provide the
  endpoints; see xref:backend/quarkus/kubernetes-and-openshift.adoc[Quarkus on Kubernetes and OpenShift].
* *ASP.NET Core and Aspire*: health checks map to the probes and Aspire can publish a deployment manifest; see
  xref:web/aspnet/core/aspire-and-cloud-native.adoc[ASP.NET Core Aspire and cloud native].
* *FastAPI*: a Python equivalent is planned as a separate section (issue #199) and is mentioned here only for
  completeness; the same probe, configuration and shutdown obligations apply.

The images themselves are built and published as described in
xref:backend/docker/image-best-practices-and-security.adoc[Docker image best practices and security] and
xref:backend/docker/registries-and-docker-hub.adoc[Registries and Docker Hub]. A list of everything that changed since the books were written is in
xref:backend/kubernetes/whats-changed-and-migration.adoc[What's Changed and Migration], managed-cluster variants are in
xref:backend/kubernetes/managed-kubernetes-and-distributions.adoc[Managed Kubernetes and Distributions], and cluster administration is in
xref:backend/kubernetes/cluster-setup-and-administration.adoc[Cluster Setup and Administration]. The volume and storage building blocks used by
PostgreSQL are in xref:backend/kubernetes/volumes-and-ephemeral-storage.adoc[Volumes and Ephemeral Storage], pod-to-pod wiring in
xref:backend/kubernetes/cluster-networking-and-cni.adoc[Cluster Networking and CNI], and device-heavy workloads in
xref:backend/kubernetes/dynamic-resource-allocation-and-devices.adoc[Dynamic Resource Allocation and Devices].
