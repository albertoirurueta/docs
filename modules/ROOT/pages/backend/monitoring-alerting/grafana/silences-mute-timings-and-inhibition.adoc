= Grafana Silences, Mute Timings and Inhibition
:description: The three ways Grafana Alerting suppresses notifications without stopping evaluation: one-off silences, recurring mute timings and active time intervals attached to child notification policies, and the Grafana 13 inhibition rules API, with matcher semantics, retention, as-code examples and a Bookshelf lab exercise.
:keywords: Grafana, alerting, silence, mute timing, active time interval, inhibition rule, inhibitionrules, maintenance window, notification policy, matchers, Unsilence, Bookshelf

Checked on 2026-11-09 against Grafana 13.3.x. Tested with Grafana Enterprise 13.3.0 in the hands-on lab: the inhibition rule request below was accepted by the `/apis` endpoint, and the HCL passes `terraform validate` with provider 4.54.0.

include::partial$monitoring-alerting-grafana-disclaimer.adoc[]

Some alerts are expected: the planned Sunday deployment restarts Bookshelf, the nightly batch job spikes latency, or a database
that is already down makes every dependent alert redundant. Deleting the rule is the wrong answer, because the rule is
right the rest of the time. Grafana Alerting offers three mechanisms that stop *notifications* while leaving everything else
running: *silences* for one-off, time-boxed needs, *mute timings* and *active time intervals* for recurring
schedules, and *inhibition rules* for suppressing a consequence while its cause is firing. The tool-neutral concepts
(including why suppression must be time-limited and owned) are explained in
xref:backend/monitoring-alerting/alerting-fundamentals.adoc[Alerting Fundamentals] and
xref:backend/monitoring-alerting/notifications-and-incident-response.adoc[Notifications and Incident Response]. This page covers the
Grafana mechanics.

== What all three have in common

Each mechanism acts on the Alertmanager side of the pipeline, after evaluation and (for mute timings) as part of routing.
That has two consequences that explain most surprises.

* *Evaluation continues.* Alert rules keep running, the alert instances keep changing state, and firing instances are
  still visible in the Grafana UI and in state history. Only the notification is suppressed.
* *Scope is one Alertmanager.* A silence, mute timing or inhibition rule belongs to a single Alertmanager (the Grafana
  Alertmanager by default) and affects only alerts that Alertmanager manages.

[cols="2,3,3,3",options="header"]
|===
|Mechanism |Trigger |Matches alerts by |Typical use

|Silence
|A fixed start and end time
|Label matchers, created per occurrence
|A one-off deployment or investigation

|Mute timing
|A recurring schedule
|Attached to a child notification policy
|Weekly maintenance window

|Active time interval
|The reverse: notify only inside the schedule
|Attached to a child notification policy
|Warnings only during office hours

|Inhibition rule
|A matching source alert is firing
|Source and target matchers plus equal labels
|Suppress symptoms while their cause is firing
|===

Source: https://grafana.com/docs/grafana/latest/alerting/configure-notifications/create-silence/[Grafana: Configure silences],
https://grafana.com/docs/grafana/latest/alerting/configure-notifications/mute-timings/[Grafana: Mute timings and active time intervals]
and https://grafana.com/docs/grafana/latest/alerting/configure-notifications/inhibition-rules/[Grafana: Inhibition rules].

== Silences

A silence stops notifications for alerts that match a set of label matchers, between a start time and an end time. Create
one when an expected event would otherwise page someone, and give it a comment that says who asked and why.

=== Create a silence

. Open *Alerts & IRM*, then *Alerting*, then *Silences*.
. Choose the Alertmanager (a dropdown; the default is the Grafana Alertmanager) and click *Create silence*.
. Set *Silence start and end*; optionally set *Duration*, which updates the end time.
. Add one or more matchers: a label name, an operator and a value.
. Check *Affected alert instances*, which lists the matching alerts that are currently firing. An empty list
  means that the matchers match nothing today (a typo is the usual reason).
. Add a *Comment* and click *Submit*.

Silences can also start from an alert: the default notification contains a silence link, and a custom
xref:backend/monitoring-alerting/grafana/notification-templates.adoc[notification template] can print it with `+{{ .SilenceURL }}+`. A custom link
can be built by hand with a URL to the new-silence page whose `matcher` parameters have the form
`[label][operator][value]` and an optional `comment` (for an external Alertmanager add an `alertmanager` parameter with the
data source name).

Source: https://grafana.com/docs/grafana/latest/alerting/configure-notifications/create-silence/[Grafana: Configure silences].

=== Matchers

Each matcher is a label name, an operator and a value. The operators are `=` (equal), `!=` (not equal), `+=~+` (regular
expression match) and `+!~+` (regular expression non-match). Several matchers are combined with AND: every one must match.
For an alert with labels `foo=bar`, `baz=qux` and `id=12`, the matcher `pass:c[id=~[0-9\]+]` matches and `foo!=bar` does not.
To exclude alerts that carry a label (for example `team`), match the empty value with `team = ""`, `pass:c[team !~ ".+"]` or
`pass:c[team =~ "^$"]`.

A silence for the whole Bookshelf service during a planned restart needs one matcher, `application = bookshelf`.
A narrower silence for one rule uses the special matcher `+__alert_rule_uid__=<alert rule UID>+`, which is what the
*Silence notifications* action of a rule creates (a *rule-specific silence*). Prefer the narrowest matcher that
covers the event: a broad silence such as `pass:c[severity =~ ".+"]` hides the unrelated incident that happens during the window.

Source: https://grafana.com/docs/grafana/latest/alerting/configure-notifications/create-silence/[Grafana: How label matching works and rule-specific silences].

=== Editing, ending and retention

Edit a silence with the pen icon and *Submit*. To end it early select it and click *Unsilence*, which ends it immediately and
is the only way to end a silence before its end time: silences cannot be deleted manually. Expired silences are deleted
automatically after 5 days (this period cannot be configured; a cleanup job runs every 15 minutes), so the *Silences* list is a short
history, not an audit log, and the comment is the only record you can rely on.

The duration has no maximum by default, which makes a forgotten silence the most common long-lived failure of this
feature: a "temporary" silence with an end date next year is a muted rule. Administrators can limit the damage with
`alertmanager_max_silences_count` (maximum active and pending silences per tenant; expired silences count towards it; `0`
means no limit) and `alertmanager_max_silence_size_bytes` (`0` means no limit). In Grafana Cloud the standalone
Alertmanager UI is deprecated, so silences are managed in the Grafana Alerting UI.

Silences are one-off operational state, not configuration, and they are not among the alerting resources listed for
provisioning, so there is no file or Terraform form to show here. Create them in the UI when the event starts and end them with *Unsilence* when it is over.

Source: https://grafana.com/docs/grafana/latest/alerting/configure-notifications/create-silence/[Grafana: Edit silences, Remove silences, Silence duration and retention].

== Mute timings and active time intervals

A *mute timing* is a recurring schedule during which notifications are suppressed for the notification policies it is attached to. An *active
time interval* is the reverse: notifications are suppressed *unless* the moment falls inside the interval. They use the same definition, so
one list of named intervals can serve both purposes. Mute timings take precedence over active time intervals when
they overlap.

=== Time interval fields

[cols="2,5",options="header"]
|===
|Field |Behaviour

|Time range
|Start inclusive, end exclusive, in UTC unless a location is chosen.

|Location
|Interprets the time range in the local time of a location such as `Europe/Madrid`.

|Days of the week
|Days or ranges: `monday`, `monday:thursday`.

|Days of the month
|1 to 31 or ranges such as `1:7`; negative values count from the end, so `-1` is the last day.

|Months
|Numbers or names, and ranges: `1`, `may:august`.

|Years
|Years or ranges: `2026`, `2026:2027`.
|===

Matching works as follows: every field is a list and at least one element must match; a blank field matches
any value; a moment matches an interval only if *all* fields match; and one mute timing may contain several intervals, any of
which can match. The first Monday of March, June, September and December from 12:00 to 24:00 UTC is
written as time range 12:00 to 24:00, weekday `monday`, months `3, 6, 9, 12` and days of the month `1:7`.

=== Create and attach

. Open *Alerts & IRM*, *Alerting*, *Notification configuration*, the *Time intervals* tab, choose the Alertmanager and click *New time interval*.
  Complete the form and save.
. Open the *Notification policies* tab, edit a *child* policy (the three-dot menu, *Edit*) and select the interval under
  *Mute timings* or *Active timings*. Save.

Time intervals can only be assigned to child policies; the root (default) policy cannot have them and children do not
inherit them from their parent. This is a design constraint to plan around: to mute everything on Sundays, the routing tree needs a
child policy that matches everything (for example on a label every rule has) and carries the mute timing. The
structure of the tree is explained in
xref:backend/monitoring-alerting/grafana/notification-policies.adoc[Notification Policies].

Source: https://grafana.com/docs/grafana/latest/alerting/configure-notifications/mute-timings/[Grafana: Mute timings and active time intervals].

=== As code

The lab's Sunday maintenance window, as a provisioning file (under `provisioning/alerting`), uses `muteTimes`.

[source,yaml]
----
apiVersion: 1

muteTimes:
  - orgId: 1
    name: bookshelf-sunday-maintenance
    time_intervals:
      - times:
          - start_time: '02:00'
            end_time: '04:00'
        weekdays: ['sunday']
        location: 'Europe/Madrid'
----

Reference: https://grafana.com/docs/grafana/latest/alerting/set-up/provision-alerting-resources/file-provisioning/#import-mute-timings[Grafana: Import mute timings].

With Terraform, the interval and its use in a child policy (`mute_timings` suppress; `active_timings`, supported in Grafana
12.1 and later, notify only inside the interval) look like this. The `grafana_notification_policy` resource manages the *whole* tree, so
add the child to the policy resource that already describes your tree rather than creating a second one.

[source,hcl]
----
resource "grafana_mute_timing" "sunday_maintenance" {
  name = "bookshelf-sunday-maintenance"

  intervals {
    times {
      start = "02:00"
      end   = "04:00"
    }
    weekdays = ["sunday"]
    location = "Europe/Madrid"
  }
}

resource "grafana_mute_timing" "business_hours" {
  name = "bookshelf-business-hours"

  intervals {
    times {
      start = "08:00"
      end   = "18:00"
    }
    weekdays = ["monday:friday"]
    location = "Europe/Madrid"
  }
}

# Child policy inside the existing grafana_notification_policy resource:
#   policy {
#     matcher {
#       label = "team"
#       match = "="
#       value = "bookshelf-sre"
#     }
#     contact_point  = grafana_contact_point.bookshelf_webhook.name
#     mute_timings   = [grafana_mute_timing.sunday_maintenance.name]
#   }
----

Reference: https://github.com/grafana/terraform-provider-grafana/blob/main/docs/resources/mute_timing.md[Terraform provider: grafana_mute_timing]
and https://github.com/grafana/terraform-provider-grafana/blob/main/docs/resources/notification_policy.md[grafana_notification_policy].

== Inhibition rules

An *inhibition rule* suppresses notifications for *target* alerts while *source* alerts that match are firing. The
textbook case is a node that is down (source): the alerts of every service on that node (targets) tell the
responder nothing new. Where a silence has a fixed window and is created by hand per occurrence, an inhibition rule is
persistent configuration that is active exactly as long as the source alert fires.

*Availability and status.* Inhibition rules are available in Grafana 13 or higher. There is no user interface:
they are managed through the Grafana App Platform API, as the resource `inhibitionrules` in the group
`notifications.alerting.grafana.app`, version `v1beta1`. The version is beta and the documentation says it may change.
The documentation presents them mainly for compatibility with Alertmanager or Mimir configurations that were imported
into Grafana, and recommends silences or mute timings for most suppression needs; treat inhibition as an advanced tool.

=== Rule schema

[cols="2,1,5",options="header"]
|===
|Field |Required |Meaning

|`name`
|Yes
|Unique name, immutable after creation.

|`source_matchers`
|Yes
|One or more matchers selecting the inhibiting (source) alerts.

|`target_matchers`
|Yes
|One or more matchers selecting the inhibited (target) alerts.

|`equal`
|No
|Labels whose values must be equal in the source and the target alert.
|===

A matcher is an object with `label`, `type` (`=`, `!=`, `+=~+` or `+!~+`) and `value`. The `equal` list is what keeps a rule
from being too broad: with `equal: [cluster]` a source alert inhibits only targets in the same cluster; when `equal` is omitted,
any firing source alert inhibits *all* matching targets, whatever their labels. A missing label and an empty-valued label are
treated as equal for this comparison. The example from the documentation, which suppresses warnings while a
critical alert for the same cluster and namespace is firing:

[source,json]
----
{
  "name": "critical-inhibits-warnings",
  "source_matchers": [{ "label": "severity", "type": "=", "value": "critical" }],
  "target_matchers": [{ "label": "severity", "type": "=", "value": "warning" }],
  "equal": ["cluster", "namespace"]
}
----

Reference: https://grafana.com/docs/grafana/latest/alerting/configure-notifications/inhibition-rules/#example-suppress-warning-alerts[Grafana: Example, suppress warning alerts].

The documentation page shows only the rule body. On a Grafana 13.3.0 lab the resource is served at
`+/apis/notifications.alerting.grafana.app/v1beta1/namespaces/default/inhibitionrules+` (namespace `default` for organization 1, the `/apis` scheme described on
xref:backend/monitoring-alerting/grafana/installation-and-configuration.adoc[Installation and Configuration]), and the body goes into a
`metadata` and `spec` envelope. This request creates the Bookshelf rule, which suppresses everything of the application while the no-data alert is firing
(the lab alerts carry the label `application`), and was accepted with the response echoing the spec:

[source,bash]
----
curl -s -u admin:admin -X POST -H 'Content-Type: application/json' \
  http://localhost:3000/apis/notifications.alerting.grafana.app/v1beta1/namespaces/default/inhibitionrules -d '{
  "metadata": { "name": "no-data-inhibits-others" },
  "spec": {
    "source_matchers": [{ "label": "alertname", "type": "=", "value": "Bookshelf no data" }],
    "target_matchers": [{ "label": "application", "type": "=", "value": "bookshelf" }],
    "equal": ["application"]
  }
}'
----

A `GET` on the same URL lists the rules. The API is a beta version (`v1beta1`), so check the reference of your version before relying on a payload.

=== Managed and imported routes

An Alertmanager can hold several routing trees: the default Grafana-managed one and routes imported from a Prometheus
Alertmanager or Mimir configuration. A rule created through the API applies across the whole Alertmanager, including
alerts handled by imported routes. A rule that was *imported* is scoped to its own route: Grafana adds an internal label matcher so that it cannot suppress alerts
of other routes. To suppress alerts across several imported configurations, create a Grafana-managed rule through the API.

Source: https://grafana.com/docs/grafana/latest/alerting/configure-notifications/inhibition-rules/[Grafana: Inhibition rules].

== Choosing between them

* *One-off, known, short:* a silence, scoped to `application` or to a single rule UID, with a comment and an end time.
* *Recurring and predictable:* a mute timing on a child policy; use an active time interval when the rule should reach people
  only at certain hours (for example warnings only in business hours) and the opposite when it is the maintenance window.
* *Cause and consequence:* alert design first. Grouping by `alertname` and scoping rules so that one problem gives one
  notification (see xref:backend/monitoring-alerting/designing-actionable-alerts.adoc[Designing Actionable Alerts]) removes most redundant
  notifications; an inhibition rule is for what remains.
* *Maintenance of a data source or a pipeline:* if the symptom is missing data, silence the no-data rule rather than
  switching its no-data handling, which changes the rule for everyone and for good.

== What can go wrong

* *The silence matches nothing.* A mistyped label, or a regular expression anchored differently than expected, leaves
  *Affected alert instances* empty. Check the list before submitting.
* *The silence matches too much.* Broad matchers hide unrelated incidents during the window.
* *A forgotten silence.* There is no default maximum duration; review the *Silences* list and set an end time.
* *Expecting to delete a silence.* It can only be ended with *Unsilence*, and an expired silence disappears after 5 days.
* *A mute timing on the root policy.* It cannot be assigned there and is not inherited; attach it to a child policy.
* *Time zones.* A time range without a location is UTC, so a 02:00 window is not 02:00 local time.
* *An active interval and a mute timing together.* They overlap by design and the mute timing wins.
* *An inhibition rule that is too broad.* Without `equal`, one firing source alert inhibits every matching target
  anywhere, silently.
* *Using inhibition because a UI is missing.* It has no UI, the API is beta, and the documentation recommends silences
  and mute timings first.
* *Evaluation is not paused.* Suppressing notifications does not reduce evaluation load or state history.

== In the books

Salituro (Grafana 10) covers mute timings in its section on routing alerts with notification policies,
McCollam (Grafana 8) lists mute timings and silences next to contact points and policies, and Hernandez devotes a section to the differences between mute timings and silences with a comparison table; the core
distinction in those books (a recurring schedule attached to a policy against a one-off, label-matched window)
is still the one Grafana documents. Newer than the books: active time intervals as the inverse of mute timings, rule-specific
silences created from a rule, the 5-day retention of expired silences, limits on the number of silences, and the Grafana 13
inhibition rules API.

== Verify in the lab

. Fire the "high 5xx ratio" alert (failing-request mode of the load generator) and confirm the webhook receiver
  gets a notification.
. Create a silence with the matcher `application = bookshelf`, a 15-minute duration and a comment. Confirm that
  *Affected alert instances* lists the alert, that the alert stays *Firing* in the alert list, and that no new webhook arrives
  (repeat the failure after the repeat interval to see it).
. Click *Unsilence*, check that the silence is shown as expired and not deleted, and that notifications resume.
. Create a mute timing for the current hour (use your time zone as location), attach it to the `team = bookshelf-sre` child
  policy and repeat. Check that evaluation continues and that the root policy still notifies other alerts.
. Add an active time interval for a window that does not include now to the same child policy and confirm that
  the alert is suppressed until the window opens.
. Optional, on a Grafana 13 lab: create the `inhibitionrules` resource shown above through the App Platform API, fire
  both the `Bookshelf no data` source alert and a latency alert for the same `application`, and confirm that only the
  source notification arrives.
