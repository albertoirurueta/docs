An alert that fires and reaches nobody has failed. In Grafana Alerting the last hop of the pipeline, the one that
leaves Grafana, is a *contact point*: a named bundle of one or more *integrations*, each of which knows how to talk to
one destination (an e-mail server, a Slack channel, PagerDuty, a plain HTTP endpoint). Everything before that hop, such
as evaluation and routing, is covered in
xref:backend/monitoring-alerting/grafana/alerting-architecture.adoc[Alerting Architecture] and
xref:backend/monitoring-alerting/grafana/notification-policies.adoc[Notification Policies]; what the message looks like is
the subject of xref:backend/monitoring-alerting/grafana/notification-templates.adoc[Notification Templates]. This page is about
the destinations themselves, how to configure them, how to test them and how to keep them in code.

The channel-choice and on-call concepts that sit behind these settings are explained once, tool-neutrally, in
xref:backend/monitoring-alerting/notifications-and-incident-response.adoc[Notifications and Incident Response]; here the
focus is the Grafana implementation. The running example is the Bookshelf service (see
xref:backend/springboot/metrics-and-observability.adoc[Metrics and Observability]); in the
xref:backend/monitoring-alerting/hands-on-lab.adoc[Hands-on Lab] every contact point below can point at the lab's webhook
receiver, which prints exactly what Grafana sends.

== The contact point model

A contact point has a name and a list of integrations. The integrations are independent: one contact point can hold an
e-mail integration and a Slack integration, and every notification routed to that contact point is sent through each of
them. A contact point with no integrations is allowed, but no notification is sent through it, which is a quiet way to
lose alerts and worth checking for after a clean-up.

Each integration has its own settings (the mandatory ones depend on the type) and, in common, two kinds of options:

* *Optional settings*, such as the title, subject or message of the notification, which accept a
  xref:backend/monitoring-alerting/grafana/notification-templates.adoc[notification template]. Without them Grafana uses
  default templates.
* *Notification settings*, currently *Disable resolved message*, which stops the integration from sending the follow-up
  message when the alert resolves. Use it for destinations that open a ticket per message (every resolve would open another).

A contact point does nothing until something refers to it. There are two ways, and they are not exclusive:
select it in the notification options of a Grafana-managed alert rule, or add it to one or more notification policies.
Which of the two to prefer, and how severity and team labels choose the contact point, is covered in
xref:backend/monitoring-alerting/grafana/notification-policies.adoc[Notification Policies] and
xref:backend/monitoring-alerting/designing-actionable-alerts.adoc[Designing Actionable Alerts].

Source: https://grafana.com/docs/grafana/latest/alerting/fundamentals/notifications/contact-points/[Grafana: Contact points]
and https://grafana.com/docs/grafana/latest/alerting/configure-notifications/manage-contact-points/[Grafana: Configure contact points].

== Supported integrations

Grafana lists 23 integrations for the Grafana Alertmanager. The documentation does not mark any of them as preview, and
it points out that some are not supported by the Prometheus Alertmanager, so a contact point exported from Grafana is not
always importable into a plain Alertmanager.

[cols="1,3",options="header"]
|===
|Group |Integrations

|People and chat
|Email, Slack, Microsoft Teams, Telegram, Discord, Google Chat, Cisco Webex Teams, Line, DingDing, WeCom, Threema Gateway, Pushover

|On-call and incident
|PagerDuty, Opsgenie, VictorOps, Sensu Go, Grafana IRM

|Tickets and messaging
|Jira, Amazon SNS (listed as AWS SNS on the configuration page), Kafka REST Proxy, MQTT

|Generic
|Webhook, Alertmanager (forward to another Alertmanager)
|===

How to choose between them (reliability of the channel, acknowledgement, escalation, who is on call) belongs to the
concept page linked above. Two practical rules apply to Grafana in particular. A chat channel is a place to inform; a
paging tool is the place to wake someone, and the webhook integration is the escape hatch for everything else, including
the lab receiver. The administrator can restrict which types may be created with `allowed_integrations` in
`[unified_alerting]` (a comma-separated list; empty means all). Existing contact points of a disallowed type keep
delivering but cannot be edited.

Source: https://grafana.com/docs/grafana/latest/alerting/fundamentals/notifications/contact-points/[Grafana: Contact points]
(list), https://grafana.com/docs/grafana/latest/alerting/configure-notifications/manage-contact-points/#supported-contact-point-integrations[Grafana: Supported contact point integrations]
and https://grafana.com/docs/grafana/latest/setup-grafana/configure-grafana/[Grafana: Configure Grafana] (`allowed_integrations`).

== Create a contact point in the UI

. Open *Alerts & IRM*, then *Alerting*, then *Notification configuration*, and select the *Contact points* tab.
. Choose the Alertmanager in the *Choose Alertmanager* dropdown. *Grafana Alertmanager* is the default and the only one
  this section describes.
. Click *+ New contact point* and enter a name.
. Select an *Integration* type and fill in its mandatory fields.
. Optionally open *Optional settings* (title, subject, message, extra options of the type) and, under *Notification
  settings*, *Disable resolved message*.
. Save. To add another integration to the same contact point, edit it, click *Add contact point integration*, repeat the
  steps and save.

Source: https://grafana.com/docs/grafana/latest/alerting/configure-notifications/manage-contact-points/#add-a-contact-point[Grafana: Add a contact point].

=== Protected fields

Users with edit permission on a contact point can change most of its settings and add or remove integrations, but they
cannot change the *protected fields* of an existing integration: the settings that decide where notifications go, such
as target URLs and API endpoints. Changing them needs admin permission on the contact point, which is the RBAC action
`alert.notifications.receivers.protected:write`; it is granted by default to the fixed Alerting Admin role and to
contact point admins. The reason is security: an editor who could repoint a webhook could exfiltrate every alert label
and annotation. Permission handling in general is covered in
xref:backend/monitoring-alerting/grafana/users-teams-and-permissions.adoc[Users, Teams and Permissions].

Source: https://grafana.com/docs/grafana/latest/alerting/configure-notifications/manage-contact-points/[Grafana: Configure contact points] (Protected fields).

== Email and SMTP

The email integration has these settings.

[cols="2,5",options="header"]
|===
|Setting |Behaviour

|Addresses
|Recipient list. Addresses are case sensitive.

|Single email
|Send one e-mail to all addresses instead of one per address.

|Subject, Message
|Optional and templated. They replace the default subject and the main body section. The layout, HTML and CSS of the
e-mail cannot be changed through them.

|Disable resolved message
|No e-mail when the alert resolves.
|===

Grafana Cloud sends e-mail without any setup. On a self-managed Grafana (OSS or Enterprise) SMTP must be configured
first, in the `[smtp]` section of `grafana.ini` or `custom.ini`, and Grafana restarted. The settings that matter are these.

[cols="2,2,5",options="header"]
|===
|Key |Default |Meaning

|`enabled`
|`false`
|Allow Grafana to send e-mail at all.

|`host`
|`localhost:25`
|SMTP server and port; use port 465 for implicit TLS.

|`user`, `password`
|empty
|SMTP authentication. A password containing `#` or `;` must be wrapped in triple quotes.

|`from_address`, `from_name`
|`admin@grafana.localhost`, `Grafana`
|Sender of the alert e-mails. Set a real address, or the receiving server may reject the message.

|`startTLS_policy`
|empty
|`OpportunisticStartTLS`, `MandatoryStartTLS`, `NoStartTLS` or empty.

|`skip_verify`
|`false`
|Skip verification of the server certificate. Avoid it outside a lab.
|===

In a container the same keys are set with environment variables of the form `GF_SMTP_ENABLED`, `GF_SMTP_HOST` and so on.

[source,yaml]
----
# docker-compose.yml excerpt: Grafana with SMTP enabled
services:
  grafana:
    image: grafana/grafana-enterprise:13.3.0
    environment:
      GF_SMTP_ENABLED: "true"
      GF_SMTP_HOST: "smtp.example.com:587"
      GF_SMTP_USER: "alerts@example.com"
      GF_SMTP_PASSWORD__FILE: /run/secrets/smtp_password
      GF_SMTP_FROM_ADDRESS: "alerts@example.com"
      GF_SMTP_FROM_NAME: "Bookshelf alerts"
      GF_SMTP_STARTTLS_POLICY: "MandatoryStartTLS"
    secrets:
      - smtp_password
secrets:
  smtp_password:
    file: ./secrets/smtp_password.txt
----

Reference: https://grafana.com/docs/grafana/latest/setup-grafana/configure-grafana/[Grafana: Configure Grafana] (`[smtp]`,
and the `+__FILE+` suffix described on
xref:backend/monitoring-alerting/grafana/installation-and-configuration.adoc[Installation and Configuration]).

Two more settings affect e-mail contact points. `limit_email_to_org_members` in `[unified_alerting]` (default `false`)
restricts recipients to members of the organization; it is checked only when a contact point is created or updated, not
when a notification is sent. SMTP can also add trace headers to outgoing mail with `enable_tracing`, which needs a
`+tracing.opentelemetry.*+` section. The default e-mail template can be edited fully in OSS and Enterprise, but that goes
through an internal API that may change without notice and is not officially supported.

Source: https://grafana.com/docs/grafana/latest/alerting/configure-notifications/manage-contact-points/integrations/configure-email/#email-settings[Grafana: Email integration].

== Chat and paging integrations

The settings below are the ones the official pages document for the integrations most teams start with. Each page also
describes the Test button, which is available for the Grafana Alertmanager only.

=== Slack

There are two ways to connect. A *bot token* (a Bot User OAuth Token starting with `xoxb-`) plus a channel ID gives
finer permissions and suits workspaces where channels are created often; the Slack app needs the `chat:write.public`
scope. An *incoming webhook URL* (starting with `https://hooks.slack.com/services/`) is simpler, but is bound to one
channel chosen when the webhook was created. Either way a contact point supports one Slack channel only, so a second
channel needs a second integration.

Optional settings are `username`, `icon_emoji` (which wins over `icon_url`), `mentionUsers`, `mentionGroups` (comma
separated IDs), `mentionChannel` (`here`, `channel` or empty), `title`, `text`, `color` and `endpointUrl`. Title and text can use
notification templates; custom Slack blocks are not supported, so the layout cannot be changed.

Source: https://grafana.com/docs/grafana/latest/alerting/configure-notifications/manage-contact-points/integrations/configure-slack/#optional-settings[Grafana: Slack integration].

=== Microsoft Teams

Teams is configured through a *Teams workflow*, not an Office 365 connector. In Teams create a workflow from the
template "Post to a channel when a webhook request is received", copy the URL it shows at the end of the wizard and
paste it into the *URL* field of the Microsoft Teams integration. For a private channel the workflow must be edited so
that the adaptive card is posted as a user. Only the `title` and `message` can be templated, because the message is an
adaptive card. When Grafana reports success but nothing appears in the channel, the run history of the workflow is the
place to look, since the failure is on the Teams side.

Source: https://grafana.com/docs/grafana/latest/alerting/configure-notifications/manage-contact-points/integrations/configure-teams/[Grafana: Microsoft Teams integration].

=== PagerDuty

Create a PagerDuty service (choose "Create a service without an integration" in the wizard), add an *Events API V2*
integration to it and paste its key into the *Integration Key* field. A test notification opens a test incident that
shows in the service's Activity tab. Because PagerDuty correlates events, the resolved message matters for this
integration: leave *Disable resolved message* off so incidents close themselves when the alert resolves.

Source: https://grafana.com/docs/grafana/latest/alerting/configure-notifications/manage-contact-points/integrations/pager-duty/[Grafana: PagerDuty integration].

=== Grafana IRM

The Grafana IRM integration documented for Grafana OSS and Enterprise is a webhook contact point that posts to an IRM
integration. In IRM create an integration of type *Alertmanager* (templates preconfigured for Grafana and Prometheus
alerts) or *Webhook*, copy its *HTTP Endpoint* and use it as the URL of a Grafana webhook contact point. IRM itself is
a Grafana Cloud product; Grafana Cloud's own Alerting uses a separate setup described in the Cloud documentation. The
optional heartbeat turns the pipeline around: an always-firing rule (for example the query `vector(1) > 0`) with a pending period, group
wait, group interval and repeat interval all shorter than the IRM heartbeat interval keeps a second webhook contact point sending
heartbeats, and IRM raises an alert group when they stop. That is a cheap end-to-end check of the whole alerting path
and complements the meta-monitoring in
xref:backend/monitoring-alerting/grafana/monitoring-alerts-and-state-history.adoc[Monitoring Alerts and State History]. Incident handling in IRM is covered in
xref:backend/monitoring-alerting/grafana/slo-and-irm.adoc[SLOs and IRM].

Source: https://grafana.com/docs/grafana/latest/alerting/configure-notifications/manage-contact-points/integrations/configure-irm/[Grafana: Grafana IRM integration].

== The webhook integration

The webhook integration is the generic one: Grafana sends an HTTP request with a JSON body to a URL. It is how the lab
receiver sees alerts, and how Grafana alerts reach automation that has no dedicated integration.

[cols="2,5",options="header"]
|===
|Setting |Behaviour

|URL
|The endpoint. It is stored in plain text and not masked when read back, so credentials must go in the authentication
fields, never in the URL. It is a protected field.

|HTTP Method
|`POST` or `PUT`.

|Basic authentication, Authorization header scheme and credentials
|Use one or the other, not both. The scheme defaults to `Bearer`.

|Extra headers
|Additional headers; the default `Content-Type: application/json` can be overridden.

|Max alerts
|Maximum alerts per notification; extra alerts are ignored. `0` means no limit.

|TLS
|CA certificate, client certificate and client key.

|HMAC signature
|Shared secret; header defaults to `X-Grafana-Alerting-Signature`; an optional timestamp header is included in the signature to limit replay.

|OAuth2
|Client credentials: token URL, client ID and secret, scopes, endpoint parameters, TLS and proxy for the token request only. It takes precedence over basic auth and the Authorization header.

|Title, Message
|Sent as the `title` and `message` fields; both accept notification templates.

|Custom payload
|A template that replaces the whole default payload; see xref:backend/monitoring-alerting/grafana/notification-templates.adoc[Notification Templates]. Title and Message are ignored when it is used. It is not generally available in Grafana Cloud.
|===

The HMAC signature is HMAC-SHA256, sent as a hex string, over `pass:c[timestamp + ":" + body]` (or just the body when no
timestamp header is configured). A receiver validates it by recomputing the digest over the raw body with the shared
secret, comparing it with the header and rejecting stale timestamps. Validate the raw bytes, not a re-serialised JSON
object.

Source: https://grafana.com/docs/grafana/latest/alerting/configure-notifications/manage-contact-points/integrations/webhook-notifier/#webhook-settings[Grafana: Webhook settings],
https://grafana.com/docs/grafana/latest/alerting/configure-notifications/manage-contact-points/integrations/webhook-notifier/#hmac-signature[HMAC signature]
and https://grafana.com/docs/grafana/latest/alerting/configure-notifications/manage-contact-points/integrations/webhook-notifier/#oauth2-authentication[OAuth2 authentication].

`silenceURL` and `dashboardURL` for the human, `truncatedAlerts` to detect that `Max alerts` cut the list, and `state`
(`alerting` or `ok`). The alert objects may additionally carry `imageURL` when screenshots are configured (see
xref:backend/monitoring-alerting/grafana/notification-templates.adoc[Notification Templates]).

== Testing a contact point

Edit the contact point and click *Test*. Choose a predefined test notification, or *custom* to type your own labels and
annotations, and click *Send test notification*. Testing is available only for the Grafana Alertmanager. A test
proves the transport: DNS, credentials, TLS, a Teams workflow or a Slack scope. It does not prove routing, because it
bypasses the notification policy tree, and it does not prove that real alerts render well, because the labels are the
ones you typed. Treat it as the first of two checks and finish with a real alert in the lab (see the last section).

Source: https://grafana.com/docs/grafana/latest/alerting/configure-notifications/manage-contact-points/#test-a-contact-point[Grafana: Test a contact point].

== Delivery status and troubleshooting

The *Contact points* tab shows the status of each contact point's latest delivery attempts, which is the first place to
see a failing integration. For past attempts, *View notification history* can be filtered by contact point and outcome;
the history needs extra configuration on a self-managed Grafana and is described in
xref:backend/monitoring-alerting/grafana/monitoring-alerts-and-state-history.adoc[Monitoring Alerts and State History]. For Grafana
Cloud, notifications from the Grafana Alertmanager originate from the `grafana` service egress IP addresses, not from the
Hosted Alerts addresses, which matters when the destination has an allowlist.

Source: https://grafana.com/docs/grafana/latest/alerting/configure-notifications/manage-contact-points/[Grafana: Troubleshoot notification delivery].

== Contact points as code

Contact points can be provisioned from files (self-managed Grafana only, not available in Grafana Cloud), with
Terraform, or through the alerting provisioning HTTP API. A resource provisioned this way cannot be edited in the Grafana
UI, only at the source where it was created. The overview of all methods, export and the API is in
xref:backend/monitoring-alerting/grafana/provisioning-alerting-resources.adoc[Provisioning Alerting Resources].

A file placed in `provisioning/alerting` of the Grafana container (then restart, or reload with the Admin API) that
creates a plain version of the lab's webhook contact point (the lab's own file also sets `title` and `message` from the template group) and an
e-mail contact point looks like this; the lab has no SMTP server, so the e-mail contact point cannot deliver there.

[source,yaml]
----
apiVersion: 1

contactPoints:
  - orgId: 1
    name: bookshelf-webhook
    receivers:
      - uid: bookshelf-webhook
        type: webhook
        disableResolveMessage: false
        settings:
          url: http://webhook-receiver:8080/grafana
          httpMethod: POST
          maxAlerts: '0'
  - orgId: 1
    name: bookshelf-email
    receivers:
      - uid: bookshelf-email
        type: email
        settings:
          addresses: oncall@example.com;sre@example.com
          singleEmail: true
          subject: |
            {{ template "default.title" . }}
----

Reference: https://grafana.com/docs/grafana/latest/alerting/set-up/provision-alerting-resources/file-provisioning/#import-contact-points[Grafana: Import contact points].

Provisioning replaces `+$name+` with environment variables, so a literal `$` inside a template must be written `+$$+`.
Secrets such as webhook passwords or integration keys belong in environment variables referenced this way, not in the file.

The same contact point with Terraform (`grafana/grafana` provider, resource `grafana_contact_point`):

[source,hcl]
----
resource "grafana_contact_point" "bookshelf_webhook" {
  name = "bookshelf-webhook"

  webhook {
    url                     = "http://webhook-receiver:8080/grafana"
    http_method             = "POST"
    disable_resolve_message = false
  }
}
----

Reference: https://github.com/grafana/terraform-provider-grafana/blob/main/docs/resources/contact_point.md[Terraform provider: grafana_contact_point].

A contact point can also be exported from the *Contact points* tab, one or all of them, as JSON, YAML or Terraform, which
is the quickest way to turn a hand-built contact point into code.

Source: https://grafana.com/docs/grafana/latest/alerting/set-up/provision-alerting-resources/[Grafana: Provision alerting resources].

== What can go wrong

* *The contact point is never selected.* A contact point that no rule and no policy refers to never sends anything; the
  default policy's contact point receives everything that matches no other route.
* *An integration-less or half-configured contact point.* It saves without error and sends nothing.
* *SMTP not configured.* On a self-managed Grafana the e-mail test fails until `[smtp] enabled = true` and a reachable
  `host` are set and Grafana is restarted.
* *The test succeeds but real alerts are missed.* Tests bypass routing; check the policy tree and the labels of the real alert.
* *A secret in the URL.* The webhook URL is stored and shown in plain text; use the authentication fields.
* *Basic auth and an Authorization header together.* Only one of the two may be used; OAuth2 overrides both.
* *Resolved messages create noise or tickets.* Decide per integration whether *Disable resolved message* is wanted;
  paging tools usually need the resolve, ticket-per-message tools usually do not.
* *The destination rejects the payload.* Large groups are truncated only if `Max alerts` is set; set it for receivers with a size limit and read `truncatedAlerts`.
* *Teams or Slack reports success but nothing shows.* Check the Teams workflow run history, the Slack channel ID and the app scopes.
* *Someone with edit rights cannot change a URL.* This is the protected-field rule, not a bug.

== In the books

Salituro (Grafana 10) walks through an e-mail, a Slack and a PagerDuty contact point, including the SMTP settings set
as `+GF_SMTP_*+` environment variables in Docker Compose, and McCollam (Grafana 8) notes that a contact point can hold
several target systems and that a test button should be used before relying on it. Hernandez adds the contact point types
for IoT alerting. All three predate the current UI: the integration list has grown (Grafana IRM, Jira, Kafka REST Proxy,
MQTT, Amazon SNS), Microsoft Teams now uses workflows, protected fields and the webhook HMAC and OAuth2 options exist, and
contact points can be provisioned and exported as code. The ideas, though, carry over unchanged.

== Verify in the lab

. Start the lab with `docker compose --profile grafana up -d` and open Grafana. Create the contact point
  `bookshelf-webhook` (or provision it with the YAML above) with the receiver's URL.
. Click *Test*, send the predefined notification and confirm that the receiver printed a JSON body with `status`
  `firing`, `receiver` `bookshelf-webhook` and the test labels.
. Select the contact point in the notification options of the "high 5xx ratio" rule (or add it to a policy matching
  `team=bookshelf-sre`), start the load generator in failing-request mode and wait for the alert to fire.
. In the receiver output find `alerts[0].labels.application` (`bookshelf`), `fingerprint`, `dashboardURL` (it should
  open the "Bookshelf service health" dashboard) and `silenceURL`.
. Stop the failing mode and confirm a second request with `status` `resolved`. Then enable *Disable resolved message*,
  repeat the cycle and confirm that no resolved request arrives.
. Set *Max alerts* to `1`, fire two alerts in one group and confirm that `truncatedAlerts` is `1`.
. Optional: stop the receiver, fire an alert and read the delivery status on the *Contact points* tab.
