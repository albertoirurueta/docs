Checked on 2026-11-09 against Grafana 13.3.x.

A dashboard that everybody can edit is a dashboard that nobody trusts, and an alert rule that anybody can silence is an alert that
will eventually not fire. Access control is therefore part of monitoring design, not an administrative afterthought. Grafana
answers four questions with four building blocks: who may sign in (users and the organizations they belong to), what they
can do everywhere in an organization (basic roles), what they can do with a particular set of dashboards and alert rules
(teams, folders and permissions), and how automation authenticates (service accounts). Enterprise and Cloud add finer
control with RBAC and data source permissions. This page builds the model step by step and ends with API calls that set it
up for the Bookshelf lab. Where the permissions touch alerting, the details are on
xref:backend/monitoring-alerting/grafana/alerting-high-availability-and-operations.adoc[Alerting HA and Operations] and
xref:backend/monitoring-alerting/grafana/provisioning-alerting-resources.adoc[Provisioning Alerting Resources].

== The three permission sets

Grafana distinguishes three sets of permissions, from the widest to the narrowest:

. **Server administrator permissions** (Grafana Admin): server-wide settings, access to organizations, users and licences.
  A default server administrator exists. This role is distinct from the organization administrator and does not exist in Grafana Cloud.
. **Organization permissions**: access to dashboards, alerts, plugins, teams, playlists, data sources, annotations,
  library panels and service accounts for a whole organization, through the roles Admin, Editor and Viewer.
. **Dashboard and folder permissions**: access to individual dashboards and folders, which can extend a viewer's rights or
  restrict an editor's on specific items.

Source: https://grafana.com/docs/grafana/latest/administration/roles-and-permissions/[Roles and permissions].

== Organizations

An organization is the isolation boundary inside one Grafana server. Dashboards, data sources, folders, annotations, teams,
alerts, notification channels, reports and service accounts belong to exactly one organization, while configuration settings,
authentication providers and Enterprise licences are shared by the whole server. A user can belong to several organizations,
but a member of one organization cannot see the dashboards of another. This makes several organizations easier and cheaper to
run than several Grafana servers when you must separate tenants, but it also means the same data source must be defined once per
organization.

Only a Server Administrator can create an organization (*Administration > General > Organizations*, then *New org*); the creator
becomes its organization administrator. Deleting an organization permanently removes its teams and dashboards. For most
teams that run a single product, one organization with good folder permissions is simpler than several organizations. Organization 1
is addressed as namespace `default` in the `/apis` URLs, the others as `org-<ORG_ID>`
(xref:backend/monitoring-alerting/grafana/architecture-and-ecosystem.adoc[Architecture and Ecosystem]).

Source: https://grafana.com/docs/grafana/latest/administration/organization-management/[Manage organizations].

== Users

A user is anyone who can sign in. Server Administrators manage users under *Administration > Users and access > Users*: *New user*
creates one (you choose the password, the user is not e-mailed, and the user gets Viewer permissions in a default organization,
which you can change), the account page can disable a user (the account is kept and can be re-enabled) or delete
it (permanent, from the whole server), and its *Sessions* section forces a logout of one session or of all devices. The
Grafana Admin flag is visible in the user's *Permissions* section.

Organization administrators manage the members of their own organization from *Administration > Users and access > Users*, then
*Organization users*: *Invite* by e-mail address or username with a role, review or cancel *Pending Invites*, change the
*Role* of a user, or remove a user from the organization with the red X, which does not delete the user from the server. When
roles come from an authentication provider, they are synced at every sign-in, so a manual change may be overwritten unless the
`skip_org_role_sync` setting is configured. Single sign-on (LDAP, OAuth, SAML) is configured in the server settings, see
https://grafana.com/docs/grafana/latest/setup-grafana/configure-access/configure-authentication/[Configure authentication]; Salituro's book
has a full chapter on LDAP and OAuth 2.

Source: https://grafana.com/docs/grafana/latest/administration/user-management/server-user-management/[Server user management] and
https://grafana.com/docs/grafana/latest/administration/user-management/manage-org-users/[Manage users in an organization].

| Yes

| Yes

*No basic role* has no permissions by default; permissions can be added with RBAC (Enterprise and Cloud), or by folder
permissions. For alerting, the OSS guidance is that Admin and Editor have write access to alert rules and notification
resources (only Admin assigns roles), Viewer has read access, and None has no access until folder or contact point
permissions are granted. Basic roles apply to the whole organization unless a dashboard or folder permission narrows or
extends them. On Grafana Cloud, Grafana Support is not authorised to make organization role changes, so ask your organization
administrator.

Source: https://grafana.com/docs/grafana/latest/administration/roles-and-permissions/[Roles and permissions] and
https://grafana.com/docs/grafana/latest/alerting/set-up/configure-roles/[Configure roles and permissions for alerting] (OSS).

== Teams

A team is a group of users inside an organization that shares access needs. Granting a permission to a team grants it to all
members, on dashboards, folders, data sources (Enterprise/Cloud), alerts, reports, annotations and playlists. A user can be a
member of several teams. Two rules explain most surprises:

* Everyone in a team gets the same permissions on a shared resource, so one team cannot give some members Edit and others View on the same folder.
* When a user belongs to several teams with different access to the same resource, the *most permissive* wins: Viewer from one
  team and Editor from another gives Editor.

A team has *members* (no team administration) and *administrators* (add members, change the team name, members' team roles,
preferences and home dashboard). Organization administrators manage all teams. Teams can be *isolated* (see only their own
resources) or *collaborative* (access other teams' resources).

A change in 12.0 matters for older advice: the `editors_can_admin` setting was removed, so editors can no longer create and manage
teams (they keep the teams they already created). Organization administrators manage all teams. Teams are also what Enterprise team sync fills from an authentication provider.

Source: https://grafana.com/docs/grafana/latest/administration/team-management/[Team management],
https://grafana.com/docs/grafana/latest/whatsnew/whats-new-in-v12/whats-new-in-v12-0/[What's new in 12.0] and
https://grafana.com/docs/grafana/latest/introduction/grafana-enterprise/[Grafana Enterprise] (team sync).

== Folder and dashboard permissions

Folders are the main tool for access control. A permission on a folder applies to its dashboards, its alert rules, its SLOs and
other resources, and to its subfolders. Three levels exist, each including the one below:

* **View**: see the folder and its contents, including dashboards, alert rules, silences, annotations and library panels.
* **Edit**: create subfolders, modify or delete the folder, and create or edit dashboards, alert rules, silences and library panels.
* **Admin**: manage folder and dashboard permissions.

Permissions can be given to a user, a team, a service account or a basic role. Important details from the documentation:

* *Inheritance flows downward.* You can add permissions on a subfolder, but you cannot give a user less access there than on
  the parent, and a dashboard-level permission cannot be lower than what its folder already grants (Grafana returns an
  error). Grafana applies the highest permission a user holds on a resource, and organization administrators keep full access.
* Folders can nest up to 4 levels, and folder names cannot contain `_` or `%`.
* The creator of a top-level folder or dashboard automatically gets Admin on it (not for items inside a folder).
* Folders created in the UI start with Admin for the Admin role, Edit for Editor and View for Viewer. Folders created as code
  (Terraform, API, provisioning) get only the permissions you define, plus Admin for the Admin role, so a provisioned folder
  can be invisible to Viewers until you grant View.
* Removing a permission on a folder removes access to everything inside it.

To set them in the UI, open *Dashboards*, the folder's menu and *Manage permissions*, then *Add a permission* and choose the user,
team, service account or role and the level. For a single dashboard use *Dashboard settings > Permissions*.

Source: https://grafana.com/docs/grafana/latest/administration/roles-and-permissions/folder-access-control/[Folder access control] and
https://grafana.com/docs/grafana/latest/administration/user-management/manage-dashboard-permissions/[Manage dashboard permissions].

Folder permissions are how Grafana decides who may view and edit alert rules: View and Edit access to alert rules, and their
rule-specific silences, follow the folder. Folder permissions cannot customise access to notification resources;
contact points have their own View, Edit and Admin permissions (OSS), and notification policies are covered by the basic roles
or RBAC. The consequence for design is to give each service its own folder for dashboards *and* alert rules, so that the owning team
edits both and everybody else only views.

== RBAC and data source permissions (Enterprise and Cloud)

Role-based access control extends the basic roles. It is available in Grafana Enterprise and Grafana Cloud; OSS has only basic
roles. It adds:

* **Fixed roles**: predefined, not changeable, assignable to users, teams and service accounts, covering alerting, dashboards,
  data sources, users and more.
* **Custom roles**: your own combinations of actions and scopes, recommended only when fixed roles do not fit. A permission pairs an
  *action* (what is allowed) with a *scope* (where), for example the action `teams.roles:read` with the scope `teams:id:1`.
* **Basic role changes**: basic role permissions can be changed (but the roles cannot be deleted), by provisioning, and an
  organization role *No Basic Role* plus fixed or custom roles is the pattern for least privilege.
* **Data source permissions**: by default anyone in the organization can query any data source; Enterprise and Cloud
  restrict query, edit and admin access by user, service account, team or basic role. This matters when production and
  staging data sources live in one organization.

Two 13.x changes affect upgrades: Grafana 13.0 enforces custom roles, Terraform-managed roles and role provisioning more
strictly (review roles that use data source permissions scoped by UID), and 13.3 lets role managers revoke access they do not
themselves hold (Enterprise). Role assignment has its own documentation page, linked below.

Source: https://grafana.com/docs/grafana/latest/administration/roles-and-permissions/access-control/[About RBAC],
https://grafana.com/docs/grafana/latest/administration/roles-and-permissions/access-control/manage-rbac-roles/[Manage RBAC roles],
https://grafana.com/docs/grafana/latest/administration/data-source-management/[Data source management],
https://grafana.com/docs/grafana/latest/whatsnew/whats-new-in-v13/whats-new-in-v13-0/#breaking-changes-and-removals[What's new in 13.0] and
https://grafana.com/docs/grafana/latest/whatsnew/whats-new-in-v13/whats-new-in-v13-3/[What's new in 13.3].

== Service accounts instead of API keys

Automation (Terraform, CI, a script that provisions dashboards) must not use a person's login. API keys, which older material
and books use, were replaced by *service accounts*: non-user identities for work through the HTTP API. They are not Grafana users.

* A service account has an organization role (including `None`, with permissions granted by RBAC) and, on Enterprise,
  RBAC roles. Creating one needs the Admin role, or the fixed roles `fixed:roles:reader` and `fixed:serviceaccounts:creator`.
* It authenticates with *tokens*: random strings that inherit the account's permissions. Tokens do not expire by default;
  set an expiry when creating one, or cap lifetimes server-wide with `token_expiration_day_limit`. Use one token per application so you can
  rotate or revoke it separately. A token's value is returned only by the create call.
* A service account stays active until deleted or disabled and is not tied to a person, so the pipeline keeps working when an
  employee leaves. It exists in one organization only and cannot do instance-wide operations (those need a Server Administrator).
* Users and teams can be given Edit or Admin permission on a service account, which controls who may manage its tokens.

In the UI: *Administration > Users and access > Service accounts*, *Add service account*, name and role, *Create*, then
*Add service account token*, optional expiry, *Generate token*. Migrating existing API keys is covered by the
https://grafana.com/docs/grafana/latest/administration/service-accounts/migrate-api-keys/[migration guide].

Source: https://grafana.com/docs/grafana/latest/administration/service-accounts/[Service accounts].

== As code: the Bookshelf access model

Design: one folder `bookshelf` holds the dashboard and the five alert rules; the team `bookshelf-sre` edits it; every
other Viewer can read it; a service account `ci-provisioner` with the Editor role is what the pipeline uses. The calls below set
that up against the lab (`GF_PASSWORD` is the admin password of the lab; the Bookshelf names are examples).
The lab's provisioning files already create a folder titled `bookshelf` with a generated uid, so to create the folder with the uid `bookshelf` as below,
use a Grafana without the lab's alerting file, or use the generated uid in the permission calls.

[source,bash]
----
GF=http://localhost:3000

# 1. a folder, through the resource API (namespace "default" is organization 1)
curl -s -X POST "$GF/apis/folder.grafana.app/v1/namespaces/default/folders" \
  -H "Content-Type: application/json" -u "admin:$GF_PASSWORD" \
  -d '{"metadata":{"name":"bookshelf"},"spec":{"title":"Bookshelf"}}'

# 2. a team
curl -s -X POST "$GF/api/teams" \
  -H "Content-Type: application/json" -u "admin:$GF_PASSWORD" \
  -d '{"name":"bookshelf-sre","email":"sre@example.com"}'

# 3. a service account and a token that expires in 7 days
curl -s -X POST "$GF/api/serviceaccounts" \
  -H "Content-Type: application/json" -u "admin:$GF_PASSWORD" \
  -d '{"name":"ci-provisioner","role":"Editor","isDisabled":false}'
curl -s -X POST "$GF/api/serviceaccounts/2/tokens" \
  -H "Content-Type: application/json" -u "admin:$GF_PASSWORD" \
  -d '{"name":"ci-token","secondsToLive":604800}'

# 4. folder permissions: Viewers view, team 1 edits (1 = View, 2 = Edit, 4 = Admin)
curl -s -X POST "$GF/api/folders/bookshelf/permissions" \
  -H "Content-Type: application/json" -u "admin:$GF_PASSWORD" \
  -d '{"items":[{"role":"Viewer","permission":1},{"role":"Editor","permission":2},{"teamId":1,"permission":2}]}'
----

Reference: https://grafana.com/docs/grafana/latest/developer-resources/api-reference/http-api/folder/[Folder API],
https://grafana.com/docs/grafana/latest/developer-resources/api-reference/http-api/api-legacy/team/[Team API],
https://grafana.com/docs/grafana/latest/developer-resources/api-reference/http-api/api-legacy/serviceaccount/[Service account API] and
https://grafana.com/docs/grafana/latest/developer-resources/api-reference/http-api/api-legacy/folder_permissions/[Folder permissions API]. The
`/api` paths are deprecated in Grafana 13 in favour of `/apis` but stay operative and are no longer updated. Adjust the
service account id (the `2`) to the `id` returned by the create call, and the team id to the one returned by the team call.

Notes on this snippet: the folder permissions call *replaces* the whole list and removes existing permissions that are not in it, so always send
every permission you want to keep. The service account token appears in the `key` field of the response of the token call, and only there; store it in
a secret manager. For real environments prefer Terraform or provisioning for these objects
(xref:backend/monitoring-alerting/grafana/observability-as-code.adoc[Dashboards as Code]); the Terraform provider has resources
for folders, teams and service accounts, see the
xref:backend/terraform/index.adoc[Terraform section] for the basics.

== What can go wrong

* **Everyone is Editor.** The default for convenience; Editors can change any dashboard and alert rule in the organization.
  Keep Viewer as the default role, and give editing through team permissions on folders.
* **No folder per service.** Access to alert rules follows the folder, so a shared "General" folder means shared control over alerts.
* **Admin tokens in CI.** A pipeline that uses a personal login or an Admin service account can do far more than it needs. Use an Editor
  or a custom-role service account and a short expiry.
* **Token never rotated.** Tokens do not expire by default; set `secondsToLive` or the server-wide limit.
* **Replaced permissions.** The legacy folder permissions call wipes unlisted entries.
* **Cloud versus self-managed.** There is no server administrator on Cloud, and Support cannot change organization roles.
* **Old advice.** `editors_can_admin`, API keys and "fine-grained access control" belong to older versions.
* **Role sync overwrites.** When roles are synced from an identity provider, a manual role change can be undone at the next sign-in.

== Verify it in the lab

. As `admin`, run the snippet above (set `GF_PASSWORD`). Each call should return a JSON object; the team and service account calls
  return an `id`.
. Create a user *viewer1* with *Administration > Users and access > Users > New user* and keep the Viewer role. Sign in as that user in a
  private window: the "Bookshelf" folder and its dashboards are visible, and the *Save* button is missing.
. Add that user to the team (`POST /api/teams/1/members` with `+{"userId": <id>}+`) and set the team to Edit on the folder with
  *Manage permissions*. Sign in again: the dashboards can now be edited (for a Viewer-role user the folder permission, not the organization role, grants Edit).
. Use the token: `curl -H "Authorization: Bearer <token>" http://localhost:3000/api/access-control/user/permissions` lists what the
  service account may do; try a call that needs more (for example creating a data source) and expect a 403.
. Remove the *Viewer* line from the folder permissions and confirm that a plain Viewer user no longer sees the folder.

Reference: the `/api/access-control/user/permissions` call is the one shown on https://grafana.com/docs/grafana/latest/administration/service-accounts/[Service accounts].

== In the books

McCollam (*Getting Started with Grafana*, chapter 5 "User Administration", Grafana 8.2/8.3) and Salituro (*Learn Grafana 10.x*,
chapter 15 "Managing Permissions for Users, Teams, and Organizations" and chapter 14 on folders, Grafana 10) are good for the
concepts: organizations, roles, teams, invite-only versus self-service sign-up, setting organization roles, folder
and dashboard permissions, and the rule of thumb to plan permissions around folders and teams. They predate several
changes: the instructions that create *API keys* are replaced by service accounts; "fine-grained access control" is now RBAC
(Enterprise and Cloud); `editors_can_admin` was removed in 12.0; the *No basic role* option exists
since 10.2; folders now nest and are stored in unified storage; and alert rules are governed by the same folder permissions.
The publisher pages are in the xref:backend/monitoring-alerting/index.adoc#_bibliography[bibliography].
