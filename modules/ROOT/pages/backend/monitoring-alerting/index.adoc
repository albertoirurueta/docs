Monitoring and alerting answer two practical questions about a running service: _is it healthy right now?_ and _who must act
when it is not?_ This section teaches the whole path from a piece of telemetry to a notified human, using the two tools that
most teams meet first: *Grafana*, a visualization and alerting layer that queries many data sources where they live, and
*Kibana*, the user interface of the Elastic Stack, which works over data stored in Elasticsearch. Every concept is taught
twice, once with each tool, on the same running example, so that you can use one tool well, choose between them, or run both.

== Monitoring and observability

*Monitoring* is watching known signals against known expectations: a dashboard of request rate, errors and latency, and an
alert when the error share crosses a threshold. *Observability* is the property of a system that lets you ask new questions of
it after the fact, because it emits enough detailed telemetry (metrics, logs, traces and, increasingly, profiles) to explain
behaviour nobody predicted. The two are not rivals. Monitoring is the part you automate (dashboards that load by themselves and
alerts that page someone), and observability is the data quality that makes monitoring possible and investigation fast.
xref:backend/monitoring-alerting/observability-fundamentals.adoc[Observability Fundamentals] defines the signals, series identity
and cardinality, and shows how a metric, a trace and a log line are correlated.

The consequences for design are concrete. Choose signals deliberately, because each has a cost.
Keep label values bounded, because every new combination is a new series. Alert on symptoms users feel, and keep causes on
dashboards. Treat dashboards and alert rules as code, because configuration that lives only in a web UI cannot be reviewed,
tested or restored. The shared pages of this section cover each of these ideas before the tool-specific subsections apply them.

Source: https://grafana.com/docs/grafana/latest/fundamentals/[Grafana fundamentals],
https://www.elastic.co/docs/solutions/observability[Elastic Observability] and
https://opentelemetry.io/docs/concepts/signals/[OpenTelemetry signals].

== How Grafana and Kibana fit

The two tools sit at different places in the pipeline, and understanding that placement explains most of their differences.

* *Grafana* is a visualization, exploration and alerting layer. It stores almost no telemetry: metrics stay in Prometheus or
  Mimir, logs in Loki or Elasticsearch, traces in Tempo, business data in a SQL database. Grafana holds its own configuration
  (dashboards, folders, users, alert rules) and sends each query to the data source that owns the data.
  See xref:backend/monitoring-alerting/grafana/architecture-and-ecosystem.adoc[Grafana: Architecture & Ecosystem].
* *Kibana* is the user interface of the Elastic Stack. Elasticsearch stores and indexes the data (logs, metrics and traces in
  data streams), the EDOT Collector or Elastic Agent collects it, and Kibana queries, visualizes and alerts on it, adding
  Observability solutions (APM, Synthetics, SLOs, infrastructure views) on top.
  See xref:backend/monitoring-alerting/kibana/architecture-and-elastic-stack.adoc[Kibana: Architecture & the Elastic Stack].

Both tools evolve towards each other: Grafana can read Elasticsearch, and Kibana 9.5 added native PromQL over time series data
streams. xref:backend/monitoring-alerting/grafana-vs-kibana.adoc[Grafana vs Kibana] compares them feature by feature, including
the alerting models, and tells you when to choose one, the other or both.

== The running example and the lab

Every page uses *Bookshelf*, the Spring Boot 4.1 book-catalogue service already used by
xref:backend/springboot/metrics-and-observability.adoc[Spring Boot metrics and observability] and
xref:backend/springboot/logging.adoc[Spring Boot logging]. It exposes Micrometer metrics, OpenTelemetry traces and JSON logs, and
uses PostgreSQL. The xref:backend/monitoring-alerting/hands-on-lab.adoc[Hands-on Lab] is a Docker Compose project with two profiles:

* `grafana`: Bookshelf, a load generator, a webhook receiver, Grafana Alloy, Prometheus, Loki, Tempo and Grafana 13.3.
  It needs about 1 GB of memory.
* `kibana`: Bookshelf, the same load generator and webhook receiver, the EDOT Collector, Elasticsearch 9.5.6 and Kibana 9.5.6.
  It needs about 4 GB of memory.

Bookshelf runs in the lab as a small stand-in service that emits the same signals, so that the lab starts quickly and its
failure and slow modes can be switched on demand by the load generator. The two *Bookshelf End to End* pages
(xref:backend/monitoring-alerting/grafana/bookshelf-end-to-end.adoc[Grafana] and
xref:backend/monitoring-alerting/kibana/bookshelf-end-to-end.adoc[Kibana]) build the same "Bookshelf service health" dashboard and
the same five alerts in each tool and record how long each notification took.

How to verify the lab: start one profile, open Grafana at `http://localhost:3000` or Kibana at `http://localhost:5601`, and
check that the webhook receiver logs a notification after you switch the load generator to its failing-request mode. The lab page lists
the check for every component.

== How the pages are written

Each page follows the same pattern: what the concept is, why it exists, how to do it in the user interface and as code, what can
go wrong, and how to verify it in the lab. Every section and example ends with a `Source:` or `Reference:` line that links the exact
official page. Where a topic also appears in one of the books in the bibliography, a short _In the books_ paragraph says what
still holds and what has changed since the book's version. The official documentation is the primary source for every fact,
setting and code sample; the books add method and context.

== In the books

Ten books were read for this section. For Grafana: Salituro (Grafana 10), Chapman and Holmes (Grafana 10.2), Hernandez
(Grafana 8) and McCollam (Grafana 8.2/8.3). For observability in general: Hausenblas. For the Elastic Stack: Shah (Kibana 8),
Paro (Elasticsearch 7), Chhajed (the ELK stack of 2015), Konda (Elasticsearch 8) and Melachi (a self-published guide to
Beats, Logstash, Elasticsearch and Kibana). They are strongest on method: how to design dashboards for an audience, how to
reason about SLOs and error budgets, how to buffer telemetry, how aggregations work. They are weakest on product detail, because every
one predates the versions described here. Ignore any instruction that mentions Grafana API keys, legacy alerting, Angular panels,
Grafana Agent, Promtail, Kibana TSVB or Timelion, Beats-only ingestion, Curator or Elasticsearch types, and use the official pages
linked from each topic instead. The publisher pages are listed in the <<_bibliography,bibliography>>.
