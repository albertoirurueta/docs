= Grafana vs Kibana
:description: A side-by-side comparison of Grafana 13.3 and Kibana 9.5 for monitoring and alerting: data model, query languages, visualizations, dashboards, alerting model, as-code tooling, licensing tiers and hosted offerings, with measured notification timings from the lab and guidance on choosing one or using both.
:keywords: Grafana, Kibana, comparison, contact points, connectors, notification policies, action frequency, silences, mute timings, snooze, maintenance windows, licensing, Terraform, PromQL, ES|QL, Bookshelf

Checked on 2026-11-09 against Grafana 13.3.x and Kibana 9.5.x.

include::partial$monitoring-alerting-disclaimer.adoc[]

Grafana and Kibana both draw dashboards and send alerts, so they are often presented as alternatives. They are better
understood as answers to different starting points. Grafana starts from the dashboard and asks "where is your data?": it
queries many back ends in place and keeps only its own configuration. Kibana starts from the data store and asks "what is in
Elasticsearch?": it is the interface of the Elastic Stack, so ingestion, storage, search, machine learning and alerting share one
platform. Most differences in the sections below follow from that. This page compares them concept by concept, shows the lab
timings measured for the same service in both tools, and ends with guidance on choosing and on combining them. The concepts
themselves are taught in the shared pages, and the tool pages are linked from every row.

== Data model and data sources

Grafana has no storage of its own for telemetry, so the data model is whatever the data source provides. A panel's query
returns data frames, and
xref:backend/monitoring-alerting/grafana/transformations-and-expressions.adoc[transformations and expressions] reshape them in
Grafana. This is why one dashboard can place a Prometheus request rate next to a Loki log panel and a PostgreSQL business
count (xref:backend/monitoring-alerting/grafana/data-sources.adoc[Data Sources]). The price is that every back end must be
installed, sized and secured separately, and every one brings its own query language.

Kibana reads Elasticsearch. Logs, metrics and traces are documents in data streams, described to Kibana by data views, and the
shared mapping (ECS or OpenTelemetry-native fields) lets one query language cover all three signals
(xref:backend/monitoring-alerting/kibana/data-views-and-discover.adoc[Data Views & Discover],
xref:backend/monitoring-alerting/kibana/data-streams-tsds-and-lifecycle.adoc[Data Streams, TSDS & Lifecycle]). Storage, retention
and downsampling are Elasticsearch features, so the same product runs ingestion, lifecycle and alerting.
xref:backend/monitoring-alerting/storage-retention-and-cost.adoc[Storage, Retention & Cost] compares the cost shape of the
two back-end families.

Reference: https://grafana.com/docs/grafana/latest/datasources/[Grafana: Data sources] and
https://www.elastic.co/docs/manage-data/data-store/data-streams[Elastic: Data streams].

== Query languages

[cols="2,3,3",options="header"]
|===
| Task
| Grafana
| Kibana

| Filter documents or log lines
| LogQL stream selectors and line filters; Lucene in the Elasticsearch data source
| KQL or Lucene in the search bar

| Rate of a counter
| PromQL `rate()`
| ES\|QL `TS` with a rate function, or the native `PROMQL` command
| Group by a dimension
| `sum by (label)`
| `+STATS ... BY field+`

| Time buckets
| Interval variables such as `+$__interval+`
| `+BUCKET(@timestamp, ...)+` or an automatic interval

| Join with reference data
| Transformations, or SQL joins in the database
| ES\|QL `LOOKUP JOIN`
|===

The practical difference is that Grafana asks you to know the language of each back end, while Kibana asks you to know ES|QL
once and use it for visualizations, variable controls and rules. Native PromQL in Kibana narrows the gap for teams that
already hold Prometheus-style queries. The Grafana Elasticsearch data source accepts Lucene, raw Query DSL in code mode and
ES|QL, so Grafana can sit on top of an Elastic back end as well.

Equivalent Bookshelf queries in both tools are in

xref:backend/monitoring-alerting/kibana/querying-with-kql-esql-and-promql.adoc[Kibana: Querying with KQL, ES|QL & PromQL].

== Alerting model

The two alerting systems solve the same problem (turn a condition into the right message for the right person) with different
building blocks. Grafana separates *what is wrong* from *who is told*: alert rules produce labelled alert instances, and a
tree of notification policies matches the labels to a contact point, groups alerts and sets the repeat interval. Kibana puts the
routing inside each rule: a rule lists actions, each action names a connector and says when it runs (on each check, on a status
change or on a custom interval).

[mermaid]
----
flowchart LR
    subgraph G[Grafana]
        GR[Alert rule] -->|labels| GP[Notification policy tree]
        GP --> GC[Contact point]
        GM[Silence or mute timing] -.->|suppresses| GP
    end
    subgraph K[Kibana]
        KR[Rule] -->|action group| KA[Action with frequency]
        KA --> KC[Connector]
        KS[Snooze or maintenance window] -.->|suppresses| KA
    end
----

Four differences matter most when you migrate a design from one tool to the other.

*Contact points versus connectors.* A Grafana contact point is a receiver that the policy tree points at, and a message template
belongs to it. A Kibana connector is a reusable integration, and each rule action chooses the connector, the action group and
the message. In Grafana you change who is paged by editing the tree once. In Kibana you change every rule that uses the
action, unless the rules are managed as code from a shared definition.

*Notification policies versus action frequency.* Grafana groups alerts that share labels into one notification and decides
when to repeat it with group wait, group interval and repeat interval. Kibana acts per rule and per action group and repeats
according to the action's frequency. Grafana's design gives one message per incident-shaped group by default. Kibana's gives
the precise per-rule control, and the cost of noise control is in the frequency settings you choose.

*Silences and mute timings versus snooze and maintenance windows.* Both pairs separate ad hoc suppression from recurring
suppression. A Grafana silence matches labels for a period and the alert still evaluates. A mute timing is a recurring schedule
attached to policies. Kibana snoozes a whole rule or one alert, and a maintenance window schedules suppression with a KQL filter
across rules. Grafana adds inhibition rules, which stop a symptom notification while its cause is already firing.

*Pending and resolution.* A Grafana rule has a pending period, so the first notification waits for the condition to hold. A
Kibana rule has no pending state, and the first run in which the condition is true creates an active alert. A Grafana resolved
message is sent when the alert resolves, subject to the policy's group interval, while a Kibana recovered message is sent only
if the rule has an action for the `recovered` action group.

Reference: https://grafana.com/docs/grafana/latest/alerting/fundamentals/[Grafana: Alerting fundamentals] and
https://www.elastic.co/docs/explore-analyze/alerting/alerts[Elastic: Alerting].

== Measured in the lab

The two end-to-end pages build the same five alerts on the Bookshelf service and switch the load generator into the failure
modes in turn. The times below are from the lab runs, measured from the moment the mode changed to the first notification at the
webhook receiver. They are lab measurements of default-style settings, not benchmarks of either product, and they mostly reflect
the pending periods and windows each page chose.

[cols="3,2,2,4",options="header"]
|===
| Scenario
| Grafana
| Kibana
| Why they differ

| High 5xx ratio
| 2 min 32 s
| 1 min 15 s
| Grafana waited for a 2 minute pending period; Kibana has none and its rule runs every minute

| p95 latency above the objective
| 6 min 51 s
| 2 min 24 s
| The Grafana rule has a 5 minute pending period; the Kibana APM rule uses a 5 minute window and no pending state

| No data (service stopped)
| 3 min 20 s
| 5 min 25 s
| Grafana alerts on a missing `up` series after 2 minutes; the Kibana rule needs a whole empty 5 minute window

| Error-log spike (log-only rule)
| 1 min 52 s
| 1 min 4 s
| Both count ERROR lines in 5 minutes; Grafana adds the policy group wait
|===

Resolved messages behave differently too: Grafana sent resolved notifications after its group interval (the 5xx rule resolved 5 min 29 s
after normal traffic returned), while the Kibana rules recovered silently because no action was attached to the `recovered`
group. Read the details on
xref:backend/monitoring-alerting/grafana/bookshelf-end-to-end.adoc[Grafana: Bookshelf End to End] and
xref:backend/monitoring-alerting/kibana/bookshelf-end-to-end.adoc[Kibana: Bookshelf End to End].

== Licensing tiers and hosted offerings

This site names no prices. What matters for the comparison is which capabilities need what.

[cols="2,3,3",options="header"]
|===
| Aspect
| Grafana
| Kibana

| Free, self-managed
| Grafana OSS and Grafana Enterprise without a licence key: dashboards, Explore, alerting, provisioning, contact points
| Elastic Stack under the basic licence: dashboards, Lens, Discover, rules with the Index and Server log connectors
| Capabilities that need a paid tier or licence
| Grafana Enterprise features such as role-based access control, data source permissions, reporting and usage insights
| Webhook, e-mail, Slack, PagerDuty and other connectors need Gold or above; machine learning, SLOs and some other features need a subscription level that includes them
| Hosted
| Grafana Cloud, which adds Grafana SLO and Grafana IRM
| Elastic Cloud Hosted (the Stack, operated) and Elastic Cloud Serverless (projects, no versions to manage)
|===

The lab uses a trial licence for the Elastic Stack so that every feature can be exercised. Check the subscription page of
each vendor for the tier of any feature before you design around it, because tiers and trials change.

== When to choose which

Choose Grafana when your telemetry is already spread over several stores (Prometheus metrics, Loki logs, Tempo traces, a SQL
database), when you want one dashboard and one alerting system across them, or when your team already speaks PromQL. Its
alerting model rewards a team that wants central routing: one tree decides who is paged for every service.

Choose Kibana when Elasticsearch already holds your logs, traces and business data, when you want search, machine learning,
APM, Synthetics and SLOs in one product, or when you ingest through Elastic Agent and the EDOT Collector. Its rule-and-action
model rewards a team that wants each rule to carry its own response.

Use both when the data and the habits are split. Grafana can query Elasticsearch through its Elasticsearch data source (raw
Query DSL and ES|QL), so an Elastic-based team can have Grafana dashboards beside Prometheus ones. Elastic 9.5 also announced a
migration tool that brings Grafana dashboards and alerts into Elastic, and native PromQL lets dashboards that already use
PromQL point at Elastic with little change. Alert on one platform at a time for a given service, because two systems paging for
the same condition double the noise.

Verify in the lab: run the `grafana` profile, then the `kibana` profile, and compare the first notification of the same
scenario in the webhook receiver log. The numbers will differ from the table above if you change a pending period or a window,
and that is the point: most of the differences you see are configuration, not product.

Reference: https://grafana.com/docs/grafana/latest/datasources/elasticsearch/[Grafana: Elasticsearch data source] and
https://www.elastic.co/blog/whats-new-elastic-9-5-0[What's new in Elastic 9.5].

== In the books

The Grafana books (Salituro, McCollam, Hernandez and Chapman and Holmes) and the Elastic books (Shah, Paro, Chhajed, Konda and
Melachi) never compare the two tools directly, and they cover versions long before the ones above. Salituro shows Grafana on
Elasticsearch data, and the Chapman and Holmes alerting chapter and the Hernandez chapter on alerting explain mute timings and silences in
the older Grafana model. Use them for method, and take current behaviour from the pages linked in each section. The publisher pages are
in the xref:backend/monitoring-alerting/index.adoc#_bibliography[bibliography].
