An alert is a request for a human to stop what they are doing. Whether that request is worth the interruption is decided
long before the alert fires, when somebody chose the query, the threshold, the labels, the text and the destination. The
tools covered in this section can evaluate almost any query on a schedule, so the hard part is never "can I alert on
this?". The hard part is deciding what *deserves* an alert, who should receive it, what they need to see in the
notification and how to prove that the rule still behaves after the system changes.

This page is the design half of alerting. The mechanics -- what a rule, an alert instance, a state and a notification are
-- are in xref:backend/monitoring-alerting/alerting-fundamentals.adoc[Alerting Fundamentals], and the Prometheus view of
the same ideas is in xref:database/prometheus/alertmanager.adoc[Alertmanager] and
xref:database/prometheus/recording-and-alerting-rules.adoc[Recording and Alerting Rules]. How the notification is worded,
delivered and followed up is in
xref:backend/monitoring-alerting/notifications-and-incident-response.adoc[Notifications and Incident Response]. The
service-level vocabulary used below is defined in
xref:backend/monitoring-alerting/slis-slos-and-error-budgets.adoc[SLIs, SLOs and Error Budgets], and the signals worth
alerting on come from
xref:backend/monitoring-alerting/monitoring-methods-red-use-golden-signals.adoc[RED, USE and the Golden Signals].

The running example is *Bookshelf*, the Spring Boot 4.1 book-catalogue service whose Micrometer and OpenTelemetry setup
is described in xref:backend/springboot/metrics-and-observability.adoc[Metrics and Observability]. The five alerts of the
xref:backend/monitoring-alerting/hands-on-lab.adoc[Hands-on Lab] (high 5xx ratio, p95 latency above the SLO, no data,
error-log spike and SLO burn rate) are used to illustrate each rule of design.

== What makes an alert actionable

The Google SRE book states the test in one sentence: every page should be actionable. It adds three qualifiers that are
worth keeping on a card next to the rule editor. A page should report a condition that is *urgent* (it cannot wait until
the next working day), *actionable* (a person can do something about it right now) and *user-visible* (something the
service's users already feel or are about to feel). If the right response is a fixed script, a machine should run the
script. If the problem is a known recurring one, the fix belongs in the backlog, not in somebody's night. Chapter 6 of
the same book also reminds the reader that people tire quickly of interruptions, so the number of pages per shift is a
resource to be spent carefully.

Grafana's best-practices page for alerting says the same in operational terms: write alerts for first responders so
that any on-call engineer can understand the problem and the next step, and if no action is possible use a dashboard
instead of an alert. The practical way to apply this is to put every candidate alert through four questions before it is
created:

[cols="2,3,3",options="header"]
|===
| Question
| If the answer is yes
| If the answer is no

| Is a user affected now, or will they be soon, without intervention?
| Candidate for a page (send to a paging destination).
| Candidate for a ticket or a dashboard panel, not a page.

| Can the person who receives it do something specific within minutes?
| Write the action into the alert (runbook link, dashboard link, summary).
| Do not alert. Put the signal on a dashboard for diagnosis.

| Does it fire once per problem, or many times for the same problem?
| Keep it.
| Group, deduplicate or aggregate it, or remove the redundant rules.

| Does a person ever decide differently because of it?
| Keep it.
| Delete it. An alert nobody acts on trains people to ignore the next one.
|===

Source: https://sre.google/sre-book/monitoring-distributed-systems/[Google SRE book -- Monitoring Distributed Systems] and https://grafana.com/docs/grafana/latest/alerting/guides/best-practices/[Grafana docs -- Alerting best practices].

== Alert on symptoms, not causes

A *symptom* is what the user or the business experiences: requests fail, pages are slow, a nightly import did not
finish. A *cause* is something inside the system that might produce a symptom: a pod restarted, CPU is at 90%, a
connection pool is half full, a disk is filling. Monitoring has to answer both "what is broken" and "why", but only the
first question should wake somebody. The SRE book's advice is to page on symptoms and use causes mainly as debugging aids,
paging on a cause only when it is definite and imminent (a disk that will be full in an hour is a legitimate exception).
Grafana's guidance matches: page on user-facing latency, errors and availability, and keep infrastructure signals such as
sustained CPU or memory pressure for dashboards, alert lists or a non-paging chat channel.

The reason is practical rather than philosophical. Causes are many and mostly benign: a restarted pod that Kubernetes
replaced within seconds hurts nobody, and a rule on restarts will fire every time a deployment rolls. Symptoms are few
and always matter. A rule on the 5xx ratio catches the database outage, the bad deployment, the exhausted thread pool and
the failing dependency with a single query, without anyone having predicted those failure modes in advance. The cause
signals are still collected, and the responder reads them on the dashboard once the symptom alert has fired.

For Bookshelf, the five lab alerts divide as follows. The classification is a design decision, not a property of the
tools, so write it down next to the rules.

[cols="2,2,3",options="header"]
|===
| Lab alert
| Class
| Reason

| High 5xx ratio
| Symptom, page
| Users get errors. Ratio rather than count, so the rule scales with traffic.

| p95 latency above the SLO
| Symptom, page when sustained
| Users wait. Percentile instead of average, over a window long enough to smooth spikes.

| SLO burn rate
| Symptom, page (fast burn) or ticket (slow burn)
| It fires when the error budget is at risk, which is the earliest user-centred signal.

| Error-log spike
| Cause or early warning, ticket or chat
| Useful for diagnosis, but a log spike with no user impact is not an emergency.

| No data
| Meta-alert, route to the platform owner
| It says the monitoring itself may be blind, not that the service is broken.
|===

Black-box checks fit the same model. A synthetic probe or a real-user measurement is an excellent symptom signal because
it sees what the user sees, including failures of DNS or the network that all the service's own metrics miss. The price is
a higher chance of false positives, because the probe also depends on things outside the team's control.

=== Escalate on confidence

Paging too early produces noise, and paging too late extends the user's pain. Grafana's guidance is to raise priority
as confidence grows: a latency increase alone is a ticket or a chat message, but latency plus a rising error ratio, or the
same condition sustained for several evaluations, is a page. Escalation may mean a louder channel, more responders or an
incident declaration. In rule terms this is two rules on related signals with different severities, or one rule with
a pending period and a stricter second rule that routes to the pager.

Source: https://grafana.com/docs/grafana/latest/alerting/guides/best-practices/[Grafana docs -- Alerting best practices, sections 1 and 2].

== Severity, ownership and routing by label

An alert with no owner is an alert nobody answers. Both stacks route notifications from *metadata attached to the rule*,
so the metadata contract is part of the design. A minimal contract that works for most teams has three labels and two
annotations:

[cols="1,2,3",options="header"]
|===
| Item
| Example
| Used for

| Label `team`
| `team=bookshelf-sre`
| Routes to the owning team's contact point and on-call schedule.

| Label `application`
| `application=bookshelf`
| Grouping (one notification per service), dashboards and ownership.

| Label `severity`
| `severity=critical`, `warning`, `info`
| Chooses the destination and the urgency: critical pages, warning opens a ticket, info goes to chat.

| Annotation `summary`
| One sentence: what is wrong and why it matters
| First line of every notification.

| Annotation `runbook_url`
| Link to the response procedure
| What the responder should do next.
|===

Keep the severity vocabulary small. Three levels are easier to route and to remember than six, and each level should have a
definition that states the expected response time ("critical: a person acts within 15 minutes, day or night"). Grafana's
docs also stress that routing matters as much as the alerts: a parent policy for default routing within the scope and
nested policies for specific cases or higher-priority issues.

=== In Grafana

Grafana labels on the rule identify the alert instance and are the only input that notification policies match on
(`=`, `!=`, `=~`, `!~`, combined with AND). Annotations carry the human-readable context; `summary`, `description` and
`runbook_url` are the well-known ones, and `+__dashboardUid__+` together with `+__panelId__+` link the alert to a
dashboard panel. The folder name is added automatically as the reserved label `grafana_folder`, and by default
notifications are grouped by `alertname` and `grafana_folder` with a 30 second group wait, a 5 minute group interval and a
4 hour repeat interval. The notification policy tree itself is covered on
xref:backend/monitoring-alerting/grafana/notification-policies.adoc[Notification Policies], and rule labels and
annotations on
xref:backend/monitoring-alerting/grafana/labels-annotations-and-rule-templates.adoc[Labels, Annotations and Rule Templates].

The rule below is the lab's first alert written as a file-provisioning resource. The query, reduce and threshold
structure is the one Grafana's own provisioning examples use. The `model` blobs are data-source specific, so the
dependable way to author them is to build the rule once in the UI and use *Export* (see
xref:backend/monitoring-alerting/grafana/provisioning-alerting-resources.adoc[Provisioning Alerting Resources]).
The `datasourceUid` is the UID of the lab's Prometheus data source (`prometheus`); adjust the selector to the labels your scrape
configuration attaches to Bookshelf's series.

[source,yaml]
----
# provisioning/alerting/bookshelf-rules.yaml
apiVersion: 1
groups:
  - orgId: 1
    name: bookshelf-service-level
    folder: bookshelf
    interval: 1m
    rules:
      - uid: bookshelf-5xx-ratio
        title: Bookshelf high 5xx ratio
        condition: C
        data:
          - refId: A
            relativeTimeRange:
              from: 600
              to: 0
            datasourceUid: prometheus
            model:
              refId: A
              expr: >-
                sum(rate(http_server_requests_seconds_count{application="bookshelf",status=~"5.."}[5m]))
                / sum(rate(http_server_requests_seconds_count{application="bookshelf"}[5m]))
              instant: true
              intervalMs: 1000
              maxDataPoints: 43200
          - refId: B
            relativeTimeRange:
              from: 0
              to: 0
            datasourceUid: '__expr__'
            model:
              refId: B
              type: reduce
              expression: A
              reducer: last
              datasource:
                type: __expr__
                uid: '__expr__'
          - refId: C
            relativeTimeRange:
              from: 0
              to: 0
            datasourceUid: '__expr__'
            model:
              refId: C
              type: math
              expression: $B > 0.05
              datasource:
                type: __expr__
                uid: '__expr__'
        noDataState: NoData
        execErrState: Error
        for: 5m
        keepFiringFor: 5m
        labels:
          team: bookshelf-sre
          application: bookshelf
          severity: critical
        annotations:
          summary: More than 5% of Bookshelf requests are failing with 5xx.
          description: The 5xx ratio has stayed above 5% for 5 minutes.
          runbook_url: https://wiki.example.com/runbooks/bookshelf-5xx
----

Reference: https://grafana.com/docs/grafana/latest/alerting/set-up/provision-alerting-resources/file-provisioning/[Grafana docs -- Provision alert rules with files]. The `keepFiringFor` key is the file-provisioning spelling of the Terraform argument `keep_firing_for` documented at https://registry.terraform.io/providers/grafana/grafana/latest/docs/resources/rule_group[`grafana_rule_group`]; if your Grafana version rejects it, remove the line and rely on the pending period alone.

Three details of the snippet deserve a comment. The expression `$B > 0.05` is a *Math* expression, and provisioning does
not interpolate environment variables in `data.model`, so the `$B` reaches Grafana untouched. The `noDataState` and
`execErrState` values decide what happens when the query returns nothing or fails (see the next section). And the
annotation `runbook_url` is a plain link: the best runbook is a short page that starts with the user impact, lists the
three most likely causes in order of likelihood, and links the dashboard that shows each.

=== In Kibana

Kibana rules carry *tags* instead of labels, and routing is configured on the rule's *actions* rather than in a central
tree. A rule has a list of actions, and each action has a connector, a frequency (per alert or summary, on every check, on
status change or at a custom interval), a "run when" group such as `Query matched` or `Recovered`, and optionally a
condition so that the action runs only for alerts matching a KQL filter or within a time frame. Severity routing is
therefore modelled by adding several actions to the same rule: a pager connector on the critical action group, a ticket
connector on warning. Rules that support severity levels expose them as action groups; the custom threshold rule offers a
warning threshold (Elastic Stack 9.5 and later) next to the critical one, and the SLO burn rate rule assigns each burn-rate
window an action group of critical, high, medium or low. The details are in
xref:backend/monitoring-alerting/kibana/actions-frequency-and-variables.adoc[Actions, Frequency and Action Variables].

The Terraform provider exposes the runbook as code, too. The `artifacts` attribute of `elasticstack_kibana_alerting_rule`
attaches an investigation guide (inline or from a Markdown file) and links to related dashboards to the rule, so the
guide lives in the same pull request as the alert. Writing it requires Elastic Stack 9.1 or later, and reading it back
(and therefore `terraform import`) works from 9.5.0 on. The full example is on
xref:backend/monitoring-alerting/observability-as-code.adoc[Observability as Code].

Source: https://www.elastic.co/docs/explore-analyze/alerting/alerts/create-manage-rules[Elastic docs -- Create and manage rules] and https://registry.terraform.io/providers/elastic/elasticstack/latest/docs/resources/kibana_alerting_rule[Terraform Registry -- `elasticstack_kibana_alerting_rule`].

== Scope alerts so one problem gives one notification

A rule per host, per endpoint or per pod produces a hundred nearly identical alerts when one dependency fails. The
alternatives are to write one *multi-dimensional* rule (one rule whose query returns one series per service, endpoint
or instance, so that each series becomes its own alert instance) and to *group* notifications so that a burst of
instances reaches the responder as a single message. Grafana's advice is to start with one dimension, such as `service` or
`endpoint`, and add `region` or `instance` only when they make the alert more actionable. Group along operational
boundaries (service or owner) and group cascading failures together: one root cause, such as a database failure, can fire
several symptom alerts and the responder needs one notification.

In Kibana the same ideas are the *Group alerts by* option of the custom threshold rule (one alert per matching group, with
multiple fields combined in a comma-separated group name) and the *summary of alerts* action frequency, which sends one
message per check or per custom interval instead of one per alert. The action frequency "On check intervals" repeats
the notification for the same condition on every check, which is precisely the pattern that creates fatigue; a custom
interval (the official example uses five minutes) or "On status changes" reduces the repeats, and the interval must not be
shorter than the check interval.

Source: https://grafana.com/docs/grafana/latest/alerting/examples/multi-dimensional-alerts/[Grafana docs -- Multi-dimensional alerts] and https://grafana.com/docs/grafana/latest/alerting/fundamentals/notifications/group-alert-notifications/[Grafana docs -- Group alert notifications].

== Missing data and connectivity errors

The most dangerous alerting failure is silence. If the query that feeds an alert returns nothing, the alert never fires,
and an outage that also removes the metrics (the pod is gone, the exporter crashed, the scrape target is unreachable) is
reported by nothing at all. Prometheus does not fire on an empty result, so empty results must be checked explicitly.
Grafana adds built-in handling that works for every data source, including the ones with no `absent` function. It
distinguishes three situations:

* A *connectivity error* happens when the query itself fails, for example the data source is down or the query is
  invalid. Grafana handles it through the rule's *error* state.
* *No Data* happens when the query runs but returns no data for any series.
* A *missing series* happens when some series that used to report disappear while others keep reporting. Grafana keeps the
  last state for two evaluation intervals, then marks the instance `Normal` with the reason `MissingSeries`, sends a
  resolved notification if it was firing, and removes it from the UI. That eviction prevents flapping during scale events,
  but it can also hide a real failure, because a resolution caused by a missing series looks like a recovery. Check the
  `grafana_state_reason` annotation in the alert history.

The rule setting *Configure no data and error handling* chooses the reaction to No Data:

[cols="2,4,3",options="header"]
|===
| Option
| Behaviour
| Typical use

| No Data (default)
| Creates a separate alert named `DatasourceNoData`.
| Missing data is itself worth investigating.

| Alerting
| Moves each existing alert instance into `Alerting`.
| Losing data must be treated as an incident.

| Normal
| Moves all instances to `Normal` and ignores the gap.
| Sporadic jobs, periodic reports, experimental services. It can hide outages.

| Keep Last State
| Holds the previous state until data returns.
| Flaky exporters with brief gaps. It can mask a prolonged failure.
|===

A failing query produces a `DatasourceError` alert in the same way. Both `DatasourceNoData` and `DatasourceError` alerts
use a dedicated alert name and do not inherit all the labels of the original rule, so they usually need their own
notification policy; without one, they land in the default policy or get lost. The Terraform resource `grafana_rule_group`
spells the options `OK`, `NoData`, `KeepLast` and `Alerting` for `no_data_state`, and `OK`, `Error`, `KeepLast` and
`Alerting` for `exec_err_state` (the default is `Alerting` for errors and `NoData` for missing data).

When label-level detection is needed in a Prometheus-compatible data source, three PromQL idioms from the official guide
cover the common cases:

[source,promql]
----
# 1. The whole metric disappeared (no labels survive, so it cannot say which series).
absent_over_time(http_server_requests_seconds_count{application="bookshelf"}[5m]) == 1

# 2. A series that reported in the last 24h but not in the last 10m (here, per instance).
group(present_over_time(http_server_requests_seconds_count{application="bookshelf"}[24h])) by (instance)
unless
group(present_over_time(http_server_requests_seconds_count{application="bookshelf"}[10m])) by (instance)

# 3. Return 0 instead of "no data" when an empty result is a normal value.
sum(rate(http_server_requests_seconds_count{application="bookshelf",status=~"5.."}[5m])) or on() vector(0)
----

Source: https://grafana.com/docs/grafana/latest/alerting/guides/missing-data/[Grafana docs -- Handle missing data in Grafana Alerting].

Scrape delay creates false gaps. The official guide suggests shifting the rule's *To* time to something like `now-1m` or
using `last_over_time` in the query so that a late sample does not look like missing data. It also warns against alerting
on every instance in a dynamic environment where pods come and go: aggregate unless an individual instance directly
affects users.

In Kibana the custom threshold rule has its own no-data model. From Elastic Stack 9.0 the option *Alert me if there's no
data* creates a no-data alert when the condition returns no data or the query fails (without group fields), or when a
previously detected group stops reporting (with group fields). On Serverless and from Elastic Stack 9.4 the rule offers
three behaviours: recover active alerts, alert about the missing data, or do nothing. A decommissioned host that keeps
raising no-data alerts is fixed by marking the alert *untracked* in the alerts table. The rule's action frequency has
a separate *No Data* condition so the notification can go to a different destination.

Source: https://www.elastic.co/docs/solutions/observability/incident-management/create-custom-threshold-rule[Elastic docs -- Custom threshold rule].

== Static thresholds, forecasts and anomalies

A static threshold ("error ratio above 5%") is the right tool when a number has a business meaning. It is the wrong tool
when normal behaviour moves with the time of day, the day of the week or the release cycle: the threshold is either low
enough to fire every Monday morning or high enough to miss a real regression. Two alternatives help.

*Forecast-based alerts* fire when a trend will cross a limit, which is the legitimate case of paging on a cause: "the
disk is full in four hours". In PromQL the function `predict_linear` fits a line to a range of samples and projects it into
the future; the range should be several times longer than the horizon.

[source,promql]
----
# Alert when the filesystem is predicted to be full within 4 hours, based on the last 6 hours of samples.
predict_linear(node_filesystem_avail_bytes{mountpoint="/"}[6h], 4 * 3600) < 0
----

Reference: https://prometheus.io/docs/prometheus/latest/querying/functions/#predict_linear[Prometheus docs -- `predict_linear`].

*Anomaly detection* learns a baseline and flags deviations, so no one has to maintain the threshold. In the Elastic Stack
it is provided by machine-learning jobs and their alerting rules (see
xref:backend/monitoring-alerting/kibana/machine-learning-and-aiops.adoc[Machine Learning and AIOps]); Grafana's own
documentation for the same capability depends on the plan and edition, so check the version you run. Chapter 7 of
_Cloud Observability in Action_ describes the same idea as a baseline of "how the service looks when everything is
healthy". Anomaly detectors are best used to open tickets or to enrich a page, because they cannot tell a harmless
deviation from a harmful one. Chapman and Holmes make a related point in their incident chapter: AIOps-style tools do not replace the
specific domain knowledge needed to name the critical signals.

== SLO burn-rate alerts

The most reliable way to page on a symptom without constant tuning is to alert on how fast the *error budget* is being
spent, instead of on the raw error rate. Suppose the objective is 99.9% of requests succeeding over 30 days. The budget is
the 0.1% that may fail. The burn rate is the ratio of the observed error rate to the allowed rate:

[stem]
++++
\mathrm{burn\ rate} = \dfrac{\text{observed error rate}}{1 - \mathrm{SLO}}
++++

A burn rate of 1 exhausts the budget exactly at the end of the window, 2 exhausts it halfway through, and 14.4 exhausts a
30-day budget in about two days. The share of the budget consumed during an alerting window is
stem:[\text{burn rate} \times \text{window} / \text{period}]: a burn rate of 14.4 sustained for one hour consumes
stem:[14.4 \times 1 / 720 = 2\%] of a 30-day (720-hour) budget.

The SRE workbook compares six ways to alert on an SLO and recommends the last: *multiple burn rates, each with a long
and a short window*. The long window supplies precision (a brief spike cannot reach the threshold), and the short window
supplies a fast reset (the alert clears minutes after the problem ends instead of an hour later). For a 99.9% SLO the
recommended table is:

[cols="1,1,1,1,2",options="header"]
|===
| Long window
| Short window
| Burn rate
| Budget consumed
| Response

| 1 hour
| 5 minutes
| 14.4
| 2%
| Page

| 6 hours
| 30 minutes
| 6
| 5%
| Page

| 3 days
| 6 hours
| 1
| 10%
| Ticket
|===

A rule fires only when *both* windows exceed the threshold. Translated to PromQL for Bookshelf (99.9% objective, so the
allowed error ratio is 0.001 and the first threshold is 14.4 times 0.001, that is 0.0144):

[source,promql]
----
(
  sum(rate(http_server_requests_seconds_count{application="bookshelf",status=~"5.."}[1h]))
  / sum(rate(http_server_requests_seconds_count{application="bookshelf"}[1h]))
) > (14.4 * 0.001)
and
(
  sum(rate(http_server_requests_seconds_count{application="bookshelf",status=~"5.."}[5m]))
  / sum(rate(http_server_requests_seconds_count{application="bookshelf"}[5m]))
) > (14.4 * 0.001)
----

Source: https://sre.google/workbook/alerting-on-slos/[Google SRE workbook -- Alerting on SLOs].

Evaluating raw `rate()` over six hours or three days on every evaluation is expensive. The usual remedy is a recording rule
per window (see xref:backend/monitoring-alerting/grafana/recording-rules.adoc[Recording Rules]), and that is what the
products below generate for you.

* *Grafana SLO* (documented under Grafana Cloud) creates the SLI recording rules (10 to 12 per SLO) and burn-rate alert
  rules for each SLO. A *fast-burn* alert signals a severe problem that consumes the budget in minutes to hours and may
  warrant paging, and a *slow-burn* alert signals an ongoing issue over hours to days that may warrant a ticket. The SLO
  documentation gives no numeric thresholds, so use the table above as a starting point. See
  xref:backend/monitoring-alerting/grafana/slo-and-irm.adoc[SLOs and IRM] and
  https://grafana.com/docs/grafana-cloud/observe-and-act/alert-and-measure-reliability/slo/introduction/[Grafana docs -- SLO introduction].
* The *Kibana SLO burn rate rule* (generally available on the Elastic Stack and on Serverless) alerts when the burn rate
  exceeds a threshold over two lookback periods, a long one and a short one equal to one twelfth of it, and fires only when
  both are exceeded; the example pair is one hour and five minutes, the same ratio as the SRE table. The rule form lets you
  define several burn-rate windows, each with a lookback in hours, a threshold and an action group that sets the severity,
  and the UI starts with four windows. Creating an SLO in the UI also creates a default burn-rate rule with no connector, so
  nobody is notified until an action is added. See
  xref:backend/monitoring-alerting/kibana/slos.adoc[SLOs] and
  https://www.elastic.co/docs/solutions/observability/incident-management/create-an-slo-burn-rate-rule[Elastic docs -- SLO burn rate rule].

Grafana's own guide on when an alert needs an SLO gives three signs that a threshold alert should graduate: nobody acts on
it but the metric matters, several teams set their own thresholds on the same user-facing metric, or the alert fires on
transient conditions that are individually harmless but accumulate. In all three cases the error budget keeps a long-term
record that a threshold alert, which resets on recovery, cannot.

Source: https://grafana.com/docs/grafana/latest/alerting/guides/when-slos-reduce-alert-noise/[Grafana docs -- When SLOs reduce alert noise].

== Control flapping

A *flapping* alert alternates between firing and resolved, producing a notification each time. Four mechanisms damp it,
from the evaluation of the rule to the delivery of the message.

[cols="2,4,4",options="header"]
|===
| Mechanism
| Grafana
| Kibana

| Require persistence
| Pending period (`for`): the condition must hold for the period before the alert fires.
| Alert delay: a number of consecutive runs that must match (Terraform `alert_delay`).

| Smooth the query
| Aggregate over a window (`avg_over_time`, `quantile_over_time`); prefer percentiles over averages for latency.
| Choose a time window large enough for the aggregation; the custom threshold rule offers percentile aggregations.

| Stay firing briefly
| `keep_firing_for`, or a recovery threshold, to avoid resolve-and-fire churn.
| Flapping detection (enabled by default): an alert with at least 6 status changes in the last 10 runs (the documented
  example) is marked `flapping`. Settings can be set per rule or for a space since Elastic Stack 9.3.

| Limit the notification rate
| Group wait, group interval and repeat interval in the notification policy; the "Single email" option for email.
| Action frequency (on status change or a custom interval), summaries, and snooze.
|===

Grafana's guide shows the difference a window makes: `cpu_usage > 90` reacts to every transient spike, while
`avg_over_time(cpu_usage[5m]) > 90` smooths them, and `quantile_over_time(0.95, http_duration_seconds[5m]) > 3` expresses
the objective for latency directly. Note that the pending period and `keep_firing_for` shift the alert in time:
a 5 minute pending period means the page comes at least 5 minutes after the breach starts, so size it against the response
time promised by the SLO.

Source: https://grafana.com/docs/grafana/latest/alerting/guides/best-practices/[Grafana docs -- Alerting best practices, section 7] and https://www.elastic.co/docs/explore-analyze/alerting/alerts/create-manage-rules[Elastic docs -- Create and manage rules, flapping and action frequency].

== Measure alert fatigue

Alert fatigue is a measurable condition: responders stop acting because most notifications are not worth acting on. The
numbers to track per team and per alert, reviewed monthly, are:

* Notifications and pages per on-call shift. The SRE book warns that people tire after only a few urgent interruptions a day.
* The share of pages that led to a human action. A rule whose pages rarely lead to action is mostly noise, and a threshold such as 50% is a reasonable first target for the review.
* Time to acknowledge and time to resolve. Rising acknowledgement times are an early symptom of fatigue.
* Repeat and duplicate notifications for the same problem, and the number of alerts that fire together.
* Alerts that flap, and alerts that have not fired for a year (candidates for deletion or for a smoke test).

Both stacks keep the data needed to compute most of this:

* Grafana can record *alert state history* in Loki or Prometheus and *notification history* in Loki (OSS and Enterprise
  need `enabled = true` under `[unified_alerting.notification_history]` and a `loki_remote_url`; Grafana Cloud manages it).
  The History page shows state changes and, on the Notifications tab, every notification with its contact point and a
  Failed badge for delivery errors. The history can be queried in Explore because it lives in Loki.
* Grafana exposes meta-monitoring metrics. `grafana_alerting_alerts` counts alert instances by state (normal, pending,
  alerting, nodata, error), and when Prometheus is configured for state history Grafana writes the series `GRAFANA_ALERTS`
  with the labels `grafana_rule_uid` and `grafana_alertstate`. A rough per-rule measure of firing time over a week is:

[source,promql]
----
sum by (grafana_rule_uid) (count_over_time(GRAFANA_ALERTS{grafana_alertstate="alerting"}[7d]))
----

* The *Alert quality* page (Alert Advisor) checks Grafana-managed rules against a policy of required labels and annotations
  (Runbook URL, Summary, Description and label keys such as team) and reports a score from 0 to 10, the share of assessed
  rules that meet every requirement. Each requirement is either detect-only or enforced, and enforcement blocks rule
  creation or updates made through Terraform and the provisioning API (writes made in the rule editor are not blocked, but
  still produce findings). It checks only that a field is present and not blank, not that a link works. The recommended
  workflow is to start detect-only, fix the findings, then enforce, and to check label changes against the notification
  policies because labels affect routing. Alert Advisor is described on a page that does not state its release status, and
  the What's new page for Grafana 13.3 lists it as public preview, so treat it as preview.
* In Kibana, the rule details page shows the *Last response* (succeeded, warning, failed) and the active alerts with
  their duration, and the *History* tab lists failed actions. The event log index holds the execution record when the
  Task Manager health API is not accurate for connector runs.

Source: https://grafana.com/docs/grafana/latest/alerting/set-up/meta-monitoring/[Grafana docs -- Monitor Grafana Alerting], https://grafana.com/docs/grafana/latest/alerting/set-up/meta-monitoring/[Grafana docs -- Meta monitoring], https://grafana.com/docs/grafana/latest/alerting/monitor-status/view-notification-history/[Grafana docs -- View notification history], https://grafana.com/docs/grafana/latest/alerting/alerting-rules/alert-rule-quality/[Grafana docs -- Alert rule quality] and https://www.elastic.co/docs/explore-analyze/alerting/alerts/create-manage-rules[Elastic docs -- Create and manage rules].

== Test alerts before an incident does

An alert that has never fired is an untested alert. The review of a rule is incomplete until somebody has watched it
change state, reach the right person, with the right text, and resolve. The lab makes this cheap, because Bookshelf, the
load generator and the webhook receiver are all local; see the xref:backend/monitoring-alerting/hands-on-lab.adoc[Hands-on Lab]
for the exact commands and service names of each profile. The procedure is the same for every lab alert:

. Confirm the rule evaluates. In Grafana open the rule and read its state (Normal) and the last evaluation time; in Kibana
  open the rule details and check that *Last response* is `succeeded`.
. Force the condition: for the 5xx and latency alerts switch the load generator to `curl -X POST localhost:8090/mode/failing` or
  `curl -X POST localhost:8090/mode/slow`; for the no-data alert stop the scrape or the collector; for the log alert emit a burst of error logs.
. Watch the lifecycle. In Grafana the instance moves from Normal to Pending (during the pending period) to Firing; in
  Kibana the alert appears as active in the rule details.
. Read the notification the webhook receiver got: does it contain the summary, the runbook link, the dashboard link and the
  silence link, and is it grouped as intended? Is the severity routed to the destination you expected?
. Restore the system and confirm the resolved notification arrives (unless resolve messages are disabled).
. Repeat the exercise for the error path: break the data source and check that the `DatasourceError` alert reaches its
  own route.

Grafana can also send a test notification from a contact point, but only for the Grafana Alertmanager. That checks the
delivery channel, not the rule, so it complements the forced breach rather than replacing it.

Source: https://grafana.com/docs/grafana/latest/alerting/configure-notifications/manage-contact-points/[Grafana docs -- Configure contact points, test a contact point].

== Review alerts regularly

Alerts decay as services change. Put a standing review on the calendar and use the incident review as the trigger for the
rest. Grafana's guidance is to review alerts on a regular schedule, remove those that do not drive action, tune the ones
that fire often without useful signal, and prefer fewer, high-quality alerts over many low-value ones. After every
incident ask which alerts fired, whether they helped, whether they came too early or too late, and what context was
missing, then adjust thresholds, priorities, escalation and annotations accordingly. The SRE book adds a deletion rule: configurations
that rarely run (the text suggests less than once a quarter) and signals that no dashboard or alert uses are candidates for removal.
Keeping rules in Git, as described in
xref:backend/monitoring-alerting/observability-as-code.adoc[Observability as Code], turns the review into a pull request
with a history.

== Common mistakes

[cols="2,3",options="header"]
|===
| Mistake
| Consequence and remedy

| Paging on CPU, memory or restarts
| Fires on benign events. Use dashboards or a ticket channel, page on the user-facing symptom.

| One rule per host
| Hundreds of alerts for one outage. Use a multi-dimensional rule and group notifications.

| No pending period on a noisy metric
| Flapping and fatigue. Add persistence, a window or `keep_firing_for`.

| Default No Data handling with no route for `DatasourceNoData`
| The meta-alert disappears into the default policy. Route `DatasourceNoData` and `DatasourceError` deliberately.

| No Data set to Normal "to stop the noise"
| A real outage that removes the data is silent. Choose the setting per rule on purpose.

| Raw error-rate threshold on a spiky service
| Pages for transient errors. Alert on burn rate with two windows.

| Alert without `runbook_url`, `summary` or an owner label
| Slow, confused response. Enforce the contract with Alert Advisor or a CI check.

| Alerts never exercised
| Fails during the first real incident. Run the forced-breach test on every rule.
|===

== In the books

Chapter 9 of _Observability with Grafana_ (Chapman and Holmes, Packt, 2023, written for Grafana 10.2) frames alerting as
part of incident management: it contrasts being alerted with being alarmed, recommends three to five SLIs per service, and
reuses RED, USE, golden signals and core web vitals as the candidates, with white-box and black-box monitoring as the two
detection styles. That advice has not aged. What has changed is the tooling around it: the separate Grafana OnCall and Grafana
Incident products it presents are now part of Grafana IRM, the Grafana UI has moved on from 10.2, and legacy alerting no
longer exists. The SLO tooling it mentions has grown (Grafana SLO now generates burn-rate alert rules). Chapter 7 of
_Cloud Observability in Action_ (Hausenblas, Manning, 2023) covers alerting with Prometheus and Grafana at a conceptual
level, and its Grafana alerting walkthrough predates the current rule editor, the Prometheus Alerting app plugin of Grafana
13.3 and the missing-data options described above. For the missing-data behaviour, the grouping defaults and the quality
policy, the official pages cited in this page are the current source. Publisher pages:
https://www.packtpub.com/product/observability-with-grafana/9781803248004[Observability with Grafana (Packt)] and
https://www.manning.com/books/cloud-observability-in-action[Cloud Observability in Action (Manning)].

== Verify in the lab

* Create the rule from this page (or its UI equivalent), then check that *Alert quality* in Grafana, or the rule details in
  Kibana, shows no missing owner, summary or runbook.
* Break the data source on purpose and confirm that the `DatasourceError` or no-data alert reaches the platform route and
  not the application team's pager.
* Run the forced-breach procedure and keep the resulting notification payloads in the repository as the reference for what
  a good alert looks like.
* Look at the notification history after a week of lab traffic and count the notifications per rule; any rule with a
  notification count much higher than its incident count needs a longer pending period, grouping or a smaller scope.
