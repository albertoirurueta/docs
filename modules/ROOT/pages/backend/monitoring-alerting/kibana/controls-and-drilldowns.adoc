= Kibana: Controls & Drilldowns
:description: Kibana dashboard controls (options list, range slider, time slider, ES|QL variable controls), pinned and unpinned scope, chaining, and the dashboard, URL and Discover drilldowns, with their limits and a Bookshelf example.
:keywords: Kibana, dashboard controls, options list, range slider, time slider, variable control, pinned controls, chaining, drilldown, dashboard drilldown, URL drilldown, Discover drilldown, Handlebars, Bookshelf

include::partial$ai-disclaimer.adoc[]

Checked on 2026-11-09 against Kibana 9.5.x.

To do this by hand, follow xref:backend/monitoring-alerting/kibana/guide-arrange-and-connect-a-dashboard.adoc[Arrange and Connect a Dashboard].

A dashboard that only shows is a poster. Two features make it a tool: *controls* let the viewer narrow every panel to one service, one route or one
status class without editing anything, and *drilldowns* turn a value on a panel (a route in a table, a slice of a pie) into a jump to the next level of detail
with the context carried along. They are Kibana's counterparts of Grafana's variables and data links
(see xref:backend/monitoring-alerting/grafana/variables.adoc[Grafana: Variables] and
xref:backend/monitoring-alerting/grafana/annotations-and-links.adoc[Grafana: Annotations and Links]), with one important difference in model: a Grafana
variable is substituted into each query, while an options list control adds a filter on a field, and only an ES|QL variable control substitutes a value into a query.
This page assumes the dashboard from xref:backend/monitoring-alerting/kibana/building-dashboards.adoc[Building Dashboards].

[mermaid]
----
flowchart LR
    V[Viewer selects a value] --> C{Control type}
    C -->|Options list or range slider| F[Filter on the control field]
    C -->|Time slider| T[Narrow the global time range]
    C -->|ES and QL variable control| Q[Substitute into the query of panels that use the variable]
    F --> P[Panels whose data view has the field]
    T --> P2[Time based panels]
    Q --> P3[ES and QL and Vega panels that name the variable]
    D[Click on a panel value] --> DD{Drilldown}
    DD --> D1[Another dashboard]
    DD --> D2[A URL]
    DD --> D3[Discover]
----

== Control types

Source: https://www.elastic.co/docs/explore-analyze/visualize/dashboard-controls[Kibana: Dashboard controls].

[cols="1,3,3",options="header"]
|===
|Control |What it does |Availability

|Options list
|A dropdown that filters by one or more selected values of a field. Best for fields with a limited set of distinct values (service, route, status class).
|Generally available on Serverless and the Stack.

|Range slider
|Filters a numeric field within a range (response size, duration). Numeric fields only.
|Generally available.

|Time slider
|Narrows the global time range to a window that the viewer moves backward and forward or animates. One per dashboard, pinned at the top.
|Generally available on Serverless and on the Stack since 9.0.

|Variable control (ES{vbar}QL)
|Binds to ES{vbar}QL query variables (`+?name+` for values, `+??name+` for field names and functions), so that a viewer can change a value, a grouping field or an aggregation function.
|Preview on Serverless; Stack preview since 9.0 (called ES{vbar}QL controls in 9.0 and 9.1).
|===

The options list and the range slider are created as *Control* filters on a data view field; the time slider needs a data view with a time field; the
variable control is described in detail in
xref:backend/monitoring-alerting/kibana/esql-visualizations-and-variable-controls.adoc[ES|QL Visualizations & Variable Controls]
and only summarised here.

== Where a control applies: pinned and unpinned

Source: https://www.elastic.co/docs/explore-analyze/visualize/dashboard-controls#controls-scope[Kibana: How controls affect the dashboard].

* *Pinned* controls sit at the top, stay visible while scrolling and apply dashboard-wide. A new control is pinned by default. A dashboard takes up to 100 pinned controls.
* *Unpinned* controls live in the body of the dashboard, can be moved and resized, and apply to the relevant panels across the dashboard, or only to the panels
  of a collapsible section when placed inside it. Unpinned controls are generally available on Serverless and on the Stack since 9.4; a section-scoped control
  filters only that section (Stack since 9.4).
* By type: options lists and range sliders affect the panels that use the control's field; the time slider narrows the global time range and so affects
  only time-based panels; a variable control affects only the visualizations whose query references its variable (ES|QL and, as a Serverless preview, Vega;
  Planned on the Stack).

The design rule for Bookshelf: pin the two controls that every panel obeys (`service.name`, `url.path`), and place a section-specific control (for
example the log level in the "Logs and traces" section) inside its section, so that choosing `ERROR` does not blank the latency charts. Anything with a different
meaning in different sections (an "status" control that means HTTP status in one section and log level in another) belongs in a section, not on the pinned bar.

== Add an options list or range slider

Source: https://www.elastic.co/docs/explore-analyze/visualize/add-controls[Kibana: Add controls to dashboards].

You need the *All* privilege for the Dashboard feature, a dashboard in edit mode and a data view with filterable fields.

. Open the *Create control* flyout: *Add > Controls > Control* (9.2 and later, and Serverless; in 9.0 and 9.1 it is *Controls > Add control*).
. Choose the data source. *Select a field* takes a data view and a field. *Write a query* (Serverless and Stack 9.5 and later) takes an ES|QL query that
  returns a single column, for example `+STATS BY service.name+`; check it under *Values preview*, limit the offered values with `WHERE`, and reference a variable
  control with `+?variable_name+`.
. Choose *Options list* or *Range slider* (the slider needs a numeric field; its minimum and maximum come from the data or the query).
. Set the label and options, and select *Save*. The control appears in edit mode so you can test it.
. The control is pinned by default; *Unpin* moves it into the body, where it can be arranged or put in a section.
. Save the dashboard.

The settings that matter (the full list is on the control settings reference):

[cols="2,4,2",options="header"]
|===
|Setting |Behaviour |Default

|Label
|Replaces the field name in the control; use a business word ("Route") for the viewers.
|Field name

|Selections (options list)
|Multiple values or a single value.
|Multiple

|Searching (options list)
|How typing matches values: *Contains*, *Prefix* or *Exact*, not case sensitive.
|Contains for text, Prefix for IP

|Use global filters
|The options offered honour the global filters, the query, the time range and the selections of other controls; this is what chains controls. In 9.0 to 9.3 it is one dashboard-wide setting.
|On

|Validate user selections
|Flags a selected value that returns no data after the other filters apply. In 9.0 to 9.3 it is dashboard-wide.
|On

|Always load all results / Ignore timeout for results
|Loads the full list for big data sets. The first is generally available on Serverless and Planned on the Stack; the second is generally available on the Stack from 9.0 to 9.5 and replaces it there.
|Off

|Step size (range slider)
|Granularity of the slider.
|None stated

|Apply selections automatically (dashboard)
|Updates the dashboard on each selection, or only when you select *Apply*. In 9.0 to 9.3 it is in the control settings dialog.
|On
|===

Reference: https://www.elastic.co/docs/explore-analyze/visualize/dashboard-control-settings[Kibana: Dashboard control settings]. Turning *Apply selections automatically* off
is worth it on a dashboard with expensive panels: a viewer picks three routes and then runs the queries once.

Managing a control: hover to see *Clear*, *Unpin* or *Pin to Dashboard*, *Edit* (field, type, query and settings), *Display settings* (minimum width and whether it expands for pinned
controls; resize by dragging for unpinned ones) and *Remove*. Unpinned controls also have *Duplicate* and *Copy to dashboard* in the panel menu (9.4 and later, and Serverless). A control
placed on a dashboard is itself a dashboard element, so it counts toward the item limits described on the building page.

== Add a time slider

Source: https://www.elastic.co/docs/explore-analyze/visualize/add-time-slider-controls[Kibana: Add a time slider control].

In edit mode choose *Add > Controls > Time slider* (Serverless and Stack 9.2 and later; *Controls > Add time slider control* in 9.0 and 9.1), then save. By default the range is a
fixed-width window that slides along the timeline; *Pin start* keeps the start fixed while the end extends, and viewers can change that too. Its initial range
comes from the global time filter, so to change the range change the time filter. There can be only one time slider on a dashboard, always pinned at the top. For an incident
review it is the tool for stepping through the five minutes around an alert and watching the panels follow.

== ES|QL variable controls in short

Source: https://www.elastic.co/docs/explore-analyze/visualize/add-variable-controls[Kibana: Add variable controls to a visualization].

Create one from the ES|QL editor (type `?` and choose *Create control*) or from the dashboard with *Add > Controls > Variable control*. The types are static values, values from
a query (the basis of chaining) and fields or functions (preview from 9.1 on the Stack). The page's example filters by a selected IP address:

[source,esql]
----
FROM kibana_sample_data_logs
| WHERE ip == ?ip
| STATS count = COUNT(*) BY day = DATE_TRUNC(1 day, @timestamp)
| SORT day
----

Reference: https://www.elastic.co/docs/explore-analyze/visualize/add-variable-controls[Kibana: Add variable controls]. `+?_tstart+` and `+?_tend+` are the built-in time variables. Multiple
selections (`MV_CONTAINS` for all, `MV_INTERSECTS` for any) work with `+?values+` variables only, and chaining, where a child query refers to its parent's variable, is a preview since 9.3.
Selecting a control's label to highlight the panels that use it is a Serverless preview and a Stack preview since 9.5. Anything beyond this summary
(multi-field breakdowns, importing a Discover session with its controls, the Bookshelf `service` and `group_by` controls) is on the
ES|QL page linked above.

== Chaining controls

Options lists and range sliders chain automatically: with *Use global filters* on, each control offers only the values that still return data given the
other selections, so choosing `service.name = bookshelf` leaves only Bookshelf's routes in the `url.path` list. Turn *Use global filters* off for a control that must always list
everything (a service selector that should not shrink when a route is picked). Chaining among field controls and chaining among variable controls are independent of each other.
What can go wrong: a chained list that is empty because the time range has no data, a selection kept after the other filters made it invalid (it is flagged while *Validate user selections* is
on, and filters to nothing when it is off), and the "all" case, which in an options list is no selection at all: an empty control means no filter.

== Drilldowns

Source: https://www.elastic.co/docs/explore-analyze/dashboards/drilldowns[Kibana: Drilldowns].

A drilldown is a navigation action on a panel: you select a value, and Kibana opens a destination you defined, carrying the selected value, the dashboard filters and the time range.
Drilldowns are generally available on Serverless and on the Stack. There are three kinds:

[cols="1,3,3",options="header"]
|===
|Type |Destination |Page

|Dashboard
|Another dashboard, filtered by the selected value (a host dashboard filtered by the host name).
|https://www.elastic.co/docs/explore-analyze/dashboards/create-dashboard-drilldown[Create a dashboard drilldown]

|URL
|Any web page, with the value in the URL (a runbook or a ticket search).
|https://www.elastic.co/docs/explore-analyze/dashboards/create-url-drilldown[Create a URL drilldown]

|Discover
|Discover, showing the documents behind the selected value.
|https://www.elastic.co/docs/explore-analyze/dashboards/create-discover-drilldown[Create a Discover drilldown]
|===

You need the *All* privilege for the Dashboard feature. Open the dashboard in edit mode, set the search, filter or time range that the drilldown should carry, open a panel menu and choose *Create drilldown*; then
save the dashboard and use the drilldown from a value on the panel. *Manage drilldowns* in the panel menu edits, copies (the copy's name ends in "(copy)") or deletes them; a panel can have
several drilldowns.

*Dashboard drilldown.* Choose *Go to dashboard*, name it, pick the destination and select *Use filters and query from origin dashboard* and/or *Use date range from origin dashboard*. It works on visualizations
that use a data view, ES|QL visualizations (from 9.4 on the Stack), Vega, Maps and the legacy TSVB, aggregation-based and Timelion panels. For Bookshelf the
standard pair is the overview dashboard drilling to a "Bookshelf route detail" dashboard filtered by `url.path`.

*Discover drilldown.* Choose *Open in Discover*, name it and decide whether to open it in a new tab (on by default). It works on data view visualizations and on ES|QL visualizations (generally available on
Serverless and on the Stack since 9.5). For an ES|QL panel, the dashboard filters and the KQL or Lucene query become a `WHERE` clause and filters that ES|QL cannot express are dropped. The same destination is
available without a drilldown: *Explore in Discover* in the panel menu (see the building page).

*URL drilldown.* Choose *Go to URL*, name it, pick a *Trigger* (preset when the panel offers only one), enter the URL template and, under *Additional options*, keep or change *Open URL in new tab* and *Encode URL*
(both on by default). ES|QL visualizations support URL drilldowns from 9.4 on the Stack. The template is an ordinary URL containing Handlebars expressions in double braces, which Kibana replaces when the
drilldown runs:

[source,text]
----
https://wiki.example.com/bookshelf/runbooks?route={{event.value}}&from={{context.panel.timeRange.from}}&to={{context.panel.timeRange.to}}
----

Reference: https://www.elastic.co/docs/explore-analyze/dashboards/create-url-drilldown[Kibana: Create a URL drilldown] (the page's own example is `+https://github.com/elastic/kibana/issues?q={{event.value}}+`). The host is a
placeholder for the lab; point it at your runbook system.

The variables the page documents:

* Global: `kibanaUrl`.
* Context (dashboard and panel): `context.panel.id`, `.title`, `.savedObjectId`, `.filters` (the dashboard filters, not the panel-only ones), `.query.query` and `.query.language`,
  `.timeRange.from` and `.to` (the panel range if set, else the dashboard range) and `.indexPatternIds`.
* Event: for a single click `event.value`, `event.key`, `event.negate`, `event.points`; for a table row `event.rowIndex`, `event.values.[x]`, `event.keys.[x]`, `event.columnNames.[x]`; for a range selection `event.from`, `event.to`, `event.key`.
* Helpers: `date` (moment patterns and relative values such as `now-15d`), `rison` and `json` (for example `+{{rison context.panel.filters}}+`), `formatNumber`, string helpers (`lowercase`, `uppercase`, `trim`, `mid`, `left`,
  `right`, `concat`, `replace`, `split`) and the encoders `encodeURIComponent` and `encodeURIQuery`.

Triggers by panel: *single click* (a pie slice or bar, on data view visualizations, ES|QL visualizations and Maps), *table row click*, *range selection* (bar, line, area, heat map and the legacy editors), *context menu*
(the only trigger for Vega, Discover and Gauge panels) and *image click* (Image panels). Because a runbook link should open to the page of the alert and not to the home page, the common design is a Markdown or Links panel for the static links
and a URL drilldown only where the value matters.

=== Limits that surprise people

* *Only indexed fields.* You cannot filter on, or drill down from, a value created at query time: a Lens formula, an aggregation result, an ES|QL `EVAL` or `STATS` result. From 9.5 (and on Serverless) you can work around it in ES|QL
  by naming an index field in the `+STATS ... BY+` clause or with `RENAME`. A table of "5xx ratio by route" drills fine on the route (an indexed field) and not on the ratio.
* A dashboard drilldown carries filters on fields, so a destination dashboard whose data views lack the filtered field has nothing to match.
* A Discover drilldown for ES|QL charts was disabled for a time and re-enabled in 9.5, and filters and drilldowns on ES|QL charts after a column rename were fixed in 9.5 (see the 9.5.0 release notes); test them
  after an upgrade.

Source for the last item: https://www.elastic.co/docs/release-notes/kibana[Kibana release notes] (9.5.0, Drilldowns).

== Verifying in the lab

. On "Bookshelf service health", pin an options list on `service.name` and `url.path`; pick `url.path` and confirm that the list of values narrows as soon as `service.name` is chosen.
. Move a log level options list into the "Logs and traces" section and confirm that choosing `ERROR` changes only that section.
. Add a time slider, narrow it to the minutes around the failing-request run of the load generator and watch the panels follow.
. On the "slowest routes" table create a dashboard drilldown to a copy of the dashboard that you saved as "Bookshelf route detail", with both *Use filters and query* and *Use date range*; click a route and check the filter pill.
. Add the Discover drilldown to the 5xx ratio chart, select a range and confirm that Discover opens with the same time range and the 5xx documents; add the URL drilldown above and read the final URL in the browser.

== In the books

Shah (_Kibana 8.x Quick Start Guide_, chapter 8) shows filtering a dashboard from the query bar and filter pills and clicking chart segments to drill into the data, and
nothing about controls or drilldown actions; the extracts of Chhajed (Kibana 4) and Melachi (Kibana 7) do not mention controls either. What has changed since: options list, range slider and time slider controls
are dashboard elements that can be pinned or placed in sections, chained and (as an ES|QL variant) substituted into queries, and drilldowns to a dashboard, a URL or Discover are configured per panel.
