:description: The Kibana dashboard panels beyond Lens: Maps, Vega and Vega-Lite custom visualizations with an ES|QL data source, Markdown, Image, Links, Alerts and custom panels, and the ML and SLO panels, with the Bookshelf uses and the availability of each.
:keywords: Kibana, Maps, Vega, Vega-Lite, Markdown panel, image panel, links panel, alerts panel, custom panel, SLO panel, anomaly swim lane, dashboard, Bookshelf

Checked on 2026-11-09 against Kibana 9.5.x.

A good service-health dashboard is not only charts. It needs a text panel that says what the dashboard is for and who owns it,
links to the runbook and to the next dashboard, the list of currently firing alerts and the SLO status, and now and then a chart
that no standard editor can draw. Kibana provides these as panels next to the Lens charts of
xref:backend/monitoring-alerting/kibana/lens.adoc[Lens]. This page covers each of them: what it is for, how to add it, how it
behaves on a dashboard and where it is limited. Layout and the dashboard as a whole are in
xref:backend/monitoring-alerting/kibana/building-dashboards.adoc[Building Dashboards], and the design reasoning (title, owner,
runbook link, signals ordered by importance) in
xref:backend/monitoring-alerting/dashboard-design-principles.adoc[Dashboard Design Principles]. The Grafana equivalents are in
xref:backend/monitoring-alerting/grafana/visualizations-logs-traces-and-special.adoc[Grafana Logs, Traces and Special Panels] and
xref:backend/monitoring-alerting/grafana/visualizations-stats-tables-and-widgets.adoc[Stats, Tables and Widgets].

Source: https://www.elastic.co/docs/explore-analyze/visualize[Kibana: Panels and visualizations] (the page that lists every panel type).

[[maps]]
== Maps

Source: https://www.elastic.co/docs/explore-analyze/visualize/maps[Kibana: Maps].

*What and when.* The Maps app builds geographic visualizations from several layers over several indices: vector layers that plot
documents or aggregated results, heat map layers for density, and tile layers for base maps. It can animate spatial-temporal data with
the *time slider*, ingest uploaded GeoJSON files and shapefiles into Elasticsearch, symbolize features by data values (size, colour,
icon), and filter with KQL, the time picker or a drawn polygon. A map can be embedded in a dashboard. An ES|QL layer, added from the
*Add layer* menu, draws the geo field of an ES|QL result; on the dashboard, a bolt badge appears when a layer's `STATS` query is
approximated, and a *Custom CPS scope* badge when a query overrides the cross-project routing on Serverless. Maps is generally
available on Serverless and on the Stack; approximation is a Serverless preview and Planned on the Stack, and cross-project search
is Serverless only.

*Bookshelf.* The book catalogue has no geographic data, so the lab has no map. A realistic monitoring use is "where do the failing
requests come from": with `client.geo.location` mapped as a `geo_point` (see
xref:database/elasticsearch/geospatial.adoc[Geospatial]) a vector layer filtered on `http.response.status_code >= 500` shows the clusters,
and the time slider replays an incident. Maps needs a `geo_point` or `geo_shape` field; without one there is nothing to draw, and a
chart with latitude and longitude as plain numbers will not work.

*What can go wrong.* Too many overlapping layers and colours make a map unreadable (Shah makes the same point), and the global time only narrows
layers that query Elasticsearch through a data view with a time field.

[[vega]]
== Vega and Vega-Lite

Source: https://www.elastic.co/docs/explore-analyze/visualize/custom-visualizations-with-vega[Kibana: Custom visualizations with Vega].

*What and when.* Vega and Vega-Lite are declarative grammars: a JSON or HJSON specification defines data, transforms and marks,
and Kibana renders it with the dashboard's filters and time range. Vega-Lite is the easier start; the two are not compatible. The
Elastic page tells you to try Lens and ES|QL visualizations first and Maps for geography, and to use Vega when you need chart types
the others lack (scatter plots, Sankey diagrams, custom themes), aggregations without a data view, nested or parent/child
aggregations, custom time filters, data from `_source`, or several data sources in one panel. Vega does not render tables, cannot
run queries conditionally and fetches all data before rendering. Add a *Vega* panel (labelled *Custom visualization* in some
versions) from the dashboard's *Add* menu.

*Data sources.* An ES|QL query (recommended), an Elasticsearch Query DSL search, Elastic Map Service shapes (`emsfile`), an external
URL (needs `vis_type_vega.enableExternalUrls: true` in `kibana.yml` and CORS headers on the remote host) or inline values.

*ES|QL source.* Set `%type%: esql` and a `query` in the `url` object. Optional keys are `%context%` (apply the dashboard
filters), `%timefield%` (the field for the dashboard time range), `dropNullColumns` (default `true`) and `params` (named
parameters, including defaults for variable controls). The result is converted from columns to one object per row. From 9.5
(GA) Kibana filters on `@timestamp` automatically and `%timefield%` selects another field; on 9.4 the query must reference `+?_tstart+`
and `+?_tend+` and set `%timefield%`. This spec draws the Bookshelf error logs per time bucket and works on both:

[source,hjson]
----
{
  $schema: https://vega.github.io/schema/vega-lite/v5.json
  title: Bookshelf error logs
  data: {
    url: {
      %type%: esql
      %timefield%: @timestamp
      query: '''
        FROM logs-*
        | WHERE log.level == "ERROR"
        | STATS errors = COUNT(*) BY bucket = BUCKET(@timestamp, 50, ?_tstart, ?_tend)
        | SORT bucket
      '''
    }
  }
  mark: {type: line, point: true}
  encoding: {
    x: {field: bucket, type: temporal, title: null}
    y: {field: errors, type: quantitative}
  }
}
----

Reference: https://www.elastic.co/docs/explore-analyze/visualize/custom-visualizations-with-vega#vega-esql-queries[Kibana: Vega ES|QL queries].
Use the field names your data view shows. Variable controls can feed a Vega query (`+?name+` and `+??name+`); that is a Serverless preview and
Planned on the Stack, and a `params` entry is needed wherever no dashboard control exists, because a variable with no value is an error.

*Query DSL source.* The `url` object accepts `%context%: true` (dashboard filters), `%timefield%: <field>`, and the tokens
`+{%timefilter%: true}+` (expands to a range query) and `+{%autointerval%: true}+` (an automatic interval). The `interval` parameter
is not supported on Elasticsearch 8.0 and later, so use `fixed_interval` or `calendar_interval`. When `%context%` or
`%timefield%` is set the body must not contain its own `query`. Source:
https://www.elastic.co/docs/explore-analyze/visualize/custom-visualizations-with-vega#vega-queries[Kibana: Vega queries].

*Interactivity and debugging.* Vega expression functions `kibanaAddFilter`, `kibanaRemoveFilter`, `kibanaRemoveAllFilters`
and `kibanaSetTimeFilter` let a click or a drag update the dashboard's filters and time range (see the tutorial *Update Kibana
filters from Vega* on the page). *Inspect* shows the Elasticsearch requests, the Vega debug view with data sets and signals, and the spec. Small edits to a
spec often produce surprising results, so save often and build up in steps. A map specification (`config.kibana.type: map`) and
Elastic Map Service shapes are preview features, and the default gradient on area marks without a fill is Serverless-only for now
(Planned on the Stack).

*What can go wrong.* A spec is code that nobody on the team may know how to maintain: prefer Lens, and keep Vega for the one chart
that needs it. Parameters that look right but are ignored (for example a `query` next to `%context%`) are the usual cause of a
chart that ignores the dashboard filters.

[[markdown]]
== Markdown text

Source: https://www.elastic.co/docs/explore-analyze/visualize/text-panels[Kibana: Add Markdown text to dashboards].

A Markdown panel (GitHub-flavoured) adds context: what the dashboard shows, the owner and the on-call rota, how to read the
panels, links to runbooks and to related dashboards, an embedded image. Add it with *Add*, *New panel*, *Markdown Text*
(9.2 and later; *Add panel*, *Text* in 9.0 and 9.1), type in the *Editor*, check the *Preview* and choose *Apply*. Since 9.4 a panel can be saved to the
Visualize library with *Save to library* and reused on several dashboards, so that a single edit to the runbook link updates every
dashboard; *Unlink from library* turns it back into a private copy. It is generally available on Serverless and since 9.0 on the Stack.
For Bookshelf, put the runbook link of each alert next to the panel it belongs to; an alert that fires should land on a
dashboard that says what to do (see xref:backend/monitoring-alerting/designing-actionable-alerts.adoc[Designing Actionable Alerts]).

[[image]]
== Image

Source: https://www.elastic.co/docs/explore-analyze/visualize/image-panels[Kibana: Add images to dashboards].

An Image panel shows a logo or a diagram. Choose *Image* from the *Add* menu (*Add panel* in 9.0 and 9.1) and upload a file, select
one you uploaded before, or use an external link; uploads are capped at 10 MiB and are managed on the *Files* page. Exporting a
dashboard does not include the uploaded files, so an imported dashboard shows a "not found" warning until the image is uploaded again in
the panel editor; use that when planning the move of dashboards between spaces (see
xref:backend/monitoring-alerting/kibana/sharing-reporting-and-saved-objects.adoc[Sharing, Reporting & Saved Objects]). It is generally
available on Serverless and on the Stack.

[[links]]
== Links

Source: https://www.elastic.co/docs/explore-analyze/visualize/link-panels[Kibana: Add links to dashboards].

A Links panel lists links, laid out vertically or horizontally, to other dashboards or to external sites. A dashboard link can carry the
filters, queries and time range of the current dashboard and can open in a new tab, which is how an overview dashboard hands
off to a detail dashboard at the same time window; a URL link follows the `externalUrl.policy` settings of the Kibana server and
can be encoded. The panel can be saved to the library and reused. It is generally available on Serverless and on the Stack. The
other navigation mechanism, drilldowns from a chart, is in
xref:backend/monitoring-alerting/kibana/controls-and-drilldowns.adoc[Controls & Drilldowns].

[[alerts]]
== Alerts

Source: https://www.elastic.co/docs/explore-analyze/visualize/alert-panels[Kibana: Add alerts to dashboards].

The Alerts panel shows alerts on the dashboard, filtered by rule tags or rule types, with an optional second filter joined by AND
or OR. On the Stack you choose the solution (Observability or Security) when you add it. From
the row menu you can open the rule or alert details and, for alerts of active rules, snooze, mute, mark as untracked or
acknowledge. Availability: generally available on the Stack since 9.1 (acknowledge since 9.4 and snooze since 9.5, mute until
9.4) and on Serverless without mute. Tag every Bookshelf rule with `bookshelf` and a panel filtered on that tag turns the service
dashboard into the place where the five lab alerts are seen next to the data. The alert states and actions are explained in
xref:backend/monitoring-alerting/kibana/alert-lifecycle-snooze-and-maintenance-windows.adoc[Alert Lifecycle, Snooze & Maintenance Windows].

[[custom]]
== Custom panels

Source: https://www.elastic.co/docs/explore-analyze/visualize/custom-panels[Kibana: Custom panels].

A custom panel is an HTML and CSS template with an optional ES|QL query whose rows are inserted with Liquid tags (`rows`, `max`, with
`.value` and `.pct` for numeric columns); the Elastic Agent Builder can write or refine the template from a chat description, but
rendering does not call the model again. It exists for layouts that the standard panels cannot produce, such as status boards,
scorecards with coloured badges or banners. It is a preview feature on Serverless and Planned on the Stack, so it is not available on
9.5. The documented limits are worth knowing in advance: templates render in a sandbox without JavaScript or external scripts, fonts
and images; a template is limited to 500 KB; one ES|QL query per panel; links must be Kibana paths under `/app/dashboards` or
`/app/discover` and carry no time range or filters (use the Links panel for that); and custom panels cannot be saved to the library.

[[ml-slo]]
== Machine learning and SLO panels

Source: https://www.elastic.co/docs/explore-analyze/visualize[Kibana: Panels and visualizations] (machine learning and observability sections).

* From machine learning: the *Anomaly swim lane*, the *Anomaly chart* and the *Single metric viewer* show anomaly detection job
  results, and a *Change point detection* panel shows change points; see
  xref:backend/monitoring-alerting/kibana/machine-learning-and-aiops.adoc[Machine Learning & AIOps].
* From Observability: *SLO overview* (health, current SLI, target and status of one SLO), *SLO Alerts* (alerts of one or more SLOs, with
  actions to configure alerts or create cases) and *SLO Error Budget* (how much budget is consumed); see
  xref:backend/monitoring-alerting/kibana/slos.adoc[SLOs]. These three panels are the Kibana way to put the burn-rate story of
  the lab next to the latency chart.
* Discover sessions can also be added as a panel (generally available on the Stack since 9.4), which puts the matching log lines
  below the chart.

== Verifying in the lab

. On the Bookshelf dashboard add a Markdown panel with the owner, the on-call contact and a link to the runbook; save it to
  the library and add it to a second dashboard.
. Add a Links panel with a dashboard link that keeps the time range, click it and confirm that the target opens on the
  same window.
. Tag a lab rule with `bookshelf`, add an Alerts panel filtered on the tag, stop the application and watch the alert appear.
. Add the Vega spec above and use *Inspect*, then *Vega debug*, to see the data set; change the time picker and check that the chart follows.

== In the books

Shah (_Kibana 8.x Quick Start Guide_, chapter 4) walks through Maps (layers, the documents layer, a `geo_point` field,
styling) and Markdown visualizations (a text panel with a link to the next dashboard), and builds Canvas workpads; Paro (_Elasticsearch
7.0 Cookbook_, chapter 11) lists the built-in widgets, including Markdown, Vega, Coordinate Map and Region Map. What has changed since: the book lists
predate the Image, Links, Alerts, SLO and custom panels, Markdown is now a dashboard panel, Vega gained an ES|QL data source, and the
coordinate and region maps of older releases are replaced by the Maps app and the Lens region map (Canvas is covered in
xref:backend/monitoring-alerting/kibana/legacy-editors-canvas-and-graph.adoc[Legacy Editors, Canvas & Graph]).
