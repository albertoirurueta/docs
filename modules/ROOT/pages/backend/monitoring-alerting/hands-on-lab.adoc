= Hands-on Lab
:description: One Docker Compose file with two profiles, grafana and kibana, that runs a Bookshelf stand-in, a load generator, a webhook receiver and either the Grafana stack (Alloy, Prometheus, Loki, Tempo, Grafana 13.3) or the Elastic stack (EDOT Collector, Elasticsearch 9.5.6, Kibana 9.5.6), with every file listed and the five alert breaches forced on demand.
:keywords: hands-on lab, Docker Compose, profiles, Grafana 13.3, Kibana 9.5, Alloy, Prometheus, Loki, Tempo, EDOT Collector, Elasticsearch, load generator, webhook receiver, Bookshelf, fault injection

include::partial$ai-disclaimer.adoc[]

Checked on 2026-11-09 against Grafana 13.3.x and Kibana 9.5.x. Tested with Grafana Enterprise 13.3.0 (the free image, no licence key) and with Elasticsearch and Kibana 9.5.6 on Docker Desktop with 8 GB of memory.

Every other page in this section ends with a "Verify it in the lab" step. This page is the lab: a single Compose project that starts
the same application, the same traffic and the same notification receiver in front of either monitoring stack, so that a dashboard or an alert
built in Grafana can be compared line by line with the one built in Kibana. Nothing here is specific to a cloud account, a licence key
or an outbound network connection once the images are pulled.

== What the lab contains

[cols="2,3,3",options="header"]
|===
|Service |Role |Profile and port

|`bookshelf`
|A small stand-in for the Bookshelf Spring Boot service (see the note below). Serves `/api/books`, `+/api/books/{id}+`, `/api/loans` and `/api/search`, exposes Micrometer-style metrics at `/actuator/prometheus`, writes JSON log lines to a file and to stdout, and exports traces and logs over OTLP.
|both; 8080

|`loadgen`
|Sends about ten requests per second. A control endpoint switches the traffic between `normal`, `failing`, `slow`, `log-errors` and `stop`.
|both; 8090

|`webhook-receiver`
|Accepts any POST, prints it as one `WEBHOOK` line and keeps the last 50 deliveries, which any GET returns as JSON. Grafana posts to `/grafana`, Kibana to `/kibana`. Inside the network it also answers to the name `webhook.lab`, because the webhook connector form of Kibana 9.5 rejects a host name without a dot.
|both; 8081 on the host, 8080 inside the network

|`postgres`
|Holds the placeholder tables `book` and `loan` that the Grafana data source pages query.
|grafana

|`alloy`
|Grafana Alloy: receives OTLP traces and forwards them to Tempo, and tails the JSON log file into Loki with the label `application="bookshelf"`.
|grafana; 12345 for its own UI

|`prometheus`
|Scrapes `bookshelf:8080/actuator/prometheus` every 15 seconds. Started with `--web.enable-remote-write-receiver`, so Tempo's span metrics and recording rules can be written to it.
|grafana; 9090

|`loki`, `tempo`
|Single-binary log and trace stores on local disk. Tempo's metrics generator writes span metrics to Prometheus.
|grafana; 3100 and 3200

|`grafana`
|Grafana Enterprise 13.3.0 image (it runs as the open-source edition without a licence). Data sources, the dashboard and the alerting resources are provisioned from files. Alert state history is stored in Loki.
|grafana; 3000

|`edot-collector`
|The Elastic Distribution of OpenTelemetry Collector in gateway mode: OTLP in, the `elasticapm` components for the APM views, Elasticsearch out.
|kibana

|`elasticsearch`, `kibana-setup`, `kibana`
|Elasticsearch 9.5.6 with security on and a self-generated trial licence, a one-shot service that sets the `kibana_system` password, and Kibana 9.5.6.
|kibana; 9200 and 5601
|===

image::monitoring-alerting-lab-topology.svg["Lab topology: loadgen drives bookshelf; bookshelf feeds Alloy, Prometheus, Loki, Tempo and Grafana in one profile or the EDOT Collector, Elasticsearch and Kibana in the other; both notify the webhook receiver",width=900]

The Bookshelf service in the lab is a stand-in written in about 150 lines of Python with no dependencies, not the Spring Boot
application. It produces what the monitoring pages need: the metric names and labels that Micrometer publishes
(`http_server_requests_seconds_count`, `_sum` and `_bucket` with `application`, `method`, `outcome`, `status` and `uri`, plus
`hikaricp_connections_active`, `hikaricp_connections_max` and `jvm_memory_used_bytes`), JSON log lines with `level`, `message`, `uri`,
`status`, `trace_id` and `span_id`, and one OTLP trace span per request with the OpenTelemetry HTTP attributes. Its failures are
on demand and repeatable, which a real application's are not. For the real setup of Spring Boot see
xref:backend/springboot/metrics-and-observability.adoc[Metrics and Observability],
xref:backend/springboot/logging.adoc[Logging] and the other Bookshelf pages linked from there.

Source: https://docs.docker.com/compose/how-tos/profiles/[Docker: Using profiles with Compose] (services with a `profiles` list start only
when a profile is selected; a service without one always starts),
https://grafana.com/docs/grafana/latest/setup-grafana/installation/docker/[Grafana: Run Grafana Docker image] and
https://www.elastic.co/docs/deploy-manage/deploy/self-managed/install-kibana-with-docker[Elastic: Install Kibana with Docker].

== Requirements

* Docker with the Compose plugin (version 2.20 or later). The files were run with Docker Desktop 29.9 and Compose v2.
* Memory: the `grafana` profile used about 1 GB in total; the `kibana` profile needs 4 GB or more (Elasticsearch alone is capped at 2 GB).
  Give Docker Desktop at least 6 GB if you run the Kibana profile. Start one profile at a time; they are built to be alternatives.
* Free host ports 3000, 3100, 3200, 5601, 8080, 8081, 8090, 9090, 9200 and 12345.
* Images are pulled on the first start: roughly 3 GB for the `grafana` profile and 4 GB for the `kibana` profile.
* The tools `curl` and `jq` on the host for the verification commands.

== Start the grafana profile

[source,bash]
----
cd lab
docker compose --profile grafana up -d
docker compose --profile grafana ps
----

Wait about one minute, then check each component:

[source,bash]
----
curl -s http://localhost:3000/api/health                 # Grafana: "database": "ok", version 13.3.0
curl -s http://localhost:9090/-/ready                    # Prometheus
curl -s http://localhost:3100/ready                      # Loki ("ready" after about 15 seconds)
curl -s http://localhost:3200/ready                      # Tempo
curl -s http://localhost:9090/api/v1/targets | jq -r '.data.activeTargets[] | "\(.labels.job) \(.health)"'
curl -s -u admin:admin http://localhost:3000/api/datasources | jq -r '.[] | "\(.uid) \(.type)"'
curl -s -u admin:admin http://localhost:3000/api/v1/provisioning/alert-rules | jq -r '.[].title'
----

Expect the targets `bookshelf up` and `prometheus up`, the data sources `prometheus`, `loki`, `tempo` and `testdata`, and five rule titles.
Grafana is at http://localhost:3000 (user `admin`, password `admin`, from `GF_SECURITY_ADMIN_PASSWORD` in `compose.yaml`; change it in
the UI if you expose the port). Open *Dashboards* and the folder `bookshelf` for "Bookshelf service health", and *Alerting* for the five
rules. A rule file whose folder does not exist creates it, and the dashboard provider finds the same folder by title, so the folder
`bookshelf` exists once; its uid is generated.

To check the telemetry paths:

[source,bash]
----
curl -s -G http://localhost:9090/api/v1/query --data-urlencode 'query=sum(rate(http_server_requests_seconds_count{application="bookshelf"}[1m]))' | jq '.data.result[0].value[1]'
curl -s -G http://localhost:3100/loki/api/v1/query_range --data-urlencode 'query={application="bookshelf"} | json' --data-urlencode limit=1 | jq '.data.result[0].stream.level'
curl -s 'http://localhost:3200/api/search?limit=1' | jq '.traces[0].rootTraceName'
----

== Start the kibana profile

Stop the other profile first (`docker compose --profile grafana down`), then:

[source,bash]
----
docker compose --profile kibana up -d
until curl -fsS http://localhost:5601/api/status >/dev/null; do sleep 5; done
----

The one-shot `kibana-setup` service exits after setting the `kibana_system` password; `docker compose ps -a` shows it as exited with code 0.
Kibana takes one to two minutes to become ready. Log in at http://localhost:5601 as `elastic` with the password from `.env`.
The self-generated trial licence is requested by `xpack.license.self_generated.type=trial`: webhook connectors need a Gold or higher
licence and maintenance windows need Platinum, so on a Basic licence those two features are unavailable. Check it with
`curl -s -u elastic:lab-elastic-password http://localhost:9200/_license | jq .license.type`, which prints `trial`. The trial lasts 30 days from the first start.

Once the load generator has run for a minute or two, create the Kibana objects (the space `bookshelf`, the data views, the webhook connector,
the five rules, the SLO, the maintenance window and the dashboard) with `kibana/setup.sh`. It needs `curl` and `jq`, and reads `ELASTIC_PASSWORD`
(default `lab-elastic-password`) and `KIBANA_URL` (default `http://localhost:5601`), so export the values from `.env` first:

[source,bash]
----
set -a; . ./.env; set +a
bash kibana/setup.sh
----

== Force the five breaches

The load generator listens on port 8090. A request to `/mode/<name>` changes the traffic for every later request; `GET /` shows the current mode. The other pages of this section call the `failing` mode the failing-request mode and the `slow` mode the slow mode.

[cols="2,3,3,3",options="header"]
|===
|Alert |Command |What changes |Where to look

|High 5xx ratio
|`curl -X POST localhost:8090/mode/failing`
|70 percent of the requests answer 500 and log an ERROR line.
|5xx ratio panel; the rule goes pending, then firing once the condition has held for its pending period.

|p95 latency above the SLO
|`curl -X POST localhost:8090/mode/slow`
|Every request takes 0.7 to 1.5 seconds, so the 95th percentile passes 0.5 s.
|p95 panel and the latency rule.

|No data
|`docker compose stop bookshelf loadgen`
|The `up` series turns 0 and the request series vanish; the Kibana trace and log counts fall to 0.
|The no-data rule; restart with `docker compose start bookshelf loadgen`.

|Error-log spike
|`curl -X POST localhost:8090/mode/log-errors`
|Every request answers 200 and logs an ERROR line, so only the log rule reacts.
|The error-log rule and the "Error logs" panel.

|SLO burn rate
|`curl -X POST localhost:8090/mode/failing`, and keep it running
|The 5xx ratio is far above 0.072 in both the 5 minute and the 1 hour window.
|The burn rate rule; in Kibana the SLO page.
|===

Return to healthy traffic with `curl -X POST localhost:8090/mode/normal`. The measured delays between the change and the first notification at the
receiver are on the two end-to-end pages. Read the deliveries with `docker compose logs --no-log-prefix webhook-receiver` (one `WEBHOOK` line each)
or `curl -s localhost:8081`, which returns the last 50 as JSON.

== Stop and clean up

[source,bash]
----
docker compose --profile grafana --profile kibana down -v
docker ps -a
----

`down -v` removes the containers, the network and the named volumes (`grafana-data`, `esdata` and the log volume), which is what you want
after an experiment: Elasticsearch data and the trial licence start from zero on the next start. Without `-v` the volumes survive,
so provisioned files that you changed are not applied to an existing Grafana database as new resources unless their `uid` is new.

== What can go wrong

* *The `kibana` profile restarts or exits with code 137.* Elasticsearch ran out of memory: raise the Docker Desktop memory or lower the load.
* *Kibana answers 503 for a while.* It waits for Elasticsearch to be healthy and then migrates saved objects; check `docker compose logs kibana` and wait.
* *Both profiles started together.* Both define the alias `otel-gateway`, so Bookshelf's OTLP traffic would go to either one; always start one profile at a time.
* *The Alloy container exits on start.* Components marked experimental are refused by default; the lab configuration uses only generally available components.
* *Rules exist but never fire.* Check *Alerting*, *Alert rules* for the evaluation state and for health errors; a query error is shown on the rule, and the
  Prometheus data source must have uid `prometheus`.
* *Webhook deliveries are missing.* Read `docker compose logs webhook-receiver` first; then the contact point or connector test; a request that
  never arrives usually means a typo in the host name (`webhook-receiver`, port 8080, paths `/grafana` and `/kibana`).
* *Changing `.env` has no effect on Elasticsearch passwords.* The `elastic` password is set on the first start with an empty `esdata` volume; run `docker compose down -v` to reset it.
* *Dashboards that were edited in the UI revert.* The provider has `allowUiUpdates: false`; edit the JSON file instead.

== In the books

Hands-on chapters of Grafana books use Docker containers for their data sources in the same way; Salituro's _Learn Grafana 10.x_ launches
its server containers at the start of the dashboard-design chapter and feeds them an InfluxDB data set. The lab here replaces InfluxDB and the
older Graphite and Telegraf examples with Prometheus, Loki and Tempo behind Alloy, which is the stack Grafana documents for new installations,
and adds the Elastic side that the books treat as a separate Beats and Logstash world.
