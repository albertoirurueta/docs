Welcome to the MySQL reference. https://www.mysql.com/[MySQL] is an open-source *relational database server*: it
stores data in tables, is queried with SQL, and uses the InnoDB storage engine to provide ACID transactions,
row-level locking, foreign keys and crash recovery. It powers a very large share of web applications and is
available as a free Community Edition, a commercial Enterprise Edition and an Oracle-hosted cloud service. This
section is a database-developer and operator reference for the MySQL server itself: how it is built, how to design
tables and indexes for it, how to read query plans, how transactions and locks behave, how to run, back up and
replicate it, and how to tune it. It is written for application developers who use MySQL every day and for the
people who operate it.

https://mariadb.org/[MariaDB] is a separate fork of MySQL whose features have diverged; it is not covered here, and
statements, defaults and file layouts that are described for MySQL should not be assumed to hold for MariaDB.

If you are new to MySQL, read xref:database/mysql/getting-started.adoc[Getting Started] first, then
xref:database/mysql/architecture.adoc[Architecture] and
xref:database/mysql/data-types-and-sql.adoc[Data Types & MySQL-specific SQL]. Everything else builds on those.
Engine-agnostic SQL (joins, subqueries, window functions) is on the sibling
xref:database/sql/index.adoc[SQL Reference], which the MySQL pages link to instead of repeating.

== Version baseline

The examples in this reference were run on *MySQL 26.10.0 Community Server*, obtained as the official `mysql:latest`
Docker image (Linux, arm64). That is an *Innovation* release; MySQL publishes two release tracks, and the Docker
image tags at the time of writing map as follows:

[cols="2,2,3"]
|===
| Track | Version | Docker tags

| Innovation | 26.10.0 | `latest`, `innovation`, `26`, `26.10`
| LTS | 9.7.4 | `lts`, `9`, `9.7`
| LTS | 8.4.13 | `8`, `8.4`
|===

*LTS* releases only receive necessary fixes and are supported for five years of premier plus three of extended
support; *Innovation* releases bring new features and are supported until the next Innovation release. Use an LTS
for long-lived production systems. Everything described here is available on every maintained release unless a page
says otherwise (for example window functions and CTEs need 8.0 or later), but a few defaults were *observed* on this
server and are worth checking on your own version:

* `explain_format` defaults to `TREE`, so a bare `EXPLAIN` prints a tree; use `SET explain_format = TRADITIONAL`
  for the table form.
* The `mysql` client in the image has local commands such as `\G` and `source` *disabled* unless started with
  `--commands`.
* The adaptive hash index is off by default, `gtid_mode` is `ON`, and the redo log capacity default is 100 MiB.

All results shown on the pages come from this server; they are trimmed where long, and the page says so. Numbers
(timings, sizes, row estimates) will differ on your hardware, but the shape of the plans and behaviour should match.
The manual is versioned, so use the matching one: https://dev.mysql.com/doc/refman/26.10/en/[26.10],
https://dev.mysql.com/doc/refman/8.4/en/[8.4 LTS].

* xref:database/mysql/cheat-sheet.adoc[Cheat Sheet] -- a single-page quick reference for the commands, statements and
  settings used throughout this section.

*Deliberately out of scope.* This section documents the MySQL server and its SQL, indexing, transaction and
operations model. The following appear in many books on MySQL but are intentionally not covered here:

* *MariaDB* -- a separate fork with diverging features; see the MariaDB documentation.
* *NDB Cluster* (`ndbcluster`) -- a different, shared-nothing product; the Community server in the Docker image
  lists the engine as not enabled.
* *MySQL Enterprise-only features* -- Enterprise Audit, Firewall, Thread Pool, Transparent Data Encryption, Enterprise
  Backup and Oracle support tooling.
* *HeatWave* -- Oracle's managed in-memory analytics and machine-learning service; mentioned only as an edition.
* *Cloud-managed services* -- Amazon RDS and Aurora, Google Cloud SQL, Azure Database for MySQL and the like. Their
  parameter groups and failover behave differently from a self-run server.
* *Installers per operating system* -- native packages, MSI, Homebrew and so on; the manual's installation chapter is
  authoritative and this section runs the server in a container, see
  xref:backend/docker/index.adoc[Docker].
* *MyISAM and other non-transactional engines* -- mentioned as history on the Architecture page only; new tables
  should use InnoDB.
* *Application object mapping* -- see xref:backend/hibernate/index.adoc[Hibernate] for JPA mapping onto MySQL.

== Running example

All pages share one small online shop: four tables, `customers`, `products`, `orders` and `order_items`, holding
4 customers, 5 products, 8 orders and 11 order lines. The full script and the commands that load it are on
xref:database/mysql/getting-started.adoc[Getting Started]; the same data model is used by the
xref:database/mongodb/index.adoc[MongoDB] and PostgreSQL sections so the engines can be compared.

[mermaid]
....
erDiagram
  CUSTOMERS ||--o{ ORDERS : places
  ORDERS ||--|{ ORDER_ITEMS : contains
  PRODUCTS ||--o{ ORDER_ITEMS : "appears in"
  CUSTOMERS {
    varchar id PK
    varchar name
    varchar email UK
    varchar city
    varchar tier
    datetime created_at
  }
  PRODUCTS {
    varchar sku PK
    varchar name
    varchar category
    decimal price
    int stock
    json tags
    json attrs
  }
  ORDERS {
    int id PK
    varchar customer_id FK
    varchar status
    datetime order_date
  }
  ORDER_ITEMS {
    int order_id PK
    varchar sku PK
    int qty
    decimal price
  }
....

* `customers` -- people who buy, with a `tier` of `free`, `pro` or `enterprise` (a `CHECK` constraint) and a unique
  e-mail.
* `products` -- items for sale, identified by `sku`, with a `price`, a `stock` count and two `JSON` columns, `tags`
  (an array) and `attrs` (an object), used on the JSON page.
* `orders` -- one per purchase, pointing at a customer, with a `status` of `open`, `shipped` or `cancelled`.
* `order_items` -- the lines of an order; its primary key is the pair `(order_id, sku)` and it carries the price
  charged at the time.

Pages add generated data (a recursive CTE creating hundreds of thousands of rows) only where an index or plan
demonstration needs volume, in a separate `lab` database.
