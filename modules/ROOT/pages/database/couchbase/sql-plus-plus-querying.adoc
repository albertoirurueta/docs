:keywords: couchbase, sql++, n1ql, query service, cbq, query workbench, cluster.query, keyspace, USE KEYS, SELECT RAW, UNNEST, NEST, ANSI JOIN, lookup join, index join, WITH, recursive CTE, LET, LETTING, ANY, EVERY, ARRAY, FIRST, query plan, optimizer, index selection, query execution

*SQL++* (formerly *N1QL*) is Couchbase's query language: SQL's `SELECT` generalised to schemaless JSON --
nested objects, arrays, and values that may be `NULL`, `MISSING`, or a different type in every document.
Statements run on the *Query service*, a stateless tier that parses and plans each request and reads data
through the Index and Data services.

== The Query service and how you run a statement

A SQL++ statement targets a *keyspace* -- the bucket / scope / collection path, such as the `airline`
collection in the `inventory` scope of the `travel-sample` bucket. Any name containing a hyphen is
wrapped in backticks, as in the examples below. You submit a statement in one of several ways:

----
# cbq -- the interactive query shell shipped with the server
$ cbq -engine=http://localhost:8093 -u Administrator -p password
cbq> SELECT name FROM `travel-sample`.inventory.airline LIMIT 3;

# the /query/service REST endpoint (what every client ultimately calls)
$ curl -s http://localhost:8093/query/service \
    -u Administrator:password \
    --data-urlencode 'statement=SELECT name FROM `travel-sample`.inventory.airline LIMIT 3'
----

The Query Workbench in the web console runs the same statements with a result grid and a visual plan. From
an SDK you call `+cluster.query(...)+` for a statement that names its keyspaces in full, or
`+scope.query(...)+` to resolve unqualified collection names against a scope:

----
// Java SDK -- named parameters, never string-concatenated input
QueryResult r = cluster.query(
    "SELECT a.name FROM `travel-sample`.inventory.airline a WHERE a.country = $country",
    queryOptions().parameters(JsonObject.create().put("country", "France")));

// scope-level: the unqualified `airline` resolves inside inventory
Scope inventory = cluster.bucket("travel-sample").scope("inventory");
inventory.query("SELECT name FROM airline WHERE country = $1",
    queryOptions().parameters(JsonArray.from("France")));
----

`USE KEYS` turns a query into a direct key-value lookup with no index scan when the document keys are
already known:

----
SELECT * FROM `travel-sample`.inventory.airline
USE KEYS ["airline_10", "airline_10748"];
----

SQL++ generalises SQL to JSON in a few ways
(https://docs.couchbase.com/server/current/n1ql/n1ql-language-reference/index.html[SQL++ language
reference]):

* *Nested-path navigation.* `geo.accuracy` and `schedule[0].day` reach into objects and arrays with dotted
  and subscripted paths.
* *`MISSING` vs. `NULL`.* An absent field evaluates to `MISSING`, distinct from an explicit `NULL`,
  and both differ from a present value. `IS MISSING`, `IS NULL` and `IS VALUED` test the three
  states; `IFMISSING()` and `IFMISSINGORNULL()` collapse them.
* *Heterogeneous results.* Rows in one result need not share a shape; a projection can return an object, a
  bare scalar (`SELECT RAW`), or a nested array.

For the relational starting point this builds on, see xref:database/sql/dml-queries.adoc[SQL Queries
(SELECT)].

== The SELECT clause set

The clause set and its evaluation order mirror SQL
(https://docs.couchbase.com/server/current/n1ql/n1ql-language-reference/selectintro.html[SELECT syntax]):

----
SELECT   r.airline, COUNT(*) AS routes, AVG(r.distance) AS avg_km
FROM     `travel-sample`.inventory.route AS r
WHERE    r.stops = 0
GROUP BY r.airline
HAVING   COUNT(*) > 100
ORDER BY routes DESC
LIMIT    10
OFFSET   0;
----

`SELECT RAW` (synonym `SELECT VALUE`) unwraps the single projected expression, so the result is an array
of bare values instead of an array of one-field objects -- ideal for feeding an `IN` list or an SDK
`+List<String>+`:

----
SELECT RAW a.name
FROM `travel-sample`.inventory.airline AS a
WHERE a.country = "France";
-- ["Air France", "Aigle Azur", ...]
----

=== Avoiding large offsets

`LIMIT`/`OFFSET` still requires the Query service to scan and discard the first `OFFSET` rows before it can
return the requested page, so deep pagination gets progressively slower. Paginate with a *seek query* on a
unique indexed field instead, carrying the last seen key forward -- no `OFFSET` at all. The field must really
be indexed for the seek to be cheap; the sample `route.id` is not, so those two statements scan and sort. The
document key is always indexed by the primary index, which makes it the natural seek field (a worked example
with its plan is under <<worked-shop,Worked example: querying the shop>>):

----
-- page 1
SELECT r.id, r.airline, r.distance
FROM `travel-sample`.inventory.route AS r
ORDER BY r.id
LIMIT 20;

-- next page: start after the last id seen, no OFFSET
SELECT r.id, r.airline, r.distance
FROM `travel-sample`.inventory.route AS r
WHERE r.id > $lastKey
ORDER BY r.id
LIMIT 20;
----

See xref:database/pagination-strategies.adoc[Pagination: Offset vs. Keyset] for why this matters and how the same
pattern applies across SQL, MongoDB, Solr, Elasticsearch, GraphQL and Spring Data.

Nested paths and array subscripts appear anywhere an expression is allowed:

----
SELECT h.name, h.geo.lat, h.geo.lon, h.reviews[0].ratings.Overall AS first_rating
FROM `travel-sample`.inventory.hotel AS h
WHERE h.geo.accuracy IS VALUED AND h.reviews[0].ratings.Overall IS VALUED;
----

*`UNNEST`* flattens an array-valued field into one row per element, joining each element back to its
parent row:

----
SELECT r.sourceairport, s.day, s.flight
FROM `travel-sample`.inventory.route AS r
UNNEST r.schedule AS s
WHERE r.airline = "AF"
LIMIT 5;
----

*`NEST`* is the inverse: it gathers matching documents from another keyspace into an array field on each
left-hand row
(https://docs.couchbase.com/server/current/n1ql/n1ql-language-reference/nest.html[NEST clause]):

----
SELECT a.name, ARRAY_LENGTH(routes) AS route_count
FROM `travel-sample`.inventory.airline AS a
NEST `travel-sample`.inventory.route AS routes
  ON routes.airlineid = META(a).id
LIMIT 5;
----

== Joins

SQL++ offers three join styles
(https://docs.couchbase.com/server/current/n1ql/n1ql-language-reference/join.html[JOIN clause]).

*Lookup join -- `ON KEYS`.* The right-hand keyspace is reached by document key computed from the left
row. Fast, and no index on the right side is needed, but the join key must be a document key:

----
SELECT r.sourceairport, r.destinationairport, a.name
FROM `travel-sample`.inventory.route AS r
JOIN `travel-sample`.inventory.airline AS a
  ON KEYS r.airlineid
LIMIT 5;
----

*ANSI join.* Any boolean predicate joins the two sides and the optimizer may use an index on either. `LEFT
[OUTER] JOIN` keeps unmatched left rows with `MISSING` right-hand fields:

----
SELECT r.sourceairport, a.name AS airline, ap.airportname
FROM `travel-sample`.inventory.route AS r
JOIN `travel-sample`.inventory.airline AS a
  ON r.airlineid = META(a).id
LEFT JOIN `travel-sample`.inventory.airport AS ap
  ON r.sourceairport = ap.faa
WHERE a.country = "United States"
LIMIT 10;
----

*Index join.* The reverse direction of a lookup join -- follow a key held on the *right* side back to the
left -- made efficient by an index on the right-hand join field:

----
CREATE INDEX idx_route_airlineid
  ON `travel-sample`.inventory.route(airlineid);

SELECT a.name, r.destinationairport
FROM `travel-sample`.inventory.airline AS a
JOIN `travel-sample`.inventory.route AS r
  ON META(a).id = r.airlineid
WHERE a.icao = "SWA";
----

A join can target the same keyspace (a self-join for hierarchy or pairing) or another one, in the same
scope or across scopes. For the relational treatment of joins see xref:database/sql/relations.adoc[SQL
Relations]; for the pipeline-stage equivalent see
xref:database/mongodb/aggregation-pipeline.adoc[MongoDB Aggregation ($lookup)].

== WITH, subqueries and collection operators

*`WITH`* binds a named result once and reuses it, the same as a SQL common table expression
(https://docs.couchbase.com/server/current/n1ql/n1ql-language-reference/with.html[WITH clause]):

----
WITH big_countries AS (
  SELECT RAW country
  FROM `travel-sample`.inventory.airport
  GROUP BY country
  HAVING COUNT(*) > 200
)
SELECT a.name, a.country
FROM `travel-sample`.inventory.airline AS a
WHERE a.country IN big_countries;
----

A *recursive* CTE (Couchbase Server 7.6) walks a hierarchy: a seed term unioned with a recursive term that
references the CTE name. The shop's `categories` collection is such a tree -- each category holds the key of its
parent -- and one statement lists it with the depth of every node. Every projected expression in the recursive
term needs an alias, otherwise `pass:c[tree.depth + 1]` becomes an anonymous `$1` field and the next iteration cannot
read `depth`:

----
WITH RECURSIVE tree AS (
  SELECT META(c).id AS id, c.name, 0 AS depth
  FROM shop.sales.categories AS c
  WHERE c.parentId IS NULL
  UNION
  SELECT META(c).id AS id, c.name, tree.depth + 1 AS depth
  FROM tree JOIN shop.sales.categories AS c ON c.parentId = tree.id
)
SELECT id, name, depth FROM tree ORDER BY depth, id;
----

----
[{"id":"cat::all","name":"All products","depth":0},
 {"id":"cat::electronics","name":"Electronics","depth":1},
 {"id":"cat::office","name":"Office","depth":1},
 {"id":"cat::displays","name":"Displays","depth":2},
 {"id":"cat::furniture","name":"Furniture","depth":2},
 {"id":"cat::peripherals","name":"Peripherals","depth":2},
 {"id":"cat::ergonomic","name":"Ergonomic desks","depth":3}]
----

An `+OPTIONS { "levels": N }+` clause after the closing parenthesis of the CTE definition caps the recursion
depth: with `+{"levels": 1}+` the same statement stops after the second row group and returns only `cat::all`,
`cat::electronics` and `cat::office`. Without a cap, a cycle in the data (a category that is its own ancestor)
would recurse until the query times out, so a recursive CTE over data you do not control should always carry
one.

*Subqueries* appear in `FROM` (a derived keyspace, which needs an explicit alias), in `WHERE`, and in
the projection. *`LET`* introduces a named expression usable in `SELECT` and `WHERE`; *`LETTING`*
does the same after `GROUP BY` for expressions over aggregates:

----
SELECT p.name, band
FROM shop.sales.products AS p
LET band = CASE WHEN p.price > 200 THEN "high" ELSE "standard" END
WHERE band = "high" ORDER BY p.name;
-- [{"name":"27in Monitor","band":"high"},{"name":"Standing Desk","band":"high"}]
----

----
SELECT r.airline, num_routes, num_routes >= 2000 AS major
FROM `travel-sample`.inventory.route AS r
GROUP BY r.airline
LETTING num_routes = COUNT(*)
HAVING num_routes > 1000
ORDER BY num_routes DESC;
-- [{"airline":"AA","num_routes":2354,"major":true},{"airline":"UA","num_routes":2180,"major":true},
--  {"airline":"DL","num_routes":1981,"major":false}, ...]
----

*Collection operators* test or transform arrays inline without `UNNEST`:

----
-- ANY / EVERY: existential and universal quantification over an array
SELECT META().id
FROM `travel-sample`.inventory.route AS r
WHERE ANY s IN r.schedule SATISFIES s.day = 1 END;

-- ARRAY: a comprehension that projects a new array
SELECT r.destinationairport,
       ARRAY s.flight FOR s IN r.schedule WHEN s.day = 1 END AS monday_flights
FROM `travel-sample`.inventory.route AS r
LIMIT 5;

-- FIRST: the first matching element
SELECT FIRST s.flight FOR s IN r.schedule WHEN s.utc > "18:00" END AS evening
FROM `travel-sample`.inventory.route AS r
LIMIT 5;
----

== Worked example: querying the shop

Everything below ran against the shop dataset built in
xref:database/couchbase/getting-started.adoc[What Couchbase Server is & how to run it]: five customers, five
products and seven orders with embedded lines. Results are shown as returned, trimmed only for length.

=== The everyday clauses

Filtering, ranges, patterns, rounding and de-duplication behave as in SQL. `ROUND` and `TRUNC` take an optional
precision; `||` concatenates strings; `DISTINCT` and `BETWEEN` are unchanged:

----
SELECT p.name, ROUND(p.price * 1.21, 1) AS gross, TRUNC(p.price) AS whole, p.name LIKE "%Cable" AS is_cable
FROM shop.sales.products p WHERE p.price BETWEEN 20 AND 300 ORDER BY p.price;
-- [{"name":"Wireless Mouse","gross":29.6,"whole":24,"is_cable":false},
--  {"name":"Mechanical Keyboard","gross":108.8,"whole":89,"is_cable":false},
--  {"name":"27in Monitor","gross":313.4,"whole":259,"is_cable":false}]

SELECT DISTINCT p.category FROM shop.sales.products p ORDER BY p.category;
-- [{"category":"cables"},{"category":"displays"},{"category":"furniture"},{"category":"peripherals"}]

SELECT p.name, p.tags[0] AS first_tag, ARRAY_LENGTH(p.tags) AS ntags
FROM shop.sales.products p WHERE "usb" IN p.tags ORDER BY p.name;
-- [{"name":"Mechanical Keyboard","first_tag":"usb","ntags":2},{"name":"Wireless Mouse","first_tag":"wireless","ntags":2}]
----

`"usb" IN p.tags` tests membership in an array field, and `p.tags[0]` is array subscripting; both are
natural in a document model and awkward in a relational one.

=== MISSING, NULL and what a projection drops

Linus Torvalds is the one customer without a `tier` field. The three tests answer differently, and a `MISSING`
result is *dropped from the output object*, which is easy to mistake for a bug:

----
SELECT c.name, c.tier IS NULL AS isnull, c.tier IS MISSING AS ismissing, c.tier IS NOT VALUED AS notvalued
FROM shop.sales.customers c WHERE c.name IN ["Linus Torvalds", "Ada Lovelace"] ORDER BY c.name;
-- [{"name":"Ada Lovelace","isnull":false,"ismissing":false,"notvalued":false},
--  {"name":"Linus Torvalds","ismissing":true,"notvalued":true}]
----

For the customer without `tier`, `c.tier IS NULL` is itself `MISSING` (the field is absent, so the question has no
answer) and the key `isnull` vanishes from the row. `IS NOT VALUED` covers both `NULL` and `MISSING`, and
`IFMISSING(c.tier, "none")` supplies a default:

----
SELECT c.name, IFMISSING(c.tier, "none") AS tier FROM shop.sales.customers c ORDER BY c.name;
-- [{"name":"Ada Lovelace","tier":"gold"}, {"name":"Alan Turing","tier":"silver"},
--  {"name":"Grace Hopper","tier":"gold"}, {"name":"Linus Torvalds","tier":"none"},
--  {"name":"Margaret Hamilton","tier":"silver"}]
----

=== Joins, NEST and UNNEST on orders

An order references its customer by key, so the natural join is the lookup join. It needs no index on the
customer collection because the key is the access path:

----
SELECT c.name, o.status, ARRAY_LENGTH(o.lines) AS n_lines
FROM shop.sales.orders AS o JOIN shop.sales.customers AS c ON KEYS o.customerId
WHERE o.status = "OPEN" ORDER BY META(o).id;
-- [{"name":"Ada Lovelace","status":"OPEN","n_lines":2},
--  {"name":"Grace Hopper","status":"OPEN","n_lines":1},
--  {"name":"Alan Turing","status":"OPEN","n_lines":2}]
----

`UNNEST` flattens the embedded lines into one row per line, which turns a revenue report into an ordinary
`GROUP BY` (cancelled orders excluded):

----
SELECT l.sku, SUM(l.qty) AS units, ROUND(SUM(l.qty * l.price), 2) AS revenue
FROM shop.sales.orders AS o UNNEST o.lines AS l
WHERE o.status != "CANCELLED" GROUP BY l.sku ORDER BY revenue DESC;
-- [{"sku":"DK-400","units":1,"revenue":420},{"sku":"KB-100","units":4,"revenue":359.6},
--  {"sku":"MN-300","units":1,"revenue":259},{"sku":"MS-200","units":7,"revenue":171.5},
--  {"sku":"CB-500","units":9,"revenue":89.91}]
----

`NEST` goes the other way and collects the orders of each customer into an array. A plain `NEST` is an inner
join, so a customer with no orders disappears; `LEFT NEST` keeps it with an empty array, which is how to count
zero:

----
SELECT c.name, ARRAY_LENGTH(os) AS orders
FROM shop.sales.customers AS c LEFT NEST shop.sales.orders AS os ON os.customerId = META(c).id
ORDER BY c.name;
-- [{"name":"Ada Lovelace","orders":2},{"name":"Alan Turing","orders":2},{"name":"Grace Hopper","orders":2},
--  {"name":"Linus Torvalds","orders":0},{"name":"Margaret Hamilton","orders":1}]
----

....
flowchart TD
    j1{"Does the left row hold the key of the right document?"} -->|yes| lk["Lookup join: JOIN ... ON KEYS"]
    j1 -->|no| j2{"Does the right document hold the key of the left one?"}

....

=== Subqueries, aggregates and window functions

A subquery in the projection runs once per row; a derived keyspace in `FROM` needs an alias. Both are shown here,
the second computing the spend of each customer from the embedded lines:

----
SELECT t.cust, t.total
FROM (SELECT o.customerId AS cust, ROUND(SUM(l.qty * l.price), 2) AS total
      FROM shop.sales.orders o UNNEST o.lines l GROUP BY o.customerId) AS t
WHERE t.total > 300 ORDER BY t.total DESC;
-- [{"cust":"customer::c-2","total":557.96},{"cust":"customer::c-5","total":518},
--  {"cust":"customer::c-1","total":417.88},{"cust":"customer::c-3","total":324.17}]
----

Window functions number or total rows without collapsing them. A running total of one customer's orders:

----
SELECT c.name, SUM(ARRAY_SUM(ARRAY l.qty * l.price FOR l IN o.lines END))
         OVER (PARTITION BY o.customerId ORDER BY o.placedAt) AS running
FROM shop.sales.orders o JOIN shop.sales.customers c ON KEYS o.customerId
WHERE o.customerId = "customer::c-1" ORDER BY o.placedAt;
-- [{"name":"Ada Lovelace","running":138.9},{"name":"Ada Lovelace","running":417.88}]
----

=== Keyset pagination on the document key

The seek query from the pagination section, applied to the shop's orders and keyed on the document ID. The
primary index is ordered by key, so the planner reads the key range from the index and stops at the limit: the
plan has an `IndexScan3` on `#primary`, a `Fetch`, a `Filter`, and a `Limit` -- and *no* `Order` operator, because
the index already delivers the rows in order.

----
SELECT META(o).id AS id, o.status
FROM shop.sales.orders o WHERE META(o).id > "order::o-1003" ORDER BY META(o).id LIMIT 2;
-- [{"id":"order::o-1004","status":"SHIPPED"},{"id":"order::o-1005","status":"OPEN"}]

EXPLAIN ... -- IndexScan3(#primary) -> Fetch -> Filter -> InitialProject -> Limit
----

Ordering by a non-unique field such as `placedAt` needs the document ID as a second sort key to make the seek
unambiguous. On the shop's `(placedAt, status)` index, `ORDER BY o.placedAt` alone was served in index order
(`IndexScan3` covering, then `Limit`), while `ORDER BY o.placedAt, META(o).id` brought an `Order` operator back
into the plan. A deep pagination design therefore either seeks on a unique field, or accepts a sort step over
the bounded set of rows that match the seek predicate.

=== Parameters and scan consistency

Values reach a statement as named (`$country`) or positional (`$1`) parameters, never by string concatenation:
the statement is planned once, an injection attempt has nowhere to go, and `+scope.query(...)+` resolves
unqualified collection names against a scope:

----
curl -s -u Administrator:password http://localhost:8093/query/service \
  --data-urlencode 'statement=SELECT a.name FROM `travel-sample`.inventory.airline a WHERE a.country = $country LIMIT 2' \
  --data-urlencode '$country="France"'
# {"results":[{"name":"Air Austral"},{"name":"Airlinair"}], "metrics":{"elapsedTime":"152ms", ... "resultCount":2, "resultSize":42}}
----

Every response carries the `metrics` block shown, with the elapsed and execution times, the result count and size.
A query also decides how fresh the index it reads must be. The default, `not_bounded`, answers from whatever the
Index service has already applied, so a document written through the key-value path a moment earlier may not
be visible yet; `request_plus` makes the query wait until the index has caught up with every mutation made
before the query was issued:

[mermaid]
....
sequenceDiagram
    participant App as Application
    participant KV as Data service
    participant IX as Index service
    participant Q as Query service
    App->>KV: upsert order (acknowledged)
    KV-->>IX: DCP mutation, asynchronous
    App->>Q: SELECT with scan_consistency
    alt not_bounded
        Q->>IX: scan now
        IX-->>Q: may not include the new order yet
    else request_plus
        Q->>IX: wait until the index reaches the current sequence numbers
        IX-->>Q: includes the new order
    end
    Q-->>App: rows
....

This is measurable. A script wrote a probe document through the key-value API and immediately queried it by key
through a `status` index, forty times per consistency level:

----
not_bounded   missed 11 of 40
request_plus  missed  0 of 40
----

The cost of `request_plus` is latency under write load, so it is chosen per statement where read-your-writes
matters (a confirmation page after a checkout) and left at the default for dashboards. The SDKs expose it as
`scanConsistency(QueryScanConsistency.REQUEST_PLUS)` in the query options. Reading by key through the key-value
API needs none of this and is always consistent.

== How a SQL++ query executes

The Query service turns each statement into a pipeline of operators: parse and semantic check, optimize
(pick a Global Secondary Index per keyspace and a join order), scan the index for candidate keys, fetch the
full documents from the Data service, then apply joins, residual filters, grouping, ordering and the final
projection.

[mermaid]
....
flowchart TD
    A[SQL++ statement] --> B[Parse and semantic check]
    B --> C[Optimize: choose indexes and join order]
    C --> D[Index scan: candidate keys from a GSI]
    D --> E[Fetch: full documents from the Data service]
    E --> F[Join / UNNEST / NEST]
    F --> G[Filter: residual WHERE predicates]
    G --> H[GROUP BY / aggregate / HAVING]
    H --> I[ORDER BY / LIMIT / OFFSET]
    I --> J[Project the SELECT list]
    J --> K[Result JSON]
....

A statement with no usable secondary index falls back to a primary scan of every key in the keyspace, so
covering the `WHERE` and `JOIN` predicates with indexes is what keeps a query fast -- see
xref:database/couchbase/indexes-and-views.adoc[Indexes & views]. Continue with
xref:database/couchbase/sql-plus-plus-dml-functions-transactions.adoc[SQL++ data modification, functions &
transactions].
