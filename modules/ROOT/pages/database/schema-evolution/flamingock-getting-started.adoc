https://docs.flamingock.io/[Flamingock] is Mongock's successor: the same code-first idea, generalized so a
"change" can target any external system, not only MongoDB. This page covers its guiding philosophy, a complete
setup you can run, and how to move an existing Mongock project onto it. The examples rebuild the bookshop
`customer` collection of the Mongock pages and were executed with Flamingock 1.4.5 against MongoDB 8 as a
one-node replica set.

== Change-as-Code (CaC)

Flamingock's documentation frames its design around *Change-as-Code*: every change to any system your
application depends on -- a database schema, a message queue topology, a third-party API call that must happen
exactly once -- is committed as versioned, reviewable code, the same as any other application change. Three
principles follow from that:

* *Safety by default* -- when Flamingock cannot guarantee a safe outcome (a failure partway through, an ambiguous
  state), it stops and requires manual intervention rather than guessing or silently continuing. This is a
  stricter default than either Liquibase or Mongock: those tools generally continue past an incomplete run once
  the failure is addressed, whereas Flamingock is designed to treat "unsure" as a hard stop. The default recovery
  strategy of every change is `MANUAL_INTERVENTION`.
* *Complete auditability* -- every change's execution, across every target system in a pipeline, is recorded in
  Flamingock's audit store (xref:database/schema-evolution/flamingock-changes-and-target-systems.adoc[Flamingock:
  Changes & Target Systems]), giving one unified history instead of a separate log per target system.
* *Configurable recovery strategies* -- how Flamingock responds to a failed change is chosen per change with the
  `@Recovery` annotation (`MANUAL_INTERVENTION` or `ALWAYS_RETRY`), rather than being a single fixed behavior for
  the whole pipeline.

The diagram shows the one structural difference from Mongock: changes are discovered by an *annotation processor at
compile time*, not by scanning the classpath at startup, so a missing processor means Flamingock finds no changes.

== Quick Start

=== Dependencies

Flamingock publishes a BOM. The community runtime is `flamingock-community`, the annotation processor
`flamingock-processor` goes in the compiler plugin's `annotationProcessorPaths`, and the MongoDB driver is a normal
dependency (the MongoDB Sync target system and audit store are bundled in `flamingock-community`):

[source,xml]
----
<properties>
  <flamingock.version>1.4.5</flamingock.version>
</properties>

<dependencyManagement>
  <dependencies>
    <dependency>
      <groupId>io.flamingock</groupId>
      <artifactId>flamingock-bom</artifactId>
      <version>${flamingock.version}</version>
      <type>pom</type>
      <scope>import</scope>
    </dependency>
  </dependencies>
</dependencyManagement>

<dependencies>
  <dependency>
    <groupId>io.flamingock</groupId>
    <artifactId>flamingock-community</artifactId>
  </dependency>
  <dependency>
    <groupId>org.mongodb</groupId>
    <artifactId>mongodb-driver-sync</artifactId>
    <version>5.2.0</version>
  </dependency>
</dependencies>

<build>
  <plugins>
    <plugin>
      <groupId>org.apache.maven.plugins</groupId>
      <artifactId>maven-compiler-plugin</artifactId>
      <version>3.11.0</version>
      <configuration>
        <annotationProcessorPaths>
          <path>
            <groupId>io.flamingock</groupId>
            <artifactId>flamingock-processor</artifactId>
            <version>${flamingock.version}</version>
          </path>
        </annotationProcessorPaths>
      </configuration>
    </plugin>
  </plugins>
</build>
----

=== A first Change

A Flamingock change is a class whose *file name carries its order*: `+_0001__CreateCustomers.java+` has order
`0001` (the digits between the first underscore and the double underscore) and the descriptive name
`CreateCustomers`. The annotations name the target system, the change identity and the two methods:

[source,java]
----
@TargetSystem(id = "bookshop-mongo")
@Change(id = "create-customers", author = "alberto")
public class _0001__CreateCustomers {

    @Apply
    public void apply(MongoDatabase db, ClientSession session) {
        db.getCollection("customer").insertMany(session, List.of(
            new Document("fullName", "Ada Lovelace").append("email", "ada@example.com"),
            new Document("fullName", "Alan Turing").append("email", "alan@example.com")));
    }

    @Rollback
    public void rollback(MongoDatabase db, ClientSession session) {
        db.getCollection("customer").drop(session);
    }
}
----

Taking `ClientSession` as a parameter is what puts the writes inside a transaction (see
xref:database/schema-evolution/flamingock-changes-and-target-systems.adoc[Flamingock: Changes & Target Systems]).
The released 1.4.x annotation is `+@TargetSystem(id = "...")+`; some pages of the online documentation show the
shorter `+@TargetSystem("...")+`, which does not compile against 1.4.5.

=== The setup class and the runner

One class carries `@EnableFlamingock`, which only describes *where the changes live*, grouped in stages (see
xref:database/schema-evolution/flamingock-stages-and-pipelines.adoc[Flamingock: Stages & Pipelines]). The `main`
method builds the target system, derives the audit store from it and runs:

[source,java]
----
@EnableFlamingock(stages = {
    @Stage(name = "pre-deploy", location = "com.example.bookshop.changes.predeploy"),
    @Stage(name = "post-deploy", location = "com.example.bookshop.changes.postdeploy")
})
public class Main {

    public static void main(String[] args) {
        try (MongoClient client = MongoClients.create(
                "mongodb://localhost:27017/?replicaSet=rs0&directConnection=true")) {
            var bookshop = new MongoDBSyncTargetSystem("bookshop-mongo", client, "bookshop_fl");

            Flamingock.builder()
                .setAuditStore(MongoDBSyncAuditStore.from(bookshop))
                .addTargetSystems(bookshop)
                .build()
                .run();
        }
    }
}
----

The imports are `io.flamingock.community.Flamingock`, `io.flamingock.store.mongodb.sync.MongoDBSyncAuditStore`,
`io.flamingock.targetsystem.mongodb.sync.MongoDBSyncTargetSystem`, and the annotations from
`io.flamingock.api.annotations`. Wiring the target system's connection and the audit store happens once, here, not
per change.

=== Running it, and what a failure looks like

The bookshop pipeline of this section has four changes in `pre-deploy` (create the customers, add the e-mail
index, expand the name into first and last name, contract the old `fullName`) and one in `post-deploy` (backfill
a loyalty tier). The third change throws when `-Dfail=true` is set. The run stops, reports precisely where, and
leaves the collection untouched by the failed change:

[source,text]
----
ERROR FK-ChangeExecution   - Change failed [change=expand-customer-name duration=6ms]: java.lang.IllegalStateException: boom after rewriting every customer
========================================================================
 Flamingock execution report — FAILED
========================================================================
 Stages:    2 total — 1 completed, 1 failed, 0 up to date, 0 not reached
 Changes:   5 total — 3 newly applied, 0 already applied, 1 failed, 1 not reached

 Per-stage breakdown:

   [FAILED]    pre-deploy (193 ms)
               changes: 2 newly applied, 0 already applied, 1 failed, 1 not reached
               failed change(s): expand-customer-name

   [COMPLETED] post-deploy (12 ms)
               changes: 1 newly applied, 0 already applied, 0 failed, 0 not reached
========================================================================
----

The audit log tells the same story, state by state. A transactional failure ends in `ROLLED_BACK`, and because that
is a clean state the next run, without the failure, simply applies the change and continues with the one that was
"not reached":

[source,text]
----
create-customers              STARTED     pre-deploy
create-customers              APPLIED     pre-deploy
create-customer-email-index   STARTED     pre-deploy
create-customer-email-index   APPLIED     pre-deploy
expand-customer-name          STARTED     pre-deploy
expand-customer-name          FAILED      pre-deploy
expand-customer-name          ROLLED_BACK pre-deploy
backfill-loyalty-tier         STARTED     post-deploy
backfill-loyalty-tier         APPLIED     post-deploy
--- second run, no failure ---
expand-customer-name          STARTED     pre-deploy
expand-customer-name          APPLIED     pre-deploy
contract-customer-full-name   STARTED     pre-deploy
contract-customer-full-name   APPLIED     pre-deploy
----

Notice that `post-deploy` ran even though `pre-deploy` failed: stages are independent. That is the subject of
xref:database/schema-evolution/flamingock-stages-and-pipelines.adoc[Flamingock: Stages & Pipelines].

== Coming From Mongock

Flamingock provides a documented migration path for an existing Mongock codebase, described at
https://docs.flamingock.io/resources/coming-from-mongock[Coming from Mongock]. At a high level, this means:

[cols="2,2"]
|===
|Mongock |Flamingock

|`@ChangeUnit(id, order, author)`
|`@Change(id, author)` plus `+@TargetSystem(id = "...")+`; the `order` moves into the file name (`+_0001__Name+`)

|`@Execution`
|`@Apply`

|`@RollbackExecution`
|`@Rollback`

|`@BeforeExecution`, `@RollbackBeforeExecution`
|No such annotation (a Change has only `@Apply` and `@Rollback`): split the work into its own change, with `transactional = false` for what must run outside a transaction

|`@EnableMongock` / `mongock.migration-scan-package`
|`@EnableFlamingock` with `+@Stage(location = ...)+`

|`mongockChangeLog`, `mongockLock` collections
|`flamingockAuditLog`, `flamingockLock` collections, configurable through the audit store
|===

* The method bodies themselves are typically unchanged, since both still receive a `MongoDatabase` or equivalent;
  the difference to remember is that a Flamingock change takes `ClientSession` explicitly to join a transaction.
* Mongock's existing audit history has to be carried over so already-applied change units are not re-run.
  Flamingock ships importer modules for this (for example `mongock-importer-mongodb` on the classpath of
  `flamingock-community`), described in the migration guide.
* Flamingock's stage/pipeline grouping
  (xref:database/schema-evolution/flamingock-stages-and-pipelines.adoc[Flamingock: Stages & Pipelines]) replaces
  the flat, `order`-sorted list; for a first migration one stage that points at the old package is enough.

Because Mongock is now maintained under the Flamingock GitHub organization
(https://github.com/flamingock/mongock[github.com/flamingock/mongock]), this migration is treated by the
maintainers as an in-family upgrade rather than a switch to a competing tool -- see
https://docs.flamingock.io/resources/faq[FAQ] for specifics on version compatibility and supported migration
scenarios.

See https://docs.flamingock.io/get-started/Introduction[Introduction] and
https://docs.flamingock.io/get-started/quick-start[Quick start] for the official setup steps.
