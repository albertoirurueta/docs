== Stages

A *stage* is an ordered group of Changes that execute sequentially, in the order given by the numeric segment of
their file names (`+_0001__...+`, `+_0002__...+`) -- the same ordering guarantee Mongock gives a flat list of
`@ChangeUnit` classes
(xref:database/schema-evolution/mongock-changeunits.adoc[Mongock: ChangeUnits]), but scoped to a named subset
rather than everything Flamingock finds. A stage maps to a *package* (or a resource directory) that holds its
changes, and is declared on the setup class:

[source,java]
----
@EnableFlamingock(stages = {
    @Stage(name = "pre-deploy", location = "com.example.bookshop.changes.predeploy"),
    @Stage(name = "post-deploy", location = "com.example.bookshop.changes.postdeploy")
})
public class Main { /* ... */ }
----

`@Stage` has a required `location`, an optional `name` (derived from the location when omitted) and an optional
`description`. `@EnableFlamingock` only defines the setup -- it does not run anything -- and also takes
`strictStageMapping` (default `true`), which controls how a change found outside every declared stage is treated.
A project that prefers configuration to annotations can point at a YAML file instead:

[source,java]
----
@EnableFlamingock(configFile = "config/setup.yaml")
----

[source,yaml]
----
pipeline:
  stages:
    - name: pre-deploy
      description: Schema changes the new code depends on
      location: com.example.bookshop.changes.predeploy
    - name: post-deploy
      location: com.example.bookshop.changes.postdeploy
----

The order within a stage is the digits in the file name, compared as text. The documentation recommends four
zero-padded digits (`0001`, `0002`, `0010`); a date-based form such as `20250207_02` is also accepted. As with
Mongock, never renumber a change after it has shipped.

== Pipelines

A *pipeline* is one or more stages. Flamingock guarantees ordering *within* a stage, but explicitly does *not*
guarantee ordering *across* stages -- stages may run before, after or concurrently with each other. This is the key
structural difference from a single flat changelog: grouping into stages lets you say "these changes must happen in
this order" for one subset while leaving a different subset free to run on its own schedule. Changes that depend on
each other therefore belong in the *same* stage.

== What a Stage Failure Does

Two properties of a stage matter in practice, and both can be seen by running the bookshop pipeline with its third
change failing:

* *Inside a stage, a failure stops the stage.* The failing change is not applied, and the changes after it are
  reported as "not reached".
* *Across stages, nothing stops the other stages.* The other stage runs to completion.

[source,text]
----
 Stages:    2 total — 1 completed, 1 failed, 0 up to date, 0 not reached
 Changes:   5 total — 3 newly applied, 0 already applied, 1 failed, 1 not reached

   [FAILED]    pre-deploy (193 ms)
               changes: 2 newly applied, 0 already applied, 1 failed, 1 not reached
               failed change(s): expand-customer-name

   [COMPLETED] post-deploy (12 ms)
               changes: 1 newly applied, 0 already applied, 0 failed, 0 not reached
----

In `pre-deploy` the changes `_0001`, `_0002` were applied, `+_0003__ExpandName+` failed and `+_0004__ContractFullName+`
was not reached -- which is what protects the data, since the contract step that removes `fullName` must never run
after a failed expand. When the same contract change is placed in `post-deploy` instead, it runs
independently of the failed `pre-deploy` and deletes `fullName` from every document while `firstName` and
`lastName` were never written, which is data loss. The lesson is the rule above: *never put a change in a
different stage from the change it depends on*.

== Why This Matters for Lifecycle-Scoped Rollout

Splitting changes into stages maps onto deployment lifecycle phases only when the stages are genuinely independent. A
common shape is a "pre-deploy" stage (schema changes the new application code depends on, which must complete before
the new code starts) and a "post-deploy" stage (cleanup, backfills, or changes that are safe to apply once the new
code is already running) -- the same expand/contract shape covered in
xref:database/schema-evolution/best-practices.adoc[Best Practices]. Because stages do not wait for each other, make
the application's startup depend on the *outcome* of the pre-deploy stage (the runner throws and the process exits
on a failed stage) rather than on stage order, and keep each stage's changes self-sufficient:

[mermaid]
....
flowchart TB
    subgraph Stage1["Stage: pre-deploy (sequential, ordered)"]
        C1["0001 CreateCustomers"] --> C2["0002 AddEmailIndex"] --> C3["0003 ExpandName"] --> C4["0004 ContractFullName"]
    end
    subgraph Stage2["Stage: post-deploy (sequential, ordered)"]
        C5["0001 BackfillLoyaltyTier"]
    end
    Stage1 -.order not guaranteed across stages.-> Stage2
....

Configuring stages is done via Flamingock's setup configuration -- see
https://docs.flamingock.io/flamingock-library-config/setup-and-stages[Setup & Stages] for the exact
configuration shape and how a pipeline ties multiple stages together at startup.
