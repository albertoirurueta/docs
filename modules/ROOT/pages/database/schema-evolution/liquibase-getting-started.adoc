:description: Installing the Liquibase CLI, running via Docker, the Maven/Gradle plugin or Spring Boot auto-run-on-startup, the four changelog formats, a first changeset applied with liquibase update against PostgreSQL, and the status, updateSQL and history commands.

https://www.liquibase.org/[Liquibase] tracks and applies relational schema changes from a version-controlled
*changelog*. This page covers the three common ways to run it and the four formats a changelog can be written in,
then builds the first version of the running example used by every Liquibase page in this section: the
`customer` table of a small online bookshop, which later pages evolve one release at a time. The output shown
below was produced by Liquibase 5.0.4 against PostgreSQL 17.

== How a Liquibase run works

Every invocation of `update` follows the same sequence: connect, take the lock, read `DATABASECHANGELOG`,
compare it with the changelog file, run only the changesets that are missing, and record each one as it
completes.

[mermaid]
....
sequenceDiagram
    participant CLI as Liquibase (CLI, plugin or Spring Boot)
    participant Lock as DATABASECHANGELOGLOCK
    participant Log as DATABASECHANGELOG
    participant DB as Application tables
    CLI->>Lock: set LOCKED = true
    CLI->>Log: read applied changesets and checksums
    CLI->>CLI: parse changelog, validate checksums, compute pending changesets
    loop each pending changeset in order
        CLI->>DB: run the generated SQL
        CLI->>Log: insert id, author, filename, checksum, exectype
    end
    CLI->>Lock: set LOCKED = false
....

The two bookkeeping tables are created automatically on first use, in the same schema as the application tables.

== Running Liquibase

=== The CLI

Liquibase ships a standalone command-line tool. Once installed and pointed at a changelog and a JDBC URL, the
core commands are:

[source,shell]
----
liquibase update              # apply every pending changeset
liquibase update-sql          # print the SQL that update would run, without running it
liquibase status --verbose    # list pending changesets
liquibase history             # list what has been applied, and when
liquibase rollback <tag>      # see liquibase-rollback.adoc
----

Since Liquibase 4.x every command also has a kebab-case spelling (`update-sql`, `rollback-count`, `release-locks`);
the older camel-case spellings (`updateSQL`, `rollbackCount`, `releaseLocks`) keep working. Arguments can be
passed as flags or kept in a `liquibase.properties` file next to the changelog:

[source,properties]
----
changelog-file=changelog/db.changelog-master.yaml
url=jdbc:postgresql://localhost:5432/bookshop
username=app
password=app
----

See https://docs.liquibase.com/pro/user-guide-4-33[the User guide] for the full CLI reference and installation
instructions per platform.

=== The Docker image

The official `liquibase/liquibase` image bundles the CLI and a Java runtime, which makes it convenient in CI and
for trying things out without installing anything. The image does not include the PostgreSQL JDBC driver, so mount
the driver jar into `/liquibase/internal/lib`:

[source,shell]
----
docker run --rm --network my-net \
  -v "$PWD":/liquibase/changelog_root \
  -v "$PWD/drivers/postgresql-42.7.4.jar":/liquibase/internal/lib/postgresql.jar \
  -w /liquibase/changelog_root \
  liquibase/liquibase:5.0 --defaults-file=liquibase.properties update
----

Forgetting the driver produces `Cannot find database driver: org.postgresql.Driver`. The other examples in this
section abbreviate the command above as `liquibase <command>`.

=== Maven / Gradle Plugin

For a JVM project, the `liquibase-maven-plugin` or the community Gradle plugin runs the same commands as part of
the build. The plugin needs the JDBC driver as a plugin dependency, because the plugin classpath is separate from
the project classpath:

[source,xml]
----
<plugin>
    <groupId>org.liquibase</groupId>
    <artifactId>liquibase-maven-plugin</artifactId>
    <version>5.0.4</version>
    <configuration>
        <changeLogFile>src/main/resources/db/changelog/db.changelog-master.yaml</changeLogFile>
        <url>jdbc:postgresql://localhost:5432/bookshop</url>
        <username>app</username>
        <password>app</password>
    </configuration>
    <dependencies>
        <dependency>
            <groupId>org.postgresql</groupId>
            <artifactId>postgresql</artifactId>
            <version>42.7.4</version>
        </dependency>
    </dependencies>
</plugin>
----

[source,shell]
----
mvn liquibase:update
mvn liquibase:status
----

=== Spring Boot Auto-Run-on-Startup

With `liquibase-core` on the classpath, Spring Boot runs `update` automatically on application startup, before
the rest of the context finishes initializing:

[source,yaml]
----
spring:
  liquibase:
    change-log: classpath:db/changelog/db.changelog-master.yaml
    contexts: prod
----

This is the most common setup for an application that owns its own schema -- the schema is always current the
moment the application is up, with no separate deployment step. The trade-off is that a failing changeset keeps
the application from starting, and that every replica of a horizontally scaled application tries to migrate at
once, which is exactly the situation the lock table exists for (see
xref:database/schema-evolution/liquibase-tracking-and-locking.adoc[Liquibase: Tracking & Locking]).

== The Four Changelog Formats

A Liquibase changelog is a list of changesets and can be written in any of four formats -- mix and match across
`include`/`includeAll` as needed:

[cols="1,3"]
|===
|Format |Notes

|SQL
|Plain SQL with `+--liquibase formatted sql+` structured comments marking each changeset. Most familiar to a DBA,
least portable across database vendors.

|XML
|The original, most fully-featured format -- every Liquibase change type has an XML representation.

|YAML
|Same structure as XML, less verbose; the most common choice for new projects.

|JSON
|Same structure as XML/YAML, in JSON; useful when changelogs are generated programmatically.
|===

The same changeset in the two formats you are most likely to meet side by side:

[source,xml]
----
<changeSet id="add-customer-email" author="alberto">
    <addColumn tableName="customer">
        <column name="email" type="varchar(255)"/>
    </addColumn>
</changeSet>
----

[source,sql]
----
--liquibase formatted sql

--changeset alberto:add-customer-email
ALTER TABLE customer ADD COLUMN email varchar(255);
--rollback ALTER TABLE customer DROP COLUMN email;
----

The declarative formats (XML, YAML, JSON) describe *what* should change and let Liquibase generate vendor-specific
SQL, which is what makes them portable and gives them an automatic rollback. A formatted SQL changelog is exactly
the SQL you wrote, so there is nothing to translate, but rollback must always be written by hand.

See https://docs.liquibase.com/concepts/changelogs/home.html[What is a Changelog?] for the full format
reference.

== A First Minimal Example

The bookshop starts with one table. The master changelog includes the first changelog file:

[source,yaml]
----
databaseChangeLog:
  - include:
      file: changelog/001-create-customer.yaml
  - includeAll:
      path: changelog/releases/
----

and `001-create-customer.yaml` holds a single changeset creating the table:

[source,yaml]
----
databaseChangeLog:
  - changeSet:
      id: create-customer-table
      author: alberto
      changes:
        - createTable:
            tableName: customer
            columns:
              - column:
                  name: id
                  type: bigint
                  autoIncrement: true
                  constraints:
                    primaryKey: true
              - column:
                  name: full_name
                  type: varchar(255)
                  constraints:
                    nullable: false
----

=== Look before you leap: `update-sql` and `status`

Before touching the database, ask Liquibase what it would do. `+status --verbose+` lists the pending changesets
by their full identity (`filename::id::author`), and `update-sql` prints the exact SQL, including the writes to
the two bookkeeping tables:

[source,text]
----
$ liquibase status --verbose
1 changeset has not been applied to app@jdbc:postgresql://localhost:5432/bookshop
     changelog/001-create-customer.yaml::create-customer-table::alberto

$ liquibase update-sql
-- Lock Database
UPDATE public.databasechangeloglock SET LOCKED = TRUE, LOCKEDBY = '86b09a18767d (172.22.0.3)', LOCKGRANTED = NOW() WHERE ID = 1 AND LOCKED = FALSE;
-- Changeset changelog/001-create-customer.yaml::create-customer-table::alberto
CREATE TABLE public.customer (id BIGINT GENERATED BY DEFAULT AS IDENTITY NOT NULL, full_name VARCHAR(255) NOT NULL, CONSTRAINT customer_pkey PRIMARY KEY (id));
INSERT INTO public.databasechangelog (ID, AUTHOR, FILENAME, DATEEXECUTED, ORDEREXECUTED, MD5SUM, DESCRIPTION, COMMENTS, EXECTYPE, ...) VALUES ('create-customer-table', 'alberto', ...);
-- Release Database Lock
UPDATE public.databasechangeloglock SET LOCKED = FALSE, LOCKEDBY = NULL, LOCKGRANTED = NULL WHERE ID = 1;
----

Note how the declarative `createTable` became PostgreSQL-specific SQL (`GENERATED BY DEFAULT AS IDENTITY`); on
another database the same changeset produces different DDL. Applied from the CLI:

[source,shell]
----
liquibase update
----

This creates the `customer` table and records one row in `DATABASECHANGELOG` for changeset
`create-customer-table` by `alberto` (see
xref:database/schema-evolution/liquibase-tracking-and-locking.adoc[Liquibase: Tracking & Locking] for what gets
recorded). A second `update` finds nothing to do:

[source,text]
----
Database is up to date, no changesets to execute
UPDATE SUMMARY
Run:                          0
Previously run:               1
Filtered out:                 0
-------------------------------
Total change sets:            1
----

xref:database/schema-evolution/liquibase-changelogs-and-changesets.adoc[Liquibase: Changelogs & Changesets],
covers changeset identity and organizing changelogs across multiple files in more depth.
