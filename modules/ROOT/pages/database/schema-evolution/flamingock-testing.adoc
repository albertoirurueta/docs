= Flamingock: Testing
:description: The change validator for metadata checks, unit testing a single Change, the BDD-style given-when-then testing API with an in-memory audit store and a real MongoDB target, and Spring Boot integration testing, with a passing JUnit run.
:keywords: Flamingock testing, change validator, BDD API, FlamingockTestSupport, InMemoryFlamingockBuilder, ChangeValidator

include::partial$ai-disclaimer.adoc[]

Flamingock changes are ordinary classes, so they can be tested at three levels: cheap *metadata* checks that need no
database at all, *unit* tests of one change's logic, and *pipeline* tests that run real changes against a real
target system and assert on the audit trail. All examples below were run with JUnit 5 against Flamingock 1.4.5 and
the one-node MongoDB replica set from
xref:database/schema-evolution/flamingock-getting-started.adoc[Flamingock: Getting Started].

The test support lives in a separate artifact, managed by the Flamingock BOM:

[source,xml]
----
<dependency>
  <groupId>io.flamingock</groupId>
  <artifactId>flamingock-test-support</artifactId>
  <scope>test</scope>
</dependency>
----

== The Change Validator

`ChangeValidator` checks a change's *declared metadata* -- id, author, order, target system, transactionality,
recovery strategy and the presence of a rollback -- without starting Flamingock, a container or an external system.
Assertions are queued and `validate()` runs them all, reporting every failure in a single `AssertionError`. This is
a cheap guard against the mistakes that cost the most in production, such as renaming an `id` after deployment or
forgetting the rollback:

[source,java]
----
@Test
void expandChangeMetadataIsCorrect() {
    ChangeValidator.of(_0003__ExpandName.class)
        .withId("expand-customer-name")
        .withAuthor("alberto")
        .withOrder("0003")
        .isTransactional()
        .withTargetSystem("bookshop-mongo")
        .hasRollbackMethod()
        .validate();
}
----

It works on code-based changes (through reflection) and on YAML template-based changes
(`ChangeValidator.of(Path)`), which add `+withTemplateName(...)+`, `hasRollback()` and step-level checks.

Note the difference from the *audit* of a run: the validator does not look at executions at all. It is not a filter
over the audit log.

== Unit Testing a Single Change

Because a `@Change` class is plain Java with `@Apply`/`@Rollback` methods
(xref:database/schema-evolution/flamingock-changes-and-target-systems.adoc[Flamingock: Changes & Target
Systems]), it can be unit tested like any other class -- instantiate it, call `+apply(...)+` with a mocked or
in-memory target-system client, and assert on the result, independent of Flamingock's own execution machinery.
For a change that talks to `MongoDatabase` this means either mocking the driver interfaces or, more usefully,
running against a throwaway MongoDB (Testcontainers is the usual choice). This is the fastest layer that still
exercises real logic; it does not verify ordering, transactions or the audit trail.

== The BDD-Style Given-When-Then API

The test-support module also runs a whole pipeline inside a test. The chain is `+givenBuilder(...)+`, optionally
`+andExistingAudit(...)+`, `whenRun()`, then `+thenExpectAuditFinalStateSequence(...)+` (or `+thenExpectException(...)+`),
and finally `verify()` -- *nothing executes until `verify()` is called*. The builder is a normal Flamingock builder;
`InMemoryFlamingockBuilder` supplies an in-memory audit store and lock, so the test needs only the target system:

[source,java]
----
@Test
void wholePipelineAppliesInOrder() {
    var target = new MongoDBSyncTargetSystem("bookshop-mongo", client, "bookshop_fl_test");

    FlamingockTestSupport
        .givenBuilder(InMemoryFlamingockBuilder.create().addTargetSystems(target))
        .whenRun()
        .thenExpectAuditFinalStateSequence(
            APPLIED(_0001__CreateCustomers.class),
            APPLIED(_0002__AddEmailIndex.class),
            APPLIED(_0003__ExpandName.class),
            APPLIED(_0004__ContractFullName.class),
            APPLIED(_0001__BackfillLoyaltyTier.class))
        .verify();

    var ada = client.getDatabase("bookshop_fl_test").getCollection("customer")
        .find(new Document("email", "ada@example.com")).first();
    assertEquals("Lovelace", ada.getString("lastName"));
    assertEquals("STANDARD", ada.getString("loyaltyTier"));
    assertNull(ada.get("fullName"));
}
----

`APPLIED`, `FAILED`, `ROLLED_BACK` and `ROLLBACK_FAILED` are static factories of `AuditEntryDefinition`. Passing
the *change class* (recommended) makes the definition pick up the id, author and target system from the
annotations; fluent overrides (`withAuthor`, `withTargetSystemId`, `withOrder`, `withErrorTrace`,
`withTransactional`) tighten the check, and only the fields you set are compared.

`thenExpectAuditFinalStateSequence` checks *final* states only -- the `STARTED` entries recorded along the way are
ignored -- requires the exact number of entries, and checks their order. The test above therefore proves the
ordering rule of the stage and that the whole pipeline ends applied.

`andExistingAudit(APPLIED(PreviousChange.class))` seeds the audit with changes that "already ran", which is how to
test an *upgrade* -- the state of a production database at release N -- rather than only a fresh install.

For a negative test, `+thenExpectException(...)+` asserts that the run fails and `+andExpectAuditFinalStateSequence(...)+`
asserts what was left behind. The change `+_0003__ExpandName+` throws when the system property `fail` is set, so the test
switches it on, expects the stage to fail, and expects the contract change to *not* appear in the audit:

[source,java]
----
@Test
void failedExpandStopsBeforeContract() {
    var target = new MongoDBSyncTargetSystem("bookshop-mongo", client, "bookshop_fl_test2");
    System.setProperty("fail", "true");
    try {
        FlamingockTestSupport
            .givenBuilder(InMemoryFlamingockBuilder.create().addTargetSystems(target))
            .whenRun()
            .thenExpectException(FlamingockException.class,
                ex -> assertTrue(String.valueOf(ex.getMessage()).contains("failed")))
            .andExpectAuditFinalStateSequence(
                APPLIED(_0001__CreateCustomers.class),
                APPLIED(_0002__AddEmailIndex.class),
                FAILED(_0003__ExpandName.class).withMethodName("apply"),
                ROLLED_BACK(_0003__ExpandName.class).withMethodName("native_db_engine"),
                APPLIED(_0001__BackfillLoyaltyTier.class))
            .verify();
    } finally {
        System.clearProperty("fail");
    }
}
----

Two details of the audit trail are visible in the assertions. A failed change appears as *two* final entries,
`FAILED` and then `ROLLED_BACK`, and when the rollback was done by the database's own transaction abort rather
than by the `@Rollback` method, the recorded method name is `native_db_engine`. The last entry is the independent
`post-deploy` stage, which still applied (see
xref:database/schema-evolution/flamingock-stages-and-pipelines.adoc[Flamingock: Stages & Pipelines]).
`FlamingockException` is `io.flamingock.internal.common.core.error.FlamingockException`. All three tests pass:

[source,text]
----
[INFO] Tests run: 3, Failures: 0, Errors: 0, Skipped: 0, Time elapsed: 4.321 s -- in com.example.bookshop.CustomerChangesTest
[INFO] BUILD SUCCESS
----

== Spring Boot Integration Testing

For a Spring Boot application there is a companion artifact, `flamingock-springboot-test-support`, with the same
fluent API integrated into Spring's test context. A test can boot the application context (or a slice of it), let
Flamingock run its normal startup migration flow, and then assert against the real, fully-wired target-system beans
instead of mocks -- the appropriate level for confirming a Change behaves correctly against the actual Spring Data
`MongoTemplate`/`JdbcTemplate` configuration the application uses in production, rather than a hand-constructed
client in a plain unit test.

See https://docs.flamingock.io/testing/flamingock-bdd-api[Flamingock BDD API] for the full API reference and
Spring Boot test-slice configuration.
