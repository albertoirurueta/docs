= Choosing a Migration Tool
:description: A decision guide for choosing between Liquibase, Mongock and Flamingock -- default recommendation plus named reasons to deviate, with a decision flowchart.
:keywords: Liquibase vs Mongock vs Flamingock, choosing a migration tool, database migration tool comparison

include::partial$ai-disclaimer.adoc[]

The three tools in this guide are not interchangeable -- each one targets a different combination of "what am I
migrating" and "what does my codebase already look like." This page gives a default recommendation per situation
and names the specific reasons to deviate from it, in the same style as
xref:database/choosing-the-right-database.adoc[Choosing the Right Database].

== Default: Liquibase for a Relational/SQL Target

If the target is a relational database and there is no existing investment in Mongock, default to
*https://www.liquibase.org/[Liquibase]*. It has no JVM requirement to run standalone (only the CLI, Maven/Gradle
plugin, or Spring Boot integration if you do run on the JVM), its changelog is declarative (SQL, XML, YAML or
JSON) and reviewable by a DBA who doesn't read the application's language, and it is the most mature and widely
adopted of the three for relational schemas.

Deviate from this only when the target is not relational -- see below.

== Mongock: An Existing MongoDB + Java/Spring Project, Already Invested

Choose *https://docs.mongock.io/[Mongock]* when a project already has MongoDB, is on Java/Spring, and already has
Mongock change units in place, with no specific reason to move off it. Its code-first `@ChangeUnit` model fits
naturally into a JVM codebase, and there is real switching cost -- rewriting `@ChangeUnit` classes as Liquibase
changelogs (which doesn't natively target MongoDB the way it targets SQL) or as Flamingock `@Change` classes --
that has to be worth paying before you pay it.

Do *not* default to Mongock for a *new* project. It is still maintained, but its own documentation positions
Flamingock as the forward path
(xref:database/schema-evolution/flamingock-getting-started.adoc#_coming_from_mongock[Coming from Mongock]), and
starting new work on the predecessor when the successor is the vendor's own recommended direction just moves the
eventual migration cost later without avoiding it.

== Flamingock: New Projects, Multiple Target Systems, or Migrating Off Mongock

Choose *https://docs.flamingock.io/[Flamingock]* when:

* You are starting a *new project* that will use MongoDB, or any of Flamingock's other supported target systems.
* You need *one Change-as-Code model across several target systems* -- SQL, MongoDB, DynamoDB, Couchbase, and
  non-database systems such as message brokers, external APIs or cloud services -- instead of running a separate
  tool per target
  (xref:database/schema-evolution/flamingock-changes-and-target-systems.adoc[Flamingock: Changes & Target
  Systems]).
* You have an *existing Mongock project* and no reason to stay on it -- Flamingock provides a documented
  migration path
  (xref:database/schema-evolution/flamingock-getting-started.adoc#_coming_from_mongock[Coming from Mongock])
  rather than a rewrite from scratch.

Flamingock's safety-by-default philosophy (stopping and requiring manual intervention rather than guessing when a
safe outcome can't be guaranteed) and its explicit target-system model also make it the better fit whenever a
change unit has to coordinate a database change with a side effect on a non-database system -- something neither
Liquibase nor Mongock is designed to express directly.

== The Same Change in All Three Tools

Seeing one change written three times makes the differences concrete. The bookshop needs a unique index on the
customer e-mail.

*Liquibase* -- declarative, vendor-neutral, rollback generated:

[source,yaml]
----
- changeSet:
    id: index-customer-email
    author: alberto
    changes:
      - createIndex:
          tableName: customer
          indexName: idx_customer_email
          unique: true
          columns:
            - column: { name: email }
----

*Mongock* -- a Java class, order as an attribute, rollback hand-written:

[source,java]
----
@ChangeUnit(id = "create-customer-email-index", order = "001", author = "alberto")
public class V001_CreateCustomerIndex {
    @Execution
    public void execution(MongoDatabase db) {
        db.getCollection("customer").createIndex(Indexes.ascending("email"), new IndexOptions().unique(true));
    }
    @RollbackExecution
    public void rollback(MongoDatabase db) {
        db.getCollection("customer").dropIndex(Indexes.ascending("email"));
    }
}
----

*Flamingock* -- a Java class, order in the file name, an explicit target system:

[source,java]
----
@TargetSystem(id = "bookshop-mongo")
@Change(id = "create-customer-email-index", author = "alberto", transactional = false)
public class _0002__AddEmailIndex {
    @Apply
    public void apply(MongoDatabase db) {
        db.getCollection("customer").createIndex(Indexes.ascending("email"), new IndexOptions().unique(true));
    }
    @Rollback
    public void rollback(MongoDatabase db) {
        db.getCollection("customer").dropIndex(Indexes.ascending("email"));
    }
}
----

== Behaviour Under Failure

The tools were each run against the same bookshop scenario with a change that throws partway through. The results
decide more projects than the feature lists do:

[cols="2,3,3,3"]
|===
|Question |Liquibase (PostgreSQL) |Mongock (replica set) |Flamingock (replica set)

|Failed change, transactional target
|Changeset transaction rolled back, not recorded, next run retries it
|Transaction aborted, no `EXECUTED` entry, next run retries it
|`FAILED` then `ROLLED_BACK` in the audit, next run retries it

|What the next run does by default
|Retries the pending changeset
|Retries the unit
|Stops if the strategy is `MANUAL_INTERVENTION` and the state is not clean; a clean `ROLLED_BACK` is retried

|Later changes after the failure
|Not run (the update aborts)
|Not run (the run aborts)
|Not run in the *same stage*; other stages still run

|Edited after being applied
|Checksum validation failure, nothing runs
|Silently never re-run
|Silently never re-run

|Dry run
|`update-sql`, `status`
|None
|None, but `ChangeValidator` and in-memory pipeline tests
|===

== Summary Table

[cols="2,3,3"]
|===
|Situation |Default |Why

|New relational/SQL project
|Liquibase
|Declarative changelog, DBA-reviewable, no JVM requirement.

|Existing MongoDB + Java/Spring, already on Mongock
|Mongock
|Switching cost outweighs the benefit without a specific driver.

|New MongoDB (or other) project
|Flamingock
|Vendor-recommended forward path; one model across target systems.

|Multiple target systems (SQL + MongoDB + non-database)
|Flamingock
|The only one of the three built for this from the start.

|Migrating an existing Mongock codebase forward
|Flamingock
|Documented migration path -- see
xref:database/schema-evolution/flamingock-getting-started.adoc#_coming_from_mongock[Coming from Mongock].
|===
