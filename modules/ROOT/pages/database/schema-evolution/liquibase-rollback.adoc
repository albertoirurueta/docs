= Liquibase: Rollback
:description: Automatic rollback with Liquibase-generated inverse SQL, custom rollback blocks for change types with no well-defined inverse, previewing with rollback-sql, rolling back by tag, count or date, and testing rollbacks before production.
:keywords: Liquibase rollback, custom rollback, rollback tag, rollback-sql, rollback-count, rollback-one-changeset, updateTestingRollback

include::partial$ai-disclaimer.adoc[]

Liquibase can undo changesets it has applied. Rollback is *not* a time machine for data: it replays the inverse
of each changeset, in reverse order of execution, and only the changes that can be expressed as an inverse can be
rolled back. This page uses a small release of the bookshop changelog (`004-drop-legacy.yaml`) that makes a
column nullable, creates a `loyalty` table and drops it again.

[mermaid]
....
flowchart LR
    T["liquibase tag release-1.0"] --> U["update: changesets A, B, C applied"]
    U --> R{"rollback release-1.0"}
    R --> RC["undo C first"]
    RC --> RB["then undo B"]
    RB --> RA["then undo A"]
    RA --> RS["stop: changesets before the tag stay applied"]
    RC -.-> Rm["each undone changeset row is deleted from DATABASECHANGELOG"]
....

== Automatic Rollback

For change types with an obvious, well-defined inverse, Liquibase generates the rollback SQL automatically --
`createTable` rolls back to `dropTable`, `addColumn` to `dropColumn`, `createIndex` to `dropIndex`, and so on. No
extra authoring is needed:

[source,yaml]
----
- changeSet:
    id: create-loyalty-table
    author: alberto
    changes:
      - createTable:
          tableName: loyalty
          columns:
            - column: { name: id, type: bigint }
----

Rolling this back (see <<Rolling Back by Tag, Count or Date>>) issues `DROP TABLE public.loyalty` without any
explicit `<rollback>` block, per
https://docs.liquibase.com/secure/user-guide-5-2-1/what-is-a-rollback[What is a Rollback?].

== Custom Rollback for Change Types With No Inverse

Some change types have no well-defined automatic inverse: `dropTable` (the data is gone -- there is nothing to
recreate it from), `insert` (which row should `delete` remove, if several look alike?), and raw `sql` blocks (the
tool cannot infer intent from arbitrary SQL text). Liquibase fails *at rollback time*, not when the changeset is
written, which is why it is easy to discover the gap too late. With a `dropTable` changeset that has no
`rollback` block, `liquibase rollback release-1.0` stops on the first changeset it cannot invert:

[source,text]
----
Rolling Back Changeset: changelog/releases/004-drop-legacy.yaml::drop-loyalty-table::alberto
ERROR: Exception Primary Class:  RollbackImpossibleException
ERROR: Exception Primary Reason:  No inverse to liquibase.change.core.DropTableChange created
----

For these, an explicit `<rollback>` block is required if the changeset should be reversible at all --
https://docs.liquibase.com/community/user-guide-5-0-3/create-custom-rollback-statements-in-liquibase[Create
custom rollback statements]:

[source,yaml]
----
- changeSet:
    id: drop-loyalty-table
    author: alberto
    changes:
      - dropTable:
          tableName: loyalty
    rollback:
      - createTable:
          tableName: loyalty
          columns:
            - column: { name: id, type: bigint }
----

The `rollback` block recreates the table's shape -- but note this restores the *schema*, not the *data* that was
in it, since `dropTable` destroyed that. A changeset with no meaningful inverse at all (a one-way data backfill,
for instance) can declare `rollback: []` or `<rollback/>` explicitly to document "not reversible" rather than
leaving Liquibase to fail when a rollback is attempted. The `backfill-customer-last-name` changeset of the
bookshop example, which runs raw SQL, carries a custom block of its own:

[source,yaml]
----
- changeSet:
    id: backfill-customer-last-name
    author: alberto
    changes:
      - sql:
          sql: UPDATE customer SET last_name = split_part(full_name, ' ', 2) WHERE last_name IS NULL
    rollback:
      - sql:
          sql: UPDATE customer SET last_name = NULL
----

A rollback block may also reference changes in other changesets by id (`+<rollback changeSetId="..." changeSetAuthor="..."/>+`),
which avoids repeating a long inverse that is already written down elsewhere.

== Preview First: `rollback-sql`

As with `update`, ask for the SQL before running it. After tagging the state before release 4 and applying it,
`rollback-sql` shows what rolling back to the tag would do -- note the reverse order, and that each undone
changeset also deletes its own row from `DATABASECHANGELOG`:

[source,text]
----
$ liquibase rollback-sql release-1.0
CREATE TABLE public.loyalty (id BIGINT);
DELETE FROM public.databasechangelog WHERE ID = 'drop-loyalty-table' AND AUTHOR = 'alberto' AND FILENAME = 'changelog/releases/004-drop-legacy.yaml';
DROP TABLE public.loyalty;
DELETE FROM public.databasechangelog WHERE ID = 'create-loyalty-table' AND AUTHOR = 'alberto' AND FILENAME = 'changelog/releases/004-drop-legacy.yaml';
ALTER TABLE public.customer ALTER COLUMN  full_name SET NOT NULL;
DELETE FROM public.databasechangelog WHERE ID = 'drop-customer-full-name-not-null' AND AUTHOR = 'alberto' AND FILENAME = 'changelog/releases/004-drop-legacy.yaml';
----

The last statement shows the practical limit of the automatic inverse: `SET NOT NULL` fails if any row received a
`NULL` in `full_name` while the column was nullable. A rollback that is correct for the schema can still fail for
the data.

== Rolling Back by Tag, Count or Date

Liquibase can roll back to a named tag, a fixed number of changesets, or a point in time:

[source,shell]
----
liquibase tag release-1.0                 # mark the current state
liquibase rollback release-1.0            # undo everything applied after that tag
liquibase rollback-count 3                # undo the last 3 changesets
liquibase rollback-to-date 2026-01-01     # undo everything applied after that date
----

Tagging a known-good state before a release (`liquibase tag`) is what makes `rollback <tag>` a reliable way
back to it. Rolling back a *single* changeset out of order (`rollback-one-changeset`, with `+--changeset-id+`,
`+--changeset-author+` and `+--changeset-path+`) is not part of the open-source CLI: running it with the
community `liquibase/liquibase:5.0` image answers `Unexpected argument(s): rollback-one-changeset`. It belongs to
the commercial editions, together with the other targeted rollback commands.

After the real rollback, the three changesets of release 4 are pending again and `status` lists them; a further
`rollback-count 1` undoes the most recently executed changeset, here the reporting index from release 2:

[source,text]
----
$ liquibase rollback release-1.0
Rolling Back Changeset: changelog/releases/004-drop-legacy.yaml::drop-loyalty-table::alberto
Rolling Back Changeset: changelog/releases/004-drop-legacy.yaml::create-loyalty-table::alberto
Rolling Back Changeset: changelog/releases/004-drop-legacy.yaml::drop-customer-full-name-not-null::alberto

$ liquibase rollback-count 1
Rolling Back Changeset: changelog/releases/002-add-email.yaml::index-customer-email::alberto
----

Counting and dating use *execution order*, not file order: in the example of
xref:database/schema-evolution/liquibase-preconditions-contexts-labels.adoc[Liquibase: Preconditions, Contexts &
Labels] the seed changeset and the index of release 2 were executed after release 3, so they are the "last" ones.
Counting also walks into changesets you may not have thought of: `rollback-count 3` on that database stops with
`No inverse to liquibase.change.core.InsertDataChange created`, because the third-last changeset is the seed
`insert`, which has no automatic inverse.

== Rollback in Practice

* *Rollback only reverses structure.* A destructive change (`dropTable`, `dropColumn`) can be reversed in shape but
  not in content. Taking a backup before such a release, or following expand/contract so that the destructive step
  is separate and last (see xref:database/schema-evolution/best-practices.adoc[Best Practices]), is the real safety
  net.
* *Prefer rolling forward.* In production the usual answer to a bad migration is a new changeset that fixes it;
  the audit trail then shows the mistake and the fix, and application instances already running the new schema
  are not forced back.
* *Test the rollback.* `update-testing-rollback` applies the pending changesets, rolls the most recent ones back,
  and applies them again, which proves in CI that their rollbacks exist and work on a copy of the database:
+
[source,text]
----
Running Changeset: changelog/releases/002-add-email.yaml::index-customer-email::alberto
Rolling Back Changeset: changelog/releases/002-add-email.yaml::index-customer-email::alberto
Running Changeset: changelog/releases/002-add-email.yaml::index-customer-email::alberto
----
* *Rollback blocks are code.* Review them with the same care as the forward change: an inverse that was never run is
  the most common way a rollback fails when it is finally needed.
