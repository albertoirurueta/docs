= Core Concepts
:description: The vocabulary shared by Liquibase, Mongock and Flamingock before diving into any single tool -- change unit, changelog, idempotency, checksums, the audit table, distributed locking, contexts, rollback and dry run.
:keywords: change unit, changelog, idempotency, checksum, audit table, distributed lock, contexts, rollback, dry run

include::partial$ai-disclaimer.adoc[]

Liquibase, Mongock and Flamingock each use their own name for the same handful of ideas. This page introduces
that shared vocabulary once, names which tool calls each concept what, and links each one to an official doc page
-- so the tool-specific pages that follow can use the terms directly without re-explaining them.

At startup (or on a CLI invocation, for Liquibase), every one of these tools follows the same generic shape:
acquire a lock so only one instance migrates at a time, read what has already run from an audit/tracking store,
compute what is left to run, execute it in order, and record each execution as it completes.

This is why the lock in that sequence matters: without it, two instances starting at once would both compute the
same pending change units and could execute them concurrently.

[mermaid]
....
sequenceDiagram
    participant A as Instance A (startup)
    participant B as Instance B (startup)
    participant Lock as Distributed lock
    participant Audit as Audit / tracking table
    par concurrent startup
        A->>Lock: acquire lock
        B->>Lock: acquire lock (blocks)
    end
    Lock-->>A: lock granted
    A->>Audit: read applied change units, execute pending ones
    A->>Lock: release lock
    Lock-->>B: lock granted
    B->>Audit: read applied change units
    Note over B: nothing pending -- A already ran them
    B->>Lock: release lock
....

== The Life of a Change Unit

Each change unit moves through a small set of states, and the tools differ mainly in how many of them they record.
Liquibase writes a row only when a changeset has finished (or was deliberately skipped); Flamingock writes a row
when a change *starts* and another when it ends, so a crash in the middle is visible in the audit log.

[mermaid]
....
stateDiagram-v2
    [*] --> Pending
    Pending --> Filtered: context, label or profile excludes it
    Filtered --> Pending: a later run lets it through
    Pending --> Skipped: precondition fails with MARK_RAN
    Pending --> Started: lock held, change begins
    Started --> Applied: success
    Started --> Failed: exception
    Failed --> RolledBack: rollback ran or transaction aborted
    Failed --> NeedsAttention: rollback impossible or unsafe
    RolledBack --> Pending: retried on the next run
    Applied --> [*]
    Skipped --> [*]
....

The names of the states above are generic. Liquibase's real values are `EXECUTED`, `MARK_RAN` and `RERAN`; Flamingock's
audit states are `STARTED`, `APPLIED`, `FAILED`, `ROLLED_BACK` and `ROLLBACK_FAILED`; Mongock records `EXECUTED` (and
a failed unit simply leaves no `EXECUTED` entry).

== Change Unit

A *change unit* is one atomic, uniquely identified piece of migration work -- the smallest thing that runs and
gets recorded as having run. Liquibase calls it a *changeset*
(https://docs.liquibase.com/concepts/changelogs/changeset.html[What is a Changeset?]); Mongock calls it a
*changeunit* (https://docs.mongock.io/v5/migration/[Migration / ChangeUnit reference]); Flamingock calls it a
*change*. In every case, identity is the combination of an id, an author (or ordering key) and, for Liquibase,
the file it was declared in -- change that identity and the tool treats it as a brand-new unit rather than an
edit to the old one.

== Changelog / Ordering

The *changelog* is the ordered, append-only list of change units a tool knows about. Liquibase's changelog is an
explicit file (SQL, XML, YAML or JSON) that lists changesets in the order they appear, optionally pulling in
other files via `include`/`includeAll`
(see xref:database/schema-evolution/liquibase-changelogs-and-changesets.adoc[Liquibase: Changelogs & Changesets]).
Mongock derives ordering from the `order` attribute of each `@ChangeUnit` class; Flamingock derives it from the
numeric segment of the change's file name (`+_0001__CreateCustomers.java+`), since the "changelog" there is the
set of annotated classes on the classpath rather than a single file. In all three, the rule is the same: change units already recorded as applied are skipped, and new
ones run in ascending order.

== Idempotency

A change unit must be safe to *define once and run exactly one time* against a given target. This matters because
the tool's own bookkeeping -- not the target's own state -- is what decides whether a unit runs again: if a change
unit is edited after it has already been recorded as applied, none of these tools re-runs it automatically (see
<<Checksums / Hashes>>). If a change unit's logic is not naturally idempotent (e.g. `INSERT` without a guard,
or a MongoDB update that isn't safe to repeat), and it somehow does run twice -- a partially-applied run retried
after a crash, for instance -- it must not corrupt data or fail hard the second time. The general fix is to guard
the operation itself: `CREATE TABLE IF NOT EXISTS`, an `upsert` instead of an unconditional insert, or an explicit
existence check before acting.

=== A Worked Example: The Bookshop Seed Data

The running example of this section is a small online bookshop whose `customer` data evolves from a single
`full_name` field to separate first and last names. The first version seeds two customers. Written as an
unguarded insert, it creates duplicates if it ever runs twice; written as an upsert it does not:

[source,java]
----
// not idempotent: a second run inserts the same customers again
customers.insertOne(new Document("email", "ada@example.com").append("fullName", "Ada Lovelace"));

// idempotent: a second run finds the document and changes nothing
customers.updateOne(
    Filters.eq("email", "ada@example.com"),
    Updates.setOnInsert("fullName", "Ada Lovelace"),
    new UpdateOptions().upsert(true));
----

Idempotency is a second line of defence, not a substitute for the audit table: the tool already prevents a
recorded unit from running again, and idempotency covers the gap where the data was changed but the record was
never written. In a relational database the same gap exists for databases that commit DDL implicitly (see
xref:database/schema-evolution/liquibase-tracking-and-locking.adoc[Liquibase: Tracking & Locking]).

== Checksums / Hashes

Liquibase computes a *checksum* (or hash) of a changeset's content the first time it runs, and stores it
alongside the record of execution. On every later run, Liquibase recomputes the checksum and compares it: a
mismatch means an already-applied changeset was edited after the fact, which is exactly the situation idempotency
assumptions can't protect against, because the tool has no way to know whether the edited version was ever
actually run. Liquibase treats this as a validation failure by default and stops (see
xref:database/schema-evolution/liquibase-tracking-and-locking.adoc[Liquibase: Tracking & Locking] for how to
resolve one). Mongock and Flamingock have no equivalent check for their code-based change units -- identity is
just the declared `id`, with no content hash, so editing an already-applied `@ChangeUnit`/`@Change` class doesn't
fail loudly: the tool simply never re-runs it anywhere it already ran, silently and without error. Either way,
the fix is the same: never edit an applied change unit -- append a new one that makes the additional change
instead (see xref:database/schema-evolution/best-practices.adoc[Best Practices]).

== The Audit / Tracking Table

Each tool persists a durable record of what ran, when, by whom (as declared in the change unit), and its
checksum. Liquibase writes this to the `DATABASECHANGELOG` table inside the target database itself
(xref:database/schema-evolution/liquibase-tracking-and-locking.adoc[Liquibase: Tracking & Locking]). Mongock
writes to an audit collection in the target MongoDB deployment. Flamingock generalizes this into a configurable
*audit store*, decoupled from any single target system, since a Flamingock pipeline may not even have a
database as one of its targets
(xref:database/schema-evolution/flamingock-changes-and-target-systems.adoc[Flamingock: Changes & Target
Systems]).

What each tool really writes, from runs of the same bookshop migration against PostgreSQL and MongoDB:

[cols="1,3"]
|===
|Tool |Tracking record

|Liquibase
|One row per changeset in `DATABASECHANGELOG`, written *after* it ran: `id`, `author`, `filename`, `exectype`,
`orderexecuted` and an `md5sum` such as `9:0129796fdb343c9a0ea83f1098474ab9`.

|Mongock
|Documents in the `mongockChangeLog` collection with `changeId`, `author`, `state` (`EXECUTED`), `type`,
`changeLogClass`, `executionMillis` and `executionHostname`. No checksum field. Mongock also records its own
internal `system-change-00001` units and a `_before` entry for every unit with a `@BeforeExecution` method.

|Flamingock
|Documents in the `flamingockAuditLog` collection with `changeId`, `stageId`, `state`, `targetSystemId`,
`changeOrder`, `recoveryStrategy` and `transactionFlag`. Each change has a `STARTED` document followed by an
`APPLIED`, `FAILED` or `ROLLED_BACK` one.
|===

== Distributed Locking

Before executing anything, each tool acquires a *distributed lock* so that two application instances starting up
concurrently -- the common case in a horizontally scaled deployment -- don't both try to run the same pending
change units at once. Liquibase's lock lives in the `DATABASECHANGELOGLOCK` table
(xref:database/schema-evolution/liquibase-tracking-and-locking.adoc[Liquibase: Tracking & Locking]); Mongock
acquires a lock document in its own lock collection before a migration run
(xref:database/schema-evolution/mongock-transactions-and-locking.adoc[Mongock: Transactions & Locking]);
Flamingock does the same against its configured audit store. The lock lives in `DATABASECHANGELOGLOCK` for Liquibase, in the `mongockLock` collection for Mongock and in
`flamingockLock` for Flamingock. In every tool, a process that crashes while holding the lock can leave it
stuck, and each tool provides a way to release it manually.

== Contexts / Environments

Sometimes a change unit should run in some environments and not others -- a seed-data changeset for `test` but
never `production`, say. Liquibase supports this natively with *contexts* and *labels*
(xref:database/schema-evolution/liquibase-preconditions-contexts-labels.adoc[Liquibase: Preconditions, Contexts &
Labels]). Mongock and Flamingock have no context or label syntax in the change unit itself, so the same result is achieved
at the application level -- typically by pointing the runner at a different package of change classes per
environment (for Flamingock, a different stage location), by conditionally registering a class, or by using
Spring profiles -- since their changelog is code rather than a declarative file with a built-in filtering
mechanism.

== Forward-Only vs. Reversible Changes

A change unit can define only how to move forward, or it can also define its own inverse. Liquibase can often
*auto-generate* the inverse for simple, well-known change types (`createTable` → `dropTable`) and otherwise
requires an explicit `<rollback>` block
(xref:database/schema-evolution/liquibase-rollback.adoc[Liquibase: Rollback]). Mongock's
`@RollbackExecution` and Flamingock's `@Rollback` are both explicit methods the author writes by hand -- there is
no automatic inverse for arbitrary code, and for a non-transactional target system (a message queue, a REST API)
a rollback method is often the *only* way to undo a partially-applied change
(xref:database/schema-evolution/flamingock-changes-and-target-systems.adoc[Flamingock: Changes & Target
Systems]).

== Dry Run / Preview

Before actually applying anything, it is useful to see what *would* run. Liquibase's `updateSQL` command prints
the SQL a real `update` would execute without running it. Mongock and Flamingock don't expose an equivalent
preview command in the same way, since their change units are compiled code rather than declarative SQL/YAML --
the closer equivalent there is reading the pending-change-unit list the tool computes at startup (visible in
its logs) before it executes anything, or testing a Change in isolation
(xref:database/schema-evolution/flamingock-testing.adoc[Flamingock: Testing]).
