== Transactional Execution

MongoDB supports multi-document ACID transactions only on a *replica set or sharded cluster* -- never on a
standalone `mongod`. When the target deployment supports it, Mongock wraps a change unit's `@Execution` in a
transaction automatically: the `MongoDatabase` it injects is already bound to the session, so if the method throws
partway through, every write it made is rolled back by MongoDB itself, rather than being left half-applied.

The bookshop example shows it. The third change unit sets `vip = true` on every customer and then throws. On a
one-node replica set the run aborts, the collection is untouched, and the unit is not recorded, so a corrected
deployment retries it:

[mermaid]
....
sequenceDiagram
    participant M as Mongock runner
    participant S as ClientSession
    participant DB as MongoDB replica set
    participant A as mongockChangeLog
    M->>S: startTransaction
    M->>DB: updateMany set vip = true (inside the transaction)
    M->>M: unit throws IllegalStateException
    M->>S: abortTransaction
    S->>DB: discard the updateMany
    Note over A: no EXECUTED entry for tag-vip-customers
    M-->>M: stop with MongockException
....

This is exactly why `@BeforeExecution` exists (xref:database/schema-evolution/mongock-changeunits.adoc[Mongock:
ChangeUnits]): operations MongoDB disallows inside a transaction -- creating a collection or an index chief among
them -- have to run outside it, which is what that hook is for. A unit that must do something transactions cannot
cover can also opt out entirely with `@ChangeUnit(transactional = false)`, in which case its writes are applied
immediately and cannot be undone by an abort.

=== What Happens on a Standalone `mongod`

Because transactions need a replica set, the default transactional setup does *not* quietly degrade on a standalone
server. Running the bookshop runner against a plain `mongod` aborts before any change unit runs, while Mongock is
creating its own bookkeeping, and records its housekeeping unit as rolled back:

[source,text]
----
ERROR io.mongock.runner.core.executor.system.SystemUpdateExecutor - Mongock has failed executing system updates
io.mongock.api.exception.MongockException: com.mongodb.MongoClientException: This MongoDB deployment does not support retryable writes. Please add retryWrites=false to your connection string.
Caused by: com.mongodb.MongoCommandException: Command failed with error 20 (IllegalOperation): 'Transaction numbers are only allowed on a replica set member or mongos'

> db.mongockChangeLog.find({}, {_id: 0, changeId: 1, state: 1})
[ { changeId: 'system-change-00001_before', state: 'ROLLED_BACK' } ]
----

The remedies are the ones the message names: run the target as a (even one-node) replica set, which is also what
production MongoDB deployments should be, or configure Mongock for non-transactional operation as described in
https://docs.mongock.io/[the Mongock Documentation]. If you do run non-transactionally, idempotency
(xref:database/schema-evolution/core-concepts.adoc[Core Concepts]) becomes the only safety net against a
partially-applied run, and `@RollbackExecution` is what an operator can use to compensate.

== The Distributed Lock

Before running any pending change units, Mongock acquires a lock document in its own lock collection,
`mongockLock`, in the target MongoDB deployment -- the same distributed-locking concept every tool in this guide
implements (xref:database/schema-evolution/core-concepts.adoc[Core Concepts]). This is what prevents two instances
of an application starting up concurrently from both attempting to run the same change units.

[mermaid]
....
sequenceDiagram
    participant A as Instance A
    participant B as Instance B
    participant L as mongockLock
    A->>L: insert lock document with an expiry
    L-->>A: acquired
    B->>L: try to acquire
    L-->>B: held by A, wait
    A->>A: run pending change units
    A->>L: release
    B->>L: acquired
    B->>B: nothing pending
    B->>L: release
....

After a successful run `mongockLock` is empty again: the lock document exists only while a run is in progress. The
lock is created with an expiry, so a process that crashes while holding it does not block deployments forever:
the document expires based on Mongock's configured lock lease duration. The runner also exposes settings for how
long to wait for a held lock and whether to throw or carry on when it times out -- consult
https://docs.mongock.io/[Mongock Documentation] for the exact lock-acquisition and lease settings for the version
in use. Choose a lease longer than your slowest migration, because a unit that outlives the lease can let a second
instance start the same work.

== Multi-Tenant Considerations

A common Mongock deployment shape is one application serving many tenants, each with its own MongoDB database
(or, less commonly, a shared database with tenant-scoped collections). Running the same change units against
every tenant database raises two considerations:

* *Per-tenant tracking* -- Mongock's audit collection needs to live per tenant (alongside that tenant's own
  data), or be keyed by tenant, so that one tenant's applied change units are tracked independently of every
  other tenant's. Running the standard single-database setup once per tenant connection, iterating tenants in
  the application startup code, is the usual approach:
+
[source,java]
----
for (String tenantDb : tenantDatabases) {
    MongockStandalone.builder()
        .setDriver(MongoSync4Driver.withDefaultLock(client, tenantDb))
        .addMigrationScanPackage("com.example.bookshop.migrations")
        .buildRunner()
        .execute();
}
----
* *Partial failure across tenants* -- if a change unit succeeds for some tenants and fails for others (a
  transient error, a tenant with an unexpected existing data shape), the tenants are now in different states. The
  application needs its own retry/alerting strategy for this, since Mongock's transactional guarantee
  (<<Transactional Execution>>) is scoped to one execution against one target, not to a fan-out across many.
  Collect the failures per tenant instead of letting the first exception end the loop, and remember that
  tenants that were skipped simply run the same units on the next start.

For guidance on when a system's needs outgrow Mongock's MongoDB-only model, see
xref:database/schema-evolution/choosing-a-migration-tool.adoc[Choosing a Migration Tool].
