= Getting Started
:description: Introduces PostgreSQL, how it is distributed, how to run it in Docker, how to drive it with psql, how to load the shop seed used throughout this section, and a first working session.
:keywords: PostgreSQL, Postgres, psql, Docker, getting started, shop seed, connection string, postgres image, PGDATA, versions, release policy

include::partial$ai-disclaimer.adoc[]

PostgreSQL is an open-source *object-relational database management system*. It stores data in tables of typed
rows, speaks SQL (with a large and well-documented conformance to the standard), and adds its own extensions on
top: arrays, ranges, enums, `jsonb`, full-text search, user-defined types and operators, and a rich extension
mechanism. It is ACID by default, uses multiversion concurrency control so readers never block writers, and is
developed by a community project rather than by a single vendor. This page explains where it fits, runs a real
server in a container, introduces `psql`, loads the shop dataset that the rest of this section reuses, and walks
through a first session.

Everything shown here was executed against *PostgreSQL 18.6* (the `postgres:latest` Docker image on an arm64
host). Output is real; long results are trimmed and say so.

== What PostgreSQL is and where it fits

PostgreSQL is a general-purpose relational database. Typical roles are the primary store of an operational
application, a system of record for analytics-style queries over moderate volumes, a geospatial store (with the
PostGIS extension), a document store (through `jsonb`) and, with pgvector, a vector store. The trade-offs that
follow from its design:

* *Strong SQL and strong consistency.* Transactional DDL, constraints, deferrable foreign keys and
  serializable isolation are first-class. See xref:database/postgresql/transactions-and-mvcc.adoc[Transactions,
  Isolation & MVCC].
* *Extensibility.* New data types, index methods, procedural languages and whole feature sets ship as
  extensions. See xref:database/postgresql/extensions.adoc[Extensions].
* *Process-per-connection model.* Each client connection is a separate operating-system process, so a pooler
  is normal in front of busy applications. See xref:database/postgresql/architecture.adoc[Architecture].
* *Single-primary write scaling.* Writes go to one primary; read scaling and availability come from replicas.
  See xref:database/postgresql/replication-and-ha.adoc[Replication & High Availability].

For the engine-agnostic SQL language itself (DDL, queries, joins, window functions) see the sibling
xref:database/sql/index.adoc[SQL Reference]; for choosing between engines see
xref:database/choosing-the-right-database.adoc[Choosing the Right Database].

== Editions and distribution

There is exactly one PostgreSQL: the open-source server released under the permissive
https://www.postgresql.org/about/licence/[PostgreSQL License] by the PostgreSQL Global Development Group. There
is no "community versus enterprise" split in the core server. What varies is how it is packaged and operated:

* *Official source and packages.* Source tarballs, the PGDG apt and yum repositories, and the interactive
  installers listed on https://www.postgresql.org/download/[the download page].
* *Docker images.* The official https://hub.docker.com/_/postgres[`postgres` image], used on this page.
* *Vendor distributions and forks.* Commercial distributions and hosted services (managed cloud offerings,
  vendor builds with extra tooling) package the same core, sometimes with additions. They are outside the scope
  of this section.

The project releases one *major version* per year, supports each for five years, and publishes quarterly *minor*
releases containing only bug and security fixes. Since version 10 a version number is `major.minor` (for
example `18.6`); upgrading between minors is a binary swap and restart, while a major upgrade needs `pg_upgrade`
or a dump and restore. The authoritative policy is the
https://www.postgresql.org/support/versioning/[versioning policy].

== Running PostgreSQL in Docker

The official image initialises a new cluster on first start. Only `POSTGRES_PASSWORD` is mandatory:

[source,bash]
----
docker run -d --name pg --restart unless-stopped \
  -e POSTGRES_PASSWORD=secret \
  -p 5432:5432 \
  -v pgdata:/var/lib/postgresql \
  postgres:latest
----

[NOTE]
====
From PostgreSQL 18 the image keeps the cluster in a version-specific directory, `PGDATA=/var/lib/postgresql/18/docker`,
and declares `/var/lib/postgresql` as its volume. Mount the volume at `/var/lib/postgresql`, not at
`/var/lib/postgresql/data` as older tutorials show, so that one volume can hold the data directories of several major versions.
====

[mermaid]
....
flowchart LR
  H["host: docker exec or a psql client"] -->|"port 5432"| S
  subgraph CT["container pg (postgres:latest)"]
    S["postgres server"] --> V[("volume pgdata at /var/lib/postgresql")]
  end
....

Wait until the server accepts connections, then ask it who it is:

[source,bash]
----
docker exec pg pg_isready -U postgres
docker exec pg psql -U postgres -c "SELECT version()"
----

[source,text]
----
/var/run/postgresql:5432 - accepting connections
                                                         version                                                          
--------------------------------------------------------------------------------------------------------------------------
 PostgreSQL 18.6 (Debian 18.6-1.pgdg13+2) on aarch64-unknown-linux-gnu, compiled by gcc (Debian 14.2.0-19) 14.2.0, 64-bit
(1 row)
----

Useful environment variables of the image: `POSTGRES_USER` (default `postgres`), `POSTGRES_DB` (default equal to
the user), `POSTGRES_INITDB_ARGS` (for example `--data-checksums`, which is already the default from 18) and any
`+*.sql+` or `+*.sh+` file mounted under `/docker-entrypoint-initdb.d/`, which runs once when the cluster is created.
The official `postgres` image, like any container, is covered in xref:backend/docker/index.adoc[Docker].

== psql basics

`psql` is the interactive terminal client shipped with the server. In the container it is already installed, so
the examples use `docker exec -it pg psql -U postgres`; on a workstation the same flags apply
(`psql -h localhost -p 5432 -U postgres`).

[source,bash]
----
docker exec -it pg psql -U postgres          # interactive session
docker exec pg psql -U postgres -c "SELECT 1" # one statement, then exit
docker exec -i pg psql -U postgres < file.sql # run a script from the host
----

Two kinds of input exist: SQL statements, terminated by a semicolon, and *backslash meta-commands*, which
`psql` itself interprets and which need no semicolon. The ones used most often:

[cols="2,5"]
|===
|Command |Purpose

|`\?` / `\h CREATE INDEX`
|Help on meta-commands / on the syntax of an SQL command.

|`\conninfo`
|Show the current connection (database, user, socket or host, backend PID).

|`\l` / `\c dbname`
|List databases / connect to another database.

|`\dn`, `\dt`, `\d table`
|List schemas, list tables, describe a table (columns, indexes, constraints, references).

|`\x`
|Toggle expanded (one field per line) output; `\x auto` switches by width.

|`\timing`
|Print the elapsed time of each statement.

|`\i file`, `\copy`
|Run a script file; client-side `COPY` from or to a local file.

|`\q`
|Quit.
|===

The meta-commands for data work (`\copy`, `\gset`,
`\gexec`, `\watch`) are covered in xref:database/postgresql/data-types-and-sql.adoc[Data Types & PostgreSQL-specific SQL].

== Connecting

A client connects to a database as a role over a Unix socket or TCP. The same information can be given as
discrete flags, environment variables (`PGHOST`, `PGPORT`, `PGUSER`, `PGDATABASE`, `PGPASSWORD`) or a *connection
URI*:

[source,text]
----
postgresql://postgres:secret@localhost:5432/postgres?sslmode=prefer&application_name=reporting
----

The `sslmode`, `connect_timeout` and `application_name` parameters are the ones you meet first;
`application_name` is visible in `pg_stat_activity`, which makes it worth setting from every application.
Inside the container the default `pg_hba.conf` trusts local socket and loopback connections, which is why the
`docker exec` commands above need no password; connections over TCP from the host (any other address) use
`scram-sha-256` and therefore the password. Who may connect, and how,
is the subject of xref:database/postgresql/administration.adoc[Administration].

Common connection problems: `connection refused` (server down, wrong port, or `listen_addresses` not including
the interface), `no pg_hba.conf entry` (the host, database, user and method are not allowed), `password
authentication failed`, and `too many clients already` (the `max_connections` limit, 100 by default, is
reached).

== Loading the shop seed

The rest of this section reuses a small online shop: `customers`, `products`, `orders` and `order_items`, in a
schema named `shop` (4 customers, 5 products, 8 orders and 11 order lines). The same data set backs the
xref:database/mongodb/index.adoc[MongoDB Reference]. Save the following script as `seed.sql`.

[source,sql]
----
-- seed.sql -- the relational "shop" running example (PostgreSQL)
DROP SCHEMA IF EXISTS shop CASCADE;
CREATE SCHEMA shop;
SET search_path = shop;

CREATE TABLE customers (
  id         text PRIMARY KEY,
  name       text NOT NULL,
  email      text NOT NULL UNIQUE,
  city       text NOT NULL,
  tier       text NOT NULL CHECK (tier IN ('free', 'pro', 'enterprise')),
  created_at timestamptz NOT NULL
);

CREATE TABLE products (
  sku      text PRIMARY KEY,
  name     text NOT NULL,
  category text NOT NULL,
  price    numeric(10,2) NOT NULL CHECK (price >= 0),
  stock    integer NOT NULL CHECK (stock >= 0),
  tags     text[] NOT NULL DEFAULT '{}',
  attrs    jsonb NOT NULL DEFAULT '{}'
);

CREATE TABLE orders (
  id          integer PRIMARY KEY,
  customer_id text NOT NULL REFERENCES customers(id),
  status      text NOT NULL CHECK (status IN ('open', 'shipped', 'cancelled')),
  order_date  timestamptz NOT NULL
);

CREATE TABLE order_items (
  order_id integer NOT NULL REFERENCES orders(id),
  sku      text NOT NULL REFERENCES products(sku),
  qty      integer NOT NULL CHECK (qty > 0),
  price    numeric(10,2) NOT NULL,
  PRIMARY KEY (order_id, sku)
);

[source,bash]
----

The `NOTICE` appears on a fresh cluster because `DROP SCHEMA IF EXISTS` found nothing to drop. The script
re-creates the schema every time, so it is safe to re-run.

To avoid typing `shop.` everywhere, set the schema search path for the session (or permanently with
`+ALTER ROLE ... SET search_path+`):

[source,sql]
----
SET search_path = shop, public;
SHOW search_path;
----

Where PostgreSQL stores the cluster and which port and version it runs on are also queryable:

[source,sql]
----
SHOW server_version;
SHOW data_directory;
SELECT name, setting FROM pg_settings WHERE name IN ('port', 'max_connections', 'data_checksums', 'wal_level');
----

== Versions

The version numbering, support policy and release notes are published at
https://www.postgresql.org/docs/release/[the release notes] and the
https://www.postgresql.org/support/versioning/[versioning page]. Notable features by version that matter for this
section:

[cols="1,5"]
|===
|Version |Highlights used or mentioned in these pages

|12
|Stored generated columns; CTEs inlined by default (the `MATERIALIZED` keyword restores the old behaviour).

|13
|Incremental sort; B-tree index deduplication.

|14
|Multirange types; `scram-sha-256` as the default password hash.

|15
|`MERGE`.

|16
|SQL/JSON constructors such as `JSON_OBJECT`; `pg_stat_io`; logical decoding on standbys.

|17
|`JSON_TABLE` and more SQL/JSON query functions; `+MERGE ... RETURNING+`.

|18
|Asynchronous I/O (`io_method`); data checksums enabled by default in `initdb`; virtual generated columns;
`uuidv7()`; `OLD` and `NEW` in `RETURNING`.
|===

Features introduced after the baseline are called out where they appear. See the
xref:database/postgresql/index.adoc[section index] for the reading path.
