= Connecting from an application & the tooling
:description: How applications talk to MongoDB -- the official drivers and their shared CRUD/aggregation surface, the connection-string URI and its options, connection pooling and the singleton client, the Stable API, and the mongosh/Compass/Database Tools/Atlas CLI tooling.
:keywords: mongodb, drivers, pymongo, node driver, connection string, mongodb+srv, replica set, authSource, retryWrites, write concern, readPreference, tls, connection pool, maxPoolSize, singleton client, stable api, apiVersion, mongosh, mongoshrc, compass, database tools, atlas cli

include::partial$ai-disclaimer.adoc[]

An application never speaks the wire protocol directly -- it uses an official driver, configured by a
connection-string URI, holding a pooled connection to the deployment. This page covers the drivers, the URI
and its options, why the client is a singleton, the Stable API, and the surrounding command-line and GUI
tooling.

[mermaid]
....
flowchart LR
    APP[Application code] --> API["Driver API: collection.find, insertOne, aggregate"]
    API --> POOL["Connection pool (one per server)"]
    MON["Monitor threads: topology discovery, heartbeats"] --> POOL
    POOL -->|"wire protocol over TCP, optionally TLS"| RS[(Replica set or mongos)]
    URI["Connection string URI"] -.configures.-> API
    URI -.configures.-> POOL
....

All examples on this page work against the `shop.orders` collection of the running example: three orders, two of them
`OPEN`. The same three-line task, finding the open orders newest first and totalling them per customer, is
shown below in Node.js, Python and Java, and each program was run against a live server and produced the same answer.

== Official drivers

MongoDB publishes and maintains drivers for Node.js, Python (PyMongo), Java, C#/.NET, Go, Rust, PHP, Ruby,
C++, Kotlin, and Scala. They differ in idiom -- callbacks and promises, blocking and async, builders and
plain documents -- but every one exposes the same operations you use in `mongosh`: `insertOne`/`insertMany`,
`find`, `updateOne`/`updateMany`, `deleteOne`/`deleteMany`, `aggregate`, `bulkWrite`, transactions, and
change streams. Learning the query and pipeline language once carries across all of them. The PHP driver with
Laravel's MongoDB package is covered in xref:web/php-laravel/redis-mongodb-and-search.adoc[Redis, MongoDB and
Search].

[source,javascript]
----
// Node.js driver
import { MongoClient } from "mongodb";

const client = new MongoClient(process.env.MONGODB_URI);
const orders = client.db("shop").collection("orders");

await orders.insertOne({ customerId: 42, total: 19.99, status: "OPEN" });

const open = await orders
  .find({ status: "OPEN" })
  .sort({ orderDate: -1 })
  .limit(20)
  .toArray();

const byCustomer = await orders.aggregate([
  { $match: { status: "OPEN" } },
  { $group: { _id: "$customerId", total: { $sum: "$total" } } }
]).toArray();
----

Run against the example data, the two queries print:

[source,text]
----
[ { customerId: 7, total: 12.5 }, { customerId: 42, total: 19.99 } ]
[ { _id: 7, total: 12.5 }, { _id: 42, total: 19.99 } ]
----

The same three operations in PyMongo -- identical query documents, identical pipeline:

[source,python]
----
from pymongo import MongoClient, DESCENDING
import os

client = MongoClient(os.environ["MONGODB_URI"])
orders = client["shop"]["orders"]

orders.insert_one({"customerId": 42, "total": 19.99, "status": "OPEN"})

open_orders = list(
    orders.find({"status": "OPEN"}).sort("orderDate", DESCENDING).limit(20)
)

by_customer = list(orders.aggregate([
    {"$match": {"status": "OPEN"}},
    {"$group": {"_id": "$customerId", "total": {"$sum": "$total"}}},
]))
----

The JVM flavour uses the same operations with typed *builders* (`Filters`, `Sorts`, `Aggregates`) in place of
raw documents, which gives compile-time checking of the shape of a query but produces exactly the same BSON on
the wire. This is a complete program (Maven dependency `org.mongodb:mongodb-driver-sync`):

[source,java]
----
package demo;

import com.mongodb.client.MongoClient;
import com.mongodb.client.MongoClients;
import com.mongodb.client.MongoCollection;
import org.bson.Document;

import java.util.List;

import static com.mongodb.client.model.Accumulators.sum;
import static com.mongodb.client.model.Aggregates.group;
import static com.mongodb.client.model.Aggregates.match;
import static com.mongodb.client.model.Aggregates.sort;
import static com.mongodb.client.model.Filters.eq;
import static com.mongodb.client.model.Sorts.ascending;
import static com.mongodb.client.model.Sorts.descending;

public class Shop {
    public static void main(String[] args) {
        // one client for the whole process
        try (MongoClient client = MongoClients.create(System.getenv("MONGODB_URI"))) {
            MongoCollection<Document> orders = client.getDatabase("shop").getCollection("orders");

            for (Document d : orders.find(eq("status", "OPEN")).sort(descending("orderDate")).limit(20)) {
                System.out.println(d.getInteger("customerId") + " " + d.get("total"));
            }

            orders.aggregate(List.of(
                    match(eq("status", "OPEN")),
                    group("$customerId", sum("total", "$total")),
                    sort(ascending("_id"))))
                .forEach(d -> System.out.println(d.toJson()));
        }
    }
}
----

[source,text]
----
7 12.5
42 19.99
{"_id": 7, "total": 12.5}
{"_id": 42, "total": 19.99}
----

The surface is deliberately parallel across languages. The same operations, side by side:

[cols="2,3,3,3",options="header"]
|===
| Operation | `mongosh` / Node.js | PyMongo | Java (sync driver)

| Insert one | `insertOne(doc)` | `insert_one(doc)` | `insertOne(doc)`
| Filter and sort | `find(f).sort(s)` | `find(f).sort(key, direction)` | `find(f).sort(s)`
| Update | `updateOne(f, u)` | `update_one(f, u)` | `updateOne(f, u)`
| Pipeline | `+aggregate([...])+` | `+aggregate([...])+` | `+aggregate(List.of(...))+`
| Session | `startSession()` | `start_session()` | `startSession()`
| Transaction | `withTransaction(fn)` | `with_transaction(fn)` | `withTransaction(body)`
| Change stream | `watch(pipeline)` | `watch(pipeline)` | `watch(pipeline)`
|===

Naming follows each language's conventions (camelCase against snake_case), but the *documents* inside are the same:
a query filter written for `mongosh` can be pasted into a Python dictionary or a `+Document.parse(...)+` call. The
transaction and change-stream calls are used for real in
xref:database/mongodb/transactions.adoc[Multi-document ACID transactions] and
xref:database/mongodb/change-streams.adoc[Reacting to data changes].

See https://www.mongodb.com/docs/drivers/[MongoDB Drivers] for the per-language guides, and
xref:database/mongodb/crud-query.adoc[CRUD: query] for the query language the driver examples above reuse
verbatim.

== The connection string URI

Every driver is configured from one URI. The two schemes:

* `mongodb://host1:27017,host2:27017,host3:27017/?replicaSet=rs0` -- an explicit *seed list*. You name every
  member; the driver discovers the rest of the topology from them.
* `mongodb+srv://cluster.example.com/` -- *DNS seedlist*. A single hostname whose DNS `SRV` records supply the
  member list and whose `TXT` record supplies default options. Atlas hands you this form; it means the member
  list can change without touching the app.

Common options, given as URI query parameters:

* `replicaSet=rs0` -- the replica-set name the driver must verify it is connected to.
* `authSource=admin` -- the database that holds the user's credentials (often `admin`, not the app database).
* `retryWrites=true` -- retry a write once, automatically, after a transient network error or a failover
  (the default in current drivers).
* `w=majority` -- default write concern: acknowledge only after a majority of members have the write.
* `readPreference=secondaryPreferred` -- where reads may be routed (`primary` by default).
* `tls=true` -- require TLS for the connection (implied by `mongodb+srv://`).
* `maxPoolSize=100` -- upper bound on connections in the pool (see below).

[source,javascript]
----
const uri =
  "mongodb+srv://appuser:pw@cluster.example.com/shop" +
  "?authSource=admin&retryWrites=true&w=majority" +
  "&readPreference=secondaryPreferred&maxPoolSize=50";
----

[source,python]
----
uri = (
    "mongodb://appuser:pw@rs1:27017,rs2:27017,rs3:27017/shop"
    "?replicaSet=rs0&authSource=admin&retryWrites=true&w=majority&tls=true"
)
----

What the driver makes of a URI can be checked without connecting. PyMongo's parser, applied to a seed-list URI with
options, returns:

[source,python]
----
from pymongo.uri_parser import parse_uri
u = parse_uri("mongodb://appuser:pw@rs1:27017,rs2:27017,rs3:27017/shop"
              "?replicaSet=rs0&authSource=admin&retryWrites=true&w=majority&tls=true"
              "&maxPoolSize=50&readPreference=secondaryPreferred")
print(u["nodelist"], u["database"], u["username"])
print(u["options"])
----

[source,text]
----
[('rs1', 27017), ('rs2', 27017), ('rs3', 27017)] shop appuser
{'replicaSet': 'rs0', 'readPreference': 'secondaryPreferred', 'maxPoolSize': 50, 'w': 'majority',
 'authSource': 'admin', 'tls': True, 'retryWrites': True}
----

Note the two different databases in that URI: `shop` is the *default database* of the connection, `authSource=admin`
is where the user `appuser` is looked up. They are unrelated, and mixing them up is the commonest cause of
authentication failures. Against a server with access control, the user `orders-app` created in the `shop` database
connects only with `authSource=shop`:

[source,text]
----
mongodb://orders-app:...@localhost:27017/shop?authSource=admin  ->  MongoServerError: Authentication failed.
mongodb://orders-app:...@localhost:27017/shop?authSource=shop   ->  connected as orders-app
mongodb://orders-app:wrong@localhost:27017/shop?authSource=shop ->  MongoServerError: Authentication failed.
----

The server deliberately returns the *same* error for an unknown user, a wrong password and a wrong `authSource`, so
that an attacker learns nothing; check the three in that order when it happens to you. Because a URI contains a
password, keep it in an environment variable or a secret store, and percent-encode special characters in the
password (`@` becomes `%40`).

See https://www.mongodb.com/docs/manual/reference/connection-string/[Connection String URI Format] for every
option, and xref:database/mongodb/replication.adoc[Replication] for how the seed list and `replicaSet` name
drive topology discovery and failover.

== Connection pooling and the singleton client

The driver's client object owns a *connection pool* per server -- a set of reusable sockets, capped at
`maxPoolSize` -- plus background threads that monitor topology. Creating a client is therefore expensive:
DNS resolution, TCP and TLS handshakes, an initial `hello` to every member, and authentication.

The cost is measurable even on a local machine with no TLS and no authentication. Thirty throw-away clients, each
doing one `find` and kept open, made the server hold 90 more connections (about three per client: one pooled
socket and two monitoring sockets). And 200 operations each with a brand-new client took 2.13 ms per operation
against 0.22 ms per operation on one shared client, roughly ten times slower, before a single byte of TLS or a
network round trip over a real link is added.

Create *one client for the lifetime of the process* and share it across all requests. A new client per
request (or per function invocation) exhausts server connections, adds handshake latency to every call, and
defeats the pool. In serverless runtimes, cache the client outside the handler so it survives warm
invocations.

[source,javascript]
----
// module scope -- created once, imported everywhere
export const client = new MongoClient(process.env.MONGODB_URI, { maxPoolSize: 50 });
await client.connect();
----

See https://www.mongodb.com/docs/manual/administration/connection-pool-overview/[Connection Pool Overview] and
your driver's connection-management guide.

== The Stable API

Declaring `+{ apiVersion: "1" }+` on the client opts every operation into a versioned, backward-compatible
subset of the server API. The server then guarantees those commands behave identically across future
releases, so a server upgrade cannot silently change your app's behaviour. Add `strict: true` to have the
server reject any command outside the versioned set, which surfaces accidental use of unstable features at
development time.

[source,javascript]
----
const client = new MongoClient(uri, {
  serverApi: { version: "1", strict: true, deprecationErrors: true }
});
----

[source,python]
----
from pymongo.server_api import ServerApi
client = MongoClient(uri, server_api=ServerApi("1", strict=True, deprecation_errors=True))
----

`strict` is not decorative. Against the example server, a client declared with `ServerApi("1", strict=True)` could still
count orders, but a diagnostic command outside the versioned API was refused:

[source,text]
----
find via strict client: 3
serverStatus under strict: 323 APIStrictError - Provided apiStrict:true, but the command serverStatus is not in API Version 1.
collStats under strict: APIStrictError
----

That is the intended trade: an application that must not break on a server upgrade uses only versioned commands,
and administrative tooling (`serverStatus`, `collStats`) uses a separate client without `strict`.

See https://www.mongodb.com/docs/manual/reference/stable-api/[Stable API].

== Tooling

*mongosh* -- the interactive shell and a full JavaScript environment: it takes the same connection URI as a
driver, runs scripts with `mongosh --file script.js` or `+mongosh --eval '...'+`, and loads `+~/.mongoshrc.js+` on
startup for custom prompts, helpers, and default settings. It is the reference environment the CRUD and
aggregation pages are written against -- see xref:database/mongodb/getting-started.adoc[Getting started].

[source,bash]
----
mongosh "mongodb+srv://cluster.example.com/shop" --username appuser
mongosh --file migrate-orders.js "mongodb://localhost:27017"
----

A script run with `--file` prints only what it prints itself, which makes `mongosh` a convenient scripting tool for
operations work. For example, this file (`open-by-customer.js`) and its output against the example data:

[source,javascript]
----
// open-by-customer.js
const rows = db.getSiblingDB("shop").orders.aggregate([
  { $match: { status: "OPEN" } },
  { $group: { _id: "$customerId", total: { $sum: "$total" } } },
  { $sort: { _id: 1 } }
]).toArray();
rows.forEach(r => print(`customer ${r._id}: ${r.total}`));
----

[source,bash]
----
mongosh --quiet --file open-by-customer.js "mongodb://localhost:27017"
# customer 7: 12.5
# customer 42: 19.99
----

[source,javascript]
----
// ~/.mongoshrc.js
prompt = () => `${db.getName()}> `;
config.set("displayBatchSize", 20);
----

*MongoDB Compass* -- the official GUI: browse and edit documents, build queries and aggregation pipelines
visually, and read a graphical `explain` plan to see index usage. Useful for exploring an unfamiliar data set
and for prototyping a pipeline before pasting it into code.
https://www.mongodb.com/docs/compass/[Compass documentation].

*MongoDB Database Tools* -- the standalone bundle of `mongodump`, `mongorestore`, `mongoexport`,
`mongoimport`, `bsondump`, `mongostat`, `mongotop`, and `mongofiles`, versioned and installed separately from
the server. https://www.mongodb.com/docs/database-tools/[Database Tools]. See
xref:database/mongodb/backup-and-data-tools.adoc[Backups, import/export & GridFS] for how they are used.

*Atlas CLI* -- `atlas`, the command-line interface to MongoDB Atlas: create and manage clusters, database
users, network access, and backups, and spin up a local Atlas deployment for development. It targets the
hosted platform, so it is linked rather than documented here:
https://www.mongodb.com/docs/atlas/cli/current/[Atlas CLI].
