= What MongoDB is & how to run it
:description: Introduces MongoDB as a general-purpose document database, contrasts the document model with the relational model, and shows how to run a local mongod, connect with mongosh, and use mongosh as a JavaScript REPL.
:keywords: mongodb, document database, bson, mongod, mongosh, mongo shell, community edition, enterprise, atlas, mongoshrc, getting started

include::partial$ai-disclaimer.adoc[]

MongoDB is a general-purpose database that stores records as JSON-like *documents* rather than as rows in
fixed tables. It aims to be a primary datastore for operational applications -- the same role a relational
database usually fills -- while letting the shape of each record vary and letting a deployment scale
horizontally across many machines. This page explains the model and its trade-offs, then walks through
running a local server and driving it from the shell.

== The document model and where it fits

A MongoDB deployment holds one or more *databases*; each database holds *collections*; each collection holds
*documents*; each document is a set of *field*/value pairs. The tiers map cleanly onto the relational
vocabulary, with one difference: a collection does not impose a single column list on the documents it holds.

image::mongodb-document-hierarchy.svg["MongoDB database/collection/document/field hierarchy beside the relational database/table/row/column analogy, with each tier mapped to its counterpart",width=720,role=text-center]

A document that models an order can embed its line items as an array instead of splitting them into a
separate table:

[source,json]
----
{
  "_id": 1001,
  "customer": { "id": 42, "name": "Ada Lovelace" },
  "status": "OPEN",
  "items": [
    { "sku": "A-1", "qty": 2, "price": 9.99 },
    { "sku": "B-7", "qty": 1, "price": 19.00 }
  ]
}
----

The trade-offs that follow from this model:

* *Flexible schema.* Two documents in one collection may carry different fields. Structure is still real --
  it lives in the application and, optionally, in a
  https://www.mongodb.com/docs/manual/core/schema-validation/[JSON Schema validator] attached to the
  collection -- but the database does not require you to declare it up front or migrate every record when it
  changes.
* *Horizontal scale.* A collection can be https://www.mongodb.com/docs/manual/sharding/[sharded] across many
  servers on a shard key, spreading both data and load. See xref:database/mongodb/sharding.adoc[Sharding].
* *No server-side joins by default.* Related data is usually embedded in the same document and read in one
  operation. Cross-collection joins exist through the
  https://www.mongodb.com/docs/manual/reference/operator/aggregation/lookup/[`$lookup`] aggregation stage,
  but they are not the primary access pattern; xref:database/mongodb/data-modeling.adoc[Data modeling]
  covers embed-versus-reference.

For a narrative overview, see https://www.mongodb.com/docs/manual/introduction/[Introduction to MongoDB] and
the https://www.mongodb.com/docs/manual/tutorial/getting-started/[Getting Started tutorial] in the manual.

== How the pieces fit together

Before running anything it helps to know which process does what. Applications never touch data files: they
speak the MongoDB wire protocol to a `mongod` server through a *driver* (or through `mongosh`, Compass, or a
Database Tools command, which are all clients too). Inside `mongod`, a command is parsed, the query planner
chooses an index or a collection scan, the executor runs the plan, and the storage engine (WiredTiger) reads
and writes pages in its cache, protected by a write-ahead journal.

[mermaid]
....
flowchart LR
  subgraph Clients
    APP[Application + driver]
    SH[mongosh]
    CP[Compass]
  end
  subgraph mongod [mongod process]
    NET[Wire protocol listener]
    CMD[Command layer: auth, parse, validate]
    QE[Query planner and executor]
    SE[WiredTiger storage engine]
    NET --> CMD --> QE --> SE
  end
  APP --> NET
  SH --> NET
  CP --> NET
  SE --> J[(Journal)]
  SE --> D[(Data and index files in dbPath)]
....

Two consequences follow. First, everything a driver can do, `mongosh` can do too, so every example on these
pages can be pasted into a shell. Second, the unit of deployment is the `mongod` process: one process is a
*standalone*; several cooperating processes form a replica set (see
xref:database/mongodb/replication.adoc[Replica Sets & High Availability]) or a sharded cluster (see
xref:database/mongodb/sharding.adoc[Horizontal Scaling with Sharded Clusters]).

== Editions and how you run it

MongoDB ships in three forms:

* *Community Edition* -- the free, source-available server. Sufficient for development and for most
  self-managed production use.
* *Enterprise Advanced* -- Community plus commercial add-ons (in-memory storage engine, Kerberos/LDAP auth,
  auditing, `mongodbtools` such as `mongodecrypt`) and a support subscription.
* *Atlas* -- MongoDB's fully managed cloud service. It runs the same server and adds provisioning, backups,
  monitoring, and Atlas-only features (Atlas Search, Atlas Vector Search) on top. Atlas-only capabilities are
  linked from these pages, not documented step by step.

See https://www.mongodb.com/docs/manual/installation/[Install MongoDB] for packages for each platform.

=== Start a local mongod

`mongod` is the database server process. It listens on TCP port `27017` by default and needs a data
directory to exist before it starts:

[source,bash]
----
mkdir -p /data/db

# Foreground server, explicit data directory and bind address.
mongod --dbpath /data/db --bind_ip 127.0.0.1 --port 27017

# Equivalent settings in a config file (mongod --config /etc/mongod.conf):
#   https://www.mongodb.com/docs/manual/reference/configuration-options/
----

[source,yaml]
----
# /etc/mongod.conf
storage:
  dbPath: /data/db
net:
  bindIp: 127.0.0.1
  port: 27017
----

xref:database/mongodb/storage-and-durability.adoc[Storage & durability] covers the data files `--dbpath`
manages; xref:database/mongodb/administration-and-monitoring.adoc[Administration & monitoring] covers running
`mongod` as a managed service.

=== Connect with mongosh

`mongosh` is the official shell. With no arguments it connects to `mongodb://127.0.0.1:27017`:

[source,console]
----
$ mongosh
test> show dbs
admin   40.00 KiB
config  12.00 KiB
local   40.00 KiB
test> use shop
switched to db shop
shop> db.orders.insertOne({ _id: 1001, status: "OPEN" })
{ acknowledged: true, insertedId: 1001 }
shop> show collections
orders
shop> db.orders.find()
[ { _id: 1001, status: 'OPEN' } ]
----

`show dbs` lists databases, `use <db>` selects one (and creates it lazily on first write), `show
collections` lists its collections, and `db.<coll>.find()` reads documents. Full command reference:
https://www.mongodb.com/docs/mongodb-shell/[the mongosh documentation]. The `db.<coll>.find()` /
`insertOne()` calls are the Query API, covered in xref:database/mongodb/crud-query.adoc[Querying documents]
and xref:database/mongodb/crud-insert-and-write-concern.adoc[Inserting documents].

== mongosh is a JavaScript REPL

`mongosh` evaluates JavaScript. Query results are ordinary values you can assign and manipulate, and a
`find()` returns a cursor:

[source,javascript]
----
// Assign a result and work with it as a normal object.
const order = db.orders.findOne({ _id: 1001 })
order.status                       // 'OPEN'

// find() returns a cursor; the shell prints the first batch (20 docs) and
// leaves the cursor open. Type `it` to page through the rest.
db.orders.find({ status: "OPEN" })
// Type:  it        -> next batch

// Drive the cursor explicitly instead of relying on `it`.
db.orders.find().forEach(doc => print(doc._id))

// Cursor helpers: https://www.mongodb.com/docs/manual/reference/method/js-cursor/
db.orders.find().sort({ _id: -1 }).limit(5).toArray()
----

Startup and scripting:

[source,bash]
----
# ~/.mongoshrc.js runs on every interactive start -- put helpers and prompt
# tweaks there. https://www.mongodb.com/docs/mongodb-shell/reference/startup/
echo 'prompt = () => `${db.getName()}> `;' >> ~/.mongoshrc.js

# Run a script file non-interactively (exits when the file finishes).
mongosh "mongodb://127.0.0.1:27017/shop" seed.js

# Or load a file into the current interactive session.
#   shop> load("seed.js")
----

`mongosh` replaces the legacy `mongo` shell, which is no longer shipped with the server.

== Hands-on: MongoDB in Docker and the running example

The quickest way to get a disposable server is the official `mongo` image. Every example in this section runs
against the same small *online shop* -- a `shop` database with `customers`, `products` and `orders` -- so that
the pages build on one another. The container below starts `mongod` as a one-member replica set: that costs
nothing locally, and it unlocks `w: "majority"` writes, transactions, change streams and the oplog on later
pages. (Use any free host port in place of `27017` if it is already taken.)

[source,bash]
----
docker run -d --name mongo-shop -p 27017:27017 mongo:8 mongod --replSet rs0 --bind_ip_all

# one-time initiation of the single-member replica set
docker exec mongo-shop mongosh --quiet --eval 'rs.initiate({ _id: "rs0", members: [{ _id: 0, host: "localhost:27017" }] }).ok'
# 1

docker exec mongo-shop mongosh --quiet --eval 'db.version()'
# 8.3.13   (the exact patch release depends on the image tag you pull)

# clean up when you are done
docker rm -f mongo-shop
----

Save the following script as `seed.js`. It drops and recreates the `shop` database with four customers, five
products and eight orders; every worked example on the following pages starts from this state.

Run it non-interactively by copying it into the container and passing it to `mongosh --file`:

[source,bash]
----
docker cp seed.js mongo-shop:/tmp/seed.js
docker exec mongo-shop mongosh --quiet --file /tmp/seed.js
docker exec -it mongo-shop mongosh shop      # interactive session on the shop database
----

=== A first session

With the data loaded, the document model and the shell's JavaScript nature are easiest to see by asking a few
questions. The output below is what `mongosh` printed against a freshly seeded container:

[source,javascript]
----
shop> db.getCollectionNames()
[ 'orders', 'customers', 'products' ]

shop> db.customers.findOne({ email: "ada@example.com" })
{
  _id: 'c-1',
  name: 'Ada Lovelace',
  email: 'ada@example.com',
  city: 'London',
  tier: 'pro',
  createdAt: ISODate('2025-01-10T09:00:00.000Z')
}

shop> db.orders.countDocuments({ status: "shipped" })
4

shop> db.orders.find({ customerId: "c-1" }, { status: 1, orderDate: 1 }).sort({ orderDate: -1 })
[
  { _id: 1007, status: 'shipped', orderDate: ISODate('2026-03-18T08:30:00.000Z') },
  { _id: 1002, status: 'open',    orderDate: ISODate('2026-02-11T15:20:00.000Z') },
  { _id: 1001, status: 'shipped', orderDate: ISODate('2026-01-05T10:00:00.000Z') }
]
----

Notice what is *not* needed: no `CREATE TABLE`, no join to fetch an order together with its line items (they
live inside the order document), and no schema declaration before the first insert. What the model costs in
exchange is covered on xref:database/mongodb/data-modeling.adoc[Schema Design for the Document Model].

Because `mongosh` is a JavaScript REPL, the same session can compute with the results. This one totals one
order's value on the client, which the aggregation pipeline (see
xref:database/mongodb/aggregation-pipeline.adoc[The Aggregation Framework]) can also do on the server:

[source,javascript]
----
shop> const o = db.orders.findOne({ _id: 1004 })
shop> o.items.reduce((sum, i) => sum + i.qty * i.price, 0)
1456
----

== What MongoDB is not

* *Not a cache.* It persists to disk with journaling and configurable
  xref:database/mongodb/crud-insert-and-write-concern.adoc[write concern]; it is a system of record, not a
  volatile key/value layer in front of one.
* *Not "schemaless" in the sense of having no rules.* Every document must be valid BSON under the 16 MB size
  limit, `_id` is always unique within its collection, index key constraints still apply, and a collection
  can enforce a https://www.mongodb.com/docs/manual/core/schema-validation/[schema validator]. What is
  flexible is that the schema is not declared centrally, not that anything goes.
* *Not a drop-in SQL replacement.* There is no `JOIN` as the default access path, no cross-document foreign
  keys, and multi-document transactions -- while supported, see
  xref:database/mongodb/transactions.adoc[Transactions] -- are a deliberate choice rather than the norm.
  Porting a normalized relational schema unchanged usually works against the model.

For the relational baseline these points contrast with, see xref:database/sql/index.adoc[SQL Reference].
Continue with xref:database/mongodb/documents-and-bson.adoc[Documents, BSON & data types].
