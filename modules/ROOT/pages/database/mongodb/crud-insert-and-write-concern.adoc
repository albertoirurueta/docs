= Inserting data, bulk writes & write concern
:description: How to insert single and multiple documents, run mixed bulk writes, choose ordered vs. unordered execution, read the write-result shape, and control durability with write concern and retryable writes.
:keywords: mongodb, insertOne, insertMany, bulkWrite, ordered, unordered, write result, ObjectId, write concern, w majority, journal, wtimeout, retryable writes, idempotent

include::partial$ai-disclaimer.adoc[]

This page covers getting documents *into* a collection: the `insertOne` / `insertMany` / `bulkWrite`
methods, the result objects they return, and the write concern that decides how many nodes must acknowledge a
write before the driver considers it done. For updating and removing documents see
xref:database/mongodb/crud-update-and-delete.adoc[Updating & deleting]; for reads see
xref:database/mongodb/crud-query.adoc[Querying].

== insertOne and insertMany

`insertOne` writes a single document; `insertMany` writes an array of documents in one round trip. If a
document has no `_id` field, the driver adds one -- an `ObjectId` by default -- before sending it.

[source,javascript]
----
// https://www.mongodb.com/docs/manual/tutorial/insert-documents/
db.products.insertOne({ name: "Widget", price: 9.99 })

db.products.insertMany([
  { name: "Cog",    price: 2.50 },
  { name: "Sprong", price: 4.00 }
])
----

The result reports whether the write was acknowledged and the `_id` values that were stored (generated ones
included). As printed by `mongosh`:

[source,javascript]
----
shop> db.p2.insertOne({ name: "gen" })
{ acknowledged: true, insertedId: ObjectId('6af31e629a75683a312054ae') }

shop> db.p2.insertMany([ { name: "Cog" }, { name: "Sprong" } ])
{
  acknowledged: true,
  insertedIds: {
    '0': ObjectId('6af31e629a75683a312054af'),
    '1': ObjectId('6af31e629a75683a312054b0')
  }
}
----

The driver, not the server, generated those `ObjectId` values before sending the documents, which is why the
client knows the `_id` of a document it inserted without a second query. The practical consequence is that a
retry of an `insertOne` after a network error re-sends the *same* `_id`, so a duplicate-key error on retry
means the first attempt succeeded.

`insertMany` batches documents transparently: a driver splits a very large array into several wire-protocol
messages (each bounded by the server's maximum message size, 48 MB, and a maximum batch count) so a list of a
million documents is not a single giant request. Prefer a few thousand documents per call as a practical batch
size; it keeps memory bounded and gives a natural checkpoint when a load fails half way.
=== Ordered vs. unordered

By default `insertMany` is *ordered*: the server inserts documents in array order and stops at the first
error, leaving the remaining documents un-inserted. Passing `{ ordered: false }` makes it *unordered*: the
server attempts every document, skipping only the ones that fail, and reports all errors together.

[source,javascript]
----
// second document duplicates an existing _id
db.products.insertMany(
  [ { _id: 10, name: "A" }, { _id: 10, name: "B" }, { _id: 11, name: "C" } ],
  { ordered: false }
)
// ordered:false -> _id 10 (first) and 11 inserted, the duplicate is reported in writeErrors
// ordered:true  -> only _id 10 (first) inserted, then execution halts
----

[mermaid]
....
flowchart LR
  subgraph O ["ordered: true, the default"]
    direction LR
    O1[insert _id 10] -->|ok| O2[insert _id 10 again]
    O2 -->|duplicate key| OX[stop: _id 11 never attempted]
  end
  subgraph U ["ordered: false"]
    direction LR
    U1[insert _id 10] -->|ok| U2[insert _id 10 again]
    U2 -->|duplicate key, recorded| U3[insert _id 11]
    U3 -->|ok| UE[report all errors together]
  end
....

Run for real on an empty `products` collection, both modes raise the same duplicate-key error, but the collection
ends up different:

[source,javascript]
----
shop> db.p2.insertMany([ { _id: 10, name: "A" }, { _id: 10, name: "B" }, { _id: 11, name: "C" } ])
MongoBulkWriteError: E11000 duplicate key error collection: shop.p2 index: _id_ dup key: { _id: 10 }
shop> db.p2.find()          // error.result.insertedCount was 1
[ { _id: 10, name: 'A' } ]

shop> db.p2.drop()
shop> db.p2.insertMany([ { _id: 10, name: "A" }, { _id: 10, name: "B" }, { _id: 11, name: "C" } ], { ordered: false })
MongoBulkWriteError: E11000 duplicate key error collection: shop.p2 index: _id_ dup key: { _id: 10 }
shop> db.p2.find()          // error.result.insertedCount was 2
[ { _id: 10, name: 'A' }, { _id: 11, name: 'C' } ]
----

Inspect the `MongoBulkWriteError` rather than treating it as all-or-nothing: `error.result.insertedCount` says how
many documents were stored and `error.writeErrors` lists each failure with the `index` of the offending operation
in the array you sent. Unordered execution is also the faster mode, because the server may reorder and run
operations in parallel, so use it whenever the documents are independent of one another (bulk loads, idempotent
imports) and ordered execution only when a later operation depends on an earlier one.

== bulkWrite

`bulkWrite` sends a mixed batch of `insertOne`, `updateOne`, `updateMany`, `deleteOne`, `deleteMany` and
`replaceOne` operations in one call. It also honours `ordered` (default `true`) vs. `{ ordered: false }`,
with the same stop-on-first-error vs. attempt-all semantics as `insertMany`.

[source,javascript]
----
// https://www.mongodb.com/docs/manual/core/bulk-write-operations/
db.inventory.bulkWrite([
  { insertOne:  { document: { _id: "sku-1", qty: 100 } } },
  { updateOne:  { filter: { _id: "sku-2" }, update: { $inc: { qty: -3 } } } },
  { replaceOne: { filter: { _id: "sku-3" }, replacement: { _id: "sku-3", qty: 0 } } },
  { deleteOne:  { filter: { _id: "sku-4" } } }
], { ordered: false })
----

The result tallies each operation kind and lists any generated ids. Seeded with `sku-2` (10), `sku-3` (5) and
`sku-4` (1), the batch above printed:

[source,javascript]
----
{
  acknowledged: true,
  insertedCount: 1,
  insertedIds: { '0': 'sku-1' },
  matchedCount: 2,
  modifiedCount: 2,
  deletedCount: 1,
  upsertedCount: 0,
  upsertedIds: {}
}
shop> db.inventory.find().sort({ _id: 1 })
[ { _id: 'sku-1', qty: 100 }, { _id: 'sku-2', qty: 7 }, { _id: 'sku-3', qty: 0 } ]
----

`bulkWrite` is scoped to *one collection*. Operations that touch several collections -- placing an order that
inserts into `orders` and decrements `products.stock`, say -- are not a bulk write; they need two calls, kept
consistent by a transaction (see xref:database/mongodb/transactions.adoc[Transactions]) or by careful ordering.

A realistic single-collection use is restocking the shop catalogue in one round trip: add stock to one product,
correct a price, upsert a brand-new product, and sweep out low-stock furniture. Run unordered, with one
deliberately failing insert (`C-3` already exists) placed before a good one:

[source,javascript]
----
shop> db.products.bulkWrite([
...   { updateOne: { filter: { _id: "A-1" }, update: { $inc: { stock: 20 } } } },
...   { updateOne: { filter: { _id: "B-7" }, update: { $set: { price: 24.99 } } } },
...   { updateOne: { filter: { _id: "D-5" }, update: { $set: { name: "Webcam", category: "electronics", price: 59, stock: 40, tags: ["usb"] } }, upsert: true } },
...   { deleteMany: { filter: { stock: { $lt: 20 }, category: "furniture" } } },
...   { insertOne: { document: { _id: "C-3", name: "dup" } } },
...   { insertOne: { document: { _id: "E-1", name: "after the error" } } }
... ], { ordered: false })
MongoBulkWriteError: E11000 duplicate key error collection: shop.products index: _id_ dup key: { _id: "C-3" }
// error.result:
BulkWriteResult {
  insertedCount: 1,         // only E-1; the C-3 insert failed
  matchedCount: 2,          // A-1 and B-7
  modifiedCount: 1,         // A-1 changed; B-7 already had that price, so it matched without modifying
  deletedCount: 0,
  upsertedCount: 1,         // D-5
  upsertedIds: { '2': 'D-5' },
  insertedIds: { '0': 'C-3', '1': 'E-1' }   // lists the ids the batch tried to insert, failed one included
}
// error.writeErrors[0].err.index === 4  -- the position of the failing operation in the array
----

Two details to notice. `insertedIds` lists every id the batch *attempted* to insert, so trust `insertedCount` and
`writeErrors` for what happened; and `matchedCount` minus `modifiedCount` is the number of no-op updates.

The update, replace and delete operations above are described in
xref:database/mongodb/crud-update-and-delete.adoc[Updating & deleting].

== Write concern

Write concern is the level of acknowledgement requested from the deployment. It is expressed as a document
`{ w, j, wtimeout }`:

* `w` -- how many members must acknowledge. `w: 1` means the primary alone; `w: "majority"` means a majority
  of voting members, so the write survives a failover. A number greater than 1 names an explicit count.
* `j` -- if `true`, each acknowledging member must have written the operation to its on-disk journal, not
  merely to memory.
* `wtimeout` -- a millisecond cap on how long to wait for the `w` acknowledgements; on expiry the client
  gets a timeout error, though the write may still have been applied.

The server default write concern is `{ w: "majority" }` for most deployments; it can be inspected and changed
with `getDefaultRWConcern` / `setDefaultRWConcern` (replica sets and sharded clusters only -- a standalone
`mongod` rejects the command). On the single-member replica set from
xref:database/mongodb/getting-started.adoc[Getting Started] it reports:

[source,javascript]
----
shop> db.adminCommand({ getDefaultRWConcern: 1 }).defaultWriteConcern
{ w: 'majority', wtimeout: 0 }
----

The default is applied when the client names no write concern of its own, so a plain `insertOne` already waits for
majority acknowledgement on a replica set. Write concern can be set per operation, or per connection
via the connection string (`?w=majority&journal=true`).

[source,javascript]
----
// https://www.mongodb.com/docs/manual/reference/write-concern/
db.orders.insertOne(
  { _id: 7, total: 42 },
  { writeConcern: { w: "majority", j: true, wtimeout: 5000 } }
)

// per-connection default in the URI:
// mongodb://host1,host2,host3/shop?replicaSet=rs0&w=majority&journal=true
----

A write concern that cannot be satisfied is reported as an *error but not a rollback*. On the one-member replica
set above, asking for two acknowledgements fails immediately -- yet the document is already stored, because
write concern only governs what the client waits for, never whether the write is applied:

[source,javascript]
----
shop> db.orders.insertOne({ _id: 3001 }, { writeConcern: { w: 2, wtimeout: 300 } })
MongoServerError: Not enough data-bearing nodes        // code 100, UnsatisfiableWriteConcern
shop> db.orders.find({ _id: 3001 })
[ { _id: 3001 } ]
shop> db.orders.insertOne({ _id: 3002 }, { writeConcern: { w: "majority", j: true, wtimeout: 5000 } })
{ acknowledged: true, insertedId: 3002 }
----

The same rule explains `wtimeout`: when the timeout fires on a real multi-member set, the error means "not enough
members acknowledged in time", not "the write did not happen". A client that must know the outcome retries the
operation idempotently or reads the document back, rather than assuming failure. `w: 0` (unacknowledged) is
fire-and-forget and is almost never what an application wants; `j: true` adds a journal flush at the cost of
latency, and with `w: "majority"` the majority members already journal, so `j` mostly matters for standalones and
for `w: 1`.

A `"majority"` acknowledgement is tied to the replica set's oplog and majority-commit point; see
xref:database/mongodb/replication.adoc[Replication] for how the oplog and majority reads and writes fit
together.

== Retryable writes

With retryable writes enabled (the driver default; `retryWrites=true` in the connection string), the driver
automatically retries a write *once* if it fails due to a transient network error or a primary election. The
server deduplicates the retry using the operation's statement id and the session's transaction number, so a
single-document `insertOne`, `updateOne`, `deleteOne`, `findAndModify` or `replaceOne` is applied at most
once even though it was sent twice.

[source,javascript]
----
// https://www.mongodb.com/docs/manual/core/retryable-writes/
// mongodb://host1,host2,host3/shop?replicaSet=rs0&retryWrites=true
db.accounts.updateOne({ _id: "a-1" }, { $inc: { balance: -100 } })
// if the primary steps down mid-write, the driver retries once against the new primary;
// the $inc is not applied twice
----

The retry is safe because of how it is deduplicated:

[mermaid]
....
sequenceDiagram
    participant C as Driver
    participant P1 as Old primary
    participant P2 as New primary
    C->>P1: updateOne(lsid, txnNumber 7, stmtId 0)
    P1-->>P1: apply, record in oplog and in the session table
    P1--xC: network error, ack lost
    Note over C: retryWrites=true, so retry once after server selection
    C->>P2: updateOne(lsid, txnNumber 7, stmtId 0)
    P2-->>P2: statement already applied, do not execute again
    P2-->>C: original result returned
....

The `lsid` (logical session id) and `txnNumber` identify the operation; the second primary recognises a statement
it has already replicated and replies with the recorded outcome instead of applying it again. Retryable writes
therefore require a replica set or sharded cluster (a standalone `mongod` has no oplog to carry the record) and a
driver that supports sessions.

Multi-document operations that are not inherently idempotent (`updateMany`, `deleteMany`) are not retried.
Wrapping several writes in a transaction (see
xref:database/mongodb/transactions.adoc[Transactions]) gives all-or-nothing semantics across documents.
