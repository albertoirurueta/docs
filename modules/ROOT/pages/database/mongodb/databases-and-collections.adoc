= Databases, collections & schema control
:description: How MongoDB creates databases and collections on first write, the naming rules that constrain them, and the schema-control tools: $jsonSchema validation, capped, TTL, clustered and time series collections, plus views and materialized views.
:keywords: mongodb, database, collection, db.createCollection, db.stats, schema validation, $jsonSchema, validationLevel, validationAction, capped collection, tailable cursor, ttl index, clustered collection, view, materialized view, $merge, time series

include::partial$ai-disclaimer.adoc[]

A MongoDB deployment holds one or more *databases*; each database holds *collections*; each collection holds
BSON *documents* (see xref:database/mongodb/documents-and-bson.adoc[Documents & BSON]). Neither a database nor
an ordinary collection has to be declared before use, but several specialised collection types must be created
explicitly to opt into fixed size, automatic expiry, a different physical layout, or a query-time pipeline.

== Implicit creation on first write

Referencing a database with `use` does not create it, and referencing a collection does not create it either.
The database and the collection first appear on disk when the first document is written to them.

[source,javascript]
----
// https://www.mongodb.com/docs/manual/core/databases-and-collections/
use shop                          // no-op until something is written
db.products.insertOne({ _id: 1, name: "Widget", price: 9.99 })
// -> database "shop" and collection "products" now exist

db.getMongo().getDBNames()       // "shop" is listed only after the insert
show collections
----

Checking this against a fresh server, the database name is absent before the first write and present afterwards,
with the collection created by the same operation:

[source,javascript]
----
shop> const d = db.getSiblingDB("lazy")
shop> db.getMongo().getDBNames().includes("lazy")        // before any write
false
shop> d.products.insertOne({ _id: 1, name: "Widget", price: 9.99 })
shop> db.getMongo().getDBNames().includes("lazy")        // the insert created both
true
shop> d.getCollectionNames()
[ 'products' ]
----

An index build (`createIndex`) on a missing collection also creates it -- `d.idx.createIndex({ a: 1 })` on a
database with no `idx` collection leaves `[ 'idx' ]` behind. The corollary of implicit creation is that a typo in
a collection name silently creates a second, empty collection instead of failing; applications that care create
their collections explicitly at deployment time, with validators and indexes, rather than at first write. The
naming rules are enforced: `+d.getCollection("system.x").insertOne(...)+` fails with `Invalid system namespace`,
and a name containing `$` is rejected by the shell before it reaches the server. To create a collection with no
documents and no options, call `createCollection` with just a name.

=== Naming rules and restrictions

Database names are case-sensitive, limited to 63 bytes, and cannot contain `/\. "$*<>:|?` or the null
character; `admin`, `local` and `config` are reserved for the system. Collection names cannot start with
`system.`, cannot contain `$` or the null character, cannot be empty, and the fully-qualified
`<db>.<collection>` namespace has a length limit. See
https://www.mongodb.com/docs/manual/reference/limits/#naming-restrictions for the exact list.

[source,javascript]
----
db.createCollection("audit_log")                       // explicit, empty, default options
db.createCollection("orders", { collation: { locale: "en", strength: 2 } })

// inspect sizes and counts
db.stats()                                             // storage totals for the whole database
db.orders.stats()                                      // per-collection storage, index sizes, counts
// https://www.mongodb.com/docs/manual/reference/method/db.stats/
----

== Flexible schema is not "no schema"

MongoDB does not require a collection-wide schema declaration: two documents in one collection may carry
different fields and different BSON types for the same field name. That flexibility is a migration and
modelling convenience, not an absence of structure -- application code, indexes and queries all still assume a
shape. A field's meaning, type and presence are part of the design; they are simply enforced by the
application, by optional validation rules, or both, rather than by a mandatory DDL step. See
https://www.mongodb.com/docs/manual/core/data-modeling-introduction/ and
xref:database/mongodb/data-modeling.adoc[Data modeling].

[source,json]
----
// both documents are valid in the same collection, but the second is probably a bug
{ "_id": 1, "sku": "A-1", "price": 9.99, "tags": ["new"] }
{ "_id": 2, "sku": 42,    "price": "cheap" }
----

== Schema validation with $jsonSchema

`db.createCollection` (or `collMod` for an existing collection) accepts a `validator`. The `$jsonSchema`
operator is the recommended form: it constrains required fields, BSON types, value ranges and enumerations.
`validationLevel` selects which documents are checked and `validationAction` selects what happens on failure.

* `validationLevel`: `strict` (default -- check every insert and every update) or `moderate` (check inserts,
  and updates only to documents that already satisfy the schema, leaving existing invalid documents alone).
* `validationAction`: `error` (default -- reject the write) or `warn` (allow the write, record a warning in
  the log).

[source,javascript]
----
// https://www.mongodb.com/docs/manual/core/schema-validation/
db.createCollection("customers", {
  validator: {
    $jsonSchema: {
      bsonType: "object",
      required: ["email", "createdAt"],
      properties: {
        email:     { bsonType: "string", pattern: "^.+@.+$" },
        createdAt: { bsonType: "date" },
        tier:      { enum: ["free", "pro", "enterprise"] }
      }
    }
  },
  validationLevel: "moderate",
  validationAction: "warn"
})

// tighten the rules later without recreating the collection
db.runCommand({
  collMod: "customers",
  validator: { $jsonSchema: { bsonType: "object", required: ["email", "createdAt", "tier"] } },
  validationLevel: "strict",
  validationAction: "error"
})
----

A write that violates a `strict` / `error` validator fails with error code 121 (`DocumentValidationFailure`).
Since MongoDB 5.0 the error also carries `errInfo`, a structured explanation of which rule failed for which
value, so the failure is diagnosable without guessing. Creating the `customers_v` collection of the example
above as `strict` / `error` and inserting a customer with a malformed e-mail address printed:

[source,javascript]
----
shop> db.customers_v.insertOne({ email: "nope", createdAt: new Date() })
MongoServerError: Document failed validation
Additional information: {
  failingDocumentId: ObjectId('6af31e3bfb42787dce379694'),
  details: {
    operatorName: '$jsonSchema',
    schemaRulesNotSatisfied: [
      {
        operatorName: 'properties',
        propertiesNotSatisfied: [
          {
            propertyName: 'email',
            details: [
              {
                operatorName: 'pattern',
                specifiedAs: { pattern: '^.+@.+$' },
                reason: 'regular expression did not match',
                consideredValue: 'nope'
              }
            ]
          }
        ]
      }
    ]
  }
}
shop> db.customers_v.insertOne({ email: "ada@example.com", createdAt: new Date(), tier: "pro" }).acknowledged
true
----

The `validationLevel` distinction is easiest to see on a collection that already contains a bad document.
Starting from `{ _id: 1, email: 5 }` (an `email` that is not a string) and a schema that requires a string
`email`, a `moderate` level lets an unrelated update through because the stored document was already invalid,
while `strict` rejects the very same update:

[source,javascript]
----
shop> db.m.insertOne({ _id: 1, email: 5 })
shop> db.runCommand({ collMod: "m", validator: { $jsonSchema: { bsonType: "object",
...   properties: { email: { bsonType: "string" } } } }, validationLevel: "moderate" })
{ ok: 1 }
shop> db.m.updateOne({ _id: 1 }, { $set: { x: 1 } })       // allowed: the document was already invalid
shop> db.runCommand({ collMod: "m", validationLevel: "strict" })
shop> db.m.updateOne({ _id: 1 }, { $set: { x: 2 } })       // rejected with code 121
----

`moderate` is therefore the tool for tightening the rules of a collection that already holds legacy data: new
and conforming documents are held to the schema, and nothing already stored becomes un-updatable overnight.
Adding `validationAction: "warn"` first, reading the log for violations, and only then switching to `error` is a
safe rollout path. A validator never inspects documents already on disk until they are written again.

== Capped collections

A capped collection is created with a fixed maximum size in bytes (and optionally a maximum document count).
It preserves insertion order and, once full, overwrites its oldest documents to make room for new ones.
Capped collections support *tailable cursors*, which stay open after reaching the end and
return new documents as they are inserted -- useful for feed-style consumers.

[source,javascript]
----
// https://www.mongodb.com/docs/manual/core/capped-collections/
db.createCollection("recent_events", { capped: true, size: 1048576, max: 5000 })

db.recent_events.insertOne({ at: new Date(), kind: "login", user: "ada" })
----

Because eviction is automatic and FIFO, the collection behaves like a ring buffer. A capped collection created
with `max: 3` and fed five documents keeps only the newest three, still in insertion order:

[source,javascript]
----
shop> db.createCollection("cap", { capped: true, size: 4096, max: 3 })
shop> for (let i = 1; i <= 5; i++) db.cap.insertOne({ _id: i })
shop> db.cap.find()
[ { _id: 3 }, { _id: 4 }, { _id: 5 } ]
shop> db.cap.isCapped()
true
----

Older versions of the manual state that documents cannot be deleted from a capped collection and that an update
may not grow a document. On the 8.x server used to verify this page both operations succeeded -- `deleteOne({ _id: 4 })`
returned `deletedCount: 1` and a growing `$set` was accepted -- so do not rely on those restrictions either way:
the guarantees that remain are the size and count cap, insertion-order reads, and tailable cursors. Plan a capped
collection around "oldest data falls off", not around immutability.

`mongosh` has no tailable-cursor helper; the drivers do. With the Node.js driver you pass the cursor options
and keep iterating -- when the cursor reaches the end it blocks (up to `maxAwaitTimeMS`) instead of closing:

[source,javascript]
----
// Node.js driver: keep reading recent_events as new documents arrive
const cursor = db.collection("recent_events")
  .find({}, { tailable: true, awaitData: true, maxAwaitTimeMS: 1000 });

for await (const event of cursor) {
  handle(event);
}
----

For most "keep only recent data" needs a TTL collection (below) is a better fit, because it allows normal
deletes and updates.

== TTL collections

A TTL ("time to live") collection is an ordinary collection with a single-field TTL index on a `Date` field.
A background thread deletes documents once the indexed date is older than `expireAfterSeconds`. Set
`expireAfterSeconds: 0` to expire exactly at the stored date.

[source,javascript]
----
// https://www.mongodb.com/docs/manual/core/index-ttl/
db.sessions.createIndex({ lastActive: 1 }, { expireAfterSeconds: 3600 })
db.sessions.insertOne({ _id: "sess-1", lastActive: new Date() })
// removed by the TTL monitor roughly one hour after lastActive
----

A background task, the *TTL monitor*, wakes roughly once a minute, so an expired document can outlive its
deadline by up to about a minute plus the time to delete a large batch; a TTL index is a retention policy, not a
precise timer. To watch it work, create the index with a short expiry and insert a document whose date is already
in the past -- it vanishes at the next sweep:

[source,javascript]
----
shop> db.sess.createIndex({ lastActive: 1 }, { expireAfterSeconds: 5 })
lastActive_1
shop> db.sess.insertOne({ _id: "s1", lastActive: new Date(Date.now() - 3600 * 1000) })
shop> db.sess.countDocuments()      // immediately afterwards
1
shop> db.sess.countDocuments()      // after the next TTL pass, under a minute later
0
----

Only documents whose indexed field holds a BSON date (or an array containing one) expire; a missing field or a
string never does. On a replica set the TTL monitor runs on the primary and the deletes replicate like any other
delete. To change `expireAfterSeconds` on an existing TTL index use `collMod` instead of rebuilding the index.
See xref:database/mongodb/indexes.adoc[Indexes] for TTL index constraints (single field, not on `_id`, not
compound).

== Clustered collections

A clustered collection stores its documents *in `_id` index order* -- the collection and its primary index
are the same B-tree, so there is no separate `_id` index and `_id`-based lookups and range scans avoid a
second seek. It is created with `clusteredIndex` and the key must be `{ _id: 1 }`.

[source,javascript]
----
// https://www.mongodb.com/docs/manual/core/clustered-collections/
db.createCollection("readings", {
  clusteredIndex: { key: { _id: 1 }, unique: true, name: "readings_id_clustered" }
})
----

The `_id` order is visible in the plan: a range query on `_id` is answered by a `CLUSTERED_IXSCAN` that reads
the collection itself between two record bounds, with no separate index structure and no fetch step, and the
only index reported by `getIndexes()` is the clustered one.

[source,javascript]
----
shop> db.cl.getIndexes()
[ { v: 2, key: { _id: 1 }, name: 'cl_id', unique: true, clustered: true } ]
shop> db.cl.insertMany([ { _id: 2 }, { _id: 1 }, { _id: 3 } ])
shop> db.cl.find()                     // stored and returned in _id order, not insertion order
[ { _id: 1 }, { _id: 2 }, { _id: 3 } ]
shop> db.cl.find({ _id: { $gt: 1 } }).explain().queryPlanner.winningPlan
{ stage: 'CLUSTERED_IXSCAN', direction: 'forward', minRecord: 1, maxRecord: Infinity, ... }
----

Best suited to collections queried mostly by `_id` or by `_id` ranges, or that would otherwise carry a large
`_id` index.

== Views

A view is a read-only, non-materialised query object defined by a name, a source collection, and an
aggregation pipeline. Reading the view runs the pipeline against the source each time; the view stores no
data of its own and cannot be written to.

[source,javascript]
----
// https://www.mongodb.com/docs/manual/core/views/
db.createView(
  "active_customers",              // view name
  "customers",                     // source collection
  [
    { $match: { tier: { $ne: "free" } } },
    { $project: { email: 1, tier: 1, _id: 0 } }
  ]
)

db.active_customers.find({ tier: "pro" })   // pipeline runs now, against customers
----

Against the shop's four customers the view returns the two paying tiers and hides everything not projected, and any
attempt to write to it is refused:

[source,javascript]
----
shop> db.active_customers.find()
[ { email: 'ada@example.com', tier: 'pro' }, { email: 'grace@example.com', tier: 'enterprise' } ]
shop> db.active_customers.insertOne({ a: 1 })
MongoServerError: Namespace shop.active_customers is a view, not a collection
----

Views are a convenient access-control and simplification device -- grant a role read access to the view but not to
`customers` and the hidden fields stay hidden -- but a view cannot have its own indexes. Queries on a view use the
indexes of the source collection, applied to the pipeline's leading `$match`.

== On-demand materialized views

When the pipeline is expensive and staleness is acceptable, write its result to a real collection with a
`$merge` (or `$out`) stage and re-run it on a schedule. The target collection can be indexed and queried like
any other; `$merge` updates it in place rather than replacing it wholesale.

[source,javascript]
----
// https://www.mongodb.com/docs/manual/core/materialized-views/
db.orders.aggregate([
  { $match: { status: { $ne: "cancelled" } } },
  { $set: { total: { $sum: { $map: { input: "$items", as: "i", in: { $multiply: ["$$i.qty", "$$i.price"] } } } } } },
  { $group: { _id: "$customerId", spend: { $sum: "$total" }, orders: { $sum: 1 } } },
  { $set: { spend: { $round: ["$spend", 2] } } },
  { $merge: { into: "customer_spend", whenMatched: "replace", whenNotMatched: "insert" } }
])
----

Running it against the shop leaves one row per customer, and re-running it after more orders arrive updates those
rows in place:

[source,javascript]
----
shop> db.customer_spend.find().sort({ _id: 1 })
[
  { _id: 'c-1', spend: 867.48, orders: 3 },
  { _id: 'c-2', spend: 241.95, orders: 2 },
  { _id: 'c-3', spend: 1456, orders: 1 },
  { _id: 'c-4', spend: 63.99, orders: 1 }
]
----

The `$round` stage matters: summing binary doubles produced `63.989999999999995` for customer `c-4` before it was
added. After a further shipped order for that customer (a Monitor 27in at 279) and a second run of the same
pipeline, `$merge` replaced that single row and left the other three untouched: `c-4` became
`+{ spend: 342.99, orders: 2 }+`.

See xref:database/mongodb/aggregation-pipeline.adoc[Aggregation pipeline] for the full `$merge` stage
options.

== Time series collections

For a stream of timestamped measurements (metrics, sensor readings, prices), a *time series collection*
stores data in a compressed, time-bucketed layout and is created with a `timeseries` option naming the time
field and an optional metadata field. It is the purpose-built alternative to hand-rolling a capped or TTL
collection for this data.

[source,javascript]
----
// overview only -- see https://www.mongodb.com/docs/manual/core/timeseries-collections/
db.createCollection("weather", {
  timeseries: { timeField: "ts", metaField: "station", granularity: "minutes" },
  expireAfterSeconds: 7776000
})
----

Behind the scenes a time series collection is a *view over an internal bucket collection*: inserting two readings
and listing the collections shows both the logical collection and the physical one that holds the buckets.

[source,javascript]
----
shop> db.weather.insertMany([ { ts: new Date(), station: "MAD", temp: 21.4 }, { ts: new Date(), station: "MAD", temp: 21.6 } ])
shop> db.getCollectionInfos({ name: "weather" })[0].type
timeseries
shop> db.getCollectionNames().filter(n => n.includes("weather"))
[ 'weather', 'system.buckets.weather' ]
----

Documents with the same `metaField` value are packed together into buckets, which is why the metadata field
should hold the *identity* of the series (a station, a device) and not a value that changes with every reading.
`granularity` tells the server how wide a bucket's time span should be; pick `seconds`, `minutes` or `hours` to
match the real arrival rate. The trade-off against ordinary collections is a narrower write model: historically
documents in a time series collection could not be updated or deleted individually, and the supported update and
delete forms have grown release by release, so check the manual page for the exact rules of the version you run.

== Choosing a collection type

Every specialised collection above solves one problem; the question to ask is what should happen to the data
over time, and how it will be read.

[mermaid]
....
flowchart TD
  S[New data to store] --> T{Timestamped measurements arriving continuously?}
  T -- yes --> TS[Time series collection]
  T -- no --> R{Old data must disappear automatically?}
  R -- "by age of a date field" --> TTL[Ordinary collection plus TTL index]
  R -- "by total size, oldest first" --> CAP[Capped collection]
  R -- no --> V{Read mostly by _id or _id ranges?}
  V -- yes --> CL[Clustered collection]
  V -- no --> Q{Is it a stored query over other collections?}
  Q -- "always fresh, read-only" --> VW[View]
  Q -- "precomputed, refreshed on a schedule" --> MV[Collection filled by merge]
  Q -- no --> ORD[Ordinary collection, with a validator if the shape matters]
....

Whatever the type, the second decision is whether to attach a `$jsonSchema` validator: it is available on
ordinary, capped and clustered collections and is the cheapest insurance against the type drift shown in the
"Flexible schema" section above.
