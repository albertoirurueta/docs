include::partial$ai-disclaimer.adoc[]

An index is an ordered, on-disk data structure (a B-tree) that lets the query planner locate documents by
value instead of scanning the whole collection. This page covers how to create and inspect indexes, the index
types and the key-order rule that makes compound indexes effective, how to read `explain()`, and the index
properties you tune per workload. For query syntax itself see xref:database/mongodb/crud-query.adoc[Querying
documents], and for text, geospatial and Atlas search indexes see
xref:database/mongodb/special-indexes-and-search.adoc[Text, wildcard, geospatial & Atlas search].

== Why indexes exist

Without a useful index, a query is a *collection scan*: the server reads every document and tests the
predicate on each one, so cost grows linearly with collection size. An index stores just the indexed field
values plus a pointer to each document, kept sorted, so the planner can seek to a value or walk a contiguous
range and touch only the matching documents. The same ordering also satisfies `sort()` without loading results
into memory first. See https://www.mongodb.com/docs/manual/indexes/[Indexes] for the overview.

[source,javascript]
----
// No index on "email": this must examine every document.
db.users.find({ email: "ada@example.com" }).explain("executionStats").executionStats.totalDocsExamined
// => 500000

db.users.createIndex({ email: 1 })

// With the index: a seek, then one document fetched.
db.users.find({ email: "ada@example.com" }).explain("executionStats").executionStats.totalDocsExamined
// => 1
----

Structurally an index is a B-tree whose keys are the indexed values in sorted order and whose entries point to the
documents. A lookup walks from the root to a leaf in a handful of page reads, and because the leaves are linked in
key order a range scan simply keeps walking right. Compound indexes sort by the first field, then the second within
equal firsts, and so on -- which is exactly why key order decides what the index can serve.

[mermaid]
....
flowchart TD
  R["root page: keys 'cancelled' | 'returned' | 'shipped'"] --> L1["leaf: open ... open (many entries)"]
  R --> L2["leaf: returned ... shipped"]
  L1 --> D1[(documents on disk)]
  L2 --> D2[(documents on disk)]
  L1 -. next leaf .-> L2
....

Indexes are not free. Every index adds storage, and every `insert`, `update` that changes an indexed field,
and `delete` must also update each affected index entry, so write throughput drops as index count grows. Index
only the fields your real queries filter, sort, or cover on.

== Creating and listing indexes

`db.collection.createIndex(keys, options)` builds an index; `keys` maps field names to a direction (`1`
ascending, `-1` descending). Creating an index that already exists (same keys and options) is a no-op. See
https://www.mongodb.com/docs/manual/reference/method/db.collection.createIndex/[`db.collection.createIndex()`].

[source,javascript]
----
db.orders.createIndex({ customerId: 1, orderDate: -1 }, { name: "customer_recent" })
----

`db.collection.getIndexes()` lists every index on the collection, including the auto-generated name and any
properties; `db.collection.dropIndex()` removes one by name or key spec. See
https://www.mongodb.com/docs/manual/reference/method/db.collection.getIndexes/[`getIndexes()`] and
https://www.mongodb.com/docs/manual/reference/method/db.collection.dropIndex/[`dropIndex()`].

[source,javascript]
----
db.orders.getIndexes()
db.orders.dropIndex("customer_recent")
db.orders.dropIndex({ customerId: 1, orderDate: -1 })   // by key spec, equivalent
----

[source,json]
----
[
  { "v": 2, "key": { "_id": 1 }, "name": "_id_" },
  { "v": 2, "key": { "customerId": 1, "orderDate": -1 }, "name": "customer_recent" }
]
----

Every collection has a unique index on `_id` that MongoDB creates automatically and that cannot be dropped; it
is what enforces primary-key uniqueness for the collection. See
https://www.mongodb.com/docs/manual/indexes/#default-_id-index[The default `_id` index].

Use `db.collection.stats()` (or `$indexStats`) to see index sizes and per-index usage counts before deciding
what to drop:

[source,javascript]
----
db.orders.stats().indexSizes                 // bytes per index
db.orders.aggregate([ { $indexStats: {} } ]) // "accesses.ops" == times the planner picked each index
----

On the 100,000-order collection with three secondary indexes, the sizes show the cost of each index in bytes, and
`$indexStats` the number of times the planner actually used it:

[source,javascript]
----
shop> db.bigorders.stats().indexSizes
{ _id_: 4096, status_date_qty: 1392640, open_cust: 266240, cust_total: 2088960 }
shop> db.bigorders.aggregate([ { $indexStats: {} }, { $project: { name: 1, "accesses.ops": 1 } } ])
[ { name: 'status_date_qty', accesses: { ops: Long('1') } },
  { name: 'cust_total',      accesses: { ops: Long('0') } },
  { name: 'open_cust',       accesses: { ops: Long('0') } },
  { name: '_id_',            accesses: { ops: Long('0') } } ]
----

`cust_total` occupies about 2 MB and shows zero accesses in that run -- the kind of finding that justifies a
`hideIndex()` trial and then a drop. Remember that `$indexStats` counters reset when the server restarts, so look
at a window long enough to include the monthly report.

== Reading explain()

`+db.collection.find(...).explain(verbosity)+` shows what the planner chose. Verbosity `"queryPlanner"` (the
default) reports the winning plan and rejected plans; `"executionStats"` also runs the query and reports
counters; `"allPlansExecution"` adds the trial results for every candidate. See
https://www.mongodb.com/docs/manual/reference/explain-results/[Explain results].

[source,javascript]
----
db.orders.find({ status: "shipped" }).sort({ orderDate: 1 }).explain("executionStats")
----

[source,json]
----
{
  "queryPlanner": {
    "winningPlan": {
      "stage": "FETCH",
      "inputStage": { "stage": "IXSCAN", "indexName": "status_1_orderDate_1", "direction": "forward" }
    },
    "rejectedPlans": []
  },
  "executionStats": {
    "nReturned": 1200,
    "totalKeysExamined": 1200,
    "totalDocsExamined": 1200,
    "executionTimeMillis": 4
  }
}
----

Read it like this:

* *`COLLSCAN`* as the leaf stage means no index was used -- the query read the whole collection. *`IXSCAN`*
  means an index drove the query; the following `FETCH` stage loads the matched documents (absent for a
  covered query).
* Compare *`totalKeysExamined`* and *`totalDocsExamined`* to *`nReturned`*. When they are close, the index is
  selective. When `totalKeysExamined` greatly exceeds `nReturned`, the index scans many non-matching entries
  (often a missing equality prefix). A `SORT` stage in the plan means the index did not supply the order and
  the server sorted in memory. A blocking sort has a 100 MB memory budget; since MongoDB 6.0 the server parameter
  `allowDiskUseByDefault` is `true`, so both `find()` and `aggregate()` spill a larger sort to temporary files
  instead of failing (see the worked example below for the error you get when the opt-in is withdrawn).

After it picks a plan for a given *query shape* (the filter/sort/projection structure, independent of the
literal values), MongoDB stores it in the *plan cache* and reuses it for later queries of that shape,
re-evaluating only if the plan starts performing badly or indexes change. Inspect or clear it with the plan
cache commands. See https://www.mongodb.com/docs/manual/core/query-plans/[Query plans].

[source,javascript]
----
db.orders.getPlanCache().list()
db.orders.getPlanCache().clear()
----

An entry appears only when the planner had more than one candidate plan to compare. With indexes
`{ status: 1, qty: 1, orderDate: 1 }` and `{ status: 1, orderDate: 1, qty: 1 }` on the 100,000 orders, running
`find({ status: "open", qty: 3 })` a few times leaves one active entry for that query shape, caching a `FETCH` <-
`IXSCAN` on `status_qty_date` -- the order with the equality field followed by the range field was cheaper for this
shape -- and `getPlanCache().list()` shows `createdFromQuery`, `isActive` and the cached plan.

[mermaid]
....
flowchart TD
  Q[Query arrives] --> P[Parse and canonicalize into a query shape]
  P --> C{Plan cache entry for this shape?}
  C -- hit --> W[Take the cached winning plan]
  C -- miss --> E[Enumerate candidate plans: one per usable index, plus COLLSCAN]
  E --> T[Trial period: race candidates over a sample of documents]
  T --> S[Score plans: fewest work units, penalise blocking SORT]
  S --> W
  W --> X[Execute winning plan stages: IXSCAN then FETCH then SORT/PROJECT]
  X --> K[Cache the winning plan for this shape]
....

== Worked example: tuning the order-history query

The numbers below come from a `bigorders` collection of 100,000 orders in the shop's `orders` shape
(`customerId`, `status` with four values, `qty` from 0 to 49, `orderDate`, `total`), measured with
`explain("executionStats")` on a MongoDB 8.x server. The question is the dashboard's: "the ten oldest shipped
orders with `qty` of at least 40". A helper that prints the stage chain and the counters keeps the comparison honest:

[source,javascript]
----
function stats(label, cursor) {
  const e = cursor.explain("executionStats"), s = e.executionStats, stages = [];
  for (let p = e.queryPlanner.winningPlan; p; p = p.inputStage) stages.push(p.stage + (p.indexName ? "(" + p.indexName + ")" : ""));
  console.log(label, "| stages:", stages.join(" <- "), "| returned", s.nReturned, "keys", s.totalKeysExamined, "docs", s.totalDocsExamined);
}
const q = () => db.bigorders.find({ status: "shipped", qty: { $gte: 40 } }).sort({ orderDate: 1 }).limit(10);
----

[mermaid]
....
flowchart LR
  A[Slow query reported] --> B[explain executionStats]
  B --> C{COLLSCAN or SORT stage?}
  C -- yes --> D[Create or reorder an index using the ESR rule]
  C -- no --> E{keys and docs examined close to nReturned?}
  D --> B
  E -- no --> D
  E -- yes --> F[Good: keep it, watch write cost]
....

Three configurations of the same query, in the order they were tried:

[cols="3,3,1,1,1",options="header"]
|===
| Index | Winning plan | `totalKeysExamined` | `totalDocsExamined` | Time

| none | `SORT` <- `COLLSCAN` | 0 | 100000 | 22 ms
| `+{ status: 1, qty: 1, orderDate: 1 }+` (Equality, Range, Sort) | `FETCH` <- `SORT` <- `IXSCAN` | 5000 | 10 | 2 ms
| `+{ status: 1, orderDate: 1, qty: 1 }+` (Equality, Sort, Range) | `LIMIT` <- `FETCH` <- `IXSCAN` | 50 | 10 | under 1 ms
|===

The first row is the baseline: every document is read and sorted. The second index fixes the scan but leaves a
`SORT` stage, because within `status: "shipped"` the keys are ordered by `qty`, not by date: all 5,000 matching
index entries are read and sorted in memory before the first ten are returned. The ESR index lists the sort field
before the range field, so the entries for `shipped` are already in `orderDate` order; the executor walks them in
order, tests `qty >= 40` against the key itself, and stops after ten hits -- 50 keys in total, because about one
order in five has `qty >= 40`. With `allPlansExecution` the planner reports the other index as a rejected plan,
and left to choose freely it picks the ESR index:

[source,javascript]
----
shop> db.bigorders.createIndex({ status: 1, orderDate: 1, qty: 1 }, { name: "status_date_qty" })
shop> q().explain("executionStats").queryPlanner.winningPlan.inputStage.inputStage.indexBounds
{ status: [ '["shipped", "shipped"]' ], orderDate: [ '[MinKey, MaxKey]' ], qty: [ '[40, inf]' ] }
----

Read the bounds as the contract: an equality becomes a single point, the sort field is scanned across its whole
range because the query does not restrict it, and the trailing range field filters inside the index. *Without*
the `limit`, the same ESR index examines 25,000 keys (every `shipped` entry) against 5,000 returned, whereas the
Equality-Range-Sort index examines only the 5,000 that match and then sorts them; ESR is the right default because
it avoids the blocking sort and short-circuits with `limit`, but it is a rule of thumb, not a theorem -- measure
with `explain` for the real query mix.

The same helper shows the other index facts of this page:

[cols="3,3,1,1,1",options="header"]
|===
| Query | Plan | Keys | Docs | Returned

| `find({ customerId: "c-7" }, { _id: 0, total: 1 })` with index `{ customerId: 1, total: 1 }` | `PROJECTION_COVERED` <- `IXSCAN` | 50 | 0 | 50
| the same query, projection left at the default (`_id` included) | `PROJECTION_SIMPLE` <- `FETCH` <- `IXSCAN` | 50 | 50 | 50
| `find({ total: 5 })`, using only the second field of that index | `COLLSCAN` | 0 | 100000 | 101
| `find({ customerId: "c-7" }).sort({ qty: 1 })` | `SORT` <- `FETCH` <- `IXSCAN` | 50 | 50 | 50
|===

The covered query is the only row that reads zero documents; adding `_id` to the projection forces a fetch because
`_id` is not in the index. The non-prefix query shows the prefix rule: the index leads with `customerId`, so a
filter on `total` alone cannot use it.

A blocking sort needs memory. With the memory budget lowered to 1 MB
(`setParameter: internalQueryMaxBlockingSortMemoryUsageBytes`) and no index on `total`, sorting all 100,000
documents by `total` still succeeded under the default `allowDiskUseByDefault: true` -- the server wrote spill
files -- but the same query with `.allowDiskUse(false)` failed with
`QueryExceededMemoryLimitNoDiskUseAllowed: Sort exceeded memory limit of 1000000 bytes, but did not opt in to
external sorting`. The durable fix is an index that supplies the order, not a larger budget.

== Index properties

Each option below is passed in the `createIndex` options document.

*Unique* -- rejects a second document with a duplicate value for the indexed key.
https://www.mongodb.com/docs/manual/core/index-unique/[Unique indexes].

[source,javascript]
----
db.users.createIndex({ email: 1 }, { unique: true })
----

Building a unique index over data that already contains duplicates fails and leaves the collection unchanged: on the
100,000 orders, `createIndex({ qty: 1 }, { unique: true })` is rejected with `DuplicateKey`. Find the offenders with a
`$group` and `$match: { n: { $gt: 1 } }` first, resolve them, then build the index.

*Partial* -- indexes only the documents matching `partialFilterExpression`, keeping the index small and its
writes cheap. The planner uses it only when the query implies the same filter.
https://www.mongodb.com/docs/manual/core/index-partial/[Partial indexes].

[source,javascript]
----
db.orders.createIndex(
  { customerId: 1 },
  { partialFilterExpression: { status: { $eq: "open" } } }
)
----

The planner may use a partial index only when the query *implies* the filter. On the 100,000 orders, a partial index
on `{ customerId: 1 }` restricted to `status: "open"` is used by `find({ customerId: "c-4", status: "open" })`
(`FETCH` <- `IXSCAN`, 50 keys, 50 documents) and ignored by `find({ customerId: "c-4" })`, which falls back to a
`COLLSCAN` over all 100,000 documents because the index cannot answer for the other statuses. The payoff is size and
write cost: only a quarter of the orders are indexed.

*Sparse* -- indexes only documents in which the field is present. Superseded in most cases by a partial index
with an `$exists` filter, but still useful with `unique` to allow many documents that omit the field.
https://www.mongodb.com/docs/manual/core/index-sparse/[Sparse indexes].

[source,javascript]
----
db.members.createIndex({ badgeNumber: 1 }, { unique: true, sparse: true })
----

*TTL* -- a single-field index on a date whose `expireAfterSeconds` tells a background task to delete documents
once the date is that many seconds in the past. Used for sessions, logs, and caches.
https://www.mongodb.com/docs/manual/core/index-ttl/[TTL indexes].

[source,javascript]
----
db.sessions.createIndex({ lastSeen: 1 }, { expireAfterSeconds: 3600 })
----

*Hidden* -- kept up to date on writes but ignored by the planner, so you can measure the effect of dropping an
index before actually dropping it. https://www.mongodb.com/docs/manual/core/index-hidden/[Hidden indexes].

[source,javascript]
----
db.orders.hideIndex("customer_recent")   // then watch query performance
db.orders.unhideIndex("customer_recent") // instant rollback if it mattered
----

Hiding the covering index from the tuning example above turns the covered query into
`PROJECTION_SIMPLE` <- `COLLSCAN` with 100,000 documents examined -- precisely the regression you want to discover
while the index can still be restored instantly, rather than after a drop and a slow rebuild. `getIndexes()` lists
the hidden index with `hidden: true`.

*Collation* -- binds language/locale comparison rules to the index. A `strength: 2` collation gives a
case-insensitive index that a query with the matching collation can use.
https://www.mongodb.com/docs/manual/core/index-case-insensitive/[Case-insensitive indexes].

[source,javascript]
----
db.users.createIndex({ name: 1 }, { collation: { locale: "en", strength: 2 } })
db.users.find({ name: "ADA" }).collation({ locale: "en", strength: 2 })  // matches "Ada", "ada"
----

With the three documents `Ada`, `ada` and `ADA`, the collation query returns all three through an `IXSCAN`, while
the same filter without the collation returns none and uses a `COLLSCAN`: the index is only eligible when the
query's collation matches the index's.

== Index builds, hint, and when not to index

On a replica set, building an index on a large existing collection is best done as a *rolling build* -- build
on each secondary in turn with the member stepped out of the replica set, then step down the primary and build
there -- to avoid the build's load affecting the whole set at once. See
https://www.mongodb.com/docs/manual/tutorial/build-indexes-on-replica-sets/[Rolling index builds].

`hint()` forces a specific index (or `{ $natural: 1 }` for a deliberate collection scan), which is useful for
testing and for the rare case where the planner's choice is wrong. See
https://www.mongodb.com/docs/manual/reference/method/cursor.hint/[`cursor.hint()`].

[source,javascript]
----
db.orders.find({ status: "shipped", qty: { $gte: 20 } }).hint({ status: 1, orderDate: 1, qty: 1 })
----

Do not add an index when: the collection is tiny (a scan is already cheap); the field has very low
cardinality and the query returns a large fraction of the collection (a scan is cheaper than an index scan
plus fetches); the query runs rarely and writes are hot; or an existing compound index already covers the
need as a prefix. Prefer extending or reordering an existing compound index over adding a near-duplicate one.
For the full list of types and options see
https://www.mongodb.com/docs/manual/core/indexes/index-types/[Index types] and
xref:database/mongodb/special-indexes-and-search.adoc[Text, wildcard, geospatial & Atlas search].

See also xref:database/diagnosing-slow-queries.adoc[] for how a missing or poorly-ordered compound index shows
up as a slow query in an execution plan, and how to confirm it before adding one.
