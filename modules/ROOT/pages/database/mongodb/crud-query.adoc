= Reading data with the Query API
:description: How MongoDB reads documents with the Query API -- find and findOne, the query filter document, projection, query operators, embedded-document and array matching, and cursor behavior.
:keywords: mongodb, query api, find, findOne, filter, projection, query operators, $elemMatch, cursor, sort, skip, limit, hint, countDocuments, distinct, collation

include::partial$ai-disclaimer.adoc[]

The Query API reads documents from a collection by matching them against a *filter document* and shaping the
result with a *projection*. This page covers `find` / `findOne`, the operators that build filters, how
matching works against embedded documents and arrays, and the cursor that carries results back. The canonical
walkthrough is https://www.mongodb.com/docs/manual/tutorial/query-documents/[Query Documents] in the manual.

== find and findOne

`db.collection.find(filter, projection)` returns a *cursor* over every matching document;
`db.collection.findOne(filter, projection)` returns a single document (the first match) or `null`. An empty or
omitted filter matches every document.

[source,javascript]
----
// every document in the collection
db.products.find()

// first match only, as a plain document
db.products.findOne({ sku: "A-1001" })
----

See https://www.mongodb.com/docs/manual/reference/method/db.collection.find/[`db.collection.find()`] for the
full method signature and options.

Against the shop dataset from xref:database/mongodb/getting-started.adoc[Getting Started], a filter and a
projection together answer "which orders were shipped, and to whom?" -- and nothing else crosses the wire:

[source,javascript]
----
shop> db.orders.find({ status: "shipped" }, { customerId: 1, status: 1, _id: 0 })
[
  { customerId: 'c-1', status: 'shipped' },
  { customerId: 'c-2', status: 'shipped' },
  { customerId: 'c-3', status: 'shipped' },
  { customerId: 'c-1', status: 'shipped' }
]
----

Compared with SQL (xref:database/sql/dml-queries.adoc[Queries (SELECT)]): the filter document plays the role
of the `WHERE` clause, the projection plays the role of the `SELECT` column list, and cursor modifiers
(`sort`, `limit`, `skip`) correspond to `ORDER BY`, `LIMIT`, and `OFFSET`.

== How a find is executed

Reading the stages in the order the server performs them explains most of the Query API's behaviour -- why a
projection can save a fetch, why `skip` is costly, and why a sort can be free. The filter is matched first
(through an index when one fits), then the matching documents are fetched, then sorted if no index supplied the
order, then `skip` and `limit` are applied, and the projection shapes what is sent back. The cursor then hands the
result to the client in batches.

[mermaid]
....
flowchart LR
  F[Filter document] --> PL{Planner: usable index?}
  PL -- yes --> IX[IXSCAN: seek keys in the index]
  PL -- no --> CS[COLLSCAN: read every document]
  IX --> FE[FETCH: load matching documents]
  CS --> FE
  FE --> SO[SORT, unless the index already supplies the order]
  SO --> SL[SKIP then LIMIT]
  SL --> PR[PROJECTION: choose the fields]
  PR --> CU[Cursor: first batch, then getMore calls]
....

The first batch of a cursor holds up to 101 documents (or 16 MB); later `getMore` calls return up to 16 MB each,
and `cursor.batchSize(n)` tunes the document count. The shell prints 20 documents and waits for `it`, but that is
a display limit, not a server one.

== The query filter document

A filter is a document. A field paired with a plain value is an *implicit equality* test; several fields in
the same filter are an *implicit `$and`* -- every condition must hold.

[source,javascript]
----
// status == "active" AND qty == 50
db.products.find({ status: "active", qty: 50 })

// the same, written explicitly
db.products.find({ $and: [ { status: "active" }, { qty: 50 } ] })
----

An equality test against an array field matches when the array *contains* that value; an equality test
against a document value requires an exact match (see <<Embedded documents>> and <<Arrays>>).

== Projection

The second argument to `find` selects which fields come back. Values of `1` (or `true`) *include* fields;
values of `0` (or `false`) *exclude* them. Inclusion and exclusion cannot be mixed in one projection, except
that `_id` -- included by default -- may always be switched off.

[source,javascript]
----
// include only name and price (plus _id)
db.products.find({}, { name: 1, price: 1 })

// include name and price, drop _id
db.products.find({}, { name: 1, price: 1, _id: 0 })

// exclude internal fields, keep everything else
db.products.find({}, { internalNotes: 0, _vector: 0 })
----

Projection also accepts array-shaping operators:

[source,javascript]
----
// $slice: first 3 elements of the reviews array
db.products.find({}, { reviews: { $slice: 3 } })

// $slice with [skip, limit]: elements 5..14
db.products.find({}, { reviews: { $slice: [5, 10] } })

// $elemMatch: return only the first tags-subdocument matching the condition
db.products.find({}, { variants: { $elemMatch: { color: "red" } } })

// $ positional: return only the first array element matched by the filter
db.products.find({ "grades.score": { $gt: 90 } }, { "grades.$": 1 })

// $meta: expose the text-search relevance score (needs a $text filter)
db.articles.find({ $text: { $search: "mongodb" } }, { score: { $meta: "textScore" } })
----

Applied to the shop's `orders`, the array projections each return a different slice of the same order:

[source,javascript]
----
shop> db.orders.find({ _id: 1001 }, { items: { $elemMatch: { sku: "B-7" } } })    // first matching line only
[ { _id: 1001, items: [ { sku: 'B-7', qty: 2, price: 24.99 } ] } ]

shop> db.orders.find({ _id: 1004 }, { items: { $slice: 1 } })                      // first line, whole order otherwise
[ { _id: 1004, customerId: 'c-3', status: 'shipped', orderDate: ISODate('2026-02-20T18:45:00.000Z'),
    items: [ { sku: 'A-2', qty: 4, price: 189.5 } ] } ]

shop> db.orders.find({ "items.price": { $gt: 300 } }, { "items.$": 1 })            // the line the filter matched
[ { _id: 1001, items: [ { sku: 'A-1', qty: 1, price: 349 } ] },
  { _id: 1004, items: [ { sku: 'A-1', qty: 2, price: 349 } ] } ]
----

Details and restrictions are in
https://www.mongodb.com/docs/manual/tutorial/project-fields-from-query-results/[Project Fields to Return].
Choosing a projection that an index fully satisfies produces a *covered query*; see
xref:database/mongodb/indexes.adoc[Indexes].

== Query operators

Operators are documents of the form `{ field: { $operator: value } }`. The full list is the
https://www.mongodb.com/docs/manual/reference/operator/query/[Query and Projection Operators] reference.

=== Comparison

`$eq`, `$ne`, `$gt`, `$gte`, `$lt`, `$lte` compare a field against a single value; `$in` and `$nin` compare
against a list.

[source,javascript]
----
db.products.find({
  price:  { $gte: 10, $lte: 100 },   // 10 <= price <= 100
  status: { $ne: "discontinued" },
  brand:  { $in: ["acme", "globex"] }
})
----

=== Logical

`$and`, `$or`, `$nor` take an array of clause documents; `$not` negates a single operator expression.

[source,javascript]
----
db.products.find({
  $or: [ { onSale: true }, { price: { $lt: 20 } } ],
  qty: { $not: { $lt: 1 } }          // qty is not < 1
})
----

=== Element

`$exists` tests for the presence of a field; `$type` tests its BSON type (by string alias or number).

[source,javascript]
----
// discountCode present, and expiresAt stored as a real Date
db.coupons.find({
  discountCode: { $exists: true },
  expiresAt:    { $type: "date" }
})
----

=== Evaluation

`$regex` matches strings against a pattern, `$mod` matches by remainder, `$expr` embeds an aggregation
expression (so one field can be compared to another), `$text` runs a text-index search, and `$jsonSchema`
validates a document against a schema.

[source,javascript]
----
db.products.find({
  name:  { $regex: /^wid/i },                    // starts with "wid", case-insensitive
  qty:   { $mod: [4, 0] },                       // qty divisible by 4
  $expr: { $gt: ["$spent", "$budget"] },         // spent > budget (field vs. field)
  $jsonSchema: { required: ["sku"], properties: { sku: { bsonType: "string" } } }
})
----

`$expr` uses the same expression language as the
xref:database/mongodb/aggregation-pipeline.adoc[aggregation pipeline].

=== $where and its risk

`$where` runs a JavaScript predicate against every candidate document. It cannot use indexes, runs the
server-side JavaScript engine per document, and executes arbitrary code, so it is slow and a security
concern. Prefer `$expr` or a rewritten filter.

[source,javascript]
----
// avoid: full collection scan, JS evaluated per document
db.products.find({ $where: "this.price * this.qty > 1000" })

// prefer: $expr, index-friendlier and no JS engine
db.products.find({ $expr: { $gt: [ { $multiply: ["$price", "$qty"] }, 1000 ] } })
----

The `$expr` form is also the way to compare two fields of one document. On the shop's `products`, "inventory
value above 5000" (`price` times `stock`) selects exactly the Office Chair (189.5 x 30) and the Monitor
(279 x 25):

[source,javascript]
----
shop> db.products.find({ $expr: { $gt: [{ $multiply: ["$price", "$stock"] }, 5000] } }, { name: 1 })
[ { _id: 'A-2', name: 'Office Chair' }, { _id: 'C-9', name: 'Monitor 27in' } ]
----

See https://www.mongodb.com/docs/manual/reference/operator/query/where/[`$where`] for the security notes.

== Embedded documents

A filter value that is itself a document requires an *exact match*: the same fields, the same values, in the
same order. To match a single nested field regardless of the rest of the subdocument, use *dot notation*.

[source,javascript]
----
// exact match: address must equal this document exactly
db.people.find({ address: { city: "Oslo", zip: "0150" } })

// dot notation: only address.city matters
db.people.find({ "address.city": "Oslo" })

// dot notation with an operator
db.people.find({ "address.zip": { $in: ["0150", "0151"] } })
----

Full rules are in
https://www.mongodb.com/docs/manual/tutorial/query-embedded-documents/[Query on Embedded/Nested Documents].

== Arrays

Matching rules for array fields are covered in
https://www.mongodb.com/docs/manual/tutorial/query-arrays/[Query an Array].

[source,javascript]
----
// contains the element "red"
db.products.find({ tags: "red" })

// at least one element > 90 AND at least one element < 100 (possibly different elements)
db.products.find({ scores: { $gt: 90, $lt: 100 } })

// $elemMatch: ONE element satisfies BOTH conditions
db.products.find({ scores: { $elemMatch: { $gt: 90, $lt: 100 } } })

// $all: array contains every listed value (in any order)
db.products.find({ tags: { $all: ["red", "sale"] } })

// $size: array has exactly 3 elements
db.products.find({ tags: { $size: 3 } })

// positional path: the first element's "grade" field
db.students.find({ "results.0.grade": "A" })

// $elemMatch on an array of subdocuments
db.orders.find({ items: { $elemMatch: { sku: "A-1", qty: { $gte: 2 } } } })
----

Without `$elemMatch`, multiple conditions on an array field may be satisfied by *different* elements; with
`$elemMatch`, a single element must satisfy all of them. This is the most common source of wrong results in
queries over embedded arrays, so it is worth seeing on real data. "Orders containing at least two units of the
Standing Desk (`A-1`)":

[source,javascript]
----
// WRONG: "some line has sku A-1" AND "some line has qty >= 2" -- possibly different lines
shop> db.orders.find({ "items.sku": "A-1", "items.qty": { $gte: 2 } }, { _id: 1 })
[ { _id: 1001 }, { _id: 1004 } ]

// RIGHT: one line must be A-1 AND have qty >= 2
shop> db.orders.find({ items: { $elemMatch: { sku: "A-1", qty: { $gte: 2 } } } }, { _id: 1 })
[ { _id: 1004 } ]
----

Order `1001` contains one desk (`qty: 1`) and, on a different line, two lamps (`qty: 2`). Each half of the dotted
filter is satisfied -- by different array elements -- so it matches although no single line is "two or more desks".
The same applies to `$gt` / `$lt` pairs on one numeric array, as in the `scores` example above.

A few more operators on the shop's `products`, with their results:

[source,javascript]
----
shop> db.products.find({ tags: { $all: ["office", "sale"] } }, { name: 1 })        // has both tags
[ { _id: 'A-2', name: 'Office Chair' } ]
shop> db.products.find({ tags: { $size: 3 } }, { name: 1 })                         // exactly three tags
[ { _id: 'A-2', name: 'Office Chair' } ]
shop> db.products.find({ name: { $regex: /^desk/i } }, { name: 1 })                 // anchored, case-insensitive
[ { _id: 'B-7', name: 'Desk Lamp' } ]
shop> db.products.find({ $or: [{ category: "lighting" }, { price: { $lt: 40 } }], stock: { $not: { $lt: 100 } } }, { name: 1 })
[ { _id: 'B-7', name: 'Desk Lamp' } ]
----

A case-insensitive `$regex` cannot use an ordinary index efficiently, and an unanchored pattern cannot seek at all
(only a case-sensitive pattern anchored with `+^+` can walk a bounded index range); for case-insensitive equality
use a collation (below), and for word search use a text index (see
xref:database/mongodb/special-indexes-and-search.adoc[Text, Wildcard, Geospatial & Atlas Search]).

== Cursors

`find` returns a lazily evaluated cursor. In `mongosh` the cursor is iterated automatically for display;
in code it is walked with `hasNext` / `next` or `forEach`, fetching documents in batches from the server.

[source,javascript]
----
const cursor = db.products.find({ status: "active" });
while (cursor.hasNext()) {
  printjson(cursor.next());
}
----

=== sort, skip, limit

[source,javascript]
----
// newest first, rows 21..40
db.products.find()
  .sort({ createdAt: -1 })   // -1 descending, 1 ascending
  .skip(20)
  .limit(20)
----

`sort` corresponds to SQL `ORDER BY`, `limit` to `LIMIT`, and `skip` to `OFFSET`
(xref:database/sql/dml-queries.adoc[Queries (SELECT)]). See
https://www.mongodb.com/docs/manual/reference/method/cursor.sort/[`cursor.sort()`].

The order of the modifiers in the call chain does not matter -- the server always applies sort, then skip, then
limit -- but the sort must be deterministic for paging to be correct. Two documents that tie on the sort key can
swap places between calls, so a page boundary may repeat or lose a row. Add a unique tiebreaker such as `_id` to
the sort: `sort({ orderDate: -1, _id: -1 })`. On the shop:

[source,javascript]
----
shop> db.orders.find({}, { _id: 1 }).sort({ orderDate: -1 }).skip(2).limit(2)
[ { _id: 1006 }, { _id: 1005 } ]
----

=== hint

`hint` forces a specific index instead of letting the query planner choose.

[source,javascript]
----
db.products.find({ status: "active", brand: "acme" }).hint({ status: 1, brand: 1 })
----

Index selection and forcing is covered in xref:database/mongodb/indexes.adoc[Indexes].

=== countDocuments and distinct

[source,javascript]
----
// accurate count of documents matching a filter
db.products.countDocuments({ status: "active" })

// unique values of a field among matching documents
db.products.distinct("brand", { status: "active" })
----

On the shop, `db.orders.countDocuments({ status: "open" })` returns `3` and `db.orders.distinct("status")` returns
`[ 'cancelled', 'open', 'shipped' ]`. `countDocuments` runs an aggregation (a `$match` plus a `$group`), so it is
accurate but costs a scan of the matching keys; `estimatedDocumentCount()` reads collection metadata instead and
is instant but takes no filter and can be off after an unclean shutdown. `distinct` returns one array, which must
fit in a single 16 MB document; for high-cardinality fields use `$group` instead.

`countDocuments` is documented at
https://www.mongodb.com/docs/manual/reference/method/db.collection.countDocuments/[`countDocuments()`];
prefer it over the legacy `count()`.

=== collation

`collation` controls string comparison and sort order for the query -- locale, case sensitivity, and
accent sensitivity.

[source,javascript]
----
// case-insensitive match and sort for Norwegian
db.people.find({ name: "aa" })
  .collation({ locale: "nb", strength: 1 })
----

Collation matters for equality and for sort order alike. Against a collection holding the names `Aasen`, `aasen`,
`Åsen` and `Berg`, an English strength-2 collation (case-insensitive, accent-sensitive) finds both spellings of
"aasen" and not the accented one:

[source,javascript]
----
shop> db.n.find({ name: "aasen" }, { _id: 0 }).collation({ locale: "en", strength: 2 })
[ { name: 'Aasen' }, { name: 'aasen' } ]
----

A query collation is honoured by an index only if the index was created with the *same* collation; otherwise the
planner falls back to a collection scan. See xref:database/mongodb/indexes.adoc[Indexing & Query Performance].

See https://www.mongodb.com/docs/manual/reference/collation/[Collation].

=== Avoiding large skips

`skip(n)` still walks and discards the first `n` documents, so deep pagination gets progressively slower.
Paginate with a *range query* on an indexed field instead, carrying the last seen key forward.

[source,javascript]
----
// page 1
db.products.find().sort({ _id: 1 }).limit(20)

// next page: start after the last _id seen, no skip
db.products.find({ _id: { $gt: lastId } }).sort({ _id: 1 }).limit(20)
----

The difference is measurable. On 100,000 orders with an index on `orderDate`, asking for ten rows after skipping
50,000 versus asking for ten rows after the last date already seen gives these `explain("executionStats")`
counters:

[cols="3,2,1,1,1",options="header"]
|===
| Query | Stages | `nReturned` | `totalKeysExamined` | `totalDocsExamined`

| `+find().sort({ orderDate: 1 }).skip(50000).limit(10)+` | `IXSCAN`, `SKIP`, `FETCH`, `LIMIT` | 10 | 50010 | 10
| `+find({ orderDate: { $gt: lastSeen } }).sort({ orderDate: 1 }).limit(10)+` | `IXSCAN`, `FETCH`, `LIMIT` | 10 | 10 | 10
|===

The skipped 50,000 index entries are walked and thrown away on every request, so the cost of page *n* grows with
*n*; the range query seeks straight to the first key after `lastSeen` and reads exactly the ten it returns. The
price is that the client can only move to the "next" page, not jump to page 300, and the sort key must be unique
(or combined with `_id`) so that no row is skipped or repeated.

See xref:database/pagination-strategies.adoc[Pagination: Offset vs. Keyset] for why offset-based paging degrades
regardless of store, and how this same range-query pattern compares to SQL's seek method, Solr's `cursorMark`,
Elasticsearch's `search_after`, and Spring Data's `Window<T>` scrolling.

=== No-timeout cursors

The server closes an idle cursor after about 10 minutes. A long-running scan can request
`noCursorTimeout`, but it must then be closed explicitly or it leaks server resources.

[source,javascript]
----
const cursor = db.events.find().noCursorTimeout();
try {
  cursor.forEach(doc => process(doc));
} finally {
  cursor.close();
}
----

See https://www.mongodb.com/docs/manual/reference/method/cursor.noCursorTimeout/[`cursor.noCursorTimeout()`].
