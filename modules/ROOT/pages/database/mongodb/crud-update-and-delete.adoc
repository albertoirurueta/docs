= Updating & deleting documents
:description: How MongoDB changes and removes documents -- updateOne/updateMany/replaceOne, field and array update operators, upserts, findOneAndUpdate, pipeline-form updates, and deleteOne/deleteMany.
:keywords: mongodb, update, updateOne, updateMany, replaceOne, upsert, $set, $unset, $inc, $push, $pull, arrayFilters, findOneAndUpdate, deleteOne, deleteMany, drop

include::partial$ai-disclaimer.adoc[]

Writes that change existing data come in two shapes: *operator updates*, which modify named fields in place,
and *full replacement*, which swaps the whole document (except `_id`). This page covers the update and delete
methods, the field and array update operators, upserts, the `findOneAndX` family, and pipeline-form updates.
The manual's overview is https://www.mongodb.com/docs/manual/tutorial/update-documents/[Update Documents].

== updateOne, updateMany, replaceOne

`updateOne(filter, update)` modifies the first document matching `filter`; `updateMany(filter, update)`
modifies all of them. The `filter` is exactly the filter document from
xref:database/mongodb/crud-query.adoc[Reading data with the Query API]. An *operator update* uses `$`-prefixed
operators and touches only the named fields; a *replacement* passes a plain document and replaces every field
but `_id`. `replaceOne` is the dedicated method for the replacement case.

[source,javascript]
----
// operator update: only "status" and "updatedAt" change
db.orders.updateOne(
  { _id: 42 },
  { $set: { status: "shipped", updatedAt: new Date() } }
)

// updateMany: same change across many documents
db.orders.updateMany({ status: "open" }, { $set: { status: "cancelled" } })

// replaceOne: whole document swapped (keeps _id)
db.orders.replaceOne({ _id: 42 }, { customerId: 7, status: "shipped", lines: [] })
----

The methods return a write result describing what happened. `mongosh` prints it like this (the `upsertedId` field
appears only when an upsert inserted a document):

[source,javascript]
----
shop> db.orders.updateOne({ _id: 1002 }, { $set: { status: "shipped" } })
{ acknowledged: true, insertedId: null, matchedCount: 1, modifiedCount: 1, upsertedCount: 0 }
shop> db.orders.updateOne({ _id: 1002 }, { $set: { status: "shipped" } })      // same value again
{ acknowledged: true, insertedId: null, matchedCount: 1, modifiedCount: 0, upsertedCount: 0 }
----

`matchedCount` counts documents that matched the filter; `modifiedCount` counts those actually changed (a
`$set` to the value a field already holds matches but does not modify, as the second call shows).

The difference between an operator update and a replacement is easy to underestimate. `replaceOne` keeps only
`_id` and the fields you pass -- everything else is gone:

[source,javascript]
----
shop> db.orders.replaceOne({ _id: 1002 }, { customerId: "c-1", status: "shipped" })
shop> db.orders.findOne({ _id: 1002 })
{ _id: 1002, customerId: 'c-1', status: 'shipped' }        // orderDate and items were wiped
----

Use `$set` for "change these fields" and reserve `replaceOne` for "this is the complete new state", ideally paired
with a version field in the filter (see <<Optimistic locking with a version field>>). Every single
document write is atomic: a concurrent reader sees either the document before the update or after it, never a
half-applied mix of the operators in one update document.

== Field update operators

The full list is https://www.mongodb.com/docs/manual/reference/operator/update/[Update Operators].

[source,javascript]
----
db.products.updateOne(
  { _id: "A-1" },
  {
    $set:         { name: "Widget", "spec.color": "red" },  // set fields (creates if absent)
    $unset:       { legacyCode: "" },                       // remove a field
    $rename:      { desc: "description" },                   // rename a field
    $inc:         { views: 1, stock: -2 },                  // add to numeric fields
    $mul:         { price: 1.1 },                           // multiply a numeric field
    $min:         { lowestSeen: 9.99 },                     // set only if given value is lower
    $max:         { highestSeen: 19.99 },                   // set only if given value is higher
    $currentDate: { updatedAt: true },                      // set to current date/time
    $setOnInsert: { createdAt: new Date() }                 // applied only on an upsert insert
  }
)
----

`$setOnInsert` has no effect on a plain update; it only seeds fields when an upsert creates a new document
(see <<Upserts>>). Run against the Standing Desk (`A-1`), a combined update showed these effects -- the unknown
fields `spec.color`, `lowestSeen` and `highestSeen` were created, `tags` was renamed and `stock` dropped from
12 to 10, while `$setOnInsert` was ignored:

[source,javascript]
----
shop> db.products.updateOne({ _id: "A-1" }, {
...   $set: { "spec.color": "oak" }, $inc: { stock: -2 }, $min: { lowestSeen: 9.99 }, $max: { highestSeen: 349 },
...   $rename: { tags: "labels" }, $currentDate: { updatedAt: true }, $setOnInsert: { x: 1 } })
shop> db.products.findOne({ _id: "A-1" })
{ _id: 'A-1', name: 'Standing Desk', category: 'furniture', price: 349, stock: 10, highestSeen: 349,
  labels: [ 'office', 'ergonomic' ], lowestSeen: 9.99, spec: { color: 'oak' }, updatedAt: ISODate('2026-11-10T13:46:26.863Z') }
----

Two rules the server enforces: one update document may not touch the same path twice, so combining `$min` and
`$max` on one field fails with `Updating the path 'price' would create a conflict at 'price'`; and `$min` /
`$max` / `$inc` create a missing field (using the given value as the starting point), so they are safe to use on
documents that may not have it yet. `$inc` on a missing field adds to zero, which makes a counter that starts
itself.

== Array update operators

=== $push (with $each, $slice, $sort, $position)

[source,javascript]
----
// append one element
db.carts.updateOne({ _id: 1 }, { $push: { items: "sku-9" } })

// append several, keep the array sorted and capped at 10, inserting at index 0
db.feeds.updateOne(
  { _id: 1 },
  { $push: { entries: {
      $each: [ { ts: 3 }, { ts: 1 } ],
      $sort: { ts: 1 },
      $slice: -10,
      $position: 0
  } } }
)
----

Seeing the effect of `$each`, `$sort` and `$slice` together: pushing three timestamps into an empty array while
keeping the two newest leaves `[ { ts: 2 }, { ts: 3 } ]`, and `$position: 0` against `[ { ts: 5 } ]` produces
`[ { ts: 3 }, { ts: 1 }, { ts: 5 } ]`. A bounded feed ("keep the last 50 notifications") is one `updateOne` with
`$push`, `$each` and a negative `$slice`, applied atomically, with no read-modify-write race.

=== $addToSet

[source,javascript]
----
// add only if not already present (set semantics)
db.products.updateOne({ _id: "A-1" }, { $addToSet: { tags: { $each: ["sale", "new"] } } })
----

On the Office Chair (`A-2`, tags `[ 'office', 'ergonomic', 'sale' ]`), `$addToSet` with `["sale", "new"]` adds only
`new`, because `sale` is already there, giving `[ 'office', 'ergonomic', 'sale', 'new' ]`. Then
`$pull: { tags: { $in: ["sale", "new"] } }` removes both again, and `$pop: { tags: -1 }` removes the first element,
leaving `[ 'ergonomic' ]`.

=== $pop

[source,javascript]
----
db.carts.updateOne({ _id: 1 }, { $pop: { items: 1 } })   // 1 removes last, -1 removes first
----

=== $pull and $pullAll

[source,javascript]
----
// $pull: remove every element matching a condition
db.carts.updateOne({ _id: 1 }, { $pull: { items: { qty: { $lte: 0 } } } })

// $pullAll: remove every listed value exactly
db.carts.updateOne({ _id: 1 }, { $pullAll: { skus: ["sku-1", "sku-2"] } })
----

=== Positional operators $, $[], $[<identifier>]

`$` updates the *first* array element matched by the query filter. `$[]` updates *every* element.
`$[<identifier>]` updates every element matched by a matching entry in `arrayFilters`. These are documented as the
https://www.mongodb.com/docs/manual/reference/operator/update/positional/[first-match],
https://www.mongodb.com/docs/manual/reference/operator/update/positional-all/[all-elements], and
https://www.mongodb.com/docs/manual/reference/operator/update/positional-filtered/[filtered] positional operators.

[source,javascript]
----
// $ : bump the qty of the matched line only
db.orders.updateOne(
  { _id: 1, "lines.sku": "A-1" },
  { $set: { "lines.$.qty": 5 } }
)

// $[] : apply a discount to every line
db.orders.updateOne({ _id: 1 }, { $mul: { "lines.$[].price": 0.9 } })

// $[elem] with arrayFilters : only lines over 100
db.orders.updateOne(
  { _id: 1 },
  { $set: { "lines.$[big].flagged": true } },
  { arrayFilters: [ { "big.price": { $gt: 100 } } ] }
)
----

== Upserts

Passing `{ upsert: true }` makes an update that matches nothing *insert* a new document instead. The new
document is built from the equality conditions in the filter plus any `$setOnInsert` and other update
operators.

[source,javascript]
----
db.counters.updateOne(
  { _id: "invoice" },                 // equality condition -> seeds _id
  {
    $inc: { seq: 1 },                 // applied to the new document too
    $setOnInsert: { createdAt: new Date() }
  },
  { upsert: true }
)
----

If no `invoice` counter exists, the upsert inserts `{ _id: "invoice", seq: 1, createdAt: <now> }`; the write
result then carries `upsertedId`. The decision the server makes:

[mermaid]
....
flowchart TD
  U[updateOne with upsert: true] --> M{Does a document match the filter?}
  M -- yes --> A[Apply the update operators to it]
  M -- no --> B[Build a new document from the filter equality fields]
  B --> C[Apply the update operators, including setOnInsert]
  C --> I[Insert it and report upsertedId]
  A --> R[Report matchedCount and modifiedCount]
....

Run twice against an empty `counters` collection, the first call inserts and the second increments:

[source,javascript]
----
shop> db.counters.updateOne({ _id: "invoice" }, { $inc: { seq: 1 }, $setOnInsert: { createdAt: new Date() } }, { upsert: true })
{ acknowledged: true, insertedId: 'invoice', matchedCount: 0, modifiedCount: 0, upsertedCount: 1 }
shop> db.counters.updateOne({ _id: "invoice" }, { $inc: { seq: 1 }, $setOnInsert: { createdAt: new Date() } }, { upsert: true })
{ acknowledged: true, insertedId: null, matchedCount: 1, modifiedCount: 1, upsertedCount: 0 }
shop> db.counters.find()
[ { _id: 'invoice', createdAt: ISODate('2026-11-10T13:39:00.119Z'), seq: 2 } ]
----

An upsert is atomic, but two concurrent upserts on a field *without a unique index* can both decide "no match" and
insert twice. When the filter does not include `_id`, back it with a unique index so that the loser fails with a
duplicate-key error and the driver can retry the now-matching update. See
https://www.mongodb.com/docs/manual/reference/method/db.collection.updateOne/#upsert[the upsert notes].

=== Optimistic locking with a version field

Single-document updates are atomic, but a read-modify-write cycle spanning two calls is not: two clients can read the
same document and overwrite each other. Putting a `version` in the *filter* turns the update into a
compare-and-swap, with no lock held between the read and the write:

[source,javascript]
----
shop> db.products.updateOne({ _id: "C-3" }, { $set: { version: 1 } })
shop> const a = db.products.findOne({ _id: "C-3" }), b = db.products.findOne({ _id: "C-3" })   // two clients, both see version 1
shop> db.products.updateOne({ _id: "C-3", version: a.version }, { $set: { price: 42 }, $inc: { version: 1 } }).modifiedCount
1
shop> db.products.updateOne({ _id: "C-3", version: b.version }, { $set: { price: 45 }, $inc: { version: 1 } }).matchedCount
0                                   // the second client lost: re-read, re-apply, retry
shop> db.products.findOne({ _id: "C-3" }, { price: 1, version: 1 })
{ _id: 'C-3', price: 42, version: 2 }
----

A `matchedCount` of `0` is the conflict signal. For a plain counter you do not need this at all -- `$inc` is already
atomic and never loses an update.

== findOneAndUpdate, findOneAndReplace, findOneAndDelete

These modify (or delete) a single document and *return a document* in one atomic step. `returnDocument`
chooses which version comes back: `"before"` (the default) or `"after"`. They also accept `sort` (to pick
which document when several match) and `projection`.

[source,javascript]
----
// atomically claim the next queued job and get it back
const job = db.jobs.findOneAndUpdate(
  { status: "queued" },
  { $set: { status: "running", startedAt: new Date() } },
  { sort: { priority: -1 }, returnDocument: "after" }
)

db.people.findOneAndReplace({ _id: 1 }, { name: "Ada", role: "admin" }, { returnDocument: "after" })

db.jobs.findOneAndDelete({ status: "done" }, { sort: { finishedAt: 1 } })
----

The atomic claim above is the building block of a work queue: no two workers can receive the same document,
because the match and the update happen as one operation on that document. With three queued jobs of priority 1,
5 and 3, four consecutive claims returned the jobs in priority order and then `null` when the queue was empty:

[source,javascript]
----
shop> for (let i = 0; i < 4; i++) printjson(db.jobs.findOneAndUpdate({ status: "queued" }, { $set: { status: "running" } }, { sort: { priority: -1 } }))
{ _id: 2, status: 'queued', priority: 5 }       // the document as it was BEFORE the update (default returnDocument)
{ _id: 3, status: 'queued', priority: 3 }
{ _id: 1, status: 'queued', priority: 1 }
null
----

Note that the returned documents still say `queued` -- the default `returnDocument: "before"` returns the
pre-update state; pass `"after"` to see `running`. Back such a queue with an index on `{ status: 1, priority: -1 }` so
the claim does not scan.

See https://www.mongodb.com/docs/manual/reference/method/db.collection.findOneAndUpdate/[`findOneAndUpdate()`].

== Update with an aggregation pipeline

The update argument can be an *array* -- an aggregation pipeline (`$set`/`$addFields`, `$unset`, `$replaceRoot`,
`$replaceWith`). This allows an update that references other fields of the same document.

[source,javascript]
----
// total is computed from price and qty already in the document
db.orders.updateMany(
  {},
  [ { $set: { total: { $multiply: ["$price", "$qty"] },
              updatedAt: "$$NOW" } } ]
)
----

On the shop's order shape, one pipeline update derives both the order total and the line count from the embedded
items, a computation the operator-style update language cannot express:

[source,javascript]
----
shop> db.o3.insertOne({ _id: 1, items: [ { qty: 2, price: 10 }, { qty: 1, price: 5 } ] })
shop> db.o3.updateOne({ _id: 1 }, [ { $set: {
...   total: { $sum: { $map: { input: "$items", as: "i", in: { $multiply: ["$$i.qty", "$$i.price"] } } } },
...   itemCount: { $size: "$items" } } } ])
shop> db.o3.findOne()
{ _id: 1, items: [ { qty: 2, price: 10 }, { qty: 1, price: 5 } ], total: 25, itemCount: 2 }
----

An array passed as the update is *always* a pipeline: `[ { $set: { a: 1 } } ]` is not the same as
`{ $set: { a: 1 } }` even though the outcome looks alike, and mixing `$push`-style operators into the array is an
error. The allowed stages and worked examples are in
https://www.mongodb.com/docs/manual/tutorial/update-documents-with-aggregation-pipeline/[Update Documents with
Aggregation Pipeline]; the expression language is the same one described in
xref:database/mongodb/aggregation-pipeline.adoc[Aggregation pipeline].

== deleteOne and deleteMany

`deleteOne(filter)` removes the first matching document; `deleteMany(filter)` removes all of them. The filter
is again the query filter document. The walkthrough is
https://www.mongodb.com/docs/manual/tutorial/remove-documents/[Delete Documents].

[source,javascript]
----
db.sessions.deleteOne({ _id: "s-1" })

db.sessions.deleteMany({ expiresAt: { $lt: new Date() } })

// delete every document, keep the collection, its indexes, and its options
db.sessions.deleteMany({})
----

The delete result reports how many were removed:

[source,javascript]
----
shop> db.orders.updateMany({ status: "open" }, { $set: { status: "cancelled" } })
{ acknowledged: true, insertedId: null, matchedCount: 3, modifiedCount: 3, upsertedCount: 0 }
shop> db.orders.deleteMany({ status: "cancelled" })
{ acknowledged: true, deletedCount: 4 }
----

(Three open orders were cancelled, joining the one that was already cancelled, and all four were removed.)
There is no "are you sure": a `deleteMany` with a mistyped filter is permanent, so a careful routine first runs
`countDocuments` with the same filter, or `find` with a projection, and only then deletes -- or takes a backup
(see xref:database/mongodb/backup-and-data-tools.adoc[Backups, Import/Export & GridFS]). An empty filter
`{}` deletes everything, including on a typo. Soft deletion (a `deletedAt` field plus a partial index) is the
usual alternative when the data must remain recoverable.
== drop() versus deleting all documents

`db.collection.deleteMany({})` empties a collection but leaves the collection, its indexes, and its
configured options in place. `db.collection.drop()` removes the collection itself -- including every index --
and is typically much faster because it does not process documents one by one.

[source,javascript]
----
db.sessions.drop()   // collection and its indexes are gone
----

The difference is visible in the metadata. A collection with one secondary index and two documents, emptied with
`deleteMany({})`, still lists two indexes (`+_id_+` and the secondary one) and zero documents; after `drop()` the
collection is no longer in `getCollectionNames()` at all.

See https://www.mongodb.com/docs/manual/reference/method/db.collection.drop/[`db.collection.drop()`].
