= Quantization & Compression
:description: Shrinking vector memory and speeding up scoring with scalar, product, and binary quantization, plus PCA and Matryoshka dimensionality reduction, illustrated with FAISS, pgvector, Qdrant, and Elasticsearch.
:keywords: quantization, scalar quantization, halfvec, int8, product quantization, faiss, indexpq, indexivfpq, index_factory, indexrefineflat, binary quantization, binary_quantize, pgvector, qdrant, elasticsearch, bbq, pca, indexpretransform, matryoshka, dimensionality reduction

include::partial$vector-rag-disclaimer.adoc[]

Examples on this page target Python 3.12, FAISS 1.15.1, and pgvector 0.8.6. Every quantization scheme below
trades a small amount of recall for a reduction in memory and, usually, faster distance computation; the
goal is always to pick the smallest representation that still meets a recall target, not the smallest
representation available.

== Why vectors are memory-bound

A single `float32` embedding of dimension `d` costs `4d` bytes, and an ANN index adds graph or list overhead
on top of that (xref:database/vector-rag/ann-indexes.adoc[] derives HNSW's per-vector memory formula
`(d·4 + M·2·4)` bytes). At 768 dimensions -- the *DocsAssistant* scenario's embedding size -- a bare
`float32` vector already costs 3,072 bytes, so 10 million chunks cost roughly 30 GB before any index
overhead. Vector search is therefore usually memory-bound, not CPU-bound: fitting the working set in RAM
(or in a smaller, faster storage tier) matters more than raw FLOP throughput, and it directly determines
which instance sizes and how many replicas a deployment needs.

=== Scalar quantization

The simplest lever is to store each component in fewer bits:

[cols="1,2,3",options="header"]
|===
| Representation | Bytes per dimension | Notes

| `float32` (baseline) | 4 | Full IEEE-754 precision; the default in every engine unless configured otherwise.
| `float16` / `halfvec` | 2 | Half the memory, usually near-lossless recall for cosine/inner-product search. pgvector's `halfvec` type stores this directly and supports its own operators and an HNSW/IVFFlat index built over it.
| `int8` | 1 | Requires a per-vector or per-collection scale/offset (`x_int8 = round((x - min) / (max - min) * 255)`); a small, usually acceptable recall cost.
| 4-bit | 0.5 | Aggressive; only a few engines expose it directly (e.g. as part of product or binary quantization below), since 4-bit scalar quantization alone loses too much precision for most embedding models.
|===

pgvector stores a `halfvec` column exactly like a `vector` column, just at half the size:

[source,sql]
----
ALTER TABLE chunk_embeddings ADD COLUMN embedding_half halfvec(768);
UPDATE chunk_embeddings SET embedding_half = embedding::halfvec(768);

CREATE INDEX chunk_embeddings_hnsw_half
  ON chunk_embeddings
  USING hnsw (embedding_half halfvec_cosine_ops)
  WITH (m = 16, ef_construction = 64);
----

See https://github.com/pgvector/pgvector#half-precision-vectors[pgvector: Half-precision vectors]. FAISS
exposes scalar quantization as its own index family, `IndexScalarQuantizer`, with `QT_8bit`, `QT_4bit`, and
`QT_fp16` quantizer types:

[source,python]
----
import faiss

d = 768
index = faiss.IndexScalarQuantizer(d, faiss.ScalarQuantizer.QT_8bit, faiss.METRIC_INNER_PRODUCT)
index.train(training_vectors)   # learns per-dimension min/max
index.add(chunk_embeddings)
----

See https://github.com/facebookresearch/faiss/wiki/Scalar-quantizers[FAISS wiki: Scalar quantizers].

== Product quantization

Product quantization (PQ) compresses a vector far more aggressively than scalar quantization by learning a
small codebook per subspace instead of a single scale per dimension.

=== Step by step

. *Split into subspaces.* A `d`-dimensional vector is cut into `m` equal contiguous subspaces of `d / m`
  dimensions each. For a 768-dim embedding with `m = 16`, each subspace holds `768 / 16 = 48` dimensions.
. *Train a codebook per subspace.* For each subspace, k-means is run independently over the training
  vectors' sub-vectors in that subspace, producing `k` centroids (typically `k = 256`, so each centroid ID
  fits in one byte). This gives `m` codebooks, each with `k` centroids of `d / m` dimensions.
. *Encode.* Each vector is replaced by `m` codes: for every subspace, the ID of the nearest centroid in
  that subspace's codebook. With `k = 256`, each code is one byte, so the whole vector compresses to `m`
  bytes total, regardless of the original `d`.
. *Distance computation is asymmetric* (ADC, asymmetric distance computation): the *query* stays
  full-precision, but for each subspace the distance from the query's sub-vector to every one of the `k`
  centroids is precomputed once into a small lookup table. Scoring a database vector then sums `m`
  table lookups (one per subspace) instead of computing `d` multiplications directly, which is both cheaper
  and avoids quantizing the query itself (only the indexed vectors are quantized).

=== Memory arithmetic for 768 dimensions

[cols="1,1,1",options="header"]
|===
| Representation | Bytes per vector | Compression vs. `float32`

| `float32` (baseline) | 768 x 4 = 3072 | 1x
| PQ, `m = 16`, `k = 256` (1 byte/code) | 16 | 192x
| PQ, `m = 64`, `k = 256` | 64 | 48x
|===

The codebooks themselves (`m x k x (d / m)` floats, e.g. `16 x 256 x 48 x 4` bytes ~ 786 KB for the whole
collection) are shared across every vector and amortize to nothing at scale, which is why PQ's per-vector
cost is just `m` bytes.

=== FAISS `IndexPQ` and `IndexIVFPQ`

`IndexPQ` applies product quantization directly over a flat (exhaustive) scan; combining it with an IVF
coarse quantizer (xref:database/vector-rag/ann-indexes.adoc[] covers `nlist` / `nprobe`) adds a first
partitioning step so only a handful of inverted lists are scanned per query:

[source,python]
----
import faiss

d = 768
m = 16          # number of subspaces
nbits = 8       # bits per code -> k = 2**nbits = 256 centroids per subspace

# Flat PQ: exhaustive scan, PQ-compressed distances
index_pq = faiss.IndexPQ(d, m, nbits, faiss.METRIC_INNER_PRODUCT)
index_pq.train(training_vectors)
index_pq.add(chunk_embeddings)

# IVF + PQ: partition into nlist coarse cells, then PQ-encode within each
nlist = 64
quantizer = faiss.IndexFlatIP(d)
index_ivfpq = faiss.IndexIVFPQ(quantizer, d, nlist, m, nbits, faiss.METRIC_INNER_PRODUCT)
index_ivfpq.train(training_vectors)
index_ivfpq.add(chunk_embeddings)
index_ivfpq.nprobe = 8

# equivalently, built from a factory string:
index_ivfpq = faiss.index_factory(d, "IVF64,PQ16", faiss.METRIC_INNER_PRODUCT)
----

`index_factory("IVF64,PQ16")` reads as: an IVF coarse quantizer with 64 lists, followed by product
quantization into 16 subspaces (`nbits` defaults to 8). See
https://github.com/facebookresearch/faiss/wiki/The-index-factory[FAISS wiki: The index factory] and
https://github.com/facebookresearch/faiss/wiki/Faster-search[FAISS wiki: Faster search].

=== Refinement and rescoring

Because PQ distances are approximate, FAISS can wrap a PQ index with `IndexRefineFlat` (or its IVF
equivalent), which over-fetches a larger candidate set using the fast PQ index and then re-scores exactly
those candidates against their full-precision vectors kept in a flat side index:

[source,python]
----
base_index = faiss.index_factory(d, "IVF64,PQ16", faiss.METRIC_INNER_PRODUCT)
base_index.train(training_vectors)
base_index.add(chunk_embeddings)

refine_index = faiss.IndexRefineFlat(base_index)
refine_index.k_factor = 4   # fetch 4x k candidates from the PQ index before exact rescoring

distances, ids = refine_index.search(query_vectors, k=10)
----

See https://github.com/facebookresearch/faiss/wiki/Pre--and-post-processing[FAISS wiki: Pre- and
post-processing]. The same over-fetch-then-rescore shape reappears with binary quantization below and with
cross-encoder re-ranking on xref:database/vector-rag/hybrid-search-and-reranking.adoc[].

== Binary quantization plus rescoring

Binary quantization goes further still: each dimension collapses to a single bit (typically the sign of the
component), so a 768-dim vector fits in `768 / 8 = 96` bytes -- a 32x reduction over `float32` -- and
similarity becomes a Hamming distance computable with a CPU population-count instruction, which is far
cheaper than a floating-point dot product. The recall cost is larger than PQ's, so binary quantization is
almost always paired with a rescoring step against the original full-precision vectors.

pgvector exposes this as a `bit` expression index plus a two-step SQL query: quantize on the fly for the
index, then re-rank the shortlist by the exact vector operator:

[source,sql]
----
-- expression index on the binary-quantized embedding
CREATE INDEX chunk_embeddings_binary_hnsw
  ON chunk_embeddings
  USING hnsw ((binary_quantize(embedding)::bit(768)) bit_hamming_ops);

-- over-fetch on the cheap binary index, then re-rank exactly
SELECT id, content
FROM (
  SELECT c.id, c.content, c.embedding
  FROM chunk_embeddings c
  ORDER BY binary_quantize(c.embedding)::bit(768) <~> binary_quantize($1)::bit(768)
  LIMIT 200
) shortlist
ORDER BY embedding <=> $1
LIMIT 10;
----

See https://github.com/pgvector/pgvector#binary-quantization[pgvector: Binary quantization]. Qdrant's
binary quantization and Elasticsearch's Better Binary Quantization (BBQ) follow the same over-fetch-and-
rescore pattern, tuned into the engine's own query path rather than hand-written SQL:
https://qdrant.tech/documentation/guides/quantization/#binary-quantization[Qdrant: Binary quantization] and
https://www.elastic.co/search-labs/blog/elasticsearch-bbq-vector-search[Elasticsearch: Better Binary
Quantization (BBQ)] (see also xref:database/qdrant/vector-indexing-and-hnsw.adoc[] and
xref:database/lucene/knn-vector-search.adoc[]).

== Dimensionality reduction

Quantization shrinks each component; dimensionality reduction removes components outright before any
quantization happens at all.

=== PCA via `IndexPreTransform`

FAISS can prepend a trained PCA matrix to any index with `IndexPreTransform`, projecting each vector onto
its top principal components before it reaches the underlying index:

[source,python]
----
d_in, d_out = 768, 128
pca_matrix = faiss.PCAMatrix(d_in, d_out)

base_index = faiss.IndexFlatIP(d_out)
index = faiss.IndexPreTransform(pca_matrix, base_index)
index.train(training_vectors)   # fits the PCA matrix, then trains base_index
index.add(chunk_embeddings)
----

See https://github.com/facebookresearch/faiss/wiki/Pre--and-post-processing[FAISS wiki: Pre- and
post-processing]. PCA is learned from the training set's variance, so it should be retrained whenever the
embedding model or corpus distribution changes meaningfully.

=== Matryoshka truncation

Models trained with a Matryoshka representation objective (see
xref:database/vector-rag/embeddings.adoc[]) keep the most informative signal in the leading dimensions by
construction, so truncating the stored vector to a prefix -- no PCA training, no codebooks, just slicing --
already yields a usable, smaller embedding:

[source,python]
----
from sentence_transformers import SentenceTransformer

model = SentenceTransformer("mixedbread-ai/mxbai-embed-large-v1", truncate_dim=256)
embedding = model.encode("How do I speed up similarity search?", normalize_embeddings=True)
----

See https://sbert.net/examples/sentence_transformer/applications/matryoshka/README.html[sentence-transformers:
Matryoshka embeddings]. Matryoshka truncation and PQ/binary quantization compose: a truncated 256-dim vector
can still be product- or binary-quantized afterward for further savings.

=== Measuring the recall cost

None of these techniques are free, and the right amount of compression is whatever a measured recall@k
against an exact `IndexFlatIP` baseline can tolerate for a given workload (xref:database/vector-rag/ann-indexes.adoc[]
shows the same recall@k-vs-`efSearch` measurement for HNSW):

[source,python]
----
ground_truth = faiss.IndexFlatIP(d)
ground_truth.add(chunk_embeddings)
_, gt_ids = ground_truth.search(query_vectors, k=10)

_, candidate_ids = candidate_index.search(query_vectors, k=10)

recall_at_10 = sum(
    len(set(gt_row) & set(cand_row)) / 10
    for gt_row, cand_row in zip(gt_ids, candidate_ids)
) / len(query_vectors)
----

|===
| Technique | Bytes per vector (768-dim) | Compression vs. `float32`

| `float32` (baseline) | 3072 | 1x
| `float16` / `halfvec` | 1536 | 2x
| `int8` | 768 | 4x
| PQ, `m = 16` | 16 | 192x
| PQ, `m = 64` | 64 | 48x
| Binary (1 bit/dim) | 96 | 32x
| PCA to 128 dims (`float32`) | 512 | 6x
| Matryoshka truncation to 256 dims (`float32`) | 1024 | 3x
|===

== In LangChain and Spring AI

Quantization is usually configured at the vector-store or index level rather than in application code, but
both frameworks surface the knobs each store exposes.

=== LangChain

LangChain's `PGVector` store (see
xref:database/vector-rag/integrating-with-langchain.adoc#langchain-vector-stores[Integrating with
LangChain]) does not add its own quantization layer; it manages whichever column type
(`vector`/`halfvec`/`bit`) and index the underlying pgvector schema was created with, so choosing `halfvec`
or a binary-quantized expression index is a schema decision made outside the LangChain call, then used
transparently through the same `similarity_search` API.

=== Spring AI

Spring AI's `PgVectorStore` exposes the distance metric and index type as configuration
(`spring.ai.vectorstore.pgvector.distance-type`, `spring.ai.vectorstore.pgvector.index-type`), covered on
xref:database/vector-rag/integrating-with-spring-ai.adoc#spring-ai-vector-store-api[Integrating with Spring
AI]; picking `HNSW` there is the store's index-type knob, while switching the underlying column to
`halfvec` or adding a binary expression index (as in the SQL above) is done directly against the pgvector
schema, since `PgVectorStore` does not manage that choice itself.
