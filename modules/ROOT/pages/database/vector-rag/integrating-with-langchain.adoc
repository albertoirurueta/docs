[[langchain-embeddings]]
== Embeddings

LangChain's `Embeddings` interface abstracts over an embedding provider behind two methods: `embed_documents`
for a batch of texts and `embed_query` for a single query string, so retrieval code never depends on which
model produced the vectors.

[source,python]
----
from langchain_ollama import OllamaEmbeddings

embeddings = OllamaEmbeddings(model="nomic-embed-text")

doc_vectors = embeddings.embed_documents([
    "search_document: HNSW builds a multi-layer proximity graph over the vectors.",
    "search_document: pgvector adds a vector column type and distance operators to PostgreSQL.",
])
query_vector = embeddings.embed_query("search_query: what does ef_search control?")
----

See https://docs.langchain.com/oss/python/integrations/text_embedding/ollama[LangChain: Ollama embeddings]. A
hosted or self-hosted HuggingFace model plugs into the same interface through
`langchain-huggingface`'s `HuggingFaceEmbeddings` (local `sentence-transformers` models) or
`HuggingFaceEndpointEmbeddings` (a remote Inference Endpoint):

[source,python]
----
from langchain_huggingface import HuggingFaceEmbeddings

embeddings = HuggingFaceEmbeddings(model_name="sentence-transformers/all-MiniLM-L6-v2")
----

See https://docs.langchain.com/oss/python/integrations/text_embedding/huggingfacehub[LangChain: HuggingFace
embeddings]. `generating-embeddings-in-practice.adoc` walks through `OllamaEmbeddings` end to end, including
task prefixes and caching; see xref:database/vector-rag/generating-embeddings-in-practice.adoc[].

[[langchain-vector-stores]]
== Vector stores

Every LangChain vector store implements the same `VectorStore` base class, so swapping the underlying engine
is a one-line change to the constructor. The methods used throughout this section are:

[cols="1,3"]
|===
| Method | Purpose

| `add_documents(documents, ids=None)`
| Embeds and writes a batch of `Document` objects (page content plus a metadata dict).

| `similarity_search(query, k=5, filter=None)`
| Returns the `k` nearest `Document` objects to the query's embedding.

| `similarity_search_with_score(query, k=5, filter=None)`
| Same as above, but also returns each result's raw distance or similarity score.

| `max_marginal_relevance_search(query, k=5, fetch_k=20, lambda_mult=0.5)`
| Diversity-aware retrieval: over-fetches `fetch_k` candidates, then greedily selects `k` that balance
  relevance to the query against dissimilarity to what has already been picked (see
  xref:database/vector-rag/hybrid-search-and-reranking.adoc[Hybrid Search & Re-ranking]'s MMR section).

| `filter`
| A store-specific keyword argument (a dict, a SQL-like expression string, or a store's own filter object)
  restricting the search to matching metadata, as shown on
  xref:database/vector-rag/metadata-filtering.adoc[Metadata Filtering].

| `delete(ids=None, filter=None)`
| Removes documents by id or by a metadata filter.
|===

Against the *DocsAssistant* scenario, `langchain-postgres`'s `PGVector` store is the one used throughout this
section. It owns its own schema under the collection name `docsassistant` -- separate tables from the
hand-written `documents` / `chunks` / `chunk_embeddings` schema on
xref:database/vector-rag/postgresql-pgvector.adoc[PostgreSQL & pgvector], because each framework manages its
own storage layout rather than reusing another framework's tables:

[source,python]
----
from langchain_postgres import PGVector
from langchain_ollama import OllamaEmbeddings

vector_store = PGVector(
    embeddings=OllamaEmbeddings(model="nomic-embed-text"),
    collection_name="docsassistant",
    connection="postgresql+psycopg://docs:docs@localhost:5432/docsassistant",
    use_jsonb=True,
)

vector_store.add_documents(chunks, ids=[c.metadata["chunk_id"] for c in chunks])
hits = vector_store.similarity_search_with_score(
    "search_query: what does ef_search control?", k=5, filter={"component": {"$eq": "vector-rag"}},
)
----

See https://docs.langchain.com/oss/python/integrations/vectorstores/pgvector[LangChain: PGVector]. Three more
stores are used elsewhere in this section as lighter-weight or local alternatives:

* `SQLiteVec`, wrapping the sqlite-vec `vec0` table pattern from
  xref:database/vector-rag/sqlite-vector-search.adoc[Vector Search in SQLite]; see
  https://docs.langchain.com/oss/python/integrations/vectorstores/sqlitevec[LangChain: SQLiteVec].
* `FAISS`, a disposable, single-process store backed by the library covered on
  xref:database/vector-rag/faiss.adoc[FAISS]; see
  https://docs.langchain.com/oss/python/integrations/vectorstores/faiss[LangChain: FAISS vector store].
* `InMemoryVectorStore`, an ephemeral, dependency-free store useful for tests and small demos that keeps
  every vector in a Python dict and scores it with brute-force cosine similarity -- no server, no
  persistence:
+
[source,python]
----
from langchain_core.vectorstores import InMemoryVectorStore
from langchain_ollama import OllamaEmbeddings

vector_store = InMemoryVectorStore(OllamaEmbeddings(model="nomic-embed-text"))
vector_store.add_documents(chunks)
----
+
See https://docs.langchain.com/oss/python/integrations/vectorstores/in_memory[LangChain: InMemoryVectorStore].

For every other engine this site documents, LangChain ships an equivalent store: Qdrant
(`langchain-qdrant`'s `QdrantVectorStore`, see
xref:database/qdrant/rag-integration-patterns.adoc[Qdrant: RAG Integration Patterns]), Redis
(`langchain-redis`'s `RedisVectorStore`, see
xref:database/redis/vector-search.adoc[Redis: Vector Search]), Elasticsearch
(`langchain-elasticsearch`'s `ElasticsearchStore`, see
xref:database/elasticsearch/vector-and-semantic-search.adoc[Elasticsearch: Vector & Semantic Search]),
MongoDB (`langchain-mongodb`'s `MongoDBAtlasVectorSearch`, see
xref:database/mongodb/special-indexes-and-search.adoc[MongoDB: Special Indexes & Search]), and Neo4j
(`langchain-neo4j`'s `Neo4jVector`, see
xref:database/neo4j/vector-search-and-genai.adoc[Neo4j: Vector Search & GenAI]). See
https://docs.langchain.com/oss/python/integrations/vectorstores[LangChain: vector store integrations] for the
full list and each store's own configuration.

[[langchain-splitters]]
== Splitters

A document loader reads source files into LangChain `Document` objects (page content plus a metadata dict).
For the *DocsAssistant* sample corpus -- `docs/vector-rag/hnsw.adoc`, `docs/vector-rag/pgvector.adoc` and
`docs/spring-ai/rag.adoc` -- `langchain-community`'s `DirectoryLoader` globs the AsciiDoc files and reads each
one with `TextLoader`, which records the file path under the `source` metadata key; the loop then maps it to the
section's `source_path` and `component` keys:

[source,python]
----
from langchain_community.document_loaders import DirectoryLoader, TextLoader

loader = DirectoryLoader(
    "docs", glob="**/*.adoc", loader_cls=TextLoader, loader_kwargs={"encoding": "utf-8"},
)
documents = loader.load()
for doc in documents:
    doc.metadata["source_path"] = doc.metadata["source"]
    doc.metadata["component"] = "spring-ai" if "/spring-ai/" in doc.metadata["source"] else "vector-rag"
----

See
https://reference.langchain.com/python/langchain-community/document_loaders/directory/DirectoryLoader[LangChain
reference: `DirectoryLoader`],
https://reference.langchain.com/python/langchain-community/document_loaders/text/TextLoader[LangChain reference:
`TextLoader`] and https://docs.langchain.com/oss/python/integrations/document_loaders/index[LangChain: Document
loaders] for the PDF, HTML and other format-specific loaders shown on
xref:database/vector-rag/document-ingestion-and-chunking.adoc[Document Ingestion & Chunking].

`langchain-text-splitters` then turns the loaded documents into the chunks a vector store indexes. The package used
throughout xref:database/vector-rag/document-ingestion-and-chunking.adoc[Document Ingestion & Chunking] covers
`RecursiveCharacterTextSplitter` (recursive character/token windows with overlap) and
`MarkdownHeaderTextSplitter` (structure-aware splitting on heading levels), both shown there against the
*DocsAssistant* sample corpus:

[source,python]
----
from langchain_text_splitters import RecursiveCharacterTextSplitter

splitter = RecursiveCharacterTextSplitter(chunk_size=1000, chunk_overlap=200)
chunks = splitter.split_documents(documents)
----

See
https://docs.langchain.com/oss/python/integrations/splitters/recursive_text_splitter[LangChain: Recursive
character text splitter] and
https://docs.langchain.com/oss/python/integrations/splitters/markdown_header_metadata_splitter[LangChain:
Markdown header text splitter]. Every chunking strategy this section covers -- fixed windows, sentence-aware,
recursive, structure-aware, semantic, parent-child, late chunking and contextual retrieval -- is explained in
depth, with the trade-offs between them, on
xref:database/vector-rag/document-ingestion-and-chunking.adoc#_chunking_strategies[Document Ingestion &
Chunking: Chunking strategies].

[[langchain-retrievers]]
== Retrievers

Every `VectorStore` exposes a `Runnable` retriever through `as_retriever`, so it composes with the rest of a
LangChain pipeline (prompts, chains, agent tools) without the caller touching the store's own API:

[source,python]
----
retriever = vector_store.as_retriever(
    search_type="mmr",
    search_kwargs={"k": 5, "fetch_k": 20, "lambda_mult": 0.5, "filter": {"component": {"$eq": "vector-rag"}}},
)
docs = retriever.invoke("what does ef_search control?")
----

`search_type` selects `"similarity"` (default), `"similarity_score_threshold"` (drop results below a minimum
score), or `"mmr"` (the diversity-aware search from <<langchain-vector-stores>>); `search_kwargs` forwards the
matching keyword arguments -- `k`, `score_threshold`, `filter`, `fetch_k` and `lambda_mult` -- to the
underlying store method. See https://docs.langchain.com/oss/python/langchain/retrieval[LangChain: Retrieval].
Beyond this basic retriever, `langchain_classic.retrievers` packages the retrieval techniques covered on
xref:database/vector-rag/hybrid-search-and-reranking.adoc[Hybrid Search & Re-ranking] (`EnsembleRetriever`,
`ContextualCompressionRetriever`) and
xref:database/vector-rag/retrieval-strategies.adoc[Retrieval Strategies] (`MultiQueryRetriever`,
`ParentDocumentRetriever`, `SelfQueryRetriever`); see
https://reference.langchain.com/python/langchain_classic/retrievers/[LangChain:
`langchain_classic.retrievers`].

[[langchain-rag-chain]]
== RAG chain

xref:database/vector-rag/rag-fundamentals.adoc[RAG Fundamentals] shows the full pipeline this anchor refers
to: a retriever built with `as_retriever`, a `ChatPromptTemplate` that formats the retrieved documents and the
question, and a chat model, composed with LangChain Expression Language's `|` operator into one `Runnable`:

[source,python]
----
from langchain_ollama import ChatOllama
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.runnables import RunnablePassthrough
from langchain_core.output_parsers import StrOutputParser

prompt = ChatPromptTemplate.from_template(
    "Answer using only the context below.\n\nContext:\n{context}\n\nQuestion: {question}"
)
model = ChatOllama(model="llama3.1:8b", temperature=0.1, num_ctx=8192)


def format_docs(docs):
    return "\n\n".join(f"[{d.metadata['title']} § {d.metadata['section']}]\n{d.page_content}" for d in docs)


rag_chain = (
    {"context": retriever | format_docs, "question": RunnablePassthrough()}
    | prompt
    | model
    | StrOutputParser()
)
answer = rag_chain.invoke("what does ef_search control?")
----

See https://docs.langchain.com/oss/python/langchain/retrieval[LangChain: Retrieval] for this composition
pattern, and xref:database/vector-rag/prompt-augmentation-and-generation.adoc[Prompt Augmentation &
Generation] for the context-formatting and prompt-template choices behind `format_docs` and `prompt`.

[[langchain-agentic-rag]]
== Agentic RAG

xref:database/vector-rag/agentic-rag.adoc[Agentic RAG] covers the shift from a fixed chain to an LLM that
*decides* whether and what to retrieve. LangChain 1.x's `create_agent` builds a tool-calling agent from a chat
model and a list of tools -- including a retriever exposed as a tool -- in one call:

[source,python]
----
from langchain.agents import create_agent
from langchain_ollama import ChatOllama
from langchain_core.tools import tool


@tool
def search_docs(query: str, component: str | None = None, k: int = 5) -> list[dict]:
    """Search the DocsAssistant documentation for passages relevant to the query."""
    filter_ = {"component": {"$eq": component}} if component else None
    hits = vector_store.similarity_search_with_score(query, k=k, filter=filter_)
    return [{"source_path": d.metadata["source_path"], "section": d.metadata["section"],
              "content": d.page_content, "score": score} for d, score in hits]


agent = create_agent(model=ChatOllama(model="llama3.1:8b", temperature=0.1), tools=[search_docs])
result = agent.invoke({"messages": [{"role": "user", "content": "What does ef_search control?"}]})
----

See https://docs.langchain.com/oss/python/langchain/agents[LangChain: Agents] for `create_agent`'s full
configuration (system prompts, structured output, middleware). For multi-step agentic RAG -- retrieve, grade
the retrieved documents, then rewrite the query or generate the answer -- LangChain 1.x agents run on a
LangGraph graph underneath; building that graph directly gives explicit control over the retrieve/grade/
rewrite/generate nodes that `create_agent`'s default loop does not expose. See
https://docs.langchain.com/oss/python/langgraph/agentic-rag[LangChain: Agentic RAG (LangGraph)].

Memory for such an agent comes from LangGraph: a *checkpointer* persists each thread's conversation state
(short-term memory, keyed by `thread_id`), and a *store* holds long-term memories that are searched by
embedding similarity across threads. `langgraph-checkpoint-postgres` provides both against the same
*DocsAssistant* PostgreSQL database, with the store's semantic index using the same `nomic-embed-text`
embeddings:

[source,python]
----
from langchain.agents import create_agent
from langchain_ollama import ChatOllama, OllamaEmbeddings
from langgraph.checkpoint.postgres import PostgresSaver
from langgraph.store.postgres import PostgresStore

DB_URI = "postgresql://docs:docs@localhost:5432/docsassistant"
embeddings = OllamaEmbeddings(model="nomic-embed-text")

with (
    PostgresSaver.from_conn_string(DB_URI) as checkpointer,
    PostgresStore.from_conn_string(
        DB_URI, index={"dims": 768, "embed": embeddings, "fields": ["text"]},
    ) as store,
):
    checkpointer.setup()  # creates the checkpoint tables on first run
    store.setup()         # creates the store tables and its pgvector index

    store.put(("docsassistant", "user-42"), "pref-1", {"text": "Prefers answers with SQL examples."})
    memories = store.search(("docsassistant", "user-42"), query="how should answers be formatted?", limit=3)

    agent = create_agent(
        model=ChatOllama(model="llama3.1:8b", temperature=0.1),
        tools=[search_docs],
        checkpointer=checkpointer,
        store=store,
    )
    result = agent.invoke(
        {"messages": [{"role": "user", "content": "And which operator computes cosine distance?"}]},
        {"configurable": {"thread_id": "conversation-1"}},
    )
----

Install with `pip install langgraph-checkpoint-postgres "psycopg[binary]"`. See
https://docs.langchain.com/oss/python/langchain/short-term-memory[LangChain: Short-term memory] for the
Postgres checkpointer, https://docs.langchain.com/oss/python/langchain/long-term-memory[LangChain: Long-term
memory] for the store and its semantic index, and
xref:database/vector-rag/agent-memory-and-semantic-cache.adoc#_langgraph_checkpointer_and_store_for_long_term_memory[Agent
Memory & Semantic Cache: LangGraph checkpointer and store] for how this maps onto the section's hand-written
`message_embeddings` memory.

[[langchain4j]]
== LangChain4j

LangChain4j is the JVM counterpart used throughout this section wherever a page shows a Java client alongside
its Python and Spring AI ones (for example
xref:database/vector-rag/generating-embeddings-in-practice.adoc[Generating Embeddings in Practice]'s
`OllamaEmbeddingModel` and xref:database/vector-rag/document-ingestion-and-chunking.adoc[Document Ingestion &
Chunking]'s `EmbeddingStoreIngestor`). Its central interfaces mirror LangChain's Python ones under different
names:

[cols="1,2"]
|===
| Interface | Role

| `EmbeddingStore<TextSegment>`
| The vector-store abstraction, equivalent to LangChain's `VectorStore` -- `add`, `search`, `remove`.

| `EmbeddingStoreIngestor`
| Wires a document loader, a splitter, an `EmbeddingModel` and an `EmbeddingStore` into one ingestion call,
  equivalent to a LangChain load → split → embed → `add_documents` sequence.

| `EmbeddingStoreContentRetriever`
| Wraps an `EmbeddingStore` as a `ContentRetriever`, LangChain4j's retriever abstraction, equivalent to
  `as_retriever`.

| `AiServices` with a `RetrievalAugmentor`
| Declares an interface-backed chat service and augments every call with retrieved content before it reaches
  the model, equivalent to composing a retriever into a LangChain RAG chain.
|===

`PgVectorEmbeddingStore` is the `EmbeddingStore` implementation used against the *DocsAssistant* database; like
the Python `PGVector` store, it owns its own table (`docs_lc4j_embeddings`), separate from the hand-written
schema and from Spring AI's `docs_vector_store`:

[source,java]
----
import dev.langchain4j.data.segment.TextSegment;
import dev.langchain4j.model.embedding.EmbeddingModel;
import dev.langchain4j.model.ollama.OllamaChatModel;
import dev.langchain4j.model.ollama.OllamaEmbeddingModel;
import dev.langchain4j.store.embedding.EmbeddingStore;
import dev.langchain4j.store.embedding.pgvector.PgVectorEmbeddingStore;
import dev.langchain4j.store.embedding.EmbeddingStoreIngestor;
import dev.langchain4j.rag.content.retriever.EmbeddingStoreContentRetriever;
import dev.langchain4j.rag.DefaultRetrievalAugmentor;
import dev.langchain4j.service.AiServices;

EmbeddingModel embeddingModel = OllamaEmbeddingModel.builder()
        .baseUrl("http://localhost:11434")
        .modelName("nomic-embed-text")
        .build();

EmbeddingStore<TextSegment> embeddingStore = PgVectorEmbeddingStore.builder()
        .host("localhost").port(5432).database("docsassistant")
        .user("docs").password("docs")
        .table("docs_lc4j_embeddings")
        .dimension(768)
        .useIndex(true)        // creates an IVFFlat index (vector_cosine_ops) ...
        .indexListSize(100)    // ... whose lists count is required whenever useIndex is true
        .build();

EmbeddingStoreIngestor.builder()
        .embeddingModel(embeddingModel)
        .embeddingStore(embeddingStore)
        .build()
        .ingest(documents);

EmbeddingStoreContentRetriever contentRetriever = EmbeddingStoreContentRetriever.builder()
        .embeddingStore(embeddingStore)
        .embeddingModel(embeddingModel)
        .maxResults(5)
        .build();

interface DocsAssistant {
    String answer(String question);
}

DocsAssistant assistant = AiServices.builder(DocsAssistant.class)
        .chatModel(OllamaChatModel.builder().baseUrl("http://localhost:11434").modelName("llama3.1:8b").build())
        .retrievalAugmentor(DefaultRetrievalAugmentor.builder().contentRetriever(contentRetriever).build())
        .build();
----

`useIndex(true)` makes the store create an IVFFlat index on its table, and `indexListSize` (the IVFFlat
`lists` parameter) must then be set to a value greater than zero -- otherwise table initialization throws an
`IllegalArgumentException`. See
https://docs.langchain4j.dev/integrations/embedding-stores/pgvector[LangChain4j: PGVector embedding store].

The Maven coordinates for the pieces above (the pgvector module is published on LangChain4j's `-beta`
track, so its version carries the `-beta30` suffix):

[source,xml]
----
<dependency>
    <groupId>dev.langchain4j</groupId>
    <artifactId>langchain4j</artifactId>
    <version>1.20.1</version>
</dependency>
<dependency>
    <groupId>dev.langchain4j</groupId>
    <artifactId>langchain4j-ollama</artifactId>
    <version>1.20.1</version>
</dependency>
<dependency>
    <groupId>dev.langchain4j</groupId>
    <artifactId>langchain4j-pgvector</artifactId>
    <version>1.20.1-beta30</version>
</dependency>
----

LangChain4j groups RAG implementations into three levels of the same taxonomy used on
xref:database/vector-rag/rag-fundamentals.adoc#_a_naive_advanced_modular_and_agentic_rag_taxonomy[RAG Fundamentals]: *Easy RAG*
(`EmbeddingStoreIngestor` with default settings, for a first working pipeline), *Naive RAG* (an explicit
`EmbeddingStoreContentRetriever` composed by hand, as above), and *Advanced/Modular RAG* (a
`RetrievalAugmentor` with a configurable `QueryTransformer`, `QueryRouter` and `ContentAggregator`, covered in
depth on xref:database/vector-rag/retrieval-strategies.adoc#_langchain4j[Retrieval Strategies: LangChain4j]).
See https://docs.langchain4j.dev/tutorials/rag/[LangChain4j: Retrieval-Augmented Generation] and
https://docs.langchain4j.dev/tutorials/embedding-stores/[LangChain4j: embedding (vector) stores].

== Spring AI equivalents

Every concept above has a Spring AI counterpart under its own fixed anchor on
xref:database/vector-rag/integrating-with-spring-ai.adoc[Integrating with Spring AI]: embeddings
(`EmbeddingModel`, `#spring-ai-embeddings`), vector stores (`VectorStore` and `PgVectorStore`,
`#spring-ai-vector-store-api`), metadata filtering (`#spring-ai-filter-expressions`), ingestion
(`#spring-ai-etl`), the RAG chain (`QuestionAnswerAdvisor`, `#spring-ai-rag-advisors`), modular RAG
(`#spring-ai-modular-rag`), and agent memory (`ChatMemory`, `#spring-ai-chat-memory`) alongside tool-calling
(`@Tool`, `#spring-ai-tools`). Where LangChain composes a `Runnable` pipeline or wraps a service in
`AiServices`, Spring AI composes an advisor chain around a `ChatClient`; the two frameworks solve the same
retrieval and augmentation problems with different composition styles, and every concept page in this section
shows both side by side.
