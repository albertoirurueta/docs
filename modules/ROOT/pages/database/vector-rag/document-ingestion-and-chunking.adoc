== What HNSW is

Hierarchical Navigable Small World (HNSW) is a graph-based approximate nearest-neighbor index. Vectors
become nodes connected across several layers, with sparser, longer-range links at the top and denser,
short-range links at the bottom. A search starts at an entry point in the top layer and greedily walks
toward the query, descending a layer each time no closer neighbor remains, until it reaches layer zero.

== Tuning parameters

`M` bounds how many edges each node keeps per layer, trading memory for connectivity. `ef_construction`
controls the candidate list size while the graph is built, and a larger value produces a better-connected
graph at the cost of slower inserts. `ef_search` is the same idea applied at query time: a larger candidate
list improves recall at the cost of latency, and unlike `M` it can be changed per query without rebuilding
the index.

== When to prefer it

HNSW suits workloads that insert continuously and query for low latency, since it needs no training step
and tolerates incremental updates far better than a clustering-based index.

== Adding vector search to PostgreSQL

pgvector is a PostgreSQL extension, not a separate database. `CREATE EXTENSION vector` adds a `vector`
column type and a handful of distance operators, so embeddings live as ordinary rows next to the rest of
an application's schema and can be joined, filtered and transacted like any other column.

== Operators and indexes

`<->` computes Euclidean distance, `<#>` negative inner product, and `<=>` cosine distance; a query orders
by whichever operator matches the embedding model's intended metric. An HNSW or IVFFlat index on the vector
column turns that `ORDER BY ... LIMIT` into an approximate search instead of a full scan, at the usual
recall-versus-latency trade-off every ANN index makes.

== Picking a distance operator

Most sentence embedding models, including the ones this site's examples use, are trained and evaluated
with cosine similarity, so `<=>` is the default choice unless a specific model's documentation says
otherwise.

== The QuestionAnswerAdvisor

Spring AI's `QuestionAnswerAdvisor` wraps a `ChatClient` call: before the prompt reaches the model, it runs
a similarity search against a configured `VectorStore`, formats the results as context, and appends them to
the user's question. The application code calls `chatClient.prompt()` exactly as it would without
retrieval; the advisor does the rest.

== Wiring a VectorStore

Any `VectorStore` implementation -- `PgVectorStore`, a Redis or Elasticsearch store, or an in-memory one for
tests -- can back the advisor, since they all share the same `add` / `similaritySearch` interface. Swapping
the backing store is a configuration change, not a code change, as long as the embedding model stays the
same one the store was populated with.

== Filtering retrieved context

`SearchRequest.builder().filterExpression(...)` narrows retrieval to a subset of stored documents, for
example a single component of a larger corpus, before the advisor ever builds its prompt.

== Loading documents

A loader's job is to turn a source file into plain text (and, ideally, some structural hints) before
chunking ever runs. The three formats an ingestion pipeline meets most often need different handling:

* *Markdown and AsciiDoc* are the easiest case: they are already plain text with explicit structure
  (`#`/`##` headings, `=`/`==` section markers), so a loader can keep both the text and the heading
  hierarchy with almost no work. The corpus above is AsciiDoc for exactly this reason.
* *HTML* needs its markup stripped without losing the content it wraps -- navigation, footers and script
  tags should not become chunk text, but heading tags (`<h1>`-`<h3>`) are worth preserving as structural
  hints, the same role AsciiDoc's `==` plays.
* *PDF* is the hardest case, because a PDF encodes visual layout, not document structure: there is no
  reliable "this is a heading" or "this is a new paragraph" signal in the file format itself.

=== PDF pitfalls

Two PDF layouts routinely break naive text extraction:

* *Multi-column pages* -- a plain top-to-bottom, left-to-right text extractor reads across columns instead
  of down each one, interleaving unrelated sentences from the left and right column into nonsense chunks.
  Column-aware extraction has to first detect column boundaries from character coordinates before ordering
  text.
* *Equations and figures* -- formulas rendered as glyphs or images have no reliable plain-text
  representation, and captions can end up detached from the figure or table they describe.

Two specialized tools exist because general-purpose PDF text extraction gets both of these wrong on
structured documents:
https://grobid.readthedocs.io/[Grobid] parses scientific PDFs into structured XML (sections, references,
figures, multi-column layout) using machine-learned layout models rather than raw coordinate heuristics, and
https://github.com/facebookresearch/nougat[Nougat] is an OCR model trained specifically to transcribe
academic PDFs -- including LaTeX-style equations -- into markup instead of plain, equation-mangled text.
Neither is needed for the *DocsAssistant* corpus, which is plain AsciiDoc, but both are the standard answer
once a corpus includes PDF papers or reports with equations or multi-column layout.

=== Cleaning and quality filtering

Whatever the source format, a loader's raw output usually needs a cleaning pass before chunking: collapsing
repeated whitespace, dropping boilerplate (headers, footers, page numbers repeated on every page),
de-hyphenating words split across a line break, and normalizing Unicode. A quality filter then discards
what cleaning cannot fix -- documents that are mostly navigation links, near-duplicate pages, or extracted
text so short or garbled (a common symptom of a scanned, non-OCR'd PDF) that no chunk built from it would
be useful. Filtering before chunking is cheaper than filtering after: a bad document produces many bad
chunks, and every wasted chunk still costs an embedding call.

== Chunking strategies

Chunking splits a loaded document into the units that actually get embedded, stored and retrieved. Every
strategy below is shown against the corpus's `hnsw.adoc` text; xref:#chunk-size-guidance[chunk-size
guidance] follows the strategies themselves.

=== Fixed word or token windows with overlap

The simplest strategy: cut the text into windows of a fixed size, sliding forward by less than the window
so consecutive chunks overlap. Overlap keeps a sentence that falls near a boundary intact in at least one
chunk, at the cost of storing (and later embedding) some words twice -- xref:#chunking-overlap-figure[the
figure below] shows the same window/overlap shape as code.

[source,python]
----
def fixed_window_chunks(words: list[str], window: int = 200, overlap: int = 50) -> list[str]:
    step = window - overlap
    chunks = []
    for start in range(0, len(words), step):
        window_words = words[start:start + window]
        if not window_words:
            break
        chunks.append(" ".join(window_words))
        if start + window >= len(words):
            break
    return chunks
----

=== Sentence-aware chunking

Cutting mid-sentence is the fixed-window strategy's main weakness. A sentence-aware splitter groups whole
sentences into a chunk instead, stopping once the next sentence would push the chunk past a target size:

[source,python]
----
import re

_SENTENCE_BOUNDARY = re.compile(r"(?<=[.!?])\s+")

def sentence_aware_chunks(text: str, target_words: int = 200) -> list[str]:
    sentences = _SENTENCE_BOUNDARY.split(text.strip())
    chunks, current, current_len = [], [], 0
    for sentence in sentences:
        sentence_len = len(sentence.split())
        if current and current_len + sentence_len > target_words:
            chunks.append(" ".join(current))
            current, current_len = [], 0
        current.append(sentence)
        current_len += sentence_len
    if current:
        chunks.append(" ".join(current))
    return chunks
----

A production pipeline typically reaches for a proper sentence tokenizer (NLTK's `sent_tokenize`, or the
sentence boundaries a library like spaCy detects) rather than the regular expression above, since a bare
regular expression on `.`/`!`/`?` mishandles abbreviations and decimal numbers.

=== Recursive character splitting

LangChain's `RecursiveCharacterTextSplitter` generalizes sentence-aware splitting to arbitrary text: it
tries a list of separators from "most structural" to "least structural" (paragraph break, line break,
sentence-ending punctuation, then a bare space), recursively splitting a too-large piece with the next
separator down the list until every chunk fits the target size:

[source,python]
----
from langchain_text_splitters import RecursiveCharacterTextSplitter

splitter = RecursiveCharacterTextSplitter(
    chunk_size=1000,
    chunk_overlap=200,
    separators=["\n\n", "\n", ". ", " ", ""],
)
chunks = splitter.split_text(hnsw_adoc_text)
----

See https://docs.langchain.com/oss/python/integrations/splitters/recursive_text_splitter[LangChain:
Recursive character text splitter].

=== Structure-aware chunking

When a document already carries explicit structure -- Markdown headings or AsciiDoc `==` section markers,
exactly like the sample corpus -- splitting along that structure keeps each chunk topically coherent
without any length heuristic at all. LangChain's `MarkdownHeaderTextSplitter` splits on heading levels and
attaches the heading path as metadata on each resulting chunk:

[source,python]
----
from langchain_text_splitters import MarkdownHeaderTextSplitter

splitter = MarkdownHeaderTextSplitter(
    headers_to_split_on=[("#", "h1"), ("##", "h2")],
)
docs = splitter.split_text(markdown_text)
# each doc.metadata now carries {"h1": "...", "h2": "..."}
----

AsciiDoc has no ready-made equivalent in `langchain-text-splitters`, but its section markers are just as
regular, so a small custom splitter on `== ` (mirroring the corpus's own `== ` sections above) does the
same job:

[source,python]
----
import re

_SECTION = re.compile(r"^== (.+)$", re.MULTILINE)

def split_asciidoc_sections(text: str) -> list[tuple[str, str]]:
    matches = list(_SECTION.finditer(text))
    sections = []
    for i, match in enumerate(matches):
        end = matches[i + 1].start() if i + 1 < len(matches) else len(text)
        sections.append((match.group(1), text[match.start():end].strip()))
    return sections
----

Applied to `hnsw.adoc`, this yields exactly the three `(section_path, content)` pairs -- "What HNSW is",
"Tuning parameters", "When to prefer it" -- that `chunks.section_path` stores for that document. See
https://docs.langchain.com/oss/python/integrations/splitters/markdown_header_metadata_splitter[LangChain:
Markdown header text splitter].

=== Semantic chunking

Instead of splitting on a fixed size or on markup, a semantic splitter embeds successive sentences (or
small groups of them) and cuts wherever the similarity between neighboring sentences drops sharply --
the same signal a human editor uses to notice a topic change:

[source,python]
----
import numpy as np

def semantic_boundaries(sentence_embeddings: list[list[float]], drop_threshold: float = 0.25) -> list[int]:
    boundaries = []
    for i in range(1, len(sentence_embeddings)):
        a, b = np.array(sentence_embeddings[i - 1]), np.array(sentence_embeddings[i])
        cosine = a.dot(b) / (np.linalg.norm(a) * np.linalg.norm(b))
        if cosine < 1 - drop_threshold:
            boundaries.append(i)
    return boundaries
----

Semantic chunking produces chunks that track meaning better than any fixed rule, at the cost of an
embedding call per sentence during ingestion itself, before the chunk-level embeddings this page's schema
stores are even computed.

=== Parent-child (small-to-big) chunking

Small chunks retrieve precisely -- their embedding is not diluted by unrelated surrounding text -- but a
small chunk alone can be too little context for the model to answer from. Parent-child chunking keeps both
sizes: a small *child* chunk is embedded and searched, but the *parent* chunk (a larger surrounding span,
or the whole section) is what actually gets sent to the model once its child chunk is retrieved:

[source,python]
----
def parent_child_chunks(section_text: str, parent_id: int) -> list[dict]:
    children = fixed_window_chunks(section_text.split(), window=100, overlap=20)
    return [
        {"content": child, "parent_id": parent_id, "parent_content": section_text}
        for child in children
    ]
----

`chunks.section_path` already gives *DocsAssistant* a natural parent unit (the section a chunk came from);
xref:database/vector-rag/retrieval-strategies.adoc[] covers expanding a hit back out to its parent at query
time in depth.

=== Late chunking

Ordinary chunking embeds each chunk in isolation, so a pronoun or an implicit reference near a chunk
boundary ("it", "the index above") loses the context that would resolve it. *Late chunking* reverses the
order: the whole document (or as much of it as the embedding model's context window allows) is run through
the model's transformer layers first, producing token-level, context-aware representations, and only then
is the token sequence split into chunks -- each chunk's embedding is a pooling of its tokens' already
context-aware representations, so it still carries information from the rest of the document even though
the chunk boundaries are the same ones a normal splitter would choose:

[source,python]
----
# illustrative -- requires an embedding model exposing token-level output
# (e.g. a long-context sentence-transformers model), not every model supports this
def late_chunk(token_embeddings: list[list[float]], chunk_token_spans: list[tuple[int, int]]) -> list[list[float]]:
    import numpy as np
    return [
        np.mean(token_embeddings[start:end], axis=0).tolist()
        for start, end in chunk_token_spans
    ]
----

See https://arxiv.org/abs/2409.04701[Late Chunking: Contextual Chunk Embeddings Using Long-Context Embedding
Models] for the technique in full, and Jina AI's
https://jina.ai/news/late-chunking-in-long-context-embedding-models/[accompanying explanation] for a more
approachable walkthrough.

=== Contextual retrieval

A cheaper way to give a chunk back its missing context, without needing a long-context embedding model at
all, is to have an LLM generate a short prefix describing where the chunk sits in the document, then embed
the prefix together with the chunk:

[source,python]
----
CONTEXT_PROMPT = """Document: {document_title}
Chunk: {chunk_text}

Write a one-sentence context statement situating this chunk within the document,
to be prepended to the chunk before it is embedded. Answer with the sentence only."""

def add_context_prefix(chat, document_title: str, chunk_text: str) -> str:
    context = chat.invoke(CONTEXT_PROMPT.format(document_title=document_title, chunk_text=chunk_text))
    return f"{context.content.strip()}\n\n{chunk_text}"
----

For example, a chunk from "Tuning parameters" in `hnsw.adoc` might be prefixed with "This chunk explains the
`M`, `ef_construction` and `ef_search` parameters of the HNSW index described earlier in this document." --
now the chunk is retrievable even by a query that never mentions HNSW by name. See Anthropic's
https://www.anthropic.com/news/contextual-retrieval[Introducing Contextual Retrieval] for the technique and
its accompanying evaluation.

=== Chunk-size guidance and tuning

Two rules of thumb cover most of this page's strategies:

* *Word-based splitting* (fixed windows, sentence-aware): around 200 words per chunk with a 50-word overlap
  -- roughly a quarter of the window -- is a reasonable starting point for prose documentation like the
  sample corpus.
* *Token-based splitting* (recursive character, structure-aware, most framework splitters): 512-1,024
  tokens per chunk with about 20% overlap, chosen to comfortably fit several chunks inside a retrieval
  budget while still leaving room for the prompt and the model's answer.

Both are starting points, not fixed constants, and should be tuned against the actual corpus and retrieval
task: shorter chunks (favoring precision) suit corpora with many short, distinct facts, such as an API
reference, while longer chunks (favoring recall of surrounding context) suit narrative or tutorial content
where an answer typically spans several sentences. The only reliable way to tune chunk size is to measure
it: run the same golden questions against a few chunk-size/overlap combinations and compare retrieval
quality, rather than picking a size by intuition alone.

== Per-chunk metadata

Every chunk stored for *DocsAssistant* carries the same metadata keys, regardless of which chunking
strategy produced it: `source_path`, `title`, `section` (the AsciiDoc `section_path`), `component`, and
`chunk_index`, plus two ingestion-specific fields not part of the shared key list -- `content_hash` (a hash
of the chunk's own text, used below to detect unchanged content) and `model` (the embedding model name and
version, already required on `chunk_embeddings.model` by
xref:database/vector-rag/generating-embeddings-in-practice.adoc#_the_golden_rule_same_model_same_version_for_index_and_query[the
golden rule]). Framework
`VectorStore` metadata maps carry the same keys as free-form document metadata rather than dedicated
columns; xref:database/vector-rag/metadata-filtering.adoc[] covers filtering on them in depth.

=== Idempotent, incremental ingestion

Re-running ingestion over an unchanged corpus should not re-embed or re-write anything, and re-running it
after editing one file should touch only that file's chunks. Three pieces make this idempotent:

* *Content hashing* -- `documents.content_hash` and `chunks.content_hash` each store a hash (SHA-256 is
  enough) of the source text they were derived from. Before re-chunking or re-embedding anything, a run
  compares the freshly computed hash against the stored one and skips work whose hash has not changed.
* *UPSERT* -- inserting or updating a document/chunk uses `INSERT ... ON CONFLICT ... DO UPDATE` on the
  natural key (`source_path` for documents, `(document_id, chunk_index)` for chunks), so re-running
  ingestion on an existing file updates its rows in place instead of duplicating them.
* *Deleting orphans in one transaction* -- if a document now produces fewer chunks than it did before (a
  section was deleted), the old, now-unmatched chunk rows have to be removed, or stale content stays
  searchable forever. Deleting `chunk_index >= new_chunk_count` for that document happens in the *same*
  transaction as the UPSERTs, so a failure partway through never leaves the corpus in a half-updated state.

A small `ingest_queue` table -- the same one
xref:database/vector-rag/postgresql-pgvector.adoc#_a_processing_queue_table[introduced on the pgvector
page] -- tracks which source files still need (re-)processing, decoupling "a file changed" from "a worker
picked it up and finished re-ingesting it".

=== ingest.py

The full ingestion script below chunks each corpus file with the structure-aware AsciiDoc splitter above,
hashes and UPSERTs `documents` and `chunks`, deletes orphaned chunks, embeds only chunks whose content
actually changed, and marks the queue entry done -- all against the exact schema from
xref:database/vector-rag/postgresql-pgvector.adoc#_the_docsassistant_schema[the pgvector page].

[source,python]
----
"""docsassistant/ingest.py -- idempotent, incremental ingestion into the DocsAssistant schema."""
import hashlib
import pathlib
import re

import ollama
import psycopg
from pgvector.psycopg import register_vector

DB_DSN = "host=localhost dbname=docsassistant user=docs password=docs"
EMBEDDING_MODEL = "nomic-embed-text"
_SECTION = re.compile(r"^== (.+)$", re.MULTILINE)


def sha256(text: str) -> str:
    return hashlib.sha256(text.encode("utf-8")).hexdigest()


def split_asciidoc_sections(text: str) -> list[tuple[str, str]]:
    matches = list(_SECTION.finditer(text))
    sections = []
    for i, match in enumerate(matches):
        end = matches[i + 1].start() if i + 1 < len(matches) else len(text)
        sections.append((match.group(1), text[match.start():end].strip()))
    return sections


def embed(text: str) -> list[float]:
    response = ollama.embed(model=EMBEDDING_MODEL, input=f"search_document: {text}")
    return response["embeddings"][0]


def ingest_file(conn: psycopg.Connection, source_path: pathlib.Path, component: str) -> None:
    text = source_path.read_text(encoding="utf-8")
    title = text.splitlines()[0].lstrip("= ").strip()
    doc_hash = sha256(text)
    sections = split_asciidoc_sections(text)

    with conn.transaction():
        document = conn.execute(
            """
            INSERT INTO documents (source_path, title, component, content_hash)
            VALUES (%s, %s, %s, %s)
            ON CONFLICT (source_path) DO UPDATE
                SET title = EXCLUDED.title,
                    component = EXCLUDED.component,
                    content_hash = EXCLUDED.content_hash,
                    updated_at = now()
            RETURNING id, content_hash <> %s AS changed
            """,
            (str(source_path), title, component, doc_hash, doc_hash),
        ).fetchone()
        document_id, doc_changed = document

        for chunk_index, (section_path, content) in enumerate(sections):
            chunk_hash = sha256(content)
            chunk = conn.execute(
                """
                INSERT INTO chunks (document_id, chunk_index, section_path, content, token_count, content_hash)
                VALUES (%s, %s, %s, %s, %s, %s)
                ON CONFLICT (document_id, chunk_index) DO UPDATE
                    SET section_path = EXCLUDED.section_path,
                        content = EXCLUDED.content,
                        token_count = EXCLUDED.token_count,
                        content_hash = EXCLUDED.content_hash
                RETURNING id, content_hash IS DISTINCT FROM %s AS changed
                """,
                (document_id, chunk_index, section_path, content, len(content.split()), chunk_hash, chunk_hash),
            ).fetchone()
            chunk_id, chunk_changed = chunk

            if chunk_changed or doc_changed:
                embedding = embed(content)
                conn.execute(
                    """
                    INSERT INTO chunk_embeddings (chunk_id, model, embedding)
                    VALUES (%s, %s, %s)
                    ON CONFLICT (chunk_id) DO UPDATE
                        SET model = EXCLUDED.model, embedding = EXCLUDED.embedding
                    """,
                    (chunk_id, EMBEDDING_MODEL, embedding),
                )

        # delete chunks (and, via ON DELETE CASCADE, their embeddings) that no
        # longer exist in the current version of the document
        conn.execute(
            "DELETE FROM chunks WHERE document_id = %s AND chunk_index >= %s",
            (document_id, len(sections)),
        )


def process_queue() -> None:
    with psycopg.connect(DB_DSN, autocommit=True) as conn:
        register_vector(conn)
        while True:
            row = conn.execute(
                """
                SELECT id, source_path FROM ingest_queue
                WHERE status = 'pending'
                ORDER BY enqueued_at
                LIMIT 1
                FOR UPDATE SKIP LOCKED
                """
            ).fetchone()
            if row is None:
                break
            queue_id, source_path = row
            path = pathlib.Path(source_path)
            component = "spring-ai" if "spring-ai" in path.parts else "vector-rag"
            try:
                ingest_file(conn, path, component)
                conn.execute(
                    "UPDATE ingest_queue SET status = 'done', processed_at = now() WHERE id = %s",
                    (queue_id,),
                )
            except Exception:
                conn.execute(
                    "UPDATE ingest_queue SET status = 'failed', processed_at = now() WHERE id = %s",
                    (queue_id,),
                )
                raise


if __name__ == "__main__":
    process_queue()
----

Each chunk's `INSERT ... ON CONFLICT (document_id, chunk_index)` assumes a unique constraint on that pair,
added alongside the schema in xref:database/vector-rag/postgresql-pgvector.adoc[] for this purpose. See
https://www.psycopg.org/psycopg3/docs/basic/transactions.html[psycopg 3: Transactions] for the
`conn.transaction()` context manager used above, and
https://github.com/pgvector/pgvector-python#psycopg-3[pgvector-python: psycopg 3] for `register_vector`.

== Framework ETL pipelines

The manual `ingest.py` above is one way to populate `chunk_embeddings`; every framework this site covers
also ships its own ingestion (or "ETL") building blocks that read, split and write documents into its own
`VectorStore`/`EmbeddingStore` instead.

=== Spring AI ETL

Spring AI models ingestion explicitly as *Extract-Transform-Load*: a `DocumentReader` extracts
`Document` objects, one or more `DocumentTransformer`s (a splitter, a metadata enricher) transform them,
and a `DocumentWriter` -- ordinarily a `VectorStore` itself -- loads the result:

[source,java]
----
package com.example.docsassistant;

import java.util.List;
import org.springframework.ai.document.Document;
import org.springframework.ai.reader.tika.TikaDocumentReader;
import org.springframework.ai.reader.markdown.MarkdownDocumentReader;
import org.springframework.ai.transformer.splitter.TokenTextSplitter;
import org.springframework.ai.vectorstore.VectorStore;
import org.springframework.core.io.Resource;

public class DocumentIngestionEtl {

    private final VectorStore vectorStore;

    public DocumentIngestionEtl(VectorStore vectorStore) {
        this.vectorStore = vectorStore;
    }

    public void ingestPdfOrOffice(Resource resource, String component) {
        // TikaDocumentReader extracts text from PDF, Word, HTML and more via Apache Tika
        List<Document> extracted = new TikaDocumentReader(resource).get();
        loadWithMetadata(extracted, component);
    }

    public void ingestMarkdown(Resource resource, String component) {
        // MarkdownDocumentReader keeps heading structure as document metadata
        List<Document> extracted = new MarkdownDocumentReader(resource).get();
        loadWithMetadata(extracted, component);
    }

    private void loadWithMetadata(List<Document> extracted, String component) {
        TokenTextSplitter splitter = new TokenTextSplitter(1000, 200, 5, 10000, true);
        List<Document> chunks = splitter.apply(extracted);
        chunks.forEach(chunk -> chunk.getMetadata().put("component", component));
        vectorStore.add(chunks);
    }
}
----

`TokenTextSplitter`'s constructor arguments are (target chunk size in tokens, minimum chunk size to keep,
minimum embed length, maximum number of chunks, whether to keep the original document's metadata on every
resulting chunk) -- the 1000/200-token defaults above line up with
xref:#chunk-size-guidance[this page's token-based guidance]. `vectorStore.add(chunks)` is the writer step:
whichever `VectorStore` implementation is configured (`PgVectorStore` for *DocsAssistant*) embeds and
persists every chunk in one call. See
https://docs.spring.io/spring-ai/reference/api/etl-pipeline.html[Spring AI: ETL pipeline] for the full
reader/transformer/writer catalog, including additional readers (JSON, plain text) and transformers
(`KeywordMetadataEnricher`, `SummaryMetadataEnricher`).

=== LangChain: loaders, splitters and `add_documents`

The same three-stage shape -- load, split, write -- appears in LangChain as three separate calls rather than
one pipeline object:

[source,python]
----
from langchain_community.document_loaders import PyPDFLoader, UnstructuredHTMLLoader
from langchain_text_splitters import RecursiveCharacterTextSplitter
from langchain_postgres import PGVector
from langchain_ollama import OllamaEmbeddings

pdf_docs = PyPDFLoader("whitepaper.pdf").load()
html_docs = UnstructuredHTMLLoader("page.html").load()

splitter = RecursiveCharacterTextSplitter(chunk_size=1000, chunk_overlap=200)
chunks = splitter.split_documents(pdf_docs + html_docs)
for chunk in chunks:
    chunk.metadata["component"] = "vector-rag"

vector_store = PGVector(
    embeddings=OllamaEmbeddings(model="nomic-embed-text"),
    collection_name="docsassistant",
    connection="postgresql+psycopg://docs:docs@localhost:5432/docsassistant",
)
vector_store.add_documents(chunks)
----

`add_documents` is the LangChain equivalent of Spring AI's `vectorStore.add(chunks)`: it embeds every
`Document`'s text with the store's configured `Embeddings` and writes it, along with its metadata, into the
store's own tables. See
xref:database/vector-rag/integrating-with-langchain.adoc#langchain-splitters[Integrating with LangChain:
splitters] and
https://docs.langchain.com/oss/python/integrations/document_loaders/index[LangChain: Document loaders].

=== LangChain4j `EmbeddingStoreIngestor`

LangChain4j packages the same load/split/embed/write sequence as one configurable object,
`EmbeddingStoreIngestor`, so a call site supplies a document splitter and lets the ingestor drive embedding
and storage:

[source,java]
----
package com.example.docsassistant;

import dev.langchain4j.data.document.Document;
import dev.langchain4j.data.document.splitter.DocumentSplitters;
import dev.langchain4j.model.embedding.EmbeddingModel;
import dev.langchain4j.store.embedding.EmbeddingStore;
import dev.langchain4j.store.embedding.EmbeddingStoreIngestor;

public class LangChain4jIngestion {

    public void ingest(Document document, EmbeddingModel embeddingModel, EmbeddingStore<?> embeddingStore) {
        EmbeddingStoreIngestor ingestor = EmbeddingStoreIngestor.builder()
                .documentSplitter(DocumentSplitters.recursive(1000, 200))
                .embeddingModel(embeddingModel)
                .embeddingStore(embeddingStore)
                .build();
        ingestor.ingest(document);
    }
}
----

See xref:database/vector-rag/integrating-with-langchain.adoc#langchain4j[Integrating with LangChain:
LangChain4j] for `EmbeddingStore` and `PgVectorEmbeddingStore` setup, and
https://docs.langchain4j.dev/tutorials/rag#ingestion[LangChain4j: RAG -- ingestion] for the full ingestor
API, including custom metadata enrichment.

LangChain's abstraction for this page's load-and-split stage; see

are Spring AI's ETL pipeline; see
