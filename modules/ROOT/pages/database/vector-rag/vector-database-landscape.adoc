= The Vector Database Landscape

Examples and version references on this page target LangChain / `langchain-core` / LangGraph 1.4 / 1.6 / 1.2,
LangChain4j 1.20.1, and Spring Boot 4.1 with Spring AI 2.0.1, alongside the engine versions used throughout this
section (pgvector 0.8.6, sqlite-vec 0.1.9, FAISS 1.15.1). "Vector database" has become a loose umbrella term for
a wide range of very different tools, from a single-file embedded library to a fully managed cloud service. This
page maps that landscape into five overlapping categories, compares their features side by side, and looks at
why a query written against one of them rarely runs unchanged against another. It stops short of scoring the
engines against each other or pricing them out -- that evaluation lives on
xref:database/vector-rag/comparing-vector-databases.adoc[].

== Five categories, one underlying problem

Every tool below solves the same core problem -- given a query vector, find the nearest stored vectors quickly
-- but each one bolted that capability onto a different starting point, and that starting point still shapes
what it is good at.

image::vector-rag-landscape-map.svg["A map of the vector database landscape grouped into five categories: libraries, SQL extensions, purpose-built engines, search engines, and multi-model / NoSQL stores, with a deployment-model axis from embedded library to fully managed serverless",width=720,role=text-center]

=== Libraries

A library has no server, no network protocol and no notion of metadata or persistence beyond what the calling
process wires up itself. It is a set of in-process ANN algorithms an application links against directly.

* *FAISS* -- the reference implementation for ANN research, covered in depth on
  xref:database/vector-rag/faiss.adoc[]. It gives every index family and GPU acceleration, at the cost of every
  other database feature: no filtering, no concurrency control, no replication.

=== SQL extensions

A SQL extension adds a vector type and a handful of operators to an existing relational engine, so vector search
becomes one more thing SQL can do next to joins, transactions and the rest of the schema.

* *pgvector* -- a PostgreSQL extension; see xref:database/vector-rag/postgresql-pgvector.adoc[].
* *sqlite-vec* -- an SQLite extension for embedded, single-file use; see
  xref:database/vector-rag/sqlite-vector-search.adoc[].
* *Oracle AI Vector Search* -- a `VECTOR` type built into the converged Oracle Database, with HNSW and IVF
  indexes queried through ordinary SQL joins. It is mentioned here for completeness rather than documented in
  depth on this site.

=== Purpose-built engines

A purpose-built engine is designed around the vector index as its primary access path, rather than adding one to
something else. This is the category most people picture when they hear "vector database."

* *Qdrant* -- self-hostable, Rust-based; see xref:database/qdrant/index.adoc[].
* *Milvus* -- built for billion-scale distributed search, with a disaggregated storage/compute architecture and
  the widest index choice of any engine here (HNSW, IVF, DiskANN, GPU CAGRA).
* *Weaviate* -- ships built-in vectorizer and reranker modules so embedding can happen at ingest time, alongside
  BM25 + vector hybrid search.
* *Chroma* -- the simplest developer experience of the group, with an embedded/local mode as well as a hosted
  cloud.
* *LanceDB* -- embedded, storing vectors in the columnar Lance format directly on object storage.
* *Pinecone* -- the odd one out in this category: a fully managed serverless service with no self-hosted or
  local option at all. It is grouped here because its data model and query surface are purpose-built for vectors
  in the same way, even though "deployment model" for Pinecone is a single point, not a range.

=== Search engines

A search engine started as a lexical, inverted-index engine and added dense-vector kNN alongside it, so the same
system that already scores BM25 relevance can also rank by vector similarity.

* *Elasticsearch* -- see xref:database/elasticsearch/vector-and-semantic-search.adoc[].
* *OpenSearch* -- Elasticsearch's Apache-2.0 fork with its own vector engine choices (`faiss`, `lucene`,
  `nmslib`); it has no dedicated page in this site's reference yet, but shares the retriever concepts covered on
  the Elasticsearch page.
* *Apache Solr* -- see xref:database/solr/dense-vector-search.adoc[].
* *Apache Lucene* -- see xref:database/lucene/knn-vector-search.adoc[]. Lucene is the odd one out here too: it is
  an embeddable Java library, not a server, and both Solr and Elasticsearch build their vector search on top of
  it.

=== Multi-model / NoSQL

A multi-model or NoSQL store added a vector index next to the data model it already had -- documents, key-value
pairs, or a property graph -- so vectors live beside the operational data they describe instead of in a separate
system.

* *Redis* -- see xref:database/redis/vector-search.adoc[].
* *MongoDB* -- see xref:database/mongodb/special-indexes-and-search.adoc[].
* *Couchbase* -- see xref:database/couchbase/search-analytics-eventing.adoc[].
* *Neo4j* -- see xref:database/neo4j/vector-search-and-genai.adoc[].
* *Cassandra* -- added vector search (`CQL` `VECTOR` type, storage-attached indexing) in Cassandra 5.0; it has no
  dedicated page in this site's reference yet.

These categories overlap deliberately rather than cleanly: Redis and MongoDB are both credible purpose-built
targets for a pure vector workload; OpenSearch and Elasticsearch compete directly with Qdrant and Milvus on RAG
pipelines; and pgvector's whole appeal is that it lets a team stay inside a category (relational SQL) it was
already in, rather than adopting a new one.

== The portability problem

Every row in the table above speaks a different query language for what is conceptually the same operation:
find the `k` vectors nearest a query vector, optionally filtered, optionally blended with a lexical score. A
`SIMILARITY SEARCH` written for one engine has to be rewritten by hand for another -- there is no SQL-92-style
standard that a vector query compiles against the way relational SQL does.

This gap has been a recurring topic of community and industry discussion for several years, under names such as
"Vector Query Language" or "VQL" -- a *proposed*, illustrative idea for what a portable vector query surface
could look like, not a ratified standard with a single official specification. No engine implements the sketch
below as written; it exists to make the portability problem concrete, not to describe a product.

A conceptual VQL-style data model treats a *collection* as a named set of records, each with a vector plus
arbitrary scalar attributes -- deliberately close to what every purpose-built engine and SQL extension above
already exposes, just without a shared syntax for expressing it. A similarity search reads, in illustrative
pseudo-syntax:

[source,text]
----
SIMILARITY SEARCH TOP 10
FROM docsassistant_chunks
USING VECTOR {0.012, -0.087, 0.045, ...}
USING METRIC COSINE
----

Filtered and thresholded search compose the same clause with an ordinary predicate and a distance cutoff, mirroring
what pgvector expresses in a `WHERE` clause and Qdrant expresses as a payload filter:

[source,text]
----
SIMILARITY SEARCH TOP 10
FROM docsassistant_chunks
USING VECTOR {...}
USING METRIC COSINE
WHERE component = 'vector-rag'
MINIMUM SIMILARITY 0.75
----

A `HYBRID SEARCH` clause would fold lexical and vector scoring into one statement with explicit weights, in
place of the two-query, application-side fusion every engine on this page actually requires today:

[source,text]
----
HYBRID SEARCH TOP 10
FROM docsassistant_chunks
MATCHING TEXT 'how does ef_search affect recall'  WEIGHT 0.3
USING VECTOR {...} WEIGHT 0.7
----

`RANGE SEARCH` would return every vector within a radius rather than a fixed count -- the same shape as
FAISS's `range_search`, pgvector's `<->` used in a `WHERE` clause, and Redis's `VECTOR_RANGE`:

[source,text]
----
RANGE SEARCH
FROM docsassistant_chunks
USING VECTOR {...}
USING METRIC COSINE
WITHIN 0.35
----

Batch search (many query vectors in one call, as FAISS's `search` already does for a whole matrix at once) and
vector-valued functions and aggregations round out the sketch: an `AVG` over a group of vectors would return
their centroid, and a `GEOMETRIC_MEDIAN` aggregate would return the vector minimizing total distance to the
group -- a robustness improvement over the centroid when a group contains outliers -- illustrative of the kind of
vector-native aggregation a query language could offer, analogous to `AVG`/`MEDIAN` over scalar columns today.

=== What actually solves this today

In practice, two different layers absorb the portability problem instead of a query language doing it:

* *Framework abstractions.* LangChain's `VectorStore` interface and LangChain4j's `EmbeddingStore` interface, and
  Spring AI's `VectorStore` interface, give application code one `add`/`similaritySearch`/`delete`-shaped surface
  that each concrete implementation (pgvector, Qdrant, Redis, ...) maps onto its own native query language behind
  the scenes. Swapping the backing engine is a constructor or configuration change, not a rewrite of retrieval
  code -- see <<In LangChain and Spring AI>> below.
* *SQL extensions.* pgvector, sqlite-vec and Oracle AI Vector Search sidestep the problem differently: instead of
  inventing a new vector query language, they add a type and a few operators to SQL, which is itself already a
  portable, standardized language for everything *except* the vector-specific parts (`<->`/`<=>`, `MATCH ...
  AND k = ?`, and their Oracle equivalents still differ syntactically per engine).

Neither layer is a complete answer: a framework abstraction hides *simple* CRUD and search calls uniformly, but
advanced features -- filter-expression syntax, quantization settings, hybrid-fusion weights, index-tuning
parameters -- still leak the underlying engine's own vocabulary through the abstraction, which is exactly the
"switching cost" xref:database/vector-rag/comparing-vector-databases.adoc[] discusses.

== In LangChain and Spring AI

=== LangChain

LangChain's `VectorStore` base class gives every concrete store (`FAISS`, `PGVector`, `QdrantVectorStore`,
`Redis`, and the rest) the same construction, `add_documents`/`similarity_search`, and `as_retriever()` surface.
Choosing an engine from this landscape becomes a choice of which `VectorStore` subclass to instantiate, not a
change to the surrounding chain or agent code. See
xref:database/vector-rag/integrating-with-langchain.adoc#langchain-vector-stores[Vector stores] for the
construction and retrieval patterns, and LangChain4j's `EmbeddingStore` interface
(xref:database/vector-rag/integrating-with-langchain.adoc#langchain4j[LangChain4j]) for the equivalent on the
JVM.

=== Spring AI

Spring AI's `VectorStore` interface plays the same role on the JVM: `PgVectorStore`, `QdrantVectorStore`,
`RedisVectorStore`, `ElasticsearchVectorStore` and the other implementations listed in the feature table above
all implement the same `add`/`delete`/`similaritySearch(SearchRequest)` contract, auto-configured from Spring
Boot properties. See
xref:database/vector-rag/integrating-with-spring-ai.adoc#spring-ai-vector-store-api[VectorStore API] for the
construction pattern and `SearchRequest.builder()` usage against the *DocsAssistant* schema.
