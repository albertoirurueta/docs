= Advanced Cypher querying
:description: Chaining and composing Cypher queries with WITH, CALL \{ \} subqueries, UNION, comprehensions, UNWIND and OPTIONAL MATCH, plus variable-length paths, shortestPath, quantified path patterns and the SHORTEST keyword, all verified on the movie dataset.
:keywords: neo4j, cypher, with, call subquery, union, union all, list comprehension, map comprehension, unwind, optional match, variable-length path, shortestpath, allshortestpaths, quantified path pattern, shortest, count subquery, collect subquery

include::partial$ai-disclaimer.adoc[]

Beyond a single `MATCH` / `RETURN`, Cypher queries are built by chaining intermediate result sets and by
traversing paths whose length or endpoints are not known in advance. This page assumes the
xref:database/neo4j/cypher-fundamentals.adoc[Cypher fundamentals] page's `:Person` / `:Movie` /
`ACTED_IN` domain (the xref:database/neo4j/getting-started.adoc[movie dataset]) and builds on it. Every result
below was produced by running the statement on a Neo4j `2026.01` server loaded with that dataset and nothing else.

Which tool to reach for depends on how the pieces of the query relate to each other:

[mermaid]
....
flowchart TD
    Q{"How do the pieces combine?"} --> A["Feed one stage's rows into the next"]
    Q --> B["Run a sub-query once per row"]
    Q --> C["Stack results of independent queries"]
    Q --> D["Turn a list into rows"]
    Q --> E["Keep rows that have no match"]
    Q --> F["Follow paths of unknown length"]
    A --> A1["WITH"]
    B --> B1["CALL subquery"]
    C --> C1["UNION or UNION ALL"]
    D --> D1["UNWIND"]
    E --> E1["OPTIONAL MATCH"]
    F --> F1["Variable-length pattern<br/>shortestPath, quantified paths"]
....

== WITH for query chaining

`WITH` passes a projected, optionally aggregated or filtered, result set from one part of a query into the
next -- the same variables an earlier `MATCH` bound are not automatically visible after a `WITH` unless they
are re-listed in it. That scoping rule is the point: `WITH` is a barrier that decides exactly what continues.

[source,cypher]
----
// Actors with 3+ movies, then the titles of those movies
MATCH (p:Person)-[:ACTED_IN]->(m:Movie)
WITH p, count(m) AS movieCount
WHERE movieCount >= 3
MATCH (p)-[:ACTED_IN]->(m:Movie)
RETURN p.name, movieCount, collect(m.title) AS titles
ORDER BY movieCount DESC, p.name;
----

[source,console]
----
+------------------------------------------------------------------------------------------+
| p.name         | movieCount | titles                                                     |
+------------------------------------------------------------------------------------------+
| "Hugo Weaving" | 3          | ["Cloud Atlas", "The Matrix Reloaded", "The Matrix"]       |
| "Keanu Reeves" | 3          | ["The Matrix", "Speed", "The Matrix Reloaded"]             |
| "Tom Hanks"    | 3          | ["Cloud Atlas", "You've Got Mail", "Sleepless in Seattle"] |
+------------------------------------------------------------------------------------------+
----

The first `MATCH` produces one row per credit; `WITH p, count(m)` collapses them to one row per person and
`WHERE` filters those groups (this is the Cypher equivalent of SQL's `HAVING`); the second `MATCH` then starts
again from the surviving people. Note that `m` was *not* carried through the `WITH`, so the second `+MATCH (p)-[:ACTED_IN]->(m:Movie)+`
introduces a fresh `m`.

`WITH` also carries ordering and pagination between stages, and can aggregate an aggregate, which `RETURN`
alone cannot:

[source,cypher]
----
MATCH (m:Movie)<-[:ACTED_IN]-(p:Person)
WITH m, count(p) AS cast
WITH avg(cast) AS averageCast, max(cast) AS biggest
RETURN averageCast, biggest;
----

[source,console]
----
+-----------------------+
| averageCast | biggest |
+-----------------------+
| 2.5         | 4       |
+-----------------------+
----

== CALL \{ \} subqueries

A `+CALL { ... }+` subquery runs an independent unit of work per incoming row (or once, if uncorrelated) and
returns its results into the outer query. It is the modern replacement for most cases that used to need
`FOREACH` tricks or repeated `MATCH` clauses, and it is what makes per-row `LIMIT`, per-row aggregation and
per-row `UNION` possible without collapsing the outer rows. Variables from the outer query are imported with a
*scope clause*: `+CALL (p) { ... }+` imports `p`, and `+CALL () { ... }+` imports nothing and runs once.

[source,cypher]
----
// For every person, the title of their most recent movie -- computed per row
MATCH (p:Person)
CALL (p) {
  MATCH (p)-[:ACTED_IN]->(m:Movie)
  RETURN m.title AS latestTitle
  ORDER BY m.released DESC
  LIMIT 1
}
RETURN p.name, latestTitle
ORDER BY p.name;
----

[source,console]
----
+----------------------------------------------+
| p.name               | latestTitle           |
+----------------------------------------------+
| "Carrie-Anne Moss"   | "The Matrix Reloaded" |
| "Hugo Weaving"       | "Cloud Atlas"         |
| "Keanu Reeves"       | "The Matrix Reloaded" |
| "Laurence Fishburne" | "The Matrix Reloaded" |
| "Meg Ryan"           | "You've Got Mail"     |
| "Tom Hanks"          | "Cloud Atlas"         |
+----------------------------------------------+
----

Without the subquery, `LIMIT 1` would apply to the whole result; inside it, it applies once per person. The
older spelling `+CALL { WITH p ... }+` still works, but the scope clause is clearer about what is imported. An
uncorrelated subquery, with an empty scope clause, is evaluated once and its columns are visible to the rest of
the query:

[source,cypher]
----
CALL () {
  MATCH (m:Movie) RETURN max(m.released) AS newest
}
MATCH (m:Movie {released: newest})
RETURN m.title, newest;
----

[source,console]
----
+------------------------+
| m.title       | newest |
+------------------------+
| "Cloud Atlas" | 2012   |
+------------------------+
----

A subquery that returns no rows removes the outer row, like an inner join; to keep it, make the inner part an
`OPTIONAL MATCH`. `+CALL { } IN TRANSACTIONS+` runs a subquery in separate, batched transactions -- used for large
writes rather than in read-heavy analytical queries like the ones above, and covered with `LOAD CSV` in
xref:database/neo4j/importing-data.adoc[Importing data]
(https://neo4j.com/docs/cypher-manual/current/subqueries/subqueries-in-transactions/[CALL \{ \} IN TRANSACTIONS]).

Two subquery *expressions* cover the most common reasons to open a full subquery: `+COUNT { pattern }+` returns the
number of matches, and `+COLLECT { query }+` returns a list built from a mini query, and both can be used anywhere
an expression is allowed:

[source,cypher]
----
MATCH (m:Movie {title: "Cloud Atlas"})
RETURN m.title, COLLECT { MATCH (m)<-[:ACTED_IN]-(p) RETURN p.name ORDER BY p.name } AS cast;
----

[source,console]
----
+-----------------------------------------------+
| m.title       | cast                          |
+-----------------------------------------------+
| "Cloud Atlas" | ["Hugo Weaving", "Tom Hanks"] |
+-----------------------------------------------+
----

== UNION and UNION ALL

`UNION` combines the results of two or more queries that return the same column names, de-duplicating rows;
`UNION ALL` keeps every row, including duplicates, and is cheaper when duplicates are known not to occur or
do not matter.

[source,cypher]
----
MATCH (p:Person)-[:ACTED_IN]->(:Movie {title: "The Matrix"})
RETURN p.name AS name, "actor" AS role
UNION ALL
MATCH (p:Person)-[:DIRECTED]->(:Movie {title: "The Matrix"})
RETURN p.name AS name, "director" AS role;
----

[source,console]
----
+-----------------------------------+
| name                 | role       |
+-----------------------------------+
| "Laurence Fishburne" | "actor"    |
| "Carrie-Anne Moss"   | "actor"    |
| "Keanu Reeves"       | "actor"    |
| "Hugo Weaving"       | "actor"    |
| "Lana Wachowski"     | "director" |
+-----------------------------------+
----

The distinction shows when the branches overlap. The first two films share their cast, so `UNION ALL` returns
every person twice (eight rows) and `UNION` removes the repeats (four rows):

[source,cypher]
----
MATCH (p:Person)-[:ACTED_IN]->(:Movie {title: "The Matrix"}) RETURN p.name AS name
UNION
MATCH (p:Person)-[:ACTED_IN]->(:Movie {title: "The Matrix Reloaded"}) RETURN p.name AS name;
----

[source,console]
----
+----------------------+
| name                 |
+----------------------+
| "Laurence Fishburne" |
| "Carrie-Anne Moss"   |
| "Keanu Reeves"       |
| "Hugo Weaving"       |
+----------------------+
----

== List and map comprehensions

A list comprehension filters and/or transforms a list inline, without a separate `UNWIND` /
`collect()` round trip. A map comprehension does the same over map entries. `reduce()` folds a list into a single
value, and `COUNT`/`COLLECT` subqueries (above) cover the pattern-based cases.

[source,cypher]
----
MATCH (p:Person {name: "Tom Hanks"})-[:ACTED_IN]->(m:Movie)
RETURN [movie IN collect(m) WHERE movie.released >= 1998 | movie.title] AS recentTitles;
----

[source,console]
----
+------------------------------------+
| recentTitles                       |
+------------------------------------+
| ["Cloud Atlas", "You've Got Mail"] |
+------------------------------------+
----

[source,cypher]
----
// Map comprehension over a literal map's entries
WITH {matrix: 1999, inception: 2010, dune: 2021} AS releaseYears
RETURN [key IN keys(releaseYears) WHERE releaseYears[key] >= 2010 | key] AS from2010On;

MATCH (p:Person {name: "Keanu Reeves"})-[:ACTED_IN]->(m:Movie)
WITH collect(m) AS films
RETURN reduce(total = 0, f IN films | total + f.released) AS sumOfYears, size(films) AS n,
       [f IN films | f.title] AS titles;
----

[source,console]
----
+-----------------------+
| from2010On            |
+-----------------------+
| ["dune", "inception"] |
+-----------------------+

+-----------------------------------------------------------------+
| sumOfYears | n | titles                                         |
+-----------------------------------------------------------------+
| 5996       | 3 | ["The Matrix", "Speed", "The Matrix Reloaded"] |
+-----------------------------------------------------------------+
----

== UNWIND

`UNWIND` expands a list into one row per element -- the inverse of `collect()` -- commonly used to turn a
parameter list into rows for matching, or to flatten a list produced earlier in the same query.

[source,cypher]
----
UNWIND ["The Matrix", "Speed", "Cloud Atlas"] AS title
MATCH (m:Movie {title: title})<-[:ACTED_IN]-(p:Person)
RETURN title, collect(p.name) AS cast;
----

[source,console]
----
+--------------------------------------------------------------------------------------------+
| title         | cast                                                                       |
+--------------------------------------------------------------------------------------------+
| "The Matrix"  | ["Laurence Fishburne", "Carrie-Anne Moss", "Keanu Reeves", "Hugo Weaving"] |
| "Speed"       | ["Keanu Reeves"]                                                           |
| "Cloud Atlas" | ["Hugo Weaving", "Tom Hanks"]                                              |
+--------------------------------------------------------------------------------------------+
----

`UNWIND` of an empty list yields no rows, so the rest of the query is skipped, and `UNWIND null` behaves the same
way. `UNWIND range(1, 3) AS n` is the idiom for generating a sequence of rows.

== OPTIONAL MATCH

`OPTIONAL MATCH` behaves like an outer join: when the pattern has no match for a given row, its variables
are bound to `null` instead of dropping the row, so a person with no directing credits still appears once
in the results.

[source,cypher]
----
MATCH (p:Person {name: "Keanu Reeves"})
OPTIONAL MATCH (p)-[:DIRECTED]->(directed:Movie)
RETURN p.name, directed.title;
// directed.title is null if Keanu has never directed a movie
----

[source,console]
----
+---------------------------------+
| p.name         | directed.title |
+---------------------------------+
| "Keanu Reeves" | NULL           |
+---------------------------------+
----

Because the row survives, an aggregate over the optional part counts only real matches: `count(d)` ignores the
`null`, so people who never directed get `0`, whereas `+count(*)+` would report `1` for them.

[source,cypher]
----
MATCH (p:Person)
OPTIONAL MATCH (p)-[:DIRECTED]->(d:Movie)
RETURN p.name, count(d) AS directed
ORDER BY directed DESC, p.name
LIMIT 4;
----

[source,console]
----
+-------------------------------+
| p.name             | directed |
+-------------------------------+
| "Lana Wachowski"   | 3        |
| "Nora Ephron"      | 2        |
| "Carrie-Anne Moss" | 0        |
| "Hugo Weaving"     | 0        |
+-------------------------------+
----

Together, `WITH`, `+CALL { }+`, `UNION` / `UNION ALL`, comprehensions, `UNWIND` and `OPTIONAL MATCH` cover
the query-composition material in
https://neo4j.com/docs/cypher-manual/current/queries/[Queries] and
https://neo4j.com/docs/cypher-manual/current/clauses/[Clauses].

== Variable-length paths

A relationship pattern can specify a hop range with `+*min..max+` instead of a single hop, matching every path
whose length falls in that range. Omitting either bound defaults it: `+*+` alone means `+*1..+` (one or more hops,
unbounded), `+*..3+` means `+*1..3+`, and `+*2+` is exactly two hops.

Remember that the pattern's endpoints are still typed. In this graph `ACTED_IN` always joins a person and a
movie, so walking `ACTED_IN` hops from a person alternates person, movie, person, movie. A two-hop path ends on
another person (a co-actor); a one- or three-hop path ends on a movie. Asking for `(coActor:Person)` at the end
therefore silently selects only the even lengths:

[source,cypher]
----
// Tom Hanks's co-actors: exactly two ACTED_IN hops, through a shared movie
MATCH (origin:Person {name: "Tom Hanks"})-[:ACTED_IN*2]-(coActor:Person)
WHERE coActor <> origin
RETURN DISTINCT coActor.name ORDER BY coActor.name;
----

[source,console]
----
+----------------+
| coActor.name   |
+----------------+
| "Hugo Weaving" |
| "Meg Ryan"     |
+----------------+
----

Widening the range to four hops reaches co-actors of co-actors. Binding the whole path to a variable makes its
length available, and taking the minimum per person gives the "degrees of separation":

[source,cypher]
----
MATCH path = (origin:Person {name: "Tom Hanks"})-[:ACTED_IN*1..4]-(other:Person)
WHERE other <> origin
RETURN other.name AS person, min(length(path)) AS hops
ORDER BY hops, person;
----

[source,console]
----
+-----------------------------+
| person               | hops |
+-----------------------------+
| "Hugo Weaving"       | 2    |
| "Meg Ryan"           | 2    |
| "Carrie-Anne Moss"   | 4    |
| "Keanu Reeves"       | 4    |
| "Laurence Fishburne" | 4    |
+-----------------------------+
----

Hugo Weaving (through `Cloud Atlas`) and Meg Ryan (through the two comedies) are two hops from Tom Hanks. The three
other Matrix actors are four hops away, through Hugo Weaving and a Matrix film. Within a single pattern a
relationship is never used twice, which is what stops a cycle from being walked forever, but the number of paths
can still grow explosively with the upper bound.

An unbounded or loosely bounded variable-length pattern can traverse a very large part of the graph; always
pair it with a `LIMIT`, a tight upper bound, or a `WHERE` predicate that prunes the search
(https://neo4j.com/docs/cypher-manual/current/patterns/fixed-length-patterns/[variable-length relationships]).

== shortestPath() and allShortestPaths()

`shortestPath()` returns one shortest path between two already-bound nodes; `allShortestPaths()` returns
every path tied for shortest. Both require the two endpoint nodes to be matched first and take an upper
bound on hops so the search terminates.

[source,cypher]
----
// The shortest chain of shared-movie connections between two actors
MATCH (a:Person {name: "Tom Hanks"}), (b:Person {name: "Keanu Reeves"})
MATCH path = shortestPath((a)-[:ACTED_IN*..6]-(b))
RETURN [n IN nodes(path) | coalesce(n.name, n.title)] AS chain, length(path) AS hops;
----

[source,console]
----
+--------------------------------------------------------------------------------------------+
| chain                                                                               | hops |
+--------------------------------------------------------------------------------------------+
| ["Tom Hanks", "Cloud Atlas", "Hugo Weaving", "The Matrix Reloaded", "Keanu Reeves"] | 4    |
+--------------------------------------------------------------------------------------------+
----

Four hops is the shortest possible, but more than one path has that length, and `shortestPath()` returns just one
of them, with no promise about which. `allShortestPaths()` returns every tied path:

[source,cypher]
----
// Every co-acting connection tied for shortest, not just one of them
MATCH (a:Person {name: "Tom Hanks"}), (b:Person {name: "Keanu Reeves"})
MATCH path = allShortestPaths((a)-[:ACTED_IN*..6]-(b))
RETURN [n IN nodes(path) | coalesce(n.name, n.title)] AS chain, length(path) AS hops;
----

[source,console]
----
+--------------------------------------------------------------------------------------------+
| chain                                                                               | hops |
+--------------------------------------------------------------------------------------------+
| ["Tom Hanks", "Cloud Atlas", "Hugo Weaving", "The Matrix", "Keanu Reeves"]          | 4    |
| ["Tom Hanks", "Cloud Atlas", "Hugo Weaving", "The Matrix Reloaded", "Keanu Reeves"] | 4    |
+--------------------------------------------------------------------------------------------+
----

Dropping the relationship type from the pattern lets the path use `DIRECTED` relationships as well, which opens a
different route through the director of `Cloud Atlas` and `The Matrix`:

[source,cypher]
----
MATCH (a:Person {name: "Tom Hanks"}), (b:Person {name: "Keanu Reeves"})
MATCH path = shortestPath((a)-[*..6]-(b))
RETURN [n IN nodes(path) | coalesce(n.name, n.title)] AS chain, length(path) AS hops;
----

[source,console]
----
+-------------------------------------------------------------------------------------+
| chain                                                                        | hops |
+-------------------------------------------------------------------------------------+
| ["Tom Hanks", "Cloud Atlas", "Lana Wachowski", "The Matrix", "Keanu Reeves"] | 4    |
+-------------------------------------------------------------------------------------+
----

See
https://neo4j.com/docs/cypher-manual/current/patterns/shortest-paths/[shortest paths] for the
constraints on mixing these functions with other predicates in the same `MATCH`.

== Quantified path patterns and the SHORTEST keyword

Variable-length *relationships* repeat a single relationship. A *quantified path pattern* repeats a whole
sub-pattern -- nodes, relationships and predicates together -- between a pair of parentheses followed by a
quantifier such as `+{1,3}+`, `pass:c[+]` (one or more) or `+*+` (zero or more). The unit "co-actor hop" is exactly
`+()-[:ACTED_IN]->(m:Movie)<-[:ACTED_IN]-()+`, and a quantified path repeats it with `m` available afterwards as a
*list* of every movie matched along the way (a group variable):

[source,cypher]
----
MATCH (a:Person {name: "Tom Hanks"})
      (()-[:ACTED_IN]->(m:Movie)<-[:ACTED_IN]-()){1,3}
      (b:Person {name: "Keanu Reeves"})
RETURN size(m) AS films, count(*) AS paths
ORDER BY films;
----

[source,console]
----
+---------------+
| films | paths |
+---------------+
| 2     | 2     |
| 3     | 4     |
+---------------+
----

There are six qualifying paths: two use two films (through `Hugo Weaving`, via either Matrix film) and four use
three films (through an extra Matrix actor). Because the predicate lives inside the repeated unit, it applies to
every iteration, which a plain `+*1..3+` cannot express. Here only films released in 2003 or later may be used:

[source,cypher]
----
MATCH (a:Person {name: "Tom Hanks"})
      (()-[:ACTED_IN]->(m:Movie WHERE m.released >= 2003)<-[:ACTED_IN]-()){1,3}
      (b:Person {name: "Keanu Reeves"})
RETURN [movie IN m | movie.title] AS filmsOnTheWay;
----

[source,console]
----
+----------------------------------------+
| filmsOnTheWay                          |
+----------------------------------------+
| ["Cloud Atlas", "The Matrix Reloaded"] |
+----------------------------------------+
----

The `SHORTEST` keyword (the GQL-style replacement for the `shortestPath()` functions) takes a path pattern
with a quantifier and needs no separate endpoint `MATCH`. `SHORTEST 1` returns one shortest path,
`ALL SHORTEST` every tied path, and `SHORTEST k GROUPS` the paths of the *k* shortest distinct lengths:

[source,cypher]
----
MATCH path = ALL SHORTEST (:Person {name: "Tom Hanks"})-[:ACTED_IN]-+(:Person {name: "Keanu Reeves"})
RETURN [n IN nodes(path) | coalesce(n.name, n.title)] AS chain;

MATCH path = SHORTEST 2 GROUPS (:Person {name: "Tom Hanks"})-[:ACTED_IN|DIRECTED]-+(:Person {name: "Keanu Reeves"})
RETURN length(path) AS hops, count(*) AS paths;
----

[source,console]
----
+-------------------------------------------------------------------------------------+
| chain                                                                               |
+-------------------------------------------------------------------------------------+
| ["Tom Hanks", "Cloud Atlas", "Hugo Weaving", "The Matrix", "Keanu Reeves"]          |
| ["Tom Hanks", "Cloud Atlas", "Hugo Weaving", "The Matrix Reloaded", "Keanu Reeves"] |
+-------------------------------------------------------------------------------------+

+--------------+
| hops | paths |
+--------------+
| 4    | 4     |
| 6    | 12    |
+--------------+
----

With both relationship types allowed, there are four paths of length four and twelve of length six. The quantified
forms are available from Neo4j 5.9, and `SHORTEST` from 5.21; the older functions remain for compatibility.

== Putting it together: characterizing a graph

A common first analysis of an unfamiliar graph is its *degree distribution*: how many connections each node has,
and how many nodes share each degree. The `+COUNT { }+` expression and a second aggregation produce it in one
statement. On the movie graph, four people have degree 2 and four have degree 3, with no hubs:

[source,cypher]
----
MATCH (p:Person)
WITH COUNT { (p)--() } AS degree
RETURN degree, count(*) AS people
ORDER BY degree;
----

[source,console]
----
+-----------------+
| degree | people |
+-----------------+
| 2      | 4      |
| 3      | 4      |
+-----------------+
----

On a real graph the same statement exposes supernodes (see xref:database/neo4j/data-modeling.adoc[Data modeling])
as a long tail of nodes with very large degree.

Continue with xref:database/neo4j/cypher-fundamentals.adoc[Cypher fundamentals] for the `MATCH` / `WHERE` /
`RETURN` basics these techniques build on, and with xref:database/neo4j/data-modeling.adoc[Data modeling] for how
the shape of the graph decides how cheap these traversals are.
