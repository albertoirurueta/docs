= Similarity, embeddings and ML pipelines
:description: Node Similarity and KNN for co-starring-style similarity, FastRP/Node2Vec versus GraphSAGE embeddings, and the GDS node-classification and link-prediction ML pipelines.
:keywords: neo4j, graph data science, gds, node similarity, knn, k-nearest neighbors, fastrp, node2vec, graphsage, embeddings, node classification pipeline, link prediction pipeline, machine learning

include::partial$ai-disclaimer.adoc[]

Beyond path-finding and centrality, the Graph Data Science (GDS) library scores pairwise similarity between
nodes, projects a graph's structure into fixed-length vectors, and wraps feature engineering plus training
into repeatable ML pipelines. All three build on the same in-memory projected graph used by other GDS
algorithms.

== Node Similarity and KNN

*Node Similarity* computes an exact pairwise similarity score (Jaccard, overlap, or cosine by default) between
nodes that share a relationship type to a common set of neighbors -- the classic "customers who bought similar
products" or "actors who co-starred with the same people" pattern. It is exhaustive, so it is best on graphs
where the compared node set is not huge. *KNN* (k-nearest neighbors) approximates the same kind of scoring
using a randomized nearest-neighbor search, trading a small amount of accuracy for scaling to much larger
candidate sets, and it also accepts pre-computed embedding properties as its similarity input instead of
relationship overlap.

The first examples use the film graph of
xref:database/neo4j/graph-data-science-fundamentals.adoc[Graph Data Science Fundamentals] -- six actors, four films --
projected undirected so that similarity can be computed from either side of the `ACTED_IN` relationship.

[source,cypher]
----
CALL gds.graph.project(
  'pm-undirected',
  ['Person', 'Movie'],
  { ACTED_IN: { orientation: 'UNDIRECTED' } }
);

CALL gds.nodeSimilarity.stream('pm-undirected', {
  topK: 3,
  similarityCutoff: 0.1
})
YIELD node1, node2, similarity
RETURN coalesce(gds.util.asNode(node1).name, gds.util.asNode(node1).title) AS first,
       coalesce(gds.util.asNode(node2).name, gds.util.asNode(node2).title) AS second,
       round(similarity * 1000) / 1000.0 AS similarity
ORDER BY similarity DESC, first, second
LIMIT 8;
----

[source,text]
----
first, second, similarity
"Di", "Ed", 1.0
"Ed", "Di", 1.0
"Nine Lives", "Red Horizon", 1.0
"Red Horizon", "Nine Lives", 1.0
"Ada", "Bo", 0.667
"Bo", "Ada", 0.667
"Cy", "Di", 0.5
"Cy", "Ed", 0.5
----

Node Similarity compares the *neighbor sets* of two nodes with the Jaccard coefficient: shared neighbors divided
by the size of the union. Di and Ed each acted only in `Paper Moon`, so their sets are identical and the score is
`1.0`. Ada's films are `+{Nine Lives, Red Horizon}+` and Bo's are `+{Nine Lives, Red Horizon, Glass Orchard}+`, giving
`2 / 3 = 0.667`. Cy, with `+{Glass Orchard, Paper Moon}+`, overlaps Di's `+{Paper Moon}+` in one of two films: `0.5`.
Because the projection mixes both labels, the films are compared too -- `Nine Lives` and `Red Horizon` have the
same cast. Each pair appears in both directions; `topK` limits the number of most similar nodes kept *per node*,
and `similarityCutoff` drops weak pairs. Use `+similarityMetric: 'OVERLAP'+` or `+'COSINE'+` for the other metrics.

To compute similarity for a chosen set of source nodes only -- the practical form once all-pairs comparison is
wasteful -- use the filtered variant `gds.nodeSimilarity.filtered`; the
xref:database/neo4j/use-cases-and-algorithms-in-practice.adoc[use-cases page] builds a recommender on it.

....
flowchart LR
    Ada --> NL["Nine Lives"]
    Ada --> RH["Red Horizon"]
    Bo --> NL
    Bo --> RH
    Bo --> GO["Glass Orchard"]
    Cy --> GO
    Cy --> PM["Paper Moon"]

The `topK` approach is exhaustive per node, which is why it should be used on moderately sized graphs. KNN reaches a
similar answer for much larger sets by comparing node *properties* -- typically embeddings -- instead of
neighbor sets. The following sections produce those embeddings; KNN runs on them directly:

[source,cypher]
----
// Embed first (see below), then run KNN on the embedding property
CALL gds.fastRP.mutate('pm-undirected', {
  embeddingDimension: 16, randomSeed: 7, mutateProperty: 'embedding'
});

CALL gds.knn.stream('pm-undirected', {
  nodeLabels: ['Person'],
  nodeProperties: ['embedding'],
  topK: 2,
  sampleRate: 1.0,
  randomSeed: 42,
  concurrency: 1
})
YIELD node1, node2, similarity
RETURN gds.util.asNode(node1).name AS first,
       gds.util.asNode(node2).name AS second,
       round(similarity * 1000) / 1000.0 AS similarity
ORDER BY similarity DESC
LIMIT 4;
----

[source,text]
----
first, second, similarity
"Di", "Ed", 1.0
"Ed", "Di", 1.0
"Cy", "Flo", 0.975
"Flo", "Cy", 0.975
----

Here `+nodeLabels: ['Person']+` is safe because KNN compares a property of the node itself rather than its neighbors.
The result agrees with the topological view for Di and Ed, who occupy identical positions in the graph and
therefore receive identical embeddings. KNN is approximate: it starts from random candidate neighbors and
iteratively improves them (`sampleRate`, `deltaThreshold` and `maxIterations` trade accuracy for time), so
set `randomSeed` together with `concurrency: 1` when a result must be reproducible.

Both algorithms are also available as `.write` and `.mutate` variants to persist a `SIMILAR_TO` relationship
or an in-memory relationship for downstream use -- on the film graph,
`+gds.nodeSimilarity.write('pm-undirected', {writeRelationshipType: 'SIMILAR_TO', writeProperty: 'score', topK: 1})+` is a typical call -- and both are covered under
https://neo4j.com/docs/graph-data-science/current/algorithms/[GDS Algorithms], which groups similarity and
embedding algorithms together in the same reference.

== Embeddings: FastRP and Node2Vec versus GraphSAGE

An *embedding* turns a node into a short vector of numbers so that nodes in similar graph positions get similar
vectors. Downstream code -- KNN, clustering, a classifier, a vector index -- then works on plain numbers instead
of on graph structure.

*FastRP* and *Node2Vec* are transductive: they produce a fixed vector per node in the graph they were run on,
purely from structure (and optionally node properties), and are fast enough to run on large graphs as a
one-off `mutate`/`write` step. FastRP is a random-projection method: it starts from random vectors and repeatedly
averages them over each node's neighborhood, so after a few hops a node's vector summarizes its surroundings.
Node2Vec instead generates biased random walks and trains a skip-gram model on them, which is slower but captures
walk-based proximity. *GraphSAGE* is inductive -- it trains a model over local neighborhood aggregation
functions, so once trained it can embed nodes it never saw during training (a node added after training, or a
disjoint sub-graph) without retraining. Reach for FastRP or Node2Vec for a quick, cheap structural embedding to
feed clustering, KNN or a pipeline's feature list; reach for GraphSAGE when new nodes will need embeddings on an
ongoing basis without a full re-run, at the cost of a heavier, model-based training step.

[mermaid]
....
flowchart LR
    G["Projected graph"] --> F["FastRP transductive, fast"]
    G --> N["Node2Vec transductive, walk-based"]
    G --> S["GraphSAGE train inductive model"]
    S --> M[("Stored model")]
    M --> S2["GraphSAGE embed new or unseen nodes"]
    F --> V["Vectors per node"]
    N --> V
    S2 --> V
    V --> U["KNN, clustering, classifiers, vector index"]
....

The embedding and pipeline examples below need a graph with enough structure to learn from, which the film graph
does not have. They use a synthetic `:Account` graph of 60 nodes in three groups of twenty, with dense transfers
inside each group and a few between groups. Every account has an `amount` feature and a `label`: accounts of group
0 are flagged `1`, with four deliberate exceptions so the task is not trivial.

[source,cypher]
----
UNWIND range(0, 59) AS i
CREATE (:Account {id: i, grp: i % 3, label: CASE WHEN i % 3 = 0 THEN 1 ELSE 0 END,
                  amount: toFloat((i * 37) % 100)});

MATCH (a:Account), (b:Account)
WHERE a.id < b.id
  AND ((a.grp = b.grp AND (a.id * 7 + b.id * 13) % 5 < 2)
    OR (a.grp <> b.grp AND (a.id * 11 + b.id) % 47 = 0))
CREATE (a)-[:TRANSFER]->(b);

MATCH (a:Account) WHERE a.id IN [3, 12] SET a.label = 0;
MATCH (a:Account) WHERE a.id IN [4, 10] SET a.label = 1;

CALL gds.graph.project('accts', 'Account', {TRANSFER: {orientation: 'UNDIRECTED'}},
                       {nodeProperties: ['label', 'amount']});
----

The generator is deterministic, so the graph has 218 `TRANSFER` relationships, projected as 436 undirected
ones. FastRP, Node2Vec and GraphSAGE then run on it:

[source,cypher]
----
// FastRP: fast structural embedding, mutated onto the in-memory graph as a
// property so it can feed KNN, clustering, or a pipeline feature step.
CALL gds.fastRP.mutate('accts', {
  embeddingDimension: 16, randomSeed: 42, mutateProperty: 'embedding'
})
YIELD nodePropertiesWritten;                      // 60

// Node2Vec: walk-based embedding, streamed
CALL gds.node2vec.stream('accts', {
  embeddingDimension: 8, walkLength: 10, walksPerNode: 5, randomSeed: 42, concurrency: 1
})
YIELD nodeId, embedding
RETURN count(*) AS nodes, size(head(collect(embedding))) AS dimension;   // 60, 8
----

[source,cypher]
----
// GraphSAGE: train an inductive model, then embed any node of a compatible graph.
CALL gds.beta.graphSage.train('accts', {
  modelName: 'sageModel',
  featureProperties: ['amount'],
  embeddingDimension: 8,
  aggregator: 'mean',
  sampleSizes: [5, 3],
  epochs: 3,
  randomSeed: 42,
  concurrency: 1
})
YIELD modelInfo
RETURN modelInfo.modelName AS model, modelInfo.metrics.didConverge AS converged;   // sageModel, true

CALL gds.beta.graphSage.stream('accts', {modelName: 'sageModel'})
YIELD nodeId, embedding
RETURN count(*) AS nodes, size(head(collect(embedding))) AS dimension;             // 60, 8
----

The `sampleSizes` list sets how many neighbors are sampled at each hop (two hops here), and the model learns
how to aggregate their `featureProperties`. The trained model lives in the model catalog (`gds.model.list`), so a
new account added to the graph tomorrow can be embedded by calling `gds.beta.graphSage.stream` again with the same
`modelName` -- no retraining, which is the whole point of the inductive approach. GraphSAGE currently carries the
`beta` namespace in its procedure names.

A quick check of FastRP's usefulness is to run KNN on its output, as in the previous section: on this graph the
most similar pair was accounts `59` and `2` with a cosine similarity of `0.998`, and the runner-up pair `24` and `9` with `0.997`.

== GDS ML pipelines

A GDS *pipeline* packages the repetitive parts of a supervised task -- feature engineering, train/test
splitting, model selection and training -- into a reusable, named object. The two pipeline types are
*node classification* (predict a label on each node, e.g. fraud/not-fraud) and *link prediction* (predict
whether an edge should exist between two nodes, e.g. "will these two accounts transact"). Both follow the
same shape: add one or more feature steps (often embeddings or graph algorithm outputs), configure a
train/test split, add one or more candidate models, `train` to pick and fit the best one, then run the
trained model with `.predict`.

[mermaid]
....
flowchart LR
    C["create pipeline"] --> P["addNodeProperty e.g. fastRP"]
    P --> F["selectFeatures / addFeature"]
    F --> SP["configureSplit test fraction, folds"]
    SP --> M["add model candidates logistic regression, random forest"]
    M --> T["train cross-validate, pick best, evaluate on test"]
    T --> MD[("Trained model in the model catalog")]
    MD --> PR["predict stream, mutate or write"]
....

=== Node classification

The pipeline below predicts the `label` property. FastRP embeddings are computed *inside* the pipeline as a node
property step, so they are recomputed on the training graph and again at prediction time, avoiding leakage from
test nodes into training features.

[source,cypher]
----
CALL gds.beta.pipeline.nodeClassification.create('fraudPipe');

CALL gds.beta.pipeline.nodeClassification.addNodeProperty('fraudPipe', 'fastRP', {
  mutateProperty: 'emb', embeddingDimension: 16, randomSeed: 42
});

CALL gds.beta.pipeline.nodeClassification.selectFeatures('fraudPipe', ['emb', 'amount']);

CALL gds.beta.pipeline.nodeClassification.configureSplit('fraudPipe', {
  testFraction: 0.25, validationFolds: 3
});

CALL gds.beta.pipeline.nodeClassification.addLogisticRegression('fraudPipe', {penalty: 0.1, maxEpochs: 100});
CALL gds.beta.pipeline.nodeClassification.addRandomForest('fraudPipe', {numberOfDecisionTrees: 10});

CALL gds.beta.pipeline.nodeClassification.train('accts', {
  pipeline: 'fraudPipe',
  targetNodeLabels: ['Account'],
  targetProperty: 'label',
  modelName: 'fraudModel',
  metrics: ['F1_WEIGHTED', 'ACCURACY'],
  randomSeed: 42,
  concurrency: 1
})
YIELD modelInfo
RETURN modelInfo.bestParameters AS best,
       modelInfo.metrics.F1_WEIGHTED.outerTrain AS outerTrain,
       modelInfo.metrics.F1_WEIGHTED.test AS test;
----

[source,text]
----
best, outerTrain, test
{maxDepth: 2147483647, minLeafSize: 1, criterion: "GINI", minSplitSize: 2, numberOfDecisionTrees: 10, methodName: "RandomForest", numberOfSamplesRatio: 1.0}, 0.9779, 0.7702
----

Training cross-validates both candidates over three folds, keeps the better one -- the random forest won -- refits
it on the training split and reports the weighted F1 on data it never saw: `0.978` on the training portion but only
`0.770` on the held-out test portion. That gap is the honest signal of overfitting on 60 nodes; report the test
metric, never the training one. Exact values depend on the seed and the engine version.

[source,cypher]
----
CALL gds.beta.pipeline.nodeClassification.predict.stream('accts', {
  modelName: 'fraudModel',
  targetNodeLabels: ['Account'],
  includePredictedProbabilities: true
})
YIELD nodeId, predictedClass, predictedProbabilities
RETURN gds.util.asNode(nodeId).id AS id, predictedClass,
       [p IN predictedProbabilities | round(p * 100) / 100.0] AS probabilities
ORDER BY id LIMIT 5;
----

[source,text]
----
id, predictedClass, probabilities
0, 1, [0.0, 1.0]
1, 0, [0.9, 0.1]
2, 0, [1.0, 0.0]
3, 1, [0.4, 0.6]
4, 0, [0.8, 0.2]
----

Account `3` is the interesting row. It was relabeled `0` in the data, but it sits in group 0 and the model leans
toward `1` with probability `0.6`. In a fraud setting such a disagreement between a stored label and a confident
prediction is exactly the case worth a human look. `predict.mutate` stores the class on the in-memory graph
instead (it wrote 60 values here) and `predict.write` persists it.

=== Link prediction

The link-prediction pipeline learns which node pairs *should* be connected. It hides a fraction of the existing
relationships as positives, samples non-edges as negatives, and trains a classifier on a feature computed from the
two endpoint embeddings. The `hadamard` feature is the element-wise product of the endpoint vectors.

[source,cypher]
----
CALL gds.beta.pipeline.linkPrediction.create('lpPipe');

CALL gds.beta.pipeline.linkPrediction.addNodeProperty('lpPipe', 'fastRP', {
  mutateProperty: 'emb', embeddingDimension: 16, randomSeed: 42
});

CALL gds.beta.pipeline.linkPrediction.addFeature('lpPipe', 'hadamard', {nodeProperties: ['emb']});

CALL gds.beta.pipeline.linkPrediction.configureSplit('lpPipe', {
  testFraction: 0.2, trainFraction: 0.6, validationFolds: 3
});

CALL gds.beta.pipeline.linkPrediction.addLogisticRegression('lpPipe', {penalty: 0.1});

CALL gds.beta.pipeline.linkPrediction.train('accts', {
  pipeline: 'lpPipe',
  modelName: 'lpModel',
  targetRelationshipType: 'TRANSFER',
  metrics: ['AUCPR'],
  randomSeed: 42,
  concurrency: 1
})
YIELD modelInfo
RETURN modelInfo.metrics.AUCPR.outerTrain AS outerTrain, modelInfo.metrics.AUCPR.test AS test;
----

[source,text]
----
outerTrain, test
0.7179, 0.6467
----

The area under the precision-recall curve is `0.72` on the training split and `0.65` on the test split -- better
than guessing but modest, which is expected from a 16-dimensional embedding of a 60-node graph with a single model
candidate. Prediction ranks unseen pairs by probability:

[source,cypher]
----
CALL gds.beta.pipeline.linkPrediction.predict.stream('accts', {
  modelName: 'lpModel', topN: 3, threshold: 0.5
})
YIELD node1, node2, probability
RETURN gds.util.asNode(node1).id AS first, gds.util.asNode(node2).id AS second,
       round(probability * 1000) / 1000.0 AS probability;
----

[source,text]
----
first, second, probability
21, 24, 0.501
36, 39, 0.501
51, 54, 0.501
----

Probabilities barely above the `0.5` threshold are the model admitting it is unsure -- a useful reminder that
pipeline output needs thresholds and review, not blind trust. The pairs are within the same group, which matches
how the data was generated. Link prediction is the engine behind "who should this account be introduced to" and,
inverted, behind detecting transactions that look anomalous given the surrounding graph.

Classification metrics other than `F1_WEIGHTED` (`ACCURACY`, `PRECISION`, `RECALL`, per-class variants) and
regression pipelines for numeric targets exist as well. The node classification and link-prediction pipelines
share the vocabulary above, so everything transfers.

See https://neo4j.com/docs/graph-data-science/current/machine-learning/machine-learning/[GDS Machine Learning
Pipelines] for the full pipeline catalog, including model configuration and evaluation metrics. Embeddings
produced here are also the natural feature source for
xref:database/neo4j/vector-search-and-genai.adoc[Vector Search and GenAI], where they get indexed for
approximate nearest-neighbor retrieval instead of, or alongside, KNN. See
xref:database/vector-rag/embeddings.adoc[] for the contrasting case of text embeddings produced by a language
model rather than these graph/ML pipelines.
