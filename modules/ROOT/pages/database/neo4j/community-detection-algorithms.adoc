= Community detection algorithms
:description: Finding connected pieces, clusters and communities in a graph with the Graph Data Science library -- WCC, SCC, Triangle Count, the Local Clustering Coefficient, Louvain, Label Propagation and Leiden.
:keywords: neo4j, graph data science, gds, community detection, weakly connected components, wcc, strongly connected components, scc, triangle count, local clustering coefficient, louvain, label propagation, leiden

include::partial$ai-disclaimer.adoc[]

Community detection algorithms group nodes into clusters -- weakly related by mutual reachability, densely
interconnected, or both -- without any label telling the algorithm where one group ends and the next begins.
The Graph Data Science (GDS) library ships each of these as a graph algorithm with the same three execution
modes (`stream`, `write`, `mutate`); the examples below use `stream` to return results without persisting
anything back to the graph.

== The running example: a small social network

All examples use ten `:Member` nodes joined by `:FOLLOWS` relationships. Two tightly knit groups of four members
(Ana, Ben, Cleo, Dan and Eva, Fay, Gus, Hal) are linked by a single bridge relationship, and Ivy and Jon follow only
each other, forming a separate island.

[mermaid]
....
flowchart LR
    subgraph G1["Group 1"]
        Ana --- Ben
        Ana --- Cleo
        Ben --- Cleo
        Cleo --- Dan
        Ben --- Dan
    end
    subgraph G2["Group 2"]
        Eva --- Fay
        Eva --- Gus
        Fay --- Gus
        Gus --- Hal
        Fay --- Hal
    end
    Dan --- Eva
    Ivy --- Jon
....

[source,cypher]
----
UNWIND ['Ana','Ben','Cleo','Dan','Eva','Fay','Gus','Hal','Ivy','Jon'] AS n
CREATE (:Member {name: n});

UNWIND [['Ana','Ben'],['Ana','Cleo'],['Ben','Cleo'],['Cleo','Dan'],['Ben','Dan'],['Dan','Eva'],
        ['Eva','Fay'],['Eva','Gus'],['Fay','Gus'],['Gus','Hal'],['Fay','Hal'],['Ivy','Jon']] AS p
MATCH (a:Member {name: p[0]}), (b:Member {name: p[1]})
CREATE (a)-[:FOLLOWS]->(b);

// undirected view for most algorithms, natural direction for SCC
CALL gds.graph.project('friends', 'Member', {FOLLOWS: {orientation: 'UNDIRECTED'}});
CALL gds.graph.project('friends-directed', 'Member', {FOLLOWS: {orientation: 'NATURAL'}});
----

The projection reports `10` nodes and `24` relationships (12 follows, each stored in both directions) for
`friends`, and `10` nodes and `12` relationships for `friends-directed`. Every output below was produced from
this graph. Community ids are arbitrary numbers: algorithms label a community with one of its member ids, so
only the *grouping* is meaningful, never the number.

== Weakly Connected Components (WCC)

WCC treats every relationship as undirected and assigns every node reachable from every other node -- in
either direction -- the same component id. It is the quickest "how many disconnected pieces does this graph
have" check: run it before anything else, because a component boundary caps what any other algorithm below
can find inside it -- Louvain and Leiden can only ever split a component further, never merge across one.

[source,cypher]
----
CALL gds.wcc.stream('friends')
YIELD nodeId, componentId
RETURN gds.util.asNode(nodeId).name AS name, componentId
ORDER BY componentId;
----

For the readable form, group the members of each component:

[source,cypher]
----
CALL gds.wcc.stream('friends')
YIELD nodeId, componentId
RETURN componentId, collect(gds.util.asNode(nodeId).name) AS members
ORDER BY componentId;
----

[source,text]
----
componentId, members
0, ["Ana", "Ben", "Cleo", "Dan", "Eva", "Fay", "Gus", "Hal"]
8, ["Ivy", "Jon"]
----

Two components: the eight-member network and the Ivy-Jon island. `gds.wcc.stats` returns the same information in
summary form (`componentCount` of `2` and a `componentDistribution` with minimum `2` and maximum `8`) without one
row per node. A large singleton or tiny-island count is often the first sign of a data-quality problem such as
identifiers that failed to match.

See https://neo4j.com/docs/graph-data-science/current/algorithms/wcc/[Weakly Connected Components].

== Strongly Connected Components (SCC)

SCC respects relationship direction: two nodes share a component only if each is reachable from the other
by following relationships forward. It is best suited for finding cycles and mutual-dependency clusters in a
directed graph -- circular payment chains, mutual-follow clusters, or cyclic dependencies between services --
that WCC's undirected view would hide inside one large, unhelpful component.

[source,cypher]
----
CALL gds.scc.stream('friends-directed')
YIELD nodeId, componentId
RETURN gds.util.asNode(nodeId).name AS name, componentId
ORDER BY componentId;
----

SCC needs the directed projection (`friends-directed`). In this graph every follow points forward and none points
back, so no member can be reached from a node it reaches: each of the ten members is its own strongly connected
component, and a query such as `WHERE size(members) > 1` returns nothing. That absence is the useful result -- it
means there are no mutual-follow loops. When a cycle does exist, the members of the cycle share a `componentId`;
the use-cases page shows one for a service dependency graph.

See https://neo4j.com/docs/graph-data-science/current/algorithms/strongly-connected-components/[Strongly
Connected Components].

== Triangle Count and the Local Clustering Coefficient

Triangle Count counts, per node, how many closed triples of mutually connected neighbors it takes part in --
best suited as a cheap, local signal of how tightly-knit a node's neighborhood is, and as a building block
the algorithms below rely on internally. The Local Clustering Coefficient normalizes that count against how
many triangles the node's neighborhood *could* form, giving a 0-1 score comparable across nodes of very
different degree.

[source,cypher]
----
CALL gds.triangleCount.stream('friends')
YIELD nodeId, triangleCount
RETURN gds.util.asNode(nodeId).name AS name, triangleCount
ORDER BY triangleCount DESC;
----

[source,cypher]
----
CALL gds.localClusteringCoefficient.stream('friends')
YIELD nodeId, localClusteringCoefficient
RETURN gds.util.asNode(nodeId).name AS name, localClusteringCoefficient
ORDER BY localClusteringCoefficient DESC;
----

[source,text]
----
name     triangleCount   localClusteringCoefficient
"Ben"    2               0.67
"Cleo"   2               0.67
"Fay"    2               0.67
"Gus"    2               0.67
"Ana"    1               1.0
"Dan"    1               0.33
"Eva"    1               0.33
"Hal"    1               1.0
"Ivy"    0               0.0
"Jon"    0               0.0
----

The two result sets are merged into one table above for compactness; they come from the two queries. Ana has a
single triangle but a coefficient of `1.0`: she has only two neighbors (Ben and Cleo) and they follow each other,
so every possible triangle exists. Dan and Eva have one triangle each but a coefficient of `0.33` -- they also
touch the bridge relationship, and a node with three neighbors could form three triangles. The coefficient is
therefore the better measure of how *cohesive* a neighborhood is, while the raw count rewards high degree.
Bridge nodes such as Dan and Eva show the lowest non-zero coefficients, a cheap structural hint that they sit
between groups.

See https://neo4j.com/docs/graph-data-science/current/algorithms/triangle-count/[Triangle Count] and
https://neo4j.com/docs/graph-data-science/current/algorithms/local-clustering-coefficient/[Local Clustering
Coefficient].

== Louvain

Louvain repeatedly merges nodes into communities that locally maximize modularity, then collapses each
community into a single node and repeats on that coarser graph. It is best suited for a fast, good-enough
multi-level community structure on large graphs, and it exposes the intermediate levels so a caller can pick
a coarser or finer partition without rerunning the algorithm.

[source,cypher]
----
CALL gds.louvain.stream('friends')
YIELD nodeId, communityId
RETURN gds.util.asNode(nodeId).name AS name, communityId
ORDER BY communityId;
----

Louvain optimizes *modularity*: a score between -0.5 and 1 comparing the fraction of relationships inside
communities with what a random graph of the same degrees would give. The first phase moves each node to the
neighboring community that raises modularity most; the second collapses communities into super-nodes and repeats.

[source,cypher]
----
CALL gds.louvain.stream('friends', {includeIntermediateCommunities: true})
YIELD nodeId, communityId, intermediateCommunityIds
RETURN gds.util.asNode(nodeId).name AS name, communityId, intermediateCommunityIds
ORDER BY communityId, name;
----

[source,text]
----
name, communityId, intermediateCommunityIds
"Ana", 1, [1]
"Ben", 1, [1]
"Cleo", 1, [1]
"Dan", 1, [1]
"Eva", 7, [7]
"Fay", 7, [7]
"Gus", 7, [7]
"Hal", 7, [7]
"Ivy", 9, [9]
"Jon", 9, [9]
----

Louvain recovers exactly the three groups built into the data. `gds.louvain.stats` reports `communityCount` 3, a
final `modularity` of about `0.4896` and a single level (`ranLevels` is `1`) -- a graph this small needs only one
aggregation round. On bigger graphs `intermediateCommunityIds` lists one community id per level, which lets a caller
choose a coarser or finer partition afterwards.

See https://neo4j.com/docs/graph-data-science/current/algorithms/louvain/[Louvain].

== Label Propagation

Label Propagation starts every node with its own unique label and repeatedly relabels each node to whatever
label a plurality of its neighbors hold, until labels stop changing. It is best suited for near-linear-time
community detection on very large graphs where Louvain's or Leiden's iterative refinement would be too slow,
at the cost of less stable, sometimes trivially large communities.

[source,cypher]
----
CALL gds.labelPropagation.stream('friends')
YIELD nodeId, communityId
RETURN gds.util.asNode(nodeId).name AS name, communityId
ORDER BY communityId;
----

On this graph the run grouped the bridge-connected eight members into *one* community (and Ivy and Jon into
another), merging two groups that Louvain separated:

[source,text]
----
communityId, members
16, ["Ana", "Ben", "Cleo", "Dan", "Eva", "Fay", "Gus", "Hal"]
24, ["Ivy", "Jon"]
----

That is label propagation's trade-off in action. Each node adopts the most common label among its neighbors, so a
single bridge can let one label flood across both groups depending on the order in which nodes are processed.
The algorithm is non-deterministic and optimizes nothing globally, which is why its result can vary between runs
and why it is the cheapest, not the most precise, option. It also accepts seed properties, so a partial known
labeling can steer it.

See https://neo4j.com/docs/graph-data-science/current/algorithms/label-propagation/[Label Propagation].

== Leiden

Leiden refines Louvain's merge step with an additional partition-refinement phase that guarantees every
community it produces stays internally connected. It is Louvain's more-stable successor: it fixes Louvain's
known failure mode of occasionally producing internally-disconnected communities, and it is the modern
default choice whenever both are available.

[source,cypher]
----
CALL gds.leiden.stream('friends')
YIELD nodeId, communityId
RETURN gds.util.asNode(nodeId).name AS name, communityId
ORDER BY communityId;
----

Leiden takes a `randomSeed` for reproducible runs. Collecting the members per community gives the grouping
directly:

[source,cypher]
----
CALL gds.leiden.stream('friends', {randomSeed: 19})
YIELD nodeId, communityId
RETURN communityId, collect(gds.util.asNode(nodeId).name) AS members
ORDER BY communityId;
----

[source,text]
----
communityId, members
1, ["Ana", "Ben", "Cleo", "Dan"]
7, ["Eva", "Fay", "Gus", "Hal"]
9, ["Ivy", "Jon"]
----

Three communities with the same modularity as Louvain (about `0.4896`). On such a clean graph the two agree; the
difference appears on large noisy graphs, where Leiden's refinement phase keeps every community connected.

See https://neo4j.com/docs/graph-data-science/current/algorithms/leiden/[Leiden].

== Chaining algorithms with mutate

Community ids are most useful as a property that other algorithms and queries can read. Running Leiden in `mutate`
mode stores them on the in-memory graph, `gds.modularity` then scores the partition per community, and a final
`write` persists the property so ordinary Cypher can use it:

[source,cypher]
----
CALL gds.leiden.mutate('friends', {randomSeed: 19, mutateProperty: 'community'})
YIELD communityCount, nodePropertiesWritten;      // 3, 10

CALL gds.modularity.stream('friends', {communityProperty: 'community'})
YIELD communityId, modularity
RETURN communityId, round(modularity * 1000) / 1000.0 AS modularity
ORDER BY communityId;

CALL gds.leiden.write('friends', {randomSeed: 19, writeProperty: 'community'})
YIELD communityCount, nodePropertiesWritten;      // 3, 10

MATCH (m:Member)
RETURN m.community AS community, collect(m.name) AS members
ORDER BY community;
----

[source,text]
----
communityId, modularity
1, 0.207
7, 0.207
9, 0.076
----

The per-community modularity shows the two four-member groups contribute equally and the Ivy-Jon island very
little in absolute terms -- two nodes cannot hold much of the graph's relationship mass. The k-core decomposition
(`gds.kcore.stream`) offers a complementary view: it assigned core value `2` to the eight-member network (every
member keeps at least two neighbors after peeling) and `1` to the Ivy-Jon island.

== Choosing among them

[cols="1,3"]
|===
| Algorithm | Best suited for

| WCC | A quick "how many disconnected pieces does this graph have" check, and a required first pass before any of the algorithms below.
| SCC | Cycles and mutual-dependency clusters in a *directed* graph.
| Triangle Count | A cheap local density signal per node, and an internal building block for other algorithms.
| Local Clustering Coefficient | A degree-normalized 0-1 density score, comparable across nodes.
| Louvain | Fast, good, multi-level community structure on large graphs, with inspectable intermediate levels.
| Label Propagation | Near-linear-time community detection at very large scale, when some instability is acceptable.
| Leiden | Louvain's more-stable successor -- guaranteed internally-connected communities; the modern default.
|===

== Where this fits in a larger pipeline

Community detection is rarely the end goal by itself -- it is usually a filtering or feature-generation step
inside a larger analytical or investigative pipeline. See
xref:database/neo4j/use-cases-and-algorithms-in-practice.adoc[] for a worked fraud-ring detection example
that layers WCC, Louvain and Betweenness Centrality: WCC first isolates the connected pieces worth
examining, Louvain finds dense communities within each piece, and Betweenness Centrality then ranks the
nodes that bridge those communities as the accounts most likely to be laundering funds between rings.

For the full algorithm catalog, including centrality, similarity and path-finding algorithms not covered
here, see https://neo4j.com/docs/graph-data-science/current/algorithms/[GDS Algorithms] -- its
community-detection section covers every algorithm on this page plus a few more specialized variants
(Modularity Optimization, Approximate Maximum k-cut, Speaker-Listener Label Propagation) not detailed here.
