= Security & administration
:description: Neo4j access control -- native, LDAP and OIDC authentication, role-based privileges with GRANT/DENY/REVOKE and the built-in roles -- plus a brief overview of multi-database, backup/restore, Bolt+TLS encryption and auditing.
:keywords: neo4j, security, authentication, authorization, RBAC, native users, LDAP, OIDC, built-in roles, GRANT, DENY, REVOKE, privileges, multi-database, backup, restore, neo4j-admin, bolt, TLS, encryption, auditing, security event log

include::partial$ai-disclaimer.adoc[]

Neo4j controls access in two layers: *authentication* decides who a connecting client is, and
*authorization* -- a role-based privilege system -- decides what that identity may read, write or
administer. This page covers both, plus the administration tasks (multi-database, backup/restore,
transport encryption and auditing) that sit alongside them.

[mermaid]
....
flowchart LR
    C["Client driver or browser"] -->|"Bolt over TLS"| AU{"Authentication native, LDAP, OIDC"}
    AU -->|identity| RL["Roles of the user"]
    RL --> PR{"Privileges GRANT minus DENY"}
    PR -->|allowed| DBS[("Database, graph, label, relationship type, property")]
    PR -.->|denied| ERR["Access denied"]
    AU -.->|failed login| LOG["Security event log"]
    PR -.-> LOG
....

[NOTE]
====
Role-based access control, `SHOW PRIVILEGES`, `CREATE DATABASE`, composite databases and online backup are *Enterprise
Edition* features. On a Community Edition server -- the default `neo4j` Docker image used for the examples in this
section -- native user management works, but the statements that need Enterprise answer with
`not supported in this edition`. The Enterprise statements below were checked against the Cypher parser (they are
recognized and rejected only because of the edition), and the native-user and `neo4j-admin dump`/`load` examples were
executed end to end.
====

== Authentication: native, LDAP and OIDC

A fresh installation ships one native user, `neo4j`, that must change its password on first login. Beyond
that default, three authentication providers can be configured, and more than one can be enabled at once so
different clients authenticate different ways
(https://neo4j.com/docs/operations-manual/current/authentication-authorization/[Auth & Authorization]):

* *Native* -- users and their hashed passwords are stored inside Neo4j itself, managed with
  `CREATE USER` / `ALTER USER` / `DROP USER`.
* *LDAP* -- delegates authentication (and optionally role mapping) to a directory server, so credentials
  never live in Neo4j.
* *OIDC* -- delegates to an external OpenID Connect identity provider (Okta, Entra ID, Keycloak, ...) for
  single sign-on, mapping token claims to Neo4j roles.

[source,cypher]
----
// Native user management -- run against the system database.
CREATE USER alice SET PASSWORD 'a-temporary-value' CHANGE REQUIRED
  SET STATUS ACTIVE;

ALTER USER alice SET PASSWORD CHANGE NOT REQUIRED;

SHOW USERS YIELD user, roles, suspended;

DROP USER alice;
----

On a Community server the first statement creates the user and `SHOW USERS` lists both accounts:

[source,text]
----
user, roles, passwordChangeRequired, suspended, home
"alice", NULL, FALSE, NULL, NULL
"neo4j", NULL, FALSE, NULL, NULL
----

The `roles`, `suspended` and `home` columns are `NULL` because those features are Enterprise-only; the clause
`SET STATUS ACTIVE`/`SUSPENDED` is rejected with `+'SET STATUS' is not supported in community edition+`. A user changes
their own password with `+ALTER CURRENT USER SET PASSWORD FROM 'old' TO 'new'+`; an administrator resets someone else's
with `ALTER USER`. Because a Community server has a single privilege level (every authenticated user can do everything),
it is suitable for development, not for exposing to untrusted users.

LDAP and OIDC are turned on in `neo4j.conf` (`dbms.security.authentication_providers`,
`dbms.security.authorization_providers`); the directory/provider connection details and the claim-to-role
mapping live alongside them. That configuration surface is large enough that it is only linked here, not
reproduced -- see
https://neo4j.com/docs/operations-manual/current/authentication-authorization/[Auth & Authorization] for the
full provider setup.

== Role-based access control: built-in roles and privileges

Every user is granted one or more *roles*, and every role holds a set of *privileges* -- each privilege
names an action (`MATCH`, `TRAVERSE`, `WRITE`, `CREATE INDEX`, ...), a target (a database, a graph, a
label, a relationship type, a property) and an effect (`GRANT`, `DENY`). A user's effective access is the
union of their roles' grants, minus any deny -- *deny always wins over grant*, even from a different role
held by the same user
(https://neo4j.com/docs/operations-manual/current/authentication-authorization/manage-privileges/[Manage
Privileges]).

Six roles exist out of the box
(https://neo4j.com/docs/operations-manual/current/authentication-authorization/built-in-roles/[Built-in
Roles]): `PUBLIC`, which every user holds implicitly and which grants access to the default database, and five that
build on each other:

[cols="1,3"]
|===
| Role | Grants

| `reader` | Read-only access to every graph.
| `editor` | Everything `reader` can do, plus writing to existing nodes, relationships and properties -- but not creating new labels, relationship types or property names.
| `publisher` | Everything `editor` can do, plus creating new labels, relationship types and property names.
| `architect` | Everything `publisher` can do, plus index and constraint management.
| `admin` | Everything `architect` can do, plus user, role, privilege and database administration over the whole DBMS.
|===

[mermaid]
....
flowchart LR
    reader --> editor --> publisher --> architect --> admin
....

Each role is a strict superset of the one before it, so assigning the lowest role that covers a job is the safe default.
Custom roles are for everything the ladder does not express, such as "read only `Movie` nodes in one database".

Custom roles compose the same privilege grammar. A typical pattern is a purpose-built role scoped to one
label and one database:

[source,cypher]
----
// Create a role that may only read Movie nodes in the "moviesdb" database.
CREATE ROLE movieReader;

GRANT ACCESS ON DATABASE moviesdb TO movieReader;
GRANT MATCH {*} ON GRAPH moviesdb NODE Movie TO movieReader;

// Assign it to a user, then confirm what the role can do.
GRANT ROLE movieReader TO alice;
SHOW ROLE movieReader PRIVILEGES;
----

`DENY` overrides any broader `GRANT` -- useful for carving an exception out of a wide role without
rewriting it:

[source,cypher]
----
// Members of movieReader may traverse Employee nodes, but can never read the salary
// property, even if a broader grant is added later.
DENY READ {salary} ON GRAPH moviesdb NODE Employee TO movieReader;
----

Privileges are removed with the mirror-image `REVOKE`, which takes an optional `GRANT` or `DENY` to remove
only that half:

[source,cypher]
----
REVOKE GRANT MATCH {*} ON GRAPH moviesdb NODE Movie FROM movieReader;
REVOKE DENY READ {salary} ON GRAPH moviesdb NODE Employee FROM movieReader;
----

`SHOW PRIVILEGES` audits the full picture across every role:

[source,cypher]
----
SHOW ALL PRIVILEGES YIELD role, graph, segment, action, access;
----

Compare this label/relationship-scoped grant model with
xref:database/mongodb/security.adoc[MongoDB's built-in and custom roles], which scope privileges to actions
and resources (a database, a collection, or a cluster) rather than to graph labels and properties -- the
same GRANT/DENY-style idea, applied to a different data model.

== Administration: multi-database, backup, encryption and auditing

This section is an overview only -- the full treatment of multi-database topology, Fabric and clustering
lives in xref:database/neo4j/clustering-and-multi-database.adoc[].

*Multi-database.* A single DBMS instance hosts several independent databases, each with its own data,
schema and (via the privilege grammar above) its own access rules. `SHOW DATABASES` lists them; `CREATE
DATABASE` / `DROP DATABASE` manage the set.

[source,cypher]
----
CREATE DATABASE moviesdb IF NOT EXISTS;
SHOW DATABASES YIELD name, currentStatus, role;
STOP DATABASE moviesdb;
----

On Community Edition `SHOW DATABASES` works and lists the two databases every server has, `neo4j` and `system`, both
`online` and `primary`; `CREATE DATABASE` and `STOP DATABASE` report that they need Enterprise Edition.

*Backup and restore.* There are two mechanisms, and which one is available depends on the edition.

* `neo4j-admin database dump` writes a single-file archive of a database and `neo4j-admin database load` restores it.
  Both are available in Community Edition, but they work on a database that is *offline*, so they suit migrations and
  scheduled maintenance windows rather than continuous protection.
* `neo4j-admin database backup` takes an online backup of a running database and `neo4j-admin database restore`
  loads a backup chain into an empty database. Online backup is an Enterprise feature (on Aura, backups are managed for
  you).

[source,shell]
----
# https://neo4j.com/docs/operations-manual/current/backup-restore/
# Enterprise: online backup and restore
neo4j-admin database backup moviesdb --to-path=/backups/moviesdb
neo4j-admin database restore moviesdb --from-path=/backups/moviesdb --overwrite-destination=true

# Community and Enterprise: offline dump and load
neo4j-admin database dump neo4j --to-path=/backups/dumps
neo4j-admin database load neo4j --from-path=/backups/dumps --overwrite-destination=true
----

The dump and load pair was run with the Docker image: a throwaway container with a named volume mounted at `/data`
created two nodes, the container was stopped (the store must not be in use), and a second, short-lived container ran
the admin commands against the same volume:

[source,shell]
----
docker run --rm -v neo4j-data:/data neo4j:latest bash -c \
  'mkdir -p /data/dumps && neo4j-admin database dump neo4j --to-path=/data/dumps && ls -la /data/dumps'
----

[source,text]
----
Files: 36/36, data: 100.0%
Done: 36 files, 257.9MiB processed in 0.216 seconds.
... Dump completed successfully
-rw-r--r-- 1 neo4j neo4j 12737 Nov 10 13:50 neo4j.dump
----

`neo4j-admin database info neo4j` on the same volume reported `Database in use: false`, `Store needs recovery: false`
and `Last committed transaction id: 6`, a quick consistency signal before taking or loading a dump. Running the dump
against a live server instead fails with `+The database is in use. Stop database 'neo4j' and try again+`, and
`neo4j-admin database check` verifies store consistency. Whatever the mechanism, a backup is only a backup once a
restore has been rehearsed.

*Bolt+TLS.* Client-driver traffic can be encrypted independently of intra-cluster traffic. Enable it in
`neo4j.conf` (`server.bolt.tls_level=REQUIRED`, plus a certificate under `server.directories.certificates`),
then require it from the driver:

[source,cypher]
----
// Driver connection URI schemes select the TLS behaviour, not a Cypher statement:
// neo4j+s://   -- encrypted, full certificate trust
// neo4j+ssc:// -- encrypted, self-signed certificates accepted
// neo4j://     -- unencrypted (only for trusted internal networks)
----

A server restart is required after changing the Bolt TLS settings. `SHOW SETTINGS` reads the effective configuration
from Cypher, which is the quickest way to confirm what is actually in force:

[source,cypher]
----
SHOW SETTINGS YIELD name, value
WHERE name STARTS WITH 'server.bolt'
RETURN name, value;
----

*Auditing.* The security event log records authentication attempts and privilege-relevant administrative
actions (user/role/privilege changes, database lifecycle commands) to a dedicated log file, configured
under `+db.logs.security.*+` in `neo4j.conf`. It is a durable trail for who did what, separate from the
regular query log.

Continue with xref:database/neo4j/clustering-and-multi-database.adoc[] for causal clustering, Fabric and
the full multi-database story.
