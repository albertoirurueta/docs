The six connectors with their own pages in this section (Oracle, PostgreSQL, MySQL, MariaDB, SQL Server and MongoDB)
cover most migrations. Legacy estates are rarely that tidy, though: an insurance back office still runs on Db2 for z/OS
behind COBOL programs, a retail chain has Informix in its stores, a telemetry platform grew on Cassandra, and a
newer service already sits on CockroachDB or Spanner. This page covers every other Debezium source connector, in the
same way for each one: what it captures, its main prerequisite, its maturity, and when it shows up in a migration. The
Db2 connector gets the most detail, because Db2 is the most common legacy source among them.

Checked on 2026-11-09 against Debezium 3.7.1.Final. Maturity labels are copied from the two official places that
publish them, the
https://debezium.io/documentation/reference/stable/connectors/index.html[Source Connectors overview] of the 3.7
reference documentation and the https://debezium.io/databases/[Supported databases] page, as they read on that date.
Tested versions are copied from https://debezium.io/releases/3.7/[the 3.7 release page]. Nothing on this page was run:
the configurations are derived from the official connector pages.

== Maturity: what "incubating" means

An **incubating** connector, in the words of the connector overview, has been released for preview purposes and is
subject to changes that may not always be backward compatible. In a migration that means:

* configuration properties, event formats and topic names can change between minor releases, so pin the connector
  version and re-test the pipeline before every upgrade;
* there is less field experience, so plan a longer rehearsal of snapshot, restart and failure scenarios
  (xref:database/migration/testing-cdc-pipelines.adoc[Testing CDC Pipelines]);
* commercial support offerings may exclude it (check the vendor's own list; see
  xref:database/migration/cloud-and-managed-services.adoc[Cloud Databases & Managed Kafka]).

A migration is a project with an end date, and an incubating connector can still be the right tool: the alternative is
often a hand-written polling job with worse guarantees. Use it with the precautions above, and keep a reconciliation job
(xref:database/migration/verification-and-reconciliation.adoc[Verification & Reconciliation]) running until cut-over.

Where the two official sources disagree:

* **Cassandra.** The connector overview lists "Cassandra" without the incubating label, next to the stable connectors,
  while the supported databases page labels both Cassandra 4 and Cassandra 5 as *incubating*. Treat it as incubating
  when you plan: the stricter label is the safer one.
* **Db2 for z/OS.** The supported databases page shows one stable entry, "Db2 for LUW / zOS". The Db2 connector page
  itself says that using the connector with Db2 for z/OS is *incubating* (and that it has been tested with Db2 for
  Linux). So Db2 LUW is stable and Db2 for z/OS is incubating.
* **Db2 for IBM i, SQLite and TiDB** appear only on the supported databases page. The Db2 for IBM i entry links to a
  connector page that returned "Page not found" for both `stable` and `3.7` on 2026-11-09; SQLite and TiDB have no
  documentation link at all. Their only other official source is their GitHub repository.
* **Cassandra 3** is listed as "No longer supported" on the 3.7 release page: the Cassandra 3 connector was removed in
  3.7.

The `quay.io/debezium/connect:3.7.1.Final` image already contains the MongoDB, MySQL, MariaDB, PostgreSQL, SQL Server,
Oracle and JDBC sink connectors and, from the additional connectors, Db2, Spanner, Vitess, Informix, Db2 for IBM i and
CockroachDB (according to its Dockerfile in the `debezium/container-images` repository). Cassandra, YashanDB, Ingres
and Milvus are not in the image and must be installed from their plug-in archives. Licensed JDBC drivers are a separate
matter: the Db2 and Informix connector archives do not include their drivers.

== Db2 for Linux, UNIX and Windows, and Db2 for z/OS

=== What it captures and how

The Db2 connector is built on Db2 **SQL Replication**, the ASN Capture and Apply programs. The capture program reads the
Db2 log and writes the changes of every table that is *in capture mode* into a *change-data (CD) table*. The Debezium
connector queries those CD tables with SQL, much as the SQL Server connector queries SQL Server's change tables. It
takes a consistent snapshot of the tables in capture mode first, then streams from the CD tables, recording the LSN of
the last change as its offset.

[mermaid]
....
flowchart LR
    Cobol[COBOL batch and CICS programs] -->|EXEC SQL UPDATE| Db2[(Db2 tables BOOKSHOP.*)]
    Db2 --> Log[(Db2 recovery log)]
    Asn[ASN capture program asncap] -->|reads| Log
    Asn -->|writes| CD[(Change-data tables in schema ASNCDC)]
    Dbz[Debezium Db2 connector] -->|SQL queries| CD
    Dbz -->|change events| Kafka[(Kafka topics legacy-db2.*)]
....

=== Main prerequisites

* **A licence for SQL Replication.** The connector page states that the replication tools ship with Db2, but using SQL
  replication for the Debezium connector requires a separate licence to IBM InfoSphere Data Replication (IIDR), even
  though IIDR itself does not need to be installed. Clear this with your legal department before you plan the
  migration around it.
* **Tables in capture mode.** A Db2 administrator compiles and installs the Debezium management UDFs (from the
  `debezium-examples` repository), creates the ASN control tables, starts the ASN agent and puts each table into capture
  mode. Alternatively, the same is done with Db2's own replication control commands.
* **The Db2 JDBC driver**, which is not part of the connector archive for licensing reasons.
* **For z/OS**: `db2.platform=ZOS`, and, if the control and CD tables are not in `ASNCDC`, the `cdc.control.schema` and
  `cdc.change.tables.schema` properties. Db2 for z/OS versions that use 6-byte LSNs cannot be used.

.Put the Bookshop tables into capture mode with the Debezium management UDFs (Db2 LUW)
[source,sql]
----
-- After compiling asncdc and running asncdc_UDF.sql, asncdctables.sql and asncdcaddremove.sql
-- as described on the Debezium Db2 page:
VALUES ASNCDC.ASNCDCSERVICES('start','asncdc');

CALL ASNCDC.ADDTABLE('BOOKSHOP', 'BOOK');
CALL ASNCDC.ADDTABLE('BOOKSHOP', 'AUTHOR');
CALL ASNCDC.ADDTABLE('BOOKSHOP', 'ORDERS');
CALL ASNCDC.ADDTABLE('BOOKSHOP', 'ORDER_LINE');

-- Required after adding or removing tables
VALUES ASNCDC.ASNCDCSERVICES('reinit','asncdc');
VALUES ASNCDC.ASNCDCSERVICES('status','asncdc');
----
Reference: https://debezium.io/documentation/reference/stable/connectors/db2.html#putting-tables-in-capture-mode[Debezium -- Db2: putting tables into capture mode]

=== A Bookshop configuration on Db2

If the Bookshop legacy schema lived in Db2 instead of Oracle (schema `BOOKSHOP` in a database called `BOOKSHOP`), the
source connector would look like this. The topic prefix `legacy-db2` keeps it apart from the Oracle pipeline.

.bookshop-db2-source connector configuration
[source,json]
----
{
  "name": "bookshop-db2-source",
  "config": {
    "connector.class": "io.debezium.connector.db2.Db2Connector",
    "tasks.max": "1",
    "database.hostname": "db2",
    "database.port": "50000",
    "database.user": "dbzuser",
    "database.password": "${file:/opt/kafka/secrets/db2.properties:password}",
    "database.dbname": "BOOKSHOP",
    "db2.platform": "LUW",
    "topic.prefix": "legacy-db2",
    "table.include.list": "BOOKSHOP.BOOK,BOOKSHOP.AUTHOR,BOOKSHOP.ORDERS,BOOKSHOP.ORDER_LINE",
    "snapshot.mode": "initial",
    "schema.history.internal.kafka.bootstrap.servers": "kafka:9092",
    "schema.history.internal.kafka.topic": "legacy-db2.schema-history",
    "heartbeat.interval.ms": "10000",
    "decimal.handling.mode": "precise"
  }
}
----
Reference: https://debezium.io/documentation/reference/stable/connectors/db2.html#db2-connector-properties[Debezium -- Db2 connector properties]
and https://debezium.io/documentation/reference/stable/connectors/db2.html#db2-example-configuration[Db2 connector configuration example]

For Db2 for z/OS, change `db2.platform` to `ZOS` and add `cdc.control.schema` and `cdc.change.tables.schema` if the
capture control and change-data tables are not in the default `ASNCDC` schema. Like SQL Server and Oracle, the Db2
connector keeps a schema history topic, so the rules on
xref:database/migration/schema-changes-during-migration.adoc[Handling Schema Changes] apply.

=== What goes wrong on Db2

* **Change-data tables grow without limit.** Db2 does not delete CD rows that Debezium has read. Pruning is normally
  driven by the Apply program; if Apply is stopped to save resources, pruning stops too. The connector page lists the
  `IBMSNAP_REGISTER`, `IBMSNAP_PRUNCNTL`, `IBMSNAP_PRUNE_SET` and `IBMSNAP_CAPPARMS` (`PRUNE_INTERVAL`) settings that
  must be correct for the capture program to prune. Check them before the first production run.
* **Capture-agent load.** `COMMIT_INTERVAL` (default 30 seconds) and `SLEEP_INTERVAL` (default 5 seconds) in
  `IBMSNAP_CAPPARMS` trade latency against CPU on the legacy server. A 30-second commit interval means up to 30 seconds of
  latency before Debezium can see a change.
* **Schema changes.** CD table schemas are static. As on SQL Server, a DBA must update the CD table when the source table
  changes, with an offline procedure (stop Debezium, apply, re-add the table to capture mode) or an online one. Run all
  DDL for a table in one batch.
* **No recent backup.** The setup procedure requires a recent backup so that the ASN agents have a starting point.
* **TRUNCATE.** The JDBC sink cannot process standard `TRUNCATE` events coming from Db2; the sink documentation suggests
  `+ALTER TABLE ... ACTIVATE NOT LOGGED INITIALLY WITH EMPTY TABLE+` as the alternative statement.

=== Db2 behind COBOL: when it appears in a migration

Db2 is usually the database of a mainframe application written in COBOL, where business rules live in programs that
use embedded SQL. Capturing the Db2 tables with Debezium lets a new service receive every change made by those programs
without touching them, which is the data side of a mainframe strangler fig. Two pages of the COBOL reference give the
other side of the picture:

* xref:programming-languages/cobol/embedded-sql-and-db2.adoc[Embedded SQL and Db2] explains how the legacy programs read
  and write the tables (host variables, cursors, `COMMIT` in batch programs). The commit behaviour of those programs
  decides the transaction boundaries that Debezium sees: a batch job that commits every 1,000 rows produces bursts of
  1,000 change events.
* xref:programming-languages/cobol/modernization-strategies.adoc[Modernization Strategies] places CDC among the
  modernization options (keep and extend, strangler fig on a mainframe) and lists the data migration concerns, such as
  EBCDIC conversion and packed-decimal fields, that you still have to handle when the change events arrive.

Data that a COBOL system keeps in VSAM files or sequential datasets, rather than in Db2, is out of Debezium's reach.
Those need a file export or a mainframe replication product; see
xref:database/migration/migration-strategies.adoc[Migration Strategies].

== Db2 for IBM i

The supported databases page lists a **Db2 for IBM i** connector as **incubating**, tested with IBM i 7.4. It reads the
IBM i **journal**, which is the system's own change log for database files. The connector's GitHub repository lists the
object authorities that the CDC user needs on the journal library, the journal receivers and the application library.
The connector is included in the `quay.io/debezium/connect:3.7.1.Final` image, but no 3.7 reference page was reachable on
2026-11-09, so check the repository and the release notes before you rely on any property name.

When it appears in a migration: AS/400 and IBM i applications (often RPG or COBOL) that are being replaced piece by
piece. The journal must cover every file you need to capture.

.IBM i authorities for the CDC user (from the connector README)
[source,text]
----
GRTOBJAUT OBJ(<JRNLIB>) OBJTYPE(*LIB) USER(<CDC_USER>) AUT(*EXECUTE)
GRTOBJAUT OBJ(<JRNLIB>/*ALL) OBJTYPE(*JRNRCV) USER(<CDC_USER>) AUT(*USE)
GRTOBJAUT OBJ(<JRNLIB>/<JRN>) OBJTYPE(*JRN) USER(<CDC_USER>) AUT(*USE *OBJEXIST)
GRTOBJAUT OBJ(<PROJECT_LIB>) OBJTYPE(*LIB) USER(<CDC_USER>) AUT(*EXECUTE)
GRTOBJAUT OBJ(<PROJECT_LIB>/*ALL) OBJTYPE(*FILE) USER(<CDC_USER>) AUT(*USE)
----
Reference: https://github.com/debezium/debezium-connector-ibmi[debezium/debezium-connector-ibmi (GitHub)]
and https://debezium.io/databases/[Debezium -- Supported databases]

== Informix (incubating)

The Informix connector uses the **Informix Change Data Capture API**. It snapshots the tables it captures, then streams
from the CDC API, recording the LSN as its offset. It is labelled incubating on both official pages and is tested with
Informix 12, 14 and 15.

Main prerequisite: as user `informix`, run the `syscdcv1.sql` script from `$INFORMIXDIR/etc` to create the `syscdcv1`
database, and set `DB_LOCALE` to the locale of the captured database. The Informix JDBC driver and the Informix Change
Stream client are not in the connector archive and must be added next to the connector JARs.

.bookshop-informix-source connector configuration
[source,json]
----
{
  "name": "bookshop-informix-source",
  "config": {
    "connector.class": "io.debezium.connector.informix.InformixConnector",
    "database.hostname": "informix",
    "database.port": "9088",
    "database.user": "informix",
    "database.password": "${file:/opt/kafka/secrets/informix.properties:password}",
    "database.dbname": "bookshop",
    "topic.prefix": "legacy-informix",
    "table.include.list": "bookshop.informix.book,bookshop.informix.orders",
    "schema.history.internal.kafka.bootstrap.servers": "kafka:9092",
    "schema.history.internal.kafka.topic": "legacy-informix.schema-history"
  }
}
----
Reference: https://debezium.io/documentation/reference/stable/connectors/informix.html#informix-example-configuration[Debezium -- Informix connector configuration example]
and https://debezium.io/documentation/reference/stable/connectors/informix.html#setting-up-informix[Setting up Informix]

When it appears in a migration: point-of-sale and store systems, and older ERP installations. The schema change event
format of this connector is itself marked as incubating on its page.

== Cassandra 4 and 5

The Cassandra connector is different from every other Debezium source: it does **not** run on Kafka Connect. It is a
standalone JVM process deployed on **each Cassandra node**, which watches the node's `cdc_raw` directory, reads the
commit log segments placed there, sends one change event per row-level change to Kafka with a Kafka producer, and then
deletes the processed segments. There are separate plug-ins for Cassandra 4 and Cassandra 5; the Cassandra 3 connector
was removed in 3.7. See the table above for the maturity disagreement (stable-looking in the connector overview,
incubating on the supported databases page).

Main prerequisites: CDC enabled on every node in `cassandra.yaml`, and on every captured table.

.Enable CDC on the node (cassandra.yaml) and on a table (CQL)
[source,yaml]
----
# cassandra.yaml on every node
cdc_enabled: true
# defaults shown for reference
cdc_raw_directory: $CASSANDRA_HOME/data/cdc_raw
cdc_free_space_in_mb: 4096
cdc_free_space_check_interval_ms: 250
# then, in cqlsh:
#   ALTER TABLE bookshop.page_view WITH cdc=true;
----
Reference: https://debezium.io/documentation/reference/stable/connectors/cassandra.html#setting-up-cassandra[Debezium -- Setting up Cassandra]

What goes wrong: once CDC is enabled, Cassandra can no longer purge those commit logs itself; if the connector stops and
`cdc_free_space_in_mb` fills up, **writes to CDC-enabled tables are rejected**. That makes the connector a dependency of
the legacy write path, which must be monitored like the database itself. TTL on collection columns, range deletes,
static columns, triggers, materialized views, secondary indexes and lightweight transactions are not supported, so
changes from those features are ignored. On Cassandra 4, `commit.log.real.time.processing.enabled=true` reads segments
as they are written instead of waiting for them to be completed.

When it appears in a migration: moving high-volume time-series or event data from Cassandra to a relational store or a
warehouse. Because every node emits its own changes, a replicated write appears once per replica, so consumers must
de-duplicate.

== CockroachDB (stable)

The CockroachDB connector creates one CockroachDB **enriched changefeed** for the configured tables, which publishes to an
*intermediate* Kafka cluster; the connector consumes those events, converts them into the standard Debezium envelope and
produces them to the output topics. Both official pages label it stable; it is tested with CockroachDB 25.4.14.

Main prerequisites: rangefeeds enabled cluster-wide, a user with the `CHANGEFEED` privilege (or `ALL`, or `admin`), and
network access from CockroachDB to the intermediate Kafka cluster. The connector page notes that all changefeed features
are available in every CockroachDB edition without an enterprise licence.

.Prepare CockroachDB for the connector
[source,sql]
----
SET CLUSTER SETTING kv.rangefeed.enabled = true;
GRANT CHANGEFEED ON ALL TABLES IN DATABASE bookshop TO dbz_bookshop;
GRANT VIEWCLUSTERSETTING TO dbz_bookshop;
----
Reference: https://debezium.io/documentation/reference/stable/connectors/cockroachdb.html#cockroachdb-grant-changefeed-permissions[Debezium -- CockroachDB: granting changefeed permissions]

When it appears in a migration: more often as the **new** database than as the legacy one; capturing it then feeds
reverse replication or downstream consumers
(xref:database/migration/cut-over-and-reverse-replication.adoc[Cut-over & Reverse Replication]).

== Vitess (incubating)

The Vitess connector subscribes to the **VStream** gRPC service of VTGate, which provides the equivalent of the MySQL
binary logs of all shards in a keyspace. It does not connect to the MySQL instances, so it needs no database user;
VTGate (default gRPC port 15991) and VTCtld (default 15999) must be reachable. It takes a consistent snapshot of the
keyspace and then streams. Labelled incubating on both pages, tested with Vitess 12.0.x; the supported databases page
points to documented limitations with earlier Vitess versions.

When it appears in a migration: moving a sharded MySQL estate on Vitess to another store, or splitting a keyspace.

== Spanner (incubating)

The Spanner connector reads a Google Cloud Spanner **change stream** and manages the change stream partitions for you. It
does **not** take snapshots: on the first start it streams from a given start timestamp or from now, so existing data
must be copied by other means. You provide the project, instance, database and change stream name, and a service account.
Labelled incubating on both pages.

When it appears in a migration: leaving Spanner, or feeding events from a Spanner-based system into other services.

== YashanDB (incubating)

The YashanDB connector uses the YashanDB **YStream** interface to read committed transactions from the transaction logs.
YStream needs a memory pool (`ALTER SYSTEM SET STREAM_POOL_SIZE = '512M'` in the official example), and supplemental
logging must be enabled. Tables in the `SYS`, `MDSYS` and `XA_SYS` schemas are never captured. Labelled incubating on
both pages, tested with YashanDB 23.4.

When it appears in a migration: systems in sectors where YashanDB is deployed (the connector page names finance,
government and energy), migrating to or integrating with other stores.

== Ingres (incubating)

The Ingres connector captures row-level changes in Actian databases using the Ingres Change Streams Java client; its
page says it is not production ready yet, and that it is inspired by the Db2 connector. The connector user needs
`DB_ADMIN` privileges (or must own the database or instance), and journaling must be enabled on each captured database,
for example with `ckpdb +j <database name>`. Tested with Ingres 12.1.

When it appears in a migration: older Ingres or Actian applications that are being moved to another database.

== Milvus (incubating)

The Milvus connector captures inserts and deletes in the collections of a Milvus **vector database** by reading its
internal message-queue channel directly, using the channel checkpoints stored in etcd so the snapshot and the stream
line up. It requires Milvus 2.5 or later with **Kafka** as the message backend (Pulsar and RocksMQ are not supported).
Labelled incubating; its page says it is not yet recommended for production.

When it appears in a migration: moving embeddings between vector stores, which is closer to the AI use cases on
xref:database/migration/other-uses-of-change-events.adoc[Beyond Migration] than to a legacy migration.

== SQLite and TiDB (incubating, databases page only)

The supported databases page lists **SQLite** (3.x) and **TiDB** (8.0+, through TiCDC) as incubating source connectors.
Neither has a page in the 3.7 reference documentation, and both have repositories in the Debezium GitHub organisation.
Treat them as previews: read the repository README, pin the version and test thoroughly before using them in a
migration.

== Choosing when the source is not on the main list

. **Is the legacy database on the list at all?** If not, look for CDC built into the database itself (triggers into an
  outbox table that the PostgreSQL or MySQL connector captures, or a vendor replication tool), or fall back to the
  batch strategies on xref:database/migration/migration-strategies.adoc[Migration Strategies].
. **Stable or incubating?** For an incubating connector, budget time for a longer rehearsal and keep reconciliation
  running until cut-over.
. **Licences and drivers.** Db2 needs an IIDR licence for SQL Replication; Db2 and Informix drivers must be added to
  the plug-in directory.
. **Runtime.** Cassandra runs on the database nodes, not on Kafka Connect, and CockroachDB needs an intermediate Kafka
  cluster. Everything else runs on Kafka Connect, Debezium Server or the Debezium Engine
  (xref:database/migration/choosing-a-deployment-for-your-migration.adoc[Choosing a Deployment]).
. **Snapshots.** Spanner has none; plan the initial copy separately.
