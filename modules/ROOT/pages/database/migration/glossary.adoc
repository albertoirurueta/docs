The terms used across the xref:database/migration/index.adoc[Database Migration] section, in alphabetical order.
Each entry links to the page that explains the term in detail. The definitions follow the official
https://debezium.io/documentation/reference/stable/index.html[Debezium 3.7 documentation] (checked on 2026-11-09)
and the database vendors' own documentation listed in the section bibliography.

[glossary]
Anti-corruption layer::
  A translation boundary that converts the legacy system's data shapes into the new domain model, so that nothing in
  the new code depends on the legacy schema. In this section it is a set of change-event consumers. See
  xref:database/migration/consuming-change-events-in-applications.adoc[Listening to Events in Applications] and
  xref:backend/architecture/decisions-and-migrations/migration-path-legacy-to-modern-stack.adoc#_the_anti_corruption_layer[the
  legacy migration path].

Archive log (Oracle)::
  A copy of a filled online redo log file. LogMiner reads archive logs when a change is no longer in the online redo
  logs, so the database must run in `ARCHIVELOG` mode and keep the archive logs long enough. See
  xref:database/migration/oracle-connector.adoc[Oracle Connector].

Binlog (MySQL, MariaDB)::
  The binary log of all changes made to a MySQL or MariaDB server. Debezium needs it in `ROW` format with full row
  images. See xref:database/migration/mysql-and-mariadb-connectors.adoc[MySQL & MariaDB Connectors].

Blocking snapshot::
  An ad hoc snapshot started with a signal that pauses streaming while it runs, then resumes streaming. See
  xref:database/migration/incremental-and-blocking-snapshots.adoc[Incremental & Blocking Snapshots].

Change data capture (CDC)::
  Capturing the inserts, updates and deletes committed to a database and delivering them as a stream of events.
  *Log-based* CDC reads the database's transaction log; *query-based* CDC polls tables for changed rows. See
  xref:database/migration/migration-strategies.adoc[Migration Strategies].

Change event::
  The record that Debezium emits for one row-level change. It has a key (normally the primary key) and a value made of an
  envelope. See xref:database/migration/change-event-structure.adoc[Anatomy of a Change Event].

Connector (source, sink)::
  A Kafka Connect plugin. A *source* connector reads an external system and writes to Kafka topics (all Debezium CDC
  connectors). A *sink* connector reads topics and writes to an external system (the Debezium JDBC and MongoDB sinks).
  See xref:database/migration/debezium-architecture.adoc[Debezium Architecture].

Converter::
  In Kafka Connect, the component that serializes records to bytes (JSON, Avro, Protobuf). In Debezium, a *custom
  converter* is also a plugin that changes how one column type is mapped to a field. See
  xref:database/migration/serialization-avro-and-schema-registries.adoc[Serialization & Schema Registries] and
  xref:database/migration/custom-converters-and-post-processors.adoc[Custom Converters & Post Processors].

Cut-over::
  The moment that the new system becomes the source of truth for some data, first for reads and then for writes. See
  xref:database/migration/cut-over-and-reverse-replication.adoc[Cut-over & Reverse Replication].

Debezium Engine::
  The library form of Debezium. It runs a connector inside a Java application and passes change events to a callback
  instead of Kafka. See xref:database/migration/debezium-engine.adoc[Debezium Engine (Embedded)].

Debezium Management Platform::
  The web application for defining sources, destinations, transforms and pipelines on Kubernetes. It replaces the
  earlier Debezium UI. See xref:database/migration/running-on-kubernetes.adoc[Running on Kubernetes].

Debezium Server::
  A standalone Quarkus application that runs a Debezium source connector and sends its events to a sink such as Amazon Kinesis,
  Google Cloud Pub/Sub, RabbitMQ, Redis or HTTP, without Kafka Connect. See
  xref:database/migration/debezium-server.adoc[Debezium Server].

Dual write::
  An application writing the same change to two systems (two databases, or a database and a broker) without a shared
  transaction. A crash between the writes leaves them inconsistent. CDC and the transactional outbox exist to avoid it.
  See xref:database/migration/migration-strategies.adoc[Migration Strategies].

Envelope::
  The structure of a Debezium change event value: `before`, `after`, `source`, `op`, the `ts_ms` / `ts_us` /
  `ts_ns` timestamps and, optionally, `transaction`. See
  xref:database/migration/change-event-structure.adoc[Anatomy of a Change Event].

Event flattening::
  Replacing the envelope with only the `after` state of the row, using the `ExtractNewRecordState` SMT, for consumers
  and sinks that expect plain rows. See xref:database/migration/event-flattening.adoc[Event Flattening].

GTID (MySQL, MariaDB)::
  A global transaction identifier. With GTIDs enabled, a connector can continue reading from another server of the
  same replication topology after a failover. See
  xref:database/migration/mysql-and-mariadb-connectors.adoc[MySQL & MariaDB Connectors].

Heartbeat::
  A periodic message that a connector emits (and optionally an action query it runs) so that offsets keep moving
  when the captured tables are idle. On PostgreSQL this stops the WAL from growing. See
  xref:database/migration/postgresql-connector.adoc[PostgreSQL Connector].

Incremental snapshot::
  A snapshot that reads a table in chunks while streaming continues, using watermarks to resolve collisions with
  live changes. It is started with a signal and can be paused, resumed and stopped. See
  xref:database/migration/incremental-and-blocking-snapshots.adoc[Incremental & Blocking Snapshots].

Initial snapshot::
  The consistent copy of the existing rows that a connector takes before it starts streaming, controlled by
  `snapshot.mode`. Its events have `op` set to `r`. See xref:database/migration/initial-snapshots.adoc[Initial Snapshots].

LogMiner::
  The Oracle Database utility that reads redo and archive logs. It is the default adapter of the Debezium Oracle connector.
  See xref:database/migration/oracle-connector.adoc[Oracle Connector].

LSN (PostgreSQL)::
  Log sequence number, a position in the PostgreSQL write-ahead log. The PostgreSQL connector stores it in its offsets
  and reports it in `source.lsn`. See xref:database/migration/postgresql-connector.adoc[PostgreSQL Connector].

Notification::
  A message that a connector emits about its own progress (for example, an initial snapshot completed) to a topic,
  the log or JMX. See xref:database/migration/signaling-and-notifications.adoc[Signaling & Notifications].

Offset::
  The position of a source connector in the transaction log (an LSN, SCN, binlog position, resume token and so on),
  committed after its events are written. On restart the connector resumes from the last committed offset. See
  xref:database/migration/offsets-restarts-and-exactly-once.adoc[Offsets, Restarts & Exactly-Once].

`op` code::
  The kind of change in an event: `c` (create), `u` (update), `d` (delete), `r` (read, from a snapshot), `t`
  (truncate) and `m` (message, PostgreSQL logical decoding messages). See
  xref:database/migration/change-event-structure.adoc[Anatomy of a Change Event].

Oplog (MongoDB)::
  The MongoDB operations log of a replica set. Change streams are built on it, and its size limits how long a stopped
  connector can stay down. See xref:database/migration/mongodb-connector.adoc[MongoDB Connector].

Outbox::
  A table that the application writes in the same transaction as its business change. A CDC connector with the outbox
  event router publishes it as a domain event. See xref:database/migration/outbox-event-router.adoc[Outbox Event Router]
  and xref:backend/architecture/architectural-patterns/transactional-outbox.adoc[Transactional Outbox].

Post processor::
  A Debezium component that changes an event inside the connector before it is emitted, for example to re-select
  column values that the log did not contain. See
  xref:database/migration/custom-converters-and-post-processors.adoc[Custom Converters & Post Processors].

Publication (PostgreSQL)::
  The set of tables whose changes logical replication sends through the `pgoutput` plugin. See
  xref:database/migration/postgresql-connector.adoc[PostgreSQL Connector].

Reconciliation::
  Comparing the legacy and the new database (counts, checksums, samples) to prove that they hold the same data, and
  repairing any difference. See xref:database/migration/verification-and-reconciliation.adoc[Verification & Reconciliation].

Redo log (Oracle)::
  The Oracle files that record every change to the database. LogMiner reads them. See
  xref:database/migration/oracle-connector.adoc[Oracle Connector].

Replica identity (PostgreSQL)::
  The table setting that decides which old column values PostgreSQL writes to the WAL for updates and deletes, and so
  what appears in `before`. See xref:database/migration/postgresql-connector.adoc[PostgreSQL Connector].

Replication slot (PostgreSQL)::
  A server-side cursor that keeps the WAL a consumer has not yet confirmed. An abandoned slot makes the WAL grow without
  limit. See xref:database/migration/postgresql-connector.adoc[PostgreSQL Connector].

Resume token (MongoDB)::
  The position in a change stream from which the MongoDB connector resumes. If the oplog no longer contains it,
  the token becomes invalid. See xref:database/migration/mongodb-connector.adoc[MongoDB Connector].

Reverse replication::
  Replicating changes from the new database back to the legacy one after the write cut-over, so that the legacy
  system stays current and a rollback stays possible. See
  xref:database/migration/cut-over-and-reverse-replication.adoc[Cut-over & Reverse Replication].

SCN (Oracle)::
  System change number, the Oracle logical clock. The Oracle connector tracks it in its offsets and reports it in
  `source.scn` and `source.commit_scn`. See xref:database/migration/oracle-connector.adoc[Oracle Connector].

Schema history topic::
  The topic where the MySQL, MariaDB, Oracle, SQL Server and Db2 connectors record the DDL they have seen, so that they can
  interpret older log entries after a restart. See
  xref:database/migration/schema-changes-during-migration.adoc[Handling Schema Changes].

Signal::
  An instruction sent to a running connector, through a signal table, a Kafka topic, JMX, a file or a custom
  channel, for example to start an incremental snapshot. See
  xref:database/migration/signaling-and-notifications.adoc[Signaling & Notifications].

Single message transformation (SMT)::
  A Kafka Connect plugin that changes one record at a time between a connector and the converter, for example to
  route, filter or flatten events. See xref:database/migration/single-message-transformations.adoc[Debezium Transformations].

Strangler fig::
  Replacing a legacy system gradually, capability by capability, while both run, until the legacy system can be
  removed. See xref:database/migration/migration-patterns-with-cdc.adoc[Migration Patterns with CDC] and
  xref:backend/architecture/decisions-and-migrations/migration-overview.adoc[Migration Overview].

Supplemental logging (Oracle)::
  Extra information that Oracle writes to the redo log (for example all the columns of a changed row) so that LogMiner
  can rebuild full row images. See xref:database/migration/oracle-connector.adoc[Oracle Connector].

Tombstone::
  A record with a key and a `null` value, emitted after a delete event so that Kafka log compaction can remove every
  record for that key. Controlled by `tombstones.on.delete`. See
  xref:database/migration/change-event-structure.adoc[Anatomy of a Change Event].

Topic prefix::
  The `topic.prefix` connector property. It names the logical server and is the first part of every topic the connector
  writes (for example `legacy.BOOKSHOP.BOOK`). It replaced `database.server.name`. See
  xref:database/migration/debezium-architecture.adoc[Debezium Architecture].

Transaction metadata::
  Optional `BEGIN` and `END` events on a dedicated topic, plus a `transaction` block in every change event, which let
  consumers group the changes of one source transaction. See
  xref:database/migration/debezium-features-and-guarantees.adoc[Features & Delivery Guarantees].

WAL (PostgreSQL)::
  The PostgreSQL write-ahead log. With `wal_level=logical` it carries the information that logical decoding turns into
  change events. See xref:database/migration/postgresql-connector.adoc[PostgreSQL Connector].

Watermark::
  A marker that an incremental snapshot writes (or, in read-only mode, derives) around each chunk, so that a snapshot
  row and a streamed change to the same row are not both emitted out of order. See
  xref:database/migration/incremental-and-blocking-snapshots.adoc[Incremental & Blocking Snapshots].
