Every later page in this section assumes one picture in the reader's head: a database commits a change, a Debezium
connector running inside Kafka Connect reads that change from the database log, and a Kafka topic receives one event
that describes it. This page builds that picture with real software in a few minutes. It is the official Debezium
https://debezium.io/documentation/reference/stable/kc-tutorial.html[Kafka Connect tutorial], rebuilt as a single Docker
Compose file and pinned to the 3.7.1.Final images, followed by the same lab against PostgreSQL.

The tutorial uses the small `inventory` sample database that Debezium ships in its example images, not the Bookshop
schema of the rest of the section. That is on purpose: the goal here is to see the mechanics (snapshot, streaming,
offsets, restarts) with nothing else in the way. Once those mechanics are familiar, the same steps apply to the legacy
Bookshop Oracle database in xref:database/migration/oracle-connector.adoc[Oracle Connector] and
xref:database/migration/worked-example-oracle-to-postgresql.adoc[Worked Example: Oracle to PostgreSQL].

Why this matters for a migration: during a strangler-fig migration (see
xref:backend/architecture/decisions-and-migrations/migration-path-legacy-to-modern-stack.adoc#_data_synchronisation_during_the_overlap[Migration Path: From a Legacy Stack to a Modern One])
the new system depends on three guarantees that this lab lets you observe directly:

. the existing rows are copied once, as `r` (read) events, before streaming starts;
. every committed insert, update and delete after that appears as a `c`, `u` or `d` event, in commit order per row;
. if the capture process stops, it resumes from the exact log position it had reached, so changes made while it was
  down are delivered late but not lost.

Checked on 2026-11-09 against Debezium 3.7.1.Final, with Kafka 4.3.1 (KRaft mode, bundled in the Debezium images),
MySQL 8.2.0 (`example-mysql`) and PostgreSQL 18.6 (`example-postgres`). The Compose stack, both connector
configurations and every command on this page were run with Docker on 2026-11-09, and the event output shown is the
real output of that run, trimmed for width. The page uses the standard host ports (9092, 8083, 3306 and 5432).

== What you build

The stack has four containers on one Docker network, plus short-lived client containers that you start when you need
them.

[mermaid]
....
flowchart LR
    subgraph compose["Docker Compose project dbz-tutorial"]
        mysql[("mysql: example-mysql")]
        postgres[("postgres: example-postgres")]
        connect["connect: Kafka Connect with Debezium, REST on 8083"]
        kafka[["kafka: KRaft node on 9092"]]
    end
    host["Terminal: curl and docker compose exec"]
    watcher["watch-topic or kcat client container"]
    mysql -- "binlog" --> connect
    postgres -- "logical replication slot" --> connect
    connect -- "change events and offsets" --> kafka
    host -- "REST API" --> connect
    watcher -- "consume topics" --> kafka
....

The roles are the same as in a production migration pipeline (see
xref:database/migration/debezium-architecture.adoc[Debezium Architecture]):

* **Kafka** stores the change-event topics and the three internal Kafka Connect topics (connector configurations,
  source offsets and connector status).
* **Kafka Connect** runs the Debezium connector plugins. You never start a connector process yourself: you send a JSON
  configuration to the Connect REST API, and Connect starts the connector and its task.
* **The source databases** are preconfigured for change data capture. The MySQL image has the binlog enabled in `ROW`
  format with full row images and a `debezium` user with replication privileges. The PostgreSQL image runs with
  `wal_level=logical`.

== Prerequisites

* Docker Engine or Docker Desktop with the Compose plugin (`docker compose version` prints v2.x).
* About 3 GB of free memory for the containers. Without a heap limit, the Kafka Connect container can be killed by the
  out-of-memory killer on a machine with little free memory, so the Compose file below caps its heap (the `HEAP_OPTS`
  line). If `docker compose ps` shows `connect` as `Exited (137)`, give Docker more memory or stop other containers.
* `curl` and `jq` on the host. `jq` is only used to pretty-print and trim JSON.
* Free host ports 9092, 8083, 3306 and 5432. If one is taken, change only the left-hand side of the matching `ports`
  entry and use that port in the commands.

== Step 1: Start the services

The official tutorial starts Kafka, MySQL and Kafka Connect with one `docker run` command each, in separate terminals.
The Compose file below starts the same containers with the same environment variables in one step, and adds the
PostgreSQL example database used in the second half of the page.

.compose.yaml -- Kafka (KRaft), Kafka Connect and the example MySQL and PostgreSQL databases
[source,yaml]
----
name: dbz-tutorial

services:
  kafka:
    image: quay.io/debezium/kafka:3.7.1.Final
    hostname: kafka
    ports:
      - "9092:9094"
    environment:
      CLUSTER_ID: 5Yr1SIgYQz-b-dgRabWx4g
      NODE_ID: "1"
      NODE_ROLE: combined
      KAFKA_CONTROLLER_QUORUM_VOTERS: 1@kafka:9093
      KAFKA_LISTENERS: PLAINTEXT://kafka:9092,CONTROLLER://kafka:9093,EXTERNAL://0.0.0.0:9094
      KAFKA_ADVERTISED_LISTENERS: PLAINTEXT://kafka:9092,EXTERNAL://localhost:9092
      KAFKA_LISTENER_SECURITY_PROTOCOL_MAP: CONTROLLER:PLAINTEXT,PLAINTEXT:PLAINTEXT,EXTERNAL:PLAINTEXT

  mysql:
    image: quay.io/debezium/example-mysql:3.7.1.Final
    ports:
      - "3306:3306"
    environment:
      MYSQL_ROOT_PASSWORD: debezium
      MYSQL_USER: mysqluser
      MYSQL_PASSWORD: mysqlpw

  postgres:
    image: quay.io/debezium/example-postgres:3.7.1.Final
    ports:
      - "5432:5432"
    environment:
      POSTGRES_USER: postgres
      POSTGRES_PASSWORD: postgres

  connect:
    image: quay.io/debezium/connect:3.7.1.Final
    ports:
      - "8083:8083"
    depends_on:
      - kafka
      - mysql
      - postgres
    environment:
      GROUP_ID: "1"
      BOOTSTRAP_SERVERS: kafka:9092
      CONFIG_STORAGE_TOPIC: my_connect_configs
      OFFSET_STORAGE_TOPIC: my_connect_offsets
      STATUS_STORAGE_TOPIC: my_connect_statuses
      HEAP_OPTS: -Xms256m -Xmx512m
----
Reference: https://debezium.io/documentation/reference/stable/kc-tutorial.html#starting-services[Debezium -- Tutorial: Starting the services]

What each part does, and where it differs from the official `docker run` commands:

`kafka`::
A single Kafka 4.x node in KRaft mode (no ZooKeeper) that is both broker and controller (`NODE_ROLE: combined`).
`CLUSTER_ID`, `NODE_ID`, `NODE_ROLE`, `KAFKA_CONTROLLER_QUORUM_VOTERS`, `KAFKA_LISTENERS` and
`KAFKA_ADVERTISED_LISTENERS` are the variables from the official
https://debezium.io/documentation/reference/stable/kc-tutorial.html#starting-kafka[Starting Kafka] step. The cluster ID
is any 22-character base64 UUID; generate your own with `docker run --rm quay.io/debezium/kafka:3.7.1.Final
/kafka/bin/kafka-storage.sh random-uuid` if you prefer. The image's entry point turns every `+KAFKA_*+` variable into a
`server.properties` entry, formats the storage directory on first start, and prints a warning that
`KAFKA_CONTROLLER_QUORUM_VOTERS` is deprecated since Kafka 4.1.1. It converts the value to
`controller.quorum.bootstrap.servers` itself, so the warning is harmless here. +
The official command advertises only `kafka:9092`, which works for clients inside the Docker network but not for a
client on the host. This file adds a third listener, `EXTERNAL`, that listens on container port 9094, is published as
host port 9092 and advertises `localhost:9092`. Containers keep using `kafka:9092`; host tools such as a local `kcat`
or a Spring Boot application started from the IDE use `localhost:9092`.

`mysql`::
The `example-mysql` image (based on MySQL 8.2) with the `inventory` sample database. The variables are those of the
official https://debezium.io/documentation/reference/stable/kc-tutorial.html#starting-mysql-database[Starting a MySQL
database] step. The image also creates the `debezium` user (password `dbz`) that the connector uses.

`postgres`::
The `example-postgres` image (PostgreSQL 18 with `wal_level=logical`) with the same `inventory` data in a schema called
`inventory`. It is only needed for the second half of the page.

`connect`::
Kafka Connect with every Debezium connector plugin already installed. `GROUP_ID`, `BOOTSTRAP_SERVERS` and the three
`+*_STORAGE_TOPIC+` variables are those of the official
https://debezium.io/documentation/reference/stable/kc-tutorial.html#starting-kafka-connect[Starting Kafka Connect] step.
The storage topics are where Kafka Connect keeps connector configurations, source offsets and status, which is why
connectors survive a restart of the Connect container. `HEAP_OPTS` caps the JVM heap so that the stack fits on a laptop.
Compose service names resolve as host names on the project network, so the `--link` options of the official commands
are not needed.

== Step 2: Register the MySQL connector

A connector is a JSON document with a `name` and a `config` map. Save the following as `register-mysql.json`. It is
the configuration of the official tutorial, unchanged.

.register-mysql.json -- Debezium MySQL connector for the inventory database
[source,json]
----
{
  "name": "inventory-connector",
  "config": {
    "connector.class": "io.debezium.connector.mysql.MySqlConnector",
    "tasks.max": "1",
    "database.hostname": "mysql",
    "database.port": "3306",
    "database.user": "debezium",
    "database.password": "dbz",
    "database.server.id": "184054",
    "topic.prefix": "dbserver1",
    "database.include.list": "inventory",
    "schema.history.internal.kafka.bootstrap.servers": "kafka:9092",
    "schema.history.internal.kafka.topic": "schemahistory.inventory"
  }
}
----
Reference: https://debezium.io/documentation/reference/stable/kc-tutorial.html#registering-connector-monitor-inventory-database[Debezium -- Tutorial: Registering a connector to monitor the inventory database]

The properties, and what each one means in a real migration:

[cols="2,3,4",options="header"]
|===
| Property | Value here | Why it matters

| `connector.class`
| `MySqlConnector`
| Selects the plugin. Each source database has its own class; see
  xref:database/migration/mysql-and-mariadb-connectors.adoc[MySQL & MariaDB Connectors].

| `tasks.max`
| `1`
| The MySQL connector always runs a single task, because the binlog is one ordered stream. A single reader keeps the
  order of events.

| `database.hostname`, `database.port`
| `mysql`, `3306`
| The address as seen from the Connect container, not from your host. A common mistake is `localhost`, which points at
  the Connect container itself.

| `database.user`, `database.password`
| `debezium`, `dbz`
| A dedicated user with `SELECT, RELOAD, SHOW DATABASES, REPLICATION SLAVE, REPLICATION CLIENT`. In production, never put
  the password in plain text: use a Kafka Connect config provider (see
  xref:database/migration/security-and-data-protection.adoc[Security & Data Protection]).

| `database.server.id`
| `184054`
| The connector joins the MySQL replication topology as a replica, so it needs a server ID that is unique among all
  replicas of that server.

| `topic.prefix`
| `dbserver1`
| The logical name of the source. Every topic starts with it (`dbserver1.inventory.customers`), and Debezium stores
  offsets under it. Never change it on a running connector: a new prefix means new topics and a fresh snapshot.
  `topic.prefix` replaced the old `database.server.name`.

| `database.include.list`
| `inventory`
| Only this database is captured.

| `+schema.history.internal.kafka.*+`
| `kafka:9092`, `schemahistory.inventory`
| MySQL binlog events do not carry the table structure, so the connector records every DDL statement in this topic and
  replays it after a restart. These properties replaced the old `+database.history.*+` names.
|===

Reference: https://debezium.io/documentation/reference/stable/connectors/mysql.html#mysql-connector-properties[Debezium -- MySQL connector properties]

Read the two binlog positions together. In step 4 the connector recorded `mysql-bin.000003` position 157 while it held
the read lock, then copied the rows, and finally connected to the binlog at exactly that position. Anything committed
during the copy is therefore delivered as a streaming event after the snapshot events, never lost and never mixed in.
That hand-over is what makes a snapshot plus streaming a correct baseline for a migration.

== Step 3: Watch the customers topic

Open a second terminal and start a consumer that prints every event in `dbserver1.inventory.customers` from the
beginning, with its key. The Debezium Kafka image includes a `watch-topic` helper for this; it is a thin wrapper around
`kafka-console-consumer.sh`.

.Watch the topic with the watch-topic helper
[source,shell]
----
docker run -it --rm --name watcher --network dbz-tutorial_default \
  quay.io/debezium/kafka:3.7.1.Final watch-topic -a -k dbserver1.inventory.customers
----
Reference: https://debezium.io/documentation/reference/stable/kc-tutorial.html#viewing-create-event[Debezium -- Tutorial: Viewing a create event]

`-a` reads from the beginning of the topic and `-k` prints the key, separated from the value by a tab.
`dbz-tutorial_default` is the network that Compose created for the project. The plain Kafka console consumer works the
same way and is what you would script:

.The same, with kafka-console-consumer
[source,shell]
----
docker compose exec kafka /kafka/bin/kafka-console-consumer.sh --bootstrap-server kafka:9092 \
  --topic dbserver1.inventory.customers --from-beginning \
  --formatter-property print.key=true
----
Reference: https://debezium.io/documentation/reference/stable/kc-tutorial.html#viewing-create-event[Debezium -- Tutorial: Viewing a create event]

In Kafka 4.x the console consumer's `--property` option is deprecated in favour of `--formatter-property`; the old
spelling still works but prints a warning.

A third option is https://github.com/edenhill/kcat[kcat], which can print the partition offset of every message with
a format string. That is useful later for checking that nothing was lost or duplicated:

.The same, with kcat, showing the topic offset of each event
[source,shell]
----
docker run --rm --platform linux/amd64 --network dbz-tutorial_default edenhill/kcat:1.7.1 \
  -b kafka:9092 -C -t dbserver1.inventory.customers -o beginning -e -q -f '%o|%s\n'
----
Reference: https://github.com/edenhill/kcat[kcat -- README]

The `edenhill/kcat` image is published for `linux/amd64` only, so on an ARM machine Docker runs it under emulation
(hence `--platform`). If `kcat` is installed on the host, use `-b localhost:9092` instead; the `EXTERNAL` listener in
the Compose file exists for exactly this.

=== The snapshot events

The first four events are the snapshot of the four existing customers. Each message has a key and a value, and with
the default JSON converter each of them is a `schema` plus `payload` pair. The key of the last snapshot event:

.Key of a snapshot event (real output, 2026-11-09)
[source,json]
----
{
  "schema": {
    "type": "struct",
    "fields": [ { "type": "int32", "optional": false, "field": "id" } ],
    "optional": false,
    "name": "dbserver1.inventory.customers.Key"
  },
  "payload": { "id": 1004 }
}
----
Reference: https://debezium.io/documentation/reference/stable/connectors/mysql.html#mysql-change-event-keys[Debezium -- MySQL connector: change event keys]

The key is the primary key of the row. Kafka uses it to choose the partition, so every change to customer 1004 lands
in the same partition, in order. Consumers that apply events to a target table rely on that ordering.

The value carries a schema that describes `before`, `after`, `source`, `transaction`, `op` and the timestamps, and the
payload itself. The schema is around 2.5 KB per message in this table; the payload is the part you work with. With
`jq -c .payload`:

.Value payload of the last snapshot event (real output, 2026-11-09)
[source,json]
----

    "ts_ms": 1794214272000, "snapshot": "last_in_data_collection",
    "db": "inventory", "sequence": null, "table": "customers",
    "server_id": 0, "gtid": null, "file": "mysql-bin.000003", "pos": 157, "row": 0,

  "transaction": null,
  "op": "r",
  "ts_ms": 1794214272715, "ts_us": 1794214272715802, "ts_ns": 1794214272715802176
}
----
Reference: https://debezium.io/documentation/reference/stable/connectors/mysql.html#mysql-create-events[Debezium -- MySQL connector: create events]

* `op` is `r` (read): this row was copied by the snapshot, not changed by a transaction.
* `before` is `null` and `after` holds the whole row.
* `source.snapshot` marks the position within the snapshot: `first_in_data_collection`, `true`, and
  `last_in_data_collection` for the last row of this table. Streaming events have `"false"`.
* `source.file` and `source.pos` are the binlog position recorded in snapshot step 4; every snapshot event carries the
  same position.

xref:database/migration/change-event-structure.adoc[Anatomy of a Change Event] explains every field. For this lab, the
four fields that matter are `op`, `before`, `after` and `source`.

== Step 5: Stop Kafka Connect, change data, restart

This step shows the property that makes CDC usable for a long-running migration: the connector can be stopped for an
upgrade, a crash or a redeployment, and it resumes from where it stopped.

First look at where the connector has recorded its position. Kafka Connect stores source offsets in the
`my_connect_offsets` topic, keyed by connector name and source partition:

.Read the stored offsets
[source,shell]
----
docker compose exec kafka /kafka/bin/kafka-console-consumer.sh --bootstrap-server kafka:9092 \
  --topic my_connect_offsets --from-beginning --formatter-property print.key=true --timeout-ms 5000
----
Reference: https://debezium.io/documentation/reference/stable/kc-tutorial.html#restarting-kafka-connect-service[Debezium -- Tutorial: Restarting the Kafka Connect service]

.Output on 2026-11-09, about a minute after step 4
[source,text]
----
["inventory-connector",{"server":"dbserver1"}]	{"ts_sec":1794214272,"file":"mysql-bin.000003","pos":157}
----

Only the snapshot position (157) is stored, although three streaming events were already published. Kafka Connect does
not commit an offset for every event: it flushes offsets periodically, every `offset.flush.interval.ms` (60 seconds in
the Debezium image, set by its `OFFSET_FLUSH_INTERVAL_MS` variable), and on a clean shutdown. If the worker crashed at
this moment, it would restart from position 157 and publish the insert, update and delete again. That is the
at-least-once guarantee, and it is why every consumer that writes to the new database must be idempotent; see
xref:database/migration/offsets-restarts-and-exactly-once.adoc[Offsets, Restarts & Exactly-Once].

Now stop Kafka Connect gracefully, insert two rows while it is down, and start it again:

.Stop Connect, change data, start Connect
[source,shell]
----
docker compose stop connect

docker compose exec mysql mysql -umysqluser -pmysqlpw inventory -e \
  "INSERT INTO customers (first_name, last_name, email) VALUES ('Sarah', 'Thompson', 'sarah.thompson@example.com');
   INSERT INTO customers (first_name, last_name, email) VALUES ('Kenneth', 'Anderson', 'kenneth.anderson@example.com');"

docker compose start connect
----
Reference: https://debezium.io/documentation/reference/stable/kc-tutorial.html#restarting-kafka-connect-service[Debezium -- Tutorial: Restarting the Kafka Connect service]

While Connect is down the watcher prints nothing, because nothing is being produced. The rows are safe in the MySQL
binlog. The graceful stop committed the latest offset, which you can see by reading `my_connect_offsets` again:

.Offsets after the graceful stop (2026-11-09)
[source,text]
----

The new offset points into the delete transaction (`pos` 1352 is the start of that transaction, `event` 2 and `row` 1
tell the connector how many events and rows of it were already sent). Only the last offset per key counts.

. **Nothing was lost.** Both rows written while Connect was down arrived.
. **Nothing was duplicated.** The topic now has exactly ten messages (offsets 0 to 9): the eight from step 4 plus the
  two new inserts. The delete at offset 6 was not sent again, because the graceful stop had committed its offset.
. **The lag is visible.** `source.ts_ms` is 08:52:50 UTC (the commit in MySQL) and `ts_ms` is 08:55:41 UTC (when

  milliseconds once it was running.

purges old binlog files after `binlog_expire_logs_seconds`; if the connector is down for longer than that, it fails

retention of the legacy database for the longest outage you are willing to tolerate. See
https://debezium.io/documentation/reference/stable/connectors/mysql.html#mysql-purges-binlog-files-used-by-debezium[MySQL purges binlog files used by Debezium]
and xref:database/migration/troubleshooting-and-failure-recovery.adoc[Troubleshooting & Failure Recovery].

== Step 6: The same lab with PostgreSQL

The PostgreSQL connector works the same way from the outside (a JSON configuration, the same envelope, the same
offsets topic) but reads a different log. Instead of acting as a binlog replica, it creates a **logical replication
slot** in the database and receives decoded WAL changes through it. Most migrations target PostgreSQL, and many legacy
systems run on it, so it is worth seeing the differences once.

The `postgres` service is already running. Check that it is ready for logical decoding and look at the data:

.Check wal_level and the sample data
[source,shell]
----
docker compose exec postgres psql -U postgres -c "SHOW wal_level;"
docker compose exec postgres psql -U postgres -c "SELECT * FROM inventory.customers;"
----
Reference: https://debezium.io/documentation/reference/stable/connectors/postgresql.html#postgresql-server-configuration[Debezium -- PostgreSQL connector: configuring the PostgreSQL server]

`wal_level` must be `logical`; the example image sets it. The `customers` table has the same four rows as in MySQL.

Save the connector configuration as `register-postgres.json`:

.register-postgres.json -- Debezium PostgreSQL connector for the inventory schema
[source,json]
----
{
  "name": "inventory-pg-connector",
  "config": {
    "connector.class": "io.debezium.connector.postgresql.PostgresConnector",
    "tasks.max": "1",
    "database.hostname": "postgres",
    "database.port": "5432",
    "database.user": "postgres",
    "database.password": "postgres",
    "database.dbname": "postgres",
    "topic.prefix": "pgserver1",
    "schema.include.list": "inventory",
    "plugin.name": "pgoutput",
    "slot.name": "debezium_tutorial",
    "publication.name": "dbz_publication"
  }
}
----
Reference: https://debezium.io/documentation/reference/stable/connectors/postgresql.html#postgresql-connector-properties[Debezium -- PostgreSQL connector properties]

The differences from the MySQL configuration:

* `database.dbname` is required: a PostgreSQL connector captures one database. `schema.include.list` then limits it to
  the `inventory` schema.
* `topic.prefix` is `pgserver1`, not `dbserver1`. Both sources have an `inventory.customers` table, so the same prefix
  would make both connectors write to `dbserver1.inventory.customers`. Every connector in a Connect cluster needs its
  own prefix.
* `plugin.name` is `pgoutput`, the logical decoding plug-in built into PostgreSQL 10 and later and available on managed
  services. The documented default is `decoderbufs`, which needs an extension installed on the server, so set
  `pgoutput` explicitly. See
  https://debezium.io/documentation/reference/stable/connectors/postgresql.html#postgresql-property-plugin-name[plugin.name].
* `slot.name` names the replication slot (default `debezium`). One slot per connector; two connectors must never share a
  slot.
* `publication.name` is the publication that `pgoutput` reads (default `dbz_publication`). With the default
  `publication.autocreate.mode=all_tables` the connector creates it `FOR ALL TABLES` and filters with the include
  lists itself.
* There is no `+schema.history.internal.*+`: PostgreSQL sends the table structure with the logical decoding messages, so
  the PostgreSQL connector does not need a schema history topic.
* The `postgres` superuser is fine for a lab only. A production connector uses a dedicated user with the `REPLICATION`
  attribute; see xref:database/migration/postgresql-connector.adoc[PostgreSQL Connector].

=== REPLICA IDENTITY decides what before contains

The update above has a full `before` image. That is only because the `example-postgres` image sets
`REPLICA IDENTITY FULL` on its tables. A normal PostgreSQL table uses `REPLICA IDENTITY DEFAULT`, which writes only the
primary key of the old row to the WAL. To see the difference, switch the table to the default and repeat an update and
a delete:

.Switch to REPLICA IDENTITY DEFAULT, change rows, switch back
[source,shell]
----
docker compose exec postgres psql -U postgres -c "ALTER TABLE inventory.customers REPLICA IDENTITY DEFAULT;"
docker compose exec postgres psql -U postgres -c "UPDATE inventory.customers SET last_name='Bailey-Ross' WHERE id=1002;"
docker compose exec postgres psql -U postgres -c "DELETE FROM inventory.customers WHERE id=1005;"
docker compose exec postgres psql -U postgres -c "ALTER TABLE inventory.customers REPLICA IDENTITY FULL;"
----
Reference: https://debezium.io/documentation/reference/stable/connectors/postgresql.html#postgresql-replica-identity[Debezium -- PostgreSQL connector: REPLICA IDENTITY]

.Events with REPLICA IDENTITY DEFAULT (real output, 2026-11-09)
[source,text]
----
9  {"before":null,"after":{"id":1002,"first_name":"George","last_name":"Bailey-Ross","email":"gbailey@foobar.com"},"op":"u"}
10 {"before":{"id":1005,"first_name":"","last_name":"","email":""},"after":null,"op":"d"}
11 tombstone
----

With `DEFAULT`, the update has `"before": null`, and the delete has a `before` image that contains only the real primary
key: the other columns are `NOT NULL` in the schema, so the connector fills them with empty strings. A consumer that
reads `before.email` of a delete gets `""`, not the deleted customer's address. For a migration this matters in three
places:

* an anti-corruption layer that needs the old value to translate a change (for example to find the previous status of
  an order) cannot get it;
* audit or reconciliation logic that compares `before` and `after` sees nothing to compare;
* a sink that needs the old value of a non-key column to find the target row cannot find it.

Decide per table whether you need full before images, and set `REPLICA IDENTITY FULL` on the legacy tables that need it
(it increases WAL volume). The PostgreSQL connector can set it for you with `replica.identity.autoset.values`. See
xref:database/migration/postgresql-connector.adoc[PostgreSQL Connector] and
xref:database/migration/data-types-and-precision.adoc[Data Types & Precision] for the related TOAST column behaviour.

  "SELECT slot_name, active, confirmed_flush_lsn, pg_current_wal_lsn() FROM pg_replication_slots;"
docker compose start connect
----
Reference: https://debezium.io/documentation/reference/stable/connectors/postgresql.html#postgresql-when-things-go-wrong[Debezium -- PostgreSQL connector: behavior when things go wrong]

.Slot while Connect was stopped (2026-11-09)
[source,text]
----
     slot_name     | active | confirmed_flush_lsn | pg_current_wal_lsn
-------------------+--------+---------------------+--------------------
 debezium_tutorial | f      | 0/2B781B8           | 0/2B785D0
----

The slot is inactive, and its `confirmed_flush_lsn` stays behind the current WAL position. This is the PostgreSQL
counterpart of the binlog retention problem, and more dangerous: an inactive slot makes PostgreSQL **keep every WAL
segment** after `confirmed_flush_lsn`. A connector that stays stopped for days on a busy legacy database can fill the
disk. Monitor slot lag (`pg_current_wal_lsn()` minus `confirmed_flush_lsn`) and cap it with PostgreSQL's
`max_slot_wal_keep_size`; see xref:database/migration/postgresql-connector.adoc[PostgreSQL Connector].

On start, the connector reads its offset from `my_connect_offsets`, checks the slot and asks PostgreSQL to continue
from there:

== Step 7: Clean up

Deleting a connector removes its configuration from Kafka Connect, but not what it created in the source database.
For PostgreSQL that means the replication slot and the publication. A forgotten slot keeps WAL forever, so drop both:

.Delete the PostgreSQL connector, then its slot and publication
[source,shell]
----
curl -s -o /dev/null -w '%{http_code}\n' -X DELETE localhost:8083/connectors/inventory-pg-connector
# 204

docker compose exec postgres psql -U postgres -c "SELECT slot_name, active FROM pg_replication_slots;"
#      slot_name     | active
# -------------------+--------
#  debezium_tutorial | f

docker compose exec postgres psql -U postgres -c "SELECT pg_drop_replication_slot('debezium_tutorial');"
docker compose exec postgres psql -U postgres -c "DROP PUBLICATION dbz_publication;"
----
Reference: https://debezium.io/documentation/reference/stable/connectors/postgresql.html#postgresql-property-slot-drop-on-stop[Debezium -- PostgreSQL connector: slot.drop.on.stop]

`slot.drop.on.stop=true` makes the connector drop its slot on every graceful stop. That is convenient in tests but
wrong for a migration pipeline: after a restart the connector would have to take a new snapshot, because the changes
between the stop and the start are gone with the slot.

The MySQL connector leaves nothing in the database, so deleting it is enough. Then stop and remove the whole stack,
including its volumes:

.Remove the stack
[source,shell]
----
curl -s -X DELETE localhost:8083/connectors/inventory-connector
docker compose down -v
docker ps -a --filter name=dbz-tutorial
----
Reference: https://debezium.io/documentation/reference/stable/kc-tutorial.html#cleaning-up[Debezium -- Tutorial: Cleaning up]

The last command must print only the header line. Because Kafka keeps its data inside the container and the
Compose file defines no named volumes, `down -v` removes all topics, offsets and connector configurations; the next
`docker compose up -d` starts from nothing and every connector takes a new snapshot.

== What can go wrong

[cols="2,3,3",options="header"]
|===
| Symptom | Likely cause | Fix

| `curl: (7) Failed to connect to localhost port 8083`
| Kafka Connect is still scanning plugins, or the container was killed.
| Wait and retry. Check `docker compose ps`; `Exited (137)` means the out-of-memory killer stopped it. Give Docker
  more memory or keep the `HEAP_OPTS` cap.

| Task state `FAILED` with `Communications link failure` or `Connection refused`
| `database.hostname` is `localhost` or a host port.
| Use the Compose service name and the container port (`mysql`, `3306`; `postgres`, `5432`).

| Registration returns `409 Conflict`
| A connector with that name already exists.
| Update it with `PUT /connectors/<name>/config`, or delete it first.

| Two connectors write to the same topics
| Same `topic.prefix` on two connectors.
| Give each connector its own prefix.

| A host client hangs or fails on `kafka:9092`
| The client got the internal advertised listener.
| Connect from the host with `localhost:9092` (the `EXTERNAL` listener), and from containers with `kafka:9092`.

| PostgreSQL connector fails with a `decoderbufs` error
| `plugin.name` was left at its default.
| Set `plugin.name` to `pgoutput`.

| PostgreSQL disk grows while Connect is down
| The inactive replication slot retains WAL.
| Restart the connector, or drop the slot if the connector is gone for good.

| After a restart, events already seen arrive again
| The worker stopped without committing its last offset (crash or kill).
| Expected under at-least-once delivery. Make consumers idempotent.
|===

Reference: https://debezium.io/documentation/reference/stable/connectors/mysql.html#mysql-when-things-go-wrong[Debezium -- MySQL connector: behavior when things go wrong]
