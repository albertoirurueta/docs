= MongoDB Sink Connector
:description: How to use the Debezium MongoDB sink connector to write relational change events into MongoDB collections during a migration -- what it can consume, how it turns create, update and delete events into replace-with-upsert and delete operations, how event keys become the _id field, collection naming, configuration properties, type conversion to BSON, delivery and error handling, monitoring, and the Bookshop examples that copy the PostgreSQL book_review table and the legacy Oracle BOOK table into MongoDB.
:keywords: Debezium MongoDB sink connector, MongoDbSinkConnector, Kafka Connect sink, relational to document migration, MongoDB, _id, key field mapping, collection.name.format, collection.naming.strategy, sink.database, mongodb.connection.string, upsert, replaceOne, deleteOne, idempotent writes, at-least-once delivery, BSON types, Decimal128, CloudEvents, Bookshop reviews

include::partial$ai-disclaimer.adoc[]

The Debezium MongoDB sink connector reads change events that Debezium relational source connectors write to Kafka and
applies them to collections in a MongoDB database, one document per source row. It is the document-database
counterpart of the xref:database/migration/jdbc-sink-connector.adoc[JDBC Sink Connector]: no application code, and
idempotent writes keyed by the source primary key.

In a migration it covers the relational-to-document direction. The Bookshop example moves the legacy MongoDB
`bookshop.reviews` collection into the PostgreSQL table `book_review` (see
xref:database/migration/mongodb-connector.adoc[MongoDB Connector]). This page shows the other direction: changes to
`book_review` in PostgreSQL flowing back into MongoDB, and a MongoDB read model of the legacy Oracle `BOOK` table. It
also explains the limits that decide when the sink is enough and when a translating consumer is needed.

Checked on 2026-11-09 against Debezium 3.7.1.Final (the MongoDB sink ships in the `debezium-connector-mongodb`
plug-in), Apache Kafka 4.3 (Kafka Connect), PostgreSQL 18 and MongoDB 8.0. The configuration on this page is derived
from the official documentation; the connector class name, the write operations and the BSON conversions described
below were checked against the classes in the 3.7.1.Final `debezium-connector-mongodb` JAR. The connectors on this
page were not run.

== When a document target helps in a migration

A relational-to-document sink is useful in three situations:

* **Reverse replication of a document store.** After the write cut-over of reviews, the new application writes
  `book_review` in PostgreSQL, and the legacy application still reads MongoDB until it is retired. The sink keeps a
  MongoDB copy current (with the limits described in <<_writing_back_to_the_legacy_reviews_collection>>).
* **A document read model built from a relational source.** A catalogue service that serves book documents can be fed
  from the legacy `BOOKSHOP.BOOK` table while the migration is still in progress, without touching the legacy
  application. This is the CQRS use of change events described in
  xref:backend/architecture/architectural-patterns/cqrs.adoc[CQRS].
* **A relational database replaced by MongoDB.** When the new system itself uses MongoDB, the sink provides the 1:1
  copy of the tables that keep their shape, and translators build the remodelled documents, in the same way as with
  the JDBC sink.

[mermaid]
....
flowchart LR
    PG[(PostgreSQL bookshop.public.book_review)] -->|pgoutput| PGS[bookshop-pg-source]
    PGS --> T1[modern.public.book_review]
    ORA[(Oracle BOOKSHOP.BOOK)] -->|LogMiner| OS[bookshop-oracle-source]
    OS --> T2[legacy.BOOKSHOP.BOOK]
    T1 --> MS1[bookshop-mongo-reviews-sink]
    T2 --> MS2[bookshop-mongo-catalogue-sink]
    MS1 -->|replaceOne with upsert, deleteOne by _id| M1[(MongoDB bookshop.book_review)]
    MS2 -->|replaceOne with upsert, deleteOne by _id| M2[(MongoDB catalogue.books)]
....

== How the connector works

For each record the connector resolves the target collection from the topic, builds the document `+_id+` from the
record key, and adds a write operation to a bulk write against that collection. The operation depends on the `op` of
the change event:

[cols="1,2,3"]
|===
| Event | Official description | Write operation in 3.7.1.Final

| Create (`c`) and snapshot read (`r`)
| Create document
| `replaceOne` filtered by `+_id+`, with `upsert: true`, using the `after` state

| Update (`u`)
| Modify the document with the specified identifier
| `replaceOne` filtered by `+_id+`, with `upsert: true`, using the `after` state

| Delete (`d`)
| Remove the document with the specified identifier
| `deleteOne` filtered by `+_id+`

| Tombstone (`null` value)
| --
| Skipped (tombstones exist for Kafka log compaction)
|===

Three consequences follow from these operations:

* **Writes are idempotent.** A replayed create or update replaces the document with the same state again, and a
  replayed delete finds nothing to delete. Kafka Connect delivers records at least once, so this is what keeps a
  restart or a rebalance harmless, as explained for the JDBC sink in
  xref:database/migration/jdbc-sink-connector.adoc#_at_least_once_delivery[at-least-once delivery].
* **The whole document is replaced.** An update does not patch fields; the document becomes the `after` state of the
  row. Fields that another writer added to the document in MongoDB are lost at the next update of that row. Treat the
  target collection as owned by the sink.
* **Truncates are not applied.** Only create, read, update and delete events are handled.

The connector processes the events of a partition in order, and the source connectors key events by primary key, so
all changes of one row are applied in commit order. It gives no transactional guarantee across events or documents: a
legacy transaction that changed three rows becomes three independent writes, and a reader can see the first before
the third.

== Limitations

* **Relational sources only.** The connector consumes events from the Debezium connectors for MariaDB, MySQL, Oracle,
  PostgreSQL and SQL Server. It cannot consume events from the Debezium MongoDB source connector, so it is not a tool
  for MongoDB-to-MongoDB migrations (in those events `after` is a JSON string, not a structure).
* **Native envelopes only.** The value must be a Debezium change event with a `before`/`after` structure. Do not
  apply the xref:database/migration/event-flattening.adoc[event flattening] SMT before this sink; the connector rejects
  values without a non-empty `after` document for inserts and updates. The connector can also unwrap events that the
  source wrote in CloudEvents format (see <<_cloudevents_input>>).
* **Limited schema evolution.** MongoDB has no table schema, so new columns simply appear in the documents written
  after the change. Renamed or dropped columns are not cleaned up in documents written earlier; that needs a
  migration script on the MongoDB side.
* **No metrics.** The official documentation states that this release of the connector does not expose any metrics.

== Installing the connector

The sink is part of the MongoDB connector plug-in archive (`debezium-connector-mongodb`), not a separate download, and
it uses the MongoDB Java driver that the archive contains. The `quay.io/debezium/connect:3.7.1.Final` image includes
that plug-in, so the Compose stacks in this section can use it directly.

The official page gives the connector class as `+io.debezium.connector.mongodb.sink.MongoDbSinkConnector+`. In the
3.7.1.Final JAR the class registered as a Kafka Connect sink is `io.debezium.connector.mongodb.MongoDbSinkConnector`
(the `sink` package holds the task and its helpers). Check what your worker reports before you register the
connector, and use that name:

.Find the class name of the MongoDB sink connector
[source,shell]
----
curl -s http://localhost:8083/connector-plugins | jq -r '.[] | select(.type == "sink") | .class'
# io.debezium.connector.jdbc.JdbcSinkConnector
# io.debezium.connector.mongodb.MongoDbSinkConnector
# ...
----
Reference: https://debezium.io/documentation/reference/stable/connectors/mongodb-sink.html#quick-start[Debezium -- MongoDB sink quick start]

Unlike the MongoDB source connector, the sink does not need a replica set: it only writes. The user in the connection
string needs the `readWrite` role on the target database.

.MongoDB user for the sink
[source,javascript]
----
// mongosh, connected to the MongoDB deployment as an administrator
use admin
db.createUser({
  user: "bookshop_sync",
  pwd: "change-me",
  roles: [
    { role: "readWrite", db: "bookshop" },
    { role: "readWrite", db: "catalogue" }
  ]
})
----
Reference: https://www.mongodb.com/docs/manual/reference/built-in-roles/[MongoDB -- Built-in roles]

== Configuration properties

The official documentation groups the properties as follows.

=== Kafka Connect sink properties

[cols="2,1,4"]
|===
| Property | Default | Description

| `connector.class` | none | The MongoDB sink connector class (see <<_installing_the_connector>>).
| `tasks.max` | `1` | Maximum number of tasks.
| `topics` or `topics.regex` | none | The topics to consume, as a list or as a regular expression.
|===

=== MongoDB connection properties

[cols="2,1,4"]
|===
| Property | Default | Description

| `mongodb.connection.string` | none | Standard MongoDB connection string (URI) of the target deployment, for example `mongodb://localhost:27017/?replicaSet=my-replica-set`.
| `sink.database` | none | Name of the target MongoDB database. All collections of one connector are in this database.
|===

=== Sink behaviour properties

[cols="2,2,4"]
|===
| Property | Default | Description

| `collection.naming.strategy` | `io.debezium.sink.naming.DefaultCollectionNamingStrategy` | Strategy that derives the collection name. The default takes the topic name and replaces dots with underscores. A custom `CollectionNamingStrategy` implementation can be configured instead.
| `collection.name.format` | `+${topic}+` | Template for the collection name.
| `column.naming.strategy` | `io.debezium.sink.naming.DefaultColumnNamingStrategy` | Strategy that names the document fields. The default uses the original field name.
|===

=== Common sink options

[cols="2,1,4"]
|===
| Property | Default | Description

| `field.include.list` | empty | Comma-separated fields of the event value to include, as `fieldName` or `topicName:fieldName`. Not with `field.exclude.list`.
| `field.exclude.list` | empty | Comma-separated fields of the event value to exclude, in the same form. Not with `field.include.list`.
| `batch.size` | `2048` | Maximum number of records written in one batch.
|===

=== CloudEvents option

[cols="2,2,4"]
|===
| Property | Default | Description

| `cloud.events.schema.name.pattern` | `+.*CloudEvents\.Envelope$+` | Regular expression that identifies CloudEvents records by their schema name.
|===

The Kafka Connect error handling properties (`errors.tolerance`, `errors.deadletterqueue.topic.name` and the others
listed on the xref:database/migration/jdbc-sink-connector.adoc#_the_kafka_connect_error_properties[JDBC sink page])
apply to every sink connector. They cover failures in the converter and transformation stages. The official MongoDB
sink documentation does not describe sending failed MongoDB writes to a dead-letter queue, so plan for a failed bulk
write to fail the task, and watch the task status.

== Collection names

With the defaults, the collection name is the topic name with dots replaced by underscores: topic
`modern.public.book_review` becomes the collection `modern_public_book_review` in `sink.database`. That is rarely the
name you want in a migration. Set `collection.name.format` to a literal name when the connector reads a single topic,
or to a template with a prefix or suffix (for example `+mirror_${topic}+`). The default naming strategy is the same
shared class that the JDBC sink uses, which also resolves `+${source.table}+`-style placeholders from the `source` block,
but the MongoDB sink documentation only describes `+${topic}+`; the examples on this page use literal names, one topic
per connector.

Because one connector writes to a single database (`sink.database`), use one connector per target database. The
Bookshop examples use two connectors for that reason.

== From keys to `+_id+`

The record key becomes the `+_id+` of the document, and updates and deletes find the document by that `+_id+`. Debezium
relational source connectors key each event with a structure of the table's primary key columns, so the `+_id+` is an
embedded document, even for a single-column key:

.Event key and the resulting `+_id+`
[source,javascript]
----
// Kafka record key of a change to book_review (PostgreSQL primary key: id text,
// which holds the legacy MongoDB _id as extended JSON)
{ "id": "{\"$oid\": \"6af189a0c788084b3fbe7dcc\"}" }

// _id of the MongoDB document written by the sink
{ "_id": { "id": "{\"$oid\": \"6af189a0c788084b3fbe7dcc\"}" }, ... }

// Composite key, for example ORDER_LINE (ORDER_ID, LINE_NO) from bookshop-oracle-source,
// whose decimal.handling.mode=string turns every NUMBER into a string
{ "_id": { "ORDER_ID": "900017", "LINE_NO": "2" }, ... }
----
Reference: https://debezium.io/documentation/reference/stable/connectors/mongodb-sink.html#mongodb-sink-key-field-mapping[Debezium -- MongoDB sink key field mapping]

What this means in practice:

* Query the documents with the embedded `+_id+` (`+db.book_review.find({ "_id.id": '{"$oid": "6af1..."}' })+` or an
  exact match on the whole embedded document). An exact match on an embedded document depends on field order, which the sink takes
  from the key schema.
* A source table without a primary key produces events with a `null` key, and the sink cannot build an `+_id+` for
  them. Give such a table a key in the source connector with `message.key.columns`.
* Changing the source key (an SMT that rewrites the key, a different primary key after a legacy schema change) creates
  new documents next to the old ones. Keep the key stable for the life of the migration.
* Other `+_id+` shapes, such as a plain string or the original MongoDB `ObjectId`, are not described in the official
  documentation. If you need them, write the documents with a consumer (see
  xref:database/migration/consuming-change-events-in-applications.adoc[Listening to Events in Applications]).

== How values become BSON

The document body is the `after` structure of the event, one field per column, with the column names as they are in
the source (`BOOK_ID` stays upper case; use `column.naming.strategy` to change that). The value conversion follows
the Kafka Connect schema of each field. In the 3.7.1.Final classes the converter maps the primitive types to the
matching BSON types (integers, doubles, booleans, strings, binary), and gives special treatment to exactly four Kafka
Connect logical types: `Decimal` becomes `Decimal128`, and `Date`, `Time` and `Timestamp` become BSON dates.

The Debezium logical types are not converted; they are written in their primitive representation:

[cols="2,2,2"]
|===
| Source column | Event schema | Stored in MongoDB as

| PostgreSQL `uuid` | `STRING`, `io.debezium.data.Uuid` | string
| PostgreSQL `jsonb` | `STRING`, `io.debezium.data.Json` | string (the JSON text, not an embedded document)
| PostgreSQL `numeric(12,2)` (PostgreSQL connector default `precise`) | `BYTES`, `org.apache.kafka.connect.data.Decimal` | `Decimal128`
| PostgreSQL `timestamptz` | `STRING`, `io.debezium.time.ZonedTimestamp` | ISO-8601 string
| PostgreSQL `date` | `INT32`, `io.debezium.time.Date` (days since the epoch) | 32-bit integer
| Oracle `DATE` | `INT64`, `io.debezium.time.Timestamp` (milliseconds) | 64-bit integer
| Oracle `TIMESTAMP(6)` | `INT64`, `io.debezium.time.MicroTimestamp` (microseconds) | 64-bit integer
| Oracle `NUMBER(10)` and `NUMBER(10,2)` from `bookshop-oracle-source` (`decimal.handling.mode=string`) | `STRING` | string (`"7"`, `"24.50"`)
| Oracle `NUMBER(10,2)` with the `precise` default | `BYTES`, `org.apache.kafka.connect.data.Decimal` | `Decimal128`
|===

Dates stored as numbers are the main surprise: a MongoDB query cannot compare them with `ISODate` values, and a TTL
index ignores them. There are two ways to get real BSON dates:

* Set `time.precision.mode=connect` in the **source** connector, so that it emits the Kafka Connect `Date`, `Time` and
  `Timestamp` types. This changes the events for every consumer of those topics and limits precision to milliseconds
  (see xref:database/migration/data-types-and-precision.adoc[Data Types & Precision]). It is reasonable when MongoDB is
  the only consumer, or with a dedicated source connector for the MongoDB pipeline.
* Keep the defaults and convert in a consumer that writes MongoDB itself.

== Bookshop: `book_review` back to MongoDB

The reviews were migrated from MongoDB to PostgreSQL. After the write cut-over the new application owns them, and
the `bookshop-pg-source` connector (topic prefix `modern`, publication `bookshop_reverse_pub`, with `book_review`
added to it by `+ALTER PUBLICATION bookshop_reverse_pub ADD TABLE book_review+`) publishes changes to
`modern.public.book_review`. The table is the one that the lab of the
xref:database/migration/mongodb-connector.adoc[MongoDB Connector] page fills from the legacy collection:

.The `book_review` table (as defined on the MongoDB Connector page)
[source,sql]
----
CREATE TABLE book_review (
    id                 text PRIMARY KEY,   -- the Debezium key: the _id as extended JSON
    book_id            bigint,
    customer_legacy_id bigint,
    rating             smallint,
    title              text,
    body               text,
    helpful_votes      integer,
    created_at         timestamptz,
    document_json      jsonb
);
----
Reference: https://debezium.io/documentation/reference/stable/connectors/postgresql.html#postgresql-data-types[Debezium -- PostgreSQL data type mappings]

.`bookshop-mongo-reviews-sink.json`: PostgreSQL `book_review` into MongoDB
[source,json]
----
{
  "name": "bookshop-mongo-reviews-sink",
  "config": {
    "connector.class": "io.debezium.connector.mongodb.MongoDbSinkConnector",
    "tasks.max": "1",
    "topics": "modern.public.book_review",

    "mongodb.connection.string": "mongodb://bookshop_sync:change-me@mongo:27017/?authSource=admin",
    "sink.database": "bookshop",
    "collection.name.format": "book_review",
    "batch.size": "2048",

    "errors.tolerance": "none",
    "errors.log.enable": "true",
    "errors.log.include.messages": "false"
  }
}
----
Reference: https://debezium.io/documentation/reference/stable/connectors/mongodb-sink.html#mongodb-sink-configuration[Debezium -- MongoDB sink configuration]

The host name `mongo` is the MongoDB service as the Connect container sees it; replace it with your deployment. Add
the `replicaSet` option when the target is a replica set, as in the official connection string example.

.Register the sink and look at a written document
[source,shell]
----
curl -s -X POST -H "Content-Type: application/json" \
     --data @bookshop-mongo-reviews-sink.json http://localhost:8083/connectors

curl -s http://localhost:8083/connectors/bookshop-mongo-reviews-sink/status | jq '.tasks[].state'

docker compose exec mongo mongosh -u bookshop_sync -p change-me --authenticationDatabase admin \
  --quiet --eval 'db.getSiblingDB("bookshop").book_review.find().limit(1)'
----
Reference: https://debezium.io/documentation/reference/stable/connectors/mongodb-sink.html#mongodb-sink-examples[Debezium -- MongoDB sink example configuration]

A written document looks like this (values abbreviated):

.Document written for one `book_review` row
[source,json]
----
{
  "_id": { "id": "{\"$oid\": \"6af189a0c788084b3fbe7dcc\"}" },
  "id": "{\"$oid\": \"6af189a0c788084b3fbe7dcc\"}",
  "book_id": 1001,
  "customer_legacy_id": 501,
  "rating": 5,
  "title": "A classic",
  "body": "Read it twice.",
  "helpful_votes": 12,
  "created_at": "2019-03-14T10:15:00Z",

=== Writing back to the legacy `reviews` collection

The example writes to a new collection, `book_review`, not to the legacy `reviews` collection, on purpose. The sink
cannot reproduce the legacy documents:

* Their `+_id+` is the original `ObjectId`; the sink writes an embedded document that holds the extended JSON of that
  `ObjectId` as a string (`+{ "id": "{\"$oid\": ...}" }+`). Writing into `reviews` would create a second document for
  every review instead of updating the original one.
* Their shape is the legacy one (camel-case field names, arrays such as `tags`, `ISODate` dates); the sink writes the
  flat PostgreSQL row, with `created_at` as a string and `document_json` as JSON text.
* The legacy `bookshop-mongo-source` connector would capture the sink's writes and send them forward again, which is
  the replication loop described in
  xref:database/migration/cut-over-and-reverse-replication.adoc[Cut-over & Reverse Replication].

So there are two options. Either the legacy application reads the new `book_review` collection (often acceptable for
read-only legacy screens during the rollback window), or a small consumer translates each event into a legacy
`reviews` document, parsing `id` (or `document_json`) to rebuild the `ObjectId` and the original fields, and using a
marker field to break the loop. The second option
is the anti-corruption layer in reverse, and it uses the techniques of
xref:database/migration/consuming-change-events-in-applications.adoc[Listening to Events in Applications].

== Bookshop: a MongoDB catalogue from the legacy `BOOK` table

The second example builds a read model while the legacy system is still the owner of the data. The
`bookshop-mongo-catalogue-sink` connector reads the `legacy.BOOKSHOP.BOOK` topic of the `bookshop-oracle-source`
connector and keeps the `books` collection of a `catalogue` database current:

.`bookshop-mongo-catalogue-sink.json`: legacy Oracle `BOOK` into a MongoDB catalogue
[source,json]
----
{
  "name": "bookshop-mongo-catalogue-sink",
  "config": {
    "connector.class": "io.debezium.connector.mongodb.MongoDbSinkConnector",
    "tasks.max": "1",
    "topics": "legacy.BOOKSHOP.BOOK",

    "mongodb.connection.string": "mongodb://bookshop_sync:change-me@mongo:27017/?authSource=admin",
    "sink.database": "catalogue",
    "collection.name.format": "books",
    "field.exclude.list": "legacy.BOOKSHOP.BOOK:SUPPLIER_ID,legacy.BOOKSHOP.BOOK:LAST_UPD",
    "batch.size": "2048"
  }
}
----
Reference: https://debezium.io/documentation/reference/stable/connectors/mongodb-sink.html#mongodb-sink-configuration[Debezium -- MongoDB sink configuration]

Each document gets `+{ "_id": { "BOOK_ID": "1001" } }+`, the upper-case Oracle column names, every `NUMBER` column as a
string (`"PRICE": "24.50"`, because the Bookshop source uses `decimal.handling.mode=string`; with the `precise` default
`PRICE` would be a `Decimal128` and `BOOK_ID` a 64-bit integer), and `PUBLISHED` as milliseconds since the epoch unless
the source uses `time.precision.mode=connect`. A catalogue that needs numeric prices converts them in a consumer, or
reads from a dedicated source connector with different settings. The
`field.exclude.list` entries keep the supplier and the technical timestamp out of the public catalogue.

What the sink cannot do here is join: the catalogue document has `AUTHOR_ID`, not the author's name, because each
event describes one row of one table. When the read model needs data from several tables (a book with its authors,
an order with its lines), build the aggregate in a consumer or with Kafka Streams first, as shown in the Debezium blog
post on DDD aggregates, and let a sink or the consumer write the result.

== CloudEvents input

When the source connector writes events in CloudEvents format (with the CloudEvents converter), the sink recognises
them by their schema name, extracts the Debezium event from the `data` field, and applies it with the usual insert,
update and delete semantics. `cloud.events.schema.name.pattern` changes the pattern that identifies CloudEvents
records. xref:database/migration/serialization-avro-and-schema-registries.adoc[Serialization & Schema Registries]
explains the CloudEvents format.

== What can go wrong

[cols="2,3,3"]
|===
| Symptom | Cause | Fix

| `ClassNotFoundException` or "failed to find any class that implements Connector"
| The class name from the official page does not match the plug-in
| Use the class reported by `/connector-plugins` (`io.debezium.connector.mongodb.MongoDbSinkConnector` in 3.7.1.Final).

| "Value document must contain non-empty 'after' field"
| Events were flattened, or the topic is not a Debezium relational topic
| Remove `ExtractNewRecordState` from the pipeline; check that the topic comes from a relational source connector.

| Duplicate documents for the same row
| The record key changed (SMT or new source key), or another writer uses a different `+_id+`
| Keep the key stable; let only the sink write to the collection.

| Fields added in MongoDB disappear
| Updates replace the whole document
| Keep extra data in another collection, or write with a consumer that updates fields.

| Date queries do not match
| Debezium temporal types are stored as numbers or strings
| Use `time.precision.mode=connect` in the source, or convert in a consumer.

| Collections named `modern_public_book_review`
| `collection.name.format` left at `+${topic}+`
| Set a literal name or a template.

| Task fails after a MongoDB outage
| The bulk write failed
| Restart the task once MongoDB is back; the replayed records are idempotent.
|===
