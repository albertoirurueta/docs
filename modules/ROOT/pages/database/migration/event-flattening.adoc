A Debezium change event is an envelope. Its value has `before`, `after`, `source`, `op` and timestamps, as described
on xref:database/migration/change-event-structure.adoc[Anatomy of a Change Event]. That richness is what a migration
needs in Kafka: the operation type tells a consumer whether to insert, update or delete, `before` allows comparisons,
and `source` gives the position in the legacy transaction log.

Many consumers outside Debezium expect something simpler: one record per row, whose fields are the row's columns.
Generic Kafka Connect sinks (search indexes, object storage, analytics databases, other vendors' JDBC sinks), ksqlDB
or Flink tables, and a lot of hand-written consumers read records in that shape. *Event flattening* is the Debezium
SMT that produces it. The official name is *New Record State Extraction*, and the class is
`io.debezium.transforms.ExtractNewRecordState`. For MongoDB there are two counterparts:
`ExtractNewDocumentState`, which flattens a document event, and `MongoToRelationalMapper`, which projects documents to
fixed relational columns.

This page explains when to flatten during a migration, every option of the three transformations, and what each
delete-handling mode does to the target database. SMTs in general, and the other Debezium transformations, are on
xref:database/migration/single-message-transformations.adoc[Debezium Transformations].

Checked on 2026-11-09 against Debezium 3.7.1.Final. The configuration on this page is derived from the official
documentation and was not run against a live connector, except the `MongoToRelationalMapper` sink, which the lab on
xref:database/migration/mongodb-connector.adoc[MongoDB Connector] ran.

== Do you need it at all?

The most common reason to flatten, writing change events to a relational table with a JDBC sink, does *not* apply to
the Debezium JDBC sink. The official JDBC sink documentation says that the connector consumes native Debezium change
events directly, extracting the `after` section of inserts and updates and using delete events and tombstones for
deletes. `bookshop-pg-mirror-sink`, which copies `BOOK`, `AUTHOR` and `SUPPLIER_CATALOGUE` into the `+legacy_*+` tables,
therefore has no `transforms` at all (see xref:database/migration/jdbc-sink-connector.adoc[JDBC Sink Connector]).
Flattening is needed for:

* *Other sink connectors* that only understand flat records.
* *Consumers that only want state*, such as a cache or a search index that is rebuilt from the latest value of each
  key.
* *Compacted "current state" topics*, where each key's last record (or tombstone) is the row's state.

It is usually *not* what the anti-corruption layer wants. `LegacyBookTranslator` and `LegacyOrderProjector` decide
what to do from `op`, compare `before` and `after`, and record `source` positions in `processed_change` for
idempotency (see xref:database/migration/consuming-change-events-in-applications.adoc[Listening to Events in
Applications]). Flattening removes all of that unless you add it back with `add.fields`.

    T --> JDBC[bookshop-pg-mirror-sink: no SMT]

    T --> OTHER[Other sink: ExtractNewRecordState on the sink]

....

== Where to apply it: source or sink

You can configure `ExtractNewRecordState` on the Debezium source connector or on a sink connector that reads its
topics. The official page recommends the sink when you want Kafka to keep the original events, and that is the right
choice in a migration:

* With the SMT on `bookshop-oracle-source`, *every* consumer of `+legacy.BOOKSHOP.*+` receives flat records. The
  JDBC sink still works, but the translators lose `op` and `before`, and replaying the topic can never recover them.
* With the SMT on the sink, Kafka holds the full events and only that sink sees the flat version.

If a consumer that is not a Kafka Connect sink needs flat records, either flatten in its code, or run a second,
cheap pipeline (for example a Kafka Streams application, or Debezium Server with the SMT) that writes flat copies to
separate topics. Never flatten the source topics of a migration just to make one consumer simpler.

== What the transformation does

For each data change event the SMT replaces the value with the content of `after`, and the value schema with the
schema of `after`. The key is not changed. What happens to a delete depends on `delete.tombstone.handling.mode`,
explained below. Records that are not change events (heartbeats, schema change events) pass through unchanged, but
apply the SMT selectively with a predicate anyway, as the official page recommends.

== A complete sink-side configuration

The configuration below adds flattening to a sink connector that reads the three mirrored legacy topics. Only the
`transforms` and `predicates` keys are Debezium-specific; replace the connector class and its own properties with
those of the sink you use.

.ExtractNewRecordState on a sink connector, with metadata and rewritten deletes
[source,json]
----
{
  "name": "bookshop-legacy-search-sink",
  "config": {
    "connector.class": "<the sink connector class>",
    "topics": "legacy.BOOKSHOP.BOOK,legacy.BOOKSHOP.AUTHOR,legacy.BOOKSHOP.SUPPLIER_CATALOGUE",
    "key.converter": "org.apache.kafka.connect.json.JsonConverter",
    "value.converter": "org.apache.kafka.connect.json.JsonConverter",
    "key.converter.schemas.enable": "true",
    "value.converter.schemas.enable": "true",

    "transforms": "unwrap",
    "transforms.unwrap.type": "io.debezium.transforms.ExtractNewRecordState",
    "transforms.unwrap.delete.tombstone.handling.mode": "rewrite",
    "transforms.unwrap.add.fields": "op,table,source.ts_ms,source.scn",
    "transforms.unwrap.add.headers": "op",
    "transforms.unwrap.predicate": "isLegacyTable",

    "predicates": "isLegacyTable",
    "predicates.isLegacyTable.type": "org.apache.kafka.connect.transforms.predicates.TopicNameMatches",

The sink's Connect worker needs the Debezium SMT classes. They ship in every Debezium connector archive and in the
`quay.io/debezium/connect:3.7.1.Final` image. On a worker that runs only a third-party sink, put the JARs of a
Debezium connector (or the Debezium core JARs) in that sink's plug-in directory, because Kafka Connect isolates
plug-ins from each other.

== Adding metadata: add.fields and add.headers

Flattening removes `op`, `source` and the timestamps. `add.fields` puts selected metadata back into the value and
`add.headers` puts it into Kafka headers. Both take a comma-separated list *without spaces*.

* A plain name such as `op`, `table`, `lsn` or `scn` is looked up in the event and in its `source` block.
* When a name exists twice (for example `ts_ms` at the top level and in `source`), qualify it: `source.ts_ms`.
* A name can be renamed with `<field_name>:<new_field_name>`, for example `source.ts_ms:EVENT_TIMESTAMP`.
* Added fields and headers are prefixed with `+__+` (change it with `add.fields.prefix` and `add.headers.prefix`), and
  for a qualified name an underscore is inserted between the struct and the field: `source.ts_ms` becomes
  `+__source_ts_ms+`.
* A field listed in `add.fields` that does not exist in the event is still added (with a `null` value). A header
  listed in `add.headers` that does not exist is not added.
* Metadata is added to deletes only when `delete.tombstone.handling.mode` keeps the delete as a record, that is
  `rewrite` or `rewrite-with-tombstone`.

Useful metadata for a migration:

[cols="1,3",options="header"]
|===
|Field |Why you want it

|`op`
|Distinguishes a snapshot read (`r`) from an insert (`c`), an update (`u`) and, with `rewrite`, a delete (`d`).

|`table`
|Lets one sink handle several topics, or route by table after a topic routing SMT has merged them.

|`source.ts_ms`
|When the change was committed in the legacy database, which is what replication lag is measured against (see
xref:database/migration/monitoring-logging-and-tracing.adoc[Monitoring, Logging & Tracing]).

|`source.scn` (Oracle), `lsn` (PostgreSQL), `source.gtid` or `file`/`pos` (MySQL)
|The log position. A consumer can store it to skip duplicates after a restart, as the `processed_change` table does.
|===

== delete.tombstone.handling.mode

A delete in the legacy database produces two records: a delete event (`op: "d"`, with `before` and `after: null`)
and a tombstone (same key, `null` value) that lets Kafka log compaction remove the key. `ExtractNewRecordState` must
decide what to keep, because a flat record cannot say "deleted" on its own. In Debezium 3.7 this is controlled by one
option, `delete.tombstone.handling.mode`. The older `drop.tombstones` and `delete.handling.mode` options have been
removed, so old configurations that still use them must be rewritten.

[cols="1,2,3",options="header"]
|===
|Value |Records left for one legacy delete |Effect on a target table written from the flat records

|`tombstone` (default)
|The tombstone only (the delete event is dropped).
|A sink that deletes on a `null` value (a JDBC sink with delete support, an upsert table) removes the row. A sink that
ignores tombstones keeps it: the row is never deleted.

|`drop`
|Nothing.
|The target never learns about deletes. Only acceptable for append-only legacy tables or when deletes are handled
another way.

|`rewrite`
|One record: the `before` values plus `+__deleted+` set to `true`. No tombstone.
|The sink upserts the row with `+__deleted = true+`, a soft delete, so the target table needs a `+__deleted+`
column. Check how inserts and updates fill that column with your sink before you rely on it. Good for audit and for consumers that must see deletes as data. The key is never compacted
away.

|`rewrite-with-tombstone`
|The rewritten record, then the tombstone.
|The sink first marks the row as deleted, then (if it deletes on tombstones) removes it. Compaction still works.

|`delete-to-tombstone`
|One tombstone, converted from the delete event; the original tombstone is removed.
|Like `tombstone`, but the tombstone is produced from the delete event itself. Use it when the source runs with
`tombstones.on.delete=false` and the sink still needs a tombstone to delete.
|===

The mode is the most important flattening decision in a migration, because it decides whether deletes in the legacy
database reach the new one at all. Test it with a real delete (see the verification section) before you trust a
pipeline.

[mermaid]
....
flowchart TB
    D[Legacy DELETE of BOOK 1001] --> E1[Delete event op d]
    D --> E2[Tombstone with null value]
    E1 --> M{delete.tombstone.handling.mode}
    E2 --> M
    M -->|tombstone| R1[tombstone]
    M -->|drop| R2[nothing]
    M -->|rewrite| R3[before values plus __deleted true]
    M -->|rewrite-with-tombstone| R4[rewritten record, then tombstone]
    M -->|delete-to-tombstone| R5[tombstone made from the delete event]
....

== Dropping unchanged fields

`drop.fields.header.name` names a header that contains a list of fields to remove from the flat value. Combined with
the event changes SMT, which writes the list of unchanged fields into a header, it produces records that contain only
the columns an update changed. A sink that applies partial updates then does not overwrite columns that the legacy
statement did not touch.

.Keeping only the changed columns of BOOK updates
[source,properties]
----
transforms=changes,unwrap
transforms.changes.type=io.debezium.transforms.ExtractChangedRecordState
transforms.changes.header.unchanged.name=Unchanged
transforms.unwrap.type=io.debezium.transforms.ExtractNewRecordState
transforms.unwrap.drop.fields.header.name=Unchanged
transforms.unwrap.drop.fields.from.key=false
transforms.unwrap.drop.fields.keep.schema.compatible=true
----
Reference: https://debezium.io/documentation/reference/stable/transformations/event-flattening.html#extract-new-record-state-drop-fields-header-name[Debezium -- Event flattening, drop.fields.header.name]

The order matters: `changes` must run before `unwrap`, because it needs `before` and `after`.
`drop.fields.keep.schema.compatible=true` (the default) removes only optional fields, so a `NOT NULL` column such as
`BOOK_ID` stays. `drop.fields.from.key=true` would remove listed fields from the key as well, which you rarely want.
Partial records only help if every update has a complete `before` image: for Oracle, enable supplemental logging of all
columns on the captured tables.

== Routing by a column value: route.by.field

`route.by.field` sends each flattened record to the topic named by a field of `after` (or of `before` for a delete).
If a legacy `SUPPLIER_CATALOGUE` table had a column naming the target feed, `route.by.field=<that column>` would
send each row to a topic of that name. On a sink connector, where the topic name often becomes the table name, this
lets one connector write to several tables. It is a blunt instrument: the topic names come straight from data, so
validate the values first, and prefer the content-based router (see
xref:database/migration/single-message-transformations.adoc#_content_based_routing_and_filtering[Debezium
Transformations]) when you need an expression.

== replace.null.with.default

`replace.null.with.default` (default `true`) replaces a `null` value with the default value that the source column
declares. This is usually what you want, but in a migration it can hide a difference: if a legacy column
`ACTIVE_FLG CHAR(1) DEFAULT 'Y'` contains a real `NULL` in some old rows, the flattened records show `'Y'` and
reconciliation against the legacy table will report a mismatch that the pipeline introduced. Set it to `false` when
the target must reproduce `NULL` values exactly.

== A consumer that reads flat records

When a consumer reads flattened records, its code shrinks to a map of columns plus the metadata you added. The
listener below is a Spring for Apache Kafka 4.1 consumer for a hypothetical flattened copy of `legacy.BOOKSHOP.BOOK`
(topic `legacy.flat.BOOK`, JSON without schemas). It shows how the `+__op+` and `+__deleted+` fields replace the
envelope.

.A Spring Boot 4.1 listener for flattened BOOK records
[source,java]
----
package com.example.bookshop.migration;

import java.util.Map;

import org.springframework.kafka.annotation.KafkaListener;
import org.springframework.stereotype.Component;

@Component
public class FlatLegacyBookListener {

    private final BookCache cache;

    public FlatLegacyBookListener(BookCache cache) {
        this.cache = cache;
    }

    @KafkaListener(topics = "legacy.flat.BOOK", groupId = "bookshop-book-cache")
    public void onBook(Map<String, Object> row) {
        if (row == null) {
            return; // tombstone: with rewrite-with-tombstone the delete was already handled
        }
        // decimal.handling.mode=string: every Oracle NUMBER, BOOK_ID included, arrives as a JSON string
        long bookId = Long.parseLong(String.valueOf(row.get("BOOK_ID")));
        if ("true".equals(String.valueOf(row.get("__deleted")))) {
            cache.evict(bookId);
            return;
        }
        // __op is "r" for snapshot reads, "c" for inserts and "u" for updates
        cache.put(bookId, (String) row.get("TITLE"), "Y".equals(row.get("ACTIVE_FLG")));
    }

    /** The application's own cache abstraction. */
    public interface BookCache {
        void put(long bookId, String title, boolean active);

        void evict(long bookId);
    }
}
----
Reference: https://docs.spring.io/spring-kafka/reference/kafka/receiving-messages/listener-annotation.html[Spring for Apache Kafka -- @KafkaListener annotation]

The listener assumes a `JsonDeserializer`-style value deserializer that produces a `Map`, and that `+__deleted+` is a
string, which is how the official examples show it. Check the exact JSON your converter writes before you rely on the
type. Consumer configuration, error handling and idempotency are covered on
xref:backend/messaging/spring-boot-kafka.adoc[Spring Boot and Kafka] and
xref:database/migration/consuming-change-events-in-applications.adoc[Listening to Events in Applications].

== MongoDB: ExtractNewDocumentState

The MongoDB connector emits `before` and `after` as JSON *strings* that contain Extended JSON, not as structs, because
documents have no fixed schema. `io.debezium.connector.mongodb.transforms.ExtractNewDocumentState` parses `after` and
turns it into a typed Kafka Connect struct, so a typical sink can consume it. The official page shows it on sink
connectors that consume the MongoDB connector's topics. In the Bookshop example it applies to
`legacy-mongo.bookshop.reviews`, produced by `bookshop-mongo-source` (see xref:database/migration/mongodb-connector.adoc[MongoDB
Connector]).

.ExtractNewDocumentState for the reviews topic
[source,properties]
----
transforms=unwrap
transforms.unwrap.type=io.debezium.connector.mongodb.transforms.ExtractNewDocumentState
transforms.unwrap.array.encoding=array
transforms.unwrap.flatten.struct=true
transforms.unwrap.flatten.struct.delimiter=_
transforms.unwrap.delete.tombstone.handling.mode=rewrite
transforms.unwrap.delete.tombstone.handling.mode.rewrite-with-id=true
transforms.unwrap.add.fields=op,collection,source.ts_ms
transforms.unwrap.add.headers=op
transforms.unwrap.field.name.adjustment.mode=avro
----
Reference: https://debezium.io/documentation/reference/stable/transformations/mongodb-event-flattening.html#mongodb-extract-new-record-state-configuration-options[Debezium -- MongoDB event flattening configuration options]

[cols="2,1,4",options="header"]
|===
|Option |Default |Description

|`array.encoding` |`array` |`array` encodes MongoDB arrays as Connect arrays; every element must have the same type.
`document` encodes each array as a struct with fields `_0`, `_1`, and so on, which allows mixed types.
|`bson.timestamp.handling.mode` |`connect` |`connect` emits a BSON Timestamp as a Connect `Timestamp` (losing the
increment); `struct` keeps `time` and `increment`.
|`flatten.struct` |`false` |Flatten nested documents into top-level fields (`address.city` becomes `address_city`).
|`flatten.struct.delimiter` |`_` |Delimiter used by `flatten.struct`.
|`delete.tombstone.handling.mode` |`tombstone` |`drop`, `tombstone`, `rewrite` or `rewrite-with-tombstone`. The
`delete-to-tombstone` value of the relational SMT is not listed for MongoDB.
|`delete.tombstone.handling.mode.rewrite-with-id` |`false` |With `rewrite`, copy the id from the key into the payload
as `_id`, so a rewritten delete still identifies the document.
|`add.headers.prefix`, `add.headers` |`+__+`, none |As for `ExtractNewRecordState`. Fields come from `source`,
`transaction` and `updateDescription`.
|`add.fields.prefix`, `add.fields` |`+__+`, none |As above; for example `rs` (replica set) and `collection`.
|`field.name.adjustment.mode` |`none` |`avro` replaces characters that are invalid in Avro names with `_`;
`avro_unicode` replaces them with their Unicode escape.
|===

The main limitation for a document-to-table migration: fields with the same name must have the same type in every
document of the collection, and nested documents and arrays produce nested or flattened fields whose set changes from
document to document. A relational sink then sees a different schema for each event. When the target table has fixed
columns, use the relational mapping SMT instead.

== MongoDB: MongoToRelationalMapper

`io.debezium.connector.mongodb.transforms.MongoToRelationalMapper` converts the JSON strings in `before` and `after` into
structs *and keeps the Debezium envelope*: the key, `op`, `source` and headers are unchanged. Because the envelope is
kept, the Debezium JDBC sink applies its normal upsert and delete handling to the result. The official page recommends
applying it at the JDBC sink, so that Kafka keeps the original MongoDB events and a MongoDB sink can still consume them.

For each collection you configure a *projection*: a JSON object under `schema.mapping.<database>.<collection>` whose
members name output columns, with a JSON Pointer `path` into the document and a Kafka Connect `type`. The database and
collection are matched exactly against `source.db` and `source.collection`.

The Bookshop example is the legacy `bookshop.reviews` collection, which the lab of the
xref:database/migration/mongodb-connector.adoc[MongoDB Connector] page moves into PostgreSQL. A review document looks
like this:

.A legacy review document in bookshop.reviews
[source,javascript]
----
db.getSiblingDB("bookshop").reviews.insertOne({
  bookId: NumberLong("1001"),            // legacy BOOK.BOOK_ID
  customerLegacyId: NumberLong("501"),   // legacy CUSTOMER.CUST_ID
  rating: 5,
  title: "A classic",
  body: "Read it twice.",
  createdAt: ISODate("2019-03-14T10:15:00Z"),

Reference: https://debezium.io/documentation/reference/stable/transformations/mongodb-relational-mapping.html#_path_syntax_and_document_changes[Debezium -- MongoDB relational mapping, path syntax]

The target is the PostgreSQL table `book_review`, the same table as on the MongoDB Connector page. The sink writes it
with `primary.key.mode=record_key`, so its primary key is the record key's `id` field: the MongoDB connector's
serialized identifier (`+{"$oid": "..."}+`), which the SMT does not re-key. The other columns come from the projection,
and `document_json` keeps the whole document, so that fields the new model does not use yet (such as `tags`) are not
lost.

.The book_review target table in PostgreSQL

.Debezium JDBC sink with MongoToRelationalMapper for bookshop.reviews
[source,json]
----

How the rules of the SMT shape this configuration:

* *Converters must carry schemas.* The SMT expects a schemaful envelope, so the MongoDB *source* connector must also
  write schema-enabled JSON (or Avro or Protobuf). Turning schemas on at the sink cannot recover them from schemaless
  records.
* *Paths are JSON Pointers into the document*, not into the envelope. `/_id` selects the id; Extended JSON wrappers
  are not fields, so `/_id/$oid` is wrong. An empty path (`""`) selects the whole document.
* *Types are Kafka Connect types.* Primitive names (`int32`, `int64`, `string`, `boolean`, ...) are case-insensitive;
  logical types such as `org.apache.kafka.connect.data.Timestamp`, `org.apache.kafka.connect.data.Decimal` (with
  `scale` and optional `precision`) and `io.debezium.data.Json` must be fully qualified. An ObjectId converts to
  `string`; documents and arrays need `io.debezium.data.Json`.
* *Mixed-type arrays must be mapped to JSON.* An array that holds a string and a number (`["classic", 2019]`) cannot
  be a Connect array; map it to `io.debezium.data.Json`, or leave it to `document_json` as the Bookshop projection does
  with `tags`.
* *Missing paths become `null`.* All output fields are optional, so an upsert clears a column whose source field has
  disappeared. A value that exists but cannot be converted (for example a `rating` stored as `"five"`) raises an
  error instead of becoming `null`.
* *Unmatched collections fall back to schema inference.* If the database or collection name in
  `schema.mapping.<database>.<collection>` is misspelt, the SMT does not complain: it infers a schema per event. Check
  the property name against `source.db` and `source.collection` of a real event.
* *Updates need full documents.* Set `capture.mode=change_streams_update_full` (or
  `change_streams_update_full_with_pre_image`) on `bookshop-mongo-source`. Partial update events are not
  reconstructed.
* `json.output.mode=input` (default) keeps the incoming JSON text as it is; `canonical` reserializes it as MongoDB
  Extended JSON v2 canonical.
* Output names must match `+[A-Za-z_][A-Za-z0-9_]*+`. `document_json` contains *every* field of the document, including
  fields that the projection leaves out, so do not rely on omission to keep personal data out of the target.

To know which projected columns an update changed, run `ExtractChangedRecordState` *after* `map` (with
`change_streams_update_full_with_pre_image` and MongoDB pre-images enabled, so that `before` is available).

== Verifying a flattening configuration

Flattening bugs are silent: the pipeline runs, and the target slowly diverges. Check every operation type once, with a
known row:

. Insert, update and delete one row in the legacy table, for example a test `BOOK` with `BOOK_ID = 999001`.
. Read the sink's input topic with a console consumer that prints keys, headers and `null` values, and confirm that
  the delete produces exactly the records the chosen `delete.tombstone.handling.mode` promises.
. Query the target: the row must exist after the insert, have the new values after the update, and be gone (or have
  `+__deleted = true+`) after the delete.
. Look for `NULL` versus default differences in columns with `DEFAULT` clauses (`replace.null.with.default`).

.Reading a topic with keys, headers and tombstones
[source,shell]
----
kafka-console-consumer.sh --bootstrap-server localhost:9092 \
  --topic legacy.BOOKSHOP.BOOK --from-beginning \
  --formatter-property print.key=true --formatter-property print.headers=true \
  --formatter-property print.partition=true --formatter-property null.literal=TOMBSTONE
----
Reference: https://kafka.apache.org/43/operations/basic-kafka-operations/[Apache Kafka 4.3 -- Basic Kafka operations]

Row-count and checksum reconciliation between the legacy and the new database is covered on
