= Worked Example: Bookshop from Oracle to PostgreSQL
:description: A complete, runnable end-to-end walkthrough of a Debezium migration pipeline for the Bookshop example -- a Docker Compose stack with Oracle AI Database Free (gvenzl/oracle-free 23.26.3), Kafka 4 in KRaft mode, Debezium Connect 3.7.1.Final and PostgreSQL 18; preparing Oracle with ARCHIVELOG, supplemental logging and the C##DBZUSER LogMiner user; seeding the legacy BOOKSHOP schema; registering the bookshop-oracle-source connector and the bookshop-pg-mirror-sink JDBC sink; the initial snapshot; live legacy traffic from a SQL script; transaction metadata, notifications and an incremental snapshot signal; running the Spring Boot anti-corruption layer against the stack; verifying row counts and checksums on both sides; and the pitfalls found while running it on 2026-11-09.

This page puts the whole section together. It builds the Bookshop migration pipeline on one machine, from an empty
directory to rows that change in Oracle and appear in PostgreSQL a second later. The legacy side is the `BOOKSHOP`
schema of the old Java EE/Struts application, in an Oracle pluggable database. The new side is the PostgreSQL 18
database of the Spring Boot `bookshop` application. In between are Kafka, a Debezium Oracle source connector and a
Debezium JDBC sink connector, all started with one Docker Compose file. Every file is shown in full, so you can copy
the directory layout below and run the same steps.

The example follows the order of a real migration, as described in
xref:database/migration/migration-patterns-with-cdc.adoc[Migration Patterns with CDC]:

. prepare the legacy database for change data capture (archive log mode, supplemental logging, a LogMiner user);
. register the source connector and let it take the initial snapshot;
. copy the tables that keep their shape (`BOOK`, `AUTHOR`, `SUPPLIER_CATALOGUE`) into mirror tables with the JDBC sink;
. let the new application translate the tables that change shape (`CUSTOMER`, `ORDERS`, `ORDER_LINE`) through its
  anti-corruption layer;
. generate legacy traffic and watch it arrive;
. verify that both sides match, and repair a table with an incremental snapshot.

The cut-over itself, and reverse replication back to Oracle, continue in
xref:database/migration/cut-over-and-reverse-replication.adoc[Cut-over & Reverse Replication]. The architectural
background (strangler fig, anti-corruption layer, why CDC rather than dual writes) is on
xref:backend/architecture/decisions-and-migrations/migration-path-legacy-to-modern-stack.adoc#_data_synchronisation_during_the_overlap[Migration Path: From a Legacy Stack to a Modern One].

Checked on 2026-11-09 against Debezium 3.7.1.Final, with `gvenzl/oracle-free:23.26.3` (the server reports itself as
"Oracle AI Database 26ai Free Release 23.26.3.0.0", the successor of Oracle Database 23ai Free in the same 23.x
release line), `quay.io/debezium/kafka:3.7.1.Final` and `quay.io/debezium/connect:3.7.1.Final` (Apache Kafka 4.3.1,
KRaft mode) and `postgres:18`. Everything on this page except the Spring Boot application was run with Docker
(Docker Engine 29, Linux arm64 containers, 8 GB of memory for Docker) on 2026-11-09: the compose stack, the Oracle
initialisation scripts, both connectors, the initial snapshot, the traffic script, an incremental snapshot signal and
the verification queries. The outputs shown are from that run, trimmed. The Spring Boot application was not run here;
its code and its own test run are on
xref:database/migration/consuming-change-events-in-applications.adoc[Listening to Events in Applications].

== What you build

image::database-migration-bookshop-stack.svg["The worked example stack: an oracle container with the BOOKSHOP schema in FREEPDB1, a connect container running the bookshop-oracle-source and bookshop-pg-mirror-sink connectors, a kafka container in KRaft mode holding the legacy.BOOKSHOP topics, a postgres container with the legacy mirror tables and the new model, and the Spring Boot bookshop application running on the host",width=720]

Four containers run in one Compose project called `dbz-bookshop`. They reach each other by service name (`oracle`,
`kafka`, `connect`, `postgres`) on the project network, and publish their standard ports to the host:

[cols="1,2,1,3",options="header"]
|===
| Service | Image | Host port | Role

| `oracle`
| `gvenzl/oracle-free:23.26.3`
| 1521
| The legacy database: CDB `FREE`, PDB `FREEPDB1`, schema `BOOKSHOP`

| `kafka`
| `quay.io/debezium/kafka:3.7.1.Final`
| 9092
| One Kafka 4 node in KRaft mode (broker and controller in one process)

| `connect`
| `quay.io/debezium/connect:3.7.1.Final`
| 8083
| Kafka Connect with every Debezium connector, including the Oracle source and the JDBC sink

| `postgres`
| `postgres:18`
| 5432
| The new `bookshop` database: mirror tables and the new model
|===

The Spring Boot `bookshop` application runs outside Docker, against the published ports, as it does on a developer
machine.

The whole flow, from a legacy write to the two kinds of target table, looks like this:

[mermaid]
....
sequenceDiagram
    participant Script as legacy-traffic.sql
    participant Ora as Oracle FREEPDB1
    participant Src as bookshop-oracle-source
    participant K as Kafka
    participant Sink as bookshop-pg-mirror-sink
    participant App as bookshop app
    participant PG as PostgreSQL bookshop
    Script->>Ora: INSERT, UPDATE, DELETE, COMMIT
    Ora-->>Src: redo and archive logs read through LogMiner
    Src->>K: legacy.BOOKSHOP.BOOK, AUTHOR, SUPPLIER_CATALOGUE
    Src->>K: legacy.BOOKSHOP.CUSTOMER, ORDERS, ORDER_LINE
    Src->>K: legacy.transaction (BEGIN and END)
    K->>Sink: BOOK, AUTHOR, SUPPLIER_CATALOGUE events
    Sink->>PG: upsert or delete in legacy_book, legacy_author, legacy_supplier_catalogue
    K->>App: CUSTOMER, ORDERS, ORDER_LINE, BOOK, AUTHOR events
    App->>PG: customer, purchase_order, order_line, book, book_author
....

== Prerequisites

* Docker with Docker Compose v2. Give Docker at least 6 GB of memory; 8 GB is comfortable. Oracle Free alone used
  about 1.5 GB in the run, Kafka about 450 MB and Kafka Connect up to its heap limit.
* About 6 GB of free disk for the images. The Oracle image is 2.3 GB.
* `curl` and, for the application part, Java 21 and Maven.
* Free host ports 1521, 9092, 8083 and 5432. If one of them is taken, see <<_pitfalls_found_while_running_it>>.

No Oracle client is needed on the host: every SQL command runs with SQL*Plus inside the `oracle` container.

The `quay.io/debezium/connect:3.7.1.Final` image already contains the Oracle connector and the Oracle JDBC driver.
The run listed `/kafka/connect/debezium-connector-oracle/ojdbc11-23.26.1.0.0.jar` (and the same jar in the JDBC sink
directory), so no custom image is needed for LogMiner. The image README and the
https://debezium.io/documentation/reference/stable/connectors/oracle.html#oracle-deploying-a-connector[Oracle connector deployment section]
still tell you to add the driver from the Oracle Instant Client. That is only needed for the XStream adapter, which
also needs `xstreams.jar` and the native libraries, or if you build your own Connect image from the connector archive.
Check it on your image with:

.Checking that the Connect image has the Oracle driver
[source,shell]
----
docker run --rm --entrypoint ls quay.io/debezium/connect:3.7.1.Final /kafka/connect/debezium-connector-oracle | grep ojdbc
----
Reference: https://debezium.io/documentation/reference/stable/connectors/oracle.html#oracle-deploying-a-connector[Debezium -- Deploying the Oracle connector]

What each part does:

* **`name: dbz-bookshop`** fixes the project name, so container, network and volume names are predictable
  (`dbz-bookshop-oracle-1`, `dbz-bookshop_oracle-data`) and `docker compose down -v` removes exactly this stack.
* **Host ports are variables with the standard ports as defaults** (`+${KAFKA_HOST_PORT:-9092}+`). Without a `.env`
  file you get 1521, 9092, 8083 and 5432. When those ports are busy, put other values in a `.env` file next to
  `compose.yaml`; nothing else changes (see <<_pitfalls_found_while_running_it>>).
* **Oracle.** `ORACLE_PASSWORD` sets the `SYS` and `SYSTEM` passwords. The two init directories are mounted read-only:
  `init` is executed once, `scripts` holds the traffic script for later. `healthcheck.sh` is shipped in the image and
  reports healthy only when the database is open, which takes a few minutes on the first start because the init
  scripts restart the database.
* **Kafka** runs one KRaft node with three listeners: `PLAINTEXT` on 9092 for the other containers (advertised as
  `kafka:9092`), `CONTROLLER` on 9093 for the KRaft quorum, and `EXTERNAL` on 9094, published on the host as 9092 and
  advertised as `localhost:9092` for the Spring Boot application. The image's entrypoint turns every `+KAFKA_*+`
  variable into a `server.properties` entry and formats the storage with `CLUSTER_ID` on the first start.
  `controller.quorum.bootstrap.servers` replaces the older `controller.quorum.voters`, which the image converts with a
  deprecation warning.
* **Connect** waits until Kafka answers. `GROUP_ID` and the three storage topics identify this Connect cluster; their
  replication factor is 1 because there is only one broker. `HEAP_OPTS` caps the JVM heap (see the pitfalls).
  The worker keeps the image's default converters: `JsonConverter` with schemas embedded in every message.
* **PostgreSQL 18** stores its data under `/var/lib/postgresql`. From version 18 the official image puts `PGDATA` in a
  version-specific directory below that path, so the volume is mounted on the parent directory.

== Step 1: prepare Oracle

=== Archive log mode, supplemental logging and the connector user

LogMiner reads committed changes from the redo logs, so the database must archive them (ARCHIVELOG mode) and must
write enough column data into them (supplemental logging). The connector connects as a common user, `+C##DBZUSER+`,
that exists in the root container and in every PDB. The grants are those of the official LogMiner user example; the
xref:database/migration/oracle-connector.adoc[Oracle Connector] page explains each one, and how to reduce
`SELECT ANY TABLE` and `FLASHBACK ANY TABLE` to the captured tables.

.oracle/init/01-enable-logminer.sh
[source,bash]
----
#!/bin/bash
# Runs once, on the first start of the container, as the oracle OS user.
# 1. Archive log mode (needs a restart to MOUNT state).
# 2. Minimal supplemental logging at database level.
# 3. LogMiner tablespace + common user C##DBZUSER with the grants from the Debezium docs.
set -euo pipefail

mkdir -p /opt/oracle/oradata/recovery_area

sqlplus -s / as sysdba <<'EOF'
WHENEVER SQLERROR EXIT SQL.SQLCODE
ALTER SYSTEM SET db_recovery_file_dest_size = 10G;
ALTER SYSTEM SET db_recovery_file_dest = '/opt/oracle/oradata/recovery_area' SCOPE=SPFILE;
SHUTDOWN IMMEDIATE
STARTUP MOUNT
ALTER DATABASE ARCHIVELOG;
ALTER DATABASE OPEN;
ALTER PLUGGABLE DATABASE ALL OPEN;
ALTER DATABASE ADD SUPPLEMENTAL LOG DATA;
ARCHIVE LOG LIST
EOF

sqlplus -s / as sysdba <<'EOF'
WHENEVER SQLERROR EXIT SQL.SQLCODE
CREATE TABLESPACE logminer_tbs DATAFILE '/opt/oracle/oradata/FREE/logminer_tbs.dbf'
  SIZE 25M REUSE AUTOEXTEND ON MAXSIZE UNLIMITED;
ALTER SESSION SET CONTAINER = FREEPDB1;
CREATE TABLESPACE logminer_tbs DATAFILE '/opt/oracle/oradata/FREE/FREEPDB1/logminer_tbs.dbf'
  SIZE 25M REUSE AUTOEXTEND ON MAXSIZE UNLIMITED;
ALTER SESSION SET CONTAINER = CDB$ROOT;

CREATE USER c##dbzuser IDENTIFIED BY dbz
  DEFAULT TABLESPACE logminer_tbs
  QUOTA UNLIMITED ON logminer_tbs
  CONTAINER=ALL;

GRANT CREATE SESSION TO c##dbzuser CONTAINER=ALL;
GRANT SET CONTAINER TO c##dbzuser CONTAINER=ALL;
GRANT SELECT ON V_$DATABASE TO c##dbzuser CONTAINER=ALL;
GRANT FLASHBACK ANY TABLE TO c##dbzuser CONTAINER=ALL;
GRANT SELECT ANY TABLE TO c##dbzuser CONTAINER=ALL;
GRANT SELECT_CATALOG_ROLE TO c##dbzuser CONTAINER=ALL;
GRANT EXECUTE_CATALOG_ROLE TO c##dbzuser CONTAINER=ALL;
GRANT SELECT ANY TRANSACTION TO c##dbzuser CONTAINER=ALL;
GRANT LOGMINING TO c##dbzuser CONTAINER=ALL;

GRANT CREATE TABLE TO c##dbzuser CONTAINER=ALL;
GRANT LOCK ANY TABLE TO c##dbzuser CONTAINER=ALL;
GRANT CREATE SEQUENCE TO c##dbzuser CONTAINER=ALL;

GRANT EXECUTE ON DBMS_LOGMNR TO c##dbzuser CONTAINER=ALL;
GRANT EXECUTE ON DBMS_LOGMNR_D TO c##dbzuser CONTAINER=ALL;

GRANT SELECT ON V_$LOG TO c##dbzuser CONTAINER=ALL;
GRANT SELECT ON V_$LOG_HISTORY TO c##dbzuser CONTAINER=ALL;
GRANT SELECT ON V_$LOGMNR_LOGS TO c##dbzuser CONTAINER=ALL;
GRANT SELECT ON V_$LOGMNR_CONTENTS TO c##dbzuser CONTAINER=ALL;
GRANT SELECT ON V_$LOGMNR_PARAMETERS TO c##dbzuser CONTAINER=ALL;
GRANT SELECT ON V_$LOGFILE TO c##dbzuser CONTAINER=ALL;
GRANT SELECT ON V_$ARCHIVED_LOG TO c##dbzuser CONTAINER=ALL;
GRANT SELECT ON V_$ARCHIVE_DEST_STATUS TO c##dbzuser CONTAINER=ALL;
GRANT SELECT ON V_$TRANSACTION TO c##dbzuser CONTAINER=ALL;

GRANT SELECT ON V_$MYSTAT TO c##dbzuser CONTAINER=ALL;
GRANT SELECT ON V_$STATNAME TO c##dbzuser CONTAINER=ALL;
EXIT
EOF
----
Reference: https://debezium.io/documentation/reference/stable/connectors/oracle.html#_preparing_the_database[Debezium -- Oracle: preparing the database] and https://debezium.io/documentation/reference/stable/connectors/oracle.html#creating-users-for-the-connector[Creating a user account for the connector]

The script runs as the `oracle` operating-system user, so `sqlplus / as sysdba` works without a password.
`SHUTDOWN IMMEDIATE` followed by `STARTUP MOUNT` is the only way to switch on archive log mode; the
`ALTER PLUGGABLE DATABASE ALL OPEN` line makes sure `FREEPDB1` is open again before the next script runs. The data
file paths (`+/opt/oracle/oradata/FREE/...+` and `+/opt/oracle/oradata/FREE/FREEPDB1/...+`) are the ones used by the
`gvenzl/oracle-free` image.

=== The legacy schema and its seed data

The second script creates the `BOOKSHOP` user and its six tables in `FREEPDB1`, with the column names and types of the
legacy application, plus the signal table that Debezium reads ad hoc commands from. It turns on supplemental logging
for all columns of every captured table, so that update and delete events carry the full before-image of the row.
The seed data is generated with PL/SQL loops, so every run produces the same 40 authors, 200 books, 400 supplier
catalogue rows, 120 customers, 300 orders and 600 order lines.

.oracle/init/02-bookshop-schema.sql
[source,sql]
----
-- Legacy Bookshop schema and seed data, in the FREEPDB1 pluggable database.
-- Runs once as SYS, after 01-enable-logminer.sh.
WHENEVER SQLERROR EXIT SQL.SQLCODE
ALTER SESSION SET CONTAINER = FREEPDB1;

CREATE USER bookshop IDENTIFIED BY bookshop
  DEFAULT TABLESPACE users QUOTA UNLIMITED ON users;
GRANT CREATE SESSION, CREATE TABLE, CREATE SEQUENCE TO bookshop;

ALTER SESSION SET CURRENT_SCHEMA = bookshop;

CREATE TABLE author (
  author_id   NUMBER(10)    PRIMARY KEY,
  full_name   VARCHAR2(200) NOT NULL
);

CREATE TABLE book (
  book_id     NUMBER(10)    PRIMARY KEY,
  isbn        VARCHAR2(13)  NOT NULL,
  title       VARCHAR2(200) NOT NULL,
  author_id   NUMBER(10)    REFERENCES author (author_id),
  price       NUMBER(10,2),
  currency    CHAR(3),
  published   DATE,
  active_flg  CHAR(1)       DEFAULT 'Y' CHECK (active_flg IN ('Y', 'N')),
  supplier_id NUMBER(10),
  last_upd    DATE          DEFAULT SYSDATE
);

CREATE TABLE customer (
  cust_id     NUMBER(10)    PRIMARY KEY,
  cust_name   VARCHAR2(200) NOT NULL,
  email       VARCHAR2(320),
  status_cd   CHAR(1)       DEFAULT 'A' CHECK (status_cd IN ('A', 'I')),
  created_dt  DATE          DEFAULT SYSDATE
);

CREATE TABLE orders (
  order_id    NUMBER(12)    PRIMARY KEY,
  cust_id     NUMBER(10)    REFERENCES customer (cust_id),
  order_dt    DATE          DEFAULT SYSDATE,
  status_cd   VARCHAR2(2)   DEFAULT 'NW' CHECK (status_cd IN ('NW', 'PD', 'SH', 'CN')),
  total_amt   NUMBER(12,2)
);

CREATE TABLE order_line (
  order_id    NUMBER(12)    REFERENCES orders (order_id),
  line_no     NUMBER(4),
  book_id     NUMBER(10)    REFERENCES book (book_id),
  qty         NUMBER(5),
  unit_price  NUMBER(10,2),
  CONSTRAINT order_line_pk PRIMARY KEY (order_id, line_no)
);

CREATE TABLE supplier_catalogue (
  supplier_id    NUMBER(10),
  isbn           VARCHAR2(13),
  supplier_price NUMBER(10,2),
  feed_ts        TIMESTAMP,
  CONSTRAINT supplier_catalogue_pk PRIMARY KEY (supplier_id, isbn)
);

CREATE TABLE debezium_signal (
  id   VARCHAR2(42)   PRIMARY KEY,
  type VARCHAR2(32)   NOT NULL,
  data VARCHAR2(2048)
);

CREATE SEQUENCE order_seq START WITH 100001;

-- The connector writes incremental-snapshot watermarks into the signal table.
GRANT INSERT, DELETE ON debezium_signal TO c##dbzuser;

-- Full before-images for every captured table (updates and deletes carry all columns).
ALTER TABLE author             ADD SUPPLEMENTAL LOG DATA (ALL) COLUMNS;
ALTER TABLE book               ADD SUPPLEMENTAL LOG DATA (ALL) COLUMNS;
ALTER TABLE customer           ADD SUPPLEMENTAL LOG DATA (ALL) COLUMNS;
ALTER TABLE orders             ADD SUPPLEMENTAL LOG DATA (ALL) COLUMNS;
ALTER TABLE order_line         ADD SUPPLEMENTAL LOG DATA (ALL) COLUMNS;
ALTER TABLE supplier_catalogue ADD SUPPLEMENTAL LOG DATA (ALL) COLUMNS;
ALTER TABLE debezium_signal    ADD SUPPLEMENTAL LOG DATA (ALL) COLUMNS;

-- Seed data: 40 authors, 200 books, 400 catalogue rows, 120 customers,
-- 300 orders with 1 to 3 lines each. Deterministic, so every run gives the same counts.
BEGIN
  FOR i IN 1 .. 40 LOOP
    INSERT INTO author (author_id, full_name) VALUES (i, 'Author ' || LPAD(i, 3, '0'));
  END LOOP;

  FOR i IN 1 .. 200 LOOP
    INSERT INTO book (book_id, isbn, title, author_id, price, currency, published,
                      active_flg, supplier_id, last_upd)
    VALUES (i,
            '978' || LPAD(1000000000 + i, 10, '0'),
            'Legacy Title ' || LPAD(i, 4, '0'),
            MOD(i - 1, 40) + 1,
            ROUND(9.99 + MOD(i * 7, 4000) / 100, 2),
            CASE WHEN MOD(i, 10) = 0 THEN 'USD' ELSE 'EUR' END,
            DATE '2000-01-01' + i * 30,
            CASE WHEN MOD(i, 25) = 0 THEN 'N' ELSE 'Y' END,
            MOD(i, 2) + 1,
            DATE '2024-06-01' + MOD(i, 300));

    INSERT INTO supplier_catalogue (supplier_id, isbn, supplier_price, feed_ts)
    VALUES (1, '978' || LPAD(1000000000 + i, 10, '0'),
            ROUND(5.50 + MOD(i * 7, 4000) / 120, 2), TIMESTAMP '2026-10-01 06:00:00');
    INSERT INTO supplier_catalogue (supplier_id, isbn, supplier_price, feed_ts)
    VALUES (2, '978' || LPAD(1000000000 + i, 10, '0'),
            ROUND(5.75 + MOD(i * 7, 4000) / 115, 2), TIMESTAMP '2026-10-01 06:30:00');
  END LOOP;

  FOR i IN 1 .. 120 LOOP
    INSERT INTO customer (cust_id, cust_name, email, status_cd, created_dt)
    VALUES (i, 'Customer ' || LPAD(i, 4, '0'), 'customer' || i || '@example.com',
            CASE WHEN MOD(i, 9) = 0 THEN 'I' ELSE 'A' END,
            DATE '2015-01-01' + i * 20);
  END LOOP;

  FOR i IN 1 .. 300 LOOP
    INSERT INTO orders (order_id, cust_id, order_dt, status_cd, total_amt)
    VALUES (i, MOD(i - 1, 120) + 1, DATE '2025-01-01' + MOD(i, 600),
            CASE MOD(i, 4) WHEN 0 THEN 'NW' WHEN 1 THEN 'PD' WHEN 2 THEN 'SH' ELSE 'CN' END,
            0);
    FOR l IN 1 .. MOD(i, 3) + 1 LOOP
      INSERT INTO order_line (order_id, line_no, book_id, qty, unit_price)
      SELECT i, l, b.book_id, MOD(i + l, 3) + 1, b.price
        FROM book b
       WHERE b.book_id = MOD(i * 13 + l * 7, 200) + 1;
    END LOOP;
    UPDATE orders o
       SET total_amt = (SELECT SUM(qty * unit_price) FROM order_line ol WHERE ol.order_id = o.order_id)
     WHERE o.order_id = i;
  END LOOP;
  COMMIT;
END;
/
EXIT
----
Reference: https://debezium.io/documentation/reference/stable/connectors/oracle.html#_preparing_the_database[Debezium -- Oracle: supplemental logging] and https://debezium.io/documentation/reference/stable/configuration/signalling.html#debezium-signaling-enabling-source-signaling-channel[Debezium -- Enabling the source signaling channel]

Two lines in this script are easy to miss:

* `+GRANT INSERT, DELETE ON debezium_signal TO c##dbzuser+`. An incremental snapshot writes open and close watermarks
  into the signal table, as the connector user. Without this grant the snapshot request is accepted and then fails with
  `ORA-41900: missing INSERT privilege on "BOOKSHOP"."DEBEZIUM_SIGNAL"`, as the first run of this example showed.
* The `DEBEZIUM_SIGNAL` table gets supplemental logging like the others. The connector finds signal rows in the redo
  log, so the table must be logged, but it does not have to be in `table.include.list`.

== Step 2: prepare PostgreSQL

The new database gets three groups of tables. The mirror tables are written 1:1 by the JDBC sink and keep the legacy
column names in lower case. The new model is written by the Spring Boot consumers; its DDL is the same as on
xref:database/migration/consuming-change-events-in-applications.adoc#_the_tables_the_consumer_writes[Listening to Events in Applications],
including the nullable columns that let a placeholder parent row exist before its own event arrives. The
`processed_change` table is the consumers' idempotency ledger. The mirror DDL and the `bookshop_mirror` role are the
same as on xref:database/migration/jdbc-sink-connector.adoc#_prepare_the_mirror_tables[JDBC Sink Connector].

.postgres/init/01-bookshop.sql
[source,sql]
----
-- New Bookshop database (PostgreSQL 18), schema public.
-- In the real application Liquibase owns these tables; they are created here
-- so that the stack can run without the application.

-- 1. Mirror (staging) tables, written 1:1 by the bookshop-pg-mirror-sink JDBC sink.
--    Column names are the legacy names, lower-cased.
CREATE ROLE bookshop_mirror LOGIN PASSWORD 'change-me';

CREATE TABLE legacy_book (
  book_id     bigint PRIMARY KEY,   -- NUMBER(10)   -> string "7" (decimal.handling.mode=string)
  isbn        varchar(13),          -- VARCHAR2(13) -> STRING
  title       varchar(200),
  author_id   bigint,
  price       numeric(10,2),        -- NUMBER(10,2) -> string "24.50", cast by PostgreSQL
  currency    char(3),
  published   timestamp,            -- DATE         -> io.debezium.time.Timestamp
  active_flg  char(1),              -- 'Y' / 'N', kept as in the legacy table
  supplier_id bigint,
  last_upd    timestamp
);

CREATE TABLE legacy_author (
  author_id   bigint PRIMARY KEY,
  full_name   varchar(200)
);

CREATE TABLE legacy_supplier_catalogue (
  supplier_id    bigint,
  isbn           varchar(13),
  supplier_price numeric(10,2),
  feed_ts        timestamp,         -- TIMESTAMP(6) -> io.debezium.time.MicroTimestamp
  PRIMARY KEY (supplier_id, isbn)
);

GRANT SELECT, INSERT, UPDATE, DELETE
  ON legacy_book, legacy_author, legacy_supplier_catalogue TO bookshop_mirror;

-- 2. The new model, written by the Spring Boot consumers (anti-corruption layer).
--    Nullable columns on purpose: a placeholder parent row can exist before its event arrives.
CREATE TABLE author (
  id        bigint PRIMARY KEY,
  full_name text
);

CREATE TABLE book (
  id           bigint PRIMARY KEY,
  isbn         text,
  title        text,
  price        numeric(12,2),
  currency     char(3),
  published_on date,
  active       boolean,
  supplier_id  bigint,
  updated_at   timestamptz
);

CREATE TABLE book_author (
  book_id   bigint NOT NULL REFERENCES book (id) ON DELETE CASCADE,
  author_id bigint NOT NULL REFERENCES author (id),
  PRIMARY KEY (book_id, author_id)
);

CREATE TABLE customer (
  id         uuid PRIMARY KEY,
  legacy_id  bigint UNIQUE,
  name       text,
  email      text,
  status     text CHECK (status IN ('ACTIVE', 'INACTIVE')),
  created_at timestamptz
);

  id          uuid PRIMARY KEY,
  legacy_id   bigint UNIQUE,

  total       numeric(12,2)
);

CREATE TABLE order_line (
  order_id   uuid NOT NULL REFERENCES purchase_order (id) ON DELETE CASCADE,
  line_no    int NOT NULL,
  book_id    bigint,
  quantity   int,
  unit_price numeric(12,2),
  PRIMARY KEY (order_id, line_no)
);

  source_position text NOT NULL,

  type varchar(32) NOT NULL,
  data varchar(2048)

The properties, grouped by purpose:

[cols="2,3",options="header"]
|===
| Properties | Why they are set this way

| `database.dbname=FREE`, `database.pdb.name=FREEPDB1`
| The connector logs in to the CDB (LogMiner runs in the root container) and captures tables of the PDB. `FREE` is also
  the service name the listener registers.

| `topic.prefix=legacy`, `table.include.list`
| Topics are named `legacy.BOOKSHOP.<TABLE>`. Only the six application tables are listed; the signal table is not.

| `snapshot.mode=initial`
| Snapshot the current rows once, then stream. See xref:database/migration/initial-snapshots.adoc[Initial Snapshots].

| `decimal.handling.mode=string`
| Every Oracle `NUMBER` becomes a JSON string such as `"24.50"`, which the Spring Boot consumers read as `BigDecimal`
  without loss. This also applies to integer columns such as `NUMBER(10)` keys, which become `"7"`, not `7`; see the
  sample event below and the pitfalls.

| `log.mining.strategy=hybrid`
| The fast online catalog plus Debezium's own schema model, so DDL on captured tables is tracked. `redo_log_catalog` is
  deprecated.

| `+schema.history.internal.*+`
| The schema history topic `legacy.schema-history`, which the connector needs to restart.
  `store.only.captured.tables.ddl=false` (the default) records the structure of every table in the database, not only
  the six captured ones. A cut-over needs that full DDL history: removing `BOOK` and `AUTHOR` from the include list
  after the write cut-over, and adding them back in a rollback, then only means editing `table.include.list`, with no
  recovery snapshot (see
  xref:database/migration/cut-over-and-reverse-replication.adoc#_rollback[Cut-over & Reverse Replication]). The
  configuration on this page uses the default `false`; the 2026-11-09 run used `true`, which does not affect the steps
  shown here.

| `provide.transaction.metadata=true`
| Adds a `transaction` block to every event and publishes `BEGIN`/`END` events to `legacy.transaction`, which the order
  projector uses to know when an order and its lines are complete.

| `heartbeat.interval.ms=10000`
| A heartbeat record every 10 seconds on `+__debezium-heartbeat.legacy+`. With `database.pdb.name` set, the connector
  tracks changes inside the PDB only, and the official documentation requires `heartbeat.action.query` as well, so
  that a quiet `FREEPDB1` still produces a change to advance the offset. This short lab, where the traffic script runs
  minutes after the snapshot, was run without it. For a pipeline that runs for days or weeks, add the
  `BOOKSHOP.DEBEZIUM_HEARTBEAT` table to the schema script and to `table.include.list`, and set
  `heartbeat.action.query`, as in the full configuration on the xref:database/migration/oracle-connector.adoc[Oracle Connector] page, which also
  sets `log.mining.query.filter.mode=in`.

| `+signal.*+`, `+notification.*+`
| Signals from the `DEBEZIUM_SIGNAL` table and from the `legacy.signals` topic; progress notifications to
  `legacy.notifications`. `signal.data.collection` uses the PDB name; see the pitfalls.
|===

The sink reads the three topics whose tables keep their shape and writes each event to `legacy_<table>`:
`+legacy_${source.table}+` gives `legacy_BOOK`, and because identifiers are not quoted PostgreSQL folds it to
`legacy_book`, the table created in step 2. `insert.mode=upsert` with `primary.key.mode=record_key` makes every write

`delete.enabled=true` turns delete events into `DELETE` statements. The
xref:database/migration/jdbc-sink-connector.adoc[JDBC Sink Connector] page explains each property and adds batching,
connection pool and dead-letter settings for production.

string parameters untyped, so PostgreSQL casts `"7"` to `bigint` and `"24.50"` to `numeric` when it writes the
column. It is needed here because the source uses `decimal.handling.mode=string` for the application consumers; with
the default `precise` mode, numbers arrive as integers and `Decimal` values and the setting is unnecessary.

== Step 6: run the anti-corruption layer

`CUSTOMER`, `ORDERS` and `ORDER_LINE` do not map 1:1 to the new model: numeric keys become `uuid` keys, status codes
become words, `ORDERS` plus `ORDER_LINE` become the `purchase_order` aggregate, and the single `AUTHOR_ID` of a book
becomes a row in `book_author`. Those topics are consumed by the new application itself. The three components
`LegacyBookTranslator`, `LegacyCustomerTranslator` and `LegacyOrderProjector`, their envelope record, the idempotency
ledger and the error handling are listed in full on
xref:database/migration/consuming-change-events-in-applications.adoc[Listening to Events in Applications]. This
section only shows how to point the application at this stack.

The application's `application.yml` from that page already uses the stack's standard ports:

Three things connect the application to this particular stack:

* `bootstrap-servers: localhost:9092` reaches the `EXTERNAL` listener. If you change `KAFKA_HOST_PORT`, change it here
  too; if the application runs in a container on the same Compose network, use `kafka:9092` instead.
* `auto-offset-reset: earliest` makes a new consumer group start at the beginning of the topics, which hold the
  initial snapshot. With `latest` the application would only see changes made after it started.
* The message format. The consumer page assumes `decimal.handling.mode=string`, which this connector uses, and
  documents that the envelope reader accepts both bare envelopes and the `+{"schema": ..., "payload": ...}+` form. This
  stack keeps schemas embedded (the Connect default) because the JDBC sink needs them; see the pitfalls. Integer
  columns arrive as strings too (`"BOOK_ID":"7"`); the consumer's `LegacyValues.longValue` parses both forms.

The application connects to PostgreSQL as the database owner `bookshop` here. In production it gets its own role with
rights on the new-model tables only, and the mirror sink keeps `bookshop_mirror`; see
xref:database/migration/security-and-data-protection.adoc[Security & Data Protection].

== Step 7: generate legacy traffic

The traffic script plays the legacy application for a moment: a new author and book, price changes, the supplier feed,
a new customer placing an order, order status changes, a rolled-back mistake and a delete. Each block is one
transaction, as the Struts application would commit it.

.oracle/scripts/legacy-traffic.sql
[source,sql]
----
-- Simulates what the legacy Struts application does during a normal day.
-- Run as BOOKSHOP in FREEPDB1, while the connectors are running.
WHENEVER SQLERROR EXIT SQL.SQLCODE
SET FEEDBACK ON

-- 1. Two new authors (one is a typo) and a new book (three inserts, one transaction).
INSERT INTO author (author_id, full_name) VALUES (41, 'Ada Byron');
INSERT INTO author (author_id, full_name) VALUES (42, 'A. Byron');
INSERT INTO book (book_id, isbn, title, author_id, price, currency, published,
                  active_flg, supplier_id, last_upd)
VALUES (201, '9781000000201', 'Notes on the Analytical Engine', 41, 39.90, 'EUR',
        DATE '2026-10-15', 'Y', 1, SYSDATE);
COMMIT;

-- 2. A price change and a de-listing (updates).
UPDATE book SET price = 24.50, last_upd = SYSDATE WHERE book_id = 7;
UPDATE book SET active_flg = 'N', last_upd = SYSDATE WHERE book_id = 12;
COMMIT;

-- 3. The nightly supplier feed: one new row, one changed price, one removed title.
INSERT INTO supplier_catalogue (supplier_id, isbn, supplier_price, feed_ts)
VALUES (1, '9781000000201', 21.00, SYSTIMESTAMP);
UPDATE supplier_catalogue
   SET supplier_price = 12.30, feed_ts = SYSTIMESTAMP
 WHERE supplier_id = 2 AND isbn = '9781000000007';
DELETE FROM supplier_catalogue WHERE supplier_id = 2 AND isbn = '9781000000012';
COMMIT;

-- 4. A new customer places an order with two lines (one transaction, three tables).
INSERT INTO customer (cust_id, cust_name, email, status_cd, created_dt)
VALUES (121, 'Grace Hopper', 'grace@example.com', 'A', SYSDATE);
INSERT INTO orders (order_id, cust_id, order_dt, status_cd, total_amt)
VALUES (order_seq.NEXTVAL, 121, SYSDATE, 'NW', 64.40);

* The key and every `NUMBER` column are strings, because of `decimal.handling.mode=string`: `"BOOK_ID":"7"`,

* Oracle `DATE` columns (`PUBLISHED`, `LAST_UPD`) are `io.debezium.time.Timestamp`: epoch milliseconds, with no time

  application really used (`legacy-time-zone`).
* `before` has all the columns because of `SUPPLEMENTAL LOG DATA (ALL) COLUMNS`. Without it, `before` would hold only
  the key and the changed columns.
* `source.scn` and `source.commit_scn` give the position of the change in the redo stream; together with `txId` they
  are what the consumers use as an idempotency key. `source.user_name` is the Oracle user that made the change, which
  becomes important for loop prevention after the cut-over.
* `transaction` is there because `provide.transaction.metadata=true`.

A sink connector's consumer group is named `connect-<connector name>`. Its committed offsets move when the worker
flushes offsets (every 60 seconds by default, `OFFSET_FLUSH_INTERVAL_MS`), so the lag can show a few dozen records for
up to a minute even though the rows are already in PostgreSQL. In one run the group showed a lag of 41 on `AUTHOR`
while `legacy_author` already had all the rows; a minute later it was 0. Judge freshness by the data (or by the source
connector's `MilliSecondsBehindSource` metric, see
xref:database/migration/monitoring-logging-and-tracing.adoc[Monitoring, Logging & Tracing]), not by a single lag
reading. The `BOOK` offset is 404 because of the incremental snapshot in the next step.

== Pitfalls found while running it

These are the problems the run on 2026-11-09 actually hit, with the fix that is already in the files above.

Host ports already in use::
`docker compose up` fails with `Bind for 0.0.0.0:<port> failed: port is already allocated` when another process on the
machine already uses one of the standard ports. The containers talk to each other by service name, so only the
published ports matter. The fix is the `+${..._HOST_PORT:-default}+` variables in `compose.yaml`: override the busy
port in a `.env` file next to it, for example `KAFKA_HOST_PORT=9192`. The advertised `EXTERNAL` listener follows the
same variable (the Compose file does this), and the application's `bootstrap-servers` must be changed to match.

Kafka Connect killed with exit code 137::
The `connect` container stopped while it was still loading plugins; `docker inspect` showed `OOMKilled=true`. Docker's
virtual machine was out of memory, with Oracle using about 1.5 GB. Lowering the Connect heap to `-Xms256M -Xmx768M`
(`HEAP_OPTS`) was enough for this example; if it still happens, give Docker more memory or stop containers you do not
need. When a container exits with 137, check `OOMKilled` before looking for a configuration
error.

`signal.data.collection` with the CDB name was silently ignored::
The Oracle connector documentation says that for a pluggable database the signal collection uses the name of the root
database, which would be `FREE.BOOKSHOP.DEBEZIUM_SIGNAL`. With that value the connector started and streamed normally,
but a `log` signal inserted into the table never appeared in the log. With the PDB name,
`FREEPDB1.BOOKSHOP.DEBEZIUM_SIGNAL`, the same signal was logged (`+Signal received at offset ...+`) and
`execute-snapshot` signals worked. Debezium 3.7.1 matches the signal table by the PDB name, which is also the `db`
value in every event's `source` block. If signals seem to do nothing, check this first; there is no error.

Incremental snapshot failed with ORA-41900::
The first `execute-snapshot` signal was accepted (`+Requested 'INCREMENTAL' snapshot ...+`) and then failed with
`ORA-41900: missing INSERT privilege on "BOOKSHOP"."DEBEZIUM_SIGNAL"`. The connector writes snapshot window watermarks
into the signal table as `+C##DBZUSER+`. The official grant list covers reading, not this write. Fix:
`+GRANT INSERT, DELETE ON bookshop.debezium_signal TO c##dbzuser+` (in `02-bookshop-schema.sql`).

The signal table in `table.include.list`::
With `BOOKSHOP.DEBEZIUM_SIGNAL` in the include list, the signal rows were also emitted as change events, to a
`legacy.BOOKSHOP.DEBEZIUM_SIGNAL` topic that nobody needs. Leaving the table out of the include list, as the final
configuration does, still lets the connector read signals from it, as long as the table has supplemental logging.

`decimal.handling.mode=string` makes keys strings, and the sink then failed::
The Spring Boot consumers want decimals as strings. With that mode, the Oracle connector writes every `NUMBER` as a
string, including `NUMBER(10)` keys such as `BOOK_ID` and `SUPPLIER_ID`; the official numeric type mapping says so,
but it is easy to read it as applying only to decimals. The sink task then failed on the first batch with
`ERROR: column "supplier_id" is of type bigint but expression is of type character varying`. Adding
`?stringtype=unspecified` to the sink's JDBC URL lets PostgreSQL cast the values to the column types, and the sink
recovered after a task restart (`POST /connectors/bookshop-pg-mirror-sink/tasks/0/restart`). The alternative is to
keep `precise` and let the consumers decode `Decimal` values from the embedded schema or use Avro.

JSON without schemas makes the JDBC sink skip every record::
A source configured with `value.converter.schemas.enable=false` produces schemaless envelopes. A test sink fed with
them stayed `RUNNING`, wrote nothing, and logged
`+Ignore this record because it isn't a Debezium record, then cannot resolve a collection name+` for every record. The
JDBC sink needs the record schema to recognise the Debezium envelope, so when the same topics feed both a JDBC sink and
an application, keep schemas embedded (the Connect default, as in this stack) or use Avro with a registry. The same
warning appears once per tombstone with schemas enabled; that one is harmless, because the delete event before it has
already removed the row.

Lag that does not mean what it seems::
See <<_connector_health_and_lag>>: the sink's committed offsets trail the data by up to the offset flush interval.
