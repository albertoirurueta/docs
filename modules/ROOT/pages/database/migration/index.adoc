= Database Migration
:description: A practical guide to migrating a database from a legacy system to a new one without a big-bang cut-over, using Debezium change data capture (CDC) to turn every committed change into an event, publish it to Apache Kafka or another broker, and apply it to the new database while both systems run side by side: strategies and patterns, Debezium architecture, change events, source and sink connectors, snapshots, signals, transformations, the Debezium Engine and Server, schema changes, a worked Oracle to PostgreSQL migration, verification, cut-over with reverse replication, operations, a bibliography and a printable cheat sheet.
:keywords: database migration, legacy migration, change data capture, CDC, Debezium, Debezium 3.7, Kafka Connect, Apache Kafka, strangler fig, anti-corruption layer, dual writes, transaction log tailing, Oracle LogMiner, PostgreSQL logical decoding, MySQL binlog, SQL Server CDC, MongoDB change streams, JDBC sink connector, snapshots, incremental snapshots, signaling, notifications, single message transformations, outbox event router, Debezium Server, Debezium Engine, reverse replication, cut-over, reconciliation, Strimzi, Debezium Operator, bibliography, cheat sheet

include::partial$ai-disclaimer.adoc[]

Most systems that need replacing are attached to a database that cannot be switched off. The legacy application keeps
writing to it while the new system is built, tested and rolled out one capability at a time, so for weeks or months
two databases hold overlapping data and both must stay correct. This section explains how to do that with
https://debezium.io/[Debezium], the open source change data capture (CDC) platform. Debezium reads the legacy
database's own transaction log, turns every committed insert, update and delete into an event, and publishes the events
to a broker (Apache Kafka by default). Those events are then used to listen to the legacy system: to fill and maintain the new database,
to feed new services, to verify that both sides agree and, after the cut-over, to keep the legacy side current
in the other direction until it can be retired.

The architecture pages of this site already explain *why* log-based CDC is the safer way to keep a legacy and a new
database in sync:

* xref:backend/architecture/decisions-and-migrations/migration-overview.adoc[Migration Overview] sets the rules of
  every migration on this site: no big bang, the strangler fig, and showing value early.
* xref:backend/architecture/decisions-and-migrations/migration-path-legacy-to-modern-stack.adoc#_data_synchronisation_during_the_overlap[Migration
  Path: From a Legacy Stack to a Modern One] compares dual writes with CDC for the overlap period.
* xref:backend/architecture/decisions-and-migrations/migration-path-monolith-to-microservices.adoc[Migration Path: From
  a Monolith to Microservices] uses transaction-log tailing when the monolith's code cannot be changed.
* xref:backend/architecture/architectural-patterns/transactional-outbox.adoc[Transactional Outbox] compares the polling
  publisher with transaction-log tailing.
* xref:backend/messaging/kafka-connect.adoc[Kafka Connect] explains the runtime that most Debezium deployments use.

This section explains *how*: every concept of the official Debezium documentation, applied to the job of generating
change events from a legacy database, listening to them and using them to migrate the data.

The content was checked on 2026-11-09 against **Debezium 3.7.1.Final**, the current stable release.

=== Running example: Bookshop

The pages use the same Bookshop system as the architecture pages. The legacy application is a Java EE / Struts monolith
on a single **Oracle** schema, `BOOKSHOP`. The new application is a **Spring Boot 4.1** application, `bookshop`, on
**PostgreSQL 18**, with a different model. The local examples run Oracle AI Database 26ai Free (container image
`gvenzl/oracle-free:23.26.3`).

[cols="1,2,2",options="header"]
|===
| Concept | Legacy Oracle (`BOOKSHOP` schema) | New PostgreSQL (`bookshop` database)

| Books
| `BOOK` with `NUMBER(10)` key, a single `AUTHOR_ID`, `ACTIVE_FLG CHAR(1)` (`'Y'`/`'N'`), `PUBLISHED DATE`, `LAST_UPD DATE`
| `book` with `bigint` key, `active boolean`, `published_on date`, `updated_at timestamptz`, plus `book_author` for
  several authors per book

| Authors
| `AUTHOR` (`AUTHOR_ID`, `FULL_NAME`)
| `author` (`id`, `full_name`)

| Customers
| `CUSTOMER` with `STATUS_CD CHAR(1)` (`'A'`/`'I'`) and `CREATED_DT DATE`
| `customer` with a `uuid` key, `legacy_id`, `status` (`ACTIVE`/`INACTIVE`) and `created_at timestamptz`

| Orders
| `ORDERS` (`STATUS_CD` `'NW'`, `'PD'`, `'SH'`, `'CN'`) and `ORDER_LINE` (`ORDER_ID`, `LINE_NO`)
| `purchase_order` (`NEW`, `PAID`, `SHIPPED`, `CANCELLED`, `uuid` key, `legacy_id`) and `order_line`

| Supplier feed
| `SUPPLIER_CATALOGUE` (`SUPPLIER_ID`, `ISBN`, `SUPPLIER_PRICE`, `FEED_TS`)
| `legacy_supplier_catalogue`, a 1:1 mirror
|===

The pipeline built across the section is as follows:

* The `bookshop-oracle-source` connector (topic prefix `legacy`) streams the changes of the legacy schema to
  topics such as `legacy.BOOKSHOP.BOOK`.
* The `bookshop-pg-mirror-sink` JDBC sink connector copies the tables that keep their shape into `+legacy_*+` mirror
  tables.
* Consumers in the new application (`LegacyBookTranslator`, `LegacyCustomerTranslator` and `LegacyOrderProjector`) act
  as the anti-corruption layer that translates the legacy rows into the new model.
* After the cut-over, the `bookshop-pg-source` connector (topic prefix `modern`) and the `bookshop-oracle-reverse-sink`
  connector replicate changes back to Oracle, so that a rollback stays possible.

A smaller MongoDB example (`bookshop.reviews` to a PostgreSQL `book_review` table) covers the cases where one side is
a document database and the other is relational.
