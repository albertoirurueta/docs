Debezium Server is a ready-made application that runs **one** Debezium source connector and delivers its change events
directly to a **sink**: a messaging system, a cloud streaming service, a cache, a vector database or another relational
database. Kafka is one of the sinks, not a requirement. For a migration, it fills the gap between Kafka Connect (a
cluster, a broker, many moving parts) and the xref:database/migration/debezium-engine.adoc[Debezium Engine] (your own
code in your own process): you configure a properties file, start a container, and the legacy changes flow to the
messaging system your organisation already runs.

This page explains how the server is configured, lists every sink of the 3.7 documentation with its configuration keys,
and helps you choose one for a migration that runs on cloud messaging instead of Kafka. It then builds two Bookshop
labs: the legacy Oracle `CUSTOMER` table streamed through RabbitMQ to the new Spring Boot application, and a Kafka-less
copy of legacy tables into PostgreSQL mirror tables with the JDBC sink.

Checked on 2026-11-09 against Debezium 3.7.1.Final (Debezium Server needs Java 21; the container image ships a Java 21
runtime), RabbitMQ 4.2, PostgreSQL 18, Spring Boot 4.1.2 and Spring AMQP 4.1.2. The sink list and configuration keys
are taken from the official Debezium Server page. The `quay.io/debezium/server:3.7.1.Final` image was run in Docker on
2026-11-09 with the RabbitMQ sink and with the JDBC sink, using the PostgreSQL example database
(`quay.io/debezium/example-postgres:3.7.1.Final`) as the source instead of Oracle; the Spring AMQP consumer on this page
was compiled and run against that RabbitMQ with Oracle-shaped events. The Oracle source properties were not run with
Debezium Server; they follow the official connector documentation.

== What Debezium Server is

Debezium Server is a Quarkus application built around the asynchronous Debezium Engine. Each instance runs exactly one
source connector with one configuration. The engine hands batches of change events to a sink adapter, which publishes
them to the target system and then marks them as processed, so the server can store the offsets.

[mermaid]
....
flowchart LR
    ORA[(Legacy Oracle)] -- redo log --> SRC
    subgraph DS[Debezium Server container]
        SRC[Source connector] --> TR[Transforms and predicates]
        TR --> FMT[Format: json, avro, protobuf, cloudevents]
        FMT --> SINK[Sink adapter]
        SRC -.-> OFF[(Offsets and schema history)]
    end
    SINK --> T1[RabbitMQ]
    SINK --> T2[Kinesis, Pub/Sub, Event Hubs]
    SINK --> T3[(JDBC: PostgreSQL)]
....

Compared with the other ways of running a connector:

* **Against Kafka Connect**, it needs no Kafka and no Connect cluster, and supports many targets. It has no REST API to
  add connectors at runtime (one instance, one connector, configured at start), no distributed task rebalancing, and it
  writes its offsets to a store you configure.
* **Against the Debezium Engine**, it needs no code for the sinks it ships, and it is operated like any container (a
  health endpoint, metrics, logs). Custom processing is limited to transformations, unless you write a custom sink.
* On Kubernetes, the xref:database/migration/running-on-kubernetes.adoc[Debezium Operator] deploys Debezium Server
  from a `DebeziumServer` custom resource, and the Debezium Management Platform builds pipelines on top of the operator.

The choice between the three is discussed in
xref:database/migration/choosing-a-deployment-for-your-migration.adoc[Choosing a Deployment].

== Installation

=== The distribution archive

The distribution is an archive that unpacks into a `debezium-server` directory:

.Contents of the Debezium Server distribution
[source,text]
----
debezium-server/
    |-- config
    |-- connectors
    |-- debezium-server-dist-3.7.1.Final-runner.jar
    |-- jmx
    |-- lib
    |-- lib_metrics
    |-- lib_opt
    |-- run.bat
    |-- run.sh
----
Reference: https://debezium.io/documentation/reference/stable/operations/debezium-server.html#installing-debezium-server[Debezium -- Debezium Server, Installation]

`config/application.properties` holds the configuration, `lib` the dependencies, and `run.sh` (Linux) or `run.bat`
(Windows) starts the server. The documentation says to copy the Oracle JDBC driver into `lib` before using the Oracle
connector, and the Oracle JDBC driver and the XStream API files when using the XStream adapter. The JDBC sink also
needs the driver of the target database in `lib`. For offsets in a file, the directory (for example `data`) must exist
before the server starts.

=== The container image

The `quay.io/debezium/server:3.7.1.Final` image contains the same layout under `/debezium` and runs as a non-root user.
Mount the configuration at `/debezium/config/application.properties` and a volume at `/debezium/data` for the offsets
and the schema history. Inspecting the 3.7.1.Final image on 2026-11-09 showed:

* all the relational source connectors (Oracle, PostgreSQL, MySQL, MariaDB, SQL Server, Db2, Informix, MongoDB, Vitess,
  Spanner, CockroachDB and Db2 for IBM i) in `lib`, and the Cassandra connectors in `connectors`;
* the Oracle JDBC drivers `ojdbc11` and `ojdbc17` (23.26.0.0.0), and the PostgreSQL, MySQL, SQL Server and SingleStore
  drivers, already in `lib`, so the image works with an Oracle source and a PostgreSQL JDBC sink without adding jars.
  Add the XStream API files for the XStream adapter, and newer drivers if you need them;
* the sink modules for Kinesis, Pub/Sub (including Pub/Sub Lite), HTTP, Pulsar, Event Hubs, Redis, NATS Streaming, NATS
  JetStream, Fluss, Kafka, Pravega, Infinispan, RocketMQ, RabbitMQ, Milvus, Qdrant, InstructLab, JDBC and Databricks
  Zerobus. The Apache Iceberg sink is not in the image, so it needs a custom image. The image also contains `sns` and
  `sqs` sink modules that the 3.7 documentation does not describe; do not plan a migration on undocumented sinks.

.Running the container
[source,shell]
----
docker run -d --name bookshop-debezium-server \
  -v "$PWD/application.properties:/debezium/config/application.properties:ro" \
  -v bookshop-server-data:/debezium/data \
  -p 8080:8080 \
  quay.io/debezium/server:3.7.1.Final
----
Reference: https://github.com/debezium/debezium-examples/tree/main/data-replication[debezium-examples -- Kafka-less data replication]

The health endpoint is `http://localhost:8080/q/health`. In the 2026-11-09 run it reported a `debezium` check together with
the other Quarkus health checks of the image, all `UP`.

== Configuration

Debezium Server reads MicroProfile Config: `config/application.properties`, environment variables and system
properties. Five prefixes structure the file:

[cols="1,3",options="header"]
|===
| Prefix | Configures

| `+debezium.source.*+`
| The source connector: every connector property with the prefix added, plus the offset and schema history stores

| `+debezium.sink.*+`
| The sink: `debezium.sink.type` selects it, `+debezium.sink.<type>.*+` configures it

| `+debezium.format.*+`
| The serialization of keys, values and headers

| `+debezium.transforms.*+`
| Single message transformations applied before the sink

| `+debezium.predicates.*+`
| Predicates that decide when a transformation applies
|===

Reference: https://debezium.io/documentation/reference/stable/operations/debezium-server.html#debezium-server-configuration[Debezium -- Debezium Server configuration]

Two consequences of MicroProfile Config matter in practice:

* **Escape `$` in values.** A value such as `+${source.table}+` is a property expression for MicroProfile Config, which
  tries to expand it. Write `+$${source.table}+` to pass the literal `+${source.table}+` to Debezium. The JDBC sink lab
  below depends on it.
* **Environment variables override the file.** MicroProfile maps `DEBEZIUM_SOURCE_DATABASE_PASSWORD` to
  `debezium.source.database.password` (upper case, non-alphanumeric characters replaced by `_`). Keep secrets out of
  the file and pass them as environment variables or Kubernetes secrets.

Reference: https://quarkus.io/guides/config-reference#environment-variables[Quarkus -- Configuration reference, environment variables]

=== Source configuration

Source properties are the connector properties of the xref:database/migration/oracle-connector.adoc[Oracle
Connector] (or any other connector page) with `debezium.source.` in front. Because there is no Kafka Connect, the
server also needs:

[cols="2,2,3",options="header"]
|===
| Property | Default | Values

| `debezium.source.connector.class`
| (required)
| For example `io.debezium.connector.oracle.OracleConnector`

| `debezium.source.offset.storage`
| `org.apache.kafka.connect.storage.FileOffsetBackingStore`
| `FileOffsetBackingStore`, `MemoryOffsetBackingStore` (tests), `io.debezium.storage.jdbc.offset.JdbcOffsetBackingStore`,
  `io.debezium.storage.redis.offset.RedisOffsetBackingStore`

| `debezium.source.offset.storage.file.filename`
|
| The offsets file of the file store

| `debezium.source.offset.flush.interval.ms`
|
| How often offsets are flushed

| `+debezium.source.offset.storage.redis.*+`
|
| Address, user, password, TLS, key (`metadata:debezium:offsets`), wait for replicas, cluster mode

| `debezium.source.schema.history.internal`
| `io.debezium.storage.kafka.history.KafkaSchemaHistory`
| `io.debezium.storage.file.history.FileSchemaHistory`, `io.debezium.relational.history.MemorySchemaHistory`,
  `io.debezium.storage.redis.history.RedisSchemaHistory`, `io.debezium.storage.rocketmq.history.RocketMqSchemaHistory`,
  `io.debezium.storage.azure.blob.history.AzureBlobSchemaHistory`

| `debezium.source.schema.history.internal.file.filename`
|
| The file of `FileSchemaHistory`

| `+debezium.source.schema.history.internal.redis.*+`, `+.rocketmq.*+`, `+.azure.storage.*+`
|
| Settings of the other history stores
|===

Reference: https://debezium.io/documentation/reference/stable/operations/debezium-server.html#debezium-source-configuration-properties[Debezium -- Debezium Server, Source configuration]

The schema history default is the Kafka store, so a Kafka-less server with the Oracle, MySQL, SQL Server or Db2
connector **must** change it. The JDBC schema history (`io.debezium.storage.jdbc.history.JdbcSchemaHistory`, from
xref:database/migration/debezium-engine.adoc#_storing_offsets_and_schema_history[the storage documentation]) is not
listed on the server page, but its module is in the 3.7.1.Final image; the JDBC offset store was used in the JDBC sink
run on this page. Whatever you choose, the offsets and the history must be **persistent** and backed up together: a
container restart without them means a new snapshot.

=== Format configuration

[cols="2,1,3",options="header"]
|===
| Property | Default | Values

| `debezium.format.key`
| `json`
| `json`, `jsonbytearray`, `avro`, `protobuf`, `simplestring`, `binary`

| `debezium.format.value`
| `json`
| `json`, `jsonbytearray`, `avro`, `protobuf`, `cloudevents`, `simplestring`, `binary`

| `debezium.format.header`
| `json`
| `json`, `jsonbytearray`

| `+debezium.format.key.*+`, `+debezium.format.value.*+`, `+debezium.format.header.*+`
|
| Passed to the converter, for example `debezium.format.value.schemas.enable=false`
|===

Reference: https://debezium.io/documentation/reference/stable/operations/debezium-server.html#debezium-format-configuration-options[Debezium -- Debezium Server, Format configuration]

When the only reader is an application that parses JSON, you can set `debezium.format.value.schemas.enable=false`
(and the same for the key): the message then carries the bare envelope, which the reader of
xref:database/migration/consuming-change-events-in-applications.adoc[Listening to Events in Applications] accepts as
well as the schema-wrapped `payload` form. In the 2026-11-09 run, an update event of the PostgreSQL example `customers`
table was about 600 bytes without the schema. Keep schemas enabled when a JDBC sink reads the same events: it needs
them to recognise the Debezium envelope, which is why the Kafka Connect pipeline (`bookshop-oracle-source`) keeps them.

=== Transformations, predicates and message filtering

Transformations and predicates use the Kafka Connect syntax under the `debezium.` prefix:
`debezium.transforms` (a comma-separated list of names), `debezium.transforms.<name>.type`,
`+debezium.transforms.<name>.*+`, `debezium.transforms.<name>.predicate`, `debezium.transforms.<name>.negate`, and
`debezium.predicates`, `debezium.predicates.<name>.type`, `+debezium.predicates.<name>.*+`.

.Flattening events before the sink
[source,properties]
----
debezium.transforms=unwrap
debezium.transforms.unwrap.type=io.debezium.transforms.ExtractNewRecordState
debezium.transforms.unwrap.delete.tombstone.handling.mode=rewrite
debezium.transforms.unwrap.add.fields=op,source.scn
----
Reference: https://debezium.io/documentation/reference/stable/operations/debezium-server.html#debezium-transformations-configuration-options[Debezium -- Debezium Server, Transformation configuration]

The Debezium filter transformation, which evaluates Groovy or JavaScript expressions, is **disabled by default** in
the server: its scripting libraries are kept in `lib_opt` and are only added to the classpath when the environment
variable `ENABLE_DEBEZIUM_SCRIPTING=true` is set. Only enable it where access to the server configuration is restricted
to trusted operators, because a filter expression runs code in the server process.

Reference: https://debezium.io/documentation/reference/stable/operations/debezium-server.html#debezium-server-enabling-message-filtering[Debezium -- Debezium Server, Enabling message filtering]

=== Engine and Quarkus properties

The asynchronous engine properties apply as in the Debezium Engine: `record.processing.threads`,
`record.processing.shutdown.timeout.ms` (default 1000) and `task.management.timeout.ms` (default 180000). The Quarkus
properties of the server are available too; the common ones are `quarkus.http.port` (default 8080, health at
`/q/health`), `quarkus.log.level` (default `INFO`) and `quarkus.log.console.json` (default `true`; set it to `false` for
readable logs during a lab).

Reference: https://debezium.io/documentation/reference/stable/operations/debezium-server.html#debezium-additional-configuration-options[Debezium -- Debezium Server, Additional configuration]

== Choosing a sink for a migration

A sink for a migration must keep the changes of one row in order, deliver them at least once, and let the new
application consume them reliably. Ask these questions of each candidate:

* **Ordering per key.** Kinesis (partition key), Pub/Sub (ordering keys, `pubsub.ordering.enabled=true`), Event Hubs
  (partition key), Pulsar (key-based routing), Kafka and Redis Streams keep the order of a key when the consumer reads
  one partition, shard or stream sequentially. RabbitMQ keeps the order of one queue with one active consumer. The HTTP
  sink keeps order only if the receiver processes requests one at a time.
* **Durability and replay.** Streams and logs (Kinesis, Pub/Sub with retention, Event Hubs, Pulsar, Kafka, JetStream with
  file storage, RabbitMQ streams) can replay events to a new consumer. Classic queues delete a message once it is
  acknowledged, so a second consumer added later needs its own queue from the start.
* **Tombstones.** Several sinks cannot carry a null value: RabbitMQ and Redis replace it with the `null.value` text
  (`default`), and Kinesis and Pub/Sub need a key. Disable tombstones at the source
  (`debezium.source.tombstones.on.delete=false`) when the target has no log compaction that needs them; consumers rely
  on the delete event anyway.
* **What the organisation already runs.** A migration is the wrong time to introduce a new broker. If the new platform
  is on AWS, Kinesis or the Kafka sink against Amazon MSK; on Google Cloud, Pub/Sub; on Azure, Event Hubs; on premises,
  RabbitMQ or Kafka.
* **Replication without a broker.** When the only goal is to copy legacy tables into the new database, the JDBC sink
  writes them directly, as in the second lab below. Remodelled data still needs an application consumer.

[cols="2,3",options="header"]
|===
| Situation | Suggested sink

| The new platform already uses Kafka (or a managed Kafka)
| Kafka Connect, or the Debezium Server `kafka` sink when Connect is not available

| Cloud-native platform on AWS / Google Cloud / Azure
| `kinesis` / `pubsub` / `eventhubs`

| On-premises Spring applications on RabbitMQ
| `rabbitmq` (to a quorum queue with a single active consumer) or `rabbitmqstream` (for replay)

| Copy tables 1:1 into the new database, no broker
| `jdbc`

| Push changes to a service that only exposes HTTP
| `http`, with batching and authentication
|===

The database password and the RabbitMQ password are passed as the environment variables

* `routingKey.source=topic` sets the routing key to the destination name of the event (`legacy.BOOKSHOP.CUSTOMER`),
  after the `StreamNameMapper`. With `exchange` set, every event goes to that one exchange, and the bindings decide
  which queue gets which table. Without `exchange`, the sink publishes to an exchange named after the destination,
  which must then exist for every table.
* `connection.username` and `connection.password` are passed to the RabbitMQ Java client's connection factory, like any
  other `+debezium.sink.rabbitmq.connection.*+` property.
* `deliveryMode=2` makes the messages persistent. The sink uses publisher confirms and waits up to `ackTimeout` for the
  broker to confirm each batch before it marks the batch as processed, so an offset is stored only for confirmed
  messages.
* `tombstones.on.delete=false`, because RabbitMQ has no null payload: a tombstone would arrive as the text `default`
  (`debezium.sink.rabbitmq.null.value`).
* The message headers carry Debezium context headers (`+__debezium.context.connectorLogicalName+`,
  `+__debezium.context.connectorName+`, `+__debezium.context.taskId+` and `+__debezium.context.runId+` in the 2026-11-09 run).
  The record key is not sent unless `routingKey.source=key` uses it as the routing key, so the consumer reads the
  primary key from the row.
* The connector user `C##DBZUSER`, the archive log mode and the supplemental logging are prepared as described in
  xref:database/migration/oracle-connector.adoc[Oracle Connector].

=== The Spring Boot consumer

The consumer applies the same translation as the Kafka-based `LegacyCustomerTranslator` and reuses its support classes
(`DebeziumEnvelope`, `LegacyValues`, `LegacyCodes`, `LegacyIds`, `SourcePosition`, `ProcessedChangeRepository` and
`LegacySyncProperties`, shown in xref:database/migration/consuming-change-events-in-applications.adoc[Listening to Events
in Applications]). Only the transport changes: `spring-boot-starter-amqp` instead of `spring-boot-starter-kafka`, and
a `@RabbitListener`.

.LegacyCustomerRabbitListener.java
[source,java]
----
package com.example.bookshop.migration;

import java.nio.charset.StandardCharsets;
import java.time.ZoneId;

import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.amqp.core.Message;
import org.springframework.amqp.rabbit.annotation.RabbitListener;
import org.springframework.jdbc.core.simple.JdbcClient;
import org.springframework.stereotype.Component;
import org.springframework.transaction.support.TransactionTemplate;
import tools.jackson.databind.JsonNode;
import tools.jackson.databind.json.JsonMapper;

/**
 * Applies the CUSTOMER change events that Debezium Server publishes to RabbitMQ. The message body is the
 * Debezium envelope (JSON without schema); the routing key is the destination name legacy.BOOKSHOP.CUSTOMER.
 */
@Component
public class LegacyCustomerRabbitListener {

    private static final Logger log = LoggerFactory.getLogger(LegacyCustomerRabbitListener.class);

    private final JsonMapper jsonMapper;
    private final ProcessedChangeRepository processed;
    private final JdbcClient jdbc;
    private final TransactionTemplate tx;
    private final ZoneId legacyZone;

    public LegacyCustomerRabbitListener(JsonMapper jsonMapper, ProcessedChangeRepository processed, JdbcClient jdbc,
            TransactionTemplate tx, LegacySyncProperties properties) {
        this.jsonMapper = jsonMapper;
        this.processed = processed;
        this.jdbc = jdbc;
        this.tx = tx;
        this.legacyZone = properties.legacyZone();
    }

    @RabbitListener(id = "legacy-customer-rabbit", queues = "bookshop.legacy.customers")
    public void onCustomer(Message message) {
        String body = new String(message.getBody(), StandardCharsets.UTF_8);
        if (body.isBlank() || !body.startsWith("{")) {
            // RabbitMQ has no null payload: a tombstone arrives as the debezium.sink.rabbitmq.null.value text
            log.debug("Ignoring non-JSON message (tombstone placeholder) with routing key {}",
                    message.getMessageProperties().getReceivedRoutingKey());
            return;
        }
        JsonNode root = jsonMapper.readTree(body);
        DebeziumEnvelope event = jsonMapper.treeToValue(root.has("payload") ? root.get("payload") : root,
                DebeziumEnvelope.class);
        JsonNode row = event.operation() == DebeziumEnvelope.Operation.DELETE ? event.before() : event.after();
        long legacyId = LegacyValues.longValue(row, "CUST_ID");
        // The sink does not send the record key, so the position uses the primary key read from the row,
        // in the same form as the Kafka key payload ({"CUST_ID":"7"})
        JsonNode key = jsonMapper.createObjectNode().put("CUST_ID", String.valueOf(legacyId));

        tx.executeWithoutResult(status -> {
            if (!processed.firstDelivery(event.source().qualifiedTable(), SourcePosition.of(event, key))) {
                return;
            }
            switch (event.operation()) {
                case CREATE, READ, UPDATE -> jdbc.sql("""
                        INSERT INTO customer (id, legacy_id, name, email, status, created_at)
                        VALUES (:id, :legacyId, :name, :email, :status, :createdAt)
                        ON CONFLICT (id) DO UPDATE SET
                            name = EXCLUDED.name,
                            email = EXCLUDED.email,
                            status = EXCLUDED.status,
                            created_at = EXCLUDED.created_at
                        """)
                        .param("id", LegacyIds.customerId(legacyId))
                        .param("legacyId", legacyId)
                        .param("name", LegacyValues.text(row, "CUST_NAME"))
                        .param("email", LegacyValues.text(row, "EMAIL"))
                        .param("status", LegacyCodes.customerStatus(LegacyValues.text(row, "STATUS_CD")))
                        .param("createdAt", LegacyValues.legacyTimestamp(row, "CREATED_DT", legacyZone))
                        .update();
                case DELETE -> jdbc.sql("DELETE FROM customer WHERE legacy_id = :legacyId")
                        .param("legacyId", legacyId)
                        .update();
                case TRUNCATE, MESSAGE -> log.warn("Ignoring {} event on CUSTOMER", event.operation());
            }
        });
    }
}
----
Reference: https://docs.spring.io/spring-amqp/reference/amqp/receiving-messages/async-annotation-driven.html[Spring AMQP -- Annotation-driven listener endpoints]

* `acknowledge-mode: auto` acknowledges the message after the listener method returns, that is after the database
  transaction has committed. A crash before the acknowledgement redelivers the message; `processed_change` turns the
  redelivery into a no-op.
* `retry` retries in the listener thread (1 s, 2 s, 4 s ... up to 30 s, five attempts), which keeps the order of the
  queue. After the last attempt the message is rejected without requeue (`default-requeue-rejected: false`) and the
  queue's dead-letter exchange moves it to `bookshop.legacy.customers.dlq`.
* Requeueing a failed message instead would put it back at the head of the queue and loop forever on a permanent error.

What the 2026-11-09 run showed (Debezium Server with the PostgreSQL example source and this consumer): a change of the
example `customers` table, routed by the binding for `legacy.inventory.customers`, failed in the consumer because it has
no `CUST_ID` column, was retried five times and ended in `bookshop.legacy.customers.dlq`; an Oracle-shaped `CUSTOMER`
event published to `bookshop.legacy` with routing key `legacy.BOOKSHOP.CUSTOMER` became customer 7 (`ACTIVE`, created
`2020-01-31 08:00:00+00` for a Madrid `09:00`), and publishing it a second time left one row in `processed_change`.

* **`+legacy_$${source.table}+`.** The doubled `$` stops MicroProfile Config from expanding the expression, so the sink
  receives `+legacy_${source.table}+`. With `quote.identifiers=false`, PostgreSQL folds `legacy_BOOK` to `legacy_book`.
  In the 2026-11-09 run with the PostgreSQL example source, `+legacy_$${source.table}+` produced the tables
  `legacy_customers` and `legacy_products`.
* **The same settings as the mirror sink.** The source uses `decimal.handling.mode=string`, like
  `bookshop-oracle-source`, so every `NUMBER` value arrives as a string, and the sink URL ends in
  `?stringtype=unspecified` so that PostgreSQL casts them to `bigint` and `numeric` (see
  xref:database/migration/jdbc-sink-connector.adoc#_numbers_as_strings_and_stringtypeunspecified[JDBC Sink Connector]).

  `bookshop_mirror`. The 2026-11-09 run with the PostgreSQL example source used `schema.evolution=basic` instead, to let
  the sink create its tables.

  the PostgreSQL database. In the run, the table held the PostgreSQL LSN, the transaction id and the last operation, and
  an update and a delete in the source reached the target within seconds.
* **Delivery guarantees.** The official page warns that the JDBC sink in Debezium Server does not offer the same
  guarantees as the connector in Kafka Connect: features that depend on the runtime for offset management, exactly-once
  semantics or error handling and retries can behave differently or be missing. The upsert and delete by primary key
  make replays harmless, but plan for the server stopping on an error and needing a restart.
* **Drivers.** The 3.7.1.Final image already contains the PostgreSQL driver; for other targets add the driver to
  `/debezium/lib`.
* The JDBC sink properties themselves are explained in xref:database/migration/jdbc-sink-connector.adoc[JDBC Sink
  Connector].

== Operating Debezium Server

* **One connector per instance.** Run one server per source database (or per group of tables that must be stopped
  and started together). Two servers on the same Oracle database use separate offsets and separate LogMiner sessions.
* **Health and metrics.** `/q/health` reports `UP` or `DOWN`; the image also contains the `jmx` and `lib_metrics`
  directories for JMX and Prometheus metrics, described in xref:database/migration/monitoring-logging-and-tracing.adoc[Monitoring,
  Logging & Tracing].
* **Restarts.** The server exits when the connector or the sink fails permanently. Let the orchestrator restart it
  (`restart: unless-stopped` in Compose, a Deployment on Kubernetes) and alert on repeated restarts.
* **Persistent state.** Keep `/debezium/data` (file offsets and history) on a volume, or use the JDBC or Redis stores.
* **Upgrades.** Stop the server cleanly (it flushes offsets on shutdown), replace the image, and start it with the same
  state.
* **Kubernetes.** The Debezium Operator runs Debezium Server from a `DebeziumServer` resource; see
  xref:database/migration/running-on-kubernetes.adoc[Running on Kubernetes].

== Extending the server

Debezium Server uses Quarkus dependency injection (JVM mode only, not native) for two kinds of extensions:

* **A new sink**: a CDI bean that implements `DebeziumEngine.ChangeConsumer`, annotated `@Named("<name>")` and
  `@Dependent`. The bean name becomes the value of `debezium.sink.type`. It reads its configuration with the MicroProfile
  Config API, publishes the records and marks them as processed.
* **A customised existing sink**: a bean for one of the sink's injection points, typically a `StreamNameMapper` that
  renames destinations (for example, `legacy.BOOKSHOP.CUSTOMER` to `bookshop-customers`). The
  `debezium-server-name-mapper` directory of the Debezium examples repository contains one.

Reference: https://debezium.io/documentation/reference/stable/operations/debezium-server.html#debezium-server-extensions[Debezium -- Debezium Server, Extensions]

The page also has notes for running the Cassandra connector in Debezium Server (with an example using the Redis sink),
which matter only for Cassandra sources: see
https://debezium.io/documentation/reference/stable/operations/debezium-server.html#debezium-server-cassandra-connector[Cassandra
connector configuration notes].

== What goes wrong

[cols="2,2,3",options="header"]
|===
| Symptom | Cause | Fix

| The Oracle connector fails at start with a Kafka error
| `schema.history.internal` left at `KafkaSchemaHistory`
| Configure `FileSchemaHistory` (or another store) under `debezium.source.`

| Tables named `legacy_` or a startup error about an unknown property expression
| `+${source.table}+` expanded by MicroProfile Config
| Write `+$${source.table}+`

| A new snapshot after every container restart
| Offsets in the container file system
| A volume on `/debezium/data`, or the JDBC or Redis offset store

| RabbitMQ messages disappear
| No binding for the routing key, or the exchange does not exist
| Create exchange, queue and bindings before the server starts; check the routing key (`legacy.BOOKSHOP.CUSTOMER`)

| Messages with the body `default`
| Tombstones on a sink without null payloads
| `debezium.source.tombstones.on.delete=false`, and ignore non-JSON bodies

| Changes of one row applied out of order with RabbitMQ
| Several consumers on one classic queue
| Quorum queue with single active consumer, or one consumer

| The server stops with `ackTimeout` errors
| The broker does not confirm in time (overloaded, disk alarm)
| Fix the broker; raise `debezium.sink.rabbitmq.ackTimeout` only after that

| A filter transformation fails to load
| Scripting disabled by default
| `ENABLE_DEBEZIUM_SCRIPTING=true`, only where the configuration is trusted
|===
