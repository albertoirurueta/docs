Every Debezium pipeline in this section, from the first tutorial to the Bookshop Oracle to PostgreSQL migration, starts
with the same step: getting the right connector plug-ins, at the right version, into a runtime that can run them. This
page covers the ways to install Debezium and how to configure the Kafka Connect workers that host it. It shows which
choice suits a quick experiment and which suits a migration that has to run for months. It also clears up a common
source of confusion for Oracle sources: the Oracle JDBC driver.

The page covers the official container images, plug-in archives installed into a Kafka Connect `plugin.path`, Maven
artifacts, a custom Kafka Connect image built with a Dockerfile, the Strimzi `build` section (summarised here, with
details in xref:database/migration/running-on-kubernetes.adoc[Running on Kubernetes]), the Debezium Server
distribution and the Debezium CLI. It then covers the worker configuration, secrets and verification.

Checked on 2026-11-09 against Debezium 3.7.1.Final. The Debezium 3.7.1.Final images ship Apache Kafka 4.3.1 in KRaft
mode, and the Connect image runs on OpenJDK 25. The two Dockerfiles and the Docker Compose file on this page were built
and run with Docker on 2026-11-09. The custom Connect worker started against `quay.io/debezium/kafka:3.7.1.Final`,
`GET /connector-plugins` listed the Oracle, PostgreSQL and JDBC sink plug-ins at `3.7.1.Final`, and an Oracle connector
configuration that reads its credentials through configuration providers passed the Connect validation endpoint.
After the check the containers and images were removed. No Oracle database was connected in that run.

== Choosing an installation method

[cols="1,2,2",options="header"]
|===
| Method | What you get | Use it for

| Container images (`+quay.io/debezium/*+`)
| Kafka, Kafka Connect with all Debezium connectors pre-installed, Debezium Server, example databases
| Tutorials, local labs, integration tests, and as the base of your own image

| Plug-in archives in `plugin.path`
| One `.tar.gz` per connector from Maven Central, extracted into an existing Kafka Connect installation
| Kafka Connect clusters that you already run on virtual machines or bare metal

| Custom Connect image (Dockerfile)
| An image with exactly the plug-ins and drivers the migration needs, at pinned versions and checksums
| Production-like container deployments of a migration

| Strimzi `KafkaConnect` with `build`
| The Strimzi operator builds and pushes the Connect image from a list of plug-in artifacts
| Kafka Connect on Kubernetes

| Maven artifacts (`+io.debezium:*+`)
| JARs for the Debezium Engine, the Quarkus extensions and tests
| Embedding Debezium in a Java application

| Debezium Server distribution or image
| A standalone application that runs one connector and sends events to a sink
| Kafka-less pipelines (see xref:database/migration/debezium-server.adoc[Debezium Server])

| Debezium Operator and Management Platform
| Debezium Server managed on Kubernetes, with a console and an API for pipelines
| Teams that standardise on Debezium Server on Kubernetes
|===

The official install page lists Kafka Connect connectors as the main installation method and says that the operator,
Debezium Server and Debezium CLI install guides are still to come there. Their instructions are on their own pages,
linked from the sections below.

== Baselines

[cols="1,2",options="header"]
|===
| Component | Requirement for Debezium 3.7

| Debezium connectors on Kafka Connect
| Java 17 or later; Apache Kafka 3.1 or later with a Kafka Connect cluster

| Debezium Server, Debezium Operator, Outbox Quarkus extension, Quarkus Debezium engine extension
| Java 21 or later

| Container images `+quay.io/debezium/{kafka,connect,server}:3.7.1.Final+`
| Kafka 4.3.1 in KRaft mode (no ZooKeeper); the Connect image runs OpenJDK 25

| Source and sink databases
| The tested versions per database are on the https://debezium.io/releases/3.7/[Debezium 3.7 release page]
  (for example Oracle 19c, 21c, 23ai and 26ai; PostgreSQL 14 to 18)
|===

Do not mix Debezium versions in one Connect worker. All Debezium plug-ins on a worker should share the same version,
because they rely on shared Debezium libraries. The same applies to the Engine: `debezium-api`, `debezium-embedded` and
the connector artifacts must have the same version.

== Container images

Debezium publishes these images on `quay.io/debezium`, tagged with the full release version:

* `quay.io/debezium/kafka:3.7.1.Final` -- an Apache Kafka broker and controller in KRaft mode.
* `quay.io/debezium/connect:3.7.1.Final` -- Kafka Connect with the Debezium connectors already in `/kafka/connect`
  (MySQL, MariaDB, PostgreSQL, SQL Server, Oracle, MongoDB, Db2, Db2 for IBM i, Informix, Spanner, Vitess, CockroachDB
  and the JDBC sink), plus the scripting module, the Apicurio converters, Jolokia and OpenTelemetry libraries that can be
  enabled with environment variables.
* `quay.io/debezium/connect-base:3.7.1.Final` -- the same Kafka Connect image without the connectors, intended as a base
  for your own image.
* `quay.io/debezium/server:3.7.1.Final` -- Debezium Server.
* `quay.io/debezium/example-mysql:3.7.1.Final` and `quay.io/debezium/example-postgres:3.7.1.Final` -- databases
  prepared for CDC with the tutorial's `inventory` schema.

The official installation page is explicit that the images on quay.io do not undergo rigorous testing or security
analysis and are provided for testing and evaluation. They are not intended for production. For production, deploy
images from a trusted vendor that maintains and scans them, or build your own image from a base you maintain, and scan
it like any other image you ship. The tags used here are exact release tags. A floating tag such as `3.7` moves to the
next patch release without warning, which is not what a migration pipeline should do.

The Connect image is configured with environment variables:

[cols="1,2",options="header"]
|===
| Variable | Meaning

| `BOOTSTRAP_SERVERS` | Kafka brokers to connect to
| `GROUP_ID` | The Connect cluster id (`group.id`); required
| `CONFIG_STORAGE_TOPIC`, `OFFSET_STORAGE_TOPIC` | Topics for connector configurations and offsets; required
| `STATUS_STORAGE_TOPIC` | Topic for connector and task status; recommended
| `KEY_CONVERTER`, `VALUE_CONVERTER` | Converter classes; JSON by default
| `HEAP_OPTS` | JVM heap; `-Xms256M -Xmx2G` by default
| `KAFKA_CONNECT_PLUGINS_DIR` | Comma-separated plug-in directories; `/kafka/connect` by default
| `ENABLE_APICURIO_CONVERTERS`, `ENABLE_DEBEZIUM_SCRIPTING`, `ENABLE_OTEL` | Optional features shipped in the image
| `+CONNECT_*+` | Any other worker property: the prefix is removed, the name lower-cased and `_` replaced with `.`
  (`CONNECT_EXACTLY_ONCE_SOURCE_SUPPORT` becomes `exactly.once.source.support`). Values must not contain `@`.
|===

== The Oracle JDBC driver

Older guides, including the README of the Debezium container images and the `debezium-with-oracle-jdbc` example, say
that the Oracle connector needs the Oracle JDBC driver to be added to the image, because of licensing. That is no longer
true for the LogMiner adapter. The Oracle JDBC driver has been published on Maven Central under the Oracle Free Use
Terms and Conditions for years, and the Debezium 3.7.1.Final plug-in archives bundle it:

* `debezium-connector-oracle-3.7.1.Final-plugin.tar.gz` contains `ojdbc11-23.26.1.0.0.jar` (plus `orai18n` and `xdb`).
* `debezium-connector-jdbc-3.7.1.Final-plugin.tar.gz` contains the same `ojdbc11` driver, together with the PostgreSQL,
  MySQL, MariaDB and SQL Server drivers.
* `quay.io/debezium/connect:3.7.1.Final` therefore already has a driver in `/kafka/connect/debezium-connector-oracle` and
  in `/kafka/connect/debezium-connector-jdbc`, and none in `/kafka/libs`.

The consequences for the Bookshop pipeline are:

* The `bookshop-oracle-source` connector (LogMiner) and the `bookshop-oracle-reverse-sink` JDBC sink that writes back to
  Oracle work with the stock image. You do not need to add a driver.
* Do not copy a second `ojdbc` JAR into `/kafka/libs` as the older example did. Kafka Connect loads each plug-in with its
  own class loader, and JARs on the worker classpath can shadow or conflict with the ones inside the plug-in directory.
  If you need a different driver version, replace the JAR inside the plug-in directories (the second Dockerfile below
  shows how).
* The *XStream* adapter is different. It needs `xstreams.jar` and the native Oracle Instant Client libraries (OCI), which
  are not on Maven Central. The official Oracle connector page describes downloading the Instant Client, copying
  `ojdbc11.jar` and `xstreams.jar` to `<kafka_home>/libs`, and setting `LD_LIBRARY_PATH` to the Instant Client directory.
  The Connect base image already installs `libaio`, which the Instant Client needs. XStream also requires an Oracle
  GoldenGate licence.
* *Debezium Server* is packaged differently. Its documentation states that the Oracle JDBC driver must be copied to the
  server's `lib` directory before the Oracle connector is used, and that the distribution includes no JDBC drivers for
  sink databases.

== Installing plug-in archives into an existing Kafka Connect

When Kafka Connect is already installed (for example on virtual machines run by a platform team), installing a
Debezium connector means placing its plug-in directory on the worker's `plugin.path` and restarting the worker:

. Download the connector plug-in archive from Maven Central.
. Extract it into a directory on the plug-in path, so that the result is one sub-directory per connector, for example
  `/opt/kafka/plugins/debezium-connector-oracle/`.
. Add the *parent* directory (`/opt/kafka/plugins`), not the connector directory, to `plugin.path` in the worker
  configuration.
. Restart every worker in the Connect cluster. Plug-ins are discovered at start-up only, and all workers must have the
  same plug-ins, because a task can be scheduled on any of them.

.Downloading, verifying and installing the Oracle, PostgreSQL and JDBC sink plug-ins on a Connect worker
[source,shell]
----
DEBEZIUM_VERSION=3.7.1.Final
PLUGIN_DIR=/opt/kafka/plugins
REPO=https://repo1.maven.org/maven2/io/debezium

mkdir -p "$PLUGIN_DIR"
for connector in oracle postgres jdbc; do
  archive="debezium-connector-${connector}-${DEBEZIUM_VERSION}-plugin.tar.gz"
  url="${REPO}/debezium-connector-${connector}/${DEBEZIUM_VERSION}/${archive}"
  curl -fsSL -o "/tmp/${archive}" "${url}"
  # Maven Central publishes a SHA-512 checksum next to every artifact
  echo "$(curl -fsSL "${url}.sha512")  /tmp/${archive}" | sha512sum -c -
  tar -xzf "/tmp/${archive}" -C "$PLUGIN_DIR"
done

ls "$PLUGIN_DIR"
# debezium-connector-jdbc  debezium-connector-oracle  debezium-connector-postgres
----
Reference: https://debezium.io/documentation/reference/stable/install-kafka-connect.html[Debezium -- Installing Debezium Kafka Connect connectors]

.plugin.path in the worker configuration (connect-distributed.properties)
[source,properties]
----
plugin.path=/opt/kafka/plugins
----
Reference: https://debezium.io/documentation/reference/stable/install-kafka-connect.html[Debezium -- Installing Debezium Kafka Connect connectors]

The official page lists one archive per connector. Spanner, Vitess, Informix, Ingres, Milvus and YashanDB are
*incubating* connectors. Their archives are published the same way, but their behaviour and configuration can still
change between minor releases.

Since Kafka 3.6, the worker setting `plugin.discovery` controls how plug-ins are found at start-up. The default
`hybrid_warn` works with every plug-in and logs a warning for plug-ins that do not support the faster `service_load`
mode. Check the worker log for that warning before switching a production cluster to `service_load`.

== Building a custom Kafka Connect image

For a migration that runs in containers, build your own Connect image instead of running the all-in-one evaluation
image. A custom image can contain only the plug-ins that the pipeline uses, pin every version, verify every download,
and go through your registry's vulnerability scanning like any other service image.

=== A slim image with only the Bookshop plug-ins

The Bookshop pipeline needs three plug-ins: the Oracle source, the PostgreSQL source (for reverse replication) and
the JDBC sink. The Dockerfile below starts from `connect-base`, which has Kafka Connect, the plug-in directory layout
and the `docker-maven-download` helper used by the official image, and adds the three archives. The MD5 checksums are
the ones that the official `connect` image Dockerfile uses for 3.7.1.Final.

.bookshop-connect/Dockerfile -- Kafka Connect with only the plug-ins that the migration uses
[source,dockerfile]
----
# Bookshop Kafka Connect image: only the plug-ins that the migration uses
FROM quay.io/debezium/connect-base:3.7.1.Final

ENV DEBEZIUM_VERSION="3.7.1.Final" \
    ORACLE_MD5=1c25f856cf732cd73d103fa1ef3399c0 \
    POSTGRES_MD5=1ab3f57143b54413c5d353bbfc4f3c13 \
    JDBC_MD5=1f01538e6570989455d1a691424ff1c0

# Each plug-in archive is downloaded from Maven Central, checked against its MD5
# and extracted into its own directory under $KAFKA_CONNECT_PLUGINS_DIR (/kafka/connect)
RUN docker-maven-download debezium oracle   "$DEBEZIUM_VERSION" "$ORACLE_MD5" && \
    docker-maven-download debezium postgres "$DEBEZIUM_VERSION" "$POSTGRES_MD5" && \
    docker-maven-download debezium jdbc     "$DEBEZIUM_VERSION" "$JDBC_MD5"
----
Reference: https://github.com/debezium/container-images/blob/main/connect/3.7/Dockerfile[debezium/container-images -- connect 3.7 Dockerfile]

.Building the image and checking its plug-in directories
[source,shell]
----
docker build -t bookshop-connect:3.7.1.Final bookshop-connect

docker run --rm --entrypoint bash bookshop-connect:3.7.1.Final -c \
  'ls $KAFKA_CONNECT_PLUGINS_DIR; ls $KAFKA_CONNECT_PLUGINS_DIR/debezium-connector-oracle | grep ojdbc'
# debezium-connector-jdbc
# debezium-connector-oracle
# debezium-connector-postgres
# ojdbc11-23.26.1.0.0.jar
----
Reference: https://debezium.io/documentation/reference/stable/install-kafka-connect.html[Debezium -- Installing Debezium Kafka Connect connectors]

When you move to the next Debezium patch release, update `DEBEZIUM_VERSION` and the three checksums together. The
helper refuses to install an archive whose checksum does not match, so a forgotten checksum makes the build fail
instead of producing an image with an unexpected connector version.

=== Replacing the bundled Oracle JDBC driver

Sometimes a migration needs a newer Oracle driver than the one bundled with the connector, for example to pick up a
driver fix for a specific database patch level. Replace the JAR inside each plug-in that talks to Oracle, and keep
`/kafka/libs` free of drivers:

.bookshop-connect-ojdbc/Dockerfile -- the official Connect image with a newer ojdbc11 in the Oracle and JDBC plug-ins
[source,dockerfile]
----
# Debezium Connect image with a newer Oracle JDBC driver than the one bundled in the plug-ins
FROM quay.io/debezium/connect:3.7.1.Final

ENV OJDBC_VERSION="23.26.4.0.0" \
    OJDBC_MD5=485615fdff70701af864a828dcc2b703

# Replace the bundled ojdbc11 JAR in each plug-in that talks to Oracle:
# the Oracle source connector and the JDBC sink connector
RUN for plugin in debezium-connector-oracle debezium-connector-jdbc; do \
        rm -f "$KAFKA_CONNECT_PLUGINS_DIR/$plugin"/ojdbc11-*.jar && \
        curl -sfSL -o "$KAFKA_CONNECT_PLUGINS_DIR/$plugin/ojdbc11-$OJDBC_VERSION.jar" \
          "https://repo1.maven.org/maven2/com/oracle/database/jdbc/ojdbc11/$OJDBC_VERSION/ojdbc11-$OJDBC_VERSION.jar" && \
        echo "$OJDBC_MD5  $KAFKA_CONNECT_PLUGINS_DIR/$plugin/ojdbc11-$OJDBC_VERSION.jar" | md5sum -c - ; \
    done
----
Reference: https://debezium.io/documentation/reference/stable/connectors/oracle.html#obtaining-oracle-jdbc-driver-and-xstreams-api-files[Debezium -- Obtaining the Oracle JDBC driver and XStream API files]

Only do this deliberately. The bundled driver is the one Debezium tests with, so a replaced driver must go through
your own integration tests (see xref:database/migration/testing-cdc-pipelines.adoc[Testing CDC Pipelines]).

== Running Kafka and the custom Connect image with Docker Compose

The Compose file below runs a single-node Kafka in KRaft mode and one worker of the custom Connect image. It is the
minimal runtime for the Bookshop pipeline; the Oracle and PostgreSQL databases are added in
xref:database/migration/worked-example-oracle-to-postgresql.adoc[Worked Example: Oracle to PostgreSQL]. The Kafka
listener is only reachable inside the Compose network, and the Connect REST API is published on
`http://localhost:8083`.

.compose.yaml -- Kafka 4.3.1 in KRaft mode and the bookshop-connect worker
[source,yaml]
----
name: bookshop-cdc
services:
  kafka:
    image: quay.io/debezium/kafka:3.7.1.Final
    hostname: kafka
    environment:
      CLUSTER_ID: 5Yr1SIgYQz-b-dgRabWx4g
      NODE_ID: "1"
      NODE_ROLE: combined
      KAFKA_CONTROLLER_QUORUM_VOTERS: 1@kafka:9093
      KAFKA_LISTENERS: PLAINTEXT://kafka:9092,CONTROLLER://kafka:9093
      KAFKA_ADVERTISED_LISTENERS: PLAINTEXT://kafka:9092

  connect:
    build: ./bookshop-connect
    image: bookshop-connect:3.7.1.Final
    depends_on: [kafka]
    ports:
      - "8083:8083"
    volumes:
      - ./secrets:/opt/secrets:ro
    environment:
      BOOTSTRAP_SERVERS: kafka:9092
      GROUP_ID: bookshop-connect
      CONFIG_STORAGE_TOPIC: bookshop_connect_configs
      OFFSET_STORAGE_TOPIC: bookshop_connect_offsets
      STATUS_STORAGE_TOPIC: bookshop_connect_statuses
      KEY_CONVERTER: org.apache.kafka.connect.json.JsonConverter
      VALUE_CONVERTER: org.apache.kafka.connect.json.JsonConverter
      HEAP_OPTS: -Xms256M -Xmx1G
      # Configuration providers that keep secrets out of connector configurations
      CONNECT_CONFIG_PROVIDERS: env,file
      CONNECT_CONFIG_PROVIDERS_ENV_CLASS: org.apache.kafka.common.config.provider.EnvVarConfigProvider
      CONNECT_CONFIG_PROVIDERS_ENV_PARAM_ALLOWLIST_PATTERN: ^BOOKSHOP_.*
      CONNECT_CONFIG_PROVIDERS_FILE_CLASS: org.apache.kafka.common.config.provider.FileConfigProvider
      CONNECT_CONFIG_PROVIDERS_FILE_PARAM_ALLOWED_PATHS: /opt/secrets
      # Exactly-once support for source connectors (see Features & Delivery Guarantees)
      CONNECT_EXACTLY_ONCE_SOURCE_SUPPORT: enabled
      # Read by the env configuration provider
      BOOKSHOP_ORACLE_PASSWORD: dbz
----
Reference: https://debezium.io/documentation/reference/stable/kc-tutorial.html#starting-kafka-connect[Debezium tutorial -- Starting Kafka Connect]

[source,properties]
----

password=dbz
----
Reference: https://kafka.apache.org/43/configuration/configuration-providers/#fileconfigprovider[Apache Kafka -- FileConfigProvider]

[source,shell]

until curl -sf http://localhost:8083/ > /dev/null; do sleep 2; done
curl -s http://localhost:8083/

A single broker is enough for a laptop. In the verification run, the worker created its internal topics on the single
broker without extra settings. In any shared environment, run at least three brokers and give the internal topics
a replication factor of 3 (see the worker configuration below).

== Kafka Connect worker configuration

Whether the worker is configured with a `connect-distributed.properties` file, with environment variables of the
Debezium image, or with the `config` section of a Strimzi `KafkaConnect` resource, the same properties matter:

.connect-distributed.properties for the Bookshop Connect cluster
[source,properties]
----
bootstrap.servers=kafka-1:9092,kafka-2:9092,kafka-3:9092

# All workers with the same group.id form one Connect cluster
group.id=bookshop-connect

# Internal topics: configurations (1 partition), offsets and statuses (compacted)
config.storage.topic=bookshop_connect_configs
config.storage.replication.factor=3
offset.storage.topic=bookshop_connect_offsets
offset.storage.replication.factor=3
offset.storage.partitions=25
status.storage.topic=bookshop_connect_statuses
status.storage.replication.factor=3

# Default converters; a connector can override them
key.converter=org.apache.kafka.connect.json.JsonConverter
value.converter=org.apache.kafka.connect.json.JsonConverter
key.converter.schemas.enable=true
value.converter.schemas.enable=true

# How often source offsets are committed (bounds the duplicate window after a crash)
offset.flush.interval.ms=60000

# Plug-ins and topic creation
plugin.path=/opt/kafka/plugins
topic.creation.enable=true

# Secrets
config.providers=env,file
config.providers.env.class=org.apache.kafka.common.config.provider.EnvVarConfigProvider
config.providers.env.param.allowlist.pattern=^BOOKSHOP_.*
config.providers.file.class=org.apache.kafka.common.config.provider.FileConfigProvider
config.providers.file.param.allowed.paths=/opt/secrets

# Exactly-once for source connectors (all workers; use "preparing" first on an existing cluster)
exactly.once.source.support=enabled

# REST API
listeners=http://0.0.0.0:8083
----
Reference: https://kafka.apache.org/43/configuration/kafka-connect-configs/[Apache Kafka -- Kafka Connect configs]

The properties that deserve attention in a migration:

`group.id`:: Identifies the Connect cluster. Two clusters must never share it, or they will fight over the same
internal topics. Use one Connect cluster per environment (and possibly one per migration, so that a busy migration
cannot starve other connectors).
`config.storage.topic`:: Holds connector configurations. It must have a single partition and be compacted and highly
replicated. Kafka Connect creates it that way when it creates the topic itself.
`offset.storage.topic`:: Holds the source offsets of every connector in the cluster: for Bookshop, the Oracle SCN
position. It must be compacted and replicated; losing it means re-snapshotting the legacy database. The Debezium image
documentation recommends many partitions (25 or 50) for it.
`status.storage.topic`:: Holds connector and task states, used by the REST API.
Converters:: Define the bytes on the topics. JSON with schemas is verbose but self-describing; Avro or Protobuf with
a schema registry is smaller and enforces compatibility. The Bookshop pipeline uses JSON with schemas enabled for keys
and values, which the JDBC sink needs. This choice is hard to change mid-migration, so make it before the first
snapshot; see xref:database/migration/serialization-avro-and-schema-registries.adoc[Serialization & Schema Registries].
`offset.flush.interval.ms`:: The interval between offset commits. It bounds how many events can be delivered again
after a crash, as explained in xref:database/migration/debezium-features-and-guarantees.adoc[Features & Delivery Guarantees].
`exactly.once.source.support`:: Enables Kafka Connect exactly-once delivery for source connectors. It must be set on
every worker, and needs Kafka Connect in distributed mode.

=== Topic creation for Debezium topics

By default Kafka Connect creates the topics that a source connector writes to (`topic.creation.enable=true`), but only
when the connector configuration defines at least a *default topic creation group* with a replication factor and a
partition count. The groups are set per connector, so the Oracle source can create its per-table topics with the
settings it needs:

.Topic creation groups in the bookshop-oracle-source configuration
[source,json]
----
{
  "topic.creation.default.replication.factor": 3,
  "topic.creation.default.partitions": 1,
  "topic.creation.default.cleanup.policy": "delete",
  "topic.creation.default.retention.ms": 1209600000,
  "topic.creation.groups": "catalogue",
  "topic.creation.catalogue.include": "legacy\\.BOOKSHOP\\.(BOOK|AUTHOR|SUPPLIER_CATALOGUE)",
  "topic.creation.catalogue.cleanup.policy": "compact",
  "topic.creation.catalogue.min.compaction.lag.ms": 604800000,
  "topic.creation.catalogue.delete.retention.ms": 604800000
}
----
Reference: https://debezium.io/documentation/reference/stable/configuration/topic-auto-create-config.html#default-topic-creation-group-configuration[Debezium -- Default topic creation group configuration]

In this example the order topics keep two weeks of history, while the catalogue topics are compacted so they always
hold the latest state of every book, author and supplier price, which lets a new consumer rebuild the catalogue without
a new snapshot. The official topic recommendations apply: a single partition per table topic unless consumers can
handle out-of-order events for different rows, and, for compacted topics, `min.compaction.lag.ms` and
`delete.retention.ms` longer than the longest expected downtime of any consumer, so that no consumer misses a delete.
The schema history topic is created by the connector itself, not through these groups. Its requirements are in
xref:database/migration/debezium-architecture.adoc#_the_schema_history_topic[Debezium Architecture].

== Keeping secrets out of connector configurations

Connector configurations are stored in plain text in the config topic and are returned by the REST API. A
`database.password` written directly into the JSON is visible to anyone who can read that topic or call
`GET /connectors/bookshop-oracle-source`. Kafka's *configuration providers* solve this: the worker resolves placeholders
when it starts the connector, and only the placeholder is stored.

Kafka ships three providers:

* `FileConfigProvider` reads a key from a properties file: `+${file:/opt/secrets/oracle.properties:password}+`.
* `DirectoryConfigProvider` reads a whole file as a value, one file per key, which suits Kubernetes secrets mounted as
  volumes: `+${dir:/opt/secrets:password}+`.
* `EnvVarConfigProvider` reads an environment variable: `+${env:BOOKSHOP_ORACLE_PASSWORD}+`.

Restrict each provider to what it needs. Use `allowed.paths` for the file and directory providers, and
`allowlist.pattern` for the environment provider. Without these, any connector configuration submitted through the
REST API can read any file or environment variable that the worker can see. In the verification run, the worker refused
to start while `allowed.paths` pointed to a directory that did not exist, so mount the secrets before starting the
worker.

Three REST calls confirm that a worker is ready for the Bookshop connectors.

curl -s http://localhost:8083/

With the custom image, the plug-in list contains the three Debezium plug-ins at the expected version, plus the
MirrorMaker connectors that every Kafka Connect distribution includes:

[

  {"class": "io.debezium.connector.oracle.OracleConnector", "type": "source", "version": "3.7.1.Final"},

----
Reference: https://kafka.apache.org/43/kafka-connect/user-guide/#rest-api[Apache Kafka -- Kafka Connect REST API]

Before creating a connector, validate its configuration. The response lists every property with its errors, so it
catches misspelled values and unreachable databases without creating anything. The validation body is the content of
the `config` object, with `name` added.

.Validating the Oracle source configuration without creating the connector
[source,shell]
----
jq '.config + {name: .name}' bookshop-oracle-source.json > validate.json
curl -s -X PUT -H "Content-Type: application/json" --data @validate.json \
  http://localhost:8083/connector-plugins/OracleConnector/config/validate \
  | jq '{error_count, errors: [.configs[] | select(.value.errors | length > 0) | {(.value.name): .value.errors}]}'
----
Reference: https://kafka.apache.org/43/kafka-connect/user-guide/#rest-api[Apache Kafka -- Kafka Connect REST API]

An `error_count` of `0` means the configuration is valid and the database was reachable with the given credentials.
When the database is not reachable, the error is reported against `database.hostname`, for example
`Unable to connect (primary): Failed to resolve Oracle database version`.

== Kafka Connect on Kubernetes with Strimzi

On Kubernetes, the recommended way to run Debezium on Kafka Connect is the Strimzi operator. Its `KafkaConnect` resource
can build the Connect image itself: the `spec.build` section names an output registry and lists the plug-ins as
artifacts (a `tgz` URL on Maven Central, ideally with a `sha512sum`). Strimzi then runs the build, pushes the image and
rolls it out to the Connect pods. Connectors are created as `KafkaConnector` resources instead of REST calls.

  build:
    output:

    plugins:
      - name: debezium-connector-oracle
        artifacts:
          - type: tgz
            url: https://repo1.maven.org/maven2/io/debezium/debezium-connector-oracle/3.7.1.Final/debezium-connector-oracle-3.7.1.Final-plugin.tar.gz
            sha512sum: 5788ec1b3b32c87327c8d289e31056db43103d29b9f0c1eba5b04391dc01a977c68351be5979ef1e94d195e0faba3935058d80250bbe36f20e38ce10f3593a5c
----
Reference: https://debezium.io/documentation/reference/stable/operations/kubernetes.html#_creating_kafka_connect_cluster[Debezium -- Creating a Kafka Connect cluster on Kubernetes]

== Debezium Server

Debezium Server is installed by unpacking its distribution (`io.debezium:debezium-server-dist:3.7.1.Final`, a
`.tar.gz` on Maven Central) or by running `quay.io/debezium/server:3.7.1.Final`. It needs Java 21. The distribution has
`config`, `lib`, `lib_opt`, `connectors` and `run.sh`. The image keeps its configuration in `/debezium/config` and its
offsets and history in `/debezium/data`, which must be a persistent volume.

.Starting Debezium Server from the distribution
[source,shell]
----
curl -fsSLO https://repo1.maven.org/maven2/io/debezium/debezium-server-dist/3.7.1.Final/debezium-server-dist-3.7.1.Final.tar.gz
tar -xzf debezium-server-dist-3.7.1.Final.tar.gz
cd debezium-server
# Write config/application.properties first (source, sink, offset and schema history storage)
mkdir -p data
./run.sh
----
Reference: https://debezium.io/documentation/reference/stable/operations/debezium-server.html#installing-debezium-server[Debezium Server -- Installation]

Configuration and sinks are covered in xref:database/migration/debezium-server.adoc[Debezium Server]. For the Oracle
connector, remember the driver rule from the Oracle JDBC driver section above: the Debezium Server documentation asks for
the Oracle JDBC driver to be copied to `lib`.

== The Debezium CLI

The Debezium CLI (`debezium`) is a command-line tool introduced alongside Debezium 3.7. It is distributed through JBang,
so the only prerequisites are Java and JBang. It has two groups of commands:

* *Build:* `init` scaffolds a `dbz.yaml` descriptor for a source and a sink, `validate` checks it, `build` assembles a
  Debezium Server container image without a Docker daemon, and `push` publishes the image.
* *Platform:* `config`, `switch`, `catalog`, `connection`, `source`, `destination`, `transform` and `pipeline` manage
  pipelines on a Debezium Management Platform instance through its REST API, including sending signals such as an
  incremental snapshot.

.Installing the Debezium CLI with JBang and scaffolding a Debezium Server project
[source,shell]
----
curl -Ls https://sh.jbang.dev | bash -s - app setup
jbang app install debezium@debezium
debezium --version

debezium init --source postgres --sink kafka
debezium validate
----
Reference: https://debezium.io/blog/2026/10/26/debezium-cli-release/[Debezium blog -- Debezium CLI]

The CLI targets Debezium Server and the Management Platform. The announcement does not describe any support for Kafka
Connect REST deployments, so the Kafka Connect pipeline of this section is still managed with `curl`, Strimzi resources
or your own automation. The blog post describes the CLI as a new project and invites feedback; treat it as a
convenience for Server-based pipelines rather than as a required part of the installation.

== What goes wrong during installation

[cols="1,2",options="header"]
|===
| Symptom | Cause and fix

| `GET /connector-plugins` does not list a Debezium connector
| The plug-in directory is not directly under a `plugin.path` entry (for example it was extracted one level too deep),
  or the worker was not restarted. Each connector must be a sub-directory of a `plugin.path` directory.

| A connector works on one worker and fails with `ClassNotFoundException` on another
| The workers of the cluster have different plug-ins. Build all workers from the same image.

| `NoSuchMethodError` or strange driver errors
| Two copies of a library (a driver in `/kafka/libs` and another inside the plug-in, or plug-ins of different Debezium
  versions). Keep drivers inside plug-in directories and use one Debezium version per worker.

| The Connect container exits with code 137 shortly after start
| The container was killed for lack of memory; the default heap is up to 2 GB. Set `HEAP_OPTS` to fit the container's
  memory limit and size it for the largest Oracle transactions that the LogMiner buffer must hold.

| The worker stops with `+ConfigException: Path ... does not exist+`
| A `FileConfigProvider` or `DirectoryConfigProvider` `allowed.paths` entry points to a directory that is not mounted.

| Connector creation fails because a topic cannot be created
| `topic.creation.enable=false` on the worker, no default topic creation group on the connector, or missing ACLs. With
  Oracle, also check that pre-created topic names use the upper-case table names.

| The connector refuses to start with `exactly.once.support=required`
| Not every worker has `exactly.once.source.support=enabled`, or the Connect cluster runs in standalone mode.
|===
