= Getting started with Apache Lucene
:description: What Apache Lucene is -- an embedded in-process Java search library -- how to add lucene-core and its companion modules to a Maven or Gradle build, and a first end-to-end index-and-search round-trip.
:keywords: apache lucene, lucene-core, embedded search library, java 21, mmapdirectory, indexwriter, indexsearcher, directoryreader, maven, gradle, lucene-demo, termquery

include::partial$ai-disclaimer.adoc[]

Apache Lucene is a search *library*, not a server: you add a JAR to a JVM application and call its
classes directly. This page explains what that means in practice, lists the Maven and Gradle
coordinates for the modules used throughout this section, and walks one document through indexing and
back out of a query.

== Lucene is an embedded, in-process library

Lucene runs inside your JVM. There is no daemon to start, no port to open, no wire protocol, and
nothing to deploy separately -- an `IndexWriter` is an object you construct, and the index is a
directory of files on a disk you choose. The flip side is that everything a search *server* would do
for you is now your responsibility: concurrency control, when and how to persist, moving an index
between machines, replication, and sharding a corpus that outgrows one node. Lucene gives you the
inverted index, the query evaluation, and the scoring; the operational layer around it is yours to
build or to borrow.

That operational layer is exactly what xref:database/elasticsearch/index.adoc[Elasticsearch],
OpenSearch, and xref:database/solr/index.adoc[Apache Solr] are: all three embed this same Lucene
library and wrap it in a cluster, a REST API, and a persistence/replication model.
xref:database/lucene/lucene-vs-solr-vs-elasticsearch-vs-opensearch.adoc[Lucene vs. Solr vs.
Elasticsearch vs. OpenSearch] compares them directly.

These pages target the *Lucene 10.x* line. Lucene 10 requires *Java 21*, and the default directory
implementation, `MMapDirectory`, memory-maps index files through the Java Platform's foreign-memory
(Panama) API -- see xref:database/lucene/directories-and-storage.adoc[Directory implementations &
storage]. The current requirements are on the
https://lucene.apache.org/core/[Apache Lucene site] and its
https://lucene.apache.org/core/10_0_0/index.html[system-requirements page].

[source,java]
----
// No client, no connection string: you open a directory and construct a writer.
// https://lucene.apache.org/core/10_0_0/core/org/apache/lucene/store/FSDirectory.html
import org.apache.lucene.store.Directory;
import org.apache.lucene.store.FSDirectory;
import org.apache.lucene.analysis.standard.StandardAnalyzer;
import org.apache.lucene.index.IndexWriter;
import org.apache.lucene.index.IndexWriterConfig;
import java.nio.file.Path;

try (Directory dir = FSDirectory.open(Path.of("/var/data/my-index"));
     IndexWriter writer = new IndexWriter(dir, new IndexWriterConfig(new StandardAnalyzer()))) {
    // ... index documents ...
}
----

== Adding Lucene to a build

`org.apache.lucene:lucene-core` is the only mandatory dependency. The rest of this section draws on a
set of companion modules, each a separate artifact under the same group and version; add only the
ones a page actually uses. The Javadoc for every module is linked from the
https://lucene.apache.org/core/10_0_0/index.html[Lucene 10 API index].

[cols="2,3",options="header"]
|===
| Module | Used for

| `lucene-core` | `Directory`, `IndexWriter`, `DirectoryReader`, `IndexSearcher`, the core `Query` types, BKD points, doc values, the default codec.
| `lucene-analysis-common` | `CustomAnalyzer`, `EnglishAnalyzer` and the other language analyzers, `WhitespaceAnalyzer`, `KeywordAnalyzer`, and the common tokenizers and token filters (`StandardAnalyzer` and `StandardTokenizer` themselves ship in `lucene-core`) -- xref:database/lucene/analysis-pipeline.adoc[Analysis pipeline].
| `lucene-queryparser` | `QueryParser` and the other string-to-`Query` parsers -- xref:database/lucene/query-parsers.adoc[Query parsers].
| `lucene-facet` | `FacetsCollector`, taxonomy and `SortedSetDocValues` faceting -- xref:database/lucene/filtering-and-faceting.adoc[Filtering & faceting].
| `lucene-highlighter` | `UnifiedHighlighter` and the other highlighters -- xref:database/lucene/highlighting-suggesters-and-more.adoc[Highlighting, suggesters & more].
| `lucene-suggest` | Autocomplete and "did you mean" -- `AnalyzingInfixSuggester`, `DirectSpellChecker`.
| `lucene-join` | `JoinUtil` and block-join queries -- xref:database/lucene/grouping-and-joins.adoc[Grouping & joins].
| `lucene-grouping` | First-pass/second-pass result grouping.
| `lucene-expressions` | JavaScript expression `DoubleValuesSource` for sorting and scoring -- xref:database/lucene/function-and-custom-scoring.adoc[Function & custom scoring].
| `lucene-queries` | Extra `Query` implementations: `FunctionScoreQuery`, `MoreLikeThis`, `CommonTermsQuery`.
| `lucene-spatial-extras` | Grid (prefix-tree) and serialized-DV spatial strategies on top of core's `LatLonPoint`/`LatLonShape` -- xref:database/lucene/spatial-search.adoc[Spatial search].
| `lucene-monitor` | Reverse search / stored-query matching -- xref:database/lucene/monitor-reverse-search.adoc[Monitor / reverse search].
| `lucene-backward-codecs` | Read indexes written by the previous major version.
| `lucene-test-framework` | `LuceneTestCase`, `RandomIndexWriter`, `newDirectory()` -- xref:database/lucene/testing-tools-and-modules.adoc[Testing tools & modules].
|===

----
<!-- Maven: lucene-core plus the two modules almost every app also needs. -->
<!-- https://lucene.apache.org/core/10_0_0/core/index.html -->
<dependencies>
  <dependency>
    <groupId>org.apache.lucene</groupId>
    <artifactId>lucene-core</artifactId>
    <version>10.0.0</version>
  </dependency>
  <dependency>
    <groupId>org.apache.lucene</groupId>
    <artifactId>lucene-analysis-common</artifactId>
    <version>10.0.0</version>
  </dependency>
  <dependency>
    <groupId>org.apache.lucene</groupId>
    <artifactId>lucene-queryparser</artifactId>
    <version>10.0.0</version>
  </dependency>
</dependencies>
----

[source,groovy]
----
// Gradle (Groovy DSL): keep the version in one place and reuse it.
def luceneVersion = '10.0.0'
dependencies {
    implementation "org.apache.lucene:lucene-core:${luceneVersion}"
    implementation "org.apache.lucene:lucene-analysis-common:${luceneVersion}"
    implementation "org.apache.lucene:lucene-queryparser:${luceneVersion}"
    // add as needed, e.g.
    // implementation "org.apache.lucene:lucene-facet:${luceneVersion}"
    // implementation "org.apache.lucene:lucene-highlighter:${luceneVersion}"
    testImplementation "org.apache.lucene:lucene-test-framework:${luceneVersion}"
}
----

The distribution also bundles `lucene-demo`, a runnable example whose `IndexFiles` and `SearchFiles`
classes index a directory tree and query it from the command line -- a working reference for the code
below. See the https://lucene.apache.org/core/10_0_0/demo/index.html[lucene-demo module docs].

== A first index-and-search round-trip

The following opens a `Directory`, writes two documents with an `IndexWriter`, opens a
`DirectoryReader` and an `IndexSearcher`, and runs two queries: a `TermQuery` built directly, and a
query produced by the string parser. `TopDocs` holds the ranked hit list; the stored fields of each
hit are read back through `searcher.storedFields()`.

[source,java]
----
// https://lucene.apache.org/core/10_0_0/core/org/apache/lucene/index/IndexWriter.html
// https://lucene.apache.org/core/10_0_0/core/org/apache/lucene/search/IndexSearcher.html
import org.apache.lucene.analysis.standard.StandardAnalyzer;
import org.apache.lucene.document.Document;
import org.apache.lucene.document.Field;
import org.apache.lucene.document.StringField;
import org.apache.lucene.document.TextField;
import org.apache.lucene.index.*;
import org.apache.lucene.queryparser.classic.QueryParser;
import org.apache.lucene.search.*;
import org.apache.lucene.store.Directory;
import org.apache.lucene.store.FSDirectory;
import java.nio.file.Path;

Directory dir = FSDirectory.open(Path.of("/var/data/books-index"));
StandardAnalyzer analyzer = new StandardAnalyzer();

// --- index ---
try (IndexWriter writer = new IndexWriter(dir, new IndexWriterConfig(analyzer))) {
    Document a = new Document();
    a.add(new StringField("isbn", "9780134685991", Field.Store.YES)); // exact term
    a.add(new TextField("title", "Effective Java", Field.Store.YES));  // analyzed
    writer.addDocument(a);

    Document b = new Document();
    b.add(new StringField("isbn", "9780596009205", Field.Store.YES));
    b.add(new TextField("title", "Head First Java", Field.Store.YES));
    writer.addDocument(b);
}   // close() commits

// --- search ---
try (DirectoryReader reader = DirectoryReader.open(dir)) {
    IndexSearcher searcher = new IndexSearcher(reader);

    // 1. a Query built in code
    Query exact = new TermQuery(new Term("isbn", "9780134685991"));
    TopDocs byIsbn = searcher.search(exact, 10);

    // 2. a Query parsed from a string ("java" is analyzed the same way the field was)
    Query parsed = new QueryParser("title", analyzer).parse("java");
    TopDocs byTitle = searcher.search(parsed, 10);

    StoredFields stored = searcher.storedFields();
    for (ScoreDoc hit : byTitle.scoreDocs) {
        Document doc = stored.document(hit.doc);
        System.out.printf("%.3f  %s  %s%n", hit.score, doc.get("isbn"), doc.get("title"));
    }
}
----

Each of those objects is a chain: `IndexWriterConfig` carries the `Analyzer`, the `Directory` holds
the segments, the `DirectoryReader` gives the `IndexSearcher` a point-in-time view, and the `Query`
produces `TopDocs`. xref:database/lucene/architecture-and-data-flow.adoc[The index model & class
chains] draws that out. The field choice above -- `StringField` for the exact ISBN, `TextField` for
the analyzed title -- is the subject of xref:database/lucene/documents-and-fields.adoc[Documents,
fields & the capability matrix], and the two query forms open
xref:database/lucene/core-queries.adoc[Core queries].

== The running example: a book catalog

Every page in this section reuses one small corpus so that results can be compared from page to page: a catalog
of eight books. Each book has an ISBN (an identifier that must match exactly), a title and an author (text),
a one-sentence description (longer text), a publication year (a number to range-search and sort) and a couple of
tags (exact keywords). The catalog is plain Java -- a `record` and a list -- and a helper turns each entry into
a Lucene `Document`:

[source,java]
----
// The running example used throughout this section.
public record Book(String isbn, String title, String author, int year, String description, String... tags) {}

public static final List<Book> BOOKS = List.of(
    new Book("9780134685991", "Effective Java", "Joshua Bloch", 2018,
        "Best practices for the Java platform, from generics to lambdas.", "java", "best-practices"),
    new Book("9780596009205", "Head First Java", "Kathy Sierra", 2005,
        "A brain-friendly guide to learning Java.", "java", "beginner"),
    new Book("9780321349606", "Java Concurrency in Practice", "Brian Goetz", 2006,
        "Threads, locks and the Java memory model explained for practitioners.", "java", "concurrency"),
    new Book("9781933988177", "Lucene in Action", "Michael McCandless", 2010,
        "Building search applications with Lucene: indexing, analysis and searching.", "search", "lucene"),
    new Book("9781449358549", "Elasticsearch: The Definitive Guide", "Clinton Gormley", 2015,
        "A distributed real-time search and analytics engine built on Lucene.", "search", "elasticsearch"),
    new Book("9781617291029", "Solr in Action", "Trey Grainger", 2014,
        "Searching, faceting and scaling with Apache Solr and Lucene.", "search", "solr"),
    new Book("9780521865715", "Introduction to Information Retrieval", "Christopher Manning", 2008,
        "Ranking, indexing, evaluation and classification of text collections.", "search", "theory"),
    new Book("9780134190440", "The Go Programming Language", "Alan Donovan", 2015,
        "A guide to writing clear and idiomatic Go programs.", "go"));

public static Document toDoc(Book b) {
    Document d = new Document();
    d.add(new StringField("isbn", b.isbn(), Field.Store.YES));            // exact id
    d.add(new TextField("title", b.title(), Field.Store.YES));            // analyzed text
    d.add(new TextField("author", b.author(), Field.Store.YES));
    d.add(new TextField("description", b.description(), Field.Store.YES));
    d.add(new IntField("year", b.year(), Field.Store.YES));               // range + sort + stored
    for (String t : b.tags()) d.add(new KeywordField("tag", t, Field.Store.NO)); // exact, sortable, facetable
    return d;
}
----

The choice of field class for each attribute is deliberate and is explained field by field on
xref:database/lucene/documents-and-fields.adoc[Documents, fields & the capability matrix]. The later pages add
doc-values fields, term vectors and other capabilities to the same catalog as each feature needs them.

Running the round trip above against this catalog on Lucene 10.0.0 (JDK 21) prints:

[source,text]
----
directory class = MMapDirectory
numDocs=8 segments=1
isbn hits: 1 hits
parsed: title:java
0.515  9780134685991  Effective Java
0.450  9780596009205  Head First Java
0.399  9780321349606  Java Concurrency in Practice
----

Three details are worth reading out of that output. `FSDirectory.open` really did return an `MMapDirectory`.
Closing the writer flushed all eight documents into a *single* segment (`segments=1`). And the query parser
printed `title:java`: the string `java` was analyzed with the same `StandardAnalyzer` that indexed the title, and
the resulting term is what the `TermQuery` looks up. The three Java titles rank in a different order than their
position in the catalog because BM25 (see xref:database/lucene/scoring-and-similarity.adoc[Scoring & similarity])
favours the shorter field: `Effective Java` has two tokens in its title, `Head First Java` three.

== What the round trip does, step by step

[mermaid]
....
sequenceDiagram
    participant App as Application
    participant W as IndexWriter
    participant D as Directory
    participant R as DirectoryReader
    participant S as IndexSearcher
    App->>W: addDocument(doc) x 8
    W->>W: analyze text fields, buffer postings in RAM
    App->>W: close()
    W->>D: flush one segment, fsync, write segments_1
    App->>R: DirectoryReader.open(dir)
    R->>D: read segments_1 and the segment files
    App->>S: new IndexSearcher(reader)
    App->>S: search(query, 10)
    S->>R: visit each segment, score matching docs
    S-->>App: TopDocs (doc ids and scores)
    App->>S: storedFields().document(docId)
    S-->>App: stored values for display
....

Nothing is searchable until the writer has flushed *and* a reader has been opened over that state. A
`DirectoryReader` is a snapshot: documents added after it was opened are invisible to it, which is why a
long-running application reopens readers periodically instead of opening one per query -- the subject of
xref:database/lucene/near-real-time-search.adoc[Near-real-time search].

== Build and run the example

A minimal Maven project needs the three dependencies shown above and a Java 21 compiler release. Lucene 10
class files target Java 21, so running on an older JVM fails immediately and unambiguously:

[source,text]
----
Error: LinkageError occurred while loading main class lab.Lab01
java.lang.UnsupportedClassVersionError: lab/Lab01 has been compiled by a more recent version of the
Java Runtime (class file version 65.0), this version of the Java Runtime only recognizes class file
versions up to 61.0
----

[source,xml]
----
<properties>
  <maven.compiler.release>21</maven.compiler.release>
  <lucene.version>10.0.0</lucene.version>
</properties>
----

On JDK 21 you will see two harmless warnings the first time Lucene opens an index. The first is the JVM
reporting that `MMapDirectory` called a restricted foreign-memory method; start the JVM with
`+--enable-native-access=ALL-UNNAMED+` to acknowledge it. The second is Lucene noting that the optional Vector API
is unavailable:

[source,text]
----
WARNING: A restricted method in java.lang.foreign.Linker has been called
WARNING: Use --enable-native-access=ALL-UNNAMED to avoid a warning for this module
WARNING: Java vector incubator module is not readable. For optimal vector performance, pass
'--add-modules jdk.incubator.vector' to enable Vector API.
----

Passing `+--add-modules jdk.incubator.vector+` lets Lucene use SIMD instructions for vector distance
computations and some bulk operations; it changes performance, never results.

== The mistakes everyone makes on day one

Three failures account for most first-hour questions, and each one produces a precise exception:

* *Opening a reader before anything was committed.* `DirectoryReader.open(dir)` on a directory with no
  `segments_N` file throws `+IndexNotFoundException: no segments* file found ... files: []+`. Create the index
  (open and close an `IndexWriter`, or call `commit()`) before opening the reader.
* *Two writers on one index.* The second `IndexWriter` throws `LockObtainFailedException: Lock held by this
  virtual machine: .../write.lock`. Share one writer across threads instead; see
  xref:database/lucene/directories-and-storage.adoc[Directories & storage].
* *Querying with a different analyzer than indexing.* A `TermQuery` for `Lucene` finds nothing in a field
  indexed with `StandardAnalyzer`, because the index holds `lucene`. Use the same analyzer for the query
  parser, or build the term from analyzed text yourself; see
  xref:database/lucene/query-parsers.adoc[Query parsers].
