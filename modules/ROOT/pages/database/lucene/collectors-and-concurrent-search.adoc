= Collectors & concurrent search
:description: How Lucene 10 gathers hits -- the CollectorManager model that replaces bare Collector, running one query across an Executor, the total-hits threshold and TotalHits.Relation, early termination, and writing a custom CollectorManager.
:keywords: apache lucene, indexsearcher, collectormanager, topscoredoccollectormanager, topfieldcollectormanager, totalhitcountcollectormanager, concurrent search, executor, intra-segment concurrency, topdocs merge, total hits threshold, totalhits relation, query timeout, custom collector, leafslice

include::partial$ai-disclaimer.adoc[]

A search walks the postings for every leaf and hands each matching doc id to a *collector*, which
keeps whatever the caller wants -- usually a bounded heap of the top-scoring hits. Lucene 10 drives
this through `CollectorManager`: the searcher makes one collector per segment slice, runs the slices
(optionally on different threads), then reduces the partial results into one answer.

The measurements on this page come from a scaled-up copy of the book catalogue: 400,000 documents
written as eight segments of 50,000 (merging disabled, so the segment layout is known), each with a
text field and numeric `year` and `price` doc values. Outputs are real runs on Lucene 10.4.0.

== TopDocs and the search shortcuts

`IndexSearcher.search(Query, n)` returns a `TopDocs`: an array of `ScoreDoc` (doc id + score) plus a
`TotalHits`. The convenience overloads build the right `CollectorManager` internally.

[source,java]
----
// https://lucene.apache.org/core/10_0_0/core/org/apache/lucene/search/IndexSearcher.html
IndexSearcher searcher = new IndexSearcher(reader);

TopDocs top = searcher.search(query, 10);
long total = top.totalHits.value();          // see the threshold caveat below
for (ScoreDoc sd : top.scoreDocs) {
    int docId = sd.doc;
    float score = sd.score;
}

// Sorted variant returns TopFieldDocs.
TopFieldDocs byPrice = searcher.search(query, 10,
        new Sort(new SortField("price", SortField.Type.LONG)));
----

Turning a `ScoreDoc.doc` back into field values is xref:database/lucene/retrieving-results.adoc[a
separate step] -- the collector only ever sees the id and the score.

== CollectorManager and concurrent search

A bare `Collector` is single-threaded. `CollectorManager<C, T>` makes it concurrency-safe: the
searcher calls `newCollector()` once per slice, collects each slice independently, then calls
`reduce(collectors)` to merge. Pass an `Executor` to the `IndexSearcher` constructor and the slices
run in parallel.

[source,java]
----
// https://lucene.apache.org/core/10_0_0/core/org/apache/lucene/search/CollectorManager.html
import java.util.concurrent.Executors;
import org.apache.lucene.search.*;

var pool = Executors.newFixedThreadPool(Runtime.getRuntime().availableProcessors());
IndexSearcher searcher = new IndexSearcher(reader, pool);

// Top hits by score. Args: numHits, totalHitsThreshold.
var byScore = new TopScoreDocCollectorManager(10, Integer.MAX_VALUE);
TopDocs hits = searcher.search(query, byScore);

// Top hits by sort field. Args: sort, numHits, totalHitsThreshold.
var bySort = new TopFieldCollectorManager(
        new Sort(new SortField("price", SortField.Type.LONG)), 10, Integer.MAX_VALUE);
TopFieldDocs sorted = searcher.search(query, bySort);

// Count only -- no scoring, no heap.
var counter = new TotalHitCountCollectorManager(searcher.getSlices());
int count = searcher.search(query, counter);
----

These three managers (`TopScoreDocCollectorManager`, `TopFieldCollectorManager`,
`TotalHitCountCollectorManager`) replace the old `+TopScoreDocCollector.create(...)+` /
`+TopFieldCollector.create(...)+` static factories, which are removed. On the scaled catalogue, the three
calls for the term `java` (120,000 matching documents) give:

[source,text]
----
exact         : total=120000 relation=EQUAL_TO
  price asc: doc 4 key=3904
  price asc: doc 104 key=3904
  price asc: doc 204 key=3904
count via manager: 120000  searcher.count: 120000
----

=== Slices: how a search is divided

The unit of parallel work is a *slice*: a group of segments, or of parts of segments, that one task
searches with one collector. Without an executor there is exactly one slice. With an executor, the
default policy groups segments until a slice holds about 250,000 documents or five segments:

[source,text]
----
docs=400000 segments=8
slices without executor: 1
slices with executor   : 2
  slice docs=250000: seg0[0..max] seg1[0..max] seg2[0..max] seg3[0..max] seg4[0..max]
  slice docs=150000: seg5[0..max] seg6[0..max] seg7[0..max]
----

Eight segments became two slices, so at most two threads work on this query however large the pool
is. Use the static `IndexSearcher.slices(leaves, maxDocsPerSlice, maxSegmentsPerSlice,
allowSegmentPartitions)` from an overriding `slices(List)` to choose another split. With the same
eight segments, `slices(r.leaves(), 100_000, 2, true)` gives four slices and
`slices(r.leaves(), 1_000_000, 1, false)` gives one slice per segment (eight).

Lucene 10 can also split *inside* a segment (intra-segment concurrency), which matters after
`forceMerge(1)` or when a few huge segments dominate. It is not the default. After merging the 400,000
documents into one segment the default is still a single slice; opting in splits it by document id
range:

[source,java]
----
IndexSearcher partitioned = new IndexSearcher(reader, pool) {
    @Override
    protected LeafSlice[] slices(List<LeafReaderContext> leaves) {
        return IndexSearcher.slices(leaves, 100_000, 5, true);   // allowSegmentPartitions
    }
};
----

[source,text]
----
one segment of 400000 docs, slices=1
with allowSegmentPartitions=true: 4 slices
  100000 docs: seg0[0..100000]
  100000 docs: seg0[100000..200000]
  100000 docs: seg0[200000..300000]
  100000 docs: seg0[300000..400000]
count even (partitioned) = 200000
----

A partition is a half-open doc id range of one segment, and the counts are unchanged. Every collector
manager sees the slices as separate collectors, so *a `CollectorManager` must tolerate collecting
several ranges of the same segment* -- anything that assumes one `getLeafCollector` call per segment
is wrong under partitioning.

[mermaid]
....
sequenceDiagram
  participant App
  participant S as IndexSearcher
  participant P as Executor
  participant M as CollectorManager
  App->>S: search(query, manager)
  S->>S: slices(leaves)
  loop for each slice
    S->>M: newCollector()
    S->>P: submit task: weight.scorer, collect each hit
  end
  P-->>S: all tasks done
  S->>M: reduce(collectors)
  M-->>S: merged result
  S-->>App: TopDocs
....

To merge results computed separately (per shard, or per index), use `TopDocs.merge`:

[source,java]
----
// https://lucene.apache.org/core/10_0_0/core/org/apache/lucene/search/TopDocs.html
TopDocs merged = TopDocs.merge(10, new TopDocs[] { shardA, shardB, shardC });

// Sorted inputs need the Sort so the merge compares the right values.
TopFieldDocs mergedSorted = TopDocs.merge(sort, 10, new TopFieldDocs[] { a, b });
----

Doc ids are only meaningful inside one index, and `TopDocs.merge` does not tag the hits it returns:
unless `ScoreDoc.shardIndex` was set beforehand it stays -1, so a merged hit cannot be traced back to its
index, and hits with equal scores from different indexes interleave by doc id alone. Set it on every
input hit before merging. Two indexes of three identical documents, merged for the top four:

[source,java]
----
for (ScoreDoc sd : t1.scoreDocs) sd.shardIndex = 0;
for (ScoreDoc sd : t2.scoreDocs) sd.shardIndex = 1;
TopDocs m = TopDocs.merge(4, new TopDocs[] { t1, t2 });
----

[source,text]
----
without shardIndex: (doc0,shard-1) (doc0,shard-1) (doc1,shard-1) (doc1,shard-1)
with shardIndex   : (doc0,shard0) (doc1,shard0) (doc2,shard0) (doc0,shard1)
----

The migration notes describe the `CollectorManager`-only search path and the executor changes:
https://lucene.apache.org/core/10_0_0/core/org/apache/lucene/search/IndexSearcher.html[`IndexSearcher`].

== Total-hit counting and early termination

By default the top-hits managers stop counting once `totalHitsThreshold` matches have been seen (1000,
or `numHits` if larger, in the plain `search(Query, n)` shortcut). When that happens
`totalHits.value()` is a lower bound, flagged by `totalHits.relation()`. Early termination is per slice,
so the bound is only approximately the threshold:

[source,java]
----
// https://lucene.apache.org/core/10_0_0/core/org/apache/lucene/search/TotalHits.html
TopDocs top = searcher.search(query, 10);
if (top.totalHits.relation() == TotalHits.Relation.GREATER_THAN_OR_EQUAL_TO) {
    // value() is only a floor -- counting stopped early
} else {
    // TotalHits.Relation.EQUAL_TO -- value() is exact
}

// Pass Integer.MAX_VALUE as the threshold to force an exact count (slower).
var exact = new TopScoreDocCollectorManager(10, Integer.MAX_VALUE);
----

The same query over the two-slice searcher, with and without the shortcut:

[source,text]
----
default search: total=2002 relation=GREATER_THAN_OR_EQUAL_TO
exact         : total=120000 relation=EQUAL_TO
same top doc scores? true
----

Both agree on the top documents -- the cheaper search is not approximate about *which* documents rank
first, only about the *count*. Lucene stops counting when the remaining documents cannot enter the
top 10, a skip made possible by `ScoreMode.TOP_SCORES` and the impact metadata stored with each block
of postings. A UI that shows "about 120,000 results" can use the lower bound plus the relation (it shows
`1000+` style counts); a pager that needs the exact total must pay for it.

[mermaid]
....
flowchart TD
  A["search(query, 10)"] --> B["threshold = max(1000, numHits)"]
  B --> C{"matches counted so far >= threshold?"}
  C -->|no| D["count and score this match"]
  D --> C
  C -->|yes| E["stop counting; keep skipping only non-competitive blocks"]
  E --> F["TotalHits: value is a lower bound, relation is GREATER_THAN_OR_EQUAL_TO"]
  C -->|all docs visited first| G["TotalHits: exact, relation is EQUAL_TO"]
....

=== Bounding wall-clock time

The `TimeLimitingCollector` of older releases is no longer part of the core library. The supported way
to bound a query is a query timeout on the searcher, an `IndexSearcher.setTimeout(QueryTimeout)`
with the `QueryTimeoutImpl` that counts milliseconds from its construction:

[source,java]
----
// https://lucene.apache.org/core/10_0_0/core/org/apache/lucene/index/QueryTimeoutImpl.html
IndexSearcher searcher = new IndexSearcher(reader);
searcher.setTimeout(new QueryTimeoutImpl(200L));            // 200 ms from now
TopDocs partial = searcher.search(query, 10);               // returns what was collected in time
----

[source,text]
----
timeout 0ms: hits=0 total=0 hits
timeout 60s: hits=10 total=1001+ hits
----

An already-expired timeout returns an empty `TopDocs` instead of throwing, and a generous one does not
change the result. A `QueryTimeoutImpl` is fixed at construction, so create a fresh one per request
(or `reset()` it); a timeout set once at start-up expires for good. Treat a timed-out result as partial: it
has fewer hits than a complete search and nothing marks the difference except a smaller count than
expected, so log slow queries and decide at the call site whether a partial page is acceptable.
`ExitableDirectoryReader` enforces the same kind of limit inside the index reading code, below the
collector, for queries (such as large wildcard expansions) that spend their time before collection
starts.

== Writing a custom CollectorManager

Implement `CollectorManager` when the top-N heap is not what you need -- a global id set, a
histogram, a running aggregate. `newCollector()` must return an independent instance; `reduce` runs
after all slices finish.

[source,java]
----
import java.util.*;
import org.apache.lucene.index.LeafReaderContext;
import org.apache.lucene.search.*;

/** Collects every matching global doc id, in order. */
class IdCollectorManager implements CollectorManager<IdCollectorManager.Leaf, List<Integer>> {

    static final class Leaf implements Collector {
        final List<Integer> ids = new ArrayList<>();

        @Override public ScoreMode scoreMode() { return ScoreMode.COMPLETE_NO_SCORES; }

        @Override public LeafCollector getLeafCollector(LeafReaderContext ctx) {
            int base = ctx.docBase;
            return new LeafCollector() {
                @Override public void setScorer(Scorable s) { }
                @Override public void collect(int doc) { ids.add(base + doc); }
            };
        }
    }

    @Override public Leaf newCollector() { return new Leaf(); }

    @Override public List<Integer> reduce(Collection<Leaf> leaves) {
        List<Integer> all = new ArrayList<>();
        for (Leaf l : leaves) all.addAll(l.ids);
        Collections.sort(all);
        return all;
    }
}

List<Integer> matches = searcher.search(query, new IdCollectorManager());
----

Returning `COMPLETE_NO_SCORES` tells Lucene not to compute scores at all. On the scaled catalogue, 1
in 1000 documents contains the term `rareword`, and the manager finds exactly those 400:

[source,text]
----
rareword ids: 400 first=[0, 1000, 2000, 3000, 4000]
----

A collector usually needs more than the doc id. The per-document data is read from doc values inside
`getLeafCollector`, which is called once per segment (or segment range). This manager builds a
histogram of publication years over the matching documents; the leaf collectors fill private maps and
`reduce` adds them:

[source,java]
----
class YearHistogramManager implements CollectorManager<YearHistogramManager.Leaf, SortedMap<Long, Integer>> {
    static final class Leaf implements Collector {
        final SortedMap<Long, Integer> hist = new TreeMap<>();

        @Override public ScoreMode scoreMode() { return ScoreMode.COMPLETE_NO_SCORES; }

        @Override public LeafCollector getLeafCollector(LeafReaderContext ctx) throws IOException {
            NumericDocValues years = DocValues.getNumeric(ctx.reader(), "year");
            return new LeafCollector() {
                @Override public void setScorer(Scorable s) { }
                @Override public void collect(int doc) throws IOException {
                    if (years.advanceExact(doc)) hist.merge(years.longValue(), 1, Integer::sum);
                }
            };
        }
    }

    @Override public Leaf newCollector() { return new Leaf(); }

    @Override public SortedMap<Long, Integer> reduce(Collection<Leaf> leaves) {
        SortedMap<Long, Integer> out = new TreeMap<>();
        for (Leaf l : leaves) l.hist.forEach((k, v) -> out.merge(k, v, Integer::sum));
        return out;
    }
}

SortedMap<Long, Integer> histogram = searcher.search(new TermQuery(new Term("body", "lucene")), new YearHistogramManager());
----

[source,text]
----
year histogram for 'lucene': {2010=13333, 2011=13334, 2012=13333, 2015=13334, 2016=13333, 2017=13333}
----

`lucene` appears in two of the ten titles (Lucene in Action and Elasticsearch in Action), whose years
are shifted by 0 to 2 in the generated data, so six year buckets share the 80,000 matches. Because
each slice owns its own `Leaf`, no locking is needed; the only shared step is `reduce`. `CollectorManager`
contract:
https://lucene.apache.org/core/10_0_0/core/org/apache/lucene/search/CollectorManager.html[`CollectorManager`].

[mermaid]
....
flowchart TD

  SL --> A["slice A - segments 0..2"]
  SL --> B["slice B - segments 3..5"]
  SL --> C["slice C - segment 6"]
  A --> AC["newCollector(): per-slice top-N"]

This is the same scatter/gather shape that a distributed engine runs one layer higher, across nodes
rather than segment slices -- see
xref:database/solr/distributed-indexing-and-search.adoc[Solr: Distributed indexing & search].

== Choosing a collector

[cols="2,3",options="header"]
|===
| Need | Use

| The best N by score | `TopScoreDocCollectorManager(n, threshold)` or `search(query, n)`
| The best N by field | `TopFieldCollectorManager(sort, n, threshold)`
| Only a count | `TotalHitCountCollectorManager(slices)` or `searcher.count(query)`
| Facet counts | `FacetsCollectorManager` (see xref:database/lucene/filtering-and-faceting.adoc[Filtering & faceting])
| Groups | `GroupingSearch` (see xref:database/lucene/grouping-and-joins.adoc[Grouping & joins])
| A custom aggregate | your own `CollectorManager`
|===

`searcher.count(query)` is worth knowing: for simple queries it answers from index statistics without
visiting documents at all.
