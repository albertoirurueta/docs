= Spatial search
:description: Indexing and querying geographic data in Lucene -- LatLonPoint and LatLonShape in lucene-core, the prefix-tree and serialized strategies in lucene-spatial-extras, geo3d geometry on the ellipsoid in lucene-spatial3d, and WKT/GeoJSON parsing.
:keywords: apache lucene, spatial search, latlonpoint, latlondocvaluesfield, latlonshape, xyshape, lucene-spatial-extras, recursiveprefixtreestrategy, serializeddvstrategy, prefixtreestrategy, lucene-spatial3d, geo3d, geo3dpoint, simplewktshapeparser, wkt, geojson, geospatial, distance sort, date line

include::partial$ai-disclaimer.adoc[]

Lucene stores latitude/longitude points and 2D geometries as BKD-tree numeric fields in
`lucene-core`, so the common cases -- "within this box", "within this radius", "inside this polygon",
"sort by distance" -- need no extra module. `lucene-spatial-extras` adds grid (prefix-tree) and
serialized strategies for richer shape relations and non-geodetic planes, and `lucene-spatial3d`
computes on the actual ellipsoid so shapes that cross a pole or the date line behave correctly.

The running example extends the book catalogue with seven *bookshops* around New York (Midtown Books,
Village Pages, Brooklyn Reads, Harlem Stacks, Jersey Shelf, Queens Quill and Battery Books), each with
a latitude and longitude. Every output block is a real run against Lucene 10.4.0.

== Points with LatLonPoint (lucene-core)

`LatLonPoint` encodes one `(latitude, longitude)` pair into an indexed BKD point. Add a matching
`LatLonDocValuesField` when you also need distance sorting or per-hit distance values -- the indexed
point drives the query, the doc-values field drives the sort.

[source,java]
----
// https://lucene.apache.org/core/10_0_0/core/org/apache/lucene/document/LatLonPoint.html
import org.apache.lucene.document.Document;
import org.apache.lucene.document.LatLonPoint;
import org.apache.lucene.document.LatLonDocValuesField;
import org.apache.lucene.search.*;

Document d = new Document();
d.add(new StoredField("name", "Battery Books"));
d.add(new LatLonPoint("location", 40.7033, -74.0170));            // indexed, for queries
d.add(new LatLonDocValuesField("location", 40.7033, -74.0170));   // doc values, for sort / retrieval
writer.addDocument(d);

// --- query forms, all built as static factories on LatLonPoint ---
Query box = LatLonPoint.newBoxQuery("location",
        40.68, 40.75, -74.05, -73.95);                            // minLat, maxLat, minLon, maxLon
Query radius = LatLonPoint.newDistanceQuery("location",
        40.7128, -74.0060, 5_000.0);                              // metres (great-circle)
Query poly = LatLonPoint.newPolygonQuery("location",
        new org.apache.lucene.geo.Polygon(
                new double[] {40.6, 40.6, 40.8, 40.8, 40.6},
                new double[] {-74.1, -73.9, -73.9, -74.1, -74.1}));

// distance sort needs the LatLonDocValuesField, not the point
Sort nearest = new Sort(
        LatLonDocValuesField.newDistanceSort("location", 40.7128, -74.0060));
TopFieldDocs hits = searcher.search(radius, 20, nearest);

// relevance boost that decays with distance from a pivot (recency-style, but geographic)
Query feature = LatLonPoint.newDistanceFeatureQuery(
        "location", 3.0f, 40.7128, -74.0060, 10_000.0);           // boost weight, origin, pivot distance
----

For a person standing at downtown Manhattan (40.7128, -74.0060) the queries return:

[source,text]
----
box: [Battery Books, Jersey Shelf, Village Pages]
radius 5km: [Battery Books, Jersey Shelf, Village Pages]
polygon: [Battery Books, Brooklyn Reads, Jersey Shelf, Midtown Books, Village Pages]
----

The box and the 5 km radius happen to pick the same three shops, while the wider polygon adds Midtown
and Brooklyn. Note the coordinate order: every `+LatLon*+` API takes *latitude first*; the spatial4j and
WKT APIs below take *longitude first* (x, y).

The distance sort returns the per-hit distance in metres through the sort key, so it can be shown
next to each result without recomputation:

[source,text]
----
-- sorted by distance within 20 km
   Battery Books    1406 m
   Village Pages    2330 m
   Jersey Shelf     3176 m
   Midtown Books    5035 m
   Brooklyn Reads   6477 m
   Harlem Stacks    12075 m
   Queens Quill     17873 m
nearest 3: Battery Books; Village Pages; Jersey Shelf;
----

`LatLonPoint.nearest(searcher, field, lat, lon, n)` returns the *n* closest points directly, without a
bounding query, and agrees with the sort on the first three. The distance feature query is not a filter: it
returns every shop and scores by closeness, `pass:c[weight * pivot / (pivot + distance)]`:

[source,text]
----
-- distance feature (weight 3, pivot 10 km)
   2.630 Battery Books
   2.433 Village Pages
   2.277 Jersey Shelf
   1.995 Midtown Books
   1.821 Brooklyn Reads
   1.359 Harlem Stacks
   1.076 Queens Quill
----

Add it as a `SHOULD` clause to a text query to prefer nearer results without excluding the farther ones.
It is the geographic sibling of `LongField.newDistanceFeatureQuery` used for recency in
xref:database/lucene/function-and-custom-scoring.adoc[Function & custom scoring] and
xref:database/lucene/points-and-range-queries.adoc[Points & range queries]; the BKD structure that
all of these ride on is described there.

=== The date line

`newBoxQuery` handles date-line crossing when `minLon > maxLon`: it rewrites the box into two boxes, one
on each side of the 180th meridian. With four shops in the South Pacific (Fiji at longitude 178, Samoa
at -172, Tonga at -175.2 and Auckland at 174.76):

[source,java]
----
Query across = LatLonPoint.newBoxQuery("loc", -25, -10, 170, -170);   // minLon 170 > maxLon -170
Query inverted = LatLonPoint.newBoxQuery("loc", -25, -10, -170, 170); // the wide band, not the narrow one
----

[source,text]
----
box(170 -> -170)  -> [Fiji Reads, Samoa Stacks, Tonga Tomes]
box(-170 -> 170)  -> []
radius 500 km around (-17, 179.9) -> [Fiji Reads]
----

The first box is printed as two constant-score clauses (longitudes -180 to -170 and 170 to 180). The second
is the band of longitudes *between* -170 and 170, which holds none of the shops. The order of the two
longitudes, not their values, selects the interpretation, so a box built from a user's map viewport must
keep the west edge first.

== Geometries with LatLonShape and XYShape (lucene-core)

`LatLonPoint` only indexes points. To index polygons, lines, or a point that must answer
`CONTAINS`/`WITHIN`/`DISJOINT` relations, use `LatLonShape`: it tessellates each geometry into
triangles and indexes those as shape-encoded points. `XYShape` is the identical API over a flat
Cartesian plane (floats, no Earth curvature) for floor plans, game maps, or projected data.

[source,java]
----
// https://lucene.apache.org/core/10_0_0/core/org/apache/lucene/document/LatLonShape.html
import org.apache.lucene.document.Field;
import org.apache.lucene.document.LatLonShape;
import org.apache.lucene.document.ShapeField;
import org.apache.lucene.geo.Polygon;
import org.apache.lucene.search.Query;

Polygon zone = new Polygon(
        new double[] {40.68, 40.68, 40.75, 40.75, 40.68},
        new double[] {-74.05, -73.95, -73.95, -74.05, -74.05});

Document d = new Document();
for (Field f : LatLonShape.createIndexableFields("area", zone)) {   // Field[]
    d.add(f);
}
writer.addDocument(d);

// query: which indexed shapes intersect this polygon?
Query q = LatLonShape.newPolygonQuery("area", ShapeField.QueryRelation.INTERSECTS, zone);
// also: newBoxQuery, newLineQuery, newDistanceQuery (against a Circle),
//       newGeometryQuery (mix of shapes), with WITHIN / CONTAINS / DISJOINT relations
----

The relations are easiest to understand on an example. Three delivery areas are indexed: `downtown` (a
small box), `uptown` (a box partly east of it) and `metro` (a large box around both). Two probe polygons
are queried against them:

[source,text]
----
narrow probe (inside downtown, overlapping uptown):
  INTERSECTS: [downtown, metro, uptown]
  CONTAINS  : [downtown, metro]
  WITHIN    : []
  DISJOINT  : []
wide probe (covers downtown and uptown, inside metro):
  INTERSECTS: [downtown, metro, uptown]
  WITHIN    : [downtown, uptown]
  CONTAINS  : [metro]
  DISJOINT  : []
----

The relation describes the *indexed* shape relative to the *query* shape: `CONTAINS` returns the
indexed shapes that contain the probe (the areas a point of the probe is delivered by), `WITHIN`
returns the indexed shapes inside the probe, `INTERSECTS` any overlap and `DISJOINT` the shapes with
no overlap at all.

`ShapeField.QueryRelation` is the relation vocabulary (`INTERSECTS`, `WITHIN`, `CONTAINS`,
`DISJOINT`); it is Lucene's equivalent of the Elasticsearch `geo_shape` relation parameter described
in xref:database/elasticsearch/geospatial.adoc[Elasticsearch geospatial]. See the
https://lucene.apache.org/core/10_0_0/core/org/apache/lucene/document/XYShape.html[XYShape Javadoc]
for its planar variant. A polygon is cut into triangles when indexed, so a very detailed polygon
produces many indexed points: simplify coastlines and administrative boundaries before indexing, and
store the exact geometry elsewhere if the application needs it back.

== Prefix-tree strategies in lucene-spatial-extras

`lucene-spatial-extras` predates the BKD shape fields and is still the route when you need
https://github.com/locationtech/spatial4j[spatial4j] shapes, custom grids, or the serialized
doc-values approach. A `SpatialStrategy` maps a spatial4j `Shape` to indexable fields and turns a
`SpatialArgs` (operation + query shape) into a `Query`.

[cols="1,3",options="header"]
|===
| Strategy | What it does

| `RecursivePrefixTreeStrategy` | Indexes a shape as grid cells at increasing precision over a `SpatialPrefixTree` (`GeohashPrefixTree`, `QuadPrefixTree`, `S2PrefixTree`). Supports the `Intersects`, `IsWithin` and `Contains` operations and heatmap faceting. The usual choice.
| `TermQueryPrefixTreeStrategy` | The simpler `PrefixTreeStrategy` base behaviour -- grid terms, `INTERSECTS` only, no recursive pruning.
| `SerializedDVStrategy` | Stores the full geometry in a `BinaryDocValues` field and evaluates the predicate exactly per document. Precise but slow; usually paired with a coarse prefix-tree strategy in a `CompositeSpatialStrategy` (fast grid filter, exact confirm).
| `PointVectorStrategy` | Two numeric doc-values fields for a plain point -- distance sort / bbox only.
|===

[source,java]
----
// https://lucene.apache.org/core/10_0_0/spatial-extras/org/apache/lucene/spatial/prefix/RecursivePrefixTreeStrategy.html
import org.apache.lucene.spatial.prefix.RecursivePrefixTreeStrategy;
import org.apache.lucene.spatial.prefix.tree.GeohashPrefixTree;
import org.apache.lucene.spatial.prefix.tree.SpatialPrefixTree;
import org.apache.lucene.spatial.query.SpatialArgs;
import org.apache.lucene.spatial.query.SpatialOperation;
import org.apache.lucene.document.Field;
import org.locationtech.spatial4j.context.SpatialContext;
import org.locationtech.spatial4j.shape.Shape;

SpatialContext ctx = SpatialContext.GEO;
SpatialPrefixTree grid = new GeohashPrefixTree(ctx, 11);          // ~ 1 m leaf cells
RecursivePrefixTreeStrategy strategy =
        new RecursivePrefixTreeStrategy(grid, "zone");

// index: a rectangle and a circle (radius in degrees)
Shape rect   = ctx.getShapeFactory().rect(-74.05, -73.95, 40.68, 40.75);   // minX, maxX, minY, maxY
Shape circle = ctx.getShapeFactory().circle(-73.9, 40.8, 0.05);
Document d = new Document();
for (Field f : strategy.createIndexableFields(rect)) {   // Field[]
    d.add(f);
}
writer.addDocument(d);

// query
Shape queryShape = ctx.getShapeFactory().rect(-74.1, -73.9, 40.6, 40.8);
Query q = strategy.makeQuery(new SpatialArgs(SpatialOperation.Intersects, queryShape));
----

Against one indexed rectangle and one circle, with the query rectangle above:

[source,text]
----
RPT Intersects: [circle, rect]
RPT Within    : [rect]
RPT Contains  : []
RPT Disjoint  : UnsupportedSpatialOperation Disjoint
----

Two limits are visible. The recursive prefix-tree strategy answers `Intersects`, `IsWithin` and
`Contains` but *not* `IsDisjointTo`: a disjoint query throws `UnsupportedSpatialOperation`, so express
"outside this area" as a `MUST_NOT` clause around the intersects query instead. And the plain
`SpatialContext.GEO` knows rectangles, circles and points only. Asking it for a polygon fails when the
shape is built:

[source,text]
----
spatial4j polygon without JTS: UnsupportedOperationException: Unsupported shape of this SpatialContext. Try JTS or Geo3D.
----

Polygons need a context backed by JTS (`org.locationtech.jts`, which also adds validity repair and
polygons with holes) or Geo3D. The https://lucene.apache.org/core/10_0_0/spatial-extras/index.html[lucene-spatial-extras module
overview] lists every strategy and prefix-tree implementation. Solr's
`SpatialRecursivePrefixTreeFieldType` in xref:database/solr/spatial-search.adoc[Solr spatial search]
is this strategy wrapped as a field type.

== geo3d -- geometry on the ellipsoid (lucene-spatial3d)

Grid and projected-plane approaches distort near the poles and across the date line.
`lucene-spatial3d` (the `geo3d` code) represents every point as an `(x, y, z)` position on a
`PlanetModel` (`WGS84` or `SPHERE`), so great-circle distance, polygons that enclose a pole, and
paths are computed without a projection.

[source,java]
----
// https://lucene.apache.org/core/10_0_0/spatial3d/org/apache/lucene/spatial3d/Geo3DPoint.html
import org.apache.lucene.spatial3d.Geo3DPoint;
import org.apache.lucene.spatial3d.geom.GeoPolygonFactory;
import org.apache.lucene.spatial3d.geom.GeoPoint;
import org.apache.lucene.spatial3d.geom.GeoPolygon;
import org.apache.lucene.spatial3d.geom.PlanetModel;
import java.util.List;

Document d = new Document();
d.add(new Geo3DPoint("location", 40.7128, -74.0060));             // degrees in, x/y/z stored (WGS84)
writer.addDocument(d);

Query radius = Geo3DPoint.newDistanceQuery(
        "location", PlanetModel.WGS84, 40.7128, -74.0060, 5_000.0);   // degrees in, metres

// a polygon covering the North Pole -- no special-casing needed.
// GeoPoint takes RADIANS, the Geo3DPoint field and query factories take DEGREES.
GeoPolygon capPoly = GeoPolygonFactory.makeGeoPolygon(PlanetModel.WGS84, List.of(
        new GeoPoint(PlanetModel.WGS84, Math.toRadians(85), Math.toRadians(0)),
        new GeoPoint(PlanetModel.WGS84, Math.toRadians(85), Math.toRadians(120)),
        new GeoPoint(PlanetModel.WGS84, Math.toRadians(85), Math.toRadians(-120))));
Query polar = Geo3DPoint.newShapeQuery("location", capPoly);
----

The radius query returns the same three shops as the `LatLonPoint` radius query
(`[Battery Books, Jersey Shelf, Village Pages]`), and the polar polygon is built as a composite polygon
without complaint. The unit mismatch is the common trap: the field and the `newBoxQuery` /
`newDistanceQuery` factories take degrees, while the `GeoPoint` constructor of the `geom` package takes
radians; passing degrees to one and radians to the other gives a query that silently matches nothing.

`Geo3DPoint` also offers `newBoxQuery` and `newPathQuery` (a corridor of fixed width along a
polyline). The tradeoff is index size and per-query CPU: three encoded dimensions instead of two.
The https://lucene.apache.org/core/10_0_0/spatial3d/index.html[lucene-spatial3d module overview]
documents the `GeoShape` hierarchy and every planet model.

== Parsing WKT and GeoJSON

Geometries usually arrive as text. `SimpleWKTShapeParser` in `lucene-core` parses a
https://en.wikipedia.org/wiki/Well-known_text_representation_of_geometry[Well-Known Text] string into
the `org.apache.lucene.geo` objects the shape fields expect; `Polygon.fromGeoJSON` parses a GeoJSON
`Polygon` / `MultiPolygon` document.

[source,java]
----
// https://lucene.apache.org/core/10_0_0/core/org/apache/lucene/geo/SimpleWKTShapeParser.html
import org.apache.lucene.geo.SimpleWKTShapeParser;
import org.apache.lucene.geo.Polygon;
import org.apache.lucene.document.LatLonShape;

Object shape = SimpleWKTShapeParser.parse(
        "POLYGON((-74.05 40.68, -73.95 40.68, -73.95 40.75, -74.05 40.75, -74.05 40.68))");
// returns Polygon / Line / double[] point / Polygon[] / Line[] depending on the WKT type

if (shape instanceof Polygon p) {
    for (var f : LatLonShape.createIndexableFields("area", p)) {
        d.add(f);
    }
}

// GeoJSON -> Polygon[]  (an outer ring plus any holes / multipolygon parts)
Polygon[] fromJson = Polygon.fromGeoJSON(geoJsonString);
----

[source,text]
----
WKT parsed to Polygon lat0=40.68 lon0=-74.05
WKT point -> double[][-74.006, 40.7128]
GeoJSON -> 1 polygon(s), vertices=5
----

WKT and GeoJSON both write `x y`, that is *longitude then latitude*; the parser converts, and the
`Polygon` it returns stores latitudes and longitudes in separate arrays. A parsed `POINT` is a
`double[]` holding `[lon, lat]` -- the reverse of the argument order of `LatLonPoint`, which is the usual
source of mirrored coordinates. `SimpleWKTShapeParser.parseExpectedType` restricts the accepted type
when you know it in advance. For a document store that speaks GeoJSON natively rather than as a
parsing step, contrast
xref:database/mongodb/special-indexes-and-search.adoc[MongoDB's 2dsphere indexes].
