Lucene ranks matching documents with a `Similarity`: a pluggable model that turns per-term corpus
statistics (term frequency, document frequency, field length) into a score. The default is
`BM25Similarity`; several probabilistic and language-model alternatives ship in
`org.apache.lucene.search.similarities`, and any of them can be set globally or per field.

== BM25Similarity, the default

`BM25Similarity` has been the default since Lucene 6 -- earlier lines used the TF/IDF vector-space
`DefaultSimilarity` (now `ClassicSimilarity`, kept only for compatibility). BM25 scores a term with
a saturating term-frequency component and a length normalisation:

[source,text]
----
score(term, doc) = boost * idf * tf

tf  = freq / (freq + k1 * (1 - b + b * fieldLen / avgFieldLen))

idf = log(1 + (N - df + 0.5) / (df + 0.5))
----

Older descriptions of BM25 (and the original paper) multiply the numerator by `pass:c[(k1 + 1)]`. Lucene dropped that
constant factor in 8.0 because it scales every score of a query by the same amount and so cannot change
the ranking; do not look for it in an `Explanation` or add it when reproducing scores by hand.

* `k1` (default `1.2`) -- how fast term frequency saturates. Higher `k1` keeps rewarding repeated
  terms for longer; `k1 = 0` ignores term frequency entirely.
* `b` (default `0.75`) -- how strongly a long field is penalised. `b = 0` disables length
  normalisation; `b = 1` applies it fully.

[source,java]
----
// https://lucene.apache.org/core/10_0_0/core/org/apache/lucene/search/similarities/BM25Similarity.html
import org.apache.lucene.search.similarities.BM25Similarity;

BM25Similarity sim = new BM25Similarity(1.5f, 0.6f); // custom k1, b
----

=== A worked BM25 example on five short documents

To check the formula, a one-field index held five documents (the field `body`), and the query was
`body:lucene`. Documents: `lucene` (1 token), `lucene in action` (3), `lucene lucene lucene in a very long title about
search` (10 tokens, `lucene` three times), `search engines` (2, no match) and a 17-token sentence containing `lucene`
three times. The collection has N = 5 documents, `lucene` occurs in df = 4 of them, and the average field length is 6.6.
The default `BM25Similarity(1.2, 0.75)` ranked them, and `searcher.explain` printed the derivation for the second one:

[source,text]
----
0.16832462 = weight(body:lucene in 1) [BM25Similarity], result of:
  0.16832462 = score(freq=1.0), computed as boost * idf * tf from:
    0.2876821 = idf, computed as log(1 + (N - n + 0.5) / (n + 0.5)) from:
      4 = n, number of documents containing term
      5 = N, total number of documents with field
    0.5851064 = tf, computed as freq / (freq + k1 * (1 - b + b * dl / avgdl)) from:
      1.0 = freq, occurrences of term within document
      1.2 = k1, term saturation parameter
      0.75 = b, length normalization parameter
      3.0 = dl, length of field
      6.6 = avgdl, average length of field
----

Plugging the numbers in by hand reproduces the result exactly: `pass:c[idf = ln(1 + 1.5/4.5) = 0.28768]`, `tf = 1 / (1 + 1.2 *
(0.25 + 0.75 * 3 / 6.6)) = 0.58511`, and `+0.28768 * 0.58511 = 0.16832+`. The five scores follow the same arithmetic:

[cols="3,1,1,1,1",options="header"]
|===
| Document | `freq` | length | score | rank

| `lucene` | 1 | 1 | 0.2003 | 1
| `lucene lucene lucene in a very long title about search` | 3 | 10 | 0.1851 | 2
| `lucene in action` | 1 | 3 | 0.1683 | 3
| 17-token sentence, `lucene` three times | 3 | 17 | 0.1536 | 4
| `search engines` | 0 | 2 | no match | --
|===

The short single-word document wins (`tf` = 1 / (1 + 1.2 * 0.364) = 0.696, the highest of the four). Three
occurrences in ten tokens (`tf` 0.643) beat one occurrence in three tokens (`tf` 0.585) because `tf` saturates only
slowly at `k1=1.2` while the length penalty is still mild; and three occurrences in a 17-token field rank last
because the length penalty has taken over.

[mermaid]
....
flowchart TD
    Q["Query: body:lucene"] --> W["Weight: collects N, df, avgdl once per searcher"]
    W --> S1["per matching doc: freq, norm (decoded length)"]
    S1 --> TF["tf = freq / (freq + k1 * (1 - b + b * dl / avgdl))"]
    W --> IDF["idf = log(1 + (N - df + 0.5) / (df + 0.5))"]
    TF --> M["score = boost * idf * tf"]
    IDF --> M
    M --> H["priority queue of top N hits"]
....

=== What k1 and b do, measured

The same five documents were scored with different parameters (document ids in score order, scores rounded to
three decimals):

[cols="2,5",options="header"]
|===
| Parameters | Ranking

| `k1=1.2, b=0.75` (default) | doc0 0.200, doc2 0.185, doc1 0.168, doc4 0.154
| `k1=0` | all four 0.288 -- term frequency and length are ignored, only idf remains
| `k1=3` | doc0 0.138, doc2 0.121, doc1 0.104, doc4 0.090 -- same order, lower scores
| `b=0` | doc2 0.205, doc4 0.205, doc0 0.131, doc1 0.131 -- length ignored: the two three-occurrence docs now lead
| `b=1` | doc0 0.243, doc1 0.186, doc2 0.179, doc4 0.142 -- full length normalization: the shortest docs win
|===

`b=0` is the interesting row: with no length normalization, the long 17-token document ties the 10-token one, and
both beat the short documents because they simply contain more occurrences. That is the right setting for fields
where length carries no meaning, and the wrong one for titles.

=== Field-length norms and SmallFloat

`fieldLen` is not read exactly at query time -- at index time each field's length (roughly, its
token count) is quantised to a single byte by `SmallFloat.intToByte4` and written as the field
*norm*. `BM25Similarity.computeNorm` decodes that byte back to an approximate length. This is why
turning norms off (`FieldType.setOmitNorms(true)`, implicit on `StringField`) removes length
normalisation for that field, and why changing `b` does not require reindexing but changing whether
norms are stored does. See
https://lucene.apache.org/core/10_0_0/core/org/apache/lucene/util/SmallFloat.html[SmallFloat].

The quantisation is lossy for long fields. Round-tripping lengths through `SmallFloat.intToByte4` and back gives
`+1 -> 1+`, `+10 -> 10+`, `+24 -> 24+`, `+40 -> 40+`, but `+100 -> 96+` and `+1000 -> 984+`: exact for short fields,
approximate beyond about 40 tokens, which is irrelevant to ranking.

Norms can be removed per field. In a three-document test, one document held `lucene` once in a single token, one
held `lucene` twice in a 14-token field, and one did not match. With norms enabled the short document won (`0.322`
against `0.208`); with `setOmitNorms(true)` the order *reversed* (`0.382` for the long document, `0.322` for the short
one), because without length normalization the second occurrence counts and the extra words are free.

== Other Similarity implementations

[cols="1,3",options="header"]
|===
| Class | Model

| `BooleanSimilarity` | score is the query boost only -- no tf, idf, or norms (a pure filter-style match)
| `ClassicSimilarity` | the legacy TF/IDF vector-space model (pre-6 default), for compatibility
| `DFRSimilarity` | Divergence From Randomness -- pick a `BasicModel`, `AfterEffect`, `Normalization`
| `IBSimilarity` | Information-Based model -- a `Distribution`, `Lambda`, `Normalization`
| `LMDirichletSimilarity` | language model with Dirichlet smoothing (parameter `mu`, default `2000`)
| `LMJelinekMercerSimilarity` | language model with Jelinek-Mercer smoothing (parameter `lambda`)
|===

[source,java]
----
// https://lucene.apache.org/core/10_0_0/core/org/apache/lucene/search/similarities/package-summary.html
import org.apache.lucene.search.similarities.*;

Similarity dfr = new DFRSimilarity(
        new BasicModelG(), new AfterEffectB(), new NormalizationH2());
Similarity lmd = new LMDirichletSimilarity(2000f);
----

All seven models were run on the same five documents and query. Apart from `BooleanSimilarity`, every model puts the one-word document first and the
17-token document last, but the spread differs a great deal, and the models disagree about the middle two:

[cols="2,1,1,1,1",options="header"]
|===
| Similarity | doc0 (1 token) | doc1 (3 tokens) | doc2 (10 tokens) | doc4 (17 tokens)

| `BM25Similarity` | 0.200 | 0.168 | 0.185 | 0.154
| `ClassicSimilarity` | 1.182 | 0.683 | 0.648 | 0.497
| `BooleanSimilarity` | 1.000 | 1.000 | 1.000 | 1.000
| `LMDirichletSimilarity` (`mu=2000`) | 0.001 | 0.000 | 0.001 | 0.000
| `LMJelinekMercerSimilarity` (`lambda=0.7`) | 0.963 | 0.432 | 0.396 | 0.251
| `DFRSimilarity` (G, B, H2) | 2.383 | 2.231 | 2.308 | 2.180
| `IBSimilarity` (LL, DF, H2) | 1.507 | 1.103 | 1.290 | 0.995
|===

`BooleanSimilarity` makes the query a pure match with score equal to the boost, which is why it suits a tags
field. The Dirichlet model with its default `mu=2000` is tuned for documents of hundreds of words, and on
five-token documents it produces scores near zero: always verify a model's parameters on your own field lengths
before switching, and compare rankings, not raw scores, across models.

=== PerFieldSimilarityWrapper

`PerFieldSimilarityWrapper` routes each field to its own `Similarity` -- e.g. BM25 for `body`, a
language model for `title`, `BooleanSimilarity` for a `tags` field that should not influence
ranking.

[source,java]
----
// https://lucene.apache.org/core/10_0_0/core/org/apache/lucene/search/similarities/PerFieldSimilarityWrapper.html
import org.apache.lucene.search.similarities.*;

Similarity perField = new PerFieldSimilarityWrapper() {
    final Similarity bm25 = new BM25Similarity();
    final Similarity lm    = new LMDirichletSimilarity();
    @Override
    public Similarity get(String field) {
        return field.equals("title") ? lm : bm25;
    }
};
----

== Setting a Similarity: indexing vs. querying

A `Similarity` is consulted in two places, and both should normally use the same implementation:

* `+IndexWriterConfig.setSimilarity(...)+` -- used at *index* time to compute and store field norms.
  Changing this affects only segments written afterwards.
* `+IndexSearcher.setSimilarity(...)+` -- used at *query* time to score matches. Changing this takes
  effect immediately, with no reindex, for anything it can compute from stored statistics (so `k1`,
  `b`, `mu`, and switching between models all work live; enabling norms on a field that omitted
  them does not).

[source,java]
----
// indexing
IndexWriterConfig iwc = new IndexWriterConfig(analyzer);
iwc.setSimilarity(new BM25Similarity(1.5f, 0.6f));

// querying
IndexSearcher searcher = new IndexSearcher(reader);
searcher.setSimilarity(new BM25Similarity(1.5f, 0.6f));
----

== The Explanation API

`IndexSearcher.explain(Query, int docId)` returns an `Explanation` tree: the final score at the
root and every additive/multiplicative contribution beneath it, each with a human-readable
description. It is the tool for answering "why did this document score what it did" and for
verifying a custom `Similarity`.

[source,java]
----
// https://lucene.apache.org/core/10_0_0/core/org/apache/lucene/search/IndexSearcher.html#explain(org.apache.lucene.search.Query,int)
import org.apache.lucene.search.Explanation;

TopDocs hits = searcher.search(query, 10);
int docId = hits.scoreDocs[0].doc;
Explanation e = searcher.explain(query, docId);
System.out.println(e);          // full nested breakdown
System.out.println(e.getValue()); // the score as a Number
----

A BM25 explanation bottoms out in the term statistics below; the diagram shows how they combine:

[mermaid]
....
flowchart LR
  tf["tf: term occurrences in this field of this doc"] --> sat["tf saturation: freq / (freq + k1 x length factor)"]
  k1["k1 parameter"] --> sat
  b["b parameter"] --> sat
  fl["fieldLen: decoded from the stored norm byte"] --> sat
  afl["avgFieldLen: mean over the collection"] --> sat
  df["df: docs containing the term"] --> idf["idf component"]
  n["N: total docs in the field"] --> idf
  sat --> score["BM25 score = boost x idf x tf-saturation"]
  idf --> score
....
