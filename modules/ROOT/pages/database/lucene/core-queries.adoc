= The core Query classes
:description: The Lucene 10.x org.apache.lucene.search Query hierarchy -- term, boolean, phrase, multi-term, range, wrapper and set queries -- with construction examples and notes on QueryVisitor and rewriting.
:keywords: apache lucene, query, termquery, booleanquery, occur, filter, phrasequery, multiphrasequery, prefixquery, wildcardquery, regexpquery, fuzzyquery, termrangequery, matchalldocsquery, constantscorequery, boostquery, disjunctionmaxquery, terminsetquery, queryvisitor, query rewrite

include::partial$ai-disclaimer.adoc[]

Every search in Lucene executes a `Query`. The xref:database/lucene/query-parsers.adoc[query parsers]
just assemble these objects; building them directly is the norm for anything an application generates.
This page is a tour of the concrete `Query` subclasses in
https://lucene.apache.org/core/10_0_0/core/org/apache/lucene/search/package-summary.html[the
`org.apache.lucene.search` package], grouped by what they do.

== TermQuery -- the atom

Matches documents containing one exact term in one field. The term value is *not* analyzed, so it
must already be in indexed form (lower-cased, folded, stemmed -- whatever the field's analyzer
produced).

[source,java]
----
// https://lucene.apache.org/core/10_0_0/core/org/apache/lucene/search/TermQuery.html
Query q = new TermQuery(new Term("status", "published"));
----

On the catalog `new TermQuery(new Term("title", "lucene"))` finds `Lucene in Action` (score 0.85), while
`new Term("title", "Lucene")` finds nothing: the index holds the lowercased term, and a `TermQuery` is never
analyzed. A `KeywordField` tag behaves the other way round: `tag:java` matches the three Java books (0.53 each),
exact and case-sensitive.

== BooleanQuery.Builder -- combining clauses

Clauses are added with a `BooleanClause.Occur`:

[cols="1,3",options="header"]
|===
| Occur | Meaning

| `MUST` | Must match; contributes to the score.
| `SHOULD` | Optional; contributes to the score. If a query has only `SHOULD` clauses, at least one must match (unless overridden).
| `FILTER` | Must match; does *not* contribute to the score (cacheable). The modern name -- there is no `Occur.Filter`.
| `MUST_NOT` | Must not match; no score effect.
|===

`setMinimumNumberShouldMatch(n)` requires at least `n` of the `SHOULD` clauses when `MUST`/`FILTER`
clauses are also present. A `BooleanQuery` may hold at most `IndexSearcher.getMaxClauseCount()`
clauses -- 1024 by default; adding the 1025th clause throws `IndexSearcher.TooManyClauses: maxClauseCount is set to 1024`
at `build()` time.

[source,java]
----
// https://lucene.apache.org/core/10_0_0/core/org/apache/lucene/search/BooleanQuery.html
Query bq = new BooleanQuery.Builder()
    .add(new TermQuery(new Term("body", "lucene")), BooleanClause.Occur.MUST)
    .add(new TermQuery(new Term("body", "search")), BooleanClause.Occur.SHOULD)
    .add(new TermQuery(new Term("body", "server")), BooleanClause.Occur.SHOULD)
    .add(new TermQuery(new Term("lang", "en")),     BooleanClause.Occur.FILTER)
    .add(new TermQuery(new Term("status", "draft")), BooleanClause.Occur.MUST_NOT)
    .setMinimumNumberShouldMatch(1)
    .build();

IndexSearcher.setMaxClauseCount(4096);   // static; raise with care, it guards memory
----

=== What each Occur does to the result

The catalog makes the four `Occur` values and the score contribution concrete. Each query below ran against the
eight books; the number after each title is the score:

[cols="2,3,3",options="header"]
|===
| Query | Parsed form | Result

| `MUST` `description:lucene`, `SHOULD` `solr`, `SHOULD` `elasticsearch`, `FILTER` `year:[2014 TO 2016]`, `MUST_NOT` `tag:theory` | `pass:c[+description:lucene description:solr description:elasticsearch #year:[2014 TO 2016\] -tag:theory]` | `Solr in Action` (1.25), `Elasticsearch: The Definitive Guide` (0.40)
| same, but the range as `MUST` | `pass:c[+description:lucene +year:[2014 TO 2016\]]` | `Solr in Action` (1.43), `Elasticsearch: The Definitive Guide` (1.40)
| `SHOULD` `tag:go`, `SHOULD` `tag:solr` | `tag:go tag:solr` | two hits, each 1.01: at least one must match
| three `SHOULD` tags, `minimumNumberShouldMatch(2)` | `+(tag:java tag:best-practices tag:concurrency)~2+` | `Effective Java` (1.54), `Java Concurrency in Practice` (1.54)
| only `MUST_NOT` `tag:java` | `-tag:java` | no hits at all
| `MUST` `MatchAllDocsQuery`, `MUST_NOT` `tag:java` | `pass:c[+*:* -tag:java]` | the five non-Java books, each 1.00
|===

The first two rows differ only in `FILTER` versus `MUST` for the range, and the scores show it: with `FILTER` (the
`#` in the printed form) the range contributed nothing, so `Elasticsearch: The Definitive Guide` scored only the
small SHOULD part (0.40); with `MUST` the range's own score was added (1.40). Use `FILTER` for any yes-or-no
condition. A query consisting only of `MUST_NOT` clauses matches nothing, because there is nothing to exclude
*from*: pair it with a `MatchAllDocsQuery` as in the last row.

[mermaid]
....
flowchart TD
    Q["BooleanQuery"] --> M["MUST clauses: all must match, scores summed"]
    Q --> S["SHOULD clauses: optional unless there is no MUST or FILTER, scores summed"]
    Q --> F["FILTER clauses: all must match, no score, cacheable"]
    Q --> N["MUST_NOT clauses: any match excludes the doc"]
    M --> R["candidate docs = intersection of MUST and FILTER"]
    F --> R
    R --> N2["minus MUST_NOT"]
    N --> N2
    N2 --> SC["score = sum of MUST and matching SHOULD scores"]
    S --> SC
....

== Phrase queries

`PhraseQuery.Builder` matches an ordered sequence of terms within `slop` position edits (`slop=0` is
exact adjacency). Per-term position offsets support gaps. `MultiPhraseQuery` allows a *set* of
alternative terms at one position -- the query-time equivalent of a synonym at that slot.

[source,java]
----
// https://lucene.apache.org/core/10_0_0/core/org/apache/lucene/search/PhraseQuery.html
Query pq = new PhraseQuery.Builder()
    .add(new Term("title", "quick"))
    .add(new Term("title", "fox"), 2)     // "quick ? fox"
    .setSlop(1)
    .build();

// https://lucene.apache.org/core/10_0_0/core/org/apache/lucene/search/MultiPhraseQuery.html
Query mpq = new MultiPhraseQuery.Builder()
    .add(new Term("title", "quick"))
    .add(new Term[] { new Term("title", "fox"), new Term("title", "hound") })
    .build();
----

For richer positional logic see xref:database/lucene/interval-and-span-queries.adoc[Interval & span queries].

On the catalog: the phrase `"lucene in action"` on `title` matched `Lucene in Action` (score 1.91), and
`description:"search applications"` matched it (1.40) because the two words are adjacent there. With slop, the phrase
`"search lucene"` with slop 2 matched the same book at a lower score (0.49): each position moved lowers it. The
`MultiPhraseQuery` `solr in (action practice)` matched `Solr in Action` (2.77), the alternatives occupying
one position. Phrase queries need positions: a phrase on a `DOCS`-only field throws `IllegalStateException`, as shown
on xref:database/lucene/documents-and-fields.adoc[Documents & fields].

== Multi-term queries

All four enumerate the term dictionary of the field when they run. `PrefixQuery`, `WildcardQuery` and
`RegexpQuery` rewrite to a constant-score query that collects the matching documents into a bit set, so they do
*not* hit the clause-count ceiling: a prefix query over 3000 distinct terms matched all 3000 documents without
error. `FuzzyQuery` is different: it rewrites to a `BooleanQuery` of the best matching terms and keeps at most
`maxExpansions` of them (50 by default).

[source,java]
----
// https://lucene.apache.org/core/10_0_0/core/org/apache/lucene/search/PrefixQuery.html
Query prefix = new PrefixQuery(new Term("name", "lucen"));

// https://lucene.apache.org/core/10_0_0/core/org/apache/lucene/search/WildcardQuery.html
Query wild = new WildcardQuery(new Term("name", "l?cen*"));   // ? one char, * any run

// https://lucene.apache.org/core/10_0_0/core/org/apache/lucene/search/RegexpQuery.html
Query re = new RegexpQuery(new Term("name", "luc[e]+ne"));    // Lucene regex flavour, anchored

// https://lucene.apache.org/core/10_0_0/core/org/apache/lucene/search/FuzzyQuery.html
Query fuzzy = new FuzzyQuery(new Term("name", "lucene"), 2, 1);
// maxEdits 0..2 (Levenshtein automaton), prefixLength 1 exact leading char to bound expansion
----

Results of the multi-term queries on the catalog titles:

[cols="2,3,3",options="header"]
|===
| Query | Matches | Notes

| `PrefixQuery(title, "ja")` | the three Java books | constant score 1.00
| `+WildcardQuery(title, "l?cen*")+` | `Lucene in Action` | `?` is exactly one character
| `+WildcardQuery(title, "*ava")+` | the three Java books | a leading wildcard is allowed through the API; only the classic *parser* forbids it
| `FuzzyQuery(title, "lucne", 2, 1)` | `Lucene in Action` (0.68) | within 2 edits, first character fixed
|===

A `RegexpQuery` with the pattern `pass:c[so[l\]+r|luc.*]` over `title` matched `Lucene in Action` and `Solr in Action`: the
pattern has to match the *whole* indexed term, there is no implicit substring match.

Rewriting makes the difference visible: `+searcher.rewrite(new PrefixQuery(...))+` returned a
`MultiTermQueryConstantScoreBlendedWrapper` (the constant-score bit-set form), while rewriting the fuzzy query
over a field with 3000 terms produced a `BooleanQuery` of exactly 50 clauses, the default `maxExpansions`.

== TermRangeQuery

A byte-ordered range over a string/`KeywordField` term dictionary. It does *not* understand numbers
or dates -- use xref:database/lucene/points-and-range-queries.adoc[point range queries]
(`IntPoint.newRangeQuery`, `LongPoint.newRangeQuery`, ...) for those.

[source,java]
----
// https://lucene.apache.org/core/10_0_0/core/org/apache/lucene/search/TermRangeQuery.html
Query range = TermRangeQuery.newStringRange("city", "Amsterdam", "Berlin", true, false);
// lower inclusive, upper exclusive; null bound = open-ended
----

Two gotchas, both observed. A `TermRangeQuery` over `year` (an `IntField`, which writes points and no terms)
matched *zero* documents, although the printed query `year:[2014 TO 2016]` looks right: there are simply no terms to
range over. And string ranges compare bytes: `TermRangeQuery.newStringRange("title_exact", "E", "J", true, false)`
matched the four titles that start with `E`, `H` or `I` (`Effective Java`, `+Elasticsearch: ...+`, `Head First Java`,
`+Introduction ...+`), which is alphabetical only for already-uppercase initials.

== Match-all and wrappers

[source,java]
----
// https://lucene.apache.org/core/10_0_0/core/org/apache/lucene/search/MatchAllDocsQuery.html
Query all = new MatchAllDocsQuery();     // every live doc, constant score 1.0

// https://lucene.apache.org/core/10_0_0/core/org/apache/lucene/search/ConstantScoreQuery.html
Query cs = new ConstantScoreQuery(new PrefixQuery(new Term("name", "lucen")));

// https://lucene.apache.org/core/10_0_0/core/org/apache/lucene/search/BoostQuery.html
Query boosted = new BoostQuery(new TermQuery(new Term("title", "lucene")), 3.0f);

// https://lucene.apache.org/core/10_0_0/core/org/apache/lucene/search/DisjunctionMaxQuery.html
Query dm = new DisjunctionMaxQuery(
    List.of(new TermQuery(new Term("title", "lucene")),
            new TermQuery(new Term("body",  "lucene"))),
    0.3f);   // score = max(subscores) + tieBreaker * sum(other subscores)
----

`DisjunctionMaxQuery` is the right tool for "same term, several fields" -- it rewards the single best
field rather than summing, which a `SHOULD` `BooleanQuery` would do.

Scores of the two-field query for `lucene` over `title` and `description` show the difference: as two `SHOULD`
clauses `Lucene in Action` scored 1.28 (title plus description), and as a `DisjunctionMaxQuery` with tie-breaker `0.0`
it scored 0.85 (the better field only). With a tie-breaker of `0.3` it scored 0.98: the best field plus 30 percent
of the other. `BoostQuery(title:java, 3)` printed as `+(title:java)^3.0+` and scored `Effective Java` at 1.55 against 1.35
and 1.20 for the others, reordering nothing but scaling the scores. `ConstantScoreQuery` and `MatchAllDocsQuery`
return exactly 1.00.

== TermInSetQuery

One field, many acceptable exact values -- far cheaper than a `BooleanQuery` of hundreds of
`TermQuery` `SHOULD` clauses, and not bound by the clause-count limit. Constant-scoring.

[source,java]
----
// https://lucene.apache.org/core/10_0_0/core/org/apache/lucene/search/TermInSetQuery.html
Query inSet = new TermInSetQuery("tag",
    List.of(new BytesRef("java"), new BytesRef("search"), new BytesRef("lucene")));
----

== QueryVisitor and rewriting

`Query.visit(QueryVisitor)` walks a query tree without executing it -- the supported way to extract
terms (for highlighting), inspect structure, or transform a query. Override `consumeTerms`,
`getSubVisitor`, and friends.

[source,java]
----
// https://lucene.apache.org/core/10_0_0/core/org/apache/lucene/search/QueryVisitor.html
Set<Term> terms = new HashSet<>();
query.visit(new QueryVisitor() {
    @Override
    public void consumeTerms(Query q, Term... ts) { Collections.addAll(terms, ts); }
});
----

Rewriting -- expanding a `PrefixQuery`/`WildcardQuery`/`FuzzyQuery` against the actual term
dictionary -- now goes through `IndexSearcher`: `query.rewrite(indexSearcher)` in 10.x, where older
code called `query.rewrite(indexReader)`. `IndexSearcher.rewrite` is applied for you before a search;
call it explicitly only when you need the concrete rewritten form.

The visitor above, extended to skip `MUST_NOT` sub-queries (by returning `QueryVisitor.EMPTY_VISITOR` from
`getSubVisitor` when the occur is `MUST_NOT`), collected exactly the terms a highlighter would want from the Boolean
query above: `description:elasticsearch`, `description:lucene`, `description:solr`; the excluded `tag:theory` and
the range clause were not reported. Rewriting also simplifies structure: a `BooleanQuery` with a single `MUST` clause
rewrote to the bare `title:java`.
