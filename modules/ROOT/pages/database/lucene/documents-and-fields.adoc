= Documents, fields & the capability matrix
:description: The Lucene Document as a schema-free ordered list of Field objects, the modern field types and what each one enables, FieldType and IndexOptions, and a capability matrix for picking searchable vs. stored vs. sortable vs. range vs. vector.
:keywords: apache lucene, document, field, textfield, stringfield, keywordfield, storedfield, intpoint, longpoint, intfield, numericdocvaluesfield, sorteddocvaluesfield, sortedsetdocvaluesfield, knnfloatvectorfield, featurefield, latlonpoint, fieldtype, indexoptions, omitnorms

include::partial$ai-disclaimer.adoc[]

A Lucene `Document` has no schema: it is just an ordered `List` of `Field` objects, and two
documents in the same index may carry entirely different fields. What a field lets you *do* --
search it, retrieve it, sort or facet on it, run a range query, do nearest-neighbour -- is decided
entirely by which `Field` subclass you add and how its `FieldType` is configured.

== Document: an ordered list of fields

You build a `Document`, add `Field` instances to it, and hand it to `IndexWriter.addDocument`. A
field name may appear more than once (the values are all indexed). Nothing validates field names or
types across documents -- consistency is your responsibility, or your framework's.

[source,java]
----
// https://lucene.apache.org/core/10_0_0/core/org/apache/lucene/document/Document.html
import org.apache.lucene.document.*;

Document doc = new Document();
doc.add(new StringField("isbn", "9780134685991", Field.Store.YES));
doc.add(new TextField("title", "Effective Java", Field.Store.YES));
doc.add(new TextField("author", "Joshua Bloch", Field.Store.YES));
doc.add(new IntField("year", 2018, Field.Store.YES));          // point + doc values
doc.add(new TextField("tag", "java", Field.Store.NO));
doc.add(new TextField("tag", "best-practices", Field.Store.NO)); // same name, second value
writer.addDocument(doc);
----

Reading an index back with the catalog from xref:database/lucene/getting-started.adoc[Getting Started] shows
what the field classes actually record. After indexing the eight books with the helper `toDoc` (plus a
`+SortedDocValuesField("title_sort", ...)+` and a `+StoredField("cover", ...)+` added for this example), the
`FieldInfos` of the segment read:

[source,text]
----
isbn         index=DOCS                         dv=NONE            points=0
title        index=DOCS_AND_FREQS_AND_POSITIONS dv=NONE            points=0
author       index=DOCS_AND_FREQS_AND_POSITIONS dv=NONE            points=0
description  index=DOCS_AND_FREQS_AND_POSITIONS dv=NONE            points=0
year         index=NONE                         dv=SORTED_NUMERIC  points=1
tag          index=DOCS                         dv=SORTED_SET      points=0
title_sort   index=NONE                         dv=SORTED          points=0
cover        index=NONE                         dv=NONE            points=0
----

Each row is one field and each column is one structure from the segment file table on
xref:database/lucene/architecture-and-data-flow.adoc[Architecture & data flow]: `index=` is the postings
(`.tim`, `.doc`, `.pos`), `dv=` the doc values (`.dvd`), `points=` the BKD tree (`.kdd`). The `isbn` row has
`DOCS` only -- no frequencies, no positions -- because `StringField` indexes one un-analyzed term. `year`
(an `IntField`) is not in the postings at all: it is one point dimension plus sorted-numeric doc values.
`cover` (a `StoredField`) appears with everything `NONE`; it exists only in the stored-fields files.

== The field types

The modern (post-4.x) field classes each switch on a specific capability. Pick the combination that
matches how the field will be queried and read back; add two fields with the same name when you need
two capabilities (e.g. a `TextField` to search and a `SortedDocValuesField` to sort).

[cols="1,3",options="header"]
|===
| Field class | What it enables

| `TextField` | Value is run through the `Analyzer` and indexed as terms -- full-text search, phrase and interval queries. `Field.Store.YES` also keeps the original for retrieval.
| `StringField` | The whole value is indexed as a *single* un-analyzed term -- exact match, prefix, term filters. For ids, codes, enums.
| `KeywordField` | Like `StringField` for search, and *also* adds `SortedSetDocValues` so the same field sorts and facets without a second field. The preferred exact-string field in 10.x.
| `StoredField` | Stored for retrieval only -- never indexed, not searchable. For payload you show but never query.
| `IntPoint` / `LongPoint` / `FloatPoint` / `DoublePoint` | Value indexed into a BKD tree for efficient *range* and exact numeric search. Not stored, not sortable on their own.
| `IntField` / `LongField` / `FloatField` / `DoubleField` | Convenience field that bundles the matching `+*Point+` (range search) with `SortedNumericDocValues` (sort / facet) in one instance; add `Field.Store.YES` to also retrieve it.
| `NumericDocValuesField` | A single columnar `long` per document -- sort, numeric facet ranges, function scoring. Not searchable.
| `SortedDocValuesField` | One columnar `BytesRef` per document (single-valued) -- sort and facet on a string.
| `SortedSetDocValuesField` | Multiple columnar `BytesRef` values per document -- multi-valued string facets.
| `SortedNumericDocValuesField` | Multiple columnar numeric values per document -- multi-valued numeric sort / facet.
| `KnnFloatVectorField` / `KnnByteVectorField` | A dense vector per document, indexed in an HNSW graph for approximate nearest-neighbour search -- xref:database/lucene/knn-vector-search.adoc[kNN vector search].
| `FeatureField` | A named `(feature, value)` pair whose value boosts score cheaply at query time (`FeatureField.newSaturationQuery`, etc.) -- e.g. a pagerank or freshness signal.
| `LatLonPoint` | An encoded latitude/longitude point for geo distance and bounding-box / polygon queries -- xref:database/lucene/spatial-search.adoc[Spatial search]. Pair with `LatLonDocValuesField` to sort by distance.
|===

[source,java]
----
// A field's capability follows from its class -- add several with the same name for several
// capabilities.
// https://lucene.apache.org/core/10_0_0/core/org/apache/lucene/document/package-summary.html
import org.apache.lucene.document.*;

Document d = new Document();

// exact id: searchable + sortable/facetable in one field
d.add(new KeywordField("status", "PUBLISHED", Field.Store.YES));

// numeric: range search AND sort/facet
d.add(new IntField("price_cents", 1299, Field.Store.YES));

// full-text search to match, plus doc values to sort alphabetically
d.add(new TextField("title", "The Go Programming Language", Field.Store.YES));
d.add(new SortedDocValuesField("title_sort", new org.apache.lucene.util.BytesRef("the go programming language")));

// approximate nearest-neighbour
d.add(new KnnFloatVectorField("embedding", new float[] {0.12f, -0.03f, /* ... */ 0.44f}));

// cheap score signal
d.add(new FeatureField("features", "pagerank", 4.2f));

writer.addDocument(d);
----

== FieldType, IndexOptions and term vectors

Every field carries an `IndexableFieldType`. The built-in classes above ship sensible instances, but
a custom `FieldType` lets you dial exactly what goes into the index:

* *`IndexOptions`* -- how much postings detail to store: `DOCS` (which documents), `DOCS_AND_FREQS`
  (+ term frequency), `DOCS_AND_FREQS_AND_POSITIONS` (+ positions, needed for phrase and interval
  queries), `DOCS_AND_FREQS_AND_POSITIONS_AND_OFFSETS` (+ character offsets, used by the postings
  highlighter). `NONE` means the field is not indexed.
* *`setStored(true)`* -- keep the original value for `storedFields()`.
* *`setStoreTermVectors(true)`* (with `+...Positions+` / `+...Offsets+`) -- a per-document mini term list,
  used by some highlighters and "more like this".
* *`setOmitNorms(true)`* -- drop the per-document length norm; saves a byte per doc per field but
  disables length normalization in scoring. `StringField` omits norms by default.

[source,java]
----
// https://lucene.apache.org/core/10_0_0/core/org/apache/lucene/index/IndexableFieldType.html
import org.apache.lucene.document.*;
import org.apache.lucene.index.IndexOptions;

FieldType bodyType = new FieldType();
bodyType.setIndexOptions(IndexOptions.DOCS_AND_FREQS_AND_POSITIONS_AND_OFFSETS);
bodyType.setStored(true);
bodyType.setStoreTermVectors(true);
bodyType.setStoreTermVectorPositions(true);
bodyType.setStoreTermVectorOffsets(true);
bodyType.setOmitNorms(false);
bodyType.freeze();

Document d = new Document();
d.add(new Field("body", "full article text ...", bodyType));   // generic Field + custom type
writer.addDocument(d);
----

Before Lucene 4, indexing was configured with the `Field.Store` and `Field.Index` enums (and numbers
went through a single `NumericField`); today the capability is the `Field` subclass plus an optional
custom `FieldType`, and only `Field.Store` survives.

=== Capability matrix

Read down the column for the capability you need, then pick a field (or a pair) whose row has it.

[cols="2,1,1,1,1,1",options="header"]
|===
| Field | Searchable (term / match) | Range | Stored (retrieve) | Sort / facet / function | Vector

| `TextField` | analyzed | -- | opt. | -- | --
| `StringField` | exact term | -- | opt. | -- | --
| `KeywordField` | exact term | -- | opt. | yes (SortedSet) | --
| `StoredField` | -- | -- | yes | -- | --
| `IntPoint` / `LongPoint` / `DoublePoint` | exact | yes (BKD) | -- | -- | --
| `IntField` / `LongField` / `DoubleField` | exact | yes (BKD) | opt. | yes (SortedNumeric) | --
| `NumericDocValuesField` | -- | -- | -- | yes (single numeric) | --
| `SortedDocValuesField` | -- | -- | -- | yes (single string) | --
| `SortedSetDocValuesField` | -- | -- | -- | yes (multi string) | --
| `SortedNumericDocValuesField` | -- | -- | -- | yes (multi numeric) | --
| `KnnFloatVectorField` / `KnnByteVectorField` | -- | -- | -- | -- | yes (HNSW)
| `FeatureField` | boost only | -- | -- | score signal | --
| `LatLonPoint` | geo predicate | geo box / distance | -- | with `LatLonDocValuesField` | --
|===

The recurring pattern: a `+*Point+`/`+*Field+` for range, a `+*DocValuesField+` for sort and facet, and
`Field.Store.YES` (or a `StoredField`) for retrieval -- often all three under one name.
xref:database/lucene/points-and-range-queries.adoc[Points & range queries],
xref:database/lucene/filtering-and-faceting.adoc[Filtering & faceting], and
xref:database/lucene/retrieving-results.adoc[Retrieving results] each use one leg of it.

=== Picking a field: a decision flow

[mermaid]
....
flowchart TD
    A["A value to put in the index"] --> B{"Free text that users search by words?"}
    B -- yes --> TF["TextField (Analyzer applies)"]
    B -- no --> C{"Number or date?"}
    C -- yes --> IF["IntField / LongField / DoubleField / FloatField<br/>(range + sort + facet)"]
    C -- no --> D{"Exact string: id, code, enum, tag?"}
    D -- "and sort or facet on it" --> KF["KeywordField"]
    D -- "search only" --> SF["StringField"]
    D -- no --> E{"Dense vector or geo point?"}
    E -- vector --> VF["KnnFloatVectorField"]
    E -- geo --> LL["LatLonPoint + LatLonDocValuesField"]
    E -- "display only" --> ST["StoredField"]
....

The flow picks the *search* behaviour; the display and sort behaviour are separate decisions layered on the same
field name. `Field.Store.YES` (or an extra `StoredField`) adds the display copy, and a `SortedDocValuesField` or
`NumericDocValuesField` adds a sort copy.

=== Sorting: each field type needs its own SortField

A sort reads doc values, and the *kind* of doc values decides which `SortField` class works. Mixing them up is the
most common field-related runtime failure. Sorting the catalog by `year`, which is an `IntField` (sorted-numeric
doc values), with a plain `SortField("year", INT)` throws:

[source,text]
----
java.lang.IllegalStateException: unexpected docvalues type SORTED_NUMERIC for field 'year'
(expected=NUMERIC). Re-index with correct docvalues type.
----

[cols="2,3",options="header"]
|===
| Field written | Sort with

| `NumericDocValuesField` | `new SortField("price_cents", SortField.Type.LONG, reverse)`
| `IntField` / `LongField` / `FloatField` / `DoubleField` (sorted-numeric) | `new SortedNumericSortField("year", SortField.Type.INT, reverse)`
| `SortedDocValuesField` (single string) | `new SortField("title_sort", SortField.Type.STRING)`
| `KeywordField` / `SortedSetDocValuesField` (multi string) | `new SortedSetSortField("tag", reverse)`
|===

Each of those four sorts was run against the catalog: `SortedNumericSortField("year")` ascending starts with
`Head First Java` (2005), `SortedSetSortField("tag")` starts with `Head First Java` (its smallest tag,
`beginner`), and `SortField("title_sort", STRING)` starts with `Effective Java`. When a field is multi-valued, the
sorted-numeric and sorted-set variants take a *selector* (min or max of the document's values) to decide which
value represents the document.

[[field-consistency]]
=== Lucene enforces per-field consistency

Documents carry no schema, but the *index* does remember, per field name, how the field was first indexed:
its `IndexOptions`, its doc-values type and its point dimensions. Adding a document whose field disagrees
with that structure fails at `addDocument` time rather than corrupting the segment. Adding a document with a
`NumericDocValuesField("x", 5)` after an index already holds `x` as a `TextField` throws:

[source,text]
----
IllegalArgumentException: Inconsistency of field data structures across documents for field [x] of doc [1].
index options: expected 'DOCS_AND_FREQS_AND_POSITIONS', but it has 'NONE'.
----

and a document that carries both a `StringField` and an `IntField` named `x` fails the same way once `x` is
established as text (the message then says the index options were expected to be `DOCS_AND_FREQS_AND_POSITIONS` but
are `DOCS`). The practical rule: one name,
one structure. Two capabilities on the same name are fine only when they are *different* structures that do not
collide, for example postings plus doc values (`KeywordField` is exactly that), but not postings of two different
shapes. Use a second name (`title` and `title_sort`) when the shapes differ.

=== Multi-valued fields and position gaps

Adding the same field name twice stores both values. For a `TextField` the two values are analyzed one after the
other and their positions are *concatenated*: with the default `StandardAnalyzer`, whose
`getPositionIncrementGap` is `0`, the last token of the first value and the first token of the second value are
adjacent. Indexing `"lucene guide"` and `"search book"` as two values of `note` therefore makes the phrase
`"guide search"` match across the boundary (8 of 8 documents in the test run). If values must not run together,
subclass the analyzer and override `getPositionIncrementGap(String fieldName)` to return a large number such
as 100, so that no phrase of normal slop can bridge two values.

=== What FeatureField adds to a score

A `FeatureField` is indexed as a term (`DOCS_AND_FREQS`, with the value encoded in the frequency) so it carries no
text and no norms. Adding a saturation `FeatureField.newSaturationQuery("features", "pagerank", 1f, 4f)` as a
`SHOULD` clause to `title:java` reorders the three Java books by their stored feature value (`Effective Java`
scored 1.207 against 1.050 and 1.035) without touching the text relevance. More on this in
xref:database/lucene/function-and-custom-scoring.adoc[Function & custom scoring].

=== Choosing IndexOptions deliberately

`IndexOptions` is where a field trades index size for capability. The catalog fields show the two extremes:
`isbn` as `DOCS` costs only the term and its document list; a `title` at `DOCS_AND_FREQS_AND_POSITIONS` also
stores frequencies (needed for BM25) and positions (needed for phrases). Asking a field that was indexed
with `DOCS` only to run a phrase fails at query time, not index time:

[source,text]
----
IllegalStateException: field "title" was indexed without position data; cannot run PhraseQuery
(phrase=title:"lucene action")
----

The printed `FieldType` of the standard instances makes the defaults explicit: `TextField.TYPE_STORED` prints
`stored,indexed,tokenized`, `StringField.TYPE_STORED` prints `stored,indexed,omitNorms,indexOptions=DOCS`, and the
custom type from the previous section prints `stored,indexed,tokenized,termVector,termVectorOffsets,
termVectorPosition,indexOptions=DOCS_AND_FREQS_AND_POSITIONS_AND_OFFSETS`.

This is the library-level version of a server's field mapping: compare
xref:database/elasticsearch/mapping-and-field-types.adoc[Elasticsearch mapping & field types] (where
`text` vs. `keyword` and `doc_values` are mapping options) and
xref:database/solr/field-types.adoc[Solr field types] (where the same choices are `<fieldType>`
declarations in a schema).
