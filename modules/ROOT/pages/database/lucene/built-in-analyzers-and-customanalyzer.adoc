= Built-in analyzers & CustomAnalyzer
:description: The ready-made analyzers in lucene-analysis-common -- StandardAnalyzer, SimpleAnalyzer, WhitespaceAnalyzer, KeywordAnalyzer, StopAnalyzer, EnglishAnalyzer and the language set -- PerFieldAnalyzerWrapper, and building an analyzer from factory names with CustomAnalyzer.builder().
:keywords: apache lucene, standardanalyzer, simpleanalyzer, whitespaceanalyzer, keywordanalyzer, stopanalyzer, englishanalyzer, language analyzers, lucene-analysis-common, perfieldanalyzerwrapper, customanalyzer, customanalyzer builder, tokenizer factory, token filter factory, basetokenstreamtestcase, lucene-test-framework

include::partial$ai-disclaimer.adoc[]

Most indexes never need a hand-written `Analyzer`. The `lucene-analysis-common` module ships a set of
ready-made ones, `PerFieldAnalyzerWrapper` lets different fields use different analyzers, and
`CustomAnalyzer.builder()` assembles a chain from named factories without a subclass. This page tours
those options and how to test the result. For how the pipeline itself works, see
xref:database/lucene/analysis-pipeline.adoc[Analysis pipeline].

== The built-in analyzers

All of these are in `lucene-analysis-common` (packages `org.apache.lucene.analysis.core`,
`org.apache.lucene.analysis.en` and so on), except `StandardAnalyzer`, which ships in `lucene-core` together with
`StandardTokenizer`, `LowerCaseFilter`, `StopFilter` and `CharArraySet`. `KeywordAnalyzer`, a frequent source of
confusion, lives in `lucene-analysis-common` (`org.apache.lucene.analysis.core`), so a project that only declares
`lucene-core` can use `StandardAnalyzer` but not `KeywordAnalyzer` or `CustomAnalyzer`.

[cols="1,3",options="header"]
|===
| Analyzer | Chain and use

| `StandardAnalyzer` | `StandardTokenizer` + `LowerCaseFilter` + `StopFilter` (empty stop set by default). Unicode word-boundary segmentation; the sensible default for most text.
| `SimpleAnalyzer` | `LetterTokenizer` + `LowerCaseFilter` -- splits on any non-letter, so digits are discarded. Rarely what you want for real data.
| `WhitespaceAnalyzer` | `WhitespaceTokenizer` only -- splits on whitespace, no lowercasing, no punctuation handling. Good for pre-tokenized input or codes.
| `KeywordAnalyzer` | `KeywordTokenizer` -- the whole input becomes one token, unchanged. Equivalent to indexing a `StringField`; use that instead when you can.
| `StopAnalyzer` | `LetterTokenizer` + `LowerCaseFilter` + `StopFilter` -- `SimpleAnalyzer` plus stop-word removal.
| `EnglishAnalyzer` | `StandardTokenizer` + `EnglishPossessiveFilter` + `LowerCaseFilter` + `StopFilter` + `PorterStemFilter`, with a `KeywordAttribute` exclusion set. The template every language analyzer follows.
|===

`lucene-analysis-common` carries a matching analyzer for roughly forty languages --
`FrenchAnalyzer`, `GermanAnalyzer`, `RussianAnalyzer`, `CJKAnalyzer`, and so on -- each pairing the
standard tokenizer with that language's stop words and stemmer. See
xref:database/lucene/language-analysis.adoc[Language analysis] for choosing and tuning them.

[source,java]
----
// https://lucene.apache.org/core/10_0_0/analysis/common/org/apache/lucene/analysis/en/EnglishAnalyzer.html
Analyzer std = new StandardAnalyzer();
Analyzer english = new EnglishAnalyzer();          // stemming + English stop words
Analyzer french = new FrenchAnalyzer();

// Provide your own stop words instead of the language default:
Analyzer custom = new EnglishAnalyzer(
        StopFilter.makeStopSet("brand", "sku", "the", "a"));
----

== PerFieldAnalyzerWrapper

A single index usually has fields that want different treatment -- an `sku` that must stay verbatim, a
`body` that wants English stemming, a `name` that wants only lowercasing.
`PerFieldAnalyzerWrapper` takes a default analyzer plus a per-field map and dispatches by field name;
pass it to `IndexWriterConfig` and to the query parser so both sides analyze consistently.

[source,java]
----
// https://lucene.apache.org/core/10_0_0/analysis/common/org/apache/lucene/analysis/miscellaneous/PerFieldAnalyzerWrapper.html
var perField = new PerFieldAnalyzerWrapper(
        new StandardAnalyzer(),                 // default for unlisted fields
        Map.of(
            "sku", new KeywordAnalyzer(),
            "body", new EnglishAnalyzer(),
            "name", new WhitespaceAnalyzer()));

var config = new IndexWriterConfig(perField);
----

Run on the catalog, with `isbn` analyzed by `KeywordAnalyzer`, `description` by `EnglishAnalyzer`, `author` by
`WhitespaceAnalyzer` and everything else by `StandardAnalyzer`, the same classic query parser (given the wrapper
as its analyzer) produces:

[cols="2,2,1",options="header"]
|===
| Query string | Parsed as | Hits

| `description:searching` | `description:search` | 3
| `author:bloch` | `author:bloch` | 0
| `author:Bloch` | `author:Bloch` | 1
| `isbn:9781933988177` | `isbn:9781933988177` | 1
| `title:Actions` | `title:actions` | 0
|===

The first row shows the wrapper doing its job on the query side: `searching` was stemmed to `search`, the term the
`EnglishAnalyzer` stored. The next two rows show the cost of `WhitespaceAnalyzer` for names: it does not
lowercase, so only the exact capitalization `Bloch` matches. The last row shows that `StandardAnalyzer` does
not stem: `Actions` cannot find `Action`. If the query-side parser had used a plain `StandardAnalyzer` for
`description` instead of the wrapper, `description:searching` would have looked for the unstemmed term and
returned *zero* hits against the same index. Using one wrapper instance for both the `IndexWriterConfig` and the
query parser is the cheapest way to avoid that class of bug.

== CustomAnalyzer.builder(): a chain without a subclass

`CustomAnalyzer.builder()` builds an analyzer at runtime from the *SPI names* of the tokenizer and
filter factories (the same short names Solr and Elasticsearch use in their schemas -- `standard`,
`lowercase`, `stop`, `asciifolding`, `edgeNGram`, ...), each with a map of string parameters. This is
the idiomatic way to make analysis config data rather than code, and it reads a resource directory for
files such as stop-word or synonym lists.

[source,java]
----
// https://lucene.apache.org/core/10_0_0/analysis/common/org/apache/lucene/analysis/custom/CustomAnalyzer.html
Analyzer analyzer = CustomAnalyzer.builder(Path.of("conf/analysis"))
        .withTokenizer("standard")
        .addCharFilter("htmlStrip")
        .addTokenFilter("lowercase")
        .addTokenFilter("stop",
                "ignoreCase", "true",
                "words", "stopwords.txt",
                "format", "wordset")
        .addTokenFilter("asciiFolding", "preserveOriginal", "false")
        .addTokenFilter("porterStem")
        .build();
----

Call `.builder()` with no argument when no factory needs to load a file.

Parameters can be passed two ways: as alternating key and value strings (`"ignoreCase", "true", "words",
"stopwords.txt"`, as above) or as a `Map<String, String>`. The map form has a trap: the factory *removes* each
key as it consumes it, so an immutable map such as `+Map.of(...)+` throws `UnsupportedOperationException` from
inside the factory constructor, while `+new HashMap<>(Map.of(...))+` works. The varargs form avoids the problem.

=== Running it on the catalog

The chain above, with a `stopwords.txt` containing `the`, `in`, `of` and `a`, applied to
`<p>The Café in Action: Building Searches</p>` produced the terms `cafe`, `action`, `build`, `search`: the HTML
tags were stripped, `The` and `in` removed as stop words (the filter is case-insensitive), `Café` folded to `cafe`
and the Porter stemmer reduced `Building` and `Searches`. `analyzer.toString()` is not informative -- it prints the
factory class names and object hashes -- so inspect behaviour by running text through it.

Two failures worth knowing, with their real messages. A misspelt factory name fails at `build()` and lists
everything the classpath offers:

[source,text]
----
IllegalArgumentException: A SPI class of type org.apache.lucene.analysis.TokenFilterFactory with name
'nonsense' does not exist. You need to add the corresponding JAR file supporting this SPI to your classpath.
The current classpath supports the following names: [doubleMetaphone, daitchMokotoffSoundex, ... lowercase ...]
----

and forgetting the tokenizer fails with `IllegalStateException: You have to set at least a tokenizer.` The
list in the first message is *classpath-dependent*: with only `lucene-core` and `lucene-analysis-common` the
names are those of the common module (over a hundred token filters); adding `lucene-analysis-icu`,
`lucene-analysis-kuromoji` or `lucene-analysis-phonetic` adds `icuFolding`, `japaneseBaseForm`, `phonetic` and
others, which is how module analyzers become reachable by name (see
xref:database/lucene/language-analysis.adoc[Language analysis]).

Two SPI names differ from the class names and trip people up: the Snowball stemmer is `snowballPorter`
(with a `language` parameter), and the edge n-gram filter is `edgeNGram`.

[mermaid]
....
flowchart LR
    B["CustomAnalyzer.builder()"] --> TZ["withTokenizer(name, params)"]
    B --> CF["addCharFilter(name, params)"]
    B --> TF["addTokenFilter(name, params)"]
    TZ --> SPI["SPI lookup: name to factory class on the classpath"]
    CF --> SPI
    TF --> SPI
    SPI --> RL["factories that need files are informed of the ResourceLoader: builder(Path) or classpath"]
    RL --> BUILD["build(): validates the chain and returns an Analyzer"]
    BUILD --> RUN["createComponents(): factories create fresh chain objects per thread"]
....

== Testing an analyzer

For a quick check, consume the `TokenStream` and print the terms -- the pattern in
xref:database/lucene/analysis-pipeline.adoc[Analysis pipeline]. For real coverage, depend on
`lucene-test-framework` and extend `BaseTokenStreamTestCase`: its `assertAnalyzesTo` verifies the
exact terms, offsets, positions and types an analyzer produces for an input, and its
`checkRandomData` helper hammers the analyzer with generated strings to surface lifecycle bugs
(missing `reset()`, offsets going backwards).

[source,xml]
----
<dependency>
  <groupId>org.apache.lucene</groupId>
  <artifactId>lucene-test-framework</artifactId>
  <version>10.0.0</version>
  <scope>test</scope>
</dependency>
----

[source,java]
----
// https://lucene.apache.org/core/10_0_0/test-framework/org/apache/lucene/tests/analysis/BaseTokenStreamTestCase.html
public class ProductAnalyzerTest extends BaseTokenStreamTestCase {

    public void testStemmingAndStopWords() throws Exception {
        Analyzer analyzer = CustomAnalyzer.builder()
                .withTokenizer("standard")
                .addTokenFilter("lowercase")
                .addTokenFilter("stop")
                .addTokenFilter("porterStem")
                .build();

        assertAnalyzesTo(
                analyzer,
                "The Running Shoes",
                new String[] {"run", "shoe"},   // expected terms
                new int[]    {4, 12},            // start offsets
                new int[]    {11, 17},           // end offsets
                new int[]    {2, 1});            // position increments ("the" removed)

        checkRandomData(random(), analyzer, 200);
        analyzer.close();
    }
}
----

The test above passes unchanged on JUnit 4 with `lucene-test-framework` 10.0.0. A deliberately wrong
expectation is reported precisely:

[source,text]
----
assertAnalyzesTo(analyzer, "The Running Shoes", new String[] {"the", "running", "shoe"});
-> term 2 expected:<shoe[]> but was:<shoe[s]>
----

The failing index (`term 2`) and the expected-versus-actual diff with the differing characters in brackets
are what make `assertAnalyzesTo` more useful than printing terms. It also accepts overloads for terms only,
terms with offsets, or the full set of terms, offsets, types, position increments and position lengths.
`checkRandomData(random(), analyzer, 200)` feeds 200 randomized strings (including unusual Unicode and very long
tokens) through the chain and verifies the lifecycle and offset invariants, which is how a missing `reset()`
override is found.
