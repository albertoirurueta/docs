= Near-real-time search
:description: Making uncommitted IndexWriter changes searchable with DirectoryReader.open(writer) and openIfChanged, managing readers with SearcherManager and ControlledRealTimeReopenThread, stable paging with SearcherLifetimeManager, and the reference-counting rules that keep it safe.
:keywords: apache lucene, near real time, nrt, directoryreader, openifchanged, searchermanager, searcherfactory, controlledrealtimereopenthread, searcherlifetimemanager, reference counting, incref, decref, indexsearcher, reopen

include::partial$ai-disclaimer.adoc[]

*Near-real-time (NRT) search* makes documents visible to queries milliseconds after they are written,
without a durable `commit`. A `DirectoryReader` opened directly on the `IndexWriter` sees the writer's
flushed in-memory segments; periodically reopening that reader refreshes what searches can find. This
page covers the reopen APIs, the helpers that manage them, and the reference-counting discipline that
makes sharing a reader across threads safe.

== Opening and reopening an NRT reader

`DirectoryReader.open(IndexWriter)` returns a reader that includes everything the writer has flushed,
committed or not. To refresh it, never open a brand-new reader in a loop -- call
`DirectoryReader.openIfChanged(oldReader)`, which returns a new reader that *shares* unchanged
segments with the old one (cheap) or `null` when nothing has changed. Close the old reader only once
no thread is still using it.

[source,java]
----
// https://lucene.apache.org/core/10_0_0/core/org/apache/lucene/index/DirectoryReader.html
DirectoryReader reader = DirectoryReader.open(writer);   // NRT: sees uncommitted flushes
IndexSearcher searcher = new IndexSearcher(reader);

// ... time passes, more documents are indexed ...

DirectoryReader refreshed = DirectoryReader.openIfChanged(reader);
if (refreshed != null) {
    // Hand new queries the refreshed reader, then release the old one.
    reader.close();          // safe only if no in-flight search still holds it
    reader = refreshed;
    searcher = new IndexSearcher(reader);
}
----

Doing that safely by hand across many threads is fiddly, which is what the next two helpers are for.

=== Visible is not durable: what each step guarantees

Writing a document moves it through three states, and only the last is crash-safe. The catalog experiment below
used a `SearcherManager` over a writer and printed what a search could see after each step:

[source,text]
----
3 docs added (no flush, no commit)          : visible=0
after maybeRefresh()                        : visible=3
files in the directory                      : [_0.cfe, _0.cfs, _0.si]
DirectoryReader.open(dir) at that point     : IndexNotFoundException
after commit(), DirectoryReader.open(dir)   : numDocs=3
----

Right after `addDocument` the searcher saw nothing, because the manager's current reader was opened before the add.
`maybeRefresh()` produced a new reader that included the buffered documents: the writer flushed them to a new
segment *for the reader* and handed over its in-memory view. At that moment the directory held a segment
(`_0.cfs`) but no `segments_N` file, so a reader opened the ordinary way found no index at all and threw
`IndexNotFoundException`. Only `commit()` wrote `segments_1`, after which `DirectoryReader.open(dir)` saw the three
documents. In other words, near-real-time search makes data *visible*; `commit()` makes it *durable*, and the two
are independent decisions with different costs.

[mermaid]
....
stateDiagram-v2
    [*] --> Buffered: addDocument
    Buffered --> Flushed: refresh or flush (new segment, not yet in a commit)
    Flushed --> Committed: commit() writes segments_N
    Buffered --> Lost: crash
    Flushed --> Lost: crash
    Committed --> Committed: crash-safe
    Flushed --> Searchable: reader reopened over the writer
    Committed --> Searchable: reader opened on the directory
    Searchable --> [*]
....

== SearcherManager and SearcherFactory

`SearcherManager` owns the current `IndexSearcher` and hands it out under a reference count.
Threads call `acquire()`, run their query, and `release()` in a `finally`; a background caller
invokes `maybeRefresh()` to swap in a reader built from `openIfChanged`. In-flight searches keep
running against the old reader, which is closed automatically when its last user releases it. A
`SearcherFactory` customises each new `IndexSearcher` -- attaching an `Executor` for
xref:database/lucene/collectors-and-concurrent-search.adoc[intra-query concurrency], setting a
similarity, or warming caches.

[source,java]
----
// https://lucene.apache.org/core/10_0_0/core/org/apache/lucene/search/SearcherManager.html
var searcherFactory = new SearcherFactory() {
    @Override
    public IndexSearcher newSearcher(IndexReader reader, IndexReader previous) {
        var s = new IndexSearcher(reader, queryExecutor);
        s.setSimilarity(new BM25Similarity());
        return s;
    }
};
var searcherManager = new SearcherManager(writer, searcherFactory);

// Per query:
IndexSearcher searcher = searcherManager.acquire();
try {
    TopDocs hits = searcher.search(query, 10);
} finally {
    searcherManager.release(searcher);
}

// On a schedule, or after a write that must be visible now:
searcherManager.maybeRefresh();
----

Two details of `maybeRefresh()` are easy to misread. It returns `true` when *this call performed the
refresh attempt* (it obtained the manager's refresh lock), not when new documents were found: it returned `true`
even when nothing was new. And `DirectoryReader.openIfChanged` is the one that reports change, by returning
`null`; in the catalog test it returned a new reader with three leaves for a reader that had two (the two old
segments shared, one new), and `null` when called again with nothing new. Every reader obtained from a
`SearcherManager` must go back through `release`: a reader that was closed directly with `close()` threw
`AlreadyClosedException` on the next search.

== ControlledRealTimeReopenThread for bounded staleness

`ControlledRealTimeReopenThread` drives `maybeRefresh()` on a timer with two intervals -- a long one
for background reopens and a short one used when a caller is actively waiting. `IndexWriter` hands out
a monotonically increasing generation from `updateDocument`/`addDocument`; a caller that needs its own
write to be visible passes that generation to `waitForGeneration(gen)` and blocks only until a reopen
has caught up to it. This bounds staleness without reopening on every write.

[source,java]
----
// https://lucene.apache.org/core/10_0_0/core/org/apache/lucene/search/ControlledRealTimeReopenThread.html
var nrtReopenThread = new ControlledRealTimeReopenThread<>(
        writer, searcherManager,
        5.0,    // max stale seconds for ordinary background reopens
        0.025); // max stale seconds when someone is waiting on a generation
nrtReopenThread.setDaemon(true);
nrtReopenThread.start();

long gen = writer.updateDocument(new Term("id", "p-1"), doc);
nrtReopenThread.waitForGeneration(gen);   // return once this write is searchable
IndexSearcher searcher = searcherManager.acquire();
----

Measured on the catalog with the 25 ms target above, a document added right before `waitForGeneration`
was not visible to an immediate search (`visible=4`), and after `waitForGeneration(gen)` returned -- about 30
milliseconds later in the test, while the background interval was five seconds -- the same search saw it
(`visible=6`, including an earlier pending document). The generation number `gen` is the sequence number returned
by `addDocument` and `updateDocument` (the call returned 16 in this run); it is a `long` that increases with every
operation on the writer.

[mermaid]
....
sequenceDiagram
    participant U as User request
    participant W as IndexWriter
    participant T as ControlledRealTimeReopenThread
    participant M as SearcherManager
    U->>W: addDocument(...)
    W-->>U: gen (sequence number)
    U->>T: waitForGeneration(gen)
    Note over T: wakes early: a caller is waiting
    T->>M: maybeRefresh()
    M->>W: openIfChanged(writer)
    W-->>M: reader covering gen
    T-->>U: returns
    U->>M: acquire(), search, release()
    Note over U,M: the search now sees the write
....

How much does a reopen cost? On the 150,000-document benchmark index (see
xref:database/lucene/performance-tuning.adoc[Performance tuning]), adding 100 documents and calling `maybeRefresh()` took a
median of 3.4 ms across twenty rounds, and 58.6 ms in the worst round. Two things dominate: writing the tiny new segment, and,
when it happens, finishing a background merge. The cost does not grow with the size of the *old* segments because they are
shared, not reopened, which is why NRT reopening scales to large indexes.

== SearcherLifetimeManager for stable paging

When a user pages through results, each page is a separate request and the index may have changed
between them, so page 2 built on a newer searcher can drop or reorder rows already shown.
`SearcherLifetimeManager` records a searcher under a token, returns that token to the client, and
hands the *same* searcher back on the follow-up request; a pruning pass retires searchers older than a
chosen age.

[source,java]
----
// https://lucene.apache.org/core/10_0_0/core/org/apache/lucene/search/SearcherLifetimeManager.html
var lifetimeManager = new SearcherLifetimeManager();

// First page: record the searcher, send token to the client.
long token = lifetimeManager.record(searcher);

// Later page: reuse the searcher pinned by that token (null if it was pruned).
IndexSearcher paged = lifetimeManager.acquire(token);
if (paged == null) {
    paged = searcherManager.acquire();   // fell out of the window: restart from page 1
}
try {
    // ... search for the next page against "paged" ...
} finally {
    lifetimeManager.release(paged);
}

// Housekeeping, on a schedule:
lifetimeManager.prune(new SearcherLifetimeManager.PruneByAge(600.0)); // keep 10 minutes
----

In a test with two recorded searchers, the *pinned* searcher kept its original six documents while a fresh searcher
from the manager saw seven, so page two of a result list built on the pinned searcher was consistent with page one.
After sleeping past the pruning age, `prune(new PruneByAge(0.5))` removed the older searcher (`acquire(token)`
returned `null`) while the newer one stayed. Pruning never evicts the most recently recorded searcher, so a
single recorded searcher is never pruned by age. When `acquire(token)` returns `null`, restart the user at page one:
there is no way to reconstruct the old view.

== Reference counting: incRef, decRef and release

Every `IndexReader` carries a reference count that starts at 1. `incRef()` claims a share, `decRef()`
releases one, and the underlying files are closed when the count hits 0 -- `close()` is just a
`decRef` of that initial reference. `SearcherManager.acquire()`/`release()` and
`SearcherLifetimeManager` do this bookkeeping for you; you only touch `incRef`/`decRef` directly if
you hold a reader outside those helpers.

The rule that matters: *never `close()` a reader another thread might still be reading.* Closing frees
the segment files out from under an in-flight search and throws `AlreadyClosedException` (or worse).
Always go through `acquire`/`release` so the last releaser -- not whichever thread happens to call
first -- does the closing.

[source,java]
----
// https://lucene.apache.org/core/10_0_0/core/org/apache/lucene/index/IndexReader.html#incRef()
reader.incRef();               // I now hold a share; someone else may too
try {
    var s = new IndexSearcher(reader);
    s.search(query, 10);
} finally {
    reader.decRef();           // release my share; last one out closes the files
}
----
