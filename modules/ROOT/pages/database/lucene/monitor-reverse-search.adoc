= The lucene-monitor module
:description: Reverse search with lucene-monitor -- registering MonitorQuery objects in a Monitor and matching incoming documents against all of them, with a Presearcher to scale to large query sets and CandidateMatcher variants for the match detail you need.
:keywords: apache lucene, lucene-monitor, reverse search, monitor, monitorquery, candidatematcher, querymatch, highlightsmatch, presearcher, termfilteredpresearcher, multipasstermfilteredpresearcher, luwak, saved search, alerting, percolate, monitorqueryserializer

include::partial$ai-disclaimer.adoc[]

Normal search registers documents and runs a query against them. *Reverse search* inverts that: you
register the _queries_ once and stream _documents_ past them, asking "which of my stored queries does
this document match?". `lucene-monitor` (the module that was formerly the standalone *Luwak*
library) is Lucene's implementation -- the engine behind saved-search alerts, content-routing rules,
and real-time classification.

The running example is a *new-arrivals alert*: readers save searches ("tell me about any new Lucene
book"), and every book announcement is matched against all saved searches the moment it arrives.
Every output below is a real run against Lucene 10.4.0.

[mermaid]
....
flowchart LR
  subgraph reg["register once"]
    Q1["alert-1: lucene"] --> QI["Monitor: query index"]
    Q2["alert-2: search AND library"] --> QI
    Q3["alert-3: phrase second edition"] --> QI
  end
  D["incoming document"] --> MI["in-memory index of the document"]
  QI --> PS["Presearcher: build a candidate query from the document's terms"]
  MI --> PS
  PS --> C["candidate queries only"]
  C --> M["CandidateMatcher: run each candidate against the document"]
  MI --> M
  M --> R["MatchingQueries: ids, scores, highlights"]
....

== Registering queries in a Monitor

A `Monitor` holds a set of `MonitorQuery` records, each a stable id plus a parsed `Query` (and
optional original query string and metadata map). `monitor.match` takes one or more in-memory
documents and returns the ids of every registered query they satisfy.

[source,xml]
----
<dependency>
  <groupId>org.apache.lucene</groupId>
  <artifactId>lucene-monitor</artifactId>
  <version>10.4.0</version>
</dependency>
----

[source,java]
----
// https://lucene.apache.org/core/10_0_0/monitor/org/apache/lucene/monitor/Monitor.html
import org.apache.lucene.monitor.Monitor;
import org.apache.lucene.monitor.MonitorQuery;
import org.apache.lucene.monitor.MatchingQueries;
import org.apache.lucene.monitor.QueryMatch;
import org.apache.lucene.analysis.standard.StandardAnalyzer;
import org.apache.lucene.document.Document;
import org.apache.lucene.document.TextField;
import org.apache.lucene.document.Field;
import org.apache.lucene.index.Term;
import org.apache.lucene.search.TermQuery;
import org.apache.lucene.queryparser.classic.QueryParser;
import java.util.Map;

StandardAnalyzer analyzer = new StandardAnalyzer();
QueryParser parser = new QueryParser("text", analyzer);

try (Monitor monitor = new Monitor(analyzer)) {

    // register saved searches -- id, Query, original string, metadata
    monitor.register(
            new MonitorQuery("alert-1", new TermQuery(new Term("text", "lucene"))),
            new MonitorQuery("alert-2", parser.parse("search* AND (engine OR library)"),
                    "search* AND (engine OR library)", Map.of("team", "platform")),
            new MonitorQuery("alert-3", parser.parse("\"second edition\"")),
            new MonitorQuery("alert-4", parser.parse("solr OR elasticsearch")));

    // an incoming document (never added to any index)
    Document doc = new Document();
    doc.add(new TextField("text",
            "Lucene in Action, second edition: indexing and searching with the Apache Lucene library",
            Field.Store.NO));

    MatchingQueries<QueryMatch> result = monitor.match(doc, QueryMatch.SIMPLE_MATCHER);

    for (QueryMatch m : result.getMatches()) {
        System.out.println("matched " + m.getQueryId());
    }
    System.out.println("queries run: " + result.getQueriesRun() + " of " + monitor.getQueryCount());
}
----

[source,text]
----
matched alert-1
matched alert-2
matched alert-3
queries run: 3 of 4, errors={}
----

Three of the four alerts match. The fourth (`solr OR elasticsearch`) was never *run*: the presearcher
(below) saw that the announcement contains neither term and dropped the query before evaluation, which
is why `getQueriesRun()` reports 3 of 4 registered. `register` indexes the query for the presearcher and
keeps it in an in-memory cache; call it again with the same id to replace a query and
`monitor.deleteById("alert-4")` to remove one, and the next match sees the change. Several queries can be registered in one call, as above.

[source,java]
----
monitor.register(new MonitorQuery("alert-1", new TermQuery(new Term("text", "tantivy"))));  // replaces alert-1
monitor.deleteById("alert-4");
----

[source,text]
----
after update/delete: [alert-2, alert-3] registered=[alert-1, alert-2, alert-3]
----

`monitor.match(Document[], factory)` matches a batch and returns `MultiMatchingQueries`, which keeps the
matches of each document apart (`getMatches(i)`); the whole batch is indexed and searched once, which costs less than matching its documents
one by one:

[source,text]
----
batch doc 0: [alert-1, alert-2, alert-3]
batch doc 1: [alert-4]
----

== How much detail: the matcher factory

The second argument to `match` is a `MatcherFactory` that builds a `CandidateMatcher`. It decides
what each match tells you -- and how much work per candidate query:

[cols="1,3",options="header"]
|===
| Factory | Each match yields

| `QueryMatch.SIMPLE_MATCHER` | Just the matching query id. Cheapest.
| `HighlightsMatch.MATCHER` | The id plus the hit positions/offsets within the document.
| `ExplainingMatch.MATCHER` | The id plus a Lucene `Explanation` of why it matched.
| `ScoringMatch.matchWithSimilarity(sim)` | The id plus a relevance score under the given `Similarity`.
|===

[source,java]
----
// https://lucene.apache.org/core/10_0_0/monitor/org/apache/lucene/monitor/HighlightsMatch.html
import org.apache.lucene.monitor.HighlightsMatch;
import org.apache.lucene.monitor.MatchingQueries;

MatchingQueries<HighlightsMatch> hi = monitor.match(doc, HighlightsMatch.MATCHER);
for (HighlightsMatch m : hi.getMatches()) {
    m.getHits("text").forEach(h -> System.out.println(h.startOffset() + ".." + h.endOffset()));
}
----

[source,text]
----
highlights alert-1: [0..6] [73..79]
highlights alert-2: [47..56] [80..87]
highlights alert-3: [18..32]
explain alert-1: 0.1798013 = weight(text:lucene in 0) [BM25Similarity], result of:
score alert-1 = 0.1798
score alert-2 = 1.1308
score alert-3 = 0.2615
----

The offsets are character offsets into the document text, so `0..6` and `73..79` are the two
occurrences of `Lucene`, `47..56` is `searching` (matched by the wildcard `+search*+`) and `80..87` is
`library`, and `18..32` is the phrase `second edition`. Scores come from a similarity over the one
document in the in-memory index, so they only rank the matches *of that one document* against each
other; they are not comparable between documents. Use the simple matcher for routing, highlights for
"why was I alerted" snippets, and the explaining matcher when debugging a rule.

== Scaling with a Presearcher

Running every registered query against every document does not scale past a few thousand queries. A
`Presearcher` builds a secondary query from the incoming document's terms and runs it against the
query index first, so only queries that _could_ match are executed. `TermFilteredPresearcher` (the
default) is term-based; `MultipassTermFilteredPresearcher` trades more index space for fewer false
candidates. A `Monitor` takes the presearcher in its constructor; `Presearcher.NO_FILTERING` disables
filtering and runs everything.

[source,java]
----
// https://lucene.apache.org/core/10_0_0/monitor/org/apache/lucene/monitor/TermFilteredPresearcher.html
import org.apache.lucene.monitor.TermFilteredPresearcher;
import org.apache.lucene.monitor.MultipassTermFilteredPresearcher;
import org.apache.lucene.monitor.Presearcher;
import org.apache.lucene.monitor.TermWeightor;

try (Monitor monitor = new Monitor(analyzer, new TermFilteredPresearcher())) {
    monitor.register(queries);                    // 50,000 MonitorQuery objects
    MatchingQueries<QueryMatch> result = monitor.match(doc, QueryMatch.SIMPLE_MATCHER);
    // result.getQueriesRun() is now a small fraction of the registered total
}

// 3 passes over the query terms: fewer false candidates, a bigger query index
Presearcher multipass = new MultipassTermFilteredPresearcher(3, 0f, TermWeightor.DEFAULT, List.of(), Set.of());
----

The effect was measured with 50,000 registered queries, each a conjunction of two terms drawn from a
vocabulary of 3,000, and one incoming document of 60 words that matches 21 of them (average of 20
matches after a warm-up):

[cols="3,1,1,1,1",options="header"]
|===
| Presearcher | registered | queries run | matches | time per document

| `NO_FILTERING` | 50,000 | 50,000 | 21 | 105.5 ms
| `TermFilteredPresearcher` (default) | 50,000 | 1,011 | 21 | 9.6 ms
| `MultipassTermFilteredPresearcher(3 passes)` | 50,000 | 21 | 21 | 3.4 ms
|===

All three find the same 21 matches. The default presearcher cuts the evaluated queries from 50,000 to
about a thousand, and the multipass variant reaches the theoretical minimum, 21 (every candidate was a
true match), at the price of a larger query index. Why the default over-selects: it indexes *one* term of
each conjunction, so every query that merely shares that term with the document becomes a candidate;
the multipass variant indexes several terms of the query in different passes and requires the document to
satisfy all of them. A query with no extractable terms at all (a lone wildcard or `MatchAllDocsQuery`)
is always a candidate, so a workload with many of them cannot be accelerated. Compare `getQueriesRun()`
with the registered count to see the presearcher's selectivity for your workload; `monitor.debug(doc,
factory)` reports which queries the presearcher selected and the terms that selected them.

== Persisting the query set

By default the `Monitor` keeps its query index in memory and must be repopulated on restart. Give
`MonitorConfiguration.setIndexPath` a directory *and a `MonitorQuerySerializer`* and the registered
`MonitorQuery` records are stored on disk and reloaded automatically; the serializer turns a stored
query string back into a `Query`, and `MonitorQuerySerializer.fromParser` builds one from any
string-to-`Query` function such as a `QueryParser`:

[source,java]
----
import org.apache.lucene.monitor.MonitorConfiguration;
import org.apache.lucene.monitor.MonitorQuerySerializer;

MonitorQuerySerializer serializer = MonitorQuerySerializer.fromParser(s -> {
    try { return parser.parse(s); } catch (Exception e) { throw new RuntimeException(e); }
});
MonitorConfiguration config = new MonitorConfiguration().setIndexPath(Path.of("/var/data/monitor-queries"), serializer);

try (Monitor monitor = new Monitor(analyzer, config)) {
    monitor.register(new MonitorQuery("p1", parser.parse("lucene AND library"), "lucene AND library", Map.of()));
}
try (Monitor monitor = new Monitor(analyzer, config)) {       // after a restart
    System.out.println(monitor.getQueryCount() + " " + monitor.getQueryIds());
}
----

[source,text]
----
persisted queries: 1
after restart: 1 [p1] matches=1
----

Only the *query string* and the metadata are persisted, so a `MonitorQuery` registered without a query
string (as `alert-1` above, built directly from a `TermQuery`) cannot be rebuilt from disk; register
persisted queries with their original string. Asking an in-memory monitor for a stored query with
`monitor.getQuery(id)` fails for the same reason: with no serializer there is nothing to return it from.
The https://lucene.apache.org/core/10_0_0/monitor/index.html[lucene-monitor module overview] documents
`MonitorConfiguration`, the `QueryDecomposer` that splits disjunctions into separate indexed
sub-queries for better presearcher selectivity, and the purge and update-buffer settings.

== Versus Elasticsearch's percolator

Elasticsearch's `percolate` query is the same reverse-search idea as a managed feature -- stored
queries indexed in a `percolator` field type, matched against a document supplied at query time --
and it is itself built on this Lucene machinery; see
xref:database/elasticsearch/search-extras.adoc[Elasticsearch search extras].

== When to use it

* *Alerts and saved searches* -- thousands to millions of stored queries, a stream of new documents.
* *Content routing and tagging* -- each rule is a query; the matches decide the destination or label.
* *Not* for the normal case of a few queries over many documents: that is `IndexSearcher`. Reverse search
  pays off only when queries outnumber documents per unit of time, or when the documents are not in an
  index at all.
