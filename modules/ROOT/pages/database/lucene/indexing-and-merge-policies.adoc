= Indexing operations & merge policies
:description: How IndexWriter adds, updates, soft-deletes and commits documents, the IndexWriterConfig knobs that shape a segment, and why Lucene merges segments -- TieredMergePolicy and the other policies plus the merge schedulers.
:keywords: apache lucene, indexwriter, indexwriterconfig, adddocument, updatedocument, deletedocuments, softupdatedocument, soft deletes, softdeletesretentionmergepolicy, commit, flush, preparecommit, two-phase commit, setlivecommitdata, rollback, openmode, ram buffer, forcemerge, forcemergedeletes, optimize, index sorting, setindexsort, merge policy, tieredmergepolicy, logbytesizemergepolicy, nomergepolicy, filtermergepolicy, concurrentmergescheduler, serialmergescheduler

include::partial$ai-disclaimer.adoc[]

`IndexWriter` is the only class that changes an index. It buffers documents in RAM, flushes them to
immutable *segments*, records deletes as a side file, and -- through a *merge policy* and a *merge
scheduler* -- rewrites small or delete-heavy segments into larger clean ones in the background. This
page covers the write operations, the two-phase commit protocol, the `IndexWriterConfig` settings
that matter, and how merging is controlled.

== Writing documents

Every write goes through one long-lived `IndexWriter`. `addDocument` appends; `updateDocument`
atomically deletes every document matching a `Term` and then adds the replacement in one operation, so
a reader never sees zero or two copies; `deleteDocuments` takes either `Term` s or `Query` s. Lucene
has no true in-place update -- an "update" is always a delete plus an add, and the old document's
space is reclaimed only when its segment is later merged.

[source,java]
----
// https://lucene.apache.org/core/10_0_0/core/org/apache/lucene/index/IndexWriter.html
var config = new IndexWriterConfig(analyzer);
try (var dir = FSDirectory.open(Path.of("/var/index/products"));
     var writer = new IndexWriter(dir, config)) {

    var doc = new Document();
    doc.add(new StringField("id", "p-1", Field.Store.YES));
    doc.add(new TextField("name", "Trail running shoe", Field.Store.YES));
    doc.add(new IntPoint("stock", 41));
    doc.add(new NumericDocValuesField("stock", 41));
    writer.addDocument(doc);

    // Replace p-1 in one atomic step (delete-by-Term + add).
    var updated = new Document();
    updated.add(new StringField("id", "p-1", Field.Store.YES));
    updated.add(new TextField("name", "Trail running shoe v2", Field.Store.YES));
    writer.updateDocument(new Term("id", "p-1"), updated);

    writer.deleteDocuments(new Term("id", "p-legacy"));
    writer.deleteDocuments(IntPoint.newRangeQuery("stock", 0, 0)); // delete-by-Query
    writer.commit();
}
----

=== What the numbers do: add, update and delete on the catalog

The document counters of a reader make the delete-plus-add semantics visible. The program below loads the eight
books into one segment (with `NoMergePolicy`, so that no merge hides the effect), then updates, deletes by term
and deletes by query, printing `numDocs` (live documents), `maxDoc` (live plus deleted) and the segment count after
each step:

[source,text]
----
after 8 adds                                : numDocs=8 maxDoc=8 deleted=0 segments=1
after updateDocument (Effective Java)       : numDocs=8 maxDoc=9 deleted=1 segments=2 seqNo=11
after deleteDocuments(Term isbn)            : numDocs=7 maxDoc=9 deleted=2 segments=2
after deleteDocuments(Query year 2005..2006): numDocs=5 maxDoc=9 deleted=4 segments=2
hits for isbn 9780134685991                 : 1
----

`updateDocument` made `maxDoc` grow from 8 to 9 while `numDocs` stayed 8: the old version is still physically
there, flagged deleted, and the new version went into a second segment. A search for the updated ISBN returns one
hit, because the delete-and-add is atomic for readers. The deletions are not applied until a merge rewrites the
segments: with the default merge policy, simply reopening the same index afterwards reported `numDocs=5 maxDoc=5
segments=1`, because the policy noticed that more than `deletesPctAllowed` (20 percent) of the documents were dead
and merged them away on its own. `updateDocument` also returns a *sequence number* (`seqNo=11` above), a
monotonically increasing `long` that orders every operation on the writer and that the near-real-time reopen
machinery uses to decide whether a given write is visible yet.

=== Soft deletes

A *soft delete* marks a document as deleted for search but keeps it retrievable until a retention rule
lets it go -- the mechanism behind
xref:database/elasticsearch/indexing-crud-and-bulk.adoc[Elasticsearch's] `_seq_no` recovery and
useful for change-data-capture or "show me the previous version" features. Enable it by naming a field
with `+IndexWriterConfig.setSoftDeletesField(...)+` and pairing it with a
`SoftDeletesRetentionMergePolicy` that decides which soft-deleted docs a merge may finally drop.
`softUpdateDocument` then replaces a document while writing the soft-delete marker instead of a hard
delete.

[source,java]
----
// https://lucene.apache.org/core/10_0_0/core/org/apache/lucene/index/SoftDeletesRetentionMergePolicy.html
var config = new IndexWriterConfig(analyzer);
config.setSoftDeletesField("__soft_deleted");
config.setMergePolicy(new SoftDeletesRetentionMergePolicy(
        "__soft_deleted",
        () -> LongPoint.newRangeQuery("version", 5L, Long.MAX_VALUE), // keep versions >= 5
        new TieredMergePolicy()));

try (var writer = new IndexWriter(dir, config)) {
    var v = new Document();
    v.add(new StringField("id", "p-1", Field.Store.YES));
    v.add(new LongPoint("version", 6L));
    v.add(new TextField("name", "Trail running shoe v3", Field.Store.YES));
    // Marker field flags the OLD p-1 as soft-deleted rather than removing it.
    writer.softUpdateDocument(new Term("id", "p-1"), v,
            new NumericDocValuesField("__soft_deleted", 1));
}
----

Run on the catalog (one book, then a soft update that replaces it with a second version), the search-visible state
shows the mechanism: only the new version is visible (`numDocs=1`), yet `maxDoc=2` because the old version is still
in the segment. A `forceMerge(1)` with the retention policy above also left `maxDoc=2`: the retention query
(`version >= 1`) still selects the old document, so the merge was *not allowed* to drop it. Soft-deleted documents
are invisible to the writer's own near-real-time readers, but a plain `DirectoryReader.open(dir)` on the same
directory reported `numDocs=2` (it does not know which field marks soft deletes), while wrapping it in
`new SoftDeletesDirectoryReaderWrapper(reader, "soft_deleted")` reported `numDocs=1`. Choosing whether to wrap is
therefore how change-data-capture style "give me the history" features read the retained versions.

== Commits, flushes & rollback

A *flush* pushes the RAM buffer into a new on-disk segment; it happens automatically as the buffer
fills and is not durable on its own. A *commit* `fsync` s all pending segments plus a new segments
file, producing a recovery point that survives a crash and becomes visible to a freshly opened
`DirectoryReader`. Near-real-time readers opened on the writer see flushed-but-uncommitted changes
too -- see xref:database/lucene/near-real-time-search.adoc[Near-real-time search].

`prepareCommit` then `commit` is a *two-phase commit*: `prepareCommit` does all the expensive
`fsync` work, after which the final `commit` is cheap and near-atomic, which lets an `IndexWriter`
participate in a distributed transaction alongside another resource. `rollback` closes the writer and
discards everything written since the last commit.

[source,java]
----
// https://lucene.apache.org/core/10_0_0/core/org/apache/lucene/index/IndexWriter.html#prepareCommit()
writer.addDocument(doc);

// Attach opaque metadata to the commit point (checkpoint, source offset, schema hash...).
writer.setLiveCommitData(Map.of(
        "kafka.offset", "48213",
        "indexer.version", "2025.09").entrySet());

writer.prepareCommit();   // phase 1: fsync segments + prepare a new segments_N
try {
    externalResource.commit();
    writer.commit();      // phase 2: cheap, flips the pointer
} catch (Exception e) {
    writer.rollback();    // discards since the last successful commit; writer is now closed
    throw e;
}
----

Read commit user data back with `DirectoryReader.open(dir).getIndexCommit().getUserData()`.

The two-phase commit and rollback behave as documented. In a test that committed document one with commit
data `kafka.offset=100`, added document two with `kafka.offset=200`, called `prepareCommit()` and then
`rollback()`, the writer reported itself closed and a fresh reader saw `numDocs=1` with user data
`+{kafka.offset=100}+`: the prepared-but-never-committed state left no trace.

== Tuning IndexWriterConfig

`IndexWriterConfig` is single-use -- one config per `IndexWriter` -- and every setter returns `this`.
The knobs that change throughput and segment shape:

[cols="1,3",options="header"]
|===
| Setting | Effect

| `setOpenMode(OpenMode.CREATE \| APPEND \| CREATE_OR_APPEND)` | Whether to overwrite, require an existing index, or create-if-absent (the default).
| `setRAMBufferSizeMB(double)` | Flush when buffered documents reach this heap size. The primary throughput lever; the default is 16 MB, and large bulk loads often use 256 MB or more. Takes precedence over a document count.
| `setMaxBufferedDocs(int)` | Flush after this many documents regardless of size. Disabled by default; set one or the other, not usually both.
| `setUseCompoundFile(boolean)` | Pack each small segment's files into a single `.cfs` file (default `true`) to limit open file handles; large merged segments stay multi-file regardless.
| `+setMergePolicy(...)+` / `+setMergeScheduler(...)+` | Covered below.
| `setIndexSort(Sort)` | Physically order documents within every segment (see below).
|===

[source,java]
----
// https://lucene.apache.org/core/10_0_0/core/org/apache/lucene/index/IndexWriterConfig.html
var config = new IndexWriterConfig(analyzer)
        .setOpenMode(IndexWriterConfig.OpenMode.CREATE_OR_APPEND)
        .setRAMBufferSizeMB(256.0)
        .setUseCompoundFile(true);
----

=== forceMerge is not a routine operation

`forceMerge(1)` rewrites the whole index into a single segment. It was called `optimize` before
Lucene 4 and the rename was deliberate: it is enormous I/O, it temporarily needs up to 3x the index
size on disk, and the one giant segment it produces is never itself merged again, so deletes
accumulate in it with nothing to reclaim them. Only run it on an index that is now read-only.
`forceMergeDeletes()` is the narrower, occasionally-justified cousin -- it rewrites only segments
whose deleted-document percentage is high.

[source,java]
----
// https://lucene.apache.org/core/10_0_0/core/org/apache/lucene/index/IndexWriter.html#forceMerge(int)
// Do this ONLY on an index that will not be written to again.
writer.forceMerge(1);

// Steady-state alternative: reclaim space in delete-heavy segments without collapsing to one.
writer.forceMergeDeletes();
----

=== Index-time sorting

`setIndexSort(Sort)` stores documents inside each segment in a chosen order (for example newest
first). Range and top-N queries that follow the same sort can then stop early, and the sort is
preserved across merges. The constraint: `updateDocument(Iterable)` blocks -- parent/child documents
indexed as a contiguous group -- are only compatible with an index sort when the sort is on the parent
documents, because a block must stay contiguous after the segment is reordered.

[source,java]
----
// https://lucene.apache.org/core/10_0_0/core/org/apache/lucene/index/IndexWriterConfig.html#setIndexSort(org.apache.lucene.search.Sort)
config.setIndexSort(new Sort(new SortField("timestamp", SortField.Type.LONG, true)));
// Requires a matching NumericDocValuesField("timestamp", ...) on every document.
----

== Why merging exists, and the policies that drive it

Segments are immutable and deletes are recorded out-of-band, so a busy index drifts toward many small
segments each carrying dead documents -- more files to open, more term dictionaries to seek, wasted
disk. Merging is the compaction that fixes this: a *merge policy* (`findMerges`) decides *which*
segments to combine, and a *merge scheduler* decides *when and on which threads* the merge runs.

[cols="1,3",options="header"]
|===
| Merge policy | Use

| `TieredMergePolicy` | The default. Groups segments into size tiers and merges non-adjacent segments within a tier, so it copes well with the irregular segment sizes a real workload produces.
| `LogByteSizeMergePolicy` | Merges only *adjacent* segments, which preserves insertion order on disk. Chiefly of interest when you need that ordering and are not using `setIndexSort`.
| `NoMergePolicy` | Never merges. For a one-shot build where you control merging manually, or a throwaway index.
| `FilterMergePolicy` | A pass-through wrapper to override one method of another policy (the base class of `SoftDeletesRetentionMergePolicy`, `OneMergeWrappingMergePolicy`, and others).
| `SoftDeletesRetentionMergePolicy` | Wraps another policy and holds back soft-deleted documents that a retention `Query` still selects (see soft deletes above).
|===

`TieredMergePolicy` 's main knobs: `setMaxMergedSegmentMB` (default ~5 GB) caps how large a merged
segment may get, which bounds worst-case merge cost; `setSegmentsPerTier` (default 10 in 10.0, lowered to 8 in later 10.x releases) sets how many
segments accumulate in a tier before a merge is triggered -- lower means fewer segments but more merge
work; `setDeletesPctAllowed` (default 20, min 5) is the index-wide dead-document percentage above
which the policy merges purely to reclaim deletes.

[source,java]
----
// https://lucene.apache.org/core/10_0_0/core/org/apache/lucene/index/TieredMergePolicy.html
var mergePolicy = new TieredMergePolicy();
mergePolicy.setMaxMergedSegmentMB(2_048);   // cap merged segments at 2 GB
mergePolicy.setSegmentsPerTier(10);
mergePolicy.setDeletesPctAllowed(15);       // merge sooner to keep deletes low
config.setMergePolicy(mergePolicy);
----

The scheduler is a separate choice. `ConcurrentMergeScheduler` (default) runs merges on background
threads; `setMaxMergesAndThreads(maxMerges, maxThreads)` sizes it (the default configuration prints
`maxThreadCount=-1, maxMergeCount=-1`, meaning it chooses from the CPU count), and `enableAutoIOThrottle()` turns on
I/O rate limiting, which is *off* in 10.x (`ioThrottle=false`). `SerialMergeScheduler` runs each
merge on the calling thread -- deterministic, used mostly in tests.

[source,java]
----
// https://lucene.apache.org/core/10_0_0/core/org/apache/lucene/index/ConcurrentMergeScheduler.html
var scheduler = new ConcurrentMergeScheduler();
scheduler.setMaxMergesAndThreads(4, 2);     // queue up to 4 merges, run 2 at once
config.setMergeScheduler(scheduler);
----

=== Seeing the policies at work

The effect of a policy is easiest to read as a segment count. The experiment flushed one document at a time, forty
times (so forty tiny segments exist before any merge), with a `SerialMergeScheduler` and compound files off, and
counted the segments left:

[cols="3,1",options="header"]
|===
| Policy | Segments after 40 flushes (10.0.0)

| `NoMergePolicy` | 40
| `TieredMergePolicy` (defaults) | 4
| `TieredMergePolicy` with `segmentsPerTier=2` and `maxMergeAtOnce=2` | 2
| `LogByteSizeMergePolicy` with `mergeFactor=3` | 2
|===

With no policy nothing is merged. The default tiered policy tolerates up to ten segments per tier, so forty equally
small flushes collapse into four. Lowering the tier width to two leaves only two segments but performs many more
merges to get there -- the extra write amplification is the price of fewer files. On Lucene 10.6.0 the same
default run left eight segments, because the default `segmentsPerTier` fell to 8 and the policy's *floor* segment
size rose from 2 MB to 16 MB (all of these test segments are far below it, so they are treated as equal in size).
The defaults of a given release can be read at any time by printing the policy and the config:

[source,text]
----
[TieredMergePolicy: maxMergeAtOnce=10, maxMergedSegmentMB=5120.0, floorSegmentMB=2.0,
 forceMergeDeletesPctAllowed=10.0, segmentsPerTier=10.0, noCFSRatio=0.1, deletesPctAllowed=20.0,
 targetSearchConcurrency=1]

IndexWriterConfig: ramBufferSizeMB=16.0, maxBufferedDocs=-1, openMode=CREATE_OR_APPEND,
 similarity=BM25Similarity, mergeScheduler=ConcurrentMergeScheduler: maxThreadCount=-1,
 maxMergeCount=-1, ioThrottle=false, codec=Lucene100, useCompoundFile=true, commitOnClose=true,
 indexSort=null, softDeletesField=null, readerPooling=true, perThreadHardLimitMB=1945
----

The `maxMergedSegmentMB=5120.0` line is the roughly-5 GB cap mentioned above, and `ramBufferSizeMB=16.0` is the
default flush trigger.

=== Index sorting on the catalog

With `setIndexSort(new Sort(new SortedNumericSortField("year", SortField.Type.INT, true)))` the eight books were
stored in descending year order *inside the segment*: reading documents by internal id returned years
`2018, 2015, 2015, 2014, 2010, 2008, 2006, 2005` for doc ids 0 to 7, although the books were added in catalog
order. A query sorted the same way can stop after its first N matches per segment. The sort field must be doc
values of the right kind: a `SortedNumericSortField` for an `IntField`, exactly as on
xref:database/lucene/documents-and-fields.adoc[Documents & fields].

=== Open modes

`OpenMode.APPEND` on a directory that holds no index throws `IndexNotFoundException`, which makes it useful as an
assertion that an index must already exist; the default `CREATE_OR_APPEND` creates one when absent, and `CREATE`
discards whatever is there.

== Hot backups with SnapshotDeletionPolicy

Copying an index directory while a writer is running can capture a half-merged state: a merge may delete files
you are about to copy. `SnapshotDeletionPolicy` solves this by letting the application *pin* a commit. While the
snapshot is held, every file of that commit is protected from deletion no matter what the writer does next; copy
those files, then release the snapshot and Lucene cleans them up.

[source,java]
----
// https://lucene.apache.org/core/10_0_0/core/org/apache/lucene/index/SnapshotDeletionPolicy.html
SnapshotDeletionPolicy sdp = new SnapshotDeletionPolicy(new KeepOnlyLastCommitDeletionPolicy());
IndexWriterConfig cfg = new IndexWriterConfig(analyzer).setIndexDeletionPolicy(sdp);
try (Directory dir = FSDirectory.open(liveDir); IndexWriter w = new IndexWriter(dir, cfg)) {
    // ... index and commit ...
    IndexCommit snapshot = sdp.snapshot();               // pins the last commit
    try {
        for (String file : snapshot.getFileNames()) {
            Files.copy(liveDir.resolve(file), backupDir.resolve(file));
        }
    } finally {
        sdp.release(snapshot);                           // unpin
        w.deleteUnusedFiles();                           // let Lucene reclaim the old files now
    }
}
----

The catalog test exercised exactly the hostile case: it committed four books, took the snapshot (`segments_1`, 19
files), then *added four more books, deleted one, called `forceMerge(1)` and committed again*. The live directory
now held 39 files and the newest commit was `segments_2`, yet every one of the 19 snapshot files was still on disk,
so the copy was consistent. After `release(snapshot)` and `deleteUnusedFiles()` none of them remained. The backup
directory opened as an index with `numDocs=4` (the state *at snapshot time*, not the later 7 documents), and
`CheckIndex` reported it clean. The same two calls are what Solr's and Elasticsearch's snapshot features are built on,
and the `lucene-replicator` module packages the idea for shipping commits to other machines (see
xref:database/lucene/testing-tools-and-modules.adoc[Testing, tools & modules]).

== Seeing inside the writer: infoStream

When flushing or merging behaves unexpectedly, ask the writer to narrate. `+IndexWriterConfig.setInfoStream(...)+`
takes an `InfoStream` that receives a message per event from components such as `IW` (the writer), `MS` (the merge
scheduler), `TMP` (the tiered policy) and `DW` (the document writer). Implement `message` and `isEnabled` to filter by
component; the default `InfoStream.NO_OUTPUT` discards everything.

[source,java]
----
InfoStream trace = new InfoStream() {
    @Override public void message(String component, String message) { System.out.println(component + ": " + message); }
    @Override public boolean isEnabled(String component) { return component.equals("IW") || component.equals("TMP"); }
    @Override public void close() {}
};
IndexWriterConfig cfg = new IndexWriterConfig(analyzer).setInfoStream(trace);
----

Twelve single-document flushes with a `SerialMergeScheduler` produced 229 messages from `IW`, `MS` and `TMP`.
The lines that matter, trimmed: `IW: now merge` (a merge was selected), `+IW: merge seg=_b ...+` (the merged segment
and its diagnostics), `IW: startCommit(): start` and then a line saying that it wrote the pending segments file
`pending_segments_1` (phase one of the commit), `IW: commit: done writing segments file` for `segments_1` (phase two),
and, on a second `commit()` with no changes, `IW:   skip startCommit(): no changes pending`.
The last line shows that a
commit with nothing to do is free. It is the first tool to reach for when "my index has hundreds of segments" or "my
commit takes seconds": the log shows which merge was picked and which flush produced which segment.

== Tuning merges for bulk load vs steady state

For a large one-shot load, fewer, larger flushes and deferred merging win: raise
`setRAMBufferSizeMB` (256 MB+), leave the default `TieredMergePolicy`, give
`ConcurrentMergeScheduler` more threads, and call `forceMergeDeletes()` (not `forceMerge(1)`) once at
the end only if the load produced many deletes. For a steady-state index taking continuous writes,
keep the defaults and let background merging run -- lowering `setSegmentsPerTier` or
`setDeletesPctAllowed` trades extra merge I/O for a leaner index and faster searches.
xref:database/solr/partial-updates-and-concurrency.adoc[Solr's partial-update and commit tuning] and
xref:database/elasticsearch/indexing-crud-and-bulk.adoc[Elasticsearch's bulk indexing] both sit
directly on top of this machinery.
