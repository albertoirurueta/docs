= Test framework, tools & a module map
:description: The lucene-test-framework (LuceneTestCase, BaseTokenStreamTestCase, newDirectory, RandomIndexWriter, randomized and Nightly testing), CheckIndex for corruption, IndexUpgrader with lucene-backward-codecs, the Luke index browser, and the benchmark, replicator and misc tool modules -- plus a one-line map of every Lucene module.
:keywords: apache lucene, lucene-test-framework, lucenetestcase, basetokenstreamtestcase, newdirectory, randomindexwriter, randomizedtesting, nightly, checkindex, indexupgrader, backward-codecs, luke, benchmark module, replicator module, indexmergetool, highfreqterms, getterminfo, lucene modules, nrt replication, tests.seed

include::partial$ai-disclaimer.adoc[]

Lucene ships far more than `lucene-core`. This page covers the tooling you reach for when working
*on* an index rather than *through* it -- the randomized test framework, the corruption checker, the
version upgrader, the Luke GUI, and the benchmark, replicator and misc modules -- and ends with a
one-line description of every module so you know what exists before you go looking.

The tools run on a small on-disk copy of the book catalogue (ten books, one segment). Every command
and output below was executed against Lucene 10.4.0 on JDK 21.

== The lucene-test-framework

`lucene-test-framework` is the harness Lucene tests itself with, published for you to use the same
way. Add it in test scope:

[source,xml]
----
<dependency>
  <groupId>org.apache.lucene</groupId>
  <artifactId>lucene-test-framework</artifactId>
  <version>10.4.0</version>
  <scope>test</scope>
</dependency>
<!-- https://lucene.apache.org/core/10_0_0/test-framework/index.html -->
----

Extend `LuceneTestCase` and you inherit a `RandomizedRunner` that seeds every run and randomizes the
codec, `Directory` implementation, locale, time zone, and merge policy, printing the seed on failure
so you can reproduce it with `+-Dtests.seed=...+`. `newDirectory()` returns a randomly chosen,
assertion-heavy `Directory` that also verifies every file is closed. `RandomIndexWriter` is a drop-in
for `IndexWriter` that randomly flushes, commits, and reopens mid-test to shake out
segment-boundary bugs.

[source,java]
----
// https://lucene.apache.org/core/10_0_0/test-framework/org/apache/lucene/tests/util/LuceneTestCase.html
public class TitleSearchTest extends LuceneTestCase {

  public void testFindsByTitle() throws Exception {
    try (Directory dir = newDirectory();                              // random Directory impl
         RandomIndexWriter w = new RandomIndexWriter(random(), dir)) { // random flush/commit
      Document doc = new Document();
      doc.add(new TextField("title", "the left hand of darkness", Field.Store.YES));
      w.addDocument(doc);
      try (IndexReader r = w.getReader()) {
        IndexSearcher s = newSearcher(r);                             // random concurrency slices
        assertEquals(1, s.count(new TermQuery(new Term("title", "darkness"))));
      }
    }
  }
}
----

The test class needs nothing but JUnit's launcher. Run from the command line with assertions enabled
(`-ea`; the framework assumes them):

[source,text]
----
java -ea -cp "target/classes:libs/*" org.junit.runner.JUnitCore lab.TitleSearchTest lab.MyAnalyzerTest
----

A second test in the same class asserts something false on purpose (it expects 2 hits for three
matching documents). The run reports the failure *and* everything needed to replay it:

[source,text]
----
NOTE: reproduce with: gradlew test --tests TitleSearchTest.testBrokenOnPurpose -Dtests.seed=E3AD0D4CB4790BC2 -Dtests.locale=nus-Latn-SS -Dtests.timezone=America/Nipigon -Dtests.asserts=true -Dtests.file.encoding=UTF-8
NOTE: test params are: codec=Asserting(Lucene104): {title=TestBloomFilteredLucenePostings(BloomFilteringPostingsFormat(PostingsFormat(name=Lucene104)))}, docValues:{}, maxPointsInLeafNode=1303, maxMBSortInHeap=5.109150719013414, sim=Asserting(RandomSimilarity(queryNorm=false): {title=IB SPL-D1}), locale=nus-Latn-SS, timezone=America/Nipigon
1) testBrokenOnPurpose(lab.TitleSearchTest)
java.lang.AssertionError: expected:<2> but was:<3>
	at __randomizedtesting.SeedInfo.seed([E3AD0D4CB4790BC2:F9E56E8B768A80]:0)
----

The reproduction line is written for Lucene's own Gradle build; the part that matters is the seed. Pass it
as a system property to the JVM that runs the tests (`+java -Dtests.seed=E3AD0D4CB4790BC2 ...+`, or Surefire's
`argLine` in Maven) and the same randomization comes back: re-running with that seed printed the same
`Asserting(Lucene104)` codec, the same bloom-filtered postings format and the same random similarity.
In that run the *codec*, the *similarity*, `maxPointsInLeafNode` (1303 instead of the default 512) and the
locale were all chosen at random: a passing run proves the code works across them, which is what makes
this a stronger test than a fixed configuration.

[mermaid]
....
flowchart LR
  S["random seed: a fresh one per run"] --> R["RandomizedRunner chooses codec, similarity, directory, locale, merge policy"]
  R --> T["test runs with those choices"]
  T --> P{"passes?"}
  P -->|yes| OK["repeat on every build: more combinations covered over time"]
  P -->|no| F["prints the seed and the chosen parameters"]
  F --> RE["rerun with tests.seed: identical choices, identical failure"]
  RE --> FIX["debug, fix, keep the test"]
....

For analyzer tests, `BaseTokenStreamTestCase` asserts a `TokenStream` produces an exact token /
offset / position sequence, and independently fuzzes it with random strings for `reset()` / `close()`
correctness:

[source,java]
----
// https://lucene.apache.org/core/10_0_0/test-framework/org/apache/lucene/tests/analysis/BaseTokenStreamTestCase.html
public class MyAnalyzerTest extends BaseTokenStreamTestCase {
  public void testTokens() throws Exception {
    Analyzer a = new StandardAnalyzer();               // no stop words by default
    assertAnalyzesTo(a, "The 2 QUICK Brown-Foxes",
        new String[] {"the", "2", "quick", "brown", "foxes"});
    checkRandomData(random(), a, 200);      // fuzz with 200 random inputs
    a.close();
  }
}
----

This test passed (`Tests run: 3, Failures: 1` for the two classes together, the one failure being the
deliberately broken test above). `assertAnalyzesTo` checks the terms; overloads add start and end offsets,
types, position increments and final offsets, which is how a custom filter is shown to keep offsets
valid. Tag slow or large tests `@Nightly` (or `@Slow`); they run only with `-Dtests.nightly=true`, keeping
the default build fast. The randomized engine underneath is documented at
https://github.com/randomizedtesting/randomizedtesting[randomizedtesting].

== CheckIndex: detect and triage corruption

`CheckIndex` walks every segment and verifies the term dictionary, postings, doc-values, points,
norms, and stored fields against their checksums. Run it from the command line against a *closed*
index. On the healthy catalogue index:

[source,text]
----
java -ea -cp lucene-core-10.4.0.jar org.apache.lucene.index.CheckIndex work/idx

Opening index @ work/idx

Checking index with threadCount: 10
0.00% total deletions; 10 documents; 0 deletions
Segments file=segments_1 numSegments=1 version=10.4.0 id=2p82gj461pe9lh6jbaj3hb83b
1 of 1: name=_0 maxDoc=10
    version=10.4.0
    codec=Lucene104
    compound=true
    numFiles=3
    size (MB)=0.005
    no deletions
    test: open reader.........OK [took 0.028 sec]
    test: check integrity.....OK [took 0.000 sec]

No problems were detected with this index.
----

To see what it reports for damage, one byte in the middle of the segment's compound file (`_0.cfs`) of a
*copy* of the index was flipped and the checker run again:

[source,text]
----
    test: open reader.........FAILED
    WARNING: exorciseIndex() would remove reference to this segment; full exception:
org.apache.lucene.index.CorruptIndexException: checksum failed (hardware problem?) : expected=e2dc31c actual=d2ec2fa1 (resource=...)
	at org.apache.lucene.codecs.CodecUtil.checkFooter(CodecUtil.java:441)
	...
WARNING: 1 broken segments (containing 10 documents) detected
WARNING: would write new segments file, and 10 documents would be lost, if -exorcise were specified
----

Every Lucene file ends with a checksum footer, so a flipped bit is caught by `checkFooter` as soon as the
file is opened; the message says what would happen (the whole segment would be dropped) without doing
it. `-exorcise` performs that removal and is destructive, so back up first. Pass `-verbose` for
per-field detail and `-segment _N` to check one segment.

[source,text]
----
# add -exorcise to drop unrecoverable segments (destructive; back up first)
java -ea -cp lucene-core-10.4.0.jar org.apache.lucene.index.CheckIndex /var/lib/app/index -verbose
----

Or call it from a health check and act on the result:

[source,java]
----
// https://lucene.apache.org/core/10_0_0/core/org/apache/lucene/index/CheckIndex.html
try (Directory dir = FSDirectory.open(path);
     CheckIndex checker = new CheckIndex(dir)) {
  CheckIndex.Status status = checker.checkIndex();
  if (!status.clean) {
    log.error("index has broken segments: {} docs would be lost", status.totLoseDocCount);
  }
}
----

A full check reads every byte of the index, so run it offline, on a replica, or after a restore -- not
on a hot path. For normal operation Lucene already verifies a segment's checksum when it is opened.

== IndexUpgrader and lucene-backward-codecs

Lucene reads indexes written by the *previous major version* only. `lucene-backward-codecs` carries the
read-only codecs that make that one-version bridge work. It is a *separate artifact*: `lucene-core` does
not pull it in, so add it explicitly to any application that must open an index from the previous
major version. `IndexUpgrader` rewrites every segment with the current codec so the index stays
readable after the *next* major upgrade.

The behaviour was checked on a real 9.12.0 index (three documents written with Lucene 9.12.0). With
`lucene-core` 10.4.0 alone it cannot be opened:

[source,text]
----
IndexFormatTooOldException: Format version is not supported (resource ...segments_1): Could not load codec 'Lucene912'.
An SPI class of type org.apache.lucene.codecs.Codec with name 'Lucene912' does not exist.  You need to add the
corresponding JAR file supporting this SPI to your classpath.  The current classpath supports the following
names: [Lucene104]. Did you forget to add lucene-backward-codecs.jar?.
----

With the backward-codecs jar on the classpath, the upgrader rewrites the segment and the result passes
the checker:

[source,text]
----
# One hop per major version: 8.x -> 9.x on Lucene 9, then 9.x -> 10.x on Lucene 10.
java -cp lucene-core-10.4.0.jar:lucene-backward-codecs-10.4.0.jar \
  org.apache.lucene.index.IndexUpgrader -verbose /var/lib/app/index

Segments file=segments_2 numSegments=1 version=10.4.0
    version=10.4.0
    codec=Lucene104
    diagnostics = {lucene.version=10.4.0, source=merge, ... mergeMaxNumSegments=1}
No problems were detected with this index.
----

[source,java]
----
// https://lucene.apache.org/core/10_0_0/core/org/apache/lucene/index/IndexUpgrader.html
new IndexUpgrader(dir).upgrade();
// module: https://lucene.apache.org/core/10_0_0/backward-codecs/index.html
----

The upgrader is a forced merge that rewrites every segment (`source=merge` above), so it needs free disk
space of about the size of the index and the index must not be open for writing. Skipping a major
version means exporting and reindexing from source instead.

[mermaid]
....
flowchart TD
  A["Existing index"] --> B{"Written by the previous major version?"}
  B -->|no, older| X["reindex from the source of truth"]
  B -->|yes| C{"Application must still read it?"}
  C -->|yes| D["add lucene-backward-codecs to the classpath"]
  D --> E["IndexUpgrader: rewrite all segments with the current codec"]
  E --> F["CheckIndex: verify"]
  C -->|no| F
  F --> G["safe for the next major upgrade"]
....

== Luke: browse an index by hand

The `luke` module is a Swing GUI for opening an index directory and inspecting it -- term
frequencies, per-field statistics, document contents, the effect of an analyzer on a string, and
ad-hoc queries. It ships in the Lucene *binary* distribution under `luke/`:

[source,text]
----
./luke.sh          # or luke.bat on Windows; opens a directory chooser
----

Use it to answer "what actually got indexed?" without writing a probe program. Module docs:
https://lucene.apache.org/core/10_0_0/luke/index.html. The command-line equivalents of its most
common questions are in the misc tools below.

== The benchmark module

`lucene-benchmark` runs repeatable indexing and search workloads described by an `.alg` task file --
handy for a local before/after when tuning. This file indexes 20,000 generated documents from a
tab-separated file, force-merges, and runs 2,000 searches:

[source,text]
----
# collection.alg
analyzer=org.apache.lucene.analysis.standard.StandardAnalyzer
directory=ByteBuffersDirectory
work.dir=work/bench/out
content.source=org.apache.lucene.benchmark.byTask.feeds.LineDocSource
docs.file=work/bench/docs.txt
content.source.forever=false
doc.stored=false
doc.tokenized=true
log.step=-1
query.maker=org.apache.lucene.benchmark.byTask.feeds.SimpleQueryMaker
task.max.depth.log=1

ResetSystemErase
{ "Populate"
    CreateIndex
    { "MAddDocs" AddDoc > : *
    ForceMerge(1)
    CloseIndex
}
OpenReader
{ "SearchSameRdr" Search > : 2000
CloseReader
RepSumByName
----

Run it with the module's `Benchmark` main class, with the module and its dependencies on the classpath:

[source,text]
----
java -cp "lucene-benchmark-10.4.0.jar:lucene-core-10.4.0.jar:..." org.apache.lucene.benchmark.byTask.Benchmark collection.alg

Operation          round   runCnt   recsPerRun        rec/s  elapsedSec
Populate               0        1        20003    23,340.72        0.86
MAddDocs_Exhaust       0        1        20000    37,453.18        0.53
ForceMerge(1.0)        0        1            1         4.59        0.22
SearchSameRdr_2000     0        1         2000    20,618.56        0.10
----

The first lines of the algorithm are properties, the rest is a task script: braces group tasks, `> :
N` repeats a task N times (`*` until the content source is exhausted), and `Rounds` repeats a whole
block with a changing parameter. The report is the real output of this file on a laptop: the 20,000
documents indexed at about 37,000 per second and searched at about 20,000 queries per second. These
numbers show how to read the report, not what your hardware will do; use the same file, with your data,
to compare two configurations on one machine. Module docs and the full task vocabulary:
https://lucene.apache.org/core/10_0_0/benchmark/index.html. For the project's own continuous numbers
see xref:database/lucene/performance-tuning.adoc[Performance tuning].

== The replicator module

In Lucene 10 `lucene-replicator` contains one thing: *near-real-time segment replication*, the
`org.apache.lucene.replicator.nrt` package. The older commit-based replication API (`Replicator`,
`LocalReplicator`, `IndexRevision`, `ReplicationClient` and the HTTP handler) existed in 9.x and was
removed in 10.0 -- the 10.0.0 jar no longer contains `IndexRevision` or `LocalReplicator`. Code written
against the old API does not compile on Lucene 10.

What remains is a pair of abstract building blocks. A `PrimaryNode` wraps the `IndexWriter` that takes the
writes; each time it flushes a new near-real-time point it publishes a `CopyState` (the segment infos and the
list of files that make up the new view). A `ReplicaNode` owns a `Directory`; when told about a new
point (`newNRTPoint`) it works out which files it lacks, copies only those through a `CopyJob`, and opens a
searcher over the result. Segments are immutable, so a replica copies each file once and merges happen
on the primary alone; the replica never re-indexes. The transport is *yours*: `ReplicaNode`
declares `newCopyJob`, `launch` and `sendNewReplica` abstract, and `PrimaryNode` declares
`preCopyMergedSegmentFiles`, so a deployment implements them over sockets, HTTP or a shared file system.
Lucene's own test suite contains a socket-based reference implementation.

[mermaid]
....
sequenceDiagram
  participant W as Writer
  participant P as PrimaryNode
  participant R as ReplicaNode
  W->>P: addDocument, then flushAndRefresh
  P->>P: new NRT point: SegmentInfos plus file list
  P-->>R: notify: new point version
  R->>R: newNRTPoint: compare file list with local files
  R->>P: copy only the missing files, checksummed
  P-->>R: file bytes
  R->>R: open searcher on the new segments
  Note over R: searches see the new documents
....

This is the building block a home-grown distributed setup uses; see
xref:database/lucene/near-real-time-search.adoc[Near-real-time search] for the reopen side. If you need
replication without writing a transport, that is the point to use Solr or Elasticsearch, which
implement it for you (see
xref:database/lucene/lucene-vs-solr-vs-elasticsearch-vs-opensearch.adoc[Lucene vs. Solr vs. Elasticsearch vs. OpenSearch]).

== Misc command-line tools

`lucene-misc` bundles small utilities:

* `IndexMergeTool` -- merge several index directories into one from the command line (`addIndexes`
  without writing code) --
  https://lucene.apache.org/core/10_0_0/misc/org/apache/lucene/misc/IndexMergeTool.html
* `HighFreqTerms` -- list the highest-frequency terms in a field, `-t` for total term frequency; a
  fast way to spot a missing stop-word list or a tokenizer mistake --
  https://lucene.apache.org/core/10_0_0/misc/org/apache/lucene/misc/HighFreqTerms.html
* `GetTermInfo` -- print the document frequency and total term frequency of one term --
  https://lucene.apache.org/core/10_0_0/misc/org/apache/lucene/misc/GetTermInfo.html

The index path comes *first* for `HighFreqTerms` and `GetTermInfo`; the usage lines are
`HighFreqTerms <index dir> [-t] [number_terms] [field]` and `GetTermInfo <index dir> field term`. On the
catalogue index:

[source,text]
----
java -cp lucene-core-10.4.0.jar:lucene-misc-10.4.0.jar org.apache.lucene.misc.HighFreqTerms work/idx 6

body:and 	 totalTF = 10 	 docFreq = 10
body:the 	 totalTF = 5 	 docFreq = 5
title:in 	 totalTF = 4 	 docFreq = 4
title:java 	 totalTF = 3 	 docFreq = 3
title:action 	 totalTF = 3 	 docFreq = 3
body:with 	 totalTF = 3 	 docFreq = 3

java -cp lucene-core-10.4.0.jar:lucene-misc-10.4.0.jar org.apache.lucene.misc.HighFreqTerms work/idx -t 4 title
title:in 	 totalTF = 4 	 docFreq = 4
title:java 	 totalTF = 3 	 docFreq = 3
title:action 	 totalTF = 3 	 docFreq = 3
title:to 	 totalTF = 1 	 docFreq = 1

java -cp lucene-core-10.4.0.jar:lucene-misc-10.4.0.jar org.apache.lucene.misc.GetTermInfo work/idx title java
title:java 	 totalTF = 3 	 doc freq = 3
----

The first listing is the diagnosis a missing stop-word list produces: `and`, `the`, `in` and `with` head
the list in a `StandardAnalyzer` index (which, since Lucene 8, has no stop words by default). `IndexMergeTool`
takes `+[OPTION...] <mergedIndex> <index1> <index2> [index3] ...+`; by default it only copies segments
according to the merge policy, and `-max-segments N` force-merges the result:

[source,text]
----
java -cp lucene-core-10.4.0.jar:lucene-misc-10.4.0.jar org.apache.lucene.misc.IndexMergeTool -max-segments 1 work/merged work/idx work/idx2
----

Without `-max-segments` the two ten-document indexes land in the output as two segments (`_0` and `_1`),
which is the quick way to see what `addIndexes` does. The module also holds the index-surgery classes
`IndexSplitter`, `PKIndexSplitter` and `IndexRearranger`, the `BPIndexReorderer` that renumbers documents
to improve compression and locality, `DirectIODirectory` and `HardlinkCopyDirectoryWrapper`, and
`SweetSpotSimilarity`.

== A map of every module

Every artifact is `org.apache.lucene:lucene-<name>`. Most projects need only `core` plus
`analysis-common` and `queryparser`.

[cols="1,3", options="header"]
|===
| Module | What it gives you

| `core` | The index, the analysis API, `Directory`, the core queries, BM25 scoring, and codecs.
| `analysis-common` | `StandardAnalyzer`, the language-neutral tokenizers, and most `TokenFilter` implementations.
| `analysis-icu` / `-kuromoji` / `-nori` / `-smartcn` / `-stempel` / `-morfologik` / `-opennlp` / `-phonetic` | ICU segmentation and folding; Japanese; Korean; Chinese; Polish (algorithmic); dictionary stemming; OpenNLP tokenizers; phonetic (Soundex / Metaphone) filters.
| `queryparser` | The classic query-string parser plus the flexible, standard, complex-phrase, and surround parsers.
| `queries` | `FunctionScoreQuery`, `MoreLikeThis`, `IntervalQuery` and other extra `Query` implementations (`DoubleValuesSource` itself lives in `lucene-core`).
| `sandbox` | Newer, not-yet-stable queries and features.
| `facet` | Taxonomy and `SortedSetDocValues` faceting, range facets, and drill-sideways.
| `grouping` | Result grouping and block / parent grouping.
| `join` | Query-time and index-time (block) joins.
| `highlighter` | The unified, plain, and postings-based highlighters.
| `suggest` | Autocomplete and "did you mean" -- `AnalyzingInfixSuggester`, FST suggesters, spellchecker.
| `expressions` | Compile a JavaScript expression into a `DoubleValuesSource` for sorting / scoring.
| `spatial-extras` / `spatial3d` | Geospatial shapes and prefix-tree strategies; 3D / geodesic maths.
| `misc` | `IndexMergeTool`, `HighFreqTerms`, `GetTermInfo`, index splitting and reordering, `DirectIODirectory`.
| `codecs` | Alternative and experimental codecs (bloom-filter postings, block terms, id-version and others).
| `backward-codecs` | Read-only codecs for the previous major version (a separate dependency, not pulled in by `core`).
| `classification` | k-NN and naive-Bayes document classifiers over an index.
| `memory` | `MemoryIndex` -- index one document in RAM to test it against many queries.
| `monitor` | Reverse search: register many queries, stream documents past them -- see xref:database/lucene/monitor-reverse-search.adoc[Monitor / reverse search].
| `replicator` | Near-real-time segment replication between a primary and replicas (`PrimaryNode`, `ReplicaNode`).
| `benchmark` | `.alg`-driven indexing and search benchmarks.
| `test-framework` | `LuceneTestCase`, `RandomIndexWriter`, `newDirectory()`, and the randomized runner.
| `luke` | The Swing index-inspection GUI.
| `demo` | The `IndexFiles` / `SearchFiles` sample programs.
|===

The full module list with Javadoc links is on https://lucene.apache.org/core/10_0_0/[the Lucene 10
documentation index].
