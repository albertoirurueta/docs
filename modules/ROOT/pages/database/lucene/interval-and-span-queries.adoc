= Interval & span queries
:description: Positional and proximity matching in Lucene with the modern Intervals / IntervalQuery API -- term, phrase, ordered, unordered, maxgaps, containing, containedBy, notContainingInterval, overlapping, before and after -- and the legacy SpanQuery family it supersedes.
:keywords: apache lucene, intervals, intervalquery, proximity search, phrase query, ordered interval, unordered interval, maxgaps, containing, containedby, notcontaining, overlapping, before, after, spanquery, spannearquery, positional matching, matches api, sloppy frequency

include::partial$ai-disclaimer.adoc[]

Proximity matching -- "these terms, near each other, in this order, but not when a third term sits
between them" -- is expressed in modern Lucene with the *Intervals* API: composable
`IntervalsSource` factory methods wrapped in a single `IntervalQuery`. It replaces the older
`SpanQuery` family with a smaller, nestable vocabulary that reads closer to the question being asked.

== What an interval is

A field indexed with positions records, for every term occurrence, its *position* in the text. An
*interval* is a pair of positions `[start, end]` that covers one match of a source. A single term
matches an interval of width one; `Intervals.ordered(a, b)` matches the smallest interval that begins
with an occurrence of `a` and ends with a later occurrence of `b`. A document can contain many
intervals, and every operator is a rule that builds new intervals from the intervals of its inputs.

Take the sentence `quick brown red fox` (positions 0 to 3). The source
`ordered(term(quick), term(fox))` produces one interval, `[0..3]`; the positions between its ends are
the *gaps*, here two. `maxgaps(n, source)` keeps only the intervals with at most `n` gaps, and the
filtering operators (`containing`, `notContaining`, `before`, and the rest) compare the intervals of two
sources with each other.

Intervals need `IndexOptions.DOCS_AND_FREQS_AND_POSITIONS` or higher on the field, which is what
`TextField` provides. A `StringField` (docs only) cannot be searched with intervals.

== The Intervals / IntervalQuery API

`org.apache.lucene.queries.intervals.Intervals` is a factory of static methods that each build an
`IntervalsSource`; `IntervalQuery(field, source)` turns one into a runnable `Query` scoped to a
single analyzed field. Sources nest freely, so a complex proximity constraint is built up from small
parts rather than a deep tree of span classes.

[cols="1,3",options="header"]
|===
| Factory | Matches an interval that...

| `Intervals.term("t")` | is a single occurrence of term `t`
| `Intervals.phrase("a", "b")` | is `a` immediately followed by `b` (adjacent, in order)
| `Intervals.ordered(a, b, c)` | contains `a`, `b`, `c` in that order, any gaps between
| `Intervals.unordered(a, b)` | contains both `a` and `b`, in any order
| `Intervals.maxgaps(n, src)` | is `src` with at most `n` non-matching positions inside it
| `Intervals.containing(big, small)` | is `big` and also wholly contains a match of `small`
| `Intervals.containedBy(small, big)` | is `small` and is wholly inside a match of `big`
| `Intervals.notContaining(a, b)` | is `a` that does NOT contain a match of `b`
| `Intervals.notContainedBy(a, b)` | is `a` that is NOT inside a match of `b`
| `Intervals.overlapping(a, b)` | is `a` whose span overlaps a match of `b`
| `Intervals.before(a, b)` / `Intervals.after(a, b)` | is `a` that appears before / after a match of `b`
|===

See the
https://lucene.apache.org/core/10_0_0/queries/org/apache/lucene/queries/intervals/package-summary.html[`org.apache.lucene.queries.intervals`
package Javadoc] for the full list (it also covers `atLeast`, `wildcard`, `prefix`, `regexp`,
`fixField`, `extend`, `or`, `analyzedText` and the `IntervalFunction` combinators). The module ships in
`lucene-queries`:

[source,xml]
----
<dependency>
  <groupId>org.apache.lucene</groupId>
  <artifactId>lucene-queries</artifactId>
  <version>10.4.0</version>
</dependency>
----

== A worked proximity example

The test corpus is eight short texts, chosen so that each operator separates them differently. The
field is analyzed with a `StandardAnalyzer`, so terms are lowercase:

[cols="1,4",options="header"]
|===
| Doc | Text

| d0 | the quick brown fox jumps over the lazy dog
| d1 | quick fox
| d2 | the quick lazy fox
| d3 | fox quick
| d4 | quick brown red fox
| d5 | quick one two three four fox
| d6 | the lazy dog watched a quick fox
| d7 | quick fox and a lazy dog and another quick brown fox
|===

Find documents where *"quick"* and *"fox"* occur within three positions of each other, in that
order, but only when *"lazy"* does not appear between them:

[source,java]
----
// https://lucene.apache.org/core/10_0_0/queries/org/apache/lucene/queries/intervals/Intervals.html
import org.apache.lucene.queries.intervals.Intervals;
import org.apache.lucene.queries.intervals.IntervalQuery;
import org.apache.lucene.queries.intervals.IntervalsSource;
import org.apache.lucene.search.Query;

IntervalsSource near =
    Intervals.maxgaps(3,
        Intervals.ordered(
            Intervals.term("quick"),
            Intervals.term("fox")));

IntervalsSource clean =
    Intervals.notContaining(near, Intervals.term("lazy"));

Query q = new IntervalQuery("body", clean);
----

Because the field is analyzed, pass already-analyzed term text (lowercased here to match a
`StandardAnalyzer` index); `Intervals.analyzedText(text, analyzer, field, maxGaps, ordered)` runs the
analyzer for you and also copes with analyzers that emit synonyms at the same position. Combine an
`IntervalQuery` with ordinary clauses through `BooleanQuery.Builder` the same way as any other `Query`:

[source,java]
----
import org.apache.lucene.search.BooleanClause.Occur;
import org.apache.lucene.search.BooleanQuery;

Query combined = new BooleanQuery.Builder()
    .add(new IntervalQuery("body", clean), Occur.MUST)
    .add(org.apache.lucene.document.IntField.newRangeQuery("year", 1990, 2000), Occur.FILTER)
    .build();
----

=== Every operator on the same corpus

Each line below is the real result of running one operator over the eight texts. Scores are in
parentheses and are explained in the next section.

[source,text]
----
phrase quick fox           -> d1(0.500) d6(0.500) d7(0.500)
ordered(quick,fox)         -> d7(0.600) d1(0.500) d6(0.500) d0(0.333) d2(0.333) d4(0.250) d5(0.167)
unordered(quick,fox)       -> d7(0.622) d1(0.500) d3(0.500) d6(0.500) d0(0.333) d2(0.333) d4(0.250) d5(0.167)
maxgaps(3,ordered)         -> d7(0.600) d1(0.500) d6(0.500) d0(0.333) d2(0.333) d4(0.250)
maxgaps(0,ordered)         -> d1(0.500) d6(0.500) d7(0.500)
notContaining(near,lazy)   -> d7(0.600) d1(0.500) d6(0.500) d0(0.333) d4(0.250)
containing(near,lazy)      -> d2(0.333)
containedBy(lazy,near)     -> d2(0.500)
before(quick,fox)          -> d7(0.667) d0(0.500) d1(0.500) d2(0.500) d4(0.500) d5(0.500) d6(0.500)
after(quick,fox)           -> d3(0.500) d7(0.500)
overlapping(near,lazy)     -> d2(0.333)
or(brown,red) ordered fox  -> d0(0.500) d4(0.500) d7(0.500)
analyzedText("Quick FOX", maxGaps 3, ordered) -> d7(0.600) d1(0.500) d6(0.500) d0(0.333) d2(0.333) d4(0.250)
----

Reading the table:

* `phrase` and `maxgaps(0, ordered)` are the same set -- a phrase is an ordered interval with no gaps.
* `ordered` finds d5 (four words between `quick` and `fox`); `+maxgaps(3, ...)+` drops it. `unordered`
  additionally finds d3, where `fox` comes first.
* `notContaining(near, lazy)` removes only d2, the one text where `lazy` sits *inside* the interval.
  d0 and d6 keep matching because their `lazy` lies *outside* it. `containing` and `overlapping`
  select exactly that document, and `containedBy(lazy, near)` returns the `lazy` interval itself.
* `before(quick, fox)` returns the intervals of `quick` that precede some `fox`; `after` returns the
  ones that follow one, which is why d7 appears in both (it has `quick` on both sides of its first `fox`).
* `or` is how a synonym-like alternative is expressed inside an ordered source.

=== Seeing the matched positions

An `IntervalQuery` supports the `Matches` API, so the exact interval of every match can be read back.
That is how a highlighter locates the text to mark, and it is the quickest way to debug a source that
matches more or less than expected:

[source,java]
----
Query q = searcher.rewrite(new IntervalQuery("body", Intervals.maxgaps(3, Intervals.ordered(quick, fox))));
Weight weight = searcher.createWeight(q, ScoreMode.COMPLETE_NO_SCORES, 1f);
for (LeafReaderContext ctx : reader.leaves()) {
    for (int doc = 0; doc < ctx.reader().maxDoc(); doc++) {
        Matches matches = weight.matches(ctx, doc);
        if (matches == null) continue;
        MatchesIterator it = matches.getMatches("body");
        while (it.next()) {
            System.out.println("d" + doc + ": [" + it.startPosition() + ".." + it.endPosition() + "]");
        }
    }
}
----

[source,text]
----
matches d0: [1..3]
matches d1: [0..1]
matches d2: [1..3]
matches d4: [0..3]
matches d6: [5..6]
matches d7: [0..1] [8..10]
----

d7 has two intervals, the adjacent pair at the start and `quick brown fox` at the end. d5 is absent:
its interval would span positions 0 to 5, too wide for three gaps.

== Scoring

`IntervalQuery` scores with a saturation function of the *sloppy frequency* of the document: every
interval contributes `1 / (gaps + 1)`, so a tight match counts more than a loose one, and the sum is
turned into a score with `pass:c[weight * S / (S + pivot)]` (pivot 1). The explanation of d1 for the phrase
query reads:

[source,text]
----
0.5 = Saturation function on interval frequency, computed as w * S / (S + k) from:
  1.0 = w, weight of this function
  1.0 = k, pivot feature value that would give a score contribution equal to w/2
  1.0 = S, the sloppy frequency of the interval query body:BLOCK(quick,fox)
----

That formula explains the table: width-two intervals give S = 1 and score 0.5; one gap gives S = 0.5
and 0.333; two gaps 0.25; four gaps 0.167. d7 has two intervals, S = 1 + 0.5 = 1.5, and scores
1.5 / 2.5 = 0.6. Notice what is *not* in the formula: term frequency across the corpus and field
length. An interval score reflects only how tight the matches are; it is not BM25. Combine it with a
scored `SHOULD` clause when relevance should also depend on idf, or use it as a `FILTER` and let the
text query rank (see xref:database/lucene/scoring-and-similarity.adoc[Scoring & similarity]).

== The legacy SpanQuery family

Before Intervals, positional matching used `SpanQuery`: `SpanTermQuery`, `SpanNearQuery`,
`SpanOrQuery`, `SpanNotQuery`, `SpanContainingQuery`, `SpanPositionRangeQuery`, and
`FieldMaskingSpanQuery` -- see the
https://lucene.apache.org/core/10_0_0/queries/org/apache/lucene/queries/spans/package-summary.html[`org.apache.lucene.queries.spans`
package Javadoc]. These classes still exist for backward compatibility and for a few edge cases
the Intervals API does not cover, but new code should use Intervals -- it composes without the
payload/position bookkeeping and expresses the common "within N, not containing X" shapes directly.

The two APIs select the same documents for the same shape. On the eight-text corpus:

[source,java]
----
SpanNearQuery near = new SpanNearQuery(new SpanQuery[] {
        new SpanTermQuery(new Term("body", "quick")),
        new SpanTermQuery(new Term("body", "fox")) }, 3 /* slop */, true /* in order */);
SpanNotQuery notLazy = new SpanNotQuery(near, new SpanTermQuery(new Term("body", "lazy")));
----

[source,text]
----
SpanNear(slop 3, ordered) -> d1(0.071) d7(0.048) d6(0.047) d2(0.040) d4(0.030) d0(0.026)
SpanNot(near, lazy)       -> d1(0.071) d7(0.048) d6(0.047) d4(0.030) d0(0.026)
----

Same six documents as `maxgaps(3, ordered)`, and the same five as `notContaining`. Only the scores
differ: spans use a BM25-style similarity that includes idf and length normalisation, intervals use the
saturation above.

[cols="1,1",options="header"]
|===
| SpanQuery | Intervals equivalent

| `SpanTermQuery(t)` | `Intervals.term(t)`
| `SpanNearQuery(clauses, slop, true)` | `+Intervals.maxgaps(slop, Intervals.ordered(...))+`
| `SpanNearQuery(clauses, slop, false)` | `+Intervals.maxgaps(slop, Intervals.unordered(...))+`
| `SpanOrQuery` | `+Intervals.or(...)+`
| `SpanNotQuery(include, exclude)` | `Intervals.notContaining(include, exclude)` (or `notContainedBy` for the reverse)
| `SpanContainingQuery` / `SpanWithinQuery` | `Intervals.containing` / `Intervals.containedBy`
| `SpanFirstQuery`, `SpanPositionRangeQuery` | no direct operator; filter positions with a custom `IntervalsSource`
| `FieldMaskingSpanQuery` | `Intervals.fixField`
|===

== Choosing a proximity operator

[mermaid]
....
flowchart TD
  A["Terms must be near each other"] --> B{"Strictly adjacent?"}
  B -->|yes| P["PhraseQuery or Intervals.phrase"]
  B -->|no| C{"Order matters?"}
  C -->|yes| O["Intervals.ordered inside maxgaps(n)"]
  C -->|no| U["Intervals.unordered inside maxgaps(n)"]
  O --> X{"Something must not sit between them?"}
  U --> X
  X -->|yes| N["wrap with notContaining(source, excluded)"]
  X -->|no| D["done"]
  N --> D
....

A plain `PhraseQuery` (with a slop) is the right tool when only adjacency or a simple slop is needed:
it is the most heavily optimised path. Reach for intervals as soon as the question contains "not
between", "inside", "before" or an or-group inside the phrase.

== Pitfalls

* *Stop words and position gaps.* An analyzer that removes stop words leaves holes in the positions.
  `phrase("quick", "fox")` does not match `quick the fox` when `the` was removed, because the removed
  word still occupies a position; build the source from the same analyzer with `analyzedText`.
* *Single-field only.* One `IntervalQuery` addresses one field. `Intervals.fixField` re-labels a
  source when intervals from two fields that share positions (for example a field and its stemmed
  copy) must be combined.
* *No positions, no intervals.* Fields indexed `DOCS` only fail the query at search time.
* *Wide intervals are slow.* An `unordered` source over very frequent terms with a large `maxgaps`
  enumerates many overlapping intervals; keep `maxgaps` as small as the question allows.
