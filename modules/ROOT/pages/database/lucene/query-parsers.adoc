= Query parsers
:description: Lucene 10.x query parsers -- the classic QueryParser syntax and its pitfalls, SimpleQueryParser, the flexible StandardQueryParser framework, ComplexPhraseQueryParser, and when to skip parsing entirely.
:keywords: apache lucene, query parser, queryparser, classic query parser, simplequeryparser, standardqueryparser, complexphrasequeryparser, multifieldqueryparser, leading wildcard, termrangequery, boolean operator precedence, lucene-queryparser

include::partial$ai-disclaimer.adoc[]

A query parser turns a user- or application-supplied string into a
xref:database/lucene/core-queries.adoc[`Query`] tree. Lucene ships several, in the
`lucene-queryparser` module, trading expressiveness against robustness against free-text input. This
page covers what each parser accepts, the traps in the classic one, and why programmatic code should
usually build `Query` objects directly. See
https://lucene.apache.org/core/10_0_0/queryparser/org/apache/lucene/queryparser/package-summary.html[the
lucene-queryparser package summary].

== The classic QueryParser

`org.apache.lucene.queryparser.classic.QueryParser` implements the familiar Lucene query-string
grammar:

[source,text]
----
term                     field:term            "a phrase"
+required   -prohibited   AND   OR   NOT   (operators are case-sensitive, uppercase)
grouping:                (quick OR fast) AND fox
wildcards:               te?t    test*        (leading ? / * rejected by default)
fuzzy:                   roam~   roam~1       (max 2 edits)
proximity:               "lucene search"~4
boost:                   lucene^4    "phrase query"^2
inclusive range:         mod_date:[20200101 TO 20201231]
exclusive range:         count:{1 TO 5}
regex:                   name:/joh?n(ath[oa]n)/
----

[source,java]
----
// https://lucene.apache.org/core/10_0_0/queryparser/org/apache/lucene/queryparser/classic/QueryParser.html
Analyzer analyzer = new StandardAnalyzer();
QueryParser parser = new QueryParser("text", analyzer);
parser.setDefaultOperator(QueryParser.Operator.AND);   // default is OR
parser.setAllowLeadingWildcard(false);                  // keep it false in production
Query q = parser.parse("quick brown +fox -sports");
----

=== Pitfalls

* *Query text is analyzed.* Each term (except wildcard, fuzzy, regex and range terms) is run through
  the field's analyzer, so the parser's field must map to the *same* analyzer used at index time. A
  term that the analyzer splits or drops (a stop word, a hyphenated token) produces a sub-query you
  did not type, or no clause at all.
* *Wildcard, prefix, fuzzy and range terms are normalized, not analyzed.* They are not tokenized, stemmed or
  stop-filtered, but they are passed through the analyzer's `normalize` method (lowercasing, accent folding), so
  `+Fox*+` becomes the prefix `+fox*+` and `+JAVA*+` becomes `+java*+` -- both matched the lowercased index in
  the catalog test. Because no stemming applies, `+searchin*+` does not become `+search*+`. *Regular expressions*
  are not normalized at all: `+title:/J.va/+` would look for an uppercase `J` that the index does not contain.
* *Leading wildcards are disabled* because `+*foo+` must enumerate the whole term dictionary. Turning
  them on with `setAllowLeadingWildcard(true)` can be very slow on a large field.
* *Ranges build a `TermRangeQuery`*, which does a byte-ordered string comparison. Over a numeric
  `IntPoint`/`LongPoint`/`DoublePoint` field that is simply wrong -- `[10 TO 9]` sorts "correctly" as
  strings. For numeric or date ranges either post-process the parsed range, subclass
  `+getRangeQuery(...)+` to emit `+IntPoint.newRangeQuery(...)+`, or do not parse the range at all.
* *Boolean operators are not real precedence.* `a AND b OR c` is not `(a AND b) OR c`; internally the
  parser rewrites `AND`/`OR`/`NOT` into `pass:c[+]`/`-` clause modifiers, and mixing them with explicit
  `pass:c[+]`/`-` in one query is a common source of surprise. Group explicitly with parentheses.
* *`MultiFieldQueryParser`* fans each term out across several fields as a `SHOULD` disjunction; it is
  convenient but produces large boolean queries and does not deduplicate scoring the way
  `DisjunctionMaxQuery` does.

[source,java]
----
// https://lucene.apache.org/core/10_0_0/queryparser/org/apache/lucene/queryparser/classic/MultiFieldQueryParser.html
Map<String, Float> boosts = Map.of("title", 3.0f, "body", 1.0f);
QueryParser mf = new MultiFieldQueryParser(new String[] {"title", "body"}, analyzer, boosts);
Query q = mf.parse("lucene query parser");
----

=== Running the classic parser on the catalog

The classic parser was run on the book catalog (field `title`, `StandardAnalyzer`, default operator `OR`). The
column on the right is the number of books the parsed query matches:

[cols="3,3,1",options="header"]
|===
| Input | Parsed as | Hits

| `Java Concurrency` | `title:java title:concurrency` | 3
| `java AND concurrency` | `pass:c[+title:java +title:concurrency]` | 1
| `+Fox*+` | `+title:fox*+` (a `PrefixQuery`) | 0
| `+JAVA*+` | `+title:java*+` | 3
| `+lucne~1+` | `+title:lucne~1+` (a `FuzzyQuery`) | 1
| `+title:/j.va/+` | a `RegexpQuery` | 3
| `year:[2014 TO 2016]` | `year:[2014 TO 2016]` as a `TermRangeQuery` | **0**
| `the` | `title:the` (a `TermQuery`; `StandardAnalyzer` keeps stop words) | 2
| `java AND concurrency OR solr` | `pass:c[+title:java +title:concurrency title:solr]` | 1
| `(java OR solr) AND NOT guide` | `pass:c[+(title:java title:solr) -title:guide]` | 4
| `+java^4 solr+` | `+(title:java)^4.0 title:solr+` | 4
|===

The zero for `year:[2014 TO 2016]` is the numeric-range trap in action: the parsed query *prints* correctly, but a
`TermRangeQuery` over a field that holds points finds no terms. The rows for `AND`/`OR` show the precedence
problem: `java AND concurrency OR solr` did not mean `(java AND concurrency) OR solr`; the parser produced two
`MUST` clauses and one optional `SHOULD`, so `Solr in Action` (which has neither `java` nor `concurrency`) was *not*
returned: only the single book containing both words matched. Grouping with parentheses removes the guesswork.
Three malformed inputs raise `ParseException` rather than returning a partial query:

[source,text]
----
*java         -> ParseException: Cannot parse '*java': '*' or '?' not allowed as first character in WildcardQuery
java AND (    -> ParseException: Cannot parse 'java AND (': Encountered "<EOF>" at line 1, column 10.
title:"java   -> ParseException: Cannot parse 'title:"java': Lexical error at line 1, column 12.
----

Calling `parser.setAllowLeadingWildcard(true)` makes `+*ava+` parse into a `WildcardQuery` that matched the three Java
books by enumerating the entire term dictionary. User-typed text that contains syntax characters (`pass:c[+ - ( ) : [ \]]`
and so on) should go through `+QueryParser.escape(...)+` first: escaping `pass:c[C++ (in action): [2nd\] ed.]` produced a plain
five-clause `title:c title:in title:action title:2nd title:ed` query instead of an exception.

[mermaid]
....
flowchart LR
    I["user string: title:Java AND conc*"] --> L["JavaCC lexer and grammar"]
    L --> T1["field + term: title, Java"]
    L --> T2["wildcard term: conc*"]

=== MultiFieldQueryParser on the catalog

With `title` boosted 3 and `description` 1 over the fields `title` and `description`, the string `lucene search` produces
`+((title:lucene)^3.0 (description:lucene)^1.0) ((title:search)^3.0 (description:search)^1.0)+`: each word becomes a
`SHOULD` group over both fields, and the two groups are `SHOULD`. With the default operator set to `AND` the string
becomes `pass:c[+(title:lucene description:lucene) +(title:search description:search)]` and matches two books instead of
three. An explicit field prefix wins: `title:lucene search` searches `title` for the first word only, and boosts
only the second. For "best field wins" scoring, wrap the per-field clauses in a `DisjunctionMaxQuery` yourself
instead of relying on this parser (see xref:database/lucene/core-queries.adoc[Core queries]).

=== Extending the classic parser: numeric ranges and exact numbers

The classic parser is meant to be subclassed: every clause it builds goes through a protected factory method such
as `getRangeQuery` or `getFieldQuery`, which you can override. The usual reason is numeric fields. The subclass below
sends the `year` field to point queries (`IntField.newRangeQuery` and `newExactQuery`) and leaves every other field to
the default behaviour:

[source,java]
----
class NumericAwareParser extends QueryParser {
    NumericAwareParser(String field, Analyzer analyzer) { super(field, analyzer); }

    @Override
    protected Query getRangeQuery(String field, String lower, String upper,
                                  boolean startInclusive, boolean endInclusive) throws ParseException {
        if (field.equals("year")) {
            int lo = lower == null || lower.equals("*") ? Integer.MIN_VALUE
                   : Integer.parseInt(lower) + (startInclusive ? 0 : 1);
            int hi = upper == null || upper.equals("*") ? Integer.MAX_VALUE
                   : Integer.parseInt(upper) - (endInclusive ? 0 : 1);
            return IntField.newRangeQuery("year", lo, hi);
        }
        return super.getRangeQuery(field, lower, upper, startInclusive, endInclusive);
    }

    @Override
    protected Query getFieldQuery(String field, String text, boolean quoted) throws ParseException {
        if (field.equals("year")) return IntField.newExactQuery("year", Integer.parseInt(text));
        return super.getFieldQuery(field, text, quoted);
    }
}
----

Run on the catalog (default field `title`):

[cols="3,3,1",options="header"]
|===
| Input | Parsed as | Hits

| `year:[2014 TO 2016]` | `year:[2014 TO 2016]` | 3
| `+year:{2014 TO 2016}+` | `year:[2015 TO 2015]` | 2
| `+year:[* TO 2006]+` | `year:[-2147483648 TO 2006]` | 2
| `year:2018` | `year:[2018 TO 2018]` | 1
| `java AND year:[2005 TO 2006]` | `pass:c[+title:java +year:[2005 TO 2006\]]` | 2
|===

The same strings parsed by the stock classic parser matched nothing for the range inputs. Two details are easy to
get wrong: an *exclusive* bound must be converted to an inclusive one for integer points (`+{2014 TO 2016}+` is
`[2015 TO 2015]`), and a malformed number raises `NumberFormatException` from the subclass unless you catch it
and rethrow a `ParseException`. For dates, convert the user's text to epoch milliseconds the same way.

== SimpleQueryParser -- never throws

`org.apache.lucene.queryparser.simple.SimpleQueryParser` is built for raw end-user input: it never
raises a parse exception. Unbalanced quotes, a trailing operator, a stray bracket -- all are treated
as literal text. Operators are punctuation (`pass:c[+]` and, `|` or, `-` not, `"` phrase, `+*+` prefix, `+~N+`
fuzzy/slop, `(` `)` grouping) and each can be individually disabled with a flags bitmask.

[source,java]
----
// https://lucene.apache.org/core/10_0_0/queryparser/org/apache/lucene/queryparser/simple/SimpleQueryParser.html
Map<String, Float> weights = Map.of("title", 2.0f, "body", 1.0f);
SimpleQueryParser sqp = new SimpleQueryParser(analyzer, weights);
sqp.setDefaultOperator(BooleanClause.Occur.MUST);      // space means AND
Query q = sqp.parse("lucene +search -legacy \"exact phrase\" quick~2");
// A version disabling prefix and fuzzy operators:
SimpleQueryParser restricted = new SimpleQueryParser(analyzer, weights,
    SimpleQueryParser.AND_OPERATOR | SimpleQueryParser.PHRASE_OPERATOR);
----

Behaviour on the catalog (`title` and `description` weighted 2 and 1, default operator `MUST`):

[cols="3,4",options="header"]
|===
| Input | Result

| `pass:c[lucene +search -legacy]` | three required groups: `lucene`, `search`, and a negated `legacy`, each over both fields; 2 hits
| `"exact phrase` (unbalanced quote) | no exception: parsed as the two required words `exact` and `phrase`
| `java \| solr` | optional `java` or `solr` over both fields; 4 hits
| `(unbalanced` | no exception: treated as the single word `unbalanced`
| `title:java` | the colon is *not* a field operator here: it searched for the literal text `title:java` and found nothing
|===

Two consequences matter in practice. First, nothing the user types can raise an exception, which is exactly what
a search box needs. Second, field-qualified syntax is simply unavailable: the field set is fixed by the weights map
you pass, and a user cannot target another field. With the flags `AND_OPERATOR | PHRASE_OPERATOR`
only, `pass:c[luc* java~1 +x]` turned the disabled operators back into plain text (`luc`, `java`, `1`) and kept `pass:c[+x]` required.

== StandardQueryParser -- the flexible framework

`org.apache.lucene.queryparser.flexible.standard.StandardQueryParser` accepts the same syntax as the
classic parser but is built on the *flexible query parser* framework: a pipeline of syntax parser ->
`QueryNode` tree -> configurable processor pipeline -> builder. You subclass or reconfigure one stage
instead of overriding `getXxxQuery` methods, which makes it the right base for a house query language
or for changing how ranges/points are built globally.

[source,java]
----
// https://lucene.apache.org/core/10_0_0/queryparser/org/apache/lucene/queryparser/flexible/standard/StandardQueryParser.html
StandardQueryParser sp = new StandardQueryParser(analyzer);
sp.setDefaultOperator(StandardQueryConfigHandler.Operator.AND);
sp.setAllowLeadingWildcard(false);
// Point-typed numeric ranges: register a PointsConfig per numeric field.
Map<String, PointsConfig> points = Map.of(
    "price", new PointsConfig(new DecimalFormat(), Integer.class));
sp.setPointsConfigMap(points);
Query q = sp.parse("title:lucene AND price:[10 TO 100]", "body");
----

The flexible `StandardQueryParser` parsed `title:java AND year:[2005 TO 2006]` into
`pass:c[+title:java +year:[2005 TO 2006\]]` and matched two books *because* a `PointsConfig` was registered for
`year`: the same text through the classic parser produced a `TermRangeQuery` and matched none. A bare `year:2018` became
the point query `year:[2018 TO 2018]` and matched one book. This single registration is the reason to prefer the
flexible parser when users type numeric ranges.

    P --> T["QueryNode tree"]
    T --> PR["processor pipeline: lowercase, wildcard handling, points config, boost, ..."]
    PR --> T2["processed QueryNode tree"]
    T2 --> BL["builder pipeline"]
    BL --> Q["Lucene Query"]

== ComplexPhraseQueryParser

`org.apache.lucene.queryparser.complexPhrase.ComplexPhraseQueryParser` allows wildcard, prefix, fuzzy
and range sub-clauses *inside* a quoted phrase, which the classic parser forbids -- useful for
"these alternatives, in order, close together".

[source,java]
----
// https://lucene.apache.org/core/10_0_0/queryparser/org/apache/lucene/queryparser/complexPhrase/ComplexPhraseQueryParser.html
ComplexPhraseQueryParser cp = new ComplexPhraseQueryParser("text", analyzer);
cp.setInOrder(true);
Query q = cp.parse("\"(john jon jonathan) smith*\"~3");
----

On the catalog, `+"(java solr) in*"+` (with `setInOrder(true)`) matched `Solr in Action`, because the first position
accepts either `java` or `solr` and the second is a prefix; `+"jav* concurr*"~2+` matched
`Java Concurrency in Practice`. The classic parser has no way to say either: it parsed `+"jav* concurr*"+` into
the plain phrase `title:"jav concurr"` (the wildcards were stripped by the analyzer) and found nothing.

== Just build the Query

For anything programmatic -- a REST filter, a saved search, a facet drill-down -- skip parsing.
Constructing xref:database/lucene/core-queries.adoc[`Query` objects] directly removes the analyzer
round-trip surprises, is not vulnerable to syntax injection from user data, and lets the compiler
check the query shape. Reserve the parsers for text a human actually typed into a search box.

== From string to Query tree

Assuming field `text` uses `StandardAnalyzer` (lower-cases, splits on whitespace/punctuation, keeps
stop words in modern defaults) and the classic `QueryParser` with default operator `OR`:

[cols="2,2,3",options="header"]
|===
| User string | After analysis | Resulting Query

| `Quick Brown` | `quick`, `brown` | `text:quick text:brown` (two `SHOULD` clauses)
| `pass:c[+Quick brown]` | `quick`, `brown` | `pass:c[+text:quick text:brown]`
| `+"Quick Brown Fox"~2+` | `quick brown fox` | `PhraseQuery` on `text`, slop 2
| `quick AND brown` | `quick`, `brown` | `pass:c[+text:quick +text:brown]`
| `title:Quick brown` | `quick` (title), `brown` (text) | `title:quick text:brown`
| `+Qu?ck bro*+` | not analyzed | `WildcardQuery(text:qu?ck)` `PrefixQuery(text:bro)`
| `+roam~1+` | not analyzed | `FuzzyQuery(text:roam, maxEdits=1)`
| `mod_date:[20200101 TO 20201231]` | not analyzed | `TermRangeQuery` on `mod_date` (byte-ordered, *not* a point range)
| `the` (a stop word, if the analyzer drops it) | (empty) | no clause -> `MatchNoDocsQuery`
|===
