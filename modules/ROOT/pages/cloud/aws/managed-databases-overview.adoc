The running scenario, Bookshelf, uses two of these services: an Aurora PostgreSQL Serverless v2 cluster

`bookshelf-cache`. The question this page answers is how to arrive at choices like those.

== Choosing an engine first, a service second

Pick the data model and access pattern before looking at AWS service names. That decision is engine-neutral and is
covered in xref:database/choosing-the-right-database.adoc[], which compares relational, document, search, vector,
graph and other categories and walks through the questions that decide it. Only once the engine family is fixed does
the AWS question arise: which of the first-party service, a Marketplace SaaS offering or a self-managed deployment
fits your team. Each row of the next table states which of those three kinds the option is.

The decision map groups the same options by how much of the stack AWS operates for you:

image::aws-managed-databases-decision-map.svg["Decision map from each database engine on this site to its AWS option, in three columns: first-party AWS service, Marketplace SaaS billed through AWS, and self-managed on EKS or EC2",width=900]

Marketplace SaaS databases run in the partner's own AWS accounts, not in yours. You subscribe in the AWS Marketplace
console, the charges appear on your AWS bill, and you connect over the public internet or, where the vendor offers it,
over AWS PrivateLink so that traffic stays on the AWS network. Self-managed deployments run in your account: you own
patching, backups, upgrades and failover, but you also get the full engine feature set and a free choice of version.

== Common concerns across every engine

Each page linked from the map covers engine-specific setup and tuning. The concerns below apply, in some form, to every
first-party option, and several apply to the self-managed ones as well.

=== Networking: subnet groups and private access

RDS, Aurora, DocumentDB, Neptune and ElastiCache are placed into your VPC through a *subnet group* (a DB subnet group,
an ElastiCache subnet group and so on): a named set of subnets, in at least two Availability Zones, in which the service
may place nodes. Use private subnets and leave "publicly accessible" off. Access is then controlled by a VPC security
group that allows the database port only from the application's security group, not from address ranges. DynamoDB,
S3 Vectors and the other serverless services have no subnet group; you reach them through a gateway or interface VPC
endpoint (see xref:cloud/aws/vpc-networking.adoc[]). From a laptop, reach a private database through a bastion with Session
Manager port forwarding or through Client VPN (xref:cloud/aws/vpn-and-hybrid-connectivity.adoc[]) rather than by making it public.

Creating the subnet group is usually the first CLI step, because the database create call refers to it by name:

[source,bash]
----
export AWS_REGION=us-east-1
# Subnet IDs of two private subnets in different Availability Zones (placeholders).
aws rds create-db-subnet-group \
  --db-subnet-group-name bookshelf-private \
  --db-subnet-group-description "Private subnets for Bookshelf databases" \
  --subnet-ids subnet-0aaaaaaaaaaaaaaaa subnet-0bbbbbbbbbbbbbbbb
----

Derived from the
https://docs.aws.amazon.com/cli/latest/reference/rds/create-db-subnet-group.html[AWS CLI Command Reference -- rds create-db-subnet-group]
page. The ID values are placeholders.

=== Authentication: IAM database authentication and secrets

Two mechanisms replace a long-lived password in application configuration:

* *IAM database authentication* (RDS and Aurora for MySQL and PostgreSQL, Aurora DSQL, ElastiCache and MemoryDB, and
  DocumentDB where supported) lets the application's IAM role request a short-lived token and present it in place of a
  password. The role is an ECS task role, a Lambda execution role, an EKS Pod Identity role or an instance profile, as
  explained in xref:cloud/aws/identity-and-access.adoc[]. The token is generated locally (for RDS, with
  `aws rds generate-db-auth-token`) and is valid for a few minutes; it only authenticates the connection, so a pooled
  connection that outlives the token keeps working.
* *Secrets Manager-managed master passwords*: create RDS and Aurora databases with `--manage-master-user-password` and
  Secrets Manager creates, stores and rotates the master password for you, encrypted with a KMS key you choose. Older
  guides hand-build a rotation Lambda for this; that is no longer necessary for the master user. Application users that
  the engine does not manage still need ordinary secrets and rotation.

DynamoDB has no database password at all: access is IAM policy only, which is one reason it is a good fit for roles-only
workloads. For secret storage, rotation and the KMS key side of this, see xref:cloud/aws/secrets-manager-and-kms.adoc[];
for Spring Boot configuration import, see xref:backend/springboot/configuration-and-profiles.adoc[]. Marketplace SaaS and
self-managed engines use their own users and API keys, so keep those in Secrets Manager as well.

=== Backups and point-in-time recovery

[cols="2,3,3"]
|===
| Service | Automated backups / PITR | Notes

| RDS, Aurora
| Automated backups with a retention period you set (up to 35 days) and restore to any second in that window, into a new DB instance or cluster.
| Manual snapshots are kept until you delete them and can be copied across Regions and accounts. Restores always create a new database; they do not rewind the existing one.

| DynamoDB
| Point-in-time recovery, opt-in per table, with a configurable window of 1 to 35 days.
| On-demand backups, export to S3 and AWS Backup are separate mechanisms.

| DocumentDB, Neptune
| Continuous backup to S3 with PITR within the retention period, like Aurora.
| Manual cluster snapshots for longer retention.

| ElastiCache, MemoryDB
| Snapshots on a schedule (ElastiCache) or a Multi-AZ transaction log (MemoryDB, which is durable).
| An in-memory cache is normally rebuildable; treat backups as a convenience, not as the system of record.

| Self-managed on EKS/EC2
| None by default.
| Use the engine's own dump or snapshot tooling, or EBS snapshots through AWS Backup, and test the restore.
|===

AWS Backup can sit on top of most of these services to give one backup plan, retention policy and cross-Region copy for
the whole estate. Backups are encrypted with the same KMS key as the source unless you specify another.

=== High availability: Multi-AZ, replicas and global replication

* *Multi-AZ* keeps a standby or additional copies in other Availability Zones and fails over automatically. For RDS
  there are two shapes: a Multi-AZ DB instance (one synchronous standby that does not serve reads) and a Multi-AZ DB
  cluster (a writer plus two readable standbys in three AZs). Aurora's storage is always spread over three AZs, and its
  high availability then depends on having a reader instance to promote. DocumentDB, Neptune, ElastiCache, MemoryDB and
  OpenSearch Service have their own Multi-AZ options. DynamoDB and the serverless services replicate across AZs
  without a setting.
* *Read replicas* scale read traffic and can be placed in another Region for disaster recovery. They replicate
  asynchronously, so a promoted replica may lack the last writes.
* *Global replication* (Aurora Global Database, DynamoDB global tables, ElastiCache Global Datastore, DocumentDB
  global clusters, Aurora DSQL multi-Region clusters) puts the data in several Regions with different consistency and
  write-location trade-offs; read the page for each before choosing.

Multi-AZ protects against an AZ failure, not against bad data or an accidental `DROP TABLE`; that is what the backups
above are for. The Region and Availability Zone model is in xref:cloud/aws/global-infrastructure.adoc[].

=== Encryption

Encryption at rest with KMS is available on every first-party service above and is the default or can be switched on
at creation: for RDS and Aurora you must choose it when the database is created, because an unencrypted database cannot
be encrypted in place (take a snapshot, copy it with a KMS key, restore the copy). Encryption in transit is TLS: download
the service's CA bundle (RDS, DocumentDB) or enable in-transit encryption (ElastiCache, MemoryDB) and require TLS in the
client, for example `sslmode=verify-full` for PostgreSQL. Choosing between AWS-owned, AWS-managed and customer managed
KMS keys, key policies and rotation is in xref:cloud/aws/secrets-manager-and-kms.adoc[].

=== Maintenance, versions and Extended Support

Managed services patch inside a maintenance window you choose, and apply minor-version upgrades automatically if you
allow them; major-version upgrades are yours to schedule (RDS and Aurora Blue/Green Deployments make that safer). Each
engine major version has a standard-support end date. After it, RDS and Aurora (and similar for ElastiCache) keep the
database running but charge an *Extended Support* fee per vCPU-hour, rising over time, unless you upgrade first. Two
dates relevant today: PostgreSQL 13 left standard support on 2026-02-28, and MySQL 8.0 standard support ended on
2026-07-31. Check the release calendars on the RDS and Aurora pages before choosing a version, and follow
xref:cloud/aws/rds.adoc[] and xref:cloud/aws/aurora.adoc[] for upgrade mechanics.

=== Cost drivers

Every service bills differently, but the same handful of drivers recur: compute (instance hours, ACUs, node hours or
request units), storage and provisioned IOPS, backup storage beyond the free allowance, cross-AZ and cross-Region data
transfer, and Extended Support. Serverless options trade a higher unit cost for paying only while in use; provisioned
options with reserved capacity are cheaper for steady load. Use the official pricing pages and the AWS Pricing
Calculator rather than hard-coding numbers from a guide: prices differ by Region and change.

== Migrating an existing database to AWS

AWS Database Migration Service (DMS) moves data between engines and from on premises or other clouds into AWS. It has
three parts that are useful to know apart:

* *DMS replication* does a one-time full load, ongoing change data capture (CDC), or both, from a source endpoint to a
  target endpoint. DMS Serverless provisions and scales the replication capacity automatically instead of you choosing
  a replication instance.
* *DMS Schema Conversion* assesses and converts schemas and code objects when the source and target engines differ (for
  example Oracle to PostgreSQL). The older AWS Schema Conversion Tool (SCT) is a downloadable alternative.
* *DMS Fleet Advisor* inventories an on-premises estate to help pick migration candidates.

For a same-engine move, the engine's native tools are often simpler: `pg_dump` and `pg_restore` for PostgreSQL,
`mysqldump` or native replication for MySQL, `mongodump` and `mongorestore` for MongoDB-compatible targets, and
snapshot import where the service supports it. Whichever path you pick, assess compatibility first, rehearse the cutover,
and measure replication lag before switching traffic. Older guides show the standalone Schema Conversion Tool as the
only way to convert schemas; the managed DMS Schema Conversion is the current option.
