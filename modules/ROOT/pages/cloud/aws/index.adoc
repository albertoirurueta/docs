Welcome to the AWS reference. It documents Amazon Web Services for practitioners who work from the AWS
Management Console and the AWS CLI -- provisioning resources, wiring them together, and operating what results --
rather than from the perspective of a certification-style conceptual overview. It is written for developers and
operators who already build software (the rest of this site covers the Java, web and database sides) and now need to
run it on AWS. Examples across this section target AWS CLI v2 (the 2.37 line), AWS CDK v2 (`aws-cdk-lib` 2.272), AWS
SAM CLI 1.166, `eksctl` 0.230 and Amazon EKS Kubernetes 1.36; this baseline was re-verified as current on 2026-10-01,
and each page also names the service-specific versions it depends on, since AWS ships new capabilities to individual
services on its own schedule. Prices are never quoted: each page describes the pricing model and cost drivers and
links the dated official pricing page.

== The Bookshelf scenario

Most pages in this section build up one running example, *Bookshelf*: a static web front end, a `catalog-api`
(Spring Boot), an `orders-api` and a `notifier` worker that sends order-confirmation emails. It is the same
application as in the xref:cloud/azure/index.adoc[Azure section], so the two clouds can be compared side by side.
Every resource follows one naming convention, so a command copied from one page composes with a command copied from
another:

[cols="1,2", options="header"]
|===
| Concern | Name / value

| Region
| `us-east-1` (a placeholder -- pick the region closest to the reader; CloudFront certificates must be in `us-east-1`)

| Account ID
| placeholder `111122223333`, read in scripts as `$ACCOUNT_ID` with `aws sts get-caller-identity --query Account --output text`

| ECR repositories
| `bookshelf/catalog-api`, `bookshelf/orders-api`, `bookshelf/notifier`

| ECS
| cluster `bookshelf`; services `catalog-api` (Express Mode first, then a full service behind the ALB `alb-bookshelf`) and `orders-api`

| Lambda
| `notifier` (SQS-triggered), `thumbnailer` (S3-triggered)

| S3
| `bookshelf-web-<account-id>` (static site, private, reached through OAC), `bookshelf-uploads-<account-id>`

| CloudFront
| distribution `bookshelf-cdn`

| Databases
| Aurora PostgreSQL Serverless v2 `bookshelf-catalog` (database `catalog`); DynamoDB table `Orders` (or DocumentDB `bookshelf-orders` as the MongoDB variant); ElastiCache for Valkey serverless `bookshelf-cache`

| Secrets and configuration
| Secrets Manager `bookshelf/catalog/db`; Parameter Store `/bookshelf/*`; AppConfig application `bookshelf`

| EKS
| cluster `bookshelf-eks` (created with `eksctl`, workloads use Pod Identity)

| API Gateway
| HTTP API `bookshelf-api`

| VPN
| Client VPN endpoint `cvpn-bookshelf`

| SES
| domain `example.com` (placeholder), sender `no-reply@example.com`

| Java package
| `com.example.bookshelf`

| Shell variables
| `AWS_REGION`, `ACCOUNT_ID`, `CLUSTER`, `BUCKET` and so on -- never real IDs or keys
|===

Bookshelf starts on ECS (the `bookshelf` cluster, covered in the Compute group below), where `catalog-api` is first
deployed with ECS Express Mode and then as a full Fargate service, and later moves its services onto an EKS cluster
(`bookshelf-eks`), covered in xref:cloud/aws/eks-clusters.adoc[] and xref:cloud/aws/eks-microservices.adoc[]. The
figure below shows Bookshelf's *end state*, once every group's pages have been applied: CloudFront in front of a
private S3 bucket and an API Gateway HTTP API, the EKS-hosted services behind an Application Load Balancer, the
databases, secrets and configuration reached from private subnets, event-driven Lambda functions and SES for email,
an admin VPN path, and CloudWatch watching all of it. It is not the architecture a reader has running after just the
Compute pages -- see xref:cloud/aws/choosing-a-compute-service.adoc[] and xref:cloud/aws/ecs-and-fargate.adoc[] for the
earlier, ECS-only stage.

image::aws-bookshelf-architecture.svg[Bookshelf end-state architecture on AWS: CloudFront in front of a private S3
static site and an API Gateway HTTP API that reaches an Application Load Balancer in a VPC, catalog-api and
orders-api running on EKS in private subnets, Aurora PostgreSQL, DynamoDB, ElastiCache and the configuration and
secrets services in isolated data subnets, an SQS queue feeding the notifier Lambda function that sends email through
SES, a thumbnailer Lambda function triggered by S3, a Client VPN endpoint for admin access, ECR for images, and
CloudWatch observing everything]

== Reading path

Read this section foundations first -- the cloud model, accounts, regions, organizations, identity and
infrastructure as code -- then compute, where Bookshelf's services first get deployed. From there, storage and CDN
put the static front end and its assets somewhere durable and fast to serve, and managed databases give `catalog-api`
and `orders-api` somewhere to persist data. Security and runtime configuration then centralize the secrets and
settings every earlier page referenced loosely, before networking, gateways and VPN lock the whole thing behind a
private network and a proper API front door. Email and integration wire `notifier` up to the outside world, and
operations, governance and beyond closes the loop: monitoring, cost, compliance, migration paths and the developer
tooling that ties CI/CD back to everything above. A reader who only needs one topic can jump straight to its page;
each page states which earlier pages it assumes.

== Coming from Azure

Readers who know the xref:cloud/azure/index.adoc[Azure section] can use the table below to find the AWS page that covers
the closest counterpart. The mapping is a starting point, not an equivalence: the services differ in defaults,
limits, pricing and identity model, and each AWS page says where.

[cols="1,1,2", options="header"]
|===
| Azure | AWS | Notes

| xref:cloud/azure/resource-organization.adoc[Resource Organization] (management groups, subscriptions, resource groups)
| xref:cloud/aws/accounts-and-organizations.adoc[]
| AWS isolates workloads by account inside an organization; there is no resource group, so tags and CloudFormation stacks group resources.

| xref:cloud/azure/identity-and-access.adoc[] (Entra ID, RBAC, managed identities)
| xref:cloud/aws/identity-and-access.adoc[]
| IAM roles take the place of managed identities; IAM Identity Center is the workforce sign-in counterpart.

| xref:cloud/azure/infrastructure-as-code.adoc[] (Bicep, `azd`)
| xref:cloud/aws/infrastructure-as-code.adoc[]
| CloudFormation, the CDK and SAM.

| xref:cloud/azure/global-infrastructure.adoc[]
| xref:cloud/aws/global-infrastructure.adoc[]
| Regions and Availability Zones, plus Local Zones and edge locations.

| xref:cloud/azure/choosing-a-compute-service.adoc[]
| xref:cloud/aws/choosing-a-compute-service.adoc[]
| Same decision, different catalog.

| xref:cloud/azure/container-registry.adoc[] (ACR)
| xref:cloud/aws/container-registry.adoc[] (ECR)
| Repositories are created per image name.

| xref:cloud/azure/container-apps.adoc[] (Container Apps)
| xref:cloud/aws/ecs-and-fargate.adoc[] (ECS on Fargate, ECS Express Mode)
| Express Mode is the closest match to the Container Apps experience.

| xref:cloud/azure/app-service-and-functions.adoc[] (Functions)
| xref:cloud/aws/lambda.adoc[] and xref:cloud/aws/lambda-event-driven-and-serverless-apps.adoc[]
| Lambda functions with event source mappings; Elastic Beanstalk is the App Service-style option.

| xref:cloud/azure/aks-clusters.adoc[] and xref:cloud/azure/aks-microservices.adoc[] (AKS)
| xref:cloud/aws/eks-clusters.adoc[] and xref:cloud/aws/eks-microservices.adoc[] (EKS)
| EKS Auto Mode compares to AKS Automatic; Pod Identity compares to workload identity.

| xref:cloud/azure/storage-accounts.adoc[] and xref:cloud/azure/blob-storage.adoc[] (Blob Storage)
| xref:cloud/aws/s3-object-storage.adoc[] (S3), xref:cloud/aws/block-and-file-storage.adoc[] (EBS, EFS)
| There is no storage-account layer: buckets are the top-level container.

| xref:cloud/azure/front-door-and-cdn.adoc[] (Front Door)
| xref:cloud/aws/cloudfront-cdn.adoc[] (CloudFront)
| Origin access control keeps the S3 origin private.

| xref:cloud/azure/managed-databases-overview.adoc[]
| xref:cloud/aws/managed-databases-overview.adoc[]
| Engine-by-engine map on both sides.

| xref:cloud/azure/azure-sql.adoc[] and xref:cloud/azure/postgresql-and-mysql.adoc[]
| xref:cloud/aws/rds.adoc[] and xref:cloud/aws/aurora.adoc[]
| RDS for managed engines, Aurora for the cloud-native PostgreSQL/MySQL option.

| xref:cloud/azure/cosmos-db-and-documentdb.adoc[] (Cosmos DB, Azure DocumentDB)
| xref:cloud/aws/dynamodb.adoc[] and xref:cloud/aws/documentdb-and-mongodb.adoc[]
| DynamoDB for key-value/document at scale; DocumentDB for MongoDB compatibility.

| xref:cloud/azure/redis-and-partner-databases.adoc[] (Azure Managed Redis)
| xref:cloud/aws/caching-graph-and-partner-databases.adoc[] (ElastiCache for Valkey, MemoryDB)
| Valkey is the default open-source engine.

| xref:cloud/azure/key-vault-and-secrets.adoc[] (Key Vault)
| xref:cloud/aws/secrets-manager-and-kms.adoc[] (Secrets Manager and KMS)
| Secrets and keys are separate services on AWS.

| xref:cloud/azure/runtime-configuration.adoc[] (App Configuration)
| xref:cloud/aws/runtime-configuration.adoc[] (AppConfig, Parameter Store)
| ConfigMaps on EKS work as they do on AKS.

| xref:cloud/azure/virtual-networks.adoc[] (virtual networks, NSGs)
| xref:cloud/aws/vpc-networking.adoc[] (VPC, security groups)
| Subnets are bound to one Availability Zone on AWS.

| xref:cloud/azure/gateways-and-load-balancing.adoc[]
| xref:cloud/aws/load-balancers-and-gateways.adoc[] (ALB, NLB)
| ALB with the AWS Load Balancer Controller replaces Application Gateway.

| xref:cloud/azure/api-management.adoc[] (API Management)
| xref:cloud/aws/api-gateway.adoc[] (API Gateway)
| HTTP APIs are the lightweight, lower-cost option.

| xref:cloud/azure/vpn-and-hybrid-connectivity.adoc[] (VPN Gateway)
| xref:cloud/aws/vpn-and-hybrid-connectivity.adoc[] (Client VPN, Site-to-Site VPN)
| Verified Access is the VPN-less alternative.

| xref:cloud/azure/email-with-communication-services.adoc[] (Communication Services Email)
| xref:cloud/aws/ses-email.adoc[] (SES)
| New accounts start in the SES sandbox.

| xref:cloud/azure/messaging-and-integration.adoc[] (Service Bus, Event Grid, Event Hubs)
| xref:cloud/aws/messaging-and-integration.adoc[] (SQS, SNS, EventBridge, Kinesis)
| Different splitting of queues, topics and event buses.

| xref:cloud/azure/monitoring-and-observability.adoc[] (Azure Monitor)
| xref:cloud/aws/monitoring-and-observability.adoc[] (CloudWatch, CloudTrail)
| Logs, metrics and alarms in CloudWatch.

| xref:cloud/azure/governance-and-compliance.adoc[] (Azure Policy)
| xref:cloud/aws/governance-security-and-compliance.adoc[] (Config, Security Hub)
| Service control policies in Organizations are the closest guard rail.

| xref:cloud/azure/cost-management.adoc[]
| xref:cloud/aws/cost-management-and-support.adoc[]
| Cost Explorer and Budgets.

| xref:cloud/azure/architecture-migration-and-hybrid.adoc[]
| xref:cloud/aws/architecture-migration-and-hybrid.adoc[]
| Well-Architected Framework and Cloud Adoption Framework on both sides.

| xref:cloud/azure/developer-tools-and-devops.adoc[]
| xref:cloud/aws/developer-tools-and-devops.adoc[]
| GitHub Actions with OIDC works with both clouds.
|===
