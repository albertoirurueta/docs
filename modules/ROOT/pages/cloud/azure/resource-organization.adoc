= Resource Organization
:description: How Azure organizes resources into management groups, subscriptions and resource groups, and how to tag, lock and move them with the portal and the Azure CLI.
:keywords: azure resource manager, arm, management groups, subscriptions, resource groups, tags, resource locks, naming conventions, azure cli

Every resource in Azure -- a storage account, a virtual network, a Container Apps environment -- lives inside a
strict containment hierarchy, and every action on it, whatever tool issues it, passes through the same control
plane. This page covers that hierarchy, the control plane behind it, and the three organizational tools you use
day to day: naming conventions, tags and resource locks.

== The containment hierarchy

Azure organizes everything into four nested levels:

Management groups:: Optional containers above subscriptions, used to apply policy and RBAC across many
subscriptions at once (for example, one management group per business unit or environment tier).
Subscriptions:: The billing and access-management boundary. Quotas, cost reports and many RBAC assignments are
scoped at this level.
Resource groups:: A logical container for resources that share the same lifecycle -- typically deployed,
updated and deleted together. A resource belongs to exactly one resource group.
Resources:: The actual services -- storage accounts, virtual machines, Container Apps environments, and so on.

The Bookshelf sample application used throughout this section keeps everything in a single resource group,
`rg-bookshelf`, inside whichever subscription the reader is using; production estates typically split
environments (dev/test/prod) across separate subscriptions or resource groups instead.

== Azure Resource Manager: the control plane

Whichever tool you use -- the Azure portal, the Azure CLI, Azure PowerShell, a Bicep or ARM template, or
Terraform's `azurerm` provider -- every one of them ultimately calls the same REST API: Azure Resource Manager
(ARM). ARM is what makes Azure management declarative and idempotent: every create-or-update operation is a
`PUT` against a resource's URL, and sending the same `PUT` twice produces the same end state rather than a
duplicate resource. ARM is also where role-based access control (RBAC) is enforced -- a request that reaches ARM
without the right role assignment at the relevant scope (management group, subscription or resource group) is
rejected before it reaches the underlying service. Identity and RBAC are covered in depth in
xref:cloud/azure/identity-and-access.adoc[]; infrastructure-as-code tools that target ARM declaratively are
covered in xref:cloud/azure/infrastructure-as-code.adoc[].

=== Creating a resource group

==== In the Azure portal

. Sign in to the Azure portal and open *Resource groups*.
. Select *+ Create*.
. Choose the subscription, enter `rg-bookshelf` as the resource group name, and pick a region -- `eastus2` is
used throughout this section as a placeholder; choose the region closest to you instead.
. Select *Review + create*, then *Create*.

==== With the Azure CLI

[source,bash]
----
RG="rg-bookshelf"
LOCATION="eastus2" # placeholder -- pick the region closest to you

az group create --name "$RG" --location "$LOCATION"
----

Reference: https://learn.microsoft.com/azure/azure-resource-manager/management/manage-resource-groups-cli

== Naming conventions

Resource names are visible everywhere -- in the portal, in CLI output, in monitoring dashboards -- so a
consistent scheme pays off quickly. Microsoft publishes a recommended set of abbreviation prefixes per resource
type, such as `rg-` for resource groups, `st` for storage accounts (which cannot contain hyphens), and `vnet-`
for virtual networks; the Bookshelf examples in this section follow that scheme (`rg-bookshelf`,
`stbookshelfdata`, `vnet-bookshelf`). The full recommended abbreviation table is linked in
<<_references>>.

== Tags

Tags are key/value pairs attached to a resource, resource group or subscription, used for cost allocation,
ownership tracking and automation filters -- for example `environment=dev` or `owner=bookshelf-team`. The key
point to remember is that tags are *not* inherited by the resources inside a tagged resource group unless an
Azure Policy is used to apply or enforce them; tagging `rg-bookshelf` with `environment=dev` does not, by itself,
tag the storage account or Container Apps environment inside it.

=== In the Azure portal

. Open the resource group or resource, then select *Tags* in the left-hand blade.
. Enter a name and value (for example, `environment` / `dev`), select *Apply*, then repeat for additional pairs.

=== With the Azure CLI

[source,bash]
----
# Tag the resource group itself
az tag create --resource-id "$(az group show --name "$RG" --query id -o tsv)" \
  --tags environment=dev owner=bookshelf-team

# Tag a specific resource inside the group (merge, keeping existing tags)
az resource tag --tags environment=dev owner=bookshelf-team \
  --name "stbookshelfdata" \
  --resource-group "$RG" \
  --resource-type "Microsoft.Storage/storageAccounts"
----

Reference: https://learn.microsoft.com/azure/azure-resource-manager/management/tag-resources

== Resource locks

A resource lock overrides the permissions granted to any user, including an Owner or Contributor, to prevent
accidental changes or deletion. There are two lock levels: `CanNotDelete`, which allows reads and updates but
blocks deletion, and `ReadOnly`, which blocks any modification or deletion, including operations that only
appear read-only to the caller, such as adding a role assignment. Holding Owner or Contributor access on a
locked resource does not let you bypass the lock -- only an explicit `Microsoft.Authorization/locks/*` permission
does, so removing or changing a lock is itself a separately permissioned action.

=== In the Azure portal

. Open the resource group or resource, then select *Locks* in the left-hand blade.
. Select *+ Add*, enter a lock name, choose *Delete* (`CanNotDelete`) or *Read-only* (`ReadOnly`), and select
*OK*.

=== With the Azure CLI

[source,bash]
----
az lock create \
  --name "lock-rg-bookshelf" \
  --resource-group "$RG" \
  --lock-type CanNotDelete
----

Reference: https://learn.microsoft.com/azure/azure-resource-manager/management/lock-resources

== Management groups

Management groups sit above subscriptions and let you apply policy and access assignments across many
subscriptions from a single point, without repeating the assignment per subscription. A typical layout groups
subscriptions by environment (`mg-production`, `mg-nonproduction`) or by business unit.

=== In the Azure portal

. Open *Management Groups* and select *+ Create*.
. Enter a management group ID and, optionally, a display name, then select *Save*.
. Use *Add subscription* on the management group's overview page to move a subscription under it.

=== With the Azure CLI

[source,bash]
----
az account management-group create --name "mg-bookshelf-nonprod"

az account management-group list --output table
----

Reference: https://learn.microsoft.com/azure/governance/management-groups/overview

== Moving resources

Many, but not all, resource types can be moved between resource groups and, with more restrictions, between
subscriptions -- the target resource group or subscription must support the resource type, and some services
(for example, resources with dependencies pinned to a specific region's internal identifiers) refuse the move
outright. A move never changes the resource's region: the resource keeps running in the same physical location
it was created in, only its management scope (resource group or subscription) changes. Before moving anything in
your own environment, check the specific resource type's move support and any prerequisites in the reference
below, since support varies per service.

== Clean up

[source,bash]
----
az group delete --name "$RG" --yes --no-wait
----

Deleting the resource group removes every resource inside it; a `CanNotDelete` lock on the group or on any
resource inside it blocks this operation until the lock itself is removed.
