Cloud Run runs stateless containers on Google's infrastructure, starts instances when requests arrive, scales them
with the traffic (down to zero if you allow it) and bills for the resources used rather than for idle servers. It is
the service Google recommends for new users who want to run a container, a web application or an API without
operating a cluster. In the Bookshelf scenario (see xref:cloud/google-cloud/index.adoc[]) Cloud Run hosts the
`catalog-api` Spring Boot service and the `orders-api` service. This page is the "simple deployment" guide: what a
service and a revision are, how to deploy one from an image, from source or from a YAML file, how to configure,
secure, connect and expose it, what it costs and how to troubleshoot it. Autoscaling, traffic splitting, rollbacks,
jobs, worker pools and GPUs are in xref:cloud/google-cloud/cloud-run-scaling-traffic-and-jobs.adoc[]; functions and
event triggers are in xref:cloud/google-cloud/cloud-run-functions-and-events.adoc[]; the comparison with Compute
Engine, GKE and App Engine is in xref:cloud/google-cloud/choosing-a-compute-service.adoc[].

== Concepts

Service:: The long-running, request-driven resource. A service has a region, a stable `run.app` URL, an IAM policy
(who may invoke it), an ingress setting and a configuration template. Services are regional; a multi-region service
(GA 2026-06-29) is covered on the scaling page.

Revision:: An immutable snapshot of a service's configuration: container image digest, CPU and memory, environment
variables, secret references, volumes, VPC settings, timeout and concurrency. Every deploy or configuration change
creates a new revision; the service routes traffic to one or more revisions by percentage or by tag. Revisions are
named `SERVICE-00007-abc` by default.

Instance:: A running copy of a revision (one or more containers sharing a network namespace). Cloud Run adds and removes
instances automatically; each instance handles several requests at once up to the configured concurrency.

Container contract:: The container must listen for HTTP (or HTTP/2, gRPC) requests on the port in the `PORT`
environment variable (default 8080) on `0.0.0.0`, be built for 64-bit Linux, be stateless (the local filesystem is
in-memory and disappears with the instance) and handle `SIGTERM` by finishing in-flight requests, because an instance
is stopped about ten seconds after it receives the signal. Outbound-only background work is only reliable with
instance-based billing (below).

Execution environment:: Cloud Run offers a first-generation sandbox (fast cold starts, a restricted Linux
compatibility layer) and a second-generation environment (full Linux compatibility, network file systems, faster CPU
and network at the price of slightly slower starts). New services use the default chosen by Cloud Run; select one
explicitly with `--execution-environment gen1|gen2` when a library needs full Linux system-call support.

Knative lineage:: Cloud Run's API (`serving.knative.dev/v1`) is a subset of Knative Serving, which is why service
YAML looks like Kubernetes objects. Older guides still describe "Cloud Run for Anthos"; that product is now
Knative serving on GKE and is not covered here. Use the fully managed Cloud Run described on this page.

== Ways to deploy

[mermaid]
....
flowchart LR
    SRC[Source folder] -->|gcloud run deploy --source| CB[Cloud Build with buildpacks or Dockerfile]
    CB --> AR[Artifact Registry image]
    IMG[Prebuilt image from CI] --> AR
    AR -->|gcloud run deploy --image| REV[New revision]
    YAML[service.yaml] -->|gcloud run services replace| REV
    REV --> SVC[Service routes traffic]
....

From an image:: The production path. CI builds the image, pushes it to an Artifact Registry Docker repository
(`us-central1-docker.pkg.dev/$PROJECT_ID/bookshelf/catalog-api`) and the pipeline deploys by digest. Container
Registry (`gcr.io`) was shut down on 2025-03-18; older guides that push to `gcr.io/PROJECT/IMAGE` should use
Artifact Registry instead (see xref:cloud/google-cloud/container-registry-and-builds.adoc[]). Cloud Run can also
deploy public images and, since 2026-07-14, import public images from GitHub Container Registry (GA).

From source:: `gcloud run deploy --source .` uploads the folder, builds an image with Cloud Build (a `Dockerfile` if
present, otherwise Google Cloud buildpacks for Go, Node.js, Python, Java, .NET, Ruby and PHP), stores it in an
Artifact Registry repository that Cloud Run creates automatically in the region, named `cloud-run-source-deploy`,
and deploys it. It is the fastest way to a working URL and a good fit for prototypes; a pipeline with explicit
build, scan and promote stages is better for production. A Preview option (`--no-build`) deploys pre-packaged
artifacts without a build step.

Declaratively:: A Knative-style `service.yaml` applied with `gcloud run services replace`, which is repeatable and
reviewable. Terraform (below) is the infrastructure-as-code alternative; see
xref:cloud/google-cloud/infrastructure-as-code.adoc[] for how it fits with the rest of the project.

== Prerequisites for Bookshelf

The commands in this page use these shell variables and a dedicated service account for the `catalog-api` service.
The account runs the service; it is not the account that deploys it.

[source,bash]
----
gcloud services enable run.googleapis.com artifactregistry.googleapis.com \
  cloudbuild.googleapis.com secretmanager.googleapis.com \
  sqladmin.googleapis.com compute.googleapis.com

PROJECT_ID=$(gcloud config get-value project)
PROJECT_NUMBER=$(gcloud projects describe "$PROJECT_ID" --format='value(projectNumber)')
REGION=us-central1
SERVICE=catalog-api
REPO=bookshelf
IMAGE="$REGION-docker.pkg.dev/$PROJECT_ID/$REPO/$SERVICE:1.0.0"
RUNTIME_SA="$SERVICE@$PROJECT_ID.iam.gserviceaccount.com"

gcloud config set run/region "$REGION"

gcloud iam service-accounts create "$SERVICE" \
  --display-name="Bookshelf catalog-api runtime"
----

Derived from https://docs.cloud.google.com/run/docs/setup[Set up Cloud Run],
https://docs.cloud.google.com/run/docs/securing/service-identity[Configure the service identity] and
https://docs.cloud.google.com/sdk/gcloud/reference/iam/service-accounts/create[gcloud iam service-accounts create].

If a service does not name a service account, Cloud Run runs it as the Compute Engine default service account of the
project, which historically holds the broad Editor role. Google recommends a dedicated user-managed service account
per service, with only the roles the code needs, and recommends enforcing the
`iam.automaticIamGrantsForDefaultServiceAccounts` organization policy constraint so new projects do not grant the default
account that role automatically. Never set `GOOGLE_APPLICATION_CREDENTIALS` on Cloud Run and never download a
key: the platform supplies credentials for the attached account through the metadata server (Application Default
Credentials; see xref:cloud/google-cloud/identity-and-access.adoc[]).

The person or pipeline that deploys needs permission to call the Cloud Run Admin API (for example
`roles/run.developer`), `roles/iam.serviceAccountUser` on the runtime service account, and, for source deploys,
`roles/run.sourceDeveloper` and `roles/serviceusage.serviceUsageConsumer`; the Cloud Build service account needs
`roles/run.builder`.

== Deploy a service

=== In the Google Cloud console

. Select the project in the project picker, then open *Cloud Run*. If prompted, enable the Cloud Run Admin API.
. Click *Deploy container* and choose *Service*. (Cloud Shell, the terminal icon at the top right, is available for
any CLI step below.)
. Choose *Deploy one revision from an existing container image* and select the image from Artifact Registry, or
*Continuously deploy from a repository* / *Deploy from source* to build from GitHub or a local upload.
. Enter the service name `catalog-api` and choose the region `us-central1`.
. Under *Authentication*, choose *Require authentication* (recommended) or *Allow public access*.
. Under *Billing*, choose *Request-based* or *Instance-based*; under *Service scaling* set the minimum and maximum
number of instances.
. Under *Ingress control*, choose *Internal*, *Internal and Cloud Load Balancing* or *All*.
. Expand *Containers, Volumes, Networking, Security*. On *Container(s)* set the port, CPU, memory, concurrency,
request timeout and execution environment; on *Variables & Secrets* add environment variables and secret references;
on *Volumes* add Cloud Storage, NFS or in-memory volumes; on *Networking* configure Direct VPC egress; on *Security*
choose the service account.
. Click *Create*. The page shows the service URL when the first revision is ready.

=== With the gcloud CLI

From an image:

[source,bash]
----
gcloud run deploy "$SERVICE" \
  --image="$IMAGE" \
  --region="$REGION" \
  --service-account="$RUNTIME_SA" \
  --no-allow-unauthenticated \
  --port=8080 \
  --cpu=1 --memory=1Gi \
  --concurrency=80 --timeout=300 \
  --min-instances=0 --max-instances=10 \
  --cpu-boost
----

From source (Cloud Build creates the image and the `cloud-run-source-deploy` repository):

[source,bash]
----
cd catalog-api
gcloud run deploy "$SERVICE" \
  --source . \
  --region="$REGION" \
  --service-account="$RUNTIME_SA" \
  --no-allow-unauthenticated
----

From a YAML file, then read the live definition back:

[source,bash]
----
gcloud run services replace service.yaml --region="$REGION"
gcloud run services describe "$SERVICE" --region="$REGION" --format=export > service.yaml
gcloud run services describe "$SERVICE" --region="$REGION" --format='value(status.url)'
----

Derived from https://docs.cloud.google.com/run/docs/deploying[Deploy a container image],
https://docs.cloud.google.com/run/docs/deploying-source-code[Deploy services from source code] and
https://docs.cloud.google.com/sdk/gcloud/reference/run/deploy[gcloud run deploy].

Flags that are not repeated on a later `gcloud run deploy` keep their previous value, so a deploy that only changes
the image does not reset CPU or memory. `gcloud run services update SERVICE --update-env-vars ...` changes
configuration without a new image; every change still produces a new revision. A deploy that omits `--region` uses
the `run/region` property or asks interactively, which is why scripts should always pass it.

A matching `service.yaml` (placeholders only, no secrets):

[source,yaml]
----

metadata:
  name: catalog-api
  labels:
    app: bookshelf
spec:
  template:
    metadata:

              cpu: "1"

----

Derived from https://docs.cloud.google.com/run/docs/reference/yaml/v1[Cloud Run YAML reference (Knative serving API)].

== Configuration

=== CPU, memory, concurrency and timeouts

[cols="2,3,3",options="header"]
|===
|Setting |gcloud flag |Notes

|CPU and memory
|`--cpu`, `--memory`
|Up to 8 vCPU and 32 GiB per instance. Fractional CPU (below 1 vCPU) forces concurrency of 1 and request-based billing.
Larger sizes need a minimum memory per CPU; the console warns when a combination is not allowed.

|Concurrency
|`--concurrency`
|Requests one instance handles at the same time: default 80, maximum 1,000. Set to 1 for code that is not thread-safe.

|Request timeout
|`--timeout` (seconds)
|Default 300 seconds, up to 60 minutes. A request that exceeds it gets HTTP 504. Older guides quote five minutes as
the fixed limit; it is configurable now.

|Startup CPU boost
|`--cpu-boost` / `--no-cpu-boost`
|Allocates extra CPU while the container starts, which helps JVM services. See the scaling page for the effect on cold starts.

|Instances
|`--min-instances`, `--max-instances`
|Minimum keeps warm instances (and costs idle time); maximum caps cost and protects backends such as Cloud SQL connections.

|Execution environment
|`--execution-environment`
|`gen1` or `gen2`, as described under Concepts.

|Session affinity
|`--session-affinity`
|Best-effort routing of a client to the same instance via a cookie; not a substitute for external session storage.
|===

The maximum number of instances applies per revision, and the per-project, per-region quotas (1,000 services, 1,000 jobs,
4,000 revisions serving traffic) are on the quotas page linked in the references.

=== Environment variables and arguments

[source,bash]
----
gcloud run services update "$SERVICE" --region="$REGION" \
  --update-env-vars=SPRING_PROFILES_ACTIVE=prod,CATALOG_DB_NAME=catalog \
  --command=java --args=-jar,/app/app.jar
----

Derived from https://docs.cloud.google.com/run/docs/configuring/services/environment-variables[Configure environment variables for services].

`--set-env-vars` replaces the whole set, `--update-env-vars` merges, `--remove-env-vars` and `--clear-env-vars` delete.
Cloud Run reserves some names (`PORT`, `K_SERVICE`, `K_REVISION`, `K_CONFIGURATION`) and sets them for you. Spring Boot
maps `CATALOG_DB_NAME` to the property `catalog.db.name` through relaxed binding; the profile mechanics are in
xref:backend/springboot/configuration-and-profiles.adoc[].

=== Secrets as environment variables or files

Secret Manager secrets are referenced, never copied into the revision. The service account must hold
`roles/secretmanager.secretAccessor` on the secret.

[source,bash]
----
gcloud secrets add-iam-policy-binding catalog-db-password \
  --member="serviceAccount:$RUNTIME_SA" \
  --role=roles/secretmanager.secretAccessor

# As an environment variable (pin the version)
gcloud run services update "$SERVICE" --region="$REGION" \
  --update-secrets=CATALOG_DB_PASSWORD=catalog-db-password:3

# As a file; "latest" is re-read on each instance start
gcloud run services update "$SERVICE" --region="$REGION" \
  --update-secrets=/secrets/db/password=catalog-db-password:latest
----

Derived from https://docs.cloud.google.com/run/docs/configuring/services/secrets[Configure secrets for services].

An environment variable is resolved when the instance starts and therefore needs a new revision (or a restart) to see
a rotated value, so Google recommends pinning a version number. A secret mounted as a file is read when the container
starts too, but referencing `latest` gives each new instance the current value without redeploying. The mount path
must start with a slash, two secrets cannot share a path, mounting over an existing directory hides its contents, and
`/dev`, `/proc` and `/sys` are not allowed. Cloud Run does not support regional secrets; use global Secret Manager
secrets. The wider story of secrets and Parameter Manager is in
xref:cloud/google-cloud/runtime-configuration.adoc[].

=== Health checks

Cloud Run applies a default TCP startup probe on the container port to new services, giving the container up to four
minutes to open the port. Define probes explicitly when the application needs a warm-up or can deadlock:

[source,bash]
----
gcloud run services update "$SERVICE" --region="$REGION" \
  --startup-probe=httpGet.path=/actuator/health/readiness,httpGet.port=8080,initialDelaySeconds=0,timeoutSeconds=2,periodSeconds=5,failureThreshold=24 \
  --liveness-probe=httpGet.path=/actuator/health/liveness,httpGet.port=8080,periodSeconds=10,failureThreshold=3
----

Derived from https://docs.cloud.google.com/run/docs/configuring/healthchecks[Configure container health checks for services].

Probes can be HTTP (2xx or 3xx is success), TCP or gRPC. A failing startup probe stops the revision from becoming
ready; a failing liveness probe restarts the container. With Spring Boot, enable the Actuator probe groups
(`management.endpoint.health.probes.enabled=true`) as described in
xref:backend/springboot/metrics-and-observability.adoc[].

=== Sidecars and multi-container services

A service can run up to ten containers per instance: one ingress container that receives requests on the port, and up
to nine sidecars that share the network namespace and talk to it over `localhost` (sidecars GA 2023-11-13). Typical
uses are an OpenTelemetry collector, a proxy, or a Cloud SQL Auth Proxy.

[source,bash]
----
gcloud run deploy "$SERVICE" --region="$REGION" \
  --container=app --image="$IMAGE" --port=8080 \
  --container=otel-collector --image="$REGION-docker.pkg.dev/$PROJECT_ID/$REPO/otel-collector:1.0.0"
----

Derived from https://docs.cloud.google.com/run/docs/deploying#sidecars[Deploy multiple containers to a service (sidecars)].

Specify all service-level flags before the first `--container`; container-level flags such as `--image`, `--port`
and `--cpu` apply to the container named just before them. If one container depends on another (for example the app
waits for a proxy), declare container dependencies and give the dependency a startup probe so ordering is enforced.
CPU and memory are allocated per container and summed against the instance limit.

=== Volume mounts

Services can mount a Cloud Storage bucket (through Cloud Storage FUSE, GA 2024-08-27), an NFS share such as
Filestore (GA 2024-08-27) or an in-memory volume (GA 2024-11-12) as a directory:

[source,bash]
----
BUCKET=bookshelf-uploads-$PROJECT_ID
gcloud storage buckets add-iam-policy-binding "gs://$BUCKET" \
  --member="serviceAccount:$RUNTIME_SA" --role=roles/storage.objectUser

gcloud run services update "$SERVICE" --region="$REGION" \
  --add-volume=name=uploads,type=cloud-storage,bucket="$BUCKET" \
  --add-volume-mount=volume=uploads,mount-path=/mnt/uploads
----

Derived from https://docs.cloud.google.com/run/docs/configuring/services/cloud-storage-volume-mounts[Mount a Cloud Storage bucket as a volume]
and https://docs.cloud.google.com/run/docs/configuring/services/in-memory-volume-mounts[in-memory volume mounts].

A bucket mount is a file-system view of object storage, not a disk: there is no file locking, concurrent writes to the
same object are last-writer-wins, and latency is that of the Cloud Storage API. The mount is established before the
containers start (with a 30-second limit), so it lengthens cold starts slightly. Use the Cloud Storage client library
(see xref:backend/springboot/file-storage-and-object-stores.adoc[]) for write-heavy or concurrent access. An
in-memory volume counts against the instance's memory.

== Security

=== Who may call the service: invoker IAM

By default a service is private: a caller needs the `run.routes.invoke` permission, granted by `roles/run.invoker`
on the service (or its project or folder). Requests carry a Google-signed ID token in the `Authorization: Bearer`
header whose audience is the service URL.

[source,bash]
----
# Allow a service account (for example orders-api) to call catalog-api
gcloud run services add-iam-policy-binding "$SERVICE" --region="$REGION" \
  --member="serviceAccount:orders-api@$PROJECT_ID.iam.gserviceaccount.com" \
  --role=roles/run.invoker

# Call it from a workstation as yourself
URL=$(gcloud run services describe "$SERVICE" --region="$REGION" --format='value(status.url)')
curl -H "Authorization: Bearer $(gcloud auth print-identity-token)" "$URL/api/books"
----

Derived from https://docs.cloud.google.com/run/docs/authenticating/overview[Authentication overview],
https://docs.cloud.google.com/run/docs/authenticating/service-to-service[Service-to-service authentication] and
https://docs.cloud.google.com/run/docs/authenticating/developers[Authenticating developers].

=== Authenticated versus public

[cols="2,3,3",options="header"]
|===
|Mode |How |When

|Private (default for the recommended flow)
|`--no-allow-unauthenticated`; grant `roles/run.invoker` to specific principals
|Internal APIs, service-to-service calls, Pub/Sub push and Cloud Scheduler with an invoker service account.

|Public through IAM
|`--allow-unauthenticated`, which binds `roles/run.invoker` to `allUsers`
|A public website or API. Fails when domain-restricted sharing (an organization policy) forbids `allUsers`.

|Public by disabling the check
|`--no-invoker-iam-check` (GA 2025-03-28); re-enable with `--invoker-iam-check`
|Public access that works under domain-restricted sharing. Google lists it as the preferred way to make a service public.
|===

[source,bash]
----
gcloud run services update "$SERVICE" --region="$REGION" --no-invoker-iam-check
----

Derived from https://docs.cloud.google.com/run/docs/authenticating/public[Allow public (unauthenticated) access].

Changing public access needs `run.services.setIamPolicy` (part of `roles/run.admin`). Re-enabling the invoker check in
the console removes an existing `allUsers` invoker binding, so grant it again if you later want IAM-based public
access. Making `catalog-api` public is a design decision, not a default: in Bookshelf only the static front end
and an API gateway or load balancer are public, and `catalog-api` stays private behind them.

=== Ingress, IAP and other controls

* *Ingress* (`--ingress=all|internal|internal-and-cloud-load-balancing`) restricts where requests may come from. `all` also
  accepts requests to the `run.app` URL from the internet; `internal-and-cloud-load-balancing` accepts the external
  Application Load Balancer and internal sources; `internal` accepts only internal sources such as the same VPC
  network, VPC Service Controls perimeters and specific Google services (Pub/Sub, Cloud Scheduler, Eventarc,
  Cloud Tasks, Workflows). `--no-default-url` disables the `run.app` URL entirely, which also breaks Google services
  that call the default URL.
* *Identity-Aware Proxy directly on Cloud Run* (GA 2026-03-13, no load balancer needed):
  `gcloud run deploy ... --no-allow-unauthenticated --iap`, then grant `roles/run.invoker` to the IAP service agent
  (`service-<project-number>@gcp-sa-iap.iam.gserviceaccount.com`) and `roles/iap.httpsResourceAccessor` to users or groups.
  IAP can be configured either on the load balancer or on the service, not both. See
  xref:cloud/google-cloud/identity-and-access.adoc[] for IAP concepts.
* *Service-to-service*: the caller fetches an ID token for the callee's URL from the metadata server (or through
  impersonation locally) and sends it as a bearer token; the callee verifies it automatically.
* *Binary Authorization* can require signed, attested images; Cloud Run Threat Detection (GA 2025-09-10) is part of
  Security Command Center; both are optional hardening covered by
  xref:cloud/google-cloud/governance-security-and-compliance.adoc[].

== Networking

=== Direct VPC egress

By default a Cloud Run instance reaches the internet but not private IP addresses in your VPC network. Direct VPC egress
(GA 2024-04-24) gives instances addresses from a subnet so they can reach Memorystore, Cloud SQL private IP and
internal services without a Serverless VPC Access connector. Connectors remain supported for older setups, but
Google recommends Direct VPC egress for new ones because it needs no connector instances to pay for or size.

[source,bash]
----
gcloud services enable compute.googleapis.com

gcloud run services update "$SERVICE" --region="$REGION" \
  --network=bookshelf-vpc --subnet=bookshelf-run \
  --network-tags=catalog-api \
  --vpc-egress=private-ranges-only
----

Derived from https://docs.cloud.google.com/run/docs/configuring/vpc-direct-vpc[Connect to a VPC network with Direct VPC egress].

`private-ranges-only` sends only RFC 1918 and similar private destinations through the VPC and everything else directly
to the internet; `all-traffic` sends every outbound packet through the VPC, which is required for a static outbound
address through Cloud NAT. The subnet must be at least `/26`; Cloud Run reserves addresses in blocks of 16 and, for
services, plans roughly twice the number of instances plus headroom for revision changes, so size it for the
maximum instance count. Network tags let firewall rules target a revision. Throughput is capped at 1 Gbps per instance,
connection establishment can take a minute or more at start, and Cloud Run's service agent needs the
`roles/run.serviceAgent` permissions on the network. VPC design is in
xref:cloud/google-cloud/vpc-networking.adoc[].

=== Cloud SQL and Memorystore

Cloud Run can reach Cloud SQL over a Unix socket at `/cloudsql/INSTANCE_CONNECTION_NAME` (the `--add-cloudsql-instances`
flag mounts the socket and the service account needs `roles/cloudsql.client`), through the language connectors,
or over the private IP using Direct VPC egress. A single instance supports at most 100 concurrent connections to
Cloud SQL, so pool sizes and `--max-instances` must be set together.

[source,bash]
----
gcloud run services update "$SERVICE" --region="$REGION" \
  --add-cloudsql-instances="$PROJECT_ID:$REGION:bookshelf-catalog"

gcloud projects add-iam-policy-binding "$PROJECT_ID" \
  --member="serviceAccount:$RUNTIME_SA" --role=roles/cloudsql.client
----

Derived from https://docs.cloud.google.com/sql/docs/postgres/connect-run[Connect from Cloud Run to Cloud SQL for PostgreSQL].

The database setup is in xref:cloud/google-cloud/cloud-sql.adoc[]; a Valkey cache over the same VPC path is in
xref:cloud/google-cloud/memorystore-and-partner-databases.adoc[].

=== Custom domains

Cloud Run gives every service a `run.app` URL with a Google-managed certificate. To serve `catalog.example.com`
there are three routes:

[cols="2,4,3",options="header"]
|===
|Route |Notes |Status

|Global external Application Load Balancer with a serverless network endpoint group (NEG)
|The recommended production path: Google-managed certificate, Cloud CDN, Cloud Armor, one IP for several services,
URL maps for path routing. Set the service ingress to `internal-and-cloud-load-balancing` so the load balancer is the
only public entrance.
|GA

|Firebase Hosting rewrite to Cloud Run
|Lower cost, convenient when the site is mostly static content with a few dynamic routes.
|GA

|Cloud Run domain mapping (`gcloud beta run domain-mappings`)
|Maps a verified domain directly to a service. Only available in a short list of regions (ten at last check), no
wildcard or custom certificates, TLS 1.0/1.1 cannot be disabled, certificate provisioning takes from 15 minutes to 24 hours
and Google describes it as not production-ready because of latency.
|Preview
|===

Older guides present domain verification and domain mapping as the way to add a custom domain; the current
documentation recommends the load balancer instead. The mapping command, for a test environment only:

[source,bash]
----
gcloud beta run domain-mappings create --service="$SERVICE" \
  --domain=catalog.example.com --region="$REGION"
gcloud beta run domain-mappings describe --domain=catalog.example.com --region="$REGION"
----

Derived from https://docs.cloud.google.com/run/docs/mapping-custom-domains[Mapping custom domains].

The production route, with a global external Application Load Balancer, a serverless NEG, a managed certificate and a URL map:

[source,bash]
----
DOMAIN=catalog.example.com

gcloud compute addresses create catalog-lb-ip --global
gcloud compute network-endpoint-groups create catalog-neg \
  --region="$REGION" --network-endpoint-type=serverless \
  --cloud-run-service="$SERVICE"
gcloud compute backend-services create catalog-backend \
  --global --load-balancing-scheme=EXTERNAL_MANAGED
gcloud compute backend-services add-backend catalog-backend --global \
  --network-endpoint-group=catalog-neg \
  --network-endpoint-group-region="$REGION"
gcloud compute url-maps create catalog-map --default-service=catalog-backend
gcloud compute ssl-certificates create catalog-cert --domains="$DOMAIN" --global
gcloud compute target-https-proxies create catalog-proxy \
  --url-map=catalog-map --ssl-certificates=catalog-cert
gcloud compute forwarding-rules create catalog-https --global \
  --load-balancing-scheme=EXTERNAL_MANAGED \
  --address=catalog-lb-ip --target-https-proxy=catalog-proxy --ports=443

gcloud run services update "$SERVICE" --region="$REGION" \
  --ingress=internal-and-cloud-load-balancing
----

Derived from https://docs.cloud.google.com/load-balancing/docs/https/setting-up-https-serverless[Set up a global external Application Load Balancer with Cloud Run]
and https://docs.cloud.google.com/run/docs/securing/ingress[Restrict network access].

Create an `A` record for the domain that points at the reserved address; the managed certificate becomes active after
DNS resolves. The load balancer needs an invoker decision as well: it does not authenticate to Cloud Run, so either
the service is public (`--no-invoker-iam-check`), or IAP is enabled on the service or the backend. The balancer,
Cloud CDN and Cloud Armor are covered in xref:cloud/google-cloud/load-balancing-and-cloud-armor.adoc[] and DNS in
xref:cloud/google-cloud/cloud-dns-and-certificates.adoc[].

== Billing and pricing model

Cloud Run bills in two modes; the mode is a property of the revision and replaces the older names "CPU allocated only
during request processing" and "CPU always allocated".

Request-based billing (`--cpu-throttling`, the default):: Instances are billed only while they process requests, start
or shut down, plus a per-request fee. Outside requests, CPU is throttled to nearly zero, so background threads, caches
warming and scheduled work inside the container are unreliable. Best for spiky or low traffic.

Instance-based billing (`--no-cpu-throttling`):: Instances are billed for their whole lifetime, with no per-request fee and a
lower per-second rate. CPU is always available, so background work and WebSocket-style long connections behave. It
requires at least 512 MiB of memory, and idle instances are still shut down after at most 15 minutes without requests
unless minimum instances keep them. Best for steady traffic. Jobs always use instance-based billing.

[source,bash]
----
gcloud run services update "$SERVICE" --region="$REGION" --no-cpu-throttling
----

Derived from https://docs.cloud.google.com/run/docs/configuring/billing-settings[Set billing settings for services].

The cost drivers are vCPU-seconds, GiB-seconds, requests (request-based only), idle time of minimum instances, outbound
network egress, plus separate charges for Cloud Build, Artifact Registry storage and logging. Both modes have a monthly
free tier. Budget spend caps, announced in the release notes of 2026-07-27, can stop resources from exceeding a defined limit; check their launch stage before relying on them. Rates change and
differ by region and tier: use the https://cloud.google.com/run/pricing[Cloud Run pricing page] and the
https://cloud.google.com/products/calculator[pricing calculator] (both dated when you open them) and see
xref:cloud/google-cloud/cost-management-and-billing.adoc[] for budgets.

== Bookshelf catalog-api end to end

This sequence takes `catalog-api` from an empty project to a private, database-connected service behind a public front
door. It assumes the Artifact Registry repository `bookshelf`, the Cloud SQL instance `bookshelf-catalog` and the
secret `catalog-db-password` exist (see the pages linked under Related pages), and the shell variables above.

[source,bash]
----
# 1. Build and push (Jib is shown on the builds page); then deploy by digest
DIGEST=$(gcloud artifacts docker images describe "$IMAGE" --format='value(image_summary.digest)')

# 2. Grant the runtime account what the code needs
gcloud secrets add-iam-policy-binding catalog-db-password \
  --member="serviceAccount:$RUNTIME_SA" --role=roles/secretmanager.secretAccessor
gcloud projects add-iam-policy-binding "$PROJECT_ID" \
  --member="serviceAccount:$RUNTIME_SA" --role=roles/cloudsql.client

# 3. Deploy: private, 1 vCPU, Cloud SQL socket, secret as env var, boost on
gcloud run deploy "$SERVICE" --region="$REGION" \
  --image="$REGION-docker.pkg.dev/$PROJECT_ID/$REPO/$SERVICE@$DIGEST" \
  --service-account="$RUNTIME_SA" \
  --no-allow-unauthenticated \
  --cpu=1 --memory=1Gi --cpu-boost --max-instances=10 \
  --add-cloudsql-instances="$PROJECT_ID:$REGION:bookshelf-catalog" \
  --set-env-vars=SPRING_PROFILES_ACTIVE=prod,CATALOG_DB_NAME=catalog,CATALOG_INSTANCE="$PROJECT_ID:$REGION:bookshelf-catalog" \
  --update-secrets=CATALOG_DB_PASSWORD=catalog-db-password:1

# 4. Let orders-api call it, and test
gcloud run services add-iam-policy-binding "$SERVICE" --region="$REGION" \
  --member="serviceAccount:orders-api@$PROJECT_ID.iam.gserviceaccount.com" \
  --role=roles/run.invoker
URL=$(gcloud run services describe "$SERVICE" --region="$REGION" --format='value(status.url)')
curl -s -H "Authorization: Bearer $(gcloud auth print-identity-token)" "$URL/actuator/health"
----

Derived from the Cloud Run, Artifact Registry and Cloud SQL pages cited in the sections above, and
https://docs.cloud.google.com/sdk/gcloud/reference/artifacts/docker/images/describe[gcloud artifacts docker images describe].

Deploying by digest means the revision cannot silently change if a tag is moved. The request path through the platform
looks like this:

[mermaid]
....
flowchart LR
    C[Client or orders-api] -->|HTTPS with ID token| G[Google Front End]
    G -->|ingress and invoker IAM checks| R[Cloud Run router]
    R --> I[catalog-api instance]
    I -->|Unix socket or private IP| S[(Cloud SQL bookshelf-catalog)]
    I -->|metadata server token| M[Secret Manager and other APIs]
....

=== Application code: credentials and the database

Inside the container the Spring Boot application uses the attached service account through Application Default
Credentials; no key file is needed. The database settings come from the variables set above (Cloud SQL socket
factory for Postgres over the Unix socket):

[source,yaml]
----
# src/main/resources/application-prod.yaml
spring:
  datasource:
    url: jdbc:postgresql:///${CATALOG_DB_NAME}?cloudSqlInstance=${CATALOG_INSTANCE}&socketFactory=com.google.cloud.sql.postgres.SocketFactory&enableIamAuth=false
    username: catalog_app
    password: ${CATALOG_DB_PASSWORD}
    hikari:
      maximum-pool-size: 5
  lifecycle:
    timeout-per-shutdown-phase: 8s
server:
  shutdown: graceful
----

A service that calls another private service obtains an ID token for the target URL with the Google Auth Library:

[source,java]
----
package com.example.bookshelf.orders;

import com.google.auth.oauth2.GoogleCredentials;
import com.google.auth.oauth2.IdTokenCredentials;
import com.google.auth.oauth2.IdTokenProvider;
import java.io.IOException;
import java.net.URI;
import java.net.http.HttpClient;
import java.net.http.HttpRequest;
import java.net.http.HttpResponse;

public class CatalogClient {

    private final HttpClient http = HttpClient.newHttpClient();
    private final String baseUrl;
    private final IdTokenCredentials credentials;

    public CatalogClient(String baseUrl) throws IOException {
        this.baseUrl = baseUrl;
        // Application Default Credentials: the orders-api service account on Cloud Run,
        // or an impersonated account locally (gcloud auth application-default login
        // --impersonate-service-account=...)
        GoogleCredentials adc = GoogleCredentials.getApplicationDefault();
        this.credentials = IdTokenCredentials.newBuilder()
                .setIdTokenProvider((IdTokenProvider) adc)
                .setTargetAudience(baseUrl)
                .build();
    }

    public String listBooks() throws IOException, InterruptedException {
        credentials.refreshIfExpired();
        HttpRequest request = HttpRequest.newBuilder(URI.create(baseUrl + "/api/books"))
                .header("Authorization", "Bearer " + credentials.getIdToken().getTokenValue())
                .build();
        return http.send(request, HttpResponse.BodyHandlers.ofString()).body();
    }
}
----

Derived from https://docs.cloud.google.com/run/docs/authenticating/service-to-service[Service-to-service authentication]
and https://docs.cloud.google.com/docs/authentication/application-default-credentials[Application Default Credentials].

`CATALOG_INSTANCE` is the instance connection name (`my-project-id:us-central1:bookshelf-catalog`); the Cloud SQL JDBC
socket factory dependency and the Spring Cloud GCP starter versions follow the BOM described in
xref:cloud/google-cloud/developer-tools-and-devops.adoc[]. Spring Cloud GCP 8.x targets Spring Boot 4; use 7.4.x
for Spring Boot 3.

== Serving a static site from Cloud Run

Packaging static files in an NGINX container and deploying it to Cloud Run works and is simple, but a Cloud Storage
bucket behind a global external Application Load Balancer with Cloud CDN is usually cheaper, faster at the edge and
needs no instance. Bookshelf therefore serves the front end from `bookshelf-web-$PROJECT_ID` (see
xref:cloud/google-cloud/cloud-storage.adoc[] and xref:cloud/google-cloud/cloud-cdn-and-media-cdn.adoc[]) and keeps
Cloud Run for code that must run. Choose Cloud Run for a static site only when it is served together with server-side
rendering or when the build artefacts must be versioned as a container.

== Observability

Cloud Run writes stdout and stderr, request logs and system logs to Cloud Logging automatically, exports request
count, latency, instance count, CPU and memory metrics to Cloud Monitoring, and reports unhandled exceptions to
Error Reporting when they are logged in a supported format. Cloud Trace correlates requests that carry the
`traceparent` header.

[source,bash]
----
gcloud run services logs read "$SERVICE" --region="$REGION" --limit=50
gcloud logging read \
  'resource.type="cloud_run_revision" AND resource.labels.service_name="catalog-api" AND severity>=ERROR' \
  --limit=20 --freshness=1h
----

Derived from https://docs.cloud.google.com/run/docs/logging[Logging and viewing logs in Cloud Run].

Write structured JSON logs (`severity`, `message`) to stdout so Cloud Logging parses them; see
xref:backend/springboot/logging.adoc[]. Dashboards and alerts are in
xref:cloud/google-cloud/monitoring-and-observability.adoc[].

== Troubleshooting

[cols="2,4",options="header"]
|===
|Symptom |Typical cause and fix

|Revision not ready: "container failed to start and listen on the port defined by PORT"
|The process exits, listens on `127.0.0.1` instead of `0.0.0.0`, ignores `PORT`, is built for the wrong architecture, or needs
more than the startup time. Read the revision's logs and test the image locally with `docker run -e PORT=8080 -p 8080:8080`.
Raise `--cpu-boost`, add a startup probe with enough `failureThreshold`.

|403 Forbidden
|The caller lacks `run.routes.invoke` (grant `roles/run.invoker`), or ingress blocks the source.

|401 Unauthorized
|Missing or malformed bearer token, or the `aud` claim does not match the service URL.

|429 Too Many Requests
|No instance available: the service reached `--max-instances` or a quota. Raise the cap or concurrency, or reduce traffic.

|500 or 503
|Application error, a crash such as running out of memory, or a traffic spike faster than scale-out with slow starts.
Add minimum instances or startup boost, and retry with exponential backoff.

|504 Gateway Timeout
|The request ran longer than `--timeout`. Raise the timeout (up to 60 minutes) or move long work to a job.

|Memory limit exceeded
|The instance is terminated. Increase `--memory` (in-memory volumes count) or look for leaks.

|Cannot reach private IP
|Direct VPC egress not configured, wrong `--vpc-egress`, firewall rule missing for the network tag, or the subnet is full.

|Secret not found or permission denied
|The service account lacks `roles/secretmanager.secretAccessor`, the secret is regional (not supported) or the pinned version is disabled.

|Background work stops between requests
|Request-based billing throttles CPU outside requests; use instance-based billing.
|===

gcloud run revisions describe REVISION --region="$REGION" --format=yaml
gcloud run services describe "$SERVICE" --region="$REGION" \
  --format='value(status.conditions)'
----

Derived from https://docs.cloud.google.com/run/docs/troubleshooting[Troubleshoot Cloud Run issues] and

== Clean up

Delete in dependency order. Services and revisions cost nothing at rest when scaled to zero, but images, load balancer
components and Secret Manager versions do.

[source,bash]
----
# Load balancer pieces (reverse order of creation)
gcloud compute forwarding-rules delete catalog-https --global --quiet
gcloud compute target-https-proxies delete catalog-proxy --quiet
gcloud compute ssl-certificates delete catalog-cert --global --quiet
gcloud compute url-maps delete catalog-map --quiet
gcloud compute backend-services delete catalog-backend --global --quiet
gcloud compute network-endpoint-groups delete catalog-neg --region="$REGION" --quiet
gcloud compute addresses delete catalog-lb-ip --global --quiet

gcloud beta run domain-mappings delete --domain=catalog.example.com --region="$REGION" --quiet
gcloud run services delete "$SERVICE" --region="$REGION" --quiet

# Images built by source deploys
gcloud artifacts repositories delete cloud-run-source-deploy --location="$REGION" --quiet
gcloud iam service-accounts delete "$RUNTIME_SA" --quiet
----

Derived from https://docs.cloud.google.com/run/docs/managing/services#delete[Delete services] and
https://docs.cloud.google.com/sdk/gcloud/reference/run/services/delete[gcloud run services delete].

Skip the commands for pieces you did not create. Deleting the service also removes its revisions. Secret Manager
secrets and Cloud SQL instances belong to their own pages' clean up steps. For a throwaway project, deleting the
project removes everything, with the usual 30-day recovery window (see
xref:cloud/google-cloud/resource-hierarchy-and-projects.adoc[]).
