Welcome to the Google Cloud reference. It documents Google Cloud for practitioners who work from the Google Cloud
console and the gcloud CLI -- provisioning resources, wiring them together, and operating what results -- rather than
from the perspective of a certification-style conceptual overview. It is written for developers and operators who
already build software (the rest of this site covers the Java, web and database sides) and now need to run it on
Google Cloud. Examples across this section target the gcloud CLI (the 586 line), the Google Cloud Client Libraries
for Java through the `libraries-bom`, Spring Cloud GCP 8.x (Spring Boot 4) and 7.4.x (Spring Boot 3), Terraform with
the `hashicorp/google` provider v8, and GKE 1.35 on the Regular release channel; this baseline was re-verified as
current on 2026-10-01, and each page also names the service-specific versions it depends on, since Google Cloud ships
new capabilities to individual services on its own schedule. Prices are never quoted: each page describes the
pricing model and cost drivers and links the dated official pricing page. Every page also states the launch stage
(Preview or GA) of anything that is not generally available and records the dates of recent retirements and renames,
because several products widely documented in older guides have since been replaced.

== The Bookshelf scenario

Most pages in this section build up one running example, *Bookshelf*: a static web front end, a `catalog-api`
(Spring Boot), an `orders-api` and a `notifier` worker that sends order-confirmation emails. It is the same
application as in the xref:cloud/azure/index.adoc[Azure section] and the xref:cloud/aws/index.adoc[AWS section], so
the three clouds can be compared side by side. Every resource follows one naming convention, so a command copied from
one page composes with a command copied from another:

[cols="1,2", options="header"]
|===
| Concern | Name / value

| Project and region
| `PROJECT_ID=$(gcloud config get-value project)` (placeholders `my-project-id` and `<project-number>`); region `us-central1` unless a page needs another

| Artifact Registry
| Docker repository `bookshelf` -- images `us-central1-docker.pkg.dev/$PROJECT_ID/bookshelf/catalog-api`, `.../orders-api` and `.../notifier`

| Cloud Run
| services `catalog-api` (source deploy first, then an image, then revisions and traffic splits) and `orders-api`; job `nightly-report`; `notifier` as an Eventarc-triggered service or Cloud Run function on the Pub/Sub topic `orders`

| Cloud Storage
| `bookshelf-web-$PROJECT_ID` (static site, behind a global external Application Load Balancer and Cloud CDN), `bookshelf-uploads-$PROJECT_ID`

| Databases
| Cloud SQL for PostgreSQL `bookshelf-catalog` (database `catalog`; AlloyDB `bookshelf-alloy` as the scale-up variant); Firestore with MongoDB compatibility `orders` (or MongoDB Atlas); Memorystore for Valkey `bookshelf-cache`

| Secrets and configuration
| Secret Manager `catalog-db-password` and `sendgrid-api-key`; Parameter Manager parameter `bookshelf-settings`

| GKE
| Autopilot cluster `bookshelf-gke`, Workload Identity Federation for GKE, Gateway API

| Gateways
| API Gateway `bookshelf-api` (Apigee as the enterprise variant); Cloud Armor policy `bookshelf-policy`

| VPN
| HA VPN `bookshelf-vpn` with a Cloud Router to a simulated on-premises VPC; IAP TCP forwarding for administrator access

| Email
| a third-party SMTP relay or API (SendGrid), its key kept in Secret Manager

| Java package
| `com.example.bookshelf`

| Shell variables
| `PROJECT_ID`, `REGION`, `SERVICE`, `BUCKET` and so on -- never real IDs or keys
|===

Bookshelf starts on Cloud Run, where `catalog-api` is first deployed from source, then from an image, with revisions
and traffic splits, and later moves its services onto a GKE Autopilot cluster (`bookshelf-gke`), covered in
xref:cloud/google-cloud/gke-clusters.adoc[] and xref:cloud/google-cloud/gke-microservices.adoc[]. The figure below
shows Bookshelf's *end state*, once every group's pages have been applied: a global external Application Load
Balancer with Cloud CDN and Cloud Armor in front of a private Cloud Storage bucket and API Gateway, the GKE-hosted
services, the databases, secrets and configuration reached over private connectivity, Pub/Sub and Eventarc feeding
the `notifier` worker that sends email through a third-party provider, an HA VPN for the on-premises path, and Cloud
Logging and Cloud Monitoring watching all of it. It is not the architecture a reader has running after just the
Compute pages -- see xref:cloud/google-cloud/choosing-a-compute-service.adoc[] and
xref:cloud/google-cloud/cloud-run.adoc[] for the earlier, Cloud Run-only stage.

== Reading path

Read this section foundations first -- the cloud model, accounts, regions, the resource hierarchy, identity and
infrastructure as code -- then compute, where Bookshelf's services first get deployed. From there, storage and CDN
put the static front end and its assets somewhere durable and fast to serve, and managed databases give `catalog-api`
and `orders-api` somewhere to persist data. Security and runtime configuration then centralize the secrets and
settings every earlier page referenced loosely, before networking, gateways and VPN lock the whole thing behind a
private network and a proper API front door. Email and integration wire `notifier` up to the outside world, and
operations, governance and beyond closes the loop: monitoring, cost, compliance, migration paths and the developer
tooling that ties CI/CD back to everything above. A reader who only needs one topic can jump straight to its page;
each page states which earlier pages it assumes.
