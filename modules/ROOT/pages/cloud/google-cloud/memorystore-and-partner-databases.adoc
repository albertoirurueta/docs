== Memorystore in brief

Memorystore is Google Cloud's family of managed in-memory data stores. Bookshelf uses it as a cache-aside layer:
`catalog-api` looks a book up in the cache first, falls back to Cloud SQL on a miss, and writes the row back with a time to
live. The points that matter when you choose an offering:

* *Valkey is the engine to pick for new work.* Memorystore for Valkey reached general availability on 2025-04-02 and
  Google positions it as the recommended choice for new Memorystore deployments. It runs Valkey, the BSD-licensed fork
  of Redis, so core Redis data structures and commands work unchanged, but Redis 8 modules (Query Engine, JSON, vector
  sets) are not part of it. Available engine versions are 7.2, 8.0, 9.0 and 9.1, and an instance cannot be downgraded
  after you pick a version. Older guides show only "Memorystore for Redis".
* *Memorystore for Redis Cluster* is the sharded Redis-protocol offering. It is the one to choose when you need the
  Redis Query Engine for text and vector search, native JSON, or RDB and AOF persistence on a clustered service; see
  xref:database/redis/deploying-on-google-cloud.adoc[] for the limits.
* *Memorystore for Redis* (Basic and Standard tiers) is the original single-shard service, tracking Redis up to 7.2. It
  stays supported for existing workloads, but Google steers new ones to the two offerings above.
* *Memorystore for Memcached is deprecated.* Google announced that no new projects can use it after 2027-02-01 and that
  the service shuts down on 2029-01-31. If you have a Memcached cache, plan the move to Memorystore for Valkey before
  then; Bookshelf never used Memcached, so this page does not cover the migration beyond pointing to the deprecation page.
* *Private by design.* Every Memorystore instance is reachable only on private IP addresses. Valkey and Redis Cluster use
  Private Service Connect (PSC) endpoints in your VPC network; Memorystore for Redis uses private services access or
  direct peering. There is no public endpoint.
* *Not durable by default.* Treat Memorystore as a cache. Valkey and Redis Cluster can be configured with RDB or AOF
  persistence and automated backups, but a primary database for the books themselves stays in Cloud SQL (see
  xref:cloud/google-cloud/cloud-sql.adoc[]).

Reference: https://docs.cloud.google.com/memorystore/docs/valkey/product-overview[Memorystore for Valkey overview],
https://docs.cloud.google.com/memorystore/docs/valkey/release-notes[Memorystore for Valkey release notes] and
https://docs.cloud.google.com/memorystore/docs/memcached/deprecation/memcached[Memorystore for Memcached deprecation].

Memorystore for Valkey also supports vector search on newer versions and cross-region replication of instances, which
the Redis reference page describes. Pricing is per node-hour by node type (and per shard and replica), plus backup
storage and inter-zone or cross-region data transfer; there is no per-request charge. Check the dated
https://cloud.google.com/memorystore/docs/valkey/pricing[Memorystore for Valkey pricing] page before choosing a node
type, because the smallest node types are cheap enough for a development instance but are not a production sizing.

== Quick start: Memorystore for Valkey

An instance in cluster mode with one shard and one replica is the smallest highly available shape and the one used for
`bookshelf-cache`. Both the console and the CLI need the same two prerequisites: the API enabled and a *service
connection policy* in the VPC network and region where the instance lives. The policy authorizes Memorystore to create
PSC endpoints in a subnet you choose; without it, instance creation fails with a network error.

=== In the Google Cloud console

. Open the project picker at the top of the console and select your project (or open Cloud Shell, which is already
  authenticated).
. Open *Memorystore* > *Valkey* (type "Memorystore for Valkey" in the search box). If the page asks you to enable the API,
  choose *Enable*; this enables the Memorystore for Valkey, Network Connectivity and Service Consumer Management APIs.
. Choose *Create instance*. Enter the instance ID `bookshelf-cache`, pick the region `us-central1` (the same region as
  `catalog-api`) and choose *Multi-zone* availability.
. Leave *Cluster Mode* on *Enabled*, pick a node type and set the shard count to 1 and the replica count to 1.
. Under *Networking*, choose the VPC network and the subnet. If no service connection policy exists, the console offers
  to create one; accept and wait for it to finish.
. Under *Security*, choose *IAM authentication* and *Server authentication* for in-transit encryption. Leave encryption
  at rest on the Google-managed key unless you must use a customer-managed key from Cloud KMS (see
  xref:cloud/google-cloud/secret-manager-and-kms.adoc[]).
. Keep the default Valkey version, leave persistence off for a pure cache, and choose *Create instance*. Creation takes a
  few minutes; when the status is *Ready*, the *Instance details* page shows the discovery endpoint to connect to.

Reference: https://docs.cloud.google.com/memorystore/docs/valkey/create-instances[Create instances] and
https://docs.cloud.google.com/memorystore/docs/valkey/networking[Networking for Memorystore for Valkey].

=== With the gcloud CLI

Start with the APIs and the service connection policy. The policy is created once per network and region and is shared by
every Memorystore for Valkey and Redis Cluster instance there:

[source,bash]
----
export PROJECT_ID=$(gcloud config get-value project)
export REGION=us-central1
export NETWORK=default            # your VPC network
export SUBNET=default             # a subnet in $REGION with free addresses

gcloud services enable memorystore.googleapis.com \
    networkconnectivity.googleapis.com \
    serviceconsumermanagement.googleapis.com

gcloud network-connectivity service-connection-policies create bookshelf-memorystore-policy \
    --network="$NETWORK" \
    --region="$REGION" \
    --service-class=gcp-memorystore \
    --subnets="projects/$PROJECT_ID/regions/$REGION/subnetworks/$SUBNET" \
    --description="PSC endpoints for Memorystore"
----

Reference: https://docs.cloud.google.com/sdk/gcloud/reference/network-connectivity/service-connection-policies/create[gcloud network-connectivity service-connection-policies create].
The caller needs `roles/memorystore.admin` (or Owner or Editor) to create instances, and a role that includes
`networkconnectivity.serviceConnectionPolicies.create` for the policy; the subnet must have free addresses because each
instance consumes a few of them.

Create the Valkey instance next:

[source,bash]
----
gcloud memorystore instances create bookshelf-cache \
    --location="$REGION" \
    --mode=cluster \
    --shard-count=1 \
    --replica-count=1 \
    --node-type=standard-small \
    --engine-version=9.1 \
    --authorization-mode=iam-auth \
    --transit-encryption-mode=server-authentication \
    --endpoints="[{\"connections\": [{\"pscAutoConnection\": {\"network\": \"projects/$PROJECT_ID/global/networks/$NETWORK\", \"projectId\": \"$PROJECT_ID\"}}]}]"

gcloud memorystore instances describe bookshelf-cache \
    --location="$REGION" \
    --format="value(state,endpoints)"
----

Reference: https://docs.cloud.google.com/sdk/gcloud/reference/memorystore/instances/create[gcloud memorystore instances create].
The same page lists `--psc-auto-connections=network=...,projectId=...` as a shorthand for the network and project. Take the
accepted node types from `gcloud memorystore instances create --help`; the names above are the Google-documented shapes
(`shared-core-nano`, `standard-small`, `highmem-medium`, `highmem-xlarge`), and a larger `--shard-count` spreads keys
and throughput across more primaries. Repeat the `describe` call until the state is `ACTIVE`, and note the discovery
endpoint address and port for the client.

Test the connection from a Compute Engine VM or Cloud Shell in the same VPC network. IAM authentication means the
password you give the client is a short-lived access token, never a stored secret, and TLS needs the instance's
certificate authority:

[source,bash]
----
gcloud memorystore instances get-certificate-authority bookshelf-cache \
    --location="$REGION" > ca.pem

CACHE_HOST=<discovery-endpoint-ip>      # copy from the describe output
TOKEN=$(gcloud auth print-access-token)

valkey-cli -c -h "$CACHE_HOST" -p 6379 --tls --cacert ca.pem --pass "$TOKEN" PING
valkey-cli -c -h "$CACHE_HOST" -p 6379 --tls --cacert ca.pem --pass "$TOKEN" \
    SET book:9780134685991 '{"title":"Effective Java"}' EX 300
----

Reference: https://docs.cloud.google.com/memorystore/docs/valkey/connect-instance[Connect to a Memorystore for Valkey instance].
`redis-cli` works the same way if you have it installed. The `-c` flag makes the client follow cluster redirections.

=== Choosing a node type and sizing

Memorystore for Valkey is billed by node, so sizing is a choice of node type, shard count and replica count rather than
a gigabyte figure:

* *Shards* split the keyspace across primaries. Add shards when the data does not fit on one node or when throughput on
  a single primary is the bottleneck. Shard count can be changed on a running instance, with a short period of
  rebalancing.
* *Replicas* (0 to 5 per shard) give failover and extra read capacity. One replica per shard in a multi-zone instance is
  the smallest highly available layout; zero replicas is acceptable for a development cache only.
* *Node type* sets memory per node. Leave headroom for replication buffers, persistence snapshots and fragmentation
  rather than filling the node, and set an eviction policy that matches the use (see
  xref:database/redis/architecture-keyspace-and-eviction.adoc[]).
* *Cluster mode disabled* gives a single-shard instance with the classic client behaviour. Choose it only for clients
  that cannot speak the cluster protocol.

=== Redis Cluster and Redis

The older offerings use their own command groups and the same create-then-connect shape:

[source,bash]
----
# Memorystore for Redis Cluster: sharded, PSC connectivity, same service connection policy
gcloud redis clusters create bookshelf-cache-redis \
    --region="$REGION" \
    --shard-count=1 \
    --replica-count=1 \
    --node-type=redis-standard-small \
    --network="projects/$PROJECT_ID/global/networks/$NETWORK"

# Memorystore for Redis: Standard tier (replica and automatic failover), private services access
gcloud redis instances create bookshelf-cache-legacy \
    --region="$REGION" \
    --tier=standard \
    --size=1 \
    --redis-version=redis_7_2 \

    --connect-mode=private-service-access
----

Reference: https://docs.cloud.google.com/sdk/gcloud/reference/redis/clusters/create[gcloud redis clusters create] and
https://docs.cloud.google.com/sdk/gcloud/reference/redis/instances/create[gcloud redis instances create]. Flag sets differ

== IAM authentication

Memorystore for Valkey and Redis Cluster can authenticate a client with its Google Cloud identity instead of a static
password. The application runs as an attached service account (see
xref:cloud/google-cloud/identity-and-access.adoc[]); the client library obtains an OAuth 2.0 access token for that
account through Application Default Credentials and presents it as the AUTH password. Nothing is stored in Secret
Manager or in a configuration file. The details that matter:

* The identity needs `roles/memorystore.dbConnectionUser`, which holds the `memorystore.instances.connect` permission.
  Grant it on the project, or on the instance's resource where your policy allows.
* The default access token lifetime is one hour (it can be extended up to 12 hours when you generate it), so a client
  must refresh the token and use the fresh one on every new connection. A connection that is already authenticated stays
  authenticated after the token expires; only new connections need a valid token.
* IAM authentication is chosen at instance creation (or turned on later with an update); the alternative
  `token-auth` mode uses a password-style token managed in Memorystore, and `auth-disabled` leaves the instance open to
  anything that can reach the PSC endpoint.
* Compute Engine VMs and GKE nodes need the Cloud Platform access scope for the token to be usable. On Cloud Run and on GKE
  with Workload Identity Federation the attached identity already carries it.

[source,bash]
----
# Service account used by catalog-api to reach the cache
gcloud iam service-accounts create catalog-api \
    --display-name="Bookshelf catalog-api"

gcloud projects add-iam-policy-binding "$PROJECT_ID" \
    --member="serviceAccount:catalog-api@$PROJECT_ID.iam.gserviceaccount.com" \
    --role="roles/memorystore.dbConnectionUser"
----

Reference: https://docs.cloud.google.com/memorystore/docs/valkey/about-iam-auth[About IAM authentication] and
https://docs.cloud.google.com/memorystore/docs/valkey/manage-iam-auth[Manage IAM authentication]. Older guides authenticate
with a long AUTH string stored in a secret, or skip authentication entirely and rely on the private network; IAM
authentication is the current approach, and on Cloud Run the service account is simply set with `--service-account`, as
in xref:cloud/google-cloud/cloud-run.adoc[].

== Using it from Spring Boot

`catalog-api` is a Spring Boot application, so the cache is reached through Spring Data Redis and the Lettuce client, and
the Spring cache abstraction hides it behind `@Cacheable`. Add the usual starters and the Google auth library, which
supplies Application Default Credentials:

[source,xml]
----
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-data-redis</artifactId>
</dependency>
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-cache</artifactId>
</dependency>
<dependency>
    <groupId>com.google.auth</groupId>
    <artifactId>google-auth-library-oauth2-http</artifactId>
</dependency>
----

The configuration class below builds a cluster-aware Lettuce connection whose credentials provider asks Application
Default Credentials for a current token each time Lettuce needs to (re)authenticate. The discovery endpoint and the
trust store come from properties:

[source,java]
----
package com.example.bookshelf.config;

import com.google.auth.oauth2.GoogleCredentials;
import io.lettuce.core.RedisCredentials;
import io.lettuce.core.RedisCredentialsProvider;
import io.lettuce.core.SslOptions;
import io.lettuce.core.cluster.ClusterClientOptions;
import java.io.File;
import java.io.IOException;
import java.util.List;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.data.redis.connection.RedisClusterConfiguration;
import org.springframework.data.redis.connection.lettuce.LettuceClientConfiguration;
import org.springframework.data.redis.connection.lettuce.LettuceConnectionFactory;
import reactor.core.publisher.Mono;

@Configuration
class CacheConfig {

    @Bean
    LettuceConnectionFactory redisConnectionFactory(
            @Value("${bookshelf.cache.host}") String host,
            @Value("${bookshelf.cache.port:6379}") int port,
            @Value("${bookshelf.cache.ca-file}") File caFile) throws IOException {

        GoogleCredentials credentials = GoogleCredentials.getApplicationDefault()
                .createScoped("https://www.googleapis.com/auth/cloud-platform");

        // Resolved on every new connection; the credentials object caches and refreshes the token itself.
        RedisCredentialsProvider iamToken = () -> Mono.fromSupplier(() -> {
            try {
                credentials.refreshIfExpired();
                return RedisCredentials.just(null, credentials.getAccessToken().getTokenValue());
            } catch (IOException e) {
                throw new IllegalStateException("Could not obtain an IAM access token", e);
            }
        });

        SslOptions ssl = SslOptions.builder().trustManager(caFile).build();

        LettuceClientConfiguration client = LettuceClientConfiguration.builder()
                .useSsl()
                .and()
                .clientOptions(ClusterClientOptions.builder().sslOptions(ssl).build())
                .build();

        RedisClusterConfiguration cluster = new RedisClusterConfiguration(List.of(host + ":" + port));
        LettuceConnectionFactory factory = new LettuceConnectionFactory(cluster, client);
        factory.setRedisCredentialsProviderFactory(configuration -> iamToken);
        return factory;
    }
}
----

Reference: https://docs.cloud.google.com/memorystore/docs/valkey/connect-instance[Connect to a Memorystore for Valkey instance]
and https://cloud.google.com/java/docs/reference/google-auth-library/latest/com.google.auth.oauth2.GoogleCredentials[GoogleCredentials].
The `RedisCredentialsProviderFactory` hook exists on `LettuceConnectionFactory` in Spring Data Redis 3.x and 4.x; verify
the signature in the version your Spring Boot release manages. Then cache the catalog lookup with the Spring cache
abstraction:

[source,java]
----
package com.example.bookshelf.catalog;

import org.springframework.cache.annotation.Cacheable;
import org.springframework.stereotype.Service;

@Service
class BookService {

    private final BookRepository repository;

    BookService(BookRepository repository) {
        this.repository = repository;
    }

    @Cacheable(cacheNames = "books", key = "#isbn")
    Book findByIsbn(String isbn) {
        return repository.findByIsbn(isbn).orElseThrow(() -> new BookNotFoundException(isbn));
    }
}
----

[source,yaml]
----
spring:
  cache:
    type: redis
    redis:
      time-to-live: 5m
bookshelf:
  cache:
    host: ${BOOKSHELF_CACHE_HOST}      # discovery endpoint, injected as an environment variable
    port: 6379
    ca-file: /etc/bookshelf/memorystore-ca.pem
----

Reference: https://docs.spring.io/spring-boot/reference/io/caching.html[Spring Boot caching]. Cache configuration
properties and serializers are explained in xref:database/redis/spring-boot-redis-as-a-cache.adoc[]. The CA certificate
file is mounted into the container; on Cloud Run use a secret volume (see
xref:cloud/google-cloud/secret-manager-and-kms.adoc[]) or bake the public CA into the image, since a certificate authority
is public material. Because the instance is reachable only on private IP addresses, `catalog-api` on Cloud Run connects
through Direct VPC egress into the same VPC network and region as the PSC endpoint, which
xref:database/redis/deploying-on-google-cloud.adoc[] walks through end to end.

== Networking and security

* *Private Service Connect.* The service connection policy lets Memorystore place an endpoint (an internal IP address) in
  your subnet; clients in the VPC, in peered or connected networks (through HA VPN or Interconnect, see
  xref:cloud/google-cloud/vpn-and-hybrid-connectivity.adoc[]), and in Cloud Run or GKE with network access reach it on
  that address. Nothing is exposed on the internet. See xref:cloud/google-cloud/vpc-networking.adoc[] for subnets, firewall
  rules and Private Service Connect in general.
* *Firewall.* PSC endpoints are not filtered by instance firewall rules the way VM traffic is. Control who may connect with
  IAM authentication plus network reachability (which subnets and connectors can route to the endpoint).
* *TLS.* Choose server authentication so traffic is encrypted in transit and verify the instance CA in the client.
* *Encryption at rest.* Google-managed keys by default; customer-managed encryption keys from Cloud KMS are an option
  chosen at creation time.
* *Redis ACLs.* Memorystore for Valkey also supports ACL policies for per-user command and key restrictions; see
  xref:database/redis/security.adoc[] for the ACL model.
* *Least privilege.* Give the application `roles/memorystore.dbConnectionUser` and give operators `roles/memorystore.admin`
  or the narrower editor and viewer roles; never use basic Owner and Editor roles in production.

=== Pricing model and limits

* *Cost drivers.* Memorystore is billed per node-hour (node type times shards times replicas), plus backup storage and
  network traffic between zones and regions. There is no charge for requests, and an instance bills while it exists
  whether or not it is used.
* *Free tier.* There is no free Memorystore tier. Use `shared-core-nano` or `standard-small` node types for experiments and
  delete the instance when you finish.
* *Quotas.* Instance count, shard count and total node memory per project and region are quota-limited; see
  https://docs.cloud.google.com/memorystore/docs/valkey/quotas[Memorystore for Valkey quotas and limits] and request an
  increase in the console under *IAM & Admin* > *Quotas & System Limits* before a large deployment.
* *Launch stages.* Memorystore for Valkey and Redis Cluster are generally available. New features such as cross-region
  replication, vector search and newer engine versions arrive in Preview first; the release notes name the stage for each.

== Marketplace and partner databases

Several engines this site documents have no first-party Google Cloud service. They are either bought as partner software
as a service (SaaS) through Google Cloud Marketplace or run by you on GKE or Compute Engine. The workflow for every
Marketplace partner is the same, and it is not a Google Cloud service in the sense of IAM or the gcloud CLI.

image::google-cloud-partner-database-options.svg["A grid of Valkey and Redis, Elasticsearch, Couchbase, Neo4j, Qdrant, Solr and Prometheus against three columns: operated by Google, Marketplace SaaS, and self-hosted on GKE",width=860]

=== What Marketplace billing means

* The subscription is a Marketplace listing: you accept the vendor's terms and the vendor's plan, and the usage appears as
  a line item on your Google Cloud invoice. Purchases can count toward a committed Google Cloud spend when the listing is
  eligible and your billing account is enrolled; ask your Google Cloud account team to confirm for your contract.
* The cluster itself lives in the vendor's control plane, often in a vendor-owned project or in the vendor's cloud account,
  not in your project. IAM roles, Cloud KMS keys, `gcloud` commands and Cloud Asset Inventory in your project do not manage
  it. Billing, user management and deletion happen in the vendor's console.
* The Marketplace subscription must be active for the cluster to run. Deleting the cluster does not always cancel the
  subscription, so check both when you clean up.
* Connectivity is either a public TLS endpoint that you protect with an IP allow list, or a private connection. Prefer
  private: Private Service Connect where the vendor offers it, otherwise VPC peering, so database traffic stays off the
  public internet. Keep the vendor API key or connection string in Secret Manager (see
  xref:cloud/google-cloud/secret-manager-and-kms.adoc[]) and never in source control or in an environment variable file.

=== In the Google Cloud console

The flow starts in the Google Cloud console and finishes in the vendor's console. It is the same for every partner on this
list, so it is described once:

. In the Google Cloud console, open the project picker and select the project that owns the billing account.
. Open *Marketplace* (*Navigation menu* > *Marketplace*) and search for the product, for example "Elastic Cloud",
  "Couchbase Capella", "Neo4j AuraDB", "Qdrant Cloud" or "Redis Cloud".
. Open the listing, review the plans, pricing and terms, and choose *Subscribe* (or *Purchase*). Accepting the terms is a
  commercial commitment, so confirm that the plan and the billing account are what you intend.
. Choose *Sign up with <vendor>* or *Manage on provider*. You are redirected to the vendor's console to create or link an
  account.
. In the vendor's console, create the deployment, selecting Google Cloud and the region closest to `catalog-api`
  (`us-central1` for Bookshelf).
. Configure private connectivity in the vendor's console (a Private Service Connect service attachment or VPC peering),
  then create the matching endpoint or peering on the Google Cloud side as the vendor's documentation describes.

Reference: https://docs.cloud.google.com/marketplace/docs/partners[Google Cloud Marketplace documentation].

=== With the gcloud CLI

Subscribing happens in the console and the vendor's tooling, but the Google Cloud side of the private connection and the
secret that holds the vendor key are ordinary `gcloud` resources. A Private Service Connect endpoint to a vendor's
service attachment looks like this (the attachment URI is supplied by the vendor):

[source,bash]
----
gcloud compute addresses create partner-psc-ip \
    --region="$REGION" --subnet="$SUBNET"

gcloud compute forwarding-rules create partner-psc-endpoint \
    --region="$REGION" \
    --network="$NETWORK" \
    --address=partner-psc-ip \
    --target-service-attachment=<vendor-service-attachment-uri>

# Store the vendor's API key where the application can read it with IAM
echo -n "<vendor-api-key>" | gcloud secrets create partner-api-key --data-file=-
----

Reference: https://docs.cloud.google.com/vpc/docs/configure-private-service-connect-services[Private Service Connect: access published services through endpoints]
and https://docs.cloud.google.com/secret-manager/docs/creating-and-accessing-secrets[Create a secret]. Replace
`<vendor-service-attachment-uri>` and `<vendor-api-key>` with the values from the vendor's console; both are placeholders.
The vendor must approve the connection from your project before traffic flows.

*Couchbase Capella* is Couchbase's database-as-a-service, deployed into a Capella-managed network in a Google Cloud region

*Neo4j AuraDB* is the managed Neo4j graph database, available on Google Cloud regions and through Marketplace, reachable

*Qdrant Cloud* is the managed vector database from the Qdrant team, with clusters in Google Cloud regions and a Marketplace

== Self-hosting on GKE

Anything in the previous section can also run in your own GKE cluster (see xref:cloud/google-cloud/gke-clusters.adoc[] and
xref:cloud/google-cloud/gke-microservices.adoc[]), and for Apache Solr it is the only practical way, because neither Google
Cloud nor Marketplace sells a managed Solr. Self-hosting trades the vendor's operations team for flexibility and an
unmetered license fee, and it makes you responsible for upgrades, backups, scaling and incident response.

[cols="1,2,2",options="header"]
|===
| Engine | Operator or chart | Notes

| Solr
| https://solr.apache.org/operator/[Apache Solr Operator] (Helm and CRDs), with ZooKeeper
| Learn the engine from xref:database/solr/getting-started.adoc[] and xref:database/solr/deployment-and-upgrades.adoc[]. The Solr Operator project has a GKE walkthrough.

| Elasticsearch
| Elastic Cloud on Kubernetes (ECK)
| Operator manages nodes, TLS and rolling upgrades; the license tier decides which features are available.

| Qdrant
| Qdrant Helm chart
| Google publishes a tutorial for deploying Qdrant on GKE; Qdrant also documents distributed deployments.

| Neo4j
| Neo4j Helm charts
| A clustered deployment needs the Enterprise license; the Community Edition is a single instance.

| Couchbase
| Couchbase Autonomous Operator
| Operator manages cluster topology, upgrades and rebalancing; Enterprise features need a license.
|===

=== Storage on GKE

Stateful engines need durable volumes, and the StorageClass decides how they behave:

* *Hyperdisk and Persistent Disk through the CSI driver.* GKE ships the Compute Engine persistent disk CSI driver and the
  default `StorageClass` objects (`standard-rwo`, `premium-rwo`, and Hyperdisk-backed classes on supporting node types). A
  `PersistentVolumeClaim` creates a zonal or regional disk per Pod. Use SSD-backed classes for Solr, Elasticsearch and Neo4j
  data; use a regional disk class when a single-zone failure must not lose the volume. See
  xref:cloud/google-cloud/block-and-file-storage.adoc[] for disk types and snapshots.
* *Filestore CSI.* Filestore gives a `ReadWriteMany` NFS volume, useful for shared index directories or backups written by
  several Pods. It is slower and costlier than a block disk, so keep indexes on block storage.
* *Backups.* Use volume snapshots (`VolumeSnapshot` through the CSI snapshot controller) or the engine's own backup to
  Cloud Storage (see xref:cloud/google-cloud/cloud-storage.adoc[]); a PersistentVolume alone is not a backup.

[source,yaml]
----
# A StorageClass for engine data: SSD-backed, expandable, volume retained until you delete the claim
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: bookshelf-data
provisioner: pd.csi.storage.gke.io
parameters:
  type: pd-ssd
volumeBindingMode: WaitForFirstConsumer
allowVolumeExpansion: true
reclaimPolicy: Retain
----

Reference: https://docs.cloud.google.com/kubernetes-engine/docs/how-to/persistent-volumes/gce-pd-csi-driver[Use the Compute Engine persistent disk CSI driver]
and https://docs.cloud.google.com/kubernetes-engine/docs/concepts/storage-overview[About storage for GKE clusters]. A Qdrant
deployment on GKE with Helm, following the Google tutorial, looks like this:

[source,bash]
----
gcloud container clusters get-credentials bookshelf-gke --region "$REGION"

helm repo add qdrant https://qdrant.github.io/qdrant-helm
helm repo update

helm install qdrant qdrant/qdrant \
    --namespace data --create-namespace \
    --set replicaCount=3 \
    --set persistence.size=20Gi \
    --set persistence.storageClassName=bookshelf-data

kubectl get pods --namespace data --watch
----

Reference: https://docs.cloud.google.com/kubernetes-engine/docs/tutorials/deploy-qdrant[Deploy a Qdrant vector database on GKE].
Chart values change between releases; run `helm show values qdrant/qdrant` and pin a chart version in real use. The
Solr Operator follows the same shape (install CRDs and the operator chart, then apply a `SolrCloud` resource); see the
https://solr.apache.org/operator/articles/explore-v030-gke.html[Solr Operator GKE walkthrough].

=== When self-hosting makes sense

* The engine has no managed offering on Google Cloud at all (Solr).
* You need an exact version, a plugin or an enterprise feature that the SaaS tier does not provide.
* Data residency or network isolation forbids a vendor-controlled control plane.
* The team already runs GKE and has the operational skill to handle upgrades, backups and recovery.

Choose the SaaS (Marketplace) option otherwise: a three-node stateful cluster is easy to start and slow to run well.
Whichever you pick, put the connection details in Secret Manager and give pods a Workload Identity Federation identity
instead of a downloaded key (see xref:cloud/google-cloud/identity-and-access.adoc[]).

== Agent Search as a managed alternative

*Agent Search* (formerly Vertex AI Search) is Google's managed search and retrieval service for websites, documents and
structured data. It indexes content, serves ranked results with optional generative answers, and handles scaling and
relevance without you operating a search cluster. For Bookshelf's site search it can replace a self-hosted Solr or an Elastic
Cloud deployment when you do not need Lucene-level control over analyzers, query parsers or custom scoring; if you do (custom
schemas, faceting rules, plugin analyzers), stay with Solr or Elasticsearch. It is a Google-operated service with its own
pricing model, so compare it with a Marketplace or self-hosted engine on cost, control and portability before committing. See
xref:cloud/google-cloud/ai-data-and-analytics-overview.adoc[] for the wider AI services.

== Managed Service for Prometheus

Google Cloud Managed Service for Prometheus is a Prometheus-compatible metrics store built on the same backend as Cloud
Monitoring (Monarch). You keep your Prometheus exporters, `PodMonitoring` configuration, PromQL and Grafana dashboards, and
Google stores and queries the data globally without you running Prometheus servers, long-term storage or federation. Learn
the engine itself from xref:database/prometheus/index.adoc[] and
xref:database/prometheus/storage-federation-and-remote-write.adoc[]; the wider monitoring and logging story is in
xref:cloud/google-cloud/monitoring-and-observability.adoc[].

There are two ways to collect data:

* *Managed collection.* Google runs the Prometheus-compatible collectors as a managed operator in the cluster and you describe
  scrape targets with Kubernetes custom resources. It is on by default for GKE Autopilot clusters on 1.25 and later and for GKE
  Standard clusters on 1.27 and later, and can be enabled on older clusters or on clusters outside GKE.
* *Self-deployed collection.* You keep running your own Prometheus (or the OpenTelemetry collector) and send data to the
  service through a drop-in replacement binary or the OpenTelemetry Google Cloud exporter. Use this to retain an existing
  `prometheus.yml` or when the cluster is not on GKE.

=== In the Google Cloud console

. Open *Monitoring* > *Metrics Explorer* in the project that owns the cluster. If it prompts you to enable the Cloud
  Monitoring API, choose *Enable*.
. Switch the query editor to *PromQL*, enter an expression such as `rate(http_server_requests_seconds_count[5m])`, and run it.
  Prometheus metrics appear with the prefix `prometheus.googleapis.com`.
. To manage collection on a cluster, open *Kubernetes Engine* > *Clusters*, select the cluster and look under *Features* >
  *Managed Service for Prometheus*, where you can enable or disable managed collection.
. Add Grafana by pointing a Prometheus data source at the Managed Service for Prometheus query endpoint; Google documents the
  data source syncer and the authentication you need.

Reference: https://docs.cloud.google.com/stackdriver/docs/managed-prometheus/query[Query using PromQL in Cloud Monitoring].

=== With the gcloud CLI and kubectl

[source,bash]
----
gcloud services enable monitoring.googleapis.com container.googleapis.com

# Managed collection is on by default on current Autopilot/Standard clusters; enable it on an older one
gcloud container clusters update bookshelf-gke \
    --region "$REGION" \
    --enable-managed-prometheus

gcloud container clusters get-credentials bookshelf-gke --region "$REGION"
----

Reference: https://docs.cloud.google.com/stackdriver/docs/managed-prometheus/setup-managed[Get started with managed collection].
Then describe what to scrape with a `PodMonitoring` resource, here the Spring Boot Actuator Prometheus endpoint of
`catalog-api` (see xref:backend/springboot/metrics-and-observability.adoc[] for exposing it):

[source,yaml]
----
apiVersion: monitoring.googleapis.com/v1
kind: PodMonitoring
metadata:
  name: catalog-api
  namespace: bookshelf
spec:
  selector:
    matchLabels:
      app.kubernetes.io/name: catalog-api
  endpoints:
    - port: http
      path: /actuator/prometheus
      interval: 30s
----

[source,bash]
----
kubectl apply -f catalog-api-podmonitoring.yaml
kubectl get podmonitoring --namespace bookshelf
----

Reference: https://docs.cloud.google.com/stackdriver/docs/managed-prometheus/setup-managed#gmp-pod-monitoring[PodMonitoring].
A `ClusterPodMonitoring` resource scrapes across namespaces. On a cluster outside GKE the collection operator is installed from
the `prometheus-engine` manifests and the node's service account needs `roles/monitoring.metricWriter`. On GKE with Workload
Identity Federation, grant that role to the collector's Kubernetes service account instead of a key (see
xref:cloud/google-cloud/gke-clusters.adoc[]).

=== Cost and limits

Managed Service for Prometheus is billed per metric sample ingested (with discounts for volume), plus the normal Cloud
Monitoring charges for reads and alerting, and storage is included for a retention period measured in months. High-cardinality
labels (user ids, request ids) multiply cost and slow queries; relabel or drop them in the `PodMonitoring` resource. Sample
rate (`interval`) is the lever you control most directly. See the dated
https://cloud.google.com/stackdriver/pricing#google-cloud-managed-service-for-prometheus-pricing[Managed Service for Prometheus pricing]
and use the Metrics Management page in Cloud Monitoring to find the metrics that cost the most. Alerting rules are evaluated
by the managed rule evaluator (`Rules` custom resources) or by Cloud Monitoring alerting policies in PromQL; see
xref:database/prometheus/recording-and-alerting-rules.adoc[] for the rule syntax.

== Troubleshooting

[cols="2,3",options="header"]
|===
| Symptom | Likely cause and fix

| Instance creation fails with a network or connection-policy error
| No service connection policy exists for the network and region, the subnet has no free addresses, or the Network
  Connectivity API is not enabled. Create the policy with `--service-class=gcp-memorystore` and check the subnet.

| Client cannot connect (timeout)
| The client is not in a network that routes to the PSC endpoint, or is in a different region. Confirm the endpoint IP
  from `gcloud memorystore instances describe` and connect from a VM in the same VPC. On Cloud Run, enable Direct VPC egress.

| TLS handshake errors
| The instance requires TLS and the client does not use it, or the client does not trust the instance's certificate
  authority. Download the CA and configure the trust store.

| `NOAUTH` or `WRONGPASS` errors
| IAM authentication is on and the client sent no token, the token expired, or the identity lacks
  `roles/memorystore.dbConnectionUser`. Fetch a fresh token for each new connection.

| `MOVED` or `CROSSSLOT` errors
| A non-cluster-aware client talks to a cluster-mode instance, or a multi-key command spans hash slots. Use a cluster-aware
  client and hash tags.

| Evictions or `OOM command not allowed`
| The node is full. Add shards or use a larger node type, shorten TTLs, or fix the eviction policy.

| Marketplace cluster is unreachable
| Private connectivity is not approved or the allow list does not include the client. Check the connection status in the
  vendor's console and the PSC forwarding rule on the Google Cloud side.

| Prometheus metrics do not appear
| Managed collection is off, the `PodMonitoring` selector matches no Pods, or the port name is wrong. Check
  `kubectl describe podmonitoring` and the operator Pods in `gmp-system`.

| Prometheus costs are higher than expected
| High-cardinality labels or too short a scrape interval. Find the heaviest metrics in Metrics Management and relabel or drop them.
|===

For Redis-level administration and monitoring see
xref:database/redis/administration-monitoring-and-troubleshooting.adoc[].

== Clean up

Delete in dependency order and confirm each resource disappears. Memorystore instances accrue charges until they are
deleted, and an instance cannot be deleted while deletion protection is on.

[source,bash]
----
# Memorystore for Valkey instance, then the service connection policy if nothing else uses it
gcloud memorystore instances delete bookshelf-cache --location="$REGION"
gcloud network-connectivity service-connection-policies delete bookshelf-memorystore-policy --region="$REGION"

# Other Memorystore offerings, if you created them
gcloud redis clusters delete bookshelf-cache-redis --region="$REGION"
gcloud redis instances delete bookshelf-cache-legacy --region="$REGION"

# IAM binding and service account created for the cache client
gcloud projects remove-iam-policy-binding "$PROJECT_ID" \
    --member="serviceAccount:catalog-api@$PROJECT_ID.iam.gserviceaccount.com" \
    --role="roles/memorystore.dbConnectionUser"
gcloud iam service-accounts delete "catalog-api@$PROJECT_ID.iam.gserviceaccount.com"

# Partner connectivity and secrets
gcloud compute forwarding-rules delete partner-psc-endpoint --region="$REGION"
gcloud compute addresses delete partner-psc-ip --region="$REGION"
gcloud secrets delete partner-api-key

# Self-hosted engines on GKE: release first, then the claims that hold the disks
helm uninstall qdrant --namespace data
kubectl delete pvc --all --namespace data
kubectl delete storageclass bookshelf-data

# Managed collection (only to turn it off on a cluster that does not need it)
kubectl delete podmonitoring catalog-api --namespace bookshelf
----

Reference: https://docs.cloud.google.com/sdk/gcloud/reference/memorystore/instances/delete[gcloud memorystore instances delete].
Delete the service connection policy only when no other Memorystore instance in that network and region uses it. Skip the
`remove-iam-policy-binding` and service-account steps if `catalog-api` still uses that identity for other services. With
`reclaimPolicy: Retain`, deleting a claim leaves the underlying disk, so delete retained disks with
`gcloud compute disks delete` (list them with `gcloud compute disks list`). Cancel Marketplace subscriptions (Elastic Cloud,
Redis Cloud, Couchbase Capella, Neo4j AuraDB, Qdrant Cloud) in the vendor's own console first and then in the Google Cloud
console under *Marketplace* > *Your orders*; deleting Google Cloud resources does not stop them. In a throwaway project,
shutting the project down removes the Google Cloud resources (see xref:cloud/google-cloud/resource-hierarchy-and-projects.adoc[]).
