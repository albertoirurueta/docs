= Reproducible and Deterministic Builds
:description: How to make .NET builds and packages bit-for-bit reproducible -- the compiler's Deterministic mode, ContinuousIntegrationBuild and path mapping on CI (TF_BUILD, GITHUB_ACTIONS), Source Link in the SDK since .NET 8, SourceRevisionId and IncludeSourceRevisionInInformationalVersion, locked restores and pinned SDKs, deterministic NuGet packs (Deterministic, DeterministicTimestamp, SOURCE_DATE_EPOCH; opt-in from SDK 10.0.400, default in the .NET 11 preview), reproducible container digests in the .NET 11 preview, and comparing two packages built on different machines.
:keywords: reproducible build, deterministic build, Deterministic, ContinuousIntegrationBuild, PathMap, TF_BUILD, GITHUB_ACTIONS, Source Link, SourceRevisionId, InformationalVersion, IncludeSourceRevisionInInformationalVersion, deterministic pack, DeterministicTimestamp, SOURCE_DATE_EPOCH, packages.lock.json, global.json, nupkg comparison, reproducible container image, dotnet/reproducible-builds

include::partial$csharp-build-tools-disclaimer.adoc[]

A build is **deterministic** when the same inputs produce byte-identical outputs, and **reproducible** when anyone can
recreate those inputs -- the same source revision, SDK, packages and settings -- and verify the result. Reproducibility
is what lets a consumer check that a package on nuget.org really came from the tagged source, lets a cache reuse outputs
safely, and makes "works on my machine" differences visible as a diff. .NET gets most of the way by default: for modern
.NET projects the C# compiler is deterministic by default. The rest is configuration, and this page shows each piece working on
*Ledgerline* with **.NET SDK 10.0.402** (NuGet 7.9.0): two clones of the same commit, in different folders, built and
packed until their hashes match.

[cols="2,3,2",options="header"]
|===
| Input that varies | Setting that removes the variation | Default

| Compiler output (timestamps, GUIDs, order)
| `Deterministic`
| on

| Absolute source paths in PDBs and assemblies
| `ContinuousIntegrationBuild` (maps paths to `+/_/+`)
| off -- set it on CI

| Source revision and repository URL
| Source Link (`SourceRevisionId`, `RepositoryUrl`)
| on since .NET 8

| Package versions
| `packages.lock.json` + `--locked-mode`
| off
(xref:programming-languages/csharp/build-tools/nuget/lock-files-and-locked-mode.adoc[Lock Files])

| SDK version
| `global.json`
| no pin
(xref:programming-languages/csharp/build-tools/dotnet-cli/installing-and-selecting-sdks.adoc[Installing and Selecting SDKs])

| Timestamps inside `.nupkg`
| `Deterministic` + `DeterministicTimestamp` on pack
| off (on by default in .NET 11, a preview)
|===

== The compiler: Deterministic

With `Deterministic` set to `true` (the default for modern .NET projects), `csc` produces the same assembly for the
same inputs: the timestamp and MVID fields are derived from a hash of the compilation inputs instead of the clock and a
random GUID. The documented inputs include the command line, the `.rsp` file, the exact compiler version and its
referenced assemblies. "Same inputs" includes the full paths
of the source files, which end up in the PDB and in the assembly's debug directory. Building the library in two folders
shows the problem:

[source,bash]
----
git clone ~/ledgerline a
git clone ~/ledgerline agent-2/work/ledgerline
(cd a && dotnet build src/Ledgerline -c Release -f net10.0)
(cd agent-2/work/ledgerline && dotnet build src/Ledgerline -c Release -f net10.0)
sha256sum a/src/Ledgerline/bin/Release/net10.0/Ledgerline.dll agent-2/work/ledgerline/src/Ledgerline/bin/Release/net10.0/Ledgerline.dll
strings -n 8 a/src/Ledgerline/bin/Release/net10.0/Ledgerline.dll | grep '\.pdb'
----

[source,text]
----
9a3432f31ea37b9dddfa1fe48964c0c39f78833310af0b6947dac80eb1a19d3c  a/src/Ledgerline/bin/Release/net10.0/Ledgerline.dll
ee941427736451458fcbd3d4ecdefc1f4eca03c5d93614ad49989a370d82779f  agent-2/work/ledgerline/src/Ledgerline/bin/Release/net10.0/Ledgerline.dll
~/repro/a/src/Ledgerline/obj/Release/net10.0/Ledgerline.pdb
----

The assembly records where its PDB was written, so two checkouts in different folders differ.

Source: https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/compiler-options/code-generation#deterministic[C# compiler options: Deterministic].

== ContinuousIntegrationBuild

`ContinuousIntegrationBuild=true` tells the SDK the build is an official one: source paths are normalised (the source
root is mapped to `+/_/+`), and Source Link requires the source control information to be present. It should be on in CI
and **off locally**, because the debugger cannot find local sources through `+/_/+` paths. The documented pattern, which
*Ledgerline*'s `Directory.Build.props` uses, conditions it on the variables the CI systems set:

[source,xml]
----
<PropertyGroup Condition="'$(GITHUB_ACTIONS)' == 'true' or '$(TF_BUILD)' == 'true'">
  <ContinuousIntegrationBuild>true</ContinuousIntegrationBuild>
</PropertyGroup>
----

`GITHUB_ACTIONS` (GitHub Actions) and `TF_BUILD` (Azure Pipelines) are environment variables, which MSBuild turns into
properties. Simulating CI with the variable gives identical assemblies in both folders, and the PDB path is now mapped:

[source,bash]
----
export GITHUB_ACTIONS=true
(cd a && dotnet build src/Ledgerline -c Release -f net10.0 --no-incremental)
(cd agent-2/work/ledgerline && dotnet build src/Ledgerline -c Release -f net10.0 --no-incremental)
sha256sum a/src/Ledgerline/bin/Release/net10.0/Ledgerline.dll agent-2/work/ledgerline/src/Ledgerline/bin/Release/net10.0/Ledgerline.dll
strings -n 8 a/src/Ledgerline/bin/Release/net10.0/Ledgerline.dll | grep '\.pdb'
----

[source,text]
----
a748f7ce767c2a0cb0a6c8efa71e498d15ca4e0597a57645c7577c3018f6557b  a/src/Ledgerline/bin/Release/net10.0/Ledgerline.dll
a748f7ce767c2a0cb0a6c8efa71e498d15ca4e0597a57645c7577c3018f6557b  agent-2/work/ledgerline/src/Ledgerline/bin/Release/net10.0/Ledgerline.dll
/_/src/Ledgerline/obj/Release/net10.0/Ledgerline.pdb
----

Other CI systems need their own variable in the condition (for example `CI` on many hosted runners) or
`-p:ContinuousIntegrationBuild=true` on the command line.

Source: https://learn.microsoft.com/en-us/dotnet/core/project-sdk/msbuild-props#continuousintegrationbuild[MSBuild props: ContinuousIntegrationBuild].

== Source Link and the source revision

Since **.NET 8, Source Link is part of the SDK**: no `+Microsoft.SourceLink.*+` package is needed for GitHub, GitLab,
Azure Repos or Bitbucket repositories. During the build it reads the Git repository (without needing `git` on the
`PATH`), sets `SourceRevisionId` to the commit and writes a Source Link JSON map into the PDB, so debuggers can download
the exact source of each file. As a side effect -- a documented breaking change of .NET 8 -- the commit is appended to
`InformationalVersion` as SemVer build metadata:

[source,bash]
----
cd src/Ledgerline
dotnet msbuild -p:TargetFramework=net10.0 -t:GetAssemblyAttributes -getProperty:InformationalVersion
dotnet msbuild -p:TargetFramework=net10.0 -p:IncludeSourceRevisionInInformationalVersion=false -t:GetAssemblyAttributes -getProperty:InformationalVersion
git log --oneline -1
----

[source,text]
----
1.0.0+bfbb6aa4c9ab954bc44426dee0d15d4af458eab2
1.0.0
bfbb6aa local tool manifest
----

Keep the revision in official builds -- it identifies the source of a binary -- and turn it off only where the
`pass:c[+<sha>]` suffix breaks something that parses the version. A build from a source archive without `.git` has no
revision unless `SourceRevisionId` is passed explicitly. Packaging symbols and Source Link for nuget.org is covered on
xref:programming-languages/csharp/build-tools/publishing/symbols-source-link-and-deterministic-packages.adoc[Symbols, Source Link and Deterministic Packages].

Some library-guidance pages still tell you to add the `Microsoft.SourceLink.GitHub` package; with SDK 8.0.100 and later
that is unnecessary.

Source: https://learn.microsoft.com/en-us/dotnet/core/compatibility/sdk/8.0/source-link[.NET 8 breaking change: Source Link included in the .NET SDK],
https://learn.microsoft.com/en-us/dotnet/core/project-sdk/msbuild-props#sourcerevisionid[MSBuild props: SourceRevisionId],
https://learn.microsoft.com/en-us/dotnet/core/project-sdk/msbuild-props#includesourcerevisionininformationalversion[IncludeSourceRevisionInInformationalVersion].

== Deterministic packs

A `.nupkg` is a ZIP file, and ZIP entries carry modification times. Even with identical assemblies, two packs differ.
Packing the same commit in the two clones (with `GITHUB_ACTIONS=true`, so the DLLs are identical) and comparing the
packages entry by entry with a small Python script (`nupkgdiff.py`: it hashes each entry and compares its ZIP timestamp):

[source,bash]
----
(cd a && dotnet pack src/Ledgerline -c Release -o ../q1)
(cd agent-2/work/ledgerline && dotnet pack src/Ledgerline -c Release -o ../../../q2)
python3 nupkgdiff.py q1/Ledgerline.1.0.0.nupkg q2/Ledgerline.1.0.0.nupkg
----

[source,text]
----
DIFF time          Ledgerline.nuspec
SAME               README.md
DIFF time          [Content_Types].xml
DIFF time          _rels/.rels
SAME               icon.png
DIFF time          lib/net10.0/Ledgerline.dll
DIFF time          lib/net10.0/Ledgerline.xml
DIFF time          lib/net8.0/Ledgerline.dll
DIFF time          lib/net8.0/Ledgerline.xml
DIFF time          lib/netstandard2.0/Ledgerline.dll
DIFF time          lib/netstandard2.0/Ledgerline.xml
DIFF time          package/services/metadata/core-properties/nuget.psmdcp
----

Every *content* is the same; only the times differ. The pack target has two inputs for this:

[cols="1,3",options="header"]
|===
| Property | Meaning

| `Deterministic`
| Deterministic mode for the package: one timestamp for every entry. The documentation gives the default as `true`
for .NET 11 and later -- that is, it is opt-in on .NET 10.

| `DeterministicTimestamp`
| The timestamp to use: an RFC 3339 date/time, a Unix time in seconds, `true` (current time) or `false`. The pack
targets in SDK 10.0.402 default it to `false`.

| `SOURCE_DATE_EPOCH` (environment variable)
| Documented as used automatically in place of `DeterministicTimestamp` when that is not set (NuGet 7.9.0+).
|===

With both properties set, the two clones produce the same package:

[source,bash]
----
(cd a && dotnet pack src/Ledgerline -c Release -o ../p1 -p:Deterministic=true -p:DeterministicTimestamp=2026-10-23T00:00:00Z)
(cd agent-2/work/ledgerline && dotnet pack src/Ledgerline -c Release -o ../../../p2 -p:Deterministic=true -p:DeterministicTimestamp=2026-10-23T00:00:00Z)
sha256sum p1/*.nupkg p2/*.nupkg
unzip -l p1/Ledgerline.1.0.0.nupkg
----

[source,text]
----
684b9056df05624150774b7410eb4a8422c809fd837e062485fbde4d73630d89  p1/Ledgerline.1.0.0.nupkg
684b9056df05624150774b7410eb4a8422c809fd837e062485fbde4d73630d89  p2/Ledgerline.1.0.0.nupkg
Archive:  p1/Ledgerline.1.0.0.nupkg
  Length      Date    Time    Name
---------  ---------- -----   ----
      473  2026-10-23 00:00   _rels/.rels
     1260  2026-10-23 00:00   Ledgerline.nuspec
      297  2026-10-23 00:00   README.md
      680  2026-10-23 00:00   icon.png
    13312  2026-10-23 00:00   lib/net10.0/Ledgerline.dll
      …
----

A practical choice for the timestamp is the commit time, so it changes only when the source does. In SDK 10.0.402 the
`SOURCE_DATE_EPOCH` variable alone did **not** have that effect: with `SOURCE_DATE_EPOCH` exported and only
`-p:Deterministic=true`, the entries still carried the current time and the two packages differed, because the pack
targets set `DeterministicTimestamp` to `false` before NuGet looks at the variable. Passing the value explicitly works:

[source,bash]
----
export SOURCE_DATE_EPOCH=$(git log -1 --format=%ct)
(cd a && dotnet pack src/Ledgerline -c Release -o ../p5 -p:Deterministic=true -p:DeterministicTimestamp=$SOURCE_DATE_EPOCH)
(cd agent-2/work/ledgerline && dotnet pack src/Ledgerline -c Release -o ../../../p6 -p:Deterministic=true -p:DeterministicTimestamp=$SOURCE_DATE_EPOCH)
sha256sum p5/*.nupkg p6/*.nupkg
unzip -l p5/Ledgerline.1.0.0.nupkg
----

[source,text]
----
d240eb5f782e3a617a3c0817c2c31d014efda80e705e748fdef9755a9dc10b56  p5/Ledgerline.1.0.0.nupkg
d240eb5f782e3a617a3c0817c2c31d014efda80e705e748fdef9755a9dc10b56  p6/Ledgerline.1.0.0.nupkg
      473  2026-10-23 17:53   _rels/.rels
     1260  2026-10-23 17:53   Ledgerline.nuspec
----

(17:53:05 UTC is the commit time; the `unzip` listing is abridged.) The documentation is also inconsistent on
*when* deterministic pack arrived: the `dotnet pack` examples say ".NET 10.0.400 and later", the pack-target table gives
the default as ".NET 11+". Both are true -- available from 10.0.400, on by default in 11 -- and .NET 11 is still a
preview.

Source: https://learn.microsoft.com/en-us/nuget/reference/msbuild-targets#pack-target-inputs[NuGet: Pack target inputs (Deterministic, DeterministicTimestamp, SOURCE_DATE_EPOCH)],
https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-pack#examples[dotnet pack examples],
https://reproducible-builds.org/specs/source-date-epoch/[SOURCE_DATE_EPOCH specification].

== Locked restores and pinned SDKs

Determinism of the compiler and the packer is worthless if the inputs move. Two more files close the gap, each with its
own page:

* `packages.lock.json` with `RestorePackagesWithLockFile=true`, and `dotnet restore --locked-mode` on CI, so a floating
  or newly published transitive version cannot slip in
  (xref:programming-languages/csharp/build-tools/nuget/lock-files-and-locked-mode.adoc[Lock Files and Locked Mode]);
* `global.json` with a pinned SDK, because the SDK version decides the compiler, the analyzers, the default language
  version and the build logic.

== Reproducible container images (.NET 11 preview)

The SDK's built-in container publishing (`dotnet publish -t:PublishContainer`) produced different image digests for the
same inputs, because of timestamps, archive headers and file enumeration order. The **.NET 11 preview** SDK fixes this:
with `SOURCE_DATE_EPOCH` set to a stable value, independent publishes of the same inputs produce the same digest. It is
not available on SDK 10.0.402 and is not run here; see
xref:programming-languages/csharp/build-tools/dotnet-cli/container-images.adoc[Container Images].

Source: https://learn.microsoft.com/en-us/dotnet/core/whats-new/dotnet-11/sdk#reproducible-container-publishing[What's new in the .NET 11 SDK: Reproducible container publishing].

== Verifying a package

To check that a published package matches its source: check out the commit named in its `InformationalVersion` or
nuspec `repository` element, use the SDK version from the repository's `global.json`, build with the same switches
(`ContinuousIntegrationBuild`, `Deterministic`, the same `DeterministicTimestamp`), and compare -- whole-file hashes
first, then entry by entry as above. A package *signed* by nuget.org (repository signature) gains a signature file,
so compare the entries other than `.signature.p7s`. The dotnet organisation's
https://github.com/dotnet/reproducible-builds[dotnet/reproducible-builds] repository (a dotnet-org GitHub project)
collects MSBuild settings for reproducible builds.

== Common mistakes

* *`ContinuousIntegrationBuild` on for local builds* -- the debugger cannot map `+/_/+` paths back to local files.
* *A CI system whose variable is not in the condition* -- the CI build silently embeds absolute paths.
* *Relying on `SOURCE_DATE_EPOCH` alone with SDK 10.0.402* -- pass `DeterministicTimestamp` explicitly.
* *Comparing packages after nuget.org signed one* -- the repository signature changes the file.
* *Floating versions or no lock file* -- reproducible compiler, non-reproducible inputs.
* *Adding the `Microsoft.SourceLink.GitHub` package on .NET 8+* -- redundant; the SDK includes it.

== Release notes

* **.NET 8**: Source Link in the SDK; `InformationalVersion` gains `pass:c[+<commit>]`.
* **SDK 10.0.400 / NuGet 7.9**: deterministic pack (`Deterministic`, `DeterministicTimestamp`), opt-in.
* **.NET 11 (preview)**: deterministic pack by default; reproducible container digests with `SOURCE_DATE_EPOCH`.
