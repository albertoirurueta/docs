Every `PackageReference` `Version` attribute is a **range**, even when it looks like a single version, and NuGet's
version strings follow Semantic Versioning with a few differences. This page tries each notation against a feed that
holds `Ledgerline.Money` 1.0.0, 1.5.0, 2.0.0 and 2.1.0-beta.1, using **NuGet 7.9.0** in .NET SDK 10.0.402. Choosing
versions for packages you *publish* is on
xref:programming-languages/csharp/build-tools/publishing/versioning-and-prerelease-packages.adoc[Versioning and Prerelease Packages].

== Version basics

A NuGet version is `Major.Minor.Patch[.Revision][-Prerelease][+Metadata]`:

* **Prerelease** labels (`-beta.1`, `-rc.2`) sort *before* the release with the same numbers: `2.1.0-beta.1` <
  `2.1.0`. Labels are compared part by part, numeric parts numerically (`beta.2` < `beta.10`) and text parts
  alphabetically and **case-insensitively**.
* **Metadata** after `+` (`+e33226ff`) is ignored when comparing and is not part of the identity on nuget.org.
* A package using SemVer 2.0.0 features -- dotted prerelease labels or metadata -- is only visible to NuGet 4.3+
  clients.

Where NuGet's `NuGetVersion` differs from SemVer 2.0.0: it allows a fourth part (`1.0.0.1`), it requires only the major
part (`1`, `1.0`, `1.0.0` and `1.0.0.0` are equal), and it compares prerelease labels without case.

== Normalization

NuGet normalizes versions when it stores and compares them: missing parts become `0`, leading zeros are removed, a zero
fourth part is dropped, and metadata is removed. `1.5`, `1.5.0`, `01.5.00` and `1.5.0.0` are the same version -- the
reference `Version="01.5.00"` restored `Ledgerline.Money/1.5.0`. Feeds and the global-packages folder use the normalized
string in paths (`ledgerline.money/1.5.0/`).

Source: https://learn.microsoft.com/en-us/nuget/concepts/package-versioning#normalized-version-numbers[Normalized version numbers].

== Range notation

[cols="2,3,3",options="header"]
|===
| Notation | Meaning | Restored here

| `1.5` | `x >= 1.5` (minimum, inclusive) | `1.5.0`
| `+[1.5]+` | `x == 1.5` (exact) | `1.5.0`
| `+(1.0,)+` | `x > 1.0` (exclusive minimum) | `1.5.0`, with NU1604
| `+[1.0,1.5]+` | `+1.0 <= x <= 1.5+` | `1.0.0`
| `+[1.0,2.0)+` | `+1.0 <= x < 2.0+` | `1.0.0`
| `+(,2.0]+`, `+(,2.0)+` | at most 2.0 / below 2.0 (no lower bound) | `1.0.0` (the lowest available), with NU1604
| `+(1.0)+` | invalid | restore failed
|===

Two rules explain the results: NuGet picks the **lowest** version that satisfies the range
(xref:programming-languages/csharp/build-tools/nuget/dependency-resolution.adoc[Dependency Resolution]), and a plain
version is a **minimum**, not "this version". `+[1.0,1.5]+` therefore restored 1.0.0, not 1.5.0.

The exclusive lower bound produced a warning:

[source,text]
----
~/ledgerline/samples/Deps/Deps.csproj : warning NU1604: Project dependency Ledgerline.Money (> 1.0.0) does not contain an inclusive lower bound. Include a lower bound in the dependency version to ensure consistent restore results.
----

The invalid `+(1.0)+` gave no NuGet diagnostic at all -- only MSBuild's generic message that the restore task failed
silently:

[source,text]
----
~/.dotnet/sdk/10.0.402/NuGet.targets(198,5): error MSB4181: The "RestoreTask" task returned false but did not log an error. [~/ledgerline/samples/Deps/Deps.csproj]
----

A minimum that no feed has is NU1102, which lists what each source offers:

[source,text]
----
~/ledgerline/samples/Deps/Deps.csproj : error NU1102: Unable to find package Ledgerline.Money with version (>= 3.0.0)
~/ledgerline/samples/Deps/Deps.csproj : error NU1102:   - Found 4 version(s) in ledgerline-local [ Nearest version: 2.1.0-beta.1 ]
~/ledgerline/samples/Deps/Deps.csproj : error NU1102:   - Versions from ledgerline-bagetter were not considered
~/ledgerline/samples/Deps/Deps.csproj : error NU1102:   - Versions from nuget.org were not considered
----

("not considered" because the repository's package source mapping sends `+Ledgerline.*+` only to `ledgerline-local`;
xref:programming-languages/csharp/build-tools/nuget/package-sources-and-source-mapping.adoc[Package Sources and Source Mapping].)
A minimum whose exact version is missing but a higher one exists resolves with NU1603:

[source,text]
----
~/ledgerline/samples/Deps/Deps.csproj : warning NU1603: Deps depends on Ledgerline.Money (>= 2.1.0-beta.0) but Ledgerline.Money 2.1.0-beta.0 was not found. Ledgerline.Money 2.1.0-beta.1 was resolved instead.
----

https://learn.microsoft.com/en-us/nuget/concepts/package-versioning#references-in-project-files-packagereference[References in project files],

== Floating versions

A `+*+` makes the range **float** to the *highest* matching version (the opposite of the normal lowest-applicable rule):

[cols="1,3,2",options="header"]
|===
| Version | Floats to | Restored here

| `+1.*+` | highest 1.x release | `1.5.0`
| `+*+` | highest release | `2.0.0`
| `+*-*+` | highest version, including prereleases | `2.1.0-beta.1`
| `+2.1.0-*+` | highest 2.1.0 prerelease (or 2.1.0) | `2.1.0-beta.1`
|===

Floating versions make a restore depend on *when* it runs: the same commit restores differently after a new package
is published. They suit tools and experiments, not shipped builds; with lock files they are recorded at the resolved
version (xref:programming-languages/csharp/build-tools/nuget/lock-files-and-locked-mode.adoc[Lock Files and Locked Mode]),
and with Central Package Management they need `CentralPackageFloatingVersionsEnabled`.

Source: https://learn.microsoft.com/en-us/nuget/consume-packages/package-references-in-project-files#floating-versions[PackageReference: Floating versions].

== Best practice

* **Applications and libraries alike: a plain minimum** (`Version="1.5.0"`) and an update process. Exact versions and
  upper bounds in a *library* make it impossible for consumers to combine it with other packages that need a newer
  dependency (NU1107/NU1608 on
  xref:programming-languages/csharp/build-tools/nuget/dependency-resolution.adoc[Dependency Resolution]).
* **Upper bounds only for a known incompatibility**, documented next to the reference.
* **Lock files, not exact versions, for reproducible application restores.**

Source: https://learn.microsoft.com/en-us/nuget/concepts/package-versioning#best-practice[Package versioning: Best practice].

== Common mistakes

* *Reading `Version="1.5.0"` as "exactly 1.5.0"* -- it is a minimum.
* *`+(1.0)+` and other invalid ranges* -- restore fails with no NuGet message.
* *Upper bounds in library dependencies* -- consumers cannot resolve.
* *Floating versions in release builds* -- the restore changes over time.
