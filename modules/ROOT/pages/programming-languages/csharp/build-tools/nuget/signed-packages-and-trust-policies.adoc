= Signed Packages and Trust Policies
:description: Package signatures from the consumer's side with NuGet 7.9.0 -- author and repository signatures shown by dotnet nuget verify on Humanizer.Core 2.14.1, NU3004 for unsigned packages, signatureValidationMode accept and require, trusted signers (author, repository, owners) managed with dotnet nuget trust list, author, repository, source, certificate, sync and remove, NU3034 for a signed but untrusted package (also in accept mode once trusted signers are configured), verification per OS with DOTNET_NUGET_SIGNATURE_VERIFICATION (on by default on Linux since the .NET 8 SDK, off on macOS), and the SHA-1 fingerprint deprecation.
:keywords: NuGet package signing, signed package, author signature, repository signature, dotnet nuget verify, NU3004, NU3008, NU3034, NU3043, signatureValidationMode, accept, require, trustedSigners, dotnet nuget trust, trust author, trust repository, trust source, trust certificate, trust sync, trust remove, owners, DOTNET_NUGET_SIGNATURE_VERIFICATION, certificate fingerprint, SHA-256, SHA-1

include::partial$csharp-build-tools-disclaimer.adoc[]

A NuGet package can carry two signatures. An **author signature**, added by the publisher, proves who built it; a
**repository signature**, added by nuget.org to every package it accepts, proves where it came from. A consumer can
simply let NuGet check that signed packages are intact, or go further and **require** that every package is signed by a
signer it trusts. This page does both with **NuGet 7.9.0** (.NET SDK 10.0.402) on Linux. Signing your own packages is on
xref:programming-languages/csharp/build-tools/publishing/signing-packages.adoc[Signing Packages].

== Inspecting signatures

----
dotnet nuget verify --all ~/.nuget/packages/humanizer.core/2.14.1/humanizer.core.2.14.1.nupkg
----

Both certificates have expired, and the package still verifies (exit code 0): the signatures carry **timestamps**, and
a signature made while its certificate was valid stays valid. An unsigned package -- *Ledgerline*'s own, from the local
feed -- fails verification with exit code 1:

[source,text]
----
error: NU3004: The package is not signed.

Package signature validation failed.
----

== What restore checks

With the default `signatureValidationMode` of `accept`, restore checks that **signed** packages have not been modified
since signing (NU3008 if they have) and accepts unsigned packages. On Linux this verification is on by default since
the .NET 8 SDK; `DOTNET_NUGET_SIGNATURE_VERIFICATION=false` turns it off -- a detailed restore log then contained no
signature lines at all. On macOS it is off by default and the documentation recommends leaving it off; on Windows it is
always on.

Source: https://learn.microsoft.com/en-us/dotnet/core/tools/nuget-signed-package-verification#windows[Signed package verification: Windows],
https://learn.microsoft.com/en-us/dotnet/core/tools/nuget-signed-package-verification#linux[Linux],
https://learn.microsoft.com/en-us/dotnet/core/tools/nuget-signed-package-verification#macos[macOS].

== Trusted signers

`trustedSigners` in `nuget.config` lists whose signatures are trusted. `dotnet nuget trust` maintains it:

[cols="1,3",options="header"]
|===
| Command | Adds or does

| `trust list` | Show the trusted signers.
| `trust author <name> <package>` | Trust the author certificate that signed a local package.
| `trust repository <name> <package>` | Trust the repository certificate on a local package (`--owners` restricts to nuget.org owners).
| `trust source <name>` | Trust a source's repository certificates, read from its service index.
| `trust certificate <name> <fingerprint>` | Trust a certificate by fingerprint.
| `trust sync <name>` | Refresh a repository's certificates from its service index.
| `trust remove <name>` | Remove a signer.
|===

[source,bash]
----
dotnet nuget trust author Humanizer ~/.nuget/packages/humanizer.core/2.14.1/humanizer.core.2.14.1.nupkg --configfile nuget.config
dotnet nuget trust source nuget.org --configfile nuget.config
dotnet nuget trust list --configfile nuget.config
----

----

nuget.org accounts.

== Requiring trusted signatures

[source,xml]
----
<config>
  <add key="signatureValidationMode" value="require" />
</config>
----

With both signers above trusted, a project referencing `Humanizer.Core`, `Newtonsoft.Json` and the unsigned
`Ledgerline` restored the two nuget.org packages (both repository-signed by nuget.org) and rejected the third:

[source,text]
----
~/sign/S.csproj : error NU3004: Package 'Ledgerline 1.0.0' from source '~/lb/artifacts/feed': signatureValidationMode is set to require, so packages are allowed only if signed by trusted signers; however, this package is unsigned.
----

After `dotnet nuget trust remove nuget.org`, only the Humanizer author was trusted, and `Newtonsoft.Json` -- author-
signed by Json.NET and repository-signed by nuget.org, neither trusted -- was rejected:

[source,text]
----
~/sign/S.csproj : error NU3034: Package 'Newtonsoft.Json 13.0.3' from source 'https://api.nuget.org/v3/index.json': This package is signed but not by a trusted signer.
----

The same NU3034 appeared after switching back to `accept`: once a `trustedSigners` list exists, **signed** packages
must match it even in accept mode; `accept` only lets **unsigned** packages through. `require` is practical for
organisations that sign their internal packages and trust nuget.org's repository certificate (with `--owners`), and it
blocks a tampered or substituted package even when no lock file would catch it.

Source: https://learn.microsoft.com/en-us/nuget/consume-packages/installing-signed-packages#configure-package-signature-requirements[Configure package signature requirements],
https://learn.microsoft.com/en-us/nuget/reference/signed-package-verification-options[Signed package verification options].

== Fingerprints and algorithms

`trustedSigners` entries store certificate **fingerprints** with their algorithm; `dotnet nuget trust` writes SHA-256
ones. On the signing side, NuGet 6.12 deprecated SHA-1 fingerprints for `dotnet nuget sign`/`nuget sign`
(`--certificate-fingerprint`): NU3043 is a warning in .NET 9 and an error in the .NET 10 SDK
(xref:programming-languages/csharp/build-tools/publishing/signing-packages.adoc[Signing Packages]). When nuget.org
rotates its repository certificate, `dotnet nuget trust sync nuget.org` adds the new fingerprint (the three above
include past and current certificates).

Source: https://learn.microsoft.com/en-us/nuget/reference/errors-and-warnings/nu3043[NU3043],
https://learn.microsoft.com/en-us/nuget/release-notes/nuget-6.12[NuGet 6.12 release notes].

== Common mistakes

* *Expecting `accept` to ignore trusted signers* -- signed packages must still match the list.
* *Trusting the nuget.org repository without `--owners` under `require`* -- that trusts every package on nuget.org.
* *Forgetting `trust sync` after a repository certificate rotation* -- `require` starts rejecting new packages.
* *Enabling verification on macOS* -- documented as unsupported.
