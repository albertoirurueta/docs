= Build Automation Tools (MSBuild, dotnet CLI & NuGet)
:description: Landing page for the .NET build automation section -- what build automation means in .NET (one engine, MSBuild; one driver, the dotnet CLI in the .NET SDK; one package manager, NuGet), how the three divide the work of a build, the release baseline (MSBuild 18.9, .NET SDK 10.0.402, NuGet 7.9.0), the Ledgerline running example and a reading path through the shared, MSBuild, dotnet CLI, NuGet and publishing pages.
:keywords: .NET build automation, MSBuild, dotnet CLI, .NET SDK, NuGet, build engine, driver, package manager, dotnet build, dotnet pack, dotnet publish, restore, release baseline, Ledgerline, reading path, C# build tools

include::partial$csharp-build-tools-disclaimer.adoc[]

"Build automation" in .NET means that a single command -- `dotnet build`, `dotnet test`, `dotnet pack` or
`dotnet publish` -- turns a source tree into tested binaries, NuGet packages or a deployable application, the same way on
every developer machine and every CI agent. Unlike the JVM world, where Maven and Gradle compete, or Python, where
standards connect interchangeable tools, .NET ships one tool chain from one vendor, split into three parts that are
always used together:

* **MSBuild**, the *engine*. It reads the XML project files (`.csproj`, `.props`, `.targets`), evaluates their properties
  and items, and runs targets made of tasks. Every .NET build, whether started from a terminal, Visual Studio, Rider or
  VS Code, is an MSBuild build.
* **The .NET SDK and its `dotnet` CLI**, the *driver*. The SDK carries MSBuild, the Roslyn compilers, NuGet, the
  project SDKs (`Microsoft.NET.Sdk` and friends) and the templates; the `dotnet` command is a thin front end that picks
  an SDK, translates its options into MSBuild switches and invokes the right targets.
* **NuGet**, the *package manager*. It is built into both MSBuild (the `Restore` and `Pack` targets) and the CLI
  (`dotnet package`, `dotnet nuget`). It resolves `PackageReference` items against package sources, downloads `.nupkg`
  files into the global-packages folder and writes the assets file that the compiler reads.

The introduction to these tools is already on two pages of the C# Reference:
xref:programming-languages/csharp/build-and-tooling.adoc[Build and Tooling] (the `dotnet` CLI, a first look at packing,
tools, MSBuild, symbols and CI) and
xref:programming-languages/csharp/namespaces-assemblies-and-projects.adoc[Namespaces, Assemblies and Projects]
(SDK-style projects, multi-targeting, `global.json`, NuGet consuming and authoring, deployment models). This section
goes much deeper and does not repeat them. It is the .NET counterpart of the JVM build tools section (issue #300) and the
Python build tools section (issue #305); the sections share no pages.

The pages were written against **MSBuild 18.9**, the **.NET SDK 10.0.402** and **NuGet 7.9.0**. Every example was run
with SDK 10.0.402 installed by `dotnet-install.sh --version 10.0.402` into a scratch directory on Ubuntu 24.04 (x64),
on 2026-10-23; long absolute paths in the output are shortened to `+~/ledgerline+` and `<sdk>` (the SDK folder).

== One engine, one driver, one package manager

[mermaid]
....
flowchart LR
    CMD["dotnet build"] --> RES["SDK resolution: dotnet host + global.json"]
    RES --> REST["NuGet restore: PackageReference to project.assets.json"]
    REST --> EVAL["MSBuild evaluation: properties, items, imports"]
    EVAL --> EXEC["MSBuild execution: targets and tasks"]
    EXEC --> CSC["Roslyn compiler: CoreCompile"]
    CSC --> OUT["Outputs: bin/ and obj/"]
    OUT --> PACK["dotnet pack: .nupkg and .snupkg"]
    OUT --> PUB["dotnet publish: deployable app"]
    PACK --> FEED[("Package source: nuget.org, private feed, folder")]
    FEED --> REST
....

The diagram is the life of every build; the next page,
xref:programming-languages/csharp/build-tools/how-a-dotnet-build-works.adoc[How a .NET Build Works], follows it step
by step. The table below shows which part of the tool chain owns each step.

[cols="1,2,2,2",options="header"]
|===
| Step | MSBuild | .NET SDK / `dotnet` CLI | NuGet

| Choose the tools
| --
| The `dotnet` host reads `global.json` and selects an SDK (and with it an MSBuild and a NuGet)
| --

| Get dependencies
| Runs the `Restore` target
| `dotnet restore`, implicit restore in `build`/`test`/`pack`/`publish`
| Resolves versions, downloads packages, writes `project.assets.json`

| Describe the build
| Evaluates the project, `.props`, `.targets` and the project SDK
| Provides the project SDKs (`Microsoft.NET.Sdk`, `.Web`, …) and their defaults
| Generates `nuget.g.props`/`nuget.g.targets` that import package build logic

| Run the build
| Executes targets and tasks (`CoreCompile`, `Copy`, …), incrementally and in parallel
| `dotnet build`, `test`, `run`, `clean`, `format`, `watch`
| --

| Produce packages and apps
| Runs `Pack` and `Publish` targets
| `dotnet pack`, `dotnet publish`, container images
| Writes the `.nupkg`/`.snupkg`; `dotnet nuget push` uploads them
|===

The `dotnet` CLI is a driver in the strict sense: the documentation states that "running `dotnet build` is equivalent
to running `dotnet msbuild -restore`; however, the default verbosity of the output is different", and every building
command accepts MSBuild switches such as `-p:` and `-v:`.
NuGet appears twice: as MSBuild targets (`Restore`, `Pack`) inside every build, and as the `dotnet nuget` /
`dotnet package` commands for everything outside a build (sources, push, signing, search).

Source: https://learn.microsoft.com/en-us/dotnet/core/tools/#driver[.NET CLI: Driver],
https://learn.microsoft.com/en-us/dotnet/core/tools/#command-structure[.NET CLI: Command structure],
https://learn.microsoft.com/en-us/visualstudio/msbuild/msbuild#project-file[MSBuild: Project file],
https://learn.microsoft.com/en-us/nuget/what-is-nuget#nuget-tools[NuGet: NuGet tools].

=== Checking which tools you have

The three versions come from one SDK installation. `dotnet --version` prints the SDK that the current directory
selects (through `global.json`, if any); `dotnet msbuild -version` prints the MSBuild that SDK carries; and
`dotnet nuget --version` prints the NuGet client in it.

[source,bash]
----
dotnet --version
dotnet msbuild -version
dotnet nuget --version
dotnet --list-sdks
----

[source,text]
----
10.0.402
18.9.15.50611
7.9.0-rc.611+a8dd0577c5c13f43a2f57fe33b4ff11b90f6371e.a8dd0577c5c13f43a2f57fe33b4ff11b90f6371e
10.0.402 [<dotnet>/sdk]
----

The NuGet line deserves a remark: the NuGet assemblies inside SDK 10.0.402 carry the informational version
`7.9.0-rc.611+<commit>`, although the SDK's release notes and `nuget.exe` call the release **7.9.0**. The NuGet release
notes list SDK 10.0.400 as the SDK that ships NuGet 7.9; the suffix is a build label, not a sign of a preview client.

Source: https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet#options[.NET CLI: dotnet options],
https://learn.microsoft.com/en-us/visualstudio/msbuild/msbuild#use-msbuild-at-a-command-prompt[MSBuild: Use MSBuild at a command prompt],
https://learn.microsoft.com/en-us/nuget/release-notes/nuget-7.9[NuGet 7.9 release notes].

== The running example: Ledgerline

Almost every example in the section uses one original repository, *Ledgerline*, a small library for double-entry
bookkeeping ledgers. It reads a CSV journal (`date,entry,account,debit,credit,memo`), checks that every entry balances
and exports a trial balance per account as JSON. No package named `Ledgerline` exists on nuget.org, and the examples
never push one there: they publish to a folder feed (`./artifacts/feed`) and to a BaGetter server running in a container
on `http://localhost:5555`.

[source,text]
----
ledgerline/
├── Ledgerline.slnx              solution (XML format, the .NET 10 default)
├── global.json                  pins SDK 10.0.402, selects the MTP test runner
├── nuget.config                 nuget.org + the local feeds, with package source mapping
├── Directory.Build.props        shared properties (Nullable, TreatWarningsAsErrors, package metadata)
├── Directory.Build.targets      packs README.md and icon.png into every packable project
├── Directory.Packages.props     Central Package Management: every package version in one place
├── .editorconfig  README.md  LICENSE  icon.png  CHANGELOG.md
├── src/
│   ├── Ledgerline/              the library: net10.0;net8.0;netstandard2.0
│   ├── Ledgerline.Build/        an MSBuild task (ValidateLedger) + buildTransitive targets
│   ├── Ledgerline.Cli/          a .NET tool (command: ledgerline)
│   └── Ledgerline.Templates/    a template package (dotnet new ledgerline-app)
├── tests/Ledgerline.Tests/      xUnit v3 tests (VSTest and Microsoft.Testing.Platform)
└── samples/
    ├── Ledgerline.Report/       console app that consumes Ledgerline from the local feed
    └── quick-ledger.cs          a file-based app (#:package directive)
----

Building the consumer app shows all three tools at work in a few lines: NuGet restores `Ledgerline` and
`Ledgerline.Build` from the local feed, MSBuild runs the `LedgerlineValidateJournals` target that the
`Ledgerline.Build` package added to the build, and the compiler writes the app.

[source,bash]
----
cd ledgerline/samples/Ledgerline.Report
dotnet build -tl:off
dotnet run --no-build -- journal.ledger.csv
----

----

`-tl:off` turns off the Terminal Logger (the default console logger since .NET 9), whose live, redrawn output does not
survive copying into a page; the section uses it, or `-v:n`, wherever output is shown.

https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-build#options[.NET CLI: dotnet build options (--tl)].
