= Trusted Publishing

**Trusted Publishing** (announced on 2025-09-22) replaces the long-lived nuget.org API key in CI with a key that is
created for one workflow run and expires within an hour. Nothing secret is stored in the repository or its settings:
nuget.org trusts a specific repository and workflow, proven by a token that the CI system signs. Since nuget.org
limited stored API keys to 30 days in August 2026
(xref:programming-languages/csharp/build-tools/publishing/nuget-org-accounts-organizations-and-api-keys.adoc#_key_lifetimes_since_2026[Key lifetimes since 2026]),
it is the recommended way to publish. Nothing on this page was run: it needs a public GitHub repository and a nuget.org
account, and `Ledgerline` is never published. Everything is checked against the nuget.org documentation and the
`NuGet/login` action's `action.yml` and README (v1.2.0).

== How it works

image::csharp-build-tools-trusted-publishing.svg["Trusted Publishing sequence: the GitHub Actions job gets a signed OIDC token from GitHub, exchanges it at the nuget.org token service for a one-hour API key, then pushes with that key",width=820]

1. The package owner registers a **Trusted Publishing policy** on nuget.org: repository owner, repository, workflow
   file and, optionally, a GitHub **environment**.
2. The workflow job, with `permissions: id-token: write`, asks GitHub's OIDC provider for a **signed JSON Web Token**
   describing the run (repository, owner, workflow, environment, with the audience `https://www.nuget.org`).
3. The `NuGet/login` action sends the token and the nuget.org **user name** to `https://www.nuget.org/api/v2/token`.
4. nuget.org validates the token and matches it against the policies; if one matches, it returns a **temporary API
   key valid for one hour**. One token buys one key.
5. `dotnet nuget push` uses that key like any other.

Request the key just before the push; a key fetched at the start of a long job can expire before it is used.

Source: https://learn.microsoft.com/en-us/nuget/nuget-org/trusted-publishing#how-it-works[Trusted Publishing: How it works],
https://docs.github.com/en/actions/concepts/security/openid-connect[GitHub Docs: OpenID Connect],
https://devblogs.microsoft.com/dotnet/enhanced-security-is-here-with-the-new-trust-publishing-on-nuget-org/[New Trusted Publishing enhances security on NuGet.org].

== Setting it up for GitHub Actions

On nuget.org: *your user name > Trusted Publishing > add a policy*. For a repository `github.com/ledgerline/ledgerline`
with `.github/workflows/release.yml`:

[cols="1,2",options="header"]
|===
| Field | Value

| Repository Owner | `ledgerline`
| Repository | `ledgerline`
| Workflow File | `release.yml` -- the file name only, without `.github/workflows/`
| Environment (optional) | `nuget` -- only if the job declares `environment: nuget`
|===

Values are case-insensitive. In the workflow, the job that pushes needs `id-token: write`, and `NuGet/login@v1` needs
`user:` -- the nuget.org **profile name**, not an e-mail address (the docs suggest a secret such as
`+${{ secrets.NUGET_USER }}+`). Its output `NUGET_API_KEY` is the temporary key:

[source,yaml]
----
- name: NuGet login (OIDC to temporary API key)
  uses: NuGet/login@v1
  id: login
  with:
    user: ${{ secrets.NUGET_USER }}

- name: Push
  run: dotnet nuget push "artifacts/*.nupkg" --api-key "${{ steps.login.outputs.NUGET_API_KEY }}" --source https://api.nuget.org/v3/index.json --skip-duplicate
----

The action's other inputs, `token-service-url` (default `https://www.nuget.org/api/v2/token`) and `audience` (default
`https://www.nuget.org`), point it at another NuGet server that implements the same exchange. Version tags: `v1`
(moving), `v1.1.0` and `v1.2.0`; v1.2.0 runs on Node 24.

Source: https://learn.microsoft.com/en-us/nuget/nuget-org/trusted-publishing#github-actions-setup[Trusted Publishing: GitHub Actions setup],
https://github.com/NuGet/login[NuGet/login].

== GitLab

GitLab CI/CD is supported too. The job requests an ID token with the nuget.org audience, exchanges it with `curl`, and
pushes:

[source,yaml]
----
publish_nuget:
  stage: publish
  image: mcr.microsoft.com/dotnet/sdk:10.0
  id_tokens:
    NUGET_ID_TOKEN:
      aud: "https://www.nuget.org"
  script:
    - |
      API_KEY=$(curl -s -X POST "https://www.nuget.org/api/v2/token" \
        -H "Content-Type: application/json" \
        -H "Authorization: Bearer $NUGET_ID_TOKEN" \
        -d "{\"username\": \"$NUGET_USERNAME\", \"tokenType\": \"ApiKey\"}" | jq -r '.apiKey')
    - dotnet nuget push ./artifacts/*.nupkg -s https://www.nuget.org/api/v2/package -k "$API_KEY"
----

(adapted from the documentation, which uses the `sdk:8.0` image and also prints the HTTP status). The policy matches the
token's `namespace_path` and `project_path` claims (required), and `environment` and `ref` when set in the policy -- `ref`
must be a branch, so tag pipelines cannot match a `ref` policy.

Source: https://learn.microsoft.com/en-us/nuget/nuget-org/trusted-publishing#gitlab-support[GitLab support],
https://learn.microsoft.com/en-us/nuget/nuget-org/trusted-publishing#step-1--register-the-policy-on-nugetorg[Step 1: Register the policy],
https://learn.microsoft.com/en-us/nuget/nuget-org/trusted-publishing#step-2--configure-the-gitlab-cicd-pipeline[Step 2: Configure the pipeline],
https://learn.microsoft.com/en-us/nuget/nuget-org/trusted-publishing#required-token-claims[Required token claims].

== Scopes, ownership and activation

* **Scopes** -- like API keys, a policy can be limited to *publishing new packages* or *new versions of existing ones*,
  with a glob pattern of package IDs.
* **Ownership** -- a policy belongs to a user or an organization and covers all packages of that owner. An
  organization policy becomes **inactive** if its creator leaves the organization (and active again when re-added), or
  if the organization is locked or deleted; the UI shows a warning.
* **Pending activation** -- a new policy, typically for a **private** GitHub repository, can start "temporarily active"
  for **7 days**: nuget.org needs the repository and owner **IDs** from a first real token to lock the policy against a
  deleted-and-recreated repository with the same name. If nothing is published in 7 days it becomes inactive; the
  window can be restarted.

Source: https://learn.microsoft.com/en-us/nuget/nuget-org/trusted-publishing#select-scopes[Select scopes],
https://learn.microsoft.com/en-us/nuget/nuget-org/trusted-publishing#policy-ownership[Policy ownership],
https://learn.microsoft.com/en-us/nuget/nuget-org/trusted-publishing#policies-pending-full-activation[Policies pending full activation],
https://learn.microsoft.com/en-us/nuget/nuget-org/trusted-publishing#policy-ownership-warnings[Policy ownership warnings],

== The complete Ledgerline release workflow (not run here)

Build and push are separate jobs, so only the short push job can mint an OIDC token
(xref:programming-languages/csharp/build-tools/publishing/ci-release-workflows.adoc[CI Release Workflows]):

[source,yaml]
----
name: release
on:
  push:
    tags: [ 'v*' ]

permissions:
  contents: read

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
        with:
          fetch-depth: 0
      - uses: actions/setup-dotnet@v6
        with:
          global-json-file: global.json
      - run: dotnet restore --locked-mode
      - run: dotnet test --no-restore
      - run: dotnet pack --no-restore -o artifacts -p:ContinuousIntegrationBuild=true -p:Version=${GITHUB_REF_NAME#v}
      - uses: actions/upload-artifact@v7
        with:
          name: packages
          path: artifacts/*

  publish:
    needs: build
    runs-on: ubuntu-latest
    environment: nuget
    permissions:
      id-token: write
    steps:
      - uses: actions/download-artifact@v8
        with:
          name: packages
          path: artifacts
      - uses: NuGet/login@v1
        id: login
        with:
          user: ${{ secrets.NUGET_USER }}
      - run: dotnet nuget push "artifacts/*.nupkg" --api-key "${{ steps.login.outputs.NUGET_API_KEY }}" --source https://api.nuget.org/v3/index.json --skip-duplicate
----

The matching policy: owner and repository of the project, workflow file `release.yml`, environment `nuget`. The
`.snupkg` files beside the `.nupkg` files are pushed by the same command.

Source: https://learn.microsoft.com/en-us/nuget/nuget-org/trusted-publishing#github-actions-setup[Trusted Publishing: GitHub Actions setup],
https://docs.github.com/en/actions/tutorials/build-and-test-code/net#packaging-workflow-data-as-artifacts[GitHub Docs: Packaging workflow data as artifacts].

== Common failures

* *Missing `id-token: write`* -- the job can't request a token; set it on the push job (top-level `permissions` set to
  read-only does not grant it).
* *An e-mail address in `user:`* -- it must be the profile name.
* *The path in "Workflow File"* -- enter `release.yml`, not `.github/workflows/release.yml`.
* *An environment in the policy but not in the job* (or the reverse) -- the claims don't match.
* *The key requested too early* -- it lasts one hour.
* *A renamed workflow file* -- the policy names the file; renaming it breaks publishing until the
  policy is updated.

== Documentation gaps

* The Trusted Publishing page appears in neither the NuGet table of contents nor the nuget.org section's; only the
  nuget.org overview links it.
* It names the nuget.org UI differently in its two sections: *Trusted Publishing* under the user name for GitHub,
  *Account > Federated credentials* for GitLab.
* Azure Pipelines is not documented as an identity provider; pipelines there still need an API key.
* GitLab support has no announcement date that could be verified.
