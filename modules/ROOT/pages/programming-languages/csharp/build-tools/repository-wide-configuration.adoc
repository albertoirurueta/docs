= Repository-Wide Configuration
:description: The files at the root of a .NET repository and what reads each one -- global.json (SDK, test runner, MSBuild SDK versions), nuget.config (sources, mapping), Directory.Build.props and Directory.Build.targets (props versus targets, search scope, import order, multi-level merging with GetPathOfFileAbove), Directory.Build.rsp, Directory.Packages.props (Central Package Management), .editorconfig and .globalconfig with their precedence, and the dotnet-tools.json tool manifest -- with the complete Ledgerline root files and the dotnet new templates that create them.
:keywords: repository configuration, global.json, nuget.config, Directory.Build.props, Directory.Build.targets, Directory.Build.rsp, Directory.Packages.props, Central Package Management, .editorconfig, .globalconfig, global AnalyzerConfig, dotnet-tools.json, tool manifest, GetPathOfFileAbove, multi-level merging, import order, search scope, dotnet new buildprops, dotnet new buildtargets, dotnet new globaljson, dotnet new packagesprops, dotnet new editorconfig, dotnet new nugetconfig, EnforceCodeStyleInBuild

include::partial$csharp-build-tools-disclaimer.adoc[]

A .NET repository is configured mostly by *files at its root*, not by the project files. Each is found automatically by
walking up the directory tree from the project (or the current directory), so every project, every developer and every
CI job gets the same settings without anyone passing a switch. This page lists those files, the tool that reads each one
and when, and shows *Ledgerline*'s complete set as run with **.NET SDK 10.0.402**. The introduction is in
xref:programming-languages/csharp/namespaces-assemblies-and-projects.adoc#_sharing_configuration[Namespaces, Assemblies and Projects -- Sharing Configuration];
`.editorconfig` rules themselves are described in
xref:programming-languages/csharp/coding-conventions-and-documentation.adoc[Coding Conventions and Documentation].

== Where each file enters the build

[mermaid]
....
flowchart TB
    RSP["Directory.Build.rsp: command-line switches"] --> START["MSBuild startup"]
    GJ["global.json: SDK and msbuild-sdks"] --> START
    START --> SDKPROPS["Sdk.props, then Microsoft.Common.props"]
    SDKPROPS --> DBP["Directory.Build.props (nearest one above the project)"]
    DBP --> NGP["obj/*.nuget.g.props (package props)"]
    NGP --> DPP["Directory.Packages.props (via NuGet.props)"]
    DPP --> PROJ["The .csproj body"]
    PROJ --> SDKT["Sdk.targets, then Microsoft.Common.targets"]
    SDKT --> NGT["obj/*.nuget.g.targets (package targets)"]
    NGT --> DBT["Directory.Build.targets (nearest one above the project)"]
    DBT --> REST["rest of the SDK targets"]
    NC["nuget.config: sources and mapping"] -.-> NGP
    EC[".editorconfig / .globalconfig"] -.-> CSC["CoreCompile (analyzers)"]
    REST --> CSC
....

The order in the middle column is what `dotnet msbuild -pp` showed for `Ledgerline.Report` on
xref:programming-languages/csharp/build-tools/how-a-dotnet-build-works.adoc#_what_a_real_project_imports[How a .NET Build Works]:
`Directory.Build.props` is the third file read, before the project body; `Directory.Build.targets` comes after the
project body *and* after the package `.targets`, so it can override both.

Source: https://learn.microsoft.com/en-us/visualstudio/msbuild/customize-by-directory#import-order[MSBuild: Import order].

== The Ledgerline root files

[source,text]
----
ledgerline/
├── global.json
├── nuget.config

=== global.json

[source,json]
----
{
  "sdk": {
    "version": "10.0.402",
    "rollForward": "latestPatch",
    "allowPrerelease": false
  },
  "test": {
    "runner": "Microsoft.Testing.Platform"
  }
}
----

`sdk` pins the SDK feature band (any 10.0.4xx patch at or above 402); `test.runner` switches `dotnet test` to the
Microsoft.Testing.Platform mode (.NET 10). A third section, `msbuild-sdks`, would pin NuGet-delivered project SDKs.

Source: https://learn.microsoft.com/en-us/dotnet/core/tools/global-json[.NET: global.json overview].

=== nuget.config

[source,xml]
----
<?xml version="1.0" encoding="utf-8"?>
<configuration>
  <packageSources>
    <clear />
    <add key="nuget.org" value="https://api.nuget.org/v3/index.json" protocolVersion="3" />
    <add key="ledgerline-local" value="./artifacts/feed" />
    <add key="ledgerline-bagetter" value="http://localhost:5555/v3/index.json" allowInsecureConnections="True" />
  </packageSources>
  <packageSourceMapping>
    <packageSource key="nuget.org">
      <package pattern="*" />
    </packageSource>
    <packageSource key="ledgerline-local">
      <package pattern="Ledgerline" />
      <package pattern="Ledgerline.*" />
    </packageSource>
  </packageSourceMapping>
</configuration>
----

`<clear />` drops every source inherited from user- and machine-level files, so the repository restores the same way
everywhere. Package source mapping sends `+Ledgerline*+` to the local folder feed and everything else to nuget.org; the
BaGetter source on `localhost` is used only for pushing in the publishing examples, so it has no mapping (and it needs
`allowInsecureConnections` because it is plain HTTP). Credentials never go in this file -- see
xref:programming-languages/csharp/build-tools/nuget/authenticated-feeds-and-credential-providers.adoc[Authenticated Feeds].

Source: https://learn.microsoft.com/en-us/nuget/reference/nuget-config-file[NuGet: nuget.config reference],
https://learn.microsoft.com/en-us/nuget/consume-packages/package-source-mapping[NuGet: Package Source Mapping].

=== Directory.Build.props

[source,xml]
----
<Project>
  <PropertyGroup>
    <LangVersion>latest</LangVersion>
    <Nullable>enable</Nullable>
    <ImplicitUsings>enable</ImplicitUsings>
    <TreatWarningsAsErrors>true</TreatWarningsAsErrors>
    <Authors>Ledgerline contributors</Authors>
    <Company>Ledgerline</Company>
    <Copyright>Copyright (c) Ledgerline contributors</Copyright>
    <RepositoryUrl>https://example.com/ledgerline/ledgerline</RepositoryUrl>
    <RepositoryType>git</RepositoryType>
    <PackageProjectUrl>https://example.com/ledgerline</PackageProjectUrl>
    <PackageLicenseExpression>MIT</PackageLicenseExpression>
    <PackageReadmeFile>README.md</PackageReadmeFile>
    <PackageIcon>icon.png</PackageIcon>
    <IsPackable>false</IsPackable>
    <RestorePackagesWithLockFile>true</RestorePackagesWithLockFile>
  </PropertyGroup>
  <PropertyGroup Condition="'$(GITHUB_ACTIONS)' == 'true' or '$(TF_BUILD)' == 'true'">
    <ContinuousIntegrationBuild>true</ContinuousIntegrationBuild>
  </PropertyGroup>
</Project>
----

Defaults only: every value can be overridden in a project, which is how the four packable projects set `IsPackable`
back to `true`. The CI condition reads environment variables, which evaluation turns into properties in its first pass
(xref:programming-languages/csharp/build-tools/reproducible-and-deterministic-builds.adoc[Reproducible and Deterministic Builds]).

Source: https://learn.microsoft.com/en-us/visualstudio/msbuild/customize-by-directory#directorybuildprops-and-directorybuildtargets[MSBuild: Directory.Build.props and Directory.Build.targets].

=== Directory.Build.targets

[source,xml]
----
<Project>
  <ItemGroup Condition="'$(IsPackable)' == 'true'">
    <None Include="$(MSBuildThisFileDirectory)README.md" Pack="true" PackagePath="\" Visible="false" />
    <None Include="$(MSBuildThisFileDirectory)icon.png" Pack="true" PackagePath="\" Visible="false" />
  </ItemGroup>
</Project>
----

This file must be a `.targets` file: it tests `+$(IsPackable)+`, whose final value is known only after the project body
has been read. In `Directory.Build.props` the condition would see the repository default (`false`) and never add the
files. `+$(MSBuildThisFileDirectory)+` is the folder of the file that contains it, so the paths work from any project.

Source: https://learn.microsoft.com/en-us/visualstudio/msbuild/customize-by-directory#directorybuildprops-and-directorybuildtargets[MSBuild: Directory.Build.props and Directory.Build.targets].

=== Directory.Packages.props

== Directory.Build.props and .targets in detail

=== Props or targets?

The rule from the documentation: set **properties that projects or the SDK read** in `Directory.Build.props`, so
that the project file and the SDK see them; put **targets, and properties that depend on project values** (`+$(IsPackable)+`,
`+$(TargetFramework)+`, `+$(OutputType)+`, anything a package sets) in `Directory.Build.targets`. The two classic mistakes
are mirror images:

* *A TFM condition in `Directory.Build.props`*: `+Condition="'$(TargetFramework)' == 'net8.0'"+` is false in every
  single-target project and in outer builds, because the project body has not set the property yet; it only works in
  the inner builds of multi-targeted projects, where `TargetFramework` is a global property.
* *A default in `Directory.Build.targets`*: `<Nullable>enable</Nullable>` in the targets file overrides what the project
  set, instead of providing a default it can change.

Source: https://learn.microsoft.com/en-us/visualstudio/msbuild/customize-your-build#choose-between-adding-properties-to-a-props-or-targets-file[MSBuild: Choose between adding properties to a .props or .targets file].

=== Search scope and multi-level merging

MSBuild looks for `Directory.Build.props` in the project's folder and then in every parent, and **stops at the first
one it finds**. A `tests/Directory.Build.props` therefore *replaces* the root file for the test projects -- unless it
imports the parent explicitly with the `GetPathOfFileAbove` property function:

[source,xml]
----
<Project>
  <!-- Import the repository-wide file first: MSBuild stops at the first Directory.Build.props it finds. -->
  <Import Project="$([MSBuild]::GetPathOfFileAbove('Directory.Build.props', '$(MSBuildThisFileDirectory)../'))" />

  <PropertyGroup>
    <IsPackable>false</IsPackable>
    <GenerateDocumentationFile>false</GenerateDocumentationFile>
    <!-- Tests may use obsolete members of the library on purpose. -->
    <NoWarn>$(NoWarn);CS0618</NoWarn>
  </PropertyGroup>
</Project>
----

Querying the test project shows the merged values -- and, with the `Import` line removed, how much is silently lost:

[source,bash]
----
cd tests/Ledgerline.Tests
dotnet msbuild -getProperty:Nullable -getProperty:TreatWarningsAsErrors -getProperty:NoWarn -getProperty:DirectoryBuildPropsPath
----

[source,text]
----
{
  "Properties": {
    "Nullable": "enable",
    "TreatWarningsAsErrors": "true",
    "NoWarn": ";CS0618",
    "DirectoryBuildPropsPath": "~/ledgerline/tests/Directory.Build.props"
  }
}
--- without the import:
{
  "Properties": {
    "Nullable": "",
    "TreatWarningsAsErrors": "false",
    "DirectoryBuildPropsPath": "~/ledgerline/tests/Directory.Build.props"
  }
}
----

The same applies to `Directory.Build.targets` (with `+GetPathOfFileAbove('Directory.Build.targets', …)+`).
`DirectoryBuildPropsPath` shows which file was found; `ImportDirectoryBuildProps=false` (set before the import, for
example in a `-p:` switch) turns the lookup off. On Linux and macOS the file name is case-sensitive: a
`directory.build.props` is simply ignored.

Source: https://learn.microsoft.com/en-us/visualstudio/msbuild/customize-by-directory#search-scope[MSBuild: Search scope],
https://learn.microsoft.com/en-us/visualstudio/msbuild/customize-by-directory#use-case-multi-level-merging[Use case: multi-level merging],
https://learn.microsoft.com/en-us/visualstudio/msbuild/customize-by-directory#troubleshooting[Troubleshooting].

== Directory.Build.rsp

A response file holds command-line switches, one or more per line, `#` for comments. MSBuild reads `Directory.Build.rsp`
from the project's (or solution's) folder upwards for **command-line builds only** -- `dotnet build`, `dotnet msbuild`,
`msbuild.exe`, not Visual Studio:

[source,text]
----
# Defaults for every command-line build under this folder.
-nodeReuse:false
-p:LedgerlineBuildOrigin=cli
----

[source,bash]
----
cd src/Ledgerline
dotnet msbuild -getProperty:LedgerlineBuildOrigin
echo "[$(dotnet msbuild -noAutoResponse -getProperty:LedgerlineBuildOrigin)]"
----

[source,text]
----
cli
[]
----

`-noAutoResponse` (`-noautorsp`) ignores it. Because the IDE never reads it, `Directory.Build.rsp` should only hold
switches that change *how* the build runs (`-nodeReuse:false` on CI, `-warnAsMessage`, logger settings), never
properties that change *what* is built.

Source: https://learn.microsoft.com/en-us/visualstudio/msbuild/msbuild-response-files#directorybuildrsp[MSBuild: Directory.Build.rsp].

== .editorconfig and .globalconfig

Both feed options and diagnostic severities to the compiler and analyzers (and, for code style, to the IDE).
`.editorconfig` files apply to the files under their folder, by glob section; a **global AnalyzerConfig** file
(`.globalconfig`, `is_global = true`) applies to every file of the project, whatever its path. When the same key is set in
both, the documented precedence is: a later entry in the same file wins; between two `.editorconfig` files, the deeper
one wins; between two global files, the higher `global_level` wins (`.globalconfig` defaults to 100); and **between an
`.editorconfig` and a global file, the `.editorconfig` wins**. Compiler options (`-nowarn`, `-warnaserror`) beat all
of them.

A three-step demonstration with a block-scoped namespace and `EnforceCodeStyleInBuild` set to `true` (code-style rules do
not run at build time otherwise):

[source,text]
----
# .editorconfig
root = true

[*.cs]
csharp_style_namespace_declarations = file_scoped:warning
----

[source,text]
----
~/style/Accounts.cs(1,11): warning IDE0161: Convert to file-scoped namespace (https://learn.microsoft.com/dotnet/fundamentals/code-analysis/style-rules/ide0161) [~/style/Style.csproj]
----

Adding a `.globalconfig` with `dotnet_diagnostic.IDE0161.severity = error` raises it to an error (the `dotnet_diagnostic`
key beats the `:warning` suffix of the option):

[source,text]
----
~/style/Accounts.cs(1,11): error IDE0161: Convert to file-scoped namespace (https://learn.microsoft.com/dotnet/fundamentals/code-analysis/style-rules/ide0161) [~/style/Style.csproj]
----

Adding `dotnet_diagnostic.IDE0161.severity = none` to the `.editorconfig` switches it off again, because the
`.editorconfig` entry wins over the global file:

[source,text]
----
Build succeeded.
----

Source: https://learn.microsoft.com/en-us/dotnet/fundamentals/code-analysis/configuration-files#editorconfig[.NET: EditorConfig],
https://learn.microsoft.com/en-us/dotnet/fundamentals/code-analysis/configuration-files#global-analyzerconfig[Global AnalyzerConfig],
https://learn.microsoft.com/en-us/dotnet/fundamentals/code-analysis/configuration-files#precedence[Precedence].

== Common mistakes

* *A nested `Directory.Build.props` without the `GetPathOfFileAbove` import* -- the root settings vanish for that
  subtree, often unnoticed until a warning that should fail the build does not.
* *Wrong file-name casing on Linux/macOS* -- the file is ignored.
* *Project-dependent conditions in `.props`*, *unconditional defaults in `.targets`* -- see above.
* *Putting build-changing properties in `Directory.Build.rsp`* -- Visual Studio builds differ from CLI builds.
* *A `nuget.config` without `<clear />`* -- machine-level feeds leak into the repository's restores.
* *Expecting `.globalconfig` to beat `.editorconfig`* -- it is the other way round.

== Release notes

* **.NET 5**: global AnalyzerConfig files; **.NET 6**: `global_level` precedence.
* **.NET 8**: the artifacts output layout (`dotnet new buildprops --use-artifacts`).
* **.NET 10**: `test.runner` in `global.json`; `dotnet tool install` creates a manifest automatically.
