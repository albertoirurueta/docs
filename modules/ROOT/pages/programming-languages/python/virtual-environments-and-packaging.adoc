Two projects on the same machine often need *different, conflicting versions* of the same third-party package.
A *virtual environment* gives each project its own private set of installed packages, so installing one
project's dependencies never breaks another's. This page is the short introduction; pip, Poetry, lock files and publishing are
covered in depth in xref:programming-languages/python/build-tools/index.adoc[Build Automation Tools (pip & Poetry)].

== Why Virtual Environments

Without isolation, every `pip install` writes into the one global Python installation shared by *every* script
and project on the machine. Upgrading a package for project A can silently break project B, and there is no
record of which packages a given project actually needs. A virtual environment is a self-contained directory
holding its own Python interpreter (or a link to one) and its own `site-packages` -- packages installed while it
is active are invisible to any other environment. The standard library ships this as the **`venv`** module,
covered in the tutorial's https://docs.python.org/3/tutorial/venv.html[Virtual Environments and Packages]
chapter and specified in full under https://docs.python.org/3/library/venv.html[`venv`].

=== Creating and Activating an Environment

Create one with `python -m venv`, naming the directory that will hold it -- `.venv` is the common convention:

[source,bash]
----
python -m venv .venv
----

Activation adjusts the current shell so `python` and `pip` resolve to the environment's own copies; the command
differs per OS and shell:

[source,bash]
----
# macOS / Linux (bash or zsh)
source .venv/bin/activate
----

[source,bash]
----
# Windows (Command Prompt)
.venv\Scripts\activate.bat
----

[source,bash]
----
# Windows (PowerShell)
.venv\Scripts\Activate.ps1
----

Once active, the shell prompt is usually prefixed with the environment's name, and `python -m pip list` shows
only what has been installed *inside* it:

[source,bash]
----
(.venv) $ which python
/path/to/project/.venv/bin/python
----

Deactivate with a single command that works the same on every platform:

[source,bash]
----
deactivate
----

Deleting the environment is just deleting its directory -- nothing outside `.venv/` is ever touched:

[source,bash]
----
rm -rf .venv
----

== Installing Packages with pip

**`pip`** is the package installer bundled with Python; it downloads a package and its dependencies and installs
them into whichever environment is currently active. Its full command reference lives at
https://pip.pypa.io/en/stable/[pip documentation].

[source,bash]
----
pip install requests
pip install requests==2.31.0        # pin an exact version
pip install "requests>=2.28,<3"     # constrain a range
----

Uninstalling removes a package the same way:

[source,bash]
----
pip uninstall requests
----

=== Freezing and `requirements.txt`

`pip freeze` prints every installed package with the exact version currently resolved, in a format `pip` can
read back:

[source,bash]
----
pip freeze > requirements.txt
----

[source,text]
----
certifi==2024.7.4
charset-normalizer==3.3.2
idna==3.7
requests==2.32.3
urllib3==2.2.2
----

Committing `requirements.txt` to version control lets anyone -- a teammate, or a CI job -- recreate the exact
same set of installed packages in a fresh environment:

[source,bash]
----
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
----

== PyPI and `pyproject.toml`

**PyPI** (the Python Package Index, https://pypi.org) is the public repository `pip install <name>` downloads
from by default -- searching it by name or keyword is how most third-party packages are discovered before they
are added to a project. The full packaging ecosystem built around it -- how a project declares its own metadata,
dependencies, and build process -- is documented at https://packaging.python.org/[the Python Packaging User
Guide].

A modern project declares that metadata in a single file, **`pyproject.toml`**, at its root. Unlike
`requirements.txt` (a flat list of *installed* versions), `pyproject.toml` describes the project itself -- its
name, dependencies, and the tool used to build a distributable package from it:

[source,toml]
----
[project]
name = "my-project"
version = "0.1.0"
description = "A small example project"
dependencies = [
    "requests>=2.28",
]

[build-system]
requires = ["setuptools>=68"]
build-backend = "setuptools.build_meta"
----

The `[build-system]` table only names *which* build backend to use (`setuptools` above); the backend itself is a
separate tool responsible for turning the project into an installable distribution, a topic the Packaging User
Guide covers on its own. The rest of this section covers building and publishing a release with it.

=== Building Distributions

`python -m build` (the `build` package, `pip install build`) reads `pyproject.toml` and produces two
distributable files under `dist/`: a *sdist* (`.tar.gz`, the source distribution) and a *wheel* (`.whl`, a
prebuilt distribution pip installs without running the build backend again). The `[build-system]` table above
only names which backend does that work -- `setuptools` is this page's example, but `hatchling` and
`poetry-core` are interchangeable alternatives that read the same `[project]` metadata:

[source,bash]
----
python -m build              # writes dist/my_project-0.1.0.tar.gz and dist/my_project-0.1.0-py3-none-any.whl
----

=== Creating PyPI and TestPyPI Accounts

Publishing needs an account at https://pypi.org[pypi.org], and PyPI requires two-factor authentication to be
enabled on that account before it will accept a publish. A separate instance,
https://test.pypi.org[test.pypi.org], exists specifically for dry-run publishes -- it has its own independent
account and package namespace, so a broken upload or a name collision there never touches the real index.

=== Generating an API Token

*Account Settings → API tokens* creates a scoped token; PyPI recommends scoping it to a single project rather
than the whole account, which is only possible after that project's first manual upload has created it on the
index. The token is used with `twine` as a username/password pair, where the username is always the literal
string `+__token__+`:

[source,bash]
----
export TWINE_USERNAME=__token__
export TWINE_PASSWORD=pypi-AgEIcHlwaS5vcmc...   # the generated token, including its pypi- prefix
----

=== Publishing with twine

`twine` (`pip install twine`) uploads the files `python -m build` produced. A dry run against TestPyPI first
catches metadata or packaging problems without touching the real index:

[source,bash]
----
twine upload --repository testpypi dist/*
twine upload dist/*                        # the real release, once the TestPyPI upload looks right
----

=== PyPI Trusted Publishing (OIDC)

The recommended approach for a CI-driven release is PyPI's *Trusted Publishing*, which needs no stored API
token at all. A Trusted Publisher is configured once on pypi.org (under the project's *Publishing* settings),
naming the exact GitHub repository, workflow filename, and (optionally) environment allowed to publish; PyPI
then accepts a GitHub Actions OIDC token asserting the workflow run matches, in place of any credential:

[source,yaml]
----
name: build

on:
  push:
    branches: [ main ]
    tags: [ 'v*' ]
  pull_request:

jobs:
  build:
    runs-on: ubuntu-latest
    permissions:
      id-token: write        # required for PyPI Trusted Publishing

    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-python@v5
        with:
          python-version: '3.13'
          cache: 'pip'

      - run: pip install build
      - run: python -m build

      - name: Publish to PyPI
        if: startsWith(github.ref, 'refs/tags/v')
        uses: pypa/gh-action-pypi-publish@release/v1
----

== What a Virtual Environment Actually Is

A virtual environment is not a copy of Python and not a container. It is a small directory holding a `pyvenv.cfg` file,
a `bin` (or `Scripts` on Windows) folder with a `python` launcher that points back at the base interpreter, an `include`
folder and a private `lib/pythonX.Y/site-packages` directory. When the launcher starts, the interpreter reads
`pyvenv.cfg` next to it, notices it is in a venv, and sets `sys.prefix` to the environment while `sys.base_prefix` still
names the base installation. The `site` module then puts the environment's `site-packages` on `sys.path` (and, unless
`include-system-site-packages = true`, leaves the base installation's `site-packages` out). That is the whole trick: packages
installed with the environment's `pip` land in the environment's directory, and only that interpreter sees them.

[mermaid]
....
flowchart TD
    A["python in .venv/bin"] --> B["Interpreter finds pyvenv.cfg\none directory up"]
    B --> C["sys.prefix = .venv\nsys.base_prefix = base install"]
    C --> D["site module builds sys.path:\nstdlib + .venv site-packages"]
    D --> E["import requests searches\nthose directories in order"]
    F["source .venv/bin/activate"] -.-> G["Prepends .venv/bin to PATH\nso 'python' and 'pip' resolve there"]
    G -.-> A
....

[source,python]
----
import subprocess
import sys
import tempfile
import venv
from pathlib import Path

root = Path(tempfile.mkdtemp())
env = root / ".venv"
venv.create(env, with_pip=False)                 # same machinery as: python -m venv .venv

print(sorted(p.name for p in env.iterdir()))
cfg = dict(line.split(" = ", 1) for line in (env / "pyvenv.cfg").read_text().splitlines() if " = " in line)
print(sorted(cfg))                                # home, include-system-site-packages, version, ...
print(cfg["include-system-site-packages"])

python = env / "bin" / "python"
code = (
    "import sys, sysconfig;"
    "print(sys.prefix != sys.base_prefix);"
    "print(any(p.endswith('site-packages') and '.venv' in p for p in sys.path));"
    "print(sysconfig.get_paths()['purelib'].endswith('site-packages'))"
)
out = subprocess.run([str(python), "-c", code], capture_output=True, text=True).stdout.split()
print(out)
print("in a venv here:", sys.prefix != sys.base_prefix)    # false when run with the system interpreter
----

Output:

[source,text]
----
['bin', 'include', 'lib', 'pyvenv.cfg']
['command', 'executable', 'home', 'include-system-site-packages', 'version']
false
['True', 'True', 'True']
in a venv here: False
----

(The directory list also contains `lib64` on some Linux distributions, `Scripts` replaces `bin` on Windows, and the
`executable` and `command` keys of `pyvenv.cfg` were added in Python 3.11.)

=== Consequences worth knowing

* *Activation is optional.* `activate` only edits `PATH` (and the prompt). Running `.venv/bin/python script.py` or
  `+.venv/bin/pip install ...+` uses the environment without activating it, which is the robust form in scripts, cron jobs
  and CI. `python -m pip` guarantees that the `pip` matches the `python` you are running.
* *Environments are not relocatable.* The launcher records an absolute path, so moving or renaming the directory or the base
  Python breaks it. Recreate it from a lock or requirements file instead of copying it, and keep it out of version control
  (`.venv/` in `.gitignore`).
* *Isolation is about Python packages only.* System libraries, the interpreter version and environment variables still leak
  in; use a container or a tool that manages Python versions when you need more.
* *One environment per project* avoids the "works on my machine" class of failures caused by one global `site-packages`
  collecting incompatible versions, and some distributions refuse global `pip install` outright
  (https://peps.python.org/pep-0668/[PEP 668]).

=== From `requirements.txt` to a reproducible install

`pip install package` resolves the package's declared dependencies (as ranges), downloads wheels or builds source
distributions, and installs the result. A range means two installs on different days can differ, so applications record
the *exact* versions that worked (`pip freeze > requirements.txt`, or a lock file produced by a tool) and install from
that, while libraries declare loose ranges in `pyproject.toml` so they compose with other packages. Hash-checked
installs (`--require-hashes`) add integrity on top. The how and why of resolvers, lock files, build backends and
publishing are covered in depth in the xref:programming-languages/python/build-tools/index.adoc[Build Automation Tools]
sub-section.
