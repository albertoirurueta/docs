= Basic Usage & Project Setup
:description: Starting and working on a project with Poetry 2.5.1 -- poetry new (src layout by default since 2.1, --flat, --name, --readme, -i) and poetry init for an existing project, choosing the Python version, package mode vs non-package mode (package-mode = false for applications), adding dependencies, running code with poetry run (and its "Command not found", ModuleNotFoundError and ImportError errors) or activating the environment with poetry env activate, installing with and without poetry.lock, --no-root and --only-root, updating, committing the lock file, and why pip install -e . ignores the lock.
:keywords: poetry new, poetry init, src layout, flat layout, package mode, non-package mode, package-mode false, poetry add, poetry install, poetry run, poetry env activate, eval, poetry.lock, no-root, only-root, poetry update, poetry-plugin-shell, pip install -e ignores lock

include::partial$python-build-tools-disclaimer.adoc[]

This page walks through the everyday Poetry cycle: create or adopt a project, add dependencies, install, run, update. It was written
against Poetry 2.5.1 with poetry-core 2.5.0; every command ran on CPython 3.14.6 on 2026-10-22 with
`+POETRY_VIRTUALENVS_IN_PROJECT=true+`, so that each project's venv is the `.venv` next to its `pyproject.toml`. Scratch paths are
shortened to `+…+`. Installing Poetry itself is on
xref:programming-languages/python/build-tools/poetry/installation-and-self-management.adoc[Installation & Self-Management].

[mermaid]
....
flowchart LR
    A["edit code and pyproject.toml"] --> B["poetry add / remove"]
    B --> C["poetry lock (writes poetry.lock)"]
    C --> D["poetry install / sync (updates .venv)"]
    D --> E["poetry run pytest, poetry run birdtally"]
    E --> A
    F["poetry update"] --> C
....

`poetry add` and `poetry remove` lock and install for you; `poetry lock` on its own is needed after you edit `pyproject.toml` by hand.

== Creating a project: `poetry new`

[source,bash]
----
poetry new --author "The birdtally authors" birdtally
find birdtally | sort
cat birdtally/pyproject.toml
----

[source,text]
----
Created package birdtally in birdtally
birdtally
birdtally/README.md
birdtally/pyproject.toml
birdtally/src
birdtally/src/birdtally
birdtally/src/birdtally/__init__.py
birdtally/tests
birdtally/tests/__init__.py
----

[source,toml]
----
[project]
name = "birdtally"
version = "0.1.0"
description = ""
authors = [
    {name = "The birdtally authors"}
]
readme = "README.md"
requires-python = ">=3.14"
dependencies = [
]

[tool.poetry]
packages = [{include = "birdtally", from = "src"}]

[build-system]
requires = ["poetry-core>=2.0.0,<3.0.0"]
build-backend = "poetry.core.masonry.api"
----

* Since Poetry *2.1* the *src layout* is the default; `--src` is now a deprecated no-op and `--flat` creates
  `birdtally/birdtally/` instead (the trade-offs are on
  xref:programming-languages/python/build-tools/publishing/preparing-a-library.adoc[Preparing a Library]).
* `requires-python` defaults to the minor version of the Python that Poetry finds (here 3.14). For a library, lower it to the oldest
  Python you support, `>=3.10` for *birdtally*.
* Without `--author`, the author comes from your Git configuration.
* Other options: `--name` (package name if it differs from the directory), `--readme md|rst|txt`, `--description`,
  `--python`, `--dependency`, `--dev-dependency`, `-l/--license`, and `-i/--interactive` to be asked for each value.

[source,bash]
----
poetry new --flat --name flatbirds --readme rst flatbirds
find flatbirds | sort
----

[source,text]
----
Created package flatbirds in flatbirds
flatbirds
flatbirds/README.rst
flatbirds/flatbirds
flatbirds/flatbirds/__init__.py
flatbirds/pyproject.toml
flatbirds/tests
flatbirds/tests/__init__.py
----

Source: https://python-poetry.org/docs/basic-usage/#project-setup[Poetry: Project setup],
https://python-poetry.org/docs/cli/#new[Poetry CLI: new].

== Adopting an existing project: `poetry init`

`poetry init` writes a `pyproject.toml` in the current directory, asking questions unless you pass `--no-interaction`. It accepts the
same metadata options as `new` plus `--dependency` and `--dev-dependency`. A worked migration of a `requirements.txt` project is on
xref:programming-languages/python/build-tools/choosing-and-migrating.adoc#_migrating_a_requirements_txt_project_to_poetry[Choosing & Migrating].

Source: https://python-poetry.org/docs/basic-usage/#initialising-a-pre-existing-project[Poetry: Initialising a pre-existing project],
https://python-poetry.org/docs/cli/#init[Poetry CLI: init].

== Setting the Python version

`requires-python` is the range the _project_ supports; it constrains resolution (every dependency must support the whole range) and
becomes `Requires-Python` in the metadata. Which interpreter the _environment_ uses is a separate choice, made with
`poetry env use python3.14` or by running Poetry from an already active venv. If no environment exists yet, Poetry 2.5.1 starts from
the `python` on your `PATH` (or from the Python Poetry itself runs on, with `virtualenvs.use-poetry-python = true`) and, if that
does not satisfy `requires-python`, tries to find one that does; failing that it asks you to choose one with `env use`. See xref:programming-languages/python/build-tools/poetry/managing-environments.adoc[Managing Environments].

Source: https://python-poetry.org/docs/basic-usage/#setting-a-python-version[Poetry: Setting a Python version].

== Package mode and non-package mode

[cols="1,3,3",options="header"]
|===
| | Package mode (default) | Non-package mode (`package-mode = false`, Poetry 1.8)

| Use for | Libraries and anything you build or publish | Applications, scripts, notebooks, services
| `name`, `version` | Required | Optional
| `poetry install` | Also installs the project itself, in editable mode | Installs only the dependencies (as `--no-root`)
| `poetry build`, `poetry publish` | Work | Not possible
|===

*birdtally-report* is an application, so its file says:

[source,toml]
----
[project]
name = "birdtally-report"
version = "0.1.0"
description = "Weekly survey report built on birdtally."
requires-python = ">=3.10"
dependencies = ["birdtally[pretty] (>=0.1.0)"]

[tool.poetry]
package-mode = false

[tool.poetry.dependencies]
birdtally = { source = "birdwatch" }

[[tool.poetry.source]]
name = "birdwatch"
url = "http://localhost:8080/simple/"
priority = "explicit"
----

[source,bash]
----
poetry install
poetry run python report.py
----

== Adding dependencies

`poetry add rich` resolves, writes `"rich (>=15.0.0,<16.0.0)"` into `[project] dependencies`, updates `poetry.lock` and installs. Groups,
extras, Git and path dependencies are on
xref:programming-languages/python/build-tools/poetry/managing-dependencies-and-groups.adoc[Managing Dependencies & Groups], and the
constraint syntax on xref:programming-languages/python/build-tools/poetry/dependency-specification.adoc[Dependency Specification].
In short, `[project] dependencies` takes PEP 508 strings (`"rich (>=13)"`), and Poetry's caret (`+^13+`) and tilde (`+~13.7+`)
shorthands are allowed only in `[tool.poetry]` tables and on the `poetry add` command line.

Source: https://python-poetry.org/docs/basic-usage/#specifying-dependencies[Poetry: Specifying dependencies],
https://python-poetry.org/docs/basic-usage/#version-constraints[Poetry: Version constraints].

== Using the environment

=== `poetry run`

`poetry run <command>` runs a command inside the project's environment without activating it:

[source,bash]
----
poetry run birdtally survey.csv --by site
----

[source,text]
----
{
  "north-marsh": 6,
  "east-dunes": 3
}
----

The errors you meet with it all come from the environment being out of step with `pyproject.toml`:

* a command that is not installed in the environment, for example a script added to `[project.scripts]` without running
  `poetry install` again:
+
[source,text]
----
Command not found: nosuch
----
* a script entry that names a module that does not exist (`birdtally-old = "birdtally.commandline:main"`):
+
[source,text]
----
Traceback (most recent call last):
  File "…/pscr/.venv/bin/birdtally-old", line 3, in <module>
    from birdtally.commandline import main
ModuleNotFoundError: No module named 'birdtally.commandline'
----
* a script entry with a misspelt function (`birdtally-typo = "birdtally.cli:mian"`); with Poetry 2.5.1's generated launcher this is an
  `ImportError`, not an `AttributeError`:
+
[source,text]
----
Traceback (most recent call last):
  File "…/pscr/.venv/bin/birdtally-typo", line 3, in <module>
    from birdtally.cli import mian
ImportError: cannot import name 'mian' from 'birdtally.cli' (…/pscr/src/birdtally/cli.py)
----

Source: https://python-poetry.org/docs/basic-usage/#using-poetry-run[Poetry: Using poetry run],
https://python-poetry.org/docs/cli/#run[Poetry CLI: run].

=== Activating the environment

`poetry shell` left the core in Poetry 2.0. `poetry env activate` _prints_ the command that activates the environment; feed it to your
shell:

[source,bash]
----
poetry env activate
----

[source,text]
----
source …/poetry-flavour/birdtally/.venv/bin/activate
----

[source,bash]
----
eval $(poetry env activate)          # bash, zsh, csh
eval (poetry env activate)           # fish
----

[source,powershell]
----
Invoke-Expression (poetry env activate)
----

If you prefer the old sub-shell behaviour, install the `poetry-plugin-shell` plugin (see
xref:programming-languages/python/build-tools/poetry/plugins.adoc[Plugins]). When a venv is already active, or you manage one
yourself (conda, a hand-made venv), Poetry uses it and `poetry run` is not needed.

Source: https://python-poetry.org/docs/basic-usage/#using-your-virtual-environment[Poetry: Using your virtual environment],
https://python-poetry.org/docs/basic-usage/#activating-the-virtual-environment[Poetry: Activating the virtual environment],
https://python-poetry.org/docs/managing-environments/#activating-the-environment[Poetry: Activating the environment].

== Installing

*Without `poetry.lock`*, `poetry install` resolves the dependencies, writes the lock and installs. *With `poetry.lock`*, it installs
exactly the locked versions and does not resolve; if `pyproject.toml` changed in a way that makes the lock stale, it stops and asks
you to run `poetry lock` (see
xref:programming-languages/python/build-tools/poetry/lock-file-install-update-and-sync.adoc[Lock File: install, update & sync]).

In package mode `poetry install` also installs the project itself, in editable mode. `--no-root` skips it (dependencies only),
`--only-root` installs only the project:

[source,bash]
----
poetry install --no-root --only main -E pretty
poetry run python -c "import birdtally"
poetry install --only-root
poetry run python -c "import birdtally; print('ok')"
----

[source,text]
----
Updating dependencies
Resolving dependencies...

Package operations: 4 installs, 0 updates, 0 removals

  - Installing mdurl (0.1.2)
  - Installing markdown-it-py (4.2.0)
  - Installing pygments (2.21.0)
  - Installing rich (15.0.0)

Writing lock file
…
ModuleNotFoundError: No module named 'birdtally'
Installing dependencies from lock file

Installing the current project: birdtally (0.1.0)
ok
----

The first call had no lock file, so it resolved and wrote one ("Updating dependencies", "Writing lock file"); the second installed
"from lock file". `--no-root` is the first step of the Docker pattern on
xref:programming-languages/python/build-tools/ci-caching-and-containers.adoc#_poetry_no_root_no_directory_then_the_project[CI Caching & Containers].

Source: https://python-poetry.org/docs/basic-usage/#installing-dependencies[Poetry: Installing dependencies],
https://python-poetry.org/docs/basic-usage/#installing-without-poetrylock[Poetry: Installing without poetry.lock],
https://python-poetry.org/docs/basic-usage/#installing-with-poetrylock[Poetry: Installing with poetry.lock],
https://python-poetry.org/docs/basic-usage/#installing-dependencies-only[Poetry: Installing dependencies only].

== Committing the lock file

Commit `poetry.lock` for an application: everybody, CI and production then install the same versions. For a library it is optional,
because the lock has no effect on your users; if you commit it, refresh it regularly. The reasoning is on
xref:programming-languages/python/build-tools/lock-files-and-reproducible-installs.adoc#_commit_it_or_not[Lock Files & Reproducible Installs].

Source: https://python-poetry.org/docs/basic-usage/#committing-your-poetrylock-file-to-version-control[Poetry: Committing your poetry.lock file to version control],
https://python-poetry.org/docs/basic-usage/#as-an-application-developer[As an application developer],
https://python-poetry.org/docs/basic-usage/#as-a-library-developer[As a library developer].

== Updating

`poetry update` re-resolves all dependencies to the newest versions the constraints allow and rewrites the lock; `poetry update rich`
does it for one package (and what it needs). Constraints are not changed: to move beyond `+<16.0.0+`, use `poetry add rich@latest`.

Source: https://python-poetry.org/docs/basic-usage/#updating-dependencies-to-their-latest-versions[Poetry: Updating dependencies to their latest versions].

== `pip install -e .` ignores the lock

pip does not read `poetry.lock`. In a project whose lock pins `rich 14.3.3` (locked with a long cooldown to make the point), Poetry
installs that version and an editable pip install of the same directory gets the newest one:

[source,bash]
----
poetry install --only main -E pretty
poetry run python -c "import importlib.metadata as m; print('poetry env:', m.version('rich'))"
python -m venv ../pipvenv && ../pipvenv/bin/python -m pip install -q -e ".[pretty]"
../pipvenv/bin/python -c "import importlib.metadata as m; print('pip -e env:', m.version('rich'))"
----

[source,text]
----
  - Downgrading rich (15.0.0 -> 14.3.3)
poetry env: 14.3.3
pip -e env: 15.0.0
----

If someone must use pip, give them an export of the lock (`poetry export`) and `pip install --no-deps -e .` after it; see
xref:programming-languages/python/build-tools/poetry/exporting-requirements-and-bundling.adoc[Exporting Requirements & Bundling].

Source: https://python-poetry.org/docs/basic-usage/#installing-with-poetrylock[Poetry: Installing with poetry.lock],
https://pip.pypa.io/en/stable/topics/local-project-installs/#editable-installs[pip: Editable installs].
