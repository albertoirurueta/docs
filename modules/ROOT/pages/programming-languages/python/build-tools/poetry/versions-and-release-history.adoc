== How Poetry is released

* *Version numbers* are PEP 440 `major.minor.micro`, bumped "similar to Python's versioning", and explicitly *not* semantic
  versioning. A major bump (2.0.0) only comes for breaking changes that cannot go through a deprecation cycle; a minor release may
  add features, add deprecations and *drop features deprecated in an earlier minor release*; a micro release usually only fixes
  bugs and never drops a deprecated feature. So read the changelog before every minor upgrade, and pin Poetry in CI. The FAQ's
  reason: with so many users, almost any change breaks someone, and bumping the major version every time would make the minor
  number meaningless.
* *Two packages.* `poetry` is the command-line tool; `poetry-core` is the PEP 517 build back end that `[build-system]` names, with
  its own version (here 2.5.0). A project's builds depend only on poetry-core, so building it does not need the Poetry CLI at all.
* *Python support.* Poetry 2.5.1 itself requires Python `+>=3.10,<4.0+` and officially supports 3.15 since 2.5.0. Projects managed
  by it can target other Pythons; Poetry's own interpreter is independent of the project's.
* *Pre-releases* are installed with `--preview` (installer script, `poetry self update --preview`) or by pinning a version.

*Announced but not yet done* (in every release post from 2.1 to 2.5): when `pyproject.toml` has no `[build-system]`, Poetry will
fall back to setuptools, as PEP 517 says, instead of poetry-core. Poetry 2.5.1 still uses poetry-core and prints a warning, so
always declare `[build-system]`. The 2.5 post also plans to make `+installer.builtin-uninstall+` the default later.

Upgrade to 2.4.2 or later for the security fixes; every 2.x release before it is affected by at least one of the path traversal
issues.

== Pinning the Poetry a project needs

Since 2.0 (`requires-poetry` is checked before any other validation since 2.3), a project can state the Poetry versions that may manage it, and any other Poetry refuses to work on it. With
`requires-poetry = ">=3.0"` both `poetry check` and `poetry install` stop with exit code 1:

[source,toml]
----
[tool.poetry]
requires-poetry = ">=2.4.2,<3.0"
----

[source,text]
----
This project requires Poetry >=3.0, but you are using Poetry 2.5.1
----

Check the running version with `poetry --version` (`+Poetry (version 2.5.1)+`) or `poetry about`, which also prints the
poetry-core version (`Poetry-Core Version: 2.5.0`). In CI pin it explicitly (`pipx install poetry==2.5.1`; see
xref:programming-languages/python/build-tools/ci-caching-and-containers.adoc[CI Caching & Containers]). The lock file records the
Poetry that wrote it in its header comment (`+# This file is automatically @generated by Poetry 2.5.1 …+`) and its format in
`lock-version` (`2.1`). Poetry 2.5.1 reads formats 1.x and 2.x: a newer 2.x format gets the warning `The lock file might not be
compatible with the current version of Poetry.`, a 3.x format the error `The lock file is not compatible with the current version
of Poetry.`

Source: https://python-poetry.org/docs/pyproject/#requires-poetry[Poetry: requires-poetry].

== Compared with pip

pip uses calendar-based `YY.N` versions released quarterly and supports only its latest release (see
xref:programming-languages/python/build-tools/pip/versions-and-release-history.adoc[pip: Versions & Release History]). Poetry
uses `major.minor.micro` versions where a minor release may remove deprecated features; both tools ask you to read the changelog
before upgrading.
