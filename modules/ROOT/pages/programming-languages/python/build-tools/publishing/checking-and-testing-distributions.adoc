include::partial$python-build-tools-disclaimer.adoc[]

A release cannot be edited after upload, so check the files you are about to upload, not the source tree. This page runs the
checks on *birdtally*'s `dist/` with twine 7.0.0 (readme-renderer 46.0), check-wheel-contents 0.6.3 and pip 26.2.2 on CPython
3.14.6, on 2026-10-22. TestPyPI is described, not used: nothing from this section is uploaded to a public index.

== `twine check`

`twine check` validates the metadata of each file and renders its long description the way PyPI does:

[source,bash]
----
python -m pip install twine==7.0.0
twine check --strict dist/*
----

[source,text]
----
Checking dist/birdtally-0.1.0-py3-none-any.whl: PASSED
Checking dist/birdtally-0.1.0.tar.gz: PASSED
----

A reStructuredText README with a Sphinx role (`+:py:func:+` around `+birdtally.tally_by_site+`), which plain docutils on PyPI does not know,
fails with exit code 1:

[source,text]
----
Checking dist/birdtally-0.1.0-py3-none-any.whl: FAILED
ERROR    `long_description` has syntax errors in markup and would not be
         rendered on PyPI.
         line 4: Error: Unknown interpreted text role "py:func".
----

PyPI rejects such an upload ("the description failed to render"). Without a `readme`, the check passes with warnings, and
`--strict` turns warnings into a failure:

[source,text]
----
Checking …/dist/birdtally-0.1.0-py3-none-any.whl: PASSED with warnings
WARNING  `long_description_content_type` missing. defaulting to `text/x-rst`.
WARNING  `long_description` missing.
----

Use `--strict` in CI. Markdown READMEs are rendered as GitHub-flavoured Markdown by default (CommonMark with
`+text/markdown; variant=CommonMark+`); Markdown errors do not fail the check, so look at the rendering on TestPyPI once.

Source: https://twine.readthedocs.io/en/stable/#twine-check[twine: twine check],
https://packaging.python.org/en/latest/guides/making-a-pypi-friendly-readme/#validating-restructuredtext-markup[PUG: Validating reStructuredText markup],
https://packaging.python.org/en/latest/guides/making-a-pypi-friendly-readme/#including-your-readme-in-your-package-s-metadata[PUG: Including your README in your package's metadata],
https://docs.pypi.org/project-management/project-descriptions/#choosing-a-markup-language[PyPI: Choosing a markup language],
https://docs.pypi.org/publishing/troubleshooting/#why-am-i-getting-the-description-failed-to-render-error[PyPI: The description failed to render].

== `check-wheel-contents`

`twine check` does not look at the files in a wheel. The third-party check-wheel-contents does: duplicate files, `.pyc` files,
modules outside the package, an empty wheel. A typo in hatchling's wheel target (`packages = ["src/birdtaly"]`) made build
succeed and twine pass, but produced a wheel with no code:

[source,bash]
----
python -m build -w
twine check dist/*.whl
check-wheel-contents dist/*.whl
----

[source,text]
----
Successfully built birdtally-0.1.0-py3-none-any.whl
Checking …/birdtally-0.1.0-py3-none-any.whl: PASSED
…/birdtally-0.1.0-py3-none-any.whl: W007: Wheel library is empty
…/birdtally-0.1.0-py3-none-any.whl: W008: Wheel is empty
----

check-wheel-contents exits with 1 here and prints `OK` for the correct wheel. It does not notice a missing license file (the
`license-files` mistake shown on
xref:programming-languages/python/build-tools/publishing/preparing-a-library.adoc#_license_and_license_files_pep_639[Preparing a Library]
passed), so keep `unzip -l` in the routine.

Source: https://github.com/jwodder/check-wheel-contents[check-wheel-contents].

== Testing the artefacts, not the tree

Tests in the project directory can import the source instead of the installed package (less so with a src layout). Install the
built files into a fresh environment, without the index, and run the tests and the CLI there:

[source,bash]
----
python -m venv /tmp/release-check
/tmp/release-check/bin/python -m pip install --no-index --find-links dist/ birdtally
/tmp/release-check/bin/birdtally examples/survey.csv --by site
/tmp/release-check/bin/python -m pip install pytest
cd /tmp && /tmp/release-check/bin/python -m pytest -q …/birdtally/tests
----

[source,text]
----
Installing collected packages: birdtally
Successfully installed birdtally-0.1.0
{
  "north-marsh": 6,
  "east-dunes": 3
}
..                                                                       [100%]
2 passed in 0.01s
----

Run pytest from outside the project so the source tree is not on `sys.path`. Then test the sdist the same way, forcing pip to
build it (`--no-binary birdtally`). Offline, that fails, because building needs the backend:

[source,text]
----
Processing ./dist/birdtally-0.1.0.tar.gz
  Installing build dependencies: started
  Installing build dependencies: finished with status 'error'
  error: subprocess-exited-with-error
  × installing build dependencies for birdtally did not run successfully.
  │ exit code: 1
  ╰─> [3 lines of output]
      Looking in links: dist/
      ERROR: Could not find a version that satisfies the requirement hatchling>=1.27 (from versions: none)
      ERROR: No matching distribution found for hatchling>=1.27
      [end of output]
----

With the index available, `pip install dist/birdtally-0.1.0.tar.gz` built and installed it. This is exactly what a user without a
matching wheel experiences, so it is worth the minute. build's default (wheel built from the sdist) already covers most sdist
mistakes.

Source: https://build.pypa.io/en/stable/how-to/basic-usage.html#testing-the-sdist[build: Testing the sdist].

== TestPyPI

TestPyPI (`https://test.pypi.org/`) is a separate instance of PyPI for rehearsing a release (not run here):

* it needs its *own account and tokens*, and its own trusted publishers;
* its database is *pruned* from time to time, accounts included;
* it has the same rules as PyPI: a filename can be used once, so bump a dev or post version for each rehearsal
  (`0.1.0.dev1`, `0.1.0.dev2`);
* upload with `+twine upload --repository testpypi dist/*+` (see
  xref:programming-languages/python/build-tools/publishing/publishing-with-build-and-twine.adoc[Publishing with build & twine]);
* install from it with
  `pass:c[python -m pip install --index-url https://test.pypi.org/simple/ --extra-index-url https://pypi.org/simple/ birdtally]`,
  so that dependencies still come from PyPI.

That last command merges both indexes, so *any* project name could be served by TestPyPI, where anyone can upload anything: a
dependency-confusion risk. Use it only in a throwaway environment, or pin the dependencies with hashes. Size-limit increases are
requested per index, so a project that needed one on PyPI may hit TestPyPI's default limit.

Source: https://packaging.python.org/en/latest/guides/using-testpypi/#registering-your-account[PUG: Using TestPyPI: Registering your account],
https://packaging.python.org/en/latest/guides/using-testpypi/#using-testpypi-with-twine[Using TestPyPI with twine],
https://packaging.python.org/en/latest/guides/using-testpypi/#using-testpypi-with-pip[Using TestPyPI with pip],
https://packaging.python.org/en/latest/guides/using-testpypi/#setting-up-testpypi-in-pypirc[Setting up TestPyPI in .pypirc],
https://docs.pypi.org/project-management/storage-limits/#requesting-a-file-size-limit-increase[PyPI: Requesting a file size limit increase].
