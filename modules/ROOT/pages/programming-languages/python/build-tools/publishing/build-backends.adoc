= Build Backends
:description: Choosing the PEP 517 build backend that turns a project into an sdist and a wheel -- what a backend does, the same birdtally project built with setuptools 84.2.1, hatchling 1.32.4, flit-core 4.1.0, pdm-backend 2.5.0, poetry-core 2.5.0 and uv_build 0.13.5 and compared on the [build-system] snippet, PEP 639 support, the Core Metadata version written, dynamic versions, what the sdist contains and editable installs; setuptools specifics (tool.setuptools.dynamic, setup.py that is fine to keep but not to run, pkg_resources removed in 82.0.0); the extension backends scikit-build-core, meson-python and maturin; Poetry 2.1+ building with any backend; and the stale claims in the PUG and build documentation.

A *build backend* is the library named in `[build-system]` that a frontend (pip, build, Poetry, uv) calls through the PEP 517
hooks to produce an sdist and a wheel; frontends and backends are explained on
xref:programming-languages/python/build-tools/packaging-concepts-and-standards.adoc#_build_frontends_build_backends_and_build_isolation[Packaging Concepts & Standards].
The backend decides what goes into the distributions and how the metadata is written; the `[project]` table is the same for all
of them. This page builds *birdtally* (src layout, static `[project]` metadata, an MIT license, `py.typed`) with six backends,
changing only `[build-system]`, using build 1.6.1 on CPython 3.14.6 on 2026-10-22.

All six built a wheel with the same four modules, `py.typed` and `licenses/LICENSE`, and all six worked with `pip install -e`
(PEP 660 editable installs). Where they differ:

* *Metadata version*: hatchling and flit-core already write Core Metadata 2.5 (which adds `Import-Name`); the others write 2.4.
  PyPI and twine 7.0.0 accept both.
* *sdist contents* vary the most: compare `+tar tzf dist/*.tar.gz+` across backends before switching, and configure inclusion
  explicitly (`[tool.hatch.build.targets.sdist]`, `+[tool.poetry] include+`, `MANIFEST.in` for setuptools).
* *Dynamic metadata*: setuptools, hatchling, pdm-backend and flit-core can compute the version; poetry-core reads it from
  `+[tool.poetry]+`; uv_build accepts only static metadata.
* *Plugins*: hatchling, pdm-backend, poetry-core and setuptools support plugins (for example VCS versions); flit-core and uv_build
  deliberately do not.
* *config-settings* (`python -m build -C key=value`) are backend-specific. poetry-core accepts `local-version`
  (`-C local-version=dev1` built `birdtally-0.1.0+dev1-py3-none-any.whl`), although build's config-settings page says poetry-core
  supports none; setuptools wraps its command options in `+--build-option+`
  (`pass:c[-C--build-option=bdist_wheel -C--build-option=--build-number -C--build-option=123]` built
  `birdtally-0.1.0-123-py3-none-any.whl`); hatchling has `reproducible` and `shared-data`. See
  xref:programming-languages/python/build-tools/publishing/building-sdists-and-wheels.adoc[Building sdists & Wheels].

Pin a lower bound for the features you use (PEP 639 needs the versions in the table) and, for backends whose authors recommend it
(uv_build, poetry-core), an upper bound below their next breaking release.

=== Stale statements in the documentation

* The PUG tool recommendations and the build documentation's backend explanation both say poetry-core uses `+[tool.poetry]+`
  instead of the standard `[project]` table. That was true before poetry-core 2.0 (2025); the poetry-core build above used only
  `[project]`.
* The PUG packaging tutorial pins `pass:c[uv_build >= 0.12.19, <0.13.0]`, while 0.13.5 is current and the uv documentation shows
  `pass:c[uv_build>=0.13.5,<0.14]`.
* The build explanation's setuptools snippet still lists `"wheel"` in `requires`, which modern setuptools does not need.

== setuptools specifics

* `+[tool.setuptools.dynamic]+` fills `dynamic` keys from attributes or files (`version`, `readme`, `classifiers`, …); using it for
  `dependencies` and `optional-dependencies` is marked *BETA*.
* *`setup.py` is not deprecated, running it is.* A `setup.py` that only calls `setup()` (for C extensions or other programmatic
  configuration) is still supported, next to `pyproject.toml`; `python setup.py sdist`, `+bdist_wheel+`, `install`, `develop` and
  `upload` are deprecated or removed. Use `python -m build` and `pip install`. The `upload`, `register` and `+upload_docs+` commands
  are gone (setuptools 75.0.0, with the distutils merge).
* `+pkg_resources+` was removed in setuptools 82.0.0 (2026-02-08); use `importlib.metadata` and `importlib.resources`.
* To modernise a `setup.py` project: add `pyproject.toml` with `[build-system]`, move static metadata into `[project]`, keep
  `setup.py` only for what cannot be static, and list computed keys in `dynamic`.

== Backends for extension modules

[cols="1,3",options="header"]
|===
| Backend (version) | For

| setuptools | C and C++ natively, Rust and Go through plugins.
| scikit-build-core 1.1.1 | C, C++, Fortran and anything CMake builds.
| meson-python 0.22.1 | C, C++, Fortran, Rust and the other languages Meson supports; common in scientific Python.

== Poetry and other backends

Since Poetry 2.1, `poetry build` honours whatever `[build-system]` names: with another backend (or another poetry-core version
than the one Poetry bundles) it builds in an isolated environment, like `python -m build`. Without a `[build-system]` table it
still falls back to its bundled poetry-core with a warning, and the Poetry team has announced a switch to the PEP 517 default,
setuptools, in a future release. A Poetry-managed project can therefore use hatchling or maturin for its builds and Poetry for
dependencies.

Source: https://python-poetry.org/docs/libraries/#alternative-build-backends[Poetry: Alternative build backends],
https://python-poetry.org/blog/announcing-poetry-2.1.0/#support-for-alternative-build-backends-in-poetry[Announcing Poetry 2.1.0].
