= Build Automation Tools (pip & Poetry)
:description: Landing page for the Python build automation section -- what build automation means in Python and why no single tool does everything, the five roles (build frontend, build backend, installer, index, environment) and which of pip and Poetry fills each, a pip-versus-Poetry contrast, the release baseline of every tool used (pip 26.2.2, Poetry 2.5.1, poetry-core 2.5.0, build 1.6.1, twine 7.0.0 and the backends), the birdtally example project, and a reading path through the shared, pip, Poetry and publishing pages.
:keywords: Python build automation, pip, Poetry, poetry-core, build frontend, build backend, installer, package index, virtual environment, PyPI, pyproject.toml, sdist, wheel, packaging, publishing, release baseline, birdtally, reading path

include::partial$python-build-tools-disclaimer.adoc[]

In Java, one tool (Maven or Gradle) compiles, tests, packages and publishes. Python splits the same work across *standards* and
*interchangeable tools*: `pyproject.toml` describes a project, a *build backend* turns it into distribution files, an
*installer* puts those files into an *environment*, and a *package index* stores and serves them. "Build automation" in Python
is the choice and wiring of those tools, so that every developer and every CI job builds, locks, installs and publishes the same
way. This section covers the two tools most projects choose between: https://pip.pypa.io/[pip], the standard installer that ships
with Python, and https://python-poetry.org/[Poetry], an all-in-one dependency manager and packaging tool built on the same
standards. Basic virtual environments and a first upload are on
xref:programming-languages/python/virtual-environments-and-packaging.adoc[Virtual Environments & Packaging]; this section goes
much further.

== The five roles

[mermaid]
....
flowchart LR
    SRC["Source tree + pyproject.toml"] -->|"frontend calls PEP 517 hooks: pip, build, poetry build"| BE["Build backend: hatchling, setuptools, poetry-core, ..."]
    BE --> DIST["sdist (.tar.gz) and wheel (.whl)"]
    DIST -->|"upload: twine, poetry publish"| IDX[("Index: PyPI, TestPyPI, private")]
    IDX -->|"resolve + download: pip, Poetry"| INST["Installer: pip, Poetry's installer"]
    DIST -.->|"local files"| INST
    INST --> ENV["Environment: venv, Poetry env, pipx env"]
....

[cols="1,3,2,2",options="header"]
|===
| Role | Job | pip side | Poetry side

| Build frontend
| Reads `[build-system]`, creates an isolated build environment, calls the backend's hooks.
| `pip` (when installing from source), `python -m build`
| `poetry build`, `poetry install` (for the project)

| Build backend
| Turns the project into an sdist and a wheel, writing the core metadata.
| any: hatchling, setuptools, flit-core, pdm-backend, uv_build, …
| poetry-core (or any backend since Poetry 2.1)

| Installer
| Resolves versions and installs wheels into an environment.
| `pip install`
| `poetry install` / `poetry sync` (its own installer)

| Index
| Stores distributions and serves them through the simple API.
| PyPI, TestPyPI, private indexes; upload with twine
| the same; upload with `poetry publish`

| Environment
| Where the packages end up.
| a venv you create (`python -m venv`)
| one Poetry creates and manages per project
|===

*pip versus Poetry in one paragraph.* pip installs what it is told into whichever environment runs it: it resolves, downloads,
builds and installs, and since 25.1 it can write a `pylock.toml`, but it does not manage projects, environments, version bumps or
publishing ("pip is not a workflow management tool"); you combine it with venv, build, twine and a requirements or lock file.
Poetry manages the whole project: it edits `pyproject.toml` (`poetry add`), keeps a cross-platform `poetry.lock`, creates the
virtual environment, builds with poetry-core and publishes. The choice, and the way from one to the other, is on
xref:programming-languages/python/build-tools/choosing-and-migrating.adoc[Choosing & Migrating].

== The running example

Every page uses *birdtally*, a small original library that tallies bird-survey sightings from a CSV file: a `birdtally` command,
a `pretty` extra (rich tables), `test`, `lint` and `docs` dependency groups, and a `py.typed` marker. It exists in two flavours,
one managed with pip (hatchling backend, `requirements`/`pylock.toml` locks) and one with Poetry (poetry-core, `poetry.lock`),
plus a `birdtally-report` application that consumes the library from a private index. Nothing is ever uploaded to PyPI or
TestPyPI: uploads go to a local pypiserver or devpi.
