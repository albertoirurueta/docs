A docstring is Python's built-in mechanism for attaching documentation to code -- a string literal placed
where the language itself will pick it up, retrievable at runtime via `+.__doc__+` or `help()`, and consumed
both by humans reading the source and by tooling that turns it into browsable documentation.

== What Is a Docstring?

A docstring is a string literal that is the *first statement* in the body of a module, class, function, or
method. https://peps.python.org/pep-0257/[PEP 257] sets the conventions every style below builds on: a
one-line docstring fits on a single line, with the closing `"""` on that same line and no blank line before
or after it; a multi-line docstring opens with a one-line summary, a blank line, then further detail, with
the closing `"""` on its own line. Full coverage is also in the tutorial's
https://docs.python.org/3/tutorial/controlflow.html#documentation-strings[Documentation Strings section]
(the same source xref:programming-languages/python/functions.adoc[Functions] cites for its own brief mention).

[source,python]
----
"""A module for working with two-dimensional shapes."""


class Circle:
    """A circle defined by its radius."""

    def area(self):
        """Return the circle's area."""
        return 3.14159 * self.radius ** 2


import shapes
print(shapes.__doc__)          # A module for working with two-dimensional shapes.
print(shapes.Circle.__doc__)   # A circle defined by its radius.
print(shapes.Circle.area.__doc__)   # Return the circle's area.
help(shapes.Circle)             # prints a formatted summary built from these docstrings
----

== Documenting Code with Docstrings

A well-documented public function or method's docstring typically covers, in order: a one-line summary of
what it does, its parameters (name, expected type, meaning), its return value, any exceptions it may raise,
and, where it helps, a short usage example. Which of these apply depends on the code -- a simple helper may
need only the summary line, while a public API function benefits from all of them. The *style* used to lay
these out (headings, field markers, indentation) is a separate choice, covered in <<docstring-styles>> below.

An example embedded in a docstring can double as a test: an interactive-session snippet (`>>>` prompts and
their expected output) inside a docstring can be collected and run automatically via
https://docs.python.org/3/library/doctest.html[`doctest`], keeping the example honest as the code changes.

== Docstring Styles

The same function, documented in each of the styles below, to compare them directly:

=== Google Style

Named sections (`Args:`, `Returns:`, `Raises:`) with indented entries, documented in
https://google.github.io/styleguide/pyguide.html#38-comments-and-docstrings[the Google Python Style Guide]:

[source,python]
----
def divide(a, b):
    """Divide two numbers.

    Args:
        a: The dividend.
        b: The divisor.

    Returns:
        The result of a / b.

    Raises:
        ZeroDivisionError: If b is zero.
    """
    return a / b
----

=== NumPy Style

Section headers underlined with dashes and a `name : type` line per parameter, documented in
https://numpydoc.readthedocs.io/en/latest/format.html[the numpydoc format guide] -- the more verbose of the
mainstream styles, and the convention scientific-Python projects (NumPy, SciPy, pandas) use:

[source,python]
----
def divide(a, b):
    """Divide two numbers.

    Parameters
    ----------
    a : float
        The dividend.
    b : float
        The divisor.

    Returns
    -------
    float
        The result of a / b.

    Raises
    ------
    ZeroDivisionError
        If b is zero.
    """
    return a / b
----

=== reStructuredText (Sphinx) Style

Field lists (`:param:`, `:type:`, `:returns:`, `:rtype:`, `:raises:`) inline in the docstring body, the
native format for https://www.sphinx-doc.org/en/master/[Sphinx]'s documentation generator:

[source,python]
----
def divide(a, b):
    """Divide two numbers.

    :param a: The dividend.
    :type a: float
    :param b: The divisor.
    :type b: float
    :returns: The result of a / b.
    :rtype: float
    :raises ZeroDivisionError: If b is zero.
    """
    return a / b
----

=== Epytext

A *legacy* style, predating the three above and rarely chosen for new code today, but still found in older
codebases -- listed here for completeness. It uses `@`-prefixed fields (`@param`, `@return`, `@raise`)
similar in spirit to Javadoc:

[source,python]
----
def divide(a, b):
    """Divide two numbers.

    @param a: The dividend.
    @type a: float
    @param b: The divisor.
    @type b: float
    @return: The result of a / b.
    @rtype: float
    @raise ZeroDivisionError: If b is zero.
    """
    return a / b
----

== Generating Static Documentation Sites from Docstrings

Docstrings written in any of the styles above can be pulled out of the source and rendered as a browsable
documentation site, without hand-writing the reference pages:

=== Sphinx

https://www.sphinx-doc.org/en/master/[Sphinx] is the long-standing, most configurable option, and the
generator CPython's own documentation is built with. Its
https://www.sphinx-doc.org/en/master/usage/extensions/autodoc.html[`autodoc` extension] pulls docstrings
directly from live, importable code via `automodule`/`autoclass`/`autofunction` directives; its
https://www.sphinx-doc.org/en/master/usage/extensions/napoleon.html[`napoleon` extension] translates Google-
and NumPy-style docstrings into Sphinx's native reStructuredText fields, so either style renders correctly
without being rewritten:

[source,bash]
----
pip install sphinx
sphinx-quickstart      # scaffolds a docs/ project with conf.py and index.rst
sphinx-build -b html docs docs/_build
----

=== pdoc

https://pdoc.dev/[pdoc] is a zero-config alternative: it introspects a package directly and renders its
docstrings with no separate build-config file to maintain. Any of the styles above render reasonably;
Google and NumPy style render best since pdoc recognizes their section headings:

[source,bash]
----
pip install pdoc
pdoc ./my_package      # serves a live-reloading preview; add -o docs to write static HTML instead
----

=== MkDocs with mkdocstrings

https://www.mkdocs.org/[MkDocs] builds a Markdown-based documentation site from a `mkdocs.yml` config; the
https://mkdocstrings.github.io/[`mkdocstrings`] plugin injects API reference pages pulled from docstrings via
a `::: module.path` directive placed in a Markdown page, fitting naturally into a site that already mixes
hand-written guides with generated reference material:

[source,bash]
----
pip install mkdocs "mkdocstrings[python]"
mkdocs serve            # live preview at http://127.0.0.1:8000
----

Sphinx is the most configurable and extension-rich choice, and the long-standing default for large projects
(CPython included); `pdoc` is the fastest path to a browsable API reference with no configuration at all;
MkDocs with `mkdocstrings` suits projects that already publish a Markdown-based documentation site and want
API reference pages folded into it alongside hand-written guides.

== How Docstrings Are Stored and Consumed

A docstring is not a comment. When a module, class or function body *begins* with a string literal, the compiler stores
that string in the object's `+__doc__+` attribute; every other string statement is just an expression that is evaluated and
thrown away. Because the text is a live attribute, it is available at run time to `help()`, the interactive prompt,
`inspect.getdoc`, IDE hover cards, `doctest`, documentation generators and libraries that build command-line help or API
schemas from it.

[mermaid]
....
flowchart LR
    S["Docstring in source"] --> C["Compiler stores it in __doc__"]
    C --> H["help and pydoc\n(terminal help)"]
    C --> I["inspect.getdoc\n(cleans indentation)"]
    C --> D["doctest\nruns the >>> examples"]
    C --> G["Sphinx, pdoc, mkdocstrings\nparse sections and render HTML"]
    C --> E["Editors and AI assistants\nshow it on hover"]
....

[source,python]
----
import subprocess
import sys

source = (
    "def f():\n"
    '    """Documented."""\n'
    "print(f.__doc__)\n"
)
for flags in ([], ["-OO"]):
    out = subprocess.run([sys.executable, *flags, "-c", source], capture_output=True, text=True).stdout.strip()
    print(flags or "normal", "->", out)

def g():
    "A one-line docstring is just the first string literal."
    "This second string is an ordinary expression, not a docstring."
print(g.__doc__)
x = "a string statement before the function is not its docstring"
def h(): pass
print(h.__doc__)
----

Output:

[source,text]
----
normal -> Documented.
['-OO'] -> None
A one-line docstring is just the first string literal.
None
----

Because `+__doc__+` is a normal attribute, running Python with `-OO` removes docstrings from the compiled code, so a program
must never *depend* on a docstring for behaviour (some libraries that build parsers from docstrings break under `-OO`).
Indentation inside a docstring is part of the string; `inspect.cleandoc` (used by `help` and `inspect.getdoc`) removes the
common leading whitespace so that a docstring can be indented to match its code.

=== Writing the content: summary, contract, examples

A good docstring answers the questions a caller has without reading the body: *what* the function does in one imperative
summary line (the first line and then a blank line, so tools can show it alone), *what* each parameter means (not just its
type: a type hint already says that), *what* it returns, *which* exceptions it raises on purpose, and *how* to use it, with
a short example. Describe behaviour and constraints, not the implementation, and keep it in step with the code: a wrong
docstring is worse than none. Classes document the object's purpose and public attributes, with `+__init__+` arguments in the
class docstring or the initialiser's, consistently; modules open with a docstring that says what the module is for.

The sample below uses the Google style described earlier on this page. Its `>>>` lines are *doctests*: examples that
`doctest` extracts and runs, which keeps the documented behaviour true. `doctest.testmod()` printed
`TestResults(failed=0, attempted=2)`, so both examples passed; run them in a project with `python -m doctest module.py` or
`pytest --doctest-modules`.

[source,python]
----
import doctest
import inspect
import pydoc


def late_fee(days, rate=0.25):
    """Return the fine for a book returned *days* late.

    Args:
        days: Whole days past the due date; negative values mean early.
        rate: Fine per day.

    Returns:
        The fine, never negative.

    Raises:
        TypeError: If ``days`` is not an int.

    >>> late_fee(10)
    2.5
    >>> late_fee(-3)
    0.0
    """
    if not isinstance(days, int):
        raise TypeError("days must be an int")
    return max(0.0, days * rate)


class Shelf:
    """A named collection of titles.

    Attributes:
        name: Display name.
    """

    def __init__(self, name):
        self.name = name

    def add(self, title):
        """Add *title* and return the new size."""


print(late_fee.__doc__.splitlines()[0])
print(inspect.getdoc(late_fee).splitlines()[:1], inspect.cleandoc("   a\n      b\n   c"))
print(Shelf.add.__doc__, Shelf.__doc__.splitlines()[0])
print(inspect.signature(late_fee), pydoc.render_doc(late_fee, renderer=pydoc.plaintext).splitlines()[2])
print(doctest.testmod(verbose=False))                  # runs the >>> examples in this module
----

Output:

[source,text]
----
Return the fine for a book returned *days* late.
['Return the fine for a book returned *days* late.'] a
   b
c
Add *title* and return the new size. A named collection of titles.
(days, rate=0.25) late_fee(days, rate=0.25)
TestResults(failed=0, attempted=2)
----

=== Keeping documentation honest

* generate reference pages from docstrings (Sphinx with autodoc and Napoleon for Google or NumPy style, pdoc, or
  MkDocs with mkdocstrings) so there is one source of truth;
* run doctests or example tests in CI, and fail the documentation build on warnings so broken cross-references are caught;
* use type hints for types and the docstring for meaning, and pick one docstring style per project and enforce it with a linter
  (the `D` rules of Ruff or `pydocstyle`);
* link to the full documentation from the README rather than copying it, and keep examples small enough to run as tests.
