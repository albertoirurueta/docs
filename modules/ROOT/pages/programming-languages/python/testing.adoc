https://docs.pytest.org/en/stable/[pytest] is the de facto standard test runner for Python: tests are plain
functions using the built-in `assert` statement, with no special assertion API to learn. This page is grounded
primarily in the official pytest documentation rather than the general Python docs, since pytest itself is a
third-party project.

== Installing pytest and Writing a First Test

Install pytest with `pip`:

[source,bash]
----
pip install pytest
----

pytest *discovers* tests on its own: by default it recurses into the current directory and collects any file
matching `+test_*.py+` or `+*_test.py+`, then within each file any function named `+test_*+` (and any method named
`+test_*+` on a class named `+Test*+`). No test registry or base class is required. Discovery conventions are
documented under
https://docs.pytest.org/en/stable/explanation/goodpractices.html#conventions-for-python-test-discovery[Conventions
for Python test discovery].

[source,python]
----
# test_math_utils.py
from math_utils import add

def test_add_returns_sum():
    assert add(2, 3) == 5

def test_add_handles_negatives():
    assert add(-1, 1) == 0
----

pytest rewrites `assert` at import time so a failure shows the actual values of every sub-expression -- unlike
the standard library's `unittest`, there is no `assertEqual`, `assertTrue`, or similar method to remember.

== Running Tests

Run the whole suite from the project root, add `-v` for one line per test, and narrow the run to a single file,
a single test, or a substring/expression match with `-k`:

[source,bash]
----
pytest                                    # run every discovered test
pytest -v                                 # verbose: one line per test
pytest test_math_utils.py                 # only this file
pytest test_math_utils.py::test_add_returns_sum   # only this test
pytest -k "add and not negative"          # only tests whose name matches the expression
----

A failure report shows the assertion, with the values pytest substituted in:

[source,console]
----
$ pytest -v
test_math_utils.py::test_add_returns_sum PASSED
test_math_utils.py::test_add_handles_negatives FAILED

================================== FAILURES ===================================
______________________________ test_add_handles_negatives ______________________________

E       assert 0 == 2
E        +  where 0 = add(-1, 1)

test_math_utils.py:6: AssertionError
========================== 1 failed, 1 passed in 0.01s ==========================
----

Full command-line usage is documented under
https://docs.pytest.org/en/stable/how-to/usage.html[How to invoke pytest].

== Fixtures

A *fixture* is a function decorated with `@pytest.fixture` that provides setup data or a resource to any test
that names it as a parameter. By default a fixture runs once per test (`scope="function"`); `scope="module"` or
`scope="session"` share one instance across many tests:

[source,python]
----
import pytest

@pytest.fixture
def sample_data():
    return {"id": 1, "name": "widget"}

def test_name_is_widget(sample_data):
    assert sample_data["name"] == "widget"
----

A fixture written with `yield` splits into setup (before the `yield`) and teardown (after it), which runs even
if the test fails:

[source,python]
----
import pytest

@pytest.fixture(scope="module")
def db_connection():
    conn = connect_to_test_db()   # setup
    yield conn
    conn.close()                  # teardown, always runs

def test_query_returns_rows(db_connection):
    assert db_connection.execute("SELECT 1").fetchone() is not None
----

Fixtures can depend on other fixtures simply by naming them as parameters -- pytest resolves the whole chain
before the test runs:

[source,python]
----
import pytest

@pytest.fixture
def db_connection():
    conn = connect_to_test_db()
    yield conn
    conn.close()

@pytest.fixture
def seeded_db(db_connection):
    db_connection.execute("INSERT INTO widgets VALUES (1, 'widget')")
    return db_connection

def test_seeded_row_exists(seeded_db):
    assert seeded_db.execute("SELECT * FROM widgets").fetchone() is not None
----

Fixtures, their scopes, and composition are covered in full under
https://docs.pytest.org/en/stable/how-to/fixtures.html[How to use fixtures].

== Parametrization and Markers

`@pytest.mark.parametrize` runs the same test body once per set of inputs, reported as separate test IDs:

[source,python]
----
import pytest

@pytest.mark.parametrize("a, b, expected", [
    (2, 3, 5),
    (-1, 1, 0),
    (0, 0, 0),
])
def test_add(a, b, expected):
    assert add(a, b) == expected
----

Markers also flag a test's status directly: `skip` never runs it, and `xfail` runs it but does not count a
failure against the suite (an unexpected pass is reported separately, as "XPASS"):

[source,python]
----
import pytest

@pytest.mark.skip(reason="not implemented yet")
def test_future_feature():
    assert compute_future() == 42

@pytest.mark.xfail(reason="2.675 has no exact binary representation, so round() gives 2.67")
def test_rounding():
    assert round(2.675, 2) == 2.68
----

Parametrization is documented under
https://docs.pytest.org/en/stable/how-to/parametrize.html[How to parametrize fixtures and test functions], and
`skip`/`xfail` under
https://docs.pytest.org/en/stable/how-to/skipping.html[How to use skip and xfail].

== Mocking

Mocking replaces a real dependency -- a network call, a database, the clock -- with a stand-in so a test can
run fast and deterministically. Neither the introductory books consulted for this section nor
https://docs.python.org/3/[the official Python docs] cover pytest itself; the Python docs only document the
standard library's own `unittest`/`unittest.mock`, which is what pytest projects typically reach for, so this
section is grounded in
https://docs.python.org/3/library/unittest.mock.html[the `unittest.mock` reference] and pytest's own
https://docs.pytest.org/en/stable/how-to/monkeypatch.html[monkeypatch] documentation instead.

=== `Mock`, `MagicMock`, and call assertions

A plain `Mock` records every call made to it; `MagicMock` additionally implements the "magic" dunder methods
(`+__len__+`, `+__iter__+`, and so on) so it can stand in for more than a plain attribute:

[source,python]
----
from unittest.mock import Mock

def send_welcome_email(mailer, address):
    mailer.send(address, subject="Welcome")

def test_send_welcome_email_calls_mailer():
    mailer = Mock()
    send_welcome_email(mailer, "user@example.com")
    mailer.send.assert_called_once_with("user@example.com", subject="Welcome")
    print(mailer.send.call_args)   # call('user@example.com', subject='Welcome')
----

`+assert_called_once_with(...)+` fails loudly if the call happened zero times, more than once, or with different
arguments; `.call_args` exposes the most recent call's positional and keyword arguments directly for custom
checks.

=== `patch()` as a decorator and a context manager

`patch()` temporarily replaces an attribute (typically an imported name) with a `MagicMock`, restoring the
original afterwards. As a decorator it injects the mock as a test argument; as a context manager it scopes the
replacement to a `with` block:

[source,python]
----
from unittest.mock import patch

# billing.py: `def charge(amount): return payment_gateway.charge(amount)`

@patch("billing.payment_gateway")
def test_charge_calls_gateway(mock_gateway):
    from billing import charge
    charge(1000)
    mock_gateway.charge.assert_called_once_with(1000)

def test_charge_calls_gateway_context_manager():
    with patch("billing.payment_gateway") as mock_gateway:
        from billing import charge
        charge(1000)
        mock_gateway.charge.assert_called_once_with(1000)
----

=== pytest's `monkeypatch` fixture

`monkeypatch` is pytest's own built-in fixture for patching attributes, dictionary items, and environment
variables for the duration of a single test -- it undoes every change automatically, with no `with` block or
decorator needed:

[source,python]
----
import os

import pytest

def get_api_url():
    return os.environ["API_URL"]

def test_get_api_url(monkeypatch):
    monkeypatch.setenv("API_URL", "https://staging.example.com")
    assert get_api_url() == "https://staging.example.com"

def test_get_api_url_missing(monkeypatch):
    monkeypatch.delenv("API_URL", raising=False)
    with pytest.raises(KeyError):
        get_api_url()
----

=== Mock vs. stub vs. spy

The three terms describe *how* a test double is used, not a different class in `unittest.mock`:

* A *mock* asserts on *how* it was called (`assert_called_once_with`) -- use it to verify an interaction
  happened, such as an email actually being sent.
* A *stub* just returns canned data (`+mock.return_value = ...+`) so the test can exercise the code around it --
  use it when you only need a dependency to answer with something, and don't care whether or how it was called.
* A *spy* wraps a *real* object and records calls without replacing its behaviour (`Mock(wraps=real_object)`) --
  use it to confirm a real method ran while still observing what was called.

Reach for a stub first when only a return value matters, a mock when the interaction itself is the thing under
test, and a spy when the real implementation must still run.

== Organizing a Test Suite

Mirror the source layout under a `tests/` directory, and factor fixtures shared across files into a
`conftest.py` -- pytest loads it automatically, with no import needed:

[source,text]
----
myproject/
├── src/
│   └── myproject/
│       ├── __init__.py
│       └── billing.py
└── tests/
    ├── conftest.py
    ├── test_billing.py
    └── test_math_utils.py
----

[source,python]
----
# tests/conftest.py
import pytest

@pytest.fixture
def sample_data():
    return {"id": 1, "name": "widget"}
----

Configure pytest itself in `pyproject.toml` (or an equivalent `pytest.ini`) rather than passing flags by hand
every time:

[source,text]
----
[tool.pytest.ini_options]
testpaths = ["tests"]
addopts = "-v --strict-markers"
markers = [
    "slow: marks tests as slow-running",
]
----

`conftest.py` sharing is covered alongside fixtures at
https://docs.pytest.org/en/stable/how-to/fixtures.html#scope-sharing-fixtures-across-classes-modules-packages-or-session[fixture
scope and sharing], and full configuration file options are under
https://docs.pytest.org/en/stable/reference/customize.html[Configuration].

== The pytest Test Lifecycle

For each test, pytest resolves its fixtures, runs their setup up to the `yield`, runs the test body, then runs
teardown in reverse order -- independently of whether the test passed:

[mermaid]
....
flowchart TD
    A[Discover test files: test_*.py, *_test.py] --> B[Collect test functions: test_*]
    B --> C[For each collected test]
    C --> D["Run fixture setup (up to yield)"]
    D --> E[Run the test function]
    E --> F["Run fixture teardown (after yield)"]
    F --> G{Outcome}
    G -->|assert held, no exception| H[Report: pass]
    G -->|AssertionError| I[Report: fail]
    G -->|other exception during setup/call| J[Report: error]
    H --> C
    I --> C
    J --> C
....

The full pytest documentation entry point, covering everything on this page in more depth, is
https://docs.pytest.org/en/stable/[docs.pytest.org].

== Fixture Resolution, Mock Targets, and Failure Output in Depth

The examples below belong to one small module, `bookshelf_mod.py`, that lends a book, e-mails the member and computes a
due date from "today". It has the two things that make code hard to test: a collaborator that does something irreversible
(the mailer) and a hidden dependency on the clock.

[source,python]
----
import datetime


class Mailer:
    def send(self, address, subject):
        raise RuntimeError("real mail server not available in tests")


def today():
    return datetime.date.today()


def due_date(days=14):
    return today() + datetime.timedelta(days=days)


def lend(member, title, mailer):
    mailer.send(member, f"Loan: {title}")
    return {"member": member, "title": title, "due": due_date()}
----

=== How pytest builds fixtures

A test asks for a fixture simply by naming it as a parameter. Before running the test, pytest builds a dependency graph from
the parameter names, instantiates each fixture (dependencies first) at the requested *scope* (`function` by default, then
`class`, `module`, `package`, `session`), passes the values in, and after the test runs the code after `yield` in reverse
order of setup. A fixture with a wider scope is created once and shared by every test in that scope, so it must not be
mutated by tests, which is why `shelf` below copies the module-scoped `database` instead of using it directly.

[mermaid]
....
flowchart TD
    T["test_second(shelf)"] --> A{"Fixture shelf in cache\nfor function scope?"}
    A -- No --> B["Resolve parameters of shelf:\ndatabase"]
    B --> C{"database cached\nfor module scope?"}
    C -- No --> D["Run database setup up to yield"]
    C -- Yes --> E["Reuse the value"]
    D --> E
    E --> F["Run shelf setup up to yield"]
    F --> G["Run the test body"]
    G --> H["Shelf teardown after yield,\nwhen the test ends"]
    H --> I["Database teardown at the end\nof the module"]
....

The test file records each setup, test and teardown in a list and finishes with a test that asserts the exact sequence, which
turns the lifecycle into something you can read and verify:

[source,python]
----
import pytest

events = []


@pytest.fixture(scope="module")
def database():
    events.append("db setup")
    yield {"Dune": 3}
    events.append("db teardown")


@pytest.fixture
def shelf(database):                          # fixtures can depend on other fixtures
    events.append("shelf setup")
    yield dict(database)
    events.append("shelf teardown")


def test_first(shelf):
    events.append("test_first")
    assert shelf["Dune"] == 3


def test_second(shelf):
    events.append("test_second")
    shelf["Dune"] -= 1                        # a fresh copy per test: this does not leak
    assert shelf["Dune"] == 2


def test_order_of_events():
    assert events == [
        "db setup", "shelf setup", "test_first", "shelf teardown",
        "shelf setup", "test_second", "shelf teardown",
    ]
----

Output (pytest 8.4.2):

[source,text]
----
collecting ... collected 3 items

test_lifecycle.py::test_first PASSED
test_lifecycle.py::test_second PASSED
test_lifecycle.py::test_order_of_events PASSED

============================== 3 passed in 0.01s ===============================
----

Teardown code after `yield` runs even when the test fails, which is why fixtures are the right home for cleanup, and an
exception *before* the `yield` marks the test as an error rather than a failure. Shared fixtures belong in `conftest.py`,
which pytest loads automatically for every test below that directory.

=== Mocking: patch where the name is used

`unittest.mock.patch("package.module.name")` replaces the attribute `name` *in that namespace*. The rule that avoids most
confusion is "patch where it is looked up, not where it is defined": if `bookshelf_mod` does `from clock import today` the
function is now also a name inside `bookshelf_mod`, and only patching `bookshelf_mod.today` affects it. A `Mock` accepts any call
and any attribute, so a typo in an assertion passes silently; `create_autospec` (or `+patch(..., autospec=True)+`) copies the
real signature and rejects calls the real object would reject, and `assert_called_once_with` checks the arguments. Use
`return_value` and `side_effect` (a value, an exception or an iterable of values) to script collaborators, and keep the
patched region as small as possible, with a context manager or the `monkeypatch` fixture that undoes itself.

[mermaid]
....
flowchart LR
    subgraph T["The test"]
        P["patch('bookshelf_mod.today')"]
    end
    subgraph M["bookshelf_mod namespace"]
        N["today name"]
        D["due_date calls today()"]
    end
    P -->|"rebinds"| N
    D -->|"looks up at call time"| N
    L["clock module: original today"] -.->|"not affected"| N
....

[source,python]
----
import datetime
from unittest import mock

import pytest

import bookshelf_mod
from bookshelf_mod import Mailer, lend


def test_lend_sends_mail_with_autospec():
    mailer = mock.create_autospec(Mailer, instance=True)
    loan = lend("ana@example.com", "Dune", mailer)
    mailer.send.assert_called_once_with("ana@example.com", "Loan: Dune")
    assert loan["title"] == "Dune"
    with pytest.raises(TypeError):
        mailer.send("only-one-argument")      # autospec enforces the real signature


def test_fixed_clock_with_monkeypatch(monkeypatch):
    class FixedDate(datetime.date):
        @classmethod
        def today(cls):
            return cls(2026, 3, 1)

    monkeypatch.setattr(bookshelf_mod.datetime, "date", FixedDate)
    assert bookshelf_mod.due_date(10) == datetime.date(2026, 3, 11)


def test_patch_the_function_not_the_library():
    with mock.patch("bookshelf_mod.today", return_value=datetime.date(2026, 1, 31)):
        assert bookshelf_mod.due_date() == datetime.date(2026, 2, 14)


@pytest.mark.parametrize(
    "days, expected",
    [(0, 0.0), (4, 1.0), pytest.param(-2, 0.0, id="early-return")],
)
def test_fee(days, expected):
    assert max(0.0, days * 0.25) == expected


def test_float_comparison_and_exception_message():
    assert 0.1 + 0.2 == pytest.approx(0.3)
    with pytest.raises(ValueError, match="positive"):
        raise ValueError("days must be positive")


def test_tmp_path_and_capsys(tmp_path, capsys):
    target = tmp_path / "shelf.txt"
    target.write_text("Dune\n")
    print("saved", target.name)
    assert capsys.readouterr().out == "saved shelf.txt\n"
----

Notice the test identifiers: `parametrize` generates one test per row, named from the values, and `+pytest.param(..., id=...)+`
gives a row a readable name that you can select with `-k early-return`. `pytest.approx` handles floating-point comparisons,
`+pytest.raises(..., match=...)+` checks the exception type and a regular expression on its message, and `tmp_path` and
`capsys` provide an isolated directory and captured output.

=== Reading a failure

pytest rewrites `assert` statements so a failure shows the values involved, not just "AssertionError". For collections it
shows the first differing index and a diff:

[source,python]
----
def test_titles_match():
    expected = ["Dune", "Emma", "Ulysses"]
    actual = ["Dune", "Emma", "Dubliners"]
    assert actual == expected
----

Output (pytest 8.4.2):

[source,text]
----
collecting ... collected 1 item

test_failing.py::test_titles_match FAILED

=================================== FAILURES ===================================
______________________________ test_titles_match _______________________________

    def test_titles_match():
        expected = ["Dune", "Emma", "Ulysses"]
        actual = ["Dune", "Emma", "Dubliners"]
>       assert actual == expected
E       AssertionError: assert ['Dune', 'Emma', 'Dubliners'] == ['Dune', 'Emma', 'Ulysses']
E         
E         At index 2 diff: 'Dubliners' != 'Ulysses'
E         
E         Full diff:
E           [
E               'Dune',
E               'Emma',...
E         
E         ...Full output truncated (3 lines hidden), use '-vv' to show

test_failing.py:4: AssertionError
=========================== short test summary info ============================
FAILED test_failing.py::test_titles_match - AssertionError: assert ['Dune', '...
============================== 1 failed in 0.01s ===============================

The `>` marks the failing line, lines starting with `E` are the explanation, and the summary line is what CI logs show.
Add `-vv` for the full diff, `-x` to stop at the first failure, `--lf` to rerun only the last failures and `--pdb` to open the
debugger at the failure (see xref:programming-languages/python/debugging-and-tooling.adoc[Debugging and Tooling]).

=== Design for testability

* pass collaborators in (the `mailer` parameter) instead of creating them inside the function, so a test can supply a fake
  without any patching;
* isolate the clock, randomness and the file system behind a small function or parameter, and patch that;
* test behaviour through the public interface; a test that mirrors the implementation breaks on every refactor;
* keep each test to one reason to fail, name it after the behaviour, and keep tests independent of order, since fixtures
  rebuild state per test;
* prefer fakes and real in-memory implementations over deep mock chains, and reserve mocks for boundaries (network, mail, time).

The examples that do not use pytest were run with CPython 3.14.8. The pytest sessions were run with pytest 8.4.2 on
Python 3.9.6 and have not been re-run on 3.14; the timing in the summary lines is normalised to 0.01s.
