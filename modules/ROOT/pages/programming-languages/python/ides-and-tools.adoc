== How the Pieces of a Python Editor Fit Together

Whatever you choose, a Python editing environment is the same few parts talking to one *interpreter*. The editor handles
text. A *language server* (Pylance or Pyright, Jedi, or the one built into PyCharm) analyses the code for completion, hover
documentation, go to definition and diagnostics. A *debug adapter* (such as `debugpy` for VS Code) drives the program
through Python's tracing hooks. Linters, formatters and test runners are ordinary command-line tools that the editor invokes.
All of them need to know *which* interpreter and which environment your project uses; that single setting is the
cause of most "the editor says the import is unresolved but it runs fine in the terminal" reports.

=== Telling the editor which interpreter to use

Select the interpreter that belongs to the project's virtual environment (in VS Code the *Python: Select Interpreter*
command, in PyCharm the project interpreter setting, in Spyder and Thonny the preferences). The language server then reads
that environment's `site-packages` to resolve imports and the debugger launches that executable. The script below prints
the facts an editor derives from an interpreter; running it with the interpreter you selected (not the one the system
`python` happens to be) is a quick way to confirm that the editor and the terminal agree.

[source,python]
----
"""Print what an editor needs to know about an interpreter (paths are masked for display)."""
import json
import sys

info = {
    "version": ".".join(map(str, sys.version_info[:3])),
    "in_virtualenv": sys.prefix != sys.base_prefix,
    "executable_name": sys.executable.rsplit("/", 1)[-1],
    "has_site_packages": any(p.endswith("site-packages") for p in sys.path),
    "module_search_path_entries": len(sys.path) > 2,
}
print(json.dumps(info, indent=2))
----

Output when run with a system interpreter:

[source,text]
----
{
  "version": "3.9.6",
  "in_virtualenv": false,
  "executable_name": "python3",
  "has_site_packages": true,
  "module_search_path_entries": true
}
----

Run inside an activated project environment, `in_virtualenv` is `true`. If the editor and the terminal disagree, the usual
fixes are to select the interpreter explicitly, to reopen the editor from an activated shell, or to restart the language
server after installing packages.

=== Choosing a tool

[mermaid]
....
flowchart TD
    A["What are you doing?"] --> B{"Learning the language?"}
    B -- Yes --> C["Thonny, or an editor with the Python extension"]
    B -- No --> D{"Exploring data\nor teaching with results?"}
    D -- Yes --> E["JupyterLab or Spyder"]
    D -- No --> F{"Large codebase with heavy\nrefactoring and test tooling?"}
    F -- Yes --> G["PyCharm"]
    F -- No --> H["VS Code with the Python extension"]
....

A few habits matter more than the choice of tool: keep one environment per project and let the editor discover it, enable the
formatter and linter on save so style is automatic (see
xref:programming-languages/python/lexical-structure-and-style.adoc[Lexical Structure and Style]), learn the debugger early
(see xref:programming-languages/python/debugging-and-tooling.adoc[Debugging and Tooling]), and use notebooks for exploration
but move reusable logic into modules so it can be tested and imported.

Every snippet in this section was run with Python 3.9.6 and the output shown is the real output.
