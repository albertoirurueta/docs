Python has four built-in numeric types -- `int`, `float`, `complex`, and `bool` -- plus two standard-library
types, `decimal.Decimal` and `fractions.Fraction`, for arithmetic that must avoid binary floating-point error.

== `int`, `float`, `complex`, and Numeric Literals

`int` has *arbitrary precision* -- it grows to fit the value, with no fixed bit width and no silent overflow.
`float` is a 64-bit https://docs.python.org/3/tutorial/floatingpoint.html[IEEE 754 double], which means most
decimal fractions have no exact binary representation. `complex` stores a pair of floats as `real` and
`imag`. All three are documented under
https://docs.python.org/3/library/stdtypes.html#numeric-types-int-float-complex[Numeric Types -- int, float,
complex]; the tutorial's https://docs.python.org/3/tutorial/introduction.html#numbers[Numbers] section is a
gentler introduction.

[source,python]
----
big = 2 ** 100                 # int: no overflow, arbitrarily large
pi_ish = 3.14159                # float
z = 2 + 3j                      # complex: real=2.0, imag=3.0

million = 1_000_000             # underscores as visual separators
hex_val = 0x1F                  # 31, hexadecimal
oct_val = 0o17                  # 15, octal
bin_val = 0b1010                # 10, binary
----

[source,console]
----
>>> 2 ** 100
1267650600228229401496703205376
>>> 0.1 + 0.2
0.30000000000000004
>>> (2 + 3j).imag
3.0
----

That last result is not a bug: `0.1` and `0.2` cannot be represented exactly in binary, so their sum carries a
tiny error. See https://docs.python.org/3/tutorial/floatingpoint.html[Floating Point Arithmetic: Issues and
Limitations] for why, and the `decimal`/`fractions` section below for exact alternatives.

== Operators

Arithmetic operators are `pass:c[+]`, `-`, `+*+`, `/`, `//`, `%`, and `+**+`. `/` is *true division* and always returns a
`float`; `//` is *floor division* and rounds toward negative infinity; `%` is the matching modulo; `+**+` is
exponentiation.

[source,python]
----
7 / 2        # 3.5   (true division: always float)
7 // 2       # 3     (floor division)
-7 // 2      # -4    (rounds toward -infinity, not toward zero)
7 % 2        # 1
-7 % 2       # 1     (result takes the sign of the divisor)
2 ** 10      # 1024
----

Comparisons *chain*: `a < b < c` means `a < b and b < c`, evaluating `b` only once:

[source,python]
----
x = 5
print(0 < x < 10)     # True
print(10 < x < 20)    # False
----

Augmented assignment combines an operator with `=`:

[source,python]
----
total = 10
total += 5    # 15
total -= 3    # 12
total *= 2    # 24
total //= 5   # 4
total **= 2   # 16
----

== Exact Arithmetic: `decimal.Decimal` and `fractions.Fraction`

`decimal.Decimal` represents numbers in base 10, avoiding the binary rounding error shown above -- useful for
money and other values with an exact decimal representation. See
https://docs.python.org/3/library/decimal.html[the `decimal` module].

[source,python]
----
from decimal import Decimal

price = Decimal("0.1") + Decimal("0.2")
print(price)             # 0.3  (exact)
----

`fractions.Fraction` keeps an exact numerator/denominator pair, so ratios never lose precision either. See
https://docs.python.org/3/library/fractions.html[the `fractions` module].

[source,python]
----
from fractions import Fraction

f = Fraction(1, 3) + Fraction(1, 6)
print(f)                 # 1/2
print(float(f))          # 0.5
----

`bool` is an `int` subclass: `True` and `False` behave as `1` and `0` in arithmetic.

[source,python]
----
print(True + True)       # 2
print(isinstance(True, int))   # True
print(True * 10)         # 10
----

== Built-in Numeric Tools

`abs()` returns the magnitude, `round()` rounds to the given number of decimal places, and `pow()` is
exponentiation with an optional modulus. Full reference:
https://docs.python.org/3/library/stdtypes.html#numeric-types-int-float-complex[Numeric Types -- int, float,
complex].

[source,python]
----
abs(-7)          # 7
abs(-3.5)        # 3.5
round(2.5)       # 2   (banker's rounding: ties go to the nearest even int)
round(3.5)       # 4
round(3.14159, 2)  # 3.14
pow(2, 10)       # 1024
pow(2, 10, 1000) # 24  (2 ** 10 % 1000, computed efficiently)
----

The tie-breaking rule of `round()` -- *round half to even*, or "banker's rounding" -- avoids the statistical bias
of always rounding `.5` up; `round(0.5)` is `0`, and `round(1.5)` is `2`.

The `math` module supplies everything beyond these basics -- square roots, trigonometry, logarithms,
constants like `math.pi`:

[source,python]
----
import math

math.sqrt(2)      # 1.4142135623730951
math.floor(3.7)   # 3
math.pi           # 3.141592653589793
----

`math` (plus `random` and `statistics`) is covered in depth in xref:programming-languages/python/standard-library-tour.adoc[].

== How Python Represents Numbers

Python's numbers form a *numeric tower* defined by the abstract base classes in the
https://docs.python.org/3/library/numbers.html[`numbers`] module. `bool` is a subclass of `int` (so `pass:c[True + True == 2]`),
`int` registers as `Integral`, `float` as `Real`, `complex` as `Complex`, and `fractions.Fraction` as `Rational`.
`decimal.Decimal` is deliberately *not* part of the tower: mixing it with `float` raises `TypeError` rather than silently
losing exactness.

[mermaid]
....
classDiagram
    Number <|-- Complex
    Complex <|-- Real
    Real <|-- Rational
    Rational <|-- Integral
    Integral : int
    Real : float
    Rational : Fraction
    Complex : complex
    class Decimal
....

Operations between tower members promote to the "wider" type (`pass:c[int + float]` gives `float`, `pass:c[float + complex]` gives
`complex`), which is why a long chain of integer arithmetic that touches one float ends up in binary floating point.

=== Integers: arbitrary precision

A Python `int` is not a machine word. It is a variable-length sequence of 30-bit "digits" in CPython, so it never
overflows; it only gets slower and bigger. That removes a whole class of bugs from other languages (silent wrap-around),
but it also means `int` arithmetic is not constant time for huge values, and converting a huge integer to a decimal string
is quadratic in its length. Floor division and modulo follow the rule `pass:c[a == (a // b) * b + a % b]`, with the quotient
rounded toward negative infinity, so the remainder takes the sign of the divisor, unlike C or Java.

[source,python]
----
# int has arbitrary precision: it grows as needed
big = 2 ** 200
print(big)
print(big.bit_length(), len(str(big)))

# floor division and modulo round toward negative infinity
for a, b in [(7, 2), (-7, 2), (7, -2), (-7, -2)]:
    q, r = divmod(a, b)
    print(f"{a:>2} // {b:>2} = {q:>2}   {a:>2} % {b:>2} = {r:>2}   check: {q * b + r}")

# round() uses banker's rounding (round half to even) and returns an int when ndigits is omitted
print([round(x) for x in (0.5, 1.5, 2.5, 3.5)])
print(round(2.675, 2))                 # 2.67: the stored double is slightly below 2.675

# int() truncates toward zero, math.floor goes down
import math
print(int(-2.7), math.floor(-2.7), math.ceil(-2.7))

# conversions between bases
print(bin(37), oct(37), hex(37), int("100101", 2), int("ff", 16))
print((1234).to_bytes(2, "big"), int.from_bytes(b"\x04\xd2", "big"))
----

Output:

----

201 61
 7 //  2 =  3    7 %  2 =  1   check: 7
-7 //  2 = -4   -7 %  2 =  1   check: -7
 7 // -2 = -4    7 % -2 = -1   check: 7
-7 // -2 =  3   -7 % -2 = -1   check: -7

Two details in that output surprise newcomers: `round()` rounds exact halves to the nearest even number (so `0.5` and
`2.5` round down), and `round(2.675, 2)` gives `2.67` because the double nearest to 2.675 is slightly below it. The
second point is not a bug in `round`; it is the next topic.

=== Floats: IEEE 754 binary doubles

A `float` is a 64-bit IEEE 754 double: 1 sign bit, 11 exponent bits and 52 fraction bits, giving about 15 to 17
significant decimal digits. Most decimal fractions, such as 0.1, have no finite binary expansion, so the stored value is
the nearest representable double. The consequences are the same in every language that uses doubles, and Python offers
tools to see and manage them:

[source,python]
----
import math
from decimal import Decimal
from fractions import Fraction

print(0.1 + 0.2)                       # 0.30000000000000004
print((0.1).as_integer_ratio())        # the exact fraction a double really stores
print(Decimal(0.1))                    # the exact decimal expansion of that double
print((0.5).hex(), (0.1).hex())        # sign, 52-bit fraction and exponent in hex

print(0.1 + 0.2 == 0.3)                # False
print(math.isclose(0.1 + 0.2, 0.3))    # True: relative tolerance 1e-09 by default

prices = [0.10] * 10
print(sum(prices), math.fsum(prices))  # sum compensates since 3.12; fsum is exactly rounded
print(Fraction(1, 10) * 10 == 1)       # True: exact rational arithmetic

print(float("inf") > 10**308, math.isnan(float("nan")), float("nan") == float("nan"))
----

Output:

[source,text]
----

(3602879701896397, 36028797018963968)
0.1000000000000000055511151231257827021181583404541015625
0x1.0000000000000p-1 0x1.999999999999ap-4
False
True
1.0 1.0
True

Guidelines that follow from this:

* never compare floats with `==` after arithmetic; use `math.isclose` (relative tolerance) or `+abs(a - b) <= eps+` with a
  tolerance that fits the magnitude of the numbers;
* since Python 3.12 `sum` of floats uses compensated (Neumaier) summation, so it prints `1.0` above where older versions
  printed `0.9999999999999999`; `math.fsum` is still the exactly rounded choice when the last digits matter;
* `nan` is unequal to everything including itself, so test with `math.isnan`, and remember that `nan` in a `sorted()`
  call or a `max()` call gives unpredictable placement;
* money and any quantity with a legal rounding rule belong in `Decimal` or in integer cents, never in `float`.

=== Decimal contexts and money

`Decimal` carries its precision in a *context* (28 significant digits by default) that you can change globally or, safer,
locally with `localcontext()`. Always construct a `Decimal` from a string or an integer: `Decimal(0.1)` faithfully
captures the binary error of the float. Round to a currency's minor unit with `quantize` and an explicit rounding mode,
because the default, `ROUND_HALF_EVEN`, is not what most invoices use.

[source,python]
----
from decimal import Decimal, ROUND_HALF_UP, getcontext, localcontext

print(Decimal("0.10") + Decimal("0.20"))        # 0.30
print(Decimal(0.1) == Decimal("0.1"))           # False: build from strings, not floats

price = Decimal("19.99")
quantity = 3
tax_rate = Decimal("0.0825")
subtotal = price * quantity
total = (subtotal * (1 + tax_rate)).quantize(Decimal("0.01"), rounding=ROUND_HALF_UP)
print(subtotal, total)

print(getcontext().prec)                        # default precision: 28 significant digits
with localcontext() as ctx:
    ctx.prec = 5
    print(Decimal(1) / Decimal(7))              # 0.14286
print(Decimal(1) / Decimal(7))
----

Output:

[source,text]
----

False
59.97 64.92

0.14286
0.1428571428571428571428571429
----

=== Choosing a numeric type

[cols="1,2,2",options="header"]
|===
|Need |Use |Why

|Counting, indexing, identifiers |`int` |exact, unbounded
|Measurements, scientific code |`float` |fast, hardware supported, error is bounded and relative
|Money, tax, anything audited |`Decimal` (or integer minor units) |exact decimal fractions, controlled rounding
|Ratios that must stay exact |`Fraction` |exact, but denominators can grow
|Large arrays of numbers |NumPy arrays (see the xref:data-science/index.adoc[Data Science] section) |typed storage, vectorised
|===
