Python is an interpreted, dynamically typed language. This page installs it, shows the two ways to run code
-- typed one line at a time or saved to a file -- and traces what actually happens between saving a `.py`
file and seeing output.

== Installing Python

Download an installer for your platform from https://www.python.org/downloads/[python.org]. On Windows, tick
*Add python.exe to PATH* on the first installer screen -- it is not checked by default. On macOS, prefer the
python.org installer or Homebrew over the system Python that ships with the OS. On Linux, most distributions
package Python through their own package manager:

[source,bash]
----
# Windows: installer from python.org, or
winget install Python.Python.3

# macOS: installer from python.org, or
brew install python3

# Debian / Ubuntu
sudo apt update && sudo apt install python3

# Fedora
sudo dnf install python3
----

Check what got installed. On Windows the launcher is usually `python`; on macOS and Linux, `python3`
(a bare `python` may not exist, or may point at a Python 2 left over from the OS):

[source,console]
----
$ python3 --version
Python 3.13.0

$ python3 -m pip --version
pip 24.2 from /usr/lib/python3.13/site-packages/pip (python 3.13)
----

If the command is not found, the installer did not add Python to your `PATH` -- re-run the installer and
enable that option, or add the install directory manually.

== Script Mode vs. Interactive Mode

Running `python3` with no file starts the *interactive mode* (the *REPL* -- Read-Eval-Print Loop): each line
is read, evaluated, and its result printed immediately, which makes it the fastest way to try an expression:

[source,console]
----
$ python3
Python 3.13.0 (main, Oct  7 2024, 15:38:29)
>>> 2 + 2
4
>>> name = "Ada"
>>> f"Hello, {name}!"
'Hello, Ada!'
>>> exit()
----

*Script mode* instead runs a whole file saved on disk. Save this as `hello.py`:

[source,python]
----
print("Hello, world!")
----

and run it by passing the filename to the interpreter:

[source,console]
----
$ python3 hello.py
Hello, world!
----

Full command-line usage, including `-c` (run a string) and `-m` (run a module as a script), is documented
under https://docs.python.org/3/tutorial/interpreter.html[Using the Python Interpreter].

=== The shebang line

On Unix-like systems (macOS, Linux), a script can be made directly executable by giving it a *shebang* as its
first line and marking the file executable:

[source,python]
----
#!/usr/bin/env python3
print("Hello, world!")
----

[source,bash]
----
chmod +x hello.py
./hello.py
----

`+#!/usr/bin/env python3+` looks up `python3` on the current `PATH` rather than hardcoding an absolute
interpreter path, so the same script works across machines with Python installed in different locations.
Windows has no shebang mechanism of its own, but the `py` launcher installed alongside python.org's Windows
build reads the same line to pick an interpreter version.

== Editors and IDEs

Any text editor can write a `.py` file, but three tools cover most Python work:

* *https://code.visualstudio.com/[VS Code]* with the official Python extension -- linting, debugging, and
  IntelliSense in a general-purpose editor.
* *https://www.jetbrains.com/pycharm/[PyCharm]* -- a Python-specific IDE with deeper refactoring and
  debugging tools built in.
* *https://docs.python.org/3/library/idle.html[IDLE]* -- the simple editor and REPL that ships with every
  python.org install; no separate download needed.

For a fuller list of IDEs, editors and notebook tools, see xref:programming-languages/python/ides-and-tools.adoc[Python IDEs & Tools].

Pick whichever is already installed to write `hello_world.py`:

[source,python]
----
def main() -> None:
    print("Hello, world!")


if __name__ == "__main__":
    main()
----

`+if __name__ == "__main__":+` guards code that should run only when the file is executed directly, not when
it is imported by another module -- see
xref:programming-languages/python/lexical-structure-and-style.adoc[] for module structure.

== The Execution Model: Source to Bytecode to the PVM

`python3 hello.py` is not a single step. CPython (the reference implementation) first *compiles* the source
to an intermediate form called *bytecode*, then a loop called the *Python Virtual Machine (PVM)* executes
that bytecode instruction by instruction:

[mermaid]
....
flowchart LR
    A["hello.py<br/>(source)"] -->|compile| B["bytecode<br/>(.pyc)"]
    B -->|execute| C["Python Virtual Machine<br/>(PVM)"]
    C --> D["program output"]
    B -.->|cached under| E["__pycache__/hello.cpython-313.pyc"]
....

For a script run directly, this compile step happens in memory on every run. For *imported* modules, CPython
caches the compiled bytecode on disk in a `+__pycache__+` directory next to the source file, named after the
interpreter version (e.g. `hello.cpython-313.pyc`), so the next import skips recompilation as long as the
source file's modification time has not changed:

[source,console]
----
$ python3 -c "import hello"
$ ls __pycache__
hello.cpython-313.pyc
----

This compile-then-interpret design is why Python is described as *interpreted* even though a real
compilation pass happens -- there is no separate step producing a native executable, and the same `.pyc`
bytecode is not portable across incompatible interpreter versions. Background on the interpreter and why
Python favours this tight edit-run loop is in
https://docs.python.org/3/tutorial/appetite.html[Whetting Your Appetite] and
https://docs.python.org/3/tutorial/interpreter.html[Using the Python Interpreter]; installers for every
platform are at https://www.python.org/downloads/[python.org/downloads].

== What Happens When You Run a Python File

CPython (the reference implementation) is a *compiler plus a virtual machine*. Running a file does not interpret the text
line by line: the source is turned into a code object once, and the virtual machine executes that. Knowing the stages
explains where each kind of error comes from and why the second run of a module is faster.

[mermaid]
....
flowchart LR
    A["Source text\nprice * 3 + 1"] --> B["Tokenizer\nNAME, OP, NUMBER"]
    B --> C["Parser\nabstract syntax tree"]
    C --> D["Compiler\ncode object: bytecode,\nconstants, names"]
    D --> E["Python virtual machine\nevaluation loop"]
    D -.->|"imported modules only"| F["__pycache__/name.cpython-XY.pyc"]
    F -.->|"next import skips A to D"| E
....

A syntax error is raised by the tokenizer or parser *before any line runs*, so a typo at the bottom of a file prevents the
whole file from starting, whereas a `NameError` or `TypeError` is raised by the virtual machine at the moment the faulty
line executes. The sample takes the same two-line program through every stage using the standard-library modules that
expose them:

[source,python]
----
import ast
import importlib.util
import io
import py_compile
import tempfile
import tokenize
from pathlib import Path

source = "total = price * 3 + 1\nprint(total)\n"

# 1. tokenizer: text -> tokens
tokens = [(tokenize.tok_name[t.type], t.string) for t in tokenize.generate_tokens(io.StringIO(source).readline)]
print(tokens[:6])

# 2. parser: tokens -> abstract syntax tree
tree = ast.parse(source)
print([type(n).__name__ for n in ast.walk(tree)][:7])

# 3. compiler: AST -> code object (bytecode plus constants and names)
code = compile(tree, "<demo>", "exec")
print(code.co_names, code.co_consts, type(code.co_code).__name__)

# 4. the virtual machine executes the code object in a namespace
namespace = {"price": 4}
exec(code, namespace)
print(namespace["total"])

# bytecode is cached in __pycache__ so the next import skips steps 1 to 3
folder = Path(tempfile.mkdtemp())
module = folder / "bookshelf.py"
module.write_text("VALUE = 1\n")
cached = Path(py_compile.compile(str(module)))
print(cached.parent.name, cached.name.startswith("bookshelf.cpython-"), cached.suffix)
print(cached.read_bytes()[:4] == importlib.util.MAGIC_NUMBER)     # the file starts with a version stamp
print(Path(importlib.util.cache_from_source(str(module))) == cached)
----

Output:

[source,text]
----
[('NAME', 'total'), ('OP', '='), ('NAME', 'price'), ('OP', '*'), ('NUMBER', '3'), ('OP', '+')]
['Module', 'Assign', 'Expr', 'Name', 'BinOp', 'Call', 'Store']
('price', 'total', 'print') (3, None) bytes
13
13
__pycache__ True .pyc
True
True
----

Details that follow from this:

* the `.pyc` cache holds *imported* modules only; the script you run directly is compiled in memory each time, so keep
  the top-level script thin and put logic in modules;
* a `.pyc` file begins with a magic number tied to the interpreter version, which is why each version writes its own file
  name (`cpython-314`) and why you must never commit `+__pycache__+` directories;
* the bytecode is an implementation detail that changes between versions (`dis.dis` shows it), so program logic must not
  depend on it; other implementations such as PyPy compile to different internal forms;
* newer releases add a specialising adaptive interpreter and an experimental JIT, which change speed but not behaviour.

=== Ways to start Python and how arguments arrive

`python script.py args` runs a file as `+__main__+` with `sys.argv` set to the script name followed by the arguments;
`python -m package.module` runs a module found through `sys.path` (and is the correct way to run a module that uses relative
imports, or tools such as `venv`, `pip` and `json.tool`); `python -c "code"` runs a string; and plain `python` starts the
interactive REPL. The flag `-i` runs a script and then drops into the REPL with its variables, which is a quick way to
explore state after a failure.

[source,python]
----
import subprocess
import sys
import tempfile
from pathlib import Path

script = Path(tempfile.mkdtemp()) / "args.py"
script.write_text(
    "import sys\n"
    "print(__name__, sys.argv[1:], sys.flags.interactive)\n"
)
run = lambda *a: subprocess.run([sys.executable, *a], capture_output=True, text=True).stdout.strip()

print(run(str(script), "dune", "--years", "3"))          # script mode: __name__ is __main__
print(run("-c", "import sys; print(sys.argv)", "x"))      # -c: argv[0] is the string -c
print(run("-m", "json.tool", "--help").splitlines()[0][:30])   # -m runs a module found on sys.path
----

Output:

[source,text]
----
__main__ ['dune', '--years', '3'] 0
['-c', 'x']
usage: python3.14 -m json.tool
----

=== Checking which Python you are really using

The most common setup problem is running a different interpreter than you installed packages for. Check
`python -c "import sys; print(sys.executable, sys.version)"`, prefer `python -m pip` so that `pip` and `python` agree, and
create one virtual environment per project (see
xref:programming-languages/python/virtual-environments-and-packaging.adoc[Virtual Environments and Packaging]). On Windows the `py` launcher
selects a version (`py -3.12`), and on macOS and Linux versioned commands such as `python3.12` coexist with the system
Python, which you should not modify.

Every snippet in this section was run with CPython 3.14.8 and the output shown is the real output.
