Every `for` loop in Python -- and every comprehension -- runs on top of the same small protocol: get an
*iterator* from an *iterable*, then call it repeatedly until it signals it is done. This page walks through
that protocol, the two constructs built directly on it (generator functions and generator expressions), and
comprehensions as sugar over the same machinery.

== The Iterator Protocol

An *iterable* is any object with an `+__iter__+` method returning an *iterator*; an iterator is any object with
both `+__iter__+` (returning itself) and `+__next__+`, which returns the next value or raises `StopIteration` when
exhausted. This is documented in the tutorial's
https://docs.python.org/3/tutorial/classes.html#iterators[Iterators] section and, at the data-model level, in
https://docs.python.org/3/library/stdtypes.html#iterator-types[Iterator Types].

A `for` loop is shorthand for calling https://docs.python.org/3/library/functions.html#iter[`iter()`] once and
https://docs.python.org/3/library/functions.html#next[`next()`] repeatedly, catching
https://docs.python.org/3/library/exceptions.html#StopIteration[`StopIteration`] to know when to stop:

[source,python]
----
numbers = [10, 20, 30]

iterator = iter(numbers)     # get an iterator from the list (an iterable)
print(next(iterator))        # 10
print(next(iterator))        # 20
print(next(iterator))        # 30
print(next(iterator))        # raises StopIteration
----

`next()` accepts an optional default, returned instead of raising:

[source,python]
----
iterator = iter([1, 2])
next(iterator)                # 1
next(iterator)                # 2
next(iterator, "done")        # 'done' -- no StopIteration raised
----

Writing a class that implements the protocol directly makes the two methods explicit. `+__iter__+` returns
`self` (the object is its own iterator), and `+__next__+` raises `StopIteration` once there is nothing left:

[source,python]
----
class Countdown:
    def __init__(self, start):
        self.current = start

    def __iter__(self):
        return self

    def __next__(self):
        if self.current <= 0:
            raise StopIteration
        self.current -= 1
        return self.current + 1

for value in Countdown(3):
    print(value)          # 3, 2, 1
----

Because `Countdown` implements `+__iter__+`, it works anywhere an iterable is expected -- `for` loops,
`+list(...)+`, `+sum(...)+`, and comprehensions all drive it through the exact same `iter()`/`next()` calls shown
above.

== Generator Functions and Generator Expressions

Writing a full iterator class is verbose for anything beyond a toy example. A *generator function* -- any
function containing `yield` -- lets Python build the iterator for you: calling it returns a generator object
without running any of the function body, and each `next()` call resumes execution up to the next `yield`.
See the tutorial's https://docs.python.org/3/tutorial/classes.html#generators[Generators] section and the
formal https://docs.python.org/3/reference/expressions.html#yield-expressions[yield expressions] reference.

[source,python]
----
def countdown(start):
    current = start
    while current > 0:
        yield current
        current -= 1

gen = countdown(3)      # no code has run yet
print(next(gen))        # 3 -- runs up to the first `yield`
print(next(gen))        # 2 -- resumes after `yield`, runs to the next one
print(next(gen))        # 1
print(next(gen))        # raises StopIteration -- the function returned
----

`countdown` above replaces the entire `Countdown` class from the previous section in four lines, and
`+__iter__+`/`+__next__+`/`StopIteration` are all generated automatically.

A *generator expression* is the same idea written inline, with the comprehension syntax but parentheses
instead of brackets. It is documented under
https://docs.python.org/3/reference/expressions.html#generator-expressions[Generator expressions]:

[source,python]
----
squares = (n ** 2 for n in range(5))
print(next(squares))    # 0
print(next(squares))    # 1
print(list(squares))    # [4, 9, 16] -- the rest, consuming the generator
----

=== Why Generators Are Memory-Efficient

A list comprehension builds the *entire* list in memory before you use any of it. A generator produces one
value at a time, on demand -- *lazy evaluation* -- so it never holds more than the current value in memory,
no matter how large the sequence is:

[source,python]
----
# Materializes 10 million ints in a list before summing -- a large, real allocation.
total = sum([n for n in range(10_000_000)])

# Produces one int at a time and discards it after summing -- effectively O(1) memory.
total = sum(n for n in range(10_000_000))
----

Both compute the same `total`, but only the generator expression scales to an unbounded or very large source
(such as lines streamed from a file) without exhausting memory.

== Comprehensions as Sugar over Iteration

List, set, and dict comprehensions all desugar to the same `iter()`/`next()` loop described above --
documented together with `for` loops in the tutorial's
https://docs.python.org/3/tutorial/datastructures.html#list-comprehensions[List Comprehensions] section and,
formally, under
https://docs.python.org/3/reference/expressions.html#displays-for-lists-sets-and-dictionaries[Displays for
lists, sets and dictionaries]:

[source,python]
----
squares = [n ** 2 for n in range(5)]        # list:  [0, 1, 4, 9, 16]
uniques = {n % 3 for n in range(6)}         # set:   {0, 1, 2}
by_n = {n: n ** 2 for n in range(5)}        # dict:  {0: 0, 1: 1, 2: 4, 3: 9, 4: 16}
----

Conceptually, `squares` above runs exactly like this explicit loop -- the comprehension is syntactic sugar
over the same iteration:

[source,python]
----
squares = []
for n in range(5):
    squares.append(n ** 2)
----

=== Nested Comprehensions

A comprehension can iterate over more than one `for` clause, evaluated left to right like nested loops --
useful for flattening or for a Cartesian product:

[source,python]
----
matrix = [[1, 2, 3], [4, 5, 6]]
flattened = [value for row in matrix for value in row]
# [1, 2, 3, 4, 5, 6]

pairs = [(x, y) for x in range(3) for y in range(2) if x != y]
# [(0, 0), (0, 1), (1, 1), (2, 0), (2, 1)]
----

A comprehension nested *inside* another (one comprehension as the expression of the outer one) builds a
list of lists instead of flattening them:

[source,python]
----
matrix = [[1, 2, 3], [4, 5, 6]]
transposed = [[row[i] for row in matrix] for i in range(3)]
# [[1, 4], [2, 5], [3, 6]]
----

=== Comprehension vs. Generator Expression

Prefer a *generator expression* over a list comprehension whenever the result will only be consumed once,
in order -- passed straight into `sum()`, `any()`, `all()`, `max()`, or a `for` loop -- since nothing needs
the intermediate list to exist:

[source,python]
----
lines = ["10", "20", "thirty", "40"]

# List comprehension: builds an intermediate list just to throw it away after summing.
total = sum([int(x) for x in lines if x.isdigit()])

# Generator expression: same result, no intermediate list ever materialized.
total = sum(int(x) for x in lines if x.isdigit())
----

Reach for the list (or set/dict) comprehension instead when you need the result more than once, need its
length or indexing, or need it to be a real `list`/`set`/`dict` for an API that requires one.

== Iteration Internals: State Machines and Lazy Pipelines

An *iterable* is anything `iter()` accepts (it defines `+__iter__+`, or the older `+__getitem__+` protocol with integer
indexes). An *iterator* is the object that does the walking: it defines `+__next__+`, returns the next value, raises
`StopIteration` when finished, and its own `+__iter__+` returns itself. The distinction matters in practice: iterating an
iterable several times works because each loop gets a fresh iterator, while iterating an iterator a second time yields
nothing because its state is already used up.

[mermaid]
....
stateDiagram-v2
    [*] --> Created: call generator function
    Created --> Suspended: next() runs to first yield
    Suspended --> Suspended: next() or send() resumes to next yield
    Suspended --> Closed: return, StopIteration, or close()
    Suspended --> Closed: exception propagates out
    Created --> Closed: close() before start
    Closed --> [*]
....

=== Iterator, iterable, and generator states

A generator function does not run when called; it returns a generator object in state `GEN_CREATED`. Each `next()`
resumes the frame until the next `yield`, leaving it `GEN_SUSPENDED` with all local variables intact, and the frame ends in
`GEN_CLOSED` after `return` (which becomes `StopIteration`), an exception or `close()`. The `inspect` module exposes the
state for debugging.

[source,python]
----
import inspect


class Countdown:
    """Iterator: remembers its own position."""
    def __init__(self, start):
        self.n = start

    def __iter__(self):
        return self

    def __next__(self):
        if self.n <= 0:
            raise StopIteration
        self.n -= 1
        return self.n + 1


class Shelf:
    """Iterable: hands out a fresh iterator each time."""
    def __init__(self, titles):
        self.titles = titles

    def __iter__(self):
        return iter(self.titles)


c = Countdown(3)
print(list(c), list(c))             # an iterator is single-use
s = Shelf(["Dune", "Emma"])
print(list(s), list(s))             # an iterable can be walked again

def titles_gen():
    yield "Dune"
    yield "Emma"

g = titles_gen()
print(inspect.getgeneratorstate(g))   # GEN_CREATED
print(next(g), inspect.getgeneratorstate(g))
print(next(g))
try:
    next(g)
except StopIteration:
    print(inspect.getgeneratorstate(g))   # GEN_CLOSED
print(iter(g) is g, iter([1]) is not iter([1]))
----

Output:

[source,text]
----
[3, 2, 1] []
['Dune', 'Emma'] ['Dune', 'Emma']
GEN_CREATED
Dune GEN_SUSPENDED
Emma
GEN_CLOSED
True True
----

A class-based iterator and a generator solve the same problem; the generator is shorter because Python keeps the
position in the suspended frame instead of in attributes. Make a *container* an iterable (return a fresh iterator from
`+__iter__+`, often simply `iter(self.items)` or a generator method), and avoid making a container its own iterator.

=== Generators as coroutines: `send`, `close`, and `yield from`

A `yield` is also an expression. `g.send(value)` resumes the generator and makes `yield` evaluate to `value`; the first
call must be `next(g)` (or `send(None)`) to run to the first `yield`. `g.close()` raises `GeneratorExit` at the paused
`yield`, so `try`/`finally` blocks in a generator do run on early exit. `yield from sub` delegates to a sub-generator,
forwarding `send` and exceptions, and the sub-generator's `return` value becomes the value of the `yield from`
expression. These mechanics are the ancestor of `async`/`await`: see
xref:programming-languages/python/concurrency-and-async.adoc[Concurrency and Async].

[source,python]
----
import inspect


def running_total():
    """A coroutine-style generator: send() pushes values in."""
    total = 0
    try:
        while True:
            amount = yield total
            total += amount
    except GeneratorExit:
        print("closing with", total)
        raise
    finally:
        print("cleanup")


g = running_total()
print(next(g))                 # prime: run to the first yield
print(g.send(10), g.send(5))
g.close()                      # raises GeneratorExit at the paused yield
print(inspect.getgeneratorstate(g))


def inner():
    got = yield "a"
    yield f"inner got {got}"
    return "inner done"

def outer():
    result = yield from inner()    # delegates; its return value becomes the expression value
    yield f"outer saw {result}"

o = outer()
print(next(o), o.send("hello"), next(o))

def lines_with_numbers(lines):
    return ((i, ln.upper()) for i, ln in enumerate(lines, 1))
print(list(lines_with_numbers(["a", "b"])))
----

Output:

[source,text]
----
0
10 15
closing with 15
cleanup
GEN_CLOSED
a inner got hello outer saw inner done
[(1, 'A'), (2, 'B')]
----

=== Lazy pipelines and memory

Generators compose: each stage pulls one item at a time from the previous stage, so a million-line file can be filtered,
transformed and summarised in constant memory, and a stage that is never pulled never runs. The list in the sample is
more than a hundred times the size of the equivalent generator object, which stores only the frame and the loop state.
The price is single-pass semantics: a generator cannot be rewound, `len()` does not work, and `sum(big_gen)` called a
second time returns zero. `itertools` supplies the building blocks (`islice`, `chain`, `takewhile`, `groupby`, `count`),
and `groupby` only groups *adjacent* equal keys, so sort first when needed.

[source,python]
----
import itertools, sys

def read_titles(lines):
    for line in lines:
        yield line.strip()

def non_empty(items):
    for item in items:
        if item:
            yield item

def title_case(items):
    for item in items:
        yield item.title()

raw = ["dune \n", "\n", "  emma\n", "ulysses\n"]
pipeline = title_case(non_empty(read_titles(raw)))     # nothing runs yet
print(type(pipeline).__name__)
print(list(itertools.islice(pipeline, 2)))             # pull only two items
print(next(pipeline))

big_list = [n * n for n in range(100_000)]
big_gen = (n * n for n in range(100_000))
print(sys.getsizeof(big_list) > 100 * sys.getsizeof(big_gen))
print(sum(big_gen), sum(big_gen))                      # exhausted the second time
print(list(itertools.chain([1], (2, 3))), list(itertools.takewhile(lambda n: n < 3, itertools.count())))
print([(k, len(list(g))) for k, g in itertools.groupby("aabccc")])
----

Output:

[source,text]
----
generator
['Dune', 'Emma']
Ulysses
True
333328333350000 0
[1, 2, 3] [0, 1, 2]
[('a', 2), ('b', 1), ('c', 3)]
----

=== When to use which

* a list comprehension when you need the whole result as a list, or will iterate it more than once;
* a generator expression when the result is consumed once (`sum`, `any`, `all`, `join`, `max`);
* a generator function when the logic needs several statements, state across items, or `try`/`finally`;
* a class-based iterator when the object also needs other methods and attributes of its own.
