= Operator Overloading
:description: How Python's dunder (double-underscore) methods let a custom class support repr/str, rich comparisons, len, indexing and slicing, iteration, calling, the context-manager protocol, and arithmetic operators.
:keywords: Python, operator overloading, dunder methods, special methods, __init__, __repr__, __str__, __eq__, __lt__, total_ordering, __len__, __getitem__, __setitem__, __iter__, __next__, __call__, __enter__, __exit__, __add__, __radd__, __iadd__, data model
:page-aliases: web/python/operator-overloading.adoc

include::partial$ai-disclaimer.adoc[]

Python does not have operator overloading via a `pass:c[+]`/`==` keyword table -- it has *dunder methods*
(double-underscore names such as `+__init__+` or `+__add__+`) that every built-in operator, function, and
piece of syntax dispatches to. Implement the right dunder and a custom class gets `repr()`, `==`, `len()`,
`obj[i]`, `for x in obj`, `obj()`, `with obj:`, and `pass:c[+]` for free. The full catalogue is the data model's
https://docs.python.org/3/reference/datamodel.html#special-method-names[special method names] reference.

== Construction and Representation

`+__init__+` initializes a new instance (construction itself is `+__new__+`, rarely overridden).
`+__repr__+` should return an unambiguous, ideally re-evaluable string aimed at developers;
`+__str__+` returns a human-readable string and falls back to `+__repr__+` if not defined. `print()` and
`str()` call `+__str__+`; the REPL and `repr()` call `+__repr__+`.

[source,python]
----
class Point:
    def __init__(self, x, y):
        self.x = x
        self.y = y

    def __repr__(self):
        return f"Point({self.x!r}, {self.y!r})"

    def __str__(self):
        return f"({self.x}, {self.y})"

p = Point(1, 2)
print(p)          # (1, 2)          -- uses __str__
print(repr(p))    # Point(1, 2)     -- uses __repr__
[p]                # [Point(1, 2)]  -- containers repr() their elements
----

== Rich Comparisons

Python has no default `<`/`>`/`+<=+`/`>=` for custom objects, and `==` defaults to identity (`is`) unless
overridden. Each operator maps to its own dunder:
https://docs.python.org/3/reference/datamodel.html#object.__eq__[`+__eq__+`],
`+__ne__+`, `+__lt__+`, `+__le__+`, `+__gt__+`, `+__ge__+` -- collectively the
https://docs.python.org/3/reference/datamodel.html#special-method-names[rich comparison methods].

[source,python]
----
class Money:
    def __init__(self, cents):
        self.cents = cents

    def __eq__(self, other):
        if not isinstance(other, Money):
            return NotImplemented
        return self.cents == other.cents

    def __lt__(self, other):
        if not isinstance(other, Money):
            return NotImplemented
        return self.cents < other.cents

    def __repr__(self):
        return f"Money({self.cents})"

print(Money(100) == Money(100))   # True
print(Money(50) < Money(100))     # True
sorted([Money(300), Money(100)])  # [Money(100), Money(300)] -- sorted() only needs __lt__
----

Return `NotImplemented` (not `False`) when the other operand's type is unsupported -- Python then tries
the reflected method on the other object before giving up with a `TypeError`.

=== `functools.total_ordering`

Defining `+__eq__+` plus just *one* of `+__lt__+`/`+__le__+`/`+__gt__+`/`+__ge__+` is enough for the
https://docs.python.org/3/library/functools.html#functools.total_ordering[`@functools.total_ordering`]
class decorator to fill in the rest:

[source,python]
----
from functools import total_ordering

@total_ordering
class Version:
    def __init__(self, major, minor):
        self.major, self.minor = major, minor

    def __eq__(self, other):
        return (self.major, self.minor) == (other.major, other.minor)

    def __lt__(self, other):
        return (self.major, self.minor) < (other.major, other.minor)

v1, v2 = Version(1, 2), Version(1, 5)
print(v1 <= v2, v1 > v2)   # True False -- __le__ and __gt__ were synthesized
----

== Container Protocol: `+__len__+`, `+__getitem__+`, `+__setitem__+`

Implementing the
https://docs.python.org/3/reference/datamodel.html#emulating-container-types[container-type special
methods] makes a class behave like a built-in sequence or mapping: `len(obj)` calls `+__len__+`,
`obj[key]` calls `+__getitem__+`, `obj[key] = value` calls `+__setitem__+`, and slicing (`obj[1:3]`) passes
a `slice` object as `key`.

[source,python]
----
class Grid:
    def __init__(self, width, height):
        self._data = [0] * (width * height)
        self.width = width

    def __len__(self):
        return len(self._data)

    def _index(self, row, col):
        return row * self.width + col

    def __getitem__(self, key):
        row, col = key
        return self._data[self._index(row, col)]

    def __setitem__(self, key, value):
        row, col = key
        self._data[self._index(row, col)] = value

g = Grid(3, 2)
g[0, 1] = 9
print(g[0, 1], len(g))   # 9 6
----

Slicing support just means checking whether `key` is a `slice`:

[source,python]
----
class Series:
    def __init__(self, values):
        self._values = list(values)

    def __len__(self):
        return len(self._values)

    def __getitem__(self, key):
        if isinstance(key, slice):
            return Series(self._values[key])   # a Series back, not a bare list
        return self._values[key]

s = Series([10, 20, 30, 40])
print(s[1])       # 20
print(s[1:3]._values)   # [20, 30]
----

=== `+__iter__+`/`+__next__+` for a Custom Iterable

A class with `+__getitem__+` is iterable by a legacy fallback, but the proper way to make a class a
first-class iterable is the iterator protocol -- `+__iter__+` returning an iterator and `+__next__+`
raising `StopIteration` when exhausted. This is covered in full, including generators as the
usual shortcut, in xref:programming-languages/python/iterators-generators-comprehensions.adoc[]:

[source,python]
----
class Countdown:
    def __init__(self, start):
        self.start = start

    def __iter__(self):
        self._current = self.start
        return self

    def __next__(self):
        if self._current <= 0:
            raise StopIteration
        self._current -= 1
        return self._current + 1

for n in Countdown(3):
    print(n)   # 3  2  1
----

== `+__call__+`: Making Instances Callable

An object with `+__call__+` can be invoked with `()` like a function, which is how decorators, memoizers,
and stateful callbacks are often implemented:

[source,python]
----
class Multiplier:
    def __init__(self, factor):
        self.factor = factor

    def __call__(self, value):
        return value * self.factor

double = Multiplier(2)
print(double(21))       # 42
print(callable(double))  # True
----

== `+__enter__+`/`+__exit__+`: Writing a Custom Context Manager

The `with` statement is syntax over a protocol: on entry it calls `+__enter__+` (whose return value is
bound by `as`), and on exit -- normal or via exception -- it calls `+__exit__+` with the exception info.
xref:programming-languages/python/files-and-context-managers.adoc[] covers this protocol in depth for the common case of
`open()`; here it is implemented directly on a class:

[source,python]
----
class Timer:
    def __enter__(self):
        import time
        self._start = time.perf_counter()
        return self

    def __exit__(self, exc_type, exc_value, traceback):
        import time
        self.elapsed = time.perf_counter() - self._start
        return False   # False/None propagates any exception; True would suppress it

with Timer() as t:
    total = sum(range(1_000_000))
print(f"took {t.elapsed:.4f}s")
----

Returning a truthy value from `+__exit__+` suppresses a raised exception; returning `False`/`None` (the
common case) lets it propagate normally after cleanup runs.

== Arithmetic Operators: `+__add__+`, `+__radd__+`, `+__iadd__+`

`pass:c[+]` dispatches to `+__add__+` on the left operand; if that returns `NotImplemented` (or the left operand's
type doesn't define it), Python tries `+__radd__+` on the *right* operand -- this is what lets
`pass:c[5 + my_vector]` work even though `+int.__add__+` knows nothing about `Vector`. `pass:c[+=]` tries the in-place
`+__iadd__+` first and only falls back to `+__add__+` (then rebinding the name) if `+__iadd__+` is absent.
Every other arithmetic operator follows the identical three-method pattern (`+__sub__+`/`+__rsub__+`, etc.)
documented alongside `+__add__+` in the
https://docs.python.org/3/reference/datamodel.html#special-method-names[special method names] reference.

[source,python]
----
class Vector:
    def __init__(self, x, y):
        self.x, self.y = x, y

    def __add__(self, other):
        if not isinstance(other, Vector):
            return NotImplemented
        return Vector(self.x + other.x, self.y + other.y)

    def __radd__(self, other):
        # supports sum([...]) starting its accumulator at int 0
        if other == 0:
            return self
        return self.__add__(other)

    def __iadd__(self, other):
        self.x += other.x
        self.y += other.y
        return self   # __iadd__ must return the (possibly mutated) instance

    def __repr__(self):
        return f"Vector({self.x}, {self.y})"

v = Vector(1, 2)
print(v + Vector(3, 4))     # Vector(4, 6)   -- __add__
print(sum([Vector(1, 1), Vector(2, 2)]))   # Vector(3, 3)  -- __radd__ handles the initial 0
v += Vector(1, 1)
print(v)                    # Vector(2, 3)   -- __iadd__ mutated in place
----

If `+__iadd__+` is omitted, `pass:c[v += other]` simply becomes `+v = v.__add__(other)+`, producing a new object
instead of mutating -- fine for immutable-style value types, but worth choosing deliberately.

== The Data Model: How Operators Dispatch

Operators and built-in functions are *syntax for special methods*. `pass:c[a + b]` is `+type(a).__add__(a, b)+`, `len(x)` is
`+type(x).__len__(x)+`, `x[i]` is `+type(x).__getitem__(x, i)+`, and `with m:` calls `+__enter__+` and `+__exit__+`. Python looks the
method up on the *type*, never on the instance, so assigning `+obj.__len__ = ...+` has no effect on `len(obj)`. This is the
reason the whole language can be extended with one idea (see the
https://docs.python.org/3/reference/datamodel.html#special-method-names[special method names] reference), and also the
reason that a special method should return the documented type and follow the documented contract.

=== Binary operators, reflected operands, and `NotImplemented`

For `pass:c[a + b]`, Python calls `+a.__add__(b)+`. If that method is missing or *returns `NotImplemented`* (a special singleton, not an
exception), Python tries the reflected method `+b.__radd__(a)+`. If that also declines the result is `TypeError`. When the right
operand's type is a *subclass* of the left operand's type and overrides the reflected method, the right operand is tried
first, so a subclass can always specialise an operation. Returning `NotImplemented` rather than raising `TypeError`
yourself is what keeps `pass:c[Money(1) + Decimal(1)]` extensible to the other type.

[mermaid]
....
flowchart TD
    A["a + b"] --> S{"type of b is a proper subclass of\ntype of a and overrides __radd__?"}
    S -- Yes --> R1["Try b.__radd__(a) first"]
    S -- No --> L["Try a.__add__(b)"]
    L --> N1{"NotImplemented\nor missing?"}
    N1 -- No --> OK["Use the result"]
    N1 -- Yes --> R2["Try b.__radd__(a)"]
    R1 --> N2{"NotImplemented?"}
    N2 -- No --> OK
    N2 -- Yes --> L
    R2 --> N3{"NotImplemented\nor missing?"}
    N3 -- No --> OK
    N3 -- Yes --> E["TypeError: unsupported operand types"]
....

[source,python]
----
class Left:
    def __add__(self, other):
        print("Left.__add__")
        return NotImplemented

    def __radd__(self, other):
        print("Left.__radd__")
        return "left-radd"


class Right:
    def __radd__(self, other):
        print("Right.__radd__")
        return "right-radd"


print(Left() + Right())          # Left.__add__ gives up, then Right.__radd__
try:
    Left() + 1
except TypeError as exc:
    print("TypeError:", exc)

class Base:
    def __add__(self, other):
        print("Base.__add__")
        return "base"

class Derived(Base):
    def __radd__(self, other):
        print("Derived.__radd__ wins: subclass priority")
        return "derived"

print(Base() + Derived())
----

Output:

[source,text]
----
Left.__add__
Right.__radd__
right-radd
Left.__add__
TypeError: unsupported operand type(s) for +: 'Left' and 'int'
Derived.__radd__ wins: subclass priority
derived
----

The same pattern applies to comparisons (`+__eq__+` and `+__lt__+` have swapped-operand counterparts), and the augmented forms
(`pass:c[x += y]`) try `+__iadd__+` first and then fall back to `+__add__+`.

=== A complete value type: `Money`

A value object ties the protocols together. The class below is immutable, hashable, ordered, supports `pass:c[+]`, `+*+` and `sum()`,
and formats itself. Three details carry the weight: every binary method returns `NotImplemented` for foreign types;
`+__eq__+` and `+__hash__+` are defined together (the contract is "equal objects hash equally"; define `+__eq__+` alone and
the class becomes unhashable); and `functools.total_ordering` derives `+<=+`, `>` and `>=` from `+__eq__+` and `+__lt__+`.

[source,python]
----
from functools import total_ordering


@total_ordering
class Money:
    """Immutable amount in cents. Arithmetic returns new objects."""
    __slots__ = ("cents",)

    def __init__(self, cents):
        object.__setattr__(self, "cents", int(cents))

    def __setattr__(self, name, value):
        raise AttributeError("Money is immutable")

    def __eq__(self, other):
        if not isinstance(other, Money):
            return NotImplemented                 # let Python try the reflected operation
        return self.cents == other.cents

    def __lt__(self, other):
        if not isinstance(other, Money):
            return NotImplemented
        return self.cents < other.cents

    def __hash__(self):
        return hash(self.cents)

    def __add__(self, other):
        if isinstance(other, Money):
            return Money(self.cents + other.cents)
        return NotImplemented

    __radd__ = lambda self, other: self if other == 0 else NotImplemented   # lets sum() start at 0

    def __mul__(self, factor):
        if isinstance(factor, int):
            return Money(self.cents * factor)
        return NotImplemented

    __rmul__ = __mul__

    def __bool__(self):
        return self.cents != 0

    def __repr__(self):
        return f"Money({self.cents})"

    def __str__(self):
        return f"{self.cents // 100}.{self.cents % 100:02d}"

    def __format__(self, spec):
        return format(str(self), spec)


a, b = Money(250), Money(199)
print(a + b, 3 * b, sum([a, b, Money(1)]), max(a, b), a > b, a >= b, sorted([a, b]))
print(f"[{a:>8}]", repr(a), bool(Money(0)))
print(a == 250, a != 250)
try:
    a + 5
except TypeError as exc:
    print("TypeError:", exc)
try:
    a.cents = 1
except AttributeError as exc:
    print("AttributeError:", exc)
----

Output:

[source,text]
----
4.49 5.97 4.50 2.50 True True [Money(199), Money(250)]
[    2.50] Money(250) False
False True
TypeError: unsupported operand type(s) for +: 'Money' and 'int'
AttributeError: Money is immutable
----

`+__repr__+` should be unambiguous and ideally valid code (used in logs and the REPL), `+__str__+` should be readable for
end users, and `+__format__+` receives the text after the colon in an f-string. `a == 250` is `False` rather than an error
because `+__eq__+` returned `NotImplemented` and the fallback for `==` is identity.

=== Containers: implement a little, inherit a lot

The `collections.abc` module defines abstract base classes that complete a protocol from a few primitives. Subclass
`MutableSequence`, implement `+__getitem__+`, `+__setitem__+`, `+__delitem__+`, `+__len__+` and `insert`, and you receive `append`,
`extend`, `pop`, `remove`, `reverse`, `index`, `count`, `in`, iteration and `reversed` for free. Note that `isinstance(s, list)`
is false: protocols are about behaviour, not inheritance from `list`. A class with only `+__getitem__+` that raises
`IndexError` at the end is already iterable through the legacy sequence protocol, and `dict` subclasses can supply
`+__missing__+` for default values on a failed lookup.

[source,python]
----
from collections.abc import MutableSequence, Mapping


class Shelf(MutableSequence):
    """Implement five methods; the ABC supplies append, extend, pop, remove, reverse, index, count, __iter__ ..."""
    def __init__(self, items=()):
        self._items = list(items)

    def __len__(self):
        return len(self._items)

    def __getitem__(self, index):
        if isinstance(index, slice):
            return Shelf(self._items[index])
        return self._items[index]

    def __setitem__(self, index, value):
        self._items[index] = value

    def __delitem__(self, index):
        del self._items[index]

    def insert(self, index, value):
        self._items.insert(index, value)

    def __repr__(self):
        return f"Shelf({self._items!r})"


s = Shelf(["Dune", "Emma"])
s.append("Ulysses")                       # supplied by MutableSequence
s.extend(["Odes"])
print(s, len(s), s[1:3], "Emma" in s, s.index("Odes"))
print(s.pop(), list(reversed(s)))
print(isinstance(s, MutableSequence), isinstance(s, list))

# __getitem__ alone is enough for iteration and 'in'
class Countdown:
    def __getitem__(self, i):
        if i >= 3:
            raise IndexError
        return 3 - i
print(list(Countdown()), 2 in Countdown())

class Config(dict):
    def __missing__(self, key):          # called by dict.__getitem__ on a miss
        return f"<{key}?>"
print(Config(a=1)["a"], Config(a=1)["b"], Config(a=1).get("b"))
----

Odes ['Ulysses', 'Emma', 'Dune']
True False
[3, 2, 1] True
1 <b?> None

=== Guidelines

* implement only the operators that have an obvious meaning for the type; a `pass:c[+]` that concatenates, merges and appends
  depending on the argument is a maintenance burden;
* keep operators free of surprising side effects and keep `+__eq__+`, `+__hash__+` and mutability consistent (mutable
  objects usually should not be hashable);
* return `NotImplemented` for unsupported operand types and let Python raise the `TypeError`;
* for simple value types prefer a frozen dataclass (see xref:programming-languages/python/dataclasses-and-enums.adoc[Dataclasses and Enums]), which generates
  `+__init__+`, `+__repr__+`, `+__eq__+` and `+__hash__+` for you.
