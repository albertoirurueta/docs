= Modules and Packages
:description: How Python organizes code into modules and packages -- import forms, the __name__ == "__main__" pattern, package layout with relative imports, and how import resolves a name via sys.path.
:keywords: Python, modules, packages, import, from import, as, __name__, __main__, __init__.py, relative imports, sys.path, module search path, circular imports, pyc cache
:page-aliases: web/python/modules-and-packages.adoc

A *module* is simply a `.py` file; a *package* is a directory of modules. Splitting code this way lets it be
reused across scripts and projects, as covered in the tutorial's
https://docs.python.org/3/tutorial/modules.html[Modules] chapter.

== Importing Modules

`import name` runs the module's top-level code once and binds the *module object* itself -- its functions,
classes, and variables are then reached as attributes:

[source,python]
----
import math

math.sqrt(16)      # 4.0
math.pi            # 3.141592653589793
----

`from module import name` binds specific names directly into the current namespace, skipping the module-object
prefix; `import module as alias` renames the bound module object:

[source,python]
----
from math import sqrt, pi

sqrt(16)            # 4.0 -- no 'math.' prefix needed
pi                  # 3.141592653589793

import numpy as np  # conventional alias
----

A module is a first-class object: attributes can be listed and introspected like any other object's:

[source,python]
----
import math

type(math)                       # <class 'module'>
"sqrt" in dir(math)               # True
math.__name__                    # 'math'
----

== The `+__name__ == "__main__"+` Pattern

Every module has a `+__name__+` attribute. When a file is *run directly*, Python sets `+__name__+` to
`+"__main__"+`; when the same file is *imported*, `+__name__+` is set to the module's own name instead. Guarding
script-only code behind this check lets one file work both as an importable module and a runnable script:

[source,python]
----
# greetings.py
def greet(name: str) -> str:
    return f"Hello, {name}!"

def main() -> None:
    print(greet("world"))

if __name__ == "__main__":
    main()          # runs only when executed as `python greetings.py`
----

[source,console]
----
$ python greetings.py
Hello, world!
----

Importing the same file elsewhere runs the function definitions but skips `main()`, since `+__name__+` is then
`"greetings"`, not `+"__main__"+`:

[source,python]
----
import greetings

greetings.greet("Ada")   # 'Hello, Ada!' -- main() never ran
----

== Packages

A *package* is a directory containing an `+__init__.py+` file (which may be empty) alongside its modules;
`+__init__.py+` marks the directory as importable and runs once, the first time the package is imported. Packages
can nest arbitrarily to form *subpackages*, as shown under
https://docs.python.org/3/tutorial/modules.html#packages[Packages] in the tutorial:

[source,text]
----
shapes/
├── __init__.py
├── circle.py
├── square.py
└── solids/
    ├── __init__.py
    └── sphere.py
----

From outside the package, import a submodule with dotted syntax:

[source,python]
----
from shapes import circle
from shapes.solids import sphere

circle.Circle(radius=2)
sphere.Sphere(radius=1)
----

*Relative imports*, valid only inside a package's own modules, reference siblings by leading dots -- one dot for
the current package, two for the parent:

[source,python]
----
# shapes/square.py
from . import circle          # sibling module in the same package
from .circle import Circle    # a specific name from a sibling module
----

== The Module Search Path

`import` does not scan the whole filesystem -- it searches `sys.path`, a list built from the script's own
directory, the `PYTHONPATH` environment variable, and installation-dependent defaults:

[source,python]
----
import sys

sys.path
# ['', '/usr/lib/python3.13', '/usr/lib/python3.13/site-packages', ...]
----

[source,console]
----
$ PYTHONPATH=/opt/mylibs python app.py
----

Once found, the module's source is compiled to bytecode and cached under `+__pycache__/*.pyc+`; a later import
reuses that cache unless the source file is newer, and either way the module body executes *only once* per
process -- a second `import` of the same name just returns the cached module object without re-running it:

[source,python]
----
import time

import config   # first import: module body executes, printed side effects appear
import config   # second import: cached module object returned, nothing re-executed
----

A *circular import* -- module `a` importing `b` while `b` imports `a` -- fails or yields a half-initialized
module, because the first import is still running when the second one starts. Avoid it by importing the
specific name inside the function that needs it (a *local import*) rather than at module top level, or by
restructuring the shared code into a third module both sides import from.

== How `import` Resolves a Name

[mermaid]
....
flowchart TD
    A["import name"] --> B{"Already in\nsys.modules?"}
    B -- Yes --> F["Bind cached module\nobject in caller"]
    B -- No --> C["Search sys.path\nfor 'name'"]
    C --> D{"Found?"}
    D -- No --> E["Raise ModuleNotFoundError"]
    D -- Yes --> G{".pyc cache\nup to date?"}
    G -- No --> H["Compile source to .pyc"]
    G -- Yes --> I["Load cached .pyc"]
    H --> J["Execute module body once\n(populates sys.modules)"]
    I --> J
    J --> F
....

The exact algorithm -- finders, loaders, and the `sys.modules` cache -- is specified in the
https://docs.python.org/3/reference/import.html[import system] reference; the tutorial's
https://docs.python.org/3/tutorial/modules.html[Modules] chapter and its
https://docs.python.org/3/tutorial/modules.html#packages[Packages] section cover the everyday usage above.

== The Import System in Detail

`import bookshelf` looks like a lookup but is a small pipeline implemented by the `importlib` machinery
(https://docs.python.org/3/reference/import.html[the import system]). The statement first checks the `sys.modules` cache.
On a miss, Python asks each *finder* on `sys.meta_path` for a *spec* describing where the module lives and how to load it.
The default path-based finder walks `sys.path` (the script's directory or the current directory, `PYTHONPATH`, the standard
library and `site-packages`). The spec's *loader* then creates the module object, Python stores it in `sys.modules`
*before* running the module's code, and finally executes the body in the new module's namespace.

[mermaid]
....
sequenceDiagram
    participant U as import bookshelf.catalog
    participant C as sys.modules
    participant F as Finders on sys.meta_path
    participant L as Loader
    U->>C: Is bookshelf in the cache?
    C-->>U: No
    U->>F: find_spec for bookshelf
    F-->>U: spec with origin and loader
    U->>L: create module, store in cache
    L->>L: run bookshelf/__init__.py
    U->>C: Is bookshelf.catalog cached?
    C-->>U: No
    U->>F: find_spec using bookshelf.__path__
    F-->>U: spec for catalog.py
    U->>L: create, cache, run catalog.py
    L-->>U: bind name bookshelf in caller
....

Importing a dotted name imports each parent package first, always running the parent's `+__init__.py+`, and then searches the
submodule inside the parent's `+__path__+`. The sample builds a real package in a temporary directory and shows each step:

[source,python]
----
import importlib
import importlib.util
import sys
import tempfile
from pathlib import Path

root = Path(tempfile.mkdtemp())
pkg = root / "bookshelf"
pkg.mkdir()
(pkg / "__init__.py").write_text(
    'print("  running bookshelf/__init__.py")\n'
    'from .catalog import Catalog\n'
    '__all__ = ["Catalog"]\n'
)
(pkg / "catalog.py").write_text(
    'print("  running bookshelf/catalog.py, __name__ =", __name__)\n'
    'class Catalog:\n'
    '    def __init__(self):\n'
    '        self.items = []\n'
)
sys.path.insert(0, str(root))                    # a finder will now search this directory

print("find_spec:", importlib.util.find_spec("bookshelf").origin == str(pkg / "__init__.py"))
print("imported yet?", "bookshelf" in sys.modules)

import bookshelf                                 # runs __init__.py, which imports catalog
print("imported yet?", "bookshelf" in sys.modules, "bookshelf.catalog" in sys.modules)

import bookshelf                                 # cache hit: nothing runs
from bookshelf import catalog                    # submodule already loaded
print(bookshelf.__name__, bookshelf.__package__, list(map(Path, bookshelf.__path__)) == [pkg])
print(catalog.__spec__.name, catalog.__spec__.parent, type(catalog.__spec__.loader).__name__)
print(bookshelf.Catalog is catalog.Catalog)

# deleting from sys.modules forces a fresh execution on the next import
del sys.modules["bookshelf.catalog"]
importlib.import_module("bookshelf.catalog")
print("reloaded:", bookshelf.catalog is not catalog)
----

Output:

[source,text]
----
find_spec: True
imported yet? False
  running bookshelf/__init__.py
  running bookshelf/catalog.py, __name__ = bookshelf.catalog
imported yet? True True
bookshelf bookshelf True
bookshelf.catalog bookshelf SourceFileLoader
True
  running bookshelf/catalog.py, __name__ = bookshelf.catalog
reloaded: True
----

What this demonstrates:

* a module's body runs once per process; later imports are dictionary lookups, which is why top-level code in a module
  is a good place for one-time setup and a bad place for work with side effects;
* `+__name__+` is the dotted path (`bookshelf.catalog`) for an imported module and `+"__main__"+` for the entry script;
* `+__package__+` and `+__spec__+` drive relative imports (`from .catalog import Catalog`), which only work inside a package
  and fail with "attempted relative import with no known parent package" if the file is run directly as a script; use
  `python -m package.module` to run a module inside its package;
* removing a name from `sys.modules` forces re-execution on the next import, and `importlib.reload(module)` re-runs the
  body in the *same* module object, which does not update names that other modules already copied with
  `from module import name`. Reloading is a development convenience, not a deployment technique.

=== Circular imports and how to break them

Because a module is added to `sys.modules` before its body finishes, a circular import hands the second module a
*partially initialised* module. `import a` then works (you get the module object) but `from a import name` fails if `name` has
not been defined yet. The sample shows the failure and the standard repair, a function-level (local) import that runs after
both modules are fully loaded; the other repairs are to move the shared code to a third module, or to depend on an
abstraction that both modules import.

[source,python]
----
import sys
import tempfile
from pathlib import Path

root = Path(tempfile.mkdtemp())
files = {
    # broken pair: each module needs a name from the other at import time
    "authors_bad.py": "import books_bad\ndef author_of(title):\n    return 'Herbert'\n",
    "books_bad.py": "from authors_bad import author_of   # authors_bad is still half-initialised here\nTITLES = ['Dune']\n",
    # fixed pair: the dependency is resolved lazily, inside the function that needs it
    "authors.py": "import books\ndef author_of(title):\n    return 'Herbert'\n",
    "books.py": (
        "TITLES = ['Dune']\n"
        "def describe(title):\n"
        "    from authors import author_of     # runs on the first call, after both modules exist\n"
        "    return f'{title} by {author_of(title)}'\n"
    ),
}
for name, text in files.items():
    (root / name).write_text(text)
sys.path.insert(0, str(root))

try:
    import authors_bad
except ImportError as exc:
    print("ImportError:", str(exc).split(" (")[0])
print("authors_bad" in sys.modules, "books_bad" in sys.modules)   # failed imports are cleaned up

import authors
import books
print(books.describe("Dune"))

# a script run as 'python file.py' is __main__, not an importable module
print(__name__, __spec__)
----

Output:

[source,text]
----
ImportError: cannot import name 'author_of' from partially initialized module 'authors_bad'
False False
Dune by Herbert
__main__ None
----

Note that Python removes a module from `sys.modules` when its import raises, so a retry re-executes it.

=== Packages: regular, namespace, and public API

A *regular package* is a directory with an `+__init__.py+`; the file runs on first import and defines what `import package`
exposes, typically by re-exporting names from submodules and setting `+__all__+` (the list `+from package import *+` uses).
A directory without `+__init__.py+` is a *namespace package*, whose parts can be spread over several `sys.path` entries;
it is useful for plugin systems and splitting one namespace across distributions, but a regular package is the better
default for an application. Prefer explicit imports (`from bookshelf.catalog import Catalog`) over star imports, keep
`+__init__.py+` light, and structure projects with a `src/` layout so tests import the *installed* package instead of the
working directory (see xref:programming-languages/python/build-tools/packaging-concepts-and-standards.adoc[Packaging Concepts & Standards]).
