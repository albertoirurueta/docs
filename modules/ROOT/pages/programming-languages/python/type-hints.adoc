A *type hint* documents the expected type of a variable, parameter, or return value. Python never checks
these at runtime -- they exist for readers and for external tools.

[#why-type-hints-and-basic-annotations]
== Why Type Hints, and Basic Annotations

Type hints improve *documentation* and enable *tooling* (autocomplete, refactoring, static analysis) --
they are not enforced by the interpreter. This distinction is explained in the
https://docs.python.org/3/library/typing.html[`typing`] module documentation and formalized in
https://peps.python.org/pep-0484/[PEP 484], which introduced the syntax:

[source,python]
----
x: int = 5
name: str = "Ada"

def greet(name: str, times: int = 1) -> str:
    return (f"Hello, {name}! " * times).strip()

# Hints are pure documentation at runtime -- this "wrong" call still executes fine:
print(greet(42))   # 'Hello, 42!' -- name violates the `str` hint, but nothing checks it
----

The interpreter never inspects `x: int` or `+def greet(name: str, times: int = 1) -> str+` to reject
mismatched values -- see <<static-checkers>> below for how a *separate* tool catches this instead.

== Generics: `list[int]`, `dict[str, int]`, and Unions

Since Python 3.9, built-in collections are subscriptable directly -- `list[int]`, `dict[str, int]`,
`tuple[int, str]` -- without importing `List`/`Dict` from `typing`. Full generic-alias coverage is in
https://docs.python.org/3/library/typing.html#generic-alias-types[Generic Alias Types]:

[source,python]
----
def total(values: list[int]) -> int:
    return sum(values)

def counts(words: list[str]) -> dict[str, int]:
    result: dict[str, int] = {}
    for word in words:
        result[word] = result.get(word, 0) + 1
    return result
----

=== Modern unions: `X | None` (3.10+)

Since Python 3.10, `|` builds a union type directly, per
https://docs.python.org/3/library/typing.html#typing.Union[`typing.Union`]:

[source,python]
----
def find(items: list[str], target: str) -> int | None:
    for i, item in enumerate(items):
        if item == target:
            return i
    return None    # int | None covers this
----

=== Older code: `Optional[X]` and `Union[X, Y]`

Before 3.10 (or for compatibility with older code), use `Optional` and `Union` from `typing`, documented
at https://docs.python.org/3/library/typing.html#typing.Optional[`typing.Optional`]:

[source,python]
----
from typing import Optional, Union

def find(items: list, target) -> Optional[int]:      # same as int | None
    for i, item in enumerate(items):
        if item == target:
            return i
    return None

def parse(value: Union[str, int]) -> str:             # same as str | int
    return str(value)
----

== `TypeVar`, Generic Functions and Classes, and `Protocol`

=== `TypeVar` for generic functions

A `TypeVar` lets a function's parameter and return type vary together while staying *consistent* across
one call -- documented at
https://docs.python.org/3/library/typing.html#typing.TypeVar[`typing.TypeVar`]:

[source,python]
----
from typing import TypeVar

T = TypeVar("T")

def first(items: list[T]) -> T:
    return items[0]

first([1, 2, 3])          # T is int; returns an int
first(["a", "b"])         # T is str; returns a str
----

=== Generic classes

A class can be generic over the same `TypeVar`, documented under
https://docs.python.org/3/library/typing.html#typing.Generic[`typing.Generic`]:

[source,python]
----
from typing import Generic, TypeVar

T = TypeVar("T")

class Box(Generic[T]):
    def __init__(self, item: T) -> None:
        self.item = item

    def get(self) -> T:
        return self.item

int_box: Box[int] = Box(42)
str_box: Box[str] = Box("hello")
----

=== `Protocol` for structural typing

A `Protocol` describes an interface by *shape* -- any object with matching methods satisfies it, with no
explicit inheritance required ("duck typing" made checkable). See
https://docs.python.org/3/library/typing.html#typing.Protocol[`typing.Protocol`]:

[source,python]
----
from typing import Protocol

class SupportsClose(Protocol):
    def close(self) -> None: ...

class FileHandle:
    def close(self) -> None:
        print("closed")

def shut_down(resource: SupportsClose) -> None:
    resource.close()

shut_down(FileHandle())   # OK: FileHandle has a matching close() method
----

=== `Callable[[int], str]`

`Callable[[ArgTypes], ReturnType]` annotates a function value, documented at
https://docs.python.org/3/library/typing.html#typing.Callable[`typing.Callable`]:

[source,python]
----
from typing import Callable

def apply(func: Callable[[int], str], value: int) -> str:
    return func(value)

apply(lambda n: f"#{n}", 7)   # "#7"
----

[#static-checkers]
== Static Checkers: mypy and pyright

Type hints are read by *opt-in* static checkers such as https://mypy-lang.org/[mypy] and
https://microsoft.github.io/pyright/[pyright] -- they analyze source *without running it* and report
mismatches the interpreter itself never catches. Install and run mypy from the command line:

[source,bash]
----
pip install mypy
mypy my_module.py
----

Given the earlier `+greet(name: str, times: int = 1) -> str+` example, mypy flags the misordered call at
analysis time, before the program ever runs:

[source,bash]
----
$ mypy my_module.py
my_module.py:10: error: Argument 1 to "greet" has incompatible type "int"; expected "str"
Found 1 error in 1 file (checked 1 source file)
----

Because hints carry no runtime effect (see <<why-type-hints-and-basic-annotations>> above), skipping
mypy/pyright means Python happily executes the same mismatched call -- the checker is the only thing
enforcing the contract the annotations describe. Background and the annotation object model itself
(`+__annotations__+`, string vs. evaluated forms) are covered in
https://docs.python.org/3/howto/annotations.html[the Annotations Best Practices HOWTO].

== What Type Hints Do (and Do Not Do) at Run Time

Annotations are *metadata*. The interpreter evaluates them (unless postponed), stores them in `+__annotations__+`, and then
ignores them: `def f(x: int)` accepts a string, and a variable annotation does not constrain later assignments. All checking
is done by separate tools that read the same source, so type hints have a development-time cost-benefit rather than a
run-time one. The two worlds meet in libraries that *do* read annotations at run time (dataclasses, Pydantic, FastAPI) and in
`typing.get_type_hints`, which resolves string annotations to real objects.

[mermaid]
....
flowchart LR
    S["Source with annotations"] --> I["Interpreter: stores\n__annotations__, never checks"]
    S --> C["Static checker\nmypy or pyright"]
    C --> R["Reports mismatches\nbefore the code runs"]
    I --> L["Runtime libraries:\ndataclasses, Pydantic, FastAPI"]
    L --> V["Validate or convert\nvalues from annotations"]
....

The runtime sample shows each piece: generic functions with `TypeVar`, a generic class, a structural `Protocol`, and the
fact that wrong calls still run. The `s.push(42)` line is a type error for a checker and a perfectly valid call for Python.

[source,python]
----
from typing import Callable, Generic, Iterable, Optional, Protocol, TypeVar, get_type_hints

T = TypeVar("T")


def first(items: Iterable[T], default: Optional[T] = None) -> Optional[T]:
    for item in items:
        return item
    return default


print(first.__annotations__)
print(get_type_hints(first))
print(first(["Dune"]), first([]), first("abc"))
# annotations are not enforced at run time: the wrong call below works
print(first.__annotations__["items"], first([1.5]))


class Stack(Generic[T]):
    def __init__(self) -> None:
        self._items: list = []

    def push(self, item: T) -> None:
        self._items.append(item)

    def pop(self) -> T:
        return self._items.pop()


s: Stack[str] = Stack()
s.push("Dune")
s.push(42)              # a checker rejects this line; Python happily runs it
print(s.pop(), type(s).__mro__[1].__name__)


class SupportsTitle(Protocol):
    title: str


class Book:
    def __init__(self, title: str):
        self.title = title


def show(item: SupportsTitle) -> str:         # any object with a title attribute qualifies
    return item.title.upper()

print(show(Book("dune")))

def count_chars(text: str) -> int:
    return len(text)
handlers: dict = {"len": count_chars}
print(handlers["len"]("Dune"))
----

=== Generics and protocols: the idea

A `TypeVar` stands for "the same type in every position where it appears", which links a function's input to its output
(`first` returns an element of whatever it received, or `None`). A generic class like `Stack[T]` records which type its
contents have, and the checker enforces it per instance. A `Protocol` is *structural typing*: a class conforms by having the
right members, with no inheritance, which suits Python's duck typing and lets you describe "anything with a `title`&quot;
without coupling modules. Prefer a small protocol or an abstract collection type (`Iterable`, `Sequence`, `Mapping`)
for parameters and a concrete type for return values: accept the most general, return the most specific.

=== Narrowing: how a checker follows your code

Checkers track the type of a name through control flow. After `if x is None: return`, the remaining code sees the
non-`None` type; `isinstance` narrows a `Union` branch by branch; a `Literal` limits a value to given constants, a
`TypedDict` describes the keys of a dictionary, and `Final` marks a name as not to be reassigned. `typing.cast` only tells
the checker to trust you and does nothing at run time, so treat it as a code smell to review. Use `Optional[X]`
(or `X | None` from 3.10) deliberately: every `Optional` return forces callers to handle `None`, which is the point.

[source,python]
----
# A type checker (mypy, pyright) reads these; the code is valid for the interpreter regardless.
from typing import Final, Literal, Optional, TypedDict, Union, cast


class BookRecord(TypedDict):
    title: str
    year: int


def find(titles: dict, key: str) -> Optional[BookRecord]:
    return titles.get(key)


def year_of(record: Optional[BookRecord]) -> int:
    if record is None:                     # narrowing: after this test the checker knows it is a BookRecord
        return 0
    return record["year"]


def describe(value: Union[int, str, list]) -> str:
    if isinstance(value, int):             # isinstance narrows a Union branch by branch
        return f"number {value + 1}"
    if isinstance(value, str):
        return f"text {value.upper()}"
    return f"list of {len(value)}"


Mode = Literal["r", "w"]
MAX: Final = 3
db = {"Dune": {"title": "Dune", "year": 1965}}
print(year_of(find(db, "Dune")), year_of(find(db, "none")))
print(describe(1), describe("a"), describe([1, 2]))
print(cast(int, "not really an int"))      # cast is a promise to the checker, with no run-time effect
----

Output:

[source,text]
----
1965 0
number 2 text A list of 2
not really an int
----

=== Adopting hints gradually

* start at the boundaries (public functions, data models) and let inference cover the inside;
* run a checker in continuous integration, begin with a lenient configuration, and tighten per module;
* use `Any` as an explicit, visible escape hatch and `object` when you mean "anything, but I must check first";
* avoid annotating with concrete containers when a protocol will do, and avoid `+# type: ignore+` without an error code and a
  comment explaining why;
* in older code, `+from __future__ import annotations+` postpones evaluation (3.7+), which allows forward references without
  quotes; libraries that read annotations at run time should call `typing.get_type_hints`.

Every snippet in this section was run with Python 3.9.6 and the output shown is the real output (the textual form of generic
types in `+__annotations__+` differs slightly between Python versions).
