== `class` Basics, `+__init__+`, Attributes, and `self`

A `class` statement defines a new type. `+__init__+` is the *initializer*, called automatically right after a
new instance is created, and is where instance attributes are usually set:

[source,python]
----
class Dog:
    species = "Canis familiaris"       # class attribute: shared by all instances

    def __init__(self, name, age):
        self.name = name               # instance attribute: unique per instance
        self.age = age

    def describe(self):                # instance method
        return f"{self.name} is {self.age} year(s) old"
----

Every method's first parameter is conventionally named `self` -- it is the instance the method was called
on, passed automatically by Python. A **class attribute** (`species` above) lives on the class object and is
shared by every instance unless an instance sets its own attribute of the same name, which then *shadows* the
class attribute for that instance only:

[source,python]
----
rex = Dog("Rex", 3)
fido = Dog("Fido", 5)

print(rex.species, fido.species)   # Canis familiaris, Canis familiaris (shared)

rex.species = "Rex's own species"  # creates an *instance* attribute, doesn't touch the class one
print(rex.species, fido.species)   # Rex's own species, Canis familiaris
----

Mutable class attributes (a `list` or `dict`) are a common trap: mutating one through an instance mutates the
*shared* object seen by every instance, so per-instance mutable state belongs in `+__init__+` instead. See
https://docs.python.org/3/tutorial/classes.html[the Classes tutorial] for the full attribute lookup rules.

== Creating Instances; `@staticmethod` and `@classmethod`

Calling a class like a function creates an instance -- `Dog("Rex", 3)` runs `+Dog.__init__+` on a freshly
created object and returns it. An **instance method** (the default) receives `self` and can read or mutate
that instance's state:

[source,python]
----
print(rex.describe())   # Rex is 3 year(s) old
----

A **`@staticmethod`** takes neither `self` nor the class -- it's a plain function namespaced under the class,
used when the logic doesn't need instance or class state:

[source,python]
----
class TemperatureConverter:
    @staticmethod
    def celsius_to_fahrenheit(c):
        return c * 9 / 5 + 32

print(TemperatureConverter.celsius_to_fahrenheit(100))   # 212.0
----

A **`@classmethod`** takes the class itself (conventionally named `cls`) instead of an instance, and is the
idiomatic way to write an alternative constructor:

[source,python]
----
class Dog:
    def __init__(self, name, age):
        self.name = name
        self.age = age

    @classmethod
    def from_birth_year(cls, name, birth_year, current_year):
        return cls(name, current_year - birth_year)   # cls(...) == Dog(...)

rex = Dog.from_birth_year("Rex", 2021, 2024)
print(rex.name, rex.age)   # Rex 3
----

Both decorators are documented under
https://docs.python.org/3/library/functions.html#staticmethod[`staticmethod`] and
https://docs.python.org/3/library/functions.html#classmethod[`classmethod`].

== Inheritance: `class Child(Parent)`, Overriding, and `super()`

A class inherits from another by naming it in parentheses; the child gets every attribute and method of the
parent and can *override* any of them by redefining it with the same name:

[source,python]
----
class Animal:
    def __init__(self, name):
        self.name = name

    def speak(self):
        return f"{self.name} makes a sound"

class Cat(Animal):
    def speak(self):                    # overrides Animal.speak
        return f"{self.name} says Meow"

generic = Animal("Something")
cat = Cat("Whiskers")
print(generic.speak())   # Something makes a sound
print(cat.speak())       # Whiskers says Meow
----

**`super()`** returns a proxy to the parent class, letting an override call the parent's version instead of
fully replacing it -- typically to extend `+__init__+` with additional attributes:

[source,python]
----
class Cat(Animal):
    def __init__(self, name, indoor):
        super().__init__(name)          # runs Animal.__init__, sets self.name
        self.indoor = indoor

    def speak(self):
        base = super().speak()          # reuse the parent's message
        return f"{base} (meow, specifically)"

whiskers = Cat("Whiskers", indoor=True)
print(whiskers.speak())   # Whiskers makes a sound (meow, specifically)
print(isinstance(whiskers, Animal))   # True
----

Inheritance and `super()` are covered in
https://docs.python.org/3/tutorial/classes.html#inheritance[the tutorial's Inheritance section]; single
inheritance is the common case, and combining several base classes brings in method-resolution-order
questions covered on xref:programming-languages/python/advanced-oop-design.adoc[].

== `+__repr__+` and `+__str__+` for Basic Display

Without any customization, printing an instance shows an unhelpful default like
`+<__main__.Dog object at 0x...>+`. Two special methods control this: `+__repr__+` should return an unambiguous,
developer-facing representation (ideally one that could recreate the object), and `+__str__+` returns a
human-readable string used by `print()` and `str()` -- Python falls back to `+__repr__+` when `+__str__+` is
absent:

[source,python]
----
class Dog:
    def __init__(self, name, age):
        self.name = name
        self.age = age

    def __repr__(self):
        return f"Dog(name={self.name!r}, age={self.age!r})"

    def __str__(self):
        return f"{self.name} ({self.age}y)"

rex = Dog("Rex", 3)
print(rex)        # Rex (3y)              -- uses __str__
print(repr(rex))  # Dog(name='Rex', age=3) -- uses __repr__
print([rex])      # [Dog(name='Rex', age=3)] -- containers always use __repr__ on their elements
----

This is a small slice of Python's *data model* -- the full catalogue of special methods (operator overloading,
comparisons, container protocols, and more) lives under
https://docs.python.org/3/reference/datamodel.html#basic-customization[Basic customization] in the language
reference, and is covered end to end on xref:programming-languages/python/operator-overloading.adoc[].

== What `class` and Instantiation Do

A `class` statement runs its body in a fresh namespace, then calls the metaclass (normally `type`) with the class name, the
bases and that namespace to build a *class object*. A class is therefore an ordinary object, created at run time, which can
be passed around, modified and inspected. Calling the class creates an instance in two steps: `+__new__+` *allocates* the
object (rarely overridden: immutable subclasses and singletons), then `+__init__+` *initialises* it.

[mermaid]
....
sequenceDiagram
    participant Caller
    participant T as type.__call__
    participant N as Book.__new__
    participant I as Book.__init__
    Caller->>T: Book("Dune", 1965)
    T->>N: __new__(Book, "Dune", 1965)
    N-->>T: new empty instance
    T->>I: __init__(instance, "Dune", 1965)
    I-->>T: None
    T-->>Caller: the instance
....

An instance keeps its own attributes in a dictionary, `+__dict__+`. Methods are *not* in that dictionary: they are plain
functions stored on the class. Accessing `b.age` finds the function on the class and binds it, producing a *bound method*
that remembers the instance in `+__self__+`. So `b.age()` and `Book.age(b)` are the same call, and `self` is only a naming
convention for the first parameter. This is the first use of the descriptor protocol covered in
xref:programming-languages/python/managed-attributes.adoc[Managed Attributes].

[source,python]
----
class Book:
    shelf_count = 0                              # class attribute: one copy, shared

    def __new__(cls, *args, **kwargs):
        print("__new__ allocates", cls.__name__)
        return super().__new__(cls)

    def __init__(self, title, year):
        print("__init__ initialises", title)
        self.title = title                       # instance attributes live in __dict__
        self.year = year

    def age(self, today=2026):
        return today - self.year


b = Book("Dune", 1965)
print(b.__dict__)
print(type(Book.__dict__["age"]).__name__)                    # in the class: a plain function
print(type(b.age).__name__)                                  # on the instance: a bound method
print(b.age.__self__ is b, b.age.__func__ is Book.__dict__["age"])
print(b.age() == Book.age(b))                    # the two spellings are the same call

b.shelf_count = 5                                # creates an instance attribute that shadows
print(Book.shelf_count, b.shelf_count)
----

Output:

[source,text]
----
__new__ allocates Book
__init__ initialises Dune
{'title': 'Dune', 'year': 1965}
function
method
True True
True
0 5
----

=== Attribute lookup: instance, class, then bases

[mermaid]
....
flowchart TD
    A["obj.name"] --> B{"Data descriptor on the\ntype, such as property?"}
    B -- Yes --> R1["Call its __get__"]
    B -- No --> C{"name in obj.__dict__?"}
    C -- Yes --> R2["Return the instance value"]
    C -- No --> D{"Found on the class or\nits bases in MRO order?"}
    D -- Yes --> R3["Return it; bind if it is\na function"]
    D -- No --> E{"__getattr__ defined?"}
    E -- Yes --> R4["Call __getattr__"]
    E -- No --> R5["AttributeError"]
....

Reading an attribute walks the instance dictionary and then the class and its bases; *writing* an attribute (`obj.x = v`)
always targets the instance dictionary (unless a descriptor intercepts it). That asymmetry explains the most common class
bug: a mutable class attribute such as `tags = []` is shared by every instance, and `+a.tags.append(...)+` mutates the shared
object, whereas `+a.tags = [...]+` creates a private attribute that shadows it. Initialise mutable state in `+__init__+`.

[source,python]
----
class Item:
    kind = "item"
    tags = []                                    # a mutable class attribute is shared

    def __init__(self, title):
        self.title = title


class Book(Item):
    kind = "book"


a, b = Book("Dune"), Book("Emma")
print(a.kind, Item.kind, a.__class__.__mro__[1].__name__)

a.tags.append("sf")                               # mutates the shared list
print(b.tags, Book.tags is Item.tags)

a.tags = ["mine"]                                 # assignment creates an instance attribute
print(a.tags, b.tags, "tags" in vars(a), "tags" in vars(b))

Book.kind = "volume"                              # classes are mutable objects too
print(a.kind, b.kind)
del a.tags
print(a.tags)                                     # the class attribute shows through again

print(hasattr(a, "missing"), getattr(a, "missing", "fallback"))
setattr(a, "dynamic", 1)
print(sorted(vars(a)))
----

Output:

[source,text]
----
book item Item
['sf'] True
['mine'] ['sf'] True False
volume volume
['sf']
False fallback
['dynamic', 'title']
----

=== `+__slots__+`, class methods, and static methods

By default every instance carries a dictionary, which is flexible but costs memory and lets typos create new attributes.
Declaring `+__slots__+` replaces the per-instance dictionary with fixed storage: instances are smaller, attribute access is a
little faster and misspelled assignments raise `AttributeError`. The trade-offs are no dynamic attributes, no weak references
unless `+"__weakref__"+` is listed, and subtle behaviour with multiple inheritance. Use it for classes with many small
instances, not by default.

`@classmethod` receives the class as its first argument, which makes it the right tool for *alternative constructors*
(`from_csv`, `from_dict`): because it calls `+cls(...)+`, a subclass inherits a constructor that builds the subclass.
`@staticmethod` receives nothing and is just a function namespaced inside the class; if it never needs the class, a
module-level function is often clearer.

[source,python]
----
import sys


class Plain:
    def __init__(self, title, year):
        self.title, self.year = title, year


class Slotted:
    __slots__ = ("title", "year")

    def __init__(self, title, year):
        self.title, self.year = title, year


p, s = Plain("Dune", 1965), Slotted("Dune", 1965)
print(hasattr(p, "__dict__"), hasattr(s, "__dict__"))
p.extra = 1
try:
    s.extra = 1
except AttributeError as exc:
    print("AttributeError:", exc)
print(sys.getsizeof(p) + sys.getsizeof(p.__dict__) > sys.getsizeof(s))


class Book:
    def __init__(self, title, year):
        self.title, self.year = title, year

    @classmethod
    def from_csv(cls, line):                      # alternative constructor; works for subclasses
        title, year = line.split(",")
        return cls(title, int(year))

    @staticmethod
    def is_valid_year(year):                      # no self or cls: just a namespaced function
        return 0 < year <= 2026

    def __repr__(self):
        return f"{type(self).__name__}({self.title!r}, {self.year})"


class Ebook(Book):
    pass

print(Book.from_csv("Dune,1965"), Ebook.from_csv("Emma,1815"), Book.is_valid_year(3000))
----

Output:

[source,text]
----
True False
AttributeError: 'Slotted' object has no attribute 'extra' and no __dict__ for setting new attributes
True
Book('Dune', 1965) Ebook('Emma', 1815) False
----

=== Rules of thumb

* give every attribute a value in `+__init__+` so the object is fully formed after construction;
* name "private by convention" attributes with a single leading underscore; a double leading underscore triggers *name
  mangling* (`+__x+` becomes `+_Class__x+`) meant only to avoid clashes in subclasses, not to enforce privacy;
* always define `+__repr__+` (see xref:programming-languages/python/operator-overloading.adoc[Operator Overloading]);
* prefer composition to deep inheritance (see xref:programming-languages/python/advanced-oop-design.adoc[Advanced OOP Design]).
