Python signals errors by *raising* exceptions rather than returning error codes, and handles them with
`try`/`except`. The full model is covered in the tutorial's
https://docs.python.org/3/tutorial/errors.html[Errors and Exceptions] chapter and the
https://docs.python.org/3/library/exceptions.html[built-in exceptions reference].

== `try` / `except` / `else` / `finally`

A `try` block runs its body; if an exception is raised, the first matching `except` clause runs instead.
`else` runs only when the body raised *nothing*; `finally` always runs, whether or not an exception
occurred:

[source,python]
----
def read_first_line(path):
    try:
        f = open(path)
    except FileNotFoundError:
        print(f"no such file: {path}")
        return None
    else:
        try:
            return f.readline()
        finally:
            f.close()   # always runs: cleans up even if readline() raises
----

=== Catch Specific Types, Not Bare `except:`

Name the exception type(s) you expect. A bare `except:` (or `except Exception:` used carelessly) also
swallows programming errors -- typos, `KeyboardInterrupt`, `SystemExit` -- that should propagate instead
of being silently hidden:

[source,python]
----
def to_int(text):
    try:
        return int(text)
    except ValueError:               # only the error int() actually raises
        return None

def risky():
    try:
        return 1 / 0
    except:                          # AVOID: catches everything, including Ctrl-C
        return None
----

A single `except` clause can name several types as a tuple, and multiple `except` clauses run in order,
the first match wins:

[source,python]
----
def parse(value):
    try:
        return int(value)
    except (TypeError, ValueError) as exc:
        print(f"bad input: {exc}")
        return 0
----

The full statement grammar is documented under
https://docs.python.org/3/tutorial/errors.html#handling-exceptions[Handling Exceptions].

== `raise`, Re-Raising, and Exception Chaining

`raise` with no argument, inside an `except` block, re-raises the exception currently being handled --
useful for logging before letting it propagate:

[source,python]
----
def load_config(path):
    try:
        return int(open(path).read())
    except ValueError:
        print(f"malformed config at {path}")
        raise   # re-raise the same exception, unchanged
----

=== `raise X from Y`

Raising a *new* exception from inside an `except` block automatically chains it to the original as
`+__context__+`, shown as "During handling of the above exception, another exception occurred". Use
`raise X from Y` to make that link *explicit* -- or `raise X from None` to suppress it when the original
is just noise:

[source,python]
----
def get_user(user_id, db):
    try:
        return db[user_id]
    except KeyError as exc:
        raise LookupError(f"no user with id {user_id}") from exc   # explicit __cause__

def parse_strict(text):
    try:
        return int(text)
    except ValueError:
        raise ValueError(f"not a number: {text!r}") from None      # hide the low-level cause
----

Chaining is documented in the same
https://docs.python.org/3/tutorial/errors.html[Errors and Exceptions] chapter, under "Exception Chaining".

== Custom Exception Classes

Subclass `Exception` (never `BaseException` directly) to define errors specific to your code. A small
*hierarchy* lets callers catch broadly or narrowly:

[source,python]
----
class AppError(Exception):
    """Base class for all errors raised by this application."""

class ValidationError(AppError):
    """Input failed validation."""
    def __init__(self, field, reason):
        super().__init__(f"{field}: {reason}")
        self.field = field
        self.reason = reason

class NotFoundError(AppError):
    """A requested resource does not exist."""

def get_item(items, key):
    if key not in items:
        raise NotFoundError(f"no item {key!r}")
    return items[key]

try:
    get_item({}, "widget")
except AppError as exc:       # catches ValidationError, NotFoundError, and any future subclass
    print(f"request failed: {exc}")
----

Custom exceptions are covered alongside the built-in hierarchy at
https://docs.python.org/3/library/exceptions.html[the exceptions reference] and in the tutorial's
https://docs.python.org/3/tutorial/errors.html#user-defined-exceptions[User-defined Exceptions] section.

== Exception Groups (3.11+) and `assert`

=== Exception Groups and `+except*+`

An `ExceptionGroup` bundles several *unrelated* exceptions raised together -- typically from concurrent
or batch operations where more than one failure can happen independently. `+except*+` matches groups by
the type of the exceptions *inside* them, and can run several handlers against the same group:

[source,python]
----
def validate_all(records):
    errors = []
    for i, record in enumerate(records):
        if not record.get("name"):
            errors.append(ValueError(f"record {i}: missing name"))
        if record.get("age", 0) < 0:
            errors.append(TypeError(f"record {i}: negative age"))
    if errors:
        raise ExceptionGroup("validation failed", errors)

try:
    validate_all([{"age": -1}, {"name": ""}])
except* ValueError as eg:
    print(f"value errors: {[str(e) for e in eg.exceptions]}")
except* TypeError as eg:
    print(f"type errors: {[str(e) for e in eg.exceptions]}")
----

Each `+except*+` clause only "peels off" the matching sub-exceptions; any left unmatched propagate in a
new group. Full semantics are in
https://docs.python.org/3/tutorial/errors.html#raising-and-handling-multiple-unrelated-exceptions[Raising
and Handling Multiple Unrelated Exceptions].

=== `assert`

`assert` raises `AssertionError` if its condition is falsy -- intended for catching *programmer* errors
and invariants during development, not for validating user input, since assertions are stripped when
Python runs with `-O`:

[source,python]
----
def half(n):
    assert n % 2 == 0, f"{n} is not even"
    return n // 2

half(4)    # 2
half(5)    # AssertionError: 5 is not even
----

`assert` is documented under
https://docs.python.org/3/reference/simple_stmts.html#the-assert-statement[the `assert` statement] in the
language reference.

== Control Flow Through `try`/`except`/`else`/`finally`

`else` and `finally` are easy to place wrong. `else` runs only on the no-exception path; `finally` runs
on *every* path, including one that exits via `return`, `break`, or an unhandled exception:

[mermaid]
....
flowchart TD
    A[Enter try block] --> B{Exception raised?}
    B -->|No| C[else block runs]
    B -->|Yes| D{Matching except clause?}
    D -->|Yes| E[except block runs]
    D -->|No| F[exception propagates unhandled]
    C --> G[finally block runs]
    E --> G
    F --> G
    G --> H[finally done: re-raise if unhandled, else continue]
....

The full execution order -- including what happens when `finally` itself contains a `return` -- is
specified in
https://docs.python.org/3/tutorial/errors.html[the Errors and Exceptions chapter] and
https://docs.python.org/3/library/exceptions.html[the built-in exceptions reference].

== How Exceptions Travel

An exception is an ordinary object (an instance of a class derived from `BaseException`) that Python *raises* and then
carries up the call stack. When `raise` runs, the interpreter stops the current frame and looks for a matching `except`
clause in it; if none matches, the frame is discarded (its `finally` blocks and context managers run) and the search
continues in the caller, and so on until a handler is found or the thread's stack is exhausted, at which point the default
handler prints the traceback and the program exits. Each frame the exception passes adds an entry to its
`+__traceback__+`.

[mermaid]
....
flowchart TD
    R["raise ValueError in parse_year"] --> A{"Matching except\nin this frame?"}
    A -- No --> F1["Run finally blocks and\nwith-block exits; discard frame"]
    F1 --> B{"Caller load_row\nhas a handler?"}
    B -- No --> F2["Unwind load_row"]
    F2 --> C{"Caller load_all\nhas an except ValueError?"}
    C -- Yes --> H["Handler runs;\nexecution continues after try"]
    C -- No --> D["Interpreter prints traceback\nand exits"]
    A -- Yes --> H
....

The `except` clauses of one `try` are tested top to bottom and the *first* class that matches (by `isinstance`) wins, so
order specific classes before general ones. A tuple of classes catches any of them. Because handlers match on the class
tree, the shape of the hierarchy matters: `KeyError` and `IndexError` share `LookupError`, file problems are `OSError`
subclasses (`FileNotFoundError`, `PermissionError`), and `KeyboardInterrupt` and `SystemExit` derive from `BaseException`
precisely so that a broad `except Exception` does not swallow them.

[source,python]
----
import sys
import traceback


def parse_year(text):
    return int(text)                          # raises ValueError for bad text


def load_row(row):
    title, year = row.split(",")
    return title, parse_year(year)


def load_all(rows):
    result = []
    for row in rows:
        try:
            result.append(load_row(row))
        except ValueError as exc:             # handled two frames above where it was raised
            print(f"skipping {row!r}: {exc}")
    return result


print(load_all(["Dune,1965", "Emma,x", "bad-row", "Ulysses,1922"]))

try:
    load_row("Emma,x")
except ValueError:
    frames = traceback.extract_tb(sys.exc_info()[2])
    print([f.name for f in frames])           # outermost call first: where the error travelled
    print(traceback.format_exc().splitlines()[-1])

# the exception class tree decides which handler matches
print([c.__name__ for c in FileNotFoundError.__mro__])
print(issubclass(KeyError, LookupError), issubclass(KeyboardInterrupt, Exception))

def classify(exc):
    try:
        raise exc
    except (KeyError, IndexError) as e:       # a tuple catches any listed type
        return f"lookup problem: {type(e).__name__}"
    except OSError as e:
        return f"os problem: {e.strerror}"
    except Exception as e:                    # last resort, after the specific handlers
        return f"other: {type(e).__name__}"

print(classify(KeyError("x")), classify(FileNotFoundError(2, "No such file")), classify(ZeroDivisionError()))
----

['FileNotFoundError', 'OSError', 'Exception', 'BaseException', 'object']

=== Designing your own exceptions

Define one base class per library or application (`CatalogError`), derive specific failures from it, and give them the
data a handler needs as attributes instead of making callers parse a message. Use `+raise ... from exc+` when translating a
low-level error into a domain error: it sets `+__cause__+`, and the traceback reads "The above exception was the direct cause
of the following exception". Raising inside an `except` block without `from` still records the original in `+__context__+`
("During handling of the above exception, another exception occurred"), and `from None` suppresses the display. A
`finally` block runs on every exit path, which makes it right for release logic and wrong for control flow: a `return`
inside `finally` silently discards a pending exception.

[source,python]
----
class CatalogError(Exception):
    """Base class: callers catch this to handle every library failure."""


class TitleNotFound(CatalogError):
    def __init__(self, title, *, nearby=()):
        super().__init__(f"no such title: {title!r}")
        self.title = title
        self.nearby = list(nearby)


def lookup(catalog, title):
    try:
        return catalog[title]
    except KeyError as exc:
        raise TitleNotFound(title, nearby=[t for t in catalog if t[0] == title[0]]) from exc


try:
    lookup({"Dune": 1, "Dubliners": 2}, "Dusk")
except CatalogError as err:
    print(type(err).__name__, err, err.nearby)
    print("cause:", repr(err.__cause__), "| suppress context:", err.__suppress_context__)

# implicit chaining: raising inside an except block records __context__
try:
    try:
        1 / 0
    except ZeroDivisionError:
        raise RuntimeError("while cleaning up")
except RuntimeError as err:
    print(repr(err.__context__), err.__cause__)

# 'from None' hides the context
try:
    try:
        {}["k"]
    except KeyError:
        raise ValueError("clean message") from None
except ValueError as err:
    print(err.__context__ is not None, err.__suppress_context__)

# finally can override the outcome: a classic trap
def risky():
    try:
        return "from try"
    finally:
        print("finally runs before the return completes")

def swallow():
    try:
        raise RuntimeError("lost")
    finally:
        return "finally return replaces the exception"

print(risky()); print(swallow())
----

ZeroDivisionError('division by zero') None

=== Idioms and pitfalls

Python prefers EAFP ("easier to ask forgiveness than permission"): attempt the operation and handle the failure, which
also avoids the race between checking and acting. Keep the `try` body small so that a handler only covers the line you
expect to fail, put the success path in `else`, and re-raise with a bare `raise` after logging so the original traceback
survives. Some details that surprise people:

* the name bound by `+except ... as name+` is deleted when the block ends, to break a reference cycle through the traceback;
  copy it to another name to keep it, and remember that a stored exception keeps its whole traceback (and every local
  variable in those frames) alive;
* `except Exception:` followed by `pass` hides bugs; if you must ignore an error, catch the narrowest class and say why;
* warnings are a separate mechanism (`warnings.warn`) that only becomes an exception when the filter says `error`, which
  is how test suites turn deprecations into failures;
* generators and context managers participate: an exception thrown into a generator appears at its paused `yield`, and
  `+__exit__+` sees the exception in flight.

[source,python]
----
import warnings
from contextlib import contextmanager


# EAFP vs LBYL: ask forgiveness; it is also race-free
def read_count(path):
    try:
        with open(path) as f:
            return int(f.read())
    except FileNotFoundError:
        return 0
    except ValueError:
        return -1

print(read_count("/nonexistent/count.txt"))

# Re-raise after logging, keeping the original traceback
def process(items):
    try:
        return sum(items)
    except TypeError:
        print("logging the failure")
        raise                                 # bare raise re-raises the active exception

try:
    process([1, "2"])
except TypeError as exc:
    print("propagated:", exc)

# __traceback__ keeps frames alive; delete names that hold exceptions if you store them
saved = []
try:
    raise OSError("disk")
except OSError as exc:
    saved.append(exc)
print(saved[0].__traceback__ is not None)

# the name bound by 'as' is deleted when the except block ends
try:
    raise ValueError("v")
except ValueError as err:
    pass
print("err" in dir())

# warnings are not exceptions unless you ask
with warnings.catch_warnings(record=True) as caught:
    warnings.simplefilter("always")
    warnings.warn("old API", DeprecationWarning)
print(len(caught), caught[0].category.__name__)
with warnings.catch_warnings():
    warnings.simplefilter("error")
    try:
        warnings.warn("old API", DeprecationWarning)
    except DeprecationWarning as w:
        print("raised:", w)
----
