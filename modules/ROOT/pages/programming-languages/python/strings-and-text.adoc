A Python `str` is an *immutable* sequence of Unicode code points -- every "modification" method returns
a *new* string, and text is always kept distinct from raw `bytes`. This page covers literals, the
methods you reach for daily, the three ways to format text, and the `str`/`bytes` split that underlies
all of it.

== String Literals, Immutability, Indexing and Slicing

Single and double quotes are interchangeable single-line literals; triple-quoted strings (`pass:c['''...'''+]` or
`+"""..."""+`) span multiple lines and are how docstrings are written. A `r` prefix makes a *raw* string,
where backslashes are kept literally -- essential for regular expressions and Windows paths -- while a
plain string interprets escape sequences such as `\n`, `\t`, and `\\`. Details are in the tutorial's
https://docs.python.org/3/tutorial/introduction.html#strings[Strings] section and the full escape-sequence
table in the lexical analysis reference's
https://docs.python.org/3/reference/lexical_analysis.html#string-and-bytes-literals[String and Bytes
literals]:

[source,python]
----
single = 'hello'
double = "hello"
triple = """line one
line two"""

path = r"C:\Users\name\docs"      # raw: backslashes are literal
escaped = "C:\\Users\\name\\docs"  # same characters, escaped manually
print(path == escaped)             # True
----

A `str` is a sequence type -- see
https://docs.python.org/3/library/stdtypes.html#text-sequence-type-str[Text Sequence Type --
str] -- so indexing and slicing work exactly like on a list, except the result of any slice is itself a
`str`. Because strings are immutable, indexed or sliced assignment is not possible; build a new string
instead:

[source,python]
----
word = "Python"
print(word[0])        # 'P'
print(word[-1])       # 'n'  (negative index counts from the end)
print(word[2:5])      # 'tho'
print(word[:3])       # 'Pyt'
print(word[::-1])     # 'nohtyP'  (reversed, via a step of -1)

# word[0] = "J"        # TypeError: 'str' object does not support item assignment
new_word = "J" + word[1:]
print(new_word)        # 'Jython'
----

== Common String Methods

Every method below returns a *new* string (or list); the original is never changed in place. The full
catalogue is under
https://docs.python.org/3/library/stdtypes.html#string-methods[String Methods]:

[source,python]
----
raw = "  Hello, World!  "

print(raw.strip())                    # 'Hello, World!'         (both ends)
print(raw.strip().lower())            # 'hello, world!'
print(raw.strip().upper())            # 'HELLO, WORLD!'

csv_line = "alice,30,engineer"
fields = csv_line.split(",")          # ['alice', '30', 'engineer']
print(fields)
print("-".join(fields))               # 'alice-30-engineer'

print(raw.strip().replace("World", "Python"))   # 'Hello, Python!'

print("report.CSV".endswith(".csv"))            # False: case-sensitive
print("report.CSV".lower().endswith(".csv"))    # True
print("report.csv".startswith("report"))        # True
----

== Formatting: f-strings, `.format()`, and `%`

=== f-strings (the modern default)

A *formatted string literal* -- an `f` prefix -- evaluates any expression inside `+{ }+` and inserts its
result. This is the preferred way to format text in modern Python; the grammar lives in the reference's
https://docs.python.org/3/reference/lexical_analysis.html#f-strings[Formatted string literals], and the
mini-language after a `:` (widths, alignment, precision, thousands separators, and so on) is the same
https://docs.python.org/3/library/string.html#format-spec-mini-language[Format Specification
Mini-Language] used by `.format()`:

[source,python]
----
name = "Ada"
age = 36
print(f"Hello, {name}! You are {age} years old.")   # Hello, Ada! You are 36 years old.
print(f"{age * 2}")                                  # 72 -- any expression is allowed

pi = 3.14159265
print(f"{pi:.2f}")            # '3.14'      -- fixed-point, 2 decimals
print(f"{1_000_000:,}")       # '1,000,000' -- thousands separator
print(f"{name:>10}")          # '       Ada' -- right-aligned in a width-10 field
----

Since Python 3.8, adding `=` after an expression prints both the *source text and its value* -- a quick
way to inline debug prints without writing the variable name twice:

[source,python]
----
count = 7
print(f"{count=}")            # count=7
print(f"{count * 2=}")        # count * 2=14
----

=== `.format()`

`str.format()` predates f-strings and is still common in code that assembles a template string
separately from the values (translated strings, logging templates). Positional and keyword placeholders
work the same way, documented at
https://docs.python.org/3/library/string.html#format-string-syntax[Format String Syntax]:

[source,python]
----
template = "{0} scored {1} points"
print(template.format("Ada", 95))              # Ada scored 95 points

template2 = "{name} scored {score} points"
print(template2.format(name="Ada", score=95))   # Ada scored 95 points

data = {"name": "Ada", "score": 95}
print(template2.format(**data))                 # Ada scored 95 points -- unpack a dict as keywords
----

=== `%`-formatting (legacy -- read, don't write)

The oldest style, borrowed from C's `printf`, is documented at
https://docs.python.org/3/library/stdtypes.html#printf-style-string-formatting[printf-style String
Formatting]. It still turns up in older codebases and logging calls, so it is worth recognizing, but new
code should prefer f-strings:

[source,python]
----
name = "Ada"
score = 95
print("%s scored %d points" % (name, score))   # Ada scored 95 points
----

== `str` vs. `bytes`: Unicode Fundamentals

Python 3 draws a hard line between *text* (`str`, a sequence of Unicode code points) and *binary data*
(`bytes`, a sequence of integers 0-255) -- there is no implicit conversion between them, unlike Python
2's blurred `str`/`unicode` split. The design rationale and history are in the
https://docs.python.org/3/howto/unicode.html[Unicode HOWTO]. Converting between the two is always
explicit: `.encode()` turns `str` into `bytes` using a named encoding (UTF-8 by default and the
overwhelming default in practice), and `.decode()` reverses it:

[source,python]
----
text = "café"                      # str: Unicode code points
encoded = text.encode("utf-8")     # bytes: b'caf\xc3\xa9'
print(encoded)
print(type(encoded))               # <class 'bytes'>

decoded = encoded.decode("utf-8")  # back to str
print(decoded)                     # café
print(decoded == text)             # True

# text + encoded                   # TypeError: can only concatenate str (not "bytes") to str
----

A `bytes` *literal* uses a `b` prefix and can only contain ASCII bytes; a mismatched encoding when
decoding raises rather than silently corrupting data:

[source,console]
----
>>> b"hello"
b'hello'
>>> "café".encode("ascii")
Traceback (most recent call last):
  ...
UnicodeEncodeError: 'ascii' codec can't encode character '\xe9' in position 3: ordinal not in range(128)
>>> "café".encode("utf-8").decode("ascii")
Traceback (most recent call last):
  ...
UnicodeDecodeError: 'ascii' codec can't decode byte 0xc3 in position 3: ordinal not in range(128)
----

Keeping `str` and `bytes` separate types -- rather than one type that is "text until it isn't" -- is
exactly what unified Python 3's text handling: a function that expects text can never be silently handed
undecoded bytes, and vice versa.

== Text Under the Hood: Unicode, Encodings, and Cost

A Python 3 `str` is an immutable sequence of Unicode *code points*, not bytes. How those code points are stored in memory
is an implementation choice (CPython picks 1, 2 or 4 bytes per character for the whole string, per
https://peps.python.org/pep-0393/[PEP 393]); what matters to programs is the boundary where text becomes bytes. That
boundary is an explicit `encode` call on the way out and a `decode` call on the way in.

[mermaid]
....
flowchart LR
    F["File, socket, or\nenvironment (bytes)"] -->|"decode('utf-8')"| S["str: sequence of\nUnicode code points"]
    S -->|"processing: slice,\nsearch, format"| S
    S -->|"encode('utf-8')"| B["bytes: sequence of\nintegers 0 to 255"]
    B --> O["File, socket, or\nsubprocess"]
    S -.->|"len counts code points,\nnot bytes or glyphs"| S
....

=== Code points, normalization, and encodings

Three different lengths hide behind "how long is this text": the number of bytes in some encoding, the number of code
points (what `len()` counts) and the number of user-perceived characters (grapheme clusters). The letter é can be one code
point or an `e` followed by a combining accent, and the two strings compare unequal until they are normalized with
`unicodedata.normalize`. UTF-8 is the encoding to use for files and the network; UTF-16 needs surrogate pairs for
characters beyond the Basic Multilingual Plane (such as emoji). The `errors=` argument decides what happens to data that
does not fit: `strict` (the default) raises, while `replace`, `ignore` and `backslashreplace` trade fidelity for
robustness.

[source,python]
----
import unicodedata

title = "Café Münch"                      # precomposed e-acute (U+00E9)
decomposed = "Café Münch"           # 'e' followed by a combining acute accent

print(title == decomposed, len(title), len(decomposed))
nfc = unicodedata.normalize("NFC", decomposed)
print(nfc == title, len(nfc))

for ch in "é€😀":
    print(f"{ch!r:>4} U+{ord(ch):04X} utf-8={ch.encode('utf-8')!r} utf-16 bytes={len(ch.encode('utf-16-le'))}")

print("straße".upper(), "straße".casefold() == "STRASSE".casefold())
print(unicodedata.name("é"), unicodedata.category("é"))

raw = "naïve".encode("utf-8")
print(raw, len(raw), raw.decode("utf-8"))
try:
    raw.decode("ascii")
except UnicodeDecodeError as exc:
    print("UnicodeDecodeError:", exc.reason, "at byte", exc.start)
print(raw.decode("ascii", errors="replace"), "naïve".encode("ascii", errors="backslashreplace"))
----

Practical rules: always pass `encoding="utf-8"` to `open()` instead of relying on the platform default (it differs
between Windows and Linux), compare user-entered text after `+normalize("NFC", ...)+`, and use `casefold()` rather than
`lower()` for case-insensitive comparison (note how `ß` becomes `ss`).

=== Immutability and the cost of building strings

Because strings cannot change, every "modification" produces a new string, and slicing copies characters. Building a long
string with repeated concatenation in a loop can therefore become quadratic on implementations that cannot reuse the
buffer; CPython has an optimisation for `pass:c[s += x]` when `s` has no other reference, but it is not guaranteed. The
portable idiom is to collect pieces in a list and call `"".join(pieces)` once. The sample below also shows the methods
that most often replace hand-written loops: `partition`, `rsplit`, `splitlines`, `strip` with a character set,
`startswith` with a tuple, and `translate`.

[source,python]
----

parts = [f"book-{n}" for n in range(2000)]

def concat():
    s = ""
    for p in parts:
        s += p + ","
    return s

def joined():
    return ",".join(parts) + ","

assert concat() == joined()
print("concat vs join produce the same text")

# Strings are immutable sequences: slicing copies, str methods return new strings
s = "bookshelf"
print(s[::-1], s[2:6], s[-4:], s.replace("book", "Book"), s)
t = s.partition("s")
print(t, s.rsplit("h", 1), s.startswith(("book", "shelf")))

# splitlines, strip with a character set, and translate
text = " \tLine one\r\nLine two\n\n"
print(text.splitlines(), repr(text.strip()), "xxhixx".strip("x"))
table = str.maketrans({"é": "e", "ü": "u"})
print("Café Münch".translate(table))
----

=== The format mini-language in practice

An f-string, `str.format` and the built-in `format()` all share one *format specification mini-language*:
`+[[fill]align][sign][#][0][width][,][.precision][type]+`. Because the specification can itself contain replacement
fields, widths can be computed at run time. The `!r` conversion applies `repr()` (invaluable in log messages and error
text, because it shows quotes and escapes), and `+{value=}+` prints both the expression and its value for quick debugging.
A table of bookshelf rows shows alignment, grouping, percentages, hexadecimal and dates formatted through
`+__format__+`:

[source,python]
----
from datetime import date

title, price, qty = "Dune", 9.5, 3
width = 12
print(f"{title:<{width}}|{price:>8.2f}|{qty:03d}|")   # nested replacement field for the width
print(f"{1234567.891:,.2f}  {0.256:.1%}  {255:#06x}  {255:b}  {1e-5:.2e}")
print(f"{title!r} {title!s} {title=}")
print(f"{date(2026, 3, 9):%d %B %Y}")
print(f"{{literal braces}} and {price * qty:.1f}")

rows = [("Dune", 3, 9.5), ("Emma", 12, 4.25), ("Ulysses", 1, 14.0)]
print(f"{'Title':<10}{'Qty':>5}{'Price':>9}")
for t, q, p in rows:
    print(f"{t:<10}{q:>5}{p:>9.2f}")

# the format mini-language is also available through format() and str.format
print(format(3.14159, ".3f"), "{:^9}".format("mid"), "{0}-{0}-{1}".format("a", "b"))
print("%-8s|%5.1f|%03d" % ("old", 2.25, 7))
----

Never build SQL, shell commands or HTML by formatting untrusted text into a string: use parameterised queries,
`subprocess` with an argument list, and an escaping template engine. The `+{value=}+` form needs Python 3.8 or newer.
