Python has no `+{+` `\}` block delimiters and no statement-terminating `;` -- *indentation itself* is
syntax, and a *style guide*, PEP 8, is close to normative for how the community writes code.

== Indentation-Based Blocks

C-family languages group statements with braces and largely ignore whitespace; Python instead uses the
*indentation* of a line to mark which block it belongs to, described in the language reference's
https://docs.python.org/3/reference/lexical_analysis.html#indentation[Indentation] section. A block (the
reference calls it a *suite*) is every consecutive line indented further than the `:` header that opens
it -- removing braces removes the possibility that indentation and block structure disagree:

[source,python]
----
def classify(n):
    if n > 0:
        sign = "positive"
    elif n < 0:
        sign = "negative"
    else:
        sign = "zero"
    return sign             # back at the function's own indentation: outside the if/elif/else

print(classify(-3))         # negative
----

Indentation must be *consistent within a block* -- every line of the same suite is indented by the same
amount, and a nested suite is indented further than its parent. Mixing tabs and spaces in a way that
makes the indentation ambiguous is a hard error, not a style nit:

[source,console]
----
>>> exec("if True:\n\tx = 1\n        y = 2\n")
Traceback (most recent call last):
  ...
TabError: inconsistent use of tabs and spaces in indentation
----

PEP 8 resolves the ambiguity before it can happen: use *spaces only*, four per level, and never mix tabs
into space-indented code -- see <<pep-8>> below.

== Comments and Statement Separators

A `+#+` starts a comment that runs to the end of the physical line; there is no block-comment syntax.
Statements normally end at a newline (the reference's
https://docs.python.org/3/reference/lexical_analysis.html#implicit-line-joining[implicit line joining]
and explicit joining rules cover the exceptions below), and `;` chains multiple statements onto one
physical line:

[source,python]
----
# Adjust for tax, then round to the nearest cent.
price = 19.99
total = price * 1.08; total = round(total, 2)   # two statements, one line
print(total)
----

Putting more than one statement per line with `;` is legal but discouraged by PEP 8 outside of
throwaway scripts -- prefer one statement per line.

A long logical line can be split across physical lines two ways. *Explicit* continuation uses a
trailing `\`:

[source,python]
----
total = 1 + 2 + 3 + \
        4 + 5 + 6
print(total)   # 21
----

*Implicit* continuation happens automatically inside any unclosed `(`, `[`, or `+{+` -- this is the
preferred style, since nothing breaks if a line is reordered and a trailing space after `\` cannot
silently break the continuation:

[source,python]
----
totals = [
    1 + 2 + 3,
    4 + 5 + 6,
]
config = {
    "host": "localhost",
    "port": 5432,
}
print(totals, config)
----

Note that the `+{ }+` above are *dict* literal delimiters, not block syntax -- Python does use braces
for dict and set literals and for f-string placeholders, just never to mark a block of statements.

== PEP 8: The Style Guide

https://peps.python.org/pep-0008/[PEP 8] is the standard library's own style guide and the de facto
convention for almost all Python code. It is short and worth reading directly rather than restated in
full here; the highlights that show up in nearly every file:

=== Naming

* `snake_case` for functions, methods, variables, and modules.
* `PascalCase` (PEP 8 calls it `CapWords`) for classes.
* `UPPER_CASE` for constants.
* A leading underscore (`+_name+`) signals "internal use"; a trailing underscore (`+name_+`) avoids clashing
  with a keyword.

[source,python]
----
MAX_RETRIES = 3               # constant: UPPER_CASE

class HttpClient:              # class: PascalCase
    def send_request(self, url):   # method: snake_case
        attempt_count = 0           # variable: snake_case
        while attempt_count < MAX_RETRIES:
            attempt_count += 1
        return attempt_count

print(HttpClient().send_request("https://example.com"))
----

=== Line Length and Whitespace

PEP 8 recommends limiting lines to *79 characters* (72 for flowing text like docstrings and comments),
one space around binary operators, no space just inside parentheses/brackets, and no space before a `,`
`;` or `:`:

[source,python]
----
# PEP 8 style
result = (first_value + second_value) * scale_factor
items = [1, 2, 3]
lookup = {"a": 1, "b": 2}

# discouraged: cramped and inconsistent spacing
result=(first_value+second_value)*scale_factor
items = [1,2,3]
lookup = {"a" :1,"b":2}
----

=== Import Ordering

Imports go at the top of the file, one per line, grouped in this order with a blank line between
groups: standard library, third-party packages, then local application imports:

[source,python]
----
import os
import sys

import requests

from mypackage import utils
----

== `import this`: The Zen of Python

Python ships an actual Easter egg that doubles as a one-page design-philosophy summary: importing the
`this` module prints *the Zen of Python* (PEP 20), referenced from the tutorial's own
https://docs.python.org/3/tutorial/controlflow.html#intermezzo-coding-style[Intermezzo: Coding Style]
section as the spirit behind PEP 8 itself:

[source,console]
----
>>> import this
The Zen of Python, by Tim Peters

Beautiful is better than ugly.
Explicit is better than implicit.
Simple is better than complex.
...
Readability counts.
...
There should be one-- and preferably only one --obvious way to do it.
...
----

The indentation rule and PEP 8 are direct expressions of a few of those lines: *readability counts*, and
there should be *one obvious way* to lay out a block -- rather than the many equivalent brace-and-indent
styles other languages tolerate.

== How Python Reads Your Source

Before parsing, the tokenizer turns the text into tokens: names, numbers, strings, operators, `NEWLINE` at the end of each
logical line, and two synthetic tokens that make Python's blocks work, `INDENT` and `DEDENT`. The tokenizer keeps a *stack
of indentation widths*. A line indented more than the top of the stack pushes it and emits `INDENT`; a line indented less pops
until it matches and emits one `DEDENT` per pop; a dedent to a width that is not on the stack is an
`IndentationError`. That is all that "indentation is syntax" means: it is the brace-free spelling of the same block
structure.

[mermaid]
....
flowchart TD
    A["New logical line"] --> B{"Blank or comment only?"}
    B -- Yes --> Z["Ignore for indentation"]
    B -- No --> C{"Width compared with\ntop of the indent stack"}
    C -- "Greater" --> D["Push width, emit INDENT"]
    C -- "Equal" --> E["No token"]
    C -- "Smaller" --> F{"Width on the stack?"}
    F -- Yes --> G["Pop until it matches,\nemit one DEDENT per pop"]
    F -- No --> H["IndentationError:\nunindent does not match"]
....

The sample prints the synthetic tokens for a small function, shows the two ways to continue a logical line over several
physical lines, and demonstrates what happens with ambiguous tabs and spaces:

[source,python]
----
import io
import keyword
import tokenize
import unicodedata

source = (
    "def late(days):\n"
    "    if days > 0:\n"
    "        return days * 2   # fine\n"
    "    return 0\n"
)
names = [tokenize.tok_name[t.type] for t in tokenize.generate_tokens(io.StringIO(source).readline)]
print([n for n in names if n in ("INDENT", "DEDENT", "NEWLINE", "COMMENT")])
print(names.count("INDENT"), names.count("DEDENT"))      # the indentation stack: pushes and pops

# implicit and explicit line joining
total = (1 +
         2 +
         3)
also = 1 + \
       2
print(total, also)

# mixing tabs and spaces ambiguously is an error, not a guess
bad = "if True:\n\tx = 1\n        y = 2\n"
try:
    compile(bad, "<demo>", "exec")
except TabError as exc:
    print("TabError:", exc.msg)

# identifiers are Unicode, normalised with NFKC
print("naïve".isidentifier(), "2fast".isidentifier(), "class".isidentifier(), keyword.iskeyword("class"))
ﬁle = 1                                                    # U+FB01 'fi' ligature normalises to 'fi'
print(file, unicodedata.normalize("NFKC", "ﬁle"))

# in 3.10+ match is a soft keyword: still an ordinary name outside a match statement
match = 3
print(match + 1)
----

=== Rules and consequences

* *Line joining.* Inside any pair of brackets a line may continue freely, which is the preferred way to wrap long expressions
  (the style guide discourages the backslash, which breaks if a space follows it). A backslash joins the next line
  explicitly.
* *Tabs and spaces.* Python 3 refuses to guess when indentation mixes them inconsistently (`TabError`); configure the editor to
  insert four spaces and never mix. Blocks must be consistent within themselves, not across the whole file.
* *Identifiers* are Unicode letters, digits and underscores, not starting with a digit, and are normalised (NFKC) when
  parsed, so `ﬁle` and `file` are the same name. Non-ASCII identifiers are legal but rarely wise in shared code; they
  also enable look-alike names, so keep to ASCII for public APIs.
* *Keywords* cannot be used as names (`keyword.kwlist` lists them). Since 3.10, `match`, `case` and `+_+` are *soft* keywords
  that only act as keywords in a `match` statement, so older code that uses `match` as a variable still works.
* *Statements and comments.* A statement ends at the end of the logical line, and `;` separates several on one line, which
  style guides discourage. A comment runs from `+#+` to the end of the line; it is a token the parser discards, so,
  unlike a docstring, it is not available at run time.

=== Style as a tool, not a taste

PEP 8 matters because a codebase read by many people is read far more often than it is written, and consistent layout lets
a reader see structure instead of formatting. In practice you do not enforce style by hand: let a formatter (Black or
`ruff format`) decide layout so reviews never argue about it, and let a linter (Ruff, Flake8 or pylint) catch
problems that formatting cannot, such as unused imports, shadowed built-ins (`list = []`), mutable default arguments, and
names that break the conventions (`snake_case` for functions and variables, `CapWords` for classes, `UPPER_CASE` for
constants, a leading underscore for "internal"). Configure both in `pyproject.toml` and run them in a pre-commit hook and in
continuous integration (see xref:programming-languages/python/debugging-and-tooling.adoc[Debugging and Tooling]).
