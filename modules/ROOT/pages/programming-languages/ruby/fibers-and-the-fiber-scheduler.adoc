A *fiber* is a block of code that can be paused and resumed, with its own stack, that runs on the thread that resumed it and gives up
control only when the program says so. Nothing preempts a fiber and nothing runs two fibers at the same time, which makes fibers the
smallest of Ruby's concurrency tools: a way to write generators, coroutines and pipelines as straight-line code, and, since Ruby 3.0, the
building block of *non-blocking I/O*, where a *fiber scheduler* switches to another fiber whenever one would wait.

fiber and the `FiberError` cases, fibers as generators (and the fibers hidden inside `Enumerator#next`), exceptions, `Fiber#raise` and
`Fiber#kill`, `resume` against `transfer`, and the three kinds of per-execution state: `+Thread#[]+` variables, thread variables and
fiber storage. The second half is the scheduler interface: what makes a fiber non-blocking, the hooks Ruby calls, a complete working
scheduler of about a hundred lines, the operations that do and do not reach the scheduler, timeouts, closing an IO that a fiber is
waiting on, how `Mutex`, `Queue` and `Monitor` behave under a scheduler, and the community schedulers (the `async` gem and the Falcon web
server) that people use in practice.

== Fibers, threads, Ractors and processes

[[concurrency-models]]
Ruby has four ways to do more than one thing at a time. They differ in who decides when to switch and whether Ruby code really runs in
parallel.

[cols="2,3,3,3,3",options="header"]
|===
| | Thread | Fiber | Ractor | Process

| Who switches
| The VM, preemptively (a time slice, or when a thread blocks)
| The program: `resume`, `Fiber.yield`, `transfer`, or a scheduler hook when a non-blocking fiber would block
| The VM, preemptively; each Ractor has its own threads
| The operating system

| Ruby code in parallel
| No, one thread at a time holds the GVL
| No, a fiber runs on the thread that resumed it
| Yes, Ractors do not share the lock
| Yes

| Shares objects
| Everything
| Everything on its thread
| Only shareable objects; others are moved or copied
| Nothing (copies, pipes, files)

| Mutable shared state needs
| `Mutex`, `Queue`, `Monitor`
| Nothing between switches; locks only where a switch can happen inside the critical section
| Messages through ports
| Pipes, sockets, files

| Typical use
| Blocking I/O in parallel, background work
| Generators, coroutines, lazy pipelines, event-loop concurrency for thousands of connections
| CPU-bound parallel work
| Isolation, CPU-bound parallel work, the `fork` model of servers
|===

The *GVL* (global VM lock, also called the GIL) is the reason threads do not make pure Ruby CPU work parallel; it is explained in
xref:programming-languages/ruby/threads-and-the-gvl.adoc[Threads and the GVL]. A fiber needs no lock because two fibers of one thread
can never run at once: control moves only at explicit points. That is both the strength and the limit of fibers. A fiber that never
reaches a switching point (a long computation, a blocking call the scheduler does not know) stops every other fiber on its thread.

The official guide describes fibers as primitives for lightweight cooperative concurrency: code blocks that can be paused and resumed,
which are never preempted and whose scheduling is the programmer's job, not the VM's. Unlike stackless coroutines in
other languages, each Ruby fiber comes with a stack, so a fiber can be paused from deep inside nested method calls.

Source: https://docs.ruby-lang.org/en/4.0/Fiber.html[Ruby 4.0 documentation: Fiber]

== Creating and driving a fiber

=== Fiber.new, resume and Fiber.yield

`Fiber.new` takes a block and returns a fiber in the *created* state; the block does not run. `fiber.resume` starts it, or continues it
from the point where it last called `Fiber.yield`. Values travel both ways:

* the arguments of the *first* `resume` become the block parameters;
* the arguments of a *later* `resume` become the value of the `Fiber.yield` expression the fiber is paused at;
* the argument of `Fiber.yield` becomes the value of the `resume` call that is waiting;
* when the block finishes, its last expression becomes the value of the final `resume`.

Several arguments to `resume` or `Fiber.yield` arrive as an Array on the other side, no arguments as `nil`, exactly like block
parameters. A fiber can be resumed only until the block ends; after that `alive?` is `false` and another `resume` raises `FiberError`.

image::ruby-fiber-resume-yield.svg["Swim-lane diagram of a caller and a fiber: Fiber.new creates the fiber, resume(10) starts the block, Fiber.yield(11) hands 11 back to resume, resume(20) continues the fiber, the block returns :finished and a further resume raises FiberError",width=940]

[source,ruby]
----
# frozen_string_literal: true

# A fiber does not run until it is resumed.
fiber = Fiber.new do |first|
  puts "started with #{first.inspect}"
  second = Fiber.yield(first + 1)
  puts "resumed with #{second.inspect}"
  third = Fiber.yield(second * 2)
  puts "resumed again with #{third.inspect}"
  :finished
end

fiber.alive?     # => true
fiber.resume(10) # => 11
fiber.resume(20) # => 40
fiber.resume(30) # => :finished
fiber.alive?     # => false

begin
  fiber.resume
rescue FiberError => e
  e.message # => "attempt to resume a terminated fiber"
end
----

Running the file prints what the block says while it runs; every `resume` returns the value of the next `Fiber.yield` (or the block value
for the last one):

[source,text]
----
started with 10
resumed with 20
resumed again with 30
----

Source: https://docs.ruby-lang.org/en/4.0/Fiber.html#method-i-resume[Fiber#resume]; https://docs.ruby-lang.org/en/4.0/Fiber.html#method-c-yield[Fiber.yield]; https://docs.ruby-lang.org/en/4.0/Fiber.html#method-i-alive-3F[Fiber#alive?]

A few details that surprise people:

* `Fiber.new` without a block raises `ArgumentError` (`tried to create Proc object without a block`).
* The block's local variables belong to the fiber, and it can also read and change the local variables of the scope it was created in,
  like any block (closures are covered in xref:programming-languages/ruby/blocks-procs-and-lambdas.adoc[Blocks, Procs and Lambdas]).
* `Fiber.yield` outside any fiber (from the main fiber) is an error, not a no-op.
* The arguments of `Fiber.yield` and of `resume` follow block-parameter rules, including keyword arguments: `+Fiber.new { |*args, **options| ... }+`
  receives `resume(1, key: 2)` as `[1]` and `+{key: 2}+`.
* `Fiber.current` returns the running fiber. On the main thread outside of any `Fiber.new` it returns the *root fiber*, which exists
  for every thread and is always a blocking fiber (see <<blocking-fibers,Blocking and non-blocking fibers>>).

=== States and inspect

A fiber is *created* (never resumed), *resumed* (running, or waiting for a fiber it resumed), *suspended* (paused in `Fiber.yield` or
`transfer`) or *terminated* (the block ended or an exception escaped). `Fiber#alive?` is `true` for the first three. The state is the last
word of `Fiber#inspect` and `Fiber#to_s`, together with the file and line of the block:

[source,ruby]
----
# frozen_string_literal: true

# Fiber#inspect ends with the state: "#<Fiber:0x... file.rb:5 (created)>".
state = ->(fiber) { fiber.inspect[/\((.+)\)>\z/, 1] }

fiber = Fiber.new { Fiber.yield 1 }
state.call(fiber)         # => "created"
fiber.resume              # => 1
state.call(fiber)         # => "suspended"
fiber.resume              # => nil
state.call(fiber)         # => "terminated"
state.call(Fiber.current) # => "resumed"
fiber.alive?              # => false
----

Source: https://docs.ruby-lang.org/en/4.0/Fiber.html#method-i-to_s[Fiber#to_s]; https://docs.ruby-lang.org/en/4.0/Fiber.html#method-c-current[Fiber.current]

=== FiberError: what can go wrong

Every illegal switch raises `FiberError`, a `StandardError`. The messages were collected on Ruby 4.0.7; they are worth recognising because they are
the only hint of which rule was broken:

[source,ruby]
----
# frozen_string_literal: true

def message
  yield
rescue FiberError => e
  e.message
end

done = Fiber.new { 1 }
done.resume
message { done.resume } # => "attempt to resume a terminated fiber"
message { Fiber.yield } # => "attempt to yield on a not resumed fiber"

me = Fiber.new { me.resume }
message { me.resume } # => "attempt to resume the current fiber"

outer = Fiber.new { Fiber.new { outer.resume }.resume }
message { outer.resume } # => "attempt to resume a resumed fiber (double resume)"

suspended = Fiber.new { Fiber.yield }
suspended.resume
other_thread = Thread.new { message { suspended.resume } }
other_thread.value # => "fiber called across threads"

message { suspended.transfer } # => "attempt to transfer to a yielding fiber"
message { done.transfer } # => "dead fiber called"
message { Fiber.new { 1 }.raise("boom") } # => "cannot raise exception on unborn fiber"
----

Source: https://docs.ruby-lang.org/en/4.0/FiberError.html[FiberError]; https://docs.ruby-lang.org/en/4.0/Fiber.html#method-i-resume[Fiber#resume]; https://docs.ruby-lang.org/en/4.0/Fiber.html#method-i-transfer[Fiber#transfer]

Two rules sit behind the list. A fiber belongs to the thread that created it: resuming it, killing it or raising into it from another
thread is a `FiberError`. And control has a direction: a fiber that is already running (the current one, or one waiting in the chain of
`resume` calls that led to the current fiber) cannot be resumed again.

=== Backtraces

`Fiber#backtrace` (Ruby 3.0) returns the stack of a *suspended* fiber, with the innermost frame (the `Fiber.yield` itself) first; it takes
the same `start`, `count` and range arguments as `Kernel#caller`. `Fiber#backtrace_locations` returns the same frames as
`Thread::Backtrace::Location` objects. A fiber that has not started yet, or has finished, has an empty stack:

[source,ruby]
----
# frozen_string_literal: true

def inner = Fiber.yield
def outer = inner

fiber = Fiber.new { outer }
fiber.backtrace # => []

fiber.resume
fiber.backtrace
# => ["fiber_backtrace.rb:3:in 'Fiber.yield'",
#     "fiber_backtrace.rb:3:in 'Object#inner'",
#     "fiber_backtrace.rb:4:in 'Object#outer'",
#     "fiber_backtrace.rb:6:in 'block in <main>'"]
fiber.backtrace(1, 2).first # => "fiber_backtrace.rb:3:in 'Object#inner'"

location = fiber.backtrace_locations.first
[location.label, location.lineno] # => ["Fiber.yield", 3]

fiber.resume
fiber.backtrace # => []
----

The reference page for the method says a finished fiber returns `nil`; Ruby 4.0.7 returns an empty Array for both unstarted and finished
fibers, so test with `empty?` rather than `nil?`.

Source: https://docs.ruby-lang.org/en/4.0/Fiber.html#method-i-backtrace[Fiber#backtrace]; https://docs.ruby-lang.org/en/4.0/Fiber.html#method-i-backtrace_locations[Fiber#backtrace_locations]

=== Fibers are cheap, but each has a stack

A fiber is far lighter than a thread (no operating-system thread is created and switching is a function-call-sized operation), but each
fiber owns a VM stack and a machine stack. Both are smaller than a thread's, so deep recursion that works on the main thread can raise
`SystemStackError` (`stack level too deep`) inside a fiber. Three environment variables from the `ruby(1)` manual page tune this (all values in bytes):

[cols="3,4,2",options="header"]
|===
| Variable | Meaning | Default (64-bit)
| `RUBY_FIBER_VM_STACK_SIZE` | VM stack of each fiber: the stack used by Ruby code | 131072
| `RUBY_FIBER_MACHINE_STACK_SIZE` | Machine (C) stack of each fiber: used by the operating system and C extensions | 524288
| `RUBY_SHARED_FIBER_POOL_FREE_STACKS` | `1` frees the stacks of pooled fibers, `0` does not (introduced in 2.7) | 1
|===

Lower values allow more fibers at the price of a higher chance of `SystemStackError` and, for the machine stack, of segmentation faults;
the threads have their own pair of variables (`RUBY_THREAD_VM_STACK_SIZE` and `RUBY_THREAD_MACHINE_STACK_SIZE`, one mebibyte by default on
64-bit CPUs). The next file measures how deep a method can recurse in the main thread, in a thread and in a fiber:

[source,ruby]
----
# frozen_string_literal: true

# How deep can a method recurse before SystemStackError?
def depth(level = 0)
  depth(level + 1)
rescue SystemStackError
  level
end

in_main = depth
in_thread = Thread.new { depth }.value
in_fiber = Fiber.new { depth }.resume

puts "main=#{in_main} thread=#{in_thread} fiber=#{in_fiber}"
puts in_fiber < in_main
----

On the test machine it printed the first block below; running it again with a larger fiber VM stack gives the second one. The absolute
depths depend on the machine and the Ruby build, only the ratio matters:

[source,text]
----
$ ruby -w fiber_stack.rb
main=10917 thread=10917 fiber=1360
true
$ RUBY_FIBER_VM_STACK_SIZE=524288 ruby -w fiber_stack.rb
main=10917 thread=10917 fiber=5456
true
----

Source: https://docs.ruby-lang.org/en/4.0/Fiber.html[Fiber] (it refers to the `ruby(1)` manual page for the fiber stack sizes); the variables are listed in the `ruby(1)` manual page installed with Ruby (`man ruby`).

On the test machine, creating and finishing 100000 trivial fibers in a loop took about half a second, which is why fibers are used for
one-per-connection or one-per-request designs; measure before relying on any such number, and see
xref:programming-languages/ruby/performance-benchmarking-and-profiling.adoc[Performance, Benchmarking and Profiling] for how.

== Fibers as generators

The most common use of the plain `resume`/`yield` pair is a *generator*: code that produces a sequence one item at a time and remembers
where it stopped, without building the whole sequence or hand-writing a state machine. The loop and the local variables of the
generator are simply the state of the paused fiber.

[source,ruby]
----
# frozen_string_literal: true

module Shelf
  Book = Data.define(:isbn, :title)
end

# An infinite generator: a fiber that hands out shelf marks on demand.
marks = Fiber.new do
  number = 0
  loop { Fiber.yield format("SH-%04d", number += 1) }
end

marks.resume                    # => "SH-0001"
Array.new(2) { marks.resume }   # => ["SH-0002", "SH-0003"]

# A finite generator: the fiber ends when its block returns.
books = [
  Shelf::Book.new("9780441172719", "Dune"),
  Shelf::Book.new("9780345339683", "The Hobbit"),
  Shelf::Book.new("9780261102217", "The Fellowship of the Ring")
]
pages = Fiber.new do
  books.each_slice(2) { |page| Fiber.yield page.map(&:title) }
  nil
end

titles = []
while (page = pages.resume)
  titles << page
end
titles.map(&:size) # => [2, 1]
titles.flatten.last # => "The Fellowship of the Ring"
pages.alive? # => false

# The same infinite generator as an Enumerator, which is built on a fiber.
issuer = Enumerator.new do |yielder|
  number = 0
  loop { yielder << format("SH-%04d", number += 1) }
end
issuer.next        # => "SH-0001"
issuer.peek        # => "SH-0002"
issuer.take(2)     # => ["SH-0001", "SH-0002"]
issuer.lazy.map(&:downcase).first(2) # => ["sh-0001", "sh-0002"]
----

Source: https://docs.ruby-lang.org/en/4.0/Fiber.html[Fiber]; https://docs.ruby-lang.org/en/4.0/Enumerator.html[Enumerator]

Notes on the example:

* The first generator never ends, so it has no terminating `nil`; callers take as many marks as they need.
* The second generator ends by returning from the block. The last `resume` returns the block's value (`nil` here), which the `while`
  loop uses as the end marker. Using a value such as `nil` as a sentinel works only if `nil` is never a real item; use `alive?` or a
  dedicated sentinel when it could be.
* In real code, prefer `Enumerator.new` (the last part of the example). It provides `next`, `peek`, `rewind`, `size`, `take`, `lazy`
  and all of `Enumerable`, reports the end with `StopIteration` instead of `FiberError`, and can be consumed both externally and
  internally. The `Fiber` version is what you write when you need to *drive the switching yourself* or to exchange data in both directions.

=== The fibers inside Enumerator#next

An `Enumerator` is not itself a fiber, but its *external iteration* methods (`next`, `peek`, `next_values`, `peek_values`) are implemented
with one: the first call creates a fiber that runs the enumerator's block, and each `next` resumes it until the next value is yielded.
Internal iteration (`each`, `map`, `to_a`, `take`, ...) runs the block directly in the caller's fiber with no fiber involved. The two
styles are therefore *not equivalent* in everything they observe, and the most common surprise is fiber-local state:

[source,ruby]
----
# frozen_string_literal: true

main = Fiber.current
Thread.current[:branch] = "Central" # fiber-local, despite the Thread receiver

where = Enumerator.new do |yielder|
  yielder << Fiber.current.equal?(main)
  yielder << Thread.current[:branch]
end

# Internal iteration (each, to_a, map ...) runs the block in the caller's fiber.
where.to_a # => [true, "Central"]

# External iteration (next, peek) runs it in a fiber of its own.
where.next # => false
where.next # => nil

# The end of the sequence raises StopIteration, which loop rescues.
begin
  where.next
rescue StopIteration => e
  e.message # => "iteration reached an end"
end

where.rewind.next # => false
----

Source: https://docs.ruby-lang.org/en/4.0/Enumerator.html#method-i-next[Enumerator#next]; https://docs.ruby-lang.org/en/4.0/Enumerator.html#method-i-peek[Enumerator#peek]; https://docs.ruby-lang.org/en/4.0/Enumerator.html#method-i-rewind[Enumerator#rewind]

`Thread.current[:branch]` returned `nil` under `next` because `+Thread#[]+` is *fiber-local* (see <<fiber-local-state,Fiber-local state>>
below). The same effect hides in libraries that keep a "current request" or "current connection" in `+Thread.current[...]+` and are then
used from an enumerator. Other consequences of the fiber behind `next`: the enumerator keeps its stack alive until it finishes or is
garbage collected, `Fiber.current` inside the block differs, and the fiber cannot cross threads (an enumerator advanced with `next` in one
thread and again in another raises `FiberError`). The lazy variants and the full set of enumerator methods are in
xref:programming-languages/ruby/enumerators-and-lazy-evaluation.adoc[Enumerators and Lazy Evaluation].

== Exceptions, Fiber#raise and Fiber#kill

An exception that is not rescued inside the fiber's block ends the fiber (it becomes *terminated*) and is raised again by the `resume`
that was running it, with the fiber's backtrace. Two methods let the *outside* push an exception or an end into a suspended fiber:

* `Fiber#raise` raises an exception *inside* the fiber at the point where it is paused: at the `Fiber.yield` for a suspended fiber (and
  at the `transfer` or scheduler wait for others). The fiber can rescue it and carry on, in which case `raise` returns what the next
  `Fiber.yield` returns, like a `resume` would. On a fiber that never started it raises `FiberError`, and on a terminated one too. It takes the
  same arguments as `Kernel#raise`; since Ruby 4.0 that includes `cause:`, and since Ruby 3.4 an Array of `Thread::Backtrace::Location`
  as the backtrace (on Ruby 3.4 and older `cause:` is read as the backtrace argument and raises `TypeError`).
* `Fiber#kill` (Ruby 3.3) terminates a fiber by raising an uncatchable exception in it: `ensure` clauses run, `rescue` clauses do not
  catch it. A fiber that never started goes straight to terminated. Calling it on the *current* fiber raises at that call site. Like
  all cross-fiber operations it raises `FiberError` for a fiber of another thread. In 4.0.7 it returns the fiber (the reference page lists
  `nil`), so do not depend on its return value.

[source,ruby]
----
# frozen_string_literal: true

module Shelf
  class Error < StandardError; end
end

# An exception that escapes the block ends the fiber and reaches the resumer.
failing = Fiber.new { raise Shelf::Error, "catalogue offline" }
begin
  failing.resume
rescue Shelf::Error => e
  [e.message, failing.alive?] # => ["catalogue offline", false]
end

# Fiber#raise raises at the point of the last Fiber.yield.
worker = Fiber.new do
  Fiber.yield :waiting
rescue Shelf::Error => e
  "recovered from #{e.message}"
end
worker.resume # => :waiting
worker.raise(Shelf::Error, "disk full") # => "recovered from disk full"
worker.alive? # => false

# Ruby 4.0: Fiber#raise accepts cause:.
sleeper = Fiber.new { Fiber.yield }
sleeper.resume
begin
  sleeper.raise(Shelf::Error, "lookup failed", cause: IOError.new("socket closed"))
rescue Shelf::Error => e
  e.cause # => #<IOError: socket closed>
end

# Fiber#kill (Ruby 3.3) ends a suspended fiber and runs its ensure clauses.
log = []
cleaner = Fiber.new do
  Fiber.yield
ensure
  log << "ensure ran"
end
cleaner.resume
cleaner.kill.alive? # => false
log.first # => "ensure ran"

# A fiber that never started is simply marked as finished.
unborn = Fiber.new { raise "never runs" }
unborn.kill.alive? # => false

# Raising into a fiber that never started is an error.
begin
  Fiber.new { 1 }.raise("too early")
rescue FiberError => e
  e.message # => "cannot raise exception on unborn fiber"
end
----

Source: https://docs.ruby-lang.org/en/4.0/Fiber.html#method-i-raise[Fiber#raise]; https://docs.ruby-lang.org/en/4.0/Fiber.html#method-i-kill[Fiber#kill]; https://docs.ruby-lang.org/en/4.0/NEWS_md.html[Ruby 4.0.0 NEWS]

`Fiber#kill` is the clean way to cancel a generator that is no longer needed: a fiber left suspended is not an error, but its `ensure`
blocks (closing a file, releasing a lock) are not run by abandoning it: in an experiment on 4.0.7 the `ensure` of a dropped suspended fiber
did not run even after `GC.start`. Under a scheduler the
scheduler itself uses `Fiber#raise` to implement timeouts and to interrupt waits when an IO is closed (see
<<timeouts-and-close,Timeouts and IO#close>>).

== resume versus transfer

`Fiber#transfer` hands control directly to another fiber instead of returning to whoever resumed you. `resume`/`Fiber.yield` form an
*asymmetric* pair (a fiber always gives control back to its resumer, so the fibers form a stack, like method calls); `transfer` is
*symmetric* (any fiber may pass control to any other, so the fibers form an arbitrary graph, like `goto` between coroutines). The rules,
from the reference page and checked by running them:

* The two styles cannot be mixed freely on one fiber. A fiber *started by `transfer`* can never `Fiber.yield` or be continued with `resume`; it can
  only `transfer` onward or finish. A fiber *started by `resume`* can `Fiber.yield` or `transfer` away, and gets control back only the
  way it gave it up: a `Fiber.yield` is continued by `resume`, a `transfer` by `transfer`.
* Breaking a rule raises `FiberError`: `attempt to transfer to a yielding fiber`, `attempt to resume a transferring fiber`, `attempt to yield on a not resumed fiber`.
* When a fiber that was entered by `transfer` finishes, control returns to the *main fiber* of the thread (the root fiber), together with the
  fiber's final value.
* Ruby 3.0 relaxed the older, stricter limitations of `transfer` (Bug #17221).

`resume`/`yield` is simpler for a single fiber ("give control away, I don't care to whom"); `transfer` is what a scheduler or a
state-machine runner needs. The next example is a tiny dispatcher: the main fiber hands a turn to each of three branch fibers in a
round, and each branch hands control back with `dispatcher.transfer` and is later continued with `transfer` again.

[source,ruby]
----
# frozen_string_literal: true

dispatcher = Fiber.current
log = []

branches = %w[Central Harbour Airport].map do |name|
  Fiber.new do |round|
    log << "#{name} opens in round #{round}"
    log << "#{name} serves a patron"
    dispatcher.transfer          # hand control back, ask to be continued
    log << "#{name} closes"
    :ignored                     # a finished transferred fiber returns to the main fiber
  end
end

2.times do |round|
  branches.each { |branch| branch.transfer(round) if branch.alive? }
end

puts log
branches.none?(&:alive?) # => true
----

[[fiber-local-state]]
== Fiber-local, thread-local and fiber storage

Ruby has three places to keep "current context" data, and they differ in how far the data is visible. Getting this wrong is the usual
way fibers leak or lose state.

[cols="3,3,4",options="header"]
|===
| Mechanism | Scope | Notes
| `+Thread.current[:key]+` (`+Thread#[]+`, `+Thread#[]=+`) | The current *fiber* | Despite the receiver, each fiber has its own set. `Thread#key?` and `Thread#keys` see only the current fiber's keys.
| `Thread#thread_variable_get` / `thread_variable_set` | The whole *thread*, all of its fibers | Not inherited by new threads.
| `+Fiber[:key]+`, `+Fiber[:key] = value+`, `Fiber.new(storage:)` (Ruby 3.2) | The *execution context*: inherited by fibers and threads created from it | A new fiber or thread gets a *shallow copy* of the creator's storage.
|===

[source,ruby]
----
# frozen_string_literal: true

Thread.current[:request_id] = "r-1"                  # fiber-local, in spite of the name
Thread.current.thread_variable_set(:locale, :en)     # really thread-local
Fiber[:user] = "ico"                                 # fiber storage (Ruby 3.2)

peek = -> { [Thread.current[:request_id], Thread.current.thread_variable_get(:locale), Fiber[:user]] }

peek.call                  # => ["r-1", :en, "ico"]
Fiber.new(&peek).resume    # => [nil, :en, "ico"]
Thread.new(&peek).value    # => [nil, nil, "ico"]

Fiber.new { Thread.current[:request_id] }.resume # => nil
Thread.current.key?(:request_id)                 # => true
Thread.current.keys                              # => [:request_id]
----

Source: https://docs.ruby-lang.org/en/4.0/Thread.html#method-i-5B-5D[Thread: element reference]; https://docs.ruby-lang.org/en/4.0/Thread.html#method-i-thread_variable_get[Thread#thread_variable_get]; https://docs.ruby-lang.org/en/4.0/Fiber.html#method-c-5B-5D[Fiber: element reference]

*Fiber storage* (Ruby 3.2) exists because both older mechanisms are awkward. Thread-locals are shared by every fiber of a thread, which
makes it impossible to isolate two requests served by two fibers of one thread; fiber-locals are isolated but are not inherited by the
fibers and threads created to do part of the same job, so a request id set in the handler is lost in the helper. The 3.2 NEWS suggests
storage for state shared implicitly by everything created in a context: a request id, a logger level, a connection pool, configuration.

[source,ruby]
----
# frozen_string_literal: true

Fiber[:user] = "ico"
Fiber[:tags] = []

# A new fiber (or thread) inherits a shallow copy of the storage.
child = Fiber.new do
  Fiber[:user] = "zelda"       # changes the copy only
  Fiber[:tags] << "seen"       # the Array itself is shared
  [Fiber[:user], Fiber[:tags]]
end
child.resume # => ["zelda", ["seen"]]
Fiber[:user] # => "ico"
Fiber[:tags] # => ["seen"]

# storage: nil starts empty, storage: {...} starts with exactly that hash.
Fiber.new(storage: nil) { Fiber[:user] }.resume                  # => nil
Fiber.new(storage: { user: "link" }) { Fiber[:user] }.resume     # => "link"
Thread.new { Fiber[:user] }.value                                # => "ico"

# Assigning nil removes the key; storage returns a copy of the Hash.
Fiber[:tags] = nil
Fiber.current.storage # => {user: "ico"}

# Keys are Symbols; storage can only be read from the fiber that owns it.
begin
  Fiber[1]
rescue TypeError => e
  e.message # => "1 is not a symbol nor a string"
end

begin
  Fiber.new { 1 }.storage
rescue ArgumentError => e
  e.message # => "Fiber storage can only be accessed from the Fiber it belongs to"
end

begin
  Fiber.new(storage: { "user" => "ico" }) { 1 }
rescue TypeError => e
  e.message # => "wrong argument type String (expected Symbol)"
end
----

Source: https://docs.ruby-lang.org/en/4.0/Fiber.html#method-c-5B-5D-3D[Fiber: element assignment]; https://docs.ruby-lang.org/en/4.0/Fiber.html#method-c-new[Fiber.new]; https://docs.ruby-lang.org/en/4.0/Fiber.html#method-i-storage[Fiber#storage]

The rules the example demonstrates:

* Keys are Symbols (a String is converted; anything else raises `TypeError`). Assigning `nil` deletes the key.
* `Fiber.new(storage: true)` (the default) copies the creator's storage; `storage: nil` starts with nothing (storage is created lazily);
  `storage: hash` uses (a copy of) that Hash, whose keys must all be Symbols. Passing `true` explicitly is documented as experimental.
* The copy is *shallow*: the `Fiber[:tags]` Array above is the same object in the parent and the child, so mutating it is visible to both,
  while reassigning the key is not. Share immutable values or deliberately shared, thread-safe objects.
* `Fiber#storage` returns a *copy* of the Hash and may only be called on the fiber that owns it, otherwise it raises `ArgumentError`.
* `Fiber#storage=` replaces the whole storage and is still *experimental*: it prints the warning below under `-w` or the default warning
  settings. Prefer assigning single keys with `Fiber[]=`, which does not clear state set by libraries.

[source,text]
----
$ ruby -w fiber_storage_assign.rb
fiber_storage_assign.rb:3: warning: Fiber#storage= is experimental and may be removed in the future!
----

The two-line file is `+Fiber.current.storage = { request_id: "r-2" }+` followed by `Fiber[:request_id]`, which returns `"r-2"`. The
warning belongs to the `:experimental` warning category and is silenced with `-W:no-experimental` or
`Warning[:experimental] = false`.

Source: https://docs.ruby-lang.org/en/4.0/Fiber.html#method-i-storage-3D[Fiber#storage=]; https://docs.ruby-lang.org/en/4.0/NEWS/NEWS-3_2_0_md.html[Ruby 3.2.0 NEWS]

[[blocking-fibers]]
== Non-blocking fibers and the fiber scheduler

Plain fibers switch only when you tell them to. The *fiber scheduler* (Ruby 3.0) adds an automatic way to switch: while a *non-blocking*
fiber is running and the thread has a scheduler, every operation that would normally block the thread (sleeping, waiting for a socket or a
pipe, waiting for a child process, taking a contended `Mutex`, popping an empty `Queue`, joining a thread) is reported to the scheduler
instead. The scheduler remembers what the fiber waits for, pauses the fiber with `Fiber.yield`, runs other fibers, and resumes the first one
when its wait is over. The application code is ordinary synchronous-looking Ruby; only the setup mentions the scheduler.

image::ruby-fiber-scheduler-loop.svg["Diagram of one thread: non-blocking fibers reach a blocking call, the matching scheduler hook records what the fiber waits for in the waiting tables and yields, the event loop waits for the nearest deadline or ready descriptor and resumes the fibers that can continue",width=940]

Ruby ships *no scheduler*. `Fiber::Scheduler` is not a class (`defined?(Fiber::Scheduler)` is `nil`): it is the name under which the
documentation describes the interface that any scheduler object must provide. The intended design is a clean separation: the
language reports blocking operations through a small set of hooks, and a library (a gem wrapping an event loop) implements them. The
official guide describes it as a thin layer with no opinions of its own: the hooks receive the arguments of the user's call unchanged, and
schedulers can be layered to add instrumentation.

=== The five methods of Fiber that matter

[cols="3,5",options="header"]
|===
| Method | Meaning
| `Fiber.set_scheduler(scheduler)` | Install `scheduler` for the *current thread*. Raises `ArgumentError` when a required hook is missing. `Fiber.set_scheduler(nil)` removes it, after calling the scheduler's close hook so waiting fibers finish. When the thread exits, Ruby does that implicitly.
| `Fiber.scheduler` | The scheduler last set for the thread, or `nil`.
| `Fiber.current_scheduler` | The same scheduler, but only if the *current fiber is non-blocking*; `nil` otherwise.
| `+Fiber.schedule { ... }+` | Ask the scheduler to run the block in a new non-blocking fiber, "immediately" in the sense of the scheduler's `fiber` hook. Raises `RuntimeError` (`No scheduler is available!`) when the thread has no scheduler.
| `+Fiber.new(blocking: false) { ... }+` | Create a fiber that is *non-blocking* (the default); `blocking: true` creates a blocking one.
|===

Source: https://docs.ruby-lang.org/en/4.0/Fiber.html#method-c-set_scheduler[Fiber.set_scheduler]; https://docs.ruby-lang.org/en/4.0/Fiber.html#method-c-scheduler[Fiber.scheduler]; https://docs.ruby-lang.org/en/4.0/Fiber.html#method-c-current_scheduler[Fiber.current_scheduler]; https://docs.ruby-lang.org/en/4.0/Fiber.html#method-c-schedule[Fiber.schedule]

=== Blocking and non-blocking fibers

A fiber is *blocking* or *non-blocking*. `Fiber#blocking?` answers for a given fiber and `Fiber.blocking?` for the current one; the class method
returns `false` for a non-blocking fiber and the integer `1` (not `true`) for a blocking one, because the documentation reserves larger
integers for future nested cases. `+Fiber.blocking { ... }+` runs its block as a blocking fiber and then restores the previous mode; it is how
code that must not switch (a critical section, a call into a C library that is not scheduler-aware) protects itself. The key rules:

* The thread's root fiber and every fiber created with `blocking: true` are blocking. Fibers created with the default `Fiber.new`
  (`blocking: false`) and by `Fiber.schedule` are non-blocking.
* The distinction matters only when the thread *has a scheduler*. Without one, blocking and non-blocking fibers behave identically and
  every blocking call blocks the thread.
* Hooks are called only from non-blocking fibers. In a blocking fiber a sleeping call really sleeps the whole thread, scheduler or not.
* The scheduler runs on a blocking fiber (the root fiber), never inside a non-blocking one; the official guide advises creating blocking
  fibers only when you are implementing a scheduler.

[source,ruby]
----
# frozen_string_literal: true

require_relative "mini_scheduler"

# Without a scheduler, blocking and non-blocking fibers behave alike.
Fiber.scheduler                       # => nil
Fiber.current.blocking?               # => true
Fiber.blocking?                       # => 1
Fiber.new(blocking: false) { Fiber.current_scheduler }.resume # => nil

states = {}
Shelf::MiniScheduler.run do
  states[:thread_root] = [Fiber.blocking?, Fiber.current_scheduler.class]

  Fiber.schedule do
    states[:scheduled] = [Fiber.blocking?, Fiber.current_scheduler.class]
  end

  Fiber.new { states[:plain_new] = Fiber.blocking? }.resume
  Fiber.new(blocking: true) { states[:blocking_new] = [Fiber.blocking?, Fiber.current_scheduler] }.resume
  Fiber.blocking { states[:blocking_block] = [Fiber.blocking?, Fiber.current_scheduler] }
end

pp states
----

Notice `plain_new: false`: once a thread has a scheduler, a plain `+Fiber.new { ... }+` is non-blocking too, so a *generator* created with
`Fiber.new` and driven with `resume` inside a scheduled fiber is itself subject to the scheduler. Pass `blocking: true` for fibers that
should keep the old behaviour.

=== The scheduler interface

A scheduler is any object that answers the hook methods below. Four are *required*: `Fiber.set_scheduler` raises `ArgumentError`
(`Scheduler must implement #block`, and so on) when one is missing. All the others are optional (a missing optional hook makes the
operation behave in a blocking way, the documentation promises). `fiber` is strongly recommended because `Fiber.schedule` calls it.

[source,ruby]
----
# frozen_string_literal: true

REQUIRED = %i[block unblock kernel_sleep io_wait].freeze

# Which hooks does Fiber.set_scheduler insist on?
REQUIRED.each do |missing|
  scheduler = Class.new do
    (REQUIRED - [missing]).each { |hook| define_method(hook) { |*| nil } }
    def fiber_interrupt(*); end
  end.new
  begin
    Fiber.set_scheduler(scheduler)
  rescue ArgumentError => e
    puts e.message
  end
end

# fiber, close, scheduler_close, io_read and the others are optional.
minimal = Class.new do
  REQUIRED.each { |hook| define_method(hook) { |*| nil } }
  def fiber_interrupt(*); end
end
Fiber.set_scheduler(minimal.new).respond_to?(:close) # => false
Fiber.set_scheduler(nil) # => nil

# Without a scheduler there is nothing for Fiber.schedule to call.
begin
  Fiber.schedule { 1 }
rescue RuntimeError => e
  e.message # => "No scheduler is available!"
end
----

[[toy-scheduler]]
=== A complete toy scheduler

The class below implements the four required hooks plus `fiber`, `process_wait`, `timeout_after`, `fiber_interrupt` and `close`. It is
meant for reading: about a hundred lines show the whole mechanism, and the full design is the picture above. The scheduler keeps three
tables (timers of blocked fibers, fibers waiting on a descriptor, and `Timeout` limits) and a thread-safe ready list; every hook records
what the fiber waits for and calls `Fiber.yield`; `close` runs the event loop. It needs Ruby 4.0 because it passes `Float::INFINITY` as a
timeout to `IO.select`, which Ruby 3.4 and 3.3 reject with `RangeError` (`Inf out of Time range`).

[source,ruby]
----
# frozen_string_literal: true

module Shelf
  # A toy Fiber::Scheduler: it understands sleeping, IO readiness, blocking
  # on a lock or a queue, and Timeout. It is for learning, not for production.
  class MiniScheduler
    def initialize
      @ready = []   # fibers woken by #unblock, possibly from another thread
      @timers = {}  # fiber => deadline of a blocked fiber (Infinity: none)
      @io = {}      # io => [fiber, events] for fibers waiting on a descriptor
      @limits = {}  # fiber => [deadline, klass, message] set by Timeout
      @interrupts = {} # fiber => exception to raise when it wakes
      @lock = Thread::Mutex.new
      @wake_reader, @wake_writer = IO.pipe
    end

    # Runs the block in a fresh thread that owns a scheduler. When the block
    # returns, the thread exits and Ruby calls #close, which runs the loop.
    def self.run
      Thread.new do
        Fiber.set_scheduler(new)
        yield
      end.join
    end

    # Called by Fiber.schedule: create the fiber and start it right away.
    def fiber(&)
      Fiber.new(blocking: false, &).tap(&:resume)
    end

    def kernel_sleep(duration = nil) = block(:sleep, duration)

    def block(_blocker, timeout = nil)
      @timers[Fiber.current] = timeout ? now + timeout : Float::INFINITY
      Fiber.yield
    end

    # Thread safe: it may be called from any thread, so it uses the lock
    # and wakes the event loop through a pipe.
    def unblock(_blocker, fiber)
      @lock.synchronize { @ready << fiber }
      @wake_writer.write_nonblock(".")
    end

    # Called, for example, by IO#close for fibers blocked on that IO.
    def fiber_interrupt(fiber, exception)
      @lock.synchronize do
        @interrupts[fiber] = exception
        @ready << fiber
      end
      @wake_writer.write_nonblock(".")
    end

    def io_wait(io, events, timeout)
      @io[io] = [Fiber.current, events]
      @timers[Fiber.current] = timeout ? now + timeout : Float::INFINITY
      Fiber.yield
    end

    # Waiting for a child process runs in a helper thread; Thread#value
    # blocks this fiber through #block and #unblock.
    def process_wait(pid, flags)
      Thread.new { Process::Status.wait(pid, flags) }.value
    end

    def timeout_after(duration, klass, message, &)
      @limits[Fiber.current] = [now + duration, klass, message]
      yield duration
    ensure
      @limits.delete(Fiber.current)
    end

    # Called when the thread exits: keep running until nothing is left.
    def close
      run
    ensure
      @wake_reader.close
      @wake_writer.close
    end

    def run
      step until idle?
    end

    private

    def now = Process.clock_gettime(Process::CLOCK_MONOTONIC)

    def idle? = @timers.empty? && @lock.synchronize { @ready.empty? }

    def step
      wait_for_events
      @lock.synchronize { @ready.slice!(0..) }.each { |fiber| wake(fiber) }
      @timers.select { |_, at| at <= now }.each_key { |fiber| wake(fiber) }
      @limits.select { |_, (at, *)| at <= now }.each { |fiber, (_, klass, message)| expire(fiber, klass, message) }
    end

    def next_deadline = [*@timers.values, *@limits.values.map(&:first)].min || Float::INFINITY

    def wait_for_events
      @io.delete_if { |io, _| io.closed? } # closed by IO#close: see fiber_interrupt
      timeout = [next_deadline - now, 0].max
      readable, = IO.select(@io.keys + [@wake_reader], nil, nil, timeout)
      readable&.each { |io| io == @wake_reader ? @wake_reader.read_nonblock(64) : wake_io(io) }
    end

    def wake_io(io)
      fiber, events = @io[io]
      wake(fiber, events)
    end

    def wake(fiber, value = nil)
      forget(fiber)
      return unless fiber.alive?

      exception = @lock.synchronize { @interrupts.delete(fiber) }
      exception ? fiber.raise(exception) : fiber.resume(value)
    end

    def expire(fiber, klass, message)
      forget(fiber)
      @limits.delete(fiber)
      fiber.raise(klass, message)
    end

    def forget(fiber)
      @timers.delete(fiber)
      @io.delete_if { |_, (waiting, _)| waiting == fiber }
    end
  end
end
----

Source: https://docs.ruby-lang.org/en/4.0/Fiber/Scheduler.html[Fiber::Scheduler]; https://github.com/ruby/ruby/blob/ruby_4_0/test/fiber/scheduler.rb[the toy scheduler in the Ruby test suite]; https://docs.ruby-lang.org/en/4.0/NEWS_md.html[Ruby 4.0.0 NEWS: IO.select accepts Float::INFINITY]

How it works, following the numbers in the figure:

1. `+Fiber.schedule { ... }+` calls `fiber`, which creates a non-blocking fiber and resumes it at once. The block runs until it calls `sleep`.
2. `Kernel#sleep` in a non-blocking fiber calls `kernel_sleep`, which here is `block(:sleep, duration)`: the fiber is recorded in `@timers` with its deadline and `Fiber.yield` returns control to whoever resumed it, which is the code that called `Fiber.schedule`.
3. The code after `Fiber.schedule` keeps running (that is the point), schedules more fibers, and finally the thread's block returns. The thread is
   about to exit, so Ruby calls `close`, which runs the loop.
4. The loop computes the nearest deadline, waits in `IO.select` (the same call also watches a pipe that `unblock` writes to, so a wake-up from another
   thread ends the wait), moves what is ready, and calls `resume` on each fiber. Each fiber continues after its `sleep`, and either finishes or blocks again.
5. `idle?` is true when no fiber waits any more, and the thread exits.

`IO.select` is acceptable inside the scheduler itself because the loop runs on a blocking fiber. In ordinary application code under a
scheduler, prefer `io.wait_readable(timeout)` and `io.wait_writable(timeout)`: they reach `io_wait`, while `IO.select` reaches `io_select`
only if the scheduler implements it. RuboCop has a cop for exactly this (see <<rubocop,RuboCop cops>>).

=== Running three lookups concurrently

Three catalogue lookups that each wait 0.2 seconds (the sleep stands in for a slow HTTP request) take 0.6 seconds one after the other and
0.2 seconds in three fibers under the scheduler. The lookup code is the same in both runs; only the way it is started changed.

[source,ruby]
----
# frozen_string_literal: true

require_relative "mini_scheduler"

def timed
  started = Process.clock_gettime(Process::CLOCK_MONOTONIC)
  yield
  (Process.clock_gettime(Process::CLOCK_MONOTONIC) - started).round(1)
end

lookup = lambda do |isbn|
  sleep 0.2 # stands in for a slow HTTP request
  "record for #{isbn}"
end

isbns = %w[9780131103627 9780596516178 9781492078005]

sequential = timed { isbns.map(&lookup) }

records = []
concurrent = timed do
  Shelf::MiniScheduler.run do
    isbns.each { |isbn| Fiber.schedule { records << lookup.call(isbn) } }
  end
end

[sequential, concurrent] # => [0.6, 0.2]
records.size             # => 3
----

Source: https://docs.ruby-lang.org/en/4.0/Fiber.html#method-c-schedule[Fiber.schedule]; https://docs.ruby-lang.org/en/4.0/Kernel.html#method-i-sleep[Kernel#sleep]

`Shelf::MiniScheduler.run` starts a thread, installs a scheduler in it, runs the block and lets the thread exit, which is when the event
loop runs; `join` returns once every fiber has finished. Installing the scheduler on the main thread works too: call
`Fiber.set_scheduler(scheduler)` before scheduling and rely on the implicit close when the program ends, or call
`Fiber.set_scheduler(nil)` to run the loop at a chosen point.

The order in which fibers continue is the order in which their waits end, not the order in which they started. The second part of the
next file shows that, and the third and fourth parts show what *stops* a fiber from switching:

[source,ruby]
----
# frozen_string_literal: true

require_relative "mini_scheduler"

def timed
  started = Process.clock_gettime(Process::CLOCK_MONOTONIC)
  yield
  (Process.clock_gettime(Process::CLOCK_MONOTONIC) - started).round(1)
end

# Fibers resume in the order their sleeps end, not the order they started.
events = []
Shelf::MiniScheduler.run do
  { "slow" => 0.3, "fast" => 0.1, "medium" => 0.2 }.each do |name, seconds|
    Fiber.schedule do
      sleep seconds
      events << name
    end
  end
  events << "all scheduled"
end
events.join(", ") # => "all scheduled, fast, medium, slow"

# A blocking fiber does not give control to the scheduler: its sleep is a
# plain, thread-blocking sleep and the other fibers wait for it.
polite = timed { Shelf::MiniScheduler.run { 2.times { Fiber.schedule { sleep 0.2 } } } }
rude = timed { Shelf::MiniScheduler.run { 2.times { Fiber.schedule { Fiber.blocking { sleep 0.2 } } } } }
[polite, rude] # => [0.2, 0.4]

# A child process is awaited through the process_wait hook, so these overlap.
processes = timed { Shelf::MiniScheduler.run { 3.times { Fiber.schedule { system("sleep 0.2") } } } }
processes.between?(0.2, 0.3) # => true
----

Source: https://docs.ruby-lang.org/en/4.0/Fiber.html#method-c-blocking[Fiber.blocking]; https://docs.ruby-lang.org/en/4.0/Process/Status.html[Process::Status] (`wait`, the target of the `process_wait` hook)

`+Fiber.blocking { ... }+` turns the fiber blocking for the duration of its block, so the two sleeps run one after the other (0.4 seconds
instead of 0.2). The child processes of `system("sleep 0.2")` overlap because the scheduler implements `process_wait`; without that hook
`system` blocks the whole thread and the three fibers take 0.6 seconds. The same applies to anything else the scheduler cannot see:
a long Ruby computation, a C extension that blocks in a system call, a `File.read` on a slow disk (a regular file is always "ready" to a poller; the 3.4 `blocking_operation_wait` hook lets a
scheduler move such blocking operations off the event loop), or a database driver that does its own
blocking I/O. A scheduler gives *concurrency for waiting*; it gives no parallelism for computing.

=== Which operation reaches which hook

A scheduler subclass that records its hook calls shows what Ruby reports. `TracingScheduler` below wraps five hooks of the toy
scheduler and `trace` returns how many times each was called while a block ran in a scheduled fiber:

[source,ruby]
----
# frozen_string_literal: true

require "timeout"
require_relative "mini_scheduler"

# Records which hooks Ruby calls, in order.
class TracingScheduler < Shelf::MiniScheduler
  attr_reader :calls

  def initialize
    super
    @calls = []
  end

  %i[kernel_sleep block unblock io_wait timeout_after].each do |hook|
    define_method(hook) do |*args, &block|
      @calls << hook
      super(*args, &block)
    end
  end
end

# Runs the block in a scheduled fiber and returns the hooks it triggered.
def trace(&)
  scheduler = TracingScheduler.new
  Thread.new do
    Fiber.set_scheduler(scheduler)
    Fiber.schedule(&)
  end.join
  scheduler.calls.tally
end

reader, writer = IO.pipe

trace { sleep 0.01 } # => {kernel_sleep: 1, block: 1}
trace { Thread::Queue.new.pop(timeout: 0.01) } # => {block: 1}
trace { Thread.new { writer.write("x") }.then { reader.wait_readable } } # => {io_wait: 1}
trace { Thread.new { sleep 0.01 }.join } # => {block: 1, unblock: 1}

expiring = lambda do
  Timeout.timeout(0.01) { sleep }
rescue Timeout::Error
  :expired
end
trace(&expiring) # => {timeout_after: 1, kernel_sleep: 1, block: 1}
----

Source: https://docs.ruby-lang.org/en/4.0/Fiber/Scheduler.html#method-i-io_wait[Fiber::Scheduler#io_wait]; https://docs.ruby-lang.org/en/4.0/Fiber/Scheduler.html#method-i-timeout_after[#timeout_after]; https://docs.ruby-lang.org/en/4.0/Thread/Queue.html[Thread::Queue]

Reading the five results: `sleep` calls `kernel_sleep`, and the toy implements it with `block`, hence two calls. `Queue#pop(timeout:)` on an empty
queue calls only `block`. Waiting for a pipe that another thread fills calls `io_wait`. `Thread#join` calls `block` and, when the joined
thread ends (in another thread), `unblock`. `Timeout.timeout` calls `timeout_after` first and then the hooks of whatever the block does.
Other operations observed in the same experiment: a contended `Mutex#lock` and a `ConditionVariable#wait` use `block` and `unblock`
(the latter also `kernel_sleep` through `Mutex#sleep`), and a read from a pipe that already holds data calls no hook at all.

[[timeouts-and-close]]
=== Timeouts and IO#close

`Timeout.timeout` in a non-blocking fiber calls `timeout_after` (Ruby 3.1), so no helper thread is created and the interruption is a
`Fiber#raise` at the point where the fiber waits. The reference documentation is explicit about the limit: only *non-blocking* operations are interrupted; a block that
never reaches the scheduler cannot be interrupted at all, and adding `sleep(0)` creates a predictable point.

[source,ruby]
----
# frozen_string_literal: true

require "timeout"
require_relative "mini_scheduler"

outcome = nil
started = Process.clock_gettime(Process::CLOCK_MONOTONIC)
Shelf::MiniScheduler.run do
  Fiber.schedule do
    outcome = Timeout.timeout(0.05) { sleep 5 }
  rescue Timeout::Error => e
    outcome = e.message
  end
end
elapsed = Process.clock_gettime(Process::CLOCK_MONOTONIC) - started

[outcome, elapsed < 1] # => ["execution expired", true]
----

Source: https://docs.ruby-lang.org/en/4.0/Timeout.html#method-c-timeout[Timeout.timeout]; https://docs.ruby-lang.org/en/4.0/Fiber/Scheduler.html#method-i-timeout_after[Fiber::Scheduler#timeout_after]

Ruby 4.0 added `fiber_interrupt` so that `IO#close` is safe: closing an IO interrupts every thread and fiber blocked on it, each receives an
`IOError`, and only then is the descriptor really closed. For scheduled fibers Ruby calls `scheduler.fiber_interrupt(fiber, exception)`; the
scheduler wakes the fiber and raises the exception in it, typically with `Fiber#raise`.

[source,ruby]
----
# frozen_string_literal: true

require_relative "mini_scheduler"

outcome = []
Shelf::MiniScheduler.run do
  reader, = IO.pipe

  Fiber.schedule do
    reader.wait_readable # nothing is ever written: the fiber waits in io_wait
  rescue IOError => e
    outcome << "reader: #{e.message}"
  end

  Fiber.schedule do
    sleep 0.05
    reader.close   # Ruby 4.0 calls scheduler.fiber_interrupt for the waiting fiber
    outcome << "closer: done"
  end
end
outcome.join("; ") # => "reader: stream closed in another thread; closer: done"
----

Source: https://docs.ruby-lang.org/en/4.0/language/fiber_md.html[Fiber guide: IO#close]; https://docs.ruby-lang.org/en/4.0/Fiber/Scheduler.html#method-i-fiber_interrupt[Fiber::Scheduler#fiber_interrupt]; https://docs.ruby-lang.org/en/4.0/IO.html#method-i-close[IO#close]

The reader fiber sat in `io_wait`; the other fiber closed the pipe; Ruby called `fiber_interrupt`; the reader saw `stream closed in another thread`.
Schedulers written for Ruby 3.x do not have this hook, so on 4.0 they print the warning shown in <<scheduler-warnings,the warnings section>> and
a fiber blocked on a closed IO is not woken up.

=== Mutex, Queue and Monitor under a scheduler

`Thread::Mutex` has been *fiber-owned* since Ruby 3.0: the fiber that locked it is the owner, not the thread. Two fibers on one thread
therefore cannot both hold it, and without a scheduler a second fiber that tries to lock a held mutex fails at once with
`ThreadError` rather than deadlocking silently. Under a scheduler the same attempt goes through `block`, the waiting fiber is paused and
the thread keeps running other fibers until the owner unlocks (`unblock`). `Thread::Queue`, `SizedQueue` and `ConditionVariable` behave
the same way, and `Monitor` is fiber-safe since 3.1.

[source,ruby]
----
# frozen_string_literal: true

require_relative "mini_scheduler"

def message
  yield
rescue ThreadError => e
  e.message
end

# Since Ruby 3.0 a Mutex belongs to a fiber, not to a thread.
lock = Thread::Mutex.new
holder = Fiber.new do
  lock.lock
  Fiber.yield
  lock.unlock
end
holder.resume
lock.owned?                  # => false
lock.locked?                 # => true
message { lock.lock }        # => "deadlock; lock already owned by another fiber belonging to the same thread"
message { lock.unlock }      # => "Attempt to unlock a mutex which is locked by another thread/fiber"
holder.resume
lock.locked?                 # => false

# Under a scheduler, a fiber that waits for a lock yields through #block.
order = []
Shelf::MiniScheduler.run do
  Fiber.schedule do
    lock.synchronize do
      sleep 0.1
      order << "first"
    end
  end
  Fiber.schedule { lock.synchronize { order << "second" } }
end
order.join(", ") # => "first, second"
----

Source: https://docs.ruby-lang.org/en/4.0/Thread/Mutex.html[Thread::Mutex]; https://docs.ruby-lang.org/en/4.0/NEWS/NEWS-3_0_0_md.html[Ruby 3.0.0 NEWS: Mutex is now acquired per-Fiber]; https://docs.ruby-lang.org/en/4.0/Monitor.html[Monitor]

The consequence for application code is that *locks stay necessary* wherever a switch can happen inside a critical section, which now
includes every blocking call in a non-blocking fiber. A section without any blocking call cannot be interrupted by another fiber, so
`+@count += 1+` is safe between fibers of one thread, but `fetch` followed by `store` around an HTTP call is not.

=== Warnings you will meet on Ruby 4.0

Two warnings appear when a scheduler written for an older Ruby meets 4.0. Both were reproduced with this file, and neither appears on Ruby 3.3 or 3.4:

[source,ruby]
----
# frozen_string_literal: true

require_relative "mini_scheduler"

# Ruby 4.0 asks every scheduler to implement fiber_interrupt.
bare = Class.new do
  %i[block unblock kernel_sleep io_wait].each { |hook| define_method(hook) { |*| nil } }
end
Fiber.set_scheduler(bare.new)
Fiber.set_scheduler(nil)

end

----

== Community schedulers

Nobody is expected to write the toy scheduler above for a real program. The scheduler is an extension point, and several gems implement it on top of an
efficient event loop. They are third-party software with their own versions and release cycles: the notes below come from their own
documentation and from the registry on 2026-10-18, and none of their code was installed or run for this page.

* *async* (the `async` gem, by the socketry project, MIT license) is the best known. Its documentation describes `Async::Scheduler`, the
  implementation of the interface (the top-level block creates an `Async::Reactor`, a subclass of it, to run the event loop); `Async::Task`, which runs on a fiber and produces a result you `wait` for; and
  the `Kernel#Async` and `Kernel#Sync` entry points. `+Async { ... }+` starts a task (and an event loop if none runs) and returns the task
  at once, like `Fiber.schedule` with a result; `+Sync { ... }+` runs the block in the current or a new event loop and returns the block's value. It
  can also be used directly through `Fiber.set_scheduler(Async::Scheduler.new)`. Its documentation says it works with most pure Ruby code and well-behaved C
  code (for example `Net::HTTP`), and warns about libraries that block, are processor bound, or keep execution state in thread locals, for which it recommends a
  background thread. Related gems from the same authors include `io-event` (an event loop library), `async-http`, `async-websocket` and `async-dns`.
* *Falcon* (the `falcon` gem) is described as a fast, asynchronous, Rack-compatible web server, built on top of `async-http`.
* Older schedulers exist as gems (`evt`, `libev_scheduler`), but their last releases date from 2020 and 2021 (registry check above); treat
  them as historical unless you verify they work with your Ruby.

The following program is the toy example rewritten with `async`. It is *not run* on this page (it needs `bundle add async`), and
follows the pattern from the gem's getting-started guide, so check the current guide for exact method names:

[source,ruby]
----
# frozen_string_literal: true

# Not run on this page: it needs `bundle add async`, a community gem.
require "async"

def lookup(isbn)
  sleep 0.2 # the scheduler turns this sleep into a fiber switch
  "record for #{isbn}"
end

isbns = %w[9780131103627 9780596516178 9781492078005]

# Sync starts an event loop if needed and returns the block's value.
records = Sync do |parent|
  isbns.map { |isbn| parent.async { lookup(isbn) } }.map(&:wait)
end
puts records
----

Source: https://socketry.github.io/async/guides/getting-started/index.html[Async: Getting Started]; https://socketry.github.io/async/guides/scheduler/index.html[Async: Scheduler]; https://rubygems.org/gems/async[async on RubyGems]; https://github.com/socketry/io-event[io-event]; https://socketry.github.io/falcon/[Falcon]

When choosing between a scheduler-based design and threads, remember what the scheduler can see. Code that uses only Ruby's standard I/O,
`sleep`, `Queue`, `Mutex` and `Thread#join` works unchanged. Code that calls blocking C libraries (some database drivers, DNS resolvers,
image libraries) does not switch, and one such call stalls every fiber on the thread; run it in a thread or process instead, as the async
documentation suggests. Programs that need several cores run several processes (one event loop each) or use Ractors
(xref:programming-languages/ruby/ractors.adoc[Ractors]).

== When to use fibers

* Use *`Enumerator`* when you need a generator: it is built on fibers and is the documented, complete interface.
* Use a plain *`Fiber`* when you must drive switching yourself: coroutines that exchange values, parsers or protocol state machines
  written as straight-line code, or cooperative multitasking with your own round-robin (`transfer`).
* Use a *scheduler* (usually `async`) when you have many concurrent waits (connections, requests, timers) and want per-wait cost low,
  or need cheap "one task per connection" code without callbacks.
* Use *threads* when you have a handful of blocking tasks, code that blocks in C, or libraries that rely on thread semantics.
* Use *Ractors* or *processes* for CPU-bound work that must use several cores.

Fibers and threads combine: a thread can own a scheduler and run thousands of fibers, and several threads can each own a scheduler.
Remember that a fiber never moves between threads, that `+Thread#[]+` storage is per fiber, and that anything shared between threads still
needs locks.

== Application patterns

Three habits keep fiber code correct:

* *Isolate per-request state with fiber storage or explicit objects, not globals.* A `$current_user` or a class-level variable is shared by
  every fiber of every thread; `+Thread.current[:user]+` is per fiber and therefore invisible to helper fibers; `Fiber[:user]` is inherited
  by everything created from the request fiber.
* *Create and finish fibers in structured groups.* A scheduler runs a fiber to completion only if somebody waits for it. Keep the handles
  (`Fiber.schedule` returns the fiber, `async` returns a task) and wait for them, or the thread's exit calls `close` and the loop drains them
  in an unpredictable order.
* *Keep fibers that do CPU work short.* If a fiber computes for a long time, call `sleep(0)` at
  safe points to let others run; a scheduler cannot interrupt Ruby code that never waits.

[[other-languages]]
== Fibers in other languages

Ruby's fibers and scheduler sit between a few designs found elsewhere:

* PHP 8.1 has a `Fiber` class with `start`, `suspend` and `resume`, very close to `Fiber.new`, `Fiber.yield` and `resume`; like Ruby it ships no event loop.
  See xref:programming-languages/php/fibers-and-asynchronous-php.adoc[Fibers and asynchronous PHP].
* Python's `asyncio` has an event loop in the standard library and marks suspension points in the source with `await`; Ruby leaves the event loop to a gem
  and keeps the code free of keywords, at the price that any blocking call can be a switch point. See
  xref:programming-languages/python/concurrency-and-async.adoc[Concurrency and async in Python].
* Java's virtual threads are scheduled by the runtime and turn blocking calls into switches transparently, which is the closest match to a
  Ruby scheduler. See xref:programming-languages/java/virtual-threads.adoc[Virtual threads].
* Rust futures are state machines polled by an executor, with `async` and `await` in the source. See
  xref:programming-languages/rust/async-await-and-futures.adoc[Async, await and futures].
* Go goroutines are scheduled by the runtime across several operating-system threads, so they run in parallel, which Ruby fibers do not. See
  xref:programming-languages/go/goroutines-and-the-scheduler.adoc[Goroutines and the scheduler].

== Where older books and tutorials are outdated

[cols="2,3",options="header"]
|===
| Older statement | Current behaviour

| "Since Ruby 3, fibers automatically yield on I/O" (also phrased as "fibers are non-blocking by default")
| Only a *non-blocking fiber on a thread that has a scheduler* switches on blocking operations, and Ruby ships no scheduler. A plain
fiber, or any fiber when `Fiber.scheduler` is `nil`, blocks the thread exactly like any other code.

| "Adding more threads does not help throughput" (a common simplification about the GVL)
| Threads do help I/O-bound programs, because the GVL is released while a thread waits; they do not make pure Ruby CPU work parallel.
See xref:programming-languages/ruby/threads-and-the-gvl.adoc[Threads and the GVL].

| `Fiber.current`, `Fiber#alive?` and `Fiber#transfer` need `require "fiber"`
| True up to Ruby 2.6 (checked on 2.6.10). On 3.2 and later they are available without a `require`; `require "fiber"` still works and does nothing useful.

| `Thread.current[:key]` is a thread-local variable
| It is *fiber-local*. Use `thread_variable_get` and `thread_variable_set` for real thread-locals, and `Fiber[:key]` (3.2) for state that
should flow to the fibers and threads you create.

| A `Mutex` belongs to a thread
| Since 3.0 it belongs to a fiber, so a second fiber of the same thread cannot take it and `lock` raises `ThreadError` without a scheduler.

| Ractors communicate with `Ractor.yield` and `Ractor#take`
| Removed in 4.0; the API is `Ractor::Port`, `#join` and `#value`. See xref:programming-languages/ruby/ractors.adoc[Ractors].

| Hand-written event loops with `resume`/`yield` to simulate async I/O
| The scheduler interface (3.0) does this for the standard library and C extensions; use `async` or a scheduler instead of polling descriptors yourself.
|===

== Pitfalls

* *Expecting automatic switching.* A fiber created with `Fiber.new` and driven with `resume` never switches on its own; and a
  non-blocking fiber without a scheduler behaves exactly like a blocking one.
* *Blocking the thread.* One CPU-bound loop, one blocking C call or one `+Fiber.blocking { ... }+` stalls every fiber of the thread. Hand
  such work to a thread (`+Thread.new { ... }.value+` is non-blocking under a scheduler).
* *Fibers and thread locals.* `+Thread.current[:x]+` disappears across `Enumerator#next`, across `Fiber.new` and in helper fibers.
  Use fiber storage or pass objects explicitly.
* *Sharing a fiber between threads.* Not allowed: `FiberError` (`fiber called across threads`). An enumerator advanced with `next` has the
  same restriction.
* *Forgetting to finish generators.* A suspended fiber holds its stack and its `ensure` blocks never run unless you `kill` it or let it finish.
* *Leaking exceptions.* An exception inside a scheduled fiber that nobody waits for (with `wait`, `join` or `value`) is reported by the scheduler (or lost); wrap the
  block in `rescue` and record the failure, or use a library that collects task errors.
* *Locks around blocking calls.* A `Mutex` held across a `sleep` or a network call in one fiber makes every other fiber that needs it
  wait, and a lock that is never released deadlocks the whole event loop.
* *`sleep` used as synchronisation.* It works only as long as the timing assumptions hold; use `Queue`, `ConditionVariable` or task
  results.
* *Writing a scheduler without a thread-safe `unblock`.* `unblock` may be called from any thread (`Thread#join`, `Queue#push` from a
  thread), and the event loop must wake up when it is: use a lock and a self-pipe as the toy scheduler does.
* *Relying on experimental pieces.* `Fiber#storage=`, `io_read`/`io_write` with `IO::Buffer` and `storage: true` are documented as
  experimental.
* *Assuming schedulers are portable across Ruby versions.* A scheduler written for 3.x lacks `fiber_interrupt` and warns on 4.0, and
  the 3.x hooks differ in the arguments they receive (for example `io_read` and `io_write` gained an offset). Pin the gem and Ruby versions.

== Version notes

[cols="1,5",options="header"]
|===
| Version | Change that concerns fibers

| 2.6 and older
| `Fiber.current`, `Fiber#alive?` and `Fiber#transfer` needed `require "fiber"` (verified on 2.6.10).

| 3.0
| `Fiber.new(blocking:)`, `Fiber#blocking?`, `Fiber.blocking?`, `Fiber.set_scheduler`, `Fiber.scheduler`; scheduler hooks for `sleep`, `IO`, `Mutex`, `Queue`, `ConditionVariable`, `Thread#join` and process waits; `Mutex` acquired per fiber; `Fiber#backtrace` and `backtrace_locations`; the restrictions of `Fiber#transfer` relaxed.

| 3.1
| Non-blocking `Timeout.timeout` through `timeout_after`; `io_read` and `io_write` with `IO::Buffer`; `address_resolve`; `Monitor` made fiber-safe.

| 3.2
| Fiber storage (`Fiber[]`, `Fiber[]=`, `Fiber#storage`, `storage=`, `Fiber.new(storage:)`); `io_select` hook; `IO#timeout=`; `Queue#pop(timeout:)`.

| 3.3
| `Fiber#kill`; the M:N thread scheduler (`RUBY_MN_THREADS=1`, see xref:programming-languages/ruby/threads-and-the-gvl.adoc[Threads and the GVL]).

| 3.4
| `blocking_operation_wait` hook; `Fiber#raise` accepts an Array of `Thread::Backtrace::Location`.

| 4.0
| `Fiber#raise(cause:)`; `fiber_interrupt` (with `IO#close` interrupting fibers blocked on the IO) and the `yield` hook; `io_close` reintroduced; `io_write` called when flushing the write buffer; `IO.select` accepts `Float::INFINITY`; a missing `fiber_interrupt` produces a warning. `Ractor::Port` replaces `Ractor.yield` and `#take`.

| 4.1 (preview)
| Not released as of 2026-10-18; no fiber change is described here.
