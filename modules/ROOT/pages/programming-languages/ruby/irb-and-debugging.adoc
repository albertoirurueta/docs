== IRB

IRB (*I*nteractive *R*u*B*y) reads an expression, evaluates it, prints the result with `inspect` and loops. It is what you get
from the `irb` command, and the same engine runs inside a program when you call `binding.irb`. Its documentation lives with the
gem, at https://ruby.github.io/irb/ and in `irb --help`; since IRB is a bundled gem in 4.0, the core documentation at
`docs.ruby-lang.org/en/4.0` no longer has an `IRB` page.

=== Starting IRB

[source,bash]
----
$ irb                                # an empty session
$ irb -I lib -r shelf                # put lib on the load path and require the gem first
$ irb -w                             # same as ruby -w: show warnings
$ irb -f                             # do not read any .irbrc
$ irb --nocolorize --noautocomplete  # plain output, useful in logs and CI consoles
----

The options in `irb --help` are the same as those of `ruby` where they overlap (`-d`, `-r`, `-I`, `-U`, `-E`, `-w`, `-W`) plus
the IRB-specific ones in the table below. All of them can also be set from a configuration file (see <<The .irbrc file>>).

[cols="3,5",options="header"]
|===
| Option | Effect
| `-f`

| `-r library`, `-I path`

=== A first session

At the prompt, every complete expression is evaluated and its result printed after `+=>+`. A statement that is not yet complete
(an open `do`, a trailing operator, an unclosed bracket) makes the editor continue on the next line, and the editor indents it
for you. The result of the last expression is available as `_`, which is the quickest way to keep working on a value you forgot
to assign.

[source,text]
----
irb(main):001> isbn = Shelf::Isbn.new("978-0-596-51774-8")
=> #<data Shelf::Isbn digits="9780596517748">
irb(main):002> isbn.digits.length
=> 13
irb(main):003> _ + 1
=> 14
----

Source: https://ruby.github.io/irb/#label-Evaluation+History[IRB documentation: Evaluation History]

An assignment prints its value too, but truncated when it is long (the default `--truncate-echo-on-assignment`), so that
loading a large object into a variable does not flood the terminal:

[source,text]
----
irb(main):002> book = Shelf::Book.new(isbn:, title: "The Ruby Programming Language", author: Shelf::Author.new("Flanagan"))
=>
#<data Shelf::Book
...
----

Evaluating the variable on its own prints the whole value, laid out with `pp` (see <<pp and p>>). Two details are worth
remembering. The value printed after `+=>+` is the *return value of the expression*, not what the expression printed: `puts "x"`
shows `x` and then `+=> nil+`. And in Ruby 3.4 and later `Hash#inspect` prints `+{isbn: 1}+` and `+{"a" => 1}+`, so the output you
see in IRB matches what `p` prints in a script of the same version.

Source: https://ruby.github.io/irb/[IRB documentation]

=== Commands

IRB has two kinds of input. Anything that is valid Ruby is evaluated. A *command* is a name followed by free text that does not
have to be valid Ruby, such as `ls -g pattern` or `show_source Shelf::Isbn#to_s`. A command is recognised only when it is the
first word of the input and *no local variable of that name exists*: if you assign `ls = 3`, the word `ls` means the variable
until you leave it. Type `help` for the list in your version and `help command` for one command.

[cols="2,5",options="header"]
|===
| Command | What it does
| `help [command]`
| List the commands, or describe one
| `ls [obj] [-g pattern]`
| Show the methods, constants, instance variables and local variables of an object or the current context, grouped by the class that defines them; `-g` filters by a pattern
| `show_source name`, `$ name`
| Print the source code of a method, class, module or constant (`Shelf::Isbn#to_s`, `Shelf::Isbn`)
| `show_doc [name]`
| Look the name up in the RI documentation and show it; with no argument start an interactive `ri` session
| `whereami`, `@`
| Show the source around the line where `binding.irb` stopped
| `cd obj`, `cd ..`
| Make `obj` the receiver (`self`) of the session, or go back; the prompt shows it
| `chws obj`, `pushws obj`, `popws`, `workspaces`, `cwws`
| Change, push, pop, list and show the current workspace (the same idea as `cd`, with a stack)
| `history [-g pattern]`
| The input history, optionally filtered; `history -G pattern` also exists
| `measure`, `measure :off`
| Print the wall time of each expression (`measure :stackprof` profiles with the `stackprof` gem)
| `edit [file or name]`
| Open a file or the definition of a method in `$VISUAL` or `$EDITOR`
| `copy expr`
| Copy the printed result to the clipboard (program overridable with `IRB_COPY_COMMAND`)
| `context`, `irb_info`
| The current configuration, and the Ruby, IRB, input method and completion in use
| `irb_load file`, `irb_require lib`, `source file`
| Load or require a file inside the session. `source` evaluates the file in the current workspace
| `exit`, `quit`, `exit!`, `disable_irb`
| Leave the session (a `binding.irb` session lets the program continue), leave the whole process, or turn later `binding.irb` calls into no-ops
| `debug`, `break`, `catch`, `next`, `step`, `continue`, `finish`, `delete`, `backtrace`, `info`
| Hand control to the `debug` gem (see <<Using IRB and the debugger together>>)
| `irb`, `jobs`, `fg`, `kill`
| Child sessions (deprecated in the IRB version shipped with 4.0)
|===

=== Pitfalls in the REPL

* *The history is global.* Every session appends to the same history file, by default `+~/.irb_history+`, which is why the
  `history` numbers in a long-lived shell are large. `IRB.conf[:SAVE_HISTORY]` (default 1000 lines) and `IRB.conf[:HISTORY_FILE]`
  control it, and a secret typed at the prompt stays in the file.
* *Redefinition is silent.* Reloading a class by pasting it again adds methods to the existing class instead of replacing it,
  exactly as in a file. Restart the session, or use `load "file.rb"`, when stale methods matter.
* *`_` is overwritten by every expression*, including the ones IRB evaluates for you, so assign anything you need to keep.
* *A command is shadowed by a local variable.* After `history = []` the word `history` is the array. Use
  `binding.local_variables` to see what you have defined.
* *Output is `inspect`, not `to_s`.* A `Data` or `Struct` whose `to_s` you overrode still prints with its structure in IRB.
* *Ctrl-C interrupts the running expression,* not the shell (the default `IRB.conf[:IGNORE_SIGINT]` is `true`), and Ctrl-D at an
  empty prompt exits.

=== binding.irb

`binding.irb` starts an IRB session *inside the running program*, with the local variables, `self` and the current method of
the line where it is written. It is `Binding#irb`, so you can call it on any binding, and it is the Ruby counterpart of
`debugger` in other languages.

[source,ruby]
----
# frozen_string_literal: true

require "shelf"

isbn = Shelf::Isbn.new("978-0-596-51774-8")
author = Shelf::Author.new("Flanagan")
book = Shelf::Book.new(isbn:, title: "The Ruby Programming Language", author:)
catalog = Shelf::Catalog.new.add(book)

titles = catalog.map(&:title)
binding.irb # rubocop:disable Lint/Debugger

puts titles.size
----

Source: https://ruby.github.io/irb/Binding.html#method-i-irb[IRB documentation: Binding#irb]

Running the script with `ruby -I/path/to/shelf/lib e01_inspect_loan.rb` stops at line 11 and shows the surrounding code with an
arrow. Everything you type is evaluated in the script's scope, so the local variables are there, and so is any change you make:

[source,text]
----

Source: https://ruby.github.io/irb/Binding.html#method-i-irb[IRB documentation: Binding#irb]

The error in the last command is the point: an exception raised by what you type is printed and the session continues, so
trying things out cannot end the program. Typing `exit` (or Ctrl-D) resumes the program after the `binding.irb` line, which is
why `1` was printed by the `puts` after the session. `exit!` ends the whole process, and `disable_irb` makes every later
`binding.irb` call do nothing, which is useful when a call sits in a loop.

Where `binding.irb` is useful and where it is not:

* It is for a *developer at a terminal*. A program without a terminal on standard input (a service, a job, a test run with
  piped input) has nothing for IRB to read; use the remote mode of the debugger instead (see <<Remote debugging>>).
* Put it where the interesting values are in scope, including inside a `rescue` clause (`+rescue => e+` then `binding.irb`),
  inside a block, or in a method called from a test. `binding.irb` in a test run waits forever in CI, so remove it before
  committing; RuboCop's `Lint/Debugger` cop exists to catch it.
* Under Bundler it needs `irb` in the `Gemfile` (see <<Debugging under Bundler>>).
* From IRB you can reach the debugger without restarting (see <<Using IRB and the debugger together>>).

=== The .irbrc file

IRB reads Ruby code from a configuration file at startup (unless `-f` is given). The first file found in this order is used:

. the path in the `IRBRC` environment variable;
. `$XDG_CONFIG_HOME/irb/irbrc`;
. `+~/.irbrc+`;
. `+~/.config/irb/irbrc+` (only when `XDG_CONFIG_HOME` is *not* set);
. `.irbrc`, `_irbrc` or `$irbrc` in the current directory.

Because the file is plain Ruby, it can configure IRB through the `IRB.conf` hash and define commands and helpers. Hash entries
set in the file win over command-line options, and `IRB.conf` is read once, when the file is interpreted, so changes made later
in a session do not affect the running context (use `conf`, the current context, for that).

[source,ruby]
----
# frozen_string_literal: true

# ~/.irbrc or ./.irbrc: Ruby code that runs once when IRB starts.
require "irb/command"
require "irb/helper_method"

IRB.conf[:SAVE_HISTORY] = 5_000              # lines kept in the history file
IRB.conf[:HISTORY_FILE] = File.join(Dir.home, ".irb_history")
IRB.conf[:PROMPT_MODE] = :SIMPLE             # ">> " instead of "irb(main):001> "
IRB.conf[:USE_PAGER] = false
IRB.conf[:ECHO_ON_ASSIGNMENT] = false        # do not print the value on `x = ...`
IRB.conf[:COMPLETOR] = :type                 # :type or :regexp
IRB.conf[:LOAD_MODULES] = %w[json]           # same as irb -r json (the rc file wins over -r)

# A command: it receives the raw text after its name, so the argument need not be valid Ruby.
class Isbn13Command < IRB::Command::Base
  category "Shelf"
  description "Convert an ISBN-10 to an ISBN-13"
  help_message "Usage: isbn13 <isbn-10>"

  def execute(arg)
    body = "978#{arg.delete('-')[0, 9]}"
    weighted = body.chars.each_with_index.sum { |digit, i| digit.to_i * (i.even? ? 1 : 3) }
    puts "#{body}#{(10 - (weighted % 10)) % 10}"
  end
end
IRB::Command.register(:isbn13, Isbn13Command)

# A helper method: an ordinary method call that returns a value.
sample_catalog = Class.new(IRB::HelperMethod::Base) do
  description "A catalog with one book in it"

  def execute
    require "shelf"
    isbn = Shelf::Isbn.new("978-0-596-51774-8")
    book = Shelf::Book.new(isbn:, title: "The Ruby Programming Language", author: Shelf::Author.new("Flanagan"))
    Shelf::Catalog.new.add(book)
  end
end
IRB::HelperMethod.register(:sample_catalog, sample_catalog)
----

Source: https://ruby.github.io/irb/Configurations_md.html[IRB documentation: Configure IRB]

| `:AT_EXIT`
|
| Hooks called when IRB exits
| `:VERBOSE`
| `--verbose`
| More detail about IRB itself
| `:COMMAND_ALIASES`
|
| A hash of aliases such as `+{ "$": :show_source, "@": :whereami }+`

Other variables IRB reads are `EDITOR` or `VISUAL` (for `edit`), `IRB_COPY_COMMAND` (for `copy`), `RI_PAGER` and `PAGER`, and
`IRB_LANG`, `LC_MESSAGES`, `LC_ALL` and `LANG` for the language of its messages.

=== Extending IRB: commands and helper methods

Since IRB 1.13 there is a supported API to add features, shown in the `.irbrc` above. Choose between the two by what the input
looks like:

* A *command* (`IRB::Command::Base` subclass registered with `IRB::Command.register`) receives the raw text after its name as one
  String, so it can accept things that are not Ruby (`isbn13 0-596-51774-0`, `ls -g pattern`). It does not return a value to the
  session. Use `category`, `description` and `help_message` to put it in `help`.
* A *helper method* (`IRB::HelperMethod::Base` subclass registered with `IRB::HelperMethod.register`) is an ordinary method call
  that returns an object (`sample_catalog.first`). It shows up under "Helper methods" in `help`, next to the built-in `conf`.

A gem can ship its own commands and helpers, loaded from its `.irbrc` or from a library that the user requires, which is how
framework consoles add their shortcuts. If you do not know which to pick, the guide recommends a command first, because it
handles more kinds of input.

Source: https://ruby.github.io/irb/EXTEND_IRB_md.html[IRB documentation: Extend IRB]

=== Type-based completion

IRB offers completion in two forms: pressing Tab, and the dialog that opens automatically while you type, showing candidates
and, for the selected one, its documentation. How candidates are computed depends on the *completor*:

* The *regexp completor* looks at the text before the cursor with regular expressions and may evaluate the receiver of a simple
  method call. It is simple and works everywhere.
* The *type completor* (`repl_type_completor`, a bundled gem since Ruby 3.4) parses the code with Prism and infers the *type* of
  the receiver from the code and from the RBS signatures of the core classes, without running anything. After `+titles.map { it.+`
  it knows `it` is a String. It is the default in IRB on Ruby 3.4 and later when the gem is available; `IRB_COMPLETOR=regexp`,
  `--regexp-completor` or `IRB.conf[:COMPLETOR] = :regexp` switches back, and `--type-completor` forces it (printing a warning
  when the gem cannot be loaded).

`irb_info` shows which one is active:

----

The gem has a small public API that IRB itself uses, so you can see what completion would offer without typing in a terminal.
The candidates are the *remaining* characters of each match (after `titles.first.up` the completion `case` completes `upcase`):

[source,ruby]

The completor knows what Ruby knows: `isbn.dig` can only complete to `digits`, `titles.first.up` offers the `String` methods
and `stock.fetch("Ruby").ze` offers the `Integer` method `zero?`, which a purely textual completor cannot know
without running the code. Its limits are those of static inference: a value that only exists at runtime (the result of
`eval`, of `send` with a computed name, of `method_missing`) is unknown to it, and it falls back to listing nothing rather
than guessing.

== The debug gem

The `debug` gem is the debugger that comes with Ruby 3.1 and later. Until Ruby 3.0 the standard library had a different
`debug.rb`; the gem was written to replace it, and it also replaces, for most people, the community debuggers that earlier
tutorials describe. It is a bundled gem (installed with Ruby), is built on `TracePoint`, supports threads, can be driven from a
terminal, a script, a remote socket, VS Code or Chrome DevTools, and is maintained at https://github.com/ruby/debug.

=== Three ways to start it

[source,bash]
----
$ ruby -r debug target.rb         # or put `require "debug"` at the top: stops only at binding.break / debugger
$ rdbg target.rb                  # run under the debugger, stopped at the first line
$ rdbg -c -- bundle exec rake test   # run another Ruby command under the debugger
----

Source: https://github.com/ruby/debug#invoke-with-the-debugger[ruby/debug repository: invoke with the debugger]

* *In the source.* Add `require "debug"` and call `binding.break` (aliases `binding.b` and `debugger`) where you want to stop. The
  program runs normally until that line, then opens the debug console. It is `binding.irb` with a debugger instead of a REPL,
  and `require "debug"` is the same as `rdbg --nonstop --no-sigint-hook`.
* *From the command line.* `rdbg script.rb args` starts `script.rb` like `ruby script.rb args` and stops at the first line;
  `rdbg -n` (`--nonstop`) does not stop there, so only your breakpoints fire. `rdbg -- -r foo -e code` passes interpreter options
  after `--`, as in `rdbg -- -I/path/to/shelf/lib target.rb`: `rdbg` has no `-I` of its own, and `rdbg -I lib target.rb` fails
  with "invalid option: -I".
* *For another Ruby executable.* `rdbg -c -- bundle exec rake test` runs the command with `rdbg -c` and the debugger attaches
  to the Ruby it starts. The `--` separates rdbg's options from the command's (`rdbg -c rake -T` would be read as
  `rdbg -c -T -- rake`). Under Bundler the `Gemfile` must list `debug`.

`require "debug/start"` starts a session stopped at that point like `rdbg` does, `require "debug/open"` and `require
"debug/open_nonstop"` open the remote port (see <<Remote debugging>>), and `DEBUGGER__.start(**options)` from `debug/session`
starts one with configuration given in code. They must be required before the code you want to debug is loaded.

=== The debug commands

a variable called `c`. Pressing Enter repeats the last stepping command. Most commands have a short form, written

=== Stopping where the failure happens

An exception breakpoint is the debugger's most useful tool when you do not know where a bad value came from. `catch

parses three ISBNs and rescues the bad ones, which hides exactly the information you want:

Source: https://github.com/ruby/debug#bindingbreak-method[ruby/debug repository: binding.break]

`catch` stopped at the first failing ISBN (`+...-9+`) inside `Shelf::Isbn#initialize`, where `p digits` is the argument that
failed validation; `frame 2` moved to the caller's block to see `text`; after `delete 0` the program ran on and printed its
own `skipped:` warnings. (The third ISBN is invalid as well, which the exception breakpoint would also have shown.) `binding.break`
takes options: `binding.break(pre: "p valid.size")` runs a debug command at the stop and keeps stopped, and
`binding.break(do: "info ;; watch @count")` runs the commands and *continues*, separated by `;;` or `\n`, which turns a
breakpoint into a probe that does not interrupt the run.

=== Scripting the debugger

Everything typed at the prompt can be given on the command line, which is how to use the debugger in a script, a Makefile or an
automated agent. `-e` runs commands (separated by `;;`) at the first stop, `-x file` runs a file of commands, `RUBY_DEBUG_COMMANDS`
and `RUBY_DEBUG_INIT_SCRIPT` do the same from the environment, and `+~/.rdbgrc+` (debug commands) and `+~/.rdbgrc.rb+` (Ruby) run at
every session. A final `q!` ends the session without a prompt:

[source,bash]

=== Remote debugging

A program without a terminal (a daemon, a container, a process whose standard streams are pipes) can still be debugged. It
opens a port, and a console attaches to it.

[cols="2,4",options="header"]
|===
| Way to open the port | Notes
| `rdbg --open target.rb` (`-O`)
| Opens a UNIX domain socket and waits for a client at the first line; `--nonstop` does not wait
| `rdbg --open --port 12345 target.rb`
| TCP on `127.0.0.1:12345` instead (`--host` to change; `--port-range n` to try the next ports)
| `require "debug/open"` or `"debug/open_nonstop"`
| The same, from inside the program; `RUBY_DEBUG_PORT` selects TCP
| `RUBY_DEBUG_OPEN=true ruby -r debug target.rb`
| Opens the port with the environment configuration
| `rdbg -A`, `rdbg -A port`, `rdbg -A host port`
| Attach to a socket (the only one in the default directory), to a local port or to a remote host and port
|===

=== Configuration

Every setting has an environment variable `RUBY_DEBUG_<NAME>` and a `config` name. The ones you will change most:

[cols="3,5",options="header"]
|===
| Setting (environment variable) | Meaning
| `show_src_lines` (`RUBY_DEBUG_SHOW_SRC_LINES`)
| Source lines shown at a stop (default 10)
| `show_frames` (`RUBY_DEBUG_SHOW_FRAMES`)
| Frames shown at a stop (default 2)
| `no_color` (`RUBY_DEBUG_NO_COLOR`, or `NO_COLOR`)
| Disable colours, which you want when saving output
| `skip_path` (`RUBY_DEBUG_SKIP_PATH`)
| Frames and stops in these paths are skipped, such as a framework's directory
| `skip_nosrc` (`RUBY_DEBUG_SKIP_NOSRC`)
| Skip stops in code that has no source
| `postmortem`, `keep_alloc_site`
| Post-mortem mode; remember where objects were allocated so `p` and `pp` show it
| `fork_mode` (`RUBY_DEBUG_FORK_MODE`)
| Which process keeps the debugger after `fork`: `both`, `parent` or `child`
| `nonstop`, `stop_at_load`
| Do not stop at the first line; stop as soon as the debugger loads
| `init_script`, `commands`, `no_rc`
| Commands to run at the first stop, and whether to read `+~/.rdbgrc+`
| `open`, `port`, `host`, `sock_path`, `cookie`, `skip_bp`
| The remote options of the previous section
| `irb_console` (`RUBY_DEBUG_IRB_CONSOLE`)
| Use IRB as the console
| `history_file`, `save_history`
| Where command history is kept
| `log_level` (`RUBY_DEBUG_LOG_LEVEL`)
| Debugger's own logging, for reporting bugs
|===

Other variables: `RUBY_DEBUG_ENABLE=0` stops `require "debug"` from enabling anything (useful in production images that still
contain the call), `RUBY_DEBUG_BB` defines `Kernel#bb` as an alias of `debugger`, and `RUBY_DEBUG_EDITOR` or `EDITOR` select
the editor for `edit`. `config set` changes a setting inside a session, and `config` lists them all with their current values.

=== Debugging under Bundler

A gem that is installed is not necessarily loadable inside `bundle exec`: Bundler restricts `require` to the gems in the
`Gemfile.lock`. In Ruby 4.0 this now matters for both tools, because IRB left the default gems. With a `Gemfile` that does not
list `irb`, `binding.irb` under `bundle exec` still works but prints a warning, and `require "debug"` fails:

[source,text]
----
$ bundle exec ruby t.rb
t.rb:3: warning: irb used to be loaded from the standard library, but is not part of the default gems since Ruby 4.0.0.
You can add irb to your Gemfile or gemspec to fix this error.
...
$ bundle exec ruby -e 'require "debug"'
.../ruby/4.0.0/bundled_gems.rb:60:in 'Kernel.require': cannot load such file -- debug (LoadError)
----

The fix is to list both in the development group:

[source,ruby]
----
# frozen_string_literal: true

source "https://rubygems.org"

gem "shelf", path: "../shelf"

group :development do
  gem "debug", platforms: %i[mri windows]
  gem "irb"
end
----

Source: https://guides.rubygems.org/gemfile-and-gemspec/[RubyGems Guides: Gemfile and gemspec]

With that Gemfile, `bundle exec ruby t.rb` starts the IRB session without a warning, and `rdbg -c -- bundle exec rake test`
debugs a Bundler run. The `platforms:` option limits `debug` to CRuby (`mri`) and Windows. `require: "debug/prelude"` on the `gem` line is a
lighter alternative to `require "debug"`: the prelude only defines `debugger` and `binding.break`, and loads the debugger the
first time one of them is called.

=== Debugging threads and forks

Debugger stops are per thread: `info threads` (or `th`) lists the threads, `th 2` switches to one, and a breakpoint hit in one
thread suspends the others while you inspect. `fork_mode` chooses whether the parent, the child or both keep a debugger after a
`fork`. The README lists support for Ractors as not done yet, so do not rely on stepping inside one (see
xref:programming-languages/ruby/ractors.adoc[Ractors] and xref:programming-languages/ruby/threads-and-the-gvl.adoc[Threads and the GVL]).

== pp and p

`p` is the oldest debugging tool and is often enough. `Kernel#p` writes `inspect` of each argument followed by a newline and
returns its argument, so it can be put in the middle of an expression without changing it. `Kernel#pp` does the same but
lays long values out over several lines. Both write to standard output (use `warn` or `$stderr.puts` if the output must not mix
with the program's).

[source,ruby]
----
# frozen_string_literal: true

require "shelf"

isbn = Shelf::Isbn.new("978-0-596-51774-8")
book = Shelf::Book.new(isbn:, title: "The Ruby Programming Language", author: Shelf::Author.new("Flanagan"))
catalog = Shelf::Catalog.new.add(book)

# p prints inspect and returns its argument, so it can be dropped into the middle of an expression.
count = p(catalog.count) + 1
puts count # => 2

# p with several arguments prints one line each and returns an array; with none it returns nil.
p(1, "two")           # prints 1 and "two"
p                     # prints nothing

# puts and print call to_s, which Data overrides here; inspect shows the structure.
puts book             # The Ruby Programming Language by Flanagan
p book                # one line, however long

# pp wraps at 80 columns and still returns its argument.
returned = pp(book)
puts returned.equal?(book) # => true

# pretty_inspect returns the pp text as a String (with a trailing newline).
puts book.pretty_inspect.lines.size

# The width can be chosen.
PP.pp(book, $stdout, 40)

# An instance-variable object: pp shows nested objects, indented.
pp catalog
----

Output:

Source: https://docs.ruby-lang.org/en/4.0/Kernel.html#method-i-pp[Ruby documentation: Kernel#pp]

The differences to remember:

* `p x` prints `x.inspect`; `puts x` and `print x` print `x.to_s` (and `puts` also expands arrays one element per line). For an
  object whose `to_s` is overridden, `p` is the one that shows the structure.
* `p` with one argument returns it, with several returns an array of them, with none returns `nil` and prints nothing.
  `pp` returns its argument in the same way. Because `p` returns its argument, `pass:c[p(x) + 1]` and `foo(p(bar))` are safe probes.
* `pp` wraps at the *terminal width minus one* (it asks the output with `io/console`, then the `COLUMNS` variable, then assumes
  80, so 79 when it cannot tell). With the output redirected to a file the width is 79 unless `COLUMNS` is set, which is why a
  `pp` in a test log can look different from the same call in a terminal. `PP.pp(obj, out, width)` chooses one, and
  `PP.singleline_pp(obj, out)` writes a single line.
* `pretty_inspect` returns the `pp` text as a String, with the trailing newline. `Kernel#pp` is available without a `require`:
  it loads the `pp` library on first use.
* Both call `inspect` on the objects. A default `inspect` shows every instance variable, which for a large object graph
  (an ActiveRecord-style model, a catalog with a mutex) is thousands of characters. Override `inspect` for a short form, or
  `pretty_print` for a layout, or limit the variables (`pretty_print_instance_variables`).
* `p(isbn:, author:)` uses the value-omission shorthand of Ruby 3.1 to print `+{isbn: ..., author: ...}+`, a labelled print that
  names the variables. In Ruby 3.3 and older that hash prints as `+{:isbn=>...}+`; the new `+{isbn: ...}+` format is the
  Ruby 3.4 `Hash#inspect`.

=== Customising inspect and pretty_print

`inspect` is what IRB, `p`, error messages and the debugger show. `pretty_print(q)` is what `pp`, IRB's result printing (IRB
uses `pp`) and the debugger's `pp` show. The `q` argument is a `PP` object with `group`, `text`, `breakable`, `comma_breakable`
and `seplist`:

[source,ruby]
----
# frozen_string_literal: true

require "shelf"

# Reopening Catalog here only to show the two hooks; real code would put them in the class.
module Shelf
  class Catalog
    # `inspect` feeds p, IRB and error messages: keep it short and free of internals such as the mutex.
    def inspect = "#<Shelf::Catalog #{count} books>"

    # `pretty_print` feeds pp (and IRB). It receives a PP object and builds a layout.
    def pretty_print(pp)
      pp.group(1, "#<Shelf::Catalog", ">") do
        pp.breakable
        pp.seplist(to_a, -> { pp.comma_breakable }) { |book| pp.text(book.title.inspect) }
      end
    end
  end
end

isbn = Shelf::Isbn.new("978-0-596-51774-8")
author = Shelf::Author.new("Flanagan")
catalog = Shelf::Catalog.new
catalog.add(Shelf::Book.new(isbn:, title: "The Ruby Programming Language", author:))
catalog.add(Shelf::Book.new(isbn:, title: "Ruby Under a Microscope", author:))
catalog.add(Shelf::Book.new(isbn:, title: "Practical Object-Oriented Design", author:))

p catalog
pp catalog

# A labelled print: the shorthand hash makes the output name the variable.
p(isbn:, author:)
----

Output:

[source,text]
----
#<Shelf::Catalog 3 books>
#<Shelf::Catalog
 "The Ruby Programming Language",
 "Ruby Under a Microscope",
 "Practical Object-Oriented Design">
{isbn: #<data Shelf::Isbn digits="9780596517748">, author: #<data Shelf::Author name="Flanagan">}
----

Source: https://docs.ruby-lang.org/en/4.0/PP.html[Ruby documentation: PP]

`Data` and `Struct` already define both methods (`+#<data Shelf::Isbn digits="...">+`), which is why they read well at a prompt.
Keep `inspect` free of secrets: it ends up in logs, exception messages (`NoMethodError` for older Rubies printed the receiver's
`inspect`) and IRB history.

=== Printing without a debugger

A few idioms cover most print debugging, and all of them keep working in a script that has no debugger, a container or a CI
log:

[source,ruby]
----
# frozen_string_literal: true

require "shelf"

# A tiny tracing helper: prints to $stderr (so it never mixes with program output),
# names the caller, and returns the value so it can wrap any expression.
def dbg(value, label = nil)
  where = caller_locations(1, 1).first
  warn "[#{File.basename(where.path)}:#{where.lineno} #{where.base_label}] #{label || value.class}: #{value.inspect}"
  value
end

def title_letters(books)
  books.sum { |book| dbg(book.title.length, "title length") }
end

isbn = Shelf::Isbn.new("978-0-596-51774-8")
author = Shelf::Author.new("Flanagan")
books = [Shelf::Book.new(isbn:, title: "Ruby", author:), Shelf::Book.new(isbn:, title: "Rails", author:)]

# tap: look at an intermediate value without breaking the chain.
titles = books.map(&:title).tap { |list| warn "titles: #{list.inspect}" }.map(&:upcase)
puts titles.inspect

# dbg: wrap an expression, keep its value.
puts dbg(title_letters(books))

# warn with uplevel: reports the caller's line, like a library deprecation warning.
def old_title_letters(books)
  warn "old_title_letters is deprecated, use title_letters", uplevel: 1
  title_letters(books)
end
old_title_letters(books)
----

Source: https://docs.ruby-lang.org/en/4.0/Kernel.html#method-i-caller_locations[Ruby documentation: Kernel#caller_locations]

Standard output of this script:

[source,text]
----
["RUBY", "RAILS"]
9
----

and standard error:

[source,text]
----

[e11_print_debugging.rb:14 title_letters] title length: 4
[e11_print_debugging.rb:14 title_letters] title length: 5
[e11_print_debugging.rb:26 <main>] Integer: 9
e11_print_debugging.rb:33: warning: old_title_letters is deprecated, use title_letters
[e11_print_debugging.rb:14 title_letters] title length: 4
[e11_print_debugging.rb:14 title_letters] title length: 5
----

Source: https://docs.ruby-lang.org/en/4.0/Kernel.html#method-i-caller_locations[Ruby documentation: Kernel#caller_locations]

`tap` returns its receiver after yielding it, so it can be inserted anywhere in a method chain; `warn` writes to `$stderr` so
that the program's real output stays clean; `+warn ..., uplevel: 1+` prefixes the message with the *caller's* file and line, the
form libraries use for deprecation warnings; `caller_locations(1, 1)` identifies who called the current method. For a quick
trace of a call chain, `puts caller(0, 5)` prints five lines of the stack, and `ruby -d` (or `$DEBUG = true`) prints each
exception when it is raised, even those that are rescued, which finds an exception that is swallowed. See
xref:programming-languages/ruby/reflection-introspection-and-tracing.adoc[Reflection, Introspection and Tracing] for
`TracePoint`, which is the engine the debugger's `trace` command is made of.

== error_highlight

`error_highlight` (a default gem, loaded by default) adds to the message of `NoMethodError` and `NameError`, and to some
`TypeError` and `ArgumentError` messages, a snippet of the source line and a row of carets under the exact part that failed.
It is useful when one line has several calls, which is the usual way to get a `NoMethodError` on `nil`: the message says
which of `book.author.name` failed. It needs the source file to be readable, so there is no snippet for code that comes from
`eval` or `-e`.

Ruby 4.0 adds to `ArgumentError` (wrong number of arguments, unknown or missing keyword) two snippets: the *caller*, where the
call is made, and the *callee*, where the method's parameters are declared (Ruby 4.0 NEWS, Feature #21543). The script below
triggers six common errors and prints each message the way an uncaught error would show it:

[source,ruby]
----
# frozen_string_literal: true

require "shelf"

isbn = Shelf::Isbn.new("978-0-596-51774-8")
book = Shelf::Book.new(isbn:, title: "The Ruby Programming Language", author: nil)
loan = Shelf::Loan.new(book)
stock = { "Ruby" => 3, "Rails" => 1 }

attempts = {
  "nil receiver" => -> { book.author.name },
  "method typo" => -> { loan.descibe },
  "variable typo" => -> { puts boook.title },
  "hash key typo" => -> { stock.fetch("Rubi") },
  "unknown constant" => -> { Shelf::Catlog.new },
  "bad keyword" => -> { Shelf::Loan.new(book, stat: :lent) }
}

attempts.each do |label, attempt|
  attempt.call
rescue StandardError => e
  puts "--- #{label}: #{e.class}"
  puts e.detailed_message(highlight: false)
end
----

`ErrorHighlight.spot(exception)` returns the location data (`:snippet`, `:first_column`, `:last_column`) so a tool can use it
itself, and the gem formats through `Exception#detailed_message`, which is the right method to override to change what is
shown for an error class. Pass `highlight: false` to get the text without terminal escape codes.

[source,ruby]
----
# frozen_string_literal: true

require "shelf"

isbn = Shelf::Isbn.new("978-0-596-51774-8")
loan = Shelf::Loan.new(Shelf::Book.new(isbn:, title: "Ruby", author: Shelf::Author.new("Flanagan")))

# did_you_mean: the suggestions are data on the exception.
begin
  loan.descibe
rescue NoMethodError => e
  puts e.corrections.inspect            # => [:describe]
  puts e.original_message               # message without the suggestions
end

# The spell checker is usable on its own, with any dictionary.
checker = DidYouMean::SpellChecker.new(dictionary: %w[available lent overdue returned])
puts checker.correct("overdu").inspect  # => ["overdue"]
puts checker.correct("zzz").inspect     # => []

# error_highlight: ask for the location of the failing expression in the source.
begin
  loan.book.author.name.upcase.nope
rescue NoMethodError => e
  spot = ErrorHighlight.spot(e)
  puts spot[:snippet].strip
  puts "columns #{spot[:first_column]}...#{spot[:last_column]}"
  puts e.detailed_message(highlight: false).lines.first
end
----

Output:

[source,text]
----

undefined method 'descibe' for an instance of Shelf::Loan
["overdue"]
[]
loan.book.author.name.upcase.nope
columns 30...35
undefined method 'nope' for an instance of String (NoMethodError)
----

Source: https://docs.ruby-lang.org/en/4.0/Exception.html#method-i-detailed_message[Ruby documentation: Exception#detailed_message]

`message` is the bare text and does not include the snippet or the suggestions: those are added by `detailed_message`, and
`full_message` combines it with the backtrace. A test that compares `e.message` is therefore not affected by either gem, while a
test that compares `e.detailed_message` or the text of an uncaught error is.

Disable it with `ruby --disable=error_highlight` (or `RUBYOPT=--disable=error_highlight`), for example while debugging an
exception object itself.

== did_you_mean

`did_you_mean` (also a default gem and loaded by default) appends `Did you mean?` and up to a few candidates to `NameError`,
`NoMethodError`, `KeyError`, `NoMatchingPatternKeyError` and `LoadError` (for `require` paths). The
suggestions come from a Jaro-Winkler and Levenshtein comparison against the methods, local variables, constants, hash keys or
paths that exist at that point. The output above shows each case: `descibe` suggests `describe`, `boook` suggests the local
variable `book`, `"Rubi"` suggests the key `"Ruby"`, and `Shelf::Catlog` suggests `Shelf::Catalog`.

The data is available to code. `e.corrections` returns the candidates, `e.original_message` the message without them, and the
spell checker works on any list of words (see the example in the previous section):
`DidYouMean::SpellChecker.new(dictionary: words).correct("input")` returns the close matches, which is how a command-line
program can suggest a mistyped subcommand. `DidYouMean.correct_error(MyError, MyChecker)` registers a checker for an error class of your own.

[source,bash]
----
$ ruby --disable=did_you_mean oops.rb
oops.rb:2:in '<main>': undefined method 'descibe' for an instance of Shelf::Loan (NoMethodError)

Shelf::Loan.new(nil).descibe
                    ^^^^^^^^
$ ruby --disable=error_highlight oops.rb
oops.rb:2:in '<main>': undefined method 'descibe' for an instance of Shelf::Loan (NoMethodError)
Did you mean?  describe
----

Source: https://docs.ruby-lang.org/en/4.0/DidYouMean.html[Ruby documentation: DidYouMean]

A suggestion is a guess: it only compares names and does not know your intent, and a "Did you mean?" is sometimes
misleading (a nearly identical method on a different class). To explore the names yourself, use `ls obj` in IRB,
`obj.methods.grep(/pattern/)` and `Module#instance_methods(false)`.

== syntax_suggest

When a file does not parse, Ruby 3.4 and later report the error with Prism, which marks the unmatched keyword and the point where
it noticed. `syntax_suggest` (a default gem since Ruby 3.2, loaded by default) adds a better guess for the most common failure
in a long file, a missing `end`. It re-parses blocks by indentation and prints the block that looks unbalanced, with line numbers.
The file below is missing the `end` of the block in `titles`:

[source,ruby]
----
# frozen_string_literal: true

module Shelf
  class Report
    def initialize(catalog)
      @catalog = catalog
    end

    def titles
      @catalog.map do |book|
        book.title.upcase
    end

    def count = @catalog.count
  end
end
----

(This file is not syntactically valid; it is the input of the demonstration.)

[source,text]
----
$ ruby bad_syntax.rb
bad_syntax.rb: --> bad_syntax.rb

Unmatched keyword, missing `end' ?

   3  module Shelf
   4    class Report
>  9      def titles
> 10        @catalog.map do |book|
> 12      end
  15    end
  16  end

bad_syntax.rb:16: syntax errors found (SyntaxError)
   1 | # frozen_string_literal: true
   2 |
>  3 | module Shelf
     | ^~~~~~ expected an `end` to close the `module` statement
   4 |   class Report
   5 |     def initialize(catalog)
  ~~~~~~
  14 |     def count = @catalog.count
  15 |   end
> 16 | end
     |    ^ unexpected end-of-input, assuming it is closing the parent top level context
----

The first part is `syntax_suggest`: it narrows the problem to `def titles` and `@catalog.map do`, whose `do` has no `end`. The
second part is the parser's own message. With `ruby --disable=syntax_suggest` only the second part is printed, and Ruby
3.2 prints the older `syntax error, unexpected end-of-input` form after the suggestion. The gem
also provides a `syntax_suggest` command that takes a file name, and `SyntaxSuggest.call` for tools. Its guess is a heuristic
based on indentation, so it works best on a consistently indented file; when the highlighted block looks right, look at the
line above it.

Source: https://docs.ruby-lang.org/en/4.0/SyntaxSuggest.html[Ruby documentation: SyntaxSuggest]

== Choosing a tool

[cols="3,3,4",options="header"]
|===
| Situation | Tool | Why
| "What does this method return?", "what methods does this object have?"
| IRB (`ls`, `show_source`, `show_doc`)
| Immediate, no program to run
| A value looks wrong in the middle of a method
| `p`, `pp`, or `binding.irb`
| Cheapest; `binding.irb` also lets you try the next line
| An exception is rescued and hidden somewhere
| `catch ExceptionClass` in `rdbg`, or `ruby -d`
| Stops at the `raise`, with the stack intact
| You do not know the call path to a method
| `trace call /name/` in `rdbg`, or `caller` in the method
| Shows who calls it, and in what order
| An instance variable changes unexpectedly
| `watch @ivar` in `rdbg`
| Stops at the assignment (it is slow, so narrow the scope)
| A process without a terminal
| `rdbg --open` and `rdbg -A`, or VS Code attach
| Debugger and program talk over a socket
| A test run
| `rdbg -c -- bundle exec rake test`, or a `binding.break` in the test
| The failing test is the reproduction
| A crash on startup that leaves no process
| Post-mortem mode
| The frames of the failure stay inspectable
|===

== Where the books are outdated

Older books and blog posts on debugging Ruby describe tools that have since changed or gone:

[cols="3,5",options="header"]
|===
| Old advice | Ruby 4.0 reality
| `ruby -r debug` opening the `(rdb:1)` debugger of the standard library, with its own command set
| That library was replaced. `require "debug"` loads the `debug` gem, whose console is `(rdbg)` and whose commands are in this page. Under Bundler it fails with a `LoadError` unless `debug` is in the `Gemfile`
| `byebug`, `ruby-debug`, `debugger` and `pry` plus `pry-byebug` as the standard debugging setup; `binding.pry`
| `byebug` is superseded by `debug`; `binding.irb` and `binding.break` cover what `binding.pry` was used for. These gems still exist and are community-maintained; this page does not cover them
| `require "irb/completion"` and `require "irb/ext/save-history"` in `.irbrc`, plus `IRB.conf[:AUTO_INDENT] = true`
| Completion and history are built into the Reline editor and are on by default; `irb/ext/save-history` no longer exists (`require` raises `LoadError`) and history is controlled with `IRB.conf[:SAVE_HISTORY]`
| IRB is a part of the standard library, `irb` always available
| IRB is a bundled gem in 4.0, and with Bundler it must be in the `Gemfile`
| Tab completion by regular expressions; `readline` as the line editor
| Reline is the editor, and the type-based completor is the default on 3.4 and later. `readline` is itself a bundled gem
| `+=> {:a=>1}+` in every REPL transcript
| `+=> {a: 1}+` since 3.4, so copy-pasted outputs in old text do not match what you see
| pass:[<code>undefined method `x' for nil:NilClass</code>] in error messages and `NoMethodError` with the receiver's whole `inspect`
| `+undefined method 'x' for nil+` and `for an instance of Foo` (3.3 and 3.4)
| `require "pp"` before using `pp`
| `pp` is available without `require`, and wraps at the terminal width
| `ruby -w` and `$DEBUG` as the way to see problems
| Still valid, plus `Warning[:category]` switches and the tools above (see xref:programming-languages/ruby/reflection-introspection-and-tracing.adoc[Reflection, Introspection and Tracing])
|===
