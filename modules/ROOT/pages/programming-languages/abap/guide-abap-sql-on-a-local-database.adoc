= ABAP Guide: ABAP SQL on a Local Database
:description: Step-by-step guide to ABAP SQL in the local ABAP playground (open-abap 2.14.30): fill a database table, read it with SELECT, WHERE, ORDER BY, DISTINCT, UP TO and COUNT, then change it with INSERT, UPDATE, MODIFY and DELETE.
:keywords: ABAP SQL, SELECT, INTO TABLE, WHERE, ORDER BY, DISTINCT, UP TO n ROWS, COUNT, SELECT SINGLE, INSERT, UPDATE, MODIFY, DELETE, sy-subrc, open-abap, SQLite, step by step, guide

Checked on 2026-11-13 against open-abap 2.14.30 (the abaplint transpiler and runtime, with open-abap-core a9acc41), abaplint 2.120.103 and Node.js 24.21.

== What you build

You write one report named `zsql_claims` that works on a database table of expense claims. It inserts five rows, reads them back in several ways (all rows, filtered rows, sorted rows, the two largest, a count, a single row) and then changes the table with `INSERT`, `UPDATE`, `MODIFY` and `DELETE`. After each statement you read the result that the program prints, and at the end you make a deliberate spelling mistake and read the error message.

The table is `zexp_claim`, the table that the ABAP lab already holds in `src/zexp_claim.tabl.xml`. The lab table is a reduced version of the full claim table used in the reference pages: it has only three columns, `claim_id` (the key, ten characters), `status` (one character: `A` approved, `S` submitted, `R` rejected) and `amount` (a whole number). Behind it the lab keeps a small in-memory SQLite database. Nobody has to install or configure it: the lab creates it, empty, every time a program starts.

The playground is open-abap, a community open-source project, not SAP software. It runs only the part of ABAP SQL that it implements, so this guide uses only statements that were run in it. Results on a real SAP system follow the same rules, but check a program there before you rely on it. Output is written with `WRITE`, the classic list statement, because that is what the playground offers.

== Before you start

* No account is needed: Node.js, the abaplint tools and open-abap install from the public npm registry without signing in. The licences you accept by installing (MIT for the abaplint packages) are listed in the README of the ABAP lab.
* Set up the lab first, with the guide xref:programming-languages/abap/guide-set-up-a-local-abap-playground.adoc[Set Up a Local ABAP Playground]: the folder `abap-lab` with `npm install` done, and an editor such as Visual Studio Code open on it. Do the guide xref:programming-languages/abap/guide-first-abap-program.adoc[Your First ABAP Program] too, so that a report, a `WRITE` statement and the terminal commands are familiar.
* The lab already holds the finished file of this guide, `modules/ROOT/examples/abap-lab/src/zsql_claims.prog.abap`. Type it yourself, block by block, rather than copying it.
* Read xref:programming-languages/abap/abap-sql-basics.adoc[ABAP SQL: Reading Data] and xref:programming-languages/abap/abap-sql-writing-data.adoc[ABAP SQL: Writing Data] if you want the reasons behind each statement. This guide only runs them.
* The figures are drawings of the editor and the terminal, not screenshots. A highlighted box with a number marks the part of the figure that belongs to the step with the same number.

== Steps

Two ideas help from the first line. An ABAP SQL statement is a normal ABAP statement that talks to the database, such as `SELECT`. A variable that you use inside it is written with a leading `@`, for example `+@DATA(all_claims)+`: the `@` tells ABAP that the name is a variable of your program and not a column of the table. After every statement the system field `sy-subrc` tells whether it worked: 0 means success, 4 means that nothing matched or the row could not be written.

=== Change rows with INSERT, UPDATE, MODIFY and DELETE

The next four blocks change the table. They run in this order, and each one reports `sy-subrc`.

[start=11]
. `INSERT` adds one row. The row is built with `+VALUE #( ... )+`, and the `+#+` is allowed here because the target table fixes the type.
. `UPDATE` changes rows that match a `WHERE` condition. The first statement sets the status of claim `C000000002` to `A` and raises its amount by 5 (`pass:c[amount = amount + 5]`, so 35 becomes 40). The second asks for a claim that does not exist: nothing changes and `sy-subrc` is 4.
. `MODIFY` writes a row whether or not it exists: a row with an existing key is replaced, a row with a new key is inserted. The first `MODIFY` replaces claim `C000000004` (its status changes from `R` to `S`), the second inserts a new claim `C000000007` with status `R`.
. `DELETE FROM` removes the rows that match its condition. Only claim `C000000007` still has status `R` (the `MODIFY` changed claim 4), so only it disappears. A last `SELECT` lists the table.
+

----

== Read your first error

Errors are normal. You make one on purpose, where you know the fix. The complete file at this point has the same blocks as the lab file, without its `tag` comment lines.

[start=16]
. Open `src/zsql_claims.prog.abap` and, in the `SELECT DISTINCT` statement of step 7, change `status` in the field list (the word right after `DISTINCT`) to `statuz`. Save the file.
. Run `npm run run:sql`. The transpiler checks the program before it translates anything, stops at the first problem and prints the message; Node.js does not run. The message has four parts: `check_syntax` is the check that failed, `checkFields, field STATUZ not found` says that the table has no such column, and `zsql_claims.prog.abap:57` is the file and the first line of the statement. A few more lines about the transpiler's own code follow; ignore them.
+
image::sap-abap-guide-abap-sql-on-a-local-database-05-first-error.svg["Terminal after npm run run:sql with a misspelled field in a SELECT: the transpiler stops with the line Error: check_syntax, checkFields, field STATUZ not found, zsql_claims.prog.abap:57 and the program does not run; callout 17 marks the error line",width=900]
. Run `npm run lint` to ask abaplint, the static checker of the lab, about the same file. It finds the same problem. The finding reads `file[line, column] - message (rule) [severity]`: line 57, column 3 is where the statement starts, `check_syntax` is the rule, and `[E]` means error.
+
[source,bash]
----
npm run lint
----
+
image::sap-abap-guide-abap-sql-on-a-local-database-06-lint-finding.svg["Terminal after npm run lint: abaplint prints one finding, src/zsql_claims.prog.abap at line 57 column 3, the message checkFields field STATUZ not found, the rule name check_syntax and the severity E, then 1 issue found in 12 files; callout 18 marks the finding",width=900]
. Change `statuz` back to `status`, save and run `npm run run:sql`. The output returns, and `npm run lint` reports `0 issue(s) found`.

== Check the result

`npm run run:sql` ends without an error. Its output begins with `Inserted five rows, sy-subrc = 0` and the five rows, contains the read groups of step 10, and ends with `After the changes` and these six rows:

[source,text]
----
  C000000001 A 120
  C000000002 A 40
  C000000003 A 80
  C000000004 S 10
  C000000005 S 64
  C000000006 S 42
----

`npm run lint` prints `abaplint: 0 issue(s) found`, and `npm test` still passes with the lab's own test class. Run `npm run run:sql` a second time: the output is the same, because the database starts empty on each run.

== Variations

* Change a condition and predict the rows before you run: `WHERE amount > 60`, `+WHERE status <> 'A'+` or `ORDER BY claim_id DESCENDING`.
* Change `UP TO 2 ROWS` to another number, or remove `ORDER BY` from that read and notice that without it the database decides which rows come first.
* Change the key of the first `MODIFY` to a claim that does not exist yet and read the table again: the row is inserted instead of replaced.

== What can go wrong

[cols="2,3,3",options="header"]
|===
|Symptom
|Cause
|Fix

|`Error: check_syntax, checkFields, field STATUZ not found, zsql_claims.prog.abap:57` and no program output
|A column name in the field list of a `SELECT` is misspelled; the table `zexp_claim` has `claim_id`, `status` and `amount` only.
|Open the file and the line named at the end of the message and correct the name.

|A read prints its title but no rows, and neither the transpiler nor `npm run lint` reports anything
|A column name in the `WHERE` condition is misspelled (the test used `amont` for `amount`). The lab does not check names in `WHERE`, so the condition matches nothing.
|When a list is empty although rows exist, read the condition and compare each name with the table.

|`INSERT, sy-subrc = 4` and the table has no new row
|`INSERT` does not replace a row: the key already exists (the test inserted claim `C000000001` again).
|Use a new key, or use `MODIFY` when an existing row may be replaced. Check `sy-subrc` after every write.

|`Error: TypeNameOrInfer, type not found: #, ZSQL_CLAIMS, zsql_claims.prog.abap line 20` and no output
|In the lab, `+VALUE #( ... )+` written inside `+INSERT ... FROM TABLE @( ... )+` has no type to infer, and `npm run lint` does not report it.
|Write the type name: `+VALUE ty_claims( ... )+`.

|The old output appears although you changed the code
|You ran `node output/project/zsql_claims.prog.mjs` yourself after a failed transpile. Node.js ran the files of the last successful build.
|Run `npm run run:sql`: it runs the program only when the transpile succeeded.
|===
