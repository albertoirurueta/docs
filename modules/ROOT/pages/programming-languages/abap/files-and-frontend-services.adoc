:description: How classic ABAP reads and writes files, on the application server with OPEN, READ, TRANSFER, CLOSE and DELETE DATASET and logical file names, and on the user's PC with CL_GUI_FRONTEND_SERVICES, for Standard ABAP 8.16 only (not ABAP Cloud).

include::partial$ai-disclaimer.adoc[]

A business program often has to exchange a file with the outside world: read a bank statement that arrives as a text file,
write a list of expense claims for another system, or let a user pick a spreadsheet on their own computer. ABAP has two
completely separate ways to do this, because a file can live in two places. It can live on the *application server*, the
computer where the ABAP program runs, or on the *front end* (the SAP documentation also says *presentation server*), the
user's own PC where SAP GUI runs. The first way is a set of statements, `OPEN DATASET` and its companions. The second is a
class, `CL_GUI_FRONTEND_SERVICES`, that asks SAP GUI to do the file work on the PC. After reading this page you can write
and read a text file on the application server, choose between text and binary mode and the right encoding, use a logical
file name so that no physical path is written in the program, protect a program against file names that come from outside,
move a file between the user's PC and the system, and name the options that replace files in ABAP Cloud. The page is
written against Standard ABAP release 8.16 (ABAP Platform 2025 in SAP S/4HANA 2025 FPS02). Both ways are classic ABAP only:
the file statements and the front-end class are not part of ABAP for Cloud Development (release 9.20, 2608), whose keyword
documentation has no page for `OPEN DATASET`, and a cloud system has no SAP GUI on a user's PC. Only the first listing could be
run here, in the open-source lab; the others need an SAP system and are labelled as not run here.

== Key terms

* xref:programming-languages/abap/glossary.adoc#application-server[Application server]: the computer that runs the ABAP
  program; the file statements work on its file system.
* xref:programming-languages/abap/glossary.adoc#presentation-server[Presentation server (front end)]: the user's PC on which
  SAP GUI runs; files there are reached through `CL_GUI_FRONTEND_SERVICES`.
* xref:programming-languages/abap/glossary.adoc#file-interface[File interface]: the ABAP statements for files on the
  application server (`OPEN DATASET`, `READ DATASET`, `TRANSFER`, `CLOSE DATASET`, `DELETE DATASET`).
* xref:programming-languages/abap/glossary.adoc#physical-file-name[Physical file name]: the real path and name of a file in
  the notation of the operating system.
* xref:programming-languages/abap/glossary.adoc#logical-file-name[Logical file name]: a platform-independent name that
  customizing links to a physical path, so the program never contains the path.
* xref:programming-languages/abap/glossary.adoc#directory-traversal[Directory traversal]: an attack in which a manipulated
  file name makes a program reach files outside the intended directory.

== Files on the application server

=== The life of a file: open, transfer, close

A program never writes to a file directly. It first *opens* the file, which tells the operating system how the program wants
to use it, then it moves data, then it *closes* the file. Five statements cover this life, and two more move or shorten the
position inside a file.

[cols="2,5"]
|===
| Statement | What it does

| `+OPEN DATASET dset FOR access IN mode+` | Opens the file named in `dset` on the host of the current application server instance. `dset` is a character-like data object holding the physical name. Opening a file that is already open in the program raises an exception.
| `+READ DATASET dset INTO dobj+` | Passes data from the file to the data object, starting at the file pointer, and moves the pointer behind what was read.
| `+TRANSFER dobj TO dset+` | Writes the content of the data object to the file at the file pointer.
| `+CLOSE DATASET dset+` | Closes the file; data still buffered by the operating system is written first. A file that is not closed explicitly is closed when the program ends.
| `+DELETE DATASET dset+` | Deletes the file; it may be open or closed.
| `+GET DATASET dset+` / `+SET DATASET dset+` | Read or change the file pointer and attributes of an open file.
| `+TRUNCATE DATASET dset+` | Sets the end of the file, which shortens it or extends it with hexadecimal zeros.
|===

The *file pointer* is the position in the file where the next read or write happens. It starts at the beginning, except in
append mode, and it moves forward with every read and write.

Source: https://help.sap.com/docs/abap-cloud/abap-keywords-standard-abap/open-dataset[Keyword Documentation for Standard ABAP: OPEN DATASET], https://help.sap.com/docs/abap-cloud/abap-keywords-standard-abap/read-dataset[READ DATASET], https://help.sap.com/docs/abap-cloud/abap-keywords-standard-abap/transfer[TRANSFER], https://help.sap.com/docs/abap-cloud/abap-keywords-standard-abap/close-dataset[CLOSE DATASET], https://help.sap.com/docs/abap-cloud/abap-keywords-standard-abap/delete-dataset[DELETE DATASET], https://help.sap.com/docs/abap-cloud/abap-keywords-standard-abap/get-dataset[GET DATASET], https://help.sap.com/docs/abap-cloud/abap-keywords-standard-abap/set-dataset[SET DATASET] and https://help.sap.com/docs/abap-cloud/abap-keywords-standard-abap/truncate-dataset[TRUNCATE DATASET]

=== Access type: what you may do with the file

The access addition after `FOR` is mandatory.

[cols="2,5"]
|===
| Addition | Effect

| `FOR INPUT` | Opens for reading, pointer at the start. If the file does not exist, `sy-subrc` is 8. You cannot write.
| `FOR OUTPUT` | Opens for writing. An existing file is emptied, a missing file is created. Reading is also allowed.
| `FOR APPENDING` | Opens for adding at the end, and creates the file if it is missing. `READ DATASET` on such a file returns `sy-subrc` 4.
| `FOR UPDATE` | Opens an existing file to change its content, pointer at the start. If the file does not exist, nothing is opened and `sy-subrc` is 8.
|===

`FOR OUTPUT` is the one that surprises newcomers: it destroys the old content at the moment of opening. A log file that must
grow uses `FOR APPENDING`.

Source: https://help.sap.com/docs/abap-cloud/abap-keywords-standard-abap/open-dataset-access[Keyword Documentation for Standard ABAP: OPEN DATASET, access]

=== Mode: text, binary and the legacy forms

The mode addition is also mandatory and decides what the bytes in the file mean.

* `IN BINARY MODE`: the bytes of the data object are written unchanged, and read back unchanged. Use byte-like data objects
  (type `x` or `xstring`) for binary files.
* `+IN TEXT MODE ENCODING ...+`: the file holds characters. Only character-like data objects can be written and read. The
  `ENCODING` addition says how characters are stored: `DEFAULT` (the same as `UTF-8`), `UTF-8` with `SKIPPING BYTE-ORDER MARK`
  or `WITH BYTE-ORDER MARK`, or `NON-UNICODE`. On writing, trailing blanks of a fixed-length character field are cut off (not
  of a `string`) and an end-of-line marker is added; on reading, one call returns one line.
* `IN LEGACY BINARY MODE` and `IN LEGACY TEXT MODE`: for files in the format of a non-Unicode system, where the byte order
  or the code page must be named explicitly.

The Keyword Documentation gives a programming guideline: write text files in UTF-8 and with a byte order mark. The encoding
page adds that a UTF-16 file can only be opened as a binary file.

The end-of-line marker needs one more decision. Without an addition it depends on the operating system of the application
server host, a profile parameter and the markers already used. The documentation therefore recommends the explicit addition
`WITH NATIVE LINEFEED`, `WITH SMART LINEFEED`, `WITH UNIX LINEFEED` or `WITH WINDOWS LINEFEED` after the encoding, and calls
the old `TYPE` addition for setting the marker obsolete.

Source: https://help.sap.com/docs/abap-cloud/abap-keywords-standard-abap/open-dataset-mode[Keyword Documentation for Standard ABAP: OPEN DATASET, mode], https://help.sap.com/docs/abap-cloud/abap-keywords-standard-abap/open-dataset-encoding[OPEN DATASET, encoding] and https://help.sap.com/docs/ABAP_Cloud/abap-cloud-docs_abap-keyword-documentation_abap_keyword_documentation_classic/abapopen_dataset_linefeed.html[OPEN DATASET, WITH LINEFEED]

=== The other additions

* `AT POSITION pos` sets the file pointer in bytes when the file is opened (0 is the start, -1 the end). Free positions suit
  binary files better than text files, and `SET DATASET` is preferred over -1 for the end of the file.
* `MESSAGE msg` receives the operating system's message when opening fails. The documentation says it must always be used:
  without it the syntax check warns, and you cannot learn why `sy-subrc` is 8.
* `IGNORING CONVERSION ERRORS` suppresses the exception `CX_SY_CONVERSION_CODEPAGE` and replaces a character that cannot be
  converted by `#`, or by the character named in `REPLACEMENT CHARACTER`. It is possible for text files, not for binary files.
* `TYPE attr` and `FILTER opcom` are operating-system-specific, and the filter starts an operating system command: avoid them
  unless an administrator asks for them.

Source: https://help.sap.com/docs/abap-cloud/abap-keywords-standard-abap/open-dataset-position[Keyword Documentation for Standard ABAP: OPEN DATASET, position], https://help.sap.com/docs/abap-cloud/abap-keywords-standard-abap/open-dataset-error-handling[OPEN DATASET, error_handling] and https://help.sap.com/docs/abap-cloud/abap-keywords-standard-abap/open-dataset-os-additions[OPEN DATASET, os_additions]

=== A complete example: write, read, delete

The running example is the expense claim. The listing writes two claims as semicolon-separated lines to a text file, reads
them back line by line, deletes the file and shows what a read of the deleted file returns. It uses the lab's reduced claim
fields (claim_id, status, amount); with the full `ZEXP_CLAIM` of
xref:programming-languages/abap/ddic-tables-and-structures.adoc[DDIC Tables and Structures] the line would also carry the
currency and the employee. Every statement is followed by a `sy-subrc` check, which is the habit that the next section
explains.

[source,abap]
----
REPORT zp_file.

TYPES: BEGIN OF ty_claim,
         claim_id TYPE i,
         status   TYPE string,
         amount   TYPE i,
       END OF ty_claim.

DATA claims TYPE STANDARD TABLE OF ty_claim WITH EMPTY KEY.
DATA claim  TYPE ty_claim.
DATA line   TYPE string.
DATA msg    TYPE string.
DATA id     TYPE string.
DATA st     TYPE string.
DATA am     TYPE string.

claims = VALUE #( ( claim_id = 1 status = `NEW`      amount = 120 )
                  ( claim_id = 2 status = `APPROVED` amount = 75 ) ).

CONSTANTS file TYPE string VALUE `claims.csv`.

OPEN DATASET file FOR OUTPUT IN TEXT MODE ENCODING UTF-8 MESSAGE msg.
IF sy-subrc <> 0.
  WRITE: / `Cannot open for writing:`, msg.
  RETURN.
ENDIF.
LOOP AT claims INTO claim.
  line = |{ claim-claim_id };{ claim-status };{ claim-amount }|.
  TRANSFER line TO file.
ENDLOOP.
CLOSE DATASET file.

OPEN DATASET file FOR INPUT IN TEXT MODE ENCODING UTF-8 MESSAGE msg.
IF sy-subrc <> 0.
  WRITE: / `Cannot open for reading:`, msg.
  RETURN.
ENDIF.
DO.
  READ DATASET file INTO line.
  IF sy-subrc <> 0.
    EXIT.
  ENDIF.
  SPLIT line AT ';' INTO id st am.
  WRITE: / |read: { id } { st } { am }|.
ENDDO.
CLOSE DATASET file.

DELETE DATASET file.
WRITE: / |delete sy-subrc = { sy-subrc }|.

OPEN DATASET file FOR INPUT IN TEXT MODE ENCODING UTF-8 MESSAGE msg.
WRITE: / |open after delete sy-subrc = { sy-subrc }|.
----

Run here, in a copy of the ABAP lab. The lab's transpiler runtime has no file system of its own, so the lab's
`setup.mjs` sets `+abap.context.dataset = new MemoryDataset()+` (the class `MemoryDataset` comes from
`@abaplint/runtime`), which keeps the "files" in memory. On a real application server the same statements use the file system
of the host. The output was:

[source,text]
----
read: 1 NEW 120
read: 2 APPROVED 75
delete sy-subrc = 0
open after delete sy-subrc = 8
----

The loop `+DO ... READ DATASET ... EXIT+` is the standard way to read a file: `sy-subrc` becomes 4 when the end of the file is
reached. A second run of the same kind, with two `FOR APPENDING` opens of one file, printed `first`, `second` and then
`sy-subrc = 4` at the end of the file, which shows that appending keeps the old line.

Source: the statements follow https://help.sap.com/docs/abap-cloud/abap-keywords-standard-abap/open-dataset[Keyword Documentation for Standard ABAP: OPEN DATASET], https://help.sap.com/docs/abap-cloud/abap-keywords-standard-abap/read-dataset[READ DATASET] and https://help.sap.com/docs/abap-cloud/abap-keywords-standard-abap/delete-dataset[DELETE DATASET]

=== Return codes and exceptions

The file statements report problems in two ways, the return code `sy-subrc` and class-based exceptions.

[cols="2,3,3"]
|===
| Statement | `sy-subrc`

| `OPEN DATASET` | 0 the file was opened; 8 the operating system could not open it (read the `MESSAGE` text).
| `READ DATASET` | 0 data read; 4 an attempt to read after the end of the file. In a binary file 4 also means that data was read to the end and the target was longer than needed.
| `TRANSFER` | Always 0, whether or not an exception was raised: never test it.
| `CLOSE DATASET` | Always 0 for a file opened without `FILTER`, even if the file was already closed.
| `DELETE DATASET` | 0 deleted; 4 could not be deleted.
|===

The catchable exceptions named on the keyword pages include `CX_SY_FILE_OPEN` (the file is already open, or cannot be opened),
`CX_SY_FILE_AUTHORITY` (no authorization for the file), `CX_SY_TOO_MANY_FILES` (a program may keep at most 100 files open per
internal session, and the platform may allow fewer), `CX_SY_FILE_CLOSE` (the file could not be closed, for instance for lack
of space) and `CX_SY_CODEPAGE_CONVERTER_INIT` and `CX_SY_CONVERSION_CODEPAGE` (a code page problem). Without a `CATCH`, each
one ends the program with a runtime error, for example `OPEN_DATASET_NO_AUTHORITY`.

Source: https://help.sap.com/docs/abap-cloud/abap-keywords-standard-abap/open-dataset[Keyword Documentation for Standard ABAP: OPEN DATASET], https://help.sap.com/docs/abap-cloud/abap-keywords-standard-abap/transfer[TRANSFER], https://help.sap.com/docs/abap-cloud/abap-keywords-standard-abap/close-dataset[CLOSE DATASET] and https://help.sap.com/docs/abap-cloud/abap-keywords-standard-abap/delete-dataset[DELETE DATASET]

=== Binary files and structures

A flat structure can be written to a file, but the documentation warns against text mode for mixed structures. To save numeric
or mixed data it recommends assigning the structure to a byte-like typed field symbol with `+ASSIGN ... CASTING+` and
transferring that, in a binary file. Such a file depends on the byte order and the code page of the system, so it is only
recommended for short-term storage inside the same system. For data that another system must read, write text (CSV or
JSON, see xref:programming-languages/abap/outbound-http-json-and-xml.adoc[Outbound HTTP, JSON and XML]) in UTF-8.

Source: https://help.sap.com/docs/abap-cloud/abap-keywords-standard-abap/transfer[Keyword Documentation for Standard ABAP: TRANSFER] and https://help.sap.com/docs/abap-cloud/abap-keywords-standard-abap/read-dataset[READ DATASET]

== Physical and logical file names

A *physical file name* is the real path in the notation of the operating system, for example a directory on a Linux host. A
file name without an absolute path refers to the directory set by the profile parameter `DIR_HOME`, and with several
application server instances each instance usually has its own file system, unless an administrator shares one. Two problems
follow. A program that contains `+/usr/sap/...+` works on one platform only, and a path written in the code is a security
risk. SAP solves both with *logical file names*.

A logical file name is a name such as `ZEXP_CLAIMS_EXPORT` (an invented name for this example) that customizing links to a
physical path for each operating system. Client-independent names are maintained with transaction FILE, client-dependent ones
with the customizing activity SF01. The program asks the function module `FILE_GET_NAME` for the physical name at runtime. Its
parameters include `LOGICAL_FILENAME` (in upper case), `PARAMETER_1` to `PARAMETER_3` for placeholders in the path and
`INCLUDING_DIR` (set it to `abap_true` to get an absolute path). The exception `FILE_NOT_FOUND` is raised when the logical
name is unknown, and also when a name of data format `DIR` (a directory) is requested without `INCLUDING_DIR`.

[source,abap]
----
DATA log_name  TYPE filename-fileintern VALUE 'ZEXP_CLAIMS_EXPORT'.
DATA phys_name TYPE string.
DATA line      TYPE string VALUE `1;NEW;120`.
DATA msg       TYPE string.

CALL FUNCTION 'FILE_GET_NAME'
  EXPORTING
    logical_filename = log_name
    including_dir    = abap_true
  IMPORTING
    file_name        = phys_name
  EXCEPTIONS
    file_not_found   = 2
    OTHERS           = 4.
IF sy-subrc <> 0.
  MESSAGE 'Logical file name is not defined' TYPE 'E'.
ENDIF.

TRY.
    OPEN DATASET phys_name FOR OUTPUT IN TEXT MODE ENCODING UTF-8
         WITH SMART LINEFEED MESSAGE msg.
    IF sy-subrc <> 0.
      MESSAGE msg TYPE 'E'.
    ENDIF.
    TRANSFER line TO phys_name.
    CLOSE DATASET phys_name.
  CATCH cx_sy_file_authority cx_sy_file_open.
    MESSAGE 'The file cannot be used' TYPE 'E'.
ENDTRY.
----

Requires an SAP system; not run here. The logical file name must first be defined in transaction FILE, and the user needs
the authorization described next. The call of `FILE_GET_NAME` follows the sample of the documentation page on validating
file names.

Source: https://help.sap.com/docs/ABAP_PLATFORM_NEW/7bfe8cdcfbb040dcb6702dada8c3e2f0/9e49819d5b2a440fb508772494b9a473.html[ABAP Platform: Physical and Logical File Names], https://help.sap.com/docs/ABAP_PLATFORM_NEW/7120868b257c4f96b79a2512474ec895/48d59192982b424be10000000a421937.html[Logical File Names], https://help.sap.com/docs/ABAP_PLATFORM_NEW/7120868b257c4f96b79a2512474ec895/48dff95bab21280ce10000000a42189c.html[Function Module FILE_GET_NAME] and https://help.sap.com/docs/ABAP_PLATFORM_NEW/7bfe8cdcfbb040dcb6702dada8c3e2f0/922b318d87f047deb635d505df93f024.html[Validation of File Names]

== Authorizations and safe file names

When a file is opened or deleted, the system performs an *automatic authorization check*. According to the documentation it
uses the authorization object `S_DATASET` and, together with the table `SPTH`, the object `S_PATH`. A missing authorization
raises `CX_SY_FILE_AUTHORITY`. The automatic check is only a minimum, and self-programmed checks with `AUTHORITY-CHECK` may be
needed too (see xref:programming-languages/abap/authority-checks.adoc[Authority Checks]). One rule of the documentation is easy
to miss: use absolute paths, because a relative path is not resolved before the check, so the literal text is compared
instead.

The larger risk is *directory traversal*. If a file name, or part of it, comes from a selection screen, an interface or a
request, a caller may enter something like `../../secret/file` and make the program read or delete a file outside the
intended directory. The keyword documentation names `OPEN DATASET` and `DELETE DATASET` as the statements concerned and gives
three defences:

* use logical file names only and build the physical name with `FILE_GET_NAME` just before the statement; then validation is
  usually not necessary;
* if the user enters a physical name, check it with the function module `FILE_VALIDATE_NAME`, which compares it with a logical
  file name or a valid directory defined in transaction FILE or SF01;
* never pass an unchecked name to `OPEN DATASET` or `DELETE DATASET`.

The documentation also notes that the class `CL_FS_PATH` offers methods to analyze, transform or create file names and path
entries.

Source: https://help.sap.com/docs/abap-cloud/abap-keywords-standard-abap/directory-traversal[Keyword Documentation for Standard ABAP: Directory Traversal], https://help.sap.com/docs/ABAP_PLATFORM_NEW/7bfe8cdcfbb040dcb6702dada8c3e2f0/922b318d87f047deb635d505df93f024.html[ABAP Platform: Validation of File Names] and https://help.sap.com/docs/abap-cloud/abap-keywords-standard-abap/open-dataset[OPEN DATASET]

== Files on the front end

=== The class CL_GUI_FRONTEND_SERVICES

The class `CL_GUI_FRONTEND_SERVICES` lets the program run operating system functions on the PC of the user. It isolates the
program from the operating system of the PC and from the GUI implementation. It supports SAP GUI for Windows, SAP GUI for the
Java Environment and SAP GUI for HTML, and does not support Web Dynpro. The methods that matter for files are these.

[cols="2,5"]
|===
| Methods | Purpose

| `GUI_UPLOAD`, `GUI_DOWNLOAD` | Transfer data between an internal table on the server and a file on the PC.
| `+FILE_...+` methods, for example `FILE_EXIST` | Examine and process files on the PC.
| `+DIRECTORY_...+` methods, for example `DIRECTORY_EXIST` and `DIRECTORY_CREATE` | Examine and process directories on the PC.
| `EXECUTE` | Run an operating system program or open a document.
|===

Most methods of the class call `+CL_GUI_CFW=>FLUSH+` internally, the call that sends buffered instructions to the PC; where the
caller has to do it, the method documentation says so (see
xref:programming-languages/abap/control-framework-and-gui-controls.adoc[Control Framework and GUI Controls] for the automation
queue). Because the work happens in SAP GUI, such a program only makes sense in dialog processing. The keyword example guards
with the function module `GUI_IS_AVAILABLE`, because a program started in the background has no GUI and would end with a
runtime error.

The next listing follows the keyword documentation example, shortened: it writes an XML representation of the claims through
`GUI_DOWNLOAD` in binary mode, then reads the file back with `GUI_UPLOAD`. The path is the example's Windows path and the
`rc` values of the directory methods are checked as there.

[source,abap]
----
DATA gui TYPE c LENGTH 1.
CALL FUNCTION 'GUI_IS_AVAILABLE'
  IMPORTING
    return = gui.
IF gui IS INITIAL.
  RETURN.
ENDIF.

FINAL(file) = `C:\temp\my_temp\claims.xml`.

TYPES data_line TYPE x LENGTH 255.
DATA data_tab TYPE STANDARD TABLE OF data_line WITH EMPTY KEY.

SELECT * FROM zexp_claim INTO TABLE @DATA(claims).
CALL TRANSFORMATION id SOURCE claims = claims
                       RESULT XML data_tab.

cl_gui_frontend_services=>gui_download(
  EXPORTING
    filename = file
    filetype = 'BIN'
  CHANGING
    data_tab = data_tab
  EXCEPTIONS
    OTHERS   = 4 ).
IF sy-subrc <> 0.
  MESSAGE 'File could not be written' TYPE 'I' DISPLAY LIKE 'E'.
  RETURN.
ENDIF.

CLEAR data_tab.
cl_gui_frontend_services=>gui_upload(
  EXPORTING
    filename = file
    filetype = 'BIN'
  CHANGING
    data_tab = data_tab
  EXCEPTIONS
    OTHERS   = 4 ).
IF sy-subrc <> 0.
  MESSAGE 'File could not be read' TYPE 'I' DISPLAY LIKE 'E'.
ENDIF.
----

Requires an SAP system with SAP GUI and a PC directory that exists; not run here. The table name `ZEXP_CLAIM` is the running
example's table, and the keyword page does not use it; the transformation call follows its pattern of writing the data to a
table of byte lines.

Source: https://help.sap.com/docs/ABAP_Cloud/abap-cloud-docs_abap-keyword-documentation_abap_keyword_documentation_classic/abenfrontend_files.html[Keyword Documentation for Standard ABAP: Files on the Presentation Server] and https://help.sap.com/docs/ABAP_PLATFORM_NEW/5a005e044eef436f8b27bbd3f73a3cfc/c89421e2cf1d45c18adf862476234c0c.html[ABAP Platform: CL_GUI_FRONTEND_SERVICES]

=== The older function modules

Before the class existed, programs used function modules for the same jobs. The keyword documentation says that the methods
of `CL_GUI_FRONTEND_SERVICES` replace older function modules, among them `GUI_UPLOAD`, `GUI_DOWNLOAD`, `WS_UPLOAD` and
`WS_DOWNLOAD`. A page of the SAP Support knowledge base that lists replacements for obsolete function modules maps `UPLOAD`
and `WS_UPLOAD` to `GUI_UPLOAD`, `DOWNLOAD` and `WS_DOWNLOAD` to `GUI_DOWNLOAD`, and `WS_QUERY` to the methods `FILE_EXIST` and
`DIRECTORY_EXIST`; in each case the target may be the method of the class or the function module of the same name. Code that
still calls `UPLOAD`, `DOWNLOAD`, `WS_UPLOAD` or `WS_DOWNLOAD`, which older articles and teaching material show, should be
moved to the class.

Source: https://help.sap.com/docs/ABAP_Cloud/abap-cloud-docs_abap-keyword-documentation_abap_keyword_documentation_classic/abenfrontend_files.html[Keyword Documentation for Standard ABAP: Files on the Presentation Server] and https://help.sap.com/docs/SUPPORT_CONTENT/abap/3353525875.html[SAP Support content: NEW FM in Place of Obsolete FM] (a knowledge-base page, not product documentation)

== Which one to use

[cols="3,4"]
|===
| Situation | Use

| A batch job, an interface or an export that nobody watches | Files on the application server, with a logical file name and a UTF-8 text file
| The user picks a local file to load or a place to save a result | `CL_GUI_FRONTEND_SERVICES`, in a dialog program, or ALV's own export (see xref:programming-languages/abap/alv.adoc[ALV (SAP List Viewer)])
| A file that arrives from another system | Application server directory, read by a job; the other system writes there, or sends through RFC or HTTP (see xref:programming-languages/abap/rfc-bapis-and-idocs.adoc[RFC, BAPIs and IDocs])
| A program that will run in ABAP Cloud | No file statements: see the next section
|===

== Alternatives in ABAP Cloud

ABAP for Cloud Development has no application server file system and no SAP GUI, and its keyword documentation has no page for
`OPEN DATASET`; the same lookup succeeds for a statement such as `SELECT`. The work that files do in classic programs is done
differently:

* *A file that a user uploads or downloads in a Fiori app.* A RAP business object keeps the file in a large object field. The
  database table gets fields for the content (`abap.rawstring(0)`), the MIME type and the file name, and the CDS view entity
  marks the content field with the annotation `@Semantics.largeObject`, which names the MIME type and file name fields and can
  list the accepted MIME types. The SAPUI5 documentation describes how a Fiori elements list report or object page then
  enables upload, download and deletion of the file ("stream support"). See
  xref:programming-languages/abap/rap-overview.adoc[RAP Overview] for the business object.
* *A file that another system provides.* The data is fetched or sent with an outbound call, see
  xref:programming-languages/abap/outbound-http-json-and-xml.adoc[Outbound HTTP, JSON and XML], or arrives through an
  inbound OData service, instead of through a shared directory.
* *Data that must be exchanged in batches.* A released API or a business event replaces the file hand-over, see
  xref:programming-languages/abap/rap-business-events.adoc[RAP Business Events].

In a system that offers both worlds, such as S/4HANA on premise, new code that must stay clean-core ready should use these
patterns, and code that only has to run in classic reports can keep the file interface.

Source: https://help.sap.com/docs/ABAP_Cloud/f055b8bf582d4f34b91da667bc1fcce6/18c1c26edc4644d2a15c9ce7852c32d9.html[Defining the Large Object Field in the Data Model], https://help.sap.com/docs/ABAP_Cloud/abap-cloud-docs_abap-keyword-documentation_abap-for-cloud-development/abencds_514907485_anno.html[Semantics.largeObject.acceptableMimeTypes] and https://help.sap.com/docs/SAPUI5/b2f662dd9d7a4ec680056733050b4d34/b236d32d48b74304887b3dd5163548c1.html[SAPUI5: Enabling Stream Support]

== Common mistakes

[cols="2,3"]
|===
| Mistake | Effect and cure

| `FOR OUTPUT` on a file that must keep its content | The old content is deleted at once. Use `FOR APPENDING`.
| No `MESSAGE` addition | `sy-subrc` is 8 and nobody knows why (wrong path, no right, a directory). Always add `MESSAGE`.
| Testing `sy-subrc` after `TRANSFER` or `CLOSE DATASET` | Both always return 0. Catch the exceptions instead.
| Opening the same file twice | `CX_SY_FILE_OPEN`. Close it first.
| Leaving files open | At most 100 per internal session; open files are only closed automatically when the program ends.
| Writing a numeric or mixed structure to a text file | Not possible in text mode. Convert to text, or use a binary file for short-term use inside one system.
| No explicit encoding or line feed | The result depends on the host and on a profile parameter. Write `ENCODING UTF-8` and `+WITH ... LINEFEED+`.
| A file name from a screen or interface used directly | Directory traversal. Use a logical file name or `FILE_VALIDATE_NAME`.
| `CL_GUI_FRONTEND_SERVICES` in a background job | There is no GUI. Guard with `GUI_IS_AVAILABLE` and do not use it in jobs.
| New code with `WS_UPLOAD`, `WS_DOWNLOAD`, `UPLOAD` or `DOWNLOAD` | Obsolete. Use `GUI_UPLOAD` and `GUI_DOWNLOAD` of the class.
|===

== Summary

* A file is on the application server or on the user's PC; ABAP has a separate tool for each, and both are classic ABAP only.
* The file interface is `OPEN DATASET` (access, mode, encoding), `READ DATASET`, `TRANSFER`, `CLOSE DATASET` and `DELETE DATASET`.
  Always add `MESSAGE`, write text files in UTF-8 with an explicit line feed, and remember that `FOR OUTPUT` empties the file.
* Prefer logical file names (transaction FILE, function module `FILE_GET_NAME`) to physical paths, and validate any name that
  comes from outside with `FILE_VALIDATE_NAME` to stop directory traversal.
* Files on the PC go through `CL_GUI_FRONTEND_SERVICES` (`GUI_UPLOAD`, `GUI_DOWNLOAD`), only in dialog programs; the old function
  modules such as `WS_UPLOAD` are obsolete.
* In ABAP Cloud use a RAP large object field, an HTTP call or a released API instead of files.
