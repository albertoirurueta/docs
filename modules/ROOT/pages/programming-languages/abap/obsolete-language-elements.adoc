= Obsolete Language Elements
:description: ABAP statements that still work but are obsolete, such as header lines, OCCURS, RANGES, TABLES, MOVE, CALL METHOD, FORM and CATCH SYSTEM-EXCEPTIONS, each paired with its modern replacement, for Standard ABAP 8.16 and ABAP Cloud 9.20.
:keywords: ABAP, obsolete, deprecated, header line, OCCURS, RANGES, TABLES, MOVE, ADD, COMPUTE, CALL METHOD, FORM, PERFORM, CATCH SYSTEM-EXCEPTIONS, logical database, FIELD-GROUPS, extract, WS_DOWNLOAD, GRAPH_DIALOG, ON CHANGE OF, REFRESH

include::partial$ai-disclaimer.adoc[]

ABAP has kept almost every statement it ever had. When a better way arrived, the
old way was not removed: it was marked obsolete. An obsolete statement still runs, and SAP keeps it only so that old
programs do not break. A newcomer meets obsolete statements the first day, because most books, forum answers and
programs in a real system were written before the modern forms existed. This page lists the obsolete statements you are
most likely to meet, shows each next to the statement that replaces it, runs the pairs that the local playground can run
and says which ones it cannot. It is written against Standard ABAP release 8.16 and ABAP for Cloud Development release
9.20 (2608). Obsolete elements belong to classic Standard ABAP, on premise and in a private cloud system. In ABAP Cloud,
the restricted language version ABAP for Cloud Development, nearly all of them are not allowed at all.

== Before you read

* xref:programming-languages/abap/data-types-and-data-objects.adoc[Data Types and Data Objects]: structures, table types
  and inline declarations, which several replacements use.
* xref:programming-languages/abap/expressions-and-operators.adoc[Expressions, Operators and Assignments]: the
  assignment operators and calculation assignments that replace `MOVE`, `COMPUTE` and `ADD`.
* xref:programming-languages/abap/internal-tables.adoc[Internal Tables]: what a header line is and why the table kinds
  replaced it.
* xref:programming-languages/abap/classes-and-objects.adoc[Classes and Objects]: methods, which replace subroutines and
  are called without `CALL METHOD`.
* xref:programming-languages/abap/exceptions.adoc[Class-Based Exceptions]: `TRY` and `CATCH`, which replace
  `CATCH SYSTEM-EXCEPTIONS`.

== Key terms

* xref:programming-languages/abap/glossary.adoc#obsolete-language-element[Obsolete language element]: a statement or
  addition that still works for old programs but that SAP tells you not to use in new code.
* xref:programming-languages/abap/glossary.adoc#header-line[Header line]: a hidden work area with the same name as an
  internal table, created in old programs and not allowed in classes.
* xref:programming-languages/abap/glossary.adoc#ranges-table[Ranges table]: an internal table of the form sign,
  option, low and high that holds a set of conditions on one value.
* xref:programming-languages/abap/glossary.adoc#subroutine[Subroutine]: a block of code between `FORM` and `ENDFORM`
  that the statement `PERFORM` calls, the old way to split a program into parts.
* xref:programming-languages/abap/glossary.adoc#work-area[Work area]: a single structure that holds one row while you
  read it from or write it to a table.
* xref:programming-languages/abap/glossary.adoc#exception-class[Exception class]: a class whose objects describe an
  error situation and that `TRY` and `CATCH` handle.
* xref:programming-languages/abap/glossary.adoc#abap-cloud[ABAP Cloud]: the restricted language version and
  development model for cloud-ready code, in which obsolete statements are mostly forbidden.

== What obsolete means

The Keyword Documentation gives the rule in one paragraph. The language elements it lists as obsolete are available only
for compatibility with older releases, you may still meet them in older programs, but they should no longer be used in new
programs. Most of them are forbidden in the syntax of classes, so they can be used only outside classes, in reports,
function modules and other classic program parts. The documentation also says that a replacement exists for every
obsolete element and that the replacement is more efficient and easier to read.

The language version decides what the compiler accepts. In ABAP for Cloud Development most elements that Standard ABAP
marks as obsolete are not allowed. The few that are still allowed there are marked as deprecated, which means their
syntax is supported only for a time. The version baseline and the difference between the two language versions are
explained in xref:programming-languages/abap/abap-language-versions-and-released-apis.adoc[Language Versions and Released APIs].

[mermaid]
----
flowchart TD
    A[You meet an obsolete statement] --> B{Where does the code live?}
    B -- In a class or a method --> C[Most obsolete statements are a syntax error here]
    B -- In a report or function module --> D[Standard ABAP still runs it]
    B -- In ABAP Cloud development --> E[Not allowed, or deprecated for a time]
    C --> F[Use the modern form from the table]
    D --> G{Writing new code or fixing old code?}
    G -- New code --> F
    G -- Old code --> H[Leave it, or replace one statement at a time with a test]
    E --> F

== Pairs of obsolete and modern statements

The table lists the pairs a newcomer meets most often. The right-hand column is what you write today. The last column
says where the Keyword Documentation says the obsolete form is forbidden or what else you should know. Every row is
written from the page of the Keyword Documentation for Standard ABAP that describes the obsolete statement; the pages
are listed under References.

[cols="3,3,3",options="header"]
|===
| Obsolete | Modern | What the documentation says

| `+DATA itab TYPE ... WITH HEADER LINE+`
| A table without header line and a separate work area, or an inline declaration such as `+LOOP AT itab INTO DATA(row)+`
| Header lines exist only outside classes and make a statement ambiguous, because the name means the table in one place and the hidden work area in another

| `+DATA: BEGIN OF itab OCCURS 0, ... END OF itab.+` and `+DATA itab TYPE ... OCCURS n+`
| `DATA itab TYPE STANDARD TABLE OF ty_row WITH EMPTY KEY` and a named type for the row
| Forbidden in classes. The statement is exactly a standard table with the default key and an initial size

| Short forms `APPEND itab.`, `INSERT itab.`, `MODIFY itab.`, `COLLECT itab.`, `DELETE TABLE itab.` and a `LOOP AT itab.` without `INTO`, and a `READ TABLE` without target
| The same statements with an explicit work area, `INTO wa`, `FROM wa` or `ASSIGNING <fs>`
| They work only on tables with a header line and are forbidden in classes

| `REFRESH itab`
| `CLEAR itab`, or `FREE itab` to release the memory too
| Equal to `CLEAR itab[]`. The documentation says `CLEAR` or `FREE` can always be used

| `RANGES r FOR dobj`
| `+DATA r TYPE RANGE OF type+`
| `RANGES` creates a table with a header line. Forbidden in classes

| `TABLES dbtab`
| `DATA claim TYPE zexp_claim`, a structure typed with the table or structure name
| Forbidden in classes. Still needed only to pass data to and from the fields of a classic dynpro

| `MOVE a TO b`
| `b = a`
| The documentation says to use only the assignment operators `=` and `?=`

| `+COMPUTE c = a * b+`
| `+c = a * b+`
| The keyword `COMPUTE` is ignored by the assignment, unless the addition `EXACT` is used

| `ADD 1 TO n`
| `pass:c[n += 1]`
| The calculation assignment `pass:c[+=]` replaced `ADD` fully, and its operands can be expressions

| `+CALL METHOD obj->meth EXPORTING ... RECEIVING ...+`
| `+obj->meth( ... )+`, or `+lcl_calc=>double( 21 )+` for a static method
| The documentation says `CALL METHOD` is now only meant for dynamic method calls

| `FORM` and `PERFORM`
| A method of a class, called as `+obj->meth( )+`
| The documentation says not to create subroutines in new programs. Where a subroutine is still required, keep it as a thin wrapper around a method

| `PERFORM subr(prog)`
| `PERFORM subr IN PROGRAM prog`, or better a method or function module
| Forbidden in classes. External subroutine calls are obsolete anyway

| `CATCH SYSTEM-EXCEPTIONS` and `ENDCATCH`
| `TRY`, `CATCH cx_sy_zerodivide` and `ENDTRY`
| Each catchable runtime error has an exception class today. The two structures cannot be used in the same processing block

| `ON CHANGE OF field` and `ENDON`
| An `IF` that compares the field with an explicitly declared helper variable
| Forbidden in classes. The hidden helper variable is global to the program, which makes the structure error prone

| `+SORT itab BY <fs>+` and `+AT <fs>+` inside `LOOP`
| The component name in parentheses, `+SORT itab BY (name)+`
| Field symbols as sort or group criteria need header lines

| `FIELD-GROUPS`, `INSERT` into a field group and `EXTRACT`
| An internal table, or several
| Extracts have no data type and one dataset per program. The documentation says to use internal tables

| Logical databases and the event `GET`
| A global class that provides the data as a service
| No new logical databases should be created. The function module `LDB_PROCESS` still reads existing ones
|===

The same page of the Keyword Documentation also lists obsolete system fields, obsolete operand positions, obsolete
language versions and a number of other statements. Not every entry has a one-line replacement, and a few are
useful only to people who maintain very old systems, so this page does not repeat them.

== Header lines and OCCURS

A header line is a work area that Standard ABAP creates for you with the same name as the table. The Keyword
Documentation lists the places that create one: the addition `WITH HEADER LINE`, the old statement string
`+DATA: BEGIN OF ... OCCURS+`, `RANGES`, `SELECT-OPTIONS`, and table parameters of function modules and subroutines. Outside
classes, a statement such as `APPEND itab.` then reads the hidden row, and `itab[]` names the table itself.

The first pair builds the same two lists the old way and the modern way. The first listing uses a header line and the
`OCCURS` form, the second a plain table, an explicit type and an inline work area. Both run in the local playground and
print `total: 155, legacy lines: 1`.

[source,abap]
----
REPORT zobs_hl_old.

TYPES: BEGIN OF ty_item,
         item_no TYPE i,
         amount  TYPE i,
       END OF ty_item.

" obsolete: a table with a header line, and the OCCURS form
DATA items TYPE STANDARD TABLE OF ty_item WITH HEADER LINE.
DATA: BEGIN OF legacy OCCURS 0,
        item_no TYPE i,
      END OF legacy.
DATA total TYPE i.

items-item_no = 1.
items-amount = 120.
APPEND items.
items-item_no = 2.
items-amount = 35.
APPEND items.
legacy-item_no = 7.
APPEND legacy.

LOOP AT items.
  total = total + items-amount.
ENDLOOP.

WRITE / |total: { total }, legacy lines: { lines( legacy ) }|.
----

Source: https://help.sap.com/docs/abap-cloud/abap-keywords-standard-abap/data-occurs[Keyword Documentation for Standard ABAP: DATA, OCCURS] and https://help.sap.com/docs/abap-cloud/abap-keywords-standard-abap/internal-tables-with-header-line[Internal Tables with a Header Line]

[source,abap]
----
REPORT zobs_hl_new.

TYPES: BEGIN OF ty_item,
         item_no TYPE i,
         amount  TYPE i,
       END OF ty_item.

DATA items  TYPE STANDARD TABLE OF ty_item WITH EMPTY KEY.
DATA legacy TYPE STANDARD TABLE OF i WITH EMPTY KEY.
DATA total  TYPE i.

APPEND VALUE #( item_no = 1 amount = 120 ) TO items.
APPEND VALUE #( item_no = 2 amount = 35 ) TO items.
APPEND 7 TO legacy.

LOOP AT items INTO DATA(item).
  total = total + item-amount.
ENDLOOP.

WRITE / |total: { total }, legacy lines: { lines( legacy ) }|.
----

Source: https://help.sap.com/docs/abap-cloud/abap-keywords-standard-abap/data-occurs[Keyword Documentation for Standard ABAP: DATA, OCCURS]

The pitfall of a header line is that two things share one name. The Keyword Documentation shows it with `REFRESH`: after
`REFRESH numbers` on a table with a header line, the table body is empty but the header line still holds the last value
that was assigned to it. The following report reads both and prints which of them is still filled. In a real system it
prints that the header line is filled and the table body is not. It requires an SAP system; not run here, because the
local playground does not model the header line and the body as two separate objects.

[source,abap]
----
REPORT zobs_hl2.

DATA numbers TYPE STANDARD TABLE OF i WITH HEADER LINE.
DATA header_set TYPE abap_bool.
DATA body_set TYPE abap_bool.

DO 3 TIMES.
  numbers = sy-index.
  APPEND numbers.
ENDDO.

REFRESH numbers.

IF numbers IS NOT INITIAL.
  header_set = abap_true.
ENDIF.
IF numbers[] IS NOT INITIAL.
  body_set = abap_true.
ENDIF.
WRITE / |header line filled: { header_set }, table body filled: { body_set }|.
----

Source: https://help.sap.com/docs/abap-cloud/abap-keywords-standard-abap/refresh[Keyword Documentation for Standard ABAP: REFRESH]

== MOVE, COMPUTE and ADD

`MOVE`, `COMPUTE` and `ADD` were the original statements for assigning and calculating, before the assignment operator
`=` and the calculation assignments existed. `MOVE a TO b` does what `b = a` does. The keyword `COMPUTE` in front of an
assignment changes nothing, apart from the addition `EXACT`. `ADD 1 TO n` is `pass:c[n += 1]`. The pair below runs both
ways in the playground and prints `b: 6 c: 12`. The modern listing declares `c` inline at its first use, which `COMPUTE`
does not allow.

[source,abap]
----
REPORT zobs_calc_old.

DATA a TYPE i VALUE 5.
DATA b TYPE i.
DATA c TYPE i.

MOVE a TO b.
ADD 1 TO b.
COMPUTE c = b * 2.
WRITE / |b: { b } c: { c }|.
----

Source: https://help.sap.com/docs/abap-cloud/abap-keywords-standard-abap/move[Keyword Documentation for Standard ABAP: MOVE], https://help.sap.com/docs/abap-cloud/abap-keywords-standard-abap/add[ADD] and https://help.sap.com/docs/abap-cloud/abap-keywords-standard-abap/compute[COMPUTE]

[source,abap]
----
REPORT zobs_calc_new.

DATA a TYPE i VALUE 5.
DATA b TYPE i.

b = a.
b += 1.
DATA(c) = b * 2.
WRITE / |b: { b } c: { c }|.
----

Source: https://help.sap.com/docs/abap-cloud/abap-keywords-standard-abap/add[Keyword Documentation for Standard ABAP: ADD]

== CALL METHOD

In older programs a method is called with `CALL METHOD`, a parameter list with `EXPORTING` and `IMPORTING`, and a result
caught with `RECEIVING`. Today a method is called like a function: the parameters go into parentheses, and a method with
a returning parameter can be written wherever a value is expected. The old statement is not removed; the documentation says
it is now meant for dynamic method calls, where the method name comes from a variable. The two listings call the same
static and instance method and print `r1: 42 r2: 5` in the local playground.

[source,abap]
----
REPORT zobs_call_old.

CLASS lcl_calc DEFINITION.
  PUBLIC SECTION.
    CLASS-METHODS double IMPORTING value TYPE i RETURNING VALUE(result) TYPE i.
    METHODS add IMPORTING a TYPE i b TYPE i RETURNING VALUE(result) TYPE i.
ENDCLASS.

CLASS lcl_calc IMPLEMENTATION.
  METHOD double.
    result = value * 2.
  ENDMETHOD.
  METHOD add.
    result = a + b.
  ENDMETHOD.
ENDCLASS.

START-OF-SELECTION.
  DATA calc TYPE REF TO lcl_calc.
  DATA r1 TYPE i.
  DATA r2 TYPE i.
  CREATE OBJECT calc.
  CALL METHOD lcl_calc=>double EXPORTING value = 21 RECEIVING result = r1.
  CALL METHOD calc->add EXPORTING a = 2 b = 3 RECEIVING result = r2.
  WRITE / |r1: { r1 } r2: { r2 }|.
----

Source: https://help.sap.com/docs/abap-cloud/abap-keywords-standard-abap/call-method-static-method-call-obsolete[Keyword Documentation for Standard ABAP: CALL METHOD, Static Method Call (Obsolete)]

[source,abap]
----
REPORT zobs_call_new.

CLASS lcl_calc DEFINITION.
  PUBLIC SECTION.
    CLASS-METHODS double IMPORTING value TYPE i RETURNING VALUE(result) TYPE i.
    METHODS add IMPORTING a TYPE i b TYPE i RETURNING VALUE(result) TYPE i.
ENDCLASS.

CLASS lcl_calc IMPLEMENTATION.
  METHOD double.
    result = value * 2.
  ENDMETHOD.
  METHOD add.
    result = a + b.
  ENDMETHOD.
ENDCLASS.

START-OF-SELECTION.
  DATA(calc) = NEW lcl_calc( ).
  DATA(r1) = lcl_calc=>double( 21 ).
  DATA(r2) = calc->add( a = 2 b = 3 ).
  WRITE / |r1: { r1 } r2: { r2 }|.
----

Source: https://help.sap.com/docs/abap-cloud/abap-keywords-standard-abap/call-method-static-method-call-obsolete[Keyword Documentation for Standard ABAP: CALL METHOD, Static Method Call (Obsolete)]

== RANGES

`RANGES` declares a table of conditions, the same shape that a selection screen builds, but with a header line. The
modern `TYPE RANGE OF` gives the same table without it, and `VALUE` fills a row in one expression. Both listings print
`50 in range: X`, where `X` is the value of the true flag.

[source,abap]
----
REPORT zobs_rng_old.

RANGES r_amount FOR sy-index.
DATA hit TYPE abap_bool.

r_amount-sign = 'I'.
r_amount-option = 'BT'.
r_amount-low = 10.
r_amount-high = 100.
APPEND r_amount.

IF 50 IN r_amount.
  hit = abap_true.
ENDIF.
WRITE / |50 in range: { hit }|.
----

Source: https://help.sap.com/docs/abap-cloud/abap-keywords-standard-abap/ranges[Keyword Documentation for Standard ABAP: RANGES]

[source,abap]
----
REPORT zobs_rng_new.

DATA r_amount TYPE RANGE OF i.
DATA hit TYPE abap_bool.

APPEND VALUE #( sign = 'I' option = 'BT' low = 10 high = 100 ) TO r_amount.

IF 50 IN r_amount.
  hit = abap_true.
ENDIF.
WRITE / |50 in range: { hit }|.
----

Source: https://help.sap.com/docs/abap-cloud/abap-keywords-standard-abap/ranges[Keyword Documentation for Standard ABAP: RANGES]

== TABLES and REFRESH

The statement `TABLES zexp_claim` creates a structure with the same name as the dictionary table and shares it with every
program of the same program group. The documentation says it is needed only to pass data between a classic dynpro and
the program, and that it is forbidden in classes. The modern way is an ordinary data declaration typed with the table
name. The pair also replaces `REFRESH` with `CLEAR`. The lab table `ZEXP_CLAIM` is a reduced version of the Expense claims
table with the columns `claim_id`, `status` and `amount`, so the listing uses only `claim_id`. Both listings print
`claim: C-1001, ids: 0` in the local playground.

[source,abap]
----
REPORT zobs_tab_old.

TABLES zexp_claim.
DATA ids TYPE STANDARD TABLE OF i WITH EMPTY KEY.

zexp_claim-claim_id = 'C-1001'.
APPEND 1 TO ids.
REFRESH ids.
WRITE / |claim: { zexp_claim-claim_id }, ids: { lines( ids ) }|.
----

Source: https://help.sap.com/docs/abap-cloud/abap-keywords-standard-abap/tables[Keyword Documentation for Standard ABAP: TABLES] and https://help.sap.com/docs/abap-cloud/abap-keywords-standard-abap/refresh[REFRESH]

[source,abap]
----
REPORT zobs_tab_new.

DATA claim TYPE zexp_claim.
DATA ids TYPE STANDARD TABLE OF i WITH EMPTY KEY.

claim-claim_id = 'C-1001'.
APPEND 1 TO ids.
CLEAR ids.
WRITE / |claim: { claim-claim_id }, ids: { lines( ids ) }|.
----

Source: https://help.sap.com/docs/abap-cloud/abap-keywords-standard-abap/tables[Keyword Documentation for Standard ABAP: TABLES]

== FORM and PERFORM

A subroutine is a block between `FORM` and `ENDFORM` that `PERFORM` calls. It was the way to split a program before ABAP
Objects. The Keyword Documentation gives the reasons not to write new ones: the parameter interface has positional
parameters instead of keyword parameters, no real input parameters in pass by reference, only optional typing and no
optional parameters, and every subroutine belongs implicitly to the public interface of its program. It allows them
only as thin wrappers where a method cannot yet be used, for example with `PERFORM ON COMMIT`. Both listings add two
items and print `total: 155`.

[source,abap]
----
REPORT zobs_form_old.

DATA gv_total TYPE i.

START-OF-SELECTION.
  PERFORM add_item USING 120.
  PERFORM add_item USING 35.
  WRITE / |total: { gv_total }|.

FORM add_item USING amount TYPE i.
  gv_total = gv_total + amount.
ENDFORM.
----

Source: https://help.sap.com/docs/abap-cloud/abap-keywords-standard-abap/subroutines[Keyword Documentation for Standard ABAP: Subroutines]

[source,abap]
----
REPORT zobs_form_new.

CLASS lcl_totals DEFINITION.
  PUBLIC SECTION.
    METHODS add_item IMPORTING amount TYPE i.
    METHODS total RETURNING VALUE(result) TYPE i.
  PRIVATE SECTION.
    DATA sum TYPE i.
ENDCLASS.

CLASS lcl_totals IMPLEMENTATION.
  METHOD add_item.
    sum = sum + amount.
  ENDMETHOD.
  METHOD total.
    result = sum.
  ENDMETHOD.
ENDCLASS.

START-OF-SELECTION.
  DATA(totals) = NEW lcl_totals( ).
  totals->add_item( 120 ).
  totals->add_item( 35 ).
  WRITE / |total: { totals->total( ) }|.
----

Source: https://help.sap.com/docs/abap-cloud/abap-keywords-standard-abap/subroutines[Keyword Documentation for Standard ABAP: Subroutines]

The form `PERFORM subr(prog)`, with the program name in parentheses, is a separate obsolete variant. It calls a subroutine
of another program, and the Keyword Documentation calls external subroutine calls critical, because it cannot normally be
determined statically which program group the called program joins. Use a method or a function module as the explicit
interface of a program, as described in
xref:programming-languages/abap/modularization-overview.adoc[Modularization Overview].

== CATCH SYSTEM-EXCEPTIONS

Before class-based exceptions existed, a runtime error that a program could survive was a catchable runtime error. A
program handled one with `CATCH SYSTEM-EXCEPTIONS`: the block stops at the first error, the program continues after
`ENDCATCH` and `sy-subrc` holds the number that the program assigned. If an error occurs that the list does not name, the
program ends with a short dump. Each catchable runtime error now has an exception class, and `TRY` with `CATCH` handles it.
The obsolete listing requires an SAP system; not run here, because the local playground does not support the statement. The
modern listing runs in the playground and prints `division failed`.

[source,abap]
----
REPORT zobs_sysex_old.

DATA a TYPE i VALUE 10.
DATA b TYPE i VALUE 0.
DATA c TYPE i.

CATCH SYSTEM-EXCEPTIONS arithmetic_errors = 4.
  c = a / b.
ENDCATCH.
IF sy-subrc = 4.
  WRITE / 'division failed'.
ENDIF.
----

Source: https://help.sap.com/docs/abap-cloud/abap-keywords-standard-abap/catch-system-exceptions[Keyword Documentation for Standard ABAP: CATCH SYSTEM-EXCEPTIONS] and https://help.sap.com/docs/abap-cloud/abap-keywords-standard-abap/obsolete-catchable-runtime-errors[Obsolete Catchable Runtime Errors]

[source,abap]
----
REPORT zobs_sysex_new.

DATA a TYPE i VALUE 10.
DATA b TYPE i VALUE 0.
DATA c TYPE i.

TRY.
    c = a / b.
  CATCH cx_sy_zerodivide.
    WRITE / 'division failed'.
ENDTRY.
----

Source: https://help.sap.com/docs/abap-cloud/abap-keywords-standard-abap/obsolete-catchable-runtime-errors[Keyword Documentation for Standard ABAP: Obsolete Catchable Runtime Errors]

xref:programming-languages/abap/exceptions.adoc[Class-Based Exceptions] explains `TRY`, `CATCH` and the exception
categories in full.

== ON CHANGE OF and sort criteria by field symbol

Two more structures need a few words and no listing. `ON CHANGE OF field` runs its block when the field differs from
the value it had the last time the statement ran. The program keeps that value in a hidden helper variable that is global
to the program, and the Keyword Documentation calls the structure particularly prone to errors and says to replace it by
branches with explicitly declared helper variables: declare a variable, compare it in an `IF`, and assign the new value.
The forms `+SORT itab BY <fs>+` and `+AT <fs>+` take their column from a field symbol that points into a header line; the
documentation says to use a parenthesized character-like data object holding the component name instead.

Source: https://help.sap.com/docs/abap-cloud/abap-keywords-standard-abap/on-change-of[Keyword Documentation for Standard ABAP: ON CHANGE OF]

== Whole concepts that are obsolete

Some obsolete elements are not one statement but a way of building a program.

* *Logical databases.* A logical database is a program that reads a tree of tables and hands the rows one by one to a
  report through an interface work area and the event `GET`. The Keyword Documentation says they should no longer be
  used, because they rely on global data shared across programs, implicit subroutine calls and event control, and that no
  new logical database should be created. A global class that provides the data as a service replaces them. When you
  must read an existing one from a method, the function module `LDB_PROCESS` can be called there.
* *Extracts.* `FIELD-GROUPS`, `EXTRACT` and a `SORT` or `LOOP` over the extract dataset keep rows of different structures
  in one dataset per program. The documentation says internal tables should be used instead.
* *Interface work areas.* The statement `TABLES` creates a structure shared by the programs of a program group. The
  documentation says such work areas are error prone and are still useful only for classic dynpros.

Source: https://help.sap.com/docs/abap-cloud/abap-keywords-standard-abap/logical-databases-ldb-obsolete[Keyword Documentation for Standard ABAP: Logical Databases (LDB, Obsolete)] and https://help.sap.com/docs/abap-cloud/abap-keywords-standard-abap/obsolete-extracts[Obsolete Extracts]

== Obsolete function modules

Programs also call obsolete function modules, and the language does not mark them. A page of the SAP Support knowledge
base (a knowledge-base page, not product documentation) lists replacements. Among its entries, `WS_UPLOAD` and `UPLOAD`
are replaced by `GUI_UPLOAD`, `WS_DOWNLOAD` and `DOWNLOAD` by `GUI_DOWNLOAD`, each as the function module or as the method of
`CL_GUI_FRONTEND_SERVICES`, `WS_EXECUTE` by the method `EXECUTE` of that class, and `POPUP_TO_DECIDE` by
`POPUP_TO_CONFIRM`. The functions `GRAPH_DIALOG` and `GRAPH_SET_CUA_STATUS` appear in the same list with no replacement
named. The older business graphics are not covered by a modern pair, and a newcomer who finds a call to a `GRAPH_`
function module should treat it as a candidate for a rebuild, not a statement to translate. The file transfer pair is
explained with a listing in
xref:programming-languages/abap/files-and-frontend-services.adoc[Files: Application Server and Front End]. All of these

== Older material you may meet

The book Complete ABAP (SAP PRESS, 1st edition 2016, covering AS ABAP 7.4 and 7.5) is a broad classic source, and it
shows how much of the day-to-day style changed. It calls methods with `CALL METHOD` throughout, including the call of a
static method and of the parent class `super`, whereas today the parenthesized call is the rule and the statement is kept
for dynamic calls. It presents subroutines with `FORM` and `PERFORM` as the normal means to reuse code inside a program,
and it shows a ranges table with a header line, whereas new code writes `TYPE RANGE OF` and uses methods. The book
itself calls a few elements obsolete, among them the `TABLES` addition of a subroutine, macros and interface work areas.
When you learn from it, read the listings for the idea and write the modern form from the table above. The publisher
page of the current edition is listed in the Bibliography of this section.

Programs written before inline declarations also declare every variable at the top and fill tables row by row with a work
area, as described in xref:programming-languages/abap/internal-tables.adoc[Internal Tables].

== Finding and replacing obsolete code

A few habits make the work safe.

* Do not rewrite code that works only because it looks old. Replace obsolete statements when you change that part of a
  program, one statement at a time, and run the tests after each change.
* A tool finds them for you. The ABAP Test Cockpit reports obsolete statements through its check variants, and the
  open-source checker abaplint has rules for several of them. See
  xref:programming-languages/abap/atc-and-code-inspector.adoc[ABAP Test Cockpit (ATC)].
* Moving a program to a class is the usual moment to drop most of them: the syntax check of a class refuses the elements
  that are forbidden there. The step-by-step method for a whole program is the subject of the page on xref:programming-languages/abap/migrating-classic-code-to-abap-cloud.adoc[migrating classic code to ABAP Cloud].
* Where a statement has no entry in the table, look it up in the Keyword Documentation for Standard ABAP under
  Obsolete Language Elements, which gives the replacement on the page of each statement.

== Summary

* Obsolete elements still run, but SAP says not to use them in new code, and most of them are forbidden in classes and in
  ABAP Cloud.
* A replacement exists for each: `+WITH HEADER LINE+` and `OCCURS` give way to explicit tables and work areas, `RANGES` to
  `TYPE RANGE OF`, `TABLES` to a typed data object, `MOVE`, `COMPUTE` and `ADD` to `=` and `pass:c[+=]`, `CALL METHOD` to the
  parenthesized call, `FORM` to methods and `CATCH SYSTEM-EXCEPTIONS` to `TRY`.
* The playground ran every pair above except the obsolete `CATCH SYSTEM-EXCEPTIONS` and the header line pitfall, which
  need a real system.
* Whole concepts such as logical databases and extracts have no one-line pair: rebuild them with classes and internal
  tables.
* Old books show the old forms as normal; read them for the idea and write the modern form.
