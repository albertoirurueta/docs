= Clean Core and Cloud Readiness
:description: What clean core means for ABAP, the four clean core levels A to D, how SAP marks objects as released, classic or not recommended in the Cloudification Repository, and how the ABAP Test Cockpit and a local abaplint run tell you where your custom code stands, for ABAP for Cloud Development 9.20 and SAP S/4HANA 2025 FPS02.
:keywords: ABAP, clean core, clean core level, level A, level B, level C, level D, cloud readiness, Cloudification Repository, released API, classic API, noAPI, successor, ABAP Test Cockpit, ATC, technical debt score, wrapper, abaplint, upgrade-stable
:stem: latexmath

Every company that runs SAP software adds its own programs, tables and apps, and every one of them is a promise to keep working after the next upgrade. Clean core is SAP's name for the discipline of keeping that promise: your additions touch SAP software only through doors that SAP has labelled safe, so that SAP can change the inside without breaking you. This page explains what those labels are, how SAP groups custom code into four clean core levels A to D, where SAP publishes the list of safe and unsafe objects (the Cloudification Repository), which checks measure your code, and what to do about code that fails. It is written against ABAP for Cloud Development release 9.20 (2608, SAP S/4HANA Cloud Public Edition and the SAP BTP ABAP environment) and SAP S/4HANA on premise and Private Edition 2025 FPS02 (October 2026). The levels are defined in the SAP Cloud ALM documentation; the repository and the checks apply to Public Edition, Private Edition and on-premise systems, with the differences stated where they matter. After reading you can say which level a piece of code is on and why, and look up the safe replacement for an object that is not safe.

== Key terms

* xref:programming-languages/abap/glossary.adoc#clean-core[Clean core]: keeping the SAP standard free of changes and extending it only through released or officially classified interfaces, so that upgrades stay simple.
* xref:programming-languages/abap/glossary.adoc#clean-core-level[Clean core level]: one of the four classes A, B, C and D that SAP uses to rate how upgrade-stable a custom object is.
* xref:programming-languages/abap/glossary.adoc#released-api[Released API]: an SAP object that SAP has marked as stable for use by your code.
* xref:programming-languages/abap/glossary.adoc#classic-api[Classic API]: an older SAP object, such as a function module or a class of classic ABAP, that SAP has nominated as the next-best option where no released API exists.
* xref:programming-languages/abap/glossary.adoc#cloudification-repository[Cloudification Repository]: SAP's published list that says, for each SAP object, whether it is released, classic, deprecated or not recommended, and which object replaces it.
* xref:programming-languages/abap/glossary.adoc#abap-test-cockpit[ABAP Test Cockpit]: the SAP tool that runs quality and compatibility checks over development objects and reports the findings with a priority.
* xref:programming-languages/abap/glossary.adoc#wrapper[Wrapper]: a small class of your own that calls a classic API on the inside and is itself released, so that ABAP Cloud code can use it.
* xref:programming-languages/abap/glossary.adoc#abap-cloud[ABAP Cloud]: the development model that combines ABAP for Cloud Development with released APIs only.

== What clean core means

An upgrade replaces SAP's code with newer code. If your own code only calls SAP objects that SAP promised not to change, the upgrade cannot break it. If your code calls an internal helper that SAP never promised to keep, or if you edited the SAP code itself, the upgrade can break it, and somebody has to repair it by hand. Clean core is the habit of choosing the first kind of dependency. SAP does not ask you to give up extensions: it asks that they stay on the outside of the standard and use its doors.

Two words are used for two related questions. Cloud readiness asks whether your custom code could run in a cloud system, where only ABAP for Cloud Development and released objects are allowed. Clean core asks the broader question of how stable your code is across upgrades in whichever system it runs, including systems that still allow classic ABAP. The same list of SAP objects answers both, and the same ABAP Test Cockpit machinery does the checking.

== The four clean core levels

The SAP Cloud ALM documentation defines four levels and shows how they appear in the ABAP Test Cockpit. A custom object is rated by the SAP objects it uses, so the definitions below read from the best case to the worst.

[cols="1,2,3,2",options="header"]
|===
|Level |SAP's verdict |What the custom object does |ABAP Test Cockpit result

|A
|Clean core
|Built only on released APIs and released extension points, written in the language version ABAP for Cloud Development. It is upgrade-stable.
|No finding

|B
|Clean core
|Uses only SAP objects and development patterns officially classified as classic APIs or released APIs, written in classic ABAP. It is upgrade-stable, but the stability rests on SAP product experts nominating the API, not on a stability contract.
|Priority 3 finding (information message)

|C
|Conditional clean core
|References SAP internal objects that are neither classified nor intended for customer use. SAP gives no support scope, complete documentation or long-term stability for them, and may later reclassify them as classic (level B) or not recommended (level D).
|Priority 2 finding (warning message)

|D
|Not clean core
|Uses objects SAP has declared not recommended for external use, which includes objects labelled `noAPI`, and includes modifications. It is not upgrade-stable and carries the most technical debt.
|Priority 1 finding (error message)
|===

Source: https://help.sap.com/docs/CloudALM/877c96cf971648b09ee0d0a64f7f4fef/eaa61d6ae6744ccdb0d18820fb8998c9.html[Extensibility, SAP Cloud ALM Application Help]

The Cloud ALM page words its short description of level A as "cloud development and usage of released APIs", and of level B as the usage of best practice or classic APIs. Level D is described as not clean core, not upgrade-stable and not recommended. Modifications are tracked in a separate Cloud ALM figure, and the page on xref:programming-languages/abap/modifications-and-modification-assistant.adoc[Modifications, Modification Assistant and SPAU/SPDD] explains them.

[mermaid]
----
flowchart TD
    S["Your custom object uses an SAP object"] --> Q1{"Is it a released API or a released extension point?"}
    Q1 -->|"yes"| A["Level A: clean core"]
    Q1 -->|"no"| Q2{"Is it a classic API or a classic extension point?"}
    Q2 -->|"yes"| B["Level B: clean core"]
    Q2 -->|"no"| Q3{"Is it classified as not recommended, or is SAP code modified?"}
    Q3 -->|"yes"| D["Level D: not clean core"]
    Q3 -->|"no"| C["Level C: conditional clean core, an internal object"]
----

The diagram reads one use at a time. An object that makes several uses is held to the weakest of them: the definitions say that level C is reached as soon as an internal object is referenced, so a class that uses one released API and one internal object is not level A.

== Released-API tiers in the Cloudification Repository

SAP publishes the classification of its objects in a public GitHub repository, the Cloudification Repository, and as a viewer web page on top of it. The repository holds two kinds of JSON file, and the same object can appear in both with different words.

[cols="2,2,4",options="header"]
|===
|File content |States that occur |Meaning
|Release information (`objectReleaseInfoLatest.json` and the `PCE` files)
|`released`, `deprecated`, `notToBeReleased`
|Whether the object is a released API. A deprecated or not-to-be-released object can name one or more successor objects.
|Classifications (`objectClassifications_SAP.json`)
|`classicAPI`, `noAPI`
|Whether SAP nominated the object as a classic API, or declared it not recommended. Only the classification file speaks about classic APIs.
|===

Read together, the states match the levels: `released` is the base of level A, `classicAPI` of level B, an object found in neither list is an internal object (level C) and `noAPI` belongs to level D. The README of the repository describes the target systems: for the Public Edition content the release information file is used, and for Private Edition and on-premise systems there are files per feature pack stack (for example the 2025 release) plus the classification file, which is what the classic API checks need. The repository calls its Public Edition content "SAP Cloud ERP" and its Private Edition content "SAP Cloud ERP Private".

You can query the files yourself. The following Node.js script looks objects up in both files and prints their state and successors. It was run here against the files downloaded from the `main` branch of the repository on 2026-11-13; the list changes over time, so your output may differ.

[source,javascript]
----
// lookup.mjs: node lookup.mjs NAME [NAME ...]
import fs from 'fs';
const classic = JSON.parse(fs.readFileSync('oc.json', 'utf8')).objectClassifications;
const release = JSON.parse(fs.readFileSync('ori.json', 'utf8')).objectReleaseInfo;
for (const name of process.argv.slice(2)) {
  const c = classic.find(o => o.objectKey === name);
  const r = release.find(o => o.objectKey === name);
  const succ = r?.successors?.map(s => s.objectKey).join(', ');
  console.log(name.padEnd(24),
    ('classification: ' + (c ? c.state : '-')).padEnd(31),
    ('release: ' + (r ? r.state : '-')).padEnd(28),
    succ ? 'successors: ' + succ : '');
}
----

Source: https://github.com/SAP/abap-atc-cr-cv-s4hc[SAP Cloud ERP: released and classic API list for the ATC cloud readiness and clean core checks (Cloudification Repository)]

The two files are fetched from the `src` folder of that repository (`objectClassifications_SAP.json` as `oc.json` and `objectReleaseInfoLatest.json` as `ori.json`). Running the script for six objects that appear in this section's examples printed:

----
CL_ABAP_RANDOM_INT       classification: classicAPI      release: released
POPUP_TO_CONFIRM         classification: classicAPI      release: -
CL_SALV_TABLE            classification: classicAPI      release: -
BAPI_ACC_DOCUMENT_POST   classification: classicAPI      release: notToBeReleased     successors: I_JOURNALENTRYTP
MARA                     classification: -               release: notToBeReleased     successors: I_PRODUCT, I_PRODUCTPROCUREMENT, I_PRODUCTQM, I_PRODUCTSALES, I_PRODUCTSTORAGE_2
I_JOURNALENTRY           classification: -               release: released
----

Reading the rows shows the whole model in miniature. The class `CL_ABAP_RANDOM_INT` is both a classic API and released, so code using it is level A. The function module `POPUP_TO_CONFIRM` and the class `CL_SALV_TABLE` are classic APIs only: level B code may call them, ABAP for Cloud Development may not. The function module `BAPI_ACC_DOCUMENT_POST` is a classic API that SAP marks as not to be released, with the behavior definition `I_JOURNALENTRYTP` as its successor, so a RAP-based replacement exists. The table `MARA` is not to be released, and its successors are CDS views of the product data, among them `I_PRODUCT`. The CDS view `I_JOURNALENTRY` is released. The lesson is the habit: before you read a table or call a function module, look it up, and take the successor if one is named.

The word "tier" is used for the layers of this model in SAP's own material. The sample repository for mitigating missing released APIs shows a three-tier extensibility model, and the generator that creates wrappers is named `tier2-rfc-proxy`. This page uses the repository's states instead, because they are the ones a check can test.

== Checks that measure your code

The checks run in the ABAP Test Cockpit (ATC), the same tool that runs other quality checks over custom code. The README of the Cloudification Repository names them:

* *Usage of Released APIs (Cloudification Repository)* is the cloud readiness check. It reports every use of an object that is not released. It is available in the SAP BTP ABAP environment in its latest version and can be fed with the repository's JSON files in an on-premise system, where you enter the file's URL in the check's attributes.
* *Usage of APIs* is the clean core check. It accepts classic as well as released APIs, which is why it can tell level B from the worse levels.
* *Allowed Enhancement Technologies* checks which enhancement techniques the code uses. The README lists it with Usage of APIs as the Clean Core Check available since August 2025.

The SAP Cloud ALM documentation adds that an ATC variant for clean core should contain three checks: Allowed SAP enhancement technologies, Usage of APIs, and Critical statements. The Critical statements check is to be parameterised as in an SAP blog post that the page names, and extra checks add findings that the Cloud ALM dashboard does not display. SAP recommends running the checks in development and test systems, not in a productive system, because they add load there. The check variants that exist in the repository data include `ABAP_CLOUD_READINESS`, `ABAP_CLEAN_CORE_READINESS`, `ABAP_CLOUD_DEVELOPMENT_DEFAULT` and `ABAP_CLEAN_CORE_DEVELOPMENT`, all with the state released; three older variants are deprecated and name the new one as successor. Which checks a variant contains, and how to start a run in a given release, is described in the ATC documentation of your system; the steps need an SAP system and are not repeated here.

SAP Cloud ALM can turn an ATC result into numbers. After you import the check result, its dashboard shows how many custom objects fall on each level, the clean core share, and a technical debt score. The score is a weighted sum of the ATC messages against your custom objects: ten points per error, five per warning and one per information message, only for objects on levels B, C and D.

[stem]
++++
S = 10E + 5W + I
++++

Here stem:[E], stem:[W] and stem:[I] are the numbers of error, warning and information messages. SAP's own example is five errors, twenty warnings and ten information messages, which give stem:[S = 5 \cdot 10 + 20 \cdot 5 + 10 \cdot 1 = 160] points. A high score means more technical debt, and level A objects do not change it.

Source: https://help.sap.com/docs/CloudALM/877c96cf971648b09ee0d0a64f7f4fef/eaa61d6ae6744ccdb0d18820fb8998c9.html[Extensibility, SAP Cloud ALM Application Help]

== A local cloud-readiness check with abaplint

You do not need an SAP system to see the principle. The open-source tool abaplint can check ABAP source against a chosen language version, and its Cloud language version rejects the statements that ABAP for Cloud Development forbids and function modules it cannot find in the released list. It is a community tool, not an SAP product, and its list is smaller than SAP's ATC check, so a clean abaplint run proves nothing about your system. It is useful as an early warning in a pipeline.

The class below is the running example's claim ticket class, written the old way on purpose. It asks a question through a function module, uses a table with a header line, and uses the statements `MOVE` and `WRITE`.

[source,abap]
----
CLASS zcl_exp_claim_ticket DEFINITION PUBLIC FINAL CREATE PUBLIC.
  PUBLIC SECTION.
    METHODS ask.
    METHODS old_style.
ENDCLASS.

CLASS zcl_exp_claim_ticket IMPLEMENTATION.
  METHOD ask.
    CALL FUNCTION 'POPUP_TO_CONFIRM'
      EXPORTING
        text_question = 'Delete the claim?'.
  ENDMETHOD.

  METHOD old_style.
    DATA lt_claims TYPE STANDARD TABLE OF i WITH HEADER LINE.
    MOVE 1 TO lt_claims.
    APPEND lt_claims.
    WRITE / 'done'.
  ENDMETHOD.
ENDCLASS.
----

Source: https://github.com/abaplint/abaplint[abaplint, ABAP linter]

The configuration selects the Cloud language version and turns on the rules that matter here.

[source,json]
----
{ "global": {"files": "/src/**/*.*"},
  "syntax": {"version": "Cloud", "errorNamespace": "^(Z|Y|LCL_|TY_|LIF_)"},
  "rules": {"parser_error": true, "check_syntax": true, "unknown_types": true,
            "obsolete_statement": true, "forbidden_identifier": true, "cloud_types": true} }
----

Source: https://github.com/abaplint/abaplint[abaplint, ABAP linter]

Running `npx abaplint abaplint-Cloud.json` in a copy of the local ABAP lab (abaplint 2.120.103) printed these findings, after its banner lines:

----
src/zcl_exp_claim_ticket.clas.abap[9, 5]   - Function module "POPUP_TO_CONFIRM" not found/released (check_syntax) [E]
src/zcl_exp_claim_ticket.clas.abap[15, 45] - WITH HEADER LINE is obsolete (obsolete_statement) [E]
src/zcl_exp_claim_ticket.clas.abap[16, 5]  - Statement does not exist in the configured ABAP version(or a parser error), "MOVE" (parser_error) [E]
src/zcl_exp_claim_ticket.clas.abap[18, 5]  - Statement does not exist in the configured ABAP version(or a parser error), "WRITE" (parser_error) [E]
abaplint: 4 issue(s) found, 2 file(s) analyzed
----

With the language version changed to a classic release (`v758`) the same class gave only two findings, the header line and `MOVE`, both flagged as obsolete, and none for the function module or `WRITE`. That difference is the whole idea: the call is allowed in classic ABAP, so it costs you level A and nothing more. The rest of the work is to fix each finding, as the next section describes.

Source: https://github.com/abaplint/abaplint[abaplint, ABAP linter]

== Fixing code that fails a check

Each finding has one of a small number of cures, listed here from best to worst.

. *Use a released replacement.* The repository names successors for objects that have one, such as the behavior definition `I_JOURNALENTRYTP` for `BAPI_ACC_DOCUMENT_POST` above, or released CDS views instead of a table such as `MARA`. This moves the code to level A.
. *Use a classic API.* Where no released API exists, a classic API keeps the code on level B in a classic ABAP system. It is the next-best option, not the goal.
. *Wrap the classic API.* A wrapper is a class of your own, written in classic ABAP, that calls the classic function module or class on the inside, and that you release for use in ABAP Cloud. The code that does the business work then stays in ABAP for Cloud Development and calls only the released wrapper. SAP describes this in its ABAP Cloud API enablement guidelines and in a hands-on workshop that wraps a BAPI; the sample generator for wrappers of RFC-enabled function modules requires an SAP S/4HANA system from release 2022 on premise, with developer extensibility switched on. The wrapper leaves the classic API underneath, so keep it small and keep an eye out for SAP releasing a successor.
. *Replace a modification or an enhancement of SAP code.* Cloud ALM asks you to avoid business modifications, because they are neither clean-core-compliant nor upgrade-stable; moving the change to a released extension point removes the risk.

The page on xref:programming-languages/abap/enhancements-and-badis.adoc[Enhancements and BAdIs] covers the extension points, and a later page of this section walks through migrating a classic program step by step.

== Public Edition, Private Edition and on premise

The levels and the repository are the same everywhere, but the freedom differs. In the SAP BTP ABAP environment and in SAP S/4HANA Cloud Public Edition only ABAP for Cloud Development exists, so level A is not a goal there but a rule: the syntax check rejects whatever is not released. In SAP S/4HANA Cloud Private Edition and in on-premise SAP S/4HANA, classic ABAP stays available, so levels B, C and D are possible and the ATC checks are how you stay out of the worse ones. The classic API list is specific to Private Edition and on-premise systems, and so are the feature-pack files of the repository. This page makes no statement about how a given customer's landscape is licensed or named by SAP in marketing material; the technical documentation still names the editions as written above.

== Older material you may meet

Books and blog posts on classic ABAP were written before the four levels existed. Two examples are the first edition of Complete ABAP (2016, for AS ABAP 7.4 and 7.5) and the first edition of the ABAP RESTful Programming Model (2019, for SAP S/4HANA 1909). Neither speaks of clean core, released APIs or the Cloudification Repository. The first describes the Code Inspector as the check tool and treats modifications and enhancements as ordinary options. The second calls the cloud platform SAP Cloud Platform and mentions the ABAP Test Cockpit only in passing. Their concepts are still sound: internal tables, classes, BAPIs and enhancement points are what level B code is made of. What changed is the question you must ask before using them, which is no longer "does it work" but "which level does it put me on", and where the book says "modify the SAP program" the current answer is a released extension point.

== Summary

* Clean core means that custom code uses only SAP objects that SAP has labelled safe, so that upgrades do not break it.
* The clean core levels run from A (released APIs, ABAP for Cloud Development) through B (classic APIs, classic ABAP) and C (internal objects, conditional) to D (not recommended objects, not clean core).
* The Cloudification Repository publishes the state of each SAP object and, for objects that are not to be released, the successor to use instead.
* ATC checks map to the levels: no finding is level A, an information message level B, a warning level C and an error level D.
* Where no released API exists, wrap a classic API in a released class of your own instead of calling it from ABAP Cloud code.
* A local abaplint run with the Cloud language version is an early warning, not a replacement for the ATC checks of your own system.
