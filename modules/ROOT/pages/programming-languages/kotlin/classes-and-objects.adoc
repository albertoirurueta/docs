= Classes and Objects
:description: Kotlin class declarations, primary and secondary constructors, properties with custom get/set and backing fields, init blocks, visibility modifiers, and the "classes are final by default" rule.
:keywords: Kotlin, classes, primary constructor, secondary constructor, properties, custom getter setter, backing field, init block, visibility modifiers, final by default
:page-aliases: apps/android/kotlin/classes-and-objects.adoc

include::partial$ai-disclaimer.adoc[]

Kotlin classes fold field declarations, a getter, a setter, and constructor parameters into one concise declaration
wherever the intent is a plain data holder -- with everything Java-style, fully explicit, still available when needed.
This page covers primary and secondary constructors, the exact order in which property initializers and `init` blocks run,
properties with custom accessors and backing fields and how they map to JVM getters, setters and fields, visibility
modifiers (including `private set`), nested and inner classes, delegated properties, value classes, and the rule that
classes are `final` by default. The examples use the lending library of this section (`Book`, `Member`, `Loan`).

== The Primary Constructor

Constructor parameters that also become properties are declared directly in the class header:

[source,kotlin]
----
class Member(val name: String, var city: String)

fun main() {
    val ada = Member("Ada", "London")
    println(ada.name)           // Ada: name is a read-only property (val)
    ada.city = "Paris"          // city is mutable (var)
    println(ada.city)
}
----

Output:

[source,text]
----
Ada
Paris
----

This one line replaces what Java would spell out as two fields, a constructor, and (if using getters and setters at all)
three accessor methods. A primary-constructor parameter *without* `val` or `var` is just a plain constructor parameter, not
a property, and is only usable inside an `init` block or another property initializer. Constructor parameters can have
default values and be named at the call site (`Member(city = "Rome", name = "Bo")`), which replaces most of the
telescoping-constructor and builder patterns of Java; a trailing comma is allowed.

The class body is optional: `class Marker` is a complete class, and the empty braces can be dropped.

== Secondary Constructors and `init` Blocks

A class can declare additional constructors with `constructor`, each of which must ultimately delegate to the primary
constructor via `+this(...)+`. `init` blocks run, in declaration order interleaved with property initializers, as part of the
primary constructor's execution -- the place to put validation or derived setup that a one-line parameter list cannot
express:

[source,kotlin]
----
class Rectangle(val width: Double, val height: Double) {

    val area: Double                      // property with no initializer here...

    init {
        require(width > 0 && height > 0) { "dimensions must be positive" }
        area = width * height             // ...assigned inside init
    }

    constructor(side: Double) : this(side, side)   // secondary constructor: delegates to the primary
}

fun main() {
    val square = Rectangle(4.0)           // uses the secondary constructor
    println(square.area)                  // 16.0
}
----

Output:

[source,text]
----
16.0
----

=== Initialisation order

When an instance is created, the work happens in this order: a secondary constructor, if one is called, first delegates to
the primary one; the primary constructor then runs the property initializers and `init` blocks *in the order they appear in
the class body*; finally the body of the secondary constructor, if any, runs. The order of the source text matters:

[source,kotlin]
----
class Loan(val title: String, val days: Int) {
    val label = "Loan of $title"                       // 1. runs first, in source order
    init { println("init 1: $label") }                 // 2.
    val dueIn = days.also { println("property dueIn = $it") }   // 3.
    init { println("init 2: due in $dueIn days") }      // 4.

    constructor(title: String) : this(title, 14) {      // 5. body runs after the primary constructor finished
        println("secondary constructor body")
    }
}

fun main() {
    Loan("Dune")
}
----

Output:

[source,text]
----
init 1: Loan of Dune
property dueIn = 14
init 2: due in 14 days
secondary constructor body
----

A property that is used in an `init` block before its own declaration is not yet initialised, and the compiler rejects the
direct access: this is the same rule that makes calling an `open` method from a constructor dangerous (see
xref:programming-languages/kotlin/inheritance-and-interfaces.adoc[Inheritance and Interfaces]).

== Properties: Custom Getters, Setters, and Backing Fields

Any property can replace its default accessor with a custom one. A *backing field*, referenced as `field` inside the
accessor, is generated automatically whenever an accessor actually reads or writes the property's stored value:

[source,kotlin]
----
class Temperature(celsiusInitial: Double) {
    var celsius: Double = celsiusInitial
        set(value) {
            field = value                           // "field" is the auto-generated backing field
            println("celsius set to $value")
        }

    val fahrenheit: Double                          // a computed, read-only property: no backing field at all
        get() = celsius * 9 / 5 + 32
}

fun main() {
    val t = Temperature(20.0)
    println(t.fahrenheit)       // 68.0: recomputed on every access
    t.celsius = 25.0            // triggers the custom setter
    println(t.fahrenheit)       // 77.0
}
----

Output:

[source,text]
----
68.0
celsius set to 25.0
77.0
----

A property with no custom accessor at all is exactly the field + getter (+ setter, for `var`) pair a Java POJO would
hand-write. Inside the accessors, never write `celsius = value`: it calls the setter again and recurses until the stack
overflows; use `field`.

=== Properties on the JVM

A Kotlin property is not a field: it is a *getter* (and a *setter* for `var`) plus, when needed, a private backing field.
`class Member(val name: String)` compiles to a private final field `name` and a public method `getName()`. For a `Boolean`
property named `isActive` the getter is `isActive()` and the setter `+setActive(...)+`. A property with a custom getter and no
`field` use has no field at all. Four annotations adjust the mapping: `@JvmField` exposes the field itself (no accessors),
`@JvmName` renames an accessor, `const val` (top-level or in an `object`) creates a compile-time constant that is inlined,
and `@get:` / `@set:` use-site targets (see
xref:programming-languages/kotlin/annotations-and-reflection.adoc[Annotations and Reflection]) put an annotation on an
accessor.

=== Restricting a setter and other accessor modifiers

A visibility modifier on an accessor narrows the property's default, which is the usual way to expose state read-only while
keeping it mutable inside:

[source,kotlin]
----
class Shelf {
    var count = 0
        private set                       // anyone can read count; only Shelf can change it

    private val titles = mutableListOf<String>()

    fun add(title: String) {
        titles += title
        count = titles.size
    }
}

fun main() {
    val shelf = Shelf()
    shelf.add("Dune")
    println(shelf.count)                   // 1
    // shelf.count = 5                     // compile error: the setter is private
}
----

== Delegated Properties

A property can delegate its accessors to another object with `by`. The standard delegates are `lazy` (compute on first
use), `Delegates.observable` and `Delegates.vetoable` (react to or veto changes) and `Map`-backed properties, and any class
that provides `getValue` (and `setValue`) operator functions is a delegate:

[source,kotlin]
----
import kotlin.properties.Delegates

class Book(val title: String) {
    val summary: String by lazy {                       // computed once, on first access
        println("computing summary")
        "A summary of $title"
    }

    var copies: Int by Delegates.observable(1) { _, old, new ->
        println("copies: $old -> $new")                   // runs after each change
    }
}

fun main() {
    val book = Book("Dune")
    println(book.summary)
    println(book.summary)                                 // cached
    book.copies = 3
}
----

Output:

[source,text]
----
computing summary
A summary of Dune
A summary of Dune
copies: 1 -> 3
----

== Visibility Modifiers

[cols="1,2"]
|===
|Modifier |Visible from

|`public` (default)
|everywhere -- Kotlin's default, unlike Java's package-private default.

|`internal`
|anywhere in the same Gradle or Maven *module* (one compilation unit of the build) -- Kotlin's addition. Java's package-private
is the nearest analogue, but it is bounded by the *package*, not by the module, so it is not equivalent. On the JVM,
`internal` members are compiled as public with a mangled name, so Java code can still reach them.

|`protected`
|the declaring class and its subclasses (not the whole package, unlike Java's `protected`).

|`private`
|the declaring class only (or, for a top-level declaration, the containing file only).
|===

A nested class can use the `private` members of its outer class when it is given an instance, but the outer class cannot see
the `private` members of its nested classes. Constructors can have their own visibility, written before
the `constructor` keyword: `+class Loan private constructor(...)+` hides the constructor and forces callers through a
factory (see xref:programming-languages/kotlin/objects-and-companion-objects.adoc[Objects and Companion Objects]).

== Nested, Inner and Local Classes

A class declared inside another is *nested* and, unlike Java, does not hold a reference to an outer instance: it is the
equivalent of a Java `static` nested class. Mark it `inner` to get an outer reference (`this@Outer`). A class can also be
declared inside a function, in which case it is local to that function and can capture its variables.

[source,kotlin]
----
class Library(val name: String) {
    class Config(val maxLoans: Int)                 // nested: no access to a Library instance

    inner class Desk(val number: Int) {             // inner: holds a reference to its Library
        fun describe() = "desk $number of $name"    // can use the outer instance's members
    }
}

fun main() {
    val config = Library.Config(3)                  // created without an instance of Library
    val desk = Library("Central").Desk(2)           // created from an instance
    println(config.maxLoans)
    println(desk.describe())
}
----

Output:

[source,text]
----
3
desk 2 of Central
----

== Value Classes

A class with a single property can be declared as an inline *value class*, which the compiler erases to the underlying type
where possible, giving a distinct type with no allocation. Wrap identifiers so the compiler stops you passing an `Isbn`
where a member id is expected:

[source,kotlin]
----
@JvmInline
value class Isbn(val value: String) {
    init { require(value.isNotBlank()) { "ISBN must not be blank" } }
}

fun find(isbn: Isbn) = "looking up ${isbn.value}"

fun main() {
    println(find(Isbn("978-0441172719")))
    // find("978-0441172719")           // compile error: String is not Isbn
}
----

Value classes cannot have more than one stored property, cannot be `open`, and are boxed when used as a nullable, a generic
argument or an interface type.

== Classes Are `final` by Default

Unlike Java, where any non-`final` class can be subclassed, *every Kotlin class is implicitly `final`* -- inheriting from it
requires the base class to be explicitly marked `open`:

[source,kotlin]
----
class Base                  // cannot be subclassed
open class OpenBase         // can be subclassed, see Inheritance and Interfaces

// class Derived : Base()   // compile error: Base is final
class Derived : OpenBase()  // fine
----

This default exists to make inheritance a deliberate, opt-in design decision rather than an accident of omitting `final`
(a principle also argued for in _Effective Java_: design for inheritance or prohibit it) -- and it is why frameworks that
need to subclass application classes behind the scenes (most notably Spring's CGLIB-proxied `@Configuration` and `@Service`
beans) require an "all-open" compiler plugin; see
xref:programming-languages/kotlin/inheritance-and-interfaces.adoc[Inheritance and Interfaces] and
xref:backend/springboot/java-or-kotlin.adoc[Java or Kotlin for Spring Boot?] for how that plugin resolves it.
