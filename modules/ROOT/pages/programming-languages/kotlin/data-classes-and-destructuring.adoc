= Data Classes and Destructuring
:description: Kotlin data classes, the compiler-generated equals/hashCode/toString/copy, componentN() functions, and destructuring declarations in for loops and lambdas.
:keywords: Kotlin, data class, equals, hashCode, toString, copy, componentN, destructuring declarations
:page-aliases: apps/android/kotlin/data-classes-and-destructuring.adoc

include::partial$ai-disclaimer.adoc[]

A `data class` marks a class whose entire purpose is holding values, and the compiler generates the boilerplate
every Java IDE would otherwise auto-generate by hand: structural `equals()` and `hashCode()`, a readable
`toString()`, a `copy()` function and the `componentN()` functions that power destructuring. This page explains what
exactly is generated and from which properties, the rules and restrictions that follow, how a data class looks after
compilation to JVM bytecode, the pitfalls of mutable data classes, and destructuring declarations in all the places
they are allowed. Every example on this page belongs to one running example, a small lending library whose domain
types are `Book`, `Member` and `Loan`; the same domain is used by the other pages of this section.

== Declaring a Data Class

A data class needs a primary constructor with at least one parameter, and every primary-constructor parameter must be
a `val` or a `var`. Here is the first type of the running example:

[source,kotlin]
----
data class Book(
    val isbn: String,
    val title: String,
    val author: String,
    val year: Int,
)

fun main() {
    val a = Book("978-1617299599", "Kotlin in Action", "Aigner et al.", 2024)
    val b = Book("978-1617299599", "Kotlin in Action", "Aigner et al.", 2024)

    println(a)                              // generated toString()
    println(a == b)                         // generated equals(): structural comparison
    println(a === b)                        // two distinct objects
    println(a.hashCode() == b.hashCode())   // generated hashCode(), consistent with equals()
}
----

Output:

[source,text]
----
Book(isbn=978-1617299599, title=Kotlin in Action, author=Aigner et al., year=2024)
true
false
true
----

The compiler generates the following members, all derived from the properties declared in the *primary constructor*
and in the order they are declared:

* `equals(other: Any?)`, which compares every constructor property with `==` (null-safe), so two `Book` values are
  equal when all four properties are equal;
* `hashCode()`, combining the hash codes of the same properties, so it is consistent with `equals()`;
* `toString()`, in the form `+ClassName(property=value, ...)+`;
* `component1()`, `component2()`, and so on, one per constructor property, used by destructuring declarations;
* `copy()`, with one parameter per constructor property, each defaulting to the current value.

The following diagram shows the resulting shape of `Book`. The generated members are drawn after the properties.

[mermaid]
....

        +String isbn
        +String title
        +String author
        +Int year

....

A Java `record` covers the same ground for equality and `toString()`, but it is immutable only, has no `copy()`
and no per-component default values. A Kotlin data class may also have `var` properties, which is both its flexibility
and its main hazard (see <<_mutable_properties_and_hash_based_collections,Mutable Properties and Hash-Based
Collections>>).

== Only Constructor Properties Count

The generated members look only at properties declared in the primary constructor. A property declared in the class
body is ignored by `equals()`, `hashCode()`, `toString()`, `copy()` and `componentN()`:

[source,kotlin]
----
data class Member(val id: Int, val name: String) {
    var lastSeen: String = "never"    // body property: not part of the generated members
}

fun main() {
    val m1 = Member(1, "Ada")
    val m2 = Member(1, "Ada")
    m1.lastSeen = "2026-11-01"

    println(m1 == m2)         // true: lastSeen is ignored
    println(m1)               // Member(id=1, name=Ada)
    println(m1.copy().lastSeen)  // never: copy() builds a fresh instance through the constructor
}
----

Output:

[source,text]
----
true
Member(id=1, name=Ada)
never
----

This is a deliberate feature: it lets a data class carry derived or cached state that should not take part in its
identity. It is also a classic bug source, because `copy()` silently drops body state, as the last line shows.

== Rules and Restrictions

* The primary constructor must have at least one parameter, and each must be marked `val` or `var`.
* A data class cannot be `abstract`, `open`, `sealed` or `inner`. Because it is final, the generated members cannot
  be overridden by a subclass, which is what makes the equality contract safe.
* A data class can implement interfaces and extend another (non-data) class. If a supertype provides a final
  implementation of `equals()`, `hashCode()` or `toString()`, the compiler does not generate that member; if the data
  class body declares its own, that explicit version wins over the generated one.
* Providing explicit implementations of `componentN()` and `copy()` in the data class body is not allowed.
* Equality of a data class that extends another class does not include the properties of the superclass, only
  those of its own primary constructor.

== What a Data Class Compiles To

On the JVM a data class becomes an ordinary final class. For `Book` the compiler produces, in terms of Java:

* a `private final` field and a public getter per `val` (`getIsbn()`, `getTitle()`, ... ; `var` properties also get
  setters);
* `component1()` to `component4()`, `+copy(...)+` and a synthetic `+copy$default(...)+` static method that fills in
  the default arguments when a caller of `copy()` omits some;
* `equals`, `hashCode` and `toString` overrides.

A Java caller sees the getters and `copy`, but not the named arguments: Java has no named or default arguments, so the
`copy` method takes all parameters. If Java code has to construct the class with fewer arguments, declare the primary constructor with
`+@JvmOverloads constructor(...)+`. You can inspect the bytecode with `javap -p -c Book` on the compiled class file,
or in IntelliJ IDEA with the _Show Kotlin Bytecode_ action.

== `copy()`

`copy()` returns a new instance with the same property values, except for whichever named arguments are supplied. It
is the standard way to produce a modified value from an otherwise immutable data class, and it is what makes
immutable domain models practical in Kotlin:

[source,kotlin]
----
data class Loan(
    val book: Book,
    val member: Member,
    val dueDate: String,
    val returned: Boolean = false,
)

fun main() {
    val book = Book("978-0132350884", "Clean Code", "Martin", 2008)
    val ada = Member(1, "Ada")

    val loan = Loan(book, ada, dueDate = "2026-12-01")
    val extended = loan.copy(dueDate = "2026-12-15")
    val closed = extended.copy(returned = true)

    println(loan.dueDate)
    println(extended.dueDate)
    println(closed.returned)
    println(loan.book === closed.book)   // copy() is shallow: both loans share the same Book
}
----

Output:

[source,text]
----
2026-12-01
2026-12-15
true
true
----

`copy()` is a *shallow* copy: nested objects are shared, not cloned. This is harmless when the nested values are
immutable, as `Book` is here, and a source of aliasing bugs when a data class holds a `MutableList` or another
mutable object. Store read-only `List`, `Set` and `Map` types and replace them with new collections on change:

[source,kotlin]
----
data class Shelf(val name: String, val books: List<Book> = emptyList()) {
    fun add(book: Book): Shelf = copy(books = books + book)
}
----

== Mutable Properties and Hash-Based Collections

Because `hashCode()` is computed from the properties, mutating a `var` property of an object that is already stored in
a `HashSet` or used as a `HashMap` key changes its hash. The collection then looks in the wrong bucket and can no
longer find the element:

[source,kotlin]
----
data class Counter(var count: Int)

fun main() {
    val c = Counter(1)
    val set = hashSetOf(c)
    println(c in set)    // true

    c.count = 2          // the hash code changes while c sits in the set
    println(c in set)    // false: the element is still stored, but under its old hash
    println(set.size)    // 1
}
----

Output:

[source,text]
----
true
false
1
----

The rule of thumb is to make data classes immutable (`val` everywhere) and to use `copy()` for changes. Use `var`
only for objects that are never put into hashed collections or compared by value.

== `componentN()` and Destructuring Declarations

Each constructor property also gets a `componentN()` function (`component1()`, `component2()`, ...), which is what
lets a data class be *destructured* into several variables in one statement. The declaration is translated by
the compiler into one call per variable:

[source,kotlin]
----
fun main() {
    val book = Book("978-0134685991", "Effective Java", "Bloch", 2018)

    val (isbn, title, author, year) = book
    println("$title by $author ($year), ISBN $isbn")

    // The line above is equivalent to:
    val isbn2 = book.component1()
    val title2 = book.component2()
    println("$isbn2 $title2")
}
----

Output:

[source,text]
----
Effective Java by Bloch (2018), ISBN 978-0134685991
978-0134685991 Effective Java
----

Destructuring is purely *positional*: the variable names you choose have nothing to do with the property names. Writing
`val (title, isbn) = book` compiles and silently swaps the two strings. Reordering the constructor parameters of a
data class therefore breaks destructuring call sites without any compile error when the types stay compatible, so
destructure data classes with only a few components and prefer plain property access for larger ones.

The unused components of a destructuring declaration can be named `+_+`, which skips the `componentN()` call:

[source,kotlin]
----
val (_, title) = Book("978-0134685991", "Effective Java", "Bloch", 2018)
----

Destructuring is not limited to data classes. `Map.Entry`, `Pair` and `Triple` support it out of the box, and any
class can opt in by defining operator functions named `component1()`, `component2()`, and so on, member or extension:

[source,kotlin]
----
class Range3(val from: Int, val to: Int, val step: Int)

operator fun Range3.component1() = from
operator fun Range3.component2() = to
operator fun Range3.component3() = step

fun main() {
    val (from, to, step) = Range3(0, 10, 2)
    println("$from..$to step $step")
}
----

Output:

[source,text]
----
0..10 step 2
----

== Destructuring in Loops, Lambdas and Returns

Destructuring shows up most often in three places: `for` loops over a map, lambda parameters, and functions that
return a `Pair` or a small data class.

[source,kotlin]
----
fun minMaxYear(books: List<Book>): Pair<Int, Int> =
    books.minOf { it.year } to books.maxOf { it.year }

fun main() {
    val books = listOf(
        Book("1", "Clean Code", "Martin", 2008),
        Book("2", "Effective Java", "Bloch", 2018),
        Book("3", "Refactoring", "Fowler", 1999),
    )

    val perAuthor = books.associate { it.author to it.title }
    for ((author, title) in perAuthor) {       // destructuring Map.Entry in a for loop
        println("$author: $title")
    }

    perAuthor.forEach { (author, _) ->         // lambda parameter destructuring; _ ignores the value
        println("author $author")
    }

    val (oldest, newest) = minMaxYear(books)   // destructuring a returned Pair
    println("$oldest to $newest")

    val titlesByYear = books.map { (_, title, _, year) -> "$year $title" }
    println(titlesByYear)
}
----

Output:

[source,text]
----
Martin: Clean Code
Bloch: Effective Java
Fowler: Refactoring
author Martin
author Bloch
author Fowler
1999 to 2018
[2008 Clean Code, 2018 Effective Java, 1999 Refactoring]
----

The lambda form takes the destructured parameter inside its own parentheses. Writing `+{ author, title -> ... }+`
instead declares two separate lambda parameters, which is a different thing and the usual cause of a type error with a
single map entry.

== Choosing Between Data Classes, Pairs and Value Classes

* Use a *data class* for any value with domain meaning, even for two components. `Pair<String, Int>` says nothing
  about what the two values are; `Book(title, year)` does.
* Use `Pair` and `Triple` for local, short-lived tuples, for example the result of one transformation step.
* Use a `@JvmInline value class` (see xref:programming-languages/kotlin/classes-and-objects.adoc[Classes and Objects])
  when the type wraps exactly one property and must be free of allocation, such as `Isbn(val value: String)`.
