include::partial$ai-disclaimer.adoc[]

Building on xref:programming-languages/kotlin/coroutines-basics.adoc[Coroutines Basics], this page covers what actually
determines *where* a coroutine runs, how it is cancelled cleanly, and how it handles failure -- three concerns Kotlin
bundles together as a coroutine's `CoroutineContext`. It explains the context as a map of elements, the standard
dispatchers and how to switch between them, cooperative cancellation (including cleanup and the traps around
`CancellationException`), timeouts, how exceptions travel through the coroutine tree and what `SupervisorJob`,
`supervisorScope` and `CoroutineExceptionHandler` change. The examples use the lending library of this section and the
`kotlinx-coroutines-core` library.

== `CoroutineContext`

Every coroutine carries a `CoroutineContext` -- a set-like collection of elements, indexed by key, that together describe
how and where it runs. The standard elements are a `Job` (the lifecycle), a `ContinuationInterceptor` (almost always a
`CoroutineDispatcher`), a `CoroutineName` and a `CoroutineExceptionHandler`. Context elements combine with `pass:c[+]`, the
right-hand element replacing a left-hand one with the same key, and an element is read with the indexing operator:

[source,kotlin]
----
import kotlinx.coroutines.*

fun main() = runBlocking {
    val context = Dispatchers.Default + CoroutineName("data-loader")
    println(context[CoroutineName]?.name)            // data-loader

    launch(context) {
        println("inside: ${coroutineContext[CoroutineName]?.name}")
        println("job is active: ${coroutineContext[Job]?.isActive}")
    }.join()

    val renamed = context + CoroutineName("renamed")  // same key: the right-hand element wins
    println(renamed[CoroutineName]?.name)             // renamed
    println(coroutineContext[CoroutineName])          // null: runBlocking's own context has no name
}
----

Output:

[source,text]
----
data-loader
inside: data-loader
job is active: true
renamed
null
----

A child coroutine *inherits* its parent's context and then applies the overrides passed to the builder. Its `Job` is always
a new one, a child of the parent's `Job`, which is how the tree of structured concurrency is built.

....

        PD["Dispatcher: Default"]

== `Dispatchers`

A `Dispatcher` decides which thread(s) a coroutine's code actually runs on -- suspending does not, by itself, guarantee any
particular thread:

[cols="1,2"]
|===
|Dispatcher |Use

|`Dispatchers.Default`
|CPU-bound work (sorting, parsing, computation) -- backed by a thread pool sized to the number of CPU cores (at least two).

|`Dispatchers.IO`
|blocking I/O (network calls, file access, JDBC) -- a larger, elastic thread pool designed for many simultaneously blocked
threads. It shares threads with `Default`, so switching between them does not always need a thread switch.

|`Dispatchers.Main`
|the UI thread on a platform that has one (Android's main thread, the JavaFX or Swing event thread) -- only available when
the corresponding platform artifact is on the classpath.

|`Dispatchers.Unconfined`
|starts in the caller's thread and resumes in whatever thread the suspension function resumed on; meant for special cases such as
tests, not for ordinary code.
|===

`withContext` changes the context for a block and returns its result. It suspends the calling coroutine, runs the block on
the requested dispatcher, and resumes back on the original one automatically once the block completes -- there is no manual
"post back to the UI thread" callback to write:

[source,kotlin]
----
import kotlinx.coroutines.*

data class Book(val isbn: String, val title: String)

fun loadFromDisk(isbn: String): Book {                 // a blocking function: it does not suspend
    Thread.sleep(50)
    return Book(isbn, "Dune")
}

suspend fun loadAndRender(isbn: String) {
    val book = withContext(Dispatchers.IO) {           // switches to the IO dispatcher for this block only...
        loadFromDisk(isbn)
    }
    println("render ${book.title}")                    // ...then back on the caller's dispatcher
}

fun main() = runBlocking {
    loadAndRender("1")
    val onWorker = withContext(Dispatchers.Default) { Thread.currentThread().name.startsWith("DefaultDispatcher-worker") }
    println(onWorker)                                  // true
}
----

Output:

[source,text]
----
render Dune
true
----

Because `withContext` is a suspending function that waits for its block, it does *not* start concurrency: use it to move
blocking or CPU-heavy work off the caller's thread, and `async`/`launch` to run several things at once. To limit
parallelism on a shared pool (for example to cap concurrent database calls), use `Dispatchers.IO.limitedParallelism(4)`.

== Cancellation and Timeouts

Cancellation in coroutines is *cooperative*: a coroutine must actually check for cancellation (which every suspending
function in `kotlinx.coroutines`, like `delay`, does automatically) to actually stop. Calling `cancel()` on a `Job` marks it
cancelled; the coroutine stops at its next suspension point, which throws a `CancellationException` that unwinds the
stack and runs `finally` blocks:

[source,kotlin]
----
import kotlinx.coroutines.*

fun main() = runBlocking {
    val job = launch {
        try {
            repeat(5) { i ->
                println("working $i")
                delay(100)                          // a suspension point: cancellation is checked here
            }
        } finally {
            println("cleanup")                      // runs on cancellation too
        }
    }
    delay(250)
    println("cancelling")
    job.cancelAndJoin()                             // cancel() then join(): wait for the cleanup to finish
    println("done")
}
----

Output:

[source,text]
----
working 0
working 1
working 2
cancelling
cleanup
done
----

A long-running, non-suspending computation (a tight loop with no `delay` or other suspension point inside it) will *not*
respond to cancellation on its own -- `ensureActive()`, `isActive` or `yield()` must be checked explicitly inside such a
loop for it to cooperate:

[source,kotlin]
----
import kotlinx.coroutines.*

fun main() = runBlocking {
    val job = launch(Dispatchers.Default) {
        var count = 0L
        while (isActive) {                          // without this check the loop would never stop
            count++
        }
        println("stopped cleanly")
    }
    delay(50)
    job.cancelAndJoin()
}
----

Output:

[source,text]
----
stopped cleanly
----

=== Cleanup that must suspend

Once a coroutine is cancelled, any further suspending call in it throws `CancellationException` immediately, including calls
in `finally`. To run a suspending cleanup step (for example to flush a buffer or release a remote lock), wrap it in
`withContext(NonCancellable)`:

[source,kotlin]
----
import kotlinx.coroutines.*

fun main() = runBlocking {
    val job = launch {
        try {
            delay(1_000)
        } finally {
            withContext(NonCancellable) {
                delay(50)                           // allowed: this block is not cancellable
                println("released the lock after cancellation")
            }
        }
    }
    delay(100)
    job.cancelAndJoin()
}
----

Output:

[source,text]
----
released the lock after cancellation
----

=== `CancellationException` is not an error

`CancellationException` is how cancellation is signalled, and it is deliberately treated as a normal completion rather than
a failure: it does not cancel the parent and it is not reported by a `CoroutineExceptionHandler`. The corollary is that a
`catch (e: Exception)` (or `runCatching`) around a suspending call also catches it, and unless it is rethrown the coroutine
carries on as though it had not been cancelled. Catch specific exception types, or rethrow:

[source,kotlin]
----
import kotlinx.coroutines.*
import kotlin.coroutines.cancellation.CancellationException

suspend fun safeCall(block: suspend () -> Unit) {
    try {
        block()
    } catch (e: CancellationException) {
        throw e                                     // never swallow cancellation
    } catch (e: Exception) {
        println("recovered from ${e.message}")
    }
}
----

=== Timeouts

`withTimeout` cancels its block automatically if it runs too long, throwing `TimeoutCancellationException` (a subclass of
`CancellationException`); `withTimeoutOrNull` does the same but returns `null` instead of throwing:

[source,kotlin]
----
import kotlinx.coroutines.*

suspend fun slowLookup(): String { delay(1_000); return "found" }

fun main() = runBlocking {
    val result = withTimeoutOrNull(150) { slowLookup() }    // milliseconds; cancelled, so the result is null
    println(result)

    try {
        withTimeout(100) { slowLookup() }
    } catch (e: TimeoutCancellationException) {
        println("timed out: ${e.message}")
    }
}
----

Output:

[source,text]
----
null
timed out: Timed out waiting for 100 ms
----

A timeout is just a cancellation triggered by a timer, so everything above (cooperation, `finally`, `NonCancellable`)
applies. Resources acquired inside a `withTimeout` block must be released in `finally`, because the block can stop at any
suspension point.

== How Exceptions Travel

An exception thrown in a coroutine does not simply disappear: it follows the tree. A failing child cancels its parent
(unless the parent is a supervisor), the parent cancels all the other children, and the exception finally surfaces at the
root. `launch` and `async` differ in how it is exposed:

[mermaid]
....
flowchart TD
    T["child coroutine throws"] --> K{"builder?"}
    K -->|"launch"| L["propagates to the parent immediately"]
    K -->|"async"| A["stored in the Deferred and also propagates to the parent"]
    L --> P{"parent is a supervisor?"}
    A --> P
    P -->|"no"| N["parent cancelled, siblings cancelled, exception rethrown from the scope"]
    P -->|"yes"| S["only this child fails, siblings keep running"]
    N --> R{"root coroutine?"}
    R -->|"yes"| H["CoroutineExceptionHandler or the thread's uncaught handler"]
    R -->|"no"| U["continues up the tree"]
....

The practical consequence for code that calls a scope: wrap the *call to the scope function* in `try`/`catch`, not the
`launch` inside it. A `try`/`catch` around `+launch { }+` catches nothing, because the exception is thrown later, in the
child, and propagates through the job tree:

[source,kotlin]
----
import kotlinx.coroutines.*

fun main() = runBlocking {
    try {
        coroutineScope {
            launch { delay(100); println("sibling finished") }     // never prints: it is cancelled
            launch { throw IllegalStateException("boom") }
        }
    } catch (e: IllegalStateException) {
        println("caught ${e.message}")                              // the scope rethrows the child's failure
    }
}
----

Output:

[source,text]
----
caught boom
----

== `SupervisorJob`

By default (structured concurrency, see xref:programming-languages/kotlin/coroutines-basics.adoc[Coroutines Basics]), one
child's failure cancels every sibling and the parent. A `SupervisorJob` changes that: a child's failure is isolated to that
child, leaving its siblings running -- the shape needed for, say, a screen with several independent widgets that should not
all crash because one of them failed to load. `+supervisorScope { }+` is the scoped form for a single suspend function:

[source,kotlin]
----
import kotlinx.coroutines.*

fun main() = runBlocking {
    val handler = CoroutineExceptionHandler { _, e -> println("handled: ${e.message}") }

    supervisorScope {
        launch(handler) { throw IllegalStateException("widget A failed") }   // this one fails...
        launch { delay(100); println("widget B loaded") }                    // ...but this one is unaffected
        val c = async { throw IllegalStateException("widget C failed") }
        try { c.await() } catch (e: IllegalStateException) { println("await rethrew: ${e.message}") }
    }
}
----

Output:

[source,text]
----
handled: widget A failed
await rethrew: widget C failed
widget B loaded
----

The supervisor only affects its *direct* children: a `launch` nested inside another `launch` still propagates to its parent.
`SupervisorJob()` is a common mistake as an argument of `launch`: `+launch(SupervisorJob()) { ... }+` replaces the parent job
and so *breaks* structured concurrency (the new coroutine no longer has the caller as parent), which defeats the point. Use
a supervisor as part of a scope or `supervisorScope`.

== `CoroutineExceptionHandler`

An uncaught exception from a `launch` coroutine (not `async` -- a `Deferred`&#39;s exception surfaces at `await()` instead) is,
by default, propagated up and, at the root, handed to the thread's uncaught-exception handler, which for a plain `main`
prints the stack trace. A `CoroutineExceptionHandler`, installed on the top-level scope, intercepts it instead:

[source,kotlin]
----
import kotlinx.coroutines.*

fun main() = runBlocking {
    val handler = CoroutineExceptionHandler { _, exception ->
        println("unhandled coroutine failure: ${exception.message}")
    }

    val scope = CoroutineScope(SupervisorJob() + Dispatchers.Default + handler)
    val job = scope.launch { throw IllegalStateException("boom") }    // caught by handler instead of crashing
    job.join()
    println("scope still alive: ${scope.coroutineContext[Job]?.isActive}")
}
----

Output:

[source,text]
----
unhandled coroutine failure: boom
scope still alive: true
----

`CoroutineExceptionHandler` only has an effect on a *root* coroutine (one launched directly in a scope, or a direct child of
a supervisor, not nested inside another coroutine) and is commonly paired with `SupervisorJob` for exactly the "many
independent tasks, log and continue" pattern above. It is a last-resort *logging* hook, not a recovery mechanism: the
coroutine has already failed when the handler runs, and it cannot resume it. On `async`, installing a handler has no
effect, because the exception is kept for `await()`.

== Summary of the Rules

* Choose a dispatcher by the kind of work: `Default` for CPU, `IO` for blocking calls, `Main` for the UI; switch with
  `withContext`, never with `runBlocking`.
* Make loops cancellable with `isActive`, `ensureActive()` or `yield()`; do suspending cleanup in `NonCancellable`.
* Never swallow `CancellationException`; catch specific types, or rethrow.
* A scope function throws what its children throw, so put `try`/`catch` around the scope call.
* Use `SupervisorJob` or `supervisorScope` only for independent children, and a `CoroutineExceptionHandler` only on root
  coroutines, for logging.
