= Basic Types and Variables

Kotlin is statically typed like Java, but leans heavily on type inference so explicit type annotations are the exception
rather than the rule. This page covers `val` and `var` and the reasoning behind preferring `val`, type inference, the
built-in number types with their literals, explicit conversions and overflow behaviour, `Boolean` and `Char`, the three
types at the edges of the hierarchy (`Any`, `Unit`, `Nothing`) and how they relate, arrays, unsigned integers, constants and
type aliases. The examples use the lending library of this section (`Book`, `Member`, `Loan`).

== `val` and `var`

Every declaration is either read-only (`val`, assignable exactly once) or mutable (`var`):

[source,kotlin]
----
fun main() {
    val name = "Ada"        // read-only; "name" cannot be reassigned
    var loans = 0           // mutable
    loans += 1

    val pi: Double = 3.14159   // explicit type annotation (rarely needed: inferred here anyway)

    val title: String          // a val may be assigned later, exactly once, before first use
    if (loans > 0) title = "Dune" else title = "Emma"

    val shelf = mutableListOf("Dune")
    shelf.add("Emma")          // the reference is read-only, the list is not
    // shelf = mutableListOf() // compile error: val cannot be reassigned

    println("$name $loans $pi $title $shelf")
}
----

Output:

[source,text]
----
Ada 1 3.14159 Dune [Dune, Emma]
----

`val` is *not* the same guarantee as Java's `final` on a mutable object -- a `val` reference cannot be reassigned, but if it
refers to a mutable object (for example a `MutableList`), that object's contents can still change. A `val` property with a
custom getter can even return a different value on each read. Prefer `val` by default; reach for `var` only when
reassignment is genuinely needed, and keep the *scope* of every variable as small as possible (declare it where it is first
used, not at the top of the function). Immutability makes code easier to reason about, safe to share between threads, and
allows the compiler to smart-cast the value (see xref:programming-languages/kotlin/null-safety.adoc[Null Safety]). This
preference runs through the whole language -- see
xref:programming-languages/kotlin/data-classes-and-destructuring.adoc[Data Classes and Destructuring] and
xref:programming-languages/kotlin/collections-and-sequences.adoc[Collections and Sequences] for where it matters most.

== Type Inference

The compiler infers a declaration's type from its initializer, so most `val` and `var` declarations carry no explicit type
at all -- `val x: Int = 5` and `val x = 5` compile to the identical type. An explicit type is still required for a function
parameter, and useful whenever the inferred type would be wider or narrower than intended, or when it is not obvious to a
reader:

[source,kotlin]
----
fun main() {
    val count = 5                        // Int
    val ratio = 5.0                      // Double
    val total = 5L                       // Long
    val letter = 'k'                     // Char
    val flag = count > 3                 // Boolean
    val titles = listOf("Dune", "Emma")  // List<String>
    val mixed = listOf(1, "two")         // a list of the common supertype of Int and String
    val empty = emptyList<String>()      // inference needs help: no elements to look at

    val bytes: Byte = 100                // an explicit type changes the literal's type
    val asDouble: Double = 5.0

    println("${count::class.simpleName} ${ratio::class.simpleName} ${total::class.simpleName} ${mixed.size}")
    println("$letter $flag $titles $empty $bytes $asDouble")
}
----

Output:

[source,text]
----
Int Double Long 2
k true [Dune, Emma] [] 100 5.0
----

Inference applies to local variables, properties and function return types (for single-expression functions); the public
API of a library should still declare its types, so the signature does not change when the body does.

== The Built-In Number, Boolean, and Char Types

[cols="1,2"]
|===
|Type |Notes

|`Byte`, `Short`, `Int`, `Long`
|8/16/32/64-bit signed integers; integer literals default to `Int`, suffix `L` for `Long`.

|`Float`, `Double`
|32/64-bit IEEE 754 floating-point; literals default to `Double`, suffix `f` or `F` for `Float`.

|`Boolean`
|`true` and `false`, no implicit conversion to or from any numeric type.

|`Char`
|a single UTF-16 code unit, in single quotes (`pass:c['A'+]`) -- *not* itself a numeric type, unlike Java's `char` (explicit conversion
via `code` and `Char(code)` is required).
|===

Unlike Java, Kotlin has *no separate primitive vs. boxed-wrapper types at the language level* -- `Int` is always just `Int`.
The compiler represents it as the JVM primitive `int` wherever possible and only boxes to `java.lang.Integer` when a nullable
type (`Int?`) or a generic type parameter forces it -- an optimization detail the source code never has to spell out.

[source,kotlin]
----
val age: Int = 30          // compiles to a JVM primitive int
val maybeAge: Int? = null  // boxed to java.lang.Integer, because null needs a reference type
val ages: List<Int> = listOf(30, 31)   // List<Int> holds boxed Integer objects
----

=== Literals

Number literals support several readable forms: underscores for grouping (`1_000_000`), hexadecimal (`0xFF`), binary
(`0b1010`) and scientific notation (`1.5e3`). There is no octal literal. A literal adapts to the expected type when it fits,
but a variable never converts implicitly:

[source,kotlin]
----
fun main() {
    val million = 1_000_000
    val mask = 0xFF
    val bits = 0b1010
    val big = 3_000_000_000L          // too large for Int: needs the L suffix
    val small: Byte = 100             // the literal fits and adapts to Byte
    val sci = 1.5e3

    println("$million $mask $bits $big $small $sci")
}
----

Output:

[source,text]
----
1000000 255 10 3000000000 100 1500.0
----

=== Conversions and overflow

There are *no implicit widening conversions*: an `Int` is not assigned to a `Long`, and comparing an `Int` with a `Long`
using `==` does not compile. Every number type has explicit `toInt()`, `toLong()`, `toDouble()` and so on. Arithmetic on
integers wraps on overflow silently, and conversions can lose information:

[source,kotlin]
----
fun main() {
    val i: Int = 7
    val l: Long = i.toLong()                  // explicit widening
    // val bad: Long = i                      // compile error: type mismatch
    println(i.toLong() == l)

    println(Int.MAX_VALUE + 1)                // -2147483648: wraps around silently
    println(300.toByte())                     // 44: the low 8 bits
    println(3.99.toInt())                     // 3: truncates toward zero
    println(Math.round(3.99))                 // 4
    println("42".toInt() + "8".toIntOrNull()!!)   // 50: parsing is explicit; toIntOrNull avoids the exception
    println(7 / 2)                            // 3: integer division
    println(7 / 2.0)                          // 3.5: promotes the Int operand in an expression
}
----

Output:

[source,text]
----
true
-2147483648
44
3
4
50
3
3.5
----

Arithmetic operators between different number types do promote the result type (`Int` plus `Double` gives `Double`), which
is the one place conversion is implicit. For exact decimal arithmetic, such as money, use `java.math.BigDecimal`, not
`Double`: `pass:c[0.1 + 0.2]` is not `0.3` in binary floating point.

== `Any`, `Unit`, and `Nothing`

Three types sit at the edges of Kotlin's type hierarchy and have no direct Java equivalent:

* *`Any`* -- the root of the non-nullable type hierarchy (Kotlin's analogue of `Object`, but every type, including the number
  types, is a subtype of it -- there is no primitive/reference split to work around). `Any?` is the root of everything,
  including nullable types.
* *`Unit`* -- the return type of a function that "returns nothing meaningful," Kotlin's analogue of `void`, but it *is* a
  real, singleton-valued type -- this is what allows a lambda parameter typed `+() -> Unit+` to be used uniformly wherever a
  callback with no useful return value is needed, and a generic `Result<Unit>` to make sense.
* *`Nothing`* -- the type of an expression that *never completes normally* (always throws, or is an infinite loop); a function
  like `fun fail(msg: String): Nothing = throw IllegalStateException(msg)` lets the compiler treat every branch after a call
  to it as unreachable, which is what makes `+?: throw ...+` type-check cleanly in
  xref:programming-languages/kotlin/null-safety.adoc[Null Safety]'s Elvis-operator examples.

[mermaid]
....
flowchart BT
    N["Nothing: bottom type, no instances"] -->|"subtype of"| I["Int"]
    N -->|"subtype of"| S["String"]
    N -->|"subtype of"| B["Book"]
    I -->|"subtype of"| A["Any"]
    S -->|"subtype of"| A
    B -->|"subtype of"| A
    U["Unit"] -->|"subtype of"| A
    A -->|"subtype of"| AN["Any?: top type, includes null"]
    NN["Nothing?: the type of null"] -->|"subtype of"| AN
    I -->|"also a subtype of"| IN["Int?"]
    IN --> AN
....

The relation is the subtype relation: `Int` is a subtype of `Any`, which is a subtype of `Any?`; `Int?` is a subtype of
`Any?` but not of `Any`. `Nothing` is a subtype of every type, so an expression of type `Nothing` can stand wherever any
type is expected; `null` itself has the type `Nothing?`. The type checks and casts in the language relate to the hierarchy:
`is` tests membership (with smart cast), `as` casts (throws on failure) and `as?` returns `null` instead.

[source,kotlin]
----
fun describe(x: Any): String = when (x) {
    is Int -> "an int: ${x + 1}"
    is String -> "a string of length ${x.length}"
    else -> "something else: ${x::class.simpleName}"
}

fun fail(message: String): Nothing = throw IllegalStateException(message)

fun main() {
    println(describe(41))
    println(describe("Dune"))
    println(describe(2.5))
    val title: String = if (true) "Dune" else fail("unreachable")   // Nothing fits where String is needed
    println(title)
}
----

Output:

[source,text]
----
an int: 42
a string of length 4
something else: Double
Dune
----

== Arrays

`Array<T>` is a fixed-size, mutable, indexable container, distinct from Kotlin's `List` and `MutableList` (covered in
xref:programming-languages/kotlin/collections-and-sequences.adoc[Collections and Sequences]):

[source,kotlin]
----
fun main() {
    val letters = arrayOf("a", "b", "c")
    val zeros = IntArray(5)                  // primitive-backed, no boxing: [0, 0, 0, 0, 0]
    val squares = IntArray(5) { it * it }    // lambda-initialized: [0, 1, 4, 9, 16]

    println(letters[1])                      // b
    letters[1] = "B"
    println(letters.contentToString())       // [a, B, c]: arrays print as identity unless converted
    println(zeros.contentToString())
    println(squares.sum())                   // 30
    println(squares.toList())                // convert to a List when an array's fixed size is not needed
}
----

Output:

[source,text]
----
b
[a, B, c]
[0, 0, 0, 0, 0]
30
[0, 1, 4, 9, 16]
----

Dedicated primitive-array types (`IntArray`, `DoubleArray`, `BooleanArray`, ...) avoid boxing overhead, mirroring Java's
`int[]`, `double[]` and so on; `Array<Int>` (boxed) also exists but is rarely what you want for numeric data. Arrays are
*invariant* (`Array<String>` is not an `Array<Any>`, unlike in Java) and use reference equality: `==` on two arrays compares
identity, so use `contentEquals`. Prefer `List` in application code and keep arrays for performance-critical loops and for Java
APIs that take them (`vararg` parameters are arrays; see xref:programming-languages/kotlin/functions.adoc[Functions]).

== Unsigned Integer Types

Kotlin adds unsigned variants with no Java equivalent -- `UByte`, `UShort`, `UInt`, `ULong` -- for values that are
conceptually never negative (sizes, bit flags, hash codes read from an external format):

[source,kotlin]
----
fun main() {
    val port: UInt = 8080u
    val fileSize: ULong = 4_294_967_296uL
    val maxByte: UByte = 255u
    println("$port $fileSize $maxByte")
    println(maxByte.toInt() + 1)                 // 256: widened first, no wrap-around
    println((-1).toUInt())                       // 4294967295: the same bits, read as unsigned
}
----

Output:

[source,text]
----
8080 4294967296 255
256
4294967295
----

They are represented, like the signed types, as their same-width JVM primitive at runtime, with the sign reinterpreted --
there is no wider "real" unsigned JVM type underneath. Unsigned types are inline value classes under the hood, so they are
boxed when nullable or used as generic arguments, and Java callers see the underlying signed type.

== Constants and Type Aliases

A compile-time constant is declared `const val` at the top level or in an `object` (only for primitives and `String`), and
is inlined at use sites like a Java `static final`. A *type alias* gives a long or domain-specific type a shorter name
without creating a new type:

[source,kotlin]
----
const val MAX_LOANS = 3                          // a compile-time constant

typealias Isbn = String                          // the same type as String: assignable both ways
typealias Catalog = Map<Isbn, List<String>>      // a long generic type, named

fun lookup(catalog: Catalog, isbn: Isbn): List<String> = catalog[isbn].orEmpty()

fun main() {
    val catalog: Catalog = mapOf("1" to listOf("Dune", "Emma"))
    println(lookup(catalog, "1"))                // [Dune, Emma]
    println(lookup(catalog, "9"))                // []
    println(MAX_LOANS)
}
----

Because an alias is the same type, it does not prevent mixing up an `Isbn` and any other `String`: use a value class (see
xref:programming-languages/kotlin/classes-and-objects.adoc[Classes and Objects]) when that distinction must be enforced.
