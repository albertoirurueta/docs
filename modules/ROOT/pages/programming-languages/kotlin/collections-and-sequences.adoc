= Collections and Sequences
:description: Kotlin read-only vs. mutable collection interfaces, collection builders, functional operations (map, filter, fold, groupBy, associateBy), and Sequence (lazy) vs. eager collections.
:keywords: Kotlin, collections, List, MutableList, Set, Map, collection builders, map, filter, fold, groupBy, associateBy, Sequence, lazy evaluation
:page-aliases: apps/android/kotlin/collections-and-sequences.adoc

Kotlin does not ship its own collection implementations: it reuses the Java collections and adds a layer of interfaces,
factory functions and several hundred extension functions on top. That layer is what makes everyday data processing
short and safe. This page covers the two interface families (read-only and mutable) and what "read-only" really
promises, the builders, the functional operations (transform, filter, group, aggregate, sort, combine), maps, the
pitfalls of mutation and of Java interop, and `Sequence` for lazy evaluation, including how sequences are executed
and when they pay off. The examples use the lending library of this section (`Book`, `Member`, `Loan`).

== Read-Only vs. Mutable Collection Interfaces

Kotlin exposes every collection through *two interface families*: `List`, `Set` and `Map` expose only read operations,
while `MutableList`, `MutableSet` and `MutableMap` add `add`, `remove`, `put` and so on. There is no separate runtime
type behind this -- it is purely a *compile-time* view; the concrete class underneath (`ArrayList`, `LinkedHashMap`,
...) is exactly Java's:

[source,kotlin]
----
fun main() {
    val readOnly: List<Int> = listOf(1, 2, 3)      // no add()/remove() visible through this reference
    val mutable: MutableList<Int> = mutableListOf(1, 2, 3)
    mutable.add(4)

    // readOnly.add(4)     // compile error: List has no "add"

    val alsoMutable = readOnly as? MutableList<Int>  // may succeed: listOf(1, 2, 3) is a java.util.Arrays$ArrayList
    println(alsoMutable?.javaClass?.name)

    val shared = mutableListOf("Dune")
    val view: List<String> = shared                 // a read-only *view* of the same object
    shared.add("Emma")
    println(view)                                   // [Dune, Emma]: the "read-only" list changed underneath
    val snapshot = shared.toList()                  // a real copy
    shared.add("Ulysses")
    println(snapshot)                               // [Dune, Emma]
}
----

Output:

[source,text]
----
java.util.Arrays$ArrayList
[Dune, Emma]
[Dune, Emma]
----

This is a compile-time safety net, not an immutability guarantee: a Kotlin `List` reference can still be backed by a
mutable list that some other `MutableList`-typed reference to the same object changes underneath it. The conventions
that keep this safe are to expose `List` from a class while keeping a private `MutableList` field, and to return
`toList()` copies where a caller must not see later changes. For guaranteed immutability use the persistent collections
of `kotlinx.collections.immutable`.

Two further facts follow from the design. First, `List<out E>` is *covariant* -- a `List<Book>` is a
`List<Any>` -- while `MutableList<E>` is invariant (see xref:programming-languages/kotlin/generics-and-variance.adoc[Generics
and Variance]). Second, collections coming from Java have *platform types* (`MutableList<String!>!`), so a Java
method returning `List<String>` can yield a list that contains `null` or that is immutable at run time; see
xref:programming-languages/kotlin/null-safety.adoc[Null Safety].

== Collection Builders

`listOf`, `setOf` and `mapOf` (read-only) and `mutableListOf`, `mutableSetOf` and `mutableMapOf` (mutable) are the
standard factory functions, alongside `+buildList { }+`, `+buildSet { }+` and `+buildMap { }+` for building up a collection
imperatively and exposing it as read-only afterwards. `emptyList()` and `+listOfNotNull(...)+` cover the empty and the
null-filtering cases. `arrayListOf` and `hashMapOf` give a concrete Java type when one is required:

[source,kotlin]
----
fun main() {
    val titles = listOf("Dune", "Emma", "Ulysses")
    val stock = mapOf("Dune" to 3, "Emma" to 0)

    val computed = buildList {
        add("first")
        if (stock.isNotEmpty()) add("has stock data")
        addAll(titles)
    }
    println(computed)
    println(listOfNotNull("a", null, "b"))        // [a, b]
    println(setOf(1, 2, 2, 3))                    // [1, 2, 3]: a Set drops duplicates, keeping insertion order
    println(titles.toMutableList().apply { add("Walden") })
}
----

Output:

[source,text]
----
[first, has stock data, Dune, Emma, Ulysses]
[a, b]
[1, 2, 3]
[Dune, Emma, Ulysses, Walden]
----

`listOf` and `setOf` return insertion-ordered implementations, and `mapOf` a `LinkedHashMap`, so iteration order is
deterministic; `hashSetOf` and `hashMapOf` do not promise an order.

== Functional Operations

The bulk of everyday collection code uses a chain of functional operations rather than manual loops -- Kotlin's answer
to Java's `Stream` API, but operating directly on the collection interfaces themselves rather than through a separate
stream type. The operations fall into a few families:

[source,kotlin]
----
data class Book(val title: String, val author: String, val year: Int, val pages: Int)

fun main() {
    val books = listOf(
        Book("Clean Code", "Martin", 2008, 464),
        Book("Refactoring", "Fowler", 1999, 431),
        Book("Clean Architecture", "Martin", 2017, 432),
        Book("Effective Java", "Bloch", 2018, 412),
    )

    // transform
    println(books.map { it.title })
    println(books.flatMap { listOf(it.author, it.year.toString()) }.take(4))

    // filter
    println(books.filter { it.year > 2005 }.map { it.title })
    val (long, short) = books.partition { it.pages > 430 }
    println("${long.size} long, ${short.size} short")

    // aggregate
    println(books.sumOf { it.pages })
    println(books.maxByOrNull { it.year }?.title)
    println(books.fold(0) { acc, b -> acc + b.pages })        // like Stream.reduce with a seed
    println(books.count { it.author == "Martin" })
    println(books.any { it.year < 2000 })
    println(books.all { it.pages > 400 })

    // group and associate
    println(books.groupBy { it.author }.mapValues { (_, bs) -> bs.size })
    println(books.associateBy { it.title }.keys)
    println(books.groupingBy { it.author }.eachCount())

    // sort
    println(books.sortedBy { it.year }.map { it.year })
    println(books.sortedWith(compareBy<Book> { it.author }.thenByDescending { it.year }).map { it.title })

    // combine and window
    println(books.map { it.title }.zip(books.map { it.year }).first())
    println(listOf(1, 2, 3, 4, 5).chunked(2))
    println(listOf(1, 2, 3, 4).windowed(2))
    println(listOf(1, 2, 2, 3).distinct())
}
----

Output:

[source,text]
----

[Martin, 2008, Fowler, 1999]
[Clean Code, Clean Architecture, Effective Java]
3 long, 1 short

{Martin=2, Fowler=1, Bloch=1}

----

`map`, `filter`, `fold`, `groupBy` and `associateBy` are all defined as extension functions on `Iterable<T>` (see
xref:programming-languages/kotlin/extension-functions-and-scope-functions.adoc[Extension Functions and Scope
Functions]), so they work uniformly across `List`, `Set` and any custom `Iterable`. Some operations have a safe
variant that returns `null` instead of throwing: `first()` throws `NoSuchElementException` on an empty list while
`firstOrNull()` returns `null`; `maxOrNull`, `getOrNull(i)` and `singleOrNull()` follow the same convention.

== Maps

A `Map<K, V>` is read through `get`/`[]` (which returns `V?`), `getValue` (which throws), `getOrDefault` and
`getOrElse`, and it is iterated with destructured entries. `MutableMap` adds `put`, `getOrPut`, `remove`, and the
indexed assignment operator:

[source,kotlin]
----
fun main() {
    val loansPerMember = mutableMapOf<String, Int>()

    for (name in listOf("Ada", "Grace", "Ada", "Ada")) {
        loansPerMember[name] = (loansPerMember[name] ?: 0) + 1     // get returns Int?, so Elvis supplies 0
    }
    println(loansPerMember)

    val shelves = mutableMapOf<String, MutableList<String>>()
    shelves.getOrPut("fiction") { mutableListOf() }.add("Dune")     // creates the list only if missing
    shelves.getOrPut("fiction") { mutableListOf() }.add("Emma")
    println(shelves)

    println(loansPerMember.getOrDefault("Bo", 0))                   // 0
    println(loansPerMember.filterValues { it > 1 }.keys)            // [Ada]
    println(loansPerMember.entries.sortedByDescending { it.value }.first().key)   // Ada
    loansPerMember.merge("Bo", 1) { old, one -> old + one }
    println(loansPerMember.toSortedMap())                           // {Ada=3, Bo=1, Grace=1}
}
----

Output:

[source,text]
----
{Ada=3, Grace=1}
{fiction=[Dune, Emma]}
0
[Ada]
Ada
{Ada=3, Bo=1, Grace=1}
----

== `Sequence` (Lazy) vs. Eager Collections

Every operation above, called on a `List` or `Set`, runs *eagerly*: each `+map { }+` or `+filter { }+` in a chain allocates
and fully populates a new intermediate list before the next step runs. `Sequence` runs the same operations *lazily*,
element by element, exactly like a Java `Stream`: the operations on a sequence are *intermediate* (they only add a stage
to the pipeline) until a *terminal* operation such as `toList()`, `first()`, `sum()` or `count()` pulls the values
through.

[source,kotlin]
----
fun main() {
    val eager = listOf(1, 2, 3, 4, 5)
        .map { println("map $it"); it * 2 }        // fully evaluated: prints 5 times right here
        .first { it > 4 }
    println("eager result $eager")

    val lazy = sequenceOf(1, 2, 3, 4, 5)
        .map { println("map $it"); it * 2 }        // nothing runs yet
        .first { it > 4 }                          // pulls elements one at a time until satisfied
    println("lazy result $lazy")
}
----

Output:

[source,text]
----
map 1
map 2
map 3
map 4
map 5
eager result 6
map 1
map 2
map 3
lazy result 6
----

The order of operations differs too. A sequence processes *one element through the whole pipeline* before taking the
next, whereas a list finishes each operation on every element before starting the following one:

[mermaid]
....
sequenceDiagram
    participant Src as Source
    participant M as map
    participant F as filter
    participant T as Terminal (first)
    T->>F: give me the next element
    F->>M: give me the next element
    M->>Src: next
    Src-->>M: 1
    M-->>F: 2
    F-->>F: rejected, ask again
    F->>M: next
    M->>Src: next
    Src-->>M: 2
    M-->>F: 4
    F-->>T: accepted, stop pulling
....

`asSequence()` converts any `Iterable` to a `Sequence`; `+generateSequence(seed) { next }+` and the `+sequence { yield(x) }+`
builder create sequences from scratch, including infinite ones:

[source,kotlin]
----
fun main() {
    val firstSquares = generateSequence(1) { it + 1 }      // infinite: 1, 2, 3, ...
        .map { it * it }
        .filter { it % 2 == 1 }
        .take(4)
        .toList()
    println(firstSquares)                                   // [1, 9, 25, 49]

    val fib = sequence {
        var a = 0
        var b = 1
        while (true) {
            yield(a)                                        // suspends until the consumer asks for more
            val next = a + b
            a = b
            b = next
        }
    }
    println(fib.take(8).toList())                           // [0, 1, 1, 2, 3, 5, 8, 13]
}
----

The difference matters for *large or infinite collections* and for *short-circuiting chains* (`+first { }+`, `take(n)`,
`+any { }+`): a `Sequence` avoids building full intermediate collections at every step, at the cost of some per-element
overhead (a lambda call and an iterator step per stage) that makes eager collections faster for small, fully consumed
chains. As a rule of thumb: default to `List`, and reach for `Sequence` when a chain is long, the source is large, or
the terminal operation can stop early. A sequence is also single-use for some sources (it may fail on a second
iteration), and sorting (`sorted`) is a *stateful* operation that must buffer everything, which cancels much of the
laziness.

== Common Pitfalls

* Mutating a collection while iterating it throws `ConcurrentModificationException`; use `+removeAll { }+`,
  `iterator.remove()` or build a filtered copy.
* `+listOf(...)+` is not thread-safe once shared and mutated through another reference, and Kotlin's collections have no
  built-in concurrent variants: use `java.util.concurrent` classes or confine the data to a coroutine.
* Prefer `List` and `Map` in public APIs, and convert with `toList()` where a defensive copy is needed.
* An `Array<T>` is a JVM array: it is mutable, invariant and has no `map`-style laziness; use `List` unless a Java API or
  performance needs an array.
