Most real projects never invoke `kotlinc` directly (see
xref:programming-languages/kotlin/getting-started.adoc[Getting Started]) -- Gradle or Maven drive the compiler as part of
an ordinary build. This page covers the Gradle Kotlin DSL for a JVM project (plugins, toolchains, compiler options,
version catalogs, running and packaging), Maven's Kotlin plugin including mixed Java and Kotlin modules, the compiler
plugins that give Kotlin its framework support, IDE support, static analysis, what makes Kotlin builds fast or slow, and
publishing. The sample project is a small command-line app for the lending library used throughout this section (`Book`,
`Member`, `Loan`).

How a build turns sources into a running program:

[mermaid]
....
flowchart LR
    K["src/main/kotlin: .kt files"] --> C["Kotlin compiler (K2) with compiler plugins"]
    J["src/main/java: .java files"] --> JC["javac"]
    C --> B["build/classes: .class files"]
    JC --> B
    C -.->|"reads Java sources to resolve references"| J
    B --> P["jar or application distribution"]
    D["dependencies from Maven Central"] --> C
    D --> P
    B --> T["test task: JUnit 5 platform"]
....

== The Gradle Kotlin DSL (`build.gradle.kts`)

Gradle build scripts can be written in Kotlin itself (`.kts`, a `.gradle.kts` file extension) instead of the older Groovy
DSL -- this is the default for new Kotlin *and* new Android projects today, and gets full IDE autocompletion and
type-checking, unlike a dynamically-typed Groovy script:

[source,kotlin]
----
// build.gradle.kts
plugins {
    kotlin("jvm") version "2.4.0"
    application
}

repositories {
    mavenCentral()
}

dependencies {
    implementation("org.jetbrains.kotlinx:kotlinx-coroutines-core:<version>")
    testImplementation(kotlin("test"))
}

kotlin {
    jvmToolchain(21)                       // compile with, and target, JDK 21 whatever JDK runs Gradle
}

application {
    mainClass.set("com.example.library.MainKt")   // a top-level main() in Main.kt compiles to class MainKt
}

tasks.test {
    useJUnitPlatform()
}
----

`+plugins { }+`, `+dependencies { }+`, and `+tasks.test { }+` are all lambda-with-receiver blocks over Gradle's own configuration
model -- see xref:programming-languages/kotlin/type-safe-builders-and-dsls.adoc[Type-Safe Builders and DSLs] for the
language mechanism this is built on. An Android module additionally applies `id("com.android.application")` (or `.library`)
alongside the Kotlin Android support (see
xref:programming-languages/kotlin/kotlin-for-android.adoc[Kotlin for Android]).

The standard layout is `src/main/kotlin` and `src/test/kotlin` (Java sources may sit beside them in `src/main/java`), with
the package structure mirrored in directories by convention. `./gradlew run` runs the application, `./gradlew test` the
tests, `./gradlew build` compiles, tests and packages, and `./gradlew installDist` creates a runnable distribution with start
scripts.

=== Toolchains and compiler options

`jvmToolchain(21)` makes Gradle locate (or download) a JDK 21 and use it for both Kotlin and Java compilation and for
running tests, which avoids the "works on my machine" difference between developers' JDKs and keeps the Kotlin and Java
targets consistent. Compiler flags go in `compilerOptions`:

[source,kotlin]
----
import org.jetbrains.kotlin.gradle.dsl.JvmTarget

kotlin {
    compilerOptions {
        allWarningsAsErrors.set(true)                       // treat warnings as errors in CI
        jvmTarget.set(JvmTarget.JVM_21)
        freeCompilerArgs.add("-Xjsr305=strict")              // honour JSR-305 nullability annotations as errors
    }
}
----

`-Xjsr305=strict` makes Kotlin treat Spring's and other libraries' `@Nullable` and `@NonNull` annotations as real types,
which removes many platform types; flags starting with `-X` are advanced and subject to change.

=== Version catalogs

A *version catalog* (`gradle/libs.versions.toml`) names every version and library in one file, so that several modules
share them and updates happen in one place:

[source,text]
----
# gradle/libs.versions.toml
[versions]
kotlin = "2.4.0"
coroutines = "<version>"

[libraries]
coroutines-core = { module = "org.jetbrains.kotlinx:kotlinx-coroutines-core", version.ref = "coroutines" }

[plugins]
kotlin-jvm = { id = "org.jetbrains.kotlin.jvm", version.ref = "kotlin" }
----

The build script then reads `alias(libs.plugins.kotlin.jvm)` and `implementation(libs.coroutines.core)`, with type-safe
accessors generated by Gradle.

== Maven's Kotlin Plugin

Maven support comes from the `kotlin-maven-plugin`, bound to the `compile` and `test-compile` phases:

[source,xml]
----
<build>
  <plugins>
    <plugin>
      <groupId>org.jetbrains.kotlin</groupId>
      <artifactId>kotlin-maven-plugin</artifactId>
      <version>2.4.0</version>
      <configuration>
        <jvmTarget>21</jvmTarget>
      </configuration>
      <executions>
        <execution>
          <id>compile</id>
          <goals><goal>compile</goal></goals>
        </execution>
        <execution>
          <id>test-compile</id>
          <goals><goal>test-compile</goal></goals>
        </execution>
      </executions>
    </plugin>
  </plugins>
</build>
----

A mixed Java/Kotlin Maven module needs the Kotlin execution to run *before* `maven-compiler-plugin`&#39;s own compile, so
Java sources can reference Kotlin classes (see xref:programming-languages/kotlin/kotlin-and-the-jvm.adoc[Kotlin and the
JVM] on interoperability). The Kotlin compiler reads the Java sources in the same module to resolve their types, so the
two directions work: Kotlin calls Java and Java calls Kotlin. The documented setup disables the default Java compile
executions and re-binds them to run after Kotlin's:

[source,xml]
----
<plugin>
  <artifactId>maven-compiler-plugin</artifactId>
  <executions>
    <execution><id>default-compile</id><phase>none</phase></execution>
    <execution><id>default-testCompile</id><phase>none</phase></execution>
    <execution><id>java-compile</id><phase>compile</phase><goals><goal>compile</goal></goals></execution>
    <execution><id>java-test-compile</id><phase>test-compile</phase><goals><goal>testCompile</goal></goals></execution>
  </executions>
</plugin>
----

Also declare the source directories (`src/main/kotlin` and `src/main/java`) in the Kotlin plugin's `<sourceDirs>` so both
are seen.

== Compiler Plugins

Several Kotlin features are not in the compiler itself but in *compiler plugins*, enabled in the build:

[cols="1,3"]
|===
|Plugin |What it does

|`all-open` (`kotlin("plugin.allopen")`, `kotlin("plugin.spring")`, `kotlin("plugin.jpa")`)
|makes classes carrying given annotations `open`, so that frameworks that subclass them at run time (Spring proxies) work
despite Kotlin's final-by-default classes. See
xref:programming-languages/kotlin/inheritance-and-interfaces.adoc[Inheritance and Interfaces].

|`no-arg` (`kotlin("plugin.noarg")`, included in the JPA preset)
|generates a synthetic no-argument constructor for annotated classes, as JPA and some serialisation libraries require.

|`kotlinx.serialization` (`kotlin("plugin.serialization")`)
|generates serialisers at compile time, with no reflection.

|Compose compiler (`kotlin("plugin.compose")`)
|the compiler transformation behind Jetpack Compose and Compose Multiplatform, shipped with the Kotlin compiler since 2.0.

|KSP (`com.google.devtools.ksp`)
|Kotlin Symbol Processing, the annotation-processing API used by Room, Moshi codegen and others; faster than kapt.

|`kapt` (`kotlin("kapt")`)
|runs Java annotation processors (Dagger, older libraries) against Kotlin through generated stubs; in maintenance mode, so
prefer KSP when the library supports it.
|===

The plugins are applied by name in the `+plugins { }+` block, and the all-open annotations are listed under `+allOpen { }+`
if the presets are not enough. Compiler plugins are the reason an IDE sometimes needs to be told to re-import the Gradle
project after a plugin change.

== IntelliJ IDEA and Android Studio

Both IDEs bundle first-class Kotlin support out of the box (Android Studio is itself built on the IntelliJ platform) --
syntax highlighting, refactoring, a Java-to-Kotlin converter (paste Java code into a `.kt` file and IntelliJ offers to
convert it automatically), and inline bytecode and decompiled-Java views of any Kotlin declaration, useful for understanding
exactly what a given Kotlin construct compiles down to. For other IDEs and editors, see
xref:programming-languages/kotlin/ides-and-tools.adoc[Kotlin IDEs & Tools]. Since Kotlin 2.0 the IDE's analysis and the
command-line compiler share the same front end (K2), so errors shown in the editor match the build.

== Static Analysis: `ktlint` and `detekt`

Two tools cover Kotlin's equivalent of Checkstyle/PMD:

* https://ktlint.github.io/[*ktlint*] -- a formatter/linter enforcing the official
  xref:programming-languages/kotlin/lexical-structure-and-style.adoc[Kotlin coding conventions] with no configuration needed
  for the common case; it can also auto-fix most violations.
* https://detekt.dev/[*detekt*] -- a broader static-analysis tool (complexity, code smells, potential bugs) configured via a
  `detekt.yml` rule set, closer in spirit to PMD/SpotBugs than to a pure formatter.

[source,kotlin]
----
// build.gradle.kts
plugins {
    id("org.jlleitschuh.gradle.ktlint") version "12.1.1"
    id("io.gitlab.arturbosch.detekt") version "1.23.7"
}
----

Both are typically run as their own Gradle tasks (`ktlintCheck`, `detekt`) alongside the ordinary `test` task in CI.
`ktlintFormat` rewrites the files to match the style. The compiler itself is also a linter: `allWarningsAsErrors` (above)
plus the deprecation and unused warnings catch a great deal.

== Build Speed

Kotlin builds are incremental by default: the compiler tracks which source files and ABI changes affect which classes and
recompiles only those. Practical points:

* The *Kotlin daemon* keeps a warm compiler between builds; the first build after the machine starts is the slow one.
* Gradle's *build cache* (`org.gradle.caching=true` in `gradle.properties`) and *configuration cache*
  (`org.gradle.configuration-cache=true`) skip work that has not changed.
* Splitting a large project into modules lets Gradle compile them in parallel and recompile only the modules downstream of a
  change; an `api` versus `implementation` dependency choice controls how far a change propagates.
* `kapt` adds a stub-generation step to every compile, a main reason to migrate to KSP.

== A Pointer to Kotlin Multiplatform

xref:programming-languages/kotlin/kotlin-and-the-jvm.adoc[Kotlin and the JVM] introduced Kotlin Multiplatform (KMP) as the
mechanism for sharing Kotlin source across the JVM, JS, Native, and Wasm back ends. From a build-tooling perspective, KMP is
configured via the `kotlin("multiplatform")` Gradle plugin instead of `kotlin("jvm")`, declaring one or more source sets
(`commonMain`, `androidMain`, `iosMain`, and so on) compiled to their respective targets from largely shared code -- a
large enough topic that it is only pointed at here, not covered in depth. The dedicated
xref:apps/kotlin-multiplatform/index.adoc[Kotlin Multiplatform] section covers the Gradle DSL, source sets and
compatibility in full, starting with
xref:apps/kotlin-multiplatform/gradle-configuration-and-compatibility.adoc[Gradle Configuration, the Multiplatform DSL and
Compatibility].

== Publishing to Maven Central

A Kotlin/JVM library publishes through the exact same Sonatype Central Portal flow as a Java library: the same
`central-publishing-maven-plugin` (Maven) or `com.vanniktech.maven.publish` (Gradle) plugins apply unmodified to a Kotlin
source tree, since both work at the level of the packaged JAR and its signatures rather than the language that produced
them. Two Kotlin particulars: the library needs a *sources JAR* and a *Javadoc JAR* (use the Dokka HTML output, or an empty
Javadoc JAR, as the repository rules require), and `explicitApi()` in the `+kotlin { }+` block makes the compiler demand
explicit visibility modifiers and return types on public declarations, the usual discipline for a published API.

See xref:programming-languages/java/build-and-tooling.adoc#_publishing_to_maven_central[Publishing to Maven Central] for the
full account setup, user token, GPG key, and GitHub Actions release workflow -- none of that is repeated here since
nothing about it differs for Kotlin.

NOTE: A Kotlin Multiplatform library publishes multiple platform-specific artifacts (JVM, JS, Native, ...) under one shared
coordinate; `com.vanniktech.maven.publish` and the `kotlin("multiplatform")` plugin handle that automatically once each
target is declared, with no extra publishing configuration beyond what a single-platform library needs.
