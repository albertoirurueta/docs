= Null Safety

:keywords: Kotlin, null safety, nullable types, safe call, Elvis operator, not-null assertion, safe cast, platform types, smart casts, NullPointerException
:page-aliases: apps/android/kotlin/null-safety.adoc

Null safety is arguably Kotlin's best-known feature: nullability is part of the *type*, checked by the compiler at
compile time, rather than discovered as a `NullPointerException` at run time. This page covers nullable types and how
they are represented on the JVM, the operators that work with them (`?.`, `?:`, `!!`, `as?`), the combination with
`let`, collections of nullable values, `lateinit` and `lazy`, platform types at the Java boundary, smart casts and the
exact conditions under which the compiler grants them, and the remaining ways a `NullPointerException` can still appear.
The examples use the lending library of this section (`Book`, `Member`, `Loan`).

== Nullable Types

Every type is non-nullable by default; appending `?` makes it nullable, and the compiler then *requires* a null check
before most operations on it. `String` and `String?` are different types, and a `String` is a subtype of `String?`:

[source,kotlin]
----
class Member(val name: String, val email: String?)      // a member may not have an e-mail address

fun main() {
    var name: String = "Ada"
    // name = null                  // compile error: String is non-nullable

    var maybeName: String? = "Ada"
    maybeName = null                // fine: String? explicitly allows null

    // println(maybeName.length)    // compile error: maybeName might be null
    println(maybeName == null)      // true: == null is always allowed

    val member = Member("Ada", null)
    println(member.email)           // null
}
----

Output:

[source,text]
----
true
null
----

On the JVM there is no separate runtime type: `String?` and `String` are both `java.lang.String`, and the nullability is
recorded as annotations (`@Nullable` and `@NotNull`) and in Kotlin metadata for the compiler's benefit. For public
functions the compiler also inserts a run-time check at the top of each non-null parameter
(`Intrinsics.checkNotNullParameter`), so a Java caller that passes `null` fails immediately with a clear message, at the
boundary, rather than somewhere deeper. Primitive types such as `Int` compile to JVM primitives when non-null and to boxed
`Integer` when nullable (`Int?`) or used as a generic argument.

== Safe Call (`?.`)

`?.` calls a member only if the receiver is non-null, and evaluates to `null` otherwise -- avoiding an explicit `if (x != null)`
guard for a single call, and chaining cleanly across several nullable steps:

[source,kotlin]
----
class Address(val city: String?)
class Reader(val name: String, val address: Address?)

fun main() {
    val maybeName: String? = "Ada"
    val length: Int? = maybeName?.length               // null if maybeName is null, else its length
    println(length)

    val reader: Reader? = Reader("Grace", Address(null))
    val city: String? = reader?.address?.city           // chains through several nullable links safely;
    println(city)                                       // short-circuits to null at the first null link

    var shelfSize: Int? = null
    shelfSize?.let { println("size $it") }              // the block is skipped when the value is null
    reader?.address?.city?.let { println("lives in $it") }
}
----

Output:

[source,text]
----
3
null
----

`?.` can also appear on the left of an assignment (`reader?.name = "x"` is skipped if `reader` is null), and a `?.` chain
short-circuits: once a link is `null`, the *rest of the chain* is not evaluated, including argument expressions.

== Elvis Operator (`?:`)

`?:` supplies a default when the left side is `null` -- Kotlin's concise stand-in for a ternary `x != null ? x : default`:

[source,kotlin]
----
data class Book(val isbn: String, val title: String)

val catalog = mapOf("1" to Book("1", "Dune"))
fun findBook(isbn: String): Book? = catalog[isbn]

fun requireBook(isbn: String): Book =
    findBook(isbn) ?: throw NoSuchElementException("no book with ISBN $isbn")   // "?:" combined with "throw"

fun titleOf(isbn: String): String {
    val book = findBook(isbn) ?: return "unknown"      // early return when absent: the main path stays flat
    return book.title
}

fun main() {
    val maybeName: String? = null
    val length: Int = maybeName?.length ?: 0           // 0 if maybeName is null
    println(length)
    println(titleOf("1"))
    println(titleOf("2"))
    println(runCatching { requireBook("2") }.exceptionOrNull()?.message)
}
----

Output:

[source,text]
----
0
Dune
unknown
no book with ISBN 2
----

Because `throw` and `return` are themselves expressions of type `Nothing` (see
xref:programming-languages/kotlin/basic-types-and-variables.adoc[Basic Types and Variables]), these forms type-check: the
Elvis operator's result type is non-null `Book` or `String` regardless, since the right side either produces a value or
never returns at all. After `+val book = findBook(isbn) ?: return ...+`, the variable `book` is a non-null `Book` for the rest
of the function, which is the idiomatic *guard clause*.

== Not-Null Assertion (`!!`)

`!!` forces a nullable expression to non-null, *throwing `NullPointerException` immediately if it actually is null*. It
exists as an escape hatch, but its use is a deliberate statement that null there would be a bug, not a normal condition to
handle -- reach for `?.` and `?:` first in ordinary code:

[source,kotlin]
----
fun main() {
    val maybeName: String? = null
    val result = runCatching { maybeName!!.length }     // throws NPE right here if maybeName is null
    println(result.exceptionOrNull() is NullPointerException)
}
----

Output:

[source,text]
----
true
----

When a value must be non-null and a clear message helps, prefer `+requireNotNull(x) { "message" }+` (an
`IllegalArgumentException`) or `+checkNotNull(x) { "message" }+` (an `IllegalStateException`), which also smart-cast `x` to
non-null afterwards. A `!!` in production code is a code smell worth a comment; in tests it is usually fine.

== Safe Cast (`as?`)

`as?` attempts a cast and evaluates to `null` on failure, instead of throwing `ClassCastException` the way a plain `as`
cast would:

[source,kotlin]
----
fun main() {
    val value: Any = "hello"
    val asInt: Int? = value as? Int            // null: value is not an Int, no exception thrown
    val asString: String? = value as? String   // "hello"
    println("$asInt $asString")

    val nothing: Any? = null
    println(nothing as? String)                // null: as? on null is null, while "null as String" would throw
}
----

Output:

[source,text]
----
null hello
null
----

`as?` combines naturally with the Elvis operator: `(x as? Book)?.title ?: "n/a"`.

== Nullable Values in Collections

The nullability of the *elements* is part of the type: `List<String?>` is a list that may contain `null`, `List<String>?` is
a list that may be `null`, and `List<String?>?` is both. The standard library has helpers that remove the nulls and
refine the type:

[source,kotlin]
----
fun main() {
    val emails: List<String?> = listOf("ada@example.com", null, "grace@example.com")

    val present: List<String> = emails.filterNotNull()          // List<String>: the type is narrowed, too
    println(present)

    val domains = emails.mapNotNull { it?.substringAfter("@") } // map and drop nulls in one step
    println(domains)

    val firstOrNull: String? = emails.firstOrNull { it == null }
    println(firstOrNull)

    val map = mapOf("a" to 1)
    println(map["b"])                                           // null: Map.get returns V?
    println(map.getValue("a"))                                  // throws for a missing key instead
}
----

Output:

[source,text]
----
[ada@example.com, grace@example.com]
[example.com, example.com]
null
null
1
----

== Late Initialisation: `lateinit` and `lazy`

Sometimes a property cannot be set in the constructor but is guaranteed to be set before use (dependency injection, a view
bound after creation). Making it nullable forces `?.` or `!!` at every use; two alternatives keep it non-null:

* `lateinit var` for a non-null `var` that is assigned later. Reading it before assignment throws
  `UninitializedPropertyAccessException`, and `::property.isInitialized` tests it. It works only for non-primitive,
  non-nullable types.
* `+val x by lazy { ... }+` for a `val` computed on first access, thread-safe by default.

[source,kotlin]
----
class Catalog {
    lateinit var owner: String                    // set after construction
    fun hasOwner() = ::owner.isInitialized        // isInitialized is only available inside the declaring class
    val books: List<String> by lazy {             // computed on first access, then cached
        println("loading books")
        listOf("Dune", "Emma")
    }
}

fun main() {
    val catalog = Catalog()
    println(catalog.hasOwner())                   // false
    catalog.owner = "Ada"
    println(catalog.owner)
    println(catalog.books)                        // prints "loading books" first
    println(catalog.books)                        // cached: no second load
}
----

Output:

[source,text]
----
false
Ada
loading books
[Dune, Emma]
[Dune, Emma]
----

== Platform Types from Java Interop

A type coming from Java code (which has no compile-time nullability information -- see
xref:programming-languages/kotlin/kotlin-and-the-jvm.adoc[Kotlin and the JVM]) is represented as a *platform type*, notated
`String!` in error messages -- Kotlin relaxes its usual compile-time null checks for it and trusts the caller to know
whether it can actually be null (informed, ideally, by a `@Nullable` or `@NonNull` annotation on the Java side, which
Kotlin *does* respect when present, for JSR-305, JetBrains, Android, Checker Framework and other annotations):

[source,kotlin]
----
fun main() {
    // System.getProperty is a Java method with no nullability annotation: its result is the platform type String!
    val raw = System.getProperty("library.owner")        // no compile error, whatever the actual value is
    val safe: String? = System.getProperty("library.owner")   // declaring it nullable is the safe choice
    println(safe?.length)                                // null when the property is not set

    // val risky: String = System.getProperty("library.owner")  // compiles, but throws at this assignment when null
}
----

Treating an unannotated platform type as non-null when it can genuinely be null is one of the few ways a
`NullPointerException` can still surface in Kotlin code -- almost always at a Java interop boundary. The defence is to
declare the *type you mean* explicitly (`String?`) when assigning a Java return value to a variable or a property.

== Smart Casts

Once the compiler has proven a value is non-null (or of a narrower type) along a particular code path, it *automatically*
treats it that way for the rest of that path -- no explicit cast needed:

[source,kotlin]
----
fun printLength(text: String?) {
    if (text != null) {
        println(text.length)       // smart-cast to non-null String inside this branch: no "!!" needed
    }
    if (text.isNullOrEmpty()) return
    println(text.length)           // smart-cast again, through a function with a contract
}

fun describe(value: Any) {
    if (value is String) {
        println(value.uppercase())      // smart-cast to String, see Control Flow's "is" branches
    }
    if (value !is Int) return
    println(value + 1)                  // after the early return, value is an Int
}

fun main() {
    printLength("Dune")
    describe("Dune")
    describe(41)
}
----

Output:

[source,text]
----
4
4
DUNE
42
----

A smart cast requires the compiler to be certain the value cannot change between the check and the use. It applies to:
`val` local variables; `var` local variables that are not captured in a lambda that modifies them and not modified between
the check and the use; `val` properties that are private or internal, or in the same module, and have no custom getter and
are not `open`; and *not* to a `var` property or to a `val` property declared in another module or with a custom getter,
because another thread or another part of the program could change them in between. The usual fix for the second case is
a local `val` copy:

[source,kotlin]
----
class Session {
    var user: String? = null

    fun greet() {
        // if (user != null) println(user.length)   // compile error: user is a mutable property, it may change
        val current = user                           // read once into a local val
        if (current != null) println(current.length) // smart cast works on the stable local
    }
}
----

== Where `NullPointerException` Can Still Occur

* Explicit `!!` on a null value, and `lateinit` read before assignment (a different exception, for the same kind of
  bug).
* Platform types assigned to non-null declarations, as above.
* Initialisation-order bugs: calling an `open` member from a constructor before the subclass has initialised its properties
  (see xref:programming-languages/kotlin/inheritance-and-interfaces.adoc[Inheritance and Interfaces]).
* Java code calling Kotlin with `null` for a non-null parameter is rejected by the generated parameter check, but
  reflection and serialisation libraries that bypass constructors can leave a non-null property `null` (a typical
  problem with Gson and a Kotlin class that has defaults).
* Generic type parameters have the upper bound `Any?`, so `T` may be nullable; declare `T : Any` to forbid it.

== Design Guidance

* Make a type nullable only when *absence is a valid state*, and model "failed" separately with an exception or a result
  type (see xref:programming-languages/kotlin/exceptions-and-error-handling.adoc[Exceptions and Error Handling]).
* Prefer returning `null` (`toIntOrNull`, `firstOrNull`) over throwing for expected absence, and prefer `emptyList()` over
  `null` for collections.
* Resolve nullability at the *edge* of your code (parsing, Java calls, deserialisation) and pass non-null types inward.
