= Extension Functions and Scope Functions
:description: Kotlin extension functions and properties, and the five scope functions (let, run, with, apply, also) with a decision table for which to use when.
:keywords: Kotlin, extension functions, extension properties, scope functions, let, run, with, apply, also
:page-aliases: apps/android/kotlin/extension-functions-and-scope-functions.adoc

include::partial$ai-disclaimer.adoc[]

Two features account for much of the "feels like a different language" quality of everyday Kotlin: *extension
functions*, which add members to types you do not own, and the five *scope functions* (`let`, `run`, `with`, `apply`,
`also`), which run a block against an object. This page explains how extensions are declared, resolved and compiled
(including the rule that a member always wins), extension properties and nullable receivers, member extensions, then the
five scope functions, how to choose between them with a simple decision procedure, and the readability pitfalls. The
examples use the lending library of this section (`Book`, `Member`, `Loan`).

== Extension Functions and Properties

An extension function is declared *outside* the class it appears to extend, with the receiver type prefixed before the
function name (`ReceiverType.functionName`). It compiles to an ordinary static function taking the receiver as a hidden
first parameter -- no subclassing, and no modification of the original type, actually happens:

[source,kotlin]
----
fun String.isPalindrome(): Boolean {
    val cleaned = this.lowercase().filter { it.isLetter() }
    return cleaned == cleaned.reversed()
}

val String.wordCount: Int                 // extension property: no backing field is allowed, only a getter
    get() = trim().split(Regex("\\s+")).size

fun main() {
    println("Racecar".isPalindrome())              // true: called exactly like a real member function
    println("the quick brown fox".wordCount)       // 4
}
----

Output:

[source,text]
----
true
4
----

This is how much of the Kotlin standard library extends `java.lang.String`, `java.util.Collection` and friends with
idiomatic-feeling members (`trim()`, `+filter { }+`, `sum()`) without touching the JDK classes themselves -- see
xref:programming-languages/kotlin/strings-and-text.adoc[Strings and Text] and
xref:programming-languages/kotlin/collections-and-sequences.adoc[Collections and Sequences] for many such examples in
practice.

=== Extensions for the domain

Extensions are the natural way to add behaviour to a data class without bloating it, or to give a library type
domain-specific vocabulary. Here they add reporting to the library types, generic helpers to `List` and a nullable-receiver
helper:

[source,kotlin]
----
data class Book(val title: String, val author: String, val year: Int)

fun Book.citation(): String = "$author ($year). $title."

fun List<Book>.byAuthor(author: String): List<Book> = filter { it.author == author }

fun <T : Comparable<T>> List<T>.isSorted(): Boolean = zipWithNext().all { (a, b) -> a <= b }

fun String?.orPlaceholder(): String = if (isNullOrBlank()) "(none)" else this   // extension on a nullable receiver

fun main() {
    val books = listOf(
        Book("Clean Code", "Martin", 2008),
        Book("Clean Architecture", "Martin", 2017),
        Book("Refactoring", "Fowler", 1999),
    )
    println(books.first().citation())
    println(books.byAuthor("Martin").map { it.title })
    println(books.map { it.year }.isSorted())
    println(books.map { it.year }.sorted().isSorted())
    val note: String? = null
    println(note.orPlaceholder())            // safe to call on null: the receiver type is String?
}
----

Output:

[source,text]
----
Martin (2008). Clean Code.
[Clean Code, Clean Architecture]
false
true
(none)
----

An extension on a nullable receiver (`String?`) can be called on `null` without a safe call, because the receiver is just
a parameter. The standard library uses this for `isNullOrEmpty()`, `orEmpty()` and `toString()` on `Any?`.

=== Resolution rules and limits

* *Static resolution.* An extension is chosen by the *declared* type of the expression at the call site, not its runtime
  type, unlike a virtual member:
+
[source,kotlin]
----
open class Media
class Dvd : Media()

fun Media.kind() = "media"
fun Dvd.kind() = "dvd"

fun main() {
    val m: Media = Dvd()
    println(m.kind())        // media: chosen by the declared type Media, not by the runtime type Dvd
}
----

* *Members win.* If a class has a member with the same signature as an extension, the member is called, and the
  compiler warns that the extension is shadowed. Extensions can overload a member with a different signature.
* *Extensions cannot access private or protected members*, because they live outside the class. A property needing
  state needs another place to store it (a map keyed by the receiver is rarely a good idea).
* *Scope.* Extensions are ordinary top-level or member declarations: they must be imported (`import
  com.example.citation`) unless they are in the same package, and a `private` extension is only visible in its file.
  Wildcard imports of a package bring in all of its extensions.
* There are no extension *fields* with state, and no extension on a companion unless the class declares one
  (`fun Book.Companion.empty()` works only if `Book` has a companion object).

=== How extensions compile

`fun Book.citation()` in `Library.kt` becomes `public static final String citation(Book $this$citation)` in the class
`LibraryKt`. A Kotlin caller writes `book.citation()`; a Java caller writes `LibraryKt.citation(book)`. Use
`@file:JvmName("BookExtensions")` at the top of the file to choose the class name. The unusual feature is that nothing
about `Book` changes, so extensions can be added to final classes, to Java classes and to interfaces.

=== Member extensions

An extension declared *inside* a class has two receivers: the extension receiver and the dispatch receiver (the
enclosing class instance). It is the mechanism behind DSLs such as `operator fun String.unaryPlus()` in
xref:programming-languages/kotlin/type-safe-builders-and-dsls.adoc[Type-Safe Builders and DSLs]. Inside it, `this` is the
extension receiver and `this@Outer` the dispatch receiver.

== The Five Scope Functions

`let`, `run`, `with`, `apply` and `also` all execute a lambda "in the context of" a value; they differ only in (a) how the
value is referenced inside the lambda (`it` versus `this`) and (b) what the whole expression returns (the lambda's result
versus the original value):

[cols="1,1,1,3"]
|===
|Function |Receiver as |Returns |Typical use

|`let`
|`it`
|lambda result
|null-checking a nullable value, or transforming it into something else -- `+x?.let { ... }+`.

|`run`
|`this`
|lambda result
|initializing then computing a result from an object in one expression.

|`with`
|`this`
|lambda result
|calling several members on an existing (non-null) object without repeating its name -- not an extension function
itself, called as `+with(obj) { ... }+`.

|`apply`
|`this`
|the object itself
|configuring an object's properties right after construction, then returning it (chainable).

|`also`
|`it`
|the object itself
|a side effect (logging, an assertion) in the middle of a chain, without breaking the chain.
|===

A full example, one function per line of the table, around a `Member` that borrows books:

[source,kotlin]
----
class Member(val name: String) {
    var email: String? = null
    val loans = mutableListOf<String>()
    fun borrow(title: String) { loans += title }
}

fun main() {
    // let: transform a nullable value only if it is not null; 'it' is the value
    val email: String? = "ada@example.com"
    val domain = email?.let { it.substringAfter("@") }
    println(domain)                                   // example.com

    // run: compute a result using 'this'
    val ada = Member("Ada")
    val summary = ada.run { "$name has ${loans.size} loans" }
    println(summary)                                  // Ada has 0 loans

    // with: several calls on one object, no "obj." prefix needed
    val report = with(StringBuilder()) {
        append("Member: ").append(ada.name)
        append(", loans: ").append(ada.loans.size)
        toString()
    }
    println(report)                                   // Member: Ada, loans: 0

    // apply: configure, then return the same object (classic builder-style usage)
    val grace = Member("Grace").apply {
        email = "grace@example.com"
        borrow("Dune")
        borrow("Emma")
    }
    println("${grace.name} ${grace.email} ${grace.loans}")   // Grace grace@example.com [Dune, Emma]

    // also: a side effect that does not change what is returned
    val titles = grace.loans
        .map { it.uppercase() }
        .also { println("after map: $it") }           // logging in the middle of a chain
        .filter { it.startsWith("D") }
    println(titles)                                   // [DUNE]
}
----

Output:

[source,text]
----
example.com
Ada has 0 loans
Member: Ada, loans: 0
Grace grace@example.com [Dune, Emma]
after map: [DUNE, EMMA]
[DUNE]
----

There is also a non-extension `+run { }+` that just evaluates a block as an expression, useful for a local scope, and the
related `+takeIf { }+` and `+takeUnless { }+`, which return the receiver or `null` according to a predicate, so that
`+member.email.takeIf { it?.isNotBlank() == true }+` chains well with `?.let`.

== Choosing Between Them

The decision procedure is two questions. *What should the expression return?* The object itself: `apply` or `also`. The
result of the block: `let`, `run` or `with`. *How should the object be named inside?* As the implicit `this`, so its
members can be used without a prefix: `apply`, `run`, `with`. As the explicit `it` (or a name you choose): `also` and
`let`.

[mermaid]
....
flowchart TD
    Q1{"Return the object itself?"}
    Q1 -->|"yes"| Q2{"Refer to it as this?"}
    Q1 -->|"no, the block result"| Q3{"Refer to it as this?"}
    Q2 -->|"yes: configure it"| A["apply"]
    Q2 -->|"no: observe it"| B["also"]
    Q3 -->|"yes"| Q4{"Object already in hand, not nullable?"}
    Q3 -->|"no: it"| C["let"]
    Q4 -->|"yes"| D["with"]
    Q4 -->|"no, call on a receiver"| E["run"]
....

A practical rule of thumb: use `apply` and `also` when the point is the *object itself* (configuring it, or observing it,
before continuing to use it); use `let` and `run` when the point is the *result of a computation* performed against it;
reach for `with` specifically when calling several members on an object you already have in hand (not one you just
created). All five are ordinary `inline` extension functions in the standard library (`with` is a plain `inline` function
taking the receiver as an argument) -- nothing about them is special-cased by the compiler beyond `inline` itself (see
xref:programming-languages/kotlin/lambdas-and-higher-order-functions.adoc[Lambdas and Higher-Order Functions]). Because
they are inlined, they cost no lambda allocation, and a `return` in the block returns from the enclosing function.

=== Pitfalls

* *Nesting hides `this`.* In `+apply { run { ... } }+` two implicit receivers are in scope and the inner call may silently
  resolve against the wrong one. Past one level of nesting, switch to named parameters (`+also { member -> ... }+`) or to a
  plain local `val`.
* *Mind the return value.* `let` returns the lambda result, so `+x?.let { println(it) }+` has type `Unit?` and does not
  return `x`; use `also` to keep the object.
* *Null handling.* `+x?.let { }+` runs the block only for non-null `x`, but it also yields `null` when `x` is null, so it
  is not a replacement for `+if (x != null) ... else ...+` when the else branch matters; add `?: fallback`.
* *Overuse.* Chains of scope functions are harder to read and debug than a few named statements. If the scope function
  adds no value (no null check, no result), plain code is clearer.
