= Sealed Classes and Enums
:description: Kotlin sealed class and sealed interface hierarchies with exhaustive when matching, and enum class with members and methods.
:keywords: Kotlin, sealed class, sealed interface, exhaustive when, enum class, enum members
:page-aliases: apps/android/kotlin/sealed-classes-and-enums.adoc

include::partial$ai-disclaimer.adoc[]

Both `sealed` types and `enum` classes model a *closed* set of possibilities, and the compiler uses that closedness to
check `when` expressions for completeness. They differ in what each possibility is: an enum constant is one single
instance with a fixed shape, whereas the subtypes of a sealed hierarchy are full classes, each of which can have many
instances and its own data. This page covers declaring and restricting sealed hierarchies, exhaustive `when` and what
changes when a subtype is added, generic sealed types, `data object`, enums with properties, constant-specific
bodies and interfaces, `EnumMap` and `EnumSet`, how both compile to the JVM, and how to choose between them. The
examples use the lending library of this section (`Book`, `Member`, `Loan`): the state of a loan is a sealed
hierarchy, and the genre of a book is an enum.

== `sealed class` and `sealed interface`

A `sealed` type restricts its subtypes to those declared *in the same module and package* -- the compiler knows the
complete, closed set of possibilities, unlike an ordinary `open` class or interface, whose subtypes could be anywhere.
The direct subtypes may live in different files of that package, or be nested in the sealed type itself:

[source,kotlin]
----
import java.time.LocalDate

sealed interface LoanState {
    data class Active(val dueDate: LocalDate) : LoanState
    data class Overdue(val dueDate: LocalDate, val daysLate: Int) : LoanState
    data object Returned : LoanState                 // a variant with no data at all
}
----

`sealed` subtypes are commonly ``data class``es carrying variant-specific data, plus `object` (or `data object`) for a
variant with no data -- exactly the modeling job Java's `sealed` plus `record` combination was later added to cover, and
the shape most naturally suited to representing "one of several distinct outcomes" (an API response, a UI state, a parse
result). `data object` (stable since Kotlin 1.9) is an `object` with a readable `toString()`: `println(LoanState.Returned)`
prints `Returned` instead of `LoanState$Returned@1b2c3d`.

The hierarchy, with the sealed supertype at the top:

=== Sealed class or sealed interface?

A `sealed class` can hold shared state and logic, has a constructor that is `protected` by default (it can only be called
from its subclasses) and, being a class, takes only single inheritance. A `sealed interface` carries no state and lets a
subtype implement several sealed hierarchies at once, which is the better default when the supertype has nothing to share.
Both are implicitly abstract and cannot be instantiated directly:

[source,kotlin]
----
sealed class Notification(val member: String) {
    class DueSoon(member: String, val title: String) : Notification(member)
    class Fine(member: String, val amount: Double) : Notification(member)

    fun greeting() = "Dear $member"                  // shared behaviour lives in the sealed class
}
----

The sealed rule is enforced by the compiler: a class in another module or package cannot extend a sealed type. When
compiling for JVM 17 or later, the compiler also records the permitted subclasses in the class file, in the same form as
Java's `sealed` types.

== Exhaustive `when`

A `when` expression over a `sealed` subject needs *no `else` branch* once every subtype is covered -- the compiler
verifies exhaustiveness and raises a compile error (not just a warning) if a new subtype is added later and a `when`
site is not updated to handle it. A `when` used as a statement over a sealed or enum subject must also be exhaustive
since Kotlin 1.7:

[source,kotlin]
----
import java.time.LocalDate

fun describe(state: LoanState): String = when (state) {
    is LoanState.Active -> "due on ${state.dueDate}"                      // smart-cast to Active in this branch
    is LoanState.Overdue -> "${state.daysLate} days late (due ${state.dueDate})"
    LoanState.Returned -> "returned"                                      // objects are compared by identity
    // no else needed: adding a new LoanState subtype makes this when a compile error until it is handled
}

fun main() {
    val today = LocalDate.of(2026, 11, 10)
    val states = listOf(
        LoanState.Active(today.plusDays(7)),
        LoanState.Overdue(today.minusDays(3), 3),
        LoanState.Returned,
    )
    states.forEach { println(describe(it)) }
}
----

Output:

[source,text]
----
due on 2026-11-17
3 days late (due 2026-11-07)
returned
----

This exhaustiveness check is the payoff for sealing the hierarchy in the first place: it turns "did I forget to handle a
case?" from a runtime bug into a compile-time one. The corollary is that an `else` branch on a sealed `when` is a
liability: it hides exactly the error the compiler would have reported, so leave it out.

For a sealed class, `is` checks on subtypes with type parameters are subject to the usual erasure rules; the compiler
accepts `+is Ok<*>+` and accepts `is Ok` when the type argument is determined by the subject.

=== Generic sealed hierarchies

Sealed types combine with generics to model results, trees and lists. A covariant `out` parameter lets one
`Failure` object serve every `Outcome<T>`:

[source,kotlin]
----
sealed interface Outcome<out T> {
    data class Ok<out T>(val value: T) : Outcome<T>
    data class Failed(val reason: String) : Outcome<Nothing>     // Nothing is a subtype of every T
}

fun <T, R> Outcome<T>.map(transform: (T) -> R): Outcome<R> = when (this) {
    is Outcome.Ok -> Outcome.Ok(transform(value))
    is Outcome.Failed -> this
}

fun main() {
    val a: Outcome<Int> = Outcome.Ok(21)
    val b: Outcome<Int> = Outcome.Failed("not found")
    println(a.map { it * 2 })
    println(b.map { it * 2 })
}
----

Output:

[source,text]
----
Ok(value=42)
Failed(reason=not found)
----

Sealed hierarchies are also how recursive structures are expressed: an expression tree is a sealed interface with `Num`
and `Add` variants, and its evaluator is one exhaustive `when` with a recursive call per case.

== `enum class`

An `enum class` declares a fixed set of named instances, each of which can carry constructor arguments, its own members,
and even a *constant-specific body* overriding a member per-constant:

[source,kotlin]
----
enum class Genre(val label: String, val loanDays: Int) {
    FICTION("Fiction", 21),
    SCIENCE("Science", 14),
    REFERENCE("Reference", 0);                          // the semicolon ends the constants before further members

    val lendable: Boolean get() = loanDays > 0

    fun next(): Genre = entries[(ordinal + 1) % entries.size]
}

enum class LateFee {
    STANDARD {
        override fun fee(daysLate: Int) = daysLate * 0.25            // constant-specific body
    },
    STUDENT {
        override fun fee(daysLate: Int) = maxOf(0, daysLate - 3) * 0.10
    };

    abstract fun fee(daysLate: Int): Double
}

fun main() {
    println(Genre.SCIENCE.loanDays)                   // 14
    println(Genre.REFERENCE.lendable)                 // false
    println(Genre.REFERENCE.next())                   // FICTION
    println(Genre.valueOf("FICTION").label)           // Fiction
    println(Genre.entries.map { it.name })            // [FICTION, SCIENCE, REFERENCE]
    println(LateFee.STANDARD.fee(8))                  // 2.0
    println(LateFee.STUDENT.fee(8))                   // 0.5
}
----

Output:

[source,text]
----
14
false
FICTION
Fiction
[FICTION, SCIENCE, REFERENCE]
2.0
0.5
----

`Genre.entries` (the modern replacement for the older `values()`) returns an immutable `List` of every constant in
declaration order; `ordinal` is its zero-based position and `name` its declared identifier -- both inherited
automatically, exactly like Java's `Enum`. `valueOf(text)` throws `IllegalArgumentException` for an unknown name, so
parse user input with `+entries.firstOrNull { it.name == text }+`, or `enumValueOf` / `enumValues` for generic code. An
`enum class` cannot be `sealed` and does not need to be: it is already a closed set by construction, and `when` over one is
exhaustive on the same terms as above. Enums can implement interfaces (each constant may override the members), but
cannot extend another class.

=== Enums on the JVM, `EnumMap` and `EnumSet`

An enum compiles to a final class extending `java.lang.Enum`, with one `public static final` field per constant. That is
why enum constants work in `switch` on the Java side, are safe to compare with `==`, serialise by name, and can be used in
the efficient array-backed collections `EnumMap` and `EnumSet`, which are the right containers when the keys are enum
constants:

[source,kotlin]
----
import java.util.EnumMap

fun main() {
    val perGenre = EnumMap<Genre, MutableList<String>>(Genre::class.java)
    perGenre.getOrPut(Genre.SCIENCE) { mutableListOf() }.add("Cosmos")
    perGenre.getOrPut(Genre.FICTION) { mutableListOf() }.add("Dune")
    println(perGenre)                                  // {FICTION=[Dune], SCIENCE=[Cosmos]}: ordered by ordinal
}
----

Never rely on `ordinal` for persistence: reordering the constants changes it. Store `name`, or an explicit property.

== Choosing Between Sealed Types and Enums

[cols="1,2,2",options="header"]
|===
|
|`enum class`
|`sealed` hierarchy

|Instances
|Exactly one per constant
|Any number per subtype; each carries its own data

|Shape of each case
|Identical (same properties)
|Different per subtype

|`valueOf`, `entries`, `ordinal`
|Built in
|Not available

|Exhaustive `when`
|Yes
|Yes

|Typical use
|Fixed vocabulary: genre, day, status code
|Outcomes and states with data: result, UI state, AST
|===

If every case is just a name, with at most a constant property, use an enum. As soon as some case needs its own data, use
a sealed hierarchy. A sealed hierarchy whose subtypes are all `data object` is a legitimate alternative to an enum when the
cases must also implement different interfaces.
