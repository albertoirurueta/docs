= Inheritance and Interfaces
:description: Kotlin open and override, abstract classes, interfaces with default and property members, and class delegation via "by".
:keywords: Kotlin, inheritance, open, override, abstract class, interfaces, default methods, class delegation, by keyword
:page-aliases: apps/android/kotlin/inheritance-and-interfaces.adoc

include::partial$ai-disclaimer.adoc[]

Kotlin's inheritance model is Java's, with one inversion (explicit `open`, covered on
xref:programming-languages/kotlin/classes-and-objects.adoc[Classes and Objects]) and one addition with no Java equivalent
(class delegation via `by`). This page covers `open` and `override`, constructor chaining and the order in which
constructors run (and the trap that comes with it), abstract classes, interfaces with default methods and properties,
how conflicts between inherited implementations are resolved, class delegation as the idiomatic alternative to
inheritance, the type hierarchy at the top (`Any`, `Nothing`), and guidance on when to inherit at all. The examples use
the lending library of this section (`Book`, `Member`, `Loan`), whose lendable items form a small hierarchy.

== `open` and `override`

A base class -- and each member a subclass should be able to override -- must be marked `open` explicitly; overriding
itself must be marked `override` explicitly too, so accidentally overriding (or accidentally failing to override) a base
member is a compile error rather than a silent typo:

[source,kotlin]
----
open class LibraryItem(val title: String) {
    open val loanDays: Int = 14                          // an open property can be overridden too
    open fun describe(): String = "$title, $loanDays days"
    fun id() = title.lowercase().replace(" ", "-")       // NOT open: cannot be overridden
}

class Book(title: String, val author: String) : LibraryItem(title) {
    override fun describe(): String = "${super.describe()}, by $author"     // calls the base implementation
}

class Dvd(title: String, val minutes: Int) : LibraryItem(title) {
    override val loanDays: Int = 7
    final override fun describe(): String = "$title (${minutes} min), $loanDays days"   // final: no further override
}

fun main() {
    val items: List<LibraryItem> = listOf(Book("Dune", "Herbert"), Dvd("Alien", 117))
    items.forEach { println(it.describe()) }               // dynamic dispatch: each subclass's override runs
    println(items[0].id())
}
----

Output:

[source,text]
----
Dune, 14 days, by Herbert
Alien (117 min), 7 days
dune
----

`final override fun describe()` re-seals a member so no *further* subclass can override it again -- the inheritance
equivalent of Java's `final` on a method, but only meaningful once something is already `open`. A subclass calls the base
version with `super.describe()`, and the primary constructor of the subclass must call a base constructor, here
`LibraryItem(title)` in the class header. An overriding member is itself `open` unless marked `final`. A property can be
overridden by another property (a `val` may be overridden by a `var`, but not the reverse, because a setter cannot be
removed).

== Abstract Classes

`abstract class` works as in Java: it cannot be instantiated directly, and its `abstract` members carry no body -- and,
notably, an `abstract` member is implicitly `open` (there would be no point requiring `open` on a member with no default
implementation to protect). An abstract class can mix abstract members with state and concrete behaviour:

[source,kotlin]
----
abstract class Loanable(val title: String) {
    abstract val dailyFee: Double                           // no "open" needed: abstract members already are
    abstract fun kind(): String

    fun feeFor(daysLate: Int) = daysLate * dailyFee         // concrete code using the abstract part
    override fun toString() = "${kind()} '$title'"
}

class Novel(title: String) : Loanable(title) {
    override val dailyFee = 0.25
    override fun kind() = "novel"
}

class Reference(title: String) : Loanable(title) {
    override val dailyFee = 1.0
    override fun kind() = "reference work"
}

fun main() {
    val items = listOf(Novel("Dune"), Reference("Atlas"))
    for (item in items) println("$item costs ${item.feeFor(4)} for 4 days late")
}
----

Output:

[source,text]
----
novel 'Dune' costs 1.0 for 4 days late
reference work 'Atlas' costs 4.0 for 4 days late
----

An abstract class is a template with state; an interface (next) is a contract. A class can extend only one class, but
implement any number of interfaces.

== Interfaces with Default and Property Members

A Kotlin interface can declare a method *with a body* (a default implementation, like Java's `default` methods) and can
declare abstract *properties* -- something Java interfaces cannot do at all:

[source,kotlin]
----
interface Greetable {
    val greeting: String                       // abstract property: the implementer must provide it

    fun greet() = println(greeting)            // default implementation, like Java's "default" methods
}

class English : Greetable {
    override val greeting = "Hello!"           // implemented as a property
}

class Loud : Greetable {
    override val greeting get() = "HELLO!!"    // implemented as a computed property
    override fun greet() = println(greeting.repeat(2))   // overriding the default too
}

fun main() {
    English().greet()
    Loud().greet()
}
----

Output:

[source,text]
----
Hello!
HELLO!!HELLO!!
----

Unlike a class, an interface has no state of its own -- an interface property must either be abstract (as above) or
computed from something else; it cannot hold a backing field. Interface members are `open` by default. An interface can
also extend other interfaces, and a Java interface can be implemented the same way. On the JVM, how default bodies are
compiled depends on the `-jvm-default` compiler option: either as real Java default methods or as a companion
`DefaultImpls` class with forwarding methods in implementing classes; the setting matters mostly to Java code that
implements Kotlin interfaces.

=== Resolving conflicts between inherited implementations

When a class inherits the same member from two supertypes with an implementation each, it *must* override it, and it can
call either one with `super<Type>`:

[source,kotlin]
----
interface Printable {
    fun print() = println("printable")
}

interface Exportable {
    fun print() = println("exportable")
}

class Report : Printable, Exportable {
    override fun print() {
        super<Printable>.print()              // name the supertype to disambiguate
        super<Exportable>.print()
    }
}

fun main() {
    Report().print()
}
----

Output:

[source,text]
----
printable
exportable
----

== Initialisation Order and the `open` Member Trap

A superclass constructor runs *before* the subclass's property initializers. If the superclass constructor (or an `init`
block) calls an `open` member that the subclass overrides to use its own properties, the override sees them uninitialised
-- `null` for objects and zero for primitives:

[source,kotlin]
----
open class Base {
    init {
        println("Base init: ${describe()}")     // calls an open member from the constructor
    }
    open fun describe() = "base"
}

class Derived(private val title: String) : Base() {
    init { println("Derived init: ${describe()}") }
    override fun describe() = "derived with $title"
}

fun main() {
    Derived("Dune")
}
----

Output:

[source,text]
----
Base init: derived with null
Derived init: derived with Dune
----

The order is: base constructor and its `init` blocks, then the subclass's property initializers and `init` blocks. The
compiler warns about "calling a non-final function in a constructor". The fix is to avoid calling `open` members from
constructors, `init` blocks and property initializers of an `open` class, or to make the member `final`.

== Class Delegation via `by`

Kotlin can implement an interface by *delegating every member to another object*, with one keyword and zero boilerplate
forwarding methods -- there is no equivalent one-liner in Java, where the same result requires hand-writing every
forwarding method:

[source,kotlin]
----
data class Book(val id: Int, val title: String)

interface BookRepository {
    fun findById(id: Int): Book?
    fun all(): List<Book>
}

class InMemoryRepository : BookRepository {
    private val data = mapOf(1 to Book(1, "Dune"), 2 to Book(2, "Emma"))
    override fun findById(id: Int) = data[id]
    override fun all() = data.values.toList()
}

// LoggingRepository implements BookRepository entirely by forwarding to "delegate" ...
class LoggingRepository(private val delegate: BookRepository) : BookRepository by delegate {
    // ...except for findById, which is overridden to add logging around the delegated call
    override fun findById(id: Int): Book? {
        println("looking up $id")
        return delegate.findById(id)
    }
}

fun main() {
    val repository: BookRepository = LoggingRepository(InMemoryRepository())
    println(repository.findById(2))
    println(repository.all().map { it.title })      // forwarded automatically
}
----

Output:

[source,text]
----
looking up 2
Book(id=2, title=Emma)
[Dune, Emma]
----

This is the *Decorator pattern* with the forwarding boilerplate eliminated by the compiler -- `by delegate` generates an
implementation of every interface member that simply calls the same member on `delegate`, and any member declared
explicitly (as `findById` is above) overrides that generated forwarding. Note that the delegate does not know about the
wrapper: if `InMemoryRepository.all()` called its own `findById`, it would call its own, not the wrapper's override. The
delegate can also be an expression instead of a parameter (`by InMemoryRepository()`), and a class can delegate to several
interfaces.

Delegation is the recommended way to *reuse behaviour without inheritance*: composition keeps the classes decoupled and
avoids the fragile-base-class problem, where a change in a superclass breaks its subclasses.

== The Top of the Hierarchy: `Any`, `Nothing`, `Unit`

Every class implicitly extends `Any`, which declares only `equals()`, `hashCode()` and `toString()` (not Java's `wait`,
`notify` and `getClass`, which are reached through `java.lang.Object` if needed). `Any?` is the root of everything
including nullable types. `Nothing` is the bottom of the hierarchy: a subtype of every type, with no instances, used as
the type of `throw`. The `is` and `as` operators work against this hierarchy, with smart casts after an `is` check (see
xref:programming-languages/kotlin/null-safety.adoc[Null Safety]). A `sealed` hierarchy closes the set of subclasses (see
xref:programming-languages/kotlin/sealed-classes-and-enums.adoc[Sealed Classes and Enums]).

== Kotlin's Explicit `open` vs. Java's Implicit-Open Default

[mermaid]
....
classDiagram
    class JavaShape {
        &lt;&lt;Java&gt;&gt;
        +area() double
    }
    class JavaCircle {
        &lt;&lt;Java&gt;&gt;
        +area() double
    }
    JavaShape <|-- JavaCircle : subclasses freely, any non-final class is open by default

    class KotlinShape {
        &lt;&lt;Kotlin&gt;&gt;
        +open area() double
    }
    class KotlinCircle {
        &lt;&lt;Kotlin&gt;&gt;
        +override area() double
    }
    class KotlinFinalShape {
        &lt;&lt;Kotlin&gt;&gt;
        +area() double
    }
    KotlinShape <|-- KotlinCircle : allowed, the base is explicitly open
    note for KotlinFinalShape "final by default: subclassing requires open"
....

The consequences of the inversion: a library author must decide, per class and per member, what may be overridden, which
makes extension points visible and makes libraries safer to evolve. The cost is for frameworks that create subclasses at
run time (proxies for transactions, lazy loading, mocking): they need the Kotlin `all-open` compiler plugin (Spring and JPA
presets), or an interface-based proxy, or a mock library that can mock final classes (MockK does).

== Inheritance, Delegation or Interface?

* A *is-a* relationship with shared state and a stable base: a class hierarchy (keep it shallow, document the extension
  points, and prefer `abstract` or `sealed` bases).
* A *capability* that unrelated classes share: an interface, with a default implementation if useful.
* *Reuse of behaviour* from another class without being a subtype of it: delegation with `by`.
* A fixed set of cases: a `sealed` hierarchy or an `enum`.
