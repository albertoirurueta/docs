https://kotlinlang.org/[Kotlin] is a modern, statically-typed programming language created by
https://www.jetbrains.com/[JetBrains] and released under the Apache 2.0 license. It first shipped in 2011,
reached 1.0 in 2016, and became an https://www.jetbrains.com/company/#history[Apache-licensed, open-source
project governed with community input] from the start. Kotlin is *interoperable with Java* and targets several
platforms through Kotlin Multiplatform, but the JVM has always been its first and most mature target -- this
whole section documents Kotlin on the JVM (see xref:programming-languages/kotlin/kotlin-and-the-jvm.adoc[Kotlin and the
JVM] for how the other targets relate).

== Installing Kotlin

You rarely install a standalone Kotlin compiler on its own -- most projects get it transitively through a build
tool or an IDE -- but three options exist:

* **SDKMAN (Linux/macOS/WSL)** -- the simplest command-line install:
+
[source,shell]
----
curl -s "https://get.sdkman.io" | bash
sdk install kotlin
----
* **Homebrew (macOS/Linux)**:
+
[source,shell]
----
brew install kotlin
----
* **IntelliJ IDEA / Android Studio** -- both ship a bundled Kotlin plugin and toolchain, so no separate install
  is needed when you create a project from the IDE. See xref:programming-languages/kotlin/ides-and-tools.adoc[Kotlin IDEs & Tools]
  for the full list of IDEs and editors.

See https://kotlinlang.org/docs/command-line.html[Working with command-line compiler] for platform-specific
installer downloads (a `.zip`/`.tar.gz` release) if you prefer a manual install.

== `kotlinc`, the Compiler

`kotlinc` compiles `.kt` files to JVM class files, exactly as `javac` does for `.java` files:

[source,shell]
----
kotlinc hello.kt -include-runtime -d hello.jar
java -jar hello.jar
----

`-include-runtime` bundles the small Kotlin standard-library runtime into the jar so it runs standalone; without
it, `kotlin-stdlib.jar` must be on the classpath separately (which is what a Gradle/Maven build does for you
automatically -- see xref:programming-languages/kotlin/build-and-tooling.adoc[Build and Tooling]).

== The Kotlin REPL and the Kotlin Playground

`kotlinc` with no arguments starts an interactive REPL (read-eval-print loop), useful for quick experiments:

[source,console]
----
$ kotlinc
Welcome to Kotlin version 2.4.0 (JRE 21.0.4+7)
Type :help for help, :quit for quit
>>> val greeting = "Hello"
>>> println("$greeting, Kotlin!")
Hello, Kotlin!
----

No local install is needed at all to try Kotlin: https://play.kotlinlang.org/[the Kotlin Playground] runs and
shares snippets entirely in the browser, against a real (if sandboxed) Kotlin compiler -- the fastest way to try
an idea from this section without touching a project.

== "Hello, World"

A complete Kotlin program can be a single top-level function -- no enclosing class, and no access modifier, is
required:

[source,kotlin]
----
fun main() {
    println("Hello, World!")
}
----

Compare this to Java's mandatory `+public class Main { public static void main(String[] args) { ... } }+`
boilerplate -- Kotlin's `fun main()` compiles to a real `public static void main(String[])` method on a
synthetic class (named after the file, e.g. `HelloKt`), it just doesn't make you write that ceremony by hand.
`main` may optionally take `args: Array<String>` when command-line arguments are needed.

== Compiling to JVM Bytecode

`kotlinc` compiles Kotlin source to the *same `.class` bytecode format* the JVM already runs and `javac`
already produces -- there is no separate "Kotlin runtime" the way, say, a scripting language needs an
interpreter. This is the foundation for everything in
xref:programming-languages/kotlin/kotlin-and-the-jvm.adoc[Kotlin and the JVM]: full Java interoperability, running
anywhere a JVM runs, and using the entire Java ecosystem (libraries, application servers, profilers) unmodified.

[source,shell]
----
kotlinc hello.kt -d out/
javap -c out/HelloKt.class | head -5
----

== Command-Line Arguments and Input

`main` may take `args: Array<String>`, and the standard library reads standard input with `readln()` (throws at end of input)
and `readlnOrNull()` (returns `null`). A first program for the lending library that every later page of this section
builds on, a loan counter driven by the command line:

[source,kotlin]
----
// Loans.kt
data class Loan(val title: String, val days: Int)

fun parseLoan(text: String): Loan? {
    val parts = text.split(":")
    val days = parts.getOrNull(1)?.toIntOrNull() ?: return null     // null for malformed input, no exception
    return Loan(parts[0], days)
}

fun main(args: Array<String>) {
    val loans = args.mapNotNull(::parseLoan)                       // keep only the arguments that parsed
    if (loans.isEmpty()) {
        println("usage: loans Title:days ...")
        return
    }
    loans.forEach { println("${it.title} is out for ${it.days} days") }
    println("total days: ${loans.sumOf { it.days }}")
}
----

Compile and run it with the commands shown above (`kotlinc Loans.kt -include-runtime -d loans.jar`, then
`java -jar loans.jar Dune:14 Emma:7 broken`):

[source,text]
----
Dune is out for 14 days
Emma is out for 7 days
total days: 21
----

The class holding `main` is generated from the file name: `Loans.kt` becomes `LoansKt`, so the jar's manifest entry point is
`LoansKt`. The `broken` argument has no colon, so `parseLoan` returned `null` and `mapNotNull` dropped it.

== Kotlin Scripts

A file named `something.main.kts` is a *Kotlin script*: top-level statements run without a `main` function, and
`@file:DependsOn("group:artifact:version")` pulls a library from Maven Central. Scripts suit small automation tasks and are
launched with `kotlin something.main.kts`; for anything beyond a single file, a Gradle project (see
xref:programming-languages/kotlin/build-and-tooling.adoc[Build and Tooling]) is the better home.

[source,kotlin]
----
// hello.main.kts
val names = listOf("Ada", "Grace")
names.forEach { println("Hello, $it!") }
----

== What the Toolchain Does

Whatever the entry point (the command line, a script, a build tool, an IDE), the same compiler produces the same bytecode:

[mermaid]
....
flowchart LR
    KT["hello.kt or Loans.kt"] --> KC["kotlinc: the Kotlin compiler"]
    KC --> CL["HelloKt.class: JVM bytecode"]
    STD["kotlin-stdlib.jar"] --> RUN
    CL --> RUN["java -jar or the JVM running the classes"]
    KC -. "-include-runtime bundles the stdlib" .-> JAR["hello.jar"]
    JAR --> RUN
....

== Why Kotlin

Kotlin was designed to be *pragmatic*: concise syntax that removes Java boilerplate (data classes, properties, type
inference, default arguments), *safety* built into the type system (nullability, read-only references), full *Java
interoperability* so that nothing is rewritten to start, and excellent *tool support* from the company that makes the IDEs.
The rest of this section follows the order a newcomer needs: the language fundamentals first, then object-oriented and
functional programming, the type system, collections, error handling and coroutines.
