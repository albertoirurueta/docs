A *type-safe builder* is a function that takes a lambda, runs it against a freshly created object and returns the result,
so that nested calls read like a declarative document and the compiler checks the structure. The one language feature
that makes this possible is the *function type with receiver*; a handful of conventions (builder classes, `apply`,
`@DslMarker`, operator overloads) complete the pattern. This page explains the mechanism, shows how it compiles, builds
a small HTML builder and then a DSL for the lending library of this section (`Book`, `Member`, `Loan`), introduces
`@DslMarker` to stop receivers leaking between nesting levels, and lists the trade-offs and the well-known DSLs in the
Kotlin ecosystem.

== Lambdas with Receiver

An ordinary function type is `+(T) -> R+`; a function type *with receiver* is written `+T.() -> R+` -- inside such a lambda,
members of `T` are callable directly (via an implicit `this`), exactly as if the lambda's body were written inside a
member function of `T`:

[source,kotlin]
----
class HtmlBuilder {
    private val content = StringBuilder()

    fun text(value: String) {
        content.append(value)
    }

    override fun toString() = content.toString()
}

fun html(block: HtmlBuilder.() -> Unit): String {   // "block" has HtmlBuilder as its receiver
    val builder = HtmlBuilder()
    builder.block()                                   // calling the lambda AS IF it were a member of builder
    return builder.toString()
}

fun main() {
    val page = html {
        text("Hello, ")     // "text" is called with no explicit receiver: resolved against the implicit this
        text("World!")
    }
    println(page)
}
----

Output:

[source,text]
----
Hello, World!
----

This is exactly the same mechanism that `run`, `with` and `apply`
(xref:programming-languages/kotlin/extension-functions-and-scope-functions.adoc[Extension Functions and Scope Functions])
use internally -- a scope function's lambda parameter is itself typed `+T.() -> R+`.

=== How it compiles

A function type with receiver is the same type as one that takes the receiver as its first parameter:
`+HtmlBuilder.() -> Unit+` and `+(HtmlBuilder) -> Unit+` are interchangeable at run time (both are `Function1`), and a value of
one can be passed where the other is expected. A lambda with receiver is compiled to a function whose first
parameter is the receiver, and `builder.block()` is the call `block(builder)`. An *extension function* is the same idea
for named functions: the receiver is the first parameter of a static method. That is why the lambda body can call
members of `T` without qualification: the compiler resolves them against the extra implicit receiver.

The lambda with receiver is also not tied to a nested class: it can be stored, passed on, or invoked with
`block(builder)` or `block.invoke(builder)`.

== Building a Small Type-Safe HTML Builder

Nesting builder classes, each exposing member functions that themselves take a lambda with receiver, produces a
tree-shaped DSL where the Kotlin compiler enforces the *structure* (only a `<li>` inside a `<ul>`, say) at compile time
-- unlike a plain string-templating approach, which catches nothing until the output is rendered:

[source,kotlin]
----
class Ul {
    private val items = mutableListOf<String>()
    fun li(text: String) { items += "<li>$text</li>" }
    override fun toString() = "<ul>${items.joinToString("")}</ul>"
}

class Html {
    private val parts = mutableListOf<String>()
    fun ul(block: Ul.() -> Unit) { parts += Ul().apply(block).toString() }
    override fun toString() = parts.joinToString("")
}

fun html(block: Html.() -> Unit): String = Html().apply(block).toString()

fun main() {
    val page = html {
        ul {
            li("first")
            li("second")
        }
    }
    println(page)
}
----

Output:

[source,text]
----
<ul><li>first</li><li>second</li></ul>
----

Each nested `block` call chains to a *new* receiver (`Ul`, not `Html`) for its own body -- `+li(...)+` is only callable
inside a `+ul { }+` block, which is the compile-time structural guarantee this style buys over generating markup with raw
string concatenation.

[mermaid]
....
flowchart TD
    A["html { ... }"] -->|receiver: Html| B["ul { ... }"]
    B -->|receiver: Ul| C["li('first')"]
    B -->|receiver: Ul| D["li('second')"]
    C --> E["Ul.toString()"]
    D --> E
    E --> F["Html.toString(): full page markup"]
....

== A DSL for the Library Domain

The same pattern, applied to the running example, gives a configuration DSL that reads like data. The recipe has four
parts: a data model (immutable), one builder class per nesting level (mutable, private to the DSL), one entry function
that creates the root builder and runs the lambda, and member functions on each builder that take a lambda for the child
level:

[source,kotlin]
----
data class Book(val title: String, val author: String, val year: Int)
data class Member(val name: String, val loans: List<String>)
data class Library(val books: List<Book>, val members: List<Member>)

@DslMarker
annotation class LibraryDsl

@LibraryDsl
class BookBuilder {
    var title = ""
    var author = ""
    var year = 0
    fun build() = Book(title, author, year)
}

@LibraryDsl
class MemberBuilder(private val name: String) {
    private val loans = mutableListOf<String>()
    fun borrows(title: String) { loans += title }
    fun build() = Member(name, loans.toList())
}

@LibraryDsl
class LibraryBuilder {
    private val books = mutableListOf<Book>()
    private val members = mutableListOf<Member>()

    fun book(init: BookBuilder.() -> Unit) { books += BookBuilder().apply(init).build() }
    fun member(name: String, init: MemberBuilder.() -> Unit) { members += MemberBuilder(name).apply(init).build() }
    fun build() = Library(books.toList(), members.toList())
}

fun library(init: LibraryBuilder.() -> Unit): Library = LibraryBuilder().apply(init).build()

fun main() {
    val lib = library {
        book {
            title = "Dune"
            author = "Herbert"
            year = 1965
        }
        book {
            title = "Emma"
            author = "Austen"
            year = 1815
        }
        member("Ada") {
            borrows("Dune")
        }
    }
    println(lib)
}
----

Output:

[source,text]
----
Library(books=[Book(title=Dune, author=Herbert, year=1965), Book(title=Emma, author=Austen, year=1815)], members=[Member(name=Ada, loans=[Dune])])
----

The structure of the scopes, and which receiver is active at each level, is:

[mermaid]
....
flowchart TD
    L["library { ... }: receiver LibraryBuilder"] --> B1["book { ... }: receiver BookBuilder"]
    L --> B2["book { ... }: receiver BookBuilder"]
    L --> M["member { ... }: receiver MemberBuilder"]
    B1 --> P1["title, author, year: properties assigned"]
    M --> P2["borrows(title): adds a loan"]
    L --> R["build(): immutable Library value"]
....

The builders are mutable, but the result is an immutable data model: each `build()` copies mutable state (`toList()`).
That is the standard design, because callers receive a value that cannot be changed afterwards.

== Scope Control with `@DslMarker`

Lambdas nest, and in a nested lambda *all* enclosing receivers are available. Without a guard the inner block of
`+member("Ada") { ... }+` could silently call `+book { }+` of the outer `LibraryBuilder`, which compiles but means something
different from what the author intended. `@DslMarker` is the guard: annotate every builder class of the DSL with the same
marker annotation, and the compiler then forbids calling members of an *outer* receiver implicitly from an inner block
of the same DSL:

[source,kotlin]
----
fun broken() = library {
    member("Ada") {
        borrows("Dune")
        // book { title = "x" }          // compile error: 'book' can't be called in this context by implicit receiver
        this@library.book { title = "x" }  // allowed: the outer receiver is named explicitly
    }
}
----

An explicit `this@library` still reaches the outer receiver. The marker is the standard defence for large DSLs such as
`kotlinx.html` and Compose's layout scopes, where accidentally nesting a `div` in the wrong place would otherwise
compile.

== Operators and Infix Calls in DSLs

Operator overloads let a DSL drop punctuation. The classic example is `unaryPlus` for adding text, and `invoke` to make
an object callable like a block:

[source,kotlin]
----
class Paragraph {
    private val parts = mutableListOf<String>()
    operator fun String.unaryPlus() { parts += this }       // +"text" appends a part
    override fun toString() = "<p>${parts.joinToString(" ")}</p>"
}

fun p(block: Paragraph.() -> Unit) = Paragraph().apply(block).toString()

fun main() {
    println(p {
        +"A library"
        +"of books"
    })
}
----

Output:

[source,text]
----
<p>A library of books</p>
----

Other tools used in DSLs are: `infix` functions (`"Dune" borrowedBy "Ada"`), an `invoke` operator on a class so that
`+config { }+` can be a property, extension functions on the builder to add vocabulary from outside, and `inline`
functions so that the block lambdas are inlined with no allocation.

== Trade-Offs

* A DSL is a *small language*: it needs documentation, error messages that make sense, and tests. Use it when the
  configuration is deeply nested or repeated enough that plain constructors and named arguments become unreadable.
* Without `@DslMarker`, nested scopes can leak. With it, Java callers still see only ordinary classes and methods.
* Builders are mutable and not thread-safe; share only the immutable result.
* Because lambdas are `inline` or allocated closures, a DSL has a small run-time cost; for hot paths prefer a plain
  constructor.
* Kotlin offers builder functions in the standard library too: `+buildString { }+`, `+buildList { }+`, `+buildMap { }+` and
  `+buildSet { }+` all take a lambda with a mutable receiver and return the read-only result.

== Where This Pattern Shows Up

* *`kotlinx.html`* -- an HTML-generation library built on exactly this pattern, one builder class per HTML element.
* *The Gradle Kotlin DSL* (`build.gradle.kts`) -- `+plugins { }+`, `+dependencies { }+` and `+tasks.named { }+` are all
  lambda-with-receiver blocks over Gradle's own configuration objects, which is what gives `build.gradle.kts` IDE
  autocompletion a Groovy `build.gradle` never had.
* *Routing DSLs* (for example Ktor's `+routing { get("/users") { ... } }+`) -- the same nested-receiver structure, scoped
  to defining HTTP routes instead of markup.
* *Compose UI* -- composable content lambdas have receiver scopes such as `ColumnScope` and `RowScope`, whose
  member functions are only callable inside the matching container.
* *Test frameworks* -- Kotest and Spek nest `+describe { }+` and `+it { }+` blocks, and MockK's `+every { }+` and `+verify { }+`
  are lambdas whose receivers expose the mocking vocabulary.
