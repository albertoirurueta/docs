= Kotlin and the JVM
:description: Kotlin/JVM compiles to the same bytecode the JVM runs, is fully Java-interoperable, and runs anywhere a JVM does -- servers, CLI tools, desktop apps, build tooling, and Android, which is one target among several under Kotlin Multiplatform (JVM, JS, Native, Wasm).
:keywords: Kotlin, JVM, bytecode, Java interoperability, Kotlin Multiplatform, Kotlin/JS, Kotlin/Native, Kotlin/Wasm, Android, Compose Multiplatform, Gradle Kotlin DSL
:page-aliases: apps/android/kotlin/kotlin-and-the-jvm.adoc

Kotlin is often introduced through Android, and Android is indeed the platform where Google has
https://developer.android.com/kotlin/first[recommended Kotlin as the preferred language since 2019] -- but Kotlin *is a
general-purpose JVM language first*. This page states that plainly before the rest of this section gets into language
details, because the framing changes how several later features read (all-open classes, coroutines, the build tooling).
It covers what the compiler produces, how Kotlin types map to JVM types, how to call Java from Kotlin and Kotlin from
Java (including the annotations that shape the generated bytecode), where Kotlin/JVM runs, and how it sits among the
other Kotlin targets.

== Kotlin/JVM Compiles to the Same Bytecode Java Does

`kotlinc` compiles `.kt` source to standard JVM `.class` files -- the identical bytecode format `javac` produces from `.java`
source. There is no Kotlin-specific virtual machine, no interpreter, and no separate runtime beyond a small
`kotlin-stdlib.jar` (extension functions, `Sequence`, coroutine primitives, and similar library code) that ships alongside
your compiled classes like any other JAR dependency.

Because of this, Kotlin/JVM:

* Runs on *any JVM* that already runs Java -- the same HotSpot/OpenJDK/GraalVM you already deploy to, with the same class
  loading, garbage collection, JIT compilation, and profiling and monitoring tools (JFR, async-profiler, VisualVM) --
  nothing Kotlin-specific to install on the runtime side.
* Is *fully Java-interoperable in both directions*: Kotlin code calls Java classes and libraries directly (Kotlin was
  designed from day one to sit on top of the existing Java ecosystem with no wrapper layer), and Java code calls Kotlin
  classes just as directly, since a compiled Kotlin class *is* a JVM class like any other.
* Works with *any Java build tool* -- Maven, Gradle -- via a compiler plugin (see
  xref:programming-languages/kotlin/build-and-tooling.adoc[Build and Tooling]).

You can see exactly what the compiler generates. This file:

[source,kotlin]
----
// Library.kt, in the default package
data class Book(val title: String, val year: Int)

fun describe(book: Book): String = "${book.title} (${book.year})"

fun main() {
    println(describe(Book("Dune", 1965)))
}
----

compiles to two classes, `Book.class` (the data class: private final fields, getters, `copy`, `component1`, `equals`,
`hashCode`, `toString`) and `LibraryKt.class` (a *file facade*: the top-level functions `describe` and `main` become
`public static` methods of a class named after the file). `kotlinc Library.kt -include-runtime -d library.jar` and
`java -jar library.jar` print `Dune (1965)`, and `javap -p LibraryKt.class` lists
`public static final java.lang.String describe(Book)` and `public static final void main()`.

== Type Mapping

Kotlin types map onto JVM types in a way that is mostly invisible, but worth knowing at the interop boundary:

[cols="2,2,3"]
|===
|Kotlin |JVM |Note

|`Int`, `Long`, `Double`, `Boolean`, `Char`
|`int`, `long`, `double`, `boolean`, `char`
|primitives when non-null and not a generic argument; boxed (`Integer`, ...) as `Int?`, `List<Int>` and similar.

|`Unit`
|`void`
|a `Unit` function compiles to a `void` method; used as a type argument it is the singleton `Unit` object.

|`Nothing`
|`Void` (as a return type, the method never returns)
|the type of `throw`; rarely visible from Java.

|`String`, `Any`
|`java.lang.String`, `java.lang.Object`
|the same classes; Kotlin only adds extension functions.

|`List`, `MutableList`, `Map`, `Set`
|`java.util.List`, `java.util.Map`, `java.util.Set`
|read-only and mutable interfaces are *views* of the same Java type; Java code can mutate a Kotlin `List`.

|`Array<String>`, `IntArray`
|`String[]`, `int[]`
|`Array<T>` is `T[]`; `IntArray` and the other primitive arrays avoid boxing.

|Function types `+(A) -> B+`
|`kotlin.jvm.functions.Function1<A, B>`
|Java calls them as `Function1`, with `invoke`; Java lambdas can implement them.

|`String?`, `String`
|`java.lang.String` with `@Nullable` or `@NotNull`
|nullability is recorded in annotations and metadata, not in the runtime type.
|===

== Calling Java from Kotlin

Java classes and methods are used as if they were Kotlin, with a few adaptations the compiler makes automatically:

* *Getters and setters become properties*: `person.getName()` is written `person.name`, and `setName("x")` is an
  assignment (a boolean `isActive()` is the property `isActive`).
* *SAM conversion*: a Java interface with one abstract method (`Runnable`, `Comparator`) takes a Kotlin lambda.
* *Platform types*: Java return values have no nullability information and are typed `T!`; Kotlin trusts you, and the
  safe choice is to declare the nullable type yourself (see
  xref:programming-languages/kotlin/null-safety.adoc[Null Safety]).
* *Checked exceptions are not enforced*; you do not write `try` or `throws` for them.
* Java `static` members are called through the class name, and a Java member whose name is a Kotlin keyword (such as `in` or `is`)
  is written with backticks.

[source,kotlin]
----
import java.time.LocalDate
import java.util.Collections

fun main() {
    val today = LocalDate.of(2026, 11, 10)
    println(today.plusDays(7).dayOfWeek)              // getDayOfWeek() is the property dayOfWeek

    val titles = mutableListOf("Emma", "Dune", "Walden")
    Collections.sort(titles) { a, b -> a.length - b.length }     // lambda converted to a java.util.Comparator
    println(titles)

    val builder = StringBuilder()                    // a Java class used directly
    builder.append("Dune").append(1965)
    println(builder)
}
----

Output:

[source,text]
----
TUESDAY
[Emma, Dune, Walden]
Dune1965
----

== Calling Kotlin from Java

A Kotlin declaration may have no direct Java equivalent: top-level functions, default arguments, properties, companion
objects, `object` singletons, extension functions. The compiler generates a predictable Java-visible shape for each, and
annotations adjust it:

[cols="2,3,3"]
|===
|Kotlin |What Java sees |Annotation to improve it

|top-level `fun f()` in `Util.kt`
|`UtilKt.f()` (static method in the file facade)
|`@file:JvmName("Util")` renames the class to `Util`.

|`+object Config { fun load() }+`
|`Config.INSTANCE.load()`
|`@JvmStatic` on `load` also generates a static `Config.load()`.

|`+companion object { fun create() }+` in `class Foo`
|`Foo.Companion.create()`
|`@JvmStatic` makes `Foo.create()` work.

|`val name` (property)
|`getName()` (and `setName` for `var`)
|`@JvmField` exposes a public field instead; `@get:JvmName("name")` renames the getter.

|default arguments, `fun f(a: Int, b: Int = 1)`
|only `f(int, int)`
|`@JvmOverloads` generates `f(int)` too.

|extension `fun String.shout()`
|`UtilKt.shout(String)` (receiver is the first parameter)
|none: it is an ordinary static method.

|`fun f()` that may throw `IOException`
|no `throws` clause, so Java cannot catch the checked exception specifically
|`@Throws(IOException::class)`.

|`const val MAX = 3`
|`public static final int MAX`
|none needed; it is a compile-time constant.
|===

The following Kotlin class, written for use from both languages, applies the annotations:

[source,kotlin]
----
// Loans.kt
@file:JvmName("Loans")

package library

import java.io.IOException

class Loan @JvmOverloads constructor(val title: String, val days: Int = 14) {
    companion object {
        @JvmStatic
        fun standard(title: String) = Loan(title)

        const val MAX_DAYS = 60
    }
}

@Throws(IOException::class)
fun loadLoans(path: String): List<Loan> = emptyList()

fun Loan.describe() = "$title for $days days"
----

and its use from Java, which reads like ordinary Java:

[source,java]
----
import library.Loan;
import library.Loans;

public class Main {
    public static void main(String[] args) throws java.io.IOException {
        Loan a = new Loan("Dune");                 // @JvmOverloads generated this constructor
        Loan b = Loan.standard("Emma");            // @JvmStatic: no Companion in the call
        System.out.println(a.getTitle() + " " + b.getDays());   // properties as getters
        System.out.println(Loans.describe(a));     // the extension is a static method of the file facade Loans
        System.out.println(Loan.MAX_DAYS);         // const val is a static final field
        Loans.loadLoans("loans.txt");              // @Throws made the checked exception visible
    }
}
----

Output:

[source,text]
----
Dune 14
Dune for 14 days
60
----

Because Kotlin writes extra *metadata* into each class (nullability, `inline`, default values, properties), Kotlin code sees
more precise types than Java does for the same classes, and Java sees an ordinary class with no trace of it.

== Where Kotlin/JVM Runs

Because it is JVM bytecode, Kotlin/JVM runs wherever a JVM does, well beyond Android:

* *Servers* -- Spring Boot officially supports Kotlin as a first-class language; see
  xref:backend/springboot/java-or-kotlin.adoc[Java or Kotlin for Spring Boot?].
* *CLI tools and scripts* -- `kotlinc` compiles a standalone executable jar, and Kotlin scripting (`.kts`) runs snippets
  without a full build.
* *Desktop applications* -- via https://www.jetbrains.com/lp/compose-multiplatform/[Compose Multiplatform] for a modern
  declarative UI, or plain JavaFX/Swing called directly from Kotlin.
* *Build tooling* -- Gradle itself supports build scripts written in Kotlin (the *Gradle Kotlin DSL*,
  `build.gradle.kts`), which is how most new Gradle projects (Kotlin and Android alike) are configured today.
* *Android* -- Google's officially preferred application language since 2019 -- covered in depth in
  xref:programming-languages/kotlin/kotlin-for-android.adoc[Kotlin for Android], but it is one deployment target among the
  several above, not Kotlin's defining one. Android runs the bytecode through its own runtime after conversion to DEX, so
  the same Kotlin source follows the same rules with a different JVM-library surface.

== Performance and Footprint

Kotlin compiles to the same instructions a Java compiler would produce, so the *run-time* performance of equivalent code is
the same. Differences come from specific features: `inline` functions remove lambda allocations, `Sequence` and collection
operations allocate intermediate objects, boxed `Int?` and `List<Int>` cost memory, a captured `var` in a lambda is boxed
in a `Ref` object, and the standard library is one more JAR on the class path (shrunk away on Android by R8).
Compilation is slower than `javac` for the same code, mitigated by incremental builds and the daemon (see
xref:programming-languages/kotlin/build-and-tooling.adoc[Build and Tooling]).

== Kotlin/JVM in the Wider Kotlin Multiplatform Picture

The Kotlin compiler front end is shared, but its back end can target more than the JVM under
https://kotlinlang.org/docs/multiplatform.html[Kotlin Multiplatform (KMP)]:

* *Kotlin/JVM* -- this section's subject: JVM bytecode.
* *Kotlin/JS* -- compiles to JavaScript, for browser or Node.js code.
* *Kotlin/Native* -- compiles ahead-of-time to native machine code (LLVM-based) for platforms without a JVM, most notably
  iOS, but also native Linux/Windows/macOS binaries.
* *Kotlin/Wasm* -- compiles to WebAssembly.

The xref:apps/kotlin-multiplatform/index.adoc[Kotlin Multiplatform] section documents KMP in depth. KMP lets a project share
business-logic Kotlin source across all four back ends while writing platform-specific UI/IO code natively per platform --
typically to share code between an Android app (Kotlin/JVM) and an iOS app (Kotlin/Native) from one codebase. This section
documents Kotlin/JVM only; Kotlin/Native and Kotlin/JS are out of scope beyond this orientation.
