Coroutines are Kotlin's answer to asynchronous programming -- code that reads top-to-bottom like ordinary sequential
code, but can suspend without blocking the underlying thread. They ship as a separate library, `kotlinx.coroutines`, not
the language core itself, though the `suspend` keyword that makes them possible is a language feature. This page covers
what a coroutine is and how a `suspend` function is compiled, the builders that start coroutines, scopes and the
structured-concurrency tree that ties lifetimes together, the life cycle of a `Job`, running work concurrently or
sequentially, and the pitfalls that account for most real-world coroutine bugs. The examples use the lending library of
this section (`Book`, `Member`, `Loan`) and need only the `kotlinx-coroutines-core` dependency:

[source,kotlin]
----
// build.gradle.kts
dependencies {
    implementation("org.jetbrains.kotlinx:kotlinx-coroutines-core:<version>")   // the current 1.x release
}
----

== Why Coroutines

A thread is an operating-system resource: it reserves a megabyte or so of stack, and switching between threads is
expensive, so a server that blocks one thread per request runs out of threads long before it runs out of work. A
coroutine is a lightweight, resumable computation that costs a few dozen bytes while suspended and is *multiplexed* onto
a small pool of threads: thousands of coroutines waiting for the network can share a handful of threads, and code that
waits (`delay`, a network call, `channel.receive()`) frees its thread instead of blocking it. In contrast with callbacks
and reactive chains, the code still reads as a straight line, with `try`/`catch`, loops and local variables intact.

== `suspend` Functions

A function marked `suspend` may pause its execution at a well-defined point (for example while awaiting an I/O result) and
resume later, *without blocking the thread it started on* -- the compiler transforms it into a state-machine-like
implementation behind the scenes:

[source,kotlin]
----
import kotlinx.coroutines.delay
import kotlinx.coroutines.runBlocking

data class Book(val isbn: String, val title: String)

suspend fun findBook(isbn: String): Book {
    delay(100)                       // "delay" suspends, unlike Thread.sleep which blocks the thread
    return Book(isbn, "Dune")
}

fun main() = runBlocking {
    println("looking up")
    val book = findBook("978-0441172719")   // suspension point: main's coroutine pauses, the thread is free
    println("found ${book.title}")
}
----

Output:

[source,text]
----
looking up
found Dune
----

A `suspend` function can only be called from another `suspend` function, or from inside a coroutine -- this "coloring" is
deliberate: it makes it visible at every call site whether a function can suspend, the same way Kotlin makes
nullability visible in a type rather than leaving it implicit. A `suspend` function is not asynchronous by itself: it
runs sequentially on the caller's coroutine, and concurrency begins only where a builder (below) starts another one.

=== How a suspend function compiles

The compiler uses *continuation-passing style*. `suspend fun findBook(isbn: String): Book` becomes a method that takes an
extra `Continuation<Book>` parameter and returns `Any?`. The body is split into *states* at each suspension point. When
the function reaches a call that suspends, it saves its local variables and the number of the next state into a
continuation object and returns the special marker `COROUTINE_SUSPENDED`, which unwinds the stack and frees the thread.
When the awaited operation completes, the dispatcher calls the continuation's `resumeWith`, which jumps back into the
function at the saved state with the locals restored. A suspend call that completes immediately simply returns its
value with no suspension at all.

[mermaid]
....
sequenceDiagram
    participant C as Caller coroutine
    participant F as findBook state machine
    participant D as delay and the dispatcher
    C->>F: findBook(isbn, continuation) with state 0
    F->>D: delay(100, continuation) schedules a resume
    D-->>F: returns COROUTINE_SUSPENDED
    F-->>C: returns COROUTINE_SUSPENDED, thread is free
    Note over C,D: 100 ms later, no thread is blocked meanwhile
    D->>F: continuation.resumeWith(Unit) with state 1
    F->>F: executes return Book(...)
    F->>C: resumes the caller with the result
....

== Coroutine Builders: `launch`, `async`, `runBlocking`

A coroutine is *started* by a builder function, each suited to a different situation:

[cols="1,2"]
|===
|Builder |Use

|`launch`
|fire-and-forget -- starts a coroutine and returns a `Job` handle, with no result value.

|`async`
|starts a coroutine that *does* produce a result, returned as a `Deferred<T>`; call `await()` to suspend until it
completes.

|`runBlocking`
|bridges regular blocking code into the coroutine world by *blocking the current thread* until its coroutine body
completes -- almost always confined to a `main` function or a test, never used inside application code that already runs
in a coroutine.

|`coroutineScope`
|a suspending function (not a launcher) that creates a child scope and returns only when every coroutine started in it has
finished; the building block of structured concurrency.
|===

[source,kotlin]
----
import kotlinx.coroutines.*

fun main() = runBlocking {                          // bridges main (not a suspend function) into coroutines
    val job = launch {                              // fire-and-forget child coroutine
        delay(100)
        println("launched work done")
    }

    val deferred = async {                          // produces a result
        delay(50)
        42
    }
    println("the answer is ${deferred.await()}")    // suspends here until async completes

    println("main continues after the async; launch may still be running: ${job.isActive}")
    job.join()                                      // suspends until the launched coroutine completes
    println("all done")
}
----

Output:

[source,text]
----
the answer is 42
main continues after the async; launch may still be running: true
launched work done
all done
----

`launch` and `async` return *immediately*; the new coroutine runs concurrently with the code that follows. The body of `runBlocking`
is itself a coroutine, and it does not finish until its children have, so even without the `join()` above, `launched
work done` would have been printed before `main` returned.

== Concurrent versus Sequential Composition

Calling suspend functions one after the other is sequential, even though each one suspends. To run them *concurrently*,
start each in its own `async` and await both:

[source,kotlin]
----
import kotlinx.coroutines.*

data class Book(val isbn: String, val title: String)
data class Review(val isbn: String, val stars: Int)

suspend fun findBook(isbn: String): Book { delay(300); return Book(isbn, "Dune") }
suspend fun findReview(isbn: String): Review { delay(200); return Review(isbn, 5) }

fun main() = runBlocking {
    val t0 = System.currentTimeMillis()
    val book1 = findBook("1")
    val review1 = findReview("1")                   // starts only after findBook has returned
    val sequential = System.currentTimeMillis() - t0
    println("sequential: ${book1.title} ${review1.stars}, at least 500 ms: ${sequential >= 500}")

    val t1 = System.currentTimeMillis()
    val book = async { findBook("1") }
    val review = async { findReview("1") }          // both coroutines are in flight now
    println("concurrent: ${book.await().title} ${review.await().stars}")
    val concurrent = System.currentTimeMillis() - t1
    println("concurrent took less than the sum: ${concurrent < 500}")
}
----

Output:

[source,text]
----
sequential: Dune 5, at least 500 ms: true
concurrent: Dune 5
concurrent took less than the sum: true
----

The same `async` calls can also be started lazily with `async(start = CoroutineStart.LAZY)`, in which case they run only
when `await()` or `start()` is called.

== `CoroutineScope`

Every coroutine builder is an extension function on `CoroutineScope` -- a coroutine can only be launched *within* a
scope, and that scope is what ties the coroutine's lifetime to something meaningful (a screen, a request, a test). A scope
is a thin wrapper around a `CoroutineContext` that contains a `Job`:

[source,kotlin]
----
import kotlinx.coroutines.*

class CatalogRepository(private val scope: CoroutineScope) {
    fun refreshInBackground() {
        scope.launch {
            delay(50)
            println("catalog refreshed")
        }
    }
}

fun main() = runBlocking {
    val repository = CatalogRepository(this)       // runBlocking's own scope: children are awaited
    repository.refreshInBackground()
    println("requested a refresh")
}
----

Output:

[source,text]
----
requested a refresh
catalog refreshed
----

On Android, `viewModelScope` and `lifecycleScope` (see xref:programming-languages/kotlin/kotlin-for-android.adoc[Kotlin for
Android]) are the ready-made scopes tied to the lifetime of a `ViewModel` or of a `Lifecycle`-aware component, so coroutines
are cancelled automatically when the screen goes away. On the server, a scope belongs to a request or to the application.
To create one yourself, write `pass:c[CoroutineScope(SupervisorJob() + Dispatchers.Default)]` and call `scope.cancel()` when the
owner is disposed.

`GlobalScope` also exists, but it has *no* lifecycle: coroutines launched in it are never cancelled by an owner and
outlive the code that started them, which is the very problem structured concurrency solves. It is marked as a delicate
API and should be avoided in application code.

== Structured Concurrency

*Structured concurrency* means a coroutine started inside a scope becomes a *child of that scope*, and the parent will not
consider itself "done" until every child has finished -- cancelling a parent automatically cancels every descendant, and an
unhandled exception in a child propagates up to the parent by default. This is what prevents the classic fire-and-forget
coroutine that outlives its owner and leaks, a bug a manually managed thread pool is prone to:

[source,kotlin]
----
import kotlinx.coroutines.*

data class Dashboard(val book: String, val reviews: Int)

suspend fun loadDashboard(): Dashboard = coroutineScope {      // creates a scope tied to THIS suspend call
    val book = async { delay(100); "Dune" }                    // child 1
    val reviews = async { delay(150); 12 }                     // child 2
    Dashboard(book.await(), reviews.await())                   // suspends until BOTH children complete
}   // coroutineScope itself does not return until every child (even ones not awaited) has completed or been cancelled

fun main() = runBlocking {
    println(loadDashboard())
}
----

Output:

[source,text]
----
Dashboard(book=Dune, reviews=12)
----

Failure follows the same tree. If one `async` child of `loadDashboard` throws, the exception cancels its sibling, then
cancels the scope, and surfaces from `coroutineScope` itself, so the caller can catch it with an ordinary `try`/`catch`
around the call. The opt-out for independent children (`supervisorScope`, `SupervisorJob`) is explained on
xref:programming-languages/kotlin/coroutine-context-cancellation-and-exceptions.adoc[Coroutine Context, Cancellation and
Exceptions].

== The Life Cycle of a `Job`

Every coroutine is represented by a `Job`, which moves through a small set of states. The three observable properties are
`isActive`, `isCompleted` and `isCancelled`:

[mermaid]
....
stateDiagram-v2
    [*] --> New: start = LAZY
    [*] --> Active: launch or async
    New --> Active: start, join or await
    Active --> Completing: body finished, children still running
    Completing --> Completed: all children finished
    Active --> Cancelling: cancel or failure
    Completing --> Cancelling: cancel or failure
    Cancelling --> Cancelled: cleanup and children finished
    Completed --> [*]
    Cancelled --> [*]
....

A parent in the *Completing* state waits for its children; a child that fails moves its parent to *Cancelling*. `join()`
returns when the job reaches a final state, whether it completed or was cancelled, and `await()` rethrows the failure for
a cancelled `Deferred`.

== Common Pitfalls

* *Blocking inside a coroutine.* `Thread.sleep`, blocking I/O or a long CPU loop on a dispatcher thread starves the other
  coroutines that share it. Use `delay` and suspending APIs, or move blocking work to `Dispatchers.IO` with `withContext`.
* *`runBlocking` inside a coroutine.* It blocks a dispatcher thread and can deadlock; call the suspend function directly.
* *A forgotten `await()`.* An `async` whose result is never awaited still runs, and its exception is only observed when
  awaited or when it cancels the parent: do not use `async` for fire-and-forget; use `launch`.
* *Catching `CancellationException`.* A `catch (e: Exception)` around a suspend call swallows cancellation and the
  coroutine keeps running; rethrow it, as described on the next page.
* *Leaking a scope.* A scope you create must be cancelled by its owner; a `+CoroutineScope(...)+` that is never cancelled is
  `GlobalScope` in disguise.
* *Shared mutable state.* Coroutines on a multi-threaded dispatcher run in parallel: protect shared state with a `Mutex`,
  an atomic type or confinement to one coroutine, as for threads.
