include::partial$ai-disclaimer.adoc[]

Where a `suspend` function produces exactly one value asynchronously, `Flow<T>` produces *zero or more* values over time
-- Kotlin's coroutine-based answer to a reactive stream (comparable in spirit to Project Reactor's `Flux`, but built
entirely on `suspend` functions rather than a separate reactive-streams runtime). This page covers cold flows and what
"cold" means for execution, the builders and the most useful operators, error handling and completion, the context in
which a flow runs, hot flows (`StateFlow` and `SharedFlow`), and buffering and conflation. The examples use the lending
library of this section (`Book`, `Member`, `Loan`) and the `kotlinx-coroutines-core` library.

== Cold Flow Basics

A `Flow` is *cold*: its producing code does not run at all until something actually *collects* it, and it runs again, from
scratch, for every new collector:

[source,kotlin]
----
import kotlinx.coroutines.*
import kotlinx.coroutines.flow.*

fun numbers(): Flow<Int> = flow {          // the flow { } builder: nothing runs yet
    println("starting to emit")
    for (i in 1..3) {
        delay(100)
        emit(i)                            // suspends until the collector is ready for the next value
    }
}

fun main() = runBlocking {
    val stream = numbers()                 // still nothing has run
    println("about to collect")
    stream.collect { value -> println("got $value") }        // NOW "starting to emit" prints, then values arrive
    println("collecting again")
    stream.collect { value -> println("again $value") }      // the producer block runs again, from the start
}
----

Output:

[source,text]
----
about to collect
starting to emit
got 1
got 2
got 3
collecting again
starting to emit
again 1
again 2
again 3
----

This is the direct analogue of `Sequence`&#39;s laziness
(xref:programming-languages/kotlin/collections-and-sequences.adoc[Collections and Sequences]) applied to values that
arrive over time rather than all at once. A flow is *sequential*: the producer and the collector run in the same
coroutine, and `emit` returns only when the collector has handled the value, which is why a slow collector slows the
producer down.

== Flow Builders and Common Operators

Besides `+flow { }+`, `flowOf(1, 2, 3)` and `(1..3).asFlow()` build a `Flow` from fixed values or an existing collection or
range; `callbackFlow` adapts a callback-based API, and `channelFlow` lets several coroutines emit. Intermediate operators
like `map` and `filter` mirror their `Sequence` and collection counterparts, and are themselves suspending-aware: the
lambda may call suspend functions. Operators never run anything: they return a new `Flow` that wraps the upstream. Only a
*terminal* operator starts the pipeline: `collect`, `toList`, `toSet`, `first`, `single`, `reduce`, `fold`, `count` or
`launchIn(scope)`.

[source,kotlin]
----
import kotlinx.coroutines.*
import kotlinx.coroutines.flow.*

fun main() = runBlocking {
    println((1..6).asFlow().filter { it % 2 == 0 }.map { it * it }.toList())      // [4, 16, 36]

    println((1..5).asFlow().take(2).toList())                                      // [1, 2]: cancels upstream after 2
    println((1..4).asFlow().scan(0) { acc, v -> acc + v }.toList())                // [0, 1, 3, 6, 10]
    println((1..3).asFlow().fold(0) { acc, v -> acc + v })                         // 6
    println((1..2).asFlow().transform { emit("start $it"); emit("end $it") }.toList())

    println(flowOf("Dune", "Emma").zip(flowOf(1, 2, 3)) { title, n -> "$n:$title" }.toList())   // [1:Dune, 2:Emma]
    println(flowOf(1, 2).flatMapConcat { n -> flowOf("$n a", "$n b") }.toList())   // [1 a, 1 b, 2 a, 2 b]

    flowOf("Dune", "Emma", "Walden")
        .onEach { println("processing $it") }
        .filter { it.length > 4 }
        .collect { println("long title: $it") }
}
----

Output:

[source,text]
----
[4, 16, 36]
[1, 2]
[0, 1, 3, 6, 10]
6
[start 1, end 1, start 2, end 2]
[1:Dune, 2:Emma]
[1 a, 1 b, 2 a, 2 b]
processing Dune
processing Emma
processing Walden
long title: Walden
----

The whole pipeline, with intermediate operators wrapping the source and the terminal operator pulling values through:

Other operators worth knowing: `debounce` (waits for a pause in the stream, as for search-as-you-type), `distinctUntilChanged`,
`combine` (the latest value from each of several flows), `flatMapLatest` and `flatMapMerge` (for flows of flows; check
the API reference for their opt-in status), `runningReduce` and `retry`. The set is smaller than RxJava's by design; custom operators are plain extension functions built on `+flow { }+`.

== Errors and Completion

Exceptions in the producer or in an operator propagate to the collector. `catch` handles *upstream* exceptions only:
it catches what happens before it in the chain and lets the flow continue with a fallback, but it does *not* catch an
exception thrown by the collector's own lambda (that is downstream). `onCompletion` runs when the flow ends, normally or
exceptionally, like a `finally` block:

[source,kotlin]
----
import kotlinx.coroutines.*
import kotlinx.coroutines.flow.*

fun main() = runBlocking {
    flow {
        emit(1)
        emit(2)
        throw IllegalStateException("source failed")
    }
        .catch { e -> println("caught: ${e.message}"); emit(-1) }     // upstream failure: recover with a fallback
        .onCompletion { cause -> println("completed, cause = $cause") }
        .collect { println("value $it") }

    try {
        flowOf(1, 2, 3)
            .catch { println("not reached for downstream failures") }
            .collect { if (it == 2) throw IllegalArgumentException("collector failed") }
    } catch (e: IllegalArgumentException) {
        println("downstream failure surfaced: ${e.message}")
    }
}
----

Output:

[source,text]
----
value 1
value 2
caught: source failed
value -1
completed, cause = null
downstream failure surfaced: collector failed
----

This property is called *exception transparency*: a flow must not catch exceptions from its collector, and `emit` inside a
`try`/`catch` in the producer is not allowed to hide them. Cancellation works as for any coroutine: cancelling the
collecting coroutine cancels the flow, and a `take(n)` terminates the upstream with an internal cancellation.

== The Context of a Flow: `flowOn`

A flow is collected in the context of the collecting coroutine, and the *context preservation* rule forbids emitting from a
different context with `withContext` inside `+flow { }+`. To run the producer on another dispatcher, use `flowOn`, which
changes the context of the operators *upstream* of it, and introduces a buffer between the two parts:

[source,kotlin]
----
import kotlinx.coroutines.*
import kotlinx.coroutines.flow.*

fun main() = runBlocking {
    flow {
        emit(Thread.currentThread().name.startsWith("DefaultDispatcher"))   // producer thread
    }
        .flowOn(Dispatchers.Default)                    // everything above runs on Default
        .collect { println("producer ran on Default: $it") }
}
----

Output:

[source,text]
----
producer ran on Default: true
----

== `StateFlow` vs. `SharedFlow`

Both are *hot* flows -- unlike `+flow { }+`, they run independently of whether anything is collecting, and multiple collectors
share the same running producer instead of each triggering it from scratch. A collector of a hot flow never completes
by itself: it collects until cancelled.

[cols="1,2"]
|===
|Type |Use

|`StateFlow<T>`
|always holds a *current value* (`value`), conflates rapid updates (a slow collector only ever sees the *latest* value, not
every intermediate one), skips repeats of an equal value, and always has at least one value -- the natural fit for UI
state (the `ViewModel` pattern on xref:programming-languages/kotlin/kotlin-for-android.adoc[Kotlin for Android] uses it
extensively).

|`SharedFlow<T>`
|a more general broadcast stream with configurable replay and no requirement to hold a "current" value -- the right fit
for one-off *events* (a snackbar message, a navigation command) that should not be replayed as "state" the way
`StateFlow` would.
|===

[mermaid]
....
flowchart TD
    subgraph Cold["cold Flow: one producer run per collector"]
        C1["collector 1"] --> P1["producer run 1"]
        C2["collector 2"] --> P2["producer run 2"]
    end
    subgraph Hot["hot StateFlow or SharedFlow: one shared producer"]
        PS["MutableStateFlow or MutableSharedFlow"] --> H1["collector 1"]
        PS --> H2["collector 2"]
        U["emit or value assignment"] --> PS
    end
....

[source,kotlin]
----
import kotlinx.coroutines.*
import kotlinx.coroutines.flow.*

class ShelfViewModel {
    private val _count = MutableStateFlow(0)
    val count: StateFlow<Int> = _count.asStateFlow()     // read-only view exposed publicly

    fun add() {
        _count.update { it + 1 }                          // atomic read-modify-write; every collector sees the new value
    }
}

fun main() = runBlocking {
    val vm = ShelfViewModel()
    val job = launch { vm.count.collect { println("count = $it") } }

    delay(50); vm.add()
    delay(50); vm.add()
    delay(50); vm.add(); vm.add()          // two updates before the collector runs: it only sees the latest, 4
    delay(50)
    println("current value: ${vm.count.value}")
    job.cancel()
}
----

Output:

[source,text]
----
count = 0
count = 1
count = 2
count = 4
current value: 4
----

A `StateFlow` has a current value from the moment it is created, so a new collector immediately receives it. Prefer
`+update { }+` over `pass:c[value = value + 1]`, which is not atomic when several coroutines write. A cold flow can be turned into a
hot one with `stateIn` and `shareIn`, usually with `SharingStarted.WhileSubscribed(5_000)` so that the upstream stops when
nobody is listening.

`SharedFlow` is configured by `replay` (how many past values a new subscriber receives), `extraBufferCapacity` and
`onBufferOverflow` (what to do when a subscriber is slow: suspend, drop oldest or drop latest). With the defaults,
`emit` suspends until every current subscriber has received the value, and a value emitted when nobody is subscribed is lost:

[source,kotlin]
----
import kotlinx.coroutines.*
import kotlinx.coroutines.flow.*

fun main() = runBlocking {
    val events = MutableSharedFlow<String>()                // no replay
    val job = launch { events.collect { println("subscriber got $it") } }
    yield()                                                  // let the subscriber start collecting
    events.emit("borrowed Dune")
    events.emit("returned Dune")
    job.cancel()

    val withReplay = MutableSharedFlow<String>(replay = 1)
    withReplay.tryEmit("welcome")                            // no subscriber yet, but one value is kept for replay
    val late = launch { withReplay.collect { println("late subscriber got $it") } }
    yield()
    late.cancel()
}
----

Output:

[source,text]
----
subscriber got borrowed Dune
subscriber got returned Dune
late subscriber got welcome
----

== Buffering

By default, a slow collector makes the upstream producer *suspend* until it catches up, because `emit` and the collector's
lambda run in sequence. `buffer()` decouples them with an internal channel, letting the producer run ahead; `conflate()`
goes further and drops intermediate values entirely, keeping only the latest when the collector is behind -- the same
conflation `StateFlow` applies automatically; and `collectLatest` cancels the collector's work for the previous value as
soon as a new one arrives:

[source,kotlin]
----
import kotlinx.coroutines.*
import kotlinx.coroutines.flow.*

fun readings(): Flow<Int> = flow {
    for (i in 1..5) {
        delay(100)               // fast producer
        emit(i)
    }
}

fun main() = runBlocking {
    println("-- conflate: the slow collector skips values")
    readings().conflate().collect { v ->
        println("start $v")
        delay(350)                // slow collector
        println("end $v")
    }

    println("-- collectLatest: unfinished work is cancelled")
    readings().collectLatest { v ->
        println("start $v")
        delay(350)
        println("end $v")
    }
}
----

Output:

[source,text]
----
-- conflate: the slow collector skips values
start 1
end 1
start 4
end 4
start 5
end 5
-- collectLatest: unfinished work is cancelled
start 1
start 2
start 3
start 4
start 5
end 5
----

Use `buffer()` when every value matters but producing and consuming can overlap (for example reading a file while
writing to a database); `conflate()` or `collectLatest` when only the newest value matters (a UI showing a sensor
reading); and the default when back-pressure is the desired behaviour.

== Choosing Between Flow, Sequence and suspend Functions

* One value, asynchronously: a `suspend` function.
* Many values, computed lazily and synchronously: a `Sequence`.
* Many values arriving over time, possibly suspending to compute each: a cold `Flow`.
* State that several consumers observe, with a current value: `StateFlow`; events broadcast to the current subscribers:
  `SharedFlow`.
