Kotlin's surface syntax will feel familiar coming from Java, with a handful of deliberate simplifications:
optional semicolons, a package declaration that need not match the directory layout, and a documentation-comment
format (KDoc) built for its own tooling.

== File and Package Structure

A `.kt` file may declare **any number of top-level classes, functions, and properties**, and its package
declaration -- unlike Java's -- **does not need to match the containing directory**, though following the
convention keeps a project navigable and is what every real project does:

[source,kotlin]
----
package com.example.billing

import kotlin.math.max

const val MAX_RETRIES = 3          // top-level property, no enclosing class needed

fun retryDelay(attempt: Int): Int = // top-level function, no enclosing class needed
    max(attempt * 100, 1000)

class InvoiceService                // an ordinary top-level class
----

A file with no package declaration belongs to the *default package*. `import` works as in Java, plus two
Kotlin-specific forms: importing a top-level function directly, and aliasing on import to resolve a name clash --
`import kotlin.math.PI as MathPi`.

== Identifiers

Identifiers follow the usual rules (start with a letter or underscore, then letters/digits/underscores) with one
notable Kotlin addition: **backtick-escaped identifiers** allow any Unicode text, including spaces and reserved
words, most commonly used for descriptive test-method names:

[source,kotlin]
----
class `given an empty cart` {
    @org.junit.jupiter.api.Test
    fun `checkout should fail with an empty-cart error`() {
        // ...
    }
}
----

This is why a JUnit report for Kotlin test code so often reads like a full sentence -- the backtick-quoted method
name *is* the display name, no `@DisplayName` annotation needed.

== Comments

Kotlin has the same three C-style comment forms as Java, plus KDoc for API documentation:

[source,kotlin]
----
// a single-line comment

/* a
   multi-line comment (can nest, unlike Java's) */

/**
 * KDoc: Kotlin's documentation-comment format.
 *
 * @param name the customer's display name
 * @return a greeting string
 */
fun greet(name: String): String = "Hello, $name!"
----

KDoc is processed by https://kotlinlang.org/docs/dokka-introduction.html[Dokka] (Kotlin's Javadoc equivalent);
its tag set is a superset of Javadoc's, with Markdown allowed in the description body.

== Optional Semicolons

A statement terminator is **inferred at the end of a line** wherever the parser can tell the statement is
complete, so semicolons are almost always omitted in idiomatic Kotlin:

[source,kotlin]
----
val a = 1
val b = 2
println(a + b)          // no semicolons needed

val c = 1; val d = 2    // still legal on one line, just uncommon
----

The inference has a well-known gotcha: a line that could plausibly continue (ending in an operator, or the line
below starting with `.`, `(`, or `[`) is treated as continuing, which occasionally produces surprises with a
value expression placed right before a lambda -- covered concretely in
xref:programming-languages/kotlin/functions.adoc[Functions] and
xref:programming-languages/kotlin/lambdas-and-higher-order-functions.adoc[Lambdas and Higher-Order Functions].

== Official Coding Conventions

JetBrains publishes an official
https://kotlinlang.org/docs/coding-conventions.html[Kotlin coding conventions] document (4-space indentation, no
tabs, 120-character soft line limit, `UpperCamelCase` for types, `lowerCamelCase` for functions/properties,
`UPPER_SNAKE_CASE` for `const val` top-level/companion constants). https://ktlint.github.io/[ktlint] enforces
this convention automatically and is the de facto formatter/linter for most Kotlin projects (see
xref:programming-languages/kotlin/build-and-tooling.adoc[Build and Tooling] for wiring it into a build).

== Keywords

Kotlin has three kinds of keywords, which matters because only the first kind is truly reserved:

* *Hard keywords* are always keywords and cannot be used as identifiers without backticks: `as`, `break`, `class`,
  `continue`, `do`, `else`, `false`, `for`, `fun`, `if`, `in`, `interface`, `is`, `null`, `object`, `package`, `return`,
  `super`, `this`, `throw`, `true`, `try`, `typealias`, `typeof`, `val`, `var`, `when`, `while`.
* *Soft keywords* act as keywords only in a specific context and are ordinary identifiers elsewhere: `by`, `catch`,
  `constructor`, `delegate`, `field`, `file`, `finally`, `get`, `import`, `init`, `param`, `property`, `receiver`, `set`,
  `setparam`, `value`, `where`. A variable called `value` or `field` outside an accessor is legal.
* *Modifier keywords* appear in declarations and are identifiers elsewhere: `abstract`, `annotation`, `companion`, `const`,
  `crossinline`, `data`, `enum`, `expect`, `external`, `final`, `infix`, `inline`, `inner`, `internal`, `lateinit`,
  `noinline`, `open`, `operator`, `out`, `override`, `private`, `protected`, `public`, `reified`, `sealed`, `suspend`,
  `tailrec`, `vararg`.

The practical consequence is that a Java API with a member named `in`, `is`, `object` or `fun` is called from Kotlin by
wrapping the member name in backticks, and that adding a modifier keyword to the language does not break existing code that
used the word as a name.

== Naming and Layout in Practice

The conventions below are the ones that `ktlint` and the IDE formatter enforce, shown on a small file from the lending
library used throughout this section:

[source,kotlin]
----
package com.example.library                  // lowercase, no underscores; mirrors the directory by convention

import java.time.LocalDate

const val DEFAULT_LOAN_DAYS = 14             // const val: UPPER_SNAKE_CASE

/**
 * A copy of a [Book] lent to a [Member].
 *
 * @property title the book's title
 * @property dueDate the date the loan expires
 */
data class Loan(                              // types: UpperCamelCase; one blank line between declarations
    val title: String,                        // properties and parameters: lowerCamelCase
    val dueDate: LocalDate,
) {
    /** Returns the number of days between [today] and the due date, negative when overdue. */
    fun daysLeft(today: LocalDate): Long =    // functions: lowerCamelCase, a verb or verb phrase
        today.until(dueDate, java.time.temporal.ChronoUnit.DAYS)

    private val isOpen get() = true           // Boolean properties read as questions: isOpen, hasLoans
}

fun main() {
    val loan = Loan("Dune", LocalDate.of(2026, 12, 1))
    println(loan.daysLeft(LocalDate.of(2026, 11, 10)))     // 21
}
----

Output:

[source,text]
----
21
----

Further points from the conventions: a file containing a single class is named after it (`Loan.kt`), a file with several
declarations gets a descriptive `UpperCamelCase` name (`LoanExtensions.kt`); enum constants are `UPPER_SNAKE_CASE` or
`UpperCamelCase`; a backing property is named with a leading underscore (`+_state+` with a public `state`); a trailing comma
is recommended in multi-line parameter and argument lists, which keeps diffs small; and a *declaration-site* name should
read well at the call site, because Kotlin supports named arguments (`lend(title = "Dune", days = 7)`).

How a `.kt` file maps to the JVM, which explains why file names matter for Java callers:

== KDoc

KDoc comments sit before the declaration they describe and use Markdown, with `[Name]` as a link to another symbol and the
block tags `@param`, `@property`, `@return`, `@throws`, `@see`, `@sample` and `@since`. For a primary constructor, document
each parameter with `@param` and each constructor property with `@property` in the class's comment (as above). Dokka renders
KDoc to HTML or Javadoc-style output, and the IDE shows it on hover with Ctrl+Q (F1 on macOS).
