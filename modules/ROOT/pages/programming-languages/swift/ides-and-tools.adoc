== What Ships With a Toolchain

An IDE is a front end; the *toolchain* underneath does the work, and the same toolchain is behind every editor. A toolchain installed
with Xcode (or with Swiftly, or the packages from swift.org) provides the compiler, the package manager, the language server, the debugger, the
formatter and the documentation compiler:

[source,text]
----
$ swift --version
Apple Swift version 6.4.2 (swiftlang-6.4.2.1.9 clang-2100.4.1.1)
Target: arm64-apple-macosx27.2.0
$ xcrun --find sourcekit-lsp
.../XcodeDefault.xctoolchain/usr/bin/sourcekit-lsp
$ xcrun --find swift-format
.../XcodeDefault.xctoolchain/usr/bin/swift-format
$ xcrun --find docc
.../XcodeDefault.xctoolchain/usr/bin/docc
----

(The version printed is that of the machine the page was checked on; the Swift 6 language mode is available from Swift 6.0 onwards.)
`xcrun` is the macOS way to locate a tool in the active developer directory; on Linux and Windows the same binaries are in the toolchain's
`bin` directory and on `PATH`.

== Choosing an Environment

[cols="2,3,3",options="header"]
|===
| You are building | Reasonable choice | Why
| an iOS, macOS, watchOS or visionOS app | Xcode | simulators, Interface Builder previews, Instruments, signing and the App Store workflow only exist there
| a cross-platform library or a command-line tool | VS Code with the Swift extension, or any editor with an LSP client | works on macOS, Linux and Windows, built on the same SourceKit-LSP that Xcode uses
| server-side Swift | VS Code or Xcode, plus containers for Linux builds | the production target is Linux, so build and test there too
| scripts and experiments | `swift file.swift` and the REPL | no project needed
|===

Whatever the editor, the *project* is a Swift package, so the build, the tests and CI commands are the same for everyone on the team:
`swift build`, `swift test`, `swift format lint --recursive Sources Tests`. See
xref:programming-languages/swift/swift-package-manager.adoc[Swift Package Manager] and
xref:programming-languages/swift/build-and-tooling.adoc[Build and Tooling] for the details.

=== Pitfalls

* Two toolchains on one machine (the Xcode one and one from swift.org or Swiftly) can make `swift --version` in the terminal differ from the
  version Xcode builds with; check which is active before diagnosing a "works in Xcode" mismatch.
* SourceKit-LSP indexes a package after its first build; a package that has never built shows weak completion and navigation.
* Keep formatter and linter versions pinned (in a CI image or a lock file) so that formatting does not change between machines.
