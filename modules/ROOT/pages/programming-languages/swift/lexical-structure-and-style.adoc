== Whitespace and Comments

Whitespace (spaces, tabs, newlines) separates tokens but is otherwise not significant -- Swift has no
significant indentation. A newline *does* end a statement when no semicolon is present (see <<Semicolons>>).

[source,swift]
----
// A single-line comment, to the end of the line.

/* A block comment.
   /* Block comments nest, unlike in C or Java. */
   That nesting is what lets you comment out a region that already contains a block comment. */

/// A single-line documentation comment, in a lightweight Markdown dialect.
/// - Parameter name: The name to greet.
/// - Returns: A greeting string.
func greeting(for name: String) -> String {
    "Hello, \(name)!"
}

/**
 * A multi-line documentation comment. Either `///` repeated per line or a `/** */` block
 * is recognised by DocC and by Quick Help in Xcode; this section uses `///` throughout.
 */
----

DocC (via `swift package generate-documentation` or Xcode's *Build Documentation*) renders `pass:c[///]` and `pass:c[/** */]`
comments -- including their Markdown, callouts (`- Note:`, `- Warning:`) and symbol links (`` ``Type/member`` ``)
-- into browsable reference documentation.

== Identifiers and Keywords

An identifier starts with a letter, `+_+`, or certain Unicode categories (including emoji), and continues with
those plus digits and combining marks. Swift is *case-sensitive*.

Swift has no separate "contextual keyword" list exposed to you the way some languages do; instead, *any* keyword
can be used as an identifier by escaping it with backticks:

[source,swift]
----
let `class` = "still usable as a name"
let `for` = 10
func `return`() -> Int { 42 }
----

This matters most for interop -- a C or Objective-C API might use a name that happens to be a Swift keyword --
and is rarely needed in ordinary code; prefer renaming over backticks where you have the choice.

Swift's reserved keywords fall into a few groups:

[cols="1,3",options="header"]
|===
| Category | Examples

| Declarations | `associatedtype`, `class`, `deinit`, `enum`, `extension`, `func`, `import`, `init`, `let`, `protocol`, `struct`, `subscript`, `typealias`, `var`
| Statements | `break`, `case`, `continue`, `default`, `defer`, `do`, `else`, `fallthrough`, `for`, `guard`, `if`, `in`, `repeat`, `return`, `switch`, `where`, `while`
| Expressions and types | `Any`, `as`, `catch`, `false`, `is`, `nil`, `rethrows`, `self`, `Self`, `super`, `throw`, `throws`, `true`, `try`
| Concurrency (Swift 5.5+) | `actor`, `async`, `await`
| Pattern matching | `+_+`
|===

A large second set are keywords only in specific positions (declaration modifiers, argument-label position,
attributes) and remain valid identifiers everywhere else -- `get`, `set`, `willSet`, `didSet`, `some`, `any`,
`nonisolated`, `sending`, `override`, `mutating`, `final`, `lazy`, `weak`, `unowned`, and more. This is why, for
example, a parameter can be named `set` without conflict.

== Literals

[source,swift]
----
// Integer literals: decimal, binary, octal, hexadecimal; `_` as a free digit separator.
let decimal   = 17
let readable  = 1_000_000
let binary    = 0b1010_0101
let octal     = 0o21
let hex       = 0x11

// Floating-point literals: decimal and hexadecimal (with a required binary exponent `p`).
let pi        = 3.14159
let expo      = 1.25e4          // 12500.0
let hexFloat  = 0x1p2           // 4.0 (1 * 2^2)

// String literals.
let plain     = "escapes: \n \t \\ \"; interpolation: \(1 + 1)"
let multiline = """
    Preserves newlines.
    Leading whitespace up to the closing quotes' indentation is stripped.
    """
let raw       = #"No \escapes or \(interpolation) happen in here."#
let rawInterp = #"Unless you double the pound: \#(1 + 1)."#

// Regular expression literals (Swift 5.7+).
let regex = /[a-z]+\d+/
let anchored = #/^\d{3}-\d{4}$/#   // extended delimiters allow `/` and whitespace inside the pattern

// Boolean and nil.
let flag: Bool = true
let absent: Int? = nil
----

A regex literal is checked for syntax at *compile time* and has static type `Regex<Output>`, inferred from its
capture groups -- see xref:programming-languages/swift/regular-expressions.adoc[Regular Expressions].

== Operators

Operators are built from a fixed set of ASCII and Unicode "operator characters"
(`pass:c[ / = - + ! * % < > & | ^ ~ ? ]` plus a range of Unicode math/symbol code points); an operator token is a
maximal run of such characters, tokenised the same way regardless of which operator it turns out to be.
Whitespace around an operator controls whether it is parsed as *infix*, *prefix* or *postfix*:

[source,swift]
----
let a = -1        // prefix `-`: no space after it, so it binds to `1`
let b = 3 - 1      // infix `-`: space on both sides
// let c = 3 -1    // error: ambiguous -- looks like `3` followed by a prefix `-1`
----

Swift lets you declare entirely new operators and custom precedence groups:

[source,swift]
----
infix operator **: MultiplicationPrecedence

func ** (base: Double, exponent: Double) -> Double {
    pow(base, exponent)
}

2.0 ** 10.0   // 1024.0
----

== Semicolons

[source,swift]
----
let x = 1
let y = 2   // no semicolon needed -- the newline ends the statement

let m = 1; let n = 2   // a semicolon is required only to put two statements on one line
----

A trailing semicolon after the last statement on a line is legal but never required, and is omitted throughout
this section.

== The API Design Guidelines

Swift's standard library and virtually all published packages follow the *API Design Guidelines*, referenced
directly from the language's own documentation. The overriding goal is *clarity at the point of use* -- a call
site should read as a grammatical phrase, even at the cost of a longer declaration:

[source,swift]
----
// Clear at the call site, even though the declaration repeats information:
extension Array {
    func removingDuplicates() -> [Element] where Element: Hashable { /* ... */ Array(Set(self)) }
}
let unique = [1, 1, 2, 3].removingDuplicates()

// Argument labels form part of that phrase, distinct from the internal parameter name:
func move(_ piece: Piece, to destination: Square) { /* first arg unlabeled, second reads "to destination" */ }
move(knight, to: .e4)
----

Key rules the guidelines spell out:

* *Omit needless words* -- name a method `remove(at:)`, not `removeElement(atIndex:)`, when the type already
  makes the meaning obvious.
* *Argument labels* -- the first argument is often unlabeled when the base reads naturally with it
  (`x.distance(to: y)`), and every other argument is normally labeled; use `+_+` to suppress a label deliberately.
* *Mutating/non-mutating pairs* use `-ed`/`-ing` for the non-mutating, value-returning form and the bare verb for
  the mutating one: `array.sort()` mutates in place, `array.sorted()` returns a new array;
  `set.formUnion(other)` mutates, `set.union(other)` returns a new set.
* *Fluent usage* -- read a call site as English where possible: `x.insert(y, at: z)`, not
  `x.insert(y, z)`.
* Types and protocols are `UpperCamelCase`; everything else (functions, methods, properties, cases, variables) is
  `lowerCamelCase`.

== `MARK` and `TODO`

[source,swift]
----
// MARK: - Networking
// MARK: Equatable
// TODO: Replace with async/await once the minimum deployment target allows it.
// FIXME: This retries indefinitely on a 429 response.
----

`// MARK: -` (with a leading dash) inserts a separator line in Xcode's jump bar/minimap in addition to a
section label; plain `// MARK:` adds a label without the separator. `TODO`/`FIXME` are recognised the same way
and surfaced in Xcode's issue navigator, but carry no compiler meaning.

== `swift-format`

`swift-format` (part of the swiftlang project, bundled with recent toolchains as `swift format`) is the
canonical formatter and linter, enforcing most of the layout conventions implied above -- two-space
indentation, trailing-comma rules, brace placement -- as well as a subset of the API Design Guidelines as lint
rules:

[source,bash]
----
swift format lint --recursive Sources/      # report style violations
swift format format --recursive --in-place Sources/   # rewrite files in place
----

A `.swift-format` JSON file at the repository root configures indentation width, line length and which rules are
enabled, and is picked up automatically by both the CLI and Xcode's built-in formatting support.

== Worked Example: A Small API That Follows the Guidelines

Style in Swift is anchored by the *API Design Guidelines*, whose central idea is *clarity at the point of use*: a call should read
close to an English phrase, and the declaration should carry only the words the reader needs. The listing below is a
small, compile-checked library API; the comments mark the guideline each choice follows.

[source,swift]
----
// A small API written to the Swift API Design Guidelines.

/// A book that can be lent to a reader.
///
/// - Note: Titles are compared case-insensitively by ``Shelf/contains(title:)``.
struct Book {
    /// The title as printed on the cover.
    let title: String
    /// The number of pages, always positive.
    let pageCount: Int
    let isLent: Bool

    // MARK: - Lending

    /// Returns a copy of the book marked as lent.
    ///
    /// - Returns: A new `Book`; the receiver is unchanged.
    func lent() -> Book { Book(title: title, pageCount: pageCount, isLent: true) }

    /// Returns the number of days the book may be kept, given the reader's tier.
    /// - Parameter tier: A tier from 1 (guest) to 3 (staff).
    func loanDays(forTier tier: Int) -> Int { tier * 7 }
}

struct Shelf {
    private(set) var books: [Book] = []

    // Verb phrases for side effects, noun phrases for queries.
    mutating func add(_ book: Book) { books.append(book) }
    func contains(title: String) -> Bool {
        books.contains { $0.title.lowercased() == title.lowercased() }
    }

    // A mutating method and its non-mutating twin: ed/ing suffix for the value-returning form.
    mutating func sort() { books.sort { $0.title < $1.title } }
    func sorted() -> [Book] { books.sorted { $0.title < $1.title } }
}

// Booleans read as assertions; labels make the call site read as a phrase.
var shelf = Shelf()
shelf.add(Book(title: "Kim", pageCount: 336, isLent: false))
shelf.add(Book(title: "Emma", pageCount: 474, isLent: false).lent())
print(shelf.contains(title: "EMMA"), shelf.sorted().map(\.title), shelf.books.map(\.isLent))
print(Book(title: "Dune", pageCount: 412, isLent: false).loanDays(forTier: 2))

// Identifiers may use Unicode, and backticks allow keywords as names.
let πDay = "March 14"
let `class` = "Fiction"
print(πDay, `class`)

// Semicolons are optional; they only separate statements on one line.
let a = 1; let b = 2
print(a + b)

// Nested block comments let you disable code that already has comments.
/* disabled: /* inner */ print("not printed") */
----

[source,text]
----
true ["Emma", "Kim"] [false, true]
14
March 14 Fiction
3
----

[cols="3,3,3",options="header"]
|===
| Instead of | Write | Why
| `book.isLentOut()` as a method returning `Bool` | `book.isLent` as a property | Boolean properties read as assertions
| `shelf.addBook(book)` | `shelf.add(book)` | the type already says what is added
| `shelf.sort()` and `shelf.getSortedBooks()` | `sort()` mutates, `sorted()` returns a copy | the `-ed`/`-ing` suffix marks the non-mutating twin
| `func loanDays(tier: Int)` | `func loanDays(forTier tier: Int)` | the label makes the call read as a phrase
| a keyword such as `class` or `default` as a name | pick another name; wrap it in backticks only if unavoidable | keywords as names are legal but awkward
|===

Reading the example, in order:

* *Types are `UpperCamelCase`, everything else `lowerCamelCase`.* Acronyms that are common in the language (`URL`, `ID`) are written
  in capitals when they are not at the start of a lowercase name (`userID`) and in lowercase when they are (`urlString`).
* *Documentation comments are Markdown.* `///` lines become the Quick Help and DocC text; `- Parameter` and `- Returns` are
  callouts, and a symbol path wrapped in double backticks creates a link to another symbol. The first sentence is a summary fragment: a
  *noun phrase* for properties and a *verb phrase* for methods.
* *Name by role, not by type.* `books` and `title` say what the value is for; `bookArray` or `titleString` repeat the type.
* *`// MARK: -` sections* organise a long file in Xcode's jump bar and the outline of other editors.
* *Unicode and backticks.* `πDay` is a valid identifier and wrapping a keyword in backticks allows it as a name; both are legal, and both
  are rarely a good idea.
* *Semicolons only separate statements on one line,* and nested block comments let you disable code that already contains comments.

=== Pitfalls

* Omitting labels (`+_+`) everywhere trades readability for brevity; keep the first label when the argument does not complete a phrase
  (`move(from:to:)`).
* Abbreviations that are not universally known (`btn`, `cnt`) make code harder to search and to read aloud.
* Run `swift format` (see below) in CI so that discussions about whitespace stay out of code review.
* Documentation comments on `private` members are optional, but every `public` declaration should have a summary, even a short one.
