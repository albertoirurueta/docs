= Functional Programming
:description: Functional programming in Swift -- immutability with let and value types, pure functions, first-class and higher-order functions, function composition and custom composition operators, currying and partial application, recursion, map/filter/reduce pipelines and lazy, and Optional/Result as containers with map/flatMap.
:keywords: Swift, functional programming, immutability, pure function, higher-order function, function composition, currying, recursion, map, filter, reduce, lazy, flatMap

include::partial$ai-disclaimer.adoc[]

Swift is not a purely functional language, but its value types, first-class functions, and rich set of
higher-order algorithms make a functional style -- immutable data, pure functions, composition over mutation --
a natural fit alongside its object-oriented and protocol-oriented features.

== Immutability and Pure Functions

[source,swift]
----
struct Point { let x, y: Double }             // an immutable value type: every mutation produces a new Point

func translated(_ point: Point, dx: Double, dy: Double) -> Point {
    Point(x: point.x + dx, y: point.y + dy)    // pure: same inputs always produce the same output, no side effects
}

let origin = Point(x: 0, y: 0)
let moved = translated(origin, dx: 3, dy: 4)   // origin is untouched -- moved is a new value
----

Declaring with `let` and favoring value types (structs, enums -- see
xref:programming-languages/swift/structures-and-classes.adoc[Structures and Classes]) over classes makes
"changing" a value mean producing a new one rather than mutating shared state, which is what makes a function
like `+translated(_:dx:dy:)+` *pure*: it reads only its arguments, has no observable side effect, and always
returns the same result for the same inputs -- callers can reason about it, test it, and run it concurrently
without synchronization, unlike a method that mutates a shared class instance.

== First-Class and Higher-Order Functions

[source,swift]
----
func square(_ x: Int) -> Int { x * x }
let operation: (Int) -> Int = square           // a function used as an ordinary value

func apply(_ f: (Int) -> Int, to values: [Int]) -> [Int] {
    values.map(f)                               // apply is itself higher-order: it takes a function as a parameter
}
apply(square, to: [1, 2, 3])                    // [1, 4, 9]

func adder(_ amount: Int) -> (Int) -> Int {     // returns a function -- also makes apply's caller higher-order
    { value in value + amount }
}
let addFive = adder(5)
addFive(10)                                     // 15
----

A function that can be stored in a variable, passed as an argument, or returned from another function is
*first-class* -- true of every Swift function and closure. A *higher-order* function either takes a function as
a parameter (`+apply(_:to:)+`) or returns one (`+adder(_:)+`); see
xref:programming-languages/swift/closures.adoc[Closures] for the closure-expression syntax (`+{ value in ... }+`)
used to write one inline.

== Composition, Currying and Partial Application

[source,swift]
----
infix operator >>>: AdditionPrecedence
func >>> <A, B, C>(_ f: @escaping (A) -> B, _ g: @escaping (B) -> C) -> (A) -> C {
    { a in g(f(a)) }                            // custom composition operator: f then g
}

let double = { (x: Int) in x * 2 }
let increment = { (x: Int) in x + 1 }
let doubleThenIncrement = double >>> increment
doubleThenIncrement(5)                          // 11 -- (5 * 2) + 1

func curriedAdd(_ a: Int) -> (Int) -> Int {     // a curried function: takes its arguments one at a time
    { b in a + b }
}
let addTen = curriedAdd(10)                     // partial application: fixing the first argument
addTen(32)                                       // 42
----

Function *composition* builds a new function by feeding one function's output into another's input; the custom
`>>>` operator above is one common convention for writing that left-to-right, building on the operator-overloading
tools in xref:programming-languages/swift/advanced-operators.adoc[Advanced Operators]. *Currying* is writing a
multi-argument function as a chain of single-argument functions (`+curriedAdd(_:)+` returns a function rather than
taking two parameters directly), which makes *partial application* -- fixing some arguments now and supplying
the rest later, as `addTen` does -- fall out naturally, without any dedicated language feature for it.

== Recursion

[source,swift]
----
func factorial(_ n: Int) -> Int {
    n <= 1 ? 1 : n * factorial(n - 1)           // no built-in tail-call optimization guarantee -- deep recursion
}                                                 // can still overflow the call stack for large n

indirect enum Expr {
    case value(Int)
    case add(Expr, Expr)
}
func evaluate(_ expr: Expr) -> Int {
    switch expr {
    case .value(let v): v
    case .add(let a, let b): evaluate(a) + evaluate(b)   // recursive descent over a recursive (indirect) enum
    }
}
----

Recursion -- a function calling itself, directly or through an `indirect` enum's recursive case (see
xref:programming-languages/swift/enumerations.adoc[Enumerations]) -- is the functional-style alternative to a
loop with mutable state, and reads naturally over tree-shaped data. Swift makes no guarantee of tail-call
optimization, so an iterative loop remains the right choice when recursion depth could be large or unbounded.

== `map`/`filter`/`reduce` Pipelines and `lazy`

[source,swift]
----
let numbers = Array(1...1_000_000)

let result = numbers
    .lazy                                        // defers every step below to run element-by-element, on demand
    .filter { $0.isMultiple(of: 3) }
    .map { $0 * $0 }
    .prefix(5)                                    // only the first 5 matches are ever actually computed
Array(result)                                     // [9, 36, 81, 144, 225]

let total = numbers.reduce(0, +)                  // sums the whole (non-lazy) array eagerly
----

Chaining `map`/`filter`/`reduce` (covered per-collection in
xref:programming-languages/swift/collections.adoc[Collections]) expresses a data transformation as a pipeline of
independent steps rather than a hand-written loop with an accumulator. Each step in an eager chain allocates a
full intermediate array, though -- `.lazy` switches the same chain to a `LazySequence`/`LazyCollection` that
defers every operation until an element is actually demanded, which matters when only a prefix of a large or
infinite sequence is ever consumed, as `.prefix(5)` does above.

== `Optional` and `Result` as Containers

[source,swift]
----
func parseInt(_ text: String) -> Int? { Int(text) }
func reciprocal(_ n: Int) -> Double? { n == 0 ? nil : 1.0 / Double(n) }

let value = parseInt("8")
    .map { $0 * 2 }                               // Optional.map: transform the value if present, else stay nil
    .flatMap(reciprocal)                           // flatMap: chain another Optional-returning step, no double-wrapping

func fetchUser(id: Int) -> Result<String, Error> {
    id > 0 ? .success("user\(id)") : .failure(URLError(.badURL))
}
let greeting = fetchUser(id: 7)
    .map { "Hello, \($0)" }                        // Result.map: transform .success, pass .failure through untouched
    .flatMap { name in
        name.count > 3 ? .success(name) : .failure(URLError(.badURL))
    }
----

`Optional` and `Result` (see xref:programming-languages/swift/optionals.adoc[Optionals] and
xref:programming-languages/swift/error-handling.adoc[Error Handling]) are both, from a functional standpoint,
*containers* that may or may not hold a value -- `Optional` unconditionally, `Result` alongside a specific
failure reason. Their `map` transforms a contained value without unwrapping it by hand; their `flatMap` chains
another container-returning step without producing a nested `Optional<Optional<T>>` or
`+Result<Result<...>, ...>+`, the same "flatten as you go" shape `Sequence.flatMap` provides for collections. Both
types compose naturally with protocols and actors -- an `async` function returning `Result`, or a `Sendable`
value type flowing through an actor boundary -- rather than being at odds with Swift's other paradigms; see
xref:programming-languages/swift/protocols.adoc[Protocols] and
xref:programming-languages/swift/actors-isolation-and-sendable.adoc[Actors, Isolation and Sendable].

== A Pipeline Over the Bookshelf

Functional style in Swift is not an all-or-nothing choice: it is a habit of describing *what* result you want as a chain
of small pure functions over values, instead of mutating variables inside a loop. The bookshelf below shows the usual
building blocks working on one array of immutable `Book` values.

[source,swift]
----
struct Book {
    let title: String
    let author: String
    let pages: Int
    let year: Int
}

let books = [
    Book(title: "Dune", author: "Herbert", pages: 412, year: 1965),
    Book(title: "Children of Dune", author: "Herbert", pages: 444, year: 1976),
    Book(title: "Emma", author: "Austen", pages: 474, year: 1815),
    Book(title: "Persuasion", author: "Austen", pages: 249, year: 1817),
    Book(title: "Kim", author: "Kipling", pages: 336, year: 1901),
]

// A pipeline: filter -> map -> reduce, each step a pure function over values.
let longTitles = books.filter { $0.pages > 400 }.map(\.title)
print(longTitles)
let totalPages = books.reduce(0) { $0 + $1.pages }
print(totalPages)

// Group, then summarise each group.
let byAuthor = Dictionary(grouping: books, by: \.author)
for (author, group) in byAuthor.sorted(by: { $0.key < $1.key }) {
    print(author, group.count, group.map(\.pages).reduce(0, +))
}

// Laziness: the pipeline below does no work until the first element is requested.
var inspected = 0
let firstLong = books.lazy
    .filter { inspected += 1; return $0.pages > 400 }
    .map(\.title)
    .first
print(firstLong ?? "none", "inspected:", inspected)
inspected = 0
_ = books.filter { inspected += 1; return $0.pages > 400 }.first
print("eager inspected:", inspected)

// Functions are values: build new functions from old ones.
func compose<A, B, C>(_ f: @escaping (A) -> B, _ g: @escaping (B) -> C) -> (A) -> C { { g(f($0)) } }
let shortLabel = compose({ (b: Book) in b.title }, { $0.prefix(4).uppercased() })
print(books.map(shortLabel))

// Currying with a closure: fix the first argument.
func pagesOver(_ limit: Int) -> (Book) -> Bool { { $0.pages > limit } }
print(books.filter(pagesOver(440)).count)

// flatMap flattens; compactMap drops nil.
print(books.flatMap { [$0.author, String($0.year)] }.count)
print(["12", "x", "7"].compactMap { Int($0) })
----

----
["Dune", "Children of Dune", "Emma"]
1915
Austen 2 723
Herbert 2 856
Kipling 1 336
Dune inspected: 1
eager inspected: 5
["DUNE", "CHIL", "EMMA", "PERS", "KIM"]
2
10
[12, 7]
----

Points worth noticing:

* *Each stage returns a new value.* `filter`, `map` and `reduce` never modify `books`; the original array is
  unchanged and can be reused by the next statement. This is why the style is easy to test and to run concurrently:
  there is no shared mutable state.
* *`Dictionary(grouping:by:)` replaces a hand-written loop with an accumulator.* The key path `\.author` is used as
  the grouping function (see xref:programming-languages/swift/key-paths-and-dynamic-member-lookup.adoc[Key Paths and
  Dynamic Member Lookup]).
* *Laziness changes the cost model, not the result.* The `.lazy` pipeline stops after the first matching book (one
  element inspected), while the eager `filter` examined all five elements before `first` was asked for. A lazy
  chain also never builds the intermediate arrays.
* *Functions compose.* `compose` and `pagesOver` return functions, so behaviour can be assembled and passed around
  like data. Closures that escape need `@escaping`, which is why `compose` declares it.
* *`compactMap` is "map, then drop nil"*, the idiomatic way to turn optional conversions into a clean array;
  `flatMap` on a sequence flattens one level of nesting.

=== Pitfalls

* A closure passed to `map` that performs side effects (printing, appending to an outside array) defeats the point and
  hides bugs; use `forEach` or a loop for effects.
* Chaining many `lazy` operators and then capturing a mutable variable, as the example does with `inspected`, makes
  the evaluation order observable; keep lazy closures pure.
* `reduce` with an array accumulator that is rebuilt on every step (appending with the `pass:c[+]` operator) is
  quadratic; use `reduce(into:)` to mutate the accumulator in place.
* Long chains are not always clearer than a loop. If the intermediate names would help the reader, introduce
  `let` constants for them.
