= Extensions and Nested Types
:description: Swift extensions and nested types -- extension syntax, adding computed properties, initializers, methods (including mutating), subscripts and nested types via extensions, retroactive conformance and its @retroactive warning, organising a type across extensions, nested types for namespacing and scoped enums, and referring to nested types.
:keywords: Swift, extension, retroactive conformance, retroactive, nested type, namespacing, scoped enum

include::partial$ai-disclaimer.adoc[]

An *extension* adds new functionality to an existing class, structure, enumeration, or protocol type -- including
one defined in another module, or even in the standard library -- without needing access to its original source
code. A *nested type* is a type declared inside another type, scoping it to that enclosing type's namespace.

== Extension Syntax

[source,swift]
----
extension Double {
    var km: Double { self * 1_000.0 }
    var m: Double { self }
    var cm: Double { self / 100.0 }
}

let oneInch = 25.4.cm
let threeFeet = 3.0 * 12.0.cm
print("One inch is \(oneInch) meters")
----

`+extension SomeType { ... }+` opens a new block of declarations that are added to `SomeType` as if they had been
written in its original declaration. An extension may adopt one or more protocols at the same time
(`+extension SomeType: SomeProtocol { ... }+`), exactly like the type's own declaration would.

== Adding Computed Properties, Initializers, Methods, Subscripts and Nested Types via Extensions

[source,swift]
----
struct Point { var x = 0.0, y = 0.0 }

extension Point {
    init(both value: Double) {                     // extensions can add new initializers...
        self.init(x: value, y: value)               // ...but only convenience-style ones for a class: see below
    }

    func translated(by dx: Double, _ dy: Double) -> Point {    // ...instance and mutating methods...
        Point(x: x + dx, y: y + dy)
    }

    mutating func moveToOrigin() {
        self = Point()
    }

    subscript(index: Int) -> Double {               // ...subscripts...
        index == 0 ? x : y
    }

    enum Quadrant { case i, ii, iii, iv }             // ...and nested types.
}

var p = Point(both: 3.0)
print(p[0], p[1])
p.moveToOrigin()
----

Extensions can add computed instance and type properties, instance and type methods (including `mutating`
methods on a structure or enumeration), initializers, subscripts, nested types, and protocol conformances -- but
never *stored* properties, property observers on properties the extension didn't declare, or a *designated*
initializer or `deinit` for a class (a class extension may only add *convenience* initializers, since the class's
original declaration remains solely responsible for its designated initializers and full stored-property setup;
see xref:programming-languages/swift/initialization-and-deinitialization.adoc[Initialization and
Deinitialization]).

== Retroactive Conformance and `@retroactive`

[source,swift]
----
protocol TextRepresentable {
    var textualDescription: String { get }
}

// Conforming a type you don't own (e.g. from another module) to a protocol you don't own either
// is a *retroactive* conformance -- mark it explicitly so the compiler can warn about the risk:
extension Array: @retroactive TextRepresentable where Element: TextRepresentable {
    var textualDescription: String {
        "[" + map(\.textualDescription).joined(separator: ", ") + "]"
    }
}
----

Adding a protocol conformance to a type via an extension -- even a type you don't own, conforming it to a
protocol you don't own either -- is called *retroactive conformance*, and it is genuinely useful (e.g. teaching a
standard-library or third-party type to conform to one of your own protocols). It is also risky: if the type's
own module, or the protocol's own module, later adds the very same conformance itself, the two conflict at link
time. `@retroactive` makes this explicit at the declaration site so both the compiler and a reader can see the
conformance is being asserted from outside, rather than accidentally duplicating one that may appear upstream
later.

== Organising a Type Across Extensions

[source,swift]
----
struct Employee {
    var name: String
    var salary: Double
}

// Grouping related functionality into its own extension, rather than one large original declaration,
// is a common way to organize a type -- especially one whose declaration lives in a different file.
extension Employee: CustomStringConvertible {
    var description: String { "\(name) (\(salary))" }
}

extension Employee: Equatable {
    static func == (lhs: Employee, rhs: Employee) -> Bool {
        lhs.name == rhs.name && lhs.salary == rhs.salary
    }
}
----

Splitting a type's protocol conformances, or a logically distinct group of members, into separate extensions --
often one extension per conformance, as above -- is a common organizational convention: each extension reads as a
self-contained unit (&quot;``here is how ``Employee`` prints itself``&quot;, &quot;``here is how ``Employee`` compares for
equality``") without needing the type's full original declaration open at the same time. This is purely an
organizational device: Swift does not distinguish members added in the original declaration from members added
in an extension at the call site.

== Nested Types for Namespacing and Scoped Enums

[source,swift]
----
struct BlackjackCard {
    enum Suit: Character {                          // scoped to BlackjackCard -- referred to as BlackjackCard.Suit
        case spades = "♠", hearts = "♡", diamonds = "♢", clubs = "♣"
    }

    enum Rank: Int {
        case two = 2, three, four, five, six, seven, eight, nine, ten
        case jack, queen, king, ace

        struct Values {                              // nested two levels deep: BlackjackCard.Rank.Values
            let first: Int
            let second: Int?
        }

        var values: Values {
            switch self {
            case .ace: Values(first: 1, second: 11)
            case .jack, .queen, .king: Values(first: 10, second: nil)
            default: Values(first: rawValue, second: nil)
            }
        }
    }

    let rank: Rank
    let suit: Suit
}
----

Nesting a type inside another scopes its name to the enclosing type's namespace -- `Suit` and `Rank` above exist
only as `BlackjackCard.Suit` and `BlackjackCard.Rank` from outside `BlackjackCard`, which avoids polluting the
module's top-level namespace with names (`Suit`, `Rank`) that only make sense in the context of a playing card.
This is the idiomatic way to give an enum, struct, or class a home when it exists purely to support one other
type -- a *scoped enum*, in `Suit`/`Rank`&#39;s case.

== Referring to Nested Types

[source,swift]
----
let aceOfSpades = BlackjackCard(rank: .ace, suit: .spades)   // inferred: no need to spell out the enclosing type
print(aceOfSpades.rank.values.first)

let heartsSuit: BlackjackCard.Suit = .hearts                  // spelled out fully, from outside BlackjackCard
let jackValues: BlackjackCard.Rank.Values = BlackjackCard.Rank.jack.values
----

Inside the enclosing type (or when the expected type is already known, as with `rank: .ace` above), a nested
type's cases and members can be referred to with the same shorthand `.member` syntax as any other type. From
*outside* the enclosing type, a nested type's full name must be qualified with its enclosing type's name(s), as
`BlackjackCard.Suit` and `BlackjackCard.Rank.Values` show -- exactly as a top-level type's name would be qualified
by its module when needed.

== Organising a Type With Extensions

Extensions are Swift's main tool for *structuring* a type, not only for patching types you do not own. The bookshelf
below keeps the stored data in the primary declarations and adds everything else in focused extensions: derived
properties, a nested type, protocol conformances, a conditional conformance and a constrained method.

[source,swift]
----
struct Book {
    let title: String
    let pages: Int
}

struct Shelf {
    var books: [Book] = []
}

// 1. Extension adding computed properties and methods (no stored properties allowed).
extension Shelf {
    var totalPages: Int { books.reduce(0) { $0 + $1.pages } }
    mutating func add(_ book: Book) { books.append(book) }

    // 2. A nested type declared in an extension.
    enum Size: String {
        case small, medium, large
    }
    var size: Size {
        switch books.count {
        case 0..<3: .small
        case 3..<10: .medium
        default: .large
        }
    }
}

// 3. Conformance in a separate extension keeps the primary declaration short.
extension Book: CustomStringConvertible {
    var description: String { "\(title) (\(pages)p)" }
}
extension Book: Comparable {
    static func < (a: Book, b: Book) -> Bool { a.pages < b.pages }
}
extension Shelf: Sequence {
    func makeIterator() -> IndexingIterator<[Book]> { books.makeIterator() }
}

// 4. Conditional conformance: an array of Books reports a catalogue line only when Element is Book.
protocol Catalogued { var catalogueLine: String { get } }
extension Book: Catalogued { var catalogueLine: String { "- \(self)" } }
extension Array: Catalogued where Element: Catalogued {
    var catalogueLine: String { map(\.catalogueLine).joined(separator: "\n") }
}

// 5. A constrained extension adds a method only for some element types.
extension Sequence where Element == Book {
    func longest() -> Book? { self.max() }
}

var shelf = Shelf()
shelf.add(Book(title: "Emma", pages: 474))
shelf.add(Book(title: "Kim", pages: 336))
print(shelf.totalPages, shelf.size, shelf.size.rawValue)
shelf.add(Book(title: "Dune", pages: 412))
print(shelf.size)
print(shelf.longest() ?? Book(title: "none", pages: 0))
print(shelf.books.catalogueLine)
print(shelf.sorted().map(\.title))
----

[source,text]
----
810 small small
medium
Emma (474p)
- Emma (474p)
- Kim (336p)
- Dune (412p)
["Kim", "Dune", "Emma"]
----

What each extension demonstrates:

* *Only computed members.* The first `Shelf` extension adds `totalPages` and `size` but no stored property, because an
  extension cannot change the memory layout of the type it extends. State has to be declared in the type itself.
* *A nested type from an extension.* `Shelf.Size` is a real nested type, referred to as `Shelf.Size` from outside
  and `.small` when the expected type is known.
* *One conformance per extension.* Putting `CustomStringConvertible`, `Comparable` and `Sequence` in their own
  extensions groups each protocol's requirements together; a reader can see exactly which members exist because of
  which protocol, and the compiler treats this identically to listing them on the type.
* *Conditional conformance.* `Array` conforms to `Catalogued` only when its `Element` does, so
  `shelf.books.catalogueLine` compiles but `[1, 2, 3].catalogueLine` does not.
* *Constrained extensions.* `longest()` exists only on sequences of `Book`; calling it on a sequence of integers is
  a compile error rather than a runtime surprise.

=== Pitfalls

* Extensions on types from other modules can clash if a library later adds the same member; give extension methods
  distinctive names, and mark conformances of external types to external protocols `@retroactive` to acknowledge the
  risk (SE-0364).
* An extension in a different file cannot see `private` members of the type, only `fileprivate` and wider members
  of the same file; code spread over many extensions can force you to widen access.
* Overriding a method through an extension is not possible for classes: extension methods are not part of the
  class's dispatch table in a way subclasses can replace, and Objective-C-visible ones have separate rules.
* Protocol conformance added in an extension is global: once any module declares `extension Book: Comparable`, the
  conformance exists for every module that can see it.
