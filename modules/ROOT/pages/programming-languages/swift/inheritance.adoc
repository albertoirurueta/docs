= Inheritance
:description: Swift inheritance -- base classes, subclassing, overriding methods/properties/observers and calling super, final, dynamic dispatch and polymorphism, and when to subclass vs. compose or use protocols.
:keywords: Swift, inheritance, subclass, superclass, override, super, final, dynamic dispatch, polymorphism, composition over inheritance, protocol-oriented programming

include::partial$ai-disclaimer.adoc[]

A class can inherit methods, properties, subscripts and other characteristics from another class. Inheritance is
what most fundamentally distinguishes classes from the other named types --
xref:programming-languages/swift/structures-and-classes.adoc[structs and enums cannot inherit] from another
struct or enum at all.

== Base Classes and Subclassing

[source,swift]
----
class Animal {
    let name: String
    var energy = 100

    init(name: String) {
        self.name = name
    }

    func makeSound() -> String {
        "..."
    }

    var summary: String {
        "\(name) says \(makeSound())"
    }
}

class Dog: Animal {
    var breed: String

    init(name: String, breed: String) {
        self.breed = breed
        super.init(name: name)              // a subclass's own storage is set first, then the superclass's
    }
}

let generic = Animal(name: "Generic Animal")
let rex = Dog(name: "Rex", breed: "Labrador")
print(rex.name, rex.breed)                   // Dog inherits `name` and `energy` from Animal for free
----

A class with no explicit superclass (`Animal` above) is a *base class* -- Swift classes do not implicitly
inherit from a universal root class the way Objective-C classes inherit from `NSObject`. Writing `: Animal` after
`Dog` makes it a *subclass* of `Animal`, inheriting every method, property and subscript `Animal` declares; a
subclass may add its own storage and behavior on top, and a subclass initializer that adds stored properties must
call `+super.init(...)+` to let the superclass finish initializing its own storage (see
xref:programming-languages/swift/initialization-and-deinitialization.adoc[Initialization and Deinitialization]
for the full delegation and safety-check rules this feeds into).

== Overriding Methods, Properties and Observers, and Calling `super`

[source,swift]
----
class Cat: Animal {
    override func makeSound() -> String {                     // `override` replaces the inherited implementation
        "Meow"
    }

    override var summary: String {                             // computed properties can be overridden too
        super.summary + " (a cat, obviously)"                   // `super.` reaches the superclass's version
    }

    override var energy: Int {
        didSet {                                                // adding an observer to an *inherited* property
            if energy < oldValue {
                print("\(name) used some energy, now at \(energy)")
            }
        }
    }
}

let whiskers = Cat(name: "Whiskers")
print(whiskers.summary)     // Whiskers says Meow (a cat, obviously)
whiskers.energy -= 10        // Whiskers used some energy, now at 90
----

`override` is required whenever a subclass redeclares an inherited method, subscript, or property (the compiler
rejects an accidental redeclaration missing the keyword, and rejects `override` on a member that overrides
nothing). A property override may change nothing but *add* observers to an inherited stored or computed property,
as `Cat.energy` does above -- the inherited implementation still runs first, and the override's `willSet`/`didSet`
runs in addition to it. `super.<member>` reaches the superclass's own implementation of a method, computed
property, or subscript from inside an override -- most commonly to extend rather than fully replace the inherited
behavior, as `summary` does above.

== `final`, Dynamic Dispatch and Polymorphism

[source,swift]
----
class Base {
    final func cannotBeOverridden() -> String { "fixed behavior" }   // `final` on a member: no subclass may override it
}

final class Sealed: Base {}    // `final` on the class itself: no subclass of Sealed may ever be declared

let animals: [Animal] = [generic, rex, whiskers]
for animal in animals {
    print(animal.summary)      // each call dispatches to the *runtime* type's implementation, not `Animal`'s
}
----

Marking a method, property or subscript `final` forbids any subclass from overriding it; marking the class itself
`final` forbids subclassing it at all -- both are optimization and API-design tools: a `final` member can be
dispatched statically instead of dynamically, and a sealed hierarchy can't be extended in ways its author didn't
anticipate. Calling an overridable member through a superclass-typed reference or array element (`animal.summary`
above) is *dynamic dispatch*: Swift looks up the actual runtime type of the instance and calls its implementation,
which is what lets a loop over `[Animal]` produce `Dog`&#39;s, `Cat`&#39;s and `Animal`&#39;s own behavior side by side --
*polymorphism*.

== When to Subclass vs. Compose or Use Protocols

[mermaid]
....
classDiagram
    class Animal {
        +name: String
        +energy: Int
        +makeSound() String
        +summary: String
    }
    class Dog {
        +breed: String
        +makeSound() String
    }
    class Cat {
        +makeSound() String
        +summary: String
    }
    Animal <|-- Dog
    Animal <|-- Cat
....

The `Animal`/`Dog`/`Cat` hierarchy above is small enough to be harmless, but it already shows inheritance's known
problems at scale: a subclass inherits *everything* from its superclass whether it wants it or not (a `RobotDog`
would still inherit `energy`, which makes no sense for a machine); Swift classes support only *single*
inheritance, so once a type needs to combine "makes a sound" with "can be drawn on screen" and "can be encoded to
JSON", a class hierarchy alone cannot express all three without one of them living awkwardly inside another; and
a change to a base class's implementation can silently break a distant subclass that depended on the old
behavior (the *fragile base class* problem) -- worse the deeper the hierarchy grows.

*Composition* (a type holding another type as a property and delegating to it, rather than inheriting from it)
and *protocols* (declaring a set of requirements any type -- class, struct, or enum -- can adopt, with no
implementation and no single-inheritance limit) sidestep all three: prefer composing or adopting a protocol over
subclassing whenever the relationship is "has a" or "can do", and reserve subclassing for a genuine "is a"
relationship where sharing a base class's *stored* state and initializers is actually wanted. This is the
motivation behind *protocol-oriented programming*, covered in full in
xref:programming-languages/swift/protocols.adoc[Protocols].

== How Dispatch and Initialization Work

Inheritance is a runtime mechanism, and two compiler rules explain most of its surprises: *two-phase
initialization* and *dynamic dispatch through a method table*. The running bookshelf example uses a small hierarchy
`Item`, `Book` and `AudioBook`, each inheriting from the previous one, that overrides a computed property and a method.

[source,swift]
----
class Item {
    let title: String
    init(title: String) {
        self.title = title
        print("Item.init(\(title))")
    }
    var loanDays: Int { 14 }
    func describe() -> String { "\(title): \(loanDays) days" }
    deinit { print("deinit Item \(title)") }
}

class Book: Item {
    let pages: Int
    init(title: String, pages: Int) {
        self.pages = pages                    // phase 1: own properties first
        super.init(title: title)              // then the superclass
        print("Book.init done")               // phase 2: self is fully usable
    }
    override var loanDays: Int { pages > 500 ? 28 : 21 }
}

final class AudioBook: Book {
    let hours: Double
    init(title: String, pages: Int, hours: Double) {
        self.hours = hours
        super.init(title: title, pages: pages)
    }
    override var loanDays: Int { super.loanDays - 7 }
    override func describe() -> String { super.describe() + " (\(hours) h audio)" }
}

func printAll(_ items: [Item]) {
    for item in items { print(item.describe()) }      // dynamic dispatch picks the override
}

do {
    let items: [Item] = [Item(title: "Pamphlet"), Book(title: "Emma", pages: 474), AudioBook(title: "Dune", pages: 612, hours: 21)]
    printAll(items)
    // Downcasting asks the runtime for the dynamic type.
    for item in items {
        switch item {
        case let a as AudioBook: print("audio", a.hours)
        case let b as Book: print("book", b.pages)
        default: print("plain item")
        }
    }
}
print("end of scope")
----

[source,text]
----
Item.init(Pamphlet)
Item.init(Emma)
Book.init done
Item.init(Dune)
Book.init done
Pamphlet: 14 days
Emma: 21 days
Dune: 21 days (21.0 h audio)
plain item
book 474
audio 21.0
deinit Item Pamphlet
deinit Item Emma
deinit Item Dune
end of scope
----

Reading the output top to bottom:

* *Phase 1 runs subclass first, then upwards.* `Book.init` assigns its own `pages` _before_ calling `super.init`;
  Swift refuses to let you touch `self` or call methods until every stored property of the whole chain has a value.
  Only after `super.init` returns does phase 2 begin, where `self` is fully formed and may be used.
* *Overrides are chosen at run time.* `printAll` only knows `Item`, yet the pamphlet shows 14 days, the 474-page book
  21 days and the long audio book 28 minus 7 = 21 days. The call goes through the object's class, not through the
  static type of the variable.
* *`super` is a static call.* `super.loanDays` and `super.describe()` always call the parent implementation, which is
  how an override extends rather than replaces behaviour.
* *Deinitialization chains upwards*: a subclass's `deinit` runs first and then the superclass's (here only `Item` declares one), and the messages are printed when the
  `do` block ends and the array releases the last references (see
  xref:programming-languages/swift/automatic-reference-counting.adoc[Automatic Reference Counting]).

=== The Method Table

For a non-`final` class method or property, the compiler emits an indirect call through a *vtable*: an array of
function pointers stored with the class metadata. Each class copies its parent's table and replaces the slots it
overrides. The object header holds a pointer to its class, so `item.describe()` loads the table of the object's
real class and jumps to the slot for `describe`.

[mermaid]
....
flowchart LR
    obj[AudioBook instance<br/>isa pointer] --> meta[AudioBook metadata]
    meta --> vt[vtable]
    vt --> s1[loanDays: AudioBook version]
    vt --> s2[describe: AudioBook version]
    vt --> s3[deinit: AudioBook version]
....

Marking a class or member `final`, or making it `private`/`fileprivate` or part of a whole-module-optimised module
with no overrides, lets the compiler call it directly or inline it. That is the real performance argument for
`final`; it also documents that the type is not designed for subclassing.

=== Pitfalls

* Calling an overridable method from an initializer before phase 1 completes is not allowed; after it, the method may
  run an override that depends on state the subclass has not initialised -- keep initializers free of virtual calls.
* Overriding a stored property is not possible; only its getters, setters or observers can be overridden, and a
  `let` cannot be overridden at all.
* Class inheritance couples the subclass to the parent's implementation. Prefer protocols and composition when
  the relationship is "can do" rather than "is a" (see the previous section of this page).
