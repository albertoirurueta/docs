Swift was designed from the start to sit alongside C and Objective-C, and more recently gained first-class
{cpp} interop as well. All three follow the same underlying idea -- a compiler-generated *importer* maps foreign
declarations into their nearest Swift equivalent -- but each language's importer has its own rules, gaps, and
annotations for smoothing over the differences.

== The Clang Importer: C into Swift

When a Swift target imports a C header (directly, or via a bridging header -- see <<objc-interop-section>>
below), the *Clang importer* translates it, largely following the same conventions
xref:programming-languages/objective-c/swift-interoperability.adoc[Objective-C's own importer] uses for its
`NS`-prefixed types:

[cols="1,2",options="header"]
|===
| C construct | Imported as

| `int`, `double`, `+_Bool+` | `Int32`, `Double`, `Bool` -- fixed-width, never the platform-dependent `int`.
| `+struct Point { double x, y; }+` | `Point`, a Swift struct with the same fields, memberwise `init` synthesized.
| `union` | A Swift struct exposing every member at the same memory offset -- reading one after writing another
  is undefined behavior, exactly as in C.
| `typedef` | A Swift `typealias` (or, for `NS_ENUM`-style patterns, a real Swift enum).
| `+T *+` | `UnsafeMutablePointer<T>` (or `UnsafePointer<T>` for a `+const T *+`); `+T **+` becomes a pointer to a
  pointer type the same way.
| `+void (*)(int)+` (function pointer) | A Swift closure type, `+(Int32) -> Void+`.
| `+#define MAX_SIZE 128+` | A global `let` constant, when the importer can infer a type; more complex macros may
  not import at all.
| Preprocessor conditionals (`+#if+`/`+#ifdef+`) | Resolved by Clang before Swift ever sees the header -- Swift
  never sees the macro itself, only the branch Clang picked.
|===

[source,swift]
----
// Point.h:  struct Point { double x, y; };  double distance(struct Point a, struct Point b);

var origin = Point(x: 0, y: 0)               // memberwise init, synthesized by the importer
let d = distance(origin, Point(x: 3, y: 4))   // free C functions import as free Swift functions
----

See xref:programming-languages/c/structures-unions-and-type-aliases.adoc[C: Structures, Unions and Type
Aliases] and xref:programming-languages/c/pointers.adoc[C: Pointers] for these constructs on the C side, and
xref:programming-languages/swift/memory-safety-and-unsafe-pointers.adoc[Memory Safety and Unsafe Pointers] for
working with the `+Unsafe*Pointer+` family an imported C API hands back.

== Module Maps and System-Library Targets in SwiftPM

A plain C header has no notion of a Swift "module" -- a **module map** (`module.modulemap`) is what tells the
Clang importer which headers belong to which module and how to expose them:

[source,swift]
----
// Sources/CZlib/module.modulemap
module CZlib [system] {
    header "shim.h"
    link "z"
    export *
}
----

[source,swift]
----
// Package.swift
let package = Package(
    name: "MyTool",
    targets: [
        .systemLibrary(name: "CZlib", pkgConfig: "zlib"),   // wraps a C library already on the system
        .target(name: "MyTool", dependencies: ["CZlib"])
    ]
)
----

A `systemLibrary` target wraps a C library that is expected to already be installed (via `pkgConfig`, or a
`providers` list naming the system package manager's package name), rather than one SwiftPM builds itself; an
ordinary `.target` with a `+Sources/<Name>/include/*.h+` layout works the same way for a C library that *is* built
from source as part of the package. See
xref:programming-languages/swift/swift-package-manager.adoc[Swift Package Manager] for package targets in
general.

== Objective-C Interop

[cols="1,2",options="header"]
|===
| Mechanism | Purpose

| Bridging header (`<Target>-Bridging-Header.h`) | Exposes chosen Objective-C headers to every Swift file in an
  app target, with no `import` needed on the Swift side.
| `@objc` / `@objcMembers` | Exposes a Swift declaration (or every member of a class) to Objective-C, which
  requires inheriting from `NSObject`.
| `NS_SWIFT_NAME` | Renames an Objective-C declaration as seen from Swift.
| Nullability (`nonnull`/`nullable`, `NS_ASSUME_NONNULL_BEGIN`/`END`) | Becomes `T` vs. `T?` on the Swift side --
  an unaudited header imports as implicitly-unwrapped optionals throughout.
| Lightweight generics (`+NSArray<NSString *> *+`) | Becomes a properly parameterized Swift collection
  (`[String]`) instead of `[Any]`.
| `+- (BOOL)op:(NSError **)error+` | Imported as `func op() throws` -- the error out-parameter becomes a thrown
  `Error`.
|===

[source,swift]
----
// Objective-C: - (void)fetchUserWithID:(NSInteger)userID
//                  completion:(void (^)(User * _Nullable, NSError * _Nullable))completion;

let user = try await service.fetchUser(id: 42)   // imported as an `async throws` function -- no completion handler
----

An Objective-C API following the `+completion:(void (^)(Result, NSError *))+` pattern is imported as an `async`
function automatically, unifying it with native Swift concurrency (see
xref:programming-languages/swift/async-await-and-tasks.adoc[Async/Await and Tasks]) with no manual bridging.
Exposing Swift *to* Objective-C is the mirror image: a class must inherit `NSObject` and mark members `@objc`
(or `@objcMembers`), and the compiler emits a `<Module>-Swift.h` header for Objective-C files to `+#import+`.

This reference's xref:programming-languages/objective-c/index.adoc[Objective-C Reference] covers this direction
in much greater depth, in particular
xref:programming-languages/objective-c/swift-interoperability.adoc[Swift Interoperability] (the bridging header
and generated header mechanics, the full table of imported constructs, and mixed-language project practices) and
xref:programming-languages/objective-c/lightweight-generics-and-nullability.adoc[Lightweight Generics and
Nullability] (the annotations that produce a clean Swift API).

== {cpp} Interop

[source,swift]
----
// Package.swift
.target(
    name: "MySwiftTarget",
    swiftSettings: [.interoperabilityMode(.Cxx)]     // enables -cxx-interoperability-mode=default
)
----

{cpp} interop is opt-in per target, via `-cxx-interoperability-mode=default` (or `.interoperabilityMode(.Cxx)`
in a SwiftPM manifest). Once enabled:

[source,swift]
----
// Point.hpp:  struct Point { double x, y; double distance(const Point& other) const; };

var origin = Point()
origin.x = 0
origin.y = 0
let other = Point(x: 3, y: 4)                // {cpp} constructors are imported too
origin.distance(other)                       // member functions become Swift methods

var vec = std.vector<Int32>()                // std::vector<int> imported as a Swift-usable generic type
vec.push_back(1)
vec.push_back(2)
for value in vec { print(value) }             // std::vector conforms to Swift's Sequence when interop is on
----

[cols="1,2",options="header"]
|===
| {cpp} construct | Imported as

| A {cpp} class/struct | A Swift struct or class exposing its public members and methods.
| References (`T&`, `const T&`) | Mapped to Swift's own parameter-passing conventions; a `const T&` parameter
  behaves like an implicit borrow.
| `std::vector`, `std::string`, `std::map`, ... | Usable directly from Swift, with `Sequence`/`Collection`
  conformance synthesized where the shape allows it.
| {cpp} templates | Only concrete instantiations actually used from Swift are imported -- an uninstantiated
  template has nothing for Swift to bind to.
|===

Exposing Swift *to* {cpp} works in the same target, once interop is enabled -- a {cpp} file can `+#include+` the
generated Swift header and call exposed Swift functions and methods directly, though (as of Swift 6.3) the
Swift-to-{cpp} direction supports a narrower set of Swift features than the {cpp}-to-Swift direction does. See
xref:programming-languages/cpp/templates.adoc[{cpp}: Templates] and
xref:programming-languages/cpp/containers.adoc[{cpp}: Containers] for these constructs on the {cpp} side.

This reference's xref:programming-languages/cpp/index.adoc[{cpp} Reference] and its own
xref:programming-languages/cpp/memory-management-and-smart-pointers.adoc[Memory Management and Smart Pointers]
page cover ownership and lifetime rules relevant to values crossing the boundary.

== Worked Example: A C Catalogue Library Called From Swift

The previous sections list the rules; this section builds a package that follows them. `ShelfTool` has a C target, `CCatalogue`, with
a header in its `include` directory, and a Swift executable that imports it. SwiftPM generates the module map for the C target
automatically, so `import CCatalogue` is all the Swift side needs.

[source,swift]
----
// swift-tools-version: 6.0
import PackageDescription

let package = Package(
    name: "ShelfTool",
    targets: [
        .target(name: "CCatalogue"),                       // C sources and a public header in include/
        .executableTarget(name: "shelfcli", dependencies: ["CCatalogue"]),
    ]
)
----

The C header declares a struct, two functions and a callback type:

[source,c]
----
#ifndef CATALOGUE_H
#define CATALOGUE_H
#include <stddef.h>

typedef struct {
    int pages;
    double rating;
} CBook;

/// Sum of pages of `count` books.
int catalogue_total_pages(const CBook *books, size_t count);

/// Writes a label into `buffer` (at most `size` bytes including the NUL) and returns its length.
int catalogue_label(const CBook *book, char *buffer, size_t size);

typedef int (*catalogue_visitor)(const CBook *book, void *context);
void catalogue_visit(const CBook *books, size_t count, catalogue_visitor visitor, void *context);

#endif
----

and the implementation is ordinary C:

[source,c]
----
#include "catalogue.h"
#include <stdio.h>

int catalogue_total_pages(const CBook *books, size_t count) {
    int total = 0;
    for (size_t i = 0; i < count; i++) total += books[i].pages;
    return total;
}

int catalogue_label(const CBook *book, char *buffer, size_t size) {
    return snprintf(buffer, size, "%d pages, rated %.1f", book->pages, book->rating);
}

void catalogue_visit(const CBook *books, size_t count, catalogue_visitor visitor, void *context) {
    for (size_t i = 0; i < count; i++) {
        if (visitor(&books[i], context) == 0) break;
    }
}
----

The Swift side shows the four things every C interop needs: constructing imported structs, passing arrays, getting data out through buffers
and handling callbacks.

[source,swift]
----
import CCatalogue

// The C struct arrives as a Swift struct with a memberwise initializer.
let books = [
    CBook(pages: 412, rating: 4.5),
    CBook(pages: 336, rating: 3.8),
    CBook(pages: 474, rating: 4.1),
]

// const CBook * plus size_t becomes UnsafePointer<CBook> plus Int; an array passes as a pointer.
let total = books.withUnsafeBufferPointer { buffer in
    catalogue_total_pages(buffer.baseAddress, buffer.count)
}
print("total pages:", total)

// char * output: give C a buffer, then build a Swift String from the bytes.
var label = [CChar](repeating: 0, count: 64)
var first = books[0]
let written = catalogue_label(&first, &label, label.count)       // & passes the address of a variable
let text = label.withUnsafeBufferPointer { String(cString: $0.baseAddress!) }
print(written, text)

// A C callback is a @convention(c) closure: it cannot capture, so state travels through the context pointer.
final class Visitor { var seen: [Int] = [] }
let visitor = Visitor()
books.withUnsafeBufferPointer { buffer in
    catalogue_visit(buffer.baseAddress, buffer.count, { book, context in
        let visitor = Unmanaged<Visitor>.fromOpaque(context!).takeUnretainedValue()
        visitor.seen.append(Int(book!.pointee.pages))
        return book!.pointee.pages > 400 ? 1 : 0       // 0 stops the iteration
    }, Unmanaged.passUnretained(visitor).toOpaque())
}
print("visited:", visitor.seen)
----

`swift run` builds both targets and prints:

[source,text]
----
total pages: 1222
20 412 pages, rated 4.5
visited: [412, 336]
----

* *The struct arrives with a memberwise initializer.* `CBook(pages: 412, rating: 4.5)` is generated by the importer, and `int` and
  `double` become `Int32` and `Double`, which is why `Int(book!.pointee.pages)` converts in the callback.
* *Pointers need explicit addresses.* A `+const CBook *+` parameter is imported as `UnsafePointer<CBook>`. An array is passed through
  `withUnsafeBufferPointer`, which guarantees the pointer is valid only inside the closure. Passing a single value (`books[0]`) is a
  compile error (*cannot convert value of type 'CBook' to expected argument type 'UnsafePointer<CBook>'*); copy it into a `var` and
  pass `&first`.
* *Output buffers are arrays of `CChar`.* `catalogue_label` wrote 20 characters plus the terminating NUL into the buffer, and
  `String(cString:)` read them back. C's `snprintf` guards the length, which is the pattern to copy: always pass the capacity.
* *Callbacks cannot capture.* A C function pointer is imported as a `@convention(c)` closure, which has no context of its own. The closure
  above gets its state through the C API's `+void *context+`, which Swift sees as `UnsafeMutableRawPointer`; `Unmanaged` converts a class
  reference to and from that pointer without changing its reference count. The callback returned `0` for the 336-page book, so the loop
  stopped after two items.

=== Pitfalls

* The pointer from `withUnsafeBufferPointer` or `&variable` must not outlive the call; storing it and using it later is undefined
  behaviour with no diagnostic.
* C headers lack nullability and ownership information; annotate them (`+_Nonnull+`, `+_Nullable+`) so that Swift imports precise optionals,
  and document who frees returned memory.
* A header under `include/` is public to every client of the target; keep implementation-only declarations in the `.c` file or a private header.
* `String(cString:)` on a buffer without a NUL terminator reads past the end; make sure C wrote the terminator, or use `snprintf`-style bounded
  functions as above.
