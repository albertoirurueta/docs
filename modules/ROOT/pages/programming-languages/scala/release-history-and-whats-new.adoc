== Before Scala 3: 2.13.0 (11 June 2019)

Scala 2.13.0 is the release whose library Scala 3 still uses. Its announcement lists four areas: the collections were
overhauled for simplicity, performance and safety (the centerpiece), the standard library gained a faster and more robust
`Future` plus new classes and methods, the language gained literal types, partial unification and by-name implicits, and
the compiler became 5 to 10 percent faster with deterministic output.

What this means for a Scala 3 programmer today is that most of the standard library has not changed since 2.13: the
collection hierarchy, `LazyList`, `scala.util.Using` and `scala.util.chaining` all come from this release. Three
things were deprecated rather than removed in 2.13.0, and the deprecated forms still compile in Scala 3.10. A program
that uses them, compiled with `-deprecation`:

[source,scala]
----
import scala.collection.generic.CanBuildFrom

object Old {
  def main(args: Array[String]): Unit = {
    val t: Traversable[Int] = List(1, 2)
    val s = Stream.from(1).take(2).toList
    println((t, s))
  }
}
----

On Scala 2.13.18 the compiler answers:

[source,text]
----
old.scala:5: warning: type Traversable in package scala is deprecated (since 2.13.0): Use Iterable instead of Traversable
    val t: Traversable[Int] = List(1, 2)
           ^
old.scala:6: warning: value Stream in package scala is deprecated (since 2.13.0): Use LazyList instead of Stream
    val s = Stream.from(1).take(2).toList
            ^
2 warnings
(List(1, 2),List(1, 2))
----

and Scala 3.10.0 says the same, in its own format, and also runs the program:

[source,text]
----
-- Deprecation Warning: old.scala:5:11
5 |    val t: Traversable[Int] = List(1, 2)
  |           ^^^^^^^^^^^
  |type Traversable in package scala is deprecated since 2.13.0: Use Iterable instead of Traversable
-- Deprecation Warning: old.scala:6:12
6 |    val s = Stream.from(1).take(2).toList
  |            ^^^^^^
  |value Stream in package scala is deprecated since 2.13.0: Use LazyList instead of Stream
2 warnings found
(List(1, 2),List(1, 2))
----

`scala.collection.generic.CanBuildFrom` behaves the same way: it is a deprecated type whose message points to
`scala.collection.BuildFrom` ("Use scala.collection.BuildFrom instead"), and the `apply` method of `BuildFrom` is
deprecated in favour of `newBuilder`. So the accurate statement for the books is that `CanBuildFrom` and `Traversable`
are deprecated shims since 2.13.0, not removed, and new code should not use them.

The replacements, all run on 2.13.18 in one program, are `LazyList`, `BuildFrom`, `Using`, `pipe`, `tap` and literal types:

[source,scala]
----
import scala.util.Using
import scala.util.chaining._
import scala.collection.BuildFrom

object S213 {
  val one: 1 = 1                                   // literal type (2.13.0)

  def firstTwo[A, C](xs: C)(implicit ev: C => Iterable[A], bf: BuildFrom[C, A, C]): C =
    bf.fromSpecific(xs)(ev(xs).take(2))             // BuildFrom replaces CanBuildFrom

  def main(args: Array[String]): Unit = {
    val naturals = LazyList.from(1)                 // LazyList replaces Stream
    println(naturals.take(5).toList)
    println(firstTwo(Vector(1, 2, 3)))
    println(5.pipe(_ + 1).tap(x => println(s"tapped $x")))
    val n = Using(new java.io.StringReader("abc"))(_.read()).get
    println(n)
    println(one)
  }
}
----

[source,text]
----
List(1, 2, 3, 4, 5)
Vector(1, 2)
tapped 6
6
97
1
----

and xref:programming-languages/scala/collections-architecture-and-custom-collections.adoc[Collections Architecture & Custom Collections],
and `LazyList` in xref:programming-languages/scala/views-iterators-and-lazylist.adoc[Views, Iterators & LazyList].

== 3.0.0 (14 May 2021)

Scala 3 was announced after eight years of work, 28,000 commits and more than a hundred contributors. The announcement
sends readers to the Scala 3 documentation, the "New in Scala 3" article, the Book and the migration guide, and says
that one thing changed completely compared to Scala 2: macros. It also fixes the release policy: patch releases are
forward and backward compatible with each other, minor releases add language features and library APIs, and "libraries
built with Scala 3.0.0 will keep working with Scala 3.x.y". At the time of that post Scaladex listed 308 early adopter
libraries on Scala 3 against 2597 on Scala 2.13; the 3.9 announcement says that roughly 56 percent of Scala 3 libraries
now publish with 3.3 LTS.

Three of the dropped features are easy to demonstrate, because they are syntax errors on every Scala 3 compiler. This
file uses the procedure syntax, `do`-`while` and a symbol literal; each is compiled on its own so that one error does not
hide another. On 3.3.8 and on 3.10.0 the procedure syntax gives the same message:

[source,scala]
----
def proc() { println("x") }

@main def procDemo(): Unit = proc()
----

[source,text]
----
-- [E040] Syntax Error: proc.scala:1:11
1 |def proc() { println("x") }
  |           ^
  |           '=' expected, but '{' found
1 error found
Compilation failed
----

The `do`-`while` loop fails with a message that does not name the feature (`end of toplevel definition expected but 'do'
found`, then `Illegal start of toplevel definition` on the next line), which is why the form is worth recognizing, and a
symbol literal such as `+'sym+` fails with a message that tells you what to write instead: "use a string literal "sym" or an
application Symbol("sym") instead". All three still need rewriting by hand when you port a Scala 2 file; see the
incompatibilities page for the rewrite of each.

== 3.1.0 (21 October 2021)

The 3.1.0 announcement is the first one that explains the compatibility model of the 3.x series, and it explains it by
admitting a limitation. Scala 3.1 is backward binary compatible, since dependencies compiled with 3.0 work in 3.1
projects, but it is not forward binary compatible, since dependencies compiled with 3.1 do not work in 3.0 projects. The
advice at the time to library maintainers was to test with 3.1.0 and 3.0.2 but to publish with 3.0.2, so that downstream
users on either version could use the library. The same rule, unchanged, is why 3.9 LTS is the recommended publishing
target today.

Highlights of the release, all from the announcement:

* `import language.experimental.saferExceptions` and the `throws` clause, a way to declare and check which exceptions a
  function can throw. It is still experimental today.
* A `-Wconf` compiler flag to silence warnings, turn them into errors or otherwise configure them, and the `@nowarn`
  annotation back from Scala 2.13.
* Efficient bytecode (`lookupswitch`) for `match` over `String` literals.
* Simplified `Manifest` synthesis, for compatibility with Scala 2.
* `Mirror` support for hierarchical sealed types, which type class derivation builds on.
* Scala.js 1.7.0 or later is required by 3.1.

The release also changed what compiler you can run on a current JDK. A 3.1.3 compiler started on JDK 26 stops with an
error about the JDK's own class files; on JDK 17 the same compiler works. This is the output on JDK 26, for any program:

[source,text]
----
error while loading ElementType,
class file /modules/java.base/java/lang/annotation/ElementType.class is broken, reading aborted with class java.lang.RuntimeException
bad constant pool index: 0 at pos: 1220
error while loading AccessFlag,
class file /modules/java.base/java/lang/reflect/AccessFlag.class is broken, reading aborted with class java.lang.RuntimeException
bad constant pool index: 0 at pos: 6381
2 errors found
Compilation failed
----

The remedy is to run the old compiler on an older JDK (17 in the probes of this page). The JDK floor moves in the
other direction in 3.8 (see below). Old compilers on new JDKs are covered in
xref:programming-languages/scala/versions-compatibility-and-jdks.adoc[Versions, Compatibility & JDKs].

== 3.2.0 (5 September 2022)

The headline of 3.2.0 is coverage: the compiler can now generate Scoverage data itself with the `-coverage-out` flag,
without a compiler plugin, so it works for Scala 3 code (later releases added `// $COVERAGE-OFF$` markers in 3.3.8 and
3.8.3). The release also allowed exports in extension clauses (`+export richInt.*+` as a way to add extension methods in
bulk), code completion for refined `Selectable` types, better `Mirror` synthesis for local and inner classes and tuples up
to 22 elements, `given` bindings in `for` generators, easier construction of classes whose first parameter list is a
`using` clause, and the `-Vprofile` flags that report code complexity. The announcement also lists new experimental APIs
(`MainAnnotation`, `newMain`, `TupledFunction`) and a list of APIs that were stabilised.

Two changes of 3.2 matter for ordinary code because they are warnings that every project meets:

* *Pattern bindings are type checked more strictly.* The reference page says that from 3.2 on, type checking rules are
  tightened so that warnings are reported at compile time. A `val` whose pattern is more specific than the right-hand side
  warns that the match may fail at run time.
* *Non-local returns are deprecated.* A `return` inside a lambda is compiled by throwing and catching an exception, and
  3.2.0 started to warn about it.

Both are demonstrated here. This program has a pattern binding that the compiler cannot prove irrefutable:

[source,scala]
----
@main def pbind(): Unit =
  val elems = List(1, 2, 3)
  val first :: rest = elems
  println((first, rest))
----

On 3.1.3 (JDK 17) it compiles silently and prints `(1,List(2, 3))`. On 3.3.8 it warns, and the text of the advice changes
again in 3.8, where `: @unchecked` is replaced by `.runtimeChecked` (SIP-57, see 3.8):

[source,text]
----
-- Warning: pbind.scala:3:22
3 |  val first :: rest = elems
  |                      ^^^^^
  |pattern's type ::[Int] is more specialized than the right hand side expression's type List[Int]
  |
  |If the narrowing is intentional, this can be communicated by adding `: @unchecked` after the expression,
  |which may result in a MatchError at runtime.
  |This patch can be rewritten automatically under -rewrite -source 3.2-migration.
1 warning found
(1,List(2, 3))
----

The same program on 3.8.4 and on 3.10.0 prints the identical warning with "adding `.runtimeChecked` after the expression"
and "-rewrite -source 3.8-migration". The non-local return is this program:

[source,scala]
----
def firstNegative(xs: List[Int]): Int =
  xs.foreach { x => if x < 0 then return x }
  0

@main def nlr(): Unit = println(firstNegative(List(3, -2, 5)))
----

It prints `-2` on every version, and compiles without a warning on 3.1.3. On 3.2.2 the warning points to the old API:

[source,text]
----
-- Warning: nlr.scala:2:34
2 |  xs.foreach { x => if x < 0 then return x }
  |                                  ^^^^^^^^
  |Non local returns are no longer supported; use scala.util.control.NonLocalReturns instead
1 warning found
-2
----

and from 3.3 on the advice is the one that the next section introduces ("use `boundary` and `boundary.break` in
`scala.util` instead"). Both warnings are still warnings, not errors, on 3.10.0. See
xref:programming-languages/scala/exceptions-boundary-and-early-exit.adoc[Exceptions, boundary & Early Exit] and
xref:programming-languages/scala/extractors-and-pattern-bindings.adoc[Extractors & Pattern Bindings].

Sources: https://www.scala-lang.org/blog/2022/09/05/scala-3.2.0-released.html[Scala 3.2.0 released!], https://docs.scala-lang.org/scala3/reference/changed-features/pattern-bindings.html[Scala 3 Reference: Pattern bindings], https://docs.scala-lang.org/scala3/reference/dropped-features/nonlocal-returns.html[Scala 3 Reference: Deprecated nonlocal returns]

== 3.3.0 LTS (30 May 2023)

3.3.0 is the first Long Term Support release and defines the model the section relies on. Scala 3.3.x is maintained for
at least three years; new minor releases (3.4, 3.5 and so on) are called Scala Next, "equivalent to Java's feature
releases"; bug fixes and usability improvements from Scala Next are back-ported as 3.3.x patches, and apart from those
forward and backward compatible changes the LTS is feature frozen. The LTS model does not change the compatibility
guarantees: projects built with any future release can depend on a library compiled with 3.3.x.

What it added to the language and library:

* *Linting.* `-Wunused:imports`, `privates`, `locals`, `explicits`, `implicits`, `params` and `all`, and `-Wvalue-discard`,
  which catches the `map` where `flatMap` was meant.
* *Fewer braces.* A colon can replace the braces around a method argument (SIP-44, experimental in 3.2.0 and promoted to
  stable). The probe is a `map` whose lambda is on the next line:

[source,scala]
----
@main def braces(): Unit =
  val ys = List(1, 2, 3).map: x =>
    x * 2
  println(ys)
----

On 3.2.2 it does not compile (`not a legal formal parameter for a function literal`, then `Not found: x` on the next
line); on 3.3.8 it prints `List(2, 4, 6)`.

* *`boundary` and `break`,* the type-safe replacement for non-local returns. A `break` can only be called where a
  matching `Label` is in scope, so the escape is checked by the compiler.

[source,scala]
----
import scala.util.boundary, boundary.break

@main def bnd(): Unit =
  val r = boundary:
    for n <- List(1, 2, -3, 4) do
      if n < 0 then break(n)
    0
  println(r)
----

On 3.3.8 it prints `-3`. On 3.2.2 the import itself fails:

[source,text]
----
-- [E008] Not Found Error: bmin.scala:1:18
1 |import scala.util.boundary
  |                  ^^^^^^^^
  |                  value boundary is not a member of util
----

* *A new default lazy val implementation,* with better performance and safe under parallel access. It is the
  implementation whose use of `sun.misc.Unsafe` later forced the changes of 3.8; the 3.9 notes explain that code compiled
  with Scala 3.0 to 3.7 still goes through the legacy `scala.runtime.LazyVals` API, and that Scala CLI's experimental
  Sloth support rewrites such dependencies.
* A known incompatibility: `inline` parameters are no longer assumed to be stable paths, so `inline def method(inline
  param: Outer): param.Inner` is an error and the fix is to drop the `inline` modifier on that parameter.

3.3 is also the line with the longest tail. The final LTS patch at the check date is 3.3.8 (10 June 2026), which adds JDK
26 support, the `// $COVERAGE-OFF$` markers, an `@uncheckedOverride` annotation and a `-Yfuture-lazy-vals` option that
produces lazy vals compatible with JDK 9 and later. The notes of 3.3.8 say that the next 3.3 release will include the
updates introduced up to the last 3.9.x before 3.10. See xref:programming-languages/scala/optional-braces-and-indentation.adoc[Optional Braces & Indentation]
and xref:programming-languages/scala/compiler-options-linting-and-errors.adoc[Compiler Options, Linting & Errors].

Sources: https://www.scala-lang.org/blog/2023/05/30/scala-3.3.0-released.html[Scala 3.3.0 released!], https://www.scala-lang.org/news/3.3.8/[Scala 3.3.8 LTS is now available!]

== 3.4.0 (29 February 2024) and the missing 3.3.2

Scala 3.4.0 and 3.3.3 were released the same day, and the announcement is the clearest statement of the split. 3.3.3
"focused solely on bug fixes and usability improvements" and keeps full binary and source compatibility (the team checked
that every one of more than a thousand projects that worked with 3.3.1 still worked with 3.3.3); 3.4.0 adds features and
deprecates legacy mechanisms. 3.3.2 does not exist on the all-versions page: a bug in the TASTy reader made it emit TASTy
files incompatible with 3.3.0 and 3.3.1, so the release was abandoned and users were told to bump to 3.3.3.

The changes of 3.4 are three groups:

* *Stabilised SIPs:* SIP-54 (multi-source extension overloads: extension methods with the same name imported from
  different sources), SIP-53 (a more expressive type-variable syntax in quote patterns, so `+case '[ (t, t, t) ]+` matches
  a three-element tuple) and SIP-56 (a proper specification for match types, which means some previously accepted match
  types are now illegal).
* *Type inference:* `+foldRight((Nil, Nil))(...)+` now infers `(List[T], List[T])`, polymorphic lambdas may omit parameter
  types, and the compiler no longer synthesizes `given` definitions that loop. Polymorphic lambdas compile to JVM lambdas.
* *Deprecations.* This is the release that made legacy syntax warn: `+_+` as a type wildcard, `private[this]`, `+var x = _+`,
  `with` as a type operator, `+xs: _*+` varargs and a trailing `+_+` to force eta expansion, and refutable patterns in a `for`
  generator need an explicit `case`. The 3.9 migration section gives the rewrite: `-rewrite -source:3.4-migration`.

The `with` type operator is the clearest example, because it is one of the few deprecations that was later promoted to an
error. This file uses it for an intersection type:

[source,scala]
----
trait Named { def name: String }
trait Aged { def age: Int }

def describe(x: Named with Aged): String = s"${x.name} (${x.age})"

@main def withty(): Unit =
  val p = new Named with Aged { val name = "Ana"; val age = 41 }
  println(describe(p))
----

On 3.3.8 it compiles without a message and prints `Ana (41)`. On 3.4.3, and unchanged on 3.9.0, it prints a warning and
still runs:

[source,text]
----
-- [E003] Syntax Warning: withty.scala:4:22
4 |def describe(x: Named with Aged): String = s"${x.name} (${x.age})"
  |                      ^^^^
  |with as a type operator has been deprecated; use & instead
  |This construct can be rewritten automatically under -rewrite -source 3.4-migration.
  |
1 warning found
Ana (41)
----

On 3.10.0 the same text is reported as an error and compilation fails:

[source,text]
----
-- [E003] Syntax Error: withty.scala:4:22
4 |def describe(x: Named with Aged): String = s"${x.name} (${x.age})"
  |                      ^^^^
  |with as a type operator has been deprecated; use & instead
  |This construct can be rewritten automatically under -rewrite -source 3.4-migration.
  |
1 error found
Compilation failed
----

Note that only `Named with Aged` as a type is affected: the `+new Named with Aged { ... }+` expression is the ordinary
mixin syntax and was not flagged by any of the three compilers. The progression warning in 3.4, still a warning in 3.9,
error in 3.10 is the timeline that
xref:programming-languages/scala/incompatibilities-and-dropped-features.adoc[Incompatibilities & Dropped Features] and
xref:programming-languages/scala/upgrading-between-scala-3-versions.adoc[Upgrading Between Scala 3 Versions] repeat for the other
features.

Other items of the 3.4 notes, not run here: the improved message for an incompatible TASTy version, which now says which
Scala version produced the file and which to use, a similar message for broken class files that points at the JDK
compatibility of your Scala version, compilation progress in IDEs, exporting diagnostics (including unused warnings) to
SemanticDB, the ported JVM backend parallelization, and the experimental `@publicInBinary` annotation that SIP-52
stabilised in 3.7.

Source: https://www.scala-lang.org/blog/2024/02/29/scala-3.4.0-and-3.3.3-released.html[Scala 3.4.0 and 3.3.3 LTS released!]

== 3.5.0 (22 August 2024)

3.5.0 made Scala CLI part of the Scala distribution. The `scala` command installed by a package manager became the Scala
runner implemented by Scala CLI (SIP-46): it compiles, runs, tests, packages and publishes single-module projects, with
`//> using` directives and toolkits built in. On the Scala 3.10.0 distribution used for this page, the command reports:

[source,text]
----
$ scala --version
Scala code runner version: 1.17.1
Scala version (default): 3.10.0
----

This is the biggest shift for the first chapter of any Scala book: the `scala` program that older books describe runs a
class from a classpath (`+scala -classpath ...+`), while today it runs source files. See
xref:programming-languages/scala/scala-cli.adoc[Scala CLI]. Coursier 2.1.10 or later is needed to install it.

Other changes in 3.5:

* *Binary integer literals* (SIP-42): `0b1000_0010` is 130. The probe is one line, `println(0b1000_0010)`: on 3.4.3 it
  does not compile (`+',' or ')' expected, but identifier found+`, with the caret under `b1000_0010`) and on 3.5.2 it prints
  `130`.
* *Best-effort compilation* (experimental): the compiler writes BETASTy files for code that does not compile, so Metals
  can keep offering IDE features while you type; enabled in Metals by `-Dmetals.enable-best-effort=true`.
* *Pipelined builds,* enabled in sbt with `ThisBuild / usePipelining := true`, for faster multi-module compilation.
* *`var` in type refinements:* `+type A = { var number: Int }+` is legal.
* *Named tuples* (SIP-58) arrived as an experimental feature behind `import scala.language.experimental.namedTuples`; they
  became stable in 3.7. This probe is the experimental form:

[source,scala]
----
import scala.language.experimental.namedTuples

@main def ntuple(): Unit =
  val p = (x = 1, y = 2)
  println(p.x + p.y)
----

On 3.4.3 the import itself is reported (`value namedTuples is not a member of object language.experimental`) and so are
`Not found: x` and `value x is not a member of (Unit, Unit)`. On 3.5.2 and on 3.7.4 the program prints `3`.

* *New givens and context bounds syntax* (SIP-64, experimental in 3.5, stable in 3.6.2) and *a new modularity* proposal
  (`-language:experimental.modularity` with `-source:future`, still experimental; it adds the `Self` type member and
  `is`).
* *An announcement of the given prioritization change,* introduced as warnings in 3.6 and in force from 3.7.

Source: https://www.scala-lang.org/blog/2024/08/22/scala-3.5.0-released.html[Scala 3.5.0 released!]

== 3.6.2 (10 December 2024) and the 3.6.0 accident

3.6.0 and 3.6.1 should never be used. While 3.6.0-RC1 was being released an accident published artifacts versioned as
3.6.0 to the immutable Maven repository, so 3.6.1 was released as a hotfix to stop automatic tooling from using the
broken version, and 3.6.2 is "effectively 3.6.0 for all intents and purposes". The all-versions page lists 3.6.2 as the
first 3.6 release, and a project that must pin 3.6 pins 3.6.2 or later (3.6.4 exists).

The 3.6 line is the one that changed how a type class instance is written:

* *SIP-64, the new syntax for context bounds and givens.* `given Order[Int]:` replaces `given Order[Int] with`, a
  conditional given is written `+given [T: Order] => Order[List[T]]:+` or `+given (config: Config) => Factory = ...+`, context
  bounds can be named and aggregated (`+T: {Order as o, Show}+`), and abstract context bounds on type members use
  `compiletime.deferred`. The probe is the simplest form:

[source,scala]
----
trait Show[T]:
  def show(t: T): String

given Show[Int]:
  def show(t: Int): String = s"int:$t"

@main def given36(): Unit = println(summon[Show[Int]].show(7))
----

On 3.5.2 it fails (`+an identifier expected, but 'def' found+` and `Declaration of given instance Show not allowed here:
only classes can have declared but undefined members`); on 3.6.2 and on 3.10.0 it prints `int:7`. The old `given Show[Int]
with` form still compiles. See xref:programming-languages/scala/givens-and-using-clauses.adoc[Givens & Using Clauses] and
xref:programming-languages/scala/context-bounds-and-deferred-givens.adoc[Context Bounds & Deferred Givens].

* *SIP-47, clause interleaving:* type and term parameter clauses can be interleaved (`+def getOrElse(k: Key)[V >: k.Value](default: V): V+`),
  which helps path-dependent APIs. See xref:programming-languages/scala/currying-and-parameter-lists.adoc[Currying & Parameter Lists].
* *SIP-56 amendment:* match type extractors follow aliases and singleton types.
* *Experimental in 3.6.2:* SIP-62 (better fors, aliases at the start of a `for`) and SIP-57 (`runtimeChecked`), both stable
  in 3.8.
* *Context bounds now desugar to `using` parameters* instead of implicit ones, which can change implicit resolution and
  affects macros and compiler plugins that inspect argument lists by flag; Java-defined annotations with more than one
  parameter require named arguments.

Source: https://www.scala-lang.org/news/3.6.2/[Scala 3.6.2 is now available!]

== 3.7.0 (7 May 2025)

3.7.0 stabilised two SIPs, introduced the idea of a preview feature and changed given resolution.

*SIP-58, named tuples,* became stable: they give names to tuple elements for construction, destructuring and pattern
matching, they allow matching a subset of case-class fields by name, and `Selectable` gained a `Fields` type member
that can be a named tuple so that structural types can be computed without macros. The program of 3.5 above, without the
import, is the stable form:

[source,scala]
----
@main def ntuple(): Unit =
  val p = (x = 1, y = 2)
  println(p.x + p.y)
----

It fails on 3.5.2 (`Not found: x`, `Not found: y`, `value x is not a member of (Unit, Unit)`) and prints `3` on 3.7.4 and on
3.10.0. See xref:programming-languages/scala/tuples-and-named-tuples.adoc[Tuples & Named Tuples].

*SIP-52, binary APIs.* `@publicInBinary` is stable. It lets an `inline` method access a non-public member without the
compiler generating an accessor that is not subject to binary compatibility, and it allows an inline method to call a
private constructor. `-WunstableInlineAccessors` (available since 3.4.0) reports the accessors that are generated.

*Preview features.* 3.7 introduced a stage between experimental and stable: "fully implemented and SIP-approved, but
potentially subject to small refinements before becoming stable". Preview features are guaranteed to be standardised in a
future minor release, may change in small and possibly binary incompatible ways, and are discouraged in published
libraries; the `-preview` compiler option enables all of them at once. The first one was SIP-62, better fors. Without the
option, 3.7.4 rejects it, and with the option it works:

[source,scala]
----
@main def bf(): Unit =
  val r = for
    a = 1
    b <- Some(2)
  yield a + b
  println(r)
----

----

  |      '<-' expected, but '=' found
-- [E007] Type Mismatch Error: bf.scala:3:9

(The `+...+` stands for two lines of the compiler's note about implicit conversions.) The `-preview` flag is the one that
Scala 3.10 uses for its three preview SIPs, and the page on
xref:programming-languages/scala/language-evolution-sips-preview-and-experimental.adoc[Language Evolution: SIPs, Preview & Experimental]
explains the whole experimental, preview, stable path.

*Experimental in 3.7:* SIP-61 (`@unroll`) and SIP-68 (referenceable package objects). Both became preview features in 3.10.

*The given prioritization change.* Announced in 3.5 and warned about in 3.6, the new rule applies from 3.7: given search
now picks the most general instance that satisfies the request instead of the most specific one. The probe uses a
covariant type class and asks for `Pick[Animal]` when both `Pick[Animal]` and `Pick[Dog]` are available:

*Explicit arguments for implicit parameters.* From 3.7 the compiler warns when an argument is passed to an `implicit`
parameter list without `using`:

[source,scala]
----
def scale(x: Int)(implicit factor: Int): Int = x * factor

@main def explicit2(): Unit =
  println(scale(10)(3))
----

which `-rewrite -source:3.7-migration` fixes.

Other items from the release notes, not run here: the expression compiler behind the Metals and IntelliJ debug consoles
moved into the compiler repository, the presentation compiler shows the expected type of a type hole on hover, the
experimental subset of the Quotes API gained `apply` methods for import selectors and `summonIgnoring`, and
the standard library moved to 2.13.16, where `.tail` and `.init` on the empty string throw instead of returning it.

== 3.8.0 (January 2026)

3.8 is the release that modernises the foundations. The announcement is dated 22 January 2026 and carries a warning
that is part of the history: a runtime regression was detected after 3.8.0 was published (JVM linkage errors at runtime
that could affect Scala 3 users who execute Scala 2.13 libraries and uses of specialized members of the standard
library), so "please use Scala 3.8.1 instead"; two further bugs in 3.8.0 and 3.8.1 (incorrect behaviour of some `for`
comprehensions and a compile failure with some Java standard library calls) were announced as fixed in 3.8.2, released
on 24 February 2026. That is why this section tells you to use 3.8.2 or later; the last 3.8 release is 3.8.4 (5 June
2026), which includes fixes from the security audit of the Scala codebase (hardened TASTy parsing, a Scaladoc XSS fix).

What 3.8 changed:

* *JDK 17 is required* to compile and run. The reason given is JDK 26 and later, which restrict the `sun.misc.Unsafe`
  functionality that the old lazy-vals implementation used; the lazy vals now use `VarHandle`. 3.3 LTS continues to
  produce JDK 8 bytecode, and the notes recommend 3.3.8 and its `-Yfuture-lazy-vals` flag for libraries that must support
  an older JVM.
* *The standard library is compiled with Scala 3.* It is the same API as 2.13, and the release is binary compatible, but
  the context bounds in library classes now desugar to `given` instead of `implicit`, which makes explicit arguments
  need `using`. The probe is `Array.empty(ClassTag.Int)`:

[source,scala]
----
import scala.reflect.ClassTag

@main def ctag(): Unit =
  val xs = Array.empty(ClassTag.Int)
  println(xs.length)
----

[source,text]
----

-- Warning: ctag.scala:4:32

  |                       ^^^^^^^^^^^^
  |Implicit parameters should be provided with a `using` clause.
  |This code can be rewritten automatically under -rewrite -source 3.7-migration.
  |To disable the warning, please use the following option:
  |  "-Wconf:msg=Implicit parameters should be provided with a `using` clause:s"
1 warning found
0
### scala 3.8.4 ctag.scala
-- [E172] Type Error: ctag.scala:4:22
4 |  val xs = Array.empty(ClassTag.Int)
  |                      ^
  |                      No ClassTag available for T
  |
  |                      where:    T is a type variable
1 error found

----

The fix is `Array.empty(using ClassTag.Int)` or, better, `Array.empty[Int]`. The migration is the reason that the notes
recommend running 3.7.4 with `-source:3.7-migration -rewrite` before the bump. This is also the boundary at which Scala
2.13's `-Ytasty-reader` stops being able to read Scala 3 libraries (it works up to 3.7), and at which
`scala.reflect.runtime.universe` can fail when initialised against the Scala 3 standard library, the best-known case being
Apache Spark; both are covered in xref:programming-languages/scala/upgrading-between-scala-3-versions.adoc[Upgrading Between Scala 3 Versions].
* *`App` is deprecated.* `trait App` has been deprecated since 3.8.0; on 3.10.0 and on 3.9.0 `object Main extends App:` with
  `-deprecation` prints `trait App in package scala is deprecated since 3.8.0: Support for trait App is deprecated in Scala 3`
  and the program still prints its output. Use `@main`, see
  xref:programming-languages/scala/hello-world-and-main-methods.adoc[Hello World & @main Methods].
* *The REPL is a separate artifact* (`scala3-repl`) rendered with fansi and pprint, so long values no longer dump as one
  unreadable line.
* *SIP-62, better fors, is stable.* Aliases may start a `for`, and a final `map` is omitted when it would be the identity
  (see the probe in 3.7). 3.8.2 added a warning for a `for` with several `val` bindings and an overloaded `map`, because
  the result type can change: the 3.8.2 notes show a `Map` iterated with two aliases that yields
  `List((43,29), (43,30), (43,31))` on 3.7 and `+Map(43 -> 31)+` on 3.8.
* *SIP-57, `runtimeChecked`, is stable.* It replaces the `: @unchecked` ascription:

[source,scala]
----
@main def rc(): Unit =
  def port(name: String): Option[Int] = if name == "http" then Some(80) else None
  val Some(p) = port("http").runtimeChecked
  println(p)
----

On 3.7.4 the compiler reports `method runtimeChecked is marked @experimental` and on 3.8.4 the program prints `80`.

* *`into` in preview* (SIP-71, see 3.9). On 3.8.4 the compiler stops with `type into is marked @preview` and
  `Preview definition may only be used when compiling with the -preview compiler flag` unless `-preview` is passed.
* *Experimental additions:* SIP-67 (strict equality pattern matching), SIP-70 (flexible varargs, `multiSpreads`), SIP-75
  (single-line lambdas after `:`, `relaxedLambdaSyntax`), match expressions with sub-cases, and, from 3.8.3, a `safe` mode
  for capability-safe code. 3.8 also opened a feature freeze for 3.9: "any codebase using Scala 3.8 should not require any
  additional changes to use Scala 3.9 LTS".
* *3.8.3 (31 March 2026)* added the optional Scala 2 bytecode optimizer (`-opt`, `-opt-inline`) and local coverage exclusions
  with `// $COVERAGE-OFF$`. 3.8.4 added `:help` for every compiler setting (for example `-Wunused:help`).
* *Tooling floors named in the notes:* sbt 1.11.5 minimum and 1.12.0 recommended, Scala CLI 1.9.0 minimum and 1.11.0
  recommended, Mill 1.0.5 minimum, scalafmt 3.10.1 minimum, Metals 1.6.4 recommended.

Sources: https://www.scala-lang.org/news/3.8/[Scala 3.8 released!], https://www.scala-lang.org/news/3.8.2/[Scala 3.8.2], https://www.scala-lang.org/news/3.8.3/[Scala 3.8.3], https://www.scala-lang.org/news/3.8.4/[Scala 3.8.4]

== 3.9.0 LTS (3 September 2026)

3.9.0 opens the new LTS. It "succeeds Scala 3.3 LTS as the recommended baseline for library authors and conservative
production users", it is guaranteed to be maintained for at least three years, and 3.3 LTS stays actively maintained for
one year after 3.9.0 (3.3.9 is planned within a month of the announcement). Because the feature freeze held, 3.9 has the
same feature set as 3.8 apart from what was promoted. Library authors should read one sentence of the announcement as a
rule: artifacts built with 3.9 cannot be consumed by Scala 3.3 projects, so moving from 3.3 LTS to 3.9 LTS is a
minor-version publishing decision for the libraries you maintain. The notes give the Open Community Build numbers behind
the migration: about 1,780 of nearly 2,000 projects build on 3.9 with no or minimal changes.

* *SIP-71, `into`, is stable.* It marks selected parameters or types as accepting implicit conversions without an
  `import scala.language.implicitConversions` at the call site. The probe (3.8 and 3.9 notes) is:

[source,scala]
----
import scala.Conversion.into

def concat[A](xs: List[A], ys: into[IterableOnce[A]]): List[A] = xs ++ ys

given Conversion[Array[Int], IterableOnce[Int]] = _.iterator

@main def intoDemo(): Unit =
  println(concat(List(1, 2), Array(3, 4)))
----

3.7.4: `type into is marked @experimental`. 3.8.4 without `-preview`: `type into is marked @preview`. 3.8.4 with `-preview`
and 3.9.0 without any flag: `List(1, 2, 3, 4)`. See
xref:programming-languages/scala/conversions-into-and-implicit-resolution.adoc[Conversions, into & Implicit Resolution].

* *Documentation snippets can declare the errors they expect.* Scaladoc compiles the snippets it finds in documentation, and
  3.9 lets a snippet mark the lines that must fail with `// error` and the warnings with `// warn`; every diagnostic must
  be accounted for. See xref:programming-languages/scala/scaladoc.adoc[Scaladoc].
* *Scala CLI updates:* the REPL can start JShell (`scala repl --jshell`), tests can use JUnit 5, `export` can target sbt
  2, WebAssembly is supported experimentally, Ammonite support is dropped, and experimental built-in support for Sloth
  rewrites dependencies compiled with the old lazy val bytecode.
* *Scala.js 1.22.0 is bundled,* and its WebAssembly backend is stable (it targets a JavaScript host such as Node.js, Deno,
  Bun or a browser). The Scala.js version is fixed for the whole 3.9 LTS line because the backend is part of the compiler.
* *Inaccessible companion implicits are deprecated.* A given defined in a private companion object is no longer an
  eligible instance at the call site, because the specification has always required that an eligible implicit be
  accessible. 3.9 reports every such resolution under `-deprecation`, and 3.10 stops finding them. The probe:

----

@main def companion(): Unit =

* *The 3.3 to 3.9 summary.* The announcement summarises each minor between 3.3 and 3.9 (breaking changes, new stable
  features, notable changes) and a recommended upgrade order: build tool first, then JDK 17 or later on the current Scala
  version, then Scala.js, then Scala, then libraries. The list of `-source:3.x-migration` rewrites to apply in order is the
  core of xref:programming-languages/scala/upgrading-between-scala-3-versions.adoc[Upgrading Between Scala 3 Versions].

On 3.9, the older preview and experimental gates matter in a way that is easy to forget when reading 3.10 material: the
three features that are preview features in 3.10 were still experimental in 3.9. `@unroll` on 3.9.0 is rejected with
`class unroll is marked @experimental: under review as part of SIP-61` and needs `-experimental` (or an experimental
import), after which the same program prints `Hello, Ana!`; SIP-75 (`+xs.map: v => v + 1+`) fails on 3.9.0 with `not a legal formal parameter for a function literal`, and referenceable
package objects fail too, as the next section shows.

== 3.10.0 (12 October 2026)

3.10.0 is the first release of the Scala Next series that follows 3.9 LTS, and the first release that removes legacy
features. Binary compatibility is preserved (libraries compiled with earlier Scala 3 versions keep working, including those
that used features now removed), but source that still uses the removed features must be updated. Because cross-compilation
between Scala 2 and 3.10 is no longer supported, the notes expect cross-compiled libraries to stay on 3.9 LTS
indefinitely; check a 3.10 artifact with MiMa 1.2.1 or later, which adds 3.9 and 3.10 support.

*Stable:* SIP-67. Under `strictEquality`, `x == y` still needs a `CanEqual`, but `match` on an enum or case object no longer
does. The probe:

[source,scala]
----
import scala.language.strictEquality

enum Foo:
  case Bar
  case Baz(f: Int => Int)

def eval(x: Foo): Int = x match
  case Foo.Bar    => 0
  case Foo.Baz(f) => f(0)

@main def strictDemo(): Unit = println(eval(Foo.Baz(_ + 1)))
----

On 3.7.4 and on 3.9.0 it fails with `Values of types Foo and Foo cannot be compared with == or !=` (under the `case Foo.Bar`
pattern); on 3.10.0 it prints `1`. See xref:programming-languages/scala/pattern-matching.adoc[Pattern Matching] and
xref:programming-languages/scala/multiversal-equality.adoc[Multiversal Equality].

*Preview features (`-preview`).* SIP-61 (`@unroll`), SIP-75 (relaxed lambda syntax) and SIP-68 (referenceable package
objects) moved from experimental to preview, and the experimental language imports that previously gated them are
deprecated. SIP-74 (partial function literals with parentheses) is a fourth preview feature on 3.10.0: the SIP page says
it is a preview feature in 3.10.0 and will be on by default in the next minor release, although the SIP list calls it
"shipped" and the reference's preview index does not list it yet. Three probes, each compiled without and with the flag:

[source,scala]
----
@main def relaxed(): Unit =
  val xs = Option(2)
  val ys = xs.map: v => v + 1
  println(ys)
----

[source,text]
----
### scala 3.10.0 relaxed.scala
-- Error: relaxed.scala:3:11
3 |  val ys = xs.map: v => v + 1
  |           ^^^^^^^^^
  |           not a legal formal parameter for a function literal
-- [E006] Not Found Error: relaxed.scala:3:24
3 |  val ys = xs.map: v => v + 1
  |                        ^
  |                        Not found: v
2 errors found
Compilation failed
### scala 3.10.0 relaxed.scala -preview
Some(3)
----

The same probe with `package lib` and `package object json` (a `val api = lib.json` that treats the package object as a
value) fails on 3.9.0 with `package lib.json is not a value`, on 3.10.0 with `Preview package object values may only be
used when compiling with the -preview compiler flag`, and prints `42` on 3.10.0 with `-preview`. The SIP-74 probe
`+xs.collect(case (a, b) if b > 2 => a)+` fails on 3.9.0 and on 3.10.0 with `expression expected but case found` and prints
`List(3)` with `-preview`. `@unroll` behaves differently: on 3.10.0 the one-parameter probe compiled and printed
`Hello, Ana!` without the flag, which is the same observation recorded in
xref:programming-languages/scala/versions-compatibility-and-jdks.adoc[Versions, Compatibility & JDKs]; pass `-preview`
anyway.

*Breaking changes.* The notes list them; the ones demonstrated here:

* `A with B` as a type is an error (probe in 3.4 above); `-source:3.4-migration -rewrite` rewrites it to `A & B`, and in
  typed patterns the intersection must be parenthesised (`+case x: (A & B) =>+`).
* Givens in inaccessible companions are no longer found (probe in 3.9 above).
* `this` is illegal in top-level definitions. `val self = this` at the top of a file prints `ok` for the rest of the
  program on 3.9.0 and fails on 3.10.0:

[source,text]
----
-- Error: toplevelthis.scala:1:11
1 |val self = this
  |           ^^^^
  |           Top-level definitions cannot refer to this
1 error found
----

* The primitive `+Rich*+` wrappers (`runtime.RichInt` and the others) are gone: `until`, `to`, `abs` and `max` are extension
  methods in the companions of `Int`, `Long` and the other primitive types, and `+a -> b+` is an inline extension method;
  `Predef.ArrowAssoc` is deprecated and no longer an implicit conversion. A DSL that defines `+->+` through an implicit
  class should change it to an extension method. Macros that inspect the old trees need updating; ZIO 2.1.26 and other
  macro-heavy libraries published releases for that reason.
* Java generic signatures use boxed types for primitive type arguments, so MiMa may report `IncompatibleSignatureProblem`
  when you republish, and `-Xmax-fuel` replaces catching `StackOverflowError`: very deep types now report `Recursion limit
  exceeded` (default fuel 550) and may need `-Xmax-fuel` and `-Xss`. See
  xref:programming-languages/scala/compiler-options-linting-and-errors.adoc[Compiler Options, Linting & Errors].

*New in the language and library.* Java records can be used as extractor patterns, `\s` is a string escape for a space, and
`IArray` has `Factory`, `IsSeq` and `BuildFrom` instances. The two probes:

[source,text]
----
### scala 3.9.0 sesc.scala
-- Error: sesc.scala:2:13
2 |  println("a\sb")
  |             ^
  |             invalid escape character
1 error found
### scala 3.10.0 sesc.scala
a b
a\sb
----

(The second line is `println(raw"a\sb")`, where `raw` keeps the two characters.) For the record pattern, a `Point.java`
holding `+public record Point(int x, int y) {}+`, compiled with `javac` and put on the class path, and the program
`+Point(3, 4) match case Point(x, y) => println(s"point $x,$y")+` fail on 3.9.0 (`Point cannot be used as an extractor in a
pattern because it lacks an unapply or unapplySeq method with the appropriate signature`) and print `point 3,4` on 3.10.0.
See xref:programming-languages/scala/using-java-from-scala.adoc[Using Java from Scala].

*Tools in 3.10.* The distribution bundles Scala CLI 1.17.1 (Java instance main methods without a class on JDK 25 and later,
`//> using resource`, and the `lts` version tag resolving to the 3.9 series), the REPL accepts `//> using dep`, `//> using
toolkit` and `//> using jar` directives and gained `:save` and `:replay`, and Scala is now also published as `.deb` and
`.rpm` packages. Scala CLI, the REPL and the packages are described in
xref:programming-languages/scala/scala-cli.adoc[Scala CLI] and xref:programming-languages/scala/installing-scala.adoc[Installing Scala];
the REPL additions come from the release notes only and were not run here.

*What is next.* The notes say that 3.10.1 has its release branch cut and 3.10.2 will follow, and that development then moves
to 3.11, expected around March or April 2027. 3.9 LTS remains the recommended publishing baseline.

Source: https://www.scala-lang.org/news/3.10/[Scala 3.10 released!], https://docs.scala-lang.org/sips/74.html[SIP-74]

== Which version to use

A short decision list, taken from the release notes and the compatibility page:

* *Publishing a library:* 3.9 LTS (3.9.0 or the latest 3.9 patch). Stay on 3.3 LTS only while your users are stuck on it,
  and never compile with a Scala Next release unless you rely on a feature that exists only there.
* *Writing an application:* 3.10 (Scala Next), or 3.9 LTS for the most conservative path. Any Scala 3 minor can be mixed
  with libraries built by an older Scala 3 minor, but not the other way round.
* *On JDK 8 or 11:* 3.3.8 LTS or 3.7.4. From 3.8 on, JDK 17 or later is required.
* *With Scala 2.13 consumers of your Scala 3 library:* stay on 3.7 or earlier, or publish a 2.13 artifact, because the TASTy
  reader of 2.13 cannot read libraries built by 3.8 or later.
* *Never:* 3.6.0 and 3.6.1, which should never be used, and 3.8.0 and 3.8.1, which had regressions; 3.3.2 does not exist.

== Pitfalls

* Reading a date from Maven Central instead of the announcement. Artifacts are published days before the news item (3.9.0
  on 26 August 2026 against the announcement of 3 September 2026), so a table built from repository timestamps disagrees
  with the official dates.
* Running an old compiler on a new JDK. The 3.1.3 compiler on JDK 26 stops with "class file ... is broken" for the JDK's own
  classes; use the JDK that matches the compiler (17 for 3.1 to 3.7 in the probes here), and use JDK 17 or later from 3.8.
* Treating "deprecated" as "removed". `Traversable`, `Stream` and `CanBuildFrom` still compile on 3.10.0, with
  warnings; `A with B` and a given in an inaccessible companion do not. The warning release and the error release are
  different, and the table of the 3.9.0 notes is the way to see which is which.
* Treating a preview feature like a stable one. `-preview` features can change incompatibly before they are stabilised,
  and are discouraged in published libraries; a library that needs one should say so in its documentation.
* Taking the experimental import for the preview flag. On 3.10 the old experimental imports for the three promoted
  features are deprecated and point to `-preview`; the `-experimental` flag is a different, much wider switch that
  also opts everything marked `@experimental` into your build.
* Upgrading libraries before the compiler. A newer library may need a newer compiler; the recommended order is build tool,
  JDK, Scala.js, Scala, then libraries.
* Believing a tutorial about the Toolkit. The official tutorial pages show Toolkit 0.7.0, sttp 4.0.0-RC1 and uPickle 4.1.0
  while 0.9.2 is current. Likewise, a book that starts programs with `App` predates its deprecation in 3.8.0.
