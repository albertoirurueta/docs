Scala has one collections library that every program uses, with a deliberately small set of ideas: a few abstract traits
describe *what* a collection can do (`Iterable`, `Seq`, `Set`, `Map`), concrete classes decide *how* (`List`, `Vector`,
`HashSet`, `TreeMap`, ...), and a single decision, immutable or mutable, is made by choosing a package. The examples use the
trailhead scenario, a toolkit that plans hikes on a network of mountain trails.

== The three big ideas

* *Immutable by default.* `List`, `Vector`, `Set` and `Map` written without any import are the immutable ones. "Updating"
an immutable collection returns a new collection that shares most of its structure with the old one.
* *One uniform vocabulary.* Every collection supports the same operations (`map`, `filter`, `foldLeft`, `groupBy`, ...),
and the result type follows the receiver: mapping a `Vector` gives a `Vector`, mapping a `Set` gives a `Set`.
* *Interfaces first.* Declare parameters as `Seq`, `Set`, `Map` or `Iterable` and pick the implementation where the value is
built, as in Java's `List`/`ArrayList`.

== The hierarchy

image::scala-collections-hierarchy.svg["The Scala collections hierarchy: Iterable at the top with Seq, Set and Map below it, and the immutable and mutable concrete classes",width=960]

The trait hierarchy has three layers:

* `scala.collection` holds the *shared* abstract traits: `Iterable`, `Seq`, `IndexedSeq`, `LinearSeq`, `Set`, `SortedSet`,
`Map` and `SortedMap`. A method that only reads can accept these and works with both families.
* `scala.collection.immutable` holds the traits and classes that can never change after construction: `List`, `Vector`,
`Range`, `LazyList`, `Queue`, `HashSet`, `TreeSet`, `BitSet`, `HashMap`, `TreeMap`, `ListMap`, `VectorMap`, `ArraySeq`.
* `scala.collection.mutable` holds the in-place counterparts: `ArrayBuffer`, `ListBuffer`, `ArrayDeque`, `Queue`,
`StringBuilder`, `HashSet`, `LinkedHashSet`, `HashMap`, `LinkedHashMap`, `TreeMap`, `WeakHashMap`.

Every one of the facts in the next program is checked by the compiler; `summon[A <:< B]` only compiles when `A` is a subtype of
`B`, and `=:=` only when the two types are the same type.

[source,scala]
----
//> using scala 3.10.0
package trailhead

import scala.collection.{immutable as i, mutable as m}

@main def hierarchy(): Unit =
  summon[i.List[Int] <:< i.LinearSeq[Int]]
  summon[i.Vector[Int] <:< i.IndexedSeq[Int]]
  summon[i.Range <:< i.IndexedSeq[Int]]
  summon[i.LazyList[Int] <:< i.LinearSeq[Int]]
  summon[m.ArrayBuffer[Int] <:< m.Buffer[Int]]
  summon[m.ArrayBuffer[Int] <:< m.IndexedSeq[Int]]
  summon[m.ListBuffer[Int] <:< m.Buffer[Int]]
  summon[i.TreeSet[Int] <:< i.SortedSet[Int]]
  summon[i.BitSet <:< i.SortedSet[Int]]
  summon[i.TreeMap[Int, Int] <:< i.SortedMap[Int, Int]]
  summon[m.Map[Int, Int] <:< scala.collection.Map[Int, Int]]
  summon[i.Map[Int, Int] <:< scala.collection.Map[Int, Int]]
  summon[Seq[Int] =:= i.Seq[Int]]
  println("every subtype fact compiled")
----

[source,text]
----
every subtype fact compiled
----

The last line of the program is the important one for newcomers: the plain `Seq` in scope is `immutable.Seq`.

=== What each abstract trait promises

[cols="2,5"]
|===
|Trait |Contract

|`Iterable`
|Can produce an `Iterator` and be traversed more than once. All the transformation methods are defined here.

|`Seq`
|An ordered collection with positions (`apply(i)`, `indexOf`, `sorted`, `reverse`). Two flavours: `IndexedSeq` (fast random access, such as `Vector`) and `LinearSeq` (fast `head` and `tail`, such as `List`).

|`Set`
|No duplicate elements; the main operation is membership (`contains`, also available as `apply`). A `Set[A]` is also a function `+A => Boolean+`.

|`Map`
|Keys mapped to values; each key appears once. A `Map[K, V]` is also a `PartialFunction[K, V]`, and iterating it yields `(K, V)` tuples.

|`SortedSet`, `SortedMap`
|Keep the elements or keys ordered according to an `Ordering` and offer range operations.

|`Buffer` (mutable only)
|A growable `Seq` with `pass:c[+=]`, `append`, `insert`, `remove` and friends.
|===

Under `scala.collection.mutable` the traits carry the same names (`mutable.Seq`, `mutable.Set`, `mutable.Map`) and add the
operations that change a collection in place. A `mutable.Map` is *not* a subtype of `immutable.Map`, and vice versa; both
extend `scala.collection.Map`.

== Default imports and the two meanings of Seq

A few names are available in every Scala file because `scala` and `Predef` are imported automatically: `List`, `Vector`, `Seq`,
`IndexedSeq`, `Iterable`, `Set`, `Map`, `Range`, `Nil`, `LazyList`, `StringBuilder`, `::` and `Option`. The collection
aliases in `scala` and `Predef` (`List`, `Seq`, `Set`, `Map`, `Vector`, `LazyList`, ...) point at the *immutable* versions;
`Iterable` and `Iterator` have no mutable flavour and point at `scala.collection`, and `StringBuilder` is the one mutable
name in scope. The factory `apply` methods choose a concrete class for you:

[source,scala]
----
//> using scala 3.10.0
package trailhead

@main def defaults(): Unit =
  val trails: List[String] = List("Ridge", "Falls", "Pass")
  val dist: Map[String, Double] = Map("Ridge" -> 12.5, "Falls" -> 4.0)
  println(trails)
  println(dist)
  println(Set(1, 2, 2, 3))
  println(Seq(1, 2, 3).getClass.getName)
  println(Iterable(1, 2).getClass.getName)
  println(Set(1, 2).getClass.getName)
  println(Map(1 -> 2).getClass.getName)
  println(Vector(1, 2).getClass.getName)
----

----

Source: https://docs.scala-lang.org/overviews/core/collections-migration-213.html#scalaseq-varargs-and-scalaindexedseq-migration[Scala 2.13 Collections: Migrating from 2.12, scala.Seq and scala.IndexedSeq]

Reading the output: `pass:c[Seq(...)]` and `pass:c[Iterable(...)]` build a `List` (the class `::` is the non-empty `List` cell, here shown as
`$colon$colon`); `Set` and `Map` with up to four entries use small specialised classes (`Set2`, `Map1`, ... `Set4`, `Map4`)
that store the elements in fields and keep *insertion order*; beyond four entries they switch to hash tries (`HashSet`,
`HashMap`) whose order is unspecified. Never rely on the iteration order of a plain `Set` or `Map`. When an order matters,
choose `ListMap`/`VectorMap`/`LinkedHashSet` (insertion order) or `TreeSet`/`TreeMap` (sorted order), described in
xref:programming-languages/scala/sets-and-maps.adoc[Sets & Maps].

To use the mutable versions, import them explicitly. The usual idiom keeps the package name visible so that no reader mistakes a
mutable collection for an immutable one:

[source,scala]
----
//> using scala 3.10.0
package trailhead

import scala.collection.mutable

def describe(xs: scala.collection.Iterable[Int]): String =
  xs.getClass.getSimpleName + " sum=" + xs.sum

@main def mutability(): Unit =
  val imm = Vector(3, 1, 2)
  val mut = mutable.ArrayBuffer(3, 1, 2)
  println(describe(imm))
  println(describe(mut))
  val more = imm :+ 4
  println(imm)
  println(more)
  mut += 4
  println(mut)
  val shared = mutable.Map("a" -> 1)
  val snapshot = shared.toMap
  shared("b") = 2
  println(snapshot)
  println(shared)
----

[source,text]
----
Vector1 sum=6
ArrayBuffer sum=6
Vector(3, 1, 2)
Vector(3, 1, 2, 4)
ArrayBuffer(3, 1, 2, 4)
Map(a -> 1)
HashMap(a -> 1, b -> 2)
----

`describe` accepts `scala.collection.Iterable`, so it takes both an immutable `Vector` and a mutable `ArrayBuffer`. The
immutable `pass:c[imm :+ 4]` leaves `imm` untouched and returns a new `Vector`; the mutable `pass:c[mut += 4]` changes the buffer itself.
`toMap` makes an immutable snapshot, which is the safe way to hand out the contents of a mutable map.

Source: https://docs.scala-lang.org/scala3/book/collections-classes.html#three-main-categories-of-collections[Scala 3 Book: Three main categories of collections]

Because the plain `Seq` is `immutable.Seq`, handing a mutable collection to a method that expects `Seq` is a compile-time error,
and the compiler tells you why:

[source,scala]
----
//> using scala 3.10.0
import scala.collection.mutable

def takesSeq(xs: Seq[Int]): Int = xs.sum

@main def run(): Unit =
  val buf = mutable.ArrayBuffer(1, 2)
  println(takesSeq(buf))
----

[source,text]
----
-- [E007] Type Mismatch Error: c.scala:6:19
6 |  println(takesSeq(buf))
  |                   ^^^
  |               Found:    (buf : scala.collection.mutable.ArrayBuffer[Int])
  |               Required: Seq[Int]
----

Two ways out: accept `scala.collection.Seq` in the method (read-only access to anything sequence-like), or convert at the call
site with `buf.toSeq` (a copy). The rule of thumb from the library's authors is the same as for Java's `List` versus
`Collections.unmodifiableList`: a `Seq` parameter is a *promise* that nobody will change the collection underneath the method.

Source: https://docs.scala-lang.org/overviews/collections-2.13/overview.html#an-overview-of-the-collections-api[Collections 2.13: An overview of the collections API]

== Choosing a collection

Start from what the program does with the collection, then refine.

[cols="3,3,4",options="header"]
|===
|You need |Reach for |Why

|An ordered sequence, mostly processed with `map`, `filter`, folds
|`List`
|Cheap prepend and `head`/`tail`, ideal for recursion and pattern matching with `::`. Poor at indexing.

|An ordered sequence with fast indexing and updates, or you are not sure
|`Vector`
|Effectively constant time for `apply`, `updated`, append and prepend. The default general-purpose `Seq`.

|A growable sequence you fill in a loop
|`ArrayBuffer` (or `ListBuffer`)
|Amortised constant time append; convert with `toList`/`toVector` when done.

|A range of numbers or characters
|`Range` (`1 to 10`, `0 until n by 2`)
|Stores only start, end and step; use it in `for` loops and `map`.

|Fixed-size, primitive-speed storage, interop with Java arrays
|`Array`
|Maps to a JVM array; see <<_array_arrayseq_and_iarray>>.

|Unique elements, membership tests
|`Set` (`HashSet`)
|Fast `contains`; `TreeSet` when you need sorted iteration.

|Look up values by key
|`Map` (`HashMap`)
|Fast `get`; `TreeMap` for sorted keys; `VectorMap`/`LinkedHashMap` for insertion order.

|A FIFO or double-ended queue
|`Queue`, `ArrayDeque`
|`ArrayDeque` is the fast mutable choice for stacks, queues and deques.

|A possibly unbounded or expensive-to-compute sequence
|`LazyList`, `Iterator`, `.view`
|Elements are computed on demand; see xref:programming-languages/scala/views-iterators-and-lazylist.adoc[Views, Iterators & LazyList].

|Shared state across threads
|`scala.collection.concurrent.TrieMap`, or Java's `ConcurrentHashMap`
|Immutable collections are safe to share; mutable ones are not thread-safe. See xref:programming-languages/scala/sets-and-maps.adoc[Sets & Maps].
|===

Two guidelines cover most code. First, prefer the immutable collection and a `val`; if you need to change a value, create a
new one (`pass:c[val next = current :+ x]`) or keep an immutable collection in a `var` that is local and short-lived. Second, when you
do need mutation, build with a mutable collection or a `Builder` and publish the result as an immutable one:
`buffer.toList`, `map.toMap`, or `List.newBuilder[Int]` followed by `.result()`. The performance consequences of these
choices are tabulated in xref:programming-languages/scala/collection-performance-and-equality.adoc[Collection Performance & Equality].

== Array, ArraySeq and IArray

`Array[T]` is the JVM array with Scala syntax. It is the one collection that is *not* a `Seq`: it is mutable, fixed-size,
indexed with parentheses (`a(0)`), invariant in `T` and reified at run time, and the compiler uses an implicit conversion to
give it all the sequence operations. Three related types exist for specific needs:

* `ArraySeq` (`scala.collection.immutable.ArraySeq` and the mutable `scala.collection.mutable.ArraySeq`) wraps an array as a
real `Seq`. `ArraySeq.unsafeWrapArray(arr)` wraps *without copying*, so later changes to `arr` show through; that is what
the word "unsafe" warns about.
* `IArray[T]` is an *immutable array* added in Scala 3. At run time it is the same JVM array, but its type has no `update`
method, so it cannot be changed through the type. It is declared as an opaque type (see
xref:programming-languages/scala/opaque-types-and-value-classes.adoc[Opaque Types & Value Classes]) and is a Scala 3 only
feature, so it is unavailable on 2.13.
* `Seq` parameters accept an `Array` only through the deprecated copying implicit conversion `copyArrayToImmutableIndexedSeq`;
use `toIndexedSeq` (copy) or `ArraySeq.unsafeWrapArray` (no copy) explicitly.

[source,scala]
----
//> using scala 3.10.0
package trailhead

import scala.collection.immutable.ArraySeq

def total(xs: Seq[Int]): Int = xs.sum

@main def arrays(): Unit =
  val arr = Array(1, 2, 3)
  println(total(arr.toIndexedSeq))
  val wrapped = ArraySeq.unsafeWrapArray(arr)
  arr(0) = 10
  println(wrapped)
  val frozen = IArray(3, 1, 2)
  println(frozen.map(_ + 1).mkString(","))
  println(frozen.sorted.mkString(","))
  println(frozen.toList)
  println(frozen.getClass.getName)
  println(total(arr))
----

compiler:

[source,scala]
----
//> using scala 3.10.0

  val frozen = IArray(3, 1, 2)
  frozen(0) = 5
----

`IArray` is "immutable" only at the type level: someone holding the underlying `Array` (for example through
`asInstanceOf`) can still change it. Use it for the common case of a
local, read-only table of numbers where the speed of a primitive array matters; use `Vector` or `ArraySeq` otherwise. More
operations and the generic `ClassTag` requirement are covered in
xref:programming-languages/scala/sequences.adoc[Sequences].

== Converting to and from Java collections

Scala collections and Java collections are different class hierarchies, but `scala.jdk.CollectionConverters` provides cheap
*wrapper views* in both directions through `asScala` and `asJava`. The converters share the underlying data: no elements are
copied, and a change through one side shows through the other.

[source,scala]
----
//> using scala 3.10.0
package trailhead

import java.util.ArrayList
import scala.jdk.CollectionConverters.*

@main def javaInterop(): Unit =
  val jl = ArrayList[String]()
  jl.add("x")
  jl.add("y")
  val view = jl.asScala
  view += "z"
  println(jl)
  val back: java.util.List[Int] = List(1, 2, 3).asJava
  println(back.getClass.getName)
  try back.add(4)
  catch case e: UnsupportedOperationException => println("immutable on the Scala side")
  val jm = java.util.HashMap[String, Int]()
  jm.put("a", 1)
  println(jm.asScala.toMap)
----

[source,text]
----
[x, y, z]
scala.collection.convert.JavaCollectionWrappers$SeqWrapper
immutable on the Scala side
Map(a -> 1)
----

Appending to the Scala view changed the Java list; the `java.util.List` produced from an immutable Scala `List` throws on
every mutating call; and `asScala.toMap` takes an immutable snapshot of a Java map. The wildcard import `+*+` is the Scala 3
spelling (`+_+` in Scala 2). The older `scala.collection.JavaConverters` (implicit `.asScala` with a different import name) is
deprecated since 2.13.0 with the message "Use `scala.jdk.CollectionConverters` instead"; `JavaConversions`, which converted
*implicitly* without any `asScala` call, was removed in 2.13. See also
xref:programming-languages/scala/using-java-from-scala.adoc[Using Java from Scala] and
xref:programming-languages/scala/calling-scala-from-java.adoc[Calling Scala from Java].

Source: https://www.scala-lang.org/api/current/scala/jdk/CollectionConverters$.html[Scala API: CollectionConverters]

== Building collections and converting between them

Every collection companion has the same family of factories, and every collection can be converted with `to` and the
`toXxx` methods. The varargs parameter `+T*+` is an `immutable.Seq` (an `ArraySeq` when you splat an `Array` with `+arr*+`), and
`Traversable`, the old root of the hierarchy, is a deprecated alias of `Iterable`:

[source,scala]
----
//> using scala 3.10.0
package trailhead

def total(xs: Int*): Int = xs.sum
def kind(xs: Int*): String = xs.getClass.getName

@main def factories(): Unit =
  val arr = Array(1, 2, 3)
  println(total(arr*))
  println(kind(1, 2))
  println(kind(arr*))
  println(List(3, 1, 2).to(Vector))
  println(Vector.from(Set(1)))
  println(List.from(1 to 3))
  val t: Traversable[Int] = List(1)
----

== Equality across collection types

Equality is structural within a family: two sequences are equal when they have the same elements in the same order, whether
immutable or mutable, and likewise for sets and maps. Arrays are the exception, because they use Java reference equality:

[source,scala]
----
//> using scala 3.10.0
package trailhead

import scala.collection.mutable

@main def equality(): Unit =
  println(List(1, 2) == Vector(1, 2))
  println(Set(1, 2) == mutable.Set(2, 1))
  println(Map("a" -> 1) == mutable.Map("a" -> 1))
  println(Array(1, 2) == Array(1, 2))
  println(Array(1, 2).toSeq == Array(1, 2).toSeq)
----

[source,text]
----
true
true
true
false
true
----

Different families are never equal (a `List` is not a `Set`), and Scala 3 refuses to compile the comparison at all, because the
built-in check rejects `==` between unrelated types:

[source,text]
----
-- [E172] Type Error: eqbad.scala:3:10
3 |  println(List(1, 2) == Set(1, 2))
  |          ^^^^^^^^^^^^^^^^^^^^^^^
  |   Values of types List[Int] and Set[Int] cannot be compared with == or !=
-- [E172] Type Error: eqbad.scala:4:10
4 |  println(Seq(1, 2) == Array(1, 2))
  |          ^^^^^^^^^^^^^^^^^^^^^^^^
  |  Values of types Seq[Int] and Array[Int] cannot be compared with == or !=
----

Source: https://docs.scala-lang.org/overviews/collections-2.13/equality.html[Collections 2.13: Equality]

The rules behind this, and how to opt into the stricter `strictEquality` mode, are in
xref:programming-languages/scala/multiversal-equality.adoc[Multiversal Equality] and

== Comparison with Java and Kotlin

[cols="2,3,3,3",options="header"]
|===
|Aspect |Scala |Java |Kotlin

|Immutability
|`List`, `Set`, `Map` are immutable by default; mutable ones live in `scala.collection.mutable`.
|`List.of`, `Set.of` and `Map.of` give unmodifiable collections that still have mutating methods that throw at run time.
|Read-only interfaces (`List`) and mutable ones (`MutableList`) are different types, but a read-only `List` may be a mutable object underneath.

|"Updating"
|`updated`, `pass:c[+]`, `-`, `pass:c[:+]` return a new collection that shares structure.
|Copy (`List.copyOf`) or mutate in place.
|`pass:c[+]` and `-` operators return a copy; mutable lists mutate.

|Common root
|`Iterable` (and `scala.collection` read-only traits).
|`Iterable` and `Collection`; `Map` is separate.
|`Iterable` and `Collection`; `Map` is separate.

|Default `List`
|A singly linked list.
|`List` is an interface; the usual implementation is `ArrayList`.
|`List` is read-only, usually backed by `ArrayList`.

|Transformations
|Strict methods on the collection (`map`, `filter`); lazy via `.view`.
|`Stream` pipelines (`pass:c[stream().map(...).toList()]`).
|Strict extension functions; lazy via `asSequence()`.

|Variance
|Declared on the type: `pass:c[List[+A\]]` is covariant.
|Use-site wildcards, `List<? extends Gear>`.
|Declaration-site `out`/`in`, `List<out E>`.

|Arrays
|`Array[T]` is invariant and not a `Seq`; an implicit conversion adds operations.
|Arrays are covariant (and unsound), with only `Arrays` helpers.
|`Array<T>` is invariant, with extension functions.
|===

The Java page covers `Optional` and lambdas in xref:programming-languages/java/optional.adoc[Optional] and
xref:programming-languages/java/lambdas-and-method-references.adoc[Lambdas & Method References]; Scala's `Option` is the
subject of xref:programming-languages/scala/option-and-null-safety.adoc[Option & Null Safety], and Kotlin's counterpart to
`Seq` and coroutine flows starts at xref:programming-languages/kotlin/coroutines-basics.adoc[Coroutines Basics]. Java's
virtual threads (xref:programming-languages/java/virtual-threads.adoc[Virtual Threads]) do not change collection thread safety:
a plain `HashMap` still needs synchronisation in Scala, Java and Kotlin alike.

== Common pitfalls

* Expecting `Seq` to be mutable, or passing an `ArrayBuffer` to a `Seq` parameter (error E007, shown above).
* Relying on the iteration order of a `Set` or `Map` with more than four entries. It is unspecified and can change between
library versions.
* Calling `pass:c[+=]` on a `val` immutable collection: the compiler reports `pass:c[value += is not a member of List[Int\]]`. Either use a
mutable collection, or a `var` with `pass:c[xs :+= x]`, or build a new collection.
* Forgetting that `Array` equality is by reference, and that `println(array)` prints an identity string.
* Mutating a collection while iterating it: for mutable collections the result is unspecified. Iterate over `copy` or use
`filterInPlace`, `mapInPlace` and friends.
* Holding on to a `mutable` collection from a long-lived object and returning it from a public method; return an immutable
copy instead.

== Where the books are outdated

* Scala 2.12 and earlier material describes `scala.Seq` as `scala.collection.Seq`, so a mutable `ArrayBuffer` could be passed to
a `Seq` parameter. Since 2.13 the default `Seq` is immutable, so that code no longer compiles.
* `Traversable`, `TraversableOnce`, `Stream` (replaced by `LazyList`), `JavaConversions` and `JavaConverters` appear in older material and in StackOverflow
answers. `Traversable`, `TraversableOnce`, `Stream` and `JavaConverters` are deprecated since 2.13.0; `JavaConversions` was removed. `mutable.Stack` was deprecated in 2.12 but
was reimplemented and is no longer deprecated in 2.13 (it compiles without a warning on 3.10.0).
* `mapValues` and `filterKeys` on a `Map` used to return live views. In 2.13 they are deprecated in favour of
`.view.mapValues(f).toMap`, described in xref:programming-languages/scala/sets-and-maps.adoc[Sets & Maps].
* Descriptions of the 2.8 to 2.12 library mention `CanBuildFrom`; it was replaced by `Factory` and `BuildFrom`, covered in
xref:programming-languages/scala/collections-architecture-and-custom-collections.adoc[Collections Architecture & Custom Collections].
* Books for Scala 2 show `import scala.collection.JavaConverters._` and `+_+` wildcard imports; in Scala 3 write
`+import scala.jdk.CollectionConverters.*+`.

== Scala 3.9 LTS versus 3.10

The collections API is the Scala 2.13 API in all Scala 3 releases (since 3.8 the library is built by Scala 3), and
the compiler-side behaviour shown in this page (the E007 mismatch, the E172 equality error, the
`copyArrayToImmutableIndexedSeq` deprecation, the `Traversable` deprecation) is the same on 3.3.8, 3.9.0 and 3.10.0. The hierarchy, defaults, mutability, factories, Java conversion, equality and `IArray`
examples were compiled and run on 3.3.8 and 3.10.0 (and the hierarchy, `IArray`, equality-error and conversion examples
also on 3.9.0) with identical output. `IArray` itself exists since Scala 3.0.
