== The model: caller, callee and run unit

A program that executes `CALL` is the _calling program_; the program it names is the _called program_ or _subprogram_. Together with everything they call, they form a _run unit_: the set of programs that run from the first program started until `STOP RUN` (or an abend) ends it. Several rules follow from this and are worth stating before the syntax:

* A called program does not end the run unit. It ends with `GOBACK` or `EXIT PROGRAM`, which return control to the caller; `STOP RUN` in a subprogram ends the whole run unit.
* A subprogram keeps its `WORKING-STORAGE` between calls (its _last-used state_) unless it is `INITIAL` or is cancelled. Both are shown below.
* Parameters are matched by position, never by name. The caller's argument and the callee's parameter may have different names and even different data descriptions, but for `CALL` they must have the same length in bytes (the compiler cannot check this across separately compiled programs, so a mismatch is a run-time bug, see the section on mismatches).
* The data the callee describes in its `LINKAGE SECTION` occupies no storage of its own. It is a template laid over whatever the caller passed.

== The CALL statement

The general form, rewritten for readability, is:

[source,text]
----
CALL program-name-literal | program-name-identifier
    [ USING { [BY REFERENCE] argument ...
            | BY CONTENT argument ...
            | BY VALUE argument ... } ... ]
    [ RETURNING result-item ]
    [ ON EXCEPTION imperative-statement ]
    [ NOT ON EXCEPTION imperative-statement ]
[ END-CALL ]
----

* *Literal or identifier.* `CALL "BKCHECK"` names the program in a literal; `CALL WS-PROG` names it in a data item that holds the program name at run time. The identifier form always resolves the program at run time, which is what makes a table-driven dispatcher possible (a menu choice, a file type, a customer-specific rule). The literal form may be resolved at link time, depending on the options described below.
* *`USING`.* Arguments follow `USING`, and each carries a passing mode that applies until the next mode keyword (the mode before the first argument is `BY REFERENCE`). A list of arguments without `USING` is a syntax error.
* *`RETURNING`.* The called program's result goes into one item of the caller.
* *`ON EXCEPTION` (synonym `ON OVERFLOW`).* Runs when the called program cannot be made available. It is covered with the other run-time error phrases on xref:programming-languages/cobol/error-handling-and-declaratives.adoc[Error Handling and Declaratives], and is used below.
* *The program name.* It is the `PROGRAM-ID` name (or the `AS` literal of `PROGRAM-ID`) of the called program. On z/OS it must also match the name of the program object or an alias of it, and the `PGMNAME` option decides how names longer than eight characters or in mixed case are handled.

== Passing arguments: BY REFERENCE, BY CONTENT and BY VALUE

The three modes differ in one thing: who owns the bytes the callee works on.

image::cobol-call-passing-modes.svg["CALL passing modes: BY REFERENCE shares the caller's bytes, BY CONTENT passes a temporary copy, BY VALUE passes the value itself",width=720]

* *`BY REFERENCE`* (the default when no mode is written) passes the address of the caller's own data item. The callee's parameter is the caller's item, so every change the callee makes is visible to the caller. It is the mode for groups, tables, records and output parameters.
* *`BY CONTENT`* makes the `CALL` copy the argument into temporary storage and passes the address of that copy. The callee still receives an address and still declares an ordinary `LINKAGE SECTION` item, but it can change only the copy: the caller's item is untouched. An argument may be a literal, and the compiler checks that the data description matches, with no conversion, extension or truncation. It cannot be an unbounded group or a function identifier.
* *`BY VALUE`* passes the value itself in the parameter list, not an address. The callee gets a temporary copy, and a change to it does not reach the caller. The argument must be an elementary item or literal of a type with a defined value representation: binary (`BINARY`, `COMP`, `COMP-4`, `COMP-5`), floating point (`COMP-1`, `COMP-2`), a pointer or function or procedure pointer, one alphanumeric or national character, or an item taken from the `LENGTH OF` special register; groups are not allowed. A fixed-point numeric literal with nine or fewer digits is passed as a fullword binary value and a floating-point literal as an 8-byte `COMP-2`. `BY VALUE` exists mostly for calls to C, assembler and Java, which expect values, and is the subject of the C interoperability page.

The next program passes the book master fields in all three ways to a subprogram that changes each of them (the two are built together). The subprogram is called `PASSSUB`; it declares all four parameters with the default mode, which is how a callee receives a `BY REFERENCE` or a `BY CONTENT` argument.

[source,cobol]
----
      * Caller: three passing modes and RETURNING.
       IDENTIFICATION DIVISION.
       PROGRAM-ID. PASSMODE.
       DATA DIVISION.
       WORKING-STORAGE SECTION.
       01  WS-COPIES            PIC 9(3) VALUE 3.
       01  WS-PRICE             PIC 9(4)V99 VALUE 24.50.
       01  WS-DAYS              PIC S9(9) COMP-5 VALUE 4.
       01  WS-FINE              PIC 9(4)V99 VALUE ZERO.
       PROCEDURE DIVISION.
       MAIN-PARA.
           DISPLAY "before: copies=" WS-COPIES " price=" WS-PRICE
                   " days=" WS-DAYS
           CALL "PASSSUB" USING BY REFERENCE WS-COPIES
                                BY CONTENT WS-PRICE
                                BY CONTENT WS-DAYS
                                BY REFERENCE WS-FINE
           DISPLAY "after:  copies=" WS-COPIES " price=" WS-PRICE
                   " days=" WS-DAYS " fine=" WS-FINE
           STOP RUN.
       END PROGRAM PASSMODE.
----

[source,cobol]
----
      * Callee: changes all its parameters; BY REFERENCE is the default..
       IDENTIFICATION DIVISION.
       PROGRAM-ID. PASSSUB.
       DATA DIVISION.
       LINKAGE SECTION.
       01  LK-COPIES            PIC 9(3).
       01  LK-PRICE             PIC 9(4)V99.
       01  LK-DAYS              PIC S9(9) COMP-5.
       01  LK-FINE              PIC 9(4)V99.
       PROCEDURE DIVISION USING LK-COPIES LK-PRICE LK-DAYS LK-FINE.
       MAIN-PARA.
           SUBTRACT 1 FROM LK-COPIES
           MULTIPLY 2 BY LK-PRICE
           ADD 100 TO LK-DAYS
           COMPUTE LK-FINE = LK-DAYS * 0.35
           DISPLAY "callee: copies=" LK-COPIES " price=" LK-PRICE
                   " days=" LK-DAYS
           GOBACK.
       END PROGRAM PASSSUB.
----

Compiled with `cobc -x -Wall -o passmode passmode.cob passsub.cob`, no warnings, it prints:

[source,text]
----
before: copies=003 price=0024.50 days=+0000000004
callee: copies=002 price=0049.00 days=+0000000104
after:  copies=002 price=0024.50 days=+0000000004 fine=0036.40
----

The callee decremented `LK-COPIES` and the caller saw 002 (`BY REFERENCE`); the callee doubled the price and added 100 to the days, yet the caller still holds 24.50 and 4 (`BY CONTENT`); and the fine came back through the fourth, `BY REFERENCE`, parameter. With `-std=ibm` the results are the same and the implied-decimal items are displayed without the decimal point (`002450`), as `DISPLAY` does under that dialect.

`BY VALUE` is shown with a function everyone has, the C library `abs`, so that no C source is needed. The argument is a `COMP-5` item (a native 4-byte integer, which is what a C `int` is) and the result comes back with `RETURNING`:

[source,cobol]
----
      * BY VALUE: call the C library function abs().
       IDENTIFICATION DIVISION.
       PROGRAM-ID. BYVAL.
       DATA DIVISION.
       WORKING-STORAGE SECTION.
       01  WS-DELTA             PIC S9(9) COMP-5 VALUE -17.
       01  WS-ABS               PIC S9(9) COMP-5 VALUE ZERO.
       PROCEDURE DIVISION.
       MAIN-PARA.
           CALL "abs" USING BY VALUE WS-DELTA
                      RETURNING WS-ABS
           DISPLAY "delta=" WS-DELTA " abs=" WS-ABS
           STOP RUN.
       END PROGRAM BYVAL.
----

Compiled with `cobc -x -Wall -o byval byval.cob`, no warnings, it prints:

[source,text]
----
delta=-0000000017 abs=+0000000017
----

The same program built with `-std=ibm` printed the same line. Two GnuCOBOL 3.2 limits matter for portable code. First, a COBOL _callee_ that receives a `BY VALUE` parameter compiles with a warning, because that part of the implementation is unfinished:

[source,text]
----
passsub.cob:12: warning: handling of parameters passed BY VALUE is unfinished; implementation is likely to be changed [-Wunfinished]
   10 |        PROCEDURE DIVISION USING BY REFERENCE LK-COPIES
   11 |                                 BY REFERENCE LK-PRICE
   12 >                                 BY VALUE LK-DAYS
   13 |                                 BY REFERENCE LK-FINE.
----

Second, a COBOL program cannot declare `RETURNING` in its own `PROCEDURE DIVISION` header: `cobc` says `program RETURNING is not implemented [-Wpending]`, and a program that was built that way and called with `+CALL ... RETURNING+` stopped with "attempt to reference invalid memory address (signal)". Between GnuCOBOL programs, the portable way to return a result is an extra `BY REFERENCE` parameter (as `LK-FINE` above); calls to C functions with `RETURNING` work, as `abs` shows.

== The LINKAGE SECTION and PROCEDURE DIVISION USING

The called program receives its parameters through the `PROCEDURE DIVISION USING` header and describes them in the `LINKAGE SECTION`:

[source,text]
----
PROCEDURE DIVISION [ USING { [BY REFERENCE] [OPTIONAL] parameter ...
                           | BY VALUE parameter ... } ... ]
                   [ RETURNING result-item ].
----

* Every `USING` parameter must be a level-01 or level-77 item in the `LINKAGE SECTION`. The caller can pass an item of any level.
* The correspondence is by position. The number of parameters should equal the number of arguments; the compiler cannot correct a mismatch, and it will not even detect one across separately compiled programs.
* A `LINKAGE SECTION` item allocates no storage and cannot have a `VALUE` clause (except for condition names). Before the program touches a `LINKAGE SECTION` item that is not a parameter, its address has to be set with `SET ADDRESS OF`, as in the section on addresses below.
* The header's `BY REFERENCE` is the default; a callee that receives an argument passed `BY CONTENT` or `BY REFERENCE` declares it `BY REFERENCE` or with no mode, as `PASSSUB` does.
* A parameter may have a `REDEFINES` clause, and a group parameter is described with its elementary items so the callee can use the fields by name.

The best way to keep caller and callee in step is to describe the data once, in a copybook, and `COPY` it into the caller's `WORKING-STORAGE SECTION` (or `FILE SECTION`) and the callee's `LINKAGE SECTION`. The Circulation driver below reads `BOOKMAST` through `BOOKREC` and passes the record to `BKCHECK`, which declares the same record from the same copybook (see xref:programming-languages/cobol/copybooks-and-replace.adoc[Copybooks and COPY REPLACING]):

[source,cobol]
----
      * Circulation: read the book master, ask BKCHECK to check out one copy.
       IDENTIFICATION DIVISION.
       PROGRAM-ID. CIRCMAIN.
       ENVIRONMENT DIVISION.
       INPUT-OUTPUT SECTION.
       FILE-CONTROL.
           SELECT BOOK-FILE ASSIGN TO "BOOKMAST"
               ORGANIZATION IS LINE SEQUENTIAL.
       DATA DIVISION.
       FILE SECTION.
       FD  BOOK-FILE.
       COPY BOOKREC.
       WORKING-STORAGE SECTION.
       01  WS-EOF               PIC X VALUE "N".
           88  END-OF-BOOKS     VALUE "Y".
       01  WS-RESULT            PIC 9 VALUE ZERO.
           88  CHECKOUT-OK      VALUE 0.
           88  BOOK-WITHDRAWN-R VALUE 1.
           88  NO-COPIES-LEFT   VALUE 2.
       PROCEDURE DIVISION.
       MAIN-PARA.
           OPEN INPUT BOOK-FILE
           PERFORM UNTIL END-OF-BOOKS
               READ BOOK-FILE
                   AT END SET END-OF-BOOKS TO TRUE
                   NOT AT END PERFORM CHECK-ONE
               END-READ
           END-PERFORM
           CLOSE BOOK-FILE
           STOP RUN.
       CHECK-ONE.
           CALL "BKCHECK" USING BOOK-RECORD WS-RESULT
           EVALUATE TRUE
               WHEN CHECKOUT-OK
                   DISPLAY BOOK-ID " " BOOK-TITLE " copies now "
                           BOOK-COPIES
               WHEN BOOK-WITHDRAWN-R
                   DISPLAY BOOK-ID " withdrawn"
               WHEN NO-COPIES-LEFT
                   DISPLAY BOOK-ID " no copies left"
           END-EVALUATE.
       END PROGRAM CIRCMAIN.
----

[source,cobol]
----
      * Subprogram: one checkout against a book record (BY REFERENCE).
       IDENTIFICATION DIVISION.
       PROGRAM-ID. BKCHECK.
       DATA DIVISION.
       LINKAGE SECTION.
       COPY BOOKREC.
       01  LK-RESULT            PIC 9.
       PROCEDURE DIVISION USING BOOK-RECORD LK-RESULT.
       MAIN-PARA.
           EVALUATE TRUE
               WHEN BOOK-WITHDRAWN
                   MOVE 1 TO LK-RESULT
               WHEN BOOK-COPIES = ZERO
                   MOVE 2 TO LK-RESULT
               WHEN OTHER
                   SUBTRACT 1 FROM BOOK-COPIES
                   MOVE 0 TO LK-RESULT
           END-EVALUATE
           GOBACK.
       END PROGRAM BKCHECK.
----

With `BOOKMAST` in the current directory (its four books have 3, 2, 1 and 1 copies, the last one withdrawn), compiled with `cobc -x -Wall -I. -o circmain circmain.cob bkcheck.cob`, no warnings, it prints:

[source,text]
----
000001 DATA STRUCTURES                copies now 002
000002 COBOL BASICS                   copies now 001
000003 BATCH PROCESSING               copies now 000
000004 withdrawn
----

`BKCHECK` changed `BOOK-COPIES` directly in the caller's record because the record was passed `BY REFERENCE`, and reported what it did through `LK-RESULT`. Two points are worth noting. The copybook also defines the level 88 names `BOOK-ACTIVE` and `BOOK-WITHDRAWN`, so the callee tests the status without a literal. And the driver's own result item could not be called `BOOK-WITHDRAWN`, because the copybook already owns that name in the caller; this is the usual cost of copying the same record into both programs and is solved with `+COPY ... REPLACING+` where it matters. With `-std=ibm` the output is the same.

== RETURNING and RETURN-CODE

A subprogram can hand a result back in two ways, and they should not be mixed up:

* *`RETURNING`.* `+CALL ... RETURNING item+` stores the callee's result in `item`. In Enterprise COBOL the callee must also declare `RETURNING` in its `PROCEDURE DIVISION` header, the two items must agree in `PICTURE`, `USAGE`, `SIGN`, `SYNCHRONIZE`, `JUSTIFIED` and `BLANK WHEN ZERO`, and the callee must initialize its result item because it is output only. If the call fails with an exception the item is unchanged, and the `RETURN-CODE` special register is not set by a `CALL` that uses `RETURNING`. It is the same convention as C's return value, which is why it is the way to call C functions.
* *`RETURN-CODE`.* Every program has this special register, and it is the traditional way for a called program to report success (zero) or a severity (4, 8, 12, 16) to its caller, and on z/OS to the job step's condition code. It is covered with `STOP RUN` and `GOBACK` on the error handling page.

The following pair is the Enterprise COBOL form, in which the library computes a fine and returns it (z/OS; not run here, checked against the Language Reference; as shown above, GnuCOBOL 3.2 cannot compile the callee):

[source,cobol]
----
      * Caller
       CALL "FINECALC" USING BY REFERENCE WS-DAYS
                       RETURNING WS-FINE
      * Callee, PROCEDURE DIVISION header
       PROCEDURE DIVISION USING LK-DAYS RETURNING LK-FINE.
----

When a subprogram returns exactly one value and has no side effects, a user-defined function is often clearer, because it can be used inside an expression; see xref:programming-languages/cobol/user-defined-functions-and-prototypes.adoc[User-Defined Functions and Prototypes].

== OMITTED and OPTIONAL arguments

A caller can leave out a `BY REFERENCE` argument by writing `OMITTED` in its place, which lets a shared subprogram gain a parameter without every caller changing at once. Enterprise COBOL also assumes an extra `OMITTED` argument after the last one named. The callee has two ways to find out.

The first works everywhere: an omitted parameter has a null address, so `IF ADDRESS OF parameter = NULL` is true. The caller below calls `OMITSUB` twice, the second time without a member:

[source,cobol]
----
      * Caller: omits the second argument on purpose.
       IDENTIFICATION DIVISION.
       PROGRAM-ID. OMITCALL.
       DATA DIVISION.
       WORKING-STORAGE SECTION.
       01  WS-BOOK-ID           PIC 9(6) VALUE 1.
       01  WS-MEMBER-ID         PIC 9(6) VALUE 100.
       PROCEDURE DIVISION.
       MAIN-PARA.
           CALL "OMITSUB" USING WS-BOOK-ID WS-MEMBER-ID
           CALL "OMITSUB" USING WS-BOOK-ID OMITTED
           STOP RUN.
       END PROGRAM OMITCALL.
----

[source,cobol]
----
      * Callee: tests whether the second argument was supplied.
       IDENTIFICATION DIVISION.
       PROGRAM-ID. OMITSUB.
       DATA DIVISION.
       LINKAGE SECTION.
       01  LK-BOOK-ID           PIC 9(6).
       01  LK-MEMBER-ID         PIC 9(6).
       PROCEDURE DIVISION USING LK-BOOK-ID LK-MEMBER-ID.
       MAIN-PARA.
           DISPLAY "book " LK-BOOK-ID WITH NO ADVANCING
           IF ADDRESS OF LK-MEMBER-ID = NULL
               DISPLAY " (no member given)"
           ELSE
               DISPLAY " for member " LK-MEMBER-ID
           END-IF
           GOBACK.
       END PROGRAM OMITSUB.
----

Compiled with `cobc -x -Wall -o omitcall omitcall.cob omitsub.cob`, no warnings, it prints:

[source,text]
----
book 000001 for member 000100
book 000001 (no member given)
----

The second way is the `OPTIONAL` phrase, new in Enterprise COBOL 6.5, which declares a parameter as allowed to be absent and permits the `OMITTED` class test on it. It is not allowed under the `LP(64)` option. GnuCOBOL 3.2 accepts it, as this callee shows (the caller is the same as above):

[source,cobol]
----
      * Callee with an OPTIONAL second parameter (COBOL 2023 syntax).
       IDENTIFICATION DIVISION.
       PROGRAM-ID. OPTSUB.
       DATA DIVISION.
       LINKAGE SECTION.
       01  LK-BOOK-ID           PIC 9(6).
       01  LK-MEMBER-ID         PIC 9(6).
       PROCEDURE DIVISION USING LK-BOOK-ID OPTIONAL LK-MEMBER-ID.
       MAIN-PARA.
           IF LK-MEMBER-ID IS OMITTED
               DISPLAY "book " LK-BOOK-ID " (member omitted)"
           ELSE
               DISPLAY "book " LK-BOOK-ID " for member " LK-MEMBER-ID
           END-IF
           GOBACK.
       END PROGRAM OPTSUB.
----

Built with `cobc -x -Wall -o optcall optcall.cob optsub.cob` (`optcall.cob` is `omitcall.cob` with the program names changed), no warnings, it prints:

[source,text]
----
book 000001 for member 000100
book 000001 (member omitted)
----

With `-std=ibm` the output is the same, but `cobc` adds the note `warning: USING OPTIONAL used [-Wdialect]`, because the dialect file of 3.2 predates the 6.5 syntax. An omitted parameter must never be referenced before it has been tested: the next section shows what happens when it is not.

== ADDRESS OF as an argument or a parameter

Because every `BY REFERENCE` argument is an address, a program can pass an address explicitly. The caller makes a `POINTER` item point at a record with `SET ptr TO ADDRESS OF record` and passes the pointer; the callee declares the record in its `LINKAGE SECTION`, receives the pointer as its parameter, and overlays the record with `SET ADDRESS OF record TO ptr`. This is how a subprogram works on data that its caller allocated dynamically or that it receives from the operating system (a parameter area, a buffer). The record can have any description the callee prefers, because only the address is shared:

[source,cobol]
----
      * Caller passes the address of a record instead of the record.
       IDENTIFICATION DIVISION.
       PROGRAM-ID. PTRMAIN.
       DATA DIVISION.
       WORKING-STORAGE SECTION.
       COPY BOOKREC.
       01  WS-BOOK-PTR          USAGE POINTER.
       PROCEDURE DIVISION.
       MAIN-PARA.
           MOVE 2 TO BOOK-ID
           MOVE "COBOL BASICS" TO BOOK-TITLE
           MOVE 2 TO BOOK-COPIES
           SET WS-BOOK-PTR TO ADDRESS OF BOOK-RECORD
           CALL "PTRSUB" USING WS-BOOK-PTR
           DISPLAY "caller sees copies=" BOOK-COPIES
           STOP RUN.
       END PROGRAM PTRMAIN.
----

[source,cobol]
----
      * Callee: maps its own record layout onto the received address.
       IDENTIFICATION DIVISION.
       PROGRAM-ID. PTRSUB.
       DATA DIVISION.
       LINKAGE SECTION.
       COPY BOOKREC.
       01  LK-BOOK-PTR          USAGE POINTER.
       PROCEDURE DIVISION USING LK-BOOK-PTR.
       MAIN-PARA.
           SET ADDRESS OF BOOK-RECORD TO LK-BOOK-PTR
           ADD 5 TO BOOK-COPIES
           DISPLAY "callee sees " BOOK-TITLE
           GOBACK.
       END PROGRAM PTRSUB.
----

Compiled with `cobc -x -Wall -o ptrmain ptrmain.cob ptrsub.cob`, no warnings, it prints:

[source,text]
----
callee sees COBOL BASICS
caller sees copies=007
----

The callee added 5 to `BOOK-COPIES` through its own `BOOK-RECORD` template, and the caller's record changed, since both describe the same 60 bytes. A pointer can also be passed with `BY VALUE`, which is the common form with C; GnuCOBOL 3.2 accepts it in the caller but warns, as above, when a COBOL callee declares it `BY VALUE`, so the pointer item itself is passed by reference here. The rules for where `ADDRESS OF` and `POINTER` may be used, and the dangers of dangling addresses, are on xref:programming-languages/cobol/pointers-and-dynamic-storage.adoc[Pointers and Dynamic Storage].

== Static and dynamic calls

How the called program is found is a build decision, not a language one, and it differs between the platforms.

=== Enterprise COBOL: NODYNAM, DYNAM and CALL identifier

The compiler options `DYNAM` and `NODYNAM` (default `NODYNAM`) decide how a `CALL` with a literal is resolved, and a `CALL` with an identifier is always dynamic:

[cols="2,3,3",options="header"]
|===
| Form | `NODYNAM` (default) | `DYNAM`
| `CALL "BKCHECK"` (literal)
| _Static_: the called program is link-edited with the caller into one program object, is already in storage, and control branches straight to it.
| _Dynamic_: the called program is a separate program object, loaded from a load library the first time it is called.
| `CALL WS-PROG` (identifier)
| _Dynamic_, whatever the option says.
| _Dynamic_.
|===

The consequences are practical:

* *Speed.* A static call is faster; the Performance Tuning Guide reports the call overhead under `DYNAM` as higher than under `NODYNAM`, so a program that makes millions of calls should be linked statically.
* *Maintenance.* A dynamically called program can be replaced by compiling and link-editing just that program; the callers are not touched. A statically linked one needs every caller re-linked.
* *Storage.* `CANCEL` frees the storage of a dynamically called program and, under `NODYNAM`, does nothing useful for a statically linked one (it is already part of the caller's object).
* *State.* A statically or dynamically called program keeps its last-used state between calls unless it is `INITIAL`. The first dynamic call gets a fresh copy, and later calls from any program in the run unit use that copy.
* *Mixing.* Using a literal `CALL` under `NODYNAM` and an identifier `CALL` to the same program within one program loads a second copy of the subprogram, so its state is not shared; avoid it.
* *Restrictions.* The `DYNAM` option page says not to use `DYNAM` with programs that contain `EXEC SQL` when they run under CICS or are called by a program that uses the Db2 call attach facility, and not to use it when calling DLLs (compile with `NODYNAM` and `DLL` instead). A September 2026 PTF (PH73033) is listed as "DYNAM with CICS" in the what's-new page of 6.5; read its notes before relying on either statement. A dynamically called program must be in a load library, not in the z/OS UNIX file system.
* *Names.* The `PROGRAM-ID` or entry name must match the name of the program object or one of its aliases, or the call fails with messages such as `CEE3593I`, `CEE3541S`, `CEE3574I` or `IGZ0178S`.

The flow is simple enough to draw. The decision a build makes for each `CALL` is:

[mermaid]
----
flowchart TD
    A["CALL"] --> B{"Operand is a literal?"}
    B -->|"no, an identifier"| D["Dynamic: program loaded by name at run time"]
    B -->|"yes"| C{"Compiled with DYNAM?"}
    C -->|"yes"| D
    C -->|"no, NODYNAM"| S["Static: called program is part of the same program object"]
    D --> E["CANCEL frees it; the next CALL loads it again"]
    S --> F["Already in storage; faster; re-link callers to change it"]
----

Source: https://www.ibm.com/docs/en/SS6SG3_6.5/pg/ui/up5520.html[Enterprise COBOL for z/OS 6.5 Programming Guide: DYNAM]; https://www.ibm.com/docs/en/SS6SG3_6.5/pg/tasks/tpsub03.html[Making static calls]; https://www.ibm.com/docs/en/SS6SG3_6.5/pg/tasks/tpsub04.html[Making dynamic calls]; https://www.ibm.com/docs/en/SS6SG3_6.5/pg/tasks/tpsub09.html[Making both static and dynamic calls]; https://www.ibm.com/docs/en/SS6SG3_6.5/pg/concepts/cpsub02a.html[Performance considerations of static and dynamic calls]; https://www.ibm.com/docs/en/SS6SG3_6.5/pdf/perfguide.pdf[Performance Tuning Guide (PDF)]; https://www.ibm.com/docs/en/SS6SG3_6.5/new/sum.html[What's new in Enterprise COBOL for z/OS 6.5]

=== GnuCOBOL: modules, executables and -fstatic-call

GnuCOBOL has no `DYNAM` option; its model has the same two ends under different names. By default every `CALL`, literal or identifier, is resolved at run time, first among the programs linked into the executable and then among _dynamically loadable modules_ (`.so` files on Linux, `.dll` on Windows) that `cobc -m` builds. The compiler switch `-fstatic-call` turns literal calls into ordinary linker references to the called program's entry point, which then must be linked into the executable (`cobc -x main.cob sub.cob -fstatic-call`). The practical consequences are covered in the build section below.

Source: https://gnucobol.sourceforge.io/HTML/gnucobpg.html#Dynamic-vs-Static-Subprograms[GnuCOBOL 3.2 Programmer's Guide: Dynamic vs Static Subprograms]

== CANCEL, INITIAL and what a subprogram remembers

A subprogram's `WORKING-STORAGE` keeps the values of its last call, which is what a counter wants and what a table lookup may not. Three things control it: `CANCEL`, the `INITIAL` attribute, and `LOCAL-STORAGE`. The subprogram below counts calls in both sections, and the second, `TALLYI`, is the same counter declared `IS INITIAL`:

[source,cobol]
----
      * Subprogram: counts calls in WORKING-STORAGE and LOCAL-STORAGE.
       IDENTIFICATION DIVISION.
       PROGRAM-ID. TALLY.
       DATA DIVISION.
       WORKING-STORAGE SECTION.
       01  WS-CALLS             PIC 9(3) VALUE ZERO.
       LOCAL-STORAGE SECTION.
       01  LS-CALLS             PIC 9(3) VALUE ZERO.
       LINKAGE SECTION.
       01  LK-NAME              PIC X(8).
       PROCEDURE DIVISION USING LK-NAME.
       MAIN-PARA.
           ADD 1 TO WS-CALLS LS-CALLS
           DISPLAY LK-NAME " working=" WS-CALLS " local=" LS-CALLS
           GOBACK.
       END PROGRAM TALLY.
----

[source,cobol]
----
      * Same counter, declared IS INITIAL.
       IDENTIFICATION DIVISION.
       PROGRAM-ID. TALLYI IS INITIAL.
       DATA DIVISION.
       WORKING-STORAGE SECTION.
       01  WS-CALLS             PIC 9(3) VALUE ZERO.
       LINKAGE SECTION.
       01  LK-NAME              PIC X(8).
       PROCEDURE DIVISION USING LK-NAME.
       MAIN-PARA.
           ADD 1 TO WS-CALLS
           DISPLAY LK-NAME " working=" WS-CALLS
           GOBACK.
       END PROGRAM TALLYI.
----

The driver calls `TALLY` three times through an identifier, cancels it, calls it again, then calls `TALLYI` twice, and finally asks for a program that does not exist. The `ON EXCEPTION` outcome is recorded in a flag and tested afterwards, which is the portable form discussed on the error handling page, because GnuCOBOL 3.2 also runs `NOT ON EXCEPTION` after a `DISPLAY` in the `ON EXCEPTION` branch:

[source,cobol]
----
      * Driver: dynamic calls by identifier, CANCEL and ON EXCEPTION.
       IDENTIFICATION DIVISION.
       PROGRAM-ID. DRIVER.
       DATA DIVISION.
       WORKING-STORAGE SECTION.
       01  WS-PROG              PIC X(8).
       01  WS-NAME              PIC X(8) VALUE "BATCH".
       01  WS-LOADED            PIC X VALUE "Y".
           88  PROGRAM-LOADED   VALUE "Y".
           88  PROGRAM-MISSING  VALUE "N".
       PROCEDURE DIVISION.
       MAIN-PARA.
           MOVE "TALLY" TO WS-PROG
           PERFORM 3 TIMES
               CALL WS-PROG USING WS-NAME
           END-PERFORM
           CANCEL WS-PROG
           DISPLAY "after CANCEL"
           CALL WS-PROG USING WS-NAME
           MOVE "TALLYI" TO WS-PROG
           CALL WS-PROG USING WS-NAME
           CALL WS-PROG USING WS-NAME
           MOVE "NOSUCH" TO WS-PROG
           SET PROGRAM-LOADED TO TRUE
           CALL WS-PROG USING WS-NAME
               ON EXCEPTION
                   SET PROGRAM-MISSING TO TRUE
           END-CALL
           IF PROGRAM-MISSING
               DISPLAY "cannot call " FUNCTION TRIM(WS-PROG)
           END-IF
           STOP RUN.
       END PROGRAM DRIVER.
----

Each subprogram was built as a module (`cobc -m -Wall -o TALLY.so tally.cob`, the same for `TALLYI`) and the driver with `cobc -x -Wall driver.cob`, no warnings. Run in the same directory it prints:

[source,text]
----
BATCH    working=001 local=001
BATCH    working=002 local=001
BATCH    working=003 local=001
after CANCEL
BATCH    working=001 local=001
BATCH    working=001
BATCH    working=001
cannot call NOSUCH
----

Reading the output line by line explains each feature:

* *Last-used state.* `WS-CALLS` counted 1, 2, 3 across the three calls: `WORKING-STORAGE` survived between them.
* *`LOCAL-STORAGE`.* `LS-CALLS` was 1 every time. `LOCAL-STORAGE` is allocated and initialized again on every call, and released when the program returns, so it never remembers anything and is the right place for work fields of a recursive or multithreaded program.
* *`CANCEL`.* After `CANCEL WS-PROG` the next call started from the initial state (`working=001`). `CANCEL` returns a subprogram to its initial state, frees its dynamic-length buffers and closes the files that it opened (the files' `USE` procedures do not run), and has no effect on a program that was never dynamically called or is already cancelled. It can be issued by a program other than the caller as long as it sits at or above the called program in the calling hierarchy, the program must have ended with `GOBACK` or `EXIT PROGRAM` first, and cancelling a program also cancels the programs nested in it. External data is left unchanged. In GnuCOBOL, whether a module is physically unloaded depends on the run-time variable `COB_PHYSICAL_CANCEL`; the initial state is restored either way.
* *`IS INITIAL`.* `TALLYI` printed `working=001` on both calls: an `INITIAL` program, and the programs nested in it, are put in their initial state on every call (`VALUE` clauses applied, files not left open, `PERFORM` and altered `GO TO` states reset). It is the declarative way to say "never remember anything", at the price of re-initializing on each call. It is not supported with the `THREAD` option.
* *`ON EXCEPTION`.* The call of `NOSUCH` reached the exception branch instead of ending the run. Without the phrase the same call stops GnuCOBOL with `+libcob: error: module 'NOSUCH' not found+`, and on z/OS ends in a Language Environment condition that the program must be prepared for.

Built as one executable instead, with `cobc -x -Wall -o all driver.cob tally.cob tallyi.cob`, the output is the same, because the identifier calls find the programs inside the executable. A `CANCEL` behaves the same whether the program is a module or part of the executable.

Source: https://www.ibm.com/docs/en/SS6SG3_6.5/lr/ref/rlpscanc.html[Enterprise COBOL for z/OS 6.5 Language Reference: CANCEL statement]; https://www.ibm.com/docs/en/SS6SG3_6.5/pg/tasks/tpsub04a.html[Programming Guide: Canceling a subprogram]; https://www.ibm.com/docs/en/SS6SG3_6.5/lr/ref/rlidepid.html[Language Reference: PROGRAM-ID paragraph]; https://gnucobol.sourceforge.io/HTML/gnucobpg.html#CANCEL[GnuCOBOL 3.2 Programmer's Guide: CANCEL]; https://gnucobol.sourceforge.io/HTML/gnucobpg.html#Run-Time-Environment-Variables[GnuCOBOL 3.2 Programmer's Guide: Run Time Environment Variables]

== Recursion and LOCAL-STORAGE

A program may call itself, directly or through other programs, only if its `PROGRAM-ID` has `IS RECURSIVE` (COBOL 2002). Each activation then has its own `LOCAL-STORAGE`, while `WORKING-STORAGE` is shared by all activations, so a recursive program keeps its per-level values in `LOCAL-STORAGE` and the shared ones in `WORKING-STORAGE`. The next program computes a factorial (here a stand-in for any problem that divides itself, such as walking a classification tree of the library):

[source,cobol]
----
      * RECURSIVE program: each activation has its own LOCAL-STORAGE.
       IDENTIFICATION DIVISION.
       PROGRAM-ID. FACT IS RECURSIVE.
       DATA DIVISION.
       LOCAL-STORAGE SECTION.
       01  LS-PREV              PIC 9(9).
       LINKAGE SECTION.
       01  LK-N                 PIC 9(2).
       01  LK-RESULT            PIC 9(9).
       PROCEDURE DIVISION USING LK-N LK-RESULT.
       MAIN-PARA.
           IF LK-N <= 1
               MOVE 1 TO LK-RESULT
           ELSE
               SUBTRACT 1 FROM LK-N
               CALL "FACT" USING LK-N LS-PREV
               ADD 1 TO LK-N
               COMPUTE LK-RESULT = LK-N * LS-PREV
           END-IF
           GOBACK.
       END PROGRAM FACT.
----

[source,cobol]
----
      * Driver for FACT.
       IDENTIFICATION DIVISION.
       PROGRAM-ID. RECDRV.
       DATA DIVISION.
       WORKING-STORAGE SECTION.
       01  WS-N                 PIC 9(2) VALUE 6.
       01  WS-RESULT            PIC 9(9) VALUE ZERO.
       PROCEDURE DIVISION.
       MAIN-PARA.
           CALL "FACT" USING WS-N WS-RESULT
           DISPLAY WS-N "! = " WS-RESULT
           STOP RUN.
       END PROGRAM RECDRV.
----

Compiled with `cobc -x -Wall -o recdrv recdrv.cob recur.cob`, no warnings, it prints:

[source,text]
----
06! = 000000720
----

The result is the same with `-std=ibm`. The rules of Enterprise COBOL are stricter than the standard in two ways: `RECURSIVE` may be coded only on the outermost program of a compilation unit, and a recursive program cannot contain nested programs; it also cannot use `ALTER`, `GO TO` without a procedure name, `RERUN`, `SEGMENT-LIMIT` or `USE FOR DEBUGGING`. A recursive (or `THREAD`) program cannot rely on `LINKAGE SECTION` items of an earlier activation after a new call, so parameters are handled in the activation that received them. Without the `RECURSIVE` attribute an active program cannot be reentered. GnuCOBOL is lenient: removing `IS RECURSIVE` compiled with a note and still ran, which is not portable behaviour:

[source,text]
----
norec.cob:16: warning: CALL to own PROGRAM-ID used [-Wdialect]
norec.cob:16: note: assuming RECURSIVE attribute [-Wdialect]
----

Source: https://www.ibm.com/docs/en/SS6SG3_6.5/lr/ref/rlidepid.html[Enterprise COBOL for z/OS 6.5 Language Reference: PROGRAM-ID paragraph]; https://www.ibm.com/docs/en/SS6SG3_6.5/pg/concepts/cppgm28.html[Programming Guide: Comparison of WORKING-STORAGE and LOCAL-STORAGE]; https://gnucobol.sourceforge.io/HTML/gnucobpg.html#Recursive-Subprograms[GnuCOBOL 3.2 Programmer's Guide: Recursive Subprograms]

== Sharing data without passing it: EXTERNAL and GLOBAL

Arguments are the clean way to move data between programs. Two clauses share data without them:

* *`EXTERNAL`* is coded on a level-01 item of the `WORKING-STORAGE SECTION` (and on files). Any program of the run unit that declares an item with the same name and the identical description addresses the same storage. Items under an `EXTERNAL` group are external too, and none of them may have a `VALUE` clause, so the first program to use the area initializes it. Any program that can reach it can change it, so it is unsuitable for protected data.
* *`GLOBAL`* is coded on a level-01 item and makes it visible to every program _nested_ in the declaring program, unless a nested program declares the same name itself. It does not reach siblings or the outside.

A nested program cannot see its sibling's data at all, so siblings share data through `EXTERNAL` items or through `GLOBAL` items of their container. The nested-program rules (`COMMON`, who may call whom, the practical limits) and a working example with a `GLOBAL` item are on xref:programming-languages/cobol/program-structure-and-divisions.adoc[Program Structure and Divisions]. The `EXTERNAL` case with separately compiled programs is shown here: a run statistics area that `EXTCOUNT` updates and the driver reads, with neither passing it:

[source,cobol]
----
      * EXTERNAL data: a counter shared without passing it.
       IDENTIFICATION DIVISION.
       PROGRAM-ID. EXTMAIN.
       DATA DIVISION.
       WORKING-STORAGE SECTION.
       01  RUN-STATS EXTERNAL.
           05  STAT-CHECKOUTS   PIC 9(5).
           05  STAT-RETURNS     PIC 9(5).
       PROCEDURE DIVISION.
       MAIN-PARA.
           MOVE ZERO TO STAT-CHECKOUTS STAT-RETURNS
           CALL "EXTCOUNT" USING "O"
           CALL "EXTCOUNT" USING "O"
           CALL "EXTCOUNT" USING "R"
           DISPLAY "checkouts=" STAT-CHECKOUTS
                   " returns=" STAT-RETURNS
           STOP RUN.
       END PROGRAM EXTMAIN.
----

[source,cobol]
----
      * Subprogram that updates the same EXTERNAL group by name.
       IDENTIFICATION DIVISION.
       PROGRAM-ID. EXTCOUNT.
       DATA DIVISION.
       WORKING-STORAGE SECTION.
       01  RUN-STATS EXTERNAL.
           05  STAT-CHECKOUTS   PIC 9(5).
           05  STAT-RETURNS     PIC 9(5).
       LINKAGE SECTION.
       01  LK-TYPE              PIC X.
       PROCEDURE DIVISION USING LK-TYPE.
       MAIN-PARA.
           IF LK-TYPE = "O"
               ADD 1 TO STAT-CHECKOUTS
           ELSE
               ADD 1 TO STAT-RETURNS
           END-IF
           GOBACK.
       END PROGRAM EXTCOUNT.
----

Compiled with `cobc -x -Wall -o extmain extmain.cob extcount.cob`, no warnings, it prints:

[source,text]
----
checkouts=00002 returns=00001
----

The driver moved zero to the counters itself because `EXTERNAL` items cannot carry `VALUE`. The identical level-01 description in both programs is best kept in a copybook so that the two cannot drift apart. The same output came from the `-std=ibm` build.

== Building multi-program executables

=== GnuCOBOL: cobc -m, -x with several sources and COB_LIBRARY_PATH

Three `cobc` forms cover every arrangement of programs:

[source,bash]
----
cobc -x -o circmain circmain.cob bkcheck.cob     # one executable, several sources
cobc -m -o BKCHECK.so bkcheck.cob                # a loadable module
cobc -x -o circmain circmain.cob                 # executable that loads BKCHECK at run time
cobc -b -o CIRC.so circmain.cob bkcheck.cob      # one shared library holding both programs
----

* `-x` builds an executable and treats the first source as the main program; the other sources are compiled and linked in. Nothing is looked up at run time, and `CALL` of a linked-in program works by either form of operand.
* `-m` builds a dynamically loadable module, the equivalent of a program object in a load library. The file name is taken from the first source unless `-o` is given.
* `-b` builds a shared library that can hold several programs. With `CIRC.so` built from both sources, `cobcrun CIRCMAIN` failed with `+module 'CIRCMAIN' not found+` until the library was named in `COB_PRE_LOAD` (`COB_PRE_LOAD=CIRC cobcrun CIRCMAIN` then ran).
* The module's _file_ name matters. For `CALL "TALLY"`, `cobc -m tally.cob` produced `tally.so`, and on Linux the call failed with `+libcob: error: module 'TALLY' not found+`, because the run time looks for the upper-case name. Naming the module `TALLY.so` fixed it, and so did setting `COB_LOAD_CASE=LOWER`. (On a case-insensitive file system, such as the default macOS or Windows one, the lower-case name is found anyway, which makes the problem appear only when the program moves to Linux.)
* `COB_LIBRARY_PATH` lists the directories searched for modules, as an additional list: with the variable pointing at a nonexistent directory the module in the executable's own directory was still found, and with the module moved to `mods` the call succeeded after `COB_LIBRARY_PATH=mods`. `COB_PRE_LOAD` loads named modules when the program starts; it applies only to modules called with a literal.
* `cobcrun` runs a module as a program without building an executable: with `CIRCMAIN.so` and `BKCHECK.so` built by `cobc -m` (the first from `circmain.cob`), `cobcrun CIRCMAIN` printed the four book lines above. It looks for a module of that name in the library path and does not accept a path.
* `-fstatic-call` makes literal calls ordinary linker references. Built with `cobc -x -Wall -fstatic-call -o st driver2.cob tally.cob`, a program using `CALL "TALLY"` and `CANCEL "TALLY"` needed no module and printed the same three lines as the dynamic build:

[source,text]
----
BATCH    working=001 local=001
BATCH    working=002 local=001
BATCH    working=001 local=001
----

The same source without `-fstatic-call` and without `tally.cob` on the command line fails at run time (`+libcob: error: module 'TALLY' not found+`), whereas with `-fstatic-call` and no `tally.cob` the link step fails instead (`+undefined reference to 'TALLY'+`). That difference is the practical meaning of static: a missing program is found when the application is built, not on the first call.

Source: https://gnucobol.sourceforge.io/HTML/gnucobpg.html#Compiling-Programs[GnuCOBOL 3.2 Programmer's Guide: Compiling Programs]; https://gnucobol.sourceforge.io/HTML/gnucobpg.html#Dynamically-Loaded-Subprograms[GnuCOBOL 3.2 Programmer's Guide: Dynamically Loaded Subprograms]; https://gnucobol.sourceforge.io/HTML/gnucobpg.html#Run-Time-Environment-Variables[GnuCOBOL 3.2 Programmer's Guide: Run Time Environment Variables]

=== z/OS: compile, link-edit and run

On z/OS, compiling produces an object module, and the binder (the program of the link-edit step, `IEWL`) combines object modules into a program object in a load library. With `NODYNAM` a statically called program is simply another object module included in the same link-edit; with `DYNAM` or `CALL identifier` it is link-edited by itself into its own member of a load library that the run finds through `STEPLIB` or `JOBLIB` (it cannot be in the z/OS UNIX file system). The shape of a static link step for the Circulation driver is below; data set names, the object library and the member names are the scenario's, the binder control statements are the standard `INCLUDE` and `NAME`, and the compile step itself and the Language Environment options are on xref:programming-languages/cobol/compiling-linking-and-language-environment.adoc[Compiling, Linking and Language Environment] (z/OS; not run here):

[source,text]
----
//LKED     EXEC PGM=IEWL,PARM='LIST,XREF,MAP'
//SYSLIB   DD DISP=SHR,DSN=CEE.SCEELKED
//OBJ      DD DISP=SHR,DSN=USERID.CIRC.OBJ
//SYSLMOD  DD DISP=SHR,DSN=USERID.CIRC.LOADLIB
//SYSPRINT DD SYSOUT=*
//SYSLIN   DD *
  INCLUDE OBJ(CIRCMAIN)
  INCLUDE OBJ(BKCHECK)
  NAME CIRCMAIN(R)
/*
//RUN      EXEC PGM=CIRCMAIN
//STEPLIB  DD DISP=SHR,DSN=USERID.CIRC.LOADLIB
//BOOKMAST DD DISP=SHR,DSN=USERID.CIRC.BOOKMAST
//SYSOUT   DD SYSOUT=*
----

For a dynamic arrangement the `BKCHECK` object would instead be bound into the load library with its own `NAME BKCHECK(R)` statement, and the `INCLUDE OBJ(BKCHECK)` line of the driver's step would go. Running the driver then needs `BKCHECK` in a library on `STEPLIB`, and a missing member shows up at the first call as the `ON EXCEPTION` condition or an abend. The JCL itself is explained on xref:programming-languages/cobol/jcl-for-cobol-programmers.adoc[JCL for COBOL Programmers].

== Mismatched arguments

The compiler checks an argument list against the parameters only when it can see both programs: in the same source file, or, in Enterprise COBOL 6.4 and later, through a program prototype (see xref:programming-languages/cobol/user-defined-functions-and-prototypes.adoc[User-Defined Functions and Prototypes]). For separately compiled programs nothing is checked, and the mismatch surfaces as a run-time fault. This is the most common subprogram bug, and GnuCOBOL 3.2 shows its forms.

A callee that touches a parameter the caller did not pass:

[source,cobol]
----
      * Caller passes one argument; the callee expects two.
       IDENTIFICATION DIVISION.
       PROGRAM-ID. FEWCALL.
       DATA DIVISION.
       WORKING-STORAGE SECTION.
       01  WS-BOOK-ID           PIC 9(6) VALUE 1.
       PROCEDURE DIVISION.
       MAIN-PARA.
           CALL "NOCHECK" USING WS-BOOK-ID

Argument lists whose lengths differ are not detected at all. `PIC 9(6)` passed to a `PIC 9(3)` parameter passes six bytes of which the callee sees three, and the reverse reads storage that belongs to something else. == Common mistakes

* *Passing a literal when the callee writes to the argument.* A literal is for `BY CONTENT` or `BY VALUE`; an argument the callee must change has to be a data item passed `BY REFERENCE`.
* *Expecting a `BY CONTENT` argument to be changed.* The callee changes the temporary copy and the caller silently keeps the old value.
* *Different numbers or lengths of arguments.* Parameters are matched by position and for `CALL` must have the same length; separately compiled programs are not checked, so test builds should use `-debug` (GnuCOBOL) or `PARMCHECK` (Enterprise COBOL), and both sides should `COPY` one description.
* *Referencing a `LINKAGE SECTION` item that was never passed.* An omitted or missing parameter is a null address; test it before use.
* *Assuming a subprogram starts clean.* `WORKING-STORAGE` keeps its last-used state, so a flag set on the first call is still set on the second. Use `IS INITIAL`, `LOCAL-STORAGE` or `CANCEL` when that is not wanted.
* *Using `STOP RUN` in a subprogram.* It ends the whole run unit; use `GOBACK`.
* *Relying on a `CANCEL` to free memory under `NODYNAM`.* A statically linked program is part of the caller's program object; only dynamically loaded programs are freed.
* *Mixing a literal `CALL` and an identifier `CALL` of the same program under `NODYNAM`.* A second copy is loaded and the two copies keep separate state.
* *Module file names in lower case on Linux.* `CALL "TALLY"` looks for `TALLY.so`; name the module accordingly or set `COB_LOAD_CASE`.
* *Handling `ON EXCEPTION` and `NOT ON EXCEPTION` with output in the first branch (GnuCOBOL 3.2).* Record the outcome in a flag and decide afterwards.
* *Using `BY VALUE` for COBOL-to-COBOL calls on GnuCOBOL.* The callee's side is unfinished; use `BY REFERENCE` or `BY CONTENT` between COBOL programs.
* *Recursion without `IS RECURSIVE`.* Enterprise COBOL does not allow an active program to be reentered; GnuCOBOL accepts it with a note, so the bug appears only on z/OS.
