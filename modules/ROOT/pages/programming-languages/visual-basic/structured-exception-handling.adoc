== How a Try statement executes

A `Try` statement has a `Try` block, any number of `Catch` blocks and an optional `Finally` block; at least one `Catch` or the
`Finally` is required (BC30030 otherwise). When code in the `Try` block throws, the runtime searches the `Catch` blocks of that
statement from top to bottom, then of the enclosing `Try` statements in the same method, then of the callers, for the first block
whose type matches and whose `When` condition is `True`. Only after that search has found a handler does the runtime unwind the
stack, running the `Finally` blocks of the frames it leaves, and then enter the `Catch` block. If the search finds nothing, the
exception is unhandled and the process ends (see Global handlers below).

[mermaid]
....
flowchart TD
    A(["Code in a Try block throws"]) --> B{"Search: a Catch whose type matches and whose When is True?"}
    B -->|"yes, in this Try or a caller"| C["Unwind the stack and run the Finally blocks of the frames being left"]
    C --> D["Run the matching Catch block"]
    D --> E["Run the Finally block of the Try that caught it"]
    E --> F(["Continue after End Try"])
    B -->|"no handler anywhere"| G["Unhandled: UnhandledException event, then the process ends"]
....

== Try, Catch and Finally

The first example parses text with `Integer.Parse` and handles three cases with three `Catch` blocks. Each block names an
exception type, so only that type (and types derived from it) enter it. The `Finally` block runs after every iteration, whether
the `Try` block completed or a `Catch` block ran.

[source,vbnet]
----
Option Strict On

Module Program
    Sub Main()
        For Each text As String In {"3", "three", "", "99999999999"}
            Try
                Dim copies As Integer = Integer.Parse(text)
                Console.WriteLine("copies = " & copies)
            Catch ex As OverflowException
                Console.WriteLine("too big: " & ex.GetType().Name)
            Catch ex As FormatException
                Console.WriteLine("not a number: " & ex.Message)
            Catch ex As Exception
                Console.WriteLine("anything else: " & ex.GetType().Name)
            Finally
                Console.WriteLine("  finished '" & text & "'")
            End Try
        Next
    End Sub
End Module
----

[source,text]
----
copies = 3
  finished '3'
not a number: The input string 'three' was not in a correct format.
  finished 'three'
not a number: The input string '' was not in a correct format.
  finished ''
too big: OverflowException
  finished '99999999999'
----

The rules in one place:

[cols="2,5",options="header"]
|===
|Rule |Detail

|Matching |a `Catch` block handles an exception when the exception is an instance of the named type, including derived types; `Catch ex As Exception` handles everything that derives from `Exception`
|Order |the first matching block wins; blocks are not searched for the best match, so put derived types before base types
|Variable scope |the variable declared in `Catch ex As T` exists only inside that block, so sibling blocks can reuse the name `ex`; reusing it for another local in the same method is BC30616
|`Finally` |runs when the `Try` block ends normally, when a `Catch` block runs, when `Exit Try`, `Return` or `Exit Sub` leaves the statement, and when an exception goes unhandled to an outer handler
|Locals |a variable declared inside the `Try` block is not visible in `Catch` or `Finally` (BC30451); declare it before the `Try`
|Result |a `Try` statement is a statement, not an expression; it has no value
|===

=== Catch order

Because the first matching block wins, a base type placed before a derived type makes the derived block unreachable. The compiler
notices it, but as a warning, not an error: BC42029 is a warning, so it becomes an error only when the project treats warnings as
errors (as the other examples on this page do).

[source,vbnet]
----
Option Strict On

Module Program
    Sub Main()
        Try
            Console.WriteLine("a")
        Catch ex As Exception
            Console.WriteLine("general")
        Catch ex As ArgumentException
            Console.WriteLine("specific")
        End Try
    End Sub
End Module
----

Built without `TreatWarningsAsErrors`; the compiler printed:

[source,text]
----
Program.vb(9,9): warning BC42029: 'Catch' block never reached, because 'ArgumentException' inherits from 'Exception'.
----

Put `Catch ex As ArgumentException` first and `Catch ex As Exception` last. Catching `Exception` is legitimate at the outermost
layer of a program (a request handler, a worker loop, `Sub Main`) where the aim is to log and continue or stop cleanly; deep in
a library it hides bugs, which is what the code-analysis rule CA1031 warns about.

=== Catch forms

A bare `Catch` with no type handles everything, and each `Catch` block has its own scope for the exception variable. `When` may use
`pass:c[TypeOf ... Is]` to treat several types alike without repeating the body.

[source,vbnet]
----
Option Strict On

Module Program
    Function Quiet() As Integer
        Try
            Return 1
        Catch
            Return -1
        End Try
    End Function

    Sub Main()
        ' Catch without a type catches Exception 
        Try
            Throw New FormatException("bare Catch")
        Catch
            Console.WriteLine("caught without naming a type")
        End Try

        ' Each Catch block has its own scope, so the same name can be reused
        For Each code As Integer In {1, 2}
            Try
                If code = 1 Then Throw New ArgumentException("one")
                Throw New InvalidOperationException("two")
            Catch ex As ArgumentException
                Console.WriteLine("A: " & ex.Message)
            Catch ex As InvalidOperationException
                Console.WriteLine("B: " & ex.Message)
            End Try
        Next

        ' TypeOf in a filter instead of a separate Catch
        Try
            Throw New TimeoutException("slow")
        Catch ex As Exception When TypeOf ex Is TimeoutException OrElse TypeOf ex Is OperationCanceledException
            Console.WriteLine("timeout or cancellation: " & ex.GetType().Name)
        End Try

        Console.WriteLine(Quiet())
    End Sub
End Module
----

----

B: two
timeout or cancellation: TimeoutException
1
----

refers to an existing one, which is why it fails when there is none (BC30451):

Module Program
    Sub Main()

            Throw New KeyNotFoundException("short form")
        Catch ex
            Console.WriteLine(ex.Message)
        End Try
    End Sub
End Module

== Exception filters: Catch ... When

`pass:c[Catch ex As T When condition]` adds a Boolean expression to the match. If the expression is `False`, the runtime behaves
as if the block were not there and keeps searching. Visual Basic compiles `When` to a real CLR exception filter, not to an `If`
inside the block followed by a rethrow, and the difference is observable:

* The filter runs during the search phase, _before_ the `Finally` blocks of inner frames run. In the first case below, the
  filter prints before `inner Finally`.
* Because the stack has not been unwound when the filter runs, the original stack trace and the debugger's view of the throwing
  frame are intact.
* An exception thrown inside a filter is swallowed and counts as `False` (case 3).
* A filter that logs and returns `False` observes every exception without ever catching it (case 4). Compare this with
  `Catch ex As Exception` followed by `Throw`, which changes the trace and unwinds first.

[source,vbnet]
----
Option Strict On

Module Program
    Private Function Check(label As String, result As Boolean) As Boolean
        Console.WriteLine("  filter " & label & " -> " & result)
        Return result
    End Function

    Private Sub Inner()
        Try
            Throw New InvalidOperationException("loan table locked")
        Finally
            Console.WriteLine("  inner Finally")
        End Try
    End Sub

    Private Function Faulty() As Boolean
        Throw New NotSupportedException("filter bug")
    End Function

    Sub Main()
        Console.WriteLine("1. filters run before inner Finally blocks:")
        Try
            Inner()
        Catch ex As InvalidOperationException When Check("outer", True)
            Console.WriteLine("  caught " & ex.Message)
        End Try

        Console.WriteLine("2. a False filter lets the next Catch look:")
        Try
            Throw New ArgumentException("code 7")
        Catch ex As ArgumentException When ex.Message.EndsWith("9")
            Console.WriteLine("  nine")
        Catch ex As ArgumentException When ex.Message.EndsWith("7")
            Console.WriteLine("  seven")
        Catch ex As ArgumentException
            Console.WriteLine("  other")
        End Try

        Console.WriteLine("3. an exception inside a filter is swallowed (filter = False):")
        Try
            Try
                Throw New InvalidOperationException("original")
            Catch ex As InvalidOperationException When Faulty()
                Console.WriteLine("  never printed")
            End Try
        Catch ex As Exception
            Console.WriteLine("  outer caught " & ex.GetType().Name & ": " & ex.Message)
        End Try

        Console.WriteLine("4. logging filter that never catches:")
        Try
            Try
                Throw New TimeoutException("lookup timed out")
            Catch ex As Exception When Check("log " & ex.Message, False)
                Console.WriteLine("  never printed")
            End Try
        Catch ex As TimeoutException
            Console.WriteLine("  handled by the outer Catch")
        End Try
    End Sub
End Module
----

  filter outer -> True
  inner Finally
  caught loan table locked
2. a False filter lets the next Catch look:
  seven

Source: https://learn.microsoft.com/dotnet/visual-basic/language-reference/statements/try-catch-finally-statement[Try...Catch...Finally Statement]

Keep filters short, free of side effects other than logging, and cheap: they run for exceptions the block will not handle too.
Typical uses are matching on a property (`ex.HResult`, `ex.ParamName`, `ex.StatusCode`), on the type of the inner exception, or on a
retry counter held in a local variable.

== Finally, Exit Try and Using

`Finally` is for cleanup that must happen on every path. `Exit Try` leaves the `Try` or `Catch` part immediately, skipping the rest of
that block, but it does not skip the `Finally`. A `Return` inside `Try` evaluates its value first, then runs the `Finally`, then
returns. A `Using` statement is a `pass:c[Try ... Finally]` that calls `Dispose`: the resources are disposed (in reverse order of
declaration) before the `Catch` block of an enclosing `Try` runs, because the unwinding happens before the handler starts.

[source,vbnet]
----
Option Strict On

Public Class Connection
    Implements IDisposable

    Private ReadOnly _name As String

    Public Sub New(name As String)
        _name = name
        Console.WriteLine("  open " & _name)
    End Sub

    Public Sub Dispose() Implements IDisposable.Dispose
        Console.WriteLine("  close " & _name)
    End Sub
End Class

Module Program
    Private Function Work() As String
        Try
            Return "value from Try"
        Finally
            Console.WriteLine("  Finally runs after Return was evaluated")
        End Try
    End Function

    Sub Main()
        Console.WriteLine("Using inside Try:")
        Try
            Using first As New Connection("catalog"), second As New Connection("loans")
                Console.WriteLine("  working")
                Throw New InvalidOperationException("lost connection")
            End Using
        Catch ex As InvalidOperationException
            Console.WriteLine("  Catch: " & ex.Message)
        Finally
            Console.WriteLine("  Finally")
        End Try

        Console.WriteLine("Exit Try still runs Finally:")
        Try
            Console.WriteLine("  before Exit Try")
            Exit Try
            Console.WriteLine("  never printed")
        Finally
            Console.WriteLine("  Finally")
        End Try

        Console.WriteLine(Work())

        Console.WriteLine("An exception thrown in Finally replaces the original:")
        Try
            Try
                Throw New InvalidOperationException("original")
            Finally
                Throw New ApplicationException("from Finally")
            End Try
        Catch ex As Exception
            Console.WriteLine("  " & ex.GetType().Name & ": " & ex.Message & " (inner is Nothing: " & (ex.InnerException Is Nothing) & ")")
        End Try
    End Sub
End Module
----

[source,text]
----

  Catch: lost connection
  Finally

  before Exit Try

Two rules matter in `Finally`:

* An exception thrown from `Finally` replaces the one in flight. The original is lost unless you wrap it as the `InnerException`
  of the new one. So `Finally` code should be small and should not throw; `Dispose` implementations must not throw.
* Control cannot leave a `Finally` block: `Return`, `Exit For`, `Exit Do`, `GoTo` and `Exit Sub` out of it are errors (BC30101).
  C# has the same rule (CS0157).

[source,vbnet]
----
Option Strict On

Module Program
    Function Finish() As Integer
        Try
            Return 1
        Finally
            Return 2
        End Try
    End Function
    Sub Loop2()
        For i As Integer = 1 To 3
            Try
                Console.WriteLine(i)
            Finally
                Exit For
            End Try
        Next
    End Sub
    Sub Main()
    End Sub
End Module
----

[source,text]
----
Program.vb(8,13): error BC30101: Branching out of a 'Finally' is not valid.
Program.vb(16,17): error BC30101: Branching out of a 'Finally' is not valid.
----

Cleanup of memory is not the job of `Finally`: the garbage collector reclaims managed memory. Use `Finally`/`Using` for files,
sockets, locks, database connections, temporary state and anything with a `Dispose`. See
xref:programming-languages/visual-basic/object-lifetime-and-disposal.adoc[Object Lifetime and Disposal].

== Throw and rethrow

`Throw expression` raises an exception object (it must derive from `System.Exception`). A bare `Throw` inside a `Catch` block rethrows
the exception being handled and preserves its original stack trace. `Throw ex` also compiles, but it throws the same object as if it
were new at that point: the trace restarts at the `Throw ex` statement and the frames below it are lost. The analyzer CA2200 warns about
this, and it is a warning by default, so the example below was built without `TreatWarningsAsErrors`. (With warnings as errors the
SDK reports `error CA2200` for the same line.) Throwing a new exception that carries the caught one as its `InnerException`, the third
case, keeps both traces.

[source,vbnet]
----
Option Strict On

Public Class CatalogException
    Inherits Exception

    Public Sub New(message As String, innerException As Exception)
        MyBase.New(message, innerException)
    End Sub
End Class

Module Program
    Private Sub Level3()
        Throw New InvalidOperationException("level 3 failed")
    End Sub

    Private Sub Level2(mode As Integer)
        Try
            Level3()
        Catch ex As InvalidOperationException
            Select Case mode
                Case 1
                    Throw                     ' rethrow, keeps the original stack trace
                Case 2
                    Throw ex                  ' throws the same object, restarts the stack trace here
                Case Else
                    Throw New CatalogException("catalog lookup failed", ex)
            End Select
        End Try
    End Sub

    Private Sub Level1(mode As Integer)
        Level2(mode)
    End Sub

    Private Function Frames(ex As Exception) As String
        Dim names As New List(Of String)
        For Each line As String In ex.StackTrace.Split(New String() {Environment.NewLine}, StringSplitOptions.RemoveEmptyEntries)
            Dim text As String = line.Trim().Substring(3)
            names.Add(text.Substring(0, text.IndexOf("("c)))
        Next
        Return String.Join(" <- ", names)
    End Function

    Sub Main()
        For mode As Integer = 1 To 3
            Try
                Level1(mode)
            Catch ex As Exception
                Console.WriteLine("mode " & mode & ": " & ex.GetType().Name & " | " & Frames(ex))
                If ex.InnerException IsNot Nothing Then
                    Console.WriteLine("        inner: " & ex.InnerException.GetType().Name & " | " & Frames(ex.InnerException))
                End If
            End Try
        Next
    End Sub
End Module
----

Built with one warning (`warning CA2200: Re-throwing caught exception changes stack information`). Output:

[source,text]
----
mode 1: InvalidOperationException | ShelfDocs.Program.Level3 <- ShelfDocs.Program.Level2 <- ShelfDocs.Program.Level1 <- ShelfDocs.Program.Main
mode 2: InvalidOperationException | ShelfDocs.Program.Level2 <- ShelfDocs.Program.Level1 <- ShelfDocs.Program.Main
mode 3: CatalogException | ShelfDocs.Program.Level2 <- ShelfDocs.Program.Level1 <- ShelfDocs.Program.Main
        inner: InvalidOperationException | ShelfDocs.Program.Level3 <- ShelfDocs.Program.Level2
----

Source: https://learn.microsoft.com/dotnet/fundamentals/code-analysis/quality-rules/ca2200[CA2200: Rethrow to preserve stack details]

In mode 1 the trace still starts in `Level3`, where the failure happened. In mode 2, after `Throw ex`, `Level3` is gone from the trace.
In mode 3 the new `CatalogException` starts in `Level2` and the original, with its full trace, is its `InnerException`.

To keep a trace while moving an exception between threads or to a later point, capture it with `ExceptionDispatchInfo` (shown
in the properties example below); rethrowing it appends to the original trace instead of replacing it.

=== Throw is a statement, not an expression

C# can write `+value = text ?? throw new ArgumentNullException(...)+`, and C# 7.0 allows `throw` in a conditional or lambda expression
body. Visual Basic has no throw expression: `Throw` is a statement and cannot appear where a value is expected. Use a guard clause
(`ArgumentNullException.ThrowIfNull`, below), an `If` statement, or a small helper `Function` that throws and is used as the second
argument of `If(a, b)`.

[source,vbnet]
----
Option Strict On

Module Program
    Private Function Fail() As Integer
        Throw New InvalidOperationException("fail")
    End Function

    Sub Main()
        ' C# writes: value = text ?? throw new ArgumentNullException(...)   VB has no throw expression.
        Dim text As String = Nothing
        Try
            Dim value As String = If(text, Throw())
        Catch ex As Exception
        End Try
    End Sub
End Module
----

[source,text]
----
Program.vb(12,44): error BC30201: Expression expected.
----

== Exception properties

The members worth knowing, shown in one program: `Message`, `Source` (the assembly name by default), `TargetSite`, `HResult`, the
`Data` dictionary for extra context, `InnerException` and `GetBaseException`, `AggregateException.Flatten`, and `ExceptionDispatchInfo`.

[source,vbnet]
----
Option Strict On
Imports System.Runtime.ExceptionServices

Module Program
    Private Function Boom(code As Integer) As Exception
        Try
            Throw New InvalidOperationException("boom " & code)
        Catch ex As InvalidOperationException
            Return ex
        End Try
    End Function

    Sub Main()
        Dim never As New InvalidOperationException("never thrown")
        Console.WriteLine("StackTrace of an exception that was never thrown is Nothing: " & (never.StackTrace Is Nothing))

        Dim ex As Exception = Boom(1)
        ex.Data("isbn") = "9780306406157"
        ex.Data("attempt") = 2
        ex.HelpLink = "https://example.org/help/boom"
        Console.WriteLine("Message   : " & ex.Message)
        Console.WriteLine("Source    : " & ex.Source)
        Console.WriteLine("TargetSite: " & ex.TargetSite.Name)
        Console.WriteLine("HResult   : 0x" & ex.HResult.ToString("X8"))
        For Each entry As System.Collections.DictionaryEntry In ex.Data
            Console.WriteLine("Data      : " & entry.Key.ToString() & " = " & entry.Value.ToString())
        Next
        Console.WriteLine("GetBaseException: " & ex.GetBaseException().Message)

        Dim wrapped As New InvalidOperationException("outer", New FormatException("middle", New ArgumentException("inner")))
        Console.WriteLine("Base exception of a chain: " & wrapped.GetBaseException().GetType().Name)
        Dim current As Exception = wrapped
        Dim depth As Integer = 0
        Do While current IsNot Nothing
            Console.WriteLine(New String(" "c, depth * 2) & current.GetType().Name & ": " & current.Message)
            current = current.InnerException
            depth += 1
        Loop

        Dim agg As New AggregateException("several", New Exception() {
            New TimeoutException("a"),
            New AggregateException(New Exception() {New FormatException("b"), New KeyNotFoundException("c")})})
        Console.WriteLine("Flatten: " & String.Join(", ", agg.Flatten().InnerExceptions.Select(Function(e) e.GetType().Name)))

        ' Capture an exception here and rethrow it later, keeping its original stack trace
        Dim captured As ExceptionDispatchInfo = ExceptionDispatchInfo.Capture(Boom(2))
        Try
            captured.Throw()
        Catch e2 As InvalidOperationException
            Console.WriteLine("Rethrown with ExceptionDispatchInfo: " & e2.Message & ", trace still mentions Boom: " & e2.StackTrace.Contains("Boom"))
        End Try
    End Sub
End Module
----

== The exception hierarchy

=== The exceptions you meet most often

The program below triggers the common run-time exceptions on purpose, with the messages that .NET 10 produced. Visual Basic's

=== Exceptions that cannot be handled

`StackOverflowException`, and in practice `OutOfMemoryException` when the process really is out of memory, are not something a `Try`
block can recover from. A stack overflow ends the process immediately: neither the `Catch` nor the `Finally` below runs, and the
runtime writes the repeated frame and aborts (exit code 134 on Linux).

[source,vbnet]

Module Program
    Private Function Depth(n As Integer) As Integer

    End Function

    Sub Main()
        Try
            Console.WriteLine("calling")
            Console.WriteLine(Depth(0))
        Catch ex As Exception
            Console.WriteLine("never reached: " & ex.GetType().Name)
        Finally
            Console.WriteLine("never reached: Finally")
        End Try
    End Sub
End Module
----

== Divide by zero, and exceptions as flow control

Introductory material often says that dividing by zero throws `DivideByZeroException`. In Visual Basic that is true only for some
operators. `/` converts both operands to `Double` and divides, so `10 / 0` is `Infinity` and `0 / 0` is `NaN`, with no exception
at all. Integer division `\`, `Mod`, and `Decimal` division throw. `Integer.MinValue \ -1` throws `OverflowException`.

[source,vbnet]
----
Option Strict On

Module Program
    Private Sub Try1(label As String, action As Func(Of Object))
        Try
            Console.WriteLine(label & " = " & Convert.ToString(action()))
        Catch ex As Exception
            Console.WriteLine(label & " throws " & ex.GetType().Name)
        End Try
    End Sub

    Private Function Average(values As IReadOnlyList(Of Integer)) As Double
        If values.Count = 0 Then
            Return 0.0
        End If
        Return CDbl(values.Sum()) / values.Count
    End Function

    Sub Main()
        Dim ten As Integer = 10
        Dim zero As Integer = 0
        Dim minusOne As Integer = -1
        Dim minimum As Integer = Integer.MinValue
        Dim d As Double = 0.0
        Dim m As Decimal = 0D

        Try1("10 / 0 (Integer / Integer)", Function() ten / zero)
        Try1("10 \ 0 (integer division)", Function() ten \ zero)
        Try1("10 Mod 0", Function() ten Mod zero)
        Try1("10.0 Mod 0.0", Function() CDbl(ten) Mod d)
        Try1("10D / 0D", Function() CDec(ten) / m)
        Try1("Integer.MinValue \ -1", Function() minimum \ minusOne)
        Try1("Math.DivRem(10, 0)", Function() Math.DivRem(ten, zero).Quotient)

        Console.WriteLine("average of nothing: " & Average(New List(Of Integer)))
        Try1("Enumerable.Average of nothing", Function() New List(Of Integer)().Average())
        Try1("Enumerable.Max of nothing", Function() New List(Of Integer)().Max())
    End Sub
End Module
----

The practical lessons are the same as for any exception:

* Validate the input instead of catching the failure when the failure is expected: test `If divisor = 0 Then`, return a default,
  or return a result type. `Average` of an empty list is a design decision (zero, `Nothing`, an error), not a case for `Try`.
* Do not use exceptions for ordinary control flow. The `Try` pattern (`Integer.TryParse`, `Dictionary.TryGetValue`, the shelf's
  `Isbn.TryParse`) produces the same results without throwing; a thrown-and-caught exception captures a stack trace and
  unwinds frames, which costs far more than a failed parse. The two loops below give identical results:

[source,vbnet]
----
Option Strict On

Module Program
    Sub Main()
        Dim inputs As New List(Of String)
        For i As Integer = 0 To 9999
            inputs.Add(If(i Mod 4 = 0, "x" & i, i.ToString()))
        Next

        ' 1. Exceptions as the validation mechanism: expensive when most inputs fail
        Dim bad1 As Integer = 0
        Dim sum1 As Long = 0
        For Each text As String In inputs
            Try
                sum1 += Integer.Parse(text)
            Catch ex As FormatException
                bad1 += 1
            End Try
        Next

        ' 2. The Try pattern: no exception object, no stack trace capture
        Dim bad2 As Integer = 0
        Dim sum2 As Long = 0
        For Each text As String In inputs
            Dim value As Integer
            If Integer.TryParse(text, value) Then
                sum2 += value
            Else
                bad2 += 1
            End If
        Next

        Console.WriteLine("Parse + Catch    : bad=" & bad1 & " sum=" & sum1)
        Console.WriteLine("TryParse         : bad=" & bad2 & " sum=" & sum2)
    End Sub
End Module
----

----

== Custom exceptions and guard clauses

Derive custom exceptions from `Exception` (or from a more specific type), not from `ApplicationException`: the .NET design
guidelines no longer recommend that base class, and it adds nothing. Name them with the `Exception` suffix, offer the standard
constructors (no arguments, a message, a message and an inner exception), and add properties for the data a handler needs.
Create a custom type only when callers will handle it differently from the existing ones; otherwise throw a standard
type (`ArgumentException`, `InvalidOperationException`, `NotSupportedException`).

Guard clauses check arguments first and throw before any work is done. The throw helpers on `ArgumentNullException`,
`ArgumentException` and `ArgumentOutOfRangeException` capture the parameter name from the argument expression, so the message names
the parameter without a string literal. They are ordinary shared methods, so they work from Visual Basic exactly as from C#.

[source,vbnet]
----
Option Strict On

Public Class CatalogException
    Inherits Exception

    Public Sub New()
        MyBase.New()
    End Sub

    Public Sub New(message As String)
        MyBase.New(message)
    End Sub

    Public Sub New(message As String, innerException As Exception)
        MyBase.New(message, innerException)
    End Sub
End Class

Public Class BookNotFoundException
    Inherits CatalogException

    Public ReadOnly Property IsbnText As String

    Public Sub New(isbnText As String)
        MyBase.New("No book with ISBN " & isbnText & " is in the catalog.")
        Me.IsbnText = isbnText
    End Sub
End Class

Public Class Catalog
    Private ReadOnly _titles As New Dictionary(Of String, String)

    Public Sub Add(isbnText As String, title As String, copies As Integer)
        ArgumentException.ThrowIfNullOrWhiteSpace(isbnText)
        ArgumentNullException.ThrowIfNull(title)
        ArgumentOutOfRangeException.ThrowIfNegativeOrZero(copies)
        _titles(isbnText) = title
    End Sub

    Public Function TitleOf(isbnText As String) As String
        Dim title As String = Nothing
        If Not _titles.TryGetValue(isbnText, title) Then
            Throw New BookNotFoundException(isbnText)
        End If
        Return title
    End Function
End Class

Module Program
    Sub Main()
        Dim catalog As New Catalog()
        Dim attempts As New List(Of Action) From {
            Sub() catalog.Add("9780306406157", Nothing, 1),
            Sub() catalog.Add("   ", "Dune", 1),
            Sub() catalog.Add("9780306406157", "Dune", 0),
            Sub() catalog.Add("9780306406157", "Dune", 2),
            Sub() Console.WriteLine(catalog.TitleOf("9780306406157")),
            Sub() Console.WriteLine(catalog.TitleOf("9781234567897"))
        }
        For Each attempt As Action In attempts
            Try
                attempt()
            Catch ex As ArgumentException
                Console.WriteLine(ex.GetType().Name & ": " & ex.Message.Replace(Environment.NewLine, " | ") & " [ParamName=" & ex.ParamName & "]")
            Catch ex As BookNotFoundException
                Console.WriteLine(ex.GetType().Name & ": " & ex.Message & " [IsbnText=" & ex.IsbnText & "]")
            End Try
        Next
    End Sub
End Module
----

Notes on the example:

* `ArgumentNullException.ThrowIfNull` exists since .NET 6; `ArgumentException.ThrowIfNullOrWhiteSpace`,
  `ArgumentOutOfRangeException.ThrowIfNegativeOrZero` and the comparison helpers such as `ThrowIfGreaterThan` since .NET 8. The
  older form is `If title Is Nothing Then Throw New ArgumentNullException(NameOf(title))`.
* The message of the `ArgumentOutOfRangeException` has two lines on .NET 10 (the example replaces the line break with a bar).
* The parameter in the constructor is named `isbnText` and the property `IsbnText`. Visual Basic is case-insensitive, so the
  assignment is written `Me.IsbnText = isbnText`; plain `IsbnText = isbnText` would assign the parameter to itself.

== Global handlers and logging

An exception that no `Catch` handles is _unhandled_ and, in a .NET process, ends the process after the runtime has given the
application one chance to log it. Global handlers are for logging and for a clean shutdown (or, in a UI, for keeping the window
open), not for routine error handling: after an `AppDomain.UnhandledException` the process terminates whatever the handler does.

[cols="3,5,3",options="header"]
|===
|Hook |Fires for |Where it applies

|`AppDomain.CurrentDomain.UnhandledException` |an exception not caught on any thread; the process ends afterwards (`IsTerminating` is `True`) |every application type
|`AppDomain.CurrentDomain.FirstChanceException` |every exception when first thrown, before any handler is searched; observation only |every application type
|`TaskScheduler.UnobservedTaskException` |a faulted `Task` that nobody awaited, observed when the task is finalized; `SetObserved()` marks it handled |every application type
|`Application.ThreadException` |an exception from a Windows Forms event handler or message-loop callback on the UI thread |Windows Forms
|`My.Application.UnhandledException` |the same, in a Windows Forms project that uses the VB Application Framework; `e.ExitApplication = False` keeps the app running |Windows Forms with the Application Framework
|`Dispatcher.UnhandledException` |an exception on a WPF dispatcher thread |WPF
|===

The console program below registers three of the hooks, handles one exception normally, leaves a faulted task unobserved and then
throws an exception that nothing catches. The runtime prints its own report after the handler finishes and the process aborts
(exit code 134 on Linux; Windows reports a different code).

[source,vbnet]
----
Option Strict On
Imports System.Runtime.CompilerServices
Imports System.Runtime.ExceptionServices

Module Program
    <MethodImpl(MethodImplOptions.NoInlining)>
    Private Sub FaultAndForget()
        Task.Run(Sub() Throw New TimeoutException("task nobody awaited"))
        Threading.Thread.Sleep(200)
    End Sub

    Sub Main()
        AddHandler AppDomain.CurrentDomain.FirstChanceException,
            Sub(sender As Object, e As FirstChanceExceptionEventArgs)
                Console.WriteLine("FirstChance : " & e.Exception.GetType().Name)
            End Sub

        AddHandler AppDomain.CurrentDomain.UnhandledException,
            Sub(sender As Object, e As UnhandledExceptionEventArgs)
                Dim ex As Exception = DirectCast(e.ExceptionObject, Exception)
                Console.WriteLine("Unhandled   : " & ex.Message & " (IsTerminating=" & e.IsTerminating & ")")
            End Sub

        AddHandler TaskScheduler.UnobservedTaskException,
            Sub(sender As Object, e As UnobservedTaskExceptionEventArgs)
                Console.WriteLine("Unobserved  : " & e.Exception.InnerException.Message)
                e.SetObserved()
            End Sub

        Try
            Throw New FormatException("handled one")
        Catch ex As FormatException
            Console.WriteLine("Caught      : " & ex.Message)
        End Try

        FaultAndForget()
        GC.Collect()
        GC.WaitForPendingFinalizers()

        Console.WriteLine("Throwing an exception nobody catches...")
        Throw New InvalidOperationException("nobody catches this")
    End Sub
End Module
----

=== Logging

Log an exception once, where it is handled, with the whole exception object, not just `ex.Message`: the logger renders the type,
the message, the inner exceptions and the stack trace, and structured loggers keep the exception as a field.
`Microsoft.Extensions.Logging` is the abstraction used by ASP.NET Core, the generic host and many libraries; sinks such as
Serilog and NLog plug in behind it. The example uses the console provider from the `Microsoft.Extensions.Logging.Console` package
(version 10.0.0, restored from NuGet), and a message template with named placeholders rather than string concatenation.

[source,xml]
----
<Project Sdk="Microsoft.NET.Sdk">
  <PropertyGroup>
    <OutputType>Exe</OutputType>
    <TargetFramework>net10.0</TargetFramework>
    <RootNamespace>ShelfDocs</RootNamespace>
    <OptionStrict>On</OptionStrict>
    <TreatWarningsAsErrors>true</TreatWarningsAsErrors>
    <NuGetAudit>false</NuGetAudit>
  </PropertyGroup>
  <ItemGroup>
    <PackageReference Include="Microsoft.Extensions.Logging.Console" Version="10.0.0" />
  </ItemGroup>
</Project>
----

[source,vbnet]
----
Option Strict On
Imports Microsoft.Extensions.Logging

Public Class LoanService
    Private ReadOnly _logger As ILogger(Of LoanService)

    Public Sub New(logger As ILogger(Of LoanService))
        _logger = logger
    End Sub

    Public Sub Renew(loanId As Integer, extraDays As Integer)
        Try
            ArgumentOutOfRangeException.ThrowIfGreaterThan(extraDays, 14)
            _logger.LogInformation("Loan {LoanId} renewed by {ExtraDays} days", loanId, extraDays)
        Catch ex As ArgumentOutOfRangeException
            _logger.LogError(ex, "Could not renew loan {LoanId}", loanId)
            Throw
        End Try
    End Sub
End Class

Module Program
    Sub Main()
        Using factory As ILoggerFactory = LoggerFactory.Create(
            Sub(builder) builder.SetMinimumLevel(LogLevel.Information).AddSimpleConsole())
            Dim service As New LoanService(factory.CreateLogger(Of LoanService)())
            service.Renew(7, 7)
            Try
                service.Renew(8, 30)
            Catch ex As ArgumentOutOfRangeException
                System.Console.WriteLine("caller still sees: " & ex.GetType().Name)
            End Try
        End Using
    End Sub
End Module
----

----

      Loan 7 renewed by 7 days
caller still sees: ArgumentOutOfRangeException
fail: ShelfDocs.LoanService[0]
      Could not renew loan 8

Source: https://learn.microsoft.com/dotnet/core/extensions/logging[Logging in .NET]

Two details. The `LogError(ex, template, args)` overload takes the exception first. And the `Throw` after logging rethrows to the
caller; the outcome is a logged and still-propagating exception, which is right when this layer cannot recover. Logging and then
swallowing is only right at a boundary that really handles the failure. The console provider writes on a background thread, so the
order of its lines relative to `Console.WriteLine` is not guaranteed (here `caller still sees` came out before the `fail` entry).
Because the logging namespace contains a child namespace called `Console`, the program qualifies `System.Console.WriteLine`; with
`Imports Microsoft.Extensions.Logging` an unqualified `Console.WriteLine` fails with BC30456, because `Console` now binds to
`Microsoft.Extensions.Logging.Console`.

== Exceptions in asynchronous code

Exceptions thrown inside an `Async` method are stored in the returned `Task`, and `Await` rethrows them with their original type at the
awaiting line. `Task.WhenAll` collects several failures, but `Await` rethrows only the first; the full list is in `Task.Exception`. Blocking
with `Wait()` or `.Result` wraps everything in an `AggregateException`.

[source,vbnet]
----
Option Strict On

Module Program
    Private Async Function LookupAsync(isbnText As String) As Task(Of String)
        Await Task.Delay(10)
        Throw New KeyNotFoundException("no book " & isbnText)
    End Function

    Private Async Function FailAfterAsync(ms As Integer, label As String) As Task
        Await Task.Delay(ms)
        Throw New InvalidOperationException(label)
    End Function

    Private Async Function RunAsync() As Task
        Try
            Dim title As String = Await LookupAsync("9780306406157")
            Console.WriteLine(title)
        Catch ex As KeyNotFoundException
            Console.WriteLine("Await rethrows the original type: " & ex.Message)
        End Try

        Dim both As Task = Task.WhenAll(FailAfterAsync(10, "first"), FailAfterAsync(30, "second"))
        Try
            Await both
        Catch ex As InvalidOperationException
            Console.WriteLine("Await keeps only the first: " & ex.Message)
            Console.WriteLine("Task.Exception has them all: " & both.Exception.InnerExceptions.Count)
        End Try

        Try
            both.Wait()
        Catch ex As AggregateException
            Console.WriteLine("Wait wraps them: " & ex.GetType().Name & " with " & ex.InnerExceptions.Count & " inner exceptions")
        End Try
    End Function

    Sub Main()
        RunAsync().GetAwaiter().GetResult()
    End Sub
End Module
----

[source,text]
----
Await rethrows the original type: no book 9780306406157
Await keeps only the first: first
Task.Exception has them all: 2
Wait wraps them: AggregateException with 2 inner exceptions
----

Source: https://learn.microsoft.com/dotnet/visual-basic/language-reference/operators/await-operator[Await Operator]

Visual Basic has a restriction that C# no longer has: `Await` cannot appear inside a `Catch` block, a `Finally` block or a `SyncLock`
(BC36943). Move the awaited call after the `Try` statement, record the outcome in a local variable, or restructure the loop.

[source,vbnet]
----
Option Strict On

Module Program
    Private Async Function RunAsync() As Task
        Try
            Throw New InvalidOperationException("in Try")
        Catch ex As InvalidOperationException
            Await Task.Delay(1)
        Finally
            Await Task.Delay(1)
        End Try
    End Function

    Sub Main()
        RunAsync().GetAwaiter().GetResult()
    End Sub
End Module
----

[source,text]
----
Program.vb(8,13): error BC36943: 'Await' cannot be used inside a 'Catch' statement, a 'Finally' statement, or a 'SyncLock' statement.
Program.vb(10,13): error BC36943: 'Await' cannot be used inside a 'Catch' statement, a 'Finally' statement, or a 'SyncLock' statement.
----

More on `Task`, cancellation and `Async Sub` on xref:programming-languages/visual-basic/async-and-await.adoc[Async and Await].

== Differences from C#

[cols="3,4,4",options="header"]
|===
|Topic |Visual Basic |C#

|Syntax |`pass:c[Try ... Catch ex As T When ... Finally ... End Try]` |`+try { } catch (T ex) when (...) { } finally { }+`
|Rethrow |`Throw` keeps the trace; `Throw ex` restarts it (CA2200 warning) |`throw;` keeps the trace; `throw ex;` restarts it
|Throw in an expression |not possible (BC30201) |`+x ?? throw ...+`, `+cond ? a : throw ...+` since C# 7.0
|`Await` in `Catch`/`Finally` |not allowed (BC36943) |allowed since C# 6
|Leaving `Finally` |BC30101 |CS0157
|Unreachable catch order |BC42029 warning |CS0160 error
|Exception variable |declared by `As` in each `Catch` |declared in the parentheses
|Overflow |checked by default: `pass:c[Integer.MaxValue + 1]` throws `OverflowException` |unchecked by default; use `checked`
|`/` on integers |returns `Double`, so division by zero gives `Infinity` |integer division, throws `DivideByZeroException`
|Text to number |`CInt("12x")` throws `InvalidCastException`; `Integer.Parse` throws `FormatException` |`int.Parse` throws `FormatException`
|Legacy model |`On Error`, `Resume`, `Err` |none
|===

== Where introductory material is out of date

Introductory VB.NET books and tutorials, including popular ones, were mostly written for earlier Visual Studio versions. For exceptions, check these points when
you meet them:

* `10 / 0` does not throw: it is `Infinity`. Only `\`, `Mod` and `Decimal` division throw `DivideByZeroException`.
* `ApplicationException` as the base of custom exceptions is outdated advice; derive from `Exception`.
* A serialization constructor and `<Serializable>` on custom exceptions are no longer needed and warn on .NET 10 (SYSLIB0051).
* `Catch` order matters, and a base type first produces BC42029, not a working program.
* `CInt`, `CDbl` and `CDate` on text throw `InvalidCastException`, not `FormatException`. Prefer the `TryParse` methods.
* Logging with `Debug.WriteLine` or a text file is replaced by `Microsoft.Extensions.Logging` (or a framework behind it).
* A global handler cannot keep a console or service process alive after `AppDomain.UnhandledException`; only a UI framework
  event such as `Application.ThreadException` can.
* `On Error` is not how new Visual Basic is written; see
  xref:programming-languages/visual-basic/unstructured-error-handling-on-error.adoc[On Error].

== Version notes and pitfalls

[cols="3,5",options="header"]
|===
|Topic |Note

|`Try`/`Catch`/`Finally`, `Throw` |available since the first .NET version of Visual Basic; the replacement for the VB6 `On Error` model
|`When` filters |compile to CLR exception filters (observable in the first-pass behaviour above)
|Throw helpers |`ThrowIfNull` since .NET 6; `ThrowIfNullOrWhiteSpace`, `ThrowIfNegativeOrZero`, `ThrowIfGreaterThan` since .NET 8
|Obsolete serialization constructor |SYSLIB0051 on current .NET versions
|Windows-only hooks |`Application.ThreadException` and `My.Application.UnhandledException` are Windows Forms; WPF has `Dispatcher` events
|.NET Framework |the same `Try` model; `Microsoft.Extensions.Logging` is a NuGet package there; the Application Framework hooks are the same
|===

Pitfalls:

* Catching `Exception` and doing nothing hides defects. Log and rethrow, or handle a specific type.
* `Throw ex` loses the trace; use `Throw`.
* Messages are for people. Do not parse `ex.Message`; branch on the type, on `HResult` or on a property.
* An exception in `Finally` or `Dispose` masks the original.
* Do not catch `NullReferenceException`, `IndexOutOfRangeException` or `InvalidCastException` to cope with bad input; test the
  input. They indicate defects.
* `Using` and `Finally` do not run when the process is terminated (stack overflow, `End`, `Environment.FailFast`).
