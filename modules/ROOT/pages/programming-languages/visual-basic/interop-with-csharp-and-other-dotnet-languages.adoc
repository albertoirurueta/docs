include::partial$visual-basic-disclaimer.adoc[]

This page is written against Visual Basic 17.13 on .NET 10 (SDK 10.0.402, with the C# 14 and F# compilers of that SDK) and was checked on 2026-10-19. Every program on it is part of one
scratch solution, `Shelf.slnx`, that was built in the .NET 10 SDK container (Linux, arm64) with warnings treated as errors, and the console programs were run there. The programs that are meant to fail
show the compiler messages the SDK printed; in those, warnings are not errors. The root namespaces are `Shelf.Core`, `Shelf.Pricing`, `Shelf.Cli`, `Shelf.CsClient` and `Shelf.Fs`.
The version numbers in the second column of the feature table (15, 16.9, 17.13) are the Visual Basic versions recorded in this section's research notes for when support was added; they were not re-measured here.
The behaviours are what the 17.13 compiler in the container actually did, and they are the part to rely on. Microsoft's release notes for the language are linked from https://learn.microsoft.com/dotnet/visual-basic/whats-new/[What's new for Visual Basic].

A .NET assembly does not remember the language it was written in. A C# class library, a Visual Basic one and an F# one all compile to the same metadata and the same IL, so a project in any of them can
reference a project or package in any other. What does not cross freely is *language features*: a feature that the C# compiler encodes in metadata (a modifier, an attribute, a special method name) can be used
from Visual Basic only if the Visual Basic compiler knows how to read that encoding. The Visual Basic language is in a stable, consumption-only mode (see
xref:programming-languages/visual-basic/history-versions-and-language-strategy.adoc[History, Versions and Language Strategy]): new C# and runtime features are added to Visual Basic only when
they are needed to consume them. This page is the map of where that boundary lies in version 17.13, in both directions.

== Referencing another language

* *Project references* are the normal case in one repository. `ProjectReference` copies the output assembly and flows its dependencies (the F# project brings `FSharp.Core` with it into `Shelf.Cli`).
* *Package references* work the same: a NuGet package written in C# is just an assembly. The next program is a separate Visual Basic project that references the `Humanizer.Core` package (written in C#) and calls its extension methods.
* *Assembly references* (`Reference` with a `HintPath`) are the fallback for a binary that is not in a package. Prefer a package or project.
* *Target frameworks* should match or be compatible: a `net10.0` project can reference `net10.0` and `netstandard2.0` libraries, not the other way round. See
  xref:programming-languages/visual-basic/projects-msbuild-and-the-dotnet-cli.adoc[Projects, MSBuild and the .NET CLI] and xref:programming-languages/csharp/namespaces-assemblies-and-projects.adoc[Namespaces, Assemblies and Projects (C#)] for the shared platform detail.

[source,xml]
----
<Project Sdk="Microsoft.NET.Sdk">
  <PropertyGroup>
    <OutputType>Exe</OutputType>
    <TargetFramework>net10.0</TargetFramework>
    <RootNamespace>NugetApp</RootNamespace>
    <OptionStrict>On</OptionStrict>
    <TreatWarningsAsErrors>true</TreatWarningsAsErrors>
    <NuGetAudit>false</NuGetAudit>
  </PropertyGroup>
  <ItemGroup>
    <PackageReference Include="Humanizer.Core" Version="2.14.1" />
  </ItemGroup>
</Project>
----

[source,vbnet]
----
Option Strict On

Imports Humanizer

Module Program
    Sub Main()
        Dim count As Integer = 2
        Console.WriteLine("PascalCaseTitle".Humanize())
        Console.WriteLine("book".ToQuantity(count))
        Console.WriteLine(TimeSpan.FromMinutes(90).Humanize())
    End Sub
End Module
----

1 hour

== What Visual Basic can consume from modern C#

The C# library is split into short files, each shown with the Visual Basic that uses it. The rows of the table below are all tested, and the compiler messages for the failures follow the code.

[cols="3,2,5",options="header"]
|===
|C# feature |Visual Basic version |Result in Visual Basic 17.13 on .NET 10

|Records (C# 9) |n/a |usable as a class: constructor, properties, value `Equals`, `=`, the generated `ToString`, an ordinary `Deconstruct` method; no `With` expression, no positional deconstruction
|Init-only setters (C# 9) |16.9 |assignable in an object initializer or in a constructor of the class; elsewhere BC37311
|`required` members (C# 11) |enforced |BC37321 when not set in the initializer; `SetsRequiredMembers` constructors are honoured; Visual Basic cannot declare `required` or `init`
|Default interface methods (C# 8) |consumed |callable through an interface variable; a Visual Basic class that implements the interface must still write the body (BC30149); not callable on a class variable (BC30456)
|`ref` returns (C# 7) |15 |a ref return can be read into a value and also assigned through; `ref readonly` returns are rejected (BC30657)
|`Span(Of T)`, `ReadOnlySpan(Of T)` (C# 7.2) |local use |a call may pass an array where the parameter is a span; a returned span can be held by an inferred local and its `Length` and `ToArray()` used; its indexer and enumerator cannot (BC30643) and the type cannot be named (BC30668)
|`params Integer()` |ParamArray |works like a Visual Basic `ParamArray`
|`params ReadOnlySpan` (C# 13) |not supported |the values cannot be passed separately (BC30311, BC30057); an array can be passed
|`INumber(Of T)` and other generic-math constraints (C# 11) |consumed |a generic method with the constraint can be called with `Integer` or `Double`; Visual Basic cannot implement `static abstract` interface members (BC37315)
|`unmanaged` constraint (C# 7.3) |17.13 |accepted for blittable value types; `String` is rejected (BC37332 and BC32105)
|`OverloadResolutionPriority` (C# 13) |17.13 |honoured when choosing between overloads
|Extension methods and extension blocks (C# 14) |consumed |methods in an `extension` block are callable as extension methods; extension properties are only reachable as static accessor methods
|Nullable reference annotations (C# 8) |ignored |no warning; passing `Nothing` compiles and fails at run time inside the callee
|Named tuples (C# 7) |15 |element names are honoured
|`async`, `Task`, `IAsyncEnumerable` |consumed |`Await` works; there is no `Await For Each` (BC30201 and BC30092 on the `For`), and `Await` is not allowed in `Finally` (BC36943)
|Events, delegates, indexers, optional parameters |consumed |all work; indexers appear as default properties
|`dynamic` (C# 4) |`Object` |the attribute is ignored; use a late-bound call site, see xref:programming-languages/visual-basic/early-and-late-binding.adoc[Early and Late Binding]
|F# unions and options |consumed |factory methods and `Tag`; `None` is `Nothing`; `FSharp.Core` must be referenced
|===

The authoritative list of what the C# compiler itself supports in each version is Roslyn's *Language Feature Status* page, https://github.com/dotnet/roslyn/blob/main/docs/Language%20Feature%20Status.md[Language Feature Status]; the C# column above corresponds to the versions in
https://learn.microsoft.com/dotnet/csharp/whats-new/[What's new in C#]. A feature that is not in the table has simply not been tested for this page.

=== Records, init-only setters and required members

The C# side defines a positional record, a class with an init-only property and a `required` member, a default interface method, and an abstract base class:

[source,csharp]
----
using System.Diagnostics.CodeAnalysis;

namespace Shelf.Pricing;

// A positional record: Visual Basic sees a class with properties, a constructor and value equality.
public record Price(decimal Amount, string Currency);

// An init-only setter and a required member.
public sealed class Discount
{
    public required string Code { get; init; }
    public decimal Percent { get; init; }

    public Discount() { }

    [SetsRequiredMembers]
    public Discount(string code, decimal percent)
    {
        Code = code;
        Percent = percent;
    }
}

// A default interface method: the body lives in the interface.
public interface ILabel
{
    string Text { get; }
    string Upper() => Text.ToUpperInvariant();
}

public sealed class ShelfLabel : ILabel
{
    public string Text { get; init; } = "";
}

// An abstract base class that Visual Basic classes can derive from.
public abstract class Pricer
{
    public virtual string Name => "base pricer";
    public abstract decimal Compute(decimal basePrice);
}
----

Three details are worth reading out of the output. `first = second` compiled and returned `True`, because a record defines `op_Equality` and Visual Basic resolves `=` through it; `ReferenceEquals` is `False`, so the equality is by value. `Deconstruct` is an ordinary method with
`ByRef` parameters (there is no `Dim (a, b) = price` in Visual Basic; see xref:programming-languages/visual-basic/tuples-and-anonymous-types.adoc[Tuples and Anonymous Types]).
And the initializer syntax `+New Discount With {.Code = "SPRING", .Percent = 15D}+` is the only way to set an init-only property of an object you did not construct inside the class.

=== Default interface members and inheritance

A C# interface can carry a method body (`Upper` in `ILabel`). Visual Basic can call it through an interface variable, but a Visual Basic class that implements the interface must write the body itself. Visual Basic can derive from the C# abstract class `Pricer` and override its virtual members.

[source,vbnet]
----
Option Strict On

Imports Shelf.Pricing

Public Class SeasonalPricer
    Inherits Pricer

    Public Overrides ReadOnly Property Name As String
        Get
            Return "seasonal (" & MyBase.Name & ")"
        End Get
    End Property

    Public Overrides Function Compute(basePrice As Decimal) As Decimal
        Return Math.Round(basePrice * 0.9D, 2)
    End Function
End Class

Public Class PlainLabel
    Implements ILabel

    Public ReadOnly Property Text As String Implements ILabel.Text
        Get
            Return "plain"
        End Get
    End Property

    ' Visual Basic classes must write the body of a default interface method themselves.
    Public Function Upper() As String Implements ILabel.Upper
        Return Text.ToUpperInvariant()
    End Function
End Class

Module InterfacesAndInheritance
    Sub Run()
        Dim label As ILabel = New ShelfLabel With {.Text = "abc"}
        Console.WriteLine(label.Upper())

        ' A Visual Basic implementation of the interface, with its own Upper.
        Dim plain As ILabel = New PlainLabel()
        Console.WriteLine(plain.Upper())

        Dim pricer As Pricer = New SeasonalPricer()
        Console.WriteLine(pricer.Name)
        Console.WriteLine(pricer.Compute(20D))
    End Sub
End Module
----

=== Ref returns, spans and params

[source,csharp]
----
using System.Numerics;
using System.Runtime.CompilerServices;
using Shelf.Core;

namespace Shelf.Pricing;

public static class PriceMath
{
    // Ref returns, spans and params.
    public static ref int RefTo(int[] values, int index) => ref values[index];

    public static ref readonly int RefReadOnlyTo(int[] values, int index) => ref values[index];

    public static int SumSpan(ReadOnlySpan<int> values)
    {
        int sum = 0;
        foreach (int v in values) sum += v;
        return sum;
    }

    public static ReadOnlySpan<int> Head(int[] values) => values.AsSpan(0, 2);

    public static int Total(params int[] values) => values.Sum();

    public static int TotalSpan(params ReadOnlySpan<int> values) => SumSpan(values);

    // Generic constraints that Visual Basic cannot write itself.
    public static T Sum<T>(IEnumerable<T> values) where T : INumber<T>
    {
        T total = T.Zero;
        foreach (T v in values) total += v;
        return total;
    }

    public static int SizeOf<T>() where T : unmanaged => Unsafe.SizeOf<T>();

    // Overload resolution priority (C# 13): the object overload wins for a string argument.
    [OverloadResolutionPriority(1)]
    public static string Prefer(object value) => "object (priority 1)";

    public static string Prefer(string value) => "string";

    // ByRef and Optional.
    public static void Swap<T>(ref T a, ref T b) => (a, b) = (b, a);

    public static bool TryRate(string key, out decimal rate)
    {
        rate = key == "EUR" ? 1.0m : 1.1m;
        return key.Length == 3;
    }

    public static int Optional(int a, int b = 10, string label = "n") => a + b + label.Length;

    // Tuples, nullable annotations and non-null parameters.
    public static (string Name, int Count) Stats(Catalog catalog) => ("catalog", catalog.Search("").Count());

    public static string? Find(string key) => key == "x" ? "found" : null;

    public static int LengthOf(string text) => text.Length;

    // Async.
    public static Task<Price> LoadAsync(decimal amount) => Task.FromResult(new Price(amount, "EUR"));

    public static async IAsyncEnumerable<int> CountAsync(int n)
    {
        for (int i = 1; i <= n; i++)
        {
            await Task.Yield();
            yield return i;
        }
    }

    public static dynamic MakeDynamic() => new System.Dynamic.ExpandoObject();
}
----

The Visual Basic side uses the first group:

[source,vbnet]
----
Option Strict On

Imports Shelf.Pricing

Module RefsSpansAndParams
    Sub Run()
        Dim numbers = New Integer() {1, 2, 3}

        ' A ref return can be read, and also written through.
        Dim copy As Integer = PriceMath.RefTo(numbers, 1)
        Console.WriteLine(copy)
        PriceMath.RefTo(numbers, 1) = 99
        Console.WriteLine(numbers(1))

        ' Spans: an array converts to ReadOnlySpan(Of Integer) at the call.
        Console.WriteLine(PriceMath.SumSpan(numbers))

        ' A returned span can be held in an inferred local; its indexer cannot be used.
        Dim head = PriceMath.Head(numbers)
        Console.WriteLine(head.Length)
        Console.WriteLine(String.Join(",", head.ToArray()))

        ' A params ReadOnlySpan parameter accepts an array, not a list of values.
        Console.WriteLine(PriceMath.TotalSpan(numbers))

        ' params Integer() is a ParamArray.
        Console.WriteLine(PriceMath.Total(1, 2, 3))
        Console.WriteLine(PriceMath.Total())
    End Sub
End Module
----

`PriceMath.RefTo(numbers, 1) = 99` changed the array element: Visual Basic treats a call that returns a reference as an assignable expression. That is a useful low-level
tool, and also a way to change data from a place that looks like a read, so keep it out of ordinary application code. `SumSpan(numbers)` passed an array where the parameter is a `ReadOnlySpan(Of Integer)`, because
the span type has an implicit conversion from arrays and Visual Basic honours user-defined conversions on method arguments.

What does not work is any use of a `ref struct` (such as a span) beyond holding it in an inferred local:

== Names, case and CLS compliance

Visual Basic identifiers are case-insensitive, C# ones are not, and the Common Language Specification (CLS) is the set of rules for a public API that every language can use. A C# library that declares `Value` and `value` in the same class is legal C#, and not CLS-compliant. A project that marks
its assembly `CLSCompliant(True)` asks its own compiler to report these problems:

[source,csharp]
----
[assembly: System.CLSCompliant(true)]

namespace Shelf.Cls;

public class Clash
{
    public int Value { get; set; } = 1;
    public int value { get; set; } = 2;
    public string Name() => "method";
    public string name() => "other";
    public uint Counter() => 7;
}

public class Ok
{
    public int Count { get; set; } = 3;
}
----

The C# compiler reports, for that file:

[source,text]
----
Cls/Cls.cs(8,16): warning CS3005: Identifier 'Clash.value' differing only in case is not CLS-compliant
Cls/Cls.cs(8,24): warning CS3005: Identifier 'Clash.value.get' differing only in case is not CLS-compliant
Cls/Cls.cs(8,29): warning CS3005: Identifier 'Clash.value.set' differing only in case is not CLS-compliant
Cls/Cls.cs(10,19): warning CS3005: Identifier 'Clash.name()' differing only in case is not CLS-compliant
Cls/Cls.cs(11,17): warning CS3002: Return type of 'Clash.Counter()' is not CLS-compliant
----

Visual Basic cannot decide which member a case-insensitive name means. Two members that differ only in case, or a method and a property with the same name, are ambiguous at the call site:

[source,vbnet]
----
Option Strict On

Imports Shelf.Core
Imports Shelf.Pricing
Imports Shelf.Cls

Module Program
    Sub Main()
        Dim item As New Clash()
        Console.WriteLine(item.Value)
    End Sub
End Module
----

[source,text]
----
Program.vb(10,32): error BC31429: 'Value' is ambiguous because multiple kinds of members with this name exist in class 'Clash'. 
----

Source: https://learn.microsoft.com/dotnet/visual-basic/misc/bc31429[BC31429]

[source,vbnet]
----
Option Strict On

Imports Shelf.Core
Imports Shelf.Pricing

Module Program
    Sub Main()
        Dim cls As New Shelf.Cls.Clash()
        Console.WriteLine(cls.Name())
    End Sub
End Module
----

[source,text]
----
Program.vb(9,31): error BC31429: 'Name' is ambiguous because multiple kinds of members with this name exist in class 'Clash'. 
----

Source: https://learn.microsoft.com/dotnet/standard/language-independence[Language independence] and https://learn.microsoft.com/dotnet/api/system.clscompliantattribute[CLSCompliantAttribute]

The same attribute on the Visual Basic side makes the Visual Basic compiler report a public member that other languages could not use, such as an unsigned type:

[source,vbnet]
----
Option Strict On

<Assembly: CLSCompliant(True)>

Public Class Reading
    Public Function Counter() As UInteger
        Return 7UI
    End Function

    Public Sub Scale(factor As ULong)
    End Sub

    Public Sub Print()
    End Sub

    Public Sub print(value As Integer)
    End Sub
End Class

Module Program
    Sub Main()
    End Sub
End Module
----

[source,text]
----
Program.vb(6,21): warning BC40027: Return type of function 'Counter' is not CLS-compliant. 
Program.vb(10,22): warning BC40028: Type of parameter 'factor' is not CLS-compliant. 
----

For a mixed-language solution the rules reduce to a short list:

[cols="3,5",options="header"]
|===
|Rule |Reason

|Do not expose members that differ only in case, in either language |Visual Basic cannot bind them (BC31429); C# callers cannot tell which is meant when a Visual Basic library is reached by case-folding tools
|Prefer `Integer`, `Long`, `Double`, `Decimal`, `String`, `Boolean`, `Date` in public signatures; avoid unsigned types and `ref` structs |not CLS-compliant (CS3002 in C#, BC40027 and BC40028 in Visual Basic) and `ref` structs cannot be named in Visual Basic
|Avoid public members named like keywords of either language |`[End]`, `@class` work but make every caller type brackets
|Avoid parameterised properties and `Module`-only designs in libraries that C# callers use |C# sees accessor methods; a module is a static class
|Avoid `ref readonly`, `params` spans, `static abstract` implementations and `required` or `init` in an API that a Visual Basic project must implement |Visual Basic cannot implement or express them
|Put `<Assembly: CLSCompliant(True)>` (or `[assembly: CLSCompliant(true)]`) on the library and keep warnings visible |the compiler of the library's own language then lists the problems for you
|===

== Other .NET languages

* *F#* is shown above. The things to remember are `FSharp.Core` (a runtime dependency of any assembly that exposes F# types), unions as classes with `New` factories and `Tag`, and `option` being a nullable reference.
* *C++/CLI* (Windows only) produces ordinary managed assemblies too; they are referenced like any other, and the same CLS rules apply. This was not tested for this page.
* *Visual Basic from C#* works through the same mechanisms in reverse. If the public API of a Visual Basic library exposes Visual Basic runtime types such as `Collection`, the C# project needs `Microsoft.VisualBasic.Core`, which is part of the shared framework, so no package is needed. xref:programming-languages/csharp/csharp-and-dotnet.adoc[C# and .NET] has the C# view of the same options.
* *Java* is not a .NET language and has no built-in interoperability with Visual Basic; bridges such as IKVM or JNI exist as third-party and native options and are not covered here.

== When a library needs a feature Visual Basic cannot express

Visual Basic is in a stable, consumption-only state, so the right move for a feature it lacks is to *put that part in C#* in the same solution, as `Shelf.Pricing` does here. The pattern that works:

. Isolate the unsupported feature in a small C# class library (generic math, ref structs, spans, source generators, `static abstract` interface implementations, `required`/`init`, `ref readonly`).
. Expose a CLS-friendly public API from it: arrays, `IReadOnlyList(Of T)`, `Task`, plain classes and records, delegates. Avoid spans and `ref` in the signatures Visual Basic must call.
. Reference it from the Visual Basic project with a `ProjectReference` (as `Shelf.Cli` does) and put both under one solution so that a single `dotnet build` and `dotnet test` cover them.
. Test the boundary from Visual Basic. The example above is the template: one Visual Basic file per C# feature, built with `Option Strict On`.
. Use `InternalsVisibleTo` for test projects only; do not use it to give a Visual Basic project access to C# internals.

Source generators are an example that crosses the boundary badly: the generated code is C#, and in the experiments for xref:programming-languages/visual-basic/serialization-json-and-xml.adoc[Serialization: JSON and XML] a generator attached to a Visual Basic project was not usable (BC30610), so put types that need a generator in a C# project and reference it.

== Where older material is outdated

* Older guides describe interoperating by adding a reference to a `.dll` built for .NET Framework, and registering assemblies in the GAC. For current .NET use project and package references; the GAC is a .NET Framework concept.
* Advice that Visual Basic "cannot use" modern C# is too strong and too weak: it can consume records, `init`, `required`, default interface members, generic-math methods and overload priority; it cannot implement `static abstract` members, use spans, or declare the newer modifiers. The table above is the current state.
* Statements that a C# project cannot reference a Visual Basic project, or the reverse, are wrong for SDK-style projects: any language mix is fine.
* Material that treats the `Microsoft.VisualBasic` namespace as a .NET Framework component to avoid in C# is outdated for .NET: `Microsoft.VisualBasic.Core` is part of the shared framework.
