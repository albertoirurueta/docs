== The SDK-style project file

A Visual Basic project today is an *SDK-style* project: a short XML file whose root element names an SDK
(`Sdk="Microsoft.NET.Sdk"`). The SDK supplies, through imported `.props` and `.targets` files, everything a project used to list by
hand: the source files (a glob), the references to the framework, the default imports, the compiler settings and the build targets.
This is what `dotnet new` writes for the three most common project types (the sources are in the next sections; the listing shows
the project files exactly as the templates wrote them):

[source,xml]
----
<!-- dotnet new classlib -lang VB -o Shelf.Core -->
<Project Sdk="Microsoft.NET.Sdk">

  <PropertyGroup>
    <RootNamespace>Shelf.Core</RootNamespace>
    <TargetFramework>net10.0</TargetFramework>
  </PropertyGroup>

</Project>

<!-- dotnet new console -lang VB -o Shelf.Cli, then: dotnet add Shelf.Cli reference Shelf.Core -->
<Project Sdk="Microsoft.NET.Sdk">

  <ItemGroup>
    <ProjectReference Include="..\Shelf.Core\Shelf.Core.vbproj" />
  </ItemGroup>

  <PropertyGroup>
    <OutputType>Exe</OutputType>
    <RootNamespace>Shelf.Cli</RootNamespace>
    <TargetFramework>net10.0</TargetFramework>
  </PropertyGroup>

</Project>

<!-- dotnet new mstest -lang VB -o Shelf.Tests -->
<Project Sdk="Microsoft.NET.Sdk">

  <PropertyGroup>
    <TargetFramework>net10.0</TargetFramework>
    <LangVersion>latest</LangVersion>
    <ImplicitUsings>enable</ImplicitUsings>
    <Nullable>enable</Nullable>
  </PropertyGroup>

  <ItemGroup>
    <PackageReference Include="MSTest" Version="4.0.2" />
  </ItemGroup>

  <ItemGroup>
    <Using Include="Microsoft.VisualStudio.TestTools.UnitTesting" />
  </ItemGroup>

</Project>
----

Three things stand out. A library has no `OutputType` (the default is `Library`), a console application has `OutputType` `Exe`, and
`RootNamespace` is written into Visual Basic templates (C# templates have no such property, see the next table). The
test template carries `LangVersion` `latest` (harmless: it means the newest version) and three C#-isms, `ImplicitUsings`, `Nullable` and a `Using` item, that have no effect in a Visual Basic project: the captured
`vbc` command lines in this page do not change when they are set (see
<<properties-that-do-nothing,Properties that do nothing in Visual Basic>>). The
test template's own sources and the way the tests run are on xref:programming-languages/visual-basic/testing.adoc[Testing].

The project name matters more in VB than in C#, because three names are derived from it and they are independent:

[cols="2,3,3",options="header"]
|===
|Property |Controls |Default

|`AssemblyName`
|The file name of the output (`Shelf.Core.dll`) and the assembly identity.
|The project file name without extension.

|`RootNamespace`
|The namespace the compiler prefixes to every `Namespace` block and to types declared outside one (`/rootnamespace`). It also appears in CLR exception messages and in the name of embedded resources and `My` types.
|The project file name, with characters that are not valid in an identifier replaced.

|`PackageId`
|The NuGet package id (see xref:programming-languages/visual-basic/libraries-packaging-and-deployment.adoc[Libraries, Packaging and Deployment]).
|`AssemblyName`.
|===

=== What the SDK adds to your project

The following are *not* in the project file above, but are in force for every `Microsoft.NET.Sdk` Visual Basic project. Each was observed with
`dotnet msbuild -getProperty` / `-getItem`, or in the captured command line below.

[cols="2,5",options="header"]
|===
|Implicit |What it is

|Source files
|`+Compile Include="**/*.vb"+`, minus `bin`, `obj` and other default excludes; switched off by `EnableDefaultCompileItems` = `false`. `+**/*.resx+` become `EmbeddedResource` items, everything else is `None`. Putting a file into the folder is enough; listing it again is an error (NETSDK1022, shown below).
|Framework reference
|The `Microsoft.NETCore.App` reference pack for the target framework: 167 reference assemblies (for `net10.0` on this SDK) passed as `/reference:`, plus `/nostdlib /nosdkpath` so the compiler never looks anywhere else.
|Visual Basic runtime
|`Microsoft.VisualBasic.dll` (which type-forwards to `Microsoft.VisualBasic.Core`) passed as `/vbruntime:<path>`, so `Left`, `Mid`, `CInt`, `Format`, `Like` and the `My` machinery are available without a `Reference`.
|Global imports
|`/imports:Microsoft.VisualBasic,System,System.Collections,System.Collections.Generic,System.Diagnostics,System.Linq,System.Xml.Linq,System.Threading.Tasks` (`System.Data` is added on .NET Framework targets).
|Option defaults
|`OptionStrict` `Off`, `OptionExplicit` `On`, `OptionInfer` `On`, `OptionCompare` `Binary`.
|Warning defaults
|`NoWarn` = `41999,42016,42017,42018,42019,42020,42021,42022,42032,42036` (plus `BC41997` added on .NET targets), `WarningLevel` `1`, and `WarningsAsErrors` `NU1605;SYSLIB0011`.
|Conditional symbols
|`CONFIG`, `DEBUG`, `TRACE`, `PLATFORM`, `_MyType`, and the target framework symbols (`NET`, `NET10_0`, `NETCOREAPP`, ...); see <<defineconstants-and-the-implicit-symbols,DefineConstants and the implicit symbols>>.
|Generated source
|`obj/<config>/<tfm>/<name>.AssemblyInfo.vb` (assembly attributes from `Version`, `Company` and friends, when `GenerateAssemblyInfo` is `true`) and `+obj/.../.NETCoreApp,Version=v10.0.AssemblyAttributes.vb+` (the `TargetFramework` attribute).
|Analyzers
|The .NET analyzers (`Microsoft.CodeAnalysis.VisualBasic.NetAnalyzers.dll` and `Microsoft.CodeAnalysis.NetAnalyzers.dll`) and a global analyzer config for `AnalysisLevel`.
|===

Where does it come from? The `Sdk` attribute makes MSBuild import `Sdk.props` before the project body and `Sdk.targets` after it. The
VB-specific pieces are two small files in the SDK's `Sdks/Microsoft.NET.Sdk/targets` folder, selected by the project extension:

[cols="3,5",options="header"]
|===
|File (under the SDK folder) |Contents

|`Sdks/Microsoft.NET.Sdk/targets/Microsoft.NET.Sdk.VisualBasic.props`
|Imported by `Microsoft.NET.Sdk.props` when the project extension is `.vbproj`. Defaults for `WarningLevel`, `NoWarn`, `OptionExplicit`, `OptionCompare`, `OptionStrict`, `OptionInfer`, `WarningsAsErrors` (adds `NU1605`) and `DefineDebug` / `DefineTrace` per configuration.
|`Sdks/Microsoft.NET.Sdk/targets/Microsoft.NET.Sdk.VisualBasic.targets`
|Imported by `Microsoft.NET.Sdk.targets` when the language is VB. The implicit `Import` items, `FinalDefineConstants`, the `VBRuntime` / `UseReferencedVBRuntime` logic, `DisableSdkPath`, the `_MyType="Empty"` define, the `SupportsHotReload` capability and the `SYSLIB0011` rule.
|`Roslyn/Microsoft.VisualBasic.Core.targets`
|The `CoreCompile` target, which calls the `Vbc` task with 90 parameters, each fed by one property or item (listed below).
|`Roslyn/Microsoft.Managed.Core.targets`
|Behaviour shared with C#: `UseSharedCompilation` (default `true`), analyzer skipping, the `Features` property, source link and embedded files.
|===

Because those are plain text files in the installed SDK, every statement about defaults on this page can be checked on your machine
with `dotnet msbuild -getProperty:Name`, and the files are the authoritative reference when the documentation lags behind (it
does, as the sections below point out).

=== The default items and the NETSDK1022 error

The glob is the single most common cause of a first migration error: a project converted from the old format still lists every
file, so the SDK sees each file twice.

[source,xml]
----
<!-- P.vbproj : SDK-style project that also lists a file the glob already included -->
<Project Sdk="Microsoft.NET.Sdk">

  <PropertyGroup>
    <OutputType>Exe</OutputType>
    <TargetFramework>net10.0</TargetFramework>
    <RootNamespace>P</RootNamespace>
    <NuGetAudit>false</NuGetAudit>
  </PropertyGroup>

  <ItemGroup>
    <Compile Include="Program.vb" />
  </ItemGroup>

</Project>
----

[source,text]
----
$ dotnet build
/usr/share/dotnet/sdk/10.0.402/Sdks/Microsoft.NET.Sdk/targets/Microsoft.NET.Sdk.DefaultItems.Shared.targets(190,5): error NETSDK1022: Duplicate 'Compile' items were included. The .NET SDK includes 'Compile' items from your project directory by default. You can
----

(The message continues with the two ways out; the line is cut here.) You either delete the `Compile` item, or switch the glob off
with `EnableDefaultCompileItems` set to `false` and list every file yourself. To *exclude* files from the glob, use `Remove`:

[source,xml]
----
  <ItemGroup>
    <Compile Remove="Old/**" />
  </ItemGroup>
----

With `Old/Legacy.vb` (a second `Sub Main` in the same folder tree) the project built with 0 warnings and 0 errors and printed `main`, and
`dotnet msbuild -getItem:Compile` listed only `Program.vb`: the removed file was never compiled. With `EnableDefaultCompileItems`
set to `false` and `<Compile Include="Program.vb" />` the same query also listed only `Program.vb`. Built and run: 2 projects.

Source: https://learn.microsoft.com/dotnet/core/project-sdk/overview[.NET project SDKs], https://learn.microsoft.com/visualstudio/msbuild/msbuild-items[MSBuild items], https://learn.microsoft.com/visualstudio/msbuild/customize-your-build[Customize your build]

== From project properties to vbc options

`dotnet build` does not understand Visual Basic; it asks MSBuild to evaluate the project and run its targets. One of those targets,
`CoreCompile`, calls the `Vbc` task, and the task turns property values into a command line for the Roslyn Visual Basic compiler.
So a property is never "applied" by the compiler: each property named below is read by the SDK's targets and turned into
zero or more `vbc` options. The diagram shows the path, and the table after it lists the option each property produces.

* `OptionCompare` `Text` became `/optioncompare:Text`; `OptionStrict` `On` became `pass:c[/optionstrict+]`; `RemoveIntegerChecks` became `pass:c[/removeintchecks+]`.
* `NoWarn` got the SDK's default list *plus* `BC42350` plus `BC41997`, which the SDK appends for .NET (Core) targets. The leading `BC` is accepted.
* `DefineConstants` is a *comma* separated list; the SDK prepends `CONFIG`, `DEBUG`, `TRACE` and `PLATFORM`, leaves an empty entry
  (`,,`) where the empty `$(DefineConstants)` was, and appends `_MyType="Empty"` and the framework symbols. The string value `GREETING="hi"` had its quotes escaped.
* `StartupObject` became `/main:Ks.Program`, and `GenerateDocumentationFile` became `/doc:` with a path under `obj`.
* `TreatWarningsAsErrors` became `pass:c[/warnaserror+]`, `WarningsNotAsErrors` a trailing `/warnaserror-:BC42024`, and the SDK's own
  `WarningsAsErrors` (`NU1605;SYSLIB0011`) a `pass:c[/warnaserror+:]` list.
* `/noconfig`, `/nostdlib`, `/nosdkpath`, `/errorreport:prompt`, `pass:c[/highentropyva+]`, `/filealign:512`, `/utf8output`, `/refout:` and
  the two analyzers were not asked for: they are SDK defaults.
* The generated `AssemblyInfo.vb` and the assembly-attributes file are compiled together with your source.

The command line is the same one you would type by hand (see <<running-vbc-by-hand,Running vbc by hand>>); only `-v:diag` or a binary log shows it
during a normal build.

=== Printing the command line without compiling

Reading `-v:diag` output (it is roughly 50,000 lines for a tiny project) is clumsy. The SDK has a switch meant for IDEs,
`ProvideCommandLineArgs`, which makes the `Vbc` task return its arguments as an item instead of running the compiler. With the
`-getTargetResult` switch of `dotnet msbuild` you get one JSON entry per argument:

[source,bash]
----
dotnet msbuild Map.vbproj -nologo -v:q -t:ResolveReferences,CoreCompile \
  -p:SkipCompilerExecution=true -p:ProvideCommandLineArgs=true -getTargetResult:CoreCompile
----

This is how every row of the property table below was produced: the command is run with the baseline project and once more with
one extra `-p:Name=Value`, and the lines that changed are the option(s) that property controls. The baseline (a `dotnet new console -lang VB`
project renamed `Map`, default configuration) is:

[source,text]
----
/noconfig
/imports:Microsoft.VisualBasic,System,System.Collections,System.Collections.Generic,System.Diagnostics,System.Linq,System.Xml.Linq,System.Threading.Tasks
/optioncompare:Binary
/optionexplicit+
/optionstrict:custom
/nowarn:41999,42016,42017,42018,42019,42020,42021,42022,42032,42036,BC41997
/nosdkpath
/optioninfer+
/nostdlib
/errorreport:prompt
/rootnamespace:Map
/highentropyva+
/vbruntime:<ref>/Microsoft.VisualBasic.dll
/define:"CONFIG=\"Debug\",DEBUG=-1,TRACE=-1,PLATFORM=\"AnyCPU\",_MyType=\"Empty\",NET=-1,NET10_0=-1,NETCOREAPP=-1,..."
/debug+
/debug:portable
/filealign:512
/optimize-
/out:obj/Debug/net10.0/Map.dll

/warnaserror-
/utf8output
/deterministic+

----

The first surprise is `/optionstrict:custom`. The SDK's default of `OptionStrict` `Off` does not
become `/optionstrict-`; it becomes *custom*, a mode that raises the individual Option Strict diagnostics as warnings. Those warnings
(BC42016 to BC42022 and a few more) are then silenced by the SDK's default `NoWarn`, which is why a default project accepts
implicit narrowing silently. The consequence is demonstrated in <<the-nowarn-trap,The NoWarn trap>>.

== Default values of a VB console project

`dotnet msbuild -getProperty:Name` prints the final value of a property after evaluation, with no build. Run on a fresh `dotnet new console -lang VB`
project renamed `App` (`net10.0`, Debug unless stated), it gives the following. An empty value means "not set"; the SDK's targets then behave as the third column says.

[cols="3,3,5",options="header"]
|===
|Property |Value |Meaning of the default

|`OutputType`
|`Exe`
|Set by the console template; a library project has no value and builds as `Library`.

|`AssemblyName`, `RootNamespace`
|`App`, `App`
|Both come from the project file name.

|`StartupObject`
|(empty)
|The compiler looks for exactly one `Sub Main`; two give BC30738.

|`LangVersion`
|(empty)
|No `/langversion` option is passed, so the compiler default applies (`default`, which is 17.13 on this SDK).

|`OptionStrict`
|`Off`
|Becomes `/optionstrict:custom`; see below.

|`OptionExplicit`, `OptionInfer`, `OptionCompare`
|`On`, `On`, `Binary`
|Same as the language defaults.

|`RemoveIntegerChecks`, `MyType`, `VBRuntime`
|(empty)
|Integer overflow is checked; `_MyType="Empty"` is defined; the runtime comes from `UseReferencedVBRuntime`.

|`UseReferencedVBRuntime`
|`true`
|The SDK passes the reference pack's `Microsoft.VisualBasic.dll` as `/vbruntime:`.

|`DefineDebug`, `DefineTrace`
|`true`, `true` (Debug); (empty), `true` (Release)
|Decide whether `DEBUG=-1` and `TRACE=-1` are defined.

|`DefineConstants`
|(empty)
|Your own symbols; the SDK builds the final list in `FinalDefineConstants`.

|`GenerateDocumentationFile`
|`false`
|No `/doc`.

|`NoWarn`
|`41999,42016,42017,42018,42019,42020,42021,42022,42032,42036`
|The SDK default list, hidden warnings of Option Strict Custom and similar.

|`WarningLevel`, `TreatWarningsAsErrors`
|`1`, `false`
|Warnings are reported and do not fail the build.

|`WarningsAsErrors`
|`;NU1605;SYSLIB0011`
|Two diagnostics are errors in every VB project.

|`Optimize`, `DebugSymbols`, `DebugType`
|`false`, `true`, `portable` (Debug); `true`, `false`, `portable` (Release)
|Release optimizes and emits no PDB.

|`Deterministic`, `ProduceReferenceAssembly`
|`true`, `true`
|`pass:c[/deterministic+]` and `+/refout:obj/.../refint/App.dll+`.

|`PlatformTarget`, `Prefer32Bit`
|(empty), `false`

|`FileAlignment`, `HighEntropyVA`, `Utf8Output`, `ErrorReport`
|`512`, `true`, `true`, `prompt`

|`GenerateAssemblyInfo`
|`true`
|The SDK writes `+obj/.../App.AssemblyInfo.vb+`.

|`AnalysisLevel`, `EnableNETAnalyzers`, `EnforceCodeStyleInBuild`

[cols="2,3,3,3",options="header"]
|===
|Configuration |Symbols in `/define` |Debug options |Other options

The symbol that equals the upper-cased configuration name (`RELEASE`, `STAGING`) comes from `ImplicitConfigurationDefine`; set
`DisableImplicitConfigurationDefines` to `true` to stop that. `DEBUG` and `TRACE` come from `DefineDebug` and `DefineTrace`, which the
VB `.props` file sets per configuration. Setting `DefineDebug` to `false` on a Debug configuration does *not* remove `DEBUG`: the observed
list still contains `DEBUG=-1` (it moves to the end), because the implicit configuration define re-adds it. To really drop
`DEBUG` in a Debug build, change `Configuration`, or set `DisableImplicitConfigurationDefines` and `DefineDebug` to `false` together.

[[properties-that-do-nothing]]
=== Properties that do nothing in Visual Basic

C# project files and templates use several properties that look portable and are not. For each, the table says what was tested.

[cols="3,6",options="header"]
|===
|Property or item |Result in a VB project

|`Nullable`
|No effect. `Nullable` `enable` produced no change in the `vbc` command line. Visual Basic has no nullable reference types; `String` is always nullable.

|`ImplicitUsings`, `+<Using Include="...">+`
|No effect. With `ImplicitUsings` `enable` and `<Using Include="System.Text" />`, `Dim sb As New StringBuilder()` failed with `+error BC30002: Type 'StringBuilder' is not defined.+`; replacing the `Using` item with `<Import Include="System.Text" />` compiled and ran. The VB `mstest` template still writes both, harmlessly.

|`LangVersion` `preview`
|Rejected by the build: `+vbc : error BC2014: the value 'preview' is invalid for option 'langversion'+`. VB has no preview versions.

|`AllowUnsafeBlocks`, `CheckForOverflowUnderflow`
|No effect: neither changed the `vbc` command line. VB has no `unsafe` code; the nearest equivalent of the second is `RemoveIntegerChecks` (inverted meaning).

|`InvariantGlobalization`
|Not a compiler setting: it is written to `runtimeconfig.json` and read by the .NET runtime, so it works the same in VB.

== What the properties do at run time

The next project reads its own build settings back, so one program shows five properties at once: `RootNamespace`, `Version`,
`OptionCompare`, `RemoveIntegerChecks` and the conditional-compilation symbols. The project file sets `OptionStrict` and
`TreatWarningsAsErrors`, and `DefineConstants` with two symbols of its own. Its root namespace is `Shelf.Build`. The code has no `Imports` for
`System`, `System.Collections.Generic` or `System.Linq`: they come from the SDK's implicit `Import` items.

    <OptionStrict>On</OptionStrict>

    <TreatWarningsAsErrors>true</TreatWarningsAsErrors>
    <NuGetAudit>false</NuGetAudit>

[[the-nowarn-trap]]
=== The NoWarn trap

The SDK's default `NoWarn` hides BC42016 to BC42022, the warnings of the *custom* Option Strict mode. Assigning `NoWarn` without
`$(NoWarn)` throws that list away and makes those warnings appear in every file of the project:

[source,vbnet]
----
Public Module Program
    Public Sub Main()
        Dim count As Integer = 3.5
        Console.WriteLine(count)
    End Sub
End Module
----

[source,xml]
----
<NoWarn>BC42024</NoWarn>
----

[source,text]
----
Program.vb(3,32): warning BC42016: Implicit conversion from 'Double' to 'Integer'.
----

With the default `NoWarn` the same file builds silently (and prints `4`: the narrowing is real, only the warning is hidden). Write `<NoWarn>$(NoWarn);BC42024</NoWarn>` to append. A project that sets
`OptionStrict` to `On` is not exposed to this trap, because there is nothing left to warn about.

=== OptionStrict is a Boolean in MSBuild

The `Vbc` task declares `OptionStrict` as a Boolean, so the third state of the language statement (`Option Strict Custom` does not exist as a
statement either) is not available as a project value:

[source,xml]

[source,text]
----
Microsoft.VisualBasic.Core.targets(103,10): error MSB4030: "Custom" is an invalid value for the "OptionStrict" parameter of the "Vbc" task. The "OptionStrict" parameter is of type "System.Boolean".
----

`Off` is what already gives the custom mode, as the command lines above show.

=== DefineConstants separators

`DefineConstants` is passed to `/define`, which separates entries by *commas*. The semicolon that MSBuild uses elsewhere (and that C# projects
use for this very property) breaks the build:

[source,xml]
----
<DefineConstants>ALPHA=1;BETA=True</DefineConstants>
----

[source,text]
----
vbc : error BC31030: Conditional compilation constant 'ALPHA=1 ^^ ^^ ;BETA=True' is not valid: End of statement expected.
----

Appending with `$(DefineConstants);ALPHA=1;BETA=True` fails the same way (BC31030, "Identifier expected" for the empty first entry). Both of

[source,xml]
----
<DefineConstants>ALPHA=1,BETA=True</DefineConstants>
<DefineConstants>$(DefineConstants),ALPHA=1,BETA=True</DefineConstants>
----

built, and a program using `+#If ALPHA = 1+`, `+#If BETA+` and `+#If DEBUG+` printed `ALPHA is 1`, `BETA is on`, `DEBUG is on`.
The ordering of the options the task writes (a `,,` empty entry for an empty `$(DefineConstants)`) is harmless. Built and run: 19 small projects in this section, plus 4 variants of the `DefineConstants` project.

[[global-imports-and-the-missing-global-using]]
== Global imports and the missing global using

C# 10 introduced `global using` and `ImplicitUsings`. Visual Basic had global imports first, and they are an *item* of the project, not
a statement of the language: `<Import Include="System.Text" />` becomes an entry in `/imports:`. There is no
`Global Imports` statement; each file still declares its own `Imports`. The SDK adds eight `Import` items for you (the eight
namespaces in the table above; `System.Data` is the ninth when the target is .NET Framework). The VB templates add more:

[cols="2,6",options="header"]
|===
|Template |Import items written into the `.vbproj`

|`console`, `classlib`, `mstest`, `xunit`, `nunit`
|none (the SDK ones apply)

|`winforms`
|`System.Data`, `System.Drawing`, `System.Windows.Forms`

|`wpf`
|`System.Windows`, `System.Windows.Controls`, `System.Windows.Data`, `System.Windows.Documents`, `System.Windows.Input`, `System.Windows.Media`, `System.Windows.Media.Imaging`, `System.Windows.Navigation`, `System.Windows.Shapes`
|===

The `Import` item in a project must not be confused with MSBuild's own `+<Import Project="..." />+` element, which pulls in
another project file. They look alike and are unrelated. Two further behaviours follow from the tests above:

* Setting `UseWindowsForms` or `UseWPF` does not add `Import` items; the template does. If you create the project by hand, add them yourself.
* The VB `mstest` template still writes a C#-style `+<Using Include="..." />+` item that does nothing in VB (see the table of properties that do nothing). The tests use an ordinary
  `Imports` statement in the file.

An alias is possible in a file (`Imports Sb = System.Text.StringBuilder`) but not as a project-wide import. Because the compiler imports
nothing implicitly beyond this list, a type of another namespace (`StringBuilder`, `Regex`, `HttpClient`) always needs a file-level `Imports` or an `Import` item,
exactly as in the failing `ImplicitUsings` example above.

== MyType and the Visual Basic runtime

Two groups of settings decide what the `Microsoft.VisualBasic` library looks like to the program. `MyType` selects the `My` classes the compiler
generates; `VBRuntime` selects which `Microsoft.VisualBasic` is linked. The SDK's own comment in `Microsoft.NET.Sdk.VisualBasic.targets` states the defaults, and the captured command
lines agree with it:

[cols="3,4,4",options="header"]
|===
|Target |`/vbruntime` option observed |Why

|`net10.0`, `net8.0`
|`/vbruntime:<reference pack>/Microsoft.VisualBasic.dll`
|`UseReferencedVBRuntime` is `true` for .NET Core 3.0 and later: the runtime is the `Microsoft.VisualBasic` among the references.

|`net10.0-windows` with `UseWindowsForms`
|`+/vbruntime:.../microsoft.windowsdesktop.app.ref/10.0.13/ref/net10.0/Microsoft.VisualBasic.dll+`
|The Windows Desktop reference pack contains the runtime with the Windows Forms application services.

|`net481`
|`+/vbruntime:.../microsoft.netframework.referenceassemblies.net481/1.0.3/build/.NETFramework/v4.8.1/Microsoft.VisualBasic.dll+`
|The .NET Framework's own `Microsoft.VisualBasic.dll`, found in the reference assemblies package that the SDK downloads, which is why `net481` builds even on Linux.

|`netstandard2.0`
|`+/vbruntime*+`
|`VBRuntime` `Embed`: the runtime is compiled into your assembly, because no `Microsoft.VisualBasic.dll` is available for `netstandard`. 
|===

For a library that targets `netstandard2.0` the embedded runtime means the library carries its own copy of the Visual Basic runtime functions it uses, and some runtime functions are
not available to it (the effects are on

BC30002 ("Type ... is not defined") and `Web` does not build at all; `Empty` is the default and
the right choice for console programs and libraries. `WindowsFormsWithCustomSubMain` is for Windows Forms projects that write their own `Sub Main`, as
the template does. The `My` namespace and what each value generates are on xref:programming-languages/visual-basic/the-my-namespace.adoc[The My Namespace].

[[directory-build-props-and-friends]]
== Sharing settings across a solution

Every setting above belongs in the project file if it is specific to the project and in one of four *solution-level* files if it is shared. MSBuild looks upward from each project directory, and the first file of each kind it
finds is imported automatically: `Directory.Build.props` before the project body (so project files can override it), `Directory.Build.targets` after the SDK targets
(so it can override them), `Directory.Packages.props` for central package versions, and `global.json` (read by the `dotnet` host) for the SDK version. The `buildprops`, `buildtargets`,
`packagesprops`, `globaljson`, `editorconfig`, `nugetconfig` and `gitignore` short names of `dotnet new` create starters for them.

The experiment: a repository with `Directory.Build.props` (sets `TargetFramework`, `OptionStrict` `On`, `LangVersion`, `TreatWarningsAsErrors`, `Deterministic`, `Version` and
`ManagePackageVersionsCentrally`), `Directory.Build.targets` (prints the effective values after every build), `Directory.Packages.props` (one `PackageVersion`) and
`global.json`; and two projects, `src/Core` that adds nothing and `src/Tools` that sets `OptionStrict` `Off` and `Version` `0.1.0`.

[source,xml]
----
<!-- Directory.Build.props -->
<Project>

  <PropertyGroup>
    <TargetFramework>net10.0</TargetFramework>
    <OptionStrict>On</OptionStrict>
    <LangVersion>latest</LangVersion>
    <TreatWarningsAsErrors>true</TreatWarningsAsErrors>
    <Deterministic>true</Deterministic>
    <Version>2.0.0</Version>
    <NuGetAudit>false</NuGetAudit>
    <ManagePackageVersionsCentrally>true</ManagePackageVersionsCentrally>
  </PropertyGroup>

</Project>

<!-- Directory.Build.targets -->
<Project>

  <Target Name="ShowOptions" AfterTargets="Build">
    <Message Importance="high" Text="$(MSBuildProjectName): OptionStrict=$(OptionStrict) Version=$(Version) RootNamespace=$(RootNamespace)" />
  </Target>

</Project>

<!-- Directory.Packages.props -->
<Project>

  <ItemGroup>
    <PackageVersion Include="Microsoft.Extensions.Logging.Abstractions" Version="10.0.0" />
  </ItemGroup>

</Project>

<!-- global.json -->
{ "sdk": { "version": "10.0.100", "rollForward": "latestFeature" } }

<!-- src/Core/Core.vbproj -->
<Project Sdk="Microsoft.NET.Sdk">

  <PropertyGroup>
    <RootNamespace>Shelf.Core</RootNamespace>
  </PropertyGroup>

  <ItemGroup>
    <PackageReference Include="Microsoft.Extensions.Logging.Abstractions" />
  </ItemGroup>

</Project>

<!-- src/Tools/Tools.vbproj -->
<Project Sdk="Microsoft.NET.Sdk">

  <PropertyGroup>
    <RootNamespace>Shelf.Tools</RootNamespace>
    <OptionStrict>Off</OptionStrict>
    <Version>0.1.0</Version>
  </PropertyGroup>

</Project>
----

(The `PackageReference` in `Core.vbproj` has no `Version`: with central package management the version comes from `Directory.Packages.props`.)

(`Tools` kept `Off` and `0.1.0`); the command-line `-p:OptionStrict=On` won over the project; `global.json` asked for `10.0.100` with `latestFeature`
and the installed `10.0.402` satisfied it. The central package version `10.0.0` was applied to a `PackageReference` without a `Version`. Built and run: 2 projects.

*Nested files.* Only the nearest `Directory.Build.props` is imported. A file deeper in the tree that wants the parent's settings imports it explicitly, which is what a
`tests` folder normally does. This was run with `tests/Directory.Build.props`:

[source,xml]
----

  <Import Project="$([MSBuild]::GetPathOfFileAbove('Directory.Build.props', '$(MSBuildThisFileDirectory)../'))" />

  <PropertyGroup>
    <IsPackable>false</IsPackable>
    <WarningsNotAsErrors>$(WarningsNotAsErrors);BC42024</WarningsNotAsErrors>
  </PropertyGroup>

  <ItemGroup>
    <Import Include="System.Text" />
  </ItemGroup>

</Project>
----

The test project got the parent's `OptionStrict` `On`, `TreatWarningsAsErrors` `true` and `Company` `Shelf`, plus `IsPackable` `false`, `WarningsNotAsErrors` `;BC42024` and
a ninth `Import` item `System.Text`; the project in `src/` got only the parent's values and `IsPackable` `true`. Built and run: 2 projects.

The Shelf reference solution of this site sets `OptionStrict`, `TreatWarningsAsErrors` and `NuGetAudit` in one `Directory.Build.props`, which is what you
should do for any multi-project Visual Basic repository: it makes `OptionStrict` `On` a solution policy instead of a per-file chore. The `.editorconfig`
keys for style and analyzer severity are on xref:programming-languages/visual-basic/xml-documentation-analyzers-and-code-style.adoc[XML Documentation, Analyzers and Code Style].

=== What each command does to the MSBuild model

[cols="3,4,6",options="header"]
|===
|Command |MSBuild equivalent |Visual Basic notes

|`dotnet restore`
|`msbuild -t:Restore`
|Reads `PackageReference`, `ProjectReference` and `Directory.Packages.props` and writes `obj/project.assets.json`; `build`, `run`, `test` do it first unless `--no-restore`. Offline builds need the packages already in the NuGet cache.

|`dotnet build [-c Release] [-o dir] [-f tfm] [--no-restore] [--no-incremental] [-p:Name=Value] [-v:level] [-bl]`
|`msbuild -t:Build`
|`-p:` sets a *global* property that beats the project file (shown above); `-f` selects one target of a multi-targeted project; `-bl` writes `msbuild.binlog`, readable with the MSBuild Structured Log Viewer, the best tool for "why did this property get that value" questions.

|`dotnet run [--project p] [-c cfg] [--no-build] [-- args]`
|build, then `dotnet App.dll`
|Everything after `--` goes to `Main`. The program's return value is the exit code. A stale build after `+-p:StartupObject=...+` is a known trap: use `dotnet build --no-incremental` and then run.

|`+dotnet test [project] [--filter ...]+`
|build, then the test host
|The VB `mstest`, `xunit` and `nunit` templates; see xref:programming-languages/visual-basic/testing.adoc[Testing] for the runner differences. In this SDK the argument is a project path; a `--solution` switch is not accepted. `--list-tests` lists the test names without running them.

|`dotnet pack`, `dotnet publish`
|`msbuild -t:Pack`, `-t:Publish`
|`pack` makes a `.nupkg` (a warning about the missing readme is normal); `publish` creates the deployable folder. Publish modes are on xref:programming-languages/visual-basic/libraries-packaging-and-deployment.adoc[Libraries, Packaging and Deployment].

|`dotnet clean`
|`msbuild -t:Clean`
|Deletes the outputs of the build.

|`dotnet sln add / remove / list / migrate`
|(solution file edit)
|Works on `.sln` and `.slnx`; `migrate` writes the `.slnx`.

|`dotnet add reference / package`, `+dotnet remove ...+`, `+dotnet list ...+`
|(project file edit)
|Edits the `.vbproj`; `dotnet add package` also restores (its output is the `info :` lines shown above).

|`dotnet format`
|(Roslyn workspace, not MSBuild targets)
|Applies `.editorconfig` formatting and style rules; it supports Visual Basic.

|`dotnet msbuild`
|the same MSBuild engine
|`-getProperty:A,B`, `-getItem:Name` and `-getTargetResult:Target` print values as JSON without building; `-pp:out.xml` writes the fully expanded project, with every imported file inlined in evaluation order, which is the best way to read the SDK's contribution.

== The vbc option reference

`vbc` is the Roslyn Visual Basic compiler. In the .NET SDK it is `Roslyn/bincore/vbc.dll` under the SDK folder
(`/usr/share/dotnet/sdk/10.0.402/Roslyn/bincore/vbc.dll` in the container), a framework-dependent program started with `dotnet`;

"compiler options listed by category" page and the individual option pages describe an older compiler; the table below is the output of `vbc -help` of
this compiler, in its eight groups, plus five options the compiler accepts but does not list. The Learn page of an option (where one exists) is linked in the references.
In the "Option" column `pass:c[[+|-\]]` means the option may be followed by `pass:c[+]` (on), `-` (off) or nothing (on).

Each option below was passed to the SDK 10.0.402 compiler on a small module. All were accepted; the ones that take a file reported a
problem with the (deliberately missing) file instead of "unrecognized option", which proves the option itself was understood. A made-up option
produces warning BC2007 and is ignored: `+vbc : warning BC2007: unrecognized option '-bogusoption'; ignored+`. That is also why a
misspelled switch in a response file does not stop a build, which is worth knowing when you read a build log.

[[running-vbc-by-hand]]
=== Running vbc by hand

Nothing prevents compiling without MSBuild; you need the reference assemblies and the right standard-library options because `vbc` on .NET does not find them itself.
The project below is one source file, a response file with the options and a response file listing the 167 reference assemblies (made with
`+ls $REF/*.dll | sed 's|^|-reference:|' > refs.rsp+`, where `REF` is the `microsoft.netcore.app.ref` folder `+.../ref/net10.0+` of the reference pack):

[source,vbnet]
----
Option Strict On

Public Module Hello

    Public Sub Main()
        Console.WriteLine("Hello from vbc " & Left("compiled by hand", 11))
    End Sub

End Module
----

[source,text]
----
# build.rsp
-nologo
-noconfig
-nostdlib
-nosdkpath
-target:exe
-out:Hello.dll
-optionstrict+
-rootnamespace:Hand
-define:_MyType="Empty"
-imports:System,Microsoft.VisualBasic
-vbruntime:<ref>/Microsoft.VisualBasic.dll
@refs.rsp
Hello.vb
----

[source,bash]
----
dotnet /usr/share/dotnet/sdk/10.0.402/Roslyn/bincore/vbc.dll @build.rsp
----

[source,text]
----
vbc : warning BC2025: ignoring /noconfig option because it was specified in a response file
vbc exit code: 0
----

The `Hello.runtimeconfig.json` that `dotnet` needs to run a framework-dependent program (the SDK writes it for you in a project build) is three lines of JSON that name the framework `Microsoft.NETCore.App` version `10.0.0`; with it, `dotnet Hello.dll` printed:

[source,text]
----
Hello from vbc compiled by
----

Notes from the run: `-noconfig` must be on the real command line (BC2025 otherwise, a warning only); without `-define:_MyType="Empty"` the compiler generates its default `My` classes and reports BC30002 for the Windows-only types they use
(`+Type 'Global.Microsoft.VisualBasic.ApplicationServices.ApplicationBase' is not defined.+`), and the line is how the SDK stops that; and a response file is simply the options, one per line, expanded in place, which is how MSBuild itself invokes the compiler. Built and run: 1 program.

Source: https://learn.microsoft.com/dotnet/visual-basic/reference/command-line-compiler/[Visual Basic command-line compiler], https://learn.microsoft.com/dotnet/visual-basic/reference/command-line-compiler/specify-response-file[Response files], https://learn.microsoft.com/dotnet/visual-basic/reference/command-line-compiler/sample-compilation-command-lines[Sample compilation command lines]

== Legacy (non-SDK) project files

Until .NET Core, every Visual Basic project used a verbose format that listed everything by hand. You meet it in .NET Framework solutions, in older repositories and in the books that
predate the SDK. The sample below is a typical project of that kind for a console application (legacy format, shown for recognition; not built here).

[source,xml]
----
<?xml version="1.0" encoding="utf-8"?>
<Project ToolsVersion="15.0" xmlns="http://schemas.microsoft.com/developer/msbuild/2003">
  <Import Project="$(MSBuildExtensionsPath)\$(MSBuildToolsVersion)\Microsoft.Common.props"
          Condition="Exists('$(MSBuildExtensionsPath)\$(MSBuildToolsVersion)\Microsoft.Common.props')" />
  <PropertyGroup>
    <Configuration Condition=" '$(Configuration)' == '' ">Debug</Configuration>
    <Platform Condition=" '$(Platform)' == '' ">AnyCPU</Platform>
    <ProjectGuid>{00000000-0000-0000-0000-000000000000}</ProjectGuid>
    <OutputType>Exe</OutputType>
    <StartupObject>Shelf.Cli.Program</StartupObject>
    <RootNamespace>Shelf.Cli</RootNamespace>
    <AssemblyName>Shelf.Cli</AssemblyName>
    <FileAlignment>512</FileAlignment>
    <MyType>Console</MyType>
    <TargetFrameworkVersion>v4.8</TargetFrameworkVersion>
    <OptionExplicit>On</OptionExplicit>
    <OptionCompare>Binary</OptionCompare>
    <OptionStrict>Off</OptionStrict>
    <OptionInfer>On</OptionInfer>
  </PropertyGroup>
  <PropertyGroup Condition=" '$(Configuration)|$(Platform)' == 'Debug|AnyCPU' ">
    <DebugSymbols>true</DebugSymbols>
    <DebugType>full</DebugType>
    <DefineDebug>true</DefineDebug>
    <DefineTrace>true</DefineTrace>
    <OutputPath>bin\Debug\</OutputPath>
    <NoWarn>42016,41999,42017,42018,42019,42032,42036,42020,42021,42022</NoWarn>
  </PropertyGroup>
  <ItemGroup>
    <Reference Include="System" />
    <Reference Include="System.Core" />
    <Reference Include="System.Data" />
    <Reference Include="System.Xml.Linq" />
  </ItemGroup>
  <ItemGroup>
    <Import Include="Microsoft.VisualBasic" />
    <Import Include="System" />
    <Import Include="System.Collections.Generic" />
    <Import Include="System.Linq" />
  </ItemGroup>
  <ItemGroup>
    <Compile Include="Program.vb" />
    <Compile Include="My Project\AssemblyInfo.vb" />
    <Compile Include="My Project\Application.Designer.vb">
      <AutoGen>True</AutoGen>
      <DependentUpon>Application.myapp</DependentUpon>
    </Compile>
  </ItemGroup>
  <ItemGroup>
    <None Include="App.config" />
    <None Include="My Project\Application.myapp">
      <Generator>MyApplicationCodeGenerator</Generator>
      <LastGenOutput>Application.Designer.vb</LastGenOutput>
    </None>
  </ItemGroup>
  <Import Project="$(MSBuildToolsPath)\Microsoft.VisualBasic.targets" />
</Project>
----

What the SDK-style project made redundant:

[cols="4,5",options="header"]
|===
|Legacy construct |SDK-style replacement

|`ToolsVersion`, the `xmlns`, the `Microsoft.Common.props` and `Microsoft.VisualBasic.targets` imports
|`<Project Sdk="Microsoft.NET.Sdk">`

|`ProjectGuid`, default `Configuration` and `Platform`
|Not needed (the solution file still carries project ids)

|`TargetFrameworkVersion` `v4.8`
|`TargetFramework` `net48` or `net481`; the same project file can then move to `net10.0`

|One `PropertyGroup` per configuration with `DefineDebug`, `DefineTrace`, `OutputPath`, `NoWarn`
|The SDK defaults (the same `NoWarn` list as above) and `+Condition="'$(Configuration)' == 'Release'"+` groups only for real differences

|A `Compile Include` for every file
|The `+**/*.vb+` glob (NETSDK1022 if you keep the list)

|`Reference Include="System"` and `HintPath` into a `packages` folder with `packages.config`
|Implicit framework references and `PackageReference`

|`Import Include` items for the default namespaces
|The SDK's implicit imports (keep only your own)

|`My Project\AssemblyInfo.vb`
|Generated from `Version`, `Company` and so on; keeping the old file with `GenerateAssemblyInfo` `true` produces duplicate-attribute errors (BC30663), so either delete the file or set `GenerateAssemblyInfo` to `false`

|`My Project\Application.myapp` and `Application.Designer.vb`
|Still used by Windows Forms projects that use the application framework; Console and library projects need only `MyType`

|`Settings.settings`, `Resources.resx`
|Unchanged in structure; they stay `None` / `EmbeddedResource` items
|===

Almost every *property* name is the same in both formats (`OutputType`, `RootNamespace`, `OptionStrict`, `MyType`, `DefineConstants`), which is why a conversion is mostly deletion. A reasonable order is:
create an SDK-style project that targets the same .NET Framework version (`net48`, `net481`: it compiles anywhere with the reference assemblies package, as the multi-targeting example showed), delete the
lists the SDK now provides, replace `packages.config` with `PackageReference`, fix the `AssemblyInfo` duplicates, get the build green on the old framework, and only then change the target to `net10.0` and deal with the APIs
that moved. Microsoft's Upgrade Assistant and the app-modernization tooling can automate part of this; their current capabilities were not tested for this page. Web Forms and ASP.NET MVC projects
are .NET Framework projects, normally in the legacy format, as described in
xref:programming-languages/visual-basic/web-http-and-services.adoc[Web, HTTP and Services]. The strategy side is on
xref:programming-languages/visual-basic/migrating-legacy-visual-basic.adoc[Migrating Legacy Visual Basic].

== Pitfalls checklist

[cols="4,5,5",options="header"]
|===
|What you see |Why |Fix

|BC42016 and other Option Strict warnings suddenly appear everywhere
|`NoWarn` was assigned without `$(NoWarn)`, removing the SDK's default list
|`<NoWarn>$(NoWarn);BC42024</NoWarn>`, or set `OptionStrict` `On`

|BC31030 "Conditional compilation constant ... is not valid"
|Semicolon (or an empty first entry) in `DefineConstants`
|Comma separated: `$(DefineConstants),A=1,B=2`

|`DEBUG` is still defined after `DefineDebug` `false`
|`ImplicitConfigurationDefine` re-adds the upper-cased configuration name
|Use another configuration name or `DisableImplicitConfigurationDefines`

|MSB4030 for `OptionStrict` `Custom`
|The task parameter is a Boolean
|`Off` already gives `/optionstrict:custom`

|NETSDK1022 duplicate `Compile` items
|A legacy project still lists the files
|Delete the items, or `EnableDefaultCompileItems` `false`

|BC30738 "'Sub Main' is declared more than once"
|Two entry points
|`StartupObject` with the root namespace prefix

|Namespaces come out as `Shelf.Cli.Shelf.Cli`
|`Namespace Shelf.Cli` written inside a project whose root namespace is already `Shelf.Cli`
|Write the namespace without the root namespace

|BC2014 for `LangVersion` `17`, `17.0`, `preview`
|VB has no such values
|`17.13`, `latest` or `default`

|`ImplicitUsings`, `Nullable`, `Using` do nothing
|C# features
|`Import` items and file-level `Imports`

|BC30002 for `StringBuilder`, `List`, `Regex`
|Missing import (or `DisableImplicitNamespaceImports`)
|`Imports` in the file or an `Import` item

|BC30451 for `Left`, `Mid`, `Format`
|`Microsoft.VisualBasic` not imported
|`Imports Microsoft.VisualBasic`, or do not disable the implicit imports

|BC30663 duplicate attribute
|Hand-written `AssemblyInfo.vb` and a generated one
|Delete one, or `GenerateAssemblyInfo` `false`

|BC2007 "unrecognized option"
|An option the compiler does not know (`RuntimeMetadataVersion`, or a typo)
|Remove it; warnings of this kind do not fail the build

|`+-p:StartupObject=...+` seems ignored by `dotnet run`
|An incremental build kept the old output
|`dotnet build --no-incremental` first

|A project value is ignored
|A `-p:Name=Value` global property beats the project file, `Directory.Build.props` and the SDK
|Remove the command-line property, or set it conditionally

|A `net481` build runs on Linux nowhere
|It can be compiled anywhere, run only on Windows
|Build it in CI on any OS, test it on Windows

|`MyType` `Console` fails with BC30002
|On .NET 10 the `Console` My classes are not available
|Leave `MyType` empty for console programs and libraries
|===

== Differences from C# and from .NET Framework

[cols="3,5,5",options="header"]
|===
|Topic |Visual Basic |C#

|Project templates
|Fewer: console, classlib, test, WinForms, WPF; none for web, worker or MAUI
|All of them

|Namespace prefix
|`RootNamespace` is prepended to every `Namespace` block
|No such property; the `Namespace` is as written

|Language strictness
|`OptionStrict`, `OptionExplicit`, `OptionInfer`, `OptionCompare` are project settings; SDK default `OptionStrict` is `Off`
|Equivalent behaviour is fixed (or `Nullable`, `CheckForOverflowUnderflow` as settings)

|Overflow
|`RemoveIntegerChecks` removes checks that are on by default
|`CheckForOverflowUnderflow` adds checks that are off by default

|Symbols
|`DefineConstants` is comma separated; `DEBUG`, `TRACE` and the configuration name; `_MyType`, `VBC_VER`
|Semicolon separated; `DEBUG`, `TRACE`

|Global imports
|`Import` items; no `global using`, no `ImplicitUsings`
|`global using`, `ImplicitUsings`, `Using` items

|Language versions
|`9` to `16.9`, `17.13`, `default`, `latest`; no `preview`; no new syntax since 15.5 (apart from where comments may go)
|Numbers up to the current one, `preview`, `latest`, `default`, `latestMajor`

|Runtime library
|`Microsoft.VisualBasic` with `My`, controlled by `MyType` and `VBRuntime`
|None
|===

*Compared with .NET Framework.* An SDK-style project can target `net48` or `net481` and keep `MyType` `Windows` / `WindowsForms`, `System.Data` in the default imports, `/subsystemversion:6.00`
and the Framework's own `Microsoft.VisualBasic.dll`; a project on `net10.0` gets `_MyType="Empty"` until the template sets another value, eight default imports and the reference pack's runtime.

== Where the books and the older documentation are outdated

The books that predate the SDK-style format describe Visual Basic through a .NET Framework console template and a Visual Studio of that time; on current tooling the same
programs are created with `dotnet new console -lang VB` or *File > New* in Visual Studio 2026 and build against .NET 10 (see
xref:programming-languages/visual-basic/getting-started.adoc[Getting Started]). Beyond the books, a few official pages lag behind the product, and a reader following them gets a wrong
picture:

* The Learn pages *-langversion* and *Select the Visual Basic language version* list `LangVersion` values only up to `16.9` (the compiler also accepts `17.13`), and the first says the option can be set only
  on the command line, which is not true for a project.
* The Learn *Vbc task* page lists 53 parameters, 50 of them still current; the targets pass 90.
* The Learn *MSBuild properties for Microsoft.NET.Sdk* page does not mention the Visual Basic-specific properties (`OptionStrict`, `OptionExplicit`, `OptionInfer`, `OptionCompare`, `RemoveIntegerChecks`,
  `MyType`, `VBRuntime`, `RootNamespace`, `StartupObject` and `DefineConstants` each had zero matches in the page), so this page's tables come from the SDK files themselves.
* The Learn compiler-option pages do not cover everything `vbc -help` prints; the options `-analyzer`, `-additionalfile`, `-checksumalgorithm`, `-errorlog`, `-ruleset`, `-reportanalyzer`,
  `-skipanalyzers`, `-instrument`, `-sourcelink`, `-publicsign`, `-generatedfilesout`, `-parallel`, `-preferreduilang`, `-nosdkpath`, `-reportivts` and `-version` have no page named after them.
* The Learn *Compile Page* and *Application Page* of the Project Designer say they apply to Visual Studio 2017.
* The default `OptionStrict` is `Off` in the SDK although Learn and every style guide recommend `On`; there is no project template that changes it.

== Summary

* A Visual Basic project is an SDK-style `.vbproj`; the SDK adds the sources (glob), the references, eight global imports, the option defaults and a `NoWarn` list.
* Properties become `vbc` options through the `Vbc` task (90 parameters). `dotnet msbuild -getTargetResult:CoreCompile` with `ProvideCommandLineArgs` shows the result without compiling.
* `OptionStrict` `Off` is passed as `/optionstrict:custom` and relies on the default `NoWarn`; write `+$(NoWarn);...+`, or better set `OptionStrict` `On` in `Directory.Build.props`.
* `DefineConstants` is comma separated; `DefineDebug` `false` does not remove `DEBUG`; `Import` items replace `ImplicitUsings`; `Nullable` and `Using` are inert.
* `LangVersion` accepts `9` to `16.9`, `17.13`, `default` and `latest`; the syntax gates are those of the language history, and no syntax has been added since 15.5.
* `MyType`, `VBRuntime` and `UseReferencedVBRuntime` choose the `My` classes and the runtime; they differ for `net10.0`, `net10.0-windows`, `net481` and `netstandard2.0`.
* Share settings with `Directory.Build.props`, `Directory.Packages.props` and `global.json`; a command-line `-p:` property wins over all of them.
* `dotnet new -lang VB`, `sln`, `add`, `build`, `run`, `test`, `pack`, `publish` and `format` are the day-to-day commands; `dotnet msbuild -pp` shows the expanded project.
