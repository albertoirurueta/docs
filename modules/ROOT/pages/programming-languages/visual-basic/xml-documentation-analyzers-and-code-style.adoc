Three things keep a Visual Basic code base readable over years: comments that become *documentation* (a machine-readable XML file that
editors show as you type), *analyzers* that find mistakes the compiler allows, and *code style* rules that make the formatting and
naming uniform without arguments in code review. They share one mechanism, which is why they are on one page: the Roslyn compiler runs
them in the same pass, reports them with the same ids (`BCnnnnn`, `CAnnnn`, `IDEnnnn`) and lets you configure them with the same
files. The projects themselves are on

== XML documentation comments

A documentation comment is a comment that starts with *three* apostrophes, written immediately above the declaration that it
documents. The comment text is XML. The compiler reads it, checks part of it and, if you ask, writes all of it to an `.xml` file that
editors and documentation generators read.

* The marker is `+'''+` (C# uses `///`). Typing the three apostrophes above a member in Visual Basic's editors inserts a skeleton with
  a `summary`, a `param` per parameter and a `returns` for a function.
* Only the three-apostrophe form is a documentation comment; an ordinary comment (one apostrophe or `Rem`) is ignored. Text in a
  documentation comment that should show angle brackets needs `&lt;` and `&gt;`, because it is XML.
* The comment documents types (classes, structures, modules, interfaces, enumerations, delegates) and their members (methods,
  constructors, operators, properties, fields, events, enumeration members). It cannot document a namespace, and for a `Partial` type
  only one part may have a comment (see the diagnostics below).
* The file is written when the project sets `<GenerateDocumentationFile>true</GenerateDocumentationFile>` (the MSBuild form of the
  compiler option `-doc`). Its name is `<assembly name>.xml`, and it is written next to the assembly. The SDK pack step puts it into
  the NuGet package beside the DLL (see
  xref:programming-languages/visual-basic/libraries-packaging-and-deployment.adoc[Libraries, Packaging and Deployment]).

Source: https://learn.microsoft.com/dotnet/visual-basic/programming-guide/program-structure/documenting-your-code-with-xml[Documenting your code with XML], https://learn.microsoft.com/dotnet/visual-basic/reference/command-line-compiler/doc[-doc], https://learn.microsoft.com/dotnet/visual-basic/language-reference/xmldoc/[XML comments]

=== Every tag in one program

The program documents a generic class with all of the tags that the Microsoft reference lists: `summary`, `remarks`, `para`, `list`,
`typeparam`, `typeparamref`, `param`, `paramref`, `returns`, `value`, `exception`, `example`, `code`, `c`, `see`, `seealso` and
`include`, plus `inheritdoc` on an overriding constructor. The project sets `GenerateDocumentationFile` to true, and it is the
only change from the usual project file:

[source,xml]
----
<Project Sdk="Microsoft.NET.Sdk">
  <PropertyGroup>
    <OutputType>Exe</OutputType>
    <TargetFramework>net10.0</TargetFramework>
    <RootNamespace>ShelfDocs</RootNamespace>
    <OptionStrict>On</OptionStrict>
    <TreatWarningsAsErrors>true</TreatWarningsAsErrors>
    <NuGetAudit>false</NuGetAudit>
    <GenerateDocumentationFile>true</GenerateDocumentationFile>
  </PropertyGroup>
</Project>
----

[source,vbnet]
----
Option Strict On

''' <summary>
''' Lends items from the shelf.
''' </summary>
''' <remarks>
''' <para>A <see cref="Loan(Of T)"/> is created for every successful call.</para>
''' <list type="bullet">
'''   <item><description>Books can be borrowed for 21 days.</description></item>
'''   <item><description>Magazines can be borrowed for 7 days.</description></item>
''' </list>
''' </remarks>
''' <typeparam name="T">The kind of item that is lent.</typeparam>
''' <example>
''' Lend a title and read the due date:
''' <code language="vb">
''' Dim loan = New Loan(Of String)("Dune", 21)
''' Console.WriteLine(loan.Days)
''' </code>
''' </example>
Public Class Loan(Of T)
    Private ReadOnly _item As T
    Private ReadOnly _days As Integer

    ''' <summary>Creates a loan.</summary>
    ''' <param name="item">The item being lent.</param>
    ''' <param name="days">The loan period in days; must be positive.</param>
    ''' <exception cref="ArgumentOutOfRangeException"><paramref name="days"/> is zero or negative.</exception>
    Public Sub New(item As T, days As Integer)
        If days <= 0 Then Throw New ArgumentOutOfRangeException(NameOf(days))
        _item = item
        _days = days
    End Sub

    ''' <summary>The loan period in days.</summary>
    ''' <value>A positive number of days.</value>
    Public ReadOnly Property Days As Integer
        Get
            Return _days
        End Get
    End Property

    ''' <summary>Gets the due date.</summary>
    ''' <param name="start">The day the loan starts.</param>
    ''' <returns>The last day on which the <typeparamref name="T"/> may be kept, as <c>start + Days</c>.</returns>
    ''' <seealso cref="Days"/>
    ''' <seealso href="https://learn.microsoft.com/dotnet/visual-basic/">Visual Basic documentation</seealso>
    Public Function DueOn(start As Date) As Date
        Return start.AddDays(_days)
    End Function

    ''' <summary>Raised when the item is returned.</summary>
    Public Event Returned As EventHandler

    ''' <summary>Marks the loan as returned.</summary>
    Public Sub GiveBack()
        RaiseEvent Returned(Me, EventArgs.Empty)
    End Sub

    ''' <summary>Adds two periods.</summary>
    ''' <param name="a">First period.</param>
    ''' <param name="b">Second period.</param>
    ''' <returns>The sum.</returns>
    Public Shared Operator +(a As Loan(Of T), b As Loan(Of T)) As Integer
        Return a.Days + b.Days
    End Operator
End Class

''' <summary>A magazine loan that reuses the documentation of its base.</summary>
Public Class MagazineLoan
    Inherits Loan(Of String)

    ''' <inheritdoc/>
    Public Sub New(item As String, days As Integer)
        MyBase.New(item, days)
    End Sub
End Class

''' <summary>Includes documentation from another file.</summary>
''' <include file="Shared.xml" path="docs/member[@name='Policy']/*"/>
Public Module Policy
    ''' <summary>The default loan period.</summary>
    Public Const DefaultDays As Integer = 21

    ''' <summary>Describes the <c>Overdue</c> state.</summary>
    Public Enum State
        ''' <summary>Not yet due.</summary>
        Open
        ''' <summary>Past the due date.</summary>
        Overdue
    End Enum
End Module

Module Program
    Sub Main()
        Dim l As New Loan(Of String)("Dune", Policy.DefaultDays)
        Console.WriteLine(l.DueOn(New Date(2026, 10, 19)).ToString("yyyy-MM-dd"))
    End Sub
End Module
----

What the file shows:

* *Member ids.* Each `+<member name="...">+` is a code that identifies the member in metadata: `T:` for a type, `M:` for a method or
  constructor (`+#ctor+`), `P:` property, `F:` field (also enumeration members and constants), `E:` event. A generic type with one type
  parameter gets the suffix `++`1++` (the id of the class `Loan(Of T)` is `++T:ShelfDocs.Loan`1++`), a type parameter of the type is
  referred to as `++`0++` in signatures, and the operator `pass:c[+]` of `Loan(Of T)` is the method `op_Addition`. The ids include the root
  namespace (`ShelfDocs`), which is why a project with a wrong `RootNamespace` ships documentation that does not match its types.
* *`cref` is rewritten.* `<see cref="Loan(Of T)"/>` was written by the programmer in Visual Basic syntax; the compiler resolved it and wrote
  the id `++T:ShelfDocs.Loan`1++`. A `cref` is how a tool knows which member is meant, so it is the one attribute worth being careful with.
* *Text is kept as written.* The compiler does not interpret `summary`, `remarks` and the formatting tags; it copies them. The
  `language="vb"` on `code` is a convention that DocFX and editors use to colour the sample.
* *`include` is expanded by the compiler.* The `Policy` module's comment now contains the `remarks` from `Shared.xml`.
* *`inheritdoc` is not.* The constructor of `MagazineLoan` still contains `<inheritdoc/>`. The compiler leaves the tag for the
  consumer to resolve (Visual Studio IntelliSense and DocFX do so; the DocFX run below showed it resolved).
* The documentation of the module member `DefaultDays` and of the nested enumeration appear with their own ids; a `Public Module`
  is a type like any other (`T:ShelfDocs.Policy`).

The reference for the tag set is the Microsoft page "Recommended XML tags for documentation comments (Visual Basic)". It lists the
tags above plus `permission`, and states that the compiler *verifies the syntax* of the tags whose attribute names a code element
(`cref`, `exception`, `include`, `param`, `see`, `seealso`, `typeparam`, `permission`), which is where the warnings in the next section come
from.

[cols="2,5,3",options="header"]
|===
|Tag |Use |Checked by the compiler

|`summary`
|One or two sentences: what it is. This is the text IntelliSense shows first.
|Placement only.

|`remarks`
|Detail, usage notes, links to the concepts; can contain `para` and `list`.
|Placement only.

|`param`, `typeparam`
|One per parameter or type parameter, with the exact name.
|The name must exist (BC42307, BC42317), and must not be repeated (BC42305).

|`paramref`, `typeparamref`
|A reference to a parameter inside text.
|Not checked in the test that produced this page.

|`returns`
|What a function returns.
|Not allowed on a `Sub` (BC42306).

|`value`
|What a property holds.
|Placement only.

|`exception`
|A type that the member can throw, with the condition.
|`cref` is required (BC42319) and must resolve (BC42309).

|`see`, `seealso`
|A reference to a type or member (`cref`), a web page (`href`) or a keyword (`langword`).
|`cref` must resolve (BC42309).

|`example`, `code`, `c`
|A sample, a block of code, inline code.
|Not compiled: the code in the comment can rot.

|`list`, `para`, `item`, `description`
|Structure inside `remarks`.
|Well-formed XML only.

|`include`
|Text from another XML file, selected by an XPath expression.
|Expanded at compile time; a failure is written into the XML (see below).

|`inheritdoc`
|Copy the documentation from the base type or interface.
|Not expanded; consumers do it.
|===

== What the compiler checks, and what it does not

The compiler reports documentation problems as warnings, with the ids BC42301 to BC42321. Because they are warnings, a project that sets
`TreatWarningsAsErrors` turns them into errors, and that is the setting that keeps documentation accurate. The next program contains
one of each content error. It was built with `TreatWarningsAsErrors` set to false so that the warnings print:

[source,vbnet]
----
Option Strict On

Public Class Content
    ''' <summary>The parameter name is misspelled.</summary>
    ''' <param name="wrong">There is no such parameter.</param>
    Public Sub A(right As Integer)
    End Sub

    ''' <summary>The same parameter is documented twice.</summary>
    ''' <param name="x">First.</param>
    ''' <param name="x">Second.</param>
    Public Sub B(x As Integer)
    End Sub

    ''' <summary>An unresolved reference: <see cref="Nowhere"/>.</summary>
    Public Sub C()
    End Sub

    ''' <summary>The type parameter does not exist.</summary>
    ''' <typeparam name="U">No such type parameter.</typeparam>
    Public Sub D()
    End Sub

    ''' <summary>An exception tag without cref.</summary>
    ''' <exception>Something goes wrong.</exception>
    Public Sub E()
    End Sub

    ''' <summary>A returns tag on a Sub.</summary>
    ''' <returns>Nothing is returned.</returns>
    Public Sub F()
    End Sub

    ''' <summary>The XML is not well formed: <b>unclosed.</summary>
    Public Sub G()
    End Sub

    ''' <summary>A property has no parameters to document.</summary>
    ''' <param name="v">Not allowed here.</param>
    Public Property P As Integer

    Public Sub Undocumented()
    End Sub
End Class

Module Program
    Sub Main()
    End Sub
End Module
----

Observations:

* *The well-formedness error is reported four times* for the one unclosed `<b>` tag (BC42304), and the whole comment of that member
  is dropped from the XML file ("XML comment will be ignored"). One typo costs the member its documentation.
* *Parameters are matched by name and kind.* BC42307 mentions the kind of declaration (`sub`, `property`); a property has no
  parameters to document (apart from an indexed one), so `param` on `P` is wrong.
* *The member without a comment gives no warning.* `Undocumented` is public and has no comment, and the compiler printed nothing. Unlike
  C# (warning CS1591 when `GenerateDocumentationFile` is on), the Visual Basic compiler has no "missing XML comment" warning in this
  test. If missing documentation must fail the build, you need a review rule or a custom analyzer; the .NET analyzers below do not
  include one for Visual Basic.
* *A `cref` to an overload resolves only if the form exists:* in another run `<see cref="D(Integer)"/>` resolved and `<see cref="D(String)"/>`
  (no such overload) printed BC42309.

The partial-class rule is the one that surprises people: if *both* parts of a `Partial` class have a summary, the compiler ignores
the comments of the class (BC42314, reported at both parts) and keeps those of the members. Document one part only, usually the one in
the main file. The namespace comment (BC42312 at line 3) confirms that a namespace cannot carry documentation, and the comment after
the last member (line 23) has nothing to attach to.

=== An include that fails is not a warning

A missing include file or a wrong XPath does not produce a build warning at all. The compiler writes the failure *into the XML file* as
a comment, and the build reports `0 Warning(s)`:

[source,vbnet]
----
Option Strict On

Public Class Inc
    ''' <include file="nothing.xml" path="a/b"/>
    Public Sub F()
    End Sub

    ''' <include file="Shared.xml" path="docs/member[@name='Nope']/*"/>
    Public Sub G()
    End Sub
End Class

Module Program
    Sub Main()
    End Sub
End Module
----

[source,xml]
----
<member name="M:ShelfDocs.Inc.F">
 <!--warning BC42321: Unable to include XML fragment 'a/b' of file 'nothing.xml'. File not found.-->
</member>
<member name="M:ShelfDocs.Inc.G">
 <!--warning BC42320: Unable to include XML fragment 'docs/member[@name='Nope']/*' of file 'Shared.xml'.-->
</member>
----

Build output: `0 Warning(s)`. So a documentation file can contain BC42320 and BC42321 while the build is green; after any change to
included documents, search the generated XML for `warning BC`.

== Generating a documentation site (DocFX)

The XML file is input to documentation generators; the one the .NET team uses is **DocFX** (the site's C# section describes its
configuration in
xref:programming-languages/csharp/coding-conventions-and-documentation.adoc[Coding Conventions and Documentation]). The Visual Basic
result of a DocFX 2.81.0 run on the program above was:

* Pointing `docfx metadata` at the `.vbproj` failed in the test with `error BC30002: Type 'Global.Microsoft.VisualBasic.ApplicationServices.ApplicationBase' is not defined`
  (and similar for `Computer` and `User`), the same missing My types as in a project with the wrong `MyType` (see
  xref:programming-languages/visual-basic/the-my-namespace.adoc[The My Namespace]), and the run ended with 4 errors and no output.
* Pointing it at the compiled assembly (`"src": "bin/Debug/net10.0", "files": ["Tags.dll"]`) worked: it wrote `ShelfDocs.Loan-1.yml` and
  the other pages, each with `content` in C# *and* `content.vb` in Visual Basic (`content.vb: Public Class Loan(Of T)`,
  `content.vb: Public Function DueOn(start As Date) As Date`), and it resolved the `inheritdoc` (the constructor of `MagazineLoan` got
  the summary `Creates a loan.` of its base).

So the workable pipeline for a Visual Basic library is: build with `GenerateDocumentationFile`, point DocFX at the DLL, publish the HTML.

Source: https://dotnet.github.io/docfx/[DocFX]

For DocFX itself, see xref:documentation-tools/docfx/dotnet-api-docs.adoc[DocFX .NET API Docs] in the Documentation Tools section.

== .NET analyzers: CA and IDE rules

The .NET SDK includes the Roslyn analyzers; nothing needs to be installed for projects that target .NET 5 or later. There are two
families, both documented per rule on Learn:

* *Code quality rules* (`CAnnnn`): correctness, security, performance, design and usage (`CA2200` rethrow, `CA1305` culture,
  `CA1822` could be static, `CA1062` validate arguments).
* *Code style rules* (`IDEnnnn`): formatting, naming, preferences (`IDE0005` unnecessary import, `IDE0044` readonly field,
  `IDE0055` formatting, `IDE1006` naming).

The next project has one class with deliberate smells and an `.editorconfig` that is moved out of the way for the first runs. The
project is the usual one with `TreatWarningsAsErrors` off:

[source,xml]
----
<Project Sdk="Microsoft.NET.Sdk">
  <PropertyGroup>
    <OutputType>Exe</OutputType>
    <TargetFramework>net10.0</TargetFramework>
    <RootNamespace>ShelfDocs</RootNamespace>
    <OptionStrict>On</OptionStrict>
    <TreatWarningsAsErrors>false</TreatWarningsAsErrors>
    <NuGetAudit>false</NuGetAudit>
    <GenerateDocumentationFile>false</GenerateDocumentationFile>
  </PropertyGroup>
</Project>
----

[source,vbnet]
----
Option Strict On

Imports System.Text

Public Class shelfItem
    Private count As Integer
    Private ReadOnly _titles As New List(Of String)()

    Public Function Describe(value As Double, unusedParameter As Integer) As String
        Dim label As String
        If value > 1 Then
            label = "big"
        Else
            label = "small"
        End If
        Return label & value.ToString()
    End Function

    Public Sub Rethrow()
        Try
            Console.WriteLine("work")
        Catch ex As InvalidOperationException
            Throw ex
        End Try
    End Sub

    Public Function Total(items As Integer()) As Integer
        Dim sum As Integer = 0
        For Each i As Integer In items
            sum = sum + i
        Next
        Return sum
    End Function
End Class

Module Program
    Sub Main()
        Dim item As New shelfItem()
        Console.WriteLine(item.Describe(2.5, 0))

== Configuring severity

A diagnostic has an id, a default severity and a *configured* severity. Where the configuration comes from, in the order that most
people meet it:

[cols="3,5",options="header"]
|===
|Mechanism |What it does

|`.editorconfig`
|A text file in the project directory or above. A section header such as `+[*.vb]+` selects files. `dotnet_diagnostic.CA2200.severity = error`
sets one rule; `dotnet_analyzer_diagnostic.category-Style.severity = warning` sets a category (only for rules that are enabled by default); the
values are `error`, `warning`, `suggestion`, `silent`, `none` and `default`.

|`.globalconfig`
|The same keys with `is_global = true` at the top and no section headers; applies to the whole project and need not be in a folder
hierarchy. A file named `.globalconfig` is picked up automatically.

|MSBuild properties
|`NoWarn` (list of ids), `WarningsAsErrors`, `WarningsNotAsErrors`, `TreatWarningsAsErrors`, `AnalysisLevel`, `AnalysisMode`,
`EnforceCodeStyleInBuild`. They map to the compiler options `-nowarn`, `-warnaserror` and `-warnaserror-`.

|In-source directives
|`#Disable Warning` and `#Enable Warning` around a region, or `<SuppressMessage>` on a declaration.
|===

The Visual Basic compiler has no warning *level* option: its help lists `-nowarn`, `-warnaserror`, `-ruleset`, `-errorlog`,
`-skipanalyzers` but not `-warn:n`, which C# has. Visual Basic controls warnings by id, never by wave. The older `.ruleset` files are superseded by `.editorconfig`; the Microsoft documentation says that rule set files are
deprecated in favour of EditorConfig. Do not start a new project with a ruleset.

unused locals, three of them suppressed in different ways. The code:

== Code style and naming with .editorconfig

Style rules (`IDE` ids) decide how the code should look. An `.editorconfig` has general options (indentation, line endings), .NET
style options (`dotnet_style_*`), Visual Basic-specific options (`visual_basic_*`) and *naming rules*. This is the file used in
the next run. Everything is in the `+[*.vb]+` section:

[source,ini]
----
root = true

[*.vb]
indent_style = space
indent_size = 4

# naming rules: types are PascalCase, private fields start with an underscore
dotnet_naming_symbols.types.applicable_kinds = class, struct, interface, enum
dotnet_naming_symbols.private_fields.applicable_kinds = field
dotnet_naming_symbols.private_fields.applicable_accessibilities = private
dotnet_naming_style.pascal.capitalization = pascal_case
dotnet_naming_style.underscore_camel.required_prefix = _
dotnet_naming_style.underscore_camel.capitalization = camel_case
dotnet_naming_rule.types_are_pascal.symbols = types
dotnet_naming_rule.types_are_pascal.style = pascal
dotnet_naming_rule.types_are_pascal.severity = warning
dotnet_naming_rule.private_fields_underscore.symbols = private_fields
dotnet_naming_rule.private_fields_underscore.style = underscore_camel
dotnet_naming_rule.private_fields_underscore.severity = warning

# style options and the severity of the rules that use them
dotnet_style_prefer_conditional_expression_over_assignment = true:warning
dotnet_style_prefer_compound_assignment = true:warning
dotnet_code_quality_unused_parameters = all:warning

* *`IDE` rules do not run in `dotnet build` unless `EnforceCodeStyleInBuild` is true* (run 5 shows only the two `CA` warnings). They always
  run in Visual Studio's editor. Put the property in `Directory.Build.props` so that the build and the editor agree.
* *The compiler told us what was missing for IDE0005.* The line starting `vbc : warning EnableGenerateDocumentationFile` says that the
  unnecessary-import rule is enforced on build only when `GenerateDocumentationFile` is true (it needs the XML-documentation analysis
  pass). That is a good reason to switch it on in every project. Without it, the unused `Imports System.Text` of `Playground.vb` is not
  reported by the build (the text above shows no IDE0005 line).
* *The naming rules need two settings.* The `dotnet_naming_rule.*.severity` lines alone did not produce a build diagnostic in the test:
  the line `dotnet_diagnostic.IDE1006.severity = warning` was needed as well (the second last block of the file). With both, the
  class `shelfItem` and the field `count` were reported.
* *Naming rules read like data.* A rule has three parts: a symbol group (`applicable_kinds`: `class`, `struct`, `interface`, `enum`,
  `field`, `property`, `method`, `parameter`, `local` and others; `applicable_accessibilities`; `required_modifiers`), a style
  (`capitalization`, `required_prefix`, `required_suffix`, `word_separator`) and a severity, and when several rules match a
  symbol the most specific one applies (see the Learn page on naming rules for the order).
* *The messages come from the same analyzers as C#.* IDE0045 says "'If' statement can be simplified" and the fix is
  `If(condition, a, b)`.
* Formatting rule IDE0055 works on Visual Basic (see `dotnet format` below).

== Applying style: dotnet format and Code Cleanup

`dotnet format` is part of the SDK and fixes what the analyzers find. It has three subcommands: `whitespace` (indentation, spacing, line
endings), `style` (the IDE rules) and `analyzers` (the CA rules); with none, it runs all three. `--verify-no-changes` makes it a CI
check. The project below has the `.editorconfig` above and a deliberately untidy file:

[source,vbnet]
----

Imports System

    Private _total As Integer

    Public Sub  Add( amount As Integer )
            _total = _total + amount
    End Sub

    Public Function Label() As String
        Dim text As String
        If _total > 10 Then
            text = "many"
        Else
            text = "few"
        End If
        Return text
    End Function
End Class

Module Program
    Sub Main()
        Dim c As New Counter()
        c.Add( 3 )
        Console.WriteLine(c.Label())
    End Sub
End Module
----

== Naming and coding standards

Documentation and tools do not replace a convention; they enforce one. The Microsoft naming guidance applies to Visual Basic as it
does to C#, and the Visual Basic coding conventions page adds the language-specific rules. The rules that matter most in review are in
the table. The `Option` statements and the explicit-typing rules behind them are on
xref:programming-languages/visual-basic/option-statements.adoc[Option Statements]; the consolidated list of habits is on
xref:programming-languages/visual-basic/best-practices-and-common-pitfalls.adoc[Best Practices and Common Pitfalls].

[cols="3,4,4",options="header"]
|===
|Subject |Convention |Enforced by

|Types, methods, properties, events, constants
|PascalCase, a noun for a type, a verb for a method; interfaces start with `I`
|naming rule `dotnet_naming_rule` + IDE1006

|Parameters and locals
|camelCase; no type prefixes (`strName`, `intCount` are Hungarian notation from VB6)
|naming rule, review

|Private fields
|`_camelCase` is the common convention in .NET code (a decision for the team, then an `.editorconfig` rule)
|naming rule + IDE1006

|Case
|Visual Basic is case-insensitive: two members that differ only by case collide (the compiler reports a duplicate declaration), and a
parameter named like a member hides it. Keep one spelling
|compiler; review

|Types and strings
|`Option Strict On` in the project, `&` for concatenation, `AndAlso`/`OrElse`, `Is Nothing`
|project property; `Option` statements

|Comments
|Say why, not what; XML comments on every public member of a library; never leave commented-out code
|`TreatWarningsAsErrors` (BC4230x); review
|===

Source: https://learn.microsoft.com/dotnet/visual-basic/programming-guide/program-structure/coding-conventions[Visual Basic coding conventions], https://learn.microsoft.com/dotnet/standard/design-guidelines/naming-guidelines[Naming guidelines]

== Putting it together

A repository that wants documentation, analysis and style enforced from the first commit needs four files and one command:

[source,xml]
----
<Project>
  <PropertyGroup>
    <TargetFramework>net10.0</TargetFramework>
    <OptionStrict>On</OptionStrict>
    <TreatWarningsAsErrors>true</TreatWarningsAsErrors>
    <GenerateDocumentationFile>true</GenerateDocumentationFile>
    <EnforceCodeStyleInBuild>true</EnforceCodeStyleInBuild>
    <AnalysisLevel>latest-recommended</AnalysisLevel>
  </PropertyGroup>
</Project>
----

saved as `Directory.Build.props` at the root, an `.editorconfig` next to it with the severities and naming rules above, and a CI step
`dotnet build` followed by `dotnet format --verify-no-changes`. Adopt it on an existing code base in this order: turn
`TreatWarningsAsErrors` on with `WarningsNotAsErrors` for the known backlog, fix the BC4230x documentation warnings (they are cheap),
raise the analysis level one step at a time, and run `dotnet format` as one commit that changes nothing else. The older approach
that books describe, FxCop binary analysis and rule set files in the Visual Studio project properties, is superseded: the analyzers
are in the SDK, the configuration is a text file, and the documentation warnings are compiler warnings, not a separate tool.
