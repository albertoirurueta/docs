== PHPStan

PHPStan analyses a code base at a chosen *rule level*, from 0 (basic checks: unknown classes, functions and methods)
to 10 (everything, including strictness about `mixed`). New projects start at a high level; existing projects raise
the level gradually, often with a *baseline* that records today's errors so that only new ones fail the build.

[cols="1,3",options="header"]
|===
| Level | Adds

| 0 | unknown classes, functions, methods called on `$this`, wrong argument counts
| 1-2 | possibly undefined variables, unknown methods on all expressions, PHPDoc validation
| 3-4 | return types, property types, dead code, always-true/false conditions
| 5 | argument types of method and function calls
| 6 | missing type declarations (typehints)
| 7 | union types: every member must support the operation
| 8 | nullability: calling methods on possibly `null` values
| 9 | strictness with explicit `mixed`
| 10 | strictness with implicit `mixed` (missing types)
|===

[source,bash]
----
composer require --dev phpstan/phpstan
vendor/bin/phpstan analyse src --level=9
vendor/bin/phpstan analyse --generate-baseline      # record existing errors in phpstan-baseline.neon
----

[source,yaml]
----
# phpstan.neon
parameters:
    level: 9
    paths:
        - src
    # includes:
    #     - phpstan-baseline.neon
----

Source: https://phpstan.org/user-guide/rule-levels[PHPStan -- Rule Levels] and https://phpstan.org/user-guide/baseline[PHPStan -- The Baseline]

=== What it finds

Given this code, which runs without errors in many cases:

[source,php]
----
<?php

declare(strict_types=1);

namespace Library;

final readonly class Book
{
    public function __construct(public string $title, public int $year) {}
}

final class Report
{
    /**
     * @param array{title: string, year: int} $row
     */
    public static function fromRow(array $row): Book
    {
        return new Book($row['title'], $row['yaer']);          // typo in the key
    }

    /** @param Shelf<Book> $shelf */
    public static function firstTitle(Shelf $shelf): string
    {
        return $shelf->first()->title;                          // first() may return null
    }

    public static function count(array $titles): int
    {
        return count($titles) . ' titles';                      // returns a string
    }
}
----

PHPStan at level 9 reports four errors:

[source,text]
----

=== PHPDoc types and generics

PHP's native types cannot express element types, shapes or generics, so analysers read a richer type language from
PHPDoc. Both PHPStan and Psalm understand it:

[cols="1,3",options="header"]
|===
| Type | Meaning

| `list<Book>`, `array<string, int>`, `non-empty-array<…>` | arrays by key and value type
| `+array{title: string, year: int, subtitle?: string}+` | array *shapes* (optional keys with `?`)
| `non-empty-string`, `numeric-string`, `positive-int`, `int<1, 5>`, `literal-string` | refined scalars
| `class-string<Book>`, `callable(string): int`, `Closure(Book): bool` | class names and callable signatures
| `@template T`, `@template T of object`, `@extends Collection<Book>`, `@implements IteratorAggregate<int, Book>` | generics
| `@phpstan-param`, `@phpstan-return`, `@psalm-…` | tool-specific overrides that other tools ignore
| `@phpstan-assert`, `@phpstan-impure`, `@readonly` | assertions and purity
|===

A generic collection, checked by PHPStan wherever it is used:

[source,php]
----
<?php

declare(strict_types=1);

namespace Library;

/**
 * @template T of object
 */
final class Shelf
{
    /** @var list<T> */
    private array $items = [];

    /** @param T $item */
    public function add(object $item): void
    {
        $this->items[] = $item;
    }

    /** @return T|null */
    public function first(): ?object
    {
        return $this->items[0] ?? null;
    }
}

/** @var Shelf<\DateTimeImmutable> $returns */
$returns = new Shelf();
$returns->add(new \DateTimeImmutable('2026-10-05'));
echo $returns->first()?->format('Y-m-d'), "\n";      // PHPStan knows first() returns ?DateTimeImmutable
----

Source: https://phpstan.org/writing-php-code/phpdoc-types[PHPStan -- PHPDoc Types] and https://phpstan.org/blog/generics-in-php-using-phpdocs[PHPStan -- Generics in PHP using PHPDocs]

=== Why generics stay in PHPDoc

Native generics have been discussed for a decade: runtime-checked generics would be expensive in PHP's engine, and
erased generics (checked only by tools) raise the question of what the engine should do with them. Successive RFC
drafts and research by the PHP Foundation have not produced an accepted design, so the ecosystem has standardised on
PHPDoc generics: PHPStan, Psalm and PhpStorm all support `@template`, and framework code (Laravel's collections,
Doctrine's repositories) is annotated with them.

== Extensions and framework support

PHPStan understands framework magic through *extensions*: Larastan for Laravel (Eloquent models, facades, container),
`phpstan-symfony`, `phpstan-doctrine`, `phpstan-phpunit`, plus rule packages such as `phpstan-strict-rules`. Install
them with Composer and, with `phpstan/extension-installer`, they register themselves.

[source,bash]
----
composer require --dev larastan/larastan     # in a Laravel project
vendor/bin/phpstan analyse --memory-limit=1G
----

Source: https://phpstan.org/user-guide/extension-library[PHPStan -- Extension Library] and https://github.com/larastan/larastan[Larastan]

== Psalm

*Psalm* is the other major analyser. It has the same goals and the same PHPDoc type language, with different
strengths: *taint analysis* (tracking untrusted input to dangerous sinks such as SQL queries or `echo`), a powerful
`@psalm-assert` system, and automatic fixes with `psalter`. Version 6 is the current stable line (7.0 is in release
candidate on the date of writing). Teams usually pick one analyser; running both is uncommon.

[source,bash]
----
composer require --dev vimeo/psalm
vendor/bin/psalm --init               # creates psalm.xml with an error level
vendor/bin/psalm --taint-analysis
----

Source: https://psalm.dev/docs/[Psalm documentation] and https://psalm.dev/docs/security_analysis/[Psalm -- Security Analysis]

== Rector: automated refactoring and upgrades

*Rector* parses code and applies *rules* that rewrite it: upgrading to a newer PHP version, adding type declarations
inferred from code, removing dead code, migrating framework APIs (Laravel, Symfony, PHPUnit). It is the standard way
to move a large code base forward, together with tests and a static analyser to confirm the result.

[source,php]
----
<?php

declare(strict_types=1);

// rector.php
use Rector\Config\RectorConfig;

return RectorConfig::configure()
    ->withPaths([__DIR__ . '/legacy'])
    ->withPhpSets(php85: true)                                      // all upgrades up to PHP 8.5
    ->withPreparedSets(deadCode: true, typeDeclarations: true);
----

Given a PHP 7-style class:

[source,php]
----
<?php

namespace Library\Legacy;

class Loan
{
    private $isbn;
    private $days;

    public function __construct(string $isbn, int $days = null)
    {
        $this->isbn = $isbn;
        $this->days = $days;
    }

    public function describe()
    {
        return $this->isbn . ' for ' . $this->days . ' days';
    }

    public function status($code)
    {
        switch ($code) {
            case 1:
                return 'active';
            case 2:
                return 'returned';
            default:
                return 'unknown';
        }
    }

    public function hasPrefix($isbn)
    {
        return strpos($isbn, '978') !== false;
    }
}
----

Applied rules:
 * ClassPropertyAssignToConstructorPromotionRector
 * StrContainsRector
 * ChangeSwitchToMatchRector
 * ReadOnlyPropertyRector
 * BoolReturnTypeFromBooleanStrictReturnsRector
 * StringReturnTypeFromStrictStringReturnsRector

Note how it also fixes the implicitly nullable `int $days = null` (deprecated in 8.4) into `?int`. Review the diff,
run the tests, then apply it with `vendor/bin/rector process`. Laravel Shift and Rector's framework rule sets automate
framework upgrades in the same way (see xref:web/php-laravel/whats-changed-and-upgrading.adoc[What's Changed and
Upgrading]).

== Putting it in CI

A typical quality pipeline runs, on every pull request: the coding-style fixer in check mode, the static analyser at
the project's level, the tests, and `composer audit`:

[source,bash]
----
vendor/bin/php-cs-fixer fix --dry-run --diff     # or vendor/bin/pint --test
vendor/bin/phpstan analyse --no-progress --error-format=github
vendor/bin/phpunit
composer audit
----

Coding style tools are described in xref:programming-languages/php/psr-standards-and-coding-style.adoc[PSR Standards
and Coding Style], testing in xref:programming-languages/php/testing-with-phpunit-and-pest.adoc[Testing with PHPUnit
and Pest].

Source: https://phpstan.org/user-guide/output-format[PHPStan -- Output format]

== Where older books and tutorials are outdated

None of the books consulted for this section covers static analysis: PHPStan (2016), Psalm (2016) and Rector (2017)
appeared around or after their publication, and the PHPDoc type language (generics, array shapes, refined scalar types)
matured later. Books rely on runtime checks and code review for the kinds of bugs these tools find automatically.
PHPStan 2.0 (2024) added level 10 and stricter `list` handling; the PHPCompatibility sniffs for PHP_CodeSniffer
complement Rector by detecting code that will break on a newer PHP version.
