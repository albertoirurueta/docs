== The operators at a glance

The specification groups the operators and defines the precedence of the binary ones in
https://go.dev/ref/spec#Operator_precedence[Operator precedence]. Unary operators bind tighter than every binary
operator. Binary operators of the same precedence associate from left to right.

[cols="1,3,3",options="header"]
|===
| Precedence | Operators | Meaning

| 5
| `+*+`  `+/+`  `+%+`  `+<<+`  `+>>+`  `+&+`  `+&^+`
| multiplication, division, remainder, shifts, bitwise AND, bit clear (AND NOT)

| 4
| `pass:c[+]`  `-`  `\|`  `+^+`
| addition or concatenation, subtraction, bitwise OR, bitwise XOR

| 3
| `==`  `!=`  `<`  `+<=+`  `>`  `>=`
| comparison, giving an untyped boolean

| 2
| `+&&+`
| logical AND, short-circuiting

| 1
| `\|\|`
| logical OR, short-circuiting

| unary
| `pass:c[+]`  `-`  `!`  `+^+`  `+*+`  `+&+`  `+<-+`
| identity, negation, logical NOT, bitwise complement, pointer dereference, address-of, channel receive
|===

Go has five binary precedence levels where C has more than a dozen, and the bitwise operators sit with the arithmetic ones
rather than below the comparisons. That removes one of the classic C traps, discussed under
<<_precedence_and_associativity,Precedence and associativity>>. Assignment (`=`, `:=` and the compound forms such as
`+=`) and `pass:c[++]`/`--` are not part of the expression grammar at all: they are statements, covered in
<<_assignment_and_incrementdecrement,Assignment and increment/decrement>>.

== Arithmetic operators

The arithmetic operators `pass:c[+]`, `-`, `+*+` and `/` apply to numeric types and `pass:c[+]` also concatenates strings; `%` and the bitwise
operators apply only to integers. Both operands must have the same type (or one must be an untyped constant that
converts to the other's type): Go never converts silently, so `int + int64` or `int * float64` is a compile error, not a
promotion. The rules are in https://go.dev/ref/spec#Arithmetic_operators[Arithmetic operators].

Three behaviours deserve attention:

* *Integer division truncates toward zero* and the remainder takes the sign of the dividend, so
  `(a/b)*b + a%b == a` always holds. This differs from Python and Ruby, whose `%` follows the divisor, and matches
  C99 and Java.
* *Integer overflow wraps around* at run time for signed and unsigned types. There is no trap and no undefined behaviour,
  unlike signed overflow in C. The wrapped value is the one the two's-complement representation gives, and it is
  well defined by the spec ("Integer overflow"). The single signed division that overflows, the most negative value
  divided by `-1`, does not panic either: it yields the dividend.
* *Floating-point arithmetic follows IEEE 754*: division by zero gives an infinity or `NaN` and never panics. *Integer*
  division or remainder by a zero divisor panics at run time with `integer divide by zero`.

[source,go]
----
package main

import (
	"fmt"
	"math"
)

func main() {
	// Integer division truncates toward zero; the remainder takes the sign
	// of the dividend, so (a/b)*b + a%b == a always holds.
	for _, p := range [][2]int{{7, 2}, {-7, 2}, {7, -2}, {-7, -2}} {
		a, b := p[0], p[1]
		fmt.Printf("%2d / %2d = %2d   %2d %% %2d = %2d\n", a, b, a/b, a, b, a%b)
	}

	// Integer overflow wraps around silently at run time.
	var small int8 = math.MaxInt8
	small++
	var u uint8
	u--
	fmt.Println("int8 127+1 =", small, " uint8 0-1 =", u)

	// The one signed division that overflows: MinInt64 / -1 does not panic.
	m, minus1 := int64(math.MinInt64), int64(-1)
	fmt.Println("MinInt64 / -1 =", m/minus1, " MinInt64 % -1 =", m%minus1)

	// Floating point follows IEEE 754: no panic on division by zero.
	zero := 0.0
	fmt.Println(1/zero, -1/zero, zero/zero, zero/zero == zero/zero)

	// Complex numbers support + - * / and ==.
	c := complex(1, 2) * complex(3, -1)
	fmt.Println(c, real(c), imag(c))

	// Integer division by zero is a run-time panic.
	defer func() { fmt.Println("recovered:", recover()) }()
	d := 0
	fmt.Println(10 / d)
}
----

Code that must detect overflow at run time uses explicit range checks or the helpers in
https://pkg.go.dev/math/bits[math/bits] (`bits.Add64`, `bits.Mul64` and friends return a carry or the high word), or
the `math` constants such as `math.MaxInt64` in a comparison before the operation. Floating-point values are not for
money: use integer cents or a decimal library, as xref:programming-languages/go/types-and-values.adoc[Types and Values] explains.

The `int` type is 64 bits wide on 64-bit platforms and has been since Go 1.1; the language only promises that it is at
least 32 bits, so write `int64` when the width matters. Complex numbers (`complex64`, `complex128`) support
`pass:c[+]`, `-`, `+*+`, `/`, `==` and `!=`, with the built-ins `complex`, `real` and `imag`, as the first example shows.

== Bitwise operators and shifts

The bitwise operators work on integers and operate bit by bit: `&` (AND), `|` (OR), `^` (XOR), `&^` (AND NOT, "bit
clear") and the unary `^` (complement, which C spells `~`). `a &^ b` clears in `a` every bit that is set in `b`, which is
the idiomatic way to remove a flag from a bit set. Because Go has no `~` unary operator on integers (the symbol `~T` in
a constraint is something else, see xref:programming-languages/go/generics.adoc[Generics]), the complement of an
unsigned `x` is `^x` and for signed integers `^x` equals `-x - 1`.

[source,go]
----
package main

import "fmt"

func main() {
	const a, b uint8 = 0b1100_1010, 0b1010_0110
	fmt.Printf("a      %08b\n", a)
	fmt.Printf("b      %08b\n", b)
	fmt.Printf("a & b  %08b  (AND)\n", a&b)
	fmt.Printf("a | b  %08b  (OR)\n", a|b)
	fmt.Printf("a ^ b  %08b  (XOR)\n", a^b)
	fmt.Printf("a &^ b %08b  (AND NOT, bit clear)\n", a&^b)
	fmt.Printf("^a     %08b  (unary ^ is bitwise NOT)\n", ^a)
	fmt.Printf("-5 as ^4: %d, ^0 = %d\n", ^4, ^0)

	// Shifts: left fills with zeros; right shift of a signed value copies the
	// sign bit (arithmetic shift); of an unsigned value it fills with zeros.
	var s int8 = -16
	var us uint8 = 240
	fmt.Println(s>>2, us>>2, s<<1, us<<1)

	// A shift count at or beyond the width gives 0 (or -1 for a negative signed value).
	var n uint = 70
	fmt.Println(uint64(1)<<n, int64(-8)>>n, int64(8)>>n)

	// Since Go 1.13 the shift count may be a signed integer.
	// A negative count panics at run time.
	k := 3
	fmt.Println(1<<k, 256>>k)
	defer func() { fmt.Println("recovered:", recover()) }()
	k = -1
	fmt.Println(1 << k)
}
----

The shift operators `<<` and `>>` behave as follows:

* The left operand is the value, the right operand the *shift count*. Since Go 1.13 the count may be of any integer
  type, signed or unsigned; before then it had to be unsigned, and code written for older releases is full of
  `uint(n)` conversions that are no longer needed. A *negative count panics* at run time; a negative constant count is a
  compile error.
* `<<` fills with zeros. `>>` on an *unsigned* value fills with zeros; on a *signed* value it replicates the sign bit
  (an arithmetic shift), so `-16 >> 2` is `-4`.
* Shifting by the operand's width or more is not undefined as in C: the result is `0`, or `-1` for a negative signed
  value shifted right.
* A shift of a constant by a constant is exact; a *non-constant* shift of an untyped constant is subtle: the constant
  takes the type it would have had if the shift were replaced by its left operand. That makes
  `var f float64 = 1 << s` illegal (a shift of a float) while `var a int32 = 1 << s` computes in `int32`.

[source,go]
----
package main

import "fmt"

func main() {
	var s uint = 33

	// An untyped constant in a non-constant shift takes the type it would
	// have if the shift were replaced by its left operand alone.
	var a int32 = 1 << s // 1 is an int32 here: 1<<33 overflows to 0
	var b int64 = 1 << s // 1 is an int64 here
	var c = 1 << s       // 1 is an int
	fmt.Println(a, b, c)
	fmt.Printf("%T %T %T\n", a, b, c)

	// In a constant shift the operands are exact; the result stays untyped.
	const big = 1 << 100
	fmt.Println(big >> 98)
}
----

== Comparison operators and comparability

`==` and `!=` test equality; `<`, `+<=+`, `>` and `>=` test order. The result of any comparison is an *untyped boolean*
value, which is why `type Flag bool; var f Flag = x == y` compiles. The rules, in
https://go.dev/ref/spec#Comparison_operators[Comparison operators], hinge on two properties of the *type*:

* a type is *comparable* if `==` is defined for it;
* a type is *ordered* if `<` is defined for it.

[cols="2,2,3",options="header"]
|===
| Type | Comparable with `==` | Ordered with `<`

| booleans
| yes
| no

| integers, floats, complex numbers
| yes (floats: `NaN` is never equal, not even to itself)
| integers and floats yes; complex no

| strings
| yes (byte-wise)
| yes (lexicographic by byte)

| pointers
| yes (equal if same address or both nil)
| no

| channels
| yes (same channel or both nil)
| no

| arrays
| yes if the element type is comparable
| no

| structs
| yes if every field is comparable (blank `_` fields are ignored)
| no

| interfaces
| yes, but may panic: see below
| no

| slices, maps, functions
| *only against `nil`*
| no

| type parameters
| if constrained by `comparable` (or a type set of comparable types)
| if constrained by `cmp.Ordered` or an equivalent type set
|===

Both operands must be assignable to a common type, so `int == int64`, `int == float64` and a defined type against its
underlying type with a typed operand are compile errors. An untyped constant converts to the other operand's type, which
is why `isbn == "x"` is fine while `isbn == s` for a `string` variable `s` is not.

[source,go]
----
package main

import (
	"fmt"
	"math"
	"strings"
)

type ISBN string

type Loan struct {
	Book   ISBN
	Member string
	Days   int
}

type Point [2]int

func main() {
	// Numbers, strings, booleans, pointers, channels, interfaces, structs of
	// comparable fields and arrays of comparable elements are comparable.
	l1 := Loan{"9780134190440", "ada", 14}
	l2 := Loan{"9780134190440", "ada", 14}
	fmt.Println("structs:", l1 == l2, l1 != Loan{})
	fmt.Println("arrays: ", Point{1, 2} == Point{1, 2}, [3]string{"a"} == [3]string{"a", "", ""})
	fmt.Println("pointers:", &l1 == &l1, &l1 == &l2)

	// Strings are ordered byte-wise; compare with < <= > >=.
	fmt.Println("strings:", "Go" < "Rust", "apple" < "Apple", "é" > "z", strings.Compare("a", "b"))

	// NaN is unordered: every comparison with it is false except !=.
	nan := math.NaN()
	fmt.Println("NaN:", nan == nan, nan < 1, nan > 1, nan != nan)

	// Interface values are equal when dynamic types and values are equal.
	var a, b any = 1, 1
	var c any = int64(1)
	var n1, n2 any
	fmt.Println("interfaces:", a == b, a == c, n1 == n2, a == nil)

	// Comparison of an interface with a concrete value converts the value.
	fmt.Println("mixed:", a == 1, a == int64(1), c == 1)

	// A map key or == on interface values holding uncomparable dynamic
	// types panics at run time.
	defer func() { fmt.Println("recovered:", recover()) }()
	var x, y any = []int{1}, []int{1}
	fmt.Println(x == y)
}
----

Several things in that output are worth stating explicitly:

* Struct and array equality is *field-by-field and element-by-element*; there is no identity comparison. A pointer
  comparison (`&l1 == &l2`) tests addresses, not contents.
* `"apple" < "Apple"` is false because comparison is by byte value and uppercase letters sort first in ASCII and UTF-8.
  Ordering by locale or case-insensitively needs `strings.EqualFold`, `strings.ToLower`, or the
  `golang.org/x/text/collate` package. `strings.Compare(a, b)` returns -1, 0 or +1 but is almost never better than the
  operators; the `cmp` package (`cmp.Compare`, `cmp.Less`, `cmp.Or`) is the generic equivalent.
* *`NaN` breaks reflexivity*: `x == x` is false for a floating-point `NaN`, so a `NaN` can never be found in a slice by
  value and `math.IsNaN` is required. A `NaN` used as a map key creates entries that cannot be looked up or deleted
  (only `clear` removes them).
* An *interface* value is equal to another if both are nil or if both hold identical dynamic types and equal dynamic
  values. A value of a concrete type compared with an interface is first converted to the interface type, which is why
  `a == int64(1)` is false when `a` holds an `int`.
* If the two dynamic types are identical but not comparable, the comparison *panics at run time*:
  `runtime error: comparing uncomparable type []int`. The compiler cannot catch it, because the static type is only
  `any`. The same panic occurs when such a value is used as a map key.

=== The comparable constraint

In generic code the predeclared constraint `comparable` (Go 1.18) admits the types on which `==` and `!=` are defined.
Go 1.20 relaxed it: an interface type such as `any` now *satisfies* `comparable`, because the comparison is well defined
for it, even though it may panic at run time for an uncomparable dynamic type. Before 1.20 `+Index([]any{...}, x)+` failed
to compile with `any does not satisfy comparable`.

[source,go]
----
package main

import (
	"cmp"
	"fmt"
	"slices"
)

// Index uses the comparable constraint: T must support == and !=.
func Index[T comparable](xs []T, want T) int {
	for i, x := range xs {
		if x == want {
			return i
		}
	}
	return -1
}

func main() {
	fmt.Println(Index([]string{"a", "b"}, "b"))
	fmt.Println(Index([]float64{1, 2}, 2))

	// Since Go 1.20 an interface type satisfies comparable; the comparison
	// can still panic at run time if a dynamic type is not comparable.
	fmt.Println(Index([]any{1, "x", 2.5}, any("x")))
	defer func() { fmt.Println("recovered:", recover()) }()
	fmt.Println(Index([]any{[]int{1}}, any([]int{1})))
}

func init() {
	// cmp.Ordered covers the types that support < <= > >=.
	fmt.Println(cmp.Compare(2, 10), cmp.Compare("b", "a"), slices.Max([]string{"ant", "bee"}))
}
----

== Logical operators

`&&`, `||` and `!` operate on booleans only. There is no truthiness: `if n {` for an integer, or `!n`, is a compile
error (see xref:programming-languages/go/control-flow.adoc[Control Flow]). `&&` and `||` are *short-circuit*
operators: the right operand is evaluated only if the left one does not already decide the result. Use that for guards
(`len(s) > 0 && s[0] == 'x'`, `p != nil && p.ok`). `&&` binds tighter than `||`, so
`a || b && c` means `a || (b && c)`.

[source,go]
----
package main

import "fmt"

func check(name string, v bool) bool {
	fmt.Println("  evaluated", name)
	return v
}

func main() {
	fmt.Println("false && ...:")
	_ = check("A", false) && check("B", true) // B is skipped

	fmt.Println("true || ...:")
	_ = check("C", true) || check("D", false) // D is skipped

	fmt.Println("mixed, && binds tighter than ||:")
	r := check("E", false) || check("F", true) && check("G", true)
	fmt.Println("result:", r)

	// Typical use: a guard before a dereference or an index.
	var names []string
	if len(names) > 0 && names[0] == "Ada" {
		fmt.Println("found")
	}
	fmt.Println(!true, !(1 > 2))
}
----

== Address, dereference and receive operators

Three unary operators connect values to storage and channels:

* `&x` yields a pointer to `x`. The operand must be *addressable*: a variable, a pointer indirection, a slice index
  expression, a field selector of an addressable struct, or an index of an addressable array. As a special case `+&T{...}+`
  takes the address of a composite literal. Map elements are *not* addressable (the map may move them when it grows),
  nor are function results, constants or literals.
* `*p` dereferences a pointer. Dereferencing a nil pointer panics at run time with
  `invalid memory address or nil pointer dereference`. For field and method access Go inserts the dereference for you:
  `p.Title` means `(*p).Title`.
* `+<-ch+` receives from a channel and is an *expression*; the form `+v, ok := <-ch+` reports whether the value was
  actually sent (`ok` is false on a closed, drained channel). The send `+ch <- v+` is a *statement*, not an expression,
  and sending on a receive-only channel is a compile error.

Since Go 1.26 the built-in `new` accepts an expression, `new(int64(5))`, returning a pointer to a variable initialized
with that value; it replaces the helper functions such as `func ptr[T any](v T) *T` that programs used to declare for
optional fields.

[source,go]
----
package main

import "fmt"

type Book struct {
	ISBN  string
	Title string
}

func main() {
	b := Book{"9780134190440", "The Go Programming Language"}
	p := &b // address-of: p has type *Book
	p.Title = "TGPL"
	fmt.Println(b.Title, (*p).Title == p.Title)

	// A composite literal is the one non-variable operand &x accepts.
	q := &Book{ISBN: "1"}
	n := &[]int{1, 2}
	fmt.Println(q.ISBN, *n)

	// *p dereferences; *p = v stores through the pointer.
	x := 1
	px := &x
	*px += 41
	fmt.Println(x, *px)

	// new(expr) (Go 1.26) allocates a variable initialised with a value.
	ptr := new(int64(5))
	fmt.Println(*ptr)

	// Receive: <-ch is an expression; ch <- v is a statement.
	ch := make(chan int, 1)
	ch <- 7
	v, ok := <-ch
	fmt.Println(v, ok)
	close(ch)
	v, ok = <-ch
	fmt.Println(v, ok)

	// A nil pointer dereference panics at run time.
	defer func() { fmt.Println("recovered:", recover()) }()
	var np *Book
	fmt.Println(np.Title)
}
----

----

1 [1 2]

5

0 false

----

== Assignment and increment/decrement

`pass:c[++]` and `--` are *statements* that apply to a numeric variable, and only in the postfix form: `pass:c[i++]` is shorthand for
`i += 1`. There is no `pass:c[++i]`, and `pass:c[j := i++]` or `pass:c[f(i++)]` is a syntax error. Removing the prefix form and the
value-producing form removes a class of order-of-evaluation puzzles. Each binary operator `op` has a compound
assignment `x op= y`, which evaluates the operands of `x` only once (so `t[next()] += 5` calls `next` once).

[source,go]
----
package main

import "fmt"

func main() {
	i := 0
	j := i++
	fmt.Println(j)
}
----

[source,text]
----
main.go:7:8: syntax error: unexpected ++ at end of statement
----

[source,go]
----
package main

import "fmt"

func main() {
	i := 0
	++i
	fmt.Println(i)
}
----

[source,text]
----
main.go:7:2: syntax error: unexpected ++, expected }
----

*Tuple assignment* assigns several values at once. The index expressions and pointer indirections on the left and all
the expressions on the right are evaluated first, in the usual order; then the assignments are carried out left to right.
That is why `a, b = b, a` swaps and why `x, y = y, x+y` advances a Fibonacci pair without a temporary. The blank
identifier `_` discards a value.

[source,go]
----
package main

import "fmt"

func main() {
	// ++ and -- are statements, not expressions; only the postfix form exists.
	i := 0
	i++
	i += 10
	i <<= 2
	i %= 7
	fmt.Println(i)

	// Tuple assignment: all right-hand operands (and index/pointer operands
	// on the left) are evaluated first, then the assignments happen.
	a, b := 1, 2
	a, b = b, a
	fmt.Println(a, b)

	x, y := 0, 1
	for range 10 {
		x, y = y, x+y
	}
	fmt.Println("fib:", x)

	// The spec's example: the index i is evaluated before i is assigned.
	s := []int{10, 20, 30}
	j := 0
	j, s[j] = 1, 99
	fmt.Println(j, s)

	// Swap slice elements and a map entry.
	s[0], s[2] = s[2], s[0]
	m := map[string]int{"a": 1, "b": 2}
	m["a"], m["b"] = m["b"], m["a"]
	fmt.Println(s, m)

	// The blank identifier discards a value.
	_, err := fmt.Sscanf("7", "%d", &i)
	fmt.Println(i, err)

	// Compound assignment evaluates its left operand once.
	idx := 0
	next := func() int { idx++; return idx - 1 }
	t := []int{1, 1, 1}
	t[next()] += 5
	fmt.Println(t, idx)
}
----

[source,text]
----
2
2 1
fib: 55
1 [99 20 30]
[30 20 99] map[a:2 b:1]
7 <nil>
[6 1 1] 1
----

Source: https://go.dev/ref/spec#Assignment_statements[The Go Programming Language Specification: Assignment statements] and https://go.dev/ref/spec#IncDec_statements[IncDec statements]

The short variable declaration `:=` has its own rules (at least one new variable on the left, redeclaration only in the same
scope) described in xref:programming-languages/go/variables-constants-and-iota.adoc[Variables, Constants and iota]; the
mistakes it produces look like this:

	c, d := 5

	}

}
----

----

main.go:9:10: assignment mismatch: 2 variables but 1 value
main.go:10:5: undefined: x
----

== Precedence and associativity

With five levels there is not much to memorise, and the two traps of C are gone. First, `&`, `|` and `^` do not sit
below the comparison operators: `x&1 == 0` means `(x&1) == 0`, whereas in C it parses as `x & (1 == 0)`. Second, the
shifts have the same precedence as multiplication, so `1<<2+1` is `(1<<2)+1`, which is `5`, not `8`. `gofmt` formats
expressions so that spacing hints at the grouping (`x&y + 1`), and it is a reliable way to check what you meant.

[source,go]
----
package main

import "fmt"

func main() {
	x, y := 6, 3
	p, q, r := true, false, false

	// Precedence 5: * / % << >> & &^     Precedence 4: + - | ^
	fmt.Println("1+2*3     =", 1+2*3)
	fmt.Println("(1+2)*3   =", (1+2)*3)
	fmt.Println("1+2<<3    =", 1+2<<3, "  // 1 + (2<<3): << binds like *")
	fmt.Println("1<<2+1    =", 1<<2+1, "  // (1<<2) + 1")
	fmt.Println("x&y+1     =", x&y+1, "  // (x&y) + 1")
	fmt.Println("x|y == 7  =", x|y == 7, " // | is level 4, == is level 3")
	fmt.Println("x&1 == 0  =", x&1 == 0, " // & is level 5: no parentheses needed, unlike C")
	fmt.Println("-x*y      =", -x*y, "  // unary operators bind tightest")
	fmt.Println("^x&y      =", ^x&y)
	fmt.Println("p||q&&r  =", p || q && r, "  // p || (q && r): && is level 2, || is level 1")
}
----

[source,text]
----

(1+2)*3   = 9
1+2<<3    = 17   // 1 + (2<<3): << binds like *
1<<2+1    = 5   // (1<<2) + 1
x&y+1     = 3   // (x&y) + 1

x&1 == 0  = true  // & is level 5: no parentheses needed, unlike C

Source: https://go.dev/ref/spec#Operator_precedence[The Go Programming Language Specification: Operator precedence]

There is no exponent operator (use `math.Pow` for floating point and a loop or `math/big` for integers), no comma
operator, no ternary conditional (`cond ? a : b`; write an `if` statement, or in generic helper code a small function)
and no `sizeof` operator (the `unsafe.Sizeof` function covers that). The `min`, `max` and `clear` built-ins (Go 1.21)
fill some of the gaps that operators leave:

[source,go]
----
package main

import (
	"fmt"
	"math"
)

func main() {
	// min and max (Go 1.21) work on any ordered type, including strings.
	fmt.Println(min(3, 1, 2), max(2.5, 1), min("pear", "apple"))

	// If any argument is NaN the result is NaN; -0.0 is less than +0.0.
	fmt.Println(min(1.0, math.NaN()), max(math.Copysign(0, -1), 0))

	// Constant arguments give a constant result.
	const lim = min(10, 20, 5)
	var buf [lim]byte
	fmt.Println(len(buf))

	// clear (Go 1.21) empties a map or zeroes a slice's elements.
	m := map[string]int{"a": 1}
	s := []int{1, 2, 3}
	clear(m)
	clear(s[1:])
	fmt.Println(m, len(m), s)
}
----

[source,text]
----
1 2.5 apple
NaN 0
5
map[] 0 [1 0 0]
----

Source: https://go.dev/ref/spec#Min_and_max[The Go Programming Language Specification: Min and max] and https://go.dev/ref/spec#Clear[Clear]

== Order of evaluation

The specification fixes the order only partly (https://go.dev/ref/spec#Order_of_evaluation[Order of evaluation]):

* all *function calls, method calls, receive operations and binary logical operations* in an expression are evaluated in
  the usual lexical left-to-right order;
* the order between those and the evaluation of *plain variables, map indexing and other operands* is **not** specified.

So `a + f()` may read `a` before or after `f` modifies it, and `[]int{a, f()}` may be `[1 2]` or `[2 2]`. Real programs
must not depend on it; assign to temporaries when a function with side effects appears in an expression that also reads
the variable it changes.

[source,go]
----
package main

import "fmt"

func trace(name string, v int) int {
	fmt.Print(name, " ")
	return v
}

func sum(args ...int) int {
	t := 0
	for _, a := range args {
		t += a
	}
	return t
}

func main() {
	// Function calls, method calls, receive operations and binary logical
	// operations are evaluated in lexical left-to-right order.
	r := trace("a", 1) + trace("b", 2)*trace("c", 3)
	fmt.Println("=", r)

	fmt.Print("args: ")
	fmt.Println("=", sum(trace("x", 1), trace("y", 2), trace("z", 3)))

	// The order of evaluation of a plain variable against a function call is
	// NOT specified. The spec says this may print either [1 2] or [2 2].
	a := 1
	f := func() int { a++; return a }
	x := []int{a, f()}
	fmt.Println("unspecified:", x)

	// Map index order relative to calls is unspecified too, but each
	// operand is evaluated exactly once.
	m := map[string]int{}
	m["k"] += trace("rhs", 5)
	fmt.Println(m)
}
----

[source,text]
----
a b c = 7
args: x y z = 6
unspecified: [2 2]
rhs map[k:5]
----

Source: https://go.dev/ref/spec#Order_of_evaluation[The Go Programming Language Specification: Order of evaluation]

The line `unspecified: [2 2]` is what this toolchain happens to print; another compiler version is allowed to print
`[1 2]`. Arguments to a call are evaluated left to right before the call, and `defer` and `go` evaluate their
function value and arguments at the statement itself (see
xref:programming-languages/go/functions-closures-and-defer.adoc[Functions, Closures and Defer]).

== String concatenation

`pass:c[+]` on strings creates a *new* string: strings are immutable, so `pass:c[s += w]` allocates a new buffer and copies both
operands every time. A loop that builds a long string with `pass:c[+=]` is therefore quadratic in the result length, with one
allocation per iteration. Constant strings are concatenated by the compiler and cost nothing at run time.

The standard remedies are `strings.Builder` (an amortised-growth byte buffer that converts to a string without copying;
call `Grow` when the final size is known), `strings.Join` for a slice of strings, and `bytes.Buffer` or `bufio.Writer`
when the destination is an `io.Writer` anyway. `fmt.Sprintf` is convenient for a few values but slower than direct
concatenation.

[source,go]
----
package main

import (
	"fmt"
	"strings"
	"testing"
)

var words = strings.Fields(strings.Repeat("shelf ", 100))

func plus() string {
	s := ""
	for _, w := range words {
		s += w + " "
	}
	return s
}

func builder() string {
	var sb strings.Builder
	sb.Grow(len(words) * 6)
	for _, w := range words {
		sb.WriteString(w)
		sb.WriteByte(' ')
	}
	return sb.String()
}

func join() string { return strings.Join(words, " ") }

func main() {
	const greeting = "Hello, " + "shelf" // constant expression: folded at compile time
	fmt.Println(greeting, len(greeting))

	fmt.Println(plus() == builder()+"", len(plus()))
	fmt.Println("allocs with +=:      ", testing.AllocsPerRun(20, func() { _ = plus() }))
	fmt.Println("allocs with Builder: ", testing.AllocsPerRun(20, func() { _ = builder() }))
	fmt.Println("allocs with Join:    ", testing.AllocsPerRun(20, func() { _ = join() }))
}
----

[source,text]
----
Hello, shelf 12
true 600
allocs with +=:       100
allocs with Builder:  1
allocs with Join:     1
----

Source: https://pkg.go.dev/strings#Builder[strings: Builder] and https://pkg.go.dev/testing#AllocsPerRun[testing: AllocsPerRun]

The compiler can concatenate a handful of operands in one expression with a single allocation (`a + b + c` copies
once), so the quadratic cost appears in loops. Details of the string representation, ranging by rune and the cost of
conversions are in xref:programming-languages/go/strings-runes-and-utf8.adoc[Strings, Runes and UTF-8].

== No operator overloading, no implicit conversion

Operators work on the built-in types and on defined types whose underlying type supports them; you cannot define `pass:c[+]` for
your own struct, and there are no operator methods. Defined numeric types keep the operators of their underlying type
but are distinct types, so mixing them needs an explicit conversion. The standard example is
`time.Duration`, an `int64` count of nanoseconds:

[source,go]
----
package main

import (
	"fmt"
	"time"
)

func main() {
	n := 3
	fmt.Println(n * time.Second)
}
----

[source,text]
----
main.go:10:14: invalid operation: n * time.Second (mismatched types int and time.Duration)
----

[source,go]
----
package main

import (
	"fmt"
	"time"
)

func main() {
	n := 3
	// No operator overloading: Duration is an int64 and arithmetic is the
	// ordinary integer kind, so the operand types must match exactly.
	d := time.Duration(n) * time.Second
	fmt.Println(d, 2*time.Second, d+500*time.Millisecond, d/2)
	fmt.Println(d > time.Second, time.Duration(1.5*float64(time.Second)))
}
----

[source,text]
----
3s 2s 3.5s 1.5s
true 1.5s
----

Source: https://pkg.go.dev/time#Duration[time: Duration]

The program shows that `2*time.Second` compiles because `2` is an untyped constant, while `n*time.Second` with an `int`
variable does not. Compare xref:programming-languages/rust/standard-traits-and-operator-overloading.adoc[Rust's operator
traits], which allow user-defined `pass:c[+]`, and xref:programming-languages/cpp/index.adoc[C++], which allows overloading
broadly; Go chooses named methods (`Add`, `Mul`, `Equal`, `Compare`) so that every operation is visible at the call site.

Some operator misuse compiles but is almost certainly wrong. `go vet` reports it, and the checks run automatically as
part of `go test`:

[source,go]
----
package main

import "fmt"

func main() {
	var b byte = 1
	x := 3
	x = x
	fmt.Println(b<<8, x == 1 || x == 1)
	if x&1 == 0 || x&1 == 0 {
		fmt.Println("even")
	}
	var f func()
	fmt.Println(f == nil, fmt.Sprint)
}
----

[source,text]
----
main.go:8:2: self-assignment of x
main.go:9:20: redundant or: x == 1 || x == 1
main.go:10:5: redundant or: x&1 == 0 || x&1 == 0
main.go:14:2: fmt.Println arg fmt.Sprint is a func value, not called

The analyzers behind these lines are `assign` (self-assignment), `bools` (redundant or suspect boolean operands),

== Where the books are outdated

Learning Go by Bodner (chapter 2, 2021) and Learning Go Programming by Vivien (chapter 2, 2016) predate several changes
to operators and expressions:

* Both predate *signed shift counts* (Go 1.13). Code that converts counts to `uint` is no longer necessary.
* Neither covers the `min`, `max` and `clear` built-ins (Go 1.21), or `new(expr)` (Go 1.26), which replaces the
  pointer-to-literal helper functions the books recommend.
* Both predate *`any` satisfying `comparable`* (Go 1.20) and, in Vivien's case, generics altogether; the type-constraint
  operators `<` and `pass:c[+]` are expressed today through `cmp.Ordered` and the type sets of Go 1.18 and later.
* The statement that every Go type can be tested for equality is incorrect: slices, maps and functions can be compared
  only to `nil`, and structs and arrays containing them are not comparable at all. Interface comparison can additionally
  panic at run time.
