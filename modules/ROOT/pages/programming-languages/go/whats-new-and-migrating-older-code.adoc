== How "since version" works

Three mechanisms decide whether a change applies to your code, and they are easy to confuse.

[cols="1,2,2",options="header"]
|===
|Mechanism |What it controls |Example
|The toolchain (`go version`) |The compiler, linker, `go` command, runtime and standard library you run. New library functions and new tools appear with it. |`slices.Concat` exists in every toolchain from 1.22 on, whatever the module says.
|The `go` line of `go.mod` (or `//go:build go1.N` in a file) |The *language version* of each package and the minimum toolchain. A new language feature is rejected below its version, and a few behavior changes depend on it. |`min(3, 1, 2)` fails to compile with `go 1.20`; per-iteration loop variables apply only with `go 1.22` or later.
|`GODEBUG` defaults, derived from the `go` line |Run-time behavior changes that could break programs. The `go` line selects the defaults that were current for that version, and a `godebug` directive or `//go:debug` comment overrides single settings. |`httpmuxgo121=1` restores the old `ServeMux`; `randseednop=0` makes `rand.Seed` work again.
|===

The compiler enforces the language version. This is the real message for a builtin from 1.21 in a module that says
`go 1.20`:

[source,text]
----
./m.go:3:16: built-in min requires go1.21 or later (-lang was set to go1.20; check go.mod)
----

Library symbols are not checked by the compiler, but since Go 1.27 `go test` runs the `stdversion` vet analyzer by
default (`go vet` has run it since Go 1.23). With `go 1.21` in `go.mod` and a call to `slices.Concat`, which arrived in
Go 1.22, `go vet` reports:

[source,text]
----
main.go:9:16: slices.Concat requires go1.22 or later (module is go1.21)
----

The program still builds and runs on a newer toolchain; the report tells you the code would not build on the toolchain
the `go` line promises. The analyzer only reasons about modules that declare `go 1.21` or later, because earlier `go`
lines were advisory.

== Release by release

The tables list what a working programmer is most likely to meet. Each release also fixed bugs, added ports and
sharpened vet and the compiler; the linked release notes are the complete record. "GA" means generally available after
an experiment or preview.

=== Go 1.18 (2022-03-15)

[cols="1,4",options="header"]
|===
|Area |Change
|Language |Type parameters on functions and types, the predeclared `any` and `comparable`, constraint interfaces with unions and `+~T+`; a generic function can be instantiated explicitly or inferred. Several limits shipped at first (for example no type declarations inside generic functions) and were lifted later. See xref:programming-languages/go/generics.adoc[Generics].
|Tools |Native fuzzing (`go test -fuzz`); `go work` workspaces (`go.work`); `go get` stops building and installing packages, which `go install pkg@version` does; the build embeds version control information (`go version -m`); `GOAMD64` microarchitecture levels.
|Runtime |Slice capacity growth uses a threshold of 256 and a smoother formula instead of doubling to 1024; the register ABI reaches arm64 and ppc64.
|Library |`strings.Cut` and `bytes.Cut`, `net/netip`, `sync.Mutex.TryLock`, `reflect.Pointer`, `debug/buildinfo`.
|===

=== Go 1.19 (2022-08-02)

[cols="1,4",options="header"]
|===
|Area |Change
|Language |No language change. The Memory Model was revised (still the version of June 6, 2022 today): sequentially consistent atomics are defined, and the model aligns with C, C++ and Rust. See xref:programming-languages/go/memory-model-and-data-races.adoc[Memory Model and Data Races].
|Tools |`//go:build unix` constraint; doc comments gain links, lists and headings, and `gofmt` reformats them. See xref:programming-languages/go/documentation-and-doc-comments.adoc[Documentation and Doc Comments].
|Runtime |The soft memory limit `GOMEMLIMIT` (and `debug.SetMemoryLimit`); initial goroutine stack size adapts to the average; jump tables for large `switch` statements.
|Library |Typed atomics (`atomic.Int64`, `atomic.Pointer[T]` and friends), `sort` switches to pattern-defeating quicksort, `url.JoinPath`, `fmt.Append` family, `flag.TextVar`, `os/exec` refuses relative-path results (`ErrDot`).
|===

=== Go 1.20 (2023-02-01)

[cols="1,4",options="header"]
|===
|Area |Change
|Language |Conversion from a slice to an array (and to an array pointer since 1.17); `unsafe.SliceData`, `unsafe.String`, `unsafe.StringData`; an interface type that is not strictly comparable (such as `any`) now satisfies `comparable`; struct and array comparison is specified to stop at the first difference.
|Tools |Profile-guided optimization preview; coverage profiles for whole programs (`go build -cover`, `GOCOVERDIR`); the standard library is no longer shipped precompiled; `go test -skip`.
|Runtime |`math/rand` seeds its global generator randomly at start-up; `rand.Seed` is deprecated.
|Library |`errors.Join` and several `%w` verbs in one `fmt.Errorf`; `context.WithCancelCause`; `http.ResponseController`; `time.DateTime`, `DateOnly`, `TimeOnly` and `Time.Compare`; `strings.CutPrefix` and `CutSuffix`; `exec.Cmd.Cancel` and `WaitDelay`; `crypto/ecdh`; the experimental `arena` package.
|===

=== Go 1.21 (2023-08-08)

[cols="1,4",options="header"]
|===
|Area |Change
|Language |Builtins `min`, `max` and `clear`; `panic(nil)` now produces a `+*runtime.PanicNilError+` (`GODEBUG=panicnil=1` restores the old result); package initialization order is specified precisely; type inference handles generic functions passed as arguments and untyped constants better.
|Tools |The `go` line becomes a strict minimum, the `toolchain` line and `GOTOOLCHAIN` let the `go` command download the toolchain a module needs; `GODEBUG` defaults follow the `go` line; PGO GA (`default.pgo` is picked up automatically with `-pgo=auto`); the `wasip1` port and `//go:wasmimport`; Windows 10 or later required.
|Library |New packages `log/slog`, `slices`, `maps`, `cmp`, `testing/slogtest`; `sync.OnceFunc`, `OnceValue` and `OnceValues`; `context.WithoutCancel`, `AfterFunc`, `WithDeadlineCause` and `WithTimeoutCause`; `errors.ErrUnsupported`; `runtime.Pinner`; `reflect.Value.Clear`.
|===

=== Go 1.22 (2024-02-06)

[cols="1,4",options="header"]
|===
|Area |Change
|Language |Each iteration of a `for` loop has its own copy of the loop variables, for modules that say `go 1.22` or later; `for i := range 10` ranges over an integer; range-over-func is available as `GOEXPERIMENT=rangefunc` only.
|Tools |`go/version`; `go work vendor`; vet checks for `time.Since` in `defer`, `append` with a single argument, and `slog` argument mismatches; `go test -cover` reports packages without tests; vet stops reporting loop-variable captures in files that require Go 1.22.
|Runtime |A redesigned execution tracer (lower overhead, streaming, per-thread buffers); metadata layout changes cut CPU overhead 1 to 3 percent; PGO enables inlining and devirtualization improvements.
|Library |`math/rand/v2` (and a `ChaCha8` and `PCG` generator); `ServeMux` accepts methods and wildcards in patterns, with `Request.PathValue`; `http.ServeFileFS`, `FileServerFS`; `slices.Concat`, `Insert` always panics on a bad index, `Delete`/`Compact`/`Replace` zero the vacated tail; `cmp.Or`; `database/sql.Null[T]`; `reflect.TypeFor`.
|===

=== Go 1.23 (2024-08-13)

[cols="1,4",options="header"]
|===
|Area |Change
|Language |Range over function types (`func(yield func(K, V) bool)`), with the standard `iter.Seq` and `iter.Seq2` and `iter.Pull`. See xref:programming-languages/go/iterators-and-range-over-func.adoc[Iterators and Range-over-Func].
|Tools |The `godebug` directive in `go.mod` and `//go:debug` comments; Go telemetry (local by default); `go mod tidy -diff`; `go env -changed`; restrictions on `//go:linkname` pulls into the standard library; the `stdversion` vet analyzer.
|Runtime |Timers and tickers that are no longer referenced become collectable even if not stopped, and their channels are unbuffered (synchronous) in modules that say `go 1.23` or later; `GODEBUG=asynctimerchan=1` could undo it until Go 1.27 removed the setting.
|Library |`unique` (canonicalizing handles), `structs.HostLayout`, iterator forms in `slices` and `maps` (`All`, `Values`, `Collect`, `Sorted`, `Chunk`, `Keys`, `Insert`), `slices.Repeat`, `os.CopyFS`, `sync.Map.Clear`, `path/filepath.Localize`, `reflect.Value.Seq`.
|===

=== Go 1.24 (2025-02-11)

[cols="1,4",options="header"]
|===
|Area |Change
|Language |Generic type aliases (`+type Set[T comparable] = map[T]struct{}+`).
|Tools |`tool` directives in `go.mod`, `go get -tool`, `go tool` runs them, the `tool` meta-pattern; `go build -json` and structured `go test -json` build output; `GOAUTH` for private module fetches; the main module's version is stamped into binaries (`pass:c[+dirty]` for uncommitted changes); `GOCACHEPROG`; cgo annotations `#cgo noescape` and `#cgo nocallback`; vet gains `tests` and a non-constant format string check.
|Runtime |Swiss-table maps, a new internal mutex and cheaper small-object allocation (2 to 3 percent less CPU on average); `runtime.AddCleanup`.
|Library |`os.Root`; `testing.B.Loop`, `T.Context`, `T.Chdir`; `weak` pointers; `crypto/mlkem`, `crypto/hkdf`, `crypto/pbkdf2`, `crypto/sha3`; the FIPS 140-3 module; `omitzero` for `encoding/json`; `strings.Lines`, `SplitSeq`, `FieldsSeq`; `maphash.Comparable`; `rand.Text`; `//go:wasmexport` and a WASI reactor mode; the experimental `testing/synctest`.
|===

=== Go 1.25 (2025-08-12)

[cols="1,4",options="header"]
|===
|Area |Change
|Language |No change affecting programs. The notion of *core types* was removed from the spec in favor of dedicated prose for each operation.
|Tools |`ignore` directive in `go.mod`; `go doc -http`; `go version -m -json`; the `work` package pattern; vet analyzers `waitgroup` (misplaced `Add`) and `hostport` (`Sprintf("%s:%d")` addresses); `go build -asan` leak detection; module roots in repository subdirectories; the `go` command stops adding a `toolchain` line when it updates the `go` line.
|Runtime |`GOMAXPROCS` respects cgroup CPU limits and is updated at run time; the Green Tea collector as an experiment; the trace flight recorder; a nil-check bug introduced in 1.21 is fixed (programs that used a result before checking its error can now panic correctly); DWARF 5; unhandled re-panics print `[recovered, repanicked]`.
|Library |`sync.WaitGroup.Go`; `testing/synctest` GA; `encoding/json/v2` experiment; `http.CrossOriginProtection`; `T.Attr` and `T.Output`; `hash.Cloner`; `reflect.TypeAssert`; more `os.Root` methods.
|===

=== Go 1.26 (2026-02-10)

[cols="1,4",options="header"]
|===
|Area |Change
|Language |`new` takes an expression (`new(yearsSince(born))` yields a `+*int+` holding the value); a generic type may refer to itself in its own type parameter list (`+type Adder[A Adder[A]] interface{ Add(A) A }+`).
|Tools |`go fix` rewritten: it is now the home of the modernizers, shares the analysis framework with `go vet`, and supports `//go:fix inline`; `go mod init` is documented to write a lower `go` line (see <<go-mod-init>> for what go1.27.2 actually wrote); `cmd/doc` and `go tool doc` removed (use `go doc`); the pprof web UI opens on the flame graph.
|Runtime |Green Tea GC enabled by default (10 to 40 percent less GC overhead in GC-heavy programs; `GOEXPERIMENT=nogreenteagc` opt-out, which the 1.26 notes said was expected to go in 1.27); cgo calls about 30 percent cheaper; randomized heap base address on 64-bit platforms; the goroutine leak profile as an experiment.
|Library |`errors.AsType[T]`; `slog.NewMultiHandler`; `crypto/hpke`; `bytes.Buffer.Peek`; `io.ReadAll` about twice as fast with half the allocation; `ServeMux` trailing-slash redirects use status 307; `T.ArtifactDir`; reflect iterators (`Type.Fields`, `Type.Methods`, `Value.Fields`); `os/signal.NotifyContext` cancels with a cause naming the signal; `testing/cryptotest`; the experimental `simd/archsimd` and `runtime/secret`.
|===

=== Go 1.27 (2026-08-19)

[cols="1,4",options="header"]
|===
|Area |Change
|Language |Generic methods (a method declaration may declare its own type parameters; interface methods may not, and generic methods cannot implement interface methods); a struct literal key may be any valid field selector, so promoted fields can be named; function type inference applies wherever a generic function is assigned or converted to a matching function type.
|Tools |`go test` runs the `stdversion` vet check; `go test -json` output lines get an `OutputType`; `go doc pkg@version` and `go doc -ex`; new modernizers `atomictypes`, `embedlit`, `slicesbackward`, `unsafefuncs`, and `waitgroup` renamed `waitgroupgo`; `go mod tidy` merges duplicate `require` blocks into at most two for `go 1.27` modules; `gofmt` alignment fix that can change whitespace in a few files; bzr support removed; response files (`@file`) for the compile, link, asm, cgo, cover and pack tools; `go tool trace -http=:6060` listens on localhost only; vet reports wrapping a pointer to an error type with `%w`.
|Runtime |Size-specialized allocation (up to 30 percent cheaper for small objects, about 60 KB of binary growth, `GOEXPERIMENT=nosizespecializedmalloc` opt-out expected to go in 1.28); the goroutine leak profile GA (`goroutineleak`, `/debug/pprof/goroutineleak`); tracebacks include pprof goroutine labels for `go 1.27` modules; the `asynctimerchan` setting removed, so timer channels are always synchronous; macOS 13 or later required.
|Library |`encoding/json/v2` and `encoding/json/jsontext` GA with `encoding/json` reimplemented on top of v2 (opt-out `GOEXPERIMENT=nojsonv2`); `uuid`; `crypto/mldsa`; `strings.CutLast` and `bytes.CutLast`; `Rand.N` as a generic method in `math/rand/v2`; `httptest.NewTestServer` for `synctest`; `url.URL.Clone`; `synctest.Sleep`; `maphash.Hasher`; `database/sql.ConvertAssign`; Unicode 17; the experimental `simd` and `simd/archsimd`.
|===

=== Go 1.28 (upcoming)

Go 1.28 is not released. The release notes at `go.dev/doc/go1.28` are an empty stub on 2026-10-18, so nothing can be
documented from them. Planning discussions mention a `url.MustParse`, an HTTP `QUERY` method and iterator methods in

leaves support.

== A tour of the new features in one program

The program below uses one feature from each release 1.18 to 1.27 and prints a line per release. It needs a toolchain of
1.27 or later (the generic method and the `uuid` package are 1.27 features), so its `go.mod` says `go 1.27`.

[source,go]
----
package main

import (
	"errors"
	"fmt"
	"iter"
	"maps"
	"math/rand/v2"
	"slices"
	"strings"
	"sync"
	"sync/atomic"
	"uuid"
)

// Book is the running example from the shelf module.
type Book struct {
	Title string
	Pages int
}

// Set is a generic alias (1.24) for a map used as a set.
type Set[T comparable] = map[T]struct{}

// Shelf holds books.
type Shelf struct{ books []Book }

// Project is a generic method (1.27): the method declares its own type parameter.
func (s *Shelf) Project[T any](f func(Book) T) []T {
	out := make([]T, 0, len(s.books))
	for _, b := range s.books {
		out = append(out, f(b))
	}
	return out
}

// Pages is an iterator (1.23).
func (s *Shelf) Pages() iter.Seq[int] {
	return func(yield func(int) bool) {
		for _, b := range s.books {
			if !yield(b.Pages) {
				return
			}
		}
	}
}

// Map is a generic function (1.18).
func Map[T, U any](in []T, f func(T) U) []U {
	out := make([]U, 0, len(in))
	for _, v := range in {
		out = append(out, f(v))
	}
	return out
}

type notFound struct{ title string }

func (e *notFound) Error() string { return "not found: " + e.title }

func main() {
	shelf := &Shelf{books: []Book{{"Dune", 612}, {"Emma", 474}, {"Ulysses", 730}}}

	// 1.18: generics, strings.Cut
	fmt.Println("1.18", Map(shelf.books, func(b Book) int { return len(b.Title) }))
	before, after, _ := strings.Cut("978-0141439518", "-")
	fmt.Println("1.18 cut:", before, after)

	// 1.19: typed atomics
	var loans atomic.Int64
	loans.Add(2)
	fmt.Println("1.19", loans.Load())

	// 1.20: errors.Join
	err := errors.Join(errors.New("title missing"), errors.New("isbn invalid"))
	fmt.Printf("1.20 %q\n", err.Error())

	// 1.21: min, max, clear, slices, maps
	fmt.Println("1.21", min(3, 1, 2), max(2.5, 1), slices.Max([]int{4, 9, 2}))
	m := map[string]int{"a": 1}
	clear(m)
	fmt.Println("1.21 cleared:", len(m))

	// 1.22: range over int and math/rand/v2 with an explicit seed
	r := rand.New(rand.NewPCG(1, 2))
	for i := range 3 {
		fmt.Print("1.22 ", i, " ", r.IntN(10), "; ")
	}
	fmt.Println()

	// 1.23: range over func, iterator helpers
	fmt.Println("1.23", slices.Collect(shelf.Pages()), slices.Sorted(maps.Keys(map[string]int{"b": 1, "a": 2})))

	// 1.24: generic alias, strings.SplitSeq
	s := Set[string]{"Dune": {}}
	for part := range strings.SplitSeq("a,b,c", ",") {
		fmt.Print(part, " ")
	}
	fmt.Println("1.24 set size", len(s))

	// 1.25: WaitGroup.Go
	var wg sync.WaitGroup
	var total atomic.Int64
	for _, b := range shelf.books {
		wg.Go(func() { total.Add(int64(b.Pages)) })
	}
	wg.Wait()
	fmt.Println("1.25 pages:", total.Load())

	// 1.26: new(expr) and errors.AsType
	pages := new(len(shelf.books))
	var wrapped error = fmt.Errorf("lookup: %w", &notFound{"Persuasion"})
	if nf, ok := errors.AsType[*notFound](wrapped); ok {
		fmt.Println("1.26", *pages, nf.title)
	}

	// 1.27: generic method, strings.CutLast, uuid

== Migrating older code: the plan

Migrating is mostly mechanical, and the toolchain does most of it. The order below keeps every step small enough to
review and to revert.

[cols="1,3,3",options="header"]
|===
|Step |Command or action |Why this order
|1 |Commit a clean tree and run the tests with the toolchain you have now. |You need a green baseline to tell a migration problem from an old one.
|2 |Install the current toolchain (or let `GOTOOLCHAIN=auto` fetch it) and run the tests again without touching `go.mod`. |A new toolchain with an old `go` line keeps the old language rules and the old `GODEBUG` defaults, so this step isolates library and tool changes.
|3 |`+go vet ./...+` |Fix what vet reports first. The checks are cheap and `go test` runs a subset of them anyway.
|4 |Raise the `go` line (`go get go@1.27` or edit `go.mod`) and run the tests. |This turns on the language and `GODEBUG` changes for your module: per-iteration loop variables, the new `ServeMux`, timers and the rest of the table in the `GODEBUG` section.
|5 |`+go fix -diff ./...+`, review, then `+go fix ./...+`, then `gofmt -l .` and the tests again. |The modernizers rewrite old idioms without changing behavior. Run it on a clean tree and commit the result on its own.
|6 |Replace the things no tool can rewrite: third-party routers, `log` calls, the `b.N` loops, header-cast `unsafe` code, `golint` in CI. |These need judgement; the sections below show the current form of each.
|7 |Remove `godebug` entries that were only a stopgap. |Each entry is a deferral, not a fix. `go version -m` shows the settings the binary was built with.
|===

[[go-mod-init]]
=== Starting a module and the version in the `go` line

`go mod init` writes the `go` line. The Go 1.26 release notes say it defaults to a lower version so that new modules
stay usable with the supported releases: the toolchain `1.N.X` writes `go 1.(N-1).0`. What go1.27.2 wrote in a fresh
directory on 2026-10-18 was the toolchain's own version:

[source,bash]
----
$ go version
go version go1.27.2 darwin/arm64
$ mkdir shelf && cd shelf && go mod init example.com/shelf
go: creating new go.mod: module example.com/shelf
$ cat go.mod
module example.com/shelf

go 1.27.2
----

Check the line you get and set it deliberately; `go mod edit -go=1.27` or `go get go@1.27` changes it. A library that
wants to stay usable with Go 1.26 can keep `go 1.26`: the language rules and `GODEBUG` defaults of that line then apply
to the library's own packages, and it cannot use generic methods or the other 1.27 library additions.

Source: https://go.dev/doc/go1.26#go-command[Go 1.26 release notes: Go command]

Source: https://go.dev/ref/mod#go-mod-init[Go Modules Reference: go mod init]

== Habit by habit: older form and current form

=== GOPATH to modules

*Older code you may meet:* code that lives under `$GOPATH/src/<import path>` and is built by `go build` with no `go.mod`.
Go 1.11 introduced modules, Go 1.13 made the proxy and checksum database the default way to fetch them, and Go 1.16
made module mode the default. Inside a directory without `go.mod`, the real go1.27.2 result is:

[source,text]
----
$ go build .
go: go.mod file not found in current directory or any parent directory; see 'go help modules'
----

The old mode still exists as an explicit opt-out, for archaeology only. With `GO111MODULE=off` and a `GOPATH` that
holds the package under `src/`, the program builds and runs:

[source,text]
----
$ GO111MODULE=off GOPATH=$PWD/../.. go run .
built in GOPATH mode
----

The current form is a module anywhere on disk, created with `go mod init`. `GOPATH` is now only the default location of
the module cache (`$GOPATH/pkg/mod`) and of the binaries `go install` writes (`$GOPATH/bin`); on this machine
`go env GOPATH` prints `/Users/albertoirurueta/go`. See
xref:programming-languages/go/modules-and-dependency-management.adoc[Modules and Dependency Management] and
xref:programming-languages/go/workspaces-versioning-and-publishing.adoc[Workspaces, Versioning and Publishing] for
`go work`, which replaced the habit of keeping several repositories side by side under one `GOPATH` (Go 1.18).

Source: https://go.dev/blog/using-go-modules[Using Go Modules]

Source: https://go.dev/ref/mod[Go Modules Reference]

=== go get to go install

*Older code you may meet:* `go get github.com/someone/tool` to download, build and install a command. Go 1.17 deprecated
that use and Go 1.18 removed it; `go get` now only edits `go.mod`. Outside a module it fails with a message that names the
replacement:

[source,text]
----
$ go get example.com/cmd/shelf
go: go.mod file not found in current directory or any parent directory.
	'go get' is no longer supported outside a module.
	To build and install a command, use 'go install' with a version,
	like 'go install example.com/cmd@latest'
	For more information, see https://go.dev/doc/go-get-install-deprecation
	or run 'go help get' or 'go help install'.
----

The current form is `go install example.com/cmd/shelf@v1.2.3` (or `@latest`), which builds the command at that version,
ignoring any `go.mod` in the current directory, and installs it in `$GOBIN` or `$GOPATH/bin`. With `GOPROXY=off` the
lookup fails honestly:

[source,text]
----
$ go install example.com/cmd/shelf@v1.2.3
go: example.com/cmd/shelf@v1.2.3: module lookup disabled by GOPROXY=off
----

Source: https://go.dev/doc/go-get-install-deprecation[Deprecation of go get for installing executables]

=== tools.go to tool directives

*Older code you may meet:* a file named `tools.go` that blank-imports the command packages a project depends on, behind
a `//go:build tools` constraint, only so that `go.mod` records the versions. Go 1.24 added the `tool` directive: the
module records the tool itself, `go get -tool` adds it, `go tool name` runs it (and caches the executable), and the
`tool` meta-pattern means "every tool of this module", for example `go get tool` to upgrade them all or `go install tool`
to install them. The `go.mod` form, written here with `+go mod edit -tool=...+` (no network is needed to record the
directive):

[source,text]
----
module example.com/shelf

go 1.27

tool honnef.co/go/tools/cmd/staticcheck
----

Running `go tool staticcheck` then needs the module in `go.mod` (run `go get -tool honnef.co/go/tools/cmd/staticcheck@version`
with network access). Without it, go1.27.2 explains exactly what is missing:

[source,text]
----
$ go tool staticcheck -version
no required module provides package honnef.co/go/tools/cmd/staticcheck; to add it:
	go get honnef.co/go/tools/cmd/staticcheck
----

`go tool` with no arguments also lists the tools that ship with the distribution (`asm`, `cgo`, `compile` and the rest),
and since Go 1.25 fewer of them are prebuilt: the ones not needed by `go build` or `go test` are built the first time you
run them. The `tools.go` file can be deleted once its imports are `tool` directives.

Source: https://go.dev/doc/modules/managing-dependencies#tools[Managing dependencies: Tools]

Source: https://go.dev/doc/go1.24#go-command[Go 1.24 release notes: Go command]

=== interface{} to any

*Older code you may meet:* `+interface{}+` as the empty interface, in every book and tutorial before Go 1.18. `any` is a
predeclared alias for exactly that type (Go 1.18), so the two are identical and interchangeable, and `any` also reads
better in constraints (`[T any]`). The `any` modernizer of `go fix` rewrites every use, which the diff above shows for
`describe`. Where a single file must stay compilable with Go 1.17 or earlier, only the `go` line decides: the compiler
rejects `any` for packages whose language version is below 1.18.

=== io/ioutil to os and io

*Older code you may meet:* the `io/ioutil` package, deprecated in Go 1.16 when its functions moved. It is frozen, not
removed, so old code builds; the replacement is a one-to-one rename, and `go fix` performs it for the functions with a
direct equivalent (the diff above changed `TempDir`, `WriteFile` and `ReadFile`).

[cols="1,1,3",options="header"]
|===
|Older function |Current function |Notes
|`ioutil.ReadAll` |`io.ReadAll` |About twice as fast and allocating about half as much since Go 1.26
|`ioutil.ReadFile` |`os.ReadFile` |Same behavior
|`ioutil.WriteFile` |`os.WriteFile` |Same behavior
|`ioutil.ReadDir` |`os.ReadDir` |Returns `[]fs.DirEntry` (cheaper, no `Stat` per entry) instead of `[]fs.FileInfo`, sorted by file name
|`ioutil.TempFile` |`os.CreateTemp` |The pattern may contain a `+*+` that is replaced by the random part
|`ioutil.TempDir` |`os.MkdirTemp` |Same pattern rule
|`ioutil.NopCloser` |`io.NopCloser` |Same behavior
|`ioutil.Discard` |`io.Discard` |Same behavior
|===

See xref:programming-languages/go/io-files-and-the-filesystem.adoc[I/O, Files and the Filesystem] for `os.Root`
(Go 1.24), `os.CopyFS` and the `io/fs` abstractions that came with the replacements.

Source: https://pkg.go.dev/io/ioutil[io/ioutil (deprecated)]

=== rand.Seed and math/rand/v2

*Older code you may meet:* `rand.Seed(time.Now().UnixNano())` at the start of `main`, because both books and a decade of
tutorials say the global generator of `math/rand` is deterministic. It was: before Go 1.20 an unseeded program produced
the same numbers on every run. Since Go 1.20 the global generator is seeded randomly at start-up, `rand.Seed` is
deprecated, and since Go 1.24 it is a no-op for modules that say `go 1.24` or later (unless `GODEBUG=randseednop=0`).
Go 1.22 added `math/rand/v2`, with cleaner names and better generators; a reproducible sequence now comes from an
explicit source:

[cols="1,1",options="header"]
|===
|`math/rand` (older) |`math/rand/v2` (current)
|`rand.Intn(n)` |`rand.IntN(n)`
|`rand.Int63n(n)`, `rand.Int31n(n)` |`rand.Int64N(n)`, `rand.Int32N(n)`
|`rand.Int()` |`rand.Int()` (non-negative `int`, same name)
|`rand.Seed(s)` and the global generator |`rand.New(rand.NewPCG(seed1, seed2))`, or `rand.NewChaCha8(seed)` for a stronger stream
|`rand.New(rand.NewSource(s))` |`rand.New(rand.NewPCG(s, s))`
|`time.Duration(rand.Int63n(int64(d)))` |`rand.N(d)`, a generic function (and, since Go 1.27, the method `Rand.N`)
|`rand.Perm(n)`, `rand.Shuffle(n, swap)` |Same names
|===

Neither package is for secrets: `crypto/rand` is, and `rand.Text` (Go 1.24) generates a random string suitable for a
token. The reasons for the changes are in xref:programming-languages/go/collections-and-utility-packages.adoc[Collections and Utility Packages]
and xref:programming-languages/go/crypto-and-security.adoc[Crypto and Security].

Source: https://go.dev/blog/randv2[Evolving the Go Standard Library with math/rand/v2]

Source: https://pkg.go.dev/math/rand/v2[math/rand/v2]

=== // +build to //go:build

*Older code you may meet:* build constraints written as `pass:c[// +build linux darwin]` (comma means AND, space means
OR, and the line must be followed by a blank line). Go 1.17 introduced `//go:build linux || darwin` with real boolean
operators; `gofmt` adds the new line next to an old one and keeps them in sync, vet's `buildtag` analyzer checks them, and
the `plusbuild` modernizer removes the old line (Go 1.16 and earlier were the last releases that needed it). The two-pass `go fix` run above is exactly this. Go 1.19 added the `unix` constraint, which stands
for every Unix-like GOOS and shortens the common case:

[source,text]
----
//go:build unix
----

Constraints may also name a Go version (`//go:build go1.22`); vet since Go 1.24 rejects a point release such as
`go1.23.1` there. See xref:programming-languages/go/directives-code-generation-and-embedding.adoc[Directives, Code Generation and Embedding].

Source: https://pkg.go.dev/cmd/go#hdr-Build_constraints[cmd/go: Build constraints]

=== b.N loops to b.Loop

*Older code you may meet:* a benchmark body written as `pass:c[for i := 0; i < b.N; i++ { ... }]`. It is not wrong, but the
compiler may optimize away the work if the result is unused, the framework runs the function several times with growing
`b.N` (so setup runs repeatedly), and forgetting the loop silently measures nothing. Go 1.24 added `b.Loop()`: the
function runs once per `-count`, setup and cleanup outside the loop execute once, and the compiler keeps the loop body
alive. The two versions side by side (no modernizer rewrites this; it is a manual change):

[source,go]
----
package benchloop

import (
	"strings"
	"testing"
)

var sink string

func BenchmarkJoinBN(b *testing.B) {
	parts := []string{"Dune", "Emma", "Ulysses"}
	b.ReportAllocs()
	for i := 0; i < b.N; i++ {
		sink = strings.Join(parts, ", ")
	}
}

func BenchmarkJoinLoop(b *testing.B) {
	parts := []string{"Dune", "Emma", "Ulysses"}
	b.ReportAllocs()
	for b.Loop() {
		sink = strings.Join(parts, ", ")
	}
}
----

[source,text]
----
$ go test -bench . -benchtime=200000x
goos: darwin
goarch: arm64
pkg: example.com/shelf
cpu: Apple M5
BenchmarkJoinBN-10      	  200000	        53.47 ns/op	      24 B/op	       1 allocs/op
BenchmarkJoinLoop-10    	  200000	        51.86 ns/op	      24 B/op	       1 allocs/op
PASS
ok  	example.com/shelf	0.203s
----

The timings are machine-specific; the point is that the two forms agree here and that `b.Loop` is the one that stays
correct when the body gets cheap enough for the compiler to remove it. `-benchtime=Nx` (a fixed count) has existed since
Go 1.12. See xref:programming-languages/go/benchmarks-fuzzing-and-synctest.adoc[Benchmarks, Fuzzing and synctest].

Source: https://go.dev/blog/testing-b-loop[More predictable benchmarking with testing.B.Loop]

=== Loop-variable copies

*Older code you may meet:* `v := v` (or `t := t`) as the first line of a loop body, or the loop variable passed to a
goroutine as an argument, to avoid the classic bug in which every closure sees the last value. Before Go 1.22 a `for`
loop declared its variables once for the whole loop. Since Go 1.22, a module whose `go` line is 1.22 or later gets a new
copy per iteration, and the copy is redundant. The same file, built under four `go` lines, shows that the language
version of the module decides:

[source,go]
----
package main

import "fmt"

func main() {
	var show []func() int
	for i := 0; i < 3; i++ {
		show = append(show, func() int { return i })
	}
	for _, f := range show {
		fmt.Print(f(), " ")
	}
	fmt.Println()
}
----

[cols="1,2",options="header"]
|===
|`go` line in `go.mod` |Output
|`go 1.20` |`3 3 3`
|`go 1.21` |`3 3 3`
|`go 1.22` |`0 1 2`
|`go 1.27` |`0 1 2`
|===

There is no `GODEBUG` for this: the `go` line (or a `//go:build go1.22` constraint in a file) is the switch, which also
means that a library with `go 1.21` in its `go.mod` keeps the old semantics for its own packages even when an
application with `go 1.27` imports it. The `forvar` modernizer removes the redundant copies. One consequence is a new vet
warning in 1.24: a three-clause loop whose variable contains a `sync.Locker` copies the lock on every iteration. See
xref:programming-languages/go/control-flow.adoc[Control Flow] and
xref:programming-languages/go/common-mistakes-and-gotchas.adoc[Common Mistakes and Gotchas].

=== Third-party routers to ServeMux patterns

*Older code you may meet:* a router package added to a project only because the standard `ServeMux` matched fixed
paths and prefixes and ignored the request method. Since Go 1.22 patterns can name a method, a path wildcard and a
rest-of-path wildcard, and `Request.PathValue` reads the value. A method mismatch becomes a `405` automatically:

[source,go]
----
package main

import (
	"fmt"
	"net/http"
	"net/http/httptest"
)

func main() {
	mux := http.NewServeMux()
	mux.HandleFunc("GET /books/{isbn}", func(w http.ResponseWriter, r *http.Request) {
		fmt.Fprintf(w, "book %s\n", r.PathValue("isbn"))
	})
	mux.HandleFunc("GET /files/{path...}", func(w http.ResponseWriter, r *http.Request) {
		fmt.Fprintf(w, "file %s\n", r.PathValue("path"))
	})
	mux.HandleFunc("GET /{$}", func(w http.ResponseWriter, r *http.Request) {
		fmt.Fprintln(w, "home")
	})

	for _, c := range []struct{ method, target string }{
		{"GET", "/"},
		{"GET", "/books/9780141439518"},
		{"POST", "/books/9780141439518"},
		{"GET", "/files/a/b/c.txt"},
		{"GET", "/nothing"},
	} {
		rec := httptest.NewRecorder()
		mux.ServeHTTP(rec, httptest.NewRequest(c.method, c.target, nil))
		fmt.Printf("%-4s %-22s -> %d %q\n", c.method, c.target, rec.Code, rec.Body.String())
	}
}
----

[source,text]
----
GET  /                      -> 200 "home\n"
GET  /books/9780141439518   -> 200 "book 9780141439518\n"
POST /books/9780141439518   -> 405 "Method Not Allowed\n"
GET  /files/a/b/c.txt       -> 200 "file a/b/c.txt\n"
GET  /nothing               -> 404 "404 page not found\n"
----

The patterns `+{path...}+` (match the rest of the path) and `+{$}+` (match exactly the trailing slash) cover what routers
added. Conflicting patterns panic at registration, not at request time. Go 1.26 changed the trailing-slash redirect of
`ServeMux` to status 307, which keeps the method of a `POST`. A router is still a sensible choice when you need regular
expressions, route groups or generated documentation; it is no longer needed for method and parameter routing. The old
behavior is a `GODEBUG` away: with `httpmuxgo121=1` the same `+GET /books/{isbn}+` pattern in the earlier example no longer
matches as a wildcard, and the request returns `404 404 page not found`. Full coverage is on
xref:programming-languages/go/net-http-clients-and-servers.adoc[net/http Clients and Servers].

Source: https://go.dev/blog/routing-enhancements[Routing Enhancements for Go 1.22]

Source: https://pkg.go.dev/net/http#ServeMux[net/http: ServeMux]

=== log to slog

*Older code you may meet:* the `log` package with `Printf`-style messages that bake the fields into text, so a line like
`+lent isbn=... member=...+` has to be parsed back into fields by whatever collects the logs. Go 1.21 added `log/slog`, with
leveled, structured records and pluggable handlers (text, JSON, or your own), and keeps the old API working by routing it
through the same handler:

[source,go]
----
package main

import (
	"log"
	"log/slog"
	"os"
)

func main() {
	// Older style: a formatted line, with the fields baked into the message.
	old := log.New(os.Stdout, "", 0)
	old.Printf("lent isbn=%s member=%d", "9780141439518", 42)

	// Current style: a message plus typed key/value attributes.
	opts := &slog.HandlerOptions{ReplaceAttr: func(groups []string, a slog.Attr) slog.Attr {
		if a.Key == slog.TimeKey && len(groups) == 0 {
			return slog.Attr{} // drop the time so the output is stable
		}
		return a
	}}
	logger := slog.New(slog.NewTextHandler(os.Stdout, opts))
	logger.Info("lent", "isbn", "9780141439518", "member", 42)

	// Bridge: code that still calls log.Printf now flows through the slog handler.
	slog.SetDefault(logger)
	log.Printf("legacy call isbn=%s", "9780141439518")

	jsonLogger := slog.New(slog.NewJSONHandler(os.Stdout, opts))
	jsonLogger.Warn("overdue", slog.Group("loan", slog.String("isbn", "9780141439518"), slog.Int("days", 3)))
}
----

[source,text]
----
lent isbn=9780141439518 member=42
level=INFO msg=lent isbn=9780141439518 member=42
level=INFO msg="legacy call isbn=9780141439518"
{"level":"WARN","msg":"overdue","loan":{"isbn":"9780141439518","days":3}}
----

`slog.SetDefault` makes the top-level `log` functions write through the slog handler (at level `INFO`), so a codebase can
migrate package by package. Go 1.22 added a vet check for mismatched key/value arguments, and Go 1.26 added
`slog.NewMultiHandler` to fan one record out to several handlers. See
xref:programming-languages/go/structured-logging-with-slog.adoc[Structured Logging with slog].

Source: https://go.dev/blog/slog[Structured Logging with slog]

=== JSON v1 to v2

*Older code you may meet:* `encoding/json` only. In Go 1.27 the package is still there and still the default, but it is now
implemented on top of `encoding/json/v2`, and the new package and its low-level companion `encoding/json/jsontext` are
generally available (a Go 1.25 and 1.26 experiment before that; `GOEXPERIMENT=nojsonv2` selects the original
implementation and is expected to go away). The v2 defaults are stricter. This program runs the same inputs through both
packages:

[source,go]
----
package main

import (
	"encoding/json"
	jsonv2 "encoding/json/v2"
	"fmt"
)

type Book struct {
	Title   string   `json:"title"`
	Authors []string `json:"authors"`
	Pages   int      `json:"pages,omitzero"`
}

func main() {
	b := Book{Title: "Dune"}

	v1, _ := json.Marshal(b)
	v2, _ := jsonv2.Marshal(b)
	fmt.Println("v1 nil slice:", string(v1))
	fmt.Println("v2 nil slice:", string(v2))

	// A key that differs only in case: v1 matches it loosely, v2 does not.
	in := []byte(`{"TITLE":"Emma","pages":474}`)
	var a, c Book
	err1 := json.Unmarshal(in, &a)
	err2 := jsonv2.Unmarshal(in, &c)
	fmt.Printf("v1: %+v err=%v\n", a, err1)
	fmt.Printf("v2: %+v err=%v\n", c, err2)

	// Duplicate member names: v1 keeps the last, v2 reports an error.
	dup := []byte(`{"title":"A","title":"B"}`)
	var d1, d2 Book
	e1 := json.Unmarshal(dup, &d1)
	e2 := jsonv2.Unmarshal(dup, &d2)
	fmt.Printf("v1: %q err=%v\n", d1.Title, e1)
	fmt.Printf("v2: %q err=%v\n", d2.Title, e2)

	// Opting back into the old nil-slice rendering while using the v2 API.
	v2old, _ := jsonv2.Marshal(b, jsonv2.FormatNilSliceAsNull(true))
	fmt.Println("v2 + option:", string(v2old))
}
----

[source,text]
----
v1 nil slice: {"title":"Dune","authors":null}
v2 nil slice: {"title":"Dune","authors":[]}
v1: {Title:Emma Authors:[] Pages:474} err=<nil>
v2: {Title: Authors:[] Pages:474} err=<nil>
v1: "B" err=<nil>
v2: "A" err=jsontext: duplicate object member name "title"
v2 + option: {"title":"Dune","authors":null}
----

Three differences show: a nil slice marshals as `[]` in v2 and `null` in v1, member names match case-sensitively in v2
(the `TITLE` key was ignored), and duplicate names are an error. v2 also rejects invalid UTF-8. Because v1 is now built
on v2 with options that preserve its historical behavior, nothing has to change for existing code, but error message
texts may differ. Migrating gradually is supported: pass v2 options to get v1 behavior one difference at a time, then
drop them. The official migration guide lists all the differences and options. See
xref:programming-languages/go/encoding-json.adoc[encoding/json].

Source: https://go.dev/doc/jsonv2-migration[Migrating to encoding/json/v2]

Source: https://pkg.go.dev/encoding/json/v2[encoding/json/v2]

=== Header-cast unsafe code to unsafe.String, StringData, Slice and SliceData

*Older code you may meet:* converting between strings and byte slices by casting the addresses of `reflect.StringHeader`
and `reflect.SliceHeader` values (Bodner, chapter 14). Both header types are deprecated, and the technique is fragile:
the garbage collector may not see the data pointer as a pointer, which is the vet message shown above. The Go 1.17 and
1.20 functions `unsafe.Slice`, `unsafe.SliceData`, `unsafe.String` and `unsafe.StringData` express the same operations
with checked types, as `view` did in the current file above. The result of viewing a string as `[]byte` must still be
treated as read-only. The `unsafefuncs` modernizer (Go 1.27) rewrites pointer arithmetic on `unsafe.Pointer` to these
functions where it can. See xref:programming-languages/go/unsafe-and-low-level-programming.adoc[unsafe and Low-Level Programming].

Source: https://pkg.go.dev/unsafe[unsafe]

The `panic(nil)` change deserves a run, because it changes what `recover` returns. With `go 1.27`:

[source,go]
----
package main

import (
	"fmt"
	"runtime"
)

func main() {
	defer func() {
		r := recover()
		_, isNil := r.(*runtime.PanicNilError)
		fmt.Printf("recovered %T, PanicNilError: %v\n", r, isNil)
		fmt.Println("message:", r)
	}()
	panic(nil)
}
----

[source,text]
----
recovered *runtime.PanicNilError, PanicNilError: true
message: runtime error: panic called with nil argument
----

The same program in a module that says `go 1.20` prints `recovered <nil>: <nil>` (adjusting the format for the type),
because the `go` line selects the old `panicnil` default. Slice capacity growth changed in Go 1.18 and is not
controlled by any setting; appending 5000 integers one at a time to a nil slice reports these capacities on go1.27.2:

[source,text]
----
4 8 16 32 64 128 256 512 848 1280 1792 2560 3408 5120
----

The pre-1.18 rule doubled the capacity up to 1024 elements. The current rule switches to gradual growth after 256
elements, visible in the steps 512, 848, 1280, 1792, 2560 and beyond, and rounds each request to an allocator size class
(the first `append` on this toolchain already allocates room for four integers). See xref:programming-languages/go/arrays-and-slices.adoc[Arrays and Slices].

== GODEBUG settings that preserve old behavior

A change to run-time behavior that could break a working program ships with a `GODEBUG` setting, so that the new
toolchain can keep behaving the old way. The rules (Go 1.21 and later) are:

* A setting that was added in Go 1.N has, for each Go version, a default; the `go` line of the main module picks the
  defaults of that version. A `go 1.20` module on a 1.27 toolchain behaves like Go 1.20 for every setting that exists.
* A project overrides single settings in three places: a `godebug` directive in `go.mod` (Go 1.23), a `//go:debug`
  comment in a `package main` source file, or the `GODEBUG` environment variable at run time (which wins).
* `go version -m binary` prints the `DefaultGODEBUG` the binary was built with, which is how you audit a deployed program.
* Settings are kept for at least two years (four releases) and some for much longer; the policy permits removing them
  later. Since Go 1.27 the `go` command refuses a removed setting only if it is set to an old value, so programs that set
  a removed setting to its final default keep building.

A `go.mod` that keeps the pre-1.22 `ServeMux` while the rest of the module moves on:

[source,text]
----
module example.com/shelf

go 1.27

godebug httpmuxgo121=1
----

[source,text]
----
$ go build -o muxbin . && go version -m muxbin | grep -i godebug
	build	DefaultGODEBUG=httpmuxgo121=1
----

The `go 1.27` line contributes no old defaults, so only the one explicit setting is listed. The same toolchain building a
module that says `go 1.21` reports many more, because every setting added after Go 1.21 defaults to its old value for that
module:

[source,text]
----
$ go build -o app . && go version -m app | grep -o 'httplaxcontentlength=1,httpmuxgo121=1\|randseednop=0'
httplaxcontentlength=1,httpmuxgo121=1
randseednop=0
----

A `package main` can carry the same override without touching `go.mod`:

[source,text]
----
//go:debug randseednop=0
package main
----

=== Settings that were removed

A setting is removed when keeping it costs more than it is worth. The permanently removed ones are:

[cols="2,1,3",options="header"]
|===
|Setting |Removed |Note
|`x509sha1`, `tlskyber` |1.24 |Certificates signed with SHA-1 are rejected; the Kyber draft key exchange is gone (the `tlskyber` removal was documented in the 1.27 notes)
|`asynctimerchan` |1.27 |Timer and ticker channels are always synchronous and unbuffered, in every module
|`gotypesalias` |1.27 |`go/types` always produces `Alias` nodes
|`tlsunsafeekm`, `tlsrsakex`, `tls3des`, `tls10server`, `x509keypairleaf` |1.27 |Insecure TLS options that older modules could re-enable
|===

A removed setting set to its final default is accepted; set to an old value it stops the build. Here a `go 1.27`
`go.mod` carries `godebug asynctimerchan=1`:

[source,text]
----
$ go build .
go: error loading go.mod:
go.mod:5: removed GODEBUG "asynctimerchan" set to old value "1" (https://go.dev/doc/godebug#go-127)
----

The effect on code: the timer program below prints the same result in a module that says `go 1.22` and one that says
`go 1.27`, because the asynchronous channel of old modules no longer exists:

[source,go]
----
package main

import (
	"fmt"
	"time"
)

func main() {
	t := time.NewTimer(10 * time.Millisecond)
	time.Sleep(50 * time.Millisecond)
	fmt.Println("len:", len(t.C), "cap:", cap(t.C))
	fmt.Println("Stop reports:", t.Stop())
}
----

[source,text]
----
len: 0 cap: 0
Stop reports: true
----

Before Go 1.23 the channel had a buffer of one and the same program printed `len: 1 cap: 1` and `Stop reports: false`;
code that drained the channel after `Stop` or tested `len(t.C)` to see whether a timer had fired must now use the return
value of `Stop` and `Reset` instead. See xref:programming-languages/go/time-and-timers.adoc[Time and Timers].

== Where the books are outdated: every statement in one table

This reference took its structure and narrative from two books, both of which describe an older Go:

* Jon Bodner, *Learning Go: An Idiomatic Approach to Real-World Go Programming*, 1st edition (O'Reilly, March 2021),
  written for Go 1.15, with a look at the then draft generics design. A 2nd edition exists (O'Reilly, January 2024) and was
  not consulted.
* Vladimir Vivien, *Learning Go Programming* (Packt, October 2016), written for Go 1.6 and 1.7 and the GOPATH workflow.

Neither text, listings nor figures are copied from either book; the table paraphrases each outdated statement in this
page's words. Where the table says "unchanged", the book is still right. The current behavior is verified against the Go
1.27 documentation, which wins on any discrepancy. The "Version" column is the release in which the situation changed.

== How to keep up

* Read the release notes of each release before you upgrade: `go.dev/doc/go1.N` is short and has a section per area.
* Raise the `go` line one release at a time; the `stdversion` vet check and `go test` tell you if a file uses a library
  symbol your `go` line does not allow.
* Run `+go fix -diff ./...+` on every upgrade. New modernizers arrive each release (four in 1.27).
* Keep `godebug` entries in `go.mod` with a comment saying why and when to remove them.
* Check the supported releases (1.27 and 1.26 on 2026-10-18) and plan to leave a release before it falls out of support.
  Go 1.28 is expected in February 2027, and when it ships Go 1.26 stops receiving fixes.
* For topic-by-topic detail follow the links in the tables to the page of the section that covers it. The cheat sheet
  collects the current idioms on one page.
