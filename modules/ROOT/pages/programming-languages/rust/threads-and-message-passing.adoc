This page is written against Rust 1.99.0 and the 2024 edition, checked on 2026-10-06. Rust's standard library exposes
operating-system threads directly: one `std::thread` per OS thread, with no green threads or runtime. What Rust adds is
compile-time checking -- through ownership and the `Send`/`Sync` traits -- that rules out data races, which the
community calls *fearless concurrency*. This page covers starting threads and communicating by message passing; sharing
memory between threads is on xref:programming-languages/rust/shared-state-send-sync-and-atomics.adoc[Shared State,
Send/Sync & Atomics], and async tasks on xref:programming-languages/rust/async-await-and-futures.adoc[Async/Await &
Futures].

== Spawning threads

`std::thread::spawn` takes a closure, runs it on a new thread, and returns a `JoinHandle<T>`. `join()` waits for the
thread and returns `pass:c[Result<T, Box<dyn Any + Send>>]`: `Ok` with the closure's return value, or `Err` with the panic payload
if the thread panicked.

[source,rust]
----
use std::thread;
use std::time::Duration;

fn main() {
    let handle = thread::spawn(|| {
        for i in 1..=3 {
            println!("indexer: batch {i}");
            thread::sleep(Duration::from_millis(5));
        }
        42 // the thread's result
    });

    println!("main thread keeps working");
    let indexed = handle.join().expect("indexer thread panicked");
    println!("indexed {indexed} books");
}
----

Source: https://doc.rust-lang.org/book/ch16-01-threads.html[The Book: Using Threads to Run Code Simultaneously]

When `main` returns, the process exits and every other thread is killed mid-flight, so join the threads whose work must
finish. A `JoinHandle` that is dropped without joining *detaches* the thread.

=== move closures

A spawned thread may outlive the function that spawned it, so its closure must be `+'static+`: it cannot borrow local
variables. Without `move`, the compiler reports https://doc.rust-lang.org/error_codes/E0373.html[E0373] ("closure may
outlive the current function, but it borrows `titles`") and suggests `move`, which transfers ownership into the thread:

[source,rust]
----
use std::thread;

fn main() {
    let titles = vec!["Dune".to_string(), "Emma".to_string(), "Kindred".to_string()];
    let handle = thread::spawn(move || {
        titles.into_iter().map(|t| t.len()).sum::<usize>() // the thread owns `titles` now
    });
    println!("total length {}", handle.join().unwrap());
    // println!("{titles:?}"); // would not compile: `titles` was moved into the thread (E0382)
}
----

To keep using data in the spawning thread as well, clone it before the move, share it with `Arc`, or use scoped
threads.

=== thread::Builder

`thread::Builder` names a thread (shown in panic messages, debuggers and profilers) and sets its stack size; `spawn`
returns an `io::Result` instead of panicking if the OS refuses. `thread::available_parallelism()` reports how many
threads can usefully run at once:

[source,rust]
----
use std::thread;

fn main() -> std::io::Result<()> {
    let workers = thread::available_parallelism().map(|n| n.get()).unwrap_or(1);
    let handle = thread::Builder::new()
        .name("cover-thumbnailer".into())
        .stack_size(4 * 1024 * 1024)
        .spawn(move || format!("{} running with {workers} cores available", thread::current().name().unwrap_or("?")))?;
    println!("{}", handle.join().unwrap());
    Ok(())
}
----

Source: https://doc.rust-lang.org/std/thread/struct.Builder.html[std::thread::Builder]

== Scoped threads: borrowing from the parent

`std::thread::scope` (1.63) creates a scope in which threads can *borrow* local data, because the scope guarantees that
every thread spawned inside it is joined before `scope` returns. This is the easiest way to parallelise work over a
local slice:

[source,rust]
----
use std::thread;

fn main() {
    let ratings = [5, 3, 4, 4, 2, 5, 1, 5];
    let mut stats = (0u32, 0u32);

    thread::scope(|s| {
        let (left, right) = ratings.split_at(ratings.len() / 2);
        let a = s.spawn(|| left.iter().sum::<u32>());   // borrows `ratings` -- no move, no Arc
        let b = s.spawn(|| right.iter().sum::<u32>());
        stats.0 = a.join().unwrap() + b.join().unwrap();
        s.spawn(|| stats.1 = ratings.len() as u32);     // may even borrow mutably
    }); // all threads joined here

    println!("sum {} over {} ratings", stats.0, stats.1);
}
----

Source: https://doc.rust-lang.org/std/thread/fn.scope.html[std::thread::scope]

The borrow checker applies inside the scope as usual: several threads may share `&ratings`, but only one may hold
`&mut stats`. For data-parallel loops over large collections, Rayon builds on the same idea with a work-stealing pool
(see xref:programming-languages/rust/data-parallelism-with-rayon.adoc[Data Parallelism with Rayon]).

== Message passing with channels

"Do not communicate by sharing memory; share memory by communicating." A *channel* has a sending half and a receiving
half; values sent are *moved* to the receiver, so there is never shared access to them. `std::sync::mpsc` provides
*multi-producer, single-consumer* channels:

* `mpsc::channel()` returns an unbounded `(Sender<T>, Receiver<T>)`: `send` never blocks;
* `mpsc::sync_channel(n)` returns a bounded `(SyncSender<T>, Receiver<T>)`: `send` blocks when `n` messages are queued,
  which gives *backpressure* (with `n = 0`, every send waits for a matching receive -- a rendezvous).

[mermaid]
....
sequenceDiagram
    participant P1 as Importer thread 1
    participant P2 as Importer thread 2
    participant C as Channel (queue)
    participant R as Catalogue writer
    P1->>C: send(Book "Dune")
    P2->>C: send(Book "Emma")
    C-->>R: recv() returns Dune
    P1->>C: send(Book "Kindred")
    C-->>R: recv() returns Emma
    Note over P1,P2: senders dropped when importers finish
    C-->>R: recv() returns Kindred
    C-->>R: recv() returns Err: all senders gone, loop ends
....

[source,rust]
----
use std::sync::mpsc;
use std::thread;

#[derive(Debug)]
struct Book {
    title: String,
    source: &'static str,
}

fn main() {
    let (tx, rx) = mpsc::sync_channel::<Book>(16); // bounded: importers wait if the writer falls behind

    let mut importers = Vec::new();
    for (source, titles) in [("csv", vec!["Dune", "Emma"]), ("json", vec!["Kindred"])] {
        let tx = tx.clone(); // one Sender per producer
        importers.push(thread::spawn(move || {
            for t in titles {
                tx.send(Book { title: t.to_string(), source }).expect("writer hung up");
            }
        })); // this clone of tx is dropped when the thread ends
    }
    drop(tx); // drop the original, or the loop below never ends

    let writer = thread::spawn(move || {
        let mut count = 0;
        for book in rx {               // iterates until every Sender is dropped
            println!("store {} (from {})", book.title, book.source);
            count += 1;
        }
        count
    });

    for i in importers {
        i.join().unwrap();
    }
    println!("stored {} books", writer.join().unwrap());
}
----

Source: https://doc.rust-lang.org/book/ch16-02-message-passing.html[The Book: Using Message Passing to Transfer Data Between Threads]

Receiving: `recv()` blocks and returns `Err(RecvError)` once all senders are gone; `try_recv()` never blocks;
`recv_timeout(d)` waits at most `d`; iterating a `Receiver` (or `rx.iter()`) loops until disconnection. Sending returns
`Err` when the receiver has been dropped, giving the producer a chance to stop. Forgetting to drop the original `Sender`
-- as noted in the example -- is the classic reason a consumer loop never terminates.

For *multiple consumers*, a `select` over several channels, or more performance, the `crossbeam-channel` crate offers
MPMC channels; in async code use `tokio::sync::mpsc`, `broadcast` and `watch` (see
xref:programming-languages/rust/async-runtimes-and-tokio.adoc[Async Runtimes & Tokio]).

== Thread-local storage

`thread_local!` declares a `static` with one independent copy per thread, initialised lazily on first access in each
thread. Combine it with `Cell` or `RefCell` for per-thread mutable state such as caches, counters or a reusable buffer:

[source,rust]
----
use std::cell::{Cell, RefCell};
use std::thread;

thread_local! {
    static PROCESSED: Cell<u32> = const { Cell::new(0) };
    static SCRATCH: RefCell<String> = RefCell::new(String::with_capacity(256));
}

fn normalise(title: &str) -> String {
    PROCESSED.set(PROCESSED.get() + 1);
    SCRATCH.with_borrow_mut(|buf| {         // reuse this thread's buffer
        buf.clear();
        buf.extend(title.chars().filter(|c| c.is_alphanumeric()).flat_map(char::to_lowercase));
        buf.clone()
    })
}

fn main() {
    let h = thread::spawn(|| {
        normalise("Dune!");
        normalise("Emma.");
        PROCESSED.get()
    });
    normalise("Kindred");
    println!("worker processed {}, main processed {}", h.join().unwrap(), PROCESSED.get()); // 2, 1
}
----

Source: https://doc.rust-lang.org/std/macro.thread_local.html[std::thread_local]

The `+const { ... }+` initialiser avoids the lazy-initialisation check when the value is a constant. Thread-locals are
destroyed when their thread exits; in async code a task may move between threads at every `.await`, so use task-local
storage (`tokio::task_local!`) instead.

== Panics in threads

A panic unwinds and ends only the panicking thread. The parent sees it as `Err` from `join()`; if it unwraps that, the
panic propagates. Locks held by the panicking thread become *poisoned*. With `+panic = "abort"+` in the profile, a panic in
any thread aborts the whole process.

[source,rust]
----
use std::thread;

fn main() {
    let worker = thread::spawn(|| {
        let isbn = "978x";
        isbn.parse::<u64>().expect("invalid ISBN") // panics in the worker
    });
    match worker.join() {
        Ok(n) => println!("parsed {n}"),
        Err(payload) => {
            let msg = payload.downcast_ref::<String>().map(String::as_str).unwrap_or("unknown panic");
            println!("worker panicked: {msg}");
        }
    }
    println!("main continues");
}
----

Source: https://doc.rust-lang.org/std/thread/index.html#the-threading-model[std::thread: The threading model]

== Parking, sleeping and yielding

`thread::sleep(d)` blocks for at least `d`; `thread::yield_now()` hints that other threads should run; `thread::park()`
blocks the current thread until another thread calls `handle.thread().unpark()` -- a low-level building block for custom
synchronisation. Most programs should use channels, `Condvar` or `Barrier` instead.

== Compared with other languages

Java's `Thread` and executors, {cpp}'s `std::thread` and `std::jthread`, and C11's `thrd_create` (or POSIX threads) offer
the same OS threads; the difference is that Rust rejects at compile time the programs that would share non-thread-safe
data or let a thread outlive borrowed data. See xref:programming-languages/java/concurrency-basics.adoc[Java:
Concurrency Basics], xref:programming-languages/cpp/threads-and-synchronization.adoc[{cpp}: Threads &
Synchronization] and xref:programming-languages/c/threads.adoc[C: Threads].

== Common errors

|===
|Error |Cause and fix
|https://doc.rust-lang.org/error_codes/E0373.html[E0373] closure may outlive the current function |add `move`, or use

|https://doc.rust-lang.org/error_codes/E0277.html[E0277] `Rc<..>` cannot be sent between threads safely |use `Arc`;

|===
