== The 2024 edition

The 2024 edition was stabilised in Rust 1.85 (2025-02-20). New Cargo projects use it by default. Its changes, grouped as in
the Edition Guide:

=== Language

[cols="2,3,1",options="header"]
|===
|Change |What it means |Page
|RPIT lifetime capture |`impl Trait` in return position captures all in-scope lifetimes; use `+use<..>+` to capture less
|xref:programming-languages/rust/lifetimes.adoc[Lifetimes]
|`if let` temporary scope |temporaries in the `if let` condition are dropped before the `else` block (fixes lock-in-else
deadlocks) |xref:programming-languages/rust/control-flow.adoc[Control Flow]
|Tail-expression temporary scope |temporaries in a block's tail expression are dropped before its locals
|xref:programming-languages/rust/control-flow.adoc[Control Flow]
|Match ergonomics reservations |explicit `ref`/`mut`/`&` inside patterns that already bind by reference are errors
|xref:programming-languages/rust/borrowing-and-references.adoc[Borrowing & References]
|Unsafe `extern` blocks |`+unsafe extern "C" { ... }+`, with `safe`/`unsafe` items |xref:programming-languages/rust/ffi-and-c-interop.adoc[FFI & C Interop]
|Unsafe attributes |`+#[unsafe(no_mangle)]+`, `+#[unsafe(export_name)]+`, `+#[unsafe(link_section)]+`
|xref:programming-languages/rust/unsafe-rust.adoc[Unsafe Rust]
|`unsafe_op_in_unsafe_fn` warns |unsafe operations inside `unsafe fn` need their own `+unsafe {}+` block
|xref:programming-languages/rust/unsafe-rust.adoc[Unsafe Rust]
|References to `static mut` denied |`static_mut_refs` is deny-by-default; use atomics, locks or `&raw`
|xref:programming-languages/rust/variables-mutability-and-constants.adoc[Variables, Mutability & Constants]
|Never-type fallback |unconstrained `!` falls back to `!` instead of `()`, which can change inference in rare unsafe code |--
|Macro fragment specifiers |`expr` also matches `+const {}+` and `+_+`; `expr_2021` keeps the old meaning; a missing fragment
specifier is an error |xref:programming-languages/rust/macros.adoc[Macros]
|`gen` keyword |reserved for future generator blocks |xref:programming-languages/rust/iterators.adoc[Iterators]
|Reserved syntax |`+#"..."#+` guarded strings and `+##+` are reserved for future use |--
|===

[source,rust]
----
// 2024: let chains (1.88), unsafe attribute and the if-let temporary scope in one place.
use std::sync::Mutex;

#[unsafe(no_mangle)] // 2021: #[no_mangle]
pub extern "C" fn shelf_version() -> u32 {
    3
}

fn take(stock: &Mutex<Vec<&'static str>>) -> &'static str {
    if let Some(t) = stock.lock().unwrap().pop()
        && !t.is_empty()
    {
        t
    } else {
        stock.lock().unwrap().push("Dune"); // 2021: deadlock, the first guard was still alive here
        "restocked"
    }
}

fn main() {
    let stock = Mutex::new(vec![]);
    println!("{} {} v{}", take(&stock), take(&stock), shelf_version());
}
----

Source: https://doc.rust-lang.org/edition-guide/rust-2024/index.html[The Edition Guide: Rust 2024]

=== Standard library

* `Future` and `IntoFuture` are in the prelude.
* `Box<[T]>` implements `IntoIterator` by value (`boxed_slice.into_iter()` yields `T`).
* `std::env::set_var`, `std::env::remove_var` and `CommandExt::before_exec` are `unsafe`
  (see xref:programming-languages/rust/io-files-processes-and-environment.adoc[I/O, Files, Processes & Environment]).

=== Cargo

* The *MSRV-aware resolver* (`+resolver = "3"+`) is the default for 2024 packages.
* Manifests reject the old underscore key spellings (`dev_dependencies`, `build_dependencies`, `crate_types`,
  `default_features`, `proc_macro`).
* An unused `default-features = false` on an inherited workspace dependency is an error.

See xref:programming-languages/rust/cargo-and-workspaces.adoc[Cargo & Workspaces].

=== rustdoc and rustfmt

* *Combined doctests*: rustdoc compiles all doctests of a crate into one binary where possible, which is much faster; mark
  a test `standalone_crate` to opt out. Nested `include!` in doctests resolves paths relative to the including file.
* rustfmt has a *style edition* independent of the language edition (`+style_edition = "2024"+`): version sorting of
  identifiers, formatting fixes, and a different sort order for raw identifiers.

See xref:programming-languages/rust/documentation-with-rustdoc.adoc[Documentation with rustdoc] and
xref:programming-languages/rust/tooling-clippy-rustfmt-and-rust-analyzer.adoc[Tooling].

== Migrating a crate with cargo fix --edition

[source,bash]
----
rustup update stable
cargo update && cargo test                 # start green on the old edition
cargo fix --edition --all-targets --all-features   # apply the migration lints while still on 2021
# edit Cargo.toml: edition = "2024" (and in [workspace.package] for workspaces)
cargo build --all-targets && cargo test    # fix whatever the lints could not
cargo fmt                                  # reformat with the 2024 style edition
cargo clippy --all-targets -- -D warnings
----

Source: https://doc.rust-lang.org/edition-guide/editions/transitioning-an-existing-project-to-a-new-edition.html[The Edition Guide: Transitioning to a new edition]

`cargo fix --edition` is conservative: it may add `+use<..>+` bounds, rewrite `if let` into `match` to preserve old drop
order, change `expr` to `expr_2021` in macros and wrap `set_var` calls in `unsafe` blocks. Review those rewrites; most can
be simplified once you have checked that the new behaviour is what you want. Migrate one crate of a workspace at a time --
crates of different editions interoperate freely.

== Work in progress (nightly only)

Several long-running efforts are visible on nightly but not part of stable Rust:

* *Polonius*, a more precise borrow checker that accepts some programs NLL rejects (notably conditional returns of
  borrows), being integrated as a location-sensitive analysis;
* the *next-generation trait solver*, already used for coherence checking, being extended to all trait solving;
* *generators* and `gen` blocks (the keyword is reserved), *specialisation*, *const generic expressions*
  (`generic_const_exprs`), the `!` type in all positions, and *async drop*;
* *Cranelift* as a faster code-generation backend for debug builds.

A *2027 edition* has been discussed by the project but is not announced; treat any list of its contents as speculative.
The project's goals for each half-year are published at https://goals.rust-lang.org/.
