= Dictionaries and containers.Map
:description: How to store and look up data by key in MATLAB with the dictionary type introduced in R2022b, covering creation, configureDictionary, indexing, insert, lookup and remove, keys, values and entries, typing rules, cell values, value semantics, reading and writing JSON, and how the older containers.Map class differs and how to migrate from it
:keywords: MATLAB, dictionary, configureDictionary, insert, lookup, remove, isKey, keys, values, entries, numEntries, readdictionary, writedictionary, containers.Map, key-value, hash map, associative array, migration

include::partial$matlab-disclaimer.adoc[]

Written against MATLAB R2026b. The `dictionary` type needs R2022b, and the `configureDictionary`, `insert`, `lookup` and `remove` functions need R2023b; `readdictionary` and `writedictionary` need R2024b. The Octave 11.3.0 sessions below cover only the legacy `containers.Map`, because Octave has no `dictionary`. Everything about `dictionary` is checked line by line against the R2026b documentation and is labelled "not run here".

A *dictionary* stores data as key-value pairs. Every key is unique and maps to one value, and you look values up by key instead of by position. Other languages call the idea a map, a hash map, a hash table or an associative array. In MATLAB, an ordinary array is indexed by positive integers; a cell array or structure can be indexed by position or field name; a dictionary lets the key be a string, a number or almost any other value. It is the right container when the program asks "what is the value for this name?" many times, for example a sensor identifier to plate coordinates in the heatflow scenario (xref:programming-languages/matlab/index.adoc#_the_heatflow_scenario[The heatflow scenario]). The documentation page says lookups and updates take constant time, regardless of the number of entries. Cell arrays are on xref:programming-languages/matlab/cell-arrays.adoc[Cell Arrays], structures on xref:programming-languages/matlab/structures.adoc[Structures] and tables on xref:programming-languages/matlab/tables.adoc[Tables].

== Choosing a container

[cols="1,2,2",options="header"]
|===
|Need |Use |Why

|Fixed named fields, known when you write the code
|A structure (`s.name`)
|Field names are identifiers; tooling and tab completion know them.

|Many records of the same columns, to filter and summarise
|A table
|Columns have types; tables are not accepted as dictionary keys or values.

|Values looked up by a key that is only known at run time
|A `dictionary`
|Keys can be strings, numbers or other types; lookup is by key and vectorised.

|Code that must run on a release before R2022b
|`containers.Map`
|It has existed since R2008b; the documentation now recommends `dictionary` over it.
|===

== Creating a dictionary

=== From keys and values

`d = dictionary(keys,values)` creates a dictionary from two arrays of the same size (or a scalar value, which is mapped to every key). `+d = dictionary(k1,v1,...,kN,vN)+` takes the pairs as separate arguments. If a key is repeated, only the last value is kept. The result is always a 1-by-1 object, whatever the number of entries.

[source,matlab]
----
ids   = ["S1" "S2" "S3"];
temps = [21.5 22.0 19.8];
d = dictionary(ids,temps)
----

The documentation shows output of this form for a similar dictionary (MATLAB R2026b layout, adapted to these values, not run here):

[source,text]
----
d =

  dictionary (string ⟼ double) with 3 entries:

    "S1" ⟼ 21.5000
    "S2" ⟼ 22.0000
    "S3" ⟼ 19.8000
----

The header `string ⟼ double` shows the configured key and value types. Keys and values do not need to share a type, but all keys must share one type and all values must share one type, or be convertible to the configured ones. Character vectors given as keys or values are converted to string scalars.

Source: https://www.mathworks.com/help/matlab/ref/dictionary.html[MATLAB documentation: dictionary]

=== Empty and configured dictionaries

`d = dictionary` creates an *unconfigured* dictionary: it has no entries and no types. The first entry you add fixes the key type and the value type. When you want the types fixed in advance, create an empty *configured* dictionary with `configureDictionary` (R2023b):

[source,matlab]
----
positions = configureDictionary("string","cell");
temps     = configureDictionary("string","double");
----

Both calls display `dictionary (string ⟼ cell) with no entries.` and the corresponding line for `double` (not run here). Before R2023b the way to configure an empty dictionary was to pass empty arrays of the intended types, such as `dictionary(string.empty,double.empty)`. The type arguments are class names given as text; the documentation says a type must be a non-abstract class or a subclass of `matlab.mixin.Heterogeneous`, and that `"char"` is converted to `"string"`.

A configured dictionary converts compatible entries. With `temps` configured as `string` keys and `double` values, `+temps("S1") = int8(21)+` and `+temps("S2") = "22.5"+` both store doubles, and an entry that cannot be converted raises an error. An unconfigured dictionary has no types to convert to, so several functions refuse it: `isKey`, `lookup` and `entries` throw an error for an unconfigured dictionary, while `numEntries` returns 0.

Source: https://www.mathworks.com/help/matlab/ref/dictionary.configuredictionary.html[MATLAB documentation: configureDictionary]

== Looking up, adding, changing and removing

The dictionary is indexed with parentheses and a key. Every operation also works on arrays of keys, which is the vectorised form.

[source,matlab]
----
d = dictionary(["S1" "S2" "S3"],[21.5 22.0 19.8]);

d("S2")                     % look up one value
d(["S1" "S3"])              % look up several: returns [21.5 19.8]
d("S2") = 22.4;             % change an existing entry
d("S4") = 20.3;             % a new key adds an entry at the end
d(["S5" "S6"]) = [18.9 19.1];   % several at once
d("S3") = [];               % assigning [] removes the entry
----

Rules, from the documentation:

* *Order.* Entries keep the order in which they were added, and `keys`, `values` and `entries` return them in that order. Changing the value of an existing key does not move it; each new key goes to the end. (`containers.Map` is different: it returns keys sorted.)
* *Missing key.* Looking up a key that is not in the dictionary is an error, not an empty result. Test with `isKey` first or use `lookup` with a fallback (below). The wording of the error varies by release (not run here).
* *Duplicates.* If you assign several values to one key in a single statement, only the last is stored.
* *Merge.* `d(keys(d2)) = values(d2)` copies every entry of `d2` into `d`; keys that exist in both take the value from `d2`. The key and value types must be identical or convertible, and the values must support concatenation.

Source: https://www.mathworks.com/help/matlab/matlab_prog/getting-started-with-dictionaries.html[MATLAB documentation: Create and Manage Dictionaries]

=== insert, lookup and remove (R2023b)

Three functions do the same work as the indexing forms, with options that indexing lacks. Each returns the new or looked-up value instead of modifying its input in place, so reassign the result.

[cols="2,3",options="header"]
|===
|Syntax |Meaning

|`d2 = insert(d1,key,value)`
|Same as `d(key) = value`; an existing key is overwritten.

|`d2 = insert(d1,key,value,Overwrite=false)`
|Adds only the keys that are new; existing entries are left unchanged. `Overwrite=true` is the default.

|`value = lookup(d,key)`
|Same as `value = d(key)`; an error if a key is absent.

|`value = lookup(d,key,FallbackValue=fallback)`
|Returns `fallback` for each key that is absent instead of an error. The fallback is not validated unless it is needed.

|`d2 = remove(d1,key)`
|Same as `d(key) = []`; `key` can be an array.
|===

[source,matlab]
----
temps = dictionary(["S1" "S2"],[21.5 22.0]);
temps = insert(temps,["S2" "S3"],[99 19.8],Overwrite=false);   % S2 keeps 22.0
t5 = lookup(temps,["S1" "S9"],FallbackValue=NaN);             % [21.5 NaN]
temps = remove(temps,"S1");
----

Source: https://www.mathworks.com/help/matlab/ref/dictionary.insert.html[MATLAB documentation: insert], https://www.mathworks.com/help/matlab/ref/dictionary.lookup.html[lookup], https://www.mathworks.com/help/matlab/ref/dictionary.remove.html[remove]

== Inspecting a dictionary

[cols="2,3",options="header"]
|===
|Function |Result

|`numEntries(d)`
|Number of key-value pairs; 0 for an unconfigured dictionary.

|`isKey(d,key)`
|Logical array, the size of `key`; an error for an unconfigured dictionary.

|`keys(d)`
|An N-by-1 array of keys, in insertion order. `keys(d,"cell")` returns a cell array.

|`values(d)`
|An N-by-1 array of values, in the same order. When values are cells it is a cell array.

|`entries(d)`
|A table with variables `Key` and `Value`. `entries(d,"struct")` and `entries(d,"cell")` give a structure array or an N-by-2 cell array, for types that tables cannot hold.

|`types(d)`
|The key and value types.

|`isConfigured(d)`
|Whether the dictionary has types assigned.
|===

To loop over a dictionary, iterate over a row of keys. A `for` loop visits one column at a time, and `keys(d)` is a column, so transpose it; the documentation uses this form:

[source,matlab]
----
for id = keys(d)'
    fprintf("%s: %.1f\n",id,d(id));
end
----

Because the loop variable `id` is a string scalar on each pass, `d(id)` is one value. `numEntries` replaces the `Count` property of `containers.Map` and `length`, and a dictionary is an object, not an array, so `size(d)` is `1 1`.

Source: https://www.mathworks.com/help/matlab/ref/dictionary.keys.html[MATLAB documentation: keys], https://www.mathworks.com/help/matlab/ref/dictionary.entries.html[entries], https://www.mathworks.com/help/matlab/ref/dictionary.iskey.html[isKey], https://www.mathworks.com/help/matlab/ref/dictionary.numentries.html[numEntries]

== Which types fit

Keys and values can be of almost any type, with these limits from the documentation:

* All keys share one type and all values share one type (or can be converted to it).
* Tables, tall arrays and distributed arrays are not accepted as keys or values. Wrap a value in a cell to store it anyway; keys can also be wrapped in a cell if the type supports `keyHash` and `keyMatch`.
* Vectorised operations (several lookups at once) need values that can be concatenated, and are not supported for structures with different fields.
* A dictionary hashes each key to a `uint64` code (`keyHash`) and compares keys with `keyMatch`. For a custom class that compares only some of its properties, overload both so that equal keys hash equally.
* Adding to a string-typed dictionary converts a number to text: `+d("newKey") = 1+` stores `"1"`.

Source: https://www.mathworks.com/help/matlab/matlab_prog/managedatatypesindictionaries.html[MATLAB documentation: Manage Data Types in Dictionaries], https://www.mathworks.com/help/matlab/matlab_prog/dictionaries-and-custom-classes.html[Dictionaries and Custom Classes]

=== Values that are arrays, structures or objects

Values must be of one type, so a dictionary of arrays of different sizes, or of mixed types, uses `cell` as the value type. When the values are cells (R2023a), curly braces read and write the contents directly: `+d{key}+` returns the contents of the cell, a comma-separated list for an array of keys (see xref:programming-languages/matlab/comma-separated-lists.adoc[Comma-Separated Lists]), and `+d{key} = value+` stores any value. Using braces on a dictionary whose values are not cells is an error.

[source,matlab]
----
positions = configureDictionary("string","cell");
positions{"S1"} = [0.2 0.8];
positions{"S2"} = [0.5 0.5];
positions{"S3"} = [0.9 0.1];
xy = positions{"S2"}      % [0.5 0.5]
----

A dictionary can hold dictionaries, which gives a nested structure; read it with chained braces, as in `+dnest{"The Stranger"}{"author"}+` on the documentation page. Prefer a table or a structure array when the nested level is a record with fixed fields.

== Value semantics

A `dictionary` behaves as a value, like a numeric array or a string: `b = d` followed by a change to `b` does not alter `d` (not run here; the reference pages describe `insert`, `remove` and `lookup` as returning a new dictionary, which is consistent with this). It is not a handle object. This is the main behavioural difference from `containers.Map`, which is a handle class, so two variables can refer to the same map and a function can modify a map passed to it. Writing `d = insert(d,key,value)` and `d(key) = value` are the same operation.

== Saving and loading

A dictionary can be saved to a MAT file with `save("mydict","d")` and restored with `load("mydict.mat","d")`, as the documentation page shows (see xref:programming-languages/matlab/workspace-variables-and-mat-files.adoc[Workspace Variables and MAT-Files]). Since R2024b, `writedictionary` and `readdictionary` use JSON instead:

[source,matlab]
----
writedictionary(d,"sensor-temps.json")
d2 = readdictionary("sensor-temps.json")
----

`readdictionary` reads a JSON object into a dictionary: string keys, and a value type chosen from the contents. When all values are numbers the result is `string ⟼ double`; when the values mix types the value type is `cell` (a JSON `null` becomes `<missing>`, as in the documentation example). `writedictionary(d,filename,PrettyPrint=false)` writes without indentation, and `FileType="json"` forces the format when the extension is not `.json`. Numbers are written with a decimal point, so `1` is stored as `1.0`. JSON in general is on xref:programming-languages/matlab/json-xml-and-web-access.adoc[JSON, XML and Web Access].

Source: https://www.mathworks.com/help/matlab/ref/writedictionary.html[MATLAB documentation: writedictionary], https://www.mathworks.com/help/matlab/ref/readdictionary.html[readdictionary]

== The older containers.Map

`containers.Map` is a class that has existed since R2008b. The documentation marks it as superseded: "dictionary is recommended over containers.Map because it accepts more data types as keys and values and provides better performance" (reference page note, since R2022b). It remains available, so existing code keeps working. You meet it in code written before 2022 and in books.

[source,matlab]
----
coords = containers.Map({'S3','S1','S2'},{[0.2 0.8],[0.5 0.5],[0.9 0.1]});
disp(class(coords))
disp(coords.Count)
disp(keys(coords))
disp(isKey(coords,'S1'))
disp(isKey(coords,{'S1','S9'}))
p = coords('S2')
alias = coords;
alias('S4') = [0.3 0.3];
disp(coords.Count)
remove(coords,'S3');
disp(keys(coords))
try
  coords('S9')
catch err
  disp(err.message)
end
n = containers.Map('KeyType','double','ValueType','any');
n(7) = 'seven';
disp(n(7))
disp(class(n.Count))
----

Octave 11.3.0 output (MATLAB's layout of the `keys` cell array and the text of the missing-key error differ; MATLAB's own wording is not run here):

[source,text]
----
containers.Map
3
{
  [1,1] = S1
  [1,2] = S2
  [1,3] = S3
}
1
  1  0
p =

   0.9000   0.1000

4
{
  [1,1] = S1
  [1,2] = S2
  [1,3] = S4
}
containers.Map: specified key <S9> does not exist
seven
uint64
----

What the run shows, and what the reference page confirms for MATLAB:

* The keys come back *sorted* (`S1`, `S2`, `S3`) although they were given in a different order; a `dictionary` keeps insertion order.
* `isKey` accepts a cell array of keys and returns a logical array.
* `alias = coords` does not copy: adding through `alias` changed `coords.Count` from 3 to 4. This is handle behaviour.
* `Count` is a `uint64` (the reference page shows `uint64 4`), which surprises arithmetic that expects a `double`.
* Keys are character vectors or numeric scalars only: a string array is converted to character vectors and `KeyType` becomes `+'char'+`. The permitted numeric key types are `double`, `single`, `int32`, `uint32`, `int64` and `uint64`.
* The values are uniform scalars (or all character vectors) unless you pass `+'UniformValues',false+`, and `ValueType` can be `+'any'+`.
* A missing key is an error.

Source: https://www.mathworks.com/help/matlab/ref/containers.map.html[MATLAB documentation: containers.Map]

=== Migrating from containers.Map to dictionary

[cols="2,2,3",options="header"]
|===
|containers.Map |dictionary |Notes

|`+M = containers.Map(k,v)+`
|`d = dictionary(k,v)`
|`k` can be an array instead of a cell array of text; `v` an array (or a cell for non-scalar values).

|`+containers.Map('KeyType','char','ValueType','double')+`
|`configureDictionary("string","double")`
|Use `"string"` rather than `char`; `char` is converted to `string`.

|`M(key)`
|`d(key)`
|Both error on a missing key; `dictionary` also offers `lookup` with `FallbackValue`.

|`M(key) = v`
|`d(key) = v`
|Same.

|`isKey(M,key)`
|`isKey(d,key)`
|Same name and meaning.

|`remove(M,key)`
|`d(key) = []` or `d = remove(d,key)`
|`remove` on a `dictionary` returns a new dictionary; reassign it.

|`keys(M)` (cell array, sorted)
|`keys(d)` (array, insertion order)
|Add a `"cell"` argument for a cell array. Do not rely on sorted order; call `sort(keys(d))`.

|`values(M)` (cell array)
|`values(d)` (array, or cell when values are cells)
|`values(M,keySet)` has no counterpart; index with `d(keySet)`.

|`M.Count`, `length(M)`
|`numEntries(d)`
|`Count` is a `uint64` property; `numEntries` is a function.

|Handle: copies share one map
|Value: copies are independent
|Check any function that mutated a map passed to it; it must now return the dictionary.

|Heterogeneous values with `+'UniformValues',false+`
|A `cell` value type with `+d{key}+`
|Needs R2023a for the braces.
|===

== Pitfalls

* *Forgetting to reassign.* `insert(d,k,v)` and `remove(d,k)` return the result; calling them as statements does nothing to `d`. With `containers.Map` the same call mutates the map, so the habit carries over wrongly.
* *Unconfigured is not empty-typed.* `d = dictionary` has no types and `isKey(d,"a")` is an error. Use `configureDictionary` when the dictionary may be queried before it is filled.
* *Mixed key types.* All keys share one configured type; a key of another type is converted to it if possible and is an error if not. Put heterogeneous keys in cells only if their types support `keyHash` and `keyMatch`.
* *Scalar values only for arrays.* Non-scalar or heterogeneous values (a coordinate pair) need a cell value type; with a numeric value type the assignment errors or the vectorised lookup fails.
* *Order.* Do not assume sorted order, and do not assume the order of a dictionary rebuilt from JSON is the order in another program; sort explicitly where order matters.
* *Looking up a key you never added.* `d("S9")` is an error. Guard with `isKey` or use `lookup` with `FallbackValue`.
* *`char` versus `string` keys.* Character-vector keys are stored as strings; a `char` key of a different case or with trailing blanks is a different key. Normalise with `lower` and `strtrim`.

== The heatflow sensors

The thermocouples in the heatflow scenario are identified by strings in `sensors.csv`, and each one sits at a known place on the plate. A dictionary from sensor identifier to plate coordinates is the natural container (fragment, not run here; MATLAB R2026b):

[source,matlab]
----
positions = configureDictionary("string","cell");
positions{"S1"} = [0.2 0.8];
positions{"S2"} = [0.5 0.5];
positions{"S3"} = [0.9 0.1];

latest = configureDictionary("string","double");
latest("S1") = 21.5;
latest("S2") = 22.0;
latest("S3") = 19.8;

for id = keys(latest)'
    xy = positions{id};
    fprintf("%s at (%.1f, %.1f): %.1f degC\n",id,xy(1),xy(2),latest(id));
end

unknown = ~isKey(positions,"S7")      % true: warn about an unregistered sensor
----

The same data as a `containers.Map` is the code run in the Octave session above. Once the log has many rows per sensor, keep the readings in a table (see xref:programming-languages/matlab/tables.adoc[Tables]) with a categorical sensor variable (see xref:programming-languages/matlab/categorical-arrays.adoc[Categorical Arrays]), and keep the dictionary for per-sensor metadata.

== Where older books differ

Books written before 2022 introduce `containers.Map` as the only built-in key-value type (for example the chapter on "other data types" in Davis's text) and often describe structures with dynamic field names (`s.(name)`) as the substitute. Both still work. The current recommendation is `dictionary`: it takes more types as keys and values, keeps insertion order, is a value type, and has a documented vectorised syntax. A book that says a map must have character or numeric scalar keys is describing `containers.Map`. The functions `insert`, `lookup`, `remove`, `configureDictionary`, `readdictionary` and `writedictionary` appear in no book published before 2023.
