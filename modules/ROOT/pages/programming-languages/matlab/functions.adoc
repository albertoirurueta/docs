The sessions below were run in GNU Octave 11.3.0 (MATLAB code that Octave also accepts) and show Octave's output with blank lines omitted; the layout and the error texts that MATLAB prints differ, and the MATLAB wording is given only where it is stated as "not run here". The `arguments` block is only introduced here and is covered on xref:programming-languages/matlab/argument-validation.adoc[Argument Validation].

A function takes inputs, returns outputs and keeps its variables to itself. It is the unit of reuse in MATLAB: scripts (see xref:programming-languages/matlab/scripts-and-code-sections.adoc[Scripts and Code Sections]) run in an existing workspace and share its variables, functions run in their own. In the heatflow scenario every step of the simulation is a function: assemble the system, apply the boundary condition, relax the field, summarise the result.

== Function files

A function stored in its own file is the standard form. The file `plateStats.m` below summarises a plate temperature field `T`.

[source,matlab]
----
function [tmax, tmin, tmean] = plateStats(T)
% PLATESTATS  Summary statistics of a plate temperature field.
%   [tmax, tmin, tmean] = plateStats(T) returns the maximum, minimum
%   and mean of the finite entries of T.
    vals = T(isfinite(T));
    tmax = max(vals);
    if nargout > 1
        tmin = min(vals);
    end
    if nargout > 2
        tmean = mean(vals);
    end
end
----

Save it as `plateStats.m` in the current folder or in a folder on the search path (see xref:programming-languages/matlab/search-path-startup-and-files.adoc[Search Path, Startup and Files]) and call it like any built-in function.

[source,matlab]
----
T = [20 25 30; 22 NaN 35; 21 24 33];
tmax = plateStats(T)
[tmax, tmin] = plateStats(T)
[~, ~, avg] = plateStats(T)
----

Octave 11.3.0 output:

[source,text]
----
tmax = 35
tmax = 35
tmin = 20
avg = 26.250
----

Source: https://www.mathworks.com/help/matlab/matlab_prog/create-functions-in-files.html[MATLAB documentation: Create Functions in Files]

=== The definition line

The first executable line of every function is the definition line. It has these parts, in this order:

[cols="1,3",options="header"]
|===
|Part |Rule

|`function`
|The keyword, in lowercase. Required.

|Outputs
|Optional. One output needs no brackets (`function y = f(x)`); several outputs are enclosed in square brackets and separated by commas or spaces (`function [a, b, c] = f(x)`). With no outputs, omit the part or write empty brackets (`function f(x)`, `function [] = f(x)`).

|Name
|Required. The same rules as for variable names: it starts with a letter and contains letters, digits and underscores.

|Inputs
|Optional. Names in parentheses, separated by commas. With no inputs the parentheses may be omitted (`function f`).

|`arguments` blocks
|Optional. Declarative checks of class, size and validators for inputs and outputs (R2019b for inputs; `arguments (Output)` blocks since R2022b). See xref:programming-languages/matlab/argument-validation.adoc[Argument Validation].
|===

A function cannot be defined at the Command Window prompt. It lives in a file: a function file, or a script file that contains local functions (R2016b, anywhere in the script since R2024a; see xref:programming-languages/matlab/scripts-and-code-sections.adoc[Scripts and Code Sections]).

=== The file name wins

MATLAB associates the program with the *file name*, not with the name on the definition line. If `heatSum.m` starts with `function y = other(x)`, you call it with `heatSum`, and `other` is ignored. The documentation advises using the same name for the file and for the first function, and a script file cannot have the same name as a function defined in it. Because the file name is what counts, it follows the same naming rules as a variable.

The first function in a function file is the *main function*, the one visible to the command line and to other files. Functions that follow it are local functions, visible only inside the file (see xref:programming-languages/matlab/local-nested-and-private-functions.adoc[Local, Nested and Private Functions]).

=== The `end` statement

A function ends with an `end`, with the end of the file, or with the definition line of the next local function, whichever comes first. `end` is *required* when any function in the file contains a nested function, when the function is a local function in a script file, and, in a function file, when any local function in that file uses `end`. The documentation recommends it anyway for readability. Use `end` in every function and never mix the two styles in one file; the Code Analyzer (see xref:programming-languages/matlab/code-analyzer-and-code-quality.adoc[Code Analyzer and Code Quality]) reports many such problems before you run the code.

== Inputs and outputs

* Inputs are *positional*: the first value in the call goes to the first name, and so on. Trailing inputs may be left out, and a function that uses a missing one fails with an undefined-variable error when it reaches it. List required inputs first and optional ones after them.
* Outputs are assigned by *name*: the function must assign each requested output before it ends. Calling `[tmax, tmin] = plateStats(T)` requests two outputs; the function may not have assigned the third, and nothing is wrong because it was not requested.
* A function returns only what the caller asked for. Writing `plateStats(T)` with no semicolon prints the first output as `ans`; assigning nothing stores the first output in `ans` when it exists.
* Names of outputs are not special: `tmax` in the function and `tmax` in the caller are different variables that only happen to have the same name.

=== Multiple outputs

A function that returns several values lists them in brackets, and the caller receives them with the same shape of bracketed list. Requesting fewer outputs than the function defines is legal and takes the first ones. Requesting more is an error (see <<Errors raised at the call>>).

Output order is part of the interface. When a function has more outputs than most callers want, put the most used ones first, and let the function skip the expensive ones when `nargout` says they are not needed, as `plateStats` does above.

=== `nargin` and `nargout`

Inside a function, `nargin` is the number of inputs the caller passed and `nargout` is the number of outputs it requested. Both are available as plain names without calling anything. `nargin(fname)` and `nargout(fname)` with a function name or handle give the number of declared inputs or outputs of that function; a function that declares `varargin` or `varargout` reports a negative count (see xref:programming-languages/matlab/variable-number-of-arguments.adoc[Variable Number of Arguments]).

[source,matlab]
----
function r = argCount(a, b, c)
    r = [nargin nargout];
end
----

[source,matlab]
----
r = argCount(1)
r = argCount(1,2,3)
nargin("argCount"), nargout("argCount")
----

Octave 11.3.0 output:

[source,text]
----
r =
   1   1
r =
   3   1
ans = 3
ans = 1
----

Use `nargin` to supply defaults for trailing inputs, and `nargout` to avoid computing outputs nobody asked for. For optional or name-value inputs prefer an `arguments` block, which also documents the function (see xref:programming-languages/matlab/argument-validation.adoc[Argument Validation]). `narginchk` and `nargoutchk` check the counts; `nargchk` was removed.

Source: https://www.mathworks.com/help/matlab/matlab_prog/create-functions-in-files.html[MATLAB documentation: Create Functions in Files]

=== Ignoring outputs and inputs with the tilde

To ignore an output the caller does not need, put the tilde operator in its place. It works in any position and any number of times, with consecutive tildes separated by commas, and it avoids creating a variable that would only waste memory.

[source,matlab]
----
[~, ~, avg] = plateStats(T)
----

Without the tilde you can only request the first N outputs. For example `tmax = plateStats(T)` keeps just the first output and ignores the rest.

The same operator works in a *definition line* for inputs that a function must accept but does not use. The typical case is a callback, which MATLAB calls with a fixed argument list (for example `+function onSlider(src, ~)+`). The tilde makes the intent clear and keeps the unused name out of the function workspace. A definition such as `+function f(myInput, ~, ~)+` is allowed.

Source: https://www.mathworks.com/help/matlab/matlab_prog/ignore-function-outputs.html[MATLAB documentation: Ignore Function Outputs], https://www.mathworks.com/help/matlab/matlab_prog/ignore-function-inputs.html[MATLAB documentation: Ignore Inputs in Function Definitions]

== Leaving early with `return`

`return` ends the function (or script) at once and gives control back to the caller. The outputs must already have been assigned. It is useful for guard clauses at the top, so the rest of the function is not nested one level deeper.

[source,matlab]
----
function k = firstAbove(T, tol)
    k = 0;
    if isempty(T)
        return
    end
    for k = 1:numel(T)
        if T(k) > tol
            return
        end
    end
end
----

[source,matlab]
----
firstAbove([1 2 9 4], 5)
firstAbove([], 5)
firstAbove([1 2 3], 5)
----

Octave 11.3.0 output:

[source,text]
----
ans = 3
ans = 0
ans = 3
----

The last call shows a pitfall. When nothing is above the tolerance the loop finishes, and `k` keeps the last value of the loop variable (here `3`), which looks like a hit at position 3. The loop variable survives the loop, so assign an explicit "not found" value after the loop, or use `find(T > tol, 1)`, which returns an empty array when nothing matches. Details of `break`, `continue` and `return` are on xref:programming-languages/matlab/control-flow.adoc[Control Flow].

Source: https://www.mathworks.com/help/matlab/ref/return.html[MATLAB documentation: return]

== The function workspace

Each call of a function gets a fresh *function workspace*. It holds the inputs, the outputs and every variable the function creates, and it is separate from the base workspace and from the workspace of every other function, even local functions in the same file. When the function ends, the workspace is discarded; only the requested outputs survive.

* A variable of the caller is invisible to the function unless it is passed as an input, and the other way round.
* A script called from a function runs in that function's workspace; a script called from the Command Window runs in the base workspace.
* Nested functions are the exception: they share the variables of their parent function (see xref:programming-languages/matlab/local-nested-and-private-functions.adoc[Local, Nested and Private Functions]).
* Data can also be shared through `global` and `persistent` variables, which break the isolation and are covered with the other scope tools on xref:programming-languages/matlab/workspaces-scope-global-and-persistent.adoc[Workspaces, Scope, Global and Persistent].

=== Pass by value

Inputs behave as if they were *copied*: assigning to an input inside the function changes the function's copy and never the caller's variable. MATLAB avoids the real copy until the function writes to the input (copy on write), so passing a large array and only reading it costs no memory. The idiom `T = process(T)` therefore does not leave a stale `T` behind and does not copy twice.

[source,matlab]
----
function T = scaleField(T, factor)
    T = T * factor;
    tmp = 99;
end
----

[source,matlab]
----
T = [1 2 3]; tmp = 1;
S = scaleField(T, 10)
T
tmp
----

Octave 11.3.0 output:

[source,text]
----
S =
   10   20   30
T =
   1   2   3
tmp = 1
----

`T` and `tmp` in the base workspace did not change, although `scaleField` assigned both names. Handle objects (see xref:programming-languages/matlab/value-and-handle-classes.adoc[Value and Handle Classes]) are the exception: passing a handle copies the *reference*, so the function can modify the object it points to.

Source: https://www.mathworks.com/help/matlab/matlab_prog/base-and-function-workspaces.html[MATLAB documentation: Base and Function Workspaces]

== Types of functions

The documentation distinguishes these kinds of functions. Only the first is stored on its own; the others are defined next to code that uses them or without a file.

[cols="2,3,3",options="header"]
|===
|Type |Where it lives |Visible to

|Main function (function file)
|A file named after the function
|The command line and other files, through the search path

|Local function
|After the main function in a function file, or in a script file
|Only the functions in the same file. It takes precedence over functions in other files with the same name.

|Nested function
|Completely inside another function in a program file (`end` required for every function of the file)
|The parent, siblings and nested levels as in the scope rules on xref:programming-languages/matlab/local-nested-and-private-functions.adoc[Local, Nested and Private Functions]. It reads and writes the variables of its parents.

|Private function
|A file in a subfolder named `private`
|The functions and scripts in the folder immediately above `private`, and the other functions in the same `private` folder

|Anonymous function
|An expression in a variable, `@(x) expression`, without a file
|Wherever the handle is passed. See xref:programming-languages/matlab/anonymous-functions-and-function-handles.adoc[Anonymous Functions and Function Handles].

|Method of a class
|Inside a `classdef` file or an `@class` folder
|Through objects of the class. See xref:programming-languages/matlab/properties-and-methods.adoc[Properties and Methods].
|===

How MATLAB chooses among functions of the same name (variables first, then nested, local, private, class and path functions) is the subject of xref:programming-languages/matlab/function-precedence-and-name-resolution.adoc[Function Precedence and Name Resolution]. Since R2019b a name that is used as a variable anywhere in a function cannot also be called as a function in that function, which removes a class of surprising behaviour with variables created by `eval` or `load`.

Source: https://www.mathworks.com/help/matlab/matlab_prog/types-of-functions.html[MATLAB documentation: Types of Functions]

== Help text

The comment lines that follow the definition line (or, for a file, the first block of comments) are the function's help text. `help plateStats` prints them, and the Live Editor and the function hints use them. Octave 11.3.0 shows the same lines for the `plateStats` file above:

[source,text]
----
'plateStats' is a function from the file /work/plateStats.m
 PLATESTATS  Summary statistics of a plate temperature field.
   [tmax, tmin, tmean] = plateStats(T) returns the maximum, minimum
   and mean of the finite entries of T.
----

The first line is the H1 line, which `lookfor` searches, so make it a one-line summary starting with the function name. The conventions for help text, `help` on local and private functions and the Live Editor format are on xref:programming-languages/matlab/help-text-and-documenting-code.adoc[Help Text and Documenting Code]; where to read help is on xref:programming-languages/matlab/getting-help-and-documentation.adoc[Getting Help and Documentation].

Source: https://www.mathworks.com/help/matlab/matlab_prog/add-help-for-your-program.html[MATLAB documentation: Add Help for Your Program]

== Errors raised at the call

The table lists the common errors of a function call. MATLAB raises them with these identifiers; the messages and identifiers are quoted from documentation and experience and are *not run here* (the wording varies by release; Octave prints its own texts, for example `argCount: function called with too many inputs`).

[cols="2,3,3",options="header"]
|===
|Identifier |Message (MATLAB) |Cause

|`MATLAB:TooManyInputs`
|Too many input arguments.
|The call passes more inputs than the definition line has names and no `varargin`.

|`MATLAB:TooManyOutputs`
|Too many output arguments.
|The call requests more outputs than the definition declares and no `varargout`.

|`MATLAB:minrhs`
|Not enough input arguments.
|The function reads an input that the call did not pass.

|`MATLAB:unassignedOutputs`
|Output argument "out" (and maybe others) not assigned during call to "maybeValue".
|A requested output was never assigned on the path the function took.

|`MATLAB:UndefinedFunction`
|Unrecognized function or variable 'x'.
|A name is neither a variable nor a function on the path, for example a misspelled function name or a variable that was never created.
|===

The unassigned-output case depends on the path through the function:

[source,matlab]
----
function out = maybeValue(flag)
    if flag
        out = 1;
    end
end
----

[source,matlab]
----
a = maybeValue(true)
try, b = maybeValue(false), catch err, disp(err.message), end
----

Octave 11.3.0 output:

[source,text]
----
a = 1
value on right hand side of assignment is undefined
----

The first call works and the second fails because the `if` branch assigned nothing. Assign every output at the top of the function (even to `[]` or `NaN`) so that every path returns something. How to catch these errors is on xref:programming-languages/matlab/errors-warnings-and-exceptions.adoc[Errors, Warnings and Exceptions].

Source: https://www.mathworks.com/help/matlab/matlab_prog/create-functions-in-files.html[MATLAB documentation: Create Functions in Files]

== Pitfalls

* *The file name and the function name differ.* MATLAB calls the file name; the name on the definition line is ignored, and a reader looking for the function by name will not find it.
* *Forgetting to assign an output* on one path, which raises the unassigned-output error at run time. The Code Analyzer reports many of these before you run the code.
* *Using `nargin` to guess defaults for many optional inputs* produces long `if` chains. Use an `arguments` block, or name-value arguments.
* *Reading the loop variable after a loop* that found nothing (see `firstAbove` above).
* *Shadowing a function with a variable.* Assigning `max = 3` hides the `max` function in that workspace; clear the variable or rename it. Since R2019b this also applies inside a function if a name is used both as a variable and as a function.
* *Changing the current folder and losing the function.* A function file must be in the current folder or on the path (see xref:programming-languages/matlab/search-path-startup-and-files.adoc[Search Path, Startup and Files]). An unsaved edit in the Editor is not the function that MATLAB calls.
* *Expecting a function to modify its input in place.* Return the new value and assign it in the caller, unless the argument is a handle object.
* *Calling a function with the same name as a script or a variable* that comes earlier in the lookup order.
* *`i` and `j` as loop variables* hide the imaginary unit in the same function workspace.
* *Large numbers of outputs.* More than three or four outputs usually mean the function returns a structure or a table instead.

== Where older books differ

Older books define functions with the same definition line and the same `nargin`/`nargout` idioms, and those still work. Differences to be aware of:

* They cover `nargchk` for argument counts; it has been removed, use `narginchk`/`nargoutchk` or an `arguments` block (R2019b).
* They validate inputs by hand with `if` chains, `isnumeric` and `error`, or with `inputParser` and `validateattributes`; the declarative `arguments` block is the current approach.
* They put helper functions in their own files or as subfunctions at the end of a function file. Local functions in scripts (R2016b, anywhere in the script since R2024a) were not possible when the books were written.
* They use `nargin` to detect name-value pairs; the `Name=Value` call syntax (R2021a) and `arguments` blocks replace that.
