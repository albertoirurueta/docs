An `enum` gives a set of named constants a single type. It is the one part of TypeScript that is not purely a type annotation -- it emits real JavaScript at runtime. This page follows the official https://www.typescriptlang.org/docs/handbook/enums.html[Enums] handbook chapter, then shows the erasable alternative most modern codebases prefer.

== Numeric enums

By default an `enum` is numeric. The first member is `0` and each following member auto-increments, unless you set an initializer, after which auto-increment resumes from that value.

[source,ts]
----
enum Direction {
  North,        // 0
  East,         // 1
  South,        // 2
  West,         // 3
}

enum StatusCode {
  Ok = 200,
  NotFound = 404,
  Teapot,       // 405 (auto-increment continues from 404)
}

const heading: Direction = Direction.East;   // 1
----

== String enums

Every member of a string enum needs an explicit string initializer -- there is no auto-increment. String enums produce readable values at runtime, which is why they are the common choice for values that get logged or serialized.

[source,ts]
----
enum LogLevel {
  Debug = "debug",
  Info = "info",
  Warn = "warn",
  Error = "error",
}

const level = LogLevel.Warn;   // "warn"
----

== Heterogeneous enums

An enum can mix numeric and string members. The handbook notes this is rarely useful and advises against it; it is listed here only so you recognize it.

[source,ts]
----
enum Mixed {
  No = 0,
  Yes = "YES",
}
----

== Reverse mappings

Numeric enums get a *reverse mapping*: the emitted object maps names to values and values back to names. String enums do not -- only the forward direction exists.

[source,ts]
----
enum Direction {
  North,
  East,
}

Direction.North;          // 0        (forward)
Direction[0];             // "North"  (reverse, numeric only)

enum LogLevel {
  Info = "info",
}

LogLevel["info"];         // Error: no reverse mapping on string enums
----

The reverse mapping is part of the runtime object the compiler generates, covered next.

== enum is not erasable

Everything else in the type layer -- annotations, `interface`, `type`, generics -- is *erased* during compilation, leaving no trace in the output. `enum` is the exception: it compiles to a live JavaScript object.

[source,ts]
----
enum Direction {
  North,
  East,
}
----

The emitted JavaScript builds and populates that object, including the reverse-mapping entries:

[source,js]
----
"use strict";
var Direction;
(function (Direction) {
  Direction[Direction["North"] = 0] = "North";
  Direction[Direction["East"] = 1] = "East";
})(Direction || (Direction = {}));
----

A string enum emits the same wrapper without the reverse assignments:

[source,js]
----
"use strict";
var LogLevel;
(function (LogLevel) {
  LogLevel["Info"] = "info";
  LogLevel["Warn"] = "warn";
})(LogLevel || (LogLevel = {}));
----

Because this construct generates code, it interacts with single-file transpilation. See xref:programming-languages/typescript/javascript-interop.adoc[] for more on what does and does not survive compilation.

== const enum, and why it is discouraged

A `const enum` asks the compiler to *inline* each member's value at every use site and emit no object at all.

[source,ts]
----
const enum Size {
  Small = 1,
  Large = 2,
}

const box = Size.Large;
// emitted JS: const box = 2 /* Size.Large */;
----

That sounds ideal, but inlining requires the compiler to see the enum declaration while compiling every file that uses it -- something file-by-file transpilers cannot guarantee:

* Under `isolatedModules` (required by esbuild, swc, Babel, and Vite, which compile each file in isolation), a `const enum` imported from another module cannot be inlined, so it either breaks or forces a fallback.
* `--erasableSyntaxOnly` (TypeScript 5.8+) rejects `const enum` -- and every plain `enum` -- outright, because the flag bans any construct that is not pure type syntax.
* Bundlers that compile file-by-file may leave dangling references to an object that was never emitted.

The https://www.typescriptlang.org/docs/handbook/enums.html#const-enums[const enums] section of the handbook spells out these pitfalls. For library code the guidance is: do not ship `const enum` in your public types. `preserveConstEnums` keeps the object around for debuggers but gives up the inlining benefit. The tsconfig flags involved are described on xref:programming-languages/typescript/tsconfig-and-compiler-options.adoc[].

== How the checker treats an enum

An enum declares *both* a value (the runtime object) and a type (the union of its members), which is why it can
appear in value position (`Direction.East`) and type position (`d: Direction`). Since TypeScript 5.0 every enum
whose members are literal values is a *union enum*: each member is its own type, and the enum type is their union.
That has three visible effects, shown here against the `Direction` and `LogLevel` enums from the previous sections:

[source,typescript]
----
enum Direction { North, East, South, West }
enum LogLevel { Debug = "debug", Info = "info" }

let d: Direction = Direction.East;
d = 2;                         // ok: 2 is a member's value
d = 42;                        // error: no member has the value 42
d = "north";                   // error
let l: LogLevel = LogLevel.Info;
l = "info";                    // error: a string enum is nominal
const s: string = l;           // ok: a string enum widens to string

function f(x: Direction.North | Direction.East) {}
f(Direction.South);            // error: members are types

type Names = keyof typeof Direction;   // "North" | "East" | "South" | "West"
const n: Names = "Up";                 // error

enum Other { A }
d = Other.A;                           // error: two enums are never interchangeable
----

[source,console]
----
en2.ts(6,1): error TS2322: Type '42' is not assignable to type 'Direction'.
en2.ts(7,1): error TS2322: Type '"north"' is not assignable to type 'Direction'.
en2.ts(9,1): error TS2322: Type '"info"' is not assignable to type 'LogLevel'.
en2.ts(12,3): error TS2345: Argument of type 'Direction.South' is not assignable to parameter of type 'Direction.North | Direction.East'.
en2.ts(14,7): error TS2322: Type '"Up"' is not assignable to type '"North" | "East" | "South" | "West"'.
en2.ts(16,1): error TS2322: Type 'Other' is not assignable to type 'Direction'.
----

Note `d = 2` is accepted, a hole that remains for numeric enums: any number that equals a member's value is
assignable, so a numeric enum is only half nominal. String enums have no such hole, which is the best argument for
preferring them when you do use an enum.

[mermaid]
....
flowchart LR
    DECL["enum Direction { North, East }"] --> V["value: a runtime object<br/>{ 0: 'North', 1: 'East',<br/>North: 0, East: 1 }"]
    DECL --> T["type: union<br/>Direction.North | Direction.East"]
    V -->|"Direction.East"| EXPR["expression of type Direction.East"]
    T -->|"d: Direction"| ANN["annotation"]
    EXPR -->|"assignable"| ANN
....

=== Exhaustiveness works with enums

Because the enum type is a union, `switch` narrows it and the exhaustiveness technique from
xref:programming-languages/typescript/unions-and-narrowing.adoc[Unions and Narrowing] applies. Leaving out a member is
detected by the return-type check:

[source,typescript]
----
function label(x: Direction): string {
  switch (x) {
    case Direction.North: return "N";
    case Direction.East: return "E";
  }
}
----

[source,console]
----
en2.ts(22,31): error TS2366: Function lacks ending return statement and return type does not include 'undefined'.
----

Adding the `South` and `West` cases removes the error, and so does adding a member later: the function stops
compiling until the new case is handled.

== The reverse-mapping gotcha, with real output

A numeric enum's runtime object holds both directions, so anything that enumerates it sees twice as many entries
as you declared. This surprises every newcomer who writes `Object.values(Direction)`:

[source,typescript]
----
enum Direction { North, East, South, West }
console.log(Object.values(Direction));
console.log(Object.keys(Direction));
console.log(Direction[1], Direction[Direction.West]);

const DirectionC = { North: "north", East: "east" } as const;
console.log(Object.values(DirectionC));
----

[source,console]
----
[ 'North', 'East', 'South', 'West', 0, 1, 2, 3 ]
[ '0', '1', '2', '3', 'North', 'East', 'South', 'West' ]
East West
[ 'north', 'east' ]
----

(Node prints the arrays in columns when they are long; the contents are as above.) To list only the names of a
numeric enum you must filter out the numeric keys. The `as const` object has no such problem, which is the
practical reason that the pattern in the next sections is easier to iterate.

== Emitted code and the flags that change it

The same two-line source file can be compiled in three ways, and the emitted code shows what each flag really does:

[source,typescript]
----
const enum Size { Small = 1, Large = 2 }
export const box = Size.Large;
----

[cols="2,4",options="header"]
|===
|Compiler flags |Emitted `en3.js`

|default
|`+export const box = 2 /* Size.Large */;+` -- the enum object is gone, the value is inlined

|`--preserveConstEnums`
|The same line, preceded by the full `pass:c[var Size; (function (Size) { ... })(Size \|\| (Size = {}));]` object, kept for
debugging and for code that reads the enum at run time

|`--erasableSyntaxOnly`
|No emit: the compiler reports `+error TS1294: This syntax is not allowed when 'erasableSyntaxOnly' is enabled.+` on
every `enum` declaration, plain or `const`
|===

So a project that must run under Node's type stripping, or under any tool that only deletes types, cannot use
enums at all, and the string-literal-union pattern below is not just a style preference.

== Choosing between an enum and the literal alternative

[mermaid]
....
flowchart TD
    A["A fixed set of named values"] --> B{"Must run under type stripping<br/>or erasableSyntaxOnly?"}
    B -->|yes| LIT["as const object + derived union"]
    B -->|no| C{"Do callers need to be forced<br/>through the named constant?"}
    C -->|yes| SE["string enum (never const enum)"]
    C -->|no| D{"Will the values be iterated,<br/>serialised or sent over a wire?"}
    D -->|yes| LIT
    D -->|no| E["either; prefer the literal union for simplicity"]
....

Whichever you choose, keep the values themselves stable and meaningful. A string whose text is the wire format
(`"debug"`, `"info"`) can be logged, stored and read back; a numeric enum value such as `2` means nothing outside
the program and changes meaning if someone reorders the members.

== The alternative: string-literal union plus an as const object

The common replacement is a union of string literals for the *type* and an `as const` object for the *values*. Neither emits anything the compiler would not have emitted for a plain object, so both are fully erasable-friendly.

[source,ts]
----
export const Direction = {
  North: "north",
  East: "east",
  South: "south",
  West: "west",
} as const;

// Derive the union from the object -- no repetition:
export type Direction = (typeof Direction)[keyof typeof Direction];
// "north" | "east" | "south" | "west"

function move(d: Direction) { /* ... */ }
move(Direction.North);   // ok
move("north");            // ok -- plain strings assign, unlike an enum
move("up");               // Error: not assignable to Direction
----

The `(typeof Direction)[keyof typeof Direction]` idiom reads outward: `typeof Direction` is the object's type, `keyof typeof Direction` is `+"North" | "East" | ...+`, and indexing the first by the second yields the union of the *value* types. Declaring a `const` and a `type` with the same name is allowed -- they live in different namespaces and merge into one importable symbol.

Iteration and a reverse lookup are one line each:

[source,ts]
----
for (const value of Object.values(Direction)) {
  console.log(value);            // "north", "east", ...
}

const nameByValue = Object.fromEntries(
  Object.entries(Direction).map(([k, v]) => [v, k]),
) as Record<Direction, string>;
nameByValue.north;              // "North"
----

=== Trade-offs

[cols="1,3"]
|===
| Concern | enum vs. `as const` object

| Erasability
| `enum` emits a runtime object and is banned by `--erasableSyntaxOnly`; the `as const` object is an ordinary object literal.

| Tree-shaking
| The `enum` IIFE wrapper is hard for bundlers to drop; a plain `const` object with unused keys shakes out cleanly.

| Iteration
| Numeric `enum` needs a filter to skip reverse-mapping keys; `Object.values(Obj)` on the `as const` object is direct.

| Reverse lookup
| Free on numeric `enum`, absent on string `enum`; a one-line `Object.fromEntries` on the object.

| Nominal-ness
| `enum` members are nominal -- a bare `"north"` is *not* a `Direction`. The union accepts any matching string literal, which is more permissive.

| Ergonomics
| `enum` is a single declaration; the object pattern needs the object plus the `+typeof ... [keyof typeof ...]+` line.
|===

If you need the nominal guarantee -- callers must go through the named constant and cannot pass a raw string -- an `enum` (string form, never `const`) still buys you that. Otherwise the union pattern is lighter and plays well with every build tool. Narrowing a string-literal union with `switch` and exhaustiveness checks is covered on xref:programming-languages/typescript/unions-and-narrowing.adoc[], and the broader question of when to reach for each modeling tool is on xref:programming-languages/typescript/type-design-and-best-practices.adoc[].
