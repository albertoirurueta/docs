A generic is a type with holes in it. You name the holes as *type parameters* and TypeScript fills them in
-- usually by inference at the call site -- so one definition serves every element type. The official
https://www.typescriptlang.org/docs/handbook/2/generics.html[Generics] handbook chapter is the companion to
this page; what follows is the working summary.

== Where type parameters are declared

A type parameter list `<T>` can be attached to a function, an interface, a `class`, or a `type` alias. It is
in scope for the rest of that declaration.

[source,ts]
----
// Generic function -- T is bound when the function is called.
function first<T>(items: readonly T[]): T | undefined {
  return items[0];
}
const n = first([1, 2, 3]);        // T inferred as number  -> number | undefined
const s = first(["a", "b"]);       // T inferred as string  -> string | undefined

// Generic interface -- T is bound when you write out the type.
interface Box<T> {
  value: T;
}
const bn: Box<number> = { value: 1 };

// Generic type alias.
type Pair<A, B> = { left: A; right: B };
const p: Pair<string, number> = { left: "id", right: 42 };

// Generic class -- T is bound at construction.
class Stack<T> {
  #items: T[] = [];
  push(item: T): void { this.#items.push(item); }
  pop(): T | undefined { return this.#items.pop(); }
}
const st = new Stack<string>();     // or: new Stack() and let T be inferred from first push
----

For a generic *function*, the type parameter is *bound at call time*: TypeScript matches the arguments you
pass against the parameter types and solves for `T`. For a generic *interface*, *alias*, or *class*, it is
bound when you name the type (`Box<number>`) or when a constructor call gives enough to infer it. Methods
can carry their *own* type parameters, separate from the container's.

See xref:programming-languages/typescript/functions.adoc[Functions] for call signatures and overloads, and
xref:programming-languages/typescript/classes.adoc[Classes] for generic classes in depth.

== Constraints

`<T extends Constraint>` restricts what may be substituted for `T`, and inside the body `T` is known to have
at least the constraint's members.

[source,ts]
----
interface HasLength {
  length: number;
}

function longest<T extends HasLength>(a: T, b: T): T {
  return a.length >= b.length ? a : b;
}

longest([1, 2], [1, 2, 3]);        // ok -- arrays have length
longest("ab", "abc");              // ok -- strings have length
// longest(10, 20);                // Error: number has no 'length'
----

The return type is `T`, not `HasLength`, so the caller keeps the precise type it passed in.

== keyof plus a constrained parameter

Pairing `keyof` with a second, constrained type parameter is the canonical typed property accessor: `K`
ranges only over the keys of `T`, and the result is the exact property type.

[source,ts]
----
function getProp<T, K extends keyof T>(obj: T, key: K): T[K] {
  return obj[key];
}

const user = { id: 1, name: "Ada", active: true };
const id = getProp(user, "id");        // number
const name = getProp(user, "name");    // string
// getProp(user, "email");             // Error: "email" is not a key of user
----

`keyof`, indexed access `T[K]`, and mapped types are covered in
xref:programming-languages/typescript/type-manipulation.adoc[Type Manipulation].

== Defaults and multiple type parameters

A type parameter may have a default, and a later parameter's default or constraint can refer to an earlier
one.

[source,ts]
----
interface ApiResult<TData = unknown, TError = Error> {
  data?: TData;
  error?: TError;
}

const r1: ApiResult = {};                          // TData = unknown, TError = Error
const r2: ApiResult<string> = { data: "ok" };      // TError still defaults to Error

// A default that depends on an earlier parameter:
type Dictionary<V, K extends string | number = string> = Record<K, V>;
const scores: Dictionary<number> = { alice: 10 };  // K defaults to string
----

Defaults apply only where TypeScript cannot otherwise infer the argument; an inferred type always wins over
the default.

== Generics as functions between types

Read a generic as a function whose inputs and output are *types*: `Array<T>` maps the type `T` to the type
an array of `T`; `Pick<T, K>` maps a type and a key union to a narrowed object type. This is why the utility
types in xref:programming-languages/typescript/utility-types.adoc[Utility Types] are all generic -- each is a small
type-level function you apply with `+<...>+`.

[source,ts]
----
type Nullable<T> = T | null;                 // T          -> T | null
type Unwrap<T> = T extends Promise<infer U> ? U : T;  // Promise<X> -> X, else T

type A = Nullable<number>;                    // number | null
type B = Unwrap<Promise<string>>;             // string
type C = Unwrap<boolean>;                     // boolean
----

== The golden rule: a type parameter must relate two positions

A type parameter earns its place only if it appears *at least twice* -- linking an input to another input,
or an input to the output. A parameter used once is not doing any work and should be replaced by the type it
stands for (often `unknown` or an explicit union).

[source,ts]
----
// Unnecessary: P appears once. This is just (x: unknown) => void with extra noise,
// and the annotation gives callers a false sense of type safety.
function logOnce<P>(x: P): void {
  console.log(x);
}

// Better:
function logPlain(x: unknown): void {
  console.log(x);
}

// Legitimate: T ties the argument to the return value.
function identity<T>(x: T): T {
  return x;
}

// Legitimate: T ties two arguments together, K ties the key to the result.
function pluck<T, K extends keyof T>(items: readonly T[], key: K): T[K][] {
  return items.map((item) => item[key]);
}
----

A related smell is a type parameter that only ever appears in the return position with nothing to infer
from -- that is an unsafe cast in disguise (`function make<T>(): T`), and the caller can pick any `T`.

=== Naming conventions

Single uppercase letters are the norm: `T` for a lone parameter, `T`/`U`/`V` for successive ones, `K` for a
key type, `V` for a value type, `E` for an element, `R` for a return type. When a generic has several
parameters with distinct roles, prefer descriptive `PascalCase` names with a `T` prefix (`TData`,
`TError`, `TContext`) so signatures stay readable.

== Inference and how to guide it

TypeScript infers type arguments from the values you pass. You can override that by writing the type
arguments explicitly, or shape the inference by *how* a parameter is typed.

[source,ts]
----
function wrap<T>(value: T): { value: T } {
  return { value };
}

wrap("hello");            // T inferred as string
wrap<"hello">("hello");   // T pinned to the literal type "hello"

// Guide inference toward a literal-preserving shape with a constraint:
function keys<T extends Record<string, unknown>>(o: T): (keyof T)[] {
  return Object.keys(o) as (keyof T)[];
}
keys({ a: 1, b: 2 });    // ("a" | "b")[]
----

Because plain object and array literals widen (`"hello"` becomes `string`), inference often loses the
literal types you wanted.

=== const type parameters

Marking a type parameter `const` makes TypeScript infer the *most specific* (as-if `as const`) type for
arguments matched to it -- tuples stay tuples, string literals stay literals -- without the caller writing
`as const`. Added in TypeScript 5.0; see
https://www.typescriptlang.org/docs/handbook/release-notes/typescript-5-0.html#const-type-parameters[the
5.0 release notes].

[source,ts]
----
function route<const T extends readonly string[]>(segments: T): T {
  return segments;
}

const r = route(["users", "profile"]);
//    ^? const r: readonly ["users", "profile"]   -- not string[]
----

=== NoInfer<T>

`NoInfer<T>` (TypeScript 5.4) marks a spot as *not* an inference source, so `T` is solved from the other
positions only. Use it to make one argument follow another instead of widening the parameter.

[source,ts]
----
function paint<T extends string>(palette: readonly T[], selected: NoInfer<T>): T {
  return selected;
}

paint(["red", "green", "blue"], "green");   // ok
// paint(["red", "green", "blue"], "purple");
//   Error: "purple" is not assignable to "red" | "green" | "blue"
//   Without NoInfer, T would widen to include "purple" and the mistake would compile.
----

See https://www.typescriptlang.org/docs/handbook/utility-types.html#noinfertype[`NoInfer<T>`] in the
utility types reference, and xref:programming-languages/typescript/utility-types.adoc[Utility Types].

== Promise<T>

`Promise<T>` is the generic that types an eventual value: `T` is what the promise resolves to. A rejection
carries no type -- it is always `any`/`unknown` at the `catch`.

[source,ts]
----
function fetchUser(id: number): Promise<{ id: number; name: string }> {
  return fetch(`/api/users/${id}`).then((res) => res.json());
}

fetchUser(1).then((user) => {
  user.name;   // string -- T flows through .then
});
----

An `async` function always returns a `Promise`; you annotate the *inner* type and TypeScript wraps it
(`async function f(): Promise<number>` -- the body ``return``s a `number`). Awaiting a `Promise<T>` yields
`T`. That mechanism, plus `Awaited<T>`, error typing, and async iterators, lives on
xref:programming-languages/typescript/async-and-iterators.adoc[Async and Iterators].

== How inference solves for `T`

When you call a generic function without writing the type arguments, the checker collects *candidates* for each type
parameter from every argument, picks one, and then checks the arguments against the result. Seeing that procedure
explains most surprises: why `pair(1, "a")` fails, why an argument can fix a wide `T`, and why a constraint changes
what is inferred.

[mermaid]
....
flowchart TD
    CALL["call: pair(1, 'a')"] --> CAND["collect candidates for T<br/>from each argument: number, string"]
    CAND --> ONE{"one best common<br/>supertype among them?"}
    ONE -->|"yes"| PICK["T = that type"]
    ONE -->|"no"| FIRST["T = first candidate (number)"]
    PICK --> CON{"satisfies the constraint<br/>(extends ...)?"}
    FIRST --> CON
    CON -->|"no"| FALL["T = the constraint itself"]
    CON -->|"yes"| CHECK["check every argument against<br/>the instantiated signature"]
    FALL --> CHECK
    CHECK -->|"mismatch"| ERR["error on the argument that disagrees"]
    CHECK -->|"ok"| RET["result type uses T"]
....

[source,typescript]
----
function pair<T>(a: T, b: T): [T, T] { return [a, b]; }

const p1 = pair(1, 2);                       // [number, number]
const p2 = pair(1, "a");                     // error
const p3 = pair<string | number>(1, "a");    // ok: you state T instead of inferring it
----

[source,console]
----
ge.ts(3,20): error TS2345: Argument of type 'string' is not assignable to parameter of type 'number'.
----

With two unrelated candidates the checker settles on the first (`number`) and blames the second argument. Writing the
argument explicitly, as in `p3`, is the fix when the union is what you meant. Notice that `p1` is `[number, number]`
and not `[1, 2]`: unless a constraint or `const` type parameter asks for it, literals widen.

== A constraint is both a restriction and a source of members

The earlier `keyof` pairing shows both roles of a constraint. `K extends keyof T` rejects a key that does not exist,
and tells the checker that `T[K]` is a valid lookup:

[source,typescript]
----
function pick<T, K extends keyof T>(obj: T, key: K): T[K] { return obj[key]; }
const v = pick({ id: 1, name: "a" }, "name");    // string
const bad = pick({ id: 1, name: "a" }, "nam");   // error
const nn: number = v;                              // error: v is string
----

[source,console]
----
ge.ts(8,40): error TS2345: Argument of type '"nam"' is not assignable to parameter of type '"name" | "id"'.
ge.ts(9,7): error TS2322: Type 'string' is not assignable to type 'number'.
----

(The order in which the compiler lists the union members is an implementation detail and can differ between
releases.) A constraint also grants members, so a body may use `.length`; but the body can only rely on what the
constraint promises, not on what some particular argument happens to have:

[source,typescript]
----
function longest<T extends { length: number }>(a: T, b: T): T {
  return a.length >= b.length ? a : b;
}
longest("ab", "abc");        // ok: T = string
longest([1], [1, 2]);        // ok: T = number[]
longest(1, 2);               // error: number has no length

function maxLen<T extends { length: number }>(x: T): T {
  return x.length > 3 ? x : { length: 3 };    // error
}
----

[source,console]
----
ge.ts(44,9): error TS2345: Argument of type 'number' is not assignable to parameter of type '{ length: number; }'.
ge.ts(46,29): error TS2322: Type '{ length: number; }' is not assignable to type 'T'.
  '{ length: number; }' is assignable to the constraint of type 'T', but 'T' could be instantiated with a different subtype of constraint '{ length: number; }'.
----

The last error is the one that confuses people the most. `T` might be `string` or a specific tuple, and the
object `+{ length: 3 }+` is not that type, so returning it would be a lie. The cure is a different design (return the
constraint type, or overload), not an assertion.

== The return-only generic is a hidden cast

A type parameter that appears *only in the return type* cannot be inferred from the arguments, so the caller
supplies it, and nothing checks that the value really has that shape. `getJson<User>` below is `as User` wearing a
disguise:

[source,typescript]
----
async function getJson<T>(url: string): Promise<T> {
  const res = await fetch(url);
  return (await res.json()) as T;      // the cast happens here
}
interface User { id: string; name: string }

async function main() {
  const u = await getJson<User>("/u");  // trusted, not checked
  const w = await getJson("/u");        // T could not be inferred: unknown
  const wn: number = w;                 // error: unknown is not assignable to number
}
----

[source,console]
----
ge.ts(19,7): error TS2322: Type 'unknown' is not assignable to type 'number'.
----

This is the *golden rule* from earlier restated: a type parameter earns its place by relating two positions. Here
there is only one, so the honest signature returns `unknown` and the caller narrows or validates:

[source,typescript]
----
function parseUser(x: unknown): User {
  if (typeof x === "object" && x !== null && "id" in x && "name" in x
      && typeof x.id === "string" && typeof x.name === "string") {
    return { id: x.id, name: x.name };
  }
  throw new Error("not a User");
}
----

Real systems replace that hand-written guard with a schema library whose parser returns the validated type; the
point is that the check happens at run time, in code, at the boundary. Compare the `RequestState<T>` of the worked
example, where `T` genuinely relates the `data` field to the caller's expectation and the type parameter is used in
two places.

== Defaults make a parameter optional

A default after `=` lets callers omit the argument, and the most useful default is the common case:

[source,typescript]
----
interface Result<T = string, E = Error> { ok: boolean; value?: T; error?: E }
const rd: Result = { ok: true, value: "s" };                 // T = string, E = Error
const re: Result<number> = { ok: true, value: "s" };         // error: T is number
----

[source,console]
----
ge.ts(52,40): error TS2322: Type 'string' is not assignable to type 'number'.
----

Parameters with defaults must come after those without, exactly like function parameters.
