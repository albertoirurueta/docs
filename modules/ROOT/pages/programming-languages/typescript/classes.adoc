TypeScript classes are ES2015 classes (see xref:programming-languages/javascript/classes.adoc[]) plus a type layer: member type
annotations, visibility modifiers, `abstract`, `implements`, and `override` checking. Most of that layer is
erased at compile time, but parameter properties, `+#private+` members and `static` blocks emit real runtime code.
This page follows https://www.typescriptlang.org/docs/handbook/2/classes.html[the handbook's Classes chapter].

== Fields, methods and accessors

Fields carry a type; methods and `get`/`set` accessors are annotated like functions. A field with an initializer
infers its type from that initializer.

[source,ts]
----
class Circle {
  radius: number;
  readonly kind = "circle";   // literal type "circle", cannot be reassigned
  label?: string;             // optional: type is string | undefined
  constructor(radius: number) {
    this.radius = radius;
  }
  area(): number {
    return Math.PI * this.radius ** 2;
  }
  get diameter(): number {
    return this.radius * 2;
  }
  set diameter(value: number) {
    this.radius = value / 2;
  }
}
----

With `strict` on -- specifically
https://www.typescriptlang.org/tsconfig/#strictPropertyInitialization[`strictPropertyInitialization`] -- every
non-optional field must be assigned in its declaration or in the constructor. When a field is really initialized
elsewhere (a lifecycle hook, a shared `init()` helper), the definite-assignment assertion `!:` tells the
compiler to trust you.

[source,ts]
----
class Config {
  settings!: Record<string, string>;   // "trust me, this is assigned before use"
  constructor() {
    this.settings = load();
  }
}
----

== Visibility: erased modifiers vs. hard privacy

`public` (the default), `protected` and `private` are *compile-time only*. They are checked and then erased -- at
runtime the properties are ordinary and reachable through `(obj as any).x`. The ECMAScript `+#name+` form is real:
the JavaScript runtime itself forbids access from outside the class body.

[source,ts]
----
class Account {
  public owner: string;
  protected balance = 0;
  private pin: string;
  #token = crypto.randomUUID();   // genuinely private at runtime
  constructor(owner: string, pin: string) {
    this.owner = owner;
    this.pin = pin;
  }
  sameToken(other: Account): boolean {
    return this.#token === other.#token;   // OK: still inside the class body
  }
}

const a = new Account("Ada", "0000");
a.balance;        // Error: 'balance' is protected
a.pin;            // Error: 'pin' is private
(a as any).pin;   // compiles and works -- 'private' was erased
// a.#token;      // SyntaxError at parse time -- hard privacy
----

Prefer `+#private+` when the boundary must hold at runtime; the `private` keyword is fine for plain intra-team
encapsulation and is friendlier to tests and debuggers.

=== `static` members and `static` blocks

`static` attaches a member to the class object rather than to instances. A `static` block runs once when the
class is initialized and can see private static state.

[source,ts]
----
class Registry {
  static readonly items: string[] = [];
  static #count = 0;
  static {
    Registry.items.push("default");
    Registry.#count = Registry.items.length;
  }
  static get count(): number {
    return Registry.#count;
  }
}
----

=== `abstract` classes and members

An `abstract` class cannot be instantiated directly. `abstract` methods and fields have no body and must be
implemented by concrete subclasses; concrete methods on the abstract class may call the abstract ones.

[source,ts]
----
abstract class Shape {
  abstract area(): number;
  describe(): string {
    return `area is ${this.area().toFixed(2)}`;
  }
}

class Square extends Shape {
  constructor(private readonly side: number) {
    super();
  }
  area(): number {
    return this.side ** 2;
  }
}

new Shape();   // Error: cannot create an instance of an abstract class
----

== Parameter properties

Declaring a constructor parameter with a visibility modifier (or `readonly`) both takes the argument and
declares-and-assigns a field of the same name. `constructor(private readonly x: number)` replaces a field
declaration, a parameter, and a `this.x = x` line. See
https://www.typescriptlang.org/docs/handbook/2/classes.html#parameter-properties[Parameter Properties].

[source,ts]
----
class Vector {
  constructor(
    public readonly x: number,
    public readonly y: number,
  ) {}
  plus(other: Vector): Vector {
    return new Vector(this.x + other.x, this.y + other.y);
  }
}

new Vector(1, 2).plus(new Vector(3, 4));   // Vector { x: 4, y: 6 }
----

Unlike type annotations, parameter properties *emit runtime code* -- the compiler generates the field
assignments -- so they are not erasable syntax. A file that uses them cannot be handled by a pure type-stripping
step (`--erasableSyntaxOnly`, Node's built-in type stripping, some fast loaders); write the field and the
assignment out by hand if every construct must be erasable.

== `implements` vs. `extends`, and `override`

`extends` inherits implementation from one base class. `implements` only adds a *check* that the class is
assignable to one or more interfaces -- it contributes nothing to the body and does not infer or fill in members.

[source,ts]
----
interface Serializable {
  toJSON(): string;
}

class Session extends EventTarget implements Serializable {
  constructor(private readonly id: string) {
    super();
  }
  toJSON(): string {
    return JSON.stringify({ id: this.id });
  }
}
----

When overriding an inherited member, mark it `override`. With
https://www.typescriptlang.org/tsconfig/#noImplicitOverride[`noImplicitOverride`] on, redefining an inherited
member *without* `override` is an error, and an `override` member whose base member later disappears is flagged
too -- both directions stay honest as the base class evolves.

[source,ts]
----
class Base {
  greet(): string {
    return "hi";
  }
}

class Loud extends Base {
  override greet(): string {
    return super.greet().toUpperCase();
  }
}
----

=== A class is both a value and a type

Declaring `class Duration` introduces a *type* named `Duration` (the instance shape) and a *value* named
`Duration` (the constructor object). `typeof Duration` is the constructor's type.

[source,ts]
----
class Duration {
  constructor(public readonly ms: number) {}
}

const d: Duration = new Duration(1000);   // 'Duration' as a type
const ctor = Duration;                    // 'Duration' as a value
type Ctor = typeof Duration;              // new (ms: number) => Duration
----

=== `this` types and polymorphic `this`

Inside a class, `this` is a type that resolves to the *actual* subclass at each call site. Returning `this` from
a builder method keeps the fluent chain typed as the most-derived class.

[source,ts]
----
class QueryBuilder {
  protected parts: string[] = [];
  where(clause: string): this {
    this.parts.push(clause);
    return this;
  }
}

class SqlQueryBuilder extends QueryBuilder {
  limit(n: number): this {
    this.parts.push(`LIMIT ${n}`);
    return this;
  }
}

new SqlQueryBuilder().where("a = 1").limit(10);   // still SqlQueryBuilder, so .limit() stays visible
----

== Generic classes and mixins

Classes take type parameters just like functions: `class Box<T>`. The full treatment -- constraints, defaults,
`const` type parameters, inference -- is on xref:programming-languages/typescript/generics.adoc[].

[source,ts]
----
class Box<T> {
  constructor(public value: T) {}
  map<U>(f: (value: T) => U): Box<U> {
    return new Box(f(this.value));
  }
}

new Box(2).map((n) => n.toString());   // Box<string>
----

The *mixin* pattern composes reusable slices of behavior with functions that take a class and return an extended
subclass, using a generic constructor type as the constraint. See
https://www.typescriptlang.org/docs/handbook/mixins.html[the handbook's Mixins page].

[source,ts]
----
type Constructor<T = object> = new (...args: any[]) => T;

function Timestamped<TBase extends Constructor>(Base: TBase) {
  return class extends Base {
    createdAt = Date.now();
  };
}

class User {
  constructor(public name: string) {}
}

const TimestampedUser = Timestamped(User);
const u = new TimestampedUser("Ada");
u.name;        // from User
u.createdAt;   // from the mixin
----

For adding behavior through class and member *decorators* instead, see
xref:programming-languages/typescript/decorators-and-metadata.adoc[].

== What privacy really means at run time

TypeScript offers two ways to hide a member, and they differ in the one place that matters: whether the hiding
survives to run time. `private` and `protected` are *compile-time* annotations, erased like every other type. A `+#name+`
member is a genuine JavaScript private field that the engine enforces.

[source,typescript]
----
class Account {
  private balance = 5;
  #secret = "s";
  protected owner = "o";
  peek() { return this.#secret; }
}
const a = new Account();
a.balance;          // error
a.#secret;          // error
a.owner;            // error
console.log((a as any).balance, Object.keys(a), JSON.stringify(a), a.peek());
----

[source,console]
----
cl.ts(9,3): error TS2341: Property 'balance' is private and only accessible within class 'Account'.
cl.ts(10,3): error TS18013: Property '#secret' is not accessible outside class 'Account' because it has a private identifier.
cl.ts(11,3): error TS2445: Property 'owner' is protected and only accessible within class 'Account' and its subclasses.
----

The three accesses are rejected, but the `as any` escape reaches `balance` anyway, and the running program shows what
is and is not protected:

[source,console]
----
5 [ 'balance' ] {"balance":5} s
----

`balance` is an ordinary enumerable property (it appears in `Object.keys` and in `JSON.stringify`, so it is also
*serialised*), while `+#secret+` is invisible to both and unreachable from outside the class even with a cast. Choose
`+#+` for anything that must stay hidden, such as tokens or password hashes, and `private` when you only want to
steer other developers.

== Parameter properties and what the emitter writes

A constructor parameter with an accessibility modifier or `readonly` is shorthand for declaring a field and assigning it.
That is one of the few places where TypeScript emits code that has no JavaScript source equivalent:

[source,typescript]
----
class Pt { constructor(public x: number, private y = 0, readonly z?: string) {} }
console.log(new Pt(1));
----

[source,console]
----
Pt { x: 1, y: 0, z: undefined }
----

With `target: es2022` the emitted class is:

[source,js]
----
class Pt {
    x;
    y;
    z;
    constructor(x, y = 0, z) {
        this.x = x;
        this.y = y;
        this.z = z;
    }
}
----

The three field declarations (`x;`) come from `useDefineForClassFields`, which is the default for `target` ES2022 and
newer and gives the standard JavaScript field semantics. With `"useDefineForClassFields": false` those lines disappear
and only the constructor assignments remain. The difference becomes visible when a subclass redeclares a field:
under define semantics the subclass's initialiser runs after the base constructor, so a base constructor that reads
the field sees the *base* value (or `undefined`), not the subclass one. Parameter properties are also why Node's
type stripping rejects such classes: they need emitted code, so `--erasableSyntaxOnly` bans them.

Private identifiers need a target of ES2015 or newer, because older targets would have to emulate them with
``WeakMap``s: compiling the `Account` above for `es5` reports `error TS18028: Private identifiers are only available when
targeting ECMAScript 2015 and higher.`

== `override`, `implements` and `abstract`, as the checker reports them

[source,typescript]
----
abstract class Shape { abstract area(): number; describe() { return `area ${this.area()}`; } }
new Shape();                                   // error
class Sq extends Shape {}                      // error
class Circle extends Shape {
  constructor(public r: number) { super(); }
  area() { return Math.PI * this.r ** 2; }
}
console.log(new Circle(1).describe());         // area 3.141592653589793

interface Named { name: string; greet(): string }
class Q implements Named { name = "x"; }                                   // error
class Cb implements Named { name = "x"; greet(extra: number) { return ""; } }   // error

class Base { run(): void {} stop(): void {} }
class Derived extends Base {
  override run(): void {}
  override halt(): void {}                     // error
  stop(): void {}                              // accepted unless noImplicitOverride is on
}
----

[source,console]
----
cl.ts(16,1): error TS2511: Cannot create an instance of an abstract class.
cl.ts(17,7): error TS2515: Non-abstract class 'Sq' does not implement inherited abstract member area from class 'Shape'.
cl.ts(27,7): error TS2420: Class 'Q' incorrectly implements interface 'Named'.
  Property 'greet' is missing in type 'Q' but required in type 'Named'.
cl.ts(28,41): error TS2416: Property 'greet' in type 'Cb' is not assignable to the same property in base type 'Named'.
  Type '(extra: number) => string' is not assignable to type '() => string'.
    Target signature provides too few arguments. Expected 1 or more, but got 0.
cl.ts(34,12): error TS4113: This member cannot have an 'override' modifier because it is not declared in the base class 'Base'.
----

With `noImplicitOverride` on (not part of `strict`), the accepted `stop()` becomes `+error TS4114: This member must have an
'override' modifier because it overrides a member in the base class 'Base'.+` That is the setting that turns a
base-class rename from a silent bug (the subclass method stops overriding anything) into a compile error.

`implements` only *checks* that a class has the shape of an interface; it does not copy anything into the class or add
types to its members. A parameter that the interface declares as `+() => string+` cannot be satisfied by a method that
requires an argument (the `Cb` case), but a method that accepts *fewer* parameters is fine.

== `this` in constructors and the order of initialisation

Initialisation order is the classic class pitfall, and the checker catches the two most common mistakes:

[source,typescript]
----
class Animal { name: string; constructor(n: string) { this.name = n; } }
class Dog extends Animal { constructor() { this.name = "d"; super("d"); } }     // error
class Late { value: number; constructor() { this.init(); } init() { this.value = 1; } }  // error
----

[source,console]
----
cl.ts(47,44): error TS17009: 'super' must be called before accessing 'this' in the constructor of a derived class.
cl.ts(48,14): error TS2564: Property 'value' has no initializer and is not definitely assigned in the constructor.
----

The second error is deliberate: the checker does not follow `this.init()` into a method to see the assignment, so it
asks you to assign in the constructor, give a default, or write `value!: number` and take responsibility for it.
Returning `this` from a method keeps subclasses chainable: `set(): this` makes `new Sub().set().extra()` compile because
the polymorphic `this` type follows the receiver.
