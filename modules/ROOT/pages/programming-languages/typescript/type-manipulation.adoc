The type system is a small pure language for computing types from other types. The
https://www.typescriptlang.org/docs/handbook/2/types-from-types.html[Types from Types] handbook chapter is
the map; this page tours each operator with a runnable example. See xref:programming-languages/typescript/generics.adoc[] for
the type parameters these operators run on, and xref:programming-languages/typescript/utility-types.adoc[] for the standard
library built from them.

== Type queries: keyof, typeof, indexed access

`keyof T` is the union of `T`&#39;s known public property keys. The *type query* `typeof x` reads the static
type of a value binding -- it is a type-position operator, unrelated to the runtime `typeof` in a JavaScript
expression. An *indexed access type* `T[K]` looks up the type stored at key `K`.

[source,ts]
----
interface User {
  id: number;
  name: string;
  admin: boolean;
}

type UserKey = keyof User;          // "id" | "name" | "admin"
type Name = User["name"];           // string   -- indexed access with a literal key
type Value = User[keyof User];      // number | string | boolean

const scores = { math: 90, art: 82 };
type Scores = typeof scores;        // { math: number; art: number }  -- type query
type Subject = keyof typeof scores; // "math" | "art"

const tuple = [1, "a", true] as const;
type Elem = (typeof tuple)[number]; // 1 | "a" | true  -- number index on a tuple/array
----

The key in `T[K]` can be a literal (`+User['id']+`), a union (`+User['id' | 'name']+` gives `number | string`),
or `number` to read the element type of an array or tuple.

== Conditional types

A conditional type `T extends U ? X : Y` picks a branch by testing whether `T` is assignable to `U`. The
`infer` keyword, valid only in the `extends` clause, captures part of the matched type into a fresh type
variable.

[source,ts]
----
type IsString<T> = T extends string ? true : false;
type A = IsString<"hi">;    // true
type B = IsString<number>;  // false

type ElementType<T> = T extends readonly (infer E)[] ? E : T;
type C = ElementType<string[]>; // string
type D = ElementType<number>;   // number  -- no match, falls through to T

type ReturnOf<F> = F extends (...args: any[]) => infer R ? R : never;
type E = ReturnOf<() => Date>;  // Date
----

The full rules -- nested conditionals, multiple `infer` sites, and constrained inference -- are in
https://www.typescriptlang.org/docs/handbook/2/conditional-types.html[Conditional Types].

=== Distributive conditional types

When the checked type is a *naked type parameter*, the conditional distributes over a union, evaluating once
per member and re-uniting the results:

[source,ts]
----
type ToArray<T> = T extends unknown ? T[] : never;
type Dist = ToArray<string | number>; // string[] | number[]  -- distributed

// Wrap both sides in a one-tuple to turn distribution OFF:
type ToArrayNonDist<T> = [T] extends [unknown] ? T[] : never;
type NonDist = ToArrayNonDist<string | number>; // (string | number)[]
----

Distribution is what makes `Exclude` and `NonNullable` filter unions member by member. The `[T] extends [U]`
idiom is the standard way to compare two unions as whole types instead.

== Mapped types

A mapped type walks the keys of an existing type -- `[K in keyof T]` -- and rebuilds each property. The
https://www.typescriptlang.org/docs/handbook/2/mapped-types.html[Mapped Types] chapter is the reference.

[source,ts]
----
type MyPartial<T> = { [K in keyof T]?: T[K] };
type MyReadonly<T> = { readonly [K in keyof T]: T[K] };
----

The `?` and `readonly` modifiers accept an explicit `pass:c[+]` or `-` prefix to *add* or *remove* them. A bare
`readonly` or `?` means `pass:c[+readonly]` / `pass:c[+?]`.

[source,ts]
----
type Mutable<T>  = { -readonly [K in keyof T]: T[K] };
type Required2<T> = { [K in keyof T]-?: T[K] };
type Concrete<T> = { -readonly [K in keyof T]-?: T[K] };

interface Cfg { readonly host: string; port?: number }
type C1 = Mutable<Cfg>;   // { host: string; port?: number }
type C2 = Required2<Cfg>; // { readonly host: string; port: number }
----

=== Key remapping with `as`

An `as` clause rewrites each key. Map a key to `never` and the property is dropped.

[source,ts]
----
type Getters<T> = {
  [K in keyof T & string as `get${Capitalize<K>}`]: () => T[K];
};
interface Point { x: number; y: number }
type PointGetters = Getters<Point>;
// { getX: () => number; getY: () => number }

type RemoveKind<T> = { [K in keyof T as Exclude<K, "kind">]: T[K] };
type Bare = RemoveKind<{ kind: "circle"; r: number }>; // { r: number }
----

`Record<Keys, Value>` is the library's basic mapped type -- every key in `Keys` mapped to the same `Value`:

[source,ts]
----
type Role = "admin" | "user" | "guest";
type Permissions = Record<Role, string[]>;
// { admin: string[]; user: string[]; guest: string[] }
----

== Template literal types

A template literal type interpolates unions into a string pattern and produces every combination as a
string-literal type. See
https://www.typescriptlang.org/docs/handbook/2/template-literal-types.html[Template Literal Types].

[source,ts]
----
type Lang = "en" | "fr";
type Page = "home" | "about";
type Route = `/${Lang}/${Page}`;
// "/en/home" | "/en/about" | "/fr/home" | "/fr/about"

// `infer` inside a template literal parses a string type apart.
type EventName<T extends string> = T extends `on${infer Rest}` ? Lowercase<Rest> : never;
type Ev = EventName<"onClick">; // "click"
----

The four intrinsic string types -- `Uppercase`, `Lowercase`, `Capitalize`, `Uncapitalize` -- are compiler
built-ins with no TypeScript source, and are most useful inside key remapping, as the `+get${Capitalize<K>}+`
mapping above shows:

[source,ts]
----
type Loud  = Uppercase<"hello">;    // "HELLO"
type Quiet = Lowercase<"HELLO">;    // "hello"
type Title = Capitalize<"hello">;   // "Hello"
type Lower = Uncapitalize<"Hello">; // "hello"
----

== never, and testing your types

`never` is the empty type: no value has it. It vanishes from a union, wins an intersection, and silently
removes conditional and mapped-type entries -- which is exactly how filtering idioms work.

[source,ts]
----
type U = never | string;  // string
type I = never & string;  // never
type Keep<T> = T extends string ? T : never;
type Filtered = Keep<"a" | 1 | "b">; // "a" | "b"

// A remapped key that resolves to `never` deletes the property entirely.
type OnlyStrings<T> = { [K in keyof T as T[K] extends string ? K : never]: T[K] };
type S = OnlyStrings<{ a: string; b: number }>; // { a: string }
----

Because these types are real logic, test them. `@ts-expect-error` asserts that the *next line fails* to
compile:

[source,ts]
----
type Eq<A, B> =
  (<T>() => T extends A ? 1 : 2) extends (<T>() => T extends B ? 1 : 2) ? true : false;
type Assert<T extends true> = T;

type _ok = Assert<Eq<Uppercase<"hi">, "HI">>;

// @ts-expect-error -- a string is not a Record of string arrays
const bad: Record<"a", string[]> = "nope";
----

For a real suite use a dedicated tool: https://github.com/mmkal/expect-type[expect-type]'s
`expectTypeOf<X>().toEqualTypeOf<Y>()`, or https://github.com/tsdjs/tsd[tsd]'s `expectType` /
`expectError` assertions in `+*.test-d.ts+` files.

Two habits worth keeping:

* *Pay attention to how a type displays.* Hover it in the editor or use the `+//   ^?+` twoslash query. A
  helper such as `+type Prettify<T> = { [K in keyof T]: T[K] } & {}+` forces the compiler to flatten an
  intersection into one readable object literal without changing its meaning.
* *Tail-recursive generic types have a depth limit.* TypeScript optimizes a conditional type whose result
  is a direct recursive call with an accumulator, allowing roughly 1000 iterations before the
  "Type instantiation is excessively deep and possibly infinite" error (`TS2589`). Non-tail recursion caps
  out far sooner.

[source,ts]
----
// Tail-recursive: the recursive call IS the result.
type BuildTuple<N extends number, Acc extends unknown[] = []> =
  Acc["length"] extends N ? Acc : BuildTuple<N, [...Acc, unknown]>;

type Ten = BuildTuple<10>["length"]; // 10
// type Huge = BuildTuple<100000>;   // error TS2589
----

== Evaluating a conditional type step by step

Conditional types are small programs that the checker runs while it resolves a type, and like any program they
are easier to understand with a trace. Take the distributive helper from above, `ToArray<T> = T extends unknown ?
T[] : never`, applied to `string | number`:

[mermaid]
....
flowchart TD
    A["ToArray of string | number"] --> B{"T is a naked type parameter,<br/>so split the union"}
    B --> C["ToArray of string<br/>string extends unknown? yes -> string[]"]
    B --> D["ToArray of number<br/>number extends unknown? yes -> number[]"]
    C --> E["union the results"]
    D --> E
    E --> F["string[] | number[]"]
    G["[T] extends [unknown]<br/>(wrapped, not naked)"] --> H["no splitting: one test on<br/>[string | number]"]
    H --> I["(string | number)[]"]
....

The checker is observable in the assignment errors you get when you assign the wrong value, which is a reliable
way to print a type that is otherwise invisible:

[source,typescript]
----
type ToArray<T> = T extends unknown ? T[] : never;
type D = ToArray<string | number>;
const dd: D = 1;                                 // error names the evaluated type
type NonDist<T> = [T] extends [unknown] ? T[] : never;
const nd: NonDist<string | number> = 1;
----

[source,console]
----
tm.ts(48,7): error TS2322: Type 'number' is not assignable to type 'D'.
tm.ts(50,7): error TS2322: Type 'number' is not assignable to type '(string | number)[]'.
----

The error on the first line names only the alias `D`; hovering `D` in an editor shows `string[] | number[]`. The second
shows the type fully expanded, which is the difference in practice between the two forms.

== Worked example: deriving handlers from `RequestState`

The `RequestState<T>` union from the xref:programming-languages/typescript/worked-example.adoc[worked example] already
contains everything needed to *derive* the types of a handler map, with no repetition. Three of the operators from
this page do the work: an indexed access to list the kinds, `Extract` to pick one arm, and a key-remapping mapped
type to build the handler names.

[source,typescript]
----
type RequestState<T> =
  | { readonly kind: "idle" }
  | { readonly kind: "loading" }
  | { readonly kind: "success"; readonly data: T }
  | { readonly kind: "error"; readonly error: string };

type Kind = RequestState<unknown>["kind"];                  // "idle" | "loading" | "success" | "error"
type Arm<K extends Kind, T = unknown> = Extract<RequestState<T>, { kind: K }>;

type Handlers<T> = {
  [K in Kind as `on${Capitalize<K>}`]: (state: Arm<K, T>) => void;
};
// { onIdle: (state: {kind:"idle"}) => void; onLoading: ...; onSuccess: (state: {kind:"success"; data: T}) => void; ... }

declare const h: Handlers<{ name: string }>;
h.onSuccess({ kind: "success", data: { name: 1 } });        // error
h.onError({ kind: "error", error: "x" });                   // ok
const k: keyof Handlers<number> = "onIdle";                 // ok
const k2: keyof Handlers<number> = "onFoo";                 // error
----

[source,console]
----
tm.ts(15,40): error TS2322: Type 'number' is not assignable to type 'string'.
tm.ts(18,7): error TS2322: Type '"onFoo"' is not assignable to type '"onError" | "onIdle" | "onLoading" | "onSuccess"'.
----

Add a fifth arm to `RequestState` (a `"cancelled"` state, say) and `Handlers` grows an `onCancelled` member with the
right argument type automatically: the derived type cannot go stale, which is the reason to prefer derivation over
copying.

== Worked example: parsing a path with template literal types

A recursive conditional type with `infer` inside a template literal can parse string types. This one extracts the
`:param` names from a route pattern, and a generic function then requires exactly those parameters:

[source,typescript]
----
type PathParams<P extends string> =
  P extends `${string}:${infer Name}/${infer Rest}`
    ? Name | PathParams<`/${Rest}`>
    : P extends `${string}:${infer Name}` ? Name : never;

type PP = PathParams<"/users/:id/posts/:postId">;           // "id" | "postId"

function url<P extends string>(path: P, params: Record<PathParams<P>, string>): string {
  return path.replace(/:(\w+)/g, (_, n) => (params as Record<string, string>)[n]!);
}

console.log(url("/users/:id/posts/:postId", { id: "7", postId: "9" }));
url("/users/:id/posts/:postId", { id: "7" });                // error: postId is missing
const bad: PP = "nope";                                      // error
----

[source,console]
----
/users/7/posts/9
tm.ts(29,33): error TS2345: Argument of type '{ id: string; }' is not assignable to parameter of type 'Record<"id" | "postId", string>'.
  Property 'postId' is missing in type '{ id: string; }' but required in type 'Record<"id" | "postId", string>'.
tm.ts(30,7): error TS2322: Type '"nope"' is not assignable to type '"id" | "postId"'.
----

(Compiler 7.0 reports the missing property directly as TS2741 instead of wrapping it in TS2345; the cause named is the same.) The first
`PathParams` branch peels off one parameter and recurses on the rest of the string, the second handles a
parameter at the very end, and `never` ends the recursion. The same technique types router libraries, query-string
parsers and SQL tagged templates.

== Recursive mapped types and flattening

Mapped types recurse through nested objects when they call themselves on each property. A `DeepReadonly` combines
a conditional (to treat arrays specially) with a recursive mapped type:

[source,typescript]
----
type DeepReadonly<T> = T extends (infer E)[] ? readonly DeepReadonly<E>[]
  : T extends object ? { readonly [K in keyof T]: DeepReadonly<T[K]> } : T;

interface Cfg { host: string; limits: { rps: number; paths: string[] } }
declare const c: DeepReadonly<Cfg>;
c.limits.rps = 3;               // error
c.limits.paths.push("x");       // error
----

[source,console]
----
tm.ts(36,10): error TS2540: Cannot assign to 'rps' because it is a read-only property.
tm.ts(37,16): error TS2339: Property 'push' does not exist on type 'readonly string[]'.
----

When a result is an intersection, error messages list the pieces separately. The `Prettify` idiom from the
previous section rewrites an intersection as one object so that messages and hovers are readable:

[source,typescript]
----
type Show<T> = { [K in keyof T]: T[K] } & {};
type Merged = { a: 1 } & { b: 2 };
type Flat = Show<Merged>;
const f: Flat = 1;       // Type 'number' is not assignable to type '{ a: 1; b: 2; }'.
const m: Merged = 1;     // Type 'number' is not assignable to type 'Merged'.
                         //   Type 'number' is not assignable to type '{ a: 1; }'.
----

Both types are identical to the checker; only the display differs.
