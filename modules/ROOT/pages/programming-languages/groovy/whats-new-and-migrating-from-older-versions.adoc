This page collects in one place what changed between Groovy releases and how to move code forward. The baseline is
*Groovy 6.0.0* (released 2026-09-22, JDK 17 or newer); every example on the page was run with Groovy 6.0.0 on JDK 26 on
2026-10-14. Version numbers, dates and maintained lines were checked on that day against the official
https://groovy-lang.org/changelogs.html[change log] and the
https://groovy-lang.org/releases.html[release notes]. Features introduced after Groovy 4.0 name their release, and a
feature described as *incubating* may still change in a minor release. Each change is explained in depth on the guide page
linked from it.

The page has four parts: the xref:#_release_by_release_1_0_to_6_0[release-by-release table and timeline], the
xref:#_legacy_to_modern[legacy-to-modern table], the xref:#_breaking_changes_and_how_to_migrate[breaking changes with
migration steps] and a xref:#_upgrade_checklist[checklist].

== Release by release: 1.0 to 6.0

Groovy follows https://groovy-lang.org/versioning.html[semantic versioning]. Two release numbers never shipped under
their original name: 1.1 was renamed *1.5* and 1.9 was renamed *2.0*. A 2.6 line was planned as a JDK 7 back-port of the
3.0 parser but was retired after four alpha releases (the last on 2018-06-23), so it is not in the table. A 7.0 release-notes
page exists but is marked as under development with no release on the change log; nothing on this page depends on it.

== Legacy to modern

Older books, blog posts and Stack Overflow answers describe Groovy 1.x and 2.x. Most of what they teach still works, but
several statements are now wrong and many idioms have a better replacement. The first table lists the specific places where
a Groovy 1.0 reference (the era of the first generation of printed books) no longer matches Groovy 6.0; the second table
lists further legacy-to-modern replacements. The guide pages always show the current form.

=== Where Groovy 1.0 material is out of date

[cols="3,4,2",options="header"]
|===
|Older statement or form |Groovy 6.0 |Page

|The classic `for(init; test; inc)` loop is not available
|Supported since 1.5; the enhanced forms (several variables in 3.0, an index variable in 5.0) exist too
|xref:programming-languages/groovy/control-structures.adoc[Control Structures]

|There is no `do`/`while` loop
|`do`/`while` has been available since 3.0 (the Parrot parser)
|xref:programming-languages/groovy/control-structures.adoc[Control Structures]

|Java's package-wide default visibility cannot be expressed
|The `@PackageScope` AST transformation (1.6) gives package-private members
|xref:programming-languages/groovy/classes-fields-and-properties.adoc[Classes, Fields & Properties]

|No lambdas, method references, `!in`/`!instanceof`, `===`, `?=`, safe indexing `?[]`, try-with-resources or Java-style
array initialisers
|All added by the Parrot parser in 3.0; the `+==>+` operator in 5.0; `val` and module imports in 6.0
|xref:programming-languages/groovy/differences-with-java.adoc[Differences with Java]

|Examples avoid annotations, enums, generics, static imports and varargs (they target a JDK that lacks them)
|All supported since 1.5
|xref:programming-languages/groovy/enums-and-annotations.adoc[Enums & Annotations]

|Metaprogramming means `invokeMethod`, `MetaClass` and categories
|`ExpandoMetaClass` and `methodMissing`/`propertyMissing` (1.5), AST transformations (1.6), extension modules (2.0),
traits (2.3, which replace `@Mixin`)
|xref:programming-languages/groovy/runtime-metaprogramming-and-the-mop.adoc[Runtime Metaprogramming & the MOP]

|Everything is dynamic
|Optional static type checking and static compilation (`@TypeChecked`/`@CompileStatic`, 2.0)
|xref:programming-languages/groovy/static-type-checking-and-compile-static.adoc[Static Type Checking & @CompileStatic]

|JSR 241 makes Groovy the second standard language of the JVM, and Groovy is a Codehaus project
|JSR 241 has been dormant since 2012; Groovy is a top-level Apache Software Foundation project
|xref:programming-languages/groovy/index.adoc[Groovy]

|`groovy:groovy` or `org.codehaus.groovy` coordinates, the `groovy-all` jar and the `+org.codehaus.groovy.*+` legacy
packages
|`org.apache.groovy` since 4.0; the legacy packages are gone; `groovy-all` is a POM that pulls in modules
|xref:programming-languages/groovy/build-tools-gradle-maven-and-ant.adoc[Build Tools: Gradle, Maven & Ant]

|`GroovyTestCase` (JUnit 3) as the base class for tests
|JUnit 5 or 6 with `GroovyAssert`, or Spock; `GroovyTestCase` is legacy
|xref:programming-languages/groovy/testing-with-junit-and-groovy-test.adoc[Testing with JUnit & Groovy Test]

|No built-in dependency management
|Grape and `@Grab` (1.6); a Maven Resolver based engine in 6.0
|xref:programming-languages/groovy/grape-dependency-management.adoc[Grape Dependency Management]

|Swing, Ant and SQL classes live in the core jar
|Separate modules (`groovy-swing`, `groovy-ant`, `groovy-sql`, `groovy-xml`, `groovy-json`, and more) since 2.0
|xref:programming-languages/groovy/databases-with-groovy-sql.adoc[Databases with Groovy SQL]

|XML-RPC and GroovySOAP for remote calls
|Those modules are no longer maintained; use the JDK `HttpClient` or the `groovy-http-builder` module (6.0, incubating)
|xref:programming-languages/groovy/http-client-with-httpbuilder.adoc[HTTP Client with HttpBuilder]

|Groovlets run on `javax.servlet`
|Jakarta Servlet is the default since 5.0; `javax` is still supported
|xref:programming-languages/groovy/groovlets-servlets-and-jmx.adoc[Groovlets, Servlets & JMX]

|`groovy -l` listens on every interface
|It binds the loopback address unless you give a host, and it has no authentication
|xref:programming-languages/groovy/running-scripts-and-the-groovy-command.adoc[Running Scripts & the groovy Command]

|The launchers append `.` to your classpath
|Since 6.0 a classpath you supply is used exactly as written
|xref:programming-languages/groovy/running-scripts-and-the-groovy-command.adoc[Running Scripts & the groovy Command]

|Sandboxing relies on the Java Security Manager
|Security Manager support was removed in 6.0; use `SecureASTCustomizer`, containers and operating system isolation
|xref:programming-languages/groovy/compilation-customizers-and-secure-scripting.adoc[Compilation Customizers & Secure Scripting]

|`groovysh` is a simple line reader
|Rewritten on JLine 3 in 5.0 with commands and completion; `/img` for inline images in 6.0
|xref:programming-languages/groovy/groovysh-and-groovyconsole.adoc[groovysh & groovyconsole]

|Call-site caching is how method dispatch works
|`invokedynamic` is the default since 4.0; the classic runtime is the optional `groovy-callsite` module in 6.0
|xref:programming-languages/groovy/performance-invokedynamic-and-native-images.adoc[Performance, invokedynamic & Native Images]

|Concurrency means `Thread.start` and GPars as an add-on
|Async/await, parallel collections, actors, agents and dataflow in `groovy.concurrent` (6.0, incubating)
|xref:programming-languages/groovy/async-await.adoc[Async/Await]
|===

[cols="3,4,2",options="header"]
|===
|Legacy idiom |Modern replacement |Page

|`groovy.util.XmlSlurper`, `groovy.util.XmlParser`, `groovy.util.AntBuilder`, `groovy.util.GroovyTestCase`
|`groovy.xml.XmlSlurper`, `groovy.xml.XmlParser`, `groovy.ant.AntBuilder`, `groovy.test.GroovyTestCase` (4.0 removed the

|xref:programming-languages/groovy/xml-parsing-gpath-and-security.adoc[XML Parsing, GPath & Security]

|xref:programming-languages/groovy/traits.adoc[Traits]

|xref:programming-languages/groovy/dates-and-times.adoc[Dates & Times]

|`%` handled by a `mod` method
|`remainder` since 5.0 (a fallback to `mod` is kept)
|xref:programming-languages/groovy/operator-overloading.adoc[Operator Overloading]

|Anonymous inner classes and `Closure` subclasses for callbacks
|Lambdas and method references (3.0); closures still coerce to functional interfaces
|xref:programming-languages/groovy/closures.adoc[Closures]

|`file != null`; since 5.0 `File` and `Path` are falsy when the path does not exist
|xref:programming-languages/groovy/booleans-and-the-groovy-truth.adoc[Booleans & the Groovy Truth]

|`switch` with `break` in every branch
|Switch expressions with `+->+` arms (4.0); position decides statement or expression (6.0)
|xref:programming-languages/groovy/control-structures.adoc[Control Structures]

|`+'org.mysql.Driver' as Class+` to register a JDBC driver
|Drivers register through `ServiceLoader`; call `Class.forName` explicitly if you really need the side effect (6.0 no
longer runs the static initialiser for the coercion)
|xref:programming-languages/groovy/databases-with-groovy-sql.adoc[Databases with Groovy SQL]

|Untyped `def` everywhere
|`var` (3.0), `val` for final locals (6.0) and optional types that `@CompileStatic` checks
|xref:programming-languages/groovy/variables-typing-def-var-and-val.adoc[Variables, Typing, def, var & val]

|A parallel library such as GPars for futures
|Native async/await, channels and structured concurrency (6.0, incubating)
|xref:programming-languages/groovy/generators-channels-and-structured-concurrency.adoc[Generators, Channels & Structured Concurrency]

|Hand-rolled SQL strings in loops
|GINQ queries (4.0, stable in 6.0) and `groovy.sql.Sql` with bound parameters
|xref:programming-languages/groovy/ginq-sql-like-collection-queries.adoc[GINQ: SQL-like Collection Queries]

|Hand-written JSON or XML parsing with default factories
|`JsonSlurper` and the secure-by-default XML parsers (6.0)
|xref:programming-languages/groovy/json.adoc[JSON]

|Reflection tricks to call another language's code
|Joint compilation and the `JavaShell` (stable in 6.0)
|xref:programming-languages/groovy/compiling-groovyc-and-joint-compilation.adoc[Compiling with groovyc & Joint Compilation]
|===

=== Writing the same code in the old and the new style

The script below uses only forms that Groovy 1.0 did not have or that arrived with the Parrot parser and later. It runs
unchanged on Groovy 6.0.0:

[source,groovy]
----
// Forms that Groovy 1.0 lacked or that only arrived with the Parrot parser (3.0) and later.
import java.util.function.Function

// classic for loop (1.5), do/while (3.0), Java-style array initializer (3.0)
int[] sizes = [3, 5, 8] as int[]
int[] more = new int[]{4, 6}
def total = 0
for (int i = 0; i < sizes.length; i++) { total += sizes[i] }
int n = 3
do { n-- } while (n > 0)

// lambdas and method references (3.0)
Function<String, Integer> len = s -> s.length()
def upper = 'tomato'.&toUpperCase

// negated operators, identity, Elvis assignment, safe indexing (3.0)
def seed = null
seed ?= 'basil'
List<String> none = null

// try-with-resources (3.0)
String first
try (def r = new StringReader('line1\nline2')) { first = new BufferedReader(r).readLine() }

// 5.0: loop with an index variable
def idx = []
for (int i, var item in ["a", "b", "c"]) { idx << "$i$item" }

// 6.0: val
val final1 = 42

assert total == 16 && more.length == 2 && n == 0
assert len('lettuce') == 7 && upper() == 'TOMATO'
assert 'x' !in ['a', 'b'] && !('x' instanceof Integer)
assert seed == 'basil' && none?[0] == null
assert first == 'line1'
assert idx == ['0a', '1b', '2c']
assert (false ==> true) && !(true ==> false)
assert final1 == 42
println 'modern syntax ok'
----

[source,text]
----

== Breaking changes and how to migrate

Groovy keeps minor releases compatible; the breaking changes cluster in the major releases and are listed in the
"Breaking changes" section of each release-notes page. The tables below cover the ones that affect typical projects.

=== Moving to Groovy 3.0

Groovy 3.0 introduced the Parrot parser (enabled by default; the old parser could still be selected by a system property)
and, to prepare for the Java module system, duplicated many classes into JPMS-friendly packages. Nothing had to change
yet, but this is the release in which you should start moving to the new package names, because 4.0 removes the old ones.

=== Moving to Groovy 4.0

[cols="2,4,3",options="header"]
|===
|Change |What to do |Where

|*Maven coordinates*: the `groupId` changed from `org.codehaus.groovy` to `org.apache.groovy`
|Update Gradle, Maven and Ant build files (the Gradle and Maven snippets are below)
|xref:programming-languages/groovy/build-tools-gradle-maven-and-ant.adoc[Build Tools]

|*Legacy packages removed*: the duplicated classes in the old packages are gone
|Replace `groovy.util.XmlSlurper` with `groovy.xml.XmlSlurper`, `groovy.util.XmlParser` with `groovy.xml.XmlParser`,
`groovy.util.AntBuilder` with `groovy.ant.AntBuilder`, `groovy.util.GroovyTestCase` with `groovy.test.GroovyTestCase`, and
so on for the classes listed in the 3.0 notes
|xref:programming-languages/groovy/xml-parsing-gpath-and-security.adoc[XML Parsing, GPath & Security]

|*Old parser removed*: the Antlr 2 based parser no longer exists
|Fix any source that only compiled with the old parser; if you cannot, stay on 3.0
|xref:programming-languages/groovy/lexical-structure-comments-keywords-and-identifiers.adoc[Lexical Structure]

|*`invokedynamic` is on by default*: one set of jars, no `-indy` variants
|Remove the `indy` classifier; set `groovy.target.indy=false` only if you must disable it
|xref:programming-languages/groovy/performance-invokedynamic-and-native-images.adoc[Performance, invokedynamic & Native Images]

|*`groovy-all` contents*: `groovy-yaml` is now included, `groovy-testng` is not
|Add `groovy-testng` explicitly if you use it
|xref:programming-languages/groovy/build-tools-gradle-maven-and-ant.adoc[Build Tools]

|*Modules removed*: `groovy-jaxb` (JAXB left the JDK) and `groovy-bsf` (BSF 2 reached end of life)
|Use the Groovy 3 version of those modules or switch libraries
|xref:programming-languages/groovy/integrating-groovy-into-java-applications.adoc[Integrating Groovy into Java Applications]

|*`intersect` with a projection* now draws elements from the receiver, as in other languages
|Re-check calls of `intersect` that pass a closure or comparator
|xref:programming-languages/groovy/working-with-collections.adoc[Working with Collections]
|===

// Gradle: Groovy 4 and later (groovy-all is a POM-only artifact; add the modules you need individually)

----

  <groupId>org.apache.groovy</groupId>
  <artifactId>groovy-all</artifactId>
  <version>6.0.0</version>
  <type>pom</type>
</dependency>
----

=== Moving to Groovy 5.0

The runtime minimum rises to JDK 11. The notable breaking changes:

[cols="2,4,3",options="header"]
|===
|Change |What to do |Where

|*Duplicate imports are errors*: two imports of the same simple name, or an import and a class with that name, used to
let the last one win
|Remove or alias the duplicates
|xref:programming-languages/groovy/program-structure-packages-imports-and-scripts.adoc[Program Structure, Packages, Imports & Scripts]

|*`java.time` is a default import*, so classes such as `Year`, `Month` and `Duration` in the default package now conflict
|Rename them, move them into a package or alias the import
|xref:programming-languages/groovy/dates-and-times.adoc[Dates & Times]

|*`File` and `Path` truthiness*: a path that does not exist is falsy
|Test `file != null` for "is it set"; `-Dgroovy.truth.file.exists.enabled=false` restores the old behaviour while you port

|xref:programming-languages/groovy/booleans-and-the-groovy-truth.adoc[Booleans & the Groovy Truth]

|*`%` calls `remainder`* instead of `mod`
|Rename an overload named `mod`; the fallback keeps old classes working
|xref:programming-languages/groovy/operator-overloading.adoc[Operator Overloading]

|*Scripts with only a static `main`* no longer extend `Script` (JEP 512 compatibility)
|Turn them into plain scripts or use an instance `run` method
|xref:programming-languages/groovy/running-scripts-and-the-groovy-command.adoc[Running Scripts & the groovy Command]

|*Visibility and property access* tightened for package-private members, anonymous classes and map-like classes; `abstract`/`final`
on an enum is an error; some AST annotations have `SOURCE` retention
|Compile and fix; framework authors should re-test AST transform annotations
|xref:programming-languages/groovy/classes-fields-and-properties.adoc[Classes, Fields & Properties]

|*Iterator extension methods* such as `findIndexValues` and `chop` now return iterators; `chop` stops when the collection is used up
|Add `.toList()` where you need a list
|xref:programming-languages/groovy/working-with-collections.adoc[Working with Collections]

=== Moving to Groovy 5.1

Groovy 5.1 keeps the 5.0 JDK requirements. Its breaking changes are small and security-motivated:

* `deleteDir()` on `File` and `Path` treats symbolic links as leaves instead of following them into their targets. If you
  relied on deleting the contents of a linked directory, resolve the link and delete the target yourself.
* Grape coordinates containing `+..+` sequences are rejected.
* The deprecated `run(JApplet)` method was removed from the Groovy Console so that it loads on JDK 26 and later.

Source: https://groovy-lang.org/releasenotes/groovy-5.1.html[Groovy documentation: Groovy 5.1 release notes]

=== Moving to Groovy 6.0

The runtime minimum rises to JDK 17 (Groovy 6.0 was tested on JDK 17 to 27). The headline breaking changes:

[cols="2,4,3",options="header"]
|===
|Change |What to do |Where

|*Security Manager support removed*: Groovy no longer calls `AccessController.doPrivileged` or uses the related
infrastructure (the Security Manager itself is deprecated for removal in the JDK)
|Stop relying on policy files; restrict scripts with `SecureASTCustomizer` and isolate with containers and the operating system
|xref:programming-languages/groovy/compilation-customizers-and-secure-scripting.adoc[Compilation Customizers & Secure Scripting]

|*The launchers no longer add `.` to a classpath you supply*
|Add `.` yourself (`-cp lib.jar:.`, or `-cp lib.jar;.` on Windows)
|xref:programming-languages/groovy/running-scripts-and-the-groovy-command.adoc[Running Scripts & the groovy Command]

|*Switch: position decides*: a `switch` whose value is used is an expression (an unmatched selector throws
`IllegalStateException`, a missing `default` is an error under static checking); a `switch` whose value is unused is a statement
|Add a `default` arm to expression switches; statement switches behave as in 4.x and 5.x
|xref:programming-languages/groovy/control-structures.adoc[Control Structures]

|*Generic types must be well formed*: generic array creation, a generic class extending `Throwable`, wildcards in
instance creation, primitive type arguments, `+new T()+` and similar constructs that older versions silently erased are compile errors
|Use the workaround shown in the Generics section of the release notes (for example `Array.newInstance` or a raw array)
|xref:programming-languages/groovy/inheritance-interfaces-and-generics.adoc[Inheritance, Interfaces & Generics]

|*`val` is a keyword* (contextual) for final locals
|Rename a field or variable named `val` in the ambiguous positions, or set `-Dgroovy.val.enabled=false` while porting
|xref:programming-languages/groovy/variables-typing-def-var-and-val.adoc[Variables, Typing, def, var & val]

|*`key in map`* tests the key
|Use `map.containsValue(v)` or `v in map.values()` to test values
|xref:programming-languages/groovy/maps.adoc[Maps]

|*A `for-in` loop variable* captured by a closure or lambda has a fresh binding per iteration
|Nothing, unless your code relied on the final value; `-Dgroovy.forin.per.iteration.capture=false` restores the old behaviour
|xref:programming-languages/groovy/closures.adoc[Closures]

|*The classic call-site runtime* moved to the optional `groovy-callsite` module
|Add the module only if you run with `invokedynamic` disabled
|xref:programming-languages/groovy/performance-invokedynamic-and-native-images.adoc[Performance, invokedynamic & Native Images]

|*XML is secure by default*; `GroovyServlet` hides error details; `groovy-sql` rejects GString queries with a quoted dynamic
expression; `JsonSlurper` rejects numbers longer than 1000 characters
|Use the documented opt-out properties only as porting aids
|xref:programming-languages/groovy/xml-parsing-gpath-and-security.adoc[XML Parsing, GPath & Security]

|*String-to-`Class` coercion* no longer initialises the class
|Call `Class.forName(name)` where the static initialiser matters
|xref:programming-languages/groovy/databases-with-groovy-sql.adoc[Databases with Groovy SQL]

|*Method-level `@TypeChecked`/`@CompileStatic`* now overrides a class-level `SKIP`
|Remove the method annotation or give it `SKIP` mode
|xref:programming-languages/groovy/static-type-checking-and-compile-static.adoc[Static Type Checking & @CompileStatic]
|===

==== The classpath dot

A script that loads a class from the working directory while you also pass `-cp` for a library used to work because the
launcher appended the current directory. With 6.0 the classpath you pass is used as is. The demonstration compiles a class

groovy use.groovy                        # no classpath given: falls back to the current directory
groovy -cp /nonexistent-dir use.groovy   # explicit classpath: the current directory is not added
groovy -cp "/nonexistent-dir:." use.groovy
----

SEVERE: Caught: {0}
groovy.lang.MissingPropertyException: No such property: Watering for class: use
...
water at dawn
----

==== Replacing the Security Manager

Setting a Security Manager is not possible on current JDKs, and Groovy 6 no longer cooperates with one. On JDK 26 the call
fails immediately:

[source,groovy]
----
println System.getSecurityManager()
try { System.setSecurityManager(null) } catch (e) { println e.class.name }
----

[source,text]
----
null
java.lang.UnsupportedOperationException
----

For scripts that you do not fully trust, restrict what they may compile with a `SecureASTCustomizer` (and still run them in a
container or an unprivileged operating-system account, because a compile-time allow-list is not a full sandbox):

[source,groovy]
----
import org.codehaus.groovy.control.CompilerConfiguration
import org.codehaus.groovy.control.customizers.SecureASTCustomizer
import org.codehaus.groovy.control.MultipleCompilationErrorsException

def secure = new SecureASTCustomizer()
secure.with {
    // allow-list of receiver types for method calls: System.exit(...) is not on it
    allowedReceiversClasses = [Object, Integer, String, Math]
}
def config = new CompilerConfiguration()
config.addCompilationCustomizers(secure)
def shell = new GroovyShell(config)

println shell.evaluate('Math.max(2, 7)')
try {
    shell.evaluate('System.exit(1)')
} catch (MultipleCompilationErrorsException e) {
    println 'rejected at compile time: ' + e.errorCollector.getError(0).cause.message.readLines().first()
}
----

[source,text]
----
7
rejected at compile time: Method calls not allowed on [java.lang.System]
----

Source: https://groovy-lang.org/security.html[Groovy documentation: Security]
and https://groovy-lang.org/releasenotes/groovy-6.0.html#Groovy6.0-breaking[Groovy 6.0 breaking changes]

==== The switch position rule

Whether a `switch` is a statement or an expression no longer depends on the arrow: it depends on whether the value is used.
A `switch` that ends a method is a statement whose matched value is returned by the implicit `return` (and is `null`
when nothing matches, as in 4.x and 5.x); a `switch` on the right of an assignment is an expression and must be exhaustive:

[source,groovy]
----
def label(int i) {
    switch (i) {
        case 1 -> 'one'
        case 2 -> 'two'
    }
}
println label(1)
println label(9)
def viaExpr = { int i -> def r = switch (i) { case 1 -> 'one'; default -> 'many' }; r }
println viaExpr(7)
try {
    def s = 9
    def r = switch (s) { case 1 -> 'one' }
} catch (IllegalStateException e) { println "expression with no match: ${e.class.simpleName}" }
----

[source,text]
----
one
null
many
expression with no match: IllegalStateException
----

Source: https://groovy-lang.org/releasenotes/groovy-6.0.html#switch-alignment[Groovy documentation: Switch, position decides, not the arrow]

==== Generic syntax

Groovy 4 and 5 accepted generic constructs that Java rejects by quietly treating them as raw types. Groovy 6 applies the Java
rules in every compilation unit, scripts included. The real error for generic array creation:

[source,groovy]
----
List<String>[] buckets = new List<String>[3]
----

[source,text]
----
generics.groovy: 1: generic array creation of List<java.lang.String>
 @ line 1, column 26.
   List<String>[] buckets = new List<String>[3]
                            ^
----

Use a `List<List<String>>` or a raw array with a cast instead. Source:
https://groovy-lang.org/releasenotes/groovy-6.0.html#java-generics[Groovy documentation: Generic type syntax]

==== Two behaviours that change silently

Two 6.0 changes compile and run without any message, so they deserve a test in your suite. The first is the `in` operator
on a map, which now tests keys; the second is the `for-in` capture rule:

[source,groovy]
----
def stock = [basil: 0, mint: 3]
println('basil' in stock)      // key-based since 6.0
println(0 in stock)            // values are no longer tested
println(0 in stock.values())
----

[source,text]
----
true
false
true
----

[source,groovy]
----
def tasks = []
for (crop in ['basil', 'mint', 'sage']) { tasks << { crop } }
println tasks*.call()
----

[source,text]
----
[basil, mint, sage]
----

With `-Dgroovy.forin.per.iteration.capture=false` the same script prints `[sage, sage, sage]`, which is what earlier releases
did (every closure shared one binding).

Source: https://groovy-lang.org/releasenotes/groovy-6.0.html#Groovy6.0-breaking[Groovy documentation: Groovy 6.0 breaking changes]

== Upgrade checklist

. *Pick the target line.* Use the maintained-lines table above; a project on JDK 8 can stay on 4.0, JDK 11 on 5.x, JDK 17 or
  later can take 6.0.
. *Upgrade one major at a time* if you are far behind (3.0, then 4.0, then 5.0, then 6.0): each release-notes page lists the
  breaking changes for that step only.
. *Fix coordinates and imports first.* Switch `org.codehaus.groovy` to `org.apache.groovy`, move legacy packages to
  their `groovy.xml`, `groovy.ant`, `groovy.test` and similar homes, and add any optional module that `groovy-all` no longer includes.
. *Build and run the tests on the new line.* Read compile errors against the tables above; run with the documented porting
  flags only to separate behavioural changes from syntax changes, and remove them afterwards.
. *Check the toolchain.* Gradle, Maven plugins, IDEs, Jenkins and JMeter embed their own Groovy line; see
  xref:programming-languages/groovy/build-tools-gradle-maven-and-ant.adoc[Build Tools: Gradle, Maven & Ant].
. *Re-check tests and frameworks.* Spock publishes one artifact per Groovy line (for example `2.5-groovy-6.0`), see
  xref:programming-languages/groovy/testing-with-spock-and-geb.adoc[Testing with Spock & Geb].
. *Adopt new features gradually.* `var`, `val`, switch expressions, records and `@CompileStatic` are low risk; treat async/await and
  other incubating features as subject to change.

For the Java side of the same questions (language levels, the module system and build tooling) see
xref:programming-languages/java/build-and-tooling.adoc[Java: Build & Tooling] and
xref:programming-languages/java/packages-and-modules.adoc[Java: Packages & Modules].
