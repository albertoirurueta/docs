= Booleans & the Groovy Truth
:description: Groovy boolean literals and the Groovy Truth in depth -- how null, numbers, strings, collections, maps, arrays, matchers, iterators, enumerations, Optional and your own classes are coerced to boolean, customising it with asBoolean(), and the classic pitfalls with 0, empty strings and the Elvis operator.
:keywords: Groovy, boolean, Boolean, true, false, Groovy Truth, truthiness, asBoolean, coercion, null, empty collection, Elvis operator, Matcher, Iterator, Optional, as boolean, find, any, short-circuit

include::partial$groovy-disclaimer.adoc[]

This page is written against Groovy 6.0 (6.0.0, 2026-09-22) and every example was run with Groovy 6.0.0 on JDK 26 on
2026-10-14. Groovy has the `boolean` literals `true` and `false` like Java, but it also lets *any* object stand where
a condition is expected: `if (list)`, `while (line)`, `assert name`, `x ? a : b` and `!value` all apply a set of
coercion rules known as the *Groovy Truth*. The rules are small and uniform, but they are also the source of a few
classic bugs (`0`, `''` and empty collections are all false), so this page lists them exhaustively and shows how to
override them for your own classes. The statements that consume a condition are covered in
xref:programming-languages/groovy/control-structures.adoc[Control Structures]; the operators that produce booleans in
xref:programming-languages/groovy/operators-arithmetic-relational-and-logical.adoc[Operators: Arithmetic, Relational & Logical].

== The boolean literals

Groovy has two boolean literals, `true` and `false`. In dynamic code a `boolean` variable is a `java.lang.Boolean`
at runtime (primitives are boxed when they flow through the dynamic call machinery), and the logical operators `&&`,
`||`, `!` and `+^+` work as in Java. Unlike Java, a `Boolean` may hold `null`, and `&&`/`||` always yield a `boolean`
(never one of their operands).

[source,groovy]
----
boolean open = true
Boolean maybe = null
def done = false

assert open instanceof Boolean          // primitives are boxed in dynamic code
assert !done
assert maybe == null
assert (true && false) == false
assert (true || false)
assert (true ^ true) == false           // exclusive or
assert !(open && !open)
println([open.class.name, true.class.name, (1 < 2).class.name])
----

[source,text]
----
[java.lang.Boolean, java.lang.Boolean, java.lang.Boolean]
----

Source: https://groovy-lang.org/syntax.html#_booleans[Groovy documentation: Syntax, Booleans]

Comparison operators such as `==`, `<` and `!=` produce booleans, and `==` is value equality (it calls `equals` or
`compareTo`) rather than identity; see
xref:programming-languages/groovy/operators-arithmetic-relational-and-logical.adoc[Operators: Arithmetic, Relational & Logical].
For the Java side of this comparison see
xref:programming-languages/java/primitive-types-and-variables.adoc[Java: Primitive Types & Variables].

== The Groovy Truth

When a value that is not already a `Boolean` appears where a condition is expected, Groovy calls the GDK method
`asBoolean()` on it. The same coercion happens for `!x`, for `x as boolean`, for `x ? a : b` and `x ?: y`, in `assert`,
in `if`/`while`/`for` conditions, in `&&`/`||` operands, and when a value is assigned to a `boolean`-typed variable,
parameter or return type. The built-in rules are:

[cols="2,3,3",options="header"]
|===
| Type | True when | False when

| `Boolean` | the value is `true` | `false`, or `null`
| `Collection`, array | it has at least one element | it is empty
| `Map` | it has at least one entry | it is empty
| `CharSequence` (`String`, `GString`, `StringBuilder`) | it is non-empty (a blank string like `' '` is true) | it is empty
| `Number`, `Character` | it is non-zero | it is zero (`0`, `0.0`, `0.00`, `0G`, `(char) 0`)
| `Matcher` | the input contains at least one match | there is no match
| `Iterator`, `Enumeration` | it has more elements | it has no further elements
| `Optional` | a value is present (even `0`) | it is empty
| any other object reference | it is not `null` | it is `null`
|===

image::groovy-truth-by-type.svg["The Groovy Truth by type: false values on the left and similar-looking true values on the right",width=720]

The rules look at the *container*, not at what is inside it, which is why `[0]`, `[null]` and `[a: null]` are all true.
The following script prints the coercion of a representative set of values, using `value as boolean`:

[source,groovy]
----
def samples = [
    'true Boolean'   : true,
    'false Boolean'  : false,
    'null'           : null,
    'empty list'     : [],
    'list [0]'       : [0],
    'empty map'      : [:],
    'map [a: null]'  : [a: null],
    'empty string'   : '',
    'blank string'   : ' ',
    "'false' string" : 'false',
    'int 0'          : 0,
    'double 0.0'     : 0.0,
    'BigDecimal 0.00': 0.00,
    'int -1'         : -1,
    'char 0'         : (char) 0,
    'empty array'    : new int[0],
    'array [0]'      : new int[] {0},
    'no-match Matcher': ('abc' =~ /\d/),
    'match Matcher'  : ('a1' =~ /\d/),
    'empty iterator' : [].iterator(),
    'Optional.empty' : Optional.empty(),
    'Optional.of(0)' : Optional.of(0),
    'new Object()'   : new Object(),
]
samples.each { label, value -> printf('%-18s -> %s%n', label, value as boolean) }
----

=== Collections, arrays and maps

Non-empty collections, arrays and maps are true. Because only the size matters, an element that is itself false does
not change the result.

[source,groovy]
----
assert ![]                  // empty list
assert [0]                  // non-empty list, even though its element is 0
assert [null]
assert ![:]                 // empty map
assert [a: null]
assert !(new int[0])
assert new int[] {0}
assert !([] as Set)
----

Source: https://groovy-lang.org/semantics.html#_collections_and_arrays[Groovy documentation: Semantics, collections and arrays] and https://groovy-lang.org/semantics.html#_maps[maps]

=== Strings and numbers

Any non-empty `CharSequence` is true, including `'false'` and `' '`: Groovy does not parse text, so
`+'false' as boolean+` is `true`. Use `Boolean.valueOf('false')` (or `Boolean.parseBoolean`) when you really have a
textual boolean. Numbers of every type, including `BigDecimal` and `BigInteger`, are false only when they are zero.
`Character` follows the same rule (the NUL character is false).

[source,groovy]
----
assert !''
assert ' '                  // blank but not empty
assert 'false'              // any non-empty text
assert !0
assert 0.1
assert !0.0
assert !(0.0G)
assert !(0G)
assert -1
assert Boolean.valueOf('false') == false
assert ('false' as boolean) // truthy text, not parsed
----

Source: https://groovy-lang.org/semantics.html#_strings[Groovy documentation: Semantics, strings] and https://groovy-lang.org/semantics.html#_numbers[numbers]

=== Matchers, iterators and enumerations

A `Matcher` is true when the input contains at least one match, which is what makes the idiom
`+if (text =~ /pattern/)+` work (see xref:programming-languages/groovy/regular-expressions.adoc[Regular Expressions]).
In Groovy 6.0.0 the test is repeatable: it does not consume the match, so you can test a matcher several times and read
the first match afterwards, and a matcher you have already stepped through with `find()` is true again as long as the
input has any match (the coercion starts again from the beginning).

[source,groovy]
----
def m = 'a1b2' =~ /\d/
assert m.find() && m.group() == '1'
assert m.find() && m.group() == '2'
assert m                    // truth test starts again from the beginning
assert m.group() == '1'
def none = 'abc' =~ /\d/
assert !none
assert none.count == 0
println 'ok'
----

[source,text]
----
ok
----

Iterators and enumerations are true while they still have elements, so they are *consumed* by use, unlike
collections:

[source,groovy]
----
assert [0].iterator()
assert ![].iterator()
Vector<Integer> v = [0] as Vector
Enumeration<Integer> e = v.elements()
assert e
e.nextElement()
assert !e
println 'enumeration ok'
----

[source,text]
----
enumeration ok
----

Source: https://groovy-lang.org/semantics.html#the-groovy-truth[Groovy documentation: Semantics, The Groovy Truth]

=== Optional and other object references

Any object reference that is not `null` is true. The GDK extends that rule for `java.util.Optional`: an empty
`Optional` is false and a present one is true, whatever it holds (`Optional.of(0)` is true). Everything not covered by
a more specific rule, such as `new Object()` or a domain object, is true when it is not `null` and false when it is
`null`.

== Customising the truth with asBoolean()

To change how your own classes are evaluated, implement a no-argument method `boolean asBoolean()`. Groovy calls it
whenever it needs to coerce an instance. The method receives the object as `this`, so it can inspect any state. In the
greenhouse scenario a greenhouse is considered "usable" only when it has a name and at least one reading:

[source,groovy]
----
class Greenhouse {
    String name
    List<Integer> readings = []
    boolean asBoolean() { name && readings }
}
assert !new Greenhouse()
assert !new Greenhouse(name: 'north')
assert new Greenhouse(name: 'north', readings: [21])
def g = new Greenhouse(name: 'north')
if (g) println 'truthy' else println 'no readings yet'
----

[source,text]
----
no readings yet
----

The final expression `name && readings` is itself evaluated with the Groovy Truth, and `&&` returns a
real `boolean`, so the method honours its return type. For a class you do not own, an
xref:programming-languages/groovy/extension-modules.adoc[extension module] or a category from
xref:programming-languages/groovy/metaclasses-expandometaclass-and-categories.adoc[Metaclasses, ExpandoMetaClass & Categories]
can supply `asBoolean()` instead. Groovy also lets you coerce explicitly with `as boolean`, or normalise to a real
`Boolean` with the double negation `!!`:

[source,groovy]
----
assert (0 as boolean) == false
assert ([1] as boolean)
assert 'x'.asBoolean()
assert !(null as boolean)
assert !!'abc' == true
assert ('a' && 'b') == true      // && and || return booleans, not operands
assert ('' || 'z') == true
----

Source: https://groovy-lang.org/semantics.html#the-groovy-truth[Groovy documentation: Semantics, Customizing the truth with asBoolean() methods]

== Static compilation and typed declarations

The truth rules also apply in statically compiled code, so `@CompileStatic` does not force you to write
`!list.isEmpty()`. A `boolean` return type, a `boolean` variable or a parameter coerces its argument with the same
rules, and a `null` is stored as `false`:

[source,groovy]
----
import groovy.transform.CompileStatic

@CompileStatic
class Check {
    static String describe(List<Integer> xs) { xs ? "has ${xs.size()}" : 'empty' }
    static boolean flag(String s) { s }          // implicit truth coercion on return
}
assert Check.describe([]) == 'empty'
assert Check.describe([4]) == 'has 1'
assert Check.flag('x') && !Check.flag('')
boolean primitive = 'text'     // assigned through truth
assert primitive
boolean fromNull = null
assert fromNull == false
println 'ok'
----

[source,text]
----
ok
----

Source: https://groovy-lang.org/semantics.html#the-groovy-truth[Groovy documentation: Semantics, The Groovy Truth] and https://groovy-lang.org/semantics.html#compilestatic-annotation[the @CompileStatic annotation]

More on static checking in
xref:programming-languages/groovy/static-type-checking-and-compile-static.adoc[Static Type Checking & @CompileStatic].

== Pitfalls

=== Falsy but meaningful values

The convenience of the rules is also their danger: a perfectly valid `0`, `0.0`, `''` or empty list is *false*. Three
recurring traps:

* `find` returns the matching element, so when the match is `0`, `''` or `false` the result is found but falsy.
  Use `any`, `contains`, `indexOf` or compare with `null`/`!= -1` when the element itself can be falsy.
* Map values: `if (map.hits)` is false both when the key is missing and when it is `0`. Use `containsKey` to
  distinguish the two.
* Filtering with a bare closure (`findAll`, `+count { it }+`) keeps only truthy values, which silently drops zeros,
  empty strings and `false`.

[source,groovy]
----
def m2 = [:]
m2.hits = 0
assert !m2.hits
assert m2.containsKey('hits')
assert m2.hits == 0
assert [0, 1].find { it == 0 } == 0
assert ![0, 1].find { it == 0 }      // pitfall: found but falsy
assert [0, 1].any { it == 0 }        // use any / contains / indexOf
assert [0, 1].contains(0)
println([0, 1, '', 'a', null, [], [1], false].findAll())
println([0, 1, '', 'a', null, [], [1], false].count { it })
----

[source,text]
----
[1, a, [1]]
3
----

Source: https://groovy-lang.org/semantics.html#the-groovy-truth[Groovy documentation: Semantics, The Groovy Truth]

=== Elvis operator versus truthiness

The Elvis operator `?:` tests its left operand with the Groovy Truth, not with `!= null`. That makes it a good default
for "missing or empty" strings and collections, and a bug for numbers where `0` is a legitimate value. When only
`null` should trigger the default, use an explicit ternary or the null-safe tools from
xref:programming-languages/groovy/object-operators.adoc[Object Operators].

[source,groovy]
----
def temp = 0
def shown = temp ?: 20
assert shown == 20          // 0 is false, so Elvis replaces a legitimate 0
def shown2 = temp != null ? temp : 20
assert shown2 == 0
String label = ''
assert (label ?: 'unnamed') == 'unnamed'
assert ([] ? 'full' : 'empty') == 'empty'
Boolean flag = null
assert !flag
assert flag != false         // null is falsy but not equal to false
def list = null
assert (list?.size() ?: 0) == 0
----

Source: https://groovy-lang.org/operators.html#_elvis_operator[Groovy documentation: Operators, Elvis operator]

The last two lines show the usual split: `flag != false` shows that a `null` `Boolean` is not `false` for
equality, while the null-safe `?.` combined with `?:` provides a default size of zero. See also
xref:programming-languages/groovy/optionality.adoc[Optionality].

=== Other points to remember

* `x == true` is almost never what you want: `'abc' == true` is `false` even though `'abc'` is true. Write `if (x)`
  or `x as boolean`.
* A `Boolean` field holding `null` is falsy in conditions, so unlike Java it does not throw a `NullPointerException`
  when unboxed in `if (flag)`.
* Properties of type `boolean` are declared like any other; see
  xref:programming-languages/groovy/classes-fields-and-properties.adoc[Classes, Fields & Properties].
* Assertions use the same rules, so `assert list` fails for an empty list; see
  xref:programming-languages/groovy/assertions-and-power-assert.adoc[Assertions & Power Assert].

== Where the book is outdated

The book consulted for this section (see the section bibliography) describes the Groovy Truth as it stood in the 1.x
era. Treat its rule list as a starting point only: the official documentation page referenced below is the current,
versioned list, and the GDK adds coercions for types the book does not mention, such as `Optional`. Always confirm a
surprising case by running `value as boolean` in
xref:programming-languages/groovy/groovysh-and-groovyconsole.adoc[groovysh], as the examples above do.
