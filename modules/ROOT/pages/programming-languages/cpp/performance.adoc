== The Zero-Overhead Principle

Stroustrup's founding design rule for {cpp}: a feature you don't use costs you nothing, and a feature you do use
should cost no more than writing the equivalent by hand. Classes, templates, and exceptions (when not thrown)
compile down to code as fast as the hand-written C equivalent -- the abstraction is "free" at run time, paid
only in compile time and, for virtual functions, one pointer indirection (see
xref:programming-languages/cpp/inheritance-and-polymorphism.adoc[Inheritance and Polymorphism]).

== Measure Before Optimizing

Intuition about where time is spent is frequently wrong -- profile first, always:

[source,shell]
----
perf record ./myprogram
perf report

# or, for a quick wall-clock A/B comparison without a full profiler:
g++ -O2 -o bench bench.cpp && time ./bench
----

Optimizing code that isn't actually the bottleneck wastes effort and adds complexity/risk for zero measured
benefit -- the classic "premature optimization" trap.

== Avoiding Copies

Covered mechanically in xref:programming-languages/cpp/move-semantics-and-value-categories.adoc[Move Semantics
and Value Categories] and xref:programming-languages/cpp/strings-and-text.adoc[Strings and Text]/
xref:programming-languages/cpp/containers.adoc[Containers]; as a checklist:

[source,cpp]
----
#include <string>
#include <string_view>
#include <span>
#include <vector>

void takesByValue(std::string s);              // copies (or moves, if the caller passes an rvalue)
void takesByConstRef(const std::string& s);      // never copies
void takesByView(std::string_view s);             // never copies, works on literals/substrings too

void takesVectorByConstRef(const std::vector<int>& v);   // never copies
void takesSpan(std::span<const int> v);                    // never copies, ALSO works on C arrays/std::array
----

Default to `const T&`/`std::string_view`/`std::span` for read-only parameters; reserve by-value parameters for
when the function genuinely needs its own copy (and let move semantics make even that cheap for an rvalue
argument).

== Reserving and Contiguous Containers

[source,cpp]
----
#include <vector>

std::vector<int> withoutReserve;
for (int i = 0; i < 10000; ++i) withoutReserve.push_back(i);   // may reallocate (and copy/move existing
                                                                   // elements) roughly log2(10000) times

std::vector<int> withReserve;
withReserve.reserve(10000);                                       // one allocation, up front
for (int i = 0; i < 10000; ++i) withReserve.push_back(i);           // zero reallocations
----

Prefer `std::vector`/`std::array` (contiguous, cache-friendly) over `std::list`/`std::map` unless a specific
access pattern (frequent middle insertion, ordered keys) genuinely needs them -- see
xref:programming-languages/cpp/containers.adoc[Containers]'s decision chart.

== `constexpr` Evaluation

Moving work from run time to compile time (see
xref:programming-languages/cpp/compile-time-programming.adoc[Compile-Time Programming]) trades compile time for
zero run-time cost -- most valuable for values that are genuinely fixed at compile time (lookup tables, fixed
configuration), not for anything depending on run-time input.

== Inlining and `+[[likely]]+`

The compiler already inlines small, hot functions automatically at `-O2`/`-O3` -- `inline` today is mostly
about the ODR exception for header-defined functions (see
xref:programming-languages/cpp/program-structure-and-compilation.adoc[Program Structure and Compilation]), not a
performance directive the compiler is obligated to follow. `+[[likely]]+`/`+[[unlikely]]+` (see
xref:programming-languages/cpp/control-flow.adoc[Control Flow]) are the same: hints, not guarantees -- both are
only worth adding once profiling shows a specific branch matters.

== Allocation Strategies

Heap allocation (`new`, `std::vector` growth, `std::string` beyond its Small String Optimization threshold) is
one of the more expensive common operations in {cpp}. Beyond `reserve()`:

[source,cpp]
----
#include <memory_resource>
#include <array>
#include <vector>

std::array<std::byte, 4096> stackBuffer{};
std::pmr::monotonic_buffer_resource pool(stackBuffer.data(), stackBuffer.size());
std::pmr::vector<int> fastVector(&pool);   // allocates from stackBuffer, not the heap, until exhausted
----

See xref:programming-languages/cpp/memory-management-and-smart-pointers.adoc[Memory Management and Smart
Pointers] for `std::pmr` in more depth; object pools and arena allocators follow the same idea for
higher-throughput allocation patterns.

== Undefined Behavior and the Optimizer

The optimizer is *allowed to assume* undefined behavior never happens, and will silently produce surprising
(not necessarily "safe-looking") code when it does:

[source,cpp]
----
int dangerous(int x) {
    return x + 1 > x;    // the compiler may assume signed overflow (UB) never happens, and optimize this
}                          // to "return true;" unconditionally -- NOT to "check whether x+1 actually overflowed"
----

This is why `-Wall -Wextra` alone does not catch every UB-adjacent bug, and why sanitizers (below) exist as a
complementary, run-time-checking layer.

== Profiling and Sanitizers

[source,shell]
----
# AddressSanitizer: catches heap/stack buffer overflows, use-after-free, use-after-return
g++ -fsanitize=address -g -o app app.cpp && ./app

# UndefinedBehaviorSanitizer: catches signed overflow, null derefs, misaligned access, and more
g++ -fsanitize=undefined -g -o app app.cpp && ./app

# ThreadSanitizer: catches data races
g++ -fsanitize=thread -g -o app app.cpp && ./app
----

Sanitizers add significant run-time overhead (2-20x, depending on which one) -- run them in CI/testing, not in
production; see xref:programming-languages/cpp/build-and-tooling.adoc[Build and Tooling] for how they fit into a
project's build configuration.

== Measuring Instead of Guessing

Performance advice is only useful with numbers. Wall-clock timings vary between machines, so the examples here count
*events that are deterministic* (heap allocations, instructions a sanitizer reports) and describe how to time the
rest. The baseline rule stays: write clear code, measure it with a profiler on realistic data, then change the
slowest thing.

[mermaid]
....
flowchart LR
    W["write clear code"] --> B["build with optimization<br/>-O2, release flags"]
    B --> M["measure on realistic data<br/>profiler or benchmark"]
    M --> H{"hot spot<br/>found?"}
    H -->|"no: fast enough"| D["stop"]
    H -->|"yes"| C["change ONE thing:<br/>algorithm, data layout, allocation"]
    C --> M
....

=== Counting allocations

Heap allocation is usually the first cost worth removing from a loop. Replacing the global `operator new` with a
counting version makes the allocations of every standard container visible:

.alloc.cpp
[source,cpp]
----
#include <cstdlib>
#include <new>
#include <print>
#include <string>
#include <vector>

static int g_allocs = 0;
void* operator new(std::size_t n) {
    ++g_allocs;
    if (void* p = std::malloc(n)) return p;
    throw std::bad_alloc();
}
void operator delete(void* p) noexcept { std::free(p); }
void operator delete(void* p, std::size_t) noexcept { std::free(p); }

struct Book { std::string title; };

int count_allocs(auto&& f) {
    int before = g_allocs;
    f();
    return g_allocs - before;
}

int main() {
    std::println("push_back 100 ints, no reserve: {} allocations", count_allocs([] {
        std::vector<int> v;
        for (int i = 0; i < 100; ++i) v.push_back(i);
    }));
    std::println("push_back 100 ints, reserve(100): {} allocation", count_allocs([] {
        std::vector<int> v;
        v.reserve(100);
        for (int i = 0; i < 100; ++i) v.push_back(i);
    }));

    std::vector<Book> shelf;
    shelf.reserve(10);
    std::string long_title(64, 'x');
    std::println("push_back(copy of a long title): {} allocation(s)", count_allocs([&] { shelf.push_back(Book{long_title}); }));
    std::println("push_back(std::move(title)): {} allocation(s)", count_allocs([&] { shelf.push_back(Book{std::move(long_title)}); }));
    std::println("short string (fits in SSO): {} allocation(s)", count_allocs([] { std::string s("Dune"); }));
    std::println("long string: {} allocation(s)", count_allocs([] { std::string s(100, 'x'); }));
}
----

[source,console]
----
$ clang++ -std=c++23 -Wall -Wextra alloc.cpp -o alloc
$ ./alloc
push_back 100 ints, no reserve: 8 allocations
push_back 100 ints, reserve(100): 1 allocation
push_back(copy of a long title): 1 allocation(s)
push_back(std::move(title)): 0 allocation(s)
short string (fits in SSO): 0 allocation(s)
long string: 1 allocation(s)
----

* `push_back` without `reserve` triggers a reallocation each time the capacity is exhausted: 8 allocations for 100
  elements (capacities 1, 2, 4, 8, 16, 32, 64, 128). `reserve(100)` does it once. When the size is known or
  bounded, reserve.
* Copying a 64-character title allocates a new buffer for the copy; moving it allocates nothing. Passing `std::move`
  where the source is not needed again is a free optimization (see
  xref:programming-languages/cpp/move-semantics-and-value-categories.adoc[Move Semantics and Value Categories]).
* The `Dune` string needs no allocation because of the small string optimization, while the 100-character one does.
  Strings shorter than about 22 characters on this library never touch the heap.

=== The optimizer assumes your program has no undefined behaviour

Because signed overflow is undefined, the compiler may treat `pass:c[a + 1 > a]` as always true. The function lives in its
own file so the optimizer cannot see the caller:

.ub_lib.cpp
[source,cpp]
----
// compiled separately so the optimizer sees only this function
bool always_greater(int a) { return a + 1 > a; }   // true unless a + 1 overflows -- which is UB, so "always true"
----

.ub_main.cpp
[source,cpp]
----
#include <climits>
#include <print>
bool always_greater(int a);
int main() { std::println("always_greater(INT_MAX) = {}", always_greater(INT_MAX)); }
----

[source,console]
----
$ clang++ -std=c++23 -O0 ub_lib.cpp ub_main.cpp -o ub0 && ./ub0
always_greater(INT_MAX) = false
----

[source,console]
----
$ clang++ -std=c++23 -O2 ub_lib.cpp ub_main.cpp -o ub2 && ./ub2
always_greater(INT_MAX) = true
----

The same source gives different answers at different optimization levels, because at `-O0` the addition wraps to
`INT_MIN` and the comparison is false, and at `-O2` the compiler is entitled to fold the whole function to `true`.
Neither is "wrong": the program was already invalid. This is the reason to run tests with UndefinedBehaviorSanitizer,
which reports the overflow at the source line:

.ubsan.cpp
[source,cpp]
----
#include <climits>
#include <print>
int main() {
    volatile int a = INT_MAX;
    std::println("{}", a + 1);   // signed overflow
}
----

[source,console]
----
$ clang++ -std=c++23 -fsanitize=undefined ubsan.cpp -o ubsan && ./ubsan 2>&1 | sed 's#/private[^ ]*/##'
ubsan.cpp:5:26: runtime error: signed integer overflow: 2147483647 + 1 cannot be represented in type 'int'
SUMMARY: UndefinedBehaviorSanitizer: undefined-behavior ubsan.cpp:5:26 
-2147483648
----

=== Sanitizers and profilers

AddressSanitizer catches out-of-bounds and use-after-free errors. `operator[]` on a `std::vector` is not bounds
checked, so this program reads past the end:

.oob.cpp
[source,cpp]
----
#include <vector>
#include <print>
int main() {
    std::vector<int> copies{1, 2, 3};
    int i = 3;                                   // one past the end
    std::println("copies[3] = {}", copies[i]);   // operator[] does not check bounds: undefined behaviour
}
----

[source,console]
----
$ clang++ -std=c++23 -g -fsanitize=address oob.cpp -o oob && ./oob 2>&1 | grep -E 'ERROR: AddressSanitizer' | sed -E 's/==[0-9]+==//; s/ on address.*//'
ERROR: AddressSanitizer: heap-buffer-overflow
----

Use `-fsanitize=address,undefined` in debug and CI builds, `-fsanitize=thread` for concurrent code (it cannot be
combined with AddressSanitizer), and a sampling profiler (`perf` on Linux, Instruments on macOS, Visual Studio's
profiler on Windows) on the *optimized* binary with debug symbols (`-O2 -g`) to find where time goes. Profile the
program you ship: a profile of a `-O0` build points at the wrong functions.
