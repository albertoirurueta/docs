== Operator Precedence and Associativity

{cpp} has around 40 operators across roughly 18 precedence levels (the full table is at cppreference, linked
below); the ones that most often surprise newcomers:

[source,cpp]
----
int a = 2 + 3 * 4;          // 14, not 20 -- * binds tighter than +
bool b = 1 < 2 == true;     // ((1 < 2) == true) -- relational binds tighter than equality
int c = 1 << 2 + 1;         // 1 << (2 + 1) == 8 -- shift binds LOOSER than + (a frequent surprise)
----

When in doubt, add parentheses -- they cost nothing at run time and remove any ambiguity for the reader.

== Value Categories

Every {cpp} expression is exactly one of three value categories, which govern whether it can be moved from and
whether its address can be taken:

* **lvalue** -- has identity, cannot (in general) be moved from implicitly: a named variable, `+*ptr+`, `arr[i]`.
* **prvalue** ("pure rvalue") -- has no identity, is the initializer of the object it produces: a literal, the
  result of `pass:c[a + b]`, a temporary from a by-value return.
* **xvalue** ("eXpiring value") -- has identity *and* may be moved from: the result of `std::move(x)`, or a
  function returning `T&&`.

[source,cpp]
----
int x = 5;
int& lref = x;              // x is an lvalue -- binds to int&
int&& rref = 5;              // 5 is a prvalue -- binds to int&&
int&& rref2 = std::move(x);  // std::move(x) is an xvalue -- also binds to int&&
----

lvalues and xvalues are jointly called **glvalues** ("generalized lvalues"); prvalues and xvalues are jointly
**rvalues**. See xref:programming-languages/cpp/move-semantics-and-value-categories.adoc[Move Semantics and Value
Categories] for how this drives overload resolution between copy and move.

== Sequencing

Since {cpp}17, most compound expressions with two operands have a guaranteed evaluation order, which fixed
several pre-{cpp}17 undefined-behavior traps. The order depends on the operator: in a simple assignment the
*right* operand is sequenced before the left one, while `<<`/`>>` chains and function-call
argument-to-callee sequencing run left-to-right:

[source,cpp]
----
#include <vector>

int main() {
    std::vector<int> v = {1, 2, 3};
    int i = 0;
    v[i] = i++;             // well-defined since C++17: the right operand (i++) is sequenced before the left
                            // one, so i++ yields 0 and leaves i == 1 -- the write lands on v[1], not v[0]
    return v[1];             // deterministically 0; v[0] is untouched and still 1
}
----

Function *argument* evaluation order relative to *other arguments* is still unspecified, though -- `f(g(), h())`
may call `h()` before `g()`; do not rely on the order.

== Integer Promotions

Before most arithmetic/comparison operators run, small integer types (`bool`, `char`, `short`, and unscoped
enums) are **promoted** to `int` (or `unsigned int` if `int` cannot hold every value):

[source,cpp]
----
char a = 100, b = 100;
int result = a + b;         // both promoted to int first: 200, not a char overflow
static_assert(sizeof(a + b) == sizeof(int));
----

== `+<=>+`: Three-Way Comparison

The **spaceship operator** ({cpp}20) returns an ordering category and lets the compiler synthesize the other five
relational operators from one function:

[source,cpp]
----
#include <compare>

struct Version {
    int major, minor, patch;
    auto operator<=>(const Version&) const = default;   // defaults to lexicographic member-wise comparison
};

static_assert(Version{1, 2, 0} < Version{1, 3, 0});
static_assert(Version{2, 0, 0} > Version{1, 9, 9});
static_assert(Version{1, 0, 0} == Version{1, 0, 0});
----

See xref:programming-languages/cpp/operator-overloading-and-conversions.adoc[Operator Overloading and Conversions]
for hand-written (non-defaulted) `+<=>+` and the three ordering categories it can return.

== Safe Integer Comparison: `std::cmp_less` and Friends

Comparing a signed and an unsigned integer directly is a classic bug source: the signed value converts to
unsigned first, so `-1 < 1u` is `false`. {cpp}20's `<utility>` comparison functions compare the *mathematical*
values instead:

[source,cpp]
----
#include <utility>
#include <cassert>

int main() {
    int signedValue = -1;
    unsigned unsignedValue = 1;

    assert((signedValue < unsignedValue) == false);          // the classic pitfall: -1 wraps to a huge unsigned
    assert(std::cmp_less(signedValue, unsignedValue) == true); // std::cmp_less compares the real values: -1 < 1
    return 0;
}
----

`std::cmp_equal`, `std::cmp_less`, `std::cmp_greater`, `std::cmp_less_equal`, `std::cmp_greater_equal`, and
`std::in_range<T>(value)` round out the set.

== Bit Manipulation

[source,cpp]
----
#include <bit>
#include <cstdint>
#include <cassert>

int main() {
    uint32_t x = 0b0000'0000'0000'0000'0000'0000'0010'1100;
    assert(std::popcount(x) == 3);          // number of set bits (C++20)
    assert(std::has_single_bit(8u));         // is x a power of two?
    assert(std::bit_width(8u) == 4);          // bits needed to represent x
    uint32_t rotated = std::rotl(x, 4);       // rotate left (C++20)
    (void)rotated;

    uint32_t y = 5;
    y |= (1u << 3);      // set bit 3
    y &= ~(1u << 0);     // clear bit 0
    y ^= (1u << 1);      // toggle bit 1
    (void)y;
    return 0;
}
----

== Precedence, Sequencing and Comparison, Run Through the Compiler

Operators are where {cpp} inherits the most from C, including its sharpest edges. The program below demonstrates the
ones that matter in practice, with the inventory domain supplying the types. It builds with `-Wno-parentheses` only
so that the deliberately wrong line does not flood the page with notes; without that flag the compiler flags it.

.ops.cpp
[source,cpp]
----
#include <compare>
#include <cstdint>
#include <print>
#include <string>
#include <type_traits>
#include <utility>

struct Version {
    int major, minor;
    auto operator<=>(const Version&) const = default;   // also generates ==
};

int next() {
    static int n = 0;
    return ++n;
}

int main() {
    // Precedence trap: == binds tighter than &, so the flag test needs parentheses.
    unsigned flags = 0b100;
    bool wrong = flags & 0b100 == 0b100;     // parsed as flags & (0b100 == 0b100) -> flags & 1
    bool right = (flags & 0b100) == 0b100;
    std::println("without parentheses: {}, with: {}", wrong, right);

    // Sequencing: since C++17 the right operand of << is sequenced after the left, and arguments
    // of one call are indeterminately sequenced.
    std::string s = "inventory";
    s.replace(0, 1, "I").append("!");
    std::println("{}", s);

    // Integer promotion: uint8_t operands become int before the operation.
    std::uint8_t a = 200, b = 100;
    auto sum = a + b;
    std::uint8_t narrowed = static_cast<std::uint8_t>(a + b);
    std::println("200 + 100 = {} (int), narrowed to uint8_t = {}", sum, narrowed);

    // Three-way comparison: all six operators from one defaulted function.
    Version v1{1, 4}, v2{1, 10};
    std::println("v1 < v2: {}  v1 == v2: {}  v1 != v2: {}", v1 < v2, v1 == v2, v1 != v2);
    auto order = v1 <=> v2;
    std::println("is less: {}", order == std::strong_ordering::less);

    // Safe integer comparison.
    int minus = -1;
    unsigned big = 4'000'000'000u;
    std::println("-1 < 4e9u (built-in): {}  std::cmp_less: {}", minus < big, std::cmp_less(minus, big));

    // Value categories seen through decltype.
    int x = 5;
    static_assert(std::is_same_v<decltype((x)), int&>);       // (x) is an lvalue expression
    static_assert(std::is_same_v<decltype(x + 1), int>);       // x + 1 is a prvalue
    static_assert(std::is_same_v<decltype(std::move(x)), int&&>);   // std::move(x) is an xvalue
    std::println("value category checks passed at compile time");

    // The built-in comma operator sequences its operands left to right (function arguments are not).
    std::println("call counter reached {}", (next(), next(), next()));
}
----

=== Value categories

Every expression has a type *and* a value category, and the category decides what you may do with it: bind it to a
reference, move from it, take its address.

[mermaid]
....
flowchart TB
    E["expression"] --> GL["glvalue<br/>has an identity (a location)"]
    E --> R["rvalue<br/>can be moved from"]
    GL --> L["lvalue<br/>x, *p, a[i], a string literal"]
    GL --> X["xvalue<br/>std::move(x), static_cast of T to T&amp;&amp;"]
    R --> X
    R --> P["prvalue<br/>42, x + 1, a call returning T by value"]
....

The three `static_assert` lines in the program ask the compiler which category it assigned: `decltype((x))` is `int&`
(an lvalue), `pass:c[decltype(x + 1)]` is `int` (a prvalue) and `decltype(std::move(x))` is `int&&` (an xvalue). The
parentheses in `decltype((x))` matter: `decltype(x)` names the declared type, `decltype((x))` examines the
expression. Value categories are the foundation of
xref:programming-languages/cpp/move-semantics-and-value-categories.adoc[Move Semantics and Value Categories].

=== What the output teaches

* `flags & 0b100 == 0b100` evaluates `0b100 == 0b100` first (comparison binds tighter than bitwise `&`), producing
  `flags & 1`, which is zero for the value `0b100`. Always parenthesize a mask test.
* Since {cpp}17, `a << b`, `a >> b`, `a = b`, `a[b]` and `a.f(b)` evaluate the left operand before the right one.
  Function *arguments*, however, are still evaluated in an unspecified order: `f(next(), next())` may call either
  `next()` first. An expression that modifies and reads the same scalar without sequencing, such as `pass:c[i++ + i]`,
  is undefined behaviour.
* `uint8_t` operands are promoted to `int` before the addition, so `pass:c[200 + 100]` is `300`, and only the explicit
  cast produces the wrapped `44`.
* `+operator<=>+` defaulted with `= default` generates `==` too, comparing members in declaration order. Put the
  most significant member first.
