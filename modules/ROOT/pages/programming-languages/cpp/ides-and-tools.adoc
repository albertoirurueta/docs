== What an IDE Does With Your Code

A {cpp} IDE or editor is mostly a front end for four separate programs, and knowing which one is responsible makes
configuration problems much easier to diagnose. Code completion, go-to-definition and inline diagnostics come from a
*language server* or the IDE's own parser; building comes from the compiler driven by a *build system*; stepping
through code comes from a *debugger*; and style and bug-pattern warnings come from *static analysis tools*.

[mermaid]
....
flowchart LR
    IDE["IDE or editor<br/>(CLion, VS Code, Xcode, ...)"]
    LS["language server / indexer<br/>(clangd or built-in parser)"]
    BS["build system<br/>(CMake, Make, MSBuild, Xcode)"]
    CC["compiler<br/>(clang++, g++, MSVC)"]
    DBG["debugger<br/>(lldb, gdb, MSVC debugger)"]
    CDB[("compile_commands.json")]
    IDE --> LS
    IDE --> BS
    IDE --> DBG
    BS --> CC
    BS -->|"exports"| CDB
    CDB -->|"flags per file"| LS
    CC -->|"binary with debug info"| DBG
....

The piece that most often breaks is the arrow from the build system to the language server. {cpp} source cannot be
parsed correctly without the exact flags it is compiled with: the `-std=` level, the `-I` include directories and
the `-D` macros all change what a file means. Tools therefore read a *compilation database*,
`compile_commands.json`, which records one compiler command per source file. You can see the raw material with
clang's `-MJ` flag, which writes one database entry while compiling:

[source,console]
----
$ clang++ -std=c++23 -c inventory0.cpp -o /dev/null -MJ cc.json && tr ',' '\n' < cc.json | sed 's#/private[^"]*/src#/project#' | head -8
{ "directory": "/project"
 "file": "inventory0.cpp"
 "output": "/dev/null"
 "arguments": ["/Applications/Xcode.app/Contents/Developer/Toolchains/XcodeDefault.xctoolchain/usr/bin/clang"
 "-xc++"
 "inventory0.cpp"
 "-o"
 "/dev/null"
----

If completion in an editor shows false errors such as "file not found" on a header that builds fine, the editor is
almost always parsing without the flags above. Generate the database (CMake does it with
`-DCMAKE_EXPORT_COMPILE_COMMANDS=ON`, see xref:programming-languages/cpp/build-and-tooling.adoc[Build and Tooling])
and point the tool at it.

=== Picking a setup

[cols="1,2,2"]
|===
|If you... |A reasonable choice |Why

|work on Windows with MSVC
|Visual Studio
|Best integration with the MSVC toolchain and debugger.

|work across Linux, macOS and Windows with CMake
|CLion, or VS Code with the C/{cpp} or clangd extension
|Both read CMake projects and the compilation database directly.

|target Apple platforms
|Xcode
|Required for signing, simulators and Instruments profiling.

|build Qt applications
|Qt Creator
|Understands Qt's `moc`, resources and designer files.

|work over SSH or in containers
|VS Code remote, or a terminal editor with clangd
|The language server runs next to the code and the compiler.
|===

Whatever the editor, keep the build reproducible from a terminal: the same `cmake --build` command that the IDE
runs should work in CI, because the IDE project files are rarely the source of truth.
