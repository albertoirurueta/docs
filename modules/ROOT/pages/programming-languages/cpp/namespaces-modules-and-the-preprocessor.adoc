== Namespaces

A **namespace** groups related names and avoids collisions between libraries:

[source,cpp]
----
namespace geometry {
    struct Point { double x, y; };
    double distance(Point a, Point b);
}

geometry::Point p{1.0, 2.0};   // fully qualified
----

== Unnamed and Inline Namespaces

An **unnamed namespace** gives its contents internal linkage (see
xref:programming-languages/cpp/program-structure-and-compilation.adoc[Program Structure and Compilation]); an
**inline namespace** ({cpp}11) makes its contents visible as if they were in the enclosing namespace, used mainly
for versioning a library's ABI:

[source,cpp]
----
namespace mylib {
    inline namespace v2 {          // "inline": mylib::Widget resolves to mylib::v2::Widget transparently
        struct Widget { int id; };
    }
    namespace v1 {                  // still reachable explicitly for old callers: mylib::v1::Widget
        struct Widget { int id; };
    }
}

mylib::Widget w{1};                 // resolves to mylib::v2::Widget -- the current version
mylib::v1::Widget legacy{1};         // still available, explicitly
----

== `using`-Declarations and `using`-Directives

[source,cpp]
----
#include <string>

using std::string;                // using-declaration: brings ONE name into scope
// using namespace std;           // using-directive: brings EVERY name in std:: into scope -- avoid at
                                    // namespace/global scope in headers; it leaks into every includer

void demo() {
    using namespace std::literals;   // fine in a narrow local scope, like a function body
    auto s = "hi"s;
    (void)s;
}
string greeting = "hello";
----

== Argument-Dependent Lookup (ADL)

**ADL** ("Koenig lookup") finds a free function based on the *namespace of its arguments*, even without
qualification or a `using`-declaration -- it's why `std::swap(a, b)` usually isn't needed and plain `swap(a,
b)` (found via ADL if `a`/`b`&#39;s type defines its own `swap` in its own namespace) works, and it's the entire
mechanism behind range-`for`&#39;s unqualified `begin(x)`/`end(x)` calls:

[source,cpp]
----
namespace geometry {
    struct Point { double x, y; };
    void describe(Point p) { /* ... */ }   // found via ADL below, with no "geometry::" prefix needed
}

void demo() {
    geometry::Point p{1, 2};
    describe(p);       // ADL finds geometry::describe because p's type lives in namespace geometry
}
----

== The Preprocessor

[source,cpp]
----
#define MAX_SIZE 100                 // object-like macro
#define SQUARE(x) ((x) * (x))         // function-like macro -- parenthesize every use of x, and the whole result

#if defined(_WIN32)
    #define PLATFORM "Windows"
#elif defined(__linux__)
    #define PLATFORM "Linux"
#else
    #define PLATFORM "Unknown"
#endif

#define STRINGIFY(x) #x                    // stringification: STRINGIFY(hello) -> "hello"
#define CONCAT(a, b) a##b                   // concatenation: CONCAT(foo, bar) -> foobar

#define LOG(fmt, ...) printf(fmt __VA_OPT__(,) __VA_ARGS__)   // C++20: __VA_OPT__(,) inserts the comma ONLY
                                                                 // if variadic arguments were actually passed,
                                                                 // avoiding LOG("no args") producing "fmt,"
----

Prefer `constexpr`/`inline`/templates over macros wherever possible -- macros have no scope, no type checking,
and are invisible to the debugger; they remain necessary mainly for conditional compilation and
stringification/concatenation, which no other {cpp} feature replaces.

== Modules and Module Partitions

Module basics were introduced in
xref:programming-languages/cpp/program-structure-and-compilation.adoc[Program Structure and Compilation]. A
module can be split into **partitions** -- internal pieces assembled into one logical module, useful for
organizing a large module's implementation across multiple files:

[source,cpp]
----
// math-basics.cppm -- a module partition (note the colon)
export module math:basics;

export int add(int a, int b) { return a + b; }
----

[source,cpp]
----
// math.cppm -- the primary module interface, importing and re-exporting its partitions
export module math;
export import :basics;

export int addTwice(int a, int b) { return add(a, b) * 2; }
----

== Feature-Test Macros and `<version>`

Feature-test macros let code check, at preprocessing time, whether a given language/library feature is
available -- essential for code that must build across multiple compiler versions:

[source,cpp]
----
#include <version>

#if __cpp_lib_expected >= 202202L
    #include <expected>
    // use std::expected
#else
    // fall back to a manual error-code/variant-based approach
#endif

#if defined(__cpp_concepts) && __cpp_concepts >= 201907L
    // concepts are available
#endif
----

`<version>` centralizes every standard-library feature-test macro in one header, rather than requiring the
actual feature header to be included just to test for its presence.

== Name Lookup, ADL, Inline Namespaces and Macros in One Program

Namespaces group names and prevent collisions, but the part that surprises people is *how* an unqualified name is
looked up. For a function call the compiler searches the usual scopes and, in addition, the namespaces of the
argument types. This is *argument-dependent lookup* (ADL), and it is why `print(b)` finds `lib::print` and
`std::cout << b` finds `lib::operator<<` without any `using`.

[mermaid]
....
flowchart TB
    CALL["print(b)   with b of type lib::Book"] --> ORD["ordinary unqualified lookup<br/>block, class, enclosing namespaces,<br/>using-declarations"]
    CALL --> ADL["ADL: associated namespaces of the argument types<br/>lib (from lib::Book)"]
    ORD --> SET["candidate set = union of both"]
    ADL --> SET
    SET --> OR["overload resolution picks the best match"]
    OR --> RES["lib::print(const Book&amp;)"]
....

.ns.cpp
[source,cpp]
----
#include <algorithm>
#include <iostream>
#include <print>
#include <string>
#include <vector>

namespace lib {

struct Book { std::string title; };

// Found by ADL: because the argument is lib::Book, unqualified `swap`/`print` finds these.
void print(const Book& b) { std::println("lib::print: {}", b.title); }
std::ostream& operator<<(std::ostream& os, const Book& b) { return os << "<" << b.title << ">"; }

inline namespace v2 {            // the current API version; callers write lib::describe
    std::string describe(const Book& b) { return "v2:" + b.title; }
}
namespace v1 {                    // old version still reachable as lib::v1::describe
    std::string describe(const Book& b) { return "v1:" + b.title; }
}

namespace {                       // unnamed: internal linkage, private to this file
    int counter = 0;
}
int next_id() { return ++counter; }

}  // namespace lib

namespace other { void print(int n) { std::println("other::print: {}", n); } }

// Macro pitfalls: no scope, no types, textual substitution.
#define SQUARE(x) x * x
#define SQUARE_OK(x) ((x) * (x))

#ifndef FEATURE_LEVEL
#define FEATURE_LEVEL 2
#endif

int main() {
    lib::Book b{"Dune"};
    print(b);                        // no lib:: needed: ADL looks in the namespace of the argument
    std::cout << b << "\n";          // operator<< found by ADL as well
    std::println("{} {}", lib::describe(b), lib::v1::describe(b));
    std::println("ids: {} {}", lib::next_id(), lib::next_id());

    using other::print;              // using-declaration: also considers other::print
    print(7);
    print(b);                        // still picks lib::print: better match

    int n = 3;
    std::println("SQUARE(n + 1) = {}, SQUARE_OK(n + 1) = {}", SQUARE(n + 1), SQUARE_OK(n + 1));
#if FEATURE_LEVEL >= 2
    std::println("feature level 2 enabled");
#else
    std::println("feature level below 2");
#endif
    std::println("__cplusplus = {}, __cpp_concepts = {}", __cplusplus, __cpp_concepts);
}
----

[source,console]
----
$ clang++ -std=c++23 -Wall -Wextra ns.cpp -o ns
$ ./ns
lib::print: Dune
<Dune>
v2:Dune v1:Dune
ids: 1 2
other::print: 7
lib::print: Dune
SQUARE(n + 1) = 7, SQUARE_OK(n + 1) = 16
feature level 2 enabled
__cplusplus = 202302, __cpp_concepts = 202002
----

* `print(b)` compiles without `lib::` because of ADL. After `using other::print;`, the call `print(7)` finds
  `other::print` through the using-declaration, and `print(b)` still resolves to `lib::print`: ADL contributes
  candidates and overload resolution chooses by argument type.
* `inline namespace v2` makes its members appear as if they were declared in the enclosing `lib`, so
  `lib::describe` means `v2::describe` while `lib::v1::describe` remains available to old callers. Libraries use
  this to version an API or an ABI (`+std::__1+` in libc{plus}{plus} is an inline namespace).
* The unnamed namespace gives `counter` internal linkage: no other translation unit can see or collide with it.
  Prefer it to `static` at namespace scope in new code.
* `pass:c[SQUARE(n + 1)]` prints `7`, not `16`: the preprocessor pasted `pass:c[n + 1 * n + 1]`. A macro has no scope, no types
  and evaluates arguments each time it uses them; make every argument and the whole body parenthesized, or better,
  replace the macro by an `inline` or `constexpr` function. Macros remain necessary for include guards,
  conditional compilation and feature detection (`+__cpp_concepts+`, `+__has_include+`).
* Never put `using namespace std;` in a header: it injects every name of the library into every file that
  includes it. In a source file prefer targeted using-declarations.

== Modules: What the Syntax Looks Like

A named module replaces textual inclusion with a compiled interface: importing it does not re-parse its contents,
macros do not leak across the boundary, and only the names marked `export` are visible. The interface unit for the
inventory looks like this:

.inventory.cppm
[source,cpp]
----
module;                       // global module fragment: ordinary #includes go here
#include <string>
export module inventory;      // the module declaration

export struct Book {          // exported: visible to importers
    std::string title;
    int copies;
};

export int total_copies(const Book* books, int n) {
    int sum = 0;
    for (int i = 0; i < n; ++i) sum += books[i].copies;
    return sum;
}

int secret_helper() { return 42; }   // not exported: invisible outside the module
----

.use_module.cpp
[source,cpp]
----
#include <print>
import inventory;

int main() {
    Book shelf[] = {{"Dune", 2}, {"Emma", 3}};
    std::println("total copies: {}", total_copies(shelf, 2));
}
----

The toolchain used for this page (Apple clang 21 with libc{plus}{plus}) does not enable C{plus}{plus}20 named modules, and rejects the
interface unit:

[source,console]
----
$ clang++ -std=c++23 -x c++-module --precompile inventory.cppm -o inventory.pcm 2>&1 | head -3
inventory.cppm:1:1: error: a type specifier is required for all declarations
    1 | module;                       // global module fragment: ordinary #includes go here
      | ^
----

Support is toolchain- and build-system-dependent: GCC (with `-fmodules-ts`), upstream Clang and MSVC build named
modules, CMake 3.28 and later can scan and order the module units, and `import std;` (the standard library as a
module) needs a recent compiler *and* library. Until your whole toolchain supports them, keep headers with include
guards (or `+#pragma once+`) as the portable baseline, and treat modules as an opt-in for projects where you control
the compiler.
