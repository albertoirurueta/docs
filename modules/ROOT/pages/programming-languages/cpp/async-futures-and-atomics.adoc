== `std::promise`, `std::future`, and `std::shared_future`

A `promise`/`future` pair moves a value (or an exception) from a producer to a consumer, one time, possibly
across threads:

[source,cpp]
----
#include <future>
#include <thread>
#include <iostream>

void produce(std::promise<int> p) {
    p.set_value(42);                    // or p.set_exception(std::current_exception()) on failure
}

int main() {
    std::promise<int> p;
    std::future<int> f = p.get_future();
    std::thread t(produce, std::move(p));
    std::cout << f.get() << '\n';         // blocks until produce() calls set_value; re-throws if
    t.join();                              // set_exception was called instead
}
----

`std::future::get()` can only be called **once**; `std::shared_future` (obtained via `future::share()`) may be
copied and its `.get()` called from multiple consumers, each receiving the same result.

== `std::async` and Launch Policies

`std::async` runs a callable and returns a `future` for its result -- often simpler than manually wiring a
`thread` + `promise`:

[source,cpp]
----
#include <future>
#include <iostream>

int compute() { return 6 * 7; }

int main() {
    auto f1 = std::async(std::launch::async, compute);      // runs on a new thread, guaranteed
    auto f2 = std::async(std::launch::deferred, compute);    // runs lazily, on THIS thread, only when .get()
                                                                // or .wait() is actually called
    auto f3 = std::async(compute);                             // implementation-defined choice of the two above

    std::cout << f1.get() << ' ' << f2.get() << '\n';
}
----

Calling `std::async` without an explicit policy leaves the choice of whether/when a new thread is spawned up to
the implementation -- specify `std::launch::async` explicitly whenever concurrent execution is actually required.

== `std::packaged_task`

Wraps a callable so its result is delivered through a `future`, decoupling *invocation* from *result retrieval*
-- the building block behind simple thread-pool implementations:

[source,cpp]
----
#include <future>
#include <thread>
#include <iostream>

int main() {
    std::packaged_task<int()> task([] { return 42; });
    std::future<int> f = task.get_future();

    std::thread t(std::move(task));      // the task can be handed to any executor -- a thread, a queue, ...
    std::cout << f.get() << '\n';
    t.join();
}
----

== `std::atomic` and Memory Orders

`std::atomic<T>` provides lock-free (for most `T` on most platforms) read-modify-write operations without a
mutex:

[source,cpp]
----
#include <atomic>
#include <thread>
#include <vector>
#include <iostream>

std::atomic<int> counter{0};

void incrementMany() {
    for (int i = 0; i < 1000; ++i) counter.fetch_add(1, std::memory_order_relaxed);
}

int main() {
    std::vector<std::thread> threads;
    for (int i = 0; i < 4; ++i) threads.emplace_back(incrementMany);
    for (auto& t : threads) t.join();
    std::cout << counter.load() << '\n';   // 4000, no data race
}
----

The default `std::memory_order_seq_cst` (used implicitly by `load()`/`store()`/`fetch_add()` with no explicit
order) is the safest, simplest choice; `std::memory_order_relaxed` (only ordering guarantee: atomicity itself)
is a deliberate, measured optimization for counters like the one above where *ordering* relative to other memory
operations genuinely does not matter -- reach for it only after profiling shows the default order matters,
never as a first choice.

== `std::atomic_ref` and `atomic<shared_ptr>`

`std::atomic_ref<T>` ({cpp}20) provides atomic operations *on an existing, non-atomic object* -- useful when a
type can't be declared `std::atomic<T>` throughout (e.g. a field in a struct shared with non-atomic code, or a
plain array element updated concurrently just for this one algorithm):

[source,cpp]
----
#include <atomic>

struct Stats { int hits = 0; };

void recordHit(Stats& stats) {
    std::atomic_ref<int> atomicHits(stats.hits);   // "stats.hits" itself is a plain int
    atomicHits.fetch_add(1, std::memory_order_relaxed);
}
----

{cpp}20 also specializes `std::atomic<std::shared_ptr<T>>`, giving lock-free-when-possible atomic operations on a
`shared_ptr` itself (its pointer/control-block pair) -- previously requiring an external mutex around every
`shared_ptr` access from multiple threads.

NOTE: this specialization is standard-conformant {cpp}20/23 (verified against cppreference and the working
draft), but this environment's libstdc{plus}{plus} 13 does not yet implement it -- `std::atomic<std::shared_ptr<T>>`
fails its own `is_trivially_copyable` static assertion here. A newer libstdc{plus}{plus}, or libc{plus}{plus}/MSVC, provides it.

== Parallel Algorithms with Execution Policies

Many `<algorithm>`/`<numeric>` functions accept an **execution policy** as their first argument, letting the
implementation parallelize (and/or vectorize) the operation across cores:

[source,cpp]
----
#include <execution>
#include <algorithm>
#include <numeric>
#include <vector>

int main() {
    std::vector<int> v(1'000'000);
    std::iota(v.begin(), v.end(), 0);

    std::sort(std::execution::par, v.begin(), v.end());                       // may run on multiple threads
    long long sum = std::reduce(std::execution::par_unseq, v.begin(), v.end(), 0LL);  // parallel + vectorized
    (void)sum;
}
----

`std::execution::seq` (sequential, the default with no policy given), `par` (parallel, but each element still
processed by one thread at a time -- no data races assumed between elements), and `par_unseq` (parallel and
vectorized -- the callable must itself be safe to interleave/reorder at the instruction level, e.g. no locks
inside it) are the three standard policies.

== Parallel Map/Fold

`std::transform`/`std::reduce` (or `std::transform_reduce` to fuse both into one pass) with an execution policy
are the standard library's "parallel map/fold":

[source,cpp]
----
#include <execution>
#include <numeric>
#include <vector>

int main() {
    std::vector<int> input(100, 3);
    long long sumOfSquares = std::transform_reduce(
        std::execution::par,
        input.begin(), input.end(),
        0LL,
        std::plus<>{},                       // the "fold"/reduce step
        [](int x) { return static_cast<long long>(x) * x; }   // the "map"/transform step
    );
    (void)sumOfSquares;
}
----

== Futures and Atomics, Run and Explained

`std::async`, `std::promise`/`std::future` and `std::packaged_task` are three ways to get *one result* back from
another thread. A future is the receiving end of a one-shot channel; the sending end is the async task itself, a
promise or a packaged task. The shared state also carries an exception, which is rethrown by `get()` in the
receiving thread.

[mermaid]
....
flowchart LR
    subgraph producer["thread that computes"]
      A["std::async task /<br/>std::promise /<br/>std::packaged_task"]
    end
    A -->|"set_value / set_exception /<br/>return"| SS[("shared state<br/>value or exception")]
    SS -->|"future.get(): blocks until ready,<br/>returns the value or rethrows"| F["thread that needs the result"]
....

.futures.cpp
[source,cpp]
----
#include <atomic>
#include <chrono>
#include <functional>
#include <future>
#include <numeric>
#include <print>
#include <stdexcept>
#include <string>
#include <thread>
#include <vector>

int count_copies(const std::vector<int>& v, std::size_t from, std::size_t to) {
    return std::accumulate(v.begin() + from, v.begin() + to, 0);
}

int risky() { throw std::runtime_error("catalog server unreachable"); }

int main() {
    std::vector<int> copies(1000, 2);   // 1000 books with 2 copies each

    // std::async with launch::async: runs on another thread; get() waits and returns the value.
    auto first = std::async(std::launch::async, count_copies, std::cref(copies), 0, 500);
    auto second = std::async(std::launch::async, count_copies, std::cref(copies), 500, 1000);
    std::println("total = {}", first.get() + second.get());

    // Exceptions travel through the future and rethrow on get().
    auto bad = std::async(std::launch::async, risky);
    try { (void)bad.get(); } catch (const std::exception& e) { std::println("get() rethrew: {}", e.what()); }

    // The launch::deferred policy runs lazily, on the thread that calls get().
    auto lazy = std::async(std::launch::deferred, [] { return std::this_thread::get_id(); });
    std::println("deferred ran on the calling thread: {}", lazy.get() == std::this_thread::get_id());

    // promise/future: a one-shot channel between two threads.
    std::promise<std::string> p;
    std::future<std::string> f = p.get_future();
    std::thread t([&p] { p.set_value("catalog loaded"); });
    std::println("{}", f.get());
    t.join();

    // packaged_task wraps a callable so its result goes to a future.
    std::packaged_task<int(int, int)> task([](int a, int b) { return a + b; });
    auto sum = task.get_future();
    std::thread(std::move(task), 2, 3).join();
    std::println("packaged_task result: {}", sum.get());

    // Atomics: lock-free counter vs relaxed counter vs publish/subscribe with release/acquire.
    std::atomic<int> counter{0};
    std::vector<std::thread> threads;
    for (int i = 0; i < 4; ++i)
        threads.emplace_back([&] { for (int k = 0; k < 10000; ++k) counter.fetch_add(1, std::memory_order_relaxed); });
    for (auto& th : threads) th.join();
    std::println("atomic counter: {}", counter.load());

    int payload = 0;                       // plain data published through the atomic flag
    std::atomic<bool> ready{false};
    std::thread producer([&] { payload = 42; ready.store(true, std::memory_order_release); });
    std::thread consumer([&] {
        while (!ready.load(std::memory_order_acquire)) std::this_thread::yield();
        std::println("consumer sees payload {} after acquiring the flag", payload);
    });
    producer.join();
    consumer.join();
    std::println("lock-free int: {}, lock-free bool: {}", std::atomic<int>::is_always_lock_free,
                 std::atomic<bool>::is_always_lock_free);
}
----

[source,console]
----
$ clang++ -std=c++23 -Wall -Wextra futures.cpp -o futures
$ ./futures
total = 2000
get() rethrew: catalog server unreachable
deferred ran on the calling thread: true
catalog loaded
packaged_task result: 5
atomic counter: 40000
consumer sees payload 42 after acquiring the flag
lock-free int: true, lock-free bool: true
----

* The two `+std::async(std::launch::async, ...)+` calls compute half of the catalog each, in parallel, and
  `get()` blocks until each result is ready. `std::cref` passes the vector by reference; arguments are copied by
  default. If you ignore the returned future of a `launch::async` call, its destructor *blocks* until the task ends,
  which silently serializes code that looks asynchronous.
* The default launch policy (`async | deferred`) lets the implementation choose, so a task may never start until
  `get()` is called. State the policy you want. `launch::deferred` runs the callable lazily on the thread that calls
  `get()`, as the `true` line shows.
* The exception thrown by `risky()` in the task is stored in the shared state and rethrown by `bad.get()`, so error
  handling works across threads without any extra code.
* `std::atomic<int>` makes each increment indivisible. `memory_order_relaxed` is enough for a counter, because
  nothing else depends on the order of the increments. The release/acquire pair on `ready` is what makes the plain
  `payload` visible to the consumer: the release store *publishes* everything written before it, and the acquire
  load that reads `true` *synchronizes with it*, so reading `payload` afterwards is not a race. The default,
  `memory_order_seq_cst`, is correct for everything and the right choice until profiling shows otherwise.
* `is_always_lock_free` tells you whether the type is implemented with hardware atomics rather than a hidden lock.

=== Parallel algorithms

Many `<algorithm>` and `<numeric>` functions take an execution policy as their first argument
(`std::execution::par`, `par_unseq`) to split the work across threads. They are declared by `<execution>`, which
this libc{plus}{plus} ships only behind `-fexperimental-library`:

.pexec.cpp
[source,cpp]
----
#include <algorithm>
#include <execution>
#include <numeric>
#include <print>
#include <vector>
int main() {
    std::vector<int> v(1000, 1);
    std::println("{}", std::reduce(std::execution::par, v.begin(), v.end(), 0));
}
----

[source,console]
----
$ clang++ -std=c++23 -Wall -Wextra -fexperimental-library pexec.cpp -o pexec
$ ./pexec
1000
----

With libstdc{plus}{plus} the same code needs the TBB library on the link line (`-ltbb`); with MSVC it works out of the box.
The operation passed to a parallel algorithm must be free of data races and must not depend on evaluation order, and
a floating-point `reduce` can give a different sum from `accumulate` because addition is not associative.
