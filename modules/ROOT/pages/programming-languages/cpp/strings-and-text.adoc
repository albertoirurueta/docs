== `std::string` and `std::string_view`

`std::string` owns and manages a growable buffer of `char`; `std::string_view` ({cpp}17) is a non-owning
`(pointer, length)` view -- pass it by value to avoid copying when a function only needs to *read* text:

[source,cpp]
----
#include <string>
#include <string_view>
#include <iostream>

void printLength(std::string_view sv) {          // accepts std::string, "literals", substrings -- no copy
    std::cout << sv.size() << '\n';
}

int main() {
    std::string s = "Hello, World!";
    s += " Goodbye.";
    printLength(s);
    printLength("a literal");                     // implicitly builds a string_view, not a std::string
    printLength(std::string_view(s).substr(0, 5)); // "Hello" -- substr on a view is itself non-allocating
}
----

A `string_view` must never outlive the buffer it points into -- a common bug is returning one that views a
now-destroyed temporary `std::string`.

== Character Types and Unicode

{cpp} has no built-in Unicode-aware string type; `std::string` is a sequence of `char` (commonly UTF-8 encoded by
convention, not enforced by the type), `std::u8string` ({cpp}20) is a sequence of `char8_t` explicitly meant for
UTF-8, and `std::u16string`/`std::u32string` hold UTF-16/UTF-32 code units:

[source,cpp]
----
#include <string>

std::string narrow = "caf\xc3\xa9";      // UTF-8 bytes for "café", typed as plain char
std::u8string utf8 = u8"café";            // same bytes, typed as char8_t -- distinguishable at compile time
std::u32string codepoints = U"café";       // one char32_t per Unicode code point (4 code points: c, a, f, é)
----

Iterating a UTF-8 `std::string` by `char` walks *bytes*, not code points or grapheme clusters -- for real
Unicode segmentation, reach for a library like https://icu.unicode.org/[ICU] or
https://github.com/tahonermann/text_view[a codepoint-aware view]; the standard library alone does not provide
one.

== Raw String Literals and User-Defined Literals

See xref:programming-languages/cpp/lexical-structure-and-style.adoc[Lexical Structure and Style] for the general
raw-string and UDL syntax; the standard library's own string UDLs live in `std::literals::string_literals`:

[source,cpp]
----
#include <string>
#include <string_view>
using namespace std::literals;

auto s = "hello"s;          // std::string, not const char*
auto sv = "hello"sv;         // std::string_view, zero-allocation
----

== `<charconv>`: Locale-Independent Conversions

`std::to_chars`/`std::from_chars` ({cpp}17) convert numbers to/from text without allocating, without exceptions,
and without any locale dependency -- the fastest and most predictable conversion path available:

[source,cpp]
----
#include <charconv>
#include <array>
#include <string_view>
#include <cassert>

int main() {
    std::array<char, 16> buffer{};
    auto [ptr, ec] = std::to_chars(buffer.data(), buffer.data() + buffer.size(), 42);
    assert(ec == std::errc{});
    std::string_view written(buffer.data(), ptr - buffer.data());
    assert(written == "42");

    int parsed = 0;
    auto [ptr2, ec2] = std::from_chars(written.data(), written.data() + written.size(), parsed);
    assert(ec2 == std::errc{});
    assert(parsed == 42);
    (void)ptr2;
    return 0;
}
----

== `std::format` and `std::print`

`std::format` ({cpp}20, header `<format>`) is a type-safe, Python-style formatting facility that replaces
`printf`&#39;s format-string/argument mismatches (a common source of undefined behavior) with compile-time-checked
placeholders:

[source,cpp]
----
#include <format>
#include <iostream>
#include <string>

int main() {
    std::string s = std::format("{} is {} years old, pi ~= {:.2f}", "Ada", 36, 3.14159);
    std::cout << s << '\n';                      // Ada is 36 years old, pi ~= 3.14
    std::cout << std::format("{0} {1} {0}", "a", "b") << '\n';   // positional args: a b a
    std::cout << std::format("{:>10}|{:<10}|{:^10}", "r", "l", "c") << '\n';  // alignment
}
----

`std::print`/`std::println` ({cpp}23, header `<print>`) write formatted text directly to a stream, skipping the
intermediate `std::string`:

[source,cpp]
----
#include <print>

int main() {
    std::println("{} is {} years old", "Ada", 36);
}
----

NOTE: `<print>` is standard-conformant {cpp}23 and needs a recent standard library: libstdc{plus}{plus} from GCC 14,
libc{plus}{plus} from LLVM 18 (including the Apple clang 21 and libc{plus}{plus} toolchain used for this section), or MSVC (see
xref:programming-languages/cpp/getting-started.adoc[Getting Started]); `std::format` itself, used above, is
available in libstdc{plus}{plus} from GCC 13.

=== Custom Formatters

A type opts into `std::format` by specializing `std::formatter`:

[source,cpp]
----
#include <format>
#include <string>

struct Point { int x, y; };

template <>
struct std::formatter<Point> : std::formatter<std::string> {
    auto format(const Point& p, std::format_context& ctx) const {
        return std::formatter<std::string>::format(
            std::format("({}, {})", p.x, p.y), ctx);
    }
};

// std::format("{}", Point{1, 2}) now yields "(1, 2)"
----

== `<regex>`

[source,cpp]
----
#include <regex>
#include <string>
#include <iostream>

int main() {
    std::string text = "order-42, order-7";
    std::regex pattern(R"(order-(\d+))");
    for (std::sregex_iterator it(text.begin(), text.end(), pattern), end; it != end; ++it) {
        std::cout << "matched id: " << (*it)[1] << '\n';   // 42, then 7
    }
}
----

`<regex>` is notorious for compile-time cost and, on some standard libraries, run-time performance well below
hand-written parsers or dedicated libraries (e.g. RE2, Boost.Xpressive) -- fine for one-off scripts, worth
benchmarking before using on a hot path.

== Strings in Memory, and Text in Practice

`std::string` is a class that owns a buffer of `char`. Understanding its layout explains three behaviours that
surprise newcomers: why a short string never allocates, why `std::string_view` is cheap but dangerous to store, and
why `size()` counts bytes rather than characters.

[mermaid]
....
flowchart LR
    subgraph small["std::string holding 'Dune' (short)"]
      S1["size = 4"] --- S2["inline buffer: D u n e 0 ...<br/>no heap allocation"]
    end
    subgraph large["std::string holding 100 chars"]
      L1["size = 100<br/>capacity >= 100"] --- L2["pointer"] --> H["heap block<br/>100 chars + terminator"]
    end
    V["std::string_view"] -.->|"pointer + length, no ownership"| H
    V -.-> S2
....

Most standard libraries implement the *small string optimization* (SSO): the object is 24 bytes here, and a short
string is stored directly inside those bytes. The consequence is that moving a short string copies bytes, and that
a `string_view` or iterator into a short string is invalidated by moving the string, because the characters move
with the object.

.strings.cpp
[source,cpp]
----
#include <charconv>
#include <format>
#include <print>
#include <regex>
#include <string>
#include <string_view>
#include <system_error>

int main() {
    // Small string optimization: short strings live inside the object, long ones allocate.
    std::string small = "Dune";
    std::string large(100, 'x');
    std::println("sizeof(std::string) = {}", sizeof(std::string));
    std::println("small data inside object: {}",
                 reinterpret_cast<const char*>(&small) <= small.data() &&
                     small.data() < reinterpret_cast<const char*>(&small) + sizeof(small));
    std::println("large data inside object: {}",
                 reinterpret_cast<const char*>(&large) <= large.data() &&
                     large.data() < reinterpret_cast<const char*>(&large) + sizeof(large));

    // string_view: cheap, non-owning. Safe parameter, unsafe to store or return from locals.
    std::string_view v = "Neuromancer";
    std::println("{} has {} chars, first 6: {}", v, v.size(), v.substr(0, 6));

    // UTF-8: size() counts bytes, not characters.
    std::string accent = "Garc\xC3\xAD" "a";   // "García"; the literal is split because \x consumes every hex digit that follows
    std::println("{} has {} bytes but 6 characters", accent, accent.size());

    // <charconv>: no locale, no allocation, no exceptions.
    std::string_view num = "2013 and more";
    int year = 0;
    auto [ptr, ec] = std::from_chars(num.data(), num.data() + num.size(), year);
    std::println("parsed {} and stopped at '{}', ec ok: {}", year, *ptr, ec == std::errc{});
    int bad = 0;
    std::string_view bad_text = "x42";
    auto r2 = std::from_chars(bad_text.data(), bad_text.data() + bad_text.size(), bad);
    std::println("\"x42\" parse error: {}", r2.ec == std::errc::invalid_argument);

    char buf[16];
    auto [end, ec2] = std::to_chars(buf, buf + sizeof(buf), 1985);
    std::println("to_chars: {}", std::string_view(buf, end - buf));

    // std::format: type-safe, positional, with width, alignment and precision.
    std::println("{:>8} | {:<8} | {:^8} | {:08.3f} | {:#x}", "right", "left", "mid", 3.14159, 255);
    std::println("{1} before {0}", "second", "first");
    std::println("{:*^20}", " report ");

    // <regex>: works, but is slow; fine for configuration parsing, not for hot paths.
    std::regex isbn(R"(\d{3}-\d-\d{2}-\d{6}-\d)");
    std::println("valid isbn: {}", std::regex_match("978-0-13-468599-1", isbn));
    std::println("bad isbn: {}", std::regex_match("978-0-13-468599", isbn));

    std::println("done");
}
----

* `string_view` is a pointer and a length. It is the right type for function *parameters* that only read text, as
  it accepts literals, `std::string` and substrings without a copy. It is the wrong type for a member variable or a
  return value unless the owner is guaranteed to outlive it: a function that builds a local `std::string` and
  returns a `string_view` of it hands the caller a pointer into freed memory, and clang diagnoses the simplest
  forms with `-Wreturn-stack-address`.
* `string_view` is not guaranteed to be zero-terminated, so never pass `sv.data()` to a C API that expects a
  C string unless you built the view from one.
* The literal `"Garc\xC3\xAD" "a"` is written as two pieces because a hexadecimal escape consumes every hex digit
  that follows it: `\xADa` would be read as the single, out-of-range value `0xADA`, and clang rejects it. For
  non-ASCII text, `+u8"..."+` literals or `í` universal character names avoid the trap.
* `std::from_chars` and `std::to_chars` convert without locale, allocation or exceptions, report failure through
  the returned `errc`, and tell you where parsing stopped, so they are the right choice for parsing fields in a
  loop. `std::stoi` throws on bad input and consults the current locale.
* The format string of `std::format` and `std::println` is checked at compile time, so `+std::println("{}")+` with a
  missing argument is a compile error, not a run-time crash.
* `<regex>` is correct but slow, and compiling an expression on every call is the usual cost; construct it once and
  reuse it, or use a hand-written parser for hot paths.
