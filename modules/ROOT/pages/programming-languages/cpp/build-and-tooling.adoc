== Compilers and Flags

Covered in xref:programming-languages/cpp/getting-started.adoc[Getting Started]; flags worth knowing beyond
`pass:c[-std=c++23 -Wall -Wextra]`:

[cols="1,3"]
|===
|Flag |Effect

|`-Werror` |Treat every warning as an error -- add once a codebase is warning-clean.
|`-O0` / `-O2` / `-O3` |Optimization level: none (fast builds, best debugging) through aggressive.
|`-g` |Include debug symbols (needed by debuggers and most sanitizers).
|`-fsanitize=address,undefined` |Enable ASan/UBSan (see xref:programming-languages/cpp/performance.adoc[Performance]).
|`-Wshadow` |Warn when a variable shadows an outer-scope one -- not in `-Wall`/`-Wextra`, worth adding explicitly.
|`-Wconversion` |Warn on implicit narrowing conversions -- catches the pitfalls from
xref:programming-languages/cpp/basic-types-and-values.adoc[Basic Types and Values].
|===

== CMake

The de facto standard {cpp} build-system generator -- CMake itself generates Makefiles/Ninja files/Visual Studio
projects rather than compiling directly:

[source,cmake]
----
cmake_minimum_required(VERSION 3.28)
project(MyApp CXX)

set(CMAKE_CXX_STANDARD 23)
set(CMAKE_CXX_STANDARD_REQUIRED ON)

add_library(mylib src/mylib.cpp)
target_include_directories(mylib PUBLIC include)

add_executable(myapp src/main.cpp)
target_link_libraries(myapp PRIVATE mylib)

# Sanitizers behind an option -- the Continuous Integration section below turns this on
# for the fast per-commit job.
option(ENABLE_SANITIZERS "Build with ASan and UBSan" OFF)
if(ENABLE_SANITIZERS)
    target_compile_options(myapp PRIVATE -fsanitize=address,undefined -fno-omit-frame-pointer)
    target_link_options(myapp PRIVATE -fsanitize=address,undefined)
endif()

enable_testing()
add_subdirectory(tests)
----

Modern CMake is **target-based**: `target_link_libraries`/`target_include_directories` attach properties to a
specific target (propagating to whatever links against it, if `PUBLIC`), rather than the old global
`include_directories()`/`link_libraries()` that leaked into every target in the project.

`CMakePresets.json` (CMake 3.19+) captures reproducible configure/build/test invocations (compiler, generator,
flags, cache variables) in one checked-in file, instead of everyone remembering their own `+cmake -B build
-DCMAKE_BUILD_TYPE=...+` invocation:

[source,json]
----
{
  "version": 6,
  "configurePresets": [
    {
      "name": "debug-asan",
      "generator": "Ninja",
      "binaryDir": "${sourceDir}/build/debug-asan",
      "cacheVariables": {
        "CMAKE_BUILD_TYPE": "Debug",
        "CMAKE_CXX_FLAGS": "-fsanitize=address,undefined -g"
      }
    }
  ]
}
----

[source,shell]
----
cmake --preset debug-asan
cmake --build --preset debug-asan
----

== Package Managers: vcpkg and Conan

Both resolve and build third-party {cpp} dependencies, integrating with CMake via a toolchain file (vcpkg) or a
generated `find_package`-compatible config (Conan):

[source,shell]
----
# vcpkg
vcpkg install fmt catch2
cmake -B build -DCMAKE_TOOLCHAIN_FILE=/path/to/vcpkg/scripts/buildsystems/vcpkg.cmake

# Conan
conan install . --output-folder=build --build=missing
cmake -B build -DCMAKE_TOOLCHAIN_FILE=build/conan_toolchain.cmake
----

Before either, {cpp} had no de facto package manager -- most projects either vendored dependencies directly or
relied on system package managers (`apt`, `brew`), which vcpkg/Conan largely superseded for portable,
per-project dependency management.

== `clang-format`

Automated, configurable code formatting -- removes formatting bikeshedding from code review entirely:

[source,yaml]
----
# .clang-format
BasedOnStyle: Google
IndentWidth: 4
ColumnLimit: 100
----

[source,shell]
----
clang-format -i src/*.cpp include/*.h    # reformat in place
----

== `clang-tidy`

Static analysis covering far more than a compiler's own warnings -- modernization suggestions
(`use-nullptr`, `use-auto`), bug-prone-pattern detection, and Core Guidelines checks:

[source,shell]
----
clang-tidy src/main.cpp -- -std=c++23
clang-tidy --checks='modernize-*,bugprone-*' src/main.cpp -- -std=c++23
----

== `compile_commands.json`

A per-file record of the exact compiler invocation used to build it -- generated automatically by CMake with
`CMAKE_EXPORT_COMPILE_COMMANDS=ON` (or by Ninja/Bear for other build systems), and consumed by `clang-tidy`,
clangd (editor tooling), and other analysis tools so they see the *actual* flags/include paths a file was built
with, rather than guessing:

[source,shell]
----
cmake -B build -DCMAKE_EXPORT_COMPILE_COMMANDS=ON
# generates build/compile_commands.json
----

== Valgrind

=== Installing Valgrind

[source,console]
----
# Debian / Ubuntu
$ sudo apt-get install valgrind

# Fedora / RHEL
$ sudo dnf install valgrind

# macOS (Homebrew) -- the mainline formula lags behind the newest macOS/Xcode releases;
# on a recent macOS, use the community tap instead:
$ brew install valgrind                                    # older macOS
$ brew tap LouisBrunner/valgrind && brew install --HEAD LouisBrunner/valgrind/valgrind

# Windows -- no native build; run it inside WSL (Ubuntu), same commands as above.
----

[NOTE]
====
Valgrind supports Linux, FreeBSD, Solaris and Android natively; macOS support trails new OS releases; there is
no native Windows build, so a Windows-only team needs WSL or a Linux CI runner -- this is why the CI example
below targets `ubuntu-latest`.
====

=== Running Memcheck on {cpp} Binaries

Valgrind instruments compiled machine code, so it works transparently on {cpp} binaries with no special flags:
it catches raw `new`/`delete` mistakes exactly like C's `malloc`/`free`, and it correctly follows RAII
destructor calls and exception unwinding.

[source,console]
----
$ valgrind --leak-check=full --show-leak-kinds=all --track-origins=yes ./app
----

Memcheck's leak report groups every unfreed block into one of four categories:

* *definitely lost* -- a real leak, with no pointer chain to the block.
* *indirectly lost* -- lost because the block(s) pointing to it are themselves lost.
* *possibly lost* -- only an interior-pointer chain reaches it; ambiguous.
* *still reachable* -- a pointer to the block still exists at exit; often not a bug.

See xref:programming-languages/c/build-and-tooling.adoc[C: Build and Tooling] for the full suppressions/
exit-code/XML-output reference, which applies identically here.

== Continuous Integration

The fast per-commit job builds in Debug with the `ENABLE_SANITIZERS` option already defined in the CMake
example above, and runs the test suite through CTest:

[source,console]
----
$ cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug -DENABLE_SANITIZERS=ON
$ cmake --build build -j
$ ctest --test-dir build --output-on-failure
----

Valgrind is roughly 20-30x slower than an uninstrumented run, so it belongs in a separate, scheduled job rather
than blocking every commit alongside the sanitizer-based checks above:

[source,yaml]
----
name: memcheck

on:
  push:
    branches: [ main ]
  pull_request:
  schedule:
    - cron: '0 3 * * *'   # nightly -- Valgrind is far slower than the sanitizer job above

jobs:
  valgrind:
    runs-on: ubuntu-latest

    steps:
      - uses: actions/checkout@v4

      - name: Install Valgrind
        run: sudo apt-get update && sudo apt-get install -y valgrind

      - name: Configure and build (Debug, no sanitizers -- Valgrind instruments the plain binary)
        run: |
          cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug
          cmake --build build -j

      - name: Run tests under Memcheck
        run: |
          ctest --test-dir build --output-on-failure \
            -T memcheck --overwrite MemoryCheckCommand=/usr/bin/valgrind \
            --overwrite "MemoryCheckCommandOptions=--leak-check=full --show-leak-kinds=all --error-exitcode=1"
----

`ctest -T memcheck` is CTest's built-in Valgrind integration, configured via `MemoryCheckCommand`: it runs every
registered test under Memcheck and fails the step on `--error-exitcode`, without needing to invoke `valgrind` on
each test binary by hand.

== Incremental Builds, Verified

A build system has one job: recompile the minimum after a change. It does that by tracking, for every object file,
the source and the headers it included. The compiler can produce that list itself with `-MMD`, which writes a `.d`
file of dependencies next to each object. The Makefile below uses it, and shows the whole mechanism in twelve lines.

[mermaid]
....
flowchart LR
    S1["main.cpp"] -->|"compile"| O1["main.o + main.d"]
    S2["book.cpp"] -->|"compile"| O2["book.o + book.d"]
    H["book.hpp"] -.->|"listed in both .d files"| O1
    H -.-> O2
    O1 -->|"link"| X["shelf"]
    O2 --> X
    H2["touch book.hpp"] -->|"both objects out of date"| R["recompile both, relink"]
    S3["touch main.cpp"] -->|"only main.o out of date"| R2["recompile one, relink"]
....

.Makefile
[source,make]
----
CXX      := clang++
CXXFLAGS := -std=c++23 -Wall -Wextra -Wpedantic -O2 -MMD -MP
OBJS     := main.o book.o

shelf: $(OBJS)
	$(CXX) $(CXXFLAGS) $^ -o $@

%.o: %.cpp
	$(CXX) $(CXXFLAGS) -c $< -o $@

-include $(OBJS:.o=.d)

clean:
	rm -f shelf *.o *.d
.PHONY: clean
----

[source,console]
----
$ cd mk && make clean > /dev/null && make && echo '--- second run' && make && sleep 1 && touch book.hpp && echo '--- after touching the header' && make && sleep 1 && touch main.cpp && echo '--- after touching main.cpp' && make
clang++ -std=c++23 -Wall -Wextra -Wpedantic -O2 -MMD -MP -c main.cpp -o main.o
clang++ -std=c++23 -Wall -Wextra -Wpedantic -O2 -MMD -MP -c book.cpp -o book.o
clang++ -std=c++23 -Wall -Wextra -Wpedantic -O2 -MMD -MP main.o book.o -o shelf
--- second run
make: `shelf' is up to date.
--- after touching the header
clang++ -std=c++23 -Wall -Wextra -Wpedantic -O2 -MMD -MP -c main.cpp -o main.o
clang++ -std=c++23 -Wall -Wextra -Wpedantic -O2 -MMD -MP -c book.cpp -o book.o
clang++ -std=c++23 -Wall -Wextra -Wpedantic -O2 -MMD -MP main.o book.o -o shelf
--- after touching main.cpp
clang++ -std=c++23 -Wall -Wextra -Wpedantic -O2 -MMD -MP -c main.cpp -o main.o
clang++ -std=c++23 -Wall -Wextra -Wpedantic -O2 -MMD -MP main.o book.o -o shelf
----

The header change rebuilt both translation units (both include it, as the `.d` files record) and the source change
rebuilt one. Without `-MMD` a header edit would silently leave stale objects, the classic cause of "it works after a
clean build". CMake and Ninja do this bookkeeping for you; the principle is the same.

=== The same project in CMake

A `CMakeLists.txt` for this project declares *targets* and their relationships instead of commands. The listing is
the CMake equivalent of the Makefile above, plus a test target; it is shown for reference and is not run on this page:

.CMakeLists.txt
[source,cmake]
----
cmake_minimum_required(VERSION 3.28)
project(inventory LANGUAGES CXX)

set(CMAKE_CXX_STANDARD 23)
set(CMAKE_CXX_STANDARD_REQUIRED ON)
set(CMAKE_CXX_EXTENSIONS OFF)               # -std=c++23, not -std=gnu++23
set(CMAKE_EXPORT_COMPILE_COMMANDS ON)       # writes compile_commands.json for clangd and clang-tidy

add_library(inventory book.cpp)
target_include_directories(inventory PUBLIC ${CMAKE_CURRENT_SOURCE_DIR})
target_compile_options(inventory PRIVATE -Wall -Wextra -Wpedantic)

add_executable(shelf main.cpp)
target_link_libraries(shelf PRIVATE inventory)   # PRIVATE/PUBLIC/INTERFACE decide who inherits usage requirements

enable_testing()
add_executable(inventory_tests minitest.cpp)
add_test(NAME inventory COMMAND inventory_tests)
----

* `target_link_libraries(shelf PRIVATE inventory)` means "shelf needs inventory to link, and consumers of shelf do
  not inherit that dependency". `PUBLIC` also propagates the include directories and flags to anything that links
  `inventory`. Setting flags per target (`target_compile_options`) instead of global variables keeps libraries
  from leaking options into each other.
* `CMAKE_CXX_EXTENSIONS OFF` selects `pass:c[-std=c++23]` instead of `pass:c[-std=gnu++23]`, so you do not depend on compiler
  extensions by accident.
* Configure and build out of source: `cmake -S . -B build -DCMAKE_BUILD_TYPE=Release` and
  `cmake --build build`. The build directory is disposable; never commit it.

=== The flag set to start from

[source,console]
----
clang++ -std=c++23 -Wall -Wextra -Wpedantic -Wconversion -Wshadow -O2 -g file.cpp
----

Add `-Werror` in CI, and run the test suite once more under `-fsanitize=address,undefined`. Both the compiler flags
and the sanitizers are documented in xref:programming-languages/cpp/performance.adoc[Performance].
