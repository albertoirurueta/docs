== Literate programming

The idea is to write one document for people and let the machine extract and run the program that is inside it. The document has the explanation, the code and, after it is processed, the results, so the explanation cannot drift away from the numbers it describes. Two operations are named after the original tools: to _weave_ is to run the code and produce the readable document, and to _tangle_ is to extract the code and produce the program. In R, Sweave was the first implementation and it is still part of R; knitr, which grew out of the same idea with more output formats and more options, is the engine of both current systems, and its function names remember the words: `knit()` weaves, `purl()` tangles, after the knitting term "knit one, purl one" in the help page of `knit()`.

A document in either system is a Markdown file with three kinds of content. The YAML header, between two lines of three hyphens at the top of the file, holds metadata and options: the title, the output format, the parameters, the execution options. Markdown is the prose. Code chunks, fenced with three backticks and the language in braces, are code that is run when the document is rendered, and inline code is a short expression inside a sentence. Rendering has two steps, shown in the table with the programs that do each of them.

[cols="2,5,3",options="header"]
|===
|Piece |What it does |Where it comes from
|knitr |Runs the code in the chunks and inline expressions, captures the text, messages, warnings, errors and plots, and writes a plain Markdown file in which the results are inserted after the code that made them (weaving). It also tangles (`purl()`) |R package, 1.52 here
|Pandoc |Converts the Markdown file to HTML, Word, slides, PDF through LaTeX or Typst, and many other formats |a separate program: rmarkdown uses the one it finds (3.1.3 here), Quarto uses the one it ships (3.10.0)
|rmarkdown |`render()` calls knitr and then Pandoc; the output formats of R Markdown (`html_document()`, `word_document()`, `pdf_document()`...) are functions of this package |R package, 2.32 here
|Quarto |The `quarto` command: reads `.qmd` (and `.Rmd` and `.ipynb`) files, calls knitr for R code (or Jupyter for Python), calls Pandoc, and adds projects, formats, cross-references and websites |a separate program, 1.10.19 here; it is not an R package
|`quarto` (R package) |A wrapper that calls the `quarto` command from R: `quarto_render()`, `quarto_preview()` and the vignette engine |not installed here
|Sweave |The first weaving system in R, for LaTeX documents with the extension `.Rnw`: `Sweave()` and `Stangle()` of the `utils` package, `R CMD Sweave` and `R CMD Stangle` |part of R
|===

Source: https://quarto.org/docs/computations/r.html[Quarto documentation: Using R]

The consequence of this arrangement is that the R side of a document does not change when the program around it changes. A Quarto document with R chunks is executed by knitr, exactly like an R Markdown document; the Quarto documentation says so, and says that Quarto can render most existing `.Rmd` files without modification. What differs is the packaging: how options are written, the names of the output formats, and what is available on top (projects, cross-references, a larger set of formats). The next sections use the shelf report to show each piece in the order in which a reader meets it.

== The shelf monthly report

The report answers two questions about the loans: how many loans were made in each month since a given month, and which members have loans that were overdue. A loan is overdue when it was out for more than `loan_days` days; a loan that has not been returned counts up to `shelf_today`. The project directory has the two data files and the document:

[source,text]

├── books.csv
├── loans.csv
└── report.qmd
----

Source: https://quarto.org/docs/projects/quarto-projects.html[Quarto documentation: Project Basics]

The document, `report.qmd`, is the following. Its header gives the title, asks for the `html` format, declares one parameter, `since`, with the default `2026-01`, and sets `echo: false` for the whole document with the `execute` key, so that the code is not shown unless a chunk asks for it. The first chunk, with `include: false`, reads the data and computes the loans of interest: it runs, and nothing of it is shown. The paragraph after it contains four pieces of inline code. The table and the figure chunks have labels that start with `tbl-` and `fig-`, which is how Quarto makes them cross-referenceable, so the text can say `+@tbl-months+` and `+@fig-months+`. The last chunk shows its code (`echo: true`) because the way the overdue loans are computed is part of what a reader of the report wants to check.

[source,markdown]
----
---

format: html
params:
  since: "2026-01"
execute:
  echo: false
---

```{r}
#| label: load
#| include: false
books <- read.csv("books.csv")
loans <- read.csv("loans.csv", colClasses = "character")

loans$return_date <- as.Date(loans$return_date, format = "%Y-%m-%d")

loan_days <- 21L
loans$month <- format(loans$loan_date, "%Y-%m")
recent <- loans[!is.na(loans$month) & loans$month >= params$since, ]
```

== How a document is processed

A few rules explain most of what happens in a render and most of the surprises.

The document is evaluated top to bottom, in one R session and one environment: a variable created in an early chunk exists in later chunks, so the order of the chunks matters, and nothing is saved between renders unless caching is on. Quarto starts a new R process for every render, so objects of an interactive session are not visible to the document, and a render starts from a clean state, which is the point of a report. `rmarkdown::render()` is different: its argument `envir` defaults to `parent.frame()`, so called from the console it evaluates the chunks in the calling environment, where the console's objects are visible and the document's objects are left behind. The help page suggests `new.env()` to guarantee an empty environment, and rendering from a script run with `Rscript` (as the R Markdown examples below do) avoids the problem. Code that works in a render only because of an object defined earlier in the console is the most common reason for a report that cannot be reproduced.

The working directory is the directory of the document. That is why `read.csv("books.csv")` finds the file, and why a document that is moved without its data fails. The help page of `knit()` says it so: the working directory when evaluating chunks is the directory of the input document by default, it is possible to change it with the package option `+opts_knit$set(root.dir = ...)+`, and changing it with a call to `setwd` in a chunk is not recommended, because figure and cache files may be written to the wrong places. Quarto has its own switch for a project: `execute-dir` in the `project` key, whose values are `file` (the directory of the document being executed) and `project` (the root of the project). The `quarto render` option `--execute-dir` sets it for one render.

Everything the code writes to the standard output, standard error, the graphics devices and the condition system is collected: output text becomes a block after the chunk, a message, warning or error is inserted as text, and a plot becomes an image file in the support directory. A chunk that fails stops the render with the chunk's label and line numbers unless the error is allowed to continue; both cases are shown in the sections on chunk options and on errors.

Quarto finds R on the system `PATH` (the Quarto documentation names the environment variable `QUARTO_R` for pointing it to another installation), and needs the rmarkdown package, which brings knitr with it. == Chunks and chunk options

A code chunk starts with three backticks and the language in braces, `+{r}+` for R, and ends with three backticks. What happens to it is controlled by chunk options. There are two places to write them.

[source,markdown]
----
```{r overdue, echo=TRUE, fig.width=6}
summary(cars)
```

```{r}
#| label: overdue
#| echo: true
#| fig-width: 6
summary(cars)
```
----

Source: https://quarto.org/docs/computations/r.html[Quarto documentation: Using R]

The first chunk is the R Markdown form, in the header line after the language: a label (the first unnamed item), then `name=value` pairs separated by commas, with R syntax for the values. The second is the Quarto form: comment lines at the top of the chunk that start with the characters hash and pipe (`+#|+`), with YAML syntax for the values. The Quarto documentation explains why: long options such as captions are easier to write on their own line, and editors that do not understand chunk headers can still edit the options. The form is not Quarto's invention. It is a feature of knitr since version 1.35, whose NEWS says that options written inside a chunk after `+#|+` override the same options in the header, so the hash-pipe form also works in R Markdown documents, with either YAML syntax or the comma-separated syntax of the header. The comment character is that of the language of the chunk: knitr 1.51 made a pipe comment in a chunk follow it, and the next block of this section shows what that means for a `sql` chunk. A value that has to be computed is written with `!expr`, which is a YAML tag: the Quarto documentation gives `#| fig-cap: !expr 'paste("Air", "Quality")'`. The Quarto FAQ adds that `!expr` works inside chunk options and not in the YAML header of the document or the project, and that `!r` (the R Markdown spelling) is not accepted by Quarto's validation anywhere.

Quarto also translates names. In its own spelling, the words of an option are separated by hyphens (`fig-width`, `out-width`, `fig-cap`), because Quarto follows Pandoc and YAML conventions, and knitr's dotted spelling (`fig.width`) is accepted as well. The next document uses both on two chunks that draw the same figure; the first gives the hyphenated names, the second the dotted ones, and the output document is the same for both.

=== The options that matter

The knitr documentation lists the options with their defaults; the table has the ones this page uses and the spelling for each system. A default that differs between knitr's own `knit()` and a render is noted, because it is the source of a common surprise.

[cols="3,3,5",options="header"]
|===
|knitr (R Markdown) |Quarto |What it does and its default
|`eval` |`eval` |Whether to run the chunk (`TRUE`). `FALSE` shows the code and does not run it. A numeric vector selects the expressions to run, `eval = c(1, 3)`.
|`echo` |`echo` |Whether to show the source code (`TRUE`). A numeric vector selects expressions. Quarto sets `false` by default in presentation formats such as revealjs, beamer and pptx. In Quarto, `echo: fenced` also prints the chunk delimiter.
|`include` |`include` |Whether the chunk's output goes into the document (`TRUE`). With `FALSE` the code still runs and files such as plots are still made, but nothing is written; knitr stops on an error in such a chunk even when errors are otherwise allowed, because the error would be easy to overlook.
|`results` |`results`, `output` |How text results are shown. In knitr, `results` is `'markup'` (fenced code blocks), `'asis'` (raw Markdown), `'hold'` (all text after the chunk's code) or `'hide'`; Quarto accepts these values in `results` and also has `output`, with `true`, `false` and `asis`.
|`message`, `warning` |`message`, `warning` |Whether messages and warnings are kept (`TRUE`). `FALSE` drops them; `NA` prints them on the console instead of capturing them; a numeric value selects which warnings to keep.
|`error` |`error` |Whether an error is kept in the output and the evaluation continues. knitr's own default is `TRUE`; R Markdown and Quarto change it to `FALSE`, so that a failing chunk stops the render.
|`collapse` |`collapse` |Merge the source and its output into one block (`FALSE`).
|`comment` |`comment` |The prefix of each line of text output; knitr's default is `+##+`, and the examples of this section use `+#>+`.
|`fig.width`, `fig.height` |`fig-width`, `fig-height` |The size of a plot in inches. The knitr default is 7 by 7; Quarto sets a default for each format (7 by 5 in general, 9 by 5 for revealjs, 5.5 by 3.5 for PDF) and passes it on to these options.
|`fig.cap`, `fig.alt` |`fig-cap`, `fig-alt` |Caption and alternative text of a figure.
|`out.width`, `out.height` |`out-width`, `out-height` |The size of the plot in the output, which may differ from the size at which it was drawn.
|`tab.cap` |`tbl-cap` |Caption of a table. In Quarto, a `tbl-` label turns the caption into a numbered, referenceable table.
|`label` |`label` |The name of the chunk, used for file names, for the progress report, for the cache and for references.
|`cache` |`cache` |Whether to cache the chunk's results (`FALSE`); see the caching section below.
|`child` |`child` |Paths of documents to run and include.
|`R.options` |`R.options` |A list of R options set while the chunk runs and restored afterwards.
|`engine` |the language in the braces |The language of the chunk (`'R'`); see the engines section below.
|===

Quarto adds options of its own that knitr does not have: `code-fold` and `code-summary`, `fig-subcap`, `fig-align`, `layout-ncol`, `column`, `output-location` for revealjs, and the cross-reference conventions of the label. === What the options do

The best way to learn the options is to see them act. The next R Markdown file has one chunk for each of the main options, and the script after it runs `knitr::knit()` on it and prints the Markdown that comes out. `knit()` is the first step of every render, and calling it by hand is a good way to see the intermediate file that the render pipeline normally deletes. Its output file is a temporary file, so no path is shown.

[source,markdown]
----
---
title: "Chunk options"
---

```{r setup, include=FALSE}
knitr::opts_chunk$set(comment = "#>")
```

`echo = FALSE` hides the code and keeps the result:

```{r hidden, echo=FALSE}
nchar("shelf")
```

`eval = FALSE` shows the code and does not run it:

```{r not-run, eval=FALSE}
stop("never runs")
```

`include = FALSE` runs the chunk and shows neither code nor output:

```{r silent, include=FALSE}
secret <- 42
```

The value is still there: `r secret`.

`collapse = TRUE` puts the code and its output in one block:

```{r merged, collapse=TRUE}
x <- c(3, 5, 8)
mean(x)
sum(x)
```

`results = 'hold'` prints all output after the code:

```{r hold, results='hold'}
cat("first\n")
print("second")
cat("third\n")
```

`results = 'asis'` passes the output through as markdown:

```{r asis, results='asis'}
cat("**bold** text written by cat()\n")
```

`message = FALSE` and `warning = FALSE` drop those conditions:

```{r quiet, message=FALSE, warning=FALSE}
message("a message")
warning("a warning")
1 + 1
```

`error = TRUE` keeps going and shows the error:

```{r failing, error=TRUE}
stop("stopped")
```

`child` pulls in another file:


=== Setting the options for the whole document

An option that every chunk needs is not repeated on every chunk. There are four places to set it, and a more specific place wins over a more general one: the chunk, the document, the project.

* In the setup chunk with `knitr::opts_chunk$set()`, which works in both systems (the R Markdown way; the setup chunk usually has `include = FALSE`).
* In the YAML header: `execute:` for the execution options of Quarto, as the report does, and `knitr: opts_chunk:` to pass any knitr option, in Quarto. The Quarto documentation gives the second form with `collapse: true` and `comment: "#>"`, and also `opts_knit` for package options; the section on inline code below uses it.
* In the project file `+_quarto.yml+` or, for the documents of one directory, in `+_metadata.yml+`, the same keys; the section on projects shows it.
* On the command line, `quarto render report.qmd -M echo:false`, where `-M` (`--metadata`) sets a metadata value for one render.

=== Labels, references and reuse

Give chunks labels. A label is the name used for the figure file (`fig-months-1.png`), for the cache files, and in the progress report and the error message (`+Quitting from ... A chunk can reuse the code of another with `ref.label` (the code of the referenced chunks is inherited), and the older form `+<<label>>+` inside a chunk includes a chunk by name.

----

Source: https://search.r-project.org/CRAN/refmans/knitr/html/knit.html[knitr package documentation: knit]

=== Figures and tables

Plots made by base graphics, lattice or ggplot2 are saved as files and inserted at the point where they were drawn, with the size from `fig-width` and `fig-height` and the caption from `fig-cap`; one chunk may draw several. The graphics devices are the subject of xref:programming-languages/r/base-graphics-and-devices.adoc[Base Graphics and Devices], and a ggplot2 object is printed in a chunk the same way (ggplot2 4.0.3 is installed; the report uses base graphics so that it needs no package, and no ggplot2 chunk was run for this page). Tables are Markdown tables made by `knitr::kable()`, which takes a data frame and returns Markdown, so it works in every output format; `col.names` and `caption` are its everyday arguments, and in Quarto a `tbl-cap` option can supply the caption instead. The document option `df-print` (`default`, `kable`, `tibble` or `paged` in HTML) sets how data frames are printed when a chunk ends with one; `kable` as the choice makes every printed data frame a Markdown table.

=== Caching

Some chunks are slow, and re-running them at every render is a waste while the text around them is being written. The cache stores a chunk's results after the first evaluation and loads them in later renders when the chunk has not changed. It is enabled with the `cache` option, for one chunk or for the document under `execute`; with `cache: true` in the header, the next document caches its only chunk.

[source,markdown]
----
---

format: gfm

  cache: true
---

```{r}
#| label: slow
loans <- read.csv("loans.csv")
nrow(loans)
```
----

[source,bash]
----

----

Source: https://quarto.org/docs/computations/execution-options.html[Quarto documentation: Execution Options]

[source,text]
----
cached_cache
cached.md
cached.qmd
commonmark
----

Source: https://quarto.org/docs/computations/execution-options.html[Quarto documentation: Execution Options]

(The two listings are the output of the two commands, one after the other.) Inside the format directory the chunk is stored in three files named after its label plus a hash, with the extensions `.RData`, `.rdb` and `.rdx`, and a file called `+__packages+`. The knitr documentation explains the hash: it is an MD5 digest of the R code and the chunk options, so any change to the chunk produces a new name and invalidates the cache. That is also the weakness. The digest covers the chunk, not the data files it reads or the other chunks it depends on, so a chunk that reads `loans.csv` is not recomputed when the file changes, and a chunk that uses an object made in another chunk must say so with `dependson` or `autodep`. Chunks with side effects (writing a file, setting an option, loading a package) are not replayed from the cache. The command-line switches `--cache`, `--no-cache` and `--cache-refresh` of `quarto render` force the use of the cache, disable it, or refresh it without editing the document. Two alternatives that do not have these problems are described in the Quarto documentation: disable execution when the page is prose (`execute: enabled: false`), and `freeze` in a project, shown in the project section below. For a short report like this one, the best cache is no cache.

== Inline code

Numbers in prose are where reports go stale, so they are computed too. Inline code is an expression in the middle of a sentence, between single backticks. There are two syntaxes for R. R Markdown uses the form with a backtick, the letter `r`, a space, the expression and a closing backtick. Quarto 1.4 added a form that is the same for all engines: the language in braces, as in a chunk, then the expression. Both work in a Quarto document with knitr, and the report uses the second. The difference is in how the result is treated: the Quarto form treats the result as text and escapes any Markdown in it, while the knitr form treats the result as Markdown, which the Quarto documentation says is equivalent to wrapping the expression in `I()`. The next document shows the two forms, the effect of `I()`, the escape for documenting the syntax, the `knitr:` key of the header that sets the options of all chunks, and the Quarto shortcode for including another file.

format: gfm

  opts_chunk:
    collapse: true
    comment: "#>"
---

```{r}
loans <- read.csv("loans.csv", colClasses = "character")
n_loans <- nrow(loans)
n_loans
```

The knitr form keeps it: `r "**bold**"`.

Reading the result: both forms gave 60; the Quarto form escaped the asterisks of `+**bold**+` (they appear as `+\*\*bold\*\*+` in the Markdown, so the reader sees two asterisks on each side), the knitr form made the word bold, and `I()` restored that in the Quarto form. The extra backtick and the doubled braces both turn the example into text that is not evaluated, which is how the Quarto documentation writes about the syntax, and the shortcode `+{{< include intro.md >}}+` inserted the file (it needs no chunk, unlike the `child` option). The `knitr:` key in the header is the way to give the whole document the options `collapse: true` and `comment: "#>"`, and the output shows `+#>+` in the first chunk.

The rules to remember are the ones in the Quarto documentation. Keep inline expressions simple, confined to values already computed in chunks, because the protocol they use is not compatible with some libraries. Inline code cannot be used in the YAML header, so a title or a figure caption that must contain a computed number cannot use it; for a caption the documentation recommends combining inline code with the cross-reference div syntax, and a chunk option can take a computed value with `!expr`. The inline expressions of a document with no executable chunk are not evaluated unless the `engine` is set explicitly. And a result is formatted as R formats a single value, so `format()` and `round()` decide what the reader sees: `+{r} nrow(recent)+` is an integer, but the share of overdue loans needs `+round(100 * mean(...))+` or `format()`.

The version history is short. The form with the letter `r` is knitr's own and the one in all older tutorials. The 1.4 release notes of Quarto (January 2024) list support for executing inline expressions, with the Python spelling as the example, under the Jupyter engine; the Inline Code article documents the single `+{lang}+` syntax for all engines, with `+{r}+` for knitr, and says that the native knitr syntax stays supported. This page ran the `+{r}+` form on Quarto 1.10.19 and does not claim in which 1.x release it started to work for knitr documents.

== Parameters

A parameterized report is a document with inputs. The monthly report is the example: it is the same document every month, and only the first month to include changes. Parameters are declared in the YAML header with default values, as `report.qmd` does:

[source,yaml]
----
params:
  since: "2026-01"
----

Source: https://quarto.org/docs/computations/parameters.html[Quarto documentation: Parameters]

In the code, the values are the list `params`, so `params$since` is `"2026-01"`. For the knitr engine, Quarto uses the standard knitr `params` YAML option (for Jupyter it uses a cell tagged `parameters`, in the style of Papermill, and for Julia the keys become variables). The default is a character string and not a number, and it is quoted in the YAML for that reason: the comparison with the month strings of the loans is a comparison of text.

To render with other values, pass them on the command line with `-P` (`--execute-param`), one `key:value` for each parameter, or put them in a YAML file and give it to `--execute-params`. Each command writes to a different file with `--output`, so that the first report is not overwritten. The file `params-2026-03.yml` has the single line `since: "2026-03"`.

=== One report per month

A parameterized report is made to be rendered in a loop, once for each value. The script renders the R Markdown report for three months from a script; the function builds a file name from the month so that the outputs do not overwrite one another, and returns the names. `vapply()` is used instead of a loop that grows a vector.

[source,r]
----
months <- c("2026-01", "2026-02", "2026-03")
render_month <- function(month) {
  out <- rmarkdown::render("report.Rmd",
                           output_file = paste0("monthly-", month, ".html"),
                           params = list(since = month), quiet = TRUE)
  basename(out)
}
vapply(months, render_month, character(1L), USE.NAMES = FALSE)
#> [1] "monthly-2026-01.html" "monthly-2026-02.html" "monthly-2026-03.html"
----

Source: https://rmarkdown.rstudio.com/docs/reference/render.html[R Markdown documentation: render]

The same loop for the Quarto document can be written without the `quarto` R package by calling the program from R with `system2()`; the script renders the February report and returns the exit status of the command, which is `0` when it succeeded:

[source,r]
----
status <- system2("quarto", c("render", "report.qmd", "--quiet",
                              "-P", "since:2026-02",
                              "--output", "report-feb.html"))
status
#> [1] 0
file.exists("report-feb.html")
#> [1] TRUE
----

Source: https://search.r-project.org/R/refmans/base/html/system2.html[R documentation: system2]

With the `quarto` R package installed, the same call is `quarto::quarto_render("report.qmd", execute_params = list(since = "2026-02"))`; that package is not installed in the image, so the call is described and not run. The help page of `quarto_render()` has the arguments `input`, `output_format`, `output_file`, `execute`, `execute_params`, `execute_dir`, `cache`, `metadata`, `quiet` and `quarto_args`, and says that it runs the program, which is why the program has to be installed in any case. To produce the reports in a scheduled job, put the loop in a script and run it with `Rscript`, as in xref:programming-languages/r/scripts-and-the-command-line.adoc[Scripts and the Command Line].

=== HTML

HTML is the default and the richest format. == Quarto projects and _quarto.yml

A Quarto project is a directory with a `+_quarto.yml+` file. The project gives four things, according to the documentation: a way to render all or some of the files of a directory with one command, a way to share YAML options between documents, the ability to redirect the outputs to another directory, and the ability to freeze rendered output so that documents are not re-executed unless they changed. A project has a type: `default` (a set of documents), `website`, `book` or `manuscript` (the documentation also lists `blog` and `confluence` among the choices of `quarto create project`), and the type adds behaviour: a website has navigation and a search box, a book has chapters and cross-references. Documents do not need a project, as the render of `report.qmd` above shows; a project is for several documents, or for options that should apply to all of them.

The project file for the shelf report is the smallest useful one. It names the document to render, so that other `.qmd` files in the directory (a draft, a test) are not rendered; it gives all HTML documents a table of contents; and it freezes the execution of the documents.

[source,yaml]
----
project:
  type: default
  render:
    - report.qmd

format:
  html:
    toc: true

execute:
  freeze: auto
----

Source: https://quarto.org/docs/reference/projects/options.html[Quarto documentation: Project Options]

The options come from the documentation. Under `project`: `type`, `render` (the files to render; the default is all valid input files, apart from those whose name starts with a dot or an underscore and `README` files), `output-dir`, `execute-dir`, `lib-dir`, `resources`, `pre-render` and `post-render` scripts, and `preview`. The `format` key holds the options for each output format, here `toc: true` for the HTML of every document of the project, and the `execute` key the defaults for chunks, here `freeze: auto`. The `render` list accepts wildcards and a `!` prefix to exclude files, for example `+"*.qmd"+` and `+"!draft.qmd"+`. Document options are merged with the project options: objects and arrays are merged instead of replaced, the document wins on a conflict, and the exception is `format`: a document that defines `format` must define the whole list of formats it wants. The order is `+_quarto.yml+`, then a `+_metadata.yml+` in a directory (the options of the documents under it), then the YAML of the document. A file `+_quarto.yml.local+` holds changes that are not for version control, such as `execute: cache: true` on one machine, and `metadata-files` includes other YAML files.

== R Markdown is still maintained

R Markdown is the older of the two systems, and it did not stop when Quarto appeared. The Quarto FAQ for R Markdown users says it plainly: R Markdown is not going away, it will continue to be actively supported, everything that is in it will continue to work, and there are no plans to deprecate it; it also says that no major feature initiatives are planned for R Markdown and its related packages, which keep being maintained (smaller improvements and bug fixes) for a long time, that some new features may exist only in Quarto, that there is no need to switch, and that switching is cheap, because most `.Rmd` files render unmodified with Quarto. The facts agree with that: rmarkdown 2.32 was published on CRAN on 2026-09-01 and knitr 1.52 on 2026-09-06, and the rmarkdown NEWS for 2.32 lists fixes (LaTeX auxiliary files written to the output directory, a fix for `intermediates_dir`, `render()` in a forked cluster), a new minimum Pandoc of 2.8 and a change of the licence to MIT. The R Markdown ecosystem (bookdown for books, blogdown for sites, xaringan for slides, flexdashboard for dashboards, distill for articles) is the part that Quarto replaces with built-in features; those packages are separate and none was run on this page. All but distill had a CRAN release in the last year (distill's last release is from 2023), as the CRAN pages show. A rule of thumb that follows from this: keep the documents you have as they are, and start a new project in Quarto when it needs a feature that only Quarto has, such as its projects, its cross-references or Typst.

The R Markdown twin of the report differs from `report.qmd` only in syntax. The script tangles the twin with the default level of documentation, which adds a comment with the chunk header before each chunk, and the Quarto document, where the hash-pipe options are kept as comments (since knitr 1.44). == Sweave, the older form

Sweave is the original weaving system of R, and it ships with R, in the `utils` package. It processes `.Rnw` files, which are LaTeX documents with R code, and it is the format that the manual section on package vignettes is written around. A chunk begins with `+<<label, options>>=+` at the start of a line and ends with `@` at the start of a line; an inline expression is `+\Sexpr{...}+`. The file for the shelf is the smallest example that has a chunk with its code and result, an inline expression and a chunk with `echo=FALSE`:

[source,text]
----
\documentclass{article}
\begin{document}

<<load>>=
loans <- read.csv("loans.csv", colClasses = "character")
nrow(loans)
@

The shelf recorded \Sexpr{nrow(loans)} loans.

<<years, echo=FALSE>>=
table(substr(loans$loan_date, 1, 4))
@

\end{document}
----

Source: https://cran.r-project.org/doc/manuals/r-release/R-exts.html#Writing-package-vignettes[Writing R Extensions: Writing package vignettes]

The result has `knitrout` and `kframe` environments instead of `Schunk`, the code is highlighted by LaTeX macros (`\hlkwd{read.csv}`), and the output lines have the knitr prefix `+##+`. That is the difference in miniature: the document is the same, the engine is knitr, and the options and the look come from knitr. The cost of Sweave and `.Rnw` is that everything, including the text, is LaTeX, so a web page, a Word file or slides need a different source. Sweave is still supported and is still the format that the manual `Writing R Extensions` describes, with an engine `utils::Sweave` that needs no `VignetteBuilder` field; other engines are named by the package that provides them, and `Non-Sweave vignettes` is the section that explains how.

== Vignettes and the quarto package

A package vignette is a report that is a part of a package, and it is built when the package is built. The `shelf` package has one, `vignettes/shelf.Rmd`, which is an R Markdown document with the header lines that R reads (`+%\VignetteEngine{knitr::rmarkdown}+`) and the field `VignetteBuilder: knitr` in `DESCRIPTION`; xref:programming-languages/r/documentation-with-rd-roxygen2-and-vignettes.adoc[Documentation with Rd, roxygen2 and Vignettes] shows the file and builds it, and xref:programming-languages/r/creating-packages.adoc[Creating Packages] the package. A vignette in Quarto uses `VignetteBuilder: quarto` in `DESCRIPTION`, `quarto` in `Suggests` and the engine `+%\VignetteEngine{quarto::html}+` in the `.qmd` file; the `quarto` R package, which provides the engine and `quarto_render()`, is not installed in the image, so that route is described and not run (the documentation page shows the Quarto program rendering such a file by hand). The `quarto` package version on CRAN at the time of writing is 1.5.1.

For a vignette the choice between the systems is practical. knitr with R Markdown has no dependency outside R and Pandoc, and is the default of the package tooling. Quarto vignettes need the Quarto program on every machine that builds the package, and are best kept for a package whose other documentation is already in Quarto.

== Pitfalls

* Paths. Every path in a chunk is relative to the directory of the document (or to `execute-dir` in a project, or to `root.dir`). A report that works from the project directory and fails from another one is reading a file by a path that depends on where it was started; keep the data next to the document or build the path from the project, and do not call `setwd` in a chunk.
* The clock. A report that asks for `Sys.Date` or `Sys.time` is a different report every day, so it cannot be compared with last month's or reproduced from the same inputs. Put the date of the report in a parameter, as the report puts `shelf_today` at the top, and show it in the text.
* Randomness. A chunk that simulates or samples gives different numbers at each render. Call `set.seed()` in the first chunk, and remember that the sequence depends on the order of the chunks, and on the RNG kind, which xref:programming-languages/r/distributions-and-random-numbers.adoc[Distributions and Random Numbers] explains.
* The session. Under `rmarkdown::render()` with the default `envir`, the document sees the objects of the calling environment. Render from a clean process (a script run with `Rscript`, or Quarto), and with `envir = new.env()` when you must call it from a session.
* The defaults of `echo`, `error` and `fig-width` differ between knitr's `knit()`, R Markdown, Quarto and the output format (revealjs shows no code by default). Set what you rely on in the header.
* Inline code in the YAML header does not work (the Quarto documentation says so), and Markdown in the result of the Quarto inline form is escaped; the knitr form keeps it.
* A figure and a table that are `fig-` and `tbl-` labelled are numbered by Quarto; R Markdown has no such cross references of its own (the bookdown package adds them), so the same labels only name the chunks.
* Large outputs. An HTML file with embedded resources is one large file, and a cache directory can grow quickly; keep `*_cache` and `.quarto` out of version control, and commit `+_freeze+` deliberately.
* Dependencies. A document that loads a package that is not installed fails at that chunk. Declare the packages with `library()` in the first chunk, so that the failure is early and clear, and pin the versions of a long-lived report with xref:programming-languages/r/reproducible-environments-with-renv.adoc[Reproducible Environments with renv].
* Secrets. A report that is rendered on a server needs credentials for its data; take them from environment variables (`Sys.getenv()`), never from the document, because the document and its HTML are often published.

|Older tutorial writes |Current practice |Why |Since
