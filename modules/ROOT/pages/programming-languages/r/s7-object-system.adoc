== What S7 is and where it stands

S7 was designed and implemented by the R Consortium Object-Oriented Programming Working Group, a group that includes members of R Core, of Bioconductor, of Posit and the tidyverse, and of the wider R community (https://rconsortium.github.io/S7/[S7 package documentation: S7]). Its motivation is a list of difficulties that the group found in practice with the two systems that ship with R (https://rconsortium.github.io/S7/articles/motivation.html[S7 package documentation: Motivation for S7]):

* S3 has no formal class definition, so nothing says which properties an object has, and its attributes are read with `attr()`, which matches partially and returns `NULL` for a misspelt name. S7 describes a class with an object made by `new_class()` and reads properties with `@`, which does neither.
* The dispatch rules of S3 are complicated and `NextMethod()` depends on the whole class hierarchy and on what methods happen to be registered. S7 asks for an explicit `super()` call that names the parent class.
* S3 is built for single dispatch. S7 provides multiple dispatch for any generic.
* S4 allows multiple inheritance and picks methods with a distance metric that is hard to predict. S7 has single inheritance and a simpler lookup. S4 was also a clean break from S3, while S7 objects are S3 objects, which is what makes it possible to convert an existing package with little work.
* Properties can be dynamic (computed on demand), so the representation of an object can change while code that reads `x@name` keeps working.

The standing of the package needs a careful statement, because it is easy to find it overstated. As of R 4.6.1 S7 is not part of base R: it has to be installed from CRAN and attached or called with `S7::`, and `exists("new_class", envir = baseenv())` is `FALSE`. The site of the package says that its long-term goal is to merge S7 into base R, that the design is considered sound, but that the package is somewhat experimental because it has little use in the wild so far and breaking changes are possible (https://rconsortium.github.io/S7/[S7 package documentation: S7]). The one thing that did arrive in base R is groundwork. R 4.4.0 renamed the internal type `S4SXP` to `OBJSXP` "to support experimenting with alternative object systems", with contributions from the same working group (https://cran.r-project.org/doc/manuals/r-release/NEWS.html[R NEWS: Changes in R 4.4.0]; the type table is in https://cran.r-project.org/doc/manuals/r-release/R-ints.html#SEXPTYPEs[R Internals: SEXPTYPEs]). An S7 object is such an object, and `typeof()` prints `"object"` for it, as the first script shows. R 4.3.0 had already made the `@` operator an S3 generic (https://cran.r-project.org/doc/manuals/r-release/NEWS.html[R NEWS: Changes in R 4.3.0]), which is what lets `@` read the properties of an S7 object. The base-types background is in xref:programming-languages/r/oop-overview-and-base-types.adoc[OOP Overview and Base Types].

The package is nevertheless used by a very widely installed one. The ggplot2 4.0.0 NEWS lists, under breaking changes, that "the S3 parts of ggplot2 have been replaced with S7 bits" (https://ggplot2.tidyverse.org/news/index.html[ggplot2 NEWS]), and the script below shows what a plot object looks like in ggplot2 4.0.3. The practical consequence for a reader of this page is the same as for any package that exports S7 classes: the plot objects are S7 objects, `@` and `prop_names()` work on them (`p@data` is the data frame of the plot), and their class vector now includes `"S7_object"`.

Five things to take from the output. The attached package is version 0.2.2 and `new_class` is not in the base environment. An S7 object has type `"object"` (the `OBJSXP` type of R 4.4.0 and later), it is an object for `is.object()` and not an S4 object for `isS4()`, and its attributes are `class`, `S7_class` and one attribute per property: S7 stores the class definition inside every instance, and properties are attributes. The S3 class vector has two elements, the class name and `S7_object`. ggplot2 4.0.3 builds its plots as S7 objects, which `S7_inherits()` confirms with one argument. And the `:=` operator used by the development documentation does not exist in 0.2.2: code copied from the site fails with `could not find function ":="`, and the working form is `+Dog <- new_class("Dog", ...)+`.

== Classes with `new_class()`

A class is defined by calling `new_class()` and is represented by the object it returns. That object is also the constructor: calling it makes instances. The result should be assigned to a variable with the same name as the first argument, the class name, which is what appears in messages and in the S3 class vector. The arguments are:

[cols="2,5",options="header"]
|===
|Argument |Meaning
|`name` |The class name, a string. By convention CamelCase and equal to the variable the result is assigned to.
|`parent` |The parent class: another S7 class, a base class such as `class_double` (see below), an S3 class declared with `new_S3_class()` or an S4 class. The default is `S7_object`, the root of every S7 hierarchy.
|`package` |The package that defines the class, or `NULL`. Inside a package, `new_class()` fills it in automatically. When it is set, the S3 class vector contains `"package::Class"` instead of `"Class"`.
|`properties` |A named list of properties. A plain class (`class_character`) is a shorthand for `new_property(class_character)`; use `new_property()` for a default, getter, setter or validator.
|`abstract` |`TRUE` makes a class that cannot be instantiated; only its subclasses can.
|`constructor` |A function that replaces the default constructor. It must end with a call to `new_object()`.
|`validator` |A function of one argument, `self`, that returns `NULL` when the object is valid and a character vector describing the problems otherwise.
|===

Source: https://rconsortium.github.io/S7/reference/new_class.html[S7 package documentation: new_class]

The book of the shelf scenario becomes the class below, with the six fields of `book()` in the same order and the same rules as `validate_book()` in `scenario.R`: every field has length one, the title is not empty, a present ISBN passes `is_valid_isbn13()`, and the year is at most 2100. The `default = NA_character_` of each property matters: without a default a property starts as a zero-length vector (`character(0)`), and a validator that insists on length one would reject the class's own default object, as the last part of the second script shows.

[source,r]
----
library(S7)
source("scenario.R")
# nolint start: object_name_linter.

# The six scenario fields, each a property with a type and an NA default.
Book <- new_class("Book",
  properties = list(
    title = new_property(class_character, default = NA_character_),
    author = new_property(class_character, default = NA_character_),
    isbn = new_property(class_character, default = NA_character_),
    year = new_property(class_integer, default = NA_integer_),
    genre = new_property(class_character, default = NA_character_),
    pages = new_property(class_integer, default = NA_integer_)
  ),
  # The same rules as validate_book() in scenario.R. The validator returns NULL
  # (valid) or a character vector of problems.
  validator = function(self) {
    if (any(lengths(props(self)) != 1L)) {
      return("every property of a book must have length 1")
    }
    if (is.na(self@title) || !nzchar(self@title)) {
      return("a book needs a title")
    }
    if (!is.na(self@isbn) && !is_valid_isbn13(self@isbn)) {
      return(paste("invalid ISBN-13:", self@isbn))
    }
    if (!is.na(self@year) && self@year > 2100L) {
      return(paste("implausible year:", self@year))
    }
    NULL
  }
)

dune <- Book(
  title = "Dune", author = "Frank Herbert", isbn = "9780306406157",
  year = 1965L, genre = "Science fiction", pages = 412L
)

== Properties with `new_property()`

A property is the S7 counterpart of an S3 attribute or an S4 slot. In its simplest form it is just a class, which S7 checks on every assignment. `new_property()` adds four things that a plain class cannot express:

* `default`, the value a new object gets when the constructor is not given one. A quoted call, such as `quote(Sys.time())`, becomes a lazy default evaluated at construction.
* `validator`, a function of the value that returns `NULL` or a message. The message should not repeat the property name: S7 prepends `@name`, which lets one property definition be reused for several properties.
* `setter`, a function of `self` and `value` that returns the modified object. It runs on every assignment, including the one made by the constructor, and is the place to normalise a value.
* `getter`, a function of `self` that computes the value on demand. A property with a getter and no setter is read-only. A property with both is fully dynamic and can be assigned.

The class below adds three of them to the book: an `isbn` setter that normalises the ISBN with `normalise_isbn()` from the scenario, a validator for `pages` and an `age` property computed from `year` and `shelf_today`. The assignment `+self@isbn <- value+` inside the setter does not call the setter again.

[source,r]
----
# new_property() adds what a plain class cannot say: a default, a validator for
# one property, a setter and a getter.
Book <- new_class("Book",
  properties = list(
    title = new_property(class_character, default = NA_character_),
    author = new_property(class_character, default = NA_character_),
    # A setter returns the modified object; this one normalises the ISBN.
    isbn = new_property(
      class_character,
      default = NA_character_,
      setter = function(self, value) {
        if (length(value) == 1L && !is.na(value)) {
          value <- normalise_isbn(value)
        }
        self@isbn <- value
        self
      }
    ),
    year = new_property(class_integer, default = NA_integer_),
    genre = new_property(class_character, default = NA_character_),
    # A property validator returns a message; S7 adds "@pages" itself.
    pages = new_property(
      class_integer,
      default = NA_integer_,
      validator = function(value) {
        if (length(value) == 1L && !is.na(value) && value < 1L) {
          "must be positive"
        }
      }
    ),
    # A getter makes the property computed: read-only without a setter.
    age = new_property(
      class_integer,
      getter = function(self) {
        if (is.na(self@year)) {
          return(NA_integer_)
        }
        as.integer(format(shelf_today, "%Y")) - self@year
      }
    )
  ),
  validator = function(self) {
    if (is.na(self@title) || !nzchar(self@title)) {
      "a book needs a title"
    }
  }
)

dune <- Book(title = "Dune", isbn = "978-0-306-40615-7", year = 1965L)

== Validation: when it runs and how to avoid it

S7 validates an object at three moments: when the constructor builds it, whenever a property is assigned with `+@<-+` or `+prop<-+`, and when `validate()` is called. Validation has two layers. First S7 checks the declared type of every property and the property validators (`properties = TRUE`, the default of `validate()`). If all of them pass, the validator of the class runs, and then the validators of the parent classes up the chain (`recursive = TRUE`); the problems of all the classes are collected and reported together. The class validator is the place for rules that involve several properties, and property validators are the place for rules about one.

An assignment that fails leaves the object unchanged (the script prints the title after a rejected assignment). Direct use of `attr()` bypasses the checks, which is what `validate()` is for. The script below shows both, and then a case where checking after every assignment is a nuisance: a `Loan` whose return date must not precede its loan date (row 12 of the scenario's `loans` is such a loan, and it is rejected by the constructor), and which is moved by changing both dates. Moving them one at a time passes through an invalid state, so the first assignment is rejected. `pass:c[props<-()]` assigns both at once and validates once, and `valid_eventually()` runs any function on the object with validation switched off and validates at the end. `valid_implicitly()` is the same without the final check, for performance-critical code that cannot produce an invalid object.

== Constructors and `new_object()`

The default constructor of a class has one argument per property, in order, with the property defaults as default values (parent properties first). It is a good constructor when the arguments are the properties. When they are not, because the caller should be able to give raw values that the constructor tidies up, supply `constructor =`. A constructor is an ordinary function that ends with a call to `new_object()`: the first argument is an object of the parent class (`S7_object()` when there is no parent), followed by one named argument per property. `new_object()` creates the object, runs the property setters and validates it, so a custom constructor does not have to call `validate()`.

The constructor below does for the S7 `Book` what the `book()` helper does for the S3 `book`: it trims the strings, normalises the ISBN and coerces the numbers, so the user can pass the values exactly as they come out of `books.csv`. Because the checks happen in `new_object()`, the padded title of row 3 is trimmed first and an invalid ISBN is still rejected.

A subclass of a class with a custom constructor does not need one of its own. The default constructor of the subclass takes `+...+`, forwards it to the parent constructor, and adds one named argument for each property the subclass introduces, as the printed `args(AudioBook)` shows (the first arguments are the parent's, `narrator` and `minutes` are the new ones). That is the design choice behind the rule that a constructor must end with `new_object()`: the object for the parent class is built by the parent constructor, and the child adds its own properties.

== Inheritance, abstract classes and class queries

A class is a subclass of another when `parent =` names it. S7 has single inheritance only: `parent` is one class. A subclass has the properties of its parent first and then its own, its constructor accepts both sets, and its validator is checked in addition to the parent's. The `AudioBook` below adds `narrator` and `minutes` to a trimmed `Book`. The parent part of the object is built and validated first, which is why the first message reports `<Book>` and not `<AudioBook>`; `validate()` checks the whole object against the validator of the class and of every ancestor and reports all the problems.

== Generics and methods

In S7, as in S3 and S4, a method belongs to a generic function and not to a class: a call looks like any other function call, `describe(x)`, and the generic finds the method that matches the class of its arguments. A generic is created with `new_generic(name, dispatch_args)`: the name of the generic (assigned to a variable with the same name, for the same reason as a class) and the character vector of the arguments that take part in dispatch. The default body is a single call to `S7_dispatch()`, which finds the method for the classes of the dispatch arguments and calls it with the arguments of the generic call. Printing a generic shows its signature and the methods registered so far, so unlike an S3 generic it is easy to find out what exists.

A method is registered with `pass:c[method(generic, class) <- function]`, and the rest of the page writes it like that. The first arguments of the method must be the dispatch arguments, without default values. A method may add arguments that the generic does not have, provided the generic has `+...+`, which the generic created by `new_generic()` does. The package documentation advises that the methods themselves normally do not take `+...+`, so that a misspelt argument is an error and not silently swallowed, and says this is a deliberate difference from S3 (https://rconsortium.github.io/S7/articles/generics-methods.html[S7 package documentation: Generics and methods]).

A child class inherits the method of its parent until it has a method of its own. A child method that wants to reuse the parent's implementation calls the generic on `super(x, to = Book)`: the object is passed through the generic again, but dispatch treats it as an instance of `Book`. That is the difference from `NextMethod()` and `callNextMethod()`: the parent class is named where the call is written, every argument is passed explicitly, and nothing depends on the class vector at run time (https://rconsortium.github.io/S7/reference/super.html[S7 package documentation: super]). When there is no method for the class of the argument, the error names the generic and the dispatch class, with `MISSING` for an omitted argument. `class_any` registers a fallback for every class, S7 or not.

=== Customising the generic

The default body is generated, but `new_generic(name, dispatch_args, fun)` accepts a function of your own, which must contain a call to `S7_dispatch()`, usually the last call. There are four reasons to write one:

* To add a required argument that does not take part in dispatch: give it no default.
* To add an optional argument: put it after `+...+`, so that callers must name it in full.
* To do some standard work before dispatch, such as checking an argument once for every method.
* To drop `+...+`, for a low-level generic whose methods must not take extra arguments.

When a method is registered, S7 compares it with the generic. A method that lacks an argument the generic added, or gives it a different default, only produces a warning (the generic may come from another package that is changing its interface), but a method whose first arguments are not the dispatch arguments is an error. Registering a method twice replaces the first and prints a message. The script uses a `due()` generic with a `days` argument that defaults to the scenario's `loan_days`.

== Multiple dispatch

A generic with more than one dispatch argument chooses its method from the classes of all of them. `new_generic("compare", c("x", "y"))` has two, and a method is registered for a list of two classes. `class_any` matches any class and `class_missing` an omitted argument, so a three-method generic can cover a specific pair, a specific class and a catch-all, as the script does. The lookup for each argument walks from the class itself up its hierarchy to `ANY`; the pair that is found first, scanning the first argument's classes and, within each, the second's, wins. `method_explain()` prints the whole search order, which is the way to understand why `compare(audio, "Dune")` ran the `(Book, character)` method. S7 chose a deliberately simple, greedy rule instead of the distance metric of S4, and the authors say they do not expect multiple dispatch to be used as much as it is in S4 (https://rconsortium.github.io/S7/articles/generics-methods.html[S7 package documentation: Generics and methods]). A class union (below) in a method signature is shorthand for one method per member class.

[source,r]
----
Book <- new_class("Book",
  properties = list(
    title = new_property(class_character, default = NA_character_),
    year = new_property(class_integer, default = NA_integer_)
  )
)
AudioBook <- new_class("AudioBook",
  parent = Book,
  properties = list(
    minutes = new_property(class_integer, default = NA_integer_)
  )
)

# Two dispatch arguments: methods are registered for a list of two classes.
compare <- new_generic("compare", c("x", "y"))
method(compare, list(Book, Book)) <- function(x, y, ...) {
  sign(x@year - y@year)
}
method(compare, list(Book, class_character)) <- function(x, y, ...) {
  as.integer(x@title == y)
}
method(compare, list(class_any, class_any)) <- function(x, y, ...) {
  NA_integer_
}
compare
#> <S7_generic> compare(x, y, ...) with 3 methods:
#> 1: method(compare, list(Book, class_character))
#> 2: method(compare, list(Book, Book))
#> 3: method(compare, list(class_any, class_any))

older <- Book(title = "Emma", year = 1815L)
newer <- Book(title = "Dune", year = 1965L)
audio <- AudioBook(title = "Dune", year = 1965L, minutes = 1260L)

compare(older, newer)
#> [1] -1
compare(newer, audio)
#> [1] 0
compare(audio, "Dune")
#> [1] 1
compare("Dune", audio)
#> [1] NA
compare(1, 2)
#> [1] NA

# class_missing matches an argument that was not supplied.
compare(older)
#> [1] NA
method(compare, list(Book, class_missing)) <- function(x, y, ...) {
  "no second book"
}
compare(older)
#> [1] "no second book"

== `print`, `format` and the S3 generics

Printing an S7 object without a method shows the class name and one line per property. To change it, register a method for `print`, which is an S3 generic: `method()` accepts S3 generics, S4 generics and S7 generics alike, and for an S3 generic S7 registers an S3 method for the class behind the scenes, so `print(x)`, auto-printing at the console and `methods(class = "Book")` all see it (https://rconsortium.github.io/S7/articles/compatibility.html[S7 package documentation: Compatibility with S3 and S4]). The same applies to `format()`, `length()`, `as.character()`, `summary()` and to the operators, which take two dispatch arguments: a method for `==` is registered for a `list` of two classes. Methods for the arithmetic and comparison operators are covered with the group generics of S3 in xref:programming-languages/r/s3-group-generics-and-operator-overloading.adoc[S3 Group Generics and Operator Overloading].

[source,r]
----

The `format()` error at the start is worth reading. Three cautions come out of the last part. First, the method for `==` decides what "equal" means: it compares titles and authors, so a book without a year equals the one with a year, while `identical()` compares everything. Second, `all.equal()` of two S7 objects returned `TRUE` for objects whose properties differ, on R 4.6.1 with S7 0.2.2, so it must not be used to compare them (`identical()` and `all.equal(props(x), props(y))` do compare the properties; https://search.r-project.org/R/refmans/base/html/all.equal.html[R documentation: all.equal]). Third, `super()` is for S7 generics: inside a method for an S3 generic such as `print()` it produces a printable "super" object and not the parent's result, and the recommended way to reach the underlying vector of a class built on a base type is `S7_data()`, as the last two prints show.

== Conversion, unions and base classes

`convert(from, to)` is the one built-in generic of S7. It dispatches on both arguments, and it is special in two ways: `to` is a class and not an object, and the class of `to` does not use inheritance, because a conversion method written for a parent would return parent objects. It has two default methods, down to a parent (the extra properties are dropped) and up to a child (the properties are copied and the new ones are initialised, optionally by extra arguments). Any other conversion is a method on a pair of classes, which replaces the S3 convention of `as.foo()` generics and the `setAs()` of S4 (https://rconsortium.github.io/S7/reference/convert.html[S7 package documentation: convert]). The first part of the script converts a `Book` to a string and a list to a `Book`.

A union says that a property or a method signature accepts one of several classes. `new_union()` builds it and `|` is the shorthand; `NULL | class_character` is the idiom for an optional property, whose default is `NULL`. The default value of a union property is the default of its first member, which is why `class_numeric` (itself the union of integer and double) gives `int(0)` for `pages` in the constructor. In a method, a union is only shorthand for registering the method once for each member; `method()` cannot look one up (`+Can't dispatch on unions; must be a concrete type+`). This differs from S4, where a class union is resolved at dispatch time (https://rconsortium.github.io/S7/reference/new_union.html[S7 package documentation: new_union]).

== Working with S3

S7 is implemented on top of S3, which is why most interaction with S3 just works (https://rconsortium.github.io/S7/articles/compatibility.html[S7 package documentation: Compatibility with S3 and S4]). An S7 object has the S3 class attribute, so `class(x)` is the class vector (`"Book"`, `"S7_object"`, with every parent in between), `inherits()` works, and a plain S3 method such as `summary.Book` is found by an S3 generic. The differences from an S3 object are that S7 adds the `S7_class` attribute that holds the class definition and that its fields are properties, implemented as attributes: code that reads them with `attr()` still works, but inside S7 code properties should be read with `@`. When the class belongs to a package, the S3 class name is `"package::Class"`, which is a name that needs backticks in a hand-written S3 method definition (the `Pkg` class below shows the vector).

An S3 class that has no formal definition, like the `book` of the scenario, has to be declared before S7 can use it. `new_S3_class("book")` makes the declaration from the S3 class vector, and it can be used in three places: as the dispatch class of a method, as the type of a property, and as a member of a union. Declaring the class with only its name is enough for those three. What it cannot do is make S7 construct an object of the class: a property of an S3 type with no default makes `Shelf(label = "A")` fail with `+S3 class <book> doesn't have a constructor+`, and extending an S3 class with `parent = ` needs a constructor whose first argument is `.data`, which is more work and is described in https://rconsortium.github.io/S7/reference/new_S3_class.html[S7 package documentation: new_S3_class]. The S7 definition of `data.frame` that ships with the package, `class_data.frame`, is such a declaration.

== Working with S4

S4 classes can take part in S7 in three places, each shown in the next script. An S4 class (its definition from `methods::getClass()`) can be the dispatch class of an S7 method and the type of an S7 property. For the opposite direction, an S7 method for an S4 generic, the S7 class is first registered with S4 by `S4_register()`, once, and then `method()` is used as for any generic. After that the S4 generic keeps its S4 methods next to the S7 one. An S7 object itself is not an S4 object: `isS4()` is `FALSE` for it, although `methods::is()` knows its class.

[source,r]
----
Book <- new_class("Book",
  properties = list(
    title = new_property(class_character, default = NA_character_),
    year = new_property(class_integer, default = NA_integer_)
  )
)
dune <- Book(title = "Dune", year = 1965L)

# Rscript attaches methods, so setClass() and friends are available; the
# methods:: prefix is only for clarity.
methods::setClass("Reader", slots = c(name = "character"))
ana <- methods::new("Reader", name = "Ana Ruiz")

# 1. An S4 class in an S7 method signature: pass its class definition.
greet <- new_generic("greet", "x")
method(greet, methods::getClass("Reader")) <- function(x, ...) {
  paste("Hello,", x@name)
}
greet(ana)
#> [1] "Hello, Ana Ruiz"

# 2. An S4 class as the type of an S7 property.
Loan <- new_class("Loan",
  properties = list(
    member = methods::getClass("Reader"),
    book = Book
  )
)
loan <- Loan(member = ana, book = dune)
loan@member@name
#> [1] "Ana Ruiz"
loan@book@title
#> [1] "Dune"

# 3. An S7 method for an existing S4 generic: register the S7 class with S4
# once, then use method() as usual.
methods::setGeneric("label", function(x) standardGeneric("label"))
#> [1] "label"
S4_register(Book)
method(label, Book) <- function(x) paste0("[", x@title, "]")
label(dune)
#> [1] "[Dune]"

# 4. The same S4 generic keeps its S4 methods next to the S7 one.
methods::setMethod("label", "Reader", function(x) paste0("<", x@name, ">"))
label(ana)
#> [1] "<Ana Ruiz>"

# The S7 object itself is not an S4 object.
isS4(dune)
#> [1] FALSE
isS4(ana)
#> [1] TRUE
methods::is(dune, "Book")
#> [1] TRUE
# nolint end
----

Source: https://rconsortium.github.io/S7/reference/S4_register.html[S7 package documentation: S4_register]

`Rscript` attaches the `methods` package, so `setClass()` and friends need no `library(methods)`; the `methods::` prefix in the script is for clarity (the S4 system is described in xref:programming-languages/r/s4-classes-and-methods.adoc[S4 Classes and Methods]). S7 properties play the role of S4 slots, with the difference that an S7 property can be computed by a getter while an S4 slot is a stored field with a declared class. Unions behave differently as well: an S4 class union is resolved at dispatch time, an S7 union at the time a method is registered. The package documentation describes further interoperability that the development version has (an S7 class that extends an S4 class, and an S4 class that extends an S7 class); it is not part of 0.2.2 and is not used here.

== S7 in a package

The packages article of the S7 site collects what is different when classes and generics are defined in a package instead of a script (https://rconsortium.github.io/S7/articles/packages.html[S7 package documentation: Using S7 in a package]). The checklist, for 0.2.2:

* Add `S7` to the `Imports` field of `DESCRIPTION`, and import its functions into the namespace (`import(S7)` in `NAMESPACE`, or `@import S7` with roxygen2).
* Call `S7::methods_register()` in the package's `.onLoad()`. S7 registers methods when the package is loaded, not with `export` directives in `NAMESPACE` the way S3 and S4 do. The call is strictly necessary only when the package registers methods for generics defined in other packages, but there is no harm in adding it, and it keeps the next change from forgetting it.
* Export the class and the generics that users should call: a class is exported by exporting its constructor, which is the object returned by `new_class()`. If a class is exported, set its `package` argument so that classes with the same name in different packages are told apart; inside a package `new_class()` fills it in.
* Define subclasses after their parents and methods after both the class and the generic. When the definitions live in several files, the `Collate` field of `DESCRIPTION` (or the roxygen2 `@include` tag) fixes the loading order.
* To register methods for generics (or classes) from a package that is only suggested, use `new_external_generic()` (the article of the site also names `new_external_class()` for classes, which 0.2.2 does not export) so that the method is registered when that package is loaded.
* S7 properties are read with `@`. Before R 4.3.0 `@` only works for S4 objects, so a package that supports older R versions has to use `prop()` or conditionally import S7's `@`; requiring R 4.3.0 or later with `Depends: R (>= 4.3.0)` avoids the problem.

The `DESCRIPTION` stores the roxygen2 version in `Config/roxygen2/version` (roxygen2 8.x; older versions used a different field), and `Config/roxygen2/markdown: TRUE` turns on the Markdown syntax in comments.

With roxygen2, a class is documented like its constructor function and a generic like any other function: `@param` documents the arguments, which are the properties unless the constructor was customised, `@returns` the object, and `@export` makes the name visible. == The book in S3, S4, R6 and S7

The sibling pages of this section model the same `book` of the shelf scenario with the same six fields in the same order (`title`, `author`, `isbn`, `year`, `genre`, `pages`) and the same validation rules as `validate_book()`: the S3 `book` of xref:programming-languages/r/s3-classes-and-generics.adoc[S3 Classes and Generics], the S4 class `Book` of xref:programming-languages/r/s4-classes-and-methods.adoc[S4 Classes and Methods], the Reference Class `BookRC` and the R6 class `BookR6` of xref:programming-languages/r/reference-classes-and-r6.adoc[Reference Classes and R6], and the S7 class `Book` of this page. The next script builds a trimmed version (title, author and year) of each of S3, S4, R6 and S7, and of a Reference Class, in one session and asks the questions on which they differ in behaviour: is an empty title rejected when the object is built, when a field is assigned afterwards, is a value of the wrong type rejected, what happens to the original when a copy is modified, and what do `class()`, `typeof()` and `isS4()` say. The S4 class is called `BookS4` there only so that it can live next to the S7 `Book` in the same session.

Reading the table row by row, the S7 column differs from S3 in that classes are defined and validated, from S4 in that the validation also runs at assignment and the dispatch rule is simpler, and from R6 in that objects are values and methods belong to generics. The choice is not exclusive: S7 interoperates with S3 and S4, and the plot object of ggplot2 4.0.3 is an S7 object that is also an S3 object.

== Pitfalls collected

* The type check is strict about integers and doubles: `year = 1965` is rejected with `@year must be <integer>, not <double>`; use `1965L` or coerce in a custom constructor.
* A property without `default` starts empty, with length zero, so a validator that wants length one rejects the default object: give every property a `default`.
* The name given to `new_class()` and `new_generic()` should be the name of the variable the result is assigned to; the string is what the S3 class vector and the messages use.
* `@` does not match names partially and a misspelt property is an error, `+Can't find property <Book>@subtitle+`, but the constructor reports a misspelt argument as the plain R error `unused argument`.
* `+method(generic, class) <- f+` needs the first arguments of `f` to be the dispatch arguments, otherwise registration is an error; a missing or different extra argument is only a warning, so read warnings from `pass:c[method<-]`.
* A call with no matching method says `+Can't find method for+` the generic and the dispatch class. `class_any` is the explicit fallback.
* `super()` works in S7 generics and does not work in S3 generics such as `print()`; use `S7_data()` there.
* `all.equal()` on two S7 objects returned `TRUE` for different properties with R 4.6.1 and S7 0.2.2; compare `props()` or use `identical()`.
* `format()` of an S7 object without a method fails inside `format.default()` with an unusual message; register a method for `format`.
* A class union cannot be the target of `method()` lookup and cannot be dispatched on as a concrete type: the lookup says `+Can't dispatch on unions; must be a concrete type+`.
* `methods_register()` belongs in a package `.onLoad()`; at the console it fails with `not a namespace`.
* The `:=` operator and some features of the development documentation (the S4 class helpers of the compatibility article, `new_external_class()`) are not in 0.2.2. Check `packageVersion("S7")` before copying code from the site.
