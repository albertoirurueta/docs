== Two graphics systems on one engine

=== The layers

https://cran.r-project.org/doc/manuals/r-release/R-ints.html#Graphics[R Internals] describes the structure in a few paragraphs (chapter 6, https://cran.r-project.org/doc/manuals/r-release/R-ints.html#Graphics-Devices[6.1 Graphics Devices] for the device layer). The graphics internals were redesigned so that several graphics systems can be installed on top of one graphics engine, and two exist: the base system (the R code of package `graphics`, https://cran.r-project.org/doc/manuals/r-release/R-ints.html#Base-graphics[6.3 Base graphics]) and the one implemented in package `grid`. At the bottom is the graphics device, which manages a plotting surface, a window or a file, and implements a small set of primitives: a circle, a rectangle, a line, connected lines, a polygon, a path, text and a raster image, plus a clipping rectangle, and answers questions such as the width of a string. Above it is the engine, which clips lines, rectangles and polygons, centres and adjusts text, renders plotmath expressions, maps colour names to the internal representation and manages display lists and snapshots. At the top are the graphics systems, base and grid. The engine has provision for 24 of them (since about 2001), but only these two exist. Base graphics records its operations on the engine's display list as `.Internal` calls, and grid records its own as `.Call.graphics` calls.

The packages follow the layers. `grDevices` holds the devices (`pdf()`, `svg()`, `png()`) and the colour tools; `graphics` is the base system; `grid` is the other system. `lattice` is a recommended package: it ships with R, it is installed in the default library, and it depends only on the base packages. The first script shows the package priorities and what the lattice `DESCRIPTION` says it needs.

=== Why grid exists

Base graphics draws into a single plotting region at a time. It has a state, the `par()` list, and each high-level function (`plot()`, `hist()`) draws a complete figure into a figure region it computes from `par("mfrow")`, `par("mar")` and friends. A drawn figure is pixels or vector commands; the only way to change a title is to draw the plot again. That model is simple and fast; chapter 12 of https://cran.r-project.org/doc/manuals/r-release/R-intro.html#Graphical-procedures[An Introduction to R] describes its procedures, and the xref:programming-languages/r/base-graphics-and-devices.adoc[base graphics page] shows how far it goes. grid was written to remove four limits.

* *Regions are objects.* A viewport is a rectangular region of the device (or of another viewport) with its own coordinate systems. A figure is made of viewports inside viewports, and layouts divide a viewport into rows and columns that may contain further layouts.
* *Units are symbolic.* A length can be given as a fraction of the region, in centimetres, in lines of text, or as the width of a string, and lengths can be added: `unit(1, "npc") - unit(2, "lines")` is "the height of the region minus two lines". The sum is worked out when the thing is drawn, in the region and font that apply then.
* *Graphical objects are R objects.* A rectangle, a text label or a whole axis can be created without drawing (`rectGrob()`), stored, combined in a tree (`gTree()`), edited and drawn.
* *A drawn plot can be edited.* Grid keeps its own display list of what was drawn, so `grid.edit()` can change a drawn label or colour and redraw.

Lattice and ggplot2 use all four. Lattice's panels, strips, axes and keys are grid viewports and grobs, which is why a lattice plot can be changed after it is drawn (the section on `trellis.focus()` below), and ggplot2's `ggplotGrob()` returns a table of grobs. The cost is that grid is lower-level and more verbose than base graphics for a quick plot, and that it is a different system.

=== Grid and base graphics do not mix

The two systems share the engine and the device but not their state. The overview help page of the package, `?Grid`, says in a single sentence that the two systems do not mix. Output from both can be put on the same page, and the script below does it, but the systems do not know about each other: base graphics does not know where grid put a viewport, grid does not list a base plot among its objects, and `+par(mfrow = ...)+` has no effect on grid or lattice output. The error "cannot pop the top-level viewport ('grid' and 'graphics' output mixed?)" is raised when `popViewport()` is called with nothing left to pop, and its wording points at the usual cause. The add-on package https://cran.r-project.org/web/packages/gridBase/index.html[gridBase] (not installed here and not run) provides functions to share a page between the two systems, and https://cran.r-project.org/web/packages/gridGraphics/index.html[gridGraphics] provides `grid.echo()`, which redraws a base graphics plot as grid objects so that it can be edited with grid tools; both are named here so that you know they exist, and their documentation is on CRAN.

[source,r]
----
source("scenario.R")
library(lattice)

# Loan duration in days next to the pages and genre of each returned book.
books$isbn <- normalise_isbn(books$isbn)
books$genre <- factor(tolower(trimws(books$genre)))
dur <- merge(loans, books, by = "isbn")
dur$days <- as.numeric(dur$return_date - dur$loan_date)
dur <- dur[!is.na(dur$days) & dur$days >= 0, ]
library(grid)
svg(tempfile(fileext = ".svg"), width = 6, height = 4)

# Base graphics keeps its state in par(); grid keeps it in viewports.
old <- par(mfrow = c(1, 2))
par("mfrow")
#> [1] 1 2
plot(dur$pages, dur$days)
# grid output does not know about base graphics: it has its own display list.
grid.ls()
#>
grid.rect(name = "on_top")
grid.ls()
#> on_top
par(old)

# par() settings have no effect on a lattice plot.
width_of_panel <- \() {
  trellis.focus("panel", 1, 1, highlight = FALSE)
  w <- convertWidth(unit(1, "npc"), "inches", valueOnly = TRUE)
  trellis.unfocus()
  round(w, 2)
}
grid.newpage()
print(xyplot(days ~ pages, data = dur))
width_of_panel()
#> [1] 4.85
par(mfrow = c(2, 2), mar = c(1, 1, 1, 1))
grid.newpage()
print(xyplot(days ~ pages, data = dur))
width_of_panel()
#> [1] 4.85
par(old)

# base layout() returns the number of figures; grid.layout() returns an object.
n_figures <- layout(matrix(1:4, nrow = 2))
n_figures
#> [1] 4
class(grid.layout(2, 2))
#> [1] "layout"
invisible(dev.off())
----

Source: https://search.r-project.org/R/refmans/grid/html/Grid.html[R documentation: Grid]

The last lines of that script show the other trap in the vocabulary. Base graphics has a function called `layout()`, which splits the device into figure regions by a matrix of numbers and returns the number of figures; grid has `grid.layout()`, which returns an object that describes the rows and columns of a viewport. The help page of `grid.layout()` warns not to confuse them, and not to use the base `layout()` together with grid graphics.

=== Devices

Both systems draw on a graphics device (xref:programming-languages/r/base-graphics-and-devices.adoc[Base Graphics and Devices]). With no device open, the first drawing call opens the default one. In an interactive session that is a window; under `Rscript` it is a PDF file called `Rplots.pdf`, which is why every script on this page opens an `svg()` device with a file in the session's temporary directory first. `svg()` is a Cairo-based device, and it is a good test device for grid because it supports the newer engine features (below). The default size of an `svg()` or `pdf()` device is 7 by 7 inches, and the conversions in later examples show it.

== Viewports

=== What a viewport is

`viewport()` describes a rectangular region of its parent, which is the device at the top level or another viewport. The object is only a description: it has no effect until it is pushed on the viewport tree. The arguments below are the ones in `viewport(x, y, width, height, default.units, just, gp, clip, mask, xscale, yscale, angle, layout, layout.pos.row, layout.pos.col, name)`.

[cols="2,5",options="header"]
|===
|Argument |Meaning
|`x`, `y`, `width`, `height` |Position and size, as units or numbers. A bare number is read in `default.units`, which is `"npc"`. The defaults are the centre of the parent and its whole size.
|`just` |Where the viewport hangs from its `(x, y)`: a name (`"left"`, `"right"`, `"centre"`, `"bottom"`, `"top"`) or two numbers from 0 (left or bottom) to 1.
|`xscale`, `yscale` |The data range of the region, `c(0, 1)` by default. They define the `"native"` unit.
|`gp` |A `gpar()` of graphical parameters that apply to everything drawn inside (below).
|`clip` |`"on"`, `"inherit"` (the default) or `"off"`. Since R 4.1.0 it can also be a grob, whose outline is a clipping path.
|`mask` |`"none"`, `"inherit"` or, since R 4.1.0, a grob that masks what is drawn inside.
|`angle` |Rotation of the region in degrees, anticlockwise.
|`layout` |A `grid.layout()` that splits the region into rows and columns.
|`layout.pos.row`, `layout.pos.col` |The cells of the parent's layout that this viewport occupies (rows and columns as a number or a range).
|`name` |An identifier used to find the viewport in the tree. If it is missing, grid makes one up, such as `GRID.VP.1`.
|===

Source: https://search.r-project.org/R/refmans/grid/html/viewport.html[R documentation: viewport]

Clipping obeys only the most recent viewport that sets `clip`: if one viewport clips and a viewport inside it clips again, the second replaces the first. The help page of `viewport()` states this; it is why a clipping viewport inside a clipping viewport does not give the intersection.

=== The viewport tree

Grid keeps a tree of viewports. Its root, called `ROOT`, is the whole device. `pushViewport()` adds a viewport below the current one and makes it current. `popViewport(n)` removes the current viewport and its descendants and makes the parent current. `upViewport(n)` goes to the parent without removing anything. `downViewport(name)` goes to a viewport further down the tree and `seekViewport(name)` goes to one anywhere in it. `upViewport(0)` goes up to the root, and `popViewport(0)` pops everything. All drawing and all conversion of units is relative to the current viewport. A viewport pushed with the same `name` as a sibling replaces it.

`current.viewport()` returns the current viewport, `current.vpPath()` the path from the root as a `vpPath` (names joined by `::`, and `NULL` at the root), `current.vpTree()` the whole tree, and `current.transform()` the transformation matrix of the viewport. The script pushes, goes up, goes down and pops, and prints the tree after each step.

[source,r]
----
library(grid)
svg(tempfile(fileext = ".svg"))

# A viewport is a rectangular region with its own coordinate systems.
vp <- viewport(x = 0.5, y = 0.5, width = 0.8, height = 0.6, name = "panel")
vp
#> viewport[panel]
class(vp)
#> [1] "viewport"
vp$width
#> [1] 0.8npc

# Nothing is pushed yet: the current viewport is the top-level one.
current.viewport()
#> viewport[ROOT]

# pushViewport() makes the new region current and keeps its parent.
pushViewport(vp)
current.viewport()
#> viewport[panel]
current.vpPath()
#> panel
pushViewport(viewport(width = 0.5, name = "inner"))
current.vpPath()
#> panel::inner
current.vpTree()
#> viewport[ROOT]->(viewport[panel]->(viewport[inner]))

# upViewport() leaves a viewport on the tree; popViewport() removes it.
upViewport()
current.vpPath()
#> panel
current.vpTree()
#> viewport[ROOT]->(viewport[panel]->(viewport[inner]))
downViewport("inner")
current.vpPath()
#> panel::inner
popViewport()
current.vpTree()
#> viewport[ROOT]->(viewport[panel])
popViewport()
current.vpTree()
#> viewport[ROOT]
invisible(dev.off())
----

Source: https://search.r-project.org/R/refmans/grid/html/viewports.html[R documentation: pushViewport]

Two points in that output are easy to miss. After `upViewport()` the `inner` viewport is still in the tree (`current.vpTree()` shows it), so `downViewport("inner")` finds it; after `popViewport()` it is gone. And a `viewport` object is not tied to the tree: the same object can be pushed many times, in different places.

=== Several viewports at once

`vpStack(a, b)` pushes `a` and then `b` inside it; `vpList(a, b)` pushes `a` and `b` as siblings, going back up after each; and `vpTree(parent, children)` pushes a parent and a `vpList` of children. All three build one object, so a whole structure can be pushed with one call. After pushing a `vpTree` the current viewport is the last child. A path is built with `vpPath("page", "right")`, which prints as `page::right`, and `downViewport()` accepts it, which is the way to name a viewport that has the same name as another one elsewhere in the tree.

[source,r]
----
library(grid)
svg(tempfile(fileext = ".svg"))

# Three ways to describe several viewports at once.
tree <- vpTree(
  viewport(name = "page"),
  vpList(viewport(name = "left"), viewport(name = "right"))
)
tree
#> viewport[page]->(viewport[left], viewport[right])
class(tree)
#> [1] "vpTree"   "viewport"
chain <- vpStack(viewport(name = "outer"), viewport(name = "inner"))
chain
#> viewport[outer]->viewport[inner]
class(chain)
#> [1] "vpStack"  "viewport"

# Pushing a tree pushes the parent and every child; the last one is current.
pushViewport(tree)
current.vpTree()
#> viewport[ROOT]->(viewport[page]->(viewport[right], viewport[left]))
current.vpPath()
#> page::right

# Go back to the root, then find a viewport by name or by path.
upViewport(0)
current.vpPath()
#> NULL
seekViewport("left")
current.vpPath()
#> page::left
upViewport(0)
downViewport(vpPath("page", "right"))
current.vpPath()
#> page::right
vpPath("page", "right")
#> page::right
invisible(dev.off())
----

Source: https://search.r-project.org/R/refmans/grid/html/viewport.html[R documentation: vpTree]

The order of the children in the printed tree after the push is the reverse of the order they were given in. This is how the tree prints; navigation by name does not depend on it.

=== Errors and warnings

The messages below are the ones R 4.6.1 gives. A viewport name that is not in the tree is an error. Popping more levels than the tree has is an error from the C code, with the wording that mentions mixed output. A bad width is only a warning in `viewport()` (it makes `NA` the width), and an unknown unit name is an error in `unit()`.

[source,r]
----
library(grid)
svg(tempfile(fileext = ".svg"))
pushViewport(viewport(name = "only"))

msg <- \(expr) tryCatch(expr, error = \(e) conditionMessage(e))

# A name that is not in the tree.
msg(downViewport("missing"))
#> [1] "Viewport 'missing' was not found"
msg(seekViewport("missing"))
#> [1] "Viewport 'missing' was not found"
# Popping more levels than the tree has (the top-level viewport cannot go).
msg(popViewport(3))
#> [1] "cannot pop the top-level viewport ('grid' and 'graphics' output mixed?)"
# The width must be a unit or a number (read as npc): a string is only a
# warning.
tryCatch(viewport(width = "wide"), warning = \(w) conditionMessage(w))
#> [1] "NAs introduced by coercion"
# A unit name that grid does not know is an error.
msg(viewport(x = unit(1, "furlongs")))
#> [1] "Invalid unit"
invisible(dev.off())
----

Source: https://search.r-project.org/R/refmans/grid/html/viewports.html[R documentation: popViewport]

The usual causes of "cannot pop the top-level viewport" are a `popViewport()` without a matching push, and a script that was interrupted by an error between a push and its pop in an interactive session, so that the next run starts with a different tree. `upViewport(0)` followed by `grid.newpage()` starts clean.

== Units

=== The unit types

A grid length is a `unit`: a number and the name of a coordinate system. Both are vectors, so `unit(1:3, c("cm", "npc", "lines"))` has length 3. The table lists the names; `help("unit")` has the full text and the aliases (`"in"` and `"inch"` for `"inches"`, `"centimetre"` and `"centimeter"` for `"cm"`).

[cols="2,5",options="header"]
|===
|Name |Meaning
|`"npc"` |Normalised parent coordinates: 0 is the left or bottom edge of the viewport, 1 the right or top edge. The default unit of a viewport's position and size.
|`"native"` |The viewport's own data scale, from `xscale` and `yscale`.
|`"snpc"` |Square npc: the lesser of the npc width and height, so that a length in it is the same horizontally and vertically.
|`"cm"`, `"mm"`, `"inches"` |Physical lengths (1 in = 2.54 cm).
|`"points"`, `"bigpts"` |Printer's points (72.27 per inch) and big points (72 per inch, the PostScript point).
|`"picas"`, `"dida"`, `"cicero"`, `"scaledpts"` |Other typesetting units (1 pica = 12 points; 65536 scaled points = 1 point).
|`"lines"` |Lines of text: multiples of `+fontsize * lineheight+` of the current viewport (and `cex`, below).
|`"char"` |Multiples of the nominal font height, `fontsize` times `cex`.
|`"strwidth"`, `"strheight"` |The width or height of the string in the third argument (`data`), in the current font.
|`"grobwidth"`, `"grobheight"` |The width or height of the grob in the `data` argument.
|`"null"` |A relative share, which only means something for the widths and heights of a layout (below).
|===

Source: https://search.r-project.org/R/refmans/grid/html/unit.html[R documentation: unit]

R 4.0.0 replaced the internal implementation of units (R NEWS: the visible effects are a slightly different print format for unit arithmetic, faster unit operations and the new functions `unitType()` and `unit.psum()`). The class of a unit is now `c("unit", "unit_v2")`; everything in this page uses the exported functions, not the structure.

=== Arithmetic

Arithmetic on units is symbolic. Units of the same name are simplified (`+2 * unit(1, "cm")+` is `2cm`, and `sum(unit(1:3, "cm"))` is `6cm`); a mixture is stored as a sum or a maximum and kept until it is converted in a viewport. `pass:c[+]`, `-`, a number times a unit, `max()`, `min()`, `sum()` and the parallel `unit.pmax()`, `unit.pmin()` and `unit.psum()` work on units, and `unit.c()` joins units into one vector. `c()` is not the way: it drops the unit class and returns plain numbers, as the script shows. Two units cannot be multiplied or divided by each other.

[source,r]
----
library(grid)
svg(tempfile(fileext = ".svg"))

# A unit is a number plus a unit name; both are vectorised.
u <- unit(1:3, c("cm", "npc", "lines"))
u
#> [1] 1cm    2npc   3lines
length(u)
#> [1] 3
u[2]
#> [1] 2npc
unitType(u)
#> [1] "cm"    "npc"   "lines"
as.numeric(u)
#> [1] 1 2 3
class(u)
#> [1] "unit"    "unit_v2"

# The second argument is required: a unit has no default name.
unit(0.5, "npc")
#> [1] 0.5npc
unit(c(1, 2), "inches")
#> [1] 1inches 2inches

# Arithmetic is symbolic: nothing is converted until drawing time.
unit(1, "npc") - unit(2, "lines")
#> [1] sum(1npc, -2lines)
unit(1, "npc") - unit(2, "lines") + unit(1, "cm")
#> [1] sum(1npc, -2lines, 1cm)
2 * unit(1, "cm")
#> [1] 2cm
unit(1, "npc") / 2
#> [1] 0.5npc
unit.c(unit(1, "cm"), unit(2, "inches"), unit(1, "null"))
#> [1] 1cm     2inches 1null
# c() does not know about units: it drops them and returns plain numbers.
c(unit(1, "cm"), unit(2, "inches"))
#> [1] 1 2

# max(), min() and sum() build summary units, again unevaluated.
max(unit(1, "cm"), unit(1, "inches"))
#> [1] max(1cm, 1inches)
sum(unit(1:3, "cm"))
#> [1] 6cm
unit.pmax(unit(1:2, "cm"), unit(0.5, "inches"))
#> [1] max(1cm, 0.5inches) max(2cm, 0.5inches)
rep(unit(1, "mm"), 3)
#> [1] 1mm 1mm 1mm
invisible(dev.off())
----

Source: https://search.r-project.org/R/refmans/grid/html/unit.html[R documentation: unit]

The text of the symbolic sums is worth reading: `sum(1npc, -2lines)` is exactly the expression written.

=== Converting units

`convertUnit(x, unitTo, axisFrom, typeFrom, axisTo, typeTo, valueOnly)` converts in the current viewport on the current device; `convertX()`, `convertY()`, `convertWidth()` and `convertHeight()` are the shorthands that fix the axis and the type (location or dimension), which matters for `"native"` units because a location and a dimension differ by the scale offset. With `valueOnly = TRUE` the result is a plain number. A conversion needs an open device, because the answer depends on its size and its fonts; the device in the script is 6 by 4 inches.

[source,r]
----
library(grid)
svg(tempfile(fileext = ".svg"), width = 6, height = 4)

# Conversion needs a device and a current viewport: the answer is in inches
# because this device is 6 by 4 inches.
convertWidth(unit(1, "npc"), "inches")
#> [1] 6inches
convertHeight(unit(1, "npc"), "inches")
#> [1] 4inches
convertUnit(unit(1, "inches"), "cm")
#> [1] 2.54cm
convertX(unit(0.25, "npc"), "inches", valueOnly = TRUE)
#> [1] 1.5

# Relative units depend on the font: a line is fontsize * lineheight points.
convertHeight(unit(1, "lines"), "points")
#> [1] 14.454points
convertHeight(unit(1, "char"), "points")
#> [1] 12.045points
convertWidth(unit(1, "lines"), "mm", valueOnly = TRUE)
#> [1] 5.08

# Text units measure a string or a grob in the current font.
convertWidth(stringWidth("loan"), "points")
#> [1] 24.09points
convertWidth(stringWidth("loan"), "points", valueOnly = TRUE) <
  convertWidth(stringWidth("loan period"), "points", valueOnly = TRUE)
#> [1] TRUE
convertHeight(unit(1, "strheight", "Ag"), "points")
#> [1] 9.03375points
convertWidth(grobWidth(textGrob("shelf")), "points")
#> [1] 26.0975points

# "snpc" is the smaller of the width and the height: a square unit (R 4.6.0
# lets convertWidth() and its relatives convert to it).
convertWidth(unit(1, "snpc"), "inches")
#> [1] 4inches
convertHeight(unit(1, "snpc"), "inches")
#> [1] 4inches

# A mixed expression is evaluated now, in the current viewport.
convertHeight(unit(1, "npc") - unit(2, "lines"), "inches")
#> [1] 3.6inches

# The same npc is a different size in a smaller viewport.
pushViewport(viewport(width = 0.5, height = 0.25))
convertWidth(unit(1, "npc"), "inches")
#> [1] 3inches
convertHeight(unit(1, "npc"), "inches")
#> [1] 1inches
popViewport()
invisible(dev.off())
----

Source: https://search.r-project.org/R/refmans/grid/html/grid.convert.html[R documentation: convertUnit]

Reading the output: one line of text is 14.454 points on this device, because the default `fontsize` is 12 big points, the default `lineheight` is 1.2 and 72.27 points make an inch while 72 big points do: 12 * 1.2 * 72.27 / 72 = 14.454. A `"char"` is 12.045 points for the same reason. The same `1npc` is 6 inches wide at the top level and 3 inches inside a viewport half as wide. `convertHeight(unit(1, "npc") - unit(2, "lines"), "inches")` is 3.6 inches (4 inches minus 28.908 points).

=== Native units and data scales

`xscale` and `yscale` give a viewport a data range, and the `"native"` unit then converts like any other. This is how a data plot is made in grid: a viewport whose scales are the range of the data, and primitives that take `"native"` locations. Lattice panels are exactly that.

[source,r]
----
library(grid)
svg(tempfile(fileext = ".svg"), width = 6, height = 4)

# xscale and yscale give a viewport its own data coordinates ("native" units).
pushViewport(viewport(
  width = 0.8, height = 0.8,
  xscale = c(0, 400), yscale = c(0, 40), name = "data"
))
current.viewport()$xscale
#> [1]   0 400
current.viewport()$yscale
#> [1]  0 40

# 200 pages is the middle of the x range; 30 days is 3/4 of the y range.
convertX(unit(200, "native"), "npc")
#> [1] 0.5npc
convertY(unit(30, "native"), "npc")
#> [1] 0.75npc
convertX(unit(200, "native"), "inches")
#> [1] 2.4inches

# The scale also converts the other way, and works for widths.
convertX(unit(0.25, "npc"), "native")
#> [1] 100native
convertWidth(unit(100, "native"), "npc")
#> [1] 0.25npc

# Native and absolute units mix freely.
x <- unit(200, "native") + unit(1, "cm")
convertX(x, "inches")
#> [1] 2.79370078740157inches
popViewport()

# A location and a width differ when the scale does not start at zero.
pushViewport(viewport(xscale = c(100, 500)))
convertWidth(unit(100, "native"), "npc")
#> [1] 0.25npc
convertX(unit(100, "native"), "npc")
#> [1] 0npc
popViewport()
invisible(dev.off())
----

Source: https://search.r-project.org/R/refmans/grid/html/unit.html[R documentation: unit]

200 pages is half of the 0 to 400 range, so it is `0.5npc` from the left of the viewport; 30 days of a 0 to 40 range is `0.75npc`; and the viewport is 80 percent of a 6 inch wide device, so the middle of the range is 2.4 inches from the viewport's left edge. `convertWidth(unit(100, "native"), "npc")` is `0.25npc` (a quarter of the range) and `convertX(unit(0.25, "npc"), "native")` is `100native`. The two agree here because the scales start at zero. With `xscale = c(100, 500)`, which the last lines of the script use, a width of 100 native units is still `0.25npc`, but a location of 100 native units is the left edge, `0npc`: that is why there are separate `convertX()` and `convertWidth()`.

=== Unit errors and surprises

[source,r]
----
library(grid)
svg(tempfile(fileext = ".svg"))
msg <- \(expr) tryCatch(expr, error = \(e) conditionMessage(e))

# An unknown unit name is an error.
msg(unit(1, "furlongs"))
#> [1] "Invalid unit"
# Names are recycled against values without a warning.
unit(1:2, c("cm", "mm", "npc"))
#> [1] 1cm  2mm  1npc
# A "null" unit has no size of its own: outside a layout it converts to 0.
convertWidth(unit(1, "null"), "cm")
#> [1] 0cm
# Mixed arithmetic cannot be simplified, so it is stored as a sum.
unit(1, "null") + unit(1, "cm")
#> [1] sum(1null, 1cm)
# Only one operand of a product may be a unit.
msg(unit(1, "cm") * unit(1, "cm"))
#> [1] "only one operand may be a unit"
invisible(dev.off())
----

Source: https://search.r-project.org/R/refmans/grid/html/unit.html[R documentation: unit]

A `"null"` unit outside a layout converts to zero, and `unit(1, "null") + unit(1, "cm")` is a legal sum that stays symbolic; grid does not warn. `unit(1:2, c("cm", "mm", "npc"))` recycles the shorter vector to the length of the longer one without a warning, as R usually does. And `+unit(1, "cm") * unit(1, "cm")+` fails with "only one operand may be a unit".

== Layouts

A layout divides a viewport into a grid of rows and columns. `grid.layout(nrow, ncol, widths, heights, default.units, respect, just)` creates the object; the viewport that holds the layout is created with `viewport(layout = lay)`; and the viewports that occupy its cells are created with `layout.pos.row` and `layout.pos.col`, each a cell number or a range. Row 1 is the top row, as in a table.

Widths and heights are units. Fixed units (`"cm"`, `"lines"`) take exactly their size. A `"null"` unit takes a share of what is left after the fixed ones, in proportion to its value: with `widths = unit(c(2, 1, 1), c("cm", "null", "null"))` the first column is 2 cm and the other two split the rest equally. The default widths and heights are `unit(1, "null")` for every column and row, so `grid.layout(2, 3)` is six equal cells.

[source,r]
----
library(grid)
svg(tempfile(fileext = ".svg"), width = 8, height = 6)

# Two rows, three columns: fixed first and last column, flexible middle.
lay <- grid.layout(
  nrow = 2, ncol = 3,
  widths = unit(c(2, 1, 1), c("cm", "null", "null")),
  heights = unit(c(1, 3), c("lines", "null"))
)
class(lay)
#> [1] "layout"
dim(lay)
#> [1] 2 3
lay$widths
#> [1] 2cm   1null 1null
lay$heights
#> [1] 1lines 3null
lay$respect
#> [1] FALSE

# A layout belongs to a viewport; children choose cells by row and column.
pushViewport(viewport(layout = lay, name = "page"))
pushViewport(viewport(layout.pos.row = 2, layout.pos.col = 2:3, name = "body"))
current.vpPath()
#> page::body
convertWidth(unit(1, "npc"), "inches")
#> [1] 7.21259842519685inches
convertHeight(unit(1, "npc"), "inches")
#> [1] 5.8inches
upViewport()

pushViewport(viewport(layout.pos.row = 1, layout.pos.col = 1, name = "corner"))
convertWidth(unit(1, "npc"), "cm")
#> [1] 2cm
convertHeight(unit(1, "npc"), "points")
#> [1] 14.454points
popViewport(2)

invisible(dev.off())
----

Source: https://search.r-project.org/R/refmans/grid/html/grid.layout.html[R documentation: grid.layout]

The cell `layout.pos.row = 2, layout.pos.col = 2:3` is the whole bottom row minus the first column: on the 8 by 6 inch device the layout has 2 cm for the first column, the rest (8 inches minus 2 cm) is divided equally between the other two columns, and the viewport that spans both is 7.2126 inches wide. The bottom row is `3null` of `1lines + 3null`, so it takes the height left after the one line. The top-left cell is exactly 2 cm wide and one line high.

=== respect

By default null units in widths and in heights are independent: the cells fill the region, whatever its shape. With `respect = TRUE` all null widths and heights keep their ratio to each other, so a layout of `1null` by `1null` cells has square cells, as large as will fit, and is justified in the region according to `just`. `respect` can also be a matrix of the same shape as the layout whose non-zero entries mark which cells are respected.

[source,r]
----
library(grid)
svg(tempfile(fileext = ".svg"), width = 8, height = 2)

cell_size <- \(respect) {
  lay <- grid.layout(1, 2, widths = unit(c(1, 1), "null"),
                     heights = unit(1, "null"), respect = respect)
  pushViewport(viewport(layout = lay))
  pushViewport(viewport(layout.pos.col = 1))
  size <- c(
    width = convertWidth(unit(1, "npc"), "inches", valueOnly = TRUE),
    height = convertHeight(unit(1, "npc"), "inches", valueOnly = TRUE)
  )
  popViewport(2)
  size
}

# Without respect the cells fill the 8 by 2 inch device: 4 by 2 inches each.
cell_size(FALSE)
#>  width height
#>      4      2
# With respect = TRUE a null width and a null height keep the ratio 1 : 1,
# so the cells are 2 by 2 inch squares, the largest that fit.
cell_size(TRUE)
#>  width height
#>      2      2

# A matrix selects which cells are respected.
m <- rbind(c(1, 0))
m
#>      [,1] [,2]
#> [1,]    1    0
grid.layout(1, 2, respect = m)$respect.mat
#>      [,1] [,2]
#> [1,]    1    0
invisible(dev.off())
----

Source: https://search.r-project.org/R/refmans/grid/html/grid.layout.html[R documentation: grid.layout]

`grid.show.layout(lay)` draws a diagram of a layout and `grid.show.viewport(vp)` one of a viewport, to look at while designing; they draw on the device and have nothing to print, so no example runs them.

Grid layouts nest: a viewport that occupies one cell can itself carry a layout. That is how a lattice plot is built: a layout with rows for the title, the strips, the panels, the axes and the labels, whose panel cells are viewports named `plot_01.panel.1.1.vp`, and so on.

== Graphical parameters

`gpar()` collects graphical parameters in a named list of class `"gpar"`. It is the value of the `gp` argument of every viewport and every grob. The parameters are:

[cols="2,5",options="header"]
|===
|Parameter |Meaning
|`col`, `fill` |Colour of lines and borders; colour of the inside of shapes. In R 4.1.0 and later `fill` can also be a gradient or a pattern (below).
|`alpha` |Opacity from 0 to 1; combined with the alpha of the individual colour by multiplying.
|`lty`, `lwd`, `lex` |Line type, line width, and a multiplier applied to the width.
|`lineend`, `linejoin`, `linemitre` |How lines end (`"round"`, `"butt"`, `"square"`) and join (`"round"`, `"mitre"`, `"bevel"`), and the mitre limit.
|`fontsize`, `cex` |The size of text in points, and a multiplier on it; text is `+fontsize * cex+`.
|`fontfamily`, `fontface`, `font`, `lineheight` |Family, face (`"plain"`, `"bold"`, `"italic"`, `"bold.italic"`, or 1 to 4), and the height of a line as a multiple of the text size. A line is `+fontsize * cex * lineheight+`.
|===

Source: https://search.r-project.org/R/refmans/grid/html/gpar.html[R documentation: gpar]

The rules of inheritance are the reason to keep the tree in mind. The root viewport takes its settings from the device (the default `fill` differs between devices: on `svg()` it is `"white"`). A viewport that is pushed and a grob that is drawn enforce their `gp` for as long as they are current, and the settings go back when the viewport is popped or the grob has finished drawing. A grob's own `gp` overrides the viewport's, for that grob only. `cex`, `alpha` and `lex` are cumulative: a viewport with `cex = 0.5` inside another one with `cex = 0.5` has an effective `cex` of 0.25. `get.gpar()` returns the settings in force at the current viewport.

[source,r]
----
library(grid)
svg(tempfile(fileext = ".svg"))

# gpar() collects graphical parameters; it is a named list with a class.
gp <- gpar(col = "red", fill = "grey90", lwd = 2, lty = "dashed", cex = 1.5)
class(gp)
#> [1] "gpar"
names(gp)
#> [1] "col"  "fill" "lwd"  "lty"  "cex"

# The defaults come from the device, and every viewport inherits.
unlist(get.gpar(c("col", "fill", "lwd", "fontsize", "cex", "lineheight")))
#>        col       fill        lwd   fontsize        cex lineheight
#>    "black"    "white"        "1"       "12"        "1"      "1.2"

# Setting a parameter in a viewport changes it for everything inside.
pushViewport(viewport(gp = gpar(fontsize = 20, col = "blue")))
unlist(get.gpar(c("fontsize", "col", "cex")))
#> fontsize      col      cex
#>     "20"   "blue"      "1"
# cex multiplies fontsize; this viewport changes cex, not fontsize.
pushViewport(viewport(gp = gpar(cex = 0.5)))
unlist(get.gpar(c("fontsize", "col", "cex")))
#> fontsize      col      cex
#>     "20"   "blue"    "0.5"
# One line is fontsize * cex * lineheight: 20 * 0.5 * 1.2 big points here.
convertHeight(unit(1, "lines"), "bigpts")
#> [1] 12bigpts
popViewport(2)

# A grob can set parameters for itself, which override the viewport's.
t1 <- textGrob("a", gp = gpar(fontsize = 8))
t2 <- textGrob("a")
pushViewport(viewport(gp = gpar(fontsize = 30)))
convertWidth(grobWidth(t1), "points", valueOnly = TRUE) <
  convertWidth(grobWidth(t2), "points", valueOnly = TRUE)
#> [1] TRUE
popViewport()

# alpha multiplies down the tree too.
pushViewport(viewport(gp = gpar(alpha = 0.5)))
pushViewport(viewport(gp = gpar(alpha = 0.5)))
get.gpar("alpha")$alpha
#> [1] 0.25
popViewport(2)
invisible(dev.off())
----

Source: https://search.r-project.org/R/refmans/grid/html/gpar.html[R documentation: gpar]

That script prints `get.gpar()` values coerced to character by `unlist()`; the numbers are numbers in R. Notice that the second viewport changes only `cex`, so `fontsize` stays 20 and a line is `+20 * 0.5 * 1.2 = 12+` big points.

== Graphical objects

=== Draw now or make an object

Every grid primitive comes in two forms. `grid.rect()`, https://search.r-project.org/R/refmans/grid/html/grid.text.html[`grid.text()`], `grid.lines()`, `grid.points()`, `grid.polygon()`, `grid.circle()`, `grid.segments()`, `grid.xaxis()` and `grid.yaxis()` create the object and draw it at once, and return the object invisibly. `rectGrob()`, `textGrob()`, `linesGrob()`, `pointsGrob()`, `polygonGrob()`, `circleGrob()`, `segmentsGrob()`, `xaxisGrob()` and `yaxisGrob()` only create it. A grob is an ordinary R object (a list with class `c("rect", "grob", "gDesc")`): it describes what to draw, and https://search.r-project.org/R/refmans/grid/html/grid.draw.html[`grid.draw()`] draws it, in whatever viewport is current. That makes the `+*Grob()+` form the one to use when the object is to be stored, modified, put in a tree or drawn in several places, and the `+grid.*()+` form the one for a direct drawing.

[source,r]
----
library(grid)
svg(tempfile(fileext = ".svg"))

# rectGrob() makes an object and draws nothing.
r <- rectGrob(width = 0.5, name = "frame", gp = gpar(fill = "grey90"))
r
#> rect[frame]
class(r)
#> [1] "rect"  "grob"  "gDesc"
grid.ls() # an empty listing prints one blank line
#>

# grid.draw() draws it; the display list now has one entry.
grid.draw(r)
grid.ls()
#> frame

# grid.rect() is rectGrob() followed by grid.draw(); it returns the grob.
g <- grid.rect(height = 0.5, name = "band")
class(g)
#> [1] "rect"  "grob"  "gDesc"
grid.ls()
#> frame
#> band

# The fields of a grob are ordinary list elements, and a grob is a copy:
# changing r does not change what is on the page.
r$width
#> [1] 0.5npc
r$width <- unit(0.9, "npc")
r$width
#> [1] 0.9npc
grid.get("frame")$width
#> [1] 0.5npc

# grid.newpage() clears the page and the display list.
grid.newpage()
grid.ls()
#>
invisible(dev.off())
----

Source: https://search.r-project.org/R/refmans/grid/html/grid.rect.html[R documentation: grid.rect]

Three things in that output matter. `rectGrob()` drew nothing: `grid.ls()` listed nothing until `grid.draw()`. A grob is a value: `+r$width <- unit(0.9, "npc")+` changed the copy `r` and left the drawn object, found with `grid.get()`, at `0.5npc`. And the names (`frame`, `band`) are what the display list is searched by: when a name is not given, grid makes one up from a counter (`GRID.rect.1`), which is fine for a quick figure and unhelpful for editing.

=== The primitives and their units

The `x`, `y`, `width` and `height` of the primitives are read in `"npc"` unless a unit is given, so `rectGrob()` fills its viewport. `pointsGrob()` and `grid.points()` read bare numbers as `"native"`. The way to draw data is therefore a viewport with `xscale` and `yscale`, and primitives with native locations; axes (`grid.xaxis()`, `grid.yaxis()`) read the scale of the viewport they are drawn in, and take an `at` argument to fix the ticks.

[source,r]
----
library(grid)
svg(tempfile(fileext = ".svg"), width = 6, height = 4)

# Each primitive has a grid.*() function that draws and a *Grob() that makes.
prims <- list(
  rect = rectGrob(), text = textGrob("loans"), lines = linesGrob(),
  points = pointsGrob(1:3, 1:3), polygon = polygonGrob(),
  circle = circleGrob(), segments = segmentsGrob(),
  xaxis = xaxisGrob(at = 1:3), yaxis = yaxisGrob(at = 1:3)
)
vapply(prims, \(g) class(g)[[1L]], character(1L))
#>       rect       text      lines     points    polygon     circle   segments
#>     "rect"     "text"    "lines"   "points"  "polygon"   "circle" "segments"
#>      xaxis      yaxis
#>    "xaxis"    "yaxis"

# Default units: x, y, width and height are "npc" unless given a unit;
# points() also take "native" (the units of the viewport's scales).
prims$rect$x
#> [1] 0.5npc
prims$points$x
#> [1] 1native 2native 3native
prims$points$pch
#> [1] 1

#>   data

#>       ticks

The listing shows the tree for the data viewport: the points, the x axis (an axis is a gTree of `major`, `ticks` and `labels`), the y axis, the label and the line. The y axis shows no children. That is deliberate: an axis without `at` works out its ticks when it is drawn, and until then it has no children. `grid.force()` (below) makes the children appear.

The general constructors are `+grob(..., name, gp, vp, cl)+` and `+gTree(..., name, gp, vp, children, childrenvp, cl)+`; every primitive is built on them. Other primitives that this page does not run are `grid.raster()` for images, `grid.path()` for shapes with holes, `grid.curve()` and `grid.xspline()` for curves, `grid.roundrect()`, `grid.function()` and the `grid.legend()` family; they all follow the same `+grid.*()+` and `+*Grob()+` pattern.

=== gTrees

A `gTree` is a grob with children. Its `children` argument is a `gList`, a list of grobs, and drawing a gTree draws its children in order. The `vp` argument of any grob is a viewport that is pushed before the grob draws and popped after, which is how a gTree puts its parts in a region, and `childrenvp` is a viewport pushed before the children and popped (with `upViewport`) so that each child can name a place inside it with a `vpPath`. All the children of a gTree must have different names; the gTree itself need not be unique on the page.

`gPath("card", "title")`, written `card::title`, names a grob inside a gTree, in the same way that `vpPath` names a viewport. `childNames()` lists the children of one gTree, `getGrob(tree, "title")` returns a child, `+editGrob(tree, "title", label = ...)+` returns a copy with a changed child, `addGrob(tree, grob)` and `removeGrob(tree, "name")` add and remove a child, and `setGrob(tree, "name", newGrob)` replaces one. All of them return a modified copy and leave the tree they were given unchanged. The `+grid.*+` forms of the same operations change what has been drawn, and are the subject of the next subsection.

[source,r]
----
library(grid)
svg(tempfile(fileext = ".svg"))

# A gTree is a grob whose children are grobs; gList() is a list of grobs.
card <- gTree(
  children = gList(
    rectGrob(name = "frame", gp = gpar(fill = "grey95")),
    textGrob("The Dispossessed", y = 0.7, name = "title"),
    textGrob("Ursula K. Le Guin", y = 0.3, name = "author",
             gp = gpar(fontsize = 8))
  ),
  name = "card",
  vp = viewport(width = 0.6, height = 0.4, name = "card_vp")

=== Editing what is drawn

A grob that has been drawn lives on grid's display list, and `grid.edit()` changes it in place and redraws the page. The functions are `grid.get()`, `grid.edit()`, `grid.add()`, `grid.remove()` and `grid.set()`, the drawn versions of `getGrob()`, `editGrob()`, `addGrob()`, `removeGrob()` and `setGrob()`. They take a `gPath`, and a bare name is searched for at any depth unless `strict = TRUE`; `grep = TRUE` and `global = TRUE` match by regular expression and every match. `redraw = FALSE` makes the change without repainting. A name that is not on the display list is an error:

=== The display list

Grid records all drawing and viewport operations on a display list of its own (as well as the engine's), which supports editing and redrawing. === Custom gTrees

A gTree can build its children when it is drawn instead of when it is created. The class defines a `makeContent()` method that receives the gTree and returns it with its children set (`setChildren()`); `makeContext()` does the same for the viewport slots, and `drawDetails()`, `widthDetails()` and `heightDetails()` customise the drawing and the size of a grob. The help page names `grid:::makeContent.xaxis` as an example: it is how an axis decides its ticks after it has seen the viewport it is drawn in. The script defines a bar chart of loan durations as a gTree with a `days` field: the bars are made only when the tree is drawn, so a listing before `grid.force()` shows nothing below the tree.

[source,r]
----
library(grid)
svg(tempfile(fileext = ".svg"))

# A gTree subclass can build its children when it is drawn.
loan_bars <- \(days, name = NULL) {
  gTree(days = days, name = name, cl = "loan_bars")
}

makeContent.loan_bars <- \(x) { # nolint: object_name_linter.
  n <- length(x$days)
  bars <- rectGrob(
    x = unit((seq_len(n) - 0.5) / n, "npc"), y = 0,
    width = unit(0.8 / n, "npc"),
    height = unit(x$days / max(x$days), "npc"),
    just = c("centre", "bottom"), name = "bars"
  )
  setChildren(x, gList(bars))
}

bars <- loan_bars(c(10, 19, 31, 25, 23), name = "durations")
childNames(bars)
#> character(0)
grid.draw(bars)
# The children exist only while drawing, so a plain listing shows none ...
grid.ls()
#> durations
# ... and grid.force() makes the content visible.
grid.force()
grid.ls()
#> durations
invisible(dev.off())
----

Source: https://search.r-project.org/R/refmans/grid/html/makeContent.html[R documentation: makeContent]

Two details of that code are specific to S3 on grid. The method is named `makeContent.loan_bars`, after the class in `cl`, and is found by the usual S3 dispatch because it is defined in the global environment (in a package it needs `S3method(makeContent, loan_bars)` in the `NAMESPACE`; see xref:programming-languages/r/s3-classes-and-generics.adoc[S3 Classes and Generics]). The gradient and the pattern are not colours: `gpar(fill = blue_fade)` stores the object, and the class of `bar$gp$fill` is `"GridLinearGradient"`. A `linearGradient()` takes the colours, the `stops` at which each colour is reached (0 to 1 along the gradient), the two end points `x1`, `y1`, `x2`, `y2` (npc by default) and `extend`, which says what happens outside the gradient: `"pad"` (the default) repeats the end colours, `"repeat"` and `"reflect"` tile the gradient, and `"none"` draws nothing outside it. A `radialGradient()` has two circles instead of two points. `pattern(grob, width, height, extend = "repeat")` tiles a grob. `group = TRUE` (the default) makes the gradient relative to the bounding box of the whole grob, `FALSE` makes it relative to each shape in it. A grob as a clip is a clipping path, and a grob as a mask is a mask whose alpha (or luminance) decides how much of what is drawn inside shows. In every case the feature is part of the object, not of the output, so it works the same on any device that has it.

`grid.group(src, op, dst)` draws `src` (and `dst`, if given) in isolation and combines them with a compositing operator before putting the result on the page. `"over"` is the default; the Porter-Duff operators `"clear"`, `"source"`, `"over"`, `"in"`, `"out"`, `"atop"`, `"dest"`, `"dest.over"`, `"dest.in"`, `"dest.out"`, `"dest.atop"`, `"xor"`, `"add"` and `"saturate"` and the blend modes (`"multiply"`, `"screen"`, `"overlay"` and so on) are available on devices that report them. `grid.define()` and `grid.use()` define a group once and draw it many times, with an affine transformation each time.

None of this is needed for a default lattice plot; it matters when you draw with grid directly. In an R Markdown or Quarto chunk, a lattice object at the end of the chunk is printed, and so drawn, as at the console; a grob is only printed as its name (`rect[frame]`, as in the output above), so a chunk that builds a grob ends with `grid.draw()`.

== lattice

=== The Trellis model

`lattice` is the R implementation of Trellis graphics. Trellis was developed for S and S-PLUS at Bell Labs by R. A. Becker, W. S. Cleveland and colleagues, extending ideas in Cleveland's 1993 book _Visualizing Data_; the lattice help page names that book and the paper "The Visual Design and Control of Trellis Display" (Becker, Cleveland and Shyu, 1996) as the sources. Deepayan Sarkar's _Lattice: Multivariate Data Visualization with R_ is the book about the package, and it is community material, named here and not used; the package also has its own site, https://lattice.r-forge.r-project.org/[lattice package documentation: project site]. The R FAQ answers the question "Are Trellis displays implemented in R?" with lattice, and explains the name: because Trellis was claimed as a trademark, R does not use that word for the package, which is called lattice (the class of its objects is still `"trellis"`).

The idea is that one figure is an array of small plots, each of a different subset of the data, drawn with the same axes, so that the eye compares them. The subsets are defined by _conditioning variables_, factors or shingles written after a bar in the formula: `+days ~ pages | genre+` is "days against pages, for each genre". Each combination of levels is a _packet_ of rows, and each packet is drawn in a _panel_ by a _panel function_. The panels are arranged in a rectangular array, which can run over several pages, and a strip above each panel names its packet. Because the packets share the scales (by default), a difference between panels is a difference in the data.

The user interface is a set of high-level generic functions, each of which draws one kind of display by default. They have common arguments for conditioning, layout, scales, keys and titles, documented mainly in `?xyplot`, and a default panel function named `panel.` followed by the name of the function (`panel.xyplot`, `panel.bwplot`). A high-level function does not plot. It returns an object of class `"trellis"`, and printing the object draws it.

=== The high-level functions

=== The trellis object

An object of class `"trellis"` is a list with some forty components. It holds the formula, the call, the data of every panel, the limits of the scales, the layout, the key, the strip functions and the graphical settings to use. `print()` reads it and draws; `summary()` describes it; `dim()` and `dimnames()` give the shape of the array of panels; `update()` returns a changed copy; and `[` selects packets. === The plot is drawn when the object is printed

A trellis object is drawn by its print method. At the console the value of an expression is printed automatically, so `+xyplot(...)+` appears to draw. The automatic printing is suppressed where R does not print values: inside a function, inside a loop (`for`, `while`) and inside `source()`. There an explicit `print()` (or `plot()`, which is an alias) is needed. The R FAQ lists it as 7.22, "Why do lattice/trellis graphics not work?", and the same is true of ggplot2.

[source,r]

source("scenario.R")

#> [1] TRUE

plot_loans <- \() xyplot(days ~ pages, data = dur)

#> [1] 0

#> [1] 0

}
drawn() > 0
#> [1] TRUE

=== Formulas

The formula of the lattice functions is `+y ~ x | g1 * g2+`. The variables left and right of the tilde are the primary variables, those after the bar are the conditioning variables, and `pass:c[*]` and `pass:c[+]` between conditioning variables are equivalent (`pass:c[g1 + g2]` is also accepted). A formula without a bar makes one panel. The formula can contain expressions (`+sqrt(days) ~ log(pages)+`), and the variables are looked up in `data` first and then in the environment of the formula, as in xref:programming-languages/r/formulas.adoc[Formulas].

For the displays with one numeric and one categorical variable (`bwplot()`, `dotplot()`, `stripplot()`, `barchart()`), the factor is the one that is not the measurement, and which side it is on decides the orientation: `horizontal` is `FALSE` when the variable on the right of the tilde is the factor (or shingle) and `TRUE` otherwise. `+genre ~ days+` gives horizontal boxes and `+days ~ genre+` vertical boxes. The univariate displays (`histogram()`, `densityplot()`, `qqmath()`) take a one-sided formula. `barchart()` and `dotplot()` also accept a table. In `xyplot()` both sides are numeric, and a factor on either side labels the axis with its levels.

Several terms on either side, `pass:c[y1 + y2 ~ x | g]`, are the "extended formula interface": the two responses are superposed in each panel, as if they were groups. `pass:c[I(y1 + y2)]` or `allow.multiple = FALSE` make the `pass:c[+]` an arithmetic sum. `outer = TRUE` puts the terms in separate panels instead.

=== Smoothers, grids and the type argument

`panel.xyplot()` has an argument `type`, a character vector whose elements are combined: `"p"` points, `"l"` lines, `"b"` and `"o"` both, `"h"` vertical lines to the origin, `"s"` and `"S"` steps, `"r"` a regression line, `"smooth"` a loess fit, `"spline"` a smoothing spline, `"a"` the line of means for each distinct `x`, and `"g"` a background grid. Because arguments that a high-level function does not use itself are passed to the panel function, `type = c("p", "r")` can be given to `xyplot()` directly. The help page of `panel.xyplot()` recommends two arguments over these letters: `smooth` (`"lm"`, `"loess"`, `"spline"`, `"average"`, or `TRUE` for loess; added in lattice 0.21) in place of the smoothing letters, and `grid` (`TRUE`, or a list passed on to `panel.grid()`; added in lattice 0.19) in place of `"g"`. `grid` is not data-dependent like the other `type` values, and the two combine without the string algebra. `type` is kept for backwards compatibility.

=== Conditioning

Conditioning is the central idea, and it has four parts: which variables, how the panels are arranged, how they are ordered, and what they share.

*Which variables.* Conditioning variables must be factors or shingles; a character variable is converted to a factor and a numeric variable to a shingle. Unused factor levels are dropped (`drop.unused.levels`, `TRUE` by default for the conditioning variables and for the data).

*Arrangement.* `layout = c(columns, rows)` or `c(columns, rows, pages)` fixes the array. With one conditioning variable the default is `c(0, n)`: a 0 in the first place means "work it out from the number of panels per page, the aspect ratio and the device size" when the plot is printed. With two conditioning variables the first is across and the second is down by default. `as.table = TRUE` fills the panels from the top left, like a table, rather than from the bottom left, like a graph. `between = list(x = 0.5, y = 0.5)` puts space between the panels, in character heights. `skip` leaves positions empty, and `aspect` sets the shape of a panel (`"fill"`, `"xy"` for banking to 45 degrees, `"iso"` for equal scales, or a ratio).

*Order.* `perm.cond` permutes the conditioning variables and `index.cond` reorders or drops levels, either of which is better applied to an existing object with `update()` than recomputed. `index.cond` can also be a function of the panel's data, which sorts the panels by, say, their median.

*What they share.* The default `scales$relation = "same"` gives every panel the same axis limits. See _Scales_ below.

If the panels do not fit in the layout they continue on further pages. The next script uses two conditioning variables, changes the arrangement with `update()`, prints a plot that spans two pages, subsets by packet index and reorders.

=== Shingles

A shingle is lattice's generalisation of a factor to a numeric variable: a number together with a set of possibly overlapping intervals, which are its "levels". `equal.count(x, number, overlap)` makes the intervals so that each contains about the same number of values, with overlap given as a fraction; `shingle(x, intervals)` takes the intervals you choose; `as.shingle()`, `is.shingle()`, `levels()` and `nlevels()` work as for factors. A shingle as a conditioning variable makes one panel per interval, and a row can appear in more than one panel. A numeric conditioning variable that is not a shingle is converted with `shingle()`, whose default intervals are the unique values, which is a panel for each distinct number and rarely what is wanted. Use `equal.count()` (the lattice documentation says it is often more appropriate) or `cut()` for a factor.

[source,r]
----
source("scenario.R")
library(lattice)

# Loan duration in days next to the pages and genre of each returned book.

books$genre <- factor(tolower(trimws(books$genre)))

dur$days <- as.numeric(dur$return_date - dur$loan_date)
dur <- dur[!is.na(dur$days) & dur$days >= 0, ]
svg(tempfile(fileext = ".svg"))

# A shingle is a number with overlapping intervals as its "levels".
pg <- dur$pages[!is.na(dur$pages)]
s <- equal.count(pg, number = 3, overlap = 0.1)
class(s)
#> [1] "shingle"
nlevels(s)
#> [1] 3
levels(s)
#>      [,1] [,2]
#> [1,]   84  218
#> [2,]  210  326
#> [3,]  318  436
# equal.count() asks for about the same number of values in each interval.
vapply(seq_len(nlevels(s)), \(i) {
  lim <- levels(s)[[i]]
  sum(pg >= lim[[1L]] & pg <= lim[[2L]])
}, numeric(1L))
#> [1] 19 17 16

# shingle() takes the intervals you choose.
short_long <- shingle(pg, intervals = rbind(c(0, 250), c(200, 500)))
levels(short_long)
#>      [,1] [,2]
#> [1,]    0  250
#> [2,]  200  500

# Used as a condition, a shingle gives one panel per interval; rows may
# appear in more than one panel.
dur$pages_band <- equal.count(dur$pages, number = 3, overlap = 0.1)
p <- xyplot(days ~ year | pages_band, data = dur, layout = c(3, 1))
dim(p)
#> [1] 3
p$packet.sizes
#> pages_band
#>  [ 84, 218 ] [ 210, 326 ] [ 318, 436 ]
#>           19           17           16
# A numeric condition that is not a shingle is converted to one with shingle().
p_raw <- xyplot(days ~ year | pages, data = dur)
dim(p_raw)
#> [1] 13

=== groups and keys

`groups` superposes subsets inside each panel and varies the graphical parameters by group, taken from the `superpose.symbol` and `superpose.line` entries of the theme. A grouping variable makes the panel function receive `groups` and `subscripts`; the default panel functions handle them, and a custom panel function must accept them or use `panel.superpose()`. A key (a legend) explains the groups: `auto.key = TRUE` draws a simple one with the levels of `groups` as text, `+auto.key = list(...)+` adjusts it (`space` is one of `"top"`, `"bottom"`, `"left"`, `"right"`, with `columns`, `title`, `points`, `lines`, `rectangles`, `cex`), `+key = list(...)+` builds one in detail, and `+legend = list(right = list(fun = ...))+` places arbitrary grobs. With the current defaults the `auto.key` legend is placed on the right (the example shows `names(p$legend)`), and lattice 0.21 improved its default placement and its handling of the `type` argument.

The difference between `auto.key` and `key` is when the symbols are fixed. `auto.key` stores only the labels and the key is built at plotting time, so it matches the settings that are in force when the plot is drawn. `key` is built when the object is created, with the settings that were current then, and keeps them even if the object is printed on a device with different settings.

=== Panel functions

The panel function is where the drawing happens. A panel function receives the `x` and `y` of one packet and every argument of the high-level call that lattice did not use itself, so `pch = 16` given to `xyplot()` arrives in the panel function. The panel function must be written with grid, not with base graphics: `lines()` and `points()` do not work inside a panel (the error is "plot.new has not been called yet"), and lattice supplies grid versions that behave like them, named `+panel.*+` and `+l*+`: `panel.points()`/`lpoints()`, `panel.lines()`/`llines()`, `panel.text()`/`ltext()`, `panel.segments()`, `panel.rect()`, `panel.polygon()` and so on.

The building blocks in `?panel.functions` are the usual ones:

[cols="2,5",options="header"]
|===
|Function |What it draws

|`panel.abline(a, b, h, v, reg)` and `panel.refline()` |Lines: a slope and intercept, a horizontal or vertical line, or a fitted model (`panel.refline()` draws a reference line in the reference style of the theme).
|`panel.lmline(x, y)`, `panel.loess(x, y)`, `panel.spline(x, y)`, `panel.average(x, y, fun)` |Smoothers and summaries added on top of the points.
|`panel.grid(h, v)` |A background grid; positive `h` and `v` are the number of lines, and `-1` places them at `pretty` locations, which usually match the axis labels.

Two numbers say which panel is being drawn. `panel.number()` is the order of drawing, 1, 2, 3, ..., and `packet.number()` the position of the packet in the natural order of the conditioning levels. They coincide unless `perm.cond` or `index.cond` changes the order, which is what the second half of the example shows. They are available inside the panel function, the strip function and the axis function, and while interacting with a plot through `trellis.focus()`, but not in the `prepanel` function, which runs before the plotting.

The panel function is evaluated when the plot is printed, not when `xyplot()` is called. The script records what each panel receives in an environment, and the count is zero until `print()`. Note `+...+` in the panel function: it passes `pch = 16` on to `panel.xyplot()`.

source("scenario.R")
library(lattice)

# Loan duration in days next to the pages and genre of each returned book.
books$isbn <- normalise_isbn(books$isbn)
books$genre <- factor(tolower(trimws(books$genre)))

# A panel function gets the x and y of one packet plus everything else that
# the high-level call did not use. Keep `...` so those extras flow through.
loan_panel <- \(x, y, ...) {
  panel.grid(h = -1, v = -1, col = "grey85")
  panel.xyplot(x, y, ...)
  ok <- !is.na(x) & !is.na(y)
  if (sum(ok) > 2L) {
    panel.lmline(x[ok], y[ok], col = "firebrick")
  }
  panel.text(min(x, na.rm = TRUE), max(y, na.rm = TRUE),
             labels = panel.number(), adj = c(0, 1))
  assign(
    sprintf("panel_%d", panel.number()),
    c(packet = packet.number(), n = length(x)),
    envir = seen
  )
}

p <- xyplot(days ~ pages | genre, data = dur, panel = loan_panel, pch = 16)
# xyplot() has not called the panel function: that happens when it is drawn.
length(ls(seen))
#> [1] 0
print(p)

=== Scales

`scales` is a list that controls the axes: tick marks, labels, limits, and whether the limits are shared. It can hold the same components for both axes or a sub-list for `x` and `y`, and a bare character string is read as `relation`.

[cols="2,5",options="header"]
|===
|Component |Effect
|`relation` |`"same"` (the default: all panels share the limits), `"free"` (each panel gets its own) or `"sliced"` (own limits, but the same length of range, so slopes are comparable).
|`log` |`TRUE` (base 10), a number or `"e"`: the variable is log-transformed before it reaches the panel function, and the ticks are labelled in the original scale.
|`at`, `labels`, `tick.number` |Positions and labels of ticks, or the suggested number of ticks.
|`limits` |As `xlim` and `ylim`.
|`draw`, `alternating` |Whether to draw the axis at all, and whether the labels alternate between the two sides of the array (default), or a vector choosing for each row or column: 0 none, 1 bottom or left, 2 top or right, 3 both.
|`rot`, `cex`, `col`, `font`, `tck` |Appearance of tick labels and marks.
|`abbreviate`, `minlength` |Abbreviate long labels, as in `scales = list(x = list(abbreviate = TRUE))`.
|`equispaced.log` |Equally spaced ticks for log scales (default) or ticks as in traditional graphics.
|===

Source: https://search.r-project.org/CRAN/refmans/lattice/html/xyplot.html[lattice package documentation: xyplot]

With `relation = "same"`, `x.limits` holds one pair; with `"free"` or `"sliced"` it holds a list with one pair per panel, which the script prints.

The warning "log scales cannot be changed via 'update'" is real and instructive: a log scale transforms the data when the packets are built, so it cannot be applied to an existing object, and `update(p, scales = list(x = list(log = TRUE)))` warns and leaves the scale unchanged. The help page of `xyplot()` says that `scales = list(x = list(log = 2))` is equivalent to writing `log2(x)` in the formula, apart from the axis labelling. More generally the help page of `update.trellis()` says that anything that would change the data within each panel (`formula`, `data`, `groups`, `subscripts`, `subset`) is not available to `update()`.

=== Strips and titles

The strips above the panels show the conditioning level. `strip = FALSE` removes them, `+strip = strip.custom(...)+` changes them (`strip.names = TRUE` shows the variable name with the level, `strip.levels = c(TRUE, FALSE)` controls whether levels are shown, `style` changes the look, `bg` and `fg` the colours), `strip.left = TRUE` puts strips on the left of the panels, which suits wide, short panels, and `par.strip.text = list(cex, col, font, lines, abbreviate, minlength)` formats the text. The title and labels are `main`, `sub`, `xlab`, `ylab`, and `xlab.top` and `ylab.right` for the other sides; each can be a character string, an expression (plotmath), a list that passes arguments such as `cex`, `col` and `font` to the text grob, or a grob. `xlab = NULL` removes a label.

=== Themes and par.settings

Lattice does not read `par()`. Its graphical parameters are in a settings list per device, queried with `trellis.par.get()`, changed with `trellis.par.set()`, and set for one object with the `par.settings` argument. A change to `+par(mfrow = ...)+` or `+par(mar = ...)+` has no effect on lattice plots (the lattice help page says so, and the base-versus-grid script above proves it for the panel width). Grid parameters that apply to the whole plot go in the `grid.pars` component of the settings.

The settings are kept per device _name_, not per device instance. Opening a second `svg()` device inherits what the first one left behind, and `trellis.device()` resets them: the example shows the symbol colour changed, then inherited by the next `svg()` device, then reset by `trellis.device()`. The help page says the settings of a device name are created when `trellis.device()` opens it or when a lattice plot is first drawn on it. A change with `trellis.par.set()` therefore lasts for the session unless the device is reopened with `trellis.device()`, and `par.settings` is the way to change only one plot.

=== Several plots on one page

`print(x, split = c(col, row, ncol, nrow), position = c(xmin, ymin, xmax, ymax), more = FALSE, newpage = TRUE)` places a trellis plot on a page that holds others. `split` says that the plot goes in cell `(col, row)` of an `ncol` by `nrow` array, with the origin at the top left. `position` places it in a rectangle with coordinates from 0 to 1 and the origin at the bottom left, and the two can be combined. `more = TRUE` says the page is not finished, so the next plot is drawn on the same page instead of starting a new one. `newpage = FALSE` draws into the current grid viewport, which makes it possible to embed a lattice plot in an arbitrary viewport, and `draw.in = "name"` goes to a named viewport. The `prefix` argument names the plot's viewports and grobs; by default it is `plot_01`, `plot_02`, and so on, by serial number on the current page. This replaces `gridExtra::grid.arrange()` (not installed here) for lattice plots, and `par(mfrow)` and `layout()` of base graphics, which do not work. The help page warns that positioning a multi-page display does not work.

[source,r]
----
source("scenario.R")
library(lattice)

books$genre <- factor(tolower(trimws(books$genre)))

dur <- dur[!is.na(dur$days) & dur$days >= 0, ]
library(grid)

scatter <- xyplot(days ~ pages, data = dur, main = "Duration by length")
boxes <- bwplot(genre ~ days, data = dur, main = "Duration by genre")

# split = c(x, y, nx, ny): the plot goes in cell (x, y) of an nx by ny array;
# more = TRUE says the page is not finished.
print(scatter, split = c(1, 1, 2, 1), more = TRUE)
print(boxes, split = c(2, 1, 2, 1))

# Each plot got its own prefix in the names of its viewports.
vps <- grid.ls(viewports = TRUE, grobs = FALSE, print = FALSE)$name
unique(sub("\\..*$", "", grep("toplevel", vps, value = TRUE)))
#> [1] "plot_01" "plot_02"

# position = c(xmin, ymin, xmax, ymax) places the plot in a rectangle of the
# page, in [0, 1] coordinates, and can overlap another plot.

print(scatter, position = c(0, 0, 1, 1), more = TRUE)

vps <- grid.ls(viewports = TRUE, grobs = FALSE, print = FALSE)$name

=== update(), trellis.last.object() and the plot arguments

`+update(p, ...)+` returns a copy of a trellis object with the named components replaced, using the same names as the high-level call; it records the change in the `call` component. The help page says that `perm.cond` and `index.cond` change the arrangement without recalculating the data subsets. A component set to `NULL` is removed. Some changes cannot be made this way: the data cannot change, and neither can the log scale above. `t()` transposes a plot with two conditioning variables. `trellis.last.object()` returns the last object that was printed (lattice saves it on printing, which the `save.object` option controls), and `+trellis.last.object(...)+` is `update()` on it. The `plot.args` component holds arguments for `print()` that travel with the object, such as a `split`.

=== Lattice is grid: trellis.focus()

Because a lattice plot is a tree of grid viewports and grobs, it can be changed after it is drawn. The names are predictable: for the plot with prefix `plot_01`, the panel in column 2 and row 1 is the viewport `plot_01.panel.2.1.vp`, its strip is `plot_01.strip.2.1.vp`, and `trellis.vpname()` builds the names. `trellis.focus(name, column, row)` makes the viewport current, so that any grid function can draw in it, and `trellis.unfocus()` returns to the top. Rows count from the bottom unless the plot was made with `as.table = TRUE`. The help page calls these interaction functions experimental, so their details may change. `trellis.panelArgs()` returns the data of the focused panel, `current.panel.limits()` its data limits, and `panel.identify()` and `trellis.grobname()` are the tools for interactive use. The lattice-aware panel functions (`panel.abline()`, `panel.text()`) draw into the focused panel, and what they draw is a named grob, so it can also be found with `grid.ls()`.

=== Options, devices and a lattice-wide default

`lattice.options()` holds the package-wide non-graphical settings; `lattice.getOption(name)` reads one. The ones used most are `default.args` (the defaults of `as.table`, `aspect`, `auto.key`, `between`, `grid`, `skip`, `strip` and the scale and axis functions, as the script lists), `default.theme`, `save.object`, `panel.error`, `drop.unused.levels` and the names of the default panel functions (`panel.xyplot`, `panel.bwplot`, and so on). `lattice.options(old)` restores the value returned by a previous call. A call-specific change is the `lattice.options =` argument of a high-level function, which applies only for that call and stays with the object.

`+trellis.device(device, color, theme, new, retain, ...)+` opens a device and initialises the lattice settings for it, with `theme` a list, a function that returns one, or its name. It is not needed to draw a lattice plot, since any open device works and the first plot creates the settings for it. Older tutorials call `trellis.device()` and `trellis.par.set()` at the top of every script to get a white background and a good colour scheme; with the current defaults that is rarely needed. == Grid underneath ggplot2

ggplot2 draws with grid too, in its own way: a plot is built from layers, and `ggplotGrob()` turns it into a `gtable`, a gTree that is a table of grobs (a layout whose cells hold the panel, the axes, the strips and the legend). So grid knowledge applies to ggplot2 (editing a drawn ggplot2 figure, putting it in a viewport, drawing annotations with grid functions), and lattice and ggplot2 plots can sit on the same page. The script uses ggplot2 4.0.3. Its class vector shows the S7 object system that ggplot2 4.0 adopted (the ggplot2 NEWS says the S3 parts were replaced with S7 ones; see xref:programming-languages/r/s7-object-system.adoc[The S7 Object System]).

The choice is partly taste and partly the data. lattice is small, ships with R, and is at its best for many comparable panels of the same display with scales shared on purpose, which was its design; ggplot2 is better when a plot is made of layers of different geometry and when the style should be consistent across a project. Both are worth reading the data from the same data frame, and neither replaces base graphics for a quick look.

== Pitfalls

* *No `print()` where R does not print.* A lattice or ggplot2 object returned from a function or created in a loop is not drawn (R FAQ 7.22); return it and print it at the top level, or call `print()`.
* *Base graphics functions in a panel function.* `lines()`, `points()`, `abline()` and `text()` fail inside a panel with "plot.new has not been called yet". Use `panel.lines()`/`llines()`, `panel.points()`, `panel.abline()` and `panel.text()`. By default lattice catches the error and writes it in the panel (`panel.error`), so a failed panel shows as text and the script continues; use `print(p, panel.error = stop)` while developing.
* *A panel function without `+...+`.* The extra arguments of the high-level call, such as `pch = 16`, are dropped silently, with no message. Always end a custom panel function's arguments with `+...+` and pass it on.
* *Numeric conditioning variables.* `+xyplot(y ~ x | z)+` with a numeric `z` makes one panel per distinct value. Use `equal.count(z, number = 4)` or `+cut(z, ...)+`.
* *Mixing systems.* `par()` has no effect on grid or lattice; `layout()` and `grid.layout()` are different functions, and base functions and grid functions do not know each other's state. To combine, use `print(split =)` for lattice plots, a grid layout of viewports, or gridBase/gridGraphics.
* *`update()` cannot change data.* `formula`, `data`, `groups`, `subscripts` and `subset` are not accepted by `update()`, and a log scale cannot be added (a warning says so). Build a new plot instead.
* *The settings belong to the device name.* A `trellis.par.set()` made for one `svg()` device is still there on the next one in the same session. Use `par.settings` for a change that is meant for one plot, and `trellis.device()` to reset.
* *`dimnames()` is not what is shown.* After `[` or `index.cond`, `dim()` is right and `dimnames()` still lists every level.
* *Panel order.* With `as.table = FALSE` (the default) panels start at the bottom left, like a graph, which is the reverse of reading order; `as.table = TRUE` starts at the top left.
* *Grob names and counters.* Automatically generated grob names depend on a counter (`GRID.rect.1`), and a figure that is drawn more than once in a session gets different numbers. Name grobs that code will look for.
* *Interactive state.* `grid.locator()`, `panel.identify()` and `trellis.focus()` called without a panel read the mouse, so they need an interactive screen device; they are not run on this page.
* *The `Rplots.pdf` file.* A drawing call with no open device opens the default one; under `Rscript` that writes `Rplots.pdf` in the working directory. Open a device first (`png()`, `svg()`, `pdf(NULL)`) and close it with `dev.off()`.
