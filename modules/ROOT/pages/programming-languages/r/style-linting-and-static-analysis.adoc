== Three jobs, four kinds of tool

The tools differ in what they read, what they may change and how sure their answer is.

[cols="2,4,3,3",options="header"]
|===
|Kind |What it does |Changes files? |On this page
|Style guide |Rules for people: names, spaces, line length, where the braces go. It is a document, so it cannot be run |No |The tidyverse style guide and Google's R style guide (both community documents)
|Formatter |Rewrites the layout of code (spaces, indentation, line breaks and a few tokens) so that it follows the rules |Yes, which is why it should run on files under version control |styler; Air is named in a sentence
|Linter |Reads code without running it and reports a line, a column and a message for every place that breaks a rule or looks wrong |No |lintr
|Static analysis |Finds likely mistakes from the structure of the code: an undefined variable, a local variable that is never used, a call to a function that does not exist |No |codetools, and the `R CMD check` step that uses it
|===

Source: https://cran.r-project.org/doc/manuals/r-release/R-exts.html#Checking-packages[Writing R Extensions: Checking packages]

The division is not sharp. Some lintr linters are plain style rules (spaces after commas), some find real mistakes (`x == NA` is never what was meant), and `object_usage_linter` is codetools in a lintr wrapper: its help page says that it checks closures with `codetools::checkUsage()` and that it runs `eval()` on the code, so it must not be used with untrusted code (lintr package documentation: object_usage_linter). A formatter is the opposite case: it never reports anything, it only rewrites, and a clean formatter run says nothing about whether the code is right.

R itself checks very little. The parser rejects code that does not parse and nothing else; an undefined variable is found only when the line runs. Everything on this page therefore runs before the code does, in the editor, in a pre-commit hook, in continuous integration or as one step of `R CMD check`. The manual for writing packages states the minimum in a sentence: `R CMD check` checks the R code of a package for possible problems with codetools.

== The tidyverse style guide

The most widely used style for R code is the tidyverse style guide (https://style.tidyverse.org/[style.tidyverse.org]), a community document written by the tidyverse team and not part of R. It has a part for analyses (files, syntax, functions, pipes, ggplot2) and a part for packages (files, documentation, tests, error messages, NEWS). The R language does not require any of it, and base R itself does not follow it, but it is the style that lintr's default linters and styler's `tidyverse_style()` implement, so reading the guide is the quickest way to know what those tools will say. This section summarises the rules in the guide's own order; the guide is the authority and changes from time to time (the version notes at the end list what changed in the tools after the single-indent change of function definitions).

=== Names

The guide asks for variable and function names that use only lowercase letters, numbers and underscores (snake case), with nouns for variables and verbs for functions, concise but meaningful, and that avoid reusing the names of common functions and variables (`T`, `c`, `mean`). It reserves the dot for the S3 system: a method is called `function.class`, so a function or class name with dots in it produces confusing methods such as `as.data.frame.data.frame()`. The R FAQ describes what the language allows, which is more: a syntactic name consists of letters, digits, the dot and the underscore and starts with a letter or with a dot not followed by a digit (R FAQ 7.14).

Base R was not written to this guide, and its own function names mix the styles. The script counts the functions of the base package whose names start with a lowercase letter, by style, and then shows the two ways in which `T` and `F` are not like `TRUE` and `FALSE`.

[source,r]
----
# How base R names its own functions.
fns <- ls(baseenv())
is_fn <- vapply(fns, \(nm) is.function(get(nm, baseenv())), logical(1L))
fns <- fns[is_fn & grepl("^[a-z]", fns)]
snake <- grepl("^[a-z][a-z0-9]*(_[a-z0-9]+)+$", fns)
dotted <- grepl("^[a-z][a-z0-9]*(\\.[a-z0-9]+)+$", fns)
camel <- grepl("^[a-z][a-z0-9]*([A-Z][a-z0-9]*)+$", fns)
c(
  snake_case = sum(snake),
  dot.case = sum(dotted),
  camelCase = sum(camel),
  lowercase_only = sum(grepl("^[a-z][a-z0-9]*$", fns))
)
#>     snake_case       dot.case      camelCase lowercase_only
#>              8            344            200            371
fns[snake]
#> [1] "l10n_info"       "numeric_version" "package_version" "pcre_config"
#> [5] "rep_len"         "seq_along"       "seq_len"         "sort_by"
head(fns[dotted], 4L)
#> [1] "all.equal"             "all.equal.character"   "all.equal.default"
#> [4] "all.equal.environment"

T <- FALSE # nolint: T_and_F_symbol_linter, object_name_linter.

In base R 4.6.1 there are 344 dotted names (`all.equal`, `is.na`, `as.numeric`) against 8 in snake case (`seq_len`, `seq_along`, `rep_len`, `sort_by`, `numeric_version`, `package_version`, `pcre_config` and `l10n_info`), and 200 in camel case (`addNA`, `readLines`, `tryCatch`). A new package that follows the tidyverse guide will therefore sit next to base functions in three styles; `object_name_linter` checks only the names the package defines.

The last two lines of the script are the reason for the guide's rule about `T` and `F`. The help page says that `TRUE` and `FALSE` are reserved words and `T` and `F` are global variables whose initial values are those constants. Assigning to `T` is allowed, and `c(TRUE, T)` then holds `TRUE` and `FALSE`; assigning to `TRUE` is a syntax-level error (`invalid (do_set) left-hand side to assignment`). `T_and_F_symbol_linter` is a default linter for that reason.

=== Spacing, braces and line length

The guide puts a space after a comma and never before it; no spaces inside the parentheses of a call; a space before the parenthesis of `if`, `for` and `while`; a space after the parentheses of `function`; and a space on both sides of most infix operators. The exceptions that take no space are the high-precedence operators `::`, `$`, `@`, `[`, `[[`, `^`, unary minus and plus, and `:`. The embracing operator is written with inner spaces, `{{ var }}`. Extra spaces are allowed only to align `=` or `+<-+` in neighbouring lines.

A line should have at most 80 characters, and a call that does not fit goes one argument per line with the closing parenthesis on its own line. A braced expression has `{` as the last character of its line, indents its contents by two spaces and has `}` as the first character of its line, with `else` on the same line as `}`. The body of a loop is always braced; a one-line `if` may omit the braces only when it has no side effects and does not change the control flow, so `if (y < 0) stop("Y is negative")` belongs in braces. Semicolons are never recommended.

=== Assignment, quotes and logical values

Assignment uses `+<-+`, not `=`. Writing R Extensions says the same in its section on tidying code: it recommends the consistent use of `+<-+` rather than `=` for assignment. Strings use double quotes unless the text itself contains double quotes and no single quotes. `TRUE` and `FALSE` are written in full. The guide also asks for explicit conditions: `if (length(x) > 0)` instead of `if (length(x))`, `&&` and `||` (never `&` and `|`) inside an `if`, and no assignment inside a function call.

=== Control flow and functions

Anything that changes the control flow (`return()`, `stop()`, `break`, `next`) goes on its own line in braces. The guide asks for `return()` only for early exits: the last expression of a function is its value, so `pass:c[add_two <- function(x, y) { x + y }]` is preferred to a version that ends with `return(x + y)`. A function that is called for its side effects should return its first argument invisibly so that it can sit inside a pipe, which is what `print()` methods do (`invisible(x)`).

Short anonymous functions use the lambda `+\(x) x + 1+` (R 4.1.0), but the guide says not to use `+\()+` for functions that span several lines, for named functions or inside a pipe; it asks for `function(x) {` in those cases. A function definition that does not fit on one line has two accepted layouts: the single-indent layout, with each argument indented by two spaces and `) {` on its own line, and the hanging-indent layout, with the arguments aligned under the first one.

=== Pipes

The guide recommends the base pipe `+|>+` over magrittr's `%>%` (it says that as of R 4.3.0 the base pipe has every feature of magrittr that it recommends). `+|>+` has a space before it and usually a new line after it, and from the second step on each line is indented by two spaces, so each step is one line. A short pipe may stay on one line, but the guide says that short pipes tend to grow and recommends one function per line. A pipe is for a sequence of steps applied to one object; it is not used when several objects are manipulated at once or when an intermediate object deserves a name. The page xref:programming-languages/r/pipes-and-the-native-pipe.adoc[Pipes and the Native Pipe] covers the operator itself.

=== Comments and files

A comment starts with `#` followed by one space and explains why, not what or how; comments are in sentence case and end with a full stop only when there are at least two sentences. A script that uses add-on packages loads them all at the very beginning. File names are lower case, contain no spaces or special characters, use `-` or `_` to separate words and end in `.R`; files that must be used in order start with a number padded to the same width (`01-load-data.R`), and a name that says `final` is a warning sign.

=== Google's R style guide is a fork

Google publishes an R style guide (https://google.github.io/styleguide/Rguide.html[google.github.io/styleguide/Rguide.html], again a community document) that describes itself as a fork of the tidyverse guide: it explains only the differences, and says that Google runs styler on every file that is checked in. The differences it lists are few:

[cols="3,4,4",options="header"]
|===
|Topic |Tidyverse guide |Google's fork
|Function names |snake case, verbs |`BigCamelCase`, and a private function starts with a dot
|Object names |snake case |Not dot.case any more: the guide says that it used to recommend dot.case and is moving away from it because it clashes with S3 methods
|Return |implicit; `return()` for early exits |explicit `return()` at the end: it asks not to rely on implicit return
|Right-hand assignment |one accepted form of pipe assignment is `+->+` at the end |not supported
|`attach()` |not discussed in the style part |do not use it
|Namespaces |not a style rule |qualify every external function (`purrr::map()`); `@importFrom` rather than `@import`
|===

Source: https://google.github.io/styleguide/Rguide.html[Google's R Style Guide (community)]; https://style.tidyverse.org/pipes.html[tidyverse style guide: Pipes (community)]

The practical consequence is on the lintr side. The default linters follow the tidyverse rules, so `return_linter` reports Google's explicit returns and `object_name_linter` reports `BigCamelCase`. A team that has chosen Google's style configures the opposite choices, `return_linter(return_style = "explicit")` and an `object_name_linter` that accepts both styles, `object_name_linter(styles = c("snake_case", "CamelCase"))`, in its `.lintr` file; lintr cannot apply a different style to functions than to other objects, so accepting both is the closest it gets. The section on configuration shows where such a line goes.

== What a linter or a formatter reads

Both kinds of tool start from the parser's token table, not from the abstract syntax tree that `quote()` returns. The syntax tree has no comments and no layout, but a formatter must keep the comments and a linter must say in which column a mistake starts. When the option `keep.source` is `TRUE`, or `parse()` is called with `keep.source = TRUE`, R's parser records every token with its position, and `getParseData()` returns that record as a data frame. The help page dates the feature to R 3.0.0, when code from Romain Francois's `parser` package was added to the parser. Each row has `line1`, `col1`, `line2`, `col2`, an `id` and a `parent` (the rows form a tree), a `token` type such as `SYMBOL`, `LEFT_ASSIGN`, `EQ_ASSIGN`, `NUM_CONST` or `COMMENT`, a `terminal` flag and the `text`. The script shows the terminal rows of the same statement written two ways.

[source,r]
----
# The token table that linters and formatters read: one row per token.
exprs <- parse(text = "n = n+1", keep.source = TRUE)
tokens <- getParseData(exprs)
tokens[tokens$terminal, c("line1", "col1", "token", "text")]
#>   line1 col1     token text
#> 1     1    1    SYMBOL    n
#> 2     1    3 EQ_ASSIGN    =
#> 5     1    5    SYMBOL    n
#> 6     1    6       '+'    +
#> 8     1    7 NUM_CONST    1

# Comments are tokens too, which is why a formatter can keep them.
exprs <- parse(text = "n <- n + 1 # count", keep.source = TRUE)
tokens <- getParseData(exprs)
tokens[tokens$terminal, c("col1", "token", "text")]
#>   col1       token    text
#> 1    1      SYMBOL       n
#> 2    3 LEFT_ASSIGN      <-
#> 4    6      SYMBOL       n
#> 5    8         '+'       +
#> 7   10   NUM_CONST       1
#> 9   12     COMMENT # count
----
Source: https://search.r-project.org/R/refmans/utils/html/getParseData.html[R documentation: getParseData]; https://search.r-project.org/R/refmans/base/html/parse.html[R documentation: parse]

The two assignments differ in one token: `=` is `EQ_ASSIGN` and `+<-+` is `LEFT_ASSIGN`, which is exactly what `assignment_linter` looks for and what styler's `scope = "tokens"` rewrites. The comment `# count` is a `COMMENT` token with a position, which is how a formatter can keep it and how `commented_code_linter` can try to parse it as code. Both tools build on this table: lintr turns it into an XML document and asks XPath questions of it (the next section writes a linter that way), and styler works on what its documentation calls a nested parse table, built from `getParseData()`. The consequence is the same for both: code that does not parse cannot be styled, and lintr reports it as a lint of type "error". The page xref:programming-languages/r/language-objects-and-quoting.adoc[Language Objects and Quoting] explains the syntax tree itself.

== lintr

lintr (https://lintr.r-lib.org/[lintr.r-lib.org]) is a linter for R code. It is a CRAN package, installed with `install.packages("lintr")`, and it is not part of R. It lints files, directories and packages, chooses its rules from a configuration file called `.lintr`, and reports in the console, in RStudio's Markers pane, in editors through the language server, and as GitHub annotations in continuous integration. The version used here is 3.4.0.

=== lint(), lint_dir() and lint_package()

`lint()` lints one file, or a string of code when it is given `text =` or a `filename` that contains a newline. `lint_dir()` lints every file of a directory whose name matches a pattern; the default pattern covers `.R`, `.Rmd`, `.qmd`, `.Rnw`, `.Rhtml`, `.Rrst`, `.Rtex` and `.Rtxt`, in any letter case. `lint_package()` lints the places where a package keeps R code: `R/`, `tests/`, `inst/`, `vignettes/`, `data-raw/`, `demo/` and `exec/`. All three return an object of class `lints`, which prints one block per lint: `file:line:column: type: [linter] message`, then the line of code, then carets under the offending part. When there is nothing to report the printed result is an informational message, `No lints found.`

[source,r]
----
library(lintr)

# lint(text =) checks code held in a string; "<text>" stands for the file name.
lints <- lint(text = "x = 1\n")
lints
#> <text>:1:3: style: [assignment_linter] Use <- for assignment, not =.
#> x = 1
#>   ^
class(lints)
#> [1] "lints" "list"
class(lints[[1L]])
#> [1] "lint" "list"
names(lints[[1L]])
#> [1] "filename"      "line_number"   "column_number" "type"
#> [5] "message"       "line"          "ranges"        "linter"
as.data.frame(lints)[, c("line_number", "column_number", "type", "linter")]
#>   line_number column_number  type            linter
#> 1           1             3 style assignment_linter

# Clean code gives an empty "lints" object and a message.
clean <- lint(text = "x <- 1\n")
clean
#> ℹ No lints found.
length(clean)
#> [1] 0
----
Source: https://lintr.r-lib.org/reference/lint.html[lintr package documentation: lint, lint_dir and lint_package]

A `lints` object is a list of `lint` objects, so `length()`, `[[` and `lapply()` work on it, and `as.data.frame()` flattens it into one row per lint with the columns `filename`, `line_number`, `column_number`, `type`, `message`, `line` and `linter`. A lint has one of the types `style`, `warning` or `error`; the linter that found it is recorded by name, not by its function. Two things are good to know about the call itself. `lint()` reads the `.lintr` file only when it lints a file, not when it lints `text =` (the `parse_settings` argument defaults to `!inline_data`, and the 3.3.0-1 release notes say that ad hoc calls such as `lint(text = "str")` no longer pick up settings automatically). And `cache = TRUE` stores results so that unchanged code is not linted again.

The next script lints the "before" file of this page. It is an overdue-loans report written the way the tutorials of 2012 might have written it: `=` for assignment, `1:length()`, `T` for `TRUE`, `x == NA`, `sapply()`, a function called `Total.Overdue`, a semicolon, an explicit `return()` and a line that is too long. The file is not linted, on purpose; the script holds its text in a raw string, writes it to a file called `messy.R` in the working directory, lints that file and deletes it. The string sits between `+# nolint start+` and `+# nolint end+` comments so that lintr does not lint the long line inside the string.

[source,r]
----
library(lintr)

# The "before" file, written to the working directory and deleted at the end.
# nolint start: line_length_linter.
messy <- r"---(# messy.R: an overdue-loans report, written badly on purpose
source("scenario.R")
loan_days = 21
count_overdue <- function(loans,today){
  n=0; unused = "x"
  for(i in 1:length(loans$loan_date)){
    if(is.na(loans$return_date[i])==T & !is.na(loans$loan_date[i])) {
      if (today - loans$loan_date[i] > loan_days) n = n+1 }
  }
  return( n )
}
per_member = sapply(split(loans, loans$member), function (x) nrow(x))
n_unreturned = sum(loans$return_date == NA)
Total.Overdue <- count_overdue(loans, shelf_today)   # the total
#old_total <- Total.Overdue + 1
message("There are ", Total.Overdue, " overdue loans among ", nrow(loans), " loans on the shelf, counted on ", format(shelf_today))
print(n_unreturned); print(length(per_member))
)---"
# nolint end
cat(messy, file = "messy.R")

lints <- lint("messy.R")
length(lints)
#> [1] 29

report <- report[, c("line_number", "column_number", "type", "linter")]
report

=== The .lintr file

The settings of a project live in a file called `.lintr` in the project root. It is a file in Debian control format (DCF, the format of `DESCRIPTION`): one `name: value` per field, with continuation lines indented, and the value of each field is evaluated as R code when lintr reads it. `lintr::use_lintr()` writes a starting file; in a package it also adds `^\.lintr$` to `.Rbuildignore`, so that the file is not part of the built tarball. The `shelf` package ships the file that `use_lintr(type = "tidyverse")` wrote. The script prints it, reads it as DCF and then lints the package twice.

The two `lint_package()` calls show a property that matters in continuous integration. In a fresh `Rscript` session the first call reports a `warning` in `tests/testthat/helper-shelf.R`: no visible global function definition for `test_path`. The helper uses testthat's `test_path()` without a prefix, as testthat helper files do, and `object_usage_linter` runs `codetools::checkUsage()` in the environment where lintr is running, where testthat has not been attached. After `library(testthat)` the same call reports no lints. The linters tagged `executing` (`namespace_linter`, `object_length_linter`, `object_name_linter`, `object_overwrite_linter`, `object_usage_linter` and `unused_import_linter`) evaluate parts of the code, for example to load the packages that a package imports, and their documentation asks that the package itself is loaded, with `pkgload::load_all()` or by installing it, before linting, and that they are not used on untrusted code (lintr package documentation: executing_linters). A CI job that lints a package therefore installs it first; the job shown later does.

The fields that `.lintr` supports are the settings that `default_settings` lists, and the lintr documentation describes these:

[cols="2,5,3",options="header"]
|===
|Field |Meaning |Default
|`linters` |the list of linters, usually `+linters_with_defaults(...)+`, `+linters_with_tags(...)+` or `+all_linters(...)+` |`default_linters`
|`exclusions` |files and directories that are not linted; a named entry (`"R/zzz.R" = c(2L, 6L)`) excludes only the listed lines of that file; globs such as `knitr*` are accepted since 3.3.0-1; paths are relative to the `.lintr` file |none (`lint_dir()` skips `renv` and `packrat`, `lint_package()` skips `R/RcppExports.R`)

A setting can also come from an R option named `lintr.` plus the name (`options(lintr.exclude = "# skip lint")` beats the file) or from an argument of `lint()`; the search order for the file itself is the option `lintr.linter_file` (default `.lintr`, or the environment variable `R_LINTR_LINTER_FILE`), the directory of the linted file, the closest parent directory, the home directory and finally the user's configuration directory. Since lintr 3.1.1 a file named `.lintr.R` is also accepted, with plain R assignments instead of DCF; the release notes call that support experimental.

`use_lintr()` writes the starting file for a project. The next script runs it on a copy of the package in a temporary directory, first with `type = "tidyverse"` (the default linters), then again to show that it refuses to overwrite a file, then with `type = "full"`, which starts from every linter in lintr and excludes the directories `renv` and `packrat`. === Excluding code: nolint

A lint on a line is dropped when the line carries a comment that matches the `exclude` pattern. The forms, which the next script runs on seven lines, are `+# nolint+` (all linters, this line), `+# nolint: assignment_linter.+` (only the named linters, this line, with a trailing full stop and several linters separated by commas), `+# nolint start+` and `+# nolint end+` (a range, optionally with `: linter_name.` after `start`) and `+# nolint next+` (the next line).

[source,r]
----
library(lintr)

# Each line of "code" is lintable on its own; the comments are the markers.
code <- c(
  "a = 1",
  "b = 2 # nolint",
  "c = 3 # nolint: assignment_linter.",
  "d = 4 # nolint: object_name_linter.",
  "# nolint start",
  "e = 5",
  "f = 6",
  "# nolint end",
  "# nolint next",
  "g = 7",
  "# nolint start: assignment_linter.",
  "h <- sapply(1:3, identity); i = 9",
  "# nolint end",
  ""
)
lints <- lint(text = paste(code, collapse = "\n"))
as.data.frame(lints)[, c("line_number", "linter")]
#>   line_number            linter
#> 1           1 assignment_linter
#> 2           4 assignment_linter
#> 3          12  semicolon_linter

# The marker patterns are settings, and they are regular expressions.
default_settings$exclude
#> #[[:space:]]*nolint
default_settings$exclude_start
#> #[[:space:]]*nolint start
default_settings$exclude_end
#> #[[:space:]]*nolint end
default_settings$exclude_next
#> #[[:space:]]*nolint next
----
Source: https://lintr.r-lib.org/articles/lintr.html[lintr package documentation: Get started (the exclusion settings)]; https://lintr.r-lib.org/reference/read_settings.html[lintr package documentation: read_settings]

Line 4 shows that the named form excludes only what it names: `+# nolint: object_name_linter.+` does not silence the assignment lint. The range on lines 11 to 13 silences `assignment_linter` and leaves the semicolon lint on line 12. This reference uses the named form with `start`/`end` or on one line, so that a reader sees which rule is being set aside (the examples above on `T` and `F`, and the string that holds the "before" file). A bare `+# nolint+` is the opposite habit: it silences every present and future linter on the line. A marker inside a string is not a comment, so it does not count: the scripts on this page contain such markers in strings and are linted normally.

=== Writing a linter

A linter is a function with the class `linter` that returns a function of a source expression. The fastest way to write one is `make_linter_from_xpath()`, which takes an XPath query on the XML version of the parse data and a message. The script reports every call to `print()`, a rule some projects have for scripts that should use `message()`. The query uses the token names of the earlier table: `SYMBOL_FUNCTION_CALL` is the token of a name in the position of a function being called.

[source,r]
----
library(lintr)

# A linter built from an XPath query on the parse tree: report calls to print().
no_print_linter <- make_linter_from_xpath(
  xpath = "//SYMBOL_FUNCTION_CALL[text() = 'print']",
  lint_message = "Use message() for progress output."
)
class(no_print_linter)
#> [1] "function"
lint(text = "print('hi')\nx <- 1\n", linters = list(no_print_linter()))
#> <text>:1:1: warning: [no_print_linter] Use message() for progress output.
#> print('hi')
#> ^~~~~
----
Source: https://lintr.r-lib.org/reference/make_linter_from_xpath.html[lintr package documentation: make_linter_from_xpath]; https://lintr.r-lib.org/articles/creating_linters.html[lintr package documentation: Creating new linters]

The vignette on creating linters describes the more general `Linter()` constructor, the variant `make_linter_from_function_xpath()` for linters about calls of named functions, and `expect_lint()`, the testthat expectation that checks the lints of a piece of code.

=== lintr in continuous integration

A CI job runs `lintr::lint_package()` and fails when there are lints. Two settings make the failure visible. The environment variable `LINTR_ERROR_ON_LINT=true` (or the `error_on_lint` setting) makes printing a non-empty `lints` object quit R with a non-zero status, and when R runs on GitHub Actions the printing turns every lint into an annotation on the pull request. The transcript runs `lint()` on a one-line file in a shell, with and without the variable; the file is printed with its absolute path, shortened here to `~/shelf`.

[source,bash]
----
printf 'x = 1\n' > demo.R
LINTR_ERROR_ON_LINT=true Rscript -e 'lintr::lint("demo.R")'
echo "exit status: $?"
Rscript -e 'lintr::lint("demo.R")'
echo "exit status: $?"
rm demo.R
----

Source: https://lintr.r-lib.org/articles/continuous-integration.html[lintr package documentation: Continuous integration]; https://search.r-project.org/R/refmans/utils/html/Rscript.html[R documentation: Rscript]

[source,text]
----
~/shelf/demo.R:1:3: style: [assignment_linter] Use <- for assignment, not =.
x = 1
  ^
exit status: 31
~/shelf/demo.R:1:3: style: [assignment_linter] Use <- for assignment, not =.
x = 1
  ^
exit status: 0
----

Source: https://lintr.r-lib.org/articles/continuous-integration.html[lintr package documentation: Continuous integration]

The status 31 is what lintr 3.4.0 used when the transcript was recorded; the documentation only says that the process is killed. The lint is printed in both runs, and without the variable the script ends normally, which is why a CI job that does not set it passes with lints in its log. For GitHub Actions the `r-lib/actions` project publishes ready-made workflows, and `usethis::use_github_action("lint")` copies the `lint.yaml` one into `.github/workflows`; `lint-changed-files` and `lint-project` are the variants for pull requests and for projects that are not packages. The workflow is a YAML file of the following shape (read on 2026-10-21 from the example in the repository, not run here, with `actions/checkout@v6` as the example pins it):

[source,yaml]

on:
  push:
    branches: [main, master]
  pull_request:

name: lint.yaml

permissions: read-all

jobs:
  lint:
    runs-on: ubuntu-latest
    env:
      GITHUB_PAT: ${{ secrets.GITHUB_TOKEN }}
    steps:
      - uses: actions/checkout@v6

      - uses: r-lib/actions/setup-r@v2

      - uses: r-lib/actions/setup-r-dependencies@v2
        with:
          extra-packages: any::lintr, local::.
          needs: lint

      - name: Lint
        run: lintr::lint_package()
        shell: Rscript {0}
        env:
          LINTR_ERROR_ON_LINT: true
----

=== Common errors and warnings

The messages below are the real ones of lintr 3.4.0. A syntax error is not an R error: the linter turns it into a lint of type `error` so that the other files are still linted. The rest are the leftovers of older code: linters given by name, a linter function that was not called, a function that was removed, and a file that is not there.

[source,r]
----
library(lintr)

# Code that does not parse is reported as a lint of type "error".
lints <- lint(text = "x <- (1\n")
lints
#> <text>:1:8: error: [error] unexpected end of input
#> x <- (1
#>        ^
lints[[1L]]$type
#> [1] "error"
lints[[1L]]$linter
#> [1] "error"

# Linters given by name, the lintr 2.x way, are refused.
tryCatch(
  lint(text = "x = 1\n", linters = "assignment_linter"),
  error = \(e) conditionMessage(e)
)
#> [1] "ℹ Expected `linters()` to be a function of class <linter>.\n✖ Instead, it is a string."

tryCatch(
  lint(text = "1:length(x)\n", linters = seq_linter),
  error = \(e) conditionMessage(e)
)
#> [1] "ℹ Expected `linters()` to be a function of class <linter>.\n✖ Instead, it is a function."

exists("with_defaults", where = asNamespace("lintr"))
#> [1] FALSE
tryCatch(with_defaults(), error = \(e) conditionMessage(e))
#> [1] "could not find function \"with_defaults\""

tryCatch(lint("no-such-file.R"), error = \(e) conditionMessage(e))
#> Warning in file(con, "r") :
#>   cannot open file 'no-such-file.R': No such file or directory

== styler

styler (https://styler.r-lib.org/[styler.r-lib.org]) is a formatter for R code: it rewrites the layout of code to follow the tidyverse style guide. It is a CRAN package (1.11.0 here), used from the console, from RStudio addins, from `languageserver` in other editors, in pre-commit hooks and in CI. Its functions are `style_text()` for a character vector, `style_file()` for files, `style_dir()` for a directory and `style_pkg()` for a package, and the style itself is `tidyverse_style()`. styler styles `.R`, `.Rmd`, `.Rmarkdown`, `.qmd` and `.Rnw` files, and `.Rprofile`; in a package it also styles the code in roxygen examples (`include_roxygen_examples = TRUE`).

Two principles run through its documentation. First, styler is a formatter, so it changes layout and not meaning: spaces, line breaks, indentation and a short list of tokens (`=` as assignment becomes `+<-+`, a single-quoted string becomes double-quoted, a semicolon becomes a line break). Second, the more a change can alter the code, the later styler lets it happen: the `scope` argument orders the changes from the least to the most invasive, and the manual for `style_file()` explains that styling below `scope = "tokens"` leaves the abstract syntax tree unchanged, so that styler can check it (round-trip validation), whereas token changes cannot be verified and have to be reviewed by a person.

=== style_text() and scope

`style_text()` returns the styled lines, and one element of the character vector is one line of code. The result has the class `vertical`; `cat(x, sep = "\n")` writes it plainly (printing it asks for the prettycode package to colour it and warns when it is missing). The script styles a four-line function that has every kind of layout problem, first with the default scope and then with each scope in turn.

[source,r]

library(styler)

  "if(is.na(loans$return_date[i]))n=n+1}",
  "n}"
)

# style_text() returns the styled lines; one element is one line of code.
styled <- style_text(code)

#> count_late <- function(loans, today) {
#>   n <- 0
#>   for (i in seq_len(nrow(loans))) {
#>     if (is.na(loans$return_date[i])) n <- n + 1

#>   n

# I() names the levels explicitly: change tokens, but leave the spacing alone.
cat(style_text("a=2", scope = I(c("tokens", "indention"))), sep = "\n")

Source: https://styler.r-lib.org/reference/style_text.html[styler package documentation: style_text]; https://styler.r-lib.org/reference/tidyverse_style.html[styler package documentation: tidyverse_style]

The five scopes are, in order of invasiveness, `"none"` (nothing), `"spaces"` (spaces between tokens on one line), `"indention"` (the indentation at the start of a line), `"line_breaks"` (line breaks between tokens) and `"tokens"` (the tokens themselves, which is the default). A string names a level and includes all the less invasive ones; `I()` names the levels one by one, as the last line of the script does: with `I(c("tokens", "indention"))` the `=` becomes `+<-+` but the missing spaces are left alone, so the result is `+a<-2+`. The output above shows the order. With `"spaces"` the spacing is fixed but the indentation is not. `"indention"` fixes the indentation, but the closing braces still follow the last statement on its line (`n = n + 1}`). `"line_breaks"` moves each closing brace to its own line, but the semicolon in `n = 0; for` stays. Only `"tokens"` splits the semicolon and turns the assignments into `+<-+`.

=== Options of tidyverse_style()

`tidyverse_style()` has six arguments: `scope`, `strict`, `indent_by`, `start_comments_with_one_space`, `reindention` and `math_token_spacing`. `style_text()`, `style_file()` and the others pass `+...+` to it, so `style_text(x, scope = "spaces")` and `style_text(x, transformers = tidyverse_style(scope = "spaces"))` are the same call. `strict = TRUE` forces exactly one space where the style wants one; `strict = FALSE` only inserts a space where there is none and leaves extra ones, which keeps the alignment of assignments that the author lined up on purpose. `indent_by` is the width of one indentation level. `math_token_spacing` is a list that says which math operators have spaces around them (`+specify_math_token_spacing(zero = ...)+`); the tidyverse default puts spaces around `pass:c[+]`, `-`, `+*+` and `/` and none around `+^+`. `start_comments_with_one_space` normalises `+#comment+` to `+# comment+`, and `reindention` lets some comments keep a different indentation.

[source,r]
----
library(styler)

# strict = TRUE (the default) forces one space; strict = FALSE keeps alignment.

cat(style_text(aligned), sep = "\n")
#> ab <- 3
#> a <- 3
#> x <- 1 + 2
cat(style_text(aligned, strict = FALSE), sep = "\n")

#> a  <- 3
#> x    <- 1 +  2

# indent_by is the width of one indentation level.
body <- c("f <- function() {", "x <- 1", "}")
cat(style_text(body, indent_by = 4), sep = "\n")
#> f <- function() {
#>     x <- 1
#> }

#> # styler: off
#> b   =  2
#> # styler: on
#> c <- 3

Four lines of the output deserve attention. `strict = FALSE` left `pass:c[a  <- 3]` and `pass:c[x    <- 1 +  2]` as the author wrote them, where the default collapsed them to one space. `math_token_spacing` gave `pass:c[1 + +1/2*2^2]` (the spaces went where the table said, and the unary plus after `pass:c[+]` got its own). === What styler does not do

The same snippet through `style_text()` shows the limit of a formatter. It shortened nothing and renamed nothing; it did not touch the `T`, the `1:length(x)`, the `sapply()` or the comparison with `NA`, because none of them is a layout problem, and it did not break a call that is longer than the line limit.

=== Files, directories and packages

`style_file()` styles files in place, `style_dir()` a directory (recursive by default) and `style_pkg()` the code of a package. All three return, invisibly, a data frame with one row per file and the column `changed`; they print a progress report, one line per file, with a tick for an unchanged file and an information sign for a changed one. The documentation of `style_file()` begins with a warning to examine the result carefully, because the function overwrites files, and recommends styling only files under version control and styling first with a `scope` below `"tokens"`, committing, and only then with tokens. The argument `dry` makes the call safe: `"off"` (the default) writes the changes back, `"on"` computes them and writes nothing, and `"fail"` raises an error when styling would change a file, which turns styler into a CI check. `dry` was added in styler 1.4.0.

The script writes the "before" file to disk, runs the three modes in turn and then lints the styled file, to see what a formatter leaves for a person.

=== Caching, addins and other ways to run styler

styler is slow on large projects, so since version 1.3.0 it has a cache of styled code. The cache stores the hash of code that already complies, so it takes no disk space to speak of; it is specific to a version of styler, and by default it is cleaned of files older than six days to comply with the CRAN policy (the option `styler.cache_root` can set a permanent one; `cache_info()`, `cache_activate()`, `cache_clear()` and `cache_deactivate()` manage it). In RStudio the addins `Style active file` and `Style selection` call `style_file()` and `style_text()` with the transformers in the option `styler.addins_style_transformer`. The vignette on third-party integrations lists the rest: the `style-files` hook of the `precommit` package (community) that styles before every commit, `usethis::use_tidy_style()` for a whole project, the GitHub Action that runs `style_pkg()` when source files change (`usethis::use_github_action("style")`), the knitr chunk option `tidy = "styler"` that formats code in R Markdown without changing the source, and the R language server, which uses styler for format-on-save in VS Code and other editors.

== codetools: checkUsage() and findGlobals()

codetools is a recommended package: it ships with R, is installed with every standard installation and needs nothing from CRAN. Its author is Luke Tierney. It analyses closures without running them, and its two jobs are `checkUsage()`, which reports possible problems in a function, and `findGlobals()`, which lists the global names a function uses. `checkUsage()` is what `object_usage_linter` calls and what `R CMD check` calls on every function of a package.

=== checkUsage()

`+checkUsage(fun, name, report = cat, all = FALSE, ...)+` checks one closure. Without `all`, it reports names that have no visible definition (global variables and functions) and local variables that are assigned and not used. `name` is the label printed at the start of every message; leaving it out prints `<anonymous>`. The script defines a function with a typo, `totl`, and an unused local, and checks it. `findGlobals()` returns everything the function uses from outside: operators, `for`, base functions and global variables; `merge = FALSE` separates functions from variables. The last call removes `loan_days`, which `source("scenario.R")` had defined, and shows that the check consults the function's environment.

[source,r]
----
library(codetools)
source("scenario.R")

# A function with a typo and a local variable that is never used.
# nolint start: object_usage_linter.
late_days <- function(loans, today) {
  unused <- 1L
  total <- 0L
  for (i in seq_len(nrow(loans))) {
    total <- total + (today - loans$loan_date[i] > loan_days)
  }
  totl
}
# nolint end
checkUsage(late_days, name = "late_days")
#> late_days: no visible binding for global variable ‘totl’

The message forms are fixed and worth recognising, because they are also the text of `R CMD check` notes: `no visible binding for global variable ‘name’` (a variable that is neither local, nor an argument, nor found in the environments of the function), `no visible global function definition for ‘name’` (the same for a name that is called), and `local variable ‘name’ assigned but may not be used`. With `all = TRUE` further messages appear, such as `parameter ‘x’ changed by assignment` and `parameter ‘x’ may not be used`. The arguments that matter: `all`, `suppressLocal` (all local-variable messages), `suppressParamAssigns`, `suppressParamUnused`, `suppressLocalUnused`, `suppressUndefined`, `skipWith`, `suppressPartialMatchArgs` and `report`, a function that receives each message (the default is `cat`). The next script shows the difference `all = TRUE` makes, a false alarm that non-standard evaluation causes, the `skipWith` argument that avoids it for `with()` and a custom `report`.

Source: https://search.r-project.org/CRAN/refmans/codetools/html/checkUsage.html[codetools package documentation: checkUsage]

`subset(d, genre == "fiction")` is correct code, and codetools reports `genre` because it cannot know that `subset()` evaluates its second argument inside the data frame. That is the one big source of false positives in static analysis of R, and the reason that functions with data masks (dplyr, `subset()`, `with()`, `transform()`, model formulas) draw notes. lintr's `object_usage_linter(skip_with = TRUE)` and `R CMD check` both skip the body of `with()` by default (`checkUsage()` itself defaults to `skipWith = FALSE`), which is why only the call without `skipWith = TRUE` complained.

=== checkUsagePackage() and checkUsageEnv()

`checkUsageEnv(env)` checks every closure in an environment and `checkUsagePackage(pack)` every function of a loaded package (it checks the namespace's internal frame). They take the options of `checkUsage()`. The script checks `shelf` with the default options, which print nothing, and with `all = TRUE`, which prints the kind of message a team can safely ignore or fix at leisure: the unused `libname` and `pkgname` that the hook signatures `.onLoad()` and `.onAttach()` require, and four parameters that are reassigned.

suppressPackageStartupMessages(library(shelf))

cat("default: nothing to report\n")

#> .onAttach: parameter ‘pkgname’ may not be used
#> .onLoad: parameter ‘libname’ may not be used
#> .onLoad: parameter ‘pkgname’ may not be used
#> clean_books: parameter ‘books’ changed by assignment

== R CMD check as static analysis

`R CMD check` runs codetools as one of its steps, which the log calls "checking R code for possible problems". The manual for writing packages says so in the paragraph that also lists the checks of the package-loading hooks, of the argument lists of S3 methods and of foreign function calls. The same step reports calls to functions of the default packages other than base that the package does not import. R 3.3.0 changed that: since then the check attaches only the base package while it analyses the code, so a use of `head()` or `median()` without `utils::` or an import is reported as an undefined global, with a suggested `importFrom()` for the `NAMESPACE` file (R NEWS, Changes in R 3.3.0). This is the origin of the most common note in package development.

The transcripts below reproduce it in a copy of `shelf`. A file `R/overdue-top.R` is added with a function that uses the column `days_out` of a data frame and `head()`. The commands build the package without building the vignette and check it without the PDF manual (which needs a TeX installation that the environment of these examples does not have) and without the tests; the header of the check, with the platform, the compiler and the time, is trimmed from the output.

[source,bash]
----
cat > shelf/R/overdue-top.R <<'EOT'
overdue_top <- function(loans, today = shelf_today()) {
  late <- overdue_loans(loans, today)
  late <- late[order(-days_out), ]
  head(late, n = 3L)
}
EOT
R CMD build --no-build-vignettes shelf
R CMD check --no-manual --no-tests --ignore-vignettes shelf_0.1.0.tar.gz
----

Source: https://cran.r-project.org/doc/manuals/r-release/R-exts.html#Checking-packages[Writing R Extensions: Checking packages]; https://search.r-project.org/R/refmans/utils/html/Rscript.html[R documentation: Rscript]

[source,text]
----
* checking R code for possible problems ... NOTE
overdue_top: no visible binding for global variable ‘days_out’
overdue_top: no visible global function definition for ‘head’
Undefined global functions or variables:
  days_out head
Consider adding
  importFrom("utils", "head")
to your NAMESPACE file.
...
Status: 1 NOTE
----

Source: https://cran.r-project.org/doc/manuals/r-release/R-exts.html#Checking-packages[Writing R Extensions: Checking packages]

The two lines have different causes and different fixes. `head` is a function of a base package that the package uses without importing it; the check suggests the fix, and the usual fix is to qualify the call, `utils::head()`, or to add `@importFrom utils head` to the roxygen block (which writes `importFrom(utils, head)` into `NAMESPACE`; see xref:programming-languages/r/packages-libraries-and-namespaces.adoc[Packages, Libraries and Namespaces]). A package that calls `utils::` or `stats::` functions should also list `utils` or `stats` in `Imports`, which is what `usethis::use_package("utils")` does. `days_out` is a column of a data frame. It is not a variable, and the code is right, but codetools cannot know that. The remedy for a variable used through non-standard evaluation is `utils::globalVariables()`, called once in a source file of the package, outside any function; it declares the names as globals for the purpose of the check. The second version of the file does both. It is a file of the package, `R/overdue-top.R`, shown as it was checked, and not a script to run on its own.

[source,r]
----
utils::globalVariables("days_out")

overdue_top <- function(loans, today = shelf_today()) {
  late <- overdue_loans(loans, today)
  late <- late[order(-days_out), ]
  utils::head(late, n = 3L)
}
----

Source: https://search.r-project.org/R/refmans/utils/html/globalVariables.html[R documentation: globalVariables]

With that file in place the same two commands print `+checking R code for possible problems ... OK+` and `Status: OK`. The usual alternative for dplyr code, recommended in dplyr's documentation for package authors, is to avoid the global variable: `.data$days_out` for data masking (with `@importFrom rlang .data`) and the string `"days_out"` for tidy selection, instead of a bare name (dplyr package documentation: using dplyr in packages). The function was removed from the copy again after the experiment.

The check does not report unused local variables by default. Its default profile for codetools is `skipWith = TRUE`, `suppressPartialMatchArgs = FALSE` and `suppressLocalUnused = TRUE`. The environment variable `+_R_CHECK_CODETOOLS_PROFILE_+` changes the profile, and the manual for writing packages recommends `suppressLocalUnused=FALSE` as a revealing customisation, because an unused local assignment can be a mistyped name or a `+<-+` that should have been `+<<-+`. The third experiment shows it:

[source,bash]
----
cat > shelf/R/overdue-top.R <<'EOT'
overdue_count <- function(loans, today = shelf_today()) {
  scratch <- overdue_loans(loans, today)
  nrow(overdue_loans(loans, today))
}
EOT
R CMD build --no-build-vignettes shelf
R CMD check --no-manual --no-tests --ignore-vignettes shelf_0.1.0.tar.gz
_R_CHECK_CODETOOLS_PROFILE_="suppressLocalUnused=FALSE" R CMD check --no-manual --no-tests --ignore-vignettes shelf_0.1.0.tar.gz
rm shelf/R/overdue-top.R
----

Source: https://cran.r-project.org/doc/manuals/r-release/R-exts.html#Checking-packages[Writing R Extensions: Checking packages]; https://cran.r-project.org/doc/manuals/r-release/R-ints.html#Tools[R Internals: Tools (the _R_CHECK_ environment variables)]

The first check ends with `+checking R code for possible problems ... OK+` and `Status: OK`; the second prints

[source,text]
----
* checking R code for possible problems ... NOTE
overdue_count: local variable ‘scratch’ assigned but may not be used
...
Status: 1 NOTE
----

Source: https://cran.r-project.org/doc/manuals/r-release/R-ints.html#Tools[R Internals: Tools (_R_CHECK_CODETOOLS_PROFILE_)]

The manual adds that this setting can give false positives, most often because of non-standard evaluation in formulas and because the intention is to return objects in the environment of a function. The environment variable `+_R_CHECK_USE_CODETOOLS_+` (true by default when the recommended packages are installed) turns the whole step off; leaving it on is almost always right. The other static checks in `R CMD check` have their own pages: undocumented objects and mismatched usage sections (xref:programming-languages/r/documentation-with-rd-roxygen2-and-vignettes.adoc[Documentation with Rd, roxygen2 and Vignettes]), the namespace and dependency checks (xref:programming-languages/r/creating-packages.adoc[Creating Packages]) and the submission rules (xref:programming-languages/r/publishing-to-cran.adoc[Publishing to CRAN]).

== Editors

Every editor integration of these tools goes through one of two routes: the editor calls the R package directly (RStudio), or it talks to the R language server (almost everything else).

*RStudio.* lintr's diagnostics show in the Markers pane (lint a file and look at the result), and the package provides two addins, for the current source and for the package, which its documentation suggests binding to `Alt+Shift+L` and `Ctrl+Shift+Alt+L`. RStudio also has its own diagnostics, switched on in Tools > Global Options > Code > Diagnostics, including an option to "provide R style diagnostics (e.g. whitespace)", and its own command Reformat Selection (`Ctrl+Shift+A` in the shortcuts reference). styler's addins `Style active file` and `Style selection` run `style_file()` and `style_text()`. See xref:programming-languages/r/ides-and-the-r-console.adoc[IDEs and the R Console].

*VS Code and other editors.* The community package languageserver implements the Language Server Protocol for R. In VS Code the R extension from REditorSupport uses it; the lintr documentation says that installing the package and the extension turns lintr on by default. The language server reads `.lintr` files, as its README says, for the linters; it formats code with styler, with `styler::tidyverse_style(indent_by = options$tabSize)` as the default style, which the option `languageserver.formatting_style` can replace. The same server serves Neovim, Emacs (eglot, lsp-mode), Sublime Text and others.

The next block is a fragment: it installs a package from CRAN and was not run.

[source,r]
----
install.packages("languageserver")
----

Source: https://github.com/REditorSupport/languageserver[languageserver README (community)]; https://lintr.r-lib.org/articles/editors.html[lintr package documentation: Editor setup]; https://posit-dev.github.io/air/editors.html[Air documentation: Editors (community)]; https://docs.posit.co/ide/user/ide/guide/code/diagnostics.html[RStudio User Guide: Code diagnostics]; https://docs.posit.co/ide/user/ide/reference/shortcuts.html[RStudio User Guide: Keyboard shortcuts]

*Positron and Air.* Positron has its own R support (the Ark kernel and language server described on the page on IDEs). The Air project (https://posit-dev.github.io/air/[posit-dev.github.io/air]) is an R formatter and language server written in Rust; its documentation has editor guides for VS Code and Positron, RStudio, Zed, Neovim, Helix and Emacs, and its formatter page says that it keeps lines within a width of 80 characters by splitting long calls and function definitions over several lines, which styler does not do. A project normally picks one formatter, styler or Air. The development version of lintr, whose `NEWS.md` on GitHub was read on 2026-10-21, adds two arguments to `line_length_linter()` for compatibility with Air, `allow_alignment_calls` and `allow_long_test_names`; the released 3.4.0 used here has only `length` and `ignore_string_bodies`, so those two are upcoming. *Emacs ESS* integrates lintr through flycheck, according to the lintr documentation.

== The style of this reference

The examples in this reference follow the tidyverse guide as the default linters enforce it, with a handful of choices that the guide leaves open or that differ from it. Knowing them helps when a reader copies a script and runs their own linter over it.

[cols="3,4,4",options="header"]
|===
|Convention |What the examples do |Where it differs from the tidyverse guide or from base R
|Assignment |`+<-+` everywhere; `=` only for arguments |as the guide
|Logical values |`TRUE` and `FALSE`, never `T` and `F` |as the guide
|Loops over indices |`seq_along(x)` and `seq_len(n)`, never `1:length(x)` |`seq_linter` is a default linter
|Applying a function |`vapply()` with a declared result type; `sapply()` appears only in a contrast marked `+# nolint+` |`sapply()` is on the undesirable list of lintr, not a rule of the guide
|Pipes |the native pipe `+\|>+`, one step per line in a pipeline |as the guide; `%>%` is mentioned, not used
|Anonymous functions |`+\(x)+` for short functions |the guide asks `function(x) {` for lambdas that span several lines, and the examples sometimes use `+\(x) {+` there; lintr does not flag it
|Returns |implicit; `return()` for early exits |as the guide; Google's guide differs
|Names |snake case for objects the examples define |base R names keep their dots and camel case
|Line length |at most 80 characters, comments included |as the guide
|Quotes |double quotes; single quotes only around a string that contains double quotes |as the guide
|Output in comments |lines that start with `+#>+` |a convention of reprex, not of the guide
|Silencing a linter |`+# nolint: name_linter.+` on the line, or `start`/`end` around a block |the guide says nothing about linters
|Dates and times in output |a fixed `shelf_today`, never `Sys.Date()` in a printed result |so that output is reproducible
|===

Source: https://style.tidyverse.org/functions.html[tidyverse style guide: Functions (community)]; https://lintr.r-lib.org/reference/linters.html[lintr package documentation: linters]

Every script in the section was run and then linted with the default linters of lintr 3.4.0 (`lintr::lint()` with no `.lintr`), and the rules above are those the linters accept; scripts that are bad on purpose live in a separate directory and are said to be unlinted where they appear.

== Where older tutorials differ

[cols="3,3,4",options="header"]
|===
|Older tutorial writes |Current practice |Why
|`lintr::with_defaults(line_length_linter(100))` |`linters_with_defaults(line_length_linter(100L))` |`with_defaults()` was deprecated in lintr 3.0.0 and removed in 3.3.0-1 (`could not find function "with_defaults"`)
|`lint("file.R", linters = list("assignment_linter"))`, or `lint(file, seq_linter)` |`lint("file.R", linters = list(assignment_linter()))` |linters are factories since 3.0.0; names and uncalled functions were deprecated in 3.0.0 and are refused since 3.3.0-1 (the error says that `linters()` is expected to be a function of class `<linter>`)
|a `.lintr` with `camel_case_linter`, `snake_case_linter` or `multiple_dots_linter`, or with `closed_curly_linter` or `open_curly_linter` |`+object_name_linter(styles = ...)+` and `brace_linter()` |the naming linters were removed in lintr 3.0.0; the curly-brace linters were merged into `brace_linter()` in 3.0.0 and removed in 3.3.0-1

|the tidy-up recipe of `source(keep.source = FALSE)` plus `dump()` |`styler::style_file()` |that recipe, in Writing R Extensions, drops comments from functions, as the manual warns
|dot.case object names, which Google's guide used to recommend |snake case in the tidyverse guide; `BigCamelCase` functions in Google's current guide |Google's current guide says that it is moving away from dot.case because of S3 methods
|`=` for assignment, as in most other languages |`+<-+` |the manual for writing packages recommends `+<-+` consistently; `assignment_linter` is a default
|`T` and `F`, `1:length(x)` and `sapply()` in examples |`TRUE` and `FALSE`, `seq_along(x)`, `vapply()` |`T_and_F_symbol_linter` and `seq_linter` are defaults; `sapply()` is on the undesirable list
|double-indented function arguments |single-indent or hanging-indent definitions |lintr 3.4.0 and styler 1.11.0 follow the guide's single-indent rule
|`%>%` as the first token of every pipeline |`+\|>+` |the guide and `pipe_consistency_linter` (default since lintr 3.3.0-1) prefer the native pipe
|`attach(df)` to avoid typing `df$` |`+with(df, ...)+` or `df$col` |`undesirable_function_linter` lists `attach`; Google's guide says not to use it; lintr and `R CMD check` skip the body of `with()` by default
|a bare `+# nolint+` to silence a lint |`+# nolint: name_linter.+` |a bare marker hides every present and future lint on the line
|ignoring `R CMD check` notes about global variables |`utils::globalVariables()`, `.data$col` or `utils::fun()` |the note is a codetools finding that the reader of the code can act on
