The one measurement that does not vary is memory: the bytes a function allocates are the same on every run, so `mem_alloc` columns are printed as they are. The lines edited this way are the ones that contain `+<n>+`, and they are the only edits made to the output. Where a message contains quotation marks, they are the typographic quotes R prints in a UTF-8 locale. A path in an error message is shortened to `+<tmp>+`. == Measure first

The manual Writing R Extensions has a chapter called "Tidying and profiling R code" for code that is worth keeping and sharing, and the advice of its section on profiling is the whole method in two sentences: profile to find the bottlenecks, then consider replacing the slow R code, perhaps with compiled code (https://cran.r-project.org/doc/manuals/r-release/R-exts.html#Profiling-R-code-for-speed[Writing R Extensions: Profiling R code for speed]). The profvis documentation states why: intuition leads people to optimise things that are a small share of the run time, and some of the commonly held beliefs are false (that the `+*apply+` functions are inherently faster than a `for` loop is the example it gives). The arithmetic behind it is Amdahl's law. If a part of the program takes a share \( p \) of the run time and is made \( s \) times faster, the whole program takes the fraction below of its old time.

\[ \frac{T_{\rm new}}{T_{\rm old}} = (1 - p) + \frac{ p }{ s } \]

A loop that takes 10% of the run time (\( p = 0.1 \)) and is made five times faster (\( s = 5 \)) leaves the program at 92% of its old time, an 8% saving, however pleased one is with the five. Measuring first tells which \( p \) is large. The working loop is the same every time: write the clearest correct code, add a test that pins its result, measure it on realistic data, profile to find the part that matters, change that part, check that the result is unchanged, and measure again. The remedies in the second half of this page are all things to try at the fourth step, never first.

The tools differ in the question they answer, and a measurement session usually uses three of them in turn.

[cols="2,3,3,2",options="header"]
|===
|Tool |Question it answers |What it costs and returns |Package
|`system.time(expr)` |How long did this one evaluation take? |Almost nothing. One `proc_time` of user, system and elapsed seconds. |base R
|`+bench::mark(...)+` |Which of these equivalent expressions is faster, and how much memory does each allocate? |Runs each expression many times; a tibble with min, median, `itr/sec`, `mem_alloc`, GC counts. |bench
|`+microbenchmark(...)+` |Which of these tiny expressions is faster? |Runs each expression `times` times with a nanosecond clock; a data frame of raw timings. |microbenchmark (community)

|`Rprofmem()`, `tracemem()`, `gc()` |Where is memory allocated and copied? |See xref:programming-languages/r/memory-and-copy-semantics.adoc[Memory and Copy Semantics]. |base R
|===

== Timing code

=== system.time and proc.time

`system.time(expr)` calls `proc.time()`, evaluates `expr`, calls `proc.time()` again and returns the difference. The result is an object of class `proc_time`: a numeric vector of length five holding the user and system CPU time of the R process (`user.self`, `sys.self`), the elapsed ("real", wall-clock) time (`elapsed`), and the user and system time of child processes that R has waited for (`user.child`, `sys.child`). Its `print` method folds the child times into the process times and shows three numbers, called `user`, `system` and `elapsed`. The help page defines the first two as the CPU time charged to the process for executing user instructions and for work done by the system on its behalf, and says that child times are not available on Windows and are `NA` there. The clock resolution is system specific: on Unix-alikes times are rounded down to milliseconds, and on Windows they are typically available to 10 ms (https://search.r-project.org/R/refmans/base/html/proc.time.html[R documentation: proc.time]). Two consequences follow. Anything shorter than a few milliseconds cannot be timed once with `system.time()`, and `elapsed` can be much smaller than `user` when a multi-threaded BLAS or other library keeps several cores busy at once.

The difference between CPU time and elapsed time is the first thing to understand about any timing. `Sys.sleep()` waits without computing: it costs elapsed time and no CPU time. A computation costs both. The script below shows the structure of the result, the sleeping against the computing, that the expression runs in the calling environment (so an assignment inside `system.time()` is visible afterwards), and the `gcFirst` argument, whose default `TRUE` runs a garbage collection just before the evaluation so that its cost is not charged to the expression that happens to trigger it.

[source,r]
----
# system.time() returns an object of class "proc_time" with five numbers.
set.seed(1)
st <- system.time(sort(runif(2e6)))
class(st)
#> [1] "proc_time"
names(st)
#> [1] "user.self"  "sys.self"   "elapsed"    "user.child" "sys.child"
length(unclass(st))
#> [1] 5

# print() combines the child times with the process times and shows three.
st
#>    user  system elapsed
#>     <n>     <n>     <n>

# Waiting costs elapsed time but no CPU time.
sleeping <- system.time(Sys.sleep(0.25))
sleeping[["elapsed"]] >= 0.25
#> [1] TRUE
sleeping[["user.self"]] < sleeping[["elapsed"]]
#> [1] TRUE

# Computing costs both.
busy <- system.time(for (i in seq_len(3e6)) i)
busy[["user.self"]] > 0
#> [1] TRUE

# The expression runs in the calling environment, so an assignment stays.
system.time(total <- sum(sort(runif(2e6))))
#>    user  system elapsed
#>     <n>     <n>     <n>
total > 0
#> [1] TRUE

# proc.time() is the clock behind it; subtracting two readings is the same.
start <- proc.time()
invisible(sort(runif(2e6)))
spent <- proc.time() - start
class(spent)
#> [1] "proc_time"
spent[["elapsed"]] >= 0
#> [1] TRUE

# Timing without the garbage collection that normally precedes it.
st2 <- system.time(sort(runif(2e6)), gcFirst = FALSE)
inherits(st2, "proc_time")
#> [1] TRUE
----

Source: https://search.r-project.org/R/refmans/base/html/system.time.html[R documentation: system.time]

If the expression fails, `system.time()` still reports how far it got, in a message that starts with `Timing stopped at:` and gives the same three numbers (see the section on common errors below). It is a good tool for a first look and for a long job, because it adds no overhead and no dependency. It is a poor tool for comparing two fast expressions, which is the reason for the next two sections.

=== One measurement is not enough

A single timing is one sample from a noisy process. The computer is doing other things, the CPU changes its clock speed, the memory caches are warm or cold, the garbage collector runs when it happens to, and the first time anything is used it can cost more than later: a package namespace is loaded, a function is byte-compiled by the JIT (a small closure on its second call, a closure with a loop on its first; see the section on the compiler), a file is read from disk instead of the cache. The remedy is the usual one in measurement: repeat, and report a statistic that does not move with the outliers, the minimum or the median rather than the mean. The script below repeats a computation ten times and shows that the numbers differ, shows that the first load of a package costs far more than the second, and times the parts of a computation separately, because the total of a section of a script hides which of its lines is slow.

[source,r]
----
# One timing is one sample from a noisy process: repeat it and look at the
# spread.
set.seed(42)
work <- function() sort(runif(5e5))
elapsed <- replicate(10, system.time(work())[["elapsed"]])
length(elapsed)
#> [1] 10
max(elapsed) > min(elapsed)
#> [1] TRUE

# The first use of something can cost far more than the later ones: here the
# first call loads and attaches the namespace of a package, the second finds
# it already loaded.
first <- system.time(loadNamespace("data.table"))[["elapsed"]]
second <- system.time(loadNamespace("data.table"))[["elapsed"]]
first > 10 * second
#> [1] TRUE

# Timing a whole section hides which part is slow: time the parts.
parts <- c(
  generate = system.time(v <- runif(2e6))[["elapsed"]],
  sort = system.time(s <- sort(v))[["elapsed"]],
  cumulate = system.time(cs <- cumsum(s))[["elapsed"]]
)
names(parts)
#> [1] "generate" "sort"     "cumulate"
parts[["sort"]] > parts[["cumulate"]]
#> [1] TRUE
----

Source: https://search.r-project.org/R/refmans/base/html/system.time.html[R documentation: system.time]

Writing the loop by hand (`+for (i in 1:100) system.time(...)+` and averaging) is what the next two tools automate, with the repeats, the warm-up, the choice of statistic, the check that the expressions agree, and, in bench, the memory.

=== bench::mark

`bench::mark()` is the benchmarking function of the bench package (version 1.1.4 here; https://bench.r-lib.org/reference/mark.html[bench package documentation: mark]). It takes any number of expressions, named or not, evaluates each at least twice, once to measure the memory allocation and store the result, and then as many times as needed to fill `min_time` seconds, and returns a tibble with one row per expression. Its arguments, with their defaults, are these.

[cols="2,2,5",options="header"]
|===
|Argument |Default |Meaning
|`+...+` |none |The expressions to compare. A name becomes the `expression` column; without one the deparsed expression is used.
|`min_time` |`0.5` |The minimum number of seconds to keep running each expression. `Inf` runs `max_iterations` times instead.
|`iterations` |`NULL` |If given, run each expression exactly this many times, overriding `min_iterations` and `max_iterations`.
|`min_iterations`, `max_iterations` |`1`, `10000` |Lower and upper bound on the number of timed runs.
|`check` |`TRUE` |Compare the results with `all.equal()`; `FALSE` skips the check and does not store the results; a function of two arguments is called on each pair of results to decide whether they agree.
|`memory` |`capabilities("profmem")` |Track allocations with `utils::Rprofmem()`. Memory allocated outside the R heap (`malloc()` or `new` in compiled code) is not counted.
|`filter_gc` |`TRUE` |Drop the iterations that contained a garbage collection before summarising. If every iteration had one, the filter is disabled, with a warning.
|`relative` |`FALSE` |Divide every summary column by the smallest, instead of reporting absolute values.
|`time_unit` |`NULL` |Report times in one unit (`"ns"`, `"us"`, `"ms"`, `"s"` and so on) instead of choosing a readable one per value.
|`env` |`parent.frame()` |The environment in which the expressions are evaluated.
|===

Source: https://bench.r-lib.org/reference/mark.html[bench package documentation: mark]

The columns of the result are `expression` (class `bench_expr`), `min` and `median` (`bench_time`), `itr/sec` (iterations per second), `mem_alloc` (`bench_bytes`), `gc/sec`, `n_itr` (the number of timed iterations after GC filtering), `n_gc` (the garbage collections over all iterations, a pseudo-measure of the pressure on the collector), `total_time`, and the list columns `result`, `memory`, `time` (the raw `bench_time` vector of each run) and `gc`. The classes print readably (`1.2ms`, `7.63MB`) and are numeric underneath. The `check` argument is the feature that matters most for correctness: an optimisation that returns a different answer is a bug, and `mark()` stops with an error if the expressions disagree. The script below is the comparison of the previous section made properly: the days a loan is overdue, for 120000 loans, computed by a preallocated loop and by vectorised arithmetic. The relative column is rounded to the nearest power of ten because the exact ratio changes from run to run (it was between 1000 and 2000 in the runs that were made), and the script passes `filter_gc = FALSE` to `mark()` and to `summary()` because the loop allocates enough small objects to collect garbage in every iteration, which would otherwise make the function print a warning.

[source,r]
----
source("scenario.R")

# The shelf loans repeated 2000 times: 120000 rows.
loan_date <- rep(loans$loan_date, 2000L)
return_date <- rep(loans$return_date, 2000L)

late_loop <- function(loan_date, return_date, today, allowed) {
  out <- integer(length(loan_date))
  for (i in seq_along(loan_date)) {
    end <- return_date[[i]]
    if (is.na(end)) {
      end <- today
    }
    out[[i]] <- max(0L, as.integer(end - loan_date[[i]]) - allowed)
  }
  out
}

late_vector <- function(loan_date, return_date, today, allowed) {
  end <- return_date
  end[is.na(end)] <- today
  pmax(0L, as.integer(end - loan_date) - allowed)
}

b <- bench::mark(
  loop = late_loop(loan_date, return_date, shelf_today, loan_days),
  vector = late_vector(loan_date, return_date, shelf_today, loan_days),
  min_iterations = 10,
  filter_gc = FALSE
)
class(b)
#> [1] "bench_mark" "tbl_df"     "tbl"        "data.frame"
names(b)
#>  [1] "expression" "min"        "median"     "itr/sec"    "mem_alloc"
#>  [6] "gc/sec"     "n_itr"      "n_gc"       "total_time" "result"
#> [11] "memory"     "time"       "gc"

# Times and memory have their own classes; the raw timings are kept per run.
vapply(b[c("min", "median", "mem_alloc")], \(x) class(x)[[1L]], character(1))
#>           min        median     mem_alloc
#>  "bench_time"  "bench_time" "bench_bytes"
b$n_itr >= 10
#> [1] TRUE TRUE
lengths(b$time) == b$n_itr
#> [1] TRUE TRUE

# By default mark() checks that the expressions return the same value.
identical(b$result[[1L]], b$result[[2L]])
#> [1] TRUE

# Absolute times depend on the machine; ratios carry over better. Even the
# ratios change from run to run, so round them to the nearest power of ten.
power_of_ten <- \(x) 10^round(log10(x))
rel <- summary(b, relative = TRUE, filter_gc = FALSE)
rel$median <- power_of_ten(rel$median)
rel[c("expression", "median")]
#> # A tibble: 2 × 2
#>   expression median
#>   <bch:expr>  <dbl>
#> 1 loop         1000
#> 2 vector          1
----

Source: https://bench.r-lib.org/reference/summary.bench_mark.html[bench package documentation: summary.bench_mark]

`bench::press()` runs `mark()` across a grid of parameters and binds the results into one tibble, which is how one finds out how a cost grows (https://bench.r-lib.org/reference/press.html[bench package documentation: press]). Named arguments define the grid, and the one unnamed expression, usually a braced block, runs once per row of the grid with the parameters available as variables. The script below grows a vector with `c()` and fills a preallocated one, for three sizes, and prints the memory column. That column shows the difference with no noise: doubling the length roughly quadruples the memory of the growing version, because every iteration allocates a new vector of the size so far, and only doubles the memory of the preallocated one. The function `bench::system_time()` is the single-shot counterpart, a `system.time()` that returns `bench_time` values called `process` (CPU) and `real` (elapsed).

[source,r]
----
# Growing a vector with c() against preallocating it, for three sizes.
grow <- function(n) {
  out <- c()
  for (i in seq_len(n)) {
    out <- c(out, i)
  }
  out
}

prealloc <- function(n) {
  out <- integer(n)
  for (i in seq_len(n)) {
    out[[i]] <- i
  }
  out
}

# Run both once or twice first so that the byte-code compiler's own
# allocations are not counted in the first measurement.
for (warm in 1:3) {
  grow(10L)
  prealloc(10L)
}

res <- bench::press(
  n = c(1000L, 2000L, 4000L),
  {
    bench::mark(
      grow = grow(n),
      prealloc = prealloc(n),
      min_iterations = 5,
      filter_gc = FALSE
    )
  },
  .quiet = TRUE
)
names(res)[1:2]
#> [1] "expression" "n"
res[c("expression", "n", "mem_alloc")]
#> # A tibble: 6 × 3
#>   expression     n mem_alloc
#>   <bch:expr> <int> <bch:byt>
#> 1 grow        1000    1.95MB
#> 2 prealloc    1000    3.95KB
#> 3 grow        2000    7.72MB
#> 4 prealloc    2000    7.86KB
#> 5 grow        4000   30.71MB
#> 6 prealloc    4000   15.67KB

# The memory column is the clearest signal: it is not noisy like a time.
# Doubling n quadruples the memory of the growing version (roughly) and
# doubles that of the preallocated one.
mem <- as.numeric(res$mem_alloc)
name <- as.character(res$expression)
mem[name == "grow" & res$n == 4000L] / mem[name == "grow" & res$n == 2000L]
#> [1] 3.975697
mem[name == "prealloc" & res$n == 4000L] /
  mem[name == "prealloc" & res$n == 2000L]
#> [1] 1.994036

# bench::system_time() times one evaluation, like system.time(), but returns
# the process (CPU) time and the real (elapsed) time as bench_time values.
tm <- bench::system_time(sort(runif(1e6)))
names(tm)
#> [1] "process" "real"
class(tm)
#> [1] "bench_time" "numeric"
----

Source: https://bench.r-lib.org/reference/press.html[bench package documentation: press]

The script warms both functions up before the first measurement. The first call of a function allocates memory for its byte code, which `mark()` would otherwise count in the memory of the first expression it measures (without the warm-up the preallocated version at 1000 elements reported a larger figure than at 2000). With a ggplot2 installation, `ggplot2::autoplot()` of a `bench_mark` result draws the distribution of the timings of each expression; that is mentioned and not run here.

=== microbenchmark

The microbenchmark package (version 1.5.0, whose help page names Olaf Mersmann as its author, on CRAN; https://cran.r-project.org/package=microbenchmark[microbenchmark on CRAN]) is a community package that predates bench and is still widely used in older answers and tutorials. `+microbenchmark(..., times = 100L)+` evaluates each expression `times` times, in an order chosen by `control$order` (`"random"`, the default, `"inorder"` or `"block"`), after `control$warmup` warm-up iterations (default 2), using the nanosecond timer of the operating system and subtracting the estimated cost of the timing calls themselves. It returns a data frame of class `microbenchmark` with one row per evaluation, whose `summary()` has the columns `expr`, `min`, `lq`, `mean`, `median`, `uq`, `max` and `neval`, and whose `unit` argument (`"relative"` among others) chooses the unit. Its differences from bench are worth knowing. The `check` argument defaults to `NULL`, which skips the check, and takes a function or one of the strings `"equal"`, `"equivalent"` and `"identical"`. There is no memory column. And its own help page says it is meant for micro-benchmarks of small pieces of code, and recommends the R profiler for hot spots in larger chunks. The script below compares `vapply()` over 100000 numbers with the vectorised expression, shows the check refusing expressions that disagree, and uses the `control` list. Its relative median is printed rounded down to a power of ten (the ratio was about 350).

[source,r]
----
library(microbenchmark)

set.seed(7)
x <- runif(1e5)

mb <- microbenchmark(
  vapply = vapply(x, \(v) v * 2 + 1, numeric(1)),
  vector = x * 2 + 1,
  times = 30L,
  check = "equal"
)
class(mb)
#> [1] "microbenchmark" "data.frame"
names(summary(mb))
#> [1] "expr"   "min"    "lq"     "mean"   "median" "uq"     "max"    "neval"

# unit = "relative" divides every statistic by the smallest median. The ratio
# changes from run to run, so print it rounded down to a power of ten.
rel <- summary(mb, unit = "relative")
rel$median <- 10^floor(log10(rel$median))
rel[c("expr", "median", "neval")]
#>     expr median neval
#> 1 vapply    100    30
#> 2 vector      1    30

# check = "equal" refuses to time expressions that disagree.
tryCatch(
  microbenchmark(sum(x), mean(x), times = 5L, check = "equal"),
  error = \(e) conditionMessage(e)
)
#> [1] "Input expressions are not equivalent."

# The control list: how many warm-up runs, and in which order to run.
mb2 <- microbenchmark(
  cumsum = cumsum(x),
  rev = rev(x),
  times = 20L,
  control = list(warmup = 5L, order = "random")
)
nrow(mb2)
#> [1] 40
levels(mb2$expr)
#> [1] "cumsum" "rev"
----

Source: https://cran.r-project.org/package=microbenchmark[microbenchmark on CRAN]

The help page also says that a timing which turns out negative after the overhead is subtracted is replaced by zero with a warning, and that if every evaluation does so, the function stops with an error: the symptom of an expression too fast to measure, such as `NULL`. The data.table documentation, in its guide to benchmarking, adds a caution that applies to every tool in this section: repeating a benchmark hundreds of times is the right design for atomic calculations, but it is not a good picture of data-processing tasks, where a handful of runs on data large enough to take seconds is more representative, because call overhead and garbage collection dominate the tiny ones (https://rdatatable.gitlab.io/data.table/articles/datatable-benchmarking.html[data.table package documentation: Benchmarking data.table]).

=== Choosing and reading a benchmark

The guidelines that follow are the ones that remove most wrong conclusions.

* Compare expressions that compute the same thing, and let the tool check it: `check = TRUE` in `bench::mark()` (with a tolerance function such as `\(a, b) isTRUE(all.equal(a, b))` for floating-point results), `check = "equal"` in `microbenchmark()`.
* Use data of realistic size. A trick that wins on 100 elements can lose on 100000, and the other way round; `bench::press()` shows the trend.
* Look at the median or the minimum, not the mean, and at the memory as well as the time. Memory is reproducible; time is not.
* Put the setup outside the timed expression: build the data once, before the call. Timing `+x <- runif(1e6); sort(x)+` times the random numbers too.
* Time the code the way it will be used: as a call of a function with its arguments, not as loose statements that read globals.
* Warm up. The first call pays for byte-compilation and lazy loading; `bench::mark()` and `microbenchmark()` run more than once, and a script that times a single call should call the function once before.
* Do not benchmark what the optimiser can skip. An expression whose value is unused may do less work than it would in real use; assign or return the value.
* Say what the machine was. The same comparison on another computer, another BLAS or with other programs running will give different ratios. A claim such as "ten times faster" needs "on this data, on this machine".

== Profiling

Timing says how long; profiling says where. R's profiler is a sampling profiler. `Rprof()` starts it, and every `interval` seconds it writes the current call stack, the list of the R functions that are being evaluated, one above the other, to a file. `summaryRprof()` reads the file and counts how many samples each function was on the stack. The approach is cheap and needs no change to the code, but it is statistical: a function that runs for less than one interval can be missed entirely, the result changes from run to run, and it is only as precise as the number of samples.

=== Rprof and summaryRprof

The usage of `Rprof()` is `Rprof(filename = "Rprof.out", append = FALSE, interval = 0.02, memory.profiling = FALSE, gc.profiling = FALSE, line.profiling = FALSE, filter.callframes = FALSE, numfiles = 100L, bufsize = 10000L, event = c("default", "cpu", "elapsed"))`. Enabling profiling disables any profiling that was running, so `Rprof(NULL)` (or `""`) stops it; calling `Rprof()` again with `append = TRUE` adds to the same file (https://search.r-project.org/R/refmans/utils/html/Rprof.html[R documentation: Rprof]).

Two details of what is recorded matter when reading a profile. Only functions that put a context on the call stack appear: some primitives, those of type `"special"`, do not, which is why `+<-+`, `pass:c[[]` and `$` never show up as time even when they take much of it (their cost is charged to the function that called them, and to `+<GC>+` when `gc.profiling` is on and they allocate). And since the profile is of R code, the time spent in compiled code that R calls, `.Call()` or `.Fortran()` for instance, is charged to the R function that made the call; the profiler cannot look inside it. The section on profiling compiled code below says what to use for that.

`summaryRprof()` returns a list: `by.self`, a data frame sorted by self time, `by.total`, sorted by total time, `sample.interval` and `sampling.time`. Both data frames have the columns `self.time`, `self.pct`, `total.time` and `total.pct`, with times in seconds and percentages of the total sampled time. Self time is the time when the function was the last one on the stack, the one doing the work. Total time is the time when it was anywhere on the stack, so it includes everything it called. A function with a high total and a low self time is a router, calling something that is slow; a function with a high self time is itself the work. The row names are the function names inside double quotes (the quotes are part of the name). The script below profiles the ISBN check from the scenario code, `is_valid_isbn13()`, over 600000 strings, and prints the structure of the result and the two tables. The seconds and percentages are replaced with `+<n>+`; the function names and their order are what was printed, with one concession: `by.self` is printed for four rows picked by name, because the first few rows of that table are near ties whose order changes from run to run.

The file that `Rprof()` writes is plain text, and knowing its shape explains several of the behaviours above. The first line is `sample.interval=` followed by the interval in microseconds, and every following line is one sample, the call stack with the innermost call first, each function name in double quotes (those are the quotes that appear in the row names of the summary tables). `append = TRUE` adds new samples to an existing file, which is how a profile of several separate stretches of a program is collected into one summary: the sampling time of the combined file is larger than that of the first session alone. Two arguments change what the samples contain. `gc.profiling = TRUE` records, for each sample, whether the garbage collector was running, and the summary then has a `+<GC>+` row. A function that allocates all the time, like the growing vector of the earlier sections, spends a visible share of its time there, and the row is the profile's way of showing allocation as time; without the argument the collector's time is charged to whatever function it interrupted. `filter.callframes = TRUE` (R 4.0.0) removes the frames that lazy evaluation and `eval()` put between a caller and the function that finally evaluates its argument. The help page gives `try(EXPR)` as the example: its call tree has `tryCatch()`, `tryCatchList()`, `tryCatchOne()` and `doTryCatch()` between `try()` and `EXPR`, and the filter drops those four. The two scripts show each: with `gc.profiling` the `+<GC>+` row appears and without it does not, and with the filter `tryCatchList` has disappeared from a profile of a function called inside `try()` while the function itself remains.

  out <- c()

  s <- summaryRprof(prof)
  unlink(prof)

Reading a profile is a matter of asking the same three questions each time.

* Which function has the largest total time that is not just the entry point? That is the branch of the program to look into.
* Within it, which function has the largest self time? That is where the work is done, and what to change.
* Is the work in R code or in compiled code? R functions such as `strsplit()` and `gsub()` are mostly compiled code behind a short R wrapper; a large self time there means the argument is large or the call is repeated, and the remedy is to call it fewer times on more data, not to rewrite it.

Three cautions apply. Profiling has a small cost of its own, and the output file can grow large for a long run at the default interval. A short profile is unreliable: a run of a few hundred milliseconds has only a few dozen samples, so repeat the work (the scripts here loop over a few hundred thousand elements for that reason) or lengthen the data. And the garbage collector runs from time to time and its time is charged to whichever function was running when it started; Writing R Extensions suggests comparing a profile taken straight after a `gc()` with one taken without (https://cran.r-project.org/doc/manuals/r-release/R-exts.html#Profiling-R-code-for-speed[Writing R Extensions: Profiling R code for speed]). R-admin adds a fourth, for installations that use a multi-threaded BLAS: profiling uses the `SIGPROF` signal, which may cause problems with threaded libraries, and the advice is to disable profiling when one is used (https://cran.r-project.org/doc/manuals/r-release/R-admin.html#Linear-algebra[R Installation and Administration: Linear algebra]).

=== Line profiling

With `line.profiling = TRUE` the profiler also records the source line that is being executed, and `summaryRprof(lines = "show")` adds a `by.line` table, sorted by source location, whose row names are `file#line`. `lines = "both"` mixes function names and locations in one table, and `lines = "hide"` (the default) shows only function names; `basenames` is the number of components of the path to display. The condition is that the code was parsed with source references: the help page names `keep.source = TRUE` in `source()` and `KeepSource: yes` in a package's `DESCRIPTION` as ways to get them (https://search.r-project.org/R/refmans/utils/html/summaryRprof.html[R documentation: summaryRprof]). This matters because `Rscript` does not keep them. The option `keep.source` is `FALSE` unless the session is interactive, so a function defined in a script has no source reference and a line profile of it is empty; the next script shows the check, and the one after it works around it by writing the function to a file and sourcing it with `keep.source = TRUE`.

=== CPU time or elapsed time: Rprof(event =) (R 4.4.0)

Before R 4.4.0 the profiler measured one thing: CPU time on Unix-alikes, elapsed time on Windows. R 4.4.0 added the `event` argument and, with it, profiling by elapsed (real, wall-clock) time on Unix (R NEWS: "Rprof() gains an event argument and support for elapsed (real) time profiling on Unix", https://cran.r-project.org/doc/manuals/r-release/NEWS.html[R NEWS: Changes in R 4.4.0]). The help page explains the difference. With `"cpu"`, the default on Unix-alikes and typically the preferred event for finding performance bottlenecks, the profiler counts CPU time of the R process, so it excludes the time R spends waiting for input or for processes started by `system()`; it can go slower than the elapsed clock when the process often waits, and faster when concurrent threads (OpenMP, a threaded BLAS) compute. With `"elapsed"`, the default and the only supported event on Windows, it counts the time the process is running and executing an R command, including a `readline()` that waits for input. The help page also says that elapsed profiling on Unix is new and considered experimental: to avoid missing a sample, R tries to use the real-time FIFO scheduling policy with the maximum priority for the internal thread that takes each sample, and if that is not allowed it falls back to the maximum priority of the current policy, which matters only when profiling a machine under high load. `"default"` is the platform's choice.

The choice changes what the profile says about code that waits, and the script below is built to show it. `wait_then_work()` sleeps for a second and then sorts a million random numbers. `Sys.sleep()` stands in for a slow download or a database query. The CPU profile never sees the sleep, only the sorting (a fraction of a second of CPU in a function that takes over a second), and the elapsed profile shows `Sys.sleep()` as nine tenths of the time. For a program that is slow because it waits on a network, a disk or another process, the CPU profile is blind to the cause and the elapsed profile is the right one. For a computation, the CPU profile is the cleaner. The script ends with the two errors the arguments can raise, with their real messages: an unknown event is an error from `match.arg()`, and an interval below the platform minimum is a warning that says what was used instead.

[source,r]
----
# A function that mostly waits: Sys.sleep() stands in for a slow download or
# a database query. It uses almost no CPU.
wait_then_work <- function() {
  Sys.sleep(1)
  sum(sort(runif(1e6)))
}

profile_with <- function(event) {
  prof <- tempfile(fileext = ".out")
  Rprof(prof, interval = 0.01, event = event)
  invisible(wait_then_work())
  Rprof(NULL)
  s <- summaryRprof(prof)
  unlink(prof)
  s
}

#> [1] TRUE

#>                  total.time total.pct self.time self.pct

=== Memory: three tools in brief

Memory use is part of speed, because allocation, copying and garbage collection are time, and the subject has its own page: xref:programming-languages/r/memory-and-copy-semantics.adoc[Memory and Copy Semantics]. In brief, there are three profiling tools. `Rprof(memory.profiling = TRUE)` writes the total allocation in small vectors, large vectors and cons cells at each sample and the number of calls to the internal `duplicate` function that copies objects, and `summaryRprof(memory = "both")` adds the change in memory to the timing tables; its caveat is that memory is attributed to the function running at the end of the sampling interval, and a collection can make the memory fall (https://cran.r-project.org/doc/manuals/r-release/R-exts.html#Memory-statistics-from-Rprof[Writing R Extensions: Memory statistics from Rprof]). `Rprofmem()` is a non-sampling profiler that writes a stack trace each time a large vector is allocated (above a threshold given in bytes) or a new page of the R heap is allocated; it is what `bench::mark()` uses for its `mem_alloc` column (https://cran.r-project.org/doc/manuals/r-release/R-exts.html#Tracking-memory-allocations[Writing R Extensions: Tracking memory allocations]). `tracemem()` marks one object and prints a message whenever it is copied (https://cran.r-project.org/doc/manuals/r-release/R-exts.html#Tracing-copies-of-an-object[Writing R Extensions: Tracing copies of an object]), and `gc()` reports the memory in use and triggers a collection (https://search.r-project.org/R/refmans/base/html/gc.html[R documentation: gc]). The last two need R to have been built with memory profiling, which `capabilities("profmem")` (shown in the script above) answers. Writing R Extensions notes that memory profiling is difficult mainly because of garbage collection: allocation happens at well-defined times and release at whenever the collector runs.

=== profvis

profvis (version 0.4.0 here, https://profvis.r-lib.org/[profvis package documentation]) draws the data of `Rprof()` as an interactive page. `profvis(expr)` runs the expression with line profiling and memory profiling on, and returns an htmlwidget of class `profvis` that RStudio and Positron show in a viewer and that `htmlwidgets::saveWidget()` writes to a self-contained HTML file. The page has the source code on top, with the time and memory attributed to each line, and a flame graph below it, where the horizontal axis is time and the vertical axis is the call stack, so the bottom block is the outermost call and every block above it is a function called by the one below; the width of a block is the time spent in it. A Data tab gives the same information as a table that expands the call stack. The documentation lists what the graph cannot show: some internal functions do not appear (`+<-+`, `pass:c[[]` and `$` among them, because they are not on the call stack, though their side effects show up as `+<GC>+` blocks), calls through an anonymous function appear as `+<Anonymous>+` unless the function is saved in a variable, white blocks are code for which profvis does not have the source (base R and packages), and nothing in C, C{pp} or Fortran is visible, only the R function that called it (https://profvis.r-lib.org/articles/profvis.html[profvis package documentation: Getting started with profvis], https://profvis.r-lib.org/articles/faq.html[profvis package documentation: Frequently asked questions]). Memory figures on a line are the allocation between the previous sample and this one, which may have happened on an earlier line.

The arguments of `profvis()` that matter are `expr`, the expression to profile (turned into the body of a function, so variables created inside it are not visible outside), `interval` (default 0.01, and values below 0.005 will probably not give accurate timings), `prof_output` (a file or directory in which to keep the `Rprof()` data; the default is a temporary file removed on exit), `prof_input` (the path to an `Rprof()` data file produced elsewhere, in which case there is no `expr`), `timing` (the event, described above), `simplify` (the equivalent of `filter.callframes`), `rerun` (run again until a sample is recorded, for expressions that return before the first sample), `torture` (garbage-collect after every so many allocations, which makes memory figures more exact) and `split` (`"h"` or `"v"`, the orientation of the divider). A terminal has no viewer, so the script below does what a script, a test or a CI job can do: it creates the widget, checks its class, saves it to a temporary HTML file, and builds a second one from an `Rprof()` file with `prof_input`. The flame graph itself is an interactive page and is described, not shown. For the first widget, which profiles the loop of the benchmarking section for 36000 loans, the data behind it has `late_loop` at the bottom of the stack, `-.Date` above it with `difftime` and `as.POSIXct.Date` above that, and `pass:c[[[.Date]` with `.Date` as the other tower: the Date arithmetic inside the loop is what the graph is made of. Under `Rscript` the code has no source references (`keep.source` is `FALSE`, as the script above showed), so the flame graph has function names only and the code panel has no per-line figures; start R interactively, or run `options(keep.source = TRUE)` earlier in the script, which was checked to bring them back, to get them.

loan_date <- rep(loans$loan_date, 600L)

=== Profiling code you cannot see

R's profiler stops at the boundary of compiled code, so a function whose self time is large and whose work is in C, C{pp} or Fortran (a `.Call()` into a package, a BLAS routine) needs a different tool. Writing R Extensions devotes a section to it, with the hints "gleaned from various R users" for Linux (`perf`, `oprofile` and `operf`, `sprof` for a shared object, and Google's `gperftools`), macOS and Windows, with the warning that this is highly system specific and that the chapter is based on reports that may not be current (https://cran.r-project.org/doc/manuals/r-release/R-exts.html#Profiling-compiled-code[Writing R Extensions: Profiling compiled code]). The tools work best when R and the packages were built with debugging symbols. For the common case, a BLAS call, `perf record R -f script.R` followed by `perf report --sort=dso` shows how the time divides between R itself, the C library, the BLAS shared object and the packages' shared objects, which is how one finds out that the time was spent in `libRblas` or `libopenblas` and not in the interpreter.

== Making code faster

Profiling has named a function and a line. What follows is the list of remedies in the order that usually pays off: do less work (a better algorithm or a lookup in place of a search), use vectorised operations, avoid growing or copying, use the right container and the right function, and only then change the machinery under the code (the compiler, the BLAS, a different package, compiled code), or spread the work over cores (xref:programming-languages/r/parallel-and-asynchronous-computing.adoc[Parallel and Asynchronous Computing]). Each remedy below is shown with a measurement, on the shelf data repeated to a size at which the difference is visible.

=== Vectorise

A vectorised function runs its loop in compiled code; a loop in R pays the interpreter's cost for every element. The effect is the largest single win in everyday R, and xref:programming-languages/r/vectorisation-and-iteration.adoc[Vectorisation and Iteration] explains the functions that replace the common loops. The measurement here is of a kind that is easy to miss: a loop that looks up each loan's book in a table. The loop calls `pass:c[which(keys == isbn[[i\]\])]` for every loan, which scans the 16 keys every time and allocates a logical vector each time; `pass:c[titles[match(isbn, keys)\]]` builds a hash table of the keys once and looks every loan up in it. The difference is about two orders of magnitude for 60000 loans. The relative column is printed with one significant digit (the ratio was between 100 and 125 in the runs that were made).

[source,r]
----
source("scenario.R")

# Look up the title of every loan by ISBN: 60000 loans, 16 books.
keys <- normalise_isbn(books$isbn)

Vectorising is not always possible. A loop whose step depends on the result of the previous step, like the running stock of a shelf below, has no vectorised form; the sections on the compiler and on C{pp} are for it. Even then the vectorised parts of the loop body are worth keeping out of the loop: compute everything that does not depend on the previous step in one pass before the loop.

=== Preallocate, and do not grow

Growing a result one element at a time (`+out <- c(out, value)+`) allocates a new vector and copies the old one on every iteration, so the total work grows with the square of the length. The section on `bench::press()` showed it in memory (doubling the length quadrupled the allocation of the growing version). xref:programming-languages/r/vectorisation-and-iteration.adoc[Vectorisation and Iteration] covers the idiom in the section called "Preallocation and the growing-vector trap" and the assignment-beyond-the-end behaviour that R 3.4.0 added; the rule is `numeric(n)`, `integer(n)`, `character(n)`, `logical(n)` or `vector("list", n)` before the loop, `pass:c[x[[i\]\] <- value]` inside it, and, when the length is unknown, a list of the pieces combined once at the end.

The same applies to data frames and is much more costly: `rbind(df, row)` inside a loop copies the whole data frame and checks the columns every time. The script below builds a 2000-row data frame three ways: `rbind()` in a loop, a list of one-row data frames combined by one `do.call(rbind, parts)`, and the columns built as vectors and wrapped in `data.frame()` once. The time ratios are printed rounded down to a power of ten, and the memory ratios to the nearest. The loop allocates a thousand times the memory of the vector version, and the list version about ten times.

[source,r]
----
# Three ways to build a data frame of 2000 rows.
rows_loop <- function(n) {
  df <- data.frame(loan_id = character(), days = integer())
  for (i in seq_len(n)) {
    row <- data.frame(loan_id = sprintf("L%04d", i), days = i %% 40L)
    df <- rbind(df, row)
  }
  df
}

rows_list <- function(n) {
  parts <- vector("list", n)
  for (i in seq_len(n)) {
    parts[[i]] <- data.frame(loan_id = sprintf("L%04d", i), days = i %% 40L)
  }
  do.call(rbind, parts)
}

rows_vector <- function(n) {
  data.frame(loan_id = sprintf("L%04d", seq_len(n)), days = seq_len(n) %% 40L)
}

# Warm up so that the compiler's allocations are not in the first measurement.
for (warm in 1:2) {
  rows_loop(5L)
  rows_list(5L)
  rows_vector(5L)
}

b <- bench::mark(
  loop = rows_loop(2000L),
  list = rows_list(2000L),
  vector = rows_vector(2000L),
  min_iterations = 3,
  filter_gc = FALSE
)

# Ratios to the fastest and to the smallest, rounded to the nearest power of
# ten (or down, for the time) because the exact values change between runs.
rel <- summary(b, relative = TRUE, filter_gc = FALSE)
rel$median <- 10^floor(log10(rel$median))
rel$mem_alloc <- 10^round(log10(rel$mem_alloc))
rel[c("expression", "median", "mem_alloc")]
#> # A tibble: 3 × 3
#>   expression median mem_alloc
#>   <bch:expr>  <dbl>     <dbl>

#> 2 list          100        10
#> 3 vector          1         1

=== Avoid copies

R's functions behave as if arguments were copied (call by value), but a copy is made only when an object is modified while something else refers to it; Writing R Extensions explains the design with a package example in which the single line `+x$call <- x$printcall+` copies the whole object `x`, and shows that data frames are slower than matrices and that "this is an example of why" (https://cran.r-project.org/doc/manuals/r-release/R-exts.html#Profiling-R-code-for-memory-use[Writing R Extensions: Profiling R code for memory use]). The consequences for speed are three. Modifying an argument inside a function copies it, however large. Setting one cell of a data frame column in a loop, `pass:c[df$x[i\] <- value]`, goes through `+$<-.data.frame+` and copies the column, and more, at every iteration, whereas the same assignment on a plain vector is done in place. And a function that takes a large object only to read a small piece of it costs nothing for the object. The script below measures the second and the first. For 10000 cells the data-frame version allocates ten thousand times the memory of the vector version, and the function that modifies its million-element argument allocates the 7.63 MB of a copy of it, while the function that only reads it allocates nothing. The remedy for the data frame is to do the loop on vectors and build the data frame once, or to work with a matrix or a list; the remedy for the argument is to make the modification a new, smaller object, or to accept the copy knowingly. xref:programming-languages/r/memory-and-copy-semantics.adoc[Memory and Copy Semantics] is the place for the rules (what counts as "something else refers to it", reference counting since R 4.0.0, and when R can modify in place) and for `tracemem()` to see a copy happen.

[source,r]
----
# Setting one cell of a data frame column inside a loop rebuilds the column
# (and checks the data frame) on every iteration; a plain vector does not.
cells_df <- function(n) {
  df <- data.frame(x = numeric(n))
  for (i in seq_len(n)) {
    df$x[i] <- i
  }
  df
}

cells_vector <- function(n) {
  x <- numeric(n)
  for (i in seq_len(n)) {
    x[[i]] <- i
  }
  data.frame(x = x)
}

# Modifying an argument inside a function copies it; reading it does not.
modify_arg <- function(v) {
  v[[1L]] <- 0
  v
}
read_arg <- function(v) {
  v[[1L]]
}

big <- as.numeric(seq_len(1e6))
for (warm in 1:2) {
  cells_df(10L)
  cells_vector(10L)
  modify_arg(big)
  read_arg(big)
}

b1 <- bench::mark(
  data_frame = cells_df(10000L),
  vector = cells_vector(10000L),
  min_iterations = 3,
  filter_gc = FALSE
)
rel <- summary(b1, relative = TRUE, filter_gc = FALSE)
rel$mem_alloc <- 10^round(log10(rel$mem_alloc))
rel[c("expression", "mem_alloc")]
#> # A tibble: 2 × 2
#>   expression mem_alloc
#>   <bch:expr>     <dbl>
#> 1 data_frame     10000
#> 2 vector             1

b2 <- bench::mark(
  modify = modify_arg(big),
  read = read_arg(big),
  check = FALSE,
  min_iterations = 3,
  filter_gc = FALSE
)
# A million doubles are 8 MB: the modifying version allocates a copy of them.
b2[c("expression", "mem_alloc")]
#> # A tibble: 2 × 2
#>   expression mem_alloc
#>   <bch:expr> <bch:byt>

=== vapply and the apply family

A very common piece of advice is to replace loops by `sapply()` or `lapply()` because they are faster. They are not, by much: the apply functions are loops written in C that call an R function once per element, and the call is the cost. The profvis documentation says the same thing, and gives it as the example of a belief that is not true. The script below applies a small fee function to 120000 loan durations with a preallocated `for` loop, `vapply()`, `sapply()`, `lapply()` plus `unlist()`, and the vectorised `pmax()` form, and prints two comparisons (the four loops are within a factor of three of each other, and the vectorised form is more than ten times faster than the best of them; the factor was a hundred in the runs made) and the memory ratios, which are the same on every run. What the apply functions offer is not speed but clarity and safety, and `vapply()` is the safe one: it declares the type and length of each result, `FUN.VALUE`, and an element that does not conform is an error, not a surprise. `sapply()` guesses: it simplifies the result to a vector, a matrix or a list depending on what the function returns, and on an empty input it returns an empty list whatever the function would have returned. The script after it shows the two errors that `vapply()` raises, with their real messages, and the empty-input case.

[source,r]
----
source("scenario.R")

# Days on loan for 120000 loans, with a small function applied per element.
days <- rep(as.integer(loans$return_date - loans$loan_date), 2000L)
days <- days[!is.na(days)]
fee <- function(d, allowed) max(0, d - allowed) * 0.25

fee_for <- function(d, allowed) {
  out <- numeric(length(d))

    out[[i]] <- fee(d[[i]], allowed)
  }
  out
}

fee_lapply <- function(d, allowed) unlist(lapply(d, fee, allowed = allowed))
fee_vector <- function(d, allowed) pmax(0, d - allowed) * 0.25

=== Matrix algebra

Matrix operations are where R hands its work to the BLAS and LAPACK (see the next section), and the way they are written still matters, because the library is fast only for the operation it is asked to do. Three rules cover most of it. Do not form an inverse that is only going to be multiplied: `solve(a, b)` solves the linear system directly, and `+solve(a) %*% b+` computes the whole inverse first, which is more work and less accurate. Use `crossprod(x)` for `+t(x) %*% x+` and `crossprod(x, y)` for `+t(x) %*% y+`: it does not build the transpose, and for a single argument it computes only half of the symmetric result (https://search.r-project.org/R/refmans/base/html/crossprod.html[R documentation: crossprod]). Prefer a decomposition (`qr()`, `chol()`) when the same matrix is used for several right-hand sides, and keep the work in matrices: a data frame converted to a matrix once is faster to compute on than the data frame, as the section on copies showed. The script below solves the normal equations of a least-squares problem with 5000 rows and 500 columns written three ways, checking that they agree, and prints which is fastest, that the naive form is at least one and a half times slower, and the memory ratios. The crossprod form allocates about a seventeenth of the memory of the naive form, which is the cleanest measure of the difference.

[source,r]
----
set.seed(123)
n <- 5000L
p <- 500L
x <- matrix(rnorm(n * p), nrow = n)
y <- rnorm(n)

# The normal equations for a least-squares fit, written three ways.
naive <- function(x, y) solve(t(x) %*% x) %*% t(x) %*% y
better <- function(x, y) solve(t(x) %*% x, t(x) %*% y)
best <- function(x, y) solve(crossprod(x), crossprod(x, y))
same <- \(a, b) isTRUE(all.equal(a, b))

b <- bench::mark(
  naive = naive(x, y),
  better = better(x, y),
  best = best(x, y),
  check = same,
  min_iterations = 15,
  filter_gc = FALSE
)
rel <- summary(b, relative = TRUE, filter_gc = FALSE)

# The fastest is crossprod() with solve(a, b); the naive form is slower.
exprs <- as.character(rel$expression)
exprs[which.min(rel$median)]
#> [1] "best"
rel$median[exprs == "naive"] > 1.5
#> [1] TRUE

# The memory ratios are the same on every run (to one decimal place).
rel$mem_alloc <- round(rel$mem_alloc, 1)
rel[c("expression", "mem_alloc")]
#> # A tibble: 3 × 2

=== A faster BLAS

R does not implement its own dense linear algebra. The Installation and Administration manual states it at the start of the appendix on linear algebra: the routines make use of BLAS (Basic Linear Algebra Subprograms) and, for most, of LAPACK; the sources contain reference implementations in Fortran, and they can be replaced by external libraries, usually tuned for specific CPUs (https://cran.r-project.org/doc/manuals/r-release/R-admin.html#Linear-algebra[R Installation and Administration: Linear algebra]). `+%*%+`, `crossprod()`, `solve()`, `chol()`, `qr(LAPACK = TRUE)`, `eigen()` and `svd()` end up there, and a tuned BLAS multiplies large matrices many times faster than the reference one, partly through CPU-specific code and partly through threads. It is the one speed-up on this page that needs no change to the program.

The choices, as the manual describes them, are these.

The ways to change the BLAS follow from where it is linked. If R was built with the shared BLAS (`--enable-BLAS-shlib`, the default on all platforms but AIX), every reference goes through `libRblas`, so the library can be swapped without rebuilding R or the packages: by symlinking an external shared BLAS over `libRblas`, or, on Debian-based systems, by building R with `--with-blas` and using `update-alternatives`; the manual points to the Debian wiki page on linear algebra libraries and says that ATLAS, MKL and OpenBLAS alternatives are available (https://cran.r-project.org/doc/manuals/r-release/R-admin.html#Shared-BLAS[R Installation and Administration: Shared BLAS]). Since 2025 this is less free: the BLAS gained routines (`dgemmtr`, `zgemmtr`) that the bundled LAPACK 3.12.1 uses, so a replacement BLAS must contain them (OpenBLAS does from version 0.3.29) or R must be built with `--with-2025blas`, and the NEWS of R 4.5.0 says that 3.12.1 is expected to be the last bundled version, after which external libraries will be required (https://cran.r-project.org/doc/manuals/r-release/NEWS.html[R NEWS: Changes in R 4.5.0]). Binary distributions make the choice for the user: the NEWS of R 4.5.0 says Windows builds use the internal BLAS by default, the manual says some CRAN builds for macOS can be switched to Accelerate, and the Linux image used for this page runs on OpenBLAS.

R can say what it is using. `extSoftVersion()` returns a named character vector whose `BLAS` entry names the library file, `La_library()` returns the file that holds LAPACK and `La_version()` its version, and `sessionInfo()` prints a "Matrix products" line (the `matprod` option), a `BLAS:` line and a `LAPACK:` line with the version (https://search.r-project.org/R/refmans/base/html/extSoftVersion.html[R documentation: extSoftVersion], https://search.r-project.org/R/refmans/base/html/La_library.html[R documentation: La_library], https://search.r-project.org/R/refmans/utils/html/sessionInfo.html[R documentation: sessionInfo]). The values are file paths and machine specific, so the script below asks questions about them (is the entry present, is it empty, does the LAPACK file name mention OpenBLAS) and shows the `sessionInfo()` lines with the paths replaced by `+<path>+`, and the answer to the last question, `TRUE`, is a fact about the machine that ran the examples and not about R: it is an OpenBLAS build, and on a build with the reference BLAS the answer is `FALSE`. The same script shows the effect of the threads. It multiplies two 1500 by 1500 matrices and checks that the CPU time (`user.self`) is larger than the elapsed time, which is only possible if several cores worked at once, and then times the same multiplication in two fresh R processes started by callr with `OPENBLAS_NUM_THREADS` set to 1 and to 4 (the variable is read when the library loads, so setting it in a running session is too late) and prints whether one thread is slower. On a computer with one core the last answer would be `FALSE`.

The manual lists the caveats of an external BLAS, and all of them matter for a decision. The results are not identical to the reference implementation; some differences are benign, such as the signs of singular vectors, but an optimised library can be less accurate, and its LAPACK can be older. R relies on IEEE 754 behaviour, and a library that assumes a term with a zero factor is zero can break it, since `+x * 0+` can be `NaN`. A multi-threaded BLAS can use more CPU time, and occasionally much more elapsed time, than a single-threaded one, notably on a busy machine and on hyper-threaded CPUs, because the threads contend for the CPU caches. BLAS and LAPACK calls inside threaded code (OpenMP sections in a package such as mgcv) may be unsafe with external libraries, whose thread-safety is not guaranteed. A threaded BLAS and the profiler disagree (the `SIGPROF` signal, noted in the section on profiling). And a threaded BLAS inside a process that is itself one of several parallel workers oversubscribes the machine: set `OPENBLAS_NUM_THREADS=1` (or `OMP_NUM_THREADS=1`) in the workers, a point xref:programming-languages/r/parallel-and-asynchronous-computing.adoc[Parallel and Asynchronous Computing] returns to. The links to the projects are https://www.openblas.net/[OpenBLAS] and https://www.mpi-magdeburg.mpg.de/projects/flexiblas[FlexiBLAS]; for MKL and Accelerate the manual's sections are the reference (https://cran.r-project.org/doc/manuals/r-release/R-admin.html#Intel-MKL[R Installation and Administration: Intel MKL], https://cran.r-project.org/doc/manuals/r-release/R-admin.html#Accelerate[R Installation and Administration: Accelerate]). The Fortran Reference page xref:programming-languages/fortran/blas-lapack-and-numerical-libraries.adoc[BLAS, LAPACK and Numerical Libraries] covers the libraries from the Fortran side.

=== The byte-code compiler and the JIT

R evaluates functions by walking their syntax tree, or, if they are compiled, by running a compact byte-code form of them on a virtual machine. The `compiler` package, part of R since 2.13.0, compiles closures (`cmpfun()`), expressions (`compile()`) and files (`cmpfile()`), and `disassemble()` prints what it produced. Since R 3.4.0 a just-in-time compiler is on by default: the NEWS says that functions are compiled on first or second use and that top-level loops are compiled and then run (https://cran.r-project.org/doc/manuals/r-release/NEWS.3.html[R NEWS: Changes in R 3.4.0]); and since R 3.5.0 all packages are byte-compiled on installation by default (https://cran.r-project.org/doc/manuals/r-release/NEWS.3.html[R NEWS: Changes in R 3.5.0]). xref:programming-languages/r/vectorisation-and-iteration.adoc[Vectorisation and Iteration] has the section "Byte-compilation" with the first look at all this; this section is about checking what the compiler did and how it is controlled.

The levels of `enableJIT(level)` are these (the help page, https://search.r-project.org/R/refmans/compiler/html/compile.html[R documentation: compile]); the function returns the previous level, a negative argument returns the current one, and level 3 needs the compiler option `optimize` to be 2 or 3.

[cols="1,6",options="header"]
|===
|Level |What is compiled
|0 |Nothing: the JIT is off.
|1 |Larger closures, before their first use.
|2 |Level 1, and some small closures before their second use.
|3 |Level 2, and in addition all top-level loops, before they are executed. The default.
|===

Source: https://search.r-project.org/R/refmans/compiler/html/compile.html[R documentation: compile]

The level of a new R process is set by the environment variable `+R_ENABLE_JIT+`, and `compilePKGS(TRUE)` (or `+_R_COMPILE_PKGS_+` set to a positive integer) makes the compiler compile packages when they are installed, but the help page says not to enable it outside installation, because it makes any serialized function be compiled, with a time and space overhead; `+R_COMPILE_PKGS+` is the variable that tells `R CMD INSTALL` whether to compile. A package can opt out in its `DESCRIPTION` with `ByteCompile: no`, and an installation can with `R CMD INSTALL --no-byte-compile` (https://cran.r-project.org/doc/manuals/r-release/R-exts.html#The-DESCRIPTION-file[Writing R Extensions: The DESCRIPTION file], https://cran.r-project.org/doc/manuals/r-release/R-admin.html#Byte_002dcompilation[R Installation and Administration: Byte-compilation]). The compiler options are `optimize` (an integer from 0 to 3; the out-of-the-box default is 2), `suppressAll`, `suppressUndefined` and `suppressNoSuperAssignVar`, read by `getCompilerOption()` and set by `setCompilerOptions()`. Two of its details are visible in everyday use. The compiler does not compile code that contains explicit calls to `browser()`, so that one can single-step from there (R NEWS, 3.4.0). And the help page remarks that the "byte code" is, when R is compiled with gcc, actually threaded code rather than byte code.

How to tell what happened? Printing a compiled function ends with a `+<bytecode: ...>+` line that holds a memory address, so the script defines `is_compiled()`, which asks whether such a line is printed, and uses it to show the three facts about the default JIT: the functions of an installed package are compiled; a closure with a loop is compiled by its first call; a small closure by its second. It ends with `cmpfun()` and `disassemble()`, whose result is a list of the form `(.Code, instructions, constants)`. For `x + 1` the instruction sequence is `GETVAR.OP` (push `x`), `LDCONST.OP` (push the constant), `ADD.OP` and `RETURN.OP`, and the operands (`1L`, `2L`, `0L`) are positions in the constant pool that is the third element: `x + 1`, `x` and `1`.

[source,r]
----
library(compiler)

# The JIT level in force (3 is the default) and the compiler's own options.
enableJIT(-1L)
#> [1] 3
getCompilerOption("optimize")
#> [1] 2

# A compiled closure prints a "<bytecode: ...>" line (with an address), so
# test for it instead of printing the function.
is_compiled <- \(f) any(grepl("^<bytecode", capture.output(print(f))))

# Functions in an installed package are byte-compiled when it is installed.
is_compiled(utils::head)
#> [1] TRUE

#>   FALSE   FALSE

#>   FALSE    TRUE

#> [1] TRUE

The effect of compilation can be measured, if the JIT is kept from compiling the function that is meant to be the interpreted one. The next script switches the JIT off with `enableJIT(0L)`, which returns the previous level (3), defines a loop, compiles a copy of it by hand with `cmpfun()`, compares the two with `bench::mark()`, and restores the level. With the JIT back on, the "interpreted" function would be compiled by its first call, so the comparison has to happen with the JIT off. The compiled copy is about ten times faster on a loop of a million scalar additions (the ratio was between 8.6 and 9.3 in the runs made, and is printed rounded to the nearest power of ten). That is the entire gain of the compiler and it is large for scalar loops, but it does nothing for work that R already does in C: the loop of the first benchmark on this page was compiled by the JIT and was still a thousand times slower than the vectorised form. The script ends with `+R_ENABLE_JIT+`, the variable that sets the level for a new R process, shown through callr: a child process started with 0 reports level 0, and one started with 1 reports level 1.

[source,r]
----
library(compiler)

sum_doubles <- function(n) {
  total <- 0
  for (i in seq_len(n)) {
    total <- total + i * 2
  }
  total
}

# Switch the JIT off (enableJIT() returns the previous level) while measuring,
# so that the plain function stays interpreted, and compare it with a copy
# compiled explicitly by cmpfun().
old <- enableJIT(0L)
old
#> [1] 3
enableJIT(-1L)
#> [1] 0
compiled <- cmpfun(sum_doubles)
b <- bench::mark(
  interpreted = sum_doubles(1e6),
  compiled = compiled(1e6),
  min_iterations = 5,
  filter_gc = FALSE
)
invisible(enableJIT(old))
enableJIT(-1L)
#> [1] 3

rel <- summary(b, relative = TRUE, filter_gc = FALSE)
# The ratio is about ten on a typical machine: show the nearest power of ten.
rel$median <- 10^round(log10(rel$median))
rel[c("expression", "median")]
#> # A tibble: 2 × 2
#>   expression  median
#>   <bch:expr>   <dbl>

Two more entry points of the package complete the picture, and both are rarely needed. `compile()` turns an expression into a byte-code object (type `"bytecode"`) that `eval()` runs, and `cmpfile()` compiles a file of R code into an `.Rc` file, writing a line that names the file, which `loadcmp()` later loads and runs. They exist for tools that distribute compiled code; ordinary programs and packages do not need them. The script also reads and sets the compiler options: `setCompilerOptions()` returns a named list of the previous values, so the old setting can be restored.

Calling `cmpfun()` by hand is therefore rarely needed: the JIT compiles what is called, and installation compiles packages. It remains useful in two cases, the one above where the interpreted time must be measured, and when the JIT is switched off on purpose (`+R_ENABLE_JIT=0+`) to debug a problem that might be the compiler's. Compiled code changes the format of tracebacks and some messages, which is why the NEWS of R 3.5.0 mentioned it among the user-visible changes.

=== data.table

data.table (version 1.18.6.1 here) is a package for tables that are large or whose operations are heavy: grouping, joins, sorting and reading and writing files. It is fast because of how it works: it modifies columns by reference instead of copying, it uses its own radix sort and optimised grouping (`GForce`), it can build indexes and keys for binary-search joins, and parts of it (`fread()`, `fwrite()`, `forder()`, grouping) use OpenMP threads. xref:programming-languages/r/data-table.adoc[data.table] covers the package, including its section on printing and threads; this page shows only where it changes the measurements. The script below, run on the shelf loans repeated 10000 times (600000 rows), makes three comparisons. A grouped mean over the eight members: here `tapply()` is as fast as data.table (the script prints that only `aggregate()` is at least three times slower), which is the honest result for few groups. The same mean over 100000 groups, where `tapply()` and `split()` followed by `vapply()` are at least ten times slower than data.table (the factor was 20 to 35 in the runs made, printed rounded down to a power of ten). Reading a 600000-row CSV file, where `fread()` is more than ten times faster than `read.csv()` (about 16 in the runs made). The R FAQ gives the reason for the third part: `read.table()` reads everything as character data first and then works out what the columns are, which takes time and memory for a large data set, and giving `colClasses` helps substantially (https://cran.r-project.org/doc/FAQ/R-FAQ.html#Why-is-read_002etable_0028_0029-so-inefficient_003f[R FAQ 7.28: Why is read.table() so inefficient?]). `fread()` detects the types itself and in parallel.

The number of threads is the thing to know before benchmarking: `getDTthreads()` reports it, `setDTthreads(n)` changes it for the session and returns the previous value (`setDTthreads(0)` is all logical CPUs), and `R_DATATABLE_NUM_THREADS` and `R_DATATABLE_NUM_PROCS_PERCENT` set it at load time. === Moving a hot loop to C{pp}

When the profile points at a loop that cannot be vectorised, because each iteration depends on the previous one, and the byte-code compiler has already done what it can, the next step is to write that loop in a compiled language. Rcpp (version 1.1.2 here, https://www.rcpp.org/[Rcpp project site], https://cran.r-project.org/package=Rcpp[Rcpp on CRAN]) is the usual way for C{pp}: `Rcpp::cppFunction("code")` compiles a function from a string and makes it callable from R, `Rcpp::sourceCpp("file.cpp")` does the same for a file whose exported functions carry a `pass:c[// [[Rcpp::export\]\]]` comment, and a package that contains such code lists Rcpp under `LinkingTo` and `Imports` in its `DESCRIPTION`. cpp11 is an alternative C{pp} interface to R. The compilation uses the tool chain of the machine: gcc and g++ 13.3 here, Rtools on Windows, the Xcode command line tools on macOS. The shelf example is a stock level that rises with returns, falls with loans and stays between zero and a capacity: `level = min(capacity, max(0, level + change))`, applied one day after another over a million days. The clamping makes it impossible to write with `cumsum()`, so the R version is a loop. The C{pp} version is the same loop on a `NumericVector`. The script checks that both return identical results before it compares them; the C{pp} function is about a hundred times faster (printed to the nearest power of ten; the ratio was between 90 and 105 in the runs made), at the price of a compiler dependency, a compilation step on every new session for `cppFunction()` (a package compiles once, at installation), and code in a second language to maintain. Because `cppFunction()` compiles the text it is given, the script's compilation takes a few seconds on first use; it prints nothing when it succeeds.

[source,r]
----
# A loop that cannot be vectorised: each step depends on the previous one.
# The stock of a shelf rises with returns, falls with loans, and stays between
# 0 and the shelf capacity.
set.seed(2026)
change <- rpois(1e6, lambda = 3) - rpois(1e6, lambda = 3)

stock_r <- function(change, capacity) {
  out <- numeric(length(change))
  level <- 0
  for (i in seq_along(change)) {
    level <- min(capacity, max(0, level + change[[i]]))
    out[[i]] <- level
  }
  out
}

Rcpp::cppFunction("
NumericVector stock_cpp(NumericVector change, double capacity) {
  int n = change.size();
  NumericVector out(n);
  double level = 0.0;
  for (int i = 0; i < n; ++i) {
    level = std::min(capacity, std::max(0.0, level + change[i]));
    out[i] = level;
  }
  return out;
}")

identical(stock_r(change, 500), stock_cpp(change, 500))

== From symptom to first step

The table maps what one observes to the first thing to do. It is a starting point for the measurement, not a substitute for it.

|Symptom |First step |Likely remedy
|A loop over rows or elements is slow |`bench::mark()` the loop against a vectorised form; profile it if the body is large |Vectorise, `match()` for lookups, `rowsum()` or `tapply()` for groups
|A function gets slower faster than the input grows |`bench::press()` over sizes, and look at `mem_alloc` |Remove the growing vector or `rbind()` in a loop; preallocate
|Memory use is large for a small result |`bench::mark()` memory column, then `tracemem()` and `Rprofmem()` |Remove copies; see the memory page

== A worked example: from slow to fast

The shelf analysis of the overdue rate by genre is the kind of computation this page is about, written the way the problem would first be described: for every loan, find its book, work out the days on loan, decide whether it is overdue, and then average by genre. The script runs the steps of the measurement loop on 120000 loans (the shelf loans repeated 2000 times). It defines the first version, `overdue_rate_slow()`, and prints its result, so that there is an answer to check against. It times one call with `system.time()`; the elapsed time is over a second, enough to matter, and is printed as `+<n>+`. It profiles one call with `Rprof()`: the top of `by.total` is the function itself, `-.Date` (about half the time) and `difftime` (nearly as much), so the cost is in subtracting dates one element at a time, and the `which()` lookup that looked suspicious in the source is not the bottleneck. It then changes two things, the title lookup (`match()`) and the date arithmetic (the whole `loan_date` and `return_date` columns subtracted at once), keeps the grouping, and checks with `all.equal()` that the answer did not change. Last it measures again with `bench::mark()` (`iterations = 3` because one call of the slow version takes over a second): the new version is about a hundred times faster. The profile of the first version is the point: reading the source, the lookup in `books` inside the loop looked like the expensive part, and the profile says that most of the time is in the date subtraction, which is where a change helps most. Measuring first is cheaper than being wrong.

[source,r]
----
source("scenario.R")

books$genre <- tolower(trimws(books$genre))
books$key <- normalise_isbn(books$isbn)
many_loans <- loans[rep(seq_len(nrow(loans)), 2000L), ]
nrow(many_loans)
#> [1] 120000

# First version: correct, written the way the problem was described.
overdue_rate_slow <- function(loans, books, today, allowed) {
  genre <- character(nrow(loans))
  overdue <- logical(nrow(loans))
  for (i in seq_len(nrow(loans))) {
    hit <- which(books$key == loans$isbn[[i]])
    genre[[i]] <- if (length(hit) > 0L) books$genre[[hit[[1L]]]] else NA
    end <- loans$return_date[[i]]
    if (is.na(end)) {
      end <- today
    }
    overdue[[i]] <- as.integer(end - loans$loan_date[[i]]) > allowed
  }
  tapply(overdue, genre, mean, na.rm = TRUE)
}

slow <- overdue_rate_slow(many_loans, books, shelf_today, loan_days)
data.frame(genre = names(slow), overdue_rate = round(unname(slow), 3))
#>             genre overdue_rate
#> 1         classic        0.600
#> 2         fiction        0.522
#> 3         mystery        0.500
#> 4     non-fiction        0.600
#> 5          poetry        0.667
#> 6 science fiction        0.467

# Step 1: measure. Is it slow enough to matter?
system.time(overdue_rate_slow(many_loans, books, shelf_today, loan_days))
#>    user  system elapsed
#>     <n>     <n>     <n>

# Step 2: profile. Where does the time go?
prof <- tempfile(fileext = ".out")
Rprof(prof, interval = 0.01)
invisible(overdue_rate_slow(many_loans, books, shelf_today, loan_days))
Rprof(NULL)
head(summaryRprof(prof)$by.total, 3)
#>                     total.time total.pct self.time self.pct
#> "overdue_rate_slow"        <n>       <n>       <n>      <n>
#> "-.Date"                   <n>       <n>       <n>      <n>
#> "difftime"                 <n>       <n>       <n>      <n>
unlink(prof)

# Step 3: change one thing at a time. The lookup becomes match(), the dates
# are subtracted as vectors, and the grouping stays.
overdue_rate_fast <- function(loans, books, today, allowed) {
  genre <- books$genre[match(loans$isbn, books$key)]
  end <- loans$return_date
  end[is.na(end)] <- today
  overdue <- as.integer(end - loans$loan_date) > allowed
  tapply(overdue, genre, mean, na.rm = TRUE)
}

# Step 4: check that the answer did not change, then measure again.
fast <- overdue_rate_fast(many_loans, books, shelf_today, loan_days)
all.equal(slow, fast)
#> [1] TRUE

b <- bench::mark(
  slow = overdue_rate_slow(many_loans, books, shelf_today, loan_days),
  fast = overdue_rate_fast(many_loans, books, shelf_today, loan_days),
  iterations = 3,
  filter_gc = FALSE
)
rel <- summary(b, relative = TRUE, filter_gc = FALSE)
rel$median <- 10^round(log10(rel$median))
rel[c("expression", "median")]
#> # A tibble: 2 × 2
#>   expression median
#>   <bch:expr>  <dbl>

#> 2 fast            1

== Pitfalls collected

[cols="3,4",options="header"]
|===
|Pitfall |What to do
|Optimising before measuring. |Profile first. The slow part is often not the one the source suggests, as the worked example shows.
|Trusting one timing. |Repeat, and report the median or the minimum; use bench for anything under a second.
|Comparing expressions that compute different things. |Use `check = TRUE` (bench) or `check = "equal"` (microbenchmark), and test the optimised function against the original.
|Benchmarking tiny inputs. |A winner on 100 elements can lose on 100000. Use `bench::press()` over sizes, and large data for data-processing tasks.
|Timing the setup. |Create the data outside the expression; assign nothing global inside it.
|Reading the memory column of the first measurement. |Warm up first: the first call allocates for byte-compilation.
|Reporting seconds. |They are specific to a machine. Report ratios and the memory, and say what the machine was.
|Using `sapply()` for speed. |It is not faster than a loop; `vapply()` is as fast and checks its types. Vectorise for speed.
|Growing vectors and data frames in a loop. |Preallocate, or collect pieces in a list and combine them once.
|`pass:c[df$col[i\] <- value]` in a loop. |Loop on a vector and put it in the data frame once; the data-frame form copied about ten thousand times the memory in the measurement above.
|Profiling too short a run. |Fewer than a few dozen samples are noise; repeat the work or lengthen it.
|Profiling a program that waits with the CPU event. |Use `Rprof(event = "elapsed")` (R 4.4.0) or `profvis` (which defaults to elapsed time on R 4.4.0 or later).
|Expecting a line profile under `Rscript`. |`keep.source` is `FALSE` there. Source with `keep.source = TRUE`.
|A multi-threaded BLAS with the profiler or with parallel workers. |Disable profiling, and set the BLAS threads to 1 in the workers.
|Assuming a faster BLAS gives the same numbers. |The results differ in the last digits and in the signs of eigenvectors; use `all.equal()`, not `identical()`.
|Calling `cmpfun()` everywhere. |The JIT already compiles; measure with the JIT off if you want to see the effect.
|Rewriting in C{pp} first. |It is the most expensive remedy. Vectorise, fix copies, then compile.
|===
