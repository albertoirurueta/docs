= Debugging

Checked against R 4.6.1 (2026-06-24) on 2026-10-20; R 4.6.2 is scheduled for 2026-10-29. Everything on this page is base R (the `base`, `utils`, `methods` and `stats` packages that ship with R), so no add-on package version applies; the `lintr` 3.4.0 default linters were used only to check the scripts. Debugging is the part of programming where you stop guessing: you ask R which calls were active when something failed, you stop the program at a chosen point and look at the variables, or you step through a function one statement at a time. R's tools for this are small and old, they work the same way in a terminal, in RStudio, in Positron and in a batch job, and the graphical debuggers are front ends to them. This page describes each tool, shows what it prints, and says which one to reach for when. The error-handling side, catching and signalling conditions, is in xref:programming-languages/r/conditions-and-error-handling.adoc[Conditions and Error Handling]; checking inputs early so that the failure is close to its cause is in xref:programming-languages/r/defensive-programming-and-input-validation.adoc[Defensive Programming and Input Validation].

There are two kinds of example. The first kind is a script that was run with `Rscript` on R 4.6.1 with warnings printed as they happen (`options(warn = 1)`); the lines that start with `+#>+` are what it printed, in the order R printed them, so a message that R writes to the error stream appears where it was written. The scripts pass the default `lintr` linters; a `pass:c[# nolint:]` comment marks a line where the code is what a default linter dislikes. The second kind is a transcript of an interactive session, shown as a `text` block with the prompts exactly as R printed them: `>` for a new command, `+` for a continued one, `Browse[1]>` inside the browser and `Selection:` in the menus of `recover()` and `debugger()`. Debugging is conversational, and the prompts are the point, so these blocks are not scripts and carry no `+#>+` lines. They were captured by feeding the commands to `R --interactive --no-save --quiet`, which makes R echo the commands it reads, and a final empty prompt is left out. An interactive session keeps the source text of the functions you type (`options(keep.source = TRUE)` is the default there), which is why the transcripts show source references such as `at #3` and `debug at #2:` that `Rscript` output does not have. The names `books`, `loans`, `shelf_today`, `loan_days` and the `book()` constructor come from the running library-shelf scenario described on the xref:programming-languages/r/index.adoc[section index]: a script that needs them starts with `source("scenario.R")`. Where a message contains quotation marks, they are the typographic quotes R prints in a UTF-8 locale.

== The tools at a glance

The R Language Definition puts it in one paragraph: most debugging takes place through calls to `browser()` or `debug()`, which rely on the same internal mechanism and give the user a special prompt at which any command can be typed, evaluated in the currently active environment (https://cran.r-project.org/doc/manuals/r-release/R-lang.html#Debugging[R-lang: Debugging]). Everything else on this page is a way of arriving at that prompt, or of finding out where to arrive. The debugger only sees interpreted R code: if a function calls compiled code, execution halts at the next statement that is evaluated in R, and a symbolic debugger such as `gdb` is needed for the compiled part (a pointer to that is in the section on compiled code below).

[cols="3,5,2,2",options="header"]
|===
|Tool |What it is for |Needs a prompt |Section
|`traceback()` |Which calls were active when the last uncaught error happened. |No |<<traceback>>
|`browser()` |Stop at a line you added to the code and look around. |Yes |<<browser>>
|`debug()`, `debugonce()` |Step through a function without editing it. |Yes |<<debug>>
|`trace()`, `setBreakpoint()` |Insert code (a message, a condition, a `browser()` call) at a chosen step of a function without editing it. |Only if it inserts a browser |<<trace>>
|`options(error = recover)` |After an error, pick any frame of the stack and look at its variables, without running the code again. |Yes |<<postmortem>>
|`dump.frames()`, `debugger()` |Save the frames of an error, to a variable or a file, and look at them later or elsewhere. |Only `debugger()` |<<postmortem>>
|`options(warn = 2)` |Turn warnings into errors, so that they stop at the offending call and leave a stack. |No |<<warnings>>
|`withCallingHandlers()` with `sys.calls()` |See the stack at the moment a condition is signalled, without unwinding it. |No |<<traceback>>
|===

Source: https://cran.r-project.org/doc/manuals/r-release/R-lang.html#Debugging[The R Language Definition: Debugging]

A debugging session has a rhythm that does not depend on the tool: find where the failure happens, form a guess about the state that causes it, look at that state, change something, and run again. The tools differ in how much they make you re-run. `traceback()` and `options(error = recover)` work on an error that has already happened. `browser()` and `trace()` ask you to run the code again with a stop in it. `debug()` asks for a new run with the stop at the start of a function. The cheapest tool that answers the question is the right one, and the sections below follow that order.

[[errors]]
== The error message is the first tool

R reports an uncaught error as `Error in <call> : <message>`. The call is the function call that was being evaluated when the error was signalled, and the message is the text given to `stop()` or produced by R itself. When the pair does not fit on one line the message moves to the next line. Both parts are available as data when the error is caught: a caught error is a condition object, a list with the fields `message` and `call`, and `conditionMessage()` and `conditionCall()` read them (https://search.r-project.org/R/refmans/base/html/conditions.html[R documentation: conditions]).

The running example for this page is a small piece of the shelf scenario. `member_report()` counts a member's loans and how many were overdue; it calls `count_overdue()`, which calls `is_overdue()` once per loan through `vapply()`. The scenario data has a loan whose date is the impossible `2025-02-30`, which `as.Date()` turned into `NA`, and the member is Ana Ruiz, so the first report that touches that loan fails. The script defines the three functions, runs the report for another member (which works), and then catches the failing one as a condition object.

[source,r]
----
source("scenario.R")

# A chain of three functions with a bug: a loan with an impossible date.
is_overdue <- function(loan_date, return_date,
                       today = shelf_today) { # nolint: object_usage_linter.
  end <- if (is.na(return_date)) today else return_date
  if (as.integer(end - loan_date) > loan_days) TRUE else FALSE # nolint: object_usage_linter, line_length_linter.
}

count_overdue <- function(rows) {
  flags <- vapply(seq_len(nrow(rows)), \(i) {
    is_overdue(rows$loan_date[i], rows$return_date[i])
  }, logical(1L))
  sum(flags)
}

member_report <- function(loans, who) {
  rows <- loans[loans$member == who, ]
  c(loans = nrow(rows), overdue = count_overdue(rows))
}

member_report(loans, "Ben Okafor")
#>   loans overdue
#>       5       3

# Catch the error as a condition object: it records the message and the call.
err <- tryCatch(member_report(loans, "Ana Ruiz"), error = \(e) e)
class(err)
#> [1] "simpleError" "error"       "condition"
conditionMessage(err)
#> [1] "missing value where TRUE/FALSE needed"
conditionCall(err)
#> if (as.integer(end - loan_date) > loan_days) TRUE else FALSE

# An error raised with call. = FALSE, like the ones validate_book() signals,
# names no call at all: the stack is then the only clue to where it came from.
bad <- tryCatch(
  book("Orchard Logic", isbn = "978-0-306-40615-8"),
  error = \(e) e
)
bad
#> <simpleError: invalid ISBN-13: 9780306406158>
conditionCall(bad)
#> NULL

# An error that was caught leaves no traceback behind.
traceback()
#> No traceback available
----

Source: https://search.r-project.org/R/refmans/base/html/conditions.html[R documentation: conditions (conditionMessage, conditionCall and tryCatch)]

The message, `missing value where TRUE/FALSE needed`, is what R says when an `if` condition is `NA`, and the call is the `if` expression itself, not the function around it: for errors that R detects in a language construct the "call" is that construct, which is why the call shown does not look like a function call. Nothing in the message says which member, which loan or which function called `is_overdue()`. That is what the next tools are for. Two details in the output matter. The error raised with `call. = FALSE` has no call at all: `conditionCall()` is `NULL` and the printed condition is `+<simpleError: ...>+` with no `in` part. `validate_book()` and `book()` in the scenario signal their errors that way, so for them the stack is the only record of where the error came from. And the final `traceback()` says `No traceback available`, because both errors were caught by `tryCatch()` and only an error that reaches the top level leaves a stack behind.

What the same error looks like when nobody catches it depends on how R was started. In an interactive session R prints the message and returns to the prompt, ready for `traceback()`. In a non-interactive session, such as `Rscript` or `R -f`, R prints the message, adds a `Calls:` line, prints `Execution halted` and exits with status 1. The next block is a script that fails on purpose and the complete output of running it with `Rscript`; it is a fragment, not a runnable example, because it ends in the error.

[source,r]
----
source("scenario.R")

is_overdue <- function(loan_date, return_date,
                       today = shelf_today) { # nolint: object_usage_linter.
  end <- if (is.na(return_date)) today else return_date
  if (as.integer(end - loan_date) > loan_days) TRUE else FALSE # nolint: object_usage_linter, line_length_linter.
}

  flags <- vapply(seq_len(nrow(rows)), \(i) {
    is_overdue(rows$loan_date[i], rows$return_date[i])
  }, logical(1L))
  sum(flags)
}

member_report <- function(loans, who) {
  rows <- loans[loans$member == who, ]
  c(loans = nrow(rows), overdue = count_overdue(rows))
}

member_report(loans, "Ben Okafor")
member_report(loans, "Ana Ruiz")
cat("not reached\n")
----

Source: https://cran.r-project.org/doc/manuals/r-release/R-intro.html#Scripting-with-R[An Introduction to R: Scripting with R]

The output of that script:

[source,text]
----
  loans overdue
      5       3
Error in if (as.integer(end - loan_date) > loan_days) TRUE else FALSE :
  missing value where TRUE/FALSE needed
Calls: member_report -> count_overdue -> vapply -> FUN -> is_overdue

----

Source: https://search.r-project.org/R/refmans/base/html/options.html[R documentation: options (showErrorCalls and showWarnCalls)]

The first report printed its answer, and the second stopped the script: `not reached` never appears. The `Calls:` line is a compact traceback, outermost call first and joined with `+->+`, and it is there because the `showErrorCalls` option is on by default in non-interactive sessions (the options help page says that the call stacks are shown by default for errors there). The anonymous function that `vapply()` calls appears as `FUN`. The line is shortened when the sequence is long: `showNCalls`, by default 50 bytes, sets the length at which ellipses are used, and `options(showErrorCalls = FALSE)` removes the line altogether, as a later script shows. It is a summary, not a traceback: it has no arguments and no source locations, and it says nothing about which iteration of `vapply()` failed.

[[traceback]]
== Reading the stack with `traceback()`

`traceback()` prints the call stack of the last uncaught error: the sequence of calls that led to it. The help page calls it useful when an error occurs with an unidentifiable error message, and Writing R Extensions recommends running it whenever the cause of an error is not immediately obvious, because errors are often reported as being in some package when the traceback shows that they were raised by another package or by base R (https://cran.r-project.org/doc/manuals/r-release/R-exts.html#Debugging-R-code[Writing R Extensions: Debugging R code]). The calls are listed in reverse order, innermost first, each with the number of its frame, so frame 1 is the call you typed. The help page adds that calls to builtins are included in the stack but calls to specials are not.

=== `traceback()` at the prompt

This is the same failing report in an interactive session. Because the session keeps source references, an entry for a call that sits inside a function typed at the prompt ends in `at #n`, the line of that function's definition on which the call is written.

[source,text]
----

4: FUN(X[[i]], ...)

       is_overdue(rows$loan_date[i], rows$return_date[i])
   }, logical(1L)) at #2

Source: https://search.r-project.org/R/refmans/base/html/traceback.html[R documentation: traceback]

Reading the numbers from the bottom, `member_report()` called `count_overdue()` from line 3 of its definition, which called `vapply()` from line 2 of its own definition, which called the anonymous function, shown as `pass:c[FUN(X[[i\]\], ...)]`, which called `is_overdue()` from line 3 of the definition of `count_overdue()` (the anonymous function is part of that definition, so its lines are counted there); and the error was detected in `is_overdue()`. The anonymous function `+\(i) ...+` is shown as `+function(i) {...}+`: the backslash form is only a different way of typing the same call. The last command, `pass:c[.traceback()[[1\]\]]`, shows that the stack is data: `.traceback()` returns the stack as a list or pairlist of calls, deepest first, with each call as a character vector of deparsed lines, and `traceback()` formats and prints that list. `.traceback()` was added in R 3.3.0, and since R 4.0.0 the stack that R records when the error is signalled (`.Traceback`) holds the calls themselves and deparses them only when `traceback()` or `.traceback()` is called; the help page warns that where `.Traceback` is stored is undocumented, so use the functions, not the variable.

=== `traceback()` in a script

An `Rscript` run ends at the first uncaught error, so there is no prompt at which to type `traceback()`. The `error` option fixes that: it holds a function, or an expression, that R runs when an error reaches the top level, after printing the message and before it halts. The next script prints the traceback from such a handler and then leaves with `q(status = 0)`. The argument `3` of `traceback()` means "skip three entries at the top of the stack": the entries for `traceback()`, `.traceback()` and the handler that called them, which the help page recommends for exactly this use.

[source,r]
----
source("scenario.R")

is_overdue <- function(loan_date, return_date,
                       today = shelf_today) { # nolint: object_usage_linter.
  end <- if (is.na(return_date)) today else return_date
  if (as.integer(end - loan_date) > loan_days) TRUE else FALSE # nolint: object_usage_linter, line_length_linter.
}

count_overdue <- function(rows) {
  flags <- vapply(seq_len(nrow(rows)), \(i) {
    is_overdue(rows$loan_date[i], rows$return_date[i])
  }, logical(1L))
  sum(flags)
}

member_report <- function(loans, who) {
  rows <- loans[loans$member == who, ]
  c(loans = nrow(rows), overdue = count_overdue(rows))
}

# Print the stack when an error reaches the top level, then leave with status 0.
# traceback(3) skips three entries at the top of the stack: traceback(),
# .traceback() and the error handler that called them.
options(error = function() {
  traceback(3)
  q(status = 0)
})
member_report(loans, "Ana Ruiz")
#> Error in if (as.integer(end - loan_date) > loan_days) TRUE else FALSE :
#>   missing value where TRUE/FALSE needed
#> Calls: member_report -> count_overdue -> vapply -> FUN -> is_overdue
#> 5: is_overdue(rows$loan_date[i], rows$return_date[i])
#> 4: FUN(X[[i]], ...)
#> 3: vapply(seq_len(nrow(rows)), function(i) {
#>        is_overdue(rows$loan_date[i], rows$return_date[i])
#>    }, logical(1L))
#> 2: count_overdue(rows)
#> 1: member_report(loans, "Ana Ruiz")
----

Source: https://search.r-project.org/R/refmans/base/html/traceback.html[R documentation: traceback]

The first three lines are R's own message and `Calls:` summary; everything from `5:` down is `traceback(3)`. With `traceback(2)` the handler itself would show up as the top entry, and for an error raised by `stop()` the `stop()` call is an entry too, as the next script shows with the smallest possible chain. The handler in this script also reads the stack through `.traceback(3)`. Called directly from the handler, `.traceback(3)` skips three entries too, but they are `.traceback()` itself, the handler and the `stop()` call, so what it returns is the three frames of `f()`, `g()` and `h()`.

[source,r]
----
f <- function(x) g(x)
g <- function(x) h(x)
h <- function(x) stop("boom in h")

# traceback(2) skips traceback() and .traceback() only, so the handler shows up.
options(error = function() {
  traceback(2)
  # .traceback() returns the same stack as a list, deepest call first.
  stack <- .traceback(3)
  cat("class:", class(stack), "\n")
  cat("length:", length(stack), "\n")
  cat("innermost:", stack[[1L]], "\n")
  q(status = 0)
})
f(1)
#> Error in h(x) : boom in h
#> Calls: f -> g -> h
#> 5: (function ()
#>    {
#>        traceback(2)
#>        stack <- .traceback(3)
#>        cat("class:", class(stack), "\n")
#>        cat("length:", length(stack), "\n")
#>        cat("innermost:", stack[[1L]], "\n")
#>        q(status = 0)
#>    })()
#> 4: stop("boom in h")
#> 3: h(x)
#> 2: g(x)
#> 1: f(1)
#> class: pairlist
#> length: 3
#> innermost: h(x)
----

Source: https://search.r-project.org/R/refmans/base/html/traceback.html[R documentation: traceback and .traceback]

The handler appears in the traceback as an anonymous function call, `+(function () {...})()+`, because R evaluates the `error` option as a call to the function. The `stop("boom in h")` entry is frame 4, above `h(x)`, since `stop()` is itself a function call and the error is signalled from inside it. The `class: pairlist` line is a detail worth knowing when you process the result: the help page says `.traceback()` returns a list or a pairlist, and for the stack of an error it is a pairlist, so wrap it in `as.list()` before using `lengths()` or `vapply()` on it (the script below does).

The `error` option takes any of three forms. A function is called with no arguments (`+options(error = function() ...)+`, or the name of one such as `recover`). An expression is evaluated: `+options(error = quote(...))+` or an `expression()` vector, which is the form that fits the one-liners in the manuals. And `NULL`, the default, restores the standard behaviour: return to the prompt in an interactive session, halt in a non-interactive one. In start-up files the functions of the `utils` package have to be written with the namespace, as `options(error = utils::recover)`, because the package is not yet attached when the file runs (the options help page says so). A `traceback()` that is very long can be shortened: `max.lines` limits the number of lines printed per call, and the options `traceback.max.lines` and `deparse.max.lines` set the limit for the whole session. A long call is what `do.call()` produces when the function is given the objects themselves: the call that R records holds the values, not the names, so a data frame argument is pasted into it. The next script shows how long such an entry gets, and what `max.lines = 2` does to it.

[source,r]
----
source("scenario.R")

first_overdue <- function(df) {
  stopifnot(nrow(df) > 100L)
  days <- df$return_date - df$loan_date
  which(days > loan_days)[1L] # nolint: object_usage_linter.
}

# do.call() puts the argument values, not their names, into the call. With a
# data frame the call that traceback() has to deparse is long: lengths() counts
# the lines of each entry, deepest call first.
options(error = function() {
  stack <- as.list(.traceback(3))
  cat("lines per entry:", lengths(stack), "\n")
  short <- as.list(.traceback(3, max.lines = 2L))
  cat("with max.lines = 2:", lengths(short), "\n")
  traceback(3, max.lines = 2L)
  q(status = 0)
})
do.call("first_overdue", list(loans))
#> Error in first_overdue(list(loan_id = c("L001", "L002", "L003", "L004",  :
#>   nrow(df) > 100L is not TRUE
#> Calls: do.call -> first_overdue -> stopifnot
#> lines per entry: 1 1 50 1
#> with max.lines = 2: 1 1 2 1
#> 4: stop(simpleError(msg, call = if (p <- sys.parent(1L)) sys.call(p)))
#> 3: stopifnot(nrow(df) > 100L)
#> 2: first_overdue(list(loan_id = c("L001", "L002", "L003", "L004",
#>    "L005", "L006", "L007", "L008", "L009", "L010", "L011", "L012",
#>     ...
#> 1: do.call("first_overdue", list(loans))
----

Source: https://search.r-project.org/R/refmans/base/html/traceback.html[R documentation: traceback (max.lines)]

The failing function was reached through `do.call("first_overdue", list(loans))`, so its entry in the stack, number 2, contains the whole data frame as an argument: `lengths()` counts 50 lines for it against 1 for the others, and `max.lines = 2L` keeps the first two lines of it and marks the cut with `+...+`. With a function object instead of its name, `do.call(first_overdue, list(loans))`, the entry would begin with the deparsed function as well. Either is a reason to pass names of objects, not objects, through `do.call()` when the call may appear in a traceback; see xref:programming-languages/r/evaluation-and-non-standard-evaluation.adoc[Evaluation and Non-Standard Evaluation] for `do.call()` itself.

=== When `traceback()` does not help

It reports the stack of the last uncaught error, and only that. An error caught by `try()` or `tryCatch()` generates no traceback, and neither does a warning; the help page says that what `traceback()` prints is the call sequence for the last uncaught error and not necessarily for the last error. The stack ends where the error was signalled, so it cannot tell what the values were. Writing R Extensions gives three more reasons it may not point at the cause. If the innermost call is `.C`, `.Fortran`, `.Call`, `.External` or `.Internal`, the error came from compiled code, and as such code can evaluate R expressions the compiled call need not be the innermost one. When S4 method dispatch is involved the traceback can stop at a call such as `+initialize(value, ...)+` while the error message names a function that is not in the stack. And for infinite recursion the message `evaluation nested too deeply: infinite recursion / options(expressions=)?` can be hard to read at the default limit of 5000 nested expressions, so the manual suggests lowering it with `options(expressions = 500)` and running the example again (the script below does this). In all three cases the tools of the next sections, which stop the program while it is still running, give more.

[[live-stack]]
=== The live stack: `sys.calls()` in a calling handler

A calling handler runs on top of the stack of the condition it handles, before anything is unwound, so it can read the live stack with `sys.calls()` (https://search.r-project.org/R/refmans/base/html/sys.parent.html[R documentation: sys.parent and its relatives]). That is the one way to get a stack for a condition that a `tryCatch()` further out would catch, and the way to log the stack of an error without stopping the program. `tryCatch()`, by contrast, unwinds first, so its handler sees only the frames outside it. The script below logs the stack of the failing report and then lets the error continue to `try()`.

[source,r]
----
source("scenario.R")

is_overdue <- function(loan_date, return_date,
                       today = shelf_today) { # nolint: object_usage_linter.
  end <- if (is.na(return_date)) today else return_date
  if (as.integer(end - loan_date) > loan_days) TRUE else FALSE # nolint: object_usage_linter, line_length_linter.
}

count_overdue <- function(rows) {
  flags <- vapply(seq_len(nrow(rows)), \(i) {
    is_overdue(rows$loan_date[i], rows$return_date[i])
  }, logical(1L))
  sum(flags)
}

# A calling handler runs on top of the stack of the error, before it unwinds, so
# sys.calls() still shows the frames that led to it. tryCatch() would have
# unwound them first.
show_stack <- function(e) {
  calls <- sys.calls()
  cat("frames on the stack:", length(calls), "\n")
  for (i in seq_along(calls)) {
    cat(i, ": ", deparse(calls[[i]])[1L], "\n", sep = "")
  }
}
result <- try(
  withCallingHandlers(
    count_overdue(loans[loans$member == "Ana Ruiz", ]),
    error = show_stack
  ),
  silent = TRUE
)
#> frames on the stack: 12

[[browser]]
== Stopping inside the code: `browser()`

A call to `browser()` in the body of a function stops the evaluation at that point and gives you a prompt, `Browse[1]>`, at which any R expression is evaluated in the environment where `browser()` was called. It is the lowest-level tool: `debug()` and the breakpoints of the IDEs use the same browser, and the RStudio user guide calls it the lowest-level debugging tool (https://cran.r-project.org/doc/manuals/r-release/R-lang.html#browser[R-lang: browser]; https://docs.posit.co/ide/user/ide/guide/code/debugging.html[RStudio user guide: Debugging]). Its signature is `browser(text = "", condition = NULL, expr = TRUE, skipCalls = 0L)`. The first two arguments carry information for helper programs and can be read back at the prompt with `browserText()` and `browserCondition()`; `expr` makes the stop conditional; `skipCalls` is for wrappers, and tells the browser to report a location further up the stack when the call to `browser()` is itself nested in another debugging function (https://search.r-project.org/R/refmans/base/html/browser.html[R documentation: browser]).

The prompt accepts ordinary R, plus a handful of one-word commands that R interprets itself. The R Language Definition lists five of them, the help page lists them all:

[cols="1,6",options="header"]
|===
|Command |What it does
|`n` |Evaluate the next statement, stepping over function calls. In step-through mode (the browser entered by `debug()`) a bare Enter does the same.
|`s` |Evaluate the next statement, stepping into function calls.
|`f` |Finish the current loop or function, then stop again at the first statement after it.
|`c` or `cont` |Leave the browser and continue; in step-through mode, continue to the end of the current context, such as the loop or the function.
|`Q` |Leave the browser and the current evaluation, and return to the top level.
|`where` |Print the stack of active function calls.
|`help` |Print this list.
|`r` |Invoke a `"resume"` restart if one is available (typically after a user interrupt); otherwise the letter is read as an R expression.
|===

Source: https://search.r-project.org/R/refmans/base/html/browser.html[R documentation: browser]

Leading and trailing blanks are ignored except on an empty line. What an empty line does depends on the option `browserNLdisabled`: if it is `TRUE`, empty lines are ignored; if not, an empty line is the same as `n`, or as `s` if that was used most recently. This is R 3.1.0 behaviour: the NEWS of that release made a call to `browser()` consistent with the browser entered by `debug()`, so that Enter means `n` rather than `c`, and added the `s` and `f` commands (https://cran.r-project.org/doc/manuals/r-release/NEWS.3.html[R NEWS: Changes in R 3.1.0]). Older tutorials that say Enter continues from a `browser()` call describe R before 3.1.0.

The transcript below puts a `browser()` call between the two statements of a small function from the shelf scenario. `days_out()` counts the days between a loan and its return, or between the loan and `shelf_today` when it is still out; `late_days()` subtracts the loan period. Loan L012 is the one that was returned three days before it was lent, and the function quietly returns 0 for it. The browser shows why.

Line by line: `+Called from: ...+` names the call whose frame the browser is in. `ls()` lists that frame, which holds the arguments and the `days` already computed; `days` prints `-3`, the day count of a loan returned before it was lent, which the arithmetic of `late_days()` turned into 0 without complaint. `help` prints the table above. `where` prints the stack, here only the call to `late_days()`, with a blank line after it. `n` enters step-through mode: R prints the statement it is about to run, `+debug at #4: ...+`, without having run it, and an expression typed at the prompt, `days - loan_days`, evaluates to -24. `c` leaves the browser and the function returns its value, `0`.

Anything entered at the prompt is evaluated in the frame, so a variable can be changed as well as read. The help page for `trace()` says the opposite about changes disappearing; what happened in the session below, where the variable changed at the prompt changed the result, matches the manual. If a local variable has the name of a command, such as `n`, `c`, `s`, `f` or `Q`, typing the name runs the command; print the variable with `print(n)`, with `(n)` or, as the R Language Definition suggests, with `get("n")`.

=== Conditional breakpoints

Stopping on every iteration of a loop is useless when the interesting one is the 512th. `browser(expr = <condition>)` evaluates the condition and enters the prompt only when it is true. The help page says that it is an illusion of conditional debugging, because execution is always paused at the call and the condition only decides whether control passes to the evaluator, and that an `if` statement around a bare `browser()` is usually more efficient; the argument is simply shorter to write in a place where an `if` is awkward. The `text` argument labels the stop, so that `browserText()` can tell several breakpoints apart.

The function in the transcript counts the loans in a data frame that were returned before they were lent. The browser stops only for the loan that is wrong, the loop variable `i` and the data say which one, and the edit to `days` at the prompt keeps the loan out of the count.

+     browser(text = "return before loan", expr = !is.na(days) && days < 0L)

=== Browser levels

The number in `Browse[1]>` is the browser level. A browser entered from the prompt of another browser is one level deeper: typing a call to a function that itself contains `browser()` gives `Browse[2]>`, `where` shows the nested call on top of the stack, and `c` returns to level 1. `debug()` replaces its browser at every step rather than nesting a new one, which is why its prompt stays at `Browse[1]>`.

After the first `c` returns to level 1, the second `c` lets `late_days()` carry on to its call of `days_out()`, whose own `browser()` stops again at level 1; `Q` quits everything. === `browser()` in a script

The prompt reads its commands from the console. When a script is run with `Rscript` there is no person at the console, and what the browser reads is the rest of the script file: the lines that follow the call become the browser's commands. The script below calls a function with a `browser()` in it and then has three more lines of its own; the output after it, from `Rscript` on R 4.6.1, shows that those lines were run at the browser prompt.

[source,r]
----
f <- function(x) {
  browser()
  x + 1
}
f(1)
cat("after the call\n")
y <- 2
y * 10
----

Source: https://search.r-project.org/R/refmans/base/html/browser.html[R documentation: browser]

[source,text]
----

after the call
[1] 20
debug: x + 1
[1] 2
----

Source: https://cran.r-project.org/doc/manuals/r-release/R-intro.html#Scripting-with-R[An Introduction to R: Scripting with R]

The output is a record of what was observed, not a documented behaviour: `Called from: f(1)` is the browser announcing itself; `after the call`, `[1] 20` are the output of the lines `cat("after the call\n")` and `+y * 10+`, run in the frame of `f()`, and `+y <- 2+` ran there too, as a local variable of `f()`; at the end of the file the browser got no more input, stepped on (`debug: x + 1`) and `f(1)` returned 2. The lesson is to remove `browser()` calls before running code in a batch job. `debug()` and `trace()` with a browser tracer behave the same way. Since R 4.3.0 the environment variable `+_R_CHECK_BROWSER_NONINTERACTIVE_+` makes non-interactive debugger invocations trappable, and `R CMD check --as-cran` enables it to detect leftover `browser()` statements in a package (https://cran.r-project.org/doc/manuals/r-release/NEWS.html[R NEWS: Changes in R 4.3.0]). Section xref:programming-languages/r/scripts-and-the-command-line.adoc[Scripts and the Command Line] covers running R non-interactively.

=== Byte-compiled code

R compiles functions to byte code after a couple of calls (the just-in-time compiler, enabled by default since R 3.4.0, which NEWS says will not compile code that contains explicit calls to `browser()`, to support single stepping from that call). The browser help page adds that for byte-compiled functions interrupted by `browser()`, `n` and `s` are equivalent to `c`, and the `debug()` help page that when debugging is enabled on a byte-compiled function the interpreted version is used until debugging is disabled.

[[debug]]
== Stepping through a function: `debug()`, `debugonce()` and `undebug()`

`browser()` needs an edit. `debug(fun)` sets a flag on a function so that every time it is called, the body is executed one statement at a time with the browser active before each statement; no source change, so it works for functions in packages and for code you did not write (https://cran.r-project.org/doc/manuals/r-release/R-lang.html#debug_002fundebug[R-lang: debug/undebug]). `undebug(fun)` removes the flag, `debugonce(fun)` sets a flag that the next call clears, and `isdebugged(fun)` asks whether the flag is set. The same commands work at the prompt as in `browser()`; the prompt appears before each statement, which is printed as `+debug at #n: ...+` (or `+debug: ...+` when the function has no source reference).

What the transcript shows, in order. `debug(late_days)` sets the flag and `isdebugged()` confirms it. The call prints `debugging in:` with the call, then the whole body once as `+debug at #1: {...}+`, and waits. `n` runs the `+{+` and stops before the first statement. `s` steps into `days_out()`, which was not flagged: stepping into a call opens a second `debugging in:` header with its own body. `where` shows two frames, `days_out()` on top, with its location in the caller (`where 1 at #2:`). `f` finishes `days_out()`: the browser prints `exiting from:` and stops at the next statement of the caller, whose variable `days` is now `-3`. === `debugonce()`

`debugonce(fun)` clears itself on the first call. It is the version to use when the function is called many times and only one call matters, or to avoid forgetting `undebug()`. Its flag is not the one `isdebugged()` reports, and `undebug()` does not clear it:

[[trace]]
== Inserting code without editing: `trace()`

`trace()` goes further than `debug()`. It builds a modified version of a function, with extra code inserted at the start, before chosen statements or on exit, and assigns it back where the original was found; `untrace()` restores the original. The help page calls it a generalization of `debug()` implemented differently. The inserted code, the tracer, can be a call to `browser()` or `recover()`, but also any expression: a `cat()` that prints a variable, a condition that stops only when something is wrong, an assignment that saves a value in the global environment. The R Language Definition describes the plainest use: with only a function name, `trace()` prints the call every time the function is evaluated (https://cran.r-project.org/doc/manuals/r-release/R-lang.html#trace_002funtrace[R-lang: trace/untrace]). The arguments are:

[cols="1,6",options="header"]
|===
|Argument |Meaning
|`what` |The function to trace, as a name or a string, possibly quoted with `quote()`. Several functions can be traced at once with a vector of quoted names or an `expression()`.
|`tracer` |A function, whose name is used and which is called with no arguments, or an unevaluated expression. `browser` and `recover` are the usual function tracers.
|`exit` |The same, evaluated when the function exits, through the `on.exit` mechanism. `returnValue()` gives the value about to be returned.
|`at` |A numeric vector, or a list of vectors, of steps of the function body; the tracer runs just before those steps instead of on entry. It works only if the body is a `+{+` block.
|`print` |If `TRUE`, the default, a descriptive line is printed before the tracer runs. Use `FALSE` with an expression tracer.
|`signature` |A method signature: trace the S4 method and not the generic.
|`where` |Where to look for the function; needed for functions that are not visible from the top level, such as methods in a namespace.
|`edit` |`TRUE`, or the name of an editor: edit the function's body interactively, for loops and other places `at` cannot reach.
|===

Source: https://search.r-project.org/R/refmans/base/html/trace.html[R documentation: trace]

The numbering of `at` is a frequent stumbling block. The steps are the elements of the body as a list, so `pass:c[[[1\]\]]` is the brace itself and the first statement is step 2. The help page says not to count in the printed function and to look at `as.list(body(f))` instead, which the first block of the script does. The rest of the script shows a plain trace, an expression tracer on entry, an expression tracer at step 3, and an `exit` tracer that prints the returned value.

[source,r]
----
source("scenario.R")

                        today = shelf_today) { # nolint: object_usage_linter.
  end <- if (is.na(return_date)) today else return_date
  days <- as.integer(end - loan_date)
  if (days > loan_days) "overdue" else "ok" # nolint: object_usage_linter.
}

# Step numbers are positions in the body: [[1]] is the brace, the statements
# start at [[2]]. Count them with as.list(body(f)), not by eye.
as.list(body(loan_status))[1:3]
#> [[1]]
#> `{`
#>
#> [[2]]
#> end <- if (is.na(return_date)) today else return_date
#>
#> [[3]]
#> days <- as.integer(end - loan_date)
#>

A `trace()` call that has more than the function name returns the name of the function visibly, so the console prints it (`[1] "loan_status"`) unless the call is wrapped in `invisible()`; `untrace()` returns its argument invisibly. With `print = FALSE` only the expression's own output appears; the plain `trace(loan_status)` prints `+trace: loan_status(...)+`, the first form the manual shows with `+trace("[<-")+`. In the `at = 3` run the tracer ran before the statement that computes `days`, in the frame of the call, so it could read `end`, which the first statement had just assigned. The `exit` tracer ran as the function returned, and `returnValue()` gave `overdue`; the help page marks `returnValue()` as experimental and says that it is meaningful only during the `on.exit` processing that runs the exit tracer.

The `at` argument can also address a step nested in another step: `at = list(c(3, 4))` is the fourth step of the third step of the body. The script below takes a function with an `if` block, shows how to reach the second assignment inside it, and then shows two more arguments: `tracingState()` switches all tracing off and on without untracing, and `where` finds a function that the top level cannot see, here `ar.yw.default`, an S3 method used inside the `stats` namespace. The help page says the namespace mechanism imports the functions a package calls, so the object seen from the top level need not be the one that the package code uses, and names a function in that namespace as `where`.

=== Breakpoints from a file: `setBreakpoint()` and `findLineNum()`

`findLineNum()` finds the function and the step that contain a given line of a source file, and `setBreakpoint()` is a wrapper that calls `trace()` for it, with `browser` as the default tracer. Both read the source references that R stores when code is parsed with `keep.source = TRUE`, so the code must have been read with `source(file, keep.source = TRUE)` (the `Rscript` default is `FALSE`) or typed at an interactive prompt. The file name is matched by its base name unless `nameonly = FALSE`, and `"file.R#nn"` gives the line (https://search.r-project.org/R/refmans/utils/html/findLineNum.html[R documentation: findLineNum and setBreakpoint]). By default they search the global environment; for code inside a package namespace or for S4 methods the `envir` and `lastenv` arguments widen the search. The RStudio user guide describes its editor breakpoints in similar terms (see below).

[source,r]
----
source("scenario.R")

=== What `trace()` cannot do

The help page lists the limits. Tracing does not nest: a call to `trace()` replaces any earlier tracing of the same function, except for edited versions, and `untrace()` always restores the untraced function. The `exit` argument will not work if the function itself uses `on.exit()` without `add = TRUE`, because the existing call overrides the one `trace()` adds. Tracing a primitive works only by a special mechanism, replaces the primitive by a function of `+...+`, gives little information, and issues a warning. The traced object is saved back where the function came from, so tracing of a function in the global environment survives in a saved workspace image and goes on in the next session, where `untrace()` removes it, while functions in packages are not saved with the image, so tracing of them ends with the session. The browser reached through `trace()` is the ordinary one. Fixes in recent releases show where the edges are: `trace()` of `coerce` works correctly since R 4.5.0, `isS3stdGeneric()` (used by `debugcall()`) has recognised an S3 generic that is being traced since R 4.0.3, and R-devel, the development version that will become R 4.7.0, makes `trace()` work for functions whose class attribute has more than one string, such as S7 generics and methods, and fixes a bad call that `trace()` could insert when tracing rematched S4 methods (https://cran.r-project.org/doc/manuals/r-devel/NEWS.html[R-devel NEWS]; upcoming, not run here).

[[postmortem]]
== After the error: post-mortem debugging

`browser()`, `debug()` and `trace()` all need a second run of the program. When the failure is expensive to reproduce, the other approach is to arrange for the error itself to leave the frames behind and to look at them afterwards. Writing R Extensions puts the sequence in order: locate the error with `traceback()`, then look at a post-mortem dump with `options(error = dump.frames)` and `debugger()`, or browse the live frames with `options(error = recover)`; and when the cause is still unclear, look at what was happening just before the error with `debug()` (https://cran.r-project.org/doc/manuals/r-release/R-exts.html#Debugging-R-code[Writing R Extensions: Debugging R code]). Post-mortem debugging is good for finding out exactly what went wrong, in the words of that chapter, "but not necessarily why".

=== `options(error = recover)`

`recover()` is a function meant to be the error option. When an error reaches the top level, R prints the message and `recover()` prints the active calls as a numbered menu. Choose a number, and the browser opens in the frame of that call: the variables there are the ones the call had when the error struck. `c` leaves the browser and returns to the menu, another number browses another frame, and `0` exits. Nothing is re-run and nothing is copied, which the help page names as its advantage over `dump.frames()` when the computation involves large data. === `dump.frames()` and `debugger()`

`dump.frames()` saves the stack: the calls and the environments of the active frames, plus the last error message. Used as the error option, `options(error = dump.frames)`, it stores them in an object named `last.dump` in the workspace, and `debugger()` browses it. The signature is `dump.frames(dumpto = "last.dump", to.file = FALSE, include.GlobalEnv = FALSE)`; `to.file = TRUE` writes the dump to the file `<dumpto>.rda` instead of the workspace, and `include.GlobalEnv = TRUE` (added in R 3.4.0) also stores a copy of the global environment, which the help page calls particularly useful in a batch job. The result is a list of environments named by the calls, with class `dump.frames`. Writing R Extensions warns that such objects can be large, so remove `last.dump` when it is no longer needed. The first script shows the dump in an `Rscript` run, where installing `dump.frames` as the error option keeps execution going, as the help page notes.

=== Batch jobs: dump to a file

A batch run has nobody to ask, but the dump can be saved for later: `+options(error = quote({dump.frames(to.file = TRUE); q()}))+` is the manual's setting (https://cran.r-project.org/doc/manuals/r-release/R-exts.html#Debugging-R-code[Writing R Extensions: Debugging R code]), and the help page's setting for non-interactive sessions ends in `q(status = 1)`, so that the exit status of the job reports the failure. The expression is wrapped in `quote()` so that it is stored in the option instead of being evaluated at once, and the function is written `utils::dump.frames` so that it also works in a start-up file, where `utils` may not be attached yet. This script is meant to fail: it writes `last.dump.rda` into the working directory, prints the error and exits with status 1. That is not a defect of the example; the exit status is the point.

[source,r]
----
f <- function(x) g(x)
g <- function(x) h(x)
h <- function(x) stop("boom in h")

# A batch job cannot be debugged on the spot. Save the frames to a file and
# quit; the exit status is 1 on purpose, so a scheduler sees the failure.
options(error = quote({
  utils::dump.frames(to.file = TRUE, include.GlobalEnv = FALSE)
  q(status = 1)
}))
f(1)
#> Error in h(x) : boom in h
#> Calls: f -> g -> h
----

Source: https://search.r-project.org/R/refmans/utils/html/debugger.html[R documentation: dump.frames and debugger (a possible setting for non-interactive sessions)]

=== Letting a script continue: `catch.script.errors`

R 4.4.0 added a documented option for the other common batch need, to carry on after an error: with `options(catch.script.errors = TRUE)`, an error in a non-interactive script is reported and evaluation continues with the next top-level expression, instead of ending the run. The options help page says to use it with care; later steps may depend on the one that failed. Its help text also says that `traceback()` provides information about the error. The script shows the continuation, the traceback, and `showErrorCalls = FALSE`, which removes the `Calls:` line.

[source,r]
----
f <- function(x) g(x)
g <- function(x) stop("boom in g")

# Since R 4.4.0, catch.script.errors = TRUE lets a non-interactive script go on
# after an error: the error is reported and evaluation continues with the next
# top-level expression. Use it with care: later steps may depend on the failed
# one.
options(catch.script.errors = TRUE)
f(1)
#> Error in g(x) : boom in g
#> Calls: f -> g
cat("the script goes on\n")
#> the script goes on

# The stack of that error is available to traceback() as usual.
traceback()
#> 3: stop("boom in g")
#> 2: g(x)
#> 1: f(1)

# showErrorCalls = FALSE removes the "Calls:" summary that non-interactive
# sessions add to the error message.
options(showErrorCalls = FALSE)
f(2)
#> Error in g(x) : boom in g
cat("and on\n")
#> and on
----

Source: https://search.r-project.org/R/refmans/base/html/options.html[R documentation: options (catch.script.errors, showErrorCalls)]

The traceback has three entries because `stop()` is a call too, and the second error is reported without the `Calls:` line. The option is a switch for the whole script. For a long simulation in which a few iterations may fail, R FAQ 7.32 recommends `try()`, which returns an object of class `"try-error"`, or preferably `tryCatch()`, where the value to use for a failed step can be chosen (https://cran.r-project.org/doc/FAQ/R-FAQ.html#How-can-I-capture-or-ignore-errors-in-a-long-simulation_003f[R FAQ 7.32]); that keeps the result of the successful steps and says exactly which step is replaced.

[[warnings]]
== Finding a warning

A warning has no stack: R signals it, shows or stores a message, and the program goes on. The message names a call, but not always the useful one: `NAs introduced by coercion` below is reported as coming from `pass:c[FUN(X[[i\]\], ...)]`, the anonymous call inside `vapply()`, which says nothing about which caller was responsible. Writing R Extensions suggests turning a warning that is a clear precursor of a later error into an error, so that the usual tools work: `options(warn = 2)` does that. The `warn` option has four documented levels: negative ignores warnings, `0` is the default and stores them until the top-level call returns, `1` prints them as they occur and `2` or more turns every warning into an error; the options help page notes that, while sometimes useful for debugging, converting warnings into errors may trigger bugs and resource leaks that would not have been triggered otherwise, which is a reason to set it for a run and not for good. The first script has a warning inside `vapply()` and shows both the immediate warning and the converted one with its traceback.

[source,r]
----
# A warning whose call is not much help: it names the inner FUN, not the caller.
pages_of <- function(txt) as.integer(sub("p\\.", "", txt))

total_pages <- function(txts) {
  sum(vapply(txts, pages_of, integer(1L)), na.rm = TRUE)
}

labels <- c("320", "288 p.", "n/a")
total_pages(labels)
#> Warning in FUN(X[[i]], ...) : NAs introduced by coercion
#> [1] 608

# With warn = 2 the warning becomes an error, which stops at the offending call
# and can be inspected like any other error: here with a traceback.
options(warn = 2, error = function() {
  traceback(3)
  q(status = 0)
})
total_pages(labels)
#> Error in FUN(X[[i]], ...) :
#>   (converted from warning) NAs introduced by coercion
#> Calls: total_pages -> vapply -> FUN
#> 7: doWithOneRestart(return(expr), restart)
#> 6: withOneRestart(expr, restarts[[1L]])
#> 5: withRestarts({
#>        .Internal(.signalCondition(simpleWarning(msg, call), msg,
#>            call))
#>        .Internal(.dfltWarn(msg, call))
#>    }, muffleWarning = function() NULL)
#> 4: .signalSimpleWarning("NAs introduced by coercion", base::quote(FUN(X[[i]],
#>        ...)))
#> 3: FUN(X[[i]], ...)
#> 2: vapply(txts, pages_of, integer(1L))
#> 1: total_pages(labels)
----

Source: https://search.r-project.org/R/refmans/base/html/options.html[R documentation: options (warn)]

Under `warn = 1` R prints `pass:c[Warning in FUN(X[[i\]\], ...) :]` at once and the call completes with `[1] 608`; the label `n/a`, which is not a number, became `NA` and was dropped by `na.rm = TRUE`. Under `warn = 2` the same condition is an error, `(converted from warning)` is added to its message, and the traceback now shows the callers: `total_pages(labels)` is frame 1, `vapply()` is frame 2. Frames 4 to 7 are R's warning machinery, the `withRestarts()` that offers the `muffleWarning` restart; ignore them. Without a converted warning, two other tools find the same place. `tryCatch(warning = )` stops at the first warning and returns the condition, whose `conditionCall()` is the call that signalled it. A calling handler sees the stack and can then muffle the warning with the `muffleWarning` restart so the computation finishes, which is the way to inspect many warnings from one run:

[source,r]
----
pages_of <- function(txt) as.integer(sub("p\\.", "", txt))

total_pages <- function(txts) {
  sum(vapply(txts, pages_of, integer(1L)), na.rm = TRUE)
}

labels <- c("320", "288 p.", "n/a")

# tryCatch() unwinds first and reports where the warning was signalled.
w <- tryCatch(total_pages(labels), warning = \(w) w)
class(w)
#> [1] "simpleWarning" "warning"       "condition"
conditionMessage(w)
#> [1] "NAs introduced by coercion"
conditionCall(w)
#> FUN(X[[i]], ...)

# A calling handler sees the stack that led to the warning. Then it muffles the
# warning, so the computation continues and returns its value.
total <- withCallingHandlers(
  total_pages(labels),
  warning = \(w) {
    calls <- sys.calls()
    cat("stack when the warning was signalled:\n")
    for (cl in calls[-length(calls)]) {
      cat("  ", deparse(cl)[1L], "\n")
    }
    invokeRestart("muffleWarning")
  }
)
#> stack when the warning was signalled:
#>    withCallingHandlers(total_pages(labels), warning = function(w) {
#>    total_pages(labels)
#>    vapply(txts, pages_of, integer(1L))
#>    FUN(X[[i]], ...)
#>    .signalSimpleWarning("NAs introduced by coercion", base::quote(FUN(X[[i]],
#>    withRestarts({
#>    withOneRestart(expr, restarts[[1L]])
#>    doWithOneRestart(return(expr), restart)
total
#> [1] 608
----

[[special]]
== Special cases

=== Infinite recursion

The error `evaluation nested too deeply: infinite recursion / options(expressions=)?` is raised when the number of nested expressions reaches the limit set by `options(expressions =)`, 5000 by default, and the manual's advice is to lower it, for example to 500, and run again so that the traceback is short. R 4.2.0 made stack-overflow errors conditions that inherit from `stackOverflowError`. The help page lists the specific classes: `CStackOverflowError` for the C stack, `protectStackOverflowError` for the pointer protection stack, `nodeStackOverflowError` for the node stack of the byte-code engine and `expressionStackOverflowError` for the limit of nested expressions, so a handler can tell them apart (https://search.r-project.org/R/refmans/base/html/StackOverflows.html[R documentation: StackOverflows]). The help page also says that such errors can be caught by exiting handlers established with `tryCatch()`, but that calling handlers may fail because there may not be enough stack to run them, which is why the script catches the error with `tryCatch()`.

[source,r]
----
# A function that calls itself without a base case.
runaway <- function(n) runaway(n + 1L)

# The default limit, 5000 nested expressions, takes a while to reach and fills
# the traceback; a small limit finds the problem faster. Restore it afterwards.
options(expressions = 500)
err <- tryCatch(runaway(1L), error = \(e) e)
options(expressions = 5000)

conditionMessage(err)
#> [1] "evaluation nested too deeply: infinite recursion / options(expressions=)?"
class(err)
#> [1] "expressionStackOverflowError" "stackOverflowError"
#> [3] "error"                        "condition"
# R 4.2.0 and later signal a classed condition, so the stack overflow can be
# told apart from other errors in a handler.
inherits(err, "stackOverflowError")
#> [1] TRUE
----

Source: https://cran.r-project.org/doc/manuals/r-release/NEWS.html[R NEWS: Changes in R 4.2.0]

The valid values of `expressions` are 25 to 500000 according to the options help page, which also warns that increasing it may cause a segfault from overflow of the C stack. The script restores the default after catching the error, and the error is of class `expressionStackOverflowError` first, then `stackOverflowError`, `error` and `condition`.

[[methods]]
=== S3 methods

For an S3 generic, `debug(fun)` flags the generic, which does little except dispatch; the method that runs is the thing to flag. When the method is visible, `debug(format.book)` works. For a method that is not exported, use the triple colon (`debug(stats:::predict.Arima)` in the manual) or `getS3method()`. `utils::debugcall()` does the lookup for you: given a call, it sets the flag on the non-generic function, S3 method or S4 method that evaluating the call would run, based on the classes of the arguments, and `undebugcall()` clears it. It was added in R 3.4.0 together with the `signature` argument of `debug()`, and R 4.4.1 made `debugcall(S3Generic())` work when a corresponding S4 generic version is in the methods cache. The help page notes that it uses non-standard evaluation to get the call, so a variable holding a call does not work, and that for non-standard S3 generics the generic itself is debugged. It does not run the call; the idiom `eval(debugcall(summary(f)))` evaluates it afterwards.

[source,r]
----
source("scenario.R")

# out the method from the classes of the arguments and flags that one. It does
# not run the call; it returns it.
isdebugged(format.book)
#> [1] FALSE
flagged <- debugcall(format(bk))
flagged
#> format(bk)
isdebugged(format.book)
#> [1] TRUE
isdebugged(format)
#> [1] FALSE

# undebugcall() clears the flag in the same way.
undebugcall(format(bk))
isdebugged(format.book)
#> [1] FALSE
----

=== S4 methods

R FAQ 8.5, "How can I debug S4 methods?", answers in one sentence: use `trace()` with the argument `signature=` to add calls to the browser, or any other code, to the method that will be dispatched for the corresponding signature (https://cran.r-project.org/doc/FAQ/R-FAQ.html#How-can-I-debug-S4-methods_003f[R FAQ 8.5]). Writing R Extensions says that `debug()` "cannot be used for S4 methods"; that text predates R 3.4.0, which added the `signature` argument to `debug()`, `debugonce()`, `undebug()` and `isdebugged()`. Since then `debug(fun, signature = )` works, implemented with the trace machinery; later releases extended it: R 3.5.0 supports methods on any object of class `genericFunction`, including group generics, and R 4.5.0 accepts a string that names an S4 generic. The script defines a tiny S4 class (the `methods` package is attached by `Rscript`), traces a method and the `show()` method, and uses `isdebugged()` with a signature.

[source,r]
----
# Rscript attaches the methods package, which tracing by signature needs.
setClass("Book", representation(title = "character", year = "integer"))
setGeneric("age_in", function(x, ...) standardGeneric("age_in"))
#> [1] "age_in"
setMethod("age_in", "Book", function(x, ...) 2026L - x@year)
setMethod("show", "Book", function(object) {
  cat("<Book>", object@title, "\n")
})

bk <- new("Book", title = "The quiet streets", year = 1999L)
age_in(bk)
#> [1] 27

# The method that runs for a Book, not the generic, gets the tracer (R FAQ 8.5).
invisible(trace(
  "age_in",
  signature = "Book",
  tracer = quote(cat("age_in method for", class(x), "called\n")),
  print = FALSE
))
age_in(bk)
#> age_in method for Book called
#> [1] 27
untrace("age_in", signature = "Book")
age_in(bk)
#> [1] 27

# show() is an S4 generic too; autoprinting a Book calls its method.
invisible(trace(
  "show",
  signature = "Book",
  tracer = quote(cat("show method for Book\n")),
  print = FALSE
))
bk
#> show method for Book
#> <Book> The quiet streets
untrace("show", signature = "Book")

# debug() with a signature uses the trace machinery, and isdebugged() asks about
# one method rather than the generic. Pass the generic function itself, not its
# name, to undebug() when the generic lives in the global environment.
isdebugged("age_in", signature = "Book")
#> [1] FALSE
debug(age_in, signature = "Book")
isdebugged("age_in", signature = "Book")
#> [1] TRUE
isdebugged("age_in")
#> [1] FALSE
undebug(age_in, signature = "Book")
isdebugged("age_in", signature = "Book")
#> [1] FALSE
----

=== Printing and checking, the cheap tools

Not every bug needs a debugger. Output that is cheap to leave in is worth having: `message()` writes to the error stream, so it does not mix with a function's printed result and can be silenced with `suppressMessages()`; `str()` and `dput()` show what an object really is, which is often the bug, such as a `Date` that is a number with a class; and `on.exit()` reports how a function was left, including by an error. The following script uses all of them on the shelf's loan with the impossible dates.

[source,r]
----
source("scenario.R")

# Print debugging that costs little to leave in: message() writes to standard
# error, so it does not mix with the function's own printed output, and it can
# be silenced with suppressMessages().
late_days <- function(loan_date, return_date, verbose = FALSE) {
  days <- as.integer(return_date - loan_date)
  if (verbose) {
    message(sprintf("late_days: %s -> %s = %d days", loan_date, return_date,
                    days))
  }
  max(days - loan_days, 0L) # nolint: object_usage_linter.
}
late_days(loans$loan_date[12], loans$return_date[12], verbose = TRUE)
#> late_days: 2025-04-23 -> 2025-04-20 = -3 days
#> [1] 0
suppressMessages(
  late_days(loans$loan_date[12], loans$return_date[12], verbose = TRUE)
)
#> [1] 0

# str() and dput() show what an object really is, which is often the bug.
str(loans[12, ])
#> 'data.frame':	1 obs. of  5 variables:
#>  $ loan_id    : chr "L012"
#>  $ isbn       : chr "9780013001331"
#>  $ member     : chr "Chloe Martin"
#>  $ loan_date  : Date, format: "2025-04-23"
#>  $ return_date: Date, format: "2025-04-20"
dput(loans$return_date[12])
#> structure(20198, class = "Date")
dput(unclass(loans$return_date[12]))
#> 20198

# on.exit() reports how a function left, including by an error.
checked <- function(x) {
  on.exit(cat("left checked() with x =", x, "\n"), add = TRUE)
  if (x < 0) stop("negative input")
  sqrt(x)
}
checked(4)
#> left checked() with x = 4
#> [1] 2
try(checked(-1), silent = TRUE)
#> left checked() with x = -1
----

Source: https://search.r-project.org/R/refmans/base/html/message.html[R documentation: message]

`dput(loans$return_date[12])` shows `structure(20198, class = "Date")`, and `+dput(unclass(...))+` the bare number of days since 1970-01-01. The `on.exit()` line is printed in both runs, also in the one that ends in an error; xref:programming-languages/r/functions.adoc[Functions] describes `on.exit()` and its `add` argument. A `stopifnot()` placed where a value must satisfy a condition turns a silent wrong result into an error at the earliest line that can detect it, and the stack then points there; that technique is the subject of xref:programming-languages/r/defensive-programming-and-input-validation.adoc[Defensive Programming and Input Validation].

== Debugging in an IDE

RStudio and Positron do not have a debugger of their own; they are front ends to the tools above, and everything they do can be reproduced at a plain console. This section is documented, not run: it is based on the RStudio user guide (the version 2026.10.0 Debugging chapter) and on the Ark README for Positron, both read on 2026-10-20, and the screenshots are not reproduced. The wording of buttons and menus changes between releases, so check the documentation of the release you have.

=== RStudio

The user guide organises debugging around the ways to enter debug mode (https://docs.posit.co/ide/user/ide/guide/code/debugging.html[RStudio user guide: Debugging]).

* An editor breakpoint is set by clicking to the left of a line number, or with `Shift+F9` on the line. It takes effect immediately and does not change the code: it works by injecting tracing code into the function object, which is the `setBreakpoint()` mechanism described above, and a function that holds a breakpoint is marked with a red dot in the Environment pane. If the function object does not exist yet, or no longer matches the editor because the file changed since `source()` was last called, the breakpoint is deferred and shown as a hollow red circle; in most cases `source()` on the file resolves it.
* A `browser()` call is the other kind of breakpoint. It is part of the code, so it takes effect only when the code is sourced, rebuilt or reloaded, but it works where editor breakpoints cannot, and with an `if` around it gives a conditional breakpoint, such as stopping at iteration 512 of a loop.
* `debugonce()` and `debug()` flag a function, for code with no local source file, such as `debugonce(devtools::install)`; the guide does not recommend leaving `debug()` set.
* On error: the Debug menu has an On Error setting whose values include the Error Inspector and Break in Code. RStudio does not start the debugger if none of your own code is on the stack, so that errors deep inside other packages do not open it; a Global Options check box (the guide names "Use debug error handler only when my code contains errors") turns that filter off. As discussed above, the guide's `options(error = browser())` overrides the Debug menu setting. Older articles describe two buttons of the Error Inspector, Show Traceback and Rerun with Debug; the current user guide does not document them, so they are not described here.

When code is stopped, the console prompt becomes `Browse[1]>`, the Environment pane shows the environment of the running function instead of the global one, with arguments that have not been evaluated shown in gray as promises, and a drop-down list shows the chain of enclosing environments. The traceback shares the space of the Environment pane; the guide says it shows the call stack and is called the traceback for symmetry with `traceback()`, that clicking a frame shows its variables and code without changing the active environment of the console (use `recover()` for that), and that internal functions are hidden unless View Internals is ticked. The code window highlights the line about to run. The console toolbar sends the same commands as the table in the `browser()` section:

[cols="3,2,5",options="header"]
|===
|Command |Shortcut |Description
|`n` or Enter |`F10` |Execute the next statement.
|`s` |`Shift+F4` |Step into the function.
|`f` |`Shift+F6` |Finish the function or loop.
|`c` |`Shift+F5` |Continue running.
|`Q` |`Shift+F8` |Stop debugging.
|===

Source: https://docs.posit.co/ide/user/ide/guide/code/debugging.html[RStudio user guide: Debugging (Debugging commands)]

The guide has a section on special circumstances, and they follow from how the mechanisms work. Breakpoints that are outside any function cannot be injected into a function object, so RStudio provides `debugSource()`, a `source()` that stops at those breakpoints; it is not recursive, so a file that is itself sourced by the debugged file is not stopped in. Package code needs an up-to-date build, and the package should be compiled with source information (`--with-keep.source`) for the breakpoints to be placed. In Shiny applications breakpoints work only inside the `shinyServer` function, not in `ui.R` or `global.R`, and a lot of Shiny infrastructure shows in the call stack before control reaches your code. In R Markdown breakpoints do not currently work in chunks, so use `browser()`; the Knit button renders in a separate R process, where the debugger cannot reach, so call `rmarkdown::render()` from the console to render in the primary process; the debugger's output is not shown while knitr is capturing output, so call `sink()` at the `Browse[1]>` prompt, or set `+options(error = function() { sink(); recover() })+` in the setup chunk (which ends with a harmless "no sink to remove" warning). For Quarto documents with the knitr engine, `rmarkdown::render()` is likewise recommended, and `quarto::quarto_render()` is documented as currently not compatible with these strategies. These two use the knitr and rmarkdown packages; they were not run here.

=== Positron

Positron's R support is provided by Ark, an R kernel. Its README describes three roles: a Jupyter kernel, a Language Server Protocol server for completions and diagnostics, and a Debug Adapter Protocol server for "sophisticated step-debugging of R functions" that manages source references, creating them on the spot if needed, and integrates with the kernel to step through R code and inspect local variables (https://github.com/posit-dev/ark[Ark README]). The same README, as read on 2026-10-20, says that support for breakpoints is currently missing and that `debug()`, `debugonce()` or `browser()` can be used to drop into the debugger. That is a statement with a date: the navigation of the Positron documentation pages that were read lists a "Debugging R code" guide, which was not among the pages checked, and the release notes should be consulted for the version in use before relying on either. The Positron features page presents the Variables pane as the place to examine variables, objects and environments while debugging. The R functions on this page are ordinary R and are available in the Positron console as in any other front end; `debug()`, `debugonce()` and `browser()` are the ones the README names. See xref:programming-languages/r/ides-and-the-r-console.adoc[IDEs and the R Console] for the other front ends, including the community debugger extension for Visual Studio Code, and for the console-level view of the same tools.

=== Emacs and compiled code

R FAQ 6.3, "Debugging R from within Emacs", is about running the R binary under `gdb`, the GNU debugger for compiled code, from Emacs, either with the GUD library or by attaching to an inferior R process started from ESS (https://cran.r-project.org/doc/FAQ/R-FAQ.html#Debugging-R-from-within-Emacs[R FAQ 6.3]).

== Compiled code

The R debugger sees interpreted code only. When the failing code is in C, C{pp} or Fortran, Writing R Extensions covers the tools in its chapter on debugging compiled code: a crash prints "caught segfault" and a traceback of the R calls active, a core dump can be examined with `gdb`, R can be run under the debugger with `R -d gdb --vanilla`, an interrupt (Ctrl-C) while a long computation runs drops into the debugger so that `where` shows where the time goes, and a debugger can be attached to a running process with `gdb -p pid`. Compiled code loaded dynamically can have breakpoints set in it only after it is loaded, so the procedure is to start R under the debugger, load the shared object with `dyn.load()` or `library()`, send an interrupt, set the breakpoints and continue. `options(CBoundsCheck = TRUE)` makes `.C` and `.Fortran` check whether compiled code writes beyond the arguments it is passed (https://cran.r-project.org/doc/manuals/r-release/R-exts.html#Debugging-compiled-code[Writing R Extensions: Debugging compiled code]). R FAQ 8.2 gives the short version (https://cran.r-project.org/doc/FAQ/R-FAQ.html#How-can-I-debug-dynamically-loaded-code_003f[R FAQ 8.2]). Writing compiled extensions is covered in xref:programming-languages/r/interfacing-c-cpp-and-fortran.adoc[Interfacing C, C{pp} and Fortran].

== A debugging workflow

. Read the message, and note the call and the text. If the call is `NULL` or unhelpful, the stack is what you need.
. Get the stack: `traceback()` at the prompt, `+options(error = function() { traceback(3); q(status = 0) })+` in a script, or `options(catch.script.errors = TRUE)` to see several failures in one run.
. If the stack names the function but not the cause, stop the program there while it is running: `options(error = recover)` to look at the frames after the error, or `debugonce()` on the function and run again to step through it.
. If the bad value is produced in a loop or in many calls, use a conditional stop, `browser(expr = )`, or a `trace()` with an expression tracer that prints only the bad case.
. If the failure is a warning, set `options(warn = 2)` for the run and treat it as an error.
. If the code runs unattended, use `dump.frames(to.file = TRUE)` and `q(status = 1)` in the `error` option, and debug the dump later.
. Fix the cause, then add the check that would have caught it earlier, with `stopifnot()` or an error with a class, and remove every `browser()`, `debug()` and `trace()` before committing: `undebug()`, `untrace()` and `options(error = NULL)` are the clean-ups.
