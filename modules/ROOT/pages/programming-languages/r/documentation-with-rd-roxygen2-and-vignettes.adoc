== Rd: the documentation format of R

R objects are documented in files written in the R documentation format, Rd. Writing R Extensions describes it as a simple markup language, much of which closely resembles (La)TeX, that can be processed into a variety of formats including LaTeX, HTML and plain text. The R distribution contains more than 1400 such files, one or more per function of the base and recommended packages, and every help page you have read in R was produced from one. When a package is installed, its Rd files are parsed and stored in the library in a binary form (the `help` directory of the installed package), and `help()` renders them on demand: as text in a terminal, as HTML in the browser. That design is the reason that the same source gives a page in the console, a page on the CRAN site, a chapter of the PDF reference manual and the examples that `example()` runs.

=== The anatomy of a file

An Rd file has three parts. The header is mandatory and gives the name of the file, the topics documented, a title, a short description and the usage of the objects documented. The body (arguments, value, details, examples and so on) gives the rest, and an optional footer carries keywords. The sections are macros that start with a backslash and take their arguments in braces, and they can appear in any order. Unless a section is allowed to repeat, only the first occurrence of a standard section is kept, with a warning. This is the file that roxygen2 wrote for `normalise_isbn()` and `is_valid_isbn13()`, which share one page:

[source,text]
----
% Generated by roxygen2: do not edit by hand
% Please edit documentation in R/isbn.R
\name{normalise_isbn}
\alias{normalise_isbn}
\alias{is_valid_isbn13}
\title{Normalise and validate ISBN-13 strings}
\usage{
normalise_isbn(x)

is_valid_isbn13(x)
}
\arguments{
\item{x}{A character vector of ISBNs; \code{NA} and empty strings are allowed.}
}
\value{
\code{normalise_isbn()} returns a character vector of the same length;
\code{is_valid_isbn13()} a logical vector of the same length, \code{FALSE} for
\code{NA} and for the empty string.
}
\description{
\code{normalise_isbn()} drops everything except digits and \code{X} and upper-cases
the result, so \code{"978-0-00-100010-0"} and \code{"9780001000100"} compare equal.
\code{is_valid_isbn13()} checks that a (normalised) string has 13 digits and a
correct check digit: the digits are multiplied alternately by 1 and 3 and
the sum must be divisible by 10.
}
\examples{
normalise_isbn("978-0-00-100010-0")
is_valid_isbn13(c("978-0-00-100010-0", "9780001000101", "", NA))
}
----

Source: https://cran.r-project.org/doc/manuals/r-release/R-exts.html#Rd-format[Writing R Extensions: Rd format]

The first two lines are Rd comments (a percent sign starts a comment that runs to the end of the line) and tell a human not to edit the file. Then come the sections, in the order roxygen2 writes them. The most used ones, with the kind of text each takes, are in the table. Writing R Extensions distinguishes four kinds of input: LaTeX-like text with markup macros, `verbatim` text where nothing but the comment marker is interpreted, R-like text for code with some embedded macros, and a rare verbatim variant, used in the first argument of `+\eqn+`, `+\deqn+`, `+\figure+` and `+\newcommand+`, in which the comment marker need not be escaped.

[cols="2,4,2",options="header"]
|===
|Section |What it holds |Input
|`+\name{topic}+` |the unique name of the Rd object, normally the base name of the file; one per file; no markup, only printable ASCII; it may not contain `!`, `\|` or `@` |verbatim
|`+\alias{topic}+` |a topic that `help()` can find; one per topic documented; an alias need not be an object's name (`format.book` is an alias of the page `book-methods`) |verbatim
|`+\title{...}+` |the title; capitalised, no final period, at most about 65 characters; exactly one |LaTeX-like
|`+\description{...}+` |a short paragraph on what the objects do; mandatory except in package overview pages |LaTeX-like
|`+\usage{...}+` |the synopsis, which has to match the code exactly so that the checks can compare them; S3 methods are written `+\method{generic}{class}(args)+`, S4 methods `+\S4method{generic}{class}(args)+` |R-like
|`+\arguments{...}+` |one `+\item{name}{description}+` per argument, or several names separated by commas |LaTeX-like
|`+\value{...}+` |what the function returns; a list can be described with `+\item{name}{description}+` entries |LaTeX-like
|`+\details{...}+` |the detailed description |LaTeX-like
|`+\note{...}+`, `+\references{...}+`, `+\author{...}+`, `+\seealso{...}+` |notes, literature (with `+\doi{}+`, `+\url{}+`), the authors, pointers to related topics |LaTeX-like
|`+\examples{...}+` |code that is shown and run by `example()` and `R CMD check` |R-like
|`+\keyword{key}+`, `+\concept{term}+` |index entries; the standard keywords are listed in the `KEYWORDS` file of R; the keyword `internal` hides a page from the topic indices |verbatim
|`+\format{...}+`, `+\source{...}+`, `+\docType{...}+` |for data sets: the structure, the origin, and the type of the object (`data`, `package`, `class`, `methods`) |LaTeX-like
|`+\section{Title}{...}+`, `+\subsection{Title}{...}+` |a section of your own, and a subsection inside a section (more than three levels do not format well); extra sections are always printed before `+\note+`, `+\seealso+` and the examples, whatever their position in the source |LaTeX-like
|`+\encoding{UTF-8}+` |the encoding, on a line by itself, when the file has non-ASCII characters |verbatim
|===

Source: https://cran.r-project.org/doc/manuals/r-release/R-exts.html#Documenting-functions[Writing R Extensions: Documenting functions]

An Rd file therefore has the same skeleton as every help page you have read in R: the title, Description, Usage, Arguments, Details, Value, Note, References, See Also and Examples. Writing R Extensions also states a rule for the title: capitalised, without a final period, no more than about 65 characters. R 4.4.0 made `tools::checkRd()` report titles and section names that end in a period; `R CMD check` ignores that finding unless the environment variable `+_R_CHECK_RD_CHECKRD_MINLEVEL_+` is set to `-5` or smaller (the NEWS entry is in the version notes below).

=== Looking at the parse tree

Rd is parsed by `tools::parse_Rd()`, which returns a list of class `Rd` in which every element carries its macro in the attribute `Rd_tag`. That is the structure that every converter and every check below walks. The script parses `man/book.Rd` (written by roxygen2 from `R/book.R`) and looks at the top level: the two comment lines, then `+\name+`, three `+\alias+` entries and the sections.

[source,r]
----
# Parse man/book.Rd (written by roxygen2) and look at the parse tree.
rd <- tools::parse_Rd("man/book.Rd")
class(rd)
#> [1] "Rd"
tags <- vapply(rd, \(x) attr(x, "Rd_tag"), character(1))
tags[tags != "TEXT"]
#>  [1] "COMMENT"       "COMMENT"       "\\name"        "\\alias"
#>  [5] "\\alias"       "\\alias"       "\\title"       "\\usage"
#>  [9] "\\arguments"   "\\value"       "\\description" "\\examples"
#> [13] "\\seealso"     "\\concept"
length(rd)
#> [1] 28

# The text of an element: its leaves pasted together.
rd_text <- \(x) paste(vapply(x, as.character, character(1)), collapse = "")

# The \alias entries are what help() searches.
vapply(rd[tags == "\\alias"], rd_text, character(1))
#> [1] "book"          "new_book"      "validate_book"

# The title and the concept index entry as plain text.
rd_text(rd[[which(tags == "\\title")]])
#> [1] "The book class"
rd_text(rd[[which(tags == "\\concept")]])
#> [1] "book class"

# The parts of the usage section, as the parser sees them.
usage <- rd[[which(tags == "\\usage")]]
attr(usage, "Rd_tag")
#> [1] "\\usage"
attr(usage[[2L]], "Rd_tag")
#> [1] "RCODE"
----

Source: https://search.r-project.org/R/refmans/tools/html/parse_Rd.html[R documentation: parse_Rd]

The three aliases of the page `book` are `book`, `new_book` and `validate_book`: `help("new_book")` finds this page because of that alias, not because of the name of the file. The same holds for `format.book` and the page `book-methods`, which the section on help lookup below shows. The technical description of the parser is the document "Parsing Rd files" on the R developer site (https://developer.r-project.org/parseRd.pdf[Parsing Rd files]).

=== Rd markup in one file

The macros for marking text, building lists and tables, linking, writing mathematics and running code are the part of Rd that people look up. This is a hand-written Rd file that uses most of them, rendered as text with `tools::Rd2txt()`. The script writes the Rd text to a temporary file with a raw string, so that the page shows the Rd as it is typed, and then converts it, running the three stages of evaluation of `+\Sexpr+` (explained below). The option `underline_titles = FALSE` only keeps the backspace-based underlining of the section titles, which a terminal shows and a page cannot, out of the output.

[source,r]
----
# A hand-written Rd file that uses most of the markup macros, rendered as text.
rd_file <- file.path(tempdir(), "loan_rules.Rd")
writeLines(r"---(\newcommand{\isbn}{\code{ISBN-13}}
\name{loan_rules}
\alias{loan_rules}
\title{Loan Rules of the Shelf Library}
\description{
  The loan period is \code{getOption("shelf.loan_days")} days; set it
  with \code{\link{options}}, or with the environment variable
  \env{SHELF_LOAN_DAYS} in \file{.Renviron}. See \pkg{shelf},
  \emph{emphasis}, \strong{strong text} and \sQuote{single} or
  \dQuote{double} quotes; \verb{x[[1]]} is shown verbatim.
  A book is identified by its \isbn{} (see \doi{10.32614/R.manuals}).
}
\details{
  \itemize{
    \item A loan is overdue after \eqn{d > 21} days.
    \item Members may hold \eqn{n \le 5}{n <= 5} loans.
  }
  \enumerate{
    \item Take the book out.
    \item Return it.
  }
  \describe{
    \item{late}{returned after the loan period.}
    \item{out}{not returned yet.}
  }
  \tabular{lrr}{
    genre \tab loans \tab overdue \cr
    Fiction \tab 12 \tab 6 \cr
    Poetry \tab 4 \tab 1

  See \url{https://example.com/shelf} and
  \href{https://example.com/shelf/rules}{the rules}.
  This text is for the console: \ifelse{text}{plain text}{rich text}.

\section{Evaluated when the page is built}{

Every macro on the page has a purpose, and the plain-text conversion shows what happens to each one. The marking macros are logical, not physical: `+\code{}+` says "a piece of R code or the name of an R object" and each output format chooses the typography (typewriter font in HTML and PDF, typographic quotes in text). `+\emph{}+` and `+\strong{}+` emphasise (the text conversion uses underscores and asterisks), `+\sQuote{}+` and `+\dQuote{}+` quote without hard-wiring the quotation marks, `+\pkg{}+` names a package, `+\file{}+` a file, `+\env{}+` an environment variable, `+\option{}+` a command-line option, `+\command{}+` a command, `+\email{}+` an address, `+\var{}+` a metasyntactic variable, `+\kbd{}+` keyboard input, `+\samp{}+` a literal sequence of characters, `+\dfn{}+` a defining use of a term, `+\cite{}+` a reference without a link, `+\acronym{}+` and `+\abbr{}+` abbreviations. `+\verb{}+` and `+\preformatted{}+` keep their text exactly, and `+\url{}+` and `+\href{url}{text}+` write links to the web (the first argument of both is verbatim, with percent signs and braces escaped by a backslash). Two macros are built in for text that cannot be written plainly: `+\R+` for the name of the language and `+\ldots+` or `+\dots+` for an ellipsis; both should be followed by `+{}+` unless a space follows.

Lists and tables have three list macros and one table macro. `+\itemize+` and `+\enumerate+` take `+\item+` followed by a space and the text, with no braces; `+\describe+` takes `+\item{label}{body}+` with two arguments, exactly like the entries of `+\arguments+` and `+\value+`; `+\tabular{lrr}{...}+` takes the alignment of each column (`l`, `r` or `c`) and then lines separated by `+\cr+` with fields separated by `+\tab+`. There must be the same number of fields on each line as columns, and there is no white space between `+\tabular+` and its first argument. Mathematics uses `+\eqn{latex}{ascii}+` for inline formulas and `+\deqn{latex}{ascii}+` for displayed ones: the first argument is typeset by KaTeX or MathJax in HTML help (from R 4.2.0) and by LaTeX in the PDF manual, the second is what the plain-text help shows, and a single argument serves for both when the LaTeX source is readable as text (the text converter also knows the relations `+\le+`, `+\ge+` and `+\ne+`). In the output above `+\eqn{d > 21}+` has the one-argument form and `+\eqn{n \le 5}{n <= 5}+` has two.

Three macros decide what an output format sees. `+\if{format}{text}+` and `+\ifelse{format}{text}{alternate}+` select by output format (`example`, `html`, `latex` or `text`; `TRUE` matches all formats); `+\out{literal}+` writes its text unescaped and is used inside `+\if{html}{}+` to emit raw HTML; and a block between a line `+#ifdef windows+` (or `+#ifdef unix+`, or `+#ifndef+` with either) and a line `+#endif+` is included or excluded for one operating system before the page is processed. Platform-specific Rd files can also live in `man/unix` and `man/windows` subdirectories. In the console conversion above, `+\ifelse{text}{plain text}{rich text}+` produced "plain text".

=== Links and cross-references

`+\link{foo}+`, usually inside `+\code{}+`, links to the help page that has `foo` as an alias, in this or any installed package; whitespace is stripped when an alias is stored but not when a link target is looked up. There are four forms, and the second matters for S3 and S4 classes, which have no function of their own to link to.

[cols="3,5",options="header"]
|===
|Form |Meaning
|`+\link{foo}+` |link to the topic `foo`, displayed as `foo`
|`+\link[=dest]{name}+` |link to the topic `dest`, displayed as `name`; the way to refer to an S3 class (`+\link[=terms.object]{terms}+`) or an S4 class (`+\link[=abc-class]{abc}+`); since R 4.5.0 the displayed text may contain markup such as `+\eqn{}+`
|`+\link[pkg]{foo}+`, `+\link[pkg:bar]{foo}+` |link to the topic `foo` (or `bar`) in package `pkg`; the package must be in `Depends`, `Imports`, `Suggests` or `Enhances`; since R 4.1.0 this is a link to the topic (before that, to a file `foo.html`)
|`+\linkS4class{abc}+`, `+\linkS4methods{xyz}+` |shorthand for the S4 class `abc` and for the methods of the generic `xyz`; the second is new in R 4.6.0
|===

Source: https://cran.r-project.org/doc/manuals/r-release/R-exts.html#Cross_002dreferences[Writing R Extensions: Cross-references]

A link to a topic that does not exist is not an error when the page is converted; it is reported by `R CMD check` ("checking Rd cross-references"), and roxygen2 reports it while documenting. Both messages appear in the roxygen2 sections below. `+\concept{term}+` adds an index term for `help.search()` and `??`, but a `+\concept+` cannot be the target of a link: link targets are aliases. Vignettes can be linked from help pages with relative URLs of the form `../doc/file.html`, and a help page can link to a vignette of another package with `../../pkg/doc/file.html`.

=== Examples: what is shown, what is run

The `+\examples+` section is both documentation and a test: its code is shown on the page, run by `example()` and run by `R CMD check`, so an example must be executable on any machine, without Internet access, without interaction and without writing outside a temporary directory. Four macros control that. They appear in the output of the previous script: the code in `+\dontrun{}+` is shown (as a comment, `## Not run:`) but never run; `+\donttest{}+` code is shown and run by `example()` but, by default, not by `R CMD check`; `+\dontshow{}+` code is run but not shown (it used to be called `+\testonly+`, which is still accepted); and `+\dontdiff{}+` (new in R 4.4.0) marks code whose output is ignored when the check output is compared with a saved reference output.

R 4.0.0 changed what `\donttest` means for a CRAN submission: `R CMD check --as-cran` now runs the `\donttest` examples too, instead of telling the tester to run them (setting `+_R_CHECK_DONTTEST_EXAMPLES_+` to a false value turns that off during development). So `\donttest` no longer hides slow or fragile examples from the CRAN checks; it only hides them from a plain `R CMD check`. The documentation recommends it only for code that may fail in circumstances that are hard to test for, with a comment that explains why. Code that needs a service, a key or a program that may be missing is better guarded by a condition, which is what the roxygen2 tag `+@examplesIf+` below writes. Examples that read from `stdin`, such as `scan()`, cannot run, because `example()` uses `source()`. Data for examples comes from random numbers or from the standard data sets (`data()`).

Source: https://cran.r-project.org/doc/manuals/r-release/R-exts.html#Documenting-functions[Writing R Extensions: Documenting functions, the examples section]

=== Dynamic pages: \Sexpr and \RdOpts

`+\Sexpr[options]{code}+` evaluates R code inside an Rd file and inserts the result. The options follow Sweave's format: `eval` (default `TRUE`), `echo` (default `FALSE`), `keep.source` (default `TRUE`), `results` (`text`, the default, applies `as.character()` to the value; `verbatim` shows the printed value; `rd` parses the result as Rd and inserts it, which is how aliases can be computed; `hide`), `strip.white` and `stage`. `stage` is the important one: `stage=build` runs when the source tarball is built, `stage=install` (the default) when the package is installed from source, and `stage=render` each time the page is displayed. The order is always build, then the `#ifdef` conditionals, then install, then render, and code runs once in each stage, so a `+\Sexpr[results=rd]+` can output a `+\Sexpr+` for a later stage but not for the current or an earlier one. `+\RdOpts{}+` sets new defaults for the `+\Sexpr+` that follow it. The file above has a build-stage and a render-stage `+\Sexpr+` in one sentence. The first conversion ran all three stages with `stages = c("build", "install", "render")` and printed "26 letters" and "R"; the second, at the end of the script, ran a small file with the default `stages = "render"` and left the build-stage macro exactly as written, because for a package that stage is over by the time the page is rendered. In a package the build stage is the way to compute something once, when the tarball is made (the R 4.6.0 macros for bibliographic citations are built that way), the install stage fits text that depends on the installation, and the render stage text that must be current every time the page is shown. Since R 4.6.0 the error message of a failed `+\Sexpr+` includes the call of the original condition, and warnings include the Rd source location.

=== User-defined macros, encoding and figures

`+\newcommand+` and `+\renewcommand+` define macros inside an Rd file. They take two verbatim arguments, the name of the new macro with its backslash and its definition, and the definition may use placeholders `#1` to `#4`; the number of arguments is the highest placeholder seen, and the arguments are substituted as text before the result is parsed. `+\newcommand+` refuses a name that is already defined, `+\renewcommand+` replaces one, built-in macros included. The file above defined `+\isbn+` as `+\code{ISBN-13}+` in its first line. R ships a set of system macros in the file `share/Rd/macros/system.Rd` that are available in every Rd file: `+\doi{}+` for a digital object identifier, `+\CRANpkg{}+` for a package on CRAN, `+\sspace+` for a space after a period that does not end a sentence, `+\packageTitle{}+` and its relatives (`+\packageDescription+`, `+\packageAuthor+`, `+\packageMaintainer+`, `+\packageDESCRIPTION+`, `+\packageIndices+`) that read the fields of `DESCRIPTION` when the package is built, and, new in R 4.6.0, `+\manual{name}{node}+` to refer to a section of one of the R manuals. Macros that several pages of a package share go into an Rd file in `man/macros`, which is installed into `help/macros`, and a package can use the macros of another by naming it in the `RdMacros` field of `DESCRIPTION`.

An Rd file with a character outside ASCII needs an `+\encoding{}+` line, unless `DESCRIPTION` declares `Encoding: UTF-8`, which `shelf` does; the file is converted to UTF-8 before parsing and UTF-8 is the preferred encoding. The manual advises avoiding non-ASCII characters in Rd files wherever possible, and also the symbols `<`, `>`, `$`, `^`, `&`, `|`, `@`, `~` and `*` outside verbatim environments, because some fonts used for PDF manuals do not render them; `tools::showNonASCIIfile()` finds the offending bytes. For one word that must be written differently where an encoding is unavailable, `+\enc{Jöreskog}{Joreskog}+` gives the encoded and the ASCII form.

Figures for help pages go into `man/figures`, and `+\figure{file}{alternate text}+` includes one: the file types `.jpg`, `.jpeg`, `.pdf`, `.png` and `.svg` in that directory are copied to the `help/figures` directory of the installed package. The text conversion shows the alternate text instead. PDF figures show in the PDF manual and not in a browser, and SVG the other way round, which is why roxygen2 has the option `restrict_image_formats` for images added through markdown.

Source: https://cran.r-project.org/doc/manuals/r-release/R-exts.html#User_002ddefined-macros[Writing R Extensions: User-defined macros]

=== Special characters

Four characters need care in Rd. A percent sign starts a comment in every kind of text and has to be written `\%`, except in the rare verbatim variant. A backslash is written `\\`. A brace that is not balanced has to be escaped, and all of `%`, `{`, `}` and `\` must be escaped in LaTeX-like text. In R-like text (the usage and examples sections) quoted strings are handled differently: braces inside a string do not need escapes. The mistake that costs most time is the percent sign, because the rest of the line, including a closing brace, disappears into the comment. `tools::checkRd()` is the tool that finds these mistakes, and the next script feeds it six small broken files and shows what it reports for each. It writes every file to a temporary directory and removes that directory from the messages.

[source,r]
----
# tools::checkRd() on small broken Rd files; each case shows what R reports.
check_rd <- \(label, lines) {
  f <- file.path(tempdir(), "broken.Rd")
  writeLines(lines, f)
  res <- NULL
  msg <- capture.output(
    res <- tryCatch(tools::checkRd(f), error = \(e) conditionMessage(e)),
    type = "message"
  )
  out <- capture.output(print(res))
  # Keep the temporary directory out of the messages.
  cat(label, ":\n", sep = "")
  cat(sub(paste0(tempdir(), "/"), "", c(msg, out), fixed = TRUE), sep = "\n")
}

check_rd("no title", c("\\name{a}", "\\alias{a}", "\\usage{a()}"))
#> no title:
#> [1] "broken.Rd: Sections \\title, and \\name must exist and be unique in Rd files"

check_rd("unclosed brace", c(
  "\\name{a}", "\\alias{a}", "\\title{T}",
  "\\description{An unclosed {brace.", "}"
))
#> unclosed brace:
#> prepare_Rd: broken.Rd:6: unexpected END_OF_INPUT '
#> '
#> checkRd: (-1) broken.Rd:4-5: Lost braces; missing escapes or markup?
#>      4 | \description{An unclosed {brace.
#>        |                          ^

check_rd("macro without its backslash", c(
  "\\name{a}", "\\alias{a}", "\\title{T}",
  "\\description{Use code{x} here.}"
))
#> macro without its backslash:
#> checkRd: (-1) broken.Rd:4: Lost braces
#>      4 | \description{Use code{x} here.}
#>        |                      ^

check_rd("misspelt macro", c(
  "\\name{a}", "\\alias{a}", "\\title{T}",
  "\\description{Use \\codee{x} here.}"
))
#> misspelt macro:
#> prepare_Rd: broken.Rd:4: unknown macro '\codee'

check_rd("unescaped percent sign", c(
  "\\name{a}", "\\alias{a}", "\\title{T}",
  "\\description{It is 50% done.}", "\\examples{x <- 1}"
))
#> unescaped percent sign:
#> prepare_Rd: broken.Rd:5: unexpected section header '\examples'
#> prepare_Rd: broken.Rd:6: unexpected END_OF_INPUT '
#> '
#> checkRd: (-1) broken.Rd:5: Lost braces; missing escapes or markup?
#>      5 | \examples{x <- 1}
#>        |          ^

check_rd("title ending in a period, item with two arguments", c(

  "\\details{\\itemize{\\item{x}{y}}}"
))
#> title ending in a period, item with two arguments:
#> checkRd: (-5) broken.Rd:3: \title should not end in a period
#> checkRd: (-3) broken.Rd:5: Lost braces
#>      5 | \details{\itemize{\item{x}{y}}}
#>        |                        ^
#> checkRd: (-1) broken.Rd:5: Lost braces in \itemize; meant \describe ?
----

Source: https://search.r-project.org/R/refmans/tools/html/checkRd.html[R documentation: checkRd]

The messages are worth learning to read. A file without a `+\title+` fails the structural check at once. An unclosed brace gives a parser message ("unexpected END_OF_INPUT") followed by "Lost braces" with the offending line and a caret. A macro without its backslash (`+code{x}+` for `+\code{x}+`) is not an error for the parser, since `+code{x}+` is just text followed by a braced group, and is reported as "Lost braces". A misspelt macro is "unknown macro" at parse time. The unescaped percent sign swallowed the closing brace of `+\description+` and the `+\examples+` section that followed, so the parser reports an "unexpected section header" and then the lost braces. The last file has two further findings: the number in parentheses is the level of the message (-5 is the lowest, for style), and the title ending in a period only appears at that low level; "Lost braces in \itemize; meant \describe ?" is the message for `+\item{x}{y}+` used inside `+\itemize+`, where `+\item+` takes no braces. In a package, `R CMD check` runs these checks for every file in `man` in the step "checking Rd files".

=== Writing Rd by hand with prompt()

`prompt()` writes an Rd skeleton for a function or data frame that you then edit, with comments (`%%`) that tell you what to write where. == roxygen2: Rd files from comments

Rd is a good format for a machine and a poor one to maintain: the usage section has to repeat the signature of the function exactly, every argument has to be described in a separate block, and each of these is far from the code that changes. roxygen2 moves the documentation into the R source, in special comments that start with `+#'+` and sit immediately above the object they document, and writes the Rd files, the `NAMESPACE` and the `Collate` field from them. The usage section is taken from the function itself, so it cannot disagree with the code, and the arguments, the exports and the documentation of a function are in one place. roxygen2 is a CRAN package (8.1.1 on 2026-10-08); the 8.0.0 release of 2026-05-01 is the one that requires R 4.1 and moved the package's settings into `Config/roxygen2/` fields of `DESCRIPTION`, as the section on `DESCRIPTION` below explains.

=== Blocks, tags and the first paragraphs

A block is a run of `+#'+` lines. The first paragraph is the title, the second is the description, and any further paragraph is the details, unless a tag says otherwise. A tag is a word that starts with `@` at the start of a line, and everything up to the next tag belongs to it. The example below uses a throwaway package in a temporary directory, so that nothing but the generated files is involved: one function with a title, a description with markdown code and a link, a details paragraph with a list, a parameter tag that documents two parameters, a return value, an example, and the two namespace tags `+@importFrom+` and `+@export+`. The script runs `roxygen2::roxygenise()` and prints the Rd file and the `NAMESPACE` that came out.

[source,r]
----
# A throwaway package with one documented function, turned into Rd by roxygen2.
pkg <- file.path(tempdir(), "demo")
dir.create(file.path(pkg, "R"), recursive = TRUE)
writeLines(c(
  "Package: demo",
  "Title: A Demonstration",
  "Version: 0.0.1",
  "Description: Shows what roxygen2 writes.",
  "License: MIT",
  "Encoding: UTF-8",
  "Config/roxygen2/markdown: TRUE"
), file.path(pkg, "DESCRIPTION"))

writeLines(r"(#' Take a book out
#'
#' Records a loan of `book` to `member`. The loan is overdue after
#' `days` days. Summarise loan lengths with [stats::median()].
#'
#' The second paragraph is the *details* section. A list:
#' * one
#' * two
#'
#' @param book A book (a string).
#' @param member,days Name of the member and length of the loan.
#' @returns A list with the three inputs.
#' @examples
#' loan_book("Dune", "Ana")
#' @importFrom stats median
#' @export
loan_book <- function(book, member, days = 21L) {
  list(book = book, member = member, days = days)
}
)", file.path(pkg, "R", "loan.R"))

invisible(capture.output(roxygen2::roxygenise(pkg), type = "message"))
cat(readLines(file.path(pkg, "man", "loan_book.Rd")), sep = "\n")

#> A list with the three inputs.

#> \description{
#> Records a loan of \code{book} to \code{member}. The loan is overdue after

Source: https://roxygen2.r-lib.org/articles/rd-functions.html[roxygen2 package documentation: Documenting functions]

The mapping is the one to remember. The title went to `+\title+`, the first paragraph after it to `+\description+`, the second to `+\details+`. `+@param member,days+` became one `+\item{member, days}+` entry, because a tag can document several arguments with one text. `+@returns+` became `+\value+`. The `+\usage+` section was not written by hand: roxygen2 took it from the function. The markdown in the description was translated (`+`book`+` to `+\code{book}+`, `+[stats::median()]+` to a link to the `median` topic in `stats`, `+*details*+` to `+\emph+`, the list to `+\itemize+`), and the two namespace tags went to the `NAMESPACE` file, not to the Rd file: `export(loan_book)` and `importFrom(stats,median)`. The tag `+@importFrom stats median+` is there only to show the directive; in a real package it sits in the block of a function that calls `median()`.

=== What roxygenise() does

`roxygen2::roxygenise()` (spelt `roxygenize()` too) takes a package directory, loads the package code, parses the blocks and runs the roclets. A roclet is a processor of the parsed blocks that produces one kind of output: `rd` writes `man/*.Rd`, `namespace` writes `NAMESPACE`, `collate` writes the `Collate` field of `DESCRIPTION` from the `+@include+` tags. Those three run by default. By default the package is loaded with pkgload, and the code is evaluated, so that roxygen2 knows what a function, a dataset or a class looks like. `devtools::document()` is the usual front end: it calls `roxygenise()` and prints its progress. `roxygen2::needs_roxygenize()` (new in 8.0.0) answers cheaply whether the Rd files are older than their sources. Every file roxygen2 writes starts with the comment lines "Generated by roxygen2: do not edit by hand" and "Please edit documentation in R/book.R", and roxygen2 only rewrites files that carry that header. The script reads the settings of `shelf` as roxygen2 sees them.

[source,r]
----
# The options roxygen2 reads for the package, and where they come from.
read.dcf("DESCRIPTION", fields = c("Roxygen", "Config/roxygen2/version"))
#>      Roxygen                 Config/roxygen2/version
#> [1,] "list(markdown = TRUE)" "8.1.1"
opts <- roxygen2::load_options(".")
opts$roclets
#> [1] "collate"   "namespace" "rd"
opts$markdown
#> [1] TRUE
opts$load
#> [1] "pkgload"
----

Source: https://roxygen2.r-lib.org/reference/load_options.html[roxygen2 package documentation: load_options]

A file that was not written by roxygen2 is left alone. This matters when you convert a package that has hand-written Rd files, and it is the message to know: the script puts a hand-written `loan_book.Rd` where roxygen2 wants to write one, and roxygen2 refuses to overwrite it, tells you why and leaves the file as it was. (The first two lines are the first-run message of roxygen2 8, which also sets the version field in `DESCRIPTION`.)

=== DESCRIPTION: version and options

roxygen2 8 keeps its settings in `Config/roxygen2/` fields of `DESCRIPTION`. The version of roxygen2 that last documented the package is `Config/roxygen2/version`; the field that roxygen2 7.x used for this purpose, a note-style field written under another name, is no longer written, and roxygen2 8 migrates a package automatically the next time it documents it (the message "First time using roxygen2. Upgrading automatically..." and the line setting `Config/roxygen2/version` in the output above are that migration for a package that had neither). The options of `roxygenise()` (`markdown`, `load`, `roclets`, `packages`, `r6`, `old_usage`, `restrict_image_formats`) can be set as `Config/roxygen2/markdown: TRUE`, and the older `Roxygen: list(markdown = TRUE)` field is still read. The `shelf` package has the second form, because that is what `usethis` 3.2.2 writes when it turns on markdown; its `DESCRIPTION` is below. Options with a structure, such as `rd_family_title` (titles for `+@family+`) and `knitr_chunk_options`, go into `man/roxygen/meta.R`, which overrides `DESCRIPTION`. Flags in `Config/roxygen2/` are read case-insensitively since roxygen2 8.1.0 (`TRUE`, `true` and `True` all work).

The `Title` and `Description` fields are documentation too. `Title` is one line in title case without a final period (the manual says that some listings truncate it to 65 characters), `Description` is one paragraph, and the checks read both: the manual asks for other packages and external software to be written in single quotes, and for URLs in angle brackets (the `Description` of `shelf` writes 'books' and 'loans' in single quotes, as it names the two data sets). The `Authors@R` field is what roxygen2 uses for the package page of the next sections. Everything else in `DESCRIPTION` is explained in xref:programming-languages/r/creating-packages.adoc[Creating Packages].

== Markdown, links and the other tags in practice

The tables above say what each tag writes. This part shows the tags at work, one script at a time, with the files that roxygen2 generated.

=== Markdown in roxygen2 comments

With markdown on (`Roxygen: list(markdown = TRUE)` or `Config/roxygen2/markdown: TRUE`), roxygen2 translates the text of the tags into Rd with the CommonMark parser. Writing markdown is faster than writing Rd and reads better in the source, and the translation is not a pass-through: it chooses the Rd macro that fits. The script documents a function whose description uses most of the forms and prints the Rd that came out. The function has no body that matters; the page is the point.

Read the output against the input. `+[mean()]+` became `+\code{\link[=mean]{mean()}}+`, a link to the topic that has the alias `mean`; `+[stats::median()]+` named the package, `+\code{\link[stats:median]{stats::median()}}+`; `+[base::paste]+`, without parentheses, links to the topic without the code font; `+[the mean][mean]+` gave a link with other text; and `+<https://...>+` became `+\url{}+`. Inline code became `+\code{x[1]}+` when it parses as R code and `+\verb{a b}+` when it does not, which is the macro that Rd defines for literal text. Emphasis and strong became `+\emph{}+` and `+\strong{}+`, the percent signs were escaped for you (`50\%`), a heading under `+@details+` made a `+\subsection+` (a level 1 heading makes a top-level `+\section+`), the numbered list made an `+\enumerate+`, the table made a `+\tabular+` and the fenced code block a `+\preformatted+` with HTML wrappers. Two rules avoid the common surprises. A square bracket that is not meant as a link has to be escaped in the comment (`+\\[+`), because markdown reads `+[word]+` as a link to the topic `word` and roxygen2 reports a link it cannot resolve. Markdown features that Rd cannot express (block quotes, inline HTML, horizontal rules) give a warning or an error. The last tag, `+@examplesIf interactive()+`, produced the three lines at the end: the example is wrapped in an `if` that is hidden from the reader by `+\dontshow+`, and `withAutoprint()` makes the code print as in a session. A package that has not turned markdown on writes Rd by hand in its comments, and the tag `+@md+` (or `+@noMd+`) switches it on (or off) for a single block; the script of a later section shows `+@md+`.

=== Parameters and returns

Every argument of every exported function needs an `+@param+` entry, and `R CMD check` reports a WARNING otherwise: the steps "checking for code/documentation mismatches" and "checking Rd \usage sections" compare the arguments in the usage with the `+\arguments+` section, and report arguments that are undocumented and arguments that are documented but do not exist. `+@param+` takes one or several names (`+@param member,days+`), the description may use markdown, and a description that applies to many functions is documented once and inherited, which is the subject of the next section. `+@returns+` documents the value: what class it has, what its length is, and whether it is returned invisibly. The tidyverse project's own conventions (community material, not part of R) ask every function to say what it returns, because `+\value+` is the first thing a reader of the page checks. The `shelf` function `overdue_loans()` documents the `days_out` column it adds, `loan_summary()` the four columns it returns, and `print.book()` says that it returns its argument invisibly.

=== Reusing documentation

Documenting the same argument ten times is both tedious and a source of inconsistency, and roxygen2's reuse tags exist to avoid it. The script builds a throwaway package with six blocks: `overdue()` documents `loans`, `today`, `+...+` and the return value and has a section and a family; `overdue_rate()` inherits all of it with `+@inheritParams+`, `+@inheritSection+`, `+@inherit+` and `+@inheritDotParams+`; `format_loan()` and `print_loan()` share one page with `+@describeIn+`; `squish_loan()` is an internal helper with `+@keywords internal+`; and `hidden_helper()` has `+@noRd+`. === Links, topics and aliases

The markdown forms above are the usual way to link. For a topic in the same package `+[book()]+` links the alias `book`; for another package `+[pkg::fun()]+` writes a link with that package as an anchor, and the package should be listed in `Imports` or `Suggests` of `DESCRIPTION`, because the check for cross-references needs it ("Always list the linked package as a dependency", in the roxygen2 message that the first run of `document()` printed). Since roxygen2 8.0.0 all generated links share one code path, links to external packages use the topic alias as the anchor (which removed the R CMD check note about non-topic package-anchored links), and infix operators such as `+[%in%]+` can be linked. A link to a class is `+[Book-class]+` for S4, `+[book]+` for S3 (when the page's alias is the class name), and `+[Book]+` for S7. The alias lists of the shelf pages show that one page often serves several topics; `help.search()` finds them by title, alias, concept and keyword.

=== Namespace tags

The same comments write the `NAMESPACE`. `+@export+` is the one every package uses, and its meaning depends on what it is on: a function gives `export(name)`, an S3 method gives `S3method(generic,class)`, an S4 class gives `exportClasses()`. The rule for S3 methods is strict: always export them, even when the generic is internal, since exporting is what registers the method; a method that is not exported is not found by dispatch in the installed package, although `devtools::load_all()` hides that mistake by exposing every function. roxygen2 warns about a method without a tag, as the "Messages" section below shows, and `+@exportS3Method NULL+` silences the warning for a method that is registered another way. For a method of a generic that lives in another package there are two ways: import the generic with `+@importFrom pkg generic+` and `+@export+` the method, or write `+@exportS3Method pkg::generic+`, which registers the method when the other package is loaded and needs no import. The `shelf` `NAMESPACE`, written by roxygen2 from the tags on `format.book()`, `print.book()`, `summary.book()` and `print.summary.book()` and on the ten exported functions, is this file:

A package that imports a function writes `+@importFrom pkg fun+` in the block of the function that uses it (or once in a package-level file), and roxygen2 8.1.1 writes the double-quoted form for non-syntactic names such as `+model<-+` to work around a base R bug in `importFrom()` directives.

=== Other tags: files, templates and generated Rd

And the `+@param y+` for an argument that does not exist was written to the page anyway (`+\item{y}{An argument that does not exist}+`); that one is found by `R CMD check`, in the step shown next.

== Checking the documentation

The loop of a package author is edit, `devtools::document()`, read the warnings, check. `devtools::check_man()` is the shortcut for the documentation part: it documents the package and runs the Rd checks of `R CMD check` (`tools::checkDocFiles()` and friends) without the rest. The script breaks a copy of `shelf` on purpose in three ways, a new argument without a tag, a tag for an argument that does not exist with a link to a missing topic, and an exported function with no page, and shows what each tool reports.

== Documenting data, the package and classes

Functions are the easy case. Three other kinds of object need their own habits: data sets, which are not exported and are documented by name; the package itself, which has an overview page; and classes of the four object systems, which are documented through their constructors, generics and methods.

=== Data sets

A data set is not a function and is not exported: it lives in `data/` (the `shelf` package builds `data/books.rda` and `data/loans.rda` from the CSV files in `data-raw/` with `usethis::use_data()`) and it is documented by a block above a string with the name of the data set. The block for `books` is in `R/data.R`; the data are made by the script `data-raw/books.R`, which the package keeps (and leaves out of the tarball through `.Rbuildignore`) so that the data can be rebuilt. === S3 classes and methods

An S3 class has no definition to document: the constructor is a function, the generics and methods are functions, and the class is described by the constructor's page. The roxygen2 article gives the working rules: document a generic like any function and say that it is a generic, document a class by its constructor, and document a method only when it has behaviour of its own, with a link back to the generic; always export S3 methods, because exporting registers them. `shelf` follows them. The constructor family `book()`, `new_book()` and `validate_book()` is one page (the `+@rdname book+` tags put the three blocks into the same file), and the four methods of the class are one more page, `book-methods`, that has no object of its own: the first block is written above `NULL` with `+@name book-methods+`, and the method blocks are `+@rdname book-methods+` and `+@export+`. This is an excerpt of `~/shelf/R/book.R`:

[source,r]

The roxygen2 article adds two more things. === S4 classes and methods

roxygen2 documents S4 without extra tags for the usual cases. A class is documented above `setClass()`, with `+@slot+` for each slot; a generic is documented above `setGeneric()` like a function; a method above `setMethod()` is merged into the generic's page with `+@rdname+`, or, for `show`, into the class's page. The generated topics follow the naming rules of Writing R Extensions: `Book-class` for the class and `describe,Book-method` for the method, and the `NAMESPACE` receives `exportClasses()` and `exportMethods()` directives. The script documents a small S4 version of the `book` class in a throwaway package and prints the two Rd files and the `NAMESPACE`.

=== R6 classes

An R6 class is an environment of methods and fields built by `R6::R6Class()`, and the documentation of its members is written inside the class definition, above each member, in comments. roxygen2 produces one page for the class with the fields, the active bindings, an index of the methods and a subsection for each method with its usage, arguments and return value, links to the methods of the superclass and an example if there is one. `+@field+` documents a field or an active binding, `+@description+` and `+@param+` a method, and the method blocks may also carry `+@returns+` and `+@examples+`. The R6 option of roxygen2 is on by default. The script documents a small R6 class and prints the beginning of the generated page (the file has 94 lines).

=== S7 classes

S7 is a newer object system; roxygen2 8.0.0 added initial support for it, and S7 0.2.2 is described by its authors as somewhat experimental, so the details below are those of these versions and may change. A class is documented like its constructor function, because `new_class()` returns one: `+@param+` documents the arguments, which are the properties, `+@returns+` the object, and `+@prop+` the properties that are not constructor arguments, such as a read-only computed property. A generic made with `new_generic()` is documented like any function. A method registered with `+method(generic, class) <- fn+` is detected automatically and documented with a usage line of the form "S7 method for class". The script documents all three in a throwaway package, whose `.onLoad()` calls `S7::methods_register()` as an S7 package must, and prints the three generated files.

== Vignettes

A help page documents one function. A vignette documents how the functions work together: a long-form guide, written in a literate format in which prose and R code are mixed, whose code is run when the document is built, so that the output it shows is real and a change that breaks it is noticed. R's name for the idea (and for the document) is "vignette", and it is part of the package system: sources live in `vignettes/`, `R CMD build` turns them into HTML or PDF in `inst/doc`, the installed package has them in its `doc` directory, `vignette()` and `browseVignettes()` find them, and `R CMD check` runs their code and checks that the outputs are up to date. Sweave is the engine that ships with R, for LaTeX documents with the extension `.Rnw`; every other engine is provided by a package, so a package with vignettes in another format says which in `DESCRIPTION`.

=== The files and the fields

The `shelf` vignette is an R Markdown file, `vignettes/shelf.Rmd`, processed by knitr (1.52) and rmarkdown (2.32), which uses Pandoc for the final conversion to HTML. Three things in `DESCRIPTION` make that work: `Suggests: knitr, rmarkdown` (the packages must be available when the package is built and checked, and are not needed to use it), `VignetteBuilder: knitr` (the name of the package that provides the vignette engine; without the field, `R CMD check` does not know that the package has non-Sweave vignettes) and, in the file itself, a `\VignetteEngine` line. The file, as `usethis::use_vignette()` created it and as the package has it, is the following. The `vignette:` block in the YAML header carries the three lines that R reads (the `+%\Vignette...+` lines are comments for R and are ignored by Pandoc), and `output: rmarkdown::html_vignette` selects an HTML format with a light style and small output that was designed for package vignettes.

=== Building: R CMD build and the tarball

`R CMD build` is where the vignettes are rendered. It installs the package into a temporary library (the vignette calls `library(shelf)`), runs the engine on every file in `vignettes/`, and copies the sources and the outputs into `inst/doc` of the tarball, which is also what lets an author use private packages, screenshots and anything else that only exists on one machine. R keeps the outputs in the tarball so that they need not be rebuilt at installation, and `R CMD check` verifies that the outputs are not older than the sources. The script builds a copy of `shelf` with `R CMD build` and lists the files of the tarball that matter, and then builds it again with `--no-build-vignettes`:

=== knitr and R Markdown in a vignette

A knitr-based vignette is an ordinary R Markdown document with the header lines above; the https://yihui.org/knitr/[knitr site] and the https://rmarkdown.rstudio.com/[rmarkdown site] document the chunk options and the output formats. The R chunks are evaluated in order, each chunk's results and figures are inserted, and the chunk options (`collapse`, `comment`, `fig.width`, `eval`, `echo`, `include`) are knitr's; a chunk with `eval = FALSE` is shown and not run, which is how a vignette shows code that needs a service or a long computation. All the chunks run when the package is checked, so a vignette is a test too. Of the engines that knitr registers, listed by the script above, `knitr::rmarkdown` (R Markdown to HTML or PDF) is the one used here, `knitr::knitr` processes Sweave-like `.Rnw` files with knitr, and the names that end in `_notangle` are the same engines without the extraction of the code. A vignette in HTML needs Pandoc, and one in PDF needs LaTeX.

Four rules keep a vignette from causing trouble on CRAN. Make it deterministic, as the `shelf` vignette does by fixing the reference date (`+today <- as.Date("2026-06-30")+`) instead of asking the system for the current date. Keep it fast, since the https://cran.r-project.org/web/packages/policies.html[CRAN Repository Policy] asks for the checks to take as little CPU time as possible (see xref:programming-languages/r/publishing-to-cran.adoc[Publishing to CRAN]). Keep files small: PDF or HTML output that is too large is a known problem (the manual mentions a PDF of 72 MB), and the CRAN policy sets a 5 MB guideline for documentation. And use only packages that are declared, because the check "unstated dependencies in vignettes" fails on a package that is used but not listed in `Suggests` or `Imports`.

If a document should be on the website of the package but not in the tarball (because it is large, or needs a service), `usethis::use_article()` creates an "article" that only pkgdown builds, in the next section.

=== Quarto vignettes

Quarto, the multi-language successor of R Markdown from Posit, can render the same kind of document, and R packages can use it for vignettes. Quarto executes R cells with knitr, so most R Markdown documents render without change. The command-line program is separate from R (version 1.10.19 is installed in the image), and what connects it to the package system is the `quarto` R package, which registers the vignette engines `quarto::html` and a PDF one. The setup, as the package's own article describes it, is `VignetteBuilder: quarto` in `DESCRIPTION`, `quarto` in `Suggests`, and the header of the `.qmd` file:

[source,yaml]
----
---
title: "Analysing library loans with shelf"
format: html
vignette: >
  %\VignetteIndexEntry{Analysing library loans with shelf}
  %\VignetteEngine{quarto::html}
  %\VignetteEncoding{UTF-8}
---
----

Source: https://quarto-dev.github.io/quarto-r/articles/hello.html[quarto package documentation: Quarto HTML Vignettes]

This is a fragment, not run: the `quarto` R package is not installed in the image, so `R CMD build` of such a package cannot run here. The Quarto program can render the file by itself, though. The shell script below makes a throwaway directory, writes a `.qmd` file with that header and one R chunk that loads the installed `shelf` and counts the overdue loans, and renders it with the program. The plain `quarto render` ignores the `vignette:` metadata and uses the default HTML format of Quarto:

[source,bash]
----

format: html

The output shows what a Quarto render looks like: the chunk was executed (`1/3`, `2/3 [unnamed-chunk-1]`, `3/3`) by knitr, Pandoc was called with the HTML options, and the result is `shelf.html` and a `shelf_files` directory. The `vignette` block is in the listed metadata as plain text, which is how Quarto passes it through; only the `quarto` R package turns it into an engine. The package's article states two limits: the HTML vignette engine produces a deliberately minimal format (a standalone file, Bootstrap off, a small stylesheet of its own, and settings that cannot be overridden from the header, although new ones such as `toc: true` can be added), and an interactive `quarto render` uses the default HTML format of Quarto and not the vignette one, so only building the package shows the real result. The intermediate files of an authoring workflow (`vignettes/*_files`) belong in `.Rbuildignore` and `.gitignore`. For PDF there is a separate engine; and `usethis::use_vignette("name.qmd")` sets a package up for Quarto if the `quarto` R package and pkgdown 2.1.0 or later are installed.

The choice between the two is practical. R Markdown with knitr is the default of the package tooling, has no dependency outside R and Pandoc, and works everywhere `R CMD check` does. Quarto vignettes need the Quarto program on the machine that builds the package, and give access to Quarto's features; for a package whose vignettes are an ordinary guide, R Markdown is the shorter road, and the Quarto road is the one for a package that already uses Quarto for its other documents. xref:programming-languages/r/reports-with-quarto-and-r-markdown.adoc[Reports with Quarto and R Markdown] is the page about the formats themselves.

=== Sweave and other vignette formats

Sweave (`.Rnw` files, LaTeX with R chunks, run by `utils::Sweave()` and extracted by `Stangle()`) is the engine that needs no `VignetteBuilder`, and the manual's section on vignettes is written in terms of it; `R CMD Sweave` and `R CMD Stangle` are the command-line forms. Documents in `inst/doc` can be in any format; the manual recommends HTML or PDF, so that users on almost all platforms can read them. New code uses R Markdown or Quarto.

== pkgdown websites

== inst/CITATION: how to cite the package

`citation()` with no argument gives the citation of R, and `citation("pkg")` the citation of a package. The text comes from the file `inst/CITATION` if the package has one, and otherwise is built from `DESCRIPTION`. The file is R code, in the encoding of the package, with one or more calls of `bibentry()`; it must produce no output when sourced and, because CRAN requires it, it must not call functions such as `packageDescription()` that assume the package is installed in a library on the search path. The object `meta`, a parsed version of `DESCRIPTION`, is available inside the file, so that a title and a version need not be repeated and get out of date. The `shelf` file is the smallest that works:

[source,text]
----
bibentry(
  bibtype = "Manual",
  title = "shelf: Tools for a Small Library Catalogue",
  author = person("Shelf", "Maintainers"),
  year = "2026",
  note = "R package version 0.1.0"
)
----

Source: https://cran.r-project.org/doc/manuals/r-release/R-exts.html#CITATION-files[Writing R Extensions: CITATION files]

The script prints the citation of R itself (a good example of the output), the citation of `shelf`, reads the installed file by hand with `readCitationFile()`, formats it in text style, and prints what R would have generated if the file did not exist, in the form of the `bibentry()` call.

  bibtype = "Manual",
  title = paste0(meta$Package, ": ", meta$Title),
  author = person("Shelf", "Maintainers"),
  year = format(as.Date("2026-06-30"), "%Y"),

  header = "To cite the shelf package:"

  bibtype = "Article",
  title = "Cleaning a Small Library Catalogue",

  year = "2025",
  volume = "3",
  number = "1",
  pages = "10--20",
  header = "And the method behind it:"
)
)", file)

length(cit)

print(cit)

#>
#>   Maintainers S (2026). _shelf: Tools for a Small Library Catalogue_. R
#>   package version 0.1.0.
#>
#> And the method behind it:

The first entry is computed from `meta` (`paste0(meta$Package, ": ", meta$Title)` gave the title shown), and the second is a journal article that does not exist (the journal is imaginary, as the authors are). If a `bibentry` contains LaTeX markup in names or titles, the argument `textVersion` supplies the plain text to print.

== NEWS.md: what changed

A `NEWS` file is the changelog that `news()` reads and that users, CRAN and pkgdown show. R looks for it, in order, in `inst/NEWS.Rd`, `NEWS.md` (since R 3.6.0, and it needs the commonmark and xml2 packages), `NEWS` and `inst/NEWS`. For `NEWS.md` the format is Markdown: a first-level heading gives the package name and the version (and optionally a date in parentheses), a second-level heading gives a category, and the bullets are the entries. `usethis::use_news_md()` writes a first file. The `shelf` file has a heading for version 0.1.0 and one bullet:

[source,text]
----
# shelf 0.1.0

* Initial version: the `book` class, `clean_books()`, `clean_loans()`,
  `overdue_loans()`, `loan_summary()` and `loans_per_month()`, with the
  `books` and `loans` datasets.
----

Source: https://search.r-project.org/R/refmans/utils/html/news.html[R documentation: news]

The script reads the installed file back with `news()`: the result is a data frame with the version, date, category, text (and an HTML rendering), `print()` formats it, and `news(Version >= "0.1.0", package = "shelf")` selects by an expression over the columns.

[source,r]
----
# news(): the NEWS.md of the installed package, as a data frame.
n <- news(package = "shelf")
class(n)
#> [1] "news_db_from_md" "news_db"         "data.frame"
names(n)
#> [1] "Version"  "Date"     "Category" "Text"     "HTML"
n$Version
#> [1] "0.1.0"
cat(n$Text, sep = "\n")
#>   - Initial version: the book class, clean_books(), clean_loans(),
#>     overdue_loans(), loan_summary() and loans_per_month(), with the
#>     books and loans datasets.

# print() formats the entries; doBrowse = FALSE keeps the text in the console.
print(n, doBrowse = FALSE)
#>                         Changes in version 0.1.0
#>
#>   - Initial version: the book class, clean_books(), clean_loans(),
#>     overdue_loans(), loan_summary() and loans_per_month(), with the
#>     books and loans datasets.

# A query over the entries.
news(Version >= "0.1.0", package = "shelf")$Version
#> [1] "0.1.0"
----

Source: https://search.r-project.org/R/refmans/utils/html/news.html[R documentation: news]

The print method shows "Changes in version 0.1.0" and the bullet with the code formatting removed. A good `NEWS.md` is written for the users, not for the commit log: it says what changed in a way that affects a user, puts the newest version at the top, mentions each deprecated function with its replacement, and names the person or issue only if that helps. R 4.3.0 made `R CMD check` report problems it meets when reading `NEWS.md`, so a malformed file is found by the check. pkgdown publishes the file on the "News" page of the site.

== README and the other files

A `README.md` is not part of R's documentation system but is where people arrive: GitHub shows it, CRAN shows it on the package's page, and pkgdown uses it as the home page. It should say what the package is for, how to install it and one short example. When the example should run, `README.Rmd` is rendered to `README.md` with `devtools::build_readme()`, as `usethis::use_readme_rmd()` sets up (the script of the package-page section created one). `usethis` adds `README.Rmd` to `.Rbuildignore` when it creates it, as the output of that script shows. `CONTRIBUTING.md` and `CODE_OF_CONDUCT.md` are other files of the same kind, and `shelf` also has a `cran-comments.md`, the notes that the author sends to CRAN with a submission, which is explained in xref:programming-languages/r/publishing-to-cran.adoc[Publishing to CRAN].

== Pitfalls

* *Editing a generated file.* A file that starts with "Generated by roxygen2: do not edit by hand" is overwritten by the next `devtools::document()`; edit the comment in the R file. The reverse also holds: roxygen2 leaves a hand-written Rd file alone (it says so, as shown above), so a package can mix the two, and a file that was once generated and is now edited by hand must lose its header.
* *Forgetting to document after a change.* `R CMD build` does not run roxygen2: it packages `man/` and `NAMESPACE` as they are. Commit both, run `devtools::document()` before every commit that touches a tag, and let `devtools::check()` catch the rest. `devtools::load_all()` does not regenerate documentation either, and it exposes every function, which hides an S3 method that lacks `+@export+`.
* *The percent sign and the braces in Rd.* In hand-written Rd, `%` starts a comment and eats the closing brace, and unbalanced braces are an error: `\%` and balanced braces. roxygen2 with markdown escapes the percent signs for you; roxygen2 without markdown does not.
* *Examples that cannot run on a check farm.* Examples may not need a network, a key, a display or write access outside a temporary directory. `\dontrun{}` hides code from every check, which reviewers dislike for code that could run; `\donttest{}` is run by `--as-cran` since R 4.0.0; `+@examplesIf+` runs the example only when its condition holds. Examples are also run by pkgdown and by `example()`.
* *Arguments that do not match.* The usage is taken from the code, so a renamed argument shows in the usage at once, but the `+@param+` for the old name stays and is reported ("Documented arguments not in \usage"), and the new one is "Undocumented". Run `devtools::check_man()` after every change of a signature.
* *A description that repeats the title.* A block with a title and nothing else gives a page whose description is the title, as the generated page for `overdue_rate()` above shows. `R CMD check` accepts it; readers and CRAN reviewers do not.
* *Markdown surprises.* A sentence in a comment that starts with `1.` becomes a list. `+[word]+` becomes a link. A heading level 1 makes a new section. Inline code that does not parse as R becomes `+\verb{}+`, not `+\code{}+`. Block quotes, inline HTML and horizontal rules are not supported.
* *The warnings of the first run.* The first `document()` of a new package warns about links to topics that are written in the same run, and the second run is clean. If a warning is still there on the second run, the link is wrong, or the linked package is not in `DESCRIPTION`.
* *The index of a pkgdown site.* Once `_pkgdown.yml` has a `reference` field, every topic has to be listed in it or be internal. `pkgdown::check_pkgdown()` finds the missing ones, before a build fails.
* *Non-deterministic vignettes.* A vignette that prints the current date, uses a random number without a seed, or reads the current state of a service changes at every build, and a changed output with no changed source confuses reviewers. The `shelf` vignette fixes the date.
* *Built vignettes in the repository.* `inst/doc` and the files in `vignettes/` that the build leaves (`+*.html+`, `+*.R+`) are products. `usethis::use_vignette()` ignores them with `.gitignore`; the tarball gets them from `R CMD build`.
* *A CITATION file that depends on installation.* The file is run when the package is not installed; calling `packageDescription()` or `utils::packageVersion()` in it works on the author's machine and fails on CRAN. Use `meta`.
* *A PDF manual needs TeX.* Without `pdflatex`, `R CMD Rd2pdf` fails as shown above, and a plain `R CMD check` reports a WARNING and an ERROR for the PDF manual. The Rd files themselves are checked by `checkRd()` and by the other steps of the check without TeX, so `--no-manual` loses only the PDF.
* *A hand-written `man` directory and roxygen2 together.* A page of the same name that roxygen2 would write is skipped, and nothing says that the roxygen2 block above the function is then not documentation: read the "Skipping" line.
