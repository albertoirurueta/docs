== How reticulate works

An R session that loads reticulate can start one Python interpreter, in the same process, and it can start only one: Python is initialised the first time something needs it, and from then on the interpreter, the modules it imported and the objects it created live until the R session ends. The word the package documentation uses is lazy: the bindings are not initialised until an API that explicitly requires Python is called, which is what lets a script, or a package, ask for a particular Python before the first call (reticulate package documentation: use_python). `py_available()` reports whether that has happened yet, and `py_config()` forces it.

Three consequences follow. First, an interpreter must be found, and it must have been built with a shared library (the `--enable-shared` option of Python's own build; the versions article says reticulate can only bind to such a build), so choosing the Python is the first decision and the subject of <<choosing>>. Second, every Python object you hold in R is a reference. An R object of class `python.builtin.module`, `python.builtin.function` or `python.builtin.dict` is a small R environment wrapping a pointer to a Python object, and printing it prints the Python `repr()`; the R class vector lists the Python class and its parents, as <<missing-module>> shows for an exception. Third, values cross the boundary by conversion, in both directions, with rules (<<conversion>>) that are mostly intuitive and have a handful of sharp edges that are worth knowing in advance: integers and doubles are different Python types, `NA` has no Python equivalent, a vector is a list, a matrix is an array that shares memory with R, and a data frame is a pandas DataFrame.

The usual first program is two lines. The package documentation's first example imports the Python `os` module and lists a directory, and the shape is always the same: `import()` a module, call its functions with `$`. The block is that example, shown as a fragment so that its output does not depend on the contents of the directory it is run in; the examples that follow are real scripts.

[source,r]
----
library(reticulate)
os <- import("os")
os$listdir(".")
----

== Choosing a Python

reticulate can bind to almost any Python installation on the machine, and since reticulate 1.41 it can also create one for you. The decision matters because the Python packages you need (NumPy, pandas) are installed per interpreter or per environment, and because the choice is made once per R session: after Python has been initialised the interpreter cannot be changed. The tools, in the order a project would reach for them today, are `py_require()` (declare what you need and let reticulate build an environment), the `+use_*()+` functions and the `RETICULATE_PYTHON` environment variable (name an interpreter or environment you manage yourself), and the commands that create environments (`virtualenv_create()`, `conda_create()`).

=== Declaring requirements with py_require()

`py_require()` was added in reticulate 1.41.0 (2025-02-24): its NEWS entry calls it a new function for declaring Python requirements for the current R session. The vignette on installing Python packages now presents it as the recommended way to declare Python dependencies, a call comparable to `library()` for Python packages, and the vignette on Python versions says that selecting an interpreter by hand has been generally unnecessary, and no longer recommended, since 1.41. A call updates a manifest that reticulate keeps for the session: Python packages (with pip-style version constraints), a constraint on the Python version itself, and an optional `exclude_newer` date that limits package versions to those published before it, which is a lightweight alternative to freezing versions. Nothing is installed at that point. The manifest is consulted when Python is first initialised, typically at the first `import()`, and only if no interpreter that you manage was found earlier in the order of discovery (<<discovery>>); reticulate then resolves the manifest into an ephemeral virtual environment, cached by the exact set of requirements, so a second run with the same requirements reuses it.

reticulate uses uv (the Python package and project manager) for this resolution. If uv is already on the machine reticulate uses it as it is; if not, it downloads uv into the directory returned by `tools::R_user_dir("reticulate", "cache")`, together with the Python builds and the ephemeral environments, and clears that cache automatically on an interval that defaults to 120 days (1.44.0) and is set with `RETICULATE_MAX_CACHE_AGE_DAYS` (1.47.0 added it as an environment variable) or the `reticulate.max_cache_age` option. Because uv does the work, its environment variables apply: `UV_OFFLINE`, `UV_INDEX`, `UV_DEFAULT_INDEX`, `UV_PRERELEASE` and `UV_PYTHON_PREFERENCE`. Two environment variables switch the feature on and off: `RETICULATE_USE_MANAGED_VENV="no"` disables the ephemeral environment, and `RETICULATE_PYTHON="managed"` forces it.

The calls go at the top of a script, next to `library()`, because after Python is initialised only additions are possible: removing a package, changing the Python version or `exclude_newer` is not. Calling `py_require()` with no arguments prints the manifest, including which R package or script requested each item, which is how to debug conflicting requirements. This is a fragment: it needs the network the first time, so the page did not run it, and the scripts on this page ran against the system interpreter through `RETICULATE_PYTHON`, a self-managed choice that makes `py_require()` irrelevant (the package documentation says the manifest has no effect when another interpreter is found first).

[source,r]
----
library(reticulate)

# Declare what the script needs, before anything starts Python.
py_require(c("numpy", "pandas"))
py_require(python_version = ">=3.11")
py_require(exclude_newer = "2026-09-01")

# The first use of Python resolves the requirements into a cached
# ephemeral environment (this needs the network the first time).
pd <- import("pandas")

# With no arguments, py_require() prints the current manifest.
py_require()
----

Source: https://rstudio.github.io/reticulate/reference/py_require.html[reticulate package documentation: py_require]

The reference page describes four arguments: `packages` (names, with optional constraints such as `"jax[cpu]>=0.5"`, or pip-style git and local-path forms), `python_version` (for example `">=3.9,<3.13"`), `exclude_newer` (an RFC 3339 timestamp, a date string, a `Date` or a `POSIXct`, the last two since 1.47.0) and `action`, one of `"add"` (the default), `"remove"` (exact matches only) and `"set"` (replace everything). R packages can declare their own requirements the same way, usually from `.onLoad()`, and the manifest combines everything that was declared (<<packages>>). If the requirements cannot all be satisfied, initialising Python fails with uv's explanation of the conflict and the current manifest, and the fix is to adjust the requirements with `action = "remove"` or `"set"`, or to roll back to a known good date with `exclude_newer`. Since 1.44.0 reticulate warns when a package declared with `py_require()` is missing from the environment it ended up using; the warning can be silenced with `RETICULATE_CHECK_REQUIRED_PACKAGES=0`.

=== Naming an interpreter: use_python(), RETICULATE_PYTHON and friends

When you manage the Python yourself, you tell reticulate which one with one of five functions or one environment variable.

[cols="2,5",options="header"]
|===
|Call |What it selects
|`use_python("<path to python>")` |A specific interpreter binary.
|`use_virtualenv("name-or-path")` |A virtual environment, by name (looked up under the virtualenv root, `+~/.virtualenvs+` by default, configurable with `WORKON_HOME`, and `RETICULATE_VIRTUALENV_ROOT` since 1.39.0) or by path.
|`use_condaenv("name")` |A conda environment, by name, prefix or interpreter path; `conda =` names the conda executable.
|`use_miniconda("name")` |A conda environment of the Miniconda that `install_miniconda()` installed.
|`use_python_version("3.12")` |A Python installed by `install_python()`.
|`RETICULATE_PYTHON` |The path to an interpreter, standalone, in a virtual environment or in a conda environment. It overrides every other request.
|===

Source: https://rstudio.github.io/reticulate/reference/use_python.html[reticulate package documentation: use_python]

All the `+use_*()+` functions take `required`. The default `NULL` is `TRUE` in most circumstances: the request is mandatory and an error is raised if the interpreter does not exist; with `required = FALSE` it is a hint, and reticulate goes on scanning when the hint cannot be satisfied. The calls only last for the R session, so they must be repeated in every script (or set once through the environment variable), and if several are made the most recent wins. They also have to come before the first use of Python. The environment variable is the one to put in `+~/.Renviron+` or in a project's `.Renviron`; it is read when Python initialises, and a value that points nowhere is an error rather than a hint. This script asks for an interpreter that does not exist in both ways, and catches the error, which is the real text reticulate raises.

[source,r]
----
# An explicit request for an interpreter that does not exist is an error,
# whether it comes from use_python(required = TRUE) ...
library(reticulate)
tryCatch(
  use_python("/opt/nowhere/bin/python", required = TRUE),
  error = \(e) conditionMessage(e)
)
#> [1] "Specified version of python '/opt/nowhere/bin/python' does not exist."

# ... or from the RETICULATE_PYTHON environment variable, which wins over
# every use_*() call.
Sys.setenv(RETICULATE_PYTHON = "/opt/nowhere/bin/python")
tryCatch(py_config(), error = \(e) conditionMessage(e))
#> [1] "Python specified in RETICULATE_PYTHON (/opt/nowhere/bin/python) does not exist"
----

Source: https://rstudio.github.io/reticulate/reference/use_python.html[reticulate package documentation: use_python]

The fragment below shows the persistent way. `.Renviron` is an ordinary text file of `NAME=value` lines read at startup, with `+${HOME}+` (the braces are required) available for the home directory (the `Startup` help page describes it, and xref:programming-languages/r/sessions-workspaces-and-startup.adoc[Sessions, Workspaces and Startup] shows the order of the startup files), so the value applies to every R session started in that project and nothing in the scripts needs to change.

[source,text]
----
RETICULATE_PYTHON="${HOME}/.virtualenvs/shelf/bin/python"
----

Source: https://rstudio.github.io/reticulate/reference/use_python.html[reticulate package documentation: use_python]

=== The order of discovery

When nothing is requested, reticulate walks a fixed list and takes the first interpreter that qualifies. The list below is the one of the Python Version Configuration article as it reads on the package site when this page was checked; it is the reference to consult when `py_require()` does not give you the environment you expect (the article says to check that nothing higher in the list is being found first, for instance the `r-reticulate` virtualenv, which `virtualenv_remove("r-reticulate")` deletes).

. The interpreter named by the `RETICULATE_PYTHON` environment variable.
. The virtual or conda environment named by `RETICULATE_PYTHON_ENV`.
. A mandatory request from `use_python()`, `use_virtualenv()` or `use_condaenv()` (`required = TRUE`, the default).
. If `RETICULATE_USE_MANAGED_VENV="yes"`, the ephemeral environment that satisfies the `py_require()` manifest.
. The environment already activated through `VIRTUAL_ENV` (an activate script run before R started, or the RStudio option to activate project-local environments).
. A poetry project (`pyproject.toml` with a `[tool.poetry]` section) or a pipenv project (`Pipfile`) in the working directory.
. A directory named `venv`, `virtualenv`, `.venv` or `.virtualenv` in the working directory, when it is a virtual environment.
. The environment named in `import("bar", delay_load = list(environment = "r-barlyr"))` by a package, if it exists.
. A `+use_*()+` request with `required = FALSE`, or one made from a package's `.onLoad()`, if that interpreter exists.
. A virtual or conda environment named `r-bar`, when the code calls `import("bar")`.
. The interpreter named by `RETICULATE_PYTHON_FALLBACK`.
. A virtual environment named `r-reticulate`, if it exists.
. Otherwise the ephemeral environment resolved from the `py_require()` manifest, unless `RETICULATE_USE_MANAGED_VENV="no"`.
. Last of all, the Python on the `PATH` (or in the Windows registry); when both `python` and `python3` are on the `PATH`, `python3` is preferred unless only `python` has NumPy installed or `python3` was built for a different architecture than R.

Source: https://rstudio.github.io/reticulate/articles/versions.html[reticulate package documentation: Python Version Configuration]

Items 1 to 3 are decisions you make; items 5 to 7 are conventions that pick up the environment of the project you are in, and items 8 to 10 are what packages can arrange; items 11 to 14 are the fallbacks, and the managed environment (item 13) is the new default one. Notice that a virtualenv left behind by an earlier tutorial (`r-reticulate`, item 12) still outranks `py_require()`.

=== Creating environments yourself

The functions that create environments predate `py_require()` and remain supported. They are fragments here, because they build environments and download packages, and the articles that describe them now carry a banner of updated guidance: managing installations by hand is generally unnecessary, and no longer recommended, since 1.41. The virtualenv functions create a venv from a "starter" interpreter (`virtualenv_starter(all = TRUE)` lists the candidates) and install into it with pip; `py_install()` is the one-line version, installing into the environment named `r-reticulate`; the conda functions do the same for conda, and `install_miniconda()` has installed miniforge rather than Miniconda since 1.44.0. `install_python()` builds a Python (3.12 by default since 1.44.1).

[source,r]
----
library(reticulate)

# A virtual environment, then the packages the shelf scripts need.
virtualenv_create("shelf")
virtualenv_install("shelf", c("numpy", "pandas"))
use_virtualenv("shelf", required = TRUE)

# The shortcut: pip-install into the default "r-reticulate" environment.
py_install(c("numpy", "pandas"))

# The conda route, with the miniforge that reticulate can install.
install_miniconda()
conda_create("shelf", packages = c("numpy", "pandas"))
use_condaenv("shelf", required = TRUE)
----

Source: https://rstudio.github.io/reticulate/articles/python_packages.html[reticulate package documentation: Installing Python Packages]

The same step in plain Python is `python -m venv` and `pip install`, covered by xref:programming-languages/python/virtual-environments-and-packaging.adoc[Virtual Environments and Packaging]; reticulate's functions are wrappers for those tools, and nothing stops you from creating the environment in a terminal and naming it with `use_virtualenv()` or `RETICULATE_PYTHON`. Inside `repl_python()` a line that starts with `!` runs a shell command, so `!pip install scipy` installs into the interpreter reticulate is using (<<repl>>).

=== Asking reticulate what it chose

`py_config()` returns a description of the interpreter that is in use and starts Python if it was not started yet; `py_discover_config()` returns the same description for the interpreter reticulate would choose, without loading it. `py_available()` is `FALSE` until Python has been initialised (unless `initialize = TRUE`), `py_module_available("numpy")` asks whether a module can be imported, and both are what a script or test uses to skip work when Python or a package is missing. The `py_config` object is a list with the fields `python`, `libpython`, `pythonhome`, `version`, `numpy` and others, among them `forced`, which names what forced the choice. Because the paths differ on every machine, the script prints only the version fields.

[source,r]
----
library(reticulate)

packageVersion("reticulate")
#> [1] ‘1.47.0’

# The interpreter is started lazily, the first time something needs it.
py_available()
#> [1] FALSE
py_module_available("numpy")
#> [1] TRUE
py_module_available("pandas")
#> [1] TRUE
py_module_available("no_such_module")
#> [1] FALSE

# py_config() describes the interpreter that was chosen, and why.
config <- py_config()
config$version
#> [1] ‘3.12’
config$numpy$version
#> [1] ‘2.5.4’
config$forced
#> [1] "RETICULATE_PYTHON"
py_available()
#> [1] TRUE

# The interpreter describes itself through its own sys module.
sys <- import("sys")
sys$version_info$major
#> [1] 3
sys$version_info$minor
#> [1] 12
----

Source: https://rstudio.github.io/reticulate/reference/py_config.html[reticulate package documentation: py_config]

=== When a module is missing

The error that users meet most is an import that fails because the package was installed into a different Python than the one reticulate bound to. It is an ordinary R error, with the Python exception's class on the condition as well, so it can be caught like one. The message names the module; the instruction to run `py_last_error()` is part of the text, and `py_last_error()` returns the exception, with the Python traceback and the R call stack that led to it, as a list of class `py_error`.

[source,r]
----
library(reticulate)

# A Python ImportError becomes an R error that carries the Python exception.
e <- tryCatch(import("no_such_module"), error = \(e) e)
class(e)
#> [1] "python.builtin.ModuleNotFoundError" "python.builtin.ImportError"
#> [3] "python.builtin.Exception"           "python.builtin.BaseException"
#> [5] "python.builtin.object"              "error"
#> [7] "condition"
conditionMessage(e)
#> [1] "ModuleNotFoundError: No module named 'no_such_module'\nRun `reticulate::py_last_error()` for details."

# py_last_error() describes the most recent Python exception.
err <- py_last_error()
class(err)
#> [1] "py_error"
names(err)
#> [1] "type"      "value"     "traceback" "message"   "r_call"    "r_class"
#> [7] "r_trace"
err$type
#> [1] "ModuleNotFoundError"
err$value
#> [1] "No module named 'no_such_module'"

# The condition classes make Python-specific handlers possible.
tryCatch(
  import("no_such_module"),
  python.builtin.ImportError = \(e) "no such module, using the fallback"
)
#> [1] "no such module, using the fallback"
----

Source: https://rstudio.github.io/reticulate/reference/py_last_error.html[reticulate package documentation: py_last_error]

Notice the condition classes: the Python class names, prefixed with `python.builtin.`, come first, then `error` and `condition`, so `+tryCatch(..., python.builtin.ImportError = )+` catches exactly this failure and nothing else. That behaviour is from reticulate 1.29.0, whose NEWS says Python exceptions now inherit from `error` and `condition` and can be passed to `stop()`; the condition became an R list instead of an environment in 1.38.0, for compatibility with rlang and purrr. The full R call stack is in `py_last_error()$r_trace$full_call`, which is the thing to inspect when the Python error was raised deep inside a callback. xref:programming-languages/r/conditions-and-error-handling.adoc[Conditions and Error Handling] explains the handlers used here.

== Importing modules and calling Python

`import("name")` is Python's `import name`, executed from R, and returns an object of class `python.builtin.module`. The dollar operator `$` reaches everything inside it, whether that is a function, a class, a constant or a submodule, and it works the same way on any Python object: `np$arange(10L)$reshape(2L, 5L)` is `np.arange(10).reshape(2, 5)`. Calling a Python function from R looks like calling an R function, with positional and named arguments; the named ones become Python keyword arguments (`builtins$sorted(x, reverse = TRUE)`).

The functions that start from a module other than a plain `import` are small: `import_builtins()` returns Python's `builtins` module (`len()`, `sorted()`, `open()`, `int()`), `import_main()` returns `+__main__+`, the module where `py_run_string()` and `py_run_file()` define things, and `import_from_path("mymodule", path = ".")` imports a module from a directory that is not on Python's path, which is how you load a module that ships inside an R package (`system.file("python", package = "mypkg")`). `import()` has an `as` argument that renames the module in the R class (aimed at package developers) and `delay_load = TRUE`, which postpones the import until first use so that a package can load without Python installed and let the user configure it first (<<packages>>). The help of a Python object is available as text with `py_help()`, its attributes with `py_list_attributes()` or `names()`, and tests for a single attribute with `py_has_attr()`.

A few Python names are not valid R names: the double-underscore attributes need backticks around the name after `$` (the script in <<sourcing>> reads a docstring that way), or `pass:c[py_get_attr(x, "__doc__")]`, and so does a Python method that happens to have the name of an R keyword. The script below uses standard-library modules, so it runs anywhere.

[source,r]
----
library(reticulate)

# import() returns a module object; `$` reaches its functions and attributes.
math <- import("math")
class(math)
#> [1] "python.builtin.module" "python.builtin.object"
math$pi
#> [1] 3.141593
math$sqrt(2)
#> [1] 1.414214
math$floor(2.7)
#> [1] 2
class(math$floor(2.7))
#> [1] "integer"

# Python's built-in functions live in the builtins module.
builtins <- import_builtins()
builtins$len("shelf")
#> [1] 5
builtins$sorted(c("b", "a", "c"))
#> [1] "a" "b" "c"
builtins$max(c(3, 9, 4))
#> [1] 9

# convert = FALSE keeps results as Python objects until py_to_r() is called.
collections <- import("collections", convert = FALSE)
counts <- collections$Counter(c("Fiction", "Poetry", "Fiction"))
counts
#> Counter({'Fiction': 2, 'Poetry': 1})
class(counts)
#> [1] "collections.Counter"   "python.builtin.dict"   "python.builtin.object"
counts$most_common(1L)
#> [('Fiction', 2)]
py_to_r(counts$most_common(1L))
#> [[1]]
#> [[1]][[1]]
#> [1] "Fiction"
#>
#> [[1]][[2]]
#> [1] 2
#>
#>

# The module's attributes can be listed and tested.
"sqrt" %in% py_list_attributes(math)
#> [1] TRUE
py_has_attr(math, "cbrt")
#> [1] TRUE
py_has_attr(math, "no_such_function")
#> [1] FALSE
head(py_list_attributes(math), 4)
#> [1] "__doc__"     "__loader__"  "__name__"    "__package__"
----

Source: https://rstudio.github.io/reticulate/reference/import.html[reticulate package documentation: import]

Several things happened there. `math$floor(2.7)` returned a Python `int`, which became an R integer; `builtins$max(c(3, 9, 4))` was handed a vector, converted to a Python list, and returned a float, which became an R double. The `Counter` was imported with `convert = FALSE`, so `counts` and `counts$most_common(1L)` stayed Python objects and printed with Python's `repr()`; `py_to_r()` converted the list of tuples into an R list at the end. That is the pattern for any chain of Python calls whose intermediate results you do not want converted: import the module with `convert = FALSE`, chain the calls, and convert the final value. The `$` operator on a module imported with `convert = FALSE` returns Python objects, and one imported with the default converts each result as it comes back.

The same machinery works on classes and instances: `collections$Counter` is a Python class, calling it creates an instance, and `counts$most_common` is a bound method. A Python object of a custom class is returned to R as a reference whose class vector starts with the module and class name (`collections.Counter` above) and ends with `python.builtin.object`; its methods and properties are used with `$` as if it were an R reference class (xref:programming-languages/r/reference-classes-and-r6.adoc[Reference Classes and R6] describes those). Python's operators work on such references through R's group generics since 1.29.0 (for example `x + y` on two NumPy arrays), and `[` and `+[<-+` call Python's `+__getitem__+` and `+__setitem__+` since 1.31.0, with Python's 0-based indexes (<<numbers>>).

The rules are the content of the "Type Conversions" section of the article Calling Python from R, and the two functions that apply them explicitly are `r_to_py()` and `py_to_r()`. This section reports what reticulate 1.47.0 actually did with each value on this page's image, which differs from the article in one place (a list of mixed types).

=== Explicit control: tuple(), dict(), py_dict(), np_array()

The automatic rules are right most of the time, and the exceptions are fixed by asking for the Python type. `tuple()` makes a tuple (its argument can be the elements or one list), `dict()` makes a dictionary from named arguments or from one named list, `py_dict()` takes a vector of keys and a vector of values (so keys can be Python objects such as tuples) and `np_array()` creates a NumPy array with a chosen `dtype` and memory `order`. The function `list()` is how you pass a single element as a Python list rather than a scalar: `foo$bar(indexes = list(42L))`, from the article.

The last two calls show a rule of `dict()` that is easy to trip over: before using the argument name as a string key, it looks the name up in the calling environment, and if a variable of that name holds a Python object, that object is the key. With `key` holding a tuple, `dict(key = "count")` made a dictionary keyed by the tuple; after `rm(key)` it made the string key `+'key'+`. The reference page says that `dict()` can create a dictionary whose keys are other Python objects, and the lookup by variable name is how the source of `dict()` finds them; it means that `dict(b = 1)` is not safe in a script in which `b` is a Python object. `py_dict()` has no such lookup.

=== Numbers, indexes and big integers

R and Python disagree about the default numeric type: `42` is a double in R and an int in Python. When a Python function wants an integer it says so with a `TypeError`, and the fix is the `L` suffix (or `as.integer()`). Python collections count from 0, and a method that takes an index takes a 0-based one, passed as an integer. The script shows the errors and then the sharpest edge in the conversion: how a Python `int` that does not fit in 32 bits is converted.

[source,r]

Source: https://rstudio.github.io/reticulate/articles/calling_python.html[reticulate package documentation: Calling Python from R]

R has only 32-bit integers, and reticulate converts a Python `int` to an R integer. In the 1.47.0 run above, values inside the 32-bit range arrive intact (`+2**31 - 1+` is `2147483647`), but `+2**31+` arrived as `NA` and `+2**40+` as `0`: the values behave as if they were truncated to 32 bits, with no warning. This is behaviour to design around rather than a rule to quote: do not let a large Python integer through the automatic conversion. Keep it a Python object (`convert = FALSE`) and convert it explicitly through a float (exact up to 2^53) or a string, as above. NumPy's `int64` scalars and arrays are not affected; they become doubles, which is exact up to 2^53 as well. reticulate has no support for the `integer64` class of the bit64 package: bit64 is not among the imports of reticulate, and a bit64 vector is sent to Python as a double whose bits are the integer's bits, which is why `r_to_py(id)` printed a value close to zero. Identifiers that must keep every digit (ISBNs, loan identifiers) belong in character vectors on both sides.

Index conventions also differ for the Python objects you hold. `titles[0L]` is the first element and `titles[-1L]` the last; `py_len()` is Python's `len()`. Mixing R's 1-based positions with Python's 0-based ones is the classic off-by-one when calling Python from R: the subsetting operators of R vectors keep R's rules, the `[` method of a Python object follows Python's.

=== Missing values

R has an `NA` in every atomic type; Python has `None` and, for floats, `nan`; NumPy and pandas add their own sentinels. reticulate converts what it can, and for the rest the result is a number, not a missing value. Read this output carefully. A double `NA` becomes `nan` and comes back as `NaN`, which `is.na()` and `mean(x, na.rm = TRUE)` both handle. A scalar integer `NA` becomes the smallest 32-bit integer, `-2147483648`, which is how R itself stores it, and an R integer vector in a data frame keeps that value in an `int32` column (it converts back to `NA` on the return trip, but pandas computes with the number). A scalar logical `NA` becomes `True`, and a logical `NA` in a data frame column becomes `False`, so the missing value is lost for good. A character `NA` becomes the string `+'NA'+` when it is a scalar or an element of a vector, but in a data frame column it is a real missing value (displayed as `NaN`) that returns as `NA`. The remedies are in <<pandas>>: convert logical and integer columns carefully, use the nullable dtypes for integers, and treat a logical `NA` as a case to handle before the data leave R.

== Running Python code

`py_run_string(code)` executes a string in the `+__main__+` module and `py_run_file(file)` a file, so the names they define are visible to later calls and to R through `py`, the object that reticulate exports for the main module (`py$loan_days` is `+__main__.loan_days+`; `+py$late_fee <- 0.25+` sets a Python variable). `py_eval(expr)` evaluates one expression and returns its value. Both functions take `convert` and `local`: with `local = TRUE` the code runs in a private dictionary that is returned instead of the main module. `py_run_string()` and `py_run_file()` return the module's dictionary invisibly, which is why the script ignores their value. Since 1.29.0 `py_run_file()` and `source_python()` put the script's directory first in Python's module search path while the script runs, as `python script.py` does at a terminal.

Source: https://rstudio.github.io/reticulate/reference/py_run.html[reticulate package documentation: py_run_string and py_run_file]

The part after the `py_capture_output()` call is the error path. `py_run_string("1 / 0")` raised a Python `ZeroDivisionError`, which reticulate turned into an R error whose message starts with the exception class, whose condition classes start with `python.builtin.ZeroDivisionError`, and whose last line is the pointer to `py_last_error()`. That function returns the most recent Python exception as a list of class `py_error` with `type`, `value`, `traceback`, `message`, `r_call`, `r_class` and `r_trace` (R's call stack, summarised); printing it is the same as `cat(err$message)`, the Python traceback exactly as the interpreter prints it. A syntax error in the string is reported the same way, with the offending line and a caret.

`py_capture_output()` evaluates an expression and returns what Python printed as a character vector, which is how to keep Python's output out of an R report (`py_suppress_warnings()` does the same for Python warnings). What Python prints is shown in the R console, and since 1.31.0 reticulate flushes Python's output buffers periodically, so the output of a long-running Python call appears while the call is still running.

[#sourcing]
=== Sourcing a Python file

A file of Python functions is the usual way to reuse Python code from R. `source_python(file)` runs the file in the main module, as `py_run_file()` does, and then copies every public object that the file created into an R environment, so Python functions can be called as R functions. The default environment is the calling one, which is convenient in a script and a trap in a larger one: the names land next to your R objects and silently replace any that have the same name. The remedy is the `envir` argument, which takes an environment of your own (or `NULL`, which assigns nothing), as the script does. The Python file is the shelf scenario's ISBN-13 check, written in Python and shown here byte for byte. `normalise_isbn()` and `is_valid_isbn13()` do what the functions of the same names in `scenario.R` do; `check_digit()` computes the last digit from the first twelve.

[source,python]
----
"""ISBN-13 helpers for the shelf scenario, mirroring scenario.R."""

import re


def normalise_isbn(text):
    """Drop everything except digits and X, and upper-case the result."""
    return re.sub(r"[^0-9X]", "", text.upper())


def is_valid_isbn13(text):
    """Return True when text is a well-formed ISBN-13 with a valid check digit."""
    digits = normalise_isbn(text)
    if len(digits) != 13 or "X" in digits:
        return False
    weights = [1, 3] * 6 + [1]
    return sum(int(d) * w for d, w in zip(digits, weights)) % 10 == 0


def check_digit(first12):
    """Return the ISBN-13 check digit for the first twelve digits."""
    weights = [1, 3] * 6
    total = sum(int(d) * w for d, w in zip(first12, weights))
    return (10 - total % 10) % 10
----

Source: https://docs.python.org/3/tutorial/modules.html[The Python Tutorial: Modules]

== Callbacks, iterators and context managers

An R function can be given to Python wherever Python wants a callable: it is converted to a Python function with the generic signature `+(*args, **kwargs)+`, so `sorted(key = )`, `map()`, `functools.reduce()` and many callbacks of scientific libraries work. A library that inspects the callback's signature needs `py_func(f)`, which wraps an R function so that Python sees the same argument names and defaults (R argument lists that Python cannot express, such as `function(a = 1, b)`, are rejected). Python may call the R function from a background thread; since 1.39.0 that is safe, and `py_main_thread_func()` is deprecated.

Python iterators and generators are consumed with `iterate()`, which applies an R function to every item or, without one, collects them into a vector; an iterator can be drained only once. `iter_next()` takes one item at a time (returning `NULL` at the end, or the `completed` value you pass), and `py_iterator()` turns an R function into a Python iterator, where returning `NULL` ends the iteration (`completed =` changes the sentinel). `with()` runs R code inside a Python context manager, using `%as%` to name the object (`+with(open(path) %as% fh, ...)+` in the article's form), and since 1.44.0 an error inside the block is forwarded to the context manager's exit handler, so a database transaction rolls back.

[source,r]
----
library(reticulate)
source("scenario.R")
builtins <- import_builtins()

# An R function passed to Python becomes a Python callable.
by_length <- \(title) nchar(trimws(title))
builtins$sorted(trimws(books$title)[1:5], key = by_length)
#> [1] "Loud Roofs"          "Midnight Ledger"     "The Dispossessed"
#> [4] "the quiet streets"   "Pride and Prejudice"

# Python generators are consumed with iterate(), which can apply an R function.
squares <- py_eval("(n * n for n in range(5))")
total <- 0
iterate(squares, \(n) total <<- total + n)
total
#> [1] 30

# Without a function, iterate() collects the items into an R vector.
words <- py_eval("iter(['loan', 'return', 'renew'])")
collected <- iterate(words)
collected
#> [1] "loan"   "return" "renew"

# An R closure can be turned into a Python iterator; NULL ends the iteration.
countdown <- local({
  n <- 3L
  function() {
    if (n == 0L) {
      return(NULL)
    }
    n <<- n - 1L
    n + 1L
  }
})
iterate(py_iterator(countdown)) |> print()
#> [1] 3 2 1

# with() runs R code inside a Python context manager and closes the file.
path <- tempfile(fileext = ".txt")
written <- with(builtins$open(path, "w") %as% handle, {
  handle$write("shelf\n")
})
written
#> [1] 6
readLines(path)
#> [1] "shelf"
unlink(path)
----

Source: https://rstudio.github.io/reticulate/articles/calling_python.html[reticulate package documentation: Calling Python from R]

`iterate()` returns its value invisibly at the top level, which is why the script prints the collected values through `print()` or an assignment; the closure in `countdown` is the R idiom for state that Python's `yield` keeps for you (see xref:programming-languages/r/scoping-environments-and-closures.adoc[Scoping, Environments and Closures] for how a closure keeps state, and xref:programming-languages/python/iterators-generators-comprehensions.adoc[Iterators, Generators, and Comprehensions] for the Python side).

[#pandas]
== R and pandas data frames

An R `data.frame` is converted to a pandas `DataFrame` column by column, and back. pandas is the Python library for tabular data, the counterpart of the data frame of xref:programming-languages/r/data-frames.adoc[Data Frames] and the data.table of xref:programming-languages/r/data-table.adoc[data.table], and being able to hand a table to it (or to receive one from a Python library that returns one) is a common reason to use reticulate. Each column follows the array rules: the numeric, logical and character vectors become NumPy arrays or pandas string columns, and the article names two extensions to them: a factor becomes a pandas categorical variable, and a `POSIXct` column becomes a `datetime64[ns]` column. If the R data frame has row names, they become the pandas index, and the other way round; since 1.47.0 explicit integer row names are preserved as the index too (the NEWS entry for r_to_py).

[#pandas-3]
=== What pandas 3.0 changed

The Python side has moved under reticulate's feet, and the changes are the reason several examples below differ from older tutorials. pandas 3.0.0 was released on 21 January 2026 and the page here uses 3.0.6. Its release notes list three changes that matter at the boundary. First, a dedicated string dtype is the default: columns of strings are inferred as the new `str` dtype (backed by PyArrow when it is installed and by NumPy objects otherwise, which is the case here), where earlier versions used the NumPy `object` dtype; the missing-value marker of the `str` dtype is always `NaN`. Second, copy-on-write is the only behaviour: the result of any indexing operation or method behaves as a copy, a chained assignment such as `df[mask]["x"] = 0` no longer works, and the `SettingWithCopyWarning` is gone. Third, when strings or datetime objects are converted to `datetime64`, pandas infers the resolution instead of always using nanoseconds, and the default for parsing strings is microseconds; the minimum supported Python is 3.11. reticulate gained pandas 3.0 support in 1.45.0 (2026-02-13), and 1.47.0 converts pandas frames and series with Arrow-backed string columns. The 1.45.0 NEWS is the first to announce pandas 3.0 support; earlier releases were not checked against pandas 3 for this page.

The first half is the happy path: strings arrive as `str`, the factor as `category` with its levels as categories, integers as `int32`. The second half is the NA trap of <<conversion>>. `shelf_py$year$isna()$sum()` reports `0` missing values although `books` has one: the R integer `NA` is the smallest 32-bit integer, and `shelf_py$year$min()` shows it as `-2147483648`. Any statistic computed in pandas treats it as a year, and `pages$mean()` came out negative. pandas has a proper answer, the nullable dtypes (`Int32`, `string`, `boolean`), whose missing value is `pd.NA`. reticulate turns them on with an R option, `reticulate.pandas_use_nullable_dtypes`, set to `TRUE` while converting (NEWS of 1.32.0: reticulate can cast R data frames to pandas data frames with nullable dtypes, opt-in); with it the `year` column is `Int32` with one missing value, the mean of `pages` ignores the two missing values, and the missing values print as `<NA>`.

The option name needs care. The code chunk of the package's "Calling Python from R" article sets `reticulate.pandas_use_nullable_data_types`, while its text and the NEWS entry both say `reticulate.pandas_use_nullable_dtypes`; in the run behind this page only the `dtypes` spelling changed anything (a column converted under the other spelling was still plain `int32`). Use the `dtypes` spelling and check the dtypes you get, as the script does.

=== Getting a data frame back

`py_to_r()` converts a pandas DataFrame to an R `data.frame`, a category column to a factor and a `datetime64` column to `POSIXct`, and the nullable dtypes to integer, logical or character vectors with `NA`. The index is not a column: it is stored in the `pandas.index` attribute of the result, and a string index also becomes the row names. This matters after `groupby()`, whose group labels are the index, and that is why the script resets the index before converting. pandas does the work here; R only receives the table.

=== The same file read on either side

Python has its own CSV reader. Reading `books.csv` with `pd$read_csv()` returns a data frame converted on the way out, and the two readers disagree about empty fields: R's `read.csv()` keeps an empty string in a character column and makes the numeric blanks `NA`; `read_csv()` reads every empty field as missing. The numbers also arrive as doubles when a column has missing values (NumPy has no integer `NA`), and the missing ones are `NaN` rather than `NA`. The arguments of `read_csv()` reproduce what R does, here with nullable integers for `year` and `pages`. The script runs in the directory that holds `books.csv`.

=== Dates and times

Dates and times need the most care at the boundary. An R `Date` becomes a Python `datetime.date`, so a `Date` column is an object column of `date` objects, and it returns as a list column with one `Date` per element. An R `POSIXct` becomes `datetime64[ns]`, the dtype pandas has for instants, and returns as `POSIXct`. (The NEWS of 1.36.0 says that a `POSIXt` vector with a non-empty `tzone` attribute converts to `datetime.datetime` values; in the data frame column below, which has the time zone `"UTC"`, the dtype was `datetime64[ns]`.) The practical rule is to convert `Date` columns to `POSIXct` before crossing, with a time zone, and to convert back with `as.Date()`. The missing values need the same care as the numbers: an `NA` in a `Date` column cannot be converted at all, and a missing `POSIXct` becomes `NaT`, pandas' missing time.

[source,r]
----
source("scenario.R")
library(reticulate)
pd <- import("pandas", convert = FALSE)

first <- loans[1:4, c("loan_id", "loan_date", "return_date")]

# A Date column becomes a pandas object column of datetime.date values ...
as_dates <- r_to_py(first)
as_dates$dtypes
#> loan_id           str
#> loan_date      object
#> return_date    object
#> dtype: object

# ... and comes back as a list column, which is rarely what you want.
class(py_to_r(as_dates)$loan_date)
#> [1] "list"

# A POSIXct column becomes datetime64[ns] and round-trips.
first$loan_date <- as.POSIXct(first$loan_date, tz = "UTC")
first$return_date <- as.POSIXct(first$return_date, tz = "UTC")
as_times <- r_to_py(first)
as_times$dtypes
#> loan_id                   str
#> loan_date      datetime64[ns]
#> return_date    datetime64[ns]
#> dtype: object
as_times
#>   loan_id  loan_date return_date
#> 1    L001 2025-01-14  2025-02-04
#> 2    L002 2025-01-16  2025-01-26
#> 3    L003 2025-01-21  2025-01-22
#> 4    L004 2025-01-26  2025-02-21
back <- py_to_r(as_times)
class(back$loan_date)
#> [1] "POSIXct" "POSIXt"
attr(back$loan_date, "tzone")
#> NULL
as.Date(back$loan_date)
#> [1] "2025-01-14" "2025-01-16" "2025-01-21" "2025-01-26"

tryCatch(r_to_py(missing_date), error = \(e) conditionMessage(e))
#> [1] "ValueError: year -2147483648 is out of range\nRun `reticulate::py_last_error()` for details."
missing_date$loan_date <- as.POSIXct(missing_date$loan_date, tz = "UTC")
r_to_py(missing_date)
#>    loan_id  loan_date
#> 19    L019 2025-07-02
#> 20    L020        NaT
#> 21    L021 2025-07-05

  c("2025-02-30", "2025-01-14"),

#> DatetimeIndex(['NaT', '2025-01-14'], dtype='datetime64[us]', freq=None)

Source: https://rstudio.github.io/reticulate/articles/calling_python.html[reticulate package documentation: Calling Python from R]

The error in the middle is a real one: the missing date was stored as an integer sentinel, and the conversion to a `datetime.date` rejected it with "year -2147483648 is out of range". The time zone is not restored on the return trip (the `tzone` attribute is `NULL`), so how the values print depends on the time zone of the R session; set it explicitly when it matters. The last call is pandas' own parser, which also shows the pandas 3 resolution change: the dtype of the result is `datetime64[us]`. The `loans` data of the scenario has the impossible date `2025-02-30` for this reason, and `errors = "coerce"` is how pandas turns it into `NaT` where R's `as.Date()` returns `NA`.

=== Copy-on-write: who owns the data

An R object is copied when it is modified (xref:programming-languages/r/assignment-names-and-values.adoc[Assignment, Names and Values] introduces copy-on-modify, and xref:programming-languages/r/memory-and-copy-semantics.adoc[Memory and Copy Semantics] goes deeper), and pandas 3.0 now behaves the same way for the user: a subset or a returned object never changes its parent. A data frame is converted column by column, and in the run below a change made on the Python side did not reach the R data frame; treat the two as separate objects. NumPy arrays are different, because a matrix shares its memory with R (<<numpy>>).

[source,r]
----
library(reticulate)
pd <- import("pandas")
pd$`__version__`
#> [1] "3.0.6"

# Since pandas 3.0 a column taken from a data frame behaves as a copy, so
# changing it never changes the data frame it came from.
py_run_string("
import pandas as pd
df = pd.DataFrame({'pages': [100, 200, 300]})
column = df['pages']
column.iloc[0] = 0
")
py$df
#>   pages
#> 1   100
#> 2   200
#> 3   300
py$column
#>   0   1   2
#>   0 200 300

# The R object that was sent over is a separate copy as well.
shelf_pages <- data.frame(pages = c(100L, 200L, 300L))
py$shelf_py <- r_to_py(shelf_pages)
py_run_string("shelf_py.iloc[0, 0] = 0")
shelf_pages
#>   pages
#> 1   100
#> 2   200
#> 3   300
py$shelf_py
#>   pages
#> 1     0
#> 2   200
#> 3   300
----

Source: https://pandas.pydata.org/docs/whatsnew/v3.0.0.html[pandas documentation: What's new in 3.0.0]

Before pandas 3.0, whether a derived object was a copy or a view depended on the operation performed, which the release notes call often confusing; under pandas 3 the column `column` is a copy as far as the user can tell, so `py$df` is unchanged while `py$column` shows the edit. The second half shows that a Python-side edit to a DataFrame built from an R data frame left the R data frame alone.

[#numpy]
== R and NumPy arrays

NumPy's `ndarray` is the Python library's dense array, and the conversion between it and an R matrix or array is the other half of the interface. The conversion rules are simple; the memory layout is what needs explaining, because R and NumPy order the elements of a matrix differently and reticulate does not hide that.

=== Column-major and row-major

A two-dimensional array is stored in memory as one long run of elements, and the layout decides which neighbours in the run are neighbours in the matrix. R, Fortran, MATLAB and the BLAS store a matrix column by column ("column-major" or Fortran order): the first index varies fastest. NumPy's default is row by row ("row-major" or C order): the last index varies fastest. A 2 by 3 matrix whose elements are numbered in memory order from 1 to 6 therefore reads like this in the two layouts.

[cols="2,3,3",options="header"]
|===
|Memory order |R (column-major) |NumPy default (row-major)
|1, 2, 3, 4, 5, 6 |`matrix(1:6, nrow = 2)` is rows `1 3 5` and `2 4 6` |`np.arange(1, 7).reshape(2, 3)` is rows `1 2 3` and `4 5 6`
|===

Source: https://rstudio.github.io/reticulate/articles/arrays.html[reticulate package documentation: Arrays in R and Python]

NumPy can use either layout and records which one an array has in its `flags` (`C_CONTIGUOUS` and `F_CONTIGUOUS`) and in its `strides`, the number of bytes to step to reach the next element along each axis. That generality is what lets reticulate hand an R matrix to NumPy without rearranging it: the array is a view of the same memory, marked Fortran-ordered. The Arrays in R and Python article states the three rules to remember: dense R arrays are presented to NumPy as column-major arrays; all NumPy arrays, whatever their layout, are presented to R as column-major arrays, because that is the only dense layout R has; and R and Python print n-dimensional arrays differently, with NumPy grouping by the first index, which makes a correct conversion look wrong.

[source,r]
----
library(reticulate)
np <- import("numpy", convert = FALSE)

# An R matrix is column-major; NumPy sees the same data without copying it.
m <- matrix(1:6, nrow = 2)
m
#>      [,1] [,2] [,3]
#> [1,]    1    3    5
#> [2,]    2    4    6
a <- r_to_py(m)
a
#> array([[1, 3, 5],
#>        [2, 4, 6]], dtype=int32)
a$shape
#> (2, 3)
a$flags
#>   C_CONTIGUOUS : False
#>   F_CONTIGUOUS : True
#>   OWNDATA : False
#>   WRITEABLE : False
#>   ALIGNED : True
#>   WRITEBACKIFCOPY : False
#>
a$strides
#> (4, 8)

# The array is a read-only view of R's memory, so Python cannot change it.
py$a <- a
tryCatch(py_run_string("a[0, 0] = 99"), error = \(e) conditionMessage(e))
#> [1] "ValueError: assignment destination is read-only\nRun `reticulate::py_last_error()` for details."
m[1, 1]
#> [1] 1

# np$array() makes a writable copy and keeps R's column-major layout.
copy <- np$array(m)
copy$flags$owndata
#> True
copy$flags$writeable
#> True
copy$flags$f_contiguous
#> True

# np_array() copies into the layout and type you ask for.
c_order <- np_array(m, order = "C")
c_order$flags$c_contiguous
#> True
c_order$flags$owndata
#> True
c_order$strides
#> (12, 4)
np_array(m, dtype = "float64")
#> array([[1., 3., 5.],
#>        [2., 4., 6.]])

# NumPy arrays always come back to R as a column-major copy.
rows <- np$arange(1L, 7L, dtype = "int32")$reshape(2L, 3L)
rows$flags$c_contiguous
#> True
back <- py_to_r(rows)
back
#>      [,1] [,2] [,3]
#> [1,]    1    2    3
#> [2,]    4    5    6
dim(back)
#> [1] 2 3
----

Source: https://numpy.org/doc/stable/reference/generated/numpy.ndarray.flags.html[NumPy documentation: ndarray.flags]

Read the flags. The array made from the R matrix is `F_CONTIGUOUS`, not `C_CONTIGUOUS`; `OWNDATA` is `False`, which says that it does not own its memory (it is a view of R's), and `WRITEABLE` is `False`: in reticulate 1.47.0 with NumPy 2.5.4 Python cannot modify an R matrix through the view, and the attempt raises `ValueError: assignment destination is read-only`, which is protection for R's copy semantics. The strides `(4, 8)` mean four bytes down a column (the next row of the same column) and eight bytes along a row (two integers of four bytes, the next column), the signature of column-major `int32`. The package article describes the same thing: R arrays are copied to Python only when they need to be, otherwise the data are shared, and Python arrays are always copied into R. Use `np$array(m)` for a writable copy that keeps R's layout (its `OWNDATA` is `True`), and `np_array(m, order = "C")` for a row-major copy with the data type you choose (`dtype = "float64"` above): do that when the NumPy code that follows walks the array row by row, for which the C layout is faster. Neither changes any value or the matrix's shape or the way it is indexed.

NumPy to R is always a copy, in column-major order. The matrix `back` has the same two rows and three columns and the same values as the NumPy array `rows`: the layout of the copy changed, not the array. That is the second rule at work: indexing `back[1, 2]` and `rows[0, 1]` reads the same element, and what differs is only the order in which each library would print or walk the data.

=== Reshaping and transposing

Reshaping is where the layouts bite. R's `+dim<-+` reinterprets the vector column by column; NumPy's `reshape` reads the elements in C order unless it is told otherwise. A script that reshapes in R and a script that reshapes in Python can therefore produce transposed results from the same vector. `array_reshape()` is the reticulate function that reshapes an R array with NumPy's semantics: it fills the new dimensions in row-major order by default (`order = "C"`), or column-major with `order = "F"`, in which case it agrees with `+dim<-+`. The base R tools to move between the layouts are `matrix(byrow = TRUE)` for two dimensions, `t()` and `aperm()` to permute the axes of a higher array.

[source,r]
----
library(reticulate)
np <- import("numpy", convert = FALSE)

# dim<- fills column by column; array_reshape() fills row by row, like NumPy.
v <- 1:6
array_reshape(v, c(2, 3))
#>      [,1] [,2] [,3]
#> [1,]    1    2    3
#> [2,]    4    5    6
array_reshape(v, c(2, 3), order = "F")
#>      [,1] [,2] [,3]
#> [1,]    1    3    5
#> [2,]    2    4    6
dim(v) <- c(2, 3)
v
#>      [,1] [,2] [,3]
#> [1,]    1    3    5
#> [2,]    2    4    6

# array_reshape() agrees with NumPy's default reshape (it returns doubles).
rows <- np$arange(1L, 7L, dtype = "int32")$reshape(2L, 3L)
all.equal(array_reshape(1:6, c(2, 3)), py_to_r(rows))
#> [1] TRUE

# Row-major data in R: byrow = TRUE for matrices, aperm() for higher arrays.
matrix(1:6, nrow = 2, byrow = TRUE)
#>      [,1] [,2] [,3]
#> [1,]    1    2    3
#> [2,]    4    5    6
cube_np <- np$arange(1L, 25L, dtype = "int32")$reshape(4L, 3L, 2L)
cube_r <- aperm(array(1:24, c(2, 3, 4)), c(3, 2, 1))
identical(py_to_r(cube_np), cube_r)
#> [1] TRUE

# The same array, indexed from 1 in R and from 0 in Python.
y <- array(1:24, c(4, 3, 2))
x <- np$array(y)
x$shape
#> (4, 3, 2)
x$flags$f_contiguous
#> True
identical(py_to_r(x[0L]), y[1, , ])
#> [1] TRUE
y[1, , ]
#>      [,1] [,2]
#> [1,]    1   13
#> [2,]    5   17
#> [3,]    9   21

# Python prints the first axis outermost, so the same data looks different.
x[0L]
#> array([[ 1, 13],
#>        [ 5, 17],
#>        [ 9, 21]], dtype=int32)
----

Source: https://rstudio.github.io/reticulate/reference/array_reshape.html[reticulate package documentation: array_reshape]

The first three results are the whole story: `array_reshape(v, c(2, 3))` gives rows `1 2 3` and `4 5 6`, the same as NumPy; `array_reshape(v, c(2, 3), order = "F")` and `+dim(v) <- c(2, 3)+` give the transposed fill. The comparison with NumPy is `all.equal()` and not `identical()` because `array_reshape()` returns doubles while the NumPy array was `int32`. The three-dimensional array `y` shows the printing rule: `x[0L]` in Python (the first slab along the first axis) has the same values as `y[1, , ]` in R, a 3 by 2 matrix, although the two outputs are printed differently. The instruction for the reverse (making an R array that a C-ordered NumPy expects) is the `aperm(array(1:24, c(2, 3, 4)), c(3, 2, 1))` of the script, which reproduces NumPy's `arange(1, 25).reshape(4, 3, 2)`. The functions are described in the help pages of `dim`, `aperm`, `matrix` and `array`.

=== Calling NumPy on R vectors

Most of the time a NumPy call is a function on an R vector, and the conversion is invisible. The R vector becomes a list, NumPy builds an array from it, and the result is converted back. What is not invisible is that NumPy and R use different defaults for the same statistic. The script computes the median and the 90th percentile of the loan durations with NumPy and with R and shows the agreement once the defaults are aligned.

[source,r]
----
source("scenario.R")
library(reticulate)
np <- import("numpy")

# Loan durations in days for the loans that were returned and have valid dates.
returned <- loans[!is.na(loans$loan_date) & !is.na(loans$return_date), ]
days <- as.numeric(returned$return_date - returned$loan_date)
length(days)
#> [1] 52

# NumPy and R agree once the defaults are lined up: np.percentile interpolates
# linearly, like quantile(type = 7), and np.std divides by n unless ddof = 1.
np$percentile(days, c(50, 90))
#> [1] 21.0 28.9
quantile(days, c(0.5, 0.9), names = FALSE)
#> [1] 21.0 28.9
np$std(days)
#> [1] 9.007804
sd(days)
#> [1] 9.095687
np$std(days, ddof = 1L)
#> [1] 9.095687

# A vector goes in as a list and comes back as a one-dimensional R array.
np$cumsum(days[1:5])
#> [1] 21 31 32 58 84
class(np$cumsum(days[1:5]))
#> [1] "array"
----

Source: https://search.r-project.org/R/refmans/stats/html/quantile.html[R documentation: quantile]

`np.percentile` interpolates linearly by default, which is `type = 7` of `quantile()` (R's default), so the two agree; `np.std` divides by the number of observations, `sd()` by the number minus one, so `ddof = 1L` is needed for them to agree. This is a general pattern when moving a statistic between libraries: check the default of the same-named function on both sides, as xref:programming-languages/r/descriptive-statistics-and-tests.adoc[Descriptive Statistics and Tests] does for R's own tests.

[#packages]
== Python in an R package

A package that wraps a Python library has three jobs: declare the Python dependency, avoid starting Python when the package loads, and find the user's environment. reticulate's article on use in an R package gives the current recipe. Since 1.41 the package calls `py_require()` from `.onLoad()` to declare its Python packages, which combine with the user's and other packages' declarations and have no effect on users who manage their own Python. The module is imported with `delay_load = TRUE`, so that loading the R package neither fails when Python is missing (important for CRAN checks) nor locks in an interpreter before the user has chosen one. Python code that ships with the package lives in `inst/python` and is imported with `import_from_path()`. The package should avoid `use_virtualenv(required = FALSE)` and the DESCRIPTION-based mechanisms of the older recipes, which `py_require()` replaces. The fragment shows the recommended `.onLoad()` and an `inst/python` module; the package itself is built as in xref:programming-languages/r/creating-packages.adoc[Creating Packages] and its namespace works as in xref:programming-languages/r/packages-libraries-and-namespaces.adoc[Packages, Libraries and Namespaces].

[source,r]
----
# R/zzz.R in a package that wraps a Python module (a fragment, not run).
isbn <- NULL

.onLoad <- function(libname, pkgname) {
  # reticulate::py_require("pandas") would go here if isbn.py needed it.
  path <- system.file("python", package = pkgname)
  isbn <<- reticulate::import_from_path("isbn", path = path, delay_load = TRUE)
}

is_valid_isbn13_py <- function(x) {
  vapply(x, isbn$is_valid_isbn13, logical(1), USE.NAMES = FALSE)
}
----

Source: https://rstudio.github.io/reticulate/articles/package.html[reticulate package documentation: Using reticulate in an R Package]

reticulate itself needs Python only at run time (its DESCRIPTION lists `SystemRequirements: Python`), so the package should also skip its Python-dependent tests when `py_module_available()` says the module is absent: `testthat::skip_if_not(py_module_available("pandas"))` is the usual form, as xref:programming-languages/r/testing-with-testthat.adoc[Testing with testthat] describes for conditional skips. For reproducibility renv can record the Python side of a project as well: `renv::use_python()` creates a project-local Python environment and `snapshot()` and `restore()` then track a `requirements.txt` next to `renv.lock` (renv package documentation: Using Python with renv; see xref:programming-languages/r/reproducible-environments-with-renv.adoc[Reproducible Environments with renv]).

== Python in reports and apps

The same interpreter serves the other tools of this group. In R Markdown, reticulate provides the `python` chunk engine, which is enabled whenever reticulate is installed (knitr 1.18 and later) and shares one Python session across all the chunks of a document; R chunks reach Python objects through `py`, and Python chunks reach R objects through an `r` object. In Quarto, a document that has both `python` and `r` code blocks is run with the Knitr engine and the reticulate package executes the Python content (Quarto documentation: Execution Options). Reports and the `python` engine are the subject of xref:programming-languages/r/reports-with-quarto-and-r-markdown.adoc[Reports with Quarto and R Markdown]. A Shiny app or a plumber API that calls Python through reticulate loads the interpreter once per R process, which is a design point for deployment: see xref:programming-languages/r/shiny-plumber-and-web-apis.adoc[Shiny, plumber and Web APIs], and for the equivalent in the other direction (a Python web service serving data-science code) xref:backend/fastapi/serving-data-science-and-ai.adoc[Serving Data Science & AI]. When the Python code is large or must run in another process, a small HTTP API (xref:programming-languages/r/http-and-web-apis.adoc[HTTP and Web APIs]) or a file format such as JSON (xref:programming-languages/r/serialization-rds-rdata-and-json.adoc[Serialization: RDS, RData and JSON]) between two programs is simpler than embedding, and it is the better choice whenever you cannot control the Python installation of the machine.

[#elsewhere]
== The same idea elsewhere: embedding and extending

reticulate is an embedding: the host language (R) starts a Python interpreter in its own process and talks to it through the interpreter's C API, converting values at the boundary. The reverse, an extension, is a library written in another language and loaded by Python as a module. xref:programming-languages/rust/python-interop-with-pyo3.adoc[Python Interop with PyO3] shows both for Rust: a `pass:c[#[pyfunction\]]` compiled into an extension module that Python imports (extending), and a Rust program that starts an interpreter and calls into it (embedding), with the GIL and Python's error types playing the part that the interpreter's global state, the conversion rules and `py_last_error()` play here. The two pages answer the same design questions: who owns the interpreter, how do values cross, how do errors cross, and where does the memory live. In R the extension side is the job of xref:programming-languages/r/interfacing-c-cpp-and-fortran.adoc[Interfacing C, C{pp} and Fortran]; for Fortran code that is called from Python the Fortran Reference has xref:programming-languages/fortran/calling-fortran-from-c-cpp-and-python.adoc[Calling Fortran from C, C{pp} and Python]. And reticulate has a neighbour in the other direction: the rpy2 package embeds R in Python, which is the same arrangement with the roles exchanged.

The Python Reference pages that matter here are xref:programming-languages/python/numbers.adoc[Numbers] (the integers and floats of the conversion rules), xref:programming-languages/python/collections.adoc[Collections] (lists, tuples, dicts and sets), xref:programming-languages/python/modules-and-packages.adoc[Modules and Packages] (what `import()` does) and xref:programming-languages/python/exceptions.adoc[Exceptions] (what `py_last_error()` shows).

|`use_condaenv("r-reticulate")` and Anaconda as the default Python |`py_require()`, or a venv chosen with `use_virtualenv()` or `RETICULATE_PYTHON` |Anaconda is no longer the default path; reticulate prompts for a venv, then manages an ephemeral one |1.31 and 1.41
|`py_install("pandas")` at the top of every script |`py_require("pandas")` |`py_install()` changes the machine each time, and `py_require()` declares the dependency for the session without installing into a shared environment |1.41
|`reticulate::conda_create()` and `conda_install()` in every project |`py_require()`, or `virtualenv_create()` when a persistent environment is needed |the vignettes now carry a banner of updated guidance against manual installations |1.41
|`install_miniconda()` expected to give Miniconda |It installs miniforge |the default conda distribution changed |1.44.0
|`py_run_string()` or `repl_python()` calls inside R chunks to run Python in a report |a `python` chunk with the reticulate engine, in R Markdown or Quarto |the engine shares one session between languages and is on by default |knitr 1.18
|`knitr::knit_engines$set(python = reticulate::eng_python)` |nothing: the engine is registered when reticulate is installed |no setup chunk is needed |knitr 1.18
|`pandas < 2` dtype behaviour: `object` for strings, `SettingWithCopyWarning`, nanosecond datetimes everywhere |pandas 3: `str` dtype, copy-on-write, inferred datetime resolution |see <<pandas-3>>; pandas 3 needs reticulate 1.45 or later |pandas 3.0.0 and reticulate 1.45.0
|The `rPython` and `PythonInR` packages |reticulate |both were removed from CRAN (`rPython` was archived on 2020-04-13 because of check problems; `PythonInR` on 2021-01-27 at the maintainer's request, and its CRAN page recommends reticulate) |2020 and 2021
|`+Sys.setenv(RETICULATE_PYTHON = ...)+` somewhere in the middle of a script |set it in `.Renviron`, or before anything uses Python |the variable is read when Python initialises; after that the interpreter is fixed for the session |always
|===
