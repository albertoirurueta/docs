A package is the unit in which R code is shared: a directory with a `DESCRIPTION` file that says what the code is, a `NAMESPACE` file that says which names it offers and which it borrows, and the code, documentation, data and tests that belong with it. This page explains what each part of that directory is for, which fields and directives R understands, how the usual tools write them, and how a source directory becomes something other people can install. The same steps are then done by hand with the `R CMD` commands that ship with R, so that nothing about the tooling is a mystery when it prints a warning.

Every example is a script that was run with `Rscript` on R 4.6.1 with warnings printed as they happen (`options(warn = 1)`), and the lines that start with `+#>+` are what it printed. The scripts pass the default `lintr` linters. The package that the page builds is called `shelf`. It is the analysis side of the running library-shelf scenario described on the xref:programming-languages/r/index.adoc[section index]: the same `books` and `loans` data frames, the same `book` class and the same overdue-loan analyses, packaged. It was created, documented, tested, built and checked for real with the tools on this page, and its files are shown as the tools wrote them (the R code of the step-by-step section as excerpts). The package directory is written `+~/shelf+` throughout, and the longer absolute paths that some messages print were shortened to it ("paths shortened"). Blocks that show a file of the package (`R/book.R`, `DESCRIPTION`, `NAMESPACE`) are package sources, not scripts: they define functions and metadata for the package and are not run by `Rscript`; they were checked with lintr's `lint_package()`, which sees the whole package at once. Blocks that show the calls of the recorded creation session (the usethis steps) are fragments of that one session, and the text before them says so. Check output is shown without its first lines: the platform header (the operating system, the compiler, the time and the temporary directory) is left out, and every check step that is shown comes from the real run.

== What a package is

R's own manual defines the word precisely, and the rest of the page depends on the definition. A package is a directory of files that extend R, and the manual distinguishes three things that people all call "the package": the source package (the master files), a tarball that contains the files of a source package, and the installed package, which is the result of running `R CMD INSTALL` on a source package. On some platforms there is a fourth, a binary package: a compressed copy of an installed package that can be unpacked instead of built. The R FAQ (question 5.5, "How can I create an R package?") gives the same list of subdirectories and files and says that a package consists of a subdirectory containing a file `DESCRIPTION` and the subdirectories `R`, `data`, `demo`, `exec`, `inst`, `man`, `po`, `src` and `tests`, some of which can be missing. R itself is distributed with about thirty packages (`base`, `stats`, `utils`, `methods` and the recommended ones), and they are built exactly like yours.

Two terms are easy to confuse. A package is not a library: a library is a directory into which packages are installed, so a library is a folder of package folders (R FAQ 7.29, "What is the difference between package and library?", says the same in one sentence: a package is a standardized collection of material extending R, and a library is a place where R knows to find packages). `library(shelf)` therefore means "find the package `shelf` in a library and load it". The other confusing word is "compile". Installing a package that contains C, C{pp} or Fortran code compiles that code, but a package of R code only is not compiled: R byte-compiles its functions on installation, which has been the default for every package since R 3.5.0 (the NEWS of R 3.5.0 lists it among the significant user-visible changes), and Writing R Extensions points out that compilation is not a correct term for a package of R code.

Why write a package at all, even for private code? A package gives a bundle of functions a name, a version and a place to live. Its namespace keeps its internal helpers from clashing with names in the user's workspace and says what is public. Its documentation is checked against its code, so a renamed argument that nobody documented is reported. Its tests run in a clean session against the installed code. Its dependencies are declared, so installing it installs what it needs, and a missing dependency is an error at install time instead of a surprise at run time. The cost of all that was once a day of reading manuals, and it is now a few commands, which is why the usual advice is to turn a collection of scripts into a package as soon as a second project reuses it. A package does not have to be published: the same directory can be installed from a local path or from a tarball on a shared disk, and the rest of the page never needs a network.

== The five states of a package

A package is not one thing but a thing in five different states. The community book R Packages (a free online book by the authors of the tools used below) names them: a source package, a bundled package, a binary package, an installed package and an in-memory package, and the page uses its vocabulary because it matches the manual. Each state is produced from an earlier one by one command, and every problem a package author meets happens at one of those steps, which is why the figure puts the command on each arrow. The left half of the figure is the directory that the next section opens, and the dashed boxes in it are the entries that `R CMD build` leaves out of the bundle.

The steps are one-way and each one adds something. The build step runs the vignettes, because a bundle should not need knitr or pandoc on the machine that installs it. The install step lays the package out as R reads it: the code of `R/` is evaluated once and stored in a lazy-load database (`R/shelf.rdb` and `R/shelf.rdx`), so loading the package does not run your top-level code again, and the help pages are converted into a database as well. A binary package is that installed layout in a tarball; the section on `R CMD INSTALL` lists its contents. The in-memory state is where almost all of the confusion about packages comes from: `library()` performs two steps, loading the namespace and attaching the package to the search path, and a namespace can be loaded without being attached, which is what `shelf::normalise_isbn()` does. The page returns to the difference when the load hooks are explained, and xref:programming-languages/r/packages-libraries-and-namespaces.adoc[Packages, Libraries and Namespaces] covers it from the user's side.

Because the five states are different files, the same package can behave differently in two of them, and most "it works on my machine" reports are of this kind. A function that reads a file with a path relative to the source tree works under `load_all()` and fails when installed; a helper that is not exported is visible from inside the package and from a `load_all()` session but not to `library()` users; a dataset that was never saved into `data/` exists in the author's workspace and nowhere else. The tools below exist to test the package in the state the user will have it in, and the habit that pays is to run `R CMD check` on a bundle, because the bundle is the state in between that the rest of the world sees.

Two files are the heart of every package and are not optional: `DESCRIPTION` and, in practice, `NAMESPACE` (every package has a namespace since R 2.14.0 in October 2011; if the author wrote no file, `R CMD build` creates a default one, as the NAMESPACE section shows). Everything else is a directory that R knows by name. Writing R Extensions lists the subdirectories that R reads: `R`, `data`, `demo`, `exec`, `inst`, `man`, `po`, `src`, `tests`, `tools` and `vignettes`; some of them can be missing, but none of them should be empty. The table gives each entry, what reads it, and what `shelf` puts there.

Writing R Extensions asks that the package subdirectory be given the same name as the package, that file names be portable (ASCII letters, digits, `.`, `_` and a handful of other characters, no two names that differ only by case, no Windows device names such as `con` or `aux`), and that a package not contain Unix-style hidden files, with a few exceptions that the tools need. The tree above has several (`.Rbuildignore`, `.gitignore`, `.lintr` and `vignettes/.gitignore`), and the build handles them in different ways: `.Rbuildignore` is read by `R CMD build` and left out of the bundle, together with the files of version-control tools such as `.gitignore`, and `.lintr` is excluded by a pattern of `.Rbuildignore` itself. `.Rinstignore` is the exception that goes the other way: it is shipped, because it is read at installation. Any other hidden file is bundled, and the check reports it, as the real run below shows.

=== The R/ directory

The R code files are read in the C locale's alphabetical order, so the order in which functions are defined does not matter for a function that is only called later: a function body is evaluated when it is called, not when it is defined. The manual says that it should be possible to read the files with `source()`, that the files should assign R objects and not call functions with side effects such as `library()`, `require()` or `options()`, and that there need be no connection between a file name and the objects defined in it. `shelf` follows the common practice of one file per topic (`book.R` for the class, `isbn.R` for ISBN handling, `clean.R`, `loans.R`) and a file called `zzz.R` for the load hooks, which sorts last.

There is a consequence of this rule that surprises everyone once. The files are evaluated at installation, and the objects they create are stored in the installed package, so a top-level expression is computed once, when the package is installed, not every time it is loaded. A definition of today's date at the top level of a file freezes the date of the installation into the package. That is why `shelf` defines `shelf_today()`, a function that returns the current date and is evaluated when it is called (the same function can be replaced in tests, a trick the testing page uses), and why `overdue_loans()` takes `today` as an argument.

Where the order of the files does matter, for example when a top-level call in one file needs an object that another file creates, or when an S4 class must exist before its methods, the `Collate` field of `DESCRIPTION` lists the order. Writing it by hand is error-prone, so roxygen2 writes it from `@include` tags; the DESCRIPTION section shows the real result.

Only ASCII characters should appear in the code files. Other characters are accepted in comments, but the comments may not read correctly in every locale, and non-ASCII characters in object names normally fail at installation. A string that needs a non-ASCII character is written with a `\u` escape, and `R CMD check` warns about the rest ("checking code files for non-ASCII characters" in the section on reading the output of `R CMD check`, which shows the real warning).

=== The man/ directory

The `man/` subdirectory holds the help pages, in R's own documentation format Rd, one `.Rd` file per topic. `R CMD check` compares them with the code: every exported object must have an entry, every argument in `\usage` must be described, and the `\usage` must match the function's real signature (the steps named "checking for missing documentation entries" and "checking for code/documentation mismatches" in the log). Nobody writes Rd files by hand any more. roxygen2 turns the comments above each function into them, which is why the first line of every file in `man/` says "% Generated by roxygen2: do not edit by hand". Rd itself, the tags and the vignettes are the subject of xref:programming-languages/r/documentation-with-rd-roxygen2-and-vignettes.adoc[Documentation with Rd, roxygen2 and Vignettes], and this page only uses them.

=== The tests/ directory

`R CMD check` runs the R files in `tests/` in a clean session with the package installed, and compares each output with a `.Rout.save` file if there is one. testthat's convention is one tiny file, `tests/testthat.R`, that loads the package and calls `test_check("shelf")`, and a directory `tests/testthat/` of `test-*.R` files, helper files and fixtures. The same call is made by `devtools::test()`, which runs the tests against the loaded source. The details are the subject of xref:programming-languages/r/testing-with-testthat.adoc[Testing with testthat]; for this page it is enough to know that the tests are part of the package and are executed by the check, and that `R CMD check --no-tests` skips them.

=== The vignettes/ directory

A vignette is a long-form document that is part of the package: a tutorial that runs real code against the package. The sources live in `vignettes/`, `R CMD build` runs them and stores the output in `inst/doc` of the bundle, and `R CMD INSTALL` installs that output. The `VignetteBuilder` field names the package that knows how to run them (`knitr` here), and that package, and `rmarkdown` for the `html_vignette` output, must be in `Suggests`. The build runs the vignettes with the package installed into a temporary library, which is why the build log says "installing the package (it is needed to build vignettes)". A tree that has `vignettes/` but a bundle without `inst/doc` is reported by the check, as the section on reading the output of `R CMD check` shows.

=== The src/ directory and compiled code

A package can contain C, C{pp} and Fortran sources in `src/`. When it is installed, `make` compiles them into one shared object that R loads with the namespace, using `useDynLib()` in `NAMESPACE`. Compiled code needs the dependency field `LinkingTo` for header-only packages such as Rcpp, a `NeedsCompilation` field set by the build, and a compiler on the machine that installs the package from source (Rtools on Windows, the Xcode command-line tools on macOS). `shelf` has no `src/` and the page treats the subject in one place: the DESCRIPTION and NAMESPACE sections name the fields and directives, and xref:programming-languages/r/interfacing-c-cpp-and-fortran.adoc[Interfacing C, C{pp} and Fortran] writes the code.

=== exec/, demo/, po/ and tools/

Four more directories are rarely needed and are named here so that their names are not a surprise. `exec/` holds scripts that the package needs at run time for an interpreter other than R (a shell, Perl or Python script): only files are installed from it, and they are marked executable. The manual remarks that most packages put such files in `inst/` instead, because `exec/` is not suited to compiled programs (installed packages can serve several architectures). `demo/` holds R scripts that `demo()` runs, with a `00Index` file listing them; they are not run by `R CMD check` unless it is asked to (`--run-demo`, added in R 4.5.0). `po/` holds the translation files for the messages of a package, which Writing R Extensions covers in the chapter on internationalization. `tools/` is the preferred place for auxiliary files needed while configuring a package that has a `configure` script.

=== The .Rbuildignore file

`.Rbuildignore` lists, one regular expression per line, the files and directories that `R CMD build` must not put in the bundle. The expressions are Perl-like and are matched case-insensitively against each path relative to the package root. Because they are regular expressions and not file globs, a dot must be escaped and the two ends should be anchored with `^` and `$`. `shelf` has these four lines, written by the usethis functions that created the files they refer to (`use_mit_license()`, `use_data_raw()`, `use_cran_comments()` and `lintr::use_lintr()`).

[source,text]
----
^LICENSE\.md$
^data-raw$
^cran-comments\.md$
^\.lintr$
----

Source: https://cran.r-project.org/doc/manuals/r-release/R-exts.html#Building-package-tarballs[Writing R Extensions: Building package tarballs]

The script below applies those patterns to a list of paths the way the build does, to make the anchoring visible. `LICENSE.md` and `license.MD` are excluded (the matching ignores case), the directory `data-raw` is excluded, and `R/data-raw-helpers.R` and `R/lintr.R` are kept; the second half of the output shows what the same names would do without anchors: a pattern `data-raw` or `lintr` matches anywhere in a path and would throw away the helper files as well.

[source,r]
----
# .Rbuildignore holds one Perl-style regular expression per line, matched
# case-insensitively against each path relative to the package root.
patterns <- c(
  "^LICENSE\\.md$", "^data-raw$", "^cran-comments\\.md$", "^\\.lintr$"
)
paths <- c(
  "DESCRIPTION", "LICENSE", "LICENSE.md", "license.MD", "data-raw",
  "data-raw/books.R", "R/data-raw-helpers.R", "cran-comments.md",
  ".lintr", "R/lintr.R"
)
is_ignored <- function(path, patterns) {
  hits <- vapply(patterns, grepl, logical(1L), x = path,
                 perl = TRUE, ignore.case = TRUE)
  any(hits)
}
ignored <- vapply(paths, is_ignored, logical(1L), patterns = patterns)
data.frame(path = paths, ignored = ignored, row.names = NULL)
#>                    path ignored
#> 1           DESCRIPTION   FALSE
#> 2               LICENSE   FALSE
#> 3            LICENSE.md    TRUE
#> 4            license.MD    TRUE
#> 5              data-raw    TRUE
#> 6      data-raw/books.R   FALSE
#> 7  R/data-raw-helpers.R   FALSE
#> 8      cran-comments.md    TRUE
#> 9                .lintr    TRUE
#> 10            R/lintr.R   FALSE

# The anchors matter. Without them a pattern matches anywhere in the path.
loose <- c("data-raw", "lintr")
vapply(paths, is_ignored, logical(1L), patterns = loose)
#>          DESCRIPTION              LICENSE           LICENSE.md
#>                FALSE                FALSE                FALSE
#>           license.MD             data-raw     data-raw/books.R
#>                FALSE                 TRUE                 TRUE
#> R/data-raw-helpers.R     cran-comments.md               .lintr
#>                 TRUE                FALSE                 TRUE
#>            R/lintr.R
#>                 TRUE

# "^data-raw$" ignores the directory; R CMD build then does not descend
# into it, so "data-raw/books.R" is not matched on its own and does not
# need to be.
----

Source: https://search.r-project.org/R/refmans/base/html/grep.html[R documentation: grep, grepl and the other regular-expression functions]

The build also leaves out, without being told, some directories and files: those of version-control systems and of editors, directories named `check`, `chm` or ending in `.Rcheck`, `Old` or `old`, files such as `GNUMakefile` and `Read-and-delete-me`, backup files ending in `~`, `.bak` or `.swp`, and the tarballs of earlier builds of the same package (Writing R Extensions, "Building package tarballs"). usethis adds a line for you: `usethis::use_build_ignore("notes.txt")` appends the escaped, anchored `^notes\.txt$`, as the section on reading the output of `R CMD check` shows. A related file, `.Rinstignore`, excludes files of `inst/` from the installation, not from the bundle.

A small experiment on a copy of the package shows the three behaviours of hidden and ignored files at once. The first lines create, inside the package directory, a file `.hidden` at the top level, a directory `inst/extra` with two files, `keep.txt` and `skip.tmp`, and a `.Rinstignore` that holds the pattern `\.tmp$`. Then the commands run from the parent of the package: the bundle is built without the vignettes to keep the run short, the listing shows what ended up in it, the package is installed into a library directory `lib`, and `R CMD check` is run with its slow steps switched off.

[source,bash]
----
cd shelf

== The DESCRIPTION file

`DESCRIPTION` is a plain text file in the format of a Debian control file: a field name, a colon, and a value, with continuation lines that start with a space or a tab. R reads it with `read.dcf()`, `library()` reads it before loading a package, `R CMD INSTALL` copies it into the installed package, and CRAN and every package manager read it to resolve dependencies. Field names are case-sensitive and all the ones R uses are capitalised. Here is the file of `shelf` exactly as the tools left it. The order of the fields is the order in which the tools added them (`Depends` is near the end because `usethis::use_package()` added it after the file existed), and the order has no meaning.

[source,text]
----
Package: shelf
Title: Tools for a Small Library Catalogue
Version: 0.1.0
Authors@R: 
    person("Shelf", "Maintainers", , "maintainer@example.com", role = c("aut", "cre", "cph"))
Description: Cleans a small library catalogue and its loans table,
    validates ISBN-13 strings, and reports overdue loans and overdue rates
    by genre. Ships the example 'books' and 'loans' datasets used by the
    documentation.
License: MIT + file LICENSE
Config/roxygen2/version: 8.1.1
Encoding: UTF-8
Roxygen: list(markdown = TRUE)
Suggests: 
    knitr,
    rmarkdown,
    testthat (>= 3.0.0),
    withr
Config/testthat/edition: 3
Depends: 
    R (>= 4.1.0)
VignetteBuilder: knitr
LazyData: true
----

Source: https://cran.r-project.org/doc/manuals/r-release/R-exts.html#The-DESCRIPTION-file[Writing R Extensions: The DESCRIPTION file]

Writing R Extensions makes seven fields mandatory: `Package`, `Version`, `License`, `Description`, `Title`, `Author` and `Maintainer`. The last two can be generated from `Authors@R` and may be left out if that field is given, and CRAN requires `Authors@R` for a submission, so a modern file has `Authors@R` and not `Author` and `Maintainer`. Everything else is optional. The sections below take the fields in the order in which a new package needs them.

[cols="2,3,6",options="header"]
|===
|Field |Written by |What it does
|`Package`, `Title`, `Version`, `Description` |`usethis::create_package()` |The name, a one-line title in title case, the version and a one-paragraph description.
|`Authors@R` |`create_package()` |R code that builds a `person` object with names, e-mail addresses and roles.
|`License` |`usethis::use_mit_license()` |A standard licence abbreviation, optionally with `+ file LICENSE`.
|`Depends`, `Imports`, `Suggests`, `LinkingTo`, `Enhances` |`usethis::use_package()` and the other `use_*` functions |The packages (and the version of R) that this package needs.

|`Config/testthat/edition`, `Config/roxygen2/version`, `Roxygen` |`use_testthat()` and roxygen2 |Settings of tools, kept in the file so that every contributor gets the same ones.
|`Collate`, `URL`, `BugReports`, `SystemRequirements`, `NeedsCompilation`, `Date`, `Language` |You, roxygen2 or the build |Optional: file order, web addresses, external software, whether there is compiled code, a release date, the language of the documentation.
|===

=== Package, Title and Description

The `Package` field is the name, and the rule is short and strict: only ASCII letters, numbers and dots, at least two characters, a letter first, and no dot at the end. A hyphen or an underscore is not allowed. usethis checks this before it creates anything, and its message names the rules; the first call below is that check.

[source,r]

#> • Have at least two characters.

The output after the error is what a package looks like straight after `create_package()` with no arguments: a `DESCRIPTION` with placeholders (`Title: What the Package Does (One Line, Title Case)`, a made-up author, a version `0.0.0.9000` and a licence field that tells you to pick one), an empty `NAMESPACE` and an empty `R/`. The calls after it show the next three steps, each writing or editing a file: `use_r()` makes `R/squish.R` (the name goes with the function), `use_mit_license()` adds the licence, and `use_news_md()` adds a `NEWS.md`.

A package name is also a name in CRAN's namespace of packages: The CRAN Repository Policy asks that a package be named in a way that does not conflict, irrespective of case, with any current or past CRAN package or any current Bioconductor package. The check that tests it is the incoming one that the section on `R CMD check` runs on `shelf`, which fails, for a reason that is the best illustration of the rule: a package called `SHELF` exists. The name is a decision to make before the first release, and xref:programming-languages/r/publishing-to-cran.adoc[Publishing to CRAN] says what to do about it.

The `Title` is what package lists show. It is a short phrase in title case, with no markup, no continuation lines and no full stop at the end; it should not repeat the package name (it is nearly always displayed after it), and other packages and external software are written in single quotes, such as 'Rcpp' or 'GDAL'. Some listings truncate it at 65 characters, so the first 65 should carry the meaning. `tools::toTitleCase()` applies the capitalisation rules. The `Description` is a paragraph of complete sentences that says what the package does and why it is useful, aimed at everyone who might look for it. It should not start with "This package" or the package name, it uses single quotes for names of software and data (as `shelf` does for 'books' and 'loans'), double quotes for quotations, and angle brackets around URLs, as in `<https://www.r-project.org>`.

=== Version

The `Version` is a sequence of at least two, and usually three, non-negative integers separated by single `.` or `-` characters. It is not a decimal number, so 0.9 is less than 0.75 because 9 is less than 75, and 1.10 is later than 1.9. R represents such versions with `numeric_version` and, for package versions, its subclass `package_version`; `getRversion()` returns the same kind of object for R itself, and `packageVersion()` returns one for an installed package. The script shows what the class does.

[source,r]
----
# Version numbers are not decimals: they are sequences of integers.
v <- package_version(c("0.1.0", "0.1.0.9000", "0.9", "0.75", "1.0.0", "1.0-1"))
v
#> [1] ‘0.1.0’      ‘0.1.0.9000’ ‘0.9’        ‘0.75’       ‘1.0.0’
#> [6] ‘1.0.1’
class(v)
#> [1] "package_version" "numeric_version"
v[[3L]] < v[[4L]]
#> [1] TRUE
sort(v)
#> [1] ‘0.1.0’      ‘0.1.0.9000’ ‘0.9’        ‘0.75’       ‘1.0.0’
#> [6] ‘1.0.1’
max(v)
#> [1] ‘1.0.1’

# The pieces of a version.
x <- package_version("0.1.0.9000")
unlist(x)
#> [1]    0    1    0 9000
x$major
#> [1] 0
x$minor
#> [1] 1
x$patchlevel
#> [1] 0

# Comparisons accept a string on one side.
package_version("1.10.0") > "1.9.0"
#> [1] TRUE
numeric_version("1.10.0") > numeric_version("1.9.0")
#> [1] TRUE
as.numeric("1.10") > as.numeric("1.9")
#> [1] FALSE

# `-` and `.` are equivalent separators, and trailing zeros are not
# significant for comparison.
package_version("1.0-1") == package_version("1.0.1")
#> [1] TRUE
package_version("0.5") == package_version("0.5.0")
#> [1] TRUE
compareVersion("1.10.0", "1.9.0")
#> [1] 1

# What R itself is.
getRversion() >= "4.1.0"
#> [1] TRUE
getRversion() >= "4.7.0"
#> [1] FALSE
is.numeric_version(getRversion())
#> [1] TRUE
class(getRversion())
#> [1] "R_system_version" "package_version"  "numeric_version"

# A malformed version is an error.
tryCatch(package_version("1.0.beta"), error = \(e) conditionMessage(e))
#> [1] "invalid version specification ‘1.0.beta’"

# Installed packages report their version as a package_version.
packageVersion("stats") >= "4.1.0"
#> [1] TRUE
packageVersion("utils")
#> [1] ‘4.6.1’

# Leading zeros are dropped within a component: "0.01" is 0.1.
unlist(package_version("0.01"))
#> [1] 0 1
----

Source: https://search.r-project.org/R/refmans/base/html/numeric_version.html[R documentation: numeric_version, package_version and R_system_version]

The comparisons in the middle of that output are the ones that matter for a package: `package_version("1.10.0") > "1.9.0"` is `TRUE` and the same comparison on decimals is `FALSE`, a string on one side is converted, `-` and `.` separate components in the same way, trailing zeros do not change the comparison, and `getRversion() >= "4.1.0"` is the idiom for code that depends on the R version. The last lines show that a leading zero is dropped inside a component (`"0.01"` is the version 0.1) and that a malformed version is an error.

Most packages use three components, `major.minor.patch`, plus a fourth component while they are in development. The convention, which comes from the community tooling and is not an R rule, is to give a development version a fourth component that starts at `9000`: `0.1.0.9000` is later than the release `0.1.0` and earlier than the next release `0.1.1` or `0.2.0`, so anybody who installs from the repository can tell a released version from a work in progress. usethis automates it with `use_version()`: the argument is `"major"`, `"minor"`, `"patch"` or `"dev"`, and it also edits the heading of `NEWS.md` (and, in a package under Git, commits the change). The script below runs the whole sequence on a copy of `shelf`: a development version, a patch release, a minor release and a development version again.

=== Authors@R and the person class

The `Authors@R` field is R code, evaluated when the package is built or installed, that creates an object of class `person` with `person()`, or several of them joined with `c()`. A person has given and family names, an e-mail address, one or more roles and a comment. The roles are codes from the MARC list of relators, and `?person` suggests how to use them in packages: `"aut"` (author) for people who made substantial contributions and should appear in the citation, `"cre"` (creator) for the maintainer, `"ctb"` (contributor) for smaller contributions, `"cph"` (copyright holder, which has to be the legal name of a person or an institution), `"fnd"` (funder) for who paid for the work, and `"com"`, `"ctr"`, `"dtc"`, `"rev"`, `"ths"` and `"trl"` for compilers, contractors, data contributors, reviewers, thesis advisors and translators. No role is assumed: a person without a role is not listed as an author. The comment can hold an ORCID or a ROR identifier under the names `ORCID` and `ROR`, which `print()` and `format()` turn into links; the identifier in the script is the example iD that ORCID itself uses in its documentation.

[source,r]
----
# Authors@R is R code that builds a "person" object.
authors <- c(
  person("Shelf", "Maintainers", email = "maintainer@example.com",
         role = c("aut", "cre", "cph")),
  person("Ada", "Contributor", role = "ctb",
         comment = c(ORCID = "0000-0002-1825-0097")),
  person("Example Library Fund", role = "fnd")
)
authors
#> [1] "Shelf Maintainers <maintainer@example.com> [aut, cre, cph]"
#> [2] "Ada Contributor [ctb] (ORCID: <https://orcid.org/0000-0002-1825-0097>)"
#> [3] "Example Library Fund [fnd]"

# The pieces are available as fields.
authors$role
#> [[1]]
#> [1] "aut" "cre" "cph"
#> [[2]]
#> [1] "ctb"
#> [[3]]
#> [1] "fnd"
authors[[1L]]$email
#> [1] "maintainer@example.com"
authors[[2L]]$comment
#>                 ORCID
#> "0000-0002-1825-0097"

# R CMD build and R CMD INSTALL derive the Author and Maintainer fields:
format(authors, include = c("given", "family", "role"))
#> [1] "Shelf Maintainers [aut, cre, cph]" "Ada Contributor [ctb]"
#> [3] "Example Library Fund [fnd]"
cre <- Filter(\(p) "cre" %in% p$role, authors)
format(cre, include = c("given", "family", "email"),
       braces = list(email = c("<", ">")))
#> [1] "Shelf Maintainers <maintainer@example.com>"
----

Source: https://search.r-project.org/R/refmans/utils/html/person.html[R documentation: person]

`R CMD build` and `R CMD INSTALL` derive the plain `Author` and `Maintainer` fields from `Authors@R`, which is what the last two lines of the script format: `Author: Shelf Maintainers [aut, cre, cph]` and `Maintainer: Shelf Maintainers <maintainer@example.com>` are in the installed `DESCRIPTION`, as the inspection section shows. The `cre` person needs a valid e-mail address that will keep working for the life of the package, because that is where CRAN writes. The address of `shelf` is a placeholder, which is one more reason why the package cannot be submitted as it is.

=== License

Every package needs a `License` field, and without one it is not even legal for other people to distribute it. R wants the field in a standard form so that tools can tell whether a licence is "free or open source" (FOSS) and whether it restricts use. A licence is written as an abbreviation from R's licence database, optionally with a version restriction, such as `GPL (>= 3)`, `LGPL (>= 2.1)` or `Apache License (== 2.0)`; as one of the standard short forms (`GPL-2`, `GPL-3`, `LGPL-2`, `LGPL-2.1`, `LGPL-3`, `AGPL-3`, `Artistic-2.0`, `BSD_2_clause`, `BSD_3_clause` and `MIT`); as `file LICENSE`, which refers to a file of the package; or as alternatives separated by a vertical bar. "Public domain" is not a valid licence, because it is not recognised everywhere. The script reads the database that ships with R and asks the internal helper that `R CMD check` uses to judge a few specifications.

[source,r]
----
# R keeps a database of recognised licences next to the standard texts.
db <- read.dcf(file.path(R.home("share"), "licenses", "license.db"))
nrow(db)
#> [1] 32
version <- ifelse(is.na(db[, "Version"]), "", paste0(" ", db[, "Version"]))
standard <- paste0(db[, "Abbrev"], version)
head(standard[!grepl("^NA", standard)], 14L)
#>  [1] "GPL 2"        "GPL 3"        "LGPL 2"       "LGPL 2.1"     "LGPL 3"
#>  [6] "AGPL 3"       "CeCILL 2"     "CeCILL 2.1"   "FreeBSD"      "MIT"
#> [11] "BSD_2_clause" "BSD_3_clause" "MPL 1.0"      "MPL 1.1"
sort(list.files(file.path(R.home("share"), "licenses"), pattern = "^[A-Z]"))
#>  [1] "AGPL-3"       "Apache-2.0"   "Artistic-2.0" "BSD_2_clause" "BSD_3_clause"
#>  [6] "CC0-1.0"      "GPL-2"        "GPL-3"        "LGPL-2"       "LGPL-2.1"
#> [11] "LGPL-3"       "MIT"

# `tools:::analyze_license()` is the internal helper that R CMD check uses
# to judge the License field; it is not a stable API, it is shown only to
# see what check sees.
specs <- c("MIT + file LICENSE", "GPL (>= 3)", "GPL-3 | file LICENSE",
           "Apache License (== 2.0)", "Public domain")
verdict <- lapply(specs, \(s) {
  a <- tools:::analyze_license(s)
  data.frame(License = s, canonical = a$is_canonical, FOSS = a$is_FOSS,
             restricts_use = a$restricts_use)
})
do.call(rbind, verdict)
#>                   License canonical FOSS restricts_use
#> 1      MIT + file LICENSE      TRUE TRUE         FALSE
#> 2              GPL (>= 3)      TRUE TRUE         FALSE
#> 3    GPL-3 | file LICENSE      TRUE TRUE         FALSE
#> 4 Apache License (== 2.0)      TRUE TRUE         FALSE
#> 5           Public domain     FALSE   NA            NA
----

Source: https://cran.r-project.org/doc/manuals/r-release/R-exts.html#Licensing[Writing R Extensions: Licensing]

`shelf` uses `MIT + file LICENSE`. The MIT licence is a template: it needs a year and a copyright holder, and R's convention is that a licence that needs additional information is written with `+ file LICENSE`, where `LICENSE` is a small file with the two fields and nothing else. `usethis::use_mit_license()` wrote that file, the full licence text as `LICENSE.md` (which GitHub shows and the bundle does not need: `^LICENSE\.md$` went into `.Rbuildignore`), and the field. The file is two lines.

[source,text]
----
YEAR: 2026
COPYRIGHT HOLDER: shelf authors
----

Source: https://usethis.r-lib.org/reference/licenses.html[usethis package documentation: licenses]

Writing R Extensions says that the copyright holder must be a real legal entity and not something vague such as the name of the package with "authors" added. `use_mit_license()` was called without a name, so it wrote `shelf authors`, which is acceptable for a demonstration and is the kind of thing the CRAN reviewers ask to change; pass your name or your organisation's, as in `use_mit_license("Shelf Maintainers")`. The other functions of the same family write other licences: `use_gpl_license()`, `use_agpl_license()`, `use_lgpl_license()` and `use_apache_license()` (each with a version and an `include_future` argument that makes the licence "or any later version"), `use_cc0_license()` and `use_ccby_license()` for data packages, and `use_proprietary_license()` for code that is not to be shared. They save the standard text as `LICENSE.md` and add it to `.Rbuildignore`, because CRAN does not accept copies of the standard licences inside a package. Which licence to use is the author's choice and a legal one; the rules of the CRAN policy are in xref:programming-languages/r/publishing-to-cran.adoc[Publishing to CRAN].

=== Depends, Imports, Suggests, LinkingTo and Enhances

A package declares what it needs in five fields that differ in what R does with the names.

[cols="2,3,5",options="header"]
|===
|Field |What R does with the packages |Use it for
|`Depends` |Installs them and attaches them to the search path before attaching this package. Also the place to state the minimum version of R. |Packages the user must have attached to use yours, such as the packages whose functions your functions are extensions of, and `R (>= x.y.z)`.
|`Imports` |Installs them and loads their namespaces when this one is loaded, but does not attach them. The names they export are available to this package through `NAMESPACE`, or through `::`. |Packages whose functions the code calls. The default home for dependencies.
|`Suggests` |Does not install them by default. They are needed to run the tests, examples and vignettes, or for an optional feature. |Testing and documentation packages, packages used only conditionally (`requireNamespace()`).
|`LinkingTo` |Makes their C and C{pp} header files available when this package's compiled code is built. |Header-only or header-providing packages such as Rcpp.
|`Enhances` |Nothing is installed. The package says that it adds support for objects or methods from these packages. |Rare: packages for whose objects you provide methods without needing them.
|===

Source: https://cran.r-project.org/doc/manuals/r-release/R-exts.html#Package-Dependencies[Writing R Extensions: Package Dependencies]

The rules in Writing R Extensions fit on a few lines. A package should be listed in only one of the fields. A package whose functions this one calls belongs in `Imports`; `Depends` is only for packages that have to be attached for the user's benefit, and the manual says that the field should be used only rarely nowadays, because attaching a package changes the search path of everybody who loads yours (the xref:programming-languages/r/packages-libraries-and-namespaces.adoc[Packages, Libraries and Namespaces] page explains masking). Packages used to run examples, tests or vignettes belong in `Suggests`, which also lets checkers verify that everything needed for a full check is installed, and code that uses a suggested package must test for it first. Version requirements are written in parentheses with a comparison operator, `testthat (>= 3.0.0)`; for `Depends` and `Imports` R checks them when the package is loaded, and for `Suggests` the code that uses the package is responsible for checking.

`usethis::use_package()` edits the right field, adds a version requirement when asked, and prints the advice that goes with the field. == The NAMESPACE file

A namespace is the part of a package that decides which of its names the world sees and which names it borrows from other packages. Without one, every function a package defines would be dumped into the user's search path, masking what was already there. With one, a package exports a chosen few, keeps the rest private, and states precisely what it imports. Writing R Extensions describes the mechanism: the `NAMESPACE` file at the top of the package holds directives for exports, imports, S3 method registration and shared objects, and although the file looks like R code (and may have R-style comments) it is not processed as R code, apart from a very simple conditional on `if` statements. Loading a package loads its namespace, and attaching it puts only the exports on the search path. Two properties follow. Namespaces are sealed once loaded, so the bindings of a package cannot be changed from outside, and a function's free variables are looked up in a fixed order: first the namespace itself, then the imports, then the base namespace, and only then the global environment and the rest of the search path.

The `NAMESPACE` of `shelf` was written by roxygen2, from the `@export` tags above the functions, the first time `document()` ran. It is a short file and it is complete.

[source,text]
----
# Generated by roxygen2: do not edit by hand

S3method(format,book)
S3method(print,book)
S3method(print,summary.book)
S3method(summary,book)
export(book)
export(clean_books)
export(clean_loans)
export(is_valid_isbn13)
export(loan_summary)
export(loans_per_month)
export(new_book)
export(normalise_isbn)
export(overdue_loans)
export(validate_book)
----

Source: https://cran.r-project.org/doc/manuals/r-release/R-exts.html#Package-namespaces[Writing R Extensions: Package namespaces]

It has two kinds of line. `export(book)` makes the function `book()` available to `library(shelf)` and to `shelf::book`. `S3method(print, book)` registers the function `print.book()` as the `print` method for class `book`, so `print(b)` dispatches to it. The function itself, `print.book`, is not exported and does not need to be, which is the point of registration: the generic `print` finds the method in a table that `library()` fills, not by searching for a name. All four methods of the `book` class are registered this way, and the print method of `summary.book` is too. The script asks the loaded namespace what it exposes.

[source,r]
----

length(exports)
#> [1] 10
"squish" %in% exports
#> [1] FALSE
"squish" %in% ls(ns)
#> [1] TRUE

# An internal function is not reachable from outside by name ...
exists("squish")
#> [1] FALSE
tryCatch(shelf::squish("x"), error = \(e) conditionMessage(e))
#> [1] "'squish' is not an exported object from 'namespace:shelf'"
# ... but `:::` reaches it, which is fine in a test and wrong in other code.
shelf:::squish("  two   words  ")
#> [1] "two words"

# Inside the package, a name is looked up in the namespace, then in the
# imports, then in the base namespace, then on the search path.
environmentName(ns)
#> [1] "shelf"
environmentName(parent.env(ns))
#> [1] "imports:shelf"
environmentName(parent.env(parent.env(ns)))
#> [1] "base"
environmentName(parent.env(parent.env(parent.env(ns))))
#> [1] "R_GlobalEnv"
----

Source: https://search.r-project.org/R/refmans/base/html/ns-reflect.html[R documentation: getNamespace, getNamespaceExports and the other namespace reflection functions]

Ten functions are exported and everything else is private: `squish()`, `shelf_today()`, the two hooks, the S3 methods, and `isbn_weights`, which lives in `R/sysdata.rda`. The error message is the one a user sees when they try to call an internal function with `::`, and `:::` goes round the barrier. Using `:::` on another package's internals is "generally not recommended" in the words of the manual, because the author may rename or remove an unexported object in a routine release. The last four lines show the lookup chain that makes the namespace useful: the namespace `shelf`, its imports environment (here empty, because `shelf` imports nothing), the base namespace, and then the global environment, which is where the search path starts.

=== Importing from other packages

A package that uses functions of another package has three ways to say so, and they differ in what they cost. `importFrom(pkg, f)` in `NAMESPACE`, made by `@importFrom pkg f`, puts `f` in the imports environment, so the code calls `f()` plainly and the `NAMESPACE` records the dependency. `pkg::f()` in the code names the package at each call, loads but does not attach `pkg` when evaluated, and is slightly slower than a formal import; Writing R Extensions notes that it also loses the advantage of recording dependencies in `NAMESPACE`, but they still have to be recorded in `DESCRIPTION`. A fully qualified call is the only way to use two functions of the same name from different packages. The third, `import(pkg)`, takes everything and risks name clashes with the package's own functions, and the manual advises against it for large packages. Whichever way is used, the package must be listed in `Imports` (or `Suggests` for a conditional use), and `R CMD check` verifies it: the real warning for an undeclared `jsonlite::toJSON()` is in the section on check messages below.

The rule that has no exception is that package code does not call `library()` or `require()` to get at a function. Both attach a package, which changes the search path of the user's whole session as a side effect of calling your function, and both fail in an uncontrolled way when the package is missing (`library()` stops, `require()` returns `FALSE` with a warning, and code that ignores the result fails later). For a package listed in `Depends` the call is unnecessary because it is already attached; for a package in `Imports`, `::` or a formal import is the tool; and for a package in `Suggests`, `requireNamespace("pkg", quietly = TRUE)` followed by `pkg::fun()` tests for it without attaching anything. `R CMD check` reports a `library()` call in package code, as the real run below shows.

Source: https://roxygen2.r-lib.org/articles/namespace.html[roxygen2 package documentation: Managing imports and exports]

Hand-written `NAMESPACE` files are the way older tutorials work, and they were the only way until roxygen2 existed. They still work, and a package that already has one can keep it. What a new package gains from the generator is that the file can no longer disagree with the code: an exported function that is renamed has its `@export` tag in the same block, so the renaming is made once.

=== A package with no NAMESPACE file

Since R 2.14.0 every package has a namespace, and a package whose author wrote none gets one made for it. A copy of `shelf` with its `NAMESPACE` deleted shows the result: `R CMD build` says that it created a default file, the file is in the bundle, and the check then notices the consequence. The first command of the script removes the file, and `tar xzOf` prints the file from the tarball to the terminal.

The default file exports every object whose name does not start with a dot. == Load hooks, options and start-up messages

Four hooks let a package run code when its namespace is loaded, attached, detached and unloaded. They are ordinary functions with fixed names, defined in the package and not exported (except for one, below), and R calls them at the right moment. The package `shelf` has two, in the file `R/zzz.R`, whose name makes it sort last, a convention that keeps the hooks out of the way. Here is the file, a package source like the others.

[source,r]
----
.onLoad <- function(libname, pkgname) {
  op <- options()
  op_shelf <- list(shelf.loan_days = 21L)
  to_set <- !(names(op_shelf) %in% names(op))
  if (any(to_set)) {
    options(op_shelf[to_set])
  }
  invisible()
}

.onAttach <- function(libname, pkgname) {
  packageStartupMessage(
    "shelf ", utils::packageVersion("shelf"),
    ": loan period is ", getOption("shelf.loan_days"), " days"
  )
}
----

Source: https://search.r-project.org/R/refmans/base/html/ns-hooks.html[R documentation: .onLoad, .onAttach and the other hooks]

`.onLoad()` runs when the namespace is loaded, and it is where the package sets its options. The idiom here is the standard one: collect the package's options with their defaults in a list, find which of them the user has not already set, and set only those. A user who put `options(shelf.loan_days = 14L)` in their `.Rprofile` keeps 14, because the hook only fills in what is missing. `.onAttach()` runs when `library()` attaches the package, and it is where the start-up banner belongs. It uses `packageStartupMessage()`, which is a `message()` with a class that `suppressPackageStartupMessages()` recognises, so a script that does not want the banner can silence it without silencing real messages, and so can `R CMD check`: one of its steps is "checking whether startup messages can be suppressed". The script shows the whole story with the installed package: the namespace is loaded without a message, the banner appears only on `library()`, it can be silenced, and a user's own setting wins.

[source,r]
----

#> [1] FALSE

#> [1] TRUE

#> [1] FALSE
shelf::normalise_isbn("978-0-00-100010-0")
#> [1] "9780001000100"

library(shelf)

"package:shelf" %in% search()
#> [1] TRUE

# A user's own setting wins: .onLoad() only fills in what is unset.
detach("package:shelf", unload = TRUE)

#> [1] 14
----

Source: https://search.r-project.org/R/refmans/base/html/message.html[R documentation: message, packageStartupMessage and suppressPackageStartupMessages]

Four lessons are packed in that output. Loading a namespace (here with `requireNamespace()`, and the same would hold for `shelf::normalise_isbn()`) runs `.onLoad()` and not `.onAttach()`: the option was set to 21 and `package:shelf` is not on the search path. `library()` runs `.onAttach()`, which printed the version and the loan period. A message created by `packageStartupMessage()` disappears under `suppressPackageStartupMessages()`. And the option of the user, set before `library()`, survived: `.onLoad()` saw `shelf.loan_days` already in `options()` and left it.

The four hooks in full, with the times at which R calls them and what each should be used for, are in the table.

[cols="2,3,5",options="header"]
|===
|Hook |Called |Use it for
|`.onLoad(libname, pkgname)` |After the code is loaded, before the namespace is sealed and its exports processed. Runs for `library()`, `loadNamespace()` and `::`. |Setting options, initialising state of the namespace, loading compiled code if there is no `useDynLib` directive. It must not assume that any package but base is attached, and must not attach one.
|`.onAttach(libname, pkgname)` |When `library()` or `attachNamespace()` attaches the package, before the package environment is sealed. |A start-up banner (through `packageStartupMessage()`), and nothing else: most packages do not need it.
|`.onDetach(libpath)` or an exported `.Last.lib(libpath)` |When the package is detached. Only one runs: `.onDetach` if the namespace has it, otherwise the exported `.Last.lib`. |Undoing what `.onAttach()` did. Should be written defensively, because it may be called even if `.onAttach()` failed.
|`.onUnload(libpath)` |Before the namespace is unloaded by `unloadNamespace()` (and so by `detach(unload = TRUE)`). |Unloading compiled code with `library.dynam.unload()`. Not in `.Last.lib` or `.onDetach`.
|===

Source: https://cran.r-project.org/doc/manuals/r-release/R-exts.html#Load-hooks[Writing R Extensions: Load hooks]

What the output shows is easy to get wrong in a package, and Writing R Extensions lists the usual mistakes. A namespace can be loaded without being attached (`loadNamespace()` ran `.onLoad` only). A package can be detached and attached again while its namespace stays loaded, so `.onAttach` ran twice and `.onLoad` once. `detach(unload = TRUE)` ran `.onDetach` first and then `.onUnload`, and the unloaded namespace was loaded again, with `.onLoad`, by the next `hooky::hello()`. Last, the two ways of writing a detach hook: `.onDetach` is in the namespace and is not exported, and the older `.Last.lib` has to be exported, and a package that defines both, like `both`, got only `.onDetach` in R 4.6.1: the help page says that the hook is called if `.onDetach` is in the namespace or `.Last.lib` is exported, and the output shows which of the two wins. People forget to export `.Last.lib`, which is why `lasty` has `export(.Last.lib)` in its `NAMESPACE`.

The rules of good practice in the help page are worth knowing by heart. A package should load silently. Any message that must be shown belongs in `.onAttach()` and goes through `packageStartupMessage()`. Hooks must not call `library()` or `require()`: a dependency is declared in `Depends`, or imported, and the namespace must not change the search path. They must not call `installed.packages()`, which is slow and can fail while another installation is running. Compiled code is loaded in `.onLoad()` (or by `useDynLib`) and unloaded in `.onUnload()` and nowhere else. And Writing R Extensions adds a warning about anything that depends on whether a suggested package is available: top-level code, `.onLoad()` functions and S4 class definitions run at installation time, and a reference to the namespace of a suggested package can be captured in the installed package, where it may be missing later.

== Data in packages

A package can carry data in three places, and they have three different purposes. Which one to use is the first decision, and the table makes it.

[cols="2,3,4",options="header"]
|===
|Where |What it is |How users and code reach it
|`data/*.rda` |Datasets for the user: `books` and `loans`. Written by `usethis::use_data()`. Documented in `R/data.R`. |`data("books", package = "shelf")`, or, because `LazyData: true`, plain `books` once the package is attached, and `shelf::books` without attaching.

=== The data directory

The `data/` directory is for data files that are to be available through `data()` or, if the `LazyData` field is true, as lazy-loaded objects that exist as soon as the package is attached. A data file is one of three kinds, recognised by its extension: R code (`.R`), a table (`.tab`, `.txt` or `.csv`, read in the formats that `?data` describes, noting that `.csv` here is not the standard CSV), or an image written by `save()` (`.rda` or `.RData`). Writing R Extensions says that `data/` should not be used for other data files that the package needs, for which the convention is `inst/extdata`, and that an R file there should be self-sufficient and silent, not attaching packages. An `.rda` file is the usual choice: it keeps the classes, attributes and `Date` columns exactly (`loans$loan_date` is a `Date`, which a CSV could not guarantee), and it is compact.

The tool that writes the files is `usethis::use_data()`, one object per file, with `compress = "bzip2"` and `version = 3` as the defaults (the serialization version that only R 3.5.0 and later can read, which is why the build added a dependency on R in the real run earlier). The tool that records how the data were made is the `data-raw/` directory, which usethis creates with `use_data_raw()`: the script in it is the recipe, the CSV files next to it are the raw material, and `.Rbuildignore` keeps them out of the bundle. The step-by-step section shows the `shelf` script and what it printed. For the installed package the `data/` directory holds a lazy-load database, which is the reason `books` costs nothing until it is used.

How the files were saved can be checked with `tools::checkRdaFiles()`, which reports the size, whether it is ASCII, the compression and the serialization version, and `tools::resaveRdaFiles()` re-saves a file with a better compression. `R CMD check` also inspects data files: the steps "checking contents of ‘data’ directory", "checking data for non-ASCII characters", "checking LazyData" and "checking data for ASCII and uncompressed saves" appear in the log. The same script loads the files into scratch environments and shows what each holds: `data/` has the two datasets and `R/sysdata.rda` the one internal object.

CRAN has a size rule that matters to anyone with a large dataset. The policy says that, as a general rule, neither data nor documentation should exceed 5MB (xref:programming-languages/r/publishing-to-cran.adoc[Publishing to CRAN] has the details), that reasonable compression should be used, and that a large amount of data is better placed in a separate data-only package. Writing R Extensions adds that `LazyDataCompression` and the `--data-compress` option of `R CMD INSTALL` choose the compression of the installed lazy-load database, and that the only way to know which is best is to try them. `R CMD build` also has `--resave-data`, with `no`, `gzip` (the default) and `best`.

A dataset needs documentation as much as a function does, and an undocumented one is reported by `R CMD check`. === R/sysdata.rda

Some data are for the package and not for the user: a table of constants, a trained model, a lookup. `shelf` has one, the check-digit weights of an ISBN-13, which are 1 and 3 alternating. The weights could be a vector in a file of `R/`, and they are computed in `data-raw/books.R` so that the data-making is in one place. The file `R/sysdata.rda` is lazy-loaded into the namespace, so `isbn_weights` is visible to every function of the package and to nobody else (`shelf:::isbn_weights` reaches it, as the output in the previous section showed). usethis writes it with `use_data(isbn_weights, internal = TRUE)`; note that this form saves every internal object into the one file, so all internal objects must be passed together, and that, unlike the files in `data/`, the objects of `sysdata.rda` follow the usual export rules, so a broad `exportPattern()` would export them. Writing R Extensions lists the file as one of two exceptions to the rule that `R/` should contain code only; the other is files ending in `.in`, generated by a `configure` script. The `R CMD check` step "checking R/sysdata.rda" is the one that looks at it, and the installed package has `sysdata.rdb` and `sysdata.rdx` in `R/`, the lazy-load database.

== inst/, system.file() and other installed files

Everything under `inst/` is copied, unchanged, to the top level of the installed package. That makes `inst/` the place for all files that are not R code, help or data in the R sense and still have to be present at run time, and it makes the names that R uses itself reserved: `R`, `data`, `demo`, `exec`, `libs`, `man`, `help`, `html` and `Meta`. The installed `shelf` shows the effect: `inst/CITATION` became `CITATION`, and the vignette that the build put in `inst/doc` is the `doc` directory.

Three things go in `inst/` in nearly every package. `inst/CITATION` is the file that `citation()` reads, `inst/extdata/` holds raw data files, and `inst/doc/` is where the built vignettes go (you do not write it yourself: `R CMD build` does). Package-level information files such as `AUTHORS` or `COPYRIGHTS` and a `NEWS.Rd` for the `news()` function also go there. Files like `README` and `ChangeLog` at the top level of the source are ignored by R and are not installed, except for `INDEX`, `LICENSE` and `NEWS` (and, from R 4.6.0 on, `README.md`, which the NEWS says is now installed and shown in the HTML help), so a file that the user should see must be put in `inst/`.

=== Finding installed files with system.file()

A file in `inst/extdata` is not at a fixed path once the package is installed: the library can be anywhere. `system.file()` finds it, given the path inside the package and the package name, and returns the empty string when the file does not exist. That returns a different path in two of the five states of a package, and pkgload (the package behind `devtools::load_all()`) makes it work in both by replacing `system.file()` with a version that looks in `inst/` of the source tree. The script shows both, on a copy of the package where `data-raw/books.csv` was copied to `inst/extdata/books.csv`: the package is first installed into a temporary library, and `system.file()` gives the path inside it, `extdata/books.csv`; then `load_all()` makes the same call return `inst/extdata/books.csv`.

[source,r]
----
# Raw files that the package needs at run time go under inst/. By
# convention inst/extdata holds data files; everything in inst/ lands in
# the top level of the installed package.
dir.create("inst/extdata", recursive = TRUE)
file.copy("data-raw/books.csv", "inst/extdata/books.csv")
#> [1] TRUE

# Installed: the file is at <package>/extdata/books.csv.
lib <- tempfile("lib")
dir.create(lib)
install.packages(".", repos = NULL, type = "source", lib = lib, quiet = TRUE)
installed <- system.file("extdata", "books.csv", package = "shelf",
                         lib.loc = lib)
sub(".*/shelf/", "", installed)
#> [1] "extdata/books.csv"
nrow(read.csv(installed))
#> [1] 16

# Under load_all() the same call is answered from the source tree, where
# the file is at inst/extdata/books.csv.
devtools::load_all(quiet = TRUE)
#> shelf 0.1.0: loan period is 21 days
dev <- system.file("extdata", "books.csv", package = "shelf")
sub(".*/shelf/", "", dev)
#> [1] "inst/extdata/books.csv"
identical(read.csv(dev), read.csv(installed))
#> [1] TRUE

# A path that does not exist gives the empty string, not an error.
system.file("extdata", "missing.csv", package = "shelf")
#> [1] ""
unlink(lib, recursive = TRUE)
----

Source: https://search.r-project.org/R/refmans/base/html/system.file.html[R documentation: system.file]

The lesson is in the paths. Code that reads `file.path("inst", "extdata", "books.csv")` would work in the source tree and fail when installed; code that uses `system.file("extdata", "books.csv", package = "shelf")` works in both states, and returns `""` (so the next `read.csv()` fails with a clear error) when the file is missing, which is also a reason to test the result with `nzchar()`. The same idea explains why paths in vignettes and examples are relative to the installed package and why tests use `testthat::test_path()` for fixtures, covered in xref:programming-languages/r/testing-with-testthat.adoc[Testing with testthat].

=== inst/CITATION

The `CITATION` file is parsed as R code and must contain calls to `bibentry()`; `citation("shelf")` prints it. If a package has no `CITATION`, R generates a citation from the `DESCRIPTION`, which is usually what you want, and Writing R Extensions recommends that a custom file start with `citation(auto = meta)` so that the entry for the package itself stays in step with the metadata, and then adds other works, such as a paper or a book. The file of `shelf` writes one entry by hand, which is simple and goes stale if the version changes.

[source,r]
----
bibentry(
  bibtype = "Manual",
  title = "shelf: Tools for a Small Library Catalogue",
  author = person("Shelf", "Maintainers"),
  year = "2026",
  note = "R package version 0.1.0"
)
----

Source: https://search.r-project.org/R/refmans/utils/html/citation.html[R documentation: citation and readCitationFile]

The output of `citation("shelf")` in the previous section is this entry formatted twice, as text and as a BibTeX entry. The requirements are that the file produces no output when it is sourced and that it does not call functions that assume the package is installed, such as `packageDescription()`, because the file must work where the package is not installed in a library on the search path (the manual calls that essential for CRAN). An early draft of this file had a `url` field with a placeholder address, and `R CMD check --as-cran` reported it as not found, which is why it has none: the check looks up the URLs it finds in a package, so any link that goes into a package must exist.

== The workflow with usethis and devtools

Making a package by hand means creating dozens of small files with the right names and the right contents, and then running a handful of `R CMD` commands in the right order. Two community packages automate it, and between them they have become the usual way to write a package. usethis (the `use_*` functions) creates and edits the files of a package and a project: it writes `DESCRIPTION`, adds a licence, a test directory, a vignette, a dependency. devtools (and the packages behind it: pkgload, pkgbuild, rcmdcheck, roxygen2 and testthat) runs the development loop: load the code, document it, test it, check it, install it. They are not part of R, and everything they do can be done with `R CMD` and an editor, as the next section shows; what they save is time and typing mistakes.

[cols="3,3,4",options="header"]
|===
|Task |With usethis and devtools |Without them
|Create the package |`usethis::create_package("~/shelf")` |Create the directory and write `DESCRIPTION` and `NAMESPACE` by hand, or `package.skeleton()`.
|Add a source file |`usethis::use_r("isbn")` |Create `R/isbn.R` in an editor.
|Declare a dependency |`usethis::use_package("withr", "Suggests")` |Edit the field of `DESCRIPTION`.
|Add a licence |`usethis::use_mit_license()` |Write the `License` field and the `LICENSE` file.
|Try the code |`devtools::load_all()` |`R CMD INSTALL shelf` then `library(shelf)` in a new session.

|Run the tests |`devtools::test()` |The tests run inside `R CMD check`; or `Rscript tests/testthat.R` against an installed package.

Source: https://usethis.r-lib.org/reference/index.html[usethis package documentation: Reference]

The loop that a package author runs many times a day is shorter than the table suggests. Edit a file in `R/`; press the shortcut for `load_all()`, which loads the package from its source in a second and attaches it as if it were installed; try the function in the console, or run the tests with `devtools::test()`; add or change a roxygen block, and run `document()`; and now and then run `check()`. Only the last of those is slow, and the other four are what makes writing a package pleasant. `load_all()` does not run `R CMD INSTALL`: it reads the files of `R/`, evaluates them into a namespace, loads the data, runs the load hooks and attaches the package, but it does not lazy-load or byte-compile anything, and it replaces `system.file()` (as shown earlier) so that files of `inst/` are found. The differences are what the other states of the package are for, and `check()` is how they are tested.

A few more of the `use_*` functions belong to the life of a package and are only named here, because they change a Git repository or talk to GitHub and are not run on this page. They are fragments, shown so that their names are known.

[source,r]
----
# Fragment, not run: they create a Git repository and talk to GitHub.
usethis::use_git()
usethis::use_github()
usethis::use_readme_rmd()
usethis::use_github_action("check-standard")
----

Source: https://usethis.r-lib.org/reference/use_git.html[usethis package documentation: use_git]

`use_git()` initialises a repository and offers a first commit, `use_github()` creates the repository on GitHub and pushes, `use_readme_rmd()` writes a `README.Rmd` (and a git hook that keeps it in step with the `README.md`), and `use_github_action()` adds a workflow that runs `R CMD check` on every push. The releases are a chain of `use_news_md()`, `use_cran_comments()`, `use_version()` and `devtools::release()`, and they belong to xref:programming-languages/r/publishing-to-cran.adoc[Publishing to CRAN].

=== What devtools::check() adds to R CMD check

`devtools::check()` is `R CMD build` followed by `R CMD check`, but with a set of choices made for you. It documents the package first, if the installed roxygen2 matches the version recorded in `DESCRIPTION`; it builds the bundle in a temporary directory and checks that; it sets the compiler flags `-Wall -pedantic`; it runs the check with `--as-cran` (its `cran = TRUE` default, which the documentation says is a best-effort copy of what CRAN does and more than the flag alone); it sets `NOT_CRAN=true`, which testthat reads to decide whether to run tests marked `skip_on_cran()`; and it switches off the checks that need the network or a complete set of suggested packages: the remote part of the CRAN incoming check and the incoming check itself, the requirement that all suggested packages be installed (`+_R_CHECK_FORCE_SUGGESTS_+`) and the report of unused imports (`+_R_CHECK_PACKAGES_USED_IGNORE_UNUSED_IMPORTS_+`). The log of the real run on `shelf` prints exactly these settings, and the report at the end is formatted by rcmdcheck: errors, warnings and notes counted, and each one explained. Its output is shown in full in the step-by-step section below.

=== build(), install() and what devtools offers now

== The shelf package, step by step

This section builds `shelf` the way a person would, one step at a time. The output of each step is the real output of the call as the tools printed it, taken from the recorded session in which the package was made, with `+~/shelf+` for the package directory. The calls are fragments of that session, in the order in which they were made, and each assumes the effect of the earlier ones (the active project, the working directory). The calls say `usethis::` in front of every function, which is how they were recorded; in an interactive session one would run `library(usethis)` or `library(devtools)` once and drop the prefixes.

=== Step 1: create the package

`create_package()` creates the directory, the `R/` subdirectory, `DESCRIPTION` and `NAMESPACE`. The call gives the title, version, description and authors, so that the file is right at once; in an interactive session `create_package("~/shelf")` alone is enough and the fields are edited in `DESCRIPTION` afterwards. `rstudio = FALSE` skips the RStudio project file and `open = FALSE` keeps the session where it is. `proj_set()` tells usethis which project the next calls apply to, because `create_package()` did not switch the session to the new project. The `DESCRIPTION` that usethis prints is the file it just wrote, with `Authors@R` shown parsed; `License` is still a hint, and `Config/roxygen2/version` and `Roxygen` were added by usethis because roxygen2 is the default way to document.

=== Step 7: the R code

The code of `shelf` is five files and the hooks. The excerpts below show what is specific to a package; each file of the finished tree continues in the same style. `R/isbn.R` holds ISBN handling: `normalise_isbn()` drops everything except digits and `X`, `is_valid_isbn13()` checks the length and the check digit, and `squish()` is a private helper. Two details of it are about packages. The function uses the `pass:c[\(i)]` shorthand for the anonymous function passed to `vapply()`, which is why the package declares R 4.1.0. And it uses `isbn_weights`, the object from `R/sysdata.rda`, which does not exist in any file of `R/` and is created in step 8. The documentation comments above the functions are roxygen2: `@export` tags make the `NAMESPACE`, `@param` and `@returns` the help page, and `@examples` the examples that `R CMD check` runs.

[source,r]
----
#' Normalise and validate ISBN-13 strings
#'
#' `normalise_isbn()` drops everything except digits and `X` and upper-cases
#' the result, so `"978-0-00-100010-0"` and `"9780001000100"` compare equal.
#' `is_valid_isbn13()` checks that a (normalised) string has 13 digits and a
#' correct check digit: the digits are multiplied alternately by 1 and 3 and
#' the sum must be divisible by 10.
#'
#' @param x A character vector of ISBNs; `NA` and empty strings are allowed.
#' @returns `normalise_isbn()` returns a character vector of the same length;
#'   `is_valid_isbn13()` a logical vector of the same length, `FALSE` for
#'   `NA` and for the empty string.
#' @examples
#' normalise_isbn("978-0-00-100010-0")
#' is_valid_isbn13(c("978-0-00-100010-0", "9780001000101", "", NA))
#' @export
normalise_isbn <- function(x) {
  gsub("[^0-9X]", "", toupper(x))
}

#' @rdname normalise_isbn
#' @export
is_valid_isbn13 <- function(x) {
  digits <- normalise_isbn(x)
  ok <- !is.na(digits) & nchar(digits) == 13L &
    !grepl("X", digits, fixed = TRUE)
  vapply(seq_along(digits), \(i) {
    if (!ok[[i]]) {
      return(FALSE)
    }
    d <- as.integer(strsplit(digits[[i]], "")[[1L]])
    sum(d * isbn_weights) %% 10L == 0L
  }, logical(1L))
}

# Collapse runs of blanks and trim the ends; NA stays NA.
squish <- function(x) {
  gsub(" +", " ", trimws(x))
}

#' trims `genre`, and replaces `isbn` by its normalised form, with `NA` where
#' the ISBN is empty or fails the check digit. `clean_loans()` parses the two

#' `NA`, because such a return cannot have happened.

#' @param books A data frame with the columns of [books].

clean_books <- function(books) {

#' Overdue loans
#'
#' A loan is overdue when it was returned more than `loan_days` days after it
#' was taken out, or when it has not been returned and `today` is more than
#' `loan_days` days after the loan date. Loans whose `loan_date` is `NA` are
#' never reported.
#'
#' @param loans A data frame with the columns of [loans], with `loan_date`
#'   and `return_date` as `Date` (see [clean_loans()]).
#' @param today The reference date for loans that are still out. Defaults to
#'   the current date.
#' @param loan_days Length of the loan period in days. Defaults to the
#'   `shelf.loan_days` option, which the package sets to 21 when it is loaded.
#' @returns The overdue rows of `loans` with an extra integer column
#'   `days_out`: the days from the loan date to the return date, or to
#'   `today` for a loan that is still out.
#' @examples
#' out <- overdue_loans(loans, today = as.Date("2026-06-30"))
#' nrow(out)
#' head(out[order(-out$days_out), ], 3)
#' @family loan analyses
#' @export
overdue_loans <- function(loans, today = shelf_today(),
                          loan_days = getOption("shelf.loan_days", 21L)) {
  end <- loans$return_date
  end[is.na(end)] <- today
  days_out <- as.integer(end - loans$loan_date)
  keep <- !is.na(days_out) & days_out > loan_days
  loans <- loans[keep, , drop = FALSE]
  loans$days_out <- days_out[keep]
  rownames(loans) <- NULL
  loans
}

# The reference date; kept as a function so that tests can replace it.
shelf_today <- function() {
  Sys.Date()
}

== R CMD build, INSTALL and check without devtools

Everything the devtools functions do for the last three steps is done by three commands that ship with R and run in a shell, not in an R session: `R CMD build`, `R CMD check` and `R CMD INSTALL`. They are the commands that CRAN and every continuous-integration service run, their messages are the ones that the earlier sections quoted, and a person who has met them once can read any build or check log. The commands below were run from the directory that contains the package directory `shelf`, because that is where `R CMD build shelf` leaves its tarball and where `R CMD check` leaves the `shelf.Rcheck` directory; the commands are shown as they were typed, and the paths in the output were shortened.

The three commands take a package from one state to the next. `R CMD build` turns the source directory (state 1) into the tarball (state 2). `R CMD check` takes the tarball, installs it into a scratch library, and runs every kind of test on the result. `R CMD INSTALL` turns the directory or the tarball into an installed package (state 4), and with `--build` it also leaves a binary package (state 3). The sections follow that order.

=== R CMD check

==== Options and environment variables

`R CMD check --help` lists the options that make a check shorter or longer (and says what each does). The ones used on this page are `--no-manual`, `--as-cran`, `--no-tests`, `--no-examples` and `--no-vignettes`. The others change what is checked: `--run-donttest` and `--run-dontrun` run example code that the author excluded, `--run-demo` (R 4.5.0) runs the scripts of `demo/`, `--no-codoc` skips the comparison of code and documentation, `--library` and `--install-args` control the test installation, `--timings` records how long each example takes, and `--use-valgrind` and `--use-gct` are for compiled code.

R Internals documents a long list of environment variables whose names start with `+_R_CHECK_+`, each of which switches an individual check on or off. Four matter to a package author. `+_R_CHECK_FORCE_SUGGESTS_+` makes a missing suggested package an error (true by default, false for CRAN submission checks, and set to false by devtools). `+_R_CHECK_CRAN_INCOMING_+` and `+_R_CHECK_CRAN_INCOMING_REMOTE_+` select the incoming checks and the part of them that needs the network, and the second defaults to the value of the first. `+_R_CHECK_SUGGESTS_ONLY_+` and `+_R_CHECK_DEPENDS_ONLY_+` run the examples, tests and vignettes in a library that holds only the declared packages, which is the check that finds a package that was used and not declared. A fifth, `NOT_CRAN`, is not R's: testthat's `skip_on_cran()` reads it, and the next section shows its effect.

=== Running the tests without devtools

The tests of a package are run by `R CMD check`, as the `checking tests` line showed, and they can also be run alone against an installed package. `tests/testthat.R` is an ordinary script: it attaches testthat and the package and calls `test_check("shelf")`, which finds the `testthat/` directory next to it. Running it from the `tests` directory with the installed package on the library path is what `R CMD check` does in its own directory. The first run is the one that a check makes: the variable `NOT_CRAN` is not set, so the two tests that call `skip_on_cran()` are skipped. The second sets it, and nothing is skipped.

cd shelf/tests
R_LIBS=../../lib Rscript testthat.R
R_LIBS=../../lib NOT_CRAN=true Rscript testthat.R
----

== Reading the output of R CMD check

A passing check is one line, and a failing one is a short list, so the skill to learn is reading the list. Every finding has a level. An ERROR means that a check failed or crashed, and the package is broken in a way that must be fixed. A WARNING is a problem that is very likely to matter, and in principle CRAN admits a package only without warnings (CRAN Repository Policy). A NOTE is something that may be fine and that a submission has to explain in `cran-comments.md`. The last line of the log, `Status:`, counts them, and `Status: OK` means that there is none. The level matters for the exit status of the command, too: in the runs on this page a check with warnings and notes exited with 0, and a check with an ERROR exited with 1.

The real findings below come from deliberately damaged copies of `shelf`. Each copy was made by copying the finished package, adding the files named in the text, and running the same commands as before. The files that are added are package sources, written to show one mistake each. They sit in a directory of unlinted contrast files, because their purpose is to be wrong: one calls `library()` inside a function, and one uses a name that is only defined by the package's data.

=== The note that appears alone: a variable that is not there

The most common single NOTE in a package that has data is the one for a dataset used by its bare name. It is also the one that deserves the most thought, because the static check cannot know that the object exists when the package is attached. The script below puts `titles.R` of the damaged copy alone into a copy of `shelf`, documents it and checks it, with the check's output limited to the summary (`quiet = TRUE`).

[source,r]
----
# Run the checks quietly: only the summary is printed at the end.
devtools::document()
#> ℹ Updating shelf documentation
#> ℹ Loading shelf
#> shelf 0.1.0: loan period is 21 days
#> Writing 'NAMESPACE'
#> Writing 'catalogue_titles.Rd'
devtools::check(manual = FALSE, quiet = TRUE)
#> ── R CMD check results ──────────────────────────────────────── shelf 0.1.0 ────
#> ❯ checking R code for possible problems ... NOTE
#>   catalogue_titles: no visible binding for global variable ‘books’
#>   Undefined global functions or variables:
#>     books
#> 0 errors ✔ | 0 warnings ✔ | 1 note ✖
----

Source: https://devtools.r-lib.org/reference/check.html[devtools package documentation: check]

The note names the function and the variable: `books` is not visible to the package code. It would be found at run time if the package was attached, and not if it was only loaded, so the function would work in the author's session and fail in a script that called `shelf::catalogue_titles()` without attaching. The robust form is the one of the fixed copy: name the package, `shelf::books`, which loads the namespace and reads the lazy-loaded dataset from it. When a name is really a column that a non-standard-evaluation function creates, the other remedy is `utils::globalVariables("name")`, once, in a file of `R/`: it tells the check that the name is not an error (R documentation: globalVariables), and it should be reserved for the names that are not objects at all.

=== Four more mistakes, and the checks that catch them

The second damaged copy shows findings that the first did not. It has a new function, `greet()`, that is exported with its documentation and whose body calls a helper that was never written; the example in the roxygen block calls it. A second edit then adds an argument to the function and does not run `document()`, and a third declares stringr in `Imports` without using it. The string in the function holds a non-ASCII character, written as an escape in the script and saved as UTF-8 in the file. The script is the one that was run in the copy.

[source,r]

== package.skeleton(): the older form

Before usethis there was `package.skeleton()`, a function of the `utils` package that turns the objects of a workspace into a package directory. The R FAQ dates it to R 1.3.0 and still describes it as the way to set up directories, save data and code and create skeleton help files for a set of functions and datasets. It starts from objects that already exist, which is its good and its bad side: a person who has been working in a session with half a dozen functions gets a package out of them in one call, and a person who starts a package from nothing gets nothing useful from it. The script defines two small functions of the running scenario and makes a package called `tinyshelf` in the working directory (`path = "."`), looks at what was created, and removes it.

Reading the output is a short course in what a source package contains. The directory has a `DESCRIPTION`, a `NAMESPACE`, one R file for each function (`R/squish.R`, `R/is_blank.R`), one Rd file for each function and one more for the package (`man/tinyshelf-package.Rd`), and a file called `Read-and-delete-me` that lists the next steps. The `DESCRIPTION` is a set of placeholders that have to be edited (a title, a version of 1.0, two made-up authors and a licence field that asks "What license is it under?"). The `NAMESPACE` lists every function in one `export()` line, since R 4.0.0 (R NEWS: Changes in R 4.0.0: `package.skeleton()` now explicitly lists all exports in the `NAMESPACE` file), and the instruction file that the function leaves behind says to edit the exports and to add the necessary imports. The Rd files are templates full of `~~` notes that tell the author what to write. The function returns the path of the new directory invisibly since R 4.6.0 (R NEWS: Changes in R 4.6.0), which is why the script prints `path` explicitly, and the same release lets it create a blank skeleton without any objects.

The skeleton is not a package that passes a check, and the real log shows how far it is from one. The commands below build it and check it without any edit.

Three things stand out. The licence field is not a standard specification, and that is a WARNING. The Rd files have empty sections that the check drops (the `prepare_Rd` lines name each of them, and only the first and the last are shown), and the `Rd contents` check recognises the template: an argument item with no description, and an auto-generated title that still says "A Capitalized Title". NOTEs and WARNINGs are what a person has to remove before the package is real, and the 1.0 version, the made-up authors and the missing tests are what the check does not know about. The longer way round with usethis and roxygen2 gets the same files with less to delete, which is why it replaced the skeleton, and the table of the workflow section shows the one-to-one mapping.

The functions that `package.skeleton()` calls are available separately for a single object: `prompt()` writes a skeleton Rd file for a function, `promptData()` for a data frame and `promptPackage()` for the package overview. The Rd files that they write are the ones that roxygen2 now generates from comments (R documentation: prompt, promptData, promptPackage), and a package that is maintained with roxygen2 should not also keep hand-edited copies: the generated file starts with a line that says not to edit it by hand, and `devtools::document()` rewrites it.


== Pitfalls

* **Editing a generated file.** `NAMESPACE` and every file of `man/` start with "Generated by roxygen2: do not edit by hand", and the next `devtools::document()` overwrites them (or, for a `NAMESPACE` without that line, refuses to touch it and leaves a hand-written file that then disagrees with the code). Change the comment in `R/` instead, and commit the generated files, because CRAN needs them in the bundle.
* **Top-level code that runs once.** The files of `R/` are evaluated when the package is installed, so a value computed at the top level of a file, such as today's date, is the value of the day of the installation. Wrap such a value in a function (`shelf_today()` does), or compute it in `.onLoad()`, which runs at every load.
* **`library()` or `require()` inside package code.** Both attach a package as a side effect of calling your function. Declare the package in `Imports` and call it with `::`, or test for a suggested package with `requireNamespace("pkg", quietly = TRUE)`. The check reports the call.
* **Using `Depends` for convenience.** A package in `Depends` is attached for every user, so the user's search path changes and masking follows (see xref:programming-languages/r/packages-libraries-and-namespaces.adoc[Packages, Libraries and Namespaces]). The one entry that belongs there for most packages is `R (>= x.y.z)`.
* **Changing a signature and not running `document()`.** The usage line of the Rd file no longer matches the function, and the check warns about the mismatch (the real message is in the table of the check section).
* **Reading files by a path relative to the source tree.** `file.path("inst", "extdata", "books.csv")` works under `load_all()` and fails when the package is installed. Use `system.file("extdata", "books.csv", package = "shelf")` and test the result with `nzchar()`, because it returns `""` for a file that is not there.
* **Checking the directory and not the bundle.** `R CMD check shelf` works on the directory and does not run every check: the checks of the package subdirectories, for example, are on by default only for a tarball (`R CMD check --help`). The tarball is what CRAN and the users receive, so build first (`R CMD build`, or `devtools::check()`, which builds first).
* **Forgetting that tests are skipped on CRAN.** `R CMD check` leaves `NOT_CRAN` unset, so tests that call `skip_on_cran()` do not run, and the summary line says `SKIP 2`; `devtools::check()` sets `NOT_CRAN=true`, so they do run. A test that passes under one and fails under the other is a real finding, not a flake.
* **Unanchored `.Rbuildignore` patterns.** The lines are regular expressions matched anywhere in the path: `data-raw` also removes `R/data-raw-helpers.R`. Anchor with `^` and `$` and escape the dots, or let `usethis::use_build_ignore()` write the line.
* **Output at load time.** A package that prints with `cat()` or `print()` when it is loaded cannot be silenced. Use `packageStartupMessage()` in `.onAttach()`, and print nothing in `.onLoad()`.
* **A dataset that is not documented.** Every dataset of `data/` needs a help page (the roxygen block above a string with the name of the dataset), and the check reports the object that has none.
* **Choosing a name last.** A package name that exists on CRAN in any capitalisation cannot be submitted, as the real check of `shelf` showed. Look the name up before the package has a hundred commits (xref:programming-languages/r/publishing-to-cran.adoc[Publishing to CRAN] shows how).
* **Installing into the system library.** An installation by an administrator changes the packages of every user, and a later update of R can orphan them. Use a per-user or per-project library (`R_LIBS_USER`, `--library`, renv), which xref:programming-languages/r/reproducible-environments-with-renv.adoc[Reproducible Environments with renv] covers.
* **Installing a package and not finding it.** A package installed into a library that the session does not search is not found by `library()`. Check `.libPaths()` and the `--library` or `lib` argument that was used; R FAQ 7.30, "I installed a package but the functions are not there", is the entry for this case.
