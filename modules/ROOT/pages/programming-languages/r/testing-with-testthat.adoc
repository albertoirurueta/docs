Testing is the habit of writing down what a piece of code is supposed to do as code that checks it, so that the checking can be repeated after every change. R itself ships only the minimal machinery for this: the `tests` directory of a package, whose `.R` files `R CMD check` runs, with optional reference output next to them. Almost every package on CRAN goes through testthat instead, an add-on package that gives that directory a structure: a test is a named block, a test contains expectations, expectations say what the result must look like and produce readable failure reports, and a few special files hold shared helpers and fixtures. This page explains that structure with the tests of the `shelf` package, the tools that run and report them, the features around them (snapshots, mocking, skipping, fixtures, the third edition), and the base-R and tinytest alternatives. It ends with coverage measurement with covr and a CI fragment.

Every example is a script that was run with `Rscript` on R 4.6.1 with warnings printed as they happen (`options(warn = 1)`), and the lines that start with `+#>+` are what it printed. The scripts also pass the default `lintr` linters (whose line limit is 80 characters). The names `books`, `loans` and `shelf_today` and the `book()` constructor come from the running library-shelf scenario described on the xref:programming-languages/r/index.adoc#shelf-files[section index]: a script that needs them starts with `source("scenario.R")`, or calls `shelf::` functions when the built package is used. The `shelf` package shown here was created, documented, tested, built and checked for real with these tools; its files are shown as the tools wrote them. The experiments that change the package (a failing test file, a changed print method, a parallel setting) ran in a throwaway copy of the package directory and each one puts everything back; the transcripts show the package path as `+~/shelf+` (paths shortened). The default testthat reporters finish a passing run with a random emoji or a short word of praise, and print a spinner line that a terminal overwrites in place but that a captured log keeps as separate lines. The scripts therefore silence the praise where they can (`StopReporter$new(praise = FALSE)`), and the few transcripts that still contain a random line say which one was left out.

[[where-tests-live]]
== Where tests live and how testthat fits

A package keeps its tests in the `tests` directory, which Writing R Extensions describes as the place for package-specific test code: `.R` files whose results are written to a `.Rout` file, which `R CMD check` compares with a `.Rout.save` file when one exists. The directory is copied to the check area, the tests run with that copy as the working directory, in a vanilla R session without a random-number seed, with `R_LIBS` set so that `library(shelf)` finds the copy of the package installed for the check. R does not say how the tests should be written. testthat is a convention on top of that mechanism, and a package opts in with three things: `Suggests: testthat` in `DESCRIPTION` (a package used only to run tests is a suggestion, not an import), a one-line driver in `tests/testthat.R`, and the test files in `tests/testthat/`.

Source: https://cran.r-project.org/doc/manuals/r-release/R-exts.html#Package-subdirectories[Writing R Extensions: Package subdirectories]

The vocabulary has four levels, and the names matter because the failure reports and the reporters use them.

[cols="1,3,3",options="header"]
|===
|Level |What it is |Where it is written
|Expectation |One check of one result: `expect_equal(x, y)`. It succeeds, fails, or is skipped, and reports what it saw.|a call of an `+expect_*()+` function
|Test |A named group of expectations that share local objects and are reported together.|`+test_that("description", { ... })+` or `+it("description", { ... })+`
|File |The tests of one source file or one topic; the unit that snapshots, filters and the progress display work on.|`+tests/testthat/test-*.R+`
|Suite |Every file, plus the helper and setup files that prepare them.|`tests/testthat/`, run by `test_check()`, `devtools::test()` or `test_local()`
|===

Source: https://testthat.r-lib.org/reference/test_that.html[testthat package documentation: test_that]

Each test runs in a fresh environment whose parent is the package namespace when the tests belong to a package, so a test can call internal functions such as `shelf_today()` without `:::`. The expectations are ordinary functions that signal an expectation condition; the reporter listening for those conditions counts them and prints the failures. Because a test is just code that runs in a controlled environment, everything the other pages teach about functions, scoping and conditions applies inside it.

=== tests/testthat/

The files in `tests/testthat/` have different jobs, decided by their names. Only names matter, not contents:

[cols="2,5",options="header"]
|===
|File or directory |Role
|`+test-*.R+` (or `+test_*.R+`, extension `.R` or `.r`) |Test files. Run in alphabetical order; each should pass when run alone or in any order. The convention is one test file for each file in `R/`: `R/loans.R` has `tests/testthat/test-loans.R`, and `usethis::use_test()` and `devtools::test_active_file()` rely on that correspondence.
|`+helper-*.R+` |Helper code: functions and constants shared by the tests, custom expectations, skip helpers. Sourced by `devtools::load_all()` and by `test_check()` and its relatives, so the helpers exist however the tests are run.
|`+setup-*.R+` (by convention `setup.R`) |Global preparation for a run, such as turning off interactive behaviour. Sourced by `test_check()` and friends but not by `load_all()`. Cleanup belongs next to the setup with `+withr::defer(..., teardown_env())+`.
|`+teardown-*.R+` |The legacy place for cleanup, no longer recommended. Run after the tests.
|`fixtures/` (any name) |Data files for the tests. Files that testthat does not know are ignored by it, which makes the directory a safe place for persistent test data; reach it with `test_path()`.
|`+_snaps/+` |Snapshot files written and read by `expect_snapshot()` and friends, named after the test file; never edited by hand, always committed.
|`+_problems/+` |Written in a check directory when a test fails under `R CMD check` (testthat 3.3.0): one reprex file for each failing expectation.
|===

Source: https://testthat.r-lib.org/articles/special-files.html[testthat package documentation: Special files]

== The tests of the shelf package

The suite of `shelf` has three test files, one helper file and one fixture. They are package test files, run by `devtools::test()` or `test_check()`, not scripts to run with `Rscript`; the blocks below are the files exactly as they are in `+~/shelf/tests/testthat/+`, and each is explained in the sections that follow. They pass the default `lintr` linters with one finding, explained below. Together they hold 52 expectations: `devtools::test()` reports `[ FAIL 0 | WARN 0 | SKIP 0 | PASS 52 ]`.

=== helper-shelf.R

The helper is loaded before every test file. It defines the one fixed date that the tests share and a function that reads the small catalogue fixture through `test_path()`.

[source,r]
----
# Loaded before every test file: a fixed "today" and a helper that reads the
# small catalogue fixture.
shelf_fixed_today <- as.Date("2026-06-30")

read_fixture_books <- function() {
  read.csv(test_path("fixtures", "books-small.csv"))
}
----

Source: https://testthat.r-lib.org/reference/test_path.html[testthat package documentation: test_path]

Linting this file in a fresh session finds one thing, and the reason is a general property of lintr and not a problem of the helper. `object_usage_linter` asks the R session which functions exist, and a plain `+Rscript -e 'lintr::lint_package()'+` has not attached testthat, so `test_path()` is "not visible". The recorded build of the package linted it after `devtools::test()` had attached testthat and found nothing. The second call below attaches testthat first:

[source,r]
----
# A fresh session does not know test_path(): lintr cannot see where it is from.
lintr::lint_package()

# With testthat attached the same file is clean.
library(testthat)
lintr::lint_package()
----

Source: https://lintr.r-lib.org/reference/lint.html[lintr package documentation: lint_package]

The first call prints the lint (the file, line and column, the linter and its message, the line of code and a marker under the name); the second prints the message `No lints found.`:

[source,text]
----
tests/testthat/helper-shelf.R:6:12: warning: [object_usage_linter] no visible global function definition for 'test_path'
  read.csv(test_path("fixtures", "books-small.csv"))
           ^~~~~~~~~
ℹ No lints found.

Source: https://lintr.r-lib.org/reference/lint.html[lintr package documentation: lint_package]

=== test-book.R

The tests of the `book` class: normalising input, optional fields, the error messages of `validate_book()`, the type check of `new_book()`, two snapshot tests, and a `describe()` block for `is_valid_isbn13()`.

test_that("book() trims the text fields and normalises the ISBN", {
  b <- book("  the quiet streets ", "Mara  Quill", "978-0-00-100010-0",
            "2019", "Fiction ", 214)
  expect_s3_class(b, "book")
  expect_identical(b$title, "the quiet streets")

The fixture is a three-row catalogue with one row of every kind of mess that `clean_books()` repairs: a title with blanks and lower case, a hyphenated ISBN, an empty ISBN and a double space in an author. The expected values in the test are small enough to be written out, which is what makes the test a good specification. The third test builds its input in the test itself, as a three-row data frame, because the impossible date and the early return belong to the case being described and a reader should see them next to the expectation.

=== test-loans.R

The tests of the loan analyses use the shared fixed date, replace the package's clock in one test, change an option in another and skip one test on CRAN.

[source,r]
----
test_that("overdue_loans() counts late returns and loans still out", {
  out <- overdue_loans(loans, today = shelf_fixed_today)
  expect_true(all(out$days_out > 21L))
  expect_identical(sum(is.na(out$return_date)), 7L)
  expect_identical(nrow(out), 32L)

== A first test: test_that() and expectations

`test_that(desc, code)` takes a description and a block of code. The description should finish the sentence "test that ...": the failure report quotes it, and a suite of well-chosen descriptions reads as a specification. The block is evaluated in its own environment with the reporter listening: every `+expect_*()+` call inside it registers one result, a failed expectation does not stop the block (the later expectations still run and are reported), and an error that is not caught by an expectation ends the block and is reported as an error against the test. A block without any expectation is reported as skipped, with the reason `empty test`. `test_that()` also calls `local_test_context()`, which sets the environment variable `TESTTHAT` and, in the third edition, makes the output reproducible (see <<reproducible-output,Reproducible output>>); it does not need a `context()` call.

A test file can also be run as a script, which is the easiest way to see the mechanics. Outside a package there is no `DESCRIPTION` to say which edition applies, so the scripts select the third edition with the environment variable `TESTTHAT_EDITION` (the third-edition section explains why). In a script, `test_that()` uses the stop reporter: a passing test prints nothing here (with praise on, it prints `Test passed` and a random emoji), and a failing test prints its report and then stops the script with an error, so the script catches it to go on.

[source,r]
----
library(testthat)
source("scenario.R")
set_reporter(StopReporter$new(praise = FALSE))

# A test is a description plus a block of expectations.
test_that("addition works", {
  expect_equal(1 + 1, 2)
  expect_true(is.numeric(1L))
})

# A test with a failing expectation stops the script; catch it to continue.
result <- tryCatch(
  test_that("a failing expectation", {
    expect_equal(1 + 1, 3)
  }),
  error = \(e) conditionMessage(e)
)
#> ── Failure: a failing expectation ──────────────────────────────────────────────
#> Expected `1 + 1` to equal 3.
#> Differences:
#> 1/1 mismatches
#> [1] 2 - 3 == -1
result
#> [1] "Test failed with 1 failure and 0 successes."

# An error inside the block is also reported against the test.
tryCatch(
  test_that("an error inside a test", {
    books$title[[100L]]
  }),
  error = \(e) conditionMessage(e)
)
#> ── Error: an error inside a test ───────────────────────────────────────────────
#> <subscriptOutOfBoundsError/error/condition>
#> Error in `books$title[[100L]]`: subscript out of bounds
#> [1] "Test failed with 1 failure and 0 successes."

# A test without expectations is skipped as empty.
test_that("nothing is checked here", {
  x <- 1 + 1
})
#> ── Skip: nothing is checked here ───────────────────────────────────────────────
#> Reason: empty test
----

Source: https://testthat.r-lib.org/reference/test_that.html[testthat package documentation: test_that]

The report of the failure shows the three parts that every failure has: the location (here the test description; in a file, the file and line), the sentence that says what the expectation expected, and the differences. Since testthat 3.3.0 every expectation states what it expected and what it saw in the same shape, and returns the value of its first argument whether it succeeds or fails, so chains of expectations work, as the last line of the script in the section on types and classes shows.

The rest of this section goes through the families of expectations. Every example here is a script in which a failed expectation raises an error; the one-line helper `failure()` catches that error and prints its message, which is exactly the text that appears in a test report. An expectation that succeeds prints nothing.

=== Equality: expect_equal() and expect_identical()

`expect_identical(object, expected)` demands that the two objects are the same, the way `identical()` does for the base data types. `expect_equal(object, expected)` demands that they are the same up to numerical error: it differs from `expect_identical()` only in setting `tolerance = testthat_tolerance()`, so small floating-point differences are ignored, and as a consequence `1` and `1L` are equal. Both compare with `waldo::compare()` in the third edition; in the second edition `expect_identical()` used `identical()` and `expect_equal()` used `all.equal()`, whose tolerance rules are different for different code paths. The tolerance is the one of `all.equal()`: relative to the size of the numbers, absolute when the differences are very small. The rule for choosing is simple. Use `expect_identical()` for what is exact by construction (strings, integers, logicals, names, classes, `NA` values) and `expect_equal()` for results of floating-point arithmetic. For the arithmetic itself, see xref:programming-languages/r/numbers-and-arithmetic.adoc[Numbers and Arithmetic].

The waldo reports are the main reason to use the third edition. The report for `b1` and `b2` is `actual$year` against `expected$year`: it names the element that differs and shows both values. For a data frame with a row missing waldo prints a side-by-side table of the differing rows and then one comparison for each column that differs, which is more than the message `all.equal()` would give but still points at the first thing to look at. The extra arguments of `expect_equal()` go to `waldo::compare()`: `ignore_attr = TRUE` ignores attributes such as names (the old `expect_equivalent()`), and `ignore_function_env` and `ignore_formula_env` ignore the environments of functions and formulas, which differ between runs when tests compare fitted models.

=== Logical, type and class expectations

`expect_true(x)` and `expect_false(x)` require a single `TRUE` or `FALSE`, not something that merely behaves like one: `expect_true(1)` fails, because `1` is a double, and `expect_true(c(TRUE, FALSE))` fails because the length is two. `expect_null()` checks `NULL`. The type and class expectations check the object system explicitly, which is why the older `expect_is()` is deprecated in the third edition: `expect_type(x, "integer")` checks `typeof()`, `expect_s3_class(x, "book")` checks that an S3 object inherits from a class (`exact = TRUE` requires the class vector to be exactly that), `expect_s4_class()` an S4 class, and `expect_s7_class()` and `expect_r6_class()` the S7 and R6 equivalents. Passing `NA` as the class asserts that the object is not an S3 (or S4) object at all. Two newer helpers check the shape in one call: `expect_vector(x, ptype, size)` and `expect_shape(x, nrow, ncol, dim)`.

=== Length, names, sets, comparisons and text

These expectations exist because `expect_equal(length(x), 6L)` and `expect_true(all(a %in% b))` fail with messages that say nothing about the objects. The dedicated forms say what they saw:

* `expect_length(x, n)` and `expect_named(x, names, ignore.order, ignore.case)`;
* `expect_setequal(x, y)`: the same elements, in any order and with any duplication; `expect_mapequal(x, y)`: the same names and the same value for each name, in any order;
* `expect_contains(x, y)`: every element of `y` is in `x`, and `expect_in(x, y)`: every element of `x` is in `y` (the two directions of subset, added in testthat 3.1.9); `expect_disjoint()` the opposite;
* `expect_lt()`, `expect_lte()`, `expect_gt()` and `expect_gte()` compare numbers, dates and times, and show both values on failure;
* `expect_match(x, regexp)` and `expect_no_match()` match text against a regular expression (see xref:programming-languages/r/strings-and-regular-expressions.adoc[Strings and Regular Expressions]), and `expect_all_true()`, `expect_all_false()` and `expect_all_equal()` check every element at once (testthat 3.3.0) and say which elements differ, where `+expect_true(all(...))+` can only say `FALSE`.

The last two calls show why `expect_all_true()` exists: for the same vector it prints the two stretches of the vector (`actual[3:9]` and `actual[12:16]`) around the two `FALSE` elements, so the missing page counts can be found, and `+expect_true(all(...))+` can only say that `actual` is `FALSE`. A few of these are easy to mix up. `expect_setequal()` is about elements and ignores order; `expect_equal()` of two vectors does not. `expect_contains(genres, "poetry")` has the larger set first and `expect_in("poetry", genres)` the smaller, so the two read in opposite orders. For a named list, `expect_mapequal()` compares the content and not the order of the names.

=== Conditions: errors, warnings and messages

`expect_error()`, `expect_warning()`, `expect_message()` and the general `expect_condition()` check that the code signals the condition. The arguments are a regular expression for the message (`regexp`), a condition class (`class`), `fixed = TRUE` to match the text literally, and `inherit` to match across the parent errors of chained errors. They return the captured condition, so it can be examined, and they are the tools to test the paths that a function rejects (see xref:programming-languages/r/defensive-programming-and-input-validation.adoc[Defensive Programming and Input Validation] and xref:programming-languages/r/conditions-and-error-handling.adoc[Conditions and Error Handling]).

In the third edition each of them captures at most one condition, the first one that matches the `regexp` and `class`, and lets every other condition bubble up. A condition that does not match is therefore not reported as "the message differs" but as the raw error, warning or message that it is; in a test, an unmatched error becomes an error of the test. The message is a regular expression, which is the usual cause of surprises with parentheses and dots (`fixed = TRUE` turns that off), and matching a message makes a test as fragile as the message. Prefer `class =` where the condition has one. If what you want to check is that the message is readable, use `expect_snapshot()`, which shows it in full.

[source,r]
----
library(testthat)
Sys.setenv(TESTTHAT_EDITION = "3")
source("scenario.R")

failure <- \(code) tryCatch(code, error = \(e) cat(conditionMessage(e), "\n"))

# expect_error() takes a regular expression for the message...
expect_error(book(""), "a book needs a title")
# ...fixed = TRUE when the message holds regular-expression characters...
expect_error(
  new_book(title = 1), "is.character(title) is not TRUE", fixed = TRUE
)
# ...and a class, which is much less fragile than the text.
expect_error(stop("no such shelf"), class = "simpleError")

# A message that does not match.
failure(expect_error(book(""), "a book needs an author"))
#> a book needs a title

# Code that does not fail, or fails in a different way.
failure(expect_error(book("A title")))
#> Expected `book("A title")` to throw a error.
failure(expect_error(stop("something else"), "a book needs a title"))
#> something else

# Warnings and messages.
expect_warning(as.integer("x"), "NAs introduced by coercion")
expect_message(message("loading"), "loading")
failure(expect_warning(1 + 1))
#> Expected `1 + 1` to throw a warning.

# A custom condition class is matched by class =.
shelf_condition <- structure(
  class = c("shelf_overdue", "warning", "condition"),
  list(message = "3 loans are overdue", call = NULL)
)
expect_warning(warning(shelf_condition), class = "shelf_overdue")
expect_condition(warning(shelf_condition), "overdue")

# The expectation returns the condition, so you can inspect it.
cnd <- expect_error(book(""), "title")
class(cnd)
#> [1] "simpleError" "error"       "condition"
conditionMessage(cnd)
#> [1] "a book needs a title"

# No condition at all.
expect_no_error(book("A title"))
expect_no_warning(as.integer("1"))
expect_no_message(1 + 1)
failure(expect_no_error(book("")))
#> Expected `book("")` not to throw any errors.
#> Actually got a <simpleError> with message:
#>   a book needs a title
failure(expect_no_warning(as.integer("x")))
#> Expected `as.integer("x")` not to throw any warnings.
#> Actually got a <simpleWarning> with message:
#>   NAs introduced by coercion
----

Source: https://testthat.r-lib.org/reference/expect_error.html[testthat package documentation: expect_error, expect_warning and expect_message]

Read the three failing examples carefully. In the first, `expect_error(book(""), "a book needs an author")`, the error that the code really signals does not match the pattern, so it escapes the expectation: the helper prints the message of the real error, `a book needs a title`, and not a report that the pattern differed. The second, `expect_error(book("A title"))`, reports `+Expected ... to throw a error.+` because the code returns normally (the article "a" before "error" is the real testthat text). In the third, the error `something else` escapes in the same way. The value returned by `expect_error()` is the condition (`class(cnd)` is `"simpleError" "error" "condition"`), so `conditionMessage(cnd)` is available. The last group is `expect_no_error()`, `expect_no_warning()`, `expect_no_message()` and `expect_no_condition()`, which assert that the code runs without that condition and print the condition when it does not.

The `+expect_no_*()+` expectations (experimental when added in testthat 3.1.5, stable since 3.2.0) are the replacements for `expect_error(code, NA)`. Two cautions apply to them. Writing R Extensions tells package authors not to test for the absence of warnings, because later versions of R or of other packages may add warnings (some deprecation notices are meant to stay for a long time) and the tests should not turn them into failures; and it advises against testing the exact text of messages produced by R or by other packages, which can change and be translated. Both are good reasons to `expect_no_warning()` only about code that you own, and to test messages of your own functions, not R's.

Source: https://cran.r-project.org/doc/manuals/r-release/R-exts.html#Writing-portable-packages[Writing R Extensions: Writing portable packages]

=== Output, silence and visibility

`expect_output(code, regexp)` checks what the code prints to the standard output. `regexp = NA` asserts that nothing is printed. `expect_silent()` asserts that the code prints nothing, signals no message and no warning; `expect_visible()` and `expect_invisible()` check whether the value of the call is printed at the console. Printing is done by `print()` methods and by `cat()`, so these are the tools for testing a print method such as `print.book()`, with the caveat that a test of the exact layout of a print method is more convenient as a snapshot.

[source,r]
----
library(testthat)
Sys.setenv(TESTTHAT_EDITION = "3")
source("scenario.R")

failure <- \(code) tryCatch(code, error = \(e) cat(conditionMessage(e), "\n"))

b <- book("Paper Moons", "Noor Haddad")

# Printed output: a regular expression, or NA for "no output at all".
expect_output(print(b), "n.d.")
failure(expect_output(print(b), "2018"))
#> Expected output from `print(b)` to match regexp "2018".
#> Actual output:
#> ✖ │ <book> Paper Moons (Noor Haddad, n.d.)
expect_output(invisible(b), NA)
failure(expect_output(print(b), NA))
#> Expected `print(b)` to produce no output.
#> Actual output:
#> <book> Paper Moons (Noor Haddad, n.d.)

# capture.output() gives the text that expect_output() matches against.

out
#> [1] "<book> Paper Moons (Noor Haddad, n.d.) "
expect_identical(out, "<book> Paper Moons (Noor Haddad, n.d.) ")

# expect_silent(): no output, no messages, no warnings.
expect_silent(format(b))
failure(expect_silent(print(b)))
#> Expected `print(b)` to run silently.
#> Actual noise: output.
failure(expect_silent(as.integer("x")))
#> Expected `as.integer("x")` to run silently.
#> Actual noise: warnings.

# Visible and invisible results.

#> Actual visibility: visible.

=== Your own expectations: pass(), fail() and succeed()

An expectation that a package needs several times can be written as a function. It has four parts: capture the value and its label with `quasi_label(rlang::enquo(object))`, call `fail(message)` for each way the value can violate the expectation, call `pass()` when it does not, and return the input invisibly so that the expectation can be piped. The message has the same shape as the built-in ones: the first element says what was expected, the following ones what was seen. testthat 3.3.0 added `pass()`, for use in place of `succeed()`, which still works and just records a success with a message. Put such functions in a `+helper-*.R+` file, so that every test file has them.

Because an expectation is a function it can have bugs, and it must signal exactly one success or exactly one failure. `expect_success()` and `expect_failure()` check that, and `expect_snapshot_failure()` records the failure message of an expectation in a snapshot. The script uses the built package through `shelf::` calls and installs the stop reporter without praise.

[source,r]
----
library(testthat)
Sys.setenv(TESTTHAT_EDITION = "3")
set_reporter(StopReporter$new(praise = FALSE))
books <- shelf::books

# A custom expectation: capture the label, fail or pass, return the input.
expect_valid_isbn <- function(object) {
  act <- quasi_label(rlang::enquo(object))
  ok <- shelf::is_valid_isbn13(act$val)
  if (!all(ok)) {
    fail(c(
      sprintf("Expected every element of %s to be a valid ISBN-13.", act$lab),
      sprintf("Invalid: %s", toString(dQuote(act$val[!ok], FALSE)))
    ))
  } else {
    pass()
  }
  invisible(act$val)
}

# Expectations are functions: test them with expect_success()/expect_failure().
test_that("expect_valid_isbn() reports one success or one failure", {
  expect_success(expect_valid_isbn(books$isbn[1:5]))
  expect_failure(expect_valid_isbn(books$isbn))
})

# And look at the message that a user would see.
tryCatch(
  test_that("the failure message names the bad ISBNs", {
    expect_valid_isbn(books$isbn)
  }),
  error = \(e) invisible(NULL)
)
#> ── Failure: the failure message names the bad ISBNs ────────────────────────────
#> Expected every element of `books$isbn` to be a valid ISBN-13.
#> Invalid: "", "978-0-01-100112-9"
----

Source: https://testthat.r-lib.org/articles/custom-expectation.html[testthat package documentation: Custom expectations]

* The first failure is `expect_equal(nrow(out), 31L)`: testthat names the expression it evaluated, `nrow(out)`, shows both values under `actual` and `expected` and does not say anything else, because there is nothing else to say about two numbers. == Describing behaviour with describe() and it()

`describe()` and `it()` are a second way of writing the same tests, in the style of behaviour-driven development tools such as RSpec for Ruby and Mocha for JavaScript. A `describe()` block names a component, an `it()` inside it names one specification, and the pair reads as a sentence: "is_valid_isbn13() accepts hyphenated and bare forms of a valid ISBN". The interface has been in testthat since version 0.9 (2014), and `it()` was exported in 3.1.8 so that it can be run interactively. Each `it()` is evaluated in its own environment like a `test_that()` block, `describe()` blocks can be nested, and a specification without code, `it("handles NA")`, is reported as a skipped test with the reason `empty test`, which makes it a to-do list that the suite shows. The help page says to use `describe()` to verify that you implement the right things and `test_that()` to ensure you do the things right: in practice most packages use `test_that()` and keep `describe()` for functions with several specifications.

The `shelf` suite has one `describe()` block, in `test-book.R`:

[source,r]
----
describe("is_valid_isbn13()", {
  it("accepts hyphenated and bare forms of a valid ISBN", {
    expect_identical(
      is_valid_isbn13(c("978-0-00-100010-0", "9780001000100")),
      c(TRUE, TRUE)
    )
  })
  it("rejects wrong check digits, short strings, empty strings and NA", {
    expect_identical(
      is_valid_isbn13(c("9780001000101", "978030640615", "", NA)),
      c(FALSE, FALSE, FALSE, FALSE)
    )
  })
  it("returns a logical of the same length, including length zero", {
    expect_identical(is_valid_isbn13(character()), logical())
  })
})
----

Source: https://testthat.r-lib.org/reference/describe.html[testthat package documentation: describe]

The names of the three tests in a report or in the data frame that the runner returns are the descriptions joined with `/`: `is_valid_isbn13() / accepts hyphenated and bare forms of a valid ISBN`. `test_file()` can run one test of a file with its `desc` argument (testthat 3.2.0), and since testthat 3.3.0 `desc` can be a character vector that names the path through nested blocks, so one `it()` of a `describe()` is selected by the two descriptions. The first row of the result is the specification that ran, and the second the enclosing `describe()`, which contains no expectation of its own:

[source,r]
----

results$test

[[snapshots]]
== Snapshot tests

Some expected results are awkward to write as code: output with many quotes and line breaks, output too long to put in a test file, a print method or an error message whose point is that a human finds it readable. For these testthat has snapshot tests, also called golden tests: instead of describing the expected result in code, the expectation runs the code, records what happened in a separate Markdown file under `tests/testthat/_snaps/`, and on later runs compares the new result with the recorded one. They were added in testthat 3.0.0 and `expect_snapshot()` stopped being experimental in 3.1.0. Snapshots work only in the third edition (in the second, `expect_snapshot()` stops with an error saying that `expect_snapshot()` requires the 3rd edition, as the section on common errors shows) and are stored only when a whole test file runs, with `test_file()`, `test_dir()` or one of the functions built on them; run at the console, a snapshot expectation only displays the result, and the testthat article shows it saying that it can't save or compare to a reference when testing interactively.

=== The first run: recording

`expect_snapshot(code)` runs `code` as if typed at the console and records the code, the printed output, the messages, the warnings and the errors. The first time it runs there is nothing to compare with, so testthat records the result and reports it as a warning, so that you read it before you commit it. The experiment below deletes the `+_snaps+` directory of the copy of the package and runs the tests twice. The spinner lines of `devtools::test()` are left out:

# Throw the stored snapshots away to see what a first run looks like.

=== When a snapshot changes

If the output changes, the expectation fails, shows a diff of the old and the new, and writes the new result to `book.new.md` next to the recorded file. The experiment below changes `print.book()` so that it prints `+<Book>+` instead of `+<book>+`, runs the tests of that file, accepts the change with `snapshot_accept()`, shows what changed in `book.md`, and restores the source and the snapshot:

[source,r]
----
# Remember the originals so that the script can put them back at the end.
book_r <- readLines("R/book.R")
snap <- readLines("tests/testthat/_snaps/book.md")

# Change what print.book() prints: "<book>" becomes "<Book>".
changed <- sub('cat("<book>"', 'cat("<Book>"', book_r, fixed = TRUE)
writeLines(changed, "R/book.R")

# The snapshot no longer matches: the test fails and a .new.md file appears.
devtools::test(filter = "book")
list.files("tests/testthat/_snaps")

# The change is deliberate: accept it, which replaces book.md by book.new.md.

* `error = TRUE` is required to record an error. `expect_snapshot(book("X", isbn = "9780001000101"))` without it fails, because an unexpected error is a failure (even on CRAN); with it, the error is recorded as a `Condition` and the test passes, and an expected error that does not occur is a failure. The error argument checks that at least one expression in the block errors, not that every one does. The display shows the call and the message the way R prints them at the console; it does not include the class of the condition unless `cnd_class = TRUE`, because classes are added by upstream packages and R itself (testthat 3.1.1 introduced the argument and 3.2.0 made the class-free display the default for every package).
* One `expect_snapshot()` can hold several statements, as the second test does: the assignment with a warning, a message, and a call whose printed value is recorded. Each statement is recorded under its own `Code` heading, followed by `Output`, `Message` or `Condition` for what it produced.
* `expect_snapshot_value(x, style)` records the value instead of the printed text. The styles are `"json"` (the default; the simplest output, for simple objects, written with the jsonlite package), `"json2"` (more verbose, for a wider range of objects), `"deparse"` (a depiction of the object as R code) and `"serialize"` (a binary serialization that works for nearly any object and is opaque); `tolerance` makes the comparison numerical, like `expect_equal()`. In the example, `deparse` records two lines of R code that rebuild the data frame.
* `expect_snapshot_file(path, name)` snapshots a whole file, such as a plot or a written CSV, in `+_snaps/<test file>/<name>+`, one file for each expectation. A changed file cannot be diffed automatically: the new version is saved as `months.new.csv` and `snapshot_review()` shows both. The function is usually called through a wrapper that skips the test on platforms where the output is not reproducible, and a wrapper should call `announce_snapshot_file()` so that testthat does not delete a snapshot that was not regenerated because the test was skipped. For plots testthat points to the vdiffr package, which is not installed here and is named only.
* `+transform = \(lines) ...+` rewrites the lines before they are recorded, which is how to remove temporary paths, versions, times and other things that vary. Here the temporary path from `withr::local_tempfile()` is replaced by `+<path>+`; without the transform, the snapshot would change on every run, and the test would fail on every run after the first.
* `variant = "r4.6"` stores the result in `+_snaps/r4.6/snapshots.md+` instead of `+_snaps/snapshots.md+`, so that one test can record the output that differs by operating system, R version or dependency version, each in its own file. testthat calls variants an advanced feature: once they exist, you are responsible for deleting the ones that are no longer used, and for having a way to get changed snapshots out of the CI system and back into the repository.

[[snapshots-and-cran]]
=== Snapshots and CRAN

`expect_snapshot()` has the argument `cran = FALSE`: by default the snapshot expectations are not verified on CRAN, because snapshot tests rely on details of the output that dependencies may change (the help page gives that reason). On CRAN they return without recording or comparing anything. In testthat 3.3.0 they stopped skipping the rest of the test (as `skip_on_cran()` would) and began returning right away, neither passing nor failing, and the test that contains them is reported as skipped on CRAN. That is what the real `R CMD check --as-cran` of the package shows: `SKIP 2`, the snapshot test in `test-book.R` and the `skip_on_cran()` test in `test-loans.R`, and `PASS 49` instead of the `PASS 52` of `devtools::test()` (see <<skipping,Skipping tests>>). Do not set `cran = TRUE` for text that depends on other packages or on R's own messages. Writing R Extensions warns against exactly that: R's messages change between versions and are translated.

=== When to use a snapshot

A snapshot is a record of what the code did, which is not the same as a statement of what it should do. A reviewer who accepts a changed snapshot without reading it has turned the test off. Use a snapshot where a human is the judge (a print method, a `cli` message, the wording of an error), where the output is long and only its stability matters, or as a first test of legacy code. Use `expect_equal()` and its relatives for values and structure, which a snapshot hides in text, and `expect_error(class = )` where an error has a class; in the `shelf` suite, `describe()` and `expect_identical()` test the logic, and only the two print methods are snapshots. Keep the code in a snapshot small, so that a failure diff points at one thing.


[[fixtures]]
== Fixtures and withr

A test should leave the world as it found it. The state after test number `i` is the starting state of test `i + 1`, so a test that sets an option, an environment variable or the working directory and forgets to undo it makes the next test depend on it, and the failures that result appear in a different place from the cause. The test-fixtures article of testthat lists the things a test typically changes: a file or a directory, a resource on an external system, an R option, an environment variable, the working directory, or the state of the package under test. A _fixture_ in this sense is a piece of code that sets one of them up for the length of a test and removes it afterwards.

testthat does not contain the tools for this itself; it relies on the package withr (3.0.3 here, an add-on package, listed under `Suggests` in `shelf` because the tests call it with `::`). Its functions come in pairs: `+with_*()+` changes something for the evaluation of one expression and `+local_*()+` changes it until the surrounding function, or the surrounding `test_that()` block, ends. The five that cover most tests are:

[cols="2,3",options="header"]
|===
|Change |withr function
|Create a temporary file that is deleted afterwards |`withr::local_tempfile()`
|Create a temporary directory |`withr::local_tempdir()`
|Set an R option |`withr::local_options()`
|Set an environment variable |`withr::local_envvar()`
|Change the working directory |`withr::local_dir()`
|===

Source: https://testthat.r-lib.org/articles/test-fixtures.html[testthat package documentation: Test fixtures]

withr has many more: `local_seed()` and `with_seed()` for the random-number generator, `local_timezone()`, `local_locale()`, `local_language()` and `local_collate()` for the things that differ between machines, `local_path()`, `local_libpaths()`, `local_connection()`, `local_db_connection()`, `local_package()` and the graphics devices (`local_png()`, `local_pdf()`, `local_svg()`). * The first test writes three rows of `books` to a temporary file and reads them back. * The second test changes an option (`digits`), a package option (`shelf.loan_days`), an environment variable and the working directory (to a temporary directory, which is itself deleted at the end). * The fourth test calls `withr::defer()` twice. The deferred actions run when the test ends, in the reverse order of registration: `cleanup 2` is printed before `cleanup 1`, after the line printed by the body of the test. Last in, first out is what makes teardown correct: a file that was created inside a temporary directory must be removed before the directory.
* The last test defines a helper, `local_loan_days()`, that changes an option for its _caller_. === on.exit() and defer()

Base R's `on.exit()` is the primitive behind all of this: it runs an expression when the current function exits, whether normally or through an error. In a test the habit is `on.exit(options(old), add = TRUE, after = FALSE)`, where the two arguments make sure that a second `on.exit()` call adds to the first instead of replacing it, and that the cleanup runs in reverse order. The test-fixtures article names three drawbacks: the arguments are easy to forget, it does nothing useful at the top level of a script (the code is never run), and it cannot be put in a helper, because it is bound to the function that calls it. `withr::defer()` has none of them: its default behaviour is the right one, it can be told which environment to bind the cleanup to (a helper passes its caller's environment), and at the top level of a script or the console it records the action and you run it with `withr::deferred_run()`. The `+local_*()+` functions are `defer()` applied to the most common setup actions. See xref:programming-languages/r/scoping-environments-and-closures.adoc[Scoping, Environments and Closures] for what `parent.frame()` is.

Source: https://search.r-project.org/R/refmans/base/html/on.exit.html[R documentation: on.exit]

The name `+local_+` is chosen on purpose: the change is local to the function or test. The article adds that a `+local_+` call can be scoped to a smaller part of a test with `+local({ ... })+`.

=== Where a fixture is applied: test, file, package

A fixture can be applied at three scopes, and the choice is a trade-off between duplication and debuggability.

* Inside a `test_that()` block, which is the default. The change lasts for that test. A failing test can be reproduced in an interactive session by running the body line by line.
* At the top of a test file, outside any `test_that()`. It then lasts to the end of the file, and so affects every test after it. This saves repetition, but a test that fails cannot be reproduced without first running the lines at the top. The testthat article leans towards copying the fixture into each test for exactly that reason.
* Package-wide, in a _setup file_ in `tests/testthat/`. The code of a file whose name starts with `setup` (by convention `setup.R`) runs once before any test file. Cleanup belongs in the same file, registered with `+withr::defer(..., teardown_env())+` or `+withr::local_options(..., .local_envir = teardown_env())+`: `teardown_env()` is a special environment that stays alive until all the tests have run. The older approach, a `+teardown-*.R+` file, still works but is no longer recommended, because setup and cleanup in different files drift apart.

A _helper file_ (`+helper-*.R+`) is different: it only defines things, such as the `shelf_fixed_today` constant and `read_fixture_books()` of the `shelf` suite, custom expectations and `+local_*+` helpers. The difference between the two matters when the tests are run interactively. Helper files are sourced by `devtools::load_all()` as well as by `test_check()` and its relatives, so the objects exist when you work on a failing test. Setup files are sourced only by the functions that run tests, not by `load_all()`, so after `load_all()` whatever a setup file would have created, such as an option, is missing. Data files for tests go in the `tests/testthat/fixtures/` directory (any name works, since testthat ignores directories it does not know), which the `shelf` suite uses for `books-small.csv`. Reach them with `test_path("fixtures", "books-small.csv")`: the function returns a path that is correct whether the tests are run from the package root, from `tests/testthat/` or by `R CMD check`. A helper that reads the file, as `read_fixture_books()` does, keeps the path in one place. Anything a test writes goes to `withr::local_tempfile()`, never into the tests directory.

[[mocking]]
== Mocking with local_mocked_bindings()

_Mocking_ means temporarily replacing a function by a fake that behaves in a way the test controls. The reasons are the ones in the mocking article of testthat: to reach a failure that is hard to produce on purpose (what if a package is missing?), to make a test faster (replace a slow computation), and to make a test reliable (replace the clock, the network, the contents of a file). The same article is frank about the cost: mocking is an advanced technique that can make tests brittle, or let them hide problems, and should be used only when a simpler technique does not work.

In `shelf` there is exactly one mock, and it is a good example of the situation. `overdue_loans()` takes the reference date as an argument, `today`, which makes nearly all the tests deterministic without any mock. Its default, `shelf_today()`, is a one-line internal function that returns the current date: the code that reads the clock is in one place, behind a name that a test can replace.

The function is defined in `R/loans.R` with a comment that says why it exists ("kept as a function so that tests can replace it"), and its body is a single call of the base function `Sys.Date`.

The test that uses it is the second one of `test-loans.R` (shown in full above):

[source,r]
----
test_that("overdue_loans() uses the current date by default", {
  local_mocked_bindings(shelf_today = function() shelf_fixed_today)
  expect_identical(
    overdue_loans(loans),
    overdue_loans(loans, today = shelf_fixed_today)
  )
})
----

Source: https://testthat.r-lib.org/reference/local_mocked_bindings.html[testthat package documentation: local_mocked_bindings]

`local_mocked_bindings(shelf_today = function() shelf_fixed_today)` replaces the binding `shelf_today` in the namespace of the package under test, for the length of the test; at the end of the test the original is put back. No `.package` argument is needed here: when a whole package's tests are run, or when one package is loaded with `devtools::load_all()`, testthat knows which package is meant. Outside a package, in a script, it must be named.

=== How the replacement works

`local_mocked_bindings()` changes the binding in the package's _namespace environment_, where the package's own functions find their free variables (see xref:programming-languages/r/packages-libraries-and-namespaces.adoc[Packages, Libraries and Namespaces] for what a namespace is and xref:programming-languages/r/scoping-environments-and-closures.adoc[Scoping, Environments and Closures] for lexical scoping). Code in the package that calls `shelf_today()` sees the replacement; code elsewhere is not affected, which is the property testthat calls hygiene. Three consequences follow from that, and each shows up in the script below:

* An unexported function cannot be reached as `shelf::shelf_today()`; the `::` operator reports that it is not exported, and `:::` reaches it. The script prints both.
* Only a binding that already exists can be replaced. The namespace of a package is locked once it is loaded, so a new binding cannot be added, and `local_mocked_bindings()` reports a missing binding.
* A function that belongs to base R, such as `Sys.Date`, has no binding in the package namespace and so cannot be replaced there. The remedies are either to put a placeholder binding for the base function in the package (`+interactive <- NULL+` is the example of the help page), or, as `shelf` does, to wrap the call in a function of the package, which is also better design. A function that the package calls as `otherpackage::fun()` is not read from the package namespace either; import it or call it through a wrapper that can be mocked.

The binding can be anything, not only a function (since testthat 3.2.1). Bindings in the imports of the package are also replaced, and so are S3 methods (since 3.1.8). `+with_mocked_bindings(code, ...)+` is the same replacement for one expression instead of the rest of the current scope.

[source,r]
----
library(testthat)
set_reporter(StopReporter$new(praise = FALSE))
loans <- shelf::loans

# shelf_today() is internal: shelf:: cannot reach it, shelf::: can.
tryCatch(shelf::shelf_today(), error = \(e) conditionMessage(e))
#> [1] "'shelf_today' is not an exported object from 'namespace:shelf'"
inherits(shelf:::shelf_today(), "Date")
#> [1] TRUE

# Which environment owns the function? The package, until it is replaced.
owner <- \() environmentName(environment(shelf:::shelf_today))
owner()
#> [1] "shelf"

# Outside the package's own tests, name the package whose binding to mock.
test_that("shelf_today() can be replaced for one test", {
  local_mocked_bindings(
    shelf_today = \() as.Date("2026-06-30"),
    .package = "shelf"
  )
  expect_identical(shelf:::shelf_today(), as.Date("2026-06-30"))
  print(owner())
  expect_identical(nrow(shelf::overdue_loans(loans)), 32L)
})
#> [1] ""

# After the test the original function is back.
owner()
#> [1] "shelf"

# The same replacement for a block of code only.
with_mocked_bindings(
  nrow(shelf::overdue_loans(loans)),
  shelf_today = \() as.Date("2026-06-30"),
  .package = "shelf"
)
#> [1] 32

# Only bindings that already exist can be mocked.
tryCatch(
  local_mocked_bindings(not_a_function = \() 1, .package = "shelf"),
  error = \(e) conditionMessage(e)
)
#> [1] "Can't find binding for `not_a_function`"

# Base functions such as Sys.Date are not bindings of the package namespace.
tryCatch(
  local_mocked_bindings(
    Sys.Date = \() as.Date("2026-06-30"),
    .package = "shelf"
  ),
  error = \(e) conditionMessage(e)
)
#> [1] "Can't find binding for `Sys.Date`"

# A mock that returns different values in turn, such as answers to a prompt.
test_that("mock_output_sequence() returns its values one at a time", {
  answer <- mock_output_sequence("3", "n")
  expect_identical(answer(), "3")
  expect_identical(answer(), "n")
  expect_error(answer(), "Can't find value for 3th iteration")
})
----

Source: https://testthat.r-lib.org/reference/local_mocked_bindings.html[testthat package documentation: local_mocked_bindings and with_mocked_bindings]

The first call prints the real text of the error that `::` gives for an internal function; the next line shows `:::` working. `owner()` asks which environment the function belongs to: before the test it is the package (`"shelf"`). Inside the test, `shelf:::shelf_today()` returns the fixed date, `owner()` prints an empty name (the replacement is a function created inside the test, whose environment has no name), and `overdue_loans(loans)`, called with no `today` argument, finds the 32 overdue loans that `today = shelf_fixed_today` found in the real test. After the test `owner()` is `"shelf"` again: the original function is back. `with_mocked_bindings()` returns the value of its expression (`32`). The next two calls are the real messages for the two mistakes above. The last test shows `mock_output_sequence()`, which creates a function that returns its arguments one at a time, for code that asks for several answers (a prompt, a retried request); asking for more values than it holds is an error, caught by `expect_error()`.

=== Other mocks, and alternatives

testthat 3.3.0 added `local_mocked_s3_method()`, `local_mocked_s4_method()` and `local_mocked_r6_class()` for methods and classes, and 3.3.2 let the S3 and S4 versions mock methods that do not exist yet or remove one temporarily. The mocking article says to reach for them once the basic idea is clear and not before.

The older `with_mock()` and `local_mock()` replaced functions by modifying the namespace of a package. The NEWS of testthat deprecated them in 3.0.0, recommending the mockr or mockery packages instead, and made them defunct in 3.3.0, because the technique that made them work is no longer permitted in R 4.5.0; the message that the script of the third-edition section printed for `with_mock()` is "with_mock() was deprecated in testthat 3.2.0 and is now defunct" followed by the advice to use `with_mocked_bindings()`. Those two packages, which were the recommendation before `local_mocked_bindings()` existed, are not used on this page; neither is installed in the image used here.

Before mocking, three designs remove the need for it, and tests written that way are simpler to read:

* Make the state an argument. `+overdue_loans(loans, today = ...)+` and `loan_summary(loans, books, today, loan_days)` take the date and the loan period as parameters with defaults, so a test passes the values it wants.
* Make the global state a package option read at call time, as `shelf.loan_days` is, and change it for one test with `withr::local_options()`.
* Separate computation from input and output, so the part under test is a pure function (see <<testable-code,Writing code that is easy to test>>).

Mocking is the right tool when none of those fits: a failure that cannot be provoked (the network is down), a slow or non-deterministic dependency, an interactive prompt, a platform check. Keep the replacement as small as possible, and test the real thing too wherever you can.


[[skipping]]
== Skipping tests

A skipped test is neither a pass nor a failure: it is a test that cannot or should not run in the current circumstances, and the reporter says why. The cases the skipping article lists are the usual ones. The test depends on a web service that sometimes fails, or on credentials that exist only on some machines. It uses a feature that some operating systems lack (Windows, for example, has had limited UTF-8 support). It needs a version of R or of a dependency that not every test machine has. Or it is simply too slow for the CRAN check farm, whose policy asks that checking a package should take as little CPU time as possible, that long-running tests may be made optional, and that a package which uses Internet resources should fail gracefully, with an informative message and without a check warning or error, when the resource is unavailable.

Source: https://cran.r-project.org/web/packages/policies.html[CRAN Repository Policy]

`skip(message)` signals a condition of class `skip`; `test_that()` catches it, abandons the rest of the block and reports the reason. The helper functions call `skip()` for you when a condition holds:

[cols="2,4",options="header"]
|===
|Function |Skips when
|`skip_if(condition, message)`, `skip_if_not(condition, message)` |The condition is `TRUE` (`skip_if()`) or not `TRUE` (`skip_if_not()`): the building blocks for your own helpers.
|`skip_if_not_installed(pkg, minimum_version)` |The package is not installed or cannot be loaded, or is older than `minimum_version`.
|`skip_unless_r(">= 4.1.0")` |The running R does not satisfy the specification (testthat 3.3.0).
|`skip_on_cran()`, `local_on_cran()` |The tests count as running on CRAN: `NOT_CRAN` is set to something other than `true`, or it is unset and the session is not interactive. `local_on_cran(TRUE)` pretends to be on CRAN for the current scope (3.3.0).
|`skip_on_os(os, arch)` |The operating system (`"windows"`, `"mac"`, `"linux"`, `"solaris"`, `"emscripten"`) and, optionally, the architecture match.
|`skip_on_ci()` |The environment variable `CI` is set, as continuous-integration services do.
|`skip_on_covr()` |covr is measuring coverage (the environment variable `R_COVR` is set).
|`skip_on_bioc()` |The check runs on a Bioconductor build machine (`IS_BIOC_BUILD_MACHINE`).
|`skip_if_offline(host)` |There is no internet connection; needs the curl package, and itself calls `skip_on_cran()`.
|`skip_if_translated(msgid)` |The message identified by `msgid` is translated in the current language.
|===

Source: https://testthat.r-lib.org/reference/skip.html[testthat package documentation: skip]

The script catches the `skip` condition with `tryCatch()` (a skip is a condition, see xref:programming-languages/r/conditions-and-error-handling.adoc[Conditions and Error Handling]) and prints the reason that each helper would have given. The helper `reason()` returns `"not skipped"` when the code ran to the end:

[source,r]
----
library(testthat)

# A skip is a condition of class "skip": catch it to read the reason.
reason <- \(code) {
  tryCatch(
    {
      code
      "not skipped"
    },
    skip = \(s) conditionMessage(s)
  )
}

reason(skip("the catalogue server is down"))
#> [1] "Reason: the catalogue server is down"
reason(skip_if(TRUE, "RUN_SLOW_TESTS is not set"))
#> [1] "Reason: RUN_SLOW_TESTS is not set"
reason(skip_if_not(FALSE))
#> [1] "Reason: FALSE is not TRUE"
reason(skip_if_not(file.exists("secure-token.json"), "no token"))
#> [1] "Reason: no token"
reason(skip_if_not_installed("nosuchpackage"))
#> [1] "Reason: {nosuchpackage} is not installed"
reason(skip_if_not_installed("testthat", minimum_version = "99.0.0"))
#> [1] "Reason: Installed testthat is version 3.3.2; but 99.0.0 is required"
reason(skip_on_os("windows"))
#> [1] "not skipped"
reason(skip_unless_r(">= 99.0"))
#> [1] "Reason: Current R version (4.6.1) does not satisfy requirement (>= 99.0)"
reason(skip_on_cran())
#> [1] "Reason: On CRAN"
reason(skip_on_ci())
#> [1] "not skipped"

# skip_on_cran() looks at NOT_CRAN, which devtools and testthat set to "true".
Sys.getenv("NOT_CRAN", "<unset>")
#> [1] "<unset>"
Sys.setenv(NOT_CRAN = "false")
reason(skip_on_cran())
#> [1] "Reason: On CRAN"
Sys.setenv(NOT_CRAN = "true")
reason(skip_on_cran())
#> [1] "not skipped"

# local_on_cran() pretends to be on CRAN until the current scope ends.
local({
  local_on_cran(TRUE)
  reason(skip_on_cran())
})
#> [1] "Reason: On CRAN"
reason(skip_on_cran())
#> [1] "not skipped"

# skip_on_ci() looks at CI.
Sys.setenv(CI = "true")
reason(skip_on_ci())
#> [1] "Reason: On CI"
----

Source: https://testthat.r-lib.org/articles/skipping.html[testthat package documentation: Skipping tests]

Notice what each line says. `skip_if_not(FALSE)` has no message of its own, and the reason is the generated `FALSE is not TRUE`. `skip_if_not_installed()` writes the package name in braces and, for a version requirement, both versions. `skip_unless_r()` prints the running version of R next to the requirement. The three helpers whose answer depends on the environment (`skip_on_cran()`, `skip_on_ci()`, `skip_on_os()`) give different answers on different machines, which is the point, but also the reason to be careful. In a plain `Rscript` session `NOT_CRAN` is not set, so `skip_on_cran()` already reports `On CRAN`, as it does on the check farm; the variable `NOT_CRAN=true` is what turns it off, and `devtools::test()` and `testthat::test_local()` set it when it is not set already (the table in <<running-tests,Running tests>> shows which test function does what). Setting `NOT_CRAN` to `"false"` skips, `"true"` does not, and `local_on_cran(TRUE)` pretends to be on CRAN until the end of its scope, which is how you rehearse a CRAN run from an interactive session.

=== Writing skip helpers, and when not to skip

A skip condition that several tests share belongs in a helper whose name starts with `+skip_+`, in a `+helper-*.R+` file. The fragment below is an example and not a script, and `shelf` has no such file:

[source,r]
----
skip_if_no_token <- function() {
  skip_if_not(file.exists("secure-token.json"), "no token")
}
----

Source: https://testthat.r-lib.org/articles/skipping.html[testthat package documentation: Skipping tests]

Another technique from the same article is to put a `skip()` inside a package function that cannot work without some tool, guarded by `testthat::is_testing()` (or the environment variable `TESTTHAT`, set to `true` while tests run), so that the function raises its normal error for users and a skip for the tests; the authors say they have mixed feelings about it, because it mixes code and tests.

Skipping is a decision with a cost. A skipped test is not a tested feature, and the usual way to fool yourself is to skip so much on CRAN or CI that the part of the suite that does run proves little. The advice in the article is to keep an eye on the skip summary. Three more points follow from this page. Do not skip because a suggested package is not installed: since testthat 3.3.0, `test_that()` does that by itself on CRAN, and the article advises assuming suggested packages are present except where they are hard to install. Do not use `skip_on_os()` to avoid a portability bug; fix the code. And if a test is slow, think about a smaller input before `skip_on_cran()`: the `shelf` test that is skipped on CRAN multiplies the loans fifty times to make the input large, and a smaller multiple would test the same thing.


[[third-edition]]
== The third edition: Config/testthat/edition and local_edition()

testthat has a very large number of reverse dependencies, and changing the behaviour of `expect_equal()` or of `expect_warning()` would turn passing test suites on CRAN into failing ones. testthat 3.0.0 (2020-10-31) therefore introduced the idea of an _edition_: a bundle of behaviours that a package must choose explicitly. A package that does not choose keeps the second edition, the behaviour of testthat 2.x; a package that chooses the third edition gets the current recommendations. The authors say that a new edition will be rare and will come with a new major version, so a fourth edition would arrive with testthat 4.0.0, and they explain why a new edition is not a new major version number: CRAN checks every package that uses testthat with the latest testthat, so incrementing the major version alone would not protect anyone from failures.

The edition is chosen in three places, from the widest to the narrowest.

* In `DESCRIPTION`, for every test of the package: `Config/testthat/edition: 3`. `usethis::use_testthat(3)` writes this field, together with the version requirement `testthat (>= 3.0.0)` in `Suggests`, as the listing of the `shelf` package earlier on this page shows.
* In a test file or a test, with `local_edition(3)` (or `local_edition(2)` to go back for one test while upgrading a suite). The change lasts until the current scope ends. `edition_get()` returns the edition in force.
* With the environment variable `TESTTHAT_EDITION`, which testthat 3.0.3 added: handy for scripts that run outside a package, because outside a package there is no `DESCRIPTION` to read, and the answer is then the second edition. This is why the scripts of this page that call third-edition behaviour start with `Sys.setenv(TESTTHAT_EDITION = "3")`, and why `edition_get()` in the script below prints `2`.

Source: https://testthat.r-lib.org/articles/third-edition.html[testthat package documentation: testthat 3e]

The third edition makes three kinds of change, and the scripts show each of them side by side with the second edition.

* *Equality is compared by waldo.* `expect_equal()` and `expect_identical()` call `waldo::compare()` instead of `all.equal()` and `identical()`. The difference is in what a failure tells you, as the first part of the script shows with two factors that have different levels. The second edition reports `Attributes: < Component “levels”: Lengths (2, 3) differ (string compare on first 2) >`, which is the message of `all.equal()`; the third reports the two level vectors one under the other with the names `levels(actual)` and `levels(expected)`. Besides the display, three behaviours differ: a single definition of tolerance everywhere (the old code mixed `all.equal()` and testthat's own `compare()`), the environments of functions and formulas are compared unless `ignore_function_env` or `ignore_formula_env` is set (this matters when testing fitted models), and a time zone that is set implicitly differs from one that is set explicitly.
* *Warnings and messages are captured one at a time and nothing is swallowed.* In the second edition `expect_warning()` swallowed every warning in the code, matching or not. In the third it captures at most one warning, the first that matches `regexp` and `class`, and every other warning bubbles up, so the second warning of `warn_twice()` is reported in the test (with the backtrace in the output). The same holds for `expect_error()`, `expect_message()` and `expect_condition()`, which use the same logic. Messages are no longer silenced automatically: the text `reading the catalogue` printed by `chatty()` appears in the output of the third-edition test and not in that of the second. Silence them with `suppressMessages()`, or test them with `expect_message()`.
* *Outdated functions are deprecated.* They still run, but each one warns, so the warnings tell you what to change; they do not make `R CMD check` fail.

[source,r]
----
library(testthat)
set_reporter(StopReporter$new(praise = FALSE))

# Outside a package there is no DESCRIPTION, so the 2nd edition is active.
edition_get()
#> [1] 2

# Equality: all.equal() in the 2nd edition, waldo in the 3rd.
a <- factor(c("fiction", "poetry"))
b <- factor(c("fiction", "poetry"), levels = c("fiction", "poetry", "classic"))
compare_in <- \(edition) {
  tryCatch(
    test_that(paste("factors in edition", edition), {
      local_edition(edition)
      expect_equal(a, b)
    }),
    error = \(e) invisible(NULL)
  )
}

=== The deprecated functions

The functions that the third edition deprecates are the ones that its own article lists. Run in the third edition, each one warns with the replacement to use, and the script below catches the warning to print its text:

[source,r]
----
library(testthat)
Sys.setenv(TESTTHAT_EDITION = "3")
source("scenario.R")

# In the 3rd edition the old helpers still run, but each one warns.
deprecation <- \(code) {
  tryCatch({
    code
    "no warning"
  }, warning = \(w) conditionMessage(w))
}

b <- book("Salt and Static", "Mara Quill", year = 2018)
deprecation(expect_is(b, "book"))
#> [1] "`expect_is()` was deprecated in the 3rd edition.\nℹ Use `expect_type()`, `expect_s3_class()`, or `expect_s4_class()` instead"
deprecation(expect_equivalent(c(a = 1), 1))
#> [1] "`expect_equivalent()` was deprecated in the 3rd edition.\nℹ Use expect_equal(ignore_attr = TRUE)"
deprecation(context("book"))
#> [1] "`context()` was deprecated in the 3rd edition."
deprecation(setup(NULL))
#> [1] "`setup()` was deprecated in the 3rd edition.\nℹ Please use test fixtures instead see vignette('test-fixtures') for details"
deprecation(teardown(NULL))
#> [1] "`teardown()` was deprecated in the 3rd edition.\nℹ Please use test fixtures instead see vignette('test-fixtures') for details"
deprecation(expect_that(1, equals(1)))
#> [1] "`expect_that()` was deprecated in the 3rd edition."
deprecation(expect_known_value(1, tempfile()))
#> [1] "`expect_known_value()` was deprecated in the 3rd edition.\nℹ Please use `expect_snapshot_value()` instead"

#> [1] "`with_mock()` was deprecated in testthat 3.2.0 and is now defunct.\nℹ Please use `with_mocked_bindings()` instead."
----

Source: https://testthat.r-lib.org/articles/third-edition.html[testthat package documentation: testthat 3e]

The replacements, in the order of the output, are: `expect_type()`, `expect_s3_class()` or `expect_s4_class()` for `expect_is()` (it forces you to say which object system you mean); `expect_equal(ignore_attr = TRUE)` for `expect_equivalent()`; nothing for `context()`, because the file name already serves as the context; test fixtures instead of `setup()` and `teardown()` (see <<fixtures,Fixtures and withr>>); plain expectations instead of the very old `expect_that(x, equals(y))` syntax; and snapshots (`expect_snapshot_value()` and its relatives) for `expect_known_value()`, `expect_known_output()`, `expect_known_hash()` and `expect_equal_to_reference()`. The last line of the output is not a warning but an error: `with_mock()` and `local_mock()`, deprecated for a long time, are defunct since testthat 3.3.0, and the message points to `with_mocked_bindings()` (see <<mocking,Mocking>>). Some other changes of the third edition are described elsewhere on this page: the condition expectations return the condition, not the value of the code (testthat 3.1.0, a change that applies to the third edition only), `expect_snapshot()` requires the third edition, and parallel testing requires it as well.

[[reproducible-output]]
=== Reproducible output

`test_that()` and `it()` call `local_test_context()` at the start of each test. It sets the environment variable `TESTTHAT` to `true` (in both editions) and, in the third edition only, calls `local_reproducible_output()`, which makes printed output the same on every machine: it turns off colour and `cli` Unicode bullets, sets the console width to 80, the collation to `C`, the language to `C` (to disable translations; this was `"en"` before testthat 3.2.2), `max.print` to its default, and so on. These are the arguments of the function and their defaults: `width = 80`, `crayon = FALSE`, `unicode = FALSE`, `rstudio = FALSE`, `hyperlinks = FALSE`, `lang = "C"`. A test that needs something else asks for it with `local_reproducible_output(width = 40)`. The script prints the values outside a test, inside, and inside a test that changes the width:

[source,r]
----
library(testthat)
Sys.setenv(TESTTHAT_EDITION = "3")
set_reporter(StopReporter$new(praise = FALSE))

# Outside a test.
c(Sys.getenv("TESTTHAT", "<unset>"), getOption("width"), is_testing())
#> [1] "<unset>" "80"      "FALSE"

# Inside test_that() testthat makes the output reproducible.
test_that("tests run in a controlled context", {
  cat("TESTTHAT:", Sys.getenv("TESTTHAT"), "\n")
  cat("width:", getOption("width"), "\n")
  cat("unicode:", getOption("cli.unicode"), "\n")
  cat("collation:", Sys.getlocale("LC_COLLATE"), "\n")
  expect_true(is_testing())
  expect_false(is_checking())
  expect_false(is_snapshot())
})
#> TESTTHAT: true
#> width: 80
#> unicode: FALSE
#> collation: C

# local_reproducible_output() lets one test ask for something else.
test_that("a test can change the console width", {
  local_reproducible_output(width = 40L)
  cat("width:", getOption("width"), "\n")
  expect_identical(getOption("width"), 40L)
})
#> width: 40
----

Source: https://testthat.r-lib.org/reference/local_test_context.html[testthat package documentation: local_test_context]

Outside a test the width is 80, R's default; `Sys.getenv("TESTTHAT")` is `+<unset>+` and `is_testing()` is `FALSE`. Inside the test `TESTTHAT` is `true`, `cli.unicode` is `FALSE` and the collation is `C`, whatever the machine's locale is. The three predicates `is_testing()`, `is_checking()` and `is_snapshot()` (testthat 3.1.9 for the last two) tell code whether it runs in tests, in a test run by `R CMD check`, or inside a snapshot. `is_parallel()` tells whether the files are run in worker processes. They exist for the few cases where a package function really has to behave differently under test.

=== Upgrading a suite from the second edition

The upgrade has four steps, in the order of the third-edition article. Activate the edition (`usethis::use_testthat(3)` does it). Replace or remove the deprecated functions. If the output became noisy, capture or suppress the warnings and messages that were silently swallowed before. Then inspect the tests that fail because the objects are no longer "all equal"; use `local_edition(2)` in a test that needs more time, and remove it afterwards. Tests that call `expect_equal()` on models, formulas or functions are the ones most likely to need a change.

=== From the console: test_file(), test_dir() and test_local()

The script runs parts of the suite of `shelf` in five ways, with the `check` reporter for the first four so that the output is compact. It must be run from the package directory. Two things in it deserve attention. `test_file()` and `test_dir()` do not load the package by themselves, so the calls give `package = "shelf"` and `load_package = "source"`. === Stopping early: set_max_fails()

A suite in which the same mistake breaks hundreds of expectations produces more output than anybody reads. The progress reporter stops a run after 10 failures; the limit is the option `testthat.progress.max_fails` or the environment variable `TESTTHAT_MAX_FAILS`, which `set_max_fails()` sets (for the current R process and any process it starts), and `set_max_fails(Inf)` removes it. The scratch file below sorts first, because its name starts with `aaa`, and fails twice:

[source,r]

# A scratch file that sorts before the others and fails twice.

test_that("second failure", expect_identical("a", "b"))

  "tests/testthat/test-aaa-failing.R"
)

# Stop after the first failing file instead of running everything.
testthat::set_max_fails(1L)
Sys.getenv("TESTTHAT_MAX_FAILS")
devtools::test()

# Inf lifts the limit again.
testthat::set_max_fails(Inf)
unlink("tests/testthat/test-aaa-failing.R")

=== Running in parallel

Test files can run in separate R processes. The conditions are the third edition and the line `Config/testthat/parallel: true` in `DESCRIPTION`. By default testthat uses `getOption("Ncpus", 2)` processes (the number of processes can be set with the environment variable `TESTTHAT_CPUS`, best put in `.Renviron`), and `TESTTHAT_PARALLEL=false` turns parallel running off temporarily, which is what to do for print debugging, because the output of `print()`, `cat()` and `message()` from the test files is lost when they run in a worker. A field `Config/testthat/start-first` lists glob patterns of test files to start first, so that the slowest ones begin early. Each worker loads testthat and the package, runs the setup files and then receives test files one at a time; state therefore persists between the files that one worker runs, which is the reason files must clean up after themselves (see <<fixtures,Fixtures and withr>>). Packages with many fast test files gain little, because starting the workers and relaying the results costs time: the article gives the tests of testthat itself as an example, 10 seconds in serial and 8 in parallel. A `test_dir()` call on a single file runs in serial since testthat 3.3.2. Some reporters cannot work in parallel (the debug, JUnit and location reporters and the stop reporter), and testthat then runs the files serially.

[source,r]
----
# Switch parallel testing on in DESCRIPTION (and put it back at the end).
description <- readLines("DESCRIPTION")
writeLines(c(description, "Config/testthat/parallel: true"), "DESCRIPTION")
tail(readLines("DESCRIPTION"), 2L)

# Two worker processes; the "check" reporter prints only the totals.
Sys.setenv(TESTTHAT_CPUS = "2")
devtools::test(reporter = "check")

# TESTTHAT_PARALLEL=false runs the files in this process again.
Sys.setenv(TESTTHAT_PARALLEL = "false")
devtools::test(reporter = "check")

writeLines(description, "DESCRIPTION")
----

Everything above ran the tests from a development session. The log is long. Its first lines (version of R, platform, compiler, session charset and the time) are trimmed here, and so are the lines of the checks that are not about tests. Two steps matter for this page: `checking for unstated dependencies in ‘tests’` (every package that the files under `tests/` load with `library()` or `::` must be declared in `DESCRIPTION`), and `checking tests` itself:

Each file that is directly in `tests/` is run in a separate R process, in a copy of the directory, with the installed package available; its output is written next to it as `+<name>.Rout+`. The test run is `ERROR` if a script stops with an error, and `OK` otherwise. Here two files ran. The first, `base-check.R`, is the plain-R test file of the section on base R below, which was added to the copy of the package for this run; its output was compared with a reference file. The second, `testthat.R`, is the driver of the suite. Its output is in `shelf.Rcheck/tests/testthat.Rout`, where the check directory keeps it, and the part that `test_check()` produced is:

The totals are not those of `devtools::test()`. `[ FAIL 0 | WARN 0 | SKIP 2 | PASS 49 ]` means that two tests were skipped on CRAN, and the report names them: `test-book.R:39:1`, the test that contains the two snapshot expectations, and `test-loans.R:40:3`, the one that calls `skip_on_cran()`. The `NOT_CRAN` environment variable is not set in a check run, and `R CMD check --as-cran` is what CRAN does, so testthat acts as it would there. Source: https://testthat.r-lib.org/reference/skip.html[testthat package documentation: skip_on_cran]

With `NOT_CRAN=true` the same suite reports `SKIP 0` and `PASS 52`, both the snapshots and the long test run, and the snapshot file `+_snaps/book.md+` is compared with the output. This is the check to run before a release (and what the continuous-integration workflow of the section on coverage does), and the other, without the variable, is the check CRAN runs. Both must pass. A suite that passes only with `NOT_CRAN=true` has hidden a problem in a skipped test; one that passes only without it has a test that depends on something the check farm does not have.

Three more things happen in a check run, all visible in the documentation of R and of testthat.

* *The number of lines kept.* The check log of a failing test shows only the last 13 lines of the output, which is the default of `+_R_CHECK_TESTS_NLINES_+` (0 keeps everything but the R preamble). The check reporter of testthat was designed so that those 13 lines are useful. The full output of a failed run is in `tests/testthat.Rout.fail` in the check directory. The section on <<reading-a-failure,reading a failure>> shows the log of a failing check.
* *Only declared packages.* With `--as-cran` the variable `+_R_CHECK_SUGGESTS_ONLY_+` is true, so tests run with a library that contains only the packages declared in `DESCRIPTION`. A test that uses a package that is not listed in `Suggests` fails in the check although it worked in the development session, where all your packages are installed (the first section of this page shows the real output of that case).
* *The time limit and the CPU time.* The CRAN Repository Policy asks that checking take as little CPU time as possible, and that long-running tests be made optional. Parallel testing must respect the limit of two cores that the policy sets for a package that uses several threads or cores; testthat's default of `getOption("Ncpus", 2)` workers keeps within it.

Source: https://cran.r-project.org/web/packages/policies.html[CRAN Repository Policy]

The tests of an installed package can also be run later with `tools::testInstalledPackage()`, the function that covr uses to run the tests under instrumentation, and `R CMD check` can take its tests from a non-standard directory with the option `--test-dir`: Writing R Extensions suggests `inst/slowTests` for slow tests, and names `inst/testWithOracle` and `inst/randomTests` as other examples.


[[base-r-tests]]
== Base R alternatives: tests/*.R, .Rout.save and stopifnot

testthat is a convention on top of a mechanism that R itself provides, and the mechanism works without it. Writing R Extensions describes it in one paragraph. The `tests` directory holds `.R` files; the results of running a file are written to a `.Rout` file; if there is a `.Rout.save` file with the same name, the two are compared, and differences are _reported but do not cause an error_. The directory is copied to the check area and the tests run with that copy as the working directory, with `R_LIBS` set so that `library(shelf)` finds the package installed for the check. The tests run in a vanilla R session and without a random-number seed, so tests that use random numbers must set one. An error in a script, such as a failed `stopifnot()`, makes the test run fail. That is the whole contract: a test is a script that stops with an error when something is wrong.

Source: https://cran.r-project.org/doc/manuals/r-release/R-exts.html#Package-subdirectories[Writing R Extensions: Package subdirectories]

The script below writes such a file into the copy of the package, `tests/base-check.R`, and lists the `tests` directory. The file loads the package, asserts with `stopifnot()` that a known ISBN is valid, builds a book, prints it and its summary, and prints two numbers about the overdue loans. It is the style of test that many older packages, and the packages of R itself, use: a script that exercises the code, with the expected output stored next to it.

stopifnot(is_valid_isbn13("978-0-306-40615-7"))

range(overdue$days_out)

  "tests/base-check.R"
)
list.files("tests")

=== stopifnot(), all.equal() and the tools package

For assertions inside the script, base R has `stopifnot()` and `all.equal()`, and the tools package has `assertError()` and `assertWarning()`. The script below runs them against the `shelf` scenario:

[source,r]
----
source("scenario.R")

# stopifnot(): silent when everything is TRUE, an error otherwise.
stopifnot(is_valid_isbn13("978-0-306-40615-7"), nrow(books) == 16L)
caught <- \(code) tryCatch(code, error = \(e) conditionMessage(e))
caught(stopifnot(nrow(books) == 20L))
#> [1] "nrow(books) == 20L is not TRUE"
caught(stopifnot("every ISBN must be valid" = all(is_valid_isbn13(books$isbn))))
#> [1] "every ISBN must be valid"
caught(stopifnot(all.equal(1, 1.1)))
#> [1] "1 and 1.1 are not equal:\n  Mean relative difference: 0.1"

# all.equal() describes the difference; identical() only says yes or no.
all.equal(0.1 + 0.2, 0.3)
#> [1] TRUE
all.equal(1, 1.1)
#> [1] "Mean relative difference: 0.1"
all.equal(c(a = 1), c(b = 1))
#> [1] "Names: 1 string mismatch"
identical(0.1 + 0.2, 0.3)
#> [1] FALSE
isTRUE(all.equal(100, 100.0000001))
#> [1] TRUE

# The tools package has assertions for conditions.
tools::assertError(book(""))
tools::assertWarning(as.integer("x"))
caught(tools::assertError(book("A title")))
#> [1] "Failed to get error in evaluating book(\"A title\")"
caught(tools::assertWarning(book("A title")))
#> [1] "Failed to get warning in evaluating book(\"A title\")"
----

Source: https://search.r-project.org/R/refmans/base/html/stopifnot.html[R documentation: stopifnot]

* `+stopifnot(...)+` is silent when every argument is `TRUE`; otherwise it stops with a message built from the failing expression: `nrow(books) == 20L is not TRUE`. Since R 4.0.0 an argument can be named, and the name is the message (`+"every ISBN must be valid" = all(...)+`), which makes the failure readable without a message in the code (R NEWS: Changes in R 4.0.0). Since R 3.5.0 the expressions can also be given in one braced block as `exprs =`. `stopifnot(all.equal(1, 1.1))` shows a pitfall that `stopifnot()` softens: `all.equal()` returns either `TRUE` or a _character string_ that describes the difference, so an expression such as `if (all.equal(x, y))` is an error waiting to happen. `stopifnot()` has recognised a call to `all.equal()` since R 3.4.0 and reports its message (`1 and 1.1 are not equal:` followed by `Mean relative difference: 0.1`); anywhere else, write `isTRUE(all.equal(x, y))`.
* `all.equal()` compares two objects with a tolerance (by default `sqrt(.Machine$double.eps)`, about `1.5e-8`, relative to the size of the numbers) and says how they differ: `Names: 1 string mismatch`. `identical()` says only yes or no, and is exact: `identical(0.1 + 0.2, 0.3)` is `FALSE`. These are the base R counterparts of `expect_equal()` and `expect_identical()`; in the third edition testthat uses waldo and not these two functions.
* `tools::assertError(expr)` and `tools::assertWarning(expr)` evaluate `expr` and signal an error if no error (respectively no warning) occurred, with the message `+Failed to get error in evaluating ...+`. Since R 4.0.0 they accept a `classes` argument to require a specific condition class. They are the base R counterparts of `expect_error()` and `expect_warning()`.

The table puts the three approaches side by side:

[cols="2,3,3,3",options="header"]
|===
|Question |Base R (`+tests/*.R+`) |testthat |tinytest
|Assert something is true |`stopifnot(x)` |`expect_true(x)` |`expect_true(x)`
|Equal within tolerance |`stopifnot(isTRUE(all.equal(x, y)))` |`expect_equal(x, y)` |`expect_equal(x, y)`
|Exactly identical |`stopifnot(identical(x, y))` |`expect_identical(x, y)` |`expect_identical(x, y)`
|An error with a message |`tools::assertError(f())` (message not checked) |`expect_error(f(), "text")` |`expect_error(f(), pattern = "text")`
|Printed output |`.Rout.save` |`expect_output()`, `expect_snapshot()` |`expect_stdout()`
|Grouping and names |none (a script) |`+test_that("...", { })+` |none (a script)
|On failure |the script stops at the first error |all expectations of all tests run, one report |all expectations of a file run, one report
|===

Source: https://search.r-project.org/R/refmans/base/html/all.equal.html[R documentation: all.equal]

Base-R tests are enough for a small package, they have no dependency, and they are also what to reach for in a package that must not suggest testthat. Their weakness is the failure report: a script stops at the first error with a one-line message, with no summary and no way to run one test, and the reference output compares text and not values. testthat adds the structure, and tinytest takes a middle way.

[[tinytest]]
== tinytest in brief

tinytest 1.4.3 (an add-on package, installed in the scratch library of these examples) is a small testing framework built on the idea that a test file should be a plain script. In its words, a test file is an R script in which some or all statements express an expectation; there is no `test_that()` block. It imports only the base packages `parallel` and `utils`. Its expectation functions have the names of the testthat ones (`expect_equal()`, `expect_error()`, `expect_true()`) with different arguments: the regular expression of `expect_error()` is called `pattern`, and the equality uses `all.equal()`. A test file runs from top to bottom, every expectation is recorded and nothing stops at a failure; `run_test_file()` returns an object of class `tinytests` that `all_pass()` and `summary()` inspect. The script below writes a four-expectation test file to a temporary directory and runs it. (Because the examples of this page run in a package-less script, `shelf::` calls stand in for the package that a real test file would load.)

[source,r]
----
# A tinytest file is a plain script of expect_*() calls: no test_that() blocks.
file <- file.path(tempdir(), "test_isbn.R")
writeLines(r"---(
expect_true(shelf::is_valid_isbn13("978-0-306-40615-7"))
expect_false(shelf::is_valid_isbn13(""))
expect_equal(shelf::normalise_isbn("978-0-306-40615-7"), "9780306406157")
expect_error(shelf::book(""), pattern = "a book needs a title")
)---", file)

out <- tinytest::run_test_file(file, verbose = 0L)
tinytest::all_pass(out)
#> [1] TRUE
summary(out)
#>
#> File          Results fails passes
#>   test_isbn.R       4     0      4
#>   Total             4     0      4
----

Source: https://search.r-project.org/CRAN/refmans/tinytest/html/run_test_file.html[tinytest package documentation: run_test_file]

`tinytest::setup_tinytest(pkgdir)` prepares a package: it creates `inst/tinytest/` with an example test file, creates `tests/tinytest.R` so that `R CMD check` runs the tests, and adds tinytest to `Suggests`. The experiment below runs it on a copy of the `shelf` package in a temporary directory and prints what it wrote; the real `tests/testthat.R` and its suite are not touched:

[source,r]
----

list.files(file.path(copy, "inst"), recursive = TRUE)
----

Source: https://search.r-project.org/CRAN/refmans/tinytest/html/setup_tinytest.html[tinytest package documentation: setup_tinytest]

[source,text]
----

}

[1] "CITATION"              "tinytest/test_shelf.R"

The driver `tests/tinytest.R` is the three lines printed: it calls `tinytest::test_package("shelf")` when tinytest is installed. The test files live in `inst/tinytest/` and so are installed with the package, which lets a user run `tinytest::test_package("shelf")` after installation; authors who prefer not to install them can put them in a directory under `tests/` and name it in the `testdir` argument. The grep line shows tinytest added to `Suggests` (the line is the end of the field). [[coverage]]
== Test coverage with covr

Coverage answers a narrow question: which lines of the package did the tests run? It does not say whether the lines were tested well, only that they were reached, so it finds the code that no test touches and says nothing about the quality of the tests that do. covr (3.6.5, an add-on package) is the standard tool. It modifies the code of the package, adding a tracking call to each call of the source, installs the instrumented copy in a temporary library and runs the tests with it, using `tools::testInstalledPackage()`. The covr documentation explains why it cannot run inside `R CMD check`: the modification may change behaviour in edge cases, and for compiled code the package is compiled without optimisation.

Source: https://covr.r-lib.org/index.html[covr package documentation: Test coverage for packages]

`covr::package_coverage()` takes the path of the package (the working directory by default) and the `type` of code to run: `"tests"` (the default), `"vignettes"`, `"examples"`, `"all"` or `"none"`. The script runs it on the `shelf` package and prints the result in the three forms that matter.

[source,r]
----
cov <- covr::package_coverage()
cov
covr::percent_coverage(cov)

# Lines that no test ran.
covr::zero_coverage(cov)

# Per file, as numbers.
round(covr::coverage_to_list(cov)$filecoverage, 2L)
----

`covr::codecov()` runs the coverage and uploads it to the Codecov service (named here, not run: it needs an upload token, read from the environment variable `CODECOV_TOKEN` or from a `codecov.yml` file in the package), and covr has similar functions for Coveralls, GitLab and Azure, and `to_cobertura()` and `to_sonarqube()` that write the XML formats other tools read. Lines that should not count, such as defensive branches that cannot be reached, are excluded in the source with the comment `# nocov` (one line) or a `# nocov start` and `# nocov end` pair, by the `line_exclusions` and `function_exclusions` arguments of `package_coverage()`, or with a `.covrignore` file; the patterns are the options `covr.exclude_pattern`, `covr.exclude_start` and `covr.exclude_end`. A test that should not run under coverage (a slow one, a test of timing) calls `skip_on_covr()`.

Source: https://covr.r-lib.org/index.html[covr package documentation: Exclusions]

=== A continuous-integration workflow

Coverage and the checks of the previous sections are usually run on every push by a continuous-integration service. The usethis function `use_github_action()` copies the maintained workflows of the r-lib/actions repository into `.github/workflows/` (`use_github_action("check-standard")`, `use_github_action("test-coverage")`), and covr's own documentation recommends it for setting up coverage. The fragment below shows the shape of such a workflow, with the actions pinned to `@v2` and a placeholder package; it is a fragment and was not run, because it needs a hosted runner:

[source,yaml]
----
name: R-CMD-check

  push:
    branches: [main]
  pull_request:

jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: r-lib/actions/setup-r@v2
        with:
          use-public-rspm: true
      - uses: r-lib/actions/setup-r-dependencies@v2
        with:
          extra-packages: any::rcmdcheck
          needs: check
      - uses: r-lib/actions/check-r-package@v2

  coverage:
    runs-on: ubuntu-latest
    env:
      CODECOV_TOKEN: ${{ secrets.CODECOV_TOKEN }}

      - uses: r-lib/actions/setup-r@v2

Two things in a workflow like this change what the tests see. Continuous-integration services set the environment variable `CI` (the documentation of `skip_on_ci()` names GitHub Actions among them), so `skip_on_ci()` tests skip, and a snapshot that has no stored file is a failure and not a warning (see <<snapshot-on-ci,Snapshots on CI>>), which is why the snapshot files must be committed. And whether the `skip_on_cran()` tests run in the `R CMD check` step depends on whether `NOT_CRAN` is set in the environment of the job, which the sections above showed to make the difference between `SKIP 2` and `SKIP 0`; read the skip summary in the log, and set `NOT_CRAN: true` in the `env` of the job when you want those tests to run. The workflow files themselves were not run here.


[[testable-code]]
== Writing code that is easy to test

A test is easy to write when the function under test takes what it needs as arguments and returns what it produces. It is hard to write when the function reads a file, asks for the current date, prints and returns nothing, all in one place. Most techniques of this page (fixtures, mocks, snapshots, skips) exist to cope with code of the second kind, and writing tests is a good way to push code towards the first kind. The `shelf` package follows this: `overdue_loans()` takes `today`, `loan_summary()` takes `today` and `loan_days`, `clean_books()` and `clean_loans()` take a data frame and return one, and the code that reads the clock is a one-line internal function.

The script shows the same report written both ways. The first version, `report_hard()`, reads a file and the clock and prints. The second is three functions: a pure function that counts the loans still out and the late ones from a data frame and a date, a function that formats the counts, and a thin shell that reads the file and prints. The tests then need no file and no clock for the first two, and use the fixed `shelf_today` of the scenario for the third:

[source,r]
----
library(testthat)
Sys.setenv(TESTTHAT_EDITION = "3")
set_reporter(StopReporter$new(praise = FALSE))
source("scenario.R")

# The one place that reads the clock.
current_date <- Sys.Date

# Hard to test: it reads a file, asks the clock and prints, all in one place.
report_hard <- function(path = "loans.csv") {
  loans <- read.csv(path, colClasses = "character")
  loans$loan_date <- as.Date(loans$loan_date, format = "%Y-%m-%d")
  out <- current_date() - loans$loan_date[is.na(loans$return_date)]
  cat("Still out:", length(out), "\n")
}

# Easier: a pure function that takes the date and the data as arguments...
count_out <- function(loans, today) {
  still_out <- loans[is.na(loans$return_date), ]
  c(
    out = nrow(still_out),
    late = sum(today - still_out$loan_date > 21L, na.rm = TRUE)
  )
}

# ...a function that only formats...
report_line <- function(counts) {
  sprintf("Still out: %d (%d late)", counts[["out"]], counts[["late"]])
}

# ...and a thin shell that does the input and the output.
report <- function(path = "loans.csv", today = current_date()) {
  loans <- read.csv(path, colClasses = "character")
  loans$loan_date <- as.Date(loans$loan_date, format = "%Y-%m-%d")
  loans$return_date <- as.Date(loans$return_date, format = "%Y-%m-%d")
  cat(report_line(count_out(loans, today)), "\n")
}

test_that("count_out() depends only on its arguments", {
  counts <- count_out(
    data.frame(
      loan_date = as.Date(c("2026-06-01", "2026-06-25", "2026-05-01")),
      return_date = as.Date(c(NA, NA, "2026-05-10"))
    ),
    today = shelf_today
  )
  expect_identical(counts, c(out = 2L, late = 1L))
})

test_that("report_line() formats the counts", {
  expect_identical(
    report_line(c(out = 7L, late = 5L)),
    "Still out: 7 (5 late)"
  )
})

test_that("report() works end to end with a fixed date", {
  expect_output(report(today = shelf_today), "Still out: 7 \\(\\d+ late\\)")
})
report(today = shelf_today)
#> Still out: 7 (7 late)
----

Source: https://testthat.r-lib.org/articles/test-fixtures.html[testthat package documentation: Test fixtures]

Notice what each test needs. `count_out()` is tested with a data frame of three rows written in the test, so the expected values (`out = 2L`, `late = 1L`) can be checked by reading the test. `report_line()` is a string function. Only the third test touches the file system and uses `expect_output()` with a regular expression, because the thin shell has little logic left. The last line prints the same report, `Still out: 7 (7 late)`, for the fixed date.

The habits that follow from this, in the order a reader would meet them:

* *Pass the date, the random seed, the paths and the options as arguments*, with defaults that read the real thing (`today = shelf_today()` in the package), as the test-fixtures article suggests when it says that making external state an explicit argument is often worthwhile because it shows which inputs determine the outputs.
* *Return values and let the caller print.* A function that returns a data frame can be tested with `expect_equal()` and `expect_named()`; one that only prints needs `expect_output()` or a snapshot.
* *Keep one idea in a function.* The tests in the `shelf` suite are short because `squish()`, `normalise_isbn()` and `is_valid_isbn13()` are separate functions that can be tested alone.
* *Test the edges, not only the middle.* `is_valid_isbn13()` has a specification for a wrong check digit, a short string, an empty string, `NA` and a vector of length zero; the loan tests have an impossible date and an early return. The data of the scenario already contain the awkward cases on purpose.
* *When you find a bug, write the test that fails first*, then fix it. The test stays as a record. The failure reported in the section on reading a failure (`clean_books()` of a partial catalogue) is exactly that kind of finding.
* *Test behaviour, not implementation.* A test that fixes the exact text of an error message or the exact layout of a print method breaks when those change for good reasons; test the `class` of the condition where there is one, and use a snapshot, whose diff a human reads, for text that is meant to be read.
* *Do not test R, or other people's packages.* `expect_equal(sum(1:3), 6L)` tests nothing in your package.
* *Let the file layout help.* Name the tests of `R/loans.R` `tests/testthat/test-loans.R`; `usethis::use_test()` (whose template is shown with the layout of the `tests` directory) creates the file with that name for the active source file, and `devtools::test_active_file()` runs the test file that goes with the open source file.

The layout of a test suite is also documentation. A new contributor reads the descriptions of the tests as a list of what the code is supposed to do, which is a reason to write them as the sentence "test that ...". The failure reports then read as sentences too: `+Failure ('test-failing.R:3:3'): overdue_loans() finds 31 late loans+`.

[[pitfalls]]
== Pitfalls

The pitfalls below are collected from what the experiments of this page showed. Each is followed by the cure.

* *Testing with `expect_true(a == b)`.* When it fails the report says that `a == b` is not `TRUE` and nothing else. `expect_equal(a, b)` and `expect_identical(a, b)` show both values and the difference. The rule for choosing is that values built by floating-point arithmetic go to `expect_equal()` and exact things (strings, integers, names, classes) go to `expect_identical()`. R FAQ 7.31 explains why `0.1 + 0.2` is not `0.3` to the last bit; `1L` and `1` differ for `expect_identical()` and not for `expect_equal()`.
* *A regular expression where a literal was meant.* `expect_error(f(), "is.character(title) is not TRUE")` treats the parentheses and the dots as regular-expression syntax; add `fixed = TRUE` (as the `shelf` test does) or match on `class =`. Matching on the text of a message also makes the test fragile: the message of an error raised by R or by another package can change between versions and is translated in other languages, and Writing R Extensions advises against testing it.
* *Expecting `expect_error()` to report that the pattern differed.* In the third edition an error that does not match escapes `expect_error()` and the test reports the original error, with its backtrace (the third failure of the failing-file experiment).
* *A test that depends on the clock, the locale, the time zone, the working directory, the network or a random number.* These differ between your laptop and the check machine, which is why the test passes in one and fails in the other. Pass the value in (`today = shelf_fixed_today`), replace the source with a mock (`shelf_today()`), fix the state with `withr::local_envvar()`, `withr::local_timezone()` or `withr::with_seed()`, and let the third edition make the output reproducible. Tests that use random numbers need a seed in any case, because R CMD check runs them in a vanilla session without one.
* *State that leaks from one test into the next.* An option set with `options()`, an environment variable, a changed working directory or a file written to the package directory makes the next test, or the next run, depend on this one. Use `+withr::local_*()+` and `withr::defer()`, write only to `tempdir()` (CRAN Repository Policy: a package should not write in the user's home filespace, nor anywhere else on the file system apart from the session's temporary directory, and such usage should be cleaned up), and use `set_state_inspector()` to find the culprit.
* *Tests that Writing R Extensions lists as bad practice.* It names tests of the time a command takes (you cannot know how fast or how loaded the platform is; at best a ratio of times, and even that is not advisable), tests of the exact format of R messages (they change and are translated), tests for the absence of warnings (later versions of R or of other packages can add warnings), comparisons of file paths without canonicalising them (`normalizePath()`), and numerical tests with no tolerance (only test accuracy after a formal error analysis, and always with a tolerance).
* *Test files that depend on each other.* They run in alphabetical order in a serial run, and in an order that depends on which worker is free in a parallel one. Run them with `shuffle = TRUE` (random order of the top-level expressions in a file) and in parallel now and then to find out.
* *Reading a green check as proof when tests were skipped.* `SKIP 2` in a check log is two tests that did not run. Look at the skip summary, run the check once with `NOT_CRAN=true`, and keep `skip_on_cran()` for tests that are slow or depend on a service, not for tests that are inconvenient.
* *Snapshots accepted without reading.* `snapshot_accept()` makes the new output the truth. Read the diff first. Snapshot only what a human is the judge of, keep the code in a snapshot small, use `transform` to remove paths, times and versions, and do not snapshot text that other packages or R itself produce (the messages of R change between versions and are translated). Commit `tests/testthat/_snaps/`, or the tests fail on CI.
* *Relying on a snapshot on CRAN.* The snapshot expectations return without checking on CRAN (`cran = FALSE`), so any behaviour that is checked only by a snapshot is unchecked there. Keep an ordinary expectation for what must hold.
* *Expecting `devtools::test()` to fail a script.* It returns normally when tests fail (`stop_on_failure = FALSE`). For an exit status, use `devtools::test(stop_on_failure = TRUE)`, `testthat::test_local()` or `R CMD check`; `test_check()` raises an error, and so does `test_dir()` by default.
* *A `test_that()` block with no expectation.* It is reported as a skipped test, `empty test`, not as a passing one.
* *Setup that works in `test_check()` but not in `load_all()`.* Setup files are not sourced by `devtools::load_all()`. Put what a debugging session needs in a helper file or in the test, and keep the setup file small.
* *Using `Sys.setenv()` or `options()` in a test file at the top level, outside a test.* The change lasts to the end of the process, not the end of the file, and in parallel runs it persists in the worker. Use `+withr::local_*()+` at the top of the file (it lasts to the end of the file) or inside the test.
* *Forgetting that internal functions are visible in tests.* Tests run in an environment whose parent is the package namespace, so `shelf_today()` is visible without `:::`; the same function from a script outside the package needs `shelf:::shelf_today()`. Test the exported behaviour first, and write tests of internals only for the logic that needs them.
* *A package used in tests but not declared.* Tests that call `library(somepackage)` or `somepackage::fun()` for a package missing from `DESCRIPTION` fail the check (`checking for unstated dependencies in ‘tests’`), and tests that use a suggested package must be skipped when it is missing. Since testthat 3.3.0 `test_that()` does the latter on CRAN by itself.
* *Printing noise.* A test that prints is hard to read in a log. Use `expect_output()`, `capture.output()` or a snapshot, and note that the output of `print()`, `cat()` and `message()` is lost in parallel runs.

== Where older tutorials differ

Many tutorials on testing in R were written for testthat 1.x or 2.x, or for a package workflow of the Travis CI era. They are not wrong about the principle, but several of the functions in them now warn or no longer exist.

[cols="3,4,3",options="header"]
|===
|Older material says |Now |See
|`context("name")` at the top of each test file |The file name is the context; `context()` is deprecated in the third edition |<<third-edition,The third edition>>
|`expect_is(x, "class")` |`expect_type()`, `expect_s3_class()`, `expect_s4_class()`, `expect_s7_class()`, `expect_r6_class()` |<<expectations,A first test>>
|`expect_equivalent(x, y)` |`expect_equal(x, y, ignore_attr = TRUE)` |<<third-edition,The third edition>>
|`expect_that(x, equals(y))` and `is_true()` |Plain expectations such as `expect_equal()`; the old syntax is deprecated and `is_true()`/`is_false()` were removed |<<third-edition,The third edition>>
|`expect_error(code, NA)` to assert that nothing is signalled |`expect_no_error()` and the other `+expect_no_*()+` forms |<<expectations,A first test>>
|`expect_warning(code, "text", all = TRUE)` |The `all` argument is deprecated; a third-edition expectation captures one condition, so add one expectation for each |<<third-edition,The third edition>>
|`expect_known_value()`, `expect_known_output()`, `expect_equal_to_reference()` with files in the tests directory |`expect_snapshot()` and `expect_snapshot_value()`, with the stored results in `+_snaps/+` |<<snapshots,Snapshot tests>>
|`setup()` and `teardown()` in a test file, or `+teardown-*.R+` |`withr::defer()` with `teardown_env()` in a setup file, and `+withr::local_*()+` in the test |<<fixtures,Fixtures and withr>>
|`with_mock()` and `local_mock()` |`local_mocked_bindings()` and `with_mocked_bindings()`; the old functions are defunct since 3.3.0 |<<mocking,Mocking>>
|Tests stored in `inst/tests` |`tests/testthat/`; the old location has not been supported since testthat 3.0.0 |<<the-tests-directory,The layout of the tests directory>>
|Silent messages in tests |Messages bubble up in the third edition; use `suppressMessages()` or `expect_message()` |<<third-edition,The third edition>>
|`skip_on_travis()` and `skip_on_appveyor()` for hosted CI |`skip_on_ci()`, which looks at the `CI` variable that most services set (the two older functions still exist in testthat 3.3.2) |<<skipping,Skipping tests>>
|Coverage with `testCoverage` or the `R-coverage` scripts |covr; the covr page lists both older tools as no longer supported |<<coverage,Test coverage with covr>>
|`usethis::use_testthat()` without an edition |`usethis::use_testthat(3)` records `Config/testthat/edition: 3` |<<the-tests-directory,The layout of the tests directory>>
|The `RUnit` package for unit tests |Still possible (tinytest's `+check*+` functions were made for migrating from it), but testthat and tinytest are the frameworks this page covers |<<tinytest,tinytest in brief>>
|===

Source: https://testthat.r-lib.org/articles/third-edition.html[testthat package documentation: testthat 3e]

== Where to go next

The package that the tests belong to is built step by step in xref:programming-languages/r/creating-packages.adoc[Creating Packages], and its help pages and vignette in xref:programming-languages/r/documentation-with-rd-roxygen2-and-vignettes.adoc[Documentation with Rd, roxygen2 and Vignettes]. The next steps of the same workflow are xref:programming-languages/r/style-linting-and-static-analysis.adoc[Style, Linting and Static Analysis], which checks the tests as it checks the code, and xref:programming-languages/r/publishing-to-cran.adoc[Publishing to CRAN], which runs the checks that decide whether a package is accepted. For the conditions that tests catch, read xref:programming-languages/r/conditions-and-error-handling.adoc[Conditions and Error Handling] and xref:programming-languages/r/defensive-programming-and-input-validation.adoc[Defensive Programming and Input Validation]; for finding out why a test fails, xref:programming-languages/r/debugging.adoc[Debugging]. A script that is run from the command line is tested differently from a package, with its exit status as the thing to check: xref:programming-languages/r/scripts-and-the-command-line.adoc[Scripts and the Command Line] and, in the section on command-line tools for coding agents, xref:ai/cli-for-agents/testing-clis.adoc[Testing CLIs]. The package side of the same topics is in xref:programming-languages/r/packages-libraries-and-namespaces.adoc[Packages, Libraries and Namespaces] (what a namespace is) and xref:programming-languages/r/s3-classes-and-generics.adoc[S3 Classes and Generics] (the `book` class that the tests exercise). The community book _R Packages_ (second edition) has the chapters Testing basics, Designing your test suite and Advanced testing techniques; the testthat package website has the reference and the articles listed in the references below.
