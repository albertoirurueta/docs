== Why talk to a database from R

R Data Import/Export gives the reasons in the first section of its chapter on relational databases (https://cran.r-project.org/doc/manuals/r-release/R-data.html#Why-use-a-database_003f[R Data Import/Export: Why use a database?]). Everything R manipulates is resident in memory, and several copies of the data can exist during a function call, so data objects of more than a few hundred megabytes can make R run out of memory. R does not easily support concurrent access: if several users read and update the same data, the changes of one are not visible to the others. R can store data between sessions, but in a format that is specific to R. A relational database management system is designed to do all of these things well: fast access to selected parts of large tables, summaries and cross-tabulations computed where the data is, a more organised way to store data than a rectangular grid, and concurrent access from many clients with security constraints. The manual's examples of the statistical use of a database are to extract a 10% sample, to cross-tabulate into a multi-dimensional table, and to extract the data group by group for separate analysis.

The pattern that follows from this is to push the work that the database is good at (filtering, joining, aggregating) into the query, and to bring only the result into R. The rest of this page is the machinery for doing that safely. For data that fit in memory and live in files, the routes are in xref:programming-languages/r/reading-and-writing-text-data.adoc[Reading and Writing Text Data] and xref:programming-languages/r/serialization-rds-rdata-and-json.adoc[Serialization: RDS, RData and JSON]; for data that arrive over the network, in xref:programming-languages/r/http-and-web-apis.adoc[HTTP and Web APIs].

The manual's overview of relational databases also states two points that matter for every query below (https://cran.r-project.org/doc/manuals/r-release/R-data.html#SQL-queries[R Data Import/Export: SQL queries]). The more comprehensive R interfaces generate SQL behind the scenes for common operations, but direct use of SQL is needed for complex operations in all of them. And, unlike the rows of a data frame, the rows of a table are best thought of as unordered: without an `ORDER BY`, the order of the result is indeterminate. A script that depends on the order of rows must say so in the query.

== DBI: one interface, many backends

DBI stands for DataBase Interface. Its home page says that the package separates the connection to the database management system into a front-end and a back-end: DBI defines the interface, and packages such as RPostgres, RMariaDB, RSQLite and odbc implement it for a particular system (https://dbi.r-dbi.org/[DBI package documentation: DBI]). The interface is similar in spirit to the database interfaces of Perl, Java, Python and Microsoft ODBC: connect and disconnect, create and execute statements, extract results, handle errors, ask for metadata, and manage transactions. The R Data Import/Export manual describes the same split as a proposal for a unified front-end package with a back-end per system (https://cran.r-project.org/doc/manuals/r-release/R-data.html#R-interface-packages[R Data Import/Export: R interface packages]); that proposal is now the way R talks to databases.

In R terms DBI is a set of S4 generics and a handful of virtual S4 classes. A generic such as `dbGetQuery()` is defined once, in DBI. Each backend package defines classes that extend DBI's (`SQLiteConnection` extends `DBIConnection`) and writes methods for them. When you call `dbGetQuery(con, sql)`, S4 dispatch looks at the class of `con`, finds the method of the backend that created it, and runs that. The diagram shows the layers, with dbplyr above DBI.

The class names in the diagram are the ones the backends' own documentation uses (for example the DBI page of `dbBind()` lists the methods `RSQLite::dbBind("SQLiteResult")`, `RPostgres::dbBind("PqResult")`, `RMariaDB::dbBind("MariaDBResult")`, `odbc::dbBind("OdbcResult")` and `duckdb::dbBind("duckdb_result")` (https://dbi.r-dbi.org/reference/dbBind.html[DBI package documentation: dbBind])). Three kinds of object take part, and every DBI backend has all three:

* a driver (`DBIDriver`), made by a constructor such as `RSQLite::SQLite()`, that knows how to open connections;
* a connection (`DBIConnection`), returned by `dbConnect()`, that you pass to nearly every other function and must close;
* a result (`DBIResult`), returned by `dbSendQuery()` and `dbSendStatement()`, that stands for one query in progress, from which rows are fetched, and that must be cleared.

The DBI home page names RPostgres, RMariaDB, RSQLite and odbc among the backends and says that odbc is for databases that you can access via ODBC. The specification that every backend implements is the DBI specification (https://dbi.r-dbi.org/articles/spec.html[DBI package documentation: DBI specification]); that is why the code in the rest of this page, written against SQLite, changes only in the line that creates the connection when the database changes. What does not carry over is the SQL itself, which has dialects, and a few details that the specification leaves to the backend; those are called out where they appear (the format of the parameter placeholders, the column types, the date support).

The first script asks R itself how the layers are arranged. `is()` lists the classes of an object from the most specific to the most general; `showMethods()` lists the S4 methods that exist for a generic.

[source,r]
----
library(DBI)

drv <- RSQLite::SQLite()
con <- dbConnect(drv, ":memory:")

# RSQLite's classes extend the base classes that DBI defines.
is(drv)
#> [1] "SQLiteDriver" "DBIDriver"    "DBIObject"
is(con)
#> [1] "SQLiteConnection" "DBIConnection"    "DBIObject"
extends("SQLiteResult", "DBIResult")
#> [1] TRUE
isVirtualClass("DBIConnection")
#> [1] TRUE

# dbListTables() is a DBI generic; RSQLite wrote the method for its class.
isGeneric("dbListTables")
#> [1] TRUE
showMethods("dbListTables", classes = "SQLiteConnection")
#> Function: dbListTables (package DBI)
#> conn="SQLiteConnection"
#>

# dbGetQuery() has one method for every DBIConnection: it calls
# dbSendQuery(), dbFetch() and dbClearResult() for you.
showMethods("dbGetQuery", classes = c("SQLiteConnection", "character"))
#> Function: dbGetQuery (package DBI)
#> conn="DBIConnection", statement="character"
#>

dbDisconnect(con)
----

Source: https://search.r-project.org/R/refmans/methods/html/showMethods.html[R documentation: showMethods]

The driver and the connection each have the backend class first and the DBI class after it, and both end in `DBIObject`, the root of the hierarchy. `dbListTables()` has a method written for the backend's own class, `SQLiteConnection`. `dbGetQuery()` is the other case: the method that `showMethods()` lists is the one defined for any `DBIConnection`, which a `SQLiteConnection` inherits, because the definition is the same for every backend. The DBI article on advanced usage describes what it does: `dbGetQuery()` works by calling `dbSendQuery()`, `dbFetch()` and `dbClearResult()` behind the scenes (https://dbi.r-dbi.org/articles/DBI-advanced.html[DBI package documentation: Advanced DBI usage]). Those three are what you call yourself when you want to read a result in pieces, as in the section on chunked reads below. In DBI 1.3.0 many of these generics are of the kind `"nonstandardGeneric"`, a change its NEWS lists among the breaking changes because a package that tests the generic's definition could notice; ordinary users do not.

== Connecting and disconnecting

=== A database in memory

`dbConnect()` is the first call of every session. Its first argument is the driver object; the remaining arguments are the backend's. For SQLite the one that matters is `dbname`, the file that holds the database, or the special name `":memory:"` for a database that lives in RAM and disappears when the connection is closed (https://rsqlite.r-dbi.org/reference/SQLite.html[RSQLite package documentation: SQLite]). That makes it the right database for experiments, tests and the examples on this page.

[source,r]
----
library(DBI)

con <- dbConnect(RSQLite::SQLite(), ":memory:")
con
#> <SQLiteConnection>
#>   Path: :memory:
#>   Extensions: TRUE
dbIsValid(con)
#> [1] TRUE
dbListTables(con)
#> character(0)

dbDisconnect(con)
dbIsValid(con)
#> [1] FALSE
con
#> <SQLiteConnection>
#>   DISCONNECTED

# A closed connection cannot be used again.
tryCatch(dbListTables(con), error = \(e) conditionMessage(e))
#> [1] "Invalid or closed connection"

# Close the connection even when the code in between fails.
with_shelf_db <- function(dbname, fun) {
  con <- dbConnect(RSQLite::SQLite(), dbname)
  on.exit(dbDisconnect(con), add = TRUE)
  fun(con)
}

kept <- NULL
result <- tryCatch(
  with_shelf_db(":memory:", \(con) {
    kept <<- con
    stop("something went wrong")
  }),
  error = \(e) conditionMessage(e)
)
result
#> [1] "something went wrong"
dbIsValid(kept)
#> [1] FALSE

# A connection cannot be saved: after a round trip through a file it is dead.
con <- dbConnect(RSQLite::SQLite(), ":memory:")
path <- tempfile(fileext = ".rds")
saveRDS(con, path)
restored <- readRDS(path)
dbIsValid(restored)
#> [1] FALSE
tryCatch(dbListTables(restored), error = \(e) conditionMessage(e))
#> [1] "bad_weak_ptr"
dbDisconnect(con)
unlink(path)
----

Source: https://dbi.r-dbi.org/reference/dbConnect.html[DBI package documentation: dbConnect]

The print method of a connection says what it is connected to: `<SQLiteConnection>`, the `Path`, and whether loadable `Extensions` are enabled (they are by default). It never prints a memory address, so a connection can be shown in a log. After `dbDisconnect()`, `dbIsValid()` is `FALSE`, the object prints as `DISCONNECTED`, and any function that needs the connection fails with `Invalid or closed connection`. Calling the functions on a closed connection is a programming error and not a recoverable condition, which is why the function `with_shelf_db()` at the end of the script opens the connection, registers the closing with `on.exit()` and only then runs the code it was given. The code fails with an error, the connection is closed anyway, and `dbIsValid(kept)` confirms it. The last block of the script shows that a connection is not a value that can be stored: after `saveRDS()` and `readRDS()` the restored object is not valid (`dbIsValid()` is `FALSE`) and using it fails with the unhelpful `bad_weak_ptr`, because the connection lives in memory that belongs to the session. Open a new connection in each session. `add = TRUE` keeps any other `on.exit()` handler of the function (https://search.r-project.org/R/refmans/base/html/on.exit.html[R documentation: on.exit]).

Closing is not optional. RSQLite's documentation notes that connections are cleaned up automatically after they are deleted and the garbage collector reclaims them, but that `dbDisconnect()` terminates a connection early, and that it will not actually close until all open result sets have been closed (a warning says so; see the section on chunked reads). The RPostgres documentation puts it the same way: manually disconnecting is not necessary, but still recommended, and deleting the object that holds a connection disconnects it at the next garbage collection with a warning (https://rpostgres.r-dbi.org/reference/Postgres.html[RPostgres package documentation: Postgres]). For a server database each forgotten connection is also a session the server keeps open until it times out.

Disconnecting is documented on its own page (https://dbi.r-dbi.org/reference/dbDisconnect.html[DBI package documentation: dbDisconnect]).

=== A database in a file

A file name as `dbname` makes a database that survives the session, can be opened by another R session or program, and is created if it does not exist. The next script uses a file from `tempfile()`, writes the `books` table to it, closes the connection, opens the file again, and removes it at the end. It also shows the read-only flag, and `dbCanConnect()`, which answers `TRUE` or `FALSE` instead of signalling an error.

[source,r]
----
source("scenario.R")
library(DBI)

path <- tempfile(fileext = ".sqlite")
file.exists(path)
#> [1] FALSE

con <- dbConnect(RSQLite::SQLite(), path)
dbWriteTable(con, "books", books, row.names = FALSE)
dbDisconnect(con)
file.exists(path)
#> [1] TRUE

# A second connection, even from another R session, sees the same data.
con <- dbConnect(RSQLite::SQLite(), path)
dbListTables(con)
#> [1] "books"
dbGetQuery(con, "SELECT COUNT(*) AS n FROM books")
#>    n
#> 1 16
dbDisconnect(con)

# SQLITE_RO opens the file read-only.
ro <- dbConnect(RSQLite::SQLite(), path, flags = RSQLite::SQLITE_RO)
tryCatch(
  dbExecute(ro, "DELETE FROM books"),
  error = \(e) conditionMessage(e)
)
#> [1] "attempt to write a readonly database"
dbDisconnect(ro)

# dbCanConnect() answers TRUE or FALSE instead of failing.
isTRUE(dbCanConnect(RSQLite::SQLite(), path))
#> [1] TRUE
missing_path <- tempfile(fileext = ".sqlite")
isTRUE(dbCanConnect(
  RSQLite::SQLite(), missing_path,
  flags = RSQLite::SQLITE_RO
))
#> [1] FALSE

unlink(path)
file.exists(path)
#> [1] FALSE
----

Source: https://rsqlite.r-dbi.org/reference/SQLite.html[RSQLite package documentation: SQLite]

The arguments of `dbConnect()` for an SQLite driver, as documented in version 3.53.3, are these.

[cols="2,5",options="header"]
|===
|Argument |Meaning
|`dbname` |The database file. `":memory:"` or `"file::memory:"` makes a temporary in-memory database; `""` makes a temporary on-disk database whose file is deleted when the connection is closed.
|`flags` |`SQLITE_RWC` (the default) opens read/write and creates the file if it does not exist; `SQLITE_RW` opens read/write and fails if the file does not exist; `SQLITE_RO` opens read-only.
|`extended_types` |`FALSE` by default. When `TRUE`, columns declared `DATE`, `TIME` or `DATETIME`/`TIMESTAMP` are returned as `Date`, `hms` and `POSIXct` (see the section on types).

|`synchronous` |`"off"` (the default), `"normal"` or `"full"`. The documentation calls it an advanced option: `"off"` is faster, at the very modest risk of database corruption if the operating system itself crashes.

The read-only connection in the script gets the error text of SQLite itself, `attempt to write a readonly database`. `dbCanConnect()` is the DBI generic added in DBI 1.0.0 for checking, before a long job, that the settings work. Because a file database is shared, a second connection (or a second R process) can read it while the first one is open; what happens when two of them write at once is up to SQLite's locking, which RSQLite documents under its own functions (its NEWS for 2.2.4 introduces `sqliteSetBusyHandler()` to configure what SQLite does when the database is locked), and one reason to prefer a server database when many users write.

=== Other databases

A server database needs more than a file name: where it is, which database on it, and who you are. The argument names differ by backend, as the references of RPostgres (`dbname`, `host`, `port`, `user`, `password`), RMariaDB (`dbname`, `host`, `username`, `password`), odbc (`dsn`, or `driver`, `server`, `database`, `uid`, `pwd`) and duckdb (`dbdir`, `read_only`) show. The fragment below is the shape of those calls, with every setting read from the environment (the next section explains why). It is a fragment that was only linted: the four packages are not installed here and no database server is available, so it was never run.

[source,r]
----
# Fragment, never run: RPostgres, RMariaDB, odbc and duckdb are not installed
# here, and no database server is available. The settings come from the
# environment, not from the code.
library(DBI)

connect_shelf_postgres <- function() {
  dbConnect(
    RPostgres::Postgres(),
    dbname = Sys.getenv("SHELF_DB_NAME"),
    host = Sys.getenv("SHELF_DB_HOST"),
    user = Sys.getenv("SHELF_DB_USER"),
    password = Sys.getenv("SHELF_DB_PASSWORD")
  )
}

connect_shelf_mariadb <- function() {
  dbConnect(
    RMariaDB::MariaDB(),
    dbname = Sys.getenv("SHELF_DB_NAME"),
    host = Sys.getenv("SHELF_DB_HOST"),
    username = Sys.getenv("SHELF_DB_USER"),
    password = Sys.getenv("SHELF_DB_PASSWORD")
  )
}

connect_shelf_odbc <- function() {
  dbConnect(
    odbc::odbc(),
    dsn = Sys.getenv("SHELF_DB_DSN"),
    uid = Sys.getenv("SHELF_DB_USER"),
    pwd = Sys.getenv("SHELF_DB_PASSWORD")
  )
}

connect_shelf_duckdb <- function() {
  dbConnect(duckdb::duckdb())
}

# The rest of the code does not change with the backend.
count_loans <- function(connect) {
  con <- connect()
  on.exit(dbDisconnect(con), add = TRUE)
  dbGetQuery(con, "SELECT COUNT(*) AS n FROM loans")$n
}
----

Source: https://rpostgres.r-dbi.org/reference/Postgres.html[RPostgres package documentation: Postgres]

The last function, `count_loans()`, is the point of the fragment: it takes the function that makes the connection and does not care which database it reaches. The other documentation pages for the arguments used above are https://rmariadb.r-dbi.org/reference/dbConnect-MariaDBDriver-method.html[RMariaDB package documentation: dbConnect], https://odbc.r-dbi.org/reference/dbConnect-OdbcDriver-method.html[odbc package documentation: dbConnect] and https://r.duckdb.org/reference/duckdb.html[duckdb package documentation: duckdb]. DuckDB, like SQLite, is embedded in the R package; its `dbdir` argument defaults to a database kept in RAM.

== Credentials stay out of the code

A password written in a script ends up in version control, in a shared project folder, in a screenshot of the editor and in the history of every machine the script was copied to. The DBI introduction makes the same point about its own example, which has a password in the code: that should be avoided for databases with secured access, and one way is to keep the credential in the system's credential store and query it with the keyring package (https://dbi.r-dbi.org/articles/DBI.html[DBI package documentation: Introduction to DBI]). The rules for this page and for any script that connects to a real server are:

* Read every connection setting that differs between machines (host, database name, user, password) with `Sys.getenv()`, never from a literal in the script. The values live in environment variables, set by the environment that runs the script (a shell profile, a deployment secret store, a CI secret) or by a `.Renviron` file.
* A `.Renviron` file holds `NAME=value` lines that R turns into environment variables when it starts. R looks for it in the current directory first and then in the user's home directory, unless the variable `R_ENVIRON_USER` names another file (https://search.r-project.org/R/refmans/base/html/Startup.html[R documentation: Startup]). A project-level `.Renviron` holds the names of the settings, and the file must be excluded from version control (listed in `.gitignore`). `readRenviron()` loads a file into a running session. How R reads startup files is the subject of xref:programming-languages/r/sessions-workspaces-and-startup.adoc[Sessions, Workspaces and Startup].
* Some backends read the usual environment variables of their database themselves. RPostgres documents that `host` and `port` default to the `PGHOST` and `PGPORT` variables, and `user` and `password` to `PGUSER` and `PGPASSWORD` or to the matching line of the `+~/.pgpass+` file. RMariaDB can read authentication parameters from a section of a MariaDB option file (`default.file` and `group`), and odbc can take the connection from a data source name (`dsn`) configured outside R and listed by `odbcListDataSources()`. In each case the secret is kept outside the R code.
* For interactive use, ask for the secret when it is needed instead of storing it: the askpass package prompts for a password, and keyring reads and writes the operating system's credential store (macOS Keychain, the Windows Credential Store, the Linux Secret Service). The config package returns the values for the current environment (development, test, production), which is useful as long as the secrets in the configuration are placeholders for environment variables. These three packages are named here from their CRAN descriptions and are not run.
* Make the script fail early and clearly when a setting is missing, and never print the value.

A template for the settings of the fragment above can live in the repository under another name (for example `.Renviron.example`) with the names and no secrets; each developer copies it to `.Renviron`, which is not committed, and fills in the values on their own machine:

[source,text]
----
SHELF_DB_NAME=shelf
SHELF_DB_HOST=db.example.com
SHELF_DB_USER=shelf_reader
SHELF_DB_PASSWORD=
----

Source: https://search.r-project.org/R/refmans/base/html/Startup.html[R documentation: Startup]

The host `db.example.com` is a placeholder, not a real server. The next script is the helper that goes with it. Nothing sets `SHELF_DB_PASSWORD` in this session, so the helper stops with a message that names the variable and shows no value, and it shows what `Sys.getenv()` returns for a variable that is not set.

[source,r]
----
# Read connection settings from environment variables; never from the code.
db_setting <- function(name) {
  value <- Sys.getenv(name)
  if (!nzchar(value)) {
    stop("environment variable ", name, " is not set", call. = FALSE)
  }
  value
}

# Nothing sets SHELF_DB_PASSWORD in this session, so the helper stops early
# with a message that names the variable but never shows a value.
tryCatch(db_setting("SHELF_DB_PASSWORD"), error = \(e) conditionMessage(e))
#> [1] "environment variable SHELF_DB_PASSWORD is not set"

# Sys.getenv() returns "" for an unset variable, or the value of unset =.
Sys.getenv("SHELF_DB_PASSWORD")
#> [1] ""
Sys.getenv("SHELF_DB_PASSWORD", unset = NA)
#> [1] NA

# A non-secret setting can be set for the session with Sys.setenv().
Sys.setenv(SHELF_DB_NAME = "shelf")
db_setting("SHELF_DB_NAME")
#> [1] "shelf"

----

Source: https://search.r-project.org/R/refmans/base/html/Sys.getenv.html[R documentation: Sys.getenv]

An unset variable is the empty string, not an error, which is why the helper tests it with `nzchar()`; with `unset = NA` the missing value is distinguishable from an empty one. `Sys.setenv()` changes the environment of the running R process and of the child processes it starts, and the change is gone when the session ends (https://search.r-project.org/R/refmans/base/html/Sys.setenv.html[R documentation: Sys.setenv]). Setting a variable that holds a real password with `Sys.setenv()` inside a script defeats the purpose, because the value is then in the script; the example sets only the non-secret database name.

== Tables: writing, listing, reading and removing

The functions that treat a whole table as a data frame are the shortest way in and out of a database, and the manual presents them as convenient interfaces to read, write, test and delete tables: `dbWriteTable()` copies a data frame into a table, `dbReadTable()` copies a table into a data frame, and `dbListTables()`, `dbListFields()`, `dbExistsTable()` and `dbRemoveTable()` look after the rest (https://cran.r-project.org/doc/manuals/r-release/R-data.html#DBI[R Data Import/Export: Packages using DBI]). The next script copies `books` into a database, writes to it again in the ways that fail and succeed, reads it back, and shows what happens to row names.

[source,r]
----
source("scenario.R")
library(DBI)

con <- dbConnect(RSQLite::SQLite(), ":memory:")

# Copy a data frame into the database as a table.
dbWriteTable(con, "books", books, row.names = FALSE)
dbListTables(con)
#> [1] "books"
dbListFields(con, "books")
#> [1] "title"  "author" "isbn"   "year"   "genre"  "pages"
dbExistsTable(con, "books")
#> [1] TRUE
dbExistsTable(con, "shelves")
#> [1] FALSE

# Writing to an existing table is an error unless you say what you mean.
tryCatch(
  dbWriteTable(con, "books", books, row.names = FALSE),
  error = \(e) conditionMessage(e)
)
#> [1] "Table books exists in database, and both overwrite and append are FALSE"
dbWriteTable(con, "books", books, row.names = FALSE, overwrite = TRUE)
dbWriteTable(con, "books", books[1:2, ], row.names = FALSE, append = TRUE)
dbGetQuery(con, "SELECT COUNT(*) AS n FROM books")
#>    n
#> 1 18

# Read it back: a plain data frame, with the same columns.
dbWriteTable(con, "books", books, row.names = FALSE, overwrite = TRUE)
back <- dbReadTable(con, "books")
class(back)
#> [1] "data.frame"
dim(back)
#> [1] 16  6
identical(names(back), names(books))
#> [1] TRUE
all.equal(back, books)
#> [1] TRUE

# Row names are dropped unless you ask for them.
named <- books[1:3, c("title", "year")]
rownames(named) <- c("b1", "b2", "b3")
dbWriteTable(con, "named", named)
dbListFields(con, "named")
#> [1] "title" "year"
dbWriteTable(con, "named", named, row.names = TRUE, overwrite = TRUE)
dbListFields(con, "named")
#> [1] "row_names" "title"     "year"
dbReadTable(con, "named", row.names = "row_names")
#>                   title year
#> b1     The Dispossessed 1974
#> b2  Pride and Prejudice 1813
#> b3   the quiet streets  2019

# Remove a table; removing a missing one is an error unless told otherwise.
dbRemoveTable(con, "named")
tryCatch(
  dbRemoveTable(con, "named"),
  error = \(e) conditionMessage(e)
)
#> [1] "no such table: named"
dbRemoveTable(con, "named", fail_if_missing = FALSE)

dbDisconnect(con)
----

Source: https://dbi.r-dbi.org/reference/dbWriteTable.html[DBI package documentation: dbWriteTable]

Three points in that output deserve a sentence each.

* A table that already exists is never silently replaced. `dbWriteTable()` stops with `Table books exists in database, and both overwrite and append are FALSE`. `overwrite = TRUE` replaces the table with the new data; `append = TRUE` adds the rows to the existing table, which is why the table had 18 rows after the second write. Do not pass both. In a script that must be safe to run twice, decide which of the two it means.
* `dbReadTable()` returns a plain data frame, and `all.equal()` finds no difference with the original `books`, including the `NA` values (SQL `NULL`). The rows of a table have no order of their own, so a script that needs the original order must store a key and sort by it.
* Row names are not written unless you ask. The script passes `row.names = FALSE` for `books`, and writing the data frame `named` without the argument produced only the columns `title` and `year`, because DBI's default is to leave row names out. `row.names = TRUE` adds a column called `row_names`, and `dbReadTable(row.names = "row_names")` turns it back into row names. The R Data Import/Export manual's example for the older RMySQL package (which maps row names to a `row_names` field) is where many tutorials get the habit of expecting them to be kept.

Table names are quoted for you: since RSQLite 1.1, functions that take a table name quote it with `dbQuoteIdentifier()`, so a name with a space or a reserved word is safe, and a name you quoted yourself has to be marked with `DBI::SQL()` to avoid being quoted twice (https://rsqlite.r-dbi.org/news/index.html[RSQLite package documentation: NEWS]).

=== Creating a table first

`dbWriteTable()` guesses the column types and writes the data in one call. When the table must have particular types, constraints or keys, create it with SQL (see xref:database/sql/ddl.adoc[SQL data definition]) or with `dbCreateTable()`, and then add rows with `dbAppendTable()`. Both are new generics of DBI 1.0.0 (2018-05-02), listed in its NEWS next to `dbCanConnect()` and `dbIsReadOnly()` (https://dbi.r-dbi.org/news/index.html[DBI package documentation: NEWS]).

[source,r]
----
library(DBI)

con <- dbConnect(RSQLite::SQLite(), ":memory:")

# dbCreateTable() makes an empty table from named column types ...
dbCreateTable(
  con, "members",
  c(member_id = "INTEGER", name = "TEXT", joined = "TEXT")
)
dbListFields(con, "members")
#> [1] "member_id" "name"      "joined"
dbReadTable(con, "members")
#> [1] member_id name      joined
#> <0 rows> (or 0-length row.names)

# ... and dbAppendTable() adds the rows of a data frame and returns the count.
new_members <- data.frame(
  member_id = 1:2,
  name = c("Ana Ruiz", "Ben Okafor"),
  joined = c("2024-01-05", "2024-02-11")
)
dbAppendTable(con, "members", new_members)
#> [1] 2
dbReadTable(con, "members")
#>   member_id       name     joined
#> 1         1   Ana Ruiz 2024-01-05
#> 2         2 Ben Okafor 2024-02-11

# The data frame's columns must exist in the table.
tryCatch(
  dbAppendTable(con, "members", data.frame(zzz = 1)),
  error = \(e) conditionMessage(e)
)
#> [1] "table members has no column named zzz"

# Table names can be a structured Id(), here with the schema SQLite calls main.
dbReadTable(con, Id(schema = "main", table = "members"))
#>   member_id       name     joined
#> 1         1   Ana Ruiz 2024-01-05
#> 2         2 Ben Okafor 2024-02-11

# dbListObjects() lists what the database contains, schemas included.
objects <- dbListObjects(con)
objects$is_prefix
#> [1] FALSE  TRUE
vapply(objects$table, \(id) id@name[[1L]], character(1))
#> [1] "members" "main"

dbDisconnect(con)
----

Source: https://dbi.r-dbi.org/reference/dbCreateTable.html[DBI package documentation: dbCreateTable]

`dbAppendTable()` returns the number of rows it added, and a data frame whose columns are not in the table is an error from SQLite (`table members has no column named zzz`). A table that lives in a schema other than the default is addressed with `Id()`: `Id(schema = "main", table = "members")` is the structured name that DBI, since version 0.8, quotes correctly for each backend, and `dbListObjects()` (which came with it) lists what is in the database, schemas included. SQLite calls its default schema `main` and the one for temporary tables `temp`; in the output of the script `is_prefix` is `TRUE` for `main`, which is a schema to look inside, and `FALSE` for the table `members`. The first RSQLite release with the version number aligned to SQLite (3.52.0) added `dbListObjects()` support for attached databases with a schema prefix (https://dbi.r-dbi.org/reference/dbListObjects.html[DBI package documentation: dbListObjects], https://dbi.r-dbi.org/reference/Id.html[DBI package documentation: Id]).

== Column types: from R classes to SQLite and back

The R Data Import/Export manual lists the types a DBMS commonly offers (floating point, integer, character and varying character, boolean, date, time, timestamp, text and blob) and says that the more comprehensive R interface packages hide the type conversion from the user (https://cran.r-project.org/doc/manuals/r-release/R-data.html#Overview-of-RDBMSs[R Data Import/Export: Overview of RDBMSs]). Hidden does not mean absent. SQLite has only a few storage classes and lets a column hold any of them, and the conversion has consequences for logical, date-time and factor columns. `dbDataType()` asks the backend which column type it would use for an R value; called on one column at a time it tells you what `dbWriteTable()` will declare.

[source,r]
----
source("scenario.R")
library(DBI)

con <- dbConnect(RSQLite::SQLite(), ":memory:")

samples <- data.frame(

  x = c(1.5, NA),
  label = c("a", NA),

  day = c(shelf_today, NA),
  genre = factor(c("fiction", "poetry"))

# The SQLite column type chosen for each R column.
vapply(samples, \(column) dbDataType(con, column), character(1))
#>         n         x     label      flag       day     genre
#> "INTEGER"    "REAL"    "TEXT" "INTEGER"    "REAL"    "TEXT"

# On the whole data frame the method reports DBI's generic names instead.
dbDataType(con, samples)
#>          n          x      label       flag        day      genre
#>      "INT"   "DOUBLE"     "TEXT" "SMALLINT"     "DATE"     "TEXT"

dbWriteTable(con, "samples", samples, row.names = FALSE)
back <- dbReadTable(con, "samples")

#> 'data.frame':	2 obs. of  6 variables:

What the output shows, as a table:

|===
|R column |SQLite column type declared |What `dbReadTable()` returns
|`integer` |`INTEGER` |`integer`
|`double` |`REAL` |`numeric`
|`character` |`TEXT` |`character`
|`logical` |`INTEGER` (`TRUE` is 1) |`integer`: the logical type is not restored

|`NA` of any type |`NULL` |`NA`

Source: https://rsqlite.r-dbi.org/reference/SQLite.html[RSQLite package documentation: SQLite]

Four consequences follow.

* A logical column comes back as 0, 1 and `NA`; convert with `as.logical()`. A factor comes back as text; rebuild the factor on the R side with `+factor(x, levels = ...)+` if the level order matters (see xref:programming-languages/r/factors.adoc[Factors]).
* A `Date` is stored as a number, and converting it back is up to you: `as.Date(x)` on the numbers works in R 4.3.0 and later, which accepts a numeric argument without `origin` (https://cran.r-project.org/doc/manuals/r-release/NEWS.html[R NEWS: Changes in R 4.3.0]); before it, `as.Date(x, origin = "1970-01-01")` was required. Worse, SQL date functions applied to such a column read the number as something else (SQLite's `julianday()` treats it as a Julian day number), which is why the analysis near the end of this page stores dates as ISO text.
* `extended_types = TRUE` (an argument of `dbConnect()` that appeared in RSQLite 2.2.3 and 2.2.4 and, from 2.2.6, also changes what `dbDataType()` and `dbWriteTable()` produce) is the fix. With it, columns declared `DATE`, `TIME` or `DATETIME`/`TIMESTAMP` come back as `Date`, `hms` and `POSIXct` in UTC; the script shows the `day` column declared `DATE` and returned as a `Date`. If a stored value cannot be mapped, an `NA` is returned with a warning. The RSQLite reference table says how the value is read: a numeric value is a count of days (for `DATE`) or seconds (for the other two) since 1970-01-01, and a text value must be in ISO format (`2020-01-23`, `12:34:56`, or both separated by a space).
* SQLite integers can be 64 bits wide. Values that do not fit an R integer come back as `bit64::integer64` by default, which keeps every digit, as the 16-digit example prints. The `bigint` argument of `dbConnect()` chooses another type; `"numeric"` is a plain double and, as the last line shows, rounds a value that needs more than 53 bits.

Calling `dbDataType()` on the whole data frame, as the script does once, is a trap in RSQLite 3.53.3: the data frame method reports generic type names (`INT`, `DOUBLE`, `SMALLINT`, `DATE` and `TIMESTAMP`, whatever the connection), while the columns that `dbWriteTable()` actually creates are the ones in the table above. Check a table's real declaration with `PRAGMA table_info(tablename)` or read one column at a time, as the script does.

== Running queries

=== dbGetQuery(): a SELECT, the whole result

`dbGetQuery()` sends a query, reads the whole result into a data frame, and releases the result. It is the function to use for a `SELECT` whose result fits in memory.

[source,r]
----
source("scenario.R")
library(DBI)

con <- dbConnect(RSQLite::SQLite(), ":memory:")
dbWriteTable(con, "books", books, row.names = FALSE)

# dbGetQuery() sends a SELECT and returns the whole result as a data frame.
dbGetQuery(con, "SELECT title, year FROM books WHERE year > 2015 ORDER BY year")
#>                  title year
#> 1      Midnight Ledger 2016
#> 2     Notes on Gravity 2017
#> 3      Salt and Static 2018
#> 4   the quiet streets  2019
#> 5        Orchard Logic 2020
#> 6           Loud Roofs 2021
#> 7          Ten Winters 2022
#> 8       THE LONG TABLE 2023

# No rows still gives a data frame with the right columns.
str(dbGetQuery(con, "SELECT title, year FROM books WHERE year > 3000"))
#> 'data.frame':	0 obs. of  2 variables:
#>  $ title: chr
#>  $ year : int

# SQL NULL becomes NA; COUNT(column) does not count the NULLs.
dbGetQuery(con, "SELECT COUNT(*) AS n, COUNT(pages) AS with_pages FROM books")
#>    n with_pages
#> 1 16         14

# n = limits the number of rows fetched.
dbGetQuery(con, "SELECT title FROM books ORDER BY title", n = 3)
#>                   title
#> 1    the quiet streets
#> 2         A Map of Salt
#> 3 Garden of Small Fires

# dbExecute() runs a statement that changes data and returns the row count.
dbExecute(con, "UPDATE books SET genre = LOWER(TRIM(genre))")
#> [1] 16
dbExecute(con, "DELETE FROM books WHERE year IS NULL")
#> [1] 1
dbExecute(con, "CREATE INDEX books_genre ON books (genre)")
#> [1] 0
dbGetQuery(con, "SELECT genre, COUNT(*) AS n FROM books GROUP BY genre")
#>             genre n
#> 1         classic 2
#> 2         fiction 4
#> 3         mystery 2
#> 4     non-fiction 3
#> 5          poetry 1
#> 6 science fiction 3

# A SELECT sent through dbExecute() changes nothing.
dbExecute(con, "SELECT 1")
#> [1] 0

# Only the first statement of a multi-statement string runs.
tryCatch(
  dbGetQuery(con, "SELECT 1 AS a; SELECT 2 AS a"),
  warning = \(w) conditionMessage(w)
)
#> [1] "Ignoring remaining part of query: SELECT 2 AS a"

dbDisconnect(con)
----

Source: https://dbi.r-dbi.org/reference/dbGetQuery.html[DBI package documentation: dbGetQuery]

SQL `NULL` is `NA`, and `COUNT(pages)` counts only the rows where `pages` is not null: 14 of 16, for the two missing page counts of the scenario. A query with no rows still gives a data frame with the columns and their types, so code that does `nrow(result) == 0` needs no special case. The argument `n` limits the rows fetched; when a query has no `ORDER BY`, which rows those are is up to the database.

=== dbExecute(): statements that change data

`UPDATE`, `DELETE`, `INSERT` and the statements that define tables return no rows. `dbExecute()` sends one and returns the number of rows it affected, which is the thing to check: `0` rows deleted is the usual sign of a `WHERE` that matches nothing. `dbExecute()` and `dbSendStatement()` are the DBI 0.5 names for work that older code did with `dbGetQuery()` and `dbSendQuery()`; RSQLite's NEWS says new code should use them where appropriate. In the output above, `UPDATE` reported 16 rows, `DELETE` 1 row (the book without a year) and `CREATE INDEX` 0. Sending a `SELECT` through `dbExecute()` is not an error; it returns `0`.

SQLite runs one statement per call. If the string holds two, RSQLite runs the first and warns `Ignoring remaining part of query: SELECT 2 AS a`. That is a property of this backend and a useful accident against stacked-statement tricks, but not a defence (see the section on parameters, and the contrast in the older tutorials section); other backends may run all the statements. The function is documented in https://dbi.r-dbi.org/reference/dbExecute.html[DBI package documentation: dbExecute].

=== Reading a result in chunks

When a result is too big to read at once, or when only the first rows are needed, take the three steps that `dbGetQuery()` performs by itself, and keep control of the middle one: `dbSendQuery()` sends the query and returns a result object, `dbFetch(res, n =)` fetches up to `n` rows from it (all the remaining ones if `n` is omitted or `-1`), and `dbClearResult()` releases it. `dbHasCompleted()` says whether all the rows have been fetched, `dbGetRowCount()` how many were fetched so far, and `dbColumnInfo()` what the columns are. The DBI article on advanced usage gives the loop on this pattern: fetch chunk by chunk while `dbHasCompleted()` is false.

[source,r]
----
source("scenario.R")
library(DBI)

con <- dbConnect(RSQLite::SQLite(), ":memory:")
dbWriteTable(con, "loans", loans, row.names = FALSE)

# dbSendQuery() starts the query; dbFetch(n =) pulls rows a chunk at a time.
res <- dbSendQuery(con, "SELECT loan_id, member FROM loans ORDER BY loan_id")
dbHasCompleted(res)
#> [1] FALSE
dbColumnInfo(res)
#>      name      type
#> 1 loan_id character
#> 2  member character

sizes <- integer()
while (!dbHasCompleted(res)) {
  chunk <- dbFetch(res, n = 25)
  sizes <- c(sizes, nrow(chunk))
}
sizes
#> [1] 25 25 10
dbGetRowCount(res)
#> [1] 60
dbClearResult(res)
dbIsValid(res)
#> [1] FALSE

# Put the cleanup in on.exit() so an error in the loop still releases it.
count_in_chunks <- function(con, sql, chunk_size) {
  res <- dbSendQuery(con, sql)
  on.exit(dbClearResult(res), add = TRUE)
  total <- 0L
  while (!dbHasCompleted(res)) {
    total <- total + nrow(dbFetch(res, n = chunk_size))
  }
  total
}
count_in_chunks(con, "SELECT * FROM loans", 25L)
#> [1] 60

# A result that is never cleared makes dbDisconnect() complain.
res <- dbSendQuery(con, "SELECT * FROM loans")
tryCatch(dbDisconnect(con), warning = \(w) conditionMessage(w))
#> [1] "There are 1 result in use. The connection will be released when they are closed"
dbClearResult(res)
dbDisconnect(con)
dbIsValid(con)
#> [1] FALSE
----

Source: https://dbi.r-dbi.org/reference/dbFetch.html[DBI package documentation: dbFetch]

The 60 loans came out as chunks of 25, 25 and 10 rows, and the loop stopped without a fourth, empty fetch because `dbHasCompleted()` turned `TRUE` when the last row was read. `dbSendQuery()` is documented for queries that return rows: its page describes the data retrieval flow, and `dbSendStatement()` has the matching flow for statements that change data (https://dbi.r-dbi.org/reference/dbSendQuery.html[DBI package documentation: dbSendQuery], https://dbi.r-dbi.org/reference/dbHasCompleted.html[DBI package documentation: dbHasCompleted], https://dbi.r-dbi.org/reference/dbClearResult.html[DBI package documentation: dbClearResult]). A result that is never cleared holds the connection open: `dbDisconnect()` warns with `There are 1 result in use. The connection will be released when they are closed`, and clearing it is what lets the connection go. Put `dbClearResult()` in `on.exit()`, as `count_in_chunks()` does, so that an error halfway through the loop cannot leave it behind. Chunking limits what R holds in memory at once; the database still evaluates the query.

== Parameterised queries

A query that contains a value taken from a variable has two ways to get it in. One is to build the SQL text with the value inside; the other is to leave a placeholder in the SQL and to send the value separately. The second is the rule, because it makes SQL injection impossible by construction. In the DBI documentation's words, parameterised (or prepared) queries and statements serve two purposes besides safety: the same query can be run more than once with different values, and the database may cache intermediate information such as the execution plan (https://dbi.r-dbi.org/reference/dbBind.html[DBI package documentation: dbBind]). The DBI article on advanced usage names two ways to avoid injection from user-supplied parameters, quoting and parameterised queries, and then shows parameterised queries as the way to push the substitution to the DBMS (https://dbi.r-dbi.org/articles/DBI-advanced.html[DBI package documentation: Advanced DBI usage]).

The attack, in one paragraph: a function that pastes `genre` into `+"... WHERE genre = '" ... "'"+` is correct for the values its author thought of, and a value that contains a quotation mark ends the string literal early and the rest of the value is read as SQL. The value comes from a form field, a file or a web request, so the person who types it decides part of the query. A parameter is sent to the database as data, after the SQL text has been parsed, so it can never become SQL. The demonstration with the real output is in the section on older tutorials, where the pattern belongs.

=== Placeholders and params

`dbGetQuery()`, `dbSendQuery()`, `dbExecute()` and `dbSendStatement()` take a `params` argument (partial matching on the older name `param` still works in RSQLite, but DBI 1.1.0 changed its examples to `params`). It is a list with one element per placeholder in the SQL, matched in order, or matched by name for the named style. The DBI documentation does not specify the placeholder syntax; each backend has its own, and DBI passes the SQL through unchanged (https://dbi.r-dbi.org/articles/DBI-advanced.html[DBI package documentation: Advanced DBI usage]):

[cols="3,3",options="header"]
|===
|Placeholder style |Backends that use it, per the `dbBind()` page
|`?`, matched by position in order of appearance |RMariaDB and RSQLite
|`$1`, `$2`, matched by position by index |RPostgres and RSQLite
|`:name` and `$name`, matched by name |RSQLite
|===

Source: https://dbi.r-dbi.org/reference/dbBind.html[DBI package documentation: dbBind]

RSQLite accepts all three styles. Code that must run on more than one backend should therefore keep the SQL string in one place per backend, check the backend's documentation for its placeholder style (the odbc package is not listed on that page), or use dbplyr, which writes the SQL for the connection it is given.

[source,r]
----
source("scenario.R")
library(DBI)

dbWriteTable(con, "books", books, row.names = FALSE)

# A ? placeholder is filled from params, in order; the SQL never contains
# the value, so the value cannot change the meaning of the query.
dbGetQuery(
  con, "SELECT title, year FROM books WHERE genre = ?",
  params = list("Mystery")
)
#>             title year
#> 1 Midnight Ledger 2016
#> 2 Salt and Static 2018
dbGetQuery(
  con, "SELECT title, year FROM books WHERE genre = ? AND year > ?",
  params = list("Mystery", 2016)
)
#>             title year
#> 1 Salt and Static 2018

# RSQLite also accepts named placeholders (:name and $name).
dbGetQuery(
  con, "SELECT title, year FROM books WHERE genre = :genre AND year > :after",
  params = list(genre = "Mystery", after = 2016)
)
#>             title year
#> 1 Salt and Static 2018

# A vector runs the query once per element and stacks the results ...
dbGetQuery(
  con, "SELECT title, genre FROM books WHERE genre = ?",
  params = list(c("Mystery", "Poetry"))

#>                   title   genre
#> 1       Midnight Ledger Mystery
#> 2       Salt and Static Mystery
#> 3 Garden of Small Fires  Poetry
#> 4           Paper Moons  Poetry

genres <- c("Mystery", "Poetry")

sql <- paste0(
  "SELECT title, genre FROM books WHERE genre IN (", placeholders, ")"
)
sql
#> [1] "SELECT title, genre FROM books WHERE genre IN (?, ?)"
dbGetQuery(con, sql, params = as.list(genres))
#>                   title   genre
#> 1       Midnight Ledger Mystery
#> 2 Garden of Small Fires  Poetry
#> 3           Paper Moons  Poetry
#> 4       Salt and Static Mystery

dbGetQuery(con, "SELECT ? IS NULL AS is_null", params = list(NA_character_))
#>   is_null
#> 1       1

dbGetQuery(

  params = list("title")

#>   column_name
#> 1       title
#> 2       title

tryCatch(

  error = \(e) conditionMessage(e)

Source: https://dbi.r-dbi.org/reference/dbGetQuery.html[DBI package documentation: dbGetQuery]

Reading the output:

* A value in `params` is never part of the SQL. `genre = ?` with `"Mystery"` finds the two mysteries, and a value that contains quotation marks or SQL keywords would be matched as that text.
* A vector in `params` is not one value: it is one run of the query per element, and the results are stacked. Two genres gave the four rows of two runs (all the mysteries, then all the poetry). With several parameters, the vectors must have the same length; recycling is not done (`Parameter 2 does not have length 2.`).
* So a vector is not an `IN` list. For `+WHERE genre IN (...)+` write one placeholder per value (`paste(rep("?", n), collapse = ", ")`) and pass the values as a list, as the script does; the text you paste is only question marks, never data.
* `NA` is sent as SQL `NULL`.
* A placeholder stands for a value, not for a name. `SELECT ? AS column_name` returned the string `"title"` twice, not the column `title`. Table and column names are quoted with `dbQuoteIdentifier()` (next section).
* The mismatches are reported by the backend with texts that name the problem: `Query needs to be bound before fetching` (a placeholder and no `params`), `Query requires 1 params; 2 supplied.`, `No value given for placeholder year` (a name that does not match), and `Cannot use named parameters for anonymous/numbered placeholders` when a named list is given for `?` placeholders.

=== Bulk inserts and dbBind()

`dbExecute()` accepts `params` too, and the vectors make a bulk insert: one `INSERT` statement, many rows, one call, safe by the same rule. RSQLite's NEWS describes executing the same prepared query or statement efficiently many times by passing a data-frame-like object. When one query is to be run many times with different values, `dbSendQuery()` once and `dbBind()` for each value lets the database reuse its preparation of the query: `dbBind(res, params)` binds new values to the result, then `dbFetch()` reads that run's rows. `dbSendStatement()` plays the same role for a statement, and `dbGetRowsAffected()` reports how many rows the last binding changed.

[source,r]
----
source("scenario.R")
library(DBI)

con <- dbConnect(RSQLite::SQLite(), ":memory:")
dbWriteTable(con, "books", books, row.names = FALSE)

# dbExecute(params =) with vectors inserts one row per element.
dbExecute(con, "
  CREATE TABLE members (
    member_id INTEGER PRIMARY KEY,
    name TEXT NOT NULL UNIQUE,
    joined TEXT
  )
")
#> [1] 0
dbExecute(
  con, "INSERT INTO members (name, joined) VALUES (?, ?)",
  params = list(
    c("Ana Ruiz", "Ben Okafor", "Dev Patel"),
    c("2024-01-05", "2024-02-11", "2024-03-02")
  )
)
#> [1] 3
dbReadTable(con, "members")
#>   member_id       name     joined
#> 1         1   Ana Ruiz 2024-01-05
#> 2         2 Ben Okafor 2024-02-11
#> 3         3  Dev Patel 2024-03-02

# The database enforces its own rules, and says which one failed.
tryCatch(
  dbExecute(
    con, "INSERT INTO members (name) VALUES (?)",
    params = list("Ana Ruiz")
  ),
  error = \(e) conditionMessage(e)
)
#> [1] "UNIQUE constraint failed: members.name"
tryCatch(
  dbExecute(con, "INSERT INTO members (name) VALUES (NULL)"),
  error = \(e) conditionMessage(e)
)
#> [1] "NOT NULL constraint failed: members.name"

# dbBind() runs a prepared query again with new values.
res <- dbSendQuery(con, "SELECT title, year FROM books WHERE genre = :genre")
by_genre <- lapply(c("Mystery", "Poetry"), \(g) {
  dbBind(res, list(genre = g))
  dbFetch(res)
})
by_genre
#> [[1]]
#>             title year
#> 1 Midnight Ledger 2016
#> 2 Salt and Static 2018
#>
#> [[2]]
#>                   title year
#> 1 Garden of Small Fires   NA
#> 2           Paper Moons 2005
#>
dbClearResult(res)

# dbSendStatement() + dbBind() does the same for statements that change data.
st <- dbSendStatement(con, "UPDATE members SET joined = ? WHERE name = ?")
dbBind(st, list("2025-01-01", "Ana Ruiz"))
dbGetRowsAffected(st)
#> [1] 1
dbBind(st, list(
  c("2025-02-01", "2025-03-01"),
  c("Ben Okafor", "Dev Patel")
))
dbGetRowsAffected(st)
#> [1] 2
dbClearResult(st)
dbReadTable(con, "members")
#>   member_id       name     joined
#> 1         1   Ana Ruiz 2025-01-01
#> 2         2 Ben Okafor 2025-02-01
#> 3         3  Dev Patel 2025-03-01

dbDisconnect(con)
----

Source: https://dbi.r-dbi.org/reference/dbSendStatement.html[DBI package documentation: dbSendStatement]

The UNIQUE and NOT NULL constraints belong to the table definition, and violating them is an error with the name of the table and column (`UNIQUE constraint failed: members.name`). That is how a database protects data that several programs write: the rule lives with the data, and the R code only has to handle the error (see xref:programming-languages/r/conditions-and-error-handling.adoc[Conditions and Error Handling]). Binding a vector to `dbBind()` runs the query or statement once per element, exactly like `params`, and `dbGetRowsAffected()` after the second binding reports 2 for the two updates.

== Quoting identifiers and values

A placeholder cannot stand for a table name, a column name, a sort direction or an `IN` list. When those come from a variable, they have to be built into the SQL text, and that is the one place where quoting matters. DBI provides the functions that do it for the connected database, because the quoting rules differ between databases (the output below shows backticks for SQLite).

[source,r]
----
source("scenario.R")
library(DBI)

con <- dbConnect(RSQLite::SQLite(), ":memory:")
dbWriteTable(con, "books", books, row.names = FALSE)

# Values: dbQuoteString() and dbQuoteLiteral() return text that is safe to
# paste into SQL for this database.
dbQuoteString(con, "O'Brien")
#> <SQL> 'O''Brien'
dbQuoteString(con, c("fiction", NA))
#> <SQL> 'fiction'
#> <SQL> NULL
dbQuoteLiteral(con, 3L)
#> <SQL> 3
dbQuoteLiteral(con, shelf_today)
#> <SQL> '2026-06-30'
dbQuoteLiteral(con, TRUE)
#> <SQL> 1
dbQuoteLiteral(con, NA_character_)
#> <SQL> NULL

# Names: dbQuoteIdentifier() for table and column names, which a placeholder
# cannot stand for.
dbQuoteIdentifier(con, "my table")
#> <SQL> `my table`
dbQuoteIdentifier(con, "select")
#> <SQL> `select`
table_name <- "books"
sql <- paste("SELECT COUNT(*) AS n FROM", dbQuoteIdentifier(con, table_name))
sql
#> [1] "SELECT COUNT(*) AS n FROM `books`"
dbGetQuery(con, sql)
#>    n
#> 1 16

# sqlInterpolate() fills ?name placeholders by quoting each value.
sql <- sqlInterpolate(
  con, "SELECT title FROM books WHERE genre = ?genre AND year > ?after",
  genre = "Mystery", after = 2016
)
sql
#> <SQL> SELECT title FROM books WHERE genre = 'Mystery' AND year > 2016
is(sql, "SQL")
#> [1] TRUE
dbGetQuery(con, sql)
#>             title
#> 1 Salt and Static

# A hostile value stays one string literal.
hostile <- "x'; DROP TABLE books; --"
sqlInterpolate(
  con, "SELECT title FROM books WHERE title = ?title",
  title = hostile
)
#> <SQL> SELECT title FROM books WHERE title = 'x''; DROP TABLE books; --'
dbGetQuery(
  con, "SELECT title FROM books WHERE title = :title",
  params = list(title = hostile)
)
#> [1] title
#> <0 rows> (or 0-length row.names)
dbListTables(con)
#> [1] "books"

# The values you supply must match the placeholders.
tryCatch(
  sqlInterpolate(
    con, "SELECT title FROM books WHERE genre = ?genre",
    year = 1
  ),
  error = \(e) conditionMessage(e)
)
#> [1] "Supplied values don't match named vars to interpolate"

# SQL() marks text you already know is safe SQL.
SQL("year > 2000")
#> <SQL> year > 2000

dbDisconnect(con)
----

Source: https://dbi.r-dbi.org/reference/dbQuoteIdentifier.html[DBI package documentation: dbQuoteIdentifier]

* `dbQuoteIdentifier(con, name)` makes a table or column name safe, including names with spaces or names that are reserved words. Use it whenever a name is not a constant in your source.
* `dbQuoteString(con, x)` and `dbQuoteLiteral(con, x)` do the same for a value. `dbQuoteLiteral()`, added in DBI 0.8, handles many more R types than `dbQuoteString()`, including dates (`'2026-06-30'`, as DBI 1.1.1 formats them: year-month-day, without a time zone), logicals, numbers and missing values. The doubled quote in `'O''Brien'` is the SQL way to escape one.
* `+sqlInterpolate(con, sql, ...)+` replaces `?name` placeholders in a SQL string with quoted values: use it where the SQL must be built as text, for instance to hand a query to a function that takes a string and has no `params` argument. Its documentation was extended in DBI 1.1.0 and the function has used `dbQuoteLiteral()` since then. The hostile value in the script, `x'; DROP TABLE books; --`, becomes one string literal and the table is still there. Supplying a name that is not in the SQL is an error (`+Supplied values don't match named vars to interpolate+`).
* `SQL()` marks text as already being SQL, so that DBI does not quote it a second time. Never use it on text you did not write.
* The glue package's `glue_sql()` does the same quoting for any variable written between braces in the SQL string and appears in the DBI article on advanced usage; glue is not used here.

Quoting is the second line of defence, not the first. A placeholder is simpler to get right than a function that must be called on every variable, and it works for every backend in the same way. Use `params` for values and `dbQuoteIdentifier()` for names, and nothing else. The reference page is https://dbi.r-dbi.org/reference/sqlInterpolate.html[DBI package documentation: sqlInterpolate], and the one for the value functions is https://dbi.r-dbi.org/reference/dbQuoteString.html[DBI package documentation: dbQuoteString].

== Transactions

A transaction groups statements so that they all take effect or none does. Without one, a failure halfway through a series of `INSERT`s leaves the database with half of them. DBI offers `dbWithTransaction()` for the common case, and `dbBegin()`, `dbCommit()` and `dbRollback()` for control by hand (https://dbi.r-dbi.org/reference/dbWithTransaction.html[DBI package documentation: dbWithTransaction], https://dbi.r-dbi.org/reference/transactions.html[DBI package documentation: transactions]). The database does the work; what a transaction guarantees is explained in the xref:database/sql/transactions.adoc[SQL transactions page].

[source,r]
----
library(DBI)

con <- dbConnect(RSQLite::SQLite(), ":memory:")
dbExecute(con, "CREATE TABLE members (name TEXT NOT NULL UNIQUE)")
#> [1] 0

count_members <- function() {
  dbGetQuery(con, "SELECT COUNT(*) AS n FROM members")$n
}

# dbWithTransaction() commits when the code finishes, and returns its value.
dbWithTransaction(con, {
  dbExecute(con, "INSERT INTO members (name) VALUES ('Ana Ruiz')")
  dbExecute(con, "INSERT INTO members (name) VALUES ('Ben Okafor')")
  "committed"
})
#> [1] "committed"
count_members()
#> [1] 2

# An error rolls the whole block back and is passed on.
tryCatch(
  dbWithTransaction(con, {
    dbExecute(con, "INSERT INTO members (name) VALUES ('Dev Patel')")
    dbExecute(con, "INSERT INTO members (name) VALUES ('Ana Ruiz')")
  }),
  error = \(e) conditionMessage(e)
)
#> [1] "UNIQUE constraint failed: members.name"
count_members()
#> [1] 2

# dbBreak() leaves the block and rolls back without an error.
dbWithTransaction(con, {
  dbExecute(con, "INSERT INTO members (name) VALUES ('Eva Lindqvist')")
  dbBreak()
})
count_members()
#> [1] 2

# The same steps by hand: dbBegin(), then dbCommit() or dbRollback().
dbBegin(con)
dbExecute(con, "DELETE FROM members") # two rows deleted ...
#> [1] 2
count_members() # ... and gone, inside the transaction
#> [1] 0
dbRollback(con)
count_members()
#> [1] 2

# Transactions do not nest, and there is nothing to commit outside one.
tryCatch(
  dbWithTransaction(con, dbWithTransaction(con, 1)),
  error = \(e) conditionMessage(e)
)
#> [1] "cannot start a transaction within a transaction"
tryCatch(dbCommit(con), error = \(e) conditionMessage(e))
#> [1] "cannot commit - no transaction is active"

dbDisconnect(con)
----

Source: https://dbi.r-dbi.org/reference/dbWithTransaction.html[DBI package documentation: dbWithTransaction]

* `dbWithTransaction(con, code)` starts a transaction, evaluates `code`, commits if it finishes, and returns the value of the code (`"committed"`). If `code` signals an error, it rolls back and re-throws it, so the failed insert of a duplicate name left the table unchanged (two members) and the error message was still delivered to `tryCatch()`. DBI 1.3.0 (2026-02-11) made it roll back also when the code is interrupted.
* `dbBreak()` inside the block stops it and rolls back without an error; `dbWithTransaction()` then returns `NULL` invisibly, which is why the call printed nothing.
* By hand, `dbBegin()`, the statements, and then `dbCommit()` to keep them or `dbRollback()` to discard them. The `DELETE` inside the transaction is visible to the connection that made it (the count was 0) and gone after the rollback (2 again). Other connections do not see the deletion until it is committed.
* Transactions do not nest in SQLite, and the messages from the database say so: `cannot start a transaction within a transaction`, and `cannot commit - no transaction is active` when there is nothing to commit. A function that opens a transaction cannot call another that opens one; decide which of the two owns it.
* Outside a transaction a database normally commits each statement by itself (autocommit), so statements issued without `dbBegin()` take effect one by one.

A rollback restores the database; it does not undo what the R code did meanwhile. A script that wrote a file or sent a message in the middle of the transaction cannot take that back.

== Errors and warnings

An error from the database arrives as an ordinary R error whose message is the database's own text. The condition has class `simpleError` and no call (`conditionCall()` is `NULL`), so there is nothing to parse except the message, and `+tryCatch(..., error = \(e) conditionMessage(e))+` is how the examples capture it. The text depends on the backend: the messages below are SQLite's, and PostgreSQL or MariaDB word the same mistakes differently (code that reacts to a particular failure has to test the text of the backend it uses). The script collects the messages for the typical mistakes of a first week with SQL.

[source,r]

con <- dbConnect(RSQLite::SQLite(), ":memory:")
dbWriteTable(con, "books", books, row.names = FALSE)

is.null(conditionCall(e))
#> [1] TRUE

The warnings come from the result handling, not from SQL. `Closing open result set, pending rows` is what RSQLite says when a second query is sent on a connection while an earlier result still has rows to fetch: the old result is closed (the script shows `dbIsValid(open_result)` turning `FALSE`). `There are 1 result in use. The connection will be released when they are closed` is the warning of `dbDisconnect()`; and `+Ignoring remaining part of query: ...+` is the one about a second statement in the same string. All three are bugs in the calling code, and the cure is the same: one result at a time per connection, and every result cleared (`on.exit(dbClearResult(res))`). Turn warnings into errors during testing with `options(warn = 2)` if you want them to stop the script (see xref:programming-languages/r/conditions-and-error-handling.adoc[Conditions and Error Handling]).

The script shows the five things that make dbplyr different from working with a data frame.

* *The table is lazy.* `tbl(con, "loans")` has a class that starts with `tbl_SQLiteConnection`; it knows the column names (`colnames()`), but not the number of rows (`nrow()` is `NA`), because no row has been read. Printing it sends a query that fetches the first ten rows and says so: `# A query:  ?? x 5` (the number of rows is unknown) and `# Database: sqlite 3.53.3 [:memory:]`.
* *Verbs build a query; nothing runs.* `filter()`, `group_by()`, `summarise()` and `arrange()` each add a layer to the lazy query, whose class is still `tbl_SQLiteConnection`. `show_query()` prints the SQL it would send: the `!is.na(return_date)` became `NOT((return_date IS NULL))`, `n()` became `+COUNT(*)+`, and the `desc()` became `DESC` (https://dbplyr.tidyverse.org/reference/show_query.html[dbplyr package documentation: show_query]).
* *`collect()` runs it.* The result is an ordinary tibble in R, with the class `tbl_df`, `tbl`, `data.frame`; everything after `collect()` is local R (https://dbplyr.tidyverse.org/reference/collect.tbl_sql.html[dbplyr package documentation: collect]). Do the filtering, joining and aggregating before `collect()`, and the summarising or plotting after it. A lazy table is not a data frame: `loans_db$member` is an error (`The $ method of <tbl_lazy> is for internal use only`) that points to `dplyr::pull()`, which runs the query and returns one column as a vector.
* *Functions are translated, or passed through.* dbplyr translates a fixed set of R functions into the SQL of the connection (for SQLite, `n()`, `is.na()`, the arithmetic and comparison operators and many more). A function it does not know is sent unchanged, which is why `julianday()`, an SQLite function, works in `mutate()`. The same rule makes `grepl()` fail, because SQLite has no such function: the error arrives when the query runs, wrapped by dbplyr's `Failed to collect lazy table.` and ending with the database's own words. Which R functions are translated is in the translation articles (https://dbplyr.tidyverse.org/articles/translation-function.html[dbplyr package documentation: Function translation]). A variable from R, like `loan_days` in the script, is evaluated in R and its value is put in the SQL: `held > 21`.
* *SQL aggregates drop `NULL`.* SQL's `AVG` skips missing values whatever you ask. dbplyr says so once, as a warning (`Missing values are always removed in SQL aggregation functions.`), and stops when you pass `na.rm = TRUE`. The warning is shown once every eight hours, which is why it was captured in the script instead of being left to appear.

The last line of the script is the bridge between the two worlds: `+tbl(con, sql("SELECT ..."))+` takes any SQL as the source of a lazy table, and the verbs that follow are added on top of it. Use it for a query that is easier to write in SQL than in dplyr, or one that dbplyr cannot express (https://dbplyr.tidyverse.org/reference/sql.html[dbplyr package documentation: sql]). The reverse is also true. `show_query()`, or in dbplyr 2.6.0 `last_sql()` (which returns the most recent query dbplyr generated), gives the SQL of a pipeline to read or to paste into a SQL client.

Which of DBI and dbplyr to use is a matter of the task and of the reader:

[cols="3,3,3",options="header"]
|===
|Situation |DBI (SQL text) |dbplyr (dplyr verbs)
|The analysis is already written in SQL, or uses vendor features dbplyr has no translation for |`dbGetQuery()` with the SQL |`+tbl(con, sql("..."))+` and verbs on top, if needed
|The question is a filter, a join and a summary |Works; the SQL is yours to write and maintain |Shorter, reads as the rest of the tidyverse code, checked with `show_query()`
|Writes: creating tables, inserts, updates, transactions |`dbExecute()`, `dbWriteTable()`, `dbWithTransaction()` |Not its job (dbplyr has some row-update verbs; see its documentation)
|Values from the user |`params =` |A local variable is escaped and written into the SQL text (the script's `hostile` string stays one literal)
|Same code on several databases |SQL dialects differ |The translation targets each backend's dialect
|===

== The overdue analysis, twice

The shelf scenario's central question is which loans were overdue: a returned loan is overdue when it was held for more than `loan_days` (21) days. The scenario's reference result is that 25 of the returned loans exceed 21 days. The next script puts `books` and `loans` in a database with date columns, answers the question by genre in SQL, answers it again with dbplyr verbs, checks that the two are the same, and checks both against base R on the data frames that never left R.

Two details of the data matter. The `isbn` of `loans` is 13 bare digits, and the `isbn` of `books` is sometimes hyphenated, so the join compares `REPLACE(b.isbn, '-', '')` with `l.isbn`. And the genres of `books` have nine spellings of six genres, so the grouping key is `LOWER(TRIM(genre))`. Both cleanings are done in the query, the way the data frame code of xref:programming-languages/r/data-frames.adoc[Data Frames] does them in R. The tables are created with `DATE` columns and the dates are appended as ISO text, so SQLite's `julianday()` can compute with them and, with `extended_types = TRUE`, R still receives `Date` columns.

The three results agree. The query keeps the loan period out of the SQL text (`> ?` with `params = list(loan_days)`), so the number lives in one place, in the scenario, in R. Of 53 returned loans, 25 are overdue: 8 fiction, 5 science fiction, and 3 each for classic, non-fiction and poetry, 2 for mystery, and 1 with an `unknown` genre. That last row is the lesson in the join. The loan `L005` has a one-digit-short ISBN (`978030640615`), so no book matches it. An inner `JOIN` would have dropped the loan, and the total would have been 24 and not 25, with no error to say why. The `LEFT JOIN` keeps it and gives it the genre `unknown`, which makes the data problem visible. The last query of the script finds exactly that loan. The scenario's other deliberate defects behave as they do in R: the loan with the impossible date `2025-02-30` has `NULL` dates, `julianday()` of `NULL` is `NULL`, the comparison is `NULL`, and `SUM` ignores it, so it counts as returned and not overdue; the loan returned before it was borrowed has a negative duration and is not overdue; the 7 unreturned loans are excluded by the `WHERE` (the question here is about returned loans; for the unreturned, `shelf_today` takes the place of the return date).

The dbplyr version builds the cleaning step as a lazy table (`books_key`), joins the loans to it, and ends in the same `GROUP BY`. `sql("REPLACE(isbn, '-', '')")` is a SQL fragment that dbplyr does not translate, and everything else is verbs. `show_query()` on `overdue_db` would show the nested query it generated.

== Other backends in short

* *PostgreSQL* (RPostgres): a server database that several people and programs share. The settings come from the environment (`PGHOST` and the others, or `+~/.pgpass+`), parameters can be written `$1`, `$2`, and `dbConnect()` has `timezone` and `timezone_out` arguments for time zones (https://rpostgres.r-dbi.org/reference/Postgres.html[RPostgres package documentation: Postgres]).
* *MariaDB and MySQL* (RMariaDB): `dbConnect()` takes `dbname`, `username`, `password` and `host`, and can read a MariaDB option file. Its CRAN description says it implements a DBI-compliant interface to MariaDB and MySQL, and the legacy RMySQL package points to it for a modern MySQL client (https://rmariadb.r-dbi.org/reference/dbConnect-MariaDBDriver-method.html[RMariaDB package documentation: dbConnect]).
* *ODBC* (odbc): one package for every database with an ODBC driver, from a data source name or a driver and its settings. It is a DBI backend, so everything on this page applies (https://odbc.r-dbi.org/reference/dbConnect-OdbcDriver-method.html[odbc package documentation: dbConnect]).
* *DuckDB* (duckdb): an embedded analytical database management system; like SQLite it needs no server. `dbConnect(duckdb::duckdb())` keeps the data in RAM, and `dbdir` names a file (https://r.duckdb.org/reference/duckdb.html[duckdb package documentation: duckdb]).
* *Others*, such as bigrquery, are listed on the DBI site.

Two newer parts of DBI are named here and not used, because they need packages that are not installed. DBI 1.2.0 (2023-12-20) added a family of Arrow generics (`dbGetQueryArrow()`, `dbSendQueryArrow()`, `dbFetchArrow()`, `dbReadTableArrow()`, `dbWriteTableArrow()` and others) with default implementations built on nanoarrow, and the DBI documentation labels these functions experimental (https://dbi.r-dbi.org/reference/dbGetQueryArrow.html[DBI package documentation: dbGetQueryArrow]). DBI 1.3.0 added support for OpenTelemetry through the otel and otelsdk packages. For an Arrow-based workflow, the packages that talk Arrow directly are described at https://arrow.apache.org/docs/r/ (the arrow package is not installed here and is not run).

== Pitfalls

The R FAQ has no entry about databases (a search of the FAQ finds none), so these come from the DBI and RSQLite documentation and from the examples above.

* *Building SQL by pasting values.* Use `params =`, `dbQuoteIdentifier()` for names and `sqlInterpolate()` where text is unavoidable. See the section on older tutorials for the output of a pasted query.
* *Forgetting to disconnect, or to clear a result.* Close in `on.exit()`; clear in `on.exit()`. Both produce a warning in RSQLite and a held server session elsewhere.
* *A vector in `params` is a loop, not a list of values.* Use one placeholder per value for `IN`.
* *Assuming the types survive.* Logical columns return as integers, factors as text and dates as numbers unless `extended_types = TRUE` and the column is declared `DATE`.
* *Assuming the order.* A table has no order; add `ORDER BY` when the order matters, including for `LIMIT` and `n =`.
* *`overwrite = TRUE` on the wrong table.* It replaces whatever is there.
* *Comparing text with the wrong case or blanks.* `'Fiction'`, `'fiction'` and `'Fiction '` are three different values to SQL. Clean at the source or in the query (`LOWER(TRIM(x))`).
* *Pulling everything and then filtering in R.* `dbReadTable()` followed by a filter reads the whole table. Filter in the query.
* *`NA` and `NULL` in comparisons.* `x = NULL` is never true in SQL; use `IS NULL`. In dbplyr, `is.na()` becomes `IS NULL`.
* *Secrets in the script.* Environment variables, `.Renviron`, askpass or keyring; never a literal.
* *Saving a connection.* A connection that went through `saveRDS()` and `readRDS()` is not valid (`dbIsValid()` is `FALSE`, and using it fails with the unhelpful `bad_weak_ptr`); open a new one in each session (see xref:programming-languages/r/serialization-rds-rdata-and-json.adoc[Serialization: RDS, RData and JSON]).
* *Sharing one connection between processes.* A worker of a parallel computation should open its own connection (see xref:programming-languages/r/parallel-and-asynchronous-computing.adoc[Parallel and Asynchronous Computing]).

== Where older tutorials differ

#> 2           Paper Moons
nrow(find_by_genre(con, "x' OR '1'='1"))
#> [1] 0
nrow(find_by_genre(con, "O'Brien"))
#> [1] 0

# ... and works once RSQLite is loaded, as the line above has just done.
dbDriver("SQLite")
#> <SQLiteDriver>

# fetch() is the pre-DBI name of dbFetch().
res <- dbSendQuery(con, "SELECT title FROM books ORDER BY title")
fetch(res, n = 2)
#>                  title
#> 1   the quiet streets
#> 2        A Map of Salt
dbClearResult(res)

dbDisconnect(con)
----

Source: https://dbi.r-dbi.org/articles/DBI-advanced.html[DBI package documentation: Advanced DBI usage]

The first function builds the SQL by pasting `genre` between quotation marks, which is what the manual's `+paste("select row_names, Murder from arrests", "where Rape > 30 ...")+` pattern becomes when one value is variable. It works for `"Poetry"`. A value with an apostrophe breaks it (`near "Brien": syntax error`), which is the harmless way this fails. A value that closes the string and continues the logic (`x' OR '1'='1`) makes the `WHERE` true for every row: all 16 books came back for a genre that does not exist. That is SQL injection: the person who supplies the value rewrote the query. RSQLite stopped the third attempt, the stacked `DROP TABLE`, only because it runs a single statement per call and warned about the rest (`+Ignoring remaining part of query: ...+`); that is not protection, and a backend that executes every statement in the string would not have stopped it. The rewritten function with `params = list(genre)` returns the two poetry books for `"Poetry"` and nothing for the other two values, because they are only text to compare with. `sprintf()` has the same problem as `paste()` when the format has a `%s`; `+sprintf("... %d", n)+` with a number is safe only because `%d` will not accept text.

The last lines of the script are two other habits from the manual's era. `dbDriver("SQLite")` chooses the driver by name; it fails, in a session where RSQLite has not been loaded, with `+Couldn't find driver SQLite+`, followed by the places it looked, and works after the package is loaded. `fetch()` is the name the older DBI used for what is now `dbFetch()`; RSQLite still exports it.
