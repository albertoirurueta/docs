== Why objects with reference semantics exist

R is built around values. When a function receives a vector it receives what behaves like a copy, and an assignment such as `+y <- x+` makes a second name for the same value that is copied only when one of them is modified (see xref:programming-languages/r/assignment-names-and-values.adoc[Assignment, Names and Values] and xref:programming-languages/r/memory-and-copy-semantics.adoc[Memory and Copy Semantics]). That is exactly what is wanted for data analysis, and it is why a function can never change the data frame it was given by accident. The help page of Reference Classes describes the functional model in these terms and then names the situations in which it is the wrong one: sometimes one would like all the code dealing with an object to see the exact same content, so that a change made in any computation is reflected everywhere, which suits an object with some objective reality such as a window in a user interface.

R already has one kind of object that is never copied: the environment. The manual lists environments among the basic object types and describes them as a frame plus an enclosure (https://cran.r-project.org/doc/manuals/r-release/R-lang.html#Environment-objects[R-lang: Environments]); xref:programming-languages/r/scoping-environments-and-closures.adoc[Scoping, Environments and Closures] covers the mechanism. Assigning an environment to a second name, or passing it to a function, copies the reference and not the environment, so every holder sees every change.

[source,r]
----
# A list is a value: a function that "modifies" it works on a copy.
shelf_list <- list(log = character())
add_to_list <- function(x, entry) {
  x$log <- c(x$log, entry)
  x
}
add_to_list(shelf_list, "L001 out")$log
#> [1] "L001 out"
shelf_list$log
#> character(0)

# An environment is a reference: the function and the caller share it.
shelf_env <- new.env()
shelf_env$log <- character()
add_to_env <- function(e, entry) {
  e$log <- c(e$log, entry)
  invisible(e)
}
add_to_env(shelf_env, "L001 out")
shelf_env$log
#> [1] "L001 out"

# Assignment copies the reference, not the environment.
alias <- shelf_env
alias$log <- c(alias$log, "L002 out")
shelf_env$log
#> [1] "L001 out" "L002 out"
identical(alias, shelf_env)
#> [1] TRUE
----

Source: https://cran.r-project.org/doc/manuals/r-release/R-lang.html#Environment-objects[The R Language Definition: Environments]

The list `shelf_list` behaves as a value: the function returned a changed copy and left the original empty. The environment `shelf_env` behaves as a reference: the function changed it in place, and `alias` is not a copy of it but a second name for it, which is why `identical()` reports `TRUE`. The R FAQ draws the same line when it separates the frame of a function from its enclosing environment (https://cran.r-project.org/doc/FAQ/R-FAQ.html#What-are-the-enclosing-and-parent-environments_003f[R FAQ 7.12: What are the enclosing and parent environments?]).

A bare environment is a poor class: nothing says which names it is supposed to hold, nothing checks what is stored in them, and the functions that operate on it are just functions that happen to receive it. Reference Classes and R6 both add the missing parts on top of an environment:

* a _class_: a named definition of the fields (state) and the methods (functions that work on that state), so that objects of the class all look the same;
* _methods_ called with `$`: `+obj$lend(...)+` runs a function that belongs to the object and can read and change its fields, which is the style of Java, C++ and Python;
* _inheritance_: a subclass adds fields and methods and can override the methods of its superclass;
* _initialisation_ and _printing_ hooks, and, in R6 and (partly) in Reference Classes, locking and active bindings.

"R5" is not a separate system. It is a community nickname for Reference Classes (R's other systems are S3 and S4, so the third was jokingly called R5), and the R6 package, which is a different implementation, took its own name from the joke. The R6 documentation also records that "R5" had been the code name of a different, never released object system. This page says Reference Classes for the base R system and R6 for the package.

== Reference Classes with `setRefClass()`

A Reference Class is an S4 class whose instances contain an environment. The documentation says so directly: reference classes are implemented as S4 classes with a data part of type `environment`, fields correspond to named objects in that environment, and a field with a declared class is implemented as a special form of active binding that enforces the class on assignment (https://search.r-project.org/R/refmans/methods/html/refClass.html[R documentation: refClass]). That is why they live in the `methods` package, why they are created with a function from the S4 family, and why `isVirtualClass()`, `validObject()` and `is()` work on them.

=== Fields and the generator

`setRefClass(Class, fields = , contains = , methods = )` defines the class and returns a _generator_. The `fields` argument is either a character vector of field names, which gives every field the class `"ANY"`, or a named list in which each element is usually the name of a class. A field of a declared class accepts only objects of that class or a subclass. The six fields of the scenario book are declared in that way, and `+BookRC$new(...)+` (equivalently `+BookRC(...)+`) creates an object:

Several things in that output are worth reading slowly. `BookRC` is not a class definition but an object of class `refObjectGenerator`, which is a function (it can be called as `+BookRC(...)+`) and also a reference object with methods of its own: `$new()`, `$methods()`, `$fields()`, `$help()`, `$lock()` and `$accessors()`. `BookRC$fields()` returns the declared class of every field. Two reserved names exist as fields of every object: `.self` is the whole object and `.refClassDef` is its class definition. Both are read-only, and the documentation advises against defining any field whose name begins with a dot.

=== Methods, `initialize()` and validation

Methods are ordinary functions in a named list passed as `methods`, or added later with `+Gen$methods(...)+`. Inside a method the object itself is not an argument. The environment of the method is the object, so fields and other methods are used by name, and the whole object is available as `.self`. A field is changed with the non-local assignment `+<<-+`: the documentation stresses that non-local assignment is required, because `+title <- value+` just creates a local variable as it would in any function. The reason is the one explained on the xref:programming-languages/r/scoping-environments-and-closures.adoc[scoping page]: `+<<-+` starts the search for the name in the enclosing environment of the function, which for a method is the object, where the field lives.

Two method names are special. `initialize` is called when an object is created, and its job here is the work of the scenario's `book()` function: trim the strings, normalise the ISBN, convert the numbers to integer and apply the rules of `validate_book()`. `finalize` is called before the object is garbage collected (see the section on debugging and finalizers below). The documentation's advice for an `initialize` method comes to three rules, and the example follows all of them:

. It should pass `+...+` on, with `+callSuper(...)+` or `+initFields(...)+`, so that subclasses can add fields.
. It must work when called with no arguments, because `$copy()` calls the generator that way; here that is the `missing(title)` branch.
. The standard initialisation, which is `+callSuper(...)+` and ends in `+initFields(...)+`, assigns the named arguments to the fields. Any computation on the arguments (here `trimws()` and `as.integer()`) comes before it and any check of the finished object after it.

[source,r]
----
source("scenario.R")

BookRC <- setRefClass("BookRC", # nolint: object_name_linter.
  fields = list(
    title = "character", author = "character", isbn = "character",
    year = "integer", genre = "character", pages = "integer"
  ),
  methods = list(
    initialize = function(title, author = NA_character_, isbn = NA_character_,
                          year = NA_integer_, genre = NA_character_,
                          pages = NA_integer_, ...) {
      "Create a book; with no title (as copy() does) create an empty shell."
      if (missing(title)) {
        return(callSuper(...))
      }
      callSuper(
        title = trimws(title), author = trimws(author),
        isbn = if (is.na(isbn)) isbn else normalise_isbn(isbn),
        year = as.integer(year), genre = trimws(genre),
        pages = as.integer(pages), ...
      )
      validate()
    },
    validate = function() {
      "Apply the rules of validate_book(); return the object invisibly."
      lens <- c(length(title), length(author), length(isbn),
                length(year), length(genre), length(pages))
      if (any(lens != 1L)) {
        stop("every field of a book must have length 1", call. = FALSE)
      }
      if (is.na(title) || !nzchar(title)) {
        stop("a book needs a title", call. = FALSE)
      }
      if (!is.na(isbn) && !is_valid_isbn13(isbn)) {
        stop("invalid ISBN-13: ", isbn, call. = FALSE)
      }
      if (!is.na(year) && year > 2100L) {
        stop("implausible year: ", year, call. = FALSE)
      }
      invisible(.self)
    },
    describe = function() {
      yr <- if (is.na(year)) "n.d." else year
      sprintf("%s (%s, %s)", title, author, yr)
    },
    show = function() {
      cat("<", class(.self)[[1L]], "> ", describe(), "\n", sep = "")
    }
  )
)

b1 <- BookRC$new(
  title = "  the quiet streets ", author = "Iris  Fenwick",
  isbn = "978-0-306-40615-7", year = 1999, genre = "Fiction", pages = 288
)
b1
#> <BookRC> the quiet streets (Iris  Fenwick, 1999)
b1$isbn
#> [1] "9780306406157"
b1$year
#> [1] 1999
class(b1$year)
#> [1] "integer"

try_book <- function(...) {
  tryCatch(BookRC$new(...), error = \(e) conditionMessage(e))
}
try_book(title = "")
#> [1] "a book needs a title"
try_book(title = "Orchard Logic", isbn = "9780306406158")
#> [1] "invalid ISBN-13: 9780306406158"
try_book(title = "Far Future", year = 2101L)
#> [1] "implausible year: 2101"
try_book(title = c("A", "B"))
#> [1] "every field of a book must have length 1"
----

Source: https://search.r-project.org/R/refmans/methods/html/refClass.html[R documentation: refClass]

Look at what the listing shows. The strings arrive trimmed and the ISBN arrives normalised, because `callSuper()` received the cleaned values. The year `1999` was a double in the call and is an integer in the object, because the field would otherwise have rejected it (the error text is in the section on what goes wrong). Each failed validation raises the same message as `validate_book()` does for the S3 class: the rules moved from a function that checks a list to a method that checks `.self`. The class check of a field is not a validity rule, though: `title = c("A", "B")` is a perfectly good `character` vector, which is why the length check is still needed.

The docstring at the start of `initialize` and `validate` is a convention of Reference Classes: if the first element of a method body is a literal string, `Gen$help("validate")` prints it. The method `show` is also special by name. It is what the console calls to print an object, and the documentation recommends printing the class name explicitly so that subclasses can reuse the method, which is why `class(.self)[[1L]]` appears instead of the literal `"BookRC"`.

Methods call each other by name (`validate()` inside `initialize()`), and the object is searched first, so the names of fields and methods must not collide. For that reason the scenario's `format()` became `describe()`: a method named `format` would hide `base::format()` inside every other method of the class. When a method uses another method indirectly, through `lapply()` or `do.call()`, the documentation asks for a `usingMethods(describe)` call, because only the methods that the code analysis sees are installed in the object.

`+Gen$methods(...)+` adds a method after the class exists, and the documentation prefers it to the `methods` argument of `setRefClass()` for the sake of readability. In the listing `b` was created before `age` was defined and can still call it, because methods are looked up when they are first used. The caveat in the documentation concerns methods that were already analysed: a method defined earlier is not re-analysed, so it will not call a new method of the same name unless it is redefined too. The R 3.3.2 NEWS records the repair of an earlier bug in this area (calls to `$methods()` did not re-analyse previously defined methods). The listing also shows `Gen$help()` printing the docstring, `Gen$methods()` returning the names of the inherited helpers (`callSuper`, `copy`, `field`, `export`, `import`, `initFields`, `show`, `trace`, `untrace`, `usingMethods`, `getClass`, `getRefClass`, and two internal ones whose names begin with a dot), and `obj$field(name, value)` for a field whose name is computed.

The documentation also warns that all the methods of a class belong in the source that defines it. In a package with a namespace the class definition is locked once the package is loaded, so `$methods()` and `$lock()` raise an error if they are called later from outside the package.

=== Aliasing and `$copy()`

An assignment of a reference object copies the reference. The scenario's S3 `book` has value semantics, so the same three lines give different answers:

[source,r]
----
source("scenario.R")

BookRC <- setRefClass("BookRC", # nolint: object_name_linter.
  fields = list(
    title = "character", author = "character", isbn = "character",
    year = "integer", genre = "character", pages = "integer"
  ),
  methods = list(
    describe = function() {
      yr <- if (is.na(year)) "n.d." else year
      sprintf("%s (%s, %s)", title, author, yr)
    },
    show = function() {
      cat("<", class(.self)[[1L]], "> ", describe(), "\n", sep = "")
    }
  )

# The S3 book of the scenario has value semantics ...
s3_a <- book("The Quiet Streets", "Iris Fenwick", year = 1999L)
s3_b <- s3_a
s3_b$year <- 2000L
c(a = s3_a$year, b = s3_b$year)
#>    a    b
#> 1999 2000

# ... a reference class object does not.
b1 <- BookRC$new(
  title = "The Quiet Streets", author = "Iris Fenwick",
  isbn = "9780306406157", year = 1999L, genre = "Fiction", pages = 288L
)
b2 <- b1
b2$year <- 2000L
c(b1 = b1$year, b2 = b2$year)
#>   b1   b2
#> 2000 2000
identical(b1, b2)
#> [1] TRUE

# A function can change its argument, as with an environment.
reissue <- function(book, new_year) {
  book$year <- new_year
  invisible(NULL)
}
reissue(b1, 2010L)
b1
#> <BookRC> The Quiet Streets (Iris Fenwick, 2010)

# copy() makes an independent object.
b3 <- b1$copy()
b3$year <- 1950L
c(b1 = b1$year, b3 = b3$year)
#>   b1   b3
#> 2010 1950
identical(b1, b3)
#> [1] FALSE
b3
#> <BookRC> The Quiet Streets (Iris Fenwick, 1950)
----

Source: https://search.r-project.org/R/refmans/methods/html/refClass.html[R documentation: refClass]

`+b2 <- b1+` made a second name, `+b2$year <- 2000L+` changed the one object they share, and a function that receives the object, `reissue()` above, can change the caller's object although it returns nothing. Nothing like it happens with the S3 book, where `+s3_b$year <- 2000L+` creates a modified copy and leaves `s3_a` alone. To get an independent object, ask for one: `b1$copy()` makes a new object with the same field values. This is the single most common confusion about Reference Classes, and it has a mirror image: people who expect copy-on-modify are surprised by aliasing, and people who expect aliasing are surprised that `+b3 <- b1$copy()+` does not stay linked.

`$copy()` is also where a field that is itself a reference object matters. The argument `shallow = FALSE` (the default) copies such fields too, recursively; with `shallow = TRUE` the copy shares them:

[source,r]
----
BookRC <- setRefClass("BookRC", # nolint: object_name_linter.
  fields = list(title = "character", year = "integer")
)
LoanRC <- setRefClass("LoanRC", # nolint: object_name_linter.
  fields = list(loan_id = "character", book = "BookRC", member = "character")
)

b <- BookRC$new(title = "The Quiet Streets", year = 1999L)
l1 <- LoanRC$new(loan_id = "L001", book = b, member = "Ana Ruiz")

deep <- l1$copy()
shallow <- l1$copy(shallow = TRUE)

# Change the book that l1 holds.
l1$book$year <- 2000L

c(original = l1$book$year, deep = deep$book$year,
  shallow = shallow$book$year, source = b$year)
#> original     deep  shallow   source
#>     2000     1999     2000     2000

# Reassigning the field on a shallow copy does not touch the original ...
shallow$book <- BookRC$new(title = "Another", year = 1980L)

Read the `source` entry as well: it is `2000`. When a field is assigned the reference object `b`, the field holds `b` itself, not a copy of it, so `+l1$book$year <- 2000L+` changed `b`. === Inheritance and `callSuper()`

A subclass is declared with `contains = "BookRC"`. Fields and methods are inherited, a subclass may add fields, and it may override a field only with a subclass of the inherited class. The scenario's audio book adds a narrator and a length in minutes. An overriding method reaches the method it overrides with `+callSuper(...)+`. The documentation points out that the arguments of the superclass method must be supplied explicitly: there is no convention that passes them on automatically, unlike `NextMethod()` for S3 or `callNextMethod()` for S4.

[source,r]
----
BookRC <- setRefClass("BookRC", # nolint: object_name_linter.
  fields = list(
    title = "character", author = "character", isbn = "character",
    year = "integer", genre = "character", pages = "integer"
  ),
  methods = list(
    initialize = function(...) {
      initFields(...)
      invisible(.self)
    },
    describe = function() {
      yr <- if (length(year) == 0L || is.na(year)) "n.d." else year
      sprintf("%s (%s, %s)", title, author, yr)
    },
    show = function() {
      cat("<", class(.self)[[1L]], "> ", describe(), "\n", sep = "")
    }
  )
)

AudioBookRC <- setRefClass("AudioBookRC", # nolint: object_name_linter.
  contains = "BookRC",
  fields = list(narrator = "character", minutes = "integer"),

                          minutes = NA_integer_) {
      callSuper(..., narrator = narrator, minutes = minutes)
    },
    describe = function() {
      paste0(callSuper(), ", read by ", narrator, ", ", minutes, " min")
    }

)

=== Read-only fields, accessors and function fields

`Gen$accessors("member")` generated `getMember()` and `setMember()`. The documentation says that unless you like that style there is no reason to use the mechanism. == R6 with `R6Class()`

R6 is a CRAN package by Winston Chang. Its documentation describes it as an implementation of encapsulated (classical) object-oriented programming that is similar to Reference Classes but more efficient and independent of S4 and the `methods` package. The first R6 release on CRAN was 1.0.1 (2014-07-17, from the CRAN archive); version 2.0 (2014-08-19) added the `portable` option and the `$set()` method; this page was checked against R6 2.6.1, which CRAN lists as published in February 2025. R6 is an add-on package and not part of R: `library(R6)` is needed, and a package that uses it lists R6 under `Imports` in its `DESCRIPTION`.

An R6 class is defined by one call, `+R6Class(classname, public = list(...), private = list(...), active = list(...), inherit = ...)+`. Unlike `setRefClass()` it has no separate fields list and no field classes: fields and methods sit in the same `public` list, a field is declared with an initial value (`NULL` for "set later"), and every method reaches the object through `self` and the private members through `private`. The arguments:

[cols="2,5",options="header"]
|===
|Argument |Meaning (default)
|`classname` |The name of the class, used for S3 dispatch and printing.
|`public` |A list of public fields and methods.
|`private` |An optional list of private fields and methods, reached as `private$x`.
|`active` |An optional list of active-binding functions.
|`inherit` |The generator of the superclass; captured unevaluated and evaluated in `parent_env` each time an object is created.
|`lock_objects` |`TRUE`: no new members can be added to an object after creation.
|`class` |`TRUE`: a class attribute is added; `FALSE` gives a bare environment.
|`portable` |`TRUE`: members are reached with `self$x` and `private$x`; `FALSE`: by name, and `+<<-+` assigns them.
|`lock_class` |`FALSE`: if `TRUE`, `$set()` cannot add members to the generator.
|`cloneable` |`TRUE`: objects get a `$clone()` method.
|`parent_env` |The environment used as the parent of the method environments and of new objects; by default the environment where the class is defined (`parent.frame()`).
|===

Source: https://r6.r-lib.org/reference/R6Class.html[R6 package documentation: R6Class]

=== Public members, `initialize()` and printing

The R6 version of the book re-implements the same rules in the same order as the Reference Class: `initialize` trims and converts, then calls `validate()`. Because R6 fields have no declared class, the conversion with `as.integer()` is the only thing that keeps `year` an integer, and nothing stops a later `+b1$year <- "x"+`; this is the main thing the Reference Class gives that R6 does not, and the active bindings of the next subsection are how R6 restores it where it matters.

[source,r]
----
library(R6)
source("scenario.R")

BookR6 <- R6Class("BookR6", # nolint: object_name_linter.
  public = list(
    title = NULL,
    author = NULL,
    isbn = NULL,
    year = NULL,
    genre = NULL,
    pages = NULL,
    initialize = function(title, author = NA_character_,
                          isbn = NA_character_, year = NA_integer_,
                          genre = NA_character_, pages = NA_integer_) {
      self$title <- trimws(title)
      self$author <- trimws(author)
      self$isbn <- if (is.na(isbn)) isbn else normalise_isbn(isbn)
      self$year <- as.integer(year)
      self$genre <- trimws(genre)
      self$pages <- as.integer(pages)
      self$validate()
    },
    validate = function() {
      fields <- list(self$title, self$author, self$isbn,
                     self$year, self$genre, self$pages)
      if (any(lengths(fields) != 1L)) {
        stop("every field of a book must have length 1", call. = FALSE)
      }
      if (is.na(self$title) || !nzchar(self$title)) {
        stop("a book needs a title", call. = FALSE)
      }
      if (!is.na(self$isbn) && !is_valid_isbn13(self$isbn)) {
        stop("invalid ISBN-13: ", self$isbn, call. = FALSE)
      }
      if (!is.na(self$year) && self$year > 2100L) {
        stop("implausible year: ", self$year, call. = FALSE)
      }
      invisible(self)
    },
    format = function(...) {
      yr <- if (is.na(self$year)) "n.d." else self$year
      sprintf("%s (%s, %s)", self$title, self$author, yr)
    },
    print = function(...) {
      cat("<BookR6> ", self$format(), "\n", sep = "")
      invisible(self)
    }
  )
)

b1 <- BookR6$new(
  title = "  the quiet streets ", author = "Iris  Fenwick",

`+BookR6$new(...)+` creates the environment, fills it with the fields and methods, locks it and calls `initialize`. Inside methods `self` is the object, so a field is read as `self$year` and written as `+self$year <- value+` with the ordinary `+<-+` (which is why there is no `+<<-+` in R6 code and no equivalent of the Reference Class trap). A method that returns `invisible(self)` can be chained, which the shelf example below uses.

The two methods named `print` and `format` are special. R6 registers S3 methods for class `"R6"`, and `print(b1)`, autoprinting and `b1$print()` all end at the public `print` method when it exists. If it does not, `print.R6()` prints `format(x)`, and `format.R6()` calls a public `format` method when there is one and otherwise prints the default listing of the members. The arguments of `+print(x, ...)+` are passed on to `+x$print(...)+`. That is why R6 objects print through your own method: the method is found by the S3 methods that R6 provides, not by a mechanism inside the object.

=== Private members and active bindings

The `private` list holds members that are reachable only from methods, through `private$name`; the object itself does not carry them, so `b$.isbn` is `NULL`. Active bindings look like fields but call a function every time they are read or assigned: the function takes one argument, which is missing on a read and holds the right-hand side on an assignment. They are always public. The listing moves `isbn` behind an active binding that normalises and validates on assignment (the Reference Class version validates only in `initialize`) and adds a read-only `age`, computed from `year` and the scenario's fixed `shelf_today`.

[source,r]

source("scenario.R")

    title = NULL,
    author = NULL,
    year = NULL,
    genre = NULL,
    pages = NULL,
    initialize = function(title, author = NA_character_,
                          isbn = NA_character_, year = NA_integer_,
                          genre = NA_character_, pages = NA_integer_) {
      self$title <- trimws(title)
      self$author <- trimws(author)
      self$isbn <- isbn
      self$year <- as.integer(year)
      self$genre <- trimws(genre)
      self$pages <- as.integer(pages)
    }
  ),
  private = list(
    .isbn = NA_character_,
    is_blank = function(x) is.na(x) || !nzchar(x)
  ),

    isbn = function(value) {

      as.integer(format(shelf_today, "%Y")) - self$year

`class(b)` is `c("BookR6", "R6")`, `typeof(b)` is `"environment"`, and `isS4(b)` is `FALSE`: an R6 object is an ordinary S3 object. The consequence for `inherits(b, "environment")` is easy to miss. `inherits()` looks at `class(b)`, which has an explicit class attribute, so it does not see the implicit class `"environment"` and answers `FALSE` although `is.environment(b)` is `TRUE`. `inherits(b, "BookR6")` and `inherits(b, "R6")` are the tests to use, and `R6::is.R6(b)` and `R6::is.R6Class(gen)` are shortcuts for the second. The last lines of the listing show the rule for printing: a public `format()` method alone changes both `format(x)` and how the object is printed, because `print.R6()` falls back to `format(x)`.

=== Inheritance and `super`

`inherit = BookR6` makes a subclass. The expression is captured unevaluated and evaluated when an object is created, so the superclass may be defined in another package. A subclass sees the superclass through `super`: `+super$initialize(...)+` and `+super$format(...)+` call the superclass methods, which is the counterpart of `callSuper()` in Reference Classes. Unlike classical OOP in C++, a subclass can also call the private methods of its superclass through `super$`. The class vector of an object lists the whole chain, subclass first and `"R6"` last.

[source,r]
----
library(R6)

BookR6 <- R6Class("BookR6", # nolint: object_name_linter.
  public = list(
    title = NULL, author = NULL, isbn = NULL,
    year = NULL, genre = NULL, pages = NULL,
    initialize = function(title, author = NA_character_,
                          isbn = NA_character_, year = NA_integer_,
                          genre = NA_character_, pages = NA_integer_) {
      self$title <- title
      self$author <- author
      self$isbn <- isbn
      self$year <- as.integer(year)
      self$genre <- genre
      self$pages <- as.integer(pages)
    },
    format = function(...) {
      yr <- if (is.na(self$year)) "n.d." else self$year
      sprintf("%s (%s, %s)", self$title, self$author, yr)
    },
    print = function(...) {
      cat("<", class(self)[[1L]], "> ", self$format(), "\n", sep = "")

    }
  )
)

=== Cloning

R6 objects have reference semantics, so `+alias <- b+` is another name for `b` and a change through one name is seen through the other. `$clone()` makes an independent copy. The copy is _shallow_ by default: a field that holds another R6 object, an environment or a Reference Class object is copied as a reference, so the clone and the original share it. `$clone(deep = TRUE)` clones the fields that are R6 objects but, as the documentation says, not environments, Reference Class objects, or reference objects stored inside other data structures such as a list. For any other behaviour a class can define a private method `deep_clone(name, value)`, which is called once for each field and returns the value that the clone gets.

[source,r]
----
library(R6)

BookR6 <- R6Class("BookR6", # nolint: object_name_linter.
  public = list(
    title = NULL, year = NULL,
    initialize = function(title, year = NA_integer_) {
      self$title <- title
      self$year <- as.integer(year)
    }
  )
)
LoanR6 <- R6Class("LoanR6", # nolint: object_name_linter.
  public = list(
    loan_id = NULL, book = NULL, notes = NULL,
    initialize = function(loan_id, book) {
      self$loan_id <- loan_id
      self$book <- book
      self$notes <- list(book)
    }
  )
)

  deep = deep$book$year)

#>     2010     2010     2000

#> original     deep
#>     2011     2011

  inherit = LoanR6,
  private = list(
    deep_clone = function(name, value) {
      if (name == "notes") {
        lapply(value, \(x) x$clone())
      } else if (inherits(value, "R6")) {

      } else {
        value
      }
    }
  )
)

#> original     deep
#>     1900     2011

Follow the numbers. After `+l1$book$year <- 2010L+`, the original and the shallow clone both show `2010` because they hold the same book; the deep clone, made earlier, holds its own book and keeps `2000`. After `pass:c[l1$notes[[1L\]\]$year <- 2011L]` the deep clone still shows `2011`: the book inside the list `notes` was never cloned by `deep = TRUE`, so `deep$notes[[1L]]` is still `b`. `LoanDeep` fixes that with a `deep_clone` that clones the list elements and any other R6 field. The last part of the listing shows the related trap that R6 and Reference Classes share, a reference object used as a _default_: `Shared` creates one environment when the class is defined and every object gets that same environment, so `s2$log$entry` shows what `s1` wrote. The documented fix is the one in `NotShared`: declare the field as `NULL` and create the object in `initialize`.

=== Locking, `$set()`, `cloneable` and `class = FALSE`

R6 locks aggressively. The environment of an object is locked unless `lock_objects = FALSE`, so a typo cannot silently create a new field, and the methods are locked bindings. The generator can be locked with `lock_class = TRUE`; `$set()` adds a member to an unlocked generator, but only objects created afterwards have it.

[source,r]
----
library(R6)

Point <- R6Class("Point", # nolint: object_name_linter.
  public = list(x = 0, y = 0)
)
msg <- function(expr) tryCatch(expr, error = \(e) conditionMessage(e))

# lock_objects = TRUE (the default): no new members on an object.
p <- Point$new()
msg(p$z <- 1)
#> [1] "cannot add bindings to a locked environment"
p$x <- 10
p$x
#> [1] 10

# lock_objects = FALSE allows ad hoc members.
Loose <- R6Class("Loose", # nolint: object_name_linter.
  public = list(x = 0),
  lock_objects = FALSE
)
q <- Loose$new()
q$z <- 1
q$z
#> [1] 1

# Methods are locked: they cannot be replaced on an object.
Greeter <- R6Class("Greeter", # nolint: object_name_linter.
  public = list(hello = function() "hello")
)
g <- Greeter$new()
msg(g$hello <- function() "bye")
#> [1] "cannot change value of locked binding for 'hello'"

# $set() adds a member to the generator; only objects created afterwards
# get it.
Greeter$set("public", "bye", function() "bye")
older <- g
fresh <- Greeter$new()
c(older = is.null(older$bye), fresh = is.null(fresh$bye))
#> older fresh
#>  TRUE FALSE
fresh$bye()
#> [1] "bye"

Frozen <- R6Class("Frozen", # nolint: object_name_linter.
  public = list(x = 1),
  lock_class = TRUE
)
msg(Frozen$set("public", "y", 2))
#> [1] "Can't modify a locked R6 class."
Frozen$is_locked()

Frozen$unlock()
Frozen$set("public", "y", 2)
Frozen$lock()
Frozen$is_locked()
#> [1] TRUE

#> [1] FALSE

#> [1] "attempt to apply non-function"
"clone" %in% names(Point$new())
#> [1] TRUE

The messages are those of base R for locked environments and bindings (`cannot add bindings to a locked environment`, `+cannot change value of locked binding for 'hello'+`; see `lockEnvironment()` and `lockBinding()` on the https://search.r-project.org/R/refmans/base/html/bindenv.html[R documentation: bindenv] page) plus R6's own `+Can't modify a locked R6 class.+` for the generator. `cloneable = FALSE` removes the `$clone` method, so `o$clone()` fails with `attempt to apply non-function` because `o$clone` is `NULL`. `class = FALSE` returns a plain environment without the `"R6"` class attribute: the documentation notes that it avoids the class-based dispatch of `$` and so is slightly faster, but without a class attribute S3 methods, including the pretty printing, do not apply. `$set()` takes `overwrite = TRUE` to replace an existing member and, since R6 2.3.0, adds a member with a `NULL` value instead of removing it.

=== Portable and non-portable classes

By default (`portable = TRUE`) an R6 class can be inherited from another package, and every member must be reached with `self$` or `private$`. With `portable = FALSE` an R6 class behaves more like a Reference Class: members are found by name and `+<<-+` assigns them, but inheritance across packages does not work well. The difference is the enclosing environment of the methods. In a portable class each method is enclosed in a small environment that holds `self` (and `private`, `super`), and that environment's parent is given by `parent_env` (by default the environment where the class was defined); this is why an inherited method that calls a non-exported function of its own package still finds it. In a non-portable class the methods are enclosed in the object's own environment, so fields are visible by name but a subclass defined in another package cannot see the helper functions that the superclass used. The Portable article explains it with two simulated packages, which this page does not repeat.

[source,r]
----
library(R6)

# Non-portable: fields are found by name, and <<- assigns them.
Counter <- R6Class("Counter", # nolint: object_name_linter.
  portable = FALSE,
  public = list(
    n = 0L,
    increment = function() {
      n <<- n + 1L
      invisible(self)
    },
    get = function() n
  )
)
cnt <- Counter$new()
cnt$increment()$increment()
cnt$get()
#> [1] 2

# Portable (the default): the same body does not work.
Broken <- R6Class("Broken", # nolint: object_name_linter.
  public = list(
    n = 0L,
    increment = function() {
      n <<- n + 1L
      invisible(self)
    },
    get = function() n
  )
)
br <- Broken$new()
tryCatch(br$increment(), error = \(e) conditionMessage(e))
#> [1] "object 'n' not found"
tryCatch(br$get(), error = \(e) conditionMessage(e))
#> [1] "object 'n' not found"

# The portable version names the object explicitly.
Fixed <- R6Class("Fixed", # nolint: object_name_linter.
  public = list(
    n = 0L,
    increment = function() {
      self$n <- self$n + 1L
      invisible(self)
    },
    get = function() self$n
  )
)
fx <- Fixed$new()
fx$increment()$increment()
fx$get()
#> [1] 2

# In a non-portable class the methods live in the object's own
# environment, so the object is its own enclosure.
identical(environment(cnt$get), as.environment(cnt))
#> [1] TRUE
identical(environment(fx$get), as.environment(fx))
#> [1] FALSE
class(environment(fx$get))
#> [1] "environment"
ls(environment(fx$get))
#> [1] "self"
----

Source: https://r6.r-lib.org/articles/Portable.html[R6 package documentation: Portable and non-portable R6 classes]

The portable `Broken` class has the same method bodies as the non-portable `Counter`, and both of its methods fail with `+object 'n' not found+`. The Portable article points out a worse form of the same mistake: `+y <<- 20+` in a portable method assigns to a variable `y` in the global environment, and no error is raised, because `+<<-+` found no `y` to modify in the enclosing environments and created one. Reading the enclosing environments in the last four lines shows the structure: for the non-portable object the method's environment _is_ the object, for the portable one it is a separate environment that holds `self`.

=== Debugging and finalizers

The R6 Debugging article gives the tools: add `browser()` where the debugger should stop (the article warns that RStudio breakpoints do not work in R6 methods); call `debug()` on one method of one object, `debug(s$getx)`; or call the generator's `$debug("getx")`, which flags the method for objects created afterwards, and `$undebug("getx")` to stop. `trace()` can insert a breakpoint at a given place. For Reference Classes, `debug(obj$method)` and `obj$trace(what, browser)` do the same. A non-interactive script cannot answer the browser prompt, so the listing only checks the flags with `isdebugged()`. See xref:programming-languages/r/debugging.adoc[Debugging] for the interactive tools.

A _finalizer_ is a function that R runs when an object is garbage collected, and also when R exits. In R6 it is a private method named `finalize` (R6 2.4.0 allowed it to be private; 2.6.0 prints a message when it is public). In Reference Classes it is the method `finalize`, registered by the object with `atexit = TRUE`. Both are implemented with `reg.finalizer()` and are meant for releasing a resource, such as a file or a database connection, that the object owns.

[source,r]
----
library(R6)

Simple <- R6Class("Simple", # nolint: object_name_linter.
  public = list(
    x = 10,
    getx = function() self$x
  )
)

# debug() on one method of one object: nothing is run here, because a
# non-interactive script cannot answer the browser prompt.
s <- Simple$new()
isdebugged(s$getx)
#> [1] FALSE
debug(s$getx)
isdebugged(s$getx)
#> [1] TRUE
undebug(s$getx)
isdebugged(s$getx)
#> [1] FALSE

# The generator's $debug() flags the method for objects created later.
Simple$debug("getx")
isdebugged(Simple$new()$getx)
#> [1] TRUE
isdebugged(s$getx)
#> [1] FALSE
Simple$undebug("getx")
isdebugged(Simple$new()$getx)
#> [1] FALSE

# Finalizers run when the object is garbage collected, and at exit.
Resource <- R6Class("Resource", # nolint: object_name_linter.
  public = list(
    initialize = function(name) private$name <- name
  ),
  private = list(
    name = NULL,
    finalize = function() cat("closing", private$name, "\n")
  )
)
res <- Resource$new("loans.csv")
rm(res)
invisible(gc())
#> closing loans.csv

ResourceRC <- setRefClass("ResourceRC", # nolint: object_name_linter.
  fields = list(name = "character"),
  methods = list(
    finalize = function() cat("closing", name, "\n")
  )
)
res2 <- ResourceRC$new(name = "books.csv")
rm(res2)
invisible(gc())
#> closing books.csv
----

Source: https://r6.r-lib.org/articles/Debugging.html[R6 package documentation: Debugging]

The finalizer lines depend on the garbage collector: `rm()` only removes the name, and the finalizer runs at the next collection, which the explicit `gc()` forces here. In a real program the closing may happen much later, or only when R exits, so a finalizer is a safety net and not a substitute for an explicit `close()` method.

=== Performance notes

The R6 Performance article compares Reference Classes, R6 and plain environments created by a function. Its conclusions are qualitative and are worth knowing, but the numbers depend on the machine and on the versions, so this page quotes none of them. Creating a Reference Class object is much slower than creating an R6 object, the first Reference Class object in a session costs a large amount of memory that later Reference Class objects share, and reading and writing a field is slower in a Reference Class (partly because of the class check on every assignment). Within R6, a class attribute adds a small cost to `$` (so `class = FALSE` is faster), `portable = FALSE` avoids the `self$` lookup, and `cloneable = FALSE` saves the memory of the `$clone` method. The article says that for most uses these differences are negligible; choose between the systems on features, not on speed, and measure (see xref:programming-languages/r/performance-profiling-and-benchmarking.adoc[Performance, Profiling and Benchmarking]) before changing the options.

== Living with S4 and S3

Because the two systems are built on different foundations, they meet the rest of R differently. A Reference Class is an S4 class: S4 methods defined with `setMethod()` apply to its objects, `setValidity()` rules are run by `validObject()` (and, since R 3.4.0, automatically by the default initialiser), and `isVirtualClass("BookRC")` is `FALSE` while `is(b, "envRefClass")` is `TRUE`. An R6 object is an S3 object whose class attribute is `c("BookR6", "R6")`: S3 methods such as `length.BookR6`, `summary.BookR6` and `as.character.BookR6` dispatch on it, and S4 needs `setOldClass(c("BookR6", "R6"))` to treat the class as a registered old class; after that `setMethod()` and `setGeneric()` can name `"BookR6"`. The registered class is a virtual S4 class (`isVirtualClass("BookR6")` is `TRUE` in the listing): it exists so that S4 can talk about the S3 class, not to create instances.

[source,r]
----
library(R6)

# Reference classes are S4 classes: S4 methods and validity apply.
BookRC <- setRefClass("BookRC", # nolint: object_name_linter.
  fields = list(title = "character", year = "integer")
)
setMethod("length", "BookRC", function(x) 1L)
setMethod("summary", "BookRC", function(object, ...) {
  cat("RC book:", object$title, "\n")
})
invisible(setValidity("BookRC", function(object) {
  year <- object$year
  if (length(year) == 1L && !is.na(year) && year > 2100L) {
    "year is implausible"
  } else {
    TRUE
  }
}))

b <- BookRC$new(title = "Far Future", year = 2025L)
length(b)
#> [1] 1
summary(b)
#> RC book: Far Future
b$year <- 2101L
tryCatch(validObject(b), error = \(e) conditionMessage(e))
#> [1] "invalid class “BookRC” object: year is implausible"
is(b, "envRefClass")
#> [1] TRUE
existsMethod("length", "BookRC")
#> [1] TRUE

# R6 objects are ordinary S3 objects: S3 methods apply, S4 needs setOldClass.
BookR6 <- R6Class("BookR6", # nolint: object_name_linter.
  public = list(
    title = NULL,
    initialize = function(title) self$title <- title
  )
)
length.BookR6 <- function(x) 1L
summary.BookR6 <- function(object, ...) {
  cat("R6 book:", object$title, "\n")
}

r <- BookR6$new("The Quiet Streets")
length(r)
#> [1] 1
summary(r)
#> R6 book: The Quiet Streets

setOldClass(c("BookR6", "R6"))
setGeneric("shelf_label", function(x) standardGeneric("shelf_label"))
#> [1] "shelf_label"
setMethod("shelf_label", "BookR6", function(x) paste("R6:", x$title))
shelf_label(r)
#> [1] "R6: The Quiet Streets"
is(r, "BookR6")
#> [1] TRUE
isVirtualClass("BookR6")
#> [1] TRUE
----

Source: https://search.r-project.org/R/refmans/methods/html/setOldClass.html[R documentation: setOldClass]

The `setGeneric()` call prints its name, as it always does. Methods for `length()` and `summary()` can be added with `setMethod()` without creating a generic first, because the generics already exist. The documentation also says why S4 inheritance from a non-reference S4 class is a bad idea: slots are treated functionally and fields by reference, so changes to the two kinds of property behave inconsistently inside one object.

== A worked example: lending books

The scenario needs an object that lends books and takes them back, and whose log of what happened is mutated in place as the day goes by. That is state with an identity: there is one shelf, every part of the program that talks to the shelf must talk to the same one, and a function that lends a book must not have to return a new shelf. The listing builds `BookR6` objects from the valid rows of `books` (it reuses the scenario's `book()` for the cleaning and validation), puts them on a `ShelfR6`, and keeps the loan log as a private character vector. The methods that change the shelf return `invisible(self)` so that calls can be chained, and each business rule raises an error with a message of its own.

[source,r]
----
library(R6)
source("scenario.R")

BookR6 <- R6Class("BookR6", # nolint: object_name_linter.
  public = list(
    title = NULL, author = NULL, isbn = NULL, year = NULL,
    genre = NULL, pages = NULL,
    initialize = function(title, author = NA_character_,
                          isbn = NA_character_, year = NA_integer_,
                          genre = NA_character_, pages = NA_integer_) {
      b <- book(title, author, isbn, year, genre, pages)
      for (name in names(b)) {
        self[[name]] <- b[[name]]

    format = function(...) {
      sprintf("%s (%s)", self$title, self$isbn)
    }
  )
)

ShelfR6 <- R6Class("ShelfR6", # nolint: object_name_linter.
  public = list(
    initialize = function(books) {
      names(books) <- vapply(books, \(b) b$isbn, character(1L))
      private$books <- books
    },
    lend = function(isbn, member, on) {
      if (is.null(private$books[[isbn]])) {
        stop("no book with ISBN ", isbn, call. = FALSE)
      }
      if (isbn %in% names(private$out)) {
        stop("already on loan to ", private$out[[isbn]], call. = FALSE)
      }
      private$out[[isbn]] <- member
      private$record("out", isbn, member, on)
      invisible(self)
    },
    give_back = function(isbn, on) {
      if (!isbn %in% names(private$out)) {
        stop("not on loan: ", isbn, call. = FALSE)
      }
      private$record("back", isbn, private$out[[isbn]], on)
      private$out <- private$out[names(private$out) != isbn]
      invisible(self)
    },
    available = function() {
      private$books[!names(private$books) %in% names(private$out)]
    },
    history = function() private$log
  ),
  private = list(
    books = list(),
    out = character(),
    log = character(),
    record = function(what, isbn, member, on) {
      entry <- sprintf("%s %-4s %s %s", format(on), what, isbn, member)
      private$log <- c(private$log, entry)
    }
  )
)

Points to read in the output. `length(catalogue)` is `14`: fourteen of the sixteen ISBNs in `books` are valid (the scenario's reference result), and the two rows left out are the empty ISBN and the one with the wrong check digit. The chained call `+shelf$lend(...)$lend(...)+` works because `lend()` returns `invisible(self)`. `desk` is the same shelf under a second name, so `+desk$give_back(...)+` appears in `shelf$history()`; passing the shelf to a function would behave the same way. Private state (`books`, `out`, `log`) can only be read through the methods, so `history()` returns a copy of the log vector that callers can keep without affecting the shelf. The `vapply()` over `shelf$available()` is the usual way to use a list of reference objects: each element is an object with a method, and `vapply()` asks each for a string.

The same design in a Reference Class would use `fields = list(out = "character", log = "character")`, an assignment `+log <<- c(log, entry)+` in `record()`, and `+callSuper(...)+` in `initialize`. The behaviour is identical; what changes is the vocabulary of the class and the cost of creating the objects.

== When reference semantics are the right tool

Reference semantics are a tool for state that has an identity and a lifetime. A rule of thumb that fits the examples of this page: use a reference object when "the same one" matters more than "an equal one".

* *Connections and other resources.* A file, a database connection or a socket is a handle that must be opened once, used by several pieces of code and closed once. R's own connections are reference-like (see xref:programming-languages/r/connections-and-the-file-system.adoc[Connections and the File System]), and a class that owns one can open it in `initialize`, expose methods that use it, and close it in a `close()` method and, as a safety net, in `finalize`.
* *Caches and memoisation.* A cache must outlive any one call and must be shared by all callers. `IsbnCache` below keeps its state in an environment; compare it with the closure-based memoisation of xref:programming-languages/r/function-factories-and-higher-order-functions.adoc[Function Factories and Higher-Order Functions], which gets the same effect without a class.
* *Shiny and web servers.* A Shiny session and its reactive values are shared mutable objects: `reactiveValues()` returns an object that is read and written like a list but is modified in place by `+values$a <- 3+` and shared by every reactive that holds it, and modules and plumber routers hold state between requests (see xref:programming-languages/r/shiny-plumber-and-web-apis.adoc[Shiny, plumber and Web APIs]). Many of the packages in that area are themselves written with R6, as the listing below shows.
* *Stateful parsers, queues and loggers.* A tokenizer that remembers its position, a queue of members waiting for a book, a logger that appends to one file: each is an object whose methods advance or consume its state.
* *Simulation entities.* Agents that each have a position and a history, and that are updated one step at a time, are the textbook case in other languages as well.

----
library(R6)
source("scenario.R")

# A cache whose state outlives any one call.
IsbnCache <- R6Class("IsbnCache", # nolint: object_name_linter.
  public = list(
    hits = 0L,
    misses = 0L,
    initialize = function() {
      private$store <- new.env(parent = emptyenv())
    },
    is_valid = function(isbn) {
      if (exists(isbn, envir = private$store, inherits = FALSE)) {
        self$hits <- self$hits + 1L
        return(get(isbn, envir = private$store, inherits = FALSE))
      }
      self$misses <- self$misses + 1L
      result <- is_valid_isbn13(isbn)
      assign(isbn, result, envir = private$store)
      result
    },
    size = function() length(ls(private$store))
  ),
  private = list(store = NULL)
)

cache <- IsbnCache$new()

  vapply(isbns, cache$is_valid, logical(1L), USE.NAMES = FALSE)
}

The cases where reference semantics are the wrong tool are as clear:

* *Value-like data.* A `book`, a date, a money amount or a data frame is a value: two books with the same fields are the same book, and nobody wants a function to change the argument it was given. Use a list, an S3, S4 or S7 object and copy-on-modify. The S3 `book` of the scenario is the model; the table at the end of xref:programming-languages/r/s7-object-system.adoc[The S7 Object System] compares the four ways of writing it.
* *Code that is run in parallel.* Workers started with `parallel` or `future` receive a copy of an object (or a forked copy-on-write image), so changes made to a reference object in a worker never reach the parent; see xref:programming-languages/r/parallel-and-asynchronous-computing.adoc[Parallel and Asynchronous Computing].
* *Code that is saved and restored.* `saveRDS()` serialises the environment with its contents, so a restored object is a copy that no longer shares anything with the session it came from (xref:programming-languages/r/serialization-rds-rdata-and-json.adoc[Serialization: RDS, RData and JSON]).
* *Pipelines.* The native pipe `+|>+` passes the result of one step to the next, which reads naturally for functions that take and return values (xref:programming-languages/r/pipes-and-the-native-pipe.adoc[Pipes and the Native Pipe]). Methods that change one object in place are chained with `$` and `invisible(self)` instead, and mixing the two styles in one expression is confusing.
* *Anything that needs to be reasoned about locally.* When a function can change what it receives, a reader of the calling code can no longer assume that its variables keep their values. Keep the reference object small, hide its fields behind methods, and document which methods change it.

== Reference Classes or R6?

Both systems give the same capabilities in different dress. R6 is the choice in new code that needs mutable objects, for the reasons given in its documentation (lighter objects, private members, cross-package inheritance that works) and because so much infrastructure already uses it. Reference Classes remain the right tool when a class must be an S4 class (typed fields checked on every assignment, `setValidity()`, `setMethod()` on the class) or when no add-on package may be used. S4 and S7 are better choices when objects are values and behaviour is attached to functions rather than to objects.

== Where older tutorials differ

* *"R5".* Older material calls Reference Classes R5. They are not a separate system and R does not use the name; they are `setRefClass()` in the `methods` package. The R6 package was named after the joke.
* *Creating objects and adding methods.* Older tutorials create objects with `+Gen$new(...)+` or `+new("BookRC", ...)+` and add methods in separate `+Gen$methods(...)+` calls. All of that still works. Since R 3.0.0 the value of `setRefClass()` is also a function, so `+BookRC(...)+` is the same as `+BookRC$new(...)+`, and supplying the methods in the call to `setRefClass()` or in one or more `$methods()` calls has the same effect; the help page recommends the second for readability.
* *Closures with `+<<-+` as the only way to keep state.* A function that returns a list of functions sharing an environment was the classic idiom for objects with state, and it still works (see xref:programming-languages/r/scoping-environments-and-closures.adoc[Scoping, Environments and Closures]). It gives no class, no inheritance and no printing; Reference Classes and R6 are the supported ways to write classes of mutable objects.
* *The `proto` package.* Tutorials from the era before Reference Classes recommend the `proto` package for prototype-based programming (objects that inherit from other objects). It is still on CRAN, but its last release is from 2016 and R6 or Reference Classes are the usual choices now.
* *R6 in non-portable style.* Some tutorials write `portable = FALSE` everywhere, so that methods can use `x` and `+x <<- value+` without `self$`. It works in a single package and is a little faster, but it breaks inheritance across packages and, when the habit is carried into a portable class, invites the global-variable mistake described above. The R6 documentation makes portable classes the default for that reason.
* *The `lock` argument of `R6Class()`.* It was deprecated and has been removed in R6 2.6.0; use `lock_objects`.
* *Public `finalize`.* Before R6 2.4.0 a finalizer had to be public. Since 2.4.0 it can (and should) be private, and 2.6.0 prints a message for a public one.
* *`$copy()` and `$clone()` confusion.* Many tutorials show `+y <- x+` and then are surprised that `y` changes `x`; the cure is `$copy()` for Reference Classes and `$clone()` for R6, and for R6 `deep = TRUE` only when a field is another R6 object (an environment or an object in a list needs a `deep_clone` method). Both names appear in older material for the other system.
* *"Reference classes are slow, so avoid them."* The R6 performance article shows that creating a Reference Class object costs more than an R6 object and field access is slower. It does not say that Reference Classes are unusable, and R Core has not deprecated them: there is no NEWS entry about them in R 4.0.0 to 4.6.1.
* *Typed fields in R6.* Tutorials sometimes say that R6 has no way to check a field. The usual way is an active binding that validates assignment, as `isbn` does above.
