== Why leave R, and when not to

Most of R's speed already comes from compiled code. `sum()`, `+%*%+`, `sort()`, `lm()` and the arithmetic on vectors all end in C or Fortran that someone else wrote and tested, so the first answer to a slow script is usually a better use of those: vectorise, avoid growing objects, choose another algorithm, or use a package such as data.table that is compiled for that job. xref:programming-languages/r/performance-profiling-and-benchmarking.adoc[Performance, Profiling and Benchmarking] shows how to measure, and xref:programming-languages/r/vectorisation-and-iteration.adoc[Vectorisation and Iteration] covers the byte-code compiler and preallocation that make plain R loops much faster than their reputation. The manual Writing R Extensions says the same: before using `.Call()` or `.External()` it advises to consider whether interpreted code is fast enough, and whether `.C()` is enough, because the first two give much more control and impose much greater responsibilities (https://cran.r-project.org/doc/manuals/r-release/R-exts.html#Handling-R-objects-in-C[Writing R Extensions: Handling R objects in C]).

There are four good reasons to write compiled code anyway.

* **A loop that cannot be vectorised.** Each iteration depends on the previous one (a simulation, a recursive filter, a state machine, a dynamic-programming table), so the work cannot be handed to a built-in that operates on whole vectors.
* **An existing library.** A numerical routine in Fortran, a parser in C, a geometry engine in C{pp}: wrapping it is far cheaper than porting it. The xref:programming-languages/fortran/blas-lapack-and-numerical-libraries.adoc[Fortran BLAS and LAPACK page] describes the libraries R itself links.
* **Memory control.** R copies on modification (see xref:programming-languages/r/memory-and-copy-semantics.adoc[Memory and Copy Semantics]); compiled code can fill a preallocated buffer in place.
* **A data structure R does not have.** A heap, a hash table, a trie, a spatial index, kept alive between calls behind an external pointer.

The price is real. Compiled code is the one place where a mistake does not give an R error but a crash of the whole R process, or worse, a wrong answer with no message. It needs a compiler on every machine that installs the package from source, it has to be kept in step with changes of the R C API (this page's last sections), it is harder to debug, and it makes a package harder to get onto CRAN. The rule of thumb in the R community is to profile first, change the algorithm second, and write compiled code last; the example near the end of this page puts numbers on why.

== The toolchain: what R needs on each platform

R compiles C, C{pp} and Fortran with the compilers it was configured with, and it records the commands in `etc/Makeconf` inside the R installation. `R CMD config` prints any of those variables, and `R CMD SHLIB` and `R CMD INSTALL` read them, so the compiler is never named in your own build files. The script below asks whether R can find a working compiler (`pkgbuild::has_build_tools()` compiles a small C file with `R CMD SHLIB`, which is the real test), prints the shared-object extension of this platform, and prints the C, C{pp} and Fortran compiler commands R uses. On this machine the C compiler is selected with the C23 option (`-std=gnu2x` is gcc 13's spelling of it) and the C{pp} compiler with the C{pp}20 option, which are the defaults of R 4.5.0 and R 4.6.0 respectively; the version notes at the end of the page give the NEWS entries.

[source,r]
----
# Is there a compiler R can use? TRUE means make and a C compiler were found.
pkgbuild::has_build_tools(debug = FALSE)
#> [1] TRUE

# The shared-object extension of this platform.
.Platform$dynlib.ext
#> [1] ".so"

# What R was configured to compile with (the same as `R CMD config CC`).
r_bin <- file.path(R.home("bin"), "R")
for (variable in c("CC", "CXX", "FC")) {
  value <- system2(r_bin, c("CMD", "config", variable), stdout = TRUE)
  cat(sprintf("%s: %s\n", variable, value))
}
#> CC: gcc -std=gnu2x
#> CXX: g++ -std=gnu++20
#> FC: gfortran
----

Source: https://search.r-project.org/R/refmans/base/html/system2.html[R documentation: system2]

The help page of `has_build_tools()` adds that `debug = TRUE` prints extra information, and that on Windows a failure such as `R CMD config CC` returning status 127 means that Rtools is not on the `PATH` (https://pkgbuild.r-lib.org/reference/has_build_tools.html[pkgbuild package documentation: has_build_tools]). What has to be installed differs by platform.

== From C source to a loaded shared object

=== The smallest .Call function

A function called through `.Call()` takes R objects as arguments and returns one. In C, an R object of any type is a `SEXP` (a pointer to R's internal node type, described in the next section), so the function takes `SEXP` arguments and returns a `SEXP`. The smallest useful function adds two numbers. `Rf_asReal()` coerces the first element of its argument to a C `double`, and `Rf_ScalarReal()` builds a length-one numeric vector from a `double`; the header `Rinternals.h` declares both, and `R.h` the rest of the common API.

[source,c]
----
#include <R.h>
#include <Rinternals.h>

SEXP add(SEXP x, SEXP y) {
  return Rf_ScalarReal(Rf_asReal(x) + Rf_asReal(y));
}
----

Source: https://cran.r-project.org/doc/manuals/r-release/R-exts.html#Calling-_002eCall[Writing R Extensions: Calling .Call]

`R CMD SHLIB` turns the source file into a shared object. It calls `make` with R's own rules, so it uses the compiler, the flags and the link line recorded when R was built. The transcript shows the two commands it runs, with the flags shortened (the real lines carry the include directory of this R installation and about a dozen hardening and diagnostic flags) and without the first line it prints, which names the compiler version and the operating system.

[source,bash]
----
R CMD SHLIB add.c
#> gcc -std=gnu2x -I"<R_HOME>/include" -fPIC -O2 -c add.c -o add.o
#> gcc -std=gnu2x -shared -o add.so add.o -L"<R_HOME>/lib" -lR
----

Source: https://search.r-project.org/R/refmans/utils/html/SHLIB.html[R documentation: SHLIB]

The first command compiles `add.c` into an object file; the second links the object file into `add.so` against `libR`. The options come from `R CMD SHLIB --help`; the transcript is the complete help except its last line, which gives the address for bug reports (the odd "alsp" in the `--use-C17` line is in R's own text).

`R CMD SHLIB` accepts C (`.c`), C{pp} (`.cc`, `.cpp`), fixed-form Fortran (`.f`), free-form Fortran (`.f90`, `.f95`), Objective C and Objective C{pp} sources, or object files, or linker options. Files for the Fortran preprocessor (`.F`) are not accepted. The name of the shared object is taken from the first file unless `-o` is given. Two details from the manual are worth keeping in mind: `make` does not rebuild when only the flags changed (use `--preclean`), and a file named `test.c` next to `test.f` makes `R CMD SHLIB test.f` compile the C file instead (https://cran.r-project.org/doc/manuals/r-release/R-exts.html#Creating-shared-objects[Writing R Extensions: Creating shared objects]).

=== dyn.load, is.loaded and the symbol table

`dyn.load()` loads a shared object into the running R process, and `.Call()` then finds the C function by its name. The manual advises against assuming a file extension, and recommends `file.path(path1, path2, paste0("mylib", .Platform$dynlib.ext))`. The script loads `add.so`, calls the function with doubles, integers and a missing value, shows that only the first element of each argument is used (because the C code reads it with `Rf_asReal()`), and shows the two ways to be exact about which shared object a name belongs to: the `PACKAGE` argument, and a native symbol object from `getNativeSymbolInfo()`.

[source,r]
----
# Load the shared object built by `R CMD SHLIB add.c`, then call into it.
dyn.load(paste0("add", .Platform$dynlib.ext))
is.loaded("add")
#> [1] TRUE
.Call("add", 1, 2)
#> [1] 3
.Call("add", 1L, 2L)
#> [1] 3
.Call("add", NA_real_, 2)
#> [1] NA
.Call("add", c(5, 6), c(10, 20))
#> [1] 15

# Pass PACKAGE so that the search is confined to this shared object.
add <- function(x, y) .Call("add", x, y, PACKAGE = "add")
add(0.1, 0.2) == 0.3
#> [1] FALSE
add(0.1, 0.2)
#> [1] 0.3

# The loaded objects, and the symbol as an R object.
"add" %in% names(getLoadedDLLs())
#> [1] TRUE
info <- getNativeSymbolInfo("add", PACKAGE = "add")
class(info)
#> [1] "NativeSymbolInfo"
info$name
#> [1] "add"

# Unloading is rarely needed; it lets the file be rebuilt on Windows.
invisible(dyn.unload(paste0("add", .Platform$dynlib.ext)))
is.loaded("add")
#> [1] FALSE
----

Source: https://search.r-project.org/R/refmans/base/html/dynload.html[R documentation: dyn.load]

The loaded shared object is listed by `getLoadedDLLs()`, whose elements are named after the file without the extension. `dyn.unload()` removes it; the manual calls unloading unnecessary and not safe in general, but needed on some platforms (Windows) to allow the DLL to be rebuilt. Unloading a DLL and reloading a rebuilt one with the same name may not work on every platform (https://cran.r-project.org/doc/manuals/r-release/R-exts.html#dyn_002eload-and-dyn_002eunload[Writing R Extensions: dyn.load and dyn.unload]). In practice, when you edit a C file during development, restart R after rebuilding, or use `pkgload::load_all()` (below), which handles unloading for a package.

`PACKAGE` matters more than it looks. A bare `.Call("add", x, y)` asks R to search every loaded shared object, and R's search order is most recently loaded first; if two packages define a C function called `add`, the wrong one can be called, with the wrong number of arguments, and that normally crashes R. Writing R Extensions explains that `PACKAGE` confines the search and speeds it up, and the help page of `.Call` recommends it or a native symbol object for anything called often. The manual's timing section measured the difference as small but real for functions called millions of times (https://cran.r-project.org/doc/manuals/r-release/R-exts.html#Registering-native-routines[Writing R Extensions: Registering native routines]).

=== Errors from the lookup

When the name cannot be found, R says so in a message that is the same on every platform. These are the real texts, captured by `tryCatch()` (the container's directory is replaced by `<dir>` so that the script, not the page, hides the path). The last three lines show the same failure for `.C()`, `.Fortran()` and `.External()`; only `.Fortran()` says "Fortran symbol name".

[source,r]
----
dyn.load(paste0("add", .Platform$dynlib.ext))
message_of <- function(expr) {
  tryCatch(expr, error = \(e) {
    gsub(getwd(), "<dir>", conditionMessage(e), fixed = TRUE)
  })
}

# A symbol that is not in any loaded shared object.
message_of(.Call("nope"))
#> [1] "C symbol name \"nope\" not in load table"

# A symbol searched in the wrong shared object, or in one that is not loaded.
message_of(.Call("nope", PACKAGE = "add"))
#> [1] "\"nope\" not available for .Call() for package \"add\""
message_of(.Call("add", 1, 2, PACKAGE = "nosuchdll"))
#> [1] "\"add\" not available for .Call() for package \"nosuchdll\""

# A file that does not exist (the second line is the operating system's text).
message_of(dyn.load("missing.so"))
#> [1] "unable to load shared object '<dir>/missing.so':\n  <dir>/missing.so: cannot open shared object file: No such file or directory"

# The same symbol name on the other three interfaces.
message_of(.C("nope"))
#> [1] "C symbol name \"nope\" not in load table"
message_of(.Fortran("nope"))
#> [1] "Fortran symbol name \"nope\" not in load table"
message_of(.External("nope"))
#> [1] "C symbol name \"nope\" not in load table"
----

Source: https://search.r-project.org/R/refmans/base/html/CallExternal.html[R documentation: .Call]

The second line of the `dyn.load()` message is the operating system's own text (this one is glibc's), so it differs on macOS and Windows. All four lookup errors have the same remedy: check the spelling, check that the shared object was built from the current source and loaded, and check that the function is not `static` and, in C{pp}, is declared `extern "C"`.

== Handling R objects in C

=== What a SEXP is

Every R object that C code touches is a `SEXP`, a pointer to a structure the headers call `SEXPREC`. Think of it as a variant type: the same pointer type refers to a numeric vector, a list, a function, an environment, a call or `NULL`, and `TYPEOF(x)` returns a code that says which. C code must therefore check the type before it uses the data, and it gets at the data through accessor functions, never by looking inside the structure (the structure is not part of the API and its layout is allowed to change). The types that package code meets most often are these.

[cols="1,2,3",options="header"]
|===
|`TYPEOF()` code |R object |How C reads or builds it
|`REALSXP` |numeric (double) vector |`pass:c[double *REAL(x)]` or the read-only `pass:c[const double *REAL_RO(x)]`; `Rf_allocVector(REALSXP, n)`
|`INTSXP` |integer vector (also the codes of a factor) |`pass:c[int *INTEGER(x)]`, `INTEGER_RO(x)`; missing value `NA_INTEGER`
|`LGLSXP` |logical vector |`pass:c[int *LOGICAL(x)]`, `LOGICAL_RO(x)`; values 0, 1 or `NA_LOGICAL`
|`CPLXSXP` and `RAWSXP` |complex and raw vectors |`COMPLEX(x)` (an `Rcomplex` has members `r` and `i`), `RAW(x)`
|`STRSXP` |character vector |`STRING_ELT(x, i)` gives a `CHARSXP`; `CHAR()` of that gives a `pass:c[const char *]`; `SET_STRING_ELT()` stores one
|`VECSXP` |list (generic vector) |`VECTOR_ELT(x, i)`, `SET_VECTOR_ELT(x, i, v)`
|`NILSXP` |`NULL` |the constant `R_NilValue`
|`LISTSXP`, `LANGSXP` |pairlist, call |`CAR`, `CDR`, `TAG`; see `.External()` and the callback example below
|`CLOSXP`, `ENVSXP`, `SYMSXP` |function, environment, name |`Rf_isFunction()`, `Rf_eval()`, `Rf_install()`
|===

Source: https://cran.r-project.org/doc/manuals/r-release/R-exts.html#Details-of-R-types[Writing R Extensions: Details of R types]

Two types in that table deserve a remark. A `CHARSXP` is not an R-level object but the immutable, shared element of a character vector: R keeps one copy of each distinct string in a global cache, so C code must never modify the bytes behind `CHAR()`. And `LISTSXP` is the old Lisp-style pairlist; an R list is a `VECSXP`, which is why the test for an R list is `Rf_isNewList()` and not `Rf_isList()` (https://cran.r-project.org/doc/manuals/r-release/R-exts.html#Handling-lists[Writing R Extensions: Handling lists]). R Internals describes all the types, including the ones that are not for packages (https://cran.r-project.org/doc/manuals/r-release/R-ints.html#SEXPs[R Internals: SEXPs]).

=== The Rf_ prefix and R_NO_REMAP

The functions in the manual's examples carry an `Rf_` prefix (`Rf_allocVector`, `Rf_error`, `Rf_ScalarReal`), and so do all the examples on this page. R's headers also define short names for many of them (`allocVector`, `error`, `length`), which are macros that expand to the prefixed names, and those short names clash easily with system headers and other libraries. Defining `R_NO_REMAP` before any R header removes the macros and leaves only the prefixed names. The manual states the facts that matter: the prefix is optional in C code and recommended for new C code; since R 4.5.0 `R_NO_REMAP` is always defined when the R headers are included from C{pp}, so C{pp} code must use the `Rf_` names; and a package that defines it itself should guard it with `pass:c[#ifndef R_NO_REMAP]` to avoid compiler warnings about redefinition (https://cran.r-project.org/doc/manuals/r-release/R-exts.html#The-R-API[Writing R Extensions: The R API]).

The NEWS entries behind that: R 4.4.0 added the environment variable `+_R_CXX_USE_NO_REMAP_+`, which makes `R CMD INSTALL` (and so `R CMD check`) compile C{pp} code with `-DR_NO_REMAP`, and said that this was planned to become the default; R 4.5.0 made it the default and revised the manual to describe the remapped entry points (https://cran.r-project.org/doc/manuals/r-release/NEWS.html[R NEWS: Changes in R 4.4.0 and 4.5.0]). `usethis::use_c()` writes a template that starts with `pass:c[#define R_NO_REMAP]`, as the `shelf` example later shows. Two related switches exist for other headers: `R_NO_REMAP_RMATH` does the same for `Rmath.h` (the distribution functions), and `STRICT_R_HEADERS`, which removes the old S-compatibility definitions (`PI`, `Calloc`, `Realloc`, `Free` and the `+DOUBLE_*+` constants), has been the default since R 4.5.0, with `R_Calloc`, `R_Realloc`, `R_Free` and `M_PI` as the replacements.

=== A vector in, a vector out

The next file has three functions that show the pattern every `.Call()` routine follows: check or coerce the arguments, allocate the result, fill it through a pointer, copy the attributes that should survive, and return. `overdue_days()` requires a double vector and returns the days beyond the loan limit element by element; `is_late()` coerces to integers and returns a logical vector; `count_late()` calls `is_late()` and counts.

[source,c]
----
#include <R.h>
#include <Rinternals.h>

/* Days beyond the loan period, element by element; NA and NaN pass through. */
SEXP overdue_days(SEXP days, SEXP limit) {
  if (!Rf_isReal(days)) {
    Rf_error("'days' must be a double vector");
  }
  R_xlen_t n = XLENGTH(days);
  double lim = Rf_asReal(limit);
  const double *d = REAL_RO(days);
  SEXP out = PROTECT(Rf_allocVector(REALSXP, n));
  double *o = REAL(out);
  for (R_xlen_t i = 0; i < n; i++) {
    if (ISNAN(d[i])) {
      o[i] = d[i];
    } else {
      o[i] = d[i] > lim ? d[i] - lim : 0.0;
    }
  }
  SEXP nms = Rf_getAttrib(days, R_NamesSymbol);
  if (nms != R_NilValue) {
    Rf_setAttrib(out, R_NamesSymbol, nms);
  }
  UNPROTECT(1);
  return out;
}

/* TRUE when a loan is late, NA when the number of days is missing. */
SEXP is_late(SEXP days, SEXP limit) {
  SEXP d = PROTECT(Rf_coerceVector(days, INTSXP));
  int lim = Rf_asInteger(limit);
  R_xlen_t n = XLENGTH(d);
  SEXP out = PROTECT(Rf_allocVector(LGLSXP, n));
  const int *pd = INTEGER_RO(d);
  int *po = LOGICAL(out);
  for (R_xlen_t i = 0; i < n; i++) {
    po[i] = pd[i] == NA_INTEGER ? NA_LOGICAL : pd[i] > lim;
  }
  UNPROTECT(2);
  return out;
}

/* How many loans are late; missing values are not counted. */
SEXP count_late(SEXP days, SEXP limit) {
  SEXP flags = PROTECT(is_late(days, limit));
  const int *p = LOGICAL_RO(flags);
  R_xlen_t n = XLENGTH(flags);
  int total = 0;
  for (R_xlen_t i = 0; i < n; i++) {
    if (p[i] != NA_LOGICAL && p[i]) {
      total++;
    }
  }
  UNPROTECT(1);
  return Rf_ScalarInteger(total);
}
----

Source: https://cran.r-project.org/doc/manuals/r-release/R-exts.html#Handling-R-objects-in-C[Writing R Extensions: Handling R objects in C]

Several points in the file are worth a line each.

* `XLENGTH()` and `R_xlen_t` are for lengths. R vectors can be longer than 2^31 - 1 elements on 64-bit platforms (the length is a signed 64-bit integer, with a practical limit of 52 bits), and `LENGTH()` and `Rf_length()` return an `int` that cannot hold such lengths; code that loops with an `int` index works until the day someone passes a very long vector (https://cran.r-project.org/doc/manuals/r-release/R-ints.html#Long-vectors[R Internals: Long vectors]).
* `REAL_RO()` returns a `const` pointer. The vector accessors have read-only variants (`INTEGER_RO`, `LOGICAL_RO`, `DATAPTR_RO`), and for a character vector or a list only read-only access exists, because writing straight into those would break the memory manager's assumptions. The manual adds that these pointers are valid only for vectors of positive length: a zero-length vector has no data, so `memcpy()` of zero elements through such a pointer is undefined behaviour unless the length is checked first (https://cran.r-project.org/doc/manuals/r-release/R-exts.html#Vector-accessor-functions[Writing R Extensions: Vector accessor functions]). `top_days()` below guards its copy for this reason.
* `REAL(x)` is a function call, not a field access. Store the pointer in a variable before the loop, as the file does, instead of calling `REAL(x)[i]` on every iteration.
* The result is allocated with `Rf_allocVector(REALSXP, n)`. Unlike `numeric(n)` in R, `Rf_allocVector()` does not initialise the elements of an atomic vector (it only does so for lists and character vectors), so every element must be written before the object is returned.
* The names are copied explicitly, with `Rf_getAttrib()` and `Rf_setAttrib()`. Attributes are not copied automatically; a function that should keep `names`, `dim` or `class` has to do it.
* `PROTECT()` and `UNPROTECT()` bracket the lifetime of the new object; the section after next explains why.

=== Character vectors

A character vector is a `STRSXP`: a vector whose elements are `CHARSXP` nodes. Reading goes through `STRING_ELT()` and `CHAR()`; writing builds a `CHARSXP` with `Rf_mkChar()` (from a NUL-terminated C string), `Rf_mkCharLen()` (from part of a buffer) or `Rf_mkCharLenCE()` (with an encoding mark) and stores it with `SET_STRING_ELT()`. `Rf_mkString()` makes a whole length-one character vector from a C string, and `Rf_ScalarString()` from a `CHARSXP`. The function below keeps the first blank-delimited word of each string, passes `NA` through, and, because it copies the bytes of an element it did not interpret, copies the encoding mark of the original with it.

[source,c]
----
#include <string.h>
#include <R.h>
#include <Rinternals.h>

/* The first blank-delimited word of each string; NA stays NA. */
SEXP first_word(SEXP x) {
  if (!Rf_isString(x)) {
    Rf_error("'x' must be a character vector");
  }
  R_xlen_t n = XLENGTH(x);
  SEXP out = PROTECT(Rf_allocVector(STRSXP, n));
  for (R_xlen_t i = 0; i < n; i++) {
    SEXP el = STRING_ELT(x, i);
    if (el == NA_STRING) {
      SET_STRING_ELT(out, i, NA_STRING);
      continue;
    }
    const char *s = CHAR(el);
    int len = (int) strcspn(s, " \t");
    SET_STRING_ELT(out, i, Rf_mkCharLenCE(s, len, Rf_getCharCE(el)));
  }
  UNPROTECT(1);
  return out;
}
----

Source: https://cran.r-project.org/doc/manuals/r-release/R-exts.html#Handling-character-data[Writing R Extensions: Handling character data]

The encoding rules are the part of this that goes wrong in practice. A `CHARSXP` can be marked as UTF-8 or Latin-1, and the bytes behind `CHAR()` are in whatever encoding the mark says. When C code needs to interpret the characters, the manual recommends `Rf_translateChar()` (to the current locale's encoding) or `Rf_translateCharUTF8()` (to UTF-8, which almost always represents the string faithfully), because both handle any input and allocate with `R_alloc()`; and when it only moves a string unchanged, as here, it should keep the mark with `Rf_getCharCE()` and `Rf_mkCharLenCE()` (https://cran.r-project.org/doc/manuals/r-release/R-exts.html#Character-encoding-issues[Writing R Extensions: Character encoding issues]). The help page of `.C()` adds a reason to prefer `.Call()` for text: a missing string reaches `.C()` code as the text `"NA"`, which cannot be told from a real `"NA"`.

=== Lists, classes and matrices

Lists, classes and dimensions are all attributes and vectors of vectors. `loan_stats()` below builds a named list with `Rf_mkNamed()` (which takes a C array of names ended by an empty string), fills its three elements with `SET_VECTOR_ELT()`, and sets the class attribute with `Rf_classgets()`. `day_gaps()` allocates a matrix with `Rf_allocMatrix()` (column-major, like R) and sets `dimnames` to a two-element list, reusing the names of the input for both dimensions. A data frame is a list of equal-length columns with `names`, `row.names` and `class` attributes; it is simplest to build the columns in C and call `as.data.frame()` or `data.frame()` in the R wrapper (Rcpp, later, does it in one expression).

[source,c]
----
#include <R.h>
#include <Rinternals.h>

/* A classed, named list: count, mean and maximum of the non-missing days. */
SEXP loan_stats(SEXP days) {
  SEXP d = PROTECT(Rf_coerceVector(days, REALSXP));
  const double *p = REAL_RO(d);
  R_xlen_t len = XLENGTH(d);
  int n = 0;
  double sum = 0.0, max = R_NegInf;
  for (R_xlen_t i = 0; i < len; i++) {
    if (ISNAN(p[i])) {
      continue;
    }
    n++;
    sum += p[i];
    if (p[i] > max) {
      max = p[i];
    }
  }
  const char *names[] = {"n", "mean", "max", ""};
  SEXP out = PROTECT(Rf_mkNamed(VECSXP, names));
  SET_VECTOR_ELT(out, 0, Rf_ScalarInteger(n));
  SET_VECTOR_ELT(out, 1, Rf_ScalarReal(n > 0 ? sum / n : NA_REAL));
  SET_VECTOR_ELT(out, 2, Rf_ScalarReal(n > 0 ? max : NA_REAL));
  SEXP cls = PROTECT(Rf_mkString("loan_stats"));
  Rf_classgets(out, cls);
  UNPROTECT(3);
  return out;
}

/* A matrix of differences x[i] - x[j], with names(x) as both dimnames. */
SEXP day_gaps(SEXP x) {
  SEXP xr = PROTECT(Rf_coerceVector(x, REALSXP));
  R_xlen_t n = XLENGTH(xr);
  const double *p = REAL_RO(xr);
  SEXP out = PROTECT(Rf_allocMatrix(REALSXP, (int) n, (int) n));
  double *o = REAL(out);
  for (R_xlen_t j = 0; j < n; j++) {
    for (R_xlen_t i = 0; i < n; i++) {
      o[i + n * j] = p[i] - p[j];
    }
  }
  SEXP nms = Rf_getAttrib(x, R_NamesSymbol);
  if (nms != R_NilValue) {
    SEXP dn = PROTECT(Rf_allocVector(VECSXP, 2));
    SET_VECTOR_ELT(dn, 0, nms);
    SET_VECTOR_ELT(dn, 1, nms);
    Rf_setAttrib(out, R_DimNamesSymbol, dn);
    UNPROTECT(1);
  }
  UNPROTECT(2);
  return out;
}

=== Errors, warnings, output and interrupts

C code reports problems to R with `Rf_error()` and `Rf_warning()`, which take a `printf`-style format and have the same effect as `stop()` and `warning()` in R code. Output goes through `Rprintf()` (R's standard output, which a GUI console, `sink()` or a parallel worker may redirect) and `REprintf()` (R's error stream), never `printf()` to the C library's `stdout`, whose text may not appear in the console at all; writing complete lines is advised. A long loop should call `R_CheckUserInterrupt()` now and then, because no part of R can be interrupted while it runs compiled code otherwise.

[source,c]
----
#include <R.h>
#include <Rinternals.h>
#include <R_ext/Utils.h>

/* Stops on a negative value, warns about a missing one. */
SEXP checked_sqrt(SEXP x) {
  double v = Rf_asReal(x);
  if (ISNAN(v)) {
    Rf_warning("missing value, returning NA");
    return Rf_ScalarReal(NA_REAL);
  }
  if (v < 0) {
    Rf_error("'x' must be non-negative, not %g", v);
  }
  return Rf_ScalarReal(sqrt(v));
}

/* Prints a summary on standard output and a note on standard error. */
SEXP report(SEXP days) {
  SEXP d = PROTECT(Rf_coerceVector(days, REALSXP));
  R_xlen_t n = XLENGTH(d);
  Rprintf("%lld loans\n", (long long) n);
  REprintf("(note: written to the error stream)\n");
  UNPROTECT(1);
  return R_NilValue;
}

/* A long loop that can be interrupted from the console. */
SEXP busy(SEXP iterations) {
  double steps = Rf_asReal(iterations);
  double acc = 0.0;
  for (double i = 0; i < steps; i++) {
    if (((long long) i) % 1000000 == 0) {
      R_CheckUserInterrupt();
    }
    acc += 1.0;
  }
  return Rf_ScalarReal(acc);
}
----

Source: https://cran.r-project.org/doc/manuals/r-release/R-exts.html#Error-signaling[Writing R Extensions: Error signaling]

There are rules to follow in these functions. `Rf_error()` never returns: R implements it as a non-local jump (a `longjmp`) to the nearest `tryCatch()` or the top level, skipping the C code between, so nothing after the call runs: memory from `R_alloc()` is reclaimed by R on an error, memory from `R_Calloc()` is not, and R restores the protect stack by itself. The format string is a template, so a message that comes from data must go through `"%s"` (`Rf_error("%s", msg)`), or a `%` in it will be interpreted. `+Rf_errorcall(call, ...)+` and `+Rf_warningcall(call, ...)+` take the call to blame, and `R_NilValue` omits it. The script shows what R makes of them. The error is an ordinary `simpleError` whose call is that of the R function that called `.Call()`; `capture.output()` sees the `Rprintf()` line, and its `type = "message"` form sees the `REprintf()` line.

=== Calling R from C

C code can call back into R. The routine below receives a function `f`, a vector and an environment, and applies the function to each element with `Rf_lang2()` (which builds the call `f(arg)`) and `Rf_eval()`. Each intermediate object is protected, and the check of the result's type is made in C, since the function could return anything. The environment `rho` is passed from R as `environment()` because the API has no supported entry point for the current environment (the manual's table of replacements tells packages to call `environment()` in R and pass the result).

[source,c]
----
#include <R.h>
#include <Rinternals.h>

/* Call the R function f on each element of x and collect the numbers. */
SEXP map_dbl(SEXP f, SEXP x, SEXP rho) {
  if (!Rf_isFunction(f)) {
    Rf_error("'f' must be a function");
  }
  SEXP xr = PROTECT(Rf_coerceVector(x, REALSXP));
  R_xlen_t n = XLENGTH(xr);
  SEXP out = PROTECT(Rf_allocVector(REALSXP, n));
  for (R_xlen_t i = 0; i < n; i++) {
    SEXP arg = PROTECT(Rf_ScalarReal(REAL(xr)[i]));
    SEXP call = PROTECT(Rf_lang2(f, arg));
    SEXP res = PROTECT(Rf_eval(call, rho));
    if (!Rf_isNumeric(res) || XLENGTH(res) != 1) {
      Rf_error("'f' must return a single number");
    }
    REAL(out)[i] = Rf_asReal(res);
    UNPROTECT(3);
  }
  UNPROTECT(2);
  return out;
}

A callback costs as much as an R function call, so a loop that calls R on every element gives back most of what the C code saved. Callbacks are for the occasional call (an objective function in an optimiser, a user hook) rather than for the inner loop.

=== The rules that keep a .Call routine safe

The manual's rules for `.Call()` and `.External()` code can be written as a short list.

* **Treat the arguments as read-only.** `.Call()` and `.External()` do not copy their arguments, so a vector that C code modifies in place changes every R variable that shares it. R shares freely (`+y <- x+` copies nothing, as xref:programming-languages/r/assignment-names-and-values.adoc[Assignment, Names and Values] shows). Copy with `Rf_duplicate()` (or `Rf_shallow_duplicate()` when only the top level changes) before modifying, and see xref:programming-languages/r/memory-and-copy-semantics.adoc[Memory and Copy Semantics] for how R decides when a copy is needed. The macros `NAMED` and `SET_NAMED` that older books use were replaced by reference counting in R 4.0.0; package code should use `MAYBE_SHARED()`, `MAYBE_REFERENCED()`, `NO_REFERENCES()` and `MARK_NOT_MUTABLE()`, which are documented in the section on named objects and copying (https://cran.r-project.org/doc/manuals/r-release/R-exts.html#Named-objects-and-copying[Writing R Extensions: Named objects and copying]).
* **Check the types.** A wrong guess gives a segmentation fault, not an R error. Test with `TYPEOF()` or `Rf_isReal()` and friends, or coerce with `Rf_coerceVector()` (which allocates, so the result is protected) or the scalar readers `Rf_asReal()`, `Rf_asInteger()` and `Rf_asLogical()`, which ignore all but the first element, as the `add()` example showed. `Rf_asRboolean()` (R 4.5.0) is the stricter version that errors on a length other than one. Coercion in C does not dispatch on class (a factor is just an integer), so it is usually better to coerce in the R wrapper.
* **Allocate with R and protect what you allocate** (next section), and never keep a `SEXP` in a global C variable across calls unless it is registered with `R_PreserveObject()`.
* **Stay on the main thread.** The manual is explicit that the R API may be called only from the main thread of the R process; using it from another thread can corrupt memory.
* **Prefer the documented API.** The last section of the page is about which entry points are documented.

== PROTECT and UNPROTECT

=== Why objects need protecting

R frees the memory of objects automatically, by garbage collection, and it can run the collector whenever it allocates anything. An object that C code has just created and holds only in a local variable is invisible to the collector: nothing in R's own data structures refers to it, so the next allocation can free it, and the pointer in the C variable then points at memory that may be reused. The result is not an error but corrupt output or a crash, often much later and somewhere else. `PROTECT()` puts the object on a stack that the collector treats as a root, and `UNPROTECT(n)` pops the last `n` entries. Writing R Extensions states the rule precisely: it is the object that is protected, not the pointer variable, so assigning a different object to `p` after `PROTECT(p)` leaves the new object unprotected (https://cran.r-project.org/doc/manuals/r-release/R-exts.html#Handling-the-effects-of-garbage-collection[Writing R Extensions: Handling the effects of garbage collection]).

The protect stack has rules, and the manual lists four of them for functions that cooperate.

* **Balance.** `PROTECT` and `UNPROTECT` calls must balance in each function, and a function may unprotect only what it protected itself. A jump out of the function (an error, an interrupt) restores the stack automatically.
* **Callers protect arguments.** The caller keeps every argument protected for the whole call, which is why `.Call()` routines do not protect their arguments.
* **Return values are unprotected.** An object returned by a function must be protected at once by the caller, even if the callee only returned something that already existed, because it may have been duplicated.
* **Everything allocates.** Assume that any API function or macro may allocate and so may trigger a collection; the code that is safe today because a function happens not to allocate can fail after a change in R.

The simplest style follows from them: `+SEXP x = PROTECT(Rf_allocVector(...));+` on creation, one `UNPROTECT(n)` before every `return`, with `n` the number of objects protected in that function. The stack has a fixed size (10,000 entries by default), so a loop must not protect something new on every iteration without releasing it, and the better design is to store objects in a protected container (a list) or to unprotect them immediately after use. `callback.c` above does exactly that: it protects three objects inside the loop and `UNPROTECT(3)` at the end of each iteration. Anything allocated and handed straight to `SET_VECTOR_ELT()` or `SET_STRING_ELT()` is safe from then on, as `loan_stats()` shows.

=== Changing a protected value: PROTECT_WITH_INDEX

The rule that the object is protected, and not the pointer, means that code that replaces a protected object (by coercing, duplicating or growing it) must protect the replacement. When the old object is no longer needed, `PROTECT_WITH_INDEX(s, &ipx)` records the stack position and `REPROTECT(s, ipx)` stores a new object in that position, so the stack does not grow. `total_days()` below coerces an integer argument to double only if it needs to, and keeps whichever object it ends up using protected under one index.

[source,c]
----
#include <R.h>
#include <Rinternals.h>

/* Bug: one PROTECT too many, so the protect stack is one entry deeper. */
SEXP leaky(SEXP x) {
  SEXP out = PROTECT(Rf_allocVector(REALSXP, 1));
  REAL(out)[0] = Rf_asReal(x) * 2.0;
  return out;
}

/* Bug: one UNPROTECT too many, so the caller's entry is dropped. */
SEXP too_many(SEXP x) {
  SEXP out = PROTECT(Rf_allocVector(REALSXP, 1));
  REAL(out)[0] = Rf_asReal(x) * 2.0;
  UNPROTECT(2);
  return out;
}

/* Correct: the coerced copy replaces the protected value in place. */
SEXP total_days(SEXP x) {
  PROTECT_INDEX ipx;
  SEXP v = x;
  PROTECT_WITH_INDEX(v, &ipx);
  if (TYPEOF(v) != REALSXP) {
    REPROTECT(v = Rf_coerceVector(v, REALSXP), ipx);
  }
  double total = 0.0;
  const double *p = REAL_RO(v);
  for (R_xlen_t i = 0; i < XLENGTH(v); i++) {
    total += p[i];
  }
  UNPROTECT(1);
  return Rf_ScalarReal(total);
}
----

Source: https://cran.r-project.org/doc/manuals/r-release/R-exts.html#Handling-the-effects-of-garbage-collection[Writing R Extensions: Handling the effects of garbage collection]

The file also contains the two classic mistakes, in functions that compile without a warning and return the right number: `leaky()` has one `PROTECT()` too many (it forgot `UNPROTECT(1)`), and `too_many()` has one `UNPROTECT()` too many. `.Call()` checks the protect stack when a routine returns, and when the count has changed it prints a warning. The text of that warning is real; the two numbers are the size of the protect stack before and after the call, so they depend on how deeply R is nested at that moment, and the values below are the ones from a top-level `Rscript` run. A leak makes the second number larger, an excess `UNPROTECT()` makes it smaller. The messages are written directly to the error stream when the routine returns, before the value is printed, so they are not conditions: `+tryCatch(..., warning = )+` and `withCallingHandlers()` do not see them (in this test the handler did not run). The wrong routines still return `2`.

The messages catch only a mismatch in the count. A missing `PROTECT()` is silent until the collector runs at the wrong moment, and that is much harder to find. === R_PreserveObject and the other ways to keep an object alive

`PROTECT()` is for the duration of one call. An object that has to survive between calls (a cache, a handle returned to R as an external pointer) is kept alive with `R_PreserveObject(x)` and released with `R_ReleaseObject(x)`; the manual calls this less efficient than normal protection and to be used sparingly, because releasing it is then the author's responsibility, usually from a finalizer. For parsers there is a multi-set interface (`R_NewPreciousMSet`, `R_PreserveInMSet`, `R_ReleaseFromMSet`), and the old `UNPROTECT_PTR()` is dangerous to mix with `UNPROTECT()` and is not for new code. External pointers, which wrap a C pointer in an R object with a finalizer, are the way to return a C data structure to R, and have their own section (https://cran.r-project.org/doc/manuals/r-release/R-exts.html#External-pointers-and-weak-references[Writing R Extensions: External pointers and weak references]).

== Memory allocation: R_alloc and R_Calloc

C code needs memory that is not an R object: a scratch buffer, a working copy. R provides two families, and the difference is who cleans up (https://cran.r-project.org/doc/manuals/r-release/R-exts.html#Memory-allocation[Writing R Extensions: Memory allocation]).

|Function |Lifetime |Use it for

Source: https://cran.r-project.org/doc/manuals/r-release/R-exts.html#Memory-allocation[Writing R Extensions: Memory allocation]

`memory.c` shows both. `median_days()` copies the non-missing values into an `R_alloc()` buffer, sorts it with `R_rsort()` (R's own sort for doubles) and reads the middle; `top_days()` sorts a copy held in an `R_Calloc()` buffer and frees it with `R_Free()` before returning. A check on the length precedes the `Memcpy()`, for the reason given above about zero-length vectors. Memory from `R_Calloc()` does not necessarily come from the same pool as `malloc()`, so it must not be passed to `free()` or `strdup()`.

[source,c]
----
#include <R.h>
#include <Rinternals.h>
#include <R_ext/Utils.h>

/* Median of the non-missing days: scratch space from R_alloc. */
SEXP median_days(SEXP days) {
  SEXP d = PROTECT(Rf_coerceVector(days, REALSXP));
  R_xlen_t n = XLENGTH(d);
  const double *p = REAL_RO(d);
  double *buf = (double *) R_alloc((size_t) n, sizeof(double));
  R_xlen_t m = 0;
  for (R_xlen_t i = 0; i < n; i++) {
    if (!ISNAN(p[i])) {
      buf[m++] = p[i];
    }
  }
  double med = NA_REAL;
  if (m > 0) {
    R_rsort(buf, (int) m);
    med = (m % 2 == 1) ? buf[m / 2] : 0.5 * (buf[m / 2 - 1] + buf[m / 2]);
  }
  UNPROTECT(1);
  return Rf_ScalarReal(med);
}

/* The k largest values, in decreasing order: a buffer from R_Calloc. */
SEXP top_days(SEXP days, SEXP k) {
  SEXP d = PROTECT(Rf_coerceVector(days, REALSXP));
  R_xlen_t n = XLENGTH(d);
  int kk = Rf_asInteger(k);
  if (kk == NA_INTEGER || kk < 0) {
    Rf_error("'k' must be a non-negative integer");
  }
  if (kk > n) {
    kk = (int) n;
  }
  double *buf = R_Calloc((size_t) n, double);
  if (n > 0) {
    Memcpy(buf, REAL_RO(d), (size_t) n);
  }
  R_rsort(buf, (int) n);
  SEXP out = PROTECT(Rf_allocVector(REALSXP, kk));
  for (int i = 0; i < kk; i++) {
    REAL(out)[i] = buf[n - 1 - i];
  }
  R_Free(buf);
  UNPROTECT(2);
  return out;
}
----

== Registering native routines

=== The ISBN check as a .Call routine

So far every routine was found by its name, by searching the symbols of the shared object. The rest of the page uses one routine as its running example: the ISBN-13 check of the `shelf` package. It takes a character vector and returns a logical vector. Its rule is the one `is_valid_isbn13()` implements in R: keep the digits, reject an `X`, require exactly 13 digits, and require that the digits multiplied alternately by 1 and 3 add up to a multiple of 10. `NA` and the empty string are `FALSE`. The file has a header with the prototype, and starts with `pass:c[#define R_NO_REMAP]`, so every R function in it carries the `Rf_` prefix. The constant `ISBN_DIGITS` has a default and can be overridden from the compiler command line, which the `src/Makevars` section uses.

[source,c]
----
#define R_NO_REMAP
#include <ctype.h>
#include <R.h>
#include <Rinternals.h>
#include "isbn.h"

#ifndef ISBN_DIGITS
#define ISBN_DIGITS 13
#endif

/* One string: keep the digits, reject an X, weight 1 and 3 alternately. */
static int valid_isbn(const char *s) {
  int n = 0, sum = 0;
  for (; *s != '\0'; s++) {
    if (isdigit((unsigned char) *s)) {
      if (n == ISBN_DIGITS) {
        return 0;
      }
      sum += (*s - '0') * (n % 2 == 0 ? 1 : 3);
      n++;
    } else if (*s == 'X' || *s == 'x') {
      return 0;
    }
  }
  return n == ISBN_DIGITS && sum % 10 == 0;
}

/* Vectorised: FALSE for NA, for the empty string and for a wrong check digit. */
SEXP isbn13_valid(SEXP x) {
  if (!Rf_isString(x)) {
    Rf_error("'x' must be a character vector");
  }
  R_xlen_t n = XLENGTH(x);
  SEXP out = PROTECT(Rf_allocVector(LGLSXP, n));
  int *po = LOGICAL(out);
  for (R_xlen_t i = 0; i < n; i++) {
    SEXP el = STRING_ELT(x, i);
    po[i] = el != NA_STRING && valid_isbn(CHAR(el));
  }
  UNPROTECT(1);
  return out;
}
----

=== R_registerRoutines and R_init_<name>

Registration replaces the search by a table that the shared object builds when it is loaded. When R loads `foo.so`, it looks for a function named `R_init_foo` and calls it with a `DllInfo` pointer; when it unloads the object, it calls `R_unload_foo` if there is one. The name is made from the file name without its extension, so it must be a valid part of a C identifier: the manual advises ASCII letters, digits and underscores only. The initialiser calls `R_registerRoutines()` with five arguments: the `DllInfo`, and one NULL-terminated array for each interface, in the order `.C()`, `.Call()`, `.Fortran()`, `.External()`. The array element types are `R_CMethodDef`, `R_CallMethodDef`, `R_FortranMethodDef` and `R_ExternalMethodDef`. Each entry holds the name by which R refers to the routine, a function pointer cast to `DL_FUNC`, and the number of arguments; `.External()` routines use `-1` for "any number". The entries for `.C()` and `.Fortran()` may add an array of argument types (`REALSXP`, `INTSXP`, `LGLSXP`, `STRSXP`, `VECSXP`, `SINGLESXP`) that R checks on every call.

[source,c]
----
#include <R.h>
#include <Rinternals.h>
#include <R_ext/Rdynload.h>
#include "isbn.h"

static const R_CallMethodDef call_methods[] = {
  {"isbn13_valid", (DL_FUNC) &isbn13_valid, 1},
  {NULL, NULL, 0}
};

void R_init_shelf(DllInfo *dll) {
  R_registerRoutines(dll, NULL, call_methods, NULL, NULL);
  R_useDynamicSymbols(dll, FALSE);
  R_forceSymbols(dll, TRUE);
}
----

Source: https://cran.r-project.org/doc/manuals/r-release/R-exts.html#Registering-native-routines[Writing R Extensions: Registering native routines]

Two more calls close the loophole of finding things by string. `R_useDynamicSymbols(dll, FALSE)` says that the shared object is not to be searched for symbols not in the table, so `.Call("name")` finds only registered names. `R_forceSymbols(dll, TRUE)` says that foreign function calls into this object must name the entry point with an R object (a native symbol object), and not with a character string at all. The manual's example uses a package `mypkg` with a registered routine `reg` and an unregistered `unreg`: without registration both `.Call("reg")` and `.Call("unreg")` work; with `R_useDynamicSymbols(dll, FALSE)` only the first does; with `useDynLib(mypkg, .registration = TRUE, .fixes = "C_")` in `NAMESPACE`, `.Call(C_reg)` works too; and with `R_forceSymbols(dll, TRUE)` only `.Call(C_reg)` works. That last arrangement is what a package normally wants: all its own calls go directly to its own code, and nobody finds its entry points by accident. A user who needs one from outside, for debugging, can write `.Call(mypkg:::C_reg)`.

The next script builds this object as `shelf.so` (`R CMD SHLIB -o shelf.so isbn.c init.c`; the file name makes `R_init_shelf()` the initialiser), loads it next to the unregistered `isbn.so`, and shows the registered routine as an R object, the call by object, the call by string on the unregistered object, and what the two registered-only settings do to the string calls and to a wrong number of arguments. The object returned by `getDLLRegisteredRoutines()` lists the table; `routines$.Call$isbn13_valid` is a native symbol object.

[source,r]
----
# Built with `R CMD SHLIB isbn.c` and `R CMD SHLIB -o shelf.so isbn.c init.c`.

dyn.load(paste0("shelf", .Platform$dynlib.ext))
isbns <- c("978-0-306-40615-7", "978-0-01-100112-9", NA)

class(routines)

names(routines)
#> [1] ".C"        ".Call"     ".Fortran"  ".External"
routines$.Call
#>              numParameters
#> isbn13_valid             1

class(info)
#> [1] "CallRoutine"      "NativeSymbolInfo"
names(info)
#> [1] "name"          "address"       "dll"           "numParameters"

#> [1] "isbn13_valid"

#> [1] 1

#> [1]  TRUE FALSE FALSE

#> [1]  TRUE FALSE FALSE

=== The skeleton generator

`tools::package_native_routine_registration_skeleton()` writes the `init.c` for you. It reads the R code of a package for `.C()`, `.Call()`, `.Fortran()` and `.External()` calls, takes the routine names and the number of arguments from the calls, and prints C source with the `FIXME` comment that reminds you to check the declarations against the C code. NEWS for R 3.4.0 says it automated registration for over 90% of the CRAN packages that lacked it, and that many of its failures were real bugs in the packages: dozens called entry points with varying numbers of arguments or entry points that were not there. The script builds a throwaway package whose R code still calls `.Call("isbn13_valid", x, PACKAGE = "shelf")` and runs the tool on it.

[source,r]
----
# A throwaway package whose R code still calls the C routine by name.
pkg <- file.path(tempdir(), "shelf")
dir.create(file.path(pkg, "R"), recursive = TRUE)
writeLines(
  c(
    "is_valid_isbn13_c <- function(x) {",
    '  .Call("isbn13_valid", x, PACKAGE = "shelf")',
    "}"
  ),
  file.path(pkg, "R", "isbn-c.R")
)
writeLines(
  c("export(is_valid_isbn13_c)", "useDynLib(shelf)"),
  file.path(pkg, "NAMESPACE")
)
writeLines(
  c(
    "Package: shelf", "Version: 0.1.0", "Title: Skeleton",
    "Description: Skeleton.", "License: MIT"
  ),
  file.path(pkg, "DESCRIPTION")
)

# The tool reads the R code and prints a registration skeleton to the console.
tools::package_native_routine_registration_skeleton(pkg)

#> #include <R_ext/Rdynload.h>
#>
#> /* FIXME:
#>    Check these declarations against the C/Fortran source code.
#> */
#>
#> /* .Call calls */
#> extern SEXP isbn13_valid(SEXP);

#> static const R_CallMethodDef CallEntries[] = {
#>     {"isbn13_valid", (DL_FUNC) &isbn13_valid, 1},

The output is the starting point, not the end: the prototype `extern SEXP isbn13_valid(SEXP);` is guessed from the call and belongs in a header (as `isbn.h` here), the argument counts have to be checked, and `R_forceSymbols()` is not added. The manual's walk-through of converting the splines package lists the remaining steps: add `useDynLib(pkg, .registration = TRUE)` to `NAMESPACE`; change `+.Call("name", ..., PACKAGE = "pkg")+` calls to `+.Call(name, ...)+` with the R object; add `R_useDynamicSymbols(dll, FALSE)` and then `R_forceSymbols(dll, TRUE)`; and consider hiding the C functions from the symbol table (https://cran.r-project.org/doc/manuals/r-release/R-exts.html#Example_003a-converting-a-package-to-use-registration[Writing R Extensions: Example: converting a package to use registration]). Hiding is done with `attribute_hidden` on each function, or with `PKG_CFLAGS = $(C_VISIBILITY)` in `src/Makevars` together with `attribute_visible` on `R_init_pkg` alone (https://cran.r-project.org/doc/manuals/r-release/R-exts.html#Controlling-visibility[Writing R Extensions: Controlling visibility]); it removes any chance of a name clash and speeds up loading slightly. Fortran entry points cannot use `attribute_hidden`; the variable `F_VISIBILITY` does the job for them.

=== useDynLib in NAMESPACE

The `NAMESPACE` file loads the shared object and, with `.registration = TRUE`, creates in the package's namespace one R variable for each registered routine. The directive has more forms, all from the manual.

[cols="2,3",options="header"]
|===
|`NAMESPACE` directive |Effect
|`useDynLib(shelf)` |Loads `shelf.so` when the namespace is loaded. Calls still use `PACKAGE = "shelf"` and strings.
|`pass:c[useDynLib(shelf, .registration = TRUE)]` |Loads the object and defines an R variable for every registered routine, named as registered (`isbn13_valid`), so code can say `.Call(isbn13_valid, x)`.
|`pass:c[useDynLib(shelf, .registration = TRUE, .fixes = "C_")]` |As above with a prefix: the variable is `C_isbn13_valid`. `stats` uses this, which is why its code reads `+.C(C_pansari, ...)+`. `KernSmooth` uses `.fixes = "F_"` for Fortran.
|`useDynLib(shelf, isbn13_valid)` or `useDynLib(shelf, sym = isbn13_valid)` |Looks up the listed symbols once, at load time, and defines variables for them (optionally renamed). Superseded by registration.
|`dll = useDynLib(shelf)` |Also assigns the DLL object to the variable `dll`, so `.Call(dll$isbn13_valid, x)` looks the symbol up at each call.
|===

Source: https://cran.r-project.org/doc/manuals/r-release/R-exts.html#useDynLib[Writing R Extensions: useDynLib]

The manual adds a caution: using `.registration` or `.fixes` for a package that does not register its routines only slows loading, and once routines are registered, the new R variables must not be exported by accident by an `exportPattern()` in `NAMESPACE`. With roxygen2 the directive is written in the R sources as `pass:c[@useDynLib shelf, .registration = TRUE]` (and the same for the `.fixes` argument), usually in the package-level help file, and `devtools::document()` copies it into `NAMESPACE`. The next section does exactly that, and `usethis::use_c()` and `usethis::use_rcpp()` print the lines to paste.

R also checks all of this. `R CMD check` tests every foreign function call for a `PACKAGE` argument, or a way to deduce the DLL, and `tools::checkFF()` reports the cases that need attention (https://search.r-project.org/R/refmans/tools/html/checkFF.html[R documentation: checkFF]). Since R 3.4.0, `R CMD check --as-cran` notes a package that neither registers its routines nor declares what it does about symbol search. The environment variable `+_R_CHECK_NATIVE_ROUTINE_REGISTRATION_+` makes `R CMD check` report packages whose DLL lacks the registration entry points (it needs the `nm` utility on the `PATH`, and `objdump` on Windows); the section on tools in R Internals documents it (https://cran.r-project.org/doc/manuals/r-release/R-ints.html#Tools[R Internals: Tools]). The real report is shown in the section on the C API, from a package that fails it.

== Compiled code in a package: the shelf example

A package that contains compiled code has a `src/` directory. `R CMD INSTALL` builds it with the same `R CMD SHLIB` machinery as above: when `src/` has sources with a known extension, or a `Makevars` file, and no `Makefile`, it reads `Makevars` first, then R's system makefile, then the user's personal Makevars, compiles every source file in `src/` and links them into `shelf.so` (or `shelf.dll`). The shared object is installed in the `libs/` directory of the installed package, and `useDynLib` in `NAMESPACE` loads it with the namespace. A `src/Makefile`, if present, replaces this mechanism; the manual says a `Makevars` is better and a `Makefile` should be needed only exceptionally (https://cran.r-project.org/doc/manuals/r-release/R-exts.html#Creating-shared-objects[Writing R Extensions: Creating shared objects]). Package structure in general is the subject of xref:programming-languages/r/creating-packages.adoc[Creating Packages], namespaces of xref:programming-languages/r/packages-libraries-and-namespaces.adoc[Packages, Libraries and Namespaces], and documentation and roxygen2 of xref:programming-languages/r/documentation-with-rd-roxygen2-and-vignettes.adoc[Documentation with Rd, roxygen2 and Vignettes].

The `shelf` package of those pages has an R function `is_valid_isbn13()`. This section adds a C version, `is_valid_isbn13_c()`, to a copy of the package: the files `isbn.c`, `isbn.h` and `init.c` shown above, a two-line `src/Makevars`, an R wrapper, and the `useDynLib` directive. The Rcpp version of the same function is a second copy, later. Paths in the transcripts are shortened to `+~/shelf+`.

== src/Makevars and the compiler flags

`src/Makevars` is a makefile fragment that `R CMD SHLIB` includes before R's own `Makeconf`. It is the place for settings that the package needs, and it is not the place for settings that belong to the person or the machine that builds it. The manual lists the variables.

[cols="1,3",options="header"]
|===
|Variable |Use
|`PKG_CPPFLAGS` |Preprocessor options for C and C{pp} files: `-I` include paths, `-D` and `-U` definitions, `-include`, `-pthread`. Include paths belong here and not in `PKG_CFLAGS` or `PKG_CXXFLAGS`: there a platform include path can take precedence, which has caused hard-to-debug failures.
|`PKG_CFLAGS`, `PKG_CXXFLAGS`, `PKG_FFLAGS`, `PKG_FCFLAGS` |Extra compiler flags for C, C{pp}, fixed-form Fortran and free-form Fortran. `PKG_FCFLAGS` exists for the rare package that needs different flags for the two Fortran forms.
|`PKG_LIBS` |Linker options: `-L` and `-l` for libraries the code uses. Macros from R's `Makeconf` are available for numerical code: `LAPACK_LIBS`, `BLAS_LIBS` and `FLIBS`, which must appear in that order; `FLIBS` is added automatically when the package has Fortran sources.
|`CXX_STD` |The C{pp} standard: `CXX17`, `CXX20`, `CXX23` or `CXX26` (not a make directive: no quotes, no trailing comment). For C there is no variable; the standard is set in `SystemRequirements` as `USE_C17` or `USE_C23` for a package that depends on `R (>= 4.3.0)`.
|`OBJECTS` |The list of object files to build, when the package does not want every source in `src/` (for example to include files from subdirectories). If `Makevars` sets it, `R CMD SHLIB` does not.
|`C_VISIBILITY`, `CXX_VISIBILITY`, `F_VISIBILITY` |Macros from R's `Makeconf` that hold the compiler's flag for hiding symbols; used as `PKG_CFLAGS = $(C_VISIBILITY)`.
|`SHLIB_OPENMP_CFLAGS`, `SHLIB_OPENMP_CXXFLAGS`, `SHLIB_OPENMP_FFLAGS` |The OpenMP flags for the compiler R was built with; see below.
|===

Source: https://cran.r-project.org/doc/manuals/r-release/R-exts.html#Using-Makevars[Writing R Extensions: Using Makevars]

`src/Makevars` is read on Linux and macOS; on Windows `Makevars.win` is read instead, and since R 4.2.0 `Makevars.ucrt` is preferred to `Makevars.win` when both exist (NEWS for R 4.2.0, which also added `Makefile.ucrt`, `configure.ucrt` and `cleanup.ucrt`). A `configure` script that writes `Makevars` from `Makevars.in` is the next step when the package has to adapt to the system. The Makevars of the `shelf` package is two lines, a comment and a definition. `PKG_CPPFLAGS = -DISBN_DIGITS=13` is a preprocessor option and so belongs in that variable; it passes the digit count to `isbn.c`, which has `pass:c[#ifndef ISBN_DIGITS]` to supply a default when the file is compiled alone.

[source,text]
----
# Preprocessor definitions belong in PKG_CPPFLAGS, not in the compiler flags.
PKG_CPPFLAGS = -DISBN_DIGITS=13
----

Source: https://cran.r-project.org/doc/manuals/r-release/R-exts.html#Using-Makevars[Writing R Extensions: Using Makevars]

=== Why a package must not set -Wall

The manual says in so many words not to put compiler-specific diagnostic flags in a distributed `Makevars`: `-O2`, `-Wall`, `-pedantic` and every other `-W` flag are specific to GCC and compilers that copy its options (for Oracle's compilers, `-W` flags passed arguments to compiler phases). Variables such as `CPPFLAGS` and `CFLAGS` themselves must not be set at all, because users and sites set them. `R CMD check` enforces this. This is the real output of `R CMD check --as-cran` on a deliberately wrong tiny package (`probe`, shown in the section on the C API) whose `src/Makevars` is the single line `PKG_CFLAGS = -Wall -O3`:

[source,text]
----
* checking compilation flags in Makevars ... WARNING
Non-portable flags in variable 'PKG_CFLAGS':
  -Wall -O3

Source: https://cran.r-project.org/doc/manuals/r-release/R-exts.html#Using-Makevars[Writing R Extensions: Using Makevars]

The right place for warnings is the developer's own Makevars file. The manual encourages package developers to enable a reasonable amount of compiler diagnostics this way, for example `-Wall -pedantic` for GCC and LLVM. The personal file is `+~/.R/Makevars+` (or `+~/.R/Makevars-<platform>+`, or `Makevars.win` on Windows), or any file named by the environment variable `R_MAKEVARS_USER`; there is also a site-wide `Makevars.site` and `R_MAKEVARS_SITE`; the R FAQ answers the question of changing flags in one short entry that points to the same manual section (https://cran.r-project.org/doc/FAQ/R-FAQ.html#How-can-I-change-compilation-flags_003f[R FAQ 8.4: How can I change compilation flags?]). The file used for every example on this page (its path given with `R_MAKEVARS_USER` for the test run) is:

[source,text]
----
CFLAGS = -O0 -Wall -pedantic
CXXFLAGS = -O0 -Wall -pedantic
FFLAGS = -O0 -Wall -pedantic
FCFLAGS = -O0 -Wall -pedantic
----

Source: https://cran.r-project.org/doc/manuals/r-release/R-admin.html#Customizing-package-compilation[R Installation and Administration: Customizing package compilation]

It sets the flags for all four compilers (the variables are `CFLAGS`, `CXXFLAGS`, `FFLAGS` and `FCFLAGS`) and switches off optimisation so that the compiler's analysis is simple. When the C standard or C{pp} standard is non-default the matching variable (`C17FLAGS`, `CXX20FLAGS`, and so on) must be set instead. The effect is easy to see on a file that is sloppy in the way `-Wall` catches:

[source,c]
----
#include <R.h>
#include <Rinternals.h>

SEXP double_it(SEXP x) {
  int unused = 0;
  return Rf_ScalarReal(2.0 * Rf_asReal(x));
}
----

Source: https://cran.r-project.org/doc/manuals/r-release/R-exts.html#Using-Makevars[Writing R Extensions: Using Makevars]

[source,bash]
----

#> sloppy.c: In function ‘double_it’:
#> sloppy.c:5:7: warning: unused variable ‘unused’ [-Wunused-variable]
#>     5 |   int unused = 0;
#>       |       ^~~~~~
#> gcc -std=gnu2x -shared -o sloppy.so sloppy.o -L"<R_HOME>/lib" -lR

Source: https://cran.r-project.org/doc/manuals/r-release/R-admin.html#Customizing-package-compilation[R Installation and Administration: Customizing package compilation]

The `-Wextra` flag is stricter than `-Wall` and is worth trying, with one known exception: the idiom `+(DL_FUNC) &name+` in a registration table converts a function pointer to another function pointer type, and `-Wextra` (through `-Wcast-function-type`) reports it on each entry. That is why the file above uses `-Wall -pedantic`. All the C, C{pp} and Fortran files in this page were built with these flags and produced no warning.

=== The C{pp} standard: CXX_STD

R compiles package C{pp} code with a standard that depends on the R version, and the manual's advice is to say which standard the code needs. The NEWS entries are: R 4.3.0 changed the default to C{pp}17 where available (C{pp}14 or C{pp}11 otherwise); the manual says that from R 4.4.0 only a C{pp}17 compiler is selected as the default; R 4.6.0 changed the default to C{pp}20 where available, and otherwise C{pp}17, and C{pp}11 and C{pp}14 are no longer supported; and packages can request C{pp}17 if they need it. Newer standards (C{pp}23, C{pp}26) can be requested as the compiler allows. The request is made in two places that must agree: `CXX_STD = CXX17` in `src/Makevars` (and `Makevars.win`, `Makevars.ucrt`), and `pass:c,a[SystemRequirements: C{pp}17]` in `DESCRIPTION`; if they differ, `SystemRequirements` wins, and `R CMD check` checks that they match. Code that wants a feature of a newer standard should test for it, with the standard's feature-test macros, rather than assume it.

The next pair of runs makes this visible. `std.cpp` returns the value of `+__cplusplus+` that its compiler saw, and a constant that comes from the command line.

[source,cpp]
----
#define R_NO_REMAP
#include <R.h>
#include <Rinternals.h>

#ifndef LOAN_DAYS
#define LOAN_DAYS 21
#endif

/* The language standard the compiler was asked for, as 201703 or 202002. */
extern "C" SEXP cpp_standard() {
  return Rf_ScalarInteger((int) __cplusplus);
}

/* A value injected from the command line by -DLOAN_DAYS=... */
extern "C" SEXP loan_days_default() {
  return Rf_ScalarInteger(LOAN_DAYS);
}
----

Source: https://cran.r-project.org/doc/manuals/r-release/R-exts.html#Using-C_002b_002b-code[Writing R Extensions: Using C{pp} code]

[source,text]
----
CXX_STD = CXX17
PKG_CPPFLAGS = -DLOAN_DAYS=28
----

Source: https://cran.r-project.org/doc/manuals/r-release/R-exts.html#Using-Makevars[Writing R Extensions: Using Makevars]

Built in a directory with no `Makevars`, the compiler uses R's default; built in a directory with the file above, `R CMD SHLIB` honours `CXX_STD` and `PKG_CPPFLAGS`. The compile line of the second build is

=== C standards, and the Fortran and OpenMP variables

For C, R 4.5.0 made the configure script choose a compiler option that selects C23 when one is available (gcc 15 defaults to C23 on its own). The effect on package code is stricter C: `bool`, `true` and `false` are keywords, K&R-style declarations are gone, and an empty parameter list now means no parameters, so code that relied on an unprototyped declaration can stop compiling. A package that cannot move can ask for an older standard with `USE_C17` (or `USE_C99`, `USE_C90`) in `SystemRequirements`, and a user can force one when installing with `R CMD INSTALL --use-C17`; the same option exists for `R CMD SHLIB`, as its help shows. The `+__STDC_VERSION__+` macro tells which standard the compiler claims (`202311L` for C23; some compilers used `202000L` for a draft), but the manual advises testing for the feature the code needs and not the version (https://cran.r-project.org/doc/manuals/r-release/R-exts.html#C-standards[Writing R Extensions: C standards]). The Fortran side has its own page in this section, and the Fortran Reference covers the language.

OpenMP is the usual way to use several threads inside compiled code. The compiler flag differs between compilers, so a package takes it from R: it puts `$(SHLIB_OPENMP_CFLAGS)` in both `PKG_CFLAGS` and `PKG_LIBS` for C code (and `SHLIB_OPENMP_CXXFLAGS` and `SHLIB_OPENMP_FFLAGS` for the other two languages, with a different recipe for Fortran), guards OpenMP-specific code with `pass:c[#ifdef _OPENMP]`, and includes the macros only when the code really uses OpenMP. Some toolchains, Apple's clang among them, have no OpenMP support at all, and a note in the manual says that the C{pp} macro applies to the default C{pp} compiler and not necessarily to the one selected for C{pp}17 or C{pp}20, for which a `configure` check is advised. Writing `-fopenmp` directly into `PKG_CXXFLAGS` works with gcc and fails elsewhere, which is why `R CMD check` has a check named "checking use of SHLIB_OPENMP_*FLAGS in Makefiles" (it appears in the transcript of the earlier section). Calling the R API from threaded code is, in the manual's words, for experts only and strongly discouraged: the R API changes internal data structures, and errors must be signalled only from the main thread. The threading model of R's parallel packages is the subject of xref:programming-languages/r/parallel-and-asynchronous-computing.adoc[Parallel and Asynchronous Computing]; the manual's section is https://cran.r-project.org/doc/manuals/r-release/R-exts.html#OpenMP-support[OpenMP support].

== .C: plain pointers

=== How .C passes arguments

`.C()` is the traditional interface and the simplest to write for: the C function takes pointers to plain C data and returns `void`. R copies each argument, passes a pointer to the copy, and returns a list of the (possibly modified) copies, with the names that were given to the arguments. No R header is needed, and the C function does not have to know it is called from R. The mapping from R storage modes to C types is fixed.

[cols="1,2,2",options="header"]
|===
|R storage mode |C type |Fortran type
|`integer`, `logical` |`pass:c[int *]` |`integer`
|`double` (`numeric`) |`pass:c[double *]` (or `pass:c[float *]` with the `Csingle` attribute, set by `as.single()`) |`double precision` (or `real`)
|`complex` |`pass:c[Rcomplex *]`, a structure with members `r` and `i` |`double complex`
|`character` |`pass:c[char **]` |one string only, as `+character*255+`; deprecated
|`raw` |`pass:c[unsigned char *]` |not allowed
|`list`, other |`pass:c[SEXP *]` or `SEXP` (read-only; use `.Call()` instead) |not allowed
|===

Source: https://search.r-project.org/R/refmans/base/html/Foreign.html[R documentation: .C]

A logical is sent as 0, 1 or `INT_MIN` (the last only when `NAOK = TRUE`), and the code should return one of the three values. The C type for an R integer is `int`, which is 32 bits on every platform R runs on, and not `long`: code ported from S-PLUS that used `+long *+` is wrong on most 64-bit platforms (https://cran.r-project.org/doc/manuals/r-release/R-exts.html#Interface-functions-_002eC-and-_002eFortran[Writing R Extensions: Interface functions .C and .Fortran]). Strings need most care. On entry the contents of a character vector are copied to a `+char **+` array; the C code can shorten a string by writing a `'\0'`, but it cannot lengthen one, and a missing string arrives as the text `"NA"`. For anything that is not plain numbers, use `.Call()`.

=== A .C routine

The convolution of two sequences, the manual's own example, makes the routine. `convolve()` takes the two sequences and their lengths as pointers and fills a result array that the caller allocated, since a C function cannot return a vector through `.C()`; the R wrapper allocates it with `double(length(a) + length(b) - 1)` and names it so that `$ab` extracts it from the returned list. The file also registers a second name, `convolve_checked`, for the same function with its argument types, which is how the type check below is made.

[source,c]
----
#include <R.h>
#include <Rinternals.h>
#include <R_ext/Rdynload.h>

/* .C passes pointers to copies of the arguments and returns them as a list. */
void convolve(double *a, int *na, double *b, int *nb, double *ab) {
  int nab = *na + *nb - 1;
  for (int i = 0; i < nab; i++) {
    ab[i] = 0.0;
  }
  for (int i = 0; i < *na; i++) {
    for (int j = 0; j < *nb; j++) {
      ab[i + j] += a[i] * b[j];
    }
  }
}

/* The same routine under a second name, registered with argument types. */
static R_NativePrimitiveArgType convolve_types[] = {
  REALSXP, INTSXP, REALSXP, INTSXP, REALSXP
};

static const R_CMethodDef c_methods[] = {
  {"convolve_checked", (DL_FUNC) &convolve, 5, convolve_types},
  {NULL, NULL, 0, NULL}
};

void R_init_convolve(DllInfo *dll) {
  R_registerRoutines(dll, c_methods, NULL, NULL, NULL);
}
----

Source: https://cran.r-project.org/doc/manuals/r-release/R-exts.html#Interface-functions-_002eC-and-_002eFortran[Writing R Extensions: Interface functions .C and .Fortran]

The script shows the list that `.C()` returns, the refusal of missing values, the effect of a type mistake on an unregistered routine, the registered version of the check, and the old `DUP` argument. A few results need explaining.

* `DUP` and `ENCODING` are accepted for old code and ignored. Before R 3.2.0 `DUP = FALSE` avoided the copy; since that version the NEWS says it is ignored and that the arguments are duplicated as `DUP = TRUE` would do, and the help page says `.Call()` is much preferred. The script shows that adding `DUP = FALSE` changes nothing.
* A `NA`, `NaN` or `Inf` in an argument is an error: `NA/NaN/Inf in foreign function call (arg 1)`. `NAOK = TRUE` turns the check off, and the values then reach the C code as they are; the result `1 NA` shows that `+NA * 1+` is `NA`.
* A mistake in the type is not an error at all. Passing the double `3` where the C code reads an `+int *+` makes the C code see the bit pattern of a double, whose low four bytes are zero on a little-endian machine, so `na` is 0 and the result is `0 0 0 0` instead of `0 1 2 3`, with no message. The same mistake with a character string for a `+double *+` would read pointer values as numbers. The manual says as much: coerce every argument to the right mode before calling (`as.double()`, `as.integer()`).
* Registering the argument types gives the check: `wrong type for argument 2 in call to convolve_checked` for the double, and `Incorrect number of arguments (4), expecting 5 for 'convolve_checked'` for the missing one, naming the routine and both counts. A mismatch between the number of types in the array and the number of arguments cannot be checked by the compiler, so count them.

[source,r]
----
# Built with `R CMD SHLIB convolve.c`.
dyn.load(paste0("convolve", .Platform$dynlib.ext))

# .C copies every argument, passes pointers, and returns them as a list.
convolve <- function(a, b) {
  .C("convolve",
    as.double(a), as.integer(length(a)),
    as.double(b), as.integer(length(b)),
    ab = double(length(a) + length(b) - 1),
    PACKAGE = "convolve"
  )$ab
}
convolve(c(1, 2, 3), c(0, 1, 0.5))
#> [1] 0.0 1.0 2.5 4.0 1.5
res <- .C("convolve", c(1, 2), 2L, c(3, 4), 2L, ab = double(3),
  PACKAGE = "convolve"
)
str(res)
#> List of 5
#>  $   : num [1:2] 1 2
#>  $   : int 2
#>  $   : num [1:2] 3 4
#>  $   : int 2
#>  $ ab: num [1:3] 3 10 8

# DUP and ENCODING are accepted for old code and ignored: arguments are copied.
args <- list("convolve", c(1, 2), 2L, c(3, 4), 2L, ab = double(3))
identical(
  do.call(.C, c(args, DUP = FALSE, PACKAGE = "convolve")),
  do.call(.C, c(args, PACKAGE = "convolve"))
)
#> [1] TRUE

# Missing and non-finite values are refused unless NAOK = TRUE.
message_of <- function(expr) tryCatch(expr, error = conditionMessage)
message_of(convolve(c(1, NA, 3), 1))
#> [1] "NA/NaN/Inf in foreign function call (arg 1)"
.C("convolve", c(1, NA), 2L, 1, 1L, ab = double(2),
  NAOK = TRUE, PACKAGE = "convolve"
)$ab
#> [1]  1 NA

# Nothing checks the types of an unregistered routine. A double where C reads
# an int (here na = 3) is not an error; on a little-endian machine the low
# four bytes of 3.0 are zero, so C sees na = 0 and the answer is wrong.
.C("convolve", c(1, 2, 3), 3, c(0, 1), 2L, ab = double(4),
  PACKAGE = "convolve"
)$ab
#> [1] 0 0 0 0

# The registered copy of the routine knows its types and its arity.
message_of(.C("convolve_checked", c(1, 2, 3), 3, c(0, 1), 2L, ab = double(4)))
#> [1] "wrong type for argument 2 in call to convolve_checked"
message_of(.C("convolve_checked", c(1, 2, 3), 3L, c(0, 1), 2L))
#> [1] "Incorrect number of arguments (4), expecting 5 for 'convolve_checked'"
.C("convolve_checked", c(1, 2, 3), 3L, c(0, 1), 2L, ab = double(4))$ab
#> [1] 0 1 2 3
----

Source: https://search.r-project.org/R/refmans/base/html/Foreign.html[R documentation: .C]

=== Detecting writes outside an argument

A fairly common cause of crashes in `.C()` and `.Fortran()` code is writing a little beyond the end of an argument, which corrupts something else and crashes R later. `options(CBoundsCheck = TRUE)` (or the environment variable `R_C_BOUNDS_CHECK=yes`) changes how R copies the arguments: it adds 64 guard bytes at both ends of each copy and checks them on return. `overrun()` below has the classic off-by-one, a loop that runs to `+i <= *n+`.

[source,c]
----
/* Bug: the loop runs to i == *n, one element past the end of x. */
void overrun(double *x, int *n) {
  for (int i = 0; i <= *n; i++) {
    x[i] = 0.0;
  }
}
----

Source: https://cran.r-project.org/doc/manuals/r-release/R-exts.html#Debugging-compiled-code[Writing R Extensions: Debugging compiled code]

[source,r]
----
# Built with `R CMD SHLIB overrun.c`: the C code writes one element too many.
dyn.load(paste0("overrun", .Platform$dynlib.ext))

# options(CBoundsCheck = TRUE) makes .C and .Fortran pad each argument with 64
# guard bytes at both ends and check them when the routine returns.
getOption("CBoundsCheck")
#> [1] FALSE
options(CBoundsCheck = TRUE)
tryCatch(
  .C("overrun", c(1, 2, 3), 3L, PACKAGE = "overrun"),
  error = conditionMessage
)
#> [1] "array over-run in .C(\"overrun\") in double argument 1\n"
----

Source: https://search.r-project.org/R/refmans/base/html/Foreign.html[R documentation: .C]

The message names the call, the type and the argument number. It is a debugging aid: it makes every call slower, it is off by default, and it detects only writes in the guard zones.

== .Fortran: subroutines

`.Fortran()` calls a Fortran subroutine with the same copy-and-return protocol as `.C()`, and the same argument table. Three rules are specific to Fortran. All the Fortran compilers R supports map symbol names to lower case, so `.Fortran("loan_totals")` looks for the lower-case name, and so does registration. Arguments are passed by reference, which is what Fortran expects. And the compiler decorates the symbol (often a trailing underscore); R detects the convention when it is built, which is why the R code never writes the underscore, and why C code that calls Fortran must use the macros `F77_NAME`, `F77_CALL` and `F77_SUB` from `R_ext/RS.h`, never the underscore. The help page of `.Fortran()` adds that a Fortran name with an underscore in it is not valid Fortran 77, and its translation can differ between compilers, so the portable advice is to use plain lower-case names (https://search.r-project.org/R/refmans/base/html/Foreign.html[R documentation: .Fortran]).

`R CMD SHLIB` takes `.f` as fixed-form Fortran (which includes Fortran 77), passing it to the compiler that R was configured with, and `.f90` or `.f95` as free-form. Both go to the same compiler. The manual's advice for modern code is to use `.f90`, to put a requirement in `SystemRequirements` (for example `Fortran 2018`) since the standard the compiler accepts is a property of the compiler, and, when the package has several source files that use modules, to tell `make` the compilation order in `src/Makevars`, because module files are produced by compiling and `make` cannot see the dependency. For a module `iface` used by `cmi.f90` and `dmi.f90` the line is `cmi.o dmi.o: iface.o` (https://cran.r-project.org/doc/manuals/r-release/R-exts.html#Using-modern-Fortran-code[Writing R Extensions: Using modern Fortran code]). The compile commands for Fortran are the same two lines as for C, with `gfortran` for the first:

[source,bash]
----
R CMD SHLIB loan_totals.f90
#> gfortran -fPIC -O2 -c loan_totals.f90 -o loan_totals.o
#> gcc -std=gnu2x -shared -o loan_totals.so loan_totals.o -lgfortran -lm -L"<R_HOME>/lib" -lR
----

Source: https://search.r-project.org/R/refmans/utils/html/SHLIB.html[R documentation: SHLIB]

(Flags shortened, and the first line, which names the Fortran compiler and the system, omitted. The link line still uses the C driver, with `-lgfortran -lm` added by R's `FLIBS`.)

=== A subroutine for .Fortran

`loan_totals` adds up the days beyond the loan period and counts the late loans. Every argument is declared with its intent, which is how Fortran says "input" and "output", and the sizes come from the array lengths that R passes in. The `-Wall -pedantic` flags of the personal Makevars compile it without warnings.

[source,fortran]
----
! Total and count of the days beyond the loan period, for .Fortran.
subroutine loan_totals(days, n, limit, late_total, late_count)
  implicit none
  integer, intent(in) :: n
  double precision, intent(in) :: days(n), limit
  double precision, intent(out) :: late_total
  integer, intent(out) :: late_count
  integer :: i

  late_total = 0.0d0
  late_count = 0
  do i = 1, n
    if (days(i) > limit) then
      late_total = late_total + (days(i) - limit)
      late_count = late_count + 1
    end if
  end do
end subroutine loan_totals
----

Source: https://cran.r-project.org/doc/manuals/r-release/R-exts.html#Interface-functions-_002eC-and-_002eFortran[Writing R Extensions: Interface functions .C and .Fortran]

=== Printing, warnings, errors and random numbers from Fortran

Fortran `print` and `write` statements to the default unit are not guaranteed to appear in the R console, may not interleave with C output, and on Windows interfere with C's own output (the manual describes how gfortran's initialisation changes the line endings of C's `stdout` and how to undo it in `R_init_<pkg>`). R therefore provides subroutines that print through R's own channels: `labelpr(label, nchar)` prints a label, `intpr1(label, nchar, var)`, `realpr1()` and `dblepr1()` print a labelled scalar, and `intpr()`, `realpr()` and `dblepr()` print a labelled array (`label, nchar, data, ndata`); `nchar` is the length of the label, or `-1` for all of it. There is no check on the type: a `real` passed to `dblepr` prints nonsense. For conditions, `rexit(message)` signals an error and `rwarn(message)` a warning (messages are cut to 255 characters), and `rchkusr()` is the interrupt check. `fortran_io.f90` uses all of them.

[source,fortran]
----
! Printing, a warning and an error from Fortran through R's own routines.
subroutine summarise(days, n)
  implicit none
  integer, intent(in) :: n
  double precision, intent(in) :: days(n)
  double precision :: mean

  if (n < 1) call rexit("summarise: no loans")
  if (n == 1) call rwarn("summarise: only one loan")
  mean = sum(days) / n
  call labelpr("loan summary", 12)
  call intpr1("loans", 5, n)
  call dblepr1("mean days", 9, mean)
  call rchkusr()
end subroutine summarise
----

Source: https://cran.r-project.org/doc/manuals/r-release/R-exts.html#Printing-from-Fortran[Writing R Extensions: Printing from Fortran]

Random numbers are the other thing Fortran code must not do itself. The Fortran 90 `random_number` and `random_seed`, GNU's `rand`, and the C library's `rand` all keep a state that is private to the library: packages cannot initialise it safely, two packages can interfere, and the user's `set.seed()` does not reach it. The manual's rule is to use R's generator, which a routine reaches by bracketing the draws with `GetRNGstate()` and `PutRNGstate()` and calling `unif_rand()` (or `norm_rand()`, `exp_rand()`), and it shows how to bind those C entry points from Fortran with `iso_c_binding` (https://cran.r-project.org/doc/manuals/r-release/R-exts.html#Random_002dnumber-generation-from-Fortran[Writing R Extensions: Random-number generation from Fortran]). `rngdemo.f90` does this without a line of C.

[source,fortran]
----
! Random loan lengths drawn from R's own generator (so set.seed() applies).
subroutine random_loans(n, longest, out)
  use iso_c_binding, only: c_double
  implicit none
  interface
    subroutine get_rng_state() bind(C, name = "GetRNGstate")
    end subroutine get_rng_state
    subroutine put_rng_state() bind(C, name = "PutRNGstate")
    end subroutine put_rng_state
    function unif_rand() bind(C, name = "unif_rand") result(u)
      import :: c_double
      real(c_double) :: u
    end function unif_rand
  end interface
  integer, intent(in) :: n
  double precision, intent(in) :: longest
  double precision, intent(out) :: out(n)
  integer :: i

  call get_rng_state()
  do i = 1, n
    out(i) = ceiling(longest * unif_rand())
  end do
  call put_rng_state()
end subroutine random_loans
----

Source: https://cran.r-project.org/doc/manuals/r-release/R-exts.html#Random_002dnumber-generation-from-Fortran[Writing R Extensions: Random-number generation from Fortran]

=== Modern Fortran through .C and bind(C)

For Fortran 90 and later code the help page of `.Fortran()` and the manual give the same advice: the most portable way is to give the subroutine a C interface with `iso_c_binding` and call it with `.C()`. With `bind(C, name = "isbn_check_digit")` the routine has exactly the C name given, the kinds `c_int` and `c_double` say exactly what C types the arguments are, and the compiler can check the declaration. `isbn_check_digit` computes the 13th digit of an ISBN from the first twelve.

[source,fortran]
----
! ISBN-13 check digit from the first twelve digits, callable through .C.
subroutine isbn_check_digit(digits, check) bind(C, name = "isbn_check_digit")
  use iso_c_binding, only: c_int
  implicit none
  integer(c_int), intent(in) :: digits(12)
  integer(c_int), intent(out) :: check
  integer :: i, total

  total = 0
  do i = 1, 12
    if (mod(i, 2) == 1) then
      total = total + digits(i)
    else
      total = total + 3 * digits(i)
    end if
  end do
  check = mod(10 - mod(total, 10), 10)
end subroutine isbn_check_digit
----

Source: https://cran.r-project.org/doc/manuals/r-release/R-exts.html#Interface-functions-_002eC-and-_002eFortran[Writing R Extensions: Interface functions .C and .Fortran]

=== Registering a Fortran routine

A registered `.Fortran()` routine needs a prototype in C, because the registration table is C. The prototype uses `F77_NAME(loan_totals)` for the name, with every argument a pointer; and a Fortran `LOGICAL` is declared `+int *+` in C, or better `+void *+`, because gfortran reports `+int_least32_t *+` and link-time optimisation would otherwise warn. The entry goes in an `R_FortranMethodDef` table, with the argument types, as the manual's example for `.C()` did. `R_init_<name>` is named after the shared object, which is why the object is built as `loantot.so`.

[source,c]
----
#include <R.h>
#include <Rinternals.h>
#include <R_ext/RS.h>
#include <R_ext/Rdynload.h>

/* The Fortran routine as C sees it: lower-case name, every argument a pointer. */
extern void F77_NAME(loan_totals)(double *days, int *n, double *limit,
                                  double *late_total, int *late_count);

static R_NativePrimitiveArgType loan_totals_types[] = {
  REALSXP, INTSXP, REALSXP, REALSXP, INTSXP
};

static const R_FortranMethodDef fortran_methods[] = {
  {"loan_totals", (DL_FUNC) &F77_NAME(loan_totals), 5, loan_totals_types},
  {NULL, NULL, 0, NULL}
};

void R_init_loantot(DllInfo *dll) {
  R_registerRoutines(dll, NULL, NULL, fortran_methods, NULL);
  R_useDynamicSymbols(dll, FALSE);
}
----

=== Character strings and logicals between C and Fortran

Two kinds of argument are not portable and need a special mention, and both are covered in the manual's section on calling C from Fortran and vice versa.

* **Character strings.** A Fortran string is an array of bytes plus a hidden length argument; a C string is NUL-terminated. Since 2019 gfortran passes the hidden length at the end of the argument list as a `size_t` (backported to gfortran 7 and 8), and code that ignored it broke. R defines the macro `USE_FC_LEN_T` and the type `FC_LEN_T` in `Rconfig.h` to match: a C routine called from Fortran declares the extra `FC_LEN_T msg_len` argument, and C code that calls a BLAS or LAPACK routine with character arguments (such as `+dgemm("N", "T", ...)+`) appends `FCONE` for every character argument, with no comma. `USE_FC_LEN_T` became the default in R 4.3.0, and packages that call BLAS or LAPACK with character arguments fail to install without the adjustment. The alternative is to avoid the problem, by passing integer codes instead of strings or by writing the interface with `iso_c_binding` (https://cran.r-project.org/doc/manuals/r-release/R-exts.html#Fortran-character-strings[Writing R Extensions: Fortran character strings]).
* **Logicals.** Fortran `LOGICAL` has no guaranteed size. In practice it is a 32-bit integer, and `+int *+` is the traditional C equivalent, but recent gfortran says `+int_least32_t *+`. The simplest design is to pass integers and convert in a Fortran wrapper (https://cran.r-project.org/doc/manuals/r-release/R-exts.html#Fortran-LOGICAL[Writing R Extensions: Fortran LOGICAL]).

Passing C functions to Fortran as arguments (callbacks) depends on the two compilers agreeing on the calling convention and has failed in practice; the manual's most portable suggestion is to convert the Fortran to C. For everything about the Fortran language and about calling it from C, C{pp} and Python, the xref:programming-languages/fortran/index.adoc[Fortran Reference] section added by issue #277 has the pages xref:programming-languages/fortran/interoperability-with-c.adoc[Interoperability with C], xref:programming-languages/fortran/calling-fortran-from-c-cpp-and-python.adoc[Calling Fortran from C, C{pp} and Python] and xref:programming-languages/fortran/blas-lapack-and-numerical-libraries.adoc[BLAS, LAPACK and Numerical Libraries], and the xref:programming-languages/c/build-and-tooling.adoc[C build and tooling page] explains the compilers and linkers involved.

== .External: arguments as a pairlist

`.External()` differs from `.Call()` in one respect: the C function receives a single `SEXP`, a pairlist whose first cell holds the name of the routine and whose remaining cells are the arguments. That removes the limit of 65 arguments and gives the C code the argument names (the "tags"), which is what makes a function with `+...+` natural to write. The walk over the list uses the Lisp-style macros: `CDR(args)` is the rest of the list, `CAR(args)` the current argument, `TAG(args)` its name as a symbol (or `R_NilValue`), and `PRINTNAME()` turns a symbol into a `CHARSXP`. `CADR`, `CADDR`, `CADDDR` and so on read the first few arguments by position, and `SETCAR()` and its relatives modify a cell. The first cell is skipped with `args = CDR(args)`. When registering `.External()` routines, the argument count is `-1`, which tells R not to check it.

[source,c]
----
#include <R.h>
#include <Rinternals.h>

/* .External: the arguments arrive as one pairlist; the first cell is the name. */
SEXP total_days_ext(SEXP args) {
  args = CDR(args);
  double total = 0.0;
  for (; args != R_NilValue; args = CDR(args)) {
    SEXP el = CAR(args);
    if (!Rf_isNumeric(el)) {
      Rf_error("every argument must be numeric");
    }
    SEXP v = PROTECT(Rf_coerceVector(el, REALSXP));
    for (R_xlen_t i = 0; i < XLENGTH(v); i++) {
      total += REAL(v)[i];
    }
    UNPROTECT(1);
  }
  return Rf_ScalarReal(total);
}

/* The tags (argument names) of the call, "" for unnamed arguments. */
SEXP arg_names(SEXP args) {
  args = CDR(args);
  int n = Rf_length(args);
  SEXP out = PROTECT(Rf_allocVector(STRSXP, n));
  for (int i = 0; i < n; i++, args = CDR(args)) {
    if (TAG(args) == R_NilValue) {
      SET_STRING_ELT(out, i, Rf_mkChar(""));
    } else {
      SET_STRING_ELT(out, i, PRINTNAME(TAG(args)));
    }
  }
  UNPROTECT(1);
  return out;
}
----

Source: https://cran.r-project.org/doc/manuals/r-release/R-exts.html#Calling-_002eExternal[Writing R Extensions: Calling .External]

== C{pp} without Rcpp

C{pp} code reaches R through the same C interfaces, with three differences: the entry points need C linkage, the R headers need care, and a C{pp} exception must never cross the boundary. The manual's own example is a C{pp} library of two classes that is made callable by writing a wrapper function inside `+extern "C" { }+` and building with `R CMD SHLIB` (which links with the C{pp} compiler because there is a C{pp} source file); the same page warns that C{pp} iostreams should not be used for output, because nothing guarantees that the text reaches the R console, and that R's own entry points (`Rprintf()`) should be used instead (https://cran.r-project.org/doc/manuals/r-release/R-exts.html#Interfacing-C_002b_002b-code[Writing R Extensions: Interfacing C{pp} code]). The xref:programming-languages/cpp/program-structure-and-compilation.adoc[C{pp} Reference page on program structure and compilation] explains `extern "C"` and name mangling.

The three points in practice:

* **Linkage.** `.Call()` looks up a C symbol, but the C{pp} compiler mangles names. A function called from R must be declared `extern "C"`. The header files of R can be included from C{pp} but not inside an `extern "C"` block, because they include system headers.
* **Header order and R_NO_REMAP.** Include the C{pp} standard headers before the R headers, and use the `Rf_` names, because since R 4.5.0 `R_NO_REMAP` is always defined for C{pp} (an earlier section). Several R short names (`length`, `error`) collide with identifiers in the standard library.
* **Exceptions and `longjmp`.** `Rf_error()` unwinds the stack with a `longjmp`, which skips the destructors of C{pp} objects between the call and the catching R frame: a `std::vector` or `std::string` alive at that moment leaks. A C{pp} exception must not be allowed to propagate out of an `extern "C"` function into R's C code. The safe pattern is to catch all exceptions inside the C{pp} code, copy the message into a plain character buffer, let every C{pp} object go out of scope, and only then call `Rf_error()`. For C{pp} code that must run destructors when an R error unwinds the stack, R offers `R_UnwindProtect()` with a continuation token (`R_MakeUnwindCont()` and `R_ContinueUnwind()`), which the manual describes as suitable for C{pp} stack unwinding (https://cran.r-project.org/doc/manuals/r-release/R-exts.html#Condition-handling-and-cleanup-code[Writing R Extensions: Condition handling and cleanup code]).

`cxx_median.cpp` follows the safe pattern. The vector, the sort and the exception live in an anonymous-namespace function that returns a status; the `extern "C"` function holds only plain C data when it calls `Rf_error()`.

[source,cpp]
----
#define R_NO_REMAP
#include <algorithm>
#include <cstdio>
#include <stdexcept>
#include <vector>
#include <R.h>
#include <Rinternals.h>

namespace {

// All the C++ lives here; no exception leaves this function.
// Returns 0 on success, 1 after copying an error message into msg.
int median_impl(const double *x, R_xlen_t n, double *result, char *msg,
                std::size_t msg_size) {
  try {
    std::vector<double> v;
    for (R_xlen_t i = 0; i < n; ++i) {
      if (!ISNAN(x[i])) {
        v.push_back(x[i]);
      }
    }
    if (v.empty()) {
      throw std::invalid_argument("no non-missing values");
    }
    std::sort(v.begin(), v.end());
    std::size_t m = v.size();
    *result = m % 2 == 1 ? v[m / 2] : 0.5 * (v[m / 2 - 1] + v[m / 2]);
    return 0;
  } catch (const std::exception &e) {
    std::snprintf(msg, msg_size, "%s", e.what());
    return 1;
  }
}

}  // namespace

// R calls C symbols, so the entry point has C linkage.
extern "C" SEXP median_cxx(SEXP days) {
  SEXP d = PROTECT(Rf_coerceVector(days, REALSXP));
  double result = NA_REAL;
  char msg[256];
  int status = 0;
  if (XLENGTH(d) == 0) {
    std::snprintf(msg, sizeof msg, "%s", "no non-missing values");
    status = 1;
  } else {
    status = median_impl(REAL(d), XLENGTH(d), &result, msg, sizeof msg);
  }
  UNPROTECT(1);
  if (status != 0) {
    Rf_error("%s", msg);  // only plain C data is alive here: nothing to leak
  }
  return Rf_ScalarReal(result);
}
----

Source: https://cran.r-project.org/doc/manuals/r-release/R-exts.html#Interfacing-C_002b_002b-code[Writing R Extensions: Interfacing C{pp} code]

Libraries are the other problem. Header-only C{pp} libraries (most of Boost, as packaged in the BH package; most of Armadillo, as RcppArmadillo) compile with the package and cause few problems; a library with a compiled C{pp} interface has a name-mangled ABI that depends on the compiler, its version and even preprocessor defines, so the package would have to be compiled exactly as the library was; and a library that uses C{pp} internally but offers a C interface needs the C{pp} runtime linked, which is done by including a dummy C{pp} file in `src/` so that R links with the C{pp} compiler. The manual's advice for libraries with both is to use the C interface (https://cran.r-project.org/doc/manuals/r-release/R-exts.html#External-C_002b_002b-code[Writing R Extensions: External C{pp} code]).

== Rcpp: R objects as C{pp} classes

Rcpp (version 1.1.2 here) is a package of C{pp} headers and a small runtime that wraps R's C API in classes. A numeric vector is a `NumericVector`, a list a `List`, a data frame a `DataFrame`, an R function a `Function`; conversion between R and C{pp} types happens at the boundary, `PROTECT()` is done by the object's constructor and destructor, and a C{pp} exception thrown in your code becomes an R error. The project's own site describes it as an interface that maps the key R data types to C{pp} data structures, says that it makes it easy to create a first example with `cppFunction()`, and reports that it is used by over 3000 packages on CRAN (https://www.rcpp.org/[Rcpp website]). Rcpp is community-maintained software outside the R core, not a base package: the reference below is the package's own documentation, the CRAN package page and the vignettes that come with it (among them the introduction, attributes, sugar and package vignettes cited below); the Rcpp Gallery (https://gallery.rcpp.org/) is community material with examples of a wide range of tasks, and is named here only as such.

=== What Rcpp removes

The `.Call()` routines of the earlier sections have a lot of ceremony that is the same each time: the `SEXP` signature, the coercion, the allocation, the `PROTECT()` and `UNPROTECT()` bookkeeping, the loop over `REAL(x)`, the wrapper that attaches the attributes, the registration table and the `R_init` function, and the R function that calls `.Call()`. Rcpp attributes generate all of them. A C{pp} function whose signature uses Rcpp types and which is marked with `pass:c[// [[Rcpp::export\]\]]` is turned into an R function with the same name and arguments, including default values; the glue is generated into a pair of files in a package (`RcppExports.cpp` and `RcppExports.R`) or compiled on the fly by `cppFunction()` and `sourceCpp()`.

Rcpp also provides "sugar": vectorised expressions that look like R and run as C{pp} loops. `sum(x)`, `mean(x)`, `ifelse(cond, a, b)`, `is_na(x)`, `+any(...)+`, `cumsum(x)`, `rev(x)`, `x > limit`, `x - limit` and many more are defined for the vector classes, so a loop can often be replaced by an expression; the sugar vignette lists them (https://cran.r-project.org/web/packages/Rcpp/vignettes/Rcpp-sugar.pdf[Rcpp package documentation: Rcpp-sugar vignette]).

=== evalCpp() and cppFunction()

`evalCpp("2 + 2")` compiles one C{pp} expression and returns its value, which is the quickest check that the toolchain works. `cppFunction(code)` takes the source of one function as a string, adds `#include <Rcpp.h>` and `using namespace Rcpp;`, compiles it with the C{pp} standard of the running R, and returns an R function. The arguments `depends`, `plugins` and `includes` add compile-time dependencies, plugin settings and extra includes; `rebuild` forces recompilation, and `showOutput` and `verbose` show what the compiler does (https://search.r-project.org/CRAN/refmans/Rcpp/html/cppFunction.html[Rcpp package documentation: cppFunction]). The script defines the two running examples, the overdue loop and the ISBN-13 check, from strings. The result of the second is compared with the C version above on the same five inputs.

=== sourceCpp() and a file of exports

`sourceCpp("file.cpp")` does the same for a file that may define many functions and helpers. It parses the file for `pass:c[// [[Rcpp::export\]\]]` attributes (and for `RCPP_MODULE` declarations), builds a shared library in a temporary directory (the build is cached, and only redone when the file changes unless `rebuild = TRUE`), and defines the exported functions in the calling environment. `+/*** R+` blocks in the file are R code that runs after compilation, which turns the C{pp} file into a self-testing script. Attributes also exist for dependencies (`pass:c[// [[Rcpp::depends(RcppArmadillo)\]\]]` adds the include path and flags of a package) and for plugins (`pass:c[// [[Rcpp::plugins(cpp17)\]\]]` requests a standard; the installed plugins include `cpp11` to `cpp26`, `openmp` and `unwindProtect`). Its help page lists the other arguments: `embeddedR`, `cacheDir`, `showOutput`, `verbose`, `dryRun` and `echo` (https://search.r-project.org/CRAN/refmans/Rcpp/html/sourceCpp.html[Rcpp package documentation: sourceCpp]). The help page also says that `sourceCpp()` is for one file whose only dependencies are R packages; for more files or external libraries, make a package.

`loans.cpp` has five exported functions. `overdue_days_loop()` is the C{pp} version of the loop of `vectors.c`; `overdue_days_sugar()` is the same job in one sugar expression; `loan_stats()` builds the classed list of `structures.c` in one expression; `flag_late()` takes a data frame and returns a data frame with a logical column; and `mean_days()` writes to `Rcout`, warns and stops. Nothing in the file mentions `SEXP`, `PROTECT` or `.Call`.

[source,cpp]
----
#include <Rcpp.h>
using namespace Rcpp;

// Days beyond the loan period, written as a loop; NA and NaN pass through.
// [[Rcpp::export]]
NumericVector overdue_days_loop(NumericVector days, double limit = 21) {
  R_xlen_t n = days.size();
  NumericVector out(n);
  for (R_xlen_t i = 0; i < n; ++i) {
    if (NumericVector::is_na(days[i])) {
      out[i] = days[i];
    } else {
      out[i] = days[i] > limit ? days[i] - limit : 0.0;
    }
  }
  out.attr("names") = days.attr("names");
  return out;
}

// The same result from Rcpp sugar: vectorised expressions, as in R.
// [[Rcpp::export]]
NumericVector overdue_days_sugar(NumericVector days, double limit = 21) {
  return ifelse(days > limit, days - limit, 0.0);
}

// A classed, named list, like the C version in structures.c.
// [[Rcpp::export]]
List loan_stats(NumericVector days) {
  NumericVector seen = days[!is_na(days)];
  List out = List::create(
    _["n"] = seen.size(),
    _["mean"] = seen.size() > 0 ? mean(seen) : NA_REAL,
    _["max"] = seen.size() > 0 ? max(seen) : NA_REAL
  );
  out.attr("class") = "loan_stats";
  return out;
}

// A data frame in, a data frame out: a logical column is added.
// [[Rcpp::export]]
DataFrame flag_late(DataFrame loans, double limit = 21) {
  CharacterVector member = loans["member"];
  NumericVector days = loans["days"];
  LogicalVector late(days.size());
  for (R_xlen_t i = 0; i < days.size(); ++i) {
    late[i] = NumericVector::is_na(days[i]) ? NA_LOGICAL : days[i] > limit;
  }
  return DataFrame::create(
    _["member"] = member, _["days"] = days, _["late"] = late
  );
}

// Output through Rcout, a warning and an error, all as R conditions.
// [[Rcpp::export]]
double mean_days(NumericVector days) {
  if (days.size() == 0) {
    stop("no loans");
  }
  if (is_true(any(is_na(days)))) {
    warning("missing days are ignored");
  }
  NumericVector seen = days[!is_na(days)];
  Rcout << "averaging " << seen.size() << " loans" << std::endl;
  return mean(seen);
}

=== Errors, warnings and output

`Rcpp::stop("no loans")` throws a C{pp} exception, the wrapper that Rcpp generates around every exported function catches it and calls R's error machinery, and the result is an ordinary R error whose message is the text. It is a condition of class `Rcpp::exception`, `pass:c,a[C{pp}Error]`, `error`, `condition`, as the last line of the output of the script shows, so `+tryCatch(..., error = )+` handles it and `conditionMessage()` returns `no loans`. A C{pp} exception derived from `std::exception` is converted the same way, with the text of `what()`. `Rcpp::warning()` signals an R warning that `withCallingHandlers()` can handle, and `Rcout` writes through R's output, so `capture.output()` and `sink()` see it. In the script, `mean_days(c(14, 35))` prints `averaging 2 loans` through `Rcout` and returns 24.5; with `c(14, NA, 35)` the calling handler prints `caught: missing days are ignored` to the message stream and muffles the warning, and the function carries on and averages the two known values; and with `numeric()` the error is caught. Rcpp can also use `R_UnwindProtect()` so that C{pp} destructors run when an R error unwinds the stack, and has a plugin named `unwindProtect` for it.

#include <Rcpp.h>
using namespace Rcpp;

// Keep the digits, reject an X, weight 1 and 3 alternately.
static bool valid_isbn(const std::string& s) {
  int n = 0, sum = 0;
  for (char c : s) {
    if (c >= '0' && c <= '9') {
      if (n == 13) {
        return false;
      }
      sum += (c - '0') * (n % 2 == 0 ? 1 : 3);
      ++n;
    } else if (c == 'X' || c == 'x') {
      return false;
    }
  }
  return n == 13 && sum % 10 == 0;
}

//' Check ISBN-13 strings with C++
//'
//' `is_valid_isbn13_cpp()` gives the same answers as [is_valid_isbn13()], but
//' the check runs in C++ through Rcpp.
//'
//' @param x A character vector of ISBNs; `NA` and empty strings are allowed.
//' @returns A logical vector of the same length as `x`, `FALSE` for `NA` and
//'   for the empty string.
//' @examples
//' is_valid_isbn13_cpp(c("978-0-306-40615-7", "978-0-01-100112-9", NA))
//' @export
// [[Rcpp::export]]
LogicalVector is_valid_isbn13_cpp(CharacterVector x) {
  R_xlen_t n = x.size();
  LogicalVector out(n);
  for (R_xlen_t i = 0; i < n; ++i) {
    out[i] = !CharacterVector::is_na(x[i]) && valid_isbn(as<std::string>(x[i]));
  }
  return out;
}

Two habits keep an Rcpp package healthy. === cpp11 and the other relatives

cpp11 (0.5.5 is installed; it was not run) is a header-only alternative in the r-lib family, with similar goals and a different design: C{pp}11-style attributes (`pass:c[[[cpp11::register\]\]]`), `LinkingTo: cpp11` only, copy-on-write semantics, UTF-8 everywhere, and no shared runtime library; its site describes the differences from Rcpp and how to convert (https://cpp11.r-lib.org/[cpp11 package documentation]). RcppArmadillo and RcppEigen add linear-algebra libraries to Rcpp, and RcppParallel adds threading; none of them is installed here, so they are only named. All build on the same `R CMD SHLIB` and `LinkingTo` machinery described above.

== How much faster? A measurement

Whether any of this pays is a question of numbers. The script compares four implementations of the overdue-days function on a million simulated loan durations: an R `for` loop, the vectorised R expression `pmax(days - limit, 0)`, the `.Call()` routine from `vectors.c` and a `cppFunction()` loop. `bench::mark()` checks that all four return the same result before timing them. Timings depend on the machine, the compiler flags and what else is running, so the script prints only the order of magnitude of each median relative to the fastest, as `round(log10(ratio))`; the exact ratios, which vary from run to run, are not shown. xref:programming-languages/r/performance-profiling-and-benchmarking.adoc[Performance, Profiling and Benchmarking] explains how to measure with `bench` and `microbenchmark`.

[source,r]
----
# Built with `R CMD SHLIB vectors.c`. The same job four ways on a million
# simulated loan lengths: compare the ratios, not the seconds.
library(Rcpp)
dyn.load(paste0("vectors", .Platform$dynlib.ext))

set.seed(2026)
days <- round(runif(1e6, 1, 60))

overdue_r_loop <- function(days, limit = 21) {
  out <- numeric(length(days))
  for (i in seq_along(days)) {
    out[[i]] <- if (days[[i]] > limit) days[[i]] - limit else 0
  }
  out
}
overdue_r_vector <- function(days, limit = 21) pmax(days - limit, 0)
overdue_c <- function(days, limit = 21) {
  .Call("overdue_days", days, limit, PACKAGE = "vectors")
}
overdue_cpp <- cppFunction("
NumericVector overdue_cpp(NumericVector days, double limit = 21) {
  NumericVector out(days.size());
  for (R_xlen_t i = 0; i < days.size(); ++i) {
    out[i] = days[i] > limit ? days[i] - limit : 0.0;
  }
  return out;
}")

b <- bench::mark(
  r_loop = overdue_r_loop(days),
  r_vector = overdue_r_vector(days),
  c_call = overdue_c(days),
  rcpp = overdue_cpp(days),
  min_iterations = 20
)
rel <- summary(b, relative = TRUE)
data.frame(
  expression = as.character(rel$expression),
  orders_of_magnitude_slower = round(log10(rel$median / min(rel$median)))
)
#>   expression orders_of_magnitude_slower
#> 1     r_loop                          1
#> 2   r_vector                          0
#> 3     c_call                          0
#> 4       rcpp                          0
----

Source: https://bench.r-lib.org/reference/mark.html[bench package documentation: mark]

The result is the useful lesson. The plain R `for` loop is about one order of magnitude slower than compiled code here. It is byte-compiled by the JIT (see xref:programming-languages/r/vectorisation-and-iteration.adoc[Vectorisation and Iteration]), which is why the gap is a factor of ten or twenty and not larger. The vectorised R expression, which runs in R's own compiled code, is within a factor of about three of the `.Call()` routine and the Rcpp function, which is the resolution of this measurement. Compiled code won over the loop and not over the right R expression. That is the usual outcome for work that a vectorised built-in can already do, and the reason to reach for C, C{pp} or Fortran for a loop that cannot be vectorised, and not for one that can.

== Debugging compiled code

The R debugger of xref:programming-languages/r/debugging.adoc[Debugging] sees interpreted code only: `browser()` and `debug()` stop at R lines, and a `.Call()` is a single step. Debugging compiled code uses the tools of the language, and the manual's chapter on debugging collects the R-specific tricks (https://cran.r-project.org/doc/manuals/r-release/R-exts.html#Debugging-compiled-code[Writing R Extensions: Debugging compiled code]).

* **A crash prints a traceback.** On Unix-alikes R installs a signal handler. A segmentation fault or illegal instruction prints `+*** caught segfault ***+`, the address, the R-level traceback and a menu of possible actions. Since the process may be damaged, the manual says the only really safe choices are to abort or to exit without saving the workspace.
* **Run R under the debugger.** `R -d gdb --vanilla` starts R under gdb; on macOS the debugger is lldb (`R -d lldb`), and the manual has a separate section on its hurdles there. A breakpoint cannot be set in code that is not loaded yet, so the manual's recipe is: start R under the debugger, `dyn.load()` or `library()` the shared object, send an interrupt to return to the debugger prompt, set the breakpoints, and continue with `signal 0`. Build with `-g -O0` (in a personal Makevars) so that the debugger can step through the source; `pkgload::load_all()` does so by default. `gdb -p <pid>` attaches to a running R, and `Sys.getpid()` gives the pid.
* **Look at R objects from the debugger.** `Rf_PrintValue(s)` prints an object with R's own printing; `R_PV(s)` prints only objects. From gdb, `p R_PV(ab)` prints the object `ab` (https://cran.r-project.org/doc/manuals/r-release/R-exts.html#Inspecting-R-objects-when-debugging[Writing R Extensions: Inspecting R objects when debugging]). The R FAQ has two short entries on exactly this: how to debug dynamically loaded code and how to inspect R objects when debugging (https://cran.r-project.org/doc/FAQ/R-FAQ.html#How-can-I-debug-dynamically-loaded-code_003f[R FAQ 8.2: How can I debug dynamically loaded code?] and https://cran.r-project.org/doc/FAQ/R-FAQ.html#How-can-I-inspect-R-objects-when-debugging_003f[R FAQ 8.3: How can I inspect R objects when debugging?]).
* **Catch memory errors early.** `gctorture(TRUE)` finds missing `PROTECT()` calls; `R -d valgrind --vanilla < script.R` (and `--tool=memcheck --leak-check=full`) checks reads of uninitialised memory and writes outside allocated blocks, with false positives that the manual explains; and R can be built with the address sanitizer and the undefined-behaviour sanitizer, which catch the same errors and some more (https://cran.r-project.org/doc/manuals/r-release/R-exts.html#Checking-memory-access[Writing R Extensions: Checking memory access]). `options(CBoundsCheck = TRUE)` is the cheap test for `.C()` and `.Fortran()` overruns, shown above. Fortran has its own array bounds checking: put gfortran's `-fbounds-check` in `FFLAGS` in the personal Makevars while checking.
* **Rprintf and the other print debugging.** Still the most used. `Rprintf()` and `Rf_PrintValue()` insert into the code; a C{pp} `std::cout` should not be used for it.
* **Profiling compiled code.** The R profiler (`Rprof`) sees a `.Call()` as one line. Where time goes inside it is a question for the system profilers (`perf` on Linux, Instruments on macOS, Very Sleepy on Windows), which the manual's section on profiling compiled code describes, with the caveat that it is based on user reports and may not be current (https://cran.r-project.org/doc/manuals/r-release/R-exts.html#Profiling-compiled-code[Writing R Extensions: Profiling compiled code]).

On Windows the equivalent is gdb from Rtools with a debug build of R and of the package (`Rcmd INSTALL --debug`); the details are in the R for Windows FAQ (https://cran.r-project.org/bin/windows/base/rw-FAQ.html[R for Windows FAQ 8.4: How do I debug code that I have compiled and dyn.load-ed?]).

== Portability rules for compiled code

The manual's chapter on writing portable packages has a section for C and C{pp} code, and one for Fortran, whose rules are the difference between a package that installs everywhere and one that works on the author's machine. The points that concern code written for this page's interfaces:

* **Never end the process.** Compiled code must not call `abort()` or `exit()`, which kill the user's R session and its unsaved work. This includes `assert()`, which is active unless `NDEBUG` is defined; `R CMD INSTALL` defines it, which is why the debug flags of `load_all()` start with `-UNDEBUG`. Fortran code must not call `STOP` or `EXIT`.
* **Do not write to `stdout` or `stderr`.** Use `Rprintf()` and `REprintf()`, or the Fortran print routines of R. C{pp} and Fortran I/O should not be used.
* **Do not use the system random number generators** (`rand`, `drand48`, `random`, Fortran `random_number`, the C{pp}11 `<random>` library, or third-party generators such as GSL's). Use R's through `GetRNGstate()`, `unif_rand()` and `PutRNGstate()`, so that `set.seed()` works and packages do not interfere.
* **Mind the sizes of types.** `long` is 32 bits on some R platforms (64-bit Windows) and 64 on most Unix. Use `int`, `R_xlen_t`, `size_t` or a typedef chosen by a configure test; use `intptr_t` for pointers stored in integers. A Fortran `integer` is a C `int` on all R platforms; a Fortran `logical` is not guaranteed to be.
* **Avoid `-march=native`** and other flags that produce code for the build machine's CPU only, and avoid `sprintf()` and `vsprintf()`, which `R CMD check` reports; use `snprintf()`.
* **Include the R headers in the right order** (system headers first) and never inside `extern "C"`.

Source: https://cran.r-project.org/doc/manuals/r-release/R-exts.html#Writing-portable-packages[Writing R Extensions: Writing portable packages]

The two sections on portable code in the same chapter are https://cran.r-project.org/doc/manuals/r-release/R-exts.html#Portable-C-and-C_002b_002b-code[Writing R Extensions: Portable C and C{pp} code] and https://cran.r-project.org/doc/manuals/r-release/R-exts.html#Portable-Fortran-code[Writing R Extensions: Portable Fortran code]. For the C standard library itself, xref:programming-languages/c/program-structure.adoc[C program structure] and the xref:programming-languages/c/index.adoc[C Reference] pages on pointers and dynamic allocation explain the language rules that these R rules rest on.

== The C API: what a package may call

R has a very large number of entry points in its executable and shared library, and most of them are not for packages. The manual divides them into three classes. The *API* is the set that is documented in Writing R Extensions and declared in an installed header file: packages can use it, and it is changed only after deprecation. *Public* entry points are declared in an installed header and exported on all platforms, but are not documented and can change without notice: they must not be used in distributed code, and their declarations will eventually be moved out of the installed headers. *Private* entry points are used to build R and are not declared in the installed headers at all. What `R CMD check` calls "non-API" is everything outside the first class.

The header files follow the same division. `R.h` includes the commonly used headers from `R_ext/` (`Arith.h`, `Error.h`, `Memory.h`, `Print.h`, `Random.h`, `RS.h` and `Utils.h`); `Rinternals.h` declares the `SEXP` machinery used by `.Call()`; `Rmath.h` is R's standalone math library; `Rdynload.h` (in `R_ext/`) is what registration needs; `R_ext/Altrep.h` is for packages that implement their own alternate representation of vectors, like R's compact integer sequences; `R_ext/BLAS.h` and `R_ext/Lapack.h` declare the linear algebra routines. Headers not listed there are not part of the API, and the manual notes that `Rdefines.h`, an S-style macro layer, is no longer maintained (https://cran.r-project.org/doc/manuals/r-release/R-exts.html#Organization-of-header-files[Writing R Extensions: Organization of header files]).

=== What changed in R 4.5.0 and 4.6.0

R has been tightening the API in steps, and the NEWS files of R 4.5.0 and 4.6.0 list them. The facts that matter for a package author, in the order they happened:

* **R 4.5.0** added a section to Writing R Extensions, "Moving into C API compliance", to help authors move from non-API entry points to API ones; it will keep being updated. It made strict R headers the default, so the legacy definitions `PI`, `Calloc`, `Realloc` and `Free` are gone. It made `R_NO_REMAP` the default for C{pp}. It added many functions that replace non-API ones (`R_mkClosure`, `R_ClosureFormals`, `R_ClosureBody`, `R_ClosureEnv`, `R_ParentEnv`, `R_getVar` and `R_getVarEx`, `Rf_isDataFrame`, `Rf_charIsASCII` and more, `Rf_asRboolean`). It lengthened the list of non-API entry points that `R CMD check` reports, and upgraded some of the NOTEs to WARNINGs, as preparation for removing the declarations and hiding the entry points where possible. A C23 compiler is selected by default where available.
* **R 4.6.0** removed declarations from the installed headers: the functions `LOGICAL0`, `INTEGER0`, `REAL0`, `COMPLEX0` and `RAW0`, `DATAPTR`, `VECTOR_PTR`, `Rf_isFrame` (use `Rf_isDataFrame`), and the header `R_ext/PrtUtil.h` is no longer copied to the installed `include` directory. It marked a long list of further entry points as hidden and without declarations (`ENVFLAGS`, `FRAME`, `ENCLOS`, `HASHTAB`, `IS_S4_OBJECT`, `LEVELS`, `NAMED`, `OBJECT`, `SETLENGTH`, `TRUELENGTH`, `SET_BODY` and others). It upgraded to WARNINGs the check results for further non-API functions (including `BODY`, `FORMALS`, `CLOENV`, `SET_TYPEOF`, `STRING_PTR`, `ATTRIB`, `SET_ATTRIB`, `Rf_findVarInFrame3`, `R_nchar` and `Rf_GetOption`), and made the use of any non-API variable a check NOTE. And it added replacements: `R_mapAttrib`, `R_getAttributes`, `R_class`, `R_nrow`, `R_ncol` and a new experimental API for variable bindings.
* **R-devel (4.7.0)** has no C-level entry in its NEWS section at the time of writing.

=== Toolchain notes that affect compliance

Two toolchain facts interact with all this. First, the default C standard is C23 on R 4.5.0 and later where the compiler supports it, which rejects implicit function declarations and K&R-style definitions, so older C code needs fixing or `USE_C17`; and the default C{pp} standard is C{pp}20 from R 4.6.0, which has removed some library features that C{pp}17 still has (the manual gives `std::uncaught_exception` as an example and warns that some compilers accept removed features in C{pp}17 mode). Second, Rtools is versioned with R: Rtools45 serves R 4.5.0 and every later R including R-devel, so the Windows toolchain of this page is the same GCC 14.2 for R 4.5 and 4.6; the version history is in the next section. `R CMD config` prints the compiler settings that R will use, and a CI job that checks packages on Windows, macOS and Linux with the current release and R-devel finds toolchain differences before CRAN's checks do. How packages are checked and submitted is the subject of xref:programming-languages/r/publishing-to-cran.adoc[Publishing to CRAN].

|R 3.4.0 |`R_Calloc()`, `R_Realloc()` and `R_Free()` introduced. `tools::package_native_routine_registration_skeleton()` added. `R CMD check --as-cran` notes a package that neither registers its native routines nor declares its intentions on symbol search. The `styles` member of `R_CMethodDef` and `R_FortranMethodDef` removed; packages that register routines for `.C()` or `.Fortran()` had to be reinstalled.
|R 4.0.0 |Reference counting replaces the `NAMED` mechanism (use `MAYBE_SHARED()` and related macros). The Fortran print subroutines `labelpr`, `dblepr1`, `realpr1` and `intpr1` added. `Rf_installChar()` and `Rf_installTrChar()` become identical.
|R 4.2.0 |`Makevars.ucrt`, `Makefile.ucrt`, `configure.ucrt` and `cleanup.ucrt` supported and preferred to the `.win` files on Windows; Rtools42 (a UCRT toolchain based on gcc 10.3) recommended. R can be built with `-DSTRICT_R_HEADERS`; the S-compatibility macros `PROBLEM`, `ERROR`, `WARN` and the like are no longer defined in `R_ext/RS.h`; `R_Calloc` and friends are preferred and used in error messages.
|R 4.3.0 |The default C{pp} standard becomes C{pp}17 where available (C{pp}14 or C{pp}11 otherwise). `USE_FC_LEN_T` becomes the default, so C and C{pp} calls to BLAS and LAPACK routines with character arguments must append `FCONE`. Initial C{pp}23 support. Rtools43 (gcc 12).
|R 4.4.0 |Rtools44 (gcc 13). The environment variable `+_R_CXX_USE_NO_REMAP_+` makes `R CMD INSTALL` compile C{pp} with `-DR_NO_REMAP`. The manual dates the change that only a C{pp}17 compiler is selected by default to this release. `S4SXP` becomes `OBJSXP`.
|R 4.5.0 |A C23 compiler is selected by default where available. Strict R headers are the default: `PI`, `Calloc`, `Realloc` and `Free` are removed (use `M_PI`, `R_Calloc`, `R_Realloc`, `R_Free`). `R_NO_REMAP` is the default for C{pp}. The manual gains the section "Moving into C API compliance"; many API replacements are added (`R_mkClosure`, `R_getVar`, `Rf_isDataFrame`, `Rf_asRboolean`, ...); the list of non-API entry points that `R CMD check` reports grows, and some NOTEs become WARNINGs. C{pp}26 support begins (from R 4.5.3 on Windows). Rtools45 (gcc 14.2).
|R 4.6.0 |The default C{pp} standard becomes C{pp}20 where available, otherwise C{pp}17; C{pp}11 and C{pp}14 are no longer supported. Declarations of `LOGICAL0`, `INTEGER0`, `REAL0`, `COMPLEX0`, `RAW0`, `DATAPTR` and `VECTOR_PTR` removed from the installed headers; `Rf_isFrame` removed; a long list of internal entry points hidden and undeclared; more non-API functions become check WARNINGs and non-API variables a check NOTE. New: `R_mapAttrib`, `R_getAttributes`, `R_class`, `R_nrow`, `R_ncol`, an experimental API for variable bindings, and an experimental way to allocate resizable vectors.
|R-devel (4.7.0) |No C-level entry in the NEWS section at the time of writing. (Upcoming; not run.)
|===

Source: https://cran.r-project.org/doc/manuals/r-release/NEWS.html[R NEWS: Changes in R 3.2.0 to 4.6.1]

Registration itself is older (the manual's example converts the splines package, which was converted in 2001), but R 3.4.0 is when R added the skeleton generator and a check NOTE for packages that did not register, and registration has been expected practice for packages with compiled code since then. The environment variable `+_R_CHECK_NATIVE_ROUTINE_REGISTRATION_+`, which makes `R CMD check` report packages that do not register, is documented in R Internals (https://cran.r-project.org/doc/manuals/r-release/R-ints.html#Tools[R Internals: Tools]).

== Where older tutorials differ

[cols="3,3,4,1",options="header"]
|===
|Older tutorial writes |Current practice |Why |Since
|`.C()` as the main interface, with every vector passed as `pass:c[double *]` |`.Call()` with `SEXP`, or Rcpp |`.C()` copies every argument, cannot return an object other than the list of arguments, has no `NA` for strings and no attributes; the manual lists `.Call()` as the default and `.C()` for plain numbers |always
|`dyn.load("foo.so")` and `pass:c[.Call("foo", x)]` in a script, or in `.First.lib` |A package with `pass:c[useDynLib(pkg, .registration = TRUE)]` and `+.Call(symbol, ...)+` |The package loads the right object by itself, on every platform, and the symbol is looked up once |R 3.4.0 (check NOTE)
|`.Call("foo", x, PACKAGE = "pkg")` with a string |`.Call(foo, x)` or `.Call(C_foo, x)` with `R_forceSymbols()` |Registration makes the call faster, checks the arity and the types, and removes the chance of calling another package's `foo` |R 3.4.0
|A package without `R_init_pkg()` |`R_registerRoutines()` and `R_useDynamicSymbols(dll, FALSE)` |`R CMD check --as-cran` reports its absence |R 3.4.0
|`Calloc()`, `Free()`, `PI`, `error()`, `length()` |`R_Calloc()`, `R_Free()`, `M_PI`, `Rf_error()`, `Rf_length()` and `R_NO_REMAP` |Strict R headers are the default and the short names clash with other libraries |R 3.4.0 for `R_Calloc`; R 4.5.0 for the removal
|`NAMED(x)`, `SET_NAMED(x)` to decide whether to copy |`MAYBE_SHARED(x)` and the reference-counting macros |`NAMED` is hidden and the mechanism was replaced |R 4.0.0 (replaced), R 4.6.0 (hidden)
|`ATTRIB(x)`, `STRING_PTR(x)`, `DATAPTR(x)`, `SET_TYPEOF()`, `Rf_findVar()` |`Rf_getAttrib()`, `STRING_PTR_RO()`, `DATAPTR_RO()`, `R_getVar()` and the replacement table |Non-API entry points are no longer declared, and `R CMD check` warns |R 4.5.0 and R 4.6.0
|`+.C(..., DUP = FALSE)+` to avoid copying |`.Call()`, which does not copy |`DUP` is ignored |R 3.2.0
|`R CMD SHLIB` and `source()` or `dyn.load()` as the development workflow |A package with `pkgload::load_all()`, or `Rcpp::sourceCpp()` for one file |The package keeps the build, the registration and the tests together; `load_all()` recompiles |always
|The `inline` package and `Rcpp::cxxfunction()` |`Rcpp::cppFunction()`, `Rcpp::sourceCpp()` and `pass:c[// [[Rcpp::export\]\]]` |Attributes generate the glue and the wrapper; `inline` is a separate package that is not needed |Rcpp attributes
|Rcpp modules (`RCPP_MODULE`) for exposing functions |Attributes for functions; modules for exposing C{pp} classes |Attributes are shorter and more robust for functions; `sourceCpp()` still loads modules |always
|`sourceCpp()` called inside package code to compile when loaded |`src/` with `compileAttributes()`, compiled at install time |A package is compiled once, at install time; the help page of `sourceCpp()` says to use a package for more than one file |always
|`CXX_STD = CXX11` in `Makevars` |Nothing, or `CXX_STD = CXX17` (or `CXX20`) when the code needs it |C{pp}11 and C{pp}14 are no longer supported; the default is C{pp}17 or C{pp}20 |R 4.3.0, R 4.6.0
|`-fopenmp` in `PKG_CXXFLAGS` |`pass:c[$(SHLIB_OPENMP_CXXFLAGS)]` in the flags and `PKG_LIBS` |The flag is compiler-specific; Apple's clang has no OpenMP |always
|`PKG_CFLAGS = -Wall -O3 -march=native` in a distributed package |Those flags in `+~/.R/Makevars+` |`R CMD check` warns about non-portable flags in `Makevars` |always
|Fortran `+print *+` and `+write(6, *)+`, and `+character*255+` arguments |`dblepr()`, `intpr()`, `rexit()`; integer codes or `iso_c_binding` and `.C()` |Fortran I/O may not reach the console; character passing depends on the compiler and `USE_FC_LEN_T` |R 4.0.0 (`dblepr1`), R 4.3.0
|`rand()`, `srand()`, Fortran `random_number` |`GetRNGstate()`, `unif_rand()`, `PutRNGstate()` |`set.seed()` must work, and packages must not interfere |always
|===
