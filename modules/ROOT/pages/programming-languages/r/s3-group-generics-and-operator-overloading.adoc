Almost everything in R that looks like syntax, such as `pass:c[a + b]`, `a == b` or `round(a)`, is a function call, and most of those functions are internal generics: they look at the class attribute of their arguments and run an S3 method if one exists. R does not make you write one method per function. It collects about sixty-five of them into five groups (`Math`, `Ops`, `Summary`, `Complex` and `matrixOps`) so that a single function such as `Ops.money` can give a class all of its arithmetic and comparison operators at once. This page explains how those group methods are found, what the special variable `.Generic` holds, how a method for one member beats a method for the group, what R does when the two operands of an operator belong to different classes (the `Incompatible methods` warning and the `chooseOpsMethod()` generic added in R 4.3.0), and then builds a complete `money` class on doubles with a `currency` attribute.

The scripts also pass the default `lintr` linters; a `pass:c[# nolint:]` comment marks a line where the idiom on show is what a default linter dislikes (the variables `.Generic`, `.Method` and `.Group` do not exist outside a method, so `object_usage_linter` cannot see them, and a formal argument called `na.rm` or `use.names` is not snake case), so the linter does not hide the lesson. The names `books`, `loans`, `shelf_today` and `loan_days` come from the running library-shelf scenario described on the xref:programming-languages/r/index.adoc#shelf-files[section index]: a script that needs them starts with `source("scenario.R")`. == Why group generics exist

S3 dispatch normally starts in a generic written in R: `+print <- function(x, ...) UseMethod("print")+` looks at the class of `x` and calls `print.book` or `print.default`. Arithmetic and comparison do not work like that. `pass:c[+]`, `==`, `abs()`, `sum()` and their relatives are primitive or internal functions written in C. They are still generic, because the C code checks whether an argument has a class attribute and, if it does, looks for an R method first. If you had to define the method for each of them separately, a numeric-like class would need a dozen methods before `pass:c[x + y]`, `x * y`, `x < y`, `-x` and `round(x)` all behaved. The Language Definition describes the answer in its section on group methods: the functions and operators are grouped, a method can be written for a group, and it is also possible to write a method specific to one member of a group. It adds that there is no mechanism to define additional groups, so the set is fixed.

A method for a group is named `Group.class`: `Ops.money`, `Math.money`, `Summary.money`, `Complex.money` and `matrixOps.money`. A method for one member is named like any other S3 method, `generic.class`: `pass:c[+.money]`, `round.money`, `sum.money`. The two kinds can coexist, and the specific one wins (the dispatch rules are in the section <<dispatch-order,Dispatch order>>).

Source: https://cran.r-project.org/doc/manuals/r-release/R-lang.html#Group-methods[The R Language Definition: Group methods]

Three details in that table deserve a sentence each. The member list of `matrixOps` on the `groupGeneric` help page still says that the group contains the matrix multiplication operator only and that `crossprod()` and `tcrossprod()` are meant to follow; the help page of `crossprod()` and the R 4.4.0 NEWS say that they are generic since R 4.4.0 and can be handled through `matrixOps`, and the script in the section <<matrixops-and-complex,matrixOps and Complex>> confirms that on R 4.6.1. Second, the Language Definition (section 5.6) lists three groups, `Math`, `Summary` and `Ops`, and does not mention `Complex` or `matrixOps`; the help page is the more complete reference. Third, the group generics are not ordinary lazy functions: the help page states that there is no lazy evaluation of arguments for group-generic functions, and that if the operators are called as functions, argument names are removed so that matching is always positional.

A method is used for a group or one of its members only if the object has a `class` attribute, because the internal code dispatches on `oldClass()` and not on the implicit class returned by `class()`. A method named `Ops.integer` is therefore never called for `1L + 1L`; the script in <<dispatch-order,Dispatch order>> shows it.

== Group methods that ship with R

Base R defines group methods for `factor`, `data.frame` and `difftime` in the `Math`, `Ops` and `Summary` groups, an `ordered` method for `Ops`, `Date` and `POSIXt` methods for `Math` and `Ops`, `Summary` methods for the date-times, and `package_version` methods for `Ops` and `Summary`; the `stats` package adds `Ops.ts`. The easiest way to see what the installed R has is `methods()` with the group name. Also note that `shelf_today + late` adds a `Date` and a `difftime`, two classes with different methods, and yet gives no warning: R handles that particular pairing itself, which leads to the next topic.

== Writing a group method

A group method is an ordinary function with the prototype of its group and the name `Group.class`. Inside it, R has defined a handful of variables in the method's environment, and the most important is `.Generic`, the name of the member that was actually called. That is what lets one function stand in for dozens.

=== The special variables

The help page of `UseMethod()` lists the variables that the dispatch mechanism creates: `.Generic` is a length-one character vector with the name of the generic; `.Method` is the character vector naming the method (normally of length one, and of length two for the `Ops` group, with an empty string for an operand that did not select the method); `.Class` is the remaining class vector that `NextMethod()` uses. The group help page adds `.Group`, the name of the group used for dispatch, which is the empty string when a method specific to one member was chosen.

[source,r]
----
# A toy class: a count of items.
count <- function(n) structure(as.integer(n), class = "count")

Ops.count <- function(e1, e2) {
  generic <- .Generic # nolint: object_usage_linter.
  method <- .Method # nolint: object_usage_linter.
  group <- .Group # nolint: object_usage_linter.
  cat("group method for", generic, "\n")
  cat(".Method:", paste0("\"", method, "\""), "\n")
  cat(".Group: ", group, "\n")
  cat("nargs:  ", nargs(), "\n")
  invisible(NULL)
}

x <- count(1:3)
invisible(x + 1L)
#> group method for +
#> .Method: "Ops.count" ""
#> .Group:  Ops
#> nargs:   2
invisible(2L * x)
#> group method for *
#> .Method: "" "Ops.count"
#> .Group:  Ops
#> nargs:   2
invisible(x == x)
#> group method for ==
#> .Method: "Ops.count" "Ops.count"
#> .Group:  Ops
#> nargs:   2
invisible(-x)
#> group method for -
#> .Method: "Ops.count"
#> .Group:  Ops
#> nargs:   1
----

Source: https://search.r-project.org/R/refmans/base/html/UseMethod.html[R documentation: UseMethod]

Four things in that output are worth reading carefully. `.Method` has two elements for a binary operator and records which operand supplied the method: `"Ops.count" ""` for `x + 1L` and `"" "Ops.count"` for `2L * x`. A unary operator calls the method with one argument, and `nargs()` (or `missing(e2)`) is how the method tells; the `.Method` of a unary call has a single element. The group is `Ops` in every case. And the same method served `pass:c[+]`, `*`, `==` and `-` without being told apart by anything but `.Generic`.

The same variables exist in `Math` and `Summary` methods. Both methods below call `NextMethod()`, which runs the internal default with the original arguments, so the result is the one the unclassed vector would have produced.

[source,r]
----
# Math and Summary methods see .Generic too.
Math.count <- function(x, ...) {
  generic <- .Generic # nolint: object_usage_linter.
  cat("Math method for", generic, "with", ...length(), "extra argument(s)\n")
  NextMethod()
}
Summary.count <- function(..., na.rm = FALSE) { # nolint: object_name_linter.
  generic <- .Generic # nolint: object_usage_linter.
  cat("Summary method for", generic, "- na.rm is", na.rm, "\n")
  NextMethod()
}
unclass(round(x, 1))
#> Math method for round with 1 extra argument(s)
#> [1] 1 2 3
unclass(cumsum(x))
#> Math method for cumsum with 0 extra argument(s)
#> [1] 1 3 6
max(x, na.rm = TRUE)
#> Summary method for max - na.rm is TRUE
#> [1] 3
range(x)
#> Summary method for range - na.rm is FALSE
#> [1] 1 3
# Repeating na.rm is an error (R 4.4.0 and later).
tryCatch(
  sum(1:3, na.rm = TRUE, na.rm = FALSE),
  error = \(e) conditionMessage(e)
)
#> [1] "formal argument \"na.rm\" matched by multiple actual arguments"
----

Source: https://cran.r-project.org/doc/manuals/r-release/R-lang.html#NextMethod[The R Language Definition: NextMethod]

Two details are visible here. The `digits` of `round(x, 1)` arrives in the `+...+` of a `Math` method, which is why the prototype is `+Math(x, ...)+` and the method has no formal argument called `digits`. And `na.rm` is a formal argument of a `Summary` method, so a method can read it, but every other argument, including the data, arrives in `+...+`; `Summary.count` is called with the data in `+...+`, not in a named parameter. Since R 4.4.0 a `Summary` call that repeats `na.rm` is an error rather than a silent choice of one of the two values; the message in R 4.6.1 comes from ordinary argument matching and is shown at the end of the block above.

A `+switch(.Generic, ...)+` is the usual way to write a group method, and it has one trap that is easy to hit when writing a `Math` method. An arm with no value, such as `abs = ,`, falls through to the next arm that has one; if the arm after the last fall-through has no name, `switch()` treats it as the default, and a second unnamed arm after that is a second default. The result is an error rather than a wrong answer.

[source,r]
----
# A switch() arm without a value falls through to the next one; a trailing
# comma before the unnamed default makes that default ambiguous.
tryCatch(switch("a", a = , 1, 2), error = \(e) conditionMessage(e))
#> [1] "duplicate 'switch' defaults: '1' and '2'"
----

Source: https://search.r-project.org/R/refmans/base/html/switch.html[R documentation: switch]

The `lintr` default `object_usage_linter` reports `.Generic`, `.Method` and `.Group` as "no visible binding for global variable", because it analyses the function without the dispatch environment. The pattern used throughout this page avoids repeating a `nolint` comment on every use: copy the variable once at the top of the method (`pass:c[generic <- .Generic # nolint: object_usage_linter.]`) and use `generic` after that, which also reads better in a `switch()`.

[[reaching-the-default]]
=== Reaching the default behaviour

Most group methods end up wanting the work the internal code would have done: the actual arithmetic. There are three ways to get it, and one trap. The trap is to call the operator on the objects you received. `get(.Generic)(e1, e2)` with the original classed `e1` and `e2` is a call to the generic again, which dispatches to the same method, which calls the generic, until R gives up. The first block shows the error that ends it (the script lowers `options(expressions = 200)` so that the failure is quick and its message is deterministic; on a default setting R usually fails with the same error, or with a message about the C stack, after a few thousand levels).

[source,r]
----
# Calling the operator on the original objects dispatches to the method again.
Ops.loop <- function(e1, e2) {
  generic <- .Generic # nolint: object_usage_linter.
  get(generic)(e1, e2)
}
op <- options(expressions = 200)
tryCatch(structure(1, class = "loop") + 1, error = \(e) conditionMessage(e))
#> [1] "evaluation nested too deeply: infinite recursion / options(expressions=)?"
options(op)
----

Source: https://search.r-project.org/R/refmans/base/html/options.html[R documentation: options]

The three ways to avoid the recursion are in the second block of the script.

[source,r]
----
# The three ways of reaching the default behaviour from inside a method.
Ops.celsius <- function(e1, e2) {
  generic <- .Generic # nolint: object_usage_linter.
  by_get <- get(generic)(unclass(e1), unclass(e2))
  by_docall <- do.call(generic, list(unclass(e1), unclass(e2)))
  by_next <- unclass(NextMethod())
  list(by_get = by_get, by_docall = by_docall, by_next = by_next)
}
str(structure(c(10, 20), class = "celsius") + 1)
#> List of 3
#>  $ by_get   : num [1:2] 11 21
#>  $ by_docall: num [1:2] 11 21
#>  $ by_next  : num [1:2] 11 21
----

Source: https://search.r-project.org/R/refmans/base/html/UseMethod.html[R documentation: UseMethod]

All three return the same numbers. `get(.Generic)` and `+do.call(.Generic, ...)+` both call the operator by name and are safe only after `unclass()` has removed the class attribute, which is the reason older tutorials put `unclass()` into every method. `NextMethod()` is the more direct route: it calls the internal default with the original arguments, with dispatch switched off, and it keeps the attributes that the internal arithmetic keeps (for the arithmetic operators, the attributes of both operands, so the class survives). For the `money` class below, the methods use `unclass()` through a small helper because they also validate the operands and build the result themselves; the `Summary` method uses `NextMethod()` and wraps the result.

[[dispatch-order]]
=== Dispatch order: specific, group, internal

When R evaluates `a + b` and `a` has a class, it walks the class vector of the operand from left to right. For each class it looks for a specific method `pass:c[+.class]` first and for the group method `Ops.class` second; the first function it finds is the method. If no class in the vector has either, the internal code runs. The help page puts the consequence in one sentence: a method defined for an individual member of the group takes precedence over a method defined for the group as a whole. The Language Definition says the same in other words: a class method dominates a group method. The class order matters more than the kind of method, which the second part of the script shows: a group method for the first class beats a specific method for the second.

[source,r]
----
# One group method, one specific method.
temp <- function(x) structure(as.double(x), class = "temp")

Ops.temp <- function(e1, e2) {
  generic <- .Generic # nolint: object_usage_linter.
  cat("  Ops.temp handles", generic, "\n")
  get(generic)(unclass(e1), unclass(e2))
}
`*.temp` <- function(e1, e2) {
  cat("  *.temp handles *\n")
  temp(unclass(e1) * unclass(e2))
}

a <- temp(20)
b <- temp(2.5)
cat("a * b\n")
#> a * b
unclass(a * b)
#>   *.temp handles *
#> [1] 50
cat("a - b\n")
#> a - b
unclass(a - b)
#>   Ops.temp handles -
#> [1] 17.5
cat("a > b\n")
#> a > b
a > b
#>   Ops.temp handles >
#> [1] TRUE

# The class vector is searched from left to right; within one class the
# specific method comes before the group method.
x <- structure(1, class = c("first", "second"))
`*.second` <- function(e1, e2) "the specific method of second"
Ops.first <- function(e1, e2) "the group method of first"
x * 2
#> [1] "the group method of first"
`*.first` <- function(e1, e2) "the specific method of first"
x * 2
#> [1] "the specific method of first"
----

Source: https://search.r-project.org/R/refmans/base/html/groupGeneric.html[R documentation: groupGeneric]

`*` found `pass:c[*.temp]` and never looked at `Ops.temp`; `-` and `>` have no specific method and went to the group method. In the class-vector example `x * 2` used `Ops.first` although a specific `pass:c[*.second]` existed, and used `pass:c[*.first]` as soon as that was defined. Three more consequences are visible in the rest of the script:

[source,r]
----
# NextMethod() from a specific method goes straight to the internal code.
`-.temp` <- function(e1, e2) {
  cat("  -.temp calls NextMethod()\n")
  NextMethod()
}
r <- a - b
#>   -.temp calls NextMethod()
cat("class of the result:", class(r), "\n")
#> class of the result: temp
unclass(r)
#> [1] 17.5

# A method for one member does not create a method for the group.
`*.money_like` <- function(e1, e2) "multiplied"
m <- structure(2, class = "money_like")
m * 3
#> [1] "multiplied"
unclass(m + 3)
#> [1] 5

# Group methods dispatch on the class attribute only, not on the implicit class.
Ops.integer <- function(e1, e2) "a method for integer"
1L + 1L
#> [1] 2
----

Source: https://cran.r-project.org/doc/manuals/r-release/R-lang.html#Method-dispatching[The R Language Definition: Method dispatching]

* A `NextMethod()` call inside `pass:c[-.temp]` went directly to the internal subtraction, which kept the class `temp`; it did not go through the group method `Ops.temp` that exists for the class. If a specific method needs the logic of the group method, move that logic into a helper function that both call.
* A method for one member (`pass:c[*.money_like]`) does not create a method for the group: `m + 3` ran the internal addition, and kept the class attribute of `m`.
* `Ops.integer` was never called for `1L + 1L`: group dispatch looks at the class attribute only, not at the implicit class that `class(1L)` reports. The same is true of every internal generic, which is why you can write `print.numeric` or `Ops.numeric` but cannot change what `1 + 1` does.

[[double-dispatch]]
== Double dispatch for Ops

`UseMethod()` looks at one argument. The `Ops` group looks at two, which is what makes `Date + difftime` or `money * 2` and `2 * money` work with a single method. The help page describes the algorithm: for each operand the class vector is examined to find a specific (preferred) or `Ops` method. If a method is found for just one operand, or the same method is found for both, it is used. If different methods are found, R calls the generic `chooseOpsMethod()` to pick one, and if that does not resolve the conflict there is a warning about incompatible methods, and in that case, or when no method is found for either operand, the internal method is used. The `Summary` group dispatches on the first argument supplied only, and `Math` and `Complex` on their single argument, so the conflict can only arise for `Ops` and `matrixOps`.

The script below makes two classes with different methods for the same operator, `foo` with a specific method for `*`, `pass:c[*.foo]`, and `bar` with the group method `Ops.bar`, and a small helper that runs an expression, mutes the warnings and returns both the value and the warning messages.

Read the output from the top. `foo() * foo()`, `foo() * 2` and `2 * foo()` use the method of `foo`: one method found, or the same method for both operands. `bar() * bar()` uses the group method of `bar`. The warning names the two methods in the order of the operands, so `bar() * foo()` reports them the other way round. The warning is easy to miss in a script, and the result is a plain number that has silently lost the meaning of both classes; that is the failure to design against.

A subclass that overrides a group method should keep the parent's method working for mixed operands, or define `chooseOpsMethod()` (next section) to say which of the two wins.

[[choose-ops-method]]
== chooseOpsMethod(): letting a class win

R 4.3.0 added the generic `chooseOpsMethod(x, y, mx, my, cl, reverse)` for exactly this conflict. The NEWS entry describes it as a mechanism for objects to resolve the cases in which two suitable methods are found for an `Ops` call, and says that it "supports experimenting with alternative object systems"; the help page describes it as the function the `Ops` group generic calls when two suitable methods are found. It is an S3 generic that dispatches on `x`, with these arguments:

* `x` and `y`: the objects being dispatched on (the first call has `x` as the first operand);
* `mx` and `my`: the methods that were found for `x` and for `y`;
* `cl`: the call to the group generic;
* `reverse`: `FALSE` in the first call; `TRUE` in the second call, in which `x` and `y` (and `mx` and `my`) are swapped.

It must return `TRUE` or `FALSE`, and `TRUE` means that the method `mx` should be used. R first calls it with the operands in the order they were written. If the answer is `FALSE` it calls it again with the two operands swapped and `reverse = TRUE`, so a class only has to define `chooseOpsMethod.myclass` and say `TRUE` to have its own method win regardless of the side it stands on. If neither call answers `TRUE`, the warning from the previous section is signalled. The default method in base R returns `FALSE`.

[source,r]
----
foo <- function() structure(1, class = "foo")
bar <- function() structure(2, class = "bar")
`*.foo` <- function(e1, e2) "the method of foo"
Ops.bar <- function(e1, e2) "the group method of bar"

# The default says "no preference" for every pair.
names(formals(chooseOpsMethod))
#> [1] "x"       "y"       "mx"      "my"      "cl"      "reverse"
body(getS3method("chooseOpsMethod", "default"))
#> [1] FALSE

# bar declares that its method wins against anything.
chooseOpsMethod.bar <- function(x, y, mx, my, cl, reverse) TRUE
foo() * bar()
#> [1] "the group method of bar"
bar() * foo()
#> [1] "the group method of bar"
----

Source: https://search.r-project.org/R/refmans/base/html/chooseOpsMethod.html[R documentation: chooseOpsMethod]

`chooseOpsMethod.bar` returning `TRUE` makes `bar` win in both orders: for `foo() * bar()` R first asks `foo` (no method, so the default answers `FALSE`) and then asks `bar` with the arguments swapped. The second part of the script is a more careful policy that only claims the operation when the other operand is a `foo`, and records every call; the log shows that only `bar` was ever consulted, once with `reverse = TRUE` for `foo() * bar()` and once with `reverse = FALSE` for `bar() * foo()`.

  seen$calls <- c(
    seen$calls,
    sprintf("x is %s, reverse = %s", class(x), reverse)
  )
  inherits(y, "foo")
}

Because `chooseOpsMethod()` is an ordinary S3 generic, a package registers its methods with `S3method(chooseOpsMethod, myclass)`. It is not a replacement for good design: the winning method still has to understand the other operand, or refuse it clearly, which is what `Ops.money` does below for dates. It matters most when two independently written packages define classes that must interoperate, and it is the hook that packages implementing alternative object systems use: the S7 package (CRAN version 0.2.2 when this page was checked) registers `chooseOpsMethod.S7_object`, which `methods("chooseOpsMethod")` lists after `library(S7)`. That remark was checked separately and is not part of any script on this page.

R's own S4 system has a separate and richer mechanism for the same job: the S4 group generics `Arith`, `Compare` and `Logic` (members of `Ops`), `Math`, `Math2` (which contains `round` and `signif`), `Summary` and `Complex` select their methods from the signature of both arguments; they are documented in `?S4groupGeneric` and xref:programming-languages/r/s4-classes-and-methods.adoc[S4 Classes and Methods].

[[money-class]]
== A money class built on doubles

The rest of the page builds one class in steps: `money`, a double vector with a `currency` attribute, used for the late fees of the library shelf. The design is deliberately small, and the rules are the point:

* a `money` vector has one currency, stored as an attribute, and every operation keeps it;
* money can be added to and subtracted from money of the same currency, scaled by a plain number and divided by a plain number; the ratio of two amounts is a plain number;
* it can be compared with money of the same currency;
* it can be rounded, summed, ranged and averaged; it cannot be raised to a power, square-rooted, or multiplied by itself;
* anything else is an error with a message that names the problem, never a silent `NA` or a silent loss of the class.

Doubles are used because the aim is to show the S3 machinery. Real accounting code stores whole minor units (cents) in integers, or uses a decimal type, because binary floating point cannot represent most decimal fractions exactly; the last script of this page shows `0.1 + 0.2 == 0.3` failing for the same reason. The whole class lives in one script, which is shown below in consecutive pieces. Each block continues the previous one, the output after each expression is what the script printed, and the blocks together are the script from top to bottom.

=== Constructor, formatting and printing

The pattern from xref:programming-languages/r/s3-classes-and-generics.adoc[S3 Classes and Generics] applies: a low-level `new_money()` that only builds the object, a friendly `money()` that validates, and accessors. `amount()` strips the attributes so that arithmetic on the numbers can never dispatch back to the class. `format.money()` formats with `+formatC(..., format = "f", digits = 2, big.mark = ",")+` and appends the currency; its `digits` argument defaults to `NULL` because `print.data.frame()` passes `digits = NULL` down to `format()`, and a method that did not tolerate it would print four decimals in a data frame. The `%||%` operator used for the default is in base R since 4.4.0. `print.money()` prints the formatted strings without quotes, right-aligned, and returns its argument invisibly, as every `print` method should.

=== Keeping the class through subsetting, c(), rep() and unique()

The default `[` keeps names, dimensions and dimnames and drops every other attribute, including the class. A vector class must therefore define `[` (and usually `[[` and `pass:c[[<-]`) or every subset turns back into a bare number. The standard shape is to call `NextMethod()` and re-wrap the result with the attribute taken from the original. The same applies to `c()`, `rep()` and `unique()`: each of them builds a new vector and does not keep attributes. `rev()` and `sort()` need no method of their own: the body of `rev.default` is `x[length(x):1L]` and `sort.default` indexes with `pass:c[x[order(...)\]]` for any object, so both use `pass:c[[.money]` automatically. `length()` needs nothing either, because the length of the underlying vector is the length of the money vector; it would need a method for a class built on a list.

Two details of `c.money()` come from how `c()` dispatches. It dispatches on its first argument only, so the method receives every argument, including the named `recursive` and `use.names`, in its formals; leaving them out makes `+c(..., recursive = TRUE)+`, which `range.default` calls internally, put `TRUE` into the list of parts. Since R 4.1.0 `c()` also removes `NULL` arguments before dispatching to methods (but keeps a `NULL` first argument for backward compatibility), which simplifies such methods. The assignment method `pass:c[[<-.money]` refuses to store a plain number or another currency, because the assignment would silently put numbers of the wrong kind into the vector.

=== The Ops group

`Ops.money` carries the rules from the list above in one `+switch(generic, ...)+`. A helper `same_currency()` raises the error for mixed currencies. Notice the structure: the unary case is handled first, using `nargs()`; then the binary operators are grouped by the rule they obey, with the fall-through arms (`pass:c["+" = , "-" = { ... }]`) used for the operators that share a rule; and the final unnamed arm is the default, which turns every other member of the group (`+^+`, `%%`, `%/%`, `&`, `|`) into an error.

[source,r]
----
# Part 3: the Ops group.
same_currency <- function(e1, e2, verb) {
  if (!identical(currency(e1), currency(e2))) {
    stop("cannot ", verb, " ", currency(e1), " and ", currency(e2),
         call. = FALSE)
  }
}

Ops.money <- function(e1, e2) {
  generic <- .Generic # nolint: object_usage_linter.
  if (nargs() == 1L) {
    if (generic %in% c("+", "-")) {
      return(new_money(get(generic)(amount(e1)), currency(e1)))
    }
    stop("unary ", generic, " is not meaningful for money", call. = FALSE)
  }
  both <- inherits(e1, "money") && inherits(e2, "money")
  switch(generic,
    "+" = , "-" = {
      if (!both) stop("both operands must be money", call. = FALSE)
      same_currency(e1, e2, c("+" = "add", "-" = "subtract")[[generic]])
      new_money(get(generic)(amount(e1), amount(e2)), currency(e1))
    },
    "*" = {
      if (both) stop("cannot multiply money by money", call. = FALSE)
      cur <- currency(if (inherits(e1, "money")) e1 else e2)
      new_money(amount(e1) * amount(e2), cur)
    },
    "/" = {
      if (both) {
        same_currency(e1, e2, "divide")
        amount(e1) / amount(e2)
      } else if (inherits(e1, "money")) {
        new_money(amount(e1) / amount(e2), currency(e1))
      } else {
        stop("cannot divide a number by money", call. = FALSE)
      }
    },
    "==" = , "!=" = , "<" = , ">" = , "<=" = , ">=" = {
      if (!both) stop("can only compare money with money", call. = FALSE)
      same_currency(e1, e2, "compare")
      get(generic)(amount(e1), amount(e2))
    },
    stop(sQuote(generic), " is not meaningful for money", call. = FALSE)
  )
}
----

=== The Math group

=== The Summary group

`Summary.money` dispatches on the first argument and receives all of them in `+...+`, so the method checks every one of them: it demands that all are money and all have the same currency. It then calls `NextMethod()`, which runs the internal `sum`, `min`, `max` or `range` on the original arguments, and wraps the plain number it returns in `new_money()`; the internal code drops the attributes, so the re-wrapping is not optional. `na.rm` is a formal argument of the method, and `NextMethod()` passes it on. `prod`, `all` and `any` are members of the group and are refused.

[source,r]
----
# Part 5: the Summary group.
Summary.money <- function(..., na.rm = FALSE) { # nolint: object_name_linter.
  generic <- .Generic # nolint: object_usage_linter.
  if (!generic %in% c("sum", "min", "max", "range")) {
    stop(generic, "() is not meaningful for money", call. = FALSE)
  }
  parts <- list(...)
  if (!all(vapply(parts, inherits, logical(1), what = "money"))) {
    stop("all arguments must be money", call. = FALSE)
  }
  cur <- unique(vapply(parts, currency, character(1)))
  if (length(cur) != 1L) {
    stop("cannot combine ", paste(cur, collapse = " and "), call. = FALSE)
  }
  new_money(NextMethod(), cur)
}

=== Generics that are not in a group

A frequent mistake, in tutorials and in practice, is to expect a group method to cover functions that look like members. It does not. `mean`, `median`, `rev`, `sort`, `unique`, `rep`, `c`, `seq`, `diff`, `format`, `print`, `as.character` and `as.double` are not members of any group; some are internal generics, some are ordinary S3 generics written in R, and each dispatches on its own. The following script uses a class with a `currency` attribute and no methods at all, and records, for each call, what class came back and whether the attribute survived. The `group` column says which group the function belongs to, if any.

`mean.money` and `median.money` unwrap, compute and re-wrap; `median.money` has to name `na.rm` as a formal because `median()` has it as a formal argument. `seq.money` supports `from`, `to` and `by`, and `seq()` dispatches on its first argument. `as.character.money` makes `paste()` use the formatted text (the `paste` result is `fee: 0.25 EUR`, not the bare number), and `as.double.money` returns the number; `as.numeric` is the same function, so methods are written for `as.double`.

The first line of the block is the reason for `pass:c[$.money]`: the default `$` stops on atomic vectors. A `$` method is easy to write but needs care on a class built on an atomic vector. It receives the name as a string already, `x$name` never evaluates the name, and any code that calls `$` on a `money` vector will meet your method. Define it only when the class has real named fields to expose, and prefer `[[` with a name (where names have meaning) or accessor functions such as `currency()` for everything else. A list-based class such as the `book` class of the scenario should not define `$` at all, because the default does exactly what is needed. On the other hand, `pass:c[$<-]` and `pass:c[[[<-]` are separate generics and need separate methods if the object should be modifiable by name.

[[sorting-and-xtfrm]]
=== Sorting and xtfrm()

`sort()` and `order()` rank objects with the generic `xtfrm()`, which returns a numeric vector that sorts in the same order as the objects. For a numeric class the default method returns `unclass(x)`, so `money` sorted correctly above with no `xtfrm.money`. The method matters when the class stores something that does not sort the way its numbers or text do. A copy of a library book has a condition, stored as text but ranked by quality; alphabetical order puts `fair` before `good` before `new` before `poor`.

[source,r]
----
# The condition of a library copy, stored as text but ordered by quality.
condition_levels <- c("poor", "fair", "good", "new")

copy_condition <- function(x = character()) {
  stopifnot(all(x %in% condition_levels))
  structure(x, class = "copy_condition")
}
`[.copy_condition` <- function(x, ...) copy_condition(NextMethod())
format.copy_condition <- function(x, ...) format(unclass(x), ...)
print.copy_condition <- function(x, ...) {
  print(format(x), quote = FALSE)
  invisible(x)
}

shelf <- copy_condition(c("good", "new", "poor", "fair", "good"))

# Without xtfrm() the default sorts the text alphabetically.
sort(shelf)
#> [1] fair good good new  poor
order(shelf)
#> [1] 4 1 5 2 3

# xtfrm() returns the sort keys; sort() and order() use it for any object.
xtfrm.copy_condition <- function(x) match(unclass(x), condition_levels)
xtfrm(shelf)
#> [1] 3 4 1 2 3
sort(shelf)
#> [1] poor fair good good new
sort(shelf, decreasing = TRUE)
#> [1] new  good good fair poor
order(shelf)
#> [1] 3 4 1 5 2

# A numeric class needs no method: the default returns the numbers.
getS3method("xtfrm", "default")(structure(c(3, 1, 2), class = "anything"))
#> [1] 3 1 2
----

Source: https://search.r-project.org/R/refmans/base/html/xtfrm.html[R documentation: xtfrm]

Without `xtfrm.copy_condition` the default ranks the text alphabetically; with it, `sort()` and `order()` use the quality order, and `sort(shelf, decreasing = TRUE)` reverses it. `sort()` also needs the `[` method here, since `sort.default` builds its answer with `x[order(x)]` for objects. The NEWS for R 4.0.0 records that `sort.list()` was extended to work for non-atomic objects through `xtfrm()` methods.

=== Money meets a date

The last part of the script crosses the class with one that has its own method. `late_fee[1:3] + shelf_today` adds money to a `Date`; the methods are `Ops.money` and `pass:c[+.Date]`, they differ, and `chooseOpsMethod()` is not defined yet, so R warns and uses the internal addition. `suppressWarnings()` shows what comes out: the number of days since 1970 added to the fee and presented as 20,634 EUR, which is a wrong amount that looks plausible. Defining `chooseOpsMethod.money()` that returns `TRUE` makes the money method win in both orders, and `Ops.money` then refuses the date with its own message; the money-to-money addition at the end still works.

[source,r]
----
# Part 8: mixing money with a class that has its own method.
tryCatch(late_fee[1:3] + shelf_today, warning = \(w) conditionMessage(w))
#> [1] "Incompatible methods (\"Ops.money\", \"+.Date\") for \"+\""
suppressWarnings(late_fee[1:3] + shelf_today)
#> [1] 20,634.00 EUR 20,634.00 EUR 20,634.00 EUR

chooseOpsMethod.money <- function(x, y, mx, my, cl, reverse) TRUE
tryCatch(late_fee[1:3] + shelf_today, error = \(e) conditionMessage(e))
#> [1] "both operands must be money"
tryCatch(shelf_today + late_fee[1:3], error = \(e) conditionMessage(e))
#> [1] "both operands must be money"
tryCatch(late_fee[1:3] == shelf_today, error = \(e) conditionMessage(e))
#> [1] "can only compare money with money"
late_fee[1:3] + money(1)
#> [1] 1.00 EUR 1.00 EUR 1.00 EUR
----

Source: https://search.r-project.org/R/refmans/base/html/chooseOpsMethod.html[R documentation: chooseOpsMethod]

That is the practical use of `chooseOpsMethod()`: it does not decide what the combination means, it decides whose method gets to decide. A class that wants to interoperate with another one would handle that operand inside `Ops.money` instead of refusing it.

[[matrixops-and-complex]]
== matrixOps and Complex

The two smallest groups rarely need a method of their own, but they follow the same rules. `matrixOps` was added in R 4.3.0 with `%*%`, which became an S3 generic with it; `crossprod()` and `tcrossprod()` became generic in R 4.4.0 and joined the group. Its members dispatch on both arguments exactly like `Ops`, and `.Generic` tells the method which one was called. Because `crossprod(x)` is called with one argument, the method has to handle a missing `y`. The `Complex` group dispatches on `z`.

[source,r]
----
# matrixOps: %*% dispatches on both arguments, like Ops (R 4.3.0 and later);
# crossprod() and tcrossprod() joined the group in R 4.4.0.
counts <- function(m) structure(m, class = "counts")

matrixOps.counts <- function(x, y) {
  generic <- .Generic # nolint: object_usage_linter.
  group <- .Group # nolint: object_usage_linter.
  cat("matrixOps method:", generic, "in group", group, "\n")
  if (missing(y)) {
    y <- x
  }
  counts(get(generic)(unclass(x), unclass(y)))
}

m <- counts(matrix(1:4, nrow = 2))
unclass(m %*% m)

#> [2,]   10   22

#>      [,1] [,2]
#> [1,]    4    4

== Group methods in a package

At top level of a script, or in the global environment of a session, `Ops.money` is found because it is visible from the call. Inside a package the methods live in the namespace, and S3 dispatch finds them there only through the registration database (a function that is merely defined in the namespace is not visible from the caller), so they have to be registered. The `NAMESPACE` file of a package that contains the `money` class registers each method with an `S3method()` directive; the names of operators and other non-standard names must be quoted, and group methods use the group name as the generic.

[source,text]
----
S3method("[", money)
S3method("[[", money)
S3method("[<-", money)
S3method("$", money)
S3method(Math, money)
S3method(Ops, money)
S3method(Summary, money)
S3method(c, money)
S3method(chooseOpsMethod, money)
S3method(format, money)
S3method(mean, money)
S3method(print, money)
----

Source: https://cran.r-project.org/doc/manuals/r-release/R-exts.html#Registering-S3-methods[Writing R Extensions: Registering S3 methods]

With roxygen2 these lines are generated from `@export` or `@exportS3Method` tags on the method definitions; see xref:programming-languages/r/documentation-with-rd-roxygen2-and-vignettes.adoc[Documentation with Rd, roxygen2 and Vignettes] and xref:programming-languages/r/packages-libraries-and-namespaces.adoc[Packages, Libraries and Namespaces]. A method defined for a generic from another package (such as `median`, which is in `stats`) needs that generic to be imported as well. Writing R Extensions also notes that usage sections of Rd files for S3 methods, for members of the `Ops` group and for user-defined infix operators follow the same naming rules.

== Where older tutorials differ

Many S3 tutorials were written before `chooseOpsMethod()` and before the classed-atomic improvements of `as.data.frame()`. The table below lists approaches and simplifications that are common in older material and what R 4.6.1 does instead.

[cols="3,3,4",options="header"]
|===
|Older approach or simplification |Current behaviour |Why
|S3 dispatches on the first argument only.
|`Ops` and `matrixOps` examine both operands.
|The group help page says that the classes of both arguments are considered. `Math`, `Summary` and `Complex` use one argument, `UseMethod()` generics use the first.

|Resolve incompatible methods by giving both classes the same method.
|Define `chooseOpsMethod()` for one of the classes (R 4.3.0).
|It is the supported way to say which method wins; before 4.3.0 there was only the warning and the internal fallback.

|Define `pass:c[+.money]`, `-.money`, `pass:c[*.money]` and so on, one by one.
|Define `Ops.money` and use `.Generic`.
|One group method covers the 16 members of `Ops`; the specific methods are for the exceptions, and they win over the group.

|`pass:c["+.money" <- function(e1, e2)]` with the name in quotes
|Identical to the backtick form.
|The assignment creates the same binding; the string form only matters for style (and `lintr` may flag it).

|Write `+as.data.frame.money <- as.data.frame.vector+` so the class can be a column.
|Not needed in R 4.6.1; the default method handles classed atomic vectors since R 4.3.0.
|The NEWS entry of R 4.3.0 names `roman`, `octmode` and `hexmode`; the deprecation in R 4.4.0 concerns direct calls of the base `as.data.frame.<class>()` methods.

|Using `unclass()` in every method.
|Needed when you call the operator by name; `NextMethod()` and a helper that strips attributes keep it in one place.
|Calling the operator on classed objects recurses until R stops it.

|`mean`, `median` and `range` are covered by the `Summary` group.
|Only `range` is. `mean` and `median` are ordinary generics.
|The group has seven members: `all`, `any`, `sum`, `prod`, `min`, `max`, `range`.

|`all.equal()` and `identical()` check the numbers.
|Both also compare the attributes and the class.
|See the script below: `all.equal()` reports attribute differences, `==` on doubles has the usual rounding problem.
|===

Source: https://cran.r-project.org/doc/manuals/r-release/NEWS.html[R NEWS: Changes in R 4.3.0 and 4.4.0]

The remaining items of the table are shown by a script: strings as method names, one method per operator with an `unclass()` in each, a class that forgets `pass:c[[.price]`, comparisons with `all.equal()`, and the data frame column that needs no `as.data.frame` method any more.

[source,r]
----
price <- function(x) structure(as.double(x), class = "price")

# 1. Method names written as strings: the same binding as the backtick form.
"+.price" <- function(e1, e2) price(unclass(e1) + unclass(e2)) # nolint
identical(
  get("+.price"),
  getS3method("+", "price")
)
#> [1] TRUE

# 2. One method per operator with unclass() in each, instead of Ops.price;
#    the operators without a method fall back to the internal code.
"-.price" <- function(e1, e2) price(unclass(e1) - unclass(e2)) # nolint
unclass(price(5) + price(2.5) - price(1))
#> [1] 6.5
class(price(5) * price(2))
#> [1] "price"
class(price(5) > price(2))
#> [1] "logical"

# 3. Forgetting [.price: the class (and everything else) is gone after [ .
p <- price(c(1.5, 2, 8))
class(p[1:2])
#> [1] "numeric"
class(rev(p))
#> [1] "numeric"

# 4. all.equal() on classed vectors compares the attributes too.
all.equal(p, c(1.5, 2, 8))
#> [1] "Attributes: < Modes: list, NULL >"
#> [2] "Attributes: < Lengths: 1, 0 >"
#> [3] "Attributes: < names for target but not for current >"
#> [4] "Attributes: < current is not list-like >"
#> [5] "target is price, current is numeric"
isTRUE(all.equal(p, c(1.5, 2, 8)))
#> [1] FALSE
isTRUE(all.equal(unclass(p), c(1.5, 2, 8)))
#> [1] TRUE
all.equal(price(0.1 + 0.2), price(0.3))
#> [1] TRUE
price(0.1 + 0.2) == price(0.3)
#> [1] FALSE
identical(price(0.1 + 0.2), price(0.3))
#> [1] FALSE

# 5. No as.data.frame.price <- as.data.frame.vector is needed any more.
d <- data.frame(id = 1:3, fee = p)
class(d$fee)
#> [1] "price"
nrow(d[d$fee > 1.75, ])
#> [1] 2
----

Source: https://search.r-project.org/R/refmans/base/html/groupGeneric.html[R documentation: groupGeneric]

A class with a method for `pass:c[+]` and `-` only still adds, multiplies and compares: the operators without a method run the internal code, which keeps the class for arithmetic and answers a plain logical for a comparison. The consequence is that an incomplete class does not fail, it silently does the wrong thing, and the cure is the group method. Subsetting a class without `pass:c[[.price]` returns a bare number for `p[1:2]` and for `rev(p)`. `all.equal()` on a classed vector and a plain one reports the difference in attributes and class (five lines), and with `isTRUE()` it is `FALSE`; `0.1 + 0.2 == 0.3` is `FALSE` for classed doubles, as for any doubles, while `all.equal()` with its tolerance answers `TRUE`. Finally `data.frame(id = 1:3, fee = p)` keeps the class `price` without an `as.data.frame.price` method, and the comparison `d$fee > 1.75` selects rows.
