R changes slowly and on purpose: a feature is announced in NEWS, usually deprecated before it is removed, and the manuals are updated with the release. This page puts the changes of seven releases, R 4.0.0 (2020) to R 4.6.1 (2026), in one place: a table of every language or base-R change with a link to the page of this reference that explains it, a section per release with the code that shows the difference, the removals that stop an old script, the table of habits that older tutorials still teach, the changes that R-devel lists for the next releases, and the ways to follow them.

Every example is a script that was run with `Rscript` on R 4.6.1 with warnings printed as they happen (`options(warn = 1)`), and the lines that start with `+#>+` are what it printed. The scripts also pass the default `lintr` linters; a `pass:c[# nolint:]` comment marks a line where the idiom on show is the one a default linter dislikes. The names `books`, `loans`, `shelf_today`, `loan_days` come from the running library-shelf scenario described on the xref:programming-languages/r/index.adoc#shelf-files[section index]: a script that needs them starts with `source("scenario.R")`. Because only R 4.6.1 was available, a "before" line is one of three kinds. It is an older idiom that still runs on 4.6.1 and is run (the `stringsAsFactors = TRUE` argument, a hand-written `%||%`, a magrittr pipe). Or it is an older form that now fails, caught with `tryCatch()` so that the script exits normally and the real 4.6.1 message is shown. Or it is a statement taken from NEWS and not run. No block claims output from R 4.0 to 4.5, which were not run for this page. Where a message contains quotation marks, they are the typographic quotes R prints in a UTF-8 locale.

This page does not repeat the pages it points to. Each row of the main table links to the page that documents the feature in depth, and most of those pages end with a `== Version notes` section that lists the NEWS entries of that topic; the facts here agree with them. The pitfalls that are not tied to a release (partial matching with `$`, `1:length(x)`, `sapply()` simplification, `if (NA)`, growing vectors and the rest) are in xref:programming-languages/r/idioms-and-common-pitfalls.adoc[Idioms and Common Pitfalls].

== How R versions are numbered and released

R uses a major.minor.patchlevel numbering scheme, and the R FAQ says where to find the versions in use: `r-release` is the current release, `r-patched` is the current release plus bug fixes, and `r-devel` is the version heading for the next minor or major release, where new features are introduced (https://cran.r-project.org/doc/FAQ/R-FAQ.html#What-is-the-current-version-of-R_003f[R FAQ 2.3: What is the current version of R?]). The R Core release schedule is annual: a new x.y.0 release in spring, patch releases as needed, and a final patch release of the previous version shortly before the next x.y.0 (https://developer.r-project.org/[R Developer Page: release schedule]). The dates in the next table are those of the source tarballs on CRAN, listed for the R 4 series at https://cran.r-project.org/src/base/R-4/[CRAN: source tarballs of R 4]; R 4.6.1 is the version that every manual says it describes.

Two habits of the project explain the shape of the changes below. First, a change that can break existing code is usually announced before it happens. The sequences that appear on this page are: `&&` and `||` with an operand of length greater than one gave a warning in R 4.2.0 and are an error since R 4.3.0; `default.stringsAsFactors()` was deprecated in 4.2.0 and is defunct since 4.3.0; `is.R()` was deprecated in 4.4.0 and is defunct since 4.5.0; the `xfig()` device was deprecated in 4.4.0 and removed in 4.5.0; and `+structure(NULL, ...)+` was deprecated in R 3.4.0 and is defunct since 4.6.0. The rule for `if` and `while` followed the same path over a longer time: a warning in the earlier releases and an error since R 4.2.0. The functions `.Deprecated()` and `.Defunct()` that signal these conditions are in xref:programming-languages/r/defensive-programming-and-input-validation.adoc#_evolving_an_api_deprecated_and_defunct[Defensive Programming and Input Validation]. Second, a new feature that is not settled is labelled as experimental, in NEWS or on its help page, and this page repeats that label: NEWS calls the use of `+_+` to start an extraction chain (R 4.3.0), `Tailcall()` and `Exec()` and `declare()` (R 4.4.0) experimental, and the help page of `use()` (available since R 4.4.0) says that its functionality is still experimental. Experimental features may be changed or dropped, so a package that has to run on many R versions should not build on them.

== R 4.0.0 (2020-04-24)

R 4.0.0 changed the defaults and the internals more than any later release of the series, and the NEWS opens it with the reminder that packages with compiled code needed to be reinstalled under the new version. For code written in R, five of its changes are visible every day: strings stay strings, raw string constants exist, a matrix has two classes, the default colours changed, and `list2DF()` is a new way to build a data frame. A sixth, reference counting, changed how R decides when to copy and is invisible from R code.

=== stringsAsFactors = FALSE is the default

The NEWS entry of R 4.0.0 says that R now uses a `stringsAsFactors = FALSE` default, "and hence by default no longer converts strings to factors" in calls to `data.frame()` and `read.table()`, and adds that a large number of packages had relied on the previous behaviour and needed updating. `read.csv()` is `read.table()` with different defaults, so it follows. The older behaviour is still one argument away, which is how the first block reproduces it: `stringsAsFactors = TRUE` gives the nine-level factor that every older tutorial printed. With factors, adding a value that is not a level is a warning and an `NA`, the error message of the old days that this change retired for most scripts. The function `default.stringsAsFactors()` that old code used to read the default was deprecated in R 4.2.0 and is defunct since R 4.3.0, and the last line of the block shows its real message. The page xref:programming-languages/r/data-frames.adoc#_the_stringsasfactors_default[Data Frames] explains the argument and xref:programming-languages/r/factors.adoc[Factors] explains what a factor is for.

[source,r]
----
# Since R 4.0.0 strings stay strings.
books <- read.csv("books.csv")
class(books$genre)
#> [1] "character"
df <- data.frame(title = c("The Long Table", "Rivers of Glass"))
class(df$title)
#> [1] "character"

# Before R 4.0.0 the default was TRUE; the old behaviour is one argument away.
old <- read.csv("books.csv", stringsAsFactors = TRUE)
class(old$genre)
#> [1] "factor"
nlevels(old$genre)
#> [1] 9

# With factors, a value that is not a level is a warning and an NA.
tryCatch(
  {
    old$genre[1L] <- "Cookery"
    old$genre[1L]
  },
  warning = \(w) conditionMessage(w)
)
#> [1] "invalid factor level, NA generated"

# default.stringsAsFactors() was deprecated in 4.2.0 and is defunct since 4.3.0.
tryCatch(default.stringsAsFactors(), error = \(e) conditionMessage(e))
#> [1] "'default.stringsAsFactors' is defunct.\nUse '`stringsAsFactors = FALSE`' instead.\nSee help(\"Defunct\")"
----

=== Raw string constants

R 4.0.0 added a syntax for raw character constants similar to the one of C{pp}: `+r"(...)"+`, where the dots are any character sequence that does not contain the characters `+)"+`. The NEWS says it makes it easier to write strings that contain backslashes or both single and double quotes, and refers to the help page of `Quotes`. The brackets may also be `[]` or `{}`, a capital `R` works as well as a small one, and a run of dashes between the `r` and the opening bracket (and again before the closing quote) lengthens the delimiter, so that a string may contain `+)"+` itself; the block shows the dashes. Raw strings matter most for Windows paths and regular expressions, where every backslash otherwise has to be doubled. They are a parser feature: the value is an ordinary character vector, as the `identical()` calls show. The syntax is explained in xref:programming-languages/r/syntax-and-lexical-structure.adoc#_raw_strings[Syntax and Lexical Structure] and used for patterns in xref:programming-languages/r/strings-and-regular-expressions.adoc#_raw_strings[Strings and Regular Expressions].

[source,r]
----
# A Windows path needs every backslash doubled in an ordinary string.
path_old <- "C:\\shelf\\books.csv"
path_raw <- r"(C:\shelf\books.csv)"
identical(path_old, path_raw)
#> [1] TRUE
nchar(path_raw)
#> [1] 18

# Both kinds of quote can appear without escapes.
quote_old <- "She said \"hello\" and 'goodbye'"
quote_raw <- r"(She said "hello" and 'goodbye')"
identical(quote_old, quote_raw)
#> [1] TRUE

# Dashes between the r and the bracket make a longer delimiter, so that the
# text may contain )" itself.
r"---(a )" inside a raw string)---"
#> [1] "a )\" inside a raw string"

# Regular expressions are where raw strings pay off.
iso_old <- "^\\d{4}-\\d{2}-\\d{2}$"
iso_raw <- r"(^\d{4}-\d{2}-\d{2}$)"
identical(iso_old, iso_raw)
#> [1] TRUE
grepl(iso_raw, c("2026-06-30", "30/06/2026"))
#> [1]  TRUE FALSE
----

Source: https://search.r-project.org/R/refmans/base/html/Quotes.html[R documentation: Quotes]

=== Matrices also inherit from "array"

Since R 4.0.0 a matrix has two classes, `c("matrix", "array")`. The NEWS entry warns that this "invalidates code incorrectly assuming that" the class of a matrix has length one, and adds that S3 methods for class `"array"` are now dispatched for matrices. The classic casualty is a test such as `pass:c[if (class(m) == "matrix")]`: with a condition of length two it was a warning before R 4.2.0 and is an error since R 4.2.0, as the fourth line of output shows. The correct tests are `is.matrix()` for "is this a matrix" and `inherits()` for a class vector. The lintr linter `class_equals_linter()` finds the old form (see the migration section). The page xref:programming-languages/r/matrices-and-arrays.adoc#mat-class[Matrices and Arrays] covers the class vector in detail.

[source,r]
----
m <- matrix(1:6, nrow = 2)
class(m)
#> [1] "matrix" "array"
inherits(m, "matrix")
#> [1] TRUE
is.matrix(m)
#> [1] TRUE

# Code written for R 3.x compared the whole class vector with a string.
tryCatch(
  if (class(m) == "matrix") "a matrix",
  error = \(e) conditionMessage(e)
)
#> [1] "the condition has length > 1"

# Ask the question directly instead.
if (is.matrix(m)) "a matrix"
#> [1] "a matrix"

# S3 methods for "array" are also dispatched for matrices.
describe <- function(x) UseMethod("describe")
describe.array <- function(x) "the array method"
describe.default <- function(x) "the default method"
describe(m)
#> [1] "the array method"
describe(1:3)
#> [1] "the default method"
----

=== Reference counting replaces NAMED

=== list2DF()

`list2DF()` creates a data frame from a list of variables. == R 4.1.0 (2021-05-18)

R 4.1.0 added two pieces of syntax that changed how R code looks: the native pipe and the function shorthand. Both are parsed into ordinary calls, so neither adds a new kind of object, and a package that uses either one should declare `Depends: R (>= 4.1.0)` (`R CMD build` adds the field when it is missing and says so). A third change, `+...names()+`, is a small helper for functions that take `+...+`.

=== The native pipe

The NEWS entry says that R now provides a simple native forward pipe syntax: the simple form inserts the left-hand side as the first argument of the right-hand side call. Before it, a pipe meant the magrittr package (2.0.5 here). The two look alike and differ in what they are. The magrittr `%>%` is an ordinary function that evaluates its right-hand side at run time and accepts a bare function name, an operator and the dot placeholder. The native pipe is a syntax transformation made by the parser: `books |> head(3L)` is read as `head(books, 3L)` and no pipe function is ever called, the right-hand side must be a call, and the placeholder is the underscore of the R 4.2.0 section below. The block runs both side by side and shows the transformation with `quote()` and the parse error for a right-hand side that is not a call. The magrittr lines carry a `nolint` comment because the linter `pipe_consistency_linter()` asks for one kind of pipe per file. Older code that works with magrittr keeps working; the page xref:programming-languages/r/pipes-and-the-native-pipe.adoc#_the_magrittr_pipe_package[Pipes and the Native Pipe] lists what has to change to move to the native pipe.

[source,r]
----
source("scenario.R")
library(magrittr)

# Before R 4.1.0 a pipe meant a package: magrittr 2.0.5 here.
books$pages %>% sum(na.rm = TRUE) # nolint: pipe_consistency_linter.
#> [1] 3755

# The native pipe is part of the language.
books$pages |> sum(na.rm = TRUE)
#> [1] 3755

# magrittr marks the place of the left-hand side with a dot; the native pipe
# uses a named placeholder (R 4.2.0).
books %>% # nolint: pipe_consistency_linter.
  lm(pages ~ year, data = .) %>% # nolint: pipe_consistency_linter.
  coef()
#>  (Intercept)         year
#> 2067.0926829   -0.8945014
books |> lm(pages ~ year, data = _) |> coef()
#>  (Intercept)         year
#> 2067.0926829   -0.8945014

# The native pipe is rewritten by the parser: no function is called.
quote(books |> head(3L))
#> head(books, 3L)
quote(books %>% head(3L)) # nolint: pipe_consistency_linter.
#> books %>% head(3L)

# The right-hand side must be a call.
tryCatch(parse(text = "books |> head"), error = \(e) conditionMessage(e))
#> [1] "The pipe operator requires a function call as RHS (<input>:1:10)"
----

=== The function shorthand

According to the NEWS, `pass:c[\(x) x + 1]` is parsed as `function(x) x + 1`. The shorthand is not a new kind of function: the last `identical()` in the block compares the deparsed text of the two expressions and finds it equal. It is most useful where a function is passed as an argument and the word `function` is noise, as with `vapply()`. The block uses `vapply()` with a declared result type; the `sapply()` that older tutorials use for the same job can return a list or a matrix when the input changes, which is covered in xref:programming-languages/r/idioms-and-common-pitfalls.adoc[Idioms and Common Pitfalls]. See xref:programming-languages/r/operators-and-precedence.adoc#_the_lambda_shorthand[Operators and Precedence].

[source,r]
----
source("scenario.R")
titles <- trimws(books$title[1:4])

# Before R 4.1.0 every anonymous function was spelled out.
long_old <- vapply(titles, function(x) nchar(x) > 12L, logical(1L))

# The shorthand is parsed into the very same function call.
long_new <- vapply(titles, \(x) nchar(x) > 12L, logical(1L))
identical(long_old, long_new)
#> [1] TRUE
long_new
#>    The Dispossessed Pride and Prejudice   the quiet streets          Loud Roofs
#>                TRUE                TRUE                TRUE               FALSE

deparse(quote(\(x) x + 1))
#> [1] "function(x) x + 1"
identical(deparse(quote(\(x) x + 1)), deparse(quote(function(x) x + 1)))
#> [1] TRUE
----

=== `+...names()+`

`+...names()+` returns the names of the arguments that were matched to `+...+`, without evaluating them. Older code wrote `+names(list(...))+`, which evaluates every argument just to read the names, as the last two lines of the block show with an argument that fails when evaluated. See xref:programming-languages/r/functions.adoc#_looking_inside_the_dots[Functions].

[source,r]

labels_new <- function(...) ...names()
labels_old <- function(...) names(list(...))

labels_old(title = "The Long Table", 1999L, genre = "Fiction")
#> [1] "title" ""      "genre"

tryCatch(labels_old(a = stop("evaluated")), error = \(e) conditionMessage(e))

labels_new(a = stop("evaluated"))

== R 4.2.0 (2022-04-22)

R 4.2.0 is the release that turned two sloppy habits of older code into errors: a condition of length greater than one in `if` and `while`, and a vector operand of `+&&+` and `+||+` (a warning in R 4.2.0, an error since R 4.3.0). It also added the placeholder of the native pipe, made UTF-8 the native encoding on recent Windows, and added `Sys.setLanguage()`.

=== if and while need a condition of length one

The NEWS of R 4.2.0 says that calling `if()` or `while()` with a condition of length greater than one gives an error rather than a warning, and that the environment variable `+_R_CHECK_LENGTH_1_CONDITION_+`, which made the check strict in `R CMD check`, no longer has any effect. Before, only the first element was used, which hid bugs: a whole column of the shelf's `loans` was silently reduced to its first loan. The fix is to say what is meant, with `any()`, `all()` or `isTRUE()`, and to decide what an `NA` means; `if (NA)` is an error of its own (see xref:programming-languages/r/control-flow.adoc#_turning_a_vector_or_an_na_into_one_condition[Control Flow]). The block shows the error for `if` and for `while` and the two usual repairs.

[source,r]
----
source("scenario.R")
returned <- !is.na(loans$return_date)

# R 4.2.0: if() and while() with a condition of length greater than one is an

tryCatch(
  if (returned) "all returned",
  error = \(e) conditionMessage(e)
)
#> [1] "the condition has length > 1"

# Say what you mean: any() or all(), with the NAs of the shelf dealt with.
if (all(returned)) "all returned" else "some loans are still out"
#> [1] "some loans are still out"
if (anyNA(loans$return_date)) "some return dates are missing"
#> [1] "some return dates are missing"

# The same rule holds for while().
tryCatch(
  while (returned) break,
  error = \(e) conditionMessage(e)
)
#> [1] "the condition has length > 1"
----

R 4.3.0 finished the `+&&+` and `+||+` story, extended the pipe placeholder, and made C{pp}17 the default C{pp} standard. The last item matters to package authors only; the others matter to scripts.

=== && and || need operands of length one

The NEWS of R 4.3.0 says that calling `+&&+` or `+||+` with a left-hand side or, if it is evaluated, a right-hand side of length greater than one is now always an error, with a report of the form `'length = 4' in coercion to 'logical(1)'`, and that the environment variable `+_R_CHECK_LENGTH_1_LOGIC2_+` no longer has any effect. R 4.4.0 added a handful of small tools that remove helper code from projects (`+%||%+`, `sort_by()`), two experimental language features (`Tailcall()` with `Exec()`, and `declare()`), a correction to `is.atomic()`, a new internal type name that prepares R for other object systems, and `use()`. === %||% is in base R

The NEWS of R 4.4.0 describes `x %||% y` as an expressive idiom for `if (!is.null(x)) x else y`. Projects and packages defined their own copy (the rlang package has one too); a project that still defines it can delete the definition, because the base operator has the same meaning and is documented, rather surprisingly, on the help page of `Control`. Only `NULL` is replaced: `NA`, an empty string and a zero-length vector are values. The first block defines the old helper, uses it, removes it, and shows that the name now finds the operator in the base namespace. The operator lives in xref:programming-languages/r/operators-and-precedence.adoc#ops-null-coalescing[Operators and Precedence], and its use for optional arguments is in xref:programming-languages/r/defensive-programming-and-input-validation.adoc#_missing_arguments_null_defaults_and[Defensive Programming and Input Validation]. A script that must also run on R older than 4.4.0 keeps a guarded definition, shown in the section on keeping code portable.

[source,r]
----
source("scenario.R")

# Before R 4.4.0 every project carried its own copy of the operator.
`%||%` <- function(x, y) if (is.null(x)) y else x
NULL %||% "unknown"
#> [1] "unknown"
"known" %||% "unknown"
#> [1] "known"
rm(`%||%`)

# Now it is in base R, with the same meaning.
environmentName(environment(`%||%`))

=== Tailcall() and Exec() (experimental)

R 4.4.0 added the experimental functions `Tailcall()` and `Exec()` to support recursive functions that do not grow the stack. They are experimental: the help page says they may be changed or dropped in future releases. Plain recursion in R keeps one frame per call and stops with an error (`node stack overflow` here, `evaluation nested too deeply` in other cases); `Tailcall()` replaces the running call with the new one when it is the last thing the function does. The accumulator must be evaluated before the call, because an unevaluated argument would be passed as a chain of promises that is forced all at once at the end. The older workaround was a loop or a trampoline. See xref:programming-languages/r/function-factories-and-higher-order-functions.adoc#_tail_calls_tailcall_and_exec_experimental[Function Factories and Higher-Order Functions].

[source,r]
----
# Tailcall() and Exec() (R 4.4.0) are experimental.
sum_plain <- function(n, acc = 0) {
  if (n == 0) {
    return(acc)
  }
  sum_plain(n - 1, acc + n)
}
tryCatch(sum_plain(1e5), error = \(e) conditionMessage(e))
#> [1] "node stack overflow"

sum_tail <- function(n, acc = 0) {
  if (n == 0) {
    return(acc)
  }
  acc <- acc + n # evaluate the accumulator now, not as a chain of promises
  Tailcall(sum_tail, n - 1, acc)
}
sum_tail(1e5)
#> [1] 5000050000
----

Source: https://search.r-project.org/R/refmans/base/html/Tailcall.html[R documentation: Tailcall and Exec]

=== sort_by()

`sort_by()` is a new generic function, "primarily useful for the data.frame method" that sorts the rows of a data frame by one or more columns. The columns are given as a formula (`pass:c[~ year + pages]`, later columns resolving ties in the earlier ones) or as a list, and further arguments such as `decreasing = TRUE` go on to `order()`. The result is the same as the older `pass:c[df[order(df$year, df$pages), \]]`, as the first `identical()` shows, with row names that keep the original numbers. See xref:programming-languages/r/data-frames.adoc#_sort_by[Data Frames]; the older idiom is the subject of https://cran.r-project.org/doc/FAQ/R-FAQ.html#How-can-I-sort-the-rows-of-a-data-frame_003f[R FAQ 7.23: How can I sort the rows of a data frame?].

[source,r]
----
source("scenario.R")
cols <- c("title", "year", "pages")

# Before R 4.4.0: order() inside a subscript.
old <- books[order(books$year, books$pages), cols]

# sort_by() takes the columns as a formula or as a list.
new <- sort_by(books[cols], ~ year + pages)
identical(old, new)
#> [1] TRUE
head(new, 4L)
#>                  title year pages
#> 2  Pride and Prejudice 1813   432
#> 1     The Dispossessed 1974   387
#> 8     The Lamp at Noon 1999   280
#> 11         Paper Moons 2005    88

# Further arguments go to order(), so decreasing = TRUE works.
head(sort_by(books[cols], ~year, decreasing = TRUE), 3L)
#>             title year pages
#> 10 THE LONG TABLE 2023   256
#> 15    Ten Winters 2022    NA
#> 4      Loud Roofs 2021   198

# The rows keep their original row names, as with order().
rownames(head(new, 4L))
#> [1] "2"  "1"  "8"  "11"
----

=== use() (available since 4.4.0)

`use()` attaches only the exports that are named, and always with `attach.required = FALSE`, so that the packages in `Depends` are not attached. It is the script counterpart of `importFrom` in a `NAMESPACE`: the help page says that a script written with `use()` can be turned into package code by replacing the calls with the corresponding `importFrom` directives. The R 4.5.0 NEWS lists it as a new function and adds in parentheses that it was "actually already available since R 4.4.0", which is why this page lists it under both releases. The help page calls the functionality still experimental, with interfaces that may change. The block loads `tools` the old way and the new way, and checks what each attached; code for R 4.3 or older uses `library(pkg, include.only = )`, which `use()` wraps. See xref:programming-languages/r/packages-libraries-and-namespaces.adoc#_use_attach_only_what_you_name[Packages, Libraries and Namespaces].

[source,r]
----
# Before: library() attaches every export of the package, in every script.
library(tools)
length(ls("package:tools")) > 100L
#> [1] TRUE
detach("package:tools")

# use() (available since R 4.4.0, announced in the R 4.5.0 NEWS) attaches only
# what is named. It is still experimental.
use("tools", "toTitleCase")
ls("package:tools")
#> [1] "toTitleCase"

#> [1] "The Long Table"
detach("package:tools")

# The rest of the code qualifies names, which is what a NAMESPACE would do.
tools::toTitleCase("the long table")
#> [1] "The Long Table"
isNamespaceLoaded("tools")
#> [1] TRUE
----

=== A C23 compiler by default

R 4.5.0 selects a C23 compiler by default, if one is available, for compiling R and packages. The NEWS lists the compilers known to select C23 (gcc 13 to 15 and recent clang releases, among them) and the ways out: a package can ask for the previous standard with `USE_C17` in `SystemRequirements`, or an installer with `R CMD INSTALL --use-C17`, and R itself can be built with `--without-C23` unless the compiler defaults to C23 anyway. === messageCondition()

`messageCondition()` creates a structured `"message"` condition object, analogous to `errorCondition()` and `warningCondition()` (R 3.6.0). The extra arguments become fields of the condition and `class` adds classes in front of `c("message", "condition")`, so a handler can select on the class and read the fields, which is how progress messages that carry data are written. Before, the object was assembled by hand with `structure()`, as the first lines of the block do; both produce the same classes. See xref:programming-languages/r/conditions-and-error-handling.adoc#_errorcondition_warningcondition_and_messagecondition[Conditions and Error Handling].

[source,r]
----
# Before R 4.6.0 a classed message condition was assembled by hand.
old <- structure(
  class = c("shelf_progress", "message", "condition"),
  list(message = "loan 12 of 60\n", call = NULL, done = 12L)
)

# messageCondition() builds the same object, as errorCondition() and
# warningCondition() have done since R 3.6.0. Extra fields are named arguments.
new <- messageCondition(
  "loan 12 of 60\n",
  class = "shelf_progress", done = 12L
)
class(new)
#> [1] "shelf_progress" "message"        "condition"
class(old)
#> [1] "shelf_progress" "message"        "condition"
new$done
#> [1] 12

# message() accepts a condition, and a handler can pick the class out.
withCallingHandlers(
  {
    message(new)
    "finished"
  },
  shelf_progress = \(m) {
    cat("progress:", m$done, "\n")
    invokeRestart("muffleMessage")
  }
)
#> progress: 12
#> [1] "finished"

=== match.arg(several.ok = "all")

`match.arg()` takes a new value for `several.ok`. A string that starts with `"all"` means that the argument may have more than one element and that every one of them must match `choices`. With `several.ok = TRUE`, the older option, elements that do not match are dropped without a word, which let typos through; the block shows both. The tests of valid values that people wrote by hand after `several.ok = TRUE` can be replaced. See xref:programming-languages/r/functions.adoc[Functions] and xref:programming-languages/r/defensive-programming-and-input-validation.adoc#_several_values_at_once[Defensive Programming and Input Validation].

[source,r]
----
columns <- c("title", "author", "isbn", "year")

# several.ok = TRUE drops what does not match, without a word.
match.arg(c("ti", "oops"), columns, several.ok = TRUE)
#> [1] "title"

# R 4.6.0: several.ok = "all" also accepts several values, but every one of
# them must match.
match.arg(c("ti", "au"), columns, several.ok = "all")
#> [1] "title"  "author"
tryCatch(
  match.arg(c("ti", "oops"), columns, several.ok = "all"),
  error = \(e) conditionMessage(e)
)
#> [1] "'arg' should be one of “title”, “author”, “isbn”, “year”"
----

=== substr(i2 = NULL)

`substring(txt, i1, i2)`, `substr()` and their replacement versions accept `i2 = NULL` to mean "to the end of the string". Before, `substring(x, i)` already ran to the end through its default, while `substr()` needed `nchar(x)`; the block shows the older spelling and the new one, and a replacement. See xref:programming-languages/r/strings-and-regular-expressions.adoc#_substr_substring_and_the_replacement_forms[Strings and Regular Expressions].

[source,r]
----
isbn <- "9780306406157"

# Before R 4.6.0 "to the end" was spelled out with nchar().
substr(isbn, 4L, nchar(isbn))
#> [1] "0306406157"

# i2 = NULL (R 4.6.0) means the end of the string.
substr(isbn, 4L, NULL)
#> [1] "0306406157"
substring(isbn, 4L, NULL)
#> [1] "0306406157"

# The replacement forms accept it too.
code <- "abcdef"
substr(code, 4L, NULL) <- "XYZ"
code
#> [1] "abcXYZ"
----

=== panel.first and panel.last

`hist()` gains `panel.first`, and `barplot()` and `boxplot()` (through `bxp()`) gain `panel.first` and `panel.last`; `hist()` has no `panel.last`. The block draws on a null PDF device so that nothing is written. See xref:programming-languages/r/base-graphics-and-devices.adoc[Base Graphics and Devices], where the real chart is shown.

[source,r]

source("scenario.R")
genre <- trimws(tolower(books$genre))

# panel.first and panel.last. Before, the grid was drawn on top of the data.
# hist() and barplot() take an expression; boxplot() takes a function.
h <- hist(books$pages, panel.first = grid())
class(h)
#> [1] "histogram"

length(b)

[[removals]]
== Removals and behaviour changes that stop old code

Most of the changes above add something and leave old code running. A few do the opposite: the old form fails, or quietly means something else. The next script runs four of them on R 4.6.1 and catches each error, so that the real message is shown. `UseMethod()` no longer forwards the local variables of the generic into the method (R 4.4.0): a method that read a variable the generic had defined, which older code did and which made method code hard to analyse, now fails with `object not found`, and the repair is to pass the value as an argument. The comparison operators signal an error for a symbol or a call (R 4.4.0). `+structure(NULL, ...)+` is defunct (R 4.6.0), because `NULL` cannot have attributes; it had been deprecated since R 3.4.0 and now fails, and `+structure(list(), ...)+` is the way to make an empty classed object. And `xfig()` was removed in R 4.5.0 after being deprecated in 4.4.0; the error names the replacement.

[source,r]
----
# R 4.4.0: UseMethod() no longer forwards the local variables of the generic
# to the method. Before, "loan_days" below was visible inside the method.
overdue_days <- function(x, ...) {
  loan_days <- 21L # nolint: object_usage_linter.
  UseMethod("overdue_days")
}
overdue_days.default <- function(x, ...) {
  x - loan_days # nolint: object_usage_linter.
}
tryCatch(overdue_days(30L), error = \(e) conditionMessage(e))
#> [1] "object 'loan_days' not found"

# The fix: pass the value as an argument.
overdue_days2 <- function(x, loan_days = 21L, ...) UseMethod("overdue_days2")
overdue_days2.default <- function(x, loan_days = 21L, ...) x - loan_days
overdue_days2(30L)
#> [1] 9

# R 4.4.0: <, >, <= and >= signal an error for a symbol or a call.
tryCatch(quote(pages) < 100, error = \(e) conditionMessage(e))
#> [1] "comparison (<) is not possible for language types"

# R 4.6.0: structure(NULL, ...) is defunct, because NULL has no attributes.
tryCatch(structure(NULL, class = "book"), error = \(e) conditionMessage(e))
#> [1] "attempt to set an attribute on NULL"
class(structure(list(), class = "book"))
#> [1] "book"

# R 4.5.0 removed the xfig() device, deprecated since R 4.4.0.
tryCatch(xfig(), error = \(e) conditionMessage(e))
#> [1] "'xfig' was removed in R 4.5.0.\n Consider an SVG device instead."
----

[[migrating]]
== Moving older code to a current R

A script written for R 3.x or an early R 4.x usually runs unchanged on R 4.6.1. The changes that stop it are the ones in the table above, and the ones that change its meaning without stopping it are the new defaults (strings that stay strings, a matrix with two classes, a different `is.atomic(NULL)`, a new palette). A practical order of work is the following.

. Note the R version and the package versions the code was last known to work with. A lockfile from xref:programming-languages/r/reproducible-environments-with-renv.adoc[Reproducible Environments with renv] records both, and is the way to compare an old and a new run package by package.
. Run the script on the new R with warnings printed as they happen (`options(warn = 1)` in a profile, as the scripts of this reference do; `Rscript` prints warnings after the script otherwise). A warning is the cheapest signal: the `&&` and `||` warning of R 4.2.x was the notice for the error of R 4.3.0.
. Search the code for the old idioms. The linters of lintr know many of them, and a few lines of R run them over a string of code, as the next block does for seven lines of "tutorial" code. The linters find `pass:c[class(x) == "matrix"]`, `sapply()`, `attach()`, `T` and `F`, `1:length(x)` and the magrittr pipe; they do not know `is.R()`, which a plain search finds. The page xref:programming-languages/r/style-linting-and-static-analysis.adoc#_the_default_linters[Style, Linting and Static Analysis] explains the default set and how to enable the others.
. Fix what the table of removals shows, then the habits in the last table of this page.
. State the oldest R the code needs. A package says so in `Depends`, and `R CMD build` adds `Depends: R (>= 4.1.0)` itself when the code uses the native pipe or the lambda and the field is missing. The next section shows how a script checks for itself.
. Test on the oldest R that is supported, as well as on the newest; the community tools rig (https://github.com/r-lib/rig[rig on GitHub]) and the Rocker project (https://rocker-project.org/[Rocker]) install and run several R versions side by side, and R-hub v2 runs `R CMD check` on a package in GitHub Actions (see xref:programming-languages/r/publishing-to-cran.adoc#_r_hub_v2[Publishing to CRAN]).

[source,r]
----
# Old idioms in a few lines of "tutorial" code, and what lintr 3.4.0 says.
old <- c(
  'if (class(m) == "matrix") "a matrix"',
  "x <- sapply(1:3, function(i) i + 1)",
  "attach(books)",
  "ok <- T",
  "for (i in 1:length(x)) print(i)",
  "books %>% head()",
  "if (exists('is.R') && is.R()) 1"
)
linters <- list(
  lintr::class_equals_linter(),
  lintr::undesirable_function_linter(),
  lintr::T_and_F_symbol_linter(),
  lintr::seq_linter(),
  lintr::pipe_consistency_linter()
)
for (code in old) {
  res <- lintr::lint(text = code, linters = linters)
  cat(sprintf("%s -> %d finding(s)\n", code, length(res)))
  for (r in res) {
    cat("  ", r$linter, ": ", r$message, "\n", sep = "")
  }
}
#> if (class(m) == "matrix") "a matrix" -> 1 finding(s)
#>   class_equals_linter: Use inherits(x, 'class-name'), is.<class> for S3 classes, or is(x, 'S4Class') for S4 classes, instead of comparing class(x) with ==.
#> x <- sapply(1:3, function(i) i + 1) -> 1 finding(s)
#>   undesirable_function_linter: Avoid undesirable function "sapply". As an alternative, use vapply() with an appropriate `FUN.VALUE=` argument to obtain type-stable simplification.
#> attach(books) -> 1 finding(s)
#>   undesirable_function_linter: Avoid undesirable function "attach". As an alternative, use roxygen2's @importFrom statement in packages, or `::` in scripts. attach() modifies the global search path.
#> ok <- T -> 1 finding(s)

#> books %>% head() -> 1 finding(s)
#>   pipe_consistency_linter: Use the |> pipe operator instead of the %>% pipe operator.
#> if (exists('is.R') && is.R()) 1 -> 0 finding(s)

[[portable]]
== Keeping code portable across R versions

A script or a package that has to run on an older R than the one it was written on has three tools. The first is a version test: `getRversion()` returns an object of class `numeric_version`, which compares correctly with a string (`getRversion() >= "4.1.0"`), while comparing two version strings as text does not: `"4.10.0" > "4.6.1"` is `FALSE`. The second is a feature test, which asks for the thing the code needs and not for the release that introduced it: `exists("grepv", envir = baseenv())`. The third is a definition of the missing function that is made only when it is missing, so that the current R uses its own. The block shows all three with the operator of R 4.4.0. `R.version.string` and `R.version$major` and `R.version$minor` give the version of the running R as text.

[source,r]
----
R.version.string
#> [1] "R version 4.6.1 (2026-06-24)"
getRversion()
#> [1] ‘4.6.1’
getRversion() >= "4.1.0"
#> [1] TRUE

# Compare versions as versions, not as strings: "4.10.0" comes after "4.6.1".
"4.10.0" > "4.6.1"
#> [1] FALSE
numeric_version("4.10.0") > "4.6.1"
#> [1] TRUE
compareVersion("4.10.0", "4.6.1")
#> [1] 1

# A script that must also run on R older than 4.4.0 defines the operator only
# when base R lacks it.
if (getRversion() < "4.4.0") {
  `%||%` <- function(x, y) if (is.null(x)) y else x
}
NULL %||% "unknown"
#> [1] "unknown"

# A feature test says what the code needs, not which release has it.
exists("grepv", envir = baseenv())
#> [1] TRUE
exists("no_such_function", envir = baseenv())
#> [1] FALSE
----

Source: https://search.r-project.org/R/refmans/base/html/numeric_version.html[R documentation: numeric_version]

For a package, the supported minimum goes in `DESCRIPTION`. The shelf package of this reference needs R 4.1.0 because it uses the native pipe and `pass:c[\(x)]`:

[source,text]
----

    R (>= 4.1.0)
----

Source: https://cran.r-project.org/doc/manuals/r-release/R-exts.html#Package-Dependencies[Writing R Extensions: Package Dependencies]

The field is described in xref:programming-languages/r/creating-packages.adoc#_depends_imports_suggests_linkingto_and_enhances[Creating Packages], and its relation to `Imports` and to the attaching of packages in xref:programming-languages/r/packages-libraries-and-namespaces.adoc[Packages, Libraries and Namespaces]. Two limits are worth knowing. A `Depends: R (>= x.y.z)` line only stops the installation on an older R; it does not make code written for the newer language run there. And testing on the oldest R that is supported, with a tool such as rig or the Rocker images, is the only way to find the calls that were added later.

[[news]]
== How to keep up

R announces every change in NEWS, and there are several ways to read it.

* The release NEWS (https://cran.r-project.org/doc/manuals/r-release/NEWS.html[R NEWS]) lists the changes from R 4.0.0 to the current release, newest first, in sections called Significant User-Visible Changes, New Features, Deprecated and Defunct, Bug Fixes and C-Level Facilities (the 4.6 series also has Graphics, Package Installation, Installation on a Unix-Alike, Utilities and Checking an Installation). The 3.x series has its own file (https://cran.r-project.org/doc/manuals/r-release/NEWS.3.html[R NEWS for the 3.x series]). The development NEWS (https://cran.r-project.org/doc/manuals/r-devel/NEWS.html[R-devel NEWS]) starts with the changes of the next x.y.0 and also lists the next patch release, which is why 4.6.2 appears in it before it is out.
* `news()` reads the NEWS of the installed R into a data frame with the columns `Version`, `Date`, `Category`, `Text` and `HTML`, which can be queried with an expression: the block below lists the entries of 4.6.1 by category and finds the entry that introduced `%notin%`. It reads the NEWS of the R that is running, so on an older R it does not know the newer entries. Its help page is https://search.r-project.org/R/refmans/utils/html/news.html[news].
* The R Blog (https://blog.r-project.org/[The R Blog]) carries posts by members of R Core and others about internals and infrastructure. Two that bear on this page, both read for it, are "Generalizing Support for Functional OOP in R" (2024-05-17), which explains the base R generics added for S7, among them `chooseOpsMethod()` and `nameOfClass()`, and "New Tricks for the R Sweave Drivers" (2026-09-18), about the Sweave drivers whose help pages and options change in R 4.6.0 and R-devel.

[[upcoming]]
== Upcoming: R 4.6.2 and R-devel (4.7.0)

Nothing in this section is released, nothing is run, and everything may change before it is. It was checked against the live R-devel NEWS (https://cran.r-project.org/doc/manuals/r-devel/NEWS.html[R-devel NEWS]) on 2026-10-22.

*R 4.6.2.* The R Developer Page lists the 4.6.2 beta from Monday 2026-10-19, the code freeze and release candidate for Thursday 2026-10-22, and the release for Thursday 2026-10-29; the version file of the 4.6 branch said "4.6.2 RC" on 2026-10-22, and the tarball directory of R 4 still ended at R-4.6.1 that day. The R-devel NEWS already has a section "Changes in R 4.6.2" which lists only bug fixes: among them an integer overflow in `rhyper()` when `m + n` exceeds `.Machine$integer.max`, a long-standing bug in `nlminb()` with constraints, `seq.int()` with a non-vector `along.width`, `writeChar()` in a multibyte locale, several fixes to `strptime()` and several crashes fixed in `ksmooth()`, `besselI()` and `besselK()`. If R 4.6.2 is out by the time this is read, the baseline of this page is still R 4.6.1 and the 4.6.2 NEWS is the place to look.

*R 4.7.0.* No release date is published for R 4.7.0; the schedule only says that x.y.0 releases are annual and in spring. The R-devel NEWS lists, among others, the following changes for it.

[cols="2,5",options="header"]
|===
|Item |What the R-devel NEWS says
|`Compose()`, `Funcall()`, `Partial()` |New higher-order functions (see xref:programming-languages/r/function-factories-and-higher-order-functions.adoc#_upcoming_in_r_devel_compose_partial_and_funcall[Function Factories and Higher-Order Functions])
|`cumvar()` |A new function that calculates cumulative variances
|`objectNotFoundError`, `functionNotFoundError` |"Object not found" errors signal conditions of class `objectNotFoundError`, and "function not found" errors the subclass `functionNotFoundError`; the condition classes used internally for some errors are documented in `?conditions`
|`pass:c[x[logi\]]` |A logical index now warns if `length(x)` is not a multiple of `length(logi)`
|`use()` |Gets an argument `pos`
|`.OBJSXP()` |A new low-level function that enables deparsing of non-S4 objects of type "object"
|`read.dcf()` and `write.dcf()` |Treat `DESCRIPTION` and `PACKAGES` files as UTF-8, as the Debian control file format requires
|`rbinom()` |A fix that changes results; to reproduce old results `RNGkind()` gets a new `binom.kind` argument, and `RNGversion("4.6")` keeps the previous behaviour

The facts of this page that are most often quoted wrongly, with what the NEWS says.
