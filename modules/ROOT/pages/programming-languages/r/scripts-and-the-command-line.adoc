== Running R without a person at the console

R was designed for a person typing at a prompt, and most of its defaults assume one is there: it prints the value of every top-level expression, asks whether to save the workspace on exit, opens a window for a plot and offers to correct a mistyped answer. "Non-interactive" means the opposite: no one is available to answer, so R must never wait. The help page of `interactive()` lists what changes: errors are handled differently (an uncaught error ends the run), R never asks about the workspace, the default graphics device is a file instead of a window, and a device never asks for confirmation of a new page. A script is a text file of R code that is run in that mode.

"An Introduction to R" (Appendix B, "Invoking R") describes the ways to start R, and the table below puts them side by side. The manual still names `R CMD BATCH` first for running a file, and presents `Rscript` as the front end that makes passing arguments simpler; in practice `Rscript` is the one used for new work, for the reasons in the table.

[cols="3,5,3",options="header"]
|===
|Command |What happens |Commands echoed?

|`Rscript file.R a b`
|Runs `R --no-echo --no-restore --file=file.R --args a b`. No workspace is read or saved; start-up files are read. The usual choice.
|No

|`Rscript -e 'expr'`
|The same, with one or more expressions instead of a file.
|No

|`pass:c[R CMD BATCH file.R [out\]]`
|Runs the file with `--restore --save --no-readline` unless told otherwise and writes commands and output to `file.Rout` (or `out`), with a timing trailer.
|Yes, in the output file

|`R -f file.R` or `R --file=file.R`
|Runs the file in the ordinary `R` front end; prints the banner unless `--quiet`.
|Yes, unless `--no-echo`

|`R < file.R`
|Reads the commands from standard input, as if typed; `stdin()` refers to that input.
|Yes

|`R -e 'expr'`
|One expression, echoed like typed input.
|Yes

|`source("file.R")`
|Inside a running session; no `--args`, no new process.
|Only with `echo = TRUE`
|===

Source: https://cran.r-project.org/doc/manuals/r-release/R-intro.html#Invoking-R[An Introduction to R: Invoking R]

== Rscript

`Rscript` is a small executable that sits next to `R`. Its help page calls it an alternative front end for use in `+#!+` scripts and other scripting applications, and its job is to turn a convenient command line into the longer one that `R` needs.

=== Usage and options

`Rscript --help` prints the whole interface, which is short enough to read in full.

[source,bash]
----
Rscript --help
#> Usage: Rscript [options] file [args]
#>    or: Rscript [options] -e expr [-e expr2 ...] [args]
#> A binary front-end to R, for use in scripting applications.
#>
#> Options:
#>   --help              Print usage and exit
#>   --version           Print version and exit
#>   --verbose           Print information on progress
#>   --default-packages=LIST  Attach these packages on startup;
#>                         a comma-separated LIST of package names, or 'NULL'
#> and options to R (in addition to --no-echo --no-restore), for example:
#>   --save              Do save workspace at the end of the session
#>   --no-environ        Don't read the site and user environment files
#>   --no-site-file      Don't read the site-wide Rprofile
#>   --no-init-file      Don't read the user R profile
#>   --restore           Do restore previously saved objects at startup
#>   --vanilla           Combine --no-save, --no-restore, --no-site-file,
#>                         --no-init-file and --no-environ
#>
#> Expressions (one or more '-e <expr>') may be used *instead* of 'file'.
#> Any additional 'args' can be accessed from R via 'commandArgs(TRUE)'.
#> See also  ?Rscript  from within R.
----

Source: https://search.r-project.org/R/refmans/utils/html/Rscript.html[R documentation: Rscript]

`Rscript --version` prints the version banner and exits.

[source,bash]
----
Rscript --version
#> Rscript (R) version 4.6.1 (2026-06-24)
----

Source: https://search.r-project.org/R/refmans/utils/html/Rscript.html[R documentation: Rscript]

=== What Rscript runs

The help page says that `Rscript` always supplies `--no-echo --no-restore` (which imply `--no-save`), and `--verbose` shows the command it builds. The transcript runs a script that prints its own `commandArgs()`; the long path of the `R` launcher in the first line is shortened to `R`.

[source,bash]
----
Rscript --verbose args.R a 2>&1 | sed "s|'[^ ]*R --no-echo|'R --no-echo|"
#> running
#>   'R --no-echo --no-restore --file=args.R --args a'
#>
#> number of elements: 8
#> [1] "--no-save"     "--no-restore"  "--no-echo"     "--no-restore"
#> [5] "--file=args.R" "--args"        "a"
#> [1] "a"
----

Source: https://search.r-project.org/R/refmans/utils/html/Rscript.html[R documentation: Rscript]

The script behind the lines after the blank one is `args.R`. It prints how many elements `commandArgs()` returns, the vector without its first element, and the vector with `trailingOnly = TRUE`; the first element is the path of R's executable, which is platform dependent, so it is dropped before printing.

[source,r]
----
# args.R: show what the script receives.
all_args <- commandArgs()
cat("number of elements:", length(all_args), "\n")
print(all_args[-1L])
print(commandArgs(trailingOnly = TRUE))
----

Source: https://search.r-project.org/R/refmans/base/html/commandArgs.html[R documentation: commandArgs]

So `Rscript args.R a` is `R --no-echo --no-restore --file=args.R --args a`, and the options it adds mean:

[cols="2,5",options="header"]
|===
|Option |Meaning
|`--no-echo` |Do not echo the commands. `--slave` is the older name (the R 4.0.0 NEWS calls `--no-echo` "renamed from --slave"), `-s` is the short form, and `--slave` is still accepted.
|`--no-restore` |Do not restore a saved `.RData` workspace or the command history. Together with the `--no-save` that R's own start-up script adds, nothing is read from or written to a workspace file.
|`--file=file.R` |Take the commands from the file.
|`--args` |Everything after this marker is left alone by R and is what `commandArgs(trailingOnly = TRUE)` returns.
|===

Source: https://cran.r-project.org/doc/manuals/r-release/R-intro.html#Invoking-R-from-the-command-line[An Introduction to R: Invoking R from the command line]

`--no-save` appears first in the vector because R's start-up script runs the real executable as `R_binary --no-save --no-restore` followed by the options it was given, which is why `--no-restore` occurs twice. Nothing is lost by the repetition. What `Rscript` does not add is `--no-site-file`, `--no-init-file` or `--no-environ`: the site and user environment files (`Renviron`, `.Renviron`) and profile files (`Rprofile.site`, `.Rprofile`) are read as in any R start, which is useful (a library path in `.Renviron` applies) and also a source of "works on my machine". `--vanilla` combines `--no-save`, `--no-restore`, `--no-site-file`, `--no-init-file` and `--no-environ`; it goes before the file name, and `commandArgs()` then lists it among R's own options.

[source,bash]
----
Rscript --vanilla args.R a
#> number of elements: 9
#> [1] "--no-save"     "--no-restore"  "--no-echo"     "--no-restore"
#> [5] "--vanilla"     "--file=args.R" "--args"        "a"
#> [1] "a"
----

Source: https://search.r-project.org/R/refmans/utils/html/Rscript.html[R documentation: Rscript]

A reproducible job, such as one run by a scheduler on a machine with other users, normally starts with `Rscript --vanilla` so that a stray `.Rprofile` cannot change its behaviour; the price is that settings it needed from `.Renviron` (a package library, a proxy) have to be provided another way. The files themselves are described in xref:programming-languages/r/sessions-workspaces-and-startup.adoc[Sessions, Workspaces and Startup].

=== Expressions with -e, and the order of arguments

`-e` supplies the program on the command line, and it can be repeated; the expressions run in order, each at top level, so a value is autoprinted. Anything after the last expression is an argument for the program.

[source,bash]
----
Rscript -e 'cat("one\n")' -e '2 + 2' extra1 extra2
#> one
#> [1] 4
----

Source: https://search.r-project.org/R/refmans/utils/html/Rscript.html[R documentation: Rscript]

The order is strict, and the help page says so: "the prescribed order of arguments is important", because an option placed after `-e` or after the file name is not read by `Rscript` or by R at all but passed on as an argument to the program. That is a feature: an option for your script can never be mistaken for one of R's (the script's own `--help` and `--version` are safe), and a mistake of the opposite kind, writing `Rscript script.R --vanilla`, silently does not do what it says. The next transcript passes R's own option names to a script and shows them arriving as plain arguments.

[source,bash]
----
Rscript args.R --version --help -e 1
#> number of elements: 11
#>  [1] "--no-save"     "--no-restore"  "--no-echo"     "--no-restore"
#>  [5] "--file=args.R" "--args"        "--version"     "--help"
#>  [9] "-e"            "1"
#> [1] "--version" "--help"    "-e"        "1"
----

Source: https://search.r-project.org/R/refmans/utils/html/Rscript.html[R documentation: Rscript]

The program given with `-e` is subject to the quoting of the shell that starts it, and the help page warns about exactly that. In the Bourne-style shells the expression goes in single quotes and strings inside it in double quotes, as above. In `cmd.exe` the outer quotes must be double quotes and the inner strings single-quoted or escaped, and PowerShell has its own rules for quotes passed to native programs; a script file avoids the whole subject. When `-e` is used, `commandArgs()` has no `--file=` element, and `commandArgs(TRUE)` returns the arguments that follow the expressions.

[source,bash]
----
Rscript -e 'commandArgs(TRUE)' a b c
#> [1] "a" "b" "c"
Rscript -e 'commandArgs()[-1]'
#> [1] "--no-save"         "--no-restore"      "--no-echo"
#> [4] "--no-restore"      "-e"                "commandArgs()[-1]"
----

Source: https://search.r-project.org/R/refmans/base/html/commandArgs.html[R documentation: commandArgs]

An empty expression is refused, and an uncaught error in one expression ends the run before the next, with status 1 like any other uncaught error (see <<exit-status,Exit status>>).

[source,bash]
----
Rscript -e 'cat("one\n")' -e 'stop("second expression")' -e '3'; echo $?
#> one
#> Error: second expression
#> Execution halted
#> 1
Rscript -e ''; echo $?
#> ERROR: option '-e' requires a non-empty argument
#> 1
----

Source: https://search.r-project.org/R/refmans/utils/html/Rscript.html[R documentation: Rscript]

The help page defines `-` as the file name for standard input: the script is then read from the pipe instead of a file. That is handy for generating a program in a shell pipeline, and unsuitable for a script that also needs to read data from standard input, which is already used up by the program.

[source,bash]
----
echo 'cat(1 + 1, "\n")' | Rscript -
#> 2
----

Source: https://search.r-project.org/R/refmans/utils/html/Rscript.html[R documentation: Rscript]

=== Default packages

A fresh R session attaches `datasets`, `utils`, `grDevices`, `graphics`, `stats` and `methods`. `Rscript` does the same since R 3.5.0; before that it left `methods` out, so a script that used S4 classes or Reference Classes had to attach it itself, and the 3.5.0 NEWS added an environment variable to restore the old behaviour for a while. Two options control the set. `--default-packages=LIST` takes a comma-separated list of package names, or `NULL` for none, and sets the environment variable `R_DEFAULT_PACKAGES` for the new process. Without that option, `Rscript` checks `R_SCRIPT_DEFAULT_PACKAGES` first and falls back to `R_DEFAULT_PACKAGES`; the former takes precedence over the latter, and either can be used in a `.Renviron` or a Makefile. `base` is always attached. The script below reports what is on the search path.

[source,r]
----
# packages.R: which packages are attached at startup.
attached <- grep("^package:", search(), value = TRUE)
cat("attached:", sub("^package:", "", attached), "\n")
cat("methods attached:", "package:methods" %in% attached, "\n")
----

Source: https://search.r-project.org/R/refmans/base/html/Startup.html[R documentation: Startup]

[source,bash]
----
Rscript packages.R
#> attached: stats graphics grDevices utils datasets methods base
#> methods attached: TRUE
Rscript --default-packages=NULL packages.R
#> attached: base
#> methods attached: FALSE
Rscript --default-packages=utils,stats packages.R
#> attached: stats utils base
#> methods attached: FALSE
R_SCRIPT_DEFAULT_PACKAGES=utils R_DEFAULT_PACKAGES=NULL Rscript packages.R
#> attached: utils base
#> methods attached: FALSE
----

Source: https://search.r-project.org/R/refmans/utils/html/Rscript.html[R documentation: Rscript]

The last command shows the precedence: both variables are set, and only `utils` (plus `base`) is attached. The packages attach in the order given, so the search path lists them in reverse, as the transcript for `utils,stats` shows. A script that names its dependencies with `library()` or `pkg::fn()` works with any of these settings and starts faster with `--default-packages=NULL`; one that silently relied on `stats` or `methods` being attached will fail with "could not find function", which is a reason to write `stats::median()` in a script that is run with a reduced set. Setting `R_DEFAULT_PACKAGES=""` asks for R's system default, which is the same as not setting it.

=== When Rscript cannot start the script

A missing script file is a fatal error of the front end and gives status 2, not R's usual 1; an unknown option before the file produces a warning and the run goes on. In a shell where `Rscript` is not on the `PATH`, the shell, not R, prints "command not found" (bash's wording), which is why a cron job or a service manager, with its minimal `PATH`, needs the full path to `Rscript` or a `PATH` assignment.

[source,bash]
----
Rscript nope.R; echo $?
#> Fatal error: cannot open file 'nope.R': No such file or directory
#> 2
Rscript --nonsense -e '1'; echo $?
#> WARNING: unknown option '--nonsense'
#>
#> [1] 1
#> 0
----

Source: https://search.r-project.org/R/refmans/utils/html/Rscript.html[R documentation: Rscript]

On Windows the program is `Rscript.exe`, in the `bin` directory of the R installation; give its full path or add that directory to the `PATH`, and note that the `+#!+` line of a script is not interpreted by `cmd.exe` or PowerShell. The transcripts on this page were produced on Linux; the places where Windows differs are said where they come up.

== Executable scripts

On Unix-like systems the kernel runs a file that starts with `+#!+` by starting the named interpreter with the file as its argument. For R the interpreter is `Rscript`, and since R treats `#` as a comment the line is ignored when R reads the file. "An Introduction to R" gives two forms: the first line `+#! /path/to/Rscript+`, which hard-codes a path, and `+#! /usr/bin/env Rscript+`, which finds `Rscript` on the `PATH` and is the one to use because the location differs between systems (a Homebrew install, a distribution package, a container). This is `shelf-hello.R`, a complete script that is a fragment only in the sense that it is meant to be run as a program, not with `Rscript`:

[source,r]
----
#!/usr/bin/env Rscript
args <- commandArgs(trailingOnly = TRUE)
cat("Shelf report for:", args, "\n")
----

Source: https://cran.r-project.org/doc/manuals/r-release/R-intro.html#Scripting-with-R[An Introduction to R: Scripting with R]

The two steps that need a POSIX shell (and do not exist in `cmd.exe`) are setting the executable bit and running the file by its path. Without the bit the shell answers "Permission denied" (status 126), and without a `./` the shell looks only in the `PATH`.

[source,bash]
----
chmod +x shelf-hello.R
./shelf-hello.R books.csv loans.csv
echo $?
#> Shelf report for: books.csv loans.csv
#> 0
----

Source: https://cran.r-project.org/doc/manuals/r-release/R-intro.html#Scripting-with-R[An Introduction to R: Scripting with R]

The `+#!+` mechanism passes everything after the interpreter name as a single argument on many systems, and the manual notes that, at least in Bourne and bash shells, the `+#!+` mechanism does not allow extra arguments such as `+#! /usr/bin/env Rscript --vanilla+`. The failure is the one the next fragment shows: `env` receives the string `Rscript --vanilla` and looks for a program of that name (the path of `env` in the first line of its message is shortened). GNU `env -S` splits the string, which makes a flag in the shebang possible; `-S` is not portable (it is an extension of GNU `env` that recent BSD systems also have; check it on the target), and since R 3.5.0 `Rscript` splits a single argument string given on the `+#!+` line, so a script that names `Rscript` by its path can carry several options, as in `+#! /path/to/Rscript --vanilla --default-packages=utils+`, at the price of the hard-coded path. The alternative that always works is to put the setting in the script itself, or in a small `sh` wrapper that runs `Rscript --vanilla`. The three fragments below create a two-line file with `printf`, make it executable and run it.

[source,bash]
----
printf '#!/usr/bin/env Rscript --vanilla\ncat("hello\\n")\n' > hello-vanilla
chmod +x hello-vanilla
./hello-vanilla
echo $?
#> env: ‘Rscript --vanilla’: No such file or directory
#> env: use -[v]S to pass options in shebang lines
#> 127
----

Source: https://cran.r-project.org/doc/manuals/r-release/R-intro.html#Scripting-with-R[An Introduction to R: Scripting with R]

[source,bash]
----
printf '#!/usr/bin/env -S Rscript --vanilla\ncat("hello\\n")\n' > hello-env-s
chmod +x hello-env-s
./hello-env-s
echo $?
#> hello
#> 0
----

Source: https://cran.r-project.org/doc/manuals/r-release/R-intro.html#Scripting-with-R[An Introduction to R: Scripting with R]

A file saved with Windows line endings fails in a similar way on Linux and macOS, because the interpreter name then ends with a carriage return, shown as `\r` in the message. The same file runs when `Rscript` is called on it directly, since R accepts CRLF line endings in a script. Keep scripts that carry a shebang with LF endings (`*.R text eol=lf` in `.gitattributes`).

[source,bash]
----
printf '#!/usr/bin/env Rscript\r\ncat("hello\\n")\r\n' > hello-crlf
chmod +x hello-crlf
./hello-crlf
echo $?
Rscript hello-crlf
#> env: ‘Rscript\r’: No such file or directory
#> env: use -[v]S to pass options in shebang lines
#> 127
#> hello
----

Source: https://cran.r-project.org/doc/manuals/r-release/R-intro.html#Scripting-with-R[An Introduction to R: Scripting with R]

On Windows, run `Rscript.exe script.R` explicitly, or associate the `.R` extension with it; Git Bash and Cygwin shells understand shebang lines, `cmd.exe` and PowerShell do not. A shebang script with no extension (`shelf-hello` instead of `shelf-hello.R`) is the Unix convention for a program; R does not care about the extension, but editors and linters do, which is why the examples here keep `.R`.

== Command-line arguments

=== commandArgs()

`commandArgs()` returns a copy of the command line as the R process received it, "captured before the standard R command line processing takes place", in the words of its help page, so the values are unmodified. The first element is the name of the executable and "the exact form of this element is platform dependent". With `trailingOnly = TRUE` it returns only what follows `--args`, which is where `Rscript` puts the script's arguments. With the script `args.R` shown earlier, a run with three kinds of argument (an option with a value, a quoted argument containing a space, and something that looks like another option) gives:

[source,bash]
----
Rscript args.R --genre fiction "two words" -x 3
#> number of elements: 12
#>  [1] "--no-save"     "--no-restore"  "--no-echo"     "--no-restore"
#>  [5] "--file=args.R" "--args"        "--genre"       "fiction"
#>  [9] "two words"     "-x"            "3"
#> [1] "--genre"   "fiction"   "two words" "-x"        "3"
----

Source: https://search.r-project.org/R/refmans/base/html/commandArgs.html[R documentation: commandArgs]

The last line is the vector a script normally uses. Three facts follow from the transcript.

* The shell, not R, splits the line into arguments: `"two words"` arrives as one element because the shell kept it together. R does no splitting of its own, so a script that needs a list in one argument has to split it itself (`pass:c[strsplit(args[[1\]\], ",", fixed = TRUE)]`).
* Every element is a character string. `3` is `"3"`; a number or a date must be converted by the script, and validated, because `as.integer("three")` is `NA` with a warning, not an error.
* With no script arguments there is no `--args` marker at all and `commandArgs(trailingOnly = TRUE)` is `character(0)`, so `pass:c[args[[1\]\]]` fails with `subscript out of bounds`; test `length(args)` first.

[source,bash]
----
Rscript args.R
#> number of elements: 6
#> [1] "--no-save"     "--no-restore"  "--no-echo"     "--no-restore"
#> [5] "--file=args.R"
#> character(0)
----

Source: https://search.r-project.org/R/refmans/base/html/commandArgs.html[R documentation: commandArgs]

Older scripts write `commandArgs(TRUE)`, which is the same thing: `trailingOnly` is the first and only argument, and the positional form is easy to misread. The `--args` marker belongs to R: it "skips the rest of the command line" (`R --help`), which is why `--version`, `--help`, `-e 1` and `-f other.R` pass through as the strings they are, and `commandArgs(TRUE)` returns everything after the first marker, so a second `--args` typed by the user is returned as an ordinary argument.

=== The name of the running script

A script sometimes needs to know where it lives, to read a file kept beside it. When R runs a file it receives a `--file=` argument holding the path as it was given on the command line, which is relative if the command used a relative path. `script-dir.R` finds the directory from it, and fails with a clear message when there is no such argument, which is the case under `Rscript -e` and when the code is loaded with `source()`.

[source,r]
----
# script-dir.R: find the directory of the running script.
file_arg <- grep("^--file=", commandArgs(), value = TRUE)
if (length(file_arg) == 0L) {
  stop("no --file= argument: not run as a script file")
}
script <- sub("^--file=", "", file_arg[[1L]])
script_dir <- dirname(script)
cat("script as given:   ", script, "\n")

=== Quoting, positional arguments and R's own options

* Arguments with spaces need the shell's quoting; the transcript above shows `"two words"` surviving. For `R CMD BATCH` the arguments come as one quoted string after the options, `"--args one two"`, which makes a single argument containing spaces awkward (see <<r-cmd-batch,R CMD BATCH>>).
* Option names that R itself understands (`--vanilla`, `--no-save`, `-e`) are R's only before the script name. After it they are the script's.
* A leading dash is no special case for `commandArgs()`: a negative number such as `-1` arrives as `"-1"`. A parser decides what is an option (see <<parsing-arguments,Parsing arguments>>).
* Encodings: the arguments are bytes in the current locale; `Encoding()` and `enc2utf8()` apply as for any string, and the flag `--encoding=ENC` of `R` sets the encoding assumed for standard input (not for arguments). See xref:programming-languages/r/encodings-locales-and-internationalization.adoc[Encodings, Locales and Internationalization].

== interactive()

`interactive()` is `TRUE` when R is being used by a person at a console and `FALSE` otherwise. Under `Rscript` it is always `FALSE`. `R` started in a terminal "assumes that it is interactive if stdin is connected to a (pseudo-)terminal and not if stdin is redirected to a file or pipe", and the command-line option `--interactive` overrides the assumption. The script is one line, and the transcript runs it three ways.

[source,r]
----

----

Source: https://search.r-project.org/R/refmans/base/html/interactive.html[R documentation: interactive]

[source,bash]
----

#> >

Source: https://search.r-project.org/R/refmans/base/html/interactive.html[R documentation: interactive]

R's own code uses the flag: `help()`, the debugger, `install.packages()` and `readline()` behave differently without a person. == Exit status

A process that ends returns a small integer to the process that started it, by convention 0 for success and anything else for failure. Shells (`&&`, `||`, `if`, `set -e`), `make`, cron wrappers, CI systems and agent harnesses all decide from that number, so a script that prints "ERROR" and exits with 0 has not reported an error. `quit()` (alias `q()`) ends an R session: `quit(save = "default", status = 0, runLast = TRUE)`.

=== quit() and its arguments

`save` is one of `"no"`, `"yes"`, `"ask"` or `"default"`. The default asks in interactive use and "may be overridden by command-line arguments (which must be supplied in non-interactive use)"; `Rscript` always supplies `--no-restore`, which implies `--no-save`, so it never saves. A script that quits explicitly passes `save = "no"` so that it is correct whichever front end runs it. `status` is the number returned to the operating system, "0:255 are normally valid" and reduced modulo 256 by many systems. `runLast = TRUE` runs the function `.Last()`, if it exists, immediately before normal termination, followed by `.Last.sys()`. The script below takes the status from its first argument, defines a `.Last()` and calls `quit()` before a line that is never reached.

[source,r]
----
# quit-status.R: leave with the status given as the first argument.
args <- commandArgs(trailingOnly = TRUE)
status <- if (length(args) >= 1L) as.integer(args[[1L]]) else 0L
.Last <- function() cat("goodbye from .Last()\n")
cat("about to quit with status", status, "\n")
quit(save = "no", status = status)
cat("this line is never reached\n")
----

Source: https://search.r-project.org/R/refmans/base/html/quit.html[R documentation: quit]

[source,bash]
----
Rscript quit-status.R 3
echo "exit status: $?"
#> about to quit with status 3
#> goodbye from .Last()
#> exit status: 3
Rscript quit-status.R 300
echo $?
#> about to quit with status 300
#> goodbye from .Last()
#> 44
----

Source: https://search.r-project.org/R/refmans/base/html/quit.html[R documentation: quit]

Status 300 became 44, which is 300 modulo 256, and a negative status (`-1`) is seen by the shell as 255: pick values from 0 to 255. The help page also records which numbers R uses itself. The default error handler of a non-interactive session "effectively calls q("no", 1, FALSE)" and returns 1, which is why `.Last()` is not run after an uncaught error; status 2 "is used for R suicide, that is a catastrophic failure"; and "it is recommended that users choose statuses of 10 or more". Section <<status-choices,Choosing statuses>> says what the `shelf` report does about that advice. The `.Last()` function is for the end user to control: a package must not define it, and the finalizers registered with `reg.finalizer(onexit = TRUE)` are the programmatic equivalent.

=== options(error =) and catch.script.errors

The option `error` holds a function or an expression that R runs when an error reaches the top level, after the message is printed. In a non-interactive session the default is to halt with status 1. A handler can log, print a `traceback()` (see xref:programming-languages/r/debugging.adoc[Debugging]) and leave with the status of the script's own choosing, with `runLast = FALSE` to keep the end-of-session `.Last()` from running on a failed state.

[source,r]
----

  message("handler: the run failed, leaving with status 3")
  quit(save = "no", status = 3L, runLast = FALSE)
})
check_year <- function(year) {
  stopifnot(is.numeric(year), year > 0)
  year
}
check_year(2026)

cat("never reached\n")

=== What still runs on the way out

`quit()` and an uncaught error are different exits, and the clean-up code that runs differs. The first script calls `quit()` from inside a function with an `on.exit()` handler and a `tryCatch(finally =)`; the second raises an error in a function with the same two. The `finally` clause and the `on.exit()` handler run on the error path, because the error unwinds the stack; they do not run on the `quit()` path, because `quit()` ends the process without unwinding. The `.Last()` function and a finalizer registered with `onexit = TRUE` run on `quit()`; after an error, `.Last()` does not (the default handler uses `runLast = FALSE`).

[source,r]
----
# quit-cleanup.R: what still runs when quit() is called inside a function.
tmp <- tempfile(fileext = ".txt")
writeLines("scratch data", tmp)

e <- new.env()
invisible(reg.finalizer(e, \(env) cat("finalizer ran\n"), onexit = TRUE))

.Last <- function() cat(".Last() ran\n")

leave <- function(status) {
  on.exit(cat("on.exit handler ran\n"))
  tryCatch(
    quit(save = "no", status = status),
    finally = cat("finally ran\n")
  )
}

cat("file exists before quit:", file.exists(tmp), "\n")
leave(5L)
----

Source: https://search.r-project.org/R/refmans/base/html/quit.html[R documentation: quit]

----

#> file exists before quit: TRUE
#> .Last() ran
#> finalizer ran
#> exit status: 5
----

Source: https://search.r-project.org/R/refmans/base/html/quit.html[R documentation: quit]

[source,r]

Source: https://search.r-project.org/R/refmans/base/html/on.exit.html[R documentation: on.exit]

#> Calls: work -> tryCatch -> tryCatchList -> load_data

#> on.exit handler ran

Source: https://search.r-project.org/R/refmans/base/html/on.exit.html[R documentation: on.exit]

The lesson for a script that must clean up a temporary file or a lock: do not call `quit()` from inside the code that owns the resource. Let an error propagate (or `return` a status), clean up with `on.exit()` or `finally`, and call `quit(status = )` once, at the outermost level, as the report script on this page does. Code in a package should never call `quit()`: it should signal a condition with `stop()` and let the script decide the exit status.

=== stop() or quit(status =)?

[cols="2,3,3",options="header"]
|===
|Situation |Use |Why

|A failure inside a function that a caller could handle
|`stop()`, preferably with a classed condition
|The caller can catch it with `tryCatch()`, `finally` and `on.exit()` run, and a plain script still ends with status 1.

|A script that distinguishes kinds of failure for its caller (usage versus data)
|`tryCatch()` at the top, then one `quit(status = n)`
|The status is chosen in one place; the clean-up code has run.

|"Quit now, nothing to clean up", at the top of a script
|`quit(save = "no", status = n)`
|No handler can intercept it, and it ends the process at once.

|The script is loaded with `source()` from a session
|Neither
|`quit()` would end the whole session; signal an error instead.
|===

== Standard output and standard error

A process has two output streams, and keeping them apart is what lets a shell redirect one and show the other. Standard output is the result: the report, the CSV, the number someone will read or pipe on. Standard error is everything else: progress, diagnostics, warnings, usage messages. R follows the split, and the table shows which function writes where.

[cols="3,2,5",options="header"]
|===
|Function |Stream |Remark

|`cat()`, `print()`, `writeLines()`, `write.csv()`, autoprinted values
|standard output
|`cat(file = stderr())` and `writeLines(con = stderr())` write the same text to standard error.

|`message()`, `packageStartupMessage()`
|standard error
|Signals a condition of class `message`; the default handler writes to `stderr()`.

|`warning()`
|standard error
|Deferred to the end of the top-level call (or printed at once with `options(warn = 1)`), as "Warning message:".

|`stop()` and R's own errors
|standard error
|Printed as "Error in call : message", then "Execution halted".
|===

Source: https://search.r-project.org/R/refmans/base/html/message.html[R documentation: message]

=== sink() and capture.output()

`sink(file)` diverts standard output to a file until `sink()` is called again; it does not affect the message stream. `sink(con, type = "message")` diverts messages, but only to an already open connection, and the help page warns that this should be done "with great care": only one message sink can exist, and a script that fails while it is active loses its diagnostics. For a short block, `capture.output()` returns the output as a character vector and is safer, because the stream is restored when it returns; `capture.output(type = "message")` does the same for messages.

[source,r]
----
# sink.R: divert standard output to a file, then restore it.
log_file <- tempfile(fileext = ".log")
sink(log_file)
print("diverted to the file")
cat("also diverted\n")
message("messages are not diverted by sink()")
sink()
cat("back on the console\n")
readLines(log_file)

# The message stream needs an already open connection and its own sink() call.
con <- file(log_file, open = "wt")
sink(con, type = "message")
message("now the message goes to the file")
sink(type = "message")
close(con)
readLines(log_file)
----

Source: https://search.r-project.org/R/refmans/base/html/sink.html[R documentation: sink]

This script needs no arguments and writes nothing to the current directory (the log file is a temporary file whose name is never printed). Its run on a terminal:

== Reading standard input

A program that reads data from standard input fits into a pipeline: `generate | Rscript clean.R | sort`. R has two things called "standard input", and mixing them up is the most common error on this subject. The help page of `Rscript` ends with the rule that `stdin()` refers to the input file, and `file("stdin")` to the stdin file stream of the process. `stdin()` is the connection to the console, and when R reads a script from a file, that file is the console (this allows data lines after the code, a traditional usage that "An Introduction to R" describes). `file("stdin")` is the C-level standard input of the process, the pipe or file the shell connected. The first script puts data lines after the code on purpose, so it is not valid R and is the one script of this group that is not linted; the second reads the pipe.

[source,r]
----
# stdin-console.R: stdin() is the script, not the pipe.
lines <- readLines(stdin(), n = 1L)
this line belongs to the data
cat("read:", lines, "\n")
----

Source: https://cran.r-project.org/doc/manuals/r-release/R-intro.html#Scripting-with-R[An Introduction to R: Scripting with R]

[source,bash]
----
printf 'a\nb\nc\n' | Rscript stdin-console.R
#> read: this line belongs to the data
----

Source: https://search.r-project.org/R/refmans/base/html/showConnections.html[R documentation: showConnections]

The three lines `a`, `b`, `c` were ignored; `readLines(stdin(), n = 1)` read the next line of the script itself. To read the data that was piped in, use `file("stdin")`.

[source,r]
----

----

Source: https://search.r-project.org/R/refmans/base/html/readLines.html[R documentation: readLines]

Four details matter in practice.

* *An unopened connection is opened and closed by each call.* `readLines(file("stdin"), n = 1)` twice does not read two lines: the first call opens the connection, reads from a buffered stream and closes it, and the buffered text is gone, so the second call finds nothing. To read in pieces, open the connection once, as `stdin-chunks.R` does, and close it at the end.
* *A string is a file name.* `readLines("stdin")` and `scan("stdin")` pass the name to `file()`, which treats the name `"stdin"` as the process's standard input; "An Introduction to R" uses that form. Spelling `file("stdin")` out is clearer.
* *No newline at the end.* A last line without a line terminator is read, with the warning "incomplete final line found on 'stdin'". Empty input gives `character(0)` and no error.
* *A terminal waits.* If nothing is piped in and the script is started from a terminal, `file("stdin")` waits for typed lines until end-of-file (Ctrl-D on Unix, Ctrl-Z then Enter on Windows). A script meant to be used both ways checks whether input was given.

[source,r]
----
# stdin-chunks.R: read standard input a few lines at a time.
con <- file("stdin")
open(con)
first <- readLines(con, n = 2L)
rest <- readLines(con)
close(con)
cat("first chunk:", first, "\n")
cat("the rest:", rest, "\n")
----

Source: https://search.r-project.org/R/refmans/base/html/connections.html[R documentation: connections]

[source,r]
----
# stdin-unopened.R: an unopened connection is opened and closed by each call.
first <- readLines(file("stdin"), n = 1L)
second <- readLines(file("stdin"), n = 1L)
cat("first: ", first, "\n")
cat("second:", second, "\n")
----

Source: https://search.r-project.org/R/refmans/base/html/connections.html[R documentation: connections]

[source,bash]
----

#> the rest: c d
printf 'a\nb\nc\nd\n' | Rscript stdin-unopened.R

The transcript is four commands: the chunked read gets both chunks, the unopened version loses the second line (it prints `second:` with nothing after it), the empty input gives `character(0)`, and the last command prints its warning before its result because the warning belongs to the `readLines()` call, which finished first.

The parsers that read a file also read a connection, so `read.csv(file("stdin"))` and `scan(file("stdin"))` turn a pipe into a data frame or a vector. `read.csv()` closes the connection when it finishes. == Writing to a pipe

The output side of a pipeline needs no special code: what the script writes to standard output goes to the next program. The script prints each non-empty member name of `loans.csv`, and the shell does the rest: `sort | uniq -c | sort -rn | head` counts and ranks them. Spellings in the data differ (`Ana Ruiz` and a lower-case variant with a trailing blank are one member, cleaned elsewhere), which would show lower in the ranking (the transcript keeps the first four lines).

[source,r]
----
# lines-to-stdout.R: print each member once, sorted by the shell.
loans <- read.csv("loans.csv", colClasses = "character")
writeLines(loans$member[loans$member != ""])
----

Source: https://search.r-project.org/R/refmans/base/html/writeLines.html[R documentation: writeLines]

[source,bash]
----
Rscript lines-to-stdout.R | sort | uniq -c | sort -rn | head -n 4
#>      10 Hugo Silva
#>      10 Ana Ruiz
#>       9 Chloe Martin
#>       7 Grace Liu
----

Source: https://search.r-project.org/R/refmans/base/html/writeLines.html[R documentation: writeLines]

If the reader of the pipe quits early, as `head` does after enough lines, the next write to a closed pipe signals SIGPIPE. R does not die silently of it: it converts the failure to an error, the script ends with status 1, and the shell reports the status of each stage. The `PIPESTATUS` array of bash shows it (a POSIX `sh` has only the status of the last command). This script writes two hundred thousand lines, far more than `head` reads.

[source,r]
----
# many-lines.R: write a long listing, one number per line.
for (i in seq_len(200000L)) {
  cat(i, "\n", sep = "")
}
cat("done\n", file = stderr())
----

Source: https://search.r-project.org/R/refmans/base/html/cat.html[R documentation: cat]

[source,bash]
----
bash -c 'Rscript many-lines.R | head -n 2; echo "statuses: ${PIPESTATUS[*]}"'
#> 1
#> 2
#> Error in cat(i, "\n", sep = "") : ignoring SIGPIPE signal
#> Execution halted
#> statuses: 1 0
----

Source: https://search.r-project.org/R/refmans/base/html/cat.html[R documentation: cat]

The first status, 1, is the R script's, killed by its own error message "ignoring SIGPIPE signal", the second, 0, is the status of `head`. Whether this matters depends on the pipeline: with `set -o pipefail` the whole pipeline fails. A tool that is often piped to `head` should catch the error with `tryCatch()` and exit quietly, or flush results in a way that tolerates a closed reader. The reasoning behind SIGPIPE in command-line tools is in xref:ai/cli-for-agents/streams-and-exit-codes.adoc[Streams & Exit Codes].

== R CMD BATCH, R -f and R with redirected input

`R CMD BATCH` is the oldest way to run a file and the one "An Introduction to R" names first. It runs `R` with the file as input and writes the commands and their output, standard error included, to an output file: `file.Rout` by default, or the second argument. The help page gives the contract: the default options are `--restore --save --no-readline`, the commands are echoed unless `--no-echo` or `options(echo = FALSE)` says otherwise, and a final `proc.time()` runs after the script unless `--no-timing` is given or the script calls `q(runLast = FALSE)` or is aborted. Options go before the file name, and "If infile starts with a -, use -- as the final option". The environment variable `R_BATCH_OPTIONS` adds options after the defaults. This is the script used for the next transcripts. It reads `books.csv`, prints a value and a table, echoes its arguments and ends with an assignment that prints nothing.

[source,r]
----
# batch.R: a small script for the batch interfaces.
args <- commandArgs(trailingOnly = TRUE)
books <- read.csv("books.csv")
x <- nrow(books)
x
print(table(books$genre)[1:2])
cat("arguments:", args, "\n")
y <- x * 2
----

Source: https://search.r-project.org/R/refmans/utils/html/BATCH.html[R documentation: BATCH]

The shape of the output file is the point. `--quiet` leaves out the start-up banner (version, copyright, platform, licence and help hints), which would otherwise open the file; every line of the script is echoed after the prompt (a `+>+` and a space), a value follows the line that produced it, and the file ends with the `proc.time()` call and its three timings, left out in the transcript below as `+...+` because they change on every run.

[source,bash]
----

#> > books <- read.csv("books.csv")

#> > x
#> [1] 16
#> > print(table(books$genre)[1:2])
#>

#>       2       1
#> > cat("arguments:", args, "\n")
#> arguments:
#> > y <- x * 2
#> >
#> > proc.time()
#>    user  system elapsed
#>   ...     ...     ...
----

Source: https://search.r-project.org/R/refmans/utils/html/BATCH.html[R documentation: BATCH]

The first line of output is the count of workspace files (zero, with `--vanilla`). The three differences from `Rscript` that cause trouble are these.

* *The workspace is saved and restored.* With the default `--restore --save`, `R CMD BATCH batch.R` writes the final workspace to `.RData` in the working directory, and the next batch run in that directory loads it silently (with `--quiet` there is not even the "[Previously saved workspace restored]" line). A bug that depends on an object left by an earlier run then does not appear.
* *Errors go into the file.* The status of the command is 1 after an error, but the message is in `file.Rout`, not on the terminal, so a wrapper has to look at the file or the status. The error message is the last thing in the file, before "Execution halted".
* *Arguments are one string.* Extra arguments are passed as `"--args one two"`, a single quoted word, which cannot carry an argument with a space.

[source,r]

# uses-undefined.R: use an object that this script never creates.

----

=== R -f, --file and input redirection

`R` itself accepts the same job in three ways. `-f FILE` and `--file=FILE` read the commands from the file, with or without echo; redirecting standard input (`R < file`) reads them as if typed, and the `stdin()` of that session is the input. `--quiet` (or `-q`) removes the banner, `--no-echo` (`-s`) removes the echo, and `--args` ends R's options as before. `--vanilla` is the simplest way to rule out start-up files and a saved workspace.

[source,bash]
----
R --quiet --vanilla -f batch.R --args a b
#> > # batch.R: a small script for the batch interfaces.
#> > args <- commandArgs(trailingOnly = TRUE)
#> > books <- read.csv("books.csv")
#> > x <- nrow(books)
#> > x
#> [1] 16
#> > print(table(books$genre)[1:2])
#>
#> Classic fiction
#>       2       1
#> > cat("arguments:", args, "\n")
#> arguments: a b
#> > y <- x * 2
#> >
R --no-echo --vanilla --file=batch.R --args "two words"
#> [1] 16
#>
#> Classic fiction
#>       2       1
#> arguments: two words
R --quiet --vanilla < batch.R
#> > # batch.R: a small script for the batch interfaces.
#> > args <- commandArgs(trailingOnly = TRUE)
#> > books <- read.csv("books.csv")
#> > x <- nrow(books)
#> > x
#> [1] 16
#> > print(table(books$genre)[1:2])
#>
#> Classic fiction
#>       2       1
#> > cat("arguments:", args, "\n")
#> arguments:
#> > y <- x * 2
#> >
R --quiet --vanilla -e '1 + 1'
#> > 1 + 1
#> [1] 2
#> >
----

Source: https://cran.r-project.org/doc/manuals/r-release/R-intro.html#Invoking-R-from-the-command-line[An Introduction to R: Invoking R from the command line]

The third run was given no arguments, so `args` is empty there, and `-e` echoes the expression with its prompt, unlike `Rscript -e`. `Rscript` is what remains when the echo, the banner and the workspace are all unwanted: it is `R --no-echo --no-restore --file=` with a friendlier command line.

== source() versus running a script

A file run with `Rscript` is read and evaluated one top-level expression at a time, and the value of each is autoprinted unless it is invisible. `source()` evaluates the expressions of a file inside a running session, and the differences are the ones R FAQ 7.16 gives for the question "Why is the output not printed when I source() a file?": values are not printed unless `print.eval = TRUE` or `echo = TRUE` is given. The next script has five top-level expressions and a function whose last value is visible. The first transcript runs it as a script; the second calls `source()` on it, which prints nothing; the third calls `source()` with `echo = TRUE`, which shows each expression and the value of the visible ones.

[source,r]
----
# autoprint.R: top-level values are printed by Rscript but not by source().
x <- 6 * 7
x
invisible(x)
(y <- x + 1)
if (x > 40) "big" else "small"
f <- function() {
  x
  "last value of f()"
}
f()
----

Source: https://cran.r-project.org/doc/FAQ/R-FAQ.html#Why-is-the-output-not-printed-when-I-source_0028_0029-a-file_003f[R FAQ 7.16: Why is the output not printed when I source() a file?]

[source,bash]
----
Rscript autoprint.R
#> [1] 42
#> [1] 43
#> [1] "big"
#> [1] "last value of f()"
Rscript -e 'source("autoprint.R")'
Rscript -e 'source("autoprint.R", echo = TRUE)'
#>
#> > x <- 6 * 7
#>
#> > x
#> [1] 42
#>
#> > invisible(x)
#>
#> > (y <- x + 1)
#> [1] 43
#>
#> > if (x > 40) "big" else "small"
#> [1] "big"
#>
#> > f <- function() {
#> +     x
#> +     "last value of f()"
#> + }
#>
#> > f()
#> [1] "last value of f()"
----

Source: https://search.r-project.org/R/refmans/base/html/source.html[R documentation: source]

Other differences follow from the process model. `source()` runs in the process that called it, so `commandArgs()` and `interactive()` describe that process, not the file, the `--file=` argument is absent, and a `quit()` inside the sourced file ends the whole session. `sys.source()` evaluates in a chosen environment. A script that defines functions and also runs when executed can be written so that it does both jobs: a *main guard* runs `main()` only when the file is the top-level script, which is when `sys.nframe()` is zero, the analogue of Python's `+if __name__ == "__main__"+`. When another file calls `source()` on it, the call stack is not empty and only the definitions are loaded, which is what a test file wants.

[source,r]
----
# main-guard.R: run main() only when this file is the script, not when sourced.
main <- function(args) {
  cat("main() got", length(args), "argument(s):", args, "\n")
  invisible(0L)
}

cat("run as a script:", sys.nframe() == 0L, "\n")
if (sys.nframe() == 0L) {
  main(commandArgs(trailingOnly = TRUE))
}
----

Source: https://search.r-project.org/R/refmans/base/html/sys.parent.html[R documentation: sys.parent]

[source,bash]
----
Rscript main-guard.R a b
#> run as a script: TRUE
#> main() got 2 argument(s): a b
Rscript -e 'source("main-guard.R")'
#> run as a script: FALSE
----

Source: https://search.r-project.org/R/refmans/base/html/sys.parent.html[R documentation: sys.parent]

The guard is a convention that relies on the file being evaluated at top level. For logic that has tests, put the functions in a package and keep the script thin: the script parses arguments, calls package functions and chooses the exit status, as the `shelf` report does below. See xref:programming-languages/r/testing-with-testthat.adoc[Testing with testthat] for testing the functions.

== Environment variables

Environment variables are the other channel between a process and its caller, and the right one for a setting that is not a per-run argument: a credential, a path, the locale, a mode. `Sys.getenv(x, unset = "", names = NA)` reads them; `unset = NA` makes an unset variable distinguishable from one set to the empty string ("POSIX requires the OS to distinguish, and all known current R platforms do", says the help page). `Sys.setenv(NAME = "value")` sets variables for the current process and for programs it starts, never for its parent shell; `Sys.unsetenv()` removes them. The values are always strings. On Windows, setting a variable to `""` unsets it, which POSIX systems do not do.

[source,r]
----
# env.R: read, set and unset environment variables.
Sys.getenv("SHELF_MODE")
Sys.getenv("SHELF_MODE", unset = "report")
Sys.getenv("SHELF_MODE", unset = NA)
Sys.getenv(c("SHELF_MODE", "SHELF_FORMAT"), unset = "(unset)")
Sys.getenv("SHELF_MODE", names = TRUE)

Sys.setenv(SHELF_MODE = "audit", SHELF_FORMAT = "csv")
Sys.getenv("SHELF_MODE")
Sys.getenv(c("SHELF_MODE", "SHELF_FORMAT"))
Sys.unsetenv("SHELF_MODE")
Sys.getenv("SHELF_MODE", unset = NA)

# An empty value and an unset variable look the same unless unset = NA is used.
Sys.setenv(SHELF_MODE = "")
Sys.getenv("SHELF_MODE")
is.na(Sys.getenv("SHELF_MODE", unset = NA))
nzchar(Sys.getenv("SHELF_MODE"))

# Numbers come back as text.
Sys.setenv(SHELF_LOAN_DAYS = "28")
as.integer(Sys.getenv("SHELF_LOAN_DAYS", unset = "21"))
----

=== Credentials

A password, token or key must not be written in a script, in version control or in a command line, where other users see it in the process list and the shell keeps it in its history. The usual pattern is an environment variable that the caller provides, read once, checked, never printed, and with a clear failure when absent. The placeholder credential in these pages is `SHELF_DB_PASSWORD`. `Sys.setenv()` inside a script does not make a secret safe: it only moves the literal into the script.

[source,r]
----
# secret.R: take a credential from the environment, never from the script.
password <- Sys.getenv("SHELF_DB_PASSWORD", unset = NA_character_)
if (is.na(password) || !nzchar(password)) {
  message("secret.R: set SHELF_DB_PASSWORD in the environment")
  quit(save = "no", status = 1L)
}
cat("password found,", nchar(password), "characters\n")
----

Source: https://search.r-project.org/R/refmans/base/html/Sys.getenv.html[R documentation: Sys.getenv]

[source,bash]
----
Rscript secret.R
echo $?
#> secret.R: set SHELF_DB_PASSWORD in the environment
#> 1
SHELF_DB_PASSWORD=placeholder-value Rscript secret.R
echo $?
#> password found, 17 characters
#> 0
----

Source: https://search.r-project.org/R/refmans/base/html/Sys.getenv.html[R documentation: Sys.getenv]

The second command sets the variable for the one run (a shell assignment before the command, so it is not exported to later commands). Where a value should persist for the user, the right place is `.Renviron` in the home directory, with restrictive file permissions: lines of the form `NAME=value`, read at startup, which xref:programming-languages/r/sessions-workspaces-and-startup.adoc[Sessions, Workspaces and Startup] describes. `readRenviron(path)` reads such a file on demand, and the file format allows `+${NAME-default}+` expansion, quotes like a shell, and comment lines. Scripts that keep their settings in a project file read it with `readRenviron()` or with a config package and keep that file out of version control. See xref:ai/cli-for-agents/configuration-and-auth.adoc[Configuration & Auth] for the precedence of flags, environment and files in any command-line tool.

[source,r]
----
# read-renviron.R: read variables from an environment file by hand.
env_file <- tempfile(fileext = ".Renviron")
writeLines(c(
  "# settings for the shelf report",
  "SHELF_FORMAT=csv",
  "SHELF_REPORT_DIR=\"${SHELF_BASE-/srv/shelf}/reports\""
), env_file)

Sys.getenv("SHELF_FORMAT", unset = NA)
readRenviron(env_file)
Sys.getenv("SHELF_FORMAT", unset = NA)
Sys.getenv("SHELF_REPORT_DIR")
----

----

#> [1] NA
#> [1] "csv"

=== Starting another R from R

`system2(command, args, stdout, stderr, input, env)` runs a program and `system2("Rscript", c("-e", shQuote(code)), stdout = TRUE)` runs another R, collecting standard output as a character vector. The child inherits the environment, including variables set with `Sys.setenv()`. A child that exits with a non-zero status gives a warning when its output is captured, and the status becomes the `"status"` attribute of the result; with `stdout = FALSE` the function returns the status itself. `Sys.which("Rscript")` finds the program on the `PATH` (printed here only as `nzchar()`, because the path is not the point). `file.path(R.home("bin"), "Rscript")` names the `Rscript` that belongs to the running R, which is the right choice when several R versions are installed. Use `shQuote()` for arguments, never `paste()`: a quoted string is the way to survive spaces and quotes. `callr` and `processx` are community packages for the same job with better control; they are named here and not used.

[source,r]
----
# system2.R: run another R process and capture what it prints.
cat("Rscript found on the PATH:", nzchar(Sys.which("Rscript")), "\n")

Sys.setenv(SHELF_MODE = "child")
code <- "cat(Sys.getenv('SHELF_MODE'), commandArgs(TRUE), '\\n')"
out <- system2("Rscript", c("-e", shQuote(code), "a", "b"), stdout = TRUE)
out

# A failing child: with stdout = TRUE the output is kept and the status
# becomes an attribute (R also warns, which is suppressed here).
failing <- "cat('partial\\n'); quit(status = 4)"
bad <- suppressWarnings(
  system2("Rscript", c("-e", shQuote(failing)), stdout = TRUE)
)
as.vector(bad)
attr(bad, "status")

# Without capturing, system2() returns the exit status.
status <- system2(
  "Rscript", c("-e", shQuote("quit(status = 7)")),
  stdout = FALSE, stderr = FALSE
)
status
----

== Parsing arguments

A script with more than two or three arguments needs a parser: options with values, flags, defaults, a `--help` text and a message for a mistake, ending with a non-zero status and the usage text on standard error. The same options are written three ways below, so that they can be compared; the options are the ones of the report script at the end of the page: `--today DATE`, `--genre NAME`, `--format text|csv`, `--stdin` and zero or more file names.

=== With base R

A hand-written parser is about thirty lines and has no dependency, which is the reason to prefer it for a short script or a script that must run on any R installation. The parser in `parse-base.R` accepts `--name value`, `--name=value`, flags, positional arguments and `--` to end the options; `sub()` takes the name and the value from `--name=value`, `match.arg()` checks the format, and an error signalled with a class (`usage_error`) is turned into the usage message and exit status 2 by a `tryCatch()` at the top.

[source,r]
----
# parse-base.R: a small hand-written option parser (base R only).
usage <- function() {
  cat("Usage: Rscript parse-base.R [--today DATE] [--genre NAME]",
      "[--format text|csv] [--stdin] [FILE ...]\n")
}

usage_error <- function(...) {
  stop(structure(
    class = c("usage_error", "error", "condition"),
    list(message = paste0(...), call = NULL)
  ))
}

parse_options <- function(argv) {
  opts <- list(today = NA_character_, genre = NA_character_,
               format = "text", stdin = FALSE, files = character())
  i <- 1L
  while (i <= length(argv)) {
    arg <- argv[[i]]
    if (arg == "--") {
      opts$files <- c(opts$files, argv[-seq_len(i)])
      break
    }
    if (!startsWith(arg, "--")) {
      opts$files <- c(opts$files, arg)
      i <- i + 1L
      next
    }
    name <- sub("^--([^=]*).*$", "\\1", arg)
    if (!name %in% c("today", "genre", "format", "stdin")) {
      usage_error("unknown option: --", name)
    }
    if (name == "stdin") {
      opts$stdin <- TRUE
    } else if (grepl("=", arg, fixed = TRUE)) {
      opts[[name]] <- sub("^[^=]*=", "", arg)
    } else {
      i <- i + 1L
      if (i > length(argv)) usage_error("option --", name, " needs a value")
      opts[[name]] <- argv[[i]]
    }
    i <- i + 1L
  }
  opts$format <- tryCatch(
    match.arg(opts$format, c("text", "csv")),
    error = \(e) usage_error("--format: ", conditionMessage(e))
  )
  opts
}

argv <- commandArgs(trailingOnly = TRUE)
if (any(argv %in% c("-h", "--help"))) {
  usage()
  quit(save = "no", status = 0L)
}
opts <- tryCatch(parse_options(argv), usage_error = \(e) {
  message("parse-base.R: ", conditionMessage(e))
  usage()
  quit(save = "no", status = 2L)
})
str(opts)
----

=== With optparse

optparse is a community package (CRAN, version 1.8.2 here) whose DESCRIPTION calls it a command line parser inspired by Python's `optparse` library, meant for `Rscript` shebang scripts. An `OptionParser` holds a list of options made with `make_option()` (or added with `add_option()`), and `parse_args()` returns a list with the options and, with `positional_arguments = TRUE`, the leftover arguments. It writes the `--help` text itself, prints it and quits with status 0 when asked, and for a parse error prints the usage and a message and quits with status 1. `print_help()` prints the text on demand, and `%prog` in `usage` is replaced by the script name.

[source,r]
----
# parse-optparse.R: the same options with optparse (a CRAN package).

option_list <- list(
  make_option("--today", help = "report date, YYYY-MM-DD"),
  make_option("--genre", help = "only this genre"),
  make_option("--format", default = "text",
              help = "output format: text or csv [default: %default]"),
  make_option("--stdin", action = "store_true", default = FALSE,
              help = "read the loans from standard input")
)
parser <- OptionParser(
  usage = "Rscript %prog [options] [FILE ...]",
  option_list = option_list,
  description = "Print a loan report for the shelf catalogue."
)
parsed <- parse_args(parser, positional_arguments = TRUE)
str(parsed)

Options that have no value and no default are left out of the list (`NULL` entries do not exist), so test with `is.null(opts$genre)`. A usage error exits with status 1, not 2. === Other parsers, and a choice

`docopt` (CRAN) derives the parser from the usage text itself, which is attractive for a small tool; `getopt` is an older, lower-level package still found in older scripts; `commandArgs()` plus `match.arg()` and `switch()` remains common for two-argument scripts. All of these are community packages, none is part of R, and none is needed for the example below. A choice that holds for most scripts: base R for up to three arguments; optparse when a documented `--help` and flags matter and Python is not welcome in the image; argparse when sub-commands (`git`-style) or Python-style help are wanted and Python is already there.

[#status-choices]
=== Choosing statuses

The report script returns 0 for success, 2 for a usage error (an option it does not know, a missing value, a genre that does not exist) and 1 for a data error (a file it cannot read, a file without the columns it needs). The help page of `quit()` recommends statuses of 10 or more for a script's own codes, because R uses 1 for an uncaught error and 2 for catastrophic failures, and `Rscript` itself ends with 2 when the script file cannot be opened, as the earlier transcript showed. This page uses the convention of the shell tools instead (2 for misuse, 1 for any other failure), because it is the one that callers of command-line tools expect and the one the CLI pages in this documentation recommend; the price is that a status of 2 from a caller's point of view means "usage error or `Rscript` could not open the script", which is usually the same kind of mistake. A script with several kinds of failure that a caller must distinguish should document them in `--help` and choose codes of 10 or more, as the help page suggests. A table in xref:ai/cli-for-agents/streams-and-exit-codes.adoc[Streams & Exit Codes] discusses such taxonomies in general.

[cols="1,4",options="header"]
|===
|Status |Meaning in report.R
|0 |A report was written, or `--help` was shown. Data warnings may still have been printed to standard error.
|1 |Data error: a books or loans file does not exist, or lacks a required column. Any unexpected R error (a bug) also ends with 1, by R's default.
|2 |Usage error: unknown option, missing value, bad `--format`, missing or malformed `--today`, unknown `--genre`, `--stdin` together with `--loans`.
|===

[source,r]
----
# report.R: print a loan report for the shelf catalogue.
#
# Usage: Rscript report.R [--today DATE] [--genre NAME] [--format text|csv]
#                         [--books FILE] [--loans FILE | --stdin]
#
# Exit status: 0 success, 1 data error, 2 usage error.
suppressPackageStartupMessages(library(shelf))

usage <- function(con = stdout()) {
  cat("Usage: Rscript report.R [--today DATE] [--genre NAME]\n",
      "                       [--format text|csv] [--books FILE]\n",
      "                       [--loans FILE | --stdin]\n",
      "Without --today the variable SHELF_TODAY is used.\n",
      sep = "", file = con)
}

condition_class <- function(class, ...) {
  structure(class = c(class, "error", "condition"),
            list(message = paste0(...), call = NULL))
}
usage_error <- function(...) stop(condition_class("usage_error", ...))
data_error <- function(...) stop(condition_class("data_error", ...))

parse_options <- function(argv) {
  opts <- list(today = Sys.getenv("SHELF_TODAY", unset = ""), genre = "",
               format = "text", books = "books.csv", loans = "",
               stdin = FALSE)
  i <- 1L
  while (i <= length(argv)) {
    arg <- argv[[i]]
    name <- sub("^--([^=]*).*$", "\\1", arg)
    if (!startsWith(arg, "--") || !name %in% names(opts)) {
      usage_error("unknown argument: ", arg)
    }
    if (name == "stdin") {
      opts$stdin <- TRUE
    } else if (grepl("=", arg, fixed = TRUE)) {
      opts[[name]] <- sub("^[^=]*=", "", arg)
    } else {
      i <- i + 1L
      if (i > length(argv)) usage_error("option --", name, " needs a value")
      opts[[name]] <- argv[[i]]
    }
    i <- i + 1L
  }
  opts$format <- tryCatch(
    match.arg(opts$format, c("text", "csv")),
    error = \(e) usage_error("--format must be text or csv")
  )
  if (!nzchar(opts$today)) usage_error("--today (or SHELF_TODAY) is required")
  opts$today <- as.Date(opts$today, format = "%Y-%m-%d")
  if (is.na(opts$today)) usage_error("the report date must be YYYY-MM-DD")
  if (opts$stdin && nzchar(opts$loans)) {
    usage_error("--stdin and --loans exclude each other")
  }
  if (!nzchar(opts$loans)) opts$loans <- "loans.csv"
  opts
}

read_table <- function(path, what, columns) {
  if (!identical(path, "stdin") && !file.exists(path)) {
    data_error(what, " file not found: ", path)
  }
  con <- if (identical(path, "stdin")) file("stdin") else path
  table <- read.csv(con, colClasses = "character")
  missing <- setdiff(columns, names(table))
  if (length(missing) > 0L) {
    data_error(what, " data lacks the column(s): ", toString(missing))
  }
  table
}

run <- function(argv) {
  if (any(argv %in% c("-h", "--help"))) {
    usage()
    return(invisible())
  }
  opts <- parse_options(argv)
  books <- read_table(opts$books, "books", c("title", "isbn", "genre"))
  loans <- read_table(if (opts$stdin) "stdin" else opts$loans, "loans",
                      c("loan_id", "isbn", "loan_date", "return_date"))
  books <- clean_books(books)
  loans <- clean_loans(loans)

  report <- loan_summary(loans, books, opts$today)
  if (nzchar(opts$genre)) {
    if (!opts$genre %in% report$genre) {
      usage_error("unknown genre '", opts$genre, "'; known genres: ",
                  toString(report$genre))
    }
    report <- report[report$genre == opts$genre, , drop = FALSE]
  }
  report$overdue_rate <- round(report$overdue_rate, 3)

  n_bad_date <- sum(is.na(loans$loan_date))
  if (n_bad_date > 0L) {
    warning(n_bad_date, " loan(s) have no valid loan date", call. = FALSE)
  }
  n_unknown <- sum(!loans$isbn %in% books$isbn)
  if (n_unknown > 0L) {
    warning(n_unknown, " loan(s) match no book and are left out", call. = FALSE)
  }

  if (opts$format == "csv") {
    write.csv(report, row.names = FALSE)
  } else {
    cat("Loan report for ", format(opts$today), ", loan period ",
        getOption("shelf.loan_days"), " days\n\n", sep = "")
    print(report, row.names = FALSE)
    cat("\nOverdue: ", sum(report$overdue), " of ", sum(report$loans),
        " loans\n", sep = "")
  }
}

status <- tryCatch({
  run(commandArgs(trailingOnly = TRUE))
  0L
}, usage_error = \(e) {
  message("report.R: ", conditionMessage(e))
  usage(stderr())
  2L
}, data_error = \(e) {
  message("report.R: ", conditionMessage(e))
  1L
})
quit(save = "no", status = status)
----

Source: https://search.r-project.org/R/refmans/base/html/quit.html[R documentation: quit]

The structure is the one to copy for any script of this size.

* *Parse, then validate, then work.* `parse_options()` has no side effects; it either returns the options or signals a `usage_error`. Dates are parsed with `as.Date(format = )` and an impossible date such as `2026-02-30` is a usage error, not a quietly wrong report. The flag takes its default from `Sys.getenv("SHELF_TODAY")`, so an option given on the command line wins, then the environment, then an error: no call of the current date hides inside the report, which is why the output below is reproducible.
* *Classed conditions carry the kind of failure.* `usage_error` and `data_error` are ordinary conditions with a class added; `run()` signals them with `stop()`, and only the outermost `tryCatch()` decides the status and the message. The code in `run()` never calls `quit()`.
* *One exit.* `quit(save = "no", status = status)` runs once, at the end, after the handlers have printed to standard error with `message()` and `usage(stderr())`. Success is `0L`.
* *Data come from a file or from the pipe.* `read_table()` reads a named file, or `file("stdin")` when `--stdin` is given, with `colClasses = "character"` so that ISBNs and dates stay text until `clean_books()` and `clean_loans()` handle them, and it checks the required columns before the analysis meets a missing one.
* *Warnings are for data the run could use but should say something about.* The number of loans with no valid date and of loans whose ISBN matches no book are counted and reported with `warning(call. = FALSE)`: they go to standard error, they do not change the status, and they print after the results, as R prints deferred warnings after the top-level call.
* *Output has one format switch.* `--format csv` writes `write.csv(row.names = FALSE)` to standard output, which is the part another program reads; `--format text` prints a header, the table and a total.

== Pitfalls

* *Printing instead of returning.* `print()` and autoprinting add `pass:c[[1\]]` prefixes and quotes, and `print(x)` of a data frame pads the columns. For output that another program will read, use `cat()`, `writeLines()` or `write.csv()`, and fix the format of numbers (`format()`, `sprintf()`), since the number of digits printed depends on `options(digits)` and the decimal mark on `options(OutDec)`.
* *Plots in a script.* A plot opened by a script goes to a file, `Rplots.pdf` in the working directory, because the default device of a non-interactive session is `pdf()`. Open the device you want explicitly (see xref:programming-languages/r/base-graphics-and-devices.adoc[Base Graphics and Devices]); R FAQ 7.19 explains the same for PNG files in batch mode.
* *The working directory is the caller's.* A relative path in a script is relative to where the command was started, not to the script. Take paths from arguments, or from the script's own directory (`--file=`), or from a project-root helper, and avoid changing the working directory inside a script.
* *Start-up files change the result.* `.Rprofile` and `.Renviron` apply to every run; a job on another machine behaves differently. `--vanilla` removes the variation, and a pinned set of packages (renv, a container) removes the rest.
* *Waiting for input.* A script that reads `file("stdin")` and is started from a terminal without a pipe waits for the user; `readline()` returns `""` at once. Neither is an error, and both look like a hang or a wrong result.
* *Exit status of a pipeline.* The status of a pipeline `+a | b+` is the status of `b` unless `set -o pipefail` (bash) is set; check the status of the stage that matters.
* *Warnings do not fail.* A script that must fail on bad data checks its conditions and calls `stop()`, or sets `options(warn = 2)`.
* *Secrets in arguments.* Arguments appear in process listings and shell history. Use the environment or a file with restricted permissions.
* *`quit()` in the middle.* It skips `on.exit()` and `finally`, and it ends a session that loaded the file with `source()`.

== Where older tutorials differ

[cols="3,4",options="header"]
|===
|Older advice |What to do now

|`R --slave --no-save < script.R`, or `R CMD BATCH script.R` as the way to run a script
|`Rscript script.R`. `--slave` is the old name of `--no-echo` and still works; `R CMD BATCH` saves and restores `.RData` by default, so it needs `--vanilla`. "An Introduction to R" still names `R CMD BATCH` first, but `Rscript` is the front end for arguments and shebang lines.

|`+#!/usr/bin/Rscript+` or any hard-coded path
|`+#!/usr/bin/env Rscript+`, which finds `Rscript` on the `PATH`.

|`+args <- commandArgs(TRUE)+` with positional access and no checks, or `pass:c[commandArgs()[6\]]`
|`commandArgs(trailingOnly = TRUE)`, a length check, and a parser for options. Index arithmetic on the full vector breaks with `--vanilla`.

|`library(methods)` at the top of every script
|Needed before R 3.5.0, when `Rscript` did not attach `methods`; harmless now.

|`source("script.R")` to run a script, or `source(echo = TRUE)` to see results
|Run it with `Rscript`. `source()` is for loading code into a session, and its autoprint rules differ.

|The `getopt` package for options
|`getopt` is still on CRAN; optparse (or a short base parser) is what newer scripts use.

|A `setwd` call built from `sys.frame(1)$ofile` to find the script's directory
|The `--file=` argument of `commandArgs()`, or a project-root helper such as `here` (community packages).

|`+Sys.setenv(DB_PASSWORD = "...")+` at the top of a script
|Read the credential from the environment that the caller provides (`Sys.getenv()`); never write it in a file under version control.

|`print("done")` or `cat("error\n")` for diagnostics
|`message()` for diagnostics, which goes to standard error, and a non-zero `quit(status = )` or `stop()` for failures.

|`system(paste("Rscript", f))`
|`system2("Rscript", shQuote(f), stdout = TRUE)`, which captures the output and quotes the argument.

Within R: xref:programming-languages/r/sessions-workspaces-and-startup.adoc[Sessions, Workspaces and Startup] for the files a script run reads, xref:programming-languages/r/conditions-and-error-handling.adoc[Conditions and Error Handling] and xref:programming-languages/r/defensive-programming-and-input-validation.adoc[Defensive Programming and Input Validation] for the failures a script turns into statuses, xref:programming-languages/r/creating-packages.adoc[Creating Packages] for the `shelf` package the report uses, xref:programming-languages/r/testing-with-testthat.adoc[Testing with testthat], xref:programming-languages/r/reports-with-quarto-and-r-markdown.adoc[Reports with Quarto and R Markdown] for a report that is a document instead of a table, and xref:programming-languages/r/shiny-plumber-and-web-apis.adoc[Shiny, plumber and Web APIs] for R programs that stay running.
