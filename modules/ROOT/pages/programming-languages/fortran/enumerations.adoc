run was compiled warning-free with `gfortran -std=f2023 -Wall -Wextra -pedantic -fimplicit-none -fcheck=all`

text, and, where it was possible, against the semantic analysis of Flang, not as run. Enumerations are defined in clause 7.6
of the standard ("Other nonintrinsic types"): 7.6.1 for interoperable enumerations and enum types, 7.6.2 for enumeration types.

An enumeration is a closed set of named values. Fortran has had one since Fortran 2003, but only as a companion of the C
interoperability feature: a block of `enumerator` statements that declares named integer constants with the kind that a C
compiler would pick for the matching `enum`. Fortran 2023 keeps that form, renames it *interoperable enumeration* and lets it
carry a type name (an *enum type*), and adds a second, purely Fortran feature, the *enumeration type*, whose values are not
integers at all. The two are easy to confuse, so keep this table in mind for the rest of the page.

[cols="2,3,3",options="header"]
|===
| |Interoperable enumeration (`enum, bind(c)`) |Enumeration type (`enumeration type`)

|Statement |`enum, bind(c)` ... `enumerator` ... `end enum` |`enumeration type :: name` ... `enumerator` ... `end enumeration type`
|Clause |7.6.1 |7.6.2
|What the enumerators are |named integer constants of a C-compatible kind |named constants of a new nonintrinsic type
|Interoperable with C |yes, with the matching C `enum` |no
|Type name |optional (`enum, bind(c) :: name`, new in Fortran 2023) |required
|Mixing with integers |free (an enumerator is an integer) |not allowed, except through the constructor and `int`
|Arithmetic |all integer operations |none, only comparison
|Provenance |Fortran 2003; typed form and renaming in Fortran 2023 |Fortran 2023
|GNU Fortran 16.2 |yes, untyped form only |no
|LLVM Flang 23.1.4 |yes, untyped form only |parsed and checked with `-fenumeration-type`, but not compiled
|===

Readers coming from C will find the corresponding construct in
xref:programming-languages/c/constants-enumerations-and-initialization.adoc[Constants, Enumerations and Initialization]; the
important difference is that Fortran's interoperable enumeration is in practice only a way to declare a group of integer
constants, while the F2023 enumeration type behaves like the enums of Ada or Rust. Where to place the declarations is
covered in xref:programming-languages/fortran/modules-and-submodules.adoc[Modules and Submodules], and
the integer kinds that enumerators receive in xref:programming-languages/fortran/intrinsic-types-and-kinds.adoc[Intrinsic Types and Kinds].

== Interoperable enumerations

An interoperable enumeration (7.6.1) is an `enum, bind(c)` statement, one or more `enumerator` statements and an `end enum`.
The enumerators it declares are *named integer constants*: each behaves exactly as if it had been declared with the `parameter`
attribute, so it can appear in constant expressions, array bounds, `do` bounds, `case` values and initializers, and it cannot be
assigned to. All the enumerators of one `enum` block have the same kind, and the standard requires that kind to be the one
that is interoperable with the C `enum` that would be declared with the same values in the same order (7.6.1 and 18.3.1).

[source,fortran]
----
program enum_basic
  use, intrinsic :: iso_c_binding, only: c_int
  implicit none

  enum, bind(c)
    enumerator :: red = 4, blue = 9
    enumerator :: yellow
  end enum

  integer(kind(red)) :: colour
  integer :: k

  colour = blue
  print '(a, i0)', 'kind of the enumerators: ', kind(red)
  print '(a, i0)', 'c_int:                   ', c_int
  print '(a, 3(i0, 1x))', 'values: ', red, blue, yellow
  print '(a, l1)', 'colour == blue: ', colour == blue
  k = int(colour) + 1
  print '(a, i0)', 'blue + 1 = ', k
  select case (colour)
  case (red)
    print '(a)', 'red'
  case (blue, yellow)
    print '(a)', 'blue or yellow'
  end select
end program enum_basic
----

Output (identical with GNU Fortran 16.2 and LLVM Flang 23.1.4):

[source,text]
----
kind of the enumerators: 4
c_int:                   4
values: 4 9 10
colour == blue: T
blue + 1 = 10
blue or yellow
----

Source: https://j3-fortran.org/doc/year/23/23-007r1.pdf[J3/23-007r1, 7.6.1 Interoperable enumerations and enum types]

There is no Fortran type called "enum" in this form. A variable that holds an enumerator is declared with the *kind* of the
enumerators, `integer(kind(red))`, as in the standard's own note on interoperable enumerations. `kind` accepts any one of the enumerators as its argument,
so the declaration follows the enum if its kind ever changes. Declaring the variable as plain `integer` works only while the
processor's choice happens to be the default integer kind, which it is for both compilers used here.

=== How the values are assigned

The rule of 7.6.1 is the same as in C. An enumerator with an explicit `= constant-expression` has that value. Otherwise the first
enumerator of the block has the value zero and every later one has the value of its predecessor plus one. Several
`enumerator` statements in one block are the same as one long statement: only their order matters. Values may be negative and
may repeat, because nothing in 7.6.1 requires them to be distinct, which has consequences for `select case`, shown below.

[source,fortran]
----
program enum_values
  implicit none

  ! No value given: the first enumerator is 0, each next one is previous + 1
  enum, bind(c)
    enumerator :: first, second, third
  end enum

  ! Explicit values may restart the counting, be negative, or repeat
  enum, bind(c)
    enumerator :: low = -2, mid, high = 10, higher
    enumerator :: alias_of_high = 10
  end enum

  print '(a, 3(i0, 1x))', 'first, second, third: ', first, second, third
  print '(a, 4(i0, 1x))', 'low, mid, high, higher: ', low, mid, high, higher
  print '(a, i0)', 'alias_of_high: ', alias_of_high
  print '(a, l1)', 'high == alias_of_high: ', high == alias_of_high
  print '(a, 2(i0, 1x))', 'kinds: ', kind(first), kind(low)
end program enum_values
----

Output (identical with GNU Fortran 16.2 and LLVM Flang 23.1.4):

[source,text]
----
first, second, third: 0 1 2
low, mid, high, higher: -2 -1 10 11
alias_of_high: 10
high == alias_of_high: T
kinds: 4 4
----

Source: https://j3-fortran.org/doc/year/23/23-007r1.pdf[J3/23-007r1, 7.6.1 Interoperable enumerations and enum types]

Two syntax details come from the constraint on `enumerator` (C7111): the `::` separator is optional in `enumerator yellow` but
mandatory as soon as an `=` appears in the list. An `enum` block has no name unless you use the typed form described below,
and the kind of each block is chosen separately, so two blocks in one program may in principle have different kinds.

=== Enumerators are named constants

Because an enumerator is a named constant, it is usable wherever a constant integer expression is, and it is not a variable.
The first listing uses enumerators as the bounds of an array and of a `do` loop and as an index; the second tries to assign
to one.

[source,fortran]
----
program enum_constants
  implicit none
  enum, bind(c)
    enumerator :: red = 1, green, blue
  end enum
  integer(kind(red)) :: colour
  character(len=5), parameter :: names(red:blue) = [character(len=5) :: 'red', 'green', 'blue']
  integer :: c

  ! Enumerators are integer named constants: array bounds, do bounds, case values
  do c = red, blue
    print '(i0, 1x, a)', c, trim(names(c))
  end do
  colour = green
  print '(2a)', 'colour is ', trim(names(colour))
end program enum_constants
----

Output (identical with both compilers):

[source,text]
----
1 red
2 green
3 blue
colour is green
----

Source: https://j3-fortran.org/doc/year/23/23-007r1.pdf[J3/23-007r1, 7.6.1 Interoperable enumerations and enum types and 8.5.13 PARAMETER attribute]

This is the idiom for mapping an enumerator to a name: a constant array indexed by the enumerators. It works while the enumerators are
consecutive and start at a known value, which is why the examples start the block at `= 1`; with gaps or negative values, use a
`select case` function instead (see the heatflow module below).

Deliberate error, assigning to an enumerator:

[source,fortran]
----
program enum_assign
  implicit none
  enum, bind(c)
    enumerator :: red = 1, green, blue
  end enum
  red = 5
  print '(i0)', red
end program enum_assign
----

=== Bit flags

Enumerators with distinct powers of two are the classic way to name bits. Since an enumerator is an integer, the bit
intrinsics `ior`, `iand`, `ieor` and `not` apply directly (see
xref:programming-languages/fortran/numeric-model-bit-manipulation-and-conversion.adoc[Numeric Model, Bit Manipulation and Conversion]).

[source,fortran]
----
module file_modes
  implicit none
  private
  public :: mode_read, mode_write, mode_exec, describe

  enum, bind(c)
    enumerator :: mode_read = 1, mode_write = 2, mode_exec = 4
  end enum

contains

  function describe(flags) result(text)
    integer(kind(mode_read)), intent(in) :: flags
    character(len=3) :: text
    text = '---'
    if (iand(flags, mode_read) /= 0)  text(1:1) = 'r'
    if (iand(flags, mode_write) /= 0) text(2:2) = 'w'
    if (iand(flags, mode_exec) /= 0)  text(3:3) = 'x'
  end function describe
end module file_modes

program enum_flags
  use file_modes
  implicit none
  integer(kind(mode_read)) :: perms

  perms = ior(mode_read, mode_write)
  print '(a)', describe(perms)
  perms = ior(perms, mode_exec)
  print '(a)', describe(perms)
  perms = iand(perms, not(mode_write))
  print '(a)', describe(perms)
end program enum_flags
----

Output (identical with both compilers):

[source,text]
----
rw-
rwx
r-x
----

Source: https://j3-fortran.org/doc/year/23/23-007r1.pdf[J3/23-007r1, 7.6.1 Interoperable enumerations and enum types and 16.9.100 IAND, 16.9.111 IOR and 16.9.154 NOT]

The enumerators are made `public` by name in the module's access list; `private` in the module header keeps the module's
other names hidden. Accessibility of the enumerators of an interoperable enumeration is therefore the ordinary accessibility
of named constants (8.5.2); Fortran 2028 will allow it to be set per enumerator (see below).

=== select case and overlapping values

`select case` accepts an enumerator wherever it accepts a constant integer, including ranges such as `case (mode_read:mode_exec)`
(see xref:programming-languages/fortran/control-flow.adoc[Control Flow]). Because enumerators may repeat a value, the rule that no
value may match two `case` selectors (C1154) can be violated by two different names, and the compiler reports it.

[source,fortran]
----
program case_overlap
  implicit none
  enum, bind(c)
    enumerator :: fast = 1, slow = 2
    enumerator :: default_speed = 1
  end enum
  integer(kind(fast)) :: speed

  speed = default_speed
  select case (speed)
  case (fast)
    print '(a)', 'fast'
  case (default_speed)
    print '(a)', 'default'
  case (slow)
    print '(a)', 'slow'
  end select
end program case_overlap
----

GNU Fortran 16.2:

[source,text]
----
13_case_overlap.f90:11:8:

   11 |   case (fast)
      |        1
   12 |     print '(a)', 'fast'
   13 |   case (default_speed)
      |        2
Error: CASE label at (1) overlaps with CASE label at (2)
----

LLVM Flang 23.1.4:

[source,text]
----
error: Semantic errors in 13_case_overlap.f90
13_case_overlap.f90:13:3: error: CASE (1_4) conflicts with previous cases
    case (default_speed)
    ^^^^^^^^^^^^^^^^^^^^
13_case_overlap.f90:11:3: Conflicting CASE (1_4)
    case (fast)
    ^^^^^^^^^^^
----

Source: https://j3-fortran.org/doc/year/23/23-007r1.pdf[J3/23-007r1, 11.1.9 SELECT CASE construct]

Aliases such as `default_speed` are legitimate in the enumeration but must be left out of the `select case`. Neither compiler
checks that a `select case` over an enumeration handles every enumerator, and neither warns about a missing one: put a `case default`
in every such construct.

=== The kind of the enumerators and -fshort-enums

The standard fixes only that the kind is interoperable with the corresponding C `enum`, so it is processor dependent. GNU Fortran
uses a C-compatible kind that follows its companion C compiler: by default the size of a C `int`. The GNU Fortran option
`-fshort-enums` mirrors the GCC option of the same name: it makes the compiler choose the smallest integer kind that holds all
the values of a block, so that an enum matches C code compiled with `-fshort-enums`.

[source,fortran]
----
program enum_short
  implicit none
  enum, bind(c)
    enumerator :: a = 1, b = 2, c = 100
  end enum
  print '(a, 3(i0, 1x))', 'values: ', a, b, c
  print '(a, i0)', 'kind(a) = ', kind(a)
  print '(a, i0)', 'huge of that kind: ', huge(a)
end program enum_short
----

Built with `gfortran -std=f2023 -fshort-enums` (GNU Fortran 16.2):

[source,text]
----
values: 1 2 100
kind(a) = 1
huge of that kind: 127
----

Built without the option (GNU Fortran 16.2, and also LLVM Flang 23.1.4, which does not accept `-fshort-enums`):

[source,text]
----
values: 1 2 100
kind(a) = 4
huge of that kind: 2147483647
----

Source: https://gcc.gnu.org/onlinedocs/gfortran/Code-Gen-Options.html[GNU Fortran manual: Options for code generation conventions (-fshort-enums)]

Because the option changes the kind of every enumerator in the program, it has to be applied to every Fortran file that shares
enums with the C code, and never to only some of them. Do not use it unless the C side was built with it.

=== Calling C with an enumerated argument

The point of an interoperable enumeration is to share it with C. A C `enum` is passed as an `int`-compatible value, so the
Fortran interface passes `integer(c_int), value`. The C side below is the library part of the heatflow project: it takes a
boundary condition and returns the number of ghost cells the stencil needs.

[source,c]
----
#ifndef BOUNDARY_H
#define BOUNDARY_H

enum heatflow_bc { HEATFLOW_DIRICHLET = 1, HEATFLOW_NEUMANN = 2, HEATFLOW_PERIODIC = 3 };

/* Returns the number of ghost cells needed for the given boundary condition. */
int heatflow_ghost_cells(enum heatflow_bc bc);

#endif
----

[source,c]
----
#include "boundary.h"

int heatflow_ghost_cells(enum heatflow_bc bc)
{
    switch (bc) {
    case HEATFLOW_DIRICHLET: return 0;
    case HEATFLOW_NEUMANN:   return 1;
    case HEATFLOW_PERIODIC:  return 1;
    }
    return -1;
}
----

[source,fortran]
----
module heatflow_boundary_c
  use, intrinsic :: iso_c_binding, only: c_int
  implicit none
  private
  public :: dirichlet, neumann, periodic, bc_kind, ghost_cells

  enum, bind(c)
    enumerator :: dirichlet = 1, neumann = 2, periodic = 3
  end enum
  integer, parameter :: bc_kind = kind(dirichlet)

  interface
    function ghost_cells(bc) bind(c, name='heatflow_ghost_cells') result(n)
      import :: c_int
      integer(c_int), value :: bc
      integer(c_int) :: n
    end function ghost_cells
  end interface
end module heatflow_boundary_c

program enum_c
  use heatflow_boundary_c
  implicit none
  print '(a, i0)', 'dirichlet: ', ghost_cells(dirichlet)
  print '(a, i0)', 'neumann:   ', ghost_cells(neumann)
  print '(a, i0)', 'periodic:  ', ghost_cells(periodic)
  print '(a, i0)', 'bogus 99:  ', ghost_cells(99)
end program enum_c
----

Built with `gcc -std=c17 -Wall -Wextra -pedantic -c boundary.c` and, for Fortran, the strict `gfortran` command line above plus
`boundary.o`; also built and run with `flang-23` and the same object file. Output (identical with both compilers):

[source,text]
----
dirichlet: 0
neumann:   1
periodic:  1
bogus 99:  -1
----

Source: https://j3-fortran.org/doc/year/23/23-007r1.pdf[J3/23-007r1, 7.6.1 Interoperable enumerations and enum types and 18.3.3 Interoperability of enum types]

The interface uses `integer(c_int)` rather than `integer(kind(dirichlet))` on purpose: GNU Fortran 16.2 accepts the latter but
warns that the dummy argument "may not be C interoperable" (`-Wc-binding-type`), because it does not recognise the kind of an
enumerator as a `bind(c)` kind. On the usual platforms the two are the same kind, and `bc_kind` remains available for ordinary
Fortran declarations. The last call shows what the interface does not give you: nothing stops `99`, which is not an enumerator,
from reaching C, and the C function has to handle it. See
xref:programming-languages/fortran/interoperability-with-c.adoc[Interoperability with C] for the rest of the `bind(c)` rules,
including how to pass the same `enum` through a `c_ptr` array or a derived type.

=== The heatflow boundary conditions

The heatflow project describes its three boundary conditions with an interoperable enumeration, because Fortran 2023's
enumeration type is not accepted by the compilers it targets (see below). The module also shows the parts that a plain enum does not
give you: a name lookup, a range check for values that come from outside, and a one-line conversion from an untrusted integer.

[source,fortran]
----
module heatflow_boundary
  implicit none
  private
  public :: bc_kind, dirichlet, neumann, periodic
  public :: boundary_name, is_valid_bc, bc_from_integer

  enum, bind(c)
    enumerator :: dirichlet = 1
    enumerator :: neumann = 2
    enumerator :: periodic = 3
  end enum
  integer, parameter :: bc_kind = kind(dirichlet)

contains

  pure function boundary_name(bc) result(name)
    integer(bc_kind), intent(in) :: bc
    character(len=:), allocatable :: name
    select case (bc)
    case (dirichlet)
      name = 'dirichlet'
    case (neumann)
      name = 'neumann'
    case (periodic)
      name = 'periodic'
    case default
      name = 'unknown'
    end select
  end function boundary_name

  ! The enumerators are contiguous, so a range test is enough.
  pure logical function is_valid_bc(bc)
    integer(bc_kind), intent(in) :: bc
    is_valid_bc = bc >= dirichlet .and. bc <= periodic
  end function is_valid_bc

  ! Convert an untrusted integer (for example from a namelist) and report failure.
  pure subroutine bc_from_integer(raw, bc, ok)
    integer, intent(in) :: raw
    integer(bc_kind), intent(out) :: bc
    logical, intent(out) :: ok
    ok = raw >= dirichlet .and. raw <= periodic
    bc = dirichlet
    if (ok) bc = int(raw, bc_kind)
  end subroutine bc_from_integer
end module heatflow_boundary

program boundary_demo
  use heatflow_boundary
  implicit none
  integer(bc_kind) :: bc
  integer :: bc_raw, unit, stat, i
  logical :: ok
  character(len=80) :: msg
  namelist /heatflow/ bc_raw

  ! Write and read back a one-variable namelist: an enumerator is just an integer.
  bc_raw = periodic
  open (newunit=unit, status='scratch', action='readwrite')
  write (unit, nml=heatflow)
  rewind (unit)
  bc_raw = -1
  read (unit, nml=heatflow, iostat=stat, iomsg=msg)
  close (unit)
  print '(a, i0, a, i0)', 'read back bc = ', bc_raw, ', iostat = ', stat

  call bc_from_integer(bc_raw, bc, ok)
  print '(3a, l1)', 'converted: ', boundary_name(bc), ', ok = ', ok

  do i = dirichlet, periodic
    print '(i0, 1x, a)', i, boundary_name(int(i, bc_kind))
  end do

  ! Nothing stops an out-of-range value: an enum variable is an integer.
  bc = 42_bc_kind
  print '(3a, l1)', 'forced 42: ', boundary_name(bc), ', valid = ', is_valid_bc(bc)
  call bc_from_integer(7, bc, ok)
  print '(3a, l1)', 'from 7: ', boundary_name(bc), ', ok = ', ok
end program boundary_demo
----

Output (identical with both compilers):

[source,text]
----
read back bc = 3, iostat = 0
converted: periodic, ok = T
1 dirichlet
2 neumann
3 periodic
forced 42: unknown, valid = F
from 7: dirichlet, ok = F
----

Source: https://j3-fortran.org/doc/year/23/23-007r1.pdf[J3/23-007r1, 7.6.1 Interoperable enumerations and enum types, 11.1.9 SELECT CASE construct and 13.11 Namelist formatting]

In the real heatflow code the run configuration reads the boundary condition from the namelist as a plain integer, the
conversion routine is called once, and the grid code receives an `integer(bc_kind)` and a `select case` over the enumerators.
The page on xref:programming-languages/fortran/internal-files-namelist-and-non-advancing-io.adoc[Internal Files, Namelist and Non-Advancing I/O]
shows the namelist in detail. The conversion matters because an interoperable enumeration offers no type safety at all: any
integer of the right kind is a valid value, so `bc = 42_bc_kind` compiles, runs and is only caught by the `case default`.

== Enum types: the typed interoperable enumeration

Fortran 2023 allows an interoperable enumeration to have a name: `enum, bind(c) :: colour_t`. The name defines an *enum type*
(7.6.1), an interoperable nonintrinsic type that is not a derived type and has no type parameters. It still has the
representation of the integer kind of its enumerators, so its values correspond one to one to the integers of that kind,
and it interoperates with the matching C `enum` and with the C integer type of the enumerators (18.3.3). What the type adds is a
declaration form, `type(colour_t) :: x`, and a set of rules that make the enumerators and the integers cooperate in a controlled way:

* **Declaration.** `type(colour_t) :: x = red`; the type is in scope where its name is accessible.
* **Constructor.** `colour_t(expr)` converts a scalar integer expression (or a BOZ constant) to the type (R765, C7113). The
  value must be representable in the integer kind, but it does not have to be one of the enumerators: `colour_t(12345)` is valid.
* **Assignment.** The right-hand side may be of the same enum type, or an integer expression whose primary is an enumerator of
  that type; the integer is converted as if by the constructor (10.2.1.2, Table 10.8).
* **Comparison.** The relational operators accept two operands of the enum type, or one operand of the type and an integer
  expression involving an enumerator of that type; they compare the integer values (10.1.5.5).
* **Type compatibility.** An entity of the enum type is type compatible with an integer expression that has an enumerator of that
  type as a primary (7.3.3), which is what lets `type(colour_t), value :: a` accept `red` as an actual argument.
* **Intrinsics.** `int(x)` returns the integer value of an enum-type `x` (16.9.110). Array constructors with a type specification
  accept the type as long as the elements are in type conformance with it (C7121).
* **I/O.** Values are transferred with the `I`, `B`, `O`, `Z` and `G` edit descriptors as the corresponding integer (13.7.2.1 and 13.7.2.2).
* **Association.** A nonpointer enum object may be storage-associated (in a common block) only with an object of the same type (8.10.2.4).

Not allowed: assigning a plain integer that is not an enumerator (`type(myenum) :: z = 12345`), passing a non-enumerator
integer (`call sub(999)`) without the constructor, and using an enumerator of another enum type (`call sub(f1)` when `f1`
belongs to a different enum). These are the examples of the standard's own note on the subject.

[source,fortran]
----
module enum_mod
  implicit none
  private
  public :: myenum, flags, one, two, three, f1, f2, f3, show

  enum, bind(c) :: myenum
    enumerator :: one = 1, two, three
  end enum

  enum, bind(c) :: flags
    enumerator :: f1 = 1, f2 = 2, f3 = 4
  end enum

contains

== The enumeration type

The enumeration type (7.6.2) is a type whose values are exactly a list of names, with no arithmetic and no accidental mixing
with integers. It is defined in the specification part of a program
unit, usually a module, with an `enumeration type` statement, `enumerator` statements and `end enumeration type`.

The rules of 7.6.2 in brief:

* **Syntax.** `enumeration type [[, access-spec] ::] name`, then one or more `enumerator [::] name-list` statements, then
  `end enumeration type [name]` (R766 to R769). An `access-spec` may appear only in a module (C7114); it gives the accessibility of
  the type name and the default accessibility of its enumerators.
* **Enumerators.** Each is a scalar named constant of the type. Their order defines their *ordinal position*, counting from 1.
  They have no integer value of their own.
* **Not a derived type.** It has no type parameters, and WG5 N2212 describes it as behaving like a derived type with no
  components. It is not interoperable with C. Variables may be scalars, arrays, allocatable, pointers, components of derived
  types and coarrays; they may not be polymorphic (N2212).
* **Same type.** Two entities have the same type if they are declared with reference to the same enumeration type definition.
* **Constructor.** `name(i)` produces the enumerator whose ordinal position is `i`; `i` must be positive and not greater than the
  number of enumerators (R771).
* **Assignment.** The right-hand side must be of the same enumeration type (Table 10.8). `a = 1` and `a = other_type_enumerator`
  are errors.
* **Comparison.** `==`, `/=`, `<`, `+<=+`, `>` and `>=` between two values of the same type are available, and compare ordinal positions
  (10.1.5.5.1). No other intrinsic operation exists, and none can be applied to one enumeration-type operand and an integer.
* **select case.** The case expression and the case values may be of an enumeration type; ranges such as `case (w2:w4)` follow
  the ordinal order (C1150, C1152). A constant array of the type may be written with an array constructor with a type
  specification, `[bc_t :: dirichlet, neumann]` (C7123).
* **Intrinsics.** `int(x)` returns the ordinal position (16.9.110); `huge(x)` returns the last enumerator (16.9.96); the new
  elemental functions `next(a [, stat])` and `previous(a [, stat])` return the following or preceding enumerator, and stay on the
  last or first one respectively (16.9.151 and 16.9.164). When `stat` is present it receives zero, or a positive processor-dependent
  value at the end of the range; when it is absent, running off the end initiates error termination.
* **I/O.** An enumeration-type item must not appear in a list-directed transfer (12.6.3). In a formatted transfer it corresponds
  to an `I`, `B`, `O` or `Z` edit descriptor, which write and read the ordinal position; an input value must be between 1 and the
  number of enumerators (13.7.2.2). It is not allowed in a namelist group (C8109, 8.9), in an `equivalence` (8.10.1) or in a
  `common` block (C8123, 8.10.2). Unformatted I/O is not restricted by the standard.

=== A boundary-condition type

The heatflow boundary condition kinds are the natural application. The module below is how the project would declare them with the
enumeration type: the type name replaces `bc_kind`, the `edge_t` component has a default value, and the lookup function needs no
integer conversion.

[source,fortran]
----
module heatflow_boundary
  implicit none
  private
  public :: bc_t, dirichlet, neumann, periodic, boundary_name, edge_t

  enumeration type :: bc_t
    enumerator :: dirichlet, neumann, periodic
  end enumeration type bc_t

  type :: edge_t
    type(bc_t) :: bc = periodic
    real :: value = 0.0
  end type edge_t

contains

  pure function boundary_name(bc) result(name)
    type(bc_t), intent(in) :: bc
    character(len=:), allocatable :: name
    select case (bc)
    case (dirichlet)
      name = 'dirichlet'
    case (neumann:periodic)
      name = 'neumann or periodic'
    case default
      name = 'unknown'
    end select
  end function boundary_name
end module heatflow_boundary

program enumeration_demo
  use heatflow_boundary
  implicit none
  type(bc_t) :: a, b
  type(bc_t), parameter :: all_bc(*) = [bc_t :: dirichlet, neumann, periodic]
  type(edge_t) :: edge
  integer :: i
  logical :: same, ordered

  a = bc_t(2)
  b = neumann
  same = a == b
  ordered = dirichlet < periodic
  do i = 1, size(all_bc)
    if (all_bc(i) == edge%bc) print '(2a)', 'default edge: ', boundary_name(all_bc(i))
  end do
  print '(i2)', a
  if (same .and. ordered) stop 0
end program enumeration_demo
----

== Fallbacks while compilers catch up

Three techniques cover the work of an enumeration type with what every compiler accepts; the table adds the real enumeration type for
comparison. They differ in how much the compiler checks.

[cols="2,3,3,3",options="header"]
|===
|Technique |What the compiler checks |Cost |Example in this page

|Named integer constants (`integer, parameter`) |nothing: any integer is accepted |least code; no C interoperability guarantee |the arrays-of-names idiom above
|`enum, bind(c)` |nothing: any integer of the kind is accepted; overlaps in `select case` |matches C `enum`; the heatflow choice |`heatflow_boundary` above
|Derived type with a private integer component and defined `==` and `/=` |no mixing with integers, no arithmetic, no ordering unless you define it |more code, no `select case` on the type |next example
|F2023 `enumeration type` |all of the above plus ordering and a closed set of values |needs a compiler that implements it |previous section
|===

The third technique emulates the type safety of an enumeration type with a derived type whose component is `private`: code outside
the module cannot construct a value other than the constants, cannot compare with an integer, and cannot assign an integer. The
default value of the component, 0, is "unset".

[source,fortran]
----
module heatflow_boundary_safe
  implicit none
  private
  public :: bc_t, dirichlet, neumann, periodic
  public :: operator(==), operator(/=), bc_name, bc_from_name

  ! A derived type with a private component cannot be mixed up with plain
  ! integers or with another such type, which is the guarantee that the
  ! F2023 enumeration type provides natively.
  type :: bc_t
    private
    integer :: id = 0
  end type bc_t

  type(bc_t), parameter :: dirichlet = bc_t(1)
  type(bc_t), parameter :: neumann = bc_t(2)
  type(bc_t), parameter :: periodic = bc_t(3)

  character(len=9), parameter :: names(3) = [character(len=9) :: 'dirichlet', 'neumann', 'periodic']

  interface operator(==)
    module procedure bc_equal
  end interface
  interface operator(/=)
    module procedure bc_not_equal
  end interface

contains

  elemental logical function bc_equal(a, b)
    type(bc_t), intent(in) :: a, b
    bc_equal = a%id == b%id
  end function bc_equal

  elemental logical function bc_not_equal(a, b)
    type(bc_t), intent(in) :: a, b
    bc_not_equal = a%id /= b%id
  end function bc_not_equal

  function bc_name(bc) result(name)
    type(bc_t), intent(in) :: bc
    character(len=:), allocatable :: name
    if (bc%id >= 1 .and. bc%id <= size(names)) then
      name = trim(names(bc%id))
    else
      name = 'unset'
    end if
  end function bc_name

  function bc_from_name(name, found) result(bc)
    character(len=*), intent(in) :: name
    logical, intent(out) :: found
    type(bc_t) :: bc
    integer :: i
    found = .false.
    do i = 1, size(names)
      if (trim(names(i)) == name) then
        bc = bc_t(i)
        found = .true.
        return
      end if
    end do
  end function bc_from_name
end module heatflow_boundary_safe

program safe_enum
  use heatflow_boundary_safe
  implicit none
  type(bc_t) :: left, right
  logical :: ok

  print '(2a)', 'default value: ', bc_name(left)
  left = neumann
  right = bc_from_name('periodic', ok)
  print '(3a, l1)', 'right = ', bc_name(right), ', found = ', ok
  print '(a, l1)', 'left == right: ', left == right
  print '(a, l1)', 'left /= right: ', left /= right
  right = bc_from_name('robin', ok)
  print '(3a, l1)', 'right = ', bc_name(right), ', found = ', ok
end program safe_enum
----

`private`, the structure constructor `bc_t(1)` can be written only inside the module that defines the type. When a compiler you
use accepts the enumeration type, replacing the emulation by it removes `bc_equal`, `bc_not_equal` and the `names` table, and gives
back `select case`.

== Upcoming in Fortran 2028

The latest public working draft of the next revision, J3/26-007r1 (3 March 2026), extends both kinds of enumeration. It is a draft; the text
may change before the standard is published, and no compiler used here implements any of it, so the items below are described from
the draft, not tested.

* **Scoped enumerator values (9.5).** `type-name%enumerator-name` names an enumerator through its type, "as if it were a component",
  for enum types and enumeration types alike, even when the enumerator itself is not accessible in the scoping unit. With the
  draft's own pattern, a module can keep its enumerators `private` and still let users write `light = signal%amber`, which stops
  enumerators from polluting the namespace of every program that uses the module.
* **Accessibility of enumerators.** `enumerator, private :: off, green` sets the accessibility of single enumerators in an
  `enum` or `enumeration type`, and `enum, bind(c), private :: name` the accessibility of an enum type name (7.6.1, 7.6.2).
* **Kind of an interoperable enumeration.** `enum (kind=c_long), bind(c) :: name` gives the enumerators an explicit kind, which matches
  the C23 syntax `+enum name : long { ... }+`; the draft says it follows ISO/IEC 9899:2024.
* **BOZ enumerator values.** An `enumerator` may take a `boz-literal-constant` value, for flags written in binary or hexadecimal.
* **Enumeration types in I/O.** Items of enumeration type may appear in list-directed and namelist data transfer and correspond to the
  `G` edit descriptor, which removes the restrictions that make them awkward to read and write today.

[source,fortran]
----
module traffic_signal_m
  implicit none
  enumeration type, public :: traffic_signal
    enumerator, private :: off, green, amber, red
  end enumeration type
end module traffic_signal_m
----

*Fortran 2028 draft; accepted by no compiler; not run.* Users of the module could write `light = signal%amber` with `light` of type
`traffic_signal` (here renamed `signal` in a `use` statement), following 9.5 of the draft. See
xref:programming-languages/fortran/whats-new-and-fortran-2028-preview.adoc[What's New and Fortran 2028 Preview] for the other work items.

Source: https://j3-fortran.org/doc/year/26/26-007r1.pdf[J3/26-007r1, the Fortran 2028 working draft: 7.6.1, 7.6.2 and 9.5 Scoped enumerator values]

== Pitfalls

* **An interoperable enumeration is not a type.** Any integer of the right kind is a valid "value"; the compiler warns about nothing. Validate
  values that come from outside (files, namelists, C), as `bc_from_integer` does.
* **`select case` does not check completeness.** Neither compiler warns about a missing enumerator; add `case default`, and make it fail
  loudly during development.
* **Aliased values in one `enum`** (two names with one value) are legal but cannot both appear in one `select case`: C1154 and the
  diagnostics above.
* **Using plain `integer` for the variable.** It works while the enumerator kind equals the default integer kind, then fails silently
  on a processor or with `-fshort-enums`. Declare `integer(kind(some_enumerator))`.
* **Mixing the C `enum` size with Fortran.** C23 allows enums wider than `int`; the Fortran kind is the one that is interoperable with the
  matching C type, so a `bind(c)` interface must be checked against the C compiler's choice. Use `integer(c_int)` in the interface for
  plain C `enum` types, and `-fshort-enums` consistently.
* **Name clashes.** Enumerator names are ordinary names of the scoping unit: `use heatflow_boundary` without `only` brings `dirichlet`,
  `neumann` and `periodic` into the user's scope, where a local variable called `periodic` is an error. Use `only` or a prefix such as
  `bc_`; the scoped `type%enumerator` of Fortran 2028 will relieve this for enumeration types.
* **Integer arithmetic on enumerators.** `pass:c[colour + 1]` is legal for an interoperable enumeration (it is an integer) and illegal for an
  enumeration type; code that depends on it must be rewritten with `next` and `previous` or with ordinal positions.
* **Ordinal vs value.** For an enum type or an interoperable enumeration `int(a)` is the stored integer; for an enumeration type it is the
  ordinal position, counted from 1, so the first enumerator is 1, not 0.
* **Namelist, `common` and `equivalence`.** The enumeration type cannot be used in them (constraints C8109, C8110 and C8123); keep
  such variables outside, or use an integer or a character name in the file and convert.
* **Do not rely on compiler extensions.** Flang's `-fenumeration-type` is explicitly experimental, and the default flag set rejects the
  statement; a GNU Fortran build that does not support it fails with "Unclassifiable statement", which is a hint that the compiler
  predates the feature, not that your code is wrong.

See also xref:programming-languages/fortran/common-gotchas-and-pitfalls.adoc[Common Gotchas and Pitfalls].

== Where the books are outdated

The two Fortran books consulted for this section present the interoperable enumeration in their C-interoperability chapter and the
enumeration type in the chapter on the new features of Fortran 2023. Where they differ from current practice:

[cols="2,5",options="header"]
|===
|Area |Outdated or incorrect in the books, current approach

|Terminology |the "BIND(C) ENUM" of older text is called an *interoperable enumeration* in Fortran 2023, and it can now have a type name
(an enum type); material written for Fortran 2003 to 2018 shows neither the typed form nor the new word
|Compiler support |the enumeration type is presented as a language feature that can be used; in 2026 neither GNU Fortran 16.2 nor
LLVM Flang 23.1.4 can run a program that uses it (Flang can only check it, with an experimental option), so the portable code in this
guide uses `enum, bind(c)` or the derived-type emulation
|Syntax summary |the general form of the `enumeration type` statement in the book's feature chapter has unbalanced brackets and
leaves `type` out of the `end` statement (an erratum on the page that also contains a correct example); the correct closing statement
is `end enumeration type [name]` (R769)
|Kind of enumerators |older text says an enum is "just an `int`"; the standard says the kind is the one interoperable with the matching C
`enum`, which may be chosen smaller (`-fshort-enums`) or, with C23, larger than `int`
|===
