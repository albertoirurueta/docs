== Which tool for which symptom

Fortran gives no exception, no stack trace by default and no unit test framework in the language. The tools are a
compiler flag, a library or an external program, and each one finds a different kind of fault. Choose by symptom.

[mermaid]
....
flowchart TD
    A["The program is wrong or slow"] --> B{"What do you see?"}
    B -- "wrong numbers" --> C["Unit tests with test-drive or pFUnit, then gdb, then -fcheck=all"]
    B -- "crash or garbage" --> D["-fcheck=all, then AddressSanitizer or Valgrind"]
    B -- "NaN or Infinity appears" --> E["-ffpe-trap and signalling NaN, then gdb"]
    B -- "depends on uninitialised data" --> F["-finit-real=snan, Valgrind --track-origins"]
    B -- "too slow" --> G["gprof or perf, then -fopt-info and the performance page"]
    B -- "unsure what the tests cover" --> H["gcov coverage"]
....

[cols="3,3,3,3",options="header"]
|===
|Need |gfortran 16.2 |LLVM Flang 23 |Intel `ifx` (not run)
|Unit tests |test-drive, pFUnit, Vegetables (compiler independent) |test-drive passes through `fpm test --compiler flang-23` |the frameworks are compiler independent
|Runtime checks |`-fcheck=all` |no `-fcheck` option (rejected by the driver) |`-check all`

|Optimization reports |`-fopt-info` |`-Rpass`, `-Rpass-missed`, `-Rpass-analysis` |`-qopt-report`

The Flang column is the result of trying each option with `flang-23` in the container: a rejected option prints
`+error: unknown argument+` (for example `+flang-23: error: unknown argument: '-fcheck=bounds'+`) and the compiler stops. The
`ifx` column only names options from Intel's documentation, which was not run here (see the references).

== Unit testing

A unit test calls one procedure with known inputs and compares the result with an answer worked out by hand. The test
passes or fails without anybody reading numbers, so it can run on every commit. For numerical code the comparison is
never `==` on reals: use a tolerance, absolute for values near zero and relative for large values, and choose it from the
algorithm's expected accuracy rather than from machine epsilon.

Fortran has several community frameworks. None is part of the standard or of any compiler.

[cols="2,3,4",options="header"]
|===
|Framework |Style |Notes
|https://github.com/fortran-lang/test-drive[test-drive] |plain Fortran, no preprocessor; a test is a subroutine with an allocatable `error_type` argument |a small library maintained under the fortran-lang GitHub organisation (`fpm new` does not use it: its generated `test/check.f90` is a placeholder that prints a message); builds with fpm, CMake and Meson (run here: 0.6.1)
|https://github.com/Goddard-Fortran-Ecosystem/pFUnit[pFUnit] |tests are written in `.pf` files with `@test` and `@assertEqual` annotations that a Python preprocessor turns into Fortran |supports MPI and OpenMP tests; richer assertions and fixtures; needs CMake and the preprocessor (run here: 4.20.1)
|https://gitlab.com/everythingfunctional/vegetables[Vegetables] |Fortran sources processed by a generator; described in its repository; not checked here |community project hosted on GitLab; not built or run for this page
|===

=== test-drive with fpm

fpm treats everything in `test/` as tests. A test is an ordinary program, so a test-drive suite is a main program that
collects *test suites* (one module per unit under test) and runs them. The dependency is declared once:

[source,toml]
----
[dev-dependencies]
test-drive = { git = "https://github.com/fortran-lang/test-drive", tag = "v0.6.1" }
----

and the project layout is

[source,text]
----
heatflow/
  fpm.toml
  src/                    the library (heatflow_*.f90)
  app/main.f90
  test/
    check.f90             the test runner (program)
    test_grid.f90         suite 1: module test_grid, collect_grid
    test_kernels.f90      suite 2: module test_kernels, collect_kernels
----

Source: https://fpm.fortran-lang.org/spec/manifest.html[fpm manifest reference]

A suite is a module with a `collect` subroutine that returns an array of `unittest_type` values made by
`new_unittest(name, procedure)`. Each test procedure has one dummy argument, `type(error_type), allocatable,
intent(out) :{empty}: error`; the test passes when `error` is left unallocated and fails when a check allocates it. The checks
are the generic `check` and the procedure `test_failed`; the check must be followed by `if (allocated(error)) return`
because the first failed check ends the test. This is the second suite of heatflow:

[source,fortran]
----
module test_kernels
  use testdrive, only: new_unittest, unittest_type, error_type, check, skip_test, test_failed
  use heatflow_kinds, only: dp
  use heatflow_kernels, only: jacobi_sweep, ftcs_sweep
  implicit none
  private
  public :: collect_kernels

contains

  subroutine collect_kernels(testsuite)
    type(unittest_type), allocatable, intent(out) :: testsuite(:)
    testsuite = [ &
                new_unittest('jacobi-fixed-point', test_jacobi_fixed_point), &
                new_unittest('ftcs-linear-profile', test_ftcs_linear), &
                new_unittest('ftcs-bad-expectation', test_bad_expectation, should_fail=.true.), &
                new_unittest('gpu-only', test_skipped)]
  end subroutine collect_kernels

  !> A constant field is a fixed point of the Jacobi sweep: no change, zero residual.
  subroutine test_jacobi_fixed_point(error)
    type(error_type), allocatable, intent(out) :: error
    real(dp) :: u(6, 6), unew(6, 6), res
    u = 3.0_dp
    unew = u
    call jacobi_sweep(u, unew, res)
    call check(error, res, 0.0_dp, thr=1.0e-14_dp)
    if (allocated(error)) return
    call check(error, all(unew == 3.0_dp), message='interior changed')
  end subroutine test_jacobi_fixed_point

  !> A linear temperature profile has zero second derivative, so FTCS leaves it unchanged.
  subroutine test_ftcs_linear(error)
    type(error_type), allocatable, intent(out) :: error
    real(dp) :: u(7, 7), unew(7, 7), res
    integer :: i
    do i = 1, 7
      u(i, :) = real(i, dp)
    end do
    unew = u
    call ftcs_sweep(u, unew, 1.0_dp, 1.0e-3_dp, 0.1_dp, 0.1_dp, res)
    call check(error, res, 0.0_dp, thr=1.0e-10_dp)
  end subroutine test_ftcs_linear

  !> Declared should_fail: the test passes when this check fails.
  subroutine test_bad_expectation(error)
    type(error_type), allocatable, intent(out) :: error
    call check(error, 1 + 1, 3)
  end subroutine test_bad_expectation

  subroutine test_skipped(error)
    type(error_type), allocatable, intent(out) :: error
    call skip_test(error, 'needs a GPU')
  end subroutine test_skipped
end module test_kernels
----

Source: https://github.com/fortran-lang/test-drive[test-drive README and testdrive module]

`new_unittest` takes an optional `should_fail=.true.`, used above for a test that passes only if its check fails (it is
how a test of the test framework itself, or of an error path, is written), and `skip_test` marks a test as skipped with
a message. The runner is a program that lists the suites, runs them all, and turns the number of failures into a nonzero
exit status; the version below also reads the first two command-line arguments to select one suite and one test:

[source,fortran]
----
program check
  use, intrinsic :: iso_fortran_env, only: error_unit
  use testdrive, only: run_testsuite, run_selected, new_testsuite, testsuite_type, &
                       select_suite, get_argument
  use test_grid, only: collect_grid
  use test_kernels, only: collect_kernels
  implicit none
  integer :: stat, is
  character(len=:), allocatable :: suite_name, test_name
  type(testsuite_type), allocatable :: testsuites(:)
  character(len=*), parameter :: fmt = '("#", *(1x, a))'

  stat = 0
  testsuites = [new_testsuite('grid', collect_grid), new_testsuite('kernels', collect_kernels)]

  call get_argument(1, suite_name)
  call get_argument(2, test_name)

  if (allocated(suite_name)) then
    is = select_suite(testsuites, suite_name)
    if (is < 1 .or. is > size(testsuites)) then
      write (error_unit, fmt) 'Available testsuites'
      do is = 1, size(testsuites)
        write (error_unit, fmt) '-', testsuites(is)%name
      end do
      error stop 1
    end if
    write (error_unit, fmt) 'Testing:', testsuites(is)%name
    if (allocated(test_name)) then
      call run_selected(testsuites(is)%collect, test_name, error_unit, stat)
      if (stat < 0) error stop 1
    else
      call run_testsuite(testsuites(is)%collect, error_unit, stat)
    end if
  else
    do is = 1, size(testsuites)
      write (error_unit, fmt) 'Testing:', testsuites(is)%name
      call run_testsuite(testsuites(is)%collect, error_unit, stat)
    end do
  end if

  if (stat > 0) then
    write (error_unit, '(i0, 1x, a)') stat, 'test(s) failed!'
    error stop 1
  end if
end program check
----

When a check fails, the message names the two values, and the run ends with a nonzero status that fpm reports. Changing
the expected cell spacing in `test_grid.f90` from `0.1_dp` to `0.2_dp` gives:

[source,text]
----
# Testing: grid
  Starting spacing ... (1/2)
       ... spacing [FAILED]
  Message: Floating point value mismatch
           expected 0.20000000000000001 but got 0.10000000000000001 (difference: 0.10000000000000001)
  Starting dirichlet ... (2/2)
       ... dirichlet [PASSED]
# Testing: kernels
...
1 test(s) failed!
<ERROR> Execution for object " check " returned exit code  1
<ERROR> *cmd_run*:stopping due to failed executions
STOP 1
----

The `fpm test` exit status was 1. (The `ERROR STOP 1` backtrace that gfortran prints before the suite output is
omitted, and the middle of the listing is shortened where it says `+...+`.)

The checks that `check` offers (from the test-drive README and the `check` generic interface in the source) are these.
Two overloads of `real` comparison exist, with `thr=` for an absolute tolerance and `rel=.true.` for a relative one.

[cols="2,3",options="header"]
|===
|Call |Meaning
|`check(error, logical_expr)` |true means pass
|`check(error, stat)` with an `integer` status |zero means pass; use it for `iostat`, `stat=` and similar
|`check(error, a, b)` for integers, logicals, character strings |equal means pass
|`check(error, a, b, thr=t)` for `real` and `complex` kinds `sp` and `dp` |`+abs(a - b) <= t+`; the default threshold is machine epsilon; `rel=.true.` makes it relative
|`check(error, x)` for a `real` or `complex` |fails with "Exceptional value 'not a number' found" when `x` is a NaN (every real comparison also starts with this NaN test on `actual`)
|`+check(error, ..., message='text', more='detail')+` |`message` replaces the generated message and `more` adds a second line
|`test_failed(error, message)` |allocates `error` directly, for hand-written checks
|===

The runner above does not use the extra features, but the library also writes JUnit XML (`junit_output`) and coloured
output (`init_color_output`), which its own tester uses and which continuous integration services read.

fpm builds every test with the flags of the selected profile, so a test run with `fpm test --profile debug` includes
`-fcheck=bounds` (see the runtime checks section) and is the cheapest extra safety net;
`fpm test --flag "-fcheck=all -g -fbacktrace"` adds all the checks to whatever fpm would use. With Flang the same suite
passes unchanged (`fpm test --compiler flang-23`): test-drive is standard Fortran. The output was identical to the
gfortran listing.

=== test-drive with CTest

Projects that build with CMake register each suite as a CTest test. test-drive publishes a CMake package, so
`FetchContent` can download it. Two details matter: the exported target is called `test-drive` (in version 0.6.1 the
`ALIAS` in its `CMakeLists.txt` is written `test-drive:test-drive` with a single colon, so linking to the namespaced
name `test-drive::test-drive` fails with "target was not found"), and test-drive adds its own self-tests to your CTest
list unless `TESTDRIVE_BUILD_TESTING` is switched off. This addition to heatflow's `CMakeLists.txt` runs one CTest test
per suite, using the command-line selection built into the runner:

[source,cmake]
----
include(CTest)
if(BUILD_TESTING)
  include(FetchContent)
  FetchContent_Declare(test-drive
    GIT_REPOSITORY https://github.com/fortran-lang/test-drive
    GIT_TAG v0.6.1)
  # keep test-drive's own self-tests out of our ctest run
  set(TESTDRIVE_BUILD_TESTING OFF CACHE BOOL "" FORCE)
  FetchContent_MakeAvailable(test-drive)

  add_executable(heatflow-tests test/check.f90 test/test_grid.f90 test/test_kernels.f90)
  target_link_libraries(heatflow-tests PRIVATE heatflow test-drive)

  add_test(NAME grid COMMAND heatflow-tests grid)
  add_test(NAME kernels COMMAND heatflow-tests kernels)
endif()
----

[source,bash]
----
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Debug
cmake --build build
cd build && ctest --output-on-failure
----

[source,text]
----
Test project /tmp/cb
    Start 1: grid
1/2 Test #1: grid .............................   Passed    0.00 sec
    Start 2: kernels
2/2 Test #2: kernels ..........................   Passed    0.00 sec

100% tests passed, 0 tests failed out of 2

Total Test time (real) =   0.00 sec
----

`ctest -R kernels -V` shows the suite output, `ctest --rerun-failed --output-on-failure` repeats only the failures,
`ctest -j4` runs tests in parallel, and `ctest --output-junit results.xml` writes a JUnit report (all four options
exist in CMake 3.31; the JUnit file was written and read here). CTest decides pass or fail from the exit status, so the
runner's `error stop 1` on failure is essential: a runner that only printed failures would be reported as passing.

Source: https://cmake.org/cmake/help/v3.31/manual/ctest.1.html[CTest manual (CMake 3.31)].

=== pFUnit

pFUnit is built from source with CMake (no package manager is used here) and then found with `find_package(PFUNIT)`.
The release built for this page was the `v4.20.1` tag; the build took one `cmake --build` and the install tree contained
`PFUNIT-4.20`, `GFTL-1.17`, `GFTL_SHARED-1.12` and `FARGPARSE-1.12`:

[source,bash]
----
git clone --depth 1 https://github.com/Goddard-Fortran-Ecosystem/pFUnit.git
cmake -S pFUnit -B pfunit-build -G Ninja -DCMAKE_INSTALL_PREFIX="$HOME/pfunit" -DSKIP_MPI=YES -DSKIP_OPENMP=YES
cmake --build pfunit-build
cmake --install pfunit-build
----

A pFUnit test is a `.pf` file. Lines that begin with `@` are directives for the preprocessor, which generates a driver
program and a Fortran module; the rest is ordinary Fortran. The assertion `@assertEqual(expected, actual, tolerance=t)`
works for scalars and arrays of the supported kinds, and `@test(ifdef=NAME)` compiles a test only when the macro is
defined (used below to switch a deliberately failing test on):

[source,fortran]
----
module test_kernels
  use funit
  use heatflow_kinds, only: dp
  use heatflow_kernels, only: jacobi_sweep
  implicit none

contains

  @test
  subroutine jacobi_fixed_point()
    real(dp) :: u(6, 6), unew(6, 6), res
    u = 3.0_dp
    unew = u
    call jacobi_sweep(u, unew, res)
    @assertEqual(0.0_dp, res, tolerance=1.0e-14_dp)
    @assertEqual(3.0_dp, unew, tolerance=1.0e-14_dp)
  end subroutine jacobi_fixed_point

  @test(ifdef=HEATFLOW_FAIL_DEMO)
  subroutine deliberately_wrong()
    @assertEqual(3, 1 + 1)
  end subroutine deliberately_wrong

  @test
  subroutine jacobi_averages_neighbours()
    real(dp) :: u(3, 3), unew(3, 3), res
    u = 0.0_dp
    u(1, 2) = 4.0_dp
    unew = u
    call jacobi_sweep(u, unew, res)
    @assertEqual(1.0_dp, unew(2, 2), tolerance=1.0e-14_dp)
    @assertEqual(1.0_dp, res, tolerance=1.0e-14_dp)
  end subroutine jacobi_averages_neighbours

end module test_kernels
----

Source: https://github.com/Goddard-Fortran-Ecosystem/pFUnit[pFUnit repository and documentation]

=== Vegetables and others

Vegetables is a third community framework. It was not built or run for this page, so nothing is claimed here about its
syntax or commands; see its repository for the current instructions. Whichever framework you choose, the project structure is the same: the library in `src/`, the tests
in `test/` calling only the public module interface, and an exit status that CI can read.

=== What to test

For a numerical code the useful tests are those that need no reference output: *invariants* (a constant field is a fixed
point of the Jacobi sweep; a linear profile has zero second difference, so the FTCS update leaves it alone: these are the
two tests above), *conservation* and *symmetry* properties, *convergence order* (halve the grid spacing and check that
the error falls by the expected factor), *known analytic solutions* (a single Fourier mode of the heat equation decays
as an exponential), *boundary and degenerate cases* (the smallest grid the code accepts, `nx = 3`), and *error paths*
(`should_fail`, or a status argument that must be nonzero; see
xref:programming-languages/fortran/error-handling-and-program-termination.adoc[Error Handling and Program Termination]).
Keep tests small and deterministic: seed random numbers, never depend on file paths or the clock, and make each test
independent of the order of the others.

== Let the compiler find it first

The cheapest debugging happens before the program runs. gfortran reports many faults at compile time when the
information is available: with constant bounds, an index outside an array is a warning (`Warning: Array reference at (1)
out of bounds (6 > 5) in loop beginning at (2)`), a loop variable passed to an `intent(inout)` argument inside its own
loop is an error (`Variable 'i' at (1) not definable inside loop beginning at (2) as INTENT(INOUT) argument to subroutine
'bump'`), an array assignment between constant shapes that differ is an error (`Different shape for array assignment at
(1) on dimension 1 (3 and 4)`), and a recursive call of a procedure that is not `recursive` is an error (`Function
'countdown' at (1) cannot be called recursively, as it is not RECURSIVE`). Those four messages were produced by an
earlier, constant-size version of the program in the next section; the version printed below uses run-time sizes
precisely so that the compiler cannot see the fault.

The warning options worth turning on in development, each accepted by gfortran 16.2:

[cols="2,5",options="header"]
|===
|Option |What it adds
|`-Wall -Wextra` |the baseline: unused variables, unused dummy arguments, possibly uninitialised variables (with optimization), truncated constants, and more
|`-std=f2023 -pedantic` |rejects or warns about every extension; without it `+real*8+` and similar spellings are accepted silently
|`-fimplicit-none` |makes `implicit none` the default for every scope, which also catches misspelled names in old code
|`-Wuninitialized` |warns about variables read before assignment; it needs an optimization level (`-O1` or higher) to see through the control flow, and it is silenced for variables covered by any `+-finit-*+` option
|`-Wconversion` |implicit conversions that can change a value (for example `real(dp)` assigned to `real(sp)`)
|`-Wimplicit-interface` |calls to external procedures without an interface block or module, where the compiler cannot check arguments
|`-Warray-temporaries` |compile-time notice when an array temporary will be created for an argument
|`-Wrealloc-lhs`, `-Wrealloc-lhs-all` |assignments that may reallocate the left-hand side
|`-Waliasing` |actual arguments that alias (the standard forbids this when one is modified)
|`-fmax-errors=1` |stop at the first error to avoid cascades
|===

LLVM Flang 23 reports semantic and conformance errors it finds and accepts `-Wall`, `-Wextra` and `-pedantic`, but it
does not accept `-std=f2023` (`error: Only -std=f2018 is allowed currently.`; `-std=f2018` is accepted) and its warning
set is smaller than gfortran's. A build that must be portable should therefore also be compiled with gfortran under
the flags above in continuous integration. The full list of gfortran warnings is in its manual (Error and Warning Options).

== Runtime checks

When the compiler cannot decide, it can insert tests that run with the program. They cost time (often a factor of two
or more), so they belong in debug builds and in tests, not in production runs.

=== gfortran: -fcheck

`-fcheck=` takes a comma-separated list of keywords; a keyword prefixed with `no-` turns one off, so
`-fcheck=all,no-array-temps` is everything except the temporary-array warning. The keywords, from the manual, with a
description of what each tested here reports:

[cols="2,6",options="header"]
|===
|Keyword |Checks
|`all` |every check below
|`bounds` |array subscripts against the declared bounds; for assumed-shape and deferred-shape arrays, against the actual bounds; array-shape conformance in assignments; substring ranges; the manual notes that some checks require the option when compiling the main program
|`array-temps` |a run-time warning, once per location, when a temporary array had to be created for an actual argument (it points at copies that hurt performance)
|`bits` |invalid arguments to bit intrinsics such as a shift larger than the bit size
|`do` |modification of a `do` loop variable (`pass:c[k = k + 1]` hidden behind a call)
|`mem` |memory allocation; explicit `allocate` is always checked anyway
|`pointer` |pointers and allocatables: a disassociated pointer passed where a value is required, and so on
|`recursion` |a recursive call of a subroutine or function that is not marked `recursive`
|===

`-fcheck=none` is not accepted (gfortran says `+Argument to '-fcheck' is not valid: none+`); omit the option to switch the
checks off. `-fbounds-check` is a deprecated alias for `-fcheck=bounds`. The program below has one deliberate fault per
keyword; the case number is the first command-line argument. The sizes are decided at run time so the compiler cannot
reject the code up front.

[source,fortran]
----
! One failing case per -fcheck= option; the case number is the first command-line argument.
module checks_cases
  use, intrinsic :: iso_fortran_env, only: real64
  implicit none
  private
  public :: run_case
  integer, parameter :: dp = real64

  abstract interface
    subroutine walk_i(k)
      integer, intent(in) :: k
    end subroutine walk_i
  end interface

  procedure(walk_i), pointer :: hook => null()

contains

  subroutine run_case(n)
    integer, intent(in) :: n
    select case (n)
    case (1); call case_bounds()
    case (2); call case_shape_mismatch()
    case (3); call case_substring()
    case (4); call case_pointer()
    case (5); call case_do()
    case (6); call case_recursion()
    case (7); call case_array_temp()
    case (8); call case_bits()
    case default; print '(a)', 'no such case'
    end select
  end subroutine run_case

  subroutine case_bounds()
    real(dp), allocatable :: row(:)
    integer :: i
    allocate (row(5))
    do i = 1, 6
      row(i) = real(i, dp)
    end do
    print *, row(1)
  end subroutine case_bounds

  subroutine case_shape_mismatch()
    real(dp), allocatable :: a(:), b(:)
    allocate (a(3), b(4))
    b = 1.0_dp
    a(:) = b
    print *, a(1)
  end subroutine case_shape_mismatch

  subroutine case_substring()
    character(len=8) :: name
    integer :: k
    name = 'heatflow'
    k = 9
    print *, name(k:k)
  end subroutine case_substring

  subroutine case_pointer()
    real(dp), pointer :: p
    nullify (p)
    call show(p)
  end subroutine case_pointer

  subroutine show(x)
    real(dp), intent(in) :: x
    print *, x
  end subroutine show

  subroutine case_do()
    integer, target :: i
    integer, pointer :: alias
    alias => i
    do i = 1, 3
      call bump(alias)
    end do
  end subroutine case_do

  subroutine bump(k)
    integer, intent(inout) :: k
    k = k + 1
  end subroutine bump

  subroutine case_recursion()
    hook => walk
    call hook(2)
  end subroutine case_recursion

  subroutine walk(k)
    integer, intent(in) :: k
    if (k > 0) call hook(k - 1)
  end subroutine walk

  subroutine case_array_temp()
    real(dp) :: m(4, 4)
    m = 1.0_dp
    call total(m(2, :))
  end subroutine case_array_temp

  subroutine total(x)
    real(dp), intent(in) :: x(4)
    print *, sum(x)
  end subroutine total

  subroutine case_bits()
    integer :: i, s
    i = 1
    s = 40
    print *, shiftl(i, s)
  end subroutine case_bits
end module checks_cases

program checks_demo
  use checks_cases, only: run_case
  implicit none
  character(len=8) :: arg
  integer :: n
  call get_command_argument(1, arg)
  read (arg, *) n
  call run_case(n)
end program checks_demo
----

=== Other compilers

LLVM Flang 23 has no `-fcheck` option: `flang-23 -fcheck=bounds` stops with `+error: unknown argument: '-fcheck=bounds'+`.
It does check some things on its own. The same eight cases built with `flang-23 -g` gave: case 2 aborts with
`+fatal Fortran runtime error(...): Assign: mismatching element counts in array assignment (to 3, from 4)+` (exit status
134), case 4 is a segmentation fault (exit 139), and cases 1, 3, 5, 6, 7 and 8 run to the end without any message.
So a Flang build is not a debugging substitute for a gfortran `-fcheck=all` build; test with both.

Intel `ifx` has the `-check` option with an `all` keyword (see the `-check` page of Intel's reference); it was not run for
this page, and its keyword set differs from gfortran's. Check the vendor documentation for the release you use.

== Debugging with gdb

gdb understands Fortran: it prints arrays with the Fortran subscript order, derived types with their components, shows
allocatable arrays by their current bounds, and accepts Fortran expressions (array sections, `size(u, 1)`, `%` for
components). Build with `-g` and without optimization (`-O0`; at `-O2` variables disappear into registers and lines
reorder). The demo is a short program that builds a 5 by 4 grid, sets a hot spot and calls one Jacobi sweep:

[source,fortran]
----
program gdb_demo
  use heatflow_kinds, only: dp
  use heatflow_grid, only: grid_t, make_grid
  use heatflow_boundary, only: dirichlet
  use heatflow_kernels, only: jacobi_sweep
  implicit none
  type(grid_t) :: g
  real(dp), allocatable :: unew(:, :)
  real(dp) :: residual

  g = make_grid(5, 4, 1.0_dp, 1.0_dp)
  call g%apply_boundary(dirichlet, 0.0_dp)
  call g%set_hot_spot(100.0_dp)
  unew = g%u
  call jacobi_sweep(g%u, unew, residual)
  print '(a,f8.3)', 'residual = ', residual
end program gdb_demo

== Uninitialised data and signalling NaNs

Reading a variable before it is assigned is undefined behaviour that usually does not crash: the garbage often looks
like a plausible number, and the program gives the right answer on one machine and the wrong one on another. Fortran
has no automatic initialisation of local variables, and `allocate` does not zero memory. Two techniques make the
fault loud:

* initialise every real to a *signalling NaN* and enable the invalid-operation trap, so the first use stops the
  program at the faulting line;
* use a tool that tracks definedness (Valgrind with `--track-origins=yes`, next sections).

gfortran provides the first technique with `-finit-real=snan -ffpe-trap=invalid`. The family of options (from the
manual) is `-finit-local-zero`, `-finit-derived`, `-finit-integer=n`, `-finit-real=<zero|inf|-inf|nan|snan>`,
`-finit-logical=<true|false>` and `-finit-character=n`. They do *not* initialise objects with the `pointer` attribute,
allocatable arrays or variables in an `equivalence`; and they silence `-Wuninitialized` for the variables they cover.
The manual also warns that compile-time optimization may turn a signalling NaN into a quiet one, so use these options
in `-O0` builds.

For the objects the options do not cover, make the signalling NaN yourself with `ieee_value` from
`ieee_arithmetic` (`ieee_signaling_nan` is a standard `ieee_class_type` value, see
xref:programming-languages/fortran/floating-point-and-ieee-arithmetic.adoc[Floating-Point and IEEE Arithmetic]). The
test program uses both:

[source,fortran]
----
! A work array whose halo is never initialised, caught with signalling NaNs.
program snan_demo
  use, intrinsic :: iso_fortran_env, only: real64
  use, intrinsic :: ieee_arithmetic, only: ieee_value, ieee_signaling_nan
  implicit none
  integer, parameter :: dp = real64
  real(dp) :: local(4)
  real(dp), allocatable :: work(:)
  real(dp) :: poison, total
  integer :: i, mode
  character(len=8) :: arg

  call get_command_argument(1, arg)
  read (arg, *) mode

  select case (mode)
  case (1)
    ! uninitialised local: -finit-real=snan fills it
    local(1:3) = 1.0_dp
    total = sum(local)
    print '(a,f8.3)', 'total = ', total
  case (2)
    ! allocatable: -finit-real does NOT touch it, so poison it by hand
    allocate (work(0:5))
    poison = ieee_value(poison, ieee_signaling_nan)
    work = poison
    work(1:4) = 1.0_dp
    total = 0.0_dp
    do i = 0, 5
      total = total + work(i)
    end do
    print '(a,f8.3)', 'total = ', total
  end select
end program snan_demo
----

Built plainly, case 1 prints `total =    3.000` (the fourth, unset element happened to be zero on this run) and case 2 prints
`total =      NaN` (the NaN poison propagates by itself without any trap). Built with `-finit-real=snan

== Sanitizers

`-fcheck` only knows about the arrays the compiler can see. Once an array is passed to an explicit-shape dummy, to
C, or through a pointer, its extent is gone and `-fcheck` is silent. The *sanitizers* instrument every memory access of
the compiled code and keep a shadow map of valid memory. gfortran supports the GCC sanitizers
(`-fsanitize=address`, `undefined`, `leak`, `thread`, among others, from GCC's instrumentation options); combine them
with `-g` and `-fno-omit-frame-pointer` for readable stacks. This program holds the faults that `-fcheck` misses:

[source,fortran]
----
! Memory bugs that -fcheck=all does not see once the compiler has lost the array bounds.
module memory_bugs
  use, intrinsic :: iso_fortran_env, only: real64, int32
  implicit none
  private
  public :: run_case
  integer, parameter :: dp = real64

contains

  subroutine run_case(n)
    integer, intent(in) :: n
    select case (n)
    case (1); call heap_overflow()
    case (2); call use_after_free()
    case (3); call leak()
    case (4); call int_overflow()
    case (5); call uninitialized()
    case default; print '(a)', 'no such case'
    end select
  end subroutine run_case

  !> Writes past the end of a heap array through an explicit-shape dummy.
  subroutine heap_overflow()
    real(dp), allocatable :: u(:)
    allocate (u(10))
    u = 0.0_dp
    call fill(u, 11)
    print *, u(1)
  end subroutine heap_overflow

  subroutine fill(x, n)
    integer, intent(in) :: n
    real(dp), intent(inout) :: x(n)
    x(n) = 1.0_dp
  end subroutine fill

  !> Reads through a pointer after the target was deallocated.
  subroutine use_after_free()
    real(dp), pointer :: p(:), q(:)
    real(dp) :: v
    allocate (p(10))
    p = 2.0_dp
    q => p
    deallocate (p)
    v = q(3)
    print *, v
  end subroutine use_after_free

  !> The pointer goes out of scope without a deallocate.
  subroutine leak()
    real(dp), pointer :: work(:)
    allocate (work(1000))
    work = 1.0_dp
    print *, sum(work)
  end subroutine leak

  subroutine int_overflow()
    integer(int32) :: k
    integer :: i
    k = huge(k) - 2_int32
    do i = 1, 5
      k = k + 1_int32
    end do
    print *, k
  end subroutine int_overflow

  !> A local that is read before it is ever assigned.
  subroutine uninitialized()
    real(dp) :: total, x(4)
    integer :: i
    x = [1.0_dp, 2.0_dp, 3.0_dp, 4.0_dp]
    do i = 1, 4
      total = total + x(i)
    end do
    if (total > 5.0_dp) print *, 'big'
  end subroutine uninitialized
end module memory_bugs

program memory_bugs_demo
  use memory_bugs, only: run_case
  implicit none
  character(len=8) :: arg
  integer :: n
  call get_command_argument(1, arg)
  read (arg, *) n
  call run_case(n)
end program memory_bugs_demo
----

Notes:

* *Library calls are not instrumented.* In an earlier version of the program the read in case 2 was written
  `+print *, q(3)+`; AddressSanitizer did not report it, because the element is read inside the (uninstrumented) Fortran
  runtime library, not by compiled code. Copy the value to a local first (`v = q(3)`), as the listing does, when you test
  this kind of fault.
* *Leaks in the main program.* Run through fpm (`fpm test --flag "-g -O0 -fsanitize=address,undefined
  -fno-omit-frame-pointer" --link-flag "-fsanitize=address,undefined"`), the test suite of this page passed all its tests and
  then LeakSanitizer ended the run with exit status 1 and `SUMMARY: AddressSanitizer: 59 byte(s) leaked in 3
  allocation(s)`, allocated at `test/check.f90:14`, the `+testsuites = [...]+` assignment in the runner. A variable
  declared in a main program has the `save` attribute (J3/23-007r1 8.5.16), so gfortran does not deallocate it at
  `end program`. Adding `deallocate (testsuites)` before the final check removed the report. Such leaks are harmless,
  but they make a leak-checked CI job fail; free the data or move it into a procedure.
* *Compile every file with the flag and link with it.* A sanitizer-compiled object mixed with plain ones sees only
  part of the program. (The fpm command is above.)
* *Do not combine `-fsanitize=address` with `-fsanitize=thread`*, and expect runs several times slower and memory use
  two to three times larger.
* *Flang.* `flang-23 -fsanitize=address` stops with `+error: unknown argument: '-fsanitize=address'+`; so do `undefined` and
  `thread`. Flang-built binaries can still be run under Valgrind (below) and perf.

Source: https://gcc.gnu.org/onlinedocs/gcc/Instrumentation-Options.html[GCC manual: Program instrumentation options (-fsanitize)] and
https://github.com/google/sanitizers/wiki/AddressSanitizer[AddressSanitizer wiki].

== Valgrind

Valgrind runs an unmodified binary on a virtual CPU that checks every memory access and tracks which bits of every
value are defined. It needs no special compile flag except `-g` for line numbers, is slower (typically 10 to 50 times),
and finds what AddressSanitizer finds plus uninitialised uses. On the same program, built with plain `gfortran -g -O0`
and run as `valgrind --leak-check=full --track-origins=yes -q ./a.out N`:

[source,text]

==13==    by 0x4013F3: __memory_bugs_MOD_run_case (03_memory_bugs.f90:14)
==13==    by 0x401517: MAIN__ (03_memory_bugs.f90:87)
==13==    by 0x401557: main (03_memory_bugs.f90:81)

produces no report, because the processor does not treat it as a fault. Use `-q` to drop the banner, `--error-exitcode=1`
to turn errors into a failing exit status in CI, and `--suppressions=file` for known library noise. Valgrind works on
binaries from any compiler; on this aarch64 container it was run on gfortran-built executables only.

== Profiling

A profile answers "where does the time go?" Measure the optimized program, not the debug build: bounds checks and
`-O0` change the balance. Use realistic sizes, keep `-g` for line information (it does not slow the code), and run
long enough to collect samples. The demonstration program is a 500 by 500 FTCS run of 400 steps with a deliberately
badly ordered diagnostic added; `energy_by_rows` sums the grid with the first subscript in the outer loop, so it strides
through memory:

[source,fortran]
----
! A heatflow run with a deliberately slow diagnostic, used for profiling.
program profile_demo
  use heatflow_kinds, only: dp
  use heatflow_grid, only: grid_t, make_grid
  use heatflow_boundary, only: dirichlet
  use heatflow_solver, only: solver_t, make_solver
  implicit none
  type(grid_t) :: g
  class(solver_t), allocatable :: s
  real(dp) :: residual, total
  integer :: k

  g = make_grid(500, 500, 1.0_dp, 1.0_dp)
  call g%apply_boundary(dirichlet, 0.0_dp)
  call g%set_hot_spot(100.0_dp)
  s = make_solver('ftcs', g, dirichlet, 0.0_dp, 1.0_dp, 1.0e-6_dp)
  total = 0.0_dp
  do k = 1, 400
    call s%step(residual)
    total = total + energy_by_rows(s%grid%u)
  end do
  print '(a,es10.3,a,f12.3)', 'residual = ', residual, '  mean energy = ', total/400.0_dp

contains

  !> Sums u with the first index in the outer loop: strides through memory.
  function energy_by_rows(u) result(e)
    real(dp), intent(in) :: u(:, :)
    real(dp) :: e
    integer :: i, j
    e = 0.0_dp
    do i = 1, size(u, 1)
      do j = 1, size(u, 2)
        e = e + u(i, j)
      end do
    end do
  end function energy_by_rows
end program profile_demo
----

Source: https://sourceware.org/binutils/docs/gprof/[GNU gprof manual]

=== gprof

gprof is the classic instrumenting profiler: `-pg` makes the compiler insert a call counter at each procedure entry and a
sampling timer, and the program writes `gmon.out` into the current directory when it ends. Both compile and link need the
flag; `-fno-inline` keeps small procedures visible as separate entries.

[source,bash]
----
fpm run --example profile_demo --flag "-O2 -g -pg -fno-inline" --link-flag "-pg"
gprof -b -p build/gfortran_*/example/profile_demo gmon.out | head
----

[source,text]
----

 23.54      0.14     0.04      400     0.10     0.10  energy_by_rows.0
 17.66      0.17     0.03      400     0.08     0.33  __heatflow_solver_MOD_ftcs_step
  0.00      0.17     0.00      401     0.00     0.00  __heatflow_grid_MOD_grid_apply_boundary

(The glob in the second command assumes one fpm build directory; fpm names it with a hash.) The flat profile ranks
procedures by self time: the kernel is the biggest, but the diagnostic takes a quarter of the run. `-q` prints the

Module procedures appear with their mangled names (`+__module_MOD_name+`). Limits: gprof's sample interval is 10 ms, so
short runs are noisy (this one lasted 0.17 s; read the percentages as rough); inlined procedures do not appear
(hence `-fno-inline`, which changes the optimization); and multi-threaded programs are not profiled correctly. Flang
rejects `-pg`.

=== perf

`perf` samples the program from outside, using the hardware performance counters or a software timer, with no
instrumentation and no recompilation beyond `-g`. Frame pointers (`-fno-omit-frame-pointer`) make call graphs
(`perf record -g`) reliable. On a normal Linux host the commands would be:

[source,bash]
----
fpm run --example profile_demo --flag "-O2 -g -fno-omit-frame-pointer"
perf record -g build/gfortran_*/example/profile_demo
perf report --stdio --no-children
----

The container used for this page does not allow the default hardware cycles event (`No permission to enable cycles:Pu
event`), so the run used the software clock and extra capabilities (`docker run --cap-add SYS_ADMIN --cap-add PERFMON
--security-opt seccomp=unconfined`), with `perf record -e cpu-clock -F 999` (without `-g`, because call-graph unwinding printed `unwind: get_proc_name unsupported` in this container). The report listed the same two procedures:

[source,text]
----
    46.01%  profile_demo  profile_demo      [.] __heatflow_kernels_MOD_ftcs_sweep
    39.88%  profile_demo  profile_demo      [.] energy_by_rows.0
----

`perf stat` summarises a run (`166.17 msec cpu-clock`, `0.970 CPUs utilized` here); on hardware with counters,
`perf stat -e cycles,instructions,cache-misses` shows instructions per cycle and cache behaviour, which is what tells
the strided `energy_by_rows` from the contiguous kernel. perf was run on gfortran builds only; because it needs only
symbols, it works on Flang and `ifx` binaries too. The sampled shares differ from gprof's (46 and 40 against 59 and
24) because of the low sample count and because `-fno-inline` was used for gprof only: both numbers are samples, not
measurements. Fixing `energy_by_rows` (loop over `j` outside, `i` inside, or `sum(u)`) is covered in
xref:programming-languages/fortran/performance-and-memory-layout.adoc[Performance and Memory Layout].

=== Coverage with gcov

gcov reports which lines a test run executed, which answers the question "what do the tests not test?". Compile and link

=== Compiler optimization reports

An optimization report asks the compiler what it did to a loop. For performance work this is often faster than
profiling: it tells you directly that a loop was or was not vectorized, and why. gfortran uses `-fopt-info`, with
a pass filter (`vec`, `loop`, `inline`, or `all`), a verbosity (`optimized`, `missed`, `note`, or `all`) and an optional
output file (`-fopt-info-vec=vec.txt`). On the heatflow kernels at `-O3`:

[source,bash]
----
gfortran -O3 -fopt-info-vec-optimized -c heatflow_kernels.f90
----

[source,text]
----
heatflow_kernels.f90:34:12: optimized: loop vectorized using 16 byte vectors and unroll factor 2
heatflow_kernels.f90:34:12: optimized: loop vectorized using 16 byte vectors and unroll factor 2
heatflow_kernels.f90:18:12: optimized: loop vectorized using 16 byte vectors and unroll factor 2
----

and with `-fopt-info-vec-missed` the loops that were not:

[source,text]
----
heatflow_kernels.f90:33:10: missed: couldn't vectorize loop
heatflow_kernels.f90:37:72: missed: not vectorized: complicated access pattern.
heatflow_kernels.f90:33:10: missed: couldn't vectorize loop
heatflow_kernels.f90:37:72: missed: not vectorized: not suitable for strided load _22 = *_21;
heatflow_kernels.f90:17:10: missed: couldn't vectorize loop
heatflow_kernels.f90:19:84: missed: not vectorized: complicated access pattern.
----

Lines 17 and 33 are the outer `do j` loops, 18 and 34 the inner `do i` loops. gfortran vectorized the inner loops of
both sweeps (the report mentions lines 34 and 18, a loop appearing twice when the compiler made two versions of it) and
declined the outer loops, which is the usual and desirable outcome: one level of vectorization, along the contiguous
first subscript. The `missed` lines are the reasons for the outer loops. Adding the `contiguous` attribute to the two
assumed-shape dummies did not change which loops were vectorized in this experiment. See
xref:programming-languages/fortran/performance-and-memory-layout.adoc[Performance and Memory Layout] for what to do
when an inner loop is the one that is missed.

LLVM Flang uses the LLVM remark options `-Rpass=<regex>`, `-Rpass-missed=<regex>` and `-Rpass-analysis=<regex>` (the driver
lists all three). The same kernel file compiled with `flang-23 -O3 -Rpass-missed=loop-vectorize` printed

[source,text]
----
heatflow_kernels.f90:18:7: remark: loop not vectorized [-Rpass-missed=loop-vectorize]
heatflow_kernels.f90:34:7: remark: loop not vectorized [-Rpass-missed=loop-vectorize]
----

(each remark appears twice; paths were shortened) and `-Rpass-analysis=loop-vectorize` gives the reason: `loop not
vectorized: value that could not be identified as reduction is used outside the loop`. With `-Rpass=loop-vectorize`
nothing was printed, because no loop was vectorized. The remarks refer to the inner loops (lines 18 and 34), which
update `residual` with `max` and write `unew`, so on this kernel the two compilers differ at `-O3`: gfortran vectorized
the inner loops and Flang 23 did not. That is worth knowing before comparing their speeds.

Intel `ifx` writes a report with `-qopt-report` (see the `-qopt-report` page of Intel's reference); that option and its
levels were not run here.

== Where older books and tutorials are outdated

* *Test frameworks.* Older texts recommend FUnit (the Ruby-based predecessor of pFUnit) or hand-written `if
  (abs(x - y) > tol) stop` checks. The maintained frameworks today are pFUnit 4 (rewritten, CMake, preprocessor) and the
  fortran-lang test-drive; a build system test (`fpm test`, CTest) replaces the shell-script runners.
* *Runtime checks.* Old compilers called it `-C` or `-check bounds`; gfortran spells it `-fcheck=` with keyword
  lists, `-fbounds-check` is a deprecated alias, and the list has grown (`do`, `mem`, `pointer`, `recursion`,
  `bits`, `array-temps`).
* *Recursion.* Older books say a procedure must be declared `recursive` to call itself. Since Fortran 2018 a procedure is
  recursive by default (the `recursive` keyword is advisory) and `non_recursive` states the opposite (J3/23-007r1 15.6.2.1
  and Annex C.1). gfortran 16.2 still diagnoses recursion in a procedure that is not declared `recursive`, with an error
  at compile time or the `-fcheck=recursion` error at run time, so write `recursive` for portability across compilers.
* *Sanitizers.* The AddressSanitizer and UndefinedBehaviorSanitizer family was added to GCC after most Fortran books
  were written, and works with gfortran without Fortran-specific support, but only reports what is visible to
  compiled code (not library-internal reads and not uninitialised values).
* *Profiling.* gprof and `-pg` are all that older books mention; sampling profilers (perf, VTune) need no recompilation and
  work with optimized code, and optimization reports (`-fopt-info`, `-Rpass`, `-qopt-report`) are the modern first
  step for vectorization questions.
* *Debuggers.* Debugger-specific sections in old books describe vendor debuggers; gdb prints Fortran arrays, sections and
  derived types directly.

See also xref:programming-languages/fortran/documentation-and-editor-tooling.adoc[Documentation and Editor Tooling] for
the language server and formatter, and xref:programming-languages/fortran/best-practices-and-style.adoc[Best Practices and
Style] for how tests and checks fit into project practice.
