This page is written against Fortran 2023 (ISO/IEC 1539-1:2023, read here through the free final draft J3/23-007r1) and
looks ahead to Fortran 2028, read through the public working draft J3/26-007r1 of 3 March 2026. Everything that can be
compiled was checked on 2026-10-19 with GNU Fortran (gfortran) 16.2 and LLVM Flang 23 in a container (aarch64): the
programs of this page use `-std=f2023 -Wall -Wextra -pedantic -fimplicit-none -fcheck=all` for gfortran, and the output
shown is real output. Fortran 2028 is described only as "upcoming": its Committee Draft (WG5 N2258) is not a public
document, WG5 lists it on its documents page on 13 July 2026, and the outcome of the ballot is not shown there, so this page
says "committee draft stage" and nothing more precise. The working draft changes between meetings: the
copy read for this page still contains open "Unresolved Technical Issue" notes, so every syntax shown for Fortran 2028 is
the draft's, not a promise.

The page has five jobs. First, it gives a version-by-version summary and points to the history page for the detail. Second,
it lists *every* change that Fortran 2023 made (the Introduction of the standard has the complete list), says which page of
this section covers each one and which of the two installed compilers accepts it. Third, it states what is known about
Fortran 2028: its work items, what it makes obsolescent, and what the two compilers do with the draft syntax today. Fourth,
it collects in one table the places where the reference books are outdated, which the other pages of this section note one
topic at a time. Fifth, it records the errata of the main reference book, described in my own words. The running example is
the *heatflow* project introduced in xref:programming-languages/fortran/getting-started.adoc[Getting Started].

Related pages: xref:programming-languages/fortran/history-standards-and-compilers.adoc[History, Standards and Compilers] (the
history, the revision process and the per-compiler support table, which this page does not repeat in full),
xref:programming-languages/fortran/legacy-features-and-modernization.adoc[Legacy Features and Modernization] (the
deleted and obsolescent features in depth) and

Three observations follow from the table. The language features that touch only the parser (long lines, `reduce`, the
trigonometric intrinsics, `selected_logical_kind`, `split`) are already portable between the two free compilers. The
features that need runtime support or deep semantic work (deferred-length allocation by the processor, enumeration types,
integer arrays as subscripts and bounds, put with notify) are not implemented in either, and for those the portable code
uses the Fortran 2018 idiom. And the two compilers fail in different places, so a feature that one accepts is not a reason
to rely on it. The next section shows a program that uses only the features in the portable column.

=== A Fortran 2023 program that two compilers accept

The program below combines five of the Fortran 2023 additions that both compilers implement: trigonometry in degrees and in
half-revolutions, `selected_logical_kind`, the `split` subroutine, a conditional expression and the `reduce` locality
specifier of `do concurrent`. It is the practical answer to "what can I use today without checking?".

[source,fortran]
----
! A small program using only Fortran 2023 additions that gfortran 16.2 and Flang 23
! both accept and run: degree/half-revolution trigonometry, selected_logical_kind,
! split, a conditional expression, and a reduce locality specifier.
program portable_f2023
  use, intrinsic :: iso_fortran_env, only: real64
  implicit none
  integer, parameter :: dp = real64
  character(len=*), parameter :: spec = 'nx=64;ny=32'
  integer :: start, finish, count_items, i, total
  real(dp) :: a(4), mag
  logical(selected_logical_kind(8)) :: flag

  ! trigonometry in degrees and in half-revolutions
  print '(a,2f6.3)', 'sind/cospi:', sind(30.0_dp), cospi(1.0_dp / 3.0_dp)

  ! logical kind selected by size in bits
  flag = .true.
  print '(a,i0,l2)', 'logical kind and value:', kind(flag), flag

  ! split walks the tokens of a string one by one
  start = 1
  finish = 0
  count_items = 0
  do
    call split(spec, ';', finish)
    count_items = count_items + 1
    print '(a,a)', 'token: ', spec(start:finish - 1)
    start = finish + 1
    if (finish > len(spec)) exit
  end do
  print '(a,i0)', 'tokens: ', count_items

  ! conditional expression (scalar)
  a = [1.0_dp, -2.0_dp, 3.0_dp, -4.0_dp]
  mag = (a(2) < 0.0_dp ? -a(2) : a(2))
  print '(a,f5.1)', 'abs of a(2) via ?: ', mag

  ! reduce locality in do concurrent
  total = 0
  do concurrent (i = 1:10) reduce(+: total)
    total = total + i
  end do
  print '(a,i0)', 'sum 1..10 = ', total
end program portable_f2023
----

[source,text]
----
sind/cospi: 0.500 0.500
logical kind and value:1 T
token: nx=64
token: ny=32
tokens: 2
abs of a(2) via ?: 2.0
sum 1..10 = 55
----

The output is identical with gfortran 16.2 (`-std=f2023` with the warning flags above, no diagnostics) and Flang 23
(`flang-23` with default options). The value `1` printed for the logical kind is the kind number for an 8-bit logical, a
processor-dependent number; use the named constants of `iso_fortran_env` if you need to name the kind.

Source: https://j3-fortran.org/doc/year/23/23-007r1.pdf[J3/23-007r1 (Fortran 2023), 10.1.2.3, 11.1.7, 16.9.182, 16.9.191, 16.9.196]

=== A compiler crash to know about: a conditional expression as an output item

One combination is not safe in gfortran 16.2: a conditional expression used directly as an item of an output list. The
program is valid Fortran 2023 and Flang runs it; gfortran 16.2 stops with an internal compiler error (ICE), with or
without `-fcheck=all`:

[source,fortran]
----
program ice_probe
  implicit none
  real :: a
  a = -2.0
  print '(f5.1)', (a < 0.0 ? -a : a)
end program ice_probe
----

[source,text]
----
ice_probe.f90:5:36:

    5 |   print '(f5.1)', (a < 0.0 ? -a : a)
      |                                    ^
internal compiler error: in fold_convert_loc, at fold-const.cc:2672
----

Source: https://j3-fortran.org/doc/year/23/23-007r1.pdf[J3/23-007r1 (Fortran 2023), 10.1.2.3]

Flang 23 prints `2.0` for the same file. The workaround, used in the program above, is to assign the conditional
expression to a variable and print the variable. Assignment, as in the *heatflow* time-step function on the history page,
works with both compilers.

== Compatibility with Fortran 2018

Section 4.3.3 of the standard lists the few cases where a conforming Fortran 2018 program can change meaning or stop being
conforming under Fortran 2023: the integer arguments of one `system_clock` reference must now have the same kind; a `block`
variable declared only by a `data` statement cannot be used before the statement; the `pointer` and `target` arguments of
`associated` cannot have different ranks; deferred-length allocatable character variables assigned by `iomsg=`, `errmsg=`,
an internal `write` or an `intent(out)` argument of an intrinsic subroutine get intrinsic-assignment semantics; and the
`ieee_max_num` family returns the number when the other argument is a signaling NaN. They are explained, with a
`system_clock` example that gfortran rejects under `-std=f2023`, on
xref:programming-languages/fortran/history-standards-and-compilers.adoc[History, Standards and Compilers]. Everything else
that a Fortran 2018 program does still means the same in Fortran 2023.

Corrigendum 1 of Fortran 2023 (ISO/IEC 1539-1:2023/Cor 1:2026) was published in January 2026; its draft is WG5 N2244. It is
a set of corrections, not new features. The free text used by this section, J3/23-007r1, predates it, so for contractual
work check a clause against the ISO text and the corrigendum.

== Fortran 2028

Fortran 2028 (formerly called "F202Y") is the revision after Fortran 2023. Its status, as far as public sources show:

* *Committee draft stage.* WG5 lists "N2258 Fortran 2028 Committee Draft" as a document that is not public, on its
  documents page dated 13 July 2026. The ballot outcome is not published there. The standard itself is not published, and no
  edition of ISO/IEC 1539-1 for it exists.
* *A public working draft exists.* J3/26-007r1 ("Fortran 2028 Working Draft", 3 March 2026) is the text read for this
  page. Its foreword says the sixth edition cancels and replaces the fifth (ISO/IEC 1539-1:2023), and names three main
  changes: templates, generic subprograms, and the specification of the default kinds of the intrinsic types.
* *Publication is targeted for the second half of 2028*, the schedule quoted when this section was planned; I could not
  confirm the date on a public page, so treat it as a target.
* *Compatibility.* The draft's Introduction states that a conforming Fortran 2023 program not affected by the listed
  limitations is a conforming Fortran 2028 program.

The documents to follow are the J3 papers (https://j3-fortran.org/), the WG5 page for the revision
(https://wg5-fortran.org/f2028.html[wg5-fortran.org/f2028.html]), which on the check date only says that Fortran 2028 is
the working title of the revision after Fortran 2023, and the public proposals repository
(https://github.com/j3-fortran/fortran_proposals[j3-fortran/fortran_proposals]). I could not read the WG5 work item list
(N2261) or the Convenor's report (N2262): the file name tried returned "not found". The list below therefore follows the
working draft itself, which is the authoritative description of what is in the revision at this point.

=== Templates and requirements

Clause 16 of the draft, "Templates, requirements, and instantiation", is the largest addition. A *template* is a construct
in a module, a main program or another template. It is parameterized by *deferred arguments* (deferred types, deferred
constants and deferred procedures) and contains declarations, derived types and procedures written in terms of them.
*Instantiation* with an `instantiate` statement gives the scoping unit access to the public entities of the template, built
for the arguments you supply. A *requirement* is a named set of deferred-argument declarations, stated once and reused with
`require`, which says what an argument must provide (the counterpart of a concept or a trait). A *templated subprogram*
is a procedure that is itself a template and can be instantiated inline at the point of the call. The Fortran 2023 `rank`
clause and `rank` intrinsic matter here, because they are what lets a template declare an entity whose rank depends on a
deferred argument (the draft calls such an entity *implied-rank*).

The syntax in the draft's examples puts the instantiation arguments in braces. The program below is a swap routine written as
a template, followed by an instantiation for `integer`. It is the draft's syntax, assembled from the grammar rules R1601 to
R1626 of 16.1 to 16.5; *no compiler accepts it, and it was not run.* It exists to show the shape of the feature, and the
diagnostics below show what the two compilers say today.

[source,fortran]
----
! Fortran 2028 draft (clause 16): TEMPLATE with a deferred type and INSTANTIATE {...}.
module swap_m
  implicit none
  template swap_tmpl(t)
    deferred type :: t
  contains
    subroutine swap(a, b)
      type(t), intent(inout) :: a, b
      type(t) :: tmp
      tmp = a
      a = b
      b = tmp
    end subroutine swap
  end template swap_tmpl
end module swap_m

program template_probe
  use swap_m
  implicit none
  instantiate swap_tmpl {integer}, only: swap_int => swap
  integer :: i, j
  i = 1
  j = 2
  call swap_int(i, j)
  print '(2(i0,1x))', i, j
end program template_probe
----

[source,text]
----

    4 |   template swap_tmpl(t)
      |   1
Error: Unclassifiable statement at (1)
04_template.f90:8:14:

    8 |       type(t), intent(inout) :: a, b
      |              1
Error: Derived type 't' at (1) is being used before it is defined
----

and Flang 23 stops at the first statement, because it cannot parse the construct:

[source,text]
----

Source: https://j3-fortran.org/doc/year/26/26-007r1.pdf[J3/26-007r1 (Fortran 2028 working draft), 16.1 to 16.5]

The plain Fortran 2023 ways to get the same result today are the techniques on
xref:programming-languages/fortran/generic-and-rank-independent-programming.adoc[Generic and Rank Independent Programming]
(generic interfaces with one specific per type, `+class(*)+`, include files and the preprocessor). A template-based library
will not be portable until compilers implement the clause, so any code written against the draft is an experiment.

=== Generic subprograms and `select generic`

A subprogram declared `generic` defines a family of unnamed specific procedures under one name. Its dummy arguments are
declared with ranges (for rank, `rank(0:7)`; for type, a type-generic argument), and the construct `select generic rank`
or `select generic type` supplies the body that differs between specifics, selecting at compile time one block for each
instance. The draft's own example of `select generic rank` has a block for rank 0, a block for ranks 1 to 3 and a
`rank default` block for ranks 4 to 7, which replaces seven hand-written specifics and the generic interface that lists
them. The fragment below is that idea with the draft's keywords, and it is also rejected by both compilers.

[source,fortran]
----
! Fortran 2028 draft (11.1.10): generic subprogram with SELECT GENERIC RANK.
module fill_m
  implicit none
contains
  generic subroutine fill(x)
    real, rank(0:2) :: x
    select generic rank (x)
    rank (0)
      x = 0.0
    rank default
      x = 1.0
    end select
  end subroutine fill
end module fill_m
----

Source: https://j3-fortran.org/doc/year/26/26-007r1.pdf[J3/26-007r1 (Fortran 2028 working draft), 11.1.10]

gfortran reports `+Error: Expected '::' at (1)+` at the `generic subroutine` line (and then `Invalid character in name` at the
`rank(0:2)` declaration); Flang 23 reports `+error: expected 'END'+` at the same line. Compare the `select rank`
construct of Fortran 2018, which is available today and selects a block at run time for an assumed-rank dummy argument
(see xref:programming-languages/fortran/array-arguments-assumed-shape-size-and-rank.adoc[Array Arguments: Assumed Shape, Size and Rank]).

=== The `default kind` statement

Many numerical codes need to change the precision of every unadorned `real` in a file. Today that is done with compiler
options (`-fdefault-real-8` in gfortran), which are not standard, change the meaning of all `real` declarations in the
build, and are a classic source of mismatch errors (see
xref:programming-languages/fortran/intrinsic-types-and-kinds.adoc[Intrinsic Types and Kinds] and
xref:programming-languages/fortran/compilers-and-compiler-options.adoc[Compilers and Compiler Options]). The draft adds a
standard statement, `default kind (integer = selected_int_kind(18))`, that sets the default kind of one or more of `real`,
`integer`, `logical` and `character` in a scoping unit; the default kind of `complex` always follows that of `real`. A
`use` statement with a `default_kinds` clause takes the defaults of a module. The statement is processed per scoping unit, so
different modules of one build can use different defaults. Neither compiler accepts it:

[source,text]
----
01_default_kind.f90:4:3:

    4 |   default kind (integer = selected_int_kind(18))
      |   1
Error: Unclassifiable statement at (1)
----

That is gfortran 16.2; Flang 23 says `error: expected declaration construct`. Until then, `real(dp)` with a kind from a
module such as *heatflow*'s `heatflow_kinds` is the portable way to state the precision.

=== What becomes obsolescent

The standard defines two categories: *deleted* features (not required by the standard) and *obsolescent* features, which
the standard keeps but recommends against and which a processor must be able to report. The draft's Annex B was compared
with the Fortran 2023 Annex B:

* *Deleted features.* Nothing new. B.1 (the Fortran 90 features dropped by Fortran 95) and B.2 (the arithmetic `if` statement
  and the nonblock `do`, deleted in Fortran 2023) are the same in both.
* *Obsolescent features.* Fortran 2023 lists twelve (alternate return, computed `go to`, statement functions, `data`
  statements among executable statements, assumed-length character functions, fixed source form, the `+character*+` form of a
  declaration, `entry`, the label form of `do`, `common` and `equivalence` with `block data`, specific names of intrinsic
  functions, and `forall`). The Fortran 2028 draft lists fourteen: the same twelve plus two additions. B.3.14 is the `Dw.d`
  edit descriptor and B.3.15 is *default implicit typing* (the rule that gives an undeclared name starting with `i` to `n`
  the type integer and any other the type real). The `implicit` statement itself and `implicit none` are not deleted by this:
  the obsolescent item is the default mapping.

For the working programmer this changes nothing today (both are still accepted) but confirms the advice of this whole
section: write `implicit none` in every program unit, and use `e` or `es` editing instead of `d`. See
xref:programming-languages/fortran/variables-declarations-and-attributes.adoc[Variables, Declarations and Attributes],
xref:programming-languages/fortran/format-specifications-and-edit-descriptors.adoc[Format Specifications and Edit Descriptors]
and xref:programming-languages/fortran/legacy-features-and-modernization.adoc[Legacy Features and Modernization].

Not in the draft: I searched the text of J3/26-007r1 for a standard preprocessor, namespaces and a looping construct that is
independent of rank, and found no corresponding text. So a statement that Fortran 2028 will have a standard preprocessor, namespaces or rank-independent
looping has no support in the draft; only the items in the table above are in it.

== Where the books are outdated

Each page of this section notes, topic by topic, where the reference books differ from the current standard and from
current practice. The table collects those notes in one place, grouped by area, so that a reader of the books can check

== Errata of the main reference book

The items below are slips in the printed book, recorded during the review of the book for this section. They are listed so
that a reader who works from the book does not copy them, and each is described in my own words. The three that concern
`c_f_strpointer` and the `enumeration type` statement (pages 452 to 454 and 462) were rechecked against J3/23-007r1 while
writing this page, and the correct form given is the standard's; the others were not independently rechecked here. The publisher keeps an errata file (`edits.pdf`) on the book's web
site; it could not be read from the tools used for this page (the publisher's site returned no content), so this list is not
a copy of it, and the file should be checked for items that this list does not contain. Page numbers are those of the
printed book.

[cols="1,6",options="header"]
|===
| Page | Problem and the correct form

| 1
| The introduction says that only the last chapter covers Fortran 2023. The chapter on genericity (22) also contains Fortran 2023 material (`typeof`, `classof`, the `rank` clause, integer arrays as bounds and subscripts).

| 439
| The figure with the generic-programming example declares one name for a diagonal and uses another, uses a data name that is not declared, and sizes a lower-bound array with the rank of a scalar. The rank of a scalar is 0, so that array has size zero; the intended declaration is probably an array whose size is the number of dimensions.

| 442
| An `ubound` call passes an array section where the second argument belongs. The reference is `ubound(a, rank(a))` (the array, then the dimension).

| 452
| The pointer argument of `c_f_strpointer` is described as being of kind `c_ptr`. The standard (18.2.3.5) says it is a scalar deferred-length character pointer of kind `c_char`.

| 452-453
| The length of the result is described inconsistently ("less than" in one place, "less than or equal to" in another) relative to `nchars`. The standard says the length is the largest value for which no null character appears in the sequence and which is less than or equal to `nchars` if present.

| 454
| The `getenv` example calls `c_f_pointer` with a fixed count of 32768 characters. The standard's own `getenv` example (18.2.3.5, case ii) uses `c_f_strpointer`, which finds the end of the string.

| 462
| The general form of the `enumeration type` statement has unbalanced brackets and leaves `type` out of the end statement. The end statement is `end enumeration type [name]` (R769); the example on the same page is correct.

| copyright page

statement-function, `entry`, `forall` and `%VAL` forms that appear in the reference books and in older material are not
reproduced anywhere on the modern pages of this section; they appear only, and labelled as old code, on
xref:programming-languages/fortran/legacy-features-and-modernization.adoc[Legacy Features and Modernization].

== Pitfalls

* *Writing code against the draft.* Nothing in J3/26-007r1 is implemented in either free compiler on the check date, and the
  draft still carries open technical issues. Use the Fortran 2023 techniques now and read the draft as a preview.
* *Calling the draft "the standard".* It is a working document; the Committee Draft is not public and the standard is not
  published. Cite the clause numbers of J3/26-007r1 only with the draft's date (3 March 2026).
* *Trusting `-std=f202y` to enable the draft.* In gfortran 16.2 the switch enabled none of the items probed on this page; the
  manual calls the features it gates experimental.
* *Treating obsolescent as deleted, or the reverse.* Obsolescent features (including `forall`, and from Fortran 2028
  default implicit typing and `Dw.d`) still compile. The deleted features are the ones that `-std=f2023` rejects.
* *Equating "the book says so" with "the standard says so".* Appendix A of the main reference book is the authors' list. The
  standard's lists are in Annex B.
* *Using a Fortran 2023 feature that only one compiler accepts.* The table above shows the split; probe with both a compile
  and a run, because several rejections only appear at link or run time (`tokenize` and `c_f_strpointer` in gfortran 16.2).
* *Printing a conditional expression directly.* gfortran 16.2 crashes on it; assign to a variable first.
* *Reading a status page as a promise.* A compiler's feature page, the fortran-lang compilers page and this page can lag
  or lead the compiler you installed; probe your own build.

See also xref:programming-languages/fortran/common-gotchas-and-pitfalls.adoc[Common Gotchas and Pitfalls] and
xref:programming-languages/fortran/best-practices-and-style.adoc[Best Practices and Style].
