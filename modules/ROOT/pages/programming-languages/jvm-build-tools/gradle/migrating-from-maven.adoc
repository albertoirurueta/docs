This page is written against Gradle 9.8.1 (released on 7 October 2026) and Apache Maven 3.10.0, with Gradle 8.14.6, the last 8.x release, mentioned where it differs. Every example marked as run was executed on 2026-10-16 on macOS (Apple silicon), on Oracle JDK 26 (`java version "26"`, the default JDK of the machine), once with `+*.gradle.kts+` files and once with `+*.gradle+` files. The Gradle runs used the 9.8.1 distribution, and the Maven runs used 3.10.0 with a local repository created for the page. The Java code is compiled for Java 17 (`release` 17), so the same builds work on JDK 17 and 21. The Gradle examples are compatible with the configuration cache (`org.gradle.configuration-cache=true` was set and the second run reused the entry), except the one failure that is shown on purpose. The numbers in the output use the English locale (`-Duser.language=en -Duser.country=US`), because the machine's default would print a decimal comma. Long output is shortened with a line that contains only `…`, and the scratch directory is shown as `…`. Gradle 8.14.x was not available, so what is said about it comes from the official documentation and is labelled "not run here". Two more things were not run and are labelled the same way: Build Scans (publishing to the Develocity service needs the acceptance of its terms of use) and publishing to a remote repository such as Maven Central; the publishing runs went to a `file:` repository inside the build directory.

The usual path from Maven to Gradle is to keep the Maven build, add a Gradle build next to it, convert the structure with `gradle init`, and then repair what the converter cannot know. This page follows that path with a real multi-module build and records every failure on the way. The shared page xref:programming-languages/jvm-build-tools/migrating-between-tools.adoc[Migrating Between Tools] has the overview of all migration directions and a single-module Maven to Gradle conversion; this page goes deeper into the Gradle side and into the parts of a multi-module POM that the shared page does not cover: the parent POM, `dependencyManagement`, inherited plugin configuration, Failsafe, Shade and the published POMs. For the vocabulary behind the two tools see xref:programming-languages/jvm-build-tools/build-automation-fundamentals.adoc[Build Automation Fundamentals], xref:programming-languages/jvm-build-tools/dependency-management-fundamentals.adoc[Dependency Management Fundamentals] and xref:programming-languages/jvm-build-tools/comparing-ant-maven-and-gradle.adoc[Comparing Ant, Maven & Gradle].

== The migration in seven steps

The Gradle user manual recommends this order for any Maven build, and the sections of this page follow it. Do not change the source layout, the artifact coordinates or the Maven build while you migrate: the Gradle build should produce the same artifacts, so that the switch is a matter of the CI pipeline.

[mermaid]
----
flowchart TD
  A[1. Keep the Maven build and run it in CI] --> B[2. Add the Gradle build beside it: gradle init]
  B --> C[3. Fix what init could not know: Java release, test framework, filtering, profiles]
  C --> D[4. Verify dependencies against mvn dependency:tree]
  D --> E[5. Rebuild integration tests and replace Maven plugins]
  E --> F[6. Compare artifacts, POMs and test results]
  F --> G{Same outputs?}
  G -- no --> C
  G -- yes --> H[7. Switch CI and releases, then delete the pom.xml files]
----

Source: https://docs.gradle.org/current/userguide/migrating_from_maven.html#migmvn:general_guidelines[Gradle User Manual: Migrating from Maven, general guidelines]

The manual also suggests creating a Build Scan of both builds and comparing them. That was not run here (publishing a scan needs the acceptance of the terms of use of the Develocity service); the local `--profile` report and the dependency reports used below give the same information without leaving the machine. See xref:programming-languages/jvm-build-tools/gradle/performance-profiling-and-build-scans.adoc[Performance Profiling & Build Scans].

== The Maven build that is migrated

The running example of the section is _tidepool_, a tide prediction toolkit. As a Maven build it is a parent POM with three modules: `tidepool-model` (four records), `tidepool-engine` (a `StationReader` that uses Commons CSV and a `TideEngine`) and `tidepool-cli` (a picocli program that is delivered as a shaded JAR). The parent POM sets the Java release, imports the JUnit BOM, manages the versions of the third-party libraries and of the sibling modules, declares JUnit for every module, activates a profile `ci`, and attaches the source and Javadoc JARs to every module.

== Step 1 and 2: automatic conversion with gradle init

`gradle init` run in a directory that has a `pom.xml` offers to convert it, and the type `pom` is inferred automatically when the file exists. The conversion reads the _effective_ POM and the effective settings, so inheritance, `dependencyManagement` and properties are already resolved when it writes the Gradle files, and it handles single-module and multi-module builds. It leaves every Maven file untouched, so both builds can live in the same directory: Maven writes `target/`, Gradle writes `build/`, and nothing in the sources changes. The manual lists what is converted: the general metadata (group, name, version, description), the plugins `maven-publish`, `java-library` and `war`, the compiler settings, the external and inter-module dependencies, the repositories (including the local Maven repository), sources and Javadoc packaging, the TestNG runner, exclusions, and global exclusions from the Enforcer plugin; whatever else the POM does is not converted. A Maven `compile` dependency is mapped to `api`, which keeps the exposed dependencies of the Maven project and which the manual asks you to revisit after the conversion.

Source: https://docs.gradle.org/current/userguide/build_init_plugin.html#sec:pom_maven_conversion[Gradle User Manual: Build Init plugin, Maven conversion] and https://docs.gradle.org/current/userguide/migrating_from_maven.html#migmvn:automatic_conversion[Gradle User Manual: Migrating from Maven, automatic conversion]

The conversion was run with the wrapper of the build (`gradle init` itself needs no existing Gradle build; with Gradle installed it is the same command without `./gradlew`):

.Kotlin DSL
[source,bash]
----
./gradlew init --type pom --dsl kotlin --use-defaults
----

.Groovy DSL
[source,bash]
----

----

=== What it got wrong, one failure at a time

The generated build is a starting point, and the manual says so. The first `./gradlew build` shows the first problem, and each fix shows the next one. The runs below are all on the generated build, with only the fix named in the heading applied.

*1. The Java release was lost.* The POM sets `maven.compiler.release` to 17; the conversion wrote `java.sourceCompatibility = JavaVersion.VERSION_1_8`, and the sources use records:

[source,text]
----
> Task :tidepool-model:compileJava FAILED
warning: [options] source value 8 is obsolete and will be removed in a future release
warning: [options] target value 8 is obsolete and will be removed in a future release
warning: [options] To suppress warnings about obsolete options, use -Xlint:-options.
…/init-kts/tidepool-model/src/main/java/io/tidepool/model/Constituent.java:4: error: records are not supported in -source 8
public record Constituent(String name, double amplitude, double phase) {
       ^
  (use -source 16 or higher to enable records)
…
4 errors
3 warnings
…
----

The fix is `options.release = 17` in the compile task (or a Java toolchain; see xref:programming-languages/jvm-build-tools/gradle/toolchains.adoc[Gradle Toolchains]), which also removes the `sourceCompatibility` line. `release` is also what the Maven compiler plugin uses when `maven.compiler.release` is set, and the reason why the code compiles identically in both builds.

*2. The JUnit Platform launcher has no version.* In the POM, `junit-jupiter` and the launcher that Surefire adds by itself take their versions from the imported `junit-bom`. The conversion copied the resolved version of `junit-jupiter` as a literal, did not import the BOM and did not select the JUnit Platform for the test task. With `useJUnitPlatform()` and the launcher in `testRuntimeOnly`, as the shared page recommends, the build fails because the launcher has no version:

[source,text]
----
* What went wrong:
Configuration cache state could not be cached: field `classpath` of task `:tidepool-model:test` of type `org.gradle.api.tasks.testing.Test`: error writing value of type 'org.gradle.api.internal.file.collections.DefaultConfigurableFileCollection'
> Could not resolve all files for configuration ':tidepool-model:testRuntimeClasspath'.
   > Could not find org.junit.platform:junit-platform-launcher:.
     Required by:
         project ':tidepool-model'
…
----

The BOM import of Maven becomes a platform: `testImplementation(platform("org.junit:junit-bom:6.1.3"))`, and then the `junit-jupiter` and `junit-platform-launcher` dependencies are declared without a version. The section on BOMs below explains the mapping.

*3. The integration test runs as a unit test and has no data file.* After the two fixes the build compiles. The engine module fails in the `test` task, because `StationReaderIT` is in `src/test/java` like the unit tests, Gradle's `test` task runs every class of that source set, and the system property `tidepool.data` that Surefire and Failsafe passed through `systemPropertyVariables` is not converted:

----

*5. The profile has no effect.* `-Pci` is accepted by Gradle without complaint because it is a project property, and nothing reads it. The conversion also did not look at the Surefire, Failsafe, resources or Shade configuration: only the compiler settings, the dependencies and the publishing are converted.

These five points are the usual harvest of a conversion of a real multi-module build, and the rest of the page fixes them in the order of the manual. The conversion also made three decisions that are legitimate but that you should revisit. `mavenLocal()` is the first repository, which makes the build depend on whatever a previous Maven build installed into `+~/.m2/repository+`; remove it unless you need that interoperability. The repository is declared in `buildSrc` for every project, while a single declaration in `settings.gradle(.kts)` with `RepositoriesMode.FAIL_ON_PROJECT_REPOS` is the current practice (see xref:programming-languages/jvm-build-tools/gradle/repositories-and-content-filtering.adoc[Repositories & Content Filtering]). And `buildSrc` works, but a `build-logic` included build is the form recommended for shared build logic (see xref:programming-languages/jvm-build-tools/gradle/convention-plugins-and-sharing-build-logic.adoc[Convention Plugins & Sharing Build Logic]).

== The lifecycle and the command line

Maven builds are phases in a fixed order, and each phase runs the goals bound to it. Gradle has no phases, but the `base` plugin, applied by every JVM plugin, provides lifecycle tasks (empty tasks that depend on the real ones) that line up with the main phases:

[cols="2,3,3",options="header"]
|===
|Maven phase |Gradle task |Note

|`clean`
|`clean`
|Deletes the `build` directory of the project.

|`compile`
|`classes`
|Compiles all languages and runs `processResources`, which is also where resource filtering happens.

|`test`
|`test`
|Runs the unit tests of the `test` source set.

|`package`
|`assemble`
|Builds the archives of the project: the JAR, and here the sources, Javadoc and `-all` JARs.

|`verify`
|`check`
|Runs every verification task that is attached to it; integration tests have to be attached by hand (see below).

|`install`
|`publishToMavenLocal`
|Needed only to hand artifacts to a Maven build; Gradle builds share outputs as project dependencies or through included builds.

|`deploy`
|`publish`
|Publishes every publication to every repository; `publishNamePublicationToRepoNameRepository` publishes one of them.
|===

`build` runs `assemble` and `check`. A lifecycle task is not special: you create your own by writing a task without action that depends on the ones you want, and the `mvn verify`-style run of "everything except the slow tests" is a lifecycle task of this kind. The mapping of the command line options is also direct for the common ones:

[cols="2,3,3",options="header"]
|===
|Maven |Gradle |Note

|`mvn verify -pl tidepool-cli -am`
|`./gradlew :tidepool-cli:build`
|Project dependencies are built automatically; no `-am` is needed (see the dry run above). Naming a task of one project runs that task and the tasks it needs in the other projects.

|`mvn verify -DskipTests`
|`./gradlew build -x test -x integrationTest`
|`-x` removes a task from the task graph.

|`mvn -o`
|`./gradlew --offline`
|Use the dependency cache only.

|`mvn -U`
|`./gradlew --refresh-dependencies`
|Ignore cached dependency metadata and artifacts.

|`mvn -T 4`
|`org.gradle.parallel=true` or `--parallel`
|Gradle also runs the independent tasks of a single project in parallel when the configuration cache is on.

|`mvn -P ci`
|`-Pci` (a project property)
|Different meaning, explained in the section on profiles.

|`mvn -Dprop=value`
|`-Dprop=value` (a system property) or `-Pprop=value` (a project property)
|Gradle distinguishes the two kinds of property; see the section on profiles and properties.

|`mvn -q`, `-X`
|`--quiet`, `--debug`
|Also `--info` and `--warn`. See xref:programming-languages/jvm-build-tools/gradle/directories-and-logging.adoc[Directories & Logging].

|`.mvn/maven.config`, `.mvn/jvm.config`
|`gradle.properties` (`org.gradle.jvmargs`, `org.gradle.parallel`)
|See xref:programming-languages/jvm-build-tools/gradle/build-environment-and-properties.adoc[Build Environment & Properties].

|`mvnw`
|`gradlew`
|See xref:programming-languages/jvm-build-tools/gradle/gradle-wrapper.adoc[Gradle Wrapper] and xref:programming-languages/jvm-build-tools/maven/maven-wrapper.adoc[Maven Wrapper].
|===

Running `./gradlew :tidepool-cli:build -x test -x integrationTest --offline` on the converted build, with the configuration cache, took 1 second and executed one task; the other 19 were up to date. The Maven phases and the fixed order are described in xref:programming-languages/jvm-build-tools/maven/build-lifecycle.adoc[Maven Build Lifecycle], and the Gradle model in xref:programming-languages/jvm-build-tools/gradle/build-lifecycle.adoc[Gradle Build Lifecycle] and xref:programming-languages/jvm-build-tools/gradle/command-line-interface.adoc[Command-Line Interface].

== Dependencies

Gradle uses the same coordinates as Maven (group, artifact, version, classifier) and the same repositories, so the dependency part of a migration is mostly a change of notation. What changes is the vocabulary (scopes are configurations), the place where versions are managed, and one rule of conflict resolution.

=== Scopes and configurations

[cols="2,3,3",options="header"]
|===
|Maven scope |Gradle configuration |Note

|`compile`
|`implementation` or `api`
|`api` exists only with the `java-library` plugin and is part of the compile classpath of consumers; use `implementation` by default. `gradle init` writes `api` for all of them.

|`runtime`
|`runtimeOnly`
|

|`provided`
|`compileOnly`
|The `war` plugin adds `providedCompile` and `providedRuntime`, which keep the dependency out of the WAR but on the test classpaths.

|`test`
|`testImplementation` and `testRuntimeOnly`
|Gradle separates what the tests need to compile from what they need only to run (the JUnit launcher is the second kind).

|`import` (in `dependencyManagement`)
|`+platform(...)+`
|See the section on BOMs.

|`optional`
|Feature variants
|Gradle ignores the optional dependencies of other modules, like Maven; to publish an optional dependency, declare a feature variant (see xref:programming-languages/jvm-build-tools/gradle/java-projects.adoc[Java Projects]).
|===

Gradle separates the dependencies a module needs to be built from those a module that uses it needs, which Maven does not: published POMs of Maven projects typically contain dependencies that consumers do not need. In the tidepool conversion, the engine uses Commons CSV only inside `StationReader`, and its public methods only mention types of the model, so the engine declares `api(project(":tidepool-model"))` and `implementation(libs.commons.csv)`. The published POM then lists Commons CSV with the `runtime` scope, not `compile` (see the section on publishing).

=== Repositories

Maven has an implicit repository, Central; Gradle has none, so every build must declare at least one. The equivalent of Maven's default is `mavenCentral()`, declared once in `settings.gradle(.kts)` as above. A `<repository>` element becomes `+maven { url = uri("...") }+`. A `<mirror>` of `settings.xml` has no direct counterpart in the build file; Gradle 9.8.0 can reuse the mirror settings of Maven when `org.gradle.mirror.maven.settings=true` is set, which is described, with the results of a real run, in xref:programming-languages/jvm-build-tools/gradle/repositories-and-content-filtering.adoc[Repositories & Content Filtering]. `mavenLocal()` resolves against `+~/.m2/repository+`; the manual says it is for interoperating with Maven builds only, and it should not be left in a migrated build that does not need it, because it makes the result depend on what other builds installed.

Source: https://docs.gradle.org/current/userguide/migrating_from_maven.html#migmvn:declaring_repos[Gradle User Manual: Migrating from Maven, declaring repositories]

=== Managed versions: properties, dependencyManagement and the catalog

A parent POM manages versions in two places: properties such as `<commons-csv.version>` and the `<dependencyManagement>` block that uses them. Gradle has three tools for the same job, and they are not interchangeable:

[cols="2,3",options="header"]
|===
|Maven idiom |Gradle replacement

|A version property used by one or two dependencies
|An entry in the `[versions]` table of `gradle/libs.versions.toml`, referenced with `version.ref`. The catalog is the same for every project of the build, and for the included `build-logic` build.

|`<dependencyManagement>` entry for a third-party library, with the dependency declared without a version in the module
|A catalog library (`libs.commons.csv`) with the version; the module declares the library. If the version must also apply to transitive dependencies, add a dependency constraint (`+constraints { }+`) or a platform.

|`<dependencyManagement>` entry for a sibling module
|Nothing: `project(":tidepool-model")` has no version, because the project is part of the build.

|`import` of a BOM
|`+platform(...)+` or `+enforcedPlatform(...)+`.

|A parent POM of a company that only manages versions (a BOM that other builds import)
|The `java-platform` plugin, which publishes a BOM.
|===

The version properties of the parent POM became the `[versions]` table of the catalog shown above. A value that must differ between builds comes from a Gradle property read with `providers.gradleProperty` in the build script, not from the catalog. See xref:programming-languages/jvm-build-tools/gradle/version-catalogs.adoc[Version Catalogs].

=== BOMs, platforms and java-platform

The import of the JUnit BOM, in the convention plugin above, is `testImplementation(platform(libs.findLibrary("junit-bom").get()))`. A platform adds the version constraints of the BOM to the dependency graph; `junit-jupiter` and the launcher then need no version of their own. `platform()` takes the `<dependencyManagement>` constraints of the POM and ignores the `<dependencies>` block of the BOM; `enforcedPlatform()` makes the constraints strict, so that a higher version requested elsewhere in the graph cannot override them. The Maven `scope` of a BOM import is always `import`; in Gradle the import is a normal dependency declaration in the configuration where you want the constraints (`implementation`, `testImplementation`, or both).

The other direction, publishing a BOM from a build, replaces a `<packaging>pom</packaging>` parent that only has a `dependencyManagement` section. The `java-platform` plugin produces it. This minimal build was run in both DSLs:

See xref:programming-languages/jvm-build-tools/gradle/platforms-constraints-and-rich-versions.adoc[Platforms, Constraints & Rich Versions] and xref:programming-languages/jvm-build-tools/maven/dependency-management-and-boms.adoc[Maven Dependency Management & BOMs].

Source: https://docs.gradle.org/current/userguide/migrating_from_maven.html#migmvn:using_boms[Gradle User Manual: Migrating from Maven, using BOMs] and https://docs.gradle.org/current/userguide/java_platform_plugin.html#sec:java_platform_publishing[Gradle User Manual: Java Platform plugin, publishing]

=== The one real semantic difference: which version wins

Maven resolves a conflict by _nearest definition_: the version declared closest to the root of the tree wins, and a version in your own POM always wins over a transitive one. Gradle picks the _highest_ version of the module in the graph. A converted build can therefore resolve a different version even if every declaration is identical. This was run on a small project that declares Commons CSV 1.14.1 (which needs `commons-io` 2.20.0) and, directly, `commons-io` 2.11.0:

[source,bash]
----
mvn org.apache.maven.plugins:maven-dependency-plugin:3.11.0:tree
----

[source,text]
----
[INFO] io.tidepool:mediation:jar:1.0.0
[INFO] +- org.apache.commons:commons-csv:jar:1.14.1:compile
[INFO] |  \- commons-codec:commons-codec:jar:1.19.0:compile
[INFO] \- commons-io:commons-io:jar:2.11.0:compile
----

.Kotlin DSL: build.gradle.kts
[source,kotlin]
----
plugins {
    `java-library`
}

repositories {
    mavenCentral()
}

dependencies {
    implementation("org.apache.commons:commons-csv:1.14.1")
    implementation("commons-io:commons-io:2.11.0")
}
----

[source,bash]
----
./gradlew dependencies --configuration runtimeClasspath
----

[source,text]
----
runtimeClasspath - Runtime classpath of source set 'main'.
+--- org.apache.commons:commons-csv:1.14.1
|    +--- commons-io:commons-io:2.20.0
|    \--- commons-codec:commons-codec:1.19.0
\--- commons-io:commons-io:2.11.0 -> 2.20.0
----

Maven used the older 2.11.0 declared in the POM; Gradle used 2.20.0 (`+2.11.0 -> 2.20.0+` in the report) and said why with `dependencyInsight`:

[source,text]
----

…
   Selection reasons:
      - By conflict resolution: between versions 2.20.0 and 2.11.0
…
----

If the old version must stay (a library that breaks with the new one, a security policy), say so in the build: a `strictly` version makes the declaration a hard requirement, and it overrides the request of the transitive dependency:

.Kotlin DSL
[source,kotlin]
----
dependencies {
    implementation("org.apache.commons:commons-csv:1.14.1")
    implementation("commons-io:commons-io") {
        version {
            strictly("2.11.0")
        }
    }
}
----

.Groovy DSL
[source,groovy]
----
dependencies {
    implementation 'org.apache.commons:commons-csv:1.14.1'
    implementation('commons-io:commons-io') {
        version {
            strictly '2.11.0'
        }
    }
}
----

[source,text]
----
runtimeClasspath - Runtime classpath of source set 'main'.
+--- org.apache.commons:commons-csv:1.14.1
|    +--- commons-io:commons-io:2.20.0 -> 2.11.0
|    \--- commons-codec:commons-codec:1.19.0
\--- commons-io:commons-io:{strictly 2.11.0} -> 2.11.0
----

The Groovy DSL variants of the three builds in this section (`+implementation 'commons-io:commons-io:2.11.0'+`, `+version { strictly '2.11.0' }+` and the exclusion below) were run too and printed the same reports. The list of dependencies, compared at the end of a migration with `mvn dependency:tree` or `dependency:list`, is how you find these differences before production does. The mechanisms are in xref:programming-languages/jvm-build-tools/gradle/dependency-resolution-conflicts-and-capabilities.adoc[Dependency Resolution, Conflicts & Capabilities] and the Maven rule in xref:programming-languages/jvm-build-tools/maven/dependencies-scopes-and-mediation.adoc[Maven Dependencies, Scopes & Mediation].

=== Exclusions

A Maven `<exclusion>` removes a transitive dependency from one declaration. The Gradle form is the same, but the manual advises you to understand why the exclusion exists before you carry it over: an exclusion that was only there to select a version is better expressed as a constraint or a `strictly` version, and an exclusion that removes a module for a reason unrelated to versions can be attached to the whole configuration. This was run for the exclusion of `commons-codec` from Commons CSV:

[source,text]

[INFO] +- org.apache.commons:commons-csv:jar:1.14.1:compile
[INFO] \- commons-io:commons-io:jar:2.11.0:compile
----

.Kotlin DSL
[source,kotlin]
----
implementation("org.apache.commons:commons-csv:1.14.1") {

----

.Groovy DSL

== Multi-module builds and inheritance

A Maven `<modules>` block is an `+include(...)+` in `settings.gradle(.kts)` (the conversion did this for the three modules). The dependency of one module on another becomes `project(":name")`, and a project dependency is both the ordering and the artifact reference; the order of the reactor, which Maven derives from the dependencies, is derived in the same way. `./gradlew projects` lists the result:

[source,bash]
----
./gradlew projects
----

[source,text]
----
Projects:

------------------------------------------------------------
Root project 'tidepool'
------------------------------------------------------------

Location: …/groovy

Project hierarchy:

Root project 'tidepool'
+--- Project ':tidepool-cli' - Predicts tide heights from harmonic constituents
+--- Project ':tidepool-engine' - Predicts tide heights from harmonic constituents
…
----

Inheritance has no direct counterpart. In Maven, a child POM inherits dependencies, plugins, properties and configuration from its parent in a fixed model. In Gradle the same sharing is a convention plugin (a plugin that configures other plugins), and the `+allprojects { }+` and `+subprojects { }+` blocks that injected configuration in older builds are the form the manual discourages, because they couple projects to each other. The parts of the parent POM map as follows:

[cols="2,3",options="header"]
|===
|Parent POM |Convention plugin or settings

|`<groupId>`, `<version>`
|`group` and `version` in the convention plugin (or the root `gradle.properties`)

|`<dependencies>` (inherited by every module)
|The `+dependencies { }+` block of the plugin

|`<dependencyManagement>`
|Catalog, platform or constraints (see above)

|`<pluginManagement>` (plugin versions)
|The versions in the `[plugins]` table of the catalog and in the `build.gradle.kts` of `build-logic`; each plugin has a version in exactly one place

|`<build><plugins>` (plugins applied to every module)
|`+plugins { }+` in the convention plugin

|`<properties>`
|`gradle.properties`, the catalog, or local ``val``s

|`<profiles>`
|Project properties tested in the scripts (see below)

|`<repositories>`
|`+dependencyResolutionManagement { repositories { } }+` in the settings file
|===

A module that does not belong to the parent (an aggregator without inheritance, or a parent in another repository) maps to a build with its own convention plugin, published to a plugin repository or included as a build with `includeBuild`. The shared logic of this build is in the included build `build-logic`; the conversion's `buildSrc` is the same idea in a fixed location, and the page on convention plugins compares the two. See xref:programming-languages/jvm-build-tools/gradle/multi-project-builds.adoc[Multi Project Builds], xref:programming-languages/jvm-build-tools/gradle/convention-plugins-and-sharing-build-logic.adoc[Convention Plugins & Sharing Build Logic] and xref:programming-languages/jvm-build-tools/gradle/composite-builds.adoc[Composite Builds].

Source: https://docs.gradle.org/current/userguide/migrating_from_maven.html#migmvn:multimodule_builds[Gradle User Manual: Migrating from Maven, multi-module builds] and https://docs.gradle.org/current/userguide/sharing_build_logic_between_subprojects.html#sec:convention_plugins_vs_cross_configuration[Gradle User Manual: Sharing build logic, convention plugins versus cross-configuration]

== Profiles and properties

A Maven profile is, as the manual says, a limited `if` statement. Gradle does not need formal profiles because the build script is a program: it can test a project property, an environment variable, the operating system or the JDK. The profile `ci` of tidepool only sets the property `deploy.env`; the equivalent is a project property:

.Kotlin DSL: tidepool-cli/build.gradle.kts (the part about the profile and the filtering)
[source,kotlin]
----
// Maven profile "ci" -> a project property: ./gradlew build -Pci
val deployEnv = providers.gradleProperty("ci").map { "ci" }.orElse("dev")
val projectVersion = version.toString()
----

.Groovy DSL: tidepool-cli/build.gradle (the part about the profile and the filtering)
[source,groovy]
----
// Maven profile "ci" -> a project property: ./gradlew build -Pci
def deployEnv = providers.gradleProperty('ci').map { 'ci' }.orElse('dev')
def projectVersion = version.toString()
----

`providers.gradleProperty` is a lazy, configuration-cache aware way of reading a project property: Gradle remembers that the build used the property and discards the cached configuration if its value changes. A `-Pci` on the command line has no value (`-Pci` sets it to an empty string), so the `map` ignores the value and tests only the presence. The usual forms are `-Penv=ci` read with `orElse("dev")`, or a switch in `gradle.properties` of a CI image.

Three differences between the two systems cause most surprises:

* `-P` means a profile in Maven and a project property in Gradle. `mvn -Pci` activates all the settings of the profile; `./gradlew -Pci` changes nothing unless a script reads the property. A converted build ignores the profiles silently; the conversion does not warn about them.
* Profile activation by the JDK, the operating system, the presence of a file or a property (`<activation>`) becomes plain code. The manual shows a technique with profile scripts (`profile-test.gradle`, `profile-prod.gradle`) applied with `+apply(from = ...)+` according to a property, and warns that conditions in the build make it harder to understand; prefer several tasks of the same type (the manual's example is that the Maven Publish plugin creates one `publish` task per publication and repository) over a switch.
* The properties of the POM that the `maven-resources-plugin` reads (`+${project.version}+`, `+${deploy.env}+`) exist only in Maven. The Gradle replacement is shown in the next section; the environment of the build (JVM options, parallelism, caches) goes into `gradle.properties` and is described in xref:programming-languages/jvm-build-tools/gradle/build-environment-and-properties.adoc[Build Environment & Properties]. A `gradle.properties` in the project root is overridden by the one in the Gradle user home and by command line options; a property set in the build script wins over every external file.

The profiles of a `settings.xml` (credentials, mirrors, repository URLs for a company network) are a user-level matter: credentials go to `+~/.gradle/gradle.properties+` or to environment variables, and the mirror to the setting described in xref:programming-languages/jvm-build-tools/gradle/repositories-and-content-filtering.adoc[Repositories & Content Filtering]. See xref:programming-languages/jvm-build-tools/maven/profiles.adoc[Maven Profiles] and xref:programming-languages/jvm-build-tools/maven/settings-xml-and-password-encryption.adoc[Maven settings.xml & Password Encryption].

Source: https://docs.gradle.org/current/userguide/migrating_from_maven.html#migmvn:profiles_and_properties[Gradle User Manual: Migrating from Maven, profiles and properties]

== Resource filtering

The filtered resource of the CLI is `tidepool.properties`, with the Maven placeholders `+${project.version}+` and `+${deploy.env}+`. The Gradle task `processResources` does the same copy, and its `expand` method treats the file as a Groovy template. If you keep the file unchanged during the parallel period, both builds must be able to fill the placeholders. The trick is that the template engine resolves `+${project.version}+` as property `version` of an object called `project`, so the binding can provide maps with those names:

.Kotlin DSL: tidepool-cli/build.gradle.kts
[source,kotlin]
----
tasks.processResources {
    val env = deployEnv
    val ver = projectVersion
    inputs.property("deployEnv", env)
    inputs.property("projectVersion", ver)
    filesMatching("tidepool.properties") {
        expand(
            "project" to mapOf("version" to ver),
            "deploy" to mapOf("env" to env.get())
        )
    }
}
----

.Groovy DSL: tidepool-cli/build.gradle
[source,groovy]
----
tasks.named('processResources') {
    def env = deployEnv
    def ver = projectVersion
    inputs.property('deployEnv', env)
    inputs.property('projectVersion', ver)
    filesMatching('tidepool.properties') {
        expand(project: [version: ver], deploy: [env: env.get()])
    }
}
----

The two `inputs.property` lines declare the values as inputs, so that a build with another profile re-runs the task instead of reusing the output. Without the property, `processResources` would be up to date after a change from `dev` to `ci`. Both values were checked:

[source,bash]
----
./gradlew :tidepool-cli:processResources
cat tidepool-cli/build/resources/main/tidepool.properties
./gradlew :tidepool-cli:processResources -Pci
cat tidepool-cli/build/resources/main/tidepool.properties
----

[source,text]
----
version=1.0.0
env=dev
> Task :tidepool-cli:processResources
version=1.0.0
env=ci
----

(The first command's task line, `UP-TO-DATE`, and the build summaries are left out.) The second run executed the task, as the line shows.

The same code written the obvious way fails with the configuration cache, which is why the `val env = deployEnv` lines exist. The first version of the script read the script-level `val deployEnv` and `val projectVersion` inside the `filesMatching` action. The action is stored in the configuration cache, and a reference to a top-level `val` of a Kotlin script is a reference to the script object, which cannot be stored:

[source,text]
----
FAILURE: Build failed with an exception.

* What went wrong:
Configuration cache problems found in this build.

1 problem was found storing the configuration cache.
- Task `:tidepool-cli:processResources` of type `org.gradle.language.jvm.tasks.ProcessResources`: cannot serialize Gradle script object references as these are not supported with the configuration cache.
  See https://docs.gradle.org/9.8.1/userguide/configuration_cache_requirements.html#config_cache:requirements:disallowed_types
----

The remedy is to copy the values into local variables of the configuration block, as in the script above (the failing version was the same without the two local `val` lines). Reading `project.version` or other `project` properties in the action, at execution time, is a related error: it is deprecated by Gradle 9.x and will fail in Gradle 10; read it into a variable first.

Two details differ from Maven. `expand` treats the whole file as a template, so every `$` is interpreted; a file with literal dollars needs `filter` with `org.apache.tools.ant.filters.ReplaceTokens` (the `@token@` style that Maven also supports). And the Maven `<propertiesEncoding>` setting corresponds to nothing here: Gradle copies with the platform encoding for `expand`, so set `filteringCharset = "UTF-8"` on `processResources` if the files contain non-ASCII characters. See xref:programming-languages/jvm-build-tools/gradle/working-with-files.adoc[Working with Files] and xref:programming-languages/jvm-build-tools/maven/resources-and-filtering.adoc[Maven Resources & Filtering].

Source: https://docs.gradle.org/current/userguide/migrating_from_maven.html#migmvn:filtering_resources[Gradle User Manual: Migrating from Maven, filtering resources]

== Tests and integration tests

Surefire runs the `+*Test+` classes in the `test` phase, and Failsafe runs the `+*IT+` classes in `integration-test`, then checks the result in `verify`; the split exists so that a failing integration test does not skip the cleanup that follows it. Gradle runs the `test` source set with the `Test` task, and `check` depends on it. Three things are needed:

* Select the JUnit Platform for every `Test` task (`useJUnitPlatform()`, in the convention plugin) and give the test runtime classpath the launcher. Surefire brings both by itself.
* Pass the system properties that the plugin configuration passed. `systemPropertyVariables` is `+systemProperty(...)+` on the task; the data file location comes from the root project directory instead of the `project.parent.basedir` of the POM.
* Keep integration tests apart from the unit tests.

For the period in which both builds must work on the same sources, the engine module above uses the file naming convention: the `test` task excludes `+**/*IT.class+`, and a second `Test` task, `integrationTest`, reuses the class directories and the classpath of the `test` source set and includes only those classes, and `check` depends on it. That mimics Surefire plus Failsafe in the Maven layout. The recommended form for a finished migration is the JVM test suite plugin, with the integration tests in `src/integrationTest/java`, where `check` depends on the suite and each suite has its own dependencies; the manual's integration-test section describes it and xref:programming-languages/jvm-build-tools/migrating-between-tools.adoc[Migrating Between Tools] shows a complete example. Failsafe keeps the build alive until `verify`; a Gradle suite fails the build unless `ignoreFailures` is set. Cleanup that must always run goes into a task attached with `finalizedBy`. See xref:programming-languages/jvm-build-tools/gradle/testing-jvm-projects.adoc[Testing JVM Projects], xref:programming-languages/jvm-build-tools/maven/testing-with-surefire.adoc[Testing with Surefire] and xref:programming-languages/jvm-build-tools/maven/integration-testing-with-failsafe.adoc[Maven Integration Testing with Failsafe].

The results were compared by reading the XML reports of the runs. Maven's Surefire reports are in `target/surefire-reports` and Failsafe's in `target/failsafe-reports`, and Gradle's are in `build/test-results/<task>`:

|1 test, 0 failures (`test`)

The conversion does not carry Maven plugins over; the manual's rule is to look at what a plugin does, not at how it does it. Plugins fall into four groups: those that Gradle does by itself, those with a counterpart plugin, those you do not need, and those you must rewrite.

=== Shade becomes Shadow

The `maven-shade-plugin` configuration of the CLI has a Gradle counterpart in the Shadow plugin, a third-party plugin that is maintained outside of Gradle. Version 9.6.1 was current on the Plugin Portal and was used for the run (with the other plugin of the catalog), and it applies to Java projects with the `shadowJar` task. The task is added to `assemble`, the classifier `all` is set like the Maven `shadedClassifierName`, the signature files are excluded like in the filter, and the main class goes into the manifest:

.Kotlin DSL: tidepool-cli/build.gradle.kts
[source,kotlin]
----
plugins {
    id("tidepool.java-conventions")
    alias(libs.plugins.shadow)
}

dependencies {
    implementation(project(":tidepool-engine"))
    implementation(libs.picocli)
}

// maven-shade-plugin -> the Shadow plugin
tasks.shadowJar {
    archiveClassifier = "all"
    manifest {
        attributes("Main-Class" to "io.tidepool.cli.Main")
    }
    exclude("META-INF/*.SF", "META-INF/*.DSA", "META-INF/*.RSA", "META-INF/versions/9/module-info.class")
}
----

.Groovy DSL: tidepool-cli/build.gradle
[source,groovy]
----
plugins {
    id 'tidepool.java-conventions'
    alias(libs.plugins.shadow)
}

dependencies {
    implementation project(':tidepool-engine')
    implementation libs.picocli
}

// maven-shade-plugin -> the Shadow plugin
tasks.named('shadowJar') {
    archiveClassifier = 'all'
    manifest {
        attributes('Main-Class': 'io.tidepool.cli.Main')

    exclude 'META-INF/*.SF', 'META-INF/*.DSA', 'META-INF/*.RSA', 'META-INF/versions/9/module-info.class'
}
----

== Verifying that the migration worked

The manual makes this the most important step: a Gradle build that produces the same outputs lets you switch with confidence. A good verification compares what is shipped, what is resolved and what is tested. All three were run on the tidepool build with the Maven build in `maven/` and the Gradle build in `kts/` and `groovy/`.

=== Artifacts

The JARs of the two builds were unpacked and compared entry by entry with `diff -rq` (the thin JARs of the three modules and the shaded JAR of the CLI):

[source,text]
----
--- tidepool-cli-1.0.0-all.jar
Files a/META-INF/MANIFEST.MF and b/META-INF/MANIFEST.MF differ
Only in a/META-INF/maven: io.tidepool
--- tidepool-cli-1.0.0.jar
Files a/META-INF/MANIFEST.MF and b/META-INF/MANIFEST.MF differ
Only in a/META-INF: maven
--- tidepool-engine-1.0.0.jar
Files a/META-INF/MANIFEST.MF and b/META-INF/MANIFEST.MF differ
Only in a/META-INF: maven
--- tidepool-model-1.0.0.jar
Files a/META-INF/MANIFEST.MF and b/META-INF/MANIFEST.MF differ
Only in a/META-INF: maven
----

(`a` is the Maven JAR and `b` the Gradle JAR.) Every class and the filtered `tidepool.properties` are byte-identical. There are only two differences, and both are expected. Maven adds `META-INF/maven/<group>/<artifact>/pom.xml` and `pom.properties` to every JAR; Gradle does not. And the manifests differ:

[source,text]
----
Manifest-Version: 1.0
Created-By: Maven JAR Plugin 3.5.1
Java-Version: 17
Build-Jdk-Spec: 26
Main-Class: io.tidepool.cli.Main
----

is the manifest of the Maven shaded JAR, and

[source,text]
----
Manifest-Version: 1.0
Main-Class: io.tidepool.cli.Main
Multi-Release: true
----

is the manifest of the Gradle `-all` JAR. Gradle's manifest has no `Created-By` and `Build-Jdk-Spec` entries. It does have `Multi-Release: true`, which Shadow writes because the shaded libraries declare it (the manifests of `commons-csv`, `commons-io`, `commons-codec` and `picocli` all contain `Multi-Release: true`). Both JARs contain the same `META-INF/versions` entries, but Maven's manifest does not declare the JAR as multi-release, which means the JVM reads those entries as ordinary files; this made no difference to the output of the program here. One more difference was found by the comparison and is worth recording: in this run, the `Main-Class` attribute set on the `shadowJar` task was also written to the manifest of the thin `tidepool-cli-1.0.0.jar` (removing the `manifest` block removed it from both JARs). It does not harm, but a library JAR that has a `Main-Class` is not what the Maven build produced. The manual makes the same point: small differences such as the contents of a manifest can break a deployment, so check the ones that your deployment depends on. The count of files in the `-all` JARs was 902 for Maven and 896 for Gradle, the six extra entries of Maven being the three `pom.xml` and the three `pom.properties` files.

The Groovy DSL build and the Kotlin DSL build produce the same JARs: the `-all` JAR and the thin JAR of the CLI were compared in the same way and were identical (after both had been built with `-Pci`).

Two consequences matter to the migration. First, consumers of the Gradle POM see `commons-csv` as a `runtime` dependency, because it was declared with `implementation`: a Maven project that compiled against Commons CSV through the engine's old `compile` scope no longer gets it on its compile classpath. That is the intended effect, but it is a change of the contract, and you should tell the consumers or keep `api` for the libraries whose types leak. Second, the POM does not carry the name, description, URL, licenses and developers that Maven Central requires; add them through `+publishing.publications.maven.pom { }+` (see xref:programming-languages/jvm-build-tools/gradle/publishing.adoc[Publishing] and xref:programming-languages/jvm-build-tools/maven/publishing-to-maven-central.adoc[Publishing to Maven Central]). == Both builds in the same directory

The two builds can live side by side for as long as needed. `pom.xml` and `settings.gradle(.kts)` do not interfere, the Maven output is in `target/` and the Gradle output in `build/`, and neither tool reads the other's files. Three precautions avoid surprises:

* Ignore both output directories (`target/`, `build/` and `.gradle/`) in version control.
* Give each build its own `-D` and `-P` conventions and test both in CI: run `mvn verify` and `./gradlew build` on the same commit, then compare the outputs as shown above. When the Gradle build is trusted, make it the build that releases, and remove the `pom.xml` files in a later commit.
* Do not use `mavenLocal()` or `publishToMavenLocal` to hand artifacts between the two builds unless a downstream Maven project requires them. A stale artifact in `+~/.m2+` is a typical cause of "it works on my machine" in a migration.

For the CI side see xref:programming-languages/jvm-build-tools/ci-and-ide-integration.adoc[CI & IDE Integration] and xref:programming-languages/jvm-build-tools/repositories-and-publishing-across-tools.adoc[Repositories & Publishing Across Tools].

== Classic mistakes

* *Trusting the converted build.* The generated build compiled for Java 8, did not select the JUnit Platform, dropped the profile, the filtering, the system properties, Failsafe and Shade, and wrote `api` for every dependency. Treat `gradle init` as the way to get the module list and the dependency coordinates, and review every file it wrote.
* *Passing `-Pci` and expecting a profile.* Nothing happens unless a script reads the property. Search the POMs for `<profile>` before you start and list the settings each profile changes.
* *Comparing only the build result.* A green `./gradlew build` says nothing about the version of `commons-io` that is on the classpath. Compare the dependency trees (mediation), the JAR contents and the POMs.
* *Leaving `mavenLocal()` as the first repository.* It resolves artifacts that no repository provides and hides missing publications.
* *Reading `project` in a task action.* The configuration cache rejects or warns about it; capture the value in a local variable (or a provider) while the task is configured.
* *Moving everything at once.* Converting the build, the layout and the CI pipeline in one change makes a failure impossible to diagnose. Convert the build first; keep the layout and the artifacts the same; change them later.
* *Forgetting that the wrapper is a file of the project.* `gradle init` writes a wrapper without a checksum. Add `distributionSha256Sum` and commit `gradle/wrapper/gradle-wrapper.jar` and the properties.
* *Expecting the same task order.* A Gradle build runs what the task graph requires, in an order that is only partly defined, and runs independent tasks in parallel with the configuration cache. Declare real dependencies (`dependsOn`, inputs and outputs), not sequences.

== Where the books are outdated

_Gradle in Action_ (Muschko, Manning 2014) covers the Ant and Maven migration in chapter 9, for Gradle 1.7. What it describes and what replaced it:

* *The `maven2gradle` tool.* The conversion of a POM is now the `pom` type of the `init` task of the Build Init plugin, whose implementation was inspired by `maven2gradle`; it also reads the effective POM, so it handles inheritance and `dependencyManagement`. The incubating `setupBuild` task of Gradle 1.x is the same `init` task.
* *The `compile`, `runtime`, `testCompile` and `testRuntime` configurations* in the converted dependency blocks, removed in Gradle 7.0. Use `implementation`, `api`, `compileOnly`, `runtimeOnly`, `testImplementation` and `testRuntimeOnly`.
* *The `maven` plugin and `uploadArchives`* for publishing and installing, removed in Gradle 7.0. Use `maven-publish` with `publish` and `publishToMavenLocal`.
* *Declaring dependency versions in `ext` properties* in the root build. Use a version catalog (stable since 7.4) or a platform.
* *Injecting configuration with `allprojects` and `subprojects`* from the root build. Use convention plugins in `build-logic`.
* *`+apply plugin: 'x'+`.* Use the `+plugins { }+` block.
* *`jcenter()` as the repository of the examples.* Removed in 9.0.0, and Bintray, which hosted JCenter, was shut down in 2021. Use `mavenCentral()`.

Source: https://docs.gradle.org/current/userguide/build_init_plugin.html#sec:pom_maven_conversion[Gradle User Manual: Build Init plugin, Maven conversion], https://docs.gradle.org/current/userguide/upgrading_version_6.html[Upgrading from 6.x to 7.0], https://docs.gradle.org/current/userguide/version_catalogs.html[Gradle User Manual: Version catalogs] and https://docs.gradle.org/current/userguide/upgrading_major_version_9.html[Upgrading to Gradle 9]
