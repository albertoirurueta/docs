This page is written against Gradle 9.8.1 (released on 7 October 2026) and the upgrade guides of the user manual as of 16 October 2026. Gradle 8.14.6 (released on 8 October 2026) is the last 8.x release and is the starting point of the main upgrade described here. Every example marked as run was executed
with the 9.8.1 wrapper on macOS (Apple silicon), in scratch copies of the *tidepool* build, once with `+*.gradle.kts+` files and once with `+*.gradle+` files wherever the syntax differs. The Gradle daemon ran on Oracle JDK 26 (`java version "26"`), the default JDK of the machine, except where
the text says that JetBrains Runtime 17.0.14 was used. A `gradle.properties` file in each scratch build set `org.gradle.jvmargs=-Xmx512m -Duser.language=en -Duser.country=US`, so that the messages are in English, and `org.gradle.java.installations.auto-download=false`, so that no JDK could be downloaded. The scratch directory is shown as `<work>`; the `+at ...+` stack
frame and `+(Run with --stacktrace ...)+` lines that follow each deprecation warning, the lines announcing the start of a daemon, and the long `Welcome to Gradle` text of the `help` task are left out of the listings. The examples are compatible with the configuration cache
and ran with `+--configuration-cache+` except where the text says otherwise: a configuration cache hit does not repeat the warnings that are printed while the build is configured, so every run that looks for deprecations ran with `+--no-configuration-cache+`.

*Gradle 8.14.x was not available here*, and no Gradle distribution was downloaded. Everything said about 8.14, and every difference between 8.14 and 9.x that was not observable on 9.8.1, comes from the official upgrade guides and release notes and is labelled "not run here". Three more things were not run: `+--scan+`
(publishing a Build Scan to a Develocity service requires accepting its terms of use), running Gradle 9 on a Java older than 17 (no such Java is installed) and any wrapper run that would download a distribution from `services.gradle.org`. The wrapper properties shown on this page are the official ones, with the `services.gradle.org` URL; the scratch builds
pointed the same wrapper at a local copy of the 9.8.1 archive.

An upgrade of a Gradle build is not one step. A Gradle release changes three things at once: the _engine_ that runs your build (the JVM it needs, the Kotlin and Groovy that compile your scripts, the defaults of the bundled plugins), the _API_ that your scripts and plugins call (deprecated in one release and removed in a later one), and the _behavior_ of tasks that you did not
change. The user manual answers with one upgrade guide per major line and a fixed procedure, and this page walks through the procedure, then through each guide that matters for a build that is on 8.14 today, then through the older majors, because the build files that Gradle users still find in books, blog posts and old repositories
(including the examples of _Gradle in Action_, which targets Gradle 1.7) stop working on 9.8.1 in specific, recognizable ways. The release history behind all of this is on
xref:programming-languages/jvm-build-tools/gradle/versions-compatibility-and-release-history.adoc[Gradle Versions, Compatibility & Release History]; this page is where each removal is explained and fixed. The `wrapper` task itself is described on
xref:programming-languages/jvm-build-tools/gradle/gradle-wrapper.adoc[Gradle Wrapper], the option `+--warning-mode+` on
xref:programming-languages/jvm-build-tools/gradle/command-line-interface.adoc[Gradle Command Line], the configuration cache on
xref:programming-languages/jvm-build-tools/gradle/configuration-cache-and-isolated-projects.adoc[Configuration Cache & Isolated Projects], and the other two tools' equivalents are in the last section: Maven's are on
xref:programming-languages/jvm-build-tools/maven/migrating-to-maven-4.adoc[Migrating to Maven 4] and
xref:programming-languages/jvm-build-tools/maven/maven-wrapper.adoc[Maven Wrapper], Ant's on xref:programming-languages/jvm-build-tools/ant/deprecations-and-migration.adoc[Ant: Deprecations & Migration].

== How Gradle versions and deprecations work

Since Gradle 9.0.0 the version number follows semantic versioning: `MAJOR.MINOR.PATCH`, where a major release may remove public APIs, a minor release adds features and deprecates others, and a patch release fixes bugs and vulnerabilities (9.8.1 is a patch release of 9.8.0 that closes three high-severity
vulnerabilities in the communication between client, daemon and workers, and in the handling of repositories that fail to establish an SSL connection). Before 9.0 the versions were `MAJOR.MINOR` (`8.14`) with the patch number appearing only when needed (`8.14.6`), and a "minor" release such as 7.3 or 8.2 could already contain large features.

The _feature lifecycle_ turns the numbering into a promise. A documented feature is *public*, and is not removed or changed incompatibly without first being *deprecated*; a deprecated feature keeps working, prints a warning when it is used, and "may be removed in the next major release"; the manual adds that deprecated features may be supported across
major releases but that this is not guaranteed. The deprecation messages of Gradle 9.8.1 state a target release in each message: "This will fail with an error in Gradle 10" for most, "scheduled to be removed in Gradle 11" for a few that were deprecated recently. The *incubating* state is the exception to the promise: an incubating
API may change in any release and the changes are listed in the release notes. The full lifecycle is explained on xref:programming-languages/jvm-build-tools/gradle/versions-compatibility-and-release-history.adoc#_the_feature_lifecycle[the versions page].

The consequence for upgrading is simple. A build that is free of deprecation warnings on the last minor release of a line (8.14.x) will, with very few exceptions, compile and run on the first release of the next line (9.0.0), and a build that is free of warnings on a 9.x release will run on every later 9.x release. Almost all upgrade pain comes
from skipping that discipline: from moving more than one major release at once, from ignoring the warning summary, or from plugins that use internal APIs.

The upgrade guides of the user manual have a naming scheme that is easy to misread. Each file `upgrading_version_N.html` covers the minor releases of line N _and_ the move from the last N.x to the first release of the next line; the move to Gradle 9.0.0 has a page of its own. The table lists them with the sections that this page uses.

== The upgrade procedure

The user manual gives the same four steps at the top of every upgrade guide, from the 4.x guide to the 9.x one, and they are the whole method. In the guide for moving to Gradle 9.0.0 they read:

. Run `+gradle help --scan+` and look at the _Deprecations_ view of the Build Scan; alternatively run `+gradle help --warning-mode=all+` to see the deprecations in the console, "though it may not report as much detailed information".
. Update your plugins, "because a major release can remove public APIs" and the newest version of a plugin is the most likely to be compatible.
. Run `+gradle :wrapper --gradle-version 9.0.0+` (or the version you are moving to).
. Run the project and debug any errors with the troubleshooting guide.

The guide for moving to 9.0.0 adds a precondition before the first step (for migrating within Gradle 8.x, read the older migration guide first), and the guide for the 9.x releases says the same about the 9.0.0 guide. The 4.x guide adds two more pieces of advice that remain good: move to the latest release of your current line before moving to the next major
one, because "Gradle 5.x will generate (potentially less obvious) errors if you try to upgrade directly to it", and do not upgrade Gradle and migrate to the Kotlin DSL at the same time, so that a failure has one cause. The flow, with the commands, is:

[mermaid]
----
flowchart TD
    start["Build is green on the current release"] --> latest["Move to the latest patch of the current minor, then to the last minor of the line (8.14.x)"]
    latest --> warn["help --warning-mode=all or help --scan: list deprecations"]
    warn --> fix["Fix every deprecation, update plugins to current releases"]
    fix --> clean{"Build free of deprecations and green?"}
    clean -->|"no"| warn
    clean -->|"yes"| wrap["wrapper --gradle-version N (twice)"]
    wrap --> run["Run the build, read errors with the troubleshooting guide"]
    run --> done{"Green?"}
    done -->|"no"| fix2["Fix, or use the guide for the target release"]
    fix2 --> run
    done -->|"yes"| ci["Commit the wrapper files, set --warning-mode=fail on CI"]
----

Source: https://docs.gradle.org/current/userguide/upgrading_major_version_9.html[Gradle User Manual: Upgrading from 8.x to 9.0.0], https://docs.gradle.org/current/userguide/upgrading_version_4.html#for_all_users[Upgrading from 4.x to 5.0, for all users] and https://docs.gradle.org/current/userguide/troubleshooting.html[Troubleshooting Builds]

=== Step 1: find the deprecations

By default Gradle prints the deprecation warnings of a build only as a one-sentence summary at the end of the build. That is useful as a signal, and useless as a list. This is the summary on 9.8.1 for a build that uses a deprecated Groovy DSL idiom (`+group 'io.tidepool'+`, the "space assignment" syntax) and `Project.getProperties()`; the build succeeds:

[source,text]
----
$ ./gradlew :child:help --warning-mode=summary --no-configuration-cache --console=plain
> Configure project :child
hello

> Task :child:help

Deprecated Gradle features were used in this build, making it incompatible with Gradle 10.

You can use '--warning-mode all' to show the individual deprecation warnings and determine if they come from your own scripts or plugins.

For more on this, please refer to https://docs.gradle.org/9.8.1/userguide/command_line_interface.html#sec:command_line_warnings in the Gradle documentation.

BUILD SUCCESSFUL in 1s
1 actionable task: 1 executed
----

`+--warning-mode+` selects what is printed: `summary` (the default, shown above), `all` (every warning, with the build file and line), `fail` (every warning, and the build fails if there was any) and `none`. The same choice can be made persistent with the Gradle property `org.gradle.warning.mode`, in `gradle.properties` or with `-D` on the command line,
and the command line wins over the file. With `fail` the same build prints each warning, and ends with a failure that names the first offending line of the build file:

[source,text]
----
$ ./gradlew :child:help --warning-mode=fail --no-configuration-cache --console=plain
> Configure project :child
Build file '<work>/child/build.gradle': line 2
Properties should be assigned using the 'propName = value' syntax. Setting a property via the Gradle-generated 'propName value' or 'propName(value)' syntax in Groovy DSL has been deprecated. This is scheduled to be removed in Gradle 10. Use assignment ('group = <value>') instead. Consult the upgrading guide for further information: https://docs.gradle.org/9.8.1/userguide/upgrading_version_8.html#groovy_space_assignment_syntax
Build file '<work>/child/build.gradle': line 3
The Project.getProperties method has been deprecated. This will fail with an error in Gradle 10. Consult the upgrading guide for further information: https://docs.gradle.org/9.8.1/userguide/upgrading_version_9.html#deprecated_get_properties
hello

> Task :child:help

[Incubating] Problems report is available at: file://<work>/build/reports/problems/problems-report.html

FAILURE: Build failed with an exception.

* Where:
Build file '<work>/child/build.gradle' line: 2

* What went wrong:
Deprecated Gradle features were used in this build, making it incompatible with Gradle 10

* Try:
> Run with --stacktrace option to get the stack trace.
> Run with --info or --debug option to get more log output.
> Run with --scan to get full insights from a Build Scan (powered by Develocity).
> Get more help at https://help.gradle.org.

BUILD FAILED in 1s
1 actionable task: 1 executed
[exit 1]
----

Each warning has the same anatomy, which is worth knowing because the target of the link is the upgrade guide. First the sentence of what was used; then when it stops working ("This will fail with an error in Gradle 10", or "scheduled to be removed in Gradle 11"); then the replacement; and last
the link to the section of the guide that explains the change, `+upgrading_version_9.html#deprecated_get_properties+` in the second warning above, followed by the place in the build ("Build file ...: line 3", or the `at` line that was left out of the listing). In a Kotlin DSL build the Kotlin compiler adds its own `w:` lines for the deprecated declarations before Gradle's message, as
the `by registering` delegates below show. The `at` line says which script or class made the call, and `+--stacktrace+` prints the whole stack of a warning, which is how a deprecation that is triggered by a plugin is traced to the plugin.

The run also wrote a report, and the output announced it (the line starting with `[Incubating] Problems report`, which the other listings of this page leave out): `build/reports/problems/problems-report.html` lists the deprecations and other problems of the build as an HTML page that can be opened without a Build Scan. The report is incubating in 9.8.1.

The second way is the Build Scan: `+gradle help --scan+` collects the same deprecations in a _Deprecations_ view that groups them by the plugin or script that caused them, with the stack trace and the link to the upgrade guide, which is why the guides recommend it first. Publishing a scan sends build data to a Develocity service and requires accepting its terms of use, so
`+--scan+` was *not run here*; the scan options are described on xref:programming-languages/jvm-build-tools/gradle/performance-profiling-and-build-scans.adoc[Performance Profiling & Build Scans].

Three rules make the output reliable. Run with `+--no-configuration-cache+`, or after changing a file of the build, because a configuration cache hit skips the configuration phase where most of the warnings are produced. Run the tasks that your CI runs, not only `help`, because a deprecation that is triggered by a task action (reading `Task.project`, for
example) is printed only when the task executes. Run the build of every included build and of `buildSrc` or `build-logic` too: they are separate builds and their warnings are reported with the others.

Source: https://docs.gradle.org/current/userguide/command_line_interface.html#sec:command_line_warnings[Gradle User Manual: Command-Line Interface, warnings], https://docs.gradle.org/current/userguide/build_scans.html[Build Scans] and https://docs.gradle.org/current/userguide/upgrading_major_version_9.html[Upgrading from 8.x to 9.0.0]

=== Step 2: update the plugins

A plugin is code that runs inside Gradle, so it breaks when the Gradle API it was compiled against changes. The 9.0.0 guide states the practical rule ("using the latest version of a plugin increases the likelihood that it is already compatible with the new major Gradle version") and lists, for plugins that Gradle knows about, floors below which a plugin is not supported by Gradle 9:

[cols="2,2,2",options="header"]
|===
|Plugin |Lowest supported on Gradle 8.x |Lowest supported on Gradle 9.x

|Kotlin Gradle Plugin
|1.6.10
|2.0.0

|Android Gradle Plugin
|7.3.0
|8.4.0 (and AGP 9.x from Gradle 9.6, see below)

|Gradle Enterprise plugin (now the Develocity plugin, `com.gradle.develocity`)
|3.0
|3.13.1; versions before 4.0 are deprecated from 9.6

|Plugins written with the Kotlin DSL and built with Gradle 9
|(built with 8.x: usable down to Gradle 6.8)
|usable only on Gradle 8.11 or newer (the first release that embeds Kotlin 2)

|Plugins written with the Groovy DSL and built with Gradle 9
|(built with 7.x or 8.x: usable down to Gradle 5.0)
|usable only on Gradle 7.0 or newer (the first with Groovy 3)
|===

Two of these rows matter beyond the table. An _Android_ project has to move AGP before it moves Gradle: AGP 8.4.0 is the floor for Gradle 9.0.0, and Gradle 9.6 removed internal classes of the Problems API that AGP 8.x used, so 9.6 and later need AGP 9.x (the failure mentions the removed type; staying on Gradle 9.5 is the other fix). A _plugin author_ who needs to support Gradle older than 8.11 must build the plugin with Gradle 8.x, because
the Kotlin 2.2 compiler of Gradle 9 rejects language versions below 1.8 and always writes Kotlin metadata version 2; the guide shows the `languageVersion` and `apiVersion` setting for an 8.x build and says it fails on Gradle 9. How to find the plugins a build uses and their versions: `./gradlew buildEnvironment` prints the build script classpath of each build, and the plugin versions of the
version catalog are in xref:programming-languages/jvm-build-tools/gradle/version-catalogs.adoc[Version Catalogs]. Third-party plugins that fail with a `NoSuchMethodError`, `NoClassDefFoundError` or "Could not find method" during configuration are the typical symptom of a plugin that uses an API Gradle removed; the fix is the plugin's own newest release, and if there is none, replacing the plugin.

Source: https://docs.gradle.org/current/userguide/upgrading_major_version_9.html#plugin_changes[Gradle User Manual: Upgrading to Gradle 9, plugin changes] and https://docs.gradle.org/current/userguide/upgrading_version_9.html#agp_8x_incompatible[Upgrading to 9.6, plugins relying on removed Problems API internals]

=== Step 3: update the wrapper

The wrapper is how the version of Gradle becomes part of the repository (see xref:programming-languages/jvm-build-tools/gradle/gradle-wrapper.adoc[Gradle Wrapper] for every key of `gradle-wrapper.properties`), so upgrading is running the `wrapper` task with the new version and committing the result. The manual recommends the task over editing `distributionUrl`,
because the task also refreshes the scripts and the JAR. The guides give the command as `+gradle :wrapper --gradle-version 9.0.0+`, and the wrapper chapter gives the pair that is needed to update the JAR as well:

[source,bash]
----
./gradlew wrapper --gradle-version 9.8.1 --gradle-distribution-sha256-sum <sha-256 of the -bin.zip> && ./gradlew wrapper
----

The first call runs with the old Gradle and rewrites `gradle-wrapper.properties`; the second runs with the new Gradle, which downloads it and writes the new `gradle-wrapper.jar` and scripts. When the properties file contains a `distributionSha256Sum` (a project that verifies its distribution has one) the task refuses to leave a stale checksum behind, so the new sum has to be passed with
`+--gradle-distribution-sha256-sum+`; the checksums of all releases are on https://gradle.org/release-checksums/[gradle.org/release-checksums]. Moving from 8.14.6 to 9.0.0 is the same command with `9.0.0`, and it was *not run here*, because it would download the distribution of 9.0.0 on the second call.

What could be run is the first half of the sequence with the installed 9.8.1: a scratch project whose properties file was written by hand to look like an older one (a 9.7.1 URL and its checksum) was upgraded with the installed `gradle` executable, so that nothing was downloaded, and with `+--no-validate-url+`, so that the task did not
contact the server:

[source,text]
----
$ gradle wrapper --gradle-version 9.8.1 --gradle-distribution-sha256-sum dce76f55f8e251a3a1f130eb120f30b3d271de2b76c9b0729d316b5a1b6dc01f --no-validate-url
> Task :wrapper

BUILD SUCCESSFUL in 1s
1 actionable task: 1 executed
Consider enabling configuration cache to speed up this build: https://docs.gradle.org/9.8.1/userguide/configuration_cache_enabling.html
----

The difference between the properties file before and after (`diff`, with `<` for the old file):

[source,text]
----
3,4c3,4
< distributionSha256Sum=acd53f1edaf02f1a8ff99879f8a34b302661a057d9b063ae9e35b552f804d20a
< distributionUrl=https\://services.gradle.org/distributions/gradle-9.7.1-bin.zip
---
> distributionSha256Sum=dce76f55f8e251a3a1f130eb120f30b3d271de2b76c9b0729d316b5a1b6dc01f
> distributionUrl=https\://services.gradle.org/distributions/gradle-9.8.1-bin.zip
6c6,8
< validateDistributionUrl=true
---
> retries=0
> retryBackOffMs=500
> validateDistributionUrl=false
----

The URL and the sum changed together, and the file gained `retries` and `retryBackOffMs` (the download retry settings, new in Gradle 9.5) and `validateDistributionUrl=false` from the `+--no-validate-url+` option; a normal run would have kept `true`, which makes the task check with a request that the URL exists. The scripts `gradlew` and `gradlew.bat` and the JAR were identical, because the old files in this
scratch project were already those of 9.8.1; moving from a real 8.14 wrapper would change them, which is why the second call is part of the procedure. After the second call `+./gradlew --version+` shows the new release and the four files (`gradlew`, `gradlew.bat`, `gradle/wrapper/gradle-wrapper.jar`, `gradle/wrapper/gradle-wrapper.properties`) are committed together.

Two details of the release history affect the move. The Windows start script was reworked in 9.5.0 (it no longer leaks environment variable changes into the invoked program, and a custom start script template or a batch file that calls `gradlew.bat` and relies on the "Terminate batch job" prompt must be reviewed); the 9.5 guide warns that upgrading the wrapper to the new script from a Gradle older than 8.14 can fail once, because `cmd.exe` re-reads
a script that has changed under it, and recommends going through 8.14 or 9.0.0 first. And since 9.4 the priority of system properties for a wrapper run follows the documented order (command line, then the Gradle user home `gradle.properties`, then the project's `gradle.properties`); before it, a property in the project file could override one given on the command line.

The JVM that runs the wrapper and the daemon is the other half of "which Gradle". Gradle 9.8.1 on JetBrains Runtime 17.0.14, the oldest Java that Gradle 9 supports for the daemon, with the same wrapper and no other change:

[source,text]
----
$ JAVA_HOME=<jbr-17.0.14>/Contents/Home ./gradlew --version

Revision:      39daf39feb60a18b1b6ddccde53366522fef516f

Kotlin:        2.4.10
Groovy:        4.0.33
Ant:           Apache Ant(TM) version 1.10.17 compiled on April 6 2026
Launcher JVM:  17.0.14 (JetBrains s.r.o. 17.0.14+1-b1367.22)
Daemon JVM:    ~/Library/Java/JavaVirtualMachines/jbr-17.0.14/Contents/Home (no Daemon JVM specified, using current Java home)

=== Step 4: run, then make CI keep the build clean

After the wrapper has been updated the build is run and the errors are read with the troubleshooting guide, which has sections for installation, dependency resolution, performance, attaching a debugger, tasks that rerun unexpectedly and IDE integration (see
xref:programming-languages/jvm-build-tools/gradle/best-practices-and-troubleshooting.adoc[Best Practices & Troubleshooting]). When a plugin turns out to be incompatible, and no newer release exists, staying on the last working Gradle for a while is a legitimate decision; going back is the same `wrapper` task with the old version.

Once the build is green, keep it green: a build that fails on a new deprecation is a build that is never surprised by a major release. In `gradle.properties`, for CI only through a CI-specific file or a `-D` argument, so that a developer who updates a plugin locally is not blocked by a warning that comes from it:

[source,text]
----
org.gradle.warning.mode=fail
----

The property worked as the command-line option did: a build with the property set failed on the deprecated `+group 'io.tidepool'+` with the same message as above, and `-Dorg.gradle.warning.mode=none` on the command line overrode it and the build succeeded.

[source,text]
----
$ ./gradlew :child:help --console=plain

== From Gradle 8.14 to 9.0.0

Gradle 9.0.0 (31 July 2025) is the breaking release of the current line: it is the first to require a newer Java to run, the first to embed Kotlin 2 and Groovy 4 for the build scripts, and the release that removed what had been deprecated in 7.x and 8.x. Everything in this section is in the guide
https://docs.gradle.org/current/userguide/upgrading_major_version_9.html[Upgrading from 8.x to 9.0.0]. The headline items, then the details with the runs:

[cols="2,5",options="header"]
|===
|Change |What it means for a build

|Java 17 or newer to run the daemon
|Gradle 8.14 runs on Java 8 to 24; Gradle 9 needs 17 or newer for the daemon. The code can still target older Java through toolchains.

|Kotlin 2.2 and Groovy 4
|Build scripts and plugins are compiled by a different compiler and language version.

|Plugin floors
|Kotlin Gradle Plugin 2.0.0, Android Gradle Plugin 8.4.0, Develocity plugin 3.13.1.

|Removed APIs
|`jcenter()`, the conventions (`sourceCompatibility`, `archivesBaseName` and others as project properties), `Project.exec` and `Project.javaexec`, the `+"name"()+` task reference in the Kotlin DSL, `-b` and `-c` on the command line, and more.

|Behavior changes without an error
|Reproducible archives by default, tasks that silently stop running tests, a `test` task that fails when it finds no tests, `assemble` no longer building artifacts of arbitrary configurations.

|Configuration cache
|The "preferred" mode: still off by default, but a task that is incompatible always discards the cache entry, and unsupported build event listeners fail the build.
|===

=== Java 17 to run Gradle

"Gradle 9.0.0 requires a Java Virtual Machine (JVM) version 17 or higher to run the Gradle Daemon." The change was announced in the 8.10 guide, and it is narrow. Gradle can still _compile_ for older Java (the guide says it keeps supporting compilation to Java 6 or later, and the Worker API, running tests on Java 8 and the Tooling API and TestKit clients remain compatible with Java 8); the _wrapper_ and the command-line launcher can start on Java 8, but they
then need a Java 17 or newer for the daemon, set with the Daemon JVM criteria, with `org.gradle.java.home`, or with `JAVA_HOME`. `+--no-daemon+` and `ProjectBuilder` in unit tests need Java 17 as well, since they run Gradle in the test JVM. This is why a CI image on Java 11 must change while the project can keep targeting Java 8 or 11:

* Put the Java that the build _targets_ in the build, with a toolchain (xref:programming-languages/jvm-build-tools/gradle/toolchains.adoc[Gradle Toolchains]): `+java { toolchain { languageVersion = JavaLanguageVersion.of(11) } }+`.
* Put the Java that _runs Gradle_ in the repository, with the Daemon JVM criteria (`gradle/gradle-daemon-jvm.properties`, created by `./gradlew updateDaemonJvm`, described on xref:programming-languages/jvm-build-tools/gradle/gradle-daemon.adoc[The Gradle Daemon]); the 9.2 release made that feature stable.

That Gradle 9.8.1 starts on JDK 17 was shown in step 3. Starting it on an older Java was *not run here*, as no such Java is installed. Java 27 became a supported daemon and toolchain Java in 9.8.0.

Plugins that still use the `javax.annotation` annotations continue to work. A related rule for plugin authors: `kotlinDslPluginOptions.jvmTarget` was removed, and the target of the compiled Kotlin follows the Java toolchain.

*Groovy.* Groovy 4 renamed packages (to satisfy the Java module system's split-package rule) and rewrote the parser, so Groovy build scripts that use classes such as `+groovy.util.*+` directly may need new imports. Four behavior changes need attention. First, a getter with an `is` prefix and a `Boolean` (not `boolean`) return type is no longer a property for Groovy 4; Gradle still treated such getters as properties
of its own types, announced the change as a deprecation in 8.13, and will drop it in Gradle 10. In a build script of your own:

[source,text]
----
* Where:
Build file '<work>/child/build.gradle' line: 2

* What went wrong:
A problem occurred evaluating project ':child'.
> No such property: enabled for class: Flag
----

The fix is a `get` method (or `boolean` as the type): the 8.13 guide shows keeping the old `isX` method with `@Deprecated` and `@ReplacedBy` and adding `getX`. Second, closures with the `DELEGATE_FIRST` strategy now look up dynamic properties and methods on the delegate before the owner, which can change what a bare name means inside `+with { }+` blocks (qualify with `owner.` or `this.`, or use `@CompileStatic`).
Third, closures defined in a parent class may no longer reach its private properties or methods from a subclass (a Groovy bug that stays until Groovy 5; the workaround is `@CompileStatic`). Fourth, plugins written in Groovy 3 that call `super` methods may fail at run time on Gradle 9, because Groovy 4 resolves super calls differently; rebuild such plugins with Gradle 9.

=== Behavior changes that do not fail

The dangerous changes of a major release are the ones that keep the build green. The 9.0.0 guide has several; each of the next three was reproduced.

*Archives are reproducible by default.* The tasks `Jar`, `War`, `Ear`, `Zip` and every `AbstractArchiveTask` now sort entries deterministically, give every file a fixed timestamp (1 February 1980 for ZIP-based archives; the exact value depends on the archive type) and permissions `0644`, and every directory `0755`. Before 9.0 the order depended on the file system and the times and
permissions were those of the files. The change helps builds that hash their outputs or compare them between machines (see xref:programming-languages/jvm-build-tools/supply-chain-security.adoc[Supply-Chain Security] and, for Maven's `project.build.outputTimestamp`, xref:programming-languages/jvm-build-tools/maven/security-and-reproducible-builds.adoc[Maven Security & Reproducible Builds]), and surprises builds that read the time or the permissions back, such as a distribution whose scripts must be executable. Restoring the old behavior is
per property, or for permissions with the Gradle property `org.gradle.archives.use-file-system-permissions=true`. Two source files with different permissions and times (shown with `stat`), zipped by two tasks, one with the new defaults and one restoring the old behavior:

[source,text]
----
$ stat -f '%Sp %Sm %N' -t '%Y-%m-%d %H:%M' files/*
-rw-r----- 2022-05-06 07:08 files/alpha.txt
-rw------- 2020-01-02 03:04 files/zeta.txt
----

.Kotlin DSL: build.gradle.kts
[source,kotlin]
----
val reproducible = tasks.register<Zip>("reproducibleZip") {
    from("files")
    archiveFileName = "reproducible.zip"
    destinationDirectory = layout.buildDirectory.dir("out")
}

val legacy = tasks.register<Zip>("legacyZip") {
    from("files")
    archiveFileName = "legacy.zip"
    destinationDirectory = layout.buildDirectory.dir("out")
    isReproducibleFileOrder = false
    isPreserveFileTimestamps = true
    useFileSystemPermissions()
}
----

.Groovy DSL: build.gradle
[source,groovy]
----
tasks.register('reproducibleZip', Zip) {
    from 'files'
    archiveFileName = 'reproducible.zip'
    destinationDirectory = layout.buildDirectory.dir('out')
}

tasks.register('legacyZip', Zip) {
    from 'files'
    archiveFileName = 'legacy.zip'
    destinationDirectory = layout.buildDirectory.dir('out')

[source,text]

The other changes of this kind, in the order of the guide:

* *`assemble` stops building artifacts of arbitrary configurations.* The `assemble` task used to build the artifacts of every configuration whose `visible` flag was not false, and the `archives` configuration collected them. Both were removed in 9.0; a custom artifact now needs `+tasks.named("assemble") { dependsOn(theArtifactTask) }+`. The `archives` configuration (deprecated for artifact declaration in 9.1) and `Configuration.visible` (deprecated, to be
removed in Gradle 11) remain only as deprecated shells.
* *Packaging plugins combine.* The `ear` and `war` plugins no longer suppress each other and the `jar`: applying `java`, `war` and `ear` builds a JAR, a WAR and an EAR with `assemble`.
* *Stale class files outside the build directory are no longer deleted*, a special case of source set outputs that forced every compile task to be created eagerly.
* *The signing plugin* writes OpenPGP signatures that match the version of the key (RFC 9580, version 6 keys); before 9.0 it always wrote version 4 signatures.
* *Gradle Module Metadata that is modified after an eagerly created publication* is an error instead of a warning.
* *`ValidatePlugins` needs the toolchain plugin* (`jvm-toolchains`, applied by every JVM plugin) and, since 9.2, a Java version that the daemon supports.
* *The default versions of the bundled tools* moved: Checkstyle 10.24.0, CodeNarc 3.6.0, PMD 7.13.0, JUnit Jupiter 5.12.2, TestNG 7.11.0, Spock 2.3 and Eclipse JGit 7.2.1. A new Checkstyle or PMD version brings new rules, so a quality gate that was green can turn red without a source change; pin the tool version (`toolVersion`) while upgrading and move it afterwards as a separate step.
* *`JavaExec` uses the toolchain of the `java` extension* when `java-base` is applied (announced in the 8.14 guide), where it used the Java of the daemon before. A build that sets no toolchain is unaffected; a build that does, and runs a `JavaExec` or the `run` task, now runs on the toolchain's Java.
* *Project directories must exist.* An `include` of a project without a directory (or with a read-only one) fails. Deprecated in 8.5, an error from 9.0:

=== The configuration cache in Gradle 9

Gradle 9.0.0 does not turn the configuration cache on by default (that is announced for Gradle 10), but it makes it the preferred mode and tightens three things that matter to a migration. An unsupported provider passed to `BuildEventsListenerRegistry.onTaskCompletion` used to be silently dropped when the cache was on and is now a configuration cache problem that fails the build; the property
`org.gradle.configuration-cache.unsafe.ignore.unsupported-build-events-listeners=true` restores the old behavior for now and will be removed in Gradle 10. A cache entry is always discarded when the work graph contains a task marked incompatible, even in the `warn` problems mode, which used to store it. Two entries in the table are not what a reader expects, and both could be reproduced. The 9.6 guide, "implicit lookup of properties in parent projects", is the deprecation with the widest effect, because a build that stores a shared value as an extra property (`extra["greeting"]`, `+ext.greeting+`) of the root project and reads it by its bare name in a subproject has been doing the same thing for ten years. And "Kotlin DSL delegated
properties" deprecates, in one go, the forms `+val x by tasks.registering+`, `+val x: String by project+`, `+val x by extra+` and the delegates of `Property`, so a large part of the Kotlin DSL code written between 5.0 and 9.5 produces warnings.

== The older majors: 4 to 8

An old build rarely sits on 8.14. Builds copied from books and blog posts sit on 1.x to 4.x, and the practical question is what a 4.x build needs. The upgrade guides were written one hop at a time, and the supported way to move is to follow them one hop at a time: first to the last release of the old line, then to the next major, using the deprecation warnings of the old line to find the changes. The table lists, for each hop, the changes that
a build file written in the style of the Gradle 1.x and 2.x era notices first (the guides list many more).

[cols="1,4",options="header"]
|===
|Hop |Changes that break typical build files

|4.10 to 5.0 (2018-11-26)
|Gradle 5 needs Java 8 to run (4.x needs Java 7). `+task name << { }+` no longer works; use `doLast`. The `+publishing { }+` block is no longer evaluated lazily. Dependencies declared by a POM are separated into compile and runtime scopes. Implicit wildcards in POM exclusions are honored. Annotation processors are added through the `annotationProcessor` configuration. Memory defaults of the client, daemon and workers were greatly reduced. `+enableFeaturePreview('IMPROVED_POM_SUPPORT')+`
and `+'STABLE_PUBLISHING'+` are no longer needed (they became the default). The release added the Kotlin DSL 1.0, native BOM import (`platform()`), the Worker API and `tasks.register`.

|5.6 to 6.0 (2019-11-08)
|The FindBugs, JDepend, OSGi, announce and build-announcements, and Compare Gradle Builds plugins are removed. Dependencies should no longer be declared using the `compile` and `runtime` configurations (deprecated). The legacy publication system (the `maven` plugin and `uploadArchives`) is deprecated in favor of `maven-publish` and `ivy-publish`. Gradle Module Metadata is always published, with stricter validation. Maven or Ivy repositories are no longer queried for artifacts without
metadata by default. `buildSrc` is reserved as a project name. Executing Gradle without a settings file and calling `afterEvaluate` on an evaluated project are deprecated (errors in 7.0).

|6.9 to 7.0 (2021-04-09)
|The `compile`, `runtime`, `testCompile` and `testRuntime` configurations are removed (use `implementation`, `api`, `runtimeOnly`, `testImplementation`, `testRuntimeOnly`; a Groovy `extendsFrom runtime` silently creates a configuration named `runtime` instead of failing). The `maven` plugin and `uploadArchives` are removed. `jcenter()` is deprecated. The experimental JavaScript plugins (`coffeescript-base`, `envjs`, `javascript-base`, `jshint`, `rhino`), the Play plugins and the unmaintained JVM
plugins are removed. Groovy 3. Executing a build without a settings file, and calling `afterEvaluate` on an evaluated project, are errors. Dependency locking defaults to a single file per project.

|7.6 to 8.0 (2023-02-13)
|Warnings that became errors: referencing tasks of an included build with `finalizedBy`, `mustRunAfter` or `shouldRunAfter`; invalid Java toolchain specifications; automatic toolchain download without a repository; changing the test framework after setting its options. Removed legacy APIs: the old `ArtifactTransform`, `IncrementalTaskInputs`, `JacocoMerge`, and many API clean-ups. Plugin, task and extension classes are abstract; the lowest supported Kotlin and
Android plugins were raised. Kotlin 1.8.

|8.14 to 9.0.0
|The previous section.
|===

The first column's dates are the release dates from the release history. For 4.10 to 5.0, the guide for the 4.x line has the sentence that sums up why a direct jump is risky and what to do instead: upgrade to the latest 4.10.x release first "to get the most useful warnings and deprecations information before moving to 5.0".

== Gradle in Action on Gradle 9.8.1

_Gradle in Action_ (Muschko, Manning 2014) targets Gradle 1.7 and the Groovy DSL, and it is still a good book about the model: projects, tasks, the lifecycle, configurations and the Tooling API did not change in kind. What changed is the syntax and the plugin set around them, and the changes can be traced to specific releases. This section takes the build of the book's style, shaped like the *tidepool* project, and runs it on 9.8.1 one error at a
time. The features the book teaches have their own pages in this section; here the question is only what a reader who types in the book's example finds out.

== Gradle, Maven and Ant

The three tools differ in what "version of the tool" means, and so in what an upgrade is.

[cols="2,3,3,3",options="header"]
|===
| |Ant |Maven |Gradle

|Pin the tool version in the repository
|No wrapper; the Ant on the path is used. Ant 1.10 needs Java 8 or later, and Ant 1.9, which ran on Java 5, has been end of life since 19 June 2024 (xref:programming-languages/jvm-build-tools/ant/deprecations-and-migration.adoc[Ant: Deprecations & Migration]).
|The Maven Wrapper: `mvn wrapper:wrapper -Dmaven=<version>` rewrites `.mvn/wrapper/maven-wrapper.properties` (xref:programming-languages/jvm-build-tools/maven/maven-wrapper.adoc[Maven Wrapper]).
|The `wrapper` task: `+./gradlew wrapper --gradle-version <version>+`, with `+--gradle-distribution-sha256-sum+` when the properties file has a checksum.

|What the new major needs to run
|1.10: Java 8.
|Maven 4: Java 17 (xref:programming-languages/jvm-build-tools/maven/migrating-to-maven-4.adoc[Migrating to Maven 4]).
|Gradle 9: Java 17 for the daemon.

|How the old line tells you what breaks
|The release notes (WHATSNEW) and the list of deprecated tasks on the page linked above.
|The latest 3.x prints warnings about the model; Maven 3.9.16 warns where 3.10.0 fails, and Maven 4 can be made to fail on warnings (see the page on migrating to Maven 4).
|`+--warning-mode=all+` and the Build Scan deprecations view; `+--warning-mode=fail+` for CI.

|The tool that migrates the files
|-
|`mvnup` (Maven 4).
|None for Gradle itself: the `wrapper` task changes the version, and the guides describe the changes to make by hand.
|===

The Gradle practice that stands out is the deprecation discipline: because the warnings carry the target release and a link, an upgrade can be planned as a task list. Moving a build between the tools is a different problem, covered on xref:programming-languages/jvm-build-tools/migrating-between-tools.adoc[Migrating Between Ant, Maven & Gradle], xref:programming-languages/jvm-build-tools/gradle/migrating-from-maven.adoc[Migrating from Maven] and xref:programming-languages/jvm-build-tools/gradle/ant-integration.adoc[Ant Integration].

== Checklist for an upgrade

. Commit a green build. Note the Gradle version (`+./gradlew --version+`), the Java of the daemon and the plugin versions (`./gradlew buildEnvironment`).
. Move to the last release of the current line (for 8.x, 8.14.6) and read its section in the upgrade guide.
. Run `+./gradlew <the tasks CI runs> --warning-mode=all --no-configuration-cache+`, and `+help --scan+` when the scan is allowed. Fix every warning, starting with the ones that your own scripts cause; update the plugins that cause the others.
. Run again with `+--warning-mode=fail+` until it passes. Run with `+--configuration-cache+` and fix the problems it reports.
. Make sure the daemon will have a Java the target Gradle supports (17 or newer for 9.x), and that toolchains say which Java compiles, tests and runs the code.
. Move the wrapper: `+./gradlew wrapper --gradle-version <target> --gradle-distribution-sha256-sum <sum>+`, then `./gradlew wrapper` again; check the `gradle-wrapper.properties` diff and commit the four wrapper files.
. Run the build and the tests. Compare the produced archives if you depend on their bytes, and check that every test task still runs tests.
. Pin the versions of the quality tools (Checkstyle, PMD, JaCoCo) until the upgrade has settled.
. Set `org.gradle.warning.mode=fail` (or `-Dorg.gradle.warning.mode=fail`) on CI so that the next deprecation is a failing build before it becomes an error.
. Do not migrate to the Kotlin DSL, a version catalog or a new plugin in the same change.
