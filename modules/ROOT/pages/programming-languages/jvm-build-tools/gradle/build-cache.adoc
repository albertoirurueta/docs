Every example was run through the Gradle wrapper on macOS with JDK 26 (Oracle `java version "26"`), which was both the JVM of the daemon and the JDK that compiled and tested the code, except in the one section that deliberately switches the JDK with a toolchain (JBR 21.0.10, found in the user's JDK directory; automatic JDK downloads were switched off with `org.gradle.java.installations.auto-download=false`). The commands are shown as `./gradlew <task>` and every recorded run also used `--console=plain`. The JVM default locale on the machine was Spanish; no output on this page has decimals, but the dates in two listings are printed in the Java default format. The remote cache examples talk to a toy HTTP cache node of 72 lines that was started on `127.0.0.1` for the run; its code is on this page. Develocity, the Gradle Docker cache node and HTTPS were not run here, and Gradle 8.14.x was not installed, so everything said about 8.14 comes from the official documentation and is labelled "not run here".

Gradle can skip a task in two ways. The first is the up-to-date check: if the inputs and outputs of the task are the same as in the previous execution in the same workspace, the task is skipped with the outcome `UP-TO-DATE` (see xref:programming-languages/jvm-build-tools/gradle/incremental-build.adoc[Gradle Incremental Build]). That memory is short: it holds the last execution of each task and nothing else, so switching a branch back and forth, running `clean`, or building the same commit in a second checkout all start from scratch. The second way is the *build cache*: Gradle stores the outputs of a task under a key computed from everything that influences them, and any later build, in any directory on the machine or, with a remote cache, on any machine, that computes the same key unpacks the stored outputs instead of running the task. That outcome is `FROM-CACHE`. The Ant answer to this problem is a time-stamp comparison that the build author writes (see xref:programming-languages/jvm-build-tools/ant/conditions-and-control-flow.adoc[Ant Conditions & Control Flow]) and nothing that outlives the workspace; the Maven answer is an optional core extension, the Apache Maven Build Cache Extension (see xref:programming-languages/jvm-build-tools/maven/build-performance-cache-parallel-and-mvnd.adoc[Maven Build Performance]). The shared vocabulary is on xref:programming-languages/jvm-build-tools/build-automation-fundamentals.adoc[Build Automation Fundamentals]. The reason why Gradle can do this reliably is the model described on xref:programming-languages/jvm-build-tools/gradle/tasks.adoc[Gradle Tasks] and xref:programming-languages/jvm-build-tools/gradle/writing-custom-tasks.adoc[Writing Custom Tasks]: every task declares what it reads and what it writes.

== Four caches that are easily confused

Gradle has several things called a cache, and the build cache is only one of them. Most of the confusion about "the cache" in a Gradle question comes from mixing them up.

[cols="2,3,3,3",options="header"]
|===
|Cache |What it stores |Where |Page
|Up-to-date history |The fingerprints of the inputs and outputs of the last execution of each task |`.gradle/` in the project |xref:programming-languages/jvm-build-tools/gradle/incremental-build.adoc[Incremental Build]
|*Build cache* |The *outputs* of cacheable tasks, under a key computed from their inputs |`$GRADLE_USER_HOME/caches/build-cache-1` (local) and an optional HTTP node (remote) |This page
|Configuration cache |The result of the configuration phase (the task graph) |`.gradle/configuration-cache` in the project |xref:programming-languages/jvm-build-tools/gradle/configuration-cache-and-isolated-projects.adoc[Configuration Cache & Isolated Projects]
|Dependency cache |Downloaded modules and their metadata (`modules-2`) |`$GRADLE_USER_HOME/caches/modules-2` |xref:programming-languages/jvm-build-tools/gradle/dependency-locking-verification-and-caching.adoc[Dependency Locking, Verification & Caching]
|===

The build cache is the only one of the four that is shared between checkouts and, if you configure a remote node, between machines; it is also the only one that can make a wrong result appear (a cache hit for a task whose inputs were not fully declared), which is why most of this page is about declaring inputs correctly.

== Release history

Task output caching arrived in 2017 as an incubating feature and has been stable since the 4.x series; its configuration and its cleanup changed since. The dates are those of the Gradle versions list; the changes are from the release notes and upgrade guides of each version.

[cols="2,5",options="header"]
|===
|Release (date) |Change
|3.3 (2017-01-03) |Task output properties get unique names, which prepares Gradle for the build cache that followed.
|3.5 (2017-04-10) |The build cache is introduced as an incubating feature: a local directory cache and a remote HTTP cache, task output caching.
|4.0 (2017-06-14) |*Production-ready* for Java and Groovy compilation and Java test tasks; overlapping task outputs disable caching; configurable input normalization (ignore runtime classpath resources); the remote cache honours `--offline`; automatic cleanup of the local cache.
|4.5 (2018-01-24) |Included builds of a composite share the build cache configuration of the root build; C/C++ compilation caching stable; the ANTLR task becomes cacheable.
|5.0 (2018-11-26) |`buildSrc` builds use the build cache configuration of the top-level settings; the local cache must be a `DirectoryBuildCache`; the JaCoCo plugin works with the build cache.
|6.0 (2019-11-08) |Announced deprecation warning for pulling cache hits from a remote cache over insecure HTTP; tasks with incorrectly declared inputs or outputs are called out during the build.
|7.0 (2021-04-09) |A task that fails input/output validation runs without parallel execution, up-to-date checks and the build cache.
|8.8 (2024-05-31) |Cleanup of the local cache is configured like the other caches of the Gradle User Home, in an init script (`+caches { buildCache.setRemoveUnusedEntriesAfterDays(...) }+`); `Cleanup.DISABLED` and `Cleanup.ALWAYS` apply to it; the remote cache is disabled for Groovy build script compilation (introduced in 8.7).
|9.0.0 (2025-07-31) |`buildCache.local.removeUnusedEntriesAfterDays` (deprecated in 8.8) and the `org.gradle.cache.cleanup` property are removed.
|9.7.0 (2026-08-06) |Kotlin DSL accessor generation is no longer stored in the build cache.
|===

== How a cached task execution works

When a task is about to execute, Gradle goes through the steps of the figure. The up-to-date check comes first and is purely local; the build cache is consulted only for a task that is not up to date, and only if the cache is enabled and the task is cacheable.

[mermaid]
----
flowchart TD
  start["Task is selected for execution"] --> utd{"Inputs and outputs equal to the last execution?"}
  utd -- "yes" --> uptodate(["UP-TO-DATE"])
  utd -- "no" --> cacheable{"Build cache enabled, task cacheable, no doNotCacheIf predicate true?"}
  cacheable -- "no" --> run
  cacheable -- "yes" --> key["Compute the build cache key from the task implementation, the action implementations, the input property values, the normalized input files and the output property names"]
  key --> local{"Entry for the key in the local cache?"}
  local -- "yes" --> hit(["FROM-CACHE: unpack the outputs"])
  local -- "no" --> remote{"Remote cache enabled and entry for the key found?"}
  remote -- "yes" --> download["Download and unpack the outputs, keep a copy in the local cache"]
  download --> hit
  remote -- "no" --> run["Execute the task actions"]
  run --> store["Store the outputs in every enabled cache whose push setting is true"]
----

Source: https://docs.gradle.org/current/userguide/build_cache.html#sec:build_cache_configure[Gradle User Manual: Configure the Build Cache], https://docs.gradle.org/current/userguide/build_cache_concepts.html#build_cache_key[Build cache key], https://docs.gradle.org/current/userguide/more_about_tasks.html#sec:task_outcomes[Task outcomes]

Three consequences follow from the figure and are worth keeping in mind. A task that is cached is still *skipped for its actions*, so anything it did as a side effect (printing, registering, writing outside its declared outputs) does not happen. A cache hit replaces the outputs on disk, so the result is the same as an execution if, and only if, the inputs were declared completely. And the order of the lookups matters for cost: local first, then remote, and an entry found remotely is copied into the local cache, so the second time it is found locally.

== Enabling the build cache

The build cache is off by default. There are two switches, and the command line wins over the property.

[cols="3,5",options="header"]
|===
|Switch |Effect
|`--build-cache` |Use the build cache for this build only.
|`org.gradle.caching=true` in `gradle.properties` |Use the build cache for every build that reads the file (the project, or the Gradle User Home for all projects), unless `--no-build-cache` is given.
|`--no-build-cache` |Do not use the build cache in this build, whatever the property says.
|`-Dorg.gradle.caching.debug=true` |Print how the build cache key of each task was computed (see the debugging section).
|===

These are the only intended switches. Turning the cache on from build logic, with `gradle.startParameter.buildCacheEnabled = true` in a settings file or an init script, is deprecated since Gradle 9.8.0 and will be removed in Gradle 10 (not run here).

Source: https://docs.gradle.org/current/userguide/build_cache.html#sec:build_cache_enable[Gradle User Manual: Enable the Build Cache], https://docs.gradle.org/current/userguide/upgrading_version_9.html#deprecation_enabling_build_cache_from_build_logic[Gradle User Manual: Upgrading within Gradle 9.x.y, deprecation of enabling the Build Cache from build logic]

The first example is the one that the official documentation uses: a build without the cache, then with it. Without it, `clean` throws everything away and the next build recompiles and retests everything, even though nothing changed:

The listing shows the whole vocabulary of task outcomes. `FROM-CACHE` is the build cache hit: the compilation tasks of the projects (`compileJava`, and `compileTestJava` where there are tests), the two `test` tasks and the `javadoc` task came out of the cache and their sources were not even handed to `javac`. The summary line counts "8 executed, 8 from cache": eight of the sixteen actionable tasks were avoided.

The property form is what teams use, because every developer gets the cache without remembering a flag. `--no-build-cache` is the escape hatch:

[source,text]
----
$ cat gradle.properties
org.gradle.configuration-cache=true
group=io.tidepool
version=1.0.0
org.gradle.caching=true

$ ./gradlew clean build      # first build, stores
BUILD SUCCESSFUL in 889ms
20 actionable tasks: 16 executed, 4 up-to-date

$ ./gradlew clean build      # second build, no flag needed
BUILD SUCCESSFUL in 368ms
20 actionable tasks: 12 executed, 8 from cache

$ ./gradlew clean build --no-build-cache
BUILD SUCCESSFUL in 880ms
20 actionable tasks: 19 executed, 1 up-to-date
----

The official best-practices page recommends enabling the cache. Whether it also belongs in the *user's* `gradle.properties` rather than the project's is a policy decision: the project file turns it on for every contributor and for CI, which is usually what you want once the build is known to be cache-safe; the file in the Gradle User Home turns it on for one machine only.

Source: https://docs.gradle.org/current/userguide/build_cache.html#sec:build_cache_enable[Gradle User Manual: Enable the Build Cache], https://docs.gradle.org/current/userguide/best_practices_performance.html#use_build_cache[Best practices: Use the Build Cache], https://docs.gradle.org/current/userguide/build_cache_debugging.html#in-place_caching_test[Debugging: In-place caching with the local cache]

== The build cache key

The key is a 128-bit hash, written as 32 hexadecimal digits, computed for each cacheable task from the following ingredients. Two tasks whose keys are equal are the same function applied to the same arguments, whatever they are called and wherever they live.

[cols="3,5",options="header"]
|===
|Ingredient |What it covers
|The task implementation |The class of the task and the hash of the class loader that defined it (for a task class declared in a build script, the compiled script; for a plugin task, the plugin JAR). The Gradle version is part of this through the classpath of Gradle itself.
|The task action implementations |The classes of the actions added with `doFirst {}` and `doLast {}`, with the same class loader hash.
|The names of the output properties |`destinationDirectory`, `archiveFile`, `summary`, and so on, but not the output *paths*.
|The input properties |The names and the values (hashed) of the properties annotated with `@Input` and the like, and of those added with `+inputs.property(...)+`.
|The input files |The names of the file properties and the fingerprint of their content, normalized according to the declared path sensitivity or classpath normalization (see below).
|===

Two things are deliberately *not* in the key. The task path is not (the documentation says so explicitly), so `:tidepool-engine:stationSummary` and a task of another project can reuse each other's entries when everything else is the same; and the absolute location of the project is not, unless a property is declared with `ABSOLUTE` path sensitivity. Both are what make the cache useful across checkouts and also what make an incomplete declaration dangerous.

== Cacheable tasks

A task is cacheable only if its type opted in. The built-in tasks that did, according to the user manual, are these; all other built-in tasks are not.

[cols="2,5",options="header"]
|===
|Area |Cacheable tasks
|Java |`JavaCompile`, `Javadoc`
|Groovy |`GroovyCompile`, `Groovydoc`
|Scala |`ScalaCompile`, `ScalaDoc`
|Native |`CppCompile`, `CCompile`, `SwiftCompile`
|Testing |`Test`
|Code quality |`Checkstyle`, `CodeNarc`, `Pmd`
|JaCoCo |`JacocoReport`
|Other |`AntlrTask`, `ValidatePlugins`, `WriteProperties`
|===

The third-party picture has changed since the early days: the Android Gradle plugin (3.1 and later) and the Kotlin Gradle plugin (1.2.21 and later) both ship cacheable compilation tasks, so the cache works for them without extra code. For any other plugin, its documentation says whether its tasks are cacheable; the `--info` line `+Caching disabled for task ... because: Caching has not been enabled for the task+` is how you find out.

=== Why Copy, Jar and Zip are not cached

Tasks such as `Copy`, `Sync`, `Jar`, `Zip` and `Tar` are not worth caching: they move bytes from one place on the disk to another, which is usually faster than downloading a stored copy, and caching them would waste space. The annotation `+@DisableCachingByDefault(because = "...")+` documents that on a task class (the build can still override it with the runtime API, see below), and `@CacheableTask` opts in. A subclass does not inherit `@CacheableTask`; a custom task type is not cacheable until you say so. Test tasks are cacheable, and that has a consequence that the next section comes back to: a cached `test` is a test that was not run in this build.

Source: https://docs.gradle.org/current/userguide/build_cache.html#sec:task_output_caching_cacheable_tasks[Gradle User Manual: Built-in cacheable tasks], https://docs.gradle.org/current/userguide/build_cache.html#sec:task_output_caching_disabled_by_default[Marking tasks as non-cacheable by default], https://docs.gradle.org/current/userguide/build_cache_concepts.html#non_cacheable_tasks[Non-cacheable tasks]

=== Making a custom task cacheable

The *tidepool* engine gets a small custom task that counts the stations in the CSV file and writes the count. It has one input file and one output file. The first version declares both and nothing else; it is a perfectly good task for incremental builds:

.Kotlin DSL
[source,kotlin]
----
// tidepool-engine/build.gradle.kts
abstract class StationSummary : DefaultTask() {
    @get:InputFile
    abstract val stations: RegularFileProperty

    @get:OutputFile
    abstract val summary: RegularFileProperty

    @TaskAction
    fun summarize() {
        val rows = stations.get().asFile.readLines().drop(1).filter { it.isNotBlank() }
        summary.get().asFile.writeText("stations=${rows.size}\n")
    }
}

tasks.register<StationSummary>("stationSummary") {
    stations = rootProject.layout.projectDirectory.file("data/stations.csv")
    summary = layout.buildDirectory.file("station-summary.txt")
}
----

.Groovy DSL
[source,groovy]
----
// tidepool-engine/build.gradle
abstract class StationSummary extends DefaultTask {
    @InputFile
    abstract RegularFileProperty getStations()

    @OutputFile
    abstract RegularFileProperty getSummary()

    @TaskAction
    void summarize() {
        def rows = stations.get().asFile.readLines().drop(1).findAll { it.trim() }
        summary.get().asFile.text = "stations=${rows.size()}\n"
    }
}

tasks.register('stationSummary', StationSummary) {
    stations = rootProject.layout.projectDirectory.file('data/stations.csv')
    summary = layout.buildDirectory.file('station-summary.txt')
}
----

With the cache on, `--info` says that the task is not cacheable, which is the default for a custom type:

[source,text]
----
> Task :tidepool-engine:stationSummary
Caching disabled for task ':tidepool-engine:stationSummary' because:
  Caching has not been enabled for the task
Task ':tidepool-engine:stationSummary' is not up-to-date because:
  No history is available.
----

Adding `@CacheableTask` in front of the class is not enough, and Gradle does not let it pass silently. A cacheable task must say how each file input is *normalized*, that is, which part of the path and the content identifies the file, because otherwise the outputs cannot be reused between machines or between locations on the same machine. Both DSLs fail the build with a validation problem (the Groovy DSL names the type `StationSummary`, the Kotlin DSL `Build_gradle.StationSummary`):

[source,text]
----
* What went wrong:
A problem was found with the configuration of task ':tidepool-engine:stationSummary' (type 'Build_gradle.StationSummary').
Missing normalization
  Type 'Build_gradle.StationSummary' property 'stations' is annotated with @InputFile but missing a normalization strategy
    If you don't declare the normalization, outputs can't be re-used between machines or locations on the same machine, therefore caching efficiency drops significantly
    For more information, please refer to https://docs.gradle.org/9.8.1/userguide/validation_problems.html#missing_normalization_annotation in the Gradle documentation.
    Possible solution: Declare the normalization strategy by annotating the property with either @PathSensitive, @Classpath or @CompileClasspath.
----

The normalization is declared with `@PathSensitive` (or `@Classpath` / `@CompileClasspath` for classpaths). The property that holds the input file gets `@PathSensitive(PathSensitivity.ABSOLUTE)` first, the most conservative choice, which says that the whole path of the file matters; the section on relocatability below shows what that costs and fixes it.

Source: https://docs.gradle.org/current/userguide/build_cache.html#sec:enable_caching_of_non_cacheable_tasks[Gradle User Manual: Enable caching of non-cacheable tasks], https://docs.gradle.org/current/userguide/validation_problems.html#missing_normalization_annotation[Validation problems: Missing normalization]

=== The runtime API for tasks you cannot subclass

When the task is of a type you do not control (an `Exec`, a generic task of a plugin, an ad hoc task), the same information is declared with the runtime API: `outputs.cacheIf { true }` opts the task in, and `+inputs.file(...)+` and `+outputs.file(...)+` with `withPropertyName` and `withPathSensitivity` declare the inputs and outputs. The declarations have the same effect as the annotations; file inputs and outputs declared in a base class cannot be overridden this way, input properties can. The example is an ad hoc task with the same behaviour as the class above; it was run in both DSLs and was cached and restored:

.Kotlin DSL
[source,kotlin]
----
// tidepool-engine/build.gradle.kts
val stationCount = tasks.register("stationCount") {
    val stations = rootProject.layout.projectDirectory.file("data/stations.csv")
    val count = layout.buildDirectory.file("station-count.txt")

    inputs.file(stations)
        .withPropertyName("stations")
        .withPathSensitivity(PathSensitivity.NONE)
    outputs.file(count)
        .withPropertyName("count")
    outputs.cacheIf { true }

    doLast {
        val rows = stations.asFile.readLines().drop(1).filter { it.isNotBlank() }
        count.get().asFile.writeText("stations=${rows.size}\n")
    }
}
----

.Groovy DSL
[source,groovy]
----
// tidepool-engine/build.gradle
def stationCount = tasks.register('stationCount') {
    def stations = rootProject.layout.projectDirectory.file('data/stations.csv')

        .withPropertyName('stations')
        .withPathSensitivity(PathSensitivity.NONE)
    outputs.file(count)
        .withPropertyName('count')
    outputs.cacheIf { true }

    doLast {
        def rows = stations.asFile.readLines().drop(1).findAll { it.trim() }
        count.get().asFile.text = "stations=${rows.size()}\n"

}
----

The inverse is `outputs.doNotCacheIf("reason") { predicate }`, which disables caching for a task that is normally cacheable when the predicate is true. The classic use is a `Test` task that must run every time in some environments (a nightly build, a flaky suite, tests that read the clock). }
----

=== Logic in the build script is part of the key

The task implementation and the implementation of its actions are inputs, and for a task class or a `doLast` action defined in a build script, the "implementation" is the class loader of the whole *compiled script*. So an edit to an unrelated line of the script changes the key of every cacheable task that is defined in it, while the keys of tasks that Gradle itself defines (`compileJava`) stay as they are. The listing prints the keys of `stationCount` and `compileJava` in the engine, appends an unrelated task to the engine's build script, and prints them again:

[source,text]
----
$ ./gradlew stationCount compileJava --build-cache --info --rerun | grep "Build cache key"
Build cache key for task ':tidepool-engine:stationCount' is 284e3cc127aae31fac3a5ceab445e621
Build cache key for task ':tidepool-engine:compileJava' is 2903f2d7209d1b749fbeffefcfbcd51c
# ... after appending an unrelated task to the build script ...
Build cache key for task ':tidepool-engine:stationCount' is b2173322ff0e3c284ebf1de8a0c0e0e4
Build cache key for task ':tidepool-engine:compileJava' is 2903f2d7209d1b749fbeffefcfbcd51c
----

The key of the script's own task changed (the Groovy DSL run showed the same change, with different hashes), the compiler's did not. For anything cacheable that you write, put the code in a plugin in `build-logic` or `buildSrc` instead of in a script: the plugin JAR changes only when the plugin does. That is the design on xref:programming-languages/jvm-build-tools/gradle/convention-plugins-and-sharing-build-logic.adoc[Convention Plugins & Sharing Build Logic].

=== Overlapping outputs

If two tasks write to the same file or directory, Gradle cannot say which task a file belongs to and disables caching for the task that runs second (since Gradle 4.0). The example registers a second `StationSummary` task with the same output file:

[source,text]
----
$ ./gradlew stationSummary stationSummaryAgain --build-cache --info
> Task :tidepool-engine:stationSummary
Build cache key for task ':tidepool-engine:stationSummary' is e438eef3c73bb6b3c171b52ce97735b1
Task ':tidepool-engine:stationSummary' is not up-to-date because:
  No history is available.
--
> Task :tidepool-engine:stationSummaryAgain
Caching disabled for task ':tidepool-engine:stationSummaryAgain' because:
  Gradle does not know how file 'build/station-summary.txt' was created (output property 'summary'). Task output caching requires exclusive access to output paths to guarantee correctness (i.e. multiple tasks are not allowed to produce output in the same location).

In the Groovy DSL run the two tasks happened to be scheduled in the opposite order, so the task that was refused was `stationSummary` and the one that was stored was `stationSummaryAgain`; which is which depends on the scheduling. == The local build cache

The local cache is a `DirectoryBuildCache`, enabled by default once the build cache is on, with push enabled. Its entries are in `$GRADLE_USER_HOME/caches/build-cache-1` (see xref:programming-languages/jvm-build-tools/gradle/directories-and-logging.adoc[Directories & Logging] for the whole layout of the Gradle User Home). It is configured in `settings.gradle(.kts)`, the only place for build cache configuration; the three properties are in the table.

[cols="2,2,5",options="header"]
|===
|Property (Kotlin DSL / Groovy DSL) |Default |Meaning
|`directory` |`$GRADLE_USER_HOME/caches/build-cache-1` |Where the entries are stored.
|`isEnabled` / `enabled` |`true` |Whether the build *reads* from this cache.
|`isPush` / `push` |`true` for the local cache, `false` for a remote one |Whether the build *writes* outputs into this cache.
|===

In the Kotlin DSL the Boolean properties are named `isEnabled` and `isPush` (the Groovy DSL spells them without the prefix). The user manual's local-cache snippet writes `enabled` and `push` in the Kotlin DSL too; `push` was tried here and does not compile in 9.8.1 (`Unresolved reference 'push'`), and the Develocity documentation uses the `is` form. The example moves the cache into the project and makes it read-only, which is what a build agent that must not feed a shared cache would do:

.Kotlin DSL
[source,kotlin]

// settings.gradle.kts

    local {
        directory = File(rootDir, "build-cache")
        isPush = false
    }
}
----

.Groovy DSL

=== Cleanup

Entries that were not used for some time are removed, so the directory does not grow without bound. Since Gradle 8.8 the retention period and the switch are set like for the other caches of the Gradle User Home, in an init script in `$GRADLE_USER_HOME/init.d`; the default is 7 days since the last use (the `--info` line above says `remove unused entries = after 7 days`). `Cleanup.DEFAULT` runs the cleanup periodically in the background, `Cleanup.DISABLED` never, and `Cleanup.ALWAYS` at the end of every build in the foreground:

.Kotlin DSL
[source,kotlin]
----
// $GRADLE_USER_HOME/init.d/build-cache-cleanup.init.gradle.kts
beforeSettings {
    caches {
        buildCache.setRemoveUnusedEntriesAfterDays(1)
        cleanup = Cleanup.ALWAYS
    }
}
----

.Groovy DSL
[source,groovy]
----
// $GRADLE_USER_HOME/init.d/build-cache-cleanup.init.gradle
beforeSettings { settings ->
    settings.caches {
        buildCache.removeUnusedEntriesAfterDays = 1
        cleanup = Cleanup.ALWAYS
    }
}
----

----

== A remote HTTP build cache

A remote cache lets one machine reuse the work of another. Gradle ships a client for it, `HttpBuildCache`, and the protocol is almost nothing: a `GET` of `<url><key>` that answers `200` with the entry, or `404` when there is none; a `PUT` of the same URL that stores an entry (any `2xx` is success, a `413` means "too big" and is not an error). Any HTTP server that does this can be a cache node. When both caches are enabled, Gradle looks in the local cache first, then in the remote one, and copies a remote hit into the local cache; it *pushes* to every enabled cache whose push is true. The local cache pushes by default, a remote one does not.

[cols="2,2,5",options="header"]
|===
|Property (Kotlin DSL / Groovy DSL) |Default |Meaning
|`url` |none |Base URL of the node; the key is appended to it. Include the trailing slash.
|`isPush` / `push` |`false` |Write outputs to the node.
|`isEnabled` / `enabled` |`true` |Read from the node.
|`isAllowInsecureProtocol` / `allowInsecureProtocol` |`false` |Allow an `+http://+` URL (a man-in-the-middle could serve altered outputs).
|`isAllowUntrustedServer` / `allowUntrustedServer` |`false` |Disable the check of the server certificate (a security risk, a temporary measure).
|`isUseExpectContinue` / `useExpectContinue` |`false` |Ask the server whether it will accept the body before uploading it.
|`credentials { username; password }` |none |HTTP Basic authentication, sent preemptively.
|===

=== The recommended topology: CI pushes, developers pull

The official recommendation, and the one every serious setup converges to, is that a *continuous integration server populates the cache from clean builds, while developers only load from it*. A developer can change the inputs or the outputs of a task while it is executing, for instance by saving a file in the IDE while the build runs; Gradle has no defence against that and would cache whatever is in the output directory when the task finishes, which can poison the cache for everybody. A CI agent builds a pristine checkout and does not suffer from it. In the settings file that is one line:

.Kotlin DSL
[source,kotlin]
----
// settings.gradle.kts
val isCi = providers.environmentVariable("CI").isPresent

buildCache {
    remote<HttpBuildCache> {
        url = uri("http://127.0.0.1:5071/cache/")
        isAllowInsecureProtocol = true
        isPush = isCi
    }
}
----

.Groovy DSL
[source,groovy]
----
// settings.gradle
boolean isCi = providers.environmentVariable('CI').present

buildCache {
    remote(HttpBuildCache) {
        url = 'http://127.0.0.1:5071/cache/'
        allowInsecureProtocol = true
        push = isCi
    }
}
----

The URL points at a plain-HTTP node on the local machine because that is the only server these examples had; a real node uses an `+https://+` URL, and then `allowInsecureProtocol` is not set. The property is required for plain HTTP. The runs of this page did not show it because Gradle exempts loopback addresses from the check: with the node at `+http://127.0.0.1+` Gradle 9.8.1 accepted the URL with or without the property, also under `--warning-mode all`. A non-loopback `+http://+` URL without `allowInsecureProtocol = true` stops the build while the settings are evaluated (reproduced with the documentation address `+http://192.0.2.1:5071/cache/+`):

=== A toy cache node

To show the protocol and the topology without installing anything, the examples use this node: a `PUT` writes a file named by the key, a `GET` reads it, anything else is `404`. It can require HTTP Basic authentication (`--user`, the password is read from an environment variable and never printed) and it logs one line per request. It has no eviction, no TLS and no limits, so it is a teaching tool, not a cache for a team; for that see the next sections.

[source,python]
----
#!/usr/bin/env python3
"""A toy Gradle HTTP build cache node: GET and PUT of opaque entries, one file per cache key.

Not for production use: no eviction, no TLS and (unless --user is given) no authentication.
"""
import argparse
import base64
import hmac
import os
import sys
from http import HTTPStatus
from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer

parser = argparse.ArgumentParser()
parser.add_argument("--port", type=int, default=5071)
parser.add_argument("--dir", default="entries")
parser.add_argument("--user")
parser.add_argument("--password-env", default="CACHE_PASSWORD")
args = parser.parse_args()
os.makedirs(args.dir, exist_ok=True)
EXPECTED = None
if args.user:
    token = f"{args.user}:{os.environ[args.password_env]}".encode()
    EXPECTED = "Basic " + base64.b64encode(token).decode()


class Handler(BaseHTTPRequestHandler):
    def log_message(self, fmt, *a):
        pass

    def _key(self):
        key = self.path.rsplit("/", 1)[-1]
        return key if key.isalnum() else None

    def _authorized(self):
        if EXPECTED is None:
            return True
        return hmac.compare_digest(self.headers.get("Authorization", ""), EXPECTED)

    def _log(self, status, size):
        key = self.path.rsplit("/", 1)[-1]
        print(f"{self.command} {key} {status.value} {size}", flush=True)

    def _reply(self, status, body=b"", logged=None):
        self.send_response(status)
        self.send_header("Content-Length", str(len(body)))
        self.end_headers()
        self.wfile.write(body)
        self._log(status, len(body) if logged is None else logged)

    def do_GET(self):
        key = self._key()
        if not self._authorized():
            return self._reply(HTTPStatus.UNAUTHORIZED)
        path = os.path.join(args.dir, key or "")
        if key and os.path.isfile(path):
            with open(path, "rb") as f:
                return self._reply(HTTPStatus.OK, f.read())
        self._reply(HTTPStatus.NOT_FOUND)

    def do_PUT(self):
        key = self._key()
        length = int(self.headers.get("Content-Length", "0"))
        body = self.rfile.read(length)
        if not self._authorized():
            return self._reply(HTTPStatus.UNAUTHORIZED)
        with open(os.path.join(args.dir, key), "wb") as f:
            f.write(body)
        self._reply(HTTPStatus.CREATED, logged=len(body))


ThreadingHTTPServer(("127.0.0.1", args.port), Handler).serve_forever()
----

Starting it is `python3 -I cache_node.py --dir entries --port 5071`.

The script is this page's own setup, not an example taken from the manual; the protocol it implements is the one described in the manual.

=== Security of a shared cache

Whoever can write to the cache can make every other build run what they wrote: a cache hit is an executable result (a JAR, a class file) that never went through the compiler of the machine that uses it. So the push right deserves the same care as the right to publish an artifact. Push only from builds that run on trusted, clean, ephemeral agents from reviewed code (not from pull requests of forks); give the push credentials only to those, and give developers read-only access; use HTTPS; never use `allowUntrustedServer` in a build that is not a throw-away. The wider picture is on xref:programming-languages/jvm-build-tools/supply-chain-security.adoc[Supply-Chain Security for JVM Builds] and xref:programming-languages/jvm-build-tools/ci-and-ide-integration.adoc[CI and IDE Integration].

The build cache configuration of the *root* build applies to the whole composite: included builds, and `buildSrc` of the root and of the included builds, inherit it and their own settings are ignored (since 4.5 and 5.0). Plugin builds included with `+pluginManagement { includeBuild(...) }+` are the exception, because they are loaded before the cache is configured. == Relocatability and path sensitivity

A task is *relocatable* if its outputs can be reused when the same task runs somewhere else: in another directory, another user's home, another operating system. Whether it is depends on which paths the key contains. Every file input has a path sensitivity, declared with `@PathSensitive`:

[cols="2,5",options="header"]
|===
|`PathSensitivity` |The key contains
|`ABSOLUTE` |The full path of every file and directory. Not relocatable; this is also what you get for an input without declaration, and Gradle now insists that a cacheable task declare something.
|`RELATIVE` |The location relative to the root of the file collection (the source directory, for example). Relocatable.
|`NAME_ONLY` |Only the file name. Relocatable and tolerant of moved files.
|`NONE` |No path at all, only the content. Relocatable and tolerant of renames.
|===

The right value is the least sensitive one that is still correct: a task whose result depends on the file names (a compiler that derives class names from them) needs `NAME_ONLY` or `RELATIVE`; one that only reads the content, like `StationSummary`, needs `NONE`. The Java compiler's sources are `NAME_ONLY`/`RELATIVE`, as the documentation explains: only the relative path matters for incremental compilation, not where the project lives.

== Stable inputs and input normalization

A cacheable task needs *repeatable outputs* (running it twice on the same inputs produces the same files, otherwise what is stored and what is executed differ) and *stable inputs* (the same logical inputs produce the same key). The usual enemies of stable inputs are in the manual's list: a version number with a time stamp in a manifest, a commit hash written into a properties file, the output of another task that writes the time. A task consuming such data gets a new key on every build and is never served from the cache.

=== A volatile file on the runtime classpath

To see the effect, the model project gets a task that writes `build-info.txt` with the version and the time of the build into a generated resources directory that is added to the main source set's output. It is how many builds add a "built at" stamp:

=== Ignore it on the runtime classpath

The file is irrelevant for what the tests check. Gradle lets the *consumer* of the classpath say so with input normalization: `normalization { runtimeClasspath { ignore("build-info.txt") } }` removes the file from the fingerprint of every runtime classpath input of the project, for up-to-date checks and for the build cache alike. It does not change what the tests see; the file is still on the classpath. In a multi-project build the declaration is made where the tasks are, here for all projects from the root:

.Kotlin DSL
[source,kotlin]
----
// build.gradle.kts (root)
allprojects {
    normalization {
        runtimeClasspath {
            ignore("build-info.txt")
        }
    }
}
----

.Groovy DSL
[source,groovy]
----
// build.gradle (root)
allprojects {
    normalization {
        runtimeClasspath {
            ignore 'build-info.txt'
        }
    }
}
----

== Debugging cache misses

When a task that should have been `FROM-CACHE` was executed, the question is which input differed. The official guide gives a procedure that works because it narrows the search step by step:

. *Make the build correct without the cache first.* Run `clean` and the build twice without `--build-cache`; every task that produces files should be `UP-TO-DATE` the second time. A task that is not up to date in an unchanged workspace is a task with unstable inputs or outputs, and it will also miss in the cache (see xref:programming-languages/jvm-build-tools/gradle/incremental-build.adoc[Gradle Incremental Build] for how to find out why). Tasks with no outputs always run, which does not matter.
. *In-place test.* Empty the local cache, `clean`, build with `--build-cache`, `clean`, build again. Every cacheable task must be `FROM-CACHE` (the first listing of this page).
. *Relocation test.* Check the same commit out twice, build in one, `clean` and build in the other with the same local cache. Absolute paths among the inputs show up here (the `StationSummary` listing above). Run it with no remote cache configured and with push on.
. *Cross-platform test.* If developers and CI use different operating systems, populate a remote cache from one and consume it from the other; line endings, file permissions and the JDK distribution are the usual differences.
. *Incremental use.* Make typical changes (a comment, a method body, a new class, a dependency bump) and watch how much is still cached; if too little, restructure the project to reduce the dependencies between tasks.

For a single miss, collect the data in the order from coarse to fine: the build cache key; the implementation of the task and its actions (class names and class loader hashes); the names of the output properties; the hashes of the individual input properties; and the hashes of the files in the file inputs. `--info` gives the first, `-Dorg.gradle.caching.debug=true` gives all the others. The workflow with two builds is mechanical: save the debug output of both, strip the paths with `sed` if the locations differ, and `diff` them. The lines that differ are the answer.

[source,bash]
----
./gradlew clean :tidepool-engine:test --build-cache -Dorg.gradle.caching.debug=true > build-a.txt
./gradlew clean :tidepool-engine:test --build-cache -Dorg.gradle.caching.debug=true > build-b.txt
diff build-a.txt build-b.txt
----

Remember the cascade: if a task is not loaded from the cache and its outputs differ, every task that consumes them misses as well, so the miss to investigate is the *first* cacheable task that was executed, not the last. The causes found most often, each of which was reproduced on this page:

[cols="3,3,3",options="header"]
|===
|Cause |How it shows |Fix
|An input declared with `ABSOLUTE` path sensitivity |`+ABSOLUTE_PATH{...}+` in the debug line; the key differs between checkouts |`@PathSensitive(RELATIVE)`, `NAME_ONLY` or `NONE`
|A volatile file on the runtime classpath (time stamp, commit id, build number) |The hash of the JAR or directory in `stableClasspath` differs, the file differs |Do not write it into resources; or `+normalization { runtimeClasspath { ignore(...) } }+`
|The JDK differs |`javaVersion` and `javaCompiler.metadata.languageVersion` differ |Pin the JDK with a toolchain
|The build script changed |The implementation hash of a script-defined task differs, `compileJava` does not |Move the task into `build-logic` or a plugin
|An input property that holds a value of the environment (a system property, an environment variable, a host name) |A value fingerprint differs |Do not pass it to a cacheable task, or normalize it
|Overlapping outputs |`+Caching disabled ... multiple tasks are not allowed to produce output in the same location+` |Give each task its own output location
|A task that does not clean its outputs, so that stale files end up in the stored entry |A cached build behaves differently from a clean one |Make the task delete stale outputs (cache only clean builds until it does)
|===

A Develocity Build Scan removes the manual work: its *Build Scan Comparison* shows the inputs of the same task in two builds side by side, and its timeline lists the cacheable tasks that ran. Not run here; see xref:programming-languages/jvm-build-tools/gradle/performance-profiling-and-build-scans.adoc[Performance Profiling & Build Scans].

== Using the cache on a team

A sequence that has worked for many teams, in the order in which it reduces risk:

. *Local cache for everybody.* `org.gradle.caching=true` in the project's `gradle.properties`. A single developer already gains from branch switching and `git bisect`.
. *Make the build cache-safe.* Run the in-place and relocation tests above until every cacheable task is a hit; fix the declarations; put the build logic in `build-logic` so that script edits do not change keys.
. *Remote cache, CI only.* Start with the cache on CI agents, whose environment is stable, with the node reachable by them only. Push from CI after a `clean` build of a checked-out commit, never from a build that restores a previous workspace.
. *Developers pull.* Give developers read access to the node. The first build of the day, after pulling everybody's changes, is then mostly `FROM-CACHE` for everything that CI already built.
. *Keep the local cache* next to the remote one: on CI it mirrors the remote cache and saves network traffic, on a laptop it makes branch switching free.
. *Do not let developers push* until the build has proven that incremental builds are flawless. The cache exposes stale-output problems in tasks and plugins that incremental builds hide, which is useful, but until the build has been fixed only clean builds should upload.
. *Audit requirements.* If you must prove which build produced a shipped artifact, disable the cache for the release build, or use a service that records which build produced which entry.

The build cache accelerates *tasks*; it does not replace the dependency cache or the wrapper (a CI job still needs both, kept between jobs or restored from a CI cache), and it works together with parallel execution, the daemon and the configuration cache, which are the other items of the performance checklist on xref:programming-languages/jvm-build-tools/gradle/performance-profiling-and-build-scans.adoc[Performance Profiling & Build Scans] and xref:programming-languages/jvm-build-tools/gradle/best-practices-and-troubleshooting.adoc[Best Practices & Troubleshooting].

Source: https://docs.gradle.org/current/userguide/build_cache_use_cases.html#sec:speed_up_developer_builds_with_the_local_cache[Gradle User Manual: Speed up developer builds with the local cache], https://docs.gradle.org/current/userguide/build_cache_use_cases.html#share_results_between_ci_builds[Share results between CI builds], https://docs.gradle.org/current/userguide/build_cache_use_cases.html#sec:combine_remote_results_with_local_caching[Combine remote results with local caching], https://docs.gradle.org/current/userguide/build_cache_use_cases.html#sec:share_results_between_developers[Share results between developers]

== The same idea in Maven and Ant

[cols="2,3,3,3",options="header"]
|===
|Aspect |Gradle |Maven |Ant
|Mechanism |Built in: every task declares inputs and outputs; the key is computed from them |The Apache Maven Build Cache Extension 1.3.0, a core extension that keys a whole *module build* on its sources, dependencies and effective POM |None. |Unit cached |A task |A module (all the plugin executions that produced its output) |-

== Gradle 8.14 and later

What is on this page is the behaviour of 9.8.1; the differences with the 8.x line, from the release notes and upgrade guides (not run here, Gradle 8.14.x was not installed):

* The build cache itself, the key, the `@CacheableTask` rules and the HTTP protocol are the same in 8.14 and 9.8.1.
* Before 8.8 the retention of the local cache was set with `buildCache { local { removeUnusedEntriesAfterDays = n } }` and the cleanup ran every 24 hours; from 8.8 the init script `+caches { buildCache... }+` is the way, and the old property is deprecated; it is removed in 9.0.0 (the settings file then fails to compile).
* Gradle 8.7 stored Groovy build script compilation in the remote cache; 8.8 stopped doing that.
* Gradle 9.8.0 deprecated enabling the build cache from build logic (`gradle.startParameter.buildCacheEnabled = true` in a settings file or init script), with removal in Gradle 10; `--build-cache` and `org.gradle.caching` remain the switches.
* Gradle 9.7 stopped storing the Kotlin DSL accessor generation in the build cache; the log line `Build caching of Kotlin script accessor generation disabled by property` appears in `--info` output of 9.8.1.
* The configuration cache is the preferred mode since 9.0 (and announced as the default for Gradle 10); a task action that uses `Project` at execution time, such as the predicate in the failing example above, is incompatible with it. See xref:programming-languages/jvm-build-tools/gradle/configuration-cache-and-isolated-projects.adoc[Configuration Cache & Isolated Projects]. The upgrade path is on xref:programming-languages/jvm-build-tools/gradle/upgrading-gradle.adoc[Upgrading Gradle].

|`gradle.properties` for daemon and parallel options |`org.gradle.caching=true` is one more such property |https://docs.gradle.org/current/userguide/build_cache.html#sec:build_cache_enable[Enable the Build Cache]
|`allprojects` and `subprojects` to configure everything |Logic in scripts is part of the cache key; shared logic belongs in `build-logic` |https://docs.gradle.org/current/userguide/build_cache_concepts.html#build_cache_key[Build cache key]
|===

The two other books of the series have no counterpart: the Ant book's closest concept is `<uptodate>`, and the Maven 2 book predates the Maven Build Cache Extension.

== Summary

* The build cache stores the *outputs* of cacheable tasks under a key computed from the task implementation, its actions, the input values, the normalized input files and the names of the outputs. A hit is `FROM-CACHE`, and a task is only consulted after the up-to-date check fails.
* Enable it with `--build-cache` or `org.gradle.caching=true`; the local cache in `$GRADLE_USER_HOME/caches/build-cache-1` is cleaned up after 7 days of non-use by default, configurable in an init script.
* `Copy`, `Jar` and `Zip` are deliberately not cacheable; compilation, Javadoc and `Test` are. Custom tasks opt in with `@CacheableTask` and must declare a path sensitivity; ad hoc tasks use `outputs.cacheIf`.
* A remote HTTP cache is a `GET`/`PUT` node; let CI push (from clean builds) and let developers pull; credentials and TLS belong to the node, and the push right is a supply-chain right.
* Relocatability (`@PathSensitive`), stable inputs, input normalization, the JDK and the build script are what usually decide whether the cache works; `--info` and `-Dorg.gradle.caching.debug=true` plus `diff` find the input that differs.
