== From scopes to variants

Maven describes a component with one POM: a list of dependencies, each in a *scope*, plus optional classifiers on the
artifacts. Ivy describes it with *configurations*. Neither can say "this component has a variant for compiling, another
for running, a third that ships sample data, and a fourth for Java 8". Gradle can, because it models a published or
project component as a set of *variants*:

* a *component* is a module at a version (`io.tidepool:tidepool-model:1.0`);
* a *variant* is one way of consuming it: its own *attributes* (key-value pairs), its own *dependencies*, its own
  *artifacts* and its own *capabilities*;
* an *attribute* is a typed key such as `org.gradle.usage` with a value such as `java-api`;
* a *capability* is a `group:name:version` that the variant provides; by default it is the component itself.

A consumer does not ask for a configuration by name. It asks for *attributes* ("a library, for use at compile time, for
Java 26") and Gradle selects the variant of each dependency that matches. This is *variant-aware dependency resolution*,
the engine behind the Java plugins, Android, Kotlin Multiplatform and every other ecosystem plugin. The selection happens
twice: once for the dependency graph (which variant of each component) and once for the artifacts (which files of that
variant, possibly transformed).

Source: https://docs.gradle.org/current/userguide/variant_aware_resolution.html#sec:components_variants[Gradle User Manual: Variant-Aware Dependency Resolution, Components and variants]

The attributes that the JVM plugins set are the vocabulary the rest of this page uses.

[cols="3,3,4"]
|===
|Attribute |Typical values |Meaning

|`org.gradle.usage`
|`java-api`, `java-runtime`
|Compile-time API or runtime use. Second in the precedence order, after the category.

|`org.gradle.category`
|`library`, `platform`, `documentation`, `verification`
|What kind of thing the variant is. A BOM is a `platform`, the sources jar is `documentation`.

|`org.gradle.libraryelements`
|`jar`, `classes`, `resources`
|The shape of the artifacts: a jar or a directory of classes.

|`org.gradle.dependency.bundling`
|`external`
|Whether the dependencies are bundled in (a shadow jar) or external.

|`org.gradle.jvm.version`
|`17`, `26`
|The Java version the binaries target. A consumer on Java 26 accepts a variant built for Java 26 or lower.

|`org.gradle.jvm.environment`
|`standard-jvm`, `android`
|The kind of JVM.

|`org.gradle.docstype`
|`sources`, `javadoc`
|Which kind of documentation, for variants of category `documentation`.

|`org.gradle.status`
|`release`
|The component-level status, set on published metadata.
|===

Source: https://docs.gradle.org/current/userguide/variant_attributes.html#sec:standard-attributes[Gradle User Manual: Variant Attributes, Standard attributes]

Variants arrived in stages: Gradle Module Metadata 1.0 and feature variants in Gradle 5.3, test fixtures in 5.6, and
Gradle Module Metadata published by default in 6.0. The explicit configuration roles used below (`consumable`,
`resolvable`, `dependencyScope`) are the Gradle 8.4 API. Everything on this page behaves the same on Gradle 8.14 apart
from deprecations that are named where they matter (not run here).

Source: https://docs.gradle.org/5.3/release-notes.html#gradle-module-metadata-1.0[Gradle 5.3 Release Notes: Gradle Module Metadata 1.0], https://docs.gradle.org/5.6/release-notes.html#test-fixtures-for-java-projects[Gradle 5.6 Release Notes: Test fixtures for Java projects], https://docs.gradle.org/6.0/release-notes.html[Gradle 6.0 Release Notes], https://docs.gradle.org/8.4/release-notes.html#easier-to-create-role-focused-configurations[Gradle 8.4 Release Notes: Easier to create role-focused configurations]

== The example build

All the examples use one small three-project build with a *producer*, `tidepool-model`, and two consumers, `tidepool-engine`
and `tidepool-cli`. `tidepool-model` is a `java-library` that

* registers an optional feature, `csv`, in its own source set, with its own dependency on Apache Commons CSV;
* applies `java-test-fixtures`;
* declares two custom outgoing variants, `tideData` and `harmonicsData`, that carry sample data files and are told apart by
  a custom attribute, `io.tidepool.flavor`;
* publishes all of it to a `+file://+` repository under its own build directory with `maven-publish` and `ivy-publish`.

The sample data is `data/stations.csv` (the three stations of the tidepool example) and a second file,
`data/harmonics.csv`, with three rows of constituent speeds.

The settings file declares the repository once and fails the build when a project declares its own:

.Kotlin DSL (settings.gradle.kts)
[source,kotlin]
----
rootProject.name = "tidepool"

dependencyResolutionManagement {
    repositoriesMode = RepositoriesMode.FAIL_ON_PROJECT_REPOS
    repositories {
        mavenCentral()
    }
}

include("tidepool-model", "tidepool-engine", "tidepool-cli")
----

.Groovy DSL (settings.gradle)
[source,groovy]
----

dependencyResolutionManagement {

The producer, with the feature, the test fixtures, the two custom variants and the publications:

.Kotlin DSL (tidepool-model/build.gradle.kts)
[source,kotlin]
----
plugins {
    `java-library`
    `java-test-fixtures`
    `maven-publish`
    `ivy-publish`
}

group = "io.tidepool"
version = "1.0"

val flavor = Attribute.of("io.tidepool.flavor", String::class.java)

java {
    registerFeature("csv") {
        usingSourceSet(sourceSets.create("csv"))
        withSourcesJar()
    }
}

dependencies {
    "csvApi"("org.apache.commons:commons-csv:1.14.1")
}

// two custom outgoing variants, one per flavor of sample data
fun dataVariant(name: String, flavorName: String, file: String) =
    configurations.consumable(name) {
        description = "Sample data, flavor $flavorName"
        attributes {
            attribute(Category.CATEGORY_ATTRIBUTE, objects.named<Category>("tidepool-sample"))
            attribute(Usage.USAGE_ATTRIBUTE, objects.named<Usage>("tidepool-data"))
            attribute(flavor, flavorName)
        }
        outgoing.artifact(rootProject.file(file)) {
            classifier = flavorName
        }
    }

val tideData = dataVariant("tideData", "tides", "data/stations.csv")
val harmonicsData = dataVariant("harmonicsData", "harmonics", "data/harmonics.csv")

// publish the two data variants together with the library variants
val javaComponent = components["java"] as AdhocComponentWithVariants
javaComponent.addVariantsFromConfiguration(tideData.get()) { }
javaComponent.addVariantsFromConfiguration(harmonicsData.get()) { }

publishing {
    publications {
        create<IvyPublication>("ivy") {
            from(javaComponent)
        }
        create<MavenPublication>("maven") {
            from(javaComponent)
            suppressPomMetadataWarningsFor("csvApiElements")
            suppressPomMetadataWarningsFor("csvRuntimeElements")
            suppressPomMetadataWarningsFor("csvSourcesElements")
            suppressPomMetadataWarningsFor("testFixturesApiElements")
            suppressPomMetadataWarningsFor("testFixturesRuntimeElements")
        }
    }
    repositories {
        ivy {
            name = "localIvy"
            url = uri(rootProject.layout.buildDirectory.dir("ivy-repo"))
        }
        maven {
            name = "local"
            url = uri(rootProject.layout.buildDirectory.dir("repo"))
        }
    }
}

// -PnoGmm: stop publishing the .module file
if (providers.gradleProperty("noGmm").isPresent) {
    tasks.withType<GenerateModuleMetadata>().configureEach {
        enabled = false
    }
}
----

`+configurations.consumable(name) { ... }+` creates a configuration that can only be consumed (it declares outgoing
variants and cannot hold dependencies). It is the Gradle 8.4 replacement for the old
`configurations.create(name) { isCanBeResolved = false }` idiom. The Groovy version defines the helper as a closure
rather than as a method: a `def` variable of a Groovy script is not visible inside a script method, and the failure is
confusing, because `flavor` then silently resolves to the `-Pflavor` project property of the later examples and
`attribute(flavor, flavorName)` is called with two strings (`+No signature of method: ...attribute() is applicable for
argument types: (String, String)+`).

== The attribute matching algorithm

When a consumer's resolvable configuration meets a component, Gradle runs one algorithm over the candidate variants. In
the order of the manual:

[cols="1,5"]
|===
|Step |What happens

|1
|*Compatible candidates.* Each candidate attribute must be missing, equal to the requested value, or accepted by the
attribute's *compatibility rule*. A candidate with an incompatible value is eliminated. A candidate that lacks an attribute
the consumer asked for is *not* eliminated; it is marked as missing it.

|2
|*Most matching attributes.* If one candidate is a strict superset of the others (it matches more attributes, or has no
missing attributes compared to another), it wins.

|3
|*Disambiguation by requested attributes.* The requested attributes are visited in precedence order (category, usage,
`jvm.version`, `libraryelements`, `bundling`, `jvm.environment` for the JVM; then unordered ones); each attribute's
*disambiguation rule* may choose one candidate. An attribute that has the same value on all remaining candidates is
ignored.

|4
|*Extra attributes.* Attributes that only some candidates have (and the consumer did not ask for) are used to prefer the
candidates that lack them.

|5
|*Extra attribute presence.* As a last resort, candidates that carry an extra attribute are removed.

|6
|*Failure.* If no candidate remains, resolution fails with a *no matching variant* error that lists all candidates;
if several remain, with an *ambiguity* error.
|===

Two cases skip the algorithm: a producer with no variants (a plain artifact) and a consumer that selects a configuration
by name (`dependencies { implementation(project(":a", "someConfiguration")) }`).

Source: https://docs.gradle.org/current/userguide/variant_aware_resolution.html#sec:abm-algorithm[Gradle User Manual: Attribute matching algorithm]

=== Asking for sample data

`tidepool-cli` consumes the sample data of the model. The dependency is declared on a *dependency scope* configuration,
which cannot be resolved, and the resolvable configuration extends it and carries the requested attributes. The flavor is
taken from the `-Pflavor` property so that every case below can be run; `any` means "do not ask for a flavor at all". The
file is shown in full: the attribute rules in the middle are explained in the next sections, and so are the transform and
the `showRows` task at the end.

.Kotlin DSL (tidepool-cli/build.gradle.kts)
[source,kotlin]
----
import org.gradle.api.artifacts.type.ArtifactTypeDefinition.ARTIFACT_TYPE_ATTRIBUTE

plugins {
    application
}

dependencies {
    implementation(project(":tidepool-engine"))
    implementation("info.picocli:picocli:4.7.7")
}

application {
    mainClass = "io.tidepool.cli.Main"
}

val flavor = Attribute.of("io.tidepool.flavor", String::class.java)

// "tides-v2" may also be served by a "tides" variant
abstract class TidesFallback : AttributeCompatibilityRule<String> {
    override fun execute(details: CompatibilityCheckDetails<String>) {
        if (details.consumerValue == "tides-v2" && details.producerValue == "tides") {
            details.compatible()
        }
    }
}

// when no flavor is requested at all, prefer "tides"
abstract class PreferTides : AttributeDisambiguationRule<String> {
    override fun execute(details: MultipleCandidatesDetails<String>) {
        if (details.consumerValue == null && "tides" in details.candidateValues) {
            details.closestMatch("tides")

=== Compatibility and disambiguation rules

An attribute can carry two kinds of rule, registered in the *attributes schema* of the consumer build (or of the whole
build, in the settings file):

* a *compatibility rule* says that a producer value is acceptable for a different consumer value (`tides` for a request of
  `tides-v2`). It is called in step 1 and may call `compatible()` or leave the pair incompatible.
* a *disambiguation rule* chooses among several remaining candidates (step 3). It may call `closestMatch(value)`.

Both are abstract classes that Gradle instantiates itself. Classes declared in a Kotlin build script are accepted for
attribute rules, as the `TidesFallback` and `PreferTides` classes and the `attributesSchema` block of the `tidepool-cli`
build file above show; artifact transforms are stricter, see <<transforms>>.

With the rules, `-Pflavor=tides-v2` and `-Pflavor=any` print `data/stations.csv`, as in the listing above, and the rules
show up in the resolvable configurations report (`io.tidepool.flavor` is listed under both). The ecosystem plugins ship the
same kind of rules: it is why a consumer on Java 26 accepts a library built for Java 17 (`jvm.version`) and why a request
for `libraryelements = classes` accepts a `jar` variant, as the next output shows for the test fixtures.

Source: https://docs.gradle.org/current/userguide/variant_attributes.html#sec:abm-compatibility-rules[Gradle User Manual: Compatibility rules], https://docs.gradle.org/current/userguide/variant_attributes.html#sec:abm-disambiguation-rules[Gradle User Manual: Disambiguation rules], https://docs.gradle.org/current/userguide/variant_attributes.html#sec:creating-attributes[Gradle User Manual: Creating attributes]

== Artifact transforms

Sometimes the consumer wants the same variant in a different shape: the classes directory instead of a jar, the
instrumented jar, a checksum, a count. The producer cannot publish every shape, and the consumer should not have to run
a task for each. An *artifact transform* converts an artifact of one `artifactType` (or other attribute) to another
during resolution, and Gradle chains transforms when no single one matches. A transform is like a task: it has inputs
and outputs, it is cached and up to date like one, and it runs lazily, only for the artifacts that the consumer's view
requests.

The example turns the `csv` artifact of a data variant into a one-line file with its number of data rows. A transform is
an abstract class implementing `TransformAction`, with its input injected as a `Provider`:

.Kotlin DSL (buildSrc/build.gradle.kts)
[source,kotlin]
----
plugins {
    `kotlin-dsl`
}

repositories {
    mavenCentral()
}
----

.Kotlin DSL (buildSrc/src/main/kotlin/CountRows.kt)
[source,kotlin]
----
import org.gradle.api.artifacts.transform.InputArtifact
import org.gradle.api.artifacts.transform.TransformAction
import org.gradle.api.artifacts.transform.TransformOutputs
import org.gradle.api.artifacts.transform.TransformParameters
import org.gradle.api.file.FileSystemLocation
import org.gradle.api.provider.Provider
import org.gradle.api.tasks.PathSensitive
import org.gradle.api.tasks.PathSensitivity

/** Artifact transform: a csv file becomes a file holding its number of data rows. */
abstract class CountRows : TransformAction<TransformParameters.None> {
    @get:PathSensitive(PathSensitivity.NAME_ONLY)
    @get:InputArtifact
    abstract val input: Provider<FileSystemLocation>

    override fun transform(outputs: TransformOutputs) {
        val csv = input.get().asFile
        val rows = csv.readLines().size - 1
        outputs.file(csv.nameWithoutExtension + ".rows").writeText("$rows\n")
        println("transforming ${csv.name}")
    }
}
----

It is in `buildSrc` (or any included build) because of the first classic error. Written in the build script, the Kotlin
class is an inner class of the generated script class and Gradle refuses to register it:

[source,text]
----
$ ./gradlew -q :tidepool-cli:showRows
* What went wrong:
Could not register artifact transform Build_gradle.CountRows (from {artifactType=csv} to {artifactType=rows}).
> Class Build_gradle.CountRows is a non-static inner class.
----

In the Groovy DSL the same class worked when written in the build script; the only thing Groovy needed was the import
of `TransformParameters`, because the nested `None` is not in the default imports (`unable to resolve class
TransformParameters.None` otherwise). The best-practice location for shared build logic is an
included `build-logic` build instead of `buildSrc`, see
xref:programming-languages/jvm-build-tools/gradle/convention-plugins-and-sharing-build-logic.adoc[Convention Plugins & Sharing Build Logic].

The end of the `tidepool-cli` build file above registers the transform (`registerTransform`, from `csv` to `rows` on the
`artifactType` attribute) and reads the transformed files through an *artifact view* in the `showRows` task. In the
Groovy DSL the transform class is in the same file.

The task declares the view's files as its inputs. That is the second classic error: if the files are only read in the
action (`+dataPath.map { ... }.get()+` inside `doLast`), nothing tells Gradle that the producer project has to be built,
and the transform of a project artifact fails (`Could not access project ':tidepool-model'. No task declared this project
as part of an input, so it was not scheduled`). Declaring `inputs.files(rows)` fixed it, and the example is compatible with the configuration cache.

[source,text]
----
$ ./gradlew -q --configuration-cache :tidepool-cli:showRows -Pflavor=tides
transforming stations.csv
stations.rows: 3
$ ./gradlew -q --configuration-cache :tidepool-cli:showRows -Pflavor=harmonics
transforming harmonics.csv
harmonics.rows: 3

----

On the first run in a fresh project the transform logs `transforming stations.csv` and then
`transforming harmonics.csv` for the second flavor; both lines are printed by the transform itself, and a rerun of the same
request reuses the cached result and prints only the line of the task. The `-Pflavor` selected the variant first, then the
transform converted that variant's single file; the `rows` view never saw the other flavor.

A transform with parameters, an incremental transform and transform chains are described in the manual. Secondary
variants such as `classes` (see above) are the cheaper alternative when the producer can offer the other shape itself.

Source: https://docs.gradle.org/current/userguide/artifact_transforms.html#sec:artifact-transforms-overview[Gradle User Manual: Artifact transforms overview], https://docs.gradle.org/current/userguide/artifact_transforms.html#sec:implement_a_transform[Gradle User Manual: Implement a transform], https://docs.gradle.org/current/userguide/artifact_transforms.html#sec:register_a_transform[Gradle User Manual: Register a transform], https://docs.gradle.org/current/userguide/artifact_transforms.html#sec:use_the_transform[Gradle User Manual: Use the transform], https://docs.gradle.org/current/userguide/artifact_transforms.html#sec:artifact-transform-chains[Gradle User Manual: Artifact transform chains]

== Feature variants

A *feature variant* is an optional part of a library with its own source set, its own dependencies and its own capability.
It is Gradle's answer to Maven's `<optional>true</optional>`, but typed: instead of a dependency that may or may not be
there, the feature has a name and a consumer asks for it. `registerFeature("csv")` in the model build above created:

* the source set `csv` (`src/csv/java`), which the main source set does not see;
* the configurations `csvApi` and `csvImplementation` for the feature's dependencies;
* the variants `csvApiElements`, `csvRuntimeElements` and, with `withSourcesJar()`, `csvSourcesElements`, all with the
  capability `io.tidepool:tidepool-model-csv:1.0`, which is the component's `group:name` with `-csv` appended. The
  capability is how a consumer addresses the feature.

The consumer in `tidepool-engine` wrote

[source,kotlin]
----
implementation(project(":tidepool-model")) {
    capabilities {
        requireFeature("csv")
    }
}
----

and Gradle added the `csv` variant to the same component, with the transitive dependency on Commons CSV, as the
`dependencyInsight` output above shows. A consumer that does not ask never sees Commons CSV: in the published-module
consumer below, `-Pcsv=false` resolves `tidepool-model` and nothing else. A feature can also be registered on the
main source set (`usingSourceSet(sourceSets.main)`), in which case it has no classes of its own and only contributes
dependencies.

In a publication a feature variant maps to the formats as follows (the table is from the manual and the Maven and Ivy cells
are confirmed by the published files shown later):

[cols="2,3,3,3"]
|===
|Format |Variant artifacts |Feature dependencies |Capability

|Gradle Module Metadata
|uploaded
|in the feature's variants, required by the consumer that asks for the feature
|published

|POM
|uploaded, with a distinct classifier
|`<optional>true</optional>` dependencies
|not published (warning at publication)

|`ivy.xml`
|uploaded, with a distinct classifier
|extra configurations (`csvApiElements`, `csvRuntimeElements`); not in `default`
|not published (warning at publication)
|===

Source: https://docs.gradle.org/current/userguide/how_to_create_feature_variants_of_a_library.html#sec::declare_feature_variants[Gradle User Manual: Declare feature variants], https://docs.gradle.org/current/userguide/how_to_create_feature_variants_of_a_library.html#sec::publishing_feature_variants[Gradle User Manual: Publishing features], https://docs.gradle.org/current/userguide/how_to_create_feature_variants_of_a_library.html#sec::consuming_feature_variants[Gradle User Manual: Consuming features]

== Gradle Module Metadata

Variants exist at the project level. For a *published* component they must be written down somewhere, and neither
`pom.xml` nor `ivy.xml` has room for attributes, capabilities or variant-specific dependencies. *Gradle Module Metadata*
(GMM) is that format: a JSON file named `<artifactId>-<version>.module`, published next to the POM or Ivy descriptor,
that lists every variant with its attributes, dependencies, constraints, files (with size and checksums) and
capabilities. Gradle 5.3 published and consumed version 1.0; since Gradle 6.0 `maven-publish` and `ivy-publish` generate
it by default.

=== Mapping to the POM and to ivy.xml

The POM is written for Maven and for old Gradle; it carries what Maven can express, and a marker comment:

[source,xml]
----
<?xml version="1.0" encoding="UTF-8"?>
<project xsi:schemaLocation="http://maven.apache.org/POM/4.0.0 https://maven.apache.org/xsd/maven-4.0.0.xsd" xmlns="http://maven.apache.org/POM/4.0.0"
    xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance">
  <!-- This module was also published with a richer model, Gradle metadata,  -->
  <!-- which should be used instead. Do not delete the following line which  -->
  <!-- is to indicate to Gradle or any Gradle module metadata file consumer  -->
  <!-- that they should prefer consuming it instead. -->
  <!-- do_not_remove: published-with-gradle-metadata -->
  <modelVersion>4.0.0</modelVersion>
  <groupId>io.tidepool</groupId>
  <artifactId>tidepool-model</artifactId>
  <version>1.0</version>
  <dependencies>
    <dependency>
      <groupId>org.apache.commons</groupId>
      <artifactId>commons-csv</artifactId>
      <version>1.14.1</version>
      <scope>compile</scope>
      <optional>true</optional>
    </dependency>
  </dependencies>
</project>
----

The `commons-csv` dependency appears with `<optional>true</optional>`, the feature's mapping. Everything else (variants,
the `csv` capability, the test fixtures, the data variants) is only in the `.module` file. The marker is the line
`do_not_remove: published-with-gradle-metadata`; Gradle reads the POM first, sees it, and only then fetches the module
file. The manual describes this as a saving of one request in the common case where there is no module file.

=== Consuming the published module

A separate consumer build reads the repository. Its settings file adds the repository and, optionally, makes it behave like
Maven; its build file asks for the feature and for the test fixtures:

.Kotlin DSL (consumer/settings.gradle.kts)
[source,kotlin]
----
rootProject.name = "consumer"

dependencyResolutionManagement {
    repositoriesMode = RepositoriesMode.FAIL_ON_PROJECT_REPOS
    repositories {
        maven {
            name = "tidepool"
            url = uri("../kts/build/repo")
            // -PpomOnly: behave like Maven, ignore the .module file
            if (providers.gradleProperty("pomOnly").isPresent) {
                metadataSources {
                    mavenPom()
                    ignoreGradleMetadataRedirection()
                }
            }
        }
        mavenCentral()
    }
}
----

=== Disabling GMM publication

Disabling is a build-file decision, made by disabling the task that generates the file. It is for repositories that
reject the unknown file, or for builds that use Maven- or Ivy-specific features GMM cannot represent:

.Kotlin DSL (excerpt of tidepool-model/build.gradle.kts, selected by -PnoGmm)
[source,kotlin]
----
if (providers.gradleProperty("noGmm").isPresent) {
    tasks.withType<GenerateModuleMetadata>().configureEach {
        enabled = false
    }
}
----

.Groovy DSL (excerpt of tidepool-model/build.gradle)
[source,groovy]

if (providers.gradleProperty('noGmm').present) {
    tasks.withType(GenerateModuleMetadata).configureEach {

}

== What changed from Gradle 8.14 and from the Gradle 1.x book

* Gradle 8.14: variant-aware resolution, GMM publication by default, feature variants and test fixtures are the same
  (not run here). The explicit configuration roles API (`consumable`, `resolvable`, `dependencyScope`) exists since 8.4. Gradle
  9 deprecates passing a `Project` as a dependency notation (9.6 in this run) and prints the deprecation with a stack trace
  location under `--warning-mode all`.
* Gradle in Action covers Gradle 1.7. There a *configuration* was the only unit a dependency had: `compile`, `runtime`,
  `testCompile` and custom ones, selected by name (`project(path: ':a', configuration: 'x')`). Since Gradle 7.0 the
  `compile`, `runtime` and `testCompile` configurations are gone; `implementation`, `api`, `compileOnly` and `runtimeOnly`
  are *declaration* buckets and the consumer selects an outgoing variant by attributes. The book also predates
  Gradle Module Metadata (5.3), feature variants, test fixtures (5.6) and artifact transforms; what
  Maven calls an optional dependency is a feature variant now, and the test fixtures plugin is the supported way to share
  test helpers.
* Gradle 10 is announced but not released; nothing on this page depends on it.

Source: https://docs.gradle.org/current/userguide/upgrading_version_9.html#dependency_project_notation[Gradle User Manual: Upgrading from 8.x, Project object as dependency notation]

== The same idea in the other two tools

[cols="2,3,3,3"]
|===
|Concept |Gradle |Maven |Ant with Ivy

|Component metadata
|`.module` (GMM) plus POM or `ivy.xml`
|`pom.xml`
|`ivy.xml` with configurations

|Compile versus runtime
|`java-api` and `java-runtime` usage on `apiElements` and `runtimeElements`
|dependency `scope` (compile, runtime, ...)
|configurations such as `compile` and `runtime`, mapped with `+conf="a->b"+`

|Optional parts
|feature variants with a capability
|`<optional>true</optional>`, untyped
|an extra configuration

|Same artifact, different shape
|artifact transforms
|classifier or type on the dependency (`sources`, `test-jar`)
|artifact `type` and `ext`

|Test helpers shared across projects
|test fixtures plugin
|`test-jar` with `<type>test-jar</type>`
|a configuration for the test jar
|===

== Classic mistakes

* Declaring dependencies on a `resolvable` or `consumable` configuration (<<_asking_for_sample_data>>): use a
  `dependencyScope` bucket and `extendsFrom`.
* Expecting a custom attribute to exclude variants that do not set it: it does not (<<_a_variant_that_does_not_say_anything_is_compatible>>);
  add a distinguishing category or usage.
* Registering an artifact transform from a Kotlin build script (a non-static inner class), or reading the transformed files
  in `doLast` without declaring them as task inputs (<<transforms>>).
* Creating a custom consumable configuration and expecting it in the publication: add it to the component with
  `addVariantsFromConfiguration`, and give its artifacts distinct classifiers.
* Using `def` helpers in a Groovy build script that read script-level variables: use closures.
* Publishing a library to a repository that rejects `.module` files without disabling GMM, or disabling GMM and then
  wondering why the feature variants are gone.
* Reading a POM-only view of a Gradle-published module in another tool and concluding that the library "has no
  optional features": the information is in the module file.
