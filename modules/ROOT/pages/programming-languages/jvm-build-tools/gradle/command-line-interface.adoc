== The synopsis

The official page gives the structure of a Gradle command as follows:

----
gradle [taskName...] [--option-name...]
gradle [--option-name...] [taskName...]
----

Source: https://docs.gradle.org/current/userguide/command_line_interface.html#command_line_interface[Gradle: Command-Line Interface]

Four rules from that page govern everything below:

* *Options may come before or after the task names.* `./gradlew build --parallel` and `./gradlew --parallel build` are the same command. The only
  exception is a _task option_ (below), which must follow its task.
* *Several tasks are separated by spaces* (`./gradlew clean build`) and run in one build, in the order their dependencies allow.
* *Options that take a value accept it with or without `=`*, and the documentation recommends `=` (`--console=plain`).
* *Options that switch a behaviour on have a `--no-` inverse*: `--build-cache` and `--no-build-cache`, `--parallel` and `--no-parallel`. Many long options
  also have a short one (`--help` and `-h`, `--continuous` and `-t`).

All of the examples use `./gradlew`, the wrapper script, as the official page recommends; `gradle` (a locally installed distribution, see
xref:programming-languages/jvm-build-tools/gradle/installation.adoc[Installation]) accepts exactly the same arguments. The built-in help prints
the usage line and the options in groups:

[source,bash]
----
./gradlew -h | head -12
----

[source,text]
----
To see help contextual to the project, use gradlew help

To see more detail about a task, run gradlew help --task <task>

To see a list of available tasks, run gradlew tasks

USAGE: gradlew [option...] [task...]

--                                   Signals the end of built-in options. Parses subsequent parameters as tasks or task options only.

Help:
----

(The first lines of the output are the hint about the contextual `help` task. The complete list is reproduced in the
<<_option_reference,option reference>> below.)

A build that fails ends the process with a non-zero exit code: the runs on this page ended with `0` on success and `1` on failure, which is what CI servers and shell scripts test.

== The scratch project

The examples use a copy of the running _tidepool_ project with three subprojects: `tidepool-model`, `tidepool-engine` (depends on the model, uses Commons CSV)
and `tidepool-cli` (depends on the engine, uses picocli and the `application` plugin). The settings file declares the repositories once and the
subprojects; the root build file configures every subproject, including the JUnit 5 test dependencies. The versions of the libraries are written
inline here to keep the page short; the recommended place for them is a version catalog, see
xref:programming-languages/jvm-build-tools/gradle/version-catalogs.adoc[Version Catalogs].

The test in `tidepool-engine` fails on request: it reads the system property `tidepool.fail`, which the root build file sets from the project property
`failTests` (so `-PfailTests=true` makes one test fail). That gives the failure options something to act on.

.Kotlin DSL
[source,kotlin]
----
// settings.gradle.kts
rootProject.name = "tidepool"

dependencyResolutionManagement {
    repositories {
        mavenCentral()
    }
}

include("tidepool-model", "tidepool-engine", "tidepool-cli")
----

.Groovy DSL
[source,groovy]
----
// settings.gradle
rootProject.name = 'tidepool'

dependencyResolutionManagement {
    repositories {
        mavenCentral()
    }
}

include 'tidepool-model', 'tidepool-engine', 'tidepool-cli'
----

.Kotlin DSL
[source,kotlin]
----
// build.gradle.kts (root)
subprojects {
    apply(plugin = "java")

    group = "io.tidepool"
    version = "1.0.0"

    tasks.withType<JavaCompile>().configureEach {
        options.release = 17
    }

    tasks.withType<Test>().configureEach {
        useJUnitPlatform()
        systemProperty("tidepool.fail", providers.gradleProperty("failTests").orElse("false").get())
    }

    dependencies {
        "testImplementation"(platform("org.junit:junit-bom:5.13.4"))
        "testImplementation"("org.junit.jupiter:junit-jupiter")
        "testRuntimeOnly"("org.junit.platform:junit-platform-launcher")
    }
}
----

.Groovy DSL
[source,groovy]
----
// build.gradle (root)
subprojects {
    apply plugin: 'java'

    group = 'io.tidepool'
    version = '1.0.0'

    tasks.withType(JavaCompile).configureEach {
        options.release = 17
    }

    tasks.withType(Test).configureEach {
        useJUnitPlatform()

        testImplementation platform('org.junit:junit-bom:5.13.4')
        testImplementation 'org.junit.jupiter:junit-jupiter'

----

The subproject build files are one-liners. `tidepool-model` applies `java-library`; `tidepool-engine` applies it too and adds the dependencies; `tidepool-cli`
applies `application`. The `run` task is told to format numbers in the English locale so that the output below does not depend on the machine:

.Kotlin DSL
[source,kotlin]
----
// tidepool-engine/build.gradle.kts
plugins {
    `java-library`
}

dependencies {
    api(project(":tidepool-model"))
    implementation("org.apache.commons:commons-csv:1.14.1")
}

// tidepool-cli/build.gradle.kts
plugins {
    application
}

dependencies {
    implementation(project(":tidepool-engine"))
    implementation("info.picocli:picocli:4.7.7")
}

application {
    mainClass = "io.tidepool.cli.Main"
}

tasks.named<JavaExec>("run") {
    systemProperty("user.language.format", "en")
    systemProperty("user.country.format", "US")
}
----

.Groovy DSL
[source,groovy]
----
// tidepool-engine/build.gradle
plugins {
    id 'java-library'
}

dependencies {
    api project(':tidepool-model')
    implementation 'org.apache.commons:commons-csv:1.14.1'
}

// tidepool-cli/build.gradle
plugins {
    id 'application'
}

dependencies {
    implementation project(':tidepool-engine')
    implementation 'info.picocli:picocli:4.7.7'
}

application {
    mainClass = 'io.tidepool.cli.Main'
}

tasks.named('run') {
    systemProperty 'user.language.format', 'en'
    systemProperty 'user.country.format', 'US'
}
----

Both versions of the project were built and the commands below were run on both with the same results; the DSL matters only for the build files, never for the command
line. This build is configuration-cache compatible: it was run with `--configuration-cache` (see <<_the_configuration_cache,below>>) and the entry was stored and reused.

== Executing tasks

=== Task selectors and project paths

A task is named with its _path_: the project path, a colon, and the task name. A leading colon makes the path absolute from the root project:

[source,bash]
----
./gradlew :tidepool-cli:run --args="../data/stations.csv BOS" -q
----

[source,text]
----
Boston: -0.662 m
----

(`-q` keeps only what the program prints. The decimal point follows the JVM default locale: this run used an English locale, and a locale such as Spanish prints `-0,662 m`. The relative path in `--args` is relative to the working directory of the `run` task, the project directory of `tidepool-cli`.)
The ways of writing a task name behave as follows:

[cols="2,3",options="header"]
|===
|Command |Meaning

|`./gradlew :tidepool-cli:jar`
|The `jar` task of that project, spelled with an absolute path.

|`./gradlew tidepool-cli:jar`
|The same task; the leading colon is optional when the command is run from the root.

|`./gradlew jar`
|A _task selector_: the `jar` task of *every* project that has one, reached from the root project where the command is run.

|`./gradlew :jar`
|The `jar` task of the root project only. The root project of _tidepool_ has no Java plugin, so here it fails with `Cannot locate tasks that match ':jar' as task 'jar' not found in root project 'tidepool'`.
|===

A selector is the common case. `./gradlew test` ran the `test` tasks of all three subprojects above, and `./gradlew run` found the single `run` task in `tidepool-cli`:

[source,bash]
----
./gradlew run --dry-run
----

[source,text]
----
:tidepool-model:compileJava SKIPPED
:tidepool-engine:compileJava SKIPPED
:tidepool-cli:compileJava SKIPPED
:tidepool-cli:processResources SKIPPED
:tidepool-cli:classes SKIPPED
:tidepool-engine:processResources SKIPPED
:tidepool-engine:classes SKIPPED
:tidepool-engine:jar SKIPPED
:tidepool-model:processResources SKIPPED
:tidepool-model:classes SKIPPED
:tidepool-model:jar SKIPPED
:tidepool-cli:run SKIPPED

BUILD SUCCESSFUL in 918ms
----

Some selectors run only in the project the command is invoked on and not in its subprojects; the official page names `help` and `dependencies` as examples. When Gradle is invoked from inside a subproject directory the project name is omitted (`cd tidepool-engine && ../gradlew test`), and the `-p` option (`--project-dir`) starts the build
in another directory without changing into it.

Source: https://docs.gradle.org/current/userguide/command_line_interface.html#executing_tasks_in_multi_project_builds[Gradle: Executing tasks in multi-project builds]

=== Several tasks, and their order

Tasks are run in the order their dependencies require, which may differ from the order on the command line when the command line does not constrain it. One constraint is kept:
the _command line order safety_ rule. `./gradlew clean build` runs `clean` before `build` even if running them the other way round would be faster, because `clean` removes what `build` creates;
the order depends on tasks declaring what they create, consume or remove (see
xref:programming-languages/jvm-build-tools/gradle/incremental-build.adoc[Incremental Build]).

Source: https://docs.gradle.org/current/userguide/command_line_interface.html#sec:command_line_executing_tasks[Gradle: Executing tasks], https://docs.gradle.org/current/userguide/command_line_interface.html#command_line_order_safety[Gradle: Command line order safety]

=== Task options

An option placed *right after a task name* belongs to that task, not to Gradle: `+run --args=...+` above, or `+test --tests=...+`. Task options are listed by `help --task`, which also prints the task's type, its description and all the
projects that have it:

[source,bash]
----
./gradlew help --task test -q
----

[source,text]
----
Detailed task information for test

Paths
     :tidepool-cli:test (registered by plugin 'org.gradle.jvm-test-suite')
     :tidepool-engine:test (registered by plugin 'org.gradle.jvm-test-suite')
     :tidepool-model:test (registered by plugin 'org.gradle.jvm-test-suite')

Type
     Test (org.gradle.api.tasks.testing.Test)

Options
     --debug-jvm     Enable debugging for the test process. The process is started suspended and listening on port 5005.

     --no-debug-jvm     Disables option --debug-jvm.

     --fail-fast     Stops test execution after the first failed test.

     --no-fail-fast     Disables option --fail-fast.

     --test-dry-run     Simulate test execution.

     --no-test-dry-run     Disables option --test-dry-run.

     --tests     Sets test class or method name to be included (in addition to the test task filters), '*' is supported.

     --rerun     Causes the task to be re-run even if up-to-date.

     Runs the test suite.

----

If a task defines an option with the same name as a built-in Gradle option (the official page uses the example of a `profile` option), the built-in one wins unless the task name is preceded by `--`:
`gradle mytask --profile` passes `--profile` to Gradle, while `gradle -- mytask --profile=value` passes it to the task. Every task also has the built-in `--rerun` option (below). How to declare an option on your own
task is on xref:programming-languages/jvm-build-tools/gradle/writing-custom-tasks.adoc[Writing Custom Tasks].

Source: https://docs.gradle.org/current/userguide/command_line_interface.html#sec:show_task_details[Gradle: Show task usage details], https://docs.gradle.org/current/userguide/command_line_interface.html#sec:task_options[Gradle: Task options], https://docs.gradle.org/current/userguide/custom_tasks.html#sec:declaring_and_using_command_line_options[Gradle: Declaring and using command line options]

=== Name abbreviation

Neither the project nor the task name needs to be written in full. Any prefix that identifies it uniquely works, and camel-case patterns are expanded against camel-case and kebab-case names: `tEn:tes` is `tidepool-engine:test`, and `:t-c:jar` is
`:tidepool-cli:jar` (the pattern `t-c` matches `tidepool-cli` because both words start with the given letters). Abbreviations also work after `-x`. When the abbreviation matches two names Gradle refuses to guess:

== Choosing which tasks run

=== Excluding tasks: -x

second excludes `test`; the third also excludes `compileJava`:

=== Forcing tasks to run

Gradle skips a task whose inputs and outputs have not changed (the task is reported `UP-TO-DATE`; see xref:programming-languages/jvm-build-tools/gradle/incremental-build.adoc[Incremental Build]).
Two options override that. `--rerun` is a task option and re-runs only the task it follows; `--rerun-tasks` is a Gradle option and re-runs every task in the build, as if everything had been cleaned, but without deleting the outputs.

The first run of `:tidepool-engine:test` after a `clean`, the second run (nothing changed), the third run with `--rerun`, and a run of two test tasks with `--rerun-tasks` (the filter keeps the task line, the result and the counts):

[source,bash]
----
./gradlew clean
./gradlew :tidepool-engine:test | grep -E 'engine:test( |$)|BUILD|actionable'
./gradlew :tidepool-engine:test | grep -E 'engine:test( |$)|BUILD|actionable'
./gradlew :tidepool-engine:test --rerun | grep -E 'engine:test( |$)|BUILD|actionable'
./gradlew :tidepool-engine:test :tidepool-model:test --rerun-tasks | grep -E 'engine:test( |$)|BUILD|actionable'
----

[source,text]
----
> Task :tidepool-engine:test
BUILD SUCCESSFUL in 1s
5 actionable tasks: 5 executed

> Task :tidepool-engine:test UP-TO-DATE
BUILD SUCCESSFUL in 355ms
5 actionable tasks: 5 up-to-date

> Task :tidepool-engine:test
BUILD SUCCESSFUL in 673ms
5 actionable tasks: 1 executed, 4 up-to-date

> Task :tidepool-engine:test
BUILD SUCCESSFUL in 1s
7 actionable tasks: 7 executed
----

(The four outputs are printed one after the other, separated by blank lines; the `clean` output is omitted.) Note the counts: `--rerun` executed one task and left the four it depends on up to date, while `--rerun-tasks` executed all seven.

Source: https://docs.gradle.org/current/userguide/command_line_interface.html#sec:rerun_tasks[Gradle: Forcing tasks to execute], https://docs.gradle.org/current/userguide/command_line_interface.html#sec:builtin_task_options[Gradle: Built-in task options]

=== When a task fails: --continue

By default Gradle stops at the first task failure, which shortens the build and avoids cascades of unrelated errors. `--continue` runs every task whose own dependencies succeeded and reports all the failures at the end. The tests of the
engine are made to fail with `-PfailTests=true`; without `--continue` the model's tests are never reached, with it they run:

[source,bash]
----
./gradlew build -PfailTests=true | grep -E 'engine:test|model:test|BUILD|failing|FAILED|went wrong|Execution failed|AssertionFailed|tests completed|TideEngineTest'
./gradlew build -PfailTests=true --continue | grep -E 'engine:test|model:test|BUILD|failing|FAILED|went wrong|Execution failed|AssertionFailed|tests completed|TideEngineTest'
----

[source,text]
----
> Task :tidepool-engine:testClasses UP-TO-DATE
> Task :tidepool-engine:test FAILED
TideEngineTest > failsOnRequest() FAILED
    org.opentest4j.AssertionFailedError at TideEngineTest.java:24
2 tests completed, 1 failed
* What went wrong:
Execution failed for task ':tidepool-engine:test'.
> There were failing tests. See the report at: file://<tidepool>/tidepool-engine/build/reports/tests/test/index.html
BUILD FAILED in 603ms

> Task :tidepool-engine:testClasses UP-TO-DATE
> Task :tidepool-engine:test FAILED
TideEngineTest > failsOnRequest() FAILED
    org.opentest4j.AssertionFailedError at TideEngineTest.java:24
2 tests completed, 1 failed
> Task :tidepool-model:testClasses UP-TO-DATE
> Task :tidepool-model:test
* What went wrong:
Execution failed for task ':tidepool-engine:test'.
> There were failing tests. See the report at: file://<tidepool>/tidepool-engine/build/reports/tests/test/index.html
BUILD FAILED in 801ms
----

(The two outputs are printed one after the other, separated by a blank line.) The second build still ends with `BUILD FAILED` and exit code 1; `--continue` changes what is executed, not the verdict. `--no-continue` is the inverse and is the default.
A task is skipped even under `--continue` when something it depends on failed: tests do not run when the code they test does not compile. `--continue` is the natural option for CI, where one run should report all failing modules and
all failing checks; the failure of the `test` task here also names the HTML report to open.

Source: https://docs.gradle.org/current/userguide/command_line_interface.html#sec:continue_build_on_failure[Gradle: Continue the build after a task failure]

=== Running the application

The `run` task of the `application` plugin passes `--args` to the program's `main` method. The program exits with 1 for an unknown station, and the task turns a non-zero exit value into a build failure:

[source,bash]
----
./gradlew :tidepool-cli:run --args="../data/stations.csv XXX" | grep -E 'Unknown|BUILD|FAILED|went wrong|non-zero'
----

[source,text]
----
> Task :tidepool-cli:run FAILED

== Dependencies and the network

`--offline` forbids network access; builds then use only what is in the dependency cache. With an empty Gradle user home (a per-example `GRADLE_USER_HOME` was used so that the shared cache stayed untouched) it fails with a message that names the missing module:

[source,bash]
----
GRADLE_USER_HOME=<own home> ./gradlew :tidepool-engine:compileJava --offline
----

[source,text]
----
> Task :tidepool-model:compileJava UP-TO-DATE
> Task :tidepool-engine:compileJava FAILED

FAILURE: Build failed with an exception.

* What went wrong:
Execution failed for task ':tidepool-engine:compileJava' (registered by plugin class 'org.gradle.api.plugins.JavaBasePlugin').
> Could not resolve all files for configuration ':tidepool-engine:compileClasspath'.
   > Could not resolve org.apache.commons:commons-csv:1.14.1.
     Required by:
         project ':tidepool-engine'
      > No cached version of org.apache.commons:commons-csv:1.14.1 available for offline mode.
----

(The wrapper download, the welcome text and the last part of the failure message, `* Try:` and the footer, were removed from the listing; the lines shown are as printed.) `--refresh-dependencies` (`-U`) is the opposite: it refreshes the state of the dependencies (the help text is "Refreshes the state of dependencies")
instead of trusting what the cache holds. `--offline` is therefore a way to prove that a build works without the network, and `-U` a way to start from what the repositories serve now. The rules of the cache are on
xref:programming-languages/jvm-build-tools/gradle/dependency-locking-verification-and-caching.adoc[Dependency Locking, Verification & Caching].

* `--parallel` was run above with `clean build --parallel`, whose last two lines were:

[[_the_configuration_cache]]
* The *configuration cache* stores the result of the configuration phase for a given set of requested tasks and reuses it while its inputs are unchanged. The first listing stores the entry (`+Calculating task graph ...+`); the second changes a Gradle property
that the build reads while configuring (`failTests`), so the entry cannot be reused and a new one is stored; the third repeats the second and reuses it (`Reusing configuration cache.`). The filter keeps the cache messages and the verdict:
+
[source,bash]
----

./gradlew :tidepool-engine:test --configuration-cache -PfailTests=true | grep -E 'cache|Calculating|Reusing|BUILD|Configuration'

----
+
(The three outputs are printed one after the other; the second and third builds fail, as asked, with `-PfailTests=true`.) The configuration cache is *not* on by default in Gradle 9.8.1: the 9.0 release made it the preferred mode and announced that it will be the default in Gradle 10, so the flag, `org.gradle.configuration-cache=true` in `gradle.properties` (which is what
`gradle init` writes, see below), or `--no-configuration-cache` to switch it off again, is how it is controlled. Task code that reads the `Project` object at execution time is not compatible with it (the warning example in <<_warnings_and_deprecations,warnings and deprecations>> below).

* `--profile` writes `build/reports/profile/profile-<timestamp>.html`, a per-task and per-project time report, without needing a server. The official page says that `--scan` is preferred.

* `--scan` creates a Build Scan, which captures the build's metadata and sends it to a Develocity server (the public service by default; `--develocity-url` names a private one, and the plugin is auto-applied by the flag). The first use may ask to accept the terms of use. *Not run here*: the build data would be published to an external service. Nearly every failure message
in this page ends with `Run with --scan to get full insights from a Build Scan`, and the `dependencies` output with `A web-based, searchable dependency report is available by adding the --scan option`, which is how the option is advertised.

The daemon options (`--daemon`, `--no-daemon`, `--foreground`, `--status`, `--stop`) are on xref:programming-languages/jvm-build-tools/gradle/gradle-daemon.adoc[Gradle Daemon]; the build-cache and configuration-cache pages above and
xref:programming-languages/jvm-build-tools/gradle/performance-profiling-and-build-scans.adoc[Performance Profiling & Build Scans] cover the rest.

== Output: logging, console and warnings

=== Log levels and stack traces

The default log level is `lifecycle`. The options, from least to most verbose, are `-q` (`--quiet`, errors only), `-w` (`--warn`), the default, `-i` (`--info`) and `-d` (`--debug`, which includes the normal stack trace). The property `org.gradle.logging.level` sets the same thing
from `gradle.properties`. A small build that logs one message at each level shows what each option keeps:

.Kotlin DSL
[source,kotlin]
----
// build.gradle.kts
tasks.register("levels") {
    doLast {
        logger.error("error message")
        logger.quiet("quiet message")
        logger.warn("warn message")
        logger.lifecycle("lifecycle message")
        logger.info("info message")
        logger.debug("debug message")
    }
}
----

.Groovy DSL
[source,groovy]
----
// build.gradle
tasks.register('levels') {
    doLast {
        logger.error 'error message'
        logger.quiet 'quiet message'
        logger.warn 'warn message'
        logger.lifecycle 'lifecycle message'
        logger.info 'info message'
        logger.debug 'debug message'
    }
}
----

Each command was run, and only the lines of the messages (and the `BUILD` line of the default run) were kept with `grep message`; for `-d`, the time stamp that precedes every debug line was also removed:

$ ./gradlew levels -w

=== The console

`--console` takes `auto` (default: rich on a terminal, plain otherwise), `plain`, `colored`, `rich` and `verbose`; `plain` is the default when the output is not a terminal, which is why the listings on this page have no progress bar.
`verbose` prints the task names and outcomes as in Gradle 3.5 and earlier. `--console-unicode` allows or forbids Unicode characters, and `org.gradle.console` sets the mode from a property.

The two results are identical, as expected: with no terminal attached there is nothing to prompt. The case the option exists for, a terminal that is attached but must not be asked, could not be run here (the commands were run from a tool, not a terminal). The generated `gradle.properties` contains one line, `org.gradle.configuration-cache=true`, so a project created by Gradle 9.8.1 starts with the configuration cache on.
The `init` task itself is on xref:programming-languages/jvm-build-tools/gradle/installation.adoc[Installation].

Source: https://docs.gradle.org/current/userguide/command_line_interface.html#sec:non_interactive[Gradle: Non-interactive mode], https://docs.gradle.org/9.6.0/release-notes.html#non-interactive-mode[Gradle 9.6.0 release notes: Non-interactive mode]

== Continuous builds

`-t` (`--continuous`) keeps Gradle running after the tasks have finished and runs them again whenever the inputs of the tasks change. It needs file system watching (so it does not work with `--no-daemon`), waits for a quiet period after a change before building (the property
`org.gradle.continuous.quietperiod`, in milliseconds), and, in a terminal, ends with CTRL-D. This run was time-bounded: the build was started in the background, the Java source of the model was edited after twelve seconds (a comment line appended, then removed again afterwards), and the process was stopped after another eight seconds, because without a terminal there is no CTRL-D:

[source,bash]
----
./gradlew :tidepool-model:test --continuous &
sleep 12; echo "// edit" >> tidepool-model/src/main/java/io/tidepool/model/Height.java
sleep 8; kill %1
----

[source,text]
----

> Task :tidepool-model:processResources NO-SOURCE
> Task :tidepool-model:classes UP-TO-DATE
> Task :tidepool-model:compileTestJava UP-TO-DATE
> Task :tidepool-model:processTestResources NO-SOURCE
> Task :tidepool-model:testClasses UP-TO-DATE
> Task :tidepool-model:test UP-TO-DATE

BUILD SUCCESSFUL in 272ms
3 actionable tasks: 3 up-to-date

Waiting for changes to input files...
modified: <tidepool>/tidepool-model/src/main/java/io/tidepool/model/Height.java
Change detected, executing build...

> Task :tidepool-model:compileJava
> Task :tidepool-model:processResources NO-SOURCE
> Task :tidepool-model:classes
> Task :tidepool-model:compileTestJava UP-TO-DATE
> Task :tidepool-model:processTestResources NO-SOURCE

Gradle noticed the change, recompiled the class and saw that the tests did not need to run again, since the compiled class was byte-for-byte the same (the comment changed nothing in the bytecode), which is what incremental build is for. Four limitations from the official page matter in practice: changes to *build logic* (the build files themselves) are not picked up and need a restart; only files inside the
project directory are watched; creating a previously missing input directory may not trigger a build; and a task that modifies its own inputs causes an endless loop of builds. IDEs have their own continuous compilation, and the official page suggests running `./gradlew <task> --continuous` in a terminal next to the IDE.

Source: https://docs.gradle.org/current/userguide/command_line_interface.html#sec:continuous_build[Gradle: Continuous build], https://docs.gradle.org/current/userguide/continuous_builds.html#sec:terminating_continuous_build[Gradle: Terminating continuous build], https://docs.gradle.org/current/userguide/continuous_builds.html#continuous_build_limitations[Gradle: Continuous build limitations]

== Environment options

These options choose the files and properties a build starts from. Their long-term home is `gradle.properties` and the environment (see
xref:programming-languages/jvm-build-tools/gradle/build-environment-and-properties.adoc[Build Environment & Properties]); on the command line they are the per-run override:

[cols="2,5",options="header"]
|===
|Option |Meaning

|`-g`, `--gradle-user-home`
|The Gradle user home (default `~/.gradle`): caches, downloaded distributions, daemon logs and `init.d` scripts. The environment variable `GRADLE_USER_HOME` (the same directory) was used above to give examples an empty cache.

|`-p`, `--project-dir`
|The directory the build starts in (default: the working directory).

|`--project-cache-dir`
|The per-project cache directory (default: `.gradle` in the root project).

|`-P`, `--project-prop`
|A _project property_ for the build, `-Pname=value`, read in a build file with `providers.gradleProperty("name")`. The `-PfailTests=true` above is one.

|`-D`, `--system-prop`
|A JVM system property of the _build_ process, `-Dname=value`; `org.gradle.*` properties such as `-Dorg.gradle.warning.mode=fail` can be set this way.

|`-I`, `--init-script`
|An init script to run before the build (see xref:programming-languages/jvm-build-tools/gradle/init-scripts-and-the-tooling-api.adoc[Init Scripts & the Tooling API]).

|`--include-build`
|Run the build as a composite that includes another build (see xref:programming-languages/jvm-build-tools/gradle/composite-builds.adoc[Composite Builds]).

|`-a`, `--no-rebuild`
|Do not rebuild project dependencies; useful for debugging `buildSrc`, but "can lead to wrong results".
|===

The security options are `-F`/`--dependency-verification=strict|lenient|off`, `-M`/`--write-verification-metadata`, `--refresh-keys` and `--export-keys` (dependency verification), and `--write-locks` and `--update-locks` (dependency locking); they are on
xref:programming-languages/jvm-build-tools/gradle/dependency-locking-verification-and-caching.adoc[Dependency Locking, Verification & Caching]. `-P` and `-D` are the options most often mistaken for each other. In Maven `-D` defines a user property and `-P` activates profiles; in Gradle `-P` defines a project property and `-D` a JVM system property.

Source: https://docs.gradle.org/current/userguide/command_line_interface.html#sec:environment_options[Gradle: Environment options], https://docs.gradle.org/current/userguide/build_environment.html#sec:gradle_command_line_flags[Gradle: Command-line flags]

== Gradle 8.14 and the books

The command line of Gradle 8.14 (the last 8.x line) is the same as above for everything that is not tagged with a release in this page, but four additions are missing there. *Not run here*, taken from the release notes: `--task-graph` appeared in 9.1, `tasks --provenance` in 9.5, and `--non-interactive` and `NO_COLOR` in 9.6.
Gradle 8.14 can run on a JVM as old as 8, while Gradle 9 needs JVM 17 or later to run the build (the wrapper, the client and the Tooling API client can still start on JVM 8); every example here started on JDK 26. How this reads for a migration from 8.14 is on
xref:programming-languages/jvm-build-tools/gradle/upgrading-gradle.adoc[Upgrading Gradle].

The command-line text of the Gradle 1.x books is only partly current:

[cols="3,3",options="header"]
|===
|Old text or practice |Today

|`--daemon` to opt in to the daemon
|The daemon has been the default since Gradle 3.0; `--no-daemon` switches it off. See xref:programming-languages/jvm-build-tools/gradle/gradle-daemon.adoc[Gradle Daemon].

|`-u` (`--no-search-upward`) to stop the search for `settings.gradle`
|Removed in Gradle 5.0 (the upgrade notes say all builds need a settings file). Since Gradle 7.0 a build without a settings file is an error, except for `init` and diagnostic flags such as `--version`.

|`--recompile-scripts`, `+-Dtest.single=...+`, `-Dtest.debug`
|Removed in Gradle 5.0; use test filtering (`+test --tests=...+`) and `test --debug-jvm`.

|`task name << { }` in build scripts
|Removed in 5.0; see xref:programming-languages/jvm-build-tools/gradle/tasks.adoc[Tasks].

|===

Source: https://docs.gradle.org/current/userguide/upgrading_version_4.html#potential_breaking_changes_5_0[Gradle: Upgrading from 4.x to 5.0, potential breaking changes], https://docs.gradle.org/current/userguide/upgrading_version_6.html[Gradle: Upgrading from 6.x to 7.0], https://docs.gradle.org/9.1.0/release-notes.html#task-graph-visualization[Gradle 9.1.0 release notes], https://docs.gradle.org/9.6.0/release-notes.html[Gradle 9.6.0 release notes]
