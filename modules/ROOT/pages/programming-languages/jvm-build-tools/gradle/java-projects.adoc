A Java build looks the same in every JVM build tool: put sources and resources in agreed places, compile them against a classpath that comes from the dependency declarations, run the tests, and pack the result. What differs is who knows the conventions. Ant knows none of them, so a build file lists every directory and every classpath (see xref:programming-languages/jvm-build-tools/ant/compiling-java.adoc[Compiling Java with Ant]). Maven knows one fixed set, which it calls the standard directory layout (see xref:programming-languages/jvm-build-tools/maven/philosophy-coordinates-and-directory-layout.adoc[Maven Philosophy, Coordinates & Directory Layout]). Gradle ships the conventions as plugins, every one of them can be changed in the build script, and the plugin you apply decides how much of the Java build you get: compilation only, a library with a public API, or a runnable application. This page is about those plugins, about the objects underneath them (source sets, configurations and tasks), and about the parts of a Java build that are specific to Gradle: compile avoidance, incremental compilation, annotation processors, and the split between `api` and `implementation`. The shared vocabulary (build, project, task) is on xref:programming-languages/jvm-build-tools/gradle/core-concepts.adoc[Core Concepts]; the dependency notation used here is explained on xref:programming-languages/jvm-build-tools/gradle/declaring-dependencies-and-configurations.adoc[Declaring Dependencies & Configurations]; running tests, test suites and coverage are on xref:programming-languages/jvm-build-tools/gradle/testing-jvm-projects.adoc[Testing JVM Projects]; publishing the JARs built here is on xref:programming-languages/jvm-build-tools/gradle/publishing.adoc[Publishing]. For the language itself see xref:programming-languages/java/build-and-tooling.adoc[Java Build & Tooling]; for the Kotlin side see xref:programming-languages/kotlin/build-and-tooling.adoc[Kotlin Build & Tooling].

== The JVM plugins at a glance

The plugins build on each other. Applying one applies the plugins below it, so a build script almost always names exactly one of them (the one at the top of the stack it needs).

[cols="1,3,3"]
|===
|Plugin id |What it adds |Use it for

|`java-base`
|The `java` extension, and the rules that give every source set a compile task, a resources task and a classes task. It creates no source set of its own.
|Plugin authors who want the Java model without the `main` and `test` source sets; build authors almost never apply it directly.

|`java`
|The source sets `main` and `test`, the tasks `compileJava`, `processResources`, `classes`, `jar`, `javadoc`, `test` and the other tasks of the table below, and the configurations `implementation`, `compileOnly`, `runtimeOnly`, `annotationProcessor` and their `test` counterparts.
|A module that is compiled, tested and packed, but that is not consumed as a library by other projects.

|`java-library`
|Everything of `java`, plus the configurations `api` and `compileOnlyApi`, and a separation between the dependencies that consumers need to compile against and the ones that are an implementation detail. Consumers of a project dependency compile against its classes directory instead of its JAR.
|Any project that other projects depend on, such as *tidepool-model* and *tidepool-engine*.

|`application`
|Everything of `java`, plus the `distribution` plugin and the tasks `run`, `startScripts`, `installDist`, `distZip` and `distTar`, and the `application` extension (main class, JVM arguments, script name).
|A program with a `main` method, such as *tidepool-cli*.

|`war`
|Everything of `java`, plus the `war` task, `src/main/webapp`, the configurations `providedCompile` and `providedRuntime`, and a `web` software component.
|Web applications for a servlet container (see below).

|`groovy`, `scala`
|Everything of `java`, plus `compileGroovy` and `groovydoc`, or `compileScala` and `scaladoc`, and joint compilation of the language with Java.
|Projects written wholly or partly in those languages (see below).

|`java-platform`, `java-test-fixtures`, `jvm-test-suite`, `jvm-toolchains`
|A platform of constraints without code, the `testFixtures` source set, the `+testing { suites { ... } }+` DSL, and the toolchain support that every JVM plugin applies.
|Each has its own page: xref:programming-languages/jvm-build-tools/gradle/platforms-constraints-and-rich-versions.adoc[Platforms, Constraints & Rich Versions], xref:programming-languages/jvm-build-tools/gradle/testing-jvm-projects.adoc[Testing JVM Projects] and xref:programming-languages/jvm-build-tools/gradle/toolchains.adoc[Gradle Toolchains].
|===

Source: https://docs.gradle.org/current/userguide/building_java_projects.html#sec:building_jvm_components[Gradle User Manual: Building Java & JVM projects], https://docs.gradle.org/current/userguide/java_plugin.html#sec:java_usage[The Java Plugin], https://docs.gradle.org/current/userguide/java_library_plugin.html#sec:java_library_usage[The Java Library Plugin], https://docs.gradle.org/current/userguide/application_plugin.html#sec:application_usage[The Application Plugin]

The role of `java-library` in a build with several projects is the reason it is the default choice for libraries: the `api` configuration says which dependencies are part of the library's public face, and everything else stays out of the compile classpath of the consumers (see "Libraries: api and implementation" below).

== The example build: three projects, in both DSLs

The running example of the section is _tidepool_, a small tide prediction toolkit: a model library (`Station`, `Constituent`, `Height`, `TideEvent` records), an engine library on top of it (the `TideEngine` and a `StationReader` that uses Commons CSV), and a command line application built with picocli. As a Gradle build it is one root project with three subprojects, which is the structure described on xref:programming-languages/jvm-build-tools/gradle/multi-project-builds.adoc[Multi Project Builds]. This page uses the build to show what the Java plugins do; the files are shown once, here, and the sections below refer to them.

The settings file declares the repository once for all projects, forbids repositories in project scripts and includes the three projects. The version catalog and `gradle.properties` are the same for both DSLs.

    compileClasspath += sourceSets.main.get().output
    runtimeClasspath += sourceSets.main.get().output
}

configurations[integrationTest.get().implementationConfigurationName]
    .extendsFrom(configurations.testImplementation.get())
configurations[integrationTest.get().runtimeOnlyConfigurationName]
    .extendsFrom(configurations.testRuntimeOnly.get())

val integrationTestTask = tasks.register<Test>("integrationTest") {
    description = "Runs the integration tests."
    group = "verification"
    testClassesDirs = integrationTest.get().output.classesDirs
    classpath = integrationTest.get().runtimeClasspath
    useJUnitPlatform()
    shouldRunAfter(tasks.test)
}

tasks.check {
    dependsOn(integrationTestTask)
}
----

// One executable JAR with the runtime classpath unpacked into it.
tasks.register<Jar>("fatJar") {
    description = "Assembles a single executable JAR."
    group = "build"
    archiveClassifier = "all"
    duplicatesStrategy = DuplicatesStrategy.EXCLUDE
    manifest {
        attributes("Main-Class" to application.mainClass)
    }
    from(sourceSets.main.map { it.output })
    from(configurations.runtimeClasspath.map { classpath ->
        classpath.map { if (it.isDirectory) it else zipTree(it) }
    })
}
----

== Source sets and the standard layout

A _source set_ is Gradle's name for a group of sources that are compiled together and run with one classpath: it bundles a source directory, a resources directory, an output directory, and a set of dependency configurations. The Java plugin creates two, `main` (the production code, which ends up in the JAR) and `test` (compiled against `main` and used to run tests). The layout it expects is the one every Java developer knows, and nothing has to exist: the plugin compiles whatever it finds and ignores what is missing.

[source,text]
----
tidepool-cli/build.gradle.kts
tidepool-cli/src/main/java/io/tidepool/cli/Main.java
tidepool-engine/build.gradle.kts
tidepool-engine/src/integrationTest/java/io/tidepool/engine/StationReaderIT.java
tidepool-engine/src/main/java/io/tidepool/engine/StationReader.java
tidepool-engine/src/main/java/io/tidepool/engine/TideEngine.java
tidepool-engine/src/test/java/io/tidepool/engine/TideEngineTest.java
tidepool-model/build.gradle.kts
tidepool-model/src/main/java/io/tidepool/model/Constituent.java
tidepool-model/src/main/java/io/tidepool/model/Height.java

The directory of a source set is always `src/<name>/java` for Java and `src/<name>/resources` for resources, so the hand-made source set `integrationTest` of the engine lives in `src/integrationTest/java`, with no further configuration. The build output is as regular as the input:

[cols="2,3"]
|===
|Directory under `build/` |Contents

|`classes/java/<sourceSet>`
|The compiled classes of a source set (`classes/java/main`, `classes/java/test`).

|`resources/<sourceSet>`
|The processed resources of a source set.

|`generated/sources/annotationProcessor/java/<sourceSet>`
|Java sources that annotation processors generated while compiling the source set.

|`generated/sources/headers/java/<sourceSet>`
|JNI headers, if the compiler is asked for them.

|`libs`
|JARs: `jar`, and with the options of the *tidepool-model* script `-sources.jar` and `-javadoc.jar` too.

|`distributions`
|The archives of the `application` plugin.

|`docs/javadoc`
|The output of the `javadoc` task. Together with `test-results` and `reports` these directories are properties of the `java` and `base` extensions (`docsDir`, `testResultsDir`, `testReportDir`, `libsDirectory`).

|`test-results`, `reports`, `tmp`
|Test result XML files, reports, and scratch files of tasks.
|===

Every source set has the same family of names, derived from the source set name. That is how the plugin gives a source set called `integrationTest` its own `compileIntegrationTestJava` task and `integrationTestImplementation` configuration without any code:

[cols="2,3"]
|===
|For source set `name` |What exists

|Tasks
|`compileNameJava` (type `JavaCompile`), `processNameResources` (`Copy`), `nameClasses` (a lifecycle task). `main` is the exception: its tasks are `compileJava`, `processResources` and `classes`.

|Declarable configurations
|`nameImplementation`, `nameCompileOnly`, `nameRuntimeOnly`, `nameAnnotationProcessor`. `testImplementation` extends `implementation`, and `testRuntimeOnly` extends `runtimeOnly`.

|Resolvable configurations
|`nameCompileClasspath` (extends `nameCompileOnly` and `nameImplementation`), `nameRuntimeClasspath` (extends `nameRuntimeOnly` and `nameImplementation`).

|Source set properties
|`java.srcDirs` (default `src/name/java`), `resources.srcDirs`, `output.classesDirs`, `output.resourcesDir`, `compileClasspath`, `annotationProcessorPath`, `runtimeClasspath`, `allJava`, `allSource`.
|===

The Maven equivalent of "source set" does not exist: the project has exactly one main and one test tree, and anything else (integration tests, generated sources) needs plugins that add source roots. The Ant equivalent is a `<javac>` task per tree (see the comparison table at the end of the page).

=== Changing the layout

Setting a property replaces its value; calling the matching method adds to it. That distinction, `setSrcDirs` against `srcDir` in the Kotlin DSL (`srcDirs =` against `srcDir` in the Groovy DSL), is the way to read most of the source set API. A legacy project whose sources live in `src/java` instead of `src/main/java` is described to Gradle like this:

.Kotlin DSL
[source,kotlin]
----
sourceSets {
    main {
        java {
            setSrcDirs(listOf("src/java"))
        }
    }
}
----

.Groovy DSL
[source,groovy]
----
sourceSets {
    main {
        java {
            srcDirs = ['src/java']
        }
    }
}
----

Both versions were run after moving the model's sources to `tidepool-model/src/java/io/tidepool/model` (tests stay in `src/test/java`):

[source,text]
----
> Task :tidepool-model:compileJava

BUILD SUCCESSFUL in 660ms
1 actionable task: 1 executed
tidepool-model/src/java/io/tidepool/model/Constituent.java
tidepool-model/src/java/io/tidepool/model/Height.java
tidepool-model/src/java/io/tidepool/model/Station.java
tidepool-model/src/java/io/tidepool/model/TideEvent.java
tidepool-model/src/test/java/io/tidepool/model/HeightTest.java
----

The build compiled the classes into the usual `build/classes/java/main` regardless of where the sources were. Adding a directory next to the default one uses `srcDir("thirdParty/src/main/java")`. A source set exists to give a set of sources its own classpath and its own output, so the guidance of the user manual is: if the sources need a unique classpath, produce classes that are handled differently from `main` and `test`, and are a natural part of the project, define a source set; generated sources that belong in the production JAR are better added to `main` (with the compile task depending on the generator).

Source: https://docs.gradle.org/current/userguide/building_java_projects.html#sec:custom_java_source_set_paths[Gradle User Manual: Customizing file and directory locations], https://docs.gradle.org/current/userguide/building_java_projects.html#sec:custom_java_source_sets[Compiling independent sources separately]

Resources need no configuration at all: files in `src/main/resources` are copied by `processResources` into `build/resources/main` and packed into the JAR, and the task has no sources (`NO-SOURCE` in the listings below) when the directory is absent. Replacing tokens in resource files uses the `expand` and `filter` methods of the `Copy` family described on xref:programming-languages/jvm-build-tools/gradle/working-with-files.adoc[Working with Files]; the Maven equivalent, resource filtering, is on xref:programming-languages/jvm-build-tools/maven/resources-and-filtering.adoc[Maven Resources & Filtering].

== The tasks the Java plugin adds

The plugin registers the tasks of the table and wires them with `dependsOn` relations into a graph that you rarely change. The graph, with the aggregate (lifecycle) tasks `classes`, `testClasses`, `assemble`, `check` and `build` at the joints:

[mermaid]
----
flowchart LR
  compileJava --> classes
  processResources --> classes
  classes --> jar
  classes --> javadoc
  jar --> assemble
  classes --> compileTestJava
  compileTestJava --> testClasses
  processTestResources --> testClasses
  testClasses --> test
  test --> check
  check --> build
  assemble --> build
----

Source: https://docs.gradle.org/current/userguide/java_plugin.html#sec:java_tasks[Gradle User Manual: The Java Plugin, Tasks]

[cols="2,2,3"]
|===
|Task |Type and depends on |What it does

|`compileJava`

== Compiling Java

`compileJava` is a `JavaCompile` task, and nearly everything you can tell the compiler is a property of that task type: `options.release`, `options.compilerArgs`, `options.encoding`, `options.isFork`, `options.isFailOnError` (`options.fork` and `options.failOnError` in the Groovy DSL), `options.isIncremental`, and the annotation processor path. Configure all of them at once, for `compileJava` and `compileTestJava` and every other source set, with `+tasks.withType<JavaCompile>().configureEach { ... }+` (`+tasks.withType(JavaCompile).configureEach { ... }+` in the Groovy DSL), as the three scripts above do. `+tasks.compileJava { ... }+` configures only the main compile task.

Source: https://docs.gradle.org/current/userguide/building_java_projects.html#sec:changing_compiler_options[Gradle User Manual: Changing compiler options]

=== Which Java version does the code target?

Three settings answer the question, with very different guarantees, and mixing them up is the classic Java-on-Gradle bug.

[cols="2,3,3"]
|===
|Setting |What it does |Guarantee

|Toolchain (`+java { toolchain { languageVersion = ... } }+`)
|Compiles, tests, documents and runs with a JDK of that version, found on the machine or provisioned.
|The strongest: language level, class file version and the JDK API all match. See xref:programming-languages/jvm-build-tools/gradle/toolchains.adoc[Gradle Toolchains].

|`options.release = 17` on the compile task
|Passes `--release 17` to `javac`: language level 17, class file version 61, and the API of Java 17 only.
|Almost as strong, and cheap: one newer JDK can build for older targets. Gradle supports it when the compiling JDK is Java 10 or later.

|`sourceCompatibility` and `targetCompatibility` in the `java` extension
|Pass `-source` and `-target`: language level and class file version, but the compiler still sees the API of the JDK that runs it.
|Weak, and the user manual says it is "not generally advised".
|===

=== Compiler options and lint

The projects pass `-Xlint:all` through `options.compilerArgs`, so every warning category of `javac` is on. Other options that builds commonly add are `-Werror` (warnings fail the build), `-parameters` (keep parameter names in the class files, which some frameworks and annotation processors need), `options.encoding = "UTF-8"` (the default of the JDK 18 and later is already UTF-8, but older JDKs use the platform charset), and `options.isFork = true` with `options.forkOptions` to compile in a separate JVM. Javac warnings are printed in the task output. Builds that printed warnings also ended with an `+[Incubating] Problems report is available at ...+` line that points to an HTML report under `build/reports/problems/`; that line is left out of the listings.

The Javadoc of the model is checked by doclint. The records have no `@param` tags, so the `javadoc` task in the model script switches the `missing` group off with `addBooleanOption("Xdoclint:all,-missing", true)`; without it, the task prints one warning per record component and still succeeds.

=== Compile avoidance and incremental compilation

Two separate features keep compilation cheap, and both look at the _binary interface_ of classes rather than at the files.

_Compile avoidance_ concerns consumers of a project. The compile classpath of a task is fingerprinted by the ABI of the classes on it (the part of a class that other classes can see: public and protected members, signatures, constants), and a change that does not alter the ABI does not make dependents out of date. Changing a method body, a comment, private members, a resource or the name of a JAR leaves downstream `compileJava` tasks `UP-TO-DATE`. With the `java-library` plugin the consumer even compiles against the classes directory of the project, so a change of a resource or the work of the `jar` task is not part of the compile at all.

_Incremental compilation_ concerns one compile task. Gradle recompiles the classes affected by a change (the changed ones and the ones that depend on them, by type references in bytecode) and leaves the others in the output directory untouched.

The first change to the engine is private: a new `case` in the `switch` inside `predict`. Nothing is visible to the CLI, so `tidepool-cli:compileJava` stays up to date even though the engine was recompiled:

=== Annotation processors

Annotation processors are the part of the compile classpath that Gradle treats as a separate world. A processor must be declared in the `annotationProcessor` configuration of the source set; Gradle ignores processors that are only on the compile classpath, because implementation details of a processor matter for the result of the compilation and must therefore be part of the up-to-date check. The library that holds the annotations is still declared in `implementation` or `compileOnly`, as the user manual's Dagger example shows.

The CLI uses picocli. The picocli-codegen processor reads the `@Command` and `@Parameters` annotations at compile time and writes the reflection configuration that GraalVM native image needs. It takes the output location from an option (`-Aproject`), which the build passes as a compiler argument:

== Libraries: api and implementation

Which dependencies a consumer sees is the one question that separates a library from a plain Java module. The `java-library` plugin adds the configuration `api` and the rule that decides what goes on whose classpath. The user manual's test for placing a dependency is the _binary interface_ of the library: a dependency belongs in `api` if at least one of its types is used in a superclass or interface, a public or protected method signature (parameters, return types, generic arguments), a public field, or a public annotation. A type that appears only in method bodies or private members belongs in `implementation`. Prefer `implementation`: if a type leaks, the consumers fail to compile at once, which is the signal to move the dependency.

[cols="1,3,3"]
|===
|Configuration |Compile classpath of the project |Compile classpath of consumers

|`api`
|Yes
|Yes, transitively

|`implementation`
|Yes
|No (runtime classpath only)

|`compileOnly`
|Yes
|No

|`compileOnlyApi`
|Yes
|Yes (for a dependency that is needed to compile against the library but not at runtime, such as an annotation JAR)

|`runtimeOnly`
|No
|No (runtime classpath of consumers only)
|===

Source: https://docs.gradle.org/current/userguide/java_library_plugin.html#sec:java_library_separation[Gradle User Manual: API and implementation separation], https://docs.gradle.org/current/userguide/java_library_plugin.html#sec:java_library_recognizing_dependencies[Recognizing API and implementation dependencies], https://docs.gradle.org/current/userguide/java_library_plugin.html#sec:java_library_configurations_graph[The Java Library configurations]

== A custom source set: integration tests

Integration tests are the textbook use of a second source set: they need their own classpath (they may run against real files or servers), they are compiled against `main`, and they are a natural part of the project. The engine script above builds the source set by hand. Gradle also has the JVM Test Suite plugin (`+testing { suites { ... } }+`), which does the same in a handful of declarative lines and is what the user manual recommends today; it is the subject of xref:programming-languages/jvm-build-tools/gradle/testing-jvm-projects.adoc[Testing JVM Projects]. The manual form still matters because it shows the objects that every other plugin creates: a source set, two configurations that extend the test ones, a `Test` task with the classes directory and the runtime classpath of the source set, and a connection to `check`.

.Kotlin DSL: the hand-made source set
[source,kotlin]
----
// A hand-made source set for slower tests that read the real data file.
val integrationTest = sourceSets.register("integrationTest") {
    compileClasspath += sourceSets.main.get().output
    runtimeClasspath += sourceSets.main.get().output
}

configurations[integrationTest.get().implementationConfigurationName]
    .extendsFrom(configurations.testImplementation.get())
configurations[integrationTest.get().runtimeOnlyConfigurationName]
    .extendsFrom(configurations.testRuntimeOnly.get())

val integrationTestTask = tasks.register<Test>("integrationTest") {
    description = "Runs the integration tests."
    group = "verification"
    testClassesDirs = integrationTest.get().output.classesDirs
    classpath = integrationTest.get().runtimeClasspath
    useJUnitPlatform()
    shouldRunAfter(tasks.test)
}

tasks.check {
    dependsOn(integrationTestTask)
}
----

.Groovy DSL: the hand-made source set
[source,groovy]
----
// A hand-made source set for slower tests that read the real data file.
sourceSets {
    integrationTest {
        compileClasspath += sourceSets.main.output
        runtimeClasspath += sourceSets.main.output
    }
}

configurations {
    integrationTestImplementation.extendsFrom testImplementation
    integrationTestRuntimeOnly.extendsFrom testRuntimeOnly
}

def integrationTestTask = tasks.register('integrationTest', Test) {
    description = 'Runs the integration tests.'
    group = 'verification'
    testClassesDirs = sourceSets.integrationTest.output.classesDirs
    classpath = sourceSets.integrationTest.runtimeClasspath
    useJUnitPlatform()
    shouldRunAfter tasks.test
}

tasks.check {
    dependsOn integrationTestTask
}
----

The Kotlin version registers the source set with `+sourceSets.register(...)+`. The delegate form `+val integrationTest by sourceSets.registering { ... }+` that older material uses is deprecated since Gradle 9.6 and the build printed a deprecation warning for it before it was changed (see "Gradle 8.14 and Gradle 9"). The source set contributes `compileIntegrationTestJava`, `processIntegrationTestResources`, `integrationTestClasses` and the configurations `integrationTestImplementation`, `integrationTestRuntimeOnly`, `integrationTestCompileClasspath` and so on. == Packaging

The `jar` task packs the classes and the resources of the `main` source set; `assemble` depends on it, so every build produces the JAR. The name is `<archiveBaseName>-<archiveVersion>.jar`, where the base name defaults to the project name and the version to the project version, so the model of this build is `tidepool-model-1.0.0.jar`. The directory and the base name are properties of the `base` extension (`base.libsDirectory`, `base.archivesName`, `base.distsDirectory`); the old project properties `archivesBaseName`, `libsDirName` and `distsDirName` are gone (see "Gradle 8.14 and Gradle 9").

=== Reproducible archives

Since Gradle 9.0.0 all archive tasks (`Jar`, `War`, `Ear`, `Zip`, `Tar`) produce reproducible archives by default: the order of the entries is deterministic, every entry has a fixed time stamp (the first of February 1980 in the `unzip -l` output above, the earliest date a ZIP entry can hold), directories have the permissions 0755 and files 0644. That is why the same sources give the same JAR. A hash taken after a build, and again after `clean` and a rebuild two seconds later:

[source,text]
----
875ec791c2960e71acd6235e73b2349abf31acb4067b0dbb70a502191b79a7fd  tidepool-model/build/libs/tidepool-model-1.0.0.jar
----

[source,text]
----
875ec791c2960e71acd6235e73b2349abf31acb4067b0dbb70a502191b79a7fd  tidepool-model/build/libs/tidepool-model-1.0.0.jar
----

The two hashes are identical. Builds that depend on the old behaviour (file order from the file system, real time stamps and permissions) can restore it per task with `isReproducibleFileOrder = false`, `isPreserveFileTimestamps = true` and `useFileSystemPermissions()` (the properties are called `reproducibleFileOrder` and `preserveFileTimestamps` in the Groovy DSL). In Gradle 8.14 those archives were not reproducible unless the build opted in (not run here); the Maven counterpart is `project.build.outputTimestamp`, see xref:programming-languages/jvm-build-tools/maven/security-and-reproducible-builds.adoc[Maven Security & Reproducible Builds].

=== A single executable JAR (fat JAR, uber JAR)

Gradle has no built-in fat JAR; the standard answer is a `Jar` task that unpacks the runtime classpath into the archive. The CLI script above contains it, because the way it handles the runtime classpath is the part that breaks under the configuration cache: the classpath must be a lazy `Provider` (or a closure) that is evaluated at execution time, not a `configurations.runtimeClasspath.get()` call made while the build is being configured.

.Kotlin DSL
[source,kotlin]
----
tasks.register<Jar>("fatJar") {
    description = "Assembles a single executable JAR."
    group = "build"
    archiveClassifier = "all"
    duplicatesStrategy = DuplicatesStrategy.EXCLUDE
    manifest {
        attributes("Main-Class" to application.mainClass)
    }
    from(sourceSets.main.map { it.output })
    from(configurations.runtimeClasspath.map { classpath ->
        classpath.map { if (it.isDirectory) it else zipTree(it) }
    })
}
----

.Groovy DSL
[source,groovy]
----
tasks.register('fatJar', Jar) {
    description = 'Assembles a single executable JAR.'
    group = 'build'
    archiveClassifier = 'all'
    duplicatesStrategy = DuplicatesStrategy.EXCLUDE
    manifest {
        attributes('Main-Class': application.mainClass)
    }
    from(sourceSets.main.output)
    from {
        configurations.runtimeClasspath.collect { it.directory ? it : zipTree(it) }
    }
}
----

----
./gradlew :tidepool-cli:fatJar
----

The JAR holds the classes of the CLI, of the other two projects and of the three libraries (`unzip -l` counts 758 class files), and the manifest names `io.tidepool.cli.Main`. `archiveClassifier` is the right property for the `-all` suffix (not `archiveAppendix`), because the classifier is what publishing uses to tell artifacts apart. `duplicatesStrategy = DuplicatesStrategy.EXCLUDE` keeps the first copy of a file that appears in several JARs, which is how files such as `META-INF/LICENSE` collide. The recipe copies files from JARs without merging them, so it breaks on libraries that use `META-INF/services` files, signed JARs, or multi-release JARs; those need the Shadow plugin (a third-party plugin), or the Maven Shade plugin on the Maven side. The Maven comparison, with relocation and service-file merging, is on xref:programming-languages/jvm-build-tools/maven/uber-jars-with-shade-and-assembly.adoc[Uber JARs with Shade & Assembly], and the Ant one (`<zipgroupfileset>`) is in xref:programming-languages/jvm-build-tools/ant/packaging-archives.adoc[Packaging Archives with Ant]. The question to ask first is whether a fat JAR is needed at all; the next section's distribution is usually the better artifact for a command line program.

== Applications: the application plugin

The `application` plugin turns a Java project into a program. The only mandatory setting is the main class. It adds the `run` task for development, and the tasks that build a distribution: `startScripts` (generates a Unix shell script and a Windows batch file), `distZip` and `distTar` (archives of the scripts, the project JAR and its runtime dependencies), and `installDist` (the same content copied into `build/install/<name>`). The settings of the `+application { ... }+` block that the CLI uses are `mainClass`, `applicationName` (the name of the scripts and the distribution; the default is the project name) and `applicationDefaultJvmArgs` (the JVM arguments of `run` and the scripts). Others are `executableDir` (the `bin` directory name), `mainModule` (a main class inside a Java module, which makes the scripts use the module path), and `applicationDistribution`, a copy specification for extra files. The `+distributions { main { contents { ... } } }+` block of the CLI script adds the data file to the distribution.

== Web applications, Groovy and Scala, and Java modules

These three topics are plugins and settings that follow the same pattern as the rest of the page, so each is one paragraph here; none of the following was run for this page (not run here), and each statement comes from the user manual.

The `war` plugin extends `java` with a `war` task that assembles a WAR: the content of `src/main/webapp` goes to the root, compiled classes to `WEB-INF/classes` and the runtime classpath to `WEB-INF/lib`. Dependencies that the servlet container provides are declared in `providedCompile` (visible to compilation and tests, excluded from the WAR) or `providedRuntime`; both work transitively, which is why a provided dependency's own dependencies are also left out of the WAR. These configurations are the old `providedCompile` of the Gradle 1.x books, still present; since Gradle 7.0 they cannot be consumed by other projects. Since Gradle 9.0 applying `war` together with `java` or `ear` builds all the archives during `assemble` (before 9.0 the WAR replaced the JAR), and the `war` project convention is gone, so the settings live on the `war` task itself (`webAppDirectory`, `webXml`, `+webInf { ... }+`). The Maven counterpart is the packaging type `war` (see xref:programming-languages/jvm-build-tools/maven/packaging-jars-wars-and-manifests.adoc[Maven Packaging: JARs, WARs & Manifests]), and a JSP/Struts project is described on the pages of the web section.

The `groovy` and `scala` plugins extend `java` with `src/main/groovy` and `src/main/scala` source directories that may also contain Java, and compile both languages together (joint compilation). The Groovy and Scala source directories may contain Java files next to the Groovy or Scala ones, and the compile tasks `compileGroovy` and `compileScala`, which run after `compileJava`, compile such mixed sources in one go, so classes may depend on each other in both directions. The Java source directories may contain only Java, and Java code that must call Groovy or Scala code has to live in the Groovy or Scala tree. The doc tasks are `groovydoc` and `scaladoc`. Applying `java-library` as well gives the API and implementation separation to a Groovy or Scala library. A Groovy project declares a Groovy dependency in `implementation`; a Scala project sets `scalaVersion` (an incubating property, which makes the Scala SDK dependency implicit) or declares the Scala library itself. The languages and their toolchains are described on xref:programming-languages/groovy/compiling-groovyc-and-joint-compilation.adoc[Groovy Compiling: groovyc & Joint Compilation] and xref:programming-languages/scala/sbt-and-build-tools.adoc[Scala sbt & Build Tools]; the Groovy side of Gradle (the build language) is on xref:programming-languages/jvm-build-tools/gradle/groovy-dsl-and-migrating-to-kotlin.adoc[Groovy DSL & Migrating to Kotlin].

Java modules (a `module-info.java`) need no extra plugin. With a `module-info.java` in a source set, Gradle puts the dependencies on the module path instead of the class path (`java.modularity.inferModulePath`, true by default; the `java` extension can switch it off), the `application` plugin can run a modular program if `mainModule` is set next to `mainClass`, and a library that is not a module can still be used as an automatic module. The classpath-versus-module-path distinction is explained for the language on xref:programming-languages/java/packages-and-modules.adoc[Java Packages & Modules].

== The configuration cache and the Java plugins

The core Java plugins are compatible with the configuration cache, and every build on this page ran with it on and stored or reused an entry without problems. The pitfalls are all in code that a build adds around the plugins:

* Resolving a configuration while the build is configured (`configurations.runtimeClasspath.get().files` in the body of a task registration) makes the configuration phase slow and, with the cache on, produces a problem as soon as the result is used in a task. The `fatJar` task reads the classpath lazily, through `map` in the Kotlin DSL and through a closure in the Groovy DSL (the closure is evaluated when the task runs).
* Reaching into `project` from a task action (`project.copy`, `project.exec`, `project.file`) is not allowed in a cached task; use the properties of the task, or an injected service (see xref:programming-languages/jvm-build-tools/gradle/configuration-cache-and-isolated-projects.adoc[Configuration Cache & Isolated Projects]).
* A compiler argument built from a project property, such as `+-Aproject=...+` in the CLI script, is read at configuration time and becomes part of the cached configuration. That is fine, because it is an input of `compileJava` (a different value gives a different up-to-date state).

== Classic mistakes

* *`sourceCompatibility` instead of `release`.* The build compiles, then fails on the older JVM with `NoSuchMethodError` (run above). Use `options.release` or a toolchain.
* *An implementation type in the public API.* The consumers fail with "package ... does not exist" (run above). Check the type against the `api` rules, or turn the dependency into `api`.
* *A new `Test` task that is not attached to `check`.* The tests exist and nobody runs them. Attach with `+tasks.check { dependsOn(...) }+`.
* *The old configuration names.* `compile`, `runtime`, `testCompile` and `testRuntime` were removed in Gradle 7.0. The error is `+Could not find method compile() for arguments ...+` in the Groovy DSL and an unresolved reference in the Kotlin DSL; the replacements are `api`, `implementation`, `compileOnly`, `runtimeOnly`, `testImplementation` and `testRuntimeOnly`.
* *A fat JAR that fails with `Invalid signature file digest` (a classic JVM error; not reproduced here).* A signed dependency has been unpacked into the archive. Exclude `+META-INF/*.SF+`, `+META-INF/*.DSA+` and `+META-INF/*.RSA+` in the `fatJar` task, or do not build a fat JAR.
* *A processor on the wrong classpath.* An annotation processor in `implementation` or `compileOnly` is not run by Gradle (Gradle ignores processors on the compile classpath); declare it in `annotationProcessor`.
* *A version mismatch between projects.* The "only compatible with JVM runtime version 21 or newer" message (run above) is the build telling you that a consumer targets an older Java than a library. Raise the consumer, lower the library's release, or change both through one convention plugin (see xref:programming-languages/jvm-build-tools/gradle/convention-plugins-and-sharing-build-logic.adoc[Convention Plugins & Sharing Build Logic]).
* *Running the program with the wrong working directory.* `run` starts in the project directory of the application, not in the root of the build. The relative path of the data file differs between `run`, the installed script and the IDE.

== Where the books are outdated

_Gradle in Action_ (Muschko, Manning 2014) was written for Gradle 1.7 and treats the Java plugin conventions, custom layouts and the War plugin in its chapters on the first builds and on the web (chapters 3 and 7). What its examples use and what replaced it:

* *The configurations `compile`, `runtime`, `testCompile`, `testRuntime`.* Removed in Gradle 7.0. Use `implementation`, `api`, `compileOnly`, `runtimeOnly`, `testImplementation` and `testRuntimeOnly`.
* *Project-level `sourceCompatibility = 1.7`.* The convention was deprecated in 8.2 and removed in 9.0.0. Use `+java { toolchain { ... } }+`, or `options.release` on the compile task.
* *`mainClassName`, `archivesBaseName`, `jar.archiveName`, `jar.baseName`.* `mainClassName` was removed in 7.0 in favour of `mainClass`; `archiveName`, `baseName` and the other old archive task properties were removed in 7.0 in favour of `archiveFileName` and `archiveBaseName`; the project property `archivesBaseName` went in 9.0.0 (`base.archivesName`).
* *A single compile classpath that exposes everything.* There was no `api`/`implementation` split; it came with the `java-library` plugin, together with compile avoidance and the incremental compiler.
* *`+apply plugin: 'java'+`.* The `+plugins { }+` block is the current form, and it is the only form the Kotlin DSL gives type-safe accessors for.
* *The Jetty plugin (`jettyRun`) for web applications.* Removed in Gradle 4.0; the third-party Gretty plugin covers that need. The War plugin itself, with `providedCompile`, is current.
* *Groovy and Scala plugins and joint compilation* (chapter 11). The plugins are still there with the same layout; Scala builds now declare the Scala version with `scalaVersion` or the Scala library dependency.
* *Hand-made source sets for integration tests.* Still valid, and shown above, but the JVM Test Suite plugin is the recommended form.
