wrong bucket, or a bucket used for something it was not made for, so this page is about the buckets as much as about the dependencies. Repositories are on

== Configurations and their three roles

A _configuration_ is a named collection of dependencies, and also of the artifacts a project offers and of the rules by which they are selected. The same word covers three quite different jobs, and since Gradle 8.4 the user manual calls them _roles_:

[cols="2,2,3,2",options="header"]
|===
|Role (flag)|Also called|What it is for|Example in the Java plugins

|Declarable (`canBeDeclared`)
|dependency scope, bucket
|Collects the dependencies, dependency constraints and exclude rules that are written in the `dependencies` block. It is never resolved and never consumed itself.
|`implementation`, `api`, `runtimeOnly`

|Resolvable (`canBeResolved`)
|consumer, classpath
|The root of a dependency graph. Asking it for its files makes Gradle resolve what the declarable configurations it extends collected into a set of files. Dependencies are not declared on it directly.
|`compileClasspath`, `runtimeClasspath`

|Consumable (`canBeConsumed`)
|producer, outgoing variant
|What this project offers to the projects that depend on it: artifacts plus attributes that describe them. It is selected by another project's resolution; it is not resolved here.
|`apiElements`, `runtimeElements`
|===

The three roles exist so that a build can say what it means. A dependency declared on `implementation` is a statement about this project; `compileClasspath` is the answer to "what does `javac` see?"; `apiElements` is the answer to "what does the project that depends on me
see?". The three questions have different answers, and keeping the three jobs apart is how `api` can differ from `implementation`. Before the roles were made explicit, one configuration object could be all three, and the flags `canBeResolved`, `canBeConsumed` and `canBeDeclared` were the only way to tell
(all three default to `true`, which the user manual labels "legacy, don't use"). The role factory methods `dependencyScope`, `resolvable` and `consumable` arrived in Gradle 8.4 and create configurations whose role cannot be changed afterwards; in Gradle 9.8.1 they are
still marked incubating in the Javadoc, and they are the way to create your own (see <<Your own configurations>>). Methods called on a configuration in a role they do not suit, such as resolving a declarable one, were a deprecation in the 8.x line and are an error since Gradle 9.0 (both are shown below).

In the tools that came before Gradle the same idea has other names. A Maven _scope_ is an attribute of each dependency (`compile`, `provided`, `runtime`, `test`) that decides which classpaths the dependency joins and how it is inherited, and it is the thing that is published to consumers; see
xref:programming-languages/jvm-build-tools/maven/dependencies-scopes-and-mediation.adoc[Maven Dependencies, Scopes & Mediation]. An Ivy _configuration_ is a named view of a module, and a dependency maps one configuration of mine to one of the dependency's
(`+conf="compile->default"+`); a Gradle configuration is closest to that, and Ivy's `extends` is Gradle's `extendsFrom`; see
xref:programming-languages/jvm-build-tools/ant/ivy-module-descriptors-and-configurations.adoc[Ivy: Module Descriptors & Configurations]. The section <<The same in Maven and in Ant>> lines the three up.

Source: https://docs.gradle.org/current/userguide/declaring_configurations.html#sec:resolvable-consumable-configs[Gradle: Declarable, Resolvable, and Consumable configurations],
https://docs.gradle.org/current/userguide/declaring_configurations.html#sec:configuration-flags-roles[Gradle: Configuration flags and roles],
https://docs.gradle.org/8.4/release-notes.html#easier-to-create-role-focused-configurations[Gradle 8.4 release notes: Easier to create role-focused Configurations]

== The three kinds of dependencies

Gradle distinguishes module dependencies (a published module found in a repository), project dependencies (another project of the same build) and file dependencies (files with no metadata). All three are written inside `dependencies { }`, as a
configuration name followed by the notation: `implementation("org.apache.commons:commons-csv:1.14.1")`. In the Kotlin DSL `+implementation(...)+` is a generated accessor for the configuration that the Java plugin created; a configuration that your own script creates has none, and is written
with a string (`+"tideTools"("...")+`) or through `add`. In the Groovy DSL the configuration name is a dynamic method.

=== Module dependencies

The notation of a module dependency is the string `group:name:version`, which are the same three coordinates as in a Maven POM (Gradle calls the artifactId the _name_). The optional parts follow it: `group:name:version:classifier@extension`. The forms below
were run in a single-project build named _notation_.

.Kotlin DSL: build.gradle.kts
[source,kotlin]
----
plugins {
    `java-library`
}

dependencies {
    // A module dependency: group:name:version, with a reason and an exclusion
    implementation("org.apache.commons:commons-csv:1.14.1") {
        because("reads the stations file")
        exclude(group = "commons-codec", module = "commons-codec")
    }

    // Do not follow the transitive dependencies of this module
    runtimeOnly("org.slf4j:slf4j-simple:2.0.17") {
        isTransitive = false
    }

    // A classifier selects another artifact of the same module
    runtimeOnly("info.picocli:picocli:4.7.7:sources")

    // An artifact-only notation (@jar) ignores the module metadata: no transitive dependencies
    runtimeOnly("com.google.guava:guava:33.5.0-jre@jar")

    // File dependencies: files without any metadata
    implementation(files("libs/legacy.jar"))
    implementation(fileTree("tools") { include("*.jar") })
}

tasks.register("printClasspaths") {
    val classpaths: Map<String, FileCollection> = mapOf(
        "compileClasspath" to configurations.compileClasspath.get(),
        "runtimeClasspath" to configurations.runtimeClasspath.get(),
    )
    doLast {
        classpaths.forEach { (name, files) ->
            println("$name:")
            files.map { it.name }.sorted().forEach { println("  $it") }
        }
    }
}
----

.Groovy DSL: build.gradle
[source,groovy]
----
plugins {
    id 'java-library'
}

dependencies {
    // A module dependency: group:name:version, with a reason and an exclusion
    implementation('org.apache.commons:commons-csv:1.14.1') {
        because 'reads the stations file'
        exclude group: 'commons-codec', module: 'commons-codec'
    }

    // Do not follow the transitive dependencies of this module
    runtimeOnly('org.slf4j:slf4j-simple:2.0.17') {
        transitive = false
    }

    // A classifier selects another artifact of the same module
    runtimeOnly 'info.picocli:picocli:4.7.7:sources'

    // An artifact-only notation (@jar) ignores the module metadata: no transitive dependencies
    runtimeOnly 'com.google.guava:guava:33.5.0-jre@jar'

    // File dependencies: files without any metadata
    implementation files('libs/legacy.jar')
    implementation fileTree('tools') { include '*.jar' }
}

tasks.register('printClasspaths') {
    Map<String, FileCollection> classpaths = [
        compileClasspath: configurations.compileClasspath,
        runtimeClasspath: configurations.runtimeClasspath,
    ]
    doLast {
        classpaths.each { name, files ->
            println "${name}:"
            files.collect { it.name }.sort().each { println "  ${it}" }
        }
    }
}
----

The `printClasspaths` task resolves the compile and the runtime classpath at execution time and prints the file names. It captures the two configurations as `FileCollection` values when the task is configured, and reads them only in the action: that is what makes it compatible with the
configuration cache (the section <<Your own configurations>> shows what fails when the build script is touched in the action). The output is the same in both DSLs:

[source,text]
----
compileClasspath:
  commons-csv-1.14.1.jar
  commons-io-2.20.0.jar
  extra.jar
  legacy.jar
runtimeClasspath:
  commons-csv-1.14.1.jar
  commons-io-2.20.0.jar
  extra.jar
  guava-33.5.0-jre.jar
  legacy.jar
  picocli-4.7.7-sources.jar
  slf4j-simple-2.0.17.jar
----

What each of the lines of the build did can be read from these two outputs:

* *String notation, with `because` and `exclude`.* `commons-csv` brings `commons-io` but not `commons-codec`, which the `+exclude(group = ..., module = ...)+` (Groovy: `+exclude group: ..., module: ...+`) removed from this dependency's subtree; the _because_ text is a documentation of intent that the
`dependencyInsight` report prints (see <<Viewing and debugging dependencies>>). An exclusion applies to this declaration and to everything below it; excluding a module everywhere is a rule of the configuration, which is on
xref:programming-languages/jvm-build-tools/gradle/resolution-rules-and-substitution.adoc[Resolution Rules & Substitution].
* *`isTransitive = false`* (Groovy: `transitive = false`) takes the module without any of its dependencies. `slf4j-simple` alone is in the runtime classpath, without `slf4j-api` that it would normally bring.
* *A classifier* selects another artifact of the same module. `info.picocli:picocli:4.7.7:sources` resolves the file `picocli-4.7.7-sources.jar`, and the dependency report cannot tell it from a plain one: it only lists `info.picocli:picocli:4.7.7`.
* *`@jar`, the artifact-only notation,* tells Gradle to take that artifact of the module and ignore the module's metadata, so none of its transitive dependencies come with it. Guava is the clear case. Declared plainly it brings five more modules,
as this report (run in a scratch build) shows:
+
[source,text]
----
runtimeClasspath - Runtime classpath of source set 'main'.
\--- com.google.guava:guava:33.5.0-jre
     +--- com.google.guava:failureaccess:1.0.3
     +--- com.google.guava:listenablefuture:9999.0-empty-to-avoid-conflict-with-guava
     +--- org.jspecify:jspecify:1.0.0
     +--- com.google.errorprone:error_prone_annotations:2.41.0
     \--- com.google.j2objc:j2objc-annotations:3.1
----
+
With `@jar` only `guava-33.5.0-jre.jar` is in the classpath, which is what the runtime classpath above shows. The artifact-only notation is occasionally what you want and often what causes a `NoClassDefFoundError` later; prefer
`isTransitive = false` for the same effect with a name that says what it does.

The `dependencies` report of the runtime classpath is the other view of the same build:

[source,text]
----
runtimeClasspath - Runtime classpath of source set 'main'.
+--- org.apache.commons:commons-csv:1.14.1
|    \--- commons-io:commons-io:2.20.0
+--- org.slf4j:slf4j-simple:2.0.17
+--- info.picocli:picocli:4.7.7
\--- com.google.guava:guava:33.5.0-jre
----

The tree shows `commons-io` below `commons-csv` and no `commons-codec`, and neither the sources classifier nor the `@jar` suffix. The Groovy DSL printed the same.

https://docs.gradle.org/current/userguide/declaring_dependencies_basics.html#sec:documenting-dependencies[Gradle: Documenting dependencies]

==== The multi-string notation is deprecated

Older builds write the three coordinates as named arguments: `implementation(group = "org.apache.commons", name = "commons-csv", version = "1.14.1")` in the Kotlin DSL and
`implementation group: 'org.apache.commons', name: 'commons-csv', version: '1.14.1'` in the Groovy DSL. That _multi-string_ notation (the user manual also calls it the map notation) was deprecated in Gradle 9.1 and fails with an error in Gradle 10. The build still works in

=== Project dependencies

A dependency on another project of the same build names the project by its path: `implementation(project(":tidepool-engine"))` (Groovy: `implementation project(':tidepool-engine')`). The dependent project is built from the sources in the build and not downloaded; the
task graph, the classpaths it produces, the type-safe accessors (`projects.tidepoolEngine`, which are enabled with the `TYPESAFE_PROJECT_ACCESSORS` feature preview) and the deprecation in Gradle 9.6 of passing a `Project` object as the notation are all on
xref:programming-languages/jvm-build-tools/gradle/multi-project-builds.adoc[Multi Project Builds] and are not repeated here. What matters on this page is that a project dependency is also declared on a configuration (`api` or `implementation` below) and that this
choice is what the next sections are about. The `dependencies` report writes a project dependency declared on a declarable configuration as `project tidepool-model`, and a resolved one as `project ':tidepool-model'`.

Gradle 9.3 also deprecated a related habit. Declaring `com.example:my-project:1.0.0` in the project whose own group, name and version are exactly those used to resolve to that project itself; in Gradle 10 it will be looked up in the repositories instead.
Use `+project(...)+` for the project dependency.

Source: https://docs.gradle.org/current/userguide/declaring_dependencies_basics.html#sec:project-dependencies[Gradle: Project dependencies],
https://docs.gradle.org/current/userguide/upgrading_version_9.html#module_identity_for_root_component[Gradle: Deprecation of using module coordinates to depend on the current project]

=== File dependencies

A file dependency is a set of files added to a configuration with `+files(...)+` or `+fileTree(...)+`. It has no coordinates, so it has no transitive dependencies, no version, nothing to resolve and nothing to publish: the user manual recommends declaring the files in a local
repository on a `+file://+` URL instead, and says outright that file dependencies are discouraged. They are what remains when a jar is not available from any repository, such as a vendor library checked into the repository. The _notation_ build above has one of each, with
`libs/legacy.jar` and `tools/extra.jar`, which were made with the `jar` tool for the occasion (their content is irrelevant). Both reached the compile and the runtime classpath (`legacy.jar` and `extra.jar` in the output above), because they were declared on `implementation`. In the `dependencies` report of
the declarable configuration they look like this:

[source,text]
----
implementation - Implementation dependencies for the 'main' feature. (n)
+--- org.apache.commons:commons-csv:1.14.1 (n)
+--- unspecified (n)
\--- unspecified (n)
----

Two things are visible. The `(n)` marks a declarable configuration, whose tree cannot be resolved (see the annotations in <<Viewing and debugging dependencies>>), and the file dependencies are named `unspecified`, because they have no coordinates; they do not appear in the tree of the
resolved `runtimeClasspath` above at all, even though their files are in the classpath. The report is therefore not the complete picture of a classpath that has file dependencies, and a build that has them needs to look at the files.

Two more facts from the user manual. A `fileTree` has no stable order, even on one machine, which changes the cache key of any task that takes the classpath as an input; `+files(...)+` with explicit names is stable. And when the files are produced by a task, the dependency must say
so with `builtBy`, or a project that depends transitively on this one may not run the task first:

.Kotlin DSL
[source,kotlin]
----
dependencies {
    implementation(files(layout.buildDirectory.dir("classes")) {
        builtBy("compile")
    })
}
----

.Groovy DSL
[source,groovy]
----
dependencies {
    implementation files(layout.buildDirectory.dir('classes')) {
        builtBy 'compile'
    }
}
----

This snippet is taken from the user manual and was not run here. `gradleApi()` and `localGroovy()` are file dependencies too, for the build's own plugin code (see
xref:programming-languages/jvm-build-tools/gradle/binary-plugins.adoc[Binary Plugins]).

Source: https://docs.gradle.org/current/userguide/declaring_dependencies_basics.html#sec:file-dependencies[Gradle: File dependencies]

=== Where the version comes from

The examples above spell the version out in the string. In a real build it comes from the version catalog (`implementation(libs.commons.csv)`, as in the tidepool build files below), which
xref:programming-languages/jvm-build-tools/gradle/version-catalogs.adoc[Version Catalogs] explains, and the version can be a range, a prefix, a strict constraint or an imported bill of materials, which
xref:programming-languages/jvm-build-tools/gradle/platforms-constraints-and-rich-versions.adoc[Platforms, Constraints & Rich Versions] explains. A catalog entry can take a configuration block exactly as a string can: `implementation(libs.commons.csv) { because("reads the stations file") }` is in
the engine build below.

== The configurations of the Java plugins

The `java` plugin creates the configurations for the `main` source set and for the `test` source set, and `java-library` adds `api` and `compileOnlyApi` to the main one. The `application` plugin applies `java`. All of them were
printed from the build that ran on this page, by a task that lists every configuration of `tidepool-engine` (a `java-library` project) with its roles and what it extends:

.Kotlin DSL
[source,kotlin]
----
tasks.register("printConfigurations") {
    val rows: Provider<List<String>> = provider {
        configurations.sortedBy { it.name }.map { c ->
            val roles = listOfNotNull(
                "declarable".takeIf { c.isCanBeDeclared },
                "resolvable".takeIf { c.isCanBeResolved },
                "consumable".takeIf { c.isCanBeConsumed },
            ).joinToString("+")
            "${c.name} [$roles] extends ${c.extendsFrom.map { it.name }.sorted()}"
        }
    }
    inputs.property("rows", rows)
    doLast {
        rows.get().forEach { println(it) }
    }
}
----

.Groovy DSL
[source,groovy]
----
tasks.register('printConfigurations') {
    Provider<List<String>> rows = provider {
        configurations.sort { it.name }.collect { c ->
            def roles = []
            if (c.canBeDeclared) roles << 'declarable'
            if (c.canBeResolved) roles << 'resolvable'
            if (c.canBeConsumed) roles << 'consumable'
            "${c.name} [${roles.join('+')}] extends ${c.extendsFrom*.name.sort()}".toString()
        }
    }
    inputs.property('rows', rows)
    doLast {
        rows.get().each { println it }
    }
}
----

|declarable
|only the compile classpath of this project (not the test classpath, not the runtime, not published)
|none

|`compileOnlyApi` (`java-library` only, Gradle 6.7)
|declarable
|the compile classpath of this project and of its consumers, and nothing at runtime
|`compile`, see <<Dependencies in the published metadata>>

|`runtimeOnly`
|declarable
|only the runtime classpath of this project and of its consumers
|`runtime`

|`annotationProcessor`
|declarable and resolvable
|the annotation processor path of the compiler
|none

|`testImplementation`, `testCompileOnly`, `testRuntimeOnly`
|declarable
|the compile and runtime classpath of the tests, the compile classpath of the tests, the runtime classpath of the tests; `testImplementation` extends `implementation`
|none (tests are not published)

|`compileClasspath`, `runtimeClasspath`, `testCompileClasspath`, `testRuntimeClasspath`
|resolvable
|Nothing is declared on them: they are the classpaths that `javac` and `java` (or the test JVM) are given
|none

|`apiElements`, `runtimeElements`
|consumable
|Nothing is declared on them: they are what a project that depends on this one selects (the `java-api` and `java-runtime` variants)
|the `compile` and `runtime` entries of the POM are written from them
|===

The diagram draws the main half of it as a graph. An arrow from A to B means that B `extendsFrom` A, which is why a dependency declared on `api` ends up in `implementation`, in `compileClasspath`, in `runtimeClasspath` and in both outgoing variants.

image::jvm-build-tools-gradle-configurations.svg["The configurations of a Java library project: the declarable configurations compileOnlyApi, api, compileOnly, implementation, runtimeOnly and annotationProcessor, the resolvable compileClasspath and runtimeClasspath, and the consumable apiElements and runtimeElements, joined by extendsFrom arrows",width=1000]

A few things in the output are worth reading closely:

* *`implementation` extends `api`*, so what is exposed to consumers is also available to this project, which is why one declaration on `api` is enough. *`compileOnly` extends `compileOnlyApi`* for the same reason.
* *`compileClasspath` extends `compileOnly` and `implementation`; `runtimeClasspath` extends `implementation` and `runtimeOnly`.* There is no line from `compileOnly` to the runtime and none from `runtimeOnly` to compilation; that is all `compileOnly` and `runtimeOnly` mean.
* *`apiElements` extends `api` and `compileOnlyApi`; `runtimeElements` extends `implementation` and `runtimeOnly`.* A consumer compiles against the first and runs against the second.
* *`annotationProcessor` is both declarable and resolvable*, an exception that the user manual's table does not show (it lists it as declarable only): the resolvable configurations report lists it, and `dependencies --configuration annotationProcessor` resolves it. It is resolved to the
processor path of the compiler (see <<compileOnly, annotationProcessor and runtimeOnly>>).
* *`archives` and `default`* are legacy consumable configurations that are kept for backward compatibility (`default` extends `runtimeElements`, as the output shows, and is described as "Configuration for default artifacts"; the `archives` configuration was deprecated in Gradle 9.1 and will be removed in Gradle 10).
`mainSourceElements` and `testResultsElementsForTest` are consumable configurations for tools, described by `outgoingVariants` as the list of the source directories of the main source set and the binary results of the `test` suite; no dependencies are declared on them.
* *The test configurations repeat the pattern:* `testImplementation extends implementation`, `testRuntimeOnly extends runtimeOnly`, and `testCompileOnly extends compileOnlyApi` (so test code sees the annotations that the main code sees, but not what the main code declared `compileOnly`).

What the plugins add is a matter of what is applied, not of the Gradle version. The `java` plugin has `implementation` (since Gradle 3.4), `compileOnly`, `runtimeOnly` and the test ones, and no `api`, which is why a library that must tell its consumers what is exposed applies `java-library`. The War plugin adds
`providedCompile` and `providedRuntime`, which differ from `compileOnly` in that the dependencies are on the runtime classpath of the project and the tests but are left out of the WAR. Other plugins create their own: the Android Gradle plugin per build type and flavor (`debugImplementation`),
Kotlin Multiplatform per source set (`commonMainImplementation`); see xref:apps/android/project-structure-and-gradle.adoc[Project Structure, Gradle and Build Variants] and
xref:apps/kotlin-multiplatform/dependencies-and-the-library-ecosystem.adoc[Dependencies and the Library Ecosystem]. The `java-test-fixtures` plugin (Gradle 5.6) adds `testFixturesApi` and `testFixturesImplementation`, and the JVM Test Suite plugin a set per suite (`intTestImplementation` and `intTestRuntimeOnly` for a suite called `intTest`); see xref:programming-languages/jvm-build-tools/gradle/testing-jvm-projects.adoc[Testing JVM Projects].

== api versus implementation

For a library, the most important decision about a dependency is whether the types of that dependency appear in the library's own interface. If they do, the dependency is part of the API: the consumers need it to compile against the library, so it goes on `api` and travels to their
compile classpath. If it is only used inside, it goes on `implementation`, and the consumers get it at run time but not to compile against. The user manual's rule of thumb is to prefer `implementation` whenever possible, and to reach for `api` when a type of the dependency is in the library's binary
interface:

* types used in a super class or an interface of a public class;
* types in the parameters (including the generic parameters) of a public or protected method;
* types of public fields;
* public annotations.

A type used only in method bodies, in private members or in internal classes is not part of the API. The compiler cannot tell the difference; Gradle can only be told. Choosing `implementation` is also the safer error: if an internal type leaks, the consumers fail to compile at once
and you notice. Choosing `api` by habit makes every consumer's compile classpath larger and every change of the dependency a reason to recompile them, and it lets consumers write code against a library they never declared, which breaks when the library stops exposing it. (The
user manual lists faster compilation and less recompilation as the benefits; that is not measured here.)

== compileOnly, annotationProcessor and runtimeOnly

*`compileOnly`* is for what the compiler needs and the running program must not have: annotations that are not used at run time, a servlet API that the container provides, or a dependency that is shaded into the jar. It is what Maven calls `provided`, with one difference that the Gradle 2.12
release notes state: `compileOnly` dependencies are not on the test classpath, which a Maven `provided` dependency is. A test that needs the servlet API declares it again on `testImplementation`, or on `testCompileOnly` if the tests only compile against it.
The engine proves it: its `testCompileClasspath` has the model (a project dependency, with the annotations the model exports through `compileOnlyApi`), Commons CSV and JUnit, and no `auto-service-annotations`:

[source,text]
----
testCompileClasspath - Compile classpath for source set 'test'.
+--- project ':tidepool-model'
|    \--- org.jetbrains:annotations:26.1.0
+--- org.apache.commons:commons-csv:1.14.1
|    +--- commons-io:commons-io:2.20.0
|    \--- commons-codec:commons-codec:1.19.0
\--- org.junit.jupiter:junit-jupiter:6.1.3
     +--- org.junit:junit-bom:6.1.3

*`annotationProcessor`* is a separate bucket, since Gradle 4.6, because what the compiler compiles against and what it runs as a processor are different things. Gradle 4.6 deprecated putting processors on the compile classpath and Gradle 5.0 stopped applying them, so a processor declared on the wrong
configuration is not an error: it is silently not run. That was tried here, in a scratch copy of the engine with the AutoService processor on `compileOnly` only. The build succeeded without a warning on JDK 26, and `build/classes/java/main` has no `META-INF` directory at all. The engine uses Google's AutoService, which generates the `META-INF/services` registration of a class from an annotation. The
annotations are `compileOnly`, because they are not needed at run time, and the processor is `annotationProcessor`:

.Kotlin DSL

After the build, the processor has written `build/classes/java/main/META-INF/services/java.lang.Runnable` with the line `io.tidepool.engine.Warmup`. == Test dependencies

Tests have their own copy of the three Java buckets, each extending the main one (see the table above), so a test sees everything the main code sees and what it adds. Dependencies on a test framework go on `testImplementation` (the framework's API, which the test classes compile
against) and `testRuntimeOnly` (the engine that runs them and is not compiled against). The model and the engine declare JUnit Jupiter and its launcher this way, and enable the platform on the task:

.Kotlin DSL
[source,kotlin]
----
dependencies {
    testImplementation(libs.junit.jupiter)
    testRuntimeOnly(libs.junit.platform.launcher)
}

the configuration cache; the executor number is Gradle's):

[source,text]

== Your own configurations

The Java plugins' configurations cover compiling, running and testing. A build needs its own whenever a set of dependencies has a purpose of its own: the classpath of a code generator, a documentation tool, a set of agents, a smoke test, or the data that one project hands to another. The user manual
names three uses: separating API from implementation (which the plugins already do), a resolvable configuration for a classpath, and a consumable configuration to expose something. The tidepool root project, which has no code, has one of each role:

.Kotlin DSL: build.gradle.kts
[source,kotlin]
----
plugins {
    base
}

// A bucket for the dependencies of the build's own tooling
val tideTools = configurations.dependencyScope("tideTools")

// The classpath those dependencies resolve to
val tideToolsClasspath = configurations.resolvable("tideToolsClasspath") {
    extendsFrom(tideTools.get())
}

dependencies {
    tideTools("info.picocli:picocli-codegen:4.7.7")
}

// What the root project offers to other projects: the station data
val stationsZip = tasks.register<Zip>("stationsZip") {
    from("data")
    destinationDirectory = layout.buildDirectory.dir("distributions")
    archiveBaseName = "stations"
}

val dataKind = Attribute.of("io.tidepool.data", String::class.java)

val stationData = configurations.consumable("stationData") {
    attributes.attribute(dataKind, "stations")
    outgoing.artifact(stationsZip)
}

tasks.register("listTideTools") {
    val files: FileCollection = tideToolsClasspath.get()
    doLast {
        files.map { it.name }.sorted().forEach { println(it) }
    }
}
----

.Groovy DSL: build.gradle
[source,groovy]
----
plugins {
    id 'base'
}

// A bucket for the dependencies of the build's own tooling
def toolsBucket = configurations.dependencyScope('tideTools')

// The classpath those dependencies resolve to
def tideToolsClasspath = configurations.resolvable('tideToolsClasspath') {
    extendsFrom(toolsBucket.get())
}

dependencies {
    tideTools 'info.picocli:picocli-codegen:4.7.7'
}

// What the root project offers to other projects: the station data
def stationsZip = tasks.register('stationsZip', Zip) {
    from 'data'
    destinationDirectory = layout.buildDirectory.dir('distributions')
    archiveBaseName = 'stations'
}

def dataKind = Attribute.of('io.tidepool.data', String)

def stationData = configurations.consumable('stationData') {
    attributes.attribute(dataKind, 'stations')
    outgoing.artifact(stationsZip)
}

tasks.register('listTideTools') {
    FileCollection files = tideToolsClasspath.get()
    doLast {
        files.collect { it.name }.sort().each { println it }
    }
}
----

* `configurations.dependencyScope("tideTools")` creates the bucket. In the Kotlin DSL the returned provider can be used as a function in `dependencies` (`+tideTools("...")+`); in the Groovy DSL the variable must not have the name of the configuration (it was called `toolsBucket`), or the call resolves to the variable and
fails with `Could not find method call()`.
* `+configurations.resolvable("tideToolsClasspath") { extendsFrom(...) }+` creates the consumer. It has no dependencies of its own; it extends the bucket. Its files are the resolved classpath.
* `configurations.consumable("stationData")` creates the producer, and `outgoing.artifact(stationsZip)` says what it offers. A consumable configuration needs attributes to take part in variant-aware resolution (the report marks one without them `(n)`); the attribute `io.tidepool.data = stations` is a custom one, and how attributes are matched is on
xref:programming-languages/jvm-build-tools/gradle/variant-aware-resolution-and-module-metadata.adoc[Variant-Aware Resolution & Module Metadata]. The multi-project page has an example of a project that consumes a configuration of another.

The task `listTideTools` resolves the classpath at execution time:

[source,text]
----

picocli-codegen-4.7.7.jar

[source,text]

\--- info.picocli:picocli-codegen:4.7.7

----

=== What the role locks out

Because the roles are fixed at creation, the mistakes that the older, mutable configurations allowed are errors. Each of these was run in a scratch copy of the build. Declaring a dependency on a resolvable configuration:

[source,text]
----
* What went wrong:
Dependencies can not be declared against the `tideToolsClasspath` configuration.
----

Resolving a bucket, in a task action (without the configuration cache, to see the message by itself):

[source,text]
----
* What went wrong:
Execution failed for task ':resolveBucket' (registered in build file 'build.gradle.kts').
> Resolving dependency configuration 'tideTools' is not allowed as it is defined as 'canBeResolved=false'.
  Instead, a resolvable ('canBeResolved=true') dependency configuration that extends 'tideTools' should be resolved.
----

The Groovy DSL printed the same messages (with the line `A problem occurred evaluating root project 'tidepool'.` before the first, since it fails while the script runs). Both messages tell you the fix: the second even names it, a resolvable configuration that extends the bucket. In Gradle 8.x, calling methods on a
configuration whose role does not suit them, such as `files` or `resolve` on a bucket, was deprecated and warned at run time; since Gradle 9.0 it is an error (see "Gradle 8.14 and Gradle 9").

=== Resolving at execution time, and the configuration cache

The same task as a user would write it first, with the build script object used in the action, is the example of the cache's complaint:

.Kotlin DSL (fails with the configuration cache)
[source,kotlin]
----
tasks.register("resolveBucket") {
    doLast {
        println(configurations.getByName("tideTools").files)
    }
}
----

.Groovy DSL (fails with the configuration cache)
[source,groovy]
----
tasks.register('resolveBucket') {
    doLast {
        println configurations.getByName('tideTools').files
    }
}
----

On top of the error above, the configuration cache stops the build, because the action refers to a script object. The Kotlin DSL message and the Groovy DSL message differ:

.Kotlin DSL
[source,text]
----
1 problem was found storing the configuration cache.
- Task `:resolveBucket` of type `org.gradle.api.DefaultTask`: cannot serialize Gradle script object references as these are not supported with the configuration cache.
  See https://docs.gradle.org/9.8.1/userguide/configuration_cache_requirements.html#config_cache:requirements:disallowed_types
----

.Groovy DSL
[source,text]
----
1 problem was found storing the configuration cache.
- Task `:resolveBucket` of type `org.gradle.api.DefaultTask`: invocation of 'configurations' references a Gradle script object from a Groovy closure at execution time, which is unsupported with the configuration cache.
  See https://docs.gradle.org/9.8.1/userguide/configuration_cache_requirements.html#config_cache:requirements:gradle_model_types
----

The fix is the one `printClasspaths` and `listTideTools` use: take the `FileCollection` (a configuration is one) while the task is configured, keep it in a local value, and read it in the action. The resolution then happens at execution time, as a task input, and the cache can store the task. Gradle 9.7 made `ResolutionResult` fully
compatible with the configuration cache, so that tasks can use the higher-level dependency resolution APIs; see
xref:programming-languages/jvm-build-tools/gradle/configuration-cache-and-isolated-projects.adoc[Configuration Cache & Isolated Projects].

Source: https://docs.gradle.org/current/userguide/configuration_cache_requirements.html#config_cache:requirements:use_project_during_execution[Gradle User Manual: Configuration Cache Requirements, using the Project object at execution time], https://docs.gradle.org/current/userguide/configuration_cache_requirements.html#dependency_management_types[Dependency management types]

=== Inheritance, flags and laziness

`extendsFrom` makes a configuration inherit the dependencies, the dependency constraints, the exclude rules, the artifacts and the capabilities of another in the same project. It does not inherit the attributes or the role. The user manual advises against extending a consumable or resolvable configuration with one that is not. A configuration that is both resolvable and consumable can select itself when it is resolved; the 8.x upgrade guide deprecated that and announced an error from Gradle 9.0, and the role factory methods avoid it by construction. A typical use of `extendsFrom` is a smoke test configuration that extends `testImplementation` to reuse the test framework.

The older way to create the same configurations is `configurations.create("name")` and setting `isCanBeResolved`, `isCanBeConsumed` and `isCanBeDeclared` (`canBeResolved = false` in the Groovy DSL). It still works. The role factory methods are the replacement, and the user manual's advice for build
logic that touches configurations is to keep it lazy: `configurations.all { }` and `getByName` realize every configuration at once, while `configureEach { }` and `+named(...).configure { }+` only configure what is used. Since Gradle 9.2 the consumable configurations of the bundled plugins are also initialized lazily,
so a `configure` action on `apiElements` no longer runs at configuration time unless something realizes it.

Source: https://docs.gradle.org/current/userguide/declaring_configurations.html#sec:defining-custom-configurations[Gradle: Creating custom configurations],
https://docs.gradle.org/current/userguide/declaring_configurations.html#sec:configuration_api_incubating_methods[Gradle: Configuration API incubating methods],
https://docs.gradle.org/current/userguide/declaring_configurations.html#sec:avoiding_eager_configuration[Gradle: Avoiding eager configuration],
https://docs.gradle.org/current/userguide/upgrading_version_8.html#deprecated_configuration_usage[Gradle: Using configurations incorrectly],
https://docs.gradle.org/current/userguide/configuration_cache_requirements.html#config_cache:requirements:disallowed_types[Gradle: Configuration cache requirements, disallowed types],
https://docs.gradle.org/9.7.0/release-notes.html#resolutionresult-is-fully-configuration-cache-compatible[Gradle 9.7.0 release notes: ResolutionResult is fully Configuration Cache compatible]

== Dependencies in the published metadata

What the configurations were declared on is, for a published library, what its consumers see. The model and the engine were published with `maven-publish` to a `+file://+` repository inside the scratch build (`publishAllPublicationsToTidepoolRepository`; the full publishing page is
xref:programming-languages/jvm-build-tools/gradle/publishing.adoc[Publishing]), which wrote a POM and a Gradle Module Metadata file (`.module`) for each. The engine's POM has the scopes:

[source,xml]
----
  <dependencies>
    <dependency>
      <groupId>io.tidepool</groupId>
      <artifactId>tidepool-model</artifactId>
      <version>1.0.0</version>
      <scope>compile</scope>
    </dependency>
    <dependency>
      <groupId>org.apache.commons</groupId>
      <artifactId>commons-csv</artifactId>

== Mistakes and the messages they produce

Most of them are in the sections above with their messages. Two more have not been shown yet. The first is what a build from the Gradle 1.x or 2.x era meets when it is upgraded: declaring on `compile`, a configuration removed in Gradle 7.0:

.Kotlin DSL
[source,text]
----

  Line 8:     compile("info.picocli:picocli:4.7.7")

1 error
----

.Groovy DSL
[source,text]
----

The Kotlin DSL fails when it compiles the script (the accessor `compile` no longer exists); the Groovy DSL fails when it runs it (the method does not exist). The same applies to `runtime`, `testCompile` and `testRuntime`. The replacements are `implementation` or `api`, `runtimeOnly`, `testImplementation` and `testRuntimeOnly`. A custom configuration
that used `extendsFrom runtime` in the Groovy DSL silently created a new, empty configuration named `runtime` in Gradle 7, which is a worse symptom (the user manual warns of it).

[cols="3,3,3",options="header"]
|===
|Symptom|Cause|Fix

|`+package ... does not exist+` in a consumer, though the library depends on it
|The library declared the dependency on `implementation`; it is not on the consumer's compile classpath.
|Declare it in the consumer, or put it on `api` in the library if the library's API exposes its types.
|`Unresolved reference 'compile'` (Kotlin), `Could not find method compile()` (Groovy)
|A configuration removed in Gradle 7.0.
|`implementation`, `api`, `runtimeOnly`, `testImplementation`, `testRuntimeOnly`.
|`Failed to load JUnit Platform` in `test`
|The launcher is not on the test runtime classpath.
|`testRuntimeOnly("org.junit.platform:junit-platform-launcher")`.
|`+Dependencies can not be declared against the ... configuration+`
|The configuration is resolvable or consumable.
|Declare on a `dependencyScope` bucket and extend it.
|`+Resolving dependency configuration '...' is not allowed as it is defined as 'canBeResolved=false'+`
|A bucket was asked for its files.
|Resolve a resolvable configuration that extends it.
|`cannot serialize Gradle script object references` (cache)
|The task action uses `configurations`, `project` or another script object.
|Capture the file collection when configuring the task.
|`Could not find group:name:version`
|The version is wrong, or the repository does not have it.
|Check the repository, the version and any content filter.
|A processor does not run
|It is on `compileOnly` or `implementation` instead of `annotationProcessor`.
|`annotationProcessor`, and `compileOnly` for its annotations.
|A class is missing at run time though it compiled
|`compileOnly` (or an `@jar` notation) left it out of the runtime classpath.
|Move it to `implementation` or `runtimeOnly`, or drop `@jar`.
|===

== Gradle 8.14 and Gradle 9

Gradle 8.14 was not available here, so what follows comes from the official upgrade guides and release notes and was _not run here_.

* *The roles.* The role factory methods exist in 8.14 (they were added in 8.4, incubating). In the 8.x line a configuration used in a role it does not suit (resolving a bucket, for instance) produced a deprecation warning at run time; since 9.0 it is the error shown above. The 8.4 release notes announced that the core plugins would
migrate to role-locked configurations in Gradle 9.0.
* *The multi-string notation.* It is not deprecated in 8.14, and works without a warning; the deprecation is from 9.1 and the removal is announced for Gradle 10.
* *`Project` as a notation.* It is not deprecated in 8.14; it is from 9.6 (the Gradle 10 build will fail).
* *The module coordinates of the current project.* Deprecated in 9.3, and in Gradle 10 they will resolve against the repositories.
* *The reports.* The `outgoingVariants` and `resolvableConfigurations` reports of 8.14 list every variant and configuration, with or without attributes; Gradle 9.5 hides the attribute-less ones unless `--all` is given.
* *Gradle 9 itself.* It requires a JVM of version 17 or later to run. The user manual's Groovy and Kotlin DSL examples are the same for both lines.

Announced for Gradle 10 and not released: the errors for the multi-string notation and for `Project` as a notation, the change in resolving one's own module coordinates, and the configuration cache on by default (which rejects the pattern shown in "Resolving at execution time, and the configuration cache").

Source: https://docs.gradle.org/8.4/release-notes.html#easier-to-create-role-focused-configurations[Gradle 8.4 release notes],
https://docs.gradle.org/current/userguide/upgrading_version_8.html#deprecated_configuration_usage[Gradle: Using configurations incorrectly],
https://docs.gradle.org/current/userguide/upgrading_version_9.html#dependency_project_notation[Gradle: Deprecation of using Project objects as dependency notation]

== Where the books are outdated

_Gradle in Action_ (Muschko, Manning 2014) was written for Gradle 1.7, and its chapters 5 and 6 are about dependencies. The model it teaches (configurations, module, file and project dependencies, exclusions, repositories) is still right. What changed around it:

[cols="3,4",options="header"]
|===
|Book statement or practice|Current status

|`compile`, `runtime`, `testCompile` and `testRuntime`
|Removed in Gradle 7.0. Use `implementation`, `api`, `compileOnly`, `runtimeOnly`, `testImplementation` and `testRuntimeOnly` (the error is shown above).
|`compile project(':x')` in a multi-project build
|`implementation project(':x')` or `api project(':x')`, and the choice decides what consumers can compile against.
|`providedCompile` for the container's servlet API in a WAR
|Still there with the War plugin; `compileOnly` is the general mechanism.
|Versions repeated or kept in `ext` properties
|Version catalogs (stable in 7.4).
|The Groovy DSL only
|The Kotlin DSL is the default of `gradle init` since 8.2; both are shown on this page.
|===

Dynamic versions, repositories and the dependency cache, which the book also covers, are on
xref:programming-languages/jvm-build-tools/gradle/platforms-constraints-and-rich-versions.adoc[Platforms, Constraints & Rich Versions],
xref:programming-languages/jvm-build-tools/gradle/repositories-and-content-filtering.adoc[Repositories & Content Filtering] and
xref:programming-languages/jvm-build-tools/gradle/dependency-locking-verification-and-caching.adoc[Dependency Locking, Verification & Caching].

== The same in Maven and in Ant

[cols="2,3,3,3",options="header"]
|===
|Question|Gradle|Maven|Ant with Ivy

|Where is a dependency declared?
|On a configuration: `implementation("g:a:v")`.
|In `<dependencies>`, with a `<scope>`.
|In `<dependencies>` of `ivy.xml`, with `+conf="compile->default"+`.
|Which classpath does it join?
|The resolvable configurations that extend the bucket.
|The scope decides: compile, runtime, test classpaths.
|The configurations you resolve (`+<ivy:resolve conf=...>+`, `+<ivy:cachepath conf=...>+`).
|Does it reach my consumers?
|`api`: compile and runtime. `implementation`, `runtimeOnly`: runtime only.
|`compile` and `runtime` scopes are transitive; `provided` and `test` are not.
|The `+->+` mapping decides which of the dependency's configurations are offered.
|Is the compile-time interface separate from the runtime one?
|Yes: `apiElements` and `runtimeElements`.
|No: one POM, scopes flattened.
|No built-in distinction; only the convention of `compile` and `runtime` configurations.
|Where is a custom group of dependencies written?
|A configuration of your own.
|A plugin's own `<dependencies>`; there is no named classpath of your own.
|A configuration in `ivy.xml`.
|===
