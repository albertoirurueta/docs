This page is written against Apache Maven 3.10.0 with the Apache Maven Install Plugin 3.2.0, the Apache Maven Deploy Plugin 3.2.0,
the Source Plugin 3.4.0, the Javadoc Plugin 3.12.0 and the Site Plugin 3.22.0. Every example marked as run was executed on JDK 26 on
2026-10-16 in scratch copies of the *tidepool* project (the parent `io.tidepool:tidepool-parent` with `tidepool-model`,
`tidepool-engine` and `tidepool-cli`). Maven 3.9.16 and Maven 4.0.0-rc-7 (a release candidate) were run wherever the page says so.
In the output, `<lab>` is the scratch directory, `<proj>` is the directory of the project being built, the local repository was
`<lab>/m2` (set with `-Dmaven.repo.local`, so the real `+~/.m2/repository+` was not used), lines were filtered with `grep` (said each
time), transfer sizes and speeds were cut, and the timestamp of a snapshot upload is written `TS` because it changes on every run.
*Nothing was published to a real server.* The repositories were directories reached through `file:` URLs, and, for credentials, a
small Python HTTP server on `localhost` that is described below. Publishing to Maven Central is on
xref:programming-languages/jvm-build-tools/maven/publishing-to-maven-central.adoc[Publishing to Maven Central] and is "not run here".

Building an artifact is only half of a build's job; the other half is making it available to somebody else. Maven splits that
into two steps that are easy to confuse. *Install* copies the result into the *local* repository of the machine, so that other
projects built on the same machine can use it. *Deploy* uploads it to a *remote* repository, so that the rest of the world
can. The address of that remote repository is not a property of the plugin but of the project, and lives in the POM element
`distributionManagement`. This page covers the two plugins, that element, the credentials a remote repository asks for, what exactly
gets written, and what changed in Maven 3.10 and Maven 4. The repositories themselves (layout, mirrors, managers) are on
xref:programming-languages/jvm-build-tools/maven/repositories-mirrors-and-repository-managers.adoc[Repositories, Mirrors & Repository Managers];
`settings.xml` and encrypted passwords on
xref:programming-languages/jvm-build-tools/maven/settings-xml-and-password-encryption.adoc[settings.xml & Password Encryption]; the release
process that ends in a deploy on
xref:programming-languages/jvm-build-tools/maven/releasing.adoc[Releasing]. The scenario is on the
xref:programming-languages/jvm-build-tools/index.adoc[section landing page].

== Where install and deploy sit

`install` and `deploy` are the last two phases of the default lifecycle (the others are on
xref:programming-languages/jvm-build-tools/maven/build-lifecycle.adoc[Build Lifecycle]). Each is a phase with one default binding,
and both are bound to the goal of the same name for every packaging that produces an artifact:

[cols="1,2,3",options="header"]
|===
| Phase | Default goal | What it does
| `package` | `jar:jar` for a JAR | Builds the artifact in `target/`; it is not copied anywhere yet.
| `verify` | none for most packagings | Where checks on the package (integration tests, quality gates) belong.
| `install` | `install:install` | Copies the project's artifacts into the *local* repository.
| `deploy` | `deploy:deploy` | Uploads the project's artifacts to the *remote* repository named in `distributionManagement`.
|===

A phase runs every phase before it, so `mvn deploy` also installs; there is no way to deploy without installing except by calling the
goal directly (`mvn deploy:deploy`, which needs an already built package) or skipping the install (below).

[mermaid]
----
flowchart LR
    PKG["package: target/*.jar"] --> VER["verify"]
    VER --> INS["install:install"]
    INS --> LOCAL[("local repository (default: user home .m2/repository)")]
    INS --> DEP["deploy:deploy"]
    DEP --> REL["distributionManagement/repository (release versions)"]
    DEP --> SNAP["distributionManagement/snapshotRepository (SNAPSHOT versions)"]
    SITE["site:deploy (separate goal)"] --> STE["distributionManagement/site"]
----

The diagram shows the two uploads that `deploy:deploy` chooses between by the version of the project, and the site, which is not
part of the default lifecycle and has its own goal.

Source: https://maven.apache.org/guides/introduction/introduction-to-the-lifecycle.html[Maven: Introduction to the Build Lifecycle]

== The lab: tidepool with a distributionManagement

The parent POM of the lab pins the plugins in `pluginManagement` (which is why the versions above are known, see
xref:programming-languages/jvm-build-tools/maven/plugins-and-their-configuration.adoc[Maven Plugins & Their Configuration]) and declares
two repositories. Their URLs are built from a property, so that a command line can point the same POM somewhere else, and the base
is a directory inside the project:

.pom.xml (parent, abridged)
[source,xml]
----
  <properties>
    <repo.url>file://${maven.multiModuleProjectDirectory}/build/repo</repo.url>
  </properties>

  <distributionManagement>
    <repository>
      <id>tidepool-releases</id>
      <url>${repo.url}/releases</url>
    </repository>
    <snapshotRepository>
      <id>tidepool-snapshots</id>
      <url>${repo.url}/snapshots</url>
    </snapshotRepository>
  </distributionManagement>
----

`+${maven.multiModuleProjectDirectory}+` is the directory that contains the `.mvn` directory (or the directory Maven was started
in, when there is none), and it exists on 3.9.16, 3.10.0 and 4.0.0-rc-7. Maven 3.10 and 4 also have `+${project.rootDirectory}+`,
but 3.9.16 leaves that expression unresolved in a URL, so the older name is the portable one (see
xref:programming-languages/jvm-build-tools/maven/inheritance-aggregation-and-the-effective-pom.adoc[Inheritance, Aggregation & the Effective POM]).
The `id` values, not the URLs, are what links the repository to the credentials in `settings.xml`.

Source: https://maven.apache.org/pom.html#Distribution_Management[Maven: POM Reference, Distribution Management]

== install: the local repository

=== What it writes

The Install Plugin has three goals: `install:install` (bound to the `install` phase), `install:install-file` (for a file that no
project built, see below) and `install:help`. Running the phase for the whole *tidepool* reactor
(`mvn -B install`, lines filtered with `+grep -E "install:|Installing|BUILD"+`) printed:

[source,text]
----
[INFO] --- install:3.2.0:install (default-install) @ tidepool-parent ---
[INFO] Installing pom.xml to <lab>/m2/io/tidepool/tidepool-parent/1.0.0-SNAPSHOT/tidepool-parent-1.0.0-SNAPSHOT.pom
[INFO] --- install:3.2.0:install (default-install) @ tidepool-model ---
[INFO] Installing tidepool-model/pom.xml to <lab>/m2/io/tidepool/tidepool-model/1.0.0-SNAPSHOT/tidepool-model-1.0.0-SNAPSHOT.pom
[INFO] Installing tidepool-model/target/tidepool-model-1.0.0-SNAPSHOT.jar to <lab>/m2/io/tidepool/tidepool-model/1.0.0-SNAPSHOT/tidepool-model-1.0.0-SNAPSHOT.jar
[INFO] --- install:3.2.0:install (default-install) @ tidepool-engine ---
[INFO] Installing tidepool-engine/pom.xml to <lab>/m2/io/tidepool/tidepool-engine/1.0.0-SNAPSHOT/tidepool-engine-1.0.0-SNAPSHOT.pom
[INFO] Installing tidepool-engine/target/tidepool-engine-1.0.0-SNAPSHOT.jar to <lab>/m2/io/tidepool/tidepool-engine/1.0.0-SNAPSHOT/tidepool-engine-1.0.0-SNAPSHOT.jar
[INFO] --- install:3.2.0:install (default-install) @ tidepool-cli ---
[INFO] Installing tidepool-cli/pom.xml to <lab>/m2/io/tidepool/tidepool-cli/1.0.0-SNAPSHOT/tidepool-cli-1.0.0-SNAPSHOT.pom
[INFO] Installing tidepool-cli/target/tidepool-cli-1.0.0-SNAPSHOT.jar to <lab>/m2/io/tidepool/tidepool-cli/1.0.0-SNAPSHOT/tidepool-cli-1.0.0-SNAPSHOT.jar
[INFO] BUILD SUCCESS
----

The parent installs only its POM, because a `pom` packaging has no JAR (the packaging is in
xref:programming-languages/jvm-build-tools/maven/pom-fundamentals.adoc[POM Fundamentals]). The modules install their POM *and* their JAR; the
POM matters as much as the JAR, because it is what a consumer reads to find the transitive dependencies. In the local repository a
module looks like this (`find tidepool-model -type f | sort`):

[source,text]
----
tidepool-model/1.0.0-SNAPSHOT/_remote.repositories
tidepool-model/1.0.0-SNAPSHOT/maven-metadata-local.xml
tidepool-model/1.0.0-SNAPSHOT/tidepool-model-1.0.0-SNAPSHOT.jar
tidepool-model/1.0.0-SNAPSHOT/tidepool-model-1.0.0-SNAPSHOT.pom
tidepool-model/maven-metadata-local.xml
----

There are no checksum files: the Install Plugin 3.2.0 writes none (a deploy does, below). `_remote.repositories` is a record of where each
file came from, kept by Maven Resolver:

[source,text]
----
#NOTE: This is a Maven Resolver internal implementation file, its format can be changed without prior notice.
tidepool-model-1.0.0-SNAPSHOT.jar>=
tidepool-model-1.0.0-SNAPSHOT.pom>=
----

The `>=` with nothing after it means the file was put there by an install, from no repository; a file downloaded from the repository
with the id `central` reads `>central=`, and Resolver then uses it only for builds that list that repository (the effect is on
xref:programming-languages/jvm-build-tools/maven/repositories-mirrors-and-repository-managers.adoc[Repositories, Mirrors & Repository Managers]).
`maven-metadata-local.xml` is the local version of the metadata that a remote repository keeps, here for a snapshot:

[source,xml]
----
<?xml version="1.0" encoding="UTF-8"?>
<metadata modelVersion="1.1.0">
  <groupId>io.tidepool</groupId>
  <artifactId>tidepool-model</artifactId>
  <versioning>
    <lastUpdated>TIMESTAMP</lastUpdated>
    <snapshot>
      <localCopy>true</localCopy>
    </snapshot>
    <snapshotVersions>
      <snapshotVersion>
        <extension>pom</extension>
        <value>1.0.0-SNAPSHOT</value>
        <updated>TIMESTAMP</updated>
      </snapshotVersion>
      <snapshotVersion>
        <extension>jar</extension>
        <value>1.0.0-SNAPSHOT</value>
        <updated>TIMESTAMP</updated>
      </snapshotVersion>
    </snapshotVersions>
  </versioning>
  <version>1.0.0-SNAPSHOT</version>
</metadata>
----

(`TIMESTAMP` replaces the install time, which changes on every run.) `localCopy` tells the resolver that this snapshot is a copy that was installed locally, not downloaded from a timestamped build in a remote repository.

Source: https://maven.apache.org/plugins/maven-install-plugin/usage.html#The_install.3Ainstall_goal[Maven Install Plugin: Usage, the install:install goal]

=== The parameters

The parameters below come from `help:describe -Dplugin=org.apache.maven.plugins:maven-install-plugin:3.2.0 -Ddetail`.

[cols="2,2,5",options="header"]
|===
| Goal and parameter | User property | Meaning
| `install` `skip` | `maven.install.skip` | Do not install. For artifacts that must not reach the local repository.
| `install` `installAtEnd` | `installAtEnd` | Install every project of the reactor at the end of the build instead of during each project's own `install` phase; when the build fails, nothing is installed. Described as experimental by the plugin.
| `install` `allowIncompleteProjects` | `allowIncompleteProjects` | A project with a packaging other than `pom` that has no main artifact is an error by default; this allows it (typical for a project that only attaches an assembly).
| `install-file` `file` | `file` | The file to install (required).
| `install-file` `groupId`, `artifactId`, `version`, `packaging` | same names | Coordinates; taken from `pomFile` or from a `pom.xml` inside the JAR when absent.
| `install-file` `classifier`, `sources`, `javadoc` | same names | A classifier for the file, or the bundled sources and Javadoc to install beside it.
| `install-file` `pomFile`, `generatePom` | `pomFile`, `generatePom` | An existing POM, or generate a minimal one when no POM is given (the default when the local repository has none yet).
| `install-file` `localRepositoryPath` | `localRepositoryPath` | Install into a specific directory instead of the configured local repository.
|===

== distributionManagement

`distributionManagement` says where the *outputs* of this project go. It is not to be confused with `<repositories>`, which says
where the project's *inputs* come from. The element has these children:

[cols="2,5",options="header"]
|===
| Element | Meaning
| `repository` | Where release versions are uploaded. Children: `id`, `name`, `url`, `layout`, `uniqueVersion`.
| `snapshotRepository` | Where `-SNAPSHOT` versions are uploaded. If it is absent, `repository` is used for snapshots too.
| `site` | Where `site:deploy` uploads the generated site (`id`, `name`, `url`), see below.
| `relocation` | Tells consumers that the artifact moved to other coordinates.
| `downloadUrl` | A page where users can download the artifact, for people; no tool reads it.
| `status` | The status of the artifact in the remote repository (`none`, `converted`, `partner`, `deployed`, `verified`). The reference says never to write it by hand, because Maven sets it when the project is transported to the repository.
|===

The `layout` (`default` or `legacy`) and `uniqueVersion` children date from Maven 2. Maven 3 supports only the default layout, and
`uniqueVersion` is ignored: a run with `<uniqueVersion>false</uniqueVersion>` in the repository, on a project without a
`snapshotRepository`, still wrote a timestamped file with a build number (see the next section).

=== The id is the link to the credentials

The `<id>` of a `repository`, `snapshotRepository` or `site` is the name that Maven looks up in the `<servers>` of `settings.xml` for the
user name and password (below). The id is arbitrary, but it identifies the repository among all the others of the build, so it must be
unique. A typo in the id does not fail the build: the upload is simply attempted without credentials, and a protected repository
answers `401`.

=== snapshotRepository is optional

Without a `snapshotRepository`, a snapshot version is sent to `repository`. Removing it from the lab and deploying `tidepool-model`
(filtered with `+grep -E "Uploaded to.*(jar|pom) |BUILD"+`) printed:

[source,text]
----
[INFO] Uploaded to tidepool-releases: file://<proj>/build/repo/releases/io/tidepool/tidepool-model/1.0.0-SNAPSHOT/tidepool-model-1.0.0-TS-1.pom
[INFO] Uploaded to tidepool-releases: file://<proj>/build/repo/releases/io/tidepool/tidepool-model/1.0.0-SNAPSHOT/tidepool-model-1.0.0-TS-1.jar
[INFO] BUILD SUCCESS
----

The files of a snapshot landed under `releases`, which is a trap: a repository manager that keeps release and snapshot
repositories apart may reject the upload. Keep both elements.

=== No distributionManagement at all

A project without the element cannot be deployed by the lifecycle. Deploying the same module from a POM without it failed in the Deploy
Plugin, after the build had succeeded:

[source,text]
----
[ERROR] Failed to execute goal org.apache.maven.plugins:maven-deploy-plugin:3.2.0:deploy (default-deploy) on project tidepool-model: Deployment failed: repository element was not specified in the POM inside distributionManagement element or in -DaltDeploymentRepository=id::url parameter -> [Help 1]
----

The message names the two ways out, the POM element and the `altDeploymentRepository` parameter described below.

Source: https://maven.apache.org/pom.html#Distribution_Management[Maven: POM Reference, Distribution Management]

== deploy: what is uploaded

=== A snapshot

`mvn -B -pl tidepool-model deploy` (filtered with `+grep -E "deploy:|Uploaded|BUILD"+`, the preceding phases are the usual ones) printed:

[source,text]
----
[INFO] --- deploy:3.2.0:deploy
[INFO] Uploaded to tidepool-snapshots: file://<proj>/build/repo/snapshots/io/tidepool/tidepool-model/1.0.0-SNAPSHOT/tidepool-model-1.0.0-TS-1.pom
[INFO] Uploaded to tidepool-snapshots: file://<proj>/build/repo/snapshots/io/tidepool/tidepool-model/1.0.0-SNAPSHOT/tidepool-model-1.0.0-TS-1.jar
[INFO] Uploaded to tidepool-snapshots: file://<proj>/build/repo/snapshots/io/tidepool/tidepool-model/1.0.0-SNAPSHOT/maven-metadata.xml
[INFO] Uploaded to tidepool-snapshots: file://<proj>/build/repo/snapshots/io/tidepool/tidepool-model/maven-metadata.xml

the date, the time in UTC and the sequence number), and the directory `1.0.0-SNAPSHOT` still carries the literal version. Everything the
resolver needs to find the newest one is in `maven-metadata.xml` files. After the build, with the checksum files included, the repository contained (`find build/repo -type f | sort`):

----
<?xml version="1.0" encoding="UTF-8"?>
<metadata modelVersion="1.1.0">
  <groupId>io.tidepool</groupId>
  <artifactId>tidepool-model</artifactId>

    <lastUpdated>DATETIME</lastUpdated>

    </snapshot>
    <snapshotVersions>
      <snapshotVersion>
        <extension>pom</extension>
        <value>1.0.0-DATE.TIME-2</value>
        <updated>DATETIME</updated>
      </snapshotVersion>
      <snapshotVersion>
        <extension>jar</extension>
        <value>1.0.0-DATE.TIME-2</value>
        <updated>DATETIME</updated>
      </snapshotVersion>
    </snapshotVersions>

----

`timestamp` and `buildNumber` name the newest snapshot, and each `snapshotVersion` entry maps an extension (and a classifier) to the
value to download. The other file, in the artifact's own directory, lists the versions the repository knows about:

[source,xml]
----
<?xml version="1.0" encoding="UTF-8"?>
<metadata>
  <groupId>io.tidepool</groupId>
  <artifactId>tidepool-model</artifactId>
  <versioning>
    <versions>
      <version>1.0.0-SNAPSHOT</version>
    </versions>
    <lastUpdated>DATETIME</lastUpdated>
  </versioning>
</metadata>
----

A consumer that depends on `1.0.0-SNAPSHOT` reads these files, and downloads the newest timestamped build; the update policy (`daily`
by default) decides how often it looks (see
xref:programming-languages/jvm-build-tools/maven/versions-snapshots-and-ranges.adoc[Versions, Snapshots & Ranges]). To check that the
repository is usable, a new project that declares the directory as a repository and depends on `tidepool-cli:1.0.0-SNAPSHOT`, with an
empty local repository, resolved the whole graph (`dependency:list`, filtered):

----

=== Checksums

For every file Maven also uploads a checksum, by default `.sha1` and `.md5`. They are the hash of the bytes sent, so a consumer
(or a repository manager) can detect corruption:

[source,text]
----
$ cat tidepool-model-1.0.0-TS-1.jar.sha1
4323ad73b2363318d68170288e32a1c41bd8d42b
$ shasum -a 1 tidepool-model-1.0.0-TS-1.jar
4323ad73b2363318d68170288e32a1c41bd8d42b  tidepool-model-1.0.0-TS-1.jar
----

The algorithms are a Maven Resolver setting, `aether.checksums.algorithms`, a comma-separated list that defaults to `SHA-1,MD5`. A
deploy with `-Daether.checksums.algorithms=SHA-1,SHA-256,SHA-512,MD5` on 3.10.0 listed (`ls | grep jar`):

[source,text]
----
tidepool-model-1.0.0-TS-1.jar
tidepool-model-1.0.0-TS-1.jar.md5
tidepool-model-1.0.0-TS-1.jar.sha1
tidepool-model-1.0.0-TS-1.jar.sha256
tidepool-model-1.0.0-TS-1.jar.sha512
----

The same property with `SHA-1,SHA-256` also worked on Maven 3.9.16 and 4.0.0-rc-7. Central requires `.md5` and `.sha1` files and accepts the
stronger ones in addition (see
xref:programming-languages/jvm-build-tools/maven/publishing-to-maven-central.adoc[Publishing to Maven Central]); the verification a consumer
can do with them is on
xref:programming-languages/jvm-build-tools/supply-chain-security.adoc[Supply Chain Security].

=== deployAtEnd

`-DdeployAtEnd=true` (the user property has the same name as the parameter) makes each project only register what it would deploy;
the uploads happen after the last project has built successfully:

[source,text]
----
[INFO] Deferring deploy for io.tidepool:tidepool-parent:1.0.0-SNAPSHOT at end
[INFO] Deferring deploy for io.tidepool:tidepool-model:1.0.0-SNAPSHOT at end
[INFO] Deferring deploy for io.tidepool:tidepool-engine:1.0.0-SNAPSHOT at end
[INFO] Uploaded to tidepool-snapshots: file://<proj>/build/repo/snapshots/io/tidepool/tidepool-engine/1.0.0-SNAPSHOT/tidepool-engine-1.0.0-TS-1.jar
[INFO] Uploaded to tidepool-snapshots: file://<proj>/build/repo/snapshots/io/tidepool/tidepool-model/1.0.0-SNAPSHOT/tidepool-model-1.0.0-TS-1.jar
[INFO] Uploaded to tidepool-snapshots: file://<proj>/build/repo/snapshots/io/tidepool/tidepool-cli/1.0.0-SNAPSHOT/tidepool-cli-1.0.0-TS-1.jar
[INFO] BUILD SUCCESS
----

(The last project, `tidepool-cli`, triggers the uploads, so its own `Deferring` line is not printed. The POM uploads and the parent are left out by the filter. The uploads are not in reactor order: this run uploaded the engine, the model
and then the command line module.) The point of `deployAtEnd` is to avoid publishing three of four modules when the fourth one fails its tests. It
is not atomic: if the upload of the third module fails, the first two are already in the repository, and Maven cannot take them back. The
plugin's description of the parameter says so explicitly. For something that must be all-or-nothing, deploy to a staging area and
promote it (what Central does, see
xref:programming-languages/jvm-build-tools/maven/publishing-to-maven-central.adoc[Publishing to Maven Central]). The Install Plugin has the
equivalent `installAtEnd`, above.

=== Skipping, and the typo that fails

`maven.deploy.skip` (parameter `skip`) skips the upload. A module that is a test harness or an example, never meant to be published,
sets it in its own POM:

[source,xml]
----
<properties>
  <maven.deploy.skip>true</maven.deploy.skip>
</properties>
----

and `-Dmaven.deploy.skip=true` on the command line does it for the whole build:

[source,text]
----
[INFO] --- deploy:3.2.0:deploy (default-deploy) @ tidepool-parent ---
[INFO] Skipping artifact deployment
[INFO] --- deploy:3.2.0:deploy (default-deploy) @ tidepool-model ---
[INFO] Skipping artifact deployment
[INFO] --- deploy:3.2.0:deploy (default-deploy) @ tidepool-engine ---
[INFO] Skipping artifact deployment
[INFO] --- deploy:3.2.0:deploy (default-deploy) @ tidepool-cli ---
[INFO] Skipping artifact deployment
[INFO] BUILD SUCCESS
----

Since Deploy Plugin 3.0.0-M2 the value is not only a boolean: `releases` skips when the version is a release and `snapshots` skips
when it is a snapshot (`-Dmaven.deploy.skip=snapshots` on the lab, whose version is a snapshot, printed `Skipping artifact deployment`
again); any other value *fails the build*, which protects against a typo in a control that exists to prevent a publication:

[source,text]
----
[ERROR] Failed to execute goal org.apache.maven.plugins:maven-deploy-plugin:3.2.0:deploy (default-deploy) on project tidepool-model: Unrecognized value 'snapshto' for maven.deploy.skip. Accepted values: true, false, releases, snapshots. -> [Help 1]
----

== altDeploymentRepository

`-DaltDeploymentRepository=id::url` overrides the repository of the POM for one run, which is how a CI job publishes a branch build to a
scratch location without touching the POM. Deploying `tidepool-model` from the POM *without* `distributionManagement`, with
`+-DaltDeploymentRepository=lab::file://<proj>/build/alt+`, worked (filter: `+grep -E "deploy:|Uploaded to|BUILD"+`):

[source,text]

[INFO] --- deploy:3.2.0:deploy

== Credentials

A real repository does not accept anonymous uploads. Maven finds the user name and password in `settings.xml`, in the `<server>` whose
`<id>` equals the id of the repository (a `settings.xml` is per user and never goes into the project; the elements are on
xref:programming-languages/jvm-build-tools/maven/settings-xml-and-password-encryption.adoc[settings.xml & Password Encryption]).

The runs below use a Python file server on `localhost:18090` that accepts a `PUT` only with HTTP basic authentication for the user
`deployer` with the placeholder password `changeit-example`, logs what it receives, and, to imitate a rule of repository managers, answers
`400` to a second upload of a release file. That rule is the lab's imitation, not the behaviour of any particular product. The lab uses
the project as version `1.0.0`, and `+-Drepo.url=http://localhost:18090+` sends both repositories there.

First with no `<server>` (`settings-none.xml`, an empty `<settings/>`), the build fails at the first `PUT`; the log of the server
shows both files denied:

[source,text]
----
[ERROR] Failed to execute goal org.apache.maven.plugins:maven-deploy-plugin:3.2.0:deploy (default-deploy) on project tidepool-model: Failed to deploy artifacts: Could not transfer artifact io.tidepool:tidepool-model:pom:1.0.0 from/to tidepool-releases (http://localhost:18090/releases): HTTP Status: 401 -> [Help 1]

=== Maven 3.10: credentials are scoped to an origin

According to the release notes of 3.10.0, the credentials of a server are sent only to the origin (scheme, host and port) of the
repositories and mirrors that have that id, and the match on the id is exact. Maven finds those repositories among the ones declared in
`settings.xml` and on the command line; a `distributionManagement` repository of the POM is *not* among them in these runs, because the
warning appeared for the `tidepool-releases` id that the POM itself declares. To bind the credentials explicitly, name the origin in the
server, which the same release notes document as `repositoryOrigins` (the full description is on the settings page):

.settings-origins.xml (the snapshots server is the same)
[source,xml]
----
    <server>
      <id>tidepool-releases</id>
      <username>deployer</username>
      <password>changeit-example</password>
      <repositoryOrigins>
        <repositoryOrigin>http://localhost:18090</repositoryOrigin>
      </repositoryOrigins>
    </server>
----

The property `maven.repository.credentialScope=strict` makes Maven refuse credentials that are not bound this way. A deploy with
`settings-origins.xml` and `-Dmaven.repository.credentialScope=strict` on a fresh server, per Maven version
(`+grep -E "WARN|Uploaded|BUILD|ERROR\] Failed"+`; the `Failed to execute` line is cut after the goal):

=== Release versions are immutable

Deploying the same release a second time, with the same credentials, was refused by the lab server:

[source,text]
----
[ERROR] BUILD FAILURE
[ERROR] Failed to execute goal org.apache.maven.plugins:maven-deploy-plugin:3.2.0:deploy (default-deploy) on project tidepool-model: Failed to deploy artifacts: Could not transfer artifact io.tidepool:tidepool-model:pom:1.0.0 from/to tidepool-releases (http://localhost:18090/releases): HTTP Status: 400 -> [Help 1]
----

[source,text]
----
PUT /releases/io/tidepool/tidepool-model/1.0.0/tidepool-model-1.0.0.pom user=deployer ok
PUT /releases/io/tidepool/tidepool-model/1.0.0/tidepool-model-1.0.0.jar user=deployer ok
----

`HTTP Status: 400` here is the lab's imitation of a repository manager that does not allow redeploying a release. A plain file repository
(`file:`) has no such rule and overwrites silently, so a local test does not catch a pipeline that redeploys a release. The rule is
right: a consumer that cached `1.0.0` must never see different bytes under that name. The way out is a new version, not a deploy of the
same one (see
xref:programming-languages/jvm-build-tools/maven/releasing.adoc[Releasing]).

=== Other transports and how the password is protected

`file:` and `http:`/`https:` work with the native HTTP transport of Maven 3.9 and later. `scp:`, `sftp:` and `ftp:` need a Wagon
provider added as a build extension, which the repositories page describes as "Transports: native and Wagon"; they were not run here, and
their `privateKey` and `passphrase` settings are in the server table of the settings page. The password in the file should be
encrypted with the master-password mechanism of Maven 3 or `mvnenc` of Maven 4 (the settings page runs both), or come from an
environment variable in the CI job.

Source: https://maven.apache.org/guides/mini/guide-deployment-security-settings.html[Maven: Deployment Security Settings]

Source: https://maven.apache.org/settings.html#Servers[Maven: Settings Reference, Servers]

== Attached artifacts: sources and Javadoc

A repository consumer, and Central, wants more than the JAR: a `-sources.jar` for the IDE and a `-javadoc.jar` for the documentation.
The JAR Plugin attaches nothing but the main artifact; other plugins *attach* extra files to the project, and `install` and `deploy`
publish every attached artifact. The Source Plugin's `jar-no-fork` goal (the plain `jar` goal first runs the `generate-sources` phase again, which `jar-no-fork` does not)
and the Javadoc Plugin's `jar` goal are the usual ones, bound to the package phase with an execution each:

.pom.xml (parent, added to the lab)
[source,xml]
----
    <plugins>
      <plugin>
        <artifactId>maven-source-plugin</artifactId>
        <executions>
          <execution>
            <id>attach-sources</id>
            <goals><goal>jar-no-fork</goal></goals>
          </execution>
        </executions>
      </plugin>
      <plugin>
        <artifactId>maven-javadoc-plugin</artifactId>
        <executions>
          <execution>
            <id>attach-javadocs</id>
            <goals><goal>jar</goal></goals>
          </execution>
        </executions>
      </plugin>
    </plugins>
----

(The versions come from `pluginManagement`; the executions are named so that `-X` and the logs show where each JAR comes from, and
because ids must be unique within a plugin, see
xref:programming-languages/jvm-build-tools/maven/build-lifecycle.adoc[Build Lifecycle].) Deploying `tidepool-model`
(`+grep -E "source:|javadoc:|Building jar|Uploaded to.*(jar|pom) |BUILD"+`):

[source,text]
----
[INFO] Building jar: <proj>/tidepool-model/target/tidepool-model-1.0.0-SNAPSHOT.jar
[INFO] --- source:3.4.0:jar-no-fork
[INFO] Building jar: <proj>/tidepool-model/target/tidepool-model-1.0.0-SNAPSHOT-sources.jar
[INFO] --- javadoc:3.12.0:jar

== deploy-file: uploading a file that is not a project

`deploy:deploy-file` uploads files that no project of the current build produced: a vendor JAR for the company repository, or the output
of a non-Maven build. It needs no POM at all. With a JAR compiled with `javac` and packed with `jar` (so with no `pom.xml` inside), and
the sources and Javadoc JARs of the earlier run, from a directory without a POM
(`+grep -E "deploy-file|Uploaded|BUILD"+`; `<df>` is that directory):

[source,bash]
----
mvn -B org.apache.maven.plugins:maven-deploy-plugin:3.2.0:deploy-file -Dfile=tidepool-extra.jar \
    -DgroupId=io.tidepool -DartifactId=tidepool-extra -Dversion=1.0.0 -Dpackaging=jar \
    -Durl=file://<df>/repo -DrepositoryId=tidepool-releases \
    -Dsources=tidepool-extra-sources.jar -Djavadoc=tidepool-extra-javadoc.jar
----

[source,text]
----
[INFO] --- deploy:3.2.0:deploy-file
[INFO] Uploaded to tidepool-releases: file://<df>/repo/io/tidepool/tidepool-extra/1.0.0/tidepool-extra-1.0.0.jar
[INFO] Uploaded to tidepool-releases: file://<df>/repo/io/tidepool/tidepool-extra/1.0.0/tidepool-extra-1.0.0.pom

=== The embedded POM that wins

A JAR built by Maven contains its own POM in `META-INF/maven/<groupId>/<artifactId>/pom.xml`. `deploy-file` takes the POM
from there when no `pomFile` is given, *even if the coordinates on the command line are different*. Uploading the JAR of `tidepool-model` as
`tidepool-extra` (the JAR holds):

[source,text]
----
META-INF/maven/io.tidepool/tidepool-model/pom.xml
META-INF/maven/io.tidepool/tidepool-model/pom.properties
----

succeeded, and the POM it wrote for `tidepool-extra` was the one of `tidepool-model`, with its parent and its dependency (the
`+grep -E "BUILD|artifactId|<version>"+` of the run):

[source,text]
----
[INFO] BUILD SUCCESS
    <artifactId>tidepool-parent</artifactId>
    <version>1.0.0-SNAPSHOT</version>
  <artifactId>tidepool-model</artifactId>
      <artifactId>junit-jupiter</artifactId>
----

`-DgeneratePom=true` did not change it. The artifact was published with the wrong coordinates inside its own POM, and consumers
would resolve the dependencies of another artifact. Pass an explicit POM; the file is the minimum one:

.extra-pom.xml
[source,xml]
----
<project xmlns="http://maven.apache.org/POM/4.0.0">
  <modelVersion>4.0.0</modelVersion>
  <groupId>io.tidepool</groupId>
  <artifactId>tidepool-extra3</artifactId>
  <version>1.0.0</version>
</project>
----

With `-DpomFile=extra-pom.xml` and the coordinates taken from it:

[source,text]
----
[INFO] Uploaded to tidepool-releases: file://<df>/repo2/io/tidepool/tidepool-extra3/1.0.0/tidepool-extra3-1.0.0.jar
[INFO] Uploaded to tidepool-releases: file://<df>/repo2/io/tidepool/tidepool-extra3/1.0.0/tidepool-extra3-1.0.0.pom
[INFO] BUILD SUCCESS
----

== Deploying a site

The `site` child of `distributionManagement` is the target of `site:deploy`, which uploads `target/site` using the same transports and the
same server lookup. Adding

[source,xml]
----
    <site>
      <id>tidepool-site</id>
      <url>${repo.url}/site/${project.artifactId}</url>
    </site>
----

to the parent and running `mvn -B -pl tidepool-model site site:deploy` (the site content and the reports are on
xref:programming-languages/jvm-build-tools/maven/site-and-reporting.adoc[Site & Reporting]; `+grep -E "site:|BUILD"+`) printed:

[source,text]
----
[INFO] --- site:3.22.0:site (default-site) @ tidepool-model ---
[INFO] --- site:3.22.0:deploy (default-cli) @ tidepool-model ---
[INFO] BUILD SUCCESS
----

The pages were written below the site URL. Note the path: `site/tidepool-model/tidepool-model`, with the artifact id twice. The `url`
of a `site` is *inherited by the children with the child's artifact id appended*, which is the intention for a multi-module site (one
directory per module) and a surprise when the parent URL already contains `+${project.artifactId}+`. `help:evaluate` for the child:

[source,text]
----
file://<proj>/build/repo/site/tidepool-model/tidepool-model
file://<proj>/build/repo/releases
----

and the directory listing of `build/repo/site` (first lines of `find . -maxdepth 3 | sort`) was:

[source,text]
----
.
./tidepool-model
./tidepool-model/tidepool-model
./tidepool-model/tidepool-model/css
./tidepool-model/tidepool-model/dependencies.html
./tidepool-model/tidepool-model/dependency-info.html
./tidepool-model/tidepool-model/dependency-management.html
./tidepool-model/tidepool-model/distribution-management.html

The second line of the first listing is the `repository` URL of the same child, for comparison: unlike the site URL it was not extended

from `target/site` rather than with `site:deploy`; see the site page.

== The same job in Ant and Gradle

[cols="2,3,3",options="header"]
|===
| Tool | Local install | Remote publishing
| Maven | `install` phase; `install:install-file` | `deploy` phase; `distributionManagement`; `deploy:deploy-file`
| Ant | the Resolver Ant Tasks `install` (see xref:programming-languages/jvm-build-tools/ant/maven-resolver-ant-tasks.adoc[Maven Resolver Ant Tasks]); Ivy `publish` to a local resolver | the Resolver Ant Tasks `deploy` with a `remoteRepo`; Ivy `publish` with a resolver (see xref:programming-languages/jvm-build-tools/ant/ivy-publishing-and-multi-project.adoc[Ivy: Publishing & Multi-Project Builds])
| Gradle | the `publishToMavenLocal` task of the `maven-publish` plugin | `+publishing { repositories { ... } }+` and `publish` (see xref:programming-languages/jvm-build-tools/gradle/publishing.adoc[Publishing])
|===

The three tools write the same repository layout, which is why a project deployed by one can be consumed by another; the comparison, with
the same *tidepool* modules published to `build/repo` by all of them, is on
xref:programming-languages/jvm-build-tools/repositories-and-publishing-across-tools.adoc[Repositories & Publishing Across Tools].

== Classic problems

* *`HTTP Status: 401` on deploy.* No `<server>` with the right `<id>`, a wrong password, or a password encrypted with a master password the
  build cannot read. Check the id of `distributionManagement` against `settings.xml`, and the log of the server.
* *`HTTP Status: 400` or `409` on the second deploy of a release.* The repository does not allow redeploying a release. Release a new version.
* *`repository element was not specified in the POM`.* No `distributionManagement` and no `altDeploymentRepository`.
* *The snapshots end up in the releases repository,* or are rejected: no `snapshotRepository`.
* *`deploy-file` uploads a POM with other coordinates.* The JAR has an embedded `pom.xml`; pass `-DpomFile`.
* *Some modules were deployed and the build failed.* The default deploys per module; use `deployAtEnd`, and know it is not atomic.
* *`+Unrecognized value ... for maven.deploy.skip+`.* The value must be `true`, `false`, `releases` or `snapshots`.
* *A deploy from a CI job overwrites a developer's snapshot.* Snapshots are shared by design; use CI-friendly versions that put the
  commit in the version (see
  xref:programming-languages/jvm-build-tools/maven/ci-friendly-versions.adoc[CI-Friendly Versions]).
* *A POM with `+${revision}+` is published unresolved on Maven 3.* See the same page.
* *A plugin 4.0 line on Maven 3.* `has unmet prerequisites`, above.

== Where the books are outdated

* Older books describe `deploy:deploy` with the layout in `altDeploymentRepository` (`id::default::url`), the `layout` and `uniqueVersion`
  children of `distributionManagement`, and SCP or WebDAV as the normal transports. Maven 3 has one layout, ignores `uniqueVersion`, uses
  the native HTTP transport and needs a Wagon extension for SCP and FTP.
* Plain `http:` repository URLs for downloads are blocked by default since Maven 3.8.1 (the settings and repositories pages); uploads
  to `localhost` over HTTP, as here, are for tests.
* Publishing to Central through OSSRH (`oss.sonatype.org`) ended on 2025-06-30; see
  xref:programming-languages/jvm-build-tools/maven/publishing-to-maven-central.adoc[Publishing to Maven Central].
* The `release-profile` of the super POM, which added sources and Javadoc JARs to a release, is removed in Maven 3.10 (see
  xref:programming-languages/jvm-build-tools/maven/releasing.adoc[Releasing]); attach them with the executions shown above.

== What was not run here

* Any real repository manager, Central, or an authenticated remote server other than the localhost lab server; the `scp`, `sftp` and
  `ftp` transports with Wagon extensions; `privateKey` authentication.
* `retryFailedDeploymentCount`, `allowIncompleteProjects`, `installAtEnd` combined with failing builds, and the `status` and `downloadUrl`
  elements of `distributionManagement`.
* The test JAR (`test-jar`) and assembly attachments (shown on the pages named above).
