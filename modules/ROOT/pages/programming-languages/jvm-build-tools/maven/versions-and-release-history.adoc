This page is written against Apache Maven 3.10.0 (released on 27 September 2026), with 3.9.16 (13 May 2026) where it differs and
Maven 4.0.0-rc-7 (24 September 2026), a release candidate, where named. Every example marked as run was executed on JDK 26 on
2026-10-16, on macOS, in a scratch directory; output that comes from a run is shown as printed, with the long scratch path
shortened to `<scratch>` and the home directory to `<home>`. The three Maven installations were the ones described in
xref:programming-languages/jvm-build-tools/maven/installation.adoc[Installation]. Dates and Java floors were read from the Maven
releases history page and the release notes on the same day, and the newest versions on Maven Central were checked against them.

Maven's versioning is part of its contract with plugin authors and with users who keep a build for ten years. The number of the
core tells you how much can break when you upgrade: a patch release (3.9.15 to 3.9.16) fixes bugs, a minor release (3.9 to 3.10)
may change defaults and make warnings into errors, and a major release (3 to 4) changes the model and the plugin API. This page
puts the releases on one timeline, says which Java each needs, lists what changed in the releases you are most likely to cross, and
turns the 3.9-to-3.10 changes into a checklist, each item backed by a run. The overview of Maven itself is on the
xref:programming-languages/jvm-build-tools/maven/index.adoc[Apache Maven] page; Ant's equivalent of this page is
xref:programming-languages/jvm-build-tools/ant/versions-and-release-history.adoc[Ant: Versions & Release History] and Gradle's is
xref:programming-languages/jvm-build-tools/gradle/versions-compatibility-and-release-history.adoc[Gradle: Versions, Compatibility & Release History].

== Support policy and end of life

The history page states the policy in one sentence: the Maven team maintains the last version of the last two series of GA
releases, which on 2026-10-16 are 3.10.0 and 3.9.16. Everything older has reached its end of life: the team provides no bug or
security fixes and adds no features. Maven does not distinguish "end of life" from "end of support" and uses only the first term.
The download page calls 3.10.0 "the recommended version for all users" and 3.9.16 "the previous stable minor release", still
maintained, with users encouraged to upgrade. Maven 4.0+ is listed separately as "not yet GA".

Three end-of-life dates are worth remembering:

* Maven 1.x and 2.x: end-of-life notice on 2014-02-18.
* Maven 3.8.9 (2025-06-14) is the last 3.8 release. The history page states that 3.8.9 "and before has now reached its end of
  life" and that new plugin releases require Maven 3.9.0 or later.
* The 3.9 line is maintained because it is one of the last two series; by the policy's wording that changes when a newer GA series
  appears.

== Java to run Maven, Java to build

The floors above are for the JVM that runs Maven. They are not the Java of your project: the download page says the 3.10 line
"still allows you to build against 1.3 and other JDK versions by using toolchains", and the Maven 4 article says Java 17 "is only

== The plugin compatibility plan

Maven's core and its plugins are released separately ("the core release is independent of plugin releases", say the notes of every
release), so the question "which plugin works with which Maven" has its own answer: the Maven Plugins Compatibility Plan. It sets
the minimum Java and the minimum Maven that plugins and shared components may require. Its milestones, as written on the page:

* until 2012: Maven 2.2.1 and Java 5, plugins in the 2.x line;
* since 2012: Maven 3.0 and Java 7, plugins in 3.x.y;
* since June 2020: the Maven plugin API used by plugins at 3.1.0 or later, and Java 8;
* March 2023: Maven before 3.2.5 is end of life, so plugins use 3.2.5 as their minimum;
* April 2023: Maven before 3.6.3 is end of life, so plugins use 3.6.3 as their minimum;
* February 2024: Maven 4 after 4.0.0-alpha-12 requires Java 17 (by a vote on the mailing list);
* October 2025: Maven before 3.8.3 is end of life, so plugins use 3.9.0 as their minimum.

The history page sums it up: "currently, plugins provide Maven API compatibility down to 3.9.0". The practical rules are to stay
on 3.9.0 or later, to pin every plugin version, and not to expect a new plugin release to work on a Maven that is end of life. The
plugin versions that were the latest stable ones on Maven Central on 2026-10-16 (pre-releases such as the 4.x betas excluded) are
used across this section:

Two consequences follow. A build that never pinned plugins changes behaviour when you move from 3.9.16 to 3.10.0 even if you
change nothing else, which is the argument for the `+<pluginManagement>+` section of the parent POM (see
xref:programming-languages/jvm-build-tools/maven/plugins-and-their-configuration.adoc[Plugins & Their Configuration]). And the
3.9.16 super POM also managed `maven-antrun-plugin` 3.1.0, `maven-assembly-plugin` 3.7.1, `maven-dependency-plugin` 3.7.0 and
`maven-release-plugin` 3.0.1 in a `+<pluginManagement>+` section, which 3.10.0 removed (next section), so a build that relied on
those versions without declaring them gets whatever resolves instead: with no version, the plugin metadata decides, which is
exactly the situation Maven's validation has warned about since Maven 3.

== Upgrading from 3.9 to 3.10: a checklist

The 3.10.0 notes list the "potentially breaking core changes" for a migration from 3.9.x. Each item below says what it is, what it
looks like and what to do; the ones marked "run" were reproduced here with the three Maven versions on a small POM.

=== 1. Stricter POM validation (run)

Maven 3.10 turns warnings that have existed since the 3.1 line into errors for the project being built. The notes name duplicated
dependency entries and duplicated plugin entries in their overview, and list the checks promoted to errors for the project being
built as duplicated plugins, invalid characters in a version, malformed snapshot versions and reserved or malformed repository
ids. The notes add that a parent's `+<relativePath>+` is validated for the first time and
that dependencies keep being validated at the minimal level (a failure there leads to transitive dependencies not being
available). The test POM declares `commons-csv` twice and the compiler plugin twice:

[source,xml]
----
<dependencies>
  <dependency>
    <groupId>org.apache.commons</groupId>
    <artifactId>commons-csv</artifactId>
    <version>1.14.1</version>
  </dependency>
  <dependency>
    <groupId>org.apache.commons</groupId>
    <artifactId>commons-csv</artifactId>
    <version>1.14.1</version>
  </dependency>
</dependencies>

<build>
  <plugins>
    <plugin>
      <artifactId>maven-compiler-plugin</artifactId>
      <version>3.16.0</version>
    </plugin>
    <plugin>
      <artifactId>maven-compiler-plugin</artifactId>
      <version>3.16.0</version>
    </plugin>
  </plugins>
</build>
----

`mvn -B -ntp validate` on Maven 3.9.16 builds successfully and prints warnings (the first nine lines are shown):

[source,text]
----
[INFO] Scanning for projects...
[WARNING] 
[WARNING] Some problems were encountered while building the effective model for org.example.tidepool:tidepool-dup:jar:1.0.0-SNAPSHOT
[WARNING] 'dependencies.dependency.(groupId:artifactId:type:classifier)' must be unique: org.apache.commons:commons-csv:jar -> duplicate declaration of version 1.14.1 @ line 17, column 17
[WARNING] 'build.plugins.plugin.(groupId:artifactId)' must be unique but found duplicate declaration of plugin org.apache.maven.plugins:maven-compiler-plugin @ line 30, column 15
[WARNING] 
[WARNING] It is highly recommended to fix these problems because they threaten the stability of your build.
[WARNING] 
[WARNING] For this reason, future Maven versions might no longer support building such malformed projects.
----

On Maven 3.10.0 the same POM no longer builds (the first five lines are shown; the build stops there with exit status 1):

[source,text]
----
[INFO] Scanning for projects...
[ERROR] [ERROR] Some problems were encountered while processing the POMs:
[ERROR] 'dependencies.dependency.(groupId:artifactId:type:classifier)' must be unique: org.apache.commons:commons-csv:jar -> duplicate declaration of version 1.14.1 @ line 17, column 17
[ERROR] 'build.plugins.plugin.(groupId:artifactId)' must be unique but found duplicate declaration of plugin org.apache.maven.plugins:maven-compiler-plugin @ line 30, column 15
 @ 
----

On Maven 4.0.0-rc-7 (release candidate) the same two problems are errors too, with the POM file and the exact column in the
message (the first seven lines are shown, and the warning about the missing root directory is the one explained above):

[source,text]
----
[WARNING] Unable to find the root directory. Create a .mvn directory in the root directory or add the root="true" attribute on the root project's model to identify it.
[INFO] Scanning for projects...
[ERROR] Encountered 2 problem(s) while processing the POMs
[ERROR] The build could not read 1 project -> [Help 1]
[ERROR]   
[ERROR]   The project org.example.tidepool:tidepool-dup:jar:1.0.0-SNAPSHOT (<scratch>/work/mvn-versions-install/dup/pom.xml) has 2 errors
[ERROR]     'dependencies.dependency.(groupId:artifactId:type:classifier)' must be unique: org.apache.commons:commons-csv:jar -> duplicate declaration of version 1.14.1 @ org.example.tidepool:tidepool-dup:1.0.0-SNAPSHOT, file://<scratch>/work/mvn-versions-install/dup/pom.xml, line 17, column 5
----

The fix is to delete the duplicates. The notes offer `-Dmaven.resolver.validation=off` as a way to "temporarily disable the
stricter validation". That property belongs to Resolver and governs how artifact and metadata coordinates are validated (the
notes' own words: `default` is full validation, `mild` checks only uninterpolated placeholders and `off` is the 3.9 behaviour). Two
things were observed when trying it on this POM with 3.10.0. The lowercase value from the notes fails with an internal error;
the message names an enum constant, so the value is matched case-sensitively against upper-case names:

[source,text]
----
[ERROR] Internal error: java.lang.IllegalArgumentException: No enum constant org.apache.maven.internal.aether.MavenValidatorFactory.ValidationLevel.off -> [Help 1]
----

With `OFF` the property is accepted, but it did not turn the duplicate declarations back into warnings; the build still failed:

[source,text]
----
[INFO] Scanning for projects...
[ERROR] [ERROR] Some problems were encountered while processing the POMs:
[ERROR] 'dependencies.dependency.(groupId:artifactId:type:classifier)' must be unique: org.apache.commons:commons-csv:jar -> duplicate declaration of version 1.14.1 @ line 17, column 17
exit status: 1
----

So treat `maven.resolver.validation` (in upper case, `OFF`, `MILD` or `DEFAULT`) as an escape hatch for the coordinate checks of
the Resolver, and treat duplicate declarations as something to fix in the POM. Both findings are of 3.10.0 as run here; the
release notes describe the property in lower case.

Source: https://maven.apache.org/docs/3.10.0/release-notes.html#Stricter_POM_validation[Maven 3.10.0 release notes: Stricter POM validation]

=== 2. Classpath order: level order instead of pre-order

The notes say that the dependency classpath order changed from depth-first "pre-order" to breadth-first "level-order", aligned with
Maven 4 and Resolver 2.x, and that `-Daether.system.dependencyVisitor=preOrder` restores the old order. The Resolver configuration
page documents the property: it accepts `preOrder`, `postOrder` and `levelOrder`, and its default is `levelOrder` since Resolver
2.0.0 ("in Maven 4 the default is the new levelOrder, while Maven 3 used preOrder"). This could not be reproduced here. With a POM
that declares `commons-csv` (which brings `commons-io` and `commons-codec`), `picocli` and `junit-jupiter`, the compile classpath
(read from the `-X` output of the compiler plugin) and the output of `dependency:build-classpath` had the same order on 3.9.16,
on 3.10.0 with and without `-Daether.system.dependencyVisitor=preOrder` (and with `levelOrder` and `postOrder`), and on 4.0.0-rc-7:
`commons-csv`, `commons-io`, `commons-codec`, `picocli`, then the JUnit artifacts. Either this graph is not one where the two orders
differ once Maven flattens it, or the flag acts on a different step than the one that builds those classpaths. The practical advice
does not depend on it: a build whose result depends on the order of two JARs that contain the same class is already fragile, so
find the duplicate class (the `dependency:analyze` and enforcer rules are in
xref:programming-languages/jvm-build-tools/maven/dependency-analysis-and-convergence.adoc[Dependency Analysis & Convergence])
instead of relying on the order.

=== 3. Super POM changes (run)

The 3.10 super POM removes the deprecated `release-profile` and the plugin management (each project should have its own), sets
`project.build.sourceEncoding` and `project.reporting.outputEncoding` to UTF-8 and sets `project.build.outputTimestamp`, which
makes builds reproducible by default. `help:effective-pom` on the same POM shows it. On 3.10.0 the properties are:

[source,text]
----
<properties>
  <maven.compiler.release>21</maven.compiler.release>
  <project.build.outputTimestamp>1980-02-01T00:00:00Z</project.build.outputTimestamp>
  <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
  <project.reporting.outputEncoding>UTF-8</project.reporting.outputEncoding>
</properties>
----

On 3.9.16 the effective POM had none of those three properties and had a `+<pluginManagement>+` section with four plugins
(`maven-antrun-plugin` 3.1.0, `maven-assembly-plugin` 3.7.1, `maven-dependency-plugin` 3.7.0, `maven-release-plugin` 3.0.1); the
3.10.0 and 4.0.0-rc-7 effective POMs had no `+<pluginManagement>+` at all. The `release-profile` only appears in an effective POM
when it is active, so its removal is taken from the notes ("not run here"). What to do: declare the plugins you use with versions
in your own parent POM, and write the encoding and timestamp properties explicitly if the build must behave the same on 3.9.

=== 4. Reproducible builds are on by default

Because the super POM now supplies `project.build.outputTimestamp` (the value in the effective POM above is
`1980-02-01T00:00:00Z`), the archive plugins write fixed timestamps for entries. If a consumer relied on the timestamp of the
entries in your JAR, set the property to the release time during a release or disable the behaviour; the notes point to the
Reproducible Builds FAQ. The mechanism is covered in
xref:programming-languages/jvm-build-tools/maven/security-and-reproducible-builds.adoc[Security & Reproducible Builds].

=== 5. Repository credentials are scoped to origins (not run here)

In 3.10 the credentials of a settings `+<server>+` are offered only to repositories and mirrors whose origin (scheme, host and
port) Maven could associate with that server id, and the id is matched exactly, so a server entry no longer leaks credentials to
unrelated repositories that share an id prefix. A repository declared in a profile activated through `+<activation>+` or `-P`
contributes no origin, so its credentials must be declared with `+<repositoryOrigins>+`; the notes give this form, shown here with
the placeholders `repo.example.org` and `mirror.example.org` that the notes use:

[source,xml]
----
<server>
  <id>internal</id>
  <username>${env.REPO_USER}</username>
  <password>${env.REPO_PASSWORD}</password>
  <repositoryOrigins>
    <repositoryOrigin>https://repo.example.org</repositoryOrigin>
    <repositoryOrigin>https://mirror.example.org:8443</repositoryOrigin>
  </repositoryOrigins>
</server>
----

This was not run here, because it needs an authenticated repository. The symptom of a missing origin is an authentication failure
(401) from a repository that worked on 3.9; see
xref:programming-languages/jvm-build-tools/maven/settings-xml-and-password-encryption.adoc[settings.xml & Password Encryption] and
xref:programming-languages/jvm-build-tools/maven/repositories-mirrors-and-repository-managers.adoc[Repositories, Mirrors & Repository Managers].

Source: https://maven.apache.org/docs/3.10.0/release-notes.html#Repository_credentials_are_scoped[Maven 3.10.0 release notes: Repository credentials are scoped]

=== 6. Restricted models from repositories, coordinate validation and toolchains

A model resolved from a repository (a dependency's POM, a parent or an imported BOM) now contributes less: restricted
interpolation, profile activation limited to platform-derived criteria, recessive repository merging and rejection of `system`
scoped dependencies, with the `maven.model.dependencyInterpolation.full` property as an opt-out. Resolver 2.x also rejects artifact
and metadata coordinates that cannot be mapped safely to a repository layout. A toolchain that a plugin requests but that is
misconfigured now fails the build instead of silently falling back to the JDK running Maven. None of these was run here (they
need crafted repositories); the notes are the source.

=== 7. Plugin validation

Plugins and extensions are checked against Maven's supported APIs, and warnings may appear at the end of the build. The notes
(3.9.12 and 3.10.0) describe the result as WARNINGs reported at the end of the build and refer to the plugin validation
documentation; it is not an error.

== Maven 4: release candidate

Maven 4.0.0-rc-7 is the seventh release candidate. Its release notes say it is "expected to be the last before the Maven 4.0.0 GA
release", with GA aimed at "the coming weeks, pending community feedback", and that 4.0.0-rc-4 already said it aimed to be the
last. Both notes recommend the upgrade tool, `mvnup check` to detect problems and `mvnup apply` to fix them (the tool is in the
4.0.0-rc-7 distribution next to `mvn`, as the installation page lists). Because the 3.10 line already moved to the same Resolver
lineage, the jump from 3.10 to 4 is smaller than the jump from 3.9 would have been; the largest remaining changes are the Java 17
requirement, the new POM model version 4.1.0 and the consumer POM, which the three Maven 4 pages describe. Plan the move with
xref:programming-languages/jvm-build-tools/maven/migrating-to-maven-4.adoc[Migrating to Maven 4]; this page does not repeat it.

Source: https://maven.apache.org/docs/4.0.0-rc-7/release-notes.html#Upgrading_from_Maven_3[Maven 4.0.0-rc-7 release notes: Upgrading from Maven 3]

== Where the Maven 2 book is outdated

*Apache Maven 2 Effective Implementation* (Packt, 2009) targets Maven 2.2. This section's pages are written against the current
documentation and name the old practice only where a reader of the book will trip over it:

* "Install Maven 2.2.1": Maven 2.x has been end of life since 2014-02-18, and the supported lines are 3.10.0 and 3.9.16 (4.0.0-rc-7
  is a release candidate).
* "Java 5 is enough": Maven 3.9 and 3.10 need Java 8 to run and Maven 4 needs Java 17.
* Continuum as the continuous-integration server and Archiva as the repository manager: both have been retired by the Apache Attic
  (Continuum in May 2016, Archiva in February 2024). The ideas live on in other CI servers and in repository managers such as Nexus, Artifactory or
  Reposilite (see xref:programming-languages/jvm-build-tools/ci-and-ide-integration.adoc[CI & IDE Integration]).
* Redback, LDAP and XML-RPC integration and the data migration of the book's chapter 12 and appendix C: obsolete with the
  products they served. A repository manager today is configured through its own documentation (see
  xref:programming-languages/jvm-build-tools/maven/repositories-mirrors-and-repository-managers.adoc[Repositories, Mirrors & Repository Managers]).
* Plugins used without versions, and the `RELEASE`/`LATEST` metaversions in a plugin `<version>`: Maven 3 warns about a missing
  plugin version and no longer supports the metaversions in the POM. The 3.10 super POM no longer manages any plugin (3.9 managed
  antrun, assembly, dependency and release), and the default lifecycle plugin versions differ between Maven releases, as the table
  above shows. Always pin plugin versions (see
  xref:programming-languages/jvm-build-tools/maven/plugins-and-their-configuration.adoc[Maven Plugins & Their Configuration]; the metaversions for dependencies are on
  xref:programming-languages/jvm-build-tools/maven/versions-snapshots-and-ranges.adoc[Maven Versions, SNAPSHOTs & Ranges]).
* Plain HTTP repository URLs: blocked by default since Maven 3.8.1 by the mirror `maven-default-http-blocker`.
* `M2_HOME`: no longer supported since Maven 3.5.0 (see xref:programming-languages/jvm-build-tools/maven/installation.adoc[Installation]).
* A POM with model version 4.0.0 only: Maven 4 adds 4.1.0, the consumer POM and the `bom` packaging (see
  xref:programming-languages/jvm-build-tools/maven/maven-4-pom-model-and-consumer-pom.adoc[Maven 4 POM Model & Consumer POM]).
* EMMA for coverage (with Cobertura and Clover as alternatives): EMMA is dead and the Cobertura plugin is unmaintained (2.7, 2015);
  JaCoCo is the coverage tool (see xref:programming-languages/jvm-build-tools/maven/site-and-reporting.adoc[Maven Site & Reporting]).
* FindBugs: abandoned; SpotBugs is its successor (see xref:programming-languages/jvm-build-tools/maven/site-and-reporting.adoc[Maven Site & Reporting]).
* Clirr for API compatibility: unmaintained (Clirr 0.6, 2006); japicmp or Revapi do the job (see
  xref:programming-languages/jvm-build-tools/maven/site-and-reporting.adoc[Maven Site & Reporting]).
* The Dashboard plugin and "Sonar": the Dashboard plugin stopped at 1.0.0-beta-1 (2008); SonarQube is run with the
  `sonar-maven-plugin` (see xref:programming-languages/jvm-build-tools/maven/site-and-reporting.adoc[Maven Site & Reporting]).
* Codehaus Mojo plugins and URLs: Codehaus closed; MojoHaus keeps the `org.codehaus.mojo` groupId (see
  xref:programming-languages/jvm-build-tools/maven/pom-fundamentals.adoc[Maven: POM Fundamentals]).
* Site Plugin 2.x configuration: the current Site Plugin is 3.22.0 on Doxia 2, with a different skin and descriptor schema (see
  xref:programming-languages/jvm-build-tools/maven/site-and-reporting.adoc[Maven Site & Reporting]).
* `archetype:create`: removed; `archetype:generate` is the only generation goal (see
  xref:programming-languages/jvm-build-tools/maven/archetypes.adoc[Maven Archetypes]).
* Mojos declared with Javadoc tags (`@goal`, `@phase`): plugins use the Java annotations `@Mojo` and `@Parameter`, and Maven 4
  breaks plugins still built on the old Maven 2 API (see xref:programming-languages/jvm-build-tools/maven/writing-plugins.adoc[Writing Maven Plugins]).
* The Reactor plugin and the "recent" reactor options: the plugin is retired and its goals are command-line options; Maven 4 adds
  `-r` and subprojects (see xref:programming-languages/jvm-build-tools/maven/multi-module-builds-and-the-reactor.adoc[Maven Multi-Module Builds & the Reactor]).
* The Release Plugin as the only way to release: still supported, but CI-friendly versions and tag-driven pipelines are common,
  and the super POM's `release-profile` is gone in 3.10 (see xref:programming-languages/jvm-build-tools/maven/releasing.adoc[Releasing] and
  xref:programming-languages/jvm-build-tools/maven/ci-friendly-versions.adoc[Maven CI-Friendly Versions]).
* Deploying to Central through OSSRH: OSSRH was shut down on 2025-06-30, and releases go through the Central Publisher Portal (see
  xref:programming-languages/jvm-build-tools/maven/publishing-to-maven-central.adoc[Publishing to Maven Central]).
* Integration tests run by Surefire with naming patterns, and Selenium RC: Failsafe is the standard integration-test runner, and
  Selenium RC was replaced by WebDriver (see
  xref:programming-languages/jvm-build-tools/maven/integration-testing-with-failsafe.adoc[Maven Integration Testing with Failsafe]).
* Subversion as the SCM: Git is the norm, and the Release Plugin works with it through Maven SCM (see
  xref:programming-languages/jvm-build-tools/maven/releasing.adoc[Releasing]).

== Maven, Ant and Gradle

Ant's releases are a single 1.10 line on Java 8 with no plugin ecosystem to keep in step; Gradle ties a build to its wrapper
version and publishes a compatibility matrix between Gradle, Java and Kotlin; Maven ties a build to the plugin versions it pins
and to the support window of the core. The equivalent of "which tool version do I run" is therefore the wrapper properties in
Gradle and Maven (see xref:programming-languages/jvm-build-tools/maven/maven-wrapper.adoc[Maven Wrapper]) and the installed
directory in Ant. The cross-tool comparison is in
xref:programming-languages/jvm-build-tools/comparing-ant-maven-and-gradle.adoc[Comparing Ant, Maven and Gradle].
