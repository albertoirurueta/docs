This page is written against Apache Maven 3.10.0 with the Apache Maven Release Plugin 3.3.1, the Deploy Plugin 3.2.0 and the Versions
Maven Plugin 2.23.0 (a MojoHaus plugin), and Git 2.54. Every example marked as run was executed on JDK 26 on 2026-10-16. Maven 3.9.16
and Maven 4.0.0-rc-7 (a release candidate) were run where the page says so. A release writes to a source repository, so every
run was made against a scratch Git repository that has a *local bare repository* as its "remote" (`+scm:git:file://<lab>/remote.git+`,
where `<lab>` is the scratch directory), a throwaway Git identity set through a private `GIT_CONFIG_GLOBAL` file (so the user's own
Git configuration was not touched), and a `file:` repository for the deploy. *Nothing was pushed to a real remote and nothing was
published anywhere.* In the output, `<lab>` stands for the scratch directory, commit and tag object ids are the ones of the run, the
nested build that the plugin forks is shown only where said, and lines were filtered with `grep` (said each time). Publishing to
Maven Central is on
xref:programming-languages/jvm-build-tools/maven/publishing-to-maven-central.adoc[Publishing to Maven Central] and is "not run here".

A release is the moment a version stops changing. The `1.0.0-SNAPSHOT` that everybody has been building becomes `1.0.0`, which is
tagged in the source repository, built once from that tag, and deployed to a repository where it must never change again; the
development line moves on to `1.1.0-SNAPSHOT`. There are two common ways to do it with Maven. The *Release Plugin* automates the
sequence by editing the version in the POMs and committing; the *tag-driven* way keeps the version out of the commits and lets a
pipeline build whatever a tag names. This page runs both. The deploy that ends a release is on
xref:programming-languages/jvm-build-tools/maven/install-deploy-and-distribution-management.adoc[Install, Deploy & Distribution Management];
the version syntax is on
xref:programming-languages/jvm-build-tools/maven/versions-snapshots-and-ranges.adoc[Versions, Snapshots & Ranges]; the scenario is on the
xref:programming-languages/jvm-build-tools/index.adoc[section landing page].

== The Release Plugin in two steps

The plugin splits a release into two goals so that a failure in the second does not undo the first.

* `release:prepare` makes the *source* ready: it checks the working copy, changes the version, builds and tests, commits, tags,
  moves to the next snapshot and commits again.
* `release:perform` makes the *binaries*: it checks out the tag that `prepare` created into a clean directory and runs a deploy there, so
  what is published was built from the tagged source and not from whatever was lying in the developer's working copy.

[mermaid]
----
sequenceDiagram
    participant Dev as Developer
    participant Prep as release:prepare
    participant Git as Git remote
    participant Perf as release:perform
    participant Repo as Deploy repository
    Dev->>Prep: mvn release:prepare
    Prep->>Prep: check clean tree and no SNAPSHOT dependencies
    Prep->>Prep: set 1.0.0 then run clean verify
    Prep->>Git: commit prepare release, tag v1.0.0, push
    Prep->>Prep: set 1.1.0-SNAPSHOT
    Prep->>Git: commit prepare for next development iteration, push
    Dev->>Perf: mvn release:perform
    Perf->>Git: check out tag v1.0.0 into target/checkout
    Perf->>Repo: mvn deploy in the checkout
----

The diagram shows what each goal does and where it talks to the outside: only `prepare` pushes to the source repository, only
`perform` uploads to the artifact repository.

Source: https://maven.apache.org/guides/mini/guide-releasing.html#Performing_the_release[Maven: Releasing, Performing the release]

== The lab

The lab is the *tidepool* parent with three modules, the `distributionManagement` of the deploy page (the two repositories are
directories below `-Drepo.url`), and these additions to the parent POM. The plugin is pinned in `pluginManagement`, because the 3.10 super POM
no longer manages plugin versions:

.pom.xml (parent, abridged)
[source,xml]
----
  <version>1.0.0-SNAPSHOT</version>
  <packaging>pom</packaging>

  <scm>
    <connection>scm:git:file://<lab>/remote.git</connection>
    <developerConnection>scm:git:file://<lab>/remote.git</developerConnection>
    <tag>HEAD</tag>
  </scm>

  <build>
    <pluginManagement>
      <plugins>
        <plugin><artifactId>maven-release-plugin</artifactId><version>3.3.1</version></plugin>
        <!-- clean, resources, compiler, surefire, jar, install, deploy as before -->
      </plugins>
    </pluginManagement>
  </build>
----

and a `.gitignore` with the files the plugin creates: `target/`, `build/`, `release.properties`, `pom.xml.releaseBackup` and `pom.xml.tag`.
The project was committed to the working repository (`git init`), a bare repository was created beside it (`git init --bare`), and the
working copy pushed `main` to it. The URL is a `file:` URL because it is the form that works for a local bare repository; real
projects use `https:` or `ssh:` URLs (not run here).

=== The scm section

The `<scm>` section tells the plugin, and humans, where the source is:

[cols="2,5",options="header"]
|===
| Element | Meaning
| `connection` | The URL for reading the source, in the Maven SCM form `scm:<provider>:<provider-specific URL>`, here `scm:git:` followed by a Git URL.
| `developerConnection` | The URL for writing: by convention the one with credentials. In the lab both elements held the same `file:` URL, and `release.properties` recorded it as `scm.url`. The plugin accepts a project that has either one (its error for a project with neither is quoted below).
| `url` | A web URL for browsing the source.
| `tag` | The tag or branch the POM was built from. The convention is `HEAD` during development; the plugin writes the real tag into the released POM (shown below).
|===

The plugin works through Apache Maven SCM, which has providers for Git, Subversion, Mercurial and others; the Git provider shells out to the
`git` command, which must therefore be installed and configured (user, signing).

A trap with multi-module projects is that the children *inherit* the `scm` URLs with their artifact id appended to the path, which suits
a repository with one directory per module. For a Git repository, where the whole multi-module project lives in one repository, the
inherited URL is wrong. `help:evaluate` on the child:

[source,text]
----
scm:git:file://<lab>/remote.git/tidepool-model
----

The attributes `child.scm.connection.inherit.append.path="false"` and `child.scm.developerConnection.inherit.append.path="false"` on the
`<scm>` element turn it off, and the child got the right URL:

[source,xml]
----
  <scm child.scm.connection.inherit.append.path="false" child.scm.developerConnection.inherit.append.path="false">
----

[source,text]
----
scm:git:file://<lab>/remote.git
----

Source: https://maven.apache.org/pom.html#SCM[Maven: POM Reference, SCM]

Source: https://maven.apache.org/scm/git.html[Apache Maven SCM: Git]

=== A dry run first

What each phase does, from the numbered lines above, the plugin's usage page and the runs on this page:

[cols="1,2,5",options="header"]
|===
| # | Phase | What happens
| 1 | `check-poms` | The POMs are checked for what a release needs, such as the `scm` section (a project without one fails here, see below).
| 2 | `scm-check-modifications` | The working copy must have no local changes. The plugin ignores its own files: the log says `+ignoring changes on: **/pom.xml.releaseBackup, **/pom.xml.next, **/pom.xml.tag, **/pom.xml.branch, **/release.properties, **/pom.xml.backup+`.
| 3 | `check-dependency-snapshots` | No dependency, plugin, report or extension may be a snapshot.
| 4 | `create-backup-poms` | Each `pom.xml` is copied to `pom.xml.releaseBackup`, which `release:rollback` uses.
| 5-7 | `map-release-versions`, `input-variables`, `map-development-versions` | The release version, the tag and the next development version are decided, from the command line, `release.properties` or the version policy, or by asking.
| 8 | `rewrite-poms-for-release` | The POMs are rewritten with the release version (in a dry run, to `pom.xml.tag`).
| 9 | `generate-release-poms` | Only for `release:prepare-with-pom`; "Not generating release POMs" otherwise.
| 10 | `run-preparation-goals` | The `preparationGoals` (default `clean verify`) run against the release POMs. If this fails, nothing has been committed.
| 11 | `scm-commit-release` | The release POMs are committed and, by default, pushed.
| 12 | `scm-tag` | The tag is created (and pushed).
| 13 | `rewrite-poms-for-development` | The POMs are rewritten with the next snapshot version.
| 14 | `remove-release-poms` | Removes the release POMs that `prepare-with-pom` generates ("Not removing release POMs" otherwise).
| 15 | `run-completion-goals` | The `completionGoals`, none by default.
| 16 | `scm-commit-development` | The development POMs are committed and pushed.
| 17 | `end-release` | `release.properties` is marked complete.
|===

`release.properties` is the memory of the run. The lines that matter (`grep`):

[source,text]

=== Choosing the versions

Without options the plugin asks three questions, with defaults from the version policy (it drops `-SNAPSHOT` and then increments the last
number: `1.0.0` and `1.0.1-SNAPSHOT` for the lab). Run without `-B` and with its standard input fed from a pipe, the plugin printed these
questions and took the defaults (the answers I piped in were not used, so no interactive answer is shown on this page):

[source,text]
----
What is the release version for "tidepool-parent"? (tidepool-parent) 1.0.0:
What is the SCM release tag or label for "tidepool-parent"? (tidepool-parent) tidepool-parent-1.0.0:
What is the new development version for "tidepool-parent"? (tidepool-parent) 1.0.1-SNAPSHOT:
----

In a pipeline, nobody can answer, so use batch mode (`-B`) and give the values on the command line: `-DreleaseVersion`, `-DdevelopmentVersion`,
`-Dtag` for the exact tag, or `-DtagNameFormat` for the pattern. The pattern uses `+@{...}+` and not `+${...}+`, so that Maven does not
interpolate it before the plugin has the release version. The default is `+@{project.artifactId}-@{project.version}+`, which gave
`tidepool-parent-1.0.0`; most teams prefer `+v@{project.version}+`. For a multi-module project each module is asked its own version unless
`-DautoVersionSubmodules=true`. The same options can live in the POM:

.pom.xml (the plugin entry in pluginManagement, in a copy of the lab)
[source,xml]
----
        <plugin>
          <artifactId>maven-release-plugin</artifactId>
          <version>3.3.1</version>
          <configuration>
            <tagNameFormat>v@{project.version}</tagNameFormat>
            <autoVersionSubmodules>true</autoVersionSubmodules>
            <scmCommentPrefix>[release] </scmCommentPrefix>
            <preparationGoals>clean verify</preparationGoals>
            <goals>deploy</goals>
            <arguments>-DskipTests</arguments>
          </configuration>
        </plugin>
----

A dry run with that configuration (`grep` for the lines that show the effect) printed:

[source,text]
----
[INFO] Executing goals 'clean verify'...
[INFO]     with additional arguments: -DskipTests
[INFO] Full run would be commit 4 files with message: '[release] prepare release v1.0.0'
[INFO] Full run would tag working copy '<lab>/t_cfg'
[INFO]   with label 'v1.0.0'
[INFO] Full run would commit 4 files with message: '[release] prepare for next development iteration'
[INFO] BUILD SUCCESS
----

The commit messages carry the `scmCommentPrefix`, the tag follows the pattern, and the extra arguments reach the forked build.

Source: https://maven.apache.org/maven-release/maven-release-plugin/usage/non-interactive-release.html[Maven Release Plugin: Performing a Non-interactive Release]

=== The parameters that matter

These come from `help:describe -Dplugin=org.apache.maven.plugins:maven-release-plugin:3.3.1 -Ddetail`.

[cols="2,2,5",options="header"]
|===
| Parameter | User property | Meaning
| `releaseVersion`, `developmentVersion` | the same | The versions to use; otherwise the version policy proposes them.
| `tag`, `tagNameFormat` | `tag`, `tagNameFormat` | The exact tag, or the pattern (default `+@{project.artifactId}-@{project.version}+`).
| `autoVersionSubmodules` | `autoVersionSubmodules` | Give every module the version of the parent without asking (default false).
| `dryRun` | `dryRun` | Do not commit or tag; write the modified POMs beside the originals.
| `resume` | `resume` | Resume the previous attempt from `release.properties` (default true).
| `preparationGoals`, `completionGoals`, `preparationProfiles` | the same | Goals (default `clean verify`) and profiles for the build against the release POMs; goals to run after the move to the next snapshot.
| `arguments` | `arguments` | Arguments for the forked Maven builds (see `-Darguments` below).
| `pushChanges`, `remoteTagging` | the same | Push the commits (default true); create the tag in the remote (default true).
| `scmCommentPrefix`, `scmReleaseCommitComment`, `scmDevelopmentCommitComment` | the same | The commit messages (`+@{prefix}+`, `+@{releaseLabel}+`).
| `signTag` | `signTag` | Sign the tag. Not run here.
| `projectVersionPolicyId`, `projectTagNamingPolicyId` | the same | A version policy (default `default`) or a tag naming policy, as plugin extensions.
| `autoResolveSnapshots` | `autoResolveSnapshots` | Resolve snapshot dependencies automatically (all, dependencies, plugins, reports, extensions).
| `generateReleasePoms` | `generateReleasePoms` | Only the goal `prepare-with-pom` sets it.
| `checkModificationExcludes` | `checkModificationExcludes` | More files to ignore in the modification check.
| `allowTimestampedSnapshots` | `allowTimestampedSnapshots` | Allow timestamped snapshot dependencies (default false).

== release:perform

`perform` reads `release.properties`, checks out the tag into `target/checkout` and runs `deploy` there in a forked Maven. In a real release
the deploy repository comes from the `distributionManagement` in the tagged POM and the credentials from `settings.xml`. The lab has to
tell the forked build where its repository is, and this is the classic stumbling block: *a `-D` option on the outer command line does not reach the
forked build*. They go in the `arguments` parameter. To see it, the same release was performed twice more, once with no option, once with
`+-Drepo.url=file://<lab>/repo_pa_b+` on the outer command line only. Both uploaded into the checkout, where the POM's own default points
(`+file://${maven.multiModuleProjectDirectory}/build/repo+` in the checkout), and where the next `mvn clean` or a new checkout deletes them:

[source,text]
----
[INFO] Uploaded to tidepool-releases: file://<lab>/t_pa_a/target/checkout/build/repo/releases/io/tidepool/tidepool-model/1.0.0/tidepool-model-1.0.0.jar
[INFO] BUILD SUCCESS
----

[source,text]
----
[INFO] Uploaded to tidepool-releases: file://<lab>/t_pa_b/target/checkout/build/repo/releases/io/tidepool/tidepool-model/1.0.0/tidepool-model-1.0.0.jar
[INFO] BUILD SUCCESS
----

[source,bash]

== The other goals

[cols="2,5",options="header"]
|===
| Goal | What it does
| `release:clean` | Cleans up the working copy after a failed or abandoned release or a dry run (it happens by itself after a successful `perform`). It rolls nothing back: commits and tags stay.
| `release:rollback` | Restores the POMs from the backups, commits that, and removes the tag. Needs the files that `release:clean` removes.
| `release:update-versions` | Only changes the versions in the POMs (prompting or from `-DdevelopmentVersion`); no commit, no tag.
| `release:branch` | Creates a branch from the current state, optionally with its own versions.
| `release:prepare-with-pom` | Like `prepare`, but also writes a `release-pom.xml` per project with everything resolved.
| `release:stage` | Like `perform`, to a staging repository; it replaces `site-deploy` by `site:stage-deploy`. Not run here.
|===

== When it goes wrong

A release has many parts, and the failures are usually at the seams. The messages below are those of real runs.

=== Local modifications

An uncommitted edit stops `prepare` in `scm-check-modifications`:

[source,text]
----
[ERROR] Failed to execute goal org.apache.maven.plugins:maven-release-plugin:3.3.1:prepare (default-cli) on project tidepool-parent: Cannot prepare the release because you have local modifications : 
[ERROR] [tidepool-model/src/main/java/io/tidepool/model/Height.java:modified]
[ERROR] [Help 1] http://cwiki.apache.org/confluence/display/MAVEN/MojoFailureException
----

The release descriptor is left behind, and remembers where it stopped; after the file was reverted, `git status` printed nothing (empty
listing) and `release.properties` held:

[source,text]
----
completedPhase=check-poms
----

=== The stale release.properties and resume

Because of that file, running the goal again *resumes*: the next run (a dry run) printed that it resumed and skipped the phase that had
completed:

[source,text]
----
[INFO] Resuming release from phase 'scm-check-modifications'
[INFO] 2/17 prepare:scm-check-modifications dry-run
[INFO] 3/17 prepare:check-dependency-snapshots dry-run
----

`-Dresume=false` (or `release:clean` first) starts again from phase 1:

[source,text]
----
[INFO] 1/17 prepare:check-poms dry-run
[INFO] 2/17 prepare:scm-check-modifications dry-run
----

The classic problem is a `release.properties` from an earlier, abandoned attempt: it remembers the old release version, tag name and
phase, and the new attempt silently reuses them. The rule is to run `release:clean` (or `rollback`) before starting over, and to look at
`release.properties` when a release does something unexpected.

=== Snapshot dependencies

A release must be reproducible, so every dependency must be a release too. A dependency on `io.tidepool:snap-lib:2.0-SNAPSHOT` (installed
into the scratch local repository with `install:install-file`) in `tidepool-cli` failed `check-dependency-snapshots`:

[source,text]
----
[ERROR] Failed to execute goal org.apache.maven.plugins:maven-release-plugin:3.3.1:prepare (default-cli) on project tidepool-parent: Can't release project due to non released dependencies :
[ERROR]     io.tidepool:snap-lib:jar:2.0-SNAPSHOT:compile
[ERROR] in project 'tidepool-cli' (io.tidepool:tidepool-cli:jar:1.0.0-SNAPSHOT)
----

With `-DautoResolveSnapshots=dependencies` the plugin offers to replace them with the latest release instead of failing. The proper fix is
to release the dependency first.

=== No scm section

A project without `<scm>` fails in the first phase, `check-poms`, before anything is written (no `release.properties` was created):

[source,text]
----
[ERROR] Failed to execute goal org.apache.maven.plugins:maven-release-plugin:3.3.1:prepare (default-cli) on project tidepool-parent: Missing required setting: scm connection or developerConnection must be specified. -> [Help 1]
----

== The alternative: tag-driven releases

The Release Plugin edits the POM to say `1.0.0`, commits, tags and edits the POM again. Many teams stopped doing that. The alternative is that the
*tag is the release*: a developer (or a pipeline) creates a tag; a CI job builds the tag and publishes the version the tag names, and nothing else is
committed. Two ways to put the version into the build:

* *CI-friendly versions* (`+${revision}+`, `+${sha1}+`, `+${changelist}+`): the POM keeps a default and the job passes `-Drevision=1.2.0`. This is
  all on xref:programming-languages/jvm-build-tools/maven/ci-friendly-versions.adoc[CI-Friendly Versions], including the flatten plugin that Maven 3 needs
  to publish such a POM, and the shell script that lets a tag decide.
* *`versions:set`* of the Versions Maven Plugin: a commit that sets the version in every POM, a tag on it, a deploy, and a commit that moves to the
  next snapshot. It is the manual version of `release:prepare` with the build in the middle. Run on a clone of the lab (`grep` for the plugin's lines):

[source,text]
----
$ mvn versions:set -DnewVersion=1.2.0 -DgenerateBackupPoms=false
[INFO] Processing change of io.tidepool:tidepool-parent:1.0.0-SNAPSHOT -> 1.2.0
[INFO] Processing io.tidepool:tidepool-parent
[INFO]     Updating project io.tidepool:tidepool-parent
[INFO] Processing io.tidepool:tidepool-cli
[INFO]     Updating parent io.tidepool:tidepool-parent
[INFO] Processing io.tidepool:tidepool-engine
[INFO]     Updating parent io.tidepool:tidepool-parent
[INFO] Processing io.tidepool:tidepool-model
[INFO]     Updating parent io.tidepool:tidepool-parent
[INFO] BUILD SUCCESS
$ git diff --stat
 pom.xml                 | 4 ++--
 tidepool-cli/pom.xml    | 2 +-
 tidepool-engine/pom.xml | 2 +-
 tidepool-model/pom.xml  | 2 +-
 4 files changed, 5 insertions(+), 5 deletions(-)
$ mvn deploy
[INFO] Uploaded to tidepool-releases: file://<lab>/repo_tag/releases/io/tidepool/tidepool-model/1.2.0/tidepool-model-1.2.0.jar
[INFO] Uploaded to tidepool-releases: file://<lab>/repo_tag/releases/io/tidepool/tidepool-engine/1.2.0/tidepool-engine-1.2.0.jar
[INFO] Uploaded to tidepool-releases: file://<lab>/repo_tag/releases/io/tidepool/tidepool-cli/1.2.0/tidepool-cli-1.2.0.jar
[INFO] BUILD SUCCESS
$ mvn versions:set -DnewVersion=1.3.0-SNAPSHOT -DgenerateBackupPoms=false
[INFO] BUILD SUCCESS
$ git log --oneline --decorate
42b4184 (HEAD -> main, origin/main, origin/HEAD) Start 1.3.0-SNAPSHOT
67bd957 (tag: v1.2.0) Release 1.2.0
5631a64 tidepool 1.0.0-SNAPSHOT
$ git ls-remote --tags origin
<id> refs/tags/v1.2.0
----

The release commit and the tag exist, the deploy has built from the tagged commit, and the repository received `1.2.0`. The commit
history is cleaner than the Release Plugin's (no `[maven-release-plugin]` commits, no reformatted POM headers beyond what `versions:set` changes), at the
cost of doing the sequence yourself; a script or a CI pipeline does that, and it also lets the build run before the tag is created. The trade-offs:

[cols="2,3,3",options="header"]
|===
| | Release Plugin | Tag-driven
| Version in the POM | Edited and committed twice | Default in the POM, or set in one commit
| Source of the release | `perform` checks out the tag and rebuilds | The CI job builds the tag, once
| Reproducibility | `outputTimestamp` is rewritten into the release commit | `outputTimestamp` is whatever is set; make it a function of the tag
| Rollback | `release:rollback` (leaves commits, removes the tag) | Delete the tag and revert the commit by hand; there is no plugin state to repair
| Learning cost | Many phases, files and failure modes (above) | A script
|===

A published release should be built once and promoted, not rebuilt, so that the bytes tested are the bytes released (see
xref:programming-languages/jvm-build-tools/maven/publishing-to-maven-central.adoc[Publishing to Maven Central] and
xref:programming-languages/jvm-build-tools/maven/security-and-reproducible-builds.adoc[Security & Reproducible Builds]).

* On Maven 4 the plugin worked, with a warning about the missing root directory in both goals (the clone has no `.mvn` directory because Git does not
  track an empty directory, and the checkout under `target/checkout` is a project of its own). Add a `.mvn` directory with a file in it, or the
  attribute `root="true"` on the root project, to Maven 4 builds (see
  xref:programming-languages/jvm-build-tools/maven/migrating-to-maven-4.adoc[Migrating to Maven 4]).
* On Maven 4 the deploy also published the *build POM* (`-build.pom`) beside the consumer POM of every module (the listing above); see the deploy
  page.
* The `release-profile` of the super POM exists on 3.9.16 and not on 3.10.0 or 4.0.0-rc-7 (above).
* The Release Plugin rewrites the `project.build.outputTimestamp` property at release time when the POM defines it, as the lab's parent POM does.
* The release plugin version is not managed by Maven 3.10 any more; pin it.

== The same job in Ant and Gradle

Ant has no release concept: a release is a target that sets a property, tags with `exec` or the Git tasks and publishes with the Resolver Ant
Tasks or Ivy (see xref:programming-languages/jvm-build-tools/ant/ivy-publishing-and-multi-project.adoc[Ivy: Publishing & Multi-Project Builds]).
Gradle reads the version from the build script or `gradle.properties`, and releasing is either a convention (a tag, the version passed with `-P`)
or a third-party plugin; the publishing side is on
xref:programming-languages/jvm-build-tools/gradle/publishing.adoc[Publishing]. The comparison is on
xref:programming-languages/jvm-build-tools/repositories-and-publishing-across-tools.adoc[Repositories & Publishing Across Tools].

== Where the books and old pages are outdated

* Release guides written for Maven 2 and Subversion (the official "Releasing" mini guide still shows `scm:svn:` URLs, `tagBase` and plugin 2.5.2 in its
  examples) apply to Git with different properties: `tagNameFormat` and a `developerConnection` with `scm:git:`. A `release.properties` with `+checkpoint.*+`
  entries is from the old plugin; the 3.x file has `completedPhase`.
* The `release-profile` and `useReleaseProfile` are gone or deprecated (3.10, above).
* `release:prepare` is no longer the only way to release: tag-driven pipelines with CI-friendly versions are common.
* Plugin versions: the Release Plugin 2.x is obsolete; use 3.x, and pin it.

== What was not run here

* A real remote (`https:` or `ssh:`) with credentials, signing of commits and tags, and CI jobs for Git hosts.
* Publishing to Maven Central, `release:stage`, `release:prepare-with-pom`, `-DlocalCheckout=true`, `-DconnectionUrl` without a `release.properties`,
  `-DpushChanges=false`, and Subversion.
* The interactive questions with answers (the questions were printed, the answers taken were the defaults).
