== Products and What FieldNotes Sells

App Store Connect offers four product types:

[cols="1,2,2",options="header"]
|===
| Type | Behaviour | Example

| Consumable
| Used up, can be bought again; not restored
| Extra AI summaries (FieldNotes does not sell these)

| Non-consumable
| Bought once, owned forever, restored on every device
| A one-off "lifetime Pro" unlock

| Auto-renewable subscription
| Renews every period until cancelled; belongs to a *subscription group*
| **FieldNotes Pro**, monthly or yearly

| Non-renewing subscription
| Time-limited access that does not renew; the app tracks expiry
| A season pass
|===

FieldNotes Pro is one subscription group, *FieldNotes Pro*, with two products. A person can hold only one

== How a Purchase Flows

In StoreKit 2 the App Store signs every transaction as a **JWS** (JSON Web Signature, the same format as a JWT,
see xref:backend/oauth/jwt-and-jose.adoc[JWT and JOSE]). StoreKit verifies the signature on the device before
the app sees it and hands the app a `VerificationResult<Transaction>`: `.verified` or `.unverified`. There is no
receipt to parse. A purchase can complete in the app, but it can also complete elsewhere: after Ask to Buy
approval, on another device, as a renewal at 3 a.m., or as a refund. All of those arrive through
`Transaction.updates`, which is why the listener has to run from launch.

== `StoreManager`

`StoreManager` lives in `FieldNotesServices` so every target, including the widget, can ask whether Pro is
unlocked. The `FieldNotesApp` scene owns one instance for the app's lifetime.

[source,swift]
----
// Packages/FieldNotesKit/Sources/FieldNotesServices/Store/StoreManager.swift
import Foundation
import Observation
import StoreKit

@Observable @MainActor
public final class StoreManager {
    public static let productIDs: [Product.ID] = [
        "com.example.fieldnotes.pro.monthly",
        "com.example.fieldnotes.pro.yearly",
    ]
    /// The "FieldNotes Pro" group ID from App Store Connect (and from Products.storekit).
    public static let proGroupID = "21500001"

    public private(set) var products: [Product] = []
    public private(set) var isPro = false
    public private(set) var proRenewalState: Product.SubscriptionInfo.RenewalState?

    @ObservationIgnored private var updatesTask: Task<Void, Never>?

    public init() {
        // Start listening before anything else, so no transaction is missed.
        updatesTask = Task { [weak self] in
            for await result in Transaction.updates {
                await self?.handle(result)
            }
        }
    }

    public func loadProducts() async {
        do {
            products = try await Product.products(for: Self.productIDs)
                .sorted { $0.price < $1.price }
        } catch {
            products = []          // offline or misconfigured: the store UI shows a retry button
        }
    }
}
----

See https://developer.apple.com/documentation/storekit/product/products(for:)[Apple Developer Documentation -- products(for:)]
and https://developer.apple.com/documentation/storekit/implementing-a-store-in-your-app-using-the-storekit-api[Apple Developer Documentation -- Implementing a store in your app using the StoreKit API].

`Product.products(for:)` returns only the IDs the App Store knows for the current storefront, localized, with
`displayName`, `description`, `displayPrice` (already formatted in the person's currency) and, for
subscriptions, a `subscription` property with the period, group and offers. Never hard-code prices.

The `Task` created in `init` inherits the main actor, so `handle(_:)` runs on the main actor and can update
`isPro` directly. The `[weak self]` capture keeps the loop from retaining the manager; in FieldNotes the manager
lives as long as the app, so the task never ends. How tasks inherit isolation is covered on
xref:programming-languages/swift/async-await-and-tasks.adoc[Async/Await and Tasks] and
xref:apps/apple/concurrency-in-apps.adoc[Concurrency in Apps].

The app creates it at launch and injects it next to the note store:

[source,swift]
----
// FieldNotes/FieldNotesApp.swift (excerpt)
import FieldNotesServices
import SwiftUI

@main
struct FieldNotesApp: App {
    @State private var store = AppServices.shared.store   // the single owner, see Background Execution
    @State private var storeManager = StoreManager()   // Transaction.updates starts here

    var body: some Scene {
        WindowGroup {
            ContentView()
                .environment(store)
                .environment(storeManager)
                .task {
                    await storeManager.loadProducts()
                    await storeManager.refreshEntitlements()
                }
        }
    }
}
----

See https://developer.apple.com/documentation/storekit/transaction/updates[Apple Developer Documentation -- updates].

== Purchasing

A purchase needs a UI context to anchor the payment sheet. `Product.purchase(options:)` finds one on its own
on iOS, macOS and watchOS but does not exist on visionOS, and the `purchase(confirmIn:options:)` variants take a
UIKit scene or an AppKit window. The portable choice in SwiftUI is `PurchaseAction`, read from the environment
as `@Environment(\.purchase)`. `StoreManager` accepts it as a parameter, so the manager stays free of UI code:

[source,swift]
----
// StoreManager.swift (continued)
extension StoreManager {
    public enum PurchaseOutcome { case unlocked, pending, cancelled }

    public func purchase(_ product: Product, using purchaseAction: PurchaseAction,
                         accountID: UUID? = nil) async throws -> PurchaseOutcome {
        var options: Set<Product.PurchaseOption> = []
        if let accountID { options.insert(.appAccountToken(accountID)) }   // ties it to the FieldNotes account

        switch try await purchaseAction(product, options: options) {
        case .success(let verification):
            await handle(verification)
            return isPro ? .unlocked : .pending
        case .pending:
            return .pending          // Ask to Buy or Strong Customer Authentication; arrives via updates
        case .userCancelled:
            return .cancelled
        @unknown default:
            return .cancelled
        }
    }
}

// FieldNotes/Views/ProUpgradeButton.swift
struct ProUpgradeButton: View {
    @Environment(StoreManager.self) private var storeManager
    @Environment(\.purchase) private var purchase
    let product: Product

    var body: some View {
        Button("Subscribe for \(product.displayPrice)") {
            Task { _ = try? await storeManager.purchase(product, using: purchase) }
        }
    }
}
----

See https://developer.apple.com/documentation/storekit/purchaseaction[Apple Developer Documentation -- PurchaseAction],
https://developer.apple.com/documentation/storekit/product/purchase(options:)[Apple Developer Documentation -- purchase(options:)]
and https://developer.apple.com/documentation/storekit/product/purchaseresult[Apple Developer Documentation -- Product.PurchaseResult].

`.appAccountToken(_:)` stores a UUID of the app's choosing in the signed transaction. FieldNotes passes the
account ID from `AccountManager`, so its server can match App Store Server Notifications to the right account.
`.pending` is not a failure: the transaction may still succeed hours later and will arrive through
`Transaction.updates`.

== Verifying and Finishing Transactions

`handle(_:)` is the single place where a transaction changes what the person can do. It is called from the
purchase result and from the updates listener.

[source,swift]
----
// StoreManager.swift (continued)
extension StoreManager {
    func handle(_ result: VerificationResult<Transaction>) async {
        switch result {
        case .verified(let transaction):
            await refreshEntitlements()
            await transaction.finish()            // tell the App Store the content was delivered
        case .unverified(let transaction, let error):
            // Signed by someone else, or for another device: never unlock anything.
            print("Unverified transaction \(transaction.id): \(error)")
        }
    }
}
----

See https://developer.apple.com/documentation/storekit/transaction[Apple Developer Documentation -- Transaction],
https://developer.apple.com/documentation/storekit/verificationresult[Apple Developer Documentation -- VerificationResult]
and https://developer.apple.com/documentation/storekit/transaction/finish()[Apple Developer Documentation -- finish()].

Only finish a transaction after the app has delivered what was bought. An unfinished transaction is delivered
again through `Transaction.updates` at the next launch, which is the retry mechanism. For consumables, finishing
is essential: until it happens the same product cannot be bought again.

On-device verification protects against a tampered app or a replayed transaction on another device, but a
jailbroken device can still lie to its own app. When Pro unlocks a server feature, such as sharing through the
FieldNotes server, the server must also check the purchase with the App Store Server API or App Store Server
Notifications V2; the `VerificationResult` also exposes the raw `jwsRepresentation` for that purpose.

== Entitlements and Subscription Status

`Transaction.currentEntitlements` yields the latest transaction for every product the person is currently
entitled to: active subscriptions, owned non-consumables, including purchases made on other devices and through
Family Sharing. It is the source of truth for `isPro`:

[source,swift]
----
// StoreManager.swift (continued)
extension StoreManager {
    public func refreshEntitlements() async {
        var entitled = false
        for await result in Transaction.currentEntitlements {
            guard case .verified(let transaction) = result,
                  Self.productIDs.contains(transaction.productID),
                  transaction.revocationDate == nil,              // not refunded
                  !transaction.isUpgraded else { continue }      // superseded by another product
            if let expiry = transaction.expirationDate, expiry < .now { continue }
            entitled = true
        }
        isPro = entitled
    }
}
----

See https://developer.apple.com/documentation/storekit/transaction/currententitlements[Apple Developer Documentation -- currentEntitlements],
https://developer.apple.com/documentation/storekit/transaction/revocationdate[Apple Developer Documentation -- revocationDate]
and https://developer.apple.com/documentation/storekit/transaction/isupgraded[Apple Developer Documentation -- isUpgraded].

`isPro` is published through Observation, so every view that reads it re-renders when a renewal or refund
arrives. To check a single product, `Transaction.currentEntitlements(for:)` (18.4 and later, so always
available at FieldNotes's minimum) filters by product ID.

Entitlement answers *whether* Pro is active. **Subscription status** answers *how*: subscribed, in a billing
grace period, in billing retry, expired or revoked. FieldNotes uses it to show a "Payment problem, update your
payment method" banner while a subscription is in grace period, instead of silently locking the person out:

[source,swift]
----
// StoreManager.swift (continued)
extension StoreManager {
    public func refreshStatus() async {
        let statuses = (try? await Product.SubscriptionInfo.status(for: Self.proGroupID)) ?? []
        proRenewalState = statuses
            .filter { if case .verified = $0.transaction { true } else { false } }
            .map(\.state)
            .first
    }
}

// In a view, the modifier form keeps the status current without a manual refresh:
// .subscriptionStatusTask(for: StoreManager.proGroupID) { taskState in
//     if case .success(let statuses) = taskState,
//        statuses.contains(where: { $0.state == .inGracePeriod }) { showPaymentBanner = true }
// }
----

See https://developer.apple.com/documentation/storekit/product/subscriptioninfo/status-swift.struct[Apple Developer Documentation -- Product.SubscriptionInfo.Status],
https://developer.apple.com/documentation/storekit/product/subscriptioninfo/renewalstate[Apple Developer Documentation -- Product.SubscriptionInfo.RenewalState]
and https://developer.apple.com/documentation/swiftui/view/subscriptionstatustask(for:priority:action:)[Apple Developer Documentation -- subscriptionStatusTask(for:priority:action:)].

A person with Family Sharing may have more than one status for the same group (their own and a family
member's); FieldNotes takes the first verified one, which is enough for a banner.

== Restoring Purchases with `AppStore.sync()`

Because `currentEntitlements` already includes purchases made on other devices, most people never need to
restore anything. App Review still requires a visible *Restore Purchases* control for non-consumables and
subscriptions, for the rare case where the device's transaction data is out of date. `AppStore.sync()` forces a
fresh sync with the App Store and asks the person to authenticate, so call it only from that explicit button:

[source,swift]
----
// FieldNotes/Views/SettingsView+Store.swift (excerpt)
Button("Restore Purchases") {
    Task {
        try? await AppStore.sync()
        await storeManager.refreshEntitlements()
    }
}
----

See https://developer.apple.com/documentation/storekit/appstore/sync()[Apple Developer Documentation -- sync()].

== Merchandising with StoreKit Views

StoreKit's SwiftUI views load products, format prices, show the right legal text and buttons for each platform,
and run the purchase. They are the fastest way to a store that passes review.

=== `SubscriptionStoreView` for FieldNotes Pro

`SubscriptionStoreView(groupID:)` shows every product in a subscription group, with custom marketing content on
top. The `.storeButton(_:for:)` modifier adds the restore and redeem-code buttons, and
`.onInAppPurchaseCompletion` routes the result to `StoreManager`:

[source,swift]
----
// FieldNotes/Views/ProStoreView.swift
import FieldNotesServices
import StoreKit
import SwiftUI

struct ProStoreView: View {
    @Environment(StoreManager.self) private var storeManager
    @Environment(\.dismiss) private var dismiss

    var body: some View {
        SubscriptionStoreView(groupID: StoreManager.proGroupID) {
            VStack(spacing: 12) {
                Image(systemName: "note.text.badge.plus")
                    .font(.system(size: 56))
                    .foregroundStyle(.tint)
                Text("FieldNotes Pro").font(.largeTitle.bold())
                Text("Unlimited notebooks, the AR notes map and encrypted sharing.")
                    .multilineTextAlignment(.center)
            }
            .padding()
        }
        #if os(watchOS)
        .storeButton(.visible, for: .restorePurchases)
        #else
        .subscriptionStoreControlStyle(.picker)
        .storeButton(.visible, for: .restorePurchases, .redeemCode)
        #endif
        .onInAppPurchaseCompletion { _, result in
            if case .success(.success(let verification)) = result {
                await storeManager.handle(verification)
                if storeManager.isPro { dismiss() }
            }
        }
    }
}

#Preview {
    ProStoreView()
        .environment(StoreManager())
}
----

See https://developer.apple.com/documentation/storekit/subscriptionstoreview[Apple Developer Documentation -- SubscriptionStoreView],
link:++https://developer.apple.com/documentation/swiftui/view/storebutton(_:for:)++[+Apple Developer Documentation -- storeButton(_:for:)+],
link:++https://developer.apple.com/documentation/swiftui/view/subscriptionstorecontrolstyle(_:)++[+Apple Developer Documentation -- subscriptionStoreControlStyle(_:)+]
and https://developer.apple.com/documentation/swiftui/view/oninapppurchasecompletion(perform:)[Apple Developer Documentation -- onInAppPurchaseCompletion(perform:)].

`.picker` and the redeem-code button are not available on watchOS, hence the `#if`. The preview works without App Store Connect when the scheme's StoreKit configuration is `Products.storekit`

== Monthly Subscriptions with a 12-Month Commitment

The 2026 billing option lets people pay for a **yearly** subscription **monthly**, in exchange for committing to
twelve payments. It is not a new product: in App Store Connect you enable the monthly billing plan on an existing
1-year subscription, so `com.example.fieldnotes.pro.yearly` keeps its product ID and now offers two *pricing
terms*: billed up front, or billed monthly with a 12-month commitment. Cancelling stops the commitment from
renewing, but the remaining payments of the current commitment are still billed.

The APIs arrived in 26.4 and need an app built with the Xcode 26.5 SDK or later. The billing plan is offered
worldwide except in the United States and Singapore; in those storefronts `pricingTerms` contains only the
up-front entry. Because FieldNotes's minimum is 26, every use is guarded:

[source,swift]
----
// StoreManager.swift (continued)
extension StoreManager {
    /// The yearly product's monthly commitment plan, if this storefront offers it.
    @available(iOS 26.4, macOS 26.4, watchOS 26.4, visionOS 26.4, *)
    public func commitmentTerms(for product: Product) -> Product.SubscriptionInfo.PricingTerms? {
        product.subscription?.pricingTerms.first { $0.billingPlanType == .monthly }
    }

    @available(iOS 26.4, macOS 26.4, watchOS 26.4, visionOS 26.4, *)
    public func purchaseCommitment(_ product: Product, using purchaseAction: PurchaseAction) async throws {
        let result = try await purchaseAction(product, options: [.billingPlanType(.monthly)])
        if case .success(let verification) = result { await handle(verification) }
    }
}

// FieldNotes/Views/CommitmentOfferRow.swift
struct CommitmentOfferRow: View {
    @Environment(StoreManager.self) private var storeManager
    @Environment(\.purchase) private var purchase
    let yearly: Product

    var body: some View {
        if #available(iOS 26.4, macOS 26.4, watchOS 26.4, visionOS 26.4, *),
           let terms = storeManager.commitmentTerms(for: yearly) {
            VStack(alignment: .leading) {
                // Both amounts must be visible before the person subscribes.
                Text("\(terms.billingDisplayPrice) per month for 12 months")
                Text("Total commitment: \(terms.commitmentInfo.displayPrice)")
                    .font(.footnote).foregroundStyle(.secondary)
                Button("Pay Monthly") {
                    Task { try? await storeManager.purchaseCommitment(yearly, using: purchase) }
                }
            }
        }
    }
}
----

See https://developer.apple.com/documentation/storekit/supporting-monthly-subscriptions-with-a-12-month-commitment[Apple Developer Documentation -- Supporting monthly subscriptions with a 12-month commitment]
https://developer.apple.com/documentation/storekit/product/subscriptioninfo/pricingterms-swift.struct[Apple Developer Documentation -- Product.SubscriptionInfo.PricingTerms]
and https://developer.apple.com/videos/play/wwdc2026/210/[WWDC26 -- What's new in Apple In-App Purchase].

With `SubscriptionStoreView`, a single modifier makes the store feature the commitment plan instead:

[source,swift]
----
SubscriptionStoreView(groupID: StoreManager.proGroupID)
    .preferredSubscriptionPricingTerms { _, subscriptionInfo in
        subscriptionInfo.pricingTerms.first { $0.billingPlanType == .monthly }
    }
----

See link:++https://developer.apple.com/documentation/swiftui/view/preferredsubscriptionpricingterms(_:)++[+Apple Developer Documentation -- preferredSubscriptionPricingTerms(_:)+].

In the app, each monthly payment is an ordinary transaction that grants one month; the entitlement logic in
`refreshEntitlements()` needs no change, because it already checks the transaction's own `expirationDate`. The
transaction's `commitmentInfo` (`billingPeriodNumber`, `totalBillingPeriods`, `price`, `expirationDate`) is only
for showing progress such as "payment 4 of 12". Never use `commitmentInfo.expirationDate` to decide access: a
billing issue that recovers late moves it. Billing grace period does not apply to commitment plans, so revoke
access while a monthly payment is in billing retry.

[source,swift]
----
@available(iOS 26.4, macOS 26.4, watchOS 26.4, visionOS 26.4, *)
func commitmentProgress(of transaction: Transaction) -> String? {
    guard transaction.billingPlanType == .monthly, let info = transaction.commitmentInfo else { return nil }
    return "Payment \(info.billingPeriodNumber) of \(info.totalBillingPeriods)"
}
----

See https://developer.apple.com/documentation/storekit/transaction/commitmentinfo-swift.struct[Apple Developer Documentation -- Transaction.CommitmentInfo]
and https://developer.apple.com/documentation/storekit/managing-lifecycle-of-monthly-subscriptions-with-a-12-month-commitment-[Apple Developer Documentation -- Managing the life cycle of monthly subscriptions with a 12-month commitment].

The first time someone subscribes to a commitment plan, the system shows a one-time disclosure sheet with the
number of payments and cancellation terms; the app does nothing for it. On the server, the plan adds
`billingPlanType` and `commitmentInfo` fields to the decoded JWS transaction and renewal info, and the life-cycle
article lists which App Store Server Notifications (`DID_RENEW`, `DID_CHANGE_RENEWAL_STATUS`,
`DID_FAIL_TO_RENEW`, `EXPIRED`) to handle.

== Offer Codes (27)

Offer codes give a free or discounted period, for example to a university field course. In 27 the SwiftUI
redemption sheet takes a set of `RedeemOption` values and returns the resulting transaction as a
`VerificationResult`, so the app can unlock immediately instead of waiting for `Transaction.updates`:

[source,swift]
----
struct RedeemCodeButton: View {
    @Environment(StoreManager.self) private var storeManager
    @State private var isPresented = false

    var body: some View {
        Button("Redeem Code") { isPresented = true }
        #if !os(watchOS)
            .modifier(RedeemSheet(isPresented: $isPresented, storeManager: storeManager))
        #endif
    }
}

#if !os(watchOS)
private struct RedeemSheet: ViewModifier {
    @Binding var isPresented: Bool
    let storeManager: StoreManager

    func body(content: Content) -> some View {
        if #available(iOS 27, macOS 27, visionOS 27, *) {
            content.offerCodeRedemption(options: [], isPresented: $isPresented) { result in
                if case .success(let verification) = result {
                    Task { await storeManager.handle(verification) }
                }
            }
        } else {
            content.offerCodeRedemption(isPresented: $isPresented)   // 26: the result arrives via updates
        }
    }
}
#endif
----

== StoreKit Configuration Files and Testing in Xcode

A **StoreKit configuration file** describes products, subscription groups, prices and offers locally. When a
scheme's *Run > Options > StoreKit Configuration* points at it, StoreKit talks to Xcode's local test environment
instead of the App Store: no network, no sandbox account, instant renewals, and a **Transaction Manager**
(*Debug > StoreKit > Manage Transactions*) to approve Ask to Buy, refund, expire or fail renewals. Create one
with *File > New > File from Template > StoreKit Configuration File*, name it `Products.storekit`, and either
add the products by hand or sync them from App Store Connect.

The file is JSON that Xcode's editor maintains; edit it in the editor, not by hand. An abbreviated excerpt shows
its shape:

[source,json]
----
{
  "subscriptionGroups" : [
    {
      "id" : "21500001",
      "name" : "FieldNotes Pro",
      "subscriptions" : [
        {
          "productID" : "com.example.fieldnotes.pro.monthly",
          "displayPrice" : "3.99",
          "recurringSubscriptionPeriod" : "P1M",
          "groupNumber" : 2,
          "type" : "RecurringSubscription",
          "localizations" : [ { "locale" : "en_US", "displayName" : "FieldNotes Pro Monthly",
                                "description" : "All Pro features, billed monthly" } ]
        },
        {
          "productID" : "com.example.fieldnotes.pro.yearly",
          "displayPrice" : "34.99",
          "recurringSubscriptionPeriod" : "P1Y",
          "groupNumber" : 1,
          "type" : "RecurringSubscription",
          "localizations" : [ { "locale" : "en_US", "displayName" : "FieldNotes Pro Yearly",
                                "description" : "All Pro features, billed yearly" } ]
        }
      ]
    }
  ]
}
----

See https://developer.apple.com/documentation/storekit/testing-in-app-purchases-in-xcode[Apple Developer Documentation -- Testing Apple In-App Purchases in Xcode].

Since Xcode 26.5, the editor's *Billing Plan* picker adds the monthly-with-12-month-commitment plan to the yearly
product, and the Transaction inspector shows the resulting `commitmentInfo`. *Editor > Subscription Renewal
Rate* speeds renewals up (for example, a monthly renewal every 30 seconds) to test expiry and win-back offers.

Unit tests drive the same file through `SKTestSession` from the StoreKitTest framework. Add
`Products.storekit` to the test target's resources, then:

[source,swift]
----
// FieldNotesKitTests/StoreManagerTests.swift
import FieldNotesServices
import StoreKit
import StoreKitTest
import Testing

@MainActor
struct StoreManagerTests {
    @Test func buyingYearlyUnlocksPro() async throws {
        let session = try SKTestSession(configurationFileNamed: "Products")
        session.disableDialogs = true
        session.clearTransactions()

        let manager = StoreManager()
        _ = try await session.buyProduct(identifier: "com.example.fieldnotes.pro.yearly", options: [])
        await manager.refreshEntitlements()
        #expect(manager.isPro)

        try session.expireSubscription(productIdentifier: "com.example.fieldnotes.pro.yearly")
        await manager.refreshEntitlements()
        #expect(!manager.isPro)
    }
}
----

See https://developer.apple.com/documentation/storekittest/sktestsession[Apple Developer Documentation -- SKTestSession].

Swift Testing itself is covered on xref:apps/apple/testing-with-swift-testing.adoc[Unit Testing with Swift Testing]
and xref:programming-languages/swift/testing.adoc[Swift Testing].

The three test environments build on each other:

[cols="1,2,2",options="header"]
|===
| Environment | Needs | Use it for

| Xcode (`Products.storekit`)
| Nothing: no account, no network
| Daily development, previews, unit and UI tests, edge cases via the Transaction Manager

| Sandbox
| App Store Connect products, a Sandbox Apple Account, a paid developer account
| Real signed transactions, the server's App Store Server API and Notifications V2 handling

| TestFlight
| A TestFlight build
| Beta testers buying with accelerated renewals, never charged
|===

See https://developer.apple.com/documentation/storekit/testing-at-all-stages-of-development-with-xcode-and-the-sandbox[Apple Developer Documentation -- Testing at all stages of development with Xcode and the sandbox].

== App Review and Payment Rules

The App Review Guidelines' section 3.1 governs payments. The rules FieldNotes has to follow:

* **3.1.1**: digital content and features used in the app, such as FieldNotes Pro, must be sold through
  In-App Purchase. Physical goods and person-to-person services use other payment methods.
* **3.1.2**: auto-renewable subscriptions must provide ongoing value, work on all the app's supported devices,
  and clearly state what the person gets, the price, the period and, for commitment plans, the total commitment
  before purchase. Terms of use and a privacy policy link must be reachable from the paywall.
* **Restore**: a way to restore purchases must exist (`AppStore.sync()` or the `.restorePurchases` store
  button).
* **Regional exceptions**: some storefronts allow links to, or alternative, external payment. StoreKit's
  External Purchase APIs implement those programmes and require an entitlement per region; FieldNotes does not use
  them.

See https://developer.apple.com/app-store/review/guidelines/[Apple Developer -- App Review Guidelines]
and https://developer.apple.com/documentation/storekit/external-purchase[Apple Developer Documentation -- External Purchase].

In-App Purchases are submitted for review with the app. In 2026 App Store Connect groups products, in-app events
and custom product pages into one review submission, and the App Store Connect API's `reviewSubmissions`
resources cover In-App Purchases too. Submission, metadata and TestFlight are covered on
xref:apps/apple/app-store-connect-testflight-and-review.adoc[App Store Connect, TestFlight and App Review].
