xref:apps/apple/testing-with-swift-testing.adoc[Unit Testing with Swift Testing] tested *FieldNotes* from the
inside: the store, the persistence layer and the intents, called directly. This page tests it from the outside. **UI
tests** launch the real app and use it the way a person does; **performance tests** measure how long it takes; a
**test plan** runs everything in several languages and with runtime checks enabled; **code coverage** shows what none
of the tests reached. Everything targets the **27** releases (**iOS 27, iPadOS 27, macOS 27, watchOS 27 and
visionOS 27**), built with **Xcode 27** and **Swift 6.4**, with the app's **deployment minimum of 26**. None of the
APIs on this page is new in 27; the Xcode features used (video capture in test plans) arrived in Xcode 26.

UI tests and performance tests are written with **XCTest**, because Swift Testing doesn't support UI automation or
performance metrics. XCTest itself (test classes, `setUp`, the `XCTAssert` family) is covered in the Swift reference
under xref:programming-languages/swift/testing.adoc[Testing] and, for Objective-C, under
xref:programming-languages/objective-c/testing.adoc[Testing]. The general case for having few end-to-end tests and
many unit tests is made for the web in xref:web/e2e-testing-real-browsers.adoc[E2E Testing in Real Browsers]; the
reasoning is the same for apps.

== Where UI Tests Fit

A UI test is the most realistic test and the most expensive one. It builds and launches the whole app, waits for
real animations, and fails for reasons that have nothing to do with the code under test, such as a keyboard that
covers a button. *FieldNotes* therefore tests behaviour at the lowest level that can see it, and keeps UI tests for
what only the running app can show: that the screens are wired together, that the app is accessible, and how long it
takes to launch.

The width of each layer is the number of tests: dozens of unit tests run in seconds on every build, a handful of

When a UI test fails, the first question is whether a unit test could have caught the same bug.

== UI Automation with XCUIAutomation

UI tests use **XCUIAutomation**, which XCTest imports automatically. The test runs in its own process and controls
the app through the accessibility system: `XCUIApplication` launches and terminates the app, **queries** such as
`app.buttons["capture-button"]` find elements, and `XCUIElement` methods such as `tap()` and `+typeText(_:)+` act on
them. The test never calls the app's code, so it sees exactly what a person or VoiceOver sees.

UI testing isn't available for apps built with the **visionOS SDK**; Apple Vision Pro can only run UI tests for
compatible iPhone and iPad apps. *FieldNotes* is a native visionOS app, so its UI tests run on the iPhone, iPad and Mac
destinations.

=== Accessibility identifiers

A query can find an element by its label ("Save"), but labels are localized: the same test would fail in the German
configuration, where the button may read "Sichern". An **accessibility identifier** is a stable, non-localized string
that assistive technologies ignore; it exists for tests. *FieldNotes* sets identifiers on the elements its UI tests
touch:

[source,swift]
----
// Excerpts (updated) from NoteList, NoteListToolbar, NoteDraftForm and NoteComposer: identifiers for UI tests
List(visibleNotes) { note in
    NoteRow(note: note)
}
.accessibilityIdentifier("note-list")

CaptureButton(action: capture)
    .accessibilityIdentifier("capture-button")

TextField("Title", text: $draft.title)
    .accessibilityIdentifier("note-title-field")

Button("Save") {
    store.add(Note(title: draft.title, body: draft.body, notebookID: notebookID, tags: draft.tags))
    dismiss()
}
.disabled(draft.title.isEmpty)
.accessibilityIdentifier("save-note-button")
----

See link:++https://developer.apple.com/documentation/swiftui/view/accessibilityidentifier(_:)++[+Apple Developer Documentation -- accessibilityIdentifier(_:)+].

Identifiers must never replace labels; VoiceOver still needs "Capture" and "Save". The rules for labels are on
xref:apps/apple/accessibility.adoc[Accessibility]. On the Mac, the *New Note* toolbar button carries the same
`"capture-button"` identifier, so one test works on every destination.

=== Launching FieldNotes for a test: `--uitesting`

A UI test must start from a known state. If it ran against the developer's real App Group store, the note list would
contain whatever the developer had typed, and a test that adds a note would leave it behind. *FieldNotes* therefore
recognises one **launch argument**, `--uitesting`, which the test sets through `launchArguments` before launching.
`AppServices`, introduced on xref:apps/apple/background-execution.adoc[Background Execution], reads it when it
creates the app's one `NoteStore`. Only its initializer changes:

[source,swift]
----
// FieldNotes/AppServices.swift (updated: init() only; the type's properties and attributes are unchanged)
    private init() {
        // UI tests launch with --uitesting: an empty in-memory store that never touches disk or iCloud.
        let isUITesting = ProcessInfo.processInfo.arguments.contains("--uitesting")

        let persistence: SwiftDataNotePersistence
        do {
            if isUITesting {
                persistence = SwiftDataNotePersistence(modelContainer: try .fieldNotes(inMemory: true))
            } else {
                persistence = try SharedNoteAccess.persistence()
            }
        } catch {
            // As on the SwiftData page: a store that can't be opened is a deployment error, not a runtime state.
            fatalError("FieldNotes could not open its store: \(error)")
        }
        self.persistence = persistence

        if isUITesting {
            self.store = NoteStore(syncer: NoOpNoteSyncer(), persistence: persistence)
        } else {
            self.store = NoteStore(syncer: CloudNoteSyncer(), persistence: persistence)
        }
    }
----

See https://developer.apple.com/documentation/xcuiautomation/xcuiapplication/launcharguments[Apple Developer Documentation -- launchArguments].

Arguments set in `launchArguments` arrive in the app's `ProcessInfo.processInfo.arguments` (and `CommandLine.arguments`).
Because `AppServices.shared` is created before the first scene appears, every view, delegate and intent that goes
through it sees the in-memory store. Code that opens the App Group store itself through `SharedNoteAccess`, such as
the widgets, `NoteEntityQuery` and `TogglePinIntent`, still reads the real store. That's why the App Intents tests
(`FieldNotesShortcutsTests` and `FieldNotesIntentTests`) launch *without* `--uitesting`.

This is deliberate, not an oversight. FieldNotes has no separate App Intents extension: its intents are compiled
into the app target (and, for the shared ones, into the widget extensions too), so when Siri or Shortcuts run
`TogglePinIntent` they run it in the app's own process. What makes `NoteEntityQuery`, `TogglePinIntent` and the
widgets read the real store is that they open the App Group store directly through `SharedNoteAccess` instead of
going through `AppServices.shared`, so `--uitesting` never reaches them. The widgets additionally run in their own
extension process, which WidgetKit launches and which never receives the arguments an
https://developer.apple.com/documentation/xcuiautomation/xcuiapplication/launcharguments[`launchArguments`]
array sets on the app. A UI test that exercises one of those surfaces therefore seeds and cleans up that store
itself -- for example by driving the app, launched without `--uitesting`, to create and remove the notes the test
needs -- rather than relying on the in-memory store `--uitesting` provides.

The argument isn't limited to Debug builds on purpose: the launch performance test below runs a Release build. It
gives no access to data, only an empty store, so shipping it is harmless.

=== A first UI test

`NoteCaptureUITests` captures a note and checks that it appears in the list. `continueAfterFailure = false` stops the
test at the first failure, because every later step depends on the earlier ones. The XCUIAutomation APIs are
main-actor isolated, so the test methods are `@MainActor`.

[source,swift]
----
// FieldNotesUITests/NoteCaptureUITests.swift
import XCTest

final class NoteCaptureUITests: XCTestCase {
    override func setUpWithError() throws {
        continueAfterFailure = false
    }

    /// Every UI test starts from an empty, in-memory store (see AppServices.init()).
    @MainActor
    private func launchFieldNotes() -> XCUIApplication {
        let app = XCUIApplication()
        app.launchArguments.append("--uitesting")
        app.launch()
        return app
    }

    @MainActor
    func testCapturedNoteAppearsInTheList() throws {
        let app = launchFieldNotes()

        app.buttons["capture-button"].firstMatch.tap()

        let titleField = app.textFields["note-title-field"]
        XCTAssertTrue(titleField.waitForExistence(timeout: 5))
        titleField.tap()
        titleField.typeText("Heron at the weir")

        let save = app.buttons["save-note-button"]
        XCTAssertTrue(save.wait(for: \.isEnabled, toEqual: true, timeout: 2))
        save.tap()

        let list = app.descendants(matching: .any)["note-list"]
        XCTAssertTrue(list.staticTexts["Heron at the weir"].waitForExistence(timeout: 5))
    }
}
----

See https://developer.apple.com/documentation/xcuiautomation/xcuiapplication[Apple Developer Documentation -- XCUIApplication]
and link:++https://developer.apple.com/documentation/xcuiautomation/xcuielement/wait(for:toequal:timeout:)++[+Apple Developer Documentation -- wait(for:toEqual:timeout:)+].

A few habits keep UI tests reliable:

* **Wait, don't sleep.** `waitForExistence(timeout:)` returns as soon as the element appears; `wait(for:toEqual:timeout:)`
  does the same for any property, such as `isEnabled`. A fixed `sleep` is either too short on a slow CI machine or
  wasted time everywhere else.
* **Query by identifier, and keep queries short.** `app.buttons["capture-button"]` survives layout changes;
  `app.navigationBars.element(boundBy: 0).buttons.element(boundBy: 2)` doesn't. `firstMatch` stops at the first
  match instead of requiring exactly one.
* **Query by element type where the type is stable.** A SwiftUI `List` is a collection view on iOS and an outline on
  macOS, so `descendants(matching: .any)` finds `"note-list"` on both.
* **Check user-visible results**, such as the new title in the list, not implementation details.

See https://developer.apple.com/documentation/xcuiautomation/xcuielementquery[Apple Developer Documentation -- XCUIElementQuery].

=== Recording interactions

Writing queries by hand is the slow part of a UI test. Xcode can **record** them: put the cursor inside a test method
in a UI testing target, click the record button at the edge of the editor, and use the app. Xcode launches the app,
adds a query and an action for every interaction, and stops when you click the button again. Each recorded query has
a disclosure menu of alternatives that locate the same element; pick the identifier-based one and double-click it.
The first time, macOS asks to give *Xcode Helper* the Accessibility permission in System Settings.

A raw recording of the capture flow looks like this, before the queries are switched to identifiers:

[source,swift]
----
// As recorded: queries by label, which break in the German configuration
let app = XCUIApplication()
app.activate()
app.buttons["Capture"].tap()
app.textFields["Title"].tap()
app.textFields["Title"].typeText("Heron at the weir")
app.buttons["Save"].tap()
----

See https://developer.apple.com/documentation/xcuiautomation/recording-ui-automation-for-testing[Apple Developer Documentation -- Recording UI automation for testing].

Recording produces actions only. The assertions, which make it a test, are added by hand afterwards. A recorded test
with no assertions still has value: it passes only if every interaction is still possible and the app doesn't crash.

=== Accessibility audits in UI tests

`+performAccessibilityAudit(for:_:)+` checks the screen that is currently visible for missing labels, low contrast,
clipped text, small hit targets and Dynamic Type problems, and fails the test for each issue it finds.
xref:apps/apple/accessibility.adoc[Accessibility] audits the note list in `AccessibilityAuditTests`; `NoteCaptureUITests`
also audits the composer, which the list audit never opens:

[source,swift]
----
// FieldNotesUITests/NoteCaptureUITests.swift (continued, same file)
extension NoteCaptureUITests {
    @MainActor
    func testComposerPassesAccessibilityAudit() throws {
        let app = launchFieldNotes()
        app.buttons["capture-button"].firstMatch.tap()
        XCTAssertTrue(app.textFields["note-title-field"].waitForExistence(timeout: 5))

        try app.performAccessibilityAudit()          // all audit types
    }
}
----

See link:++https://developer.apple.com/documentation/xcuiautomation/xcuiapplication/performaccessibilityaudit(for:_:)++[+Apple Developer Documentation -- performAccessibilityAudit(for:_:)+]
and https://developer.apple.com/videos/play/wwdc2023/10035/[WWDC23 -- Perform accessibility audits for your app].

The extension can call the private `launchFieldNotes()` because it is in the same file.

=== Screenshots, video and attachments

A failing UI test is much easier to diagnose with a picture. There are two ways to get one:

* **Automatically.** In a test plan configuration, *Automatic Screen Capture* decides whether the UI test runner
  captures media and whether media of passing tests is deleted, and *Preferred Capture Format* chooses **video** or
  screenshots (Xcode 26 and later). By default, media is kept only for failing runs; choose *On, and keep all* to keep
  everything, for example to reuse the video in documentation. The test report plays the video of each run, with the
  test's steps alongside.
* **Explicitly.** `XCTAttachment(screenshot:)` wraps a screenshot of the app, a window or any element. Set
  `lifetime` to `.keepAlways` to keep it even when the test passes.

[source,swift]
----
// In testCapturedNoteAppearsInTheList, after typing the title
let composer = XCTAttachment(screenshot: app.screenshot())
composer.name = "Composer with a title"
composer.lifetime = .keepAlways
add(composer)
----

See https://developer.apple.com/documentation/xctest/adding-attachments-to-tests-activities-and-issues[Apple Developer Documentation -- Adding attachments to tests, activities, and issues]
and link:++https://developer.apple.com/documentation/xctest/xctattachment/init(screenshot:)++[+Apple Developer Documentation -- init(screenshot:)+].

Attachments are saved in the result bundle (`.xcresult`) that every test run produces, so they are available from CI
as well. The *Localization Screenshots* option of a configuration is a different feature: it collects screenshots for
translators, as described on xref:apps/apple/localization.adoc[Localization with String Catalogs].

== Performance Tests

A **performance test** is an XCTest method that calls `measure(metrics:block:)`. XCTest runs the block
`iterationCount` + 1 times (set through `XCTMeasureOptions`), discards the first, warm-up iteration, records each
**metric** for the rest, and compares the average with a **baseline**. The test fails when the
result is worse than the baseline by more than the allowed standard deviation. The first run has no baseline: click
the gray icon next to `measure` in the editor, then *Set Baseline*, and edit *Max STDDEV* if the default is too
strict. Baselines are stored per device in the project, so commit them.

`XCTClockMetric` records elapsed wall-clock time. *FieldNotes* measures `+NoteStore.togglePin(_:)+` on a large
library, because it searches the notes array and runs on the main actor, where slowness becomes a visible hitch:

[source,swift]
----
// FieldNotesTests/NoteStorePerformanceTests.swift (an XCTest class in the Swift Testing target)
import XCTest
import FieldNotesModel
import FieldNotesServices

final class NoteStorePerformanceTests: XCTestCase {
    @MainActor
    func testTogglingAPinInALargeLibrary() {
        let notes = (0..<10_000).map { Note(title: "Survey note \($0)") }
        let store = NoteStore(notes: notes)
        let last = notes[notes.count - 1]

        let options = XCTMeasureOptions()
        options.iterationCount = 10

        measure(metrics: [XCTClockMetric(), XCTCPUMetric()], options: options) {
            store.togglePin(last)
        }
    }
}
----

See link:++https://developer.apple.com/documentation/xctest/xctestcase/measure(metrics:options:block:)++[+Apple Developer Documentation -- measure(metrics:options:block:)+]
and https://developer.apple.com/documentation/xctest/xctclockmetric[Apple Developer Documentation -- XCTClockMetric].

`XCTApplicationLaunchMetric` measures app launch, from process start to the first frame, or until the app is
responsive with `waitUntilResponsive: true`. It belongs in a UI test, since it launches the app each iteration:

[source,swift]
----
// FieldNotesUITests/LaunchPerformanceTests.swift
import XCTest

final class LaunchPerformanceTests: XCTestCase {
    @MainActor
    func testLaunchUntilResponsive() {
        measure(metrics: [XCTApplicationLaunchMetric(waitUntilResponsive: true)]) {
            let app = XCUIApplication()
            app.launchArguments.append("--uitesting")    // same empty store every iteration
            app.launch()
        }
    }
}
----

See https://developer.apple.com/documentation/xctest/xctapplicationlaunchmetric[Apple Developer Documentation -- XCTApplicationLaunchMetric].

Performance numbers are only meaningful under release conditions. Apple's guidance is to build for testing with the
**Release** configuration, turn off *Debug executable* in the scheme, and run from a test plan with code coverage and
the sanitizers **off**. *FieldNotes* therefore keeps its performance tests out of `FieldNotes.xctestplan` and runs
them from a second, small plan, `FieldNotesPerformance.xctestplan`, which contains only the two performance classes.
When a performance test fails, Control-click its icon in the gutter and choose *Profile* to open it in Instruments; see
xref:apps/apple/performance-and-instruments.adoc[Performance and Instruments].

See https://developer.apple.com/documentation/xcode/writing-and-running-performance-tests[Apple Developer Documentation -- Writing and running performance tests].

== Test Plans

A **test plan** (`.xctestplan`) is a file in the project that says *which* tests to run and *how*: the test targets,
the tests or tags to include or exclude, and one or more **configurations**. Xcode runs the plan's tests once for each
configuration. A scheme has one default plan, which ⌘U runs, and may have others.

`FieldNotes.xctestplan` includes `FieldNotesTests` and `FieldNotesUITests` and has three configurations:

[cols="1,3",options="header"]
|===
| Configuration | Settings

| *Default*
| *Code Coverage* on for the `FieldNotes` target and the `FieldNotesKit` modules; *Automatic Screen Capture* keeping
media for failures, *Preferred Capture Format* video; *Test Repetition Mode* "Retry on Failure", *Maximum Test
Repetitions* 3 (UI tests only); *Execution Order* random.

| *German*
| As *Default*, plus *Application Language* German and *Application Region* Germany: longer strings, other date and
number formats. Localization is covered on xref:apps/apple/localization.adoc[Localization with String Catalogs].

| *Sanitizers*
| *Address Sanitizer* and *Undefined Behavior Sanitizer* on, code coverage off, screen capture off.
Thread Sanitizer can't be combined with Address Sanitizer, so it is enabled in the scheme when needed; see
xref:apps/apple/debugging-with-xcode-and-lldb.adoc[Debugging with Xcode and LLDB].
|===

See https://developer.apple.com/documentation/xcode/organizing-tests-to-improve-feedback[Apple Developer Documentation -- Improving code assessment by organizing tests into test plans]
and https://developer.apple.com/documentation/xcode/diagnosing-memory-thread-and-crash-issues-early[Apple Developer Documentation -- Diagnosing memory, thread, and crash issues early].

The plan is edited in Xcode's test plan editor (*Product > Test Plan > Edit Test Plan*), which writes a JSON file.
Apple doesn't document the file format, and the keys can change between Xcode versions, so edit plans in the editor
and review the JSON in code review. A trimmed excerpt of what the editor writes for the configurations above looks
like this:

=== Tags, repetitions and parallel testing

**Tags.** A test plan can include or exclude Swift Testing tests by tag (Xcode 16 and later): in the plan's *Tests*
pane, type tag names such as `persistence` in *Include Tags* or *Exclude Tags*, and choose *Any Tag* or *All Tags*.
*FieldNotes*'s pull-request plan excludes `sync`, so no test needs iCloud; the tags themselves are declared on
xref:apps/apple/testing-with-swift-testing.adoc[Unit Testing with Swift Testing]. Individual suites, functions and
even single arguments of a parameterized test can also be unchecked in the plan's outline.

**Repetitions.** *Test Repetition Mode* runs each test once, a fixed number of times, until it fails, or until it
passes, up to *Maximum Test Repetitions*. "Until failure" is how to reproduce a flaky test; "Retry on failure" keeps
an occasional UI-test hiccup from failing the build, but a test that needs retries is still a bug to fix. *Relaunch
Tests for Each Repetition* starts a fresh process each time.

**Parallelization.** XCTest can split a test target across several clones of a simulator (or several processes on the
Mac), enabled per target in the plan (*Execute in parallel*). Swift Testing runs tests in parallel inside one process
anyway. UI tests parallelize well because each clone has its own app container, which is another reason for
``--uitesting``'s isolated store. *Execution Order: Random* exposes tests that only pass after another test has run.

The same controls exist on the command line:

[source,shell]
----
# Which plans does the scheme have?
xcodebuild -project FieldNotes.xcodeproj -scheme FieldNotes -showTestPlans

# Run one configuration of the plan, retrying failed tests up to 3 times, on 3 parallel simulator clones
xcodebuild test -project FieldNotes.xcodeproj -scheme FieldNotes \
  -testPlan FieldNotes -only-test-configuration German \
  -destination 'platform=iOS Simulator,name=iPhone 17' \
  -retry-tests-on-failure -test-iterations 3 \
  -parallel-testing-enabled YES -parallel-testing-worker-count 3

# Reproduce a flaky UI test: run it until it fails, at most 50 times
xcodebuild test -project FieldNotes.xcodeproj -scheme FieldNotes \
  -destination 'platform=iOS Simulator,name=iPhone 17' \
  -only-testing:FieldNotesUITests/NoteCaptureUITests/testCapturedNoteAppearsInTheList \
  -run-tests-until-failure -test-iterations 50
----

See https://developer.apple.com/documentation/xcode/organizing-tests-to-improve-feedback[Apple Developer Documentation -- Improving code assessment by organizing tests into test plans].

== Code Coverage

**Code coverage** records which lines ran during the tests. Enable it in the plan: *Configurations* tab, *Shared
Settings* or one configuration, *Code Coverage*, then check *Gather coverage for* and choose the targets. After a run,
the **Coverage** pane of the Report navigator lists each target, file and function with its percentage, and *Editor >
Code Coverage* annotates the source: each line shows how often it ran, and code that never ran is highlighted.

[source,shell]
----
# Collect coverage into a result bundle, then read it
xcodebuild test -project FieldNotes.xcodeproj -scheme FieldNotes -testPlan FieldNotes \
  -only-test-configuration Default \
  -destination 'platform=iOS Simulator,name=iPhone 17' \
  -enableCodeCoverage YES -resultBundlePath build/FieldNotes.xcresult

xcrun xccov view --report --only-targets build/FieldNotes.xcresult     # one line per target
xcrun xccov view --report --json build/FieldNotes.xcresult > build/coverage.json
----

See https://developer.apple.com/documentation/xcode/determining-how-much-code-your-tests-cover[Apple Developer Documentation -- Determining how much code your tests cover].

Coverage tells you what the tests *didn't* run, not whether the tests that did run check anything. Use it to find
untested branches, such as an error path in `NoteStore.load()`, and then write a test for them. Keep in mind that:

* skipped tests don't count, but tests that ran with a known issue or an expected failure do;
* gathering coverage slows the code down, linearly, so keep it off for performance tests;
* UI tests produce coverage too, which can make a screen look tested when only its happy path was exercised.

*FieldNotes* doesn't gate merges on a coverage percentage. It reviews the coverage of the files a change touches, and
the `FieldNotesServices` module, which holds the logic, is expected to be well covered.

== Snapshot Testing Without a Snapshot Framework

Apple ships **no snapshot-testing framework**: nothing in XCTest or Swift Testing compares a rendered view with a
reference image. *FieldNotes* covers the same need with three built-in tools:

* **Previews** for reviewing views by eye, in light and dark mode, at large text sizes and in German, while
  developing; see xref:apps/apple/xcode-projects-and-previews.adoc[Xcode Projects, Targets, Schemes and Previews].
* **Screenshots and video from UI tests**, kept for every run in the *Default* configuration of a release branch,
  to compare screens between versions.
* **Image attachments in Swift Testing** (Xcode 26.4 and later): a test renders a view with `ImageRenderer` and
  attaches the image, so each run's report contains what the view looked like.

[source,swift]
----
// FieldNotesTests/TagChipSnapshotTests.swift
import CoreGraphics
import SwiftUI
import Testing
import FieldNotesUI

@MainActor
@Suite(.tags(.ui))
struct TagChipSnapshotTests {
    @Test(arguments: [false, true])
    func rendersTagChip(isSelected: Bool) throws {
        let renderer = ImageRenderer(content: TagChip("birds", isSelected: isSelected).padding())
        renderer.scale = 2

        let image = try #require(renderer.cgImage)
        Attachment.record(image, named: isSelected ? "tag-chip-selected.png" : "tag-chip.png")
        #expect(image.width > 0 && image.height > 0)
    }
}

#Preview("Tag chips") {
    HStack {
        TagChip("birds")
        TagChip("otters", isSelected: true)
    }
    .padding()
}
----

See https://developer.apple.com/documentation/testing/attachments[Apple Developer Documentation -- Attachments],
https://developer.apple.com/documentation/swiftui/imagerenderer[Apple Developer Documentation -- ImageRenderer]
and https://developer.apple.com/documentation/swiftui/previews-in-xcode[Apple Developer Documentation -- Previews in Xcode].

These attachments are for people to look at; the test doesn't compare pixels. Third-party libraries, such as
Point-Free's swift-snapshot-testing, add reference-image comparison on top of XCTest and Swift Testing if a project
needs it; they are not Apple frameworks and pixel comparisons are sensitive to the OS version and simulator used.
