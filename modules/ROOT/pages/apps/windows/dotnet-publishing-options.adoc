Writing the app is half of the job; the other half is deciding what leaves the build machine. A Windows desktop app
built with the .NET SDK can be published as a folder that needs the .NET runtime on the target PC, as a folder that
carries its own runtime, as one executable, as precompiled ("ReadyToRun") assemblies, trimmed, or compiled ahead of
time to native code. Each choice trades download size, start-up time, prerequisites and compatibility, and the
desktop stacks do not support the same set of choices. This page is the reference for those choices and for the
`dotnet publish` command that applies them. Wrapping the result in an MSIX package, signing it and putting it in front
of users is the job of the other publishing pages of this section: xref:apps/windows/msix-packaging-and-signing.adoc[MSIX Packaging & Signing], xref:apps/windows/distribution-channels.adoc[Distribution Channels], xref:apps/windows/updates-versioning-and-telemetry.adoc[Updates, Versioning & Telemetry] and xref:apps/windows/ci-cd-with-github-actions.adoc[CI/CD with GitHub Actions] (they are named here, not linked, because
they are written independently).

== Publishing Is a Different Step from Building

`dotnet build` produces files that run on the developer machine, next to the SDK. `dotnet publish` produces the set
of files meant to be copied somewhere else. It compiles the application, reads its dependencies from the project file
and copies the result to a folder. The output contains:

* the application assemblies (IL code in `.dll` files) and, by default, a platform-specific launcher, the _apphost_
  (`Bookshelf.Desktop.exe`),
* a `.deps.json` file listing every dependency,
* a `.runtimeconfig.json` file naming the shared runtime the app expects and other runtime options, and
* the dependencies copied from the NuGet cache (and, for a self-contained app, the runtime itself).

Microsoft describes `dotnet publish` as the only officially supported way to prepare an application for deployment:
copying the `bin\Release` folder by hand skips steps such as copying the RID-specific native assets of NuGet packages.

=== The command and its options

[cols="2,4",options="header"]
|===
| Option | Meaning
| `-c`, `--configuration` | Build configuration. With the .NET 8 SDK and later the default for `dotnet publish` is `Release` for projects that target `net8.0` or later (older targets still default to `Debug`). Passing `-c Release` explicitly is still good practice in scripts.
| `-r`, `--runtime <RID>` | Target runtime identifier, such as `win-x64`. Pass `--self-contained` or `--no-self-contained` with it, so the mode is explicit.
| `--self-contained` / `--no-self-contained` (`--sc`) | Bundle the .NET runtime with the app, or require it on the target machine.
| `-a`, `--arch <ARCH>` and `--os <OS>` | Shorthand that edits the current RID: on a `win-x64` machine `--arch x86` selects `win-x86`. Do not combine them with `-r`.
| `-f`, `--framework <TFM>` | Required when the project multi-targets. A desktop project normally has one target, such as `net10.0-windows`.
| `-o`, `--output <DIR>` | Publish folder. By default `bin/<configuration>/<framework>/publish/` (framework-dependent) or `bin/<configuration>/<framework>/<runtime>/publish/` (self-contained). On a solution, `-o` is not valid in recent SDKs; use `+-p:PublishDir=<folder>+` instead.
| `-p:<Name>=<Value>` | Set any MSBuild property, for example `-p:PublishSingleFile=true`. This is how every option in later sections can be applied from a script.
| `--no-restore`, `--no-build` | Skip the implicit restore or build. After `--no-build`, use the same options you used when building (do not build framework-dependent and then publish self-contained).
| `-p:PublishProfile=<name>` | Apply a publish profile (`.pubxml`) from `Properties/PublishProfiles`.
| `--artifacts-path` | Send all build output to one folder tree (artifacts layout); pass it to every command in a pipeline.
|===

Two defaults deserve a sentence. First, framework-dependent output is the default mode of both the CLI and Visual
Studio. Second, `PublishSingleFile` implies a self-contained publish unless you say `--no-self-contained`; the
single-file section below returns to that.

[source,powershell]
----
# Framework-dependent, current machine's RID (the default mode)
dotnet publish src/Bookshelf.Desktop -c Release

# Self-contained for 64-bit Windows
dotnet publish src/Bookshelf.Desktop -c Release -r win-x64 --self-contained true -o publish/win-x64

# Same sources for an Arm64 PC (a Copilot+ laptop, for example)
dotnet publish src/Bookshelf.Desktop -c Release -r win-arm64 --self-contained true -o publish/win-arm64

# Print where the files went
Get-ChildItem publish/win-x64 | Select-Object -First 8 Name, Length
----

Source: https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-publish[dotnet publish]

=== The Quick Reference of Modes

[cols="2,3",options="header"]
|===
| Mode | Command
| Framework-dependent | `dotnet publish -c Release -r win-x64 --self-contained false`
| Framework-dependent, portable DLL only | `dotnet publish -c Release -p:UseAppHost=false` (run with `dotnet Bookshelf.Desktop.dll`; GUI apps normally keep the apphost)
| Self-contained | `dotnet publish -c Release -r win-x64 --self-contained true`
| Single-file | `dotnet publish -c Release -r win-x64 -p:PublishSingleFile=true`
| ReadyToRun | `dotnet publish -c Release -r win-x64 -p:PublishReadyToRun=true`
| Native AOT | `dotnet publish -c Release -r win-x64 -p:PublishAot=true` (not for WPF or Windows Forms)
|===

== Runtime Identifiers: win-x64, win-x86 and win-arm64

A _runtime identifier_ (RID) names the operating system and processor an app targets. NuGet uses it to choose
RID-specific assets (native libraries) from packages, and the SDK uses it to choose the apphost and, for a
self-contained app, the runtime. For Windows there are three portable RIDs:

[cols="1,3,3",options="header"]
|===
| RID | Machines | Notes
| `win-x64` | 64-bit Intel and AMD PCs. | The default choice for new releases.
| `win-x86` | 32-bit processes. | Needed only for a plugin host, a 32-bit native dependency or an old 32-bit-only machine. A 32-bit .NET Desktop Runtime is a separate install from the 64-bit one.
| `win-arm64` | Arm64 PCs. | A native build avoids running through emulation. The Windows App SDK runtime installer exists in an `X64`, `X86` and `Arm64` flavor.
|===

Since .NET 8 the SDK uses only _portable_ RIDs, those that are not tied to an operating-system version or a
distribution. Older version-specific values such as `win10-x64` appear in older articles and templates (the single-project MSIX instructions of the Windows App SDK still reference a
`win10-$(Platform).pubxml` profile), but new code should use `win-x64`,
`win-x86` and `win-arm64`. Do not parse a RID or build one in code unless you must; if you do, the casing must match
the catalog exactly.

Two project properties exist, and they mean different things:

[cols="1,3",options="header"]
|===
| Property | Meaning
| `RuntimeIdentifier` | One RID. Setting it makes `dotnet build` produce a RID-specific output. Since the .NET 8 SDK it no longer implies a self-contained app, so set `SelfContained` explicitly.
| `RuntimeIdentifiers` | A semicolon-separated list of RIDs the project can be restored for. It does not select one; it lets `dotnet publish -r win-arm64` succeed because the restore already pulled the Arm64 assets.
|===

A practical consequence: a project that is published for several architectures lists them all in
`RuntimeIdentifiers` and chooses one per publish with `-r`. Publishing from a solution file with `-r` can produce
output without the RID-specific assets because the first compilation happens without that RID; publish the project
(not the solution) or list the RIDs in the project file.

[source,xml]
----
<!-- Bookshelf.Desktop.csproj (WPF) -->
<Project Sdk="Microsoft.NET.Sdk">

  <PropertyGroup>
    <OutputType>WinExe</OutputType>
    <TargetFramework>net10.0-windows</TargetFramework>
    <UseWPF>true</UseWPF>
    <Nullable>enable</Nullable>
    <ImplicitUsings>enable</ImplicitUsings>
    <!-- Which RIDs this project can be published for. -->
    <RuntimeIdentifiers>win-x64;win-x86;win-arm64</RuntimeIdentifiers>
  </PropertyGroup>

</Project>
----

Source: https://learn.microsoft.com/en-us/dotnet/core/rid-catalog[.NET Runtime Identifier (RID) catalog]

== Publish Profiles

A _publish profile_ is a `.pubxml` MSBuild file in `Properties/PublishProfiles/` that stores the publish settings
under a name. Visual Studio creates one when you run *Build > Publish* (target *Folder*), and `dotnet publish` can
load it with `-p:PublishProfile=<name>`. MSBuild assumes the `Properties/PublishProfiles` folder and the `.pubxml`
extension, so pass only the name (`PublishProfileFullPath` takes a full path).

[source,xml]
----
<!-- Properties/PublishProfiles/win-x64-selfcontained.pubxml -->
<Project>
  <PropertyGroup>
    <Configuration>Release</Configuration>
    <Platform>Any CPU</Platform>
    <PublishDir>bin\Release\net10.0-windows\publish\win-x64\</PublishDir>
    <PublishProtocol>FileSystem</PublishProtocol>
    <TargetFramework>net10.0-windows</TargetFramework>
    <RuntimeIdentifier>win-x64</RuntimeIdentifier>
    <SelfContained>true</SelfContained>
    <PublishSingleFile>false</PublishSingleFile>
    <PublishReadyToRun>true</PublishReadyToRun>
  </PropertyGroup>
</Project>
----

[source,powershell]
----
dotnet publish src/Bookshelf.Desktop -p:PublishProfile=win-x64-selfcontained
----

Source: https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-publish[dotnet publish (.pubxml files)]

The command line honors only part of what Visual Studio stores in a profile. The documentation lists properties that
`dotnet publish` does not honor from a `.pubxml` file because they influence the build rather than the publish step:
`Configuration`, `Platform`, `LastUsedBuildConfiguration`, `LastUsedPlatform`, `TargetFramework`, `TargetFrameworks`,
`RuntimeIdentifier` and `RuntimeIdentifiers`. In the profile above, the lines for `Configuration`, `Platform`,
`TargetFramework` and `RuntimeIdentifier` therefore work in Visual Studio but are ignored by the CLI, so a CI script
using the profile must still pass `-c Release -r win-x64`. A profile also uses `PublishDir` for the CLI and
`PublishUrl` for Visual Studio; set both to the same value if the profile is used from both places.

Microsoft recommends keeping `PublishReadyToRun`, `PublishSingleFile` and `PublishTrimmed` in the project or profile
rather than on the command line, because they also change build-time analysis.

A good habit is one profile per distribution you ship: for Bookshelf Desktop, `folder-fdd-x64`, `folder-scd-x64`,
`folder-scd-arm64` and `onefile-scd-x64`. The WinUI 3 templates add profiles under the same folder; the project-structure page of this section describes it.

== Framework-Dependent versus Self-Contained

The first and most important choice is where the .NET runtime comes from.

[cols="1,3,3",options="header"]
|===
| | Framework-dependent (FDD) | Self-contained (SCD)
| Output | The app, its dependencies, the apphost. | The same plus the whole .NET runtime and the framework assemblies.
| Size | Small. | Large (the runtime and the WPF or Windows Forms assemblies travel with every copy).
| Prerequisite | The matching _.NET Desktop Runtime_ must be installed (see below). | None. The target PC needs no .NET installation.
| Runtime updates | The app rolls forward to the latest patch of its major version installed on the machine, so security patches arrive through Microsoft Update or the user's package manager. | The app keeps the runtime it shipped with; a security fix means releasing a new build.
| Behavior drift | A newer runtime on the machine can change behavior slightly. | Fully controlled by the developer.
| Typical use | Corporate PCs that standardize on a runtime; installers that include a prerequisite check. | Consumer downloads, portable zip files, locked-down PCs, side-by-side copies of different versions.
|===

Framework-dependent publishing creates an app that automatically rolls forward to the latest .NET security patch
installed on the machine. A self-contained app does not roll forward. Microsoft's own advice for self-contained
apps: you control the version, but updating the runtime means shipping the app again.

=== Where the apphost looks for .NET

A framework-dependent app starts through the apphost (`Bookshelf.Desktop.exe`), which finds a globally installed
runtime. Starting an app through `dotnet Bookshelf.Desktop.dll` is also possible, but the apphost has advantages: the
file appears as a normal executable with its own process name, a native manifest can be attached to it, and it gets
low-level security mitigations (for example Control-flow Enforcement Technology shadow stack, enabled by default
starting with .NET 9).

The search can be customized:

* `DOTNET_ROOT` points one execution to a runtime in a custom folder. Clear any variable that starts with
  `DOTNET_ROOT` first, set only `DOTNET_ROOT`, then run the apphost.
* In .NET 9 and later, `AppHostDotNetSearch` configures where the published executable looks (`AppLocal`,
  `AppRelative`, `EnvironmentVariable` or `Global`), and `AppHostRelativeDotNet` gives the relative path used by
  `AppRelative`. That lets an installer place a private runtime in a sub-folder without setting machine-wide variables.

[source,xml]
----
<PropertyGroup>
  <SelfContained>false</SelfContained>
  <!-- Look next to the app first, then in the registered global install. -->
  <AppHostDotNetSearch>AppLocal;Global</AppHostDotNetSearch>
</PropertyGroup>
----

Source: https://learn.microsoft.com/en-us/dotnet/core/deploying/#configure-net-install-search-behavior[Configure .NET install search behavior]

=== The .NET Desktop Runtime Prerequisite

A framework-dependent WPF or Windows Forms app needs the *.NET Desktop Runtime*, not just the base ".NET Runtime".
On Windows there are three runtimes, and each installer includes a different set:

[cols="2,1,1,1",options="header"]
|===
| Installer | .NET Runtime | .NET Desktop Runtime | ASP.NET Core Runtime
| .NET Runtime | Yes | No | No
| .NET Desktop Runtime | Yes | Yes | No
| ASP.NET Core Runtime | No | No | Yes
| .NET SDK | Yes | Yes | Yes
|===

The Desktop Runtime is what contains WPF and Windows Forms, so it is the prerequisite for the Bookshelf Desktop WPF and
WinForms builds (a WinUI 3 app needs the Windows App SDK runtime as well, covered later). The runtime installed must be
the same _major_ version the app targets (.NET 10 for `net10.0-windows`) and the same architecture as the app
(a 32-bit app needs the x86 runtime even on a 64-bit PC). Windows 11 and Windows 10 both run .NET 10 on x64, x86 and
Arm64; Windows 8.1 and Windows 7 are not supported by any supported .NET version.

[cols="2,3",options="header"]
|===
| How the user gets it | Details
| .NET installer (`windowsdesktop-runtime-<version>-win-x64.exe`) | Download page installs system-wide and needs administrative rights. Silent flags: `/install /quiet /norestart`. Exit code `0` is success and `3010` means a restart is required.
| WinGet | `winget install Microsoft.DotNet.DesktopRuntime.10`. System-wide installs need administrative privileges.
| `dotnet-install.ps1` | `dotnet-install.ps1 -Runtime windowsdesktop`; meant for CI and non-administrator installs.
| Bundled with your installer | Chain the runtime installer as a prerequisite in a setup program (WiX bundle, Inno Setup and similar).
| Visual Studio or the SDK | Developers already have it; an SDK install includes all three runtimes.
|===

The .NET installers can be serviced by Microsoft Update, install side by side across major and minor releases and
architectures, and (since .NET 8.0.11) honor a `RemovePreviousVersion` registry value (`always`, `never` or
`nextSession`) that controls when the older runtime is removed. Windows 7, Windows 8.1 and Windows Server 2012 builds
need the Visual C++ redistributable; a missing `hostfxr.dll` or `api-ms-win-crt-runtime-l1-1-0.dll` is the typical
symptom on such machines.

[source,powershell]
----
# prerequisite-check.ps1 -- exit 0 when a .NET 10 Desktop Runtime is installed
$runtimes = & dotnet --list-runtimes 2>$null
if ($runtimes -match 'Microsoft\.WindowsDesktop\.App 10\.') {
    Write-Host 'Microsoft.WindowsDesktop.App 10.x found.'
    exit 0
}
Write-Host 'Missing .NET 10 Desktop Runtime. Installing with WinGet...'
winget install --id Microsoft.DotNet.DesktopRuntime.10 --exact --silent `
    --accept-package-agreements --accept-source-agreements
exit $LASTEXITCODE
----

Source: https://learn.microsoft.com/en-us/dotnet/core/install/windows[Install .NET on Windows]

A user with only the apphost and no runtime sees a dialog from the apphost offering a download link; for a managed
rollout, check the prerequisite in the installer rather than relying on that dialog.

== Single-File Deployment

`PublishSingleFile` bundles the app's dependency files into one executable. It works for framework-dependent and
self-contained apps, is always specific to one OS and architecture, and can be combined with ReadyToRun and
trimming. The `+*.runtimeconfig.json+` and `+*.deps.json+` files are included in the bundle.

[source,xml]
----
<PropertyGroup>
  <OutputType>WinExe</OutputType>
  <TargetFramework>net10.0-windows</TargetFramework>
  <UseWPF>true</UseWPF>

  <RuntimeIdentifier>win-x64</RuntimeIdentifier>
  <SelfContained>true</SelfContained>
  <PublishSingleFile>true</PublishSingleFile>
</PropertyGroup>
----

[cols="2,3",options="header"]
|===
| Property | Effect
| `PublishSingleFile` | Enables single-file publish and the single-file analyzer warnings during build. Set it in the project file, not only on the command line.
| `SelfContained` | Selects self-contained or framework-dependent output. The `dotnet publish` reference says `PublishSingleFile` implicitly sets `PublishSelfContained` to true, while the single-file article shows framework-dependent single-file publishing with `--self-contained false`; write the mode explicitly so the result does not depend on the SDK default.
| `RuntimeIdentifier` | The target. A single-file app has to be built for a specific RID. Since the .NET 8 SDK a RID does not imply `SelfContained`, so set that property explicitly.
| `IncludeNativeLibrariesForSelfExtract` | Embeds the runtime's native binaries in the bundle for extraction, so you get one output file (see below).
| `IncludeAllContentForSelfExtract` | Extracts _all_ files, managed assemblies included, before the app runs. A .NET Core 3.1 compatibility mode that Microsoft does not recommend and may remove.
| `EnableCompressionInSingleFile` | Compresses the embedded assemblies; costs start-up time.
| `DebugType` = `embedded` | Embeds the PDB of your assemblies in the `.dll`.
| `ExcludeFromSingleFile` (item metadata) | Keeps a file next to the executable instead of inside the bundle.
|===

=== Native libraries

Only managed DLLs are bundled by default. When the app starts they are loaded from the bundle in memory, but the
native binaries of the runtime itself stay as separate files beside the executable. To embed them as well, set
`IncludeNativeLibrariesForSelfExtract` to `true`. The price is extraction: the native files are written to disk
before the app starts, to a directory under the path in the `DOTNET_BUNDLE_EXTRACT_BASE_DIR` environment variable if
it is set, and otherwise under `%TEMP%\.net` on Windows. To prevent tampering, that directory must not be writable by
users or services with different privileges.

A WPF app also depends on native helper libraries that ship with the desktop framework, which is why a WPF single-file
build still shows a few `.dll` files unless the property above is set (the exact file names depend on the release and
are not listed here).

=== Embedded symbols and compression

A single-file app keeps its `.pdb` files beside the executable by default. Setting `DebugType` to `embedded` in the
project puts the symbols in the assembly instead, which makes stack traces carry line numbers without an extra file.
That is the setting the Price chapter shows, and it is the one to keep in mind for crash reports.

`EnableCompressionInSingleFile` compresses the embedded assemblies, which can shrink the executable a lot, but the
assemblies must be decompressed into memory at start-up. Measure both the size change and the start-up cost; the
effect differs between applications.

[source,xml]
----
<!-- Bookshelf.Desktop.csproj -- one portable EXE for 64-bit Windows -->
<Project Sdk="Microsoft.NET.Sdk">

  <PropertyGroup>
    <OutputType>WinExe</OutputType>
    <TargetFramework>net10.0-windows</TargetFramework>
    <UseWPF>true</UseWPF>
    <Nullable>enable</Nullable>

    <RuntimeIdentifier>win-x64</RuntimeIdentifier>
    <SelfContained>true</SelfContained>
    <PublishSingleFile>true</PublishSingleFile>
    <IncludeNativeLibrariesForSelfExtract>true</IncludeNativeLibrariesForSelfExtract>
    <EnableCompressionInSingleFile>true</EnableCompressionInSingleFile>
    <DebugType>embedded</DebugType>
    <!-- Keep only the satellite languages the app really ships. -->
    <SatelliteResourceLanguages>en;es</SatelliteResourceLanguages>
  </PropertyGroup>

</Project>
----

Source: https://learn.microsoft.com/en-us/dotnet/core/deploying/single-file/overview[Create a single file for application deployment]

(`SatelliteResourceLanguages` is a general SDK property that limits which localized resource folders of dependencies
are copied; it is not part of the single-file article.)

=== Single-file pitfalls

* *File-path APIs*. In a single-file app `Assembly.Location` returns an empty string and `Assembly.CodeBase` throws
  `PlatformNotSupportedException`. Use `AppContext.BaseDirectory` for files next to the executable and
  `Environment.ProcessPath` for the executable path. Third-party libraries that load files by path can break.
* *Managed C++ components* are not well suited for single-file deployment.
* *Plug-ins* kept as separate DLLs must be marked with `ExcludeFromSingleFile` so they stay next to the app.
* *Signing before bundling*: the SDK has an extension point (the `PrepareForBundle` target runs before
  `GenerateSingleFileBundle`, and `FilesToBundle` lists the files) for tools that must modify the binaries first.
* *Self-extraction and security*: the extraction directory must not be writable by other principals.

[source,csharp]
----
using System.IO;

namespace Bookshelf.Desktop.Services;

public static class AppPaths
{
    // Works for folder deployments and single-file bundles alike.
    public static string SeedDataFile =>
        Path.Combine(AppContext.BaseDirectory, "Data", "seed-books.json");

    // Assembly.GetExecutingAssembly().Location is "" in a single-file app.
    public static string ExecutablePath => Environment.ProcessPath ?? string.Empty;
}
----

Source: https://learn.microsoft.com/en-us/dotnet/core/deploying/single-file/overview#api-incompatibility[Single-file: API incompatibility]

== ReadyToRun (R2R)

ReadyToRun precompiles the assemblies to native code in addition to IL, which reduces the work the just-in-time (JIT)
compiler does during start-up and the first use of each feature. It matters for desktop apps because a window shows
up only after a lot of code has run once: XAML loading, binding, styles. R2R is a form of ahead-of-time compilation,
but it is not Native AOT: the IL stays in the file and the JIT can still run.

[cols="1,3",options="header"]
|===
| Aspect | Detail
| Switch | `PublishReadyToRun` = `true`, effective at publish time. Microsoft recommends setting it in a publish profile rather than on the command line.
| RID | Required. R2R is only available when publishing for a specific runtime such as `win-x64`.
| Which assemblies | Those distributed with the app. For a self-contained app that includes the framework assemblies. C++/CLI binaries are not eligible. `PublishReadyToRunExclude` removes named assemblies.
| Size | An assembly typically grows to two to three times its size (it holds IL and native code).
| Gain | Large code bases benefit most. Small apps gain little because the runtime libraries are already precompiled.
| Tiering | R2R code is less optimized than JIT output; tiered compilation replaces hot R2R methods with JIT code.
| Composite | `PublishReadyToRunComposite` compiles a set of assemblies together for better optimization, with much slower compilation and a much bigger output; recommended only when tiered compilation is disabled or for Linux self-contained start-up scenarios.
| Cross-compiling | A Windows x64 machine can produce R2R images for Windows x86, x64 and Arm64 (and Linux and macOS) for .NET 6 and later.
| Symbols | `PublishReadyToRunEmitSymbols` writes `.ni.pdb` files on Windows for profilers; store them on a symbol server, not on user PCs.
| Warnings | `PublishReadyToRunShowWarnings` reports missing dependencies that could fail at run time.
|===

R2R is supported on WPF and Windows Forms projects as part of the normal desktop SDKs, and it combines with
framework-dependent, self-contained and single-file publishing. For WinUI 3 it follows the same .NET rules; test the
published output because WinUI relies on generated projection code.

[source,powershell]
----
dotnet publish src/Bookshelf.Desktop -c Release -r win-x64 --self-contained true `
    -p:PublishReadyToRun=true -p:PublishReadyToRunEmitSymbols=true -o publish/win-x64-r2r
----

Source: https://learn.microsoft.com/en-us/dotnet/core/deploying/ready-to-run[ReadyToRun deployment overview]

== Trimming

Trimming removes the parts of the framework and of your dependencies that a static analysis cannot find a use for,
which can shrink a self-contained app a lot. `PublishTrimmed` is only available to self-contained apps and is
analyzed at build time, so a code pattern the analyzer cannot follow produces a warning. Reflection is the usual
cause: serializers such as Newtonsoft.Json, `Assembly.LoadFrom` plug-in loading, `System.Reflection.Emit`, and
built-in COM marshalling are all trimming-incompatible.

[source,xml]
----
<PropertyGroup>
  <SelfContained>true</SelfContained>
  <PublishTrimmed>true</PublishTrimmed>
</PropertyGroup>
----

The trim mode (`TrimMode`: `partial` trims only assemblies that opted in, `full` trims every assembly) exists since
.NET 6, and the Price chapter shows `TrimMode partial` as the safer way to try trimming. The page about trimming
describes `PublishTrimmed` with a self-contained RID publish such as `dotnet publish -r win-x64 -p:PublishTrimmed=true`.
Which mode is the default in your SDK is not stated in the pages cited here, so set `TrimMode` explicitly when you
use trimming.

=== Why trimming is off for WPF and Windows Forms

[cols="1,3",options="header"]
|===
| Stack | Trimming status
| WPF | Not supported. WPF "makes substantial use of reflection and some features are heavily reliant on runtime code inspection", so trimming analysis cannot preserve all necessary code, almost no WPF app runs after trimming, and the .NET SDK disables it. Setting `PublishTrimmed` on a WPF project produces the SDK error NETSDK1168 (see the pitfalls). Progress is tracked in dotnet/wpf issue 3811.
| Windows Forms | Not supported. WinForms uses little reflection but depends heavily on built-in COM marshalling; almost no app runs without it, so the SDK disables trimming. Progress is tracked in dotnet/winforms issue 4649.
| WinUI 3 | Supported with work: see the next sections. Microsoft's single-instancing guidance warns that trimmed release builds have known crashes in some cases, so test any trimmed WinUI output thoroughly.
|===

Source: https://learn.microsoft.com/en-us/dotnet/core/deploying/trimming/incompatibilities[Known trimming incompatibilities]

== Native AOT

Native AOT compiles the whole app to native code at publish time: no JIT at run time, a faster start and a smaller
memory footprint, and no installed runtime needed. It is a self-contained mode that implies trimming and single-file
publishing. The cost is a long list of limitations: no dynamic loading (`Assembly.LoadFile`), no runtime code
generation (`System.Reflection.Emit`), no `pass:c[C++/CLI]`, no built-in COM on Windows, interpreted `System.Linq.Expressions`,
and many reflection-based libraries that need source generators. On Windows, building needs Visual Studio with the
"Desktop development with C++" workload (all default components). Windows supports x64, Arm64 and (since .NET 9) x86
as compilation targets.

[source,xml]
----
<PropertyGroup>
  <PublishAot>true</PublishAot>
</PropertyGroup>
----

`PublishAot` belongs in the project file, because it also turns on analysis during build and editing. The publish
command is the same RID publish: `dotnet publish -r win-x64 -c Release`. By default the debug information goes to a
separate `.pdb` file next to the native binary, which you need for debugging and crash dumps.

Source: https://learn.microsoft.com/en-us/dotnet/core/deploying/native-aot/[Native AOT deployment overview]

=== The Support Matrix per Desktop Stack

[cols="2,1,1,2",options="header"]
|===
| Capability | WPF | Windows Forms | WinUI 3 (Windows App SDK)
| Framework-dependent (FDD) | Yes | Yes | Yes (default; runtime is the Windows App SDK framework)
| Self-contained (SCD) | Yes | Yes | Yes (set `WindowsAppSDKSelfContained`, plus .NET self-contained)
| Single-file (`PublishSingleFile`) | Yes | Yes | Only for an _unpackaged, self-contained_ app (Windows App SDK 1.5 and later); not for packaged or framework-dependent apps
| ReadyToRun | Yes | Yes | Follows .NET rules; test the output
| `PublishTrimmed` | No (NETSDK1168) | No | Possible with extra work; known crash reports
| Native AOT (`PublishAot`) | No | No | Yes, since Windows App SDK 1.6 (with CsWinRT 2.1.1 or later in that release)
|===

For WinUI 3 the AOT announcement of Windows App SDK 1.6 says the `PublishAot` property is now supported, that AOT builds
on trimming support, that the app needs a package reference to `Microsoft.Windows.CsWinRT` 2.1.1 or later in that
release (until a .NET SDK servicing update made it unnecessary), and that the developer is responsible for rooting
types that are reached only through reflection, such as the targets of reflection-based `+{Binding}+`. Classes that
must be analyzed by the C#/WinRT source generator have to be declared `partial`. `x:Bind` is therefore the AOT-friendly
choice for a WinUI view, as the data-binding pages of this section explain.

Source: https://learn.microsoft.com/en-us/windows/apps/windows-app-sdk/release-notes/windows-app-sdk-1-6[Windows App SDK 1.6 release notes]

== Windows App SDK Deployment: Framework-Dependent or Self-Contained

A WinUI 3 app has a second runtime besides .NET: the Windows App SDK. A Windows App SDK project is
framework-dependent by default, so the machine needs the Windows App SDK runtime packages (framework, main,
singleton and the dynamic dependency lifetime manager).

[cols="1,2,2",options="header"]
|===
| App kind | Framework-dependent (default) | Self-contained
| Packaged (MSIX) | The manifest declares a dependency on the Windows App SDK framework package; installing the app brings it in. For packaged apps not distributed through the Store you are responsible for distributing the framework package, and calling the Deployment API (`DeploymentManager.Initialize`) is recommended so critical servicing updates reach the app. | The Windows App SDK files are included as content inside the MSIX package.
| Packaged with external location or unpackaged | You install the runtime with the Windows App SDK installer (`WindowsAppRuntimeInstall.exe`, one per `x64`, `x86` and `Arm64`) or by deploying the MSIX packages, and the app must initialize it with the bootstrapper (set `WindowsPackageType` to `None` for the auto-initializer). A Visual C++ Redistributable is a requirement. | The Windows App SDK files are copied next to the executable in the output; xcopy them or include them in an installer.
|===

Self-contained Windows App SDK deployment is one property in an app project (not in a library):

[source,xml]
----
<!-- Bookshelf.Desktop.WinUI.csproj -- unpackaged, fully self-contained -->
<PropertyGroup>
  <OutputType>WinExe</OutputType>
  <TargetFramework>net10.0-windows10.0.19041.0</TargetFramework>
  <UseWinUI>true</UseWinUI>
  <WindowsPackageType>None</WindowsPackageType>
  <RuntimeIdentifier>win-x64</RuntimeIdentifier>
  <!-- The Windows App SDK files travel with the app. -->
  <WindowsAppSDKSelfContained>true</WindowsAppSDKSelfContained>
  <!-- .NET must be self-contained as well to be fully self-contained. -->
  <SelfContained>true</SelfContained>
</PropertyGroup>
----

Source: https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/self-contained-deploy/deploy-self-contained-apps[Windows App SDK deployment guide for self-contained apps]

Notes from the same guide: a self-contained app extracts the contents of the Windows App SDK framework package into
the build output; library projects should not be switched; a C++ app also needs the hybrid CRT; and the few APIs that
depend on extra MSIX packages (push notifications need the Singleton package) either need the package deployed with
the app, a run-time `IsSupported` check, or should be avoided. `WindowsAppSdkUndockedRegFreeWinRTInitialize`
defaults to `true` for an executable that is self-contained and unpackaged, because that combination needs
registration-free WinRT.

A framework-dependent unpackaged install is silent with `WindowsAppRuntimeInstall.exe --quiet`; `--force` replaces
the MSIX packages and shuts down running Windows App SDK processes. Common return codes are `0x0` (success),
`0x80073d06` (a package failed to install) and `0x80070005` (a system-wide install without elevation). Without
administrator rights the installer registers the packages for the current user only; elevated, it provisions them for
all users.

[source,powershell]
----
# Chain the Windows App SDK runtime installer before the first launch
.\WindowsAppRuntimeInstall-x64.exe --quiet
if ($LASTEXITCODE -ne 0) { Write-Error "Windows App SDK runtime failed: $LASTEXITCODE" }
----

Source: https://learn.microsoft.com/en-us/windows/apps/windows-app-sdk/deploy-unpackaged-apps[Deploy unpackaged apps that use the Windows App SDK]

=== WinUI single-file

WinUI 3 single-file publishing is a narrow case. The unpackaged-distribution guide says unpackaged, self-contained
WinUI 3 apps support `PublishSingleFile` (Windows App SDK 1.5 and later), that it is not supported for packaged apps
or framework-dependent apps, and that dependencies are extracted to a temporary directory at first launch, so it is
not a zero-extraction binary. Required properties:

[source,xml]
----
<PropertyGroup>
  <WindowsPackageType>None</WindowsPackageType>
  <WindowsAppSDKSelfContained>true</WindowsAppSDKSelfContained>
  <SelfContained>true</SelfContained>
  <EnableMsixTooling>true</EnableMsixTooling>
  <IncludeAllContentForSelfExtract>true</IncludeAllContentForSelfExtract>
  <PublishSingleFile>true</PublishSingleFile>
</PropertyGroup>
----

The build validates this configuration: it fails if `EnableMsixTooling`, `WindowsPackageType` set to `None`, or
`IncludeAllContentForSelfExtract` is missing, and warns if `WindowsAppSDKSelfContained` or `SelfContained` is absent.
If you opt out of the auto-initializer, set the `MICROSOFT_WINDOWSAPPRUNTIME_BASE_DIRECTORY` environment variable to
`AppContext.BaseDirectory` before program entry. If extraction is unacceptable, the guide suggests MSIX packaging, a
traditional installer such as WiX or Inno Setup, or WPF or Windows Forms instead.

Source: https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/unpackage-winui-app#single-file-exe[Distribute an unpackaged WinUI 3 app: Single-file EXE]

Another Microsoft page on self-contained deployment states that `dotnet publish` bundles managed assemblies but
cannot produce a single-file EXE for WinUI 3 apps because the native runtime dependencies must remain separate files.
The two statements describe the same limit from two angles: do not expect a clean single file with no files beside
it; expect a self-extracting bundle in the unpackaged-and-self-contained case, and no bundle at all in the others.

== Choosing a Mode for Bookshelf Desktop

[cols="2,3,3",options="header"]
|===
| Scenario | Recommended publish | Why
| Internal tool on managed PCs that already deploy the Desktop Runtime | Framework-dependent, `win-x64`, ReadyToRun | Smallest download; patches come from the runtime.
| Public download from a website | Self-contained, `win-x64` and `win-arm64`, ReadyToRun, optionally single-file | No prerequisite for the user; one file per architecture is easy to explain.
| Portable zip for USB sticks or locked-down PCs | Self-contained single-file with native libraries embedded | One file; remember the extraction directory.
| WinUI 3 version, Store or MSIX | Packaged, framework-dependent or self-contained Windows App SDK | Package identity, update channels; the other pages cover signing.
| WinUI 3 version, direct download | Unpackaged, `WindowsAppSDKSelfContained` plus .NET self-contained | No two-runtime prerequisite.
| Smallest start-up for a WinUI 3 utility | Native AOT after fixing trim and reflection warnings | Only stack that supports it among the three.
|===

A repeatable script keeps the publish folders for each architecture consistent:

[source,powershell]
----
param([string]$Version = '1.0.0')

$project = 'src/Bookshelf.Desktop'
foreach ($rid in 'win-x64', 'win-x86', 'win-arm64') {
    $out = "artifacts/$rid"
    dotnet publish $project -c Release -r $rid --self-contained true `
        -p:PublishReadyToRun=true -p:Version=$Version -o $out
    if ($LASTEXITCODE -ne 0) { throw "Publish failed for $rid" }
    Compress-Archive -Path "$out/*" -DestinationPath "artifacts/Bookshelf-$Version-$rid.zip" -Force
}
----

Source: https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-publish[dotnet publish]

== What Changed Across Versions

[cols="1,3",options="header"]
|===
| Version | Change that matters when publishing
| .NET Framework | No publish step: build output plus ClickOnce or an MSI. The runtime was part of Windows. See the page on migrating from .NET Framework.
| .NET Core 3.0 / 3.1 | WPF and Windows Forms on .NET; framework-dependent executables, single-file bundles (extracting).
| .NET 5 / 6 | Trimming fully supported from .NET 6 (experimental in .NET Core 3.1 and .NET 5); composite ReadyToRun added in .NET 6.
| .NET 7 | Native AOT introduced.
| .NET 8 | `dotnet publish` defaults to `Release` for net8.0 and later targets; portable RIDs only; Native AOT for Windows x64 and Arm64; `IsAotCompatible` for libraries (enables the trim, single-file and AOT analyzers).
| .NET 9 | `AppHostDotNetSearch`; Native AOT on Windows x86; CET shadow stack on by default.
| .NET 10 | LTS; file-based apps can be published with `dotnet publish app.cs`.
| Windows App SDK 1.5 / 1.6 | Single-file for unpackaged self-contained (1.5); `PublishAot` supported (1.6).
| Windows App SDK 2.0 | SemVer versioning; NuGet version equals the SDK version.
|===

== Pitfalls

* *Publishing from a solution with `-r` and `-o`*: output of all projects lands in one folder or the RID assets are
  missing. Publish the project, or set `PublishDir` per project.
* *`RuntimeIdentifier` in a `.pubxml`* works in Visual Studio but is ignored by `dotnet publish`; pass `-r` in CI.
* *`PublishTrimmed` on a WPF or WinForms project*: the SDK stops the build (WPF reports NETSDK1168); do not look for a
  workaround, shrink the app with compression, `SatelliteResourceLanguages` and R2R choices instead.
* *Forgetting the architecture of the runtime*: an x86 app needs the x86 Desktop Runtime even on 64-bit Windows.
* *Installing the wrong runtime*: ".NET Runtime" alone does not run a WPF or Windows Forms app.
* *Single-file and file paths*: `Assembly.Location` is empty; read settings from the user's profile, not from the
  executable folder (see the local-data page of this section).
* *Extraction directory*: self-extracting apps write to `%TEMP%\.net`; make sure a service or elevated process does
  not share a writable directory with other users.
* *Mixing `--no-build` with a different mode* than the build used.
* *Self-contained apps do not get runtime security fixes*: schedule a rebuild when .NET servicing releases ship.
* *WinUI 3 single-file without `WindowsPackageType` set to `None`*: the build reports errors; packaged and
  framework-dependent apps cannot use `PublishSingleFile`.
* *Enabling `PublishAot` on WPF or Windows Forms* is not supported. Evaluate WinUI 3 or a different workload if Native AOT is a requirement.
* *Conflicting statements about WinUI single-file*: two Microsoft pages word the limit differently, so test the
  published output on a clean virtual machine before promising a single file.

== Summary

Choose the publish mode by the target machine: framework-dependent when a managed fleet carries the .NET Desktop
Runtime, self-contained when it must run anywhere. Always publish for an explicit RID (`win-x64`, `win-x86` or
`win-arm64`) and keep one profile per shipped flavor, remembering the CLI ignores the RID and configuration inside a
`.pubxml`. Use ReadyToRun to improve start-up on all desktop stacks, single-file with embedded native libraries when
one executable is worth a self-extracting start, and keep trimming and Native AOT to WinUI 3, where `PublishAot` has
worked since Windows App SDK 1.6; WPF and Windows Forms are blocked by the SDK. For WinUI 3, remember there are two
runtimes to ship (.NET and the Windows App SDK), and that single-file means unpackaged and self-contained.
