Most desktop line-of-business applications eventually have to produce a document: a report the user reads on screen,
a letter the user edits, a sheet that goes to a printer or to a file. WPF treats this as a first-class concern. It has
two document models (flow and fixed), a rich text editing control, one printing API built on the XPS print path, and a
text engine that exposes OpenType typography and several rendering options. This page covers all of them, using the
*Bookshelf Desktop* scenario: a printable book report, an editable notes field, an A4 label sheet and an XPS export.

== Two Document Models

WPF divides documents into two categories according to what the document is for.

[cols="2,3,3",options="header"]
|===
| | Flow document | Fixed document

| Purpose | Reading and editing; content reflows to the available space | Exact page layout; what you see is what you print
| Root element | `FlowDocument` | `FixedDocument` (a sequence of `PageContent`, each holding a `FixedPage`)
| Layout | Columns, hyphenation and pagination computed at run time from window size, font size and viewer | Absolute positions on a page of fixed size, identical on every device
| Viewers | `FlowDocumentReader`, `FlowDocumentPageViewer`, `FlowDocumentScrollViewer`; editable in `RichTextBox` | `DocumentViewer`, read-only
| Persisted as | XAML, RTF (through `TextRange`) | XPS (`XpsDocument`), or XAML pages
| Typical use | Help, articles, reports, notes, e-mail bodies | Forms, labels, invoices, anything with a precise template
|===

Both models share the same text elements and typography, both can be printed through the same `DocumentPaginator`
abstraction, and both can be written to an XPS file. The choice is not about quality; it is about whether the layout
belongs to the document (fixed) or to the reader (flow).

== Flow Documents

A `FlowDocument` is a tree of *blocks* that contain *inlines*. The tree is content, not UI: block and inline elements
derive from `TextElement`, which is lighter than a `UIElement`, and a `FlowDocument` is not displayed until a viewer
or a `RichTextBox` hosts it.

=== Elements

[cols="2,3,4",options="header"]
|===
| Element | Kind | Purpose

| `Paragraph` | Block | A run of inlines laid out as one paragraph; the workhorse of flow content
| `Section` | Block | Groups other blocks; applies no formatting of its own, but property values set on it apply to its children
| `List` / `ListItem` | Block | Bulleted or numbered lists
| `Table` | Block | Rows and cells of blocks, in `TableRowGroup`, `TableRow` and `TableCell`
| `BlockUIContainer` | Block | Hosts one `UIElement` (for example a `Button` or a chart) as a block
| `Run` | Inline | A span of plain text; the cheapest way to place text in a `Paragraph`
| `Span`, `Bold`, `Italic`, `Underline` | Inline | Formatting containers for other inlines
| `Hyperlink` | Inline | A link, navigated with `NavigateUri`
| `LineBreak` | Inline | A forced break
| `InlineUIContainer` | Inline | Hosts one `UIElement` inline with the text
| `Figure` | Inline | A positioned piece of content that can be anchored relative to the page, column or content
| `Floater` | Inline | Content that floats beside the text; sized at one column by default
|===

=== The FlowDocument Properties That Matter

[cols="3,5",options="header"]
|===
| Property | Effect

| `ColumnWidth` | Preferred column width; the document creates as many columns as fit the viewer
| `IsOptimalParagraphEnabled` | Distributes white space as evenly as possible; disabled by default, and costs performance
| `IsHyphenationEnabled` | Automatic hyphenation; disabled by default, and starts COM interoperability when enabled
| `PagePadding` | The padding between the page edge and the content
| `PageWidth`, `PageHeight` | Page size used when the document is paginated for print or for a page viewer
| `TextAlignment`, `FontFamily`, `FontSize` | Inherited by every block and inline in the document
|===

Because formatting properties are inherited, a document sets its font once on the `FlowDocument` and overrides it only
where needed. This is the same property value inheritance described on the dependency properties page of this section.

=== The Viewers

Three controls display a flow document. They differ in how much they let the user change.

[cols="3,5,3",options="header"]
|===
| Control | Behavior | Cost

| `FlowDocumentReader` | The user switches between a one-page view, a two-pages-at-a-time (book) view and continuous scrolling; has search, zoom and page navigation | The most resource intensive
| `FlowDocumentPageViewer` | Fixed in page-at-a-time mode | Lighter
| `FlowDocumentScrollViewer` | Fixed in continuous scrolling mode; a vertical scroll bar is always shown, a horizontal one only when needed; no toolbar unless `IsToolBarVisible` is true | Lightest
|===

The reader's view modes are the `FlowDocumentReaderViewingMode` enumeration. A control that exposes the choice to the
user costs more than one that fixes it, so use `FlowDocumentScrollViewer` for a read-only help page and
`FlowDocumentReader` only where switching modes is a feature.

=== Example: A Book Report Built From Data

The Bookshelf Desktop report lists the books with a title, an author and a running count. The builder below turns an
`IReadOnlyList<Book>` into a `FlowDocument`. It uses `Run` for text, as the performance guidance recommends, and sets
fonts once at the document level.

[source,csharp]
----
using System.Windows;
using System.Windows.Documents;
using System.Windows.Media;
using Bookshelf.Core;

namespace Bookshelf.Desktop.Reporting;

public static class BookReportBuilder
{
    public static FlowDocument Build(IReadOnlyList<Book> books, DateOnly generatedOn)
    {
        var document = new FlowDocument
        {
            FontFamily = new FontFamily("Palatino Linotype"),
            FontSize = 14,
            ColumnWidth = 400,
            PagePadding = new Thickness(48),
            IsOptimalParagraphEnabled = false,
            IsHyphenationEnabled = false,
        };

        document.Blocks.Add(new Paragraph(new Run("Bookshelf report"))
        {
            FontSize = 28,
            FontWeight = FontWeights.Bold,
            Margin = new Thickness(0, 0, 0, 4),
        });
        document.Blocks.Add(new Paragraph(new Run($"{books.Count} books, generated {generatedOn:D}"))
        {
            Foreground = Brushes.DimGray,
        });

        var table = new Table { CellSpacing = 0, BorderBrush = Brushes.Gray, BorderThickness = new Thickness(0, 0, 0, 1) };
        table.Columns.Add(new TableColumn { Width = new GridLength(40) });
        table.Columns.Add(new TableColumn { Width = new GridLength(3, GridUnitType.Star) });
        table.Columns.Add(new TableColumn { Width = new GridLength(2, GridUnitType.Star) });

        var rows = new TableRowGroup();
        rows.Rows.Add(HeaderRow("#", "Title", "Author"));
        var index = 1;
        foreach (var book in books.OrderBy(b => b.Author).ThenBy(b => b.Title))
        {
            rows.Rows.Add(DataRow(index++, book));
        }
        table.RowGroups.Add(rows);
        document.Blocks.Add(table);

        return document;
    }

    private static TableRow HeaderRow(params string[] headings)
    {
        var row = new TableRow { FontWeight = FontWeights.Bold, Background = Brushes.LightGray };
        foreach (var heading in headings)
        {
            row.Cells.Add(new TableCell(new Paragraph(new Run(heading))));
        }
        return row;
    }

    private static TableRow DataRow(int index, Book book)
    {
        var row = new TableRow();
        row.Cells.Add(new TableCell(new Paragraph(new Run(index.ToString()))));
        row.Cells.Add(new TableCell(new Paragraph(new Run(book.Title))));
        row.Cells.Add(new TableCell(new Paragraph(new Run(book.Author))));
        return row;
    }
}
----

Source: https://learn.microsoft.com/en-us/dotnet/desktop/wpf/advanced/flow-document-overview[Flow Document Overview]

Notes on the example. `FlowDocument` is a `DispatcherObject`, so build and use it on the UI thread. `PagePadding` and
the `GridLength` column widths are ordinary dependency properties. The builder is a plain static function of its input
and does not know about the view, which keeps it testable and reusable for both display and printing.

=== Showing the Document in a Viewer

`FlowDocumentReader.Document` and `FlowDocumentScrollViewer.Document` are dependency properties, so a view model can
expose the built document and the view binds to it. A view model that exposes a `FlowDocument` does reference a WPF
type, which breaks strict separation; many teams accept that for report previews, others expose the data and let a
view-side converter or behavior build the document. The example takes the first route for brevity.

[source,csharp]
----
using System.Windows.Documents;
using Bookshelf.Core;
using Bookshelf.Desktop.Reporting;
using CommunityToolkit.Mvvm.ComponentModel;
using CommunityToolkit.Mvvm.Input;

namespace Bookshelf.Desktop;

public partial class BookReportViewModel(IBookRepository repository, IPrintService printService) : ObservableObject
{
    [ObservableProperty]
    public partial FlowDocument? Report { get; set; }

    [RelayCommand]
    private async Task LoadAsync(CancellationToken cancellationToken)
    {
        var books = await repository.GetAllAsync(cancellationToken);
        Report = BookReportBuilder.Build(books, DateOnly.FromDateTime(DateTime.Today));
    }

    [RelayCommand(CanExecute = nameof(CanPrint))]
    private void Print()
    {
        if (Report is not null)
        {
            printService.PrintFlowDocument(Report, "Bookshelf report");
        }
    }

    private bool CanPrint() => Report is not null;

    partial void OnReportChanged(FlowDocument? value) => PrintCommand.NotifyCanExecuteChanged();
}
----

Source: https://learn.microsoft.com/en-us/dotnet/communitytoolkit/mvvm/generators/relaycommand[RelayCommand attribute]

[source,xml]
----
<Window x:Class="Bookshelf.Desktop.BookReportWindow"
        xmlns="http://schemas.microsoft.com/winfx/2006/xaml/presentation"
        xmlns:x="http://schemas.microsoft.com/winfx/2006/xaml"
        Title="Bookshelf report" Width="900" Height="640"
        Loaded="OnLoaded">
    <DockPanel>
        <ToolBar DockPanel.Dock="Top">
            <Button Content="Print..." Command="{Binding PrintCommand}" />
        </ToolBar>

== RichTextBox: Editing Flow Content

`RichTextBox` hosts a `FlowDocument` and lets the user edit it. Its content property is `Document`. It supports
real-time spell checking, a default context menu and the formatting commands of the `EditingCommands` class, such as
`ToggleBold` (Ctrl+B). A `TextBox`, by comparison, supports spell checking and the context menu but not formatting
commands or flow content, and it needs fewer resources, so it remains the right choice for plain form fields.

[cols="3,3,3",options="header"]
|===
| Feature | TextBox | RichTextBox

| Real-time spell checking | Yes | Yes
| Context menu | Yes | Yes
| Formatting commands such as `ToggleBold` | No | Yes
| Flow content (images, paragraphs, tables) | No | Yes
|===

Flow content inside a `RichTextBox` does not behave exactly like flow content in a viewer. There are no columns and so
no automatic resizing, and the viewer features (search, view modes, page navigation, zoom) are not available.

=== Saving and Loading Rich Content

The editor never exposes its text as a bindable `string`. To persist the notes, wrap the document in a `TextRange` and
save it to a stream in one of the `DataFormats` the range supports. The official sample saves and loads the XAML
package format (`DataFormats.XamlPackage`), which keeps images. The service below does the same through a small
abstraction, and uses `DataFormats.Rtf` for the interchange case.

[source,csharp]
----
using System.IO;
using System.Windows;
using System.Windows.Controls;
using System.Windows.Documents;

namespace Bookshelf.Desktop.Reporting;

public static class RichTextPersistence
{
    public static async Task SaveAsync(RichTextBox editor, string path, string dataFormat)
    {
        var range = new TextRange(editor.Document.ContentStart, editor.Document.ContentEnd);
        await using var stream = new FileStream(path, FileMode.Create, FileAccess.Write);
        range.Save(stream, dataFormat);
        await stream.FlushAsync();
    }

    public static async Task LoadAsync(RichTextBox editor, string path, string dataFormat)
    {
        if (!File.Exists(path))
        {
            return;
        }

        var range = new TextRange(editor.Document.ContentStart, editor.Document.ContentEnd);
        await using var stream = new FileStream(path, FileMode.Open, FileAccess.Read);
        range.Load(stream, dataFormat);
    }
}

// Usage in the notes window:
//   await RichTextPersistence.SaveAsync(NotesEditor, path, DataFormats.XamlPackage);
//   await RichTextPersistence.LoadAsync(NotesEditor, path, DataFormats.Rtf);
----

Source: https://learn.microsoft.com/en-us/dotnet/desktop/wpf/controls/richtextbox[RichTextBox Overview]

`TextRange.Save` and `TextRange.Load` are synchronous APIs; the `await` above only covers the stream flush. The
example is a pattern based on the official one: the official sample uses `FileStream` without `using` and
`DataFormats.XamlPackage` only. That `DataFormats.Rtf` is accepted by `TextRange.Save` is documented on the API page
of `TextRange`, not on the overview page cited here.

=== Detecting Changes

Use `TextChanged` to know that the content changed, not `KeyDown`, because content changes without key presses (paste,
undo, a toolbar command, a drag and drop). Unlike a `TextBox`, `RichTextBox.Document` is not a dependency property, so
it cannot be the target of a binding; load and save it in code-behind or in a behavior, as shown above.

== Fixed Documents and XPS

A `FixedDocument` is an ordered sequence of `PageContent` elements. `PageContent` is the only allowed child, and each
one refers to the content of one page, in page order. `FixedDocument` is marked as having `Pages` as its content
property, so `PageContent` elements nest directly in markup. Each page's content is a `FixedPage`, a canvas-like
surface of fixed size on which elements are positioned absolutely with the `FixedPage.Left` and `FixedPage.Top`
attached properties. A `FixedDocument` is read-only for the user: selection, keyboard navigation and search work,
editing does not.

[cols="3,5",options="header"]
|===
| Type | Role

| `FixedDocument` | One document: a sequence of pages with fixed layout; exposes `Pages` and `DocumentPaginator`
| `PageContent` | One entry in the page sequence; holds a `FixedPage` as its child, or refers to one by `Source`
| `FixedPage` | The page itself, with a fixed `Width` and `Height`
| `FixedDocumentSequence` | Several fixed documents treated as one (this is what an XPS package gives you)
| `DocumentViewer` | The control that displays fixed content, with printing, copy, zoom and text search built in
|===

=== XPS: The Package Behind Fixed Documents

XPS, the XML Paper Specification, is simultaneously an electronic document format, a print spool format and a page
description language. An `XpsDocument` is a ZIP package (built on the `System.IO.Packaging` APIs and the Open
Packaging Conventions) that holds one or more fixed documents together with all the resources needed to render them:
XML pages plus binary parts such as images and fonts. Relationships between parts say which content depends on which
resource. An XPS document can be opened in a viewer, displayed in a `DocumentViewer`, sent to the print spool or sent
directly to an XPS-capable printer. The `Microsoft XPS Document Writer` printer in the print dialog creates XPS
(and OpenXPS) files.

Packages can carry digital signatures (`PackageDigitalSignature`) to identify the originator of a part and to detect
modification; a signature does not prevent a part from being changed, only makes validation fail if it is.

=== Example: Export the Report to an XPS File

The export writes a flow document through its paginator into an XPS package, then reopens the package in a
`DocumentViewer`.

[source,csharp]
----
using System.IO;
using System.IO.Packaging;
using System.Windows;
using System.Windows.Controls;
using System.Windows.Documents;
using System.Windows.Xps;
using System.Windows.Xps.Packaging;

namespace Bookshelf.Desktop.Reporting;

public static class XpsExport
{
    public static void Save(FlowDocument document, string xpsPath, Size pageSize)
    {
        // Paginate for a fixed page size. Use a clone in a real app (see Pitfalls).
        var paginator = ((IDocumentPaginatorSource)document).DocumentPaginator;
        paginator.PageSize = pageSize;

        using var package = Package.Open(xpsPath, FileMode.Create, FileAccess.ReadWrite);
        using var xps = new XpsDocument(package, CompressionOption.Maximum);
        XpsDocument.CreateXpsDocumentWriter(xps).Write(paginator);
    }

    public static void ShowInViewer(DocumentViewer viewer, string xpsPath)
    {
        var xps = new XpsDocument(xpsPath, FileAccess.Read);
        viewer.Document = xps.GetFixedDocumentSequence();
    }
}
----

Source: https://learn.microsoft.com/en-us/dotnet/desktop/wpf/documents/printing-overview[Printing documents overview]

The official pages show `new XpsDocument(path, FileAccess.Read)` and `GetFixedDocumentSequence()` (reused above in
`ShowInViewer`) and describe `XpsDocumentWriter.Write` overloads. They do not show the `Package.Open` plus
`CompressionOption` constructor or `XpsDocument.CreateXpsDocumentWriter(XpsDocument)` used in `Save`; those signatures
are from the API reference and from knowledge, and should be checked when you compile. The XPS Viewer app is an
optional Windows feature on current Windows versions, so do not assume that users can double-click an `.xps` file;
embed a `DocumentViewer` instead.

== Printing

Printing in WPF is built on the XPS print path. Instead of translating a document into a printer language such as PCL
or PostScript, or into a GDI spool format such as EMF, the application hands XPS to the print system and, when the
printer has an XPSDrv driver, the XPS goes to the driver unchanged. If the target queue does not have an XPSDrv driver,
the `Write` and `WriteAsync` methods of `XpsDocumentWriter` convert the content from XPS to GDI automatically, so the
same code prints to every printer.

[cols="3,5",options="header"]
|===
| Benefit of the XPS print path | Explanation

| WYSIWYG | The document the user sees is the document that is spooled
| Color and transparency | Native support for advanced color profiles, CMYK, named colors, transparency and gradients
| Smaller spool files | Font subsetting, shared resources, ZIP compression and native graphics primitives instead of rasterization
| Performance | XPS features are only available to applications that target the XPS print path
|===

=== The API Levels

[cols="3,5",options="header"]
|===
| Level | Types and use

| Basic | `System.Windows.Controls.PrintDialog`: one entry point for UI, configuration and job submission. Prints a `Visual` with `PrintVisual` or a paginated document with `PrintDocument`
| Advanced | `System.Printing` and `System.Windows.Xps`: `PrintServer`, `LocalPrintServer`, `PrintQueue`, `PrintTicket`, `PrintCapabilities` and `XpsDocumentWriter`; synchronous or asynchronous printing, batch printing, no UI at all
|===

The WPF `PrintDialog` should not be confused with `System.Windows.Forms.PrintDialog`; they are different types for
different frameworks.

=== PrintDialog

`PrintDialog` shows the standard Windows print dialog. `ShowDialog()` returns a nullable Boolean that is true when the
user presses Print. The dialog lets the user pick a printer (including the XPS document writer) and, when
`UserPageRangeEnabled` is true, a range of pages; the choice is available through `PageRangeSelection` and `PageRange`.

[cols="3,5",options="header"]
|===
| Member | Use

| `ShowDialog()` | Shows the dialog; true means the user chose to print
| `PrintVisual(Visual, string)` | Prints a single visual (a control or a `DrawingVisual`) with the description shown in the spooler
| `PrintDocument(DocumentPaginator, string)` | Prints a paginated document
| `UserPageRangeEnabled` | Lets the user enter a page range
| `PageRangeSelection` | Whether the user selected all pages or a user-defined range
| `PageRange` | The `PageFrom` and `PageTo` values (one-based)
|===

Printing without showing the dialog is possible, but the official guidance recommends the `PrintQueue.AddJob` method or
the `XpsDocumentWriter.Write` and `WriteAsync` methods for performance.

=== Example: A Print Service

The service wraps `PrintDialog` so view models depend on an interface, not on WPF dialogs. It prints a flow document
by giving the paginator the printable size reported by the dialog, and prints a visual with `PrintVisual`.

[source,csharp]
----
using System.Windows;
using System.Windows.Controls;
using System.Windows.Documents;
using System.Windows.Media;

namespace Bookshelf.Desktop;

public interface IPrintService
{
    /// <summary>Shows the print dialog and prints the document. Returns false when the user cancels.</summary>
    bool PrintFlowDocument(FlowDocument document, string description);

    /// <summary>Shows the print dialog and prints a single visual. Returns false when the user cancels.</summary>
    bool PrintVisual(Visual visual, string description);
}

public sealed class WpfPrintService : IPrintService
{
    public bool PrintFlowDocument(FlowDocument document, string description)
    {
        var dialog = new PrintDialog { UserPageRangeEnabled = true };
        if (dialog.ShowDialog() != true)
        {
            return false;
        }

        var paginator = ((IDocumentPaginatorSource)document).DocumentPaginator;
        paginator.PageSize = new Size(dialog.PrintableAreaWidth, dialog.PrintableAreaHeight);

        dialog.PrintDocument(paginator, description);
        return true;
    }

    public bool PrintVisual(Visual visual, string description)
    {
        var dialog = new PrintDialog();
        if (dialog.ShowDialog() != true)
        {
            return false;
        }

        dialog.PrintVisual(visual, description);
        return true;
    }
}
----

Source: https://learn.microsoft.com/en-us/dotnet/desktop/wpf/documents/how-to-display-print-dialog[How to display a print dialog]

The official how-to shows `ShowDialog`, `PrintDocument`, `UserPageRangeEnabled`, `PageRangeSelection` and
`PageRange`. `PrintableAreaWidth` and `PrintableAreaHeight` and the use of a `FlowDocument` paginator with `PageSize`
come from the API reference and from common practice, not from a Learn sample. Register the service as a singleton in
the Generic Host (`services.AddSingleton<IPrintService, WpfPrintService>()`), and it can be replaced by a fake in
view-model tests.

=== Printing a Page Range

The paginator returned by a `FlowDocument` or an XPS document prints all pages. To honor a user page range, the
official how-to extends the abstract `DocumentPaginator` class with a wrapper that maps page numbers to the chosen
range (`PageCount`, `GetPage`, `PageSize`, `Source`, `IsPageCountValid`), and passes it to `PrintDocument` when
`PageRangeSelection` is `PageRangeSelection.UserPages`. The wrapper in the sample also contains a reflection workaround
for the "FixedPage cannot contain another FixedPage" error that occurs when printing fixed pages to XPS. Reflection on
private members is fragile; test the workaround against the .NET version you ship.

Source: https://learn.microsoft.com/en-us/dotnet/desktop/wpf/documents/how-to-display-print-dialog[How to display a print dialog]

=== Advanced Printing: PrintQueue, PrintTicket and XpsDocumentWriter

For batch printing, silent printing or control of device features, use the `System.Printing` classes directly. A
`PrintTicket` tells the printer how to process a job; `PrintCapabilities` tells you what the printer supports, so a
ticket can use only supported features. The queue's `DefaultPrintTicket` is the starting point.

[source,csharp]
----
using System.Printing;

namespace Bookshelf.Desktop;

public static class PrintTickets
{
    /// <summary>Creates a ticket that prefers collated, duplex output when the printer supports it.</summary>
    public static PrintTicket ForBookReport(PrintQueue printQueue)
    {
        PrintCapabilities capabilities = printQueue.GetPrintCapabilities();
        PrintTicket ticket = printQueue.DefaultPrintTicket;

        if (capabilities.CollationCapability.Contains(Collation.Collated))
        {
            ticket.Collation = Collation.Collated;
        }

        if (capabilities.DuplexingCapability.Contains(Duplexing.TwoSidedLongEdge))
        {
            ticket.Duplexing = Duplexing.TwoSidedLongEdge;
        }

        return ticket;
    }

    public static PrintQueueCollection LocalQueues()
    {
        var server = new LocalPrintServer();
        return server.GetPrintQueues();
    }
}
----

Source: https://learn.microsoft.com/en-us/dotnet/desktop/wpf/documents/printing-overview[Printing documents overview]

Adding an XPS document to a queue together with a ticket is done with `XpsDocumentWriter`. The writer is created for a
queue with `PrintQueue.CreateXpsDocumentWriter`, and `Write` or `WriteAsync` accepts a `FixedDocumentSequence` and a
`PrintTicket`.

[source,csharp]
----
using System.IO;
using System.Printing;
using System.Windows.Documents;
using System.Windows.Xps;
using System.Windows.Xps.Packaging;

namespace Bookshelf.Desktop;

public static class XpsPrinting
{
    public static void Print(string xpsFilePath, PrintQueue printQueue, PrintTicket printTicket)
    {
        XpsDocumentWriter writer = PrintQueue.CreateXpsDocumentWriter(printQueue);

        using var xpsDocument = new XpsDocument(xpsFilePath, FileAccess.Read);
        FixedDocumentSequence sequence = xpsDocument.GetFixedDocumentSequence();

        // Synchronous. Use writer.WriteAsync(sequence, printTicket) to avoid blocking the UI thread.
        writer.Write(sequence, printTicket);
    }
}
----

Source: https://learn.microsoft.com/en-us/dotnet/desktop/wpf/documents/printing-overview[Printing documents overview]

The official sample does not dispose the `XpsDocument`; the example above adds `using`, which is sound for the
synchronous `Write`. With `WriteAsync`, keep the document open until the write completes.

=== Printing a Visual

`PrintVisual` is the simplest way to print something that is already on screen, or something drawn in code. The
Bookshelf spine label below is a `DrawingVisual` that is rendered with `FormattedText`; the same visual can be
printed without being added to the visual tree.

[source,csharp]
----
using System.Globalization;
using System.Windows;
using System.Windows.Media;

namespace Bookshelf.Desktop.Reporting;

public static class SpineLabel
{
    public static DrawingVisual Create(string title, string author, double pixelsPerDip)
    {
        var typeface = new Typeface("Palatino Linotype");
        var visual = new DrawingVisual();

        using (DrawingContext context = visual.RenderOpen())
        {
            var heading = new FormattedText(
                title,
                CultureInfo.CurrentUICulture,
                FlowDirection.LeftToRight,
                typeface,
                emSize: 20,
                foreground: Brushes.Black,
                pixelsPerDip: pixelsPerDip)
            {
                MaxTextWidth = 220,
                MaxTextHeight = 60,
            };

            var byline = new FormattedText(
                author,
                CultureInfo.CurrentUICulture,
                FlowDirection.LeftToRight,
                typeface,
                emSize: 13,
                foreground: Brushes.DimGray,
                pixelsPerDip: pixelsPerDip);

            context.DrawRectangle(null, new Pen(Brushes.Black, 1), new Rect(0, 0, 240, 120));
            context.DrawText(heading, new Point(10, 8));
            context.DrawText(byline, new Point(10, 80));
        }

        return visual;
    }
}

//   var dpi = VisualTreeHelper.GetDpi(this).PixelsPerDip;

== Typography and OpenType

Text in WPF is rendered with ClearType and can be hardware accelerated. On top of that, the `Typography` object
exposes OpenType features through attached properties that work on any element that has text properties: `Run`,
`Paragraph`, `TextBlock`, and the controls. Most OpenType fonts expose only some of the features, and a property has no
visible effect if the font does not implement it.

[cols="3,3,4",options="header"]
|===
| Property | Values (default) | Effect

| `Typography.Capitals` | `Normal` (default), `SmallCaps`, `AllSmallCaps`, `PetiteCaps`, `AllPetiteCaps`, `Titling`, `Unicase` | Capital forms; with `SmallCaps` a leading capital is ignored
| `Typography.CapitalSpacing` | `False` | More space between letters of all-capital text
| `Typography.StandardLigatures` | `True` | fi, fl, ff joined into one glyph; set `False` to disable
| `Typography.DiscretionaryLigatures` | `False` | Ornamental ligatures
| `Typography.Kerning` | `True` | Pair kerning
| `Typography.Fraction` | `Normal` (default), `Slashed`, `Stacked` | Fraction forms
| `Typography.NumeralStyle` | `Normal` (default), `OldStyle`, and others | Lining or old-style figures
| `Typography.NumeralAlignment` | `Normal` (default), `Proportional`, `Tabular` | Tabular figures have equal widths and align in columns
| `Typography.SlashedZero` | `False` | A zero with a slash, to tell it from the letter O
| `Typography.Variants` | `Normal` (default), `Superscript`, `Subscript`, `Inferior`, `Ordinal`, `Ruby` | Superscripts and subscripts from the font
| `Typography.StylisticAlternates` | `0` | Alternate glyph sets, selected by number
| `Typography.StylisticSet1` to `StylisticSet20` | `False` | Font-defined stylistic sets
| `Typography.StandardSwashes`, `ContextualSwashes` | `0` | Decorative swash glyphs
| `Typography.ContextualAlternates` | `True` | Context-dependent alternates
|===

The same properties are exposed on the object's `Typography` property in code, for example
`run.Typography.Capitals = FontCapitals.SmallCaps;`.

=== Beyond Controls: Glyphs, FormattedText and TextFormatter

Text rendering has three layers in WPF. The highest uses controls such as `TextBlock` and `FlowDocument`. The middle
layer is `FormattedText`, which draws multi-line text with per-character formatting through a `DrawingContext`, with
ellipsis support, and can be converted to `Geometry` for outlined or filled text effects. The lowest layer is
`Glyphs` and `GlyphRun`, designed for fixed-format document presentation and print scenarios, and the most efficient
way to render text. For a custom text editor, the `System.Windows.Media.TextFormatting` namespace (`TextFormatter`,
`TextSource`) lets you implement your own layout. Almost all applications stay on the top layer.

Source: https://learn.microsoft.com/en-us/dotnet/desktop/wpf/advanced/typography-in-wpf[Typography in WPF]

== Text Rendering

The `TextOptions` class defines three attached properties that change how text is displayed in an element.

[cols="3,3,5",options="header"]
|===
| Attached property | Values | Meaning

| `TextOptions.TextFormattingMode` | `Ideal` (0), `Display` (1) | `Ideal` lays text out with ideal font metrics; `Display` uses GDI-compatible metrics
| `TextOptions.TextRenderingMode` | `Auto` (0), `Aliased` (1), `Grayscale` (2), `ClearType` (3) | Anti-aliasing algorithm used to draw the text
| `TextOptions.TextHintingMode` | `Auto` (0), `Fixed` (1), `Animated` (2) | `Fixed` renders static text at the highest static quality; `Animated` favors smooth animation over text quality
|===

`Display` formatting and `Fixed` hinting produce the sharpest static text at small sizes on a standard-DPI display, at
the cost of the resolution independence that `Ideal` gives. For text that moves (a marquee, a scale animation), set
`TextHintingMode="Animated"` on the animated element. The `Auto` defaults are right for most applications.

[source,xml]
----
<StackPanel xmlns="http://schemas.microsoft.com/winfx/2006/xaml/presentation"
            xmlns:x="http://schemas.microsoft.com/winfx/2006/xaml">

    <!-- Crisp small text in a data-dense list on a standard-DPI display. -->
    <ListView TextOptions.TextFormattingMode="Display"
              TextOptions.TextHintingMode="Fixed" />

    <!-- Moving text: favor smooth animation over static quality. -->
    <TextBlock Text="Now reading..." TextOptions.TextHintingMode="Animated">
        <TextBlock.RenderTransform>
            <TranslateTransform x:Name="Slide" />
        </TextBlock.RenderTransform>
    </TextBlock>
</StackPanel>
----

Source: https://learn.microsoft.com/en-us/dotnet/api/system.windows.media.textoptions[TextOptions class]

The enum values come from the API reference. The recommendation to use `Display` with `Fixed` for small static text is
common practice, not a statement on Microsoft Learn.

=== Performance Guidance

[cols="3,5",options="header"]
|===
| Guidance | Reason

| Use `TextBlock` for short UI text, `Label` only when you need its content model, `FlowDocument` for rich re-flowable content | `FlowDocument` has a greater performance impact than `TextBlock` or `Label`
| Inside a `FlowDocument`, use `Run` rather than `TextBlock` | `Run` derives from `TextElement` and is cheaper than the `UIElement`-derived `TextBlock`
| Inside a `TextBlock`, set text properties on the `TextBlock` rather than on a `Run` | Learn's measurement for 1000 elements: creation 146 ms with a `Run`, 43 ms without
| Bind frequently updated strings to `TextBlock.Text`, not `Label.Content` | Learn's measurement: update time 835 ms for `Label.Content` and 242 ms for `TextBlock.Text`
| Group several `Hyperlink` elements in one `TextBlock` | Fewer objects
| Avoid `IsHyphenationEnabled` and `IsOptimalParagraphEnabled` unless needed | Hyphenation uses COM interoperability; optimal paragraph costs layout time
| Declare `Figure` elements near each other or near the top | A `Figure` that collides with laid-out content can reformat a page
|===

Source: https://learn.microsoft.com/en-us/dotnet/desktop/wpf/advanced/optimizing-performance-text[Optimizing Performance: Text]

The timings are those published on the page for its test scenario (1000 elements); treat them as relative, not as
numbers for your hardware.

== Fonts

=== System Fonts and Fallback

WPF text is Unicode, independent of the system locale. A `FontFamily` is described by separate weight, stretch and
style, not by Boolean bold and italic flags. When a character is missing from a font, WPF can use composite fonts
(a portable XML description of font linking and fallback), and an incorrect font reference makes the application fall
back to an available font instead of throwing.

=== Packaging a Font With the Application

Bookshelf Desktop can ship its own typeface for labels. Fonts can be added as `Resource` items, embedded in the

== WPF, WinUI 3 and WinForms

[cols="2,3,3,3",options="header"]
|===
| | WPF | WinUI 3 (Windows App SDK) | WinForms

| Rich text editing | `RichTextBox` over a `FlowDocument`; `TextRange` for save/load (XAML, XAML package, RTF) | `RichEditBox`; content is an `ITextDocument` loaded and saved with `LoadFromStream` and `SaveToStream` (RTF) | `RichTextBox` control (RTF string)
| Read-only rich text | `FlowDocumentScrollViewer`, `FlowDocumentReader` | `RichTextBlock` (the docs recommend it for read-only rich documents) | `RichTextBox` with `ReadOnly`
| Flow and fixed documents | `FlowDocument`, `FixedDocument` | Not available | Not available
| XPS | Native: `XpsDocument`, `DocumentViewer`, `XpsDocumentWriter` | Not part of the documented UI API | Not part of the framework
| Printing API | `PrintDialog`, `PrintQueue`, `PrintTicket`, `XpsDocumentWriter` | `PrintManager` with `Microsoft.UI.Xaml.Printing.PrintDocument`; handlers for `Paginate`, `GetPreviewPage` and `AddPages` | `PrintDocument` with a `PrintPage` event and GDI+ `Graphics`; `PrintDialog` and preview dialogs
| Print UI | Standard Windows print dialog (`ShowDialog`) | System print UI from `PrintManagerInterop.ShowPrintUIForWindowAsync(hWnd)`, with a print preview fed by the app | Standard print dialog
| Typography | `Typography` attached properties, `TextOptions` | Different text model; the WPF `Typography` and `TextOptions` classes do not exist | `Graphics.DrawString`; `TextRenderer` is not supported for printing
|===

Two consequences follow. Code that builds a `FlowDocument` for display and printing is WPF only; moving the same
report to WinUI 3 means drawing pages as `UIElement` trees in the `Paginate` handler. And a report library that must
serve all three stacks should keep the report as data and put the rendering in each stack's own project.

=== Printing in WinUI 3

The WinUI printing flow differs from the WPF dialog-driven one. The app registers for printing on the window (using
the window handle, so after the window exists), creates a `PrintDocument`, and handles three events: `Paginate`
(build the pages and report the count), `GetPreviewPage` (supply the page for the preview) and `AddPages` (supply the
final pages and call `AddPagesComplete`).

[source,csharp]
----
using Microsoft.UI.Xaml;
using Microsoft.UI.Xaml.Printing;
using Windows.Graphics.Printing;

namespace Bookshelf.WinUI;

public sealed partial class ReportPage : Microsoft.UI.Xaml.Controls.Page
{
    private PrintDocument? printDocument;
    private IPrintDocumentSource? printDocumentSource;
    private readonly List<UIElement> printPages = [];

    private void RegisterForPrinting()
    {
        var hWnd = WinRT.Interop.WindowNative.GetWindowHandle(App.MainWindow);
        PrintManager printManager = PrintManagerInterop.GetForWindow(hWnd);
        printManager.PrintTaskRequested += OnPrintTaskRequested;

        printDocument = new PrintDocument();
        printDocumentSource = printDocument.DocumentSource;
        printDocument.Paginate += OnPaginate;
        printDocument.GetPreviewPage += OnGetPreviewPage;
        printDocument.AddPages += OnAddPages;
    }

    private async void OnPrintClicked(object sender, RoutedEventArgs e)
    {
        var hWnd = WinRT.Interop.WindowNative.GetWindowHandle(App.MainWindow);
        await PrintManagerInterop.ShowPrintUIForWindowAsync(hWnd);
    }

    private void OnPrintTaskRequested(PrintManager sender, PrintTaskRequestedEventArgs args)
    {
        args.Request.CreatePrintTask("Bookshelf report", sourceArgs => sourceArgs.SetSource(printDocumentSource));
    }

    private void OnPaginate(object sender, PaginateEventArgs e)
    {
        printPages.Clear();
        var options = (PrintTaskOptions)e.PrintTaskOptions;
        PrintPageDescription page = options.GetPageDescription(0);

        // One page: a panel sized to the printer page. Real reports flow content over several pages here.
        var layout = new Microsoft.UI.Xaml.Controls.StackPanel { Width = page.PageSize.Width, Height = page.PageSize.Height };
        printPages.Add(layout);

        ((PrintDocument)sender).SetPreviewPageCount(printPages.Count, PreviewPageCountType.Intermediate);
    }

    private void OnGetPreviewPage(object sender, GetPreviewPageEventArgs e)
        => ((PrintDocument)sender).SetPreviewPage(e.PageNumber, printPages[e.PageNumber - 1]);

    private void OnAddPages(object sender, AddPagesEventArgs e)
    {
        var document = (PrintDocument)sender;
        foreach (UIElement page in printPages)
        {
            document.AddPage(page);
        }
        document.AddPagesComplete();
    }
}
----

Source: https://learn.microsoft.com/en-us/windows/apps/develop/devices-sensors/print-from-your-app[Print from your app]

The structure is that of the official page, shortened: the official sample also unregisters the handlers in
`OnNavigatedFrom` (otherwise an exception is thrown when the user leaves the page and returns), guards with
`PrintManager.IsSupported()` and reports `PrintTask.Completed`. Register from the `Loaded` event, not from
`OnNavigatedTo`, because the window handle can still be null there. Re-check the settings before reflowing in
`Paginate`, because it is called again whenever the user changes a print setting.

=== Printing in WinForms

WinForms prints through the `PrintDocument` component. `Print()` raises `PrintPage`, which draws one page with the
`Graphics` from `PrintPageEventArgs`; set `HasMorePages` to true while pages remain.

[source,csharp]
----
using System.Drawing;
using System.Drawing.Printing;

namespace Bookshelf.WinForms;

public partial class ReportForm : Form
{
    private string stringToPrint = "";

    private void OnPrintClicked(object? sender, EventArgs e)
    {
        printDocument1.DocumentName = "Bookshelf report";
        stringToPrint = File.ReadAllText(Path.Combine(AppContext.BaseDirectory, "report.txt"));
        printDocument1.Print();
    }

    private void OnPrintPage(object? sender, PrintPageEventArgs e)
    {
        int charactersOnPage = 0;
        int linesPerPage = 0;

        // How much of the remaining text fits within the page margins.
        e.Graphics!.MeasureString(stringToPrint, Font, e.MarginBounds.Size, StringFormat.GenericTypographic,
            out charactersOnPage, out linesPerPage);

        e.Graphics.DrawString(stringToPrint, Font, Brushes.Black, e.MarginBounds, StringFormat.GenericTypographic);

        stringToPrint = stringToPrint[charactersOnPage..];
        e.HasMorePages = stringToPrint.Length > 0;
    }
}
----

Source: https://learn.microsoft.com/en-us/dotnet/desktop/winforms/printing/how-to-print-text-document[How to print multi-page text file (Windows Forms)]

The method in the official page does not support printing non-plain text such as a Word document or a PDF. It uses
`Graphics.DrawString` for printing because the `DrawText` methods of `TextRenderer` are not supported for printing.
The null-forgiving `!` and the range operator `[charactersOnPage..]` are the only changes from the official sample;
they follow current C# with nullable enabled.

== Pitfalls

* *Printing the document that the viewer is showing.* Setting `PageSize` on the paginator of the displayed
  `FlowDocument` changes its layout in the reader. Print a copy of the document (build a second one from the same data
  with the builder, or duplicate the content), not the instance on screen. This is common guidance; the Learn pages
  cited here do not discuss it.
* *`RichTextBox.Document` is not bindable.* It is not a dependency property. Load and save it from code-behind or a
  behavior, and expose a command to the view model, not the document.
* *Choosing `FlowDocumentReader` by default.* It is the most resource intensive viewer. Use `FlowDocumentScrollViewer`
  or `FlowDocumentPageViewer` when the view mode is fixed.
* *`TextBlock` inside a `FlowDocument`.* It works but costs more than `Run`; keep `TextBlock` for UI text.
* *Enabling hyphenation or optimal paragraphs everywhere.* Both are off by default for a reason; turn them on only for
  long, justified reading text.
* *Using `Label` for changing text.* Binding `Label.Content` to a frequently changing string is several times slower
  than `TextBlock.Text` in Learn's measurement.
* *Forgetting `pixelsPerDip`.* The `FormattedText` constructors without it are obsolete, and text drawn with a wrong
  value is blurry on high-DPI screens. Get the value with `VisualTreeHelper.GetDpi(visual).PixelsPerDip`.
* *Fixed sizes in device-independent units.* An A4 page is about 793.7 by 1122.5 units at 96 units per inch. Using
  pixels from a 150 DPI measurement makes the page too large.
* *Printer-specific tickets.* A `PrintTicket` must be built from the capabilities of the queue it will be sent to;
  setting duplex or stapling on a printer that cannot do it is a mistake. Check `PrintCapabilities` first, as the
  official sample does.
* *Blocking the UI thread.* The synchronous `PrintDocument` and `XpsDocumentWriter.Write` calls block while pages are
  produced. Use `WriteAsync` for large reports.
* *The reflection workaround in the page-range sample.* It relies on private members of WPF types; test it with every
  .NET release you ship on.
* *Font licensing.* WPF does not check font embedding permission bits. Embedding a font you are not licensed to
  redistribute is your responsibility, and the fonts supplied with Windows generally may not be redistributed.
* *`EmbeddedResource` for fonts.* Use `Resource`; the other build action is not supported.
* *`pack:` URIs in a `FontFamily` string.* An absolute `pack:` URI as the family string is invalid; use the two-part
  form with a base `Uri` and a relative reference.
* *Assuming OpenType features exist.* A `Typography` property that the font does not implement has no effect. Check
  with the font and keep a readable fallback.
* *XPS Viewer availability.* Do not tell users to open the exported `.xps` file in a viewer you do not control;
  display it in a `DocumentViewer` in your own app, or export a format your users already have.
* *Trimming and AOT.* WPF and WinForms do not support Native AOT or trimming (see the *Windows App Platforms* page of
  this section), so the reflection in the page-range workaround is not a restriction today.
