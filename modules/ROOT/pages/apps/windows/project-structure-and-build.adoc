A Windows desktop application is, to the build system, just a .NET project with a few extra switches. Those switches
decide which UI framework's reference assemblies and MSBuild targets are imported, which Windows APIs the compiler
lets you call, how XAML becomes code, and which Win32 resources (manifest, icon) end up in the executable. This page
walks through that layer for the running scenario, *Bookshelf Desktop*, on the section's baseline:

* **.NET 10 LTS** (latest patch 10.0.13, supported until 2028-11-14) and **C# 14**. **.NET 11** is at release
  candidate 2 (RC2) with general availability expected at .NET Conf, 10-13 November 2026; nothing on this page
  changes for it except the moniker (`net11.0-windows`). .NET 8 and .NET 9 leave support on 2026-11-10.
* **Visual Studio 2026** (18.11.1 at the time of writing) or the .NET SDK on its own: every command below works in a
  terminal, and the project files are identical whichever tool created them.
* **Windows App SDK 2.5.1** for the WinUI 3 project, and **CommunityToolkit.Mvvm 8.4.2** in the shared library.
* **Windows 10 and Windows 11** as run-time targets. The project files below set the minimum OS version explicitly,
  so the compiler can warn when code calls an API that an older supported Windows version lacks.

The page covers what is *in* the projects and how they are built. Choosing between WPF, WinUI 3 and Windows Forms is
the subject of the platforms page (xref:apps/windows/windows-app-platforms.adoc[Windows App Platforms: WPF, WinUI 3, WinForms, MAUI & More]), installing the
tools belongs to the xref:apps/windows/development-environment-and-tooling.adoc[Development Environment & Tooling] page, and publishing the result is covered in the
publishing pages of this section. For the general C# toolchain, see
xref:programming-languages/csharp/build-and-tooling.adoc[Build and Tooling] and
xref:programming-languages/csharp/namespaces-assemblies-and-projects.adoc[Namespaces, Assemblies and Projects] in the
C# reference; this page does not repeat them.

== The SDK-Style Project Is the Build Definition

Every .NET desktop project is an **SDK-style** project: a short XML file whose root names an SDK
(`Microsoft.NET.Sdk`), with source files, XAML pages and resources discovered by globbing rather than listed one by
one. The desktop UI frameworks do not need a different SDK for .NET 5 and later. A single property switches on the
desktop-specific targets and references.

[cols="2,3,3",options="header"]
|===
| Property | Meaning | Typical value

| `TargetFramework`
| The target framework moniker (TFM): the .NET version and, for Windows-only code, the operating-system platform.
| `net10.0-windows` (WPF, WinForms), `net10.0-windows10.0.19041.0` (WinUI 3)

| `OutputType`
| What kind of executable the compiler produces.
| `WinExe` for a GUI application, `Library` for shared code

| `UseWPF`
| Imports the WPF reference assemblies and the XAML markup-compilation targets.
| `true`

| `UseWindowsForms`
| Imports the Windows Forms reference assemblies and the designer-related targets.
| `true`

| `UseWinUI`
| Imports the WinUI 3 XAML compiler targets. Used together with the `Microsoft.WindowsAppSDK` package.
| `true`

| `Nullable`
| Enables nullable reference type analysis (C# 8 and later).
| `enable`

| `ImplicitUsings`
| Adds global `using` directives for common namespaces (`System`, `System.Linq`, and so on).
| `enable`

| `ApplicationManifest`
| Path to the `app.manifest` embedded as a Win32 resource.
| `app.manifest`

| `ApplicationIcon`
| Path to an `.ico` file embedded as the executable's icon.
| `Assets\bookshelf.ico`

| `SupportedOSPlatformVersion`
| The lowest Windows version the code is declared to run on. Drives platform-compatibility analyzer warnings.
| `10.0.17763.0`

| `RuntimeIdentifier` / `RuntimeIdentifiers`
| The Windows platform(s) the app is built for. Single value for one build, plural for multi-platform projects.
| `win-x64`; `win-x86;win-x64;win-arm64`

| `UseAppHost`
| Generates the native `.exe` launcher next to the managed `.dll`. On Windows it is on by default.
| `true`
|===

== Target Framework Monikers for Windows

A TFM has the shape `net<version>-<os><os-version>`. The part after the dash is the **target platform**. It is what
lets one compiler enforce "this API exists only on Windows" and "this API needs Windows 10 build 19041".

[cols="2,3,3",options="header"]
|===
| Moniker | Meaning | Used by

| `net10.0`
| Cross-platform .NET 10, no operating-system APIs. Can run anywhere .NET 10 runs.
| `Bookshelf.Core` (view models, interfaces, models)

| `net10.0-windows`
| .NET 10 plus the Windows-only libraries: WPF, Windows Forms, the registry, and so on. Equivalent to
  `net10.0-windows7.0`.
| WPF and WinForms apps, and libraries that touch them

| `net10.0-windows10.0.19041.0`
| As above, plus the **Windows SDK projection** for the Windows 10 version 2004 (build 19041) WinRT APIs: toast
  notifications, `Windows.Storage` pickers, and so on.
| WinUI 3 apps; WPF or WinForms apps that call WinRT APIs

| `net8.0-windows`, `net9.0-windows`
| The previous versions, supported until 2026-11-10.
| Apps not yet moved to .NET 10

| `net462`, `net48`
| .NET Framework. Windows-only, serviced with Windows, no new language runtime features.
| Legacy applications being migrated
|===

Two version numbers are easy to confuse:

* The **TFM platform version** (`windows10.0.19041.0`) selects which Windows SDK metadata the compiler references,
  that is, which WinRT APIs are visible at compile time.
* `SupportedOSPlatformVersion` (or, for WinUI projects, `TargetPlatformMinVersion`) declares the **minimum** version the app
  claims to run on. Calling an API newer than the minimum raises the platform-compatibility analyzer warning CA1416
  unless the call is guarded with `+OperatingSystem.IsWindowsVersionAtLeast(...)+` or an `[SupportedOSPlatform]`
  attribute.

A plain `net10.0` project cannot reference a `net10.0-windows` project (NuGet reports a compatibility error such as
NU1201), while the reverse works. That is why the Bookshelf solution keeps its UI-agnostic code in `net10.0` libraries
and lets only the application project use the `-windows` moniker.

== The Three UI Switches Side by Side

[cols="2,3,3,3",options="header"]
|===
| Aspect | WPF | Windows Forms | WinUI 3
| Switch | `UseWPF` | `UseWindowsForms` | `UseWinUI` plus `Microsoft.WindowsAppSDK` package
| Typical TFM | `net10.0-windows` | `net10.0-windows` | `net10.0-windows10.0.19041.0`
| `OutputType` | `WinExe` | `WinExe` | `WinExe`
| UI markup | XAML compiled to BAML | Designer C# (`*.Designer.cs`) and `.resx` | XAML compiled to XBF
| Generated code | `*.g.cs` in `obj` | None for the form; `ApplicationConfiguration.Initialize()` from MSBuild properties | `*.g.cs` and a generated `Main` unless disabled
| Platform list | Any CPU by default | Any CPU by default | `x86`, `x64`, `ARM64` per platform; `RuntimeIdentifiers` required
| Packaging default | Unpackaged | Unpackaged | Packaged (MSIX) or unpackaged with `WindowsPackageType` set to `None`
| Trimming and Native AOT | Not supported | Not supported | `PublishAot` supported since Windows App SDK 1.6
| ClickOnce | Supported | Supported | Not supported
|===

The last two rows matter at publish time, and the publishing pages of this section come back to them.

== A WPF Project File

The Bookshelf WPF application is the composition root: it references the shared libraries, owns `App.xaml` and
`MainWindow.xaml`, and is the only project that knows which UI framework is in use.

[source,xml]
----
<Project Sdk="Microsoft.NET.Sdk">

  <PropertyGroup>
    <OutputType>WinExe</OutputType>
    <TargetFramework>net10.0-windows</TargetFramework>
    <UseWPF>true</UseWPF>
    <Nullable>enable</Nullable>
    <ImplicitUsings>enable</ImplicitUsings>
    <RootNamespace>Bookshelf.Desktop</RootNamespace>
    <AssemblyName>Bookshelf</AssemblyName>
    <ApplicationManifest>app.manifest</ApplicationManifest>
    <ApplicationIcon>Assets\bookshelf.ico</ApplicationIcon>
    <SupportedOSPlatformVersion>10.0.17763.0</SupportedOSPlatformVersion>
  </PropertyGroup>

  <ItemGroup>
    <!-- Images and fonts that XAML refers to by pack URI are compiled into the assembly -->
    <Resource Include="Assets\**\*.png" />
    <Resource Include="Assets\**\*.ico" />
  </ItemGroup>

  <ItemGroup>
    <PackageReference Include="CommunityToolkit.Mvvm" />
    <PackageReference Include="Microsoft.Extensions.Hosting" />
  </ItemGroup>

  <ItemGroup>
    <ProjectReference Include="..\Bookshelf.Core\Bookshelf.Core.csproj" />
    <ProjectReference Include="..\Bookshelf.Data\Bookshelf.Data.csproj" />
  </ItemGroup>

</Project>
----

Source: https://learn.microsoft.com/en-us/dotnet/desktop/wpf/migration/how-to-upgrade-wpf[Upgrade WPF apps to .NET]

What each part does:

* `Sdk="Microsoft.NET.Sdk"` is enough. For a project that sets `UseWPF`, the .NET SDK imports the Windows Desktop
  targets automatically; older tutorials that show `Microsoft.NET.Sdk.WindowsDesktop` describe the .NET Core 3.x
  form.
* `OutputType` of `WinExe` marks the executable as a Windows GUI application: the process starts without a console
  window. The next section explains the difference from `Exe`.
* `AssemblyName` is separate from the project file name, which is handy when the folder and the executable name
  should differ.
* The `PackageReference` items have no `Version` attribute because the solution uses central package management,
  described below.
* XAML pages, `App.xaml` and C# files need no `Compile` or `Page` items: the SDK includes them by glob.
  Other files are not included automatically in the assembly. Images used as `Resource` items must be listed, as above,
  or they are not available through the `+pack://application:,,,/Assets/...+` URIs.

== OutputType: WinExe, Exe and Library

[cols="1,3,3",options="header"]
|===
| Value | Behaviour | Use in Bookshelf

| `WinExe`
| Marks the PE header with the Windows GUI subsystem. Launching from Explorer shows no console window. Writing with
  `Console.WriteLine` goes nowhere visible.
| `Bookshelf.Desktop`, `Bookshelf.WinUI` and `Bookshelf.WinForms`

| `Exe`
| Console subsystem. A console window opens (or is shared with the launching terminal). Useful temporarily for
  printing diagnostics from a UI app.
| Not used in the app; use `Debug.WriteLine` and logging instead. `Bookshelf.Tests` ends up as `Exe` (see below)

| `Library`
| A `.dll` without an entry point.
| `Bookshelf.Core`, `Bookshelf.Data`
|===

A test project does not set `OutputType` itself: for a .NET (not .NET Framework) target, the
`Microsoft.NET.Test.Sdk` package sets it to `Exe` and generates the entry point, and xUnit v3 and MSTest runner
projects are executables as well. A WPF test project that needs real windows has additional constraints
(a single-threaded apartment thread), which the xref:apps/windows/testing-view-models-and-ui.adoc[testing] page of this section covers.

== A Windows Forms Project File

A Windows Forms project is the same shape with a different switch. The `Application*` properties are Windows Forms
specific: they configure the generated `ApplicationConfiguration.Initialize()` method so `Program.cs` no longer needs
the high DPI and visual styles calls spelled out.

[source,xml]
----
<Project Sdk="Microsoft.NET.Sdk">

  <PropertyGroup>
    <OutputType>WinExe</OutputType>
    <TargetFramework>net10.0-windows</TargetFramework>
    <UseWindowsForms>true</UseWindowsForms>
    <Nullable>enable</Nullable>
    <ImplicitUsings>enable</ImplicitUsings>
    <RootNamespace>Bookshelf.WinForms</RootNamespace>
    <ApplicationManifest>app.manifest</ApplicationManifest>
    <ApplicationIcon>Assets\bookshelf.ico</ApplicationIcon>

    <!-- Inputs of the generated ApplicationConfiguration.Initialize() -->
    <ApplicationHighDpiMode>PerMonitorV2</ApplicationHighDpiMode>
    <ApplicationVisualStyles>true</ApplicationVisualStyles>
    <ApplicationUseCompatibleTextRendering>false</ApplicationUseCompatibleTextRendering>
    <ApplicationDefaultFont>Segoe UI, 9pt</ApplicationDefaultFont>
  </PropertyGroup>

  <ItemGroup>
    <PackageReference Include="CommunityToolkit.Mvvm" />
  </ItemGroup>

  <ItemGroup>
    <ProjectReference Include="..\Bookshelf.Core\Bookshelf.Core.csproj" />
    <ProjectReference Include="..\Bookshelf.Data\Bookshelf.Data.csproj" />
  </ItemGroup>

</Project>
----

Source: https://learn.microsoft.com/en-us/dotnet/desktop/winforms/high-dpi-support-in-windows-forms[High DPI support in Windows Forms]

The matching `Program.cs` is short because the project file already carries the settings:

[source,csharp]
----
namespace Bookshelf.WinForms;

internal static class Program
{
    [STAThread]
    private static void Main()
    {
        // Generated at build time from the Application* properties in the .csproj.
        ApplicationConfiguration.Initialize();
        Application.Run(new MainForm());
    }
}
----

Source: https://learn.microsoft.com/en-us/dotnet/desktop/winforms/overview/[Windows Forms overview]

With `ImplicitUsings` enabled, a Windows Forms project also gets implicit `using` directives for
`System.Windows.Forms` and `System.Drawing`. That is convenient, and it is also the reason for a classic pitfall:
setting both `UseWPF` and `UseWindowsForms` in one project makes names such as `Application`, `Button` and
`MessageBox` ambiguous. Keep the two UI stacks in separate projects, or remove one of the implicit usings with a
`<Using Remove="System.Windows.Forms" />` item. Hosting Windows Forms controls inside WPF is an
interoperation scenario with its own page.

== A WinUI 3 Project File

A WinUI 3 project additionally references the Windows App SDK NuGet package, targets a Windows SDK version, and lists
the platforms it builds for. Packaged (MSIX) is the template default; the project below shows the settings that
differ when the app is run unpackaged.

[source,xml]
----
<Project Sdk="Microsoft.NET.Sdk">

  <PropertyGroup>
    <OutputType>WinExe</OutputType>
    <TargetFramework>net10.0-windows10.0.19041.0</TargetFramework>
    <TargetPlatformMinVersion>10.0.17763.0</TargetPlatformMinVersion>
    <RootNamespace>Bookshelf.WinUI</RootNamespace>
    <ApplicationManifest>app.manifest</ApplicationManifest>
    <ApplicationIcon>Assets\bookshelf.ico</ApplicationIcon>
    <Platforms>x86;x64;ARM64</Platforms>
    <RuntimeIdentifiers>win-x86;win-x64;win-arm64</RuntimeIdentifiers>
    <UseWinUI>true</UseWinUI>
    <Nullable>enable</Nullable>
    <ImplicitUsings>enable</ImplicitUsings>

    <!-- MSIX tooling stays on so that a packaged build is a switch away -->
    <EnableMsixTooling>true</EnableMsixTooling>
    <!-- None = unpackaged (no package identity); omit for a packaged app -->
    <WindowsPackageType>None</WindowsPackageType>
  </PropertyGroup>

  <ItemGroup>
    <PackageReference Include="Microsoft.WindowsAppSDK" />
    <PackageReference Include="CommunityToolkit.Mvvm" />
  </ItemGroup>

  <ItemGroup>
    <Content Include="Assets\**" />
  </ItemGroup>

  <ItemGroup>
    <ProjectReference Include="..\Bookshelf.Core\Bookshelf.Core.csproj" />
    <ProjectReference Include="..\Bookshelf.Data\Bookshelf.Data.csproj" />
  </ItemGroup>

</Project>
----

Source: https://learn.microsoft.com/en-us/windows/apps/windows-app-sdk/single-project-msix[Single-project MSIX packaging in Visual Studio]

Differences from the WPF file:

* The `Microsoft.WindowsAppSDK` package version equals the SDK version since the 2.0 release (2.5.1 on this
  page's baseline). Central package management pins it in one place.
* `TargetPlatformMinVersion` is the WinUI project's name for the minimum supported Windows version; templates for the
  current Windows App SDK start at build 17763 (Windows 10 version 1809).
* `Platforms` and `RuntimeIdentifiers` exist because WinUI projects build per architecture. A WPF or Windows Forms
  project is "Any CPU" until the publish step chooses a runtime identifier.
* Assets are `Content` items: they are copied beside the executable (or into the package) and addressed with
  `ms-appx:///` URIs, rather than compiled into the assembly as WPF `Resource` items are.
* `EnableMsixTooling` and `WindowsPackageType` select between the packaged and unpackaged flavours. Packaging,
  the manifest and signing are the subject of the MSIX pages of this section.

== Where the Files Live

The templates for the three stacks produce a small, conventional set of files. The Bookshelf layout adds folders for
view models and services in the libraries rather than in the app, which is what keeps the app project thin.

[source,text]
----
Bookshelf.Desktop/                      (WPF)
├── Bookshelf.Desktop.csproj
├── app.manifest                    Win32 manifest: DPI awareness, supported OS, execution level
├── App.xaml                        ApplicationDefinition: application resources, startup
├── App.xaml.cs                     code-behind: composition root (Generic Host)
├── MainWindow.xaml                 Page: the main window markup
├── MainWindow.xaml.cs              code-behind: InitializeComponent() and view-only logic
├── Views/                          further windows, dialogs and user controls
├── Themes/                         ResourceDictionary files
├── Assets/                         bookshelf.ico, images (Resource)
└── Properties/                     launchSettings.json (debug profiles)
----

[cols="2,2,4",options="header"]
|===
| File | Build action | Purpose

| `App.xaml`
| `ApplicationDefinition`
| Declares the `Application` subclass. The markup compiler generates the `Main` entry point from it.

| `App.xaml.cs`
| `Compile`
| The partial class that completes `App`: `OnStartup`, `OnExit`, dependency injection setup.

| `MainWindow.xaml`
| `Page`
| The window's markup; compiled to BAML (WPF) or XBF (WinUI).

| `MainWindow.xaml.cs`
| `Compile`
| The code-behind partial class with `InitializeComponent()`. MVVM keeps it nearly empty.

| `app.manifest`
| (via `ApplicationManifest`)
| Embedded into the executable as a Win32 resource.

| `*.resx`
| `EmbeddedResource`
| Localized strings and images (primarily Windows Forms and WPF localization).

| `Assets\*.png`
| `Resource` (WPF) or `Content` (WinUI)
| Images referenced from XAML.
|===

The WinUI template adds `Package.appxmanifest` for packaged apps, a `Properties/PublishProfiles` folder with one
`.pubxml` per platform and, as the application entry point, `App.xaml`/`App.xaml.cs` plus `MainWindow.xaml`. A Windows
Forms project has `Program.cs`, `MainForm.cs`, `MainForm.Designer.cs` (generated by the designer) and
`MainForm.resx` instead of the XAML pair.

== How XAML Becomes Code: BAML and g.cs

WPF does not interpret XAML text at run time. The build runs a **markup compilation** step, and the markup compiler
produces two things for each XAML file:

. a **generated partial class** (`MainWindow.g.cs`) that declares the fields for named elements (`x:Name`), wires
  event handlers from markup attributes to the methods in your code-behind, and defines `InitializeComponent()`.
. a **BAML** file (Binary Application Markup Language), a tokenized, compact form of the same markup, embedded in the
  assembly as a resource.

At run time, `InitializeComponent()` loads the BAML resource through a pack URI and builds the object tree from it,
which is faster than parsing text. The compiler also generates the `Main` method (in `App.g.cs`) from the
`ApplicationDefinition` item.

image::windows-apps-xaml-build-pipeline.svg["Left to right: source files App.xaml, MainWindow.xaml, MainWindow.xaml.cs, handwritten C# and the manifest and icon go through markup compilation, which produces App.g.cs, MainWindow.g.cs, MainWindow.baml and a g.resources file in the obj folder; the C# compiler then combines these with the handwritten files into Bookshelf.Desktop.dll with embedded BAML, the apphost executable and the runtime configuration files in the bin folder.",width=760,role=text-center]

The intermediate files are visible, which helps when diagnosing a build error that points at a line in a generated
file:

[source,powershell]
----
dotnet build Bookshelf.Desktop -c Debug
Get-ChildItem Bookshelf.Desktop\obj\Debug\net10.0-windows -Filter "*.g.cs"
Get-ChildItem Bookshelf.Desktop\obj\Debug\net10.0-windows -Filter "*.baml"
----

Source: https://learn.microsoft.com/en-us/dotnet/desktop/wpf/advanced/code-behind-and-xaml-in-wpf[Code-behind and XAML in WPF]

[cols="2,3,3",options="header"]
|===
| Artifact | Produced by | Role
| `*.g.cs` | `MarkupCompilePass1` | Generated partial class: fields for `x:Name` elements, event hookup, `InitializeComponent()`.
| `*.g.i.cs` | Design-time build | Same idea for IntelliSense in the editor; not part of the final build.
| `*.baml` | `MarkupCompilePass1` | Binary form of the markup, embedded in `<AssemblyName>.g.resources`.
| `<AssemblyName>.g.resources` | Resource generation | The embedded resource stream that holds every BAML file and every `Resource` item.
| `*.xbf` | WinUI XAML compiler | WinUI's binary XAML format, the counterpart of BAML.
| `*_wpftmp.csproj` | `MarkupCompilePass2` preparation | A temporary project WPF may create when markup refers to types defined in the same project.
|===

This two-pass design explains two behaviours that surprise newcomers:

* XAML that refers to a type in the **same project** (a value converter or a view model in a `local:` namespace)
  needs the project compiled first. WPF handles it with a temporary assembly build, which makes the first build of a
  fresh checkout slower and can show phantom errors until the C# compiles cleanly.
* The `x:Class` attribute links the XAML file to a partial class. The class name and namespace in the XAML must match
  the C# code-behind exactly, or the build fails with an error that the partial class does not contain
  `InitializeComponent`.

=== Build Actions for XAML and Resource Files

[cols="2,4,3",options="header"]
|===
| Item type | Meaning | Reachable at run time as

| `ApplicationDefinition`
| The XAML file that defines the `Application` class. Only one per project; produces `Main`.
| (the entry point)

| `Page`
| A XAML file compiled to BAML.
| `pack://application:,,,/Views/MainWindow.xaml`

| `Resource`
| A file embedded in the assembly's `g.resources`, loadable through a pack URI.
| `pack://application:,,,/Assets/logo.png`

| `Content`
| A file copied to the output folder, not embedded.
| `+pack://siteoforigin:,,,/...+`

| `EmbeddedResource`
| A raw .NET resource (typically `.resx` strings), read with `ResourceManager`.
| `ResourceManager`

| `None`
| Part of the project but unused by the build.
| (not available)
|===

Two properties control the default globbing: `EnableDefaultPageItems` and `EnableDefaultApplicationDefinition`, which
default to `true`. Set `EnableDefaultApplicationDefinition` to `false` and mark `App.xaml` as a `Page` when you need a
custom `Main` (for example to enforce a single instance before WPF starts); then set `StartupObject` to the class
that holds it.

[source,xml]
----
<PropertyGroup>
  <EnableDefaultApplicationDefinition>false</EnableDefaultApplicationDefinition>
  <StartupObject>Bookshelf.Desktop.Program</StartupObject>
</PropertyGroup>

<ItemGroup>
  <Page Include="App.xaml" SubType="Designer" />
</ItemGroup>
----

Source: https://learn.microsoft.com/en-us/dotnet/desktop/wpf/app-development/application-management-overview[Application management overview]

== app.manifest: DPI Awareness, Supported OS and Execution Level

The application manifest is an XML document embedded in the executable. Windows reads it *before* the first line of
managed code runs, which is why some settings can only live there.

[source,xml]
----
<?xml version="1.0" encoding="utf-8"?>
<assembly manifestVersion="1.0" xmlns="urn:schemas-microsoft-com:asm.v1">
  <assemblyIdentity version="1.0.0.0" name="Bookshelf.Desktop.app"/>

  <trustInfo xmlns="urn:schemas-microsoft-com:asm.v2">
    <security>
      <requestedPrivileges xmlns="urn:schemas-microsoft-com:asm.v3">
        <!-- Run as the user who started the app; never request elevation for a book list -->
        <requestedExecutionLevel level="asInvoker" uiAccess="false" />
      </requestedPrivileges>
    </security>
  </trustInfo>

  <compatibility xmlns="urn:schemas-microsoft-com:compatibility.v1">
    <application>
      <!-- Windows 10 and Windows 11 -->
      <supportedOS Id="{8e0f7a12-bfb3-4fe8-b9a5-48fd50a15a9a}"/>
    </application>
  </compatibility>

  <application xmlns="urn:schemas-microsoft-com:asm.v3">
    <windowsSettings>
      <!-- Legacy value for older Windows 10 builds, ignored where PerMonitorV2 is understood -->
      <dpiAware xmlns="http://schemas.microsoft.com/SMI/2005/WindowsSettings">true/PM</dpiAware>
      <dpiAwareness xmlns="http://schemas.microsoft.com/SMI/2016/WindowsSettings">PerMonitorV2</dpiAwareness>
      <longPathAware xmlns="http://schemas.microsoft.com/SMI/2016/WindowsSettings">true</longPathAware>
    </windowsSettings>
  </application>
</assembly>
----

Source: https://learn.microsoft.com/en-us/dotnet/desktop/winforms/high-dpi-support-in-windows-forms[High DPI support in Windows Forms]

[cols="2,4,3",options="header"]
|===
| Element | What it controls | Notes

| `requestedExecutionLevel`
| Whether Windows shows a UAC prompt. `asInvoker` (default) runs with the caller's rights; `requireAdministrator`
  always elevates.
| Prefer `asInvoker`. Elevated apps cannot receive drag-and-drop from non-elevated Explorer windows, among other
  limitations.

| `supportedOS`
| Declares which Windows versions the app was designed for. Without the Windows 10 GUID, newer Windows can apply
  compatibility behaviour for older versions to the process.
| The same GUID covers Windows 10 and Windows 11.

| `dpiAwareness`
| The DPI awareness mode: `PerMonitorV2` (recommended), `PerMonitor`, `System`, `unaware`.
| Per-monitor V2 handles monitors with different scale factors and scale non-client areas.

| `longPathAware`
| Allows paths longer than 260 characters in Win32 APIs that honour it.
| .NET honours it for file APIs on current Windows.
|===

DPI awareness is where the three stacks differ:

* **WPF** renders in device-independent units and supports per-monitor DPI awareness, but the process must opt in.
  Add the manifest settings above so the whole process, including native dialogs and interop windows, runs in
  `PerMonitorV2` mode.
* **Windows Forms** has the `ApplicationHighDpiMode` MSBuild property (it feeds `ApplicationConfiguration.Initialize()`)
  and `+Application.SetHighDpiMode(...)+` as the code equivalent. A manifest `dpiAwareness` entry is the alternative;
  choose one place, because the process mode is set once.
* **WinUI 3** apps run per-monitor DPI aware, and the project template's `app.manifest` declares `PerMonitorV2`
  explicitly; keep that entry when you edit the file.

The Visual Studio template creates an `app.manifest` with commented examples when you choose *Add > New Item >
Application Manifest File*; the file above is the trimmed version with only the entries that matter.

== ApplicationIcon and Assembly Metadata

`ApplicationIcon` embeds an `.ico` file as the Win32 icon of the executable. That is the icon shown in Explorer, on
the taskbar before the window appears, and in the *Open with* list. It is a different thing from the window icon:

[cols="2,3,3",options="header"]
|===
| Icon | How it is set | Where it appears
| Executable icon | `<ApplicationIcon>Assets\bookshelf.ico</ApplicationIcon>` in the project | Explorer, shortcuts, taskbar pin
| WPF window icon | `Icon="pack://application:,,,/Assets/bookshelf.ico"` on `Window` | Title bar, Alt+Tab
| Windows Forms form icon | `Icon` property of the `Form` (stored in the `.resx`) | Title bar, Alt+Tab
| WinUI window icon | `AppWindow.SetIcon(path)` from code | Title bar, taskbar
| Packaged tile and logo images | `Assets` entries in `Package.appxmanifest` | Start menu, Store, installer
|===

Use a multi-resolution `.ico` file (16, 24, 32, 48 and 256 pixels as a minimum) so the shell never has to scale a
single bitmap. Assembly metadata that appears in the file's Properties dialog also comes from the project file:

[source,xml]
----
<PropertyGroup>
  <Product>Bookshelf Desktop</Product>
  <Company>Example Books Ltd</Company>
  <Copyright>Copyright 2026 Example Books Ltd</Copyright>
  <Version>1.4.0</Version>
  <FileVersion>1.4.0.0</FileVersion>
</PropertyGroup>
----

Source: https://learn.microsoft.com/en-us/dotnet/desktop/wpf/overview/[Windows Presentation Foundation overview]

`Version` feeds the assembly, file and package version in one place. Packaged apps carry a separate four-part version
in `Package.appxmanifest`, which the MSIX pages explain.

== Directory.Build.props and Central Package Management

Three projects with the same `Nullable`, `ImplicitUsings`, analyzer and version settings should state them once.
MSBuild automatically imports a file named `Directory.Build.props`, searching from the project folder upwards, and
`Directory.Packages.props` does the same for NuGet versions. Both live at the repository root, next to the solution.

[source,xml]
----
<Project>

  <PropertyGroup>
    <LangVersion>14</LangVersion>
    <Nullable>enable</Nullable>
    <ImplicitUsings>enable</ImplicitUsings>
    <AnalysisLevel>latest-recommended</AnalysisLevel>
    <EnforceCodeStyleInBuild>true</EnforceCodeStyleInBuild>
    <Deterministic>true</Deterministic>
    <UseArtifactsOutput>true</UseArtifactsOutput>

    <Product>Bookshelf Desktop</Product>
    <Company>Example Books Ltd</Company>
    <Version>1.4.0</Version>
  </PropertyGroup>

  <!-- Strict only where it is cheap: the CI build, not every developer save -->
  <PropertyGroup Condition="'$(GITHUB_ACTIONS)' == 'true'">
    <ContinuousIntegrationBuild>true</ContinuousIntegrationBuild>
    <TreatWarningsAsErrors>true</TreatWarningsAsErrors>
  </PropertyGroup>

</Project>
----

Source: https://learn.microsoft.com/en-us/dotnet/desktop/wpf/migration/how-to-upgrade-wpf[Upgrade WPF apps to .NET]

[source,xml]
----
<Project>

  <PropertyGroup>
    <ManagePackageVersionsCentrally>true</ManagePackageVersionsCentrally>
  </PropertyGroup>

  <ItemGroup>
    <PackageVersion Include="CommunityToolkit.Mvvm" Version="8.4.2" />
    <PackageVersion Include="Microsoft.WindowsAppSDK" Version="2.5.1" />
    <PackageVersion Include="Microsoft.Extensions.Hosting" Version="10.0.0" />
    <PackageVersion Include="Microsoft.EntityFrameworkCore.Sqlite" Version="10.0.0" />
    <PackageVersion Include="Microsoft.NET.Test.Sdk" Version="17.14.1" />
    <PackageVersion Include="MSTest" Version="3.9.3" />
  </ItemGroup>

</Project>
----

Source: https://learn.microsoft.com/en-us/dotnet/core/testing/unit-testing-mstest-intro[Unit testing C# with MSTest]

The versions above are the ones used by the section's other pages for the toolkit and the Windows App SDK; update the
Microsoft.Extensions, EF Core and test package versions to the current stable releases when you create the solution.
A third small file pins the SDK, so every developer and the CI runner build with the same compiler:

[source,json]
----
{
  "sdk": {
    "version": "10.0.100",
    "rollForward": "latestFeature"
  }
}
----

Source: https://learn.microsoft.com/en-us/dotnet/desktop/wpf/overview/[Windows Presentation Foundation overview]

How the three files interact:

[cols="2,4,3",options="header"]
|===
| File | Effect | Gotcha
| `Directory.Build.props` | Imported *before* the project body, so the project can override any value. | Applies to every project below it, including tests. Per-stack settings (`UseWPF`) belong in the project.
| `Directory.Build.targets` | Imported *after* the project body, so it can adjust or add targets. | Not needed for Bookshelf; mentioned because analyzers and packaging often use it.
| `Directory.Packages.props` | Central package versions; project files then omit `Version`. | A `PackageReference` that still has a `Version` attribute raises a warning or error, depending on the NuGet version.
| `global.json` | Pins the SDK version and the roll-forward policy. | Without it, the newest installed SDK is used, which can differ between machines.
|===

The C# reference covers the file mechanics in more depth; see
xref:programming-languages/csharp/build-and-tooling.adoc[Build and Tooling] for the MSBuild evaluation order.
No page in the verified Microsoft Learn set for this section documents `Directory.Build.props` itself: the desktop
documentation assumes the SDK-style project and leaves solution-wide MSBuild customization to the general MSBuild
documentation.

== Solution Layout for MVVM

MVVM needs a boundary the compiler can enforce: view models and models must not reference UI types. Splitting them
into a separate project makes that boundary a build error rather than a code-review comment.

[mermaid]
....
flowchart LR
    App["Bookshelf.Desktop"]
    Core["Bookshelf.Core"]
    Data["Bookshelf.Data"]
    Tests["Bookshelf.Tests"]
    App --> Core
    App --> Data
    Data --> Core
    Tests --> Core
    Tests --> Data
....

[cols="2,3,3,3",options="header"]
|===
| Project | Contains | `TargetFramework` | Key references

| `Bookshelf.Core`
| Models (`Book`), `IBookRepository`, `IDialogService`, `BooksViewModel`, `BookDetailsViewModel`, messages
| `net10.0`
| `CommunityToolkit.Mvvm`

| `Bookshelf.Data`
| `BookshelfDbContext`, `SqliteBookRepository`, EF Core migrations
| `net10.0`
| `Microsoft.EntityFrameworkCore.Sqlite`, project reference to Core

| `Bookshelf.Desktop`
| `App.xaml`, windows, views, value converters, `WpfDialogService`, the Generic Host composition root
| `net10.0-windows`
| Core and Data, `Microsoft.Extensions.Hosting`

| `Bookshelf.Tests`
| MSTest tests for view models, with a fake `IBookRepository`
| `net10.0`
| Core and Data, `MSTest`, `Microsoft.NET.Test.Sdk`
|===

Two rules keep the graph healthy. The arrows point only toward `Bookshelf.Core`, which references no other project.
`Bookshelf.Desktop` is the only project that depends on both libraries, because it is where the abstractions
(`IBookRepository`, `IDialogService`) are bound to implementations. The WinUI and Windows Forms variants of Bookshelf
reuse the same two libraries unchanged and replace only the app project, which is how the section's stack-comparison
pages can show the same main screen three times.

=== Creating the Solution from the Command Line

[source,powershell]
----
mkdir Bookshelf; cd Bookshelf

# Solution, then projects. Core and Data are class libraries; the app is a WPF project.
dotnet new sln --name Bookshelf
dotnet new classlib --name Bookshelf.Core --output src/Bookshelf.Core --framework net10.0
dotnet new classlib --name Bookshelf.Data --output src/Bookshelf.Data --framework net10.0
dotnet new wpf      --name Bookshelf.Desktop  --output src/Bookshelf.Desktop  --framework net10.0
dotnet new mstest   --name Bookshelf.Tests --output tests/Bookshelf.Tests --framework net10.0

# Register the projects in the solution
dotnet sln add src/Bookshelf.Core src/Bookshelf.Data src/Bookshelf.Desktop tests/Bookshelf.Tests

# Wire the dependency graph shown above
dotnet add src/Bookshelf.Data reference src/Bookshelf.Core
dotnet add src/Bookshelf.Desktop  reference src/Bookshelf.Core src/Bookshelf.Data
dotnet add tests/Bookshelf.Tests reference src/Bookshelf.Core src/Bookshelf.Data

# Packages (versions come from Directory.Packages.props once it exists)
dotnet add src/Bookshelf.Core package CommunityToolkit.Mvvm
dotnet add src/Bookshelf.Data package Microsoft.EntityFrameworkCore.Sqlite
dotnet add src/Bookshelf.Desktop  package Microsoft.Extensions.Hosting

dotnet build
dotnet test
dotnet run --project src/Bookshelf.Desktop
----

Source: https://learn.microsoft.com/en-us/dotnet/desktop/wpf/migration/how-to-upgrade-wpf[Upgrade WPF apps to .NET]

Notes on the commands:

* Since the .NET 10 SDK, `dotnet new sln` creates the XML-based **`.slnx`** solution format by default
  (`Bookshelf.slnx`); the older `.sln` is still available with `--format sln`. Visual Studio 2026 opens both.
  The `dotnet sln add` command works with either.
* `dotnet new wpf` and `dotnet new winforms` ship with the SDK. A WinUI 3 project template is installed with the
  Visual Studio "WinUI application development" workload (or from the Windows App SDK templates), so it is created
  from Visual Studio or the template package rather than assumed to exist in a bare SDK install.
* `dotnet new wpf --framework net10.0` produces a project targeting `net10.0-windows`; the template adds the
  `-windows` suffix because UI frameworks require it.
* When `Directory.Packages.props` is present, `dotnet add package` records the version in that file instead of in the
  project.

Because `Directory.Build.props` already sets `Nullable`, `ImplicitUsings` and the analysis level, the project files
contain only what is specific to each project. Core being `net10.0` has a practical payoff: its tests run without
any Windows UI thread, on any CI machine that has the .NET SDK. The same domain types and abstractions are then used
unchanged by the WPF, WinUI and Windows Forms apps.

A first view model shows the intent of the split. It lives in the WPF app, in the `Bookshelf.Desktop.ViewModels`
namespace, but depends only on the `Bookshelf.Core` abstractions and the MVVM Toolkit. It uses the toolkit's
partial-property `[ObservableProperty]` form (C# 14 and CommunityToolkit.Mvvm 8.4.1 or later) and no UI type at all:

[source,csharp]
----
using System.Collections.ObjectModel;
using Bookshelf.Core;
using CommunityToolkit.Mvvm.ComponentModel;
using CommunityToolkit.Mvvm.Input;

namespace Bookshelf.Desktop.ViewModels;

public partial class BooksViewModel(IBookRepository repository, IDialogService dialogs) : ObservableObject
{
    [ObservableProperty]
    public partial string SearchText { get; set; } = string.Empty;

    [ObservableProperty]
    public partial Book? SelectedBook { get; set; }

    public ObservableCollection<Book> Books { get; } = [];

    [RelayCommand]
    private async Task LoadAsync(CancellationToken cancellationToken)
    {
        Books.Clear();
        foreach (var book in await repository.GetAllAsync(cancellationToken))
        {
            Books.Add(book);
        }
    }

    [RelayCommand]
    private async Task DeleteSelectedAsync()
    {
        if (SelectedBook is { } book && await dialogs.ConfirmAsync("Delete book", $"Delete {book.Title}?"))
        {
            await repository.DeleteAsync(book.Id, CancellationToken.None);
            Books.Remove(book);
        }
    }
}
----

Source: https://learn.microsoft.com/en-us/dotnet/communitytoolkit/mvvm/generators/observableproperty[ObservableProperty attribute]

The project reference graph is the whole point: `IDialogService` is declared in Core and implemented in the app with
a `MessageBox` (WPF) or `ContentDialog` (WinUI), so this class uses neither and its tests need no UI thread.
The toolkit, the pattern and the services get their own pages in the MVVM part of this section.

== Building and Running

Everything the IDE does maps onto a few commands:

| Command | Effect

| `dotnet build -c Release` | Runs markup compilation and the C# compiler; output in `artifacts/` when `UseArtifactsOutput` is set, otherwise `bin/Release/net10.0-windows`.
| `dotnet run --project src/Bookshelf.Desktop` | Builds and starts the WPF or Windows Forms app. For WinUI, run from Visual Studio or use an unpackaged build.
| `dotnet watch --project src/Bookshelf.Desktop` | Rebuilds and applies Hot Reload where supported.
| `dotnet test` | Builds and runs the test project(s).
| `dotnet publish -c Release -r win-x64 --self-contained false` | Produces a framework-dependent deployment for 64-bit Windows.

== From .NET Framework Projects to .NET 8, 9 and 10

Moving a .NET Framework desktop application to the SDK-style project model is mostly a project-file change.

[cols="2,3,3",options="header"]
|===
| Area | .NET Framework (4.x) | .NET 8, 9 and 10
| Project file | Verbose, lists every file; `packages.config` common | Short SDK-style file; globbing; `PackageReference`
| Target | `<TargetFrameworkVersion>v4.8</TargetFrameworkVersion>` | `<TargetFramework>net10.0-windows</TargetFramework>`
| UI switch | Implicit (WPF references added by hand) | `UseWPF`, `UseWindowsForms`, `UseWinUI`
| Entry point | `App.xaml` as `ApplicationDefinition`, plus `app.config` | Same, plus `appsettings.json` and Generic Host
| Configuration | `app.config` and `ConfigurationManager` | `Microsoft.Extensions.Configuration`; `System.Configuration` still available as a package
| Assembly info | `Properties\AssemblyInfo.cs` | Properties in the project; `GenerateAssemblyInfo` on by default
| DPI | Opt-in via manifest and `app.config` switches | Opt-in via manifest (WPF) or `ApplicationHighDpiMode` (Windows Forms); PerMonitorV2 recommended
| Designer | In-process | Windows Forms designer is out of process
| Deployment | Installed with Windows | Framework-dependent or self-contained; own the runtime
| Unavailable | | Some technologies stay behind: AppDomains beyond the default, remoting, some Windows Communication Foundation client features, `Code Access Security`
|===

Migrating an existing project: run the .NET portability analysis, convert the project file, and fix API gaps. The
.NET Upgrade Assistant tool is **deprecated**; Microsoft now recommends GitHub Copilot modernization for
guided upgrades, and the migration pages document the manual route. The .NET 8, 9 and 10 releases did not change the
project structure: moving a project from `net8.0-windows` to `net10.0-windows` is, in practice, a one-line change plus
a package version bump. The differences between the releases are runtime and library features, not the layout described
here.

== Pitfalls

* **Forgetting the `-windows` suffix.** A project that sets `UseWPF` but targets plain `net10.0` fails with error
  NETSDK1136 (the target platform must be set to Windows). Use `net10.0-windows` (or a longer moniker).
* **Mixing `UseWPF` and `UseWindowsForms`.** Implicit usings make `Application` and `MessageBox` ambiguous. Separate
  the projects or remove an implicit using.
* **Referencing a `-windows` project from a plain `net10.0` project.** The reference is refused with a
  compatibility error (NU1201). The dependency must point from the Windows project to the portable one, never the other way.
* **Resources not found at run time.** WPF images must be `Resource` items for pack URIs to resolve; WinUI assets
  must be `Content` items. A missing item type shows as a blank image, not as a build error.
* **Setting DPI awareness twice.** Using a manifest entry and also `Application.SetHighDpiMode` or
  `ApplicationHighDpiMode` makes the effective mode depend on order. Choose one place.
* **Console output lost.** `WinExe` has no console; use logging, `Debug.WriteLine`, or temporarily switch to `Exe`.
* **Hard-coded NuGet versions drifting.** Without central package management, three projects reference three
  versions of the same package. Centralize them in `Directory.Packages.props`.
* **Mismatched `x:Class` and code-behind.** A renamed namespace in C# without the XAML change breaks
  `InitializeComponent`.
* **Treating `bin` and `obj` as source.** They are build output; keep them (and `artifacts/`) in `.gitignore`.
* **Elevation by default.** A manifest with `requireAdministrator` for convenience prevents drag-and-drop from Explorer
  and increases the damage any bug can do. Request elevation only for the operation that needs it.

== What the Official Documentation Does Not Provide

* There is **no single Microsoft Learn page for the desktop project layout** across WPF, Windows Forms and WinUI 3. The
  information is spread over the WPF, Windows Forms and Windows App SDK documentation sets. The tables above
  consolidate it; where a value is a template default (such as the minimum OS version of the WinUI template), check the
  template in your installed tooling.
* **`Directory.Build.props`, central package management and `global.json`** are general MSBuild and NuGet features. The
  desktop documentation does not describe a recommended solution layout for MVVM; the Core/Data/App/Tests split is a
  convention used by the section, not an official one.
* BAML is described in the WPF documentation as an implementation detail of XAML compilation. The intermediate file
  names and the two-pass behaviour above reflect how the build currently works; do not depend on them in tools.
* Trimming and Native AOT for WPF and Windows Forms are documented only as unsupported. WinUI's AOT support appears
  in the Windows App SDK release notes rather than in a dedicated desktop guide.

Third-party alternatives to the project and build tooling exist (for example the cross-platform Avalonia UI framework
and the Uno Platform, which use different project templates); they are outside the scope of this page.
