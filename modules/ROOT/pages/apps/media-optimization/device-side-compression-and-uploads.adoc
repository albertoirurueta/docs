= Device-Side Compression and Uploads
:description: When and how to resize or transcode media on the phone before upload: images and video, HEIC and HEVC from iOS, background and resumable uploads, progress and retries, and when to leave the work to the server.
:keywords: device-side compression, upload, background upload, resumable upload, HEIC, HEVC, pre-signed URL, WorkManager, URLSession background, tus, multipart upload, mobile upload

include::partial$media-optimization-apps-disclaimer.adoc[]

Baseline date: 2026-10-07. A phone camera produces files that are far larger than any screen needs: a 12 to 48 megapixel
photo is several megabytes, and a minute of 4K video can be hundreds of megabytes. Sending the original over a mobile
connection is slow, expensive for the user and fragile. Compressing on the device first helps, but the server still has
the final word, see xref:backend/media-optimization/upload-pipelines-queues-and-jobs.adoc[upload pipelines].

== What to do on the device, and what not to

[cols="1,2,2", options="header"]
|===
| | On the device | On the server

| Images
| Downscale to the largest size the product needs (for example 2048 pixels on the long side), apply the EXIF rotation, and
  encode as JPEG or WebP at a sane quality. Convert HEIC to JPEG only if the backend cannot read HEIC.
| Validate the file, strip metadata, produce all variants and formats, compute the BlurHash, see
  xref:backend/media-optimization/image-formats-and-encoding.adoc[image formats].

| Video
| Optionally transcode to a moderate resolution and bit rate, to shorten the upload.
| Always transcode to the ladder and package for streaming, see
  xref:backend/media-optimization/video-encoding-fundamentals.adoc[video encoding fundamentals].

| Metadata and privacy
| Strip location if the user did not intend to share it.
| Strip it again. Never rely on the client for security.
|===

Rules of thumb:

* The server must never trust the client's work: it validates and re-encodes everything. Device-side compression is an
  optimisation of the upload only.
* Compress when the user is on mobile data or the file is big. A small, already compressed JPEG gains little, and each
  re-encode loses quality (generation loss).
* Keep the original when the product needs it (for example a photo editor) and upload a compressed copy for previews.
* Do not block the UI: compression takes seconds for images and minutes for video, and drains the battery.

== HEIC and HEVC from iOS

iPhones capture HEIC photos and HEVC video by default. The files are small and not widely playable outside Apple platforms.
Two options:

* *Ask iOS for a compatible format.* Set the picker or the camera to export compatible formats (JPEG, H.264), at the cost of
  larger files. `PHPickerConfiguration.preferredAssetRepresentationMode = .compatible` and
  `UIImagePickerController.videoExportPreset` choose what is delivered. See
  xref:apps/apple/camera-media-and-photos.adoc[Camera, Media and Photos] and
  xref:apps/media-optimization/ios-avfoundation-video.adoc[AVFoundation].
* *Upload HEIC and HEVC unchanged, and convert on the server.* This keeps the smallest upload. The server needs a libheif
  and an HEVC-capable FFmpeg, which have licensing implications, see
  xref:backend/media-optimization/image-formats-and-encoding.adoc[image formats and encoding] and
  xref:backend/media-optimization/video-encoding-fundamentals.adoc[video encoding fundamentals].

Android phones record H.264 or HEVC, and many save images as JPEG, with HEIC and AVIF available on newer devices.

== Compressing images

[cols="1,3", options="header"]
|===
| Platform | Tool

| Android | Decode with the size of the target (`ImageDecoder` with `setTargetSize`, or Coil and Glide with `size`), then
  `Bitmap.compress(Bitmap.CompressFormat.WEBP_LOSSY, 80, out)` or JPEG. Apply `ExifInterface` rotation first.
| iOS | ImageIO thumbnails with `CGImageSourceCreateThumbnailAtIndex` (fast, downsampled at decode), then
  `UIImage.jpegData(compressionQuality: 0.8)` or the HEIC destination.
| React Native, Expo | `expo-image-manipulator` (resize, rotate, compress to JPEG, PNG or WebP).
| Flutter | `flutter_image_compress`, or the `image` package for pure Dart.
|===

Use the ImageIO and `ImageDecoder` downsampling paths rather than decoding the full image and then scaling, which can run
out of memory on a 48-megapixel photo. See the Bitmap section of
xref:apps/android/image-loading-coil-and-glide.adoc[Image loading with Coil and Glide].

== Compressing video

Android: Media3 Transformer, see xref:apps/media-optimization/android-video-media3.adoc[Media3]. iOS: `AVAssetExportSession`
presets, see xref:apps/media-optimization/ios-avfoundation-video.adoc[AVFoundation]. Cross-platform libraries wrap those
(for example `react-native-compressor`). Choose H.264 at 720p as the target when you transcode on the device, which every
server-side pipeline can read. Device encoders vary in quality, so treat their output as an upload format, not as a
delivery format.

== Uploading

Upload straight to object storage with a pre-signed URL from the API, as in
xref:backend/media-optimization/upload-pipelines-queues-and-jobs.adoc[upload pipelines]. The app then tells the API that the
upload is complete, or the storage event triggers processing.

=== Background uploads

A user will lock the phone or switch apps during a large upload. Use the platform's background transfer service:

* *iOS.* A background `URLSession` configuration, with `uploadTask(with:fromFile:)`. The system continues the transfer
  after the app is suspended and relaunches it on completion, see
  xref:apps/media-optimization/ios-avfoundation-video.adoc[AVFoundation] for the code.
* *Android.* WorkManager with a `CoroutineWorker` marked as a long-running foreground worker (`setForeground`), or
  `DownloadManager` for downloads. WorkManager retries with backoff and survives process death. Reference:
  https://developer.android.com/develop/background-work/background-tasks/persistent[WorkManager] and
  https://developer.android.com/develop/background-work/background-tasks/persistent/how-to/long-running[long-running workers].
* *React Native and Expo.* `expo-file-system` upload tasks with background support, or `react-native-background-upload`,
  both of which wrap the native services.

=== Resumable and multipart uploads

For files of tens of megabytes or more, a dropped connection should not restart the upload from zero:

* *S3 multipart upload*, *Google Cloud Storage resumable uploads* and *Azure Blob block uploads* split the file into parts
  that are uploaded independently and retried. The API signs one URL per part (S3) or returns a session URL (Google).
* *tus* (https://tus.io[tus.io]) is an open protocol for resumable uploads with client libraries for the main platforms,
  for backends that do not use object storage directly.
* Track which parts finished so the app can resume after a restart, and show real progress from the part count.

=== Progress and failure

Show progress from the transfer callbacks, and the server-side processing state afterwards (`processing`, `ready`,
`failed`) by polling or from a push notification, see
xref:backend/media-optimization/upload-pipelines-queues-and-jobs.adoc[upload pipelines]. Retry transient failures with
backoff, keep the compressed file until the API confirms the upload, and let the user cancel. Pre-signed URLs expire, so
ask for a new one when a retry happens after the expiry.
