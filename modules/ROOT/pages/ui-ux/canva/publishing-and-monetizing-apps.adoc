This page was checked against the official Canva Developers documentation (canva.dev) on 2026-11-07. It covers the last stretch of the developer journey for an app that runs inside the Canva editor: getting it reviewed, releasing it, keeping it up to date, and, if you want, earning money from it. Building the app is covered on xref:ui-ux/canva/building-apps-inside-canva.adoc[Building Apps Inside Canva], the extension points on xref:ui-ux/canva/app-intents.adoc[App Intents], and the end-user view of the finished catalogue on xref:ui-ux/canva/apps-marketplace-and-integrations.adoc[Apps Marketplace and Integrations].

Publishing is done in the Canva Developer Portal and is available to any developer; no particular Canva plan is needed to submit a public app. The exceptions are private apps, which are only available to teams on the Enterprise plan, and the Premium Apps Program, which is by application. Apps that use the Premium Apps Program are sold as part of Canva's paid plans (see https://www.canva.com/pricing/ for plans; no prices are repeated here). Everything described here is generally available. Canva renamed the former Apps SDK and Connect APIs to surfaces of the Canva Developers SDK; released versions keep the names and numbers they shipped under, so the Apps SDK v2 guide still says "Apps SDK".

The running example is *Bookshelf Covers*, the app from the building page whose Design Editor intent inserts book covers from the *Bookshelf* catalogue into a design. Here it goes through review and release.

== The publishing lifecycle in one picture

An app has one of two distribution modes. A *public* app is reviewed by Canva's app review team and, once released, is discoverable in the Canva editor. A *private* app is reviewed by an owner or administrator of one team and is only ever visible to that team.

A submitted app cannot be edited. To change it, cancel the submission on *Release > App status* and resubmit later. A released or rejected version cannot be edited either: you create a new version, which is a full copy of the old one including its metadata.

== Design and listing guidelines

Canva expects public apps to look and behave like part of the editor. The design guidelines cover layout, colors, typography with the Canva Sans family, icons, spacing, accessibility and localization, plus pattern pages for alerts, authentication, drag and drop, empty states, errors, external links, forms and feature support, and one page per intent. The App UI Kit implements them, so an app built from its components (see xref:web/react/index.adoc[the React section] for general React background) gets most of it for free. The App UI Kit is at version 5.15.0 on npm as checked on 2026-11-07.

The listing is what people read before opening the app. In the Developer Portal it is the *App listing details* section under *Release*, with three pages: Text, Media and Links. Prepare written content and visuals that explain the benefit, proofread them, and leave external links out of the written text. For *Bookshelf Covers* the listing would name what the app inserts, show one cover in a design, and say which Bookshelf catalogue it reads from.

Two further rules shape the listing:

* Canva recommends the app be free to use.
* Strings in the app UI should be uploaded for translation so Canva can localize the app into the supported locales.

Source: https://www.canva.dev/docs/apps/design-guidelines/[Canva Developers: Design guidelines]

== The submission checklist

The official checklist is worth running before every submission, because a rejected version cannot be reused. It groups items as follows.

[cols="1,3", options="header"]
|===
| Area | What to confirm

| Account and terms | The login email is linked to the external platform where relevant; you accept Canva's Terms of Use and the Canva Developer Terms when you submit
| Originality | The app does not copy an existing Canva app or a native feature; browse the Apps Marketplace first
| Hosting | Reliable, secure hosting sized for the expected traffic; avoid free tiers that sleep, since timeouts fail review
| Brand and design | References to Canva follow the brand guidelines; the UI follows the design guidelines and works in light and dark themes
| Security | The security guidelines for apps inside Canva are followed (see xref:backend/express/index.adoc[the Express section] for JWT-verifying backends)
| Functionality | Core features work; authentication works with and without an active session, for new and existing users; endpoints, links and buttons work; permissions are configured
| Configuration | A suitable public app name; at least one valid authentication redirect URL that is not a local URL; a valid webhook URL if the collaboration event capability is on; a valid return URL if return navigation is on
| Listing | Written content and graphics ready, proofread, without external links
| Reviewer access | A test account if the app authenticates users, plus notes on how the platform works and where content can be found
|===

After submission, Canva's ecosystem team checks guideline compliance, and progress and messages arrive through a support ticket. You can submit an app at most five times per day.

Source: https://www.canva.dev/docs/apps/submission-checklist/[Canva Developers: Submission checklist]

== Developer verification

Before a developer's apps can be listed in the Apps Marketplace, Canva collects identity and business information, partly to meet laws such as the EU trader rules, and shows some of it on the listing. It is not needed for private apps.

* You provide an identity document (for a company, one that also shows legal entity status, such as a certificate of registration), your register name and registration number if you are in a trade or public register, and a self-certification that the app complies with applicable laws.
* Identity documents are not published. The name, email, phone number, address and registration details are shown on the listing.
* New apps have had to include the information at submission since February 2024. Existing listed apps without it could be removed from the Marketplace after 17 February 2025.
* To change the information later, create a new version with the updated details and resubmit it.
* If Canva cannot verify your identity it may contact you, and failing to provide the information can keep the app from being listed.

Source: https://www.canva.dev/docs/apps/developer-verification/[Canva Developers: Developer verification]

== Procedure: submit Bookshelf Covers for review

. Upload the bundle with the Canva CLI (see the building page for `canva apps upload`) or in the Developer Portal.
. Open *Bookshelf Covers* from *Your apps* and complete *Release > App listing details*: Text, Media and Links.
. On *Release > Testing instructions*, give reviewers a test account for the Bookshelf catalogue and notes on how the integration works. This step applies to public apps whose users authenticate with credentials.
. On *Release > App status*, under *Submit app for review*, accept the terms and submit. The state becomes *Submitted* and editing is locked.
. When the review ends, read the outcome in the Developer Portal. If approved, select *Release app* and confirm.

== Review

Review runs in three stages: submission, review and outcome. A public app joins Canva's review queue and a Jira Service Desk ticket tracks it; all communication about the submission goes through that ticket. The app is approved or rejected.

* Canva publishes no expected duration for public apps, since it depends on the app's complexity and how much feedback is needed.
* A rejection is explained under *Release > App status*, which shows only the most recent feedback. Public apps continue the conversation on the original ticket.
* A rejected version cannot be modified: create a new version, fix it and submit again.
* Private apps have no Canva-enforced criteria; the team sets its own.

Source: https://www.canva.dev/docs/apps/app-review-process/[Canva Developers: App review process]

== Releasing and versioning

Approval and release are separate for public apps. After approval the owner releases on demand, often timed to a marketing moment: *Release > App status*, then *Release app*, then confirm. The app is discoverable in the Canva editor immediately. It appears in the Apps Marketplace only after a Canva employee adds it manually, which the documentation says typically takes up to a week.

Versions follow these rules:

* An app has at most two versions, the current and the previous one.
* *Create a new version* on *Your apps* is available only for apps in the Rejected or Released state.
* When a new version of a released app is released, the previous version stops being available; a new version of a rejected app replaces the rejected one.
* The app version is separate from the REST API version the app calls; creating a new app version does not change that. See xref:ui-ux/canva/rest-apis.adoc[REST APIs] for date-based API versions.

Source: https://www.canva.dev/docs/apps/releasing-apps/[Canva Developers: Releasing apps] and https://www.canva.dev/docs/apps/versioning-apps/[Canva Developers: App versioning]

== Private team apps

A private app is for one team and requires that team to be on the Enterprise plan. Submission needs no testing instructions. Review is done by a team owner or administrator in *Account settings > Team apps*, and any one of them can decide alone:

. Select *Preview* to try the app in the editor.
. Select *Release* and confirm with *Release app*. Approval and release are one step, so members can use the app at once; it never appears in the Apps Marketplace.
. Or select *Reject*, explain why and confirm.
. A released app can later be disabled with an explanation, which hides it from new and existing users. If the developer must change the frontend or the Developer Portal configuration, they create a new version and resubmit; if only the backend changes, the administrator can re-enable it directly.

For *Bookshelf*, an internal cover-checking app would go this route. Administration of the team itself is described on xref:ui-ux/canva/administration-enterprise-and-security.adoc[Administration, Enterprise and Security].

Source: https://www.canva.dev/docs/apps/managing-team-apps/[Canva Developers: Managing team apps]

== Monetization

The Canva Developers SDK has no in-app purchases. Canva documents two ways to earn from an app, and you must set up payout details to be paid through Canva's programs.

.The three Premium Apps Program access models and the external payment route
image::ui-ux-canva-publishing-and-monetizing-apps-monetization-models.svg["Four columns comparing gated, freemium and credit-based access in the Premium Apps Program with external payment links",width=720]

=== Premium Apps Program

You apply to the program, and Canva helps choose the access model.

[cols="1,3", options="header"]
|===
| Model | Behaviour

| Gated | Every feature needs a paid Canva plan, including Education and Nonprofits; Canva manages the gating and upgrade flow
| Freemium | Core features are available on Canva Free; premium features need a paid plan
| Credit-based | The app gives a starter quota of credits; when it runs out the user upgrades to unlock premium features
|===

You mark specific features as billable actions and offer different access by the user's plan. Canva recommends running billable actions through your own backend, which verifies the user's paid plan; an app without a backend should at least check that the user is enabled for the action. Existing apps earn recurring monthly revenue based on how often they are used, and apps still in development can receive grants. The SDK calls live under the monetization namespace of the `@canva/user` package (version 2.3.0 on npm as checked on 2026-11-07); see the Premium Apps documentation for their exact signatures, which this page does not reproduce. Payout rates and schedules are not published in the documentation.

Source: https://www.canva.dev/docs/apps/monetization/[Canva Developers: Monetization] and https://www.canva.dev/docs/apps/premium-apps/[Canva Developers: Premium Apps Program]

=== External payment links

An app can send users to pay on the developer's own site, with these conditions:

* Show a payment link or call to action only when `pass:c[getPlatformInfo().canAcceptPayments]` is `true`. Some platforms allow only their own payment mechanisms; when it is `false`, ask the user to open the app in a web browser instead.
* Open the link with `requestOpenExternalUrl`, paired with the `Button` or `Link` component.
* Authenticate users through the SDK so the Canva user maps to an account in your backend and paying customers can be recognised.
* Configure an uninstall webhook in the Developer Portal; Canva recommends cancelling active subscriptions on uninstall and telling the user billing has stopped.

[source,tsx]
----
import { Button } from "@canva/app-ui-kit";
import { getPlatformInfo, requestOpenExternalUrl } from "@canva/platform";

export function UpgradeButton() {
  const { canAcceptPayments } = getPlatformInfo();
  if (!canAcceptPayments) {
    return <p>Open Bookshelf Covers in a web browser to upgrade.</p>;
  }
  return (
    <Button
      variant="primary"
      onClick={() =>
        requestOpenExternalUrl({ url: "https://example.com/bookshelf/upgrade" })
      }
    >
      Upgrade on our website
    </Button>
  );
}
----

Source: https://www.canva.dev/docs/apps/accepting-payments/[Canva Developers: External payment links]. The component is a sketch assembled from the API names on that page; check the page for current signatures.

== Analytics

Public apps get a *Grow > Analytics > Usage and engagement* page in the Developer Portal; the Grow section is absent for private apps and the page is empty until release.

* *App listing views* count each time a user opens the app's installation screen in the editor; seeing the app in the Marketplace does not count unless the user selects *Use in design*.
* *App installations* count each time a user selects *Open* on that screen. Uninstalling does not lower the total, and reinstalling within 30 days is not counted twice.
* *App usage* counts unique users who use the app, for example by adding an element, uploading an asset or exporting a design. Canva notes the definition may change.

The page shows unique-user totals for the last 30 days. Third-party analytics tools such as Google Analytics cannot run in the app, because the content security policy blocks third-party scripts in the iframe; measure on your own backend instead.

Source: https://www.canva.dev/docs/apps/analytics/[Canva Developers: Analytics]

== Deep links

A deep link opens a new design with your app already open in the side panel, which suits a "Make a cover with Bookshelf Covers" button on your own website. The URL goes through Canva's login page so the destination survives sign-in:

[source,text]
----
https://www.canva.com/login/?redirect=%2Fdesign%3Fcreate%26type%3DTYPE-ID%26ui%3DAPP-UI
----

Use a `type` parameter for a design type or a `template` parameter for a template, not both, and `ui` for the app. The `ui` value is not the App ID: select *Preview* on *Your apps* and take the value after `ui=` in the address bar. Take a design type ID from the `type` parameter of a design-type link on the Canva homepage. The link always opens the latest released version. The documentation does not describe how the app reads these parameters.

Source: https://www.canva.dev/docs/apps/deep-linking/[Canva Developers: Deep linking to apps]

== Apps SDK v2 migration

Apps SDK v2 launched on 2024-09-25 and became part of the Canva Developers SDK, keeping its version numbers. Apps still on v1 were to be released upgraded by 2025-09-25, after which, per the FAQ, v1 apps were disabled and removed from the Marketplace. If you inherit an older app, run the migration tool from its directory, then finish the manual steps:

[source,bash]
----
npm install --save-dev @canva/cli@latest
npx canva apps migrate apps-sdk-v1-v2
----

The main breaking changes are:

[cols="2,3", options="header"]
|===
| v1 | v2

| `addNativeElement` | `addElementAtPoint`, or `addElementAtCursor` for documents
| `startDrag`, `makeDraggable` | `startDragToPoint`, or `startDragToCursor` for documents; `makeDraggable` is removed
| `queueMediaUpload`, `whenUploaded` | Removed; use `upload`
| Manual authentication | Removed; use frictionless authentication or OAuth
| `upload` without disclosure | `aiDisclosure` is required, for example `"none"` or `"app_generated"`
| Creating elements without alt text | `altText` is required, and may be set to `undefined` explicitly
| Upper-case discriminators such as `"EMBED"` | Lower case, such as `"embed"`
| Local `/sdk` copy from an early starter kit | Import from the npm packages
|===

Use `isSupported` to check a method before calling it, and `registerOnSupportChange` to react when support changes. The Design Editor intent migration is covered on xref:ui-ux/canva/app-intents.adoc[App Intents].

Source: https://www.canva.dev/docs/apps/upgrades-and-migrations/v2-migration-guide/[Canva Developers: Apps SDK v2 upgrade guide] and https://www.canva.dev/docs/apps/upgrades-and-migrations/v2-migration-faq/[Canva Developers: v2 migration FAQ]

== Common pitfalls

* Submitting with only local redirect URLs, or on a hosting tier that sleeps, so that the reviewer's first request times out.
* Forgetting the reviewer's test account when the app signs users in.
* Trying to fix a rejected or released version in place instead of creating a new one.
* Counting on the Apps Marketplace the day of release: the app is usable in the editor at once but listed only after Canva adds it.
* Showing a payment button when `canAcceptPayments` is `false`.
* Adding Google Analytics to the iframe.
