== Concept: version control, Git and GitHub

A *version control system* (VCS) records the history of a set of files as a sequence of snapshots, so that any
earlier state can be recovered, two states can be compared, and changes made independently by different people can
be combined. Git is a *distributed* version control system (DVCS): unlike older centralized systems, which keep the
full history only on one server and give each developer just the files for a single checkout, Git gives every clone
the entire history of the project. There is no technical difference between the copy on a developer's laptop and
the copy on a server -- both are complete repositories that can exchange history with each other.

That has practical consequences worth internalising before running a single command:

* Almost every operation -- viewing history, creating a branch, committing, comparing two versions -- is local and
  instant, because it never needs the network.
* Losing the server does not lose history: any clone can restore it, because any clone already has it.
* "Syncing" is not automatic. Two repositories only exchange history when one explicitly *pushes* to or *pulls*
  from the other; xref:git-and-github/fetch-pull-and-push.adoc[Fetch, Pull and Push] covers this
  in depth.

*Git* is the command-line tool (and the underlying data model) that implements this. It has no concept of user
accounts, issues, pull requests or a web page -- it only manages repositories and the history inside them. *GitHub*
is a separate product: a hosting service that stores Git repositories on its servers and layers collaboration
features on top -- a web UI, access control, issues, pull requests, code review, Actions for CI/CD, and more.
GitHub is one of several such platforms (GitLab and Bitbucket are others); everything this section teaches about
Git itself applies to any of them, while the "On GitHub.com" parts of each page are specific to GitHub. This
distinction is explained in GitHub's own
https://docs.github.com/en/get-started/using-git/about-git[About Git] page.

In everyday use, one Git repository lives on a developer's machine (the *local* repository) and a related copy lives
on GitHub (a *remote* repository, conventionally named `origin`). They start out identical and then diverge as each
side records its own commits, until an explicit push or pull brings them back in sync:

== Installing Git

Git 2.55 is available for every major platform. `git --version` confirms both that Git is installed and which
release it is:

[source,bash]
----
git --version
# git version 2.55.0
----

*macOS* -- the simplest path is to run a Git command from a terminal; if the Xcode Command Line Tools are not yet
installed, macOS offers to install them, which includes Git:

[source,bash]
----
git --version   # triggers the Xcode Command Line Tools installer if Git is missing
----

A more current release than the one Apple ships can be installed with the official macOS installer or a package
manager such as Homebrew:

[source,bash]
----
brew install git
----

*Windows* -- download and run the "Git for Windows" installer, which bundles the `git` command, Git Bash and Git
Credential Manager:

[source,bash]
----
winget install --id Git.Git -e --source winget
----

*Linux* -- install from the distribution's package manager, which is usually close enough to current for everyday
use; the project's own download page links a repository with newer builds when it is not:

[source,bash]
----
sudo apt install git      # Debian, Ubuntu
sudo dnf install git-all  # Fedora, RHEL, CentOS
----

Derived from https://git-scm.com/book/en/v2/Getting-Started-Installing-Git[Pro Git, 1.5 Installing Git] and
https://git-scm.com/install[Downloads for Git], which link the current installer for every platform.

== First-time setup

Git stores configuration in layered files: a system-wide file, a per-user file (`--global`), and a per-repository
file (`--local`, the default), with each level overriding the one before it. Two settings are required before
Git will let a commit be made, because every commit records who made it:

[source,bash]
----
git config --global user.name "<your-name>"
git config --global user.email "<your-email>"
----

Since Git 2.28, the name of the branch an empty repository starts on is also configurable; setting it once avoids
depending on Git's historical default of `master`:

[source,bash]
----
git config --global init.defaultBranch main
----

The editor Git opens for commit messages, merge messages and interactive rebases defaults to the platform's
`$EDITOR` or the built-in fallback `vi` (the Git for Windows installer asks for an editor during installation,
with Vim preselected); pointing it at something more
familiar is a common first tweak:

[source,bash]
----
git config --global core.editor "code --wait"   # VS Code; use vim, nano, "idea --wait" or similar as preferred
----

One more setting worth knowing about at this stage is `pull.rebase`, which decides whether `git pull` merges or
rebases the fetched commits onto the local branch --
xref:git-and-github/fetch-pull-and-push.adoc[Fetch, Pull and Push] explains the two behaviours and
when to prefer each; there is no need to set it yet.

To confirm what is currently configured, and which file each setting came from:

[source,bash]
----
git config --list --show-origin
----

Derived from https://git-scm.com/book/en/v2/Getting-Started-First-Time-Git-Setup[Pro Git, 1.6 First-Time Git Setup].

=== Getting help

Every Git command has a manual page, reachable two equivalent ways, plus a shorter usage summary:

[source,bash]
----
git help config
git config --help  # equivalent to git help config
git config -h      # a short flag summary instead of the full manual page
----

`git help <command>` and `git <command> --help` open the full manual (the same content as
https://git-scm.com/docs[the online Git reference]); `git <command> -h` prints a terse usage summary in the
terminal without leaving it. Derived from
https://git-scm.com/book/en/v2/Getting-Started-Getting-Help[Pro Git, 1.7 Getting Help].

== Creating a GitHub account and authenticating

A GitHub account is created at https://github.com/signup[github.com/signup]; the sign-up flow (username, email
verification, and enabling two-factor authentication, which GitHub strongly recommends) is covered by GitHub's own
https://docs.github.com/en/get-started/start-your-journey/creating-an-account-on-github[Creating an account on
GitHub] and is not repeated here.

Once an account exists, Git on the local machine needs a way to prove it is acting as that account whenever it
talks to GitHub over the network (`git clone`, `git push`, `git fetch`/`git pull` against a private repository).
GitHub supports two transport protocols, each with its own authentication:

[cols="1,2,2",options="header"]
|===
| | HTTPS | SSH

| URL form
| `\https://github.com/<owner>/<repo>.git`
| `git@github.com:<owner>/<repo>.git`

| Credential
| A short-lived token, stored and refreshed by a credential helper (or GitHub CLI)
| A locally generated key pair; the private key never leaves the machine

| Typical setup
| Install Git Credential Manager (bundled with Git for Windows, installable separately elsewhere), or
  `gh auth login`
| `ssh-keygen`, add the public key to the account, test with `ssh -T`

| Works through
| Most corporate proxies and firewalls (standard HTTPS traffic)
| Only where outbound SSH (port 22, or GitHub's HTTPS-tunnelled fallback) is allowed
|===

*HTTPS with a credential helper.* Git Credential Manager (GCM) is the credential helper GitHub recommends: the
first `git push` or `git clone` against a private repository over HTTPS opens a browser to sign in, and GCM then
stores and refreshes the resulting credential automatically, so it is not asked for again.

*HTTPS via GitHub CLI.* Alternatively, `gh auth login` authenticates both the `gh` command and, when asked, Git
itself for HTTPS operations:

[source,bash]
----
gh auth login
# ? Where do you use GitHub?                                         GitHub.com
# ? What is your preferred protocol for Git operations on this host?  HTTPS
# ? Authenticate Git with your GitHub credentials?                    Yes
# ? How would you like to authenticate GitHub CLI?                    Login with a web browser
----

Derived from https://docs.github.com/en/get-started/git-basics/set-up-git[Set up Git],
https://docs.github.com/en/get-started/git-basics/caching-your-github-credentials-in-git[Caching
your GitHub credentials in Git] and https://cli.github.com/manual/gh_auth_login[`gh auth login`].

*SSH keys.* Generate a modern Ed25519 key pair (RSA is still accepted but no longer recommended for new keys),
protecting it with a passphrase:

[source,bash]
----
ssh-keygen -t ed25519 -C "<your-email>"
# Enter a file in which to save the key (press Enter for the default location)
# Enter a passphrase (recommended)
----

Then add the *public* key (the `.pub` file, never the private one) to the account under *Settings > SSH and GPG
keys > New SSH key*, and confirm the connection:

[source,bash]
----
ssh -T git@github.com
# Hi <your-username>! You've successfully authenticated, but GitHub does not provide shell access.
----

Derived from https://docs.github.com/en/authentication/connecting-to-github-with-ssh[Connecting to GitHub with
SSH].

*Personal access tokens.* Where neither a credential helper nor `gh` is available -- some CI runners, some scripted
environments -- a personal access token can be used as the HTTPS password directly (`git clone
\https://<your-username>@github.com/<owner>/<repo>.git`, entering `<TOKEN>` when prompted for the password, or
stored in a credential helper). Treat a token exactly like a password: never commit it, and scope and expire it as
narrowly as the task allows. This is documented as the fallback, not the default, path in
https://docs.github.com/en/get-started/git-basics/set-up-git[Set up Git].

== IDE setup

=== IntelliJ IDEA

IntelliJ IDEA bundles Git support and only needs to know where the `git` executable is:

. Open *Settings > Version Control > Git* (*IntelliJ IDEA > Settings* on macOS).
. IntelliJ IDEA auto-detects an installed Git executable; if it cannot find one, browse to it manually in the
  "Path to Git executable" field, then use "Test" to confirm the IDE can run it.

Derived from https://www.jetbrains.com/help/idea/set-up-a-git-repository.html[Set up a Git repository].

A GitHub account is added separately, so the IDE can clone private repositories and drive pull requests:

. Open *Settings > Version Control > GitHub*.
. Click *+* to add an account, then either log in through a browser or paste a personal access token.

Derived from https://www.jetbrains.com/help/idea/github.html[Using GitHub integration in IntelliJ IDEA].

=== VS Code

VS Code has Git support built in and needs no extension for local commits, branching or viewing history through the
*Source Control* view (also reachable with kbd:[Ctrl+Shift+G], kbd:[⌃⇧G] on macOS); it only needs Git
itself to already be installed and on the `PATH`. Cloning a private repository or pushing to GitHub prompts a
browser sign-in the first time. Derived from
https://code.visualstudio.com/docs/sourcecontrol/overview[Source Control overview].

Reviewing and creating pull requests and issues from inside the editor needs the *GitHub Pull Requests and Issues*
extension:

. Install the extension from the Extensions view (search for "GitHub Pull Requests and Issues", published by
  GitHub) or the
  https://marketplace.visualstudio.com/items?itemName=GitHub.vscode-pull-request-github[Marketplace page].
. Sign in with GitHub from the GitHub icon added to the Activity Bar.

Derived from https://code.visualstudio.com/docs/sourcecontrol/github[Working with GitHub in VS Code].

== Common mistakes and tips

[cols="1,2",options="header"]
|===
| Mistake | Why it bites, and what to do instead

| Setting `user.email` to a private address
| Commits are attributed by this email; GitHub only links a commit to a profile when the email matches one on the
  account (or its no-reply address). Use the same email registered on GitHub, or its `noreply` alias.

| Skipping `init.defaultBranch`
| Git still defaults a brand-new repository's first branch to `master` unless `init.defaultBranch` is set; setting
  `main` once avoids renaming it by hand every time.

| Pasting a real token into a command or file
| Anything typed on the command line can end up in shell history, and anything committed stays in history even
  after being removed later. Always use a credential helper or an environment variable, never a literal token in a
  script or commit.

| Assuming `git help <command>` opens a website
| It opens the manual page installed locally (`man`-style on Unix, HTML in a browser on Windows) -- useful offline,
  but it reflects the locally installed Git version, not always the latest docs.
|===
