A retrieval-augmented generation (RAG) prototype takes an afternoon: split some Markdown, embed it, store the vectors,
retrieve the five nearest chunks and paste them into a prompt. The xref:database/vector-rag/index.adoc[Vector Databases &
RAG] section of this site covers exactly that path, and covers it well. Everything that happens *after* the prototype
works is the subject of this sub-section: real PDFs with tables and scanned pages, documents that change every hour, users
who must not see each other's files, conversations that span days and devices, answers that must cite their sources and
admit when they do not know, an HTTP API and an MCP server in front of the same retriever, a latency budget, a cost per
question, a knowledge graph for the questions vectors cannot answer, and the evaluation and tracing that tell you whether
last week's change made things better or worse. This is the *day-2 problem* of RAG.

== The running scenario: DocsAssistant as a production service

Every page extends the same service. *DocsAssistant* answers questions about this site's documentation. It reuses the
corpus, the pgvector schema (`documents`, `chunks`, `chunk_embeddings`) and the local models of
xref:database/vector-rag/postgresql-pgvector.adoc[PostgreSQL & pgvector], the agent of
xref:ai/langchain/index.adoc[LangChain] and xref:ai/spring-ai/index.adoc[Spring AI], and the `docs-assistant` MCP server
of xref:ai/mcp/rag-over-mcp.adoc[Exposing RAG through MCP]. Here it grows into a service with users:

[mermaid]
....
flowchart LR
  subgraph Clients
    W[Web widget]
    C[Claude Code / Copilot]
    A[LangGraph agent]
  end
  subgraph DocsAssistant
    API["/v1/ask REST + SSE"]
    MCP["MCP server search_docs"]
    O[Orchestrator]
    R[Retriever with ACL filter]
    M[(Conversation store)]
  end
  subgraph Stores
    PG[(PostgreSQL + pgvector)]
    N[(Neo4j graph)]
  end
  W --> API
  C --> MCP
  A --> MCP
  API --> O
  O --> R
  O --> M
  MCP --> R
  R --> PG
  R --> N
....

* *Ingestion* adds real PDFs with tables and images next to the AsciiDoc sources, keeps the index fresh from change
  events and deletes what was deleted.
* *`POST /v1/ask`* takes a question, a `conversationId` and optional filters, and streams the answer as server-sent events
  with citations.
* *Conversation IDs* persist memory per authenticated user, across devices.
* *Per-component ACLs* filter retrieval: a caller's groups come from the verified token and become a metadata filter.
* *The same retriever* is exposed through an MCP server, so coding assistants and agents can search the docs.
* *A Neo4j graph* of components, pages and concepts answers the questions that need relationships (GraphRAG).

Each build page shows the same capability three times: Python (LangChain 1.x with FastAPI), Java (Spring AI 2.0 on Spring
Boot 4.1) and Java (LangChain4j 1.20). Model names are never hard-coded in the snippets: every example reads the chat
and embedding model from configuration (`CHAT_MODEL`, `EMBEDDING_MODEL`, or the `spring.ai.*` and `langchain4j.*`
properties), so the same code runs against a local runtime from xref:ai/local-llms/index.adoc[Running LLMs Locally] or a
hosted provider.

=== Where the books are out of date

The requester-provided books below are excellent on concepts, but several of their APIs have moved on. The pages
flag each difference where it matters; the most important are collected here.

* *LangChain.* Older examples import `langchain.text_splitter` and build agents with `create_react_agent`. In LangChain
  1.x the splitters live in `langchain_text_splitters`, agents are built with `langchain.agents.create_agent` and
  extended with middleware, and several retrievers used in _Learning LangChain_ (`ParentDocumentRetriever`,
  `MultiVectorRetriever`, `SelfQueryRetriever`, the indexing API) now live in `langchain-classic`. LlamaIndex moved its
  documentation to `developers.llamaindex.ai` (`llama-index` 0.14.25 on 2026-09-30).
* *The Neo4j book's stack.* It uses LangChain4j 0.35, a pre-1.0 Spring AI, an earlier Haystack line, an OpenAI embedding model of
  2022 and Neo4j 5.21. The current versions are LangChain4j 1.20 (with the community Neo4j embedding store and
  text-to-Cypher retriever), Spring AI 2.0.1 (with `Neo4jVectorStore` and `Neo4jChatMemoryRepository`), `haystack-ai`
  3.2.0 with `neo4j-haystack` 2.2.1, and the
  calendar-versioned Neo4j 2026.x releases; the embedding model it uses has been superseded. It predates
  `neo4j-graphrag`'s text2cypher retrievers, `SimpleKGPipeline`, the LLM Graph Builder and the Neo4j MCP servers, which
  these pages document from Neo4j's own documentation.
* *Spring AI.* Books written for Spring AI 1.0 or earlier describe `PromptChatMemoryAdvisor` (gone in 2.0), property paths
  with an `.options` segment (dropped), and `ChatModel.call()` running tools (it no longer does). See
  xref:ai/spring-ai/migration-1x-to-2x.adoc[Migrating from 1.x to 2.x].
* *The Python cookbook's UI layer.* Its only interface is Streamlit, on the end-of-life `python:3.9` image, with the 0.x
  OpenAI Agents SDK. REST, FastAPI and server-sent events are not covered; xref:ai/rag-systems/serving-rag-as-an-api.adoc[Serving RAG as an API]
  fills that gap from the FastAPI documentation.
* *Not covered by any of the books*: SSE and WebSocket API design, authoring a RAG-behind-MCP server, and LangChain 1.x
  middleware for guardrails and memory.
