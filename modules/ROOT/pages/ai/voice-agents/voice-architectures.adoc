== Three architectures

Every voice agent turns sound into a decision and a decision into sound. What differs is whether the decision is taken on
text or on audio.

[mermaid]
....

  end
  subgraph S2S["2. Speech to speech"]

    M3 --> O3[Audio out]
  end
....

*Cascaded.* A speech-to-text (STT) service transcribes the caller, a text LLM (the DocsAssistant core) produces the
answer, and a text-to-speech (TTS) service speaks it. This is the "sandwich" that LangChain's voice-agent guide
describes. Its strengths are control and reuse: the LLM step is exactly the text agent you already operate, with its
retriever, memory, access-control filters and tests; each stage can be swapped for another vendor or a local model; and
the transcript exists at every step, which helps logging, redaction and evaluation. Its weakness is latency, because
three services and two network hops sit between the caller and the answer, and information loss, because the LLM never
hears tone, hesitation or background noise.

*Speech to speech.* One model takes audio in and produces audio out, keeping prosody and handling interruptions inside the
model. OpenAI GPT-Live and the Realtime API, Gemini Live and Azure Voice Live are of this kind (see
xref:ai/voice-agents/realtime-apis.adoc[Realtime APIs]). It is the lowest-latency and most natural option. The price is
that the model is the vendor's, the reasoning is that model's rather than your chosen LLM's, and the retrieval has to be
reached through tool calls the model decides to make.

*Hybrid.* A speech model owns the conversation (listening, turn-taking, speaking) but delegates the question to a text
backend, which is the DocsAssistant core. OpenAI's GPT-Live is designed this way: the live model handles the conversation
and delegates reasoning to your backend. A cascaded pipeline with a small fast model for chit-chat and the core for real
questions is the same idea built from parts.

== Where RAG fits

There are two places to put retrieval, and the choice follows the architecture.

* *Context injection.* Before the LLM sees the question, retrieval runs and its results are placed in the prompt. It adds a
  fixed delay to every turn, including turns that need no documents ("yes", "thanks"). In a cascaded pipeline that is
  simply the DocsAssistant core being called with the transcript.
* *Tool calls.* The model decides whether a search is needed and calls a `search_docs` tool. Greetings cost nothing and
  hard questions get one or more searches. This is the only option for speech-to-speech models, and it is how the
  xref:ai/mcp/rag-over-mcp.adoc[RAG over MCP] server is consumed by realtime APIs. The cost is that a tool round trip
  adds a pause, so the agent should say something short ("let me check the docs") while the tool runs.

The retrieval tool for a voice agent returns less than the text version: two or three short passages, not ten, because
the model has to speak the result and the listener cannot skim it. Citations come back as titles ("the installation
guide") for the model to say, not as URLs. The retrieval stack itself is covered in
xref:ai/rag-systems/index.adoc[RAG Systems in Production]; the conversation memory for a voice thread is the same
checkpointer or JDBC memory described in xref:ai/rag-systems/conversational-rag-and-memory.adoc[Conversational RAG and
Memory].

== Stream every stage

A pipeline that waits for the end of each stage before starting the next adds the full duration of each stage to the
response time. Streaming overlaps them:

* STT runs *while the caller speaks*, emitting interim and final transcripts, so by the time the caller stops, the text
  is almost ready.
* The LLM streams tokens, and the first token is what matters.
* TTS starts as soon as it has a first sentence, and returns audio in chunks.
* Playback starts at the first audio chunk, and the rest arrives while the first sentence is being spoken.

=== Sentence chunking

A TTS engine needs enough text to choose intonation but not so much that you wait for it. The usual compromise is to
buffer LLM tokens until a sentence boundary (a full stop, question mark, exclamation mark or newline followed by a
space), speak that sentence, and keep buffering. Two refinements matter in practice: do not split on abbreviations and
decimal numbers ("v1.4.3", "e.g."), and flush a first clause early if the first sentence is long, because the first
chunk decides the time to first audio.

.sentences.py: a minimal sentence chunker for a token stream
[source,python]
----
import re
from collections.abc import AsyncIterator

_BOUNDARY = re.compile(r"(?<=[.!?])\s+(?=[A-Z0-9])|\n+")


async def sentences(tokens: AsyncIterator[str], first_flush: int = 80) -> AsyncIterator[str]:
    """Yield speakable chunks from a stream of text tokens."""
    buffer, emitted_first = "", False
    async for token in tokens:
        buffer += token
        while (match := _BOUNDARY.search(buffer)):
            chunk, buffer = buffer[: match.start()], buffer[match.end():]
            if chunk.strip():
                emitted_first = True
                yield chunk.strip()
        # Long first sentence: flush at a comma so audio can start earlier.
        if not emitted_first and len(buffer) > first_flush and "," in buffer:
            head, _, buffer = buffer.rpartition(",")
            emitted_first = True
            yield head.strip() + ","
    if buffer.strip():
        yield buffer.strip()
----

This is illustrative code and is not a library API. Pipecat and LiveKit ship their own aggregators that do the same job;
see https://docs.pipecat.ai/overview/introduction[Pipecat: Introduction] and https://docs.livekit.io/agents/[LiveKit
Agents documentation].

Because the audience hears the text, the prompt of a voice agent differs from a chat prompt: ask for one or two short
sentences, plain text without markdown, numbers and identifiers written so they can be read aloud, and a spoken lead-in
before any tool call. The Spring AI version of this idea is the `SpokenText.forSpeech` helper on the
xref:ai/spring-ai/audio-transcription-and-speech.adoc[Audio Transcription & Speech] page.

== The latency budget

The response time the caller perceives, from the end of their sentence to the first audible word, is, for a cascaded
pipeline with streaming stages:

[stem]
++++
T_{resp} \approx T_{net} + T_{eot} + T_{TTFT}^{LLM} + T_{TTFB}^{TTS}
++++

where latexmath:[T_{net}] is the audio round trip between the caller and the voice server (including capture and playout
buffering), latexmath:[T_{eot}] is the end-of-turn delay (the silence the system waits before deciding the caller has finished,
plus any final-transcript delay), latexmath:[T_{TTFT}^{LLM}] is the LLM's time to first token (which includes retrieval and any
tool round trip) and latexmath:[T_{TTFB}^{TTS}] is the synthesiser's time to first audio byte for the first sentence.

Three observations follow from the formula.

. *The terms add.* A fast TTS does not help a slow end-of-turn detector. Optimise the largest term first, and measure
  before guessing.
. *latexmath:[T_{eot}] is a choice, not a cost.* Waiting for 800 ms of silence is cheap to implement and adds 800 ms to every
  turn; a semantic turn detector can answer sooner when the sentence is clearly finished and wait longer when it is not.
  See xref:ai/voice-agents/turn-taking-and-interruptions.adoc[Turn-Taking and Interruptions].
. *Retrieval sits inside latexmath:[T_{TTFT}^{LLM}].* A search before the first token delays everything. Speak a short filler
  while the search runs, cache frequent queries
  (xref:ai/rag-systems/caching-latency-and-cost.adoc[Caching, Latency and Cost]), and keep the reranker small.

A speech-to-speech model has a different budget, latexmath:[T_{resp} \approx T_{net} + T_{eot} + T_{model}], where the model
term covers hearing, thinking and the first audio together; tool calls add their own round trip on top.

=== Measuring it

Measure per stage, on real audio, at the voice server, and report percentiles rather than averages because the tail is
what callers remember. Record these timestamps for every turn:

* `t_user_end`: the moment the turn detector declared the turn finished.
* `t_stt_final`: the final transcript arrived.
* `t_llm_first_token`: the first LLM token arrived.
* `t_tts_first_byte`: the first synthesised audio byte arrived.
* `t_audio_sent`: the first audio frame was written to the transport.

The differences give each term, and `t_audio_sent - t_user_end` is the server-side part of latexmath:[T_{resp}]. Add the
transport round trip (the WebRTC stats `currentRoundTripTime`, or a ping on a WebSocket) to estimate the rest. Frameworks
expose these as metrics events; production dashboards and alert thresholds belong to
xref:ai/voice-agents/production-voice-agents.adoc[Production Voice Agents].

== Barge-in and the architecture

Whichever architecture you choose, the caller may interrupt. A cascaded pipeline must cancel the running LLM stream and
the TTS request, flush the audio already queued in the transport, and tell the conversation memory how much of the answer
was actually heard. A speech-to-speech API does the first two itself and usually asks the client to report where playback
stopped. The details are on the xref:ai/voice-agents/turn-taking-and-interruptions.adoc[next page].

== Choosing

Start with the architecture that matches the constraint that hurts most: a cascaded pipeline when you must reuse the text
core, run on premises or pick each model; speech to speech when naturalness and latency dominate and the vendor's model is
acceptable; a hybrid when you want the vendor's conversation layer but your own answers. The decision map on the
xref:ai/voice-agents/index.adoc[landing page] turns this into products, and
xref:ai/voice-agents/pipecat.adoc[Pipecat] and xref:ai/voice-agents/livekit-agents.adoc[LiveKit Agents] show the cascaded
and speech-to-speech modes in one framework.
