A retrieval-augmented assistant that only answers in a text box is not yet a product for people who are driving, cooking,
walking through a warehouse or phoning a help line. The xref:ai/rag-systems/index.adoc[RAG Systems in Production]
sub-section builds the assistant, and xref:ai/conversational-channels/index.adoc[Conversational Channels] puts it behind
chat surfaces. This sub-section adds the *spoken* channel: how audio gets to the assistant, how the answer gets back as
speech quickly enough to feel like a conversation, and how that works in a browser and on a telephone.

== Voice is not chat with a microphone

A text conversation tolerates a two-second pause, long answers, tables and links. A spoken conversation does not. People
expect a reply to start within a second or so of finishing a sentence, they interrupt when the answer is wrong or too
long, they cannot skim, and they cannot see a citation. Five consequences shape every page that follows:

* *Latency is the user experience.* The time from the end of the user's speech to the first audible word is a sum of
  network, end-of-turn detection, the model's first token and the speech synthesiser's first audio byte; each stage has
  to stream. The xref:ai/voice-agents/voice-architectures.adoc[Voice Architectures] page builds the budget.
* *Turn-taking is a feature, not a detail.* Deciding when the user has finished, and stopping instantly when they
  interrupt, decides whether the agent feels attentive or rude. See
  xref:ai/voice-agents/turn-taking-and-interruptions.adoc[Turn-Taking and Interruptions].
* *Answers are written for the ear.* Short sentences, no markdown, numbers and identifiers spelled so that they can be
  spoken, and citations read as "according to the installation guide" rather than as links.
* *The channel is lossy.* Telephone audio is 8 kHz mu-law, browsers add echo cancellation, and recognition errors
  propagate into retrieval, so the assistant must confirm what it understood when the stakes are high.
* *Recording and consent are legal matters.* Calls are regulated differently in each jurisdiction; the
  xref:ai/voice-agents/production-voice-agents.adoc[production page] links the rules rather than summarising them.

== The idea: one core, many voices

Every page uses the same running scenario, *call DocsAssistant*. The assistant answers questions about this site's
documentation and its core is the same channel-agnostic operation used by the other sub-sections:

[source,text]
----
ask(conversationId, userId, text) -> stream of { token | citation | done }
----

The core is implemented twice, as in the RAG Systems sub-section: in Python with LangChain `create_agent`, a retriever
tool, a Postgres checkpointer and FastAPI, and in Java with the Spring AI `ChatClient`, the RAG advisor, JDBC chat memory
and Spring Boot. The voice layer sits in front of it and has to turn audio into the `text` argument and the token stream
back into audio. The scenario follows four paths:

. *Browser.* A WebRTC voice widget on a documentation page speaks to a Pipecat or LiveKit worker, or directly to a
  realtime API.
. *ElevenLabs Agent.* A hosted agent calls the DocsAssistant core as its custom LLM or as a tool.
. *Phone call through Twilio.* First with ConversationRelay, where Twilio does the speech work and your WebSocket
  exchanges text; then with Media Streams, where raw audio goes through Pipecat or a hand-written Spring pipeline.
. *Company PBX.* An Asterisk extension streams audio through External Media or `chan_websocket` to a Python (Pipecat) or
  Java (Spring) voice service.

== Choosing an approach

image::ai-voice-agents-decision-map.svg["Decision map with four options for giving the DocsAssistant core a voice. A hosted voice platform such as ElevenLabs Agents gives the fastest start and receives the core as a custom LLM or tool. A realtime speech-to-speech API from OpenAI, Google or Azure gives the lowest latency and reaches the core through tool calls. An open-source framework such as Pipecat or LiveKit Agents lets you choose each model and run some locally, with the core as the LLM step. A hand-rolled pipeline gives full control and the least footprint. Delivery then branches into the web over WebRTC or WebSocket and the telephone network over Twilio, SIP or an Asterisk PBX.",width=900,role=text-center]

=== Where the books are out of date

No requester-provided book covers real-time voice in depth. Only the chapters named in the
<<_bibliography,bibliography>> are used, and only for concepts. The differences that matter:

* *Spring AI audio.* _Spring AI in Action_ (Chapter 8) targets Spring AI 1.0. In 2.0 `TranscriptionModel` extends
  `StreamingTranscriptionModel`, the text-to-speech interfaces are `TextToSpeechModel` and
  `StreamingTextToSpeechModel` (the `SpeechModel` of the book is gone), OpenAI speech streams real chunks, ElevenLabs is
  a provider, and the Azure OpenAI module was removed. The pages show the current API.
* *Hugging Face pipelines.* _Hugging Face in Action_ covers ASR pipelines and Gradio audio widgets; the speech catalogue
  and current idioms live on the xref:ai/hugging-face/speech-models.adoc[speech models] page.
* *Real-time voice.* Turn-taking, barge-in, realtime APIs, WebRTC audio and telephony are not covered by any of the five
  books; those pages rely on official documentation alone.
* *OpenAI.* Anything written about the Realtime API before 2026 describes the earlier preview models and event names;
  GPT-Live is a newer, separate API. The xref:ai/voice-agents/realtime-apis.adoc[Realtime APIs] page follows the current
  documentation.
