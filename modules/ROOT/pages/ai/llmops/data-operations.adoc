LLM applications consume four kinds of data: the documents behind retrieval, the traces captured in production, the golden
and feedback datasets used for evaluation, and the prompts and configuration (covered in
xref:ai/llmops/prompt-and-model-management.adoc[Prompt and Model Management]). Each needs an owner, a lineage and a recovery
plan.

== A ten-step preprocessing pipeline

The same sequence applies whether the output is an index, an evaluation set or a fine-tuning corpus. Each step has an
observable output so a failure can be located.

[cols="1,2,3", options="header"]
|===
| Step | Name | What it does for the DocsAssistant

| 1
| Collect
| Pull documents from the source of truth (repository, wiki, tickets) with source URI and revision.

| 2
| Validate
| Reject unreadable, empty or wrongly encoded inputs and count them.

| 3
| Normalise
| Convert to a single text format, fix encoding and whitespace, preserve headings and code blocks.

| 4
| Deduplicate
| Remove exact and near-duplicate content so retrieval does not return the same passage repeatedly.

| 5
| Filter
| Drop out-of-scope, low-quality or expired content, and content the classification rules exclude.

| 6
| Redact
| Remove or pseudonymise personal and secret data before anything is stored or sent to a model.

| 7
| Enrich
| Attach metadata: product, version, language, owner, access class and effective dates.

| 8
| Split
| Chunk along structure with the sizes the evaluation chose, keeping a pointer to the parent section.

| 9
| Embed and load
| Compute embeddings with a recorded model version and write to the index with the metadata.

| 10
| Verify and record
| Run sanity queries and the retrieval part of the golden set, then record counts, versions and lineage.
|===

Parsing, chunking and embedding choices are treated in xref:ai/rag-systems/document-parsing.adoc[Document Parsing] and
xref:ai/rag-systems/ingestion-pipelines-and-freshness.adoc[Ingestion Pipelines and Freshness]; this page covers the
operational envelope around them. Step 10 gates promotion in the same way as the checks in
xref:ai/llmops/evaluation-in-ci.adoc[Evaluation in CI].

== Dataset lineage

Lineage answers "where did this dataset or index come from, and what depends on it". Record, for every produced artefact: the
input revisions (source commit or snapshot id), the pipeline code revision, the parameter set, the output identifier (index
name and version, dataset version) and the time. Tools differ in how they store it, but the minimum is a manifest written by
the last pipeline step.

[source,python]
----
import json, hashlib, datetime, pathlib
import mlflow

def record_lineage(index_version: str, source_rev: str, code_rev: str, params: dict, eval_path: str) -> None:
    manifest = {
        "index_version": index_version,
        "source_revision": source_rev,
        "pipeline_revision": code_rev,
        "params": params,
        "eval_set_sha256": hashlib.sha256(pathlib.Path(eval_path).read_bytes()).hexdigest(),
        "created_at": datetime.datetime.now(datetime.timezone.utc).isoformat(),
    }
    pathlib.Path("manifest.json").write_text(json.dumps(manifest, indent=2))
    with mlflow.start_run(run_name=f"index-{index_version}"):
        mlflow.log_params(params)
        mlflow.log_artifact("manifest.json")
----

Source: https://mlflow.org/docs/latest/ml/tracking/[MLflow: Tracking]. For versioning the data itself, a tool such as DVC stores
content hashes in Git while the bytes live in object storage (see https://dvc.org/doc/start/data-management/data-versioning[DVC:
Data versioning]); MLflow datasets and LangSmith datasets, described in xref:ai/llmops/building-eval-sets.adoc[Building Eval
Sets], version evaluation data. Tracing a bad answer back through the trace to the chunk, the index version and the source
revision is the practical test of whether lineage is complete.

== Handling personal data

Traces and feedback contain whatever users type, which includes personal data and sometimes secrets. Controls, in order of
how early they act:

. *Minimise*: do not capture content you do not need. OpenTelemetry GenAI content capture is opt-in for this reason (see
  xref:ai/llmops/observability-with-opentelemetry.adoc[Observability with OpenTelemetry]).
. *Redact before storage*: detect and mask identifiers in prompts and responses at the SDK or collector, before the data
  leaves the process.
. *Pseudonymise* user and tenant identifiers so traces can be grouped without identifying a person.
. *Restrict access* to raw traces by role and log who reads them.
. *Retain briefly*: set a retention period per data class and delete on schedule, including copies in evaluation datasets.
. *Honour deletion requests* by knowing where a person's data can appear: traces, feedback, golden sets built from traffic,
  and caches (see xref:ai/llmops/cost-management.adoc[Cost Management] for semantic caches).

[source,python]
----
from langfuse import Langfuse

def mask(data, **kwargs):
    # Replace e-mail addresses before the event leaves the process.
    import re
    if isinstance(data, str):
        return re.sub(r"[\w.+-]+@[\w-]+\.[\w.]+", "[EMAIL]", data)
    return data

langfuse = Langfuse(mask=mask)   # credentials are read from LANGFUSE_* environment variables
----

Source: https://langfuse.com/docs/observability/features/masking[Langfuse: Masking]. A regular expression catches only the
patterns you thought of; production systems usually combine pattern rules with a dedicated detection library. Access control
for retrieved content is a separate problem, discussed in xref:ai/rag-systems/access-control-and-privacy.adoc[Access Control
and Privacy]. The legal bases and obligations (for example under the GDPR) are named in
xref:ai/llmops/operational-governance.adoc[Operational Governance] and belong to the AI Security and Responsible AI
sub-section, which is not yet published; this guide does not give legal advice.

== Vector-index freshness SLAs

A *freshness SLO* states how stale an answer may be. For the DocsAssistant: "99% of documents are searchable within 30
minutes of publication and none is older than 24 hours relative to its source". Define freshness for a document latexmath:[d] as

[stem]
++++
\mathrm{lag}(d) = t_{\mathrm{indexed}}(d) - t_{\mathrm{published}}(d)
++++

and the SLI as the fraction of documents with latexmath:[\mathrm{lag}(d) \le L] over a window. Export the lag as a metric from the
ingestion job and alert on its tail, not its mean.

[source,yaml]
----
groups:
  - name: index-freshness
    rules:
      - record: docsassistant:index_lag_seconds:p99
        expr: histogram_quantile(0.99, sum by (le) (rate(index_lag_seconds_bucket[1h])))
      - alert: IndexFreshnessSloBreached
        expr: docsassistant:index_lag_seconds:p99 > 1800
        for: 30m
        labels:
          severity: ticket
----

Source: https://prometheus.io/docs/prometheus/latest/configuration/recording_rules/[Prometheus: Recording rules]. The metric
name is this guide's convention. Deletions count as freshness too: a retired page that still ranks is a worse failure than a
slow new page, so track delete propagation separately. Event-driven versus scheduled ingestion, tombstones and re-embedding
after a model change are in xref:ai/rag-systems/ingestion-pipelines-and-freshness.adoc[Ingestion Pipelines and Freshness].

== Backups and restore tests

An index can be rebuilt from sources, but rebuilding costs embedding spend and time, and some data cannot be rebuilt.
Classify before deciding:

[cols="2,2,3", options="header"]
|===
| Asset | Rebuildable? | Backup approach

| Vector index
| Yes, from sources and the manifest.
| Snapshot to object storage for fast recovery; otherwise keep the manifest and rebuild.

| Golden and feedback datasets
| No (human labels).
| Versioned storage plus off-site copy; treat as source data.

| Traces and metrics
| No, but disposable after retention.
| Follow the retention policy; back up the aggregated reports.

| Prompt registry and gateway config
| Partly (Git holds exports).
| Export the registry on a schedule; keep gateway config in Git.
|===

A backup that has never been restored is an assumption. Schedule a restore test: restore the latest snapshot into an isolated
environment, run the retrieval part of the golden set, and compare the scores with the last release; record the time taken
against the recovery-time target in the runbook (see xref:ai/llmops/operational-governance.adoc[Operational Governance]).
Vector-store specifics are in xref:database/vector-rag/production-considerations.adoc[Production Considerations for Vector
Search and RAG].
