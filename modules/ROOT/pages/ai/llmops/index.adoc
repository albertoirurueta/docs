Building an LLM application is the easy half. The xref:ai/rag-systems/index.adoc[RAG Systems in Production] and
xref:ai/agents/index.adoc[AI Agents] sub-sections show how to build one that works on a good day. This sub-section is about
the other half: knowing whether it still works next week, after a prompt edit, a model update or a change of chunking; serving
it at a predictable latency and cost; releasing changes without surprising users; and finding out why an answer went wrong.

== What LLMOps is

*LLMOps* is the set of practices that take an LLM-based application from a working prototype to a service that is measured,
repeatable, observable and affordable. It covers five concerns that recur on every page:

* *Evaluation.* Turning "the answers look fine" into numbers that can fail a build: component and system evals, metrics,
  judges, golden sets, CI gates, and sampled evaluation of live traffic.
* *Serving.* Running models, your own or a provider's, behind a stable interface with predictable latency, throughput and
  failure behaviour.
* *Release engineering.* Versioning prompts and models separately from code, and shipping changes through shadow, canary and
  A/B stages with a rollback path.
* *Observability.* Traces, metrics and logs that explain a single bad answer and show the health of the whole fleet, using the
  OpenTelemetry GenAI conventions so that tools are interchangeable.
* *Cost and governance.* Token budgets, attribution, prompt and model registries, data operations, roles, runbooks and an
  audit trail.

=== LLMOps, MLOps and DevOps

LLMOps inherits DevOps (pipelines, infrastructure as code, monitoring) and MLOps (datasets, experiments, model registries),
but several assumptions of both stop holding:

[cols="2,3,3,3", options="header"]
|===
| Aspect | DevOps | MLOps | LLMOps

| The artefact that changes
| Code and configuration.
| Code, data and a trained model.
| Code, prompts, retrieval indexes, tool definitions and a model you usually did not train, which a vendor may change under you.

| What "correct" means
| Deterministic tests pass.
| A metric on a labelled test set clears a threshold.
| Open-ended text has many acceptable answers; correctness is estimated with rubrics, judges and human samples.

| Regression risk
| A commit.
| Retraining or data drift.
| A prompt edit, a vendor model update, a new chunking strategy or a changed tool description.

| Unit of cost
| Compute time.
| Training and serving compute.
| Tokens in and out per request, multiplied by traffic, which a loop in an agent can multiply further.

| Feedback signal
| Alerts and incidents.
| Ground-truth labels, often delayed.
| Thumbs, edits, regenerations and judge scores, noisy and biased but immediate.
|===

Concepts in this table, and the maturity levels below, are paraphrased from Chapter 2 of Aryan's _LLMOps_; the
<<_bibliography,bibliography>> lists it with the other books.

== The lifecycle loop

Every page fits one step of a loop that never ends, because the model, the data and the users all keep moving:

[mermaid]
....

  B[Build<br/>prompts, retrieval, tools] --> E[Evaluate<br/>offline: golden set, judges]

  D --> O[Observe<br/>traces, metrics, cost]
  O --> I[Improve<br/>feedback, drift, new cases]

== The maturity model

A useful way to decide what to do next is to ask which level your team is at. The levels below follow the three-step model
described in Aryan's _LLMOps_ (Chapter 2: ad hoc, managed and optimised), with the practices attached to each level taken
from this sub-section's pages.

image::ai-llmops-maturity-levels.svg["Three ascending steps. Level 0, ad hoc: prompts in code or notebooks, quality judged by eye, no traces, cost found on the invoice. Level 1, managed: prompts and models versioned, golden set in CI, traces and golden-signal metrics, gateway with keys and budgets, pinned model versions. Level 2, optimised: sampled online evaluation, feedback flowing into the golden set, shadow, canary and A/B releases, drift monitoring, cost attributed per tenant, metric owners and an audit trail."]

Moving from level 0 to level 1 is mostly the evaluation pages plus a gateway; moving from level 1 to level 2 is mostly online
evaluation, drift monitoring and governance. The self-assessment checklist is on
xref:ai/llmops/operational-governance.adoc[Operational Governance].

== The running scenario: DocsAssistant in production

Every page uses the DocsAssistant introduced in the RAG Systems sub-section, now treated as a production service. Its core
operation is the channel-agnostic one used by the other sub-sections, described on
xref:ai/rag-systems/serving-rag-as-an-api.adoc[Serving RAG as an API]:

[source,text]
----
ask(conversationId, userId, text) -> stream of { token | citation | done }
----

Around that core, the pages build the operating environment:

* a *golden evaluation set* built from the site's own pages and from real questions, versioned like code;
* *CI gates* that run the set on every change to a prompt, a model, the chunking or the index;
* a *vLLM or Ollama serving tier* behind a *LiteLLM gateway* that handles keys, routing, fallbacks and budgets;
* *OpenTelemetry traces* sent to Langfuse and to Prometheus and Grafana for dashboards and alerts;
* *sampled online judging* of live answers and a *feedback widget* in the documentation page;
* a *monthly cost report* attributed per tenant and feature.

Python covers the evaluation tooling (RAGAS, DeepEval, `openevals`, MLflow, the Langfuse SDK and the OpenTelemetry SDK), Java
covers Spring AI evaluators, Micrometer and JUnit gates, and configuration is YAML (GitHub Actions, Prometheus rules, vLLM and
LiteLLM). Every snippet is followed by a link to the official page it derives from.

=== Where the books are out of date

The requester-provided books are used for concepts only; where they differ from current tooling, the pages follow the
official documentation:

* *Serving.* _LLMOps_ (Aryan) leans on Jenkins and Triton-centred practice; current stacks use GitHub Actions with
  vLLM, SGLang and KServe, and TGI is in maintenance mode.
* *Experiment tracking and evaluation.* MLflow 3 now covers GenAI tracing, scorers, judges and a prompt registry;
  LangSmith judges come from `openevals` and `agentevals` rather than judge prompts pulled from the Hub; Langfuse is
  self-hostable and OpenTelemetry-based.
* *Observability conventions.* The `gen_ai.*` conventions post-date the books, are still at Development stability, and moved
  to their own repository.
* *Benchmarks.* The Hugging Face Open LLM Leaderboard is retired and MMLU is saturated; evaluation centres on task-specific
  evals, arenas and agent evals.
* *Spring AI.* _Spring AI in Action_ targets Spring AI 1.0; the pages use the 2.0.1 evaluator and observability APIs.
