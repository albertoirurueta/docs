== Containerising Ollama and vLLM

GPU containers need the host's NVIDIA driver plus the *NVIDIA Container Toolkit*, which lets Docker pass GPUs into
containers (`--gpus all` on the CLI, a device reservation in Compose). A DocsAssistant stack with Ollama for the
laptop-class models, vLLM for the large one, and an authenticating proxy as the only published port:

[source,yaml]
----
services:
  ollama:
    image: ollama/ollama:latest
    volumes:
      - ollama-models:/root/.ollama            # weights survive container restarts
    environment:
      OLLAMA_CONTEXT_LENGTH: "32768"
      OLLAMA_KEEP_ALIVE: "24h"
      OLLAMA_NO_CLOUD: "1"                     # no prompts to Ollama's cloud
    deploy:
      resources:
        reservations:
          devices:
            - driver: nvidia
              count: 1
              capabilities: [gpu]
    healthcheck:
      test: ["CMD", "ollama", "list"]
      interval: 30s
      timeout: 10s
      retries: 5
    # no "ports:" -- reachable only on the Compose network

  vllm:
    image: vllm/vllm-openai:latest
    command: ["meta-llama/Llama-3.1-8B-Instruct", "--max-model-len", "32768"]
    ipc: host
    environment:
      HF_TOKEN: ${HF_TOKEN}
      VLLM_API_KEY: ${VLLM_API_KEY}
    volumes:
      - hf-cache:/root/.cache/huggingface
    deploy:
      resources:
        reservations:
          devices:
            - driver: nvidia
              device_ids: ["1"]
              capabilities: [gpu]
    healthcheck:
      test: ["CMD", "python3", "-c", "import urllib.request; urllib.request.urlopen('http://localhost:8000/health')"]
      interval: 30s
      start_period: 600s                       # first start downloads and loads the weights

  gateway:
    image: nginx:stable
    ports:
      - "443:443"
    volumes:
      - ./nginx:/etc/nginx/conf.d:ro
      - ./tls:/etc/nginx/tls:ro
    depends_on:
      ollama: {condition: service_healthy}
      vllm: {condition: service_healthy}

volumes:
  ollama-models:
  hf-cache:
----

The `gateway` configuration is the nginx key check on
xref:ai/local-llms/llm-gateways.adoc#_authentication_in_front_of_local_servers[LLM Gateways]; a LiteLLM container
can take its place. Secrets come from the environment (`$\{HF_TOKEN}`), never from the file. Compose itself --
how services, networks and volumes work -- is covered on xref:backend/docker/compose-for-local-development.adoc[Compose
for Local Development] and xref:backend/docker/compose-in-practice.adoc[Compose in Practice], and
xref:backend/docker/storage-volumes-and-bind-mounts.adoc[Storage: Volumes, Bind Mounts and tmpfs] explains the
volume choices. See https://docs.ollama.com/docker[Ollama -- Docker],
https://docs.vllm.ai/en/stable/deployment/docker/[vLLM -- Docker] and
https://docs.docker.com/compose/how-tos/gpu-support/[Docker -- GPU support in Compose].

== Health checks

A model server is not ready when its process starts: it may still be downloading tens of gigabytes and then
loading them into GPU memory. Use each engine's own endpoint and give it a generous start period:

[cols="1,2",options="header"]
|===
| Engine | Health / readiness check

| Ollama | `GET /api/version` or `ollama list` answers once the server is up; models load on first use, so warm
  them with a request (`keep_alive: -1`) after start.
| llama.cpp | `GET /health` -- HTTP 503 ("Loading model") while loading, 200 once it can serve; public even with
  `--api-key`.
| vLLM | `GET /health`, and `GET /v1/models` lists the served model once loaded.
| NVIDIA NIM | `GET /v1/health/ready` (readiness) and `GET /v1/health/live` (liveness).
|===

In Kubernetes, map readiness to these endpoints and set a `startupProbe` long enough for the first load, so the
liveness probe does not kill a pod that is still reading weights. See the
https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md[llama.cpp server README],
https://docs.vllm.ai/en/stable/serving/online_serving/[vLLM -- Online serving] and
https://docs.ollama.com/api/introduction[Ollama -- API].

== Model-weight caching and volumes

Weights are the largest artefact in the system -- often larger than every container image combined -- so treat
them like data, not like image layers:

* Mount a *persistent volume* for each engine's cache: `/root/.ollama` (Ollama), `/root/.cache/huggingface`
  (vLLM, SGLang, llama.cpp's `-hf` cache), `/opt/nim/.cache` (NIM).
* *Pre-pull* in a controlled step (`ollama pull`, `hf download`, NIM's `download-to-cache`) rather than on the
  first user request, and keep a copy on internal storage so a pod reschedule or an air-gapped site does not depend
  on the public Hub.
* *Pin versions*: a model tag such as `llama3.1:8b` or a Hub repository's default branch can change underneath
  you. Pin the digest or a revision for reproducibility.
* Keep the cache on fast local disk (NVMe): load time from a network share dominates cold starts.

Do not bake large weights into images; it makes every image push, pull and scan slow. See
xref:backend/docker/image-best-practices-and-security.adoc[Image Best Practices and Supply-Chain Security] and
https://docs.vllm.ai/en/stable/deployment/k8s/[vLLM -- Kubernetes].

== Autoscaling limits

Autoscaling a GPU model server is much less elastic than scaling a web service:

* *Cold start is minutes, not seconds*: schedule a GPU node, pull the image, load tens of gigabytes into VRAM,
  and warm the caches. Scale on leading signals (queue depth, running requests, KV-cache usage), not on CPU, and
  keep a warm minimum.
* *GPUs are scarce and indivisible*: a replica needs a whole GPU (or several, with tensor parallelism); scaling
  from one to two doubles the cost in one step, and the capacity may simply not be available.
* *Scale-to-zero trades cost for a long first response*; acceptable for batch jobs, rarely for interactive use.
* *Within one replica*, continuous batching already absorbs load up to the goodput knee (see
  xref:ai/local-llms/inference-optimization.adoc#_ttft_tpot_throughput_and_goodput[goodput]); add replicas only
  past it.

The Kubernetes mechanics are covered on
xref:backend/docker/orchestration-swarm-and-kubernetes.adoc[Orchestration: Swarm Mode and Kubernetes].

== Securing endpoints

Treat a model server like a database: never on the public internet, always behind authentication.

* *Authentication*: most engines are unauthenticated by default, and vLLM's `--api-key` covers only its `/v1`-style
  routes. Terminate client authentication in a gateway or reverse proxy with per-client keys.
* *TLS*: terminate TLS at that proxy; inside a cluster, use the service mesh or mTLS if your platform provides it.
* *Network isolation*: only the gateway may reach the engines. In Kubernetes, a `NetworkPolicy` expresses that:

[source,yaml]
----
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: vllm-only-from-gateway
spec:
  podSelector:
    matchLabels: {app: docsassistant-vllm}
  policyTypes: [Ingress]
  ingress:
    - from:
        - podSelector:
            matchLabels: {app: llm-gateway}
      ports:
        - {protocol: TCP, port: 8000}
----

* *Egress*: block outbound traffic from the engines except to the model registry you mirror, so a compromised
  or misconfigured server cannot send prompts elsewhere (and disable engine cloud features such as Ollama's).
* *Model-management endpoints*: pulling, deleting and loading models (Ollama's `/api/pull` and `/api/delete`,
  Docker Model Runner's whole API, llama.cpp's `/models` router endpoints) must never be reachable by ordinary
  clients.

Prompt-injection, data-leakage and tool-abuse risks of the *applications* built on these models are covered in
xref:ai/agents/agent-guardrails-and-safety.adoc[Agent Guardrails & Safety] and the planned *AI Security &
Responsible AI* sub-section; container hardening in xref:backend/docker/security.adoc[Docker Security]. See
https://docs.vllm.ai/en/stable/usage/security/[vLLM -- Security].

== Monitoring

vLLM serves Prometheus metrics on `/metrics`; llama.cpp does so when started with `--metrics`. The metrics that
matter map directly onto the definitions on xref:ai/local-llms/inference-optimization.adoc[Inference
Optimization]:

[cols="2,2,2",options="header"]
|===
| Question | vLLM | llama.cpp

| Is it overloaded? | `vllm:num_requests_running` | `llamacpp:requests_processing`, `llamacpp:requests_deferred`
| Time to first token | `vllm:time_to_first_token_seconds` (histogram) | --
| Time per output token | `vllm:inter_token_latency_seconds` (histogram) | `llamacpp:predicted_tokens_seconds` (tokens/s)
| End-to-end latency | `vllm:e2e_request_latency_seconds` (histogram) | --
| Throughput | `rate(vllm:generation_tokens_total[5m])` | `rate(llamacpp:tokens_predicted_total[5m])`
| Memory pressure | `vllm:kv_cache_usage_perc` | --
|===

[source,yaml]
----
# prometheus.yml
scrape_configs:
  - job_name: vllm
    static_configs:
      - targets: ["vllm:8000"]
  - job_name: llamacpp
    static_configs:
      - targets: ["llamacpp:8080"]
----

A p95 TTFT alert, for example:

[source,promql]
----
histogram_quantile(0.95, sum by (le) (rate(vllm:time_to_first_token_seconds_bucket[5m]))) > 2
----

Add GPU metrics (utilisation, memory, temperature) from NVIDIA's DCGM exporter. Prometheus itself -- scraping,
PromQL, recording and alerting rules, Kubernetes monitoring -- is covered in
xref:database/prometheus/index.adoc[Prometheus & Monitoring], in particular
xref:database/prometheus/containers-and-kubernetes-monitoring.adoc[Containers & Kubernetes monitoring]. See the
https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md[llama.cpp server README] (`/metrics`) and
https://docs.vllm.ai/en/stable/[vLLM -- Documentation] (metrics).

== A cost-comparison method

This site quotes no prices -- they change monthly and differ per contract. What stays valid is the *method*. Over a
period (say a month), the cost of serving locally is

[stem]
++++
C_{local} = \frac{C_{hw}}{N_{months}} + P_{avg}\, h\, c_{kWh} + C_{ops} + C_{hosting}
++++

where stem:[C_{hw}] is the hardware price amortised over stem:[N_{months}], stem:[P_{avg}] the average power draw in
kW, stem:[h] the hours per month, stem:[c_{kWh}] the electricity price, stem:[C_{ops}] the people time to run it, and
stem:[C_{hosting}] rack or cloud-GPU rental. The hosted cost for the same traffic is

[stem]
++++
C_{hosted} = V_{in}\, p_{in} + V_{out}\, p_{out}
++++

with stem:[V_{in}], stem:[V_{out}] the monthly input and output tokens and stem:[p_{in}], stem:[p_{out}] the
provider's per-token prices (see xref:ai/llm-foundations/cost-latency-and-throughput.adoc[Cost, Latency &
Throughput]). Local serving breaks even when stem:[C_{local} = C_{hosted}], but only if the hardware can actually
carry the volume:

[stem]
++++
V_{out} \le \text{goodput}_{tokens/s} \times 3600\, h \times u
++++

where stem:[u] is the achievable utilisation (traffic is not flat). To use it: measure goodput on your hardware with
the harness on xref:ai/local-llms/vllm-and-sglang.adoc#_a_benchmark_harness[vLLM & SGLang], take your real token
volumes from the gateway's logs, plug in your own prices, and compare *equal quality* -- a local model that needs
more retries or more human correction is not cheaper. Privacy, residency and offline requirements often decide
the question before cost does (see xref:ai/local-llms/index.adoc[Running LLMs Locally]).

For a managed alternative that keeps data in a chosen cloud region without running the servers yourself, see
xref:cloud/azure/ai-data-and-iot-overview.adoc[AI, Data and IoT Services Overview] for Azure's AI services.
