== Why run locally

Hosted APIs are the default for good reasons -- the strongest models, no hardware, no operations. Running an
open-weight model yourself is worth it when one of these matters more:

* *Privacy and data residency* -- prompts, code and documents never leave your machine or your network. For
  regulated data, source code under strict policy, or customer data with residency rules, this can be the only
  acceptable option.
* *Cost at volume* -- a hosted API charges per token forever; a GPU you already own costs the same whether it
  serves a thousand requests or a million. At high, steady volume the balance can tip (the method, not prices, is
  on xref:ai/local-llms/running-local-llms-in-production.adoc#_a_cost_comparison_method[Running Local LLMs in
  Production]).
* *Offline use* -- on a plane, in an air-gapped site, or when the provider has an outage.
* *Latency* -- no network round trip, no shared queue; a small local model can answer faster than a large remote
  one.
* *Control* -- a pinned model that never changes under you, no rate limits, no deprecations, and the freedom to
  quantize, fine-tune or constrain it.

== The trade-offs

* *Quality gap* -- the best open-weight models are strong, but a model that fits a laptop is not a frontier model.
  Evaluate on your own tasks; pick the task, then the model (see
  xref:ai/local-llms/open-weight-models.adoc[Open-Weight Models]).
* *Operations burden* -- you install, update, secure, monitor and scale the servers. Most local engines are
  unauthenticated by default, which makes security your job from day one.
* *Hardware* -- memory decides which models run at all, bandwidth decides how fast (see
  xref:ai/local-llms/hardware-sizing.adoc[Hardware Sizing]); a GPU server is a capital purchase with a lead time.

A common outcome is a mix: local models for private data, bulk and offline work, hosted models for the hardest
tasks -- with a gateway routing between them (see xref:ai/local-llms/llm-gateways.adoc[LLM Gateways]).

== Choosing an engine

[cols="1,2,2",options="header"]
|===
| Situation | Engine | Why

| A laptop or workstation, one user | xref:ai/local-llms/ollama.adoc[Ollama], LM Studio or, on Apple silicon, MLX-LM
  (see xref:ai/local-llms/desktop-runners.adoc[Desktop Runners]) | One install, automatic GPU offload, a GUI (LM
  Studio) or CLI, OpenAI- and Anthropic-compatible APIs.
| A single GPU, full control | xref:ai/local-llms/llama-cpp.adoc[llama.cpp] or Ollama | Every flag exposed:
  offload, context and slots, KV-cache types, speculative decoding; any GGUF.
| Inside a Docker workflow | Docker Model Runner (see xref:ai/local-llms/desktop-runners.adoc[Desktop Runners]) |
  Models as Compose dependencies.
| A multi-user GPU server | xref:ai/local-llms/vllm-and-sglang.adoc[vLLM or SGLang] | Continuous batching,
  PagedAttention / RadixAttention, tensor parallelism, FP8 and 4-bit checkpoints.
| An enterprise with NVIDIA AI Enterprise | xref:ai/local-llms/nvidia-nim.adoc[NVIDIA NIM] | Pre-built, tuned,
  supported containers per model.
|===

== DocsAssistant, locally

*DocsAssistant*, the running example of this site's AI and vector-database sections, already runs its models
locally: Ollama serves `llama3.1:8b` for chat and `nomic-embed-text` for embeddings. This sub-section takes that
setup further. Every engine page ends with the *same three clients* -- `curl` against the OpenAI-compatible
endpoint, Python (the `openai` SDK with a `base_url`, then LangChain), and Spring AI -- so moving DocsAssistant from
Ollama to llama.cpp, vLLM or NIM is a base-URL change. The integration pages then point GitHub Copilot, Claude
Code and the open coding assistants at the same local models.
