This page describes NVIDIA NIM for LLMs as of 2026-09-28, with Python 3.12 (`openai` 3.20.0) and Spring AI 2.0.1
for the clients (see the xref:ai/local-llms/index.adoc[Running LLMs Locally] baseline). NVIDIA's documentation site
(`docs.nvidia.com`) could not be reached from the environment used to check this page, so every command below was
taken from NVIDIA's own deployment examples in the https://github.com/NVIDIA/nim-deploy[NVIDIA/nim-deploy]
repository. Check the current NIM release, image tags and licence terms on the
https://docs.nvidia.com/nim/large-language-models/latest/introduction.html[NIM for LLMs documentation] before you
rely on them.

*NIM* ("NVIDIA Inference Microservices") packages an open model together with an optimised inference engine and
an OpenAI-compatible API server in one container. At start-up, the container detects the GPUs and picks a
matching *model profile* -- precision, tensor-parallel degree and engine (for example a TensorRT-LLM or a vLLM profile) -- then
downloads the corresponding optimised weights. The result is roughly what you would build yourself from
xref:ai/local-llms/vllm-and-sglang.adoc[vLLM & SGLang] plus quantization and tuning, but pre-assembled, validated
and supported by NVIDIA.

== NIM containers for LLMs

Each model has its own image under `nvcr.io/nim/<publisher>/<model>`, for example
`nvcr.io/nim/meta/llama3-8b-instruct`, `nvcr.io/nim/meta/llama-3.1-8b-instruct` or
`nvcr.io/nim/nvidia/llama-3.3-nemotron-super-49b-v1`. Images and the weights they download come from NVIDIA's NGC
registry, which requires an *NGC API key* (created on https://build.nvidia.com/[build.nvidia.com] or in NGC):

[source,shell]
----
export NGC_API_KEY=...           # from your secrets manager; never commit it
echo "$NGC_API_KEY" | docker login nvcr.io --username '$oauthtoken' --password-stdin
----

The literal username `$oauthtoken` (in single quotes, so the shell does not expand it) is how NGC accepts an API
key as a password. See the https://github.com/NVIDIA/nim-deploy[nim-deploy] examples.

== Running a NIM

The weights are cached in a host directory mounted at `/opt/nim/.cache`, so they are downloaded only once, and the
API listens on port 8000:

[source,shell]
----
export LOCAL_NIM_CACHE=~/.cache/nim
mkdir -p "$LOCAL_NIM_CACHE"

docker run -it --rm \
  --runtime=nvidia --gpus all --shm-size=16GB \
  -e NGC_API_KEY \
  -v "$LOCAL_NIM_CACHE:/opt/nim/.cache" \
  -u "$(id -u)" \
  -p 127.0.0.1:8000:8000 \
  nvcr.io/nim/meta/llama3-8b-instruct:1.0.0
----

`-e NGC_API_KEY` passes the variable through from your shell without writing its value on the command line. The
container needs the NVIDIA Container Toolkit (see
xref:ai/local-llms/running-local-llms-in-production.adoc#_containerising_ollama_and_vllm[containerising]). To see
which profiles the container would choose on your hardware, run the image's `list-model-profiles` utility instead
of the server; `NIM_MODEL_PROFILE` pins one (for example `vllm-fp16-tp2`).

Readiness and liveness endpoints are `GET /v1/health/ready` and `GET /v1/health/live`; wait for `ready` before
sending traffic:

[source,shell]
----
until curl -sf http://localhost:8000/v1/health/ready >/dev/null; do sleep 5; done
curl http://localhost:8000/v1/models
----

NVIDIA's deployment examples call the API without any credential, so treat it as unauthenticated: publish the port
on loopback or a private network only, and front it with an authenticating proxy or gateway (see
xref:ai/local-llms/llm-gateways.adoc#_authentication_in_front_of_local_servers[authentication in front of local
servers]). See https://github.com/NVIDIA/nim-deploy[NVIDIA/nim-deploy] (Helm charts and cloud examples) and the
https://docs.nvidia.com/nim/large-language-models/latest/introduction.html[NIM for LLMs documentation].

== The OpenAI API

A running NIM exposes `/v1/chat/completions`, `/v1/completions` and `/v1/models` in the OpenAI shape, so the
client snippets below -- and every tool on this site that accepts an OpenAI base URL -- work unchanged. The `model`
field is the name reported by `/v1/models` (for the image above, `meta/llama3-8b-instruct`).

[source,shell]
----
curl http://localhost:8000/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model": "meta/llama3-8b-instruct",
       "messages": [{"role": "user", "content": "What is retrieval-augmented generation?"}],
       "max_tokens": 256}'
----

See the https://docs.nvidia.com/nim/large-language-models/latest/introduction.html[NIM for LLMs documentation].

== Licensing: NVIDIA AI Enterprise

NIM is a component of *NVIDIA AI Enterprise* (NVAIE), NVIDIA's commercially licensed software platform. NVIDIA's
deployment guides state that pulling NIM artifacts directly from NGC for self-hosted deployment requires an NVIDIA
AI Enterprise licence and an NGC API key; cloud marketplaces offer NVAIE-licensed images as an alternative
purchasing route. Terms for development and evaluation use, and the prices, are set by NVIDIA and change; this page
quotes neither, so read the current terms on NVIDIA's site before planning around them. See the
https://github.com/NVIDIA/nim-deploy[nim-deploy] cloud deployment guides and the
https://docs.nvidia.com/nim/large-language-models/latest/introduction.html[NIM for LLMs documentation].

== When an enterprise needs NIM

NIM and a self-assembled open stack serve the same OpenAI-compatible API; the difference is who owns the work in
between:

[cols="1,2,2",options="header"]
|===
| Concern | Self-assembled (vLLM / SGLang) | NIM

| Engine tuning per GPU | You choose quantization, parallelism and flags | Pre-built profiles picked at start-up
| Model support | Any Hugging Face checkpoint the engine supports | The models NVIDIA packages as NIMs
| Updates and CVEs | You track engine releases and base images | NVIDIA ships patched images
| Support | Community | Enterprise support under NVAIE
| Cost | GPU and people | GPU, people and an NVAIE licence
| Lock-in | None beyond the model | NVIDIA GPUs and the NGC registry
|===

NIM makes sense when an organisation already licenses NVIDIA AI Enterprise, runs NVIDIA data-centre GPUs, and
wants a supported, validated artefact for regulated or production use rather than maintaining engine flags itself.
It is overkill for a laptop, for AMD or Apple hardware, or for a team that is comfortable operating vLLM. A managed
cloud service is the other alternative; see
xref:cloud/azure/ai-data-and-iot-overview.adoc[AI, Data and IoT Services Overview] for Azure's options.

== Client snippets

*curl*: see <<_the_openai_api,The OpenAI API>> above.

*Python*:

[source,python]
----
from openai import OpenAI
from langchain_openai import ChatOpenAI

client = OpenAI(base_url="http://localhost:8000/v1", api_key="not-used")  # the proxy in front holds the real key
reply = client.chat.completions.create(
    model="meta/llama3-8b-instruct",
    messages=[{"role": "user", "content": "What is retrieval-augmented generation?"}],
    max_tokens=256,
)
print(reply.choices[0].message.content)

chat = ChatOpenAI(base_url="http://localhost:8000/v1", api_key="not-used", model="meta/llama3-8b-instruct")
----

*Spring AI* -- the OpenAI starter (`spring-ai-starter-model-openai`):

[source,yaml]
----
spring:
  ai:
    openai:
      base-url: http://localhost:8000
      api-key: not-used
      chat:
        model: meta/llama3-8b-instruct
----

The `ChatClient` code is the same as on xref:ai/local-llms/ollama.adoc#_client_snippets[Ollama]. See
https://github.com/openai/openai-python[openai-python],
https://docs.langchain.com/oss/python/integrations/chat/openai[LangChain -- ChatOpenAI] and
https://docs.spring.io/spring-ai/reference/api/chat/openai-chat.html[Spring AI -- OpenAI Chat].
