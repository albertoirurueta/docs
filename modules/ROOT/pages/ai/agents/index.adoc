== What an agent is

An *agent* is a system in which a language model decides, step by step, what to do next -- which tool to call,
with what arguments, and when the task is finished -- and the runtime carries those decisions out and feeds the
results back, in a loop, until the model stops or a limit stops it. The defining property is that the *path* is
chosen by the model at run time, not written in advance by a developer.

This sub-section treats agents as an engineering discipline independent of any one framework: each concept is
explained once and then shown in three stacks -- *LangGraph / LangChain 1.x* (Python), *LangChain4j* (Java without
Spring) and *Spring AI* (Spring Boot) -- with an "In other frameworks" table for the OpenAI Agents SDK, the Claude
Agent SDK, Microsoft Agent Framework and CrewAI. Framework-specific depth (every API, configuration and deployment
detail) belongs to the xref:ai/langchain/index.adoc[LangChain] and xref:ai/spring-ai/index.adoc[Spring AI] sub-sections; building MCP servers belongs to the
xref:ai/mcp/index.adoc[Model Context Protocol (MCP)] sub-section; and agentic retrieval is already covered by
xref:database/vector-rag/agentic-rag.adoc[Agentic RAG], which these pages link rather than repeat.

Every example extends *DocsAssistant*, the running example of the xref:database/vector-rag/index.adoc[Vector
Databases & RAG] section and of xref:ai/llm-foundations/index.adoc[LLM Foundations & Prompting], into an agent:
it answers questions about this site, searches the docs as a tool, opens a GitHub issue when a page is wrong -- a
write action that needs human approval -- and hands proposed fixes to a *reviewer* agent.

== Workflows vs. agents, and when not to build an agent

A *workflow* composes model calls and tools along paths the developer wrote in code; an *agent* lets the model
choose the path. Workflows are predictable, cheaper, faster and easier to test; agents are flexible where the
steps cannot be known in advance, at the cost of latency, tokens, and failure modes that are harder to foresee.

*Do not build an agent* when:

* one well-prompted model call, with good retrieval, already does the job -- most "chat with your docs" features
  are this;
* the steps are known in advance -- a fixed sequence, a classification followed by a fixed handler, a fan-out --
  which is a workflow (see xref:ai/agents/workflow-patterns.adoc[Workflow Patterns]);
* mistakes are expensive and hard to undo, and a human cannot review each action;
* the latency or cost budget cannot absorb a variable number of model calls;
* you cannot yet measure whether it works (see xref:ai/agents/agent-evaluation.adoc[Agent Evaluation]).

Build an agent when the task is open-ended, the next step genuinely depends on what the last one found, the tools
are safe or gated, and the value of solving the harder cases justifies the cost. Start with the simplest system
that could work, measure it, and add autonomy only where it demonstrably helps.

== The five components

.The five components of an LLM agent
image::ai-agents-components.svg["The five components of an LLM agent: at the centre, the model, which reasons and decides; around it, the orchestration loop of perceive, reason, act and observe with its planning, routing, stop conditions and limits; on the left, instructions (role, goals, rules, output format) and memory (short-term thread state, long-term semantic, episodic and procedural memory); on the right, tools (read tools such as docs_search and an approval-gated write tool, github_open_issue); and below, the environment the agent acts in: users and reviewers, the documentation corpus, GitHub and other agents.",width=760,role=text-center]

. *Model* -- the LLM that reasons and decides; its capability sets the ceiling of everything else (see
  xref:ai/llm-foundations/choosing-a-model.adoc[Choosing a Model]).
. *Instructions* -- the role or persona, goals, rules and output format: the system prompt and anything that shapes
  behaviour before the first step.
. *Tools* -- the actions the agent can take and the information it can fetch (see
  xref:ai/agents/tool-design.adoc[Tool Design]).
. *Memory* -- what the agent knows beyond the current prompt: the thread's history, and long-term knowledge about
  users, past experiences and procedures (see xref:ai/agents/memory.adoc[Memory]).
. *Orchestration* -- the loop that ties them together: how the next step is chosen, how plans are made and
  revised, when to stop, and the limits that bound it (see
  xref:ai/agents/agent-loop-and-architectures.adoc[Agent Loop & Architectures] and
  xref:ai/agents/planning.adoc[Planning]).

The model, tools, memory and orchestration split follows the component model in Albada's *Building Applications
with AI Agents*; making instructions (Lanham's "profile / persona") a component of its own follows the five-part
framing in Lanham's *AI Agents in Action* -- see the bibliography below.

== The autonomy ladder

Autonomy is a dial, not a switch, and the right setting is usually different for each action an agent can take:

[cols="1,3", options="header"]
|===
| Level | What the system does

| Assist
| The model drafts; a person decides and acts. (A chat assistant.)

| Suggest (confirm before execute)
| The agent proposes a concrete action; a person approves, edits or rejects it before it runs.

| Act with oversight
| The agent acts on its own and reports; a person can review, undo and stop it.

| Autonomous
| The agent acts on its own within budgets and policies, and escalates only on exceptions.
|===

DocsAssistant *acts* on reads (searching the docs) and only *suggests* on its one write (opening an issue). Moving
an action up the ladder should follow evidence -- how often reviewers approve its suggestions unchanged -- and moving
it down must be a configuration change (see xref:ai/agents/human-in-the-loop.adoc#_the_autonomy_slider[the autonomy
slider]).
