== Choosing a runtime

The Hub stores most models as PyTorch safetensors; a browser or phone cannot run those directly. Each platform therefore
relies on a converted artefact and a runtime that can execute it.

    Hub --> FL["Flutter<br/>flutter_gemma, llama_cpp_dart, onnxruntime"]

== Transformers.js in the browser

https://huggingface.co/docs/transformers.js/index[Transformers.js] is the JavaScript counterpart of the Python `transformers`
library: the same task names, run by ONNX Runtime Web in the browser (and ONNX Runtime for Node.js). It is published as
`@huggingface/transformers`; version 4.x is current. Models come from the Hub as ONNX files, mostly under the
https://huggingface.co/onnx-community[`onnx-community`] organisation, and are downloaded on first use.

.Terminal: install Transformers.js
[source,bash]
----
npm install @huggingface/transformers
----

.JavaScript: a pipeline on WebGPU with 4-bit weights
[source,javascript]
----
import { pipeline } from '@huggingface/transformers';

const pipe = await pipeline('sentiment-analysis', 'Xenova/distilbert-base-uncased-finetuned-sst-2-english', {
  device: 'webgpu',
  dtype: 'q4',
});
const result = await pipe('I love running models offline!');
----

Official reference: https://huggingface.co/docs/transformers.js/index[Transformers.js documentation].

=== WebGPU versus WASM

The `device` option picks the ONNX Runtime Web execution provider. `'webgpu'` runs the graph on the GPU and is what makes
an LLM or a large speech model usable; the documentation still calls WebGPU experimental in some browsers, so a real app
must detect support and fall back. The default backend is WASM on the CPU, which runs everywhere but is slow for large
models.

.JavaScript: choosing the device by feature detection
[source,javascript]
----
const hasWebGPU = 'gpu' in navigator && (await navigator.gpu.requestAdapter()) !== null;

const options = hasWebGPU
  ? { device: 'webgpu', dtype: 'q4f16' }  // needs shader-f16 support on the adapter
  : { device: 'wasm', dtype: 'q8' };      // the WASM default
----

The `q4f16` choice above assumes the GPU adapter supports 16-bit floats; if it does not, use `q4` or `fp32`. The pipeline
options are documented in the
https://huggingface.co/docs/transformers.js/api/pipelines[Transformers.js pipelines reference]; the browser API is
specified by https://www.w3.org/TR/webgpu/[WebGPU (W3C)].

=== dtype options

Every ONNX repository published for Transformers.js ships several precisions in its `onnx/` folder
(for example `model.onnx`, `model_fp16.onnx`, `model_q4.onnx`, `model_q4f16.onnx`, `model_quantized.onnx`). The `dtype`
option selects which file is fetched.

.dtype values documented for Transformers.js
[cols="1,3",options="header"]
|===
| dtype | Meaning

| `fp32`
| Full precision; the default on WebGPU.

| `fp16`
| Half precision; halves the download of `fp32` but needs GPU support for 16-bit floats.

| `q8`
| 8-bit quantisation; the default on WASM.

| `q4`
| 4-bit quantisation; the smallest download of the documented values, with some quality loss.

| `q4f16`
| 4-bit weights with 16-bit activations; used in the `onnx-community` LLM model cards for WebGPU. Only files that exist in the repository can be selected.
|===

Because download size is what the user waits for, estimate it before picking a model. With stem:[N] parameters stored at
stem:[b] bits:

[stem]
++++
S \approx \frac{N \cdot b}{8}\ \text{bytes}
++++

A 0.6-billion-parameter model is therefore roughly 2.4 GB at 32 bits and roughly 0.3 GB at 4 bits, before tokenizer files,
embeddings that stay in higher precision and runtime memory (activations and the KV cache of a language model, see
xref:ai/local-llms/hardware-sizing.adoc[Hardware Sizing]). The repository's file list is the authority: add up the files
that your `dtype` selects. Quantisation itself is covered in
xref:ai/local-llms/quantization-for-inference.adoc[Quantization for Inference] and, for producing the files, in
xref:ai/hugging-face/conversion-and-quantization.adoc[Conversion & Quantization].

=== Caching and offline use

By default, Transformers.js stores downloaded model files with the browser's Cache API (the `env.useBrowserCache` setting,
enabled when available), and ONNX Runtime's WASM binaries are cached too (`env.useWasmCache`). The first load is
therefore a network download and later loads come from the cache, which is what makes "goes offline" possible after one
online visit. The `env` object also lets you serve models from your own origin, which avoids the Hub entirely.

.JavaScript: serve models from your own server only
[source,javascript]
----
import { env } from '@huggingface/transformers';

env.allowRemoteModels = false;        // never contact the Hub
env.allowLocalModels = true;          // look under env.localModelPath
env.localModelPath = '/models/';      // a path on your own origin
----

Browser storage can be evicted and quotas differ per browser, so a production app should ask the browser for persistent
storage and show download progress. Official reference:
https://huggingface.co/docs/transformers.js/api/env[Transformers.js -- env] and the
https://developer.mozilla.org/en-US/docs/Web/API/Cache[Cache API (MDN)].

== DocsAssistant goes offline in JavaScript

Model loading and inference block the thread that runs them for seconds, so the four tasks run in a *Web Worker*: the page
posts a message, the worker loads the pipeline once, runs it and posts the result back. The worker below loads each
pipeline lazily and keeps it in a module-level cache, so a second question reuses the loaded models.

.worker.js: lazy, cached pipelines in a Web Worker
[source,javascript]
----
import { pipeline } from '@huggingface/transformers';

const device = 'gpu' in navigator ? 'webgpu' : 'wasm';
const loaded = new Map();

function get(task, model, options = {}) {
  const key = `${task}:${model}`;
  if (!loaded.has(key)) {
    loaded.set(key, pipeline(task, model, {
      device,
      progress_callback: (p) => self.postMessage({ type: 'progress', task, p }),
      ...options,
    }));
  }
  return loaded.get(key);
}

self.onmessage = async ({ data }) => {
  const { id, step, payload } = data;
  try {
    self.postMessage({ id, result: await steps[step](payload) });
  } catch (error) {
    self.postMessage({ id, error: String(error) });
  }
};

const steps = {};  // filled in below
----

Official reference: https://huggingface.co/docs/transformers.js/pipelines[Transformers.js -- pipeline API] and
https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API[Web Workers API (MDN)].

=== Transcribe

The `automatic-speech-recognition` pipeline takes mono audio at the model's sampling rate (16 kHz for Whisper), either a
URL or a `Float32Array`. The microphone recording is decoded and resampled in the page, then transferred to the worker.

.worker.js: transcribe a spoken question
[source,javascript]
----
steps.transcribe = async ({ audio }) => {   // Float32Array, 16 kHz, mono
  const asr = await get('automatic-speech-recognition', 'onnx-community/whisper-tiny.en', {
    dtype: 'q4',
  });
  const { text } = await asr(audio);
  return text;
};
----

Official reference: https://huggingface.co/docs/transformers.js/api/pipelines#module_pipelines.AutomaticSpeechRecognitionPipeline[AutomaticSpeechRecognitionPipeline].
Swapping in Moonshine (`onnx-community/moonshine-base-ONNX`) only changes the model id.

=== Answer

The `text-generation` pipeline accepts a chat message list. A `TextStreamer` forwards tokens as they are produced, so the
page can render the answer progressively. The dtype and device below follow the model card.

.worker.js: answer with a small LLM and stream tokens
[source,javascript]
----
import { TextStreamer } from '@huggingface/transformers';

steps.answer = async ({ question, context }) => {
  const generator = await get('text-generation', 'onnx-community/Qwen3-0.6B-ONNX', {
    dtype: 'q4f16',
  });
  const messages = [
    { role: 'system', content: 'Answer only from the provided documentation excerpts.' },
    { role: 'user', content: `Excerpts:\n${context}\n\nQuestion: ${question}` },
  ];
  const output = await generator(messages, {
    max_new_tokens: 256,
    do_sample: false,
    streamer: new TextStreamer(generator.tokenizer, {
      skip_prompt: true,
      skip_special_tokens: true,
      callback_function: (token) => self.postMessage({ type: 'token', token }),
    }),
  });
  return output[0].generated_text.at(-1).content;
};
----

Official reference: https://huggingface.co/docs/transformers.js/api/pipelines#module_pipelines.TextGenerationPipeline[TextGenerationPipeline]
and the model card https://huggingface.co/onnx-community/Qwen3-0.6B-ONNX[onnx-community/Qwen3-0.6B-ONNX]. The context excerpts
come from the retrieval step described in xref:database/vector-rag/generating-embeddings-in-practice.adoc[Generating
Embeddings in Practice]. Qwen3 models can emit a reasoning block before the answer; strip it or disable thinking mode as
the model card describes.

=== Speak

`kokoro-js` wraps the Kokoro ONNX model and its voice packs for the browser (WebGPU or WASM) and Node.js. It is a separate
package that uses Transformers.js internally.

.Terminal: install kokoro-js
[source,bash]
----
npm install kokoro-js
----

.worker.js: speak the answer with Kokoro
[source,javascript]
----
import { KokoroTTS } from 'kokoro-js';

let tts;

steps.speak = async ({ text }) => {
  tts ??= await KokoroTTS.from_pretrained('onnx-community/Kokoro-82M-v1.0-ONNX', {
    dtype: 'q8',      // documented options: fp32, fp16, q8, q4, q4f16
    device: 'wasm',   // "wasm" or "webgpu" in the browser; the README advises fp32 with webgpu
  });
  const audio = await tts.generate(text, { voice: 'af_heart' });
  return { samples: audio.audio, sampleRate: audio.sampling_rate };
};
----

Official reference: https://github.com/hexgrad/kokoro/tree/main/kokoro.js[kokoro-js README]. The page plays the returned
samples with the Web Audio API (`AudioContext` and an `AudioBuffer`). For long answers `tts.stream()` with a
`TextSplitterStream` produces audio sentence by sentence. Kokoro and Piper are compared in
xref:ai/hugging-face/speech-models.adoc[Speech Models: STT & TTS].

=== Classify a screenshot

SigLIP 2 scores an image against labels supplied at call time, so the set of screen types can change without retraining.

.worker.js: zero-shot classification of a screenshot
[source,javascript]
----
steps.classify = async ({ imageUrl }) => {
  const classifier = await get(
    'zero-shot-image-classification',
    'onnx-community/siglip2-base-patch16-224-ONNX',
    { dtype: 'q4' },
  );
  return classifier(imageUrl, ['a settings page', 'an error dialog', 'a code editor', 'a login form']);
};
----

Official reference: https://huggingface.co/docs/transformers.js/api/pipelines#module_pipelines.ZeroShotImageClassificationPipeline[ZeroShotImageClassificationPipeline].
The model card ships no snippet, so confirm that your installed version loads this repository and that the `q4` files
exist, and fall back to `fp32` if not. To *describe* a screenshot in free text instead, use a small vision-language model
such as SmolVLM, loaded with the model classes shown on the
https://huggingface.co/HuggingFaceTB/SmolVLM-256M-Instruct[SmolVLM-256M-Instruct] card; see
xref:ai/hugging-face/vision-models.adoc[Vision Models] for the catalogue.

=== Calling the worker from the page

.main.js: one promise-based call per step
[source,javascript]
----
const worker = new Worker(new URL('./worker.js', import.meta.url), { type: 'module' });
const pending = new Map();
let next = 0;

worker.onmessage = ({ data }) => {
  if (data.type) return;                       // progress or token events: update the UI
  const { resolve, reject } = pending.get(data.id);
  pending.delete(data.id);
  data.error ? reject(new Error(data.error)) : resolve(data.result);
};

export function run(step, payload) {
  return new Promise((resolve, reject) => {
    const id = next++;
    pending.set(id, { resolve, reject });
    worker.postMessage({ id, step, payload });
  });
}

const text = await run('transcribe', { audio });
const answer = await run('answer', { question: text, context });
const speech = await run('speak', { text: answer });
----

Official reference: https://developer.mozilla.org/en-US/docs/Web/API/Worker/postMessage[Worker.postMessage (MDN)].

== ONNX Runtime Web

https://onnxruntime.ai/docs/tutorials/web/[ONNX Runtime Web] (`onnxruntime-web`, 1.30.0) is the engine under
Transformers.js. Use it directly when you have a single ONNX graph, such as a classifier you exported yourself, and do not
need tokenizers or pipelines. Its execution providers are WebGPU, WebNN, WebGL (limited operator support) and WASM, which
supports every ONNX operator. The WebGPU provider is reached through a dedicated bundle import.

.JavaScript: an InferenceSession on WebGPU with a WASM fallback
[source,javascript]
----
import * as ort from 'onnxruntime-web/webgpu';

const session = await ort.InferenceSession.create('/models/classifier.onnx', {
  executionProviders: ['webgpu', 'wasm'],   // tried in order
});

const input = new ort.Tensor('float32', new Float32Array(1 * 3 * 224 * 224), [1, 3, 224, 224]);
const outputs = await session.run({ [session.inputNames[0]]: input });
const scores = outputs[session.outputNames[0]].data;
----

Official reference: https://onnxruntime.ai/docs/tutorials/web/ep-webgpu.html[ONNX Runtime Web -- Using WebGPU] and
https://onnxruntime.ai/docs/api/js/[ONNX Runtime JavaScript API]. The list of execution providers with a fallback order is
an ONNX Runtime feature that also applies on servers; see the ONNX Runtime section of
xref:ai/hugging-face/python-backends.adoc[Python Backends]. Preprocessing (resizing, normalisation) is your responsibility
and must match the model card exactly.

== ExecuTorch across platforms

https://docs.pytorch.org/executorch/stable/index.html[ExecuTorch] is PyTorch's on-device runtime for iOS, Android, desktop and embedded
targets. A model is exported once from PyTorch with `torch.export`, lowered to a hardware backend and saved as a `.pte`
file; the same file format is loaded by the iOS, Android and C++ runtimes, with backend choice (for example XNNPACK for
CPU) selected at export time. This is the route taken by `react-native-executorch` below. Android specifics are in
xref:ai/hugging-face/android.adoc[Android]; the format's place among others is in xref:ai/hugging-face/model-formats.adoc[Model Formats].

.Python: export a model to a .pte file with the XNNPACK backend
[source,python]
----
import torch
from executorch.backends.xnnpack.partition.xnnpack_partitioner import XnnpackPartitioner
from executorch.exir import to_edge_transform_and_lower

model = MyModel().eval()                       # any torch.nn.Module
example_inputs = (torch.randn(1, 3, 224, 224),)

exported = torch.export.export(model, example_inputs)
program = to_edge_transform_and_lower(exported, partitioner=[XnnpackPartitioner()]).to_executorch()

with open("model.pte", "wb") as f:
    f.write(program.buffer)
----

Official reference: https://docs.pytorch.org/executorch/stable/getting-started.html[ExecuTorch -- Getting Started]. Verify the
import paths against the release you install, since the export API has changed between minor versions. Only models whose
operators export cleanly can be converted; for large language models, prefer a ready-made `.pte` from the maintainers'
Hub collections over exporting your own.

== React Native

The JavaScript bundle of a React Native app cannot run these models; the work is done by native libraries exposed through
hooks or native modules (see
xref:apps/react-native/native-modules-and-components.adoc[Native Modules and Components] and
xref:apps/react-native/index.adoc[React Native]). Two libraries cover most DocsAssistant needs.

=== llama.rn

https://github.com/mybigday/llama.rn[llama.rn] binds llama.cpp, so it runs GGUF models (see
xref:ai/local-llms/llama-cpp.adoc[llama.cpp]). Install it with `npm install llama.rn`. The model file must already be on
the device's file system; download it with a file-system library, following the patterns in
xref:apps/react-native/storage-and-offline.adoc[Storage and Offline].

.TypeScript: load a GGUF model and stream a completion
[source,typescript]
----
import { initLlama } from 'llama.rn';

const context = await initLlama({
  model: modelPath,        // a file:// path to a .gguf file on the device
  use_mlock: true,
  n_ctx: 2048,
  n_gpu_layers: 99,        // offload layers where a GPU backend is available
});

const result = await context.completion(
  {
    messages: [
      { role: 'system', content: 'Answer from the documentation excerpts only.' },
      { role: 'user', content: question },
    ],
    n_predict: 256,
    stop: ['</s>', '<|end|>', '<|eot_id|>'],
  },
  (data) => appendToken(data.token),   // partial-completion callback
);
console.log(result.text);
----

Official reference: https://github.com/mybigday/llama.rn[llama.rn README]. Option names follow the README at the time of
writing; because the latest npm tag was a release candidate on 2026-09-30, compare them with the README of the version you
install. Release the context when the screen is closed to free native memory.

=== react-native-executorch

https://docs.swmansion.com/react-native-executorch/[react-native-executorch] (0.10.4) wraps ExecuTorch in task-specific
hooks. Its documentation lists requirements that matter for project planning: the New Architecture enabled, a recent
React Native or Expo SDK with a development build (Expo Go cannot load native code), and recent iOS and Android minimum
versions. Install it with its peer dependencies as the official getting-started page lists them (that page's command is unpinned, while the
command below follows the package's declared peer ranges).

.Terminal: install react-native-executorch and its peer dependencies
[source,bash]
----
npm install react-native-executorch react-native-worklets@^0.10.0 react-native-blob-util@^0.24.0
----

The hooks download the `.pte` model on first use and expose readiness and progress. The two snippets below use the
`useLLMChatSession` and `useSpeechToText` hooks with entries of the `models` registry, as the 0.10 documentation shows. Hook
and constant names were reorganised between releases (the 0.8.x documentation used `useLLM` with constants such as
`LLAMA3_2_1B`), so copy the snippet from the documentation of the version you install. The documented requirements for 0.10 are
the New Architecture, React Native 0.83 or newer (or Expo SDK 55 or newer with a development build), iOS 17 or newer, Android 13
or newer and a `react-native-worklets` release in the range the package declares (`>=0.10.0 <0.13.0`), so the
command above pins it, and the package also declares `react-native-blob-util` `^0.24.0` as a peer, while the newest releases of
both on npm on 2026-09-30 were outside those ranges.

.TypeScript: answer with useLLMChatSession
[source,typescript]
----
import { useState } from 'react';
import { models, useLLMChatSession } from 'react-native-executorch';

function Answer() {
  const [answer, setAnswer] = useState('');
  const session = useLLMChatSession(models.llm.LFM2_5_1_2B.DEFAULT, {
    initialMessages: [{ role: 'system', content: 'Answer from the documentation excerpts only.' }],
    generationConfig: { temperature: 0.2, maxNewTokens: 256 },
  });

  const ask = async (question: string) => {
    if (!session.isReady || !session.sendMessage) return;
    setAnswer('');
    await session.sendMessage(question, (token) => setAnswer((prev) => prev + token));
  };

  // render session.downloadProgress while loading, then the streamed answer
}
----

=== onnxruntime-react-native

For a single ONNX graph, `onnxruntime-react-native` (1.24.3 on 2026-09-30) is the React Native counterpart of ONNX Runtime
Web and uses the same `InferenceSession` API on top of the native runtime. Use it when the model is not available as a
`.pte` or GGUF file. Official reference: https://onnxruntime.ai/docs/tutorials/mobile/[ONNX Runtime -- Mobile tutorials].

considerably.

== Shipping and operating

* *Download size and first run.* Show progress, allow cancelling, and keep the weights out of the app binary unless the
  store's size limits allow it; the formula above gives a first estimate.
* *Memory.* Browsers cap per-tab memory and mobile operating systems terminate apps that exceed theirs, so prefer the
  smallest model that passes your own evaluation and unload models you no longer use.
* *Supply chain.* Pin model revisions, prefer safetensors or ONNX over pickle formats, never enable remote code from a
  repository you have not reviewed, and never ship a Hub access token in a client app; gated downloads should go through
  a server you control or a user-supplied token.
* *Fallback.* Keep a cloud path for devices that cannot run the model; the cloud counterparts are covered in
  xref:ai/hugging-face/hf-inference-providers-and-spaces.adoc[Inference Providers & Spaces].
* *Desktop runners.* For desktop apps, a local runner may be simpler than embedding a runtime; see
  xref:ai/local-llms/desktop-runners.adoc[Desktop Runners].
