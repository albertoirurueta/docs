== Why LLM security is different

Most of what you know about application security still applies: authenticate callers, validate input, patch dependencies, keep
secrets out of source control, log what matters. Three properties make LLM applications different enough to need their own
reference.

* *Non-determinism.* The same input can produce a different output on the next call, and a vendor can change the model under
  you. A test that passes once proves little, so security tests are statistical: they sample many attempts and report a rate,
  as xref:ai/security/ai-red-teaming.adoc[AI Red Teaming] shows.
* *A natural-language attack surface.* In a classic application, code and data are separate channels and an injection is a bug
  that mixes them. An LLM receives instructions and data in the same channel, as text, and cannot reliably tell which is
  which. Every document, web page, e-mail or tool result the model reads is a potential instruction. This is why
  xref:ai/security/prompt-injection.adoc[Prompt Injection] cannot be fully solved at the model level and is handled by layers
  around it.
* *Excessive autonomy.* Once a model can call tools, an injected instruction stops being a wrong answer and becomes an action:
  a record deleted, a message sent, money spent. Agency multiplies the consequence of every other weakness, which is why
  xref:ai/security/excessive-agency-and-tool-security.adoc[Excessive Agency and Tool Security] is as important as the filters.

The practical consequence is a change of stance. Treat the model as an untrusted, persuadable component that sits inside your
system, and put the controls around it (least privilege, validation of what goes in and comes out, human approval for
consequential actions, budgets, monitoring) rather than expecting the model to police itself. The same stance is called
*zero trust* or *pessimistic trust boundaries* in the security literature the bibliography lists.

== The running scenario: attacking and defending DocsAssistant

The system under test is the *DocsAssistant* used by the RAG Systems, MCP, Conversational Channels, Voice Agents and LLMOps
sub-sections (see xref:ai/rag-systems/index.adoc[RAG Systems in Production]): an agent backed by retrieval-augmented
generation over this site's documentation, with five parts that each add attack surface.

* A *`search_docs`* retrieval tool over a vector store of documentation, some of it uploaded by users.
* An *`open_issue`* write tool that files a ticket on the user's behalf.
* An *MCP server* exposing those tools to other hosts (see xref:ai/mcp/security.adoc[MCP security]).
* *Chat channels* such as a web widget, Teams or WhatsApp (see
  xref:ai/conversational-channels/index.adoc[Conversational Channels]).
* A *voice channel* over telephony (see xref:ai/voice-agents/index.adoc[Voice Agents]).

Every risk page repeats the same four steps, so that a reader who has seen one page can skim the next:

. *Attack.* A minimal, defensive demonstration against DocsAssistant. Attacks are shown only as far as needed to understand
  the defence; there is no catalogue of working jailbreaks.
. *Defend.* The defence in Python (LangChain middleware and guardrails) and in Java (Spring AI advisors and Spring Security),
  each snippet followed by the link to the official page it derives from.
. *Test.* A garak, PyRIT or promptfoo configuration that would show whether the defence holds.
. *Map.* The risk's OWASP 2026 ID, MITRE ATLAS technique and NIST AI 600-1 risk, so a finding can be reported in any
  framework's vocabulary.

=== Where the books are out of date

The requester-provided books are used for concepts only; where they differ from current material, the pages follow the
official documentation:

* *OWASP list.* _The Developer's Playbook_ (Wilson) follows version 1.1 of the OWASP Top 10 for LLM Applications from 2023.
  Two newer editions exist (2025 and 2026), with different names and numbering, so this sub-section cites 2026 as current and
  maps the older identifiers.
* *Agentic threats.* The agentic list post-dates the books, and the MCP-specific threats (tool poisoning, confused deputy,
  token passthrough) are only partly covered by _Building Applications with AI Agents_ (Albada).
* *Regulation.* The EU AI Act timeline changed after the books were written; the pages use the dated, sourced version.
* *Commercial products.* Vendor and product names in the books may have changed owners or names, so the pages name only
  open-source tools in depth.
* *Frameworks.* _Spring AI in Action_ (Walls) targets Spring AI 1.0; the pages use the 2.0.1 advisor and moderation APIs.
