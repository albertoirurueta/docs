A threat model answers four questions: what are we building, what can go wrong, what are we going to do about it, and did we do
a good enough job. For an LLM application the first answer is the hard one, because the model is not a function with a fixed
contract. The approach below is paraphrased from the threat-modelling chapters of the books listed in the
xref:ai/security/index.adoc#_bibliography[bibliography] (Wilson, Albada, Walls) and combined with the public frameworks.

== The architecture and its trust boundaries

A *trust boundary* is a line across which data or control passes between parties that deserve different levels of trust. In a
classic web application the boundaries are the network edge, the service-to-service calls and the database. An LLM application
adds boundaries that are easy to miss because they are not network hops: they are places where *text written by someone else
becomes part of the model's context*.

image::ai-security-trust-boundaries.svg["Architecture of the DocsAssistant in three zones. On the left, the untrusted zone: users, uploaded documents and web pages, third-party MCP servers and other agents, and training data. In the middle, the application boundary: input guardrails, the orchestrator with the model treated as an untrusted component, the vector store and output guardrails. On the right, the privileged zone: the search_docs read tool, the open_issue write tool needing human approval, internal services, and secrets that must never appear in the prompt. Two numbered boundaries mark the input and the tool call and result paths."]

The parties and data flows to enumerate for every system are these.

[cols="2,4,3", options="header"]
|===
| Element | Why it matters | Typical control

| Users and channels
| Anyone who can type, speak or upload is an author of model input, including anonymous users of a web widget or a phone line.
| Authentication, rate limits, input validation (see xref:ai/conversational-channels/operating-chat-channels.adoc[Operating Chat Channels]).

| The model
| Instructions and data share one channel, so the model can be persuaded by any text in its context. It is a useful but untrusted component.
| Never grant it more authority than the least privileged user it serves.

| Training and fine-tuning data
| Poisoned or leaking data persists in the weights and cannot be patched like code.
| Provenance, review and signing (see xref:ai/security/supply-chain-security.adoc[Supply Chain Security]).

| Retrieved and live data
| Documents, web pages, e-mail and database rows enter the context as text and can carry instructions (indirect injection).
| Per-document access control, ingestion sanitisation (see xref:ai/security/rag-and-vector-security.adoc[RAG and Vector Security]).

| Tools and internal services
| Tools turn model output into actions with the application's credentials.
| Least privilege, parameter validation, human approval (see xref:ai/security/excessive-agency-and-tool-security.adoc[Excessive Agency and Tool Security]).

| Other agents and MCP servers
| Their descriptions and results are text from a third party, and a compromised one can steer your agent.
| Allow-lists, pinning, scoped tokens (see xref:ai/mcp/security.adoc[MCP security]).

| The output
| What the model writes is rendered in browsers, executed by interpreters or sent to other systems.
| Treat as untrusted input (see xref:ai/security/improper-output-handling.adoc[Improper Output Handling]).
|===

The most important consequence is a rule that the later pages keep applying: *the model's authority is the minimum of the
authority of everyone whose text is in its context*. If the context contains a paragraph from an anonymous uploaded document,
then anything the model can do, that anonymous author can attempt to make it do.

== STRIDE applied to an LLM application

STRIDE is Microsoft's mnemonic for six threat categories: spoofing, tampering, repudiation, information disclosure, denial of
service and elevation of privilege. It applies to each element and flow of the diagram above; the LLM-specific reading of each
letter is the useful part.

[cols="1,3,3", options="header"]
|===
| STRIDE | LLM-specific example against the DocsAssistant | OWASP 2026 risk

| Spoofing
| An uploaded document claims to be a system message; a rogue MCP server impersonates the real docs server; a caller reuses another user's session in a chat channel.
| LLM01, LLM04

| Tampering
| Poisoned documents in the vector store, a tampered model file, an edited prompt template in a registry.
| LLM05, LLM04, LLM09

| Repudiation
| No log of which prompt, retrieved chunks and tool arguments led to an issue being opened.
| (cross-cutting; see xref:ai/security/llmsecops.adoc[LLMSecOps])

| Information disclosure
| The answer quotes a document the user may not read; the system prompt or a tool schema is echoed back; an image URL carries data to an attacker.
| LLM02, LLM08, LLM09, LLM10

| Denial of service
| Token flooding, recursive tool loops, an expensive query that exhausts the monthly budget (denial of wallet).
| LLM06

| Elevation of privilege
| Injected instructions make the agent call `open_issue` with its service account's authority instead of the user's.
| LLM03, LLM01
|===

== MAESTRO for agents

STRIDE looks at elements of a system. MAESTRO (Multi-Agent Environment, Security, Threat, Risk and Outcome), published by the
Cloud Security Alliance, organises agentic threats by *layer*, which suits systems where several agents, tools and data stores
interact. It describes seven layers: foundation models, data operations, agent frameworks, deployment and infrastructure,
evaluation and observability, security and compliance, and the agent ecosystem, and it asks the modeller to consider threats
inside each layer and *across* layers, for example a poisoned dataset in layer 2 that surfaces as a goal hijack in layer 7. For
the DocsAssistant the cross-layer view is what shows that an ingestion pipeline weakness (data operations) becomes an agent
action (ecosystem). Use STRIDE for the data-flow diagram and MAESTRO as a checklist that no layer was forgotten; the
xref:ai/security/owasp-top-10-for-agentic-applications.adoc[OWASP Top 10 for Agentic Applications] gives names to the results.

== A worked threat model of the DocsAssistant

The scope is the five parts listed on the xref:ai/security/index.adoc#_the_running_scenario_attacking_and_defending_docsassistant[landing page].
The assets are the confidential documents in the vector store, the users' identities and conversations, the ticketing system
that `open_issue` writes to, the monthly token budget, and the organisation's reputation for accurate answers. The attackers
considered are an anonymous chat user, an authenticated user trying to read documents above their clearance, an author of
a document the assistant ingests, and the operator of a third-party MCP server.

[mermaid]
....
flowchart LR
    A[Attacker text] --> B{Entry point}
    B -->|chat or voice input| C[Direct injection]
    B -->|uploaded document| D[Indirect injection via retrieval]
    B -->|MCP tool description or result| E[Tool poisoning]
    C --> F[Model context]
    D --> F
    E --> F
    F --> G{Model follows the text?}
    G -->|calls open_issue or search_docs| H[Unauthorised action or data read]
    G -->|writes output| I[Leak via link, image or markup]
    G -->|loops| J[Cost exhaustion]
    H --> K[Control: per-user authorisation and human approval]
    I --> L[Control: output encoding and URL allow-list]
    J --> M[Control: step and token budgets]
    K --> N[Residual risk logged and monitored]
    L --> N
    M --> N
....

Each path in the flow becomes one row of a *threat register*. Keep the register in the repository next to the code so it is
reviewed with every change; a format such as the following is enough.

[source,yaml]
----
# threats/docsassistant.yaml -- illustrative format, not a tool configuration
- id: T-01
  title: Instructions hidden in an uploaded document change the answer or trigger a tool call
  stride: [Tampering, Elevation of privilege]
  owasp_llm_2026: LLM01
  owasp_agentic: ASI01
  atlas: AML.T0051
  nist_600_1: Information security
  controls: [spotlighting, least-privilege tools, human approval for open_issue]
  test: promptfoo redteam, garak promptinject probes
  status: mitigated-partially
- id: T-02
  title: A user retrieves a document above their clearance through the retrieval tool
  stride: [Information disclosure]
  owasp_llm_2026: LLM02
  atlas: AML.T0057
  nist_600_1: Data privacy
  controls: [metadata filter by caller identity applied in the retriever, not the prompt]
  test: authorisation test suite with two users
  status: mitigated
----

The format is the author's own; the fields are chosen so that each risk can be reported in the vocabulary of any of the
frameworks on the xref:ai/security/index.adoc#_the_framework_map[framework map]. The NIST categories are those of
https://doi.org/10.6028/NIST.AI.600-1[NIST AI 600-1]. A threat model is "good enough" when every register row has a control, a
test and an owner, and when the residual risk is written down and accepted by a named person rather than silently carried.

== Using the model

. Draw the diagram first and mark every place where text from outside enters the model's context.
. Walk STRIDE over each flow and MAESTRO over each layer; add rows to the register.
. For each row choose controls from the risk pages and decide how it will be tested (see
  xref:ai/security/ai-red-teaming.adoc[AI Red Teaming]).
. Re-run the exercise whenever a tool, data source, channel or model changes: adding one MCP server or one document source
  adds a boundary.
