rewriting it for each of them.

== The idea: one core, many adapters

Every page uses the same running scenario, *DocsAssistant*, which answers questions about this site's documentation.
Its core exposes one channel-agnostic operation:

[source,text]
----
ask(conversationId, userId, text) -> stream of { token | citation | done }
----

The core is implemented twice, exactly as in the RAG Systems sub-section: in Python with LangChain `create_agent`, a
retriever tool, a Postgres checkpointer and FastAPI, and in Java with the Spring AI `ChatClient`, the RAG advisor, JDBC
chat memory and Spring Boot. A *channel adapter* sits in front of the core and has three jobs: map the channel's user
and thread identifiers to `userId` and `conversationId` (which drives memory and access control), map the core's token
stream to what the channel can actually do (native streaming, message edits, a typing indicator or whole messages), and
render citations in the channel's native idiom (links, cards or buttons).

== The channel landscape

*Your own surfaces* are the ones you control end to end. A streaming HTTP or WebSocket API is the base that everything
else can reuse; the AI SDK UI Message Stream and AG-UI protocols standardise what flows over it so that off-the-shelf UI
libraries can render it; ready-made UIs such as assistant-ui, Chainlit, Open WebUI and LibreChat can sit on top, or you
can embed a small widget in a web page. WebRTC data channels and XMPP are the two non-HTTP options: the first earns its
place mainly when a media connection already exists, the second when you need a federated, self-hostable chat protocol.

*Business channels* are surfaces owned by someone else, so the platform dictates the rules: registration or approval,
message formats, windows during which you may reply, and what an AI assistant is allowed to do. Microsoft Teams is the
natural channel for employees of a Microsoft 365 organisation, WhatsApp and Apple Messages for Business and RCS reach
customers on their own phones, and Slack, Telegram and Google Chat cover team and community chat.

=== Where the books are out of date

None of the requester-provided books covers messaging channels; only the chapters named in the
<<_bibliography,bibliography>> are used, and only for concepts. The differences that matter:

* *LangChain streaming.* _Learning LangChain_ (Chapter 8) describes streaming through the earlier chain and graph APIs.
  In LangChain 1.x agents are built with `langchain.agents.create_agent` and streamed with `stream_mode` values such as
  `messages`, as described in the LangChain streaming documentation.
* *Spring AI streaming.* _Spring AI in Action_ (Chapter 3) shows `stream()` returning a `Flux`; that is still the shape,
  but Spring AI 2.0 on Spring Boot 4 changed the surrounding property names and advisor classes; see
  xref:ai/spring-ai/streaming-and-reactive.adoc[Streaming and Reactive].
* *Teams and bots.* Any text that builds Teams bots on the Bot Framework SDK is out of date: its SDK repositories are
  archived. The Teams SDK and the Microsoft 365 Agents SDK are the supported paths.
