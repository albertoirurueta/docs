xref:ai/rag-systems/serving-rag-as-an-api.adoc[Serving RAG as an API] designs the public `/v1/ask` contract: request and

*channel adapter* view: the HTTP and WebSocket endpoints below are two of the adapters in front of the channel-agnostic
core, and the interesting questions are the ones every streaming adapter shares -- which transport to pick, how to cancel
a generation nobody is reading, how a dropped connection resumes, what happens when the client is slower than the model,
what proxies do to the stream and how a browser authenticates a connection that cannot carry an `Authorization` header.

The core used throughout is the one from the sub-section landing page:

[source,text]
----
ask(conversationId, userId, text) -> stream of { token | citation | done }
----

In Python it is an async generator of small frozen dataclasses built on the persistent LangChain agent of
xref:ai/langchain/streaming.adoc[LangChain: Streaming]; in Java it is a `Flux` of a sealed interface built on the Spring AI
`ChatClient` of xref:ai/spring-ai/streaming-and-reactive.adoc[Spring AI: Streaming & Reactive]. An adapter never touches
the agent or the `ChatClient`; it only translates those events to bytes on the wire and the wire's signals (disconnect,
cancel, reconnect) back to the core.

== SSE, WebSocket or NDJSON

All three carry an ordered sequence of small JSON messages from the server to the client over a long-lived HTTP
response or connection. They differ in what else they give you and in what the infrastructure in between tolerates.

[cols="1,2,2,2", options="header"]
|===
| | Server-sent events (SSE) | WebSocket | NDJSON over a streaming response

| Direction
| Server to client; the client talks with ordinary requests
| Full duplex on one connection
| Server to client; the client talks with ordinary requests

| Wire format
| `text/event-stream`: `event:`, `data:`, `id:`, `retry:` fields and `:` comment lines, events separated by a blank line
| Frames (text or binary) defined by RFC 6455; the message schema is yours
| `application/x-ndjson`: one JSON document per line; no standard media-type registration, so clients agree by convention

| Browser API
| `EventSource` (GET only, no custom headers) or `fetch` with a stream reader
| `WebSocket` (no custom headers on the handshake)
| `fetch` with `response.body.getReader()`; any HTTP method and headers

| Reconnect
| Built in: `EventSource` retries and sends `Last-Event-ID`
| None; your code reconnects and resumes
| None; your code reconnects and resumes

| Cancel a generation
| Close the connection (the server sees a disconnect) or send a separate `DELETE`/`POST`
| Send a `cancel` message on the same connection
| Abort the `fetch`, which closes the connection

| Proxies and CDNs
| Plain HTTP; works wherever response buffering is off; HTTP/2 multiplexing avoids the 6-connections-per-host limit of HTTP/1.1
| Needs an `Upgrade`-aware proxy and idle-timeout tuning; some corporate proxies break it
| Plain HTTP, with the same buffering caveats as SSE

| Best fit
| Chat answers: one question, one streamed answer, citations at the end
| Typing indicators, barge-in, several turns in flight, voice-adjacent control messages
| Service-to-service streaming and `fetch`-based clients that need `POST` with a body
|===

For a RAG chat window the default is SSE: it is plain HTTP, goes through the same authentication, rate limiting and
logging as every other route, and reconnects by itself. The browser's `EventSource` only issues `GET` requests and cannot set headers, which pushes
real applications to one of two shapes: `fetch` plus a stream parser (a `POST` with the question in the body, as in the
widget of Serving RAG as an API), or the two-step shape shown in <<_reconnecting_with_last_event_id>> (`POST` to start a
turn, `GET` to stream its events). Choose WebSocket when the client genuinely needs to talk while the server streams;
see also the .NET equivalent in xref:web/aspnet/core/signalr.adoc[SignalR], which negotiates WebSocket, SSE and long
polling for you, and the Quarkus take in xref:backend/quarkus/websockets.adoc[Quarkus WebSockets]. Choose NDJSON for
machine clients that want an uncomplicated line protocol. GraphQL subscriptions
(xref:backend/graphql/subscriptions.adoc[GraphQL Subscriptions]) and brokers
(xref:backend/messaging/protocols.adoc[Messaging Protocols]) are the heavier alternatives when the stream must fan out to
many subscribers rather than to the single asker.

== The shape of one turn

[mermaid]
----
sequenceDiagram
    autonumber
    participant B as Browser
    participant P as Reverse proxy
    participant A as HTTP adapter
    participant C as Channel-agnostic core
    participant M as LLM and retriever
    B->>P: POST /v1/turns (Authorization: Bearer ...)
    P->>A: forward (buffering off)
    A->>A: authenticate, derive userId, check conversation owner
    A-->>B: 202 {turnId}
    B->>P: GET /v1/turns/{turnId}/events
    P->>A: forward
    A->>C: ask(conversationId, userId, text)
    C->>M: retrieve, generate
    loop each token
        M-->>C: chunk
        C-->>A: token
        A-->>B: id: 7 / event: token / data: {"text": "..."}
    end
    Note over B,A: connection drops
    B->>P: GET /events (Last-Event-ID: 7)
    P->>A: forward
    A-->>B: replay events after 7, then live events
    C-->>A: citation, done
    A-->>B: event: citations, event: done
    B->>A: close (or DELETE /v1/turns/{turnId})
    A->>C: cancel
    C->>M: abort generation
----

== FastAPI: `EventSourceResponse` over LangChain `astream`

FastAPI 0.142.2 ships SSE support in `fastapi.sse`: a route declared with `response_class=EventSourceResponse` that is an
async generator yielding `ServerSentEvent` objects. The class has `data` (JSON-encoded), `raw_data` (sent as-is), `event`,
`id`, `retry` and `comment` fields. FastAPI sends a keep-alive comment every 15 seconds when nothing else is flowing and
sets `Cache-Control: no-cache` and `X-Accel-Buffering: no` on the response by itself. The core below turns the
LangChain `astream` output of the agent into the three channel-neutral events; the adapter then only has to choose
event names. The `thread_id` convention and the retriever tool are the ones from
xref:ai/rag-systems/conversational-rag-and-memory.adoc[Conversational RAG & Memory].

.docsassistant/core.py -- the channel-agnostic core as an async generator (Python, LangChain 1.4.3)
[source,python]
----
import json
import re
from collections.abc import AsyncIterator
from dataclasses import dataclass

from langchain_core.messages import AIMessage, ToolMessage

from docsassistant.agent import thread_id            # f"{user_id}:{conversation_id}"


@dataclass(frozen=True)
class Token:
    text: str


@dataclass(frozen=True)
class Citation:
    marker: int
    source: str


@dataclass(frozen=True)
class Done:
    conversation_id: str


CoreEvent = Token | Citation | Done


async def ask(agent, conversation_id: str, user_id: str, text: str) -> AsyncIterator[CoreEvent]:
    config = {"configurable": {"thread_id": thread_id(user_id, conversation_id)}}
    passages: dict[str, dict] = {}
    answer: list[str] = []
    async for part in agent.astream({"messages": [{"role": "user", "content": text}]}, config,
                                    stream_mode=["messages", "updates"], version="v2"):
        if part["type"] == "messages":
            chunk, _ = part["data"]
            if isinstance(chunk, AIMessage) and chunk.text:
                answer.append(chunk.text)
                yield Token(chunk.text)
        elif part["type"] == "updates" and "tools" in part["data"]:
            for msg in part["data"]["tools"]["messages"]:
                if isinstance(msg, ToolMessage):
                    for p in json.loads(msg.text):
                        passages[p["chunk_id"]] = p
    cited = [c for c in dict.fromkeys(re.findall(r"\[(c\d+)\]", "".join(answer))) if c in passages]
    for i, cid in enumerate(cited, start=1):
        yield Citation(i, passages[cid]["source"])
    yield Done(conversation_id)
----

Source: https://docs.langchain.com/oss/python/langchain/streaming[LangChain -- Streaming].

The HTTP adapter is then a thin generator. Everything that can fail with a status code -- the token, the conversation
ownership -- belongs in dependencies, which FastAPI resolves before the first byte; an exception inside the generator
can only become an `error` event on a response that already said 200.

.docsassistant/http_adapter.py -- the SSE adapter (Python, FastAPI 0.142.2)
[source,python]
----
from collections.abc import AsyncIterable
from typing import Annotated

from fastapi import Depends, FastAPI, Request
from fastapi.sse import EventSourceResponse, ServerSentEvent

from docsassistant.api import AskRequest, current_caller, owned_conversation   # from Serving RAG as an API
from docsassistant.core import Citation, Done, Token, ask
from docsassistant.security import Caller

app = FastAPI()


@app.post("/v1/chat/stream", response_class=EventSourceResponse)
async def chat_stream(req: AskRequest, request: Request,
                      caller: Annotated[Caller, Depends(current_caller)],
                      conversation_id: Annotated[str, Depends(owned_conversation)]) -> AsyncIterable[ServerSentEvent]:
    try:
        async for ev in ask(request.app.state.agent, conversation_id, caller.user_id, req.question):
            match ev:
                case Token(text):
                    yield ServerSentEvent(event="token", data={"text": text})
                case Citation(marker, source):
                    yield ServerSentEvent(event="citation", data={"marker": marker, "source": source})
                case Done(cid):
                    yield ServerSentEvent(event="done", data={"conversationId": cid})
    except Exception as exc:
        yield ServerSentEvent(event="error", data={"type": type(exc).__name__})
----

Source: https://fastapi.tiangolo.com/tutorial/server-sent-events/[FastAPI -- Server-Sent Events].

The adapter keeps no state of its own, which is what lets the same `ask` feed a WebSocket, a Slack handler or an XMPP
bot. How the full `/v1/ask` event vocabulary (`status`, `citations`, `grounding`) maps onto these three is a contract
decision covered in Serving RAG as an API.

== FastAPI WebSockets

A WebSocket adapter wraps the same `ask`. What it adds is a control channel: the client can send `cancel`, or a new
`ask` that supersedes the running one, without opening a second connection. The complete, tested-in-process variant with
a first-message token handshake is in the WebSocket section of Serving RAG as an API; the version below shows only the
adapter-specific part, the translation of core events and the lifecycle of the generation task.

.docsassistant/ws_adapter.py -- a WebSocket adapter over the same core (Python, FastAPI 0.142.2)
[source,python]
----
import asyncio

from fastapi import WebSocket, WebSocketDisconnect

from docsassistant.core import Citation, Done, Token, ask


async def run_turn(ws: WebSocket, agent, conversation_id: str, user_id: str, question: str) -> None:
    async for ev in ask(agent, conversation_id, user_id, question):
        match ev:
            case Token(text):
                await ws.send_json({"type": "token", "text": text})
            case Citation(marker, source):
                await ws.send_json({"type": "citation", "marker": marker, "source": source})
            case Done(cid):
                await ws.send_json({"type": "done", "conversationId": cid})


async def serve(ws: WebSocket, agent, user_id: str, conversation_id: str) -> None:
    turn: asyncio.Task | None = None
    try:
        while True:
            msg = await ws.receive_json()
            if msg["type"] == "ask":
                if turn and not turn.done():
                    turn.cancel()                                   # a new question supersedes the running one
                turn = asyncio.create_task(run_turn(ws, agent, conversation_id, user_id, msg["question"]))
            elif msg["type"] == "cancel" and turn:
                turn.cancel()
                await ws.send_json({"type": "cancelled"})
    except WebSocketDisconnect:
        if turn:
            turn.cancel()
----

Source: https://fastapi.tiangolo.com/advanced/websockets/[FastAPI -- WebSockets].

Browsers cannot set an `Authorization` header on the WebSocket handshake, so the token travels in the first message, in a
`Sec-WebSocket-Protocol` subprotocol entry, or as a short-lived single-use ticket in the URL (see <<_authenticating_eventsource_connections>>).

== Spring WebFlux: `Flux<ServerSentEvent>` from `ChatClient.stream()`

In Spring AI 2.0.1, `chatClient.prompt()...stream().content()` returns a `Flux<String>` of text deltas. The Java core
wraps that flux and appends citations and a terminal event; the adapter maps it to `ServerSentEvent` objects. WebFlux
supports a `Flux<ServerSentEvent<T>>` return value with `produces = text/event-stream` directly, and cancels the
subscription when the client disconnects. The Spring MVC variant of the same endpoint is on Serving RAG as an API; this
page uses WebFlux because a reactive pipeline is the natural fit for the cancellation and backpressure sections below
(see xref:backend/springboot/reactive-programming.adoc[Spring Boot: Reactive Programming]).

.DocsAssistantCore.java -- the channel-agnostic core as a Flux (Java 21, Spring AI 2.0.1)
[source,java]
----
import org.springframework.ai.chat.client.ChatClient;
import org.springframework.ai.chat.memory.ChatMemory;
import org.springframework.stereotype.Service;
import reactor.core.publisher.Flux;

import java.util.List;

public sealed interface CoreEvent {
    record Token(String text) implements CoreEvent {}
    record Citation(int marker, String source) implements CoreEvent {}
    record Done(String conversationId) implements CoreEvent {}
}

@Service
public class DocsAssistantCore {

    private final ChatClient chatClient;       // built with the RAG advisor and the JDBC chat memory advisor

    public DocsAssistantCore(ChatClient chatClient) {
        this.chatClient = chatClient;
    }

    public Flux<CoreEvent> ask(String conversationId, String userId, String text) {
        String memoryKey = userId + ":" + conversationId;
        Flux<CoreEvent> tokens = chatClient.prompt()
                .user(text)
                .advisors(a -> a.param(ChatMemory.CONVERSATION_ID, memoryKey))
                .stream()
                .content()
                .map(CoreEvent.Token::new);
        return tokens.concatWith(Flux.defer(() -> Flux.<CoreEvent>just(new CoreEvent.Done(conversationId))));
    }
}
----

Source: https://docs.spring.io/spring-ai/reference/api/chatclient.html[Spring AI -- ChatClient] and
https://docs.spring.io/spring-ai/reference/api/chat-memory.html[Spring AI -- Chat Memory].

Citations in this sketch would come from the RAG advisor's retrieved documents; reading them out of the response
context is covered in xref:ai/spring-ai/advisors.adoc[Spring AI: Advisors] and
xref:ai/spring-ai/chatmodel-and-chatclient.adoc[ChatModel & ChatClient] (a `chatResponse()` stream instead of `content()` exposes the metadata).

.ChatController.java -- the SSE adapter (Java 21, Spring Boot 4.1.1 WebFlux)
[source,java]
----
import org.springframework.http.MediaType;
import org.springframework.http.codec.ServerSentEvent;
import org.springframework.security.core.annotation.AuthenticationPrincipal;
import org.springframework.security.oauth2.jwt.Jwt;
import org.springframework.web.bind.annotation.*;
import reactor.core.publisher.Flux;

import java.time.Duration;
import java.util.Map;

@RestController
@RequestMapping("/v1/chat")
public class ChatController {

    private final DocsAssistantCore core;

    public ChatController(DocsAssistantCore core) {
        this.core = core;
    }

    @PostMapping(path = "/stream", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
    public Flux<ServerSentEvent<Object>> stream(@RequestBody AskRequest req, @AuthenticationPrincipal Jwt jwt) {
        Flux<ServerSentEvent<Object>> events = core.ask(req.conversationId(), jwt.getSubject(), req.question())
                .map(ev -> switch (ev) {
                    case CoreEvent.Token t -> sse("token", Map.of("text", t.text()));
                    case CoreEvent.Citation c -> sse("citation", Map.of("marker", c.marker(), "source", c.source()));
                    case CoreEvent.Done d -> sse("done", Map.of("conversationId", d.conversationId()));
                })
                .onErrorResume(e -> Flux.just(sse("error", Map.of("type", e.getClass().getSimpleName()))));
        Flux<ServerSentEvent<Object>> keepAlive = Flux.interval(Duration.ofSeconds(15))
                .map(i -> ServerSentEvent.<Object>builder().comment("keep-alive").build());
        return events.mergeWith(keepAlive.takeUntilOther(events.ignoreElements()));
    }

    private static ServerSentEvent<Object> sse(String name, Object data) {
        return ServerSentEvent.<Object>builder(data).event(name).build();
    }
}
----

Source: https://docs.spring.io/spring-framework/reference/web/webflux/reactive-spring.html[Spring Framework -- WebFlux] and
https://docs.spring.io/spring-framework/reference/web/webflux/controller/ann-methods/return-types.html[Spring Framework -- WebFlux return values].

The keep-alive merge stops when the event flux completes or errors. Spring does not add the 15-second ping that FastAPI
sends by default, so the application has to. Everything outside the stream -- the JWT, the CSRF decision, method
security -- is ordinary Spring Security, covered with the rest of the endpoint design in
xref:backend/springboot/rest-apis.adoc[Spring Boot: REST APIs] and
xref:ai/spring-ai/security-and-guardrails.adoc[Spring AI: Security & Guardrails].

== Spring WebSocket and STOMP

A STOMP adapter is worth it when the client already speaks STOMP (for example through a broker relay used by other parts
of the application), or when you want destination-based routing and user-targeted messages for free. The handler below
starts the core flux for a user and sends each event to that user's queue; it keeps the `Disposable` so that a `cancel`
message or a disconnect can stop the generation.

.ChatStompController.java -- a STOMP adapter (Java 21, Spring Boot 4.1.1)
[source,java]
----
import org.springframework.context.event.EventListener;
import org.springframework.messaging.handler.annotation.MessageMapping;
import org.springframework.messaging.simp.SimpMessagingTemplate;
import org.springframework.messaging.simp.SimpMessageHeaderAccessor;
import org.springframework.stereotype.Controller;
import org.springframework.web.socket.messaging.SessionDisconnectEvent;
import reactor.core.Disposable;

import java.security.Principal;
import java.util.Map;
import java.util.concurrent.ConcurrentHashMap;

@Controller
public class ChatStompController {

    private final DocsAssistantCore core;
    private final SimpMessagingTemplate template;
    private final Map<String, Disposable> running = new ConcurrentHashMap<>();   // keyed by WebSocket session id

    public ChatStompController(DocsAssistantCore core, SimpMessagingTemplate template) {
        this.core = core;
        this.template = template;
    }

    @MessageMapping("/ask")
    public void ask(AskRequest req, Principal principal, SimpMessageHeaderAccessor headers) {
        String session = headers.getSessionId();
        cancel(session);                                                           // supersede a running turn
        Disposable d = core.ask(req.conversationId(), principal.getName(), req.question())
                .subscribe(ev -> template.convertAndSendToUser(principal.getName(), "/queue/answer", ev));
        running.put(session, d);
    }

    @MessageMapping("/cancel")
    public void cancelMessage(SimpMessageHeaderAccessor headers) {
        cancel(headers.getSessionId());
    }

    @EventListener
    public void onDisconnect(SessionDisconnectEvent event) {
        cancel(event.getSessionId());
    }

    private void cancel(String session) {
        Disposable d = running.remove(session);
        if (d != null) {
            d.dispose();
        }
    }
}
----

Source: https://docs.spring.io/spring-framework/reference/web/websocket/stomp.html[Spring Framework -- STOMP].

`convertAndSendToUser` needs the user destination prefix and a `Principal` set during the handshake, which is where the
bearer token or ticket is validated (a `ChannelInterceptor` on the inbound channel can validate a token sent in the
STOMP `CONNECT` headers). Each token becomes one STOMP frame, so the per-frame overhead is larger than with SSE; batching
a few deltas per frame is a reasonable optimisation. Sending from a subscriber callback ignores backpressure on the outbound channel; see <<_backpressure>>.

== A Node and Express variant

Many teams put a small Node service in front of the Python or Java core, for example to share the SSE endpoint with a
Next.js front end or to terminate browser concerns (cookies, CORS) in one place. The sketch below relays the core's
event stream and propagates the browser's disconnect upstream through an `AbortController`. It assumes the core already
emits SSE, so the gateway adds authentication and nothing else.

.gateway/server.js -- an Express SSE relay with disconnect propagation (Node.js, Express 5.2.1)
[source,javascript]
----
import express from "express";
import { Readable } from "node:stream";

const app = express();
app.use(express.json());

const CORE_URL = process.env.DOCSASSISTANT_CORE_URL;          // e.g. http://core:8000/v1/chat/stream
const CORE_TOKEN = process.env.DOCSASSISTANT_CORE_TOKEN;      // service credential, never sent to the browser

app.post("/chat", async (req, res) => {
  const abort = new AbortController();
  res.on("close", () => abort.abort());                       // the browser went away: stop the upstream request

  const upstream = await fetch(CORE_URL, {
    method: "POST",
    headers: { "Content-Type": "application/json", Authorization: `Bearer ${CORE_TOKEN}` },
    body: JSON.stringify(req.body),
    signal: abort.signal,
  });

  res.status(upstream.status);
  res.set({
    "Content-Type": "text/event-stream",
    "Cache-Control": "no-cache, no-transform",
    "X-Accel-Buffering": "no",
  });
  res.flushHeaders();
  Readable.fromWeb(upstream.body).pipe(res);                  // pipe() propagates backpressure from the socket
});

app.listen(3000);
----

Source: https://expressjs.com/en/5x/api.html[Express 5.x API reference] and
https://nodejs.org/api/stream.html[Node.js -- Stream].

The comment on `pipe` is the point of using it: a slow reader pauses the upstream body instead of letting Node buffer
the whole answer in memory. A real gateway would also validate the browser's session, map it to the `userId` the core
expects, and handle an aborted request (`fetch` rejects with an `AbortError` that must not be logged as a failure).

== Cancellation and client disconnects

A generation costs tokens and holds a retrieval and database connection until it finishes, so an abandoned request must
stop it. Each transport signals abandonment differently:

[cols="1,3", options="header"]
|===
| Transport | What stops the generation

| SSE with FastAPI
| When the client closes the connection, the server cancels the response task; the `CancelledError` is raised at the
  generator's current `await`, which propagates into the `async for` over `astream` and stops the LLM call. Keep cleanup
  in `try`/`finally` and never swallow `CancelledError`. A route can also poll `await request.is_disconnected()`.

| SSE with WebFlux
| The disconnect cancels the subscription, and Reactor propagates `cancel` upstream to the Spring AI `Flux`, which
  closes the HTTP call to the model provider. Operators such as `doOnCancel` are for logging and metrics.

| WebSocket
| The server receives a close or a `cancel` message and cancels the task (Python) or disposes the subscription (Java), as
  in the snippets above.

| Express gateway
| `res.on("close")` aborts the upstream `fetch`; the core then sees its own client disconnect.
|===

What a disconnect should do to the *conversation* is a product decision. With a checkpointer the user message is
already stored when generation is cancelled, so the next turn sees a question without an answer; decide whether to
store the partial answer, drop the dangling question or mark it as interrupted. Explicit user cancellation
("Stop generating") deserves a distinct signal from a network drop: the first ends the turn, the second should allow a
resume. That distinction is the next section.

== Reconnecting with `Last-Event-ID`

When an `EventSource` loses its connection it reconnects after the `retry` interval and sends the `id` of the last event
it received in a `Last-Event-ID` header. FastAPI exposes that header like any other, and Spring through
`@RequestHeader("Last-Event-ID")`. Resuming a *model generation* is a different thing from resuming a *file download*:
the stream is not recomputable from an offset, so the server must have kept the events already produced. The usual
design is to decouple the generation from the connection:

. `POST /v1/turns` authenticates the caller, starts the core in a background task and returns `202` with a `turnId`.
. The task appends every core event to a per-turn log (an in-process list for one instance; a Redis Stream or a database
  table when several instances serve the same user).
. `GET /v1/turns/\{turnId}/events` replays the log from `Last-Event-ID + 1` and then follows it live.

The two-step shape also repairs the `EventSource` limitation: the question travels in a `POST` body, and the `GET` that
`EventSource` can issue carries no secrets, only the unguessable `turnId` and the credentials discussed in the next
sections.

.docsassistant/turns.py -- resumable event stream over an in-process log (Python, FastAPI 0.142.2)
[source,python]
----
import asyncio
from collections.abc import AsyncIterable
from typing import Annotated

from fastapi import FastAPI, Header, HTTPException
from fastapi.sse import EventSourceResponse, ServerSentEvent

app = FastAPI()
turns: dict[str, "Turn"] = {}                    # illustrative: use Redis Streams or a table for several instances


class Turn:
    def __init__(self, user_id: str) -> None:
        self.user_id = user_id
        self.events: list[ServerSentEvent] = []
        self.finished = False
        self.changed = asyncio.Condition()
        self.task: asyncio.Task | None = None

    async def append(self, name: str, data: dict) -> None:
        async with self.changed:
            self.events.append(ServerSentEvent(event=name, data=data, id=str(len(self.events)), retry=3000))
            self.changed.notify_all()

    async def finish(self) -> None:
        async with self.changed:
            self.finished = True
            self.changed.notify_all()


@app.get("/v1/turns/{turn_id}/events", response_class=EventSourceResponse)
async def turn_events(turn_id: str, caller_id: str,                      # caller_id comes from a dependency in real code
                      last_event_id: Annotated[int | None, Header()] = None) -> AsyncIterable[ServerSentEvent]:
    turn = turns.get(turn_id)
    if turn is None or turn.user_id != caller_id:
        raise HTTPException(status_code=404)                              # same answer for foreign and unknown turns
    position = 0 if last_event_id is None else last_event_id + 1
    while True:
        async with turn.changed:
            await turn.changed.wait_for(lambda: position < len(turn.events) or turn.finished)
            batch, finished = turn.events[position:], turn.finished
        for ev in batch:
            yield ev
        position += len(batch)
        if finished and position >= len(turn.events):
            return
----

Source: https://fastapi.tiangolo.com/tutorial/server-sent-events/[FastAPI -- Server-Sent Events] and
https://html.spec.whatwg.org/multipage/server-sent-events.html[WHATWG HTML -- Server-sent events].

Because the event stream no longer owns the generation, a disconnect must not cancel it; instead, cancel when the
last subscriber has been gone for a grace period, or on an explicit `DELETE /v1/turns/\{turnId}`. The log needs a time to
live (minutes, not days), and event identifiers need only be unique and ordered within one turn. Spring offers the
same shape with a `Sinks.Many` replay sink per turn; `Sinks.many().replay().all()` gives replay for late subscribers and
live delivery afterwards, with the same lifetime caveats.

== Backpressure

A model produces tokens at a rate of tens per second; a phone on a poor network may consume less. Without a policy, a
slow reader makes the server buffer the difference. If \(r_m\) is the model's token rate, \(r_c\) the client's
effective consumption rate and \(T\) the duration of the answer, the unread backlog grows as

\[
B(T) = \max\bigl(0,\,(r_m - r_c)\,T\bigr)
\]

tokens per connection, and the memory held across \(N\) concurrent slow readers is \(N \cdot B(T)\) times the size of an
event. Practical policies, from cheapest to most careful:

* *Coalesce.* Send a batch of tokens every 50 to 100 milliseconds instead of one event per token; this reduces
  per-event overhead, which is large for SSE and STOMP framing. In Reactor, `bufferTimeout` or `window` do this; in
  Python, accumulate into a buffer and flush on a timer.
* *Let the transport push back.* Reactor honours demand end to end, and WebFlux requests items only as the socket
  drains. Do not add `onBackpressureBuffer()` without a bound; use `onBackpressureBuffer(maxSize)` with an overflow
  strategy, or `onBackpressureLatest()` for state-like events (a progress indicator) where only the newest value matters.
* *Bound the per-turn log.* For text tokens, the full answer is the state: send the client an occasional snapshot and
  drop the intermediate deltas for readers that fell behind.
* *Drop the reader.* If the backlog passes a limit, close the connection with an error event; the client resumes with
  `Last-Event-ID` from the log, and the model keeps generating undisturbed.

In Python, `await ws.send_json(...)` and an SSE generator both suspend when the socket's write buffer is full, so a slow
reader naturally slows the generator and, through the `async for`, the model call; that is back pressure by
construction, and the reason an unbounded `asyncio.Queue` between the core and the adapter is the thing to avoid.

== Proxy buffering and timeouts

The most common reason a streamed answer arrives "all at once" in production is a proxy that buffers the response. Nginx
buffers proxied responses by default; it honours an `X-Accel-Buffering: no` response header and the equivalent
`proxy_buffering off;` directive per location. FastAPI's `EventSourceResponse` sets that header itself; a Spring or Express
adapter has to set it (the Express sketch above does), or the proxy configuration has to turn buffering off.

[source,nginx]
----
location /v1/chat/ {
    proxy_pass http://docsassistant_core;
    proxy_http_version 1.1;
    proxy_set_header Connection "";
    proxy_buffering off;
    proxy_cache off;
    proxy_read_timeout 300s;
}
----

Source: https://nginx.org/en/docs/http/ngx_http_proxy_module.html[nginx -- ngx_http_proxy_module].

Related points, each of which has caused a missing-stream incident somewhere:

* Compression middleware (gzip, brotli) can hold bytes until a block is full. Exclude `text/event-stream` from it, or
  flush after each event.
* `Cache-Control: no-cache, no-transform` prevents intermediaries from caching or rewriting the stream.
* Idle timeouts of load balancers, API gateways and mobile networks are often 30 to 120 seconds: a comment line every
  15 seconds (`: keep-alive`) is enough to keep the connection open while the model or a tool is thinking.
* With HTTP/1.1, browsers allow about six connections per host, and each open `EventSource` consumes one; HTTP/2 lifts
  that limit, so terminate TLS with HTTP/2 in front of the adapter.
* Cloud front ends have their own switches (response streaming, idle timeouts, WebSocket support); the Azure side is
  covered in xref:cloud/azure/container-apps.adoc[Azure Container Apps] and
  xref:cloud/azure/api-management.adoc[Azure API Management], which needs streaming explicitly enabled on the operation.

== Authenticating EventSource connections

`EventSource` and `WebSocket` cannot attach an `Authorization` header, which leaves four options:

[cols="1,2,2", options="header"]
|===
| Option | How | Trade-offs

| `fetch` plus a stream parser
| `fetch(url, {method: "POST", headers: {Authorization: ...}})` and read `response.body`; libraries such as
  `@microsoft/fetch-event-source` wrap this and add retry and `Last-Event-ID`
| Keeps standard bearer tokens and `POST` bodies; you own reconnection logic (or the library does)

| Cookie session
| `new EventSource(url, {withCredentials: true})` with a `SameSite` session cookie set by your login flow
| Simple for same-site apps; needs CSRF thought for any state-changing request and CORS with credentials for cross-origin

| Short-lived ticket
| An authenticated `POST /v1/tickets` returns an opaque, single-use value valid for about 30 seconds; the browser opens
  `/v1/turns/\{id}/events?ticket=...`
| Works with native `EventSource` and `WebSocket`; the ticket is still visible in URLs and logs, so it must be single-use
  and bound to the user and the turn

| Token in a query string
| `?access_token=...` with the real access token
| Avoid: tokens leak into access logs, browser history and `Referer` headers
|===

Whichever option is used, the adapter derives `userId` from the verified credential, never from a request field, because
that value keys conversation memory and the access-control filter of the retriever (see
xref:ai/rag-systems/access-control-and-privacy.adoc[Access Control & Privacy]). OAuth 2.0 mechanics -- which grant for a
browser client, how to keep tokens out of JavaScript, how long access tokens should live -- are in
xref:backend/oauth/browser-based-apps.adoc[OAuth for Browser-Based Apps],
xref:backend/oauth/authorization-code-and-pkce.adoc[Authorization Code & PKCE] and
xref:backend/oauth/security-best-practices.adoc[OAuth Security Best Practices]. A token that expires in the middle of
a long stream does not interrupt it; the check happens at connect time, so reconnection is the moment to re-authenticate
and a short access-token lifetime combined with `Last-Event-ID` resume is acceptable.

== Choosing, in short

* One question, one streamed answer, a browser or app client: SSE, with the two-step `POST` then `GET` shape when the
  stream must be resumable, otherwise `fetch` streaming over `POST`.
* The client talks while the server streams (cancel, supersede, typing indicators): WebSocket, or STOMP if the
  application already runs a STOMP broker.
* Service-to-service or script clients: NDJSON or SSE, whichever the client library parses with less code.
* Always: a transport-independent core, keep-alives, a disconnect policy, buffering off in every proxy on the path and the
  user identity taken from the verified credential.
