= Parallel Sessions & Worktrees
:description: Running several Copilot or Claude Code sessions at once in isolated git worktrees -- splitting work by module, fanning work out and back in, and a merge-conflict strategy for the result.
:keywords: git worktree, claude --worktree, EnterWorktree, worktree.baseRef, VS Code Agents window, copilot --cloud, fan-out, fan-in, merge conflicts

include::partial$ai-ai-assisted-development-disclaimer.adoc[]

This page targets the Claude Code CLI's `--worktree` flag and VS Code's Agents window, both checked against
https://code.claude.com/docs/en/worktrees[Claude Code -- Run parallel sessions with worktrees] and
https://code.visualstudio.com/docs/agents/run/agents-window[VS Code -- The Agents window] as of *2026-09-28*; the
GitHub Copilot CLI's cloud sandbox is checked against
https://docs.github.com/en/copilot/how-tos/cloud-and-local-sandboxes[GitHub Copilot -- Cloud and local sandboxes],
also public preview as of that date. The running example is the same *DocsAssistant API* Spring Boot + Python
sample used throughout this sub-section, with its Java sources under
`src/main/java/com/example/docsassistant/`, its tests under `src/test/java/com/example/docsassistant/`, and a
Python ingestion script under `ingest/`.

A https://git-scm.com/docs/git-worktree[git worktree] is a second working directory checked out from the same
repository, on its own branch, sharing the repository's history and remote with the main checkout. Running each
agent session in its own worktree means one session editing `DocsController.java` never touches files a second
session is editing under `ingest/`, even though both sessions share the same `.git` directory underneath.

== Running several agents with git worktrees

=== Claude Code: `--worktree`

Passing `--worktree` (or `-w`) a name creates an isolated worktree and starts Claude Code in it. By default the
worktree is created under `.claude/worktrees/<name>/` at the repository root, on a new branch named
`worktree-<name>`:

[source,console]
----
$ claude --worktree docs-endpoint
----

Running the same command again with a different name, in another terminal, starts a second isolated session; a
name left out is generated automatically (for example `bright-running-fox`). A worktree is a fresh checkout, so
project setup (installing dependencies, copying a local `.env`) has to be repeated inside it once -- or copied in
automatically for every future worktree by listing the files in a `.worktreeinclude` file at the repository root,
in `.gitignore` syntax. Claude Code also enforces isolation on its own: while a session is running inside a
worktree, it blocks file edits and git commands that target the main checkout, so a stray "also fix this in the
other module" instruction cannot cross worktrees by accident. See
https://code.claude.com/docs/en/worktrees[Claude Code -- Run parallel sessions with worktrees].

Inside a running session, asking Claude to "work in a worktree" creates one on demand with the `EnterWorktree`
tool, and it can switch to another existing worktree the same way; entering a path outside
`.claude/worktrees/` asks for approval first, because the move takes the session's working directory and
project configuration with it. New worktrees branch from the repository's default branch unless
`worktree.baseRef` is set to `"head"` in `settings.json`, which branches from the current local `HEAD` instead --
useful when a worktree needs to continue in-progress, unpushed work rather than starting clean:

[source,json]
----
// .claude/settings.json
{
  "worktree": {
    "baseRef": "head"
  }
}
----

Claude Code can also create a worktree straight from a pull request, fetching its head commit from `origin`:

[source,console]
----
$ claude --worktree "#42"
----

For a branch that already exists, or a worktree placed outside the repository, `git worktree add` directly is
the documented alternative to `--worktree`:

[source,console]
----
$ git worktree add ../docs-fix-456 fix-issue-456
$ cd ../docs-fix-456
$ claude
----

=== VS Code and the Copilot CLI

VS Code's *Agents window* (opened with the *Chat: Open Agents window* command, or `code --agents` from a
terminal) manages several concurrent agent sessions across workspaces from one place. Starting a session there
offers the option to check out an existing local branch first, and, per VS Code's own documentation, this
worktree isolation requires a local git repository with at least one commit; several sessions can stay open at
once to compare results, though only one is active for workspace actions at a time. See
https://code.visualstudio.com/docs/agents/run/agents-window[VS Code -- The Agents window].

The GitHub Copilot CLI documents a separate mechanism for running tasks in parallel: `copilot --cloud` starts an
interactive session in a GitHub-hosted cloud sandbox instead of the local machine, and its own docs describe this
as useful for running multiple tasks in parallel without consuming local resources. As of the date above this is
a public-preview feature, interactive only -- it cannot be combined with non-interactive (`-p`) runs. See
https://docs.github.com/en/copilot/how-tos/cloud-and-local-sandboxes[GitHub Copilot -- Cloud and local sandboxes].
Copilot's own background *cloud agent*, covered on
xref:ai/ai-assisted-development/cloud-and-background-agents.adoc[Cloud & Background Agents], is a third,
unattended way to run a task off the local machine; it is not a worktree and does not run locally at all.

== Splitting work by module

DocsAssistant API has a natural split for parallel work: the Java backend under
`src/main/java/com/example/docsassistant/` (and its tests) is largely independent of the Python ingestion script
under `ingest/`. Two worktrees, one per module, let two sessions work at the same time without either one seeing
the other's in-progress edits:

[source,console]
----
$ claude --worktree docs-endpoint     # backend: add GET /api/pages/{id}
$ claude --worktree ingest-retry      # ingest/: add retry logic to the ingestion script
----

Splitting by module works best when the modules' files genuinely do not overlap -- two build files, two test
suites, two sets of source files. A change that must touch both modules together (for example, an API contract
both the Java controller and the Python script serialize against) is a poor fit for two independent worktrees,
because neither session sees the other's assumptions about the shared contract until they merge; that kind of
change is better done in one session, or with the two sessions passing findings to each other rather than working
in isolation.

== Fan-out / fan-in

*Fan-out* is starting several sessions on independent pieces of a larger task at the same time; *fan-in* is
bringing their results back together once each piece is done. Two worktrees on two modules, as above, is the
simplest fan-out: one prompt per session, each scoped to its own worktree and its own piece of DocsAssistant API.

.In Claude Code, session 1 (worktree `docs-endpoint`)
[source,console]
----
$ claude --worktree docs-endpoint "add a GET /api/pages/{id} endpoint to
@src/main/java/com/example/docsassistant/DocsController.java that returns a single page by id,
using PageRepository, and returns a 404 when the id doesn't exist"
----

.In Claude Code, session 2 (worktree `ingest-retry`)
[source,console]
----
$ claude --worktree ingest-retry "add exponential-backoff retry to the HTTP calls in
@ingest/ingest.py, up to 3 attempts, and log each retry"
----

Fan-in happens at the git level, not inside either session: once both sessions finish and commit, the two
branches merge back into the integration branch one at a time, the same way any two feature branches would (see
xref:git-and-github/branches.adoc[]). A third pattern -- asking one Claude Code session to spawn several
xref:ai/ai-assisted-development/agent-mode.adoc[subagents] for *research* run in parallel inside a single
context, each investigating one module and reporting back to the same conversation -- fans in automatically
because the subagents share the parent session; it does not isolate file edits the way separate worktrees do, so
it fits read-only investigation (for example, "look at the backend and the ingestion script in parallel and
summarize how they'd need to change") better than two sessions that will both edit files. See
https://code.claude.com/docs/en/sub-agents[Claude Code -- Subagents] for the difference in depth.

== Merge-conflict strategy

Two worktrees on genuinely separate files, as in the DocsAssistant API split above, merge without conflicts most
of the time: git only needs to combine non-overlapping changes into one history. Conflicts still turn up when
both sessions touched a shared file -- a shared `pom.xml`, a shared configuration file, or a README both agents
updated -- and the strategy for handling them is the same one that applies to any two branches, agent-authored or
not:

* *Merge (or rebase) one branch before starting the next session's merge*, rather than merging both at once, so
  any conflict is between one worktree's branch and the integration branch, never between two worktrees directly.
* *Keep each worktree's changes reviewable on their own* -- a focused diff per module, as shown above -- so a
  conflict, when it happens, is easy to read: it is one small change against another, not two large ones.
* *Resolve the conflict with the same tools used for any merge conflict* -- an editor's three-way merge view, or
  `git status` plus manual edits -- and, if useful, ask the agent in one of the worktrees to look at the conflict
  markers and propose a resolution once both sides are visible in its own worktree, rather than asking an agent
  that only saw one side to guess at the other.

See xref:git-and-github/merging-rebasing-and-conflicts.adoc[] for the full mechanics of resolving a conflict.

== Worked example: two worktrees, then merge

Following the module split above end to end, from creating the two worktrees to a clean merge back into
`feature/203`:

[source,console]
----
$ git checkout feature/203
$ git pull

$ claude --worktree docs-endpoint "add a GET /api/pages/{id} endpoint to
@src/main/java/com/example/docsassistant/DocsController.java ..."
# ... session runs, commits its change on branch worktree-docs-endpoint ...

$ claude --worktree ingest-retry "add exponential-backoff retry to
@ingest/ingest.py ..."
# ... session runs, commits its change on branch worktree-ingest-retry ...

$ git checkout feature/203
$ git merge worktree-docs-endpoint
$ git merge worktree-ingest-retry
----

Because `DocsController.java` and `ingest.py` are disjoint files, both merges are fast-forward or clean
three-way merges with nothing to resolve. If a later session on a third worktree had also touched
`DocsController.java`, that third merge could conflict with the first, and the strategy above -- merge one
worktree's branch at a time, resolve with the usual conflict tools -- applies exactly as it would for any two
ordinary feature branches:

[mermaid]
....
flowchart LR
    M["feature/203"] --> W1["Worktree: docs-endpoint\n(DocsController.java)"]
    M --> W2["Worktree: ingest-retry\n(ingest.py)"]
    W1 -->|merge, no conflict| M2["feature/203"]
    W2 -->|merge, no conflict| M2
    M2 -->|next worktree touches\nthe same file| C["Possible conflict:\nresolve one merge at a time"]
....

Once both worktrees' branches are merged and their work is confirmed on `feature/203`, each worktree can be
removed with `git worktree remove` (Claude Code also does this itself on a clean interactive exit); leaving an
unnamed, unmerged worktree in place is what its periodic cleanup sweep is for, described on the same
xref:ai/ai-assisted-development/claude-code-getting-started.adoc[Getting Started with Claude Code] page's linked
worktrees documentation.
