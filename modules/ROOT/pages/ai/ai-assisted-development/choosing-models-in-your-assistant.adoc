= Choosing Models in Your Assistant

Examples on this page target the current stable release of Visual Studio Code with the built-in GitHub Copilot
and GitHub Copilot Chat extensions, and the Claude Code CLI, both checked against the official GitHub Copilot
and Claude Code documentation as of 2026-09-28. Both products add and retire specific models on their own
schedule, so this page describes the pickers and controls rather than naming which models are current; see
xref:ai/llm-foundations/choosing-a-model.adoc[Choosing a Model] for the process of picking a model in the first
place, independent of which assistant runs it. The running example is again *DocsAssistant API*, the Spring
Boot + Python sample used throughout this sub-section.

== The Copilot model picker

VS Code exposes two separate model choices, not one. *Chat* -- the panel-based conversation used for anything
from a one-off question to a multi-file agentic change -- is switched from the language model picker in the
chat input field, which lists the models your plan and organization make available and groups faster models
apart from deeper-reasoning ones. *Completions* (ghost-text and ghost-text-style inline suggestions) use a
separate model, changed from the Chat view's menu: select *Configure Inline Suggestions...*, then *Change
Completions Model...*. The two pickers are independent, so a session can run a fast model for completions while
chat uses a stronger one for a harder question:

.In GitHub Copilot (VS Code)
[source,text]
----
1. Click the model name in the chat input field to open the chat model picker, and pick a model.
2. Open the Chat view menu -> Configure Inline Suggestions... -> Change Completions Model... to pick a
   different completions model independently of the chat model.
----

See link:https://code.visualstudio.com/docs/agent-customization/language-models[VS Code -- Language models in
Visual Studio Code] and link:https://docs.github.com/en/copilot/concepts/models/overview[GitHub -- About AI
models in Copilot].

== Supported-models and model-comparison pages

GitHub keeps two reference pages instead of a fixed table on every product page: the
link:https://docs.github.com/en/copilot/reference/ai-models/supported-models[supported models] page lists which
models are currently available and to which surface (chat, completions, Copilot cloud agent, Copilot CLI, the
GitHub Copilot app), including which ones offer an extended context window on some clients; the
link:https://docs.github.com/en/copilot/reference/ai-models/model-comparison[model comparison] page groups them
by what they are good at -- general-purpose coding, fast/simple tasks, complex multi-file reasoning, and visual
input -- so a task can be matched to a category without memorizing individual model names. Both pages change
whenever GitHub adds or retires a model, which is why this page links them instead of repeating their contents:

[source,text]
----
Before picking a model for a hard multi-file refactor, check the model-comparison page's
"complex reasoning" row for the current recommendation, rather than assuming last month's answer
still holds.
----

== Auto model selection

Selecting *Auto* in the model picker, instead of a specific model, routes each request to a model Copilot
judges appropriate for that request's complexity and for real-time model availability; hovering over a chat
response shows which specific model actually answered it. Auto is a reasonable default when you would otherwise
have to guess between a fast and a reasoning model on every request:

.In GitHub Copilot (VS Code)
[source,text]
----
Model picker -> Auto
(hover any response afterward to see which model Copilot actually routed it to)
----

See link:https://docs.github.com/en/copilot/concepts/models/overview[GitHub -- About AI models in Copilot].

== Reasoning / effort levels

As of the date above, VS Code Copilot Chat exposes a per-model *Thinking Effort* control for models that support
adjustable reasoning: opening the model picker and selecting the arrow next to a model name opens a submenu
with levels from `None` up through `High`, and the picker label then shows the chosen level next to the model
name. GitHub's own cloud-agent documentation describes the same idea in different words -- a higher reasoning
level can improve quality on a complex task at the cost of more time and more of the plan's AI-request budget
-- confirming this is a real, current control and not something only VS Code exposes:

.In GitHub Copilot (VS Code)
[source,text]
----
Model picker -> select the model's ">" arrow -> Thinking Effort -> High
(the picker label then reads e.g. "<model name> · High")
----

See link:https://code.visualstudio.com/docs/agent-customization/language-models[VS Code -- Language models in
Visual Studio Code] and
link:https://docs.github.com/en/copilot/how-tos/use-copilot-agents/cloud-agent/changing-the-ai-model[GitHub --
Changing the AI model used by Copilot cloud agent].

== Org policies for model access

An organization owner controls which models beyond the plan's basic set members may use from
*organization Settings -> Copilot -> Models*, where each model-related policy has its own enforcement toggle;
GitHub documents the equivalent enterprise-wide control separately. A model an org policy has not enabled
simply will not appear in a member's picker, which is worth knowing before assuming a missing model is a bug
rather than a policy setting:

[source,text]
----
Org admin: Settings -> Copilot -> Models -> (per-model policy) -> Enabled / Disabled
----

See link:https://docs.github.com/en/copilot/how-tos/administer-copilot/manage-for-organization/manage-policies[GitHub
-- Managing policies for Copilot in your organization].

== Claude Code: `/model`, aliases, effort and fast mode

Claude Code's model controls are session-level rather than split by feature. Running `/model` with no argument
opens an interactive picker; running it with an alias or a full model name switches immediately, and the picker
then asks whether to save the choice as the new default or apply it to this session only:

[source,console]
----
$ claude
> /model
> /model sonnet
----

As of the date above, the documented aliases include a short-name family for the everyday tiers --
`sonnet` (the default for day-to-day coding), `opus` (the strongest reasoning tier, for hard architectural or
debugging work) and `haiku` (the fastest and cheapest tier, for simple, well-scoped tasks) -- plus `default`,
which clears any override and reverts to the account's own runtime default. Anthropic documents further,
more specialized aliases (an extended-context variant of a tier, and a hybrid mode that plans on one tier and
executes on another) alongside this everyday set; because the full alias list is exactly the kind of detail
that changes with each Claude Code release, check
https://code.claude.com/docs/en/model-config[Claude Code -- Model configuration] for the current one rather
than treating any list here as exhaustive.

*Effort* is a separate control from the model itself: it adjusts how much the model reasons before answering,
from a documented low end up through a documented high end, and which exact levels a given model supports
varies by model. Set it with `/effort` inside a session, with the `--effort` flag at startup, or with the
`CLAUDE_CODE_EFFORT_LEVEL` environment variable:

[source,console]
----
$ claude --model opus --effort high
----

*Fast mode* is not a different model -- it is a faster, costlier API configuration for the models that support
it, toggled on and off with `/fast`. Turning it on when the current model does not support it switches the
model to one that does; turning it off leaves you on that model rather than reverting automatically. It trades
cost for latency, which is why xref:ai/ai-assisted-development/context-management.adoc[Managing Context] links
it alongside Claude usage limits rather than repeating the cost figures here (never hard-coded on this page):

[source,console]
----
$ claude
> /fast
----

For a fixed model choice outside an interactive session -- a script, a CI job, or a shell profile -- pass
`--model` on the command line or export `ANTHROPIC_MODEL`, which Claude Code reads at startup and which
`--model` overrides for that one invocation:

[source,console]
----
$ claude --model sonnet "run the DocsAssistant test suite and summarize failures"
$ export ANTHROPIC_MODEL=opus
----

See https://code.claude.com/docs/en/model-config[Claude Code -- Model configuration],
https://code.claude.com/docs/en/cli-reference[Claude Code -- CLI reference] and
https://code.claude.com/docs/en/fast-mode[Claude Code -- Speed up responses with fast mode].

== Matching models to tasks

Both tools converge on the same underlying trade-off -- speed and cost on one end, depth of reasoning on the
other, plus a separate axis for whether the model needs to understand an image -- even though they expose it
through different pickers:

[cols="1,2,2", options="header"]
|===
| Task | Copilot | Claude Code

| Quick, well-scoped edits (rename, small fix, boilerplate)
| A fast/lightweight model, or Auto
| `haiku`, or `sonnet` with a lower effort level

| Planning and debugging across several files
| A reasoning-tier model, with Thinking Effort raised
| `opus`, or `sonnet` with a higher effort level

| Multimodal (screenshot-to-code, explaining a diagram or UI mock)
| A model marked multimodal-capable on the model-comparison page
| A current Claude model with vision support (see
  https://code.claude.com/docs/en/model-config[Claude Code -- Model configuration] for which one)
|===

xref:ai/llm-foundations/choosing-a-model.adoc[Choosing a Model] covers the underlying requirements-shortlist-
evaluate-decide workflow this table is a shortcut for; use that page's process whenever a task does not fit
neatly into one of these three rows.

== Cross-checking with a second model

A model that wrote code, or reviewed it, is not the most reliable judge of its own output -- the same blind
spots that produced a mistake often keep it from noticing the mistake on review. Asking a *second, independent*
model to review the first model's diff or plan catches a class of errors that asking the same model to
"double-check itself" tends to miss, at the cost of a second round of tokens. In practice this means running
the second review in the *other* tool, or in the same tool under a different model:

[source,text]
----
Review this diff for correctness only, not style. Assume it is meant to add a GET /api/pages/{id}
endpoint to DocsController that returns 404 when the id is missing. List any bug, off-by-one error,
or mismatch between the diff and that intent; do not restate what the diff does.

<paste the diff here>
----

Running that exact prompt against `opus` after `sonnet` produced the diff, or pasting it into Copilot Chat
after Claude Code produced the diff, are both instances of the same pattern. This is a lightweight, ad hoc
version of the deterministic-gate idea in
xref:ai/ai-assisted-development/reviewing-ai-generated-code.adoc[Reviewing AI-Generated Code] -- a second model
is a useful extra check, not a replacement for tests, linters and a human reviewer.

BYOK and fully local models -- running an open-weight model yourself instead of calling a hosted one -- are
covered in depth by the planned *Running LLMs Locally* sub-section; this page only notes that the same
task-matching and cross-checking ideas above apply just as well when one side of the comparison is a locally
run model such as `llama3.1:8b` under Ollama 0.34.
