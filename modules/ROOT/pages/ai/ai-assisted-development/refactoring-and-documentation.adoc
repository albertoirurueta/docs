Examples on this page use the current GitHub Copilot Chat extension for VS Code and the current Claude Code CLI,
both checked against their official documentation as of 2026-09-28. The running example is again *DocsAssistant
API*: the controller at `src/main/java/com/example/docsassistant/DocsController.java`, its tests under
`src/test/java/com/example/docsassistant/`, and its embeddings built by the Python script at
`ingest/build_index.py`. This page assumes
xref:ai/ai-assisted-development/prompting-coding-assistants.adoc[Prompting Coding Assistants] and builds on it:
every recipe below is the specificity checklist applied to a specific kind of request.

== Refactoring recipes with AI

Each recipe follows the same shape: describe the smell, ask for the specific transformation (not just "clean this
up"), and read the diff before accepting it. Doing the transformation in one small, reviewable step -- rather than
asking for a whole-file rewrite -- is what keeps the diff easy to check against the original behavior; see
xref:ai/ai-assisted-development/reviewing-ai-generated-code.adoc[Reviewing AI-Generated Code] for the checklist to
run over the result.

=== Extract method

`DocsController` builds an excerpt twice: once for the page itself, once for each related page in the response.

.In DocsAssistant API before the change
[source,java]
----
@GetMapping("/api/pages/{id}/related")
public List<RelatedPage> getRelatedPages(@PathVariable Long id,
                                          @RequestParam(defaultValue = "5") int limit) {
    Page page = pageRepository.findById(id).orElseThrow();
    String text = page.getContent();
    String excerpt = text.length() > 200 ? text.substring(0, 200) + "..." : text;
    page.setExcerpt(excerpt);

    List<RelatedPage> related = embeddingIndex.nearest(id, limit);
    for (RelatedPage r : related) {
        String relatedText = r.getContent();
        r.setExcerpt(relatedText.length() > 200 ? relatedText.substring(0, 200) + "..." : relatedText);
    }
    return related;
}
----

=== Decompose conditional

A nested if/else that only ever returns an empty list on any failing branch is a common early-DocsAssistant
pattern that reads better as a guard clause plus one extracted predicate:

.In DocsAssistant API before the change
[source,java]
----
public List<RelatedPage> recommendRelatedPages(Long pageId, int limit) {
    List<RelatedPage> results;
    if (pageId != null) {
        if (pageRepository.existsById(pageId)) {
            if (limit > 0) {
                results = embeddingIndex.nearest(pageId, limit);
            } else {
                results = List.of();
            }
        } else {
            results = List.of();
        }
    } else {
        results = List.of();
    }
    return results;
}
----

[source,console]

plus a private isValidRequest(Long pageId, int limit) predicate. Every branch that currently
returns List.of() should be covered by the single guard. Run the tests after."
----

.In GitHub Copilot (VS Code)
[source,text]
----

clause that returns List.of(), plus a private isValidRequest(Long pageId, int limit) predicate.

@src/main/java/com/example/docsassistant/DocsController.java to computeRelevanceScore, update every

A rename that only touches one file is safe to ask for directly; a rename of a method used across many files is
exactly the kind of multi-file change where planning first pays off -- see
xref:ai/ai-assisted-development/plan-first-workflows.adoc[Plan-First Workflows] and
https://code.claude.com/docs/en/best-practices[Claude Code -- Best practices], whose own guidance is the
opposite for a small, one-file rename: "If you could describe the diff in one sentence, skip the plan." For the
Copilot side, see https://docs.github.com/en/copilot/concepts/prompting/prompt-engineering[GitHub -- Prompt
engineering for GitHub Copilot Chat].

only sees the file you attached has no way to know whether another module still calls that method.

== The "majority problem" and making AI code your own

Code that no one on the team wrote entirely themselves tends to lose the property that makes it maintainable:
someone who can explain *why* it looks the way it does, not just *what* it does. Call this the majority
problem -- once most of a file's logic arrived through generated diffs that were skimmed and accepted rather
than written and understood, the team's shared mental model of that file erodes, and the next bug or feature in
it costs more than the tests-passing diff suggested it would.

The fix is not to write less AI-assisted code; it is to close the understanding gap before the diff lands, the
same way you would review a colleague's pull request:

* *Read every line before accepting it*, not just the parts the diff highlights -- the same "trust-then-verify
  gap" failure pattern applies whether the code was generated or copy-pasted from search results. See
  https://code.claude.com/docs/en/best-practices[Claude Code -- Best practices].
* *Ask the assistant to explain its own diff* rather than only re-reading it silently -- a prompt like
  `explain why you used a guard clause here instead of the nested if/else` surfaces reasoning that a diff alone
  does not, and any gap in that explanation is worth resolving before merging.
* *Re-derive the tricky parts by hand* once, even when the generated version is correct -- for the parts of a
  change most likely to need a fix in six months, spending a few minutes tracing the logic yourself is what
  turns "code that runs" into "code you own."
* *Use a fresh review pass as a second opinion*, not as a substitute for your own understanding: a subagent or a
  second session reviewing the diff against its stated intent catches gaps a tired first read misses, but it
  does not transfer understanding to you. See
  https://code.claude.com/docs/en/best-practices[Claude Code -- Best practices] ("Add an adversarial review
  step") and xref:ai/ai-assisted-development/reviewing-ai-generated-code.adoc[Reviewing AI-Generated Code].

=== ADR generation

An architecture decision record captures a decision, its context and its consequences so a later reader does not
have to reconstruct the reasoning from the code alone. Asking an assistant for one works best when the prompt
states which decision, what alternatives were considered, and which template to follow:

[source,console]
----
$ claude "write an ADR using the MADR template (Context and Problem Statement, Considered Options,
Decision Outcome, Consequences) documenting why DocsAssistant API's embedding index uses FAISS (in
ingest/build_index.py) rather than a pgvector-backed table, given that the index is rebuilt offline
and served read-only. List both FAISS and pgvector under Considered Options. Save it as
docs/adr/0007-embedding-index-choice.md."
----

.docs/adr/0007-embedding-index-choice.md (generated, then reviewed)
[source,markdown]
----
# Use a FAISS index file for related-page lookup

## Context and Problem Statement
DocsAssistant API's related-pages feature needs nearest-neighbor lookup over page embeddings.
The index is rebuilt offline by ingest/build_index.py and served read-only by DocsController;
no write path exists at query time. Where should the embedding index live?

## Considered Options
* FAISS index file built by ingest/build_index.py and loaded at startup
* pgvector-backed table queried per request

## Decision Outcome
Chosen option: "FAISS index file built by ingest/build_index.py and loaded at startup", because
the index is rebuilt offline and only ever read at query time, so a database write path adds
nothing.

### Consequences
* Good, because query latency does not depend on the database under load.
* Bad, because the index must be rebuilt and redeployed after every content change, instead of
  updating in place.
* Bad, because filtering related pages by metadata (e.g. by section) needs a post-filter step,
  since FAISS itself is not metadata-aware.
----

The headings follow the minimal MADR template; see https://adr.github.io/madr/[MADR -- Markdown Architectural
Decision Records] for the full template and its optional sections (Decision Drivers, Confirmation, Pros and Cons
of the Options). The generated draft is a starting point, not a finished record -- the "Consequences" section in particular
needs a human check that it reflects what the team actually decided to accept, not just what the assistant
inferred from the code.

== Legacy modernisation and translating between languages

=== Legacy modernisation

Modernising old code follows the same loop as any other refactor, just aimed at deprecated APIs and outdated
language features instead of a single method: find the legacy usage, get a recommendation, apply it in a
verifiable increment, and run the tests.

[source,console]
----
$ claude "find deprecated Spring MVC annotations in @src/main/java/com/example/docsassistant/,
suggest their current replacements, and apply them one file at a time, running the tests after
each file"
----

For porting a large codebase to a new language or framework wholesale, rather than modernising it in place,
treat it as a fan-out of many small, independently verifiable migrations instead of one large one; see
https://claude.com/blog/ai-code-migration[Anthropic -- How Anthropic teams use Claude Code for large-scale code
migrations] and https://code.claude.com/docs/en/common-workflows[Claude Code -- Common workflows] ("Refactor
code").

=== Translating between languages

Reimplementing an existing function in another language is a targeted case of the same recipe: give the source
function, name the target language and its idioms, and check the result against the same inputs. DocsAssistant
API's Python scoring helper in `ingest/build_index.py` has a small Java counterpart worth keeping in sync when
the scoring logic changes:

.ingest/build_index.py (excerpt)
[source,python]
----
def cosine_similarity(query_vec, page_vec):
    dot = sum(q * p for q, p in zip(query_vec, page_vec))
    norm_q = sum(q * q for q in query_vec) ** 0.5
    norm_p = sum(p * p for p in page_vec) ** 0.5
    if norm_q == 0 or norm_p == 0:
        return 0.0
    return dot / (norm_q * norm_p)
----

[source,console]
----
$ claude "translate the cosine_similarity function in @ingest/build_index.py into a Java static
method double[] -> double[] -> double in a new class
src/main/java/com/example/docsassistant/ScoreUtils.java, matching the zero-norm guard and zip()'s
stop-at-the-shorter-vector behavior, and add a
unit test under src/test/java/com/example/docsassistant/ that checks the same cases the Python
version would return 0.0 for."
----

.src/main/java/com/example/docsassistant/ScoreUtils.java (generated)
[source,java]
----
package com.example.docsassistant;

public final class ScoreUtils {

    private ScoreUtils() {
    }

    public static double cosineSimilarity(double[] queryVec, double[] pageVec) {
        // zip() in the Python version stops at the shorter vector; the norms still use every element.
        int n = Math.min(queryVec.length, pageVec.length);
        double dot = 0.0;
        for (int i = 0; i < n; i++) {
            dot += queryVec[i] * pageVec[i];
        }
        double normQ = 0.0;
        for (double q : queryVec) {
            normQ += q * q;
        }
        double normP = 0.0;
        for (double p : pageVec) {
            normP += p * p;
        }
        if (normQ == 0.0 || normP == 0.0) {
            return 0.0;
        }
        return dot / (Math.sqrt(normQ) * Math.sqrt(normP));
    }
}
----

A translated function still needs the same verification as any other generated code: run it against cases the
original handles (here, the zero-norm guard and vectors of different lengths) before treating the two
implementations as equivalent. A naive port that loops over `queryVec.length` alone would throw
`ArrayIndexOutOfBoundsException` when `pageVec` is shorter, where the Python silently truncates, and only a
mismatched-length test case exposes that divergence. See
https://code.claude.com/docs/en/best-practices[Claude Code -- Best practices] ("Give Claude a way to verify its
work").
