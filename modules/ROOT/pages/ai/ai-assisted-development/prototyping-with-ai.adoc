= Prototyping with AI
:description: App builders (v0, Lovable, Bolt, Firebase Studio) and screenshot-to-code, the throw-away vs. evolve decision, and the path from a generated prototype to a production DocsAssistant API feature.
:keywords: v0, Lovable, Bolt, Firebase Studio, app builder, screenshot to code, vibe coding, prototype, throw-away, production readiness

include::partial$ai-ai-assisted-development-disclaimer.adoc[]

App builders and screenshot-to-code turn a prompt or an image into a runnable UI in minutes, which is exactly
what makes them easy to misuse: a prototype optimized for speed is not automatically safe to ship. This page
compares the current app builders (as of 2026-09-28, checked against each product's own docs, since this
category changes fast), shows how Copilot Chat and Claude Code each turn a screenshot into code, and gives a
checklist for the point where a `v0` or `bolt.new` prototype becomes a real *DocsAssistant API* feature.

== App builders

An app builder is a prompt- or screenshot-driven tool that generates a runnable UI or small full-stack app from
scratch, optimized for a fast, disposable first version rather than for editing an existing large codebase --
see xref:ai/ai-assisted-development/tool-landscape.adoc[The AI Coding Tool Landscape] for how this category sits
next to completion, chat and agent tools. As of 2026-09-28:

[cols="1,3,2", options="header"]
|===
| Tool | What it generates | Official docs

| v0 (Vercel)
| A Next.js / React UI from a prompt, a screenshot or a Figma file, deployable straight to Vercel.
| https://v0.app/docs[v0 by Vercel — What is v0?]

| Lovable
| A full-stack app (frontend, backend, auth and database) from a prompt or an attached screenshot, iterated on by chatting.
| https://docs.lovable.dev/introduction/welcome[Lovable — Welcome to Lovable]

| Bolt (StackBlitz)
| A full-stack web app that runs in-browser via WebContainers, with Figma import for design-to-code.
| https://support.bolt.new[Bolt — Help Center]

| Firebase Studio (Google)
| A cloud-based, agent-assisted IDE and app-prototyping workspace, backed by Firebase's own hosting, auth and database.
| https://firebase.google.com/docs/studio[Firebase — Firebase Studio]
|===

These products ship weekly and this table intentionally lists no prices or model names; check each vendor's own
pricing and docs page before choosing one for a real project. A prompt typed into a fresh v0 project for the
running scenario:

.App builder -- a prompt that generates a new UI
[source,text]
----
Build a page that lists DocsAssistant's indexed pages with a search box, a title, a short
excerpt and a "last updated" date for each result.
----

This is the same example used on xref:ai/ai-assisted-development/tool-landscape.adoc[The AI Coding Tool
Landscape]; the point there is where app builders sit on the tool ladder, the point here is what happens to the
result afterward.

== Screenshot-to-code

Rather than typing a prompt, screenshot-to-code starts from an image -- a design mock, a competitor's page or a
whiteboard photo -- and asks the assistant to reproduce or explain it. Both app builders and general-purpose
coding assistants support this; the mechanics differ per tool.

.In GitHub Copilot Chat (VS Code)
[source,text]
----
[drag DocsAssistant-search-mock.png onto the Chat view, or paste it from the clipboard]
Recreate this search results layout as a React component, matching the existing DocsAssistant
frontend's styling.
----

Copilot Chat accepts an attached or pasted image alongside the prompt and treats it as visual context, the same
mechanism covered in
xref:ai/ai-assisted-development/copilot-getting-started.adoc[Getting Started with GitHub Copilot]'s "Attaching
files and images" section. See
https://code.visualstudio.com/docs/chat/copilot-chat-context[VS Code — Add context to chat].

.In Claude Code
[source,console]
----
$ claude
> [Ctrl+V to paste DocsAssistant-search-mock.png from the clipboard, or drag it into the window]
> Recreate this search results layout as a React component, matching the existing
  DocsAssistant frontend's styling.
----

Claude Code accepts an image the same three ways on any platform: drag-and-drop into the window, a clipboard
paste (`Ctrl+V`, or `Alt+V` on Windows and WSL -- `Cmd+V` is intercepted by some terminal apps before it reaches
the CLI), or a plain file path given in the prompt text. See
https://code.claude.com/docs/en/common-workflows#work-with-images[Claude Code — Common workflows: Work with
images].

Several app builders build screenshot- or design-to-code directly into their own flow instead of relying on a
general chat attachment: v0 and Lovable both accept a pasted screenshot or a linked Figma file as the starting
prompt, and Bolt imports a Figma design directly into a new project. Check each product's own docs (linked in
the table above) for the current mechanism, since this is an area where products iterate quickly.

== Throw-away vs. evolve

Before writing the first prompt into an app builder, decide whether the result is disposable or a real starting
point -- the two paths call for different amounts of care from the start:

[cols="1,2,2", options="header"]
|===
| | Throw-away prototype | Evolve into production

| Goal
| Validate an idea, a layout or a flow quickly; the code itself is not kept.
| The generated code becomes (part of) the shipped *DocsAssistant API* frontend or a similar real feature.

| Auth, data and secrets
| Mock data, a stub backend, or the app builder's own scratch database; never real user data or production credentials.
| Wired to the project's real backend and secret management from the first commit that leaves the prototype.

| Review depth
| Skim for obviously broken behavior; a detailed line-by-line review is wasted effort on code you're about to discard.
| Full review against
xref:ai/ai-assisted-development/reviewing-ai-generated-code.adoc[Reviewing AI-Generated Code] and
xref:ai/ai-assisted-development/securing-ai-assisted-development.adoc[Securing AI-Assisted Development], the same
bar as any other AI-generated change.

| Where it lives
| The app builder's own project, a scratch branch, or nowhere durable at all once the demo is over.
| Imported into the DocsAssistant API repository, under normal version control, CI and code ownership.

| Decision trigger
| Answers "could this work?" or "what should this look like?" -- once answered, the code's job is done.
| Answers "yes, and we're shipping this" -- someone with the authority to make that call has said so explicitly.
|===

The failure mode this table exists to prevent is a prototype quietly becoming production because nobody made
the decision explicitly -- it just kept running because it worked in the demo.

== From prototype to production

Once the decision above is "evolve," treat the generated code exactly like any other AI-written change before it
merges:

* [ ] Read every generated file rather than trusting the preview -- an app builder's live preview can look
  correct while the underlying code has placeholder logic, hard-coded sample data, or a hallucinated dependency.
* [ ] Import the code into the project's own repository and version control instead of continuing to iterate
  inside the app builder, so it gets code review, CI and history like everything else.
* [ ] Run the checklist in
  xref:ai/ai-assisted-development/reviewing-ai-generated-code.adoc[Reviewing AI-Generated Code]: intent match,
  off-by-one errors, placeholders, hallucinated APIs and packages, over-engineering, and test quality.
* [ ] Run the checklist in
  xref:ai/ai-assisted-development/securing-ai-assisted-development.adoc[Securing AI-Assisted Development]:
  replace any scratch credentials or mock auth with the project's real secret management, and check for the
  common vulnerability classes it covers (secrets, injection, insecure defaults).
* [ ] Add or generate the tests the app builder didn't write -- most optimize for a working demo, not for
  coverage; see
  xref:ai/ai-assisted-development/testing-and-debugging-with-ai.adoc[Testing and Debugging with AI].
* [ ] Match the target codebase's own style, dependencies and structure -- an app builder defaults to its own
  stack (for example a fresh Next.js app) rather than *DocsAssistant API*'s existing Spring Boot + Python layout,
  so a UI prototype typically gets rebuilt against the real frontend rather than copied in wholesale.
* [ ] Confirm the deployment target: an app builder's one-click deploy (for example to Vercel or Firebase
  Hosting) is convenient for a demo link, but a production feature deploys through the project's own pipeline.
