= Getting Started with Claude Code
:description: Installing, logging in and driving Claude Code's agentic loop, permission modes, checkpoints, sessions and IDE integrations.
:keywords: Claude Code, claude --version, agentic loop, permission modes, plan mode, checkpoints, rewind, claude --continue, claude --resume, VS Code extension, JetBrains plugin, slash commands

include::partial$ai-ai-assisted-development-disclaimer.adoc[]

Examples on this page target the Claude Code CLI, checked against the official quickstart and permission-modes
pages at https://code.claude.com/docs/en/ as of 2026-09-28. Running `claude --version` on a current native
install prints a version number followed by `(Claude Code)`; native installs update themselves automatically in
the background, so the exact number keeps moving, and this page describes behavior rather than pinning one. The
running example is the same *DocsAssistant API* used throughout this sub-section, a Spring Boot + Python sample
whose Java sources live under `src/main/java/com/example/docsassistant/`.

== Install and log in

The current recommended install is a single native-install command, one per platform, from
https://code.claude.com/docs/en/quickstart[the official quickstart] (checked 2026-09-28):

.macOS, Linux, WSL
[source,console]
----
$ curl -fsSL https://claude.ai/install.sh | bash
----

.Windows PowerShell
[source,console]
----
$ irm https://claude.ai/install.ps1 | iex
----

Homebrew (`brew install --cask claude-code`) and WinGet (`winget install Anthropic.ClaudeCode`) are documented
alternatives; unlike the native installer, those two do not auto-update, so `brew upgrade claude-code` or
`winget upgrade Anthropic.ClaudeCode` has to be run manually. After installing, open a new terminal and confirm
it worked:

[source,console]
----
$ claude --version
----

Claude Code needs an account. Starting a session with no arguments prompts you to log in on first use:

[source,console]
----
$ claude
----

Follow the browser prompts to authenticate with a Claude subscription (Pro, Max, Team or Enterprise) or a Claude
Console account; if `ANTHROPIC_API_KEY` is set in the environment, Claude Code asks you to approve that key
instead of prompting for a browser login. Once logged in, credentials are stored and later sessions skip this
step. To switch accounts or re-authenticate, run `/login` inside a running session. See
https://code.claude.com/docs/en/quickstart[Claude Code — Quickstart].

== The agentic loop

Claude Code's own architecture page describes a single loop, not a fixed sequence of named stages: for any task
it *gathers context* (reading files, searching, running read-only commands), *takes action* (editing files,
running commands, using tools), and *verifies results* (running tests, re-reading changed files, checking
output) -- and these three phases interleave and repeat rather than running once each. A one-line question may
only need the first phase; a bug fix typically cycles through all three multiple times, each result feeding the
next decision, until the task is done or you interrupt it. You stay part of the loop throughout: pressing `Esc`
stops the current tool call immediately, and typing a correction without stopping lets Claude read it as soon as
the current tool calls finish.

[mermaid]
....
flowchart LR
    P[Your prompt] --> G[Gather context]
    G --> A[Take action]
    A --> V[Verify results]
    V -->|task not done| G
    V -->|task complete| D[Done / waiting for you]
    P -.->|you can interrupt at any point| D
....

See https://code.claude.com/docs/en/how-claude-code-works[Claude Code — How Claude Code works].

== Referencing files with `@`

Typing `@` opens a path-suggestion menu; press Tab or Enter to accept a highlighted path, then Enter again to
send the message. An `@` reference works on a single file, a whole directory (which shows a file listing, not
its contents), or, in the form `@server:resource`, a resource exposed by a connected MCP server. Referencing a
file also pulls in any `CLAUDE.md` in that file's directory and its parent directories, which is why `@`
references are the fastest way to point Claude at the exact context a task needs instead of waiting for it to
search the repository itself:

[source,console]
----
$ claude "explain the pagination logic in @src/main/java/com/example/docsassistant/DocsController.java"
----

See https://code.claude.com/docs/en/common-workflows[Claude Code — Common workflows].

== Permission modes and plan mode

A permission mode sets what Claude can do without asking first. As of 2026-09-28, the CLI's `Shift+Tab` cycles
through the modes and the status bar names the active one; the ones most relevant when getting started are:

[cols="1,3", options="header"]
|===
| Mode (status bar label) | What runs without a prompt

| Manual (`default`)
| Reads only; Claude asks before file edits and shell commands.

| Accept edits (`acceptEdits`)
| Reads, file edits and common filesystem commands (`mkdir`, `mv`, `cp`, and similar).

| Plan (`plan`)
| Reads and exploration only; edits stay blocked until you approve a plan.

| Auto (`auto`)
| Almost everything, with a separate classifier model reviewing actions in the background instead of asking you.
|===

Depending on the Claude Code version, plan, and account, a new interactive session can start in Manual or in
Auto mode by default; either way, `Shift+Tab` switches modes at any time. Plan mode specifically is entered by
pressing `Shift+Tab` until the status bar shows `⏸ plan mode on`, by prefixing a single prompt with `/plan`, or
by starting the session directly in that mode:

[source,console]
----
$ claude --permission-mode plan
----

In plan mode Claude reads files and proposes a plan without editing anything; once it presents the plan you
choose to approve it (switching the session into an editing mode), keep planning, or discard it. This is the
foundation the sub-section's own
xref:ai/ai-assisted-development/plan-first-workflows.adoc[Plan-First Workflows] page builds on. See
https://code.claude.com/docs/en/permission-modes[Claude Code — Choose a permission mode].

== Checkpoints and rewind

Claude Code snapshots the files its own editing tools touch before each prompt that starts a new turn, keeping
the most recent checkpoints from the session. Running `/rewind`, or pressing `Esc` twice with an empty prompt
input, opens a menu listing every earlier prompt in the session; picking one offers *Restore code and
conversation*, *Restore conversation* only, *Restore code* only, or *summarize* the conversation from or up to
that point:

[source,console]
----
$ claude
> /rewind
----

Checkpoints only cover files Claude's own file-editing tools changed -- a file a Bash command deleted, moved or
overwrote (`rm`, `mv`, `cp`) is not tracked and cannot be restored this way, and checkpoints are not a
replacement for Git history. See https://code.claude.com/docs/en/permission-modes[Claude Code — Choose a
permission mode] for how the active permission mode changes what needs approval before it even reaches a
checkpoint.

== Sessions, IDE extensions, desktop and web

Every conversation is saved locally and tied to the directory it started in, so a task can span more than one
sitting. `claude --continue` (or `-c`) reopens the most recent session in the current directory and appends to
it; `claude --resume` (or `-r`) opens a picker (or takes a session ID or name directly) to resume a specific
past session:

[source,console]
----
$ claude --continue
$ claude --resume "docs-endpoint"
----

Beyond the terminal, the same agentic loop and tools are available through the *VS Code extension* (a native
panel with inline diffs, `@`-mentions with selected line ranges, and plan review before edits land), the
*JetBrains plugin* (which runs Claude Code in the IDE's own terminal, so `Shift+Tab` and `--permission-mode`
behave exactly as on the CLI), the *desktop app*, and the *web* at https://claude.ai/code[claude.ai/code]. Which
interface you use changes only where the conversation is displayed and, for cloud sessions, where the code
runs -- the underlying loop, tools and checkpoints are the same everywhere. See
https://code.claude.com/docs/en/quickstart[Claude Code — Quickstart] and
xref:ai/ai-assisted-development/parallel-sessions-and-worktrees.adoc[Parallel Sessions & Worktrees] for running
several sessions side by side with `git worktree`.

== The `/` command basics

Typing `/` inside a running session lists the available session commands; Tab completes a partial name. As of
2026-09-28 the everyday ones are:

[cols="1,3", options="header"]
|===
| Command | What it does

| `/help`
| Shows available commands and how to get further help.

| `/clear`
| Starts a new conversation with an empty context window (aliased as `/reset` / `/new`); pass a name to label the
conversation you're leaving so `/resume` can find it again.

| `/compact`
| Frees up context by summarizing the conversation so far; takes optional focus instructions, e.g.
`/compact focus on the controller changes`.

| `/model`
| Switches which Claude model the session uses, without restarting it.

| `/init`
| Generates a starter `CLAUDE.md` for the current project.

| `/rewind`
| Opens the checkpoint menu described above.

| `/context`
| Visualizes current context-window usage.
|===

See https://code.claude.com/docs/en/common-workflows[Claude Code — Common workflows] for these used inside
longer recipes, and xref:ai/ai-assisted-development/context-management.adoc[Managing Context] for `/compact` and
`/context` in more depth.

== Example: adding an endpoint to DocsAssistant API

This is the same task as
xref:ai/ai-assisted-development/copilot-getting-started.adoc[Getting Started with GitHub Copilot]'s chat
example: add a `GET /api/pages/\{id}` endpoint (the identifier is escaped here so AsciiDoc doesn't read it as an
attribute reference) to `DocsController`. The existing controller has a list endpoint only:

[.In DocsAssistant API before the change]
[source,java]
----
package com.example.docsassistant;

import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RestController;

import java.util.List;

@RestController
public class DocsController {

    private final PageRepository pageRepository;

    public DocsController(PageRepository pageRepository) {
        this.pageRepository = pageRepository;
    }

    @GetMapping("/api/pages")
    public List<PageSummary> listPages() {
        return pageRepository.findAllSummaries();
    }
}
----

.In Claude Code
[source,console]
----
$ claude "add a GET /api/pages/{id} endpoint to @src/main/java/com/example/docsassistant/DocsController.java
that returns a single page by id, using PageRepository, and returns a 404 when the id doesn't exist"
----

Claude reads the referenced file plus `PageRepository` and `PageSummary` on its own, proposes the change, and
(in Manual or Accept-edits mode) shows this diff before or as it applies it:

[source,diff]
----
 package com.example.docsassistant;

+import org.springframework.http.ResponseEntity;
 import org.springframework.web.bind.annotation.GetMapping;
+import org.springframework.web.bind.annotation.PathVariable;
 import org.springframework.web.bind.annotation.RestController;

 import java.util.List;

 @RestController
 public class DocsController {

     private final PageRepository pageRepository;

     public DocsController(PageRepository pageRepository) {
         this.pageRepository = pageRepository;
     }

     @GetMapping("/api/pages")
     public List<PageSummary> listPages() {
         return pageRepository.findAllSummaries();
     }
+
+    @GetMapping("/api/pages/{id}")
+    public ResponseEntity<PageSummary> getPage(@PathVariable Long id) {
+        return pageRepository.findSummaryById(id)
+                .map(ResponseEntity::ok)
+                .orElseGet(() -> ResponseEntity.notFound().build());
+    }
 }
----

Reviewing this diff before it lands is exactly what
xref:ai/ai-assisted-development/reviewing-ai-generated-code.adoc[Reviewing AI-Generated Code] covers in more
depth; the immediate follow-up here is asking Claude to run the project's tests to verify the new endpoint,
which is the "verify" part of the agentic loop above.
