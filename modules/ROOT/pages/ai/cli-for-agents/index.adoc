A command-line tool that an AI agent can drive is the same kind of tool a careful engineer would want anyway: predictable
streams, honest exit codes, structured output, no surprise prompts and safe defaults. This sub-section collects those
practices, shows them on one running example, and then shows how to wrap the finished tool as an MCP server or an agent
tool. The versions used are listed in <<_version_baseline,Version baseline>>, all checked on 2026-09-30, and every page
repeats the subset it needs in its own lead paragraph.

== Why CLIs work well with agents

An agent that can run a shell command can already use a very large tool ecosystem, and a CLI has properties that suit
that style of work:

* *Nothing to load up front.* A command costs context only when it is run, and only its output is paid for. Claude Code's
  own guidance treats command-line tools as a context-efficient way to reach external services (see
  https://code.claude.com/docs/en/best-practices[Claude Code -- Best practices]). Tool schemas, by contrast, are usually
  loaded before the first call.
* *Models already know the common ones.* `git`, `gh`, `curl` and `jq` appear throughout training data, so little
  description is needed; an unfamiliar tool costs one `--help` call, which is why
  xref:ai/cli-for-agents/self-describing-help.adoc[Self-Describing Help] matters.
* *Composition is built in.* Pipes, redirection and exit codes let an agent chain steps without a bespoke integration,
  which only works when the tool respects
  xref:ai/cli-for-agents/streams-and-exit-codes.adoc[Streams & Exit Codes].
* *Humans and CI use the same interface.* One implementation serves a terminal, a script and an agent, and the same
  contract can later be exposed as an MCP tool (see xref:ai/cli-for-agents/cli-vs-mcp.adoc[CLI vs. MCP] for the honest
  trade-offs, including where MCP is the better fit).
* *Guardrails already exist.* Hosts gate shell access with permission rules and sandboxes, described for Claude Code on
  xref:ai/customizing-ai-workflows/permissions-and-settings.adoc[Permissions & Settings]; a well-designed CLI adds
  dry-runs, confirmations and least-privilege credentials on top.

The price is that a CLI written only for people is hostile to agents: colour codes and spinners in captured output,
prompts that hang, human-only error text, unbounded output and unparseable tables. The pages below remove each of those
problems in turn. The tool-design ideas behind them are the ones in
xref:ai/agents/tool-design.adoc[Tool Design] and xref:ai/mcp/designing-good-mcp-servers.adoc[Designing Good MCP Servers],
applied to a process instead of a protocol.

== Three audiences, one tool

A command-line tool has three kinds of caller, and a good design serves all of them from one implementation.

== The docsctl running example

Every page uses the same small, fictional tool, *docsctl*, a command-line client for the documentation of this site. It
exists only on these pages, its behaviour is illustrative, and its contract is repeated identically wherever it is used so
that snippets in different languages stay comparable.

.The docsctl commands
[cols="2,3,2",options="header"]
|===
| Command | What it does | Safety

| `docsctl search QUERY`
| Full-text search over the documentation; supports `--component`, `--limit` and `--cursor`.
| Read-only, idempotent

| `docsctl show PAGE`
| Returns one page such as `irurueta-algebra::index.adoc`, optionally one section, with `--max-chars`.
| Read-only, idempotent

| `docsctl list-components`
| Lists the documented components and their versions.
| Read-only, idempotent

| `docsctl validate [PATH]`
| Checks a documentation tree for broken references and reports problems with a code, a line and a hint.
| Read-only, idempotent

| `docsctl publish --component NAME`
| Publishes a component; `--dry-run` prints a JSON plan and a confirmation token is required to apply it.
| Destructive, needs confirmation, idempotent with the same key

| `docsctl login`, `logout`, `schema`, `completion`
| Credentials, the machine-readable command tree, and shell completion.
| Credentials only, or read-only
|===

Every command accepts `--json` (or `--format json|jsonl|text`), `--no-input`, `--yes`, `--timeout` and `--no-color`,
writes data to stdout and messages to stderr, and ends with one of a small set of documented exit codes. A search looks
like this from a script or an agent:

.Searching from a script: data on stdout, nothing else
[source,bash]
----
docsctl search kalman --component irurueta-statistics --limit 3 --json --fields id,title,score
----

Output (illustrative):

[source,json]
----
{"nextCursor":null,"query":"kalman","results":[{"id":"irurueta-statistics::kalman.adoc","score":0.91,"title":"Kalman filter"}],"schemaVersion":1,"total":1,"truncated":false}
----

The primary implementations are in Python with Typer (xref:ai/cli-for-agents/frameworks-python.adoc[Python CLI Frameworks])
and in Java with picocli, compiled to a native binary with GraalVM Native Image
(xref:ai/cli-for-agents/frameworks-java.adoc[Java CLI Frameworks]). Shorter equivalents cover
xref:ai/cli-for-agents/frameworks-node.adoc[Node.js] (commander),
xref:ai/cli-for-agents/frameworks-go-and-rust.adoc[Go and Rust] (Cobra; clap, with a Ratatui interface and a Rig agent) and
xref:ai/cli-for-agents/frameworks-swift-and-dotnet.adoc[Swift and .NET] (swift-argument-parser with SwiftTUI;
System.CommandLine). The finished tool is then wrapped three ways: as an MCP server (Python FastMCP, the TypeScript SDK and
Spring AI `@McpTool`) on xref:ai/cli-for-agents/wrapping-as-an-mcp-server.adoc[Wrapping a CLI as an MCP Server], and as a
LangChain `@tool`, a Spring AI `@Tool` and a LangChain4j `@Tool` on
xref:ai/cli-for-agents/wrapping-as-an-agent-tool.adoc[Wrapping a CLI as an Agent Tool], which also shows using the CLI
directly from Claude Code and from Copilot agent mode.
