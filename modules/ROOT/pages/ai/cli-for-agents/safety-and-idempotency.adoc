An agent will call your command with confidence, sometimes with the wrong arguments, and sometimes twice. It cannot see
a consequence it was not told about. The tool therefore has to carry the safety: harmless by default, able to show what
it would do, able to stop and ask, and safe to repeat. This page turns those requirements into a pattern that works for a
person at a terminal, a CI job and an agent, and that maps cleanly onto the confirmation and annotation mechanisms of MCP and
agent frameworks (see xref:ai/agents/tool-design.adoc[Tool Design] and
xref:ai/agents/human-in-the-loop.adoc[Human-in-the-Loop]).

== Read-only by default

Split commands by what they can change, and make the dangerous ones impossible to reach by accident.

* **Reads are reads.** `search`, `show`, `list-components` and `validate` in `docsctl` have no side effects, and say so in
  their metadata (`readOnly: true`), which the help, the command tree and an MCP wrapper all reuse.
* **Writes are explicit commands,** not modes of a read command: `docsctl publish`, not `docsctl show --write`. Reading
  the command name should tell the reader which side they are on.
* **The dangerous flag is opt-in, never default,** and its name says what it does (`--force`, not `--fast`).
* **Least privilege in the credential,** too: a token that can only read cannot publish however the command line is
  spelled. That is a property of the service the CLI talks to, and the strongest control there is.

Agent hosts add their own allow and deny rules on top; see
xref:ai/customizing-ai-workflows/permissions-and-settings.adoc[Permissions & Settings]. Those rules are matched against
command lines, so a clear split between read commands and write commands makes them easy to write.

== --dry-run and JSON plans

A dry run answers "what would you do?" without doing it. For humans a list of lines is enough; for agents the plan should be
data they can inspect, summarise for the user, and hand back.

.docsctl publish --dry-run
[source,sh]
----
$ docsctl publish --component irurueta-algebra --dry-run --json
----

[source,json]
----
{"component":"irurueta-algebra","confirm":{"command":"docsctl publish --component irurueta-algebra --confirm-token pln_7c41e9 --json","required":true},"dryRun":true,"plan":{"add":3,"change":1,"files":["index.html","matrix-inversion.html","matrix-decompositions.html","search-index.js"],"remove":0},"planId":"pln_7c41e9","schemaVersion":1}
----

Rules for a dry run that can be trusted:

* **It exits 0 and writes nothing:** no files, no network side effects, no credential-store changes. (Reading remote state to
  compute the plan is fine.)
* **It uses the same code path** as the real run up to the point of the write, so the plan cannot drift from what actually
  happens. A dry run that is a separate approximation teaches the agent to distrust it.
* **The plan is structured:** counts by kind of change (`add`, `change`, `remove`), the list of affected items, and enough
  identification (`planId`) to refer to it later.
* **It says how to proceed** through the `confirm` object, described next.
* **It has a stable schema,** like any other output (see
  xref:ai/cli-for-agents/machine-readable-output.adoc[Machine-Readable Output]).

== The confirmation-envelope pattern

Humans get a prompt: "Publish 4 files? [y/N]". An agent has no reliable way to answer a prompt, and a prompt on a
non-interactive stdin would hang or be auto-answered. The pattern for agents replaces the prompt with a *refusal that tells
the caller exactly how to proceed*.

. The caller runs the destructive command without a confirmation.
. If it is not confirmed, the tool exits with a dedicated code, **5 (`CONFIRMATION_REQUIRED`)**, writes nothing, and puts an
error envelope on stderr that includes **the exact command that would confirm**.
. The agent shows the plan to the user (or to a policy check) and, only if approved, runs the confirm command.

.The confirmation envelope on stderr, exit code 5
[source,json]
----
{"error":{"code":"CONFIRMATION_REQUIRED","details":{"confirmCommand":"docsctl publish --component irurueta-algebra --confirm-token pln_7c41e9 --json","plan":{"add":3,"change":1,"remove":0}},"exitCode":5,"hint":"Review the plan, then run the confirm command.","message":"Publishing overwrites the live site for irurueta-algebra.","retryable":false},"schemaVersion":1}
----

Why this design:

* **The confirm command is the only bypass** the message names, and it is bound to the plan through the token. A token
  from a dry run for `irurueta-algebra` does not confirm a publish of anything else, and it expires; if the state changed
  since the plan, the tool rejects the token and the agent has to plan again.
* **The exit code is distinct** so callers branch on it without parsing text (see
  xref:ai/cli-for-agents/streams-and-exit-codes.adoc[Streams & Exit Codes]). 5 means "ask", not "failed".
* **The human keeps the decision.** The agent cannot confirm by itself unless a person or a policy allowed it: a wrapper that
  exposes the tool should return the envelope as a structured error and never supply the token on its own (see
  xref:ai/cli-for-agents/wrapping-as-an-mcp-server.adoc[Wrapping a CLI as an MCP Server]).
* **Interactive humans still get the prompt.** On a TTY, `docsctl publish` asks; the same command with `--no-input` or on a
  non-TTY fails fast with exit 5 and names the bypass, as described on
  xref:ai/cli-for-agents/tty-colour-and-interactivity.adoc[TTY, Colour & Interactivity].

.Emitting the envelope (Python)
[source,python]
----
import json
import sys

EXIT_CONFIRMATION_REQUIRED = 5


def require_confirmation(component: str, plan: dict, plan_id: str) -> None:
    command = f"docsctl publish --component {component} --confirm-token {plan_id} --json"
    envelope = {
        "schemaVersion": 1,
        "error": {
            "code": "CONFIRMATION_REQUIRED",
            "exitCode": EXIT_CONFIRMATION_REQUIRED,
            "message": f"Publishing overwrites the live site for {component}.",
            "hint": "Review the plan, then run the confirm command.",
            "retryable": False,
            "details": {"plan": plan, "confirmCommand": command},
        },
    }
    print(json.dumps(envelope, sort_keys=True), file=sys.stderr)
    sys.exit(EXIT_CONFIRMATION_REQUIRED)
----

The command string is built from values the tool itself validated (a known component name and a token it generated). An
agent should still run it as an argv list, not through a shell, as the security rules of this sub-section require.

== --force and --yes

Two different flags do two different jobs, and conflating them is a common mistake.

* **`--yes` / `-y` answers a confirmation prompt** with "yes" for callers that have already decided. It does not remove
  safety checks; it only removes the question.
* **`--force` overrides a check the tool would otherwise enforce:** publishing over a newer remote version, ignoring
  `validate` problems, skipping the plan-binding token. It is named for what it overrides, documented as dangerous, and
  never implied by another flag.

For agents the practical rule is: the help says that the normal path is dry-run then confirm, and that `--force` exists for a
person who has decided to bypass the guard. A skill or instructions file can then say "never pass `--force`" (see
xref:ai/cli-for-agents/self-describing-help.adoc[Self-Describing Help]), and a host's permission rules can deny it outright.

.The three ways to run docsctl publish
[source,sh]
----
# 1. Plan, then confirm with the token from the plan (the agent path)
docsctl publish --component irurueta-algebra --dry-run --json
docsctl publish --component irurueta-algebra --confirm-token pln_7c41e9 --json

# 2. A person at a terminal: prompted, answers y
docsctl publish --component irurueta-algebra

# 3. A deliberate bypass of the plan binding (documented as dangerous)
docsctl publish --component irurueta-algebra --force
----

== Idempotent create-or-update

Agents retry. A network blip, a timeout (exit 6) or a crashed session leads to the same command being run again, and the
second run must not make things worse: no duplicate resource, no double charge, no half-applied change. There are two
complementary tools.

* **Design the operation as "make it so", not "do it".** `publish` declares the desired state of the site for a component;
  running it again with the same content changes nothing and exits 0 (an idempotent no-op, which the exit-code table counts
  as success). Prefer *create-or-update* (upsert) to separate `create` and `update` commands that fail in awkward ways on
  the second call.
* **Accept an idempotency key for operations that cannot be naturally idempotent.** `--idempotency-key KEY` lets the caller
  label an attempt; the tool remembers the result for that key and returns it again instead of repeating the work. The
  key is generated once per intention by the caller and reused on every retry.

.Retrying safely with the same key
[source,sh]
----
KEY=$(uuidgen)
docsctl publish --component irurueta-algebra --confirm-token pln_7c41e9 --idempotency-key "$KEY" --json
# ...timeout, exit 6: run the very same command again
docsctl publish --component irurueta-algebra --confirm-token pln_7c41e9 --idempotency-key "$KEY" --json
----

The second call either finds the first still running, waits for it, or returns its recorded result; it never publishes twice.
The same idea is the `Idempotency-Key` HTTP header, which is what a tool like this would send to its service.

Reference: https://datatracker.ietf.org/doc/draft-ietf-httpapi-idempotency-key-header/[IETF Internet-Draft (expired, not an RFC) -- The Idempotency-Key HTTP Header Field].

== Undo and rollback hints

The friendliest destructive command is one that says how to reverse it. After a real change, print (in the result, on stdout)
the command that undoes it, so an agent or a person is not left reconstructing it under stress.

.The result of a confirmed publish
[source,json]
----
{"component":"irurueta-algebra","published":{"add":3,"change":1,"remove":0},"rollback":{"command":"docsctl publish --component irurueta-algebra --rollback pln_7c41e9 --json","note":"Restores the previous published version."},"schemaVersion":1}
----

* **Prefer reversible operations:** publish to a new version and switch a pointer, move to a trash instead of deleting,
  keep the previous version for a period.
* **Say when something cannot be undone,** in the plan itself (`"reversible": false`), so the agent tells the user before the
  confirmation, not after.
* **Log what was done,** with the plan id, on stderr and, if you can, in an audit trail: the evidence a review needs
  afterwards.

The `--rollback` flag shown here is illustrative of the idea and not part of the base contract of this sub-section.

== The flow

.Dry run, confirm and apply for docsctl publish
[mermaid]
....
flowchart TD
  A[Agent runs docsctl publish --dry-run --json] --> B{Exit code 0?}
  B -- no --> E[Read error envelope hint and fix the call]
  B -- yes --> C[Plan with planId and confirm command]
  C --> D{Plan acceptable to the user or policy?}
  D -- no --> X[Stop, nothing was written]
  D -- yes --> F[Agent runs the confirm command]
  F --> G{Exit code}
  G -- 0 --> H[Applied, result includes rollback command]
  G -- 5 --> C
  G -- 6 --> R[Retry the same command with the same idempotency key]
  R --> F
  G -- 7 --> L[Run docsctl login, then retry]
  L --> F
  A2[Agent runs docsctl publish without a token] --> G5[Exit 5 with confirmation envelope]
  G5 --> C
....

Reading the diagram: a bare `publish` never writes, it lands on the confirmation envelope (exit 5) and thus on the same plan
step as a dry run; only the confirm command applies changes; and every failure has a next step the exit code identifies.
