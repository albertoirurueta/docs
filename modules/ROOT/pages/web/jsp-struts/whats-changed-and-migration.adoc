JCP records, the Jakarta specification pages and the Struts announcements that

[#javax-to-jakarta]
== From javax to jakarta, with the Tomcat Migration Tool

Jakarta Servlet 5.0 "is only a change of namespaces", in the words of the specification's compatibility appendix, and
migrating a Servlet 4.0 project to 5.0 or later "requires the replacement of the namespace `+javax.*+` with `+jakarta.*+`".
Pages 3.0 lists the same move first among its changes (`javax.servlet.jsp` to `jakarta.servlet.jsp`), Jakarta Tags
3.0 says that applications using the Java EE package "will need to change this to the Jakarta EE package", and the
Tomcat migration guide calls it "a significant breaking change between Tomcat 9.0.x and Tomcat 10.0.x". The
xref:web/jsp-struts/introduction-and-history.adoc#javax-to-jakarta[Introduction and History] page has the table of
renamed packages; this page shows what happens to a real WAR.

Source: https://jakarta.ee/specifications/servlet/6.1/jakarta-servlet-spec-6.1.html#compatibility-with-jakarta-servlet-specification-version-4-0[Jakarta Servlet 6.1 -- Compatibility with Jakarta Servlet Specification Version 4.0], https://tomcat.apache.org/migration-10.html#Specification_APIs[Apache Tomcat -- Migration Guide 10.0.x, Specification APIs]

[#javax-bookshelf]
=== The Bookshelf as a javax WAR

The WAR was built for this page with Java 17, `javax.servlet-api` 4.0.1 and `javax.servlet.jsp-api` 2.3.3 as `provided`
dependencies and JSTL 1.2 (`javax.servlet:jstl`) in `WEB-INF/lib`. It has a servlet registered with `@WebServlet`, a
filter declared in `web.xml`, a `SimpleTag` handler with its tag library descriptor, and a JSP that uses JSTL through the
`java.sun.com` library URIs.

.The servlet and the filter of the javax era
[source,java]
----
// BooksServlet.java
import javax.servlet.annotation.WebServlet;
import javax.servlet.http.HttpServlet;
import javax.servlet.http.HttpServletRequest;
import javax.servlet.http.HttpServletResponse;

@WebServlet("/books")
public class BooksServlet extends HttpServlet {
    @Override
    protected void doGet(HttpServletRequest req, HttpServletResponse resp) throws ServletException, IOException {
        req.setAttribute("books", Arrays.asList(
                new Book(1, "Dune", "Frank Herbert", 1965),
                new Book(2, "Neuromancer", "William Gibson", 1984)));
        req.getRequestDispatcher("/WEB-INF/views/books.jsp").forward(req, resp);
    }
}

// AuditFilter.java
public class AuditFilter implements javax.servlet.Filter {
    @Override
    public void doFilter(ServletRequest req, ServletResponse res, FilterChain chain) throws IOException, ServletException {
        ((HttpServletResponse) res).setHeader("X-Bookshelf-Audit", "javax");
        chain.doFilter(req, res);
    }
}
----

Source: https://jakarta.ee/specifications/servlet/6.1/jakarta-servlet-spec-6.1.html#changes-since-jakarta-servlet-4-0[Jakarta Servlet 6.1 -- Changes Since Jakarta Servlet 4.0]

.The descriptors and the JSP of the javax era
[source,xml]
----

         version="4.0">
    <filter>
        <filter-name>audit</filter-name>
        <filter-class>org.example.bookshelf.AuditFilter</filter-class>

    <filter-mapping>
        <filter-name>audit</filter-name>

[#without-migration]
=== What Happens Without Migration

Dropped into the `webapps` directory of Tomcat 11.0.26 as it is, the WAR does not start. The filter named in `web.xml`
extends an interface that the container no longer has, so the context fails, and every URL of it answers 404:

[source,text]
----
$ curl -s -o /dev/null -w "GET /bookshelf-javax/books -> %{http_code}\n" http://localhost:18180/bookshelf-javax/books
GET /bookshelf-javax/books -> 404

SEVERE [Catalina-utility-2] org.apache.catalina.core.StandardContext.filterStart Exception starting filter [audit]
	java.lang.NoClassDefFoundError: javax/servlet/Filter
	Caused by: java.lang.ClassNotFoundException: javax.servlet.Filter
----

A servlet that is registered only by annotation fails more quietly: the annotation scan looks for
`jakarta.servlet.annotation.WebServlet`, finds nothing, and the application deploys cleanly and answers 404 without a
message. The failing "before" case of that variant, with its two servlets, is on the
xref:web/jsp-struts/introduction-and-history.adoc#javax-to-jakarta[Introduction and History] page.

Source: https://tomcat.apache.org/migration-10.html#Servlet_5.0_API[Apache Tomcat -- Migration Guide 10.0.x, Servlet 5.0 API]

[#legacy-app-base]
=== Conversion at Deployment: legacyAppBase

The first remedy needs no tool of your own. Each Tomcat host has a `legacyAppBase` directory, `webapps-javaee` by
default, and the Host documentation says that Java EE applications placed there "will be converted to Jakarta EE using
the Apache Tomcat Migration Tool for Jakarta EE", with the result placed in the `appBase`. On 11.0.26 the default
works without any configuration: the instance used for this page has no `legacyAppBase` attribute in `server.xml`, and
copying `bookshelf-javax.war` into the empty `webapps-javaee` directory produced, a few seconds later, a converted
application in `webapps` that answered normally:

[source,text]
----
$ cp bookshelf-javax.war $CATALINA_BASE/webapps-javaee/
INFO [Catalina-utility-2] org.apache.tomcat.jakartaee.Migration.execute Performing migration from source [.../webapps-javaee/bookshelf-javax.war] to destination [...]
INFO [Catalina-utility-2] org.apache.tomcat.jakartaee.Migration.migrateStream Migration starting for archive [WEB-INF/lib/jstl-1.2.jar] using streaming
INFO [Catalina-utility-2] org.apache.tomcat.jakartaee.Migration.migrateStream Migration finished for archive [WEB-INF/lib/jstl-1.2.jar]
INFO [Catalina-utility-2] org.apache.tomcat.jakartaee.Migration.execute Migration completed successfully in [188] milliseconds
INFO [Catalina-utility-2] org.apache.catalina.startup.HostConfig.deployWAR Deploying web application archive [.../webapps/bookshelf-javax.war]

$ curl -s -D - http://localhost:18180/bookshelf-javax/books
HTTP/1.1 200
X-Bookshelf-Audit: javax
Content-Type: text/html;charset=UTF-8

<h1>Bookshelf <span class="badge">javax</span></h1>
<ul>
  <li>Dune by Frank Herbert (1965)</li>
  <li>Neuromancer by William Gibson (1984)</li>

was deployed from `webapps`. The Host documentation adds the limit of the feature: the
conversion "will be performed using default settings", and for an application that needs other settings the
`migrate.sh` and `migrate.bat` scripts in `bin` run the tool by hand.

[#migration-tool]
=== Conversion Ahead of Time: the Migration Tool

The Tomcat migration guide recommends the same tool ahead of time "to benefit from faster deployment time and more
precise conversion configuration options". Tomcat 11.0.26 bundles version 1.0.12 as `lib/jakartaee-migration-1.0.12-shaded.jar`
behind `bin/migrate.sh`; the current release on Maven Central at the time of writing is 1.0.13 (published as a
`shaded` jar, with a `bin` distribution next to it), and the download page of the Apache Tomcat site lists the
same 1.0.13. The shaded jar was downloaded from Maven Central into an empty directory and its SHA-1 checked against the
`.sha1` file next to it before use.

[source,text]
----
$ java -jar jakartaee-migration-1.0.13-shaded.jar -profile=EE bookshelf-javax.war bookshelf-ee-profile.war
Performing migration from source [bookshelf-javax.war] to destination [bookshelf-ee-profile.war] with Jakarta EE specification profile [EE]
Migration starting for archive [bookshelf-javax.war] using streaming
Migration starting for archive [WEB-INF/lib/jstl-1.2.jar] using streaming
Migration finished for archive [WEB-INF/lib/jstl-1.2.jar]
Migration finished for archive [bookshelf-javax.war]
Migration completed successfully in [231] milliseconds

$ bin/migrate.sh bookshelf-javax.war bookshelf-tomcat-profile.war
INFO: Performing migration from source [bookshelf-javax.war] to destination [bookshelf-tomcat-profile.war] with Jakarta EE specification profile [TOMCAT]
INFO: Migration completed successfully in [218] milliseconds
----

Source: https://tomcat.apache.org/download-migration.cgi[Apache Tomcat -- Migration Tool for Jakarta EE Software Downloads], https://repo1.maven.org/maven2/org/apache/tomcat/jakartaee-migration/1.0.13/[Maven Central -- org.apache.tomcat:jakartaee-migration 1.0.13]

The options of the 1.0.13 command line are printed by running the jar without arguments. The ones that matter here:

[cols="3,6",options="header"]
|===
| Option | Meaning (from the tool's own usage text)

| `+-profile=TOMCAT+`
| The default: convert the Java EE APIs that Tomcat provides (Servlet, Pages, EL, WebSocket, Authentication)

| `+-profile=EE+`
| Convert all Java EE APIs, for a WAR that also uses, say, Persistence or Validation

| `+-profile=SERVLET+`
| Convert the Jakarta Servlet API only

| `+-profile=JEE8+`
| Convert back to the old Java EE 8 APIs; the usage text warns that classes using APIs added in Jakarta EE 10 or later will not work

| `+-exclude=<glob>+`
| Skip files that match; repeatable; matched against the file name unless `+-matchExcludesAgainstPathName+` is given

| `+-zipInMemory+`
| Process archives in memory when the default streaming fails on an unusual zip structure

| `+-cache+`, `+-cacheLocation=<dir>+`
| Cache converted libraries between runs, so unchanged bundled jars are not converted again
|===

Source: https://github.com/apache/tomcat-jakartaee-migration[Apache Tomcat Migration Tool for Jakarta EE -- project repository]

What the conversion changed, and what it left alone, was read from the converted WARs of both runs (the `TOMCAT` and
`EE` profiles gave the same result for this application):

[cols="3,2,5",options="header"]
|===
| Part of the WAR | Converted? | Observed

| Class files of the application
| Yes
| `javap` on `AuditFilter` shows `implements jakarta.servlet.Filter`; `BooksServlet` extends `jakarta.servlet.http.HttpServlet`

| String constants in the JSP
| Yes
| The scriptlet's `javax.servlet.http.HttpServletRequest` printed as `jakarta.servlet.http.HttpServletRequest`

| `WEB-INF/lib/jstl-1.2.jar`
| Yes
| 29 `jakarta/servlet` entries and no `javax/servlet` entry left in the converted jar

| `web.xml` namespace and version
| No
| Still `+xmlns="http://xmlns.jcp.org/xml/ns/javaee"+` and `version="4.0"`; Tomcat 11 accepts it and the filter ran

| TLD namespace and version
| No
| Still the `java.sun.com/xml/ns/javaee` schema and `version="2.1"`

| JSTL library URIs in the JSP
| No
| `+http://java.sun.com/jsp/jstl/core+` stays; it still resolves, see <<jstl-versions>>
|===

The practical reading: the tool makes a `javax` application run on a `jakarta` container, and it is the right tool for a
third-party WAR or a deadline, but it does not modernise the application. The descriptors keep naming Java EE 8, and
the next change to the application (a new `@WebServlet` that imports `javax`, a library bumped to a `jakarta` release)
mixes two namespaces in one application, which is the hard-to-find failure of this kind of migration.

Source: https://tomcat.apache.org/migration-10.html#Specification_APIs[Apache Tomcat -- Migration Guide 10.0.x, Specification APIs]

=== Conversion at the Source

The durable remedy changes the source. For the Bookshelf the whole change was a search and replace of `javax.servlet`
with `jakarta.servlet`, a new set of dependencies, and three descriptor edits. The result compiled with Java 21 and
Servlet 6.1 and ran on Tomcat 11.0.26 with the same output as the converted WAR (the filter header and the badge printed
`jakarta` this time):

The Pages specification page lists its API as `jakarta.pages:jakarta.pages-api`, which does not exist on Maven Central;
the artifact is `jakarta.servlet.jsp:jakarta.servlet.jsp-api`, as above. The JSTL pair is two artifacts on purpose: the
API (`jakarta.servlet.jsp.jstl-api`) and the implementation (`org.glassfish.web:jakarta.servlet.jsp.jstl`), which Tomcat
does not bundle.

A last distinction worth making is the version of the descriptor. Tomcat 11 starts a `web.xml` of any version it can
parse, and for pages the descriptor version has one documented effect on the language: the Pages specification says that
the default mode for JSP pages in an application delivered with a Servlet 2.3 or earlier descriptor is to ignore EL, "for
backward compatibility". Four otherwise identical WARs, each with a `pass:c[${2 + 2}]` in a JSP, prove it:

[cols="3,3,2",options="header"]
|===
| Descriptor of the WAR | `pass:c[${2 + 2}]` in a JSP | Annotated servlet

| Servlet 2.3 DTD (`DOCTYPE web-app`)
| printed literally, `pass:c[2+2=${2 + 2}]`
| 200

| Servlet 2.4 schema, `version="2.4"`
| `pass:c[2+2=4]`
| 200

| Servlet 2.5 schema, `version="2.5"`
| `pass:c[2+2=4]`
| 200

| Servlet 6.1 schema, `version="6.1"`
| `pass:c[2+2=4]`
| 200
|===

The annotation column is the second surprise: Tomcat 11 honoured `@WebServlet` in all four, so an old descriptor
version does not switch the annotation scan off the way a Servlet 2.5 container of the time would have.

== JSTL 1.0 to 3.0: the Library URIs

JSTL 1.0 (2002) came before the expression language was part of JSP, so the library had to carry its own: each area had
a twin, one library whose attributes took JSTL's EL (`+http://java.sun.com/jstl/core+`) and one whose attributes took
request-time scriptlet expressions (`+http://java.sun.com/jstl/core_rt+`). JSTL 1.1 (the JSR 52 maintenance release of
2003-11-24) dropped the twins, moved the URIs to `+http://java.sun.com/jsp/jstl/core+` and added the `fn` functions, and
Jakarta Tags 3.0 renamed the URIs again: its change log lists the item "Rename Tag URIs" (to the `+jakarta.tags.*+` form), together with the
move to Java 11 and a JPMS module descriptor.

[cols="3,3,4",options="header"]
|===
| Library URI | Generation | Request on Tomcat 11.0.26 with JSTL 3.0.1

| `+http://java.sun.com/jstl/core+`
| JSTL 1.0, EL library
| Translation error: `According to TLD or attribute directive in tag file, attribute [value] does not accept any expressions` for `+${...}+`; a literal works

| `+http://java.sun.com/jstl/core_rt+`
| JSTL 1.0, RT library
| Works: `pass:c[<c:out value="<%= 1 + 1 %>"/>]` printed `2`

| `+http://java.sun.com/jsp/jstl/core+`
| JSTL 1.1 and 1.2
| Works like `jakarta.tags.core`: `Dune`

| `+http://xmlns.jcp.org/jsp/jstl/core+`
| Never defined (the Java EE 7 namespace style)
| `+The absolute uri: [http://xmlns.jcp.org/jsp/jstl/core] cannot be resolved in either web.xml or the jar files deployed with this application+`

| `jakarta.tags.core`
| Tags 3.0
| Works: `Dune`
|===

The same applies to the other libraries (`fmt`, `sql`, `xml`, `functions`). The old URIs are still accepted because the
implementation jar `org.glassfish.web:jakarta.servlet.jsp.jstl` 3.0.1 still ships the old descriptors next to the new
ones; the specification documents only the `+jakarta.tags.*+` names, so a migration should change them even though nothing
fails, and the old URIs should never be written as links. On the old attribute spelling, `x:parse` still accepts the
JSTL 1.0 `xml` attribute on 3.0.1 (the page below used it and printed `Dune`) next to the current `doc` attribute, which
is the form to write.

[source,jsp]
----
<%-- before: JSTL 1.0 --%>
<%@ taglib uri="http://java.sun.com/jstl/core" prefix="c" %>
<%@ taglib uri="http://java.sun.com/jstl/xml" prefix="x" %>
<x:parse var="d" xml="${src}"/>

<%-- after: Tags 3.0 --%>
<%@ taglib uri="jakarta.tags.core" prefix="c" %>
<%@ taglib uri="jakarta.tags.xml" prefix="x" %>
<x:parse var="d" doc="${src}"/>
<x:out select="$d/shelf/book/title"/>
----

Source: https://jakarta.ee/specifications/tags/3.0/jakarta-tags-spec-3.0.html#changes[Jakarta Tags 3.0 -- Appendix B, Changes]

`fmt:formatDate` and `fmt:parseDate` and needs Java 21 (see <<ee-12>>).

== EL 2.2 to 6.0

EL was a chapter of the JSP specification until JSP 2.1, then an extract of it, and since EL 3.0 (JSR 341, final release
2013-05-22) it is a specification of its own that Pages, Faces and standalone code share. The Pages specification pins the
numbers: an EL expression in a JSP page is evaluated by the container's `ELResolver` chain, which since Pages 3.1
shares the default imports of the scripting environment. The change log of the EL specification covers the borders
after the namespace move:

[cols="2,6",options="header"]
|===
| Border | Changes

| EL 2.2 to 3.0 (JSR 341, 2013)
| Lambda expressions, collection construction (`[1, 2, 3]`, `+{'a': 1}+`), collection operations as streams, the string-concatenation operator `pass:c[+=]`, the assignment operator `=` and the semicolon operator `;`, static fields and methods through class names

| EL 3.0 to 4.0
| The API moved from `javax.el` to `jakarta.el`

| EL 4.0 to 5.0 (Java 11)
| `BeanELResolver` considers default methods; a lambda can be coerced to a functional interface; `ELResolver.getFeatureDescriptors()` deprecated; the misspelt `MethodExpression.isParmetersProvided()` removed; `MethodReference`; generics; array coercion; the `length` special case in `ArrayELResolver`

| EL 5.0 to 6.0 (Java 17)
| Deprecated code removed; the `java.beans` dependency becomes optional; array `length` property; `java.util.Optional` support through the new `OptionalELResolver` (opt-in); module visibility when accessing methods; references to the `SecurityManager` removed; `java.lang.Record` support through `RecordELResolver` (on by default)
|===

Source: https://jakarta.ee/specifications/expression-language/6.0/jakarta-expression-language-spec-6.0.html#changes-between-6-0-and-5-0[Jakarta Expression Language 6.0 -- Changes between 6.0 and 5.0], https://jakarta.ee/specifications/expression-language/6.0/jakarta-expression-language-spec-6.0.html#changes-between-5-0-and-4-0[Changes between 5.0 and 4.0]

Two things changed from the books' point of view. In JSP 1.2 there was no EL at all, and in a JSTL 1.0 tag the EL lived
inside the library and ended at the attribute, which is why the books' claim that EL does not work in template text is
true only of that pair; since JSP 2.0 `+${...}+` works anywhere in the page, as the ignored-EL table above shows for the
one case (an old descriptor) where it still does not. And the jump from "property access" to "a small expression
language" means that the logic a 2003 page put in a scriptlet can often be an expression, which is the direction
xref:web/jsp-struts/jsp/el-lambdas-collections-and-streams.adoc[Lambdas, Collections and Streams] takes it; the operators
and conversions are on xref:web/jsp-struts/jsp/el-operators-and-type-coercion.adoc[Operators and Type Coercion], the static

the resolver chain on xref:web/jsp-struts/jsp/el-configuration-and-elprocessor.adoc[Configuration and ELProcessor], and
the basics on xref:web/jsp-struts/jsp/expression-language-basics.adoc[Expression Language Basics].

The EL pitfalls of an upgrade are mostly in the table the earlier pages collected, and the three that bite first are these:

* `+${bean.class.name}+` stopped parsing (shown above); write `+${bean.getClass().getName()}+`.
* A record is read by its component name (`+${isbn.code}+`), and on Tomcat 11 a bean-style getter on a record is not
  reachable as a property.
* `Optional` is not resolved unless the application registers `OptionalELResolver`; support for records is on by default.

|===
| Border | Changes

| 9.0 to 10.0
| Servlet 5.0, Pages 3.0, EL 4.0, WebSocket 2.0 and Authentication 2.0: the Java package of each changes from `+javax.*+` to `+jakarta.*+`, and applications must be recompiled or converted; the guide names the migration tool and the deployment-time `legacyAppBase` route for that

| Servlet 6.0, Pages 3.1, EL 5.0; Jakarta EE 10; Java 11 minimum

The notable-changes list of the 11.0 guide has two entries a Struts or JSP application may meet when it moves: the
default `maxParameterCount` of the Connector went from 10,000 to 1,000 in 11.0.0-M5, and the cookie parser treats the
quotes of a quoted cookie value as part of the value, as RFC 6265 requires. A form with more than a thousand fields
(a Struts action binding a large collection, an editable grid) is the application that notices the first one.

Two behaviours of the container that the older books assume and 11.0.26 does not provide are worth keeping next to the
table: the character encoding of requests and responses defaults to UTF-8 through the stock `conf/web.xml`
(the specifications still say ISO-8859-1; see xref:web/jsp-struts/jsp/character-encoding.adoc[Character Encoding]), and
Jasper compiles for Java 17 unless `compilerSourceVM` and `compilerTargetVM` say otherwise, so Java 21 syntax in a
scriptlet needs the two parameters on the `jsp` servlet (see
xref:web/jsp-struts/jsp/jasper-configuration-and-precompilation.adoc[Jasper Configuration and Precompilation]).

The Tomcat distribution still ships an `examples` web application (servlets, JSP and WebSocket samples, with a `web.xml`
at `version="6.1"` in 11.0.26), which is a convenient smoke test for a new container but not a style guide: its samples are
written for the container, not for an application. The sample application of the Tomcat application developer's guide is
the older, smaller reference for the layout of a WAR.

Source: https://tomcat.apache.org/tomcat-11.0-doc/jasper-howto.html#Configuration[Apache Tomcat 11 -- Jasper How-To, Configuration], https://tomcat.apache.org/tomcat-11.0-doc/appdev/sample/[Apache Tomcat 11 -- Sample Application]

[#struts-filter]
=== The Filter and the Descriptor

The filter changed class three times. Struts 2.0 used `FilterDispatcher`, optionally with `ActionContextCleanUp`; Struts 2.3 used
`org.apache.struts2.dispatcher.ng.filter.StrutsPrepareAndExecuteFilter`; 2.5 moved it to
`org.apache.struts2.dispatcher.filter`, which is the name of 7.4.0, and the 2.3 to 2.5 guide tells to replace it in
`web.xml`. Naming either older class on 7.4.0 gives the same failure as the javax filter above: the context starts,
the filter does not, and every URL is 404.

----
<!-- Struts 2.0 -->
<filter-class>org.apache.struts2.dispatcher.FilterDispatcher</filter-class>
<!-- Struts 2.3, the name the 2.3 to 2.5 guide replaces -->
<filter-class>org.apache.struts2.dispatcher.ng.filter.StrutsPrepareAndExecuteFilter</filter-class>
<!-- Struts 2.5 to 7.4 -->
<filter-class>org.apache.struts2.dispatcher.filter.StrutsPrepareAndExecuteFilter</filter-class>
----

        return lent;
    }
}

[#struts-dmi]
=== Dynamic Method Invocation and the Method Prefixes

In the books of the Struts 2.0 era, the `action!method` syntax was on by default. Since 2.5 it is a switch, `struts.enable.DynamicMethodInvocation`,
off by default (7.4.0 `default.properties` says `false`), and the replacement is strict method invocation with an
`<allowed-methods>` list. The prefixes `method:` and `action:` are separate switches again. The Bookshelf's `BookAction`
got a `lend()` method and two mappings, one with a wildcard, and was requested in each combination on 7.4.0:

[source,xml]
----
<package name="default" extends="struts-default" namespace="/">
    <action name="books" class="org.example.bookshelf.BookAction">
        <result>/WEB-INF/views/books.jsp</result>
    </action>
    <action name="book-*" class="org.example.bookshelf.BookAction" method="{1}">
        <result>/WEB-INF/views/books.jsp</result>
        <allowed-methods>lend</allowed-methods>
    </action>
</package>
----

[cols="4,2,3,3",options="header"]
|===
| Request | DMI off (default) | DMI on, `<allowed-methods>lend` on `books` | Notes

| `/books`
| `execute ran`, 200
| not tested
| the default method

| `/books!lend` and `/books!lend.action`
| 404, `There is no Action mapped for namespace [/] and action name [books!lend]`
| `lend ran`, 200
| `!` is part of the action name when DMI is off

| `/books.action?method:lend`
| `execute ran` (the parameter is ignored)
| `lend ran`
| the `method:` prefix needs DMI

| `/book-lend` and `/book-lend.action`
| `lend ran`, 200
| not tested
| wildcard method selection with `<allowed-methods>`

| `/book-giveBack`
| 404, `There is no Action mapped`
| not tested
| the method is not in `<allowed-methods>`
|===

The change in practice is that a link or a form button written `action!method` in a 2.0-era page stops working with a
404 that says there is no such action, and the repair is to map the method as an action of its own. In `struts.xml`,
`<allowed-methods>` must come after the `<result>` elements; the other order makes the filter fail to start. The
issue statement that the `action:` and `redirect:` prefixes were removed needs correcting for 7.4.0: `method:` and
`action:` still exist behind their switches (`struts.mapper.action.prefix.enabled` is `false` by default), while the
`redirect:` and `redirectAction:` prefixes are not in the 7.4.0 `DefaultActionMapper`. The page on
xref:web/jsp-struts/struts/wildcard-mappings-and-method-invocation.adoc[Wildcard Mappings and Method Invocation] has the details.

Source: https://struts.apache.org/core-developers/action-configuration#strict-method-invocation[Struts -- Action Configuration, Strict Method Invocation], https://struts.apache.org/security/#strict-method-invocation[Struts Security -- Strict Method Invocation]

[#struts-parameters]
=== @StrutsParameter, OGNL and the Allowlist

The 6 to 7 guide calls the next group "stronger security", and it is where an application that compiles after the
repackaging still misbehaves, because nothing fails: a value is silently not bound or a property silently prints
nothing. Three Struts 7.4.0 defaults, read from `default.properties`, decide it: `struts.parameters.requireAnnotations`
is `true`, `struts.allowlist.enable` is `true`, and `struts.ognl.allowStaticFieldAccess` is `false`.

The first is parameter injection. Until 6.x any public setter received a request parameter; in 7.0 each injection point
needs `@StrutsParameter`. The unannotated `BookAction` below ignored `?filter=x`; with the annotation, or with the
constant set to `false`, the value arrived:

[source,java]
----
// Struts 6.x -- any public setter binds
public void setFilter(String filter) {
    this.filter = filter;
}

// Struts 7.x
@StrutsParameter
public void setFilter(String filter) {
    this.filter = filter;
}
----

[cols="4,3",options="header"]
|===
| Variant of the Bookshelf's `BookAction` on 7.4.0 | `GET /books?filter=x` printed

| `setFilter` without the annotation
| `Filter: ` (empty, status 200, no error on the page)

| `setFilter` with `@StrutsParameter`
| `Filter: x`

| `setFilter` without it and `<constant name="struts.parameters.requireAnnotations" value="false"/>`
| `Filter: x`
|===

The 6 to 7 guide even gives a regular expression to find the setters and a replacement that adds the annotation to every
`+*Action.java+`; a review of the result is part of the migration, because the point of the annotation is that someone
decides what may be bound. The guide's constants for the transition are `struts.parameters.requireAnnotations` and, named
in the 7.4.0 Version Notes and present in the 7.4.0 `default.properties`, `struts.parameters.requireAnnotations.transitionMode`.
xref:web/jsp-struts/struts/parameter-injection-and-struts-parameter.adoc[Parameter Injection and @StrutsParameter] explains the
`depth` and the rest.

Source: https://struts.apache.org/core-developers/struts-parameter-annotation[Struts -- StrutsParameter Annotation], https://cwiki.apache.org/confluence/spaces/WW/pages/293046977/Struts+6.x.x+to+7.x.x+migration#Struts6.x.xto7.x.xmigration-Actionparameterinjection[Struts Wiki -- 6.x.x to 7.x.x migration, Action parameter injection]

The second is the OGNL allowlist. A page that reads a property of a plain Java class outside the action's own package
prints nothing, with a warning in the log, until the class or its package is allowlisted. The Bookshelf action got a
`getFeatured()` returning an object of `org.example.bookshelf.model.Featured`:

[source,jsp]
----
featured=[<s:property value="featured.title"/>]
----

[source,xml]
----
<constant name="struts.allowlist.packageNames" value="org.example.bookshelf.model"/>
----

[cols="4,3",options="header"]
|===
| Configuration | Output of the page

| defaults
| `featured=[]`

| `struts.allowlist.packageNames` naming the model package
| `featured=[Dune]`
|===

Source: https://struts.apache.org/security/#allowlist-capability[Struts Security -- Allowlist Capability], https://cwiki.apache.org/confluence/spaces/WW/pages/293046977/Struts+6.x.x+to+7.x.x+migration#Struts6.x.xto7.x.xmigration-OGNLallowlistcapability[Struts Wiki -- OGNL allowlist capability]

The third is what OGNL may call. Static method access was removed in 6.0.0 ("it won't be possible to access static methods
using OGNL expression"), and static field access was turned off in 7.0.0. Both were requested on 7.4.0:

[source,jsp]
----
max=[<s:property value="@java.lang.Math@max(1,2)"/>] field=[<s:property value="@java.lang.Integer@MAX_VALUE"/>]
----

[cols="5,3",options="header"]
|===
| Configuration | Output

| defaults
| `max=[] field=[]`

| `struts.ognl.allowStaticFieldAccess=true`
| `max=[] field=[]` (the guide's one-line switch is not enough)

| `struts.ognl.allowStaticFieldAccess=true` and `struts.allowlist.classes=java.lang.Integer`
| `max=[] field=[2147483647]`
|===

The guide describes the constant as the way to bring static fields back; on 7.4.0 the declaring class must also pass the
allowlist, and calls of static methods stay blocked in every configuration tried (the `struts.ognl.allowStaticMethodAccess`
constant of the old books does not exist in 7.4.0). The migration advice of the guide is better than the switch: copy
the value into the action, or into a helper that the action exposes. The 6 to 7 guide also changes the limits: the OGNL
expression length is limited to 256 characters since 6.0.0, and the 7.0 section of the guide says "reduced from 200 to
150"; the 7.4.0 `default.properties` and the security guide say 256, which is the value this section uses (see
<<official-inconsistencies>>). Namespace matching became exact in 7.0 (`struts.mapper.alwaysSelectFullNamespace` is
`true`, `struts.actionConfig.fallbackToEmptyNamespace` is `false`), proxied objects are blocked
(`struts.disallowProxyObjectAccess`), default-package classes are blocked (`struts.disallowDefaultPackageAccess`) and
custom OGNL maps are blocked (`struts.ognl.disallowCustomOgnlMap`); xref:web/jsp-struts/struts/security-hardening.adoc[Security Hardening]
and xref:web/jsp-struts/struts/value-stack-action-context-and-ognl.adoc[Value Stack, ActionContext and OGNL] have the rest.

Source: https://struts.apache.org/security/#apply-a-maximum-allowed-length-on-ognl-expressions[Struts Security -- Maximum Allowed Length on OGNL Expressions], https://struts.apache.org/core-developers/default-properties[Struts -- default.properties]

[#struts-upload]
=== File Upload

The `fileUpload` interceptor and its `File`, `xxxContentType` and `xxxFileName` setters are gone. 6.4.0 added the
`actionFileUpload` interceptor with `UploadedFilesAware`, and 7.0.0 removed the old one; the 6 to 7 guide's "remove the
old interceptor reference" instruction is not optional, because an application that still names it does not start:

[source,xml]
----
<!-- Struts 2.x to 6.3 -->
<interceptor-ref name="fileUpload"/>
<interceptor-ref name="defaultStack"/>

<!-- Struts 6.4 and later -->
<interceptor-ref name="actionFileUpload">
    <param name="maximumSize">1048576</param>
    <param name="allowedTypes">text/plain</param>
</interceptor-ref>
<interceptor-ref name="defaultStack"/>
----

[source,java]
----
public class UploadAction extends ActionSupport implements UploadedFilesAware {
    @Override
    public void withUploadedFiles(List<UploadedFile> uploadedFiles) {
        for (UploadedFile f : uploadedFiles) {
            // f.getOriginalName(), f.length(), f.getContentType()
        }
    }
}
----

----

=== From 7.0 to 7.4

The lines after 7.0.0 are minor releases that are allowed to break less, and the Version Notes of 7.3.0 and 7.4.0 both have a

[cols="1,6",options="header"]
|===
| Release | Breaking change

| 7.3.0
| Struts no longer uses SLF4J or `java.util.logging` internally; annotated wildcard actions are matched most-specific-first; the JSON interceptor uses a fresh reader and writer per request; static content paths are canonicalised; `ActionFileUploadInterceptor` rejects an upload when a parameter such as `maximumSize` cannot be applied, so the literal `null` no longer lifts the size limit

[#modernisation]
== Modernisation Paths

A migration does not have to end at "the same application on a newer platform". Three destinations are realistic for a
Bookshelf-sized JSP or Struts application, and the choice is the one the repository's architecture pages already
describe for a legacy monolith.

* *Stay on JSP and Struts, current versions.* The cheapest path when the application is stable: the steps of this page,
  in order, then keep the Struts line current. It is the right answer for an internal application that changes little.
* *Struts or JSP to Spring MVC with Thymeleaf (or another template engine), one screen at a time.* The strangler-fig path.
  The Spring MVC page of this section, xref:web/jsp-struts/jsp/spring-mvc-with-jsp.adoc[Spring MVC with JSP], shows the first
  step (new controllers that still render JSP views, in a WAR), and the Thymeleaf section carries the destination:
  xref:web/thymeleaf/introduction-and-architecture.adoc[Thymeleaf: Introduction and Architecture] and
  xref:web/thymeleaf/whats-changed-and-migration.adoc[Thymeleaf: What's Changed and Migration]. The comparison of the web UI
  options for Spring Boot is xref:backend/springboot/web-ui-frameworks.adoc[Web UI Frameworks], and the `+javax.*+` to `+jakarta.*+`
  switch of Spring Boot 3 is in xref:backend/springboot/getting-started.adoc[Spring Boot: Getting Started].
* *Faces.* A component-based move is a different programming model; it is covered by the
  xref:web/jsf/migrating-to-jakarta-faces.adoc[JSF: Migrating to Jakarta Faces] page and the rest of the xref:web/jsf/index.adoc[JSF (JavaServer Faces)] section, and is not described here.

The repository's _Bookshop_ scenario, a Struts 1 and JSP monolith moved to a modern stack, is the longer story of the
first two paths with its phases, risks and decisions, in
xref:backend/architecture/decisions-and-migrations/migration-path-legacy-to-modern-stack.adoc[Migration Path: Legacy to Modern Stack], with the
general view of migration strategies in xref:backend/architecture/decisions-and-migrations/migration-overview.adoc[Migration Overview]; the
Struts 1 specifics (a dual request processor, the concept map) are on
xref:web/jsp-struts/struts/struts-1-classic-and-migration.adoc[Struts 1 (Classic) and Migration].

The mechanical core of the strangler-fig path is routing: the old application and the new code share one WAR and one
URL space, and a rule decides who answers. In a Struts application the rule is a constant. With the default
`struts.action.extension` of `action,,`, the Struts filter claims the extensionless URLs as well, so a new servlet at
`/api/books` was shadowed (Struts answered 404 for an action it did not have). Narrowing the constant to `action` gave the
new code its URLs and kept the old screens:

[source,java]
----
@WebServlet("/api/books")
public class ApiBooksServlet extends HttpServlet {
    @Override
    protected void doGet(HttpServletRequest req, HttpServletResponse resp) throws IOException {
        resp.setContentType("application/json");
        resp.getWriter().write("[\"Dune\",\"Neuromancer\"]");
    }
}
----

[source,xml]
----
<constant name="struts.action.extension" value="action"/>
----

[cols="3,2,2",options="header"]
|===
| Request on 7.4.0 / Tomcat 11.0.26 | Default `action,,` | `action`

| `/books` (old Struts action)
| 200
| 404 (links must say `books.action`)

| `/books.action`
| 200
| 200

| `/api/books` (new servlet)
| 404 from the Struts filter
| 200, `["Dune","Neuromancer"]`
|===

The price is visible in the second column of the first row: every link and redirect of the legacy screens must carry the
extension. The alternative that keeps the extensionless Struts URLs is `struts.action.excludePattern`, described with the
deployment settings on xref:web/jsp-struts/struts/deployment-and-production.adoc[Deployment and Production].

Source: https://struts.apache.org/core-developers/default-properties[Struts -- default.properties], https://docs.spring.io/spring-framework/reference/web/webmvc-view/mvc-jsp.html[Spring Framework -- JSP and JSTL]

[#pitfalls]
== Pitfalls

[cols="3,3,4",options="header"]
|===
| Pitfall | Symptom | Remedy

| A `javax` WAR dropped into Tomcat 10.1 or 11
| A filter or listener in `web.xml` stops the context (`NoClassDefFoundError: javax/servlet/Filter`, every URL 404); a servlet registered only by annotation deploys silently and answers 404
| Convert at the source, with the migration tool ahead of time, or through `webapps-javaee`; read the log, not the HTTP status (<<without-migration>>)

| Trusting the converted WAR to be modern
| The descriptors still name Java EE 8 (`xmlns.jcp.org`, `version="4.0"`, the 2.1 TLD schema) and the JSTL URIs are unchanged
| Plan the source-level migration anyway; the next `javax` import mixes two namespaces in one application (<<migration-tool>>)

| Converting only the application's own jars
| The tool also converts the jars bundled in `WEB-INF/lib`, but not libraries installed in Tomcat's `lib` directory or other shared locations
| Keep libraries in the WAR, or convert the shared jars with the same tool before installing them

| `JasperException` for an old page on the first request
| `isThreadSafe` or `jsp:plugin` fails at translation, not at startup
| Precompile with JspC in the build to find every old page at once (xref:web/jsp-struts/jsp/jasper-configuration-and-precompilation.adoc[Jasper Configuration and Precompilation])

| `+${bean.class.name}+` or `+${exception.class.name}+`
| `Failed to parse the expression`
| `+${bean.getClass().getName()}+`

| Expecting EL to work under an old descriptor
| `+${...}+` printed literally in every page of a WAR whose `web.xml` is a Servlet 2.3 DTD
| Move the descriptor to the schema of the version in use, or set `el-ignored` to false in a property group

| Old JSTL URIs left in place
| Nothing fails today (the 3.0.1 jar still resolves them), so they survive into the next library change; `xmlns.jcp.org` URIs fail immediately
| Replace with `+jakarta.tags.*+` while the diff is small

| `fileUpload` or `timer` interceptor references
| The whole application fails to start; every URL of the context is 404 and the only trace is `Unable to find interceptor class referenced by ref-name` in the log
| Replace `fileUpload` with `actionFileUpload` and drop `timer`; test the startup, not only a request

| Unannotated setters after the move to 7
| Parameters silently not bound, no error on the page
| Add `@StrutsParameter` after reviewing each setter; use the transition mode of 7.4.0 while you do it

| Plain POJOs on a page after the move to 7
| `<s:property>` prints nothing and the log has a warning about a class that is "not allowlisted"
| Add the model package to `struts.allowlist.packageNames`; do not turn the allowlist off

| Old constant names
| Silently ignored (`struts.xwork.chaining.copyMessages`)
| Use the 6.0 names from the constants table

| `action!method` links and buttons
| 404 `There is no Action mapped for namespace [/] and action name [books!lend]`
| Map the method as its own action, or use wildcard method selection with `<allowed-methods>` placed after the results

| A new servlet next to Struts at an extensionless URL
| Struts answers 404 for the URL before the servlet is reached
| `struts.action.extension` set to `action`, or `struts.action.excludePattern`; update the legacy links

| Copying a class from the official Struts documentation
| `package com.opensymphony.xwork2 does not exist`, or a `javax.validation` import that does not resolve
| Take the `org.apache.struts2` and `jakarta` names of <<struts-packages>>; the documentation page is stale, not the framework
|===

[#checklist]
== Upgrade Checklist

The checklist is the order that the sections above follow, and each step names what proves it. It assumes the target of
this section, Tomcat 11 with Java 21 and Struts 7.4, and takes a legacy `javax` JSP application with Struts 2.3 as the
longest case; a JSP-only application skips the Struts steps.

.Before touching the code
. Inventory the application: container and Java versions, `web.xml` version, JSP and JSTL libraries and their URIs, Struts version and plugins, and every third-party jar that still imports `+javax.*+`.
. Run the tests, and record the answer of ten real URLs with `curl`; they are the regression suite for everything below.
. If the aim is only to run on Tomcat 11 first, convert with the migration tool (`webapps-javaee` or the command line), run the ten URLs, and stop here for the first release.

.Platform and JSP
[start=4]
. Change `javax.servlet`, `javax.servlet.jsp` and `javax.el` imports to `+jakarta.*+`, the dependencies to `jakarta.servlet-api` 6.1.0, `jakarta.servlet.jsp-api` 4.0.0 and `jakarta.el-api` 6.0.1 (`provided`), and JSTL to the 3.0 API and the 3.0.1 implementation (<<source-level>>).
. Move `web.xml` to the 6.1 schema and every TLD to the 4.0 schema; keep `version` and namespace in step.
. Replace the removed Servlet and Pages API (`SingleThreadModel`, `HttpUtils`, `getValue` and friends, `EVAL_BODY_TAG`, `getRootCause`, the `jakarta.servlet.jsp.el` classes) with the replacements of <<servlet-changes>>.
. Delete `isThreadSafe` and `jsp:plugin`; replace `.class.name` in EL; replace the JSTL URIs with `+jakarta.tags.*+`.
. Precompile all JSPs with JspC in the build, so translation errors surface at build time.

.Struts, in the order of the guides
[start=9]
. Move to 2.5.33, then 6.12.0, then 7.4.0, running the ten URLs after each step: filter class and DTD (2.5), tag attributes and the removed `s:div` (2.5), constants, the Aware interfaces and static method access (6), `jakarta`, `org.apache.struts2`, `@StrutsParameter`, the allowlist, `actionFileUpload` and the removed plugins (7).
. Start the application and read the log from the top: a Struts filter that fails to initialise leaves a running context and a 404 for every URL.
. Review every `@StrutsParameter` you added, every `+struts.allowlist.*+` entry, and every place where a DMI link was replaced.
. Update the version of every plugin to the one of the core, and set the `struts2-bom` so that no plugin version is hard-coded.

.After
[start=13]
. Replace the old descriptor namespaces and URIs that the tool or Tomcat tolerated.
. Run the security checks of the section (xref:web/jsp-struts/struts/security-hardening.adoc[Security Hardening], xref:web/jsp-struts/jsp/security.adoc[Security]) and read the security bulletins of the line you are on (xref:web/jsp-struts/struts/security-bulletins.adoc[Security Bulletins]).
. Decide what the application is: maintained on JSP and Struts, or on its way to Spring MVC and Thymeleaf (<<modernisation>>), and write the decision next to the version numbers.
