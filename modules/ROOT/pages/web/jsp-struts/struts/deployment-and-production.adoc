[#overview]
== From Development to Production: What Changes

Struts 7.4.0 ships with production-safe defaults, and the first thing to know is how little there is to switch off. The
table lists the settings that distinguish a development run from a production run, with the 7.4.0 default (read from
`default.properties`) and the value this page uses.

.Settings that differ between development and production
[cols="3,2,2,4",options="header"]
|===
|Setting |7.4.0 default |Production |Why

|`struts.devMode` |`false` |`false` |On, it reloads configuration and resource bundles, turns on the `debugging` interceptor (`?debug=xml` dumps the value stack) and makes problems louder; the Core Developer Guide says it "can expose sensitive data"
|`struts.configuration.xml.reload` |`false` |`false` |Re-reads XML configuration when a file changes; "not recommended for production use"
|`struts.i18n.reload` |`false` |`false` |Re-reads resource bundles on each request
|`struts.freemarker.templatesCache.updateDelay` |not set (FreeMarker's 5 s) |a large value such as `3600` |How often a template file is checked for changes; templates do not change in production
|`struts.serve.static` |`true` |`false` when the container or a proxy serves the files |Struts can serve its own files from the jar, but the container "is not optimized" for it
|`struts.serve.static.browserCache` |`true` |`true` |Keeps the browser cache headers on files that Struts serves
|`struts.ognl.expressionCacheType` and `struts.ognl.beanInfoCacheType` |`wtlfu` |`wtlfu` |The bounded cache of parsed OGNL expressions and of bean information
|`struts.ognl.expressionMaxLength` |`256` |`256` |A bound on the length of an OGNL expression; a security setting, kept
|`struts.allowlist.enable` and `struts.parameters.requireAnnotations` |`true` |`true` |Security settings, never switched off to fix a development problem
|`struts.enable.DynamicMethodInvocation` |`false` |`false` |Dynamic method invocation stays off
|===

Source: https://struts.apache.org/core-developers/development-mode.html[Core Developer Guide -- Development Mode]

Source: https://struts.apache.org/core-developers/reloading-configuration.html[Core Developer Guide -- Reloading Configuration]

The development-mode behaviour, the constants one by one and the load order of the files that set them are described in
xref:web/jsp-struts/struts/configuration-struts-xml-and-constants.adoc[Configuration: struts.xml and Constants] (see its
section on xref:web/jsp-struts/struts/configuration-struts-xml-and-constants.adoc#reload[reloading and development mode]);
the debugging side of `devMode` belongs to the xref:web/jsp-struts/struts/debugging-dev-mode-and-logging.adoc[debugging page] of this section. What this page adds is everything around
the WAR: where each request is handled, which headers it carries, which container features to switch on and how the WAR
is packaged.

[#request-path]
== Who Handles Which Request

In production a request passes through more components than on a developer's laptop, and the useful question for most
problems is which of them answers. The figure shows the path of the Bookshelf WAR of this page.

[mermaid]
....
flowchart LR
  C["Browser"] --> P["Reverse proxy or load balancer: TLS, compression, caching"]
  P -->|"X-Forwarded-Proto and X-Forwarded-For"| T["Tomcat connector: optional gzip"]
  subgraph app["Tomcat: the Bookshelf web application"]
    V["Host valves: RemoteIpValve, ErrorReportValve"] --> E["ExpiresFilter for /static and /assets"]
    E --> S["StrutsPrepareAndExecuteFilter"]
    S -->|"action found"| A["Action, then JSP"]
    S -->|"excludePattern or no action mapping"| D["Container default servlet and HealthServlet"]
  end
  T --> V
  A --> R["HTML response"]
  D --> R2["Static file, health answer or error page"]
....

The proxy and the connector are the only components that can see the original scheme and client address, which is why the
valve at the start of the Tomcat pipeline restores them (see <<proxy>>). The filter mapped to `+/*+` sees every request
that reaches the web application and decides in two steps: if the URL starts with the static content path and Struts serves
static content, it answers itself; otherwise it asks the action mapper for an action. A request with no action falls
through to the next filter and, finally, to a servlet; that is how `assets/app.css` is served by Tomcat's default servlet
in the verification below, and also why an extensionless servlet URL needs the exclusion of <<health>>.

[#bookshelf-app]
== The Bookshelf Production WAR

All the examples on this page are files of one Maven project, `g12prod`, built from the Bookshelf of the xref:web/jsp-struts/struts/getting-started.adoc[Struts Getting Started]
page of this section (the Struts BOM, `struts2-core`, the Jakarta Servlet and Pages APIs as `provided` dependencies, Log4j 2).
It adds a small servlet for health checks, static assets, two error pages and an action that always fails, so that every
production behaviour can be requested.

.The files that matter for production
[cols="3,4",options="header"]
|===
|File |Role

|`src/main/resources/struts.xml` |The production constants and the `books` and `boom` actions
|`src/main/webapp/WEB-INF/web.xml` |The Struts filter, an `ExpiresFilter`, the session cookie settings and the error pages
|`src/main/resources/log4j2.xml` |Logging at `warn` for Struts and FreeMarker, written to standard output
|`src/main/java/org/example/bookshelf/HealthServlet.java` |The `/health` endpoint used by probes
|`+src/main/webapp/static/...+` |The files of the Struts jar, extracted so that the container serves them
|`src/main/webapp/assets/app.css` |The application's own stylesheet
|`src/main/webapp/WEB-INF/views/books.jsp` |The catalogue page; `session="false"` keeps JSP from creating sessions
|===

The `struts.xml` is the heart of the production configuration. Each constant is explained in the sections that follow.

.src/main/resources/struts.xml
[source,xml]
----
<?xml version="1.0" encoding="UTF-8" ?>
<!DOCTYPE struts PUBLIC
        "-//Apache Software Foundation//DTD Struts Configuration 6.0//EN"
        "https://struts.apache.org/dtds/struts-6.0.dtd">
<struts>
    <!-- production: no reloading, no development mode (these are the defaults, stated on purpose) -->
    <constant name="struts.devMode" value="false"/>
    <constant name="struts.configuration.xml.reload" value="false"/>
    <constant name="struts.i18n.reload" value="false"/>

    <!-- static content is served by the container, not by Struts -->
    <constant name="struts.serve.static" value="false"/>

    <!-- let the servlet at /health and the files under /assets bypass Struts -->
    <constant name="struts.action.excludePattern" value="/health,/assets/.*"/>

    <!-- templates do not change in production: check for changes every hour -->
    <constant name="struts.freemarker.templatesCache.updateDelay" value="3600"/>

    <!-- caches: type and size (7.4.0 defaults: wtlfu, 10000) -->
    <constant name="struts.ognl.expressionCacheType" value="wtlfu"/>
    <constant name="struts.ognl.expressionCacheMaxSize" value="10000"/>

    <package name="default" extends="struts-default" namespace="/">
        <action name="books" class="org.example.bookshelf.BookAction">
            <result>/WEB-INF/views/books.jsp</result>
        </action>
        <action name="boom" class="org.example.bookshelf.BoomAction"/>
    </package>
</struts>
----

Source: https://struts.apache.org/core-developers/constant-configuration.html[Core Developer Guide -- Constant Configuration]

The `web.xml` adds Tomcat's `ExpiresFilter` ahead of the Struts filter for the two static prefixes, the cookie settings of
the session (<<tomcat>>) and error pages, so that a failing request never shows a container page. The filter order is the
order of the `<filter-mapping>` elements.

.src/main/webapp/WEB-INF/web.xml
[source,xml]
----
<?xml version="1.0" encoding="UTF-8"?>
<web-app xmlns="https://jakarta.ee/xml/ns/jakartaee"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="https://jakarta.ee/xml/ns/jakartaee https://jakarta.ee/xml/ns/jakartaee/web-app_6_1.xsd"
         version="6.1">

    <filter>
        <filter-name>expires</filter-name>
        <filter-class>org.apache.catalina.filters.ExpiresFilter</filter-class>
        <init-param>
            <param-name>ExpiresByType text/css</param-name>
            <param-value>access plus 7 days</param-value>
        </init-param>
        <init-param>
            <param-name>ExpiresByType text/javascript</param-name>
            <param-value>access plus 7 days</param-value>
        </init-param>
    </filter>
    <filter-mapping>
        <filter-name>expires</filter-name>
        <url-pattern>/static/*</url-pattern>
        <url-pattern>/assets/*</url-pattern>
    </filter-mapping>

    <filter>
        <filter-name>struts2</filter-name>
        <filter-class>org.apache.struts2.dispatcher.filter.StrutsPrepareAndExecuteFilter</filter-class>
    </filter>
    <filter-mapping>
        <filter-name>struts2</filter-name>
        <url-pattern>/*</url-pattern>
    </filter-mapping>

    <session-config>
        <cookie-config>
            <http-only>true</http-only>
            <secure>true</secure>
            <attribute>
                <attribute-name>SameSite</attribute-name>
                <attribute-value>Lax</attribute-value>
            </attribute>
        </cookie-config>
    </session-config>

    <error-page>
        <error-code>404</error-code>
        <location>/errors/404.html</location>
    </error-page>
    <error-page>
        <error-code>500</error-code>
        <location>/errors/500.html</location>
    </error-page>
</web-app>
----

Source: https://struts.apache.org/core-developers/web-xml.html[Core Developer Guide -- web.xml]

Source: https://tomcat.apache.org/tomcat-11.0-doc/config/filter.html#Expires_Filter[Tomcat 11 -- Expires Filter]

The `ExpiresFilter` is a Tomcat class, so this `web.xml` runs on Tomcat only; on Jetty or GlassFish the same effect is
obtained with a different filter or, better, at the proxy. The filter and the session settings are explained with their
verification below. The full request matrix of this WAR is in <<worked-example>>.

== Production Constants and Environment-Specific Configuration

Struts 7.4.0 starts in production mode unless told otherwise, and `?debug=xml` is the quickest check of that. In the
Bookshelf with `struts.devMode` set to `true` the request returns the value-stack dump, and with the default it returns the
normal page (observed on Tomcat 11.0.26).

.devMode on and off (same action, same request)
[source,console]
----
$ curl -s 'http://localhost:18081/g12deploy/books?debug=xml' | head -c 8      # devMode=true
<debug>
$ curl -s 'http://localhost:18081/g12deploy/books?debug=xml' | head -c 8      # default or false
<!DOCTYPE
----

Source: https://struts.apache.org/core-developers/development-mode.html[Core Developer Guide -- Development Mode]

Teams that need different settings per environment have four mechanisms to choose from.

.Ways to give the same WAR different settings per environment
[cols="3,2,4",options="header"]
|===
|Mechanism |Result (observed) |Comment

|A filter `init-param` named like the constant, for example `struts.devMode` |Works: `?debug=xml` dumped the stack |Static: it lives in `web.xml`, so it is per build, not per environment
|An environment variable referenced in `struts.xml`: `+<constant name="struts.devMode" value="${env.STRUTS_DEV_MODE:false}"/>+` |Works: `EnvsValueSubstitutor` returned `false` with the variable unset and `true` with `STRUTS_DEV_MODE=true` |Build once, deploy everywhere: the same WAR reads the setting from the environment of each JVM, and the default after the colon is the safe one (xref:web/jsp-struts/struts/configuration-struts-xml-and-constants.adoc#substitution[Configuration: struts.xml and Constants] has the syntax)
|A Maven profile that filters a `struts.properties` file at build time |Works: the `dev` profile produced a WAR with `struts.devMode=true`, the default one `false` |One WAR per environment, which defeats "build once, deploy everywhere"
|`-Dstruts.devMode=true` on the JVM command line |Works only when the constant is referenced as `+${...}+` in `struts.xml`, for example `+value="${struts.devMode:false}"+`; with a plain value in `struts.xml` (or none), `?debug=xml` stayed a normal page (observed) |Struts constants are not read from system properties directly; `EnvsValueSubstitutor` resolves `+${name}+` from system properties and `+${env.NAME}+` from environment variables, only inside `<constant>` values
|===

The Maven variant needs only a filtered resource and a profile.

.A filtered struts.properties (src/main/resources/struts.properties) and the pom.xml parts that filter it
[source,properties]
----
struts.devMode=${struts.devMode}
struts.configuration.xml.reload=${struts.devMode}
----

[source,xml]
----
<properties>
    <struts.devMode>false</struts.devMode>
</properties>

<profiles>
    <profile>
        <id>dev</id>
        <properties>
            <struts.devMode>true</struts.devMode>
        </properties>
    </profile>
</profiles>

<build>
    <resources>
        <resource>
            <directory>src/main/resources</directory>
            <filtering>true</filtering>
            <includes>
                <include>struts.properties</include>
            </includes>
        </resource>
        <resource>
            <directory>src/main/resources</directory>
            <excludes>
                <exclude>struts.properties</exclude>
            </excludes>
        </resource>
    </resources>
</build>
----

`mvn package` then produced a `struts.properties` containing `struts.devMode=false` and `mvn package -Pdev` one containing
`struts.devMode=true`; both WARs were deployed side by side and only the second answered `?debug=xml`. Keep the filtered file
tiny, because filtering replaces every `+${...}+` in it, and filter only that file as the `pom.xml` above does. The init-params
the Struts filter itself understands (`config`, `configProviders` and others) are listed in
xref:web/jsp-struts/struts/configuration-struts-xml-and-constants.adoc#web-xml[The Filter and Its Init-Params in web.xml].
Secrets, such as database passwords, do not belong in any of these files; the Kubernetes and Docker pages of this site
(xref:backend/kubernetes/secrets.adoc[Secrets], xref:backend/kubernetes/configmaps.adoc[ConfigMaps]) show how the container
platform injects them.

Source: https://maven.apache.org/plugins/maven-resources-plugin/examples/filter.html[Maven Resources Plugin -- Filtering]

Source: https://maven.apache.org/guides/introduction/introduction-to-profiles.html[Maven -- Introduction to Build Profiles]

[#static-content]
== Static Content

Struts can serve static files itself. The Core Developer Guide describes the arrangement: the constant
`struts.ui.staticContentPath` (default `+/static+`) names a path prefix, the `StaticContentLoader` (default
`DefaultStaticContentLoader`) answers requests under it from the classpath, and the same path serves the files that the
`xhtml` and `css_xhtml` themes need (`s:head` emits links to them). The Bookshelf shows the default arrangement first.

.A request that Struts serves itself (defaults, headers as observed)
[source,console]
----
$ curl -s -D - -o /dev/null http://localhost:18081/g12deploy/static/utils.js
HTTP/1.1 200
Expires: Sun, 11 Oct 2026 11:05:50 GMT
Retry-After: Sun, 11 Oct 2026 11:05:50 GMT
Cache-Control: public
Last-Modified: Sat, 10 Oct 2026 11:05:45 GMT
Content-Type: text/javascript
----

Struts adds `Cache-Control: public` and an `Expires` one day ahead, the browser-cache behaviour that
`struts.serve.static.browserCache=true` stands for; the `Retry-After` header with the same date is sent too and means
nothing for a 200. With `struts.serve.static.browserCache=false` the answer carries `Cache-Control: no-cache`,
`Pragma: no-cache` and `Expires: -1` instead, which is useful while the static files of a plugin change. Both forms are
verified on 7.4.0.

Source: https://struts.apache.org/core-developers/static-content.html#default-content-loader[Core Developer Guide -- Static Content, Default Content Loader]

Source: https://struts.apache.org/maven/struts2-core/apidocs/org/apache/struts2/dispatcher/StaticContentLoader.html[Struts Javadoc -- StaticContentLoader]

[#static-path]
=== Changing or Disabling the Path

Two constants move or switch off the arrangement. Moving the path is a one-line constant; the old path then answers 404 and
the new one 200 (observed).

.struts.ui.staticContentPath
[source,xml]
----
<constant name="struts.ui.staticContentPath" value="/assets-struts"/>
----

Source: https://struts.apache.org/core-developers/static-content.html#default-path[Core Developer Guide -- Static Content, Default path]

Disabling it is the production choice when the container, a CDN or a proxy serves the files.

.struts.serve.static
[source,xml]
----
<constant name="struts.serve.static" value="false"/>
----

Source: https://struts.apache.org/core-developers/static-content.html#disabling-static-content[Core Developer Guide -- Static Content, Disabling static content]

With the constant `false` a request for `/static/utils.js` answers 404 (observed), but the tags do not know that: `s:head`
still writes the links, so a page that uses the `xhtml` theme and `s:head` needs the files to exist somewhere. The Core
Developer Guide says so ("make sure the JavaScript and CSS files shipped inside the core jar are extracted to your web
application directory"). Extraction is a build step. The files are not under `static/` in the jar; they are under
`org/apache/struts2/static/` and, for the theme stylesheets, `template/<theme>/styles.css`, and the loader maps them to the
URLs below, so the copy has to reproduce the URLs.

.Extracting the static files of the Struts 7.4.0 jar into the web application (run once, commit the result or run in the build)
[source,shell]
----
J=$HOME/.m2/repository/org/apache/struts/struts2-core/7.4.0/struts2-core-7.4.0.jar
mkdir -p tmp && (cd tmp && unzip -q "$J" "org/apache/struts2/static/*" \
    "template/xhtml/styles.css" "template/css_xhtml/styles.css")
D=src/main/webapp/static
mkdir -p $D/xhtml $D/css_xhtml
cp tmp/org/apache/struts2/static/* $D/
cp tmp/template/xhtml/styles.css $D/xhtml/
cp tmp/template/css_xhtml/styles.css $D/css_xhtml/
rm -rf tmp
----

Source: https://struts.apache.org/core-developers/static-content.html#default-content-loader[Core Developer Guide -- Static Content, Default Content Loader]

After this copy and with `struts.serve.static` set to `false`, the page produced by `s:head` linked
`/g12prod/static/xhtml/styles.css` and `/g12prod/static/utils.js`, and Tomcat's default servlet answered both with 200 and,
through the `ExpiresFilter` of <<bookshelf-app>>, `Cache-Control: max-age=604800` and an `Expires` seven days ahead
(observed). The application's own files under `assets/` get the same headers.

.Headers of the static files in the production WAR (observed)
[source,console]
----
$ curl -s -D - -o /dev/null http://localhost:18081/g12prod/static/utils.js
HTTP/1.1 200
Cache-Control: max-age=604800
Expires: Sat, 17 Oct 2026 11:26:41 GMT
Content-Type: text/javascript;charset=ISO-8859-1
----

The `charset=ISO-8859-1` on a JavaScript file comes from Tomcat's default servlet and its file-encoding default, not from
Struts; a proxy or an explicit `<mime-mapping>` and `fileEncoding` setting changes it, and it is harmless for the
ASCII-only files of the jar. A seven-day lifetime is safe for files whose names change when the content changes (a build
hash, a version directory) and a risk for `app.css` under a fixed name: a long `max-age` means returning visitors keep the
old file, so production builds either fingerprint the name or use a short lifetime with validation (`ETag`, `Last-Modified`),
which Tomcat's default servlet sends for files on disk.

Source: https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Caching[MDN -- HTTP caching]

Source: https://tomcat.apache.org/tomcat-11.0-doc/config/filter.html#Expires_Filter[Tomcat 11 -- Expires Filter]

[#exclude-pattern]
=== Keeping Requests Away from Struts

Files and servlets of the application itself are not served by the Struts loader. They pass through the Struts filter,
which tries to map the URL to an action and, finding none, lets the request continue. The mapping step is where a surprise
sits: the 7.4.0 default `struts.action.extension` is `action,,`, so an extensionless URL is a candidate action name. A file
with an extension (`/assets/app.css`) passes; an extensionless servlet URL (`/health`) does not.

.A servlet at an extensionless URL is swallowed by the Struts filter (observed)
[source,console]
----
$ curl -s -i http://localhost:18081/g12deploy/health | head -1
HTTP/1.1 404
$ curl -s http://localhost:18081/g12deploy/health | grep -o "There is no Action mapped[^.]*"
There is no Action mapped for namespace [&#47;] and action name [health] associated with context path [&#47;g12deploy]
----

The remedy is the exclude pattern: a comma-separated list of regular expressions matched against the request URI, which
makes the filter pass matching requests untouched.

.struts.action.excludePattern
[source,xml]
----
<constant name="struts.action.excludePattern" value="/health,/assets/.*"/>
----

With it `/health` answered 200 `UP` and `/assets/app.css` 200 (observed). Since Struts 6.1.0 a separator other than the comma
can be chosen with `struts.action.excludePattern.separator` when a pattern itself needs a comma. The expressions are Java
regular expressions, matched with the whole URI including the context path, so write them with care and prefer a narrow
pattern to `+.*+`.

Source: https://struts.apache.org/core-developers/static-content.html#preventing-struts-from-handling-a-request[Core Developer Guide -- Static Content, Preventing Struts from handling a request]

Source: https://struts.apache.org/maven/struts2-core/apidocs/org/apache/struts2/StrutsConstants.html#STRUTS_ACTION_EXCLUDE_PATTERN[Struts Javadoc -- StrutsConstants.STRUTS_ACTION_EXCLUDE_PATTERN]

[#webjars]
=== WebJars

Since Struts 7.3.0 the same pipeline serves WebJars, the client-side libraries (Bootstrap, jQuery) packaged as JARs under
`META-INF/resources/webjars/<name>/<version>/`. The core jar bundles `webjars-locator-lite`, and the `webjar` tag writes the
URL. The Bookshelf added `org.webjars:bootstrap:5.3.8` and one tag.

.A WebJar stylesheet in the page
[source,jsp]
----
<link rel="stylesheet" href="<s:webjar path="bootstrap/css/bootstrap.min.css"/>">
----

.The page and the files it links (observed)
[source,console]
----
$ curl -s http://localhost:18081/g12wj/books | grep -o 'href="[^"]*bootstrap[^"]*"'
href="/g12wj/static/webjars/bootstrap/5.3.8/css/bootstrap.min.css"
$ curl -s -o /dev/null -w "%{http_code}\n" .../static/webjars/bootstrap/5.3.8/css/bootstrap.min.css
200
$ curl -s -o /dev/null -w "%{http_code}\n" .../static/webjars/bootstrap/css/bootstrap.min.css
200
----

Several details follow from the run. The tag writes the versioned URL, although the page describes version-less requests;
both forms are served. WebJars ride the static pipeline, so they need `struts.serve.static` to be `true`: with `false` both
URLs answered 404, and a WebJar application that disables Struts static serving must let the container serve the jar's
`META-INF/resources` itself (the Servlet specification makes a container serve it for jars in `WEB-INF/lib`, under
the path `+/webjars/...+`; that route was not run here). `struts.webjars.allowlist` restricts the
names: with `jquery` as the allowlist the Bootstrap URL answered 404 and the tag wrote an empty `href`. Path traversal
(`..` and its encoded form) answered 404. The constants are `struts.webjars.enabled` (default `true`) and
`struts.webjars.allowlist` (default empty, meaning every WebJar on the classpath).

Source: https://struts.apache.org/core-developers/static-content.html#webjars-support[Core Developer Guide -- Static Content, WebJars support]

Source: https://struts.apache.org/tag-developers/webjar-tag.html[Tag Developer Guide -- webjar Tag]

The theme side of static content (`s:head`, the stylesheet of each theme, overriding templates) is in
xref:web/jsp-struts/struts/themes-and-templates.adoc[Themes and Templates]. For a high-traffic site the guide's advice is

Tomcat serve them, which is what `struts.serve.static=false` makes possible.

=== The OGNL Caches

Struts keeps two caches for OGNL, one for parsed expressions and one for `BeanInfo` objects, and 7.4.0 has caches for
localized text and proxy detection with the same constants. The _OGNL Cache Configuration_ page documents `struts.ognl.enableExpressionCache`,
`struts.ognl.expressionCacheMaxSize`, `struts.ognl.beanInfoCacheMaxSize` and two `LRUMode` constants. In 7.4.0 the `LRUMode`
constants do not exist; the cache implementation is chosen by a type constant instead.

.OGNL cache constants in 7.4.0 (read from default.properties and StrutsConstants)
[cols="4,2,4",options="header"]
|===
|Constant |Default |Meaning

|`struts.ognl.enableExpressionCache` |`true` |Toggle for the parsed-expression cache (since 6.0.0); disabling saves memory and costs speed
|`struts.ognl.expressionCacheType` |`wtlfu` |`basic` (flushes everything when full), `lru` (drops the least recently used entry) or `wtlfu` (the W-TinyLFU policy of the bundled Caffeine library)
|`struts.ognl.expressionCacheMaxSize` |`10000` |Maximum entries of the expression cache
|`struts.ognl.beanInfoCacheType` and `struts.ognl.beanInfoCacheMaxSize` |`wtlfu`, `10000` |The same for `BeanInfo` objects
|`struts.i18n.cacheType` and `struts.i18n.cacheMaxSize` |`wtlfu`, `10000` |The localized-text caches

[#freemarker-cache]
=== The FreeMarker Template Cache

FreeMarker caches compiled templates and, on each lookup, checks how long ago it last asked whether the template file
changed. The constant `struts.freemarker.templatesCache.updateDelay` sets that interval in seconds. A change to a template that
lives in the web application (for example a copy of `template/simple/text.ftl` under the web root, the way
xref:web/jsp-struts/struts/themes-and-templates.adoc[Themes and Templates] overrides templates) shows how it behaves. The
test edited the template and polled the page.

.How long a template edit stays invisible (observed, three runs each)
[cols="3,2",options="header"]
|===
|`struts.freemarker.templatesCache.updateDelay` |Edit visible after

|not set |5.1 s every time
|`1` |1.1 s
|`3600` |not within 60 s
|===

The default is therefore FreeMarker's 5 seconds, not the 500 ms of the Performance Tuning page, and the unit is seconds. In
production set the constant to a large value so that FreeMarker stops touching the file system for every template on every
request; templates inside the jar and inside the WAR do not change until the next deployment anyway.

.struts.freemarker.templatesCache.updateDelay
[source,xml]
----
<constant name="struts.freemarker.templatesCache.updateDelay" value="3600"/>
----

The page's other entries, `struts.freemarker.templatesCache` and a `freemarker.properties` file, are the pre-2.3 and
2.0.10 mechanisms and have no effect (the constant exists only as a commented line in `default.properties`).
`struts.freemarker.mru.max.strong.size` (default `0`, which selects the soft cache storage, "performs better in heavy loaded
applications") and `struts.freemarker.beanwrapperCache` (default `false`) are the two other knobs and need no change.

Source: https://struts.apache.org/tag-developers/freemarker.html#cache[Tag Developer Guide -- FreeMarker, Cache]

Source: https://struts.apache.org/core-developers/performance-tuning.html#create-a-freemarkerproperties-file-in-your-web-infclasses-directory[Core Developer Guide -- Performance Tuning, freemarker.properties]

[#whitespace]
=== Smaller HTML: Whitespace Stripping, s:compress and gzip

Three mechanisms reduce the size of the HTML. Whitespace stripping (since 7.2.0, `struts.freemarker.whitespaceStripping`,
default `true`) removes indentation and trailing whitespace from lines that contain only FreeMarker tags while the tag
templates are compiled. The `s:compress` tag (since 7.2.0, `struts.tag.compress.enabled`, default `true`) removes whitespace
between the tags of its body at run time. Neither touches text. gzip at the connector or proxy works on whatever the others
leave.

.The Bookshelf form page with each mechanism (bytes of the response body, observed)
[cols="4,2",options="header"]
|===
|Configuration |Bytes

|`struts.freemarker.whitespaceStripping=false` |825
|default (stripping on) |638
|stripping on, `s:compress` around the list, `struts.tag.compress.enabled=false` |680
|stripping on, `s:compress` around the list, enabled |660
|the final production page, plain |816
|the final production page, `Accept-Encoding: gzip` through the Tomcat connector |435
|===

.s:compress on the title list (default configuration)
[source,jsp]
----
<s:compress>
<ul>
  <s:iterator value="titles">
    <li><s:property/></li>
  </s:iterator>
</ul>
</s:compress>
----

.The output without and with s:compress (observed)
[source,html]
----
<!-- compress disabled -->
<ul>

    <li>
      Dune
    </li>

    <li>
      Neuromancer
    </li>

</ul>
<!-- compress enabled -->
<ul><li>
      Dune
    </li><li>
      Neuromancer
    </li></ul>
----

The measurements show the order of magnitude: stripping saved 187 of 825 bytes on a page that is mostly a form, `s:compress`
saved 20 bytes on a two-item list, and gzip roughly halved the page. Stripping is applied to the templates of the tags and
costs nothing at run time; `s:compress` has a run-time cost and protections (a 10 MB body limit, truncated log output,
safeguards against pathological regular expressions: `struts.tag.compress.maxSize`, `struts.tag.compress.log.maxLength`)
and is worth it only for large, whitespace-heavy pages. The documentation and `default.properties` say whitespace stripping
is "automatically disabled when devMode is active"; on 7.4.0 a run with `struts.devMode=true` (confirmed by `?debug=xml`)
still produced the 638-byte, stripped page, so do not rely on it for readable HTML while debugging.

gzip is a connector setting of the container. On Tomcat 11 it is three attributes of the HTTP connector in `server.xml`.

.A compressing connector (Tomcat server.xml)
[source,xml]
----
<Connector port="8080" protocol="HTTP/1.1"
           connectionTimeout="20000"
           redirectPort="8443"
           compression="on" compressionMinSize="256"
           compressibleMimeType="text/html,text/css,text/javascript,application/json" />
----

A request with `Accept-Encoding: gzip` then answered `Content-Encoding: gzip` and `Vary: accept-encoding` (observed, 816
bytes against 435). When a proxy terminates the connection it normally compresses too, and then the connector setting is
redundant; do one or the other, and take care to list only text types, because compressing an already compressed JPEG or
PDF wastes CPU. Compression over TLS of content that mixes secrets with attacker-controlled text is a known side-channel
class (BREACH); the xref:web/jsp-struts/struts/security-hardening.adoc[security hardening] page of this section is the place for that decision.

Source: https://struts.apache.org/core-developers/performance-tuning.html#enable-freemarker-whitespace-stripping[Core Developer Guide -- Performance Tuning, Whitespace Stripping]

Source: https://struts.apache.org/core-developers/performance-tuning.html#use-the-compress-tag-for-html-output-optimization[Core Developer Guide -- Performance Tuning, Compress Tag]

Source: https://struts.apache.org/tag-developers/compress-tag.html[Tag Developer Guide -- compress Tag]

Source: https://tomcat.apache.org/tomcat-11.0-doc/config/http.html#Standard_Implementation[Tomcat 11 -- HTTP Connector, compression attributes]

[#http-caching]
=== HTTP Caching of Dynamic Pages

The tip "use the correct HTTP headers" is about dynamic HTML. Struts adds no `Cache-Control` to an action's response (the
production request matrix below shows none on `/books`), so the response carries no caching directive at all. A page that
shows personal data must say `Cache-Control: no-store`, and a public catalogue page can be cached for a short time. The
`httpheader` result, a servlet filter in `web.xml` or the proxy can add the header; the filter mapped in front of the Struts
filter is the generic solution and works for any container.

[#sessions]
=== Sessions, I18nInterceptor and the Interceptor Stack

Struts itself does not create a session unless something asks. Two things ask without being noticed. A JSP creates a session
by default (page directive `session="true"`), so the production `books.jsp` says `session="false"`. And the `i18n`
interceptor, which is part of the default stack, stores the locale chosen with `request_locale` in the session. The Bookshelf
shows it.

.Which requests create a session (observed; the session id is replaced by a placeholder)
[source,console]
----
$ curl -s -D - -o /dev/null http://localhost:18081/g12deploy/books | grep -i set-cookie
$ curl -s -D - -o /dev/null "http://localhost:18081/g12deploy/books?request_locale=es" | grep -i set-cookie
Set-Cookie: JSESSIONID=<id>; Path=/g12deploy; HttpOnly
----

The first request has no cookie (the page has `session="false"` and nothing else touches the session); the second has one.
In this run only the request with `request_locale` created a session; an application that wants stateless,
cache-friendly pages never sends the parameter or removes the interceptor from the stack (<<stack>> shows the price). Sessions matter for scaling: each one is memory in the container and, in a cluster, state that
the load balancer has to keep together or the container has to replicate; replicated session attributes must be
`Serializable` (a servlet-container rule that this page did not run), so keep action objects out of the session and put in
it only the user and a few small values. The sibling topic page,
xref:web/jsp-struts/struts/action-chaining-sessions-and-scopes.adoc[Action Chaining, Sessions and Scopes], covers what is
legitimate to keep there, and xref:web/jsp-struts/struts/localization-and-i18n.adoc[Localization and i18n] the interceptor.

Source: https://struts.apache.org/core-developers/performance-tuning.html#do-not-create-sessions-unless-you-need-them[Core Developer Guide -- Performance Tuning, Do not create sessions unless you need them]

Source: https://struts.apache.org/core-developers/i18n-interceptor.html[Core Developer Guide -- I18n Interceptor]

[#stack]
==== A Leaner Stack Has a Price

The `defaultStack` of 7.4.0 has 24 interceptors, and the tip to use a smaller one is easy to follow with a stack that the
framework already defines: `validationWorkflowStack` is `basicStack` plus `validation` and `workflow`. The Bookshelf action
was switched to it with one line.

.Using validationWorkflowStack for one action
[source,xml]
----
<action name="books" class="org.example.bookshelf.BookAction">
    <interceptor-ref name="validationWorkflowStack"/>
    <result>/WEB-INF/views/books.jsp</result>
</action>
----

.Same request, default stack against validationWorkflowStack (observed)
[source,console]
----
$ curl -s -D - -o /dev/null "http://localhost:18081/g12deploy/books?request_locale=es"
# defaultStack: Set-Cookie JSESSIONID, Vary: Sec-Fetch-*, Cross-Origin-Embedder-Policy-Report-Only: require-corp,
#               Cross-Origin-Opener-Policy: same-origin
# validationWorkflowStack: no cookie, none of those headers
----

The saving is real (no session, fewer interceptors) and so is the loss. The `coop`, `coep` and `fetchMetadata`
interceptors of the 7.4.0 default stack write the Cross-Origin headers and the `Vary` header of the Sec-Fetch family and
implement a resource isolation policy based on the fetch metadata, and the `csp` interceptor belongs to the same family; the `debugging` interceptor is what answers
`?debug=` in development. A stack that omits them is a stack without those protections. The xref:web/jsp-struts/struts/security-headers-csp-coop-coep-fetch-metadata.adoc[security headers] page of this
section explains each one; the rule here is that "do not use interceptors you do not need" now includes security
interceptors, and that a custom stack should be built by copying `defaultStack` and deleting named entries, not by starting
from `basicStack`. See xref:web/jsp-struts/struts/interceptors.adoc[Interceptors] for the full list in order.

Source: https://struts.apache.org/core-developers/performance-tuning.html#do-not-use-interceptors-you-do-not-need[Core Developer Guide -- Performance Tuning, Do not use interceptors you do not need]

[#logging]
=== Logging

Log level is the tip with the largest effect. Struts and FreeMarker log a great deal at `debug`. On the Bookshelf, with
`org.apache.struts2` and `freemarker` at `debug`, one warm request to `/books` wrote 267 lines to standard output; with no
`log4j2.xml` and with `warn` it wrote none. A production `log4j2.xml` therefore sets the two loggers to `warn`, the root to
`info` and writes to the console, which is where Tomcat, Docker and Kubernetes collect logs.

.src/main/resources/log4j2.xml
[source,xml]
----
<?xml version="1.0" encoding="UTF-8"?>
<Configuration status="WARN">
  <Appenders>
    <Console name="Console" target="SYSTEM_OUT">
      <PatternLayout pattern="%d{ISO8601} %-5level %logger{1} - %msg%n"/>
    </Console>
  </Appenders>
  <Loggers>
    <Logger name="org.apache.struts2" level="warn"/>
    <Logger name="freemarker" level="warn"/>
    <Root level="info">
      <AppenderRef ref="Console"/>
    </Root>
  </Loggers>
</Configuration>
----

Source: https://logging.apache.org/log4j/2.x/manual/configuration.html[Apache Log4j -- Configuration]

Source: https://struts.apache.org/core-developers/performance-tuning.html#turn-off-logging-and-devmode[Core Developer Guide -- Performance Tuning, Turn off logging and devMode]

Errors are still logged: the `boom` action of the production WAR, which throws `IllegalStateException`, wrote an `ERROR`
line from `DefaultDispatcherErrorHandler` with the stack trace and the request got the 500 page of the `web.xml` (see
<<worked-example>>). The xref:web/jsp-struts/struts/debugging-dev-mode-and-logging.adoc[debugging page] of this section covers the levels in depth and the logging constants.

[#deploy-ways]
=== Context Paths, ROOT.war and Parallel Deployment

Tomcat derives the context path from the file name of the WAR. A WAR named `g12deploy.war` is served under `/g12deploy`, a
WAR named `ROOT.war` at `/`, and a name with `+##+` before a version string deploys several versions of the same path
side by side, so that a new version can take new sessions while the old one drains. All three were run on the private
instance.

.The three naming forms (observed)
[source,console]
----
$ cp g12deploy.war base/webapps/ROOT.war
$ curl -s -o /dev/null -w "%{http_code}\n" http://localhost:18081/books
200
$ curl -s http://localhost:18081/books | grep -o 'action="[^"]*"'
action="/books.action"
$ cp g12deploy.war 'base/webapps/g12pd##001.war' && cp g12deploy.war 'base/webapps/g12pd##002.war'
$ curl -s -o /dev/null -w "%{http_code}\n" http://localhost:18081/g12pd/books
200
----

With `ROOT.war` the form action is `/books.action`, because Struts builds links from the context path, which is empty; no
URL in the application may hard-code the old prefix. In a parallel deployment Tomcat sends a request without a session to the latest version and
a request with a session to the version that owns it (the rule of the Tomcat documentation); the two WARs are separate web
applications with their own Struts configuration and caches.
Remove the older version after its sessions have ended, and remember that anything with state outside the web application
(a database schema, a shared cache) must work with both versions at once, which is the real constraint of a rolling upgrade.

Source: https://tomcat.apache.org/tomcat-11.0-doc/config/context.html#Parallel_deployment[Tomcat 11 -- The Context Container, Parallel deployment]

Source: https://tomcat.apache.org/tomcat-11.0-doc/deployer-howto.html#Deploying_on_a_running_Tomcat_server[Tomcat 11 -- Deployer How-To, Deploying on a running Tomcat server]

=== JSP Compilation in Production

The views of a Struts application are JSP pages, so the Jasper settings of the container matter. The Tomcat Jasper How-To

[#proxy]
== Behind a Reverse Proxy

A production Struts application is nearly always behind a proxy or load balancer that terminates TLS. The container then
sees plain HTTP from the proxy, and Struts, which builds absolute URLs from the request, would write `http://` links. The
`s:url` tag with `forceAddSchemeHostAndPort` shows the effect, and `RemoteIpValve` the fix; the proxy has to send
`X-Forwarded-Proto` and the host.

.An absolute URL without and with the proxy headers (observed, a host name invented for the test)
[source,console]
----
$ curl -s http://localhost:18081/g12deploy/books | grep abs
<p id="abs">http://localhost:18081/g12deploy/books.action</p>
$ curl -s -H 'X-Forwarded-Proto: https' -H 'Host: books.example.test' http://localhost:18081/g12deploy/books | grep abs
<p id="abs">https://books.example.test/g12deploy/books.action</p>
----

The default `internalProxies` of the valve match loopback and private addresses, which is why the test from the same
machine was trusted; in production the valve's `internalProxies` must list exactly the proxies, so that clients cannot send
their own `X-Forwarded-For` and become someone else's address in the access log. The constants `struts.url.http.port` and `struts.url.https.port` exist for the port
Struts writes into absolute URLs when the valve cannot be used (they were not run here). Other proxy duties are the
proxy's own: TLS, HTTP/2, the large-upload limit (the `struts.multipart.maxSize` family of the
xref:web/jsp-struts/struts/file-upload-and-download.adoc#limits[file upload limits] must agree with the proxy's body size
limit), timeouts and buffering of long-running actions.

Source: https://tomcat.apache.org/tomcat-11.0-doc/config/valve.html#Remote_IP_Valve[Tomcat 11 -- Remote IP Valve]

[#health]
== Health Checks and Startup Failure

Container platforms ask the application whether it is alive and ready. The cheapest probe is a servlet that answers a
constant. It must bypass Struts (the previous section on <<exclude-pattern>>), and it must not touch the database, or the
whole fleet is restarted when the database is slow.

.src/main/java/org/example/bookshelf/HealthServlet.java
[source,java]
----
package org.example.bookshelf;

import jakarta.servlet.annotation.WebServlet;
import jakarta.servlet.http.HttpServlet;
import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;
import java.io.IOException;

@WebServlet("/health")
public class HealthServlet extends HttpServlet {
    @Override
    protected void doGet(HttpServletRequest req, HttpServletResponse resp) throws IOException {
        resp.setContentType("text/plain");
        resp.getWriter().print("UP");
    }
}
----

Source: https://jakarta.ee/specifications/servlet/6.1/apidocs/jakarta.servlet/jakarta/servlet/annotation/WebServlet.html[Jakarta Servlet 6.1 Javadoc -- WebServlet]

A servlet that always answers 200 is useful for exactly one reason that the bogus-cache run proved: when the Struts filter
fails to initialise (a bad constant, a malformed `struts.xml`, a missing class), Tomcat does not start the context at all,
and the health servlet, the static files and every action answer 404 together.

.A failed Struts filter takes the whole context down (observed)
[source,console]
----
$ curl -s -o /dev/null -w "books %{http_code}\n" http://localhost:18081/g12deploy/books
books 404
$ curl -s -o /dev/null -w "health %{http_code}\n" http://localhost:18081/g12deploy/health
health 404
$ grep -a SEVERE base/logs/catalina.out | tail -2
SEVERE ... StandardContext.startInternal One or more Filters failed to start. Full details will be found in the appropriate container log file
SEVERE ... StandardContext.startInternal Context [/g12deploy] startup failed due to previous errors
----

A readiness probe on `/health` therefore catches a configuration error (the pod never becomes ready and the rollout stops)
without the application having to say so. The error itself, with the `Caused by` chain of the Struts exception, is in the
container log; the first line to read after a failed deployment is the `SEVERE` message above, and the cause is the last
`Caused by` line.

Source: https://kubernetes.io/docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes/[Kubernetes -- Configure Liveness, Readiness and Startup Probes]

== Docker

The Docker pages of this site cover images, layers, caches, non-root users and scanning; this page shows only what is
specific to a Struts WAR. The xref:web/jsp-struts/getting-started.adoc[Getting Started] page of the JSP part has the verified multi-stage `Dockerfile` for a WAR on
the official `tomcat` image (the image's `webapps` directory is empty, a WAR named `ROOT.war` is served at `/`, and the
image runs Tomcat as `root`): xref:web/jsp-struts/getting-started.adoc#docker[A Docker Image for the WAR]. For the
production WAR the Struts-specific parts are the build, the memory flags and the way to turn the constants into environment
choices. The Docker daemon was not available for this page, so the following file was not built; it differs from the
verified one only in the final stage.

.Dockerfile (not built for this page)
[source,dockerfile]
----
# syntax=docker/dockerfile:1
FROM maven:3.9-eclipse-temurin-21 AS build
WORKDIR /build
COPY pom.xml .
RUN mvn -q -B dependency:go-offline
COPY src ./src
RUN mvn -q -B package

FROM tomcat:11.0-jdk21-temurin
COPY --from=build /build/target/g12prod.war /usr/local/tomcat/webapps/ROOT.war
ENV JAVA_OPTS="-XX:MaxRAMPercentage=75 -XX:+ExitOnOutOfMemoryError"
EXPOSE 8080
----

Source: https://hub.docker.com/_/tomcat[Docker Official Image -- tomcat]

Four rules carry over from the earlier sections. Use `JAVA_OPTS` (the JVM flags verified above were read back with `jcmd`);
if the image ships a `setenv.sh` that assigns `CATALINA_OPTS`, an environment variable of the same name is overwritten
(observed in this check with the scratch Tomcat, whose `setenv.sh` replaced the options the launcher exported). Struts
constants are not read from system properties (verified) and no mechanism for environment variables is documented, so
per-environment changes are either build
variants (<<constants>>), files mounted into the image (a `struts.properties` or an extra `+struts-*.xml+` read through the
`config` init-param) or the container platform's mechanism that the proxy and the application share. Send the logs to
standard output (the `log4j2.xml` of <<logging>>), so that `docker logs` shows them. And size the heap relative to the
container memory with `MaxRAMPercentage`, because an `-Xmx` copied from a bare-metal server is wrong in a container with a
512 Mi limit.

The Docker pages cover the rest: xref:backend/docker/dockerfile-fundamentals.adoc[Dockerfile Fundamentals],
xref:backend/docker/java-and-spring-boot-images.adoc[Java and Spring Boot Images],
xref:backend/docker/image-best-practices-and-security.adoc[Image Best Practices and Security] and
xref:backend/docker/resources-logging-and-monitoring.adoc[Resources, Logging and Monitoring]. For integration tests that
start the WAR in a container, xref:backend/docker/testcontainers-fundamentals.adoc[Testcontainers Fundamentals] applies
unchanged.

[#kubernetes]
== Kubernetes

The Kubernetes pages of this site explain every object; the manifest below only shows what a Struts WAR adds to a standard
Deployment: probes on the health servlet, JVM flags from the container memory and a memory limit that the heap setting can
use. It was parsed as YAML but not applied to a cluster, because no cluster was available.

.A Deployment and Service for the Bookshelf image (parsed only, not applied)
[source,yaml]
----
apiVersion: apps/v1
kind: Deployment
metadata:
  name: bookshelf-struts
spec:
  replicas: 2
  selector:
    matchLabels:
      app: bookshelf-struts
  template:
    metadata:
      labels:
        app: bookshelf-struts
    spec:
      terminationGracePeriodSeconds: 30
      containers:
        - name: tomcat
          image: registry.example.test/bookshelf-struts:1.0.0
          ports:
            - containerPort: 8080
          env:
            - name: JAVA_OPTS
              value: "-XX:MaxRAMPercentage=75 -XX:+ExitOnOutOfMemoryError"
          resources:
            requests:
              cpu: 250m
              memory: 512Mi
            limits:
              memory: 512Mi
          readinessProbe:
            httpGet:
              path: /health
              port: 8080
            periodSeconds: 5
          livenessProbe:
            httpGet:
              path: /health
              port: 8080
            initialDelaySeconds: 30
            periodSeconds: 10
---
apiVersion: v1
kind: Service
metadata:
  name: bookshelf-struts
spec:
  selector:
    app: bookshelf-struts
  ports:
    - port: 80
      targetPort: 8080
----

Source: https://kubernetes.io/docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes/[Kubernetes -- Configure Liveness, Readiness and Startup Probes]

The probe path `/health` answers 200 only when the Struts filter started, as shown above, and the readiness probe's
five-second period lets a bad rollout stop early. The image name is a placeholder; nothing in it is a credential. A
non-root user and a read-only root file system are good practice but need the temp, work and logs directories of Tomcat on
writable volumes, and were not tried; start from
xref:backend/kubernetes/health-probes-and-lifecycle.adoc[Health Probes and Lifecycle],
xref:backend/kubernetes/resource-management.adoc[Resource Management],
xref:backend/kubernetes/deployment-strategies.adoc[Deployment Strategies] and
xref:backend/kubernetes/configmaps.adoc[ConfigMaps] for each. A rolling update brings old and new versions up together,
so session handling matters: sessions live in the pod that created them and are lost when it is replaced, unless the
application keeps nothing important in the session or the container replicates sessions. The production Bookshelf keeps nothing in the session.

== A Production Checklist

The checklist collects the page into a table to read before a deployment. Rows that point to other pages are the ones that
need a decision rather than a constant.

.Production checklist for a Struts 7.4 WAR
[cols="3,4,3",options="header"]
|===
|Check |What to do |Where

|Development mode and reloading are off |`struts.devMode`, `struts.configuration.xml.reload`, `struts.i18n.reload` false; `?debug=xml` answers a normal page |<<constants>>
|The Struts security settings are on |`struts.allowlist.enable`, `struts.parameters.requireAnnotations`, `struts.enable.DynamicMethodInvocation=false`, the expression length limit |the xref:web/jsp-struts/struts/security-hardening.adoc[security hardening] page of this section
|Static content has an owner |`struts.serve.static=false` with the files extracted and cached, or a proxy or CDN |<<static-content>>
|Servlets and health endpoints bypass Struts |`struts.action.excludePattern` |<<exclude-pattern>>
|Caches and logging |OGNL cache type and size, FreeMarker `updateDelay`, `warn` for Struts and FreeMarker |<<performance>>
|No unnecessary sessions |`session="false"` on JSPs, a stack without `i18n` only if the headers stay |<<sessions>>
|Errors do not leak |Struts exception mappings, `web.xml` error pages, `ErrorReportValve` with `showReport` and `showServerInfo` false |<<tomcat>>
|The proxy and the application agree |`RemoteIpValve`, the cookie `Secure` and `SameSite` flags, upload limits, timeouts |<<proxy>>
|The container is minimal |No default webapps, current Tomcat 11.0.x, JSP `development=false` |<<tomcat>>, <<jasper>>
|Health and startup failure are visible |A servlet at `/health`; read the `SEVERE` line after a deployment |<<health>>
|Memory and supervision |`MaxRAMPercentage`, `ExitOnOutOfMemoryError` and something that restarts the process |<<tomcat>>, <<kubernetes>>
|Dependencies are current |The `struts2-bom` of the latest 7.x, and the bulletins read |the xref:web/jsp-struts/struts/security-bulletins.adoc[security bulletins] page of this section
|===

[#pitfalls]
== Pitfalls

.Deployment and production pitfalls, their symptoms and fixes (rows marked "observed" were reproduced on Tomcat 11.0.26 with Struts 7.4.0)
[cols="3,3,3",options="header"]
|===
|Symptom |Cause |Fix

|A servlet at `/health` answers 404 with "There is no Action mapped" (observed) |The filter on `+/*+` treats an extensionless URL as an action name because `struts.action.extension` is `action,,` |Add the path to `struts.action.excludePattern`
|Every URL of the context answers 404 after a configuration change (observed) |The Struts filter failed to initialise, so Tomcat did not start the context |Read the `SEVERE` and last `Caused by` lines in the container log
|A cache constant from the documentation seems to have no effect (observed) |`struts.ognl.expressionCacheLRUMode` and `beanInfoCacheLRUMode` do not exist in 7.4.0 and are ignored |Use `struts.ognl.expressionCacheType` and `struts.ognl.beanInfoCacheType`
|The application will not start after setting the cache type (observed) |An unknown type value fails the filter with a `NullPointerException` |Use `basic`, `lru` or `wtlfu`
|A template edit takes five seconds to show, or never shows (observed) |FreeMarker's update delay is 5 s by default; with `3600` it is an hour |Use a short delay in development and a long one in production
|Readable HTML expected under `devMode` is still compact (observed) |Whitespace stripping is not disabled by `devMode` in 7.4.0 despite the documentation |Set `struts.freemarker.whitespaceStripping` to `false` in development
|`/static/utils.js` returns 404 and forms lose their style (observed) |`struts.serve.static` is `false` and the files were not extracted |Extract them (<<static-content>>) or turn the constant back on
|WebJar URLs return 404 (observed) |WebJars ride the static pipeline, which `struts.serve.static=false` switched off, or the name is not in `struts.webjars.allowlist` |Serve the jar resources another way, or enable the pipeline and check the allowlist
|A `-Dstruts.devMode=true` option is ignored (observed) |Struts constants are not read from system properties; the option works only when referenced as `+${...}+` in `struts.xml` |Reference it in the constant (`+value="${struts.devMode:false}"+`), or use `+${env.NAME:default}+` with an environment variable (xref:web/jsp-struts/struts/configuration-struts-xml-and-constants.adoc#substitution[Configuration: struts.xml and Constants])
|JVM options set outside are missing in the process (observed) |A `setenv.sh` that assigns `CATALINA_OPTS` replaces the exported value |Use `JAVA_OPTS` or append in `setenv.sh`
|A leaner interceptor stack loses the Cross-Origin headers (observed) |`basicStack` and `validationWorkflowStack` have no `coop`, `coep`, `fetchMetadata`, `csp` |Start from a copy of `defaultStack` and remove entries by name
|A session cookie appears on a page that "uses no session" (observed) |`request_locale` makes the `i18n` interceptor store the locale in the session, and a JSP creates a session unless `session="false"` |Remove the parameter use, `session="false"`, or accept the session
|Links point to `http://` behind TLS termination (observed) |The container sees plain HTTP |`RemoteIpValve` with the forwarded headers, trusted proxies only
|The 404 page still shows `Apache Tomcat/11.0.26` |The default `ErrorReportValve` writes the version |`showServerInfo="false"` and `showReport="false"` on a Host valve, plus `<error-page>` entries
|After moving to `ROOT.war` links break |Hard-coded context path in the application |Build URLs with `s:url` and `s:form`, never with a literal prefix
|A long `max-age` serves an old `app.css` after a release |Same URL, new content |Fingerprint the file name or use a short lifetime
|The examples fail to run on a current JDK or container |The `struts-examples` parent is on 7.3.0 and Jetty 11 |Take versions from the `struts2-bom` and run on Tomcat 11 or Jetty 12.1
|The archetype generates a Struts 6.0.0 project |The archetypes were last published in 2023 |Start from the BOM, as in the Getting Started page
|===

[#books-outdated]
== Where the Books Are Outdated

The books on Struts and on web deployment were written for Struts 2.x on Tomcat 5 to 8, and four assumptions are out of date.

.Book-era practice against today (Struts 7.4, Tomcat 11)
[cols="3,3",options="header"]
|===
|Book-era practice |Today

|Tune with `struts.properties`, a `freemarker.properties` file and `struts.freemarker.templatesCache` |Constants in `struts.xml` (or `struts.properties`); `struts.freemarker.templatesCache.updateDelay` is the only template-cache knob that exists
|Rely on `struts.ognl.enableExpressionCache` and an OGNL jar swap for speed |A bounded `wtlfu` cache by default; no jar swap, OGNL is a managed dependency
|Serve `/struts/` or `/static/` content from the Struts jar and copy `template/` for FreeMarker caching |`/static` by constant; copy the static files, not the templates; templates found in the web application are cached by update delay
|Deploy to Tomcat 5, WebLogic, WebSphere or JBoss 5 from a `server.xml` context entry |A WAR in `webapps` or `ROOT.war`, with a Jakarta Servlet 6 container; the products on the Application Servers page are not targets

[#official-inconsistencies]
== Inconsistencies in the Official Documentation

Several statements of the official pages do not match 7.4.0. The first three are measured on the Bookshelf, the rest were
read from the pages and the jar.

* The _Performance Tuning_ page gives the FreeMarker `template_update_delay` default as 500 ms; the measured default is 5 s, and
  the unit of the Struts constant is seconds.
* The page and `default.properties` say whitespace stripping is disabled in `devMode`; `FreemarkerManager` has no such check
  and a `devMode` run was still stripped.
* The OGNL cache page documents `expressionCacheLRUMode` and `beanInfoCacheLRUMode`, which 7.4.0 ignores, and does not list
  `expressionCacheType`, `beanInfoCacheType` or the localized-text and proxy caches.
* The _Static Content_ page says Struts serves content "from the classpath" under `/static`; the files in the jar are under
  `org/apache/struts2/static` and `template/<theme>/`, so "extract to the web application directory" is not a plain unzip.
* `DefaultStaticContentLoader` sends a `Retry-After` header with the `Expires` date on a 200 response.
* The WebJar section describes version-less URLs; the `webjar` tag writes the versioned URL, and the feature needs
  `struts.serve.static=true`.
* The _Performance Tuning_ page still names the Ajax theme (Dojo), the Calendar tag and `struts.freemarker.templatesCache`; none
  exists in 7.4.0.
* _Application Servers_ lists servers from the 2000s and Wildfly 10.x, links only some of them, and does not name Tomcat 10.1
  or 11, Jetty 12 or GlassFish 8.
* The `struts-examples` repository is on 7.3.0 and Jetty 11 although 7.4.0 was released on 2026-10-02.
* GlassFish 8.0.5 reports `X-Powered-By: JSP/3.0` on a JSP response, although it implements Pages 4.0.

[#summary]
== Summary

A Struts 7.4 WAR is production-ready by default and the work is in what surrounds it. Keep `devMode` and the reload switches
off and check with `?debug=xml`; let the container or a proxy serve static files (`struts.serve.static=false`, the jar's
files extracted, `ExpiresFilter` or proxy caching) and send servlets and health endpoints around Struts with
`struts.action.excludePattern`; leave the OGNL caches at `wtlfu` and give FreeMarker a long update delay; keep logging at
`warn` for Struts and FreeMarker; create sessions only on purpose and do not trade the security-header interceptors for
speed; harden Tomcat with a Host-level `ErrorReportValve`, error pages, `RemoteIpValve` and cookie flags; deploy the same
WAR to Tomcat 11, Jetty 12.1 or GlassFish 8; and expose a `/health` servlet for probes, remembering that a failed Struts
filter takes the whole context down with a 404. Docker and Kubernetes add a start-up command, probes and memory limits
around that WAR and are covered by their own pages. Take learning code from `struts-examples` and the showcase, versions
from the BOM, and never from a 6.0.0 archetype.
