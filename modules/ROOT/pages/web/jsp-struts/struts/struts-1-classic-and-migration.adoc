[#status]
== Where Struts 1 Stands

Struts 1 was started in 2000 and had its last release, 1.3.10, in December 2008. The Struts project announced the end of
life of the 1.x line on 2013-04-05, in an announcement and a press release that say the same thing: the framework "has
reached its end of life and is no longer officially supported". The project's own end-of-life page lists "1.x" with the
date 5 April 2013 next to the Struts 2.3 and 2.5 lines, and says that an end-of-life version receives no more releases,
security fixes or bug fixes. The announcement's question-and-answer part, summarised on the xref:web/jsp-struts/introduction-and-history.adoc[Introduction and History] page,
has the sentences that matter for a legacy application: nothing is coming (you must find mitigations, patch the source or
migrate), there is "no drop-in replacement", Struts 2 is the recommended successor, and Spring Web MVC, Grails and
Stripes are the alternatives the team names.

=== Why It Must Not Run in Production

There are three separate reasons, and any one of them is enough.

*It is unpatched and its known vulnerabilities stay open.* The project said so in 2013, and the CVE records that were
published afterwards confirm it. All four records below were checked on 2026-10-10 against the CVE program's record
service; none of them has a fixed Struts 1 version, because there will be no further Struts 1 release.

The records name the damage, not a recipe, and this page does not give one. What matters for a team that inherits such an
application is the pattern: the weaknesses sit in the framework's request-to-bean machinery, and the framework's own
dependencies (BeanUtils 1.8.0, Commons FileUpload 1.1.1, Commons Validator 1.3.1, Commons Digester 1.8, all declared in the
1.3.10 `struts-core` POM) are as old as the framework. Updating a library next to Struts 1 is the only mitigation a team
can apply without touching the framework source, and it does not make the framework supported.

*It does not run on a current container.* The 1.3.10 `struts-core` POM declares `javax.servlet:servlet-api:2.3` as its
`provided` dependency, and the code, the tag libraries and the JSP support classes use the `javax.servlet` and
`javax.servlet.jsp` packages. Servlet 5.0 and Pages 3.0 moved the whole platform to `+jakarta.*+`, which is the namespace
of Tomcat 10 and later; Struts 1 cannot be recompiled by the project (there is no project), so it stays on Tomcat 9 and
older, or on a bytecode-converted copy that nobody supports. A `javax` WAR copied into the `webapps` folder of Tomcat 11
deploys without any warning and answers 404 for its URLs (observed and documented on the
xref:web/jsp-struts/getting-started.adoc[Getting Started] page; the Tomcat migration tool and the Host attribute
`legacyAppBase` convert such a WAR, which is a stopgap, not a fix). The platform side of this is explained in the
"javax to jakarta" part of xref:web/jsp-struts/introduction-and-history.adoc#javax-to-jakarta[Introduction and History]. Tomcat 9 itself has an end of
support date that the Tomcat site gives as "no earlier than 31 March 2027", so an application that stays on Struts 1 also
stays on a servlet container with a clock running.

Source: https://tomcat.apache.org/migration-10.html#Specification_APIs[Tomcat -- Migration Guide 10.0.x, Specification APIs]

*Nobody can hire for it, and the documentation is a zip file.* The skills are shared with the Struts 2 world only in
outline; the book that teaches Struts 1 (_Struts in Action_, 2002) describes 1.0 and 1.1 beta 2 and is outdated in the
details listed in <<books-outdated>>.

[#architecture]
== Struts 1 Architecture, to Read Legacy Code

Struts 1 is Model 2 with a servlet at the front. One servlet, `org.apache.struts.action.ActionServlet`, is mapped in
`web.xml` to a pattern (almost always `+*.do+`) and receives every request of the application. It reads one or more
configuration files at start-up, and for each request it hands over to a _request processor_, which selects the
configured _action mapping_, builds and fills a _form bean_, validates it, runs a singleton _action_ and then forwards or
redirects to the view named by the _action forward_ the action returned. Everything below is the vocabulary of that
sentence.

.One request through Struts 1.3.10 and through Struts 7.4.0
image::jsp-struts-struts1-vs-struts2-request-flow.svg["Two columns of boxes. Left, Struts 1.3.10: browser, ActionServlet, the request processor chain, ActionForm creation and population, validation, a singleton Action, ActionForward and the JSP view. Right, Struts 7.4.0: browser, StrutsPrepareAndExecuteFilter, ActionMapper and ActionProxy, the interceptor stack, validation and workflow, a new action per request, a Result and the JSP view",width=900]

|`struts-config.xml`
|The configuration file (DTD `struts-config_1_3.dtd`): `form-beans`, `global-exceptions`, `global-forwards`, `action-mappings`, `controller`, `message-resources` and `plug-in`, in that order (see <<reading-config>>)

|`ActionMapping`
|The configuration object for one request path: `path`, `type`, `name` (the form bean), `scope`, `validate`, `input`, `parameter`, `forward`, `roles`, `unknown`, the local `forward` and `exception` elements, plus any `set-property`. A custom subclass is named in `type`/`className`
|`+<action path="/bookAdd" type="..." name="bookForm" scope="request" validate="true" input="/book/form.jsp">+`

|`Action`
|The unit of work. Since 1.2 the method is `execute(ActionMapping, ActionForm, HttpServletRequest, HttpServletResponse)` (the 1.1 method `perform` was removed; the 1.3.10 `Action.java` no longer contains it) and it returns an `ActionForward`. One instance serves every request of the mapping, so it must be thread safe. `Action` offers the helpers `saveErrors`, `saveMessages`, `saveToken`, `isTokenValid`, `resetToken`, `isCancelled`, `getLocale` and `getResources`
|`public class BookAddAction extends Action`

|`ActionForm`
|The form bean: a class that extends `org.apache.struts.action.ActionForm`, with a getter and setter per field (almost always `String`), `reset(ActionMapping, HttpServletRequest)` to clear checkboxes and `validate(ActionMapping, HttpServletRequest)` to return `ActionErrors`. |`+<form-bean name="bookForm" type="...BookForm"/>+`

|`DynaActionForm`
|A form bean declared in XML with `form-property` elements instead of a class; a `DynaValidatorForm` adds the Validator. Read values with `get("title")`

|`mapping.findForward("success")` in an action; `<global-forwards>`

|`ActionMessages`, `ActionErrors`, `ActionMessage`
|The messages that a form or an action puts in the request or the session for the view; each has a property name and a message key resolved by the `MessageResources`. `ActionError` of the 1.0 and 1.1 days is no longer in the 1.3.10 core sources (`ActionMessage` replaces it)
|`ActionErrors errors = new ActionErrors(); errors.add("title", new ActionMessage("error.title.required"));`

|`MessageResources`
|The message bundle, declared with `<message-resources parameter="MessageResources"/>`, which is a base name resolved on the classpath like a `ResourceBundle`; read with `bean:message` or `html:errors` in a page

|Modules
|Several independent `struts-config` files in one web application, each with its own prefix in the URL (`/admin/user.do` for the module `/admin`), request processor, resources and forwards; `SwitchAction` moves from one module to another
|`<init-param>` named `config/admin` in `web.xml`

[#processor-chain]
=== The Request Processor Chain

The default request processor of 1.3.10 is a chain of Commons Chain commands, declared in `chain-config.xml` inside
`struts-core`. Reading it is the quickest way to learn what Struts 1 does between the servlet and your action, and what
a legacy `processPreprocess` override or a custom command was hooking into. The `process-action` chain of the 1.3.10
file runs these commands in this order (verified by reading the file in the 1.3.10 tree):

.The `process-action` chain of Struts 1.3.10
[cols="1,3,5",options="header"]
|===
|# |Command |What it does

|1 |`servlet.SelectLocale` |Selects the locale to be used for the request
|2 |`servlet.SetOriginalURI` |Sets the servlet path (the original URI) for later steps
|3 |`servlet.RequestNoCache` |Writes the no-cache headers when the controller is configured for it
|4 |`servlet.SetContentType` |Sets the content type configured on the controller
|5 |`RemoveCachedMessages` |Removes cached messages stored in the session (a command added in 1.3.5)
|6 |`servlet.SelectAction` |Matches the request path against the action mappings and finds the `ActionConfig`
|7 |`servlet.AuthorizeAction` |Checks the `roles` attribute of the mapping against the container's role information
|8 |`CreateActionForm` |Finds or creates the form bean named by the mapping, in the configured scope
|9 |`servlet.PopulateActionForm` |Calls `reset()`, then copies the request parameters onto the form bean (the BeanUtils step of CVE-2014-0114)
|10 |`servlet.ValidateActionForm` |Runs validation when the mapping says `validate="true"` and the request was not cancelled
|11 |`servlet.SelectInput` |When validation failed, selects the forward of the `input` page for the return trip
|12 |`ExecuteCommand` |Runs a Commons Chain command named by the `command` attribute of the mapping, if any
|13 |`servlet.SelectForward`, `SelectInclude`, `servlet.PerformInclude` |Handle mappings that carry only a `forward` or `include` attribute
|14 |`servlet.CreateAction` |Finds or creates the singleton `Action` for the mapping
|15 |`servlet.ExecuteAction` |Calls `execute` and stores the `ActionForward` that it returns
|===

The `process-view` chain then performs the forward (`ExecuteForwardCommand`, `servlet.PerformForward`), and a
`servlet-exception` chain handles an exception with the `ExceptionHandler` and the `global-exceptions` declarations. The
Struts 7 equivalents are the interceptor stack (the `params`, `validation` and `workflow` interceptors are steps 9 to 11),
the result and the exception mappings; the xref:web/jsp-struts/struts/architecture-and-request-lifecycle.adoc[Architecture and Request Lifecycle] page has the
full list. The difference to keep in mind is the unit of customisation: in Struts 1 a module has one lifecycle (the
chain) shared by every action in it, and in Struts 7 each action chooses its own interceptor stack.

=== The Action Library: Dispatch, Forward, Include and Switch

A legacy application rarely extends `Action` directly for every screen. The 1.3.10 `struts-extras` artifact (the package
`org.apache.struts.actions`) holds the ready-made ones that old code uses:

.Struts 1 action classes found in legacy code
[cols="2,5,4",options="header"]
|===
|Class |Behaviour |Struts 7 counterpart

|`ForwardAction`, `IncludeAction`
|Forward to, or include, the path named by the `parameter` attribute without any code: the way to put a JSP behind an action path
|An `<action>` with no class and a `<result>` (the Bookshelf `book-form` mapping below)

|`DispatchAction`
|Looks up a method whose name is in the request parameter named by the mapping's `parameter` attribute (`?method=lend`) and calls it with the `execute` signature; `unspecified` and `cancelled` are the fall-backs
|A wildcard mapping with `+method="{1}"+` and `<allowed-methods>`, or one action class with several methods

|`LookupDispatchAction`
|The dispatch method is chosen from the _label_ of the submit button, through a reverse lookup in the message resources (`getKeyMethodMap()`), so the buttons can be localised
|One mapping per button, or a method name in the button's `method:` name (strict method invocation applies)

|`MappingDispatchAction`
|The method name comes from the mapping's `parameter`, so one class serves several mappings
|The `method` attribute of `<action>` (the Bookshelf example in <<example>> uses a wildcard)

|`EventDispatchAction`
|Dispatches on a request parameter whose name, not value, selects the method (handy for image buttons)
|The `method:` prefix is gone with prefixes disabled; use separate mappings or the multi-button technique of the wildcard page

|`SwitchAction`
|Moves from one module to another through the `prefix` and `page` request parameters
|A different `namespace` (see the packages and namespaces page)

|`LocaleAction`, `DownloadAction`
|Change the session locale; stream a file
|The `i18n` interceptor with `request_locale`; the `stream` result
|===

[#taglibs]
=== The Tag Libraries, Validator and Tiles 1

Struts 1 shipped five tag libraries, each with its own URI in the descriptor (verified in the 1.3.10 TLDs):
`http://struts.apache.org/tags-html` (the `html` prefix, 29 tags in 1.3.10: `html:form`, `html:text`, `html:errors`,
`html:submit`, `html:link`, `html:option`, `html:multibox` and the others), `tags-bean` (`bean:write`, `bean:message`,
`bean:define`), `tags-logic` (`logic:iterate`, `logic:present`, `logic:equal`), `tags-nested` (the same tags with a nested
property path) and `tags-tiles`. They bind to a form bean by the `property` attribute and read from the page, request,
session or application scope, with `name` and `scope` attributes where the tag is not inside an `html:form`. A section
of JSP that uses `logic:iterate` over a collection with `bean:write` for each field is a typical page; the JSTL and EL
replacement is in the xref:web/jsp-struts/jsp/jstl-core.adoc[JSTL Core] and xref:web/jsp-struts/jsp/expression-language-basics.adoc[Expression Language Basics] pages, and the Struts 7
tag library is introduced on the xref:web/jsp-struts/struts/tags-overview-and-generic-tags.adoc[Tags Overview and Generic Tags] page.

The *Validator* is the Commons Validator integration: a `ValidatorPlugIn` loads `validator-rules.xml` (the rules, from
the `struts-core` jar) and `validation.xml` (the forms and fields of the application), a form bean extends
`ValidatorForm` or `ValidatorActionForm` (or is a `DynaValidatorForm`) and the declared rules (`required`, `mask`,
`minlength`, `email`, `intRange` and others) run on the server and, with `html:javascript`, in the browser. The
declarations for a field look like this in the 1.3.10 MailReader sample: `<field property="username"
depends="required"><arg key="prompt.username"/></field>` inside a `<form name="LogonForm">`.

*Tiles 1* is the layout framework that Struts 1 bundled (`struts-tiles`): definitions in `tiles-defs.xml`, the `tiles`
tags, and a `TilesPlugin`. It became the standalone Apache Tiles project, which was retired and moved to the Attic; a
Struts 1 application on Tiles 1 and a Struts 7 application on the Tiles plugin share the vocabulary, not the code (see
the xref:web/jsp-struts/struts/tiles-and-page-layouts.adoc[Tiles & Page Layouts] page).

[#reading-config]
== Reading a struts-config.xml

The configuration is the map of a Struts 1 application. The DTD of 1.3 (`struts-config_1_3.dtd`) fixes the order of the
top-level elements: `form-beans?`, `global-exceptions?`, `global-forwards?`, `action-mappings?`, `controller?`,
`+message-resources*+` and `+plug-in*+`. The Struts Blank application, which is the usual starting file of a legacy project,
shows each of them. The table gives the Struts 7 home of each element; the details are in <<concept-map>>.

.The elements of struts-config.xml (1.3 DTD)
[cols="2,5,4",options="header"]

== Worked Example: Moving the Bookshelf from Struts 1 to Struts 7

This is the heart of the page. The Bookshelf of a legacy shop has a book list, an "add a book" form (title, author and
ISBN, with validation and a double-submit guard), a lend and give-back action and a global error page. Each step shows
the Struts 1 "before" (a labelled sketch in the style of the Struts Blank and MailReader sources, never run) and the
Struts 7.4.0 "after" (built, deployed and requested). The "after" application is one WAR, `g12struts1.war`, with the
context path `/g12struts1` on Tomcat 11.0.26: the Struts BOM `org.apache.struts:struts2-bom:7.4.0`, `struts2-core`, the
Servlet and Pages APIs as `provided`, and the filter described in step 1. Imports and `package` lines are left out of
the listings; the package is `org.example.bookshelf`. Every request below was made with `curl` against the running
context; session identifiers and token values are removed from the output shown.

=== Step 2: Keeping the .do URLs While You Migrate

A migration is much easier when the URLs that bookmarks, other applications and a reverse proxy know do not change. The
default action extension of Struts 7.4.0 is `action,,` (the `.action` extension or none), so a legacy `book-list.do` would
answer 404. One constant fixes that for the length of the migration:

[source,xml]
----
<constant name="struts.action.extension" value="do,action"/>
----

With this value the Struts 7 actions answer to the legacy `.do` URL and to `.action`. Verified requests:

[source,console]
----
$ curl -s -o /dev/null -w '%{http_code}\n' http://localhost:18080/g12struts1/book-list.do
200
$ curl -s -o /dev/null -w '%{http_code}\n' http://localhost:18080/g12struts1/book-list.action
200
$ curl -s -o /dev/null -w '%{http_code}\n' http://localhost:18080/g12struts1/book-list
404
----

Two details matter. The first extension in the list is the one that Struts writes into the URLs it generates: the
`redirectAction` result of step 5 sent `Location: /g12struts1/book-list.do`, so the migrated pages keep emitting the
legacy URL shape. The second is that the extensionless URL stopped working, as the 404 above shows, because the trailing
empty entry of the default (`action,,`) was not repeated; write `do,action,,` if the bare name must keep working too.
The value is a migration aid: once the callers have been moved, return to the default and delete the constant.

=== Step 4: ActionForm and Action to a Validated Action

*Before (Struts 1.3.10, legacy sketch).* Two classes, one for the data and one for the logic. The form validates itself
and an `Action` copies it into the business object:

[source,java]
----
public class BookForm extends ActionForm {
    private String title;
    private String author;
    private String isbn;
    // getters and setters for the three fields

    @Override
    public void reset(ActionMapping mapping, HttpServletRequest request) {
        title = author = isbn = null;
    }

    @Override
    public ActionErrors validate(ActionMapping mapping, HttpServletRequest request) {
        ActionErrors errors = new ActionErrors();
        if (title == null || title.trim().isEmpty()) {
            errors.add("title", new ActionMessage("error.title.required"));
        }
        if (isbn != null && !isbn.matches("\\d{13}")) {
            errors.add("isbn", new ActionMessage("error.isbn.format"));
        }
        return errors;
    }
}

public class BookAddAction extends Action {
    @Override
    public ActionForward execute(ActionMapping mapping, ActionForm form,
                                 HttpServletRequest request,
                                 HttpServletResponse response) throws Exception {
        BookForm f = (BookForm) form;
        catalogue.add(new Book(f.getTitle(), f.getAuthor(), f.getIsbn()));
        return mapping.findForward("list");
    }
}
----

public class AddBookAction extends ActionSupport {

    private String author;
    private String isbn;

    @Override
    public void validate() {
        if (title == null || title.isBlank()) {
            addFieldError("title", getText("error.title.required"));
        }
        if (isbn != null && !isbn.isBlank() && !isbn.matches("\\d{13}")) {
            addFieldError("isbn", getText("error.isbn.format"));
        }
    }

    @Override
    public String execute() {
        Catalogue.add(new Catalogue.Book(title, author, isbn));
        addActionMessage(getText("book.added", new String[] {title}));
        return SUCCESS;
    }

    public String getTitle() { return title; }
    @StrutsParameter
    public void setTitle(String title) { this.title = title; }

    public String getAuthor() { return author; }
    @StrutsParameter
    public void setAuthor(String author) { this.author = author; }

    public String getIsbn() { return isbn; }
    @StrutsParameter
    public void setIsbn(String isbn) { this.isbn = isbn; }
}

=== Step 5: ActionForward to Results, and the Redirect After Post

In Struts 1 a forward is a name looked up in the mapping and then in `global-forwards`; `redirect="true"` turns it into a
redirect. In Struts 7 the action returns a result code (`SUCCESS`, `INPUT`, a custom string), and the mapping or
`global-results` binds the code to a result type. The `book-add` mapping of step 3 shows the three forwards of the
Struts 1 `bookAdd` mapping:

.Forwards and their Struts 7 results
[cols="3,3,4",options="header"]
|===
|Struts 1 |Struts 7 |Note

|`input="/WEB-INF/pages/form.jsp"` on the mapping |`<result name="input">/WEB-INF/views/form.jsp</result>` |`input` is the code the `workflow` interceptor returns when validation fails; if the mapping lacks it the request ends in 404 (see <<pitfalls>>)
|`<forward name="list" path="/bookList.do" redirect="true"/>` |`<result name="success" type="redirectAction">book-list</result>` |The post-redirect-get pattern, now by action name; the `Location` header carries the configured extension
|`<forward name="success" path="/WEB-INF/pages/list.jsp"/>` |`<result>/WEB-INF/views/list.jsp</result>` |The default result name is `success` and the default type is `dispatcher`
|`mapping.findForward("failure")` |`return ERROR;` and a `<global-results>` entry |A global result works for every action of the package
|===

Source: https://struts.apache.org/core-developers/result-configuration.html#result-elements[Struts Core Developer Guide -- Result Configuration, Result Elements]

== Migrating to Struts 7 (and Elsewhere)

The project's own advice for migration is short, and old. The wiki page "Migration Strategies" (last edited by a Struts
committer in 2023) opens with "four non-exclusive paths" and lists three:

.The strategies of the wiki page "Migration Strategies"
[cols="3,6",options="header"]
|===
|Strategy |As the wiki words it, condensed

|Dual processor, shared resources
|Add the Struts 2 JARs to the existing Struts 1.3 application; let Struts 2 handle `+*.action+` and Struts 1 handle `+*.do+`, side by side in one web application; build new features in the new framework and migrate the old pieces as needed; optionally share messages, validation rules and Tiles configuration
|Study known Struts 1 applications rewritten for Struts 2
|Familiar applications such as the Struts MailReader were rewritten to show best practice
|Use a conversion wizard
|A tool might read `web.xml` and the Struts 1 configuration and generate the Struts 2 classes, pages and configuration, marking what needs attention; full compatibility is unlikely
|===

Source: https://cwiki.apache.org/confluence/spaces/WW/pages/14221/Migration+Strategies[Apache Struts wiki -- Migration Strategies]

Two sibling wiki pages describe the tooling that was imagined in the Struts 2.0 days. "Migration Tools" is explicitly "a
whiteboard describing tools that volunteers might write, given sufficient interest": a `TextProvider` that reads the
Struts 1 message resources, an interceptor that applies Struts 1 validations to Struts 2 actions, an XSLT conversion
from `struts-config.xml` to `struts.xml`. "Struts 1 Plugin" documents what was actually built: the `struts2-struts1-plugin`
with a wrapper action `org.apache.struts2.s1.Struts1Action` that runs an unmodified Struts 1 `Action` and `ActionForm`
inside a Struts 2 application (package `struts1-default`), plus two interceptors that apply form validation and
`reset()`. It never converted the JSPs: the page's own warning says the Struts 1 tag libraries cannot continue to be
used, and the JSPs have to be rewritten for the Struts 2 tags. That plugin is gone: the 2.3 to 2.5 migration guide lists
the "Struts1 Plugin" among the plugins that were "dropped and aren't supported anymore", and Maven Central's last
`struts2-struts1-plugin` release is 2.3.37 (verified 2026-10-08), so no Struts 7 application can use it.

Source: https://cwiki.apache.org/confluence/spaces/WW/pages/13954/Migration+Tools[Apache Struts wiki -- Migration Tools]

Source: https://cwiki.apache.org/confluence/spaces/WW/pages/44227/Struts+1+Plugin[Apache Struts wiki -- Struts 1 Plugin]

Source: https://cwiki.apache.org/confluence/spaces/WW/pages/65868294/Struts+2.3+to+2.5+migration[Apache Struts wiki -- Struts 2.3 to 2.5 migration]

The wiki advice has to be adjusted to the situation of 2026 in one important way: the two frameworks cannot both be on
the target platform. Struts 1.3.10 needs the `javax` namespace (Tomcat 9 and older), and Struts 7.4.0 needs Java 17 and
Jakarta Servlet 6 (Tomcat 10.1 and 11), as the Struts 6 to 7 migration guide says in its first paragraphs. Struts 6.x is
the bridge: the 2.5 to 6.0.0 migration guide says Struts 6 needs Java 8 and Servlet API 3.1, so Struts 6.12.0 (released
the same day as 7.4.0 and still supported) runs in the same `javax` container as Struts 1. The migration therefore has two
axes, the framework and the platform, and the plan below orders them so that only one moves at a time.

Source: https://cwiki.apache.org/confluence/spaces/WW/pages/293046977/Struts+6.x.x+to+7.x.x+migration[Apache Struts wiki -- Struts 6.x.x to 7.x.x migration]

Source: https://cwiki.apache.org/confluence/spaces/WW/pages/199528120/Struts+2.5+to+6.0.0+migration[Apache Struts wiki -- Struts 2.5 to 6.0.0 migration]

=== The Migration Path

.A piecemeal migration of a Struts 1 application to Struts 7.4.0
[mermaid]
....
flowchart TD
    A["Struts 1.3.10 monolith: javax, Tomcat 9 or older, unsupported"] --> B["1. Inventory and characterization tests: every .do URL, form, rule, message"]
    B --> C["2. Freeze and contain: no new Struts 1 features, update libraries, put a WAF in front"]
    C --> D{"3. How do the two coexist?"}
    D -->|"same WAR, same container"| E["3a. Add Struts 6.x beside Struts 1: .do stays, new screens on the new filter"]
    D -->|"new deployment"| F["3b. New Struts 7 or Spring Boot app behind a reverse proxy: the strangler fig"]
    E --> G["4. Move screens one at a time: form, action, validation, messages, tags, tests"]
    F --> G
    G --> H["5. Retire Struts 1: remove ActionServlet, struts-config.xml, taglibs, Tiles 1"]
    H --> I["6. Platform step: Struts 6.x to 7.4.0, javax to jakarta, Java 17+, Tomcat 10.1 or 11"]
    I --> J["Struts 7.4.0 on Tomcat 11, supported"]
....

The steps, with what each needs:

. *Inventory and characterization tests.* List every mapping of every `struts-config.xml` (modules included), every
form bean and its scope, every `validation.xml` form and the messages. For each `.do` URL record a request and the
response it gives today (a characterization test: it pins the current behaviour, wrong or right, so a regression is
visible). The inventory also finds the unusual: custom `processorClass` subclasses, `PlugIn` classes, `ActionMapping`
subclasses and Commons Chain commands have no one-to-one successor and become interceptors or filters.
. *Freeze and contain.* No new feature in Struts 1. Update the libraries that sit next to the framework (the BeanUtils
named by CVE-2014-0114 first), restrict the request parameters at a gateway or filter, and put a web application
firewall in front. This lowers the risk during the migration; it is not a fix and does not extend any support.
. *Choose the coexistence.* Option 3a is the wiki's dual processor, brought up to date: add Struts 6.x (the line that
still uses `javax`) to the same WAR, map its filter so that it takes the new URLs, leave `ActionServlet` on `+*.do+`, and
migrate screen by screen. It shares the session, the container-managed security and the database pool, and it carries
the cost of two frameworks and two sets of Commons libraries in one class loader; whether Struts 1 and 6.x coexist
cleanly in a given application is not something this page verified (Struts 1 could not be started on the verification
platform), so prove it on a copy first. Option 3b is the strangler fig: build the new application as a separate
deployment, put a reverse proxy in front of both, and move one URL prefix at a time. It needs the session and
authentication shared or re-established (a token or a gateway) and gives the cleanest end state.
. *Move one screen at a time.* For each screen apply steps 3 to 12 of <<example>>: the mapping, the form and action
(collapsed into one action or a `ModelDriven` model), the validation, the forwards as results, the messages, the tags
and the characterization test run against the new URL. Keep the `.do` extension (step 2) while callers still use it.
. *Retire Struts 1* when the last mapping has moved: remove the servlet, the `struts-config.xml` files, the five
taglibs and Tiles 1, and the `+struts-*+` 1.3.10 jars (and with them the libraries that only they needed).
. *Take the platform step.* With only Struts 6.x left, upgrade to Struts 7.4.0 following the Struts 6 to 7 migration
guide (the repackaging of `com.opensymphony.xwork2` into `org.apache.struts2`, `@StrutsParameter`, exact namespaces, the
`jakarta` namespace and Java 17); the xref:web/jsp-struts/whats-changed-and-migration.adoc[What Changed and Migration] page of this section carries the full checklist. If the target is
Spring Boot instead of Struts 7, the same inventory drives the controller conversion in the concept map above.

[#strangler-fig]
=== The Strangler Fig and the Bookshop

The strangler fig is the migration discipline the third option relies on: put a facade (a reverse proxy) in front of the
legacy application, route a growing set of URLs to the new one, and delete the legacy code that no longer receives
traffic, instead of rewriting everything behind a big-bang switch. The repository's decisions-and-migrations section
applies it to a concrete legacy system, the _Bookshop_ (a Java EE 7, Struts 1 and JSP monolith, `bookshop-web.war`, on
WebLogic), and covers what this page leaves out: the reverse proxy and its routing rules, separating presentation from
backend first, branch by abstraction, the anti-corruption layer, data synchronisation between the old and the new schema,
and the exit criteria for switching the legacy system off. Read the xref:backend/architecture/decisions-and-migrations/migration-path-legacy-to-modern-stack.adoc[Migration Path: From a Legacy Stack to a Modern One]
page for that part, and the xref:backend/architecture/decisions-and-migrations/migration-overview.adoc[Migration Overview] page for the discipline that all migration paths share.
What this page adds to it is the technology-specific half: how a Struts 1 screen is translated (<<example>>), what the
legacy constructs are (<<architecture>>) and what each becomes (<<concept-map>>). The Bookshelf of this page and the
Bookshop are different systems on purpose: the Bookshelf is a teaching application small enough to show every step, the
Bookshop a modernization case study.

Source: https://martinfowler.com/bliki/StranglerFigApplication.html[Martin Fowler -- Strangler Fig Application]

=== A Checklist per Screen

.The conversion of one Struts 1 screen
[cols="1,4,4",options="header"]
|===
|# |Struts 1 artefact |What to do

|1 |`<action path>` and its `forward`/`input`/`parameter` |Write the `<action>` with results; keep the `.do` URL through `struts.action.extension` while callers exist
|2 |`ActionForm` / `DynaActionForm` |Move the fields to the action (with `@StrutsParameter` on the setters) or to a `ModelDriven` model; delete `reset()`
|3 |`Action.execute` |Return a result code; move servlet API calls to `Aware` interfaces only where unavoidable; make shared state explicit (the singleton is gone)
|4 |`validate()` / `validation.xml` |Port to `validate()`, XML validators or annotations; keep the message keys
|5 |`ActionMessages` / `saveMessages` |`addActionMessage` and `addFieldError`; add the `store` interceptor if the message must survive a redirect
|6 |`saveToken` / `isTokenValid` |`<s:token/>` and the `token` interceptor with the `invalid.token` result
|7 |`html`, `bean`, `logic`, `nested` tags |The Struts tags, or JSTL and EL where no form binding is needed
|8 |Tiles definition |A tile in the Tiles plugin, or a tag-file layout
|9 |`global-exceptions` |`<global-exception-mappings>` in the package
|10 |The characterization test |Run it against the new mapping; compare the status code, the redirect target and the visible text

[#pitfalls]
== Pitfalls

.Mistakes seen when reading Struts 1 code or migrating it (those marked verified were reproduced on Struts 7.4.0 and Tomcat 11.0.26)
[cols="3,3,4",options="header"]
|===
|Mistake |What happens |Fix

|Copying the structure of `struts-config.xml` without the intent
|A Struts 2 application with one action class per URL and a form class per action, which keeps the second input object that Struts 2 removed
|Use the action's properties or a `ModelDriven` model; collapse the form and the action

|Setting `struts.action.extension` to `do,action` and expecting the bare URL to keep working (verified)
|`/book-list` answers 404 while `/book-list.do` and `/book-list.action` answer 200
|Add the trailing empty entry (`do,action,,`) if the bare name is needed, and remove the constant when the callers are gone

|Putting `<allowed-methods>` before the `<result>` elements (verified)
|The filter fails to start with a parse error from the DTD (the content of the `action` element must be params, results, interceptor references and exception mappings, then `allowed-methods`), and every URL answers 404
|Put `allowed-methods` last in the `<action>` (the DTD order)

|Expecting a method not in `<allowed-methods>` to answer (verified)
|`shelf-bogus.do` answers 404; but `shelf-execute.do` answers 200 because `execute` is in the global list of `struts-default`
|List every method that a URL may reach; know the global list of the base package

|A mapping without an `input` result and a validation error (verified)
|404 with the message "No result defined for action org.example.bookshelf.AddBookAction and result input"
|Define `<result name="input">`, as the Struts 1 mapping's `input` attribute did

|`addActionMessage` before a redirect without the `store` interceptor (verified)
|The message is gone on the next page; the Struts 1 `+saveMessages(session, ...)+` kept it
|`store` in `STORE` mode on the writing action and `RETRIEVE` on the reading one

|Forgetting `@StrutsParameter` on a setter of the action
|The property stays null and validation reports a required field that the user filled in
|Annotate the setters (the action's members), or use a `ModelDriven` model, whose members are exempt

|Forgetting that Struts 1 actions were singletons
|Legacy code kept state in static or shared fields, expecting a single instance (a `synchronized` block in an action is a sign); Struts 7 creates an action per request and the old shared fields are now per request or stale
|Move shared state to a service or a scope; remove the synchronisation that only guarded the action's own fields

|Using a `record` (read with bare names inside `s:iterator`) or a DTO class that the OGNL allowlist does not cover in a view (verified with a record)
|The list printed `+ /  / +` for every book: empty values instead of an error
|Use bean classes with getters in an allowlisted package (xref:web/jsp-struts/struts/value-stack-action-context-and-ognl.adoc#records[Java Records in OGNL])

|Trying to run Struts 1 on Tomcat 10 or 11
|The `javax` WAR deploys silently and answers 404 (see the Getting Started page); converting it with the migration tool is unsupported
|Keep Struts 1 on Tomcat 9 during the migration, or migrate first

|Expecting the Struts 1 plugin to help
|No Struts 7 artifact exists; the plugin ended with 2.3.37 and never supported the Struts 1 tags
|Convert the screens; use the `.do` extension and a proxy for coexistence

|Treating `html:javascript` as portable
|No Struts 7 equivalent; client-side validation of the themes is deprecated as of 7.4.0
|Keep browser checks in your own script or HTML5 attributes; the server rule decides

|Migrating the platform and the framework at the same time
|Two sources of failure in one release; no way to tell which one broke a screen
|Do the framework step on `javax` (Struts 6.x), then the platform step (Struts 7.4.0 and `jakarta`)
|===

[#books-outdated]
== Where the Books Are Outdated

_Struts in Action_ (Husted, Dumoulin, Franciscus and Winterfeldt; Manning, 2002) is the reference book on Struts 1. It was
written against Struts 1.0.2 and 1.1 beta 2, Servlet 2.3 and JSP 1.2, and defers to an online errata page for the
differences of the final 1.1; its closing chapters on migrating from 1.0 to 1.1 cover a change that is two decades old.
_Struts 2 in Action_ (Brown, Davis and Stanlick; Manning, 2008) has a chapter, "Migration from Struts Classic", that
covers the concept mapping, running both frameworks side by side, the piecemeal conversion and the Struts 1 plugin,
against Struts 2.0. Neither book is quoted here; the table gives the points to correct.
