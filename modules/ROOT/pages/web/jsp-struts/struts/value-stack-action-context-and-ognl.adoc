[#big-picture]
== The Big Picture

Four words are used for what happens when a view needs a value, and they are easy to confuse:

[cols="2,5",options="header"]
|===
|Term |What it is

|`ActionContext` |`org.apache.struts2.ActionContext`: a thread-local holder around one `Map<String, Object>` (the context map). It is the place where everything belonging to the current request is reachable: session map, application map, request parameters, locale, the action name, the `ActionInvocation`, the servlet request, response and context, the `ValueStack` itself
|`ValueStack` |`org.apache.struts2.util.ValueStack` (the implementation is `org.apache.struts2.ognl.OgnlValueStack`): a stack of objects, seen by OGNL as one single object. The action is pushed on it, so are the model of a `ModelDriven` action, the element of an `s:iterator` loop and whatever `s:push` or `s:bean` adds. It is the OGNL root
|OGNL context |The `OgnlContext` that OGNL evaluates against. Struts makes the `ActionContext` map this context (the value stack even keeps a reference to it as `getContext()`), so "the context map", "the ActionContext map" and "the OGNL context" are the same map
|OGNL |The Object-Graph Navigation Language, a library (OGNL 3.4.12 inside Struts 7.4.0) that evaluates expression strings such as `+books[0].title+` or `+#session.user+` against a root object and a context map
|===

Source: https://struts.apache.org/tag-developers/ognl.html#context[Tag Developer Guide -- OGNL, Context]

The Tag Developer Guide states the relation in one sentence: the framework sets the OGNL context to be the
`ActionContext` and the `ValueStack` to be the OGNL root object, and along with the stack it places other objects in the
context (application, session, request, parameters, `attr` and the current action). Because OGNL treats the root
specially (properties of the root need no marker) and everything else in the context needs a `+#+`, the rule for every
expression in a Struts view follows directly: a bare name is looked up on the value stack, a name with a `+#+` in front is
looked up in the context map.

image::jsp-struts-value-stack.svg["The ValueStack as OGNL root inside the ActionContext map with the # named objects, and where five expression forms are looked up",width=940]

The diagram uses the real objects of one request to the example action of this page: the stack holds the model (a
`Book`, pushed by the `modelDriven` interceptor), the action and the `DefaultTextProvider` that every new stack starts
with, and the map holds the session, request, application and parameter views next to the stack. Both halves are created
by the framework for each request (the creation step is part of the request lifecycle described in
xref:web/jsp-struts/struts/architecture-and-request-lifecycle.adoc[Architecture and Request Lifecycle]) and discarded
with it; nothing is shared between two requests, which is why an action needs no thread safety of its own.

The names also tell where to look when something fails: a `null` from `+title+` is a stack problem (no getter, wrong
object on top, access refused by the security rules), a `null` from `+#session.user+` is a context-map problem (a
different key, an object put into the wrong scope). The rest of the page follows the same split: the context first, then
the stack, then the language that joins them.

[#action-context]
== ActionContext

=== What It Is

The Javadoc of `ActionContext` calls it the context in which an action is executed: each context is a container of the
objects an action needs for execution, like the session, parameters and locale. It is thread local, which means that the
values stored in it are unique per thread; the benefit stated by the Javadoc is that nobody has to worry about a user
specific action context and nobody has to make actions thread safe. `ActionContext.getContext()` returns the context
bound to the current thread, and `getContextMap()` returns the underlying map, which is the same map that OGNL sees as
its context.

=== What It Holds

The 7.4.0 class exposes the request state through typed getters and fluent `+with...+` setters (the setters return the
context, so they chain). The table lists the getters and the OGNL name or map key behind each one.

[cols="3,4,3",options="header"]
|===
|Getter |Returns |OGNL name or key

|`getSession()` |The session attributes as a `Map` |`+#session+`
|`getApplication()` |The `ServletContext` attributes as a `Map` |`+#application+`
|`getParameters()` |`org.apache.struts2.dispatcher.HttpParameters`, the request parameters |`+#parameters+`
|`getLocale()` |The `Locale` chosen for the request (the `i18n` interceptor can change it) |key `org.apache.struts2.ActionContext.locale`
|`getActionName()` |The name of the action being executed |key `org.apache.struts2.ActionContext.name`
|`getActionInvocation()` |The `ActionInvocation` of the request (action, proxy, stack, result code) |key `org.apache.struts2.ActionContext.actionInvocation`
|`getActionMapping()` |The `ActionMapping` of the request |key `struts.actionMapping`

=== Reaching the Scopes From an Action

Three ways exist to read or write the session, request and application from Java, and the Core Developer Guide ranks
them (the servlet-level objects behind these maps are described in
xref:web/jsp-struts/servlet-fundamentals.adoc#sessions[Servlet Fundamentals, Sessions], and the action classes that receive them in
xref:web/jsp-struts/struts/actions.adoc[Actions]). The recommended one is the `Aware` interfaces of `org.apache.struts2.action`: the framework, through the
`servletConfig` interceptor of `defaultStack`, calls the single method of each interface that an action implements, and
the action stores what it is given. The guide says that using `ActionContext` directly for this is a bad practice and
should be avoided, with the `+*Aware+` interfaces as the alternative; `ServletActionContext` (static helpers for the request,
response, servlet context, page context, action mapping and the stack of a request) is the third way and ties the action
to the servlet API in the same way as `ServletRequestAware`.

[cols="3,3,3",options="header"]
|===
|Mechanism |Method the framework calls or you call |Gives
|`SessionAware` |`void withSession(Map<String, Object>)` |the same map as `+ActionContext.getSession()+` and `+#session+`
|`ApplicationAware` |`void withApplication(Map<String, Object>)` |the application map, `+#application+`
|`ServletRequestAware` |`void withServletRequest(HttpServletRequest)` |the Jakarta request; ties the action to the Servlet API
|`ParametersAware` |`void withParameters(HttpParameters)` |the request parameters, `+#parameters+`
|`ServletResponseAware`, `ServletContextAware`, `CookiesAware`, `PrincipalAware` |`withServletResponse`, `withServletContext`, `withCookies`, `withPrincipalProxy` |the response, the servlet context, the cookies and the principal
|`ActionContext.getContext()` |static, thread local |the context map and everything in the table above; `null` on a thread that is not serving the request
|`ServletActionContext` |static: `getRequest()`, `getResponse()`, `getServletContext()`, `getPageContext()`, `getActionContext()`, `getValueStack(HttpServletRequest)`, `getActionMapping()` |the servlet objects of the current request
|===

Source: https://struts.apache.org/core-developers/accessing-application-session-request-objects.html#accessing-from-java[Core Developer Guide -- Accessing application, session, request objects, Accessing from Java]

The Aware interfaces were renamed in 6.0 (`setSession` became `withSession`, `setServletRequest` became
`withServletRequest`) and moved from `org.apache.struts2.interceptor` to `org.apache.struts2.action`; code written for
the older names does not compile on 7.x.

.AwareAction.java, session, application and request through the Aware interfaces
[source,java]
----
public class AwareAction extends ActionSupport
        implements SessionAware, ApplicationAware, ServletRequestAware {
    private Map<String, Object> session;
    private Map<String, Object> application;
    private HttpServletRequest request;
    private String report;

    @Override public void withSession(Map<String, Object> session) { this.session = session; }
    @Override public void withApplication(Map<String, Object> application) { this.application = application; }
    @Override public void withServletRequest(HttpServletRequest request) { this.request = request; }

    @Override
    public String execute() {
        session.put("lastShelf", "scifi");
        application.put("shelfCount", 3);
        request.setAttribute("requestId", 7);
        report = "session=" + session.get("lastShelf") + " application=" + application.get("shelfCount")
                + " request=" + request.getAttribute("requestId")
                + " sameMapAsContext=" + (session == ActionContext.getContext().getSession());
        return SUCCESS;
    }

    public String getReport() { return report; }
}
----

Source: https://struts.apache.org/core-developers/servlet-config-interceptor.html[Core Developer Guide -- Servlet Config Interceptor]

=== ActionContext Outside a Request

The 7.4.0 API creates and binds a context with static factories, which is what makes unit tests without a servlet
container possible: `ActionContext.of(map)` (or `of()`) creates a context around a map, the `+with...+` methods fill it,
`bind()` attaches it to the current thread and `clear()` removes it.

.ActionContextDemo.java, a context bound by hand and invisible from other threads
[source,java]
----
Map<String, Object> session = new HashMap<>();
session.put("user", "alice");
System.out.println("before bind: " + ActionContext.getContext());
ActionContext.of(new HashMap<>()).withSession(session).withLocale(Locale.FRANCE).bind();
System.out.println(ActionContext.getContext().getSession() + " " + ActionContext.getContext().getLocale());
Thread other = new Thread(() -> System.out.println("other thread: " + ActionContext.getContext()));
other.start();
other.join();
ActionContext.clear();
System.out.println("after clear: " + ActionContext.getContext());
----

Source: https://struts.apache.org/maven/struts2-core/apidocs/org/apache/struts2/ActionContext.html#bind()[Struts Javadoc -- ActionContext.bind()]

Compiled and run with the WAR's libraries on Java 21, the program printed:

[source,text]
----

{user=alice} fr_FR
other thread: null
after clear: null
----

Source: https://struts.apache.org/maven/struts2-core/apidocs/org/apache/struts2/ActionContext.html#of(java.util.Map)[Struts Javadoc -- ActionContext.of(Map)]

The third line is the practical consequence of the thread-local design: a thread that the container did not dispatch the
request to (a task submitted to an executor, a `CompletableFuture`, a servlet async callback) sees `null` from
`ActionContext.getContext()`. Code that has to run there must receive the data it needs as arguments, or capture the
values before leaving the request thread.

[#value-stack]
== ValueStack

=== What Is on the Stack and When

The interceptors that fill the stack (`modelDriven`, `params`, `servletConfig`) are described on xref:web/jsp-struts/struts/interceptors.adoc[Interceptors]. The Javadoc describes the value stack as a structure that allows multiple beans to be pushed in and dynamic expressions to
be evaluated against it; when an expression is evaluated, the stack is searched from the latest object pushed in to the
earliest, looking for a bean with a getter or setter for the given property, or a method of the given name. Four things
put objects on it during a request:

[cols="3,5",options="header"]
|===
|Who |What is pushed and when

|The framework, when it creates the stack |A `TextProvider` (observed: `DefaultTextProvider`), always the bottom element
|`DefaultActionInvocation`, before the interceptors run |The action instance
|The `modelDriven` interceptor (and `scopedModelDriven`) |The object returned by `getModel()` of a `ModelDriven` action, on top of the action
|Tags and your own code |`s:push` (an object for the length of its body), `s:iterator` (each element during its turn), `s:bean` (the created bean), `+ValueStack.push(Object)+`, `+ValueStack.set(String, Object)+` (a map that holds name and value, pushed on first use)
|===

Source: https://struts.apache.org/maven/struts2-core/apidocs/org/apache/struts2/util/ValueStack.html#class-description[Struts Javadoc -- ValueStack]

=== Seeing the Stack

The root of the stack is a `CompoundRoot`, a list that `ValueStack.getRoot()` returns, so printing its elements shows what a
view can reach. This action property lists the class of every element from the top; it is used by all the stack
experiments below.

.ShelfAction.java, the classes on the stack from the top
[source,java]
----
public String getStackReport() {
    ValueStack stack = ActionContext.getContext().getValueStack();
    StringBuilder sb = new StringBuilder("size=").append(stack.size());
    for (int i = 0; i < stack.getRoot().size(); i++) {
        sb.append("\n[").append(i).append("] ").append(stack.getRoot().get(i).getClass().getName());
    }
    return sb.toString();
}
----

=== The ValueStack API

[cols="3,5",options="header"]
|===
|Member |Role

|`+Object peek()+`, `+Object pop()+`, `+void push(Object)+`, `+int size()+` |The stack operations; `peek()` is the top, which is what the OGNL name `top` returns
|`+CompoundRoot getRoot()+` |The list behind the stack, index 0 being the top
|`+Map<String, Object> getContext()+` and `+ActionContext getActionContext()+` |The OGNL context map and the context that wraps it
|`+void set(String key, Object value)+` |Puts `value` under `key` in a map that is itself pushed on the stack, so `+findValue(key)+` and a plain name in a view find it. Repeated calls reuse the map while it is still on top
|`+Object findValue(String expr)+` and the overloads with a `+Class+` type and a `boolean throwExceptionOnFailure` |Evaluates the expression against the stack; the `Class` overload converts the result with the type converters; returns `null` when the lookup fails, unless the boolean asks for an exception
|`+String findString(String expr)+` (and with the `boolean`) |The same, converted to a `String`
|`+void setValue(String expr, Object value)+`, `+setValue(String, Object, boolean)+`, `+setParameter(String, Object)+` |Sets the property that the expression names; `setParameter` is the variant meant for request values and, unlike `setValue`, does not allow eval (chained) expressions
|`+setDefaultType(Class)+`, `+setExprOverrides(Map)+`, `+getExprOverrides()+` |A default type to convert to when no type is given, and an override map whose entries take precedence in find operations
|`+VALUE_STACK+`, `+REPORT_ERRORS_ON_NO_PROP+` |Constants: the context key of the stack and the flag for "report property errors"
|===

=== An Interceptor That Writes to the Stack

An interceptor reaches both objects through the `ActionInvocation`: `getStack()` for the stack and

=== A Model on Top of the Action

=== How a Plain Name Is Resolved

The OGNL Basics page explains why Struts needs more than plain OGNL. Standard OGNL has exactly one root, so a name that is
not a property of the root needs a `+#+` prefix. Struts wants many "roots", so the whole stack is the root and a special
property accessor looks at the entries from the top down until it finds an object that has the property. With an `Animal`
on top of a `Person` the docs show that `species` reads the animal, `salary` reads the person and `name` reads the
animal's (the top wins a tie). To reach the lower one, XWork added indexes on the stack.

[cols="2,5",options="header"]
|===
|Expression |Meaning

|`+title+` |Search the stack from the top; the first element with a `title` property answers
|`+[0].title+` |Cut the stack from element 0 (the whole stack) and search it: here the same as `+title+`
|`+[1].title+` |Cut the stack from element 1 (everything below the top) and search it
|`+top+` |The top element of the stack, the same as `+peek()+`
|`+[1].top+` |The top element of the stack cut at 1: the second element of the whole stack
|`+[0].top.filter+` |The property `filter` of the top element, reading that single object and not searching
|===

Source: https://struts.apache.org/tag-developers/ognl-basics.html#struts-specific-language-features[Tag Developer Guide -- OGNL Basics, Struts-specific language features]

On the plain `shelf` action the lines A20 to A22 printed `+[0].top.filter=sci+`, `+[1].top+` as the string form of
`org.apache.struts2.text.DefaultTextProvider` and `+top.filter=sci+`, confirming that the cut `+[1]+` starts below the
action. When no object has the name, two things can happen: the search ends with `null`, or, if the lookup fails or yields
`null`, the stack falls back to the context map under the same name. On the probe action, the bare name `session` returned
the session map `+{user=alice}+` and the bare names `action` and `struts.actionMapping` returned the action and the mapping,
all of them context entries read without a `+#+`; with `struts.ognl.valueStackFallbackToContext` set to `false` the bare
`session` returned `null` while `+#session.user+` still returned `alice`. The fallback is convenient and unintended in most
code, and the security section lists it among the settings to switch off.

== OGNL

=== What It Is and What Struts Adds

OGNL, the Object-Graph Navigation Language, is an expression language for getting and setting properties of Java objects.
It is a separate open source library (the project lives at https://github.com/orphan-oss/ognl, and Struts 7.4.0 pins
version 3.4.12); Struts uses it in four places that you meet daily: the tags (`value`, `test`, `list` and `+%{...}+`
attributes), the `params` interceptor (a request parameter name such as `book.title` is an OGNL expression that is
_set_ on the stack), the validators and the result configuration (`+${...}+` in a result parameter is OGNL as well, see xref:web/jsp-struts/struts/results-and-result-types.adoc[Results and Result Types]). The
Tag Developer Guide gives the minimum the framework adds to plain OGNL, and everything in this section is built on it:

* the value stack is the root object, and a property lookup searches the stack from the top (see the previous section);
* the `ActionContext` map is the OGNL context, so `+#name+` reads a key of it;
* a handful of named objects (`+#action+`, `+#parameters+`, `+#request+`, `+#session+`, `+#application+`, `+#attr+`) are placed in
  the context;
* tag attributes may contain `+%{...}+` to force evaluation (the next two sections).

The OGNL language itself (operators, literals, projection, selection, lambdas, `instanceof`, `new`, the `@class@member`
static syntax) is documented by the OGNL project in its https://github.com/orphan-oss/ognl/blob/master/docs/LanguageGuide.md[Language Guide]; this page covers what Struts 7.4.0 lets through.

== OGNL and JSP EL in the Same Page

A Struts JSP has two expression languages side by side, evaluated by different engines at different moments, and keeping
them apart is the first skill of Struts view code.

[cols="2,3,3",options="header"]
|===
|Aspect |OGNL (Struts tags) |JSP EL (`+${...}+`)

|Evaluated by |The Struts tag at request time, against the value stack and the context map |The JSP container (Jasper), against the page, request, session and application scopes
|Where it is written |In tag attributes (`value`, `test`, `list`) and inside `+%{...}+` |In template text and in the attributes of tags that accept runtime expressions
|Root |The value stack (properties without a marker); context entries with `+#+` |The scopes; `+${filter}+` is `+pageContext.findAttribute("filter")+`
|Output escaping |`s:property` escapes HTML by default |None: the text appears as it is, a cross-site scripting risk for request data
|Static calls, lambdas |Static fields only with a setting and the allowlist, static methods never |Governed by the EL specification (static access, lambdas, collection operations), see xref:web/jsp-struts/jsp/expression-language-basics.adoc[Expression Language Basics]
|===

Source: https://struts.apache.org/tag-developers/tag-syntax.html#expression-language-notations[Tag Developer Guide -- Tag Syntax, Expression Language Notations]

=== Expressions in Tag Attributes: the Three Rules

The Tag Syntax page reduces the way Struts evaluates attributes to three rules: every attribute whose Java type is `String`
is parsed for the `+%{ ... }+` notation, and what is outside of it is literal; every attribute of a non-`String` type
(boolean, integer, `Object`, collection) is evaluated directly as an expression; and if a non-`String` attribute does use
`+%{...}+`, the notation is stripped as redundant and the content is evaluated. The `value` attribute of the _form_ tags
(`textfield`, `hidden`, `select` and so on) is a `String` attribute, so there it must be written `+value="%{filter}"+` to read a
property, while `s:property`, `s:set`, `s:if` and `s:iterator` take an expression in `value` and `test` without the wrapper.

.more.jsp, a literal and an expression in the value of a textfield, and a non-String attribute with and without the wrapper
[source,jsp]
----
B28 <s:textfield name="q2" value="filter"/>
    <s:textfield name="q3" value="%{filter}"/>
B29 <s:iterator value="books" begin="1" end="%{1}"><s:property value="title"/></s:iterator>
----

Source: https://struts.apache.org/tag-developers/tag-syntax.html#the-value-attribute-of-form-tags[Tag Developer Guide -- Tag Syntax, The value attribute of form tags]

[source,html]
----
<input type="text" name="q2" value="filter" id="q2"/>
<input type="text" name="q3" value="sci" id="q3"/>
Neuromancer
----

Source: https://struts.apache.org/tag-developers/tag-syntax.html#non-string-attributes[Tag Developer Guide -- Tag Syntax, Non-String Attributes]

Source: https://struts.apache.org/tag-developers/textfield-tag.html[Tag Developer Guide -- textfield]

The first field shows the literal text `filter`, the second the property; `begin` and `end` are integers, so the second
`s:iterator` ran for the single element between index 1 and `+%{1}+`, the wrapper being ignored. The same rules give the
label trick of the OGNL page: `+<s:textfield name="username" label="%{#request.foo}"/>+` puts the request attribute `foo`
into a `String` attribute (`label`) that would otherwise take its text literally.

=== JSP EL Cannot Be Used Inside a Struts Tag Attribute

The Struts tags are declared in the TLD with attributes that do not accept runtime expressions, which is a different
mechanism from the OGNL evaluation. Writing a JSP EL expression where an OGNL expression belongs is therefore not
silently wrong, it fails when the page is translated.

.A JSP EL expression in a Struts tag attribute
[source,jsp]
----
<s:property value="${filter}"/>
----

Source: https://struts.apache.org/tag-developers/tag-syntax.html#expression-language-notations[Tag Developer Guide -- Tag Syntax, Expression Language Notations]

On Tomcat 11.0.26 the request returned HTTP 500 with the message `According to TLD or attribute directive in tag file,
attribute [value] does not accept any expressions` (a `JasperException` at the line and column of the attribute). The
repair is the OGNL form `+<s:property value="filter"/>+`.

=== How `+${}+` Reaches the Value Stack

JSP EL looks a name up through the scopes, page first (the scope rules are on xref:web/jsp-struts/jsp/implicit-objects-and-scopes.adoc[Implicit Objects & Scopes]), and ends with `request.getAttribute(name)`. Struts wraps the request in a
`StrutsRequestWrapper`, whose `getAttribute` returns the real attribute if there is one and otherwise asks the value stack
for the same name with `findValue(name)`. That is why `+${filter}+`, `+${books[0].title}+` and `+${banner}+` print values that
nobody put into a scope: they were found on the stack. The line A32 of `shelf.jsp` shows it:

.shelf.jsp, EL reading the stack and the scopes
[source,jsp]
----
A32 EL filter=${filter}|titles=${books[0].title}|user=${user}|requestId=${requestId}
A33 EL sessionScope=${sessionScope.user}
----

Source: https://raw.githubusercontent.com/apache/struts/STRUTS_7_4_0/core/src/main/java/org/apache/struts2/dispatcher/StrutsRequestWrapper.java[Struts 7.4.0 source -- StrutsRequestWrapper.getAttribute]

[source,text]
----
A32 EL filter=sci|titles=Dune|user=alice|requestId=42
A33 EL sessionScope=alice
----

Source: https://struts.apache.org/core-developers/accessing-application-session-request-objects.html#accessing-from-the-view-jsp-freemarker-etc[Core Developer Guide -- Accessing application, session, request objects, Accessing from the view]

`filter` and `books` came from the stack (the action), `user` from the session (the context-aware lookup: the attribute
`user` is not a request attribute, it is found because the stack search reaches the context fallback), and `requestId` from
the request. The constant `struts.disableRequestAttributeValueStackLookup`, introduced for "JSTL accessibility" according
to its Javadoc and `false` by default, switches the stack lookup off. With it set to `true`, the same page printed
`+A32 EL filter=|titles=|user=alice|requestId=42+`: the stack-based names went empty, while the real scope attributes and
`sessionScope.user` still worked. The setting closes a path from a request-supplied attribute name to the stack and is part of
the hardened configurations; it also means that EL in a page must then use the scopes explicitly or `s:set` to publish
what it needs, which is the technique of the next paragraph.

The older Tag Developer Guide page "Access to ValueStack from JSPs" describes the same need for third-party tag libraries
that read JSP EL (it names DisplayTag): expose a value with `s:set` in the request scope (its example is
`+<s:set name="'a'" value="{ 1, 2, 3, 4 }" scope="request"/>+`, with the old `name` attribute that today is `var`) and then
use `+${a[0]}+` in the third-party tag. The `B21` output above is the modern form of that idea (`+${v2}+` found the
request-scope variable). The rest of that page, a custom EL function `vs()` backed by a `wwel.tld` and a `Functions`
class that imports `com.opensymphony.xwork.ActionContext` (the pre-2.0 WebWork package) and `a.getName()`, is a historical
workaround from the JSP 2.0 era; since the request wrapper does the lookup, no custom function is needed, and the code
shown does not compile against `org.apache.struts2.ActionContext`.

.more.jsp, publishing a stack value to anything that reads JSP EL
[source,jsp]
----
<s:set var="shelfSize" value="books.size" scope="request"/>
<p>Shelf size: ${shelfSize}</p>
----

Source: https://struts.apache.org/tag-developers/access-to-valuestack-from-jsps.html[Tag Developer Guide -- Access to ValueStack from JSPs]

The page rendered `<p>Shelf size: 3</p>`; a third-party tag whose attribute accepts EL would receive the same `3`.

[#forced-evaluation]
== Forced Evaluation and Its Dangers

The notation `+%{expression}+` tells a tag to evaluate the text inside it as OGNL when the attribute is a `String`. It is
very powerful, and the Security Guide says why it is dangerous: used with wrong data it can lead to remote code
execution, so incoming data must never be used as the input of a forced expression evaluation. The danger has two forms.

*Building expression text from request data.* The text inside `+%{...}+`, in a `value` or `test` attribute and in a
message passed to `getText` is code. Reading a request value inside an expression is harmless: `+label="%{filter}"+`
evaluates the name `filter` and prints whatever the property holds. The dangerous shape is the opposite one, where the
_text of the expression itself_ comes from the request: a tag attribute assembled from request text before the tag sees
it, or an action that hands a user-supplied string to `+ValueStack.findValue(...)+` (the scratch probe action of this page
does exactly that, to demonstrate the issue, and must never be written in an application).

*Double evaluation.* Historically the evaluated result of a `+%{...}+` attribute could itself contain `+%{...}+` that the
framework evaluated again, so a request parameter holding an expression ended up executed. The bulletins S2-001 (a
remote code exploit on form validation error) and S2-029 (forced double OGNL evaluation on raw user input in tag
attributes) are examples of that class, and S2-045 (CVE-2017-5638, the Jakarta Multipart parser) showed that even the text
of an error message generated while handling a request can end up evaluated. The 7.0 migration guide still names "double
evaluations in the past" as the case that the allowlist was introduced for. The observed behaviour of 7.4.0 is that a result is not
evaluated again; the test is easy to run: the request `+/g9valuestack/shelf?filter=%25%7B1%2B1%7D+` (the parameter
`filter` holding the text `+%{1+1}+`) went through the lines that print it:

.shelf.jsp, printing a parameter that looks like an expression
[source,jsp]
----
A1 filter=<s:property value="filter"/>
A28 %{}: <s:property value="%{filter}"/>
A29 text:<s:textfield name="q" label="%{filter}" value="%{#session.user}"/>
----

Source: https://struts.apache.org/security/#do-not-use-incoming-untrusted-user-input-in-forced-expression-evaluation[Security Guide -- Do not use incoming, untrusted user input in forced expression evaluation]

[source,text]
----
A1 filter=%{1+1}
A28 %{}: %{1+1}
<label for="q" class="label">%{1+1}:</label>
----

Source: https://struts.apache.org/security/#do-not-use-incoming-untrusted-user-input-in-forced-expression-evaluation[Security Guide -- Do not use incoming, untrusted user input in forced expression evaluation]

The text of the parameter appeared as typed in every place, including the label of the `textfield`, so the value of an
expression is not evaluated a second time on 7.4.0. A third form of the problem remains by design: methods that evaluate
their _argument_ as a message template. The guide names the `+getText(...)+` methods of the `TextProvider` (for instance
`ActionSupport.getText(String)`), which evaluate expressions embedded in the key or default text. On the probe action, with
the 7.4.0 defaults:

.Evaluating a message template that contains an expression (observed with the probe action)
[source,java]
----
getText("%{1+1}")                       // returns 2
getText("x", "%{#session.user}")        // returns alice
getText("x", "a-%{filter}")             // returns a-all
----

Source: https://struts.apache.org/security/#do-not-use-incoming-values-as-an-input-for-localisation-logic[Security Guide -- Do not use incoming values as an input for localisation logic]

All three returned the evaluated result, confirming the warning: an action that passes a request parameter to `getText`
as the key or the default text hands the sender an OGNL evaluator. The rule that the guide states, and that applies to every
API on this page, is to treat the text of an expression as code: it comes from your pages and your configuration, never
from the request. Request data belongs in the value positions (`s:property` of a property, a `+{0}+` parameter of a message),
and the allowlist and the other restrictions of the next section are the second line of defence, not the first.

[#cache]
== The Expression Cache and "Compilation"

OGNL parses every expression string into a syntax tree before it can evaluate it, and parsing is the expensive part of
repeated evaluations. Struts keeps the parsed trees in an expression cache (`OgnlUtil`, backed by a cache from
`ExpressionCacheFactory`) and caches the parsed `BeanInfo` of classes in a second cache. The Core Developer Guide page on
the OGNL caches lists the settings; the 7.4.0 values come from `default.properties` and `StrutsConstants`:

[cols="4,2,4",options="header"]
|===
|Constant |7.4.0 default |Meaning

|`struts.ognl.enableExpressionCache` |`true` (the Java default; the constant is not in `default.properties`) |Master switch of the expression cache; with `false` every evaluation parses again, which costs time and saves memory
|`struts.ognl.expressionCacheType` |`wtlfu` |The cache implementation: `basic` (a map that is flushed completely when full), `lru` (the least recently used entry goes first) or `wtlfu` (the W-TinyLfu policy)
|`struts.ognl.expressionCacheMaxSize` |`10000` |The size limit, to be chosen together with the type
|`struts.ognl.beanInfoCacheType` and `struts.ognl.beanInfoCacheMaxSize` |`wtlfu` and `10000` |The same two settings for the `BeanInfo` cache
|`struts.ognl.expressionCacheFactory` and `struts.ognl.beanInfoCacheFactory` |default factories |Names of replacement factories (implementations of `OgnlCacheFactory`)
|===

Source: https://struts.apache.org/core-developers/ognl-cache-configuration.html[Core Developer Guide -- OGNL Cache Configuration]

.struts.xml, tuning the expression cache
[source,xml]
----
<constant name="struts.ognl.enableExpressionCache" value="true"/>
<constant name="struts.ognl.expressionCacheType" value="lru"/>
<constant name="struts.ognl.expressionCacheMaxSize" value="2000"/>
----

Source: https://raw.githubusercontent.com/apache/struts/STRUTS_7_4_0/core/src/main/java/org/apache/struts2/StrutsConstants.java[Struts 7.4.0 source -- StrutsConstants, STRUTS_OGNL_EXPRESSION_CACHE_TYPE]

The effect is easy to see by reading the cache size from the container, which the scratch probe action did through
`ActionContext.getContext().getInstance(OgnlUtil.class).expressionCacheSize()`. Evaluating the expressions `10+1`, `10+1`,
`10+1`, `10+2`, `10+3`, `10+3` and `books.size+100` one request after the other printed the sizes 59, 59, 59, 60, 61, 61 and 62: a new
string adds one entry, a repeated string adds none. With `struts.ognl.enableExpressionCache` set to `false` the size
stayed `0` for every request. The sizes are relative: the cache already held 58 entries parsed by the framework and the
JSP in earlier requests. Two consequences follow. A tag attribute that is
the same on every request costs one parse for the whole lifetime of the application, while an expression whose text
changes with each request (built from request data, the pattern the previous sections forbid) fills the cache with entries
that are never used again; this is the performance reason, besides the security reason, to keep expression text constant.
And the cache keeps the _tree_, not a Java class: nothing is compiled to bytecode.

The Tag Developer Guide has a page called "OGNL Expression Compilation" that suggests otherwise, and it is worth reading
for what it is. It is an integrator's guide to the OGNL 2.7 bytecode enhancement API (`Ognl.compileExpression`,
`OgnlExpressionCompiler`, `ExpressionAccessor`, Javassist) written around the Tapestry 4 integration (`HiveMindExpressionCompiler`,
`ExpressionBinding`, a pool of `OgnlContext` objects) and says of itself that it is not meant for general user reference. It
refers to the OpenSymphony JIRA and to a snapshot repository at an address from that time. Struts does not use
that API: a search of the 7.4.0 `struts2-core` classes finds no reference to `compileExpression`, `setCompiler` or
`ExpressionAccessor`, and `OgnlUtil.compile(String)` only parses the expression (through the OGNL Guard), checks that it is
not an eval chain and returns the parsed tree, caching it like every other expression. "Compilation" in a Struts context
therefore means "parsing and caching the tree", and the page matters to Struts users only if they write their own OGNL
integration, in which case they should read the OGNL project's current documentation instead.

[#worked-example]
== Worked Example: One Request to the Shelf, Step by Step

The request `GET /g9valuestack/shelf?filter=sci` touches every concept above. Reading it in order shows who creates and
fills which half.

[cols="1,4,4",options="header"]
|===
|Step |What happens |State afterwards

|1 |The filter and the dispatcher create the `ActionContext` and the `OgnlValueStack`; the stack gets the `DefaultTextProvider` |Stack `[DefaultTextProvider]`, context map with `parameters`, `request`, `session`, `application`, `attr`
|2 |The action is created and pushed |Stack `[ShelfAction, DefaultTextProvider]`; `+#action+` and `top` are the action
|3 |The `params` interceptor reads the parameter `filter=sci` and calls `+ValueStack.setParameter("filter", ...)+`; the `@StrutsParameter` on `setFilter` lets the value through |`ShelfAction.filter` is `sci`; `+#parameters.filter+` is `sci` too
|4 |`execute()` runs: it writes `user` into `ActionContext.getContext().getSession()` and `requestId` into the request |`+#session.user+` is `alice`, `+#request.requestId+` is `42`
|5 |The result forwards to `shelf.jsp`, which evaluates its expressions: bare names search the stack, `+#+` names read the context map, `+${...}+` goes through the request wrapper |The lines A1 to A33 of the page
|6 |The response is written, the stack and the context are dropped, the thread-local context is cleared |No state is shared with the next request
|===

Source: https://struts.apache.org/tag-developers/ognl.html#context[Tag Developer Guide -- OGNL, Context]

The same page also explains the odd lines of the output. `A26` printed `Neuromancer|sci|Neuromancer (1984)|sci|size=3`
because inside `s:push value="books[1]"` the stack had the `Book` on top: the first `+title+` found the book, `+filter+` fell
through to the action, `+[0].top.label+` was the book, `+[1].top.filter+` the action's property and the stack had three elements.
`A27` created a variable with `s:set` and printed it three ways, `+#n+`, `+#attr.n+` and `+${n}+`, all `3`: the variable lives in the
context and in the request attributes. And `A25` printed the value `Dune (1965)` for `+findString("books[0].label")+` from Java:
the same expressions are available to Java code through the stack.

[#inconsistencies]
== Inconsistencies in the Official Documentation

* The OGNL Basics page tells to set `struts.ognl.allowStaticMethodAccess` to `true` to use `@class@method()`. On 7.4.0 the
  constant does not exist in `StrutsConstants` and static methods stay blocked with it set (observed); the 2.5 to 6.0
  migration guide lists the same constant as a renamed one and, a few lines below, says static methods are not accessible
  any more.
* The Tag Syntax page lists `parameters`, `application`, `session`, `struts`, `request`, `servletRequest` and
  `servletResponse` as disallowed property names. On 7.4.0 an action property `getSession()` returning a string was read
  by `<s:property value="session"/>` as `ACTION-session` (observed), so as far as reading is concerned the list does not
  match the behaviour.
* The cache configuration page documents `struts.ognl.expressionCacheLRUMode` and `struts.ognl.beanInfoCacheLRUMode`; 7.4.0
  has `struts.ognl.expressionCacheType` and `beanInfoCacheType` instead and no LRU-mode constant.
* The OGNL Expression Compilation page describes the OGNL 2.7 bytecode compiler through a Tapestry 4 integration; Struts
  does not use that API (see the cache section).
* The page "Accessing application, session, request objects" sets an attribute with `application.set("myKey", "myValue")`
  on a `Map` (the method is `put`), refers to `javax.servlet.jsp.PageContext` (the package is `jakarta` since Struts 7),
  and ends with a sentence about `+#+` without a name that reads as inverted.
* The "Access to ValueStack from JSPs" page shows code against `com.opensymphony.xwork.ActionContext` and a
  `wwel.tld`; neither exists in a current Struts.
* The same `struts.ognl.expressionMaxLength` is `256` in `default.properties` and the Security Guide, `150` in the 6 to 7
  migration guide (known inconsistency; 256 is the verified value).
* The Core Developer Guide has no page of its own for the value stack or the action context (the URLs
  `core-developers/value-stack.html` and `core-developers/action-context.html` return 404); the reference is the Javadoc of
  `ValueStack` and `ActionContext` and the OGNL pages of the Tag Developer Guide.

[#summary]
== Summary

* The `ActionContext` is a thread-local map with everything of the request; the `ValueStack` is a stack of objects held in
  it as the OGNL root, with the action on it and, depending on the page, a model, an iterated element, a pushed object or a
  set map.
* A plain name searches the stack from the top; `+[n]+` cuts the stack; `+top+` is the top; `+#name+` reads the context map
  (`+#session+`, `+#request+`, `+#application+`, `+#parameters+`, `+#attr+`, `+#action+` and your variables); `+%{...}+` forces evaluation in
  a `String` attribute; `+${...}+` is JSP EL and cannot go in a Struts tag attribute.
* OGNL gives properties, indexes, projection `+{x}+`, selection `+{? ...}+`, `+{^ ...}+`, `+{$ ...}+`, literal lists and maps,
  `in` and `not in`, operators and instance methods; Struts 7.4.0 lets through only what the allowlist, the exclusion lists
  and the static rules permit, and refuses silently with a WARN line in the log.
* Keep expression text under your control: request data goes into values, never into expression text, `getText` keys or
  evaluated defaults.
* Use the property forms of collections, expose constants as getters, allowlist your model packages, and turn off the
  context fallback and the stack lookup from EL when the application does not need them.
