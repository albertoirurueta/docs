[#what-mvc-means]
== What MVC Means on the Servlet Platform

Model-View-Controller splits a web application along three responsibilities: the *model* holds the data and the rules of
the application, the *view* renders it, and the *controller* turns an HTTP request into calls on the model and picks the
view. On the servlet platform the three roles map onto concrete things, and the rest of this page is about keeping each
role in its own place.

.The MVC roles in a servlet and JSP application
[cols="1,3,3",options="header"]
|===
|Role |Implemented by |In the Bookshelf

|Controller |A servlet (or a servlet filter), plus small command classes it delegates to |`FrontController` mapped to `+/app/*+`, `Commands`
|Model: request data |Request attributes, and session attributes for what must survive a redirect |`page`, `book`, `form`, `errors`, `flash`
|Model: business logic and data |Plain Java classes with no servlet types: services and repositories |`BookService`, `BookRepository`, `JdbcBookRepository`
|View |A JSP page with EL and JSTL, composed with tag files, stored under `WEB-INF` |`books.jsp`, `book.jsp`, `book-form.jsp`, `page.tag`
|===

Source: https://jakartaee.github.io/jakartaee-documentation/jakartaee-tutorial/current/web/servlets/servlets.html#_sharing_information[Jakarta EE Tutorial -- Sharing Information]

The word "model" is used for two different things, which is a common source of confusion in the literature. In the
narrow sense used by view technologies, the model is the data the controller hands to the view for one request (in the
servlet API: request attributes). In the wider sense used by architecture books, the model is the whole business tier.
This page keeps both, and says which one it means.

[#model1]
== Model 1: The Page Does Everything

In a Model 1 (page-centric) application the browser requests a JSP directly, and that JSP receives the request, reads the
parameters, calls the data layer, makes the decisions and writes the HTML. It is the architecture of the first JSP
tutorials, and for a one-page tool it is still the shortest path. The _Bookshelf_ catalogue as a Model 1 page is a
single file that fetches the service from the application scope and loops over the result with a scriptlet.

.A Model 1 page: model1/books.jsp (a "before" snippet, deliberately using scriptlets)
[source,jsp]
----
<%@ page contentType="text/html;charset=UTF-8" import="java.util.*, org.example.bookshelf.model.*, org.example.bookshelf.service.*" %>
<%
    BookService books = (BookService) application.getAttribute("bookService");
    String q = request.getParameter("q") == null ? "" : request.getParameter("q");
    Page<Book> result = books.search(q, request.getParameter("sort"), 1);
%>
<html><body>
<h1>Catalogue (Model 1)</h1>
<ul>
<% for (Book b : result.items()) { %>
  <li><%= b.title() %> by <%= b.author() %></li>
<% } %>
</ul>
</body></html>
----

Source: https://jakarta.ee/specifications/pages/4.0/jakarta-server-pages-spec-4.0.html#_Scripting_Elements[Jakarta Pages 4.0 -- Scripting Elements]

Requesting `/g7mvc/model1/books.jsp` returned the first page of the catalogue, five `+<li>+` items sorted by title (the
output of the loop above is `+<li>Dune by Frank Herbert</li>+` and so on). It works, and everything the architecture
literature says about it is visible in the file: the page imports the model packages, knows how to read parameters,
knows the paging convention (`1` is hard-coded) and mixes Java statements with markup, so changing the catalogue means
editing a page that a designer also edits. Page-centric designs come in a few recurring shapes, and all of them have the
same limit.

.Page-centric designs and what each one costs
[cols="2,3,3",options="header"]
|===
|Shape |How it works |Limit

|Role-based pages |One page per role or use case, each with its own logic (`books.jsp`, `admin-books.jsp`) |The same query and the same rules are copied from page to page
|Action target |A form posts to a JSP that processes the request and redirects (see the next listing) |The page has no HTML of its own, only logic; it is a servlet written in the wrong file type
|Composite page |A page assembles others with `jsp:include`, each reading the request |No central place to authenticate, log or choose the next page; every fragment repeats its own checks
|Beans on the page |`jsp:useBean` and `jsp:setProperty` move parameters into a bean, the page then calls the bean |Better than raw scriptlets, still no separation between request handling and display
|===

The action-target shape is the one that shows the limit most clearly. This page binds the form fields to a bean with
`+jsp:setProperty property="*"+`, calls the service and redirects, and it renders HTML only when the request is not a POST.

.A Model 1 action target: model1/add.jsp, plus the bean it binds to (also a "before" snippet)
[source,jsp]

<% request.setCharacterEncoding("UTF-8"); %>
<jsp:useBean id="form" class="org.example.bookshelf.web.BookForm" scope="request"/>
<jsp:setProperty name="form" property="*"/>
<%

        BookService books = (BookService) application.getAttribute("bookService");
        books.create(form.getTitle(), form.getAuthor(), form.getYear());
        response.sendRedirect(request.getContextPath() + "/model1/books.jsp");
        return;
    }
%>
<html><body>
<form method="post" action="add.jsp">
  <input name="title"> <input name="author"> <input name="year"> <button>Save</button>
</form>
</body></html>

    private String author = "";

A `GET` of `/g7mvc/model1/add.jsp` returned the form, and a `POST` of `title=Model1 Book&author=Z&year=1999` returned
`302` with `Location: /g7mvc/model1/books.jsp` and created the book. The page also shows two traps of the style. The
`return;` after `sendRedirect` must stop the generated `_jspService` method, and it must be the last statement of its
block: a first version that closed the `if` in a second scriptlet, so that template text came after the `return;`, failed
to compile with `Unreachable code` at the line of the scriptlet (observed; the same error appeared when the `return;` was
placed inside a `c:if` body). And `+property="*"+` binds every request parameter that matches a property of the bean, so
adding a property to the bean later silently makes a new parameter writable by anyone.

Source: https://jakarta.ee/specifications/pages/4.0/jakarta-server-pages-spec-4.0.html#jsp:setProperty[Jakarta Pages 4.0 -- jsp:setProperty]

Source: https://jakarta.ee/specifications/pages/4.0/jakarta-server-pages-spec-4.0.html#jsp:useBean[Jakarta Pages 4.0 -- jsp:useBean]

Model 1 is not wrong for everything. A status page, an internal report or a prototype with one reader needs no
controller. It stops being a good fit when a second page needs the same logic, when the next page depends on the outcome
of the request, or when something must run for every request (authentication, encoding, a CSRF check). Those are exactly
the three jobs a controller is for.

[#model2]
== Model 2: A Servlet Controls, a JSP Displays

In Model 2 (servlet-centric) the browser never requests a JSP. It requests a servlet; the servlet handles the request,
asks the model for data, stores the results as request attributes and *forwards* to a JSP that renders them. The
servlet decides; the JSP only displays. The diagram shows the request that the finished _Bookshelf_ handles for
`GET /g7mvc/app/books?sort=year`.

.The steps of a Model 2 request
[cols="1,5",options="header"]
|===
|Step |What happens

|1-2 |The container maps the URL to the servlet with the longest matching prefix (`+/app/*+`) and calls `service`
|3 |The controller picks the command from the HTTP method and the path info, and prepares the parts every view needs (the base URL, the form token, the one-shot flash message)
|4-6 |The command calls the service, which calls the repository; the controller never touches JDBC, the repository never touches the request
|7-8 |The result is stored with `setAttribute`: this is the model of the view
|9 |`RequestDispatcher.forward` hands the same request and response objects to the JSP, which is invisible to the browser
|10 |The JSP is compiled once and then run as a servlet; EL reads the attributes, JSTL loops and escapes, and the HTML goes out
|===

Source: https://jakarta.ee/specifications/servlet/6.1/jakarta-servlet-spec-6.1.html#the-forward-method[Jakarta Servlet 6.1 -- 9.4 The Forward Method]

Source: https://docs.oracle.com/javaee/5/tutorial/doc/bnagi.html#bnagk[The Java EE 5 Tutorial -- Transferring Control to Another Web Component (archived, `javax` era)]

Three properties make Model 2 worth the extra classes. The URL space belongs to the controller, so `/app/books/12` can
stay stable while the JSP behind it is renamed. Every cross-cutting concern has one place to live (the controller or a
filter in front of it). And the view can be tested by giving it a model, without a database and without a browser.

[#choosing]
== Choosing an Architecture

The decision is not "Model 1 or Model 2" for a new project; it is how much of Model 2 you write yourself.

.Architectures for a server-rendered Java web application
[cols="2,3,3",options="header"]
|===
|Architecture |Choose it when |Cost

|Model 1, JSP pages with beans |A single internal page, a prototype, a learning exercise |Logic in views; does not scale to many pages or teams
|Hand-written Model 2 (this page) |A small application, a learning goal, or a library that must not depend on a framework; a handful of routes |You write routing, binding, validation and the error mapping that frameworks give you
|Spring MVC with JSP views |A Spring application that keeps JSPs; see the comparison below |JSP in an executable Spring Boot jar is not supported (the Boot reference says so); a WAR is needed
|Struts 2 with JSP views |An existing Struts application, or a team that wants action-based MVC with interceptors; the xref:web/jsp-struts/struts/architecture-and-request-lifecycle.adoc[Struts part] of this section |A framework with its own expression language (OGNL) and a security history to follow
|A template engine such as Thymeleaf |A new server-rendered Spring application; see the xref:web/thymeleaf/introduction-and-architecture.adoc[Thymeleaf section] |Another template language, but natural HTML templates and no scriptlets
|A single-page application plus JSON |A rich client, mobile clients sharing the API |A second codebase, and CORS, tokens and SEO to solve
|===

Source: https://docs.spring.io/spring-boot/reference/web/servlet.html#web.servlet.embedded-container.jsp-limitations[Spring Boot -- JSP Limitations]

The Java EE 5 tutorial, an early official source for this material, teaches the mechanism that Model 2 rests on (a servlet
that "transfers control to another web component", through a `RequestDispatcher`) in its chapter on servlet technology, and
the current Jakarta EE tutorial keeps the same section. The pattern has outlived the vocabulary: Struts 1 and 2, Spring
MVC and most Java web frameworks are Model 2 with a more elaborate controller.

[#front-controller]
== The Front Controller

A front controller is one servlet that receives every request of a part of the URL space and decides what to do with it.
Tomcat selects it by the prefix mapping `+/app/*+`, so `/g7mvc/app/books/12` reaches `service` with
`getServletPath()` equal to `/app` and `getPathInfo()` equal to `/books/12`. The servlet owns a small route table (an
HTTP method, a regular expression for the path info, a command), and its `service` method does the same seven things for
every request: sets the request encoding, finds the route, checks the form token for a `POST`, prepares the shared part
of the model, runs the command, dispatches on the result, and turns an `AppException` into an HTTP status.

.FrontController.java
[source,java]
----
@WebServlet(name = "front", urlPatterns = "/app/*")
public class FrontController extends HttpServlet {
    private record Route(String method, Pattern pattern, Command command) {
    }

    private final List<Route> routes = new ArrayList<>();
    private BookService books;

    @Override
    public void init() {
        books = (BookService) getServletContext().getAttribute("bookService");
        routes.add(new Route("GET", Pattern.compile("/books"), Commands::list));
        routes.add(new Route("GET", Pattern.compile("/books/new"), Commands::newForm));
        routes.add(new Route("POST", Pattern.compile("/books"), Commands::create));
        routes.add(new Route("GET", Pattern.compile("/books/(\\d+)"), Commands::show));
        routes.add(new Route("POST", Pattern.compile("/books/(\\d+)/delete"), Commands::delete));
        routes.add(new Route("POST", Pattern.compile("/books/(\\d+)/loan"), Commands::lend));
    }

    @Override
    protected void service(HttpServletRequest req, HttpServletResponse resp) throws ServletException, IOException {
        req.setCharacterEncoding("UTF-8");
        String path = req.getPathInfo() == null ? "/" : req.getPathInfo();
        if (path.equals("/")) {
            resp.sendRedirect(req.getContextPath() + req.getServletPath() + "/books", HttpServletResponse.SC_SEE_OTHER);
            return;
        }
        try {
            boolean pathKnown = false;
            for (Route route : routes) {
                Matcher m = route.pattern().matcher(path);
                if (!m.matches()) {
                    continue;
                }
                pathKnown = true;
                if (!route.method().equals(req.getMethod())) {
                    continue;
                }
                if (route.method().equals("POST")) {
                    Csrf.check(req);
                }
                List<String> params = new ArrayList<>();
                for (int i = 1; i <= m.groupCount(); i++) {
                    params.add(m.group(i));
                }
                prepareModel(req);
                dispatch(route.command().execute(new Context(req, resp, params, books)), req, resp);
                return;
            }
            if (pathKnown) {
                resp.setHeader("Allow", "GET, POST");
                throw new AppException(HttpServletResponse.SC_METHOD_NOT_ALLOWED, "Method not allowed");
            }
            throw new AppException(HttpServletResponse.SC_NOT_FOUND, "No route for " + path);
        } catch (AppException e) {
            resp.sendError(e.status(), e.getMessage());
        } catch (Exception e) {
            throw new ServletException(e);
        }
    }

    private void prepareModel(HttpServletRequest req) {
        req.setAttribute("base", req.getContextPath() + req.getServletPath());
        req.setAttribute("csrf", Csrf.tokenFor(req));
        Object flash = req.getSession().getAttribute("flash");
        if (flash != null) {
            req.getSession().removeAttribute("flash");
            req.setAttribute("flash", flash);
        }
    }

    private void dispatch(Result result, HttpServletRequest req, HttpServletResponse resp)
            throws ServletException, IOException {
        switch (result) {
            case Result.View v -> req.getRequestDispatcher("/WEB-INF/views/" + v.name() + ".jsp").forward(req, resp);
            case Result.Redirect r -> resp.sendRedirect(req.getContextPath() + req.getServletPath() + r.path(),
                    HttpServletResponse.SC_SEE_OTHER);
            case Result.Done d -> {
            }
        }
    }
}
----

Source: https://jakarta.ee/specifications/servlet/6.1/apidocs/jakarta.servlet/jakarta/servlet/annotation/WebServlet.html[Jakarta Servlet 6.1 Javadoc -- WebServlet]

Source: https://jakarta.ee/specifications/servlet/6.1/jakarta-servlet-spec-6.1.html#specification-of-mappings[Jakarta Servlet 6.1 -- 12.2 Specification of Mappings]

A few details of this class matter more than they look.

* *The servlet is shared by every thread.* There is one instance, so `routes` and `books` are written once in `init` and
  only read afterwards, and all per-request data lives in local variables and request attributes. Putting a field such
  as `currentBook` in the servlet (or in a command object that the route table keeps) is the classic bug of the style:
  two concurrent requests overwrite each other. Struts 1 `Action` classes were shared singletons too, which is why the
  same rule applied to them.
* *Overriding `service`, not `doGet` and `doPost`,* is a design choice: the controller routes on both the method and
  the path, and a method that no route accepts must answer `405` with an `Allow` header chosen by the controller; with
  separate `doGet` and `doPost` methods the routing by path would have to be repeated in each.
* *A known path with the wrong method* gives `405`, an unknown path `404`. Both go through `sendError`, so the error
  pages of the descriptor render them.
* *`req.setCharacterEncoding("UTF-8")` is the first statement.* The request encoding must be set before the first
  parameter is read; in a real application a filter or the descriptor's `+<request-character-encoding>+` does it for every
  servlet (see the servlet fundamentals page).
* *`pathKnown`* is the whole difference between 404 and 405, and it is one boolean.

The same pattern can be implemented with a servlet filter (Struts 2 does it with `StrutsPrepareAndExecuteFilter`), with
extension mappings such as `+*.do+` (Struts 1 and early frameworks), or with a root mapping `/` that also receives static
files. A prefix mapping keeps the controller away from static resources and makes the URL space explicit.

[#command-pattern]
== The Command Pattern: Context, Result and Commands

The route table points at `Command` objects. A command is one method that receives what it needs and returns where to go
next; it neither forwards nor redirects by itself. Returning a value instead of acting makes commands easy to unit test
(no mock dispatcher is needed) and gives the controller the single place where the response is dispatched.

.Command.java, Context.java and Result.java
[source,java]
----
@FunctionalInterface
public interface Command {
    Result execute(Context ctx) throws Exception;
}

public record Context(HttpServletRequest request, HttpServletResponse response,
                      List<String> pathParams, BookService books) {
    public long idParam() {
        try {
            return Long.parseLong(pathParams.get(0));
        } catch (NumberFormatException e) {
            throw new org.example.bookshelf.service.AppException(404, "Not a valid id");
        }
    }
}

public sealed interface Result {
    /** Forward to /WEB-INF/views/{name}.jsp. */
    record View(String name) implements Result {
    }

    /** Send 303 See Other to a path inside the application's front-controller space. */
    record Redirect(String path) implements Result {
    }

    /** The command already wrote the response. */
    record Done() implements Result {
    }
}
----

Source: https://jakarta.ee/specifications/servlet/6.1/apidocs/jakarta.servlet/jakarta/servlet/RequestDispatcher.html[Jakarta Servlet 6.1 Javadoc -- RequestDispatcher]

`Result` is a sealed interface with three cases, and the `switch` in `dispatch` is exhaustive, so adding a fourth case
(say, a JSON body) fails to compile until the controller handles it. `Context` is a record that bundles the request, the
response, the path variables captured by the route's regular expression and the service.

The six commands implement the _Bookshelf_ catalogue. Reading `Commands.java` is the quickest way to see what each URL
does.

.Commands.java
[source,java]
----
final class Commands {
    private Commands() {
    }

    static Result list(Context ctx) throws Exception {
        HttpServletRequest req = ctx.request();
        String q = req.getParameter("q") == null ? "" : req.getParameter("q");
        String sort = req.getParameter("sort");
        int page = parseInt(req.getParameter("page"), 1);
        Page<Book> result = ctx.books().search(q, sort, page);
        if ("csv".equals(req.getParameter("format"))) {
            ctx.response().setContentType("text/csv");
            ctx.response().setCharacterEncoding("UTF-8");
            PrintWriter out = ctx.response().getWriter();
            out.println("id,title,author,year");
            for (Book b : result.items()) {
                out.printf("%d,\"%s\",\"%s\",%d%n", b.id(), b.title().replace("\"", "\"\""),
                        b.author().replace("\"", "\"\""), b.year());
            }
            return new Result.Done();
        }
        req.setAttribute("page", result);
        req.setAttribute("q", q);
        req.setAttribute("sort", sort == null ? "title" : sort);
        return new Result.View("books");
    }

    static Result show(Context ctx) {
        ctx.request().setAttribute("book", ctx.books().get(ctx.idParam()));
        return new Result.View("book");
    }

    static Result newForm(Context ctx) {
        ctx.request().setAttribute("form", Map.of("title", "", "author", "", "year", ""));
        return new Result.View("book-form");
    }

    static Result create(Context ctx) {
        HttpServletRequest req = ctx.request();
        Map<String, String> form = new LinkedHashMap<>();
        form.put("title", trim(req.getParameter("title")));
        form.put("author", trim(req.getParameter("author")));
        form.put("year", trim(req.getParameter("year")));
        Map<String, String> errors = new LinkedHashMap<>();
        if (form.get("title").isEmpty()) {
            errors.put("title", "Title is required");
        }
        if (form.get("author").isEmpty()) {
            errors.put("author", "Author is required");
        }
        int year = parseInt(form.get("year"), -1);
        if (year < 1450 || year > 2100) {
            errors.put("year", "Year must be a number between 1450 and 2100");
        }
        if (!errors.isEmpty()) {
            ctx.response().setStatus(422);
            req.setAttribute("form", form);
            req.setAttribute("errors", errors);
            return new Result.View("book-form");
        }
        Book book = ctx.books().create(form.get("title"), form.get("author"), year);
        req.getSession().setAttribute("flash", "Saved \"" + book.title() + "\"");
        return new Result.Redirect("/books/" + book.id());
    }

    static Result delete(Context ctx) {
        ctx.books().delete(ctx.idParam());
        ctx.request().getSession().setAttribute("flash", "Book deleted");
        return new Result.Redirect("/books");
    }

    static Result lend(Context ctx) {
        long id = ctx.idParam();
        ctx.books().lend(id, trim(ctx.request().getParameter("borrower")).isEmpty()
                ? "anonymous" : trim(ctx.request().getParameter("borrower")));
        ctx.request().getSession().setAttribute("flash", "Book lent");
        return new Result.Redirect("/books/" + id);
    }

    private static String trim(String s) {
        return s == null ? "" : s.strip();
    }

    private static int parseInt(String s, int fallback) {
        try {
            return Integer.parseInt(s);
        } catch (NumberFormatException e) {
            return fallback;
        }
    }
}
----

[cols="1,2,3",options="header"]
|===
|Method |Path info |Command and outcome

The commands are method references (`Commands::list`), so the route table is the only place that connects a
URL to behaviour. A larger application would load it from annotations or configuration, which is what Struts does with
`struts.xml` and Spring MVC with `@RequestMapping`.

[#model-attributes]
== The Model: Request Attributes

The controller communicates with the view through attributes of the request. The command sets `page`, `q` and `sort`; the
JSP reads them with EL as `+${page.items}+`, `+${q}+` and `+${sort}+`. Because `forward` passes the very same request object
to the JSP, the attributes are there when the view runs, and they disappear when the request ends, which is the correct
lifetime for data that describes one response.

.Where to put model data
[cols="2,3,3",options="header"]
|===
|Scope |Use it for |Bookshelf example

|Request |Everything that describes this response: the result page, the book, the form values, the error messages |`page`, `book`, `form`, `errors`
|Session |Data that must survive a redirect or follow the user: the form token, the one-shot flash message, a login |`csrf`, `flash`
|Application |Read-mostly objects created at startup and shared: services, configuration, caches |`bookService`
|Page |Temporary variables of one JSP (`c:set`, loop variables) |`b` in the `c:forEach`
|===

Source: https://jakarta.ee/specifications/servlet/6.1/jakarta-servlet-spec-6.1.html#attributes[Jakarta Servlet 6.1 -- 3.3 Attributes]

The model of a view is easier to reason about when it is small and read-only. Two Bookshelf choices come from that: the
view receives a `Page` record (a slice of the catalogue plus the paging arithmetic) instead of a result set, and `Book`
is an immutable record. One consequence of using records in a view is worth knowing before it costs an afternoon.

.Book.java and Page.java
[source,java]
----
public record Book(long id, String title, String author, int year, boolean available) {
}

public record Page<T>(List<T> items, int page, int size, long total) {
    public int pages() {
        return (int) Math.max(1, Math.ceil(total / (double) size));
    }

    public boolean hasPrevious() {
        return page > 1;
    }

    public boolean hasNext() {
        return page < pages();
    }
}
----

Expression Language 6.0 resolves properties of a record with `jakarta.el.RecordELResolver`, which calls the accessor with
the *component name*, so `+${page.items}+`, `+${b.title}+` and `+${page.total}+` work with no `get` prefix. It does not fall
back to JavaBean getters for names that are not components: an earlier version of this class declared `getPages()` and
`isHasPrevious()`, and the page failed with a `JasperException` ("An exception occurred processing
[/WEB-INF/views/books.jsp]") whose root cause was `java.lang.NoSuchMethodException: org.example.bookshelf.model.Page.pages()`
(observed on Tomcat 11.0.26). The derived values are therefore declared as methods with the names the EL uses
(`pages()`, `hasPrevious()`, `hasNext()`), and `+${page.hasPrevious}+` calls `hasPrevious()`. The rule of thumb: for a
record, name the accessors exactly like the property you want to write in the EL; for a class, use JavaBean getters.
The xref:web/jsp-struts/jsp/el-static-access-records-and-optional.adoc[records page] has the full resolver chain.

Source: https://jakarta.ee/specifications/expression-language/6.0/apidocs/jakarta.el/jakarta/el/RecordELResolver.html[Jakarta Expression Language 6.0 Javadoc -- RecordELResolver]

[#views]
== Views Under WEB-INF

The views are JSP files under `/WEB-INF/views/`. The servlet specification says that nothing under `WEB-INF` is served
directly to a client, so a browser cannot request `books.jsp` without the controller having prepared the model: the same
request that returns the catalogue through the controller returns `404` for the file.

[source,console]
----
$ curl -s -o /dev/null -w '%{http_code}\n' http://localhost:18080/g7mvc/WEB-INF/views/books.jsp
404
$ curl -s -o /dev/null -w '%{http_code}\n' http://localhost:18080/g7mvc/app/books
200
----

Source: https://jakarta.ee/specifications/servlet/6.1/jakarta-servlet-spec-6.1.html#directory-structure[Jakarta Servlet 6.1 -- 10.5 Directory Structure]

Keeping views private has three consequences. A JSP never runs with a missing model (no `PropertyNotFoundException`
from a direct request), a view cannot be used to bypass a check that the controller makes, and the URL space stays
under the controller's control. The same rule applies to the layout: tag files live in `WEB-INF/tags`, so the
page-wrapping markup is also private. The layout of the catalogue is one tag file.

[#prg]
== Post/Redirect/Get, Flash Messages and the Form Token

A form that is answered with a page is dangerous: the browser's *Reload* repeats the `POST`. Post/Redirect/Get (PRG)
removes the problem: after a successful `POST` the controller answers with a redirect, the browser follows it with a
`GET`, and reloading repeats the harmless `GET`. In the Bookshelf the `create` command ends with this:

[source,java]
----
Book book = ctx.books().create(form.get("title"), form.get("author"), year);
req.getSession().setAttribute("flash", "Saved \"" + book.title() + "\"");
return new Result.Redirect("/books/" + book.id());
----

Source: https://jakarta.ee/specifications/servlet/6.1/apidocs/jakarta.servlet/jakarta/servlet/http/HttpServletResponse.html#sendRedirect(java.lang.String,int)[Jakarta Servlet 6.1 Javadoc -- HttpServletResponse.sendRedirect(String, int)]

and the controller dispatches `Result.Redirect` with `sendRedirect(location, HttpServletResponse.SC_SEE_OTHER)`, the
Servlet 6.1 overload that chooses the status. `303 See Other` is the status defined for exactly this: it tells the client to
retrieve another resource with a `GET`, whatever the method of the original request was. The default `sendRedirect(String)`
answers `302`, which browsers in practice also turn into a `GET` for a `POST`, but which leaves the choice of method to the client.

The run of the same application, with the headers kept:

[source,console]
----
$ curl -s -i -c jar -b jar --data-urlencode "_csrf=$T" \
    -d 'title=The Dispossessed&author=Ursula K. Le Guin&year=1974' http://localhost:18080/g7mvc/app/books
HTTP/1.1 303
Location: /g7mvc/app/books/12
Content-Length: 0
----

[source,console]
----
$ curl -s -i -b jar -c jar http://localhost:18080/g7mvc/app/books/12
HTTP/1.1 200
...
  <title>The Dispossessed - Bookshelf</title>
...
  <p class="flash">Saved &#034;The Dispossessed&#034;</p>
  <h1>The Dispossessed</h1>
  <p>by Ursula K. Le Guin, 1974</p>
  <p>Available</p>
----

A second `GET` of the same URL showed no `flash` paragraph. The message is a *flash attribute*: it is written to the
session by the command that handles the `POST`, and `prepareModel` in the controller moves it into the request (and
removes it from the session) at the start of the next request. The session is the only way for a redirect to carry data,
because a redirect starts a new request and the old request attributes are gone. The title in the message is written
through `c:out`, so a title such as `+Hail <b>Mary</b>+` is stored as typed and rendered as
`+Hail &lt;b&gt;Mary&lt;/b&gt;+` in both the heading and the `title` element (observed).

Source: https://www.rfc-editor.org/rfc/rfc9110#section-15.4.4[RFC 9110 -- 15.4.4 303 See Other]

Source: https://jakarta.ee/specifications/servlet/6.1/apidocs/jakarta.servlet/jakarta/servlet/http/HttpServletResponse.html#sendRedirect(java.lang.String,int)[Jakarta Servlet 6.1 Javadoc -- HttpServletResponse.sendRedirect(String, int)]

Source: https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-controller/ann-methods/flash-attributes.html[Spring Framework -- Flash Attributes]

PRG protects against accidental repetition (reload, back button, a double click that lands after the first response),
not against a deliberate repetition, and it does not protect against a forged request. Two small mechanisms, both owned
by the controller, cover the other two cases.

.Protecting state-changing requests in a front controller
[cols="2,3,3",options="header"]
|===
|Threat |Mechanism |In the Bookshelf

|A page makes the user's browser post to the application (cross-site request forgery) |A random per-session token in a hidden field, compared on every unsafe method; `SameSite` on the session cookie as defence in depth |`Csrf.tokenFor` stores 24 random bytes (Base64URL) in the session; `Csrf.check` compares with `MessageDigest.isEqual`; a missing or wrong token gives `403`
|The user submits the same form twice (double click, slow network) |A one-time token per form that the controller consumes, or a database uniqueness rule |The same `Csrf` token is per session, so a replay with the same token is accepted: two posts of the same body created books 10 and 11 (observed). Consume the token per form to prevent that (forms and sessions page)
|A state change by a link or by `GET` |Make every state change a `POST`, `PUT` or `DELETE`; answer other methods with `405` |`GET /books/9/delete` is `405` with `Allow: GET, POST`
|===

.Csrf.java
[source,java]
----
final class Csrf {
    private static final SecureRandom RANDOM = new SecureRandom();

    private Csrf() {
    }

    static String tokenFor(HttpServletRequest req) {
        HttpSession session = req.getSession();
        String token = (String) session.getAttribute("csrf");
        if (token == null) {
            byte[] bytes = new byte[24];
            RANDOM.nextBytes(bytes);
            token = Base64.getUrlEncoder().withoutPadding().encodeToString(bytes);
            session.setAttribute("csrf", token);
        }
        return token;
    }

    static void check(HttpServletRequest req) {
        String expected = tokenFor(req);
        String actual = req.getParameter("_csrf");
        if (actual == null || !MessageDigest.isEqual(
                expected.getBytes(StandardCharsets.UTF_8), actual.getBytes(StandardCharsets.UTF_8))) {
            throw new AppException(403, "Missing or invalid form token");
        }
    }
}
----

The run confirmed the three behaviours: a `POST` without `_csrf` answered `403` with the message "Missing or invalid form
token"; a `POST` of `/app/books/9` (a path that only accepts `GET`) answered `405` with `Allow: GET, POST`; and a normal
post answered `303`. A real application protects `PUT` and `DELETE` the same way and sends the token in a header for
`fetch` calls.

[#errors]
== Validation, Errors and Status Codes

A front controller is the right place to turn failures into HTTP responses, because it is the only code that sees every
request. The Bookshelf uses three mechanisms, each for a different kind of failure.

.Failure kinds and where they are handled
[cols="2,3,3",options="header"]
|===
|Kind of failure |Handling |Response

|The user typed something invalid (empty title, year `abc`) |The command validates, puts `form` and `errors` in the request and forwards to the form again |`422 Unprocessable Content` and the form with sticky values and messages; no redirect, so the values are not lost
|The request is wrong or not allowed (unknown id, a lent book, a missing token) |The command or controller throws `AppException` with a status; `service` catches it and calls `sendError(status, message)` |The status of the exception, rendered by the `error-page` of the descriptor
|A bug or an outage (SQL error, `NullPointerException`) |`ServletException` thrown from `service`; the container looks up the `java.lang.Throwable` error page |`500` and the generic text of `error.jsp`; the details are only in the log
|===

exposed a real failure of this example: `+getOrDefault(null, ...)+` on an immutable `+Map.of(...)+` throws, and a request
without a `sort` parameter hit it (observed). The service now treats a missing
sort as the default, and the error page no longer prints the message of a server error. The `405` and `422` responses
use the container's own page, because the descriptor maps only `403`, `404` and `Throwable`; map the codes your
application produces.

The xref:web/jsp-struts/jsp/error-handling.adoc[JSP error handling page] covers `isErrorPage`, the error attributes and
the order in which the container picks a page. Bean Validation, the standard way to declare these rules on the model,
and the file upload and session-cart forms belong to the xref:web/jsp-struts/jsp/forms-validation-and-sessions.adoc[Forms, Validation & Sessions] page of this section; the
xref:backend/hibernate/validation-with-hibernate-validator.adoc[Hibernate Validator page] shows the annotations.

[#data-access]
== Data Access in the Service Layer

Model 2 stops being worth anything if the SQL ends up in the controller. The Bookshelf has a service (`BookService`)
that the controller calls and a repository (`BookRepository`, implemented by `JdbcBookRepository`) that the service calls.
Neither class imports a servlet type, so both can be tested without a container, and replacing JDBC with JPA changes one
class.

.BookRepository.java and BookService.java
[source,java]
----
public interface BookRepository {
    List<Book> search(String query, String sortColumn, int limit, int offset) throws SQLException;

    long count(String query) throws SQLException;

    Optional<Book> findById(long id) throws SQLException;

    Book save(String title, String author, int year) throws SQLException;

    boolean delete(long id) throws SQLException;

    void lend(long bookId, String borrower) throws SQLException;
}

public class BookService {
    public static final int PAGE_SIZE = 5;
    private static final Map<String, String> SORTABLE = Map.of(
            "title", "title", "author", "author", "year", "pub_year");

    private final BookRepository repository;

    public BookService(BookRepository repository) {
        this.repository = repository;
    }

    public Page<Book> search(String query, String sort, int page) {
        String column = sort == null ? "title" : SORTABLE.getOrDefault(sort, "title");
        String q = query == null ? "" : query.strip();
        try {
            long total = repository.count(q);
            int safePage = Math.max(1, page);
            return new Page<>(repository.search(q, column, PAGE_SIZE, (safePage - 1) * PAGE_SIZE),
                    safePage, PAGE_SIZE, total);
        } catch (SQLException e) {
            throw new IllegalStateException("Catalogue query failed", e);
        }
    }

    public Book get(long id) {
        try {
            return repository.findById(id).orElseThrow(() -> new BookNotFoundException(id));
        } catch (SQLException e) {
            throw new IllegalStateException("Lookup failed", e);
        }
    }

    public Book create(String title, String author, int year) {
        try {
            return repository.save(title, author, year);
        } catch (SQLException e) {
            throw new IllegalStateException("Save failed", e);
        }
    }

    public void delete(long id) {
        try {
            if (!repository.delete(id)) {
                throw new BookNotFoundException(id);
            }
        } catch (SQLException e) {
            throw new IllegalStateException("Delete failed", e);
        }
    }

    public void lend(long id, String borrower) {
        get(id);
        try {
            repository.lend(id, borrower);
        } catch (SQLException e) {
            throw new IllegalStateException("Loan failed", e);
        }
    }
}
----

The `password=""` and `username="sa"` values are those of the throwaway in-memory H2 database of this example. A real

The `maxTotal` and `maxIdle` attributes of the resource in `context.xml` bound the pool (8 and 2 in this example), so a
connection that is never closed eventually blocks every request. The repository uses `PreparedStatement` for every value, `try-with-resources` for every `Connection`, `Statement` and
`ResultSet`, and a pool, so closing a connection returns it. Paging is a `LIMIT ? OFFSET ?` query plus a `+COUNT(*)+`, and the
sort column is the one thing that cannot be a parameter.

.JdbcBookRepository.java
[source,java]
----
public class JdbcBookRepository implements BookRepository {
    private final DataSource dataSource;

    public JdbcBookRepository(DataSource dataSource) {
        this.dataSource = dataSource;
    }

    @Override
    public List<Book> search(String query, String sortColumn, int limit, int offset) throws SQLException {
        // sortColumn comes from an allow-list in the service, never straight from the request
        String sql = "SELECT id, title, author, pub_year, available FROM book "
                + "WHERE LOWER(title) LIKE ? OR LOWER(author) LIKE ? "
                + "ORDER BY " + sortColumn + ", id LIMIT ? OFFSET ?";
        try (Connection c = dataSource.getConnection(); PreparedStatement ps = c.prepareStatement(sql)) {
            String like = "%" + query.toLowerCase() + "%";
            ps.setString(1, like);
            ps.setString(2, like);
            ps.setInt(3, limit);
            ps.setInt(4, offset);
            try (ResultSet rs = ps.executeQuery()) {
                List<Book> books = new ArrayList<>();
                while (rs.next()) {
                    books.add(map(rs));
                }
                return books;
            }
        }
    }

    @Override
    public long count(String query) throws SQLException {
        String sql = "SELECT COUNT(*) FROM book WHERE LOWER(title) LIKE ? OR LOWER(author) LIKE ?";
        try (Connection c = dataSource.getConnection(); PreparedStatement ps = c.prepareStatement(sql)) {
            String like = "%" + query.toLowerCase() + "%";
            ps.setString(1, like);
            ps.setString(2, like);
            try (ResultSet rs = ps.executeQuery()) {
                rs.next();
                return rs.getLong(1);
            }
        }
    }

    @Override
    public Optional<Book> findById(long id) throws SQLException {
        try (Connection c = dataSource.getConnection();
             PreparedStatement ps = c.prepareStatement(
                     "SELECT id, title, author, pub_year, available FROM book WHERE id = ?")) {
            ps.setLong(1, id);
            try (ResultSet rs = ps.executeQuery()) {
                return rs.next() ? Optional.of(map(rs)) : Optional.empty();
            }
        }
    }

    @Override
    public Book save(String title, String author, int year) throws SQLException {
        try (Connection c = dataSource.getConnection();
             PreparedStatement ps = c.prepareStatement(
                     "INSERT INTO book (title, author, pub_year, available) VALUES (?, ?, ?, TRUE)",
                     Statement.RETURN_GENERATED_KEYS)) {
            ps.setString(1, title);
            ps.setString(2, author);
            ps.setInt(3, year);
            ps.executeUpdate();
            try (ResultSet keys = ps.getGeneratedKeys()) {
                keys.next();
                return new Book(keys.getLong(1), title, author, year, true);
            }
        }
    }

    @Override
    public boolean delete(long id) throws SQLException {
        try (Connection c = dataSource.getConnection();
             PreparedStatement ps = c.prepareStatement("DELETE FROM book WHERE id = ?")) {
            ps.setLong(1, id);
            return ps.executeUpdate() == 1;
        }
    }

    @Override
    public void lend(long bookId, String borrower) throws SQLException {
        // two statements, one transaction: either the book is marked as lent and the loan exists, or neither
        try (Connection c = dataSource.getConnection()) {
            c.setAutoCommit(false);
            try (PreparedStatement update = c.prepareStatement(
                         "UPDATE book SET available = FALSE WHERE id = ? AND available = TRUE");
                 PreparedStatement insert = c.prepareStatement(
                         "INSERT INTO loan (book_id, borrower) VALUES (?, ?)")) {
                update.setLong(1, bookId);
                if (update.executeUpdate() != 1) {
                    throw new AppException(409, "Book " + bookId + " is not available");
                }
                insert.setLong(1, bookId);
                insert.setString(2, borrower);
                insert.executeUpdate();
                c.commit();
            } catch (SQLException | RuntimeException e) {
                c.rollback();
                throw e;
            }
        }
    }

    private static Book map(ResultSet rs) throws SQLException {
        return new Book(rs.getLong("id"), rs.getString("title"), rs.getString("author"),
                rs.getInt("pub_year"), rs.getBoolean("available"));
    }
}

.Data access decisions in this repository
[cols="2,4",options="header"]
|===
|Decision |Reason

|`ORDER BY` built from an allow-list (`SORTABLE` in `BookService`), never from the raw parameter |An identifier cannot be bound. A request with `sort=title;DROP TABLE book` and `+q=' OR 1=1--+` returned `200` and the normal catalogue (observed): the unknown sort fell back to `title`, and the query text was bound as a value
|`LIKE ?` with the pattern built in Java |The value is always a parameter; wildcards typed by the user (`%`, `_`) still act as wildcards, which is acceptable for a search box and should be escaped for an exact match
|Paging with `LIMIT` and `OFFSET`, a minimum page of 1 |`page=abc` and `page=-4` both returned `200` (the parse falls back to 1); a huge offset is slow on a large table, where keyset paging (`WHERE id > ?`) is the usual remedy
|Row mapping to records in the repository |The view never sees a `ResultSet`; closing is the repository's job. A `CachedRowSet` (`javax.sql.rowset`) is a disconnected result set, but a list of records is simpler and serializable
|One transaction for lending (`setAutoCommit(false)`, `commit`, `rollback`) |Marking the book as lent and inserting the loan must succeed or fail together. The second `POST` to the same loan returned `409`, because the conditional `UPDATE` matched no row
|The `DataSource` is looked up once and the service is stored in the application scope |A JNDI lookup per request is slow, and the service has no per-user state, so it is safe to share between threads
|===

The two statements of `lend` are the textbook case for a transaction. The `+UPDATE ... WHERE available = TRUE+` is also the
concurrency control: two users lending the same book at the same moment cannot both succeed, because only one update
finds `available = TRUE`. The same optimistic idea with versions is what JPA's `@Version` automates.

*JSTL's SQL tags are not an answer.* `sql:query` and `sql:update` run SQL inside the JSP, which puts the data tier back
into the view. The xref:web/jsp-struts/jsp/jstl-sql-and-xml.adoc[SQL and XML tags page] documents them and explains why this page
does not use them (the Jakarta EE Tutorial itself notes that a subset of Jakarta Tags has been archived in favour of
Jakarta XML Binding, Jakarta Faces and Jakarta Persistence). The
literature of the JSP 1.2 era (and the JSTL 1.0 case studies, with a message board, an RSS reader and a survey) used them
because there was no alternative in a page-centric design; with a controller, database and feed access belong in the
service, and the view renders whatever list the controller supplies. The same is true for an RSS or XML feed: fetching
and parsing it in a JSP (`c:import` and `x:parse`) ties the response time of the page to a remote server, while fetching
in a service allows caching, timeouts and error handling.

For anything more than a handful of queries, replace the repository with JPA. The Hibernate section of this
documentation covers the mapping and the session in depth: the
xref:backend/hibernate/getting-started.adoc[getting started page] sets up the dependency, the
xref:backend/hibernate/transactions.adoc[transactions page] explains the transaction boundary that `lend` writes by hand,
and the xref:backend/hibernate/fetching-and-n-plus-1.adoc[fetching and N+1 page] explains why a view that touches a lazy
collection (`+${book.reviews}+` on a detached entity) fails with a `LazyInitializationException` or silently issues one query
per row; the controller or the service must load what the view needs, and the view must not trigger queries. In a Spring
Boot application the xref:backend/hibernate/spring-boot-integration.adoc[integration page] shows the equivalent wiring.

== Several Views of the Same Data

A benefit of keeping the model out of the view is that the same model can have several views. The Bookshelf serves the
catalogue as HTML and, with `format=csv`, as a comma-separated file written by the command itself; it uses the same
`Page` of the same service call, and the controller decides which view to use from a request parameter.

[source,console]
----
$ curl -s -i -b jar "http://localhost:18080/g7mvc/app/books?format=csv&sort=year"
HTTP/1.1 200
Content-Type: text/csv;charset=UTF-8
...
id,title,author,year
4,"Foundation","Isaac Asimov",1951
7,"Solaris","Stanislaw Lem",1961
1,"Dune","Frank Herbert",1965
6,"The Left Hand of Darkness","Ursula K. Le Guin",1969
8,"Ubik","Philip K. Dick",1969

Source: https://jakarta.ee/specifications/servlet/6.1/apidocs/jakarta.servlet/jakarta/servlet/ServletResponse.html#setContentType(java.lang.String)[Jakarta Servlet 6.1 Javadoc -- ServletResponse.setContentType(String)]

The command returns `Result.Done` for this representation, which tells the controller that the response is complete
and must not be dispatched. Three variations of the same idea are common. A second JSP with
`contentType="text/xml"` or `text/plain` renders an XML or text view; the JSP stays under `WEB-INF` and the command
forwards to it. The `Accept` header selects the representation instead of a parameter. And a JSON object, written with
a JSON library, serves the page to a script: that is the beginning of a REST API, which Spring MVC and Struts both
provide as a built-in alternative to a view.

Writing a CSV by hand has two traps. Values that start with `=`, `+`, `-` or `@` are executed as formulas when the file
is opened in a spreadsheet; prefix such cells with an apostrophe or a space for exports that users open in Excel. And a
`+Content-Disposition: attachment; filename="..."+` header should be added when the response is meant to be downloaded
instead of displayed.

[#cross-cutting]
== Cross-Cutting Concerns: Filters in Front of the Controller

Some jobs belong in front of the controller, not in it: setting the character encoding, authenticating, logging, compressing,
rewriting the response. A filter mapped to `+/app/*+` runs before the front controller and after it, for all routes.
Filters, wrappers, dispatcher types and the blocking authentication filter are explained on the
xref:web/jsp-struts/servlet-fundamentals.adoc#filters[servlet fundamentals page]; the Model 2 consequences are these:

* *One entry, one filter chain.* Because every request goes through `+/app/*+`, the filter mapping is a single line, where a
  page-centric application would have to name every JSP.
* *Dispatcher types decide what the filter sees.* A filter with the default mapping runs only for the original `REQUEST`.
  The forward from the controller to the view is a `FORWARD` dispatch, so a response-wrapping filter (compression,
  minification) must also be mapped to `FORWARD`, and an authentication filter must not be, or it would run twice.
* *Login belongs in a filter or in the container.* An authentication filter sees the request before the controller picks
  a command, and can redirect to a login page. The xref:web/jsp-struts/servlet-fundamentals.adoc#blocking-filters[blocking filter example] does exactly this; container-managed
  security with `security-constraint` and a realm is the alternative that the xref:web/jsp-struts/jsp/security.adoc[Security] page of this section covers.
* *The session-bound state is a listener topic.* `HttpSessionListener` and `HttpSessionAttributeListener` observe session
  creation and the attributes the controller sets; they are the right place for audit logging of logins and counters
  of active users.

[#worked-example]
== The Bookshelf End to End: Adding a Book

The pieces above combine in the following run, the complete flow of "add a book" against the finished WAR. A cookie jar
(`jar`) keeps the session between the commands, and `$T` holds the form token that the first response contains (a random
value, different in every session).

.Step 1: the form. The controller reads the session, creates the token and forwards to `book-form.jsp`
[source,console]
----
$ curl -s -c jar -b jar http://localhost:18080/g7mvc/app/books/new | grep -E 'csrf|input name="title"'
    <input type="hidden" name="_csrf" value="...token...">
    <p><label>Title <input name="title" value=""></label>
$ T=...token...
----

Source: https://jakarta.ee/specifications/servlet/6.1/jakarta-servlet-spec-6.1.html#creating-a-session[Jakarta Servlet 6.1 -- 7.2 Creating a Session]

.Step 2: the same `POST` without the token is refused, and nothing is created
[source,console]
----
$ curl -s -o /dev/null -w '%{http_code}\n' -c jar -b jar -d 'title=X&author=Y&year=2000' \
    http://localhost:18080/g7mvc/app/books
403
----

Source: https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html[OWASP -- Cross-Site Request Forgery Prevention Cheat Sheet]

.Step 3: invalid values come back as the form with status 422, sticky values and messages (the fragment is in the errors section)
[source,console]
----
$ curl -s -i -c jar -b jar --data-urlencode "_csrf=$T" -d 'title=&author=Y&year=abc' \
    http://localhost:18080/g7mvc/app/books | head -1
HTTP/1.1 422
----

Source: https://www.rfc-editor.org/rfc/rfc9110#section-15.5.21[RFC 9110 -- 15.5.21 422 Unprocessable Content]

.Step 4: a valid `POST` answers `303`; the browser follows with a `GET`, which shows the flash message once and the escaped title
[source,console]
----
$ curl -s -i -c jar -b jar --data-urlencode "_csrf=$T" \
    --data-urlencode 'title=Hail <b>Mary</b>' -d 'author=Andy Weir&year=2021' \
    http://localhost:18080/g7mvc/app/books | grep -E 'HTTP/|Location'
HTTP/1.1 303
Location: /g7mvc/app/books/11
$ curl -s -b jar -c jar http://localhost:18080/g7mvc/app/books/11 | grep -E '<h1>|flash'
  <p class="flash">Saved &#034;Hail &lt;b&gt;Mary&lt;/b&gt;&#034;</p>
  <h1>Hail &lt;b&gt;Mary&lt;/b&gt;</h1>
----

Source: https://www.rfc-editor.org/rfc/rfc9110#section-15.4.4[RFC 9110 -- 15.4.4 303 See Other]

.Step 5: lending in one transaction, the second loan refused, deletion, and the `404` page afterwards
[source,console]
----
$ curl -s -o /dev/null -w '%{http_code} %{redirect_url}\n' -b jar -c jar --data-urlencode "_csrf=$T" \
    -d 'borrower=ana' http://localhost:18080/g7mvc/app/books/11/loan
303 http://localhost:18080/g7mvc/app/books/11
$ curl -s -o /dev/null -w '%{http_code}\n' -b jar -c jar --data-urlencode "_csrf=$T" \
    -d 'borrower=bob' http://localhost:18080/g7mvc/app/books/11/loan
409
$ curl -s -o /dev/null -w '%{http_code} %{redirect_url}\n' -b jar -c jar --data-urlencode "_csrf=$T" \
    -X POST http://localhost:18080/g7mvc/app/books/11/delete
303 http://localhost:18080/g7mvc/app/books
$ curl -s -b jar http://localhost:18080/g7mvc/app/books/11 | grep -E '<h1>|<p>'
  <h1>Error 404</h1>
      <p>No book with id 11</p>
----

Source: https://docs.oracle.com/en/java/javase/21/docs/api/java.sql/java/sql/Connection.html#setAutoCommit(boolean)[Java SE 21 -- Connection.setAutoCommit]

The sequence of statuses (`403`, `422`, `303`, `200`, `303`, `409`, `303`, `404`) is the architecture in one column: the
controller makes every decision, and every response is either a redirect, a rendered view or an error page. The id
(11) is the one of that run.

Source: https://jakarta.ee/specifications/servlet/6.1/jakarta-servlet-spec-6.1.html#using-a-request-dispatcher[Jakarta Servlet 6.1 -- 9.2 Using a Request Dispatcher]

[#pitfalls]
== Pitfalls and Error Names

.Model 2 pitfalls, their symptoms and fixes (rows marked "observed" were reproduced on Tomcat 11.0.26)
[cols="3,3,3",options="header"]
|===
|Symptom or error |Cause |Fix

|Two users see each other's data |State kept in a field of the front controller or of a command that the route table holds; one instance serves all threads |Keep per-request data in local variables and request attributes; make shared objects immutable (the route list is written only in `init`)
|`JasperException` with `+NoSuchMethodException: ...Page.pages()+` (observed) |A JavaBean getter (`getPages()`) was used on a record, and `RecordELResolver` looks only for the component-named accessor |Name the accessor like the property used in the EL (`pages()`), or use a class with getters
|`NullPointerException` for a missing request parameter (observed with `+Map.of(...).getOrDefault(null, ...)+`) |`getParameter` returns `null` when the parameter is absent, and immutable collections reject a `null` key |Test for `null` at the boundary of the controller; give parameters defaults
|Page opens with `PropertyNotFoundException` or an empty model |The JSP was requested without going through the controller |Put the views under `WEB-INF`; the direct request returns `404` (observed)
|Reload repeats the `POST` and creates a duplicate |The response to the `POST` was a rendered page |Post/Redirect/Get with `303`
|The same form posted twice still creates two rows (observed) |The session-wide token is not consumed |A per-form token removed on first use, or a unique constraint
|The flash message never appears, or appears twice |It is written to the request (lost on redirect), or it is read without removal |Write it to the session before the redirect and move it to the request, removing it, at the start of the next request
|A model attribute is missing in the view after a redirect |Request attributes do not survive a new request |Pass an id in the URL and reload it, or use a flash attribute
|`;jsessionid=` in the links of the first response (observed) |`c:url` rewrites the URL until the cookie is confirmed |`+<tracking-mode>COOKIE</tracking-mode>+`
|`IllegalStateException` on `forward` or `sendRedirect` |The response was already committed by a write or flush |Decide first and write last; `return` after `sendError` and `sendRedirect`
|`JasperException` with "Unreachable code" at a scriptlet that ends in `return;` (observed) |Template text after the `return;` in the generated `_jspService`, or a `return;` inside a `c:if` body |Make `return;` the last statement of its block, closed in the same scriptlet, or do the redirect in a servlet
|Redirect to a URL taken from a request parameter |Open redirect: the controller sends users to any site |Redirect to fixed paths or to ids that the controller maps itself
|`ORDER BY` or table name built from a parameter |Identifiers cannot be bound |Allow-list (observed: unknown sort values fall back to the default)
|Stack trace or exception message in the browser (observed) |The error page prints `jakarta.servlet.error.message` for 500s |Print it only for client errors; log the rest
|`LazyInitializationException` or a query per row when the page renders |The view reads a lazy association of a detached or lazily loaded entity |Load what the view needs in the service; keep queries out of views
|Pool exhausted, requests hang |A `Connection` was not closed (it is never returned) |`try-with-resources` for `Connection`, `Statement` and `ResultSet`
|Accented characters corrupted in a posted form |`setCharacterEncoding` was called after the first `getParameter` |Set the encoding first in the controller or a filter (done as the first statement of `service`)
|`405` shows the container page, not the application's |The descriptor maps only some status codes |Add an `error-page` for each code the controller produces, or a catch-all
|A spreadsheet runs a formula from an exported CSV |A cell starting with `=`, `+`, `-` or `@` is interpreted |Neutralise leading characters in exports that users open in a spreadsheet
|A request attribute named `page` clashes in a scriptlet |`page` is also a scripting implicit object of a JSP |Use another attribute name, or read it only through EL (it works through EL, as the Bookshelf does)
|===

== What Changed Recently

.Changes that affect the architecture on this page
[cols="2,3",options="header"]
|===
|Change |Effect

|Servlet 6.1 (Jakarta EE 11) |`sendRedirect` overloads with a status and `clearBuffer`, so a controller can answer a `POST` with `303` without writing the header by hand; error dispatches carry `jakarta.servlet.error.method` and `query_string`; Tomcat 11 implements it
|Servlet 6.0 (Jakarta EE 10) |`SingleThreadModel` was removed, so a controller cannot ask the container to serialise requests and must be stateless; the generic cookie `setAttribute` allows `SameSite` for the session cookie
|Pages 4.0 (Jakarta EE 11) |Requires Java 17; removes the `jsp:plugin` action and the `isThreadSafe` page directive attribute (deprecated in 3.1); `ErrorData` gets the error attributes `jakarta.servlet.error.query_string` and `jakarta.servlet.error.method`, which a Model 2 error view can display
|Expression Language 6.0 (Jakarta EE 11) |Records resolve through `RecordELResolver`, which is why a record is a convenient model object and why derived values need component-named accessors
|Jakarta namespace (EE 9 and later) |`javax.servlet` code from before 2020 must be migrated; a controller written for Servlet 2.3 compiles after renaming imports
|Spring Boot 4.1 and Spring Framework 7.0 |JSP remains supported only as a WAR; template engines are the default advice
|Struts 7.4 |The front controller is the filter `org.apache.struts2.dispatcher.filter.StrutsPrepareAndExecuteFilter`, as the Core Developers Guide's web.xml page configures it; the Struts pages of this section start there

[#books-outdated]
== Where the Books Are Outdated

_Web Development with JavaServer Pages_ (Manning, 2001) devotes its chapters on page-centric and servlet-centric
architecture, databases and a worked FAQ application to the material of this page, and _JSTL in Action_ (Manning, 2003)
ends with a case study of survey, message-board and RSS pages. _Struts in Action_ (2002) and _Struts 2 in Action_ (2008)
cover the framework forms of Model 2. All four are listed in the section bibliography. The architecture they argue for has
held up; the details around it have not.

.JSP 1.2-era architecture material and its equivalent today
[cols="3,4",options="header"]
|===
|The books' era |Today (Servlet 6.1, Pages 4.0)

|Model 2 explained with `javax.servlet` classes and a `RequestDispatcher` obtained from the context |`jakarta.servlet`; `+request.getRequestDispatcher(path).forward(...)+` as in this page
|A JSP of the application reaches the database, with `java.sql` code in a scriptlet or the JSTL SQL tags, in the "Working with databases" examples |A repository behind a service, a pooled JNDI `DataSource` declared in `context.xml`, JPA for larger models
|Connection handling with `DriverManager`, `finally` blocks and `CachedRowSet` for passing results |`try-with-resources`, a container pool, lists of records; `CachedRowSet` remains in `java.sql.rowset` but is rarely the right tool
|Duplicate-submission tokens kept by the controller framework of the day, or hand-written session tokens |Post/Redirect/Get with `303` as the first defence, plus a per-form token or database constraint; see the framework documentation of your version
|Beans and `jsp:useBean`/`+jsp:setProperty property="*"+` in the page as the model |A controller that sets request attributes, views that read them with EL; `+property="*"+` is a mass-assignment risk
|Scriptlet loops in views (`+<% for ... %>+`) |JSTL `c:forEach` and EL; scriptlets can be disabled with `scripting-invalid`
|Controller servlets configured with `+*.do+` mappings and an `ActionServlet` or home-grown `Controller` base class |Prefix mappings, annotated routing or a framework; Struts 2 and later use a filter
|EJB 2 session beans behind the controller, found by JNDI home interfaces |Plain classes, CDI or Spring beans; EJB 3 and later as annotated classes in a full Jakarta EE server
|Command objects registered in an `init` that reads a properties file |A route table, annotations or `struts.xml`; the same idea
|Error handling by `errorPage` directives on every JSP |Descriptor `error-page` entries and `sendError`, a catch-all for `Throwable`
|`jsp:plugin`, applets for rich pages |Removed from Pages 4.0
|Tomcat 4 or WebLogic deployment details |Tomcat 11, `context.xml` and a Maven WAR
|===
