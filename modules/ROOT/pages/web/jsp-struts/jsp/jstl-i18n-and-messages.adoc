[#concepts]
== Locale, Bundle, Basename and Key

The specification builds the library on four ideas, all taken from `java.util`.

* A *locale* is a language, optionally with a country and a variant. The language is the lower-case two-letter ISO-639
  code (`es`, `fr`), the country the upper-case two-letter ISO-3166 code (`ES`, `CA`). The semantics are those of
  `java.util.Locale`, so the legacy codes apply: `he`, `yi` and `id` are reported as `iw`, `ji` and `in` by `Locale`
  unless the JVM property `java.locale.useOldISOCodes` says otherwise.
* A *resource bundle* holds locale-specific objects, here strings, each associated with a *key*.
* A *basename* identifies a family of bundles that translate the same keys. The bundle for a locale is the basename plus
  a suffix: `Messages` is the root bundle, `Messages_es` the Spanish one, `Messages_es_ES` the Spanish of Spain.
* A *localization context* is the pair the actions actually work with: a resource bundle and the locale for which it
  was found. It is the Java class `jakarta.servlet.jsp.jstl.fmt.LocalizationContext`.

The specification names two ways of internationalizing a page. The first is one page per locale with a controller
servlet that dispatches to the right one, which suits pages where most of the content differs. The second isolates the
locale-sensitive text in bundles and fetches it with the `fmt:` actions, which suits everything else and is what the
rest of this page is about. The two combine: a controller can pick a page variant per locale and each variant still
uses bundles for its labels.

Source: https://jakarta.ee/specifications/tags/3.0/jakarta-tags-spec-3.0.html#internationalization-i18n-actions-i18n-capable-formatting-tag-library[Jakarta Standard Tag Library 3.0 -- 8.1 Overview]

Source: https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/Locale.html#legacy_language_codes[Java SE 21 API -- Locale, legacy language codes]

== Declaring the Library

The i18n actions live in the `fmt` library with the URI `jakarta.tags.fmt` (Tags 3.0 renamed the URIs from
`http://java.sun.com/jsp/jstl/*` to `jakarta.tags.*`). The prefix `fmt` is a convention, not a rule.

[source,jsp]
----
<%@ taglib prefix="fmt" uri="jakarta.tags.fmt" %>
----

Source: https://jakarta.ee/specifications/tags/3.0/jakarta-tags-spec-3.0.html#changed-between-jakarta-standard-tag-library-2-0-and-jakarta-standard-tag-library-3-0[Jakarta Standard Tag Library 3.0 -- Appendix B.1, Changes]

The old URIs still work with the 3.0.1 implementation because the jar keeps the older TLD files (`fmt-1_0.tld`,
`fmt-1_0-rt.tld`, `fmt-1_1.tld`, `fmt.tld`): `uri="http://java.sun.com/jsp/jstl/fmt"` and the JSTL 1.0 URI
`uri="http://java.sun.com/jstl/fmt"` both rendered the Bookshelf title on Tomcat 11.0.26. The URI of the JSF-era
namespace, `+http://xmlns.jcp.org/jsp/jstl/fmt+`, is not one of them and fails with `JasperException: The absolute uri:
[http://xmlns.jcp.org/jsp/jstl/fmt] cannot be resolved in either web.xml or the jar files deployed with this application`.
New code should use `jakarta.tags.fmt`.

[#first-message]
== The First Message: `fmt:setBundle` and `fmt:message`

The smallest internationalized page names a bundle once and then asks for keys. `fmt:setBundle` without a `var` makes
the bundle the default localization context of the page, and `fmt:message` reads its key from that default.

.A page whose text comes from bundles, `basic.jsp`
[source,jsp]
----
<%@ page contentType="text/html; charset=UTF-8" pageEncoding="UTF-8" %>
<%@ taglib prefix="c" uri="jakarta.tags.core" %>
<%@ taglib prefix="fmt" uri="jakarta.tags.fmt" %>
<fmt:setBundle basename="org.example.bookshelf.i18n.Messages"/>
<h1><fmt:message key="shelf.title"/></h1>
<p><fmt:message key="shelf.count"><fmt:param value="${books.size()}"/></fmt:message></p>
<ul>
<c:forEach var="b" items="${books}">
  <li><c:out value="${b.title}"/></li>
</c:forEach>
</ul>
----

With `Accept-Language: es` the page answers with the Spanish bundle, and with no `Accept-Language` header at all it
answers with the root bundle:

[source,html]
----
<!-- curl -H 'Accept-Language: es' /g5jstli18n/data/basic -->
<h1>Mi estantería</h1>
<p>Tienes 3 libros en la estantería</p>

<!-- curl /g5jstli18n/data/basic -->
<h1>My Bookshelf</h1>
<p>You have 3 books on the shelf</p>
----

The response headers are part of the result. For the Spanish request Tomcat answered `Content-Language: es` and
`Content-Type: text/html;charset=UTF-8`; for a request with `Accept-Language: en-GB` it answered `Content-Language:
en-GB`; for a request without the header there was no `Content-Language` at all. The actions set the response locale as
a side effect, which is the subject of the response section below.

The book titles are printed with `c:out`, never as a bare `+${b.title}+`, because a title is data and not a message:
bundles hold the application's own text, and the data around it still has to be escaped (the security section shows why
`fmt:message` is not an escaping tag).

Source: https://jakarta.ee/specifications/tags/3.0/jakarta-tags-spec-3.0.html#fmt:setBundle[Jakarta Standard Tag Library 3.0 -- 8.7 fmt:setBundle]

Source: https://jakarta.ee/specifications/tags/3.0/jakarta-tags-spec-3.0.html#fmt:message[Jakarta Standard Tag Library 3.0 -- 8.8 fmt:message]

[#message-reference]
== `fmt:message` and `fmt:param` Reference

`fmt:message` looks a key up in the bundle of the localization context it determines and writes the text to the current
`JspWriter`, or stores it in a scoped variable when `var` is given. It has three syntaxes: the key in an attribute and no
body, the key in an attribute with `fmt:param` children, and the key as the (trimmed) body, optionally followed by
`fmt:param` children.

.Attributes of `fmt:message`
[cols="1,1,1,4",options="header"]
|===
|Attribute |Dynamic |Type |Meaning

|`key` |yes |`String` |The message key to look up. If it is absent, the trimmed body is the key
|`bundle` |yes |`LocalizationContext` |The localization context to read the key from; wins over everything else
|`var` |no |`String` |Name of the scoped variable that receives the message instead of printing it
|`scope` |no |`String` |Scope of `var`: `page` (default), `request`, `session` or `application`; allowed only together with `var`
|===

.Attribute of `fmt:param`
[cols="1,1,1,4",options="header"]
|===
|Attribute |Dynamic |Type |Meaning

|`value` |yes |`Object` |The argument; when it is absent, the trimmed body content is the argument
|===

The error handling is specified and was observed:

.Null and error handling of `fmt:message`
[cols="3,3,3",options="header"]
|===
|Situation |Specified result |Observed output (Tomcat 11.0.26)

|The key is not in the bundle |The text `???key???` with the key between the question marks |`???no.such.key???`
|The key is null or empty |`??????`, the message processed as undefined |`??????`
|No resource bundle can be found for the context |`???key???` for every key |`???shelf.title???` inside `+fmt:bundle basename="...NoSuchBundle"+`, and also in a page with no `fmt:setBundle` and no default context
|`scope` without `var` |Constraint of the tag |Translation fails with `Illegal scope attribute without var in "fmt:message" tag.`
|`fmt:param` outside a `fmt:message` |Constraint of the tag |Translation fails with `<param> outside <message>`
|`bundle` given a `String` instead of a `LocalizationContext` |Type mismatch |`Unable to convert string [org.example.bookshelf.i18n.Messages] to class [jakarta.servlet.jsp.jstl.fmt.LocalizationContext] for attribute [bundle]`
|===

None of these failures is an exception at request time except the translation-time ones, so a missing key is visible
only as `???` in the page. A page test that greps for `???` catches most of them.

.A bundle selected by variable, the key as a body, a stored message and the error outputs, `bundle.jsp`

----
<fmt:setBundle basename="org.example.bookshelf.i18n.Messages" var="msgs"/>
<p><fmt:message key="shelf.title" bundle="${msgs}"/></p>
<fmt:message key="shelf.title" bundle="${msgs}" var="t" scope="request"/>
<p>stored: ${requestScope.t}</p>
<p>body key: <fmt:message bundle="${msgs}">  shelf.title  </fmt:message></p>
<p>missing: <fmt:message key="no.such.key" bundle="${msgs}"/></p>
<p>empty key: <fmt:message key="" bundle="${msgs}"/></p>
----

[source,html]
----
<p>Mi estantería</p>
<p>stored: Mi estantería</p>
<p>body key: Mi estantería</p>
<p>missing: ???no.such.key???</p>
<p>empty key: ??????</p>
----

[#parameters]
== Parameters and `MessageFormat`

A message that contains variables is a `java.text.MessageFormat` pattern, and `fmt:param` supplies the arguments in the
order of the tags. The specification states the mechanism exactly: with one or more `fmt:param` tags the message is
passed to `MessageFormat.applyPattern()` and the values are collected in an `Object[]` for `format()`, with the
`MessageFormat` locale set to the locale of the localization context (or, when the context has no locale, to the
formatting locale of the page, or finally to the JVM default). Without any `fmt:param` the message is left untouched and
`MessageFormat` is not used at all. That second rule explains several outputs below.

.Parameters in a message, the number, the plural and the date cases, `params.jsp`
[source,jsp]
----
<fmt:setBundle basename="org.example.bookshelf.i18n.Messages"/>
<c:set var="b" value="${books[0]}"/>
<p><fmt:message key="shelf.summary"><fmt:param value="${b.title}"/><fmt:param value="${b.author}"/><fmt:param value="${b.year}"/></fmt:message></p>
<p><fmt:message key="shelf.summary.year"><fmt:param value="${b.title}"/><fmt:param value="${b.author}"/><fmt:param value="${b.year}"/></fmt:message></p>
<p><fmt:message key="shelf.copies"><fmt:param value="${0}"/><fmt:param value="${b.title}"/></fmt:message></p>
<p><fmt:message key="shelf.copies"><fmt:param value="${1}"/><fmt:param value="${b.title}"/></fmt:message></p>
<p><fmt:message key="shelf.copies"><fmt:param value="${1234}"/><fmt:param value="${b.title}"/></fmt:message></p>
<p><fmt:message key="shelf.count"><fmt:param><fmt:formatNumber value="${12345}"/></fmt:param></fmt:message></p>
<jsp:useBean id="now" class="java.util.Date"/>
<p><fmt:message key="shelf.due"><fmt:param value="${now}"/></fmt:message></p>
----

with these extra keys in `Messages.properties` (the Spanish file has the same keys translated):

[source,properties]
----
shelf.copies=There {0,choice,0#are no copies|1#is one copy|1<are {0,number,integer} copies} of {1}
shelf.due=Due on {0,date,long}
----

.Output with `Accept-Language: en` and with `Accept-Language: es`
[source,html]
----
<p>Dune was written by Frank Herbert in 1,965</p>
<p>Dune was written by Frank Herbert in 1965</p>
<p>There are no copies of Dune</p>
<p>There is one copy of Dune</p>
<p>There are 1,234 copies of Dune</p>
<p>You have 12,345 books on the shelf</p>
<p>Due on October 8, 2026</p>

<p>Dune fue escrito por Frank Herbert en 1.965</p>
<p>Dune fue escrito por Frank Herbert en 1965</p>
<p>Hay ninguna copia de Dune</p>
<p>Hay una copia de Dune</p>
<p>Hay 1.234 copias de Dune</p>
<p>Tienes 12.345 libros en la estantería</p>
<p>Vence el 8 de octubre de 2026</p>
----

Four lessons are visible in this output.

* A number argument is formatted by `MessageFormat` with the grouping of the locale. The year 1965 printed as `1,965`
  in English and `1.965` in Spanish. The pattern `+{2,number,#}+` (a `DecimalFormat` pattern without grouping) prints
  `1965` in both. A year, an id or a postal code is not a quantity and needs that pattern, or a `String` argument.
* The `choice` format gives plural forms (`+0#...|1#...|1<...+`), and the number inside it can use its own sub-format
  (`+{0,number,integer}+` printed `1,234`). Spanish shows that the plural words are the translator's business: the
  Spanish line reads awkwardly (`Hay ninguna copia`, where a translator would write `No hay ninguna copia`), which is
  the argument for putting the whole sentence, not a fragment, in the bundle and letting the translator own it. Plural
  rules of languages with more than two forms are beyond `choice`; ICU4J's `MessageFormat` is the usual answer when they
  are needed.
* A date argument can be given a style (`+{0,date,long}+`) and is then localized by the same locale: `October 8, 2026`
  against `8 de octubre de 2026`.
* `fmt:param` accepts a body, so another action can compute the argument. `fmt:formatNumber` inside the `fmt:param`
  printed `12,345` and `12.345`, using the same formatting locale as the message.

Source: https://jakarta.ee/specifications/tags/3.0/jakarta-tags-spec-3.0.html#fmt:message[Jakarta Standard Tag Library 3.0 -- 8.8 fmt:message, parametric replacement]

Source: https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/text/MessageFormat.html#patterns[Java SE 21 API -- MessageFormat, Patterns and Their Interpretation]

[#apostrophes]
=== The apostrophe trap

`MessageFormat` uses the single quote to quote text, so an apostrophe in a message that is formatted has to be doubled,
and an apostrophe in a message that is not formatted must not be. Because `fmt:message` calls `MessageFormat` only when
there are `fmt:param` children, the same text needs different spelling in the two cases. The bundle for this example
adds three keys:

[source,properties]
----
shelf.apostrophe.plain=Don't panic
shelf.apostrophe.param=Don''t panic about {0}
shelf.apostrophe.broken=Don't panic about {0}
----

.The three spellings with and without parameters, `apostrophe.jsp` and `apos2.jsp`
[source,jsp]
----
<p>1: <fmt:message key="shelf.apostrophe.plain"/></p>
<p>2: <fmt:message key="shelf.apostrophe.param"><fmt:param value="Dune"/></fmt:message></p>
<p>3: <fmt:message key="shelf.apostrophe.broken"><fmt:param value="Dune"/></fmt:message></p>
<p>4: <fmt:message key="shelf.apostrophe.broken"/></p>
<p>5: <fmt:message key="shelf.apostrophe.param"/></p>
----

[source,html]
----
<p>1: Don't panic</p>
<p>2: Don't panic about Dune</p>
<p>3: Dont panic about {0}</p>
<p>4: Don't panic about {0}</p>
<p>5: Don''t panic about {0}</p>
----

Line 3 is the failure: the single quote started a quoted section, so the apostrophe vanished and `+{0}+` was printed
literally. Line 5 is the mirror image: the doubled apostrophe shows doubled when the message is not formatted. The rule
that works is to double the apostrophe in every message that is ever used with a `fmt:param`, and to keep a message
either always with parameters or never. A message whose parameter count may be zero should be given a dummy parameter or
should be rewritten, because the same bundle line cannot satisfy both spellings.

Source: https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/text/MessageFormat.html#patterns[Java SE 21 API -- MessageFormat, quoting with single quotes]

[#bundles-and-context]
== Bundles and the Localization Context

An i18n action needs a localization context, and the specification fixes where it comes from. The first rule that applies
wins.

.How `fmt:message` finds its localization context (Tags 3.0, section 8.2)
[cols="1,3,3",options="header"]
|===
|Order |Source |Example

|1 |The `bundle` attribute of `fmt:message`, a `LocalizationContext` object |`+<fmt:message key="x" bundle="${msgs}"/>+`
|2 |The innermost enclosing `fmt:bundle` |`+<fmt:bundle basename="..."> ... </fmt:bundle>+`
|3 |The default localization context, the configuration setting `jakarta.servlet.jsp.jstl.fmt.localizationContext`, set by `fmt:setBundle` without `var`, by a scoped configuration variable or by a `context-param` |`+<fmt:setBundle basename="..."/>+` earlier in the page
|===

If the default setting is a `LocalizationContext`, its bundle is used as it is. If it is a `String`, the action builds its
own context with that string as the basename, using the lookup algorithm of the next section.

[mermaid]
....
flowchart TD
    msg["fmt:message key"] --> a{"bundle attribute present?"}
    a -- yes --> ctx1["use that LocalizationContext"]
    a -- no --> b{"inside a fmt:bundle?"}
    b -- yes --> ctx2["use the context of the innermost fmt:bundle"]
    b -- no --> c{"default localizationContext configured?"}
    c -- "LocalizationContext object" --> ctx3["use it as it is"]
    c -- "String basename" --> ctx4["build a context from the basename with the lookup algorithm"]
    c -- "nothing" --> none["no bundle: output is ???key???"]
    ctx1 --> out["look the key up, apply MessageFormat if fmt:param children exist"]
    ctx2 --> out
    ctx3 --> out
    ctx4 --> out
....

[#fmt-bundle]
=== `fmt:bundle` and its `prefix`

`fmt:bundle` creates a localization context for its body: every `fmt:message` nested inside it, at any depth of markup,
uses it (unless the message has its own `bundle` attribute). The `prefix` attribute is prepended to the key of every
nested `fmt:message`, which saves typing for long, dotted keys. The body of `fmt:bundle` is processed normally and
written to the page.

.Attributes of `fmt:bundle` and `fmt:setBundle`
[cols="1,2,1,1,4",options="header"]
|===
|Action |Attribute |Dynamic |Type |Meaning

|`fmt:bundle` |`basename` |yes |`String` |The fully qualified resource name of the bundle, in class-name form with `.` separators and without suffix (`org.example.bookshelf.i18n.Messages`)
|`fmt:bundle` |`prefix` |yes |`String` |Text prepended to the key of every nested `fmt:message`
|`fmt:setBundle` |`basename` |yes |`String` |As above
|`fmt:setBundle` |`var` |no |`String` |Scoped variable that receives the `LocalizationContext`; if absent, the context becomes the default localization context
|`fmt:setBundle` |`scope` |no |`String` |Scope of `var` or of the default context; `page` is the default
|===

[#fmt-setbundle]
=== `fmt:setBundle`: a variable or the default

`fmt:setBundle` with a `var` stores a `LocalizationContext` that other tags can pass in their `bundle` attribute. This is
the way to use two bundles on one page, for instance the application's messages and a separate bundle of error texts,
without nesting `fmt:bundle` blocks. Without `var`, the context becomes the page's default (or, with `scope="session"`
or `scope="application"`, the default of a wider scope).

.The two uses of `fmt:setBundle`
[source,jsp]
----
<%-- 1. as a variable, used explicitly --%>
<fmt:setBundle basename="org.example.bookshelf.i18n.Errors" var="errors"/>
<fmt:message key="book.notFound" bundle="${errors}"/>

<%-- 2. as the default of the page, session or application --%>
<fmt:setBundle basename="org.example.bookshelf.i18n.Messages" scope="application"/>
----

[#locales]
== Choosing the Locale

The locale that picks the bundle (and, for the formatting actions, the number and date style) comes from one of two
places, and the specification gives the first priority.

* *Application-based.* The configuration setting `jakarta.servlet.jsp.jstl.fmt.locale` (the constant `Config.FMT_LOCALE`)
  holds a locale chosen by the application. It is set by `fmt:setLocale`, by `Config.set` from Java code, or by a
  `context-param` of the same name. It is the right choice when the user picks a language in the interface, or when the
  language is stored in the user's profile.
* *Browser-based.* If the setting is absent, the actions call `ServletRequest.getLocales()`, the ordered list built from
  the `Accept-Language` header, and try the locales in that order.

Either way an ordered list of preferred locales is fed to the bundle algorithm. One detail of the implementation matters
in tests: the `Util.getRequestLocales` of the 3.0.1 implementation returns the locales of the request only when the
request has an `Accept-Language` header. Without the header the list is empty, even though `request.getLocales()` alone
would return the server's default locale (it printed `en_US` in the test). A `curl` without the header therefore behaves
like a visitor whose browser expresses no preference, and falls to the fallback locale or the root bundle.

Source: https://jakarta.ee/specifications/tags/3.0/jakarta-tags-spec-3.0.html#preferred-locales[Jakarta Standard Tag Library 3.0 -- 8.2.1 Preferred Locales]

Source: https://jakarta.ee/specifications/tags/3.0/jakarta-tags-spec-3.0.html#locale[Jakarta Standard Tag Library 3.0 -- 8.11.1 Locale]

[#fmt-setlocale]
=== `fmt:setLocale`

.Attributes of `fmt:setLocale`
[cols="1,1,1,4",options="header"]
|===
|Attribute |Dynamic |Type |Meaning

|`value` |yes |`String` or `java.util.Locale` |A string with a lower-case language and optionally an upper-case country, separated by `-` or `_` (`es`, `es-ES`, `es_ES`). A null or empty value selects the JVM default locale
|`variant` |yes |`String` |A vendor or browser variant; ignored when `value` is a `Locale` object
|`scope` |no |`String` |Scope of the configuration variable: `page` (default), `request`, `session` or `application`
|===

`fmt:setLocale` stores the locale in the configuration variable of the requested scope and thereby switches off
browser-based selection. The specification asks for it to be declared at the beginning of the page, before any other
i18n-capable action, because the actions that run earlier have already chosen their locale.

.A fixed locale, `setlocale.jsp`
[source,jsp]
----
<fmt:setLocale value="es"/>
<fmt:setBundle basename="org.example.bookshelf.i18n.Messages"/>
<p><fmt:message key="shelf.title"/> -- <c:out value="${pageContext.response.locale}"/></p>
----

[source,html]
----
<p>Mi estantería -- es</p>        <!-- Accept-Language: en, still Spanish -->
----

The fixed locale overrides the browser: the request with `Accept-Language: en` was answered in Spanish with
`Content-Language: es`. Further observed results on Tomcat 11.0.26:

.Observed behaviour of `fmt:setLocale`
[cols="3,3",options="header"]
|===
|Input |Result

|`value="es-ES"` with `scope="session"` |The locale `es_ES` and `Content-Language: es-ES`; the next request of the same session, with no `fmt:setLocale`, was still in `es_ES` (the session scope persisted it)
|`value="es"` with `variant="ES"` |`pageContext.response.locale` printed `es__ES`, a locale with an empty country and the variant `ES`
|`value=""` |The JVM default locale, `en_US`, with `Content-Language: en-US`
|`value="xx_YY_ZZZ_bad"` |Accepted without any error: the response locale printed `XX_YY_ZZZ_BAD` and `Content-Language: xx`
|===

The last row is the reason to validate a locale before it reaches the tag. `+fmt:setLocale value="${param.lang}"+` accepts
anything the visitor sends, and the response locale (and the `Content-Language` header) follow it. The safe design is a
small allowlist of the application's own languages in a servlet or filter.

[#language-switcher]
=== A language switcher with an allowlist and `Config`

A language selector should not be a request parameter read by the tag. The pattern that scales is a servlet that
validates the choice and stores it in the session with the `Config` class, after which every page of the session uses it.
`Config.set(session, Config.FMT_LOCALE, locale)` is the Java equivalent of `fmt:setLocale scope="session"`.

.A servlet that validates and stores the locale, `LanguageServlet`
[source,java]
----
@WebServlet("/language")
public class LanguageServlet extends HttpServlet {
    private static final Set<String> SUPPORTED = Set.of("en", "es");

    @Override
    protected void doPost(HttpServletRequest req, HttpServletResponse resp) throws ServletException, IOException {
        String tag = req.getParameter("lang");
        if (tag != null && SUPPORTED.contains(tag)) {
            Config.set(req.getSession(), Config.FMT_LOCALE, Locale.forLanguageTag(tag));
        }
        resp.sendRedirect(req.getContextPath() + "/data/shelf");
    }
}
----

.The page with the two buttons, `shelf.jsp`
[source,jsp]
----
<fmt:setBundle basename="org.example.bookshelf.i18n.Messages"/>
<h1><fmt:message key="shelf.title"/></h1>
<p><fmt:message key="shelf.count"><fmt:param value="${books.size()}"/></fmt:message></p>
<form method="post" action="${pageContext.request.contextPath}/language">
  <button name="lang" value="en">English</button>
  <button name="lang" value="es">Español</button>
</form>
----

The sequence below was run with a cookie jar so that the session persisted, and with `Accept-Language: en` on every GET:

[source,text]
----
GET  /data/shelf                  ->  <h1>My Bookshelf</h1>
POST /language  lang=es           ->  302, Location: /g5jstli18n/data/shelf
GET  /data/shelf                  ->  Content-Language: es   <h1>Mi estantería</h1>
POST /language  lang=xx           ->  302 (ignored, not in the allowlist)
GET  /data/shelf                  ->  <h1>Mi estantería</h1>
----

The switch is a `POST` because it changes state of the session, and the redirect after it follows the
Post/Redirect/Get pattern. A cookie that remembers the choice across sessions is a separate decision (it is a preference
cookie, with the privacy considerations of any cookie) and is not part of the specification.

Source: https://jakarta.ee/specifications/tags/3.0/apidocs/jakarta.servlet.jsp.jstl/jakarta/servlet/jsp/jstl/core/Config.html[Jakarta Tags 3.0 Javadoc -- Config]

Source: https://jakarta.ee/specifications/tags/3.0/jakarta-tags-spec-3.0.html#configuration-data[Jakarta Standard Tag Library 3.0 -- 2.8 Configuration Data]

[#lookup-algorithm]
== The Bundle Lookup and Fallback Algorithm

Given a basename and the ordered preferred locales, the specification defines the resource bundle for a localization
context in two parts.

*The lookup of one locale* uses `ResourceBundle.getBundle(basename, locale)` but only its first level: the candidates are
`basename_language_country_variant`, `basename_language_country` and `basename_language`. The JDK's later steps (the
JVM default locale, then the root bundle) are explicitly removed so that other locales can be considered first.

*The determination of the bundle* then runs these steps and stops at the first success:

. For each preferred locale, in order, do the lookup. The first match wins and the context stores that locale and bundle.
. If none matched, do the lookup for the locale in the `jakarta.servlet.jsp.jstl.fmt.fallbackLocale` setting.
. If still nothing, load the root bundle (`basename` alone). If it exists it is used and the context has no locale.
. Otherwise the context has neither bundle nor locale and the action must take corrective action (`fmt:message` prints
  `???key???`).

[mermaid]
....
flowchart TD
    start["preferred locales, in order"] --> loop{"next preferred locale"}
    loop -- "lookup finds basename_lang[_country[_variant]]" --> done["use it: context = bundle and that locale"]
    loop -- "none left" --> fb{"fallbackLocale set and found?"}
    fb -- yes --> done2["use it: context = bundle and the fallback locale"]
    fb -- no --> root{"root bundle basename exists?"}
    root -- yes --> done3["use the root bundle: context has no locale"]
    root -- no --> none["context without a bundle: fmt:message prints ???key???"]
....

Two consequences are stated in the specification and are easy to get wrong.

* A language match beats an exact match further down the list. With the browser preferences `en` then `fr_CA` and the
  bundles `Messages_en` and `Messages_fr_CA`, the bundle used is `Messages_en`, because the lookup for `en` succeeds
  before `fr_CA` is tried.
* A bundle for a language and country (`Resources_fr_CA`) should be backed by one for the language alone
  (`Resources_fr`). A visitor whose browser asks only for `fr` finds nothing in `Resources_fr_CA`: the lookup for the
  locale `fr` does not look at `fr_CA`.

Source: https://jakarta.ee/specifications/tags/3.0/jakarta-tags-spec-3.0.html#resource-bundle-lookup[Jakarta Standard Tag Library 3.0 -- 8.3.1 Resource Bundle Lookup]

Source: https://jakarta.ee/specifications/tags/3.0/jakarta-tags-spec-3.0.html#resource-bundle-determination-algorithm[Jakarta Standard Tag Library 3.0 -- 8.3.2 Resource Bundle Determination Algorithm]

[#fallback-tests]
=== The algorithm on Tomcat 11, observed

To see the algorithm work, four families of bundles were created. `Plain` has `Plain_en` and `Plain_es` and no root.
`Region` has `Region_en` and `Region_fr_CA`. `Canada` has `Canada_en` and `Canada_fr_CA`. Each is used by a page that
prints one greeting and the response locale:

[source,jsp]
----
<fmt:bundle basename="org.example.bookshelf.i18n.Plain"><fmt:message key="greeting"/> | ${pageContext.response.locale}</fmt:bundle>
----

.Observed results (Tomcat 11.0.26, JVM default locale `en_US`)
[cols="3,3,3",options="header"]
|===
|Bundles and request |Result |Reading

|`Region`, `Accept-Language: en, fr-CA` |`Hello (en) \| en` |The language match beats the later exact match, as in the specification
|`Region`, `Accept-Language: fr-CA, en` |`Bonjour (fr_CA) \| fr_CA` |The exact match first
|`Plain`, `Accept-Language: fr,es` |`Hola desde el paquete en español \| es` |`fr` fails, `es` matches (the second preferred locale)
|`Plain`, `Accept-Language: en-GB` |`Hello from the English bundle \| en_GB` |The lookup for `en_GB` finds `Plain_en`; the context locale is the _requested_ locale
|`Canada`, `Accept-Language: fr` |`Hello from Canada (en) \| en_US` |No `Canada_fr`; `Canada_fr_CA` is not used; the English bundle appears
|`Plain`, `Accept-Language: de`, no root, no fallback |`Hello from the English bundle \| en_US` |See the next paragraph
|`Plain`, `Accept-Language: de`, `fallbackLocale=es` |`Hola desde el paquete en español \| es` |The fallback locale applies
|`Plain`, no `Accept-Language`, `fallbackLocale=es` |`Hola desde el paquete en español \| es` |An empty preference list goes straight to the fallback locale
|`Messages` (root exists), `Accept-Language: en-GB` |`My Bookshelf \| en_US` |The root bundle, used because `Messages_en_GB` and `Messages_en` do not exist
|===

The last-resort steps carry a surprise on the 3.0.1 implementation. For `Plain` with `Accept-Language: de`, there is no
German bundle, no fallback locale and no root bundle, so the specification says the result is a context without a bundle
and `???greeting???`. The page printed the English greeting instead. Inspecting the bytecode of the implementation's `BundleSupport` class shows that its last step is
`ResourceBundle.getBundle(basename, <empty locale>, contextClassLoader)`, and the JDK's own algorithm, when the root
bundle is missing, falls back to the JVM default locale (`en_US`), which finds `Plain_en`. The specification promises that the default
locale of the container's JVM is never considered "because this would result in a non-portable behavior"; this
implementation lets it in through the last step. The practical guidance is the one the specification gives: always
define a fallback locale (or a root bundle) so that the outcome never depends on the JVM that happens to run the
application.

Source: https://jakarta.ee/specifications/tags/3.0/jakarta-tags-spec-3.0.html#resource-bundle-determination-algorithm[Jakarta Standard Tag Library 3.0 -- 8.3.2, the fallback locale and the default locale]

Source: https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/ResourceBundle.html#default_behavior[Java SE 21 API -- ResourceBundle, default behavior of getBundle]

[#configuration]
== Configuration Settings

Three settings concern the i18n actions. Each is both a context-parameter name and a configuration variable name, and each
has a constant in `jakarta.servlet.jsp.jstl.core.Config`. A scoped configuration variable overrides the context parameter
for the scope where it is set.

.The i18n configuration settings (Tags 3.0, section 8.11)
[cols="3,2,2,2,3",options="header"]
|===
|Name (`web.xml` and variable) |`Config` constant |Type |Set by |Used by

|`jakarta.servlet.jsp.jstl.fmt.locale` |`Config.FMT_LOCALE` |`String` or `Locale` |`fmt:setLocale` |The i18n actions and the four formatting actions
|`jakarta.servlet.jsp.jstl.fmt.fallbackLocale` |`Config.FMT_FALLBACK_LOCALE` |`String` or `Locale` |Nothing in the tag library; use `web.xml` or `Config.set` |The same actions
|`jakarta.servlet.jsp.jstl.fmt.localizationContext` |`Config.FMT_LOCALIZATION_CONTEXT` |`String` (basename) or `LocalizationContext` |`fmt:setBundle` without `var` |`fmt:message` and the formatting actions
|===

Two more names appear in this area. `jakarta.servlet.jsp.jstl.fmt.timeZone` belongs to the formatting page. The scoped
variable `jakarta.servlet.jsp.jstl.fmt.request.charset` is set by the i18n actions in session scope and read by
`fmt:requestEncoding` (next sections).

Only strings can be given in `web.xml`. For a configuration variable the type is checked with the conversion rules of the
Expression Language, and a failure raises a `JspException` at run time. The specification's reason for the `Config` class
is a naming trick: all scopes of a `PageContext` behave as one namespace, so setting a plain attribute in one scope would
override it in all, whereas `Config` mangles the name per scope. This leads to a pitfall that was tested:

.A configuration variable set with `c:set`, `cset.jsp`
[source,jsp]
----
<c:set var="jakarta.servlet.jsp.jstl.fmt.locale" value="es" scope="request"/>
<fmt:setBundle basename="org.example.bookshelf.i18n.Messages"/>
<p><fmt:message key="shelf.title"/></p>
----

With `Accept-Language: en-GB` the page answered `<p>My Bookshelf</p>`, so the plain attribute had no effect on the
locale choice, while the same request with `Accept-Language: es` answered in Spanish from the browser preference alone.
Use `fmt:setLocale` or `+Config.set(...)+`, which write the name the library actually reads.

Source: https://jakarta.ee/specifications/tags/3.0/jakarta-tags-spec-3.0.html#configuration-settings[Jakarta Standard Tag Library 3.0 -- 8.11 Configuration Settings]

[#response-locale]
== The Response Locale and the Request Charset

The i18n actions have a side effect that the specification spells out: an action that establishes a localization context
sets the locale of the response by calling `ServletResponse.setLocale()` with the context's locale (unless the context has
no locale). `fmt:setLocale` always does it; `fmt:bundle`, `fmt:setBundle`, a `fmt:message` that establishes a context and
the formatting actions that choose a formatting locale do it too. The results of the tests above show it in the
`Content-Language` header: `es` for Spanish, `en-GB` for `Accept-Language: en-GB`.

The Servlet rule behind it is that `setLocale` also sets the response character encoding when no encoding has been set
explicitly by `setContentType` with a charset or by `setCharacterEncoding`; on a stock Tomcat 11 the two
`response-character-encoding` elements of `conf/web.xml` already say UTF-8, and the pages above also declare
`charset=UTF-8`, so the charset stayed `UTF-8` in every response. Two conditions apply in general: `setLocale` must run
before the writer is obtained, which is why the page needs a large enough buffer, and an explicit charset always wins
over the locale's. How a locale maps to a charset, and what to declare so that the result never depends on the container,
is on the xref:web/jsp-struts/jsp/character-encoding.adoc[Character Encoding page].

After setting the response locale, an action stores the charset of the response in the scoped variable
`jakarta.servlet.jsp.jstl.fmt.request.charset` in _session_ scope, if a session exists and is valid. That variable exists
for the next action.

Source: https://jakarta.ee/specifications/tags/3.0/jakarta-tags-spec-3.0.html#response-encoding[Jakarta Standard Tag Library 3.0 -- 8.4 Response Encoding]

[#request-encoding]
== `fmt:requestEncoding`

A browser encodes the values of a form with the encoding of the page that contained the form, but most browsers do not
send a charset in the request's `Content-Type`, so the container has to guess how to decode the parameters. The guess
is ISO-8859-1 unless the container or application says otherwise. `fmt:requestEncoding` sets the request character
encoding by calling `setCharacterEncoding` and must run before any parameter is read, "either explicitly or through the
use of an Expression Language expression".

.Attribute of `fmt:requestEncoding`
[cols="1,1,1,4",options="header"]
|===
|Attribute |Dynamic |Type |Meaning

|`value` |yes |`String` |The charset name to use for the parameters. If absent, the charset of the request's `Content-Type`, else the session variable `jakarta.servlet.jsp.jstl.fmt.request.charset`, else ISO-8859-1
|===

.A form page and its handlers, `form.jsp`, `search.jsp` and `search2.jsp`
[source,jsp]
----
<%-- form.jsp: the page that makes the charset variable available --%>
<fmt:setBundle basename="org.example.bookshelf.i18n.Messages"/>
<form method="post" action="${pageContext.request.contextPath}/data/search2">
  <label><fmt:message key="form.label"/> <input name="q"></label>
  <button><fmt:message key="form.search"/></button>
</form>
<p>charset var: ${sessionScope['jakarta.servlet.jsp.jstl.fmt.request.charset']}</p>

<%-- search.jsp: a fixed value --%>
<fmt:requestEncoding value="ISO-8859-1"/>
<p>q=<c:out value="${param.q}"/> length=${param.q.length()}</p>

<%-- search2.jsp: no value, so the Content-Type charset, then the session variable --%>
<fmt:requestEncoding/>
<p>q=<c:out value="${param.q}"/> length=${param.q.length()}</p>
----

|===
|Request |Result

|`GET form.jsp` after the page produced a `fmt:message` in the session |`charset var: UTF-8` (the response charset was stored in the session)
|`search2`, body `q=ni%C3%B1o` (UTF-8 bytes), no charset in `Content-Type`, session with the variable |`q=niño length=4`
|`search`, body `q=ni%F1o` (ISO-8859-1 bytes), `value="ISO-8859-1"` |`q=niño length=4`
|`search`, body `q=ni%C3%B1o`, `value="ISO-8859-1"` |`q=niÃ±o length=5` (the fixed value decodes the UTF-8 bytes as Latin-1)
|`search`, body `q=ni%C3%B1o`, `+Content-Type: ...; charset=UTF-8+`, `value="ISO-8859-1"` |`q=niÃ±o length=5`: the `value` attribute overrides the charset of the request
|`search2`, body `q=ni%F1o`, no charset (invalid UTF-8) |HTTP 400, `InvalidParameterException: Character decoding failed. Parameter [q] with value [ni?o] has been ignored`
|`search2`, body `q=ni%F1o`, `+Content-Type: ...; charset=ISO-8859-1+` |`q=niño length=4`

Three facts follow. A fixed `value` is a promise about the form's encoding and overrides what the client declares, so it
must match the page that built the form. The no-value form is meant for applications whose pages are localized
dynamically, where the form's charset varies with the locale: it reads the charset the i18n actions saved in the session
when they served the form. And on Tomcat 10.1 and 11 the container already decodes parameters as UTF-8 when nothing else
is said (the stock `conf/web.xml`), which makes the action unnecessary for an all-UTF-8 application and turns an
ISO-8859-1 client into an HTTP 400 instead of silent garbage; declaring `<request-character-encoding>UTF-8` in the
application's own `web.xml` is the container-independent equivalent. The full ordering of encodings is on the
xref:web/jsp-struts/jsp/character-encoding.adoc[Character Encoding page].

[#security]
== Security: `fmt:message` Does Not Escape

Neither `fmt:message` nor `fmt:param` escape their output. The text of the bundle is trusted (the application's own),
but a parameter that comes from the request or the database is not, and it is written into the page as markup. A message
with the visitor's input as a parameter is therefore a cross-site scripting hole unless the parameter is escaped.

.Three ways to pass a request value as a parameter, `escape.jsp` with `?t=<script>alert(1)</script>`
[source,jsp]
----
<%@ taglib prefix="fn" uri="jakarta.tags.functions" %>
<p>1: <fmt:message key="shelf.summary"><fmt:param value="${param.t}"/><fmt:param value="x"/><fmt:param value="y"/></fmt:message></p>
<p>2: <fmt:message key="shelf.summary"><fmt:param value="${fn:escapeXml(param.t)}"/><fmt:param value="x"/><fmt:param value="y"/></fmt:message></p>
<p>3: <fmt:message key="shelf.summary"><fmt:param><c:out value="${param.t}"/></fmt:param><fmt:param value="x"/><fmt:param value="y"/></fmt:message></p>
<p>4: <fmt:message key="${param.k}"/></p>
----

[source,html]
----
<p>1: <script>alert(1)</script> was written by x in y</p>
<p>2: &lt;script&gt;alert(1)&lt;/script&gt; was written by x in y</p>
<p>3: &lt;script&gt;alert(1)&lt;/script&gt; was written by x in y</p>
<p>4: Search</p>
----

Line 1 is the vulnerability. Lines 2 and 3 fix it, with `fn:escapeXml` (a function, available since JSTL 1.1) or with a
`c:out` in the `fmt:param` body. The rule to apply uniformly is to escape every parameter that is not a constant, and
to escape the whole message when the bundle itself contains no markup and the message is used as an attribute value or
text. If a translated message legitimately contains markup, such as a link, keep that markup in the bundle and escape only
the parameters.

Line 4 is a different problem: the key came from the request, so a visitor can read any message of the bundle
(`form.search` was returned), which can reveal internal or unreleased text. Keys should be literals or come from the
application, never from a request parameter. The same applies to the `basename` of `fmt:bundle` and to a locale taken
from a parameter (see the table of `fmt:setLocale`).

Bundle files are application resources. They should live inside the classpath (`WEB-INF/classes` or a library), not in a
directory served by the container, and translations received from third parties are reviewed like code, because a
translation can contain markup and the tag does not escape it.

Source: https://jakarta.ee/specifications/tags/3.0/jakarta-tags-spec-3.0.html#fmtparam[Jakarta Standard Tag Library 3.0 -- 8.9 fmt:param]

Source: https://jakarta.ee/specifications/tags/3.0/jakarta-tags-spec-3.0.html#fmt:message[Jakarta Standard Tag Library 3.0 -- 8.8 fmt:message]

[#other-frameworks]
== The Same Idea in Spring and Struts

`fmt:message` is not the only way to reach a bundle from a JSP. Spring MVC resolves the locale with a `LocaleResolver`
(accept-header, cookie or session, plus an interceptor that reads a request parameter) and reads messages with a
`MessageSource`; its JSP tag library offers `spring:message` for the same job as `fmt:message`, and the two libraries can
coexist on a page. In Struts the bundles are resolved by the framework with a different search order, and the
xref:web/jsp-struts/struts/localization-and-i18n.adoc[Localization and i18n] page of the Struts part describes it. The point for a JSP author is that
the _concept_ (locale chosen per request, text by key, parameters by position) is the same in all of them, while the bundle
search algorithm and the way a locale is selected are specific to each.

Source: https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-servlet/localeresolver.html#mvc-localeresolver-session[Spring Framework Reference -- Locale Resolution]

Source: https://docs.spring.io/spring-framework/reference/web/webmvc-view/mvc-jsp.html#mvc-view-jsp-tags[Spring Framework Reference -- JSP and JSTL, the Spring tag library]

== Where the Books Are Outdated

_JSTL in Action_ (Manning, 2002, JSTL 1.0 on JSP 1.2) devotes a chapter to formatting and internationalization, and its
chapters on configuration and on control and performance touch the topic again. It is listed in the section
bibliography. The concepts it teaches (locale, bundle, basename, the localization context, `fmt:message` with parameters, the
fallback locale, `fmt:requestEncoding`, the `Config` settings) are the same today; the platform around them is not.

.JSP 1.2 and JSTL 1.0-era i18n material and its modern equivalent
[cols="3,4",options="header"]
|===
|The book's era |Today (Tags 3.0, Pages 4.0)

|`javax.servlet.jsp.jstl.fmt.*` configuration names and classes |`jakarta.servlet.jsp.jstl.fmt.*` (EE 9 and later)
|`http://java.sun.com/jstl/fmt` and the separate `fmt_rt` twin library for request-time attribute values |`jakarta.tags.fmt`; the container evaluates the Expression Language in every attribute, so there is one library and no `_rt` twin
|Attributes that accept only literal strings or JSTL-evaluated EL, with scriptlet expressions in the `_rt` twin |EL in every dynamic attribute; no scriptlets needed (and disabled in modern configuration with `scripting-invalid`)
|Setting the configuration names as plain scoped attributes of the page, a tempting shortcut |`fmt:setLocale`, `fmt:setBundle`, or `Config.set`; the plain-name attribute has no effect with the current implementation (observed)
|`.properties` bundles written with `\uXXXX` escapes and processed with `native2ascii` |UTF-8 files read natively since Java 9
|`MessageFormat` as the only tool for plurals and gender |Still the tool behind `fmt:param`; richer rules need ICU4J's `MessageFormat` or a framework
|`request.getParameter` and `new String(bytes, "ISO-8859-1")` re-decoding to fix form encoding |`fmt:requestEncoding`, `request-character-encoding` in `web.xml`, or a filter, so the container decodes correctly the first time
|Struts 1's `MessageResources` and `<bean:message>` or Struts 2's `getText()` and `s:text` as the way to localize |Still valid inside those frameworks; the xref:web/jsp-struts/struts/localization-and-i18n.adoc[Localization and i18n] page of the Struts part covers them
|Locale chosen by a servlet and passed to the page as a request attribute |Same idea, with `Config.set(session, Config.FMT_LOCALE, locale)` so that every `fmt:` action follows it
|The EE tutorial's JSP i18n material (J2EE 1.4, Java EE 5) |Archived; the current tutorial's i18n chapter is written for Jakarta Faces
|===
