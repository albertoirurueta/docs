[#what-a-tag-file-is]
== What a Tag File Is

A tag file is a source file with the extension `.tag` (JSP syntax) or `.tagx` (XML syntax) whose content is JSP: template
text, EL, standard and custom actions, and, if you insist, scriptlets. It differs from a JSP page in four ways. It is called
as a custom action, with attributes and an optional body. It has its own directives (`tag`, `attribute`, `variable`) instead of
`page`. It has two actions a page does not (`jsp:doBody` and `jsp:invoke`). And it has its own page scope, so nothing leaks in
or out unless the tag file declares it.

The specification leaves the implementation to the container: it may compile the file to a Java tag handler or interpret it,
as long as the observable behaviour is the same. Jasper in Tomcat 11 compiles each tag file to a class that extends
`jakarta.servlet.jsp.tagext.SimpleTagSupport`, which means a tag file is a *simple tag handler* whose `doTag` method contains
the translated body of the file. The generated source of `WEB-INF/tags/ui/button.tag` below was found in the work directory as
`org/apache/jsp/tag/web/ui/button_tag.java` (`public final class button_tag extends SimpleTagSupport implements
DynamicAttributes`), which is where to look when a tag file misbehaves; the build and the generated sources are described in
<<development>>.

.A tag file next to the other ways of sharing markup
[cols="2,3,3,3",options="header"]
|===
|Mechanism |What it shares |Parameters and body |Page scope

|`include` directive |Source text, merged at translation time |None, the including page's variables are visible |Same as the page
|`jsp:include` |The output of another resource, at request time |String parameters through `jsp:param` |Separate, a new request-level dispatch
|Tag file |Markup and logic, compiled into a tag handler |Typed attributes, fragments and a body, a declared set of variables out |Separate, with explicit synchronization
|Simple or classic tag handler in Java |Logic written in Java |Attributes and body, described by a TLD |Whatever the handler does
|Thymeleaf fragment or Tiles definition |Markup of another engine |See the other pages of this guide |Not JSP
|===

Source: https://jakarta.ee/specifications/pages/4.0/jakarta-server-pages-spec-4.0.html#tag-files[Jakarta Pages 4.0 -- Chapter 8 Tag Files]

Source: https://jakarta.ee/specifications/pages/4.0/jakarta-server-pages-spec-4.0.html#semantics-of-tag-files[Jakarta Pages 4.0 -- 8.3 Semantics of Tag Files]

Tag files are current and stable: they were added in JSP 2.0, gained deferred-expression attributes and `implicit.tld` in JSP
2.1, and the list of changes of the Pages 4.0 specification (Java 17 minimum) names nothing in their chapter. They are the right default for reusable markup
in a JSP application. They are not a good place for business logic or data access, and the Bookshelf follows that rule:
data comes from the servlet or a service, and a tag file only renders it.

[#location]
== Where Tag Files Live and How They Are Found

The container recognises tag files in exactly two places: a directory tree under `/WEB-INF/tags/` of the web application, or
a tree under `/META-INF/tags/` of a JAR in `/WEB-INF/lib/`. Only files with the extension `.tag` or `.tagx` count; the
recommended extension for a segment included into a tag file is `.tagf`, the counterpart of `.jspf`. A tag file anywhere
else is not a tag extension, and the container treats it as content to be served.

.Where tag files are recognised
[cols="2,3,3",options="header"]
|===
|Location |How the page imports it |Notes

|`/WEB-INF/tags/` and each subdirectory |`+<%@ taglib prefix="ui" tagdir="/WEB-INF/tags/ui" %>+` |An implicit tag library per directory, no descriptor needed. There is no relationship between a directory and its subdirectories.
|`+/META-INF/tags/...+` in a JAR under `/WEB-INF/lib/` |`+<%@ taglib prefix="bsui" uri="https://example.org/bookshelf/ui" %>+` |Needs a tag library descriptor with a `tag-file` element; a tag file in a JAR that no descriptor names is ignored.
|`+/WEB-INF/tags/...+` named from a descriptor |As any library, through its `uri` |A `tag-file` element in a web application's TLD may name a file under `/WEB-INF/tags`.
|Anywhere else (`/tags/leak.tag`) |Not importable |Served as plain content: see <<security>>.
|===

Source: https://jakarta.ee/specifications/pages/4.0/jakarta-server-pages-spec-4.0.html#location-of-tag-files[Jakarta Pages 4.0 -- 8.4.1 Location of Tag Files]

Source: https://jakarta.ee/specifications/pages/4.0/jakarta-server-pages-spec-4.0.html#packaging-directly-in-a-web-application[Jakarta Pages 4.0 -- 8.4.3 Packaging Directly in a Web Application]

[#implicit-library]
=== The implicit tag library of a directory

For every directory under `/WEB-INF/tags/` the container behaves as if a descriptor existed with a `tlib-version` of 1.0, a
`short-name` derived from the directory (the path below `/WEB-INF/tags/` with every `/` replaced by `-`, or `tags` for the
root), and one `tag-file` element per file whose `name` is the file name without `.tag` or `.tagx` and whose `path` is the
file's path from the web application root. Two consequences are worth remembering. The *name of the file is the name of the
tag*, so `bookCard.tag` is called `<ui:bookCard>` and `hello-world.tag` is called `<v:hello-world>` (a hyphen is allowed; a
space or a dot is not a good idea). And short names are not unique (`/WEB-INF/tags/a-b/` and `/WEB-INF/tags/a/b/` both give
`a-b`), which does not matter because the page chooses the prefix itself.

A `.tagf` segment is pulled into a tag file with the `include` directive. The example below also uses the file name with a
hyphen.

.WEB-INF/tags/versioned/hello-world.tag and parts.tag
[source,jsp]
----
<%@ tag body-content="empty" %>
<%@ taglib prefix="c" uri="jakarta.tags.core" %>
hello with a hyphen; ${pageContext.request.method}
----

[source,jsp]
----
<%@ tag body-content="empty" %>
<%@ include file="/WEB-INF/tags/versioned/footer.tagf" %>
----

.implicit.jsp
[source,jsp]
----
<%@ page contentType="text/plain; charset=UTF-8" %>
<%@ taglib prefix="v" tagdir="/WEB-INF/tags/versioned" %>
<v:hello-world/>
<v:parts/>
----

.Requesting implicit.jsp
[source,shell]
----
curl http://localhost:8080/g6tagfiles/implicit.jsp
----

[source,text]
----
hello with a hyphen; GET
included from a .tagf segment
----

Source: https://jakarta.ee/specifications/pages/4.0/jakarta-server-pages-spec-4.0.html#tag-files[Jakarta Pages 4.0 -- 8.1 Overview (.tagf)]

[#implicit-tld]
=== implicit.tld: the version of the library

The JSP version of an implicit library defaults to 2.0, which matters: the attributes introduced in JSP 2.1
(`deferredValue`, `deferredValueType`, `deferredMethod`, `deferredMethodSignature`) are a translation error in a tag file
whose library is still at version 2.0. A file named `implicit.tld` in the directory sets the library's `jsp-version` and
`tlib-version`; the container ignores its `short-name`, rejects any other element, and rejects a `jsp-version` below 2.0.
Both directories below hold the same `def.tag`; only the second has an `implicit.tld` with `jsp-version` 4.0.

.WEB-INF/tags/new/implicit.tld and def.tag (the directory old/ has def.tag only)
[source,xml]
----
<?xml version="1.0" encoding="UTF-8"?>
<taglib xmlns="https://jakarta.ee/xml/ns/jakartaee"
        xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
        xsi:schemaLocation="https://jakarta.ee/xml/ns/jakartaee https://jakarta.ee/xml/ns/jakartaee/web-jsptaglibrary_4_0.xsd"
        version="4.0">
  <tlib-version>2.3</tlib-version>
  <jsp-version>4.0</jsp-version>
</taglib>
----

[source,jsp]
----
<%@ attribute name="v" deferredValue="true" %>
deferred ok
----

Calling `+<t:def v="#{x}"/>+` from each directory gives:

[source,text]
----
old/ : org.apache.jasper.JasperException: Invalid JSP version defined for tag file at [/WEB-INF/tags/old/def.tag]
new/ : deferred ok
----

Source: https://jakarta.ee/specifications/pages/4.0/jakarta-server-pages-spec-4.0.html#packaging-directly-in-a-web-application[Jakarta Pages 4.0 -- 8.4.3 Packaging Directly in a Web Application (implicit.tld)]

Source: https://jakarta.ee/xml/ns/jakartaee/web-jsptaglibrary_4_0.xsd[Jakarta EE -- web-jsptaglibrary_4_0.xsd]

If a directory holds both `a.tag` and `a.tagx`, the specification says the library is invalid. Tomcat 11.0.26 does not
reject it: with a `sameName.tag` containing `FROM-TAG` and a `sameName.tagx` containing `FROM-TAGX`, the call printed
`FROM-TAG`. Do not rely on that.

[#first-tag-file]
== A First Tag File: the Rating

The smallest useful tag file in the Bookshelf prints a rating. It has no body, one required attribute and one line of
markup.

.WEB-INF/tags/ui/rating.tag
[source,jsp]
----
<%@ tag body-content="empty" pageEncoding="UTF-8" %>
<%@ attribute name="value" required="true" type="java.lang.Integer" %>
<span class="rating" title="${value} out of 5">${value} / 5</span>
----

.Calling it from a page
[source,jsp]
----
<%@ taglib prefix="ui" tagdir="/WEB-INF/tags/ui" %>
<ui:rating value="${book.rating}"/>
----

[source,html]
----
<span class="rating" title="5 out of 5">5 / 5</span>
----

Three things happened. The `taglib` directive with `tagdir` made every tag file of the directory available under the prefix
`ui`. The `attribute` directive declared `value`, so the call is checked when the page is translated, not when it runs: a
missing `value` or an unknown attribute stops the translation. And inside the tag file the attribute is a *page-scoped
variable* named `value`, so `+${value}+` finds it with the normal EL search.

[source,text]
----
org.apache.jasper.JasperException: /bad/missing-attr.jsp (line: [2], column: [0]) According to the TLD or the tag file, attribute [label] is mandatory for tag [emptyTag]
org.apache.jasper.JasperException: /bad/unknown-attr.jsp (line: [2], column: [0]) Attribute [other] invalid for tag [emptyTag] according to TLD
----

Source: https://jakarta.ee/specifications/pages/4.0/jakarta-server-pages-spec-4.0.html#syntax-of-tag-files[Jakarta Pages 4.0 -- 8.2 Syntax of Tag Files]

Source: https://jakarta.ee/specifications/pages/4.0/jakarta-server-pages-spec-4.0.html#the-attribute-directive[Jakarta Pages 4.0 -- 8.5.2 The attribute Directive]

[#directives]
== The Directives of a Tag File

Table JSP.8-1 of the specification lists which directives a tag file may use: `taglib` and `include` behave as in a page,
`tag`, `attribute` and `variable` exist only in tag files (using them in a JSP is a translation error), and `page` is not
allowed in a tag file. The errors are:

[source,text]
----
/bad/tag-directive-in-jsp.jsp (line: [1], column: [8]) [<%@ tag] directive can only be used in a tag file
/bad/attr-directive-in-jsp.jsp (line: [1], column: [14]) [<%@ attribute] directive can only be used in a tag file
/WEB-INF/tags/bad/usesPage.tag (line: [1], column: [9]) [<%@ page] directive cannot be used in a tag file
----

Source: https://jakarta.ee/specifications/pages/4.0/jakarta-server-pages-spec-4.0.html#tag-file-directives[Jakarta Pages 4.0 -- 8.5 Tag File Directives]

[#tag-directive]
=== The tag directive

The `tag` directive describes the tag as a whole and is the tag file's counterpart of the `page` directive: it may appear
more than once, its attributes apply to the whole file, a duplicate attribute with a different value is a translation error,
and an unrecognised attribute is a translation error.

.The attributes of the tag directive (Table JSP.8-2)
[cols="2,2,4",options="header"]
|===
|Attribute |Default |Meaning

|`display-name` |File name without extension |Short name for tools.
|`body-content` |`scriptless` |`empty`, `tagdependent` or `scriptless`. Any other value, including `JSP`, is a translation error.
|`dynamic-attributes` |none |Names a page-scoped variable that receives a `Map` of the dynamic attributes; the tag handler then implements `DynamicAttributes`. See <<dynamic-attributes>>.
|`small-icon`, `large-icon` |none |Paths of images for tools.
|`description`, `example` |none |Free text for tools.
|`language` |`java` |As in the `page` directive.
|`import` |none |As in the `page` directive; repeated uses accumulate.
|`pageEncoding` |as for pages |As in the `page` directive, with no `web.xml` counterpart; not allowed in a `.tagx`.
|`isELIgnored` |as for pages |As in the `page` directive; no property-group default applies to tag files.
|`errorOnELNotFound` |as for pages |As in the `page` directive; no `web.xml` counterpart.
|`deferredSyntaxAllowedAsLiteral` |as for pages |As in the `page` directive; an error in a tag file of a library below JSP 2.1 by the specification (Tomcat 11.0.26 did not enforce that).
|`trimDirectiveWhitespaces` |as for pages |As in the `page` directive; see the whitespace pitfall in <<dynamic-attributes>>.
|===

Source: https://jakarta.ee/specifications/pages/4.0/jakarta-server-pages-spec-4.0.html#the-tag-directive[Jakarta Pages 4.0 -- 8.5.1 The tag Directive]

A tag file is not governed by `jsp-property-group` elements of `web.xml`: the table says that `isELIgnored`,
`errorOnELNotFound`, `pageEncoding`, `deferredSyntaxAllowedAsLiteral` and `trimDirectiveWhitespaces` have no global
counterpart for tag files, as the xref:web/jsp-struts/jsp/configuration-and-property-groups.adoc[configuration page]
explains. The tag file has to say it itself.

.A tag directive with a description, an empty body and an explicit trim
[source,jsp]
----
<%@ tag description="A small star rating" body-content="empty" trimDirectiveWhitespaces="true" %>
----

An invalid `body-content` fails when a page that uses the tag is translated:

[source,text]
----

----

[#attribute-directive]
=== The attribute directive

The `attribute` directive is the tag file's counterpart of the `attribute` element of a descriptor. Each attribute of the tag
is declared once; the declaration controls whether it is required, whether it accepts expressions, its Java type, and whether
it is a fragment.

.The attributes of the attribute directive (Table JSP.8-3)
[cols="2,2,4",options="header"]
|===
|Attribute |Default |Meaning

|`name` |required |The attribute's name. Declaring the same name twice, or using the name of a `variable` directive's `name-given` or of `dynamic-attributes`, is a translation error.
|`required` |`false` |Whether the caller must pass it.
|`fragment` |`false` |`true` makes the attribute a `JspFragment`; the type is then fixed and a `type` is an error, and `rtexprvalue` is fixed at `true`.
|`rtexprvalue` |`true` |Whether the value may be an expression. Unlike the descriptor element, this defaults to `true`. `false` makes it a translation-time constant.
|`type` |`java.lang.String` |The Java type of the value. A primitive type is an error by the specification.
|`description` |none |Free text.
|`deferredValue` |`false`, `true` if `deferredValueType` is set |The attribute is a deferred value expression (`+#{...}+`); needs library version 2.1 or later.
|`deferredValueType` |`java.lang.Object` when `deferredValue` |The expected type of the expression result.
|`deferredMethod` |`false`, `true` if `deferredMethodSignature` is set |The attribute is a deferred method expression.
|`deferredMethodSignature` |`void methodname()` |The signature of the method.
|===

Source: https://jakarta.ee/specifications/pages/4.0/jakarta-server-pages-spec-4.0.html#the-attribute-directive[Jakarta Pages 4.0 -- 8.5.2 The attribute Directive]

The Bookshelf's book card shows the usual declarations: a required attribute with a record type, an optional boolean, and a
body.

.WEB-INF/tags/ui/bookCard.tag
[source,jsp]
----
<%@ tag description="One book as a card" body-content="scriptless" trimDirectiveWhitespaces="true" %>
<%@ taglib prefix="c" uri="jakarta.tags.core" %>
<%@ taglib prefix="ui" tagdir="/WEB-INF/tags/ui" %>
<%@ attribute name="book" required="true" type="org.example.bookshelf.Book" description="The book to show" %>
<%@ attribute name="highlight" type="java.lang.Boolean" description="Adds the featured class" %>
<article class="card${highlight ? ' featured' : ''}" id="book-${book.id}">
  <h2><c:out value="${book.title}"/></h2>
  <p><c:out value="${book.author}"/> (${book.year}) <ui:rating value="${book.rating}"/></p>
  <div class="actions"><jsp:doBody/></div>
</article>
----

Source: https://jakarta.ee/specifications/pages/4.0/jakarta-server-pages-spec-4.0.html#syntax-of-tag-files[Jakarta Pages 4.0 -- 8.2 Syntax of Tag Files]

Note that the tag file declares its own `taglib` directives: the `c` and `ui` prefixes of the calling page are *not*
inherited. Without a `taglib` for `c`, a line such as `<c:out value="hello"/>` in the tag file is not an error: it is
copied to the output as template text.

[source,html]
----
<c:out value="hello"/>
----

[#attribute-values]
=== How attribute values reach the tag file

An attribute that is not declared as a fragment or as a deferred expression becomes a page-scoped variable of the tag file
with the same name, set to the value passed in. An optional attribute that was not passed creates no variable, so EL sees
`null`. The value is converted to the declared `type` by the same rules as any attribute of a custom action, so passing a
string to an `Integer` attribute converts it and a bad string fails at run time:

.WEB-INF/tags/bad/typed.tag and its calls
[source,jsp]
----
<%@ attribute name="n" type="java.lang.Integer" %>
n=${n + 1}
----

[source,jsp]
----
<b:typed n="41"/>
<b:typed n="abc"/>
----

[source,text]
----
n=42
java.lang.NumberFormatException: For input string: "abc"
----

Source: https://jakarta.ee/specifications/pages/4.0/jakarta-server-pages-spec-4.0.html#semantics-of-tag-files[Jakarta Pages 4.0 -- 8.3 Semantics of Tag Files]

Source: https://jakarta.ee/specifications/pages/4.0/jakarta-server-pages-spec-4.0.html#the-attribute-directive[Jakarta Pages 4.0 -- 8.5.2 The attribute Directive]

[#body]
== The Body: scriptless, tagdependent, empty and jsp:doBody

The `body-content` of the `tag` directive says what the caller may put between the start and end tags.

.The three body contents of a tag file
[cols="2,4,4",options="header"]
|===
|Value |What the caller may write |What the tag file sees

|`scriptless` (default) |Template text, EL, standard and custom actions; no scriptlets, declarations or scripting expressions |A `JspFragment` that `jsp:doBody` evaluates, in the caller's page scope.
|`tagdependent` |Anything; the container does not interpret it |The body as text; `jsp:doBody` copies it unchanged, so EL in it is not evaluated.
|`empty` |Nothing |No body; a body in the call is a translation error.
|===

Source: https://jakarta.ee/specifications/pages/4.0/jakarta-server-pages-spec-4.0.html#the-tag-directive[Jakarta Pages 4.0 -- 8.5.1 The tag Directive]

[#dobody]
=== jsp:doBody

`jsp:doBody` is available only in tag files (in a page it is a translation error). It runs the body of the call and sends its
output to the current `JspWriter`, or captures it. The body is a `JspFragment` evaluated in the page scope of the *caller*, which
is why a body written in a page sees the page's variables but not the tag file's.

.Attributes of jsp:doBody (Table JSP.5-8)
[cols="2,2,5",options="header"]
|===
|Attribute |Default |Meaning

|`var` |none |Name of a scoped attribute that receives the output as a `String`. Cannot be combined with `varReader`.
|`varReader` |none |Name of a scoped attribute that receives the output as a resettable `java.io.Reader`.
|`scope` |`page` |`page`, `request`, `session` or `application`; an error without `var` or `varReader`. A `session` scope throws `IllegalStateException` at run time when the page has no session.
|===

If the call had no body, `jsp:doBody` behaves as if it had an empty one. An element with a non-empty body is a translation
error.

Source: https://jakarta.ee/specifications/pages/4.0/jakarta-server-pages-spec-4.0.html#jspdobody[Jakarta Pages 4.0 -- 5.10 jsp:doBody]

Capturing the body is how a tag transforms it. The `shout` tag upper-cases whatever its caller wrote, using a JSTL function.

.WEB-INF/tags/ui/shout.tag, raw.tag and the page that uses them
[source,jsp]
----
<%@ tag body-content="scriptless" trimDirectiveWhitespaces="true" %>
<%@ taglib prefix="fn" uri="jakarta.tags.functions" %>
<jsp:doBody var="text"/>${fn:toUpperCase(text)}
----

[source,jsp]
----
<%@ tag body-content="tagdependent" trimDirectiveWhitespaces="true" %>
<pre><jsp:doBody/></pre>
----

[source,jsp]
----
<layout:page title="About" active="about">
  <p>A tiny catalogue. <ui:shout>loud</ui:shout></p>
  <ui:note level="warn">Beta &amp; <b>bold</b></ui:note>
  <ui:raw>${notEvaluated} <b>x</b></ui:raw>
</layout:page>
----

The relevant lines of the response of `about.jsp`:

[source,html]
----
<p>A tiny catalogue. LOUD</p>
<div class="note warn">Beta &amp; <b>bold</b></div>
<pre>${notEvaluated} <b>x</b></pre>
----

Source: https://jakarta.ee/specifications/pages/4.0/jakarta-server-pages-spec-4.0.html#jspdobody[Jakarta Pages 4.0 -- 5.10 jsp:doBody]

A `scriptless` body that contains a scriptlet is rejected, and a body in a call to an `empty` tag is too:

[source,text]
----
org.apache.jasper.JasperException: /bad/empty-body.jsp (line: [2], column: 0) According to TLD, tag [b:emptyTag] must be empty, but is not
----

[#fragments]
== Fragments: jsp:attribute, jsp:body and jsp:invoke

A *fragment* is a piece of JSP code, written by the caller, that the tag file can run zero or more times. The body of a tag
is one; a tag can also receive named fragments through attributes declared with `fragment="true"`. The caller writes a
fragment attribute as a `jsp:attribute` child element, and when it does, the body has to be written inside `jsp:body`: the
text between the tags may not contain anything else.

.A call with named fragments and an explicit body
[source,jsp]
----
<layout:page title="Catalogue" active="catalogue">
  <jsp:attribute name="head"><link rel="stylesheet" href="${pageContext.request.contextPath}/bookshelf.css"></jsp:attribute>
  <jsp:attribute name="sidebar"><p>Sidebar for ${books.size()} books</p></jsp:attribute>
  <jsp:body>
    <p>The body of the page.</p>
  </jsp:body>
</layout:page>
----

Source: https://jakarta.ee/specifications/pages/4.0/jakarta-server-pages-spec-4.0.html#jsp:attribute[Jakarta Pages 4.0 -- 5.7 jsp:attribute]

The mistake is to mix the two styles. With `jsp:attribute` present, text outside `jsp:body` is rejected:

[source,jsp]
----
<layout:page title="x">
  <jsp:attribute name="head"><meta name="x" content="y"></jsp:attribute>
  some text outside jsp:body
</layout:page>
----

[source,text]
----
org.apache.jasper.JasperException: /bad/mixed-body.jsp (line: [4], column: [2]) Must use jsp:body to specify tag body for [<layout:page] if jsp:attribute is used.
----

Source: https://jakarta.ee/specifications/pages/4.0/jakarta-server-pages-spec-4.0.html#jsp:body[Jakarta Pages 4.0 -- 5.8 jsp:body]

[#invoke]
=== jsp:invoke

`jsp:invoke` runs a named fragment attribute, in tag files only. It takes the name of the attribute in `fragment` and the same
`var`, `varReader` and `scope` attributes as `jsp:doBody`. A fragment that the caller did not pass is `null`, and the
specification says `jsp:invoke` then behaves as if the fragment produced no output, which is why an optional `head` or
`sidebar` needs no test. The action must have no body.

.Attributes of jsp:invoke (Table JSP.5-7)
[cols="2,2,5",options="header"]
|===
|Attribute |Default |Meaning

|`fragment` |required |The name of the fragment attribute.
|`var`, `varReader`, `scope` |as for `jsp:doBody` |Capture the output as a `String` or a `Reader` in a scoped attribute instead of writing it.
|===

Source: https://jakarta.ee/specifications/pages/4.0/jakarta-server-pages-spec-4.0.html#jspinvoke[Jakarta Pages 4.0 -- 5.9 jsp:invoke]

Source: https://jakarta.ee/specifications/pages/4.0/jakarta-server-pages-spec-4.0.html#storing-fragment-output[Jakarta Pages 4.0 -- 5.9.2 Storing Fragment Output]

The tabs tag below invokes a required fragment directly, captures an optional one with `var`, and declares a `NESTED`
variable so that each fragment knows which tab it is in. Naming an attribute that is not a fragment in `jsp:invoke` is not
detected by the translator: the generated class fails to compile with `The method invoke(Writer) is undefined for the type
String`.

.WEB-INF/tags/ui/tabs.tag and tabs.jsp
[source,jsp]
----
<%@ tag body-content="empty" trimDirectiveWhitespaces="true" %>
<%@ attribute name="first" fragment="true" required="true" %>
<%@ attribute name="second" fragment="true" %>
<%@ variable name-given="tabNo" variable-class="java.lang.Integer" scope="NESTED" %>
<%@ taglib prefix="c" uri="jakarta.tags.core" %>
<c:set var="tabNo" value="1"/>
<section class="tab"><jsp:invoke fragment="first"/></section>
<c:set var="tabNo" value="2"/>
<jsp:invoke fragment="second" var="secondHtml"/>
<c:if test="${not empty secondHtml}"><section class="tab">${secondHtml}</section></c:if>
----

[source,jsp]
----
<%@ taglib prefix="ui" tagdir="/WEB-INF/tags/ui" %>
<ui:tabs>
  <jsp:attribute name="first">first sees tab ${tabNo}</jsp:attribute>
  <jsp:attribute name="second">second sees tab ${tabNo}</jsp:attribute>
</ui:tabs>
----

[source,html]
----
<section class="tab">first sees tab 1</section>
<section class="tab">second sees tab 2</section>
----

Leaving out the required fragment is caught at translation time, as for any attribute:

[source,text]
----
org.apache.jasper.JasperException: /bad/missing-fragment.jsp (line: [2], column: [0]) According to the TLD or the tag file, attribute [first] is mandatory for tag [tabs]
----

Source: https://jakarta.ee/specifications/pages/4.0/jakarta-server-pages-spec-4.0.html#providing-a-fragment-access-to-variables[Jakarta Pages 4.0 -- 5.9.3 Providing a Fragment Access to Variables]

The fragment is an object (`jakarta.servlet.jsp.tagext.JspFragment`) whose single method `invoke(Writer)` writes the output
to the given writer, or to the `JspWriter` of the fragment's context when the writer is `null`.

Source: https://jakarta.ee/specifications/pages/4.0/apidocs/jakarta.servlet.jsp/jakarta/servlet/jsp/tagext/JspFragment.html#invoke(java.io.Writer)[Jakarta Pages 4.0 API -- JspFragment.invoke(Writer)]

[#variables]
== Variables: the variable Directive and Synchronization

A tag file exchanges values with its caller in two ways. *IN parameters* are attributes: a copy of the value is placed in the
tag's page scope and nothing is written back. *OUT parameters* are variables declared with the `variable` directive: a
page-scoped variable of the tag file that the container copies to (or from) the calling page's page scope at defined
moments.

.The attributes of the variable directive (Table JSP.8-4)
[cols="2,2,5",options="header"]
|===
|Attribute |Default |Meaning

|`name-given` |one of the two |The fixed name of the variable in the caller and in the tag file.
|`name-from-attribute` |one of the two |The name of an attribute whose value (a translation-time constant) is the variable's name in the caller. That attribute must be a `String`, `required` and not an `rtexprvalue`. Needs `alias`.
|`alias` |required with `name-from-attribute` |The local name in the tag file, for a variable whose name the caller chooses.
|`variable-class` |`java.lang.String` |The class of the variable.
|`declare` |`true` |Whether a scripting variable is declared in the calling page after the tag.
|`scope` |`NESTED` |`AT_BEGIN`, `AT_END` or `NESTED`.
|`description` |none |Free text.
|===

Source: https://jakarta.ee/specifications/pages/4.0/jakarta-server-pages-spec-4.0.html#the-variable-directive[Jakarta Pages 4.0 -- 8.5.3 The variable Directive]

The scope decides when the value crosses the boundary. In the table, "tag to page" means: if the variable exists in the tag
file, create or update it in the caller; if it does not, remove it from the caller.

.Variable synchronization behaviour (Table JSP.8-6)
[cols="3,2,2,2",options="header"]
|===
|Moment |AT_BEGIN |NESTED |AT_END

|Beginning of the tag file |nothing |save the caller's value |nothing
|Before any fragment (a body or a fragment attribute) |tag to page |tag to page |nothing
|After any fragment |nothing |nothing |nothing
|End of the tag file |tag to page |restore the caller's value |tag to page
|===

Source: https://jakarta.ee/specifications/pages/4.0/jakarta-server-pages-spec-4.0.html#synchronization-points[Jakarta Pages 4.0 -- 8.9.1 Synchronization Points]

In practice: `NESTED` is a loop variable, visible only in the body and gone afterwards; `AT_BEGIN` is visible in the body and
after the tag; `AT_END` is a result visible only after the tag. The three tag files below set `x` to 2, run the body, set `x`
to 4, and each prints the value of `x` before and after the body. The page sets `x` to 1 and the body sets it to 3. The page
and the output are the ones of the specification's examples, run on Tomcat 11.0.26.

.WEB-INF/tags/sync/atbegin.tag (nested.tag and atend.tag differ only in the scope)
[source,jsp]
----
<%@ variable name-given="x" scope="AT_BEGIN" %>
<%@ taglib prefix="c" uri="jakarta.tags.core" %>
inside before: [${x}]
<c:set var="x" value="2"/>
<jsp:doBody/>
inside after: [${x}]
<c:set var="x" value="4"/>
----

Source: https://jakarta.ee/specifications/pages/4.0/jakarta-server-pages-spec-4.0.html#example-of-at_begin[Jakarta Pages 4.0 -- 8.9.2.1 Example of AT_BEGIN]

.sync.jsp (the three blocks repeat the same body with s:atbegin, s:nested and s:atend)
[source,jsp]
----
<%@ page contentType="text/plain; charset=UTF-8" %>
<%@ taglib prefix="c" uri="jakarta.tags.core" %>
<%@ taglib prefix="s" tagdir="/WEB-INF/tags/sync" %>
<c:set var="x" value="1"/>
before: [${x}]
<s:atbegin>
  in body: [${x}]
  <c:set var="x" value="3"/>
</s:atbegin>
after: [${x}]
----

Source: https://jakarta.ee/specifications/pages/4.0/jakarta-server-pages-spec-4.0.html#example-of-nested[Jakarta Pages 4.0 -- 8.9.2.3 Example of NESTED]

Source: https://jakarta.ee/specifications/pages/4.0/jakarta-server-pages-spec-4.0.html#example-of-at_end[Jakarta Pages 4.0 -- 8.9.2.4 Example of AT_END]

.Output of the three scopes
[source,text]
----
== AT_BEGIN
before: [1]
inside before: []
  in body: [2]
inside after: [2]
after: [4]
== NESTED
before: [1]
inside before: []
  in body: [2]
inside after: [2]
after: [1]
== AT_END
before: [1]
inside before: []
  in body: [1]
inside after: [2]
after: [4]
----

Source: https://jakarta.ee/specifications/pages/4.0/jakarta-server-pages-spec-4.0.html#synchronization-examples[Jakarta Pages 4.0 -- 8.9.2 Synchronization Examples]

Read the output once, slowly. In `AT_BEGIN` the body sees the tag's `x` (2) because the value is copied before the body, and
the page sees the tag's final value (4) at the end. In `NESTED` the body sees 2 too, but after the tag the page's own `x` (1)
is back. In `AT_END` the body still sees the page's `x` (1); only after the tag does the page see 4. The body's own `<c:set
var="x" value="3"/>` (the "3") is never copied back in any scope: the value flows from the tag file to the page, not the other
way.

A fourth example from the specification shows that the synchronization can remove a variable: a `NESTED` variable that the tag
file sets, calls the body, removes with `c:remove`, and calls the body again.

.WEB-INF/tags/sync/remove.tag
[source,jsp]
----
<%@ variable name-given="x" scope="NESTED" %>
<%@ taglib prefix="c" uri="jakarta.tags.core" %>
<c:set var="x" value="1"/>
<jsp:doBody/>
<c:remove var="x"/>
<jsp:doBody/>
----

Called as `+<s:remove>'${x}'</s:remove>+` after `x` was set to 2, the output is `2`, `+'1'+`, `+''+` and `2` again: the body saw 1,
then nothing (the variable was removed from the caller), and the page's own 2 returned at the end.

Source: https://jakarta.ee/specifications/pages/4.0/jakarta-server-pages-spec-4.0.html#example-of-removing-parameters[Jakarta Pages 4.0 -- 8.9.2.5 Example of Removing Parameters]

[#name-from-attribute]
=== A variable whose name the caller chooses: each

JSTL's `c:forEach` takes `var` and `varStatus` as attribute names; a tag file does the same with `name-from-attribute` and
`alias`. The `each` tag repeats its body for every element of a collection and exposes the element and its index as `NESTED`
variables with the names the caller picked.

.WEB-INF/tags/ui/each.tag
[source,jsp]
----
<%@ tag description="Repeats the body for every element" body-content="scriptless" %>
<%@ attribute name="items" required="true" type="java.util.Collection" %>
<%@ attribute name="var" required="true" rtexprvalue="false" description="Name of the current element" %>
<%@ attribute name="varIndex" required="true" rtexprvalue="false" description="Name of the zero-based index" %>
<%@ variable name-from-attribute="var" alias="current" variable-class="java.lang.Object" scope="NESTED" %>
<%@ variable name-from-attribute="varIndex" alias="position" variable-class="java.lang.Integer" scope="NESTED" %>
<%@ taglib prefix="c" uri="jakarta.tags.core" %>
<c:forEach var="item" items="${items}" varStatus="st">
  <c:set var="current" value="${item}"/>
  <c:set var="position" value="${st.index}"/>
  <jsp:doBody/>
</c:forEach>
----

.Using it
[source,jsp]
----
<ui:each items="${books}" var="b" varIndex="i">
  <ui:bookCard book="${b}" highlight="${i == 0}">
    <ui:button kind="submit" class="borrow" data-id="${b.id}">Borrow</ui:button>
  </ui:bookCard>
</ui:each>
----

Inside the tag file the code uses the fixed names `current` and `position`; in the page the same values are `b` and `i`. The
attribute behind `name-from-attribute` must be `required` and not an `rtexprvalue`: leaving `required="true"` out of
`varIndex` makes Tomcat refuse the library.

[source,text]
----
org.apache.jasper.JasperException: /WEB-INF/tags/ui/each.tag (line: [6], column: [1]) The attribute directive declared at line [4] with name [varIndex] that matches the name-from-attribute value of this variable directive must be of type java.lang.String, must be "required" and must not be a "rtexprvalue".
----

Source: https://jakarta.ee/specifications/pages/4.0/jakarta-server-pages-spec-4.0.html#example-of-at_begin-and-name-from-attribute[Jakarta Pages 4.0 -- 8.9.2.2 Example of AT_BEGIN and name-from-attribute]

An `AT_END` variable gives a tag a result, the way `c:set` does for `var`. The `summary` tag computes a text from a collection
and hands it back under the name the page asks for:

.WEB-INF/tags/ui/summary.tag and its use
[source,jsp]
----
<%@ tag body-content="empty" %>
<%@ attribute name="items" required="true" type="java.util.Collection" %>
<%@ attribute name="var" required="true" rtexprvalue="false" %>
<%@ variable name-from-attribute="var" alias="result" variable-class="java.lang.String" scope="AT_END" %>
<%@ taglib prefix="c" uri="jakarta.tags.core" %>
<c:set var="result" value="${items.size()} book(s)"/>
----

[source,jsp]
----
<ui:summary items="${books}" var="total"/>
<p>${total}</p>
----

[source,html]
----
<p>3 book(s)</p>
----

Source: https://jakarta.ee/specifications/pages/4.0/jakarta-server-pages-spec-4.0.html#the-variable-directive[Jakarta Pages 4.0 -- 8.5.3 The variable Directive]

[#isolation]
== Page Scope, Implicit Objects and EL Inside a Tag File

Every call of a tag file gets a *clean page scope*: it holds the declared attributes and nothing else. The request, session
and application scopes are the caller's own, and a change to them is visible to the caller. A change to the page scope is not
visible, except through a `variable`. The tag's context object (the "JSP context wrapper") is what `getJspContext()` returns, and
it is a `PageContext` when the caller's context is one.

.The implicit objects of a tag file (Table JSP.8-5)
[cols="2,3,4",options="header"]
|===
|Variable |Type |Notes

|`request` |`ServletRequest` subtype, e.g. `HttpServletRequest` |The request, request scope.
|`response` |`ServletResponse` subtype |The response.
|`jspContext` |`jakarta.servlet.jsp.JspContext` |The context of the tag file; replaces `pageContext`.
|`session` |`HttpSession` |HTTP only; session scope.
|`application` |`ServletContext` |Application scope.
|`out` |`JspWriter` |Writes to the output.
|`config` |`ServletConfig` |
|===

Source: https://jakarta.ee/specifications/pages/4.0/jakarta-server-pages-spec-4.0.html#implicit-objects-2[Jakarta Pages 4.0 -- 8.8 Implicit Objects]

These are scripting variables, available in scriptlets and scripting expressions of the tag file. They are *not* EL
identifiers: the EL implicit objects (`pageContext`, `param`, `requestScope`...) are those of the xref:web/jsp-struts/jsp/implicit-objects-and-scopes.adoc[implicit objects page]. The tag file below prints values from both worlds.

.WEB-INF/tags/bad/pageScope.tag
[source,jsp]
----
<%@ taglib prefix="c" uri="jakarta.tags.core" %>
caller page var: [${pageScope.callerVar}] request var: [${requestScope.reqVar}]
jspContext: ${jspContext.getClass().getSimpleName()}
request: ${request.method} contextPath=${pageContext.request.contextPath}
<c:set var="leak" value="from the tag"/>
----

.The page that calls it
[source,jsp]
----
<%@ page session="false" %>
<%@ taglib prefix="b" tagdir="/WEB-INF/tags/bad" %>
<%@ taglib prefix="c" uri="jakarta.tags.core" %>
<c:set var="callerVar" value="in the page" scope="page"/>
<c:set var="reqVar" value="in the request" scope="request"/>
<b:pageScope/>
after the tag, leak=[${leak}] callerVar=[${callerVar}]
----

[source,text]
----
caller page var: [] request var: [in the request]
jspContext:
request:  contextPath=/g6tagfiles
after the tag, leak=[] callerVar=[in the page]
----

The result confirms four things. The tag file does not see the caller's page-scoped variable; it sees the request-scoped one.
`+${jspContext...}+` and `+${request.method}+` are empty, because they are scripting variables and not EL names (a missing EL
variable is not an error unless `errorOnELNotFound` is on). `+${pageContext.request.contextPath}+` works: EL's
`pageContext` is available in a tag file. And what the tag stores in its own page scope (`leak`) is gone
once the tag ends.

Source: https://jakarta.ee/specifications/pages/4.0/jakarta-server-pages-spec-4.0.html#semantics-of-tag-files[Jakarta Pages 4.0 -- 8.3 Semantics of Tag Files]

A tag file can contain scriptlets, even though its callers' bodies cannot (`body-content="scriptless"` governs the caller's
body). A `<% out.print("scriptlet"); %>` in `bad/scriptlet.tag` printed `scriptlet`. Property groups,
including `scripting-invalid`, never apply to tag files (see the xref:web/jsp-struts/jsp/configuration-and-property-groups.adoc[configuration page]),
so a project that bans scriptlets should also search `WEB-INF/tags` for `<%` in code review.

[#dynamic-attributes]
== Dynamic Attributes

The `dynamic-attributes` attribute of the `tag` directive turns on the acceptance of attributes the tag did not declare. It
names a page-scoped variable that receives a `Map` of names to values; the generated handler implements
`jakarta.servlet.jsp.tagext.DynamicAttributes`, and the container must not reject any name. Only attributes without a
namespace URI are in the map.

.WEB-INF/tags/ui/button.tag
[source,jsp]
----
<%@ tag body-content="scriptless" dynamic-attributes="extra" %>
<%@ taglib prefix="c" uri="jakarta.tags.core" %>
<%@ attribute name="kind" %>
<button type="${empty kind ? 'button' : kind}"<c:forEach var="a" items="${extra}"> ${a.key}="<c:out value='${a.value}'/>"</c:forEach>><jsp:doBody/></button>
----

[source,jsp]
----
<ui:button kind="submit" class="borrow" data-id="7">Borrow</ui:button>
----

[source,html]
----
<button type="submit" data-id="7" class="borrow">Borrow</button>
----

The map is a hash map, so the order of `data-id` and `class` is not the order written. The values are escaped with `c:out`:
a dynamic attribute is request data the moment it comes from an expression.

Source: https://jakarta.ee/specifications/pages/4.0/jakarta-server-pages-spec-4.0.html#dynamic-attribute[Jakarta Pages 4.0 -- Dynamic attributes]

Source: https://jakarta.ee/specifications/pages/4.0/apidocs/jakarta.servlet.jsp/jakarta/servlet/jsp/tagext/DynamicAttributes.html#setDynamicAttribute(java.lang.String,java.lang.String,java.lang.Object)[Jakarta Pages 4.0 API -- DynamicAttributes.setDynamicAttribute]

A tag that does not declare `dynamic-attributes` is strict: `<ui:rating value="1" extra="no"/>` stops the translation with
`+Attribute [extra] invalid for tag [rating] according to TLD+`.

[#trim]
=== trimDirectiveWhitespaces can eat the space you need

With `trimDirectiveWhitespaces="true"` the container removes template text that consists only of whitespace. In the button
tag the text before `+${a.key}+` is a single space, and an expression splits the template text into pieces, so the space is a
whitespace-only piece and is removed. The output of the same tag with the directive set to `true`:

[source,html]
----
<button type="submit"data-id="7"class="borrow">Borrow</button>
----

That is invalid HTML attribute spacing that browsers tolerate unpredictably. Either leave the directive out for such a tag,
or write the space as an expression or entity that is not whitespace-only template text.

Source: https://jakarta.ee/specifications/pages/4.0/jakarta-server-pages-spec-4.0.html#removing-whitespaces-from-template-text[Jakarta Pages 4.0 -- Removing whitespaces from template text]

[#tagx]
== Tag Files in XML Syntax

A tag file whose extension is `.tagx` is in XML syntax, like a JSP document: it must be well formed, the `jsp:root` element may
be present (in a `.tag` it may not), directives become `jsp:directive.tag`, `jsp:directive.attribute` and
`jsp:directive.variable`, and the default is *not* to generate an XML declaration. A `pageEncoding` attribute in the `tag`
directive of a `.tagx` is an error: the encoding follows the XML rules. If `jsp:root` carries a `version`, it must match the tag
file's JSP version. The xref:web/jsp-struts/jsp/jsp-documents-xml-syntax.adoc[JSP documents page] covers the XML syntax in
general.

.WEB-INF/tags/ui/note.tagx
[source,xml]
----
<jsp:root xmlns:jsp="http://java.sun.com/JSP/Page" xmlns:c="jakarta.tags.core" version="4.0">
  <jsp:directive.tag body-content="scriptless" description="A note box in XML syntax"/>
  <jsp:directive.attribute name="level" required="false"/>
  <div class="note ${empty level ? 'info' : level}"><jsp:doBody/></div>
</jsp:root>
----

It is called like any other tag; the call `<ui:note level="warn">Beta &amp; <b>bold</b></ui:note>` gives
`<div class="note warn">Beta &amp; <b>bold</b></div>`. The XML view of a tag file, the form passed to tag library
validators, is built the same way as for a page.

Source: https://jakarta.ee/specifications/pages/4.0/jakarta-server-pages-spec-4.0.html#tag-files-in-xml-syntax[Jakarta Pages 4.0 -- 8.6 Tag Files in XML Syntax]

Source: https://jakarta.ee/specifications/pages/4.0/jakarta-server-pages-spec-4.0.html#xml-view-of-a-tag-file[Jakarta Pages 4.0 -- 8.7 XML View of a Tag File]

[#jar]
== Packaging Tag Files in a JAR

To reuse tag files across applications, put them in a JAR under `/META-INF/tags/` and describe them in a tag library
descriptor in the same JAR. A tag file in a JAR that no descriptor lists is ignored. The descriptor's `tag-file` element has a
`name` and a `path`, which must start with `/META-INF/tags`; other elements of the element override the defaults of the file's
`tag` directive. A library can mix `tag` (Java) and `tag-file` elements, and both share one namespace of names, so a
duplicate name makes the library invalid. The JSP version of a tag file in a JAR is the version of the descriptor.

.META-INF/bookshelf-ui.tld
[source,xml]
----
<?xml version="1.0" encoding="UTF-8"?>
<taglib xmlns="https://jakarta.ee/xml/ns/jakartaee"
        xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
        xsi:schemaLocation="https://jakarta.ee/xml/ns/jakartaee https://jakarta.ee/xml/ns/jakartaee/web-jsptaglibrary_4_0.xsd"
        version="4.0">
  <description>Reusable Bookshelf components packaged as tag files</description>
  <tlib-version>1.0</tlib-version>
  <short-name>bsui</short-name>
  <uri>https://example.org/bookshelf/ui</uri>
  <tag-file>
    <name>badge</name>
    <path>/META-INF/tags/badges/badge.tag</path>
  </tag-file>
</taglib>
----

.META-INF/tags/badges/badge.tag
[source,jsp]
----
<%@ tag body-content="scriptless" description="A small label" trimDirectiveWhitespaces="true" %>
<%@ attribute name="tone" description="info, ok or warn" %>
<span class="badge ${empty tone ? 'info' : tone}"><jsp:doBody/></span>
----

.Building the JAR and using the tag
[source,shell]
----
jar cf src/main/webapp/WEB-INF/lib/bookshelf-ui.jar -C jarsrc META-INF
----

[source,jsp]
----
<%@ taglib prefix="bsui" uri="https://example.org/bookshelf/ui" %>
<p>Status: <bsui:badge tone="ok">on loan</bsui:badge></p>
----

[source,html]
----
<p>Status: <span class="badge ok">on loan</span></p>
----

Jasper compiled the tag into `+org/apache/jsp/tag/meta/...+` of the work directory, a separate tree from the `+tag/web/...+` of
tag files in the web application. Tomcat finds the descriptor by scanning the JARs of `WEB-INF/lib` for TLD files, as the
Tomcat JAR scanner page describes.

Source: https://jakarta.ee/specifications/pages/4.0/jakarta-server-pages-spec-4.0.html#packaging-in-a-jar[Jakarta Pages 4.0 -- 8.4.2 Packaging in a JAR]

Source: https://tomcat.apache.org/tomcat-11.0-doc/config/jar-scanner.html[Apache Tomcat 11 -- The Jar Scanner Component]

A third form, tag files compiled into Java classes and distributed as a binary tag library, is allowed but needs a tool that
produces portable code; containers are not required to supply one. Precompiling with JspC at build time is a matter for the
xref:web/jsp-struts/jsp/jasper-configuration-and-precompilation.adoc[Jasper Configuration & Precompilation].

Source: https://jakarta.ee/specifications/pages/4.0/jakarta-server-pages-spec-4.0.html#packaging-as-precompiled-tag-handlers[Jakarta Pages 4.0 -- 8.4.4 Packaging as Precompiled Tag Handlers]

[#layout]
== A Layout Template with Tag Files

Every page of the Bookshelf has the same skeleton: a head, a navigation bar, a main area, an optional second column and a
footer. In JSP the clean way to write that skeleton once is a tag file whose body is the page content and whose optional
fragments fill the other slots. This is the pattern called *Composite View*, which the JSP world also implemented with Tiles
and SiteMesh, and which Thymeleaf calls a layout.

.WEB-INF/tags/layout/page.tag
[source,jsp]
----
<%@ tag description="Bookshelf page layout" body-content="scriptless" trimDirectiveWhitespaces="true" %>
<%@ taglib prefix="c" uri="jakarta.tags.core" %>
<%@ taglib prefix="ui" tagdir="/WEB-INF/tags/ui" %>
<%@ attribute name="title" required="true" description="Text of the title element" %>
<%@ attribute name="active" description="Name of the current menu entry" %>
<%@ attribute name="head" fragment="true" description="Extra markup for the head element" %>
<%@ attribute name="sidebar" fragment="true" description="Optional second column" %>
<!DOCTYPE html>
<html lang="en">
<head>
  <meta charset="UTF-8">
  <title><c:out value="${title}"/> - Bookshelf</title>
  <jsp:invoke fragment="head"/>
</head>
<body>
<nav>
  <ui:navLink href="${pageContext.request.contextPath}/index.jsp" label="Catalogue" current="${active == 'catalogue'}"/>
  <ui:navLink href="${pageContext.request.contextPath}/about.jsp" label="About" current="${active == 'about'}"/>
</nav>
<main>
  <jsp:doBody/>
</main>
<aside><jsp:invoke fragment="sidebar"/></aside>
<footer>Bookshelf, ${books.size()} titles</footer>
</body>
</html>
----

.WEB-INF/tags/ui/navLink.tag
[source,jsp]
----
<%@ tag body-content="empty" trimDirectiveWhitespaces="true" %>
<%@ taglib prefix="c" uri="jakarta.tags.core" %>
<%@ attribute name="href" required="true" %>
<%@ attribute name="label" required="true" %>
<%@ attribute name="current" type="java.lang.Boolean" %>
<a href="<c:out value='${href}'/>"${current ? ' class="current" aria-current="page"' : ''}><c:out value="${label}"/></a>
----

Source: https://jakarta.ee/specifications/pages/4.0/jakarta-server-pages-spec-4.0.html#jspinvoke[Jakarta Pages 4.0 -- 5.9 jsp:invoke]

Source: https://jakarta.ee/specifications/pages/4.0/jakarta-server-pages-spec-4.0.html#jspdobody[Jakarta Pages 4.0 -- 5.10 jsp:doBody]

The design decisions are all visible in that file. The page-specific content comes in through `jsp:doBody`. The optional
slots are fragment attributes invoked with `jsp:invoke`, which does nothing for a slot the page did not fill. Everything the
layout reads from the model comes from a scope (here `books` from application scope); a layout that needs a variable the page
sets should ask for it as an attribute instead, since the caller's page scope is not visible. The title is escaped with
`c:out` because it is data. The navigation uses a component tag file (`ui:navLink`), a tag file calling a tag file from another
directory through its own `taglib` directive.

A page uses the layout by wrapping its content:

.index.jsp
[source,jsp]
----
<%@ page contentType="text/html; charset=UTF-8" session="false" %>
<%@ taglib prefix="c" uri="jakarta.tags.core" %>
<%@ taglib prefix="layout" tagdir="/WEB-INF/tags/layout" %>
<%@ taglib prefix="ui" tagdir="/WEB-INF/tags/ui" %>
<layout:page title="Catalogue" active="catalogue">
  <jsp:attribute name="head"><link rel="stylesheet" href="${pageContext.request.contextPath}/bookshelf.css"></jsp:attribute>
  <jsp:attribute name="sidebar"><p>Sidebar for ${books.size()} books</p></jsp:attribute>
  <jsp:body>
    <ui:each items="${books}" var="b" varIndex="i">
      <ui:bookCard book="${b}" highlight="${i == 0}">
        <ui:button kind="submit" class="borrow" data-id="${b.id}">Borrow</ui:button>
      </ui:bookCard>
    </ui:each>
    <ui:summary items="${books}" var="total"/>
    <p>${total}</p>
  </jsp:body>
</layout:page>
----

----

[#nested-layouts]
=== Layouts built on layouts

A layout can wrap another layout, which is the JSP form of Tiles definition inheritance. The `catalogue` layout adds a section
element around the body and a fixed "Filters" block in front of whatever sidebar the page supplies; it forwards its own
`sidebar` fragment to `layout:page` by invoking it inside a `jsp:attribute`.

.WEB-INF/tags/layout/catalogue.tag
[source,jsp]
----
<%@ tag description="Catalogue layout built on the page layout" body-content="scriptless" trimDirectiveWhitespaces="true" %>
<%@ taglib prefix="layout" tagdir="/WEB-INF/tags/layout" %>
<%@ attribute name="title" required="true" %>
<%@ attribute name="sidebar" fragment="true" %>
<layout:page title="${title}" active="catalogue">
  <jsp:attribute name="sidebar"><div class="filters">Filters</div><jsp:invoke fragment="sidebar"/></jsp:attribute>
  <jsp:body><section class="catalogue"><jsp:doBody/></section></jsp:body>
</layout:page>
----

.nested.jsp
[source,jsp]
----
<%@ page contentType="text/html; charset=UTF-8" session="false" %>
<%@ taglib prefix="layout" tagdir="/WEB-INF/tags/layout" %>
<layout:catalogue title="Sci-fi">
  <jsp:attribute name="sidebar"><p>Page-specific sidebar</p></jsp:attribute>
  <jsp:body><p>Three books.</p></jsp:body>
</layout:catalogue>
----

[source,html]
----
<main>
  <section class="catalogue"><p>Three books.</p></section></main>
<aside><div class="filters">Filters</div><p>Page-specific sidebar</p></aside>
----

Inside `catalogue.tag` the tag `sidebar` that `jsp:invoke` names is the attribute of `catalogue.tag` itself, even though
`layout:page` also has a `sidebar`: the two are in different page scopes. The diagram at the top of the page is this call.

[#components]
== Reusable Components

A component tag file renders one concept of the application: a book card, a rating, a navigation link, a form field. The same
rules produce good ones.

* Take typed attributes (`book` of type `Book`, not three strings) and a body for content the caller owns.
* Read nothing from the request that the caller did not pass, except the context path or other genuinely global values.
* Escape every value with `c:out` or `fn:escapeXml`: the tag file is the single place where the escaping is written.
* Give optional behaviour a name (`highlight`), not a flag of unrelated meanings.
* Keep logic to presentation. A loop that decides nothing is fine; a query, a transaction or a permission check is not.
* Put each directory of related tags under one prefix (`ui`, `layout`, `form`), and keep the names short and in the camel case
  or hyphenated style the project agrees on.

The Bookshelf's `ui` directory shows the range: `rating` (no body, one attribute), `navLink` (no body, a boolean), `bookCard`
(typed attribute, boolean, body), `each` (collection, two named variables), `summary` (an `AT_END` result), `button`
(dynamic attributes), `shout` and `raw` (body transformation) and `note` (XML syntax).

Source: https://jakarta.ee/specifications/pages/4.0/jakarta-server-pages-spec-4.0.html#tag-files[Jakarta Pages 4.0 -- Chapter 8 Tag Files]

[#worked-example]
== Worked Example: the Bookshelf Catalogue End to End

The pieces assembled: the servlet or listener puts the books in a scope, the page calls the layout, the layout renders the
skeleton, and component tags render the cards. The call chain for one request of `index.jsp` is: Jasper translates and compiles
`index.jsp`, then each tag file it uses (`layout/page.tag`, `ui/each.tag`, `ui/bookCard.tag`, `ui/rating.tag`, `ui/button.tag`,
`ui/summary.tag`, `ui/navLink.tag`) the first time it is reached. At run time `layout:page` receives three things from the
page: the attributes `title` and `active`, the two fragments `head` and `sidebar`, and the body. It writes the head, calls
`navLink` twice, runs the body (which calls `each`, which for every book runs its own body, which calls `bookCard`, whose body
is the button), and finally the aside and the footer. `summary` sets `total` once, at the end of its call, and the paragraph
that follows prints it.

sleep 6
curl -s http://localhost:8080/g6tagfiles/index.jsp | grep -c 'v2'
----

[source,text]
----

----

The three matches are the three ratings of the three cards. A change to the layout file (`<footer>` to `<footer data-v="2">`)
showed in `index.jsp` and in `about.jsp` six seconds later, so a tag file edit reaches every page that uses it.

[#development]
== Compilation, Reloading and Where the Generated Code Is

Jasper translates a tag file to Java the first time a page that uses it is translated, compiles it, and keeps the class in the
web application's work directory: `org/apache/jsp/tag/web/<directory>/<name>_tag.java` and `.class` for a file in
`WEB-INF/tags`, and `+org/apache/jsp/tag/meta/<uri>/...+` for a file in a JAR. The generated class extends `SimpleTagSupport`;
its `setJspContext` creates the `JspContextWrapper` that holds the clean page scope and the variable synchronization state,
and `doTag` calls `syncBeforeInvoke` before it invokes the body.

In development mode (the default, `development` is `true`) Jasper checks a page and its dependent files for modification at
most once per `modificationTestInterval` (4 seconds by default), and the tag files a page uses are among its dependents, as
the reload test above showed. In production mode (`development` false) the pages and tag files are checked at the
`checkInterval` or never, and precompiling with JspC removes the first-request cost. Compile errors name the tag file and
line, as in the messages of this page, and runtime errors from EL name the tag file too:

[source,text]
----
jakarta.el.PropertyNotFoundException: Property [isbn] not found on type [org.example.bookshelf.Book]
org.apache.jasper.JasperException: An exception occurred processing [/WEB-INF/tags/bad/missingprop.tag] at line [2]
----

Source: https://tomcat.apache.org/tomcat-11.0-doc/jasper-howto.html#Configuration[Apache Tomcat 11 -- Jasper 2 JSP Engine How To, Configuration]

Source: https://tomcat.apache.org/tomcat-11.0-doc/jasper-howto.html#Production_Configuration[Apache Tomcat 11 -- Jasper 2 JSP Engine How To, Production Configuration]

[#security]
== Security Notes

* **Tag file source is a secret like any JSP.** Tag files in `/WEB-INF/tags` cannot be requested by a client. A tag file
  anywhere else is just content: a `leak.tag` containing `+<%@ attribute name="x" %> SECRET-TAG-SOURCE ${x}+` in the web
  application root (`/tags/leak.tag`) was served as is, source and `+${x}+` unexpanded, with status 200. Keep tag files under
  `WEB-INF/tags` or `META-INF/tags`, always.
* **A tag file renders; it does not authorise.** Escape attribute values in the tag file with `c:out`, as the cards do. Do not
  rely on the caller to escape. Output of `jsp:doBody var="x"` and `jsp:invoke var="x"` is already markup, so printing `+${x}+`
  unescaped re-emits whatever the caller's body contained; escape only values, not captured markup.
* **Dynamic attributes are open input.** Names and values of a dynamic attribute may come from a request; the `button` tag
  escapes values, and a tag that writes attribute *names* from request data is an injection point.
* **Static attributes are constants.** A `name-from-attribute` or `rtexprvalue="false"` attribute cannot take `+${param.x}+`; that
  is a feature, since it fixes the names of scoped variables at translation time.
* **Property groups such as `scripting-invalid` do not apply to tag files.** Review `WEB-INF/tags` for scriptlets separately.
* **A shared tag JAR runs with the application's privileges**, like any library. Prefer tag files from sources you build.

Source: https://jakarta.ee/specifications/pages/4.0/jakarta-server-pages-spec-4.0.html#location-of-tag-files[Jakarta Pages 4.0 -- 8.4.1 Location of Tag Files]

[#books-outdated]
== Where the Books Are Outdated

The Pages and JSTL books of the bibliography are from the JSP 1.2 era, which predates tag files. The JSP 1.2 book builds
custom tags only as classic `Tag` and `BodyTag` handlers in Java with a JSP 1.2 TLD DTD, and has nothing like `jsp:doBody` or a
page scope for a tag; the JSTL book evaluates EL in custom tag attributes by hand with an `ExpressionEvaluatorManager`, and
builds its portal layout with `c:import`. Everything the books do with those tools is today either an EL expression, a tag
file or a simple tag handler. The Struts books use Tiles for layouts, with `tiles:insert` and definition inheritance;
a layout tag file expresses the same composition with `jsp:attribute` and nested layouts, and Tiles itself has been retired.
Where the books use a custom tag to reach a database or a feed, the modern answer is to load data before the view.
