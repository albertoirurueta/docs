[#where]
== Where Jasper Is Configured

Jasper is one servlet. In Tomcat it is the class `org.apache.jasper.servlet.JspServlet`, declared under the name `jsp` in
the global `$CATALINA_BASE/conf/web.xml` and mapped there to `+*.jsp+` and `+*.jspx+`. Every Jasper setting is an
`init-param` of that servlet (a handful are context parameters, covered below), so the question "where do I configure
it" is the question "where do I declare or redefine the `jsp` servlet". There are four places and they stack.

.Where the Jasper settings can live in Tomcat 11, from widest to narrowest scope
[cols="2,3,3",options="header"]
|===
|Place |Scope |Notes (rows marked "observed" were reproduced)
|`$CATALINA_BASE/conf/web.xml`, servlet `jsp` |Every web application of the Tomcat instance |The stock file already sets `fork` to `false` and `xpoweredBy` to `false` and loads the servlet at start-up with `load-on-startup` 3 (observed in the 11.0.26 distribution). Editing it changes the defaults of every application, which is rarely what a team wants
|`WEB-INF/web.xml`, redefining servlet `jsp` with `+<servlet-class>org.apache.jasper.servlet.JspServlet</servlet-class>+` |One web application |Observed: the redefinition may omit the `servlet-mapping`, the mapping from the global file still applies. The how-to warns that another container may not recognise the class
|`WEB-INF/tomcat-web.xml` |One web application, Tomcat only |Identical format to `web.xml`. It overrides the container defaults but not what `WEB-INF/web.xml` sets. Observed: `development=false` declared only here took effect (the page was not recompiled after an edit). The way to keep a portable `web.xml`
|Context parameters (`context-param` in `WEB-INF/web.xml`) |One web application |Used for the pluggable interpreters and the page-context pool (see below). They are read from the `ServletContext`
|===

Source: https://tomcat.apache.org/tomcat-11.0-doc/jasper-howto.html#Configuration[Apache Tomcat 11 -- Jasper 2 JSP Engine How-To, Configuration]

Parameter names are case-sensitive in Tomcat. Observed: `keepGenerated` is silently ignored (the generated `.java` file was
kept) while `keepgenerated` works, and `scratchdir` and `mappedfile` are all lower case but `genStringAsCharArray`,
`modificationTestInterval` and `compilerSourceVM` are camel case. The Jetty operations guide says the same in other
words: if a value does not take effect, try a different capitalisation, because the names are inconsistent. A typo is
never an error, the parameter is simply ignored.

.A production profile for the Bookshelf, as the `jsp` servlet redefinition in `WEB-INF/web.xml` (`g7jasperprod.war`)
[source,xml]
----
<servlet>
  <servlet-name>jsp</servlet-name>
  <servlet-class>org.apache.jasper.servlet.JspServlet</servlet-class>
  <init-param><param-name>development</param-name><param-value>false</param-value></init-param>
  <init-param><param-name>genStringAsCharArray</param-name><param-value>true</param-value></init-param>
  <init-param><param-name>trimSpaces</param-name><param-value>single</param-value></init-param>
  <init-param><param-name>keepgenerated</param-name><param-value>false</param-value></init-param>
  <init-param><param-name>xpoweredBy</param-name><param-value>true</param-value></init-param>
  <init-param><param-name>classdebuginfo</param-name><param-value>false</param-value></init-param>
  <init-param><param-name>mappedfile</param-name><param-value>false</param-value></init-param>
  <load-on-startup>3</load-on-startup>
</servlet>
----

.The same redefinition in `WEB-INF/tomcat-web.xml` keeps `web.xml` portable (`g7jaspertw.war`; only `development` is set)
[source,xml]
----
<servlet>
  <servlet-name>jsp</servlet-name>
  <servlet-class>org.apache.jasper.servlet.JspServlet</servlet-class>
  <init-param><param-name>development</param-name><param-value>false</param-value></init-param>
  <load-on-startup>3</load-on-startup>

----

Observed with `curl -D - http://localhost:18080/g7jasperprod/books`: the response carried `X-Powered-By: JSP/4.0`
(`xpoweredBy` is on), the work directory held only the `.class` file and no `.java` file (`keepgenerated` is off), and
the page body came back 184 bytes long instead of 198 (`trimSpaces`). The default `jsp` servlet of the same Tomcat sends
no `X-Powered-By` header.

[#features]
== What Jasper 2 Adds: Pooling, Background Compilation and the Eclipse Compiler

The how-to's introduction lists the reasons Jasper 2 behaves as it does, and each one maps to a parameter below.

* *Custom tag pooling.* Tag handler instances are pooled and reused, which makes pages with many custom tags
  considerably faster (`enablePooling`, `poolTagsWithExtends`).
* *Background compilation.* If a page that was already compiled changes, Jasper can compile the new version in the
  background while the old class keeps serving requests, and swap it in once compilation succeeds (`checkInterval`).
* *Recompile on a changed include.* A page that is included at translation time (the `include` directive) is tracked,
  and the including page is recompiled when it changes. The dependency list is the `_jspx_dependants` map of the
  generated class; the behaviour is covered on the xref:web/jsp-struts/jsp/includes-forwards-and-page-composition.adoc[Includes, Forwards and Page Composition] page.
* *The Eclipse JDT compiler.* The generated source is compiled with the Eclipse compiler (`ecj-4.40.jar` in the
  Tomcat 11.0.26 `lib` directory), which loads its dependencies from the container class loader. No JDK is needed at run
  time. Ant and `javac` can still be used by setting `compiler`.

Source: https://tomcat.apache.org/tomcat-11.0-doc/jasper-howto.html#Introduction[Apache Tomcat 11 -- Jasper 2 JSP Engine How-To, Introduction]

[#devprod]
== Development Versus Production

The defaults are tuned for a developer who edits a page and reloads it: modification checks on, generated source kept,
debug information on. The how-to names the four settings to revisit for production and says the main optimisation is
precompilation, which is sometimes impossible (it gives the `jsp-property-group` feature as an example) or impractical, and
that the configuration of the servlet matters most in exactly those cases.

.Development defaults against the production recommendations (Tomcat 11.0.26 how-to, with the Bookshelf's choices)
[cols="2,2,3,4",options="header"]
|===
|Parameter |Development default |Production |Why
|`development` |`true` |`false` |Stops the on-access modification check. Observed: an edited page was then never recompiled (still the old text after more than 30 seconds)
|`genStringAsCharArray` |`false` |`true` |Slightly more efficient char arrays
|`modificationTestInterval` |`4` |a high value, only if `development` must stay `true` (for example dynamically generated pages) |Fewer file system checks
|`trimSpaces` |`false` |`single` or `extended` |Removes unnecessary bytes. Observed on the Bookshelf catalogue page: 198 bytes with `false`, 179 with `true`, 184 with `single`, 156 with `extended`
|`keepgenerated` |`true` |`false` (optional) |Not in the how-to's list; keeps the work directory small. Keep it `true` while diagnosing
|`classdebuginfo`, `mappedfile`, `suppressSmap` |`true`, `true`, `false` |`false`, `false`, `true` (optional) |Smaller classes, no debugger support. The GlassFish deployment guide recommends the same set. A trade-off against being able to debug: see the testing and debugging page of this section
|===

Source: https://tomcat.apache.org/tomcat-11.0-doc/jasper-howto.html#Production_Configuration[Apache Tomcat 11 -- Jasper 2 JSP Engine How-To, Production Configuration]

=== Modification Detection in Development Mode

With the defaults, a page is checked for modification when a request arrives and at least `modificationTestInterval`
seconds have passed since the last check. The first request, the edit and a request inside the interval show the old
page, a request after the interval shows the new page and the old instance is destroyed (`jspDestroy`) before the new
one is initialised (`jspInit`).

.Observed on `g7jasper.war`: `stamp.jsp` declares `jspInit` and `jspDestroy` that print to the log; the file was edited between the second and third request
[source,bash]
----
$ curl -s http://localhost:18080/g7jasper/stamp.jsp | tail -1
Bookshelf edition: TWO
$ sed -i '' 's/TWO/THREE/' webapps/g7jasper/stamp.jsp
$ curl -s http://localhost:18080/g7jasper/stamp.jsp | tail -1      # immediately: inside the 4 second interval
Bookshelf edition: TWO
$ sleep 5
$ curl -s http://localhost:18080/g7jasper/stamp.jsp | tail -1
Bookshelf edition: THREE
----

.The log lines of the same run, in `catalina.out`
[source,text]
----
g7jasper stamp.jsp: jspDestroy
g7jasper stamp.jsp: jspInit org.apache.jsp.stamp_jsp
----

Source: https://tomcat.apache.org/tomcat-11.0-doc/jasper-howto.html#Configuration[Apache Tomcat 11 -- Jasper 2 JSP Engine How-To, Configuration (development, modificationTestInterval)]

=== Production Without Precompilation: Background Compilation

With `development` false the pages are never checked, so a changed page is only picked up by a redeploy. If pages must
change in place on a production server, set `checkInterval` above zero: Jasper then checks in the background and
compiles in the background, and the old class keeps serving until the new one is ready (the
availability point of the introduction). Observed with `development=false` and `checkInterval=2`
(`g7jaspercheck.war`): three requests in the nine seconds after the edit still returned the old page, the new text
appeared between nine and about twenty-five seconds after the edit, and in a second run after six seconds. A background check
runs when the container's background processor runs, and the Engine's `backgroundProcessorDelay` defaults to 10
seconds, so `checkInterval` cannot make the delay shorter than that cycle. The same edit in `g7jasperprod.war` (no
`checkInterval`) was still not visible after more than 30 seconds.

Source: https://tomcat.apache.org/tomcat-11.0-doc/jasper-howto.html#Introduction[Apache Tomcat 11 -- Jasper 2 JSP Engine How-To, Introduction (background compilation)]

Source: https://tomcat.apache.org/tomcat-11.0-doc/config/engine.html#Common_Attributes[Apache Tomcat 11 -- The Engine Component, backgroundProcessorDelay]

=== Recovering From a Failed Compilation

In development mode a page that fails to compile is not retried inside `modificationTestInterval`. Observed with
`modificationTestInterval=600` (`g7jrofoff.war` and `g7jrofon.war`): a page with a syntax error in a scriptlet returned
500, was fixed, and kept returning 500 for as long as it was tried (25 seconds) without `recompileOnFail`. With
`recompileOnFail=true` the fixed page returned 200 about four seconds after the edit, the same delay as the default
interval, so the retry is allowed but not instantaneous. The documentation says the setting makes the next access
trigger a recompilation attempt; the observed behaviour was a delay of about four seconds.

Source: https://tomcat.apache.org/tomcat-11.0-doc/jasper-howto.html#Configuration[Apache Tomcat 11 -- Jasper 2 JSP Engine How-To, Configuration (recompileOnFail)]

[#output]
== Shaping the Output: trimSpaces and genStringAsCharArray

Template text is the HTML around the tags, and whitespace-only runs of it are what a page's directives and loops leave
behind. The Bookshelf catalogue page is a good subject because it has two directives, a `forEach` and indented markup.
The Bookshelf servlet forwards to it and the response was measured with `curl` for each setting of `trimSpaces`.

.The catalogue page, `WEB-INF/views/books.jsp`
[source,jsp]
----
<%@ page contentType="text/html; charset=UTF-8" pageEncoding="UTF-8" %>
<%@ taglib prefix="c" uri="jakarta.tags.core" %>
<!DOCTYPE html>
<html>
<body>

  <h1>Bookshelf</h1>

  <ul>
    <c:forEach var="b" items="${books}">
      <li>${b.title} by <c:out value="${b.author}"/> (${b.year})</li>
    </c:forEach>
  </ul>

</body>
</html>
----

.The response size of `/books` for each `trimSpaces` value on Tomcat 11.0.26 (`g7jtrimf`, `g7jtrimt`, `g7jtrims` and `g7jtrime`)
[cols="2,1,4",options="header"]
|===
|`trimSpaces` |Bytes |What was removed
|`false` (default) |198 |Nothing
|`true` |179 |Template text that is only whitespace
|`single` |184 |The same text, each run replaced by one space (so two directives on separate lines leave two spaces at the top)
|`extended` |156 |Also leading and trailing whitespace of text and runs of whitespace collapsed to one newline
|===

.The complete response with `trimSpaces=extended`, produced by `curl -s http://localhost:18080/g7jtrime/books`
[source,html]
----
<!DOCTYPE html>
<html>
<body>
<h1>Bookshelf</h1>
<ul><li>Dune by Frank Herbert (1965)</li><li>Neuromancer by William Gibson (1984)</li></ul>
</body>
</html>
----

Source: https://tomcat.apache.org/tomcat-11.0-doc/jasper-howto.html#Production_Configuration[Apache Tomcat 11 -- Jasper 2 JSP Engine How-To, Production Configuration (trimSpaces)]

The page-level equivalent, `trimDirectiveWhitespaces`, is a page directive attribute and takes precedence over the
container setting for that page or tag file; it is covered with the other directives on the
xref:web/jsp-struts/jsp/directives.adoc[JSP Directives] page. Choose the container setting for a whole application and
the directive for the pages where whitespace is significant (a `pre` block or an inline-formatted fragment); `extended`
changes the layout of such text.

`genStringAsCharArray` changes how the static text is written. Observed on the two-line page `shelf.jsp` (the text
`Shelf: ` and `class=`): the default writes the text as string literals in the generated servlet and the setting writes
it through static `char` arrays.

.Fragment of the generated servlet, default (`g7jasper`) and with `genStringAsCharArray=true` (`g7jchars`)
[source,java]
----
// default
      out.write("\n");
      out.write("class=");

// genStringAsCharArray=true
      out.write(_jspx_char_array_1);
  ...
  static char[] _jspx_char_array_0 = "Shelf: ".toCharArray();
  static char[] _jspx_char_array_1 = "\nclass=".toCharArray();
----

Source: https://tomcat.apache.org/tomcat-11.0-doc/jasper-howto.html#Production_Configuration[Apache Tomcat 11 -- Jasper 2 JSP Engine How-To, Production Configuration (trimSpaces, genStringAsCharArray)]

[#workdir]
== The Work Directory, Package Names and the Scratch Directory

Jasper writes generated files below the web application's work directory, `work/Catalina/localhost/<context>/` in Tomcat,
under the package `org.apache.jsp`, with the path of the page encoded into the package: `WEB-INF/views/books.jsp` becomes
`org/apache/jsp/WEB_002dINF/views/books_jsp.java`, because `-` is not legal in a Java name. Observed on `g7jasper.war`
after three requests: a `.java` and a `.class` file for each of `books_jsp`, `shelf_jsp` and `stamp_jsp`.

`scratchdir` moves the output elsewhere and `generatedJspPackageName` renames the package. Observed
(`g7jpkg.war`, `scratchdir` pointing at an existing directory, `generatedJspPackageName=org.example.gen`): the request
returned `class=org.example.gen.shelf_jsp` and the directory held `org/example/gen/shelf_jsp.java` and `.class`.

.A scratch directory that does not exist is an initialisation error, not something Jasper creates (observed on Tomcat 11.0.26)
[source,text]
----
java.lang.IllegalStateException: The scratchDir you specified: [.../scratch-out] is unusable.
----

The failure appears as a 500 on the first request (`Servlet.init() for servlet [jsp] threw exception`), and after the
directory was created the next request succeeded without a redeploy.

The default class file level deserves a check on a new server. The how-to says `compilerSourceVM` and
`compilerTargetVM` default to 17, and the generated class files are Java 17 files (major version 61) even on a Java 21
run time; to use newer language features in scriptlets, set both parameters.

Source: https://tomcat.apache.org/tomcat-11.0-doc/jasper-howto.html#Configuration[Apache Tomcat 11 -- Jasper 2 JSP Engine How-To, Configuration (scratchdir, generatedJspPackageName, compilerSourceVM)]

[#loading]
== Controlling Which Pages Stay Loaded, and Warming Pages Up

Every page that has been requested is a loaded servlet instance. Two parameters bound that set. Observed with
`jspIdleTimeout=2` (`g7jidle.war`): `stamp.jsp` was requested and, with no further requests, `jspDestroy` was logged
within 25 seconds (the unload happens in the background processor cycle); the next request ran `jspInit` again. With `maxLoadedJsps=1` (`g7jmax.war`): after `stamp.jsp`, `shelf.jsp` and
`books.jsp` had been requested, `jspDestroy` of `stamp.jsp`, the least recently used page, was logged within the next 22
seconds; the unload is not instantaneous. Use these when a very large application would otherwise keep every page in
memory; they cost a reload for an unloaded page.

The opposite need is to avoid the slow first request. A servlet declaration can name a JSP file and give it a
`load-on-startup` value, which also gives a page a servlet name and a second URL.

.Warming a page up and mapping it to a friendly URL with `jsp-file` (`g7jfile.war`)
[source,xml]
----
<servlet>
  <servlet-name>edition</servlet-name>
  <jsp-file>/stamp.jsp</jsp-file>

== The Optimisation Extension Points: Pooling, Tag Plugins and Interpreters

The how-to's Optimisation section lists three extension points. All three change generated code and were checked by
reading the generated source.

=== Tag Handler Pooling

The default generated servlet creates one `TagHandlerPool` per tag-and-attributes combination in `_jspInit` and
releases it in `_jspDestroy`. Observed on `shelf.jsp`: six references to `TagHandlerPool` with the default and none with
`enablePooling=false` (`g7jnopool.war`), where each use is a `new org.apache.taglibs.standard.tag.rt.core.IfTag()`. The
parameter is a compilation option, so it only affects pages compiled after it is set. The behaviour that makes pooling
a correctness concern (a handler instance reused across invocations) is the subject of the
xref:web/jsp-struts/jsp/custom-tags-classic.adoc[Classic Custom Tags] page.

=== Tag Plugins

A tag plugin replaces the handler of a tag with code inlined into the page. Plugins are registered in
`WEB-INF/tagPlugins.xml`; Jasper ships plugins for the JSTL core tags in the `org.apache.jasper.tagplugins.jstl.core`
package and a sample registration file inside `jasper.jar`.

.`WEB-INF/tagPlugins.xml` registering three of the shipped JSTL plugins (`g7jplug.war`)
[source,xml]

<tag-plugins>

    <plugin-class>org.apache.jasper.tagplugins.jstl.core.If</plugin-class>

  <tag-plugin>
    <tag-class>org.apache.taglibs.standard.tag.rt.core.OutTag</tag-class>
    <plugin-class>org.apache.jasper.tagplugins.jstl.core.Out</plugin-class>
  </tag-plugin>
  <tag-plugin>
    <tag-class>org.apache.taglibs.standard.tag.rt.core.ForEachTag</tag-class>
    <plugin-class>org.apache.jasper.tagplugins.jstl.core.ForEach</plugin-class>
  </tag-plugin>
</tag-plugins>

`IfTag` and `OutTag` (two matches) and was 248 lines long; with the plugins it had no reference to either, was 207

=== The EL and String Interpreters

Two further extension points are chosen with context parameters named after the interface they replace.
`org.apache.jasper.compiler.ELInterpreter` names a class implementing the EL interpreter and
`org.apache.jasper.compiler.StringInterpreter` one that implements the String interpreter, which coerces attribute
strings. The how-to points at two implementations in `org.apache.jasper.optimizations`, and the Javadoc is blunt about
their cost: `ELInterpreterTagSetters` is described as not specification compliant, an interpreter that optimises a subset of tag
attribute setters (expressions that are solely a literal boolean, or a constant string coerced to the setter's type)
and effectively hard-codes the fourth EL resolver; `StringInterpreterEnum` coerces strings to enums.

.Context parameters that switch both implementations on, together with the page-context pool and the tag buffer limit (`g7jopt.war`)
[source,xml]
----
<context-param>
  <param-name>org.apache.jasper.compiler.ELInterpreter</param-name>
  <param-value>org.apache.jasper.optimizations.ELInterpreterTagSetters</param-value>
</context-param>
<context-param>
  <param-name>org.apache.jasper.compiler.StringInterpreter</param-name>
  <param-value>org.apache.jasper.optimizations.StringInterpreterEnum</param-value>
</context-param>
<context-param>
  <param-name>org.apache.jasper.runtime.JspFactoryImpl.POOL_SIZE</param-name>
  <param-value>-1</param-value>
</context-param>
<servlet>
  <servlet-name>jsp</servlet-name>
  <servlet-class>org.apache.jasper.servlet.JspServlet</servlet-class>
  <init-param><param-name>limitBodyContentBuffer</param-name><param-value>true</param-value></init-param>
  <init-param><param-name>bodyContentTagBufferSize</param-name><param-value>256</param-value></init-param>
  <load-on-startup>3</load-on-startup>

The last two entries are the how-to's hint for limiting memory: `POOL_SIZE=-1` disables `PageContext` pooling and
`limitBodyContentBuffer` caps tag buffers. They were set and the application ran; their performance effect was not
measured.

The effect of the two interpreters was observed with a small tag library for the Bookshelf (`bk:label`, whose handler has

[#precompilation]
== Precompilation: Doing the Translation Before the First Request

A page is translated and compiled the first time it is requested, which is the slow first request and, more
importantly, the moment a typo in a scriptlet turns into a 500 in front of a customer. Precompilation moves that work to
build time. The specification names two different things under the word, and a third is a servlet container feature.

.The three meanings of "precompile"
[cols="2,3,3",options="header"]
|===
|Mechanism |What happens |Where it is defined
|The `jsp_precompile` request parameter |A request with the parameter asks the container to translate and compile that page now and not to run it |Pages specification 11.4.2, implemented by Jasper (see below, and the xref:web/jsp-struts/jsp/lifecycle-and-translation.adoc#precompilation[lifecycle page] of this section)
|Build-time translation and compilation (JspC) |A tool turns the page sources into servlet classes plus the `web.xml` declarations that make them look like the original pages. The container then never translates |Pages specification 1.1.9 and Appendix A (non-normative); the tool is container-specific
|Load-on-startup of a page |The container translates the page when the application starts, with no tool and no request |Servlet `load-on-startup` with `jsp-file` (shown above)
|===

Source: https://jakarta.ee/specifications/pages/4.0/jakarta-server-pages-spec-4.0.html#compiling-jsp-pages[Jakarta Pages 4.0 -- 1.1.9 Compiling JSP Pages]

Source: https://jakarta.ee/specifications/pages/4.0/jakarta-server-pages-spec-4.0.html#packaging-jsp-pages[Jakarta Pages 4.0 -- Appendix A, Packaging JSP Pages]

The benefits the specification lists for build-time compilation are the removal of the start-up lag, a smaller
footprint (the Java compiler is not needed), and compilation in the context of the web application, so that relative
URLs in `include` directives, tag library references and translation-time actions are resolved. Its Appendix A shows
the whole idea in miniature: compile `HelloWorld.jsp` into a servlet class, declare it in `web.xml` with
`servlet-class` and a `servlet-mapping` to `/HelloWorld.jsp`, and package `WEB-INF/web.xml` and
`+WEB-INF/classes/...+` with no JSP source in the WAR. Every tool in this section produces that shape.

=== The jsp_precompile Request and Reserved Parameter Names

Specification 11.4.1 reserves every request parameter whose name starts with `jsp`; a page should ignore any parameter
that starts with `jsp_` and containers and users should not invent names with the prefix. Section 11.4.2 defines
`jsp_precompile`: with no value or the value `true` or `false` the request is a precompilation request and must not be
delivered to the page (the value `true` or none is the suggestion to compile, and the container may
ignore it), and any other value is illegal and yields a 500. The lifecycle page of this section verified all of that
against Tomcat 11.0.26 (see the xref:web/jsp-struts/jsp/lifecycle-and-translation.adoc#precompilation[Precompilation section]).
The Jasper-specific part is that the parameter name is configurable (`jspPrecompilationQueryParameter`, observed above),
and that the request does not deliver anything to the page: on `g7jpq.war` `?precomp=true` returned 200 with an empty body.

A build can use the request as a smoke test (request every page once with the parameter after deployment, to translate
and compile all of them and see compile errors before users do), but it needs a list of the pages and a running server;
JspC does the same job without a server.

Source: https://jakarta.ee/specifications/pages/4.0/jakarta-server-pages-spec-4.0.html#precompilation[Jakarta Pages 4.0 -- 11.4 Precompilation]

Source: https://jakarta.ee/specifications/pages/4.0/jakarta-server-pages-spec-4.0.html#request-parameter-names[Jakarta Pages 4.0 -- 11.4.1 Request Parameter Names]

=== JspC: the Pipeline

JspC is Jasper without the servlet container. It translates every JSP (and tag file) under a web application directory
into Java source, optionally compiles it, and writes the servlet declarations and mappings that bind each generated class
to the URL of its page.

.The JspC precompilation pipeline, common to the Ant task, the command line and the Jetty Maven plugin
[mermaid]
....
flowchart LR
  src["JSP pages and tag files<br/>in the web application"] --> jspc["JspC<br/>Ant task, command line,<br/>Maven plugin"]
  jspc --> java["generated Java source<br/>org.apache.jsp.*"]
  jspc --> map["servlet and servlet-mapping<br/>declarations"]
  java --> comp["compile<br/>javac, ECJ,<br/>or JspC compile=true"]
  comp --> cls["WEB-INF/classes<br/>org/apache/jsp/*.class"]
  map --> wx["WEB-INF/web.xml<br/>merged or included"]
  cls --> war["WAR"]
  wx --> war
  war --> run["container: each page URL<br/>is a plain servlet mapping,<br/>no translation at run time"]
....

The ordering matters: JspC reads the tag libraries and TLDs the pages use, so the application's libraries must already be
in `WEB-INF/lib` and its own classes in `WEB-INF/classes` when it runs. A page's relative references are resolved against
the web application root (`uriroot`).

=== JspC With the Ant jasper Task

The how-to calls Ant the preferred way to compile a web application with JspC, and ships the script, which is also
included in the Tomcat deployer download. It imports `bin/catalina-tasks.xml`, which defines the `jasper` task, runs
the task to write Java source and a `generated_web.xml`, then compiles the source with the `javac` task and a class path
of the application and Tomcat libraries. The output is then added to `web.xml` by hand, or by the task.

.The build file used on `g7jasperpre` (the how-to script with `addWebXmlMappings` and `release="21"` added; the cleanup target is unchanged)
[source,xml]
----
<project name="Webapp Precompilation" default="all" basedir=".">
  <import file="${tomcat.home}/bin/catalina-tasks.xml"/>
  <target name="jspc">
    <jasper validateXml="false"
            uriroot="${webapp.path}"
            addWebXmlMappings="true"
            webXmlInclude="${webapp.path}/WEB-INF/generated_web.xml"
            outputDir="${webapp.path}/WEB-INF/src" />
  </target>
  <target name="compile">
    <mkdir dir="${webapp.path}/WEB-INF/classes"/>
    <mkdir dir="${webapp.path}/WEB-INF/lib"/>
    <javac destdir="${webapp.path}/WEB-INF/classes" debug="on" failonerror="false"
           srcdir="${webapp.path}/WEB-INF/src" excludes="**/*.smap" release="21">
      <classpath>
        <pathelement location="${webapp.path}/WEB-INF/classes"/>
        <fileset dir="${webapp.path}/WEB-INF/lib"><include name="*.jar"/></fileset>
        <pathelement location="${tomcat.home}/lib"/>
        <fileset dir="${tomcat.home}/lib"><include name="*.jar"/></fileset>
        <fileset dir="${tomcat.home}/bin"><include name="*.jar"/></fileset>
      </classpath>
      <include name="**"/>
      <exclude name="tags/**"/>
    </javac>
  </target>
  <target name="all" depends="jspc,compile"/>
  <target name="cleanup">
    <delete>
      <fileset dir="${webapp.path}/WEB-INF/src"/>
      <fileset dir="${webapp.path}/WEB-INF/classes/org/apache/jsp"/>
    </delete>
  </target>
</project>
----

The run, on the exploded Bookshelf WAR, with Ant 1.10.15 launched directly from its two jars (the command the how-to
gives, `+ant -Dtomcat.home=... -Dwebapp.path=...+`, is the same):

.Output of the Ant run on the exploded `g7jasper.war` (abridged)
[source,text]
----

    [javac] Compiling 4 source files to .../webapp/WEB-INF/classes

.The block merged into `WEB-INF/web.xml` by `addWebXmlMappings="true"` (abridged to two pages)

    <servlet>

`/shelf.jsp`, `/stamp.jsp` and `/label.jsp` all returned 200 with the same output as before, `shelf.jsp?x=1` also returned
200, and the work directory of the application stayed empty (no `.java`, no `.class`): the container did not translate or
compile anything.

Source: https://tomcat.apache.org/tomcat-11.0-doc/jasper-howto.html#Web_Application_Compilation[Apache Tomcat 11 -- Jasper 2 JSP Engine How-To, Web Application Compilation]

The how-to's hints about the task are worth reading with the experiment in mind.

* *`addWebXmlMappings` and `webXmlInclude` go together.* The how-to presents `addWebXmlMappings` as an option that merges
  `generated_web.xml` into `web.xml` automatically. Observed on Tomcat 11.0.26: `addWebXmlMappings="true"` without
  `webXmlInclude` ends the build with `+BUILD FAILED ... java.lang.NullPointerException at
  org.apache.jasper.JspC.mergeIntoWebXml(JspC.java:1270)+`. With both, the merged block was written and no separate
  `generated_web.xml` remained in the directory.
* *Locale and verbosity.* With a non-English default locale the JspC messages are localised (the first run printed Spanish
  INFO lines); add `-Duser.language=en` when the output is parsed.
* *Do not stop at the first error.* `failOnError="false"` with `showSuccess="true"` lists every page that converted, which
  helps when a legacy application has many broken pages.
* *Java level.* The how-to says to add `source` and `target` attributes to the `javac` task to pick the Java version of the
  classes, and to set `debug="off"` for production (the build file above used `release="21"`).
* *Regenerate on every Tomcat upgrade.* The hint is explicit: when switching to another Tomcat release, regenerate and
  recompile the JSPs with the new Tomcat. The generated classes extend the Jasper runtime base class and call its
  internals; a class generated by one release is not guaranteed to run on another.

The task also takes more attributes than the how-to uses. They are the setters of the `org.apache.jasper.JspC` class, so
the Javadoc lists them. The ones a Bookshelf build needs most often: `compile` (compile inside JspC, below), `outputDir`,
`uriroot`, `jspFiles` (a list of pages instead of the whole tree), `package`, `webXml`, `webFragmentXml` (a complete
`web-fragment.xml` for packaging the pages in a library JAR), `failOnError`, `threadCount`, `trimSpaces`,
`genStringAsCharArray`, `poolingEnabled`, `mappedFile`, `classDebugInfo`, `smapSuppressed`, `smapDumped`,
`compilerSourceVM`, `compilerTargetVM`, `useNonstandardTagOptimizations` and `blockExternal`.

Source: https://tomcat.apache.org/tomcat-11.0-doc/api/org/apache/jasper/JspC.html[Apache Tomcat 11 Javadoc -- org.apache.jasper.JspC]

=== Tag Files and Libraries Under JspC

Tag files under `WEB-INF/tags` are translated and compiled with the pages. Observed with a `badge.tag` and a page that used

matches only a top-level `tags` directory of the source tree and not `org/apache/jsp/tag/web`, so it excluded nothing
in this experiment. The tag file features themselves are on the xref:web/jsp-struts/jsp/tag-files-and-layouts.adoc[Tag Files and Layouts] page, and
the specification's remark that a tag file can also be packaged as a precompiled handler is in section 8.4.4.

== Jetty: The JSP Module and the JspC Maven Plugin

Jetty uses Apache Jasper for JSP. This section is from the Jetty 12.1 operations and programming guides, from the contents of
the 12.1.14 artifacts, and from one experiment: the JspC plugin was run, and the WAR it produced was deployed on Tomcat.
Jetty itself was not started, so the run-time statements are documentation and artifact inspection.

JSP support is a module per EE level, `ee8-jsp` to `ee11-jsp` (the `ee11-jsp` module depends on `ee11-servlet`,
`ee11-annotations` and `ee11-apache-jsp`). Jetty identifies the JSP servlet by the attribute `id="jsp"` in the default
descriptor. That descriptor, `webdefault-ee11.xml` in `jetty-ee11-webapp-12.1.14.jar`, declares the servlet `jsp`
with the class `org.eclipse.jetty.ee11.jsp.JettyJspServlet`, sets `xpoweredBy` to `false` and, notably,
`compilerTargetVM` and `compilerSourceVM` to `1.8`, loads it with `load-on-startup` 0, and maps it to `+*.jsp+`, `+*.jspf+`,
`+*.jspx+` and `+*.xsp+` in lower and upper case. An application changes it by re-declaring a `servlet` with the same
`servlet-name` and `id="jsp"` in its `web.xml` and adding `init-param` entries, for example `keepgenerated` or the
`async-supported` element (the JSP servlet does not support asynchronous processing by default). Logging of the
`org.apache.jasper` packages is bridged to Jetty logging. The parameters are Jasper's, so the table above applies; the
Jetty guide lists them with Jetty's defaults and an important caveat: parameter spellings differ in some places from
Tomcat's (the guide spells `scratchDir`, `mappedFile` and `genStrAsCharArray`), and the instruction is to try all
lower case if a value does not take effect.

.Augmenting Jetty's JSP servlet from the application's `web.xml` (from the Jetty 12.1 guide; not run here)
[source,xml]
----
<servlet id="jsp">
  <servlet-name>jsp</servlet-name>
  <init-param>
    <param-name>keepgenerated</param-name>
    <param-value>true</param-value>
  </init-param>
</servlet>
----

=== The Jetty JspC Maven Plugin

For Jakarta EE 11 the plugin is `org.eclipse.jetty.ee11:jetty-ee11-jspc-maven-plugin` 12.1.14. It precompiles the pages and
works with the `maven-war-plugin` so that the classes and the merged descriptor go into the WAR. The plugin's own
documentation recommends putting it in a profile that is switched on only for a production build.

.The `prod` profile that precompiles the Bookshelf (`pom.xml` of `g7jasperjetty`; run with `mvn -Dprod clean package`)
[source,xml]
----
<profiles>
  <profile>
    <id>prod</id>
    <activation>
      <property><name>prod</name></property>
    </activation>
    <build>
      <plugins>
        <plugin>
          <groupId>org.eclipse.jetty.ee11</groupId>
          <artifactId>jetty-ee11-jspc-maven-plugin</artifactId>
          <version>12.1.14</version>
          <executions>
            <execution>
              <id>jspc</id>
              <goals>
                <goal>jspc</goal>
              </goals>
            </execution>
          </executions>
        </plugin>
        <plugin>
          <groupId>org.apache.maven.plugins</groupId>
          <artifactId>maven-war-plugin</artifactId>
          <configuration>
            <webXml>${project.basedir}/target/web.xml</webXml>
          </configuration>
        </plugin>
      </plugins>
    </build>
  </profile>
</profiles>
----

Observed: the plugin ran after the Java compilation and before the test resources step, compiled
`stamp.jsp,shelf.jsp,WEB-INF/views/books.jsp,label.jsp` from the default includes (`+**/*.jsp, **/*.jspx+`) and reported
`Generation completed with [0] errors`; the build printed three `+The XML schema [...] could not be found+` warnings that did
not matter. The WAR it produced contained `+WEB-INF/classes/org/apache/jsp/*.class+` for all four pages, a `WEB-INF/web.xml`
(the merged file `target/web.xml`) with `servlet` and `servlet-mapping` entries for each page, and also one that Tomcat
does not need: `+<context-param>org.eclipse.jetty.jsp.precompiled = true</context-param>+`, which tells Jetty's
JSP servlet to expect precompiled classes. The JSP sources stayed in the WAR, because the war plugin copies the webapp
directory. The WAR was then deployed on Tomcat 11.0.26 (`g7jasperjetty`): `/books`, `/shelf.jsp`, `/stamp.jsp` and
`/label.jsp` all returned 200 and the work directory stayed empty, so the classes the Jetty plugin generates run on
Tomcat's Jasper too. That portability is a convenience of this experiment; the classes extend the Jasper base class
of the plugin's Jasper version, and the how-to's rule of regenerating on a release change still applies.

[#glassfish]
== GlassFish: jsp-config, --precompilejsp and jspc

Eclipse GlassFish runs JSP on Eclipse WaSP (`eclipse-ee4j/wasp`, an implementation of Jakarta Pages; no separate Maven coordinate is
published for it, so only the repository is cited). This section is from the GlassFish deployment and development guides published as `latest` on glassfish.org and was not
run here: GlassFish was not installed in the scratch environment.

An application configures the engine in `WEB-INF/glassfish-web.xml` with a `jsp-config` element that holds `property`
subelements, so the settings stay out of the portable `web.xml`.

.Setting JSP engine properties for one application in `glassfish-web.xml` (from the GlassFish deployment guide; not run here)
[source,xml]
----
<glassfish-web-app>
  <jsp-config>
    <property name="development" value="false"/>
    <property name="genStrAsCharArray" value="true"/>
    <property name="trimSpaces" value="true"/>
    <property name="keepgenerated" value="false"/>
  </jsp-config>
</glassfish-web-app>
----

The property names are close to Jasper's, with GlassFish-specific additions and different defaults. The ones that matter
here, from the guide's table: `development` (default `true`), `checkInterval` (`0`), `modificationTestInterval`
(default `0` there, so a page is checked on every access in development mode), `reload-interval` (`0`; `-1` disables
checks and recompilation), `mappedfile` (`true`), `trimSpaces` (`false`, and only `true` or `false`), `suppressSmap`,
`dumpSmap`, `classdebuginfo`, `keepgenerated` (`true` with JDK 5 and before and for `jspc`, otherwise `false`),
`genStrAsCharArray` (`false`) and `genStrAsByteArray` (`true`: text as bytes encoded with the page encoding, if the page is not
buffered), `enablePooling` (`true`), `enableTldValidation`, `scratchdir`, `usePrecompiled` (`false`; when `true` an accessed
page is not compiled and its precompiled servlet class, assumed to be in `WEB-INF/lib` or `WEB-INF/classes`, is used),
`initialCapacity`, `httpMethods`, `ignoreJspFragmentErrors`, `defaultBufferNone`, `xpoweredBy` (default `true` in GlassFish,
against `false` in Tomcat), `saveBytecode`, `javaEncoding`, `compilerSourceVM`, `compilerTargetVM`, `fork`, `compiler` and
`classpath`. The guide's performance recommendation is the same list as above, expressed as GlassFish property values:
`development` false (or true with a large `modificationTestInterval`), `mappedfile` false, `trimSpaces` true,
`suppressSmap` true, `classdebuginfo` false, and `fork` false on Solaris.

GlassFish has three ways to compile JSP files: automatically at run time, with the `--precompilejsp` option of
`asadmin deploy`, and with the `jspc` command-line tool in `glassfish/bin` (`glassfish/bin/jspc -help` lists its options).
A web application that was precompiled with `jspc` is used with `usePrecompiled` set to `true`.

Source: https://glassfish.org/docs/latest/application-deployment-guide.html#jsp-config[Eclipse GlassFish Application Deployment Guide -- jsp-config]

Source: https://glassfish.org/docs/latest/application-development-guide.html#options-for-compiling-jsp-files[Eclipse GlassFish Application Development Guide -- Options for Compiling JSP Files]

Source: https://github.com/eclipse-ee4j/wasp[Eclipse WaSP (a Jakarta Pages implementation)]

[#known-issues]
== A Known Issue: Very Large Pages

The how-to lists one known issue: a JVM defect (bug 6294277, reported against Tomcat as bug 39089) can cause
`java.lang.InternalError: name is too long to represent` when compiling very large JSPs. The workarounds are to reduce the
size of the page, which is also the right fix for readability (split it into fragments with
xref:web/jsp-struts/jsp/includes-forwards-and-page-composition.adoc[includes] or xref:web/jsp-struts/jsp/tag-files-and-layouts.adoc[tag files]),
or to disable SMAP generation with `suppressSmap` set to `true`. The line table is exactly what the debugger uses, so the second
workaround trades debuggability for compilability.

Source: https://tomcat.apache.org/tomcat-11.0-doc/jasper-howto.html#Known_issues[Apache Tomcat 11 -- Jasper 2 JSP Engine How-To, Known issues]

[#bookshelf]
== The Bookshelf in Production: Putting It Together

A reasonable production arrangement for the Bookshelf, as a checklist built from the sections above.

. *Precompile in the build.* Use JspC (the Ant task, `-compile` from the command line, or the Jetty plugin in a `prod`
  profile) and package the classes with the merged `web.xml`. Do not ship the JSP sources unless an operator needs them, and delete
  `WEB-INF/src` before packaging. Then the first request cost, and a class of translation errors, are gone.
. *Check that nothing is translated at run time.* After deployment, request the pages and confirm the work directory has no
  `.java` or `.class` files for them (observed on `g7jasperpre`).
. *Keep production settings for what is still translated at run time.* Pages that cannot be precompiled, such as pages
  covered by a `jsp-property-group` or generated at run time, use the how-to's four settings (`development` false, and
  `trimSpaces`, `genStringAsCharArray`, `modificationTestInterval` as needed), a `checkInterval` if they must change in place, and
  `jspIdleTimeout` or `maxLoadedJsps` if there are very many.
. *Put the settings in the right file.* A portable `web.xml` for the application and, when it must be Tomcat specific,
  `tomcat-web.xml`; a global change in `conf/web.xml` only for a deliberate policy across every application.
. *Rebuild on every container upgrade.* Precompiled classes are bound to the Jasper runtime they were generated against;
  move from Tomcat 10.1 to 11 (the Jakarta namespace has been `+jakarta.*+` since Tomcat 10) by regenerating, never by copying
  `WEB-INF/classes/org/apache/jsp`.
. *Keep a development profile with the defaults.* Developers want modification checks, the generated source and the line table;
  a Maven or Gradle profile that precompiles only with `-Dprod` (as the Jetty guide recommends) keeps both.

== Pitfalls and Error Names

.Common problems with Jasper configuration and precompilation, with the cause and the fix (rows marked "observed" were reproduced on Tomcat 11.0.26)
[cols="3,3,4",options="header"]
|===
|Symptom |Cause |Fix
|An edited page never changes (observed) |`development` is `false`, or the check interval has not elapsed (`modificationTestInterval`, default 4 seconds) |Wait for the interval, set `development` true in development, or set `checkInterval` for background compilation
|A setting has no effect and there is no error (observed) |The name is wrong or in the wrong case (`keepGenerated` against `keepgenerated`) |Copy the name from the table; names are case-sensitive and a typo is ignored
|`+IllegalStateException: The scratchDir you specified: [...] is unusable+` on the first request (observed) |`scratchdir` points at a directory that does not exist or cannot be written |Create the directory with the right permissions
|`BUILD FAILED` with a `NullPointerException` in `JspC.mergeIntoWebXml` (observed) |The Ant task has `addWebXmlMappings="true"` without `webXmlInclude` |Set both attributes
|`FileNotFoundException` for `-webxml` on the JspC command line (observed) |The output directory was not created |Create it first
|`NoClassDefFoundError: org/apache/tools/ant/Task` running JspC from Java (observed) |JspC extends the Ant `Task` and Ant is not on the class path |Add `ant.jar`, or run it from Ant or Maven
|Precompiled pages still compiled at run time (or missing mappings) |The generated `servlet` and `servlet-mapping` entries were not merged into the deployed `web.xml` |Merge them (`addWebXmlMappings` and `webXmlInclude`, or the Maven plugin with `<webXml>` pointing at the merged file)
|No line numbers in an exception or debugger for a precompiled page (observed) |JspC leaves `smapSuppressed` on by default |Set `smapSuppressed="false"` with `compile="true"`
|`+The nested type ...$Level cannot be referenced using its binary name+` (observed) |`StringInterpreterEnum` active and a tag attribute whose type is an enum nested in the handler class |Move the enum to a top-level class, or do not use the interpreter
|Tag handler state leaks between requests, or `NullPointerException` with a custom base class |Pooling and the `extends` attribute (`poolTagsWithExtends`) |See the xref:web/jsp-struts/jsp/custom-tags-classic.adoc[classic tags page]; set `enablePooling` false to confirm, never `poolTagsWithExtends` true unless the base class calls `_jspInit()`
|`jsp_precompile=foo` returns 500 (observed on the xref:web/jsp-struts/jsp/lifecycle-and-translation.adoc#precompilation[lifecycle page]) |Only none, `true` and `false` are legal values |Use `true`
|Generated classes from the old container fail after an upgrade |Precompiled classes depend on the Jasper runtime and on the `javax` or `jakarta` namespace of the release that generated them |Regenerate with the new release's JspC and recompile
|`java.lang.InternalError: name is too long to represent` |A very large page and JVM bug 6294277 |Split the page, or set `suppressSmap` true
|Jetty ignores a Tomcat-style parameter spelling |Jetty's guide uses different spellings in places |Try all lower case, as the Jetty guide suggests, and test the effect
|===

[#outdated]
== Where the Books Are Outdated

* *Scripts and task names.* Older material commonly describes a `jspc` launcher script and earlier Ant task names.
  Tomcat 11.0.26 ships no `jspc` script; the task is named `jasper` and imported through `catalina-tasks.xml`, and the
  how-to calls Ant the preferred route.
* *A JDK on the server.* Older descriptions often assume the container compiles with the JDK's `javac` and therefore needs a JDK at
  run time; Jasper 2 compiles with the bundled Eclipse compiler, and precompilation removes the compiler from the
  run-time path altogether (the specification's own list of the benefits).
* *Hand-merging `web.xml`.* The older workflow is to paste the generated mappings into `web.xml`. The Ant task's
  `addWebXmlMappings` and the Maven plugin's merge do it; the one trap is the `webXmlInclude` pairing noted above.
* *Package names.* Examples from the `javax.servlet` era refer to the attribute `javax.servlet.context.tempdir`. The attribute is
  `jakarta.servlet.context.tempdir` now (the Jetty guide's `scratchDir` description still says `javax`).
* *`jsp_precompile` and reserved names.* This part of the specification is unchanged in Pages 4.0 (11.4), so old material on
  the parameter is still right; only the class names and defaults around it have changed.
* *Defaults.* Check any default quoted in older material against the tables above: in Tomcat 11.0.26 the source and target
  levels are 17, `fork` is `false` in the stock `conf/web.xml` and `xpoweredBy` is `false`. GlassFish defaults `xpoweredBy`
  to `true`.

Two inconsistencies were found in the official documentation while preparing the page: the how-to's `addWebXmlMappings`
paragraph leaves out that `webXmlInclude` is required (a `NullPointerException` otherwise), and the Jetty guide names the
servlet class `org.eclipse.jetty.jsp.JettyJspServlet` while the 12.1.14 default descriptor uses
`org.eclipse.jetty.ee11.jsp.JettyJspServlet`; it also says `javax.servlet.context.tempdir` and names a `genStrAsCharArray`
parameter that is GlassFish's spelling.
