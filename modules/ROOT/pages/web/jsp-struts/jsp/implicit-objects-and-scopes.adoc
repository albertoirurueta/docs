This page is written against Jakarta Pages 4.0 (the specification Tomcat 11.0.26 implements), Jakarta Expression Language
6.0, Jakarta Standard Tag Library 3.0 and Jakarta Servlet 6.1, on Java 21. Everything was verified on 2026-10-08: the facts

nothing else, so everything else a page can touch has to come from somewhere. The container supplies a fixed set of
ready-made variables, the *implicit objects*, and it provides four named storage areas, the *scopes*, in which a page, a
servlet and a tag can leave data for one another. Almost every bug of the form "the page shows nothing", "the value is
from another user" or "the page only works the second time" is a scope or implicit-object mistake, which is why this page
comes before scripting, actions and tags. The running scenario is the _Bookshelf_, a small catalogue of books: a servlet
puts a `Book` in the request and forwards to a view under `WEB-INF`, and the views below read it, keep a cart in the
session and count visits in the application. The servlet side of the same four scopes is on the
xref:web/jsp-struts/servlet-fundamentals.adoc#scopes-and-servletcontext[Servlet Fundamentals page].

[#bookshelf-app]
== The Bookshelf Used on This Page

All the examples below are views of one WAR, deployed as `g3implicit.war` under the context path `/g3implicit`. A small
servlet (`ViewServlet`, mapped to `+/view/*+`) sets the request attributes `book` and `who`, increments a visit counter,
and forwards to `/WEB-INF/views/implicit/<name>.jsp` for a fixed list of view names; a `ServletContextListener`
(`CatalogListener`) stores `catalogName` and `visits` in the application scope at start-up. `web.xml` declares the
context parameter `shelfName` and a `jsp-file` servlet. The two Java classes are shown once here; every other listing
on the page is a JSP or a descriptor.

.ViewServlet and CatalogListener, the Java side of every view (imports omitted)
[source,java]
----
@WebServlet("/view/*")
public class ViewServlet extends HttpServlet {
    private static final Set<String> VIEWS = Set.of(
            "nine", "scopes", "el", "buffer", "nosession", "includes", "boom", "cart", "tagfile",
            "plain", "overflow", "escape", "locals", "bad-decl", "bad-out", "bad-session");

    @Override
    @SuppressWarnings("unchecked")
    protected void doGet(HttpServletRequest req, HttpServletResponse resp) throws ServletException, IOException {
        String view = req.getPathInfo() == null ? "" : req.getPathInfo().substring(1);
        if (!VIEWS.contains(view)) {
            resp.sendError(HttpServletResponse.SC_NOT_FOUND);
            return;
        }
        ((AtomicInteger) getServletContext().getAttribute("visits")).incrementAndGet();
        req.setAttribute("book", new Book(1, "Dune", "Frank Herbert", 1965));
        req.setAttribute("who", "request (set by the servlet)");
        if ("cart".equals(view)) {
            HttpSession session = req.getSession();
            List<String> cart = (List<String>) session.getAttribute("cart");
            if (cart == null) {
                cart = new ArrayList<>();
                session.setAttribute("cart", cart);
            }
            String add = req.getParameter("add");
            if (add != null) {
                cart.add(add);
            }
        }
        req.getRequestDispatcher("/WEB-INF/views/implicit/" + view + ".jsp").forward(req, resp);
    }
}

@WebListener
public class CatalogListener implements ServletContextListener {
    @Override
    public void contextInitialized(ServletContextEvent event) {
        event.getServletContext().setAttribute("catalogName", "Bookshelf catalogue");
        event.getServletContext().setAttribute("visits", new AtomicInteger());
    }
}
----

[#two-sets]
== Two Sets of Implicit Objects

The specification defines implicit objects twice, because a JSP page has two languages inside it. The Java *scripting
variables* (scriptlets and scripting expressions) can use nine objects without declaring
them: `request`, `response`, `pageContext`, `session`, `application`, `out`, `config`, `page` and, in error pages only,
`exception`. The *Expression Language* sees eleven different names: `pageContext`, the four scope maps `pageScope`,
`requestScope`, `sessionScope` and `applicationScope`, the request-data maps `param`, `paramValues`, `header`,
`headerValues` and `cookie`, and the context-parameter map `initParam`. Only `pageContext` is in both lists. The objects of
the first list are real Java objects of the types in the next table; the objects of the second list are mostly
`java.util.Map` views that the EL resolver builds on demand.

.The two lists side by side
[cols="1,3,3",options="header"]
|===
| |Scripting variables (Java code in the page) |EL implicit objects

|Where usable |scriptlets `<% %>`, scripting expressions `<%= %>`; not in declarations `<%! %>` |`+${...}+` in template text and in tag attributes that accept an expression
|Names |`request`, `response`, `pageContext`, `session`, `application`, `out`, `config`, `page`, `exception` (error pages) |`pageContext`, `pageScope`, `requestScope`, `sessionScope`, `applicationScope`, `param`, `paramValues`, `header`, `headerValues`, `cookie`, `initParam`
|Status |legacy: scripting can be disabled for a whole application |current: the recommended way to read data in a view
|Reaches an attribute through |`pageContext.findAttribute`, `request.getAttribute`, `session.getAttribute` ... |the scope maps, or the bare name `+${name}+`
|Reaches `request`, `session` ... |directly |only through `+${pageContext.request}+`, `+${pageContext.session}+`
|===

Source: https://jakarta.ee/specifications/pages/4.0/jakarta-server-pages-spec-4.0.html#implicit-objects[Jakarta Pages 4.0 -- 1.8.3 Implicit Objects]

Source: https://jakarta.ee/specifications/pages/4.0/jakarta-server-pages-spec-4.0.html#_Implicit_Objects[Jakarta Pages 4.0 -- 2.4 Implicit Objects (EL)]

The glossary of the specification states the same split in one sentence: the implicit objects are `request`, `response`,
`pageContext`, `session`, `application`, `out`, `config`, `page` and `exception` for scriptlets and scripting expressions,
and `pageContext`, `pageScope`, `requestScope`, `sessionScope`, `applicationScope`, `param`, `paramValues`, `header`,
`headerValues`, `cookie` and `initParam` for EL expressions.

[#nine-objects]
== The Nine Scripting Implicit Objects

The translator declares these variables at the top of the generated service method, so a scriptlet can use them by name.
Each has a type from a core Java or Servlet package (Pages 4.0 Table JSP.1-6 and JSP.1-7).

.The scripting implicit objects (Jakarta Pages 4.0, Tables JSP.1-6 and JSP.1-7)
[cols="1,2,3,1",options="header"]
|===
|Variable |Type |What it is |Scope

|`request` |protocol-dependent subtype of `jakarta.servlet.ServletRequest`, normally `HttpServletRequest` |the request that triggered the service invocation: parameters, headers, attributes, path information |request
|`response` |subtype of `jakarta.servlet.ServletResponse`, normally `HttpServletResponse` |the response: status, headers, cookies, redirect, error |page
|`pageContext` |`jakarta.servlet.jsp.PageContext` |the page context: the single API over the four scopes and the other objects |page
|`session` |`jakarta.servlet.http.HttpSession` |the session of the requesting client, created if there is none; valid for HTTP only; unavailable when the page declares `session="false"` |session
|`application` |`jakarta.servlet.ServletContext` |the servlet context obtained from the servlet configuration: one per web application |application
|`out` |`jakarta.servlet.jsp.JspWriter` |the buffered writer through which the template text and the actions write |page
|`config` |`jakarta.servlet.ServletConfig` |the configuration of the servlet that runs this page: servlet name and initialization parameters |page
|`page` |`java.lang.Object` |the instance of the page's implementation class that handles the request; a synonym for `this` when the scripting language is Java |page

The class names are Tomcat's and differ on Jetty or GlassFish; the interface types are what a page may rely on.
`request` is an `ApplicationHttpRequest` because the page was reached by `RequestDispatcher.forward` from the servlet:
after a forward the container hands the page a request object that exposes the new path while the original is still
reachable through the `+jakarta.servlet.forward.*+` attributes. The generated class lives in the package
`org.apache.jsp` with the escaped path `WEB_002dINF.views.implicit` (the hyphen of `WEB-INF` becomes `_002d`), and `page`
is that class's instance, so `page == this` is true.

Four rules decide when these names are valid.

* **Declarations do not see them.** A `+<%! ... %>+` declaration becomes a field or a method of the class, outside the
  service method, so `request` does not exist there. `<%! String title = request.getParameter("title"); %>` fails to
  compile with `request cannot be resolved` (observed on Tomcat 11.0.26). Pass the value into a method as a parameter.
* **The names are reserved and cannot be redeclared.** `<% String out = "shadow"; %>` fails with `Duplicate local
  variable out` (observed). The specification also reserves object names with the prefixes `jsp` and `jspx` (the
  published HTML lists each of the two twice, apparently losing the underscore variants) for itself and recommends that
  new implicit objects be introduced through a tag library action such as `defineObjects` rather than as new names.
* **`session` depends on the `session` attribute of the page directive.** With `session="false"` the page does not
  participate in a session, the variable is unavailable and any reference to it is a fatal translation error:
  `session cannot be resolved` (observed).
* **`exception` exists only in an error page** (`isErrorPage="true"`), where it is the `Throwable` that caused the
  dispatch.

Source: https://jakarta.ee/specifications/pages/4.0/jakarta-server-pages-spec-4.0.html#the-page-directive[Jakarta Pages 4.0 -- 1.10.1 The page Directive]

Source: https://jakarta.ee/specifications/pages/4.0/jakarta-server-pages-spec-4.0.html#how-to-define-new-implicit-objects[Jakarta Pages 4.0 -- 7.5.1 How to Define New Implicit Objects]

A tag file has a smaller set (Table JSP.8-5): `request`, `response`, `session`, `application`, `out` and `config`, plus
`jspContext`, a `JspContext` instead of `pageContext`, because a tag file can also run outside a servlet environment. There
is no `page` and no `exception` there.

[#pagecontext]
== PageContext: One Door to Everything

`jakarta.servlet.jsp.PageContext` extends `jakarta.servlet.jsp.JspContext`. The Javadoc describes it as one API that
manages the scoped namespaces, provides convenience accessors for the other implicit objects, supplies the `JspWriter`
and offers forward, include and error handling. The generated code obtains one `PageContext` per request from
`JspFactory.getPageContext`, passing the servlet, the request, the response, the error page URL, whether the page needs
a session, the buffer size and the autoflush flag, and releases it afterwards, which is how `session="false"` and the
`buffer` and `autoFlush` attributes of the page directive reach the runtime. Page authors do not call those lifecycle
methods; the rest of the class is for them and for tag handlers.

.The members of `PageContext` and `JspContext` a page or tag author uses
[cols="2,4",options="header"]
|===
|Member |Purpose

|`PAGE_SCOPE`, `REQUEST_SCOPE`, `SESSION_SCOPE`, `APPLICATION_SCOPE` |the `int` constants 1, 2, 3 and 4 that name the scopes in every scope-taking method (the values are printed by `scopes.jsp` below)
|`setAttribute(name, value)` |stores in page scope; a `null` value is the same as `removeAttribute(name, PAGE_SCOPE)`
|`setAttribute(name, value, scope)` |stores in the given scope; a `null` value removes the attribute from that scope; `IllegalStateException` for `SESSION_SCOPE` when the page does not take part in a session or the session was invalidated
|`getAttribute(name)`, `getAttribute(name, scope)` |reads from page scope, or from the given scope; `null` if absent
|`findAttribute(name)` |searches page, request, session (if valid) and application in that order and returns the first match, or `null`
|`getAttributesScope(name)` |the scope constant in which the name is found first, or 0 when it is nowhere
|`getAttributeNamesInScope(scope)` |an `Enumeration` of all names in one scope
|`removeAttribute(name)` |removes the name from every scope; `removeAttribute(name, scope)` removes it from one
|`getOut()` |the current `JspWriter`; `pushBody()` and `popBody()` swap it for a `BodyContent` while a tag's body is evaluated
|`getRequest()`, `getResponse()`, `getSession()`, `getServletContext()`, `getServletConfig()`, `getPage()`, `getException()` |typed accessors for the other implicit objects; `getSession()` returns `null` when the page has no session
|`getErrorData()` |an `ErrorData` view of the Servlet error attributes, meaningful only in an error page
|`getELContext()` |the `ELContext` the page's expressions are evaluated with
|`forward(path)`, `include(path)`, `include(path, flush)` |dispatch to another resource of the same web application, as `jsp:forward` and `jsp:include` do
|`handlePageException(Throwable)` |called by generated code when an exception escapes: forwards to the page's `errorPage`, or rethrows
|===

Two reasons make the object worth knowing even when a page never mentions it. First, EL, JSTL and tag handlers all read
and write attributes through it: `c:set` calls `pageContext.setAttribute(name, value, scope)`, and the bare `+${name}+`
of EL is `pageContext.findAttribute(name)`. Second, in EL it is the bridge to the scripting objects, because the EL
implicit objects have no `request` or `session`: `+${pageContext.request.contextPath}+` and
`+${pageContext.session.id}+` are the only EL spellings.

[#scopes]
== The Four Scopes

A scope is a named storage area with an owner and a lifetime. The specification (1.8.2) defines four, and each is backed
by an object of the Servlet API, so what a JSP writes is visible to servlets, filters and listeners, and the reverse.

.The four scopes (Jakarta Pages 4.0, 1.8.2)
[cols="1,2,2,2,2",options="header"]
|===
|Scope |Backed by |Lifetime |Reached from a page as |Thread-safety
|page |the `PageContext` of this execution |until the response from this page is sent back, or the request is forwarded elsewhere |`pageContext`, `pageScope` |one thread; nothing to protect
|request |`ServletRequest` attributes |until the request has been processed; reachable from every page that handles the same request, including after a forward |`request`, `requestScope` |one thread, unless a servlet starts asynchronous work
|session |`HttpSession` attributes |until the session ends (timeout, `invalidate()`); not legal in a page with `session="false"` |`session`, `sessionScope` |several requests of one client may run at once: guard mutable values
|application |`ServletContext` attributes |until the context is reclaimed (the web application stops); also reachable from pages that take no part in a session |`application`, `applicationScope` |every request of every user: guard mutable values
|===

The specification adds an ideal that containers are allowed to leave unenforced: a name should mean one object at every
point of the execution, that is, all the scopes should behave as a single name space. A page that stores `who` in
every scope violates the ideal and is a bug waiting to happen, but it is legal and the lookup order decides what the page
sees. The view below exercises exactly that.

.scopes.jsp: one name in four scopes
[source,jsp]
----
<%@ page contentType="text/plain;charset=UTF-8" trimDirectiveWhitespaces="true" %>
<%@ taglib prefix="c" uri="jakarta.tags.core" %>
<c:set var="who" value="page" scope="page"/><c:set var="who" value="session" scope="session"/><c:set var="who" value="application" scope="application"/>
requestScope.who (from the servlet)  : ${requestScope.who}
who, all four scopes hold a value    : ${who} (found in scope ${pageContext.getAttributesScope('who')})
<c:remove var="who" scope="page"/>who after removing the page copy     : ${who} (scope ${pageContext.getAttributesScope('who')})

<%

    pageContext.setAttribute("tmp", "b", jakarta.servlet.jsp.PageContext.REQUEST_SCOPE);

    pageContext.removeAttribute("tmp");

The output demonstrates five rules. The nearest scope wins: the page copy hides the request copy, which hides the session copy,
which hides the application copy. Removing a copy with `c:remove` and a `scope` removes only that one, so the next scope
shows through; `c:remove` without `scope`, like `pageContext.removeAttribute(name)`, removes the name from all scopes at
once, which is what the scriptlet shows. A name found nowhere gives scope 0 and the empty string, never an error. Storing
`null` removes the attribute. The `request` copy came from the servlet, so a servlet-set request attribute and a
JSP-set page attribute are the same kind of thing seen from different sides.

The spec text of `findAttribute` says the session is searched "if valid"; that is the practical meaning of the next view.

[#session-participation]
=== Sessions: Created by Default, Optional with `session="false"`

A JSP page takes part in a session by default. The generated code asks for the session when the page starts, so even a page
that never mentions `session` makes the container create one and send the session cookie. The view below is the smallest
page there is, and the second view opts out.

Source: https://jakarta.ee/specifications/pages/4.0/jakarta-server-pages-spec-4.0.html#the-page-directive[Jakarta Pages 4.0 -- 1.10.1 The page Directive, attribute session]

Source: https://jakarta.ee/specifications/servlet/6.1/jakarta-servlet-spec-6.1.html#creating-a-session[Jakarta Servlet 6.1 -- 7.2 Creating a Session]

Two consequences follow. A public, cacheable page that nobody logs in to should declare `session="false"`, otherwise every
anonymous request creates a session object in memory, sends a cookie that defeats shared caches, and invites session

for a client that refuses cookies it can fall back to URL rewriting, which appends `+;jsessionid=...+` to the links that a page

xref:web/jsp-struts/servlet-fundamentals.adoc#session-security[Session security] and the cookie flags in the
xref:web/jsp-struts/jsp/security.adoc#cookies[Security page].

[#page-scope-and-includes]
=== Page Scope Is Per Page, Not Per Request

Page scope belongs to one `PageContext`, and a `PageContext` belongs to one page execution. Two mechanisms put a second
page into the same request, and they differ exactly in this respect: the `include` directive merges the other file into
the translation unit at translation time, so the two share one page scope, while `jsp:include` calls the other page at
request time, which gets its own `PageContext` and therefore its own page scope but the same request, session and
application scopes.

.includes.jsp, shared-part.jspf and inner.jsp
[source,jsp]
----
<%-- includes.jsp --%>
<%@ page contentType="text/plain;charset=UTF-8" trimDirectiveWhitespaces="true" %>
<%@ taglib prefix="c" uri="jakarta.tags.core" %>
<c:set var="owner" value="includes.jsp" scope="page"/><%@ include file="shared-part.jspf" %>after include directive, page scope sees : [${fromPart}]
<jsp:include page="inner.jsp"/>after jsp:include, page scope sees         : [${pageScope.innerPage}]
after jsp:include, request scope sees      : [${requestScope.innerRequest}]

<%-- shared-part.jspf --%>
<c:set var="fromPart" value="set in shared-part.jspf, owner is ${owner}" scope="page"/>

<%-- inner.jsp --%>
<%@ page contentType="text/plain;charset=UTF-8" trimDirectiveWhitespaces="true" %>
<%@ taglib prefix="c" uri="jakarta.tags.core" %>
<c:set var="innerPage" value="set in inner.jsp (page)" scope="page"/><c:set var="innerRequest" value="set in inner.jsp (request)" scope="request"/>inner.jsp page scope sees owner : [${owner}]
inner.jsp request scope sees who: [${requestScope.who}]
----

.Output of `curl http://localhost:18080/g3implicit/view/includes`
[source,text]
----

inner.jsp page scope sees owner : []
inner.jsp request scope sees who: [request (set by the servlet)]
after jsp:include, page scope sees         : []
after jsp:include, request scope sees      : [set in inner.jsp (request)]
----

Source: https://jakarta.ee/specifications/pages/4.0/jakarta-server-pages-spec-4.0.html#objects-and-scopes[Jakarta Pages 4.0 -- 1.8.2 Objects and Scopes]

So data that an included fragment must read or leave behind travels in request scope (or as `jsp:param` parameters), never
in page scope. The page that covers both inclusion mechanisms in full is xref:web/jsp-struts/jsp/includes-forwards-and-page-composition.adoc[Includes, Forwards and Page Composition] of this
section; here only the scope consequence matters.

[#request-scope]
=== Request Scope: The Controller-to-View Channel

Request scope is the channel of the Model 2 pattern. The servlet computes, calls `request.setAttribute`, and forwards; the
JSP only reads. Because the forward stays inside one request, the attributes arrive, and because a redirect starts a new
request, they do not. The cart view shows request, session and application scope in one page: the servlet put the visit
counter in the application at start-up and a `Book` in the request, and the `cart` list lives in the session across
requests.

.cart.jsp: session and application scope
[source,jsp]
----
<%@ page contentType="text/plain;charset=UTF-8" trimDirectiveWhitespaces="true" %>
<%@ taglib prefix="c" uri="jakarta.tags.core" %>
visits (application scope): ${applicationScope.visits}
catalogue                  : ${applicationScope.catalogName}
cart (session scope)       : <c:forEach var="t" items="${sessionScope.cart}" varStatus="s">${s.first ? '' : ', '}<c:out value="${t}"/></c:forEach>
----

.Two requests with the same cookie jar: `+curl -c jar "...?add=Dune"+` then `+curl -b jar "...?add=Neuromancer"+`
[source,text]
----
visits (application scope): 4
catalogue                  : Bookshelf catalogue
cart (session scope)       : Dune, Neuromancer
----

Source: https://jakarta.ee/specifications/servlet/6.1/jakarta-servlet-spec-6.1.html#binding-attributes-into-a-session[Jakarta Servlet 6.1 -- 7.4 Binding Attributes into a Session]

Source: https://jakarta.ee/specifications/servlet/6.1/jakarta-servlet-spec-6.1.html#lifetime-of-the-request-object[Jakarta Servlet 6.1 -- 3.14 Lifetime of the Request Object]

The visit count was 4 because three earlier requests had passed through `ViewServlet`; the counter is an `AtomicInteger` the
listener stored, which is the right shape for application scope: a mutable object shared by every request thread must be
thread-safe itself. The cart is a plain `ArrayList` in the session, which is acceptable only while one client rarely
sends two requests at the same time; the spec warns that a session can be reached by several threads at once, so a cart
that two browser tabs update concurrently should be a synchronized or copy-on-write structure. In a `distributable`
application every session attribute must also be `Serializable`, which `ArrayList<String>` is and a bean holding a
connection is not.

Source: https://jakarta.ee/specifications/servlet/6.1/jakarta-servlet-spec-6.1.html#important-session-semantics[Jakarta Servlet 6.1 -- 7.7 Important Session Semantics]

[#scope-security]
=== What Belongs in Which Scope

Scope is also a design decision with security consequences. The rule of thumb is to store each value in the narrowest scope
that still works.

.Choosing a scope for Bookshelf data
[cols="2,1,3",options="header"]
|===
|Data |Scope |Reason

|The `Book` a view renders |request |computed per request; gone with the response
|A loop variable or a computed label |page |not needed outside this page; `c:set` defaults to page scope
|The cart, the signed-in user's id, a flash message waiting for the redirected page |session |must survive across requests of one client; keep it small and serializable; never keep another user's data here
|The catalogue name, a read-only reference list, a thread-safe counter |application |identical for everyone; any mutable value needs its own synchronization
|A password, a token, a card number |none of them |do not store secrets in an attribute that a page or a log line could print; look them up when needed
|Per-user data in `application` |never |every user sees and overwrites it: a classic cross-user leak
|===

[#jspwriter]
== JspWriter and the Response Buffer

`out` is a `jakarta.servlet.jsp.JspWriter`, an abstract class that extends `java.io.Writer` and emulates parts of
`BufferedWriter` and `PrintWriter`. Everything the page produces goes through it: the template text, `<%= %>` values, the
output of `c:out` and of every tag. It differs from `PrintWriter` in one respect, which explains the odd signatures: its
`print` methods declare `IOException`.

The writer buffers by default, and the reason matters. If the page is not
buffered, output goes straight to the `PrintWriter` of the response and the headers are committed with the first byte. If
it is buffered, the `PrintWriter` is not even created until the buffer is flushed, so until then the page can still call
`setContentType`, `sendRedirect`, `sendError` or add headers. The specification states that headers are sent only at the
first `flush`; after that those calls are invalid.

.The members of `JspWriter`
[cols="2,4",options="header"]
|===
|Member |Purpose

|`getBufferSize()` |the size of the buffer in bytes
|`getRemaining()` |the number of unused bytes in the buffer
|`isAutoFlush()` |whether an overflow flushes (true) or fails (false)
|`flush()` |writes the buffer to the response and commits it
|`clear()` |discards the buffer; throws `IOException` if the buffer has already been flushed
|`clearBuffer()` |discards the buffer; unlike `clear()` it does not throw after a flush
|`close()` |flushes and closes the stream; the generated code calls it for the initial writer, so a page never needs to
|`print`, `println`, `newLine` |write values; every `print` and `println` overload throws `IOException`
|`NO_BUFFER`, `DEFAULT_BUFFER`, `UNBOUNDED_BUFFER` |constants for the buffering mode; `UNBOUNDED_BUFFER` is for `BodyContent`
|===

Source: https://jakarta.ee/specifications/pages/4.0/apidocs/jakarta.servlet.jsp/jakarta/servlet/jsp/JspWriter.html[Jakarta Pages 4.0 Javadoc -- JspWriter]

Source: https://jakarta.ee/specifications/pages/4.0/jakarta-server-pages-spec-4.0.html#buffering[Jakarta Pages 4.0 -- 11.3 Buffering]

The size and the overflow policy are set with the `buffer` and `autoFlush` attributes of the page directive (the default
is at least 8 KB and `autoFlush="true"`), or for a group of pages with the `buffer` element of a JSP property group. The
view below prints a few facts, discards the buffer, flushes, and then tries to change the response.

.buffer.jsp: the buffer, `clearBuffer`, and the late header
[source,jsp]
----
<%@ page contentType="text/plain;charset=UTF-8" buffer="8kb" autoFlush="true" trimDirectiveWhitespaces="true" %>
buffer size : <%= out.getBufferSize() %>
remaining   : <%= out.getRemaining() %>
autoFlush   : <%= out.isAutoFlush() %>
<%
    out.print("0123456789");
    int before = out.getRemaining();
    out.clearBuffer();
    out.println("remaining before clearBuffer: " + before + ", after: " + out.getRemaining());
    out.flush();
    response.setHeader("X-Late", "ignored");
    response.setStatus(202);
    out.println("committed after flush: " + response.isCommitted());
%>
----

.Output of `curl -si http://localhost:18080/g3implicit/view/buffer`
[source,text]
----
HTTP/1.1 200
Set-Cookie: JSESSIONID=6A03C09DEA200703F6A9A806EB4BB973; Path=/g3implicit; HttpOnly
Content-Type: text/plain;charset=UTF-8
Transfer-Encoding: chunked

remaining before clearBuffer: 8125, after: 8192
committed after flush: true
----

Source: https://jakarta.ee/specifications/pages/4.0/apidocs/jakarta.servlet.jsp/jakarta/servlet/jsp/JspWriter.html#clearBuffer()[Jakarta Pages 4.0 Javadoc -- JspWriter.clearBuffer]

Source: https://jakarta.ee/specifications/pages/4.0/jakarta-server-pages-spec-4.0.html#buffering[Jakarta Pages 4.0 -- 11.3 Buffering]

Read the output carefully. The first three lines of the page, `buffer size`, `remaining` and `autoFlush`, are gone because
`clearBuffer()` discarded everything written so far (the buffer held 67 bytes: 8192 minus 8125). The status is still 200
and there is no `X-Late` header although the scriptlet set a header and a status of 202: both calls came after `flush()`,
which had committed the response, and the container ignores them. The response is chunked because the length was no
longer known when the headers went out.

The second policy is a failure instead of a flush. With `autoFlush="false"` an overflow throws an `IOException`.

.overflow.jsp: `autoFlush="false"` and a 1 KB buffer
[source,jsp]
----
<%@ page contentType="text/plain;charset=UTF-8" buffer="1kb" autoFlush="false" trimDirectiveWhitespaces="true" %>
<%
    out.println("size " + out.getBufferSize() + ", autoFlush " + out.isAutoFlush());
    try {
        for (int i = 0; i < 200; i++) {
            out.print("0123456789");
        }
    } catch (java.io.IOException e) {
        response.setStatus(500);
        out.clearBuffer();
        out.println("IOException: " + e.getMessage());
    }
%>
----

----

----

Source: https://jakarta.ee/specifications/pages/4.0/apidocs/jakarta.servlet.jsp/jakarta/servlet/jsp/JspWriter.html[Jakarta Pages 4.0 Javadoc -- JspWriter, Buffering]

That policy suits pages whose client is an application rather than a browser and needs complete data or none, as the
Javadoc explains; an error page can then still replace a half-built answer.
With `autoFlush="true"` the same loop would flush and commit, and a later error would produce a truncated page with a
200 status. For tags, `pageContext.pushBody()` replaces `out` with a `BodyContent` so a tag can capture the output of
its body, and `popBody()` restores the previous writer; this is how `c:out` and every body tag compose output, and
the custom-tag pages of this section (xref:web/jsp-struts/jsp/custom-tags-classic.adoc[Classic Handlers] and xref:web/jsp-struts/jsp/custom-tags-simple-tag.adoc[SimpleTag]) build on it.

[#el-implicit-objects]
== EL Implicit Objects and How the Resolver Finds Them

In EL the same data is reached through the eleven implicit objects. The JSP container passes a
`jakarta.el.CompositeELResolver` to every expression, and its first component is the `ImplicitObjectELResolver`, so an
implicit object name wins over any attribute of the same name. A bare identifier that matches no implicit object reaches
`ScopedAttributeELResolver` near the end of the chain, which does exactly `pageContext.findAttribute(name)`. The
specification gives the example `+${product}+`: it searches the page, request, session and application scopes in that
order and returns the first match.

.The EL implicit objects (Jakarta Pages 4.0, 2.4)
[cols="1,3,3",options="header"]
|===
|Name |Type and source |Notes

|`pageContext` |the `PageContext` |the only bridge to `request`, `response`, `session`, `servletContext`, `out`, `exception`, `errorData`
|`pageScope` |`Map`, page-scoped attributes |only the page scope, no search
|`requestScope` |`Map`, request-scoped attributes |only the request scope
|`sessionScope` |`Map`, session-scoped attributes |empty, not an error, when the page has no session
|`applicationScope` |`Map`, application-scoped attributes |only the application scope
|`param` |`Map` name to one `String`, from `ServletRequest.getParameter` |first value of a repeated parameter
|`paramValues` |`Map` name to `String[]`, from `getParameterValues` |all values; `+${paramValues.tag[1]}+`
|`header` |`Map` name to one `String`, from `HttpServletRequest.getHeader` |header names are case-insensitive; bracket syntax for names with a hyphen: `+${header['user-agent']}+`
|`headerValues` |`Map` name to `String[]`, from `getHeaders` |all values of a repeated header
|`cookie` |`Map` name to one `Cookie`, per `HttpServletRequest.getCookies` |the first cookie of a name wins; its order is unspecified by Servlet, so do not rely on duplicates; `+${cookie.theme.value}+`
|`initParam` |`Map` name to `String`, from `ServletContext.getInitParameter` |the `<context-param>` entries of `web.xml`
|===

Source: https://jakarta.ee/specifications/pages/4.0/jakarta-server-pages-spec-4.0.html#_Implicit_Objects[Jakarta Pages 4.0 -- 2.4 Implicit Objects (EL)]

Source: https://jakarta.ee/specifications/pages/4.0/jakarta-server-pages-spec-4.0.html#resolution-of-variables-and-their-properties[Jakarta Pages 4.0 -- 2.10 Resolution of Variables and their Properties]

Because the resolver chain is shared with the whole EL language, its order is worth knowing: after the implicit objects
come the resolvers registered with `JspApplicationContext.addELResolver` (the hook Jakarta Faces uses), the stream
resolver, `StaticFieldResolver`, `MapELResolver`, `ResourceBundleELResolver`, `ListELResolver`, `ArrayELResolver`,
`RecordELResolver`, `BeanELResolver` (everything with a non-null base), and then `ScopedAttributeELResolver`,
`ImportELResolver` and `NotFoundELResolver` for names without a base. `NotFoundELResolver` always resolves, returning
`null`, which is why an unknown name prints nothing; the `errorOnELNotFound` setting turns that into a
`PropertyNotFoundException` and is the first thing to switch on while developing. The EL language itself, operators and
type coercion are on the xref:web/jsp-struts/jsp/expression-language-basics.adoc[Expression Language Basics] and xref:web/jsp-struts/jsp/el-operators-and-type-coercion.adoc[EL Operators & Type Coercion] pages of this section.

.el.jsp: the EL implicit objects and two traps
[source,jsp]
----
<%@ page contentType="text/plain;charset=UTF-8" trimDirectiveWhitespaces="true" %>
<%@ taglib prefix="c" uri="jakarta.tags.core" %>
<c:set var="param" value="attribute named param" scope="request"/>
param.q                    : ${param.q}
paramValues.tag[1]         : ${paramValues.tag[1]}
header.accept              : ${header.accept}
header['x-shelf']          : ${header['x-shelf']}
headerValues['x-shelf'][0] : ${headerValues['x-shelf'][0]}
cookie.theme.value         : ${cookie.theme.value}
initParam.shelfName        : ${initParam.shelfName}
context path               : ${pageContext.request.contextPath}
method                     : ${pageContext.request.method}
request.method (no such object) : [${request.method}]
requestScope.param         : ${requestScope.param}
requestScope.book.title    : ${requestScope.book.title}
sessionScope               : ${empty sessionScope ? 'empty' : 'has entries'}
----

.Output of `+curl -H 'X-Shelf: top' -H 'Cookie: theme=dark' "http://localhost:18080/g3implicit/view/el?q=dune&tag=sf&tag=classic"+`
[source,text]
----
param.q                    : dune
paramValues.tag[1]         : classic
header.accept              : */*
header['x-shelf']          : top
headerValues['x-shelf'][0] : top
cookie.theme.value         : dark

requestScope.param         : attribute named param
requestScope.book.title    : Dune

----

Source: https://jakarta.ee/specifications/pages/4.0/jakarta-server-pages-spec-4.0.html#_Implicit_Objects[Jakarta Pages 4.0 -- 2.4 Implicit Objects (EL)]

Source: https://jakarta.ee/specifications/pages/4.0/jakarta-server-pages-spec-4.0.html#unknown-el-identifiers[Jakarta Pages 4.0 -- 2.7 Unknown EL Identifiers]

The two traps are in the output. `+${request.method}+` is empty because EL has no `request` object: `request` there is
just a name that the scoped-attribute resolver looks up as an attribute, finds nowhere, and resolves to `null`; the
correct spelling is `+${pageContext.request.method}+`, and nothing warns about the mistake unless `errorOnELNotFound` is
on. And `+${param.q}+` still worked after `c:set` created a request attribute called `param`, because the implicit object
`param` is consulted first; the attribute is reachable only as `+${requestScope.param}+`. The same shadowing applies to
`header`, `cookie`, `initParam`, `pageContext` and the scope names, so never name an attribute after an implicit object.

Request data is untrusted. `param`, `header`, `cookie` and `initParam` values reach the page unchanged, and `+${...}+` in
template text does not escape them. The next view shows the difference in an HTML page, with the query parameter `q`
set to a script tag.

.escape.jsp: raw EL versus `c:out`
[source,jsp]
----
<%@ page contentType="text/html;charset=UTF-8" trimDirectiveWhitespaces="true" %>

<p>raw   : ${param.q}</p>
<p>c:out : <c:out value="${param.q}"/></p>
----

.Output for `q=<script>alert(1)</script>` (URL-encoded in the request)
[source,html]
----
<p>raw   : <script>alert(1)</script></p>
<p>c:out : &lt;script&gt;alert(1)&lt;/script&gt;</p>
----

Source: https://jakarta.ee/specifications/tags/3.0/jakarta-tags-spec-3.0.html#c:out[Jakarta Standard Tag Library 3.0 -- c:out]

The first line is a cross-site scripting hole; the second is the secure default. Every EL expression that prints request
data into HTML goes through `c:out` (or `fn:escapeXml`, or an encoder of the OWASP Java Encoder library), and the
`escapeXml` attribute of `c:out` defaults to true. The scope maps are equally untrusted when the value came from a user:
data stored in `sessionScope` by one request is output by another.

[#scriptlet-vs-attribute]
=== Scriptlet Locals Are Not Attributes

Java local variables of a scriptlet and scope attributes are different things that merely share a page. EL sees only
attributes, and a scriptlet sees only locals plus whatever it fetches from a scope.

.locals.jsp
[source,jsp]
----
<%@ page contentType="text/plain;charset=UTF-8" trimDirectiveWhitespaces="true" %>
<%@ taglib prefix="c" uri="jakarta.tags.core" %>
<% String shelf = "local variable"; pageContext.setAttribute("note", "page attribute"); %>
EL sees the scriptlet local shelf : [${shelf}]
scriptlet sees the attribute note : [<%= (String) pageContext.getAttribute("note") %>]
EL sees the attribute note        : [${note}]
----

[source,text]
----
EL sees the scriptlet local shelf : []
scriptlet sees the attribute note : [page attribute]
EL sees the attribute note        : [page attribute]
----

Source: https://jakarta.ee/specifications/pages/4.0/jakarta-server-pages-spec-4.0.html#objects-and-variables[Jakarta Pages 4.0 -- 1.8.1 Objects and Variables]

To hand a scriptlet value to EL, store it with `pageContext.setAttribute`; to hand an EL-visible value to a scriptlet, read
it with `pageContext.findAttribute`. Mixing the two styles in one page is the usual reason for the question "why is my
variable empty", and the cure is to stop writing scriptlets (see the xref:web/jsp-struts/jsp/scripting-elements.adoc[Scripting Elements] page of this section).

[#config-and-page]
== `config` and `page`

`config` is the `ServletConfig` of the servlet that executes the page. For a plain `.jsp` file the container creates that
servlet itself, with the name `jsp` on Tomcat and no initialization parameters; the two things a page author uses it for are
`getServletName()` and `+getInitParameter(...)+`, which are meaningful once the page is declared in `web.xml` with
`<jsp-file>`, so that the declaration can carry `<init-param>` entries. `getServletContext()` returns the same object as
`application`. `page` is the page instance, `this`, and is almost never useful to page code.

.web.xml: a `jsp-file` servlet with an init parameter, a context parameter, and `config.jsp`
[source,xml]
----
<context-param>
    <param-name>shelfName</param-name>
    <param-value>Main shelf</param-value>
</context-param>

<servlet>
    <servlet-name>shelfConfig</servlet-name>
    <jsp-file>/WEB-INF/views/implicit/config.jsp</jsp-file>
    <init-param>
        <param-name>pageSize</param-name>
        <param-value>20</param-value>
    </init-param>
</servlet>
<servlet-mapping>
    <servlet-name>shelfConfig</servlet-name>
    <url-pattern>/config</url-pattern>
</servlet-mapping>
----

[source,jsp]
----
<%@ page contentType="text/plain;charset=UTF-8" trimDirectiveWhitespaces="true" %>
servlet name        : <%= config.getServletName() %>
init-param pageSize : <%= config.getInitParameter("pageSize") %>
context-param       : <%= application.getInitParameter("shelfName") %>
application same as config.getServletContext(): <%= application == config.getServletContext() %>
page == this        : <%= page == this %>
----

.Output of `curl http://localhost:18080/g3implicit/config`
[source,text]
----
servlet name        : shelfConfig
init-param pageSize : 20
context-param       : Main shelf
application same as config.getServletContext(): true
page == this        : true
----

Source: https://jakarta.ee/specifications/servlet/6.1/apidocs/jakarta.servlet/jakarta/servlet/ServletConfig.html[Jakarta Servlet 6.1 Javadoc -- ServletConfig]

Source: https://jakarta.ee/specifications/pages/4.0/jakarta-server-pages-spec-4.0.html#implicit-objects[Jakarta Pages 4.0 -- 1.8.3 Implicit Objects]

For a context-wide setting prefer the `<context-param>` and read it as `+${initParam.shelfName}+`; the per-page
`config` is the right tool only for a page that is genuinely one configured servlet.

[#exception-and-error-data]
== `exception` and `pageContext.errorData`

A page names its error page with `+errorPage="..."+` in the page directive, and a page that serves as an error page declares
`isErrorPage="true"`. Only then does the `exception` variable exist, and `pageContext.getErrorData()` returns an
`ErrorData` with the facts the Servlet container recorded in the `+jakarta.servlet.error.*+` request attributes. Pages 4.0
added `method` and `queryString` to `ErrorData`, together with the matching Servlet 6.1 attributes
`jakarta.servlet.error.method` and `jakarta.servlet.error.query_string`. The full error-handling story, including
`web.xml` error pages and their precedence, is the subject of the xref:web/jsp-struts/jsp/error-handling.adoc[Error Handling] page of this section.

.boom.jsp and error.jsp
[source,jsp]
----
<%-- boom.jsp --%>
<%@ page contentType="text/plain;charset=UTF-8" errorPage="error.jsp" %>
<% if (true) { throw new IllegalStateException("shelf is full"); } %>

<%-- error.jsp --%>
<%@ page contentType="text/plain;charset=UTF-8" isErrorPage="true" trimDirectiveWhitespaces="true" %>
exception          : <%= exception %>
errorData.status   : ${pageContext.errorData.statusCode}
errorData.method   : ${pageContext.errorData.method}
errorData.uri      : ${pageContext.errorData.requestURI}
errorData.query    : ${pageContext.errorData.queryString}
errorData.servlet  : ${pageContext.errorData.servletName}

The request URI is the path of the page that failed (the forward target under `WEB-INF`), not the URL the user typed, and
the servlet name `jsp` is the Tomcat servlet that compiles and runs every JSP. Two cautions follow. The exception message
and class are internal information, so an error page for the public prints a generic message and logs the throwable; the
`exception` and `errorData` objects are for the log. And the `PageContext` Javadoc says `getErrorData` is meaningless in
a page that is not an error page.

[#tag-files]
== Implicit Objects and Scopes in a Tag File

A tag file is a JSP fragment packaged as a custom tag. It has its own page scope, `jspContext` is its context object, and
the request, session and application scopes are the caller's. The tag below writes one attribute to its own page scope
and one to the request, and prints the class of its `jspContext`.

.WEB-INF/tags/card.tag and tagfile.jsp
[source,jsp]
----
<%-- card.tag --%>
<%@ tag body-content="empty" trimDirectiveWhitespaces="true" %>
<%@ taglib prefix="c" uri="jakarta.tags.core" %>
<c:set var="tagLocal" value="private to the tag file" scope="page"/>
<c:set var="tagShared" value="visible to the caller" scope="request"/>
jspContext class: <%= jspContext.getClass().getName() %>
tag sees its own page scope: [${tagLocal}]
tag sees the request attribute book.title: [${requestScope.book.title}]

<%-- tagfile.jsp --%>
<%@ page contentType="text/plain;charset=UTF-8" trimDirectiveWhitespaces="true" %>
<%@ taglib prefix="b" tagdir="/WEB-INF/tags" %>
<b:card/>
page scope after the tag   : [${tagLocal}]
request scope after the tag: [${requestScope.tagShared}]
----

.Output of `curl http://localhost:18080/g3implicit/view/tagfile`
[source,text]
----
jspContext class: org.apache.jasper.runtime.JspContextWrapper
tag sees its own page scope: [private to the tag file]
tag sees the request attribute book.title: [Dune]
page scope after the tag   : []
request scope after the tag: [visible to the caller]
----

Source: https://jakarta.ee/specifications/pages/4.0/jakarta-server-pages-spec-4.0.html#implicit-objects-2[Jakarta Pages 4.0 -- 8.8 Implicit Objects (tag files)]

Source: https://jakarta.ee/specifications/pages/4.0/apidocs/jakarta.servlet.jsp/jakarta/servlet/jsp/JspContext.html[Jakarta Pages 4.0 Javadoc -- JspContext]

The page scope of the tag file is private: the caller does not see `tagLocal` unless the tag declares it with a
`variable` directive, which synchronizes a tag-file variable with the caller's page scope. The request attribute is the
shared channel, and a tag that writes request attributes without documenting them is a source of surprising coupling.
The xref:web/jsp-struts/jsp/tag-files-and-layouts.adoc[Tag Files & Layouts] and xref:web/jsp-struts/jsp/custom-tags-classic.adoc[Custom Tags] pages of this section cover `variable`, `attribute` and the variable-synchronization rules.

[#pitfalls]
== Pitfalls and Error Names

.Implicit-object and scope pitfalls (rows marked "observed" were reproduced on Tomcat 11.0.26)
[cols="3,3,3",options="header"]
|===
|Symptom or error |Cause |Fix

|`+${request.contextPath}+` prints nothing (observed) |EL has no `request` object; the name resolves to a missing attribute and `NotFoundELResolver` returns `null` |`+${pageContext.request.contextPath}+`; enable `errorOnELNotFound` in development
|`request cannot be resolved` in a `<%! %>` declaration (observed) |declarations are outside the service method, so the implicit variables do not exist there |pass the value as a method parameter, or drop the declaration
|`Duplicate local variable out` (observed) |a scriptlet redeclared an implicit variable name |choose another name; never reuse the nine names or the `jsp`/`jspx` prefixes
|`session cannot be resolved` (observed) |the page says `session="false"` and a scriptlet or expression uses `session` |remove the use, or take `session` back; in EL use `sessionScope`, which is empty
|`IllegalStateException: Cannot access session scope in page that does not participate in any session` (observed) |`+setAttribute(..., SESSION_SCOPE)+` on a page with `session="false"`, or after `invalidate()` |write to the session from a page that takes part in one, or from a servlet
|Every anonymous request gets a `JSESSIONID` cookie (observed) |JSPs take part in a session by default |`session="false"` on public pages
|An included page cannot see the including page's variable (observed) |`jsp:include` runs the target with its own page scope; only the include directive merges scopes |pass data as request attributes or `jsp:param`
|A page attribute named `param`, `header`, `cookie`, `pageContext` ... is ignored by `+${param}+` (observed) |implicit objects are resolved before attributes |reach the attribute as `+${requestScope.param}+` and rename it
|Scriptlet local variable is empty in EL (observed) |EL reads attributes, not Java locals |`pageContext.setAttribute`, or `c:set` instead of a local
|Header or status set late has no effect (observed) |the buffer was flushed, so the response was committed |set headers first; avoid explicit `out.flush()` in a page
|`IOException: Error: JSP Buffer overflow` (observed) |`autoFlush="false"` and output larger than the buffer |raise `buffer`, or write less, or use `autoFlush="true"`
|The top of the page is missing after `clearBuffer()` (observed) |`clearBuffer()` discards everything written so far, template text included |call it before the first output you want to keep, or not at all
|A counter in `application` scope loses updates |a plain `int` or `Integer` shared by all request threads |`AtomicInteger`, `LongAdder`, or a synchronized service
|One user sees another's data |per-user data stored in `application` scope, or a static field |keep user data in `session` or request scope
|`NotSerializableException` on session persistence or replication |a non-serializable object in a session of a `distributable` application |store `Serializable` values only
|Request attribute missing after a redirect |a redirect is a new request; request scope ends with the first response |store it in the session, or pass it as a query parameter and re-read it
|`+${param.q}+` prints raw HTML (observed) |EL does not escape |`c:out`, `fn:escapeXml` or an encoder
|`PropertyNotFoundException` for an EL name |`errorOnELNotFound` is on and the name is in no scope, or a typo in a bean property |check `+${pageContext.getAttributesScope('name')}+` (0 means missing)
|===

== What Changed Recently

.Changes that touch the implicit objects and scopes
[cols="2,3",options="header"]
|===
|Change |Detail

|Pages 4.0 (Jakarta EE 11) |minimum Java 17; the deprecated classes of the `jakarta.servlet.jsp.el` package are removed (`ExpressionEvaluator`, `VariableResolver` and the rest of the JSP 2.0 expression API; `JspContext` no longer has `getExpressionEvaluator` or `getVariableResolver`), together with `BodyTag.EVAL_BODY_TAG`, `JspException.getRootCause`, the `isThreadSafe` page attribute and `jsp:plugin`. `ErrorData` gains the method and the query string

|EL 6.0 |`RecordELResolver` is in the JSP resolver chain, so a `record` such as `Book` works as a bean (verified on Tomcat 11.0.26; see the Getting Started page for the GlassFish finding)

|Servlet 6.1 |`jakarta.servlet.error.method` and `jakarta.servlet.error.query_string` request attributes; `HttpSession.Accessor`

[#books-outdated]
== Where the Books Are Outdated

The implicit objects and the four scopes are the part of JSP that has changed least since 2001, so the concepts the books
teach (_Web Development with JavaServer Pages_ chapters 4 and 6, and _JSTL in Action_ chapters 1 to 3, listed in the
section bibliography) still hold. What has moved around them is the platform, the style and a few APIs.

.Material from the books and its current equivalent
[cols="3,4",options="header"]
|===
|The books' era |Today (Pages 4.0, EL 6.0, Servlet 6.1)

|The nine implicit objects used in scriptlets throughout |still valid; but scriptlets are legacy, and pages read data through EL and JSTL, with scripting switched off by a `scripting-invalid` property group
|`javax.servlet.jsp.PageContext`, `javax.servlet.http.HttpSession` |`jakarta.servlet.jsp.PageContext`, `jakarta.servlet.http.HttpSession` since Jakarta EE 9
|`session.getValue`, `putValue`, `HttpSessionContext`, `HttpUtils.getRequestURL` |removed in Servlet 6.0; `getAttribute`, `setAttribute` and `request.getRequestURL()`
|`<%@ page isThreadSafe="false" %>` to serialize access to a page |removed in Pages 4.0 together with `SingleThreadModel`; make the data thread-safe instead
|EL only inside JSTL 1.0 attribute values (the `rt` libraries) or no EL at all |container EL everywhere since JSP 2.0, with the implicit objects of this page
|JSP 1.2 and JSTL 1.0 `+http://java.sun.com/jstl/...+` URIs |`jakarta.tags.core` (and the other four), JSTL 3.0
|`+${param.name}+` and the `rt` expression libraries for escaping |`c:out` and `fn:escapeXml`; every `+${}+` into HTML needs one of them
|`session` assumed on every page without discussing the cookie it creates |`session="false"` for pages that do not need one; session cookie flags `HttpOnly`, `Secure`, `SameSite` configured in `web.xml`
|`pageContext.getExpressionEvaluator()`, `getVariableResolver()` (JSP 2.0 API) |removed in Pages 4.0; use `pageContext.getELContext()` and an `ExpressionFactory`
|Application-managed scope usage with per-user maps in `application` |a per-user value belongs to the session; shared mutable state needs thread-safe types
|`jsp:plugin` in the same chapter as the standard actions |removed in Pages 4.0, as applets are no longer supported by browsers
|===
