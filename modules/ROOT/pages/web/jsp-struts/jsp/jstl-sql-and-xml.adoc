== What the Two Libraries Are and Why They Are Discouraged

The Standard Tag Library has five libraries. Three of them (core, formatting and functions) are the everyday tools of a page
author; the other two reach outside the view layer. The table lists them as the specification and the tag library
descriptors of the implementation define them.

.The two legacy libraries of Jakarta Tags 3.0
[cols="2,3,3,4",options="header"]
|===
|Library |URI and prefix |Tags |What it is for

|SQL |`jakarta.tags.sql`, prefix `sql` |`sql:setDataSource`, `sql:query`, `sql:update`, `sql:transaction`, `sql:param`, `sql:dateParam` |Run JDBC queries and updates from a page, show the rows, group updates into a transaction (spec chapter 10)
|XML core |`jakarta.tags.xml`, prefix `x` |`x:parse`, `x:out`, `x:set` |Parse an XML document and evaluate XPath 1.0 expressions against it (spec chapter 11)
|XML flow control |`jakarta.tags.xml`, prefix `x` |`x:if`, `x:choose`, `x:when`, `x:otherwise`, `x:forEach` |Decide and loop on XPath results (spec chapter 12)
|XML transform |`jakarta.tags.xml`, prefix `x` |`x:transform`, `x:param` |Apply an XSLT 1.0 stylesheet to a document (spec chapter 13)
|===

Source: https://jakarta.ee/specifications/tags/3.0/jakarta-tags-spec-3.0.html#sql-actions-sql-tag-library[Jakarta Standard Tag Library 3.0 -- 10 SQL Actions]

Source: https://jakarta.ee/specifications/tags/3.0/jakarta-tags-spec-3.0.html#xml-core-actions-xml-tag-library[Jakarta Standard Tag Library 3.0 -- 11 XML Core Actions]

The old Sun URIs `+http://java.sun.com/jsp/jstl/sql+` and `+http://java.sun.com/jsp/jstl/xml+` are still accepted by the
3.0.1 implementation on Tomcat 11 (a page that declares them runs; checked), but the URIs of JSTL 3.0 are the `jakarta.tags.*`
ones, and only those are used on this page. The JSTL 1.0 URIs `+http://java.sun.com/jstl/sql+` and the `_rt` twin libraries
of the older books are another matter, covered in <<books-outdated>>.

=== Why they are discouraged

The sentence that opens chapter 10 of the specification is the whole argument: it is _generally preferred_ to have database
operations handled in the business logic of an MVC application, but there are situations where a page author needs them
within the page: prototyping and testing, small and simple applications, lack of developer resources. Nothing in the
libraries is wrong for those cases, and nothing in them scales beyond them.

.Why `sql:*` and `x:*` stay at the prototype end of a project
[cols="2,5,4",options="header"]
|===
|Concern |What happens |What to do instead

|Layering |SQL (or XPath and XSLT) lives in the view, so the view is coupled to table and column names, cannot be unit tested without a container and cannot be reused by a REST endpoint or a batch job |Query in a servlet or a service, put the result in a request attribute, let the page only print it (see <<alternatives>>)
|Connection management |`sql:setDataSource` with `url`, `driver`, `user` and `password` uses `DriverManager`; the specification says it should not be used other than for prototyping because it provides no connection management |A `javax.sql.DataSource` from the container (JNDI) or from the application, with a pool
|Injection |A statement built with `+${...}+` inside the body of `sql:query` is plain string concatenation (shown in <<sql-param>>); the safe form needs a `?` marker and a nested `sql:param` for every value |Parameters always; better, no SQL in pages
|Transactions |`sql:transaction` is a JDBC `Connection` transaction; its behaviour is undefined inside a larger JTA user transaction, and a rollback cannot be forced from SQL |A transaction owned by a service
|Error handling and leaks |Every failure becomes a `JspException` whose message contains the SQL statement, which must not reach a visitor |Catch and log in Java, show a reference number (see the xref:web/jsp-struts/jsp/error-handling.adoc[error handling page])
|XML parsing |Whole documents become trees in memory inside a page, with parser security that depends on the implementation (see <<xml-security>>) |Parse in Java with Jakarta XML Binding or StAX and a hardened factory, and hand the page beans
|Testing and tooling |XPath and SQL errors surface at run time as `JspException` messages with a page line number |Plain Java classes with real tests
|===

Source: https://jakarta.ee/specifications/tags/3.0/jakarta-tags-spec-3.0.html#sql-actions-sql-tag-library[Jakarta Standard Tag Library 3.0 -- 10 SQL Actions (introduction)]

Source: https://jakarta.ee/specifications/tags/3.0/jakarta-tags-spec-3.0.html#data-source[Jakarta Standard Tag Library 3.0 -- 10.1.1 Data Source]

Source: https://jakartaee.github.io/jakartaee-documentation/jakartaee-tutorial/current/web/jakarta-tags/jakarta-tags.html[Jakarta EE Tutorial -- Jakarta Tags]

The Jakarta EE Tutorial page for Jakarta Tags lists the XML, internationalisation and SQL libraries under a sentence saying
that a subset has been archived, and says the core library and the JSTL functions are still available in Facelets. The issue
that planned this section paraphrased the sentence as "the SQL, XML and i18n parts are archived"; this page uses the
tutorial's own wording, which does not name the three libraries as removed from the specification (they are in the 3.0
specification and in Jakarta EE 11), only as no longer the recommended route.

A throwaway `setup.jsp` creates and fills the two tables (a book and the number of copies on each of two shelves). It
already uses most of the tags described below, which is why it comes first: DDL through `sql:update`, a transaction around
several statements, parameters for every value and `sql:dateParam` for a date. The `fmt:` tags only produce the date and are
described on the xref:web/jsp-struts/jsp/jstl-formatting.adoc[JSTL Formatting] page of this section.

.setup.jsp (abridged: the five inserts are one loop)
[source,jsp]
----
<%@ page contentType="text/plain;charset=UTF-8" trimDirectiveWhitespaces="true" %>
<%@ taglib prefix="c" uri="jakarta.tags.core" %>
<%@ taglib prefix="sql" uri="jakarta.tags.sql" %>
<%@ taglib prefix="fmt" uri="jakarta.tags.fmt" %>
<sql:transaction>
    <sql:update>DROP TABLE IF EXISTS shelf</sql:update>
    <sql:update>DROP TABLE IF EXISTS book</sql:update>
    <sql:update>
        CREATE TABLE book (
            id BIGINT PRIMARY KEY,
            title VARCHAR(200) NOT NULL,
            author VARCHAR(100) NOT NULL,
            published_year INT NOT NULL,
            added_on DATE NOT NULL)
    </sql:update>
    <sql:update>
        CREATE TABLE shelf (
            book_id BIGINT NOT NULL REFERENCES book(id),
            location VARCHAR(20) NOT NULL,
            copies INT NOT NULL CHECK (copies >= 0),
            PRIMARY KEY (book_id, location))
    </sql:update>
</sql:transaction>
<fmt:setLocale value="en"/>
<fmt:parseDate var="d" value="2026-10-08" pattern="yyyy-MM-dd"/>
<c:set var="titles" value="${['Dune','Neuromancer','Foundation','Solaris','Hyperion']}"/>
<c:set var="authors" value="${['Frank Herbert','William Gibson','Isaac Asimov','Stanislaw Lem','Dan Simmons']}"/>
<c:set var="years" value="${[1965,1984,1951,1961,1989]}"/>
<sql:transaction>
<c:forEach var="t" items="${titles}" varStatus="s">
    <sql:update var="n">
        INSERT INTO book (id, title, author, published_year, added_on) VALUES (?, ?, ?, ?, ?)
        <sql:param value="${s.count}"/>
        <sql:param value="${t}"/>
        <sql:param value="${authors[s.index]}"/>
        <sql:param value="${years[s.index]}"/>
        <sql:dateParam value="${d}" type="date"/>
    </sql:update>
inserted ${s.count}: ${t} (${n} row)
</c:forEach>
<sql:update>INSERT INTO shelf VALUES (1, 'MAIN', 3)</sql:update>
<sql:update>INSERT INTO shelf VALUES (1, 'ANNEX', 0)</sql:update>
</sql:transaction>
done
----

Source: https://jakarta.ee/specifications/tags/3.0/jakarta-tags-spec-3.0.html#sqlupdate[Jakarta Standard Tag Library 3.0 -- 10.4 sql:update]

`curl http://localhost:18080/g5jstlsqlxml/setup.jsp` prints `inserted 1: Dune (1 row)` through `inserted 5: Hyperion (1 row)`
and `done`. The page is a setup script, not a design: it may be called by anyone who can reach the URL and it drops the
tables, which is the first reason it must never ship.

[#sql-datasource]
== Choosing the Data Source

Every SQL tag that talks to a database needs a `javax.sql.DataSource`, and the same algorithm finds it for
`sql:query`, `sql:update` and `sql:transaction`. The specification (10.2) gives the steps, and the diagram follows them.

[mermaid]
....
flowchart TD
    start["sql:query, sql:update or sql:transaction runs"] --> tx{"query or update nested in sql:transaction?"}
    tx -->|"yes"| parent["Use the connection of the parent transaction"]
    tx -->|"no"| attr{"dataSource attribute set?"}
    attr -->|"yes"| val["Use its value"]
    attr -->|"no"| cfg{"Configuration variable jakarta.servlet.jsp.jstl.sql.dataSource found by Config.find?"}
    cfg -->|"yes"| val
    cfg -->|"no"| err1["JspException: dataSource is null"]
    val --> kind{"Type of the value?"}
    kind -->|"javax.sql.DataSource object"| conn["getConnection()"]
    kind -->|"String"| jndi{"Lookup of java:comp/env/ plus the string succeeds?"}
    jndi -->|"yes"| conn
    jndi -->|"no"| dm["Read the string as url, driver, user, password and use DriverManager"]
    dm -->|"fails"| err2["JspException: Unable to get connection"]
    dm -->|"works"| conn
....

The value can therefore be given in five ways. The page `datasource.jsp` uses all of them in turn against the same database.

.The ways to name a data source
[cols="3,4,4",options="header"]
|===
|Form |Where it is written |Notes

|Configuration variable |`jakarta.servlet.jsp.jstl.sql.dataSource`: a context parameter in `web.xml`, `sql:setDataSource` without `var`, or `Config.set` in Java (`Config.SQL_DATA_SOURCE`) |Used when a tag has no `dataSource` attribute; the page needs no JDBC knowledge. A `String` here is read like the attribute below
|Attribute with a `DataSource` object |`dataSource="+${applicationScope.ds}+"` |Needs a servlet, a listener or `sql:setDataSource var` to put the object in a scope
|Attribute with a JNDI relative path |`dataSource="jdbc/bookshelf"` |`java:comp/env/` is prepended; the `Resource` is declared in `context.xml` or the server
|Attribute with the JDBC parameter string |`dataSource="url,driver,user,password"` |A comma inside a parameter is written `\,` and a backslash `\\`; for prototypes only
|`sql:setDataSource` with `url`, `driver`, `user`, `password` |Page or servlet code |Stores a `DataSource` (or the string) in `var`, or sets the configuration variable when there is no `var`; the four attributes are a simpler spelling of the parameter string
|===

.sql:setDataSource attributes
[cols="2,2,6",options="header"]
|===
|Attribute |Type |Meaning

|`dataSource` |`String` or `javax.sql.DataSource` |Alternative to the four JDBC attributes: a `DataSource`, a JNDI relative path or a parameter string
|`url` |`String` |JDBC URL (`jdbc:h2:mem:bookshelf;DB_CLOSE_DELAY=-1` in the examples)
|`driver` |`String` |Driver class name, loaded when given
|`user`, `password` |`String` |Credentials passed to `DriverManager`; an empty string when omitted
|`var` |`String` |Name of the exported variable (not dynamic)
|`scope` |`String` |Scope of `var`, or of the configuration variable when there is no `var` (default `page`)
|===

The tag is empty (no body), and a null `dataSource` is a `JspException`.

.datasource.jsp
[source,jsp]
----
<%@ taglib prefix="c" uri="jakarta.tags.core" %>
<%@ taglib prefix="sql" uri="jakarta.tags.sql" %>
<%-- 1. DriverManager parameters in a scoped variable (prototyping only; placeholder credentials) --%>
<sql:setDataSource var="proto" url="jdbc:h2:mem:bookshelf;DB_CLOSE_DELAY=-1" driver="org.h2.Driver" user="sa" password=""/>
<sql:query var="a" dataSource="${proto}">SELECT COUNT(*) AS n FROM book</sql:query>
A: ${a.rows[0].n} (setDataSource var)
<%-- 2. the "url,driver,user,password" string form --%>
<sql:query var="b" dataSource="jdbc:h2:mem:bookshelf;DB_CLOSE_DELAY=-1,org.h2.Driver,sa,">SELECT COUNT(*) AS n FROM book</sql:query>
B: ${b.rows[0].n} (parameter string)
<%-- 3. a JNDI relative path, java:comp/env/ is prepended --%>
<sql:query var="c1" dataSource="jdbc/bookshelf">SELECT COUNT(*) AS n FROM book</sql:query>
C: ${c1.rows[0].n} (JNDI relative path)
<%-- 4. the configuration variable set by the deployment descriptor (no dataSource attribute) --%>
<sql:query var="d" sql="SELECT COUNT(*) AS n FROM book"/>
D: ${d.rows[0].n} (web.xml context-param)
<%-- 5. setDataSource without var sets the configuration variable for the rest of the page scope --%>
<sql:setDataSource url="jdbc:h2:mem:other" driver="org.h2.Driver" user="sa" password=""/>
<c:catch var="err"><sql:query var="e">SELECT COUNT(*) AS n FROM book</sql:query></c:catch>
E: <c:out value="${empty err ? e.rows[0].n : err.cause.message}"/>
<%-- 6. missing JNDI name and no configuration --%>
<c:catch var="err2"><sql:query var="f" dataSource="jdbc/missing">SELECT 1</sql:query></c:catch>
F: <c:out value="${err2.message}"/>
----

Source: https://jakarta.ee/specifications/tags/3.0/jakarta-tags-spec-3.0.html#sql:setDataSource[Jakarta Standard Tag Library 3.0 -- 10.6 sql:setDataSource]

Source: https://jakarta.ee/specifications/tags/3.0/jakarta-tags-spec-3.0.html#database-access[Jakarta Standard Tag Library 3.0 -- 10.2 Database Access]

The output shows what each form does, including the surprising last two cases (line 5 is another empty in-memory database,
and line 6 shows the message for a name that is neither a JNDI resource nor a JDBC string):

[source,text]
----
A: 5 (setDataSource var)
B: 5 (parameter string)
C: 5 (JNDI relative path)
D: 5 (web.xml context-param)
E: Table "BOOK" not found (this database is empty); SQL statement:
SELECT COUNT(*) AS n FROM book [42104-252]
F: Unable to get connection, DataSource invalid: "java.sql.SQLException: No suitable driver found for jdbc/missing"
----

Case 5 is the pitfall: `sql:setDataSource` without `var` replaces the configuration variable for the page scope, so every
later tag of the page that has no `dataSource` attribute uses the new database, whatever `web.xml` says. A JNDI name that
is not bound is not reported as "name not found": the algorithm falls through to the JDBC parameter string, and the error
is the one from `DriverManager`. The helper tags are also scoped by `scope`: a `sql:setDataSource` with `scope="application"`
in a page changes the data source of every page that runs afterwards (verified: after one request to such a page, an
unrelated page that has no `dataSource` attribute failed with the other database's "Table not found"; the application had to be
redeployed), which is another reason to configure it once, in
`web.xml` or in Java.

Two rules close the section. First, the parameter string and the four JDBC attributes put a user name and a password into a
page: use them only on a laptop with a throwaway database and a placeholder account, and never commit a real password into a
JSP, a `web.xml` or a `context.xml` that is under version control. Second, a JDBC driver in `WEB-INF/lib` of a web
application is registered with `DriverManager` and not unregistered by the container on undeploy: Tomcat logs a warning that the
application "registered the JDBC driver [org.h2.Driver] but failed to unregister it" when the scratch WAR is redeployed, and the
Tomcat JNDI how-to has a section on the service provider mechanism and memory leaks that recommends putting the driver in
the server's `lib` directory for container-managed pools.

[#sql-query]
== sql:query: Reading Rows

`sql:query` runs a `SELECT` and stores a `jakarta.servlet.jsp.jstl.sql.Result` in `var`. It has three syntaxes, which differ
only in where the statement and the parameters come from.

.sql:query attributes
[cols="2,2,6",options="header"]
|===
|Attribute |Type (dynamic) |Meaning

|`sql` |`String` (yes) |The statement; alternatively it is the body of the tag
|`dataSource` |`DataSource` or `String` (yes) |See <<sql-datasource>>; must not be given when the tag is nested in `sql:transaction`
|`maxRows` |`int` (yes) |Largest number of rows kept; `-1` or absent means no limit; must be at least -1. Beats the configuration variable `jakarta.servlet.jsp.jstl.sql.maxRows` (`Config.SQL_MAX_ROWS`)
|`startRow` |`int` (yes) |Index of the first row kept; row 0 is the first row of the result set; default 0
|`var` |`String` (no) |Required: the exported `Result`
|`scope` |`String` (no) |Scope of `var`; default `page`
|===

Syntax 1 is `+<sql:query sql="..." var="r"/>+` (no body); syntax 2 puts only `sql:param` actions in the body; syntax 3 puts the
statement text and then the `sql:param` actions in the body, which the container evaluates and the tag trims. If the query
returns nothing, `var` holds an empty `Result`, not `null`. Any `SQLException` is rethrown as a `JspException` whose
message includes the SQL statement and whose cause is the original exception.

The `Result` interface has five properties, all readable from EL:

.The jakarta.servlet.jsp.jstl.sql.Result properties
[cols="2,3,5",options="header"]
|===
|EL property |Java type |Meaning

|`rows` |`SortedMap[]` |One map per row, column name to value; the map uses `String.CASE_INSENSITIVE_ORDER`, so `row.title`, `row.TITLE` and `+row['Title']+` all work whatever case the database reports
|`rowsByIndex` |`Object[][]` |One array per row in column order; the generic way to print a table without knowing the columns
|`columnNames` |`String[]` |Column labels as the database reports them (H2 reports upper case: `ID`, `TITLE`)
|`rowCount` |`int` |Number of rows kept in the result (after `startRow` and `maxRows`)
|`limitedByMaxRows` |`boolean` |`true` when `maxRows` (or the configuration variable) cut the result
|===

Source: https://jakarta.ee/specifications/tags/3.0/jakarta-tags-spec-3.0.html#sql:query[Jakarta Standard Tag Library 3.0 -- 10.3 sql:query]

Source: https://jakarta.ee/specifications/tags/3.0/apidocs/jakarta.servlet.jsp.jstl/jakarta/servlet/jsp/jstl/sql/Result.html[Jakarta Tags 3.0 API -- Result]

Source: https://jakarta.ee/specifications/tags/3.0/tagdocs/sql/query.html[Jakarta Tags 3.0 tagdocs -- sql:query]

The page `query.jsp` lists the books ordered by year, skipping the first row and keeping three. It prints the same rows
three ways: the counters, a table built from `columnNames` and `rowsByIndex` (no column is named in the page), and a list that
uses `rows` with the case-insensitive keys.

.query.jsp
[source,jsp]
----
<%@ taglib prefix="c" uri="jakarta.tags.core" %>
<%@ taglib prefix="sql" uri="jakarta.tags.sql" %>
<sql:query var="books" startRow="1" maxRows="3">
    SELECT id, title, author, published_year FROM book ORDER BY published_year
</sql:query>
<p>rowCount=${books.rowCount} limitedByMaxRows=${books.limitedByMaxRows} columns=${books.columnNames[0]},${books.columnNames[1]}</p>
<table>
    <tr>
        <c:forEach var="name" items="${books.columnNames}"><th><c:out value="${name}"/></th></c:forEach>
    </tr>
    <c:forEach var="row" items="${books.rowsByIndex}">
        <tr><c:forEach var="cell" items="${row}"><td><c:out value="${cell}"/></td></c:forEach></tr>
    </c:forEach>
</table>

=== Paging with startRow and maxRows

The two attributes are, in the words of the specification, a "poor man's way" of paging: `maxRows` protects against runaway
queries and `startRow` skips the pages already shown. With both set, the database is asked for `startRow + maxRows` rows and
the first `startRow` of them are discarded, so deep pages get slower. Without an `ORDER BY` the order is not guaranteed, so a
page can repeat or skip a row between requests. `limitedByMaxRows` tells the page whether a "next" link makes sense.

.pager.jsp
[source,jsp]
----
<c:set var="size" value="2"/>
<c:set var="page" value="${empty param.page ? 0 : param.page}"/>
<sql:query var="books" startRow="${page * size}" maxRows="${size}">
    SELECT id, title FROM book ORDER BY id
</sql:query>
<ol start="${page * size + 1}">
    <c:forEach var="row" items="${books.rows}"><li><c:out value="${row.title}"/></li></c:forEach>
</ol>
<c:if test="${books.limitedByMaxRows}"><a href="?page=${page + 1}">next</a></c:if>
----

[source,text]
----
$ curl 'http://localhost:18080/g5jstlsqlxml/pager.jsp'
<ol start="1">
    <li>Dune</li><li>Neuromancer</li></ol>
<a href="?page=1">next</a>
$ curl 'http://localhost:18080/g5jstlsqlxml/pager.jsp?page=2'
<ol start="5">
    <li>Hyperion</li></ol>
----

Source: https://jakarta.ee/specifications/tags/3.0/jakarta-tags-spec-3.0.html#sql:query[Jakarta Standard Tag Library 3.0 -- 10.3 sql:query (maxRows and startRow)]

Source: https://jakarta.ee/specifications/tags/3.0/jakarta-tags-spec-3.0.html#maxrows[Jakarta Standard Tag Library 3.0 -- 10.9.2 MaxRows]

The flag is exact: `limitedByMaxRows` is `true` only when the query had more rows than were kept. On the five-row table
`maxRows="4"` reports `true` with four rows, while `maxRows="5"` (an exact fit) reports `false` with five (verified), so a
"next" link is shown only when there really is a next page, except for rows that appear between two requests. The `web.xml`
above sets `jakarta.servlet.jsp.jstl.sql.maxRows` to 100 as a safety net for every query in the application. Real paging
belongs in the query itself or in the data layer: the tag still reads and discards every row before `startRow`.

[#sql-param]
== sql:param and sql:dateParam: Injection-Safe Values

A statement may contain `?` markers; every marker is filled, in order, by a nested `sql:param` or `sql:dateParam`. The values
travel as JDBC `PreparedStatement` parameters, so the database never parses them as SQL. Both tags locate their nearest
ancestor that implements `jakarta.servlet.jsp.jstl.sql.SQLExecutionTag` (`sql:query` and `sql:update` do) and call its
`addSQLParameter()` method, which is also the extension point for custom parameter tags.

.sql:param and sql:dateParam
[cols="2,3,6",options="header"]
|===
|Tag |Attributes |Behaviour

|`sql:param` |`value` (`Object`, dynamic); or the value as the body |A `null` value sets the SQL `NULL`. A `String` value is documented to work only for text columns (`CHAR`, `VARCHAR`, `LONGVARCHAR`); other types need a number or date object, for example one produced by `fmt:parseNumber` or `fmt:parseDate`
|`sql:dateParam` |`value` (`java.util.Date`), `type` (`date`, `time` or `timestamp`) |Converts the value to `java.sql.Date`, `java.sql.Time` or `java.sql.Timestamp`; `null` gives `NULL`
|===

Source: https://jakarta.ee/specifications/tags/3.0/jakarta-tags-spec-3.0.html#sql:param[Jakarta Standard Tag Library 3.0 -- 10.7 sql:param]

Source: https://jakarta.ee/specifications/tags/3.0/jakarta-tags-spec-3.0.html#sqldateparam[Jakarta Standard Tag Library 3.0 -- 10.8 sql:dateParam]

Source: https://jakarta.ee/specifications/tags/3.0/jakarta-tags-spec-3.0.html#sql-statement-parameters[Jakarta Standard Tag Library 3.0 -- 10.1.4 SQL Statement Parameters]

The page `param.jsp` runs the same search twice, once with a parameter and once with the request value concatenated into
the statement by EL. The second form is the vulnerable "before" snippet; it is shown so the difference can be seen, and it is
never to be used.

.param.jsp
[source,jsp]
----
<c:set var="q" value="${empty param.q ? 'Dune' : param.q}"/>
<h2>sql:param</h2>
<sql:query var="safe">
    SELECT title FROM book WHERE title = ?
    <sql:param value="${q}"/>
</sql:query>
<p>safe: ${safe.rowCount} row(s)</p>
<h2>EL concatenated into the statement</h2>
<c:catch var="err">
    <sql:query var="unsafe">
        SELECT title FROM book WHERE title = '${q}'
    </sql:query>
</c:catch>
<p>unsafe: <c:out value="${empty err ? unsafe.rowCount : 'error'}"/> row(s)</p>
<c:if test="${not empty err}"><p>cause: <c:out value="${err.cause.message}"/></p></c:if>
----

Source: https://jakarta.ee/specifications/tags/3.0/jakarta-tags-spec-3.0.html#sql:query[Jakarta Standard Tag Library 3.0 -- 10.3 sql:query (syntax 3, query with optional parameters)]

Source: https://cheatsheetseries.owasp.org/cheatsheets/SQL_Injection_Prevention_Cheat_Sheet.html#primary-defenses[OWASP -- SQL Injection Prevention Cheat Sheet, primary defenses]

With a normal value both forms agree. With `q` set to `+x' OR '1'='1+` (sent as a URL-encoded query parameter) the result
differs:

[source,html]
----
<h2>sql:param</h2>
<p>safe: 0 row(s)</p>
<h2>EL concatenated into the statement</h2>
<p>unsafe: 5 row(s)</p>
----

The parameter form found nothing, because no book has that literal title; the concatenated form returned every book, because
the EL expression was replaced by text before the statement reached the driver and the `OR '1'='1'` became part of the SQL.
(A second attempt with `+x' OR 'a+` shows the other symptom, a `JspException` whose cause is the database error with the
statement in it: _Data conversion error converting "CHARACTER VARYING to BOOLEAN"_.) The specification's examples are
safe: its money transfer example uses markers. The rule is mechanical: no `+${...}+` inside the SQL text,
only in `value` attributes. A value that cannot be a parameter, such as a table or column name chosen by the visitor, is
never taken from the request: it is looked up in a fixed list of allowed names in a servlet.

=== Dates

`sql:dateParam` takes a `java.util.Date`, which the formatting library produces from text (`fmt:parseDate`). It is also the
only way to bind a time-of-day or a timestamp without a custom tag, because `sql:param` binds the object it is given
as it is.

.dateparam.jsp
[source,jsp]
----

<fmt:parseDate var="since" value="2026-01-01" pattern="yyyy-MM-dd"/>
<sql:query var="recent">
    SELECT title, added_on FROM book WHERE added_on >= ? ORDER BY id
    <sql:dateParam value="${since}" type="date"/>
</sql:query>

----

The `fmt:setLocale` line matters for `curl`: without an `Accept-Language` header and without a configured locale, `fmt:parseDate`
cannot establish a parse locale and fails with a `JspException` ("In <parseDate>, a parse locale can not be established"),
a behaviour of the formatting library described on its own page. Whether a `String` can be bound to a numeric column depends
on the driver: the specification documents text columns only, and H2 happens to coerce `"1965"` for an `INT` column
(`WHERE published_year = ?` with `<sql:param value="1965"/>` returned the book), which another database may refuse.

[#sql-update]
== sql:update: Changing Data and Running DDL

`sql:update` runs an `INSERT`, `UPDATE` or `DELETE`, and also any statement that returns nothing, such as DDL. Its syntaxes
mirror `sql:query`: the statement in `sql`, or in the body, with `sql:param` actions.

.sql:update attributes
[cols="2,2,6",options="header"]
|===
|Attribute |Type (dynamic) |Meaning

|`sql` |`String` (yes) |The statement; alternatively the body of the tag
|`dataSource` |`DataSource` or `String` (yes) |As for `sql:query`; forbidden inside `sql:transaction`
|`var` |`String` (no) |Optional: exported as a `java.lang.Integer`, the number of rows affected
|`scope` |`String` (no) |Scope of `var`; if given, `var` is required
|===

The result is the same number `Statement.executeUpdate()` returns: zero for a statement that matched nothing and for every
DDL statement. The page `errors.jsp` checks this and some other edges in one place.

Three details are worth remembering. A `null` parameter value became SQL `NULL` (the page printed `true` for
`empty nul.rows[0].v`). A `maxRows` below -1 is rejected with the tag's own message, and a failing statement reports its
text first, which is why the message of a `JspException` from these tags must never be shown to a visitor. And each
`sql:update` that is not inside `sql:transaction` obtains its own connection, runs, and releases it before the tag ends (the
specification requires every database action to close what it opened), so on an auto-commit connection each statement is its own
transaction: two separate updates are not atomic.

[#sql-transaction]
== sql:transaction: Grouping Statements

`sql:transaction` provides one connection to the `sql:query` and `sql:update` actions nested in its body, turns auto-commit
off, and commits when the body ends or rolls back if an exception escapes. Its attributes are `dataSource` (as before) and
`isolation`.

.sql:transaction isolation levels
[cols="2,4",options="header"]
|===
|`isolation` value |JDBC constant it selects

|`read_uncommitted` |`Connection.TRANSACTION_READ_UNCOMMITTED`
|`read_committed` |`Connection.TRANSACTION_READ_COMMITTED`
|`repeatable_read` |`Connection.TRANSACTION_REPEATABLE_READ`
|`serializable` |`Connection.TRANSACTION_SERIALIZABLE`
|(not given) |The isolation level the data source is configured with
|===

The life cycle given by the specification is: at the start, read the current isolation level (a value of `TRANSACTION_NONE`
means transactions are not supported and the action fails), save and disable auto-commit, and set the requested isolation
level if it differs; at the end call `commit()`; on an exception call `rollback()` and rethrow; and in every case restore the
saved isolation level and auto-commit mode and close the connection. Three rules follow from it: the nested `sql:query` and
`sql:update` must not specify `dataSource`; transactions cannot be nested to share a connection; and executing a SQL
statement such as `rollback` with `sql:update` inside the body is not supported (the result is unpredictable). Its behaviour
inside a larger JTA user transaction is undefined.

The Bookshelf transfers copies of _Dune_ from the main shelf to the annex. The two updates are one transaction; the first one
adds copies to the annex and the second removes them from the main shelf, where the `CHECK (copies >= 0)` constraint rejects an
impossible quantity. The output of the second request shows that the first update, which had succeeded, was rolled back.

.transaction.jsp
[source,jsp]
----
<c:set var="n" value="${empty param.n ? 1 : param.n}"/>
<c:catch var="err">
    <sql:transaction isolation="read_committed">
        <sql:update>
            UPDATE shelf SET copies = copies + ? WHERE book_id = 1 AND location = 'ANNEX'
            <sql:param value="${n}"/>
        </sql:update>
        <sql:update>
            UPDATE shelf SET copies = copies - ? WHERE book_id = 1 AND location = 'MAIN'
            <sql:param value="${n}"/>
        </sql:update>
    </sql:transaction>
</c:catch>
<c:choose>
    <c:when test="${empty err}">moved ${n} copies</c:when>
    <c:otherwise>rolled back: <c:out value="${err.cause.message}"/></c:otherwise>
</c:choose>
<sql:query var="now">SELECT location, copies FROM shelf WHERE book_id = 1 ORDER BY location</sql:query>
<c:forEach var="r" items="${now.rows}">${r.location}=${r.copies} </c:forEach>
----

[#sql-xss]
== Escaping What Comes from the Database

Everything in a `Result` is data to be treated as untrusted. A title that contains markup is printed unchanged by a bare
`+${...}+` and escaped by `c:out`. The page `xss.jsp` inserts such a title through a parameter and prints it both ways.

.xss.jsp
[source,jsp]
----
<sql:update>
    INSERT INTO book (id, title, author, published_year, added_on) VALUES (99, ?, 'x', 2000, CURRENT_DATE)
    <sql:param value="<script>alert(1)</script>"/>
</sql:update>
<sql:query var="r">SELECT title FROM book WHERE id = 99</sql:query>

----

[source,html]
----

escaped: &lt;script&gt;alert(1)&lt;/script&gt;
----

Source: https://jakarta.ee/specifications/tags/3.0/jakarta-tags-spec-3.0.html#sql:param[Jakarta Standard Tag Library 3.0 -- 10.7 sql:param]

the first keeps the visitor's text from becoming SQL, the second keeps the database's text from becoming HTML.

[#alternatives]
== Doing It Properly: Replacing the SQL Tags

The replacement for `sql:*` is the structure the specification recommends: the page prints, a servlet (or a service behind
it) queries. The Bookshelf servlet `BooksServlet` gets the container's data source through `@Resource`, runs a prepared
statement, puts a list of records in the request and forwards to a page that has no SQL.

.BooksServlet.java
[source,java]
----
@WebServlet("/books-mvc")
public class BooksServlet extends HttpServlet {

    @Resource(name = "jdbc/bookshelf")
    private DataSource dataSource;

    @Override
    protected void doGet(HttpServletRequest req, HttpServletResponse resp) throws ServletException, IOException {
        String author = req.getParameter("author");
        String like = "%" + (author == null ? "" : author) + "%";
        List<Book> books = new ArrayList<>();
        try (Connection connection = dataSource.getConnection();
             PreparedStatement statement = connection.prepareStatement(
                     "SELECT id, title, author, published_year FROM book WHERE author LIKE ? ORDER BY id")) {
            statement.setString(1, like);
            try (ResultSet rs = statement.executeQuery()) {
                while (rs.next()) {
                    books.add(new Book(rs.getLong("id"), rs.getString("title"), rs.getString("author"),
                            rs.getInt("published_year")));
                }
            }
        } catch (SQLException e) {
            throw new ServletException("Cannot read the books", e);
        }
        req.setAttribute("books", books);
        req.getRequestDispatcher("/WEB-INF/views/books-mvc.jsp").forward(req, resp);
    }
}
----

.WEB-INF/views/books-mvc.jsp
[source,jsp]
----
<ul>
    <c:forEach var="book" items="${books}">
        <li><c:out value="${book.title}"/> by <c:out value="${book.author}"/> (${book.year})</li>
    </c:forEach>
</ul>
----

[source,html]
----
$ curl 'http://localhost:18080/g5jstlsqlxml/books-mvc?author=Gib'
<ul>
    <li>Neuromancer by William Gibson (1984)</li>
    </ul>
----

Source: https://jakarta.ee/specifications/tags/3.0/jakarta-tags-spec-3.0.html#sql-actions-sql-tag-library[Jakarta Standard Tag Library 3.0 -- 10 SQL Actions (the MVC preference)]

Source: https://tomcat.apache.org/tomcat-11.0-doc/jndi-datasource-examples-howto.html#Database_Connection_Pool_(DBCP_2)_Configurations[Apache Tomcat 11 -- JNDI Datasource How-To]

Source: https://cheatsheetseries.owasp.org/cheatsheets/SQL_Injection_Prevention_Cheat_Sheet.html#primary-defenses[OWASP -- SQL Injection Prevention Cheat Sheet, primary defenses]

The servlet is longer than the tag, and that is the trade: it can be tested without a container, reused by a REST endpoint,
traced, given a read-only account, and changed without touching the page. Serious projects go one step further and replace
the hand-written JDBC with a data layer: the Hibernate pages of this repository
(xref:backend/hibernate/getting-started.adoc[getting started with Hibernate]) and the
xref:backend/springboot/spring-data-jpa.adoc[Spring Data JPA page] show the options. The mapping from the old tags to
the modern code is straightforward:

.From sql tags to code
[cols="3,5",options="header"]
|===
|Tag |Replacement

|`sql:setDataSource`, `dataSource` |A pooled `DataSource` bound by the container (`Resource` in `context.xml`) or created once by the application
|`sql:query` plus `Result` |`PreparedStatement` or a repository in a servlet or service; a list of records in a request attribute
|`sql:param`, `sql:dateParam` |`setString`, `setObject` with `java.time` types (JDBC 4.2), or named parameters in the data layer
|`sql:update` |A service method with the same SQL (or an entity update) behind a `POST`
|`sql:transaction` |A transaction owned by the service layer (`@Transactional` in Spring, a JPA transaction, a JTA user transaction)
|`maxRows`, `startRow` |`LIMIT`/`OFFSET` or keyset pagination in the query, as on the xref:database/pagination-strategies.adoc[pagination strategies page]
|===

|The `select` attribute |XPath is written only in `select`; it is not dynamic, it is a literal string for the XPath engine, and EL is not evaluated in it (`select="+${x}+"` is not an XPath variable)
|Default context node |Outside an `x:forEach` body the context node is the root of an empty document, so a page must name its document explicitly: `+$catalog/catalog/book+`
|Context in `x:forEach` |Inside the body the context node is the current item, the context position is the iteration count and the context size is the number of nodes iterated
|Function library |Only the XPath 1.0 core functions (`count()`, `sum()`, `string()`, `number()`, `local-name()`, `starts-with()` and so on); no extension functions are promised
|Namespaces |Prefixes used in an XPath expression must resolve to a namespace (see <<xml-namespaces>>)
|Result types |XPath boolean, number and string become `Boolean`, `Number` and `String`; a node-set is an implementation type that the other XML tags understand
|===

=== XPath variables

Web application data enters an XPath expression through variables whose prefixes mirror the EL implicit objects. A variable
that is not bound is an exception, following the XPath specification.

.XPath variable bindings
[cols="3,5",options="header"]
|===
|Expression |Value

|Java type of the variable |XPath type

|`java.lang.Boolean` |boolean
|`java.lang.Number` |number
|`java.lang.String` |string

== Getting the XML In

The XML tags take documents as a `String` or a `Reader`; they do not open URLs. The specification routes URL access through
`c:import` (11.1.7), and relative systems identifiers through the `systemId` attribute. There are four ways to get text to
`x:parse`, and on Tomcat 11 with JSTL 3.0.1 one of the obvious ones does not work for static files.

.Where the XML text can come from
[cols="3,2,5",options="header"]
|===
|Source |Works for |Notes

|Body of `x:parse` (or `x:transform`) |Inline XML, `c:import`, `jsp:include` |`+<x:parse var="d"><c:import url="/WEB-INF/data/catalog.xml"/></x:parse>+` works for a static file: the import writes into the tag's body
|`+c:import url=... var=...+` then `doc="+${text}+"` |Absolute URLs, dynamic resources (a JSP or servlet), not static files |Verified: for `/WEB-INF/data/catalog.xml` (and for a static file in the web application root) `var` stays empty and the file's text is written into the page output instead, so `x:parse` fails with "Premature end of file"
|`+c:import ... varReader+` with `x:parse` in the body |As above |Same effect as `var` for static files
|A servlet |Anything |Reads and parses with a hardened parser, puts a `String` (or beans) in a request attribute
|===

The cause is in the implementation: the response wrapper that `c:import` hands to the included resource has an output stream
whose `flush()` copies what was written into the page's `JspWriter` and then clears it; a static file served by Tomcat's default servlet is
written to that stream and flushed, which is consistent with what was observed: the text goes to the page and `var` is empty. A JSP or a servlet that uses a
`Writer` is not affected, which is why `c:import` of a dynamic URL works, and why the examples on this page use the body form. This was verified on
2026-10-08 on Tomcat 11.0.26 with JSTL 3.0.1 for `var`, for `varReader` and for a file outside `WEB-INF`; it is recorded as an
inconsistency with the specification, which says `c:import` "works seamlessly with the XML tags". The XSLT stylesheet below
(a static file too) is imported through a one-line JSP wrapper, `catalog-xsl.jsp`, that includes it.

.imp3.jsp (the four ways, each wrapped in c:catch)
[source,jsp]

== x:parse: Building the Tree

`x:parse` parses a document and saves the result. It does not validate against a DTD or schema.

|Attribute |Type |Meaning

=== Filtering large documents

The `filter` attribute exists for performance: a DOM-like tree of a large document is expensive, so a filter can drop what
the page does not need before the tree is built. The specification's example prunes non-European customers. The Bookshelf
filter drops every `book` whose `year` attribute is older than a threshold; it is an ordinary `XMLFilterImpl` that skips the
subtree, and the page creates it with `jsp:useBean` (no scriptlet).

.YearFilter.java
[source,java]
----
public class YearFilter extends XMLFilterImpl {
    private int minYear = 1960;
    private int skipDepth;

    public void setMinYear(int minYear) {
        this.minYear = minYear;
    }

    @Override
    public void startElement(String uri, String local, String qName, Attributes atts) throws SAXException {
        if (skipDepth > 0) {
            skipDepth++;
            return;
        }
        if ("book".equals(qName) && Integer.parseInt(atts.getValue("year")) < minYear) {
            skipDepth = 1;
            return;
        }
        super.startElement(uri, local, qName, atts);
    }

    @Override
    public void endElement(String uri, String local, String qName) throws SAXException {
        if (skipDepth > 0) {
            skipDepth--;
            return;
        }
        super.endElement(uri, local, qName);
    }

    @Override
    public void characters(char[] ch, int start, int length) throws SAXException {
        if (skipDepth == 0) {
            super.characters(ch, start, length);
        }
    }
}
----

.The filter in a page (from xml-transform.jsp)
[source,jsp]
----
<jsp:useBean id="yearFilter" class="org.example.bookshelf.YearFilter"/>
<jsp:setProperty name="yearFilter" property="minYear" value="1960"/>
<x:parse var="young" filter="${yearFilter}"><c:import url="/WEB-INF/data/catalog.xml"/></x:parse>
after filter: <x:out select="count($young//book)"/> books
----

[source,text]
----
after filter: 2 books
----

Source: https://jakarta.ee/specifications/tags/3.0/jakarta-tags-spec-3.0.html#xparse[Jakarta Standard Tag Library 3.0 -- 11.2 x:parse (filtering for performance benefits)]

The filter is a bean in page scope, shared by nothing, and it keeps state (`skipDepth`) while it runs, so one instance must
not be shared between requests: put it in `page` or `request` scope (the default of `jsp:useBean` is `page`), never in
`application` scope.

=== systemId

`systemId` matters when the document refers to an external DTD or entity by a relative name. The specification says
relative URLs are treated as references to web application resources. The page below parses a file whose DOCTYPE points to
`catalog.dtd`, with and without `systemId`.

[#xml-flow]
== x:if, x:choose and x:forEach: Control Flow on XPath

The flow tags are the XPath versions of `c:if`, `c:choose` and `c:forEach`; the test expression is evaluated by XPath and
converted to a boolean as the `boolean()` function does (a number is true unless zero or NaN; a node-set is true if it is
non-empty; a string is true if it is not empty).

.The XML flow tags
[cols="2,4,5",options="header"]
|===
|Tag |Attributes |Notes

|`x:if` |`select` (required); `var`, `scope` (optional; `var` required if `scope` is given) |Renders the body when the expression is true; `var` receives the `Boolean`
|`x:choose` |none |Body only `x:when` (one or more) and then at most one `x:otherwise`; white space is allowed around them
|`x:when` |`select` |Child of `x:choose`, before any `x:otherwise`; the first true one is rendered
|`x:otherwise` |none |Last child of `x:choose`
|`x:forEach` |`select` (required); `var`, `varStatus` (a `LoopTagStatus`), `begin`, `end`, `step` (dynamic `int`) |Iterates over a node-set; `var` and `varStatus` have nested visibility; an empty `select` is a `JspException`; `begin` at least 0, `step` at least 1; `end` less than `begin` runs nothing
|===

Source: https://jakarta.ee/specifications/tags/3.0/jakarta-tags-spec-3.0.html#xif[Jakarta Standard Tag Library 3.0 -- 12.2 x:if]

Source: https://jakarta.ee/specifications/tags/3.0/jakarta-tags-spec-3.0.html#xchoose[Jakarta Standard Tag Library 3.0 -- 12.3 x:choose]

Source: https://jakarta.ee/specifications/tags/3.0/jakarta-tags-spec-3.0.html#xwhen[Jakarta Standard Tag Library 3.0 -- 12.4 x:when]

The first line of the output is wrong, and it is the most useful lesson of this page. The loop has `begin="1" end="3"
step="2"`, so it visits the books at index 1 (_Neuromancer_) and 3 (_The Great Gatsby_); `varStatus` reports `index` 1 and 3
correctly, and `$b/price` (path from the loop variable) is right, but the relative path `title` printed _Foundation &
Empire_ for the first iteration, the book at index 2. The relative XPath is evaluated against a context node that is one
step ahead of `var` whenever `step` is greater than one. A second page, `xml-loop.jsp`, reproduced it without `begin` and
`end`:

.xml-loop.jsp (the step case)
[source,jsp]
----
<x:forEach select="$catalog//book" var="b" varStatus="s" step="2">${s.index}: <x:out select="title"/> | <x:out select="$b/title"/> | <x:out select="@id"/>
</x:forEach>

[source,text]
----

2: The Great Gatsby | Foundation &amp; Empire | 4
----

Source: https://jakarta.ee/specifications/tags/3.0/jakarta-tags-spec-3.0.html#x:forEach[Jakarta Standard Tag Library 3.0 -- 12.6 x:forEach (the context node is the node exposed by var)]

The specification says the context node is "the node whose representation would be exposed by var (whether or not the var
attribute is specified)". On Tomcat 11.0.26 with JSTL 3.0.1 this holds without `step` (the plain loop printed `Dune | Dune | 1`
and so on) and not with `step` above 1, so the workaround is to name the loop variable and write paths from it (`$b/title`,
`$b/@id`) in any loop that uses `step` or `begin`; it is also the style that stays readable.

The other flow-control results: `x:if select="$catalog//book[@year < 1930]"` is true (the 1925 book) and its `var` holds
`true`; `x:choose` skipped the empty `fantasy` test and took the second `x:when`; the last loop used `$param:genre` and
a request with `?genre=scifi` listed three books. Two things about that XPath: the `<` in the first `select` is written
unescaped, because in the standard (non-XML) JSP syntax an attribute value is not an XML text and `&lt;` would be passed to XPath
as four literal characters and fail ("Expected ], but found: &lt;"); in a JSP document (XML syntax) it has to be escaped
(see the xref:web/jsp-struts/jsp/jsp-documents-xml-syntax.adoc[JSP documents page]). And a request without the `genre`
parameter is an exception, not an empty list:

[source,text]
----
resolveVariable for variable {http://java.sun.com/jstl/xpath/param}genre returning null
----

The variable namespaces still use the old `java.sun.com` URIs inside the XPath engine; that is an implementation detail and
not something a page writes.

=== The specification's x:if example

The `x:if` example in the specification, `<x:if select="$customer/[location='UK']">`, is not valid XPath 1.0 (a location
step cannot follow `/` with a predicate alone) and fails on Tomcat 11.0.26 with "A relative location path was expected
following the '/' or '//' token". The valid spelling is `$customer[location='UK']` or `$customer/*[location='UK']`. It is
recorded among the inconsistencies found while writing this section.

[#xml-namespaces]
== Namespaces

An element name without a prefix in XPath means "no namespace". A document whose elements are in a default namespace is
therefore invisible to `//entry`, a classic source of "my XPath finds nothing". The Bookshelf feed `feed.xml` declares a
default namespace and a prefixed one.

.WEB-INF/data/feed.xml
[source,xml]
----
<?xml version="1.0" encoding="UTF-8"?>
<feed xmlns="https://example.org/ns/shelf" xmlns:bk="https://example.org/ns/books">
    <entry bk:isbn="X1"><title>Dune</title></entry>
    <entry bk:isbn="X2"><title>Solaris</title></entry>
</feed>
----

.xml-more.jsp
[source,jsp]
----
<x:parse var="feed"><c:import url="/WEB-INF/data/feed.xml"/></x:parse>
<c:catch var="e1">ns prefix: <x:out select="count($feed//entry)"/></c:catch>
<c:catch var="e2">local-name: <x:out select="count($feed//*[local-name()='entry'])"/> / <x:out select="$feed//*[local-name()='entry'][2]/*[local-name()='title']"/></c:catch>
<c:catch var="e3">declared prefix: <x:out select="count($feed//s:entry)"/></c:catch> ${empty e3 ? '' : e3.message}
<c:catch var="e4">attr: <x:out select="$feed//*[local-name()='entry'][1]/@*[local-name()='isbn']"/></c:catch>
----

[source,text]
----

Source: https://jakarta.ee/specifications/tags/3.0/jakarta-tags-spec-3.0.html#xpath-context[Jakarta Standard Tag Library 3.0 -- 11.1.1 XPath Context (namespace prefix definitions)]

The specification promises "namespace prefix definitions" in the XPath context but gives no way to declare one from a page
(the tags have no attribute for it), and a prefix that is not resolvable is an error (`Prefix must resolve to a namespace`).
The portable answer is `local-name()` (and, for a namespace check, `namespace-uri()`), as in the page. The stack trace
shows the implementation: XPath is evaluated by an embedded copy of Apache Xalan's XPath engine that the implementation
bundles under `org.eclipse.tags.shaded`, which is why only XPath 1.0 is available.

[#xml-transform]
== x:transform and x:param: XSLT

`x:transform` applies an XSLT stylesheet to a document. The document comes from `doc` (a `String`, `Reader`,
`javax.xml.transform.Source`, DOM `Document`, or an object exported by `x:parse` or `x:set`) or from the body; the stylesheet
from `xslt` (a `String`, `Reader` or `Source`). Parameters are nested `x:param` tags.

.x:transform and x:param attributes
[cols="3,3,6",options="header"]
|===
|Attribute |Type |Meaning

|`doc` |See above (dynamic) |The source document; `xml` is the deprecated name
|`xslt` |`String`, `Reader`, `Source` (dynamic) |The stylesheet
|`docSystemId`, `xsltSystemId` |`String` (dynamic) |System identifiers used to resolve references in the document and in the stylesheet; `xmlSystemId` is the deprecated name of `docSystemId`
|`var`, `scope` |`String` |Store the result as an `org.w3c.dom.Document` instead of writing it
|`result` |`javax.xml.transform.Result` (dynamic) |An object that receives the result (alternative to `var`)
|`x:param` `name`, `value` |`String` and `Object` (dynamic) |A stylesheet parameter; `value` may be the body of the tag
|===

By default the result is written to the page. An empty source document or stylesheet is a `JspException`. An implementation may
cache compiled stylesheets, and the specification warns that a cache must key on both `xslt` and `xsltSystemId`.

Source: https://jakarta.ee/specifications/tags/3.0/jakarta-tags-spec-3.0.html#xtransform[Jakarta Standard Tag Library 3.0 -- 13.2 x:transform]

Source: https://jakarta.ee/specifications/tags/3.0/jakarta-tags-spec-3.0.html#xparam[Jakarta Standard Tag Library 3.0 -- 13.3 x:param]

Source: https://jakarta.ee/specifications/tags/3.0/tagdocs/x/transform.html[Jakarta Tags 3.0 tagdocs -- x:transform]

Source: https://jakarta.ee/specifications/tags/3.0/tagdocs/x/param.html[Jakarta Tags 3.0 tagdocs -- x:param]

The Bookshelf stylesheet turns the catalog into a list of the books of one genre, sorted by year; the genre is a stylesheet
parameter with a default.

.WEB-INF/data/catalog.xsl
[source,xml]
----
<?xml version="1.0" encoding="UTF-8"?>
<xsl:stylesheet version="1.0" xmlns:xsl="http://www.w3.org/1999/XSL/Transform">
    <xsl:output method="html" omit-xml-declaration="yes"/>
    <xsl:param name="genre" select="'scifi'"/>
    <xsl:template match="/catalog">
        <ul class="{$genre}">
            <xsl:for-each select="book[@genre = $genre]">
                <xsl:sort select="@year" data-type="number"/>
                <li><xsl:value-of select="title"/> (<xsl:value-of select="@year"/>)</li>
            </xsl:for-each>
        </ul>
    </xsl:template>
</xsl:stylesheet>
----

.xml-transform.jsp
[source,jsp]
----
<c:set var="genre" value="${empty param.genre ? 'scifi' : param.genre}"/>
<c:import url="/WEB-INF/data/catalog-xsl.jsp" var="xsl"/>
<x:transform xslt="${xsl}">
    <x:param name="genre" value="${genre}"/>
    <c:import url="/WEB-INF/data/catalog.xml"/>
</x:transform>
-- captured in a variable (org.w3c.dom.Document), parsed again
<x:transform var="out" xslt="${xsl}"><c:import url="/WEB-INF/data/catalog.xml"/></x:transform>
<x:out select="count($out//li)"/> items, first: <x:out select="$out//li[1]"/>
-- varDom
<x:parse varDom="dom"><c:import url="/WEB-INF/data/catalog.xml"/></x:parse>
<x:transform doc="${dom}" xslt="${xsl}"><x:param name="genre" value="classic"/></x:transform>
----

----

    <li>Dune (1965)</li>
    <li>Neuromancer (1984)</li>
</ul>

Source: https://jakarta.ee/specifications/tags/3.0/jakarta-tags-spec-3.0.html#xml-transform-actions-xml-tag-library[Jakarta Standard Tag Library 3.0 -- 13 XML Transform Actions]

Source: https://www.w3.org/TR/xslt-10/[W3C -- XSLT 1.0]

`x:transform` accepted a document in the body, a `varDom` document, and a stylesheet imported as a string (through the
one-line wrapper JSP, because a static `.xsl` would hit the `c:import` problem of <<xml-sources>>). The HTML produced by the
stylesheet is written as it is, so a stylesheet is trusted code that must escape the data it prints; `xsl:value-of` escapes
text by default, which is why `Foundation & Empire` is `&amp;` in the output. XSLT 1.0 only: `xsl:sort`, `xsl:for-each`,
parameters and the common instructions work, but nothing from XSLT 2 or 3 (no `xsl:for-each-group`, no regular expressions).

[#xml-feed]
== A Remote Feed, the Classic Use

The `JSTL in Action` book builds an RSS reader; the same shape is still the classic use of these tags, and still the one
that needs the most care. The page `rss.jsp` imports a feed over HTTP, parses it and lists the items. The scratch
application serves its own feed from `new-books.jsp`; a real page would use the publisher's URL (the host
`publisher.example.com` appears inside the feed only as data).

.rss.jsp
[source,jsp]
----
<c:set var="feedUrl" value="http://localhost:18080/g5jstlsqlxml/new-books.jsp"/>
<c:catch var="e">
    <c:import url="${feedUrl}" var="rssText"/>
    <x:parse var="rss" doc="${rssText}"/>
    <x:forEach select="$rss/rss/channel/item" var="item">
        <x:out select="$item/title"/> -> <x:out select="$item/link"/>
    </x:forEach>
</c:catch>
<c:out value="${e.message}"/>
----

[source,text]
----
Hyperion -> https://publisher.example.com/b/5
Rendezvous with Rama -> https://publisher.example.com/b/6
----

Source: https://jakarta.ee/specifications/tags/3.0/jakarta-tags-spec-3.0.html#resources-access[Jakarta Standard Tag Library 3.0 -- 11.1.7 Resources Access]

Source: https://jakarta.ee/specifications/tags/3.0/jakarta-tags-spec-3.0.html#xml-core-actions-xml-tag-library[Jakarta Standard Tag Library 3.0 -- 11 XML Core Actions]

The risks are the ones of any server-side fetch: `c:import` of an absolute URL has no timeout attribute, so a slow host
holds a request thread; the URL must never come from the request (a visitor-chosen URL makes the server fetch internal
addresses, a server-side request forgery); the document is parsed in memory on every request, so a page that serves many
visitors caches it; and the remote text is untrusted (see <<xml-security>>). A servlet with a client that has timeouts and a
cache is the right place, and the page then reads a bean.

[#xml-security]
== XML Security: XXE, XSLT, XPath Injection and Escaping

.Security of the XML tags
[cols="2,5,5",options="header"]
|===
|Risk |What was verified |What to do

|External entities (XXE) |A document with `<!DOCTYPE c [<!ENTITY s SYSTEM "file:///etc/hostname">]>` is refused by `x:parse` on Tomcat 11.0.26 with JSTL 3.0.1: "'file' access is not allowed due to restriction set by the accessExternalDTD property". The implementation enables the JAXP feature `XMLConstants.FEATURE_SECURE_PROCESSING` on its parser factory and its transformer factories (found in the class files and shown by the error). A document taken from a request parameter behaves the same |Keep the 3.0.1 implementation or newer, never turn the restrictions off with system properties, and parse documents from users in Java with a factory that disallows DOCTYPE declarations entirely
|XSLT `document()` and `xsl:include` |A stylesheet that calls `document('file:///etc/hosts')` fails with "'file' access is not allowed due to restriction set by the accessExternalStylesheet property" |Stylesheets are code: take them only from the application, never from a request
|XPath injection |XPath built by concatenating a request value into `select` would be injectable. The specification gives the safe form: `+$param:name+` and the scope variables bind the value as data (`[@genre=$param:genre]` worked above). Note that `select` is not an EL attribute, so there is no concatenation to do |Always use variables for visitor values, as with `sql:param`
|Output escaping |`x:out` escapes by default; `escapeXml="false"` does not |Leave it on for any text that did not come from you; XML attribute values and element text can carry markup
|Server-side fetch |`c:import` of a URL built from input |Use an allow-list of feed addresses in the servlet
|Denial of service |The whole document becomes a tree in memory on every request, and XPath `//` is a full scan |Size limits and caching in a servlet; the `filter` attribute prunes early
|===

Source: https://www.w3.org/TR/1999/REC-xpath-19991116/[W3C -- XPath 1.0]

Source: https://cheatsheetseries.owasp.org/cheatsheets/XML_External_Entity_Prevention_Cheat_Sheet.html#java[OWASP -- XML External Entity Prevention Cheat Sheet, Java]

Source: https://docs.oracle.com/en/java/javase/21/security/java-api-xml-processing-jaxp-security-guide.html[Oracle -- Java API for XML Processing (JAXP) Security Guide]

The test page `xml-xxe.jsp` imports the entity document from a file and from a request parameter, and the output for both was
the same error text about `accessExternalDTD` (the file read is blocked). The entity attack is the one that makes XML tags in
a page worth a security review: the restriction is a default of the implementation, not a promise of the specification
(the chapter only says `x:parse` does not validate), and a container or a different implementation on the class path may
behave otherwise. A project that keeps these tags runs the check above once per implementation upgrade.

[#restrict]
== Forbidding the Libraries: PermittedTaglibsTLV

The best defence for a team that wants nothing of this page in its code is to forbid the libraries. The specification's
chapter 14 provides two tag library validators for that. `jakarta.servlet.jsp.jstl.tlv.PermittedTaglibsTLV` lists the tag
libraries a page may import, and `ScriptFreeTLV` forbids scripting elements. A validator is attached to a tag library
descriptor; every page that imports that library is then checked at translation time. The TLD below allows the core,
formatting and functions libraries and (a requirement of the TLV) itself, and nothing else.

.WEB-INF/tlds/no-sql-xml.tld
[source,xml]
----

        version="3.0">
    <description>Allows only the core, formatting and function libraries on a page.</description>
    <tlib-version>1.0</tlib-version>
    <short-name>nosqlxml</short-name>
    <uri>https://example.org/bookshelf/no-sql-xml</uri>
    <validator>
        <validator-class>jakarta.servlet.jsp.jstl.tlv.PermittedTaglibsTLV</validator-class>
        <init-param>
            <param-name>permittedTaglibs</param-name>
            <param-value>
                jakarta.tags.core

                jakarta.tags.functions

[#bookshelf-example]
== Worked Example: Importing the Catalog File into the Database

The two libraries meet in a one-off administrative task of the Bookshelf: load `catalog.xml` into the `book` table in one
transaction. It is a prototype page, exactly what these tags are meant for, and it shows the libraries working together:
`x:forEach` inside `sql:transaction`, XPath results turned into typed parameters with `x:set`, and a count at the end.
Each book is stored with an offset of 100 on its id so that it does not collide with the rows of `setup.jsp`.

.xml-import-db.jsp
[source,jsp]
----
<%@ page contentType="text/plain;charset=UTF-8" trimDirectiveWhitespaces="true" %>
<%@ taglib prefix="c" uri="jakarta.tags.core" %>
<%@ taglib prefix="sql" uri="jakarta.tags.sql" %>
<%@ taglib prefix="x" uri="jakarta.tags.xml" %>
<x:parse var="catalog"><c:import url="/WEB-INF/data/catalog.xml"/></x:parse>
<sql:transaction>
    <sql:update>DELETE FROM shelf WHERE book_id > 100</sql:update>
    <sql:update>DELETE FROM book WHERE id > 100</sql:update>
    <x:forEach select="$catalog/catalog/book" var="b">
        <x:set var="id" select="number($b/@id) + 100"/>
        <x:set var="title" select="string($b/title)"/>
        <x:set var="author" select="string($b/author)"/>
        <x:set var="year" select="number($b/@year)"/>
        <sql:update var="n">
            INSERT INTO book (id, title, author, published_year, added_on) VALUES (?, ?, ?, ?, CURRENT_DATE)
            <sql:param value="${id}"/>
            <sql:param value="${title}"/>
            <sql:param value="${author}"/>
            <sql:param value="${year}"/>
        </sql:update>
imported ${title}: ${n} row
    </x:forEach>
</sql:transaction>
<sql:query var="r">SELECT COUNT(*) AS n FROM book WHERE id > 100</sql:query>
rows now: ${r.rows[0].n}
----

[source,text]
----
imported Dune: 1 row
imported Neuromancer: 1 row
imported Foundation & Empire: 1 row
imported The Great Gatsby: 1 row
rows now: 4
----

Source: https://jakarta.ee/specifications/tags/3.0/jakarta-tags-spec-3.0.html#xset[Jakarta Standard Tag Library 3.0 -- 11.4 x:set]

Source: https://jakarta.ee/specifications/tags/3.0/jakarta-tags-spec-3.0.html#sqltransaction[Jakarta Standard Tag Library 3.0 -- 10.5 sql:transaction]

Source: https://jakarta.ee/specifications/tags/3.0/jakarta-tags-spec-3.0.html#sql:param[Jakarta Standard Tag Library 3.0 -- 10.7 sql:param]

The `number()` results are `Double` objects (id `101.0`), which `sql:param` bound to a `BIGINT` and an `INT` without
complaint on H2; the `string()` results are `String` objects for the text columns, which is the combination the
specification documents. The page ran twice with the same result because the first statements clear the previous load. As a
design it has every smell listed at the beginning of this page (a write that a `GET` can trigger, a file and a database in a
view, no authentication), and in a real project it becomes a servlet or a batch job that uses JAXB or StAX and a repository.

[#pitfalls]
== Pitfalls and Error Names

.Pitfalls of the SQL and XML tags
[cols="3,4,4",options="header"]
|===
|Symptom or error |Cause |Fix

|`JspException` "dataSource is null" |No `dataSource` attribute and no configuration variable (`jakarta.servlet.jsp.jstl.sql.dataSource`) |Declare the context parameter in `web.xml` or use `sql:setDataSource`
|"Unable to get connection, DataSource invalid ... No suitable driver found for jdbc/missing" |A JNDI name that is not bound falls through to the JDBC parameter string |Check the `Resource` name in `context.xml`; the name is relative to `java:comp/env/`
|Everything returns another database's tables |A `sql:setDataSource` without `var` replaced the page's configuration variable |Give it a `var` and pass `dataSource` explicitly, or configure once in `web.xml`
|All rows come back for a visitor's text |The value was concatenated into the SQL with `+${...}+` |Use `?` and `sql:param`
|"It is illegal to specify a DataSource when nested within a <transaction>" |`dataSource` on a tag inside `sql:transaction` (translation-time error) |Remove the attribute; set it on the transaction
|Half of a group of updates is saved |The updates were not inside one `sql:transaction`; each `sql:update` commits on its own |Wrap them; check the result with `c:catch`
|`rollback` or `commit` as a statement does nothing useful |The tag handler commits and rolls back itself |Do not issue transaction statements through `sql:update`
|Page 2 repeats a row of page 1 |`startRow`/`maxRows` without `ORDER BY` |Always sort on a unique key
|Database error text in the HTML |The `JspException` message holds the SQL |Catch it, log it, show a reference number
|A `String` bound to a number column fails (or works only on some databases) |`sql:param` is documented for text columns |Pass a number object (`fmt:parseNumber`, `x:set` with `number()`)
|Memory leak warning at undeploy about the JDBC driver |A driver in `WEB-INF/lib` is registered with `DriverManager` |Put the driver in the container's `lib` for container pools
|`x:parse` fails with "Premature end of file" |The text was empty: `c:import` of a static file with `var` or `varReader` on Tomcat 11, or an empty response |Put `c:import` in the body of `x:parse`, or serve the file through a JSP/servlet
|XPath finds nothing in a document with `xmlns` |Unprefixed names mean "no namespace" |`*[local-name()='name']`
|"resolveVariable for variable ... returning null" |An XPath variable (`$param:x`) is not bound |Test and default it before the tag
|`+NullPointerException ... "c" is null+` |`$cookie:` in a request with no cookies |Do not read cookies in XPath
|Wrong title inside `x:forEach step=` |The relative context node is off by one with `step` above 1 |Use `+$var/path+`
|"Expected ], but found: &lt;" |`&lt;` written in `select` of a standard-syntax JSP |Write `<` there; escape only in a JSP document
|"Prefix must resolve to a namespace" |A prefix in XPath that no declaration resolves |`local-name()`
|`count()` prints `3.0` |XPath numbers are `Double` |`number()` and a formatting tag
|`SAXParseException` with "accessExternalDTD" |An external entity or DTD was refused by secure processing |Remove the DOCTYPE; do not weaken the restriction
|"Scheme specific part cannot be empty" |A relative DTD reference without `systemId` |Pass `systemId`, or drop the DOCTYPE
|===

|JSTL 2.0 (Jakarta EE 9) |Package rename: `javax.servlet.jsp.jstl` becomes `jakarta.servlet.jsp.jstl` (spec Appendix A.1)
|JSTL 3.0 (Jakarta EE 10, current) |The tag URIs are renamed to `jakarta.tags.*` (spec issue 144), the API needs Java 11, a JPMS module descriptor is added, and the XML Binding dependency leaves the API POM (Appendix B.1). The old `java.sun.com` URIs are still accepted by the 3.0.1 implementation. The implementation enables secure XML processing on its parser and transformer factories. |JSTL 3.1 (under development) |Not released; the 3.1 specification page marks it as under development. Nothing on this page depends on it

[#books-outdated]
== Where the Books Are Outdated

The two books that cover this page's tags are _JSTL in Action_ (JSTL 1.0; chapters 7 and 8 for XML and 9 for databases, with the
SQL primer in the appendices) and _Web Development with JavaServer Pages_ (JSP 1.2; chapter 9 for databases). They remain
good for the ideas (XPath data model, location paths and predicates, XPath variables, result paging, transactions and
isolation) and out of date in the details:

.Outdated in the books
[cols="3,5",options="header"]
|===
|In the books |Today

|`+http://java.sun.com/jstl/sql+`, `+http://java.sun.com/jstl/xml+` and the `sql_rt`, `x_rt` libraries |One library per area with `jakarta.tags.sql` and `jakarta.tags.xml`; the `_rt` twins do not exist since JSTL 1.1 (EL is part of JSP 2.0)
|`javax.servlet.jsp.jstl.sql.*`, configuration variables `javax.servlet.jsp.jstl.sql.dataSource` |`jakarta.servlet.jsp.jstl.sql.*` and `jakarta.servlet.jsp.jstl.sql.dataSource`
|`+<x:parse xml="...">+`, `+<x:transform xml=...>+` and `xmlSystemId` |`doc` and `docSystemId`; the old names are deprecated (still accepted by 3.0.1)
|`sql:setDataSource` with a literal password, MySQL and Oracle driver class names of 2002 (the specification's own example still names `org.gjt.mm.mysql.Driver`) |A container-managed `DataSource` with the credentials outside the page, a current driver class
|JDBC from scriptlets, `Class.forName`, a hand-written pool, `sun.jdbc.rowset.CachedRowSet` |A `DataSource`, try-with-resources, `RowSetProvider.newFactory().createCachedRowSet()` if a disconnected result is needed (JDK 7 and later), or a data layer (see the Hibernate pages)
|The XML engine of the 2002 reference implementation |The 3.0.1 implementation embeds a shaded Xalan XPath engine (`org.eclipse.tags.shaded` in its stack traces) and uses the JDK's JAXP parser and transformer, with secure processing enabled
|No mention of XXE, secure processing or `accessExternalDTD` |A current concern: see <<xml-security>>
|`$cookie`, `$param`, `$header` XPath variables |Unchanged
|`RowSet` and the `Result` classes in `javax.servlet.jsp.jstl.sql` |Same API under `jakarta.servlet.jsp.jstl.sql` (`Result`, `ResultSupport`, `SQLExecutionTag`)
|===

Source: https://www.manning.com/books/jstl-in-action[Manning -- JSTL in Action]

Source: https://www.manning.com/books/web-development-with-javaserver-pages-second-edition[Manning -- Web Development with JavaServer Pages, Second Edition]

Source: https://jakarta.ee/specifications/tags/3.0/apidocs/jakarta.servlet.jsp.jstl/jakarta/servlet/jsp/jstl/sql/ResultSupport.html[Jakarta Tags 3.0 API -- ResultSupport]

The specification examples carry old habits too. The chapter 10 sample `jdbc:mysql://localhost/,org.gjt.mm.mysql.Driver` uses a
driver class of the year 2000, `<x:if select="$customer/[location='UK']">` is not valid XPath, the syntax of `x:forEach` in
12.6 has a stray `>` after `select`, and the two example TLDs of chapter 14 do not parse. They are listed with the other
inconsistencies found in this section. What the specification is right about, and the books agree: these tags are for a
prototype, a small internal tool or a stop-gap, and the day the page needs a second consumer, a test, a pool setting or a
security review, the query moves to Java.
