[#where-it-sits]
== Where This Page Sits

JSP is the oldest of the server-side view technologies of the Java platform, and Struts is the framework that made the
servlet-centric way of building JSP applications popular. Both are now maintenance and modernisation knowledge for most
teams: the Jakarta EE Tutorial says Jakarta Pages is archived in favour of Facelets, while Struts 7.4 and 6.12 are
released and supported and Struts 1 and 2.5 are end of life. The page therefore does two jobs. It explains the vocabulary
and the history that every later page of the section assumes, and it gives the facts needed to decide what to do with a

[#static-dynamic-cgi]
== Static Content, Dynamic Content and CGI

A *static* page is a file that the web server returns unchanged: every visitor gets the same bytes. A *dynamic* page is
computed for each request from the request itself (parameters, headers, cookies, the session) and from data that lives
elsewhere (a database, another service). The first mechanism the web had for dynamic pages was the Common Gateway
Interface. RFC 3875 describes CGI as a simple interface for running external programs, software or gateways under an
information server in a platform-independent manner, and it records that the interface had been in use by the World Wide
Web since 1993. A CGI program is started by the web server for each request, receives the request through environment
variables and standard input, and writes the response to standard output.

The Jakarta Servlet specification names the two weak points of that model when it compares servlets with CGI: servlets
are generally much faster than CGI scripts because a different process model is used, and they use a standard API that is
supported by many web servers, with all the advantages of the Java programming language. A servlet is a Java class
managed by a container (Tomcat, Jetty, GlassFish and others); the container loads it once, calls it on a thread for each
request, and takes care of the HTTP details.

[cols="2,3,3,3",options="header"]
|===
| | CGI program | Servlet | JSP page

| What runs the code
| A new operating-system process for each request, started by the web server
| One instance per servlet in a long-lived container, called on a thread per request
| A servlet generated from the page by the container and then run like any other servlet

| What the author writes
| A program that prints headers and markup
| A Java class that implements `+doGet+`, `+doPost+` and friends and prints markup
| A template: markup with dynamic parts (expressions, actions, tags)

| Typical weakness
| Process start-up cost; the language of the program decides everything else
| HTML inside Java strings, hard to design and easy to leave unescaped
| Logic creeping into the template when the page also acts as controller

| Where it lives today
| Still defined by RFC 3875; rarely used for new Java work
| Jakarta Servlet 6.1, the base of every Java web framework (Struts, Spring MVC, Faces)
| Jakarta Pages 4.0, in the EE 11 Web Profile
|===

[#servlet-example]
=== The Bookshelf as a Plain Servlet

The first Bookshelf page has no template at all. The servlet asks the repository for the books and prints the markup
itself. This is how Java web pages were written before JSP, and it shows what a template system removes.

.PlainServletBooks.java, the HTML written from Java
[source,java]
----
@WebServlet("/servlet-style")
public class PlainServletBooks extends HttpServlet {
    private final BookRepository repository = new BookRepository();

    @Override
    protected void doGet(HttpServletRequest request, HttpServletResponse response) throws IOException {
        response.setContentType("text/html;charset=UTF-8");
        PrintWriter out = response.getWriter();
        out.println("<!DOCTYPE html>");
        out.println("<html><body>");
        out.println("<h1>Bookshelf</h1>");
        out.println("<ul>");
        for (Book book : repository.findAll()) {
            out.println("<li>" + book.title() + " by " + book.author() + " (" + book.year() + ")</li>");
        }
        out.println("</ul>");
        out.println("</body></html>");
    }
}
----

With the WAR deployed under the context `+/bookshelf+`, `+curl http://localhost:18080/bookshelf/servlet-style+` returned:

[source,html]
----
<!DOCTYPE html>
<html><body>
<h1>Bookshelf</h1>
<ul>
<li>Dune by Frank Herbert (1965)</li>
<li>Neuromancer by William Gibson (1984)</li>
<li>Hyperion by Dan Simmons (1989)</li>
</ul>
</body></html>
----

The page works, but the markup is buried in string literals, a designer cannot edit it, and the values are written
without escaping: a title that contains `+<script>+` would reach the browser as markup. A template system keeps the
markup as markup and makes escaping an explicit, visible step.

Source: https://jakarta.ee/specifications/servlet/6.1/jakarta-servlet-spec-6.1.html#comparing-servlets-with-other-technologies[Jakarta Servlet 6.1 -- Comparing Servlets with Other Technologies]

[#template-systems]
== Template Systems and JSP

A *template system* inverts the servlet: the author writes the page as template data (the fixed text and markup) and adds
dynamic data to it with a small number of constructs. The Jakarta Pages specification describes the technology with four
concepts: template data, the addition of dynamic data, the encapsulation of functionality (JavaBeans components and tag
libraries that deliver custom actions, functions, listener classes and validation), and good tool support. Its stated
benefits include the separation of the developer and the author roles and the separation of dynamic from static content.

JSP is a template system that is *servlet-based*. The specification divides the life of a page into two phases. In the
translation phase the container validates the syntax of the page and determines the page implementation class that
corresponds to it; in the execution phase the container manages instances of that class in response to requests. In
practice the page becomes a servlet, which is why everything that is true of servlets (threading, scopes, sessions,
filters, the servlet context) is true of JSP.

The next example is the Bookshelf view as a Jakarta Pages template. It is the view of the Model 2 version shown later in
this page, so it reads the list from a request attribute that a controller has set; the page itself contains no Java.

.books.jsp, the Bookshelf as a template
[source,jsp]
----
<%@ page contentType="text/html; charset=UTF-8" pageEncoding="UTF-8" %>
<%@ taglib prefix="c" uri="jakarta.tags.core" %>
<!DOCTYPE html>
<html>
<body>
<h1>Bookshelf (Model 2)</h1>
<ul>
<c:forEach var="b" items="${books}">
  <li><a href="book?id=${b.id}"><c:out value="${b.title}"/></a> by <c:out value="${b.author}"/> (${b.year})</li>
</c:forEach>
</ul>
</body>
</html>
----

The first request translates and compiles the page. Tomcat keeps the generated source in its `+work+` directory, so the
translation phase can be inspected. For the small page `+book.jsp+` (the detail view of one book) the generated class
extends Tomcat's `+HttpJspBase+`, has `+_jspInit+`, `+_jspService+` and `+_jspDestroy+` methods, and writes the template
text with `+out.write+`; this is the relevant part of what Tomcat 11.0.26 generated:

calls, each tag becomes a call to a generated method that drives a tag handler, a JSP gets a session by default

=== JavaBeans, Tag Libraries and "JSP in J2EE"

The first books about JSP describe the technology as part of J2EE, the Java 2 Platform, Enterprise Edition, and present
three ways of keeping Java out of the page: JavaBeans components (objects with a no-argument constructor and getters and
setters that the page reads through actions or expressions), custom tag libraries, and servlets that prepare the data
before the page runs. All three survive. The vocabulary changed with the platform's ownership:

=== Applets and Servlets

Early JSP material contrasts servlets with applets, Java programs downloaded to the browser, as the two ways of running
Java in a web application. The applet side of that comparison is gone. Browsers stopped supporting applets, the Applet
API was deprecated for removal in JDK 17, and JEP 504 removes the `+java.applet+` package in JDK 26 (together with the
`+appletviewer+` tool, which had already been removed in JDK 11). The Pages specification followed: the `+jsp:plugin+`
action and its related actions, which generated the markup that loaded an applet, were deprecated in Pages 3.1 because
no major browser supports the elements they produced, and they were removed in Pages 4.0. The server-side half of the
comparison, servlets and JSP, is what remains.

Source: https://openjdk.org/jeps/504[JEP 504 -- Remove the Applet API]

[#model-1-and-model-2]
== Model 1 and Model 2

Once the servlet and the JSP page both exist, the question is which of them does what. Two answers became the standard
vocabulary for JSP applications:

* *Model 1* (page-centric): the request goes straight to a JSP page. The page reads the parameters, calls the business
objects (usually through a JavaBean), decides what to show and writes the HTML. Variants of the page-centric design are
role-based pages (one page for each kind of user), action targets (a page that only processes a form and forwards or
redirects) and composite pages (a page assembled from included fragments).
* *Model 2* (servlet-centric, MVC): the request goes to a servlet, the *front controller*. The controller reads the
request, calls the model, stores the result as request attributes, picks a view and *forwards* to it with a
`+RequestDispatcher+`. The view (a JSP) only renders what the controller prepared. Mapping the request to the unit of
work is often done with the *command pattern*: one small object for each operation, selected by the request path.

image::jsp-struts-model1-vs-model2.svg["Model 1, where books.jsp receives the request, calls the repository and writes the HTML, and Model 2, where a controller calls the repository, sets a request attribute and forwards to a view",width=720]

[cols="2,4,4",options="header"]
|===
| Concern | Model 1 | Model 2

| Entry point
| Every page is an entry point
| One controller (or one filter) is the entry point

| Where the logic lives
| In the page, or in beans called from the page
| In the controller and in the model; the view contains presentation only

| Navigation
| Hard-coded in links, redirects and `+jsp:forward+` actions across many pages
| Decided in one place (the controller or its configuration)

| Security and cross-cutting concerns
| Repeated in each page, easy to forget in one
| One interceptor, filter or controller step for all requests

| Testing
| Needs a container
| The controller and the model are plain Java classes

| Page designers
| Must work next to Java logic
| Work on markup and tags only

| Fits
| Small, mostly-read pages and prototypes
| Applications with forms, validation, several views of the same data
|===

=== Model 1: the Page Does Everything

The Model 1 version of the Bookshelf search is one JSP page. It declares the repository as a bean in application scope
with `+jsp:useBean+`, reads `+param.filter+` and calls the repository method from an EL expression (method invocation in
EL is part of the Expression Language since EL 3.0, and Tomcat 11 supports it).

.model1/books.jsp, the page as controller, model access and view
[source,jsp]
----
<%@ page contentType="text/html; charset=UTF-8" pageEncoding="UTF-8" %>
<%@ taglib prefix="c" uri="jakarta.tags.core" %>
<jsp:useBean id="repository" class="org.example.bookshelf.BookRepository" scope="application"/>
<!DOCTYPE html>
<html>
<body>
<h1>Bookshelf (Model 1)</h1>
<form method="get" action="books.jsp">
  <input type="text" name="filter" value="<c:out value='${param.filter}'/>">
  <button type="submit">Search</button>
</form>
<ul>
<c:forEach var="b" items="${repository.search(param.filter)}">
  <li><c:out value="${b.title}"/> by <c:out value="${b.author}"/> (${b.year})</li>
</c:forEach>
</ul>
</body>
</html>
----

`+curl "http://localhost:18080/bookshelf/model1/books.jsp?filter=dune"+` returned the form with the value kept and one list
item:

[source,html]
----
<h1>Bookshelf (Model 1)</h1>
<form method="get" action="books.jsp">
  <input type="text" name="filter" value="dune">
  <button type="submit">Search</button>
</form>
<ul>

  <li>Dune by Frank Herbert (1965)</li>

</ul>
----

Escaping is the page's own job in Model 1. Sending the filter `+"><script>alert(1)</script>+` produced
`+value="&#034;&gt;&lt;script&gt;alert(1)&lt;/script&gt;"+`, because `+c:out+` escapes the five XML characters by default.
The `+${b.year}+` expression is written without `+c:out+` here because it is a number; the same expression on a string
would have been written unescaped.

Source: https://jakarta.ee/specifications/pages/4.0/jakarta-server-pages-spec-4.0.html#jsp:useBean[Jakarta Server Pages 4.0 -- jsp:useBean], https://jakarta.ee/specifications/tags/3.0/jakarta-tags-spec-3.0.html#c:out[Jakarta Standard Tag Library 3.0 -- c:out]

=== Model 2: a Front Controller and a Command Map

The Model 2 version splits the same page in three. A `+Command+` is one unit of controller work: it fills the request and
returns the name of a view. The front controller maps the path after `+/model2+` to a command and forwards to the
view with the `+RequestDispatcher+`. The views sit under `+/WEB-INF/views+`, where a browser cannot request them directly.

.Command.java and FrontController.java
[source,java]
----
@FunctionalInterface
public interface Command {
    String execute(HttpServletRequest request);
}

@WebServlet("/model2/*")
public class FrontController extends HttpServlet {
    private final BookRepository repository = new BookRepository();
    private final Map<String, Command> commands = Map.of(
            "/books", request -> {
                request.setAttribute("books", repository.search(request.getParameter("filter")));
                return "books";
            },
            "/book", request -> {
                String id = request.getParameter("id");
                Book book = id == null ? null : repository.findById(Long.parseLong(id));
                request.setAttribute("book", book);
                return book == null ? "not-found" : "book";
            });

    @Override
    protected void doGet(HttpServletRequest request, HttpServletResponse response)
            throws ServletException, IOException {
        Command command = commands.get(request.getPathInfo());
        if (command == null) {
            response.sendError(HttpServletResponse.SC_NOT_FOUND);
            return;
        }
        String view = command.execute(request);
        request.getRequestDispatcher("/WEB-INF/views/" + view + ".jsp").forward(request, response);
    }
}
----

| `+/bookshelf/model2/book?id=9+`
| 200
| The `+not-found+` view, `+<h1>No such book</h1>+` (a real application would also set the status 404)

| `+/bookshelf/model2/nothing+`
| 404
| Tomcat's error page, from the `+sendError+` call

| `+/bookshelf/model2/book?id=abc+`
| 500
| `+NumberFormatException: For input string: "abc"+`, because the command trusts the parameter

| `+/bookshelf/WEB-INF/views/books.jsp+`
| 404
| The container never serves anything under `+WEB-INF+` directly
|===

The last two rows are the lessons of Model 2. A controller is a single place where input must be validated (the `+id+`
parameter above should be checked, and an invalid one should become a 400 or a validation message, not an exception),
and the views are reachable only through the controller. Both ideas are what Struts and Spring MVC turn into
configuration: Struts gives every action an interceptor stack for exactly this kind of step.

Source: https://jakarta.ee/specifications/servlet/6.1/jakarta-servlet-spec-6.1.html#the-forward-method[Jakarta Servlet 6.1 -- The Forward Method]

=== Keeping Java Out of the Page

A Model 2 discipline can be enforced by the container. The `+scripting-invalid+` element of a `+jsp-property-group+`
turns scriptlets, declarations and expressions into translation errors for the pages it matches. The scratch WAR
declares it for the `+/strict/*+` pages and puts a scriptlet there:

.web.xml, scripting disabled for /strict/*
[source,xml]
----
<web-app xmlns="https://jakarta.ee/xml/ns/jakartaee"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="https://jakarta.ee/xml/ns/jakartaee https://jakarta.ee/xml/ns/jakartaee/web-app_6_1.xsd"
         version="6.1">
  <jsp-config>
    <jsp-property-group>
      <url-pattern>/strict/*</url-pattern>
      <scripting-invalid>true</scripting-invalid>
    </jsp-property-group>
  </jsp-config>
</web-app>
----

.strict/scriptlet.jsp
[source,jsp]
----
<%@ page contentType="text/html; charset=UTF-8" %>
<html><body>
<% out.println("Hello from a scriptlet"); %>
</body></html>
----

The request returned status 500, and the root cause of the error page read:

[source,text]
----
org.apache.jasper.JasperException: /strict/scriptlet.jsp (line: [3], column: [2]) Scripting elements ( <%!, <jsp:declaration, <%=, <jsp:expression, <%, <jsp:scriptlet ) are disallowed here.
----

A modern project sets this for all pages (`+*.jsp+`), so that the page-centric style with Java inside the template cannot
creep back in. The JSP pages of Part I teach xref:web/jsp-struts/jsp/expression-language-basics.adoc[EL], xref:web/jsp-struts/jsp/jstl-core.adoc[JSTL] and xref:web/jsp-struts/jsp/tag-files-and-layouts.adoc[tag files] for exactly that reason.

Source: https://jakarta.ee/specifications/pages/4.0/jakarta-server-pages-spec-4.0.html#disabling-scripting-elements[Jakarta Server Pages 4.0 -- Disabling Scripting Elements]

=== Design Patterns around Model 2

The books that describe Struts 1 list the design patterns behind Model 2 in an appendix. The patterns are still the
vocabulary of the framework documentation, and the section covers each one on the page where its code lives.

[cols="2,4,4",options="header"]
|===
| Pattern | Idea | Where it appears

| Front Controller
| One component receives every request and dispatches it
| The `+FrontController+` servlet above (built out in xref:web/jsp-struts/jsp/mvc-with-servlets-and-jsp.adoc[MVC with Servlets & JSP]); `+StrutsPrepareAndExecuteFilter+` in Struts 2; the `+DispatcherServlet+` in Spring MVC

| Service to Worker
| The controller delegates the work to a helper before choosing the view
| The command map above; the action class in Struts

| Composite View
| A page is assembled from reusable parts (header, menu, body)
| Includes, tag files and the Tiles plugin (xref:web/jsp-struts/jsp/tag-files-and-layouts.adoc[Tag Files & Layouts] in Part I and xref:web/jsp-struts/struts/tiles-and-page-layouts.adoc[Tiles & Page Layouts] in Part II)

| Synchronizer Token
| A one-time token in a form that the server checks, so a repeated submission can be recognised
| The token support of Struts (xref:web/jsp-struts/struts/double-submit-tokens-and-wait-pages.adoc[Double-Submit Tokens & Wait Pages] in Part II)

| Command
| One object for each operation, chosen by the request
| `+Command+` above; the action in Struts
|===

The page-centric versus servlet-centric choice also settles an old architecture question from the Enterprise JavaBeans
era: where the business logic lives. Today the answer is a service layer behind the controller, normally a Spring or CDI
bean (see the xref:backend/hibernate/index.adoc[Hibernate section] for persistence); Enterprise JavaBeans are no longer
a precondition for a Model 2 application.

[#struts-1]
== Struts 1: Model 2 as a Framework

Struts started in 2000, and its first release came in June 2001. It packaged the Model 2 idea as a framework with a
controller servlet, configuration files and a tag library, so that every application did not rewrite the front
controller. The Struts site describes the framework as a request handler mapped to a URI, a response handler that
transfers control to another resource, and a tag library for form-based applications, and it gives the reason for the
name: the framework is meant to furnish the "invisible underpinnings" of professional application development.

The Struts 1 vocabulary and its Struts 2 counterparts:

[cols="3,4,4",options="header"]
|===
| Struts 1 concept | What it is | Struts 2 and 7 counterpart

| `+ActionServlet+`
| The front controller servlet, mapped to a pattern such as `+*.do+`
| `+StrutsPrepareAndExecuteFilter+`, a servlet filter mapped to `+/*+`; the default action extension is `+action+` or none, and `+*.do+` no longer works

| `+struts-config.xml+`
| The configuration file: form beans, global forwards, action mappings, controller, message resources, plug-ins
| `+struts.xml+` and `+struts-default.xml+`: packages, namespaces, actions, results, interceptors

| `+ActionMapping+`
| The configuration of one request path (the `+path+`, the `+type+` of the action, the form, the forwards)
| The `+<action>+` element

| `+ActionForward+`
| A named destination that an action returns
| A `+<result>+`, selected by the String that the action method returns

| `+ActionForm+`
| A bean that receives the form fields, with `+reset()+` and `+validate()+`
| The action's own properties (or a `+ModelDriven+` model), filled by the Parameters interceptor and checked by the Validation interceptor; fields need `+@StrutsParameter+` in Struts 7

| `+Action+`
| The unit of work with an `+execute()+` method; one instance serves all requests
| An action class created for each request, usually extending `+ActionSupport+`

| Struts tag libraries (`+html+`, `+bean+`, `+logic+`, `+nested+`)
| JSP tags that bind to form beans
| The Struts tag library (`+s:+`), which reads from the value stack with OGNL

| Tiles
| Page layouts and definitions
| The Tiles plugin (Tiles code bundled in the plugin since 6.3.0), or SiteMesh, or tag-file layouts
|===

Two properties of Struts 1 explain much of the move away from it. Its actions were shared between requests, so the
Struts site's primer tells readers that with Struts 1 they had to know a lot about writing code that runs in a
multi-threaded environment, whereas each Struts 2 action is a plain object instantiated for each request. And its form
beans were a second copy of the data (the form bean, then the business object), which Struts 2 removes by letting the
action carry the properties.

=== The End of Struts 1

The Struts 1 end-of-life announcement of 2013-04-05 says that Struts 1.x has reached the end of its life and is no longer
officially supported. It records that the last release, 1.3.10, was published in December 2008 and that, in the meantime,
the community had pushed Struts 2 forward with as many as 23 releases by April 2013. The question-and-answer part of the
announcement is the clearest statement of what end of life means for an application that still uses it:

[cols="3,6",options="header"]
|===
| Question | Answer in short

| What happens to Struts 1 resources?
| They stay where they are: the documentation, the downloads of released 1.x versions, the source in the Apache Subversion repository and the artifacts in Maven Central.

| Will a security problem get a release?
| No. The project's answer is that users must find mitigations, patch the source themselves or migrate.

| Is there an urgent need to remove Struts 1?
| The team knew of no urgent issue in 2013, but security and bug fixes would no longer be provided.

| Can a new project still use it?
| Basically yes, but the team does not recommend it; before any code is written it is easy to choose another framework such as Struts 2.

| What to migrate to?
| There is no drop-in replacement. Struts 2 is recommended as the successor; other candidates named by the project are Spring Web MVC, Grails and Stripes.
|===

Time has confirmed the warning. CVE-2014-0114 (Apache Commons BeanUtils as distributed in Struts 1.x, a class-loader
manipulation through crafted request parameters) was published after the end-of-life announcement, and Struts 1 has
no fix. The Struts 1 documentation is no longer online (`+https://struts.apache.org/1.x/+` and the FAQ return 404); the
documentation archive of the last release is `+struts-1.3.10-docs.zip+` on `+archive.apache.org+`. The Part II page
xref:web/jsp-struts/struts/struts-1-classic-and-migration.adoc[Struts 1 (Classic) & Migration] teaches enough of it to read and migrate legacy code, and only that.

Source: https://struts.apache.org/struts1eol-announcement.html[Apache Struts 1 End-Of-Life (EOL) Announcement]

[#webwork-struts-2]
== WebWork, XWork and Struts 2

WebWork was another Model 2 framework, developed independently of Struts. Its second generation, WebWork 2, was built on
a generic command-pattern engine called XWork that does not know about HTTP, with a web layer on top of it. The Struts
announcement of the 2.0.1 beta in November 2006 describes the result in these terms: Struts 2 was originally known as
WebWork 2, and after several years of independent work the WebWork and Struts communities joined forces to create it.
The same announcement lists the design goals that Struts 2 took from WebWork: framework classes based on interfaces,
core interfaces independent of HTTP, results that can help prepare the response (unlike Struts 1 forwards), tags that
output stylesheet-driven markup, and intelligent defaults.

The three-way mapping of Model 2 onto Struts 2 is the one the later pages build on (see xref:web/jsp-struts/struts/architecture-and-request-lifecycle.adoc[Architecture & Request Lifecycle]):

[cols="2,3,4",options="header"]
|===
| MVC role | Struts 2 component | Notes

| Controller
| `+StrutsPrepareAndExecuteFilter+`
| A servlet filter, so it can sit in front of static resources and other filters; it finds the action mapping and runs the action through its interceptors

| Model
| The action (and the objects it calls)
| A plain Java class; its properties are filled from the request and are visible to the view

| View
| The result
| A JSP, a FreeMarker or Velocity template, JSON, a redirect, a stream or any other registered result type
|===

Other concepts of the architecture are named here once so that later pages can use them. The *interceptors* (xref:web/jsp-struts/struts/interceptors.adoc[Interceptors]) wrap each
action (parameter binding, validation, file upload, exception mapping and so on) and replace the `+RequestProcessor+` of
Struts 1; the *ActionContext* is the per-request context; the *ValueStack* (xref:web/jsp-struts/struts/value-stack-action-context-and-ognl.adoc[ValueStack, ActionContext & OGNL]) is the stack of objects (the action first)
that the tags and expressions search; and *OGNL* is the expression language that reads and writes the value stack.

import java.util.List;

import org.apache.struts2.interceptor.parameter.StrutsParameter;

public class BookAction extends ActionSupport {
    private final BookRepository repository = new BookRepository();

    }

    public List<Book> getBooks() {
        return repository.search(filter);

    public String getFilter() {
        return filter;
    }

    @StrutsParameter
    public void setFilter(String filter) {
        this.filter = filter;
    }
}

The example hides a pitfall that the first run of this page's scratch project hit. The first version of the view used the
`+Book+` record of the plain servlet version, and the page rendered empty list items (`+<li> by  ()</li>+`):
The cause was the OGNL allowlist, not a lack of record support: Struts 7.4.0 reads record components (`+isbn.code+` and
`+isbn.code()+` both printed the value in a re-check) once the record's package is listed in `+struts.allowlist.packageNames+`,
and prints nothing, with a WARN that the class is not allowlisted, when it is not. The `+Book+` of the Struts
project is a JavaBean with getters, and the view above renders `+Dune by Frank Herbert (1965)+`. The second
pitfall is the one Struts 7 designed in: with the `+@StrutsParameter+` annotation removed from `+setFilter+`, the same
request `+/books?filter=dune+` returned all three books, because an unannotated setter is no longer an injection point.
There was no error; the parameter was simply ignored.

[#javax-to-jakarta]
== From javax to jakarta

Oracle contributed the Java EE technologies to the Eclipse Foundation, which continues them as Jakarta EE. The first
Jakarta EE release, 8, was fully compatible with Java EE 8 and kept the `+javax.*+` packages. Jakarta EE 9 then renamed the
packages: the specification text for Servlet says that version 5.0 is only a change of namespaces, and the Pages
specification lists, as the first change of Pages 3.0 compared with JSR 245, that the API moved from the
`+javax.servlet.jsp+` package to `+jakarta.servlet.jsp+`. The rename covers everything that this section uses:

[cols="3,3,3",options="header"]
|===
| Before (Java EE 8, Jakarta EE 8) | After (Jakarta EE 9 and later) | Used for

| `+javax.servlet.*+`, `+javax.servlet.http.*+`
| `+jakarta.servlet.*+`, `+jakarta.servlet.http.*+`
| Servlets, filters, listeners, sessions

| `+javax.servlet.jsp.*+`
| `+jakarta.servlet.jsp.*+`
| Pages API, tag handlers

| `+javax.servlet.jsp.jstl.*+`
| `+jakarta.servlet.jsp.jstl.*+`
| JSTL API classes (`+Config+`, `+LocalizationContext+`)

| `+javax.el.*+`
| `+jakarta.el.*+`
| Expression Language API

| `+http://java.sun.com/jsp/jstl/core+` (and `+fmt+`, `+sql+`, `+xml+`, `+functions+`)
| `+jakarta.tags.core+` (and `+fmt+`, `+sql+`, `+xml+`, `+functions+`)
| JSTL tag-library URIs, renamed in Tags 3.0; the old URIs are identifiers and never links to follow

| `+com.opensymphony.xwork2.*+`
| `+org.apache.struts2.*+`
| Struts 7 repackaging, independent of the jakarta change

| `+xmlns="http://xmlns.jcp.org/xml/ns/javaee"+` in `+web.xml+`
| `+xmlns="https://jakarta.ee/xml/ns/jakartaee"+`
| Deployment descriptor namespace
|===

=== What Happens When a javax Application Meets Tomcat 11

Tomcat 10 and later implement the `+jakarta.*+` APIs only. The Tomcat migration guide calls the change a significant
breaking change between 9.0.x and 10.0.x: web applications must be recompiled against the new APIs. A small `+javax+`
WAR makes the symptoms concrete. It has two servlets built against `+javax.servlet-api+` 4.0.1: one registered with
`+@WebServlet+` and one declared in `+web.xml+`.

.A servlet that still imports javax.servlet
[source,java]
----
import javax.servlet.annotation.WebServlet;
import javax.servlet.http.HttpServlet;
import javax.servlet.http.HttpServletRequest;
import javax.servlet.http.HttpServletResponse;

@WebServlet("/annotated")
public class AnnotatedServlet extends HttpServlet {
    @Override
    protected void doGet(HttpServletRequest request, HttpServletResponse response) throws IOException {
        response.getWriter().println("Bookshelf on javax.servlet");
    }
}
----

On Tomcat 11.0.26 the WAR deployed without any deployment error, and then:

[cols="3,1,5",options="header"]
|===
| Request | Status | Why

| `+/bookshelf-javax/annotated+`
| 404
| Tomcat scans for the `+jakarta.servlet.annotation.WebServlet+` annotation; the `+javax+` one is just an unknown annotation, so no servlet is mapped and nothing says so

| `+/bookshelf-javax/declared+`
| 500
| The servlet declared in `+web.xml+` is found, but loading it fails with `+java.lang.ClassNotFoundException: javax.servlet.http.HttpServlet+` in the container's log
|===

Silent 404s for annotated servlets are the more dangerous of the two, because the deployment looks healthy. There are three
ways out. The first is to change the imports to `+jakarta.*+`, change the dependency to `+jakarta.servlet-api+` (with the
`+provided+` scope) and recompile; this is a mechanical change, and the only one the Servlet specification asks for. The
second is to let Tomcat convert the application at deployment time: the migration guide describes placing the web
application in the host's `+legacyAppBase+` folder (by default `+webapps-javaee+`), from where the Apache Tomcat migration
tool for Jakarta EE converts it into an equivalent Jakarta EE application in `+appBase+`; the same tool can be run ahead of
time for faster deployment. The third is to stay on Tomcat 9.0.x for as long as it is supported: its end of support is
no earlier than 31 March 2027, so it is a bridge, not a destination. Libraries matter too: a `+javax+` dependency such as an
old tag library or an old framework version must be replaced by a `+jakarta+` release, which is the real reason Struts 2.5
applications are migrated by way of 6.x.

Source: https://tomcat.apache.org/migration-10.html#Specification_APIs[Tomcat -- Migration Guide 10.0.x, specification APIs], https://tomcat.apache.org/tomcat-11.0-doc/config/host.html#Standard_Implementation[Tomcat 11 -- Host, legacyAppBase]

[#architectural-styles]
== Action-Based, Component-Based, Template Engines and SPAs

JSP and Struts belong to one of four families of web UI technologies. The families answer two questions: who owns the
HTML, and how much of the request/response cycle does the framework hide?

[cols="2,3,3,3,3",options="header"]
|===
| Style | Request model | Who builds the HTML | Examples | Trade-off

| Action-based (request-based) MVC
| One URL maps to one action; the framework hides little of HTTP
| A view template on the server, filled with the action's data
| Struts, Spring MVC, Jakarta MVC, ASP.NET Core MVC, Laravel, Django
| Full control of URLs and markup and a stateless server; the developer wires state and forms

| Component-based
| The page is a tree of server-side components that keep state and raise events
| Components render themselves, usually through a template language such as Facelets
| Jakarta Faces, Wicket, Tapestry, Vaadin
| Less HTML and JavaScript to write; the state lives on the server and the abstraction leaks when the HTML must be exact

| Server-side template engine
| Not a framework: it turns a template and a model into text
| The engine, inside a controller of any framework
| JSP and JSTL, Thymeleaf, FreeMarker, Velocity, Qute
| Choose it separately from the framework; the engines differ in how natural, how safe and how fast they are

| Single-page application (SPA)
| The server returns data (JSON); the browser holds the application
| JavaScript in the browser
| React, Angular, Vue
| Rich interactivity, a second code base, and an API that the server must secure
|===

Struts places itself explicitly in the first family. Its introduction says the framework does not try to hide the stateless
nature of the web and builds on the request/response cycle, and it recommends component frameworks (the page names Wicket
and Tapestry) for teams that want to build server-side components that render on the client side. The introduction also
notes that Struts is not tied to a front-end technology: in the old days it was JSP, then came Velocity and FreeMarker, and
it works with static HTML and a JavaScript front end as well.

Jakarta MVC 3.0 (a release aligned with Jakarta EE 11 that is not among the specifications listed for the Jakarta EE 11
platform and its profiles) is the standard action-based framework; it is aligned with Jakarta RESTful Web Services 4.0 and
its 3.0 release removes the requirement that implementations support the Facelets view engine. Jakarta Faces 4.1 is the standard component framework
and Facelets is its view declaration language. The SPA family is documented on this site in the
xref:web/react/index.adoc[React], xref:web/angular/index.adoc[Angular], xref:web/vue/index.adoc[Vue.js] and
xref:web/nextjs/index.adoc[Next.js] sections, the Vaadin component framework in the
xref:web/vaadin/index.adoc[Vaadin Reference], Jakarta Faces and Facelets in the xref:web/jsf/index.adoc[JSF (JavaServer Faces)]
section, and GWT, which compiles Java to JavaScript for the browser, in the xref:web/gwt/index.adoc[GWT (Google Web Toolkit)] section.

Source: https://struts.apache.org/birdseye.html#the-apache-struts-web-framework[Struts -- From a birds eye], https://jakarta.ee/specifications/mvc/3.0/[Jakarta MVC 3.0], https://jakarta.ee/specifications/faces/4.1/[Jakarta Faces 4.1]

The same loop, in the four engines of the table that run without a container, makes the syntax differences concrete. The
standalone scratch project renders the Bookshelf list from a list of beans with FreeMarker 2.3.35, Velocity Engine 2.4.1
and Thymeleaf 3.1.5; the JSP form is the one shown earlier (`+c:forEach+`).

.The Bookshelf loop in JSP, FreeMarker, Velocity and Thymeleaf
[source,jsp]
----
<c:forEach var="b" items="${books}">
  <li><c:out value="${b.title}"/> by <c:out value="${b.author}"/> (${b.year})</li>
</c:forEach>
----

[source,ftl]
----
<#list books as book>
  <li>${book.title} by ${book.author} (${book.year?c})</li>
</#list>
----

[source,velocity]
----
#foreach($book in $books)
  <li>$book.title by $book.author ($book.year)</li>
#end
----

[source,html]
----
<li th:each="book : ${books}"><span th:text="${book.title}">Dune</span> by <span th:text="${book.author}">Frank Herbert</span> (<span th:text="${book.year}">1965</span>)</li>
----

All three engines produced the same list for the books Dune (1965) and Neuromancer (1984): `+<li>Dune by Frank Herbert (1965)</li>+`
for FreeMarker and Velocity (Thymeleaf wrapped each value in a `+<span>+`, as its template says). One difference is worth
remembering: FreeMarker formats numbers for the locale, so with an English locale `+${book.year}+` printed `+1,965+`; the
`+?c+` built-in (computer format) is what prints `+1965+`. JSP's EL and Velocity print the integer as it is. Facelets and
Qute run only inside Jakarta Faces and Quarkus, so their rows are described from their documentation and not executed.

Source: https://www.thymeleaf.org/doc/tutorials/3.1/usingthymeleaf.html#iteration[Using Thymeleaf -- Iteration], https://freemarker.apache.org/docs/ref_builtins_number.html#ref_builtin_c[FreeMarker -- c built-in], https://velocity.apache.org/engine/2.4/user-guide.html#foreach-loop[Velocity 2.4 User Guide -- foreach loop], https://jakarta.ee/specifications/tags/3.0/jakarta-tags-spec-3.0.html#c:forEach[Jakarta Standard Tag Library 3.0 -- c:forEach]

[#pitfalls]
== Pitfalls

[cols="3,3,4",options="header"]
|===
| Symptom or error | Cause | Fix

| A `+@WebServlet+` class answers 404 on Tomcat 10 or later, with no deployment error
| The class imports `+javax.servlet.annotation.WebServlet+`; Tomcat only scans for the `+jakarta+` annotation
| Change the imports and the dependency to `+jakarta.servlet-api+`, recompile, or run the Tomcat migration tool

| `+java.lang.ClassNotFoundException: javax.servlet.http.HttpServlet+` at the first request to a `+web.xml+` servlet
| A `+javax+` WAR on a `+jakarta+` container
| The same: recompile, convert or run on Tomcat 9

| Struts list items render empty (`+<li> by  ()</li>+`) although the action returns data
| The class of the object is not in the OGNL allowlist (a record is read in 7.4.0 once its package is allowlisted)
| Add the package to `+struts.allowlist.packageNames+` (or use a JavaBean in an allowlisted package); records also work in JSP EL 6.0

| A Struts request parameter has no effect and there is no error
| The setter has no `+@StrutsParameter+` annotation, which Struts 7 requires on every injection point
| Annotate the setter with `+@StrutsParameter+` (xref:web/jsp-struts/struts/parameter-injection-and-struts-parameter.adoc[Parameter Injection and @StrutsParameter] describes the other injection points)

| `+/books.do+` returns 404 in a Struts 7 application
| The default action extension is `+action+` or none; `+.do+` is the Struts 1 convention
| Use `+/books+` or `+/books.action+`, or set `+struts.action.extension+` deliberately

| A JSP in the web root can be requested directly
| The page is outside `+WEB-INF+`, so it bypasses the controller
| Put views under `+/WEB-INF/views+` and forward to them

| `+Scripting elements ( <%!, ... ) are disallowed here+`
| A `+jsp-property-group+` with `+scripting-invalid+` matches a page that still uses a scriptlet
| Replace the scriptlet with EL, JSTL or a tag; that is the purpose of the setting

| `+NumberFormatException+` from a command or action, status 500
| The request parameter was parsed without validation
| Validate in the controller (Struts: the Validation interceptor and type conversion) and answer 400 or show a message

| FreeMarker prints `+1,965+` for a year
| FreeMarker formats numbers for the locale
| Use the `+?c+` built-in for identifiers and years, or a number format on purpose

| `+struts-7.0.dtd+` returns 404, and the example in the documentation uses `+struts-6.0.dtd+`
| The newest DTD published by the project is 6.0; there is no 7.0 DTD
| Keep the 6.0 DOCTYPE in `+struts.xml+` for Struts 7

| Documentation shows `+FilterDispatcher+`, `+com.opensymphony.xwork2.*+` or a `+javax+` `+web.xml+` namespace
| The page or book describes an older version
| Use `+StrutsPrepareAndExecuteFilter+`, `+org.apache.struts2.*+` and the `+jakarta.ee+` namespace

| JSP works in the IDE but not in the Spring Boot executable JAR
| JSP is not supported in executable JARs
| Package a WAR for Tomcat or Jetty, or choose another view technology

| A new project is started on Struts 1 "because the book says so"
| The book was written for 1.0 or 1.1, when Struts 1 was current
| Choose a maintained framework; see <<when-to-choose>>
|===

[#books-outdated]
== Where the Books Are Outdated

The four books that this section consulted (two for JSP and JSTL, two for Struts) were written for J2EE 1.3 and 1.4,
Servlet 2.3 and 2.4, JSP 1.2 and 2.0, JSTL 1.0, Struts 1.0 and 1.1 and Struts 2.0. The ideas on this page are still
valid; the details are not. No text, listing or figure of the books is used in this section: they are listed in the
bibliography of the section's index page for readers who own them. Where this page's topic is concerned, these are the
differences to know:

[cols="2,4,4",options="header"]
|===
| Area | What the books assume | Today

| Platform
| J2EE 1.3 or 1.4, Servlet 2.3 or 2.4, JSP 1.2 or 2.0, JDK 1.2 to 5, Tomcat 4 or 6, `+javax.*+`
| Jakarta EE 11, Servlet 6.1, Pages 4.0, EL 6.0, Java 21 (17 is the minimum), Tomcat 11, `+jakarta.*+`

| Script-heavy pages
| Scriptlets as the normal way to write a page
| EL, JSTL and tag files; scripting can be switched off with `+scripting-invalid+`

| Applets
| `+jsp:plugin+` to load an applet is a standard feature
| Removed in Pages 4.0; the Applet API itself is removed in JDK 26

| Removed Servlet API
| `+SingleThreadModel+`, `+HttpSessionContext+`, `+HttpUtils+`
| Removed in Servlet 6.0; use `+request.getRequestURL()+` and other current methods

| JSTL URIs
| `+http://java.sun.com/jstl/core+` and the `+_rt+` twin libraries
| `+jakarta.tags.core+` and one library for each area

| Deployment descriptor
| Servlet 2.3 DTD, `+<taglib>+` directly under `+<web-app>+`
| The Servlet 6.1 schema, `+<jsp-config>+`, annotations and tag-library auto-discovery

| Struts 1
| Struts 1.0 and 1.1 beta as the current framework; `+perform()+`, `+ActionError+`, `+data-sources+`
| End of life since 2013; `+perform()+` was removed in 1.2; teach Struts 1 only to read and migrate legacy code

| Struts 2 filter
| `+FilterDispatcher+` with `+ActionContextCleanUp+`
| `+org.apache.struts2.dispatcher.filter.StrutsPrepareAndExecuteFilter+`

| Struts 2 packages
| `+com.opensymphony.xwork2.*+`
| `+org.apache.struts2.*+` (Struts 7)

| Parameter binding and OGNL
| Any public setter is bound from request parameters; free `+%{...}+` evaluation
| `+@StrutsParameter+` is required on every injection point; the OGNL allowlist and expression limits are on by default
|===

A few errata are worth knowing when following the books alongside this page. The Struts 1 book was written against
1.1 beta 2 and defers to an online errata page, so details of 1.1 final and later differ from its text; the Struts 2 book
writes the result constant in upper case where the value is lower-case `+success+`; and the JSTL book points to the wrong
chapter for the Expression Language in one appendix and says EL does not work in template text, which is true only of
JSTL 1.0 on JSP 1.2. The official documentation has its own stale spots, recorded for the final page of the section: the
Struts "birdseye" introduction still names AngularJS as a front-end option and says that only Struts 2 is maintained, the
`+web.xml+` example of the Struts documentation still uses the `+javax+` Java EE namespace, and the specification page
for Pages is titled "Jakarta Pages" while its document and Maven artifact still say "Server Pages".
