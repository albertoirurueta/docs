This page is written against GWT 2.13.1 (2026-06-19), `gwt-maven-plugin` 1.3.0, Elemental2 1.3.2, a JDK 21 toolchain with `-sourceLevel 17`, the Jakarta Servlet 6 stack of the `modular-webapp` archetype and Spring Boot 4.1.1 (Spring Framework 7.0.9, Spring Security 7.1.1, Tomcat 11.0.24), and was checked on 2026-10-09.
Every output block was produced with the Bookshelf scenario of this section: a probe module compiled to JavaScript for each library, a Spring Boot application serving the REST API and the compiled files, and headless Chrome 155 loading the page and reporting the log.
It covers **client** code (the REST and JSON code that is compiled to JavaScript), **shared** code (the DTO classes the client libraries need), **server** code (the Spring Boot REST backend and a proxy to a third-party service) and **build** settings (the Maven coordinates, annotation processors and module inherits each library needs).

GWT-RPC is the way GWT calls a Java servlet with Java objects.
Many applications talk to something else: a REST API that other clients also use, a service written in another language, or a public JSON API.
For that, the Developer Guide says the application is free to integrate "other RPC mechanisms, such as JSON using the GWT supplied RequestBuilder class, JSNI methods or a third party library".
This page is about the third-party and browser-native options, and about the server side of the same conversation.

Reading the table:

* **Pick by the maintenance signal you need.** `domino-rest` and `domino-jackson` published releases within the last three months of the check date; Elemental2 published a release candidate (1.4.0-RC1) in July 2026, while its latest stable release, 1.3.2, is thirteen months old.
RestyGWT, AutoREST and gwt-jackson did not publish a release in the last two years, but all three still compiled and ran against GWT 2.13.1 in the probes below, which is not a promise that they will with the next GWT release.
* **A library that works today still needs an owner.** If you adopt one of the three quiet projects, plan to fork or replace it: the annotation processors and generators of those projects run inside the GWT compiler or `javac`, and a future JDK or GWT release can break them without anyone to fix them.
* **GWT itself documents none of them.** The Developer Guide names `RequestBuilder`, JSNI and "a third party library"; it never names RestyGWT, AutoREST, gwt-jackson or DominoKit. The xref:web/gwt/ecosystem-and-libraries.adoc[Ecosystem & Libraries] page lists the wider library landscape.

== The Bookshelf REST API (Spring Boot)

Every client probe below talks to the same server: a Spring Boot application with a Bookshelf controller.
This is the server half of the conversation; the Spring side is documented in depth in xref:backend/springboot/rest-apis.adoc[REST APIs with Spring MVC and WebFlux] (controllers, Bean Validation, `ProblemDetail`, CORS), and the authentication side in xref:backend/springboot/spring-security.adoc[Spring Security].
The earlier pages of this section used a read-only servlet at `/api/books`; the controller below serves the same URL with the full set of verbs.

.The contract the clients use
[cols="1,3,2,4",options="header"]
|===
| Verb | Path | Success | Failure

| GET
| `/api/books?start=0&length=10`
| 200, `+{"total":4,"books":[...]}+`
| none expected; `length` is capped at 100 by the server

| GET
| `+/api/books/{id}+`
| 200, one book
| 404 `pass:c[application/problem+json]` with `detail` `No book 99`

| POST
| `/api/books`
| 201 with a `Location` header and the saved book
| 400 for a body that fails validation; 401 or 403 without authentication or without the CSRF header

| PUT
| `+/api/books/{id}+`
| 200, the saved book
| 404, 400, 401 or 403

| DELETE
| `+/api/books/{id}+`
| 204, no body
| 404, 401 or 403
|===

The payload is a DTO, never a JPA entity: the record fixes the JSON shape that the browser depends on, and a change to the database mapping cannot leak into the contract by accident.

[source,java]
----
public record BookDto(
    Long id,
    @NotBlank @Size(max = 120) String title,
    @NotBlank @Size(max = 80) String author,
    @Min(1450) @Max(2100) int year,
    @Min(0) int copies) {
}

public record BookPageDto(int total, List<BookDto> books) {
}

@RestController
@RequestMapping("/api/books")
public class BookController {
  private final BookStore store;

  public BookController(BookStore store) {
    this.store = store;
  }

  @GetMapping
  public BookPageDto list(@RequestParam(defaultValue = "0") int start,
                          @RequestParam(defaultValue = "10") int length) {
    return new BookPageDto(store.total(), store.slice(start, Math.min(length, 100)));
  }

  @GetMapping("/{id}")
  public BookDto get(@PathVariable long id) {
    return store.find(id).orElseThrow(() -> new ResponseStatusException(HttpStatus.NOT_FOUND, "No book " + id));
  }

  @PostMapping
  public ResponseEntity<BookDto> create(@Valid @RequestBody BookDto body) {
    BookDto saved = store.add(body);
    return ResponseEntity.created(URI.create("/api/books/" + saved.id())).body(saved);
  }

  @PutMapping("/{id}")
  public BookDto update(@PathVariable long id, @Valid @RequestBody BookDto body) {
    return store.replace(id, body)
        .orElseThrow(() -> new ResponseStatusException(HttpStatus.NOT_FOUND, "No book " + id));
  }

  @DeleteMapping("/{id}")
  @ResponseStatus(HttpStatus.NO_CONTENT)
  public void delete(@PathVariable long id) {
    if (!store.remove(id)) {
      throw new ResponseStatusException(HttpStatus.NOT_FOUND, "No book " + id);
    }
  }
}
----

Source: https://docs.spring.io/spring-boot/reference/web/servlet.html#web.servlet.spring-mvc.error-handling[Spring Boot -- Spring MVC: error handling], https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-ann-rest-exceptions.html[Spring Framework -- Error responses]

`BookStore` is an in-memory map in the probe, standing in for the repository of a real application.
The configuration needs three lines, one of which turns Spring errors into RFC 9457 problem documents:

=== Security: authorisation and CSRF

Reading is public, writing needs the `LIBRARIAN` role, and the browser proves it is the same application with a double-submit cookie:

[source,java]
----
@Configuration
public class SecurityConfig {

  @Bean
  SecurityFilterChain api(HttpSecurity http) throws Exception {
    http
        .csrf(csrf -> csrf.spa())
        .authorizeHttpRequests(auth -> auth
            .requestMatchers(HttpMethod.GET, "/api/**", "/", "/*.html", "/restdemo/**").permitAll()
            .requestMatchers("/api/**").hasRole("LIBRARIAN")
            .anyRequest().denyAll())
        .httpBasic(Customizer.withDefaults());
    return http.build();
  }
}
----

Source: https://docs.spring.io/spring-security/reference/servlet/exploits/csrf.html#csrf-integration-javascript-spa[Spring Security -- CSRF: Single-Page Applications]

`csrf.spa()` (present in Spring Security 7.1.1 and shown on the Spring Security CSRF page) configures a cookie repository that is not `HttpOnly`, so the page can read it: the server writes a cookie named `XSRF-TOKEN` and expects its value back in a request header named `X-XSRF-TOKEN`.
`httpBasic` is used here only because it keeps the probe small; a real application uses a form login, OAuth 2.0 or OpenID Connect, as the Spring Security page explains.
The authorisation rule is on the server: hiding a button in the GWT client does not protect anything, because the client code is public.

[source,text]

`CsrfFilter` runs before `BasicAuthenticationFilter`, so the request is still anonymous when the token check fails, and the authentication entry point answers with 401 instead of the access-denied handler's 403 (the Spring debug log said `Invalid CSRF token found for http://localhost:8934/api/books/4`).
A client must therefore treat both 401 and 403 on a write as "not allowed or token missing" and fetch a fresh token with a GET before retrying once.
When the same check runs for a request that needs no authentication, as in the headless-browser probe of the Elemental2 section below, the answer is `403` with an empty body.

== Elemental2 fetch

Elemental2 is Google's set of Java type definitions for the browser APIs, generated from the JavaScript externs (see xref:web/gwt/dom-and-elemental2.adoc[DOM and Elemental2] for the types, `DomGlobal`, `Promise` and a first `fetch` example).
For REST it gives you `DomGlobal.fetch`, `Response`, `Headers`, `RequestInit`, `AbortSignal` and `Promise`, and nothing else: the library has no JSON-to-object mapper, so the shape of a response is a JsInterop native type that costs no code.
This is the smallest dependency set of all the options, and the right choice for a handful of calls.

=== The data shapes

A native type with `name = "Object"` is "a plain JavaScript object with these properties"; no class is generated and no copying happens.
The `@JsOverlay` factory is the only code, and it is inlined:

[source,java]
----
@JsType(isNative = true, namespace = JsPackage.GLOBAL, name = "Object")
public class BookJson {
  public double id;
  public String title;
  public String author;
  public int year;
  public int copies;

  @JsOverlay
  public static BookJson create(String title, String author, int year, int copies) {
    BookJson book = new BookJson();
    book.title = title;
    book.author = author;
    book.year = year;
    book.copies = copies;
    return book;
  }
}

@JsType(isNative = true, namespace = JsPackage.GLOBAL, name = "Object")
public class BookPageJson {
  public int total;
  public JsArray<BookJson> books;
}
----

Source: https://www.gwtproject.org/doc/latest/DevGuideCodingBasicsJsInterop.html[GWT -- Coding Basics: JsInterop]

The id is a `double` because a JavaScript number is a double: a `long` field in a native type is not a safe way to read a number from JSON, and ids above 2^53 lose precision whatever the Java type is.
If the server uses 64-bit ids that large, send them as strings.
JsInterop is described on xref:web/gwt/jsinterop.adoc[the JsInterop page].

=== A small fetch wrapper

Hand-written calls repeat the same four decisions: the headers, the CSRF token, the deadline and what an error status means.
Put them in one class:

[source,java]
----
public final class Rest {
  static final String XSRF_COOKIE = "XSRF-TOKEN";
  static final String XSRF_HEADER = "X-XSRF-TOKEN";
  static final double DEFAULT_TIMEOUT_MS = 5000;

  public static Promise<Response> send(String method, String url, Object body, double timeoutMs) {
    RequestInit init = RequestInit.create();
    init.setMethod(method);
    init.setCredentials("same-origin");
    init.setSignal(AbortSignal.timeout(timeoutMs));

    Headers headers = new Headers();
    headers.set("Accept", "application/json");
    if (body != null) {
      headers.set("Content-Type", "application/json");
      init.setBody(Global.JSON.stringify(body));
    }
    if (!isSafe(method)) {
      String token = Cookies.getCookie(XSRF_COOKIE);
      if (token != null) {
        headers.set(XSRF_HEADER, token);
      }
    }
    init.setHeaders(headers);

    return DomGlobal.fetch(url, init).then(res -> res.ok ? Promise.resolve(res) : failed(res));
  }

  public static <T> Promise<T> json(String method, String url, Object body) {
    return send(method, url, body, DEFAULT_TIMEOUT_MS)
        .then(res -> res.status == 204 ? Promise.resolve((Object) null) : res.json())
        .then(value -> Promise.resolve(Js.<T>uncheckedCast(value)));
  }

  static boolean isSafe(String method) {
    return "GET".equals(method) || "HEAD".equals(method) || "OPTIONS".equals(method);
  }

  private static Promise<Response> failed(Response res) {
    return res.text().then(text -> {
      String detail = res.status + " " + res.statusText;
      if (text != null && text.startsWith("{")) {
        JsPropertyMap<Object> problem = Js.asPropertyMap(Global.JSON.parse(text));
        Object d = problem.get("detail");
        if (d != null) {
          detail = res.status + " " + d;
        }
      }
      return Promise.reject(new HttpException(res.status, detail));
    });
  }
}
----

Source: https://developer.mozilla.org/en-US/docs/Web/API/AbortSignal/timeout_static[MDN -- AbortSignal.timeout()], https://developer.mozilla.org/en-US/docs/Web/API/Request/credentials[MDN -- Request.credentials], https://www.gwtproject.org/javadoc/latest/com/google/gwt/user/client/Cookies.html[GWT Javadoc -- Cookies]

What each decision is, and why:

* **`setSignal(AbortSignal.timeout(ms))`.** `fetch` has no timeout of its own. `AbortSignal.timeout` aborts the request after the delay and rejects the promise with a `TimeoutError` (reproduced below with a delay of 0). Without it a hung server leaves the screen waiting for ever.
* **`setCredentials("same-origin")`.** It is the default, written out so the intent is reviewable: the session cookie goes to the page's own origin and to no other.
* **`Cookies.getCookie`** is the GWT class (`com.google.gwt.user.client.Cookies`); Elemental2 has no cookie API beyond the `document.cookie` string. The wrapper sends the token on every method except GET, HEAD and OPTIONS, the "safe" methods of RFC 9110.
* **An error status resolves the promise.** `fetch` rejects only for network failures and aborts. The wrapper turns a response with `ok == false` into a rejection of its own type, `HttpException`, which carries the status and the `detail` of the problem document.
* **The Java exception is the rejection value.** `+Promise.reject(new HttpException(...))+` rejects with the Java object, so a later handler can test `error instanceof HttpException`. I did not test a `throw` inside a callback; the explicit `reject` is the form that was tested.

`HttpException` is a plain `RuntimeException` with an `int` status.

=== Running a whole conversation

The entry point chains the calls.
The first lines show the shape; the other steps (update, delete, an invalid book, an unknown id, a write without a token, a timeout, an HTML page parsed as JSON, a cross-origin call) follow the same pattern:

[source,java]
----
BooksClient.list(0, 2)
    .then(page -> {
      log("list         : total=" + page.total + " returned=" + page.books.length);
      for (int i = 0; i < page.books.length; i++) {
        BookJson b = page.books.getAt(i);
        log("  book       : #" + (long) b.id + " " + b.title + " (" + b.year + ")");
      }
      return BooksClient.get(2);
    })
    .then(book -> {
      log("get(2)       : " + book.title + " by " + book.author);

    // ... delete, invalid, unknown id, no token, timeout, callback, Promise.all

=== Adapting a Promise to an AsyncCallback

Presenters written for the GWT-RPC style (see the MVP page, xref:web/gwt/mvp-activities-and-places.adoc[Activities and Places]) keep working if the client returns an `AsyncCallback`.
An adapter is five lines:

[source,java]
----
public static <T> void call(Promise<T> promise, AsyncCallback<T> callback) {
  promise.then(
      value -> {
        callback.onSuccess(value);
        return null;
      },
      error -> {
        callback.onFailure(error instanceof Throwable ? (Throwable) error : new RuntimeException(String.valueOf(error)));
        return null;
      });
}
----

Source: https://www.gwtproject.org/javadoc/latest/com/google/gwt/user/client/rpc/AsyncCallback.html[GWT Javadoc -- AsyncCallback]

The two-argument `then` is deliberate: an exception thrown by `onSuccess` is not routed to `onFailure`, so a bug in the presenter is not reported as a network error.
This is also the shape of the bridge to the `RequestBuilder` style (see xref:web/gwt/requestbuilder-json-and-xml.adoc[RequestBuilder, JSON & XML]): a `RequestCallback` becomes a `Promise` in the same way.

=== Mapping JSON without a library

There are three ways to turn a response into Java without a mapper, in order of cost:

.JSON mapping without a library
[cols="2,3,3",options="header"]
|===
| Way | When | Limits

| Native JsInterop type (`BookJson`) read from `Response.json()`
| the usual choice; zero code per property
| no validation: a missing field is `undefined`; `long` and `Date` are not supported by JSON itself

| `JsPropertyMap` (`Js.asPropertyMap`)
| a payload whose shape you do not control, or a map of unknown keys
| every access is a string key and an `Object`

| `JsonUtils` and `JSONParser` (GWT's own classes)
| old code, and the `JSONValue` tree model
| described on the xref:web/gwt/requestbuilder-json-and-xml.adoc[RequestBuilder, JSON & XML] page
|===

A library mapper (next sections) gains real Java objects with getters, setters, collections and annotations, and loses the zero-code property: every DTO has a generated serializer and deserializer in the compiled output.

== domino-rest and domino-jackson

DominoKit publishes two libraries that are designed together, and are the only ones in this page with releases in 2026.
`domino-jackson` is a JSON mapper: it reads and writes Java objects as JSON, generated at compile time by an annotation processor.
`domino-rest` generates a REST client from a Jakarta REST interface; its JSON handling is `domino-jackson`.
The `domino-rest` README states that the same client works in the browser (GWT 2 or GWT 3 / J2CL) and on the JVM, and the `domino-jackson` README says its generated mappers avoid runtime reflection, which matters for GWT and J2CL.
Both generate their code with annotation processors, which run in `javac` before the GWT compiler starts, instead of with GWT generators.

=== DTOs, the service and the call

A DTO is a plain class annotated `@JSONMapper`; a service is an interface annotated `@RequestFactory` with Jakarta REST annotations:

[source,java]
----
@JSONMapper
public class BookDto {
  public Long id;
  public String title;
  public String author;
  public int year;
  public int copies;
}

@JSONMapper
public class BookPageDto {
  public int total;
  public List<BookDto> books;
}

@RequestFactory(serviceRoot = "/api")
public interface BooksService {

  @GET
  @Path("books")
  BookPageDto list(@QueryParam("start") int start, @QueryParam("length") int length);

  @GET
  @Path("books/{id}")
  BookDto get(@PathParam("id") long id);

  @POST
  @Path("books")
  BookDto create(@RequestBody BookDto draft);
}
----

The annotation types come from `jakarta.ws.rs` (`GET`, `POST`, `Path`, `PathParam`, `QueryParam`) and from `org.dominokit.rest.shared.request.service.annotations` (`RequestFactory`, `RequestBody`), and `JSONMapper` from `org.dominokit.jackson.annotation`.
`javac` runs the processor during `mvn compile` and writes, for this probe, seven files to `target/generated-sources/annotations`: `BooksServiceFactory`, and for each DTO a `BookDto_MapperImpl`, a `BookDtoBeanJsonSerializerImpl` and a `BookDtoBeanJsonDeserializerImpl` (the same three for the page).
The generated factory has one method per interface method, returning a `ServerRequest<RequestType, ResponseType>`:

[source,java]
----
public ServerRequest<Void, BookPageDto> list(int start, int length) {
  BooksService_list instance = new BooksService_list();
  ParameterSetter.setParameter(instance, "start", () -> start, "Query");
  ParameterSetter.setParameter(instance, "length", () -> length, "Query");
  // ... meta parameters for GET and the path "books"
  return instance;
}
----

and the call reads like a promise chain: `onSuccess`, `onFailed`, then `send()`.

[source,java]
----
DominoRestConfig.initDefaults().addRequestInterceptor(new XsrfInterceptor());

BooksServiceFactory.INSTANCE
    .list(0, 2)
    .onSuccess(page -> {
      log("list    : total=" + page.total + " returned=" + page.books.size());
      for (BookDto b : page.books) {
        log("  book  : #" + b.id + " " + b.title + " (" + b.year + ")");
      }
    })
    .onFailed(failed -> log("list failed: " + failed.getStatusCode()))
    .send();

BooksServiceFactory.INSTANCE
    .get(99)
    .onSuccess(b -> log("get(99) : unexpected " + b.title))
    .onFailed(failed -> log("get(99) : " + failed.getStatusCode() + " " + failed.getBody()))
    .send();
----

Source: https://dominokit.com/solutions/domino-rest/v2/docs/getting-started[DominoKit -- domino-rest getting started]

`DominoRestConfig.initDefaults()` must run before the first request.
The interceptor copies the CSRF cookie into the header, using the `RequestInterceptor` interface that the library documents with a token example:

[source,java]
----
public class XsrfInterceptor implements RequestInterceptor {
  @Override
  public void interceptRequest(ServerRequest request, ContextWait<ServerRequest> contextWait) {
    String token = Cookies.getCookie("XSRF-TOKEN");
    if (token != null) {
      request.setHeader("X-XSRF-TOKEN", token);
    }
    contextWait.complete(request);
  }
}
----

Source: https://github.com/DominoKit/domino-rest[GitHub -- DominoKit/domino-rest]

`ContextWait` is `org.dominokit.domino.api.shared.extension.ContextAggregator.ContextWait` (from `domino-aggregator-shared`, a transitive dependency).
The request metadata in this version has the Java method name but not the HTTP verb (`RequestMeta` has `getMethodName`, not `getMethod`), so this interceptor adds the header to every request.
That is harmless on a same-origin GET and the server ignores it, but it must never be used to send the token to another origin.

== AutoREST

AutoREST (`com.intendia.gwt.autorest`) generates a model from a JAX-RS interface whose methods return RxJava 2 types: `Single<T>` for one JSON object, `Observable<T>` for a JSON array, `Completable` for no body.
It does not map JSON itself: the GWT module's `RequestResourceBuilder` uses `XMLHttpRequest` and `JSON.parse` and returns whatever object the parse produced, so DTOs are JsInterop native types, like the Elemental2 probe above.
The same interface can be implemented by a JAX-RS server, which is the idea of the project: one definition, a client generated for GWT, the JVM or Android.
That does not apply to a Spring MVC server, whose controllers do not use JAX-RS annotations.

[source,xml]
----

with the processor also declared in the `annotationProcessorPaths` of `maven-compiler-plugin`, as for `domino-rest`.

`BooksApi_RestServiceModel` is the class the processor generates (it implements `BooksApi` and chains `+method(GET).path(...).param(...).as(Single.class, ...)+`), and `@AutoRestGwt` is `com.intendia.gwt.autorest.client.AutoRestGwt`.

----

The last line is the mapper's default: a property that the DTO does not have is an error.
Spring Boot's server-side Jackson accepts unknown properties by default, so a server that adds a field would break a client that uses this default; annotate the DTO with Jackson's `@JsonIgnoreProperties(ignoreUnknown = true)` (listed among the annotations the project supports on its wiki; I did not run that annotation) when the server may evolve first.

The `javapoet` dependency is the one the README names "for the GWT compilation only"; in the probe it arrived with the `restygwt` POM, so I did not test a build without it.
The probe compiled without the JAXB API jar that RestyGWT needed.

== Calling third-party JSON services through a server-side proxy

A page cannot call just any JSON API from the browser: the same-origin policy blocks a response from another origin unless that origin sends CORS headers (xref:web/cors.adoc[What is CORS?] explains the mechanism).
The old workaround, JSONP, runs the response as a script and is described with its risks on the xref:web/gwt/requestbuilder-json-and-xml.adoc[RequestBuilder, JSON & XML] page.
The safe and still standard answer is a **server-side proxy**: the browser calls your own origin, and your server calls the third party.
This is also a security boundary: API keys for the third party live on the server and never in the compiled JavaScript, and the server decides what comes back.

[mermaid]
....
sequenceDiagram
  participant B as GWT client
  participant S as Bookshelf server
  participant C as Third-party catalogue
  B->>S: GET /api/isbn/9780132350884 (same origin)
  Note over S: validates the ISBN, builds the URL itself
  S->>C: GET /isbn/9780132350884.json (timeouts)
  C-->>S: JSON with many fields
  S-->>B: JSON with title and number_of_pages only
....

A Bookshelf screen can fill a book form from an ISBN.
The controller below is the proxy.
The browser sends the ISBN; the server builds the upstream URL, calls it with Spring's `RestClient`, and returns only the fields the screen needs:

[source,java]
----
@RestController
public class IsbnProxyController {
  private final RestClient catalogue;

  public IsbnProxyController(RestClient.Builder builder, @Value("${bookshelf.isbn-service}") String baseUrl) {
    this.catalogue = builder.baseUrl(baseUrl).build();
  }

  public record IsbnBook(String title, Integer number_of_pages) {
  }

  @GetMapping("/api/isbn/{isbn}")
  public IsbnBook lookup(@PathVariable @Pattern(regexp = "[0-9]{13}") String isbn) {
    try {
      return catalogue.get().uri("/isbn/{isbn}.json", isbn).retrieve().body(IsbnBook.class);
    } catch (HttpClientErrorException.NotFound e) {
      throw new ResponseStatusException(HttpStatus.NOT_FOUND, "Unknown ISBN");
    } catch (RestClientException e) {
      throw new ResponseStatusException(HttpStatus.BAD_GATEWAY, "Catalogue unavailable");
    }
  }
}
----

Source: https://docs.spring.io/spring-framework/reference/integration/rest-clients.html#rest-restclient[Spring Framework -- RestClient], https://docs.spring.io/spring-boot/reference/io/rest-client.html[Spring Boot -- Calling REST services]

[source,properties]
----
bookshelf.isbn-service=http://localhost:8944
spring.http.clients.connect-timeout=2s
spring.http.clients.read-timeout=3s
----

In the probe, `bookshelf.isbn-service` pointed at a local stand-in server on port 8944 that served one JSON file with extra fields (`publishers`, `key`), so the output is reproducible without depending on a public service.
In a real deployment the property holds the base URL of the actual API, and an API key, if there is one, comes from the environment or a secret store.
Four requests against the running application (the properties are the `+spring.http.clients.*+` ones of the Spring Boot REST client page):

[source,text]
----
GET /api/isbn/9780132350884   200  {"title":"Clean Code","number_of_pages":464}
GET /api/isbn/9780000000000   404  {"detail":"Unknown ISBN","instance":"/api/isbn/9780000000000","status":404,"title":"Not Found"}
GET /api/isbn/abc             400  {"detail":"Validation failure","instance":"/api/isbn/abc","status":400,"title":"Bad Request"}
(stand-in server stopped)
GET /api/isbn/9780132350884   502  {"detail":"Catalogue unavailable","instance":"/api/isbn/9780132350884","status":502,"title":"Bad Gateway"}
----

The read timeout was tested with a stand-in that waits six seconds before answering: the request returned the same `502` after 3.1 seconds, which is the `read-timeout` of 3s.

The rules that make a proxy safe:

.Rules for a server-side proxy
[cols="2,4",options="header"]
|===
| Rule | Why

| The client sends an identifier, never a URL
| A proxy that fetches whatever URL the browser sends is a server-side request forgery (SSRF) endpoint into your internal network. The controller above builds the URL from a fixed base and a validated ISBN

| Validate the identifier strictly
| The `@Pattern` accepts exactly thirteen digits; the `abc` request never reaches the upstream call

| Set connect and read timeouts
| A slow third party must not hold your request threads; the two properties above bound the call

| Return a DTO of your own, not the upstream body
| Upstream fields can change or contain data you do not want to pass on. The response above has two fields of the upstream's many

| Map upstream failures to 502 or 404
| The browser must not see upstream stack traces, headers or internal host names

| Authenticate and rate-limit the endpoint
| It spends your quota with the third party. Apply the same authentication and CSRF rules as the rest of the API

| Cache where the terms of the service allow it
| It saves quota and latency; keep the cache on the server
|===

The client side of the proxy is one more `pass:c[Rest.json("GET", "/api/isbn/" + isbn, null)]` with a native type for the two fields.
The xref:web/gwt/xsrf-rpc-and-server-security.adoc[XSRF, RPC & Server Security] page covers XSRF, the same-origin policy and JSON hijacking in more depth than this page.

== Security notes

.Security rules for REST clients in GWT
[cols="2,5",options="header"]
|===
| Risk | Rule

| Cross-site request forgery
| Send the XSRF token header on every state-changing call (POST, PUT, PATCH, DELETE), as in `Rest.send`, the `XsrfInterceptor` and the RestyGWT dispatcher above. GWT-RPC has its own token mechanism, described on the xref:web/gwt/xsrf-rpc-and-server-security.adoc[XSRF, RPC & Server Security] page. Keep `SameSite` on the session cookie

| Authorisation in the client
| All checks are on the server. The client code is public and can be edited in the developer tools

| Untrusted JSON in the DOM
| Put response text in the page with `setText`, `setInnerText` or `textContent`, never `setHTML` or `innerHTML` with concatenated data. For rich text use `SafeHtml` (see xref:web/gwt/safehtml-and-xss.adoc[SafeHtml & XSS])

| Unvalidated JSON shapes
| A native JsInterop type is a promise, not a check: a missing property is `undefined`. Validate fields before using them in URLs, DOM or logic

| Unsafe parsers
| Use `Response.json()`, `JSON.parse` or a mapper. Never `eval` a response, and avoid `JSONP` for anything that matters

| Entity leakage
| Serve DTOs; do not return JPA entities, which can expose columns, lazy relations and internal ids

| Secrets in the client
| API keys for third-party services stay on the server (proxy section); the compiled JavaScript is readable by every visitor

| Token in a URL
| Put tokens in headers, not in query strings that end up in logs and the `Referer` header

| Error details
| Return problem documents with a stable `detail` and no stack traces; log the details on the server

| Unbounded results
| Cap `length` on the server, as the controller does, and paginate
|===

== Pitfalls

.Common problems with REST and JSON libraries in GWT (messages reproduced on GWT 2.13.1 unless marked)
[cols="3,4,4",options="header"]
|===
| Symptom | Cause | Fix

| `+[ERROR] An internal compiler exception occurred+` with `+com.google.gwt.dev.jjs.InternalCompilerException: Unexpected error during visit.+` and `+Caused by: java.lang.NoClassDefFoundError: javax/xml/bind/annotation/XmlTransient+` at `GWT.create(BooksResource.class)`
| The RestyGWT 2.2.7 generator refers to JAXB, which JDK 11 and later no longer include
| Add `javax.xml.bind:jaxb-api:2.3.1` to the compile class path

| RestyGWT calls `/restydemo/api/books` and the server answers `+No static resource restydemo/api/books.+`
| The default service root is the module base URL, so a relative `@Path` is resolved inside the module directory
| `Defaults.setServiceRoot(GWT.getHostPageBaseURL())`, or absolute paths on a configured root

| `+FailedResponseException+` with an empty message in the callback
| The RestyGWT exception carries no text; the status is on the `Method`
| Read `method.getResponse().getStatusCode()` and `getText()`

| `+Line 5: No source code is available for type com.github.nmorel.gwtjackson.client.ObjectMapper<T>; did you forget to inherit a required module?+`
| The module file does not inherit `com.github.nmorel.gwtjackson.GwtJackson`
| Add the `<inherits>` line

| `+com.github.nmorel.gwtjackson.client.exception.JsonDeserializationException: Unknown property 'unknown'+`
| The default is to reject JSON properties the DTO lacks
| Add the property, or `@JsonIgnoreProperties(ignoreUnknown = true)` on the DTO

| AutoREST requests return 400 and the URL contains `+%2F+`
| A slash in `@Path("api/books")` is encoded as part of one path segment
| Keep `@Path` to one segment and put the prefix in the `RequestResourceBuilder` base URL

| `+Uncaught TypeError: Cannot read properties of null (reading '_')+` as soon as a domino-rest call is made (production build, obfuscated)
| `DominoRestConfig.initDefaults()` was never called, so the library has no configuration
| Call it once in `onModuleLoad`, before the first request

| `mvn dependency:build-classpath` lists `elemental2-dom` 1.1.0 and `elemental2-core` 1.2.3 although the other pages of this section use 1.3.2
| `domino-rest-client` 2.0.2 depends on those versions and Maven picks the nearest declaration
| Pin Elemental2 1.3.2 in `dependencyManagement`

| `+SyntaxError: Unexpected token '<', "<!doctype "... is not valid JSON+` (Chrome 155 wording)
| The URL returned the host page, not JSON: wrong path, or a fallback route
| Check the status and the `Content-Type` header before `Response.json()`

| `+TypeError: Failed to fetch+` and, in the console, `+... has been blocked by CORS policy: No 'Access-Control-Allow-Origin' header is present on the requested resource.+`
| The URL is on another origin (even `127.0.0.1` versus `localhost`) and the server sends no CORS headers
| Serve the API from the same origin, add a proxy, or configure CORS on the server (see the Spring CORS section); do not open CORS to every origin

| `+TimeoutError: signal timed out+`
| `AbortSignal.timeout` fired before the response arrived
| Raise the limit for slow endpoints, or show a retry action

| A write returns 401 although the user is signed in, or 403 with an empty body
| The CSRF header is missing or does not match the cookie: after a Spring `+Invalid CSRF token found for http://localhost:8934/api/books/4+` in the debug log
| Read the `XSRF-TOKEN` cookie, send it in `X-XSRF-TOKEN`, and perform a GET first so the cookie exists

| `+HTTP 400 Invalid request content.+` with no field names
| Spring Boot 4.1.1 does not add the violations to the default problem document
| Add an `@ExceptionHandler` that returns the field errors, or handle `MethodArgumentNotValidException`

| Spring Boot fails to start with `+Parameter 0 of constructor in com.example.bookshelf.api.IsbnProxyController required a bean of type 'org.springframework.web.client.RestClient$Builder' that could not be found.+`
| Spring Boot 4 does not auto-configure `RestClient.Builder` from the web starter alone
| Add `spring-boot-starter-restclient`

| Maven Central says the latest RestyGWT is 1.4
| `maven-metadata.xml` for the artifact was not updated after 2013; the directory has 2.0 to 2.2.7
| Pin the version you tested; read the directory listing, not the metadata

| A `long` id loses digits in the browser
| JSON numbers are doubles in JavaScript
| Send large ids as strings, or keep ids below 2^53
|===

== Where older material is outdated

* **JSON and the proxy in GWT in Action.** The book (2007, GWT 1.3 and 1.4) devotes its chapter 13 to JSON: the JSON format, the `JSONParser` and `JSONValue` classes, and a servlet that proxies a third-party search API for the page. The idea of a server-side proxy is unchanged and is the section above. What changed is everything around it: the server code there uses Apache Commons HttpClient, whose project page says it is end of life and was replaced by Apache HttpComponents; the third-party API it targets is not used here; and GWT now has `JsonUtils.safeEval`, `JSONParser.parseStrict`, JsInterop native types and Elemental2 `fetch`, so a hand-written parse of every value is rarely needed.
* **"A third party library".** The Developer Guide still says the application can use JSON with `RequestBuilder`, JSNI "or a third party library" and does not name any. JSNI is the legacy route (see xref:web/gwt/jsni-and-overlay-types.adoc[JSNI and overlay types]); native types replace it.
* **XSRF in the Developer Guide.** The guide's XSRF protection is built for GWT-RPC (`RpcToken`, `XsrfProtectedService`). For a REST API the mechanism is the one in your server framework (here Spring Security), and the client's job is to send the token header.
* **RestyGWT's own home page.** It still offers 2.2.0 as the latest download; the latest release on Maven Central is 2.2.7 (2020-05-17). The annotations are the `javax.ws.rs` ones (`javax.ws.rs-api` 2.0.1 and its sources on the class path), not the `jakarta.ws.rs` ones that `domino-rest` uses.
* **domino-jackson badge.** The README says release 1.0.0-RC3; Central has 1.0.6.

== What changed recently

* **2025-09-15.** Elemental2 1.3.2, the version used for the `fetch` probe, is the latest stable release; 1.4.0-RC1 followed on 2026-07-07.
* **2025-12-30.** `domino-rest` 2.0.0, after release candidates in 2024 (RC1 on 2024-01-14, RC2 on 2024-11-06). 2.0.1 followed on 2026-07-29 and 2.0.2 on 2026-09-24.
* **2026-07-27.** `domino-jackson` 1.0.6, following 1.0.5 on 2024-11-06.
* **2023-11-22 to 2023-11-24.** AutoREST 0.10 and 0.11, the first releases since 0.9 in 2018.
* **2026-06-19.** GWT 2.13.1, the compiler used here; Jakarta servlet artifacts (`gwt-servlet-jakarta`) were added in 2.11.0, which is how the Bookshelf server module serves RPC next to the REST API.
* **Spring Boot 4.** Uses Jackson 3 (`tools.jackson`, version 3.1.5 in the probe) for JSON, `RestClient` for the proxy call, and needs `spring-boot-starter-restclient` for the auto-configured `RestClient.Builder`. The annotations that Jackson 3 still reads come from the 2.x annotation artifact (2.21 in the probe).
