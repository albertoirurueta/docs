== Which API for which job

A GWT application can reach the browser through six different layers.
They are not alternatives that replace each other: a normal application uses widgets for the user interface, `com.google.gwt.dom.client` inside its own widgets, and Elemental2 for the Web APIs that GWT never wrapped.

.The DOM-facing APIs available in GWT 2.13.1

== com.google.gwt.dom.client: typed overlays

Every class in `com.google.gwt.dom.client` is a **JavaScript overlay type**: a Java class that extends `JavaScriptObject` and whose methods are final, mostly native, and compile to direct property accesses on the real browser object.
`Document`, `Node`, `Element`, `Style`, `NodeList`, `NativeEvent` and the element subclasses (`DivElement`, `SpanElement`, `InputElement`, `ButtonElement`, `TableElement` and so on) are therefore not wrappers: `card.getId()` becomes `card.id`, no object is allocated, and a `DivElement` and the HTML `div` it stands for are the same value.
The class layout follows the DOM interfaces:

* `Node` has the tree operations: `appendChild`, `insertBefore`, `insertFirst`, `removeChild`, `removeFromParent`, `replaceChild`, `cloneNode`, `getFirstChild`, `getParentElement`, `getChildCount`, `isOrHasChild`, `getOwnerDocument`
* `Element` adds identity and presentation: `getId`/`setId`, `getClassName`/`setClassName`, `addClassName`, `removeClassName`, `hasClassName`, `toggleClassName`, attributes (`getAttribute`, `setAttribute`, `hasAttribute`, `removeAttribute`), properties (`getPropertyString`, `setPropertyString`, `getPropertyInt` and friends), geometry (`getOffsetWidth`, `getClientHeight`, `getAbsoluteLeft`, `getScrollTop`), `getStyle`, `setInnerText`, `setInnerHTML`, `setInnerSafeHtml`, `focus`, `blur`, `scrollIntoView`, `dispatchEvent`
* `Document` is the factory and the entry point: `Document.get()`, `getBody`, `getHead`, `getElementById`, `getElementsByTagName`, `getTitle`, `getURL`, `getReferrer`, `createUniqueId`, `isCSS1Compat`, and one `createXxxElement()` method per HTML tag, plus `createClickEvent`, `createKeyDownEvent` and the other synthetic-event factories
* `Style` is the inline `style` attribute with typed setters, `Style.Unit` (`PX`, `EM`, `PCT` and the rest), the enums `Style.Display`, `Style.Cursor`, `Style.Float`, `Style.FontWeight` and others, and the escape hatch `setProperty(String, String)` for anything not enumerated

The example creates a card for a book, styles it and finds it again.
The title goes through `setInnerText`, so the `<script>` in the book title stays text.

[source,java]
----
Document doc = Document.get();

DivElement card = doc.createDivElement();
card.setId("book-42");
card.setClassName("card");
card.setAttribute("data-isbn", "978-0-00-000000-0");

SpanElement title = doc.createSpanElement();
title.setInnerText("Dune <script>alert(1)</script>");   // text, never markup
card.appendChild(title);

card.getStyle().setDisplay(Display.INLINE_BLOCK);
card.getStyle().setWidth(12, Unit.EM);
card.getStyle().setBackgroundColor("#ffee80");
card.getStyle().setProperty("borderLeft", "4px solid #3366cc");
doc.getBody().appendChild(card);

Element found = doc.getElementById("book-42");
DivElement div = DivElement.as(found);
NodeList<Element> spans = doc.getElementsByTagName("span");
JavaScriptObject raw = card;                    // every overlay is a JavaScriptObject
----

Source: https://www.gwtproject.org/javadoc/latest/com/google/gwt/dom/client/package-summary.html[Javadoc -- com.google.gwt.dom.client]

Points worth knowing before you write more:

* **Narrowing is explicit.** `Document.getElementById` returns `Element`. Use the static `as` of the specific class (`DivElement.as(found)`) when you know the tag, `Element.is(JavaScriptObject)` to test whether an object is an element at all, and `Element.as(JavaScriptObject)` or the generic `cast()` of `JavaScriptObject` to go from an event target to an element. Because overlay types carry no runtime type, a wrong `as` does not fail at once: it fails later, when you call a method the real object lacks.
* **`Style` is the inline style only.** `card.getStyle().getWidth()` returned `12em`, the inline value (the generated code assigns `12.0em`, which the browser normalises), not the computed pixel width (`getOffsetWidth()` returned 196). Computed styles are not part of `dom.client`; prefer CSS classes (`setStyleName`, `addClassName`) and the ClientBundle/GSS pages of this section for presentation, as the Developer Guide recommends.
* **Property names for `setProperty` are the camel-case DOM names** (`borderLeft`, not `border-left`); the string is assigned to `element.style[name]`.
* **Text and markup are different methods.** `setInnerText` escapes; `setInnerHTML` is annotated `@IsSafeHtml` and is meant to receive a constant or a `SafeHtml` value, and `setInnerSafeHtml(SafeHtml)` takes the type directly. Never concatenate user data into `setInnerHTML`; the SafeHtml and XSS page of this section covers the builders and sanitisers.
* **`getElement()` still returns the old `com.google.gwt.user.client.Element`**, a deprecated subclass of `dom.client.Element`. Assign it to a `com.google.gwt.dom.client.Element` variable and the deprecation never leaks into your code.

=== What dom.client deliberately lacks

The overlay model keeps the API small, and the gaps are the reason Elemental2 exists.
`dom.client` has no `addEventListener`, no `removeEventListener`, no `querySelector`/`querySelectorAll`, no `getElementsByClassName`, no `classList`, no `dataset`, no `fetch`.
The Javadoc of `EventTarget` states the first one openly: the class intentionally does not specify `dispatchEvent`, `addEventListener` and `removeEventListener`; events reach Java through `sinkEvents` and handlers instead (next section).
Calling a method that is not there fails at compile time with the usual message for a member that is missing from an overlay:

[source,text]
----
[ERROR] Line 10: The method addEventListener(String, null) is undefined for the type BodyElement
[ERROR] Line 11: The method querySelector(String) is undefined for the type BodyElement
----

== DOM and Event: the widget event machinery

The package `com.google.gwt.user.client` holds the older, event-oriented half of the DOM support: the static helper class `DOM`, the class `Event` (which extends `NativeEvent`), the interface `EventListener` and the `Window` helpers.
Two things in it are current and you will meet them in every custom widget: **sinking events** and **native preview**.
The rest of the static `DOM` API (`DOM.getInnerText`, `DOM.setAttribute`, `DOM.eventGetKeyCode`, `DOM.compare`; about fifty methods of the class carry the annotation) is `@Deprecated` in 2.13.1 in favour of the methods on `Element` and `NativeEvent`, and `DOM.addEventPreview`/`Event.addEventPreview` give way to `Event.addNativePreviewHandler`.

=== Sinking events and onBrowserEvent

A browser element only fires an event to GWT if the element is told to.
`sinkEvents(int bits)` on a `Widget` (or `DOM.sinkEvents(Element, int)` for a bare element) registers interest in the event types whose bits are or-ed together; `onBrowserEvent(Event)` is then called on the widget when one of them reaches it.
The bit constants live on `Event`; the values are the ones the 2.13.1 `DOMImplStandard` switches on:

.Event bits of com.google.gwt.user.client.Event (2.13.1)
[cols="2,1,2,1",options="header"]
|===
| Constant | Value | Constant | Value

| `ONCLICK` | `0x00001` | `ONFOCUS` | `0x00800`
| `ONDBLCLICK` | `0x00002` | `ONBLUR` | `0x01000`
| `ONMOUSEDOWN` | `0x00004` | `ONLOSECAPTURE` | `0x02000`
| `ONMOUSEUP` | `0x00008` | `ONSCROLL` | `0x04000`
| `ONMOUSEOVER` | `0x00010` | `ONLOAD` | `0x08000`
| `ONMOUSEOUT` | `0x00020` | `ONERROR` | `0x10000`
| `ONMOUSEMOVE` | `0x00040` | `ONMOUSEWHEEL` | `0x20000`
| `ONKEYDOWN` | `0x00080` | `ONCONTEXTMENU` | `0x40000`
| `ONKEYPRESS` | `0x00100` | `ONPASTE` | `0x80000`
| `ONKEYUP` | `0x00200` | `ONTOUCHSTART` to `ONTOUCHCANCEL` | `0x100000` to `0x800000`
| `ONCHANGE` | `0x00400` | `ONGESTURESTART` to `ONGESTUREEND` | `0x1000000` to `0x4000000`
|===

The group constants `FOCUSEVENTS`, `KEYEVENTS`, `MOUSEEVENTS`, `TOUCHEVENTS` and `GESTUREEVENTS` combine the related bits.
`Event.UNDEFINED` is deprecated.
For events that have no bit (for example `dragstart`, `input`, `transitionend`) the widget layer uses `sinkBitlessEvent(String)`, which the `addDomHandler` mechanism calls for you.

Sinking is lazy for widgets: until a `Widget` is attached, `sinkEvents` only records the bits (`eventsToSink`), and `onAttach` applies them.
That detail matters for the lifecycle section below.

The following widget is built directly on a DOM element, counts clicks and still lets ordinary handlers be added to it:

[source,java]
----
static class ClickCounter extends Widget {
  private int clicks;

  ClickCounter() {
    setElement(Document.get().createDivElement());
    getElement().setId("counter");
    sinkEvents(Event.ONCLICK);
    render();
  }

  @Override
  public void onBrowserEvent(Event event) {
    switch (event.getTypeInt()) {
      case Event.ONCLICK:
        clicks++;
        render();
        Element target = Element.as(event.getEventTarget());
        Log.log("onBrowserEvent: click on <" + target.getTagName().toLowerCase() + ">, clicks=" + clicks);
        break;
      default:
        break;
    }
    super.onBrowserEvent(event);   // lets registered handlers (addDomHandler) run
  }

  private void render() {
    getElement().setInnerText("clicks: " + clicks);
  }
}
----

Source: https://www.gwtproject.org/javadoc/latest/com/google/gwt/user/client/ui/Widget.html[Javadoc -- Widget]

The caller adds an ordinary `ClickHandler`, a native preview handler and then dispatches a synthetic click built with `Document.createClickEvent`, which is also how GWT's own tests drive widgets:

[source,java]
----
ClickCounter counter = new ClickCounter();
counter.addDomHandler(new ClickHandler() {
  @Override public void onClick(ClickEvent e) {
    Log.log("ClickHandler    : client(" + e.getClientX() + "," + e.getClientY() + ")");
  }
}, ClickEvent.getType());

HandlerRegistration preview = Event.addNativePreviewHandler(p -> {
  NativeEvent ne = p.getNativeEvent();
  if ("click".equals(ne.getType())) {
    Log.log("native preview : " + ne.getType() + " firstHandler=" + p.isFirstHandler());
  }
});

RootPanel.get().add(counter);
NativeEvent click = Document.get().createClickEvent(1, 0, 0, 12, 34, false, false, false, false);
counter.getElement().dispatchEvent(click);
Log.log("text after click: " + counter.getElement().getInnerText());
preview.removeHandler();
RootPanel.get().remove(counter);
----

Source: https://www.gwtproject.org/doc/latest/DevGuideUiHandlers.html[GWT Developer Guide -- Events and Handlers]

[source,text]
----
native preview : click firstHandler=true
onBrowserEvent: click on <div>, clicks=1
ClickHandler    : client(12,34)
text after click: clicks: 1
----

The order is the design: the native preview handlers see the event **first**, then the widget's `onBrowserEvent`, and `Widget.onBrowserEvent` finally calls `DomEvent.fireNativeEvent`, which runs the handlers registered with `addDomHandler` (and therefore every `addClickHandler`).
Forgetting `super.onBrowserEvent(event)` in an override silently disables all of those handlers; this is the most common mistake in a hand-written widget.
The xref:web/gwt/events-and-handlers.adoc[Events & Handlers] page covers the handler types, `HandlerManager` and event buses in detail.
Suppressing the browser's default action is done on the native event: `NativeEvent.preventDefault()` stops the default action (a link navigation, a form submit) and `NativeEvent.stopPropagation()` stops the event bubbling to ancestors; the handler types pass the `NativeEvent` through `DomEvent.preventDefault()` and `DomEvent.stopPropagation()`.

=== Native preview

`Event.addNativePreviewHandler(Event.NativePreviewHandler)` registers a **global** handler for every native event that GWT sinks, before it is delivered to its widget.
It returns a `HandlerRegistration`.
Inside, `NativePreviewEvent.cancel()` cancels the native event so that it is not delivered, `consume()` marks it as handled and prevents any handler from cancelling it (even one that already called `cancel()`), and `isFirstHandler()` tells whether the current handler is the first to preview this event.
The Developer Guide's keyboard-shortcut example uses exactly this API:

[source,java]
----
Event.addNativePreviewHandler(new NativePreviewHandler() {
  public void onPreviewNativeEvent(NativePreviewEvent preview) {
    NativeEvent event = preview.getNativeEvent();
    Element elt = event.getEventTarget().cast();
    int keycode = event.getKeyCode();
    if (event.getCtrlKey() || event.getAltKey() || !isInterestingKeycode(keycode)) {
      return;                      // let the event continue
    }
    handleKeycode(keycode);
    preview.consume();             // mark the event as handled
  }
});
----

Source: https://www.gwtproject.org/doc/latest/DevGuideUiDom.html[GWT Developer Guide -- Using the DOM]

A preview handler lives until it is removed, whatever happens to the widget that created it.
This is the main source of leaks in real GWT applications and is the subject of the lifecycle section further down.

The other two examples of the Developer Guide page (changing a widget's background colour through `getElement().getStyle()`, and finding anchor tags with a JSNI helper) map to today's API like this:

| `htmlWidget.getElement().getStyle().setBackgroundColor("#ffee80")`

== Browser differences

The Developer Guide's "Cross-Browser Support" page promises that a GWT application built from the built-in widgets works the same on the major browsers, that GWT's `Button` is a real `<button>`, and that styling should be done in style sheets rather than through the API.
Its list of browsers (Internet Explorer, Firefox, Chrome, Safari, Opera) and the JSNI `navigator.userAgent` tip are older than the compiler: the 2.13.1 module `com.google.gwt.useragent.UserAgent` defines exactly **two** values of the `user.agent` property.

[source,xml]
----
<define-property name="user.agent" values="gecko1_8" />
<extend-property name="user.agent" values="safari" />
<property-provider name="user.agent" generator="com.google.gwt.useragent.rebind.UserAgentPropertyGenerator"/>
----

Source: https://github.com/gwtproject/gwt/blob/2.13.1/user/src/com/google/gwt/useragent/UserAgent.gwt.xml[GWT 2.13.1 -- UserAgent.gwt.xml]

The property provider is a few lines of JavaScript that tests the lower-cased `navigator.userAgent`: it answers `safari` if the string contains `webkit`, `gecko1_8` if it contains `gecko`, and the check for `safari` comes first.
Chrome, Edge and every other Chromium browser put both `AppleWebKit` and `like Gecko` in their user-agent string, so they select the **safari** permutation; Firefox (Gecko without WebKit) selects **gecko1_8**.
The compiler therefore produces two permutations per locale, which is why the Bookshelf (three locale values of its own module) compiled six, and the one-locale probe module two:

      Compiling permutation 1...

----

What the permutation selects is the **implementation of the low-level DOM operations**.
The module `com.google.gwt.dom.DOM` replaces the abstract class `com.google.gwt.dom.client.DOMImpl` by `DOMImplWebkit` for `safari` and by `DOMImplMozilla` for `gecko1_8`, and `com.google.gwt.user.DOM` does the same for the event system with `com.google.gwt.user.client.impl.DOMImpl`:

[source,xml]
----
<replace-with class="com.google.gwt.dom.client.DOMImplWebkit">
  <when-type-is class="com.google.gwt.dom.client.DOMImpl"/>
  <when-property-is name="user.agent" value="safari"/>
</replace-with>

<replace-with class="com.google.gwt.dom.client.DOMImplMozilla">
  <when-type-is class="com.google.gwt.dom.client.DOMImpl"/>
  <when-property-is name="user.agent" value="gecko1_8"/>
</replace-with>
----

Source: https://github.com/gwtproject/gwt/blob/2.13.1/user/src/com/google/gwt/dom/DOM.gwt.xml[GWT 2.13.1 -- dom/DOM.gwt.xml]

The differences these classes still absorb are small and visible in the source: WebKit events sometimes target the text node inside an element, so `DOMImplWebkit.eventGetTarget` walks to the parent; WebKit needs the `webkitUserDrag` style to make an element draggable; the Gecko class works around a `relatedTarget` bug and carries version checks from Firefox 3 and 4.
The deferred-binding mechanism behind this (the `GWT.create` call, `<replace-with>` and `<when-property-is>`) has its own page, xref:web/gwt/deferred-binding-and-generators.adoc[Deferred Binding & Generators], and the xref:web/gwt/compiler-and-compilation.adoc#_what_permutations_cost[Compiler & Compilation] page explains how the number of permutations is controlled.

What GWT does **not** hide, and what remains your job:

* **CSS and layout.** Differences in default styles, flexbox/grid support and font metrics are browser behaviour. `Document.isCSS1Compat()` reports standards versus quirks mode (`getCompatMode()` is `"CSS1Compat"` in standards mode); always give the host page a doctype.
* **Web APIs that are absent or partial.** `dom.client` wraps the 2000s-era DOM. Anything newer (`fetch`, `WebSocket`, `IntersectionObserver`, `ResizeObserver`) is a global that must exist in the user's browser. Use feature detection (`Js.isTruthy` on a global, or a `try` around the call) rather than the user-agent string.
* **The `webApiUsage` property.** `stable` or `modern` (default `modern`): with `modern` some widgets may use new, not yet standardised APIs. Choose `stable` if redeploying whenever a browser changes would be a problem. The property and the `user.agent.runtimeWarning` configuration property are defined in the same module as above.
* **Mismatch warnings.** The module comment describes `user.agent.runtimeWarning` as the switch for warnings about a compile-time `user.agent` that differs from the runtime one; it is `true` by default. This happens when a proxy serves one browser's file to another, or when `-setProperty user.agent=gecko1_8` is used for a fast development compile and the page is then opened in Chrome.

For a browser-specific dependency the Developer Guide shows a JSNI `navigator.userAgent` method; the same value is a field in Elemental2 (`DomGlobal.navigator.userAgent`), as the log above shows.

== Elemental2

Elemental2 gives Java code type-checked access to the browser's API.
Its README explains the method: the types are generated from the externs files of the Closure Compiler and are **native JsInterop types** (`@JsType(isNative = true, namespace = JsPackage.GLOBAL)`), part of the JsInterop specification that GWT 2 and J2CL both implement.
A native type has no Java implementation and no JavaScript glue; the compiler emits direct accesses on the browser's own objects (the next subsection shows the output).
Elemental2 requires GWT 2.9 or later (since its 1.0.0), and the same dependencies work on J2CL, which makes it the portable choice for new code.

document_0.body.appendChild(box);
----

Member names of native types are never renamed, so the output is the JavaScript a person would write.
A Java cast to a native class is not free of checks: it becomes `castToNative(value, $wnd.HTMLDivElement)`, a check against the browser's own constructor.

=== Elemental2 next to dom.client

Both families describe the same browser objects, so a value can be moved between them without a conversion: use `Js.cast` (from `jsinterop-base`) to treat a GWT overlay as an Elemental2 type, and `Js.uncheckedCast` to go back.
This is the practical way to get `classList` and `querySelector` on an element that a GWT widget owns:

[source,java]
----
com.google.gwt.dom.client.DivElement gwtDiv = Document.get().createDivElement();
gwtDiv.setInnerHTML("<p class=\"lead\">Hello</p>");           // constant markup only
HTMLElement el = Js.cast(gwtDiv);                         // GWT overlay -> Elemental2
el.classList.add("highlight");
Log.log("e2 bridge     : " + el.querySelector("p.lead").textContent + " / " + gwtDiv.getClassName());
com.google.gwt.dom.client.Element back = Js.uncheckedCast(el);   // Elemental2 -> GWT overlay
Log.log("e2 bridge     : back to GWT overlay, same object = " + (back == gwtDiv));
----

Source: https://github.com/google/jsinterop-base[jsinterop-base -- Js and JsPropertyMap]

[source,text]
----
e2 bridge     : Hello / highlight
e2 bridge     : back to GWT overlay, same object = true
----

The two libraries use the same simple names (`Element`, `Event`, `Document`, `Window`, `Node`, `Storage`), so a class that imports both must fully qualify one of them, as the bridge example does.
Prefer to import the Elemental2 names in classes that use Elemental2 and keep GWT's `Event` out of them; the compiler error for a clash is an ordinary Java "already defined" or "cannot be resolved" message.

=== DOM and events with Elemental2

Creating elements and listening to events with Elemental2 looks like the JavaScript it replaces, with Java types:

[source,java]
----
HTMLDivElement box = (HTMLDivElement) DomGlobal.document.createElement("div");
box.id = "box";
box.className = "panel";
box.textContent = "Add a book";

input.type = "text";
input.placeholder = "Title";

box.appendChild(button);
DomGlobal.document.body.appendChild(box);

  HTMLElement target = Js.cast(e.target);
  Log.log("e2 click       : type=" + e.type + " target=" + target.tagName);
};
button.addEventListener("click", onClick);
button.click();
button.removeEventListener("click", onClick);
button.click();                       // nothing is logged: the listener is gone
----

Source: https://developer.mozilla.org/en-US/docs/Web/API/EventTarget/addEventListener[MDN -- EventTarget.addEventListener]

[source,text]
----
e2 outerHTML  : <div id="box" class="panel">Add a book<input type="text" placeholder="Title"><button>Add</button></div>
e2 click       : type=click target=BUTTON
e2 keydown     : Enter
e2 query      : 2 children via querySelectorAll
----

Things to notice:

* **`createElement` returns `HTMLElement`**; cast it to the specific class (`HTMLDivElement`, `HTMLInputElement`, `HTMLButtonElement`) to reach `type`, `placeholder`, `value`. A cast to a specific class is checked against the browser's constructor (see the compiler output above), so a wrong cast fails at once.
* **Event targets are typed loosely.** `e.target` is an `EventTarget`; convert with `Js.cast`. Event subtypes (`KeyboardEvent`, `MouseEvent`) are obtained the same way, and constructors exist for synthetic events: `new KeyboardEvent("keydown", init)` with `KeyboardEventInit.create()` and `init.setKey("Enter")` produced the third log line.
* **Removal needs the same instance.** `removeEventListener` compares the listener object, so a second, identical-looking lambda removes nothing. The probe shows it:

[source,java]
----
int[] hits = {0};
button.addEventListener("click", e -> hits[0]++);
button.removeEventListener("click", e -> hits[0]++);   // a different lambda instance: removes nothing
button.click();
EventListener same = e -> hits[0] += 10;
button.addEventListener("click", same);
button.removeEventListener("click", same);
button.click();
----

Source: https://developer.mozilla.org/en-US/docs/Web/API/EventTarget/removeEventListener#matching_event_listeners_for_removal[MDN -- EventTarget.removeEventListener: matching event listeners for removal]

[source,text]
----
e2 identity   : hits after remove with a new lambda = 1
e2 identity   : hits after removing the same instance = 2
----

Keep the `EventListener` in a field (as `onClick` above) whenever you intend to remove it.

* **`innerHTML` is a plain `String` field.** Elemental2 has no `SafeHtml` type, so `element.innerHTML = userText` is a DOM-based XSS hole. Assign `textContent` for text, or build markup with GWT's `SafeHtml` builders (see xref:web/gwt/safehtml-and-xss.adoc[SafeHtml & XSS]) and pass the `asString()` of a `SafeHtml` only.

=== fetch and Promise

`+DomGlobal.fetch(...)+` returns an Elemental2 `Promise<Response>`.
`Promise` has `then`, `catch_` and `finally_` (the underscore avoids the Java keywords), and the static `resolve`, `reject`, `all` and `race`.
There is no `await` in Java, so asynchronous steps are chained.
The Bookshelf REST endpoint of the server module is read like this; the first `then` converts an HTTP error into a rejection, the second parses the text with `JSON.parse` and walks the array through two small native types:

[source,java]
----
@JsType(isNative = true, namespace = JsPackage.GLOBAL, name = "Object")
final class BookJson {
  public double id;
  public String title;
  public String author;
  public int year;
  public int copies;
}

@JsType(isNative = true, namespace = JsPackage.GLOBAL, name = "Object")
final class BookPageJson {
  public int total;
  public JsArray<BookJson> books;
}

static Promise<Void> fetchBooks() {
  return DomGlobal.fetch("/api/books?start=0&length=3")
      .then(res -> {
        if (!res.ok) {
          return Promise.reject("HTTP " + res.status + " " + res.statusText);
        }
        Log.log("e2 fetch      : " + res.status + " " + res.headers.get("content-type"));
        return res.text();
      })
      .then(text -> {
        BookPageJson page = Js.uncheckedCast(Global.JSON.parse(text));
        for (int i = 0; i < page.books.length; i++) {
          BookJson b = page.books.getAt(i);
          Log.log("e2 book       : #" + (int) b.id + " " + b.title + " (" + b.year + ")");
        }
        return null;
      });
}
----

Source: https://developer.mozilla.org/en-US/docs/Web/API/Window/fetch[MDN -- fetch()]

[source,text]
----
e2 fetch      : 200 application/json;charset=utf-8
e2 book       : #1 The Pragmatic Programmer (1999)
e2 book       : #2 Effective Java (2001)
e2 book       : #3 Clean Code (2008)
----

The native types need no runtime support: `name = "Object"` says "treat this as a plain JavaScript object", the public fields are property accesses, and `Js.uncheckedCast` only tells the compiler the type.
The cast is **not validated**, so a response with a missing field yields `undefined` in Java; check untrusted data field by field before using it.

Two failure modes behave differently and both appear in the next listing.
A response with an error status (the servlet answers a POST with 405) **resolves** the promise with `res.ok == false`; only a network failure (connection refused, DNS, blocked by CORS) **rejects** it:

[source,java]
----
static Promise<Void> fetchFailures() {
  RequestInit init = RequestInit.create();
  init.setMethod("POST");
  JsPropertyMap<String> headers = JsPropertyMap.of();
  headers.set("Content-Type", "application/json");
  init.setHeaders(headers);
  init.setBody("{\"title\":\"Dune\"}");
  return DomGlobal.fetch("/api/books", init)
      .then(res -> {
        Log.log("e2 POST       : ok=" + res.ok + " status=" + res.status);
        return DomGlobal.fetch("http://127.0.0.1:9/never");
      })
      .then(res -> null, err -> {
        Log.log("e2 network err: " + err);
        return null;
      });
}
----

[source,text]
----
e2 POST       : ok=false status=405
e2 network err: TypeError: Failed to fetch
----

Source: https://fetch.spec.whatwg.org/[WHATWG Fetch Standard]

Rules that keep `fetch` code safe and predictable:

* Check `res.ok` (or `res.status`) before using the body; do not assume a resolved promise means success.
* End a chain with `catch_` so that a rejection reaches your code instead of the browser console as an unhandled rejection.
* `credentials` defaults to `same-origin`, so session cookies are sent to the page's own origin. For a state-changing request (POST, PUT, DELETE) send the XSRF token your server issued, as a header, exactly as xref:web/gwt/xsrf-rpc-and-server-security.adoc[XSRF, RPC & Server Security] and xref:web/gwt/rest-and-json-libraries.adoc[REST & JSON Libraries] describe; authorisation is checked on the server, never in the client.
* Use relative URLs or build them from `GWT.getModuleBaseURL()`; cross-origin requests need CORS headers from the other server.
* `fetch` can be cancelled with an `AbortController` (`elemental2.dom.AbortController`, passed through `RequestInit.setSignal`).

=== Promise.all and typed arrays

`Promise.all` combines several promises. Its Java signature is `+static <V> Promise<V[]> all(IThenable<? extends V>... promises)+`, and the array in the result is a **JavaScript array**.
Instantiated with `V` = `String`, GWT inserts a cast to `String[]` in the lambda and the call fails at run time; with `V` = `Object` it works and each element is converted with `Js.cast`:

[source,java]
----
static Promise<String> pageText(int start) {
  return DomGlobal.fetch("/api/books?start=" + start + "&length=1").then(Response::text);
}

static Promise<Void> bothPages() {
  return Promise.<Object>all(pageText(0), pageText(1)).then(results -> {
    String first = Js.cast(results[0]);
    Log.log("e2 Promise.all: " + results.length + " responses, first starts with " + first.substring(0, 24));
    return null;
  });
}

static Promise<Void> typedAll() {
  return Promise.all(pageText(0), pageText(1)).then(texts -> {
    Log.log("e2 typed all  : " + texts.length);
    return null;
  }).catch_(err -> {
    Log.log("e2 typed all  : failed with " + err);
    return null;
  });
}
----

Source: https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Promise[MDN -- Promise]

=== WebSocket

`WebSocket` is a native class with callback fields (`onopen`, `onmessage`, `onclose`, `onerror`) typed as `@JsFunction` interfaces, so lambdas work:

[source,java]
----
static void webSocket(String url) {
  WebSocket ws = new WebSocket(url);
  ws.onopen = e -> {
    Log.log("e2 ws open    : readyState=" + ws.readyState);
    ws.send("{\"type\":\"ping\"}");
  };
  ws.onmessage = e -> {
    Log.log("e2 ws message : " + e.data.asString());
    ws.close();
  };
  ws.onclose = e -> Log.log("e2 ws close   : code=" + e.code + " clean=" + e.wasClean);
  ws.onerror = e -> Log.log("e2 ws error   : " + e.type);
}
----

Source: https://developer.mozilla.org/en-US/docs/Web/API/WebSocket[MDN -- WebSocket]

The Bookshelf server has no WebSocket endpoint; the probe connected to a small echo server on the same origin as the host page:

[source,text]
----
e2 ws open    : readyState=1
e2 ws message : echo: {"type":"ping"}
----

(The `close` callback reported code 1006 because that throwaway echo server closed the TCP connection without a complete closing handshake; a real server answers with 1000.)
`e.data` is a union type, so `asString()` is checked with `isString()` first when binary frames are possible.
Security rules for WebSockets are the same as for any endpoint: use `wss://` on an HTTPS page (a secure page may not open an insecure WebSocket), authenticate and authorise on the server for every message, and verify the `Origin` header during the handshake so that another site cannot open an authenticated socket in the user's browser.

== Elemental (1): deprecated

The first Elemental was announced in the article "Introducing Elemental" (Ray Cromwell, updated June 2012).
It generated Java from the WebKit IDL files, covered DOM, WebGL, WebAudio, WebSockets and more, included its own collections and JSON library, and was built purely from overlay types for speed.
The article is honest about its limits, which are the reasons it was replaced: the generated code had no unit tests, it was generated from WebKit IDL and so contained vendor-prefixed extensions, and its native collections were not interoperable with Java collections.

== Memory leaks and handler lifecycles

The Developer Guide-era article "DOM Events, Memory Leaks, and You" (Joel Webber, updated January 2009) explains why GWT widgets cannot attach listeners to arbitrary elements and use bit fields for events.
It opens with a note that, with the death of Internet Explorer, the information is obsolete, though it still explains the event handling mechanism of the `Widget` class.
Both statements are right, and the second is worth checking against the 2.13.1 source.

=== What the article describes and what the code does today

The leak in question is a **reference cycle between a JavaScript object and a native DOM element**: `widget` to `element` to a closure that points back to `widget`.
Old Internet Explorer's garbage collectors could not free such cycles, and the common workaround (walking the DOM at `window.onunload`) missed detached elements and long-running applications.
GWT's rule was therefore: a widget must not be in a cycle with a native element while it is detached.
Each widget has one root element; when the widget is attached, exactly one back reference from the element to the widget is created and, when it is detached, removed.

The code of 2.13.1 still follows this design.
`DOMImpl.setEventListener` stores the listener in an expando property named `+__listener+` on the element, `Widget.onAttach` calls it with the widget, and `Widget.onDetach` calls it with `null` inside a `finally` block.
`sinkEvents` assigns one shared dispatcher function to the element (`elem.onclick = dispatchEvent`, and likewise for the other events) instead of a closure per widget, which is why the article says you have to sink events with bits.
The dispatcher walks up from the event target to the first ancestor that has a `+__listener+`, so an event on a child element is delivered to the nearest widget root.
The probe checks the expando through `jsinterop-base`:

[source,java]
----
static Object listenerOf(Widget w) {
  return Js.asPropertyMap(w.getElement()).get("__listener");
}
----

[source,text]
----
before attach : __listener on tidy element = false
after attach  : __listener on tidy element = true
after detach  : __listener on tidy element = false
----

Source: https://github.com/gwtproject/gwt/blob/2.13.1/user/src/com/google/gwt/user/client/impl/DOMImpl.java[GWT 2.13.1 -- DOMImpl.java]

[mermaid]
....
sequenceDiagram
  participant P as Panel or RootPanel
  participant W as Widget
  participant E as Root element
  participant G as Global registrations

  W->>E: onAttach: set listener expando, sink events
  W->>W: onLoad, then AttachEvent(true)
  Note over G: you register here: native preview, Window, Elemental2, Timer, event bus
  P->>W: remove(widget)
  W->>W: onUnload, then AttachEvent(false)
  W->>E: onDetach: clear listener expando
  Note over G: you must unregister here
....

The consequence the article states, and the code confirms, is a design limit: a widget cannot hang listeners on elements **inside** itself. It receives the event and works out which child it came from, with `Element.as(event.getEventTarget())` and the DOM tree (`getParentElement`, `isOrHasChild`), exactly as `ClickCounter.onBrowserEvent` did above.
Cell widgets rely on the same delegation: they receive the event at their root element and work out which cell it belongs to.

What the old guarantee does **not** cover is everything that is **not** the widget's own root-element listener.
Those registrations are held by long-lived objects (the `window`, the event preview stack, a static event bus, a running timer) which keep your widget reachable through the handler's closure. A modern engine's collector handles cycles, so this is no longer a cycle problem; it is a **lifetime** problem: the widget is removed from the page but can never be collected, and its handler keeps running.

=== The attach and detach lifecycle

`Widget` exposes the lifecycle through four methods and one event, called in a fixed order:

.The widget lifecycle in GWT 2.13.1
[cols="2,5",options="header"]
|===
| Step | What happens

| `onAttach()`
| sets the attached flag, installs the `+__listener+` expando, applies the pending `sinkEvents` bits, calls `doAttachChildren()`, then `onLoad()`, then fires `AttachEvent` with `isAttached() == true`. Override `onLoad`, not `onAttach`

| `onLoad()`
| the widget and its children are fully attached; the right place to register global handlers, start timers and add Elemental2 listeners

| `onUnload()`
| called first when detaching, while everything is still attached; the right place to undo what `onLoad` did

| `onDetach()`
| calls `onUnload()`, fires `AttachEvent` with `isAttached() == false`, detaches children, clears the expando and the attached flag (the last two in `finally` blocks, so an exception in your `onUnload` does not leave the widget half-attached)
|===

`addAttachHandler(Handler)` is the non-subclassing form: it receives an `AttachEvent` on both transitions.
Subclasses that override `onAttach` or `onDetach` must call `super`; with assertions enabled GWT checks it when the parent attaches or detaches the child (the assertion message starts with "Failure of"), and a missing `super.onDetach()` leaves the expando in place, which is the leak the Javadoc of `onDetach` warns about.
Calling the methods in the wrong state throws:

* `+Should only call onAttach when the widget is detached from the browser's document+`
* `+Should only call onDetach when the widget is attached to the browser's document+`
* `Cannot set a new parent without first clearing the old parent`, when a widget that already has a parent is added to a second panel

The `Composite` and `Panel` classes manage the lifecycle of their children, and `Widget.removeFromParent()` is the call that detaches a widget.
The older safety net, `RootPanel.detachOnWindowClose(Widget)` (a list of widgets to detach when the page unloads), is `@Deprecated` in 2.13.1: its Javadoc says it was introduced to combat memory leaks in old browsers, that it is no longer necessary, that the `unload` event it relies on is being removed from browsers and that it is unreliable for guaranteeing `onUnload()` calls (issue 9908).
So is `Window.addCloseHandler`, for the same reason; the 2.12.0 release notes record that `unload`-based calls were deprecated.

=== Registrations that outlive the widget

The probe module creates two widgets for each kind of global handler: a **leaky** one that registers in its constructor and never unregisters, and a **tidy** one that registers in `onLoad` and unregisters in `onUnload`.
First the GWT native preview handler:

[source,java]
----
/** Registers a global handler in the constructor and never removes it. */
static class LeakyBadge extends Widget {
  LeakyBadge() {
    setElement(Document.get().createDivElement());
    Event.addNativePreviewHandler(p -> leakyHits++);
  }
}

/** Registers in onLoad and removes in onUnload, so the registration follows the attach state. */
static class TidyBadge extends Widget {
  private HandlerRegistration preview;

  TidyBadge() {
    setElement(Document.get().createDivElement());
  }

  @Override
  protected void onLoad() {
    preview = Event.addNativePreviewHandler(p -> tidyHits++);
  }

  @Override
  protected void onUnload() {
    if (preview != null) {
      preview.removeHandler();
      preview = null;
    }
  }
}
----

Then an Elemental2 listener on the `window`, with the same two shapes (the tidy one keeps its `EventListener` in a field so the same instance is removed):

[source,java]
----
static class ResizeAware extends Widget {
  private final boolean tidy;
  private final EventListener listener;

  ResizeAware(boolean tidy) {
    this.tidy = tidy;
    setElement(Document.get().createDivElement());
    listener = e -> { if (tidy) { tidyResize++; } else { leakyResize++; } };
    if (!tidy) {
      DomGlobal.window.addEventListener("resize", listener);   // never removed
    }
  }

  @Override
  protected void onLoad() {
    if (tidy) {
      DomGlobal.window.addEventListener("resize", listener);
    }
  }

  @Override
  protected void onUnload() {
    if (tidy) {
      DomGlobal.window.removeEventListener("resize", listener);
    }
  }
}
----

The driver attaches both widgets, dispatches one event, detaches both, dispatches two more events and prints the counters, first for a click (picked up by the native preview handlers) and then for a window `resize`:

[source,text]
----
attach event    : leaky attached=true
attach event    : tidy attached=true
click 1 (both attached): leaky=1 tidy=1
attach event    : leaky attached=false
attach event    : tidy attached=false
click 3 (both removed) : leaky=3 tidy=1
resize 1 (attached)    : leaky=1 tidy=1
resize 3 (removed)     : leaky=3 tidy=1
----

Source: https://www.gwtproject.org/javadoc/latest/com/google/gwt/user/client/Event.html[Javadoc -- Event.addNativePreviewHandler]

After the widgets were removed from the page, the leaky handlers still ran for every later event (3 in total against 1), and each of them keeps its widget and the widget's element tree alive.
That is the whole story of a GWT memory leak in 2026, and the same pattern applies to every long-lived source:

.What to register in onLoad and unregister in onUnload
[cols="3,4",options="header"]
|===
| Registration | How to undo it

| `Event.addNativePreviewHandler`
| keep the returned `HandlerRegistration`, call `removeHandler()`

| `Window.addResizeHandler`, `Window.addWindowScrollHandler`
| keep the `HandlerRegistration`, call `removeHandler()`

| handlers added to a static or application-wide event bus
| keep each `HandlerRegistration`, or register through a `ResettableEventBus` and call `removeHandlers()` once

| Elemental2 `addEventListener` on `window`, `document` or another long-lived element
| keep the `EventListener` instance and call `removeEventListener` with it

| `Timer` with `scheduleRepeating`, or a `RepeatingCommand` given to the `Scheduler`
| call `cancel()` on the timer; a `RepeatingCommand` stops when it returns `false` (see xref:web/gwt/delayed-logic-and-scheduler.adoc[Delayed Logic & Scheduler])

| `WebSocket`, `EventSource`, `IntersectionObserver`, `ResizeObserver`
| `close()` or `disconnect()`

| pending `fetch` whose callback touches the widget
| pass an `AbortSignal`, or check `isAttached()` in the callback before using the widget
|===

Handlers added with `+widget.addClickHandler(...)+` or `addDomHandler` are different: they are stored in the widget's own `HandlerManager`, so they live and die with the widget and need no cleanup.
`ResettableEventBus` is the right tool when a presenter registers many handlers on a shared bus; the probe registers one handler, fires two events, calls `removeHandlers()` after the first, and the second event finds nothing:

[source,java]
----
EventBus app = new SimpleEventBus();
ResettableEventBus scoped = new ResettableEventBus(app);
int[] seen = {0};
scoped.addHandler(PingEvent.TYPE, e -> seen[0]++);
app.fireEvent(new PingEvent());
scoped.removeHandlers();
app.fireEvent(new PingEvent());
Log.log("ResettableEventBus: handled " + seen[0] + " of 2 pings");
----

[source,text]
----
ResettableEventBus: handled 1 of 2 pings
----

Source: https://www.gwtproject.org/javadoc/latest/com/google/web/bindery/event/shared/ResettableEventBus.html[Javadoc -- ResettableEventBus]

The xref:web/gwt/mvp-activities-and-places.adoc[MVP, Activities & Places] page applies the same idea: an `Activity` gets an `EventBus` that is reset when the activity stops, so handlers registered through it disappear with the screen.

== Security notes

.Security rules for DOM and Elemental2 code
[cols="3,4",options="header"]
|===
| Risk | Rule

| DOM-based XSS through `innerHTML`, `setInnerHTML`, `outerHTML`
| user and server data goes through `setInnerText` or `textContent`; markup comes from constants or `SafeHtml` builders. Elemental2's `innerHTML` is an unchecked `String`

| Unvalidated JSON
| `Js.uncheckedCast` does not check shapes. Validate types and ranges before use; do not feed parsed values into `innerHTML`, URLs or `eval`

| Unsafe parsers
| use `Global.JSON.parse` or `JSONParser.parseStrict`; never `JSONParser.parse`, `parseLenient` or `JsonUtils.unsafeEval` on data from a network

| State-changing `fetch` calls
| send the XSRF token header; enforce authorisation on the server; never rely on the client hiding a button

| WebSocket
| `wss://` only, check `Origin` during the handshake, authorise every message on the server

| Web storage
| any script of the origin can read it; no tokens, passwords or personal data

| Cross-origin requests
| the server decides with CORS headers; the client cannot grant itself access
|===

Source: https://cheatsheetseries.owasp.org/cheatsheets/DOM_based_XSS_Prevention_Cheat_Sheet.html[OWASP -- DOM based XSS Prevention Cheat Sheet]

The xref:web/gwt/safehtml-and-xss.adoc[SafeHtml & XSS] and xref:web/gwt/xsrf-rpc-and-server-security.adoc[XSRF, RPC & Server Security] pages show the escaping and token machinery in full.

== Pitfalls

.Common problems with the DOM, events and Elemental2
[cols="3,4,4",options="header"]
|===
| Symptom | Cause | Fix

| `No source code is available for type elemental2.dom.DomGlobal; did you forget to inherit a required module?`
| The Maven dependency is present but the GWT module is not inherited
| Add `<inherits name="elemental2.dom.Dom" />` (and `Core`, `Promise`, `WebStorage` for the other artifacts) to the module XML

| `The method addEventListener(String, null) is undefined for the type BodyElement`
| `dom.client` has no `addEventListener` (the `EventTarget` class omits it on purpose)
| `sinkEvents` plus `onBrowserEvent` inside a widget, or an Elemental2 type via `Js.cast`

| `The method querySelector(String) is undefined for the type BodyElement`
| `dom.client` has no selector API
| `Js.cast` the element to `elemental2.dom.Element` or `HTMLElement` and call `querySelector`

| Handlers added with `addClickHandler` stop working in a custom widget
| `onBrowserEvent` was overridden without calling `super.onBrowserEvent(event)`
| Call `super` last, as `ClickCounter` does

| `onBrowserEvent` is never called for one event type
| The bit of that type was not sunk, or the widget is not attached yet (sinking is deferred until `onAttach`)
| Add the bit to `sinkEvents` (or register the handler with `addDomHandler`, which sinks for you) and add the widget to a panel

| `+Should only call onAttach when the widget is detached from the browser's document+`
| `onAttach` called twice, usually by hand or by an override that does not call `super` properly
| Never call `onAttach`/`onDetach` yourself; override `onLoad`/`onUnload`

| A handler keeps firing after the widget was removed
| Registration made in the constructor or in `onLoad` and never undone
| Keep the `HandlerRegistration` and call `removeHandler()` in `onUnload`

| `removeEventListener` seems to do nothing
| A new lambda instance was passed; listeners are compared by identity
| Keep the `EventListener` in a field and remove that instance

| `java.lang.ClassCastException` from a `+Promise.all(...).then(...)+` lambda
| `V[]` is instantiated as `String[]`, but the result is a JavaScript array
| Use `+Promise.<Object>all(...)+` and `Js.cast` each element

| `TypeError: Failed to fetch`
| Network failure, a blocked cross-origin request or mixed content; the promise rejects
| Handle it in `catch_`; an HTTP error such as 405 does not reject, check `res.ok`

| `+(SyntaxError) : Expected property name or '}' in JSON at position 1 (line 1 column 2)+`
| `JSON.parse` of invalid text; the wording differs by browser
| Catch `JavaScriptException`; validate the response content type first

| Two types called `Element`, `Event` or `Storage` in one file
| Both `+com.google.gwt...+` and `+elemental2...+` imported
| Import one, fully qualify the other

| `Js.uncheckedCast` result has `undefined` fields
| The server sent a different shape and nothing checks it
| Validate field by field, or deserialise with AutoBeans or a typed REST client

| Build resolves `jsinterop-annotations` 2.0.0 while the Elemental2 POMs say 2.0.2
| The GWT BOM manages the annotation version
| Accept it (it compiled and ran), or override the managed version deliberately and test
|===

Source: https://www.gwtproject.org/doc/latest/FAQ_Troubleshooting.html[GWT -- FAQ: Troubleshooting]

== Where older material is outdated

The first-edition book and the 2009 article describe a world in which the DOM layer was a listener-based API on top of Internet Explorer 6 to 8.

.Outdated statements about the DOM and events
[cols="3,4",options="header"]
|===
| Older statement | Today

| Events are handled by `ClickListener`, `ChangeListener`, `KeyboardListener` and the other listener interfaces, plus `EventPreview`
| The classes are still in `gwt-user` 2.13.1 but `@Deprecated`; use handlers (`addClickHandler`, `addDomHandler`) and `Event.addNativePreviewHandler`

| Static `DOM.xxx` methods are how you create and change elements (`DOM.createDiv`, `DOM.setStyleAttribute`, `DOM.eventGetType`)
| Most are `@Deprecated`; use `Document` factories, `Element` and `Style`, `NativeEvent` getters

| `com.google.gwt.user.client.Element` is the element type
| `@Deprecated`; `dom.client.Element` is the type, and `getElement()` is assignable to it

| The browser matrix is IE, Firefox, Safari, Opera and the compiler produces a file per browser
| Two permutations only (`gecko1_8` and `safari`); Chromium and Edge use the `safari` one

| Cross-browser event differences must be understood by the developer
| `DOMImplWebkit` and `DOMImplMozilla` absorb the ones that remain; the widget and handler layers hide the rest

| Memory leaks come from JavaScript-to-DOM reference cycles in Internet Explorer, avoided by the single `+__listener+` back reference
| The mechanism is still in the source and still protects widget root elements, but the Javadoc of `RootPanel.detachOnWindowClose` says modern browsers do not have the leaks that required that extra safety net; the leaks you can cause today come from global registrations that are never removed

| Widgets without a parent must be registered with `RootPanel.detachOnWindowClose` or they leak
| Deprecated; call `removeFromParent()` when a widget is no longer needed

| Elemental is the future of GWT browser access
| deprecated in 2.9.0; Elemental2 replaces it and is shared with J2CL
|===

Source: https://www.manning.com/books/gwt-in-action[Manning -- GWT in Action]

The Developer Guide pages on the DOM and on browser support, and the articles on Elemental and on DOM memory leaks, are otherwise accurate descriptions of the code but predate Java 8, JsInterop and Elemental2: their code samples use anonymous classes, JSNI and the listener-era names, and the Elemental article is a historical document.

== What changed recently

* 2.8.0: JsInterop and Java 8 syntax, which made native types such as Elemental2 usable from GWT.
* 2.9.0: compiles with `jsinterop-base` 1.0.0, Elemental2 1.0.0 and `jsinterop-annotations` 2.0.0; Elemental (1) is deprecated.
* 2.12.0 (also): source maps on by default in all browsers, which makes the Elemental2 and `dom.client` code debuggable as Java (see xref:web/gwt/development-mode-and-debugging.adoc[Development Mode & Debugging]).
* 2.12.0: the browser `unload` event is deprecated, so GWT deprecated the calls that require it (`Window.addCloseHandler`, `RootPanel.detachOnWindowClose`) and replaced the `mousewheel` event by `wheel` internally, transparently for applications.
* 2.13.0 and 2.13.1: the release notes list no change to the `dom.client`, `Event` or `user.agent` API; the property still has the two values `gecko1_8` and `safari`.
* Elemental2: 1.3.0 (2025-08-12), 1.3.1 (2025-08-20), 1.3.2 (2025-09-15, latest stable), 1.4.0-RC1 (2026-07-07, pre-release). The repository was last pushed on 2026-09-27 and is Apache-2.0 licensed.
