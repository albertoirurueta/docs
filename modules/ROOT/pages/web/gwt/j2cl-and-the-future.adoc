This page is written against GWT 2.13.1 (released 2026-06-19), `gwt-maven-plugin` 1.3.0 (`net.ltgt.gwt.maven`), JDK 21 running the compiler with `-sourceLevel 17`, the J2CL repository release `v20260402` (2026-04-02) and `j2cl-maven-plugin` 0.22.0 (2023-11-13), checked on 2026-10-09.
It concerns **shared** code (Java that is compiled by `javac`, by the GWT compiler and by J2CL), **client** code (the part that each of the two compilers turns into JavaScript) and **build/tooling** (Maven, Bazel, the module XML).
Every build, error message, size and browser result in the worked example was produced by running the Bookshelf scenario on this page: one shared module, one application built by `gwt-maven-plugin` 1.3.0 with GWT 2.13.1 and one built by `j2cl-maven-plugin` 0.22.0, both loaded in headless Chrome.
Statements about projects that were not run (the J2CL Bazel workflow, J2Wasm, the `watch` goal) come from the project documentation and say so.

GWT 2.13.1 is the toolkit you can ship with today.
J2CL is a second, different Java-to-JavaScript compiler from Google, and the `org.gwtproject` libraries are the part of GWT that was rewritten to run on both.
This page explains how the three relate, what is and is not available, and how to keep the code you write today portable.

== Two compilers, one language

The GWT compiler and J2CL solve the same problem, running Java in the browser, with different designs.

[mermaid]
....

    gjdt --> gdb["Deferred binding<br/>generators, permutations"]

Source: https://github.com/google/j2cl/blob/master/README.md[J2CL -- README], https://github.com/Vertispan/j2clmavenplugin/blob/main/Readme.md[j2cl-maven-plugin -- Readme: build process]

J2CL's own README describes it as a transpiler from Java to Closure style JavaScript, tightly integrated with the Closure Compiler and built with Bazel.
It is the technology behind several large Google applications (the README names Gmail, Inbox, Docs, Slides and Calendar) and says it is used in production inside Google.
The same README also says that the workflow for open-source users is not finalised, that Windows is not supported outside WSL, and in its disclaimer section that the project is an alpha developer preview and not an official Google product.
Its Wasm backend is described as working but still work in progress.

.GWT 2.13.1 and J2CL side by side
[cols="2,4,4",options="header"]
|===
| Aspect | GWT 2.13.1 (this section) | J2CL

| What it is
| A Java-to-JavaScript compiler plus a runtime library, widget set, UiBinder, RPC and tooling, all in one SDK
| A transpiler from Java to Closure-style JavaScript; the optimisation is done by the Closure Compiler; no widget set and no RPC

| Unit of compilation
| The whole application, described by a module XML file and compiled in one run into one or more permutations
| One library at a time (the Maven plugin hashes sources and dependencies and caches each result), then one Closure Compiler run for the application

| Entry point
| `EntryPoint.onModuleLoad()` named by `<entry-point>`
| None. Plain Java classes plus JavaScript that calls them (the sample archetype uses a `.native.js` file that does `new Bookshelf().onModuleLoad()`)

| Deferred binding, generators, linkers
| `GWT.create`, `<replace-with>`, `<generate-with>`, user agent and locale permutations
| No equivalent in the J2CL documentation. Code generation is done with annotation processors (the README names Dagger and AutoValue among the libraries it supports)

| JSNI
| Supported (legacy, see xref:web/gwt/jsni-and-overlay-types.adoc[JSNI & Overlay Types])
| The J2CL documentation uses JsInterop and `.native.js` files next to the Java class instead of JSNI

| JsInterop
| Annotations from `jsinterop-annotations`; exports only with `-generateJsInteropExports`; `@JsAsync` and `@JsEnum` compile but have no effect in 2.13.1
| Same annotations, J2CL semantics; exports use `goog.export`; a few documented differences (see below)

| JRE emulation
| `gwt-user` emulation library, Java 11 level collections, streams and more (see xref:web/gwt/jre-emulation-and-shared-code.adoc[JRE Emulation & Shared Code])
| Its own `jre` library; no reflection, no array bounds checks, `float` computed as `double`, `long` as `goog.math.Long` (J2CL documents these)

| Java language level
| Up to Java 17 syntax with `-sourceLevel 17` since 2.12.0; the roadmap targets Java 21
| Whatever the J2CL build in use supports. `j2cl-maven-plugin` 0.22.0 (J2CL build `v20230718-1`) rejected `var` in the lab (see Pitfalls)

| Build tool
| Maven (`gwt-maven-plugin`), community Gradle plugins, the `Compiler` command line
| Bazel (Google's `j2cl` repository); Maven through `j2cl-maven-plugin`

| UI
| Widgets, panels, UiBinder, cell widgets, Editors, ClientBundle, i18n, RPC and RequestFactory
| None. Bring Elemental2 and a UI library (the repository has samples such as `helloworld` and `guava`)

| Status checked 2026-10-09
| Stable, latest 2.13.1 (2026-06-19)
| Repository active (last push the day this page was checked), releases `v20250623`, `v20250630`, `v20260402`; README says alpha developer preview
|===

Source: https://github.com/google/j2cl/blob/master/README.md[J2CL -- README], https://github.com/google/j2cl/blob/master/docs/limitations.md[J2CL -- Limitations], https://github.com/google/j2cl/blob/master/docs/semantics.md[J2CL -- Semantics], https://github.com/google/j2cl/releases[J2CL -- Releases]

The practical consequence is that the two compilers do not replace one another feature by feature.
A GWT application that uses widgets, UiBinder, GWT-RPC, `ClientBundle`, i18n `Messages` and `GWT.create` cannot be handed to J2CL; the code that CAN be moved is the plain Java underneath it (model, validation, state machines, event bus, parsing) and the libraries that were rewritten to be independent of `gwt-user`.

=== Where J2CL differs from GWT in the language

The J2CL documentation lists the places where Java semantics are deliberately different.
They matter when shared code runs on both compilers, because the same method can behave differently.

.Documented J2CL behaviours to keep in mind for shared code
[cols="3,5",options="header"]
|===
| Topic | J2CL behaviour (from its documentation)

| Reflection
| `java.lang.reflect` and class introspection are not supported; `Class.getEnumConstants` and `Enum.valueOf` are not supported either

| Array access
| No bounds check on array access

| `float`
| Emulated with a JavaScript `number`, so it has `double` precision

| `long`
| Mapped to `goog.math.Long`

| Boxed `Double`, `Boolean`, `String`
| Represented by the JavaScript value itself (unboxed), while `Integer` stays boxed

| `String.format`
| Not emulated, because it needs large localisation code; the J2CL documentation suggests Guava `Strings.lenientFormat`

| `+java.net.*+` and similar
| Intentionally left out of the emulation

| Switch on an enum
| Does not trigger class initialisation, unlike `javac`

| JsInterop namespaces
| A non-native `@JsMethod` may not declare a namespace outside its module; `JsPackage.GLOBAL` is special; subclasses of a class with a `@JsConstructor` must also have one
|===

Source: https://github.com/google/j2cl/blob/master/docs/limitations.md[J2CL -- Limitations], https://github.com/google/j2cl/blob/master/docs/semantics.md[J2CL -- Semantics]

GWT 2.13.1 has its own list of differences (`long` as a composite of doubles, `String.split` with Java 8 semantics, configurable `+jre.checks.*+`), documented in xref:web/gwt/jre-emulation-and-shared-code.adoc[JRE Emulation & Shared Code].
Code that is correct on a JVM, correct in GWT and correct in J2CL avoids all of these corners: no reflection, no `String.format`, no reliance on `float` rounding or array-bounds exceptions.

== What "GWT 3" means today

"GWT 3" was the name given to a planned next major version built on J2CL.
Every public source checked for this page agrees on one fact: that release does not exist.

.What the sources say about GWT 3 (checked 2026-10-09)
[cols="3,5",options="header"]
|===
| Source | Statement

| Maven Central, `org.gwtproject:gwt`
| Versions published: 2.10.0, 2.10.1, 2.11.0, 2.12.0, 2.12.1, 2.12.2, 2.13.0, 2.13.1. No 3.x

| GitHub releases of `gwtproject/gwt`
| Latest 2.13.1 (2026-06-19); milestones 2.14 (open, 23 open and 29 closed issues) and 2.15 (empty)

| J2CL README, "J2CL vs. GWT?"
| The GWT team decided in early 2015 to build a separate product from scratch; the strategy later turned GWT 3 into an SDK focused on libraries and enterprise tooling rather than a compiler

| GWT roadmap page
| Names Java 21 language and JRE emulation as the goal of the next releases, and says GWT explores supporting some J2CL-exclusive JsInterop features in its own compiler. It does not announce a GWT 3

| `org.gwtproject` module READMEs
| Describe each module as a future-proof port of a `com.google.gwt` module with no dependency on `gwt-user`, meant to prepare for GWT 3 and J2CL, and carry a GWT 3 / J2CL compatibility badge

| `j2cl-maven-plugin` Readme
| Calls a J2CL-built application a GWT 3 project, and its cache parameter is named `gwt3BuildCacheDir`
|===

Source: https://repo1.maven.org/maven2/org/gwtproject/gwt/maven-metadata.xml[Maven Central -- org.gwtproject:gwt metadata], https://github.com/gwtproject/gwt/milestones[GWT -- Milestones], https://www.gwtproject.org/roadmap.html[GWT -- Roadmap], https://github.com/google/j2cl/blob/master/README.md[J2CL -- README]

Today "GWT 3" therefore means a direction, not a product:

* **GWT 2.x remains the SDK.** Releases 2.10 to 2.13.1 (2022 to 2026) added Java 11 to 17 syntax, Jakarta artifacts, `org.gwtproject` coordinates and many JRE additions. The roadmap commits to Java 21 parity.
* **J2CL is a separate compiler** that Google maintains for its own applications, usable by outsiders through Bazel or the community Maven plugin.
* **The `org.gwtproject` libraries** are the shared part: they compile with GWT 2.9 or later and with J2CL, and are what a "GWT 3" would be assembled from.
* **Shared compatibility work in GWT itself.** The 2.9.0 release notes say GWT can compile projects that use `jsinterop-base` 1.0.0, Elemental2 1.0.0 and `jsinterop-annotations` 2.0.0 (everything except `@JsAsync` and `@JsEnum`), and the 2.10.0 notes mention JRE emulation changes that keep the GWT and J2CL code bases consistent for J2CL's Wasm work.

An application started today should be written as GWT 2.13.1 code, with the J2CL-friendly rules from the later section applied to whatever is cheap to apply, and without any plan that depends on a "GWT 3" release date.

Source: https://www.gwtproject.org/release-notes.html#Release_Notes_2_9_0[GWT -- Release notes: 2.9.0], https://www.gwtproject.org/release-notes.html#Release_Notes_2_10_0[GWT -- Release notes: 2.10.0]

== The org.gwtproject modules

Since the GWT 2.10.0 release the Maven groupId of the SDK is `org.gwtproject`.
A second family of artifacts lives under the same groupId prefix: libraries in the form `org.gwtproject.<area>:gwt-<area>`, each in its own repository in the https://github.com/gwtproject[gwtproject] GitHub organisation.
The READMEs I read (core, event, dom, editor, safehtml, http, json, timer, xhr, regexp, aria, layout, animation) describe each module as a port of a `com.google.gwt` module with no dependency on `gwt-user` apart from the Java runtime emulation, aimed at GWT 3 and J2CL; the `gwt-core` README requires GWT 2.9.0 or newer.
`gwt-core` goes further: its repository contains separate GWT 2 and J2CL test modules and its README says `mvn clean verify` runs the tests on the JVM, with J2CL and with GWT 2.

Three facts shape how much to rely on this family:

* **No stable release.** There is no `1.0.0` for any of them, and the newest artifact on Central is `gwt-core` 1.0.0-RC2 from November 2023. The newest commit in any of the module repositories at the time of the check was 2024-12-17 (`gwt-editor`); `gwt-editor` has commits after its last Central release.
* **The big UI libraries were not ported.** The Central listing has no artifact for widgets, panels, UiBinder, cell widgets, `ClientBundle`, i18n, GWT-RPC or validation. The only `org.gwtproject.web` artifacts are the RequestFactory ones (`+org.gwtproject.web.bindery:requestfactory*+`), which are part of the 2.13.1 SDK, not J2CL-ready ports.
* **Mixing is allowed.** The module XML names do not collide with the `com.google.gwt` ones, and `gwt-event-compat` is a bridge: its `CompatEventBus` wraps a new-style event bus as a `com.google.gwt.event.shared.EventBus`, so a code base can move to the new event classes while libraries still use the old ones.

The libraries bring Elemental2 with them: the `gwt-core` 1.0.0-RC2 POM declares `elemental2-core` and `elemental2-dom` 1.1.0, and `gwt-dom` additionally depends on `gwt-safehtml`, `gwt-safecss`, `gwt-regexp` and `gwt-dom-style-definitions`.
An application that wants a newer Elemental2 declares it itself; Maven's nearest-wins rule then picks the application's version.

=== Using a ported module in a GWT 2.13.1 project

The migration recipe in the README of every module is the same three steps, shown here for `gwt-event` (it is the one used in the worked example):

.Replace the bindery event module
[source,xml]
----
<!-- pom.xml -->
<dependency>
  <groupId>org.gwtproject.event</groupId>
  <artifactId>gwt-event</artifactId>
  <version>1.0.0-RC1</version>
</dependency>

<!-- module .gwt.xml: replaces com.google.web.bindery.event.Event -->
<inherits name="org.gwtproject.event.Event"/>
----

.Imports change from com.google.web.bindery.event.shared to org.gwtproject.event.shared
[source,java]
----
import org.gwtproject.event.shared.Event;
import org.gwtproject.event.shared.EventBus;
import org.gwtproject.event.shared.HandlerRegistration;
import org.gwtproject.event.shared.SimpleEventBus;
----

Source: https://github.com/gwtproject/gwt-event[gwt-event -- README: migrating from com.google.web.bindery.event.Event]

xref:web/gwt/events-and-handlers.adoc[Events & Handlers] covers the `com.google.gwt.event` handler model itself, which is what most widget code uses.
Because the widget set still depends on that model, the ported event module is most useful for non-UI code: models, services and presenters that fire domain events.
Likewise xref:web/gwt/mvp-activities-and-places.adoc[MVP, Activities & Places] and xref:web/gwt/editors.adoc[Editors] use the `gwt-user` versions; `gwt-places` and `gwt-editor` exist as the J2CL-ready alternatives.

== Writing code that works with both

The rules below are the ones that kept the Bookshelf core module compiling with `javac`, GWT 2.13.1 and J2CL.

.Rules for Java that must compile with both compilers
[cols="3,4,4",options="header"]
|===
| Rule | GWT 2.13.1 | J2CL

| Keep shared code free of `+com.google.gwt.*+` types
| Allowed, but then the module is GWT-only
| `gwt-user` classes are not available; any dependency that drags `gwt-user` in is a problem (see Pitfalls)

| No JSNI
| Legacy JSNI works
| Not supported; use JsInterop plus `.native.js`

| No `GWT.create`, no generators
| Deferred binding works
| No equivalent; use constructors, factories, annotation processors

| Use JsInterop and Elemental2 for the browser API
| Elemental2 1.3.2 is the latest stable and the one the other pages of this section use
| The same libraries, but in the lab the Maven plugin needed Elemental2 1.1.0 (see Pitfalls)

| Strip server-only code with `@GwtIncompatible`
| Honoured by name, whatever package it is in
| Honoured by name too; the Maven plugin replaces the stripped members with whitespace

| Platform differences through replacement classes
| `+<super-source path="..."/>+` in the module XML (see xref:web/gwt/jre-emulation-and-shared-code.adoc[JRE Emulation & Shared Code])
| The J2CL documentation recommends a replacement file in a `super-j2cl` folder selected by the build rule (Bazel)

| Avoid reflection, `String.format`, `java.io`, `java.net`
| Not emulated either (`+No source code is available for type ...+`)
| Not emulated (`+The import ... cannot be resolved+`)

| No dependence on `long`, `float`, array-bounds or class-initialisation corner cases
| Each compiler has its own differences
| Documented differences listed above

| Use Java 8 level syntax unless both build tools are verified for more
| `-sourceLevel 17` in the Bookshelf scenario
| `j2cl-maven-plugin` 0.22.0 rejected `var`
|===

Source: https://github.com/google/j2cl/blob/master/docs/best-practices.md[J2CL -- Best practices], https://www.gwtproject.org/javadoc/latest/com/google/gwt/core/shared/GwtIncompatible.html[GWT Javadoc -- GwtIncompatible], https://www.gwtproject.org/doc/latest/DevGuideOrganizingProjects.html#DevGuideModuleXml[GWT -- Organizing Projects: Module XML files]

The J2CL best-practices page also warns against using `@GwtIncompatible` to switch application logic on and off, because the divergence then spreads through the code.
Its advice is to hide the incompatible part behind an interface and supply a different implementation per platform.
The GWT-side detail of `@GwtIncompatible` and super-source is explained in xref:web/gwt/jre-emulation-and-shared-code.adoc[JRE Emulation & Shared Code], and the JsInterop annotations used for the browser edge in xref:web/gwt/jsinterop.adoc[JsInterop] and xref:web/gwt/dom-and-elemental2.adoc[DOM & Elemental2].

=== The shared module

The core module has no dependency on `gwt-user`.
Its only dependencies are the ported event module, the JsInterop annotations (they ship with GWT and J2CL alike) and JUnit for the JVM test.

.bookshelf-core/pom.xml (dependencies and sources jar)
[source,xml]
----
<dependencies>
  <dependency>
    <groupId>org.gwtproject.event</groupId>
    <artifactId>gwt-event</artifactId>
    <version>1.0.0-RC1</version>
  </dependency>
  <dependency>
    <groupId>com.google.jsinterop</groupId>
    <artifactId>jsinterop-annotations</artifactId>
    <version>2.1.0</version>
  </dependency>
  <dependency>
    <groupId>junit</groupId>
    <artifactId>junit</artifactId>
    <version>4.13.2</version>
    <scope>test</scope>
  </dependency>
</dependencies>

<build>
  <plugins>
    <plugin>
      <groupId>org.apache.maven.plugins</groupId>
      <artifactId>maven-source-plugin</artifactId>
      <version>3.4.0</version>
      <executions>
        <execution>
          <id>attach-sources</id>
          <goals><goal>jar-no-fork</goal></goals>
        </execution>
      </executions>
    </plugin>

.Isbn.java: JsInterop type, shared logic and one server-only method
[source,java]
----
package com.example.bookshelf.core.shared;

import java.io.File;
import jsinterop.annotations.JsMethod;
import jsinterop.annotations.JsType;

@JsType(namespace = "bookshelf", name = "Isbn")
public final class Isbn {

  private Isbn() {}

  @JsMethod
  public static String normalize(String raw) {
    return raw.replace("-", "").replace(" ", "");
  }

  @JsMethod
  public static boolean isValid(String raw) {
    String digits = normalize(raw);
    if (digits.length() != 13) {
      return false;
    }
    int sum = 0;
    for (int i = 0; i < 13; i++) {
      char c = digits.charAt(i);
      if (c < '0' || c > '9') {
        return false;
      }
      sum += (c - '0') * (i % 2 == 0 ? 1 : 3);
    }
    return sum % 10 == 0;
  }

  /** Server-only: java.io.File is not part of either emulation. */
  @GwtIncompatible("java.io.File is not emulated")
  public static String coverFileName(String raw) {
    return new File("covers", normalize(raw) + ".jpg").getPath();
  }
}
----

`GwtIncompatible` is a six-line annotation declared in the same package (`@Retention(CLASS)`, targets type, method, field and constructor, one `String value()`): both tools look at its simple name only, so there is no dependency on GWT to import.

.BookAddedEvent.java and Catalog.java: shared model on the ported event bus
[source,java]
----
public class BookAddedEvent extends Event<BookAddedEvent.Handler> {

  public interface Handler {
    void onBookAdded(BookAddedEvent event);
  }

  public static final Type<Handler> TYPE = new Type<>();

  private final String title;

  public BookAddedEvent(String title) {
    this.title = title;
  }

  public String getTitle() {
    return title;
  }

  @Override
  public Type<Handler> getAssociatedType() {
    return TYPE;
  }

  @Override
  protected void dispatch(Handler handler) {
    handler.onBookAdded(this);
  }
}

public class Catalog {

  private final EventBus bus = new SimpleEventBus();
  private final List<String> titles = new ArrayList<>();

  public EventBus events() {
    return bus;
  }

  public boolean add(String title, String isbn) {
    if (!Isbn.isValid(isbn)) {
      return false;
    }
    titles.add(title);
    bus.fireEvent(new BookAddedEvent(title));
    return true;
  }

  public int size() {
    return titles.size();
  }
}

Source: https://repo1.maven.org/maven2/com/vertispan/j2cl/j2cl-maven-plugin/maven-metadata.xml[Maven Central -- j2cl-maven-plugin], https://github.com/Vertispan/j2clmavenplugin/blob/main/Readme.md[j2cl-maven-plugin -- Readme]

What the Readme documents (not all of it exercised here):

* **Per-library builds with a cache.** Each dependency is hashed together with its dependencies and the plugin version, stripped of `@GwtIncompatible` members, run through annotation processors, transpiled and cached; only changed libraries are rebuilt. The cache lives in `target` by default and can be moved to a shared directory with the `gwt3.cache.dir` property.
* **`mvn j2cl:clean`** removes cache entries, `-Dartifact=<artifactId>` limits it to one artifact and `+-Dartifact=*+` empties the cache directory.
* **Dependency rewriting.** By default the plugin replaces the `jsinterop-base` coordinates with `com.vertispan.jsinterop:base`, which the build log confirmed (`Removing dependency com.google.jsinterop:base:jar:1.0.1:compile, replacing with com.vertispan.jsinterop:base:jar:1.0.1-1`).
* **Compilation levels.** `ADVANCED_OPTIMIZATIONS` for production (the sample archetype writes `ADVANCED`, which worked), `SIMPLE_OPTIMIZATIONS`, `WHITESPACE_ONLY`, `BUNDLE` (concatenation only) and `BUNDLE_JAR` (one bundle per classpath entry, loaded in order).
* **Dev mode.** The `watch` goal recompiles the changed libraries of a whole reactor, so it is meant to be run from the parent project. It was not run for this page.

The `test` goal runs JUnit tests compiled to JavaScript (the archetype's test runs under HtmlUnit); the Readme claims the plugin is the only way to build general J2CL projects outside Bazel.
The GWT counterpart of such tests is covered in xref:web/gwt/testing.adoc[Testing GWT Applications].

=== Gradle, Bazel and the rest

The community GWT Gradle plugins mentioned in xref:web/gwt/build-tools-maven-and-gradle.adoc[Build Tools: Maven & Gradle] build GWT 2 applications; none of them was checked for J2CL.
Google's own J2CL workflow is Bazel (its getting-started page uses Bazelisk and `bazel build`/`bazel run` on the `helloworld` sample, and says the output of that sample is a single optimised line of JavaScript).
The Bazel path was not run for this page.
For a Java team that already builds with Maven, the plugin is the lower-friction route; the plugin bundles the older J2CL build `v20230718-1`, so features added since (the J2CL README mentions Wasm) are reached through Bazel; whether the plugin exposes them was not checked.

== Moving a GWT code base toward J2CL

A realistic migration is incremental and always keeps the GWT build green:

* **Isolate the portable core.** Move models, validation, formatting and domain events into a module that depends on no `gwt-user` type, as `bookshelf-core` does. Compile it with `javac` and JUnit first.
* **Replace JSNI with JsInterop.** The pages xref:web/gwt/jsni-and-overlay-types.adoc[JSNI & Overlay Types] and xref:web/gwt/jsinterop.adoc[JsInterop] describe the mapping; JsInterop works in both compilers.
* **Replace `GWT.create` and generators in the core** with factories or annotation processors (see xref:web/gwt/deferred-binding-and-generators.adoc[Deferred Binding & Generators]).
* **Swap `gwt-user` classes for ported ones** where a module exists and is acceptable to depend on at release-candidate quality (`gwt-event`, `gwt-core`, `gwt-dom`, `gwt-safehtml`, `gwt-editor`), or for Elemental2.
* **Add the second build** (J2CL) in CI and keep it as a canary. Anything that breaks it shows which GWT assumption crept into the core.
* **Leave the UI and the transport alone.** Widgets, UiBinder, cell widgets, `ClientBundle`, i18n and GWT-RPC have no J2CL-ready counterpart in `org.gwtproject`.

Mapping of the old coordinates and packages, with the other changes between GWT versions, is collected in xref:web/gwt/whats-changed-and-migration.adoc[What's Changed & Migration], in particular the recipes for xref:web/gwt/whats-changed-and-migration.adoc#migrate-coordinates[coordinates and packages], xref:web/gwt/whats-changed-and-migration.adoc#migrate-jakarta[Jakarta], xref:web/gwt/whats-changed-and-migration.adoc#migrate-jsni[JSNI] and xref:web/gwt/whats-changed-and-migration.adoc#migrate-elemental[Elemental].
A catalogue of the libraries around GWT, including alternatives for the pieces that were not ported, is in xref:web/gwt/ecosystem-and-libraries.adoc[Ecosystem & Libraries], and IDE support for GWT and J2CL projects in xref:web/gwt/tooling-and-ide-support.adoc[Tooling & IDE Support].

== Pitfalls

.Problems met while building the same module with both compilers
[cols="3,4,4",options="header"]
|===
| Symptom (exact message) | Cause | Fix

| `+Unable to find 'jsinterop/annotations/JsInterop.gwt.xml' on your classpath; could be a typo, or maybe you forgot to include a classpath entry for source?+`
| A `<inherits name="jsinterop.annotations.JsInterop"/>` line was added to the module; no such module descriptor exists in `jsinterop-annotations` 2.0.0, 2.1.0 or `gwt-user` 2.13.1
| Remove the line; the annotations compile in GWT 2.13.1 without it

| `No source code is available for type java.io.File; did you forget to inherit a required module?` (GWT) and `The import java.io.File cannot be resolved` (J2CL)
| A JRE class neither emulation provides is used in shared code
| Mark the member `@GwtIncompatible`, or hide it behind an interface with a different implementation per platform

| `+--dependency_mode=SORT_ONLY cannot be used with --entry_point, --closure_entry_point or --common_js_entry_module.+` followed by `Closure Compiler failed, check log for details`
| The `entrypoint` element was configured; the log warns `+Parameter 'entrypoint' is deprecated: Will be removed in 0.21+` and the default dependency mode is `SORT_ONLY`
| Delete `entrypoint`; start the application from a `.native.js` file as in the archetype

| `[JSC_UNDEFINED_VARIABLE] variable ElementInternals is undeclared` (and the same for `MediaStreamTrackGenerator`, `OverconstrainedError`, `SubmitEvent`, `TransitionEvent`)
| `elemental2-dom` 1.2.3 with `j2cl-maven-plugin` 0.22.0, whose Closure externs predate those browser types
| Use `elemental2-dom` 1.1.0 (the version in the plugin's own archetype)

| `The import org cannot be resolved` and `NullMarked cannot be resolved to a type` while transpiling `elemental2-promise:1.3.2`
| Elemental2 1.3.2 declares a JSpecify dependency; the transpile step of 0.22.0 could not resolve the annotations although `org.jspecify:jspecify:1.0.0` was in the dependency list
| Same fix; or build with a newer J2CL than the plugin bundles (untested here)

| `cannot find symbol` with `symbol:   class var` in the bytecode step of the shared module
| `var` (Java 10) in code that the J2CL build compiles; the plugin log shows `source value 8 is obsolete` for that step
| Keep shared code at Java 8 syntax while `j2cl-maven-plugin` 0.22.0 is the J2CL build

| `Uncaught ReferenceError: bookshelf is not defined`
| `@JsType` classes are not exported to `window` by an `ADVANCED` J2CL build
| Export explicitly with `goog.export` (see the J2CL semantics page); GWT needs `-generateJsInteropExports`

| `Uncaught ReferenceError: $jscomp is not defined` with `compilationLevel` `BUNDLE`
| The plain concatenated bundle (6.4 MB for this application) referenced `$jscomp`, which it did not define
| Use `ADVANCED` (21 KB for the same application) or `BUNDLE_JAR`

| `The import java.io.BufferedReader cannot be resolved` for `javax.validation:validation-api:1.0.0.GA:sources`
| `gwt-user` was added as a dependency of the J2CL module and the plugin tried to transpile its transitive dependencies
| Keep `gwt-user` and `gwt-dev` out of the dependency graph of J2CL modules

| `Build failed, check log for failures` from `j2cl:build`
| Generic wrapper; the real cause is an earlier `ERROR` line in the log. After an aborted build, `STALE BUILD DETECTED - build was stale after 10 seconds, deleting it to take over` lines appear and the next build may fail with them
| Read the first error; delete `target` and rebuild
|===

Source: https://github.com/Vertispan/j2clmavenplugin/blob/main/Readme.md[j2cl-maven-plugin -- Readme], https://github.com/google/j2cl/blob/master/docs/limitations.md[J2CL -- Limitations]

== What changed recently

* **GWT 2.9.0:** compiles against `jsinterop-base` 1.0.0, Elemental2 1.0.0 and `jsinterop-annotations` 2.0.0; Elemental (version 1) officially deprecated in favour of Elemental2.
* **GWT 2.10.0:** `org.gwtproject` becomes the groupId; JRE emulation simplifications to keep the GWT and J2CL code bases consistent for J2CL's Wasm backend.
