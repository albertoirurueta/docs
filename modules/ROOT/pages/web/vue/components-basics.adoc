A *component* is a reusable instance with its own template, logic, and styling. A Vue app is a tree of
components nested inside one root component. This page is the quick tour; each topic links to a deeper page.
The reference is https://vuejs.org/guide/essentials/component-basics.html[Components Basics].

== Defining a component

The usual unit is a *Single-File Component* (SFC): a `.vue` file with `<script>`, `<template>`, and optional
`<style>` blocks, compiled by the build tool. See
https://vuejs.org/guide/scaling-up/sfc.html[Single-File Components] for the format.

[source,vue]
----
<!-- ButtonCounter.vue -->
<script setup>
import { ref } from 'vue'

const count = ref(0)
</script>

<template>
  <button @click="count++">Clicked {{ count }} times</button>
</template>

<style scoped>
button { font-weight: 600; }
</style>
----

Without a build step a component can be a plain object with a `setup()` and a string `template`, but SFCs are
the norm.

== Using a component

Import it and use it in the template. With `<script setup>`, an imported component is available to the
template automatically -- no registration call.

[source,vue]
----
<script setup>
import ButtonCounter from './ButtonCounter.vue'
</script>

<template>
  <h1>A child component</h1>
  <ButtonCounter />
  <ButtonCounter />   <!-- each use is an independent instance with its own count -->
</template>
----

Use `PascalCase` in SFC templates. Components used this way are *locally registered* -- scoped to the
component that imports them. For app-wide `+app.component(...)+` registration and the trade-off it carries, see
xref:web/vue/registration-and-props.adoc[] and
https://vuejs.org/guide/components/registration.html[Component Registration].

== Passing props

Props are the custom attributes a component accepts. Declare them with `defineProps`; the parent passes them
as attributes, static or bound with `:`.

[source,vue]
----
<!-- BlogPost.vue -->
<script setup>
defineProps({
  title: String,
  likes: { type: Number, default: 0 }
})
</script>

<template>
  <h4>{{ title }} ({{ likes }})</h4>
</template>
----

[source,vue]
----
<script setup>
import BlogPost from './BlogPost.vue'

const posts = [
  { id: 1, title: 'Reactivity' },
  { id: 2, title: 'Templates' }
]
</script>

<template>
  <BlogPost v-for="post in posts" :key="post.id" :title="post.title" />
</template>
----

Props flow *one way*: parent to child. A child must not mutate a prop; to change parent state it emits an
event. Full prop validation, typing, and `defineModel` are in xref:web/vue/registration-and-props.adoc[].

== Listening to events

A child declares its events with `defineEmits` and fires one with `+emit(name, ...args)+`. The parent listens
with `@`. See https://vuejs.org/guide/essentials/component-basics.html#listening-to-events[Listening to
Events].

[source,vue]
----
<!-- BlogPost.vue -->
<script setup>
defineProps({ title: String })
const emit = defineEmits(['enlarge-text'])
</script>

<template>
  <h4>{{ title }}</h4>
  <button @click="emit('enlarge-text', 0.1)">Bigger</button>
</template>
----

[source,vue]
----
<script setup>
import { ref } from 'vue'
const fontSize = ref(1)
</script>

<template>
  <BlogPost
    title="Hello"
    @enlarge-text="(amount) => fontSize += amount" />
</template>
----

Event arguments, `v-model` on components, and fallthrough attributes are in
xref:web/vue/component-events-and-v-model.adoc[].

== A first look at slots

A slot lets a parent pass *template content* into a child; the child renders it wherever it puts `<slot />`.
See https://vuejs.org/guide/essentials/component-basics.html#content-distribution-with-slots[Content
Distribution with Slots].

[source,vue]
----
<!-- AlertBox.vue -->
<template>
  <div class="alert">
    <strong>Error!</strong>
    <slot>A default message</slot>
  </div>
</template>
----

[source,vue]
----
<template>
  <AlertBox>Something bad happened.</AlertBox>
</template>
----

Named and scoped slots have their own page: xref:web/vue/slots.adoc[].

== Dynamic components

`+<component :is="...">+` renders a different component depending on a value -- tabs, a wizard, a content
switch. `:is` takes a component (imported, or looked up in a local map) or, for a native element, a tag-name
string. See https://vuejs.org/guide/essentials/component-basics.html#dynamic-components[Dynamic Components].

[source,vue]
----
<script setup>
import { shallowRef } from 'vue'
import Home from './Home.vue'
import Posts from './Posts.vue'

const tabs = { Home, Posts }
const current = shallowRef('Home')
</script>

<template>
  <button v-for="(_, name) in tabs" :key="name" @click="current = name">
    {{ name }}
  </button>

  <component :is="tabs[current]" />
</template>
----

Switching away *unmounts* the outgoing component, so its state is lost and it is rebuilt on return. Wrap it
in `<KeepAlive>` to cache the inactive instances instead:

[source,vue]
----
<template>
  <KeepAlive>
    <component :is="tabs[current]" />
  </KeepAlive>
</template>
----

Kept-alive components fire `onActivated` / `onDeactivated` rather than mount / unmount -- see
xref:web/vue/lifecycle-hooks.adoc[].

== How a component tree is built and updated

Each use of a component tag creates a separate *component instance* with its own state, and the instances form a tree
that mirrors the template nesting. Data moves in exactly two directions along the edges of that tree: props travel
*down* from parent to child, and events travel *up* from child to parent. Keeping to that rule makes the origin of any
piece of state easy to find.

[mermaid]
....
flowchart TD
    App["App (root)"] --> List["TodoList: owns the todos array"]
    List --> Item1["TodoItem id 1"]
    List --> Item2["TodoItem id 2"]
    List -. "props: todo" .-> Item1
    List -. "props: todo" .-> Item2
    Item1 -. "events: toggle, remove" .-> List
    Item2 -. "events: toggle, remove" .-> List
....

When the parent changes the array, the parent re-renders and passes new props down; a child re-renders only if a prop
*it actually uses* changed. A child that wants something changed never edits the prop -- it emits an event, and the
owner of the data performs the update.

== Worked example: splitting the todo list

The todo list from xref:web/vue/getting-started.adoc[] becomes two components. `TodoItem` is presentational: it
receives one todo and reports what the user did.

[source,vue]
----
<!-- TodoItem.vue -->
<script setup>
defineProps({
  todo: { type: Object, required: true }
})
const emit = defineEmits(['toggle', 'remove'])
</script>

<template>
  <li :class="{ done: todo.done }">
    <label>
      <input type="checkbox" :checked="todo.done" @change="emit('toggle', todo.id)" />
      {{ todo.text }}
    </label>
    <button @click="emit('remove', todo.id)">Delete</button>
  </li>
</template>
----

`TodoList` owns the data and implements the changes in response to those events:

[source,vue]
----
<!-- TodoList.vue -->
<script setup>
import { ref } from 'vue'
import TodoItem from './TodoItem.vue'

const todos = ref([
  { id: 1, text: 'Read the guide', done: true },
  { id: 2, text: 'Build a todo list', done: false }
])

function toggle(id) {
  const todo = todos.value.find((t) => t.id === id)
  todo.done = !todo.done
}
function remove(id) {
  todos.value = todos.value.filter((t) => t.id !== id)
}
</script>

<template>
  <ul>
    <TodoItem
      v-for="todo in todos"
      :key="todo.id"
      :todo="todo"
      @toggle="toggle"
      @remove="remove" />
  </ul>
</template>
----

The checkbox is bound with `:checked` rather than `v-model`, deliberately: `v-model` on `todo.done` would let the
child mutate an object it received as a prop. Mutating a nested property of an object prop does not trigger Vue's
warning (the object is shared), but it hides where the change comes from. The event keeps the child honest. One round
trip when the user ticks a box looks like this:

[mermaid]
....
sequenceDiagram
    participant U as User
    participant I as TodoItem
    participant L as TodoList
    participant V as Vue runtime
    U->>I: change event on the checkbox
    I->>L: emit toggle with the todo id
    L->>L: find the todo and flip done
    L->>V: reactive write triggers the render effect
    V->>I: new todo prop (same object, new done value)
    I->>U: DOM patched, li gains the done class
....

Mounted with Vue Test Utils, ticking the second checkbox gives two `li.done` rows and clicking the first *Delete*
button leaves one row, which confirms the contract without any DOM code in either component.

== Choosing component boundaries

Split a component when a piece of the template has its own *state*, is *repeated*, or has a clear *name* that makes the
parent easier to read -- not merely because a file grew. A practical test is whether the extracted piece can be
described by its props and events alone, as `TodoItem` can. Components that only render (no ownership of data) are
cheap to test and to reuse; components that own data should be few and near the root. State needed by distant
components belongs higher in the tree, in xref:web/vue/provide-inject.adoc[provide / inject] or in
xref:web/vue/state-management.adoc[a store].

== In-DOM template caveats

When a template is written directly in an HTML file -- not in an SFC or a JavaScript string -- the browser
parses it before Vue sees it, so HTML rules apply. See
https://vuejs.org/guide/essentials/component-basics.html#in-dom-template-parsing-caveats[in-DOM template
parsing caveats].

* *Case-insensitive tags and attributes.* The browser lowercases everything, so `<BlogPost>` and `:someProp`
  are unreachable -- use kebab-case: `+<blog-post some-prop="...">+`.
* *No self-closing custom elements.* `<my-component />` is not recognised by the HTML parser; write
  `<my-component></my-component>`.
* *Element placement restrictions.* `<table>` allows only certain children, so a component row needs
  `<tr is="vue:blog-row">` (with the `vue:` prefix) rather than `<blog-row>` inside `<tbody>`. The same
  applies inside `<ul>`, `<ol>`, and `<select>`.

None of this affects SFCs or string templates -- their content is compiled by Vue, not by the browser.
