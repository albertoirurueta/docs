= Watchers
:description: Running side effects in response to reactive state changes in Vue -- watch with getter, multiple, deep, immediate and once options; watchEffect and automatic dependency tracking; flush timing; cleanup; and stopping a watcher.
:keywords: Vue, watch, watchEffect, watchers, deep watcher, immediate, once, getter source, flush timing, flush post, flush sync, onWatcherCleanup, stop watcher, watch vs computed, Options API watch

include::partial$ai-disclaimer.adoc[]

A *watcher* runs a side effect when reactive state changes -- fetching data, imperative DOM work, talking to
a non-reactive library, logging. For deriving a value from state, use a
xref:web/vue/computed-properties.adoc[computed property] instead. The reference is
https://vuejs.org/guide/essentials/watchers.html[Watchers] and the API entries for
https://vuejs.org/api/reactivity-core.html#watch[`watch`] and
https://vuejs.org/api/reactivity-core.html#watcheffect[`watchEffect`].

== watch

`watch(source, callback, options?)`. The source is a ref, a reactive object, a getter function, or an array
of those; the callback receives the new and previous values.

[source,vue]
----
<script setup>
import { ref, watch } from 'vue'

const question = ref('')
const answer = ref('')

// source: a ref
watch(question, async (newQuestion, oldQuestion) => {
  if (!newQuestion.includes('?')) return
  answer.value = 'Thinking...'
  const res = await fetch('https://yesno.wtf/api')
  answer.value = (await res.json()).answer
})
</script>
----

A single property of a reactive object is *not* a valid source on its own (it evaluates to a plain value) --
wrap it in a getter:

[source,js]
----
const state = reactive({ count: 0 })

// watch(state.count, ...)          // wrong -- passes a number
watch(() => state.count, (count, prev) => {
  console.log(count, prev)
})
----

Multiple sources -- pass an array; the callback gets arrays of new and old values:

[source,js]
----
watch([fooRef, () => bar.value], ([foo, bar], [prevFoo, prevBar]) => {
  /* ... */
})
----

=== deep

Passing a reactive object directly makes the watcher implicitly *deep* -- it fires on nested mutation, though
`newValue` and `oldValue` are then the same object. A getter that *returns* an object is not deep unless you
ask; `deep` also accepts a number to cap the traversal depth (3.5+).

[source,js]
----
watch(
  () => state.profile,
  (profile) => { /* also fires when state.profile.name changes */ },
  { deep: true }
)
----

=== immediate

Run the callback once right away, then on every change:

[source,js]
----
watch(source, callback, { immediate: true })
----

=== once

Run the callback at most once, then stop the watcher automatically (3.4+):

[source,js]
----
watch(source, callback, { once: true })
----

== watchEffect

`watchEffect(fn)` runs `fn` immediately and re-runs it whenever any reactive value it *read during that run*
changes. Dependencies are tracked automatically -- there is no source list. See
https://vuejs.org/guide/essentials/watchers.html#watcheffect[watchEffect].

[source,js]
----
const id = ref(1)
const data = ref(null)

watchEffect(async () => {
  const res = await fetch(`/api/todos/${id.value}`)
  data.value = await res.json()
})
----

Only synchronous reads *before the first `await`* are tracked. A `ref` accessed after an `await` does not
register as a dependency.

== watch vs. watchEffect

[cols="1,1"]
|===
| `watch` | `watchEffect`

| explicit source(s) | tracks whatever it reads
| lazy by default (`immediate` opts in) | runs once immediately
| gives `newValue` and `oldValue` | no previous value
| callback is separate from the source | tracking and effect in one function
|===

Prefer `watch` when you need the old value or want to be exact about the trigger; `watchEffect` when the
effect touches several sources you would otherwise have to list.

== Flush timing

By default the callback runs *before* Vue patches the DOM (`flush: 'pre'`). The alternatives:

* `flush: 'post'` -- run after the DOM update, so xref:web/vue/template-refs.adoc[template refs] hold the
  updated elements. `watchPostEffect()` is the shorthand for `watchEffect` with this option.
* `flush: 'sync'` -- run synchronously on every change, before batching. Inefficient; rarely the right call.

[source,js]
----
watch(source, callback, { flush: 'post' })
----

The three flush modes are three points on the same update cycle. A write to a ref only *queues* work; the
scheduler then flushes the queue in a fixed order:

[mermaid]
....
flowchart LR
    w["state write<br/>(count.value++)"] --> sy{"flush: sync?"}
    sy -->|yes| scb["callback runs now,<br/>inside the write"]
    sy -->|no| q["scheduler queue<br/>(batched, de-duplicated)"]
    q --> pre["pre watchers<br/>(DOM still old)"]
    pre --> r["component re-render<br/>and DOM patch"]
    r --> post["post watchers<br/>(DOM updated, refs fresh)"]
....

Because writes are batched, three assignments to the same ref in one tick produce *one* `pre` or `post` callback
(with the final value) but three `sync` callbacks. The order is observable:

[source,ts]
----
import { ref, watch, defineComponent, h } from 'vue'
import { mount } from '@vue/test-utils'

const seen: string[] = []
const Counter = defineComponent({
  setup() {
    const n = ref(0)
    const el = ref<HTMLElement | null>(null)
    watch(n, () => seen.push('pre:' + el.value!.textContent), { flush: 'pre' })
    watch(n, () => seen.push('post:' + el.value!.textContent), { flush: 'post' })
    watch(n, () => seen.push('sync'), { flush: 'sync' })
    return () => h('button', { ref: el, onClick: () => { n.value++; seen.push('after-write') } }, String(n.value))
  },
})
await mount(Counter).trigger('click')
// seen -> ['sync', 'after-write', 'pre:0', 'post:1']
----

The `pre` callback still reads the old text (`0`), the `post` callback reads the new one (`1`), and the `sync`
callback ran before the line after the write. Choose `post` whenever the callback measures or focuses an
element the same change is about to render.

== Cleanup

Register cleanup to run *before the next callback* (and when the watcher stops) -- abort a stale request,
clear a timer. `onWatcherCleanup()` (3.5+) is importable and must be called synchronously inside the effect:

[source,js]
----
import { watch, onWatcherCleanup } from 'vue'

watch(id, (newId) => {
  const controller = new AbortController()
  fetch(`/api/${newId}`, { signal: controller.signal })
  onWatcherCleanup(() => controller.abort())
})
----

The older form is an `onCleanup` function passed to the callback -- the third argument for `watch`, the first
for `watchEffect`:

[source,js]
----
watch(id, (newId, oldId, onCleanup) => {
  const controller = new AbortController()
  onCleanup(() => controller.abort())
})
----

== Stopping a watcher

`watch` and `watchEffect` return a stop handle:

[source,js]
----
const stop = watchEffect(() => { /* ... */ })
// later
stop()
----

A watcher created *synchronously* in `setup` / `<script setup>` is bound to the component and stops on
unmount. One created *asynchronously* -- inside `setTimeout`, or after an `await` -- is not bound and leaks
unless you stop it by hand. The docs state watchers must be created synchronously to be disposed
automatically.

=== Pausing and resuming

Since 3.5 the handle returned by `watch` and `watchEffect` is a function that also carries `pause()`, `resume()`
and `stop()`. While a watcher is paused its callback does not run; a change made during the pause is remembered,
and the callback runs once, with the latest value, as soon as the watcher resumes:

[source,ts]
----
const n = ref(0)
const handle = watch(n, (v) => console.log('changed', v))

handle.pause()
n.value = 1          // callback held back
handle.resume()      // logs "changed 1" on the next flush
handle.stop()        // same as calling handle()
----

Pausing suits bursts of programmatic writes -- for example while restoring a form from storage -- where you
want a single reaction afterwards instead of one per write, without rebuilding the watcher. To discard the
changes instead, write them while the watcher is stopped and create a new one afterwards.

== Worked example: debounced task search

The running example of this section is a small task list. Its search box needs the classic combination of
watcher features: react to the query, wait for the user to stop typing, cancel a request that is already out of
date, and never let an old answer overwrite a new one. A composable keeps the watcher next to the state it
serves (see xref:web/vue/composables.adoc[]):

[source,ts]
----
// src/composables/useTaskSearch.ts
import { ref, watch, onWatcherCleanup } from 'vue'

export interface Task { id: number; title: string; done: boolean }

export function useTaskSearch(delay = 300) {
  const query = ref('')
  const results = ref<Task[]>([])
  const status = ref<'idle' | 'waiting' | 'loading' | 'error'>('idle')

  watch(query, (q) => {
    if (!q.trim()) {
      results.value = []
      status.value = 'idle'
      return
    }
    status.value = 'waiting'
    const controller = new AbortController()
    const timer = setTimeout(async () => {
      status.value = 'loading'
      try {
        const res = await fetch(`/api/tasks?q=${encodeURIComponent(q)}`, { signal: controller.signal })
        results.value = await res.json()
        status.value = 'idle'
      } catch (e) {
        if ((e as Error).name !== 'AbortError') status.value = 'error'
      }
    }, delay)
    onWatcherCleanup(() => {
      clearTimeout(timer)
      controller.abort()
    })
  })

  return { query, results, status }
}
----

Every keystroke runs the callback again, but first Vue runs the cleanup registered by the *previous* run: the
pending timer is cleared (that is the debounce) and an in-flight request is aborted (that is the stale-response
protection). `onWatcherCleanup` is called synchronously, before any `await`, as the API requires. Cleanup also
runs when the watcher is stopped, so unmounting the component cancels the last request too.

A test drives it with fake timers and a stubbed `fetch`:

[source,ts]
----
import { it, expect, vi } from 'vitest'
import { nextTick } from 'vue'
import { useTaskSearch } from '@/composables/useTaskSearch'

it('debounces and aborts stale requests', async () => {
  vi.useFakeTimers()
  const signals: AbortSignal[] = []
  vi.stubGlobal('fetch', vi.fn((_url: string, init: RequestInit) => {
    signals.push(init.signal!)
    return new Promise(() => {})            // never resolves: the request stays in flight
  }))

  const { query } = useTaskSearch(10)
  query.value = 'a'
  await nextTick()
  vi.advanceTimersByTime(10)                // first request leaves
  query.value = 'ab'
  await nextTick()                          // cleanup of the first run executes here

  expect(signals[0].aborted).toBe(true)
})
----

== Watcher pitfalls

* **Reads after an `await` are not tracked** by `watchEffect`. Read every dependency first, or use `watch` with
  an explicit source.
* **A getter that returns an object is shallow.** `+watch(() => state.profile, cb)+` fires when `profile` is
  replaced, not when `profile.name` changes; add `+{ deep: true }+` (or a depth number) to see nested writes.
* **A reactive object source is deep, and old equals new.** Both arguments are the same mutated object, so you
  cannot diff them; watch a getter that returns a copy if you need the previous state.
* **Do not mirror state.** A watcher that only assigns `b.value = f(a.value)` is a
  xref:web/vue/computed-properties.adoc[computed property] written the long way, and it renders one tick late.
* **Create watchers synchronously** in `setup`, or keep the stop handle, as described above.
* **Avoid `flush: 'sync'`** unless the callback must run inside the write; it defeats batching.

== Options API contrast

The Options API exposes `watch:` keyed by the watched property, with a method, a string method name, or an
options object as the value. See https://vuejs.org/api/options-state.html#watch[the `watch` option].

[source,js]
----
export default {
  data() {
    return { question: '', form: { email: '' } }
  },
  watch: {
    question(newVal, oldVal) { /* ... */ },
    form: {
      handler(val) { /* ... */ },
      deep: true,
      immediate: true
    },
    'form.email'(val) { /* dotted path as a string key */ }
  }
}
----

`this.$watch()` is the imperative equivalent and returns a stop function.

== watch vs. computed

A xref:web/vue/computed-properties.adoc[computed property] *returns a cached value* and should be a pure
function of other state. A watcher *performs an effect* and returns nothing. If you catch yourself assigning
one ref inside a watcher purely to mirror another ref, you want a computed.
