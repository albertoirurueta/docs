The official https://vuejs.org/style-guide/[Vue Style Guide] ranks conventions by how much trouble ignoring
them causes, and the https://vuejs.org/guide/extras/composition-api-faq.html[Composition API FAQ] explains
why the modern authoring style is shaped the way it is. This page summarises both and adds component-design
guidance that the style guide deliberately leaves out.

== The Style Guide priority levels

The guide sorts every rule into four buckets. In practice you enforce the first two and treat the third as a
team decision.

=== Priority A -- Essential (error prevention)

Breaking these invites real bugs. See https://vuejs.org/style-guide/rules-essential.html[Essential rules].

* **Multi-word component names** -- `TodoItem`, not `Todo`, so a component never collides with a current or
  future HTML element. (The root `App` and framework components like `RouterView` are the sanctioned
  exceptions.)
* **Detailed prop definitions** -- at minimum a type; in committed code also `required` or a `default`, and a
  `validator` where the value is constrained. Fully typed `defineProps` satisfies this.
* **Keyed `v-for`** -- always bind a stable, unique `:key` so Vue patches the list correctly and preserves
  component state.
* **Avoid `v-if` with `v-for` on the same element** -- their precedence is a trap and it re-evaluates the
  condition per iteration. Filter in a computed, or move the `v-if` to a wrapper.

[source,vue]
----
<script setup lang="ts">
import { computed } from 'vue'

interface Task { id: number; title: string; done: boolean }
const props = defineProps<{ tasks: Task[] }>()
const pending = computed(() => props.tasks.filter(t => !t.done))
</script>

<template>
  <ul>
    <TaskRow v-for="task in pending" :key="task.id" :task="task" />
  </ul>
</template>
----

=== Priority B -- Strongly Recommended (readability)

Improve consistency across a codebase. See
https://vuejs.org/style-guide/rules-strongly-recommended.html[Strongly Recommended rules].

* **Component-scoped styling** -- `<style scoped>` in SFCs, CSS Modules, or a class-based convention like
  BEM; only `App` and layout-level elements get truly global styles.
* **Component files** -- one component per file, named in `PascalCase.vue`.
* **Base/presentational components** share a prefix (`BaseButton`, `AppButton`, `VButton`).
* **Single-instance components** get a `The` prefix (`TheHeader`, `TheSidebar`).
* **Name components from most general to most specific** -- `SearchButtonClear`, not `ClearSearchButton`,
  so related files sort together.
* **Self-close components with no content** -- `<UserCard />` in SFC templates.
* **PascalCase component names in templates**, and full words over abbreviations (`UserSettings`, not
  `UProf`).
* **Use directive shorthands always or never** -- `:` for `v-bind:`, `@` for `v-on:` and `#` for `v-slot:`.
  Mixing the two forms in one codebase is the violation; the style guide's own examples, and the
  `vue/v-bind-style` rule, use the shorthand.
* **Multi-attribute elements span multiple lines**, one attribute per line.
* **Keep template expressions simple** -- move anything beyond a property access or a single call into a
  computed or method.

=== Priority C -- Recommended (arbitrary but consistent)

Where more than one option is equally fine, pick one project-wide so that every file looks alike. See
https://vuejs.org/style-guide/rules-recommended.html[Recommended rules].

* **Component/instance options order** -- a consistent order for the Options API (`name`, `props`, `emits`,
  `data`, `computed`, `watch`, lifecycle hooks, `methods`, `render`); the same idea applies to the contents of
  `<script setup>`: imports, props and emits, state, computed, watchers, functions, hooks.
* **Element attribute order** -- for example `v-for`, then `v-if`, then `id`, then `ref` and `key`, then
  `v-model`, other directives and plain attributes, then events, and `v-html` / `v-text` last.
* **Empty lines in component/instance options** -- separate multi-line options with a blank line.
* **Single-file component top-level element order** -- keep `<script>`, `<template>` and `<style>` in the same
  order in every file (`<script>` and `<template>` before `<style>` is the usual choice).

=== Priority D -- Use with Caution (risky patterns)

These features exist for good reasons, but they are the usual source of problems; use them only for a
deliberate reason. See https://vuejs.org/style-guide/rules-use-with-caution.html[Use with caution].

* **Element selectors with `scoped`** -- `+p { ... }+` in a scoped style is slow because the browser has to check
  every matching element for the scope attribute; prefer class selectors.
* **Implicit parent-child communication** -- a child that mutates a prop, or one that reaches up with `$parent`,
  hides the data flow. Prefer props down and events up.
* **Non-flux global state management** -- global state belongs in a store such as Pinia (see
  xref:web/vue/state-management.adoc[]), not in `this.$root` or an event bus.

Enforce A and B automatically with https://eslint.vuejs.org/[`eslint-plugin-vue`]; its `flat/essential` and
`flat/strongly-recommended` presets cover the first two levels.

== Component design

The style guide stops at mechanics; these principles decide where a component boundary should go.

=== Single responsibility

A component should do one thing. When `setup` grows past a screen or so, or a name needs "and" to describe
it, split it -- extract child components for distinct UI regions and
xref:web/vue/composables.adoc[composables] for reusable stateful logic.

=== Props down, events up

Data flows one way: a parent passes state down as props, a child requests change by emitting an event. A
child never mutates a prop (Vue warns) and never reaches into `$parent`.

[source,vue]
----
<script setup lang="ts">
const props = defineProps<{ quantity: number }>()
const emit = defineEmits<{ 'update:quantity': [value: number] }>()
// v-model:quantity on the parent wires these together
</script>

<template>
  <button @click="emit('update:quantity', props.quantity - 1)">-</button>
  <span>{{ quantity }}</span>
  <button @click="emit('update:quantity', props.quantity + 1)">+</button>
</template>
----

=== Slots vs. props

Pass **data** as props; pass **markup** as slots. If a prop's value is a string of HTML, or you find
yourself adding `iconBefore` / `iconAfter` / `footerText` props, switch to named and scoped slots. See
https://vuejs.org/guide/components/slots.html[Slots].

[source,vue]
----
<template>
  <Card>
    <template #header><h2>{{ title }}</h2></template>
    <p>{{ body }}</p>
    <template #actions="{ close }">
      <button @click="close">Dismiss</button>
    </template>
  </Card>
</template>
----

=== Container vs. presentational

Separate components that *fetch and own state* (containers: talk to the store, the router, the API) from
components that *only render props and emit events* (presentational: no I/O, trivial to test and to reuse).
Keep presentational components the majority.

=== Folder structure

A common layout: `components/` for shared presentational components, `views/` (or `pages/`) for
route-level containers, `composables/` for `useX` functions, `stores/` for Pinia stores, and feature
folders that co-locate a feature's own components, composable, and store. Consistency matters more than the
exact names -- see https://vuejs.org/guide/scaling-up/sfc.html[Single-File Components].

== Worked example: from a violating component to a clean one

The running example is a task list. Here is a first draft written quickly, in the way style-guide rules get
broken in practice:

[source,vue]
----
<!-- Todo.vue -->
<script setup>
const props = defineProps(['items'])
</script>

<template>
  <ul>
    <li v-for="item in props.items" v-if="item.visible">{{ item.title }}</li>
  </ul>
  <task-row :task-id="1" v-bind:Title="'x'"/>
  <TaskRow></TaskRow>
</template>
----

Running `eslint-plugin-vue` with its `flat/recommended` preset reports (columns trimmed):

[source,console]
----
Todo.vue
   1:1   error    Component name "Todo" should always be multi-word             vue/multi-word-component-names
   2:28  warning  Prop "items" should define at least its type                  vue/require-prop-types
   7:5   error    Elements in iteration expect to have 'v-bind:key' directives  vue/require-v-for-key
   7:37  error    ... You should not mix 'v-for' with 'v-if'                    vue/no-use-v-if-with-v-for
   9:26  warning  Attribute 'v-bind:Title' must be hyphenated                   vue/attribute-hyphenation
   9:26  warning  Unexpected 'v-bind' before ':'                                vue/v-bind-style
  10:12  warning  Require self-closing on Vue.js custom components (<TaskRow>)  vue/html-self-closing
----

Each message names the rule that produced it, and the rules correspond to the priority levels above: multi-word
names, keys, `v-if` with `v-for` and prop types are Priority A; attribute hyphenation, directive shorthand and
self-closing components are Priority B. Fixing them also pulls the component towards the design
principles below -- typed props, a computed instead of `v-if` next to `v-for`, and a separate row component:

[source,vue]
----
<!-- TaskRow.vue : presentational -->
<script setup lang="ts">
export interface Task { id: number; title: string; done: boolean }

defineProps<{ task: Task }>()
const emit = defineEmits<{ toggle: [id: number] }>()
</script>

<template>
  <li :class="{ done: task.done }">
    <label>
      <input
        type="checkbox"
        :checked="task.done"
        @change="emit('toggle', task.id)"
      >
      {{ task.title }}
    </label>
  </li>
</template>
----

[source,vue]
----
<!-- TaskListView.vue : one responsibility, the list -->
<script setup lang="ts">
import { computed } from 'vue'
import TaskRow, { type Task } from './TaskRow.vue'

const props = defineProps<{ tasks: Task[] }>()
const emit = defineEmits<{ toggle: [id: number] }>()

const pending = computed(() => props.tasks.filter(t => !t.done))
</script>

<template>
  <ul>
    <TaskRow
      v-for="task in pending"
      :key="task.id"
      :task="task"
      @toggle="emit('toggle', $event)"
    />
  </ul>
</template>
----

With the `eslint.config.js` shown in xref:web/vue/tooling-and-project-setup.adoc[] and the `flat/recommended`
preset, linting both files prints nothing, and `vue-tsc` passes. The two components also show the *container /
presentational* split from the previous section: neither fetches data or touches a store, so each is tested
with props and emitted events alone (see xref:web/vue/testing.adoc[]).

=== How the pieces connect

[mermaid]
....
flowchart TB
    store["Pinia store<br/>(owns the task list)"] --> view["TaskPage<br/>container: reads the store,<br/>handles events"]
    view -->|"props: tasks"| list["TaskListView<br/>filters, one job"]
    list -->|"props: task"| row["TaskRow<br/>renders one task"]
    row -->|"emit: toggle id"| list
    list -->|"emit: toggle id"| view
    view -->|"calls action"| store
....

Data flows down as props, change requests flow up as events, and only the container knows the store exists.
The same shape scales: a new view reuses `TaskListView` with different data and no changes to the row.

=== Automating the rules

A style guide that is not enforced drifts. Run `eslint` in CI with at least the `flat/essential` preset (add
`flat/strongly-recommended` once Priority B warnings are cleared), keep `vue-tsc` in the type-check step, and
let a formatter such as Prettier decide whitespace so that review comments are about design, not layout. Rules
that need a team decision -- the Priority C ones -- should be written into the project's contributing notes once,
so they stop coming up in review.

== Why the Composition API

The https://vuejs.org/guide/extras/composition-api-faq.html[Composition API FAQ] gives the rationale, in
short:

* **Logic reuse** -- composables replace mixins and renderless components without their namespace clashes,
  implicit dependencies, or wrapper-component overhead.
* **Better organisation** -- code for one concern (search, pagination, drag-and-drop) sits together in one
  composable instead of being scattered across `data` / `methods` / `watch` / lifecycle options.
* **Type inference** -- `ref`, `computed`, props, and emits are plain values and functions, so TypeScript
  infers them without the `this`-typing machinery the Options API needs (see xref:web/vue/typescript.adoc[]).
* **Smaller production bundles** -- `<script setup>` code minifies better and its variable names can be
  mangled.

The FAQ is explicit that the **Options API is not deprecated** and remains a good fit for smaller apps and
for developers who prefer its structure. New code and libraries in the ecosystem default to
`<script setup>`, which is why every example in this section uses it.
