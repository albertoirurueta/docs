= Security and Accessibility
:description: Vue's built-in output escaping and the injection risks that remain -- v-html, URLs, attributes, styles, dynamic components, template compilation, SSR -- followed by building accessible Vue templates with semantic markup, focus management, ARIA bindings, labelled controls, and automated testing.
:keywords: Vue security, v-html XSS, template injection, URL injection, CSP Vue, SSR security, Vue accessibility, semantic HTML, skip link, route focus management, aria bindings, form labels, vue-axe, Lighthouse

include::partial$ai-disclaimer.adoc[]

Vue removes the most common cross-site-scripting hole by escaping interpolated content automatically, and its
component model makes accessible markup the path of least resistance. Both still need deliberate attention at
the edges. This page follows the https://vuejs.org/guide/best-practices/security.html[Security] and
https://vuejs.org/guide/best-practices/accessibility.html[Accessibility] guides.

== Security

=== Built-in HTML escaping

Text bindings -- `+{{ mustache }}+`, `v-text`, and `:` attribute bindings -- are escaped before they reach the
DOM, so user data rendered this way cannot introduce markup or script. The
https://vuejs.org/guide/best-practices/security.html#what-vue-does[What Vue Does] section spells this out.

[source,vue]
----
<script setup lang="ts">
const comment = `<img src=x onerror="alert(document.cookie)">`
</script>

<template>
  <!-- rendered as literal text, no image element, no script -->
  <p>{{ comment }}</p>
  <p :title="comment">hover me</p>
</template>
----

=== `v-html` -- the injection you opt into

https://vuejs.org/api/built-in-directives.html#v-html[`v-html`] sets `innerHTML` verbatim and bypasses all
escaping. Never point it at user-supplied or third-party content. When you must render rich text, sanitise
first with a vetted library and treat its allowlist as security-critical:

[source,vue]
----
<script setup lang="ts">
import { computed } from 'vue'
import DOMPurify from 'dompurify'
const props = defineProps<{ markdownHtml: string }>()
const safe = computed(() => DOMPurify.sanitize(props.markdownHtml))
</script>

<template>
  <article v-html="safe" />
</template>
----

=== URL, attribute, style, and `:is` injection

* **URLs** -- a bound `:href` or `:src` of `javascript:alert(1)` executes on click. Validate the scheme
  (`https:` / `mailto:` / relative) before binding, or run URLs through a sanitiser. The
  https://vuejs.org/guide/best-practices/security.html#potential-dangers[Potential Dangers] section covers
  this.
* **Attributes** -- never bind user data into `:srcdoc`, `:formaction`, or event-handler-like attributes.
  Binding user text into an ordinary attribute such as `:title` is fine (it is escaped).
* **Styles** -- do not interpolate user input into `:style` strings or `<style>` blocks; CSS can load
  resources and, in old engines, run expressions. Bind individual, validated properties instead.
* **Dynamic components** -- `+<component :is="...">+` with a user-controlled value can mount an arbitrary
  registered component or, with a string, an arbitrary element. Resolve the value against an explicit
  allowlist map, never pass it straight through.

[source,vue]
----
<script setup lang="ts">
import { computed } from 'vue'
import ChartView from './ChartView.vue'
import TableView from './TableView.vue'

const props = defineProps<{ view: string; userLink: string }>()

const views = { chart: ChartView, table: TableView } as const
// hasOwn, not `views[key]` alone: 'constructor' and '__proto__' would otherwise resolve to Object.prototype members
const current = computed(() =>
  Object.hasOwn(views, props.view) ? views[props.view as keyof typeof views] : TableView
)

function safeHref(raw: string) {
  return /^(https?:|mailto:|\/)/.test(raw) ? raw : '#'
}
</script>

<template>
  <component :is="current" />
  <a :href="safeHref(props.userLink)">link</a>
</template>
----

=== Template injection

Vue templates are code. Never build a template string from user input and hand it to `compile()`,
`h()` with a user-derived type, or a runtime `template` option. Keep templates static and drive them with
*data*.

=== Providing server data safely

Injecting state into the page for the client to pick up is a classic XSS sink. Serialise with a
context-aware tool, not `JSON.stringify` alone (which leaves `</script>` and `<!--` intact):

[source,js]
----
import serialize from 'serialize-javascript'

const html = `<script>window.__INITIAL__ = ${serialize(state, { isJSON: true })}<` + `/script>`
----

On the client, read it from a `+data-*+` attribute or a typed global -- do not `eval` it.

=== Content Security Policy

Vue's production runtime needs no `unsafe-eval`: SFCs are compiled to render functions at build time. Ship a
strict policy (`script-src 'self'`; nonce or hash for any inline bootstrap) and keep the **runtime-only**
Vue build so the `new Function` template compiler is never bundled. Avoid runtime string templates, which
would require `unsafe-eval`.

=== SSR-specific concerns

* Escape interpolations into the HTML *shell* (the parts outside the app's mount point) yourself -- Vue only
  escapes what it renders.
* Never render request-derived HTML with `v-html` on the server; a reflected payload becomes stored-looking
  XSS on first paint.
* Keep per-request state on a fresh app instance; a module-level singleton leaks one user's data into
  another's response.
* Validate that hydration data matches what the client will re-render, so an attacker cannot smuggle markup
  through a mismatch.

For the browser mechanism that governs which origins a Vue app may call, and how to validate origins on the
API, see xref:web/cors.adoc[].

=== Which sink for which content

Most Vue security decisions reduce to one question: where does this string come from, and where does it go? The
diagram turns that into a lookup:

[mermaid]
....
flowchart TD
    start["a string reaches a template"] --> src{"who controls<br/>the string?"}
    src -- "only your own code" --> any["any binding is fine"]
    src -- "users, other sites, an API" --> sink{"where does it go?"}
    sink -- "text or an ordinary attribute" --> esc["use mustache or v-bind<br/>Vue escapes it"]
    sink -- "href, src, or a URL" --> url["parse with new URL<br/>allow https, http, mailto only"]
    sink -- "HTML markup" --> html["sanitise with DOMPurify and an allowlist<br/>then v-html"]
    sink -- "component or tag name" --> allow["look up in an own-property allowlist"]
    sink -- "style or template string" --> nobind["do not bind it<br/>map to validated values instead"]
....

=== Worked example: a comment box

A comment component receives a body that may contain a little formatting, and a link supplied by the author. It shows
the body twice, once as text and once as sanitised HTML, and validates the link by parsing it rather than with a
pattern:

[source,vue]
----
<script setup lang="ts">
import { computed } from 'vue'
import DOMPurify from 'dompurify'

const props = defineProps<{ body: string; link: string }>()

function safeHref(raw: string) {
  try {
    const url = new URL(raw, 'https://app.example.com')      // relative links resolve against the app origin
    return ['https:', 'http:', 'mailto:'].includes(url.protocol) ? raw : '#'
  } catch {
    return '#'
  }
}

const cleanBody = computed(() =>
  DOMPurify.sanitize(props.body, { ALLOWED_TAGS: ['b', 'i', 'em', 'strong', 'a', 'p'], ALLOWED_ATTR: ['href'] })
)
</script>

<template>
  <section>
    <h3 class="text">{{ body }}</h3>
    <div class="html" v-html="cleanBody" />
    <a class="link" :href="safeHref(link)">link</a>
  </section>
</template>
----

Mounted in jsdom with a hostile body -- an `<img onerror>`, a bold tag, an anchor with a `javascript:` URL and a
`<script>` element -- and a `javascript:` link, the component produced:

[source,text]
----
text   <h3 class="text">&lt;img src=x onerror="alert(1)"&gt;&lt;b&gt;bold&lt;/b&gt;&lt;a href="javascript:alert(1)"&gt;x&lt;/a&gt;&lt;script&gt;...</h3>
html   <div class="html"><b>bold</b><a>x</a></div>
link   href="#"
----

The mustache binding showed the whole payload as inert text. The sanitiser kept the allowed `<b>`, dropped the image
and the script, and stripped the `javascript:` `href` from the anchor while keeping its text. The `javascript:` link
was replaced by `#`, whereas `/todos/1` and `https://example.org/a` passed through unchanged. For contrast, the same
body bound with an unsanitised `v-html` produced a live `+<img src="x" onerror="...">+` element: that is the entire
difference between the two bindings.

=== Safe state serialisation, verified

The serialisation advice above is easy to verify. For the state
`+{ note: '</script><script>alert(1)</script>' }+`, `JSON.stringify` emits the closing tag verbatim, which ends the
surrounding `<script>` element and lets the rest run. `serialize-javascript` with `isJSON: true` escapes the
characters that matter:

[source,text]
----
JSON.stringify:  {"note":"</script><script>alert(1)</script>"}
serialize:       {"note":"\u003C\u002Fscript\u003E\u003Cscript\u003Ealert(1)\u003C\u002Fscript\u003E"}
----

The second form is still valid JavaScript and parses back to the original string, but contains no `<` or `/`.

=== Allowlist lookups need own-property checks

A plain object used as an allowlist has a prototype. Looking up `views[name]` with the attacker-chosen name
`constructor` returns `Object` (a function), and `+__proto__+` returns the prototype object, which Vue then tries to
render as a component. The corrected `current` computed above uses `Object.hasOwn`, so only the keys you wrote can
match; a `Map` or an object created with `Object.create(null)` works equally well.

== Accessibility

Vue renders plain HTML, so accessibility is mostly a matter of authoring good templates. The
https://vuejs.org/guide/best-practices/accessibility.html[Accessibility] guide is the reference.

=== Semantic templates

Use landmark and heading elements instead of styled `+<div>+` elements; component boundaries do not have to match
element boundaries.

[source,vue]
----
<template>
  <header>
    <nav aria-label="Primary"><!-- ... --></nav>
  </header>
  <main>
    <h1>{{ pageTitle }}</h1>
    <article>
      <h2>{{ section.title }}</h2>
    </article>
  </main>
  <footer><!-- ... --></footer>
</template>
----

=== Skip link

Give keyboard and screen-reader users a way past repeated navigation. See
https://vuejs.org/guide/best-practices/accessibility.html#skip-link[Skip link].

[source,vue]
----
<template>
  <a class="skip-link" href="#main">Skip to main content</a>
  <!-- ...nav... -->
  <main id="main" tabindex="-1"><RouterView /></main>
</template>

<style>
.skip-link {
  position: absolute;
  transform: translateY(-120%);
}
.skip-link:focus {
  transform: translateY(0);
}
</style>
----

=== Route-change focus management

An SPA navigation does not move focus or announce the new page. After each route change, move focus to the
main region or the new `<h1>`:

[source,vue]
----
<script setup lang="ts">
import { useRoute } from 'vue-router'
import { watch, useTemplateRef } from 'vue'

const main = useTemplateRef<HTMLElement>('main')
const route = useRoute()

watch(() => route.fullPath, () => {
  main.value?.focus()
})
</script>

<template>
  <main ref="main" tabindex="-1">
    <RouterView />
  </main>
</template>
----

Pair it with a visually-hidden `aria-live="polite"` region that you update with the new page title so the
change is announced.

=== `+aria-*+` bindings

Bind ARIA state from reactive data; keep it in sync with what the user sees. See
https://vuejs.org/guide/best-practices/accessibility.html#semantic-forms[Semantic Forms] for the form
patterns.

[source,vue]
----
<script setup lang="ts">
const open = ref(false)
const busy = ref(false)
</script>

<template>
  <button
    :aria-expanded="open"
    aria-controls="panel"
    @click="open = !open"
  >
    Details
  </button>
  <section id="panel" v-show="open" :aria-busy="busy">...</section>
</template>
----

=== Labelled form controls

Every control needs a programmatic name -- a `<label for>` tied to a unique `id`, or `aria-label` /
`aria-labelledby`. https://vuejs.org/api/composition-api-helpers.html#useid[`useId`] generates SSR-stable
ids:

[source,vue]
----
<script setup lang="ts">
import { useId } from 'vue'
const nameId = useId()
const name = defineModel<string>()
</script>

<template>
  <label :for="nameId">Full name</label>
  <input :id="nameId" v-model="name" type="text" autocomplete="name" />
</template>
----

Group related controls in a `<fieldset>` with a `<legend>`; associate error text with `aria-describedby`.

=== Testing

Automated tools catch a large share of issues -- run them, then still keyboard-test and screen-reader-test by
hand:

* **`vue-axe`** -- a dev-only plugin that runs axe-core against the live component tree and logs violations
  to the console.
* **Lighthouse** -- the Accessibility category in Chrome DevTools or CI (`@lhci/cli`) for a per-page score
  and specific failures.
* **`@axe-core/playwright`** or `jest-axe` / `vitest-axe` -- assert zero violations inside component and
  end-to-end tests.

[source,js]
----
// main.ts (development only)
if (import.meta.env.DEV) {
  const { default: VueAxe } = await import('vue-axe')
  app.use(VueAxe)
}
----

For the standards behind these checks -- WCAG, the POUR principles, conformance levels, and the legal
requirements -- see xref:web/accessibility.adoc[].

=== Worked example: an accessible add-task form

The to-do app's form combines the building blocks above: a programmatically labelled input, an error that is both
visible and associated with the field, and a live region that announces the result. It uses `useId()` so the ids are
stable between server and client:

[source,vue]
----
<script setup lang="ts">
import { ref, useId } from 'vue'

const emit = defineEmits<{ add: [text: string] }>()

const fieldId = useId()
const errorId = useId()
const text = ref('')
const error = ref('')
const status = ref('')          // announced by the live region

function submit() {
  if (!text.value.trim()) {
    error.value = 'Enter a description for the task.'
    status.value = ''
    return
  }
  error.value = ''
  emit('add', text.value.trim())
  status.value = `Added "${text.value.trim()}"`
  text.value = ''
}
</script>

<template>
  <form novalidate @submit.prevent="submit">
    <label :for="fieldId">New task</label>
    <input
      :id="fieldId"
      v-model="text"
      type="text"
      :aria-invalid="error ? 'true' : undefined"
      :aria-describedby="error ? errorId : undefined"
    />
    <p v-if="error" :id="errorId" class="error">{{ error }}</p>
    <button type="submit">Add</button>
    <p role="status" class="sr-only">{{ status }}</p>
  </form>
</template>

<style>
.sr-only {
  position: absolute;
  width: 1px;
  height: 1px;
  overflow: hidden;
  clip-path: inset(50%);
  white-space: nowrap;
}
</style>
----

A Vue Test Utils test of the component asserts the accessibility contract directly instead of only the visuals:

* the `<label for>` equals the input's `id`;
* after submitting an empty field, the input has `aria-invalid="true"`, its `aria-describedby` equals the id of the
  error paragraph, and the paragraph holds the message;
* after entering text and submitting, both attributes are gone (binding `undefined` removes an attribute, whereas
  `false` renders the string `"false"` on an ARIA attribute), the `add` event carries the trimmed text, and the
  `role="status"` element reads `Added "Write docs"`.

Binding `undefined` rather than `'false'` for `aria-invalid` is deliberate: an absent attribute and
`aria-invalid="false"` mean the same thing to assistive technology, and omitting it keeps the markup clean.

The route announcer from the focus-management section can be tested the same way. With a router whose records carry a
`meta.title`, a component that watches `route.fullPath`, writes `Navigated to Todos` into an `aria-live="polite"`
paragraph and calls `focus()` on the `tabindex="-1"` main element ends up with the message set and
`document.activeElement` being the `<main>`, after `await router.push('/todos')` and `flushPromises()`. Mount with
`attachTo: document.body`, because an element that is not in the document cannot receive focus.
