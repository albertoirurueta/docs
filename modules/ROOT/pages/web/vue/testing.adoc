= Testing
:description: Testing Vue applications -- the testing pyramid, Vitest for a Vite project, component testing with Vue Test Utils (mount, props, emitted, find, trigger, setValue, nextTick, stubs), testing composables, testing with Router and Pinia, snapshots, and end-to-end testing with Cypress or Playwright.
:keywords: Vue testing, Vitest, Vue Test Utils, mount, shallowMount, emitted, findComponent, trigger, setValue, nextTick, flushPromises, stubs, testing composables, testing Pinia, testing Vue Router, snapshot testing, Cypress, Playwright, end-to-end

include::partial$ai-disclaimer.adoc[]

Vue tests split into *unit* tests (plain functions and composables), *component* tests (a component mounted
in isolation), and *end-to-end* tests (the real app in a real browser). The Vue guide's
https://vuejs.org/guide/scaling-up/testing.html[Testing] page frames the choices; this page is a practical
tour.

== The testing pyramid

Write many fast unit tests, a moderate number of component tests, and a few slow end-to-end tests. Unit and
component tests run in milliseconds under Node and catch logic and rendering bugs; end-to-end tests are the
only ones that exercise routing, real network calls, and the browser, so keep them focused on critical user
journeys.

The cost of a test grows with the amount of real machinery it exercises, so each layer answers a different
question:

[mermaid]
....
flowchart TB
    e2e["End-to-end (few)<br/>real browser, real routing and network<br/>Does the journey work?"]
    comp["Component tests (some)<br/>one mounted component in a simulated DOM<br/>Does it render and react correctly?"]
    unit["Unit tests (many)<br/>functions, stores, composables<br/>Is the logic right?"]
    unit --> comp --> e2e
....

== Vitest

https://vitest.dev/[Vitest] is the recommended runner for a Vite project: it reuses your `vite.config`
(aliases, plugins, `@vitejs/plugin-vue`) so components compile the same way in tests as in the app.
`create-vue` can add it; manually:

[source,bash]
----
npm i -D vitest @vue/test-utils happy-dom
----

[source,js]
----
// vitest.config.js
import { defineConfig, mergeConfig } from 'vitest/config'
import viteConfig from './vite.config'

export default mergeConfig(viteConfig, defineConfig({
  test: {
    environment: 'happy-dom',   // a DOM implementation for component tests
    globals: true,              // describe/it/expect without imports
  },
}))
----

`happy-dom` is the lighter option; `jsdom` is the more complete one and the better choice when a test relies on
less common DOM behaviour. Swap with `npm i -D jsdom` and `environment: 'jsdom'`. Add `"test": "vitest"` to
`package.json` scripts; `vitest run` runs once (CI) and `vitest --coverage` reports coverage when a coverage
provider is installed.

A test file:

[source,js]
----
import { describe, it, expect } from 'vitest'
import { add } from '@/utils/math'

describe('add', () => {
  it('sums two numbers', () => {
    expect(add(2, 3)).toBe(5)
  })
})
----

== Component testing with Vue Test Utils

https://test-utils.vuejs.org/[Vue Test Utils] mounts a component and returns a *wrapper* with a query and
interaction API.

[source,js]
----
import { mount } from '@vue/test-utils'
import Stepper from '@/components/Stepper.vue'

it('increments and emits the new value', async () => {
  const wrapper = mount(Stepper, {
    props: { modelValue: 1, max: 3 },
  })

  await wrapper.find('[data-test="inc"]').trigger('click')

  expect(wrapper.text()).toContain('2')
  expect(wrapper.emitted('update:modelValue')).toEqual([[2]])
})
----

Key wrapper methods:

* `mount` renders the component and its children; `shallowMount` stubs child components so the test is
  isolated to this component's own template.
* `find` / `findAll` take a CSS selector and return DOM wrappers; `findComponent` / `findAllComponents`
  take a component and return component wrappers.
* `trigger('click')`, `trigger('keydown.enter')` dispatch DOM events; `setValue('text')` sets an input's
  value and fires `input`.
* `emitted()` records every custom event -- `emitted('submit')` is an array of argument arrays, one per
  emission.
* `props()`, `text()`, `html()`, `classes()`, `isVisible()` inspect the render.

=== Waiting for updates

Vue applies DOM updates asynchronously. `trigger`, `setValue`, and `setProps` return promises you can
`await`; for state changed directly, `await nextTick()`; for pending microtasks such as resolved fetches,
`await flushPromises()`:

[source,js]
----
import { flushPromises, mount } from '@vue/test-utils'

const wrapper = mount(UserCard, { props: { id: 7 } })
await flushPromises()               // let the mocked API promise settle
expect(wrapper.text()).toContain('Ada Lovelace')
----

=== Stubs, mocks, and slots

Provide `global.stubs` to replace heavy children, `global.mocks` for injected globals, and `slots` to pass
slot content:

[source,js]
----
const wrapper = mount(Layout, {
  slots: {
    default: '<p>body</p>',
    header: HeaderStub,
  },
  global: {
    stubs: { RouterLink: true },
    mocks: { $t: (key) => key },
  },
})
----

Mock modules (an API client, `vue-router`) with `vi.mock('@/api')` from Vitest.

== Testing composables

A composable that uses no lifecycle hooks or injection can be called directly in a test:

[source,js]
----
import { useCounter } from '@/composables/useCounter'

it('counts', () => {
  const { count, inc } = useCounter()
  inc()
  expect(count.value).toBe(1)
})
----

If it calls `onMounted`, `provide`/`inject`, or `getCurrentInstance`, mount it inside a throwaway *host
component* so it runs in a real component context:

[source,js]
----
import { mount } from '@vue/test-utils'

function withSetup(composable) {
  let result
  const Comp = { setup() { result = composable(); return () => {} } }
  const wrapper = mount(Comp)
  return { result, wrapper }
}
----

See https://vuejs.org/guide/scaling-up/testing.html#testing-composables[Testing composables].

== Testing with Router and Pinia

Install a real router with in-memory history and `await router.isReady()`; install a fresh Pinia per test.
`@pinia/testing` provides `createTestingPinia()`, which stubs actions by default so you can assert they were
called:

[source,js]
----
import { createTestingPinia } from '@pinia/testing'
import { createRouter, createMemoryHistory } from 'vue-router'

const router = createRouter({ history: createMemoryHistory(), routes })

const wrapper = mount(App, {
  global: {
    plugins: [router, createTestingPinia()],
  },
})
await router.isReady()
----

== Worked example: testing the task list

The running example is the task list from xref:web/vue/state-management.adoc[], made of a presentational
`TaskItem`, a container `TaskList` that talks to the Pinia store, and a store that loads tasks with `fetch`.
Each layer gets the kind of test it deserves.

[source,vue]
----
<!-- src/components/TaskItem.vue -->
<script setup lang="ts">
import type { Task } from '@/stores/tasks'
defineProps<{ task: Task }>()
const emit = defineEmits<{ toggle: [id: number] }>()
</script>

<template>
  <li :class="{ done: task.done }">
    <label>
      <input type="checkbox" :checked="task.done" @change="emit('toggle', task.id)">
      {{ task.title }}
    </label>
  </li>
</template>
----

[source,vue]
----
<!-- src/components/TaskList.vue -->
<script setup lang="ts">
import { ref, onMounted } from 'vue'
import { storeToRefs } from 'pinia'
import { useTaskStore } from '@/stores/tasks'
import TaskItem from './TaskItem.vue'

const store = useTaskStore()
const { visible, openCount, loading } = storeToRefs(store)
const title = ref('')

function submit() {
  if (!title.value.trim()) return
  store.add(title.value.trim())
  title.value = ''
}

onMounted(() => store.load())
</script>

<template>
  <form @submit.prevent="submit">
    <input v-model="title" placeholder="What needs doing?" data-test="new-task">
    <button type="submit">Add</button>
  </form>
  <p v-if="loading" data-test="loading">Loading...</p>
  <ul v-else>
    <TaskItem v-for="t in visible" :key="t.id" :task="t" @toggle="store.toggle" />
  </ul>
  <p data-test="count">{{ openCount }} open</p>
</template>
----

=== The store, without any component

A store test needs only an active Pinia. `setActivePinia(createPinia())` in `beforeEach` gives every test a
fresh store, so tests cannot leak state into each other. `$subscribe`, `$patch` and `$onAction` can be asserted
directly:

[source,ts]
----
import { describe, it, expect, beforeEach, vi } from 'vitest'
import { createPinia, setActivePinia } from 'pinia'
import { useTaskStore } from '@/stores/tasks'

describe('task store', () => {
  beforeEach(() => setActivePinia(createPinia()))

  it('derives visible tasks and the open count', () => {
    const s = useTaskStore()
    s.add('write'); s.add('test'); s.toggle(1)
    expect(s.openCount).toBe(1)
    s.filter = 'done'
    expect(s.visible.map(t => t.title)).toEqual(['write'])
  })

  it('reports a failing load and clears the loading flag', async () => {
    const s = useTaskStore()
    vi.stubGlobal('fetch', vi.fn().mockRejectedValue(new Error('boom')))
    await expect(s.load()).rejects.toThrow('boom')
    expect(s.loading).toBe(false)
  })
})
----

=== A presentational component

`TaskItem` has no store, so the test is just props in, events out. `setValue(true)` on a checkbox sets `checked`
and fires `change`:

[source,ts]
----
import { mount } from '@vue/test-utils'
import TaskItem from '@/components/TaskItem.vue'

it('renders the title and emits toggle with the id', async () => {
  const wrapper = mount(TaskItem, { props: { task: { id: 1, title: 'Write docs', done: false } } })

  expect(wrapper.text()).toContain('Write docs')
  await wrapper.find('input').setValue(true)

  expect(wrapper.emitted('toggle')).toEqual([[1]])
})
----

=== The container with a real store

Mount `TaskList` with a real Pinia and a stubbed `fetch`. The component calls `store.load()` in `onMounted`, so
two waits matter: one `nextTick()` for the DOM to show the loading state that `onMounted` just set, and
`flushPromises()` to let the mocked request settle:

[source,ts]
----
import { mount, flushPromises } from '@vue/test-utils'
import { createPinia } from 'pinia'
import { nextTick } from 'vue'
import { vi, it, expect, afterEach } from 'vitest'
import TaskList from '@/components/TaskList.vue'
import TaskItem from '@/components/TaskItem.vue'

const apiTasks = [
  { id: 1, title: 'Write docs', done: false },
  { id: 2, title: 'Run tests', done: true },
]

afterEach(() => vi.unstubAllGlobals())

it('loads, lists and adds tasks', async () => {
  vi.stubGlobal('fetch', vi.fn().mockResolvedValue({ json: async () => apiTasks }))
  const wrapper = mount(TaskList, { global: { plugins: [createPinia()] } })

  await nextTick()
  expect(wrapper.find('[data-test="loading"]').exists()).toBe(true)

  await flushPromises()
  expect(wrapper.findAllComponents(TaskItem)).toHaveLength(2)
  expect(wrapper.get('[data-test="count"]').text()).toBe('1 open')

  await wrapper.get('[data-test="new-task"]').setValue('Ship it')
  await wrapper.get('form').trigger('submit')
  expect(wrapper.findAllComponents(TaskItem)).toHaveLength(3)
})
----

=== The container with a faked store

When the store is already tested, a component test should not re-test it. `createTestingPinia` from
`@pinia/testing` replaces every action with a spy (so `load()` never calls `fetch`), and `initialState` seeds
the state the component renders. Pass `createSpy: vi.fn` when Vitest globals are not enabled:

[source,ts]
----
import { createTestingPinia } from '@pinia/testing'
import { useTaskStore } from '@/stores/tasks'

it('toggles through the store action', async () => {
  const wrapper = mount(TaskList, {
    global: {
      plugins: [createTestingPinia({ createSpy: vi.fn, initialState: { tasks: { tasks: apiTasks } } })],
    },
  })
  const store = useTaskStore()                 // the same instance the component got

  expect(store.load).toHaveBeenCalledTimes(1)  // called from onMounted, but stubbed
  await wrapper.findAllComponents(TaskItem)[0].find('input').setValue(true)
  expect(store.toggle).toHaveBeenCalledWith(1)
})
----

`+mount(TaskList, { shallow: true, global })+` goes one step further and replaces every child component with a stub
(`<task-item-stub>`), which isolates the container from `TaskItem` entirely.

=== Composables that use lifecycle hooks

A composable that registers `onMounted` / `onUnmounted` must run inside a component. The `withSetup` helper
from earlier hosts it, and fake timers make the interval deterministic:

[source,ts]
----
import { ref, onMounted, onUnmounted } from 'vue'

export function useClock() {
  const now = ref(Date.now())
  let id: ReturnType<typeof setInterval>
  onMounted(() => { id = setInterval(() => { now.value = Date.now() }, 1000) })
  onUnmounted(() => clearInterval(id))
  return { now }
}
----

[source,ts]
----
it('ticks while mounted and stops on unmount', () => {
  vi.useFakeTimers()
  const { result, wrapper } = withSetup(useClock)
  const t0 = result.now.value

  vi.advanceTimersByTime(1000)
  expect(result.now.value).toBeGreaterThan(t0)

  const spy = vi.spyOn(globalThis, 'clearInterval')
  wrapper.unmount()
  expect(spy).toHaveBeenCalled()
  vi.useRealTimers()
})
----

The debounced search composable from xref:web/vue/watchers.adoc[] is tested the same way, with
`vi.useFakeTimers()` and `await nextTick()` between a change to the query and the assertion.

=== Anatomy of a reliable component test

[mermaid]
....
flowchart LR
    a["Arrange<br/>mount with props,<br/>plugins, stubs"] --> b["Act<br/>trigger, setValue,<br/>setProps"]
    b --> c["Wait<br/>await the act,<br/>nextTick, flushPromises"]
    c --> d["Assert<br/>text, emitted,<br/>store and spy calls"]
....

Habits that keep Vue tests from being flaky or brittle:

* **Assert behaviour, not implementation.** Check rendered text, emitted events and store calls rather than
  internal refs on `wrapper.vm`.
* **Query with `data-test` attributes or roles**, not CSS classes that exist for styling.
* **Always `await` the interaction.** `trigger`, `setValue` and `setProps` return a promise that resolves after
  the DOM has updated.
* **Wait for the right thing.** A pending promise needs `flushPromises()`; a reactive write made outside the
  wrapper needs `nextTick()`.
* **Isolate each test.** A fresh Pinia and router per test, `vi.unstubAllGlobals()` and `vi.useRealTimers()`
  in `afterEach`.
* **Use `attachTo: document.body`** only when behaviour depends on being in the document (focus, `document`
  event listeners), and call `wrapper.unmount()` afterwards.

== Snapshot testing

`expect(wrapper.html()).toMatchSnapshot()` records rendered markup and flags future diffs. Useful for
stable presentational components; avoid it for components that change often, where snapshots become noise
that gets blindly updated.

`toMatchInlineSnapshot()` writes the expected markup into the test file itself the first time it runs, which keeps
the expectation next to the test and makes review easier:

[source,ts]
----
it('renders a finished task', () => {
  const wrapper = mount(TaskItem, { props: { task: { id: 2, title: 'Run tests', done: true } } })
  expect(wrapper.html()).toMatchInlineSnapshot(
    `"<li class="done"><label><input type="checkbox" checked=""> Run tests</label></li>"`,
  )
})
----

== Component testing vs. end-to-end

Component tests mount one component under a simulated DOM -- fast, but not a real browser. End-to-end tests
drive the built app in an actual browser and are the place to verify navigation, focus management, real
CSS, and integration with a backend. Cypress and Playwright also offer a *component testing* mode that
mounts a Vue component in a real browser, a middle ground when jsdom/happy-dom fidelity is not enough.

== End-to-end with Cypress or Playwright

https://www.cypress.io/[Cypress] and https://playwright.dev/[Playwright] both start the dev server, open a
browser, and script user interactions. They auto-wait for elements and let you intercept HTTP so tests stay
deterministic. For a deeper, tool-focused reference -- install, headless vs. headed execution, evidence capture,
CI/CD, and a full Selenium/Playwright/Cypress comparison -- see xref:web/e2e-testing/index.adoc[E2E Testing in the Browser] and xref:web/e2e-testing/choosing-a-tool.adoc[Choosing a Tool].

[source,js]
----
// Playwright
import { test, expect } from '@playwright/test'

test('adds a todo', async ({ page }) => {
  await page.route('**/api/todos', (route) =>
    route.fulfill({ json: [] }),
  )
  await page.goto('/')
  await page.getByPlaceholder('What needs doing?').fill('Write tests')
  await page.getByRole('button', { name: 'Add' }).click()
  await expect(page.getByText('Write tests')).toBeVisible()
})
----

[source,js]
----
// Cypress
it('adds a todo', () => {
  cy.intercept('GET', '/api/todos', [])
  cy.visit('/')
  cy.get('[data-test="new-todo"]').type('Write tests{enter}')
  cy.contains('Write tests').should('be.visible')
})
----

`create-vue` can scaffold either one.
