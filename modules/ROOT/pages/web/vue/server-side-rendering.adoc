= Server-Side Rendering
:description: Rendering Vue on the server -- CSR vs. SSR vs. SSG vs. ISR trade-offs, createSSRApp and renderToString, client hydration and app.mount, hydration mismatches, data fetching with onServerPrefetch and useSSRContext, cross-request state pollution, ClientOnly patterns, and Nuxt and VitePress.
:keywords: Vue SSR, server-side rendering, CSR, SSG, ISR, hydration, createSSRApp, renderToString, renderToWebStream, data-allow-mismatch, onServerPrefetch, useSSRContext, state transfer, cross-request state pollution, ClientOnly, Nuxt, VitePress

include::partial$ai-disclaimer.adoc[]

By default a Vue app is *client-rendered*: the server sends an empty `<div id="app">` and JavaScript builds
the DOM in the browser. *Server-side rendering* (SSR) instead renders components to HTML strings on the
server, sends usable markup, and then *hydrates* it in the browser. The guide covers this at
https://vuejs.org/guide/scaling-up/ssr.html[Server-Side Rendering] and the API at
https://vuejs.org/api/ssr.html[Server-Side Rendering API].

== CSR, SSR, SSG, and ISR

[cols="1,3"]
|===
| Strategy | What happens

| CSR | HTML shell + JS; the browser renders. Simplest to deploy; slowest first paint; content invisible to
crawlers that do not run JS.
| SSR | HTML rendered per request on a Node/edge server, then hydrated. Fast first contentful paint and
full SEO; needs a running server and careful state handling.
| SSG | Pages rendered to static HTML at *build* time, hydrated on load. Best TTFB, host anywhere; only
suits content known at build time.
| ISR | SSG plus background regeneration: serve a cached static page, rebuild it on an interval or on
demand. Static speed with fresher content; framework-specific.
|===

The cost of SSR is complexity: code runs in two environments, so browser-only globals (`window`,
`document`, `localStorage`) are off-limits during rendering, and build tooling gets more involved. Reach for
a framework unless you have a specific reason not to.

== `createSSRApp`, `renderToString`, and hydration

On the server, create the app with `createSSRApp` (not `createApp`) and render it with `renderToString`
from `vue/server-renderer`:

[source,js]
----
// server entry
import { createSSRApp } from 'vue'
import { renderToString } from 'vue/server-renderer'
import App from './App.vue'

export async function render() {
  const app = createSSRApp(App)
  const html = await renderToString(app)
  return `<!DOCTYPE html><div id="app">${html}</div><script type="module" src="/entry-client.js"></script>`
}
----

For large pages, the streaming renderers `renderToNodeStream` / `renderToWebStream` flush HTML as it is
produced, improving time-to-first-byte.

On the client, build the *same* app with `createSSRApp` and call `app.mount`. Because the container already
contains server-rendered markup, Vue *hydrates* instead of rendering from scratch: it walks the existing DOM
and attaches reactivity and event listeners in place.

[source,js]
----
// client entry
import { createSSRApp } from 'vue'
import App from './App.vue'

createSSRApp(App).mount('#app')   // hydration, not a fresh render
----

== Hydration mismatches

Hydration assumes the client's first render produces markup identical to the server's. When it does not --
a random value, a locale-dependent date, invalid HTML nesting that the browser "fixes" -- Vue logs a
*hydration mismatch* warning and patches that subtree client-side. Fix the nondeterminism, or, when a
difference is intentional, mark the element with `data-allow-mismatch` to silence the warning for it. See
https://vuejs.org/guide/scaling-up/ssr.html#hydration-mismatch[Hydration Mismatch].

== Data fetching and state transfer

Fetch on the server, serialize the result into the HTML, and reuse it on the client so hydration matches
and no duplicate request fires:

* `+onServerPrefetch(async () => { ... })+` -- a lifecycle hook that runs only on the server; `renderToString`
  awaits it before producing HTML.
* `useSSRContext()` -- returns a per-request object you can write to on the server (for collected head tags,
  fetched data, status codes) and read back after `renderToString` resolves.

[source,vue]
----
<script setup>
import { ref, onServerPrefetch } from 'vue'

const post = ref(null)

// on the server: fill before render. on the client: read from transferred state
onServerPrefetch(async () => {
  post.value = await fetchPost(route.params.id)
})
</script>
----

=== Cross-request state pollution

On the server the module scope is shared by *every* request. A store or piece of state created once at
module load is therefore leaked across users. Create per-request state inside a factory instead:

[source,js]
----
// BAD on the server: one store shared by all requests
export const store = reactive({ user: null })

// GOOD: a fresh instance per request
export function createStore() {
  return reactive({ user: null })
}
----

The same rule is why xref:web/vue/state-management.adoc[Pinia] takes `state` as a function and why the
router uses `createMemoryHistory` per request.

== Client-only content

Some components cannot render on the server -- they need `window`, measure the DOM, or wrap a browser-only
library. Wrap them so they render only after hydration:

* `<ClientOnly>` (provided by Nuxt and VitePress; a few lines to write in a bare setup) renders its slot
  only on the client.
* `defineAsyncComponent` plus a guard, or importing the library inside `onMounted`, achieves the same in
  plain Vue SSR.

== Nuxt and VitePress

Wiring the server, client, and build entries by hand is involved. Two official-ecosystem tools do it for
you:

* **https://nuxt.com/[Nuxt]** -- the recommended full-stack framework for Vue. File-based routing, data
  fetching that transfers automatically, SSR / SSG / ISR / hybrid per route, an API layer (Nitro), and
  deployment presets for Node and edge platforms.
* **https://vitepress.dev/[VitePress]** -- a Vite-powered static-site generator aimed at documentation and
  content sites; Markdown authoring with Vue components available inline. It builds this kind of docs site.

== The request lifecycle, end to end

Putting rendering, data and state transfer together, one request goes through the following steps. Everything left
of the response is created *per request* and thrown away afterwards; only the browser keeps state between pages.

[mermaid]
....
sequenceDiagram
    participant B as Browser
    participant S as Server
    participant D as Data source
    B->>S: GET /todos
    S->>S: new store and createSSRApp(TodoPage), provide the store
    S->>D: onServerPrefetch fetches the todos
    D-->>S: todos
    S->>S: renderToString, onMounted is skipped
    S-->>B: HTML plus serialized store state
    B->>B: show HTML, no JavaScript needed yet
    B->>B: build store from the serialized state
    B->>B: createSSRApp(TodoPage).mount, hydrate the same DOM
    B->>B: onMounted runs, page is interactive
....

== Worked example: server-rendering the to-do page

The example below uses three files and a script, and was run with Vite's SSR module loader (`ssrLoadModule`), which is
the same mechanism a development server uses. It needs `vue`, `vite` and `@vitejs/plugin-vue`.

The page component fetches its data in `onServerPrefetch`, gets its store by injection, and records a document title
for the server to use:

[source,vue]
----
<!-- TodoPage.vue -->
<script setup>
import { ref, onServerPrefetch, onMounted, useSSRContext, inject } from 'vue'

const props = defineProps({ userId: String })
const store = inject('store')
const todos = ref(store.todos)

// useSSRContext() must be called synchronously in setup, and only in the server build
const ssrContext = import.meta.env.SSR ? useSSRContext() : null

onServerPrefetch(async () => {
  // runs on the server only, awaited before the HTML is produced
  const result = await store.fetchTodos(props.userId)
  todos.value = result
  store.todos = result
  ssrContext.title = `Todos for ${props.userId}`   // collected for the server to write into <head>
})

const origin = ref('server')
onMounted(() => { origin.value = 'client' })       // never runs on the server
</script>

<template>
  <h1>Todos</h1>
  <ul><li v-for="t in todos" :key="t.id">{{ t.text }}</li></ul>
  <p>rendered on the {{ origin }}</p>
</template>
----

A shared entry module builds a *new app* for each call and provides the store the caller passes in. The server calls
`render`; the client calls `createApp` and mounts:

[source,js]
----
// entry.js
import { createSSRApp } from 'vue'
import { renderToString } from 'vue/server-renderer'
import TodoPage from './TodoPage.vue'

export function createApp(userId, store) {
  const app = createSSRApp(TodoPage, { userId })
  app.provide('store', store)
  return app
}

export async function render(userId, store) {
  const ctx = {}
  const html = await renderToString(createApp(userId, store), ctx)
  return { html, ctx, state: JSON.stringify(store.todos) }
}
----

[source,js]
----
// run.mjs -- node run.mjs
import { createServer } from 'vite'
import vue from '@vitejs/plugin-vue'

const vite = await createServer({
  appType: 'custom',
  server: { middlewareMode: true },
  plugins: [vue()],
})
const { render } = await vite.ssrLoadModule('/entry.js')

const db = { u1: [{ id: 1, text: 'Write docs' }] }
const makeStore = () => ({ todos: [], fetchTodos: async (id) => db[id] })   // fresh store per request

const { html, ctx, state } = await render('u1', makeStore())
console.log(html)
console.log(ctx.title)
console.log(state)
await vite.close()
----

The output is:

[source,text]
----
<!--[--><h1>Todos</h1><ul><!--[--><li>Write docs</li><!--]--></ul><p>rendered on the server</p><!--]-->
Todos for u1
[{"id":1,"text":"Write docs"}]
----

Reading it:

* The HTML already contains the fetched item, so `onServerPrefetch` was awaited before rendering finished. The
  `+<!--[-->+` and `+<!--]-->+` comments are fragment anchors that hydration uses to line the client's VNodes up with the
  DOM.
* The paragraph says `server`: `onMounted` did not run, so `origin` kept its initial value.
* `ctx.title` carries data from a component back to the server, which writes it into `<title>`.
* `state` is what you would embed in the page (serialized safely, see
  xref:web/vue/security-and-accessibility.adoc[]) so the client can rebuild the same store.

*A pitfall found while running it.* Calling `useSSRContext()` *inside* the `onServerPrefetch` callback fails: by then the
`await` has run and there is no active instance, so Vue logs "inject() can only be used inside setup()" and the context
is `undefined`. Fetch the context once at the top of `setup()`, guarded by `import.meta.env.SSR`, as above.

=== Hydrating with and without the state

In jsdom, mounting the client app over that exact HTML behaves in two ways:

* With the store rebuilt from the transferred state (`todos` already holding the item), hydration finishes with no
  warnings, the text reads `Write docs`, and, because `onMounted` ran, the paragraph now says `client`.
* With an *empty* store -- the state was not transferred -- the client renders no list items while the HTML has one.
  Vue logs `Hydration children mismatch` and "Hydration completed but contains mismatches", then repairs the DOM by
  patching it. The page ends up correct, but the flash and the extra work are exactly what state transfer prevents.

The paragraph changing from `server` to `client` is a deliberate difference that hydration tolerates only because the
change happens in `onMounted`, after hydration finishes. Putting the same branching in the initial render (for example
`typeof window !== 'undefined' ? 'client' : 'server'` in the template) would be a mismatch.

=== Cross-request pollution, demonstrated

The module-scope warning above is easy to dismiss until you see it. Two overlapping requests, one slowed by a timer,
share a module-level `reactive` object in the first handler and use a per-request object in the second:

[source,js]
----
import { reactive } from 'vue'

const shared = reactive({ user: null })
const handleShared = async (user) => {
  shared.user = user
  await new Promise(r => setTimeout(r, user === 'a' ? 10 : 0))   // simulated async fetch
  return shared.user
}

const handlePerRequest = async (user) => {
  const state = reactive({ user })
  await new Promise(r => setTimeout(r, user === 'a' ? 10 : 0))
  return state.user
}

console.log(await Promise.all([handleShared('a'), handleShared('b')]))            // [ 'b', 'b' ]
console.log(await Promise.all([handlePerRequest('a'), handlePerRequest('b')]))    // [ 'a', 'b' ]
----

The response for user `a` is rendered with the data of user `b` when the state lives in module scope: a data leak, not just a
bug. This is why the example above takes the store as an argument and creates it in `makeStore()` for every request.
