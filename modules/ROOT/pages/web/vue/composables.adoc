= Composables
:description: What a Vue composable is, naming and return conventions, accepting reactive arguments with toValue, cleaning up side effects, the call-synchronously rule, and why composables replace mixins and renderless components.
:keywords: Vue, Vue 3, composable, Composition API, script setup, useMouse, useFetch, useLocalStorage, toValue, MaybeRefOrGetter, onUnmounted, onWatcherCleanup, watchEffect, mixins, renderless components, VueUse

include::partial$ai-disclaimer.adoc[]

A *composable* is a function that uses Vue's Composition API to package and reuse *stateful* logic. By
convention its name starts with `use`, it is called from `setup` (or the top level of `<script setup>`), and
the reactive state and lifecycle hooks it creates belong to the component that called it.

== What a composable is

A composable creates some reactive state, wires up whatever side effects it needs, and returns the state for
the caller to use in its template or logic. The canonical first example tracks the mouse position:

[source,js]
----
// composables/useMouse.js
import { ref, onMounted, onUnmounted } from 'vue'

export function useMouse() {
  const x = ref(0)
  const y = ref(0)

  function update(event) {
    x.value = event.pageX
    y.value = event.pageY
  }

  onMounted(() => window.addEventListener('mousemove', update))
  onUnmounted(() => window.removeEventListener('mousemove', update))

  return { x, y }
}
----

[source,vue]
----
<script setup>
import { useMouse } from './composables/useMouse.js'

const { x, y } = useMouse()
</script>

<template>
  <p>Mouse at {{ x }}, {{ y }}</p>
</template>
----

Each component that calls `useMouse()` gets its own independent `x` and `y`, and the listener is removed when
that component unmounts. This is the whole idea, laid out in
https://vuejs.org/guide/reusability/composables.html[the Composables guide].

== Naming and what to return

* **Name it `use<Thing>`.** The prefix is how a reader (and tooling such as the ESLint plugin) recognises a
  function that may call reactivity and lifecycle APIs.
* **Return refs, not a `reactive()` wrapper.** Returning a plain object of refs -- `+{ x, y }+` -- lets the
  caller destructure while keeping each property reactive. Destructuring a `reactive()` object breaks
  reactivity. If you prefer `state.x` access at the call site, return a single `reactive()` object instead,
  but do not do both.
* **Expose methods alongside state** when the caller needs to trigger changes: `+return { data, error, refetch }+`.

== Accepting reactive arguments

A composable is more reusable when its input can be a plain value, a `ref`, or a getter. Normalise the input
with https://vuejs.org/api/reactivity-utilities.html#tovalue[`toValue()`], and read it *inside* a
`watchEffect` so the composable re-runs when a reactive argument changes:

[source,js]
----
// composables/useFetch.js
import { ref, watchEffect, toValue } from 'vue'

export function useFetch(url) {
  const data = ref(null)
  const error = ref(null)

  watchEffect(async () => {
    data.value = null
    error.value = null
    try {
      const res = await fetch(toValue(url))   // string | Ref<string> | (() => string)
      data.value = await res.json()
    } catch (e) {
      error.value = e
    }
  })

  return { data, error }
}
----

[source,vue]
----
<script setup>
import { ref } from 'vue'
import { useFetch } from './composables/useFetch.js'

const id = ref(1)
// re-fetches whenever `id` changes, because the getter is read inside watchEffect
const { data, error } = useFetch(() => `/api/items/${id.value}`)
</script>
----

The matching TypeScript type for such a parameter is `MaybeRefOrGetter<T>`, and `toValue` is its
accessor -- see https://vuejs.org/guide/typescript/composition-api.html[TypeScript with Composition API].

== Cleaning up side effects

Anything a composable starts, it must stop, so that a component using it can mount and unmount repeatedly
without leaks.

* Register teardown for the component's lifetime with
  https://vuejs.org/api/composition-api-lifecycle.html#onunmounted[`onUnmounted`] (as `useMouse` does above).
* Clean up *per run* of a watcher with
  https://vuejs.org/guide/essentials/watchers.html#side-effect-cleanup[`onWatcherCleanup`] (Vue 3.5+), or the
  `onCleanup` argument passed to `watch` / `watchEffect` callbacks. This runs before the next invocation and
  on stop:

[source,js]
----
import { ref, watch, onWatcherCleanup } from 'vue'

export function useItem(id) {
  const item = ref(null)

  watch(id, async (newId) => {
    const controller = new AbortController()
    onWatcherCleanup(() => controller.abort())   // cancel the in-flight request
    const res = await fetch(`/api/items/${newId}`, { signal: controller.signal })
    item.value = await res.json()
  }, { immediate: true })

  return { item }
}
----

== The call-synchronously rule

A composable must be called **synchronously**, at the top level of `setup` or `<script setup>`, or from
inside another composable. Do not call one after an `await`, in an event handler, or conditionally. Vue
relies on the *currently active component instance* to attach lifecycle hooks and injected values, and that
instance is only available during the synchronous execution of `setup`. The same restriction applies to
`onMounted`, `inject`, and friends. See
https://vuejs.org/guide/reusability/composables.html#usage-restrictions[Usage restrictions].

== Worked example: useLocalStorage

Read once on setup, then persist on every change:

[source,js]
----
// composables/useLocalStorage.js
import { ref, watch } from 'vue'

export function useLocalStorage(key, initialValue) {
  const raw = localStorage.getItem(key)
  const state = ref(raw ? JSON.parse(raw) : initialValue)

  watch(state, (value) => {
    localStorage.setItem(key, JSON.stringify(value))
  }, { deep: true })

  return state
}
----

[source,vue]
----
<script setup>
import { useLocalStorage } from './composables/useLocalStorage.js'

const theme = useLocalStorage('theme', 'light')
</script>

<template>
  <button @click="theme = theme === 'light' ? 'dark' : 'light'">
    Theme: {{ theme }}
  </button>
</template>
----

In production, a library such as https://vueuse.org/[VueUse] ships hardened versions of all three of these
(`useMouse`, `useFetch`, `useLocalStorage`) with SSR guards and shared listeners.

== Who owns what a composable creates

A composable is an ordinary function, so it has no lifetime of its own. Everything it creates -- refs, computed
properties, watchers, lifecycle hooks -- is attached to whatever *reactive scope* is active when it is called. During
`setup` that scope belongs to the component instance, and Vue stops all of it when the component unmounts.

[mermaid]
....
sequenceDiagram
    participant V as Vue runtime
    participant S as setup of TodoPanel
    participant C as useTodos
    participant W as watch inside useTodos
    V->>S: create instance, activate its effect scope
    S->>C: useTodos() called synchronously
    C->>W: watch(todos) registered in the active scope
    C-->>S: returns refs and functions
    Note over S,W: component lives, state changes, watcher persists to storage
    V->>S: unmount
    V->>W: scope stops, watcher disposed
....

This ownership explains the call-synchronously rule from above: Vue can find the active scope only while `setup` is
running. It also explains how to use a composable *outside* a component: create the scope yourself with
https://vuejs.org/api/reactivity-advanced.html#effectscope[`effectScope()`] and stop it when you are done.

== Worked example: a useTodos composable

The todo list's logic -- the array, the filter, the derived counts and persistence -- moves out of the component into
one function. It takes the storage object as a parameter, which keeps it testable without a browser.

[source,js]
----
// composables/useTodos.js
import { ref, computed, watch } from 'vue'

export function useTodos(storageKey = 'todos', storage = globalThis.localStorage) {
  const raw = storage?.getItem(storageKey)
  const todos = ref(raw ? JSON.parse(raw) : [])
  const filter = ref('all') // 'all' | 'open' | 'done'

  let nextId = todos.value.reduce((max, t) => Math.max(max, t.id), 0) + 1

  const visible = computed(() => {
    if (filter.value === 'all') return todos.value
    return todos.value.filter((t) => (filter.value === 'done') === t.done)
  })
  const remaining = computed(() => todos.value.filter((t) => !t.done).length)

  function add(text) {
    todos.value.push({ id: nextId++, text, done: false })
  }
  function toggle(id) {
    const todo = todos.value.find((t) => t.id === id)
    if (todo) todo.done = !todo.done
  }
  function remove(id) {
    todos.value = todos.value.filter((t) => t.id !== id)
  }

  watch(todos, (value) => storage?.setItem(storageKey, JSON.stringify(value)), { deep: true })

  return { todos, filter, visible, remaining, add, toggle, remove }
}
----

The component shrinks to wiring:

[source,vue]
----
<script setup>
import { useTodos } from './composables/useTodos.js'

const { visible, remaining, filter, add, toggle, remove } = useTodos()
</script>

<template>
  <button @click="add('New todo')">Add</button>
  <select v-model="filter">
    <option>all</option>
    <option>open</option>
    <option>done</option>
  </select>
  <ul>
    <li v-for="t in visible" :key="t.id">
      <input type="checkbox" :checked="t.done" @change="toggle(t.id)" />
      {{ t.text }}
      <button @click="remove(t.id)">x</button>
    </li>
  </ul>
  <p>{{ remaining }} left</p>
</template>
----

The composable's `nextId` is a plain local variable, so every call of `useTodos()` has its own counter, just as it has
its own `todos` ref. Share state *between* components by creating the refs once at module level (or, better, in a
xref:web/vue/state-management.adoc[store]), not by calling a composable and hoping for a singleton.

== Testing a composable

Because `useTodos` only uses reactivity APIs (no `onMounted`, no `inject`), it can be tested with nothing but a scope.
Here the storage is a `Map`-backed stub:

[source,js]
----
import { effectScope, nextTick } from 'vue'
import { useTodos } from './composables/useTodos.js'

test('persists and restores', async () => {
  const store = new Map()
  const storage = { getItem: (k) => store.get(k) ?? null, setItem: (k, v) => store.set(k, v) }

  const scope = effectScope()
  const t = scope.run(() => useTodos('t', storage))
  t.add('a')
  t.add('b')
  t.toggle(1)
  await nextTick()                       // let the watcher write to storage

  expect(t.remaining.value).toBe(1)
  t.filter.value = 'done'
  expect(t.visible.value.map((x) => x.text)).toEqual(['a'])
  expect(JSON.parse(store.get('t'))).toHaveLength(2)

  scope.stop()                           // dispose the watcher, like an unmount would
  const again = effectScope().run(() => useTodos('t', storage))
  expect(again.todos.value).toHaveLength(2)    // restored from storage
  again.add('c')
  expect(again.todos.value.at(-1).id).toBe(3)  // ids continue after the restored ones
})
----

This test passes as written. A composable that *does* call lifecycle hooks or `inject` needs a real host instead:
mount a tiny component whose `setup` calls it (Vue Test Utils) or create an app and run it with `app.runWithContext()`.
See xref:web/vue/testing.adoc[].

== Designing a composable's interface

Three questions settle most design decisions. *What goes in?* Accept `MaybeRefOrGetter` for anything the caller might
want to be reactive and `toValue()` it inside an effect. *What comes out?* Refs for state, plain functions for actions,
and `readonly()` refs when the caller must not write them. *What does it own?* Anything with a side effect -- a
listener, timer, subscription -- must be stopped by the composable itself, so callers never need a cleanup call.

[source,js]
----
import { ref, readonly } from 'vue'

export function useCounter(start = 0) {
  const count = ref(start)
  const increment = () => count.value++
  // callers can read count but must go through increment() to change it
  return { count: readonly(count), increment }
}
----

== Composables vs. mixins vs. renderless components

[cols="1,3"]
|===
| Approach | Trade-off

| **Composable** | Plain function calls. Explicit inputs and outputs, no naming collisions, tree-shakeable,
  no component instance. The recommended way to share stateful logic.

| **Mixin** (Options API) | Merges `data` / `methods` / hooks into a component. The property source is
  invisible at the use site, two mixins can silently collide on a key, and there is no way to pass
  arguments. See https://vuejs.org/guide/reusability/composables.html#vs-mixins[Composables vs. Mixins].

| **Renderless component** | A component that owns logic and exposes it through a scoped slot while
  rendering nothing. Works, but costs a component instance and only functions inside a template. Use it only
  when the template itself must drive the slot content. See
  https://vuejs.org/guide/components/slots.html#renderless-components[Renderless Components].
|===

A composable still works from an Options-API component -- call it in `setup()` and return what you need
(shown here only as a contrast; new code uses `<script setup>`):

[source,js]
----
import { useMouse } from './composables/useMouse.js'

export default {
  setup() {
    const { x, y } = useMouse()
    return { x, y }
  }
}
----
