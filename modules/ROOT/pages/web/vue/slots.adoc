= Slots
:description: Passing template fragments into a component with default and named slots, fallback content, the shorthand syntax, conditional and dynamic slots, scoped slots that pass data back to the parent, the renderless component pattern, and typing slots with defineSlots.
:keywords: Vue 3, slots, default slot, named slots, fallback content, v-slot, slot shorthand, scoped slots, slot props, dynamic slot names, conditional slots, renderless component, defineSlots

include::partial$ai-disclaimer.adoc[]

Props pass *data* into a component; *slots* pass *template content*. The parent writes markup between the
component's tags and the child decides where -- and whether -- to render it. Scoped slots add a return
channel, letting the child hand data back out to that markup.

image::vue-slots.svg["A parent template's fragments projected into a child component's named slot outlets, with a scoped slot passing a row object back up to the parent's slot template",width=720,role=text-center]

== The default slot and fallback content

`<slot>` in the child marks where the parent's content goes:

[source,vue]
----
<!-- FancyButton.vue -->
<template>
  <button class="fancy-btn">
    <slot>Click me</slot>   <!-- fallback: shown only when the parent passes nothing -->
  </button>
</template>
----

[source,vue]
----
<!-- Parent -->
<FancyButton>Save changes</FancyButton>
<FancyButton />               <!-- renders "Click me" -->
----

Slot content compiles in the *parent's* scope: it can read the parent's state but not the child's. See
https://vuejs.org/guide/components/slots.html[Slots].

== Named slots

A component can expose several outlets. Give each `<slot>` a `name` (the unnamed one is implicitly
`default`) and target it from the parent with `<template #name>`:

[source,vue]
----
<!-- BaseLayout.vue -->
<template>
  <div class="layout">
    <header><slot name="header" /></header>
    <main><slot /></main>
    <footer><slot name="footer" /></footer>
  </div>
</template>
----

[source,vue]
----
<!-- Parent -->
<BaseLayout>
  <template #header><h1>Page title</h1></template>

  <p>Main body content goes in the default slot.</p>

  <template #footer><small>Footer text</small></template>
</BaseLayout>
----

`#header` is shorthand for `v-slot:header`. See
https://vuejs.org/guide/components/slots.html#named-slots[Named Slots].

== Conditional slots

`$slots` is an object keyed by the names of the slots the parent actually provided. Use it to drop wrapper
markup when a slot is empty:

[source,vue]
----
<template>
  <div class="card">
    <header v-if="$slots.header" class="card-header">
      <slot name="header" />
    </header>
    <div class="card-body"><slot /></div>
  </div>
</template>
----

See https://vuejs.org/guide/components/slots.html#conditional-slots[Conditional Slots].

== Dynamic slot names

A name in `v-slot` can be an expression in square brackets:

[source,vue]
----
<template>
  <BaseLayout>
    <template #[dynamicSlot]>Goes wherever dynamicSlot names</template>
  </BaseLayout>
</template>
----

See https://vuejs.org/guide/components/slots.html#dynamic-slot-names[Dynamic Slot Names].

== Scoped slots

To let slot content use data only the child has, the child passes it as attributes on `<slot>`, and the
parent receives a *slot props* object:

[source,vue]
----
<!-- TodoList.vue -->
<script setup>
defineProps({ items: Array })
</script>

<template>
  <ul>
    <li v-for="item in items" :key="item.id">
      <slot :item="item" :index="item.id">{{ item.text }}</slot>
    </li>
  </ul>
</template>
----

[source,vue]
----
<!-- Parent: destructure the slot props -->
<TodoList :items="todos">
  <template #default="{ item, index }">
    <strong>{{ index }}.</strong> {{ item.text }}
  </template>
</TodoList>
----

When only the default slot is scoped, `v-slot` can go straight on the component tag --
`+<TodoList v-slot="{ item }">+`. See
https://vuejs.org/guide/components/slots.html#scoped-slots[Scoped Slots].

== Named and scoped together

Every named slot can carry its own slot props; each `<template>` destructures the object for that slot:

[source,vue]
----
<DataTable :rows="rows">
  <template #row="{ row }">
    <td>{{ row.name }}</td>
    <td>{{ row.email }}</td>
  </template>

  <template #empty>
    <td colspan="2">No results</td>
  </template>
</DataTable>
----

See https://vuejs.org/guide/components/slots.html#scoped-slots[Scoped Slots] for the mixed case.

== The renderless component pattern

A component with *no markup of its own* -- its template is a single scoped `<slot>` passing computed values
out -- packages behaviour while leaving all rendering to the parent:

[source,vue]
----
<!-- MouseTracker.vue -->
<script setup>
import { ref, onMounted, onUnmounted } from 'vue'

const x = ref(0)
const y = ref(0)
const update = (e) => { x.value = e.pageX; y.value = e.pageY }

onMounted(() => window.addEventListener('mousemove', update))
onUnmounted(() => window.removeEventListener('mousemove', update))
</script>

<template>
  <slot :x="x" :y="y" />
</template>
----

[source,vue]
----
<MouseTracker v-slot="{ x, y }">
  <p>Pointer at {{ x }}, {{ y }}</p>
</MouseTracker>
----

The Vue docs note that a xref:web/vue/composables.adoc[composable] usually does this job with less overhead;
the renderless pattern earns its keep when the logic is inseparable from a slot-shaped API. See
https://vuejs.org/guide/components/slots.html#renderless-components[Renderless Components].

== Typing slots

`defineSlots()` is a `<script setup>` macro that emits no runtime code and only attaches types: each key is a
slot name and its function type describes the slot props the child will pass.

[source,ts]
----
defineSlots<{
  default(props: { item: Todo; index: number }): any
  empty(): any
}>()
----

See https://vuejs.org/api/sfc-script-setup.html#defineslots[`defineSlots()`].

== How slots work: content as functions

A slot is not a pre-rendered chunk of HTML. The compiler turns each slot's content into a *function*, and the child
calls that function while it renders, passing the slot props as its argument. This usage:

[source,vue]
----
<DataTable :rows="rows">
  <template #row="{ row }"><td>{{ row.name }}</td></template>
</DataTable>
----

compiles to the following (abridged; produced with `compile` from `@vue/compiler-dom`):

[source,js]
----
_createBlock(_component_DataTable, { rows: _ctx.rows }, {
  row: _withCtx(({ row }) => [
    _createElementVNode("td", null, _toDisplayString(row.name), 1 /* TEXT */)
  ]),
  _: 1 /* STABLE */
}, 8 /* PROPS */, ["rows"])
----

The object's keys are the slot names and each value is a function of the slot props, wrapped in `withCtx` so it runs
with the parent's rendering context. The `_: 1` flag marks the slots as stable, which lets the parent skip forcing the
child to re-render.

[mermaid]
....
sequenceDiagram
    participant Parent
    participant Child
    Parent->>Child: render passes slots object, name to function
    Note over Child: child render runs
    Child->>Parent: calls slots.row(rowProps) for each row
    Parent-->>Child: VNodes built with the parent's scope plus rowProps
    Child->>Child: places the VNodes inside its own markup
....

This explains three behaviours that otherwise look arbitrary:

* *Slot content sees the parent's scope, not the child's*, because the function is defined in the parent's template.
  The child's data reaches it only through slot props.
* *Slot content is rendered lazily.* A slot the child never calls (a `v-if` around a `<slot>`) never runs its
  function, so its content costs nothing.
* *Reactive reads inside slot content are tracked by the child's render effect.* In a test, a parent whose slot
  content reads `count.value` is not re-rendered when `count` changes (parent renders: 0), while the child is
  (child renders: 1) and shows the new value. Passing a slot instead of a prop is therefore a way to limit a
  re-render to the component that actually displays the data.

== Worked example: a generic, typed `DataTable`

A table component that knows how to lay out rows, an optional header and an empty state, but not what a cell looks
like, is the classic scoped-slot use. This version is generic over the row type, so the `row` slot props are typed
from the `rows` prop, and it uses `$slots` to omit the `<thead>` when no header is supplied:

[source,vue]
----
<!-- DataTable.vue -->
<script setup lang="ts" generic="T extends { id: number }">
defineProps<{ rows: T[] }>()

defineSlots<{
  header?(): any
  row(props: { row: T; index: number }): any
  empty?(): any
}>()
</script>

<template>
  <table>
    <thead v-if="$slots.header">
      <tr><slot name="header" /></tr>
    </thead>
    <tbody>
      <tr v-for="(row, index) in rows" :key="row.id">
        <slot name="row" :row="row" :index="index" />
      </tr>
      <tr v-if="rows.length === 0">
        <slot name="empty"><td>No data</td></slot>
      </tr>
    </tbody>
  </table>
</template>
----

[source,vue]
----
<!-- Usage -->
<script setup lang="ts">
import { ref } from 'vue'
import DataTable from './DataTable.vue'

const rows = ref([
  { id: 1, name: 'Ada', email: 'ada@example.org' },
  { id: 2, name: 'Bo', email: 'bo@example.org' },
])
const headerSlot = ref('header')     // a dynamic slot name
</script>

<template>
  <DataTable :rows="rows">
    <template #[headerSlot]><th>Name</th><th>Email</th></template>
    <template #row="{ row, index }">
      <td>{{ index + 1 }}. {{ row.name }}</td>
      <td>{{ row.email }}</td>
    </template>
  </DataTable>
</template>
----

Mounting this pair in a Vitest test renders a `<thead>` with the two header cells and one `<tr>` per row
(`1. Ada`, `2. Bo`); emptying the array leaves the fallback `No data` cell, because the parent supplied no `empty`
slot. Inside the `row` slot, `row.name` is type-checked against the element type of `rows` when the project is
checked with `vue-tsc` (see xref:web/vue/typescript.adoc[]).

== Slots in script and render functions

Outside the template, the same object is available in two forms. `useSlots()` returns it inside `<script setup>`
(`$slots` in the template is the same object), and its keys are exactly the slots the parent provided -- a test that
mounts a component with `default` and `footer` slots reads the keys `default` and `footer`. In a render function or
`setup()`-returned function the slots arrive as the second argument's `slots` property and are called like functions
(see xref:web/vue/rendering-render-functions-and-web-components.adoc[]):

[source,js]
----
import { h } from 'vue'

const Panel = {
  setup(props, { slots }) {
    return () =>
      h('section', [
        slots.title ? h('h2', slots.title()) : null,
        slots.default?.({ collapsed: false }),     // scoped slot call
      ])
  },
}
----

Because a slot is a function, always *call* it (`slots.default()`), and call it during render, not in a setup-time
variable -- otherwise the reactive reads inside it are tracked in the wrong place.

== Choosing between slots, props and composables

[cols="1,2"]
|===
| Need | Prefer

| a value, flag or short string | a prop
| a block of markup chosen by the caller | a slot
| per-item markup that needs the child's loop variable | a scoped slot
| reusable stateful logic with no markup | a xref:web/vue/composables.adoc[composable]
| logic plus a slot-shaped API (a tracker, a virtual list) | a renderless component
|===
