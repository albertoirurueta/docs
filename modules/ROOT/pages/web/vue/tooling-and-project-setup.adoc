The official toolchain for a Vue application is `create-vue` on top of https://vite.dev/[Vite]. This page
covers scaffolding, the dev and build steps, and the editor and quality tools that understand `.vue` files.
See https://vuejs.org/guide/scaling-up/tooling.html[Tooling] for the canonical list.

== Scaffolding with `create-vue`

`create-vue` is the official project generator. It asks a few questions (TypeScript, JSX, Vue Router, Pinia,
Vitest, ESLint, Prettier) and writes a ready-to-run Vite project:

[source,bash]
----
npm create vue@latest
# then
cd my-app
npm install
npm run dev
----

The source lives at https://github.com/vuejs/create-vue[github.com/vuejs/create-vue]. A generated project
has `index.html` at the root as the entry document, `src/main.js` (or `.ts`) creating the app, `src/App.vue`
as the root component, and `+vite.config.*+` holding the `@vitejs/plugin-vue` setup.

[source,js]
----
// src/main.js
import { createApp } from 'vue'
import App from './App.vue'
import './assets/main.css'

createApp(App).mount('#app')
----

== Vite: dev server, HMR, and build

`npm run dev` starts Vite's dev server. It serves your source over native ES modules with no bundling, so
startup is near-instant, and it patches the running page on save through *hot module replacement* -- an edit
to a `.vue` file swaps just that component and keeps its state where possible.

`npm run build` runs `vite build`, which bundles and minifies (with Rolldown from Vite 8, Rollup in earlier versions), hashes asset filenames, and
writes a static `dist/` you can host anywhere. `npm run preview` serves that `dist/` locally to check it
before deploying.

=== From scaffold to static assets

[mermaid]
....
flowchart LR
    a["npm create vue@latest<br/>(scaffold)"] --> b["vite<br/>dev server + HMR"]

    b --> c["vite build<br/>(bundle and minify)"]
    c --> d["dist/<br/>static HTML, JS, CSS"]
    d --> e["any static host<br/>or SSR adapter"]
....

=== Environment modes

Vite loads `.env` files by *mode*. `dev` runs in mode `development`, `vite build` in mode `production`;
`--mode staging` selects `.env.staging`. Only keys prefixed `VITE_` are exposed to client code, as
`+import.meta.env.VITE_*+`:

[source,bash]
----
# .env.production
VITE_API_BASE=https://api.example.com
----

[source,js]
----
const base = import.meta.env.VITE_API_BASE
----

See https://vite.dev/guide/env-and-mode.html[Env Variables and Modes].

== Vue CLI is in maintenance mode

The older Webpack-based https://cli.vuejs.org/[Vue CLI] (`@vue/cli`) is in maintenance mode and is not
recommended for new projects; https://vuejs.org/guide/scaling-up/tooling.html#project-scaffolding[the Vue
docs] point all new work at `create-vue` and Vite. Migrate existing `vue-cli` projects when practical.

== Editor support: Vue Language Tools

https://github.com/vuejs/language-tools[Vue Language Tools] (the "Vue - Official" VS Code extension,
formerly Volar) provides SFC syntax highlighting, template IntelliSense, cross-block type checking, and
go-to-definition between `<template>` and `<script setup>`. Other editors consume the same
`@vue/language-server` over the Language Server Protocol. See
https://vuejs.org/guide/typescript/overview.html#ide-support[IDE support].

== Linting and formatting

https://eslint.vuejs.org/[`eslint-plugin-vue`] parses `.vue` files and lints the template as well as the
script -- unused components, invalid directive usage, required prop defaults, and more. Pair it with
https://prettier.io/[Prettier] for formatting and let ESLint defer stylistic rules to it. `create-vue`
wires both up on request; a flat config looks like:

[source,js]
----
// eslint.config.js
import pluginVue from 'eslint-plugin-vue'

export default [
  ...pluginVue.configs['flat/recommended'],
  { rules: { 'vue/multi-word-component-names': 'off' } },
]
----

== Type-checking SFCs with `vue-tsc`

`tsc` does not understand `.vue` files. https://github.com/vuejs/language-tools/tree/master/packages/tsc[`vue-tsc`]
wraps the TypeScript compiler with the same SFC support the editor uses, so CI can type-check templates and
`<script setup>` blocks:

[source,bash]
----
vue-tsc --noEmit -p tsconfig.json
----

`create-vue` adds this as the `type-check` script. Background in
https://vuejs.org/guide/typescript/overview.html[Using Vue with TypeScript] and
xref:web/vue/typescript.adoc[].

== Vue DevTools

https://devtools.vuejs.org/[Vue DevTools] inspects a running app -- the component tree, each component's
props and reactive state, an events and performance timeline, and panels for Vue Router routes and Pinia
stores. It ships three ways:

* **Browser extension (v7)** for Chrome, Firefox, and Edge -- adds a *Vue* tab to the browser devtools.
* **Standalone app** (`npm i -g @vue/devtools`) -- an Electron window, for debugging non-browser targets or
  older browsers.
* **Vite plugin** (`vite-plugin-vue-devtools`) -- embeds the DevTools UI as an in-page overlay in `dev`,
  with extra features such as an inspector that jumps from a rendered element to its source.

[source,js]
----
// vite.config.js
import vue from '@vitejs/plugin-vue'
import vueDevTools from 'vite-plugin-vue-devtools'

export default {
  plugins: [vue(), vueDevTools()],
}
----

=== A debugging workflow with DevTools

For the task app, a typical investigation moves through the panels in this order:

[cols="1,3"]
|===
| Panel | What to look at

| Components | select a component in the tree and read its props, `setup` state and exposed values; edit a ref in place to see the UI react
| Pinia | the `tasks` store's state and getters, with edits applied live; the history of actions and mutations for time-travel
| Timeline | a chronological record of component events, mouse and keyboard events, router navigations and Pinia actions; use it to answer "what ran, and in what order, when I clicked Add?"
| Routes | the matched route record, its params, and the full route table
| Performance | per-component render and update timings, to find the component that re-renders more than it should
|===

The Timeline and Pinia panels together answer most "why did this change?" questions: find the click event, see
the store action it triggered, and see which components then re-rendered. Production builds strip DevTools
support unless `app.config.devtools` is enabled, so debug against the dev server or a preview of a development
build.

== Worked example: wiring up the task app

The running example is a task list. This section shows the small, complete configuration of a project that
runs, builds, type-checks and lints it, and what each tool reports when something is wrong. Everything below was
run against a scaffold of this shape:

[source,text]
----
tasks-app/
  index.html
  package.json
  vite.config.ts
  tsconfig.json
  eslint.config.js
  .env.production
  src/
    main.ts
    App.vue
    env.d.ts
----

=== Who checks what

Four tools look at the same `.vue` files and each catches a different class of mistake, so none replaces
another:

[mermaid]
....
flowchart TB
    src["src/*.vue and src/*.ts"]
    src --> vite["Vite + @vitejs/plugin-vue<br/>compiles; reports syntax errors<br/>and unresolved imports"]
    src --> tsc["vue-tsc<br/>type errors in script AND template"]
    src --> lint["ESLint + eslint-plugin-vue<br/>bug patterns and style rules"]
    src --> lsp["Vue Language Tools<br/>the same checks, live in the editor"]
    vite --> out["dev server / dist/"]
    tsc --> ci["CI: npm run type-check"]
    lint --> ci2["CI: npm run lint"]
....

Vite never type-checks: a type error does not stop `vite build`. That is why the type check is a separate step.

=== `vite.config.ts` and `package.json`

The configuration needs the Vue plugin and, usually, an `@` alias for `src`:

[source,ts]
----
// vite.config.ts
import { fileURLToPath, URL } from 'node:url'
import { defineConfig } from 'vite'
import vue from '@vitejs/plugin-vue'

export default defineConfig({
  plugins: [vue()],
  resolve: { alias: { '@': fileURLToPath(new URL('./src', import.meta.url)) } },
})
----

[source,json]
----
{
  "type": "module",
  "scripts": {
    "dev": "vite",
    "build": "vite build",
    "preview": "vite preview",
    "type-check": "vue-tsc --noEmit -p tsconfig.json",
    "lint": "eslint src"
  }
}
----

`"type": "module"` makes Node load `vite.config.ts` and `eslint.config.js` as ES modules, which is what the
`import` syntax above needs.

=== Typed environment variables

`import.meta.env` is typed by `vite/client`, but custom `+VITE_*+` keys are `any` until you declare them. An
`env.d.ts` file narrows them:

[source,ts]
----
// src/env.d.ts
/// <reference types="vite/client" />

interface ImportMetaEnv {
  readonly VITE_API_BASE?: string
}
interface ImportMeta {
  readonly env: ImportMetaEnv
}
----

[source,vue]
----
<!-- src/App.vue -->
<script setup lang="ts">
import { ref } from 'vue'

const apiBase = import.meta.env.VITE_API_BASE ?? '/api'
const tasks = ref<string[]>([])

async function load() {
  const res = await fetch(`${apiBase}/tasks`)
  tasks.value = await res.json()
}
</script>

<template>
  <button @click="load">Load tasks ({{ apiBase }})</button>
  <ul><li v-for="t in tasks" :key="t">{{ t }}</li></ul>
</template>
----

With `.env.production` containing `VITE_API_BASE=https://api.example.com`, `npm run build` replaces
`import.meta.env.VITE_API_BASE` at build time, and the string `https://api.example.com` is found in the emitted
`+dist/assets/*.js+`. This is also why a `VITE_` value is never a secret: it ends up in the bundle.

=== Strict template checking with `vue-tsc`

Add `+"vueCompilerOptions": { "strictTemplates": true }+` to `tsconfig.json` and `vue-tsc` checks the *props
passed in templates*, not only the script. Given a child that declares `+defineProps<{ count: number }>()+` and
a parent that writes `+<Child :count="'x'" />+`:

[source,console]
----
$ npx vue-tsc --noEmit -p tsconfig.json
src/Bad.vue(7,11): error TS2322: Type 'string' is not assignable to type 'number'.
----

The error points into the `<template>` block of the `.vue` file, which plain `tsc` cannot do. A misspelt
template identifier (`+{{ titel }}+`) is reported the same way, with a "Did you mean 'title'?" hint.

=== ESLint for `.vue` files with TypeScript

`eslint-plugin-vue` alone parses plain JavaScript in `<script>`. When the block says `lang="ts"` the parser must
be a TypeScript-aware one; without it ESLint stops with `Parsing error: Unexpected token` on the first type
annotation. `@vue/eslint-config-typescript` (the config `create-vue` generates) wires both together:

[source,js]
----
// eslint.config.js
import pluginVue from 'eslint-plugin-vue'
import { defineConfigWithVueTs, vueTsConfigs } from '@vue/eslint-config-typescript'

export default defineConfigWithVueTs(
  pluginVue.configs['flat/essential'],
  vueTsConfigs.recommended,
)
----

Linting a component with an unkeyed `v-for` and a one-word name reports:

[source,console]
----
src/Todo.vue
  1:1  error  Component name "Todo" should always be multi-word             vue/multi-word-component-names
  6:5  error  Elements in iteration expect to have 'v-bind:key' directives  vue/require-v-for-key
----

Choose the preset by how strict you want to be: `flat/essential` (error prevention), `flat/strongly-recommended`
(readability) or `flat/recommended` (both plus the consistency rules). The presets map onto the priority levels
of the style guide described in xref:web/vue/style-guide-and-best-practices.adoc[].

=== Verifying the production build

`npm run build` writes `dist/`; `npm run preview` serves exactly those files. Because `preview` runs the
production bundle, it is the right place to confirm that environment variables, asset paths and lazy-loaded
chunks behave as they will once deployed (see xref:web/vue/performance-and-deployment.adoc[]).
