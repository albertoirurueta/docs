= Provide / Inject
:description: Passing data from an ancestor component to any descendant without prop drilling, using provide and inject, app-level provides, typed injection keys, default values, keeping injected state reactive, and when to reach for a store instead.
:keywords: Vue 3, provide, inject, dependency injection, prop drilling, InjectionKey, app.provide, injection default value, readonly, reactive provide, Pinia

include::partial$ai-disclaimer.adoc[]

`provide` and `inject` let an ancestor act as a dependency provider for its whole subtree: any descendant,
however deep, can ask for a value by key without every component in between forwarding it as a prop. This page
covers the API, typing it, keeping the shared value reactive, and where a store is the better tool.

image::vue-provide-inject.svg["Left: a user prop threaded through every intermediate component to reach a deep child. Right: an ancestor provides the value and the deep child injects it directly, leaving the middle components untouched",width=720,role=text-center]

== The problem: prop drilling

When only a deep descendant needs a value, passing it as a prop forces every component on the path to accept
and re-pass it. That noise is *prop drilling* -- the left side of the figure. `provide` / `inject` removes the
intermediate hops.

== provide and inject

The ancestor calls `provide(key, value)` in its `<script setup>`:

[source,vue]
----
<script setup>
import { provide, ref } from 'vue'

const theme = ref('dark')
provide('theme', theme)
</script>
----

Any descendant calls `inject(key)`:

[source,vue]
----
<script setup>
import { inject } from 'vue'

const theme = inject('theme')   // the same ref the ancestor provided
</script>
----

Both must run *synchronously during setup*. See
https://vuejs.org/guide/components/provide-inject.html[Provide / Inject].

== App-level provide

`app.provide()` registers a value visible to *every* component the app renders. It is the natural home for
app-wide configuration and also works from inside a plugin:

[source,js]
----
import { createApp } from 'vue'

const app = createApp(App)
app.provide('apiBase', '/api/v1')
----

See https://vuejs.org/api/application.html#app-provide[`app.provide()`].

== Injection keys

A string key works, but a `Symbol` avoids collisions across a large app or a library. In TypeScript, typing
that symbol as `InjectionKey<T>` makes both ends type-safe: `provide` checks the value and `inject` infers the
result.

[source,ts]
----
// keys.ts
import type { InjectionKey, Ref } from 'vue'

export interface UserSession {
  id: string
  name: string
}

export const sessionKey = Symbol('session') as InjectionKey<Ref<UserSession | null>>
----

[source,ts]
----
// provider -- type error unless `session` is Ref<UserSession | null>
provide(sessionKey, session)

// consumer -- inferred as Ref<UserSession | null> | undefined
const session = inject(sessionKey)
----

See https://vuejs.org/guide/components/provide-inject.html#working-with-symbol-keys[Working with Symbol Keys].

== Default values

`inject` returns `undefined` when no provider is found (and warns in development). Pass a second argument as
the fallback; pass a factory plus `true` as the third argument when the default is expensive or must not be
shared between consumers:

[source,ts]
----
const theme = inject('theme', 'light')                 // simple default
const list = inject('list', () => reactive([]), true)  // factory default
----

== Keeping injected values reactive

Provide a `ref`, a `reactive` object, or a `computed` -- not a plain unwrapped value -- so that when the
ancestor updates it, every injecting descendant re-renders:

[source,vue]
----
<script setup>
import { provide, reactive, readonly } from 'vue'

const store = reactive({ count: 0 })

function increment() {
  store.count++
}

// hand out a read-only view plus an explicit mutator, so descendants
// cannot mutate the shared state directly
provide('counter', {
  state: readonly(store),
  increment
})
</script>
----

Keeping mutations inside the providing component -- and passing `readonly()` outward -- keeps the data flow
traceable. See
https://vuejs.org/guide/components/provide-inject.html#working-with-reactivity[Working with Reactivity].

== How lookup works

Each component instance inherits the `provides` object of its *parent* and, when it calls `provide()`, gets its own
copy that shadows the inherited keys. `inject()` therefore walks no tree at call time; it reads the closest
ancestor's value for that key. Three rules follow, all confirmed by mounting small component trees:

* *The nearest provider wins.* A descendant below a second `provide()` of the same key sees the inner value, and
  siblings outside it still see the outer one.
* *A component never injects its own provide.* `inject()` reads from the parent chain, so calling it in the same
  component that provides the key returns the fallback (or `undefined`).
* *No provider means the default.* Without a second argument `inject()` returns `undefined` and warns in development.

== Worked example: a to-do provider with a guarded consumer

The to-do list used across this section has a list, an item and a counter that all need the same state. Instead of
threading props through the list, a provider component exposes a small API and every consumer calls one typed
composable. The `useTodos()` function turns a missing provider into an explicit error, instead of a vague
`undefined` several calls later:

[source,js]
----
// todos.js
import { inject, provide, reactive, readonly, computed } from 'vue'

export const todosKey = Symbol('todos')

export function provideTodos(initial = []) {
  const state = reactive({ items: initial })
  const remaining = computed(() => state.items.filter(t => !t.done).length)
  const api = {
    state: readonly(state),            // consumers read, but cannot mutate
    remaining,
    add(text) { state.items.push({ id: state.items.length + 1, text, done: false }) },
    toggle(id) {
      const t = state.items.find(t => t.id === id)
      if (t) t.done = !t.done
    },
  }
  provide(todosKey, api)
  return api
}

export function useTodos() {
  const api = inject(todosKey, null)
  if (!api) throw new Error('useTodos() needs a <TodoProvider> ancestor')
  return api
}
----

A provider component calls `+provideTodos([...])+` in its `<script setup>`; the list, each `TodoItem` and the counter call
`+const { state, toggle, remaining } = useTodos()+` at any depth. A test that mounts a provider over three levels of
components confirms the behaviour:

* toggling an item in one consumer updates the `remaining` counter in a sibling consumer (the provided `computed`
  and `reactive` state are the single source of truth);
* assigning through `+state.items.push(...)+` from a consumer logs "target is readonly" and leaves the list unchanged;
* mounting a consumer with no provider throws the explicit error above.

Exposing `add` and `toggle` rather than the raw `reactive` object is what keeps every mutation in one file, so a
search for `toggle` finds every place todos change. The same shape works for a tab group (a `TabList` providing the
active id) or a form (a `Form` providing a registration function to its fields).

== provide/inject vs. a store

`provide` / `inject` is a *tree-scoped* tool: it shines for a widget family that shares context (a form and
its fields, a tab group, a design-system theme) and for skipping a couple of prop hops. It is not a general
application state container -- no devtools timeline, no cross-tree access, and testing a consumer means
mounting it under a provider.

When state is genuinely global, mutated from many unrelated places, or needs tooling and hot-module
replacement, use a store -- in the Vue ecosystem that is https://pinia.vuejs.org/[Pinia]; see
xref:web/vue/state-management.adoc[] for the comparison. Angular's hierarchical injector solves the same
tree-scoping problem -- see xref:web/angular/index.adoc[].
