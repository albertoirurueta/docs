= Functions
:description: Covers user-defined Sass functions with @function and @return, arguments and defaults, variadic parameters, how functions differ from mixins, and pointers to the built-in sass module functions.
:keywords: Sass functions, @function, @return, custom function, Sass function arguments, functions vs mixins, pure function, @error, @warn, Sass built-in functions

include::partial$ai-disclaimer.adoc[]

A Sass function takes arguments and *returns a value*. Unlike a xref:web/sass/mixins.adoc[mixin], it emits no
CSS of its own -- its result is used wherever a value is expected: a property value, a variable declaration, an
argument to another function, or a condition.

== Defining a function

`@function` declares one; `@return` produces its value.

[source,scss]
----
@use "sass:math";

@function rem($px, $base: 16px) {
  @return math.div($px, $base) * 1rem;
}

.title {
  font-size: rem(24px);       // 1.5rem
  margin-bottom: rem(12px);   // 0.75rem
}
----

[source,css]
----
.title {
  font-size: 1.5rem;
  margin-bottom: 0.75rem;
}
----

A function body may contain variables and control flow, but every path through it must reach a `@return` --
falling off the end without returning is an error.

[source,scss]
----
@use "sass:color";

@function contrast-colour($background) {
  @if color.channel($background, "lightness", $space: hsl) > 55% {
    @return #212121;
  } @else {
    @return #ffffff;
  }
}

.badge {
  background: #ffeb3b;
  color: contrast-colour(#ffeb3b);   // #212121
}
----

`@return` may only appear inside a function -- it is not a general "exit" for mixins or stylesheets.

=== What happens on a call

A function call is an ordinary expression, so the compiler evaluates it at the point the value is needed and substitutes
the result. Nothing of the call survives into the CSS:

[mermaid]
....
sequenceDiagram
    participant Rule as Rule being evaluated
    participant Call as Function call
    participant Body as Function body

    Rule->>Call: font-size: rem(24px)
    Call->>Call: bind arguments<br/>positional, named, then defaults
    Call->>Body: run statements in a new scope
    alt a path reaches @return
        Body-->>Call: value 1.5rem
        Call-->>Rule: replace the call with 1.5rem
    else @error is reached
        Body--xRule: abort compilation with message and trace
    end
....

The body runs in its own scope: variables it assigns are local, and the caller's variables are not visible by name
unless they are global. That is also why a function cannot "return early" from the rule that called it; it only
produces a value.

== Arguments

Functions take arguments exactly the way mixins do: positionally or by name, with optional defaults, and with an
optional trailing variadic parameter.

[source,scss]
----
@use "sass:math";
@use "sass:list";

@function strip-unit($number) {
  @if math.is-unitless($number) {
    @return $number;
  }
  @return math.div($number, ($number * 0 + 1));
}

@function sum($numbers...) {
  $total: 0;
  @each $n in $numbers {
    $total: $total + $n;
  }
  @return $total;
}

@function clamp-between($value, $min: 0, $max: 100) {
  @return math.max($min, math.min($max, $value));
}

$a: strip-unit(24px);            // 24
$b: sum(4px, 8px, 12px);         // 24px
$c: clamp-between(150, $max: 64); // 64
----

Named arguments make a function call readable at the call site, and -- as with mixins -- renaming a parameter is
a breaking change for callers who use its name.

=== Argument lists and spreading

A trailing variadic parameter such as `+$nums...+` collects the remaining positional arguments into an *argument list*, and any named
arguments the caller passes that match no parameter go into a keyword map that `meta.keywords()` returns. The same
`+...+` syntax at a call site spreads a list into positional arguments, or a map into named arguments:

[source,scss]
----
@use "sass:meta";

@function describe($args...) {
  @return meta.inspect(meta.keywords($args)) + " / " + meta.inspect($args);
}

@function sum($nums...) {
  $total: 0;
  @each $n in $nums {
    $total: $total + $n;
  }
  @return $total;
}

$box: (padding: 4px, margin: 8px);

.args {
  mixed: describe(1, 2, $x: 3, $y: 4);
  spread-map: describe($box...);
  spread-list: sum((3px, 4px)...);
}
----

[source,css]
----
.args {
  mixed: (x: 3, y: 4) / 1, 2;
  spread-map: (padding: 4px, margin: 8px) / ();
  spread-list: 7px;
}
----

Spreading is how a wrapper function forwards everything it receives to another function without listing the
parameters twice.

== Functions vs. mixins

They look similar and are easy to confuse. The distinction is what they produce:

[cols="1,2,2", options="header"]
|===
| | Function | Mixin

| Declared with
| `@function`
| `@mixin`

| Invoked with
| `name(args)` -- in a value position
| `@include name(args)` -- in a statement position

| Produces
| A single value, via `@return`
| CSS declarations and/or rules

| Emits CSS directly
| No
| Yes

| Can accept a block
| No
| Yes, via `@content`

| Typical use
| Compute a size, transform a colour, look up a token
| Apply a group of declarations, wrap a media query
|===

The rule of thumb: **if you want a number, colour, string, list, or map back, write a function; if you want
declarations to appear in the output, write a mixin.** They compose naturally -- a mixin's body commonly calls
functions to compute the values it emits.

[source,scss]
----
@use "sass:math";

@function rem($px, $base: 16px) { @return math.div($px, $base) * 1rem; }

@mixin type-scale($px, $line-height: 1.5) {
  font-size: rem($px);
  line-height: $line-height;
}

h1 { @include type-scale(32px); }
----

== Functions are pure

A Sass function should be a pure computation: same arguments in, same value out, with no side effects. Sass does
not enforce this -- a function body can technically reassign an outer variable -- but doing so makes stylesheets
unpredictable, because the compiler is free to evaluate expressions in an order you did not write.

Practically, this means a function should not use `!global`, and should not rely on being called a particular
number of times.

== Reporting problems: `@error`, `@warn`, `@debug`

Argument validation belongs in the function itself, so a mistake fails at compile time with a useful message
rather than emitting nonsense CSS.

[source,scss]
----
@use "sass:math";
@use "sass:meta";

@function rem($px, $base: 16px) {
  @if meta.type-of($px) != number {
    @error "rem() expects a number, got `#{$px}` (#{meta.type-of($px)}).";
  }
  @if math.is-unitless($px) {
    @warn "rem() was given a unitless value `#{$px}`; assuming px.";
    $px: $px * 1px;
  }
  @return math.div($px, $base) * 1rem;
}
----

* **`@error`** aborts compilation and prints the message with a stack trace. Use it for a genuine misuse.
* **`@warn`** prints a message and continues. Use it for deprecations and recoverable oddities.
* **`@debug`** prints a value for inspection during development; strip these before shipping.

== Recursion

A function may call itself, which is the only way to loop *inside* a function body when the work is not a simple
accumulation. Each call needs a base case, as in any language. Two classic examples are an integer power and a
string replacement, which Sass lacks as built-ins:

[source,scss]
----
@use "sass:string";

@function ipow($base, $exp) {
  @if $exp == 0 { @return 1; }
  @return $base * ipow($base, $exp - 1);
}

@function str-replace($string, $search, $replace: "") {
  $index: string.index($string, $search);
  @if $index {
    @return string.slice($string, 1, $index - 1) + $replace +
      str-replace(string.slice($string, $index + string.length($search)), $search, $replace);
  }
  @return $string;
}

.rec {
  power: ipow(2, 10);
  replaced: str-replace("a-b-c", "-", "+");
}
----

[source,css]
----
.rec {
  power: 1024;
  replaced: "a+b+c";
}
----

Recursion depth is limited by the compiler's stack, so keep it for small inputs; for numeric powers prefer
`math.pow()`, and for walking a list prefer `@each`.

== Worked example: a design-token module

The most common home for functions is a small module that the rest of the stylesheet imports, turning raw design
numbers into validated values. This one converts units, derives a modular scale, computes WCAG contrast to choose
readable text colours, and reads nested token maps with a helpful failure message:

[source,scss]
----
// _tokens.scss
@use "sass:math";
@use "sass:color";
@use "sass:map";
@use "sass:meta";

/// px to rem, validating the argument.
@function rem($px, $base: 16px) {
  @if meta.type-of($px) != number {
    @error "rem() expects a number, got `#{$px}` (#{meta.type-of($px)}).";
  }
  @return math.div($px, $base) * 1rem;
}

/// Modular scale: base * ratio^step.
@function scale-step($step, $base: 16px, $ratio: 1.25) {
  @return $base * math.pow($ratio, $step);
}

// Private helper: linear value of one sRGB channel (0-255), as WCAG defines it.
@function -linear($channel) {
  $c: math.div($channel, 255);
  @if $c <= 0.03928 {
    @return math.div($c, 12.92);
  }
  @return math.pow(math.div($c + 0.055, 1.055), 2.4);
}

@function luminance($color) {
  $r: -linear(color.channel($color, "red", $space: rgb));
  $g: -linear(color.channel($color, "green", $space: rgb));
  $b: -linear(color.channel($color, "blue", $space: rgb));
  @return 0.2126 * $r + 0.7152 * $g + 0.0722 * $b;
}

@function contrast-ratio($a, $b) {
  $la: luminance($a);
  $lb: luminance($b);
  @return math.div(math.max($la, $lb) + 0.05, math.min($la, $lb) + 0.05);
}

/// The more readable of two text colours on a background.
@function readable-on($bg, $light: #ffffff, $dark: #212121) {
  @if contrast-ratio($bg, $light) >= contrast-ratio($bg, $dark) {
    @return $light;
  }
  @return $dark;
}

/// Walk nested maps by key path and fail loudly on a miss.
@function token($map, $keys...) {
  $value: $map;
  @each $key in $keys {
    @if meta.type-of($value) != map or not map.has-key($value, $key) {
      @error "No token at `#{$keys}` (stopped at `#{$key}`).";
    }
    $value: map.get($value, $key);
  }
  @return $value;
}
----

[source,scss]
----
// main.scss
@use "tokens" as t;

$tokens: (
  space: (sm: 8px, md: 16px),
  colour: (primary: #3f51b5, accent: #ffeb3b)
);

.card {
  padding: t.token($tokens, space, md);
  font-size: t.rem(18px);
  line-height: t.scale-step(1, 1rem);
  background: t.token($tokens, colour, primary);
  color: t.readable-on(t.token($tokens, colour, primary));
}

.badge {
  background: t.token($tokens, colour, accent);
  color: t.readable-on(t.token($tokens, colour, accent));
}

.audit { ratio: t.contrast-ratio(#ffffff, #3f51b5); }
----

[source,css]
----
.card {
  padding: 16px;
  font-size: 1.125rem;
  line-height: 1.25rem;
  background: #3f51b5;
  color: #ffffff;
}

.badge {
  background: #ffeb3b;
  color: #212121;
}

.audit {
  ratio: 6.8727097437;
}
----

White text on the indigo brand colour has a contrast ratio of about 6.9, comfortably above the 4.5 that WCAG AA asks of
body text, so `readable-on()` picks white; on the yellow badge it picks the dark grey. The function stays small
because each step is its own named, testable function, and a mistake fails the build with a pointed message instead
of emitting invalid CSS:

----
Error: "No token at `space, lg` (stopped at `lg`)."
Error: "rem() expects a number, got `red` (color)."
Error: Private members can't be accessed from outside their modules.
----

The three messages come from `t.token((space: (sm: 8px)), space, lg)`, `t.rem(red)` and `t.-linear(1)`: the first
two are the module's own `@error` calls, and the third is the compiler enforcing the leading hyphen on `-linear`.

== Naming and namespacing

Custom functions live in a module like any other member (see
xref:web/sass/partials-modules.adoc[Partials & Modules]), so they are called through their module's namespace:

[source,scss]
----
// _units.scss
@use "sass:math";
@function rem($px, $base: 16px) { @return math.div($px, $base) * 1rem; }
----

[source,scss]
----
@use "units";
.title { font-size: units.rem(24px); }
----

A function whose name starts with `-` or `_` is private to its module.

Avoid naming a custom function after a plain CSS function (`calc`, `min`, `max`, `clamp`, `translate`,
`url`...). Sass has to decide whether such a call is yours or CSS's, and shadowing one leads to surprising
output. Prefixing project functions (`app-min()`, or namespacing through a module) sidesteps the problem
entirely.

== Built-in functions

Sass ships a substantial standard library -- maths, colour manipulation, list and map operations, string
handling, selector introspection, and metaprogramming -- organised into `+sass:*+` modules loaded with `@use`:

[source,scss]
----
@use "sass:math";
@use "sass:color";

.button {
  width: math.div(100%, 3);
  background: color.adjust(#3f51b5, $lightness: -10%);
}
----

Those are documented on their own page rather than listed here -- see
xref:web/sass/built-in-modules.adoc[Built-in Modules] for the module-by-module reference. Note that the older
*global* forms of these functions (`darken()`, `map-get()`, `nth()`, and so on) still work but are deprecated in
favour of the namespaced module versions.
