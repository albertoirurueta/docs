= Nesting
:description: Covers Sass nested selectors and how they flatten into CSS, the & parent selector for pseudo-classes and compound patterns like &.active and BEM suffixes, nested properties, nested media queries, and how Sass nesting compares to native CSS nesting.
:keywords: Sass nesting, nested selectors, parent selector, ampersand selector, &:hover, &::before, BEM Sass, nested properties, nested media queries, selector flattening, native CSS nesting

include::partial$ai-disclaimer.adoc[]

Nesting lets a stylesheet's structure mirror the structure of the markup it styles, so a shared selector prefix
is written once instead of repeated on every line. At compile time Sass *flattens* the nesting back into
ordinary descendant selectors.

== Nested selectors

[source,scss]
----
nav {
  background: #222;

  ul {
    margin: 0;
    padding: 0;
    list-style: none;

    li {
      display: inline-block;

      a {
        display: block;
        padding: 6px 12px;
        color: white;
      }
    }
  }
}
----

Each nesting level becomes a descendant combinator (a space) in the output:

[source,css]
----
nav { background: #222; }
nav ul { margin: 0; padding: 0; list-style: none; }
nav ul li { display: inline-block; }
nav ul li a { display: block; padding: 6px 12px; color: white; }
----

The flattening is purely textual concatenation of the selector at each level:

[mermaid]
....
flowchart TB
    A["nav"] --> B["ul"]
    B --> C["li"]
    C --> D["a"]

    A -.compiles to.-> A2["nav"]
    B -.compiles to.-> B2["nav ul"]
    C -.compiles to.-> C2["nav ul li"]
    D -.compiles to.-> D2["nav ul li a"]
....

=== Keep nesting shallow

Nesting is the feature most often overused. Every level adds a descendant combinator, and the result is long,
highly specific selectors that are hard to override later (see
xref:web/html-css/selectors-specificity.adoc[Selectors & specificity] for why specificity escalation hurts).
The example above produces `nav ul li a` -- four levels of specificity to style a link that a single `.nav-link`
class would have handled.

A widely used rule of thumb is the **inception rule**: never nest more than three levels deep. In practice,
combining shallow nesting with flat, meaningful class names (BEM, below) is better than deep nesting that
mirrors the DOM exactly.

Other selectors can be nested too, not just descendants -- put the combinator before the nested selector:

[source,scss]
----
.menu {
  > li { /* .menu > li -- direct children only */ }
  + .menu { /* .menu + .menu -- adjacent sibling */ }
  ~ .footer { /* .menu ~ .footer -- general sibling */ }
}
----

== The `&` parent selector

`&` stands for the *full compiled selector of the enclosing block*. It is what makes nesting useful for anything
other than descendants, because it lets the nested selector attach directly to the parent rather than being
separated by a space.

[source,scss]
----
.button {
  background: #3f51b5;
  color: white;

  &:hover        { background: #32408f; }   // .button:hover
  &:focus-visible { outline: 2px solid; }   // .button:focus-visible
  &::before      { content: "→ "; }         // .button::before
  &.is-active    { background: #1a237e; }   // .button.is-active
  &[disabled]    { opacity: 0.5; }          // .button[disabled]
}
----

Without `&`, writing `+:hover { ... }+` inside `.button` would compile to `.button :hover` -- a descendant --
which is almost never what is meant.

=== `&.is-active` vs. `& .is-active` vs. plain `.is-active`

Whether a class attaches to the parent or sits inside it depends on the space after (or the absence of) `&`.
Both a plain nested `.is-active` and `+& .is-active+` are descendant selectors; only `+&.is-active+` targets the
*same element* carrying two classes:

[source,scss]
----
.menu {
  &.is-active   { color: red; }   // .menu.is-active   -- one element with both classes
  & .is-active  { color: red; }   // .menu .is-active  -- descendant
  .is-active    { color: red; }   // .menu .is-active  -- identical to the line above
}
----

Chaining works with any number of classes, and the compiled selector is exactly the one written in plain CSS:

[source,scss]
----
.tarjeta {
  &.destacado.activo { border-color: gold; }   // .tarjeta.destacado.activo
}
----

The compiled rule only matches `<div class="tarjeta destacado activo">`. See
xref:web/html-css/selectors-specificity.adoc#multiple-classes[Elements with multiple classes] and xref:web/html-css/selectors-specificity.adoc#class-combinators-compared[Combining two classes] for the plain CSS semantics.

=== `&` in other positions

`&` need not come first. Putting something before it inverts the relationship, which is the idiomatic way to
express "when some ancestor or state applies to me":

[source,scss]
----
.icon {
  fill: currentColor;

  .button & { margin-right: 4px; }        // .button .icon
  [data-theme="dark"] & { fill: #ccc; }   // [data-theme=dark] .icon
  .sidebar &:hover { fill: red; }         // .sidebar .icon:hover
}
----

=== Suffixing `&` for BEM

`&` can also be concatenated with a plain string suffix, which is what makes Sass a natural fit for BEM-style
naming -- the block name is written once and each element/modifier hangs off it:

[source,scss]
----
.card {
  padding: 1rem;
  border: 1px solid #ddd;

  &__title  { font-size: 1.25rem; }   // .card__title
  &__body   { color: #555; }          // .card__body

  &--featured {                       // .card--featured
    border-color: gold;

    .card__title { color: gold; }
  }
}
----

Note that `+&--featured+` does not select two classes on one element: it creates a *new class name*,
`+.card--featured+`, which is added *alongside* the base class in the markup
(`+class="card card--featured"+`). By contrast `+&.featured+` compiles to `+.card.featured+` and targets an
element that carries the two classes `card` and `featured`. See xref:web/html-css/selectors-specificity.adoc#multiple-classes[Elements with multiple classes].

This is convenient, but it has a real cost: searching the codebase for `+.card__title+` will not find
`+&__title+`. Teams that rely heavily on grep-ability often prefer to write such class names out in full.

Note that `&` always represents the *entire* parent selector, including every comma-separated part of it. When
the parent is a selector list, `&` expands to that whole list, which can produce more output than expected:

[source,scss]
----
.alpha, .beta {
  & + & { margin-top: 8px; }
}
// compiles to:
// .alpha + .alpha, .alpha + .beta, .beta + .alpha, .beta + .beta { margin-top: 8px; }
----

`&` is also available as an ordinary value inside `@if`, functions, and interpolation, which lets mixins branch
on the context they were included in.

== Nested properties

CSS has many families of properties sharing a hyphenated prefix -- `+font-*+`, `+margin-*+`, `+border-*+`,
`+background-*+`. Sass lets that prefix be factored out into a nested block:

[source,scss]
----
.headline {
  font: {
    family: Georgia, serif;
    weight: bold;
    size: 2em;
    style: italic;
  }

  margin: auto {
    top: 2rem;
    bottom: 1rem;
  }
}
----

Compiles to:

[source,css]
----
.headline {
  font-family: Georgia, serif;
  font-weight: bold;
  font-size: 2em;
  font-style: italic;
  margin: auto;
  margin-top: 2rem;
  margin-bottom: 1rem;
}
----

Note the colon after the prefix (`font:`), and the second form -- `+margin: auto { ... }+` -- which sets the
shorthand *and* specific longhands in one block.

== Nesting media queries

A `@media` rule may be nested inside a style rule, and Sass will bubble it up to the top level of the output
while preserving the selector. This lets a component's responsive behaviour live next to its base styles rather
than in a separate breakpoint section at the bottom of the file:

[source,scss]
----
$breakpoint-md: 768px;

.sidebar {
  width: 100%;

  @media (min-width: $breakpoint-md) {
    width: 280px;
    float: left;
  }
}
----

[source,css]
----
.sidebar { width: 100%; }
@media (min-width: 768px) {
  .sidebar { width: 280px; float: left; }
}
----

Nested media queries pair particularly well with a breakpoints map and a mixin -- see
xref:web/sass/mixins.adoc[Mixins] and xref:web/sass/lists-maps.adoc[Lists & Maps].

=== How nested at-rules bubble and merge

`@media` and `@supports` are not selectors, so Sass cannot flatten them into a descendant chain. Instead it lifts the
at-rule out to the top level and re-creates the enclosing selector inside it. When at-rules are nested in one
another, the conditions are combined: media queries with `and`, a `@media` inside `@supports` stays inside it.

[source,scss]
----
$md: 768px;
$lg: 1024px;

.layout {
  display: block;

  @media (min-width: $md) {
    display: flex;
    @media (min-width: $lg) { gap: 2rem; }
    @media (orientation: landscape) { flex-direction: row; }
  }

  @supports (display: grid) {
    display: grid;
    @media (min-width: $md) { grid-template-columns: 1fr 2fr; }
  }

  .sidebar {
    width: 100%;
    @media (min-width: $md) { width: 280px; }
  }
}
----

[source,css]
----
.layout {
  display: block;
}
@media (min-width: 768px) {
  .layout {
    display: flex;
  }
}
@media (min-width: 768px) and (min-width: 1024px) {
  .layout {
    gap: 2rem;
  }
}
@media (min-width: 768px) and (orientation: landscape) {
  .layout {
    flex-direction: row;
  }
}
@supports (display: grid) {
  .layout {
    display: grid;
  }
  @media (min-width: 768px) {
    .layout {
      grid-template-columns: 1fr 2fr;
    }
  }
}
.layout .sidebar {
  width: 100%;
}
@media (min-width: 768px) {
  .layout .sidebar {
    width: 280px;
  }
}
----

[mermaid]
....
flowchart TB
    S["Source: .layout { @media A { ... @media B { ... } } }"] --> L["Collect declarations<br/>for each nesting level"]
    L --> R1[".layout { base declarations }"]
    L --> R2["@media A { .layout { ... } }"]
    L --> R3["@media A and B { .layout { ... } }"]
....

Notice that the output is *not* grouped by query: every nested `@media` produces its own block next to the rule that
contained it. If the same query appears in fifty components the compiled CSS contains fifty copies. Build tools such
as PostCSS with a media-query merger can combine them afterwards, at the cost of changing the cascade order, so it is
rarely worth doing blindly.

== Escaping the nesting with `@at-root`

Sometimes a rule must be written in the middle of a block for readability but emitted at the top level.
`@at-root` does exactly that. It also gives full control over where `&` ends up:

[source,scss]
----
.card {
  padding: 1rem;

  @at-root .card-grid & { display: grid; }   // .card-grid .card
  @at-root #{&}__icon { width: 1em; }        // .card__icon
  @at-root {
    .utility-hidden { display: none; }       // no .card prefix at all
  }

  &__title { font-size: 1.25rem; }
}
----

[source,css]
----
.card {
  padding: 1rem;
}
.card-grid .card {
  display: grid;
}

.card__icon {
  width: 1em;
}

.utility-hidden {
  display: none;
}

.card__title {
  font-size: 1.25rem;
}
----

By default `@at-root` escapes only style rules; an enclosing `@media` is kept. The `+(without: ...)+` and
`+(with: ...)+` queries choose what to escape. `+(without: media)+` steps out of the media query as well:

[source,scss]
----
@media print {
  .sheet {
    color: black;
    @at-root (without: media) { .screen-only { display: none; } }
  }
}
----

[source,css]
----
@media print {
  .sheet {
    color: black;
  }
}
.sheet .screen-only {
  display: none;
}
----

Note that the escaped rule still carries the `.sheet` parent selector, because only the media query was escaped.

== Declarations after nested rules

CSS allows declarations and nested rules to be interleaved, and current Dart Sass preserves that order rather than
hoisting declarations to the top:

[source,scss]
----
.card {
  color: red;
  .x { a: b; }
  color: blue;
}
----

[source,css]
----
.card {
  color: red;
}
.card .x {
  a: b;
}
.card {
  color: blue;
}
----

The compiler emits a second `.card` block so the final `color: blue` still comes after the nested rule, matching
how native CSS nesting treats the same source. In practice, keep declarations at the top of a block and nested
rules below them, and the output stays in one rule.

== The `&` parent selector as a value

Besides its role in selectors, `&` is a Sass value: the list of parent selectors, or `null` at the top level. This
lets mixins adapt to where they are included:

[source,scss]
----
@mixin when-inside($ancestor) {
  #{$ancestor} & { @content; }
}

.icon {
  @include when-inside(".button") { margin-right: 4px; }
}

@mixin context { @if & { in-rule: yes; } @else { @at-root .global { top: yes; } } }
@include context;        // included at the top level: & is null
.q { @include context; } // included inside a rule
----

[source,css]
----
.button .icon {
  margin-right: 4px;
}

.global {
  top: yes;
}

.q {
  in-rule: yes;
}
----

The `sass:selector` module builds on the same idea. `+selector.append(".card", "--featured")+` returns `+.card--featured+`
and can be used as a selector through interpolation, which is the programmatic equivalent of `&--featured`:

[source,scss]
----
@use "sass:selector";

$sel: selector.append(".card", "--featured");

#{$sel} { x: y; }   // .card--featured { x: y; }
----

== Worked example: a navigation component

The sections above combine into one component. This navigation bar uses BEM naming through `&`, grouped state
selectors, an ancestor-context rule written with `&` at the end, a responsive layout nested in the block, and one
`@at-root` rule that lives with the component but is global:

[source,scss]
----
$md: 768px;

.nav {
  display: flex;
  flex-direction: column;
  background: #222;

  &__item {
    list-style: none;
  }

  &__link {
    display: block;
    padding: 6px 12px;
    color: white;

    &:hover,
    &:focus-visible { background: #444; }

    &.is-active { font-weight: bold; }

    .nav--compact & { padding: 2px 8px; }
  }

  &--compact { background: #111; }

  @media (min-width: $md) {
    flex-direction: row;

    &__link { padding: 6px 20px; }
  }

  @at-root .skip-link { position: absolute; }
}
----

Compiled output:

[source,css]
----
.nav {
  display: flex;
  flex-direction: column;
  background: #222;
}
.nav__item {
  list-style: none;
}
.nav__link {
  display: block;
  padding: 6px 12px;
  color: white;
}
.nav__link:hover, .nav__link:focus-visible {
  background: #444;
}
.nav__link.is-active {
  font-weight: bold;
}
.nav--compact .nav__link {
  padding: 2px 8px;
}
.nav--compact {
  background: #111;
}
@media (min-width: 768px) {
  .nav {
    flex-direction: row;
  }
  .nav__link {
    padding: 6px 20px;
  }
}
.skip-link {
  position: absolute;
}
----

Three things are worth reading off the result. The deepest selector is `+.nav--compact .nav__link+`, two classes, even
though the source nests four levels deep, because the BEM suffixes concatenate rather than stack. The `&:hover,
&:focus-visible` group expanded into one comma-separated selector. And the `@media` block did not go to the end of the
file: it sits where it was written, after the rules that precede it in the source.

== Comparison with native CSS nesting

CSS itself now has nesting, and modern browsers support it directly with no build step. It was explicitly
modelled on what Sass had been doing for years -- see the *Native CSS nesting* subsection of
xref:web/html-css/selectors-specificity.adoc[Selectors & specificity] for the CSS-side rules.

The syntax is close enough that most Sass nesting reads as valid CSS nesting, but a few differences are worth
knowing:

* **`&` is not optional in the same places.** Native CSS is stricter about where a bare element selector may
  appear nested, and `&` behaves as a real compound selector there rather than a textual substitution.
* **String concatenation does not work.** `+&__title+` is a Sass-only trick. Native CSS nesting cannot build a new
  class name by gluing text onto `&`, so BEM suffixing has no native equivalent.
* **Specificity differs.** Native `&` takes the specificity of the *most specific* selector in the parent list
  (like `:is()`), whereas Sass simply pastes the selector text in, so the two can compute different specificity
  for the same-looking rule.
* **Output size.** Sass flattens at compile time and ships plain, widely-compatible selectors; native nesting
  ships the nesting itself, which is smaller over the wire but requires browser support.

Since Sass compiles nesting away entirely, the two do not conflict: a Sass file can use Sass nesting throughout
and still emit CSS that runs anywhere.
