= Compilation
:description: Explains why Sass must be compiled to plain CSS before a browser can use it, Dart Sass as the current official implementation with LibSass and Ruby Sass deprecated, and the CLI, bundler and editor-extension paths that feed the same compiler.
:keywords: Sass compilation, Dart Sass, sass CLI, LibSass deprecated, Ruby Sass, sass-loader, Vite Sass, source maps, compressed output style, watch mode, sass-embedded, compile on save

include::partial$ai-disclaimer.adoc[]

Browsers do not understand Sass. No browser has ever shipped support for `$variables`, `@mixin`, `@use`, or the
indented syntax, and none is planning to. Sass is a **build-time** language: a compiler reads your `.scss`/
`.sass` sources and emits plain `.css` that any browser can parse. Everything documented in this section --
variables, nesting, mixins, functions, control flow, modules -- exists only in the source and is gone by the
time the stylesheet is served.

This is the fundamental difference between a Sass variable and a CSS custom property (see
xref:web/sass/variables.adoc[Variables]): one is erased at compile time, the other is shipped and live in the
browser.

== The pipeline

[mermaid]
....
flowchart LR
    subgraph entry["Entry points"]
        CLI["sass CLI<br/>sass src:dist --watch"]
        BUNDLER["Bundler<br/>Vite / Webpack sass-loader"]
        EDITOR["Editor extension<br/>compile on save"]
    end

    SRC[".scss / .sass sources<br/>+ partials"]
    COMPILER["Dart Sass compiler"]
    CSS["plain .css output"]
    MAP["source map (.css.map)"]
    BROWSER["Browser"]

    SRC --> CLI
    SRC --> BUNDLER
    SRC --> EDITOR

    CLI --> COMPILER
    BUNDLER --> COMPILER
    EDITOR --> COMPILER

    COMPILER --> CSS
    COMPILER -.-> MAP
    CSS --> BROWSER
    MAP -.debugging.-> BROWSER

    classDef core fill:#3f51b5,stroke:#1a237e,color:#fff
    class COMPILER core
....

All three entry points drive the *same* compiler. Choosing between them is a workflow decision, not a
capability one -- the CSS produced is identical.

=== What the compiler does

Whatever the entry point, a compilation is the same four stages. Knowing them explains most error messages: a syntax
error comes from stage 1, a missing file from stage 2, a unit mismatch or failed `@error` from stage 3.

[mermaid]
....
sequenceDiagram
    participant Entry as Entry stylesheet
    participant Parser as Parser
    participant Loader as Module loader
    participant Eval as Evaluator
    participant Out as Serializer

    Entry->>Parser: main.scss text
    Parser-->>Entry: syntax tree or syntax error
    Parser->>Loader: each @use and @forward URL
    Loader-->>Parser: file found via relative path or load path
    Loader->>Eval: modules in dependency order
    Note over Eval: variables, mixins, functions,<br/>control flow and math run here
    Eval->>Out: tree of plain CSS rules
    Out-->>Entry: expanded or compressed CSS and source map
....

Because evaluation finishes before any CSS is written, the compiler can report the file and line of a mistake even
when it happened deep inside nested mixin calls, and a failing compile does not emit a half-finished stylesheet.

== Implementations

[cols="1,1,3", options="header"]
|===
| Implementation | Status | Notes

| **Dart Sass**
| Current, official
| The reference implementation. Written in Dart, distributed as a standalone executable, as a pure-JS `sass`
  npm package, and as `sass-embedded` (a fast native binary with a JS wrapper). All new features land here
  first.

| LibSass (`node-sass`)
| **Deprecated**
| The C++ implementation. Officially deprecated in 2020 and no longer maintained. It never gained the module
  system (`@use`/`@forward`) and never will. `node-sass` was its Node binding and is likewise end-of-life.

| Ruby Sass
| **End of life**
| The original implementation. Retired in 2019.
|===

The practical consequence: **if a project still depends on `node-sass`, migrate it to `sass`.** Beyond being
unmaintained, `node-sass` requires native compilation tied to specific Node versions, which is a recurring
source of install failures. The replacement is usually a one-line change:

[source,bash]
----
npm uninstall node-sass
npm install --save-dev sass
----

For build-performance-sensitive projects, `sass-embedded` offers the same API backed by a native binary:

[source,bash]
----
npm install --save-dev sass-embedded
----

== The `sass` CLI

The most direct path. Install it globally or as a dev dependency:

[source,bash]
----
npm install -g sass          # or: brew install sass/sass/sass
----

Basic invocations:

[source,bash]
----
# One file
sass scss/main.scss css/main.css

# A whole directory (partials are skipped automatically)
sass scss:css

# Recompile on every save
sass --watch scss:css

# Production build: compressed, no source map
sass scss:css --style=compressed --no-source-map
----

=== Useful flags

[cols="2,3", options="header"]
|===
| Flag | Effect

| `--watch`
| Recompile whenever a source file changes

| `--style=expanded` / `--style=compressed`
| Output formatting; `expanded` is the default, `compressed` minifies

| `--no-source-map`
| Skip the `.css.map` file (do this for production)

| `--load-path=<dir>`
| Extra directory to resolve `@use`/`@forward` from -- e.g. `node_modules`

| `--embed-sources`
| Inline the original Sass into the source map

| `--error-css` / `--no-error-css`
| Whether to emit CSS describing an error, so it shows up in the browser

| `--quiet-deps`
| Suppress deprecation warnings originating in dependencies

| `--update`
| Only recompile files whose sources changed

| `--stdin`
| Read the stylesheet from standard input, handy in scripts (`--indented` selects the indented syntax)

| `--pkg-importer=node`
| Resolve `pkg:` URLs the way Node.js resolves packages (see below)

| `--fatal-deprecation=<id>`
| Treat a deprecation as an error, e.g. `--fatal-deprecation=import`; a Sass version number covers everything
  deprecated up to it

| `--silence-deprecation=<id>`
| Hide a specific deprecation warning

| `--interactive`
| Start an interactive SassScript shell for trying out expressions
|===

[source,bash]
----
echo '.a { b: 1 }' | sass --stdin --style=compressed    # .a{b:1}
----

`--load-path=node_modules` is the one people most often need, since it lets `@use "bootstrap/scss/bootstrap"`
resolve without a relative path full of `../`.

=== Worked example: a small project

Take a project with a token partial, a component partial and one entry stylesheet:

----
scss/
  _tokens.scss
  main.scss
  components/
    _button.scss
----

[source,scss]
----
// scss/_tokens.scss
$brand: #3f51b5 !default;
$radius: 4px !default;
----

[source,scss]
----
// scss/components/_button.scss
@use "../tokens";

.button {
  padding: 8px 16px;
  border-radius: tokens.$radius;
  background: tokens.$brand;
  color: white;

  &:hover { background: #2c387e; }
}
----

[source,scss]
----
// scss/main.scss
@use "tokens";
@use "components/button";

body { margin: 0; color: tokens.$brand; }
----

`sass scss/main.scss` prints the compiled result to the terminal, with every `@use` resolved and every variable
replaced by its value:

[source,css]
----
.button {
  padding: 8px 16px;
  border-radius: 4px;
  background: #3f51b5;
  color: white;
}
.button:hover {
  background: #2c387e;
}

body {
  margin: 0;
  color: #3f51b5;
}
----

Adding `--style=compressed --no-source-map` produces the production form on a single line:

[source,css]
----
.button{padding:8px 16px;border-radius:4px;background:#3f51b5;color:#fff}.button:hover{background:#2c387e}body{margin:0;color:#3f51b5}
----

Note that compressed output also shortens `white` to `#fff`. Compiling with an output file, `sass scss/main.scss
css/main.css`, writes two files, `main.css` and `main.css.map`, and appends a `sourceMappingURL` comment to the CSS.
The directory form, `sass scss:dist`, compiles only `main.scss` to `dist/main.css`: files whose names start with an
underscore are partials, and are never compiled on their own, only through the `@use` of a file that is.

The source map lists every file that contributed, which is what lets the browser point at `_tokens.scss` rather than
at a line of generated CSS:

[source,json]
----
{"version":3,"sourceRoot":"","sources":["../scss/components/_button.scss","../scss/_tokens.scss","../scss/main.scss"],"names":[],"mappings":"AAEA;EACE;EACA,eCHO;...","file":"main.css"}
----

== Output styles

[source,scss]
----
.button { background: #3f51b5; color: white; }
----

`--style=expanded` (default) -- readable, one declaration per line:

[source,css]
----
.button {
  background: #3f51b5;
  color: white;
}
----

`--style=compressed` -- minified, whitespace stripped, for production:

[source,css]
----
.button{background:#3f51b5;color:white}
----

Dart Sass dropped the older `nested` and `compact` styles; `expanded` and `compressed` are the two that remain.

Compressed output is more than whitespace removal: the compiler also shortens colours (`white` becomes `#fff`),
drops the last semicolon of a block and removes the blank lines between rules, so never diff compressed output
by eye.

== Source maps

By default the compiler writes a `.css.map` alongside the CSS. Browser developer tools read it and report the
*original `.scss` file and line number* for each rule, instead of a line in the generated CSS. Without one,
debugging a large compiled stylesheet means tracing rules back by hand.

Ship source maps in development; drop them in production builds (`--no-source-map`) unless you deliberately want
them available.

The two build modes differ only in a handful of flags, and a team normally wires each to its own npm script:

[mermaid]
....
flowchart LR
    SRC["scss sources"] --> DEV["Development<br/>sass --watch scss:dist"]
    SRC --> PROD["Production<br/>sass scss:dist --style=compressed --no-source-map"]
    DEV --> DCSS["expanded CSS + .css.map<br/>rebuilt on every save"]
    PROD --> PCSS["compressed CSS only<br/>built once in CI"]
    DCSS --> DT["Browser devtools show<br/>the original .scss line"]
    PCSS --> CDN["Hashed file served<br/>with long-lived caching"]
....

== Deprecation warnings

Dart Sass announces language changes ahead of time through named deprecations. A warning looks like this, naming the
deprecation (`import`), the offending line and a link to the migration notes:

----
DEPRECATION WARNING [import]: Sass @import rules are deprecated and will be removed in Dart Sass 3.0.0.

More info and automated migrator: https://sass-lang.com/d/import

  ╷
1 │ @import "tokens";
  │         ^^^^^^^^
  ╵
    scss/legacy.scss 1:9  root stylesheet
----

The bracketed id is what the flags take. In CI, make the ones you have already fixed fatal so they cannot come back,
and silence ones that come from code you do not own:

[source,bash]
----
sass --fatal-deprecation=import scss/main.scss      # fails the build on any @import
sass --silence-deprecation=import scss/main.scss    # hides that warning
sass --quiet-deps scss/main.scss                    # hides warnings from files found via load paths
----

Deprecated features keep working until the next major version, which is why a green build can still hide a
migration backlog; `--fatal-deprecation` with a Sass version number (for example `--fatal-deprecation=1.80.0`) is the
way to make everything deprecated up to that release a hard error.

== The JavaScript API

Everything the CLI does is also available from Node through the `sass` package, which is what build tools call.
`sass.compile()` takes a file path and `sass.compileString()` takes source text; both return an object with the CSS,
the source map and the list of files that were loaded, and both throw an exception on a Sass error:

[source,javascript]
----
// build.mjs
import * as sass from "sass";
import { writeFileSync, mkdirSync } from "node:fs";

const result = sass.compile("scss/main.scss", {
  style: "compressed",
  sourceMap: true,
  loadPaths: ["node_modules"],
});

mkdirSync("dist", { recursive: true });
writeFileSync("dist/main.css", result.css);
writeFileSync("dist/main.css.map", JSON.stringify(result.sourceMap));
console.log(result.loadedUrls.length, "files contributed");   // the files to watch for changes
----

`compileString()` can also configure a module through `with`, as the first line of the example below does, and the
JavaScript API lets you define Sass functions in JavaScript. The key is the function signature, and arguments arrive
as typed Sass values:

[source,javascript]
----
import * as sass from "sass";

const custom = sass.compileString(
  `@use "tokens" with ($brand: #e91e63);
   .cta { color: tokens.$brand; width: px-to-rem(24px); }`,
  {
    url: new URL("file://" + process.cwd() + "/scss/entry.scss"),
    loadPaths: ["scss"],
    functions: {
      "px-to-rem($px)": (args) => {
        const px = args[0].assertNumber("px");
        return new sass.SassNumber(px.value / 16, "rem");
      },
    },
  }
);
console.log(custom.css);
----

[source,css]
----
.cta {
  color: #e91e63;
  width: 1.5rem;
}
----

Errors carry structured information, so a tool can show them in its own UI:

[source,javascript]
----
try {
  sass.compileString("a { b: 1px + 1s; }");
} catch (e) {
  console.log(e.sassMessage);            // 1px and 1s have incompatible units.
  console.log(e.span.start.line + 1);    // 1
}
----

The older `render()` and `renderSync()` functions of the legacy API are deprecated; new tooling should use the
functions above (`compileAsync()` and `compileStringAsync()` are the asynchronous forms).

=== Resolving packages with `pkg:`

Instead of `--load-path=node_modules`, a stylesheet can load a Sass entry point shipped by an npm package with a
`pkg:` URL. The `node` package importer follows Node's package resolution, honouring a `sass` condition in the
package's `exports` map, so the stylesheet needs no knowledge of where `node_modules` lives:

[source,json]
----
{
  "name": "ui-kit",
  "version": "1.0.0",
  "exports": {
    "./*": { "sass": "./scss/*.scss" },
    ".": { "sass": "./scss/index.scss" }
  }
}
----

[source,scss]
----
// app.scss
@use "pkg:ui-kit";
.a { color: ui-kit.$accent; }
----

Compiling with `sass --pkg-importer=node app.scss` (or `importers: [new sass.NodePackageImporter()]` in the
JavaScript API) prints:

[source,css]
----
.a {
  color: #e91e63;
}
----

== Bundler integrations

=== Vite

Vite supports Sass out of the box -- no plugin or config needed. Install the compiler and import the file:

[source,bash]
----
npm install --save-dev sass
----

[source,javascript]
----
// main.js
import './styles/main.scss';
----

`.module.scss` files are treated as CSS Modules automatically. Shared variables can be injected into every
stylesheet via config:

[source,javascript]
----
// vite.config.js
export default {
  css: {
    preprocessorOptions: {
      scss: {
        additionalData: `@use "src/styles/_tokens.scss" as tokens;`
      }
    }
  }
};
----

=== Webpack

Webpack needs an explicit loader chain, applied right-to-left:

[source,bash]
----
npm install --save-dev sass sass-loader css-loader style-loader
----

[source,javascript]
----
// webpack.config.js
module.exports = {
  module: {
    rules: [
      {
        test: /\.s[ac]ss$/i,
        use: [
          'style-loader',   // 3. inject the CSS into the DOM
          'css-loader',     // 2. resolve @import/url() in the CSS
          'sass-loader'     // 1. compile Sass → CSS
        ]
      }
    ]
  }
};
----

For production, replace `style-loader` with `MiniCssExtractPlugin.loader` to emit a real `.css` file rather than
injecting styles via JavaScript.

Pin `sass-loader` to the Dart Sass implementation explicitly if the project has any `node-sass` history:

[source,javascript]
----
{
  loader: 'sass-loader',
  options: {
    implementation: require('sass'),
    sassOptions: { loadPaths: ['node_modules'] }
  }
}
----

=== Other tooling

* **Parcel** -- zero-config, like Vite; install `sass` and import the file.
* **npm scripts** -- for a project with no bundler, the CLI is enough:
+
[source,json]
----
{
  "scripts": {
    "css:build": "sass scss:dist/css --style=compressed --no-source-map",
    "css:watch": "sass --watch scss:dist/css"
  }
}
----
* **Framework CLIs** -- Angular, Next.js, Nuxt, and SvelteKit all support Sass by installing the `sass` package;
  none needs further configuration in the common case.

== Editor compile-on-save

For small projects or quick experiments, an editor extension avoids any build setup at all. *Live Sass Compiler*
for VS Code is the widely used one: it watches open `.scss` files and writes the compiled CSS on save, with
configurable output path and style.

This is convenient for learning and for single-page sites, but it is not a substitute for a real build step on a
team project -- the configuration lives in one developer's editor settings rather than in the repository, so
different machines can silently produce different output.

== Where compilation fits in the wider pipeline

Sass compilation is normally one stage among several:

. **Sass → CSS** (Dart Sass, covered here).
. **Autoprefixer / PostCSS** -- add vendor prefixes and apply other CSS transforms.
. **Minification** -- either Sass's own `--style=compressed`, or a dedicated minifier such as `cssnano`.
. **Bundling and cache-busting** -- emit a hashed filename for long-lived caching.

Sass deliberately does *not* do vendor prefixing itself; that is Autoprefixer's job, driven by a
`browserslist` configuration.

For the CSS-side concerns that follow compilation -- critical CSS, loading strategy, and bundle size -- see
xref:web/html-css/performance-loading.adoc[Runtime loading performance] and
xref:web/html-css/performance-build-optimization.adoc[Build-time performance optimization].
