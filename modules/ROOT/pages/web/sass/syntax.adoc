= Syntax: SCSS vs. Sass
:description: Explains the two syntaxes Dart Sass accepts -- the brace-and-semicolon SCSS syntax (.scss), a superset of CSS, and the indentation-significant Sass syntax (.sass) -- with the same stylesheet written both ways and guidance on which to choose.
:keywords: Sass, SCSS, .scss, .sass, indented syntax, Sass syntax, SCSS vs Sass, CSS preprocessor, Dart Sass, superset of CSS, sass-convert

include::partial$ai-disclaimer.adoc[]

Sass is a CSS preprocessor: a language that adds variables, nesting, mixins, functions, and a module system on
top of CSS, then compiles down to the plain CSS a browser actually understands (see
xref:web/sass/compilation.adoc[Compilation]). What makes it slightly unusual among preprocessors is that it
offers *two different syntaxes for the same language*. Both are handled by the same compiler, expose exactly the
same features, and produce exactly the same CSS -- they differ only in punctuation.

== The two syntaxes

[cols="1,3,3", options="header"]
|===
| | SCSS | Indented Sass

| File extension
| `.scss`
| `.sass`

| Blocks
| Curly braces `+{ }+`
| Indentation

| Statement terminator
| Semicolon `;`
| Newline

| Relationship to CSS
| A strict superset -- any valid CSS file is a valid SCSS file
| Not CSS-compatible -- plain CSS must be converted first

| Typical use
| The default choice, and by far the most common in practice
| Niche; favoured by those who prefer terse, whitespace-driven syntax
|===

=== One compiler, one result

The syntax only matters to the *parser*. Once a file has been read, the compiler works on the same internal
representation regardless of where it came from, so every later stage -- evaluating variables, running mixins,
resolving `@use` -- is identical:

[mermaid]
....
flowchart LR
    A[".scss file<br/>braces and semicolons"] --> P1["SCSS parser"]
    B[".sass file<br/>indentation"] --> P2["Indented parser"]
    P1 --> T["Same syntax tree"]
    P2 --> T
    T --> E["Evaluate:<br/>variables, mixins, modules"]
    E --> C["Plain CSS"]
....

This is why the syntaxes can be mixed freely across files, and why the choice has no effect on the output.

== SCSS: the default

SCSS ("Sassy CSS") is the syntax you should reach for unless you have a specific reason not to. Because it is a
superset of CSS, you can rename an existing `.css` file to `.scss` and it will compile unchanged, then adopt
Sass features incrementally. Every example elsewhere in this section uses SCSS.

[source,scss]
----
@use "sass:color";

$primary: #3f51b5;
$radius: 4px;

@mixin button-base {
  border: 0;
  border-radius: $radius;
  cursor: pointer;
}

.card {
  padding: 1rem;
  border-radius: $radius;

  .card__title {
    margin: 0;
    color: $primary;
  }

  .card__button {
    @include button-base;
    background: $primary;
    color: white;

    &:hover {
      background: color.adjust($primary, $lightness: -10%);
    }
  }
}
----

== The indented syntax

The indented syntax -- the original one, and the reason the language is called "Sass" -- drops braces and
semicolons entirely, deriving block structure from indentation the way Python or YAML does. Here is the exact
same stylesheet:

[source,sass]
----
@use "sass:color"

$primary: #3f51b5
$radius: 4px

@mixin button-base
  border: 0
  border-radius: $radius
  cursor: pointer

.card
  padding: 1rem
  border-radius: $radius

  .card__title
    margin: 0
    color: $primary

  .card__button
    @include button-base
    background: $primary
    color: white

    &:hover
      background: color.adjust($primary, $lightness: -10%)
----

Both files compile to identical CSS:

[source,css]
----
.card {
  padding: 1rem;
  border-radius: 4px;
}
.card .card__title {
  margin: 0;
  color: #3f51b5;
}
.card .card__button {
  border: 0;
  border-radius: 4px;
  cursor: pointer;
  background: #3f51b5;
  color: white;
}
.card .card__button:hover {
  background: rgb(19.5419479267%, 25.1253616201%, 56.1443265831%);
}
----

That hover value looks odd printed as a percentage `rgb()` rather than a hex code, but it's the same colour
(`#32408f`) -- current Dart Sass's colour engine represents the output of a colour function like `color.adjust()`
in this form rather than re-serializing it back to hex.

=== Indented syntax in detail

A handful of rules are specific to the indented syntax:

* **Block structure comes from indentation.** Indentation must be consistent within a file -- mixing tabs and
  spaces is an error -- and a nested line must be indented deeper than its parent.
* **Mixins have a shorthand.** `=name` defines a mixin and `+name` includes it. The long forms `@mixin` and
  `@include` work as well and are the ones used on this site.
* **Line breaks are mostly significant.** A statement may continue onto the next line only inside parentheses or
  brackets, or after a trailing comma in a selector list. A trailing comma in a *value* does not continue it.
* **Multi-line loud comments need no closing `+*/+`.** The compiler closes them for you when the indentation ends.

[source,sass]
----
=rounded($radius: 4px)
  border-radius: $radius

h1,
h2
  +rounded(8px)
  box-shadow: (0 1px 2px red, 0 4px 8px blue)
  /* a loud comment
     over two lines
  color: red
----

Compiled with the real compiler, this produces:

[source,css]
----
h1,
h2 {
  border-radius: 8px;
  box-shadow: 0 1px 2px red, 0 4px 8px blue;
  /* a loud comment
  * over two lines */
  color: red;
}
----

Putting the value list on a second line without parentheses (`font-family: Inter,` followed by an indented
`sans-serif`) is rejected with `expected ":"`, because the compiler reads the second line as a new declaration.

== Compiling each syntax

The compiler picks the syntax from the file extension, so `sass main.scss` and `sass main.sass` need no extra
flags. When the source does not come from a file, say which syntax it is in:

[source,bash]
----
printf '.a\n  b: c\n  .d\n    e: f\n' | sass --stdin --indented
----

[source,css]
----
.a {
  b: c;
}
.a .d {
  e: f;
}
----

The JavaScript API takes a `syntax` option for the same purpose, and the two syntaxes really do yield byte-identical
CSS:

[source,javascript]
----
import * as sass from "sass";

const fromIndented = sass.compileString(".a\n  color: red\n  .b\n    color: blue\n", { syntax: "indented" }).css;
const fromScss = sass.compileString(".a { color: red; .b { color: blue; } }", { syntax: "scss" }).css;

console.log(fromIndented === fromScss); // true
----

== Which one to choose

Prefer **SCSS**. It is the default in essentially every toolchain, it is what published Sass libraries and
framework source (Bootstrap, Bulma) are written in, it is what almost all documentation and answers online use,
and its CSS-superset property means there is no translation step when copying a snippet out of a browser's
developer tools or a CSS reference. The indented syntax remains fully supported and is not deprecated -- it is
simply a stylistic preference, and choosing it costs you nothing in features but some convenience.

The two syntaxes can coexist in one project: a `.scss` file may `@use` a `.sass` partial and vice versa, since
the distinction is purely at the parsing stage. Dart Sass has no built-in syntax converter -- the old
`sass-convert` tool belonged to Ruby Sass -- so translating a codebase wholesale means using a community converter
or rewriting the files by hand. The official `sass-migrator` tool upgrades *language features* (such as `@import` to
`@use`), not the syntax.

== Comments

Comment syntax is one place worth calling out, because Sass adds a form CSS doesn't have:

[source,scss]
----
/* A standard CSS comment. This is preserved in the compiled output
   (except in compressed mode). */

// A Sass single-line comment. This is stripped from the output entirely.

/*! A loud comment. Preserved even in compressed output -- useful for licence banners. */
----

Silent `//` comments are the right default for notes meant for whoever is reading the Sass source, since they
add nothing to the bytes shipped to the browser.

The three kinds behave differently once compiled. This stylesheet uses all of them, plus the `///` form that
documentation tools such as SassDoc read (to the compiler it is just a silent comment):

[source,scss]
----
/*! (c) Example Ltd. */
/// Spacing base unit.
$unit: 4px;

/* Layout
   helpers */
.stack {
  // silent: only for readers of the source
  gap: $unit * 2; /* loud: #{$unit * 2} per step */
}
----

In the default expanded output the loud comments survive, and interpolation inside them is evaluated:

[source,css]
----
/*! (c) Example Ltd. */
/* Layout
   helpers */
.stack {
  gap: 8px; /* loud: 8px per step */
}
----

With `--style=compressed` only the `+/*!+` comment is kept:

[source,css]
----
/*! (c) Example Ltd. */.stack{gap:8px}
----

Non-ASCII characters in the output (an arrow in a `content` string, for instance) make Sass emit an
`@charset "UTF-8";` line at the top of the CSS; `--no-charset` suppresses it when the file is served with the right
`Content-Type` anyway.
