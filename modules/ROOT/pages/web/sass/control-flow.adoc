= Control Flow
:description: Covers Sass control-flow directives -- @if/@else if/@else, @for with through versus to, @each over lists and maps including destructuring, and @while -- each with worked examples such as generating utility classes.
:keywords: Sass control flow, @if, @else if, @else, @for, through vs to, @each, @while, Sass loops, utility class generation, destructuring, if() function, Sass conditionals

include::partial$ai-disclaimer.adoc[]

Control-flow directives let a stylesheet make decisions and generate rules programmatically. They run at compile
time -- the browser sees only the CSS they produced.

Note that all four directives can assign to variables in the enclosing scope directly, without `!global` (see
xref:web/sass/variables.adoc[Variables]), which is what makes accumulator patterns work.

== How the directives are evaluated

The compiler runs a control-flow directive while it evaluates the stylesheet and replaces it with whatever rules it
produced; none of the directive text survives into the output. A loop is therefore a code generator whose source is the
Sass file and whose product is a longer plain-CSS file.

[mermaid]
....
flowchart TD
    S["Evaluator reaches a directive"] --> K{"Which one?"}
    K -- "@if / @else" --> IF["Evaluate each condition in order<br/>run the first truthy branch only"]
    K -- "@for" --> FOR["Evaluate both bounds once<br/>run the body for each integer"]
    K -- "@each" --> EACH["Take the list or map once<br/>run the body per element or entry"]
    K -- "@while" --> WHL["Test the condition<br/>run the body, test again"]
    IF --> OUT["Rules and declarations<br/>emitted into the parent rule"]
    FOR --> OUT
    EACH --> OUT
    WHL --> OUT
    OUT --> CSS["Plain CSS, no trace of the directive"]
....

Two consequences follow. A condition that is false emits nothing at all, and the unused branch is never evaluated,
so an `@error` inside it cannot fire. And because a loop's bounds or collection are evaluated *once*, before the first
iteration, reassigning the collection inside the body does not change how many times the loop runs; only
`@while`, which re-tests its condition every time, reacts to the body's changes.

== `@if` / `@else if` / `@else`

[source,scss]
----
@mixin theme-surface($theme) {
  @if $theme == dark {
    background: #121212;
    color: #eeeeee;
  } @else if $theme == light {
    background: #ffffff;
    color: #212121;
  } @else {
    @error "Unknown theme `#{$theme}`; expected `dark` or `light`.";
  }
}

.panel--dark  { @include theme-surface(dark); }
.panel--light { @include theme-surface(light); }
----

Putting `@else` on the same line as the closing brace (`} @else`) is a style convention, not a requirement --
SCSS tolerates whitespace and comments between the two, so an `@else` on its own line compiles just as well.

Remember Sass's truthiness rule: **everything is truthy except `false` and `null`.** `0`, `""`, and `()` are all
truthy, unlike in JavaScript. Combined with the fact that `map.get()` returns `null` for a missing key, this
makes `@if` a natural guard:

[source,scss]
----
@use "sass:map";

@mixin elevation($level, $config) {
  $shadow: map.get($config, $level);

  @if $shadow {
    box-shadow: $shadow;
  } @else {
    @warn "No shadow defined for level `#{$level}`.";
  }
}
----

=== Combining conditions

Conditions use the boolean operators `and`, `or` and `not` (see xref:web/sass/operators.adoc[Operators]), and both
`and` and `or` return one of their operands rather than a strict `true`/`false`, which is useful for defaults:

[source,scss]
----
.n {
  x: 0 and true;      // true  -- 0 is truthy, so the result is the right operand
  y: not null;        // true
  z: null or 5;       // 5     -- the first truthy operand
}
----

[source,css]
----
.n {
  x: true;
  y: true;
  z: 5;
}
----

=== The `if()` function

For choosing between two *values* rather than two blocks, the built-in `if()` function is more compact. Unlike
`@if`, it is an expression usable anywhere a value is expected, and it evaluates only the branch it returns:

[source,scss]
----
@use "sass:color";

@function contrast($bg) {
  @return if(color.channel($bg, "lightness", $space: hsl) > 55%, #212121, #ffffff);
}

$compact: false;

.badge {
  background: #ffeb3b;
  color: contrast(#ffeb3b);           // #212121
  padding: if($compact, 4px, 12px);   // 12px
}
----

Current Dart Sass deprecates this comma-argument form of `if()` in favor of a modern CSS-style syntax
(`if(sass($condition): $if-true; else: $if-false)`) -- see
https://sass-lang.com/d/if-function[the deprecation notice]. The form above still works today and is what most
existing Sass code uses, but new code should prefer the CSS syntax.

== `@for`

`@for` iterates over a numeric range. It comes in two forms, and the difference is the endpoint:

[cols="1,3,2", options="header"]
|===
| Form | Range | `@for $i from 1 through/to 3`

| `through`
| Inclusive of the end value
| 1, 2, 3

| `to`
| Exclusive of the end value
| 1, 2
|===

`through` is the one you usually want, since stylesheets tend to count from 1.

[source,scss]
----
@use "sass:math";

// A 12-column grid
@for $i from 1 through 12 {
  .col-#{$i} {
    width: math.percentage(math.div($i, 12));
  }
}
----

[source,css]
----
.col-1 { width: 8.3333333333%; }
.col-2 { width: 16.6666666667%; }
/* ... */
.col-12 { width: 100%; }
----

A spacing scale, using the loop variable in the value rather than the name:

[source,scss]
----
$base: 4px;

@for $i from 1 through 6 {
  .m-#{$i} { margin: $base * $i; }
  .p-#{$i} { padding: $base * $i; }
}
----

Counting down works by swapping the bounds -- Sass detects the direction automatically:

[source,scss]
----
@for $i from 5 through 1 {
  .z-#{$i} { z-index: $i * 10; }   // emits .z-5 first, down to .z-1
}
----

Both bounds must be unitless integers (or numbers with compatible units); a non-integer is an error.

The two forms differ only in the final value, so the edge cases are worth knowing:

[cols="2,2,3", options="header"]
|===
| Loop | Values of `$i` | Notes

| `@for $i from 3 through 3`
| 3
| A single iteration

| `@for $i from 1 to 1`
| none
| An exclusive range with equal bounds is empty, so nothing is emitted

| `@for $i from 3 to 1`
| 3, 2
| Counts down and stops before reaching the end value

| `@for $i from 3 through 1`
| 3, 2, 1
| Counts down inclusively
|===

[mermaid]
....
flowchart LR
    A["Evaluate from and end once"] --> B{"$i past the end?<br/>through: after it<br/>to: at it"}
    B -- no --> C["Run the body with $i"]
    C --> D["Step $i by 1<br/>up or down"]
    D --> B
    B -- yes --> E["Loop finished"]
....

== `@each`

`@each` iterates over the elements of a list or the entries of a map. It is the most useful of the four in
practice, because stylesheet data is usually a set of names rather than a numeric range.

=== Over a list

[source,scss]
----
$sizes: xs, sm, md, lg, xl;

@each $size in $sizes {
  .hidden-#{$size} { display: none; }
}
----

=== Over a map

Two variables destructure each entry into its key and value:

[source,scss]
----
$theme-colours: (
  primary: #3f51b5,
  success: #43a047,
  warning: #fb8c00,
  danger:  #e53935
);

@each $name, $colour in $theme-colours {
  .text-#{$name} { color: $colour; }
  .bg-#{$name}   { background-color: $colour; }
  .border-#{$name} { border-color: $colour; }
}
----

[source,css]
----
.text-primary { color: #3f51b5; }
.bg-primary { background-color: #3f51b5; }
.border-primary { border-color: #3f51b5; }
.text-success { color: #43a047; }
/* ... and so on */
----

This is the canonical utility-class generator: one source of truth for the palette, and three families of
classes derived from it. Adding a colour to the map adds three classes automatically.

=== Destructuring a list of lists

The same multiple-variable syntax destructures nested lists, which is handy for tabular data:

[source,scss]
----
$buttons:
  (primary, #3f51b5, white),
  (secondary, #757575, white),
  (ghost, transparent, #3f51b5);

@each $name, $bg, $fg in $buttons {
  .btn-#{$name} {
    background: $bg;
    color: $fg;
  }
}
----

If an inner list is shorter than the variable list, the missing variables are `null`.

=== Nested `@each`

Combining two loops generates a matrix -- useful for responsive utilities, though it multiplies output size
quickly, so keep the input sets small:

[source,scss]
----
@use "sass:map";

$breakpoints: (sm: 576px, md: 768px, lg: 992px);
$displays: none, block, flex, grid;

@each $bp-name, $bp-width in $breakpoints {
  @media (min-width: $bp-width) {
    @each $display in $displays {
      .#{$bp-name}\:d-#{$display} { display: $display; }
    }
  }
}
----

== `@while`

`@while` repeats as long as its condition holds. It is the rarest of the four -- almost anything expressible
with `@while` is clearer as `@for` or `@each` -- but it fits when the step is not a simple increment:

[source,scss]
----
@use "sass:math";

// A modular type scale: each step is 1.25× the last, until it exceeds 48px
$size: 12px;
$step: 1;

@while $size < 48px {
  .text-#{$step} { font-size: $size; }
  $size: $size * 1.25;
  $step: $step + 1;
}
----

[source,css]
----
.text-1 { font-size: 12px; }
.text-2 { font-size: 15px; }
.text-3 { font-size: 18.75px; }
.text-4 { font-size: 23.4375px; }
.text-5 { font-size: 29.296875px; }
.text-6 { font-size: 36.62109375px; }
.text-7 { font-size: 45.7763671875px; }
----

Make sure the condition can actually become false -- a `@while` whose body never changes the variable it tests
will hang the compiler.

== Worked example: a responsive grid generator

A grid system is the classic use of loops: the same twelve column rules repeated at every breakpoint. A mixin holds the
`@for` loop, and an `@each` over the breakpoint map calls it once per media query, so the grid is defined in exactly
one place:

[source,scss]
----
@use "sass:math";

$columns: 12 !default;
$gutter: 16px !default;
$breakpoints: (sm: 576px, md: 768px, lg: 992px) !default;

.row {
  display: flex;
  flex-wrap: wrap;
  margin: 0 (-$gutter * 0.5);
}

@mixin col-widths($infix) {
  @for $i from 1 through $columns {
    .col#{$infix}-#{$i} {
      flex: 0 0 math.percentage(math.div($i, $columns));
      max-width: math.percentage(math.div($i, $columns));
      padding: 0 math.div($gutter, 2);
    }
  }
}

@include col-widths("");
@each $name, $min in $breakpoints {
  @media (min-width: $min) {
    @include col-widths("-#{$name}");
  }
}
----

The first rules of the compiled output show the pattern (the full result has 52 rules: one `.row`, twelve unprefixed
columns, and twelve more inside each of the three media queries):

[source,css]
----
.row {
  display: flex;
  flex-wrap: wrap;
  margin: 0 -8px;
}

.col-1 {
  flex: 0 0 8.3333333333%;
  max-width: 8.3333333333%;
  padding: 0 8px;
}

.col-2 {
  flex: 0 0 16.6666666667%;
  max-width: 16.6666666667%;
  padding: 0 8px;
}
----

Because `$columns`, `$gutter` and `$breakpoints` are `!default`, a project can load this file with a `with`
configuration (for example `+with ($columns: 16)+`) and get a sixteen-column grid with no change to the loops. The
compressed output of the full grid is about 3.2 KB, which is a reasonable budget; adding a fourth breakpoint costs
another twelve rules, which is the multiplication the previous section warned about.

== Worked example: component variants from a map of maps

When variants differ in more than one property, store each variant as a small map. `@each $name, $v in $variants`
destructures the outer map, `map.get()` reads the inner values, and `@if` handles the one property that is optional.
This keeps the data separate from the CSS the loop writes:

[source,scss]
----
@use "sass:map";

$variants: (
  primary: (bg: #3f51b5, fg: #ffffff, outline: true),
  success: (bg: #43a047, fg: #ffffff, outline: true),
  ghost:   (bg: transparent, fg: #3f51b5, outline: false)
);

@each $name, $v in $variants {
  $bg: map.get($v, bg);
  $fg: map.get($v, fg);

  .btn-#{$name} {
    background: $bg;
    color: $fg;

    @if map.get($v, outline) {
      border: 1px solid $bg;
    } @else {
      border: 0;
    }

    @if $name == primary or $name == success {
      font-weight: 600;
    }
  }
}
----

[source,css]
----
.btn-primary {
  background: #3f51b5;
  color: #ffffff;
  border: 1px solid #3f51b5;
  font-weight: 600;
}

.btn-success {
  background: #43a047;
  color: #ffffff;
  border: 1px solid #43a047;
  font-weight: 600;
}

.btn-ghost {
  background: transparent;
  color: #3f51b5;
  border: 0;
}
----

== Debugging loops

`@debug` prints from inside a loop, which is the fastest way to see what a generator is doing. Variables assigned in a
loop body are visible after it, so a counter can also report how many iterations ran:

[source,scss]
----
$count: 0;
@each $a in 1 2 {
  @each $b in x y {
    $count: $count + 1;
    @debug "#{$a}#{$b} -> #{$count}";
  }
}
.total { n: $count; }
----

The compiler prints the following to standard error (not into the CSS), then emits a `total` rule whose `n` is `4`:

----
lp.scss:5 DEBUG: 1x -> 1
lp.scss:5 DEBUG: 1y -> 2
lp.scss:5 DEBUG: 2x -> 3
lp.scss:5 DEBUG: 2y -> 4
----

== Choosing between them

* **`@if`** -- branch on a condition. Use `if()` when choosing between two values rather than two blocks.
* **`@each`** -- iterate over named data. The default choice for generating classes from a list or map.
* **`@for`** -- iterate over a numeric range, when the numbers themselves are meaningful (grid columns, spacing
  steps, z-index layers).
* **`@while`** -- iterate until a condition changes, when the step isn't a fixed increment.

A general caution: loops make it easy to emit a very large amount of CSS from a very small amount of source. A
nested loop over three breakpoints and twenty utilities produces sixty rules -- check the compiled output size
when generating utility families.
