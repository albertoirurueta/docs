Shipping an Angular app well means an optimized production build with enforced size budgets, attention to the
Core Web Vitals, and -- where SEO or first paint matter -- server-side rendering with hydration. See
https://angular.dev/tools/cli/build[ng build] and https://angular.dev/guide/performance[Performance].

== Production builds

`ng build` uses the `production` configuration by default: ahead-of-time template compilation, minification,
tree-shaking, dead-code elimination, and **output hashing** (`main.<hash>.js`) for long-term caching. Output
lands in `dist/<project>/`.

[source,bash]
----
ng build                             # production by default
ng build --configuration development
ng build --source-map                # emit .map files for debugging
ng build --stats-json                # for bundle analysis (esbuild --analyze, source-map-explorer)
ng deploy                            # via a deploy builder added with `ng add`
----

**Configurations** live in `angular.json` under
`projects.<name>.architect.build.configurations`. Each one can set optimization flags and a **file
replacement**, so environment-specific values are swapped at build time (see
<<environment-files,Environment files>> below):

[source,json]
----
{
  "configurations": {
    "production": {
      "outputHashing": "all",
      "budgets": [
        { "type": "initial", "maximumWarning": "500kB", "maximumError": "1MB" },
        { "type": "anyComponentStyle", "maximumWarning": "4kB", "maximumError": "8kB" }
      ]
    },
    "development": {
      "optimization": false,
      "extractLicenses": false,
      "sourceMap": true
    }
  },
  "defaultConfiguration": "production"
}
----

That is what `ng new` generates: the production configuration only needs budgets and hashing because optimization is
already the default there, and the development one switches it off and adds source maps. A configuration may also set
`optimization`, `sourceMap`, `fileReplacements`, and more.

[#environment-files]
== Environment files

`ng generate environments` creates `src/environments/environment.ts` and `environment.development.ts` and adds a
`fileReplacements` entry. In the current CLI the plain `environment.ts` holds the **production** values (it is the
file used when nothing replaces it) and the `development` configuration swaps in `environment.development.ts`:

[source,json]
----
"development": {
  "optimization": false,
  "extractLicenses": false,
  "sourceMap": true,
  "fileReplacements": [
    { "replace": "src/environments/environment.ts", "with": "src/environments/environment.development.ts" }
  ]
}
----

[source,typescript]
----
// src/environments/environment.ts          (production)
export const environment = { production: true, apiUrl: 'https://api.books.example.com' };

// src/environments/environment.development.ts
export const environment = { production: false, apiUrl: 'http://localhost:3000' };
----

Application code imports `environment` from `environments/environment` and never mentions the other file. Building
both configurations and searching the output showed the replacement is a build-time substitution: the production
bundle contained `api.books.example.com` and no trace of `localhost:3000`, and the development bundle the reverse.
Older projects used the opposite convention (`environment.ts` for development and `environment.prod.ts` swapped in for
production); both work because `fileReplacements` just names a pair of files. Because the values are compiled into
public JavaScript, an environment file must never hold secrets -- an API URL, yes; an API key with write access, no.

== Reading the build output

`ng build` for a small catalog app, with a lazily loaded route, printed:

[source,text]
----
Initial chunk files | Names         |  Raw size | Estimated transfer size
chunk-ECV4KJEZ.js   | -             | 159.85 kB |                46.73 kB
main-UJJDCOZY.js    | main          | 101.30 kB |                26.22 kB
styles-5INURTSO.css | styles        |   0 bytes |                 0 bytes

                    | Initial total | 261.15 kB |                72.94 kB

Lazy chunk files    | Names         |  Raw size | Estimated transfer size
chunk-HNG54H2Q.js   | catalog       |  42.09 kB |                 9.80 kB
----

*Initial* chunks are downloaded before the app starts; *lazy* chunks only when a route or `@defer` block needs them.
The anonymous shared chunk holds framework code, and the content hash in each file name changes only when the content
does, which is what lets the server send `Cache-Control: max-age=31536000` safely. The *estimated transfer size* is the
gzip size, the number that matters for download time; the raw size is what the browser must parse.

=== A budget failing

With the budgets tightened to 150 kB / 250 kB for the initial total and 50 kB / 90 kB for the `main` bundle, the same
build stopped with:

[source,text]
----
▲ [WARNING] bundle initial exceeded maximum budget. Budget 150.00 kB was not met by 111.15 kB with a total of 261.15 kB.
▲ [WARNING] main exceeded maximum budget. Budget 50.00 kB was not met by 51.30 kB with a total of 101.30 kB.
✘ [ERROR] bundle initial exceeded maximum budget. Budget 250.00 kB was not met by 11.15 kB with a total of 261.15 kB.
✘ [ERROR] main exceeded maximum budget. Budget 90.00 kB was not met by 11.30 kB with a total of 101.30 kB.
Application bundle generation failed.
----

The warning level is for trend-watching and the error level fails CI. Set `maximumError` a little above today's
size, so the next accidental import of a heavy library is caught in the pull request that adds it. The build also writes
files you can feed to analyzers: `ng build --stats-json` adds `browser-stats.json` next to the output (open it in a
bundle visualizer such as the esbuild bundle analyzer), and `--source-map` adds a `.map` file per chunk. The
`3rdpartylicenses.txt` that the production build emits lists the licenses of everything bundled, which is what a legal
review asks for.

**Bundle budgets** fail the build when a bundle grows past `maximumError` -- the cheapest guard against
accidental bloat such as a mis-imported library. Budget types include `initial`, `all`, `anyComponentStyle`,
`bundle`, and `allScript`. See https://angular.dev/reference/configs/workspace-config[Workspace configuration].

**Deployment:** `ng deploy` runs a deploy builder contributed by a provider package
(`ng add @angular/fire`, `angular-cli-ghpages`, and others). Without one, copy `dist/<project>/browser/` to any
static host and add a SPA fallback that serves `index.html` for unknown paths. See
https://angular.dev/tools/cli/deployment[Deployment].

== Core Web Vitals

[cols="1,2,3",options="header"]
|===
| Metric | Measures | Angular levers

| **LCP** -- Largest Contentful Paint | how fast the main content loads | `NgOptimizedImage` with `priority`, SSR / SSG, `@defer` for below-the-fold content, route-level code splitting
| **INP** -- Interaction to Next Paint | responsiveness to input | `OnPush` and signals, zoneless change detection, `withEventReplay()`, smaller bundles
| **CLS** -- Cumulative Layout Shift | visual stability | explicit `width` / `height` on images (required by `NgOptimizedImage`), reserving space for deferred and async content
|===

**`NgOptimizedImage`** -- replace `src` with `ngSrc` and Angular sets `loading` / `fetchpriority`, generates a
`srcset`, requires an explicit `width` / `height` (or `fill`), and warns on oversized files:

[source,html]
----
<img ngSrc="/assets/hero.jpg" width="1200" height="600" priority alt="Product hero" />
<img ngSrc="/assets/thumb.jpg" width="200" height="200" alt="Thumbnail" />
----

**`@defer`** loads a block's JavaScript only when a trigger fires (`on viewport`, `on interaction`, `on idle`),
shrinking the initial bundle -- recap on xref:web/angular/control-flow-and-defer.adoc[Control flow and @defer].
**Route-level code splitting** with `loadComponent` / `loadChildren` keeps each route's code out of the initial
download -- recap on xref:web/angular/routing.adoc[Routing]. See
https://angular.dev/guide/performance[Performance].

== SSR and hybrid rendering

Add SSR with `ng add @angular/ssr` (or `ng new --ssr`). It scaffolds a `server.ts` request handler, a
`main.server.ts`, and an `app.config.server.ts`. Rendering can be mixed per route: **client-side**,
**server-side (SSR)** per request, and **prerendered (SSG)** at build time.

[source,typescript]
----
// app.config.ts — hydrate the server-rendered markup on the client
import { ApplicationConfig } from '@angular/core';
import {
  provideClientHydration, withEventReplay, withIncrementalHydration,
} from '@angular/platform-browser';

export const appConfig: ApplicationConfig = {
  providers: [
    provideClientHydration(withEventReplay(), withIncrementalHydration()),
  ],
};
----

`provideClientHydration()` makes the client **reuse** the server-rendered DOM instead of re-creating it -- no
flicker and no duplicate data fetch. `withEventReplay()` records clicks and keystrokes that happen before
hydration completes and replays them once it does.

**Incremental hydration** hydrates `@defer` blocks lazily, each on its own trigger, using the `hydrate`
keyword: the server renders the content, and the client ships and activates its JavaScript only when needed.
It requires opting in with `withIncrementalHydration()` (as above); without it the `hydrate` triggers are
inert and the block behaves as a plain `@defer`.

[source,html]
----
@defer (hydrate on viewport) {
  <app-reviews [productId]="id()" />
} @placeholder {
  <p>Reviews</p>
}
----

Triggers: `hydrate on idle`, `hydrate on viewport`, `hydrate on interaction`, `hydrate on hover`,
`hydrate on immediate`, `+hydrate on timer(...)+`, `hydrate when <expr>`, and `hydrate never` for content that
stays permanently static. See https://angular.dev/guide/incremental-hydration[Incremental hydration].

**Prerendering (SSG)** renders routes to static HTML at build time -- set a route's `renderMode` to
`RenderMode.Prerender` in the server routes config and list its parameter values. The **app-shell** pattern
prerenders a minimal layout (header, nav, spinner) as the first paint while the full app bootstraps:
`ng generate app-shell`. See https://angular.dev/guide/ssr[Server-side rendering] and
https://angular.dev/guide/hydration[Hydration]. For the same ideas in React, see
xref:web/nextjs/rendering-fundamentals.adoc[Next.js Rendering Fundamentals] and xref:web/nextjs/hydration.adoc[Next.js Hydration].

== Server rendering, prerendering and client-only routes: a worked example

`ng add @angular/ssr` generated `server.ts`, `main.server.ts`, `app.config.server.ts` and `app.routes.server.ts`. The
file that decides how each route is rendered is `app.routes.server.ts`. For the catalog: book pages are prerendered at
build time for two known ids, the account area is client-only because it is behind a login, and everything else is
rendered per request.

[source,typescript]
----
// app.routes.server.ts
import { RenderMode, ServerRoute } from '@angular/ssr';

export const serverRoutes: ServerRoute[] = [
  {
    path: 'books/:id',
    renderMode: RenderMode.Prerender,
    async getPrerenderParams() {
      return [{ id: '1' }, { id: '2' }];     // which :id values to render at build time
    },
  },
  { path: 'account', renderMode: RenderMode.Client },
  { path: '**', renderMode: RenderMode.Server },
];
----

[source,typescript]
----
// app.routes.ts
export const routes: Routes = [
  { path: '', redirectTo: 'books/1', pathMatch: 'full' },
  { path: 'books/:id', loadComponent: () => import('./ssr/pages').then((m) => m.BookPage) },
  { path: 'account', loadComponent: () => import('./ssr/pages').then((m) => m.Account) },
];
----

The page itself shows what code may and may not assume on the server. It reads the platform to report where it
rendered, defers a browser-only measurement until after rendering with `afterNextRender`, and hydrates its reviews block
lazily:

[source,typescript]
----
import { Component, DOCUMENT, PLATFORM_ID, afterNextRender, inject, input, signal } from '@angular/core';
import { isPlatformBrowser } from '@angular/common';

@Component({ selector: 'app-reviews', template: '<section id="reviews">Reviews of the book</section>' })
export class Reviews {}

@Component({
  selector: 'app-book-page',
  imports: [Reviews],
  template: `
    <h1>Book {{ id() }}</h1>
    <p id="where">rendered in the {{ where() }}</p>
    <p id="width">width: {{ width() }}</p>
    @defer (hydrate on viewport) {
      <app-reviews />
    } @placeholder {
      <p>Reviews</p>
    }
  `,
})
export class BookPage {
  readonly id = input.required<string>();
  protected readonly where = signal(isPlatformBrowser(inject(PLATFORM_ID)) ? 'browser' : 'server');
  protected readonly width = signal<number | null>(null);
  private readonly doc = inject(DOCUMENT);

  constructor() {
    afterNextRender(() => this.width.set(this.doc.defaultView?.innerWidth ?? 0));   // never runs on the server
  }
}
----

with `provideRouter(routes, withComponentInputBinding())` and
`provideClientHydration(withEventReplay(), withIncrementalHydration())` in `app.config.ts`. `ng build` printed
`Prerendered 2 static routes.` and wrote `browser/books/1/index.html` and `browser/books/2/index.html`. The
prerendered HTML for book 1 contained, abridged:

[source,html]
----
<app-root ng-version="22.2.5" ngh="2" ng-server-context="ssg">
  <app-book-page ngh="1">
    <h1>Book 1</h1>
    <p id="where">rendered in the server</p>
    <p id="width">width: </p>
    <app-reviews ngh="0"><section id="reviews">Reviews of the book</section></app-reviews><!--ngh=d0-->
  </app-book-page>
</app-root>
----

Read the markers: `ng-server-context="ssg"` says it was prerendered (`ssr` for a per-request render); the `ngh`
attributes are the hydration annotations the client uses to match this DOM to its component tree instead of
rebuilding it; `+<!--ngh=d0-->+` marks the `+@defer (hydrate ...)+` block as a hydration boundary; `width` is empty because
`afterNextRender` has not run on the server, so the layout-dependent value only exists once the browser takes over. Running the
built Node server and requesting other URLs showed the other two modes: `/books/9` (not prerendered) was rendered per
request with `ng-server-context="ssr"`, and `/account` returned the empty client-rendered shell with no book content.

....
flowchart TD
    R["Request for a URL"] --> M{"Matching ServerRoute"}

....

Three practical consequences:

* **Do not touch browser globals during server rendering.** `window`, `document`, `localStorage`, and `navigator` do
  not exist (or are not meaningful) on the server. Inject `DOCUMENT` instead of using the global, guard platform-specific
  code with `isPlatformBrowser(inject(PLATFORM_ID))`, and put DOM measurements and third-party widget setup in
  `afterNextRender` / `afterEveryRender`, which are skipped on the server.
* **Hosts are allow-listed.** The generated server refuses a request whose `Host` header is not on an allow-list, as a
  defense against host-header attacks: requesting `localhost` from `curl` returned `Bad Request` with a note that the
  host "is not allowed" until `NG_ALLOWED_HOSTS=localhost` was set. In production, list your real domains under
  `security.allowedHosts` in the build options of `angular.json` (or in the `allowedHosts` option of the server engine).
* **Server and client must render the same thing.** Hydration reuses the server DOM; if client code produces a different
  structure (for instance by reading `window.innerWidth` while rendering), Angular reports a hydration mismatch.
  Anything that can differ goes behind `afterNextRender` or a `@defer` block.
