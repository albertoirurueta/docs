`TestBed` builds a miniature module around the unit under test, and `ComponentFixture` gives access to the
instance and its rendered DOM. The runner that `ng new` configures is Vitest (through the `@angular/build:unit-test`
builder); Karma with Jasmine is deprecated but still supported, and the snippets below use Jasmine's `jasmine.createSpy`
where they were written for it -- the table in <<jasmine-vs-vitest,Jasmine and Vitest side by side>> maps each to its Vitest
spelling. See https://angular.dev/guide/testing[Testing].

== Anatomy of a component test

`TestBed.configureTestingModule()` declares the standalone components, imports, and providers the test needs;
`TestBed.createComponent()` returns a `ComponentFixture`.

[source,typescript]
----
import { ComponentFixture, TestBed } from '@angular/core/testing';
import { By } from '@angular/platform-browser';
import { Counter } from './counter';

describe('Counter', () => {
  let fixture: ComponentFixture<Counter>;
  let component: Counter;

  beforeEach(async () => {
    await TestBed.configureTestingModule({
      imports: [Counter],          // standalone component
    }).compileComponents();

    fixture = TestBed.createComponent(Counter);
    component = fixture.componentInstance;
    fixture.detectChanges();       // run the first change-detection pass
  });

  it('increments when the button is clicked', () => {
    const button = fixture.debugElement.query(By.css('button'));
    button.triggerEventHandler('click');
    fixture.detectChanges();

    expect(component.count()).toBe(1);
    expect(fixture.nativeElement.textContent).toContain('Count: 1');
  });
});
----

* `fixture.detectChanges()` runs change detection -- call it after every state change you want reflected in the
  DOM; `fixture.autoDetectChanges()` does it for you.
* `fixture.componentInstance` is the class instance; `fixture.nativeElement` is the host DOM node.
* `fixture.debugElement` wraps the rendered tree -- `+query(By.css(...))+`, `+queryAll(By.css(...))+`, and
  `+By.directive(...)+` find nodes without touching the real DOM API.

See https://angular.dev/guide/testing/components-basics[Testing components basics].

== Components with inputs and outputs

`fixture.componentRef.setInput()` sets a signal or decorator input; subscribe to an `output()` like an
observable.

[source,typescript]
----
it('emits selected on click', () => {
  const fixture = TestBed.createComponent(ProductCard);
  fixture.componentRef.setInput('product', { id: 7, name: 'Widget' });
  fixture.detectChanges();

  const selected = jasmine.createSpy('selected');
  fixture.componentInstance.selected.subscribe(selected);

  fixture.debugElement.query(By.css('button')).triggerEventHandler('click');
  expect(selected).toHaveBeenCalledWith(7);
});
----

Replace a dependency with a stub through the `providers` array, and spy on its methods:

[source,typescript]
----
class FakeCart { add = jasmine.createSpy('add'); }

TestBed.configureTestingModule({
  imports: [ProductCard],
  providers: [{ provide: CartService, useClass: FakeCart }],
});
----

`jasmine.createSpy()` makes a standalone spy; `+spyOn(obj, 'method').and.returnValue(...)+` wraps an existing
method. See https://angular.dev/guide/testing/components-scenarios[Component testing scenarios].

== Services and HTTP

Test a plain service by pulling it from the injector:

[source,typescript]
----
TestBed.configureTestingModule({ providers: [PriceService] });
const service = TestBed.inject(PriceService);
expect(service.withTax(100)).toBe(121);
----

For services that call `HttpClient`, combine `provideHttpClient()` with `provideHttpClientTesting()` and drive
requests through `HttpTestingController`:

[source,typescript]
----
import { provideHttpClient } from '@angular/common/http';
import { HttpTestingController, provideHttpClientTesting } from '@angular/common/http/testing';

let http: HttpTestingController;

beforeEach(() => {
  TestBed.configureTestingModule({
    providers: [ProductApi, provideHttpClient(), provideHttpClientTesting()],
  });
  http = TestBed.inject(HttpTestingController);
});

afterEach(() => http.verify());     // fail if any request is still outstanding

it('fetches a product', () => {
  const api = TestBed.inject(ProductApi);
  let result: Product | undefined;
  api.get(7).subscribe((p) => (result = p));

  const req = http.expectOne('/api/products/7');
  expect(req.request.method).toBe('GET');
  req.flush({ id: 7, name: 'Widget' });   // resolve the request

  expect(result?.name).toBe('Widget');
});
----

See https://angular.dev/guide/testing/services[Testing services] and
https://angular.dev/guide/http/testing[HTTP testing].

=== Asynchronous testing

* **`fakeAsync` + `tick(ms)` / `flush()`** -- run timers and microtasks synchronously on a virtual clock.
  `tick(1000)` advances time; `flush()` drains every pending timer.
* **`waitForAsync` + `fixture.whenStable()`** -- wait for real promises and XHR to settle, then assert.

Both helpers are built on Zone.js, so they work in Karma/Jasmine projects and in zone-based apps; in a zoneless
workspace use `await fixture.whenStable()` and Vitest's fake timers instead (see <<zoneless-tests,Zoneless defaults in
tests>>).

[source,typescript]
----
import { fakeAsync, tick } from '@angular/core/testing';

it('debounces the search', fakeAsync(() => {
  component.search('ab');
  component.search('abc');
  tick(300);
  expect(component.results()).toHaveSize(1);
}));
----

== Pipes and attribute directives

A pipe is a plain class -- call `transform` directly:

[source,typescript]
----
expect(new TruncatePipe().transform('a long string', 6)).toBe('a long…');
----

Test an attribute directive by applying it to a small host component and asserting the effect on the host
element:

[source,typescript]
----
@Component({ imports: [HighlightDirective], template: `<p appHighlight="gold">Hi</p>` })
class Host {}

const fixture = TestBed.createComponent(Host);
fixture.detectChanges();
const p = fixture.debugElement.query(By.css('p'));
expect(p.styles['background-color']).toBe('gold');
----

== Testing the router

Provide a router with `+provideRouter([...])+` and navigate with `RouterTestingHarness`. Run a functional guard
or resolver inside `+TestBed.runInInjectionContext(...)+` so `inject()` resolves.

[source,typescript]
----
import { provideRouter } from '@angular/router';
import { RouterTestingHarness } from '@angular/router/testing';

TestBed.configureTestingModule({
  providers: [provideRouter([{ path: 'products/:id', component: ProductPage }])],
});

const harness = await RouterTestingHarness.create();
const page = await harness.navigateByUrl('/products/7', ProductPage);
expect(page.id()).toBe(7);

// A functional guard in isolation:
const allowed = TestBed.runInInjectionContext(() => authGuard(routeSnapshot, stateSnapshot));
expect(allowed).toBe(true);
----

== Component harnesses

`@angular/cdk/testing` harnesses give a stable, implementation-independent API for driving a component in
tests. Load them through a `HarnessLoader` from `TestbedHarnessEnvironment`; Angular Material ships a harness
per component.

[source,typescript]
----
import { HarnessLoader } from '@angular/cdk/testing';
import { TestbedHarnessEnvironment } from '@angular/cdk/testing/testbed';
import { MatButtonHarness } from '@angular/material/button/testing';

const loader: HarnessLoader = TestbedHarnessEnvironment.loader(fixture);
const button = await loader.getHarness(MatButtonHarness.with({ text: 'Save' }));
await button.click();
----

See https://angular.dev/guide/testing/component-harnesses-overview[Component harnesses overview].

== Zoneless defaults in tests

New workspaces run zoneless, and tests follow suit: there is no `zone.js`, so `fakeAsync`, `tick()`, `flush()` and
`waitForAsync` (which are built on Zone.js) are not available unless you add the polyfill. The replacements are
`await fixture.whenStable()` to let rendering and pending tasks settle and, for time, Vitest's fake timers.

Because components default to `OnPush` from Angular 22, a test that mutates a plain field and calls
`fixture.detectChanges()` renders nothing new -- the view was never marked dirty. Drive components the way users and
parents do: `+fixture.componentRef.setInput(...)+` for inputs, signal writes for state, and real events for clicks.

[mermaid]
....
sequenceDiagram
    participant T as Test
    participant F as ComponentFixture
    participant C as Component
    participant D as DOM
    T->>F: TestBed.createComponent(BookCard)
    T->>F: componentRef.setInput('book', dune)
    T->>F: await whenStable()
    F->>C: change detection, effects run
    C->>D: render the template
    T->>D: click the button (triggerEventHandler or click())
    D->>C: event handler runs, signals change
    T->>F: await whenStable()
    F->>D: re-render the dirty view
    T->>D: assert on text and attributes
....

== A worked example: testing the catalog

The code under test is the book catalog used throughout this section: a `Cart` service built on signals, a `BookApi`
over `HttpClient`, a `BookCard` component, a `Highlight` directive, a debounced `Search`, and a `Signup` form.

[source,typescript]
----
// catalog.ts
export interface Book { id: number; title: string; price: number }

@Injectable({ providedIn: 'root' })
export class BookApi {
  private readonly http = inject(HttpClient);
  list(q = '') { return this.http.get<Book[]>('/api/books', { params: { q } }); }
  get(id: number) { return this.http.get<Book>(`/api/books/${id}`); }
}

@Injectable({ providedIn: 'root' })
export class Cart {
  private readonly items = signal<Book[]>([]);
  readonly count = computed(() => this.items().length);
  add(b: Book) { this.items.update((i) => [...i, b]); }
}

@Component({
  selector: 'app-book-card',
  template: `
    <h2>{{ book().title }}</h2>
    <button type="button" (click)="add()">Add</button>
    <span class="count">In cart: {{ cart.count() }}</span>
  `,
})
export class BookCard {
  readonly book = input.required<Book>();
  readonly added = output<number>();
  protected readonly cart = inject(Cart);
  add() { this.cart.add(this.book()); this.added.emit(this.book().id); }
}
----

=== A component, its output, and a stubbed dependency

With Vitest, `vi.fn()` plays the role of `jasmine.createSpy()`. The first test uses the real `Cart`; the second replaces it:

[source,typescript]
----
import { TestBed } from '@angular/core/testing';
import { By } from '@angular/platform-browser';
import { vi, describe, it, expect } from 'vitest';

const dune: Book = { id: 7, title: 'Dune', price: 12.5 };

describe('BookCard', () => {
  it('adds to the cart and emits', async () => {
    const fixture = TestBed.createComponent(BookCard);
    fixture.componentRef.setInput('book', dune);
    await fixture.whenStable();
    const added = vi.fn();
    fixture.componentInstance.added.subscribe(added);

    fixture.debugElement.query(By.css('button')).triggerEventHandler('click');
    await fixture.whenStable();

    expect(added).toHaveBeenCalledWith(7);
    expect(fixture.nativeElement.querySelector('.count').textContent).toBe('In cart: 1');
  });

  it('works with a stubbed Cart', async () => {
    const add = vi.fn();
    TestBed.configureTestingModule({
      providers: [{ provide: Cart, useValue: { add, count: () => 99 } }],
    });
    const fixture = TestBed.createComponent(BookCard);
    fixture.componentRef.setInput('book', dune);
    await fixture.whenStable();

    (fixture.nativeElement.querySelector('button') as HTMLButtonElement).click();

    expect(add).toHaveBeenCalledWith(dune);
    expect(fixture.nativeElement.querySelector('.count').textContent).toBe('In cart: 99');
  });
});
----

The stub only has to satisfy the members the component touches; here `count` is a plain function because the template
just calls it. Both tests passed unmodified against a real Angular 22 workspace.

=== HTTP success and failure

[source,typescript]
----
describe('BookApi', () => {
  let http: HttpTestingController;

  beforeEach(() => {
    TestBed.configureTestingModule({ providers: [provideHttpClient(), provideHttpClientTesting()] });
    http = TestBed.inject(HttpTestingController);
  });
  afterEach(() => http.verify());

  it('GETs one book', () => {
    let got: Book | undefined;
    TestBed.inject(BookApi).get(7).subscribe((b) => (got = b));

    const req = http.expectOne('/api/books/7');
    expect(req.request.method).toBe('GET');
    req.flush(dune);

    expect(got).toEqual(dune);
  });

  it('surfaces a 500 as an error', () => {
    let status = 0;
    TestBed.inject(BookApi).get(7).subscribe({ error: (e) => (status = e.status) });

    http.expectOne('/api/books/7').flush('boom', { status: 500, statusText: 'Server Error' });

    expect(status).toBe(500);
  });
});
----

`+flush(body, { status, statusText })+` simulates an error response, so the unhappy path costs one extra test and no
server.

=== Debounce with fake timers

The typeahead from xref:web/angular/rxjs-and-async.adoc[RxJS and async] debounces input for 300 ms. Without `fakeAsync`,
Vitest's fake timers control the clock that `debounceTime` uses:

[source,typescript]
----
describe('Search', () => {
  beforeEach(() => {
    vi.useFakeTimers();
    TestBed.configureTestingModule({ providers: [provideHttpClient(), provideHttpClientTesting()] });
  });
  afterEach(() => vi.useRealTimers());

  it('sends one request after the debounce', () => {
    const http = TestBed.inject(HttpTestingController);
    const fixture = TestBed.createComponent(Search);
    fixture.detectChanges();

    fixture.componentInstance.q.setValue('du');
    fixture.componentInstance.q.setValue('dun');
    vi.advanceTimersByTime(299);
    http.expectNone((r) => r.url === '/api/books');       // still waiting
    vi.advanceTimersByTime(1);
    http.expectOne((r) => r.url === '/api/books' && r.params.get('q') === 'dun').flush([dune]);

    fixture.detectChanges();
    expect(fixture.nativeElement.querySelectorAll('li').length).toBe(1);
  });
});
----

Two keystrokes inside the window produced a single request, for the last value -- the behavior the operator chain is
meant to guarantee, now pinned by a test.

=== A directive and a form

[source,typescript]
----
@Component({ imports: [Highlight], template: `<p appHighlight="gold">Hi</p>` })
class Host {}

it('colours the host on hover', async () => {
  const fixture = TestBed.createComponent(Host);
  await fixture.whenStable();
  const p = fixture.debugElement.query(By.directive(Highlight));

  p.triggerEventHandler('mouseenter');
  await fixture.whenStable();
  expect((p.nativeElement as HTMLElement).style.backgroundColor).toBe('gold');

  p.triggerEventHandler('mouseleave');
  await fixture.whenStable();
  expect((p.nativeElement as HTMLElement).style.backgroundColor).toBe('');
});

it('validates the signup form and emits the e-mail', async () => {
  const fixture = TestBed.createComponent(Signup);
  await fixture.whenStable();
  const el: HTMLElement = fixture.nativeElement;
  const input = el.querySelector('#email') as HTMLInputElement;
  const button = el.querySelector('button') as HTMLButtonElement;
  expect(button.disabled).toBe(true);                       // required, so invalid at the start

  input.value = 'nope';
  input.dispatchEvent(new Event('input'));
  input.dispatchEvent(new Event('blur'));                   // touched, so the error becomes visible
  await fixture.whenStable();
  expect(el.querySelector('.err')?.textContent).toBe('Invalid e-mail');

  const sent = vi.fn();
  fixture.componentInstance.sent.subscribe(sent);
  input.value = 'a@b.co';
  input.dispatchEvent(new Event('input'));
  await fixture.whenStable();
  expect(button.disabled).toBe(false);
  (el.querySelector('form') as HTMLFormElement).dispatchEvent(new Event('submit'));
  expect(sent).toHaveBeenCalledWith('a@b.co');
});
----

The form test types into the real `<input>` by setting its value and dispatching `input`, so the forms directives
run exactly as they do for a user. Asserting on the DOM rather than on `form.valid` also proves the template reacts.

=== A hand-written harness

Angular Material ships harnesses for its components; you can write one for yours with `ComponentHarness`, so tests
describe *what the user does* instead of *which selector to query*:

[source,typescript]
----
import { ComponentHarness } from '@angular/cdk/testing';
import { TestbedHarnessEnvironment } from '@angular/cdk/testing/testbed';

class BookCardHarness extends ComponentHarness {
  static hostSelector = 'app-book-card';

  private readonly title = this.locatorFor('h2');
  private readonly addButton = this.locatorFor('button');
  private readonly count = this.locatorFor('.count');

  async titleText() { return (await this.title()).text(); }
  async add() { await (await this.addButton()).click(); }
  async inCart() { return (await this.count()).text(); }
}

it('drives the card through its harness', async () => {
  const fixture = TestBed.createComponent(BookCard);
  fixture.componentRef.setInput('book', dune);
  const card = await TestbedHarnessEnvironment.harnessForFixture(fixture, BookCardHarness);

  expect(await card.titleText()).toBe('Dune');
  await card.add();
  expect(await card.inCart()).toBe('In cart: 1');
});
----

Harness methods are asynchronous because the same harness works against a real browser (Protractor-style) and the unit
test environment; in `TestBed` they also wait for stability before each step, so you do not call `whenStable()` yourself.

=== Coverage thresholds

Enforce a minimum with a Vitest configuration passed through `--runner-config`:

[source,typescript]
----
// vitest-base.config.ts
import { defineConfig } from 'vitest/config';

export default defineConfig({
  test: {
    coverage: {
      thresholds: { statements: 80, branches: 70, functions: 80, lines: 80 },
    },
  },
});
----

[source,bash]
----
ng test --coverage --runner-config=vitest-base.config.ts
----

When the numbers are under the thresholds the run fails with messages such as `Coverage for lines (23.75%) does not meet
global threshold (80%)`, which is what you want in a pipeline.

== Jasmine and Vitest side by side

[cols="1,1",options="header"]
|===
| Jasmine / Karma | Vitest

| `jasmine.createSpy('x')` | `vi.fn()`
| `spyOn(obj, 'm').and.returnValue(1)` | `vi.spyOn(obj, 'm').mockReturnValue(1)`
| `expect(x).toHaveSize(1)` | `expect(x).toHaveLength(1)`
| `+fakeAsync(() => { tick(300); })+` | `vi.useFakeTimers(); vi.advanceTimersByTime(300);`
| `waitForAsync` + `whenStable()` | `await fixture.whenStable()`
| `ng test --code-coverage` and `karma.conf.js` thresholds | `ng test --coverage` and `thresholds` in a Vitest config
| `describe`, `it`, `beforeEach`: globals | the same names, importable from `vitest`
|===

== Coverage and the Vitest migration

Run `ng test --coverage` to collect coverage. With the Vitest runner, install a coverage provider first --
`npm i -D @vitest/coverage-v8` (or `@vitest/coverage-istanbul`) -- otherwise the command stops and names the missing
package. Treat coverage as a gap finder, not a target. See https://angular.dev/guide/testing/code-coverage[Code
coverage].

Angular started the move from **Karma/Jasmine** (now deprecated) to **Vitest**, and a workspace generated by the
current CLI already uses it; existing ones follow
https://angular.dev/guide/testing/migrating-to-vitest[the Vitest migration guide]. `TestBed`,
`ComponentFixture`, and component harnesses are unchanged -- only the runner and its assertion globals differ
(`vi` in place of `jasmine`, Jest-style matchers).

== End-to-end Testing

Angular apps are commonly e2e-tested with the same real-browser tools used for any other web app --
Playwright or Cypress -- rather than an Angular-specific tool. See
xref:web/e2e-testing/index.adoc[E2E Testing in the Browser] for the full tool-focused reference: install, headless vs. headed
execution, evidence capture, CI/CD, and a Selenium/Playwright/Cypress comparison.
