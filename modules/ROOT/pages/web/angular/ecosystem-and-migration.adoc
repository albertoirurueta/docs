= Ecosystem and Migration
:description: What NgModule was and why standalone replaced it, the automated standalone and control-flow migrations, keeping an app up to date with ng update, the state-management options, and the build, monorepo, and meta-framework tooling around Angular.

Modern Angular is standalone-first, releases on a predictable schedule, and sits in a wide ecosystem of
state-management and build tooling. This page covers the move off `NgModule`, how to stay current, and the
libraries most often paired with Angular.

== From NgModule to standalone

An `NgModule` was a class with an `@NgModule` decorator that grouped related pieces: `declarations` (the
components, directives, and pipes it owned), `imports` (other modules whose exports it needed), `providers`
(services), and -- for the root module -- `bootstrap` (the component to render first). Every component had to
belong to exactly one module, so adding a component meant editing a module too.

*Standalone* components, directives, and pipes declare their own dependencies through the `imports` array on
their decorator, so `NgModule` is no longer needed. The app boots from a component instead of a module:

[source,typescript]
----
import { bootstrapApplication } from '@angular/platform-browser';
import { provideRouter } from '@angular/router';
import { provideHttpClient } from '@angular/common/http';
import { App } from './app/app';
import { routes } from './app/app.routes';

bootstrapApplication(App, {
  providers: [provideRouter(routes), provideHttpClient()],
});
----

Two schematics automate the change to an existing codebase. The standalone migration converts declarations,
drops now-empty `NgModule` classes, and rewrites the bootstrap:

[source,bash]
----
ng generate @angular/core:standalone
----

The control-flow migration rewrites `+*ngIf+` / `+*ngFor+` / `+*ngSwitch+` to the built-in `@if` / `@for` / `@switch`
blocks:

[source,bash]
----
ng generate @angular/core:control-flow
----

See https://angular.dev/guide/ngmodules[the NgModules guide] for the legacy model and
https://angular.dev/reference/migrations[the migrations reference] for every automated schematic (standalone,
control flow, `inject()`, signal inputs / outputs / queries, and more).

== Deep dive: migrating a small NgModule application

The schematics are best understood by running them. This walk-through takes a deliberately classic BookShelf -- a root
`NgModule`, a `BooksModule` that declares one component, a constructor-injected service, `+*ngFor+` / `+*ngIf+` in the
template -- and migrates it step by step with the CLI. Each step is followed by a build, because a schematic can only
rewrite what it can analyse.

[mermaid]
....
flowchart TD
    START["NgModule application that builds"] --> S1["ng g @angular/core:standalone --mode=convert-to-standalone"]
    S1 --> B1{"Build passes?"}
    B1 -->|"fix by hand"| S1
    B1 -->|"yes"| S2["... --mode=prune-ng-modules"]
    S2 --> B2{"Build passes?"}
    B2 -->|"fix by hand"| S2
    B2 -->|"yes"| S3["... --mode=standalone-bootstrap"]
    S3 --> B3{"Build passes?"}
    B3 -->|"fix by hand"| S3
    B3 -->|"yes"| S4["control-flow, then inject, then signal-inputs and outputs"]
    S4 --> DONE["Modern standalone application"]
....

The starting point (abridged):

[source,typescript]
----
// books/books.module.ts
@NgModule({
  declarations: [BookListComponent],
  imports: [CommonModule],
  exports: [BookListComponent],
})
export class BooksModule {}

// books/book-list.component.ts
@Component({
  selector: 'app-book-list',
  standalone: false,
  template: `
    <ul>
      <li *ngFor="let b of books; trackBy: byId">
        {{ b.title | uppercase }}
        <span *ngIf="b.price > 40; else cheap">premium</span>
        <ng-template #cheap>budget</ng-template>
      </li>
    </ul>
    <p *ngIf="books.length === 0">No books</p>
    <button (click)="picked.emit(books[0])">Pick first</button>
  `,
})
export class BookListComponent implements OnInit {
  @Input() title = '';
  @Input({ required: true }) pageSize!: number;
  @Output() picked = new EventEmitter<{ title: string }>();
  books: { id: string; title: string; price: number }[] = [];

  constructor(private readonly service: BookService) {}
  ngOnInit(): void { this.books = this.service.list(); }
  byId(_: number, b: { id: string }): string { return b.id; }
}
----

*Step 1 -- convert declarations.* `ng generate @angular/core:standalone --mode=convert-to-standalone` removes
`standalone: false`, gives the component an `imports` array with only what its template uses (`NgFor`, `NgIf`,
`UpperCasePipe`), and lists the component in the module's `imports` instead of `declarations`.

*Step 2 -- delete the modules.* `--mode=prune-ng-modules` removes `BooksModule` and the references to it.

*Step 3 -- bootstrap without a module.* `--mode=standalone-bootstrap` deletes `app-module.ts`, rewrites `main.ts` to
`bootstrapApplication`, and converts the root component. The result keeps a bridge for the one module it cannot remove:

[source,typescript]
----
// main.ts after step 3
bootstrapApplication(App, {
  providers: [
    importProvidersFrom(BrowserModule, AppRoutingModule),
    provideBrowserGlobalErrorListeners(),
  ],
}).catch((err) => console.error(err));
----

In this example the build now fails with `NG8001: 'app-book-list' is not a known element`: the root component's template used `<app-book-list>`, but nothing had added `BookListComponent` to the root
component's `imports`. *Automated migrations are a starting point, not a guarantee, which is why each step is followed by a
build.* The fix is one line, and the leftover `importProvidersFrom` bridge is replaced by the router's own provider:

[source,typescript]
----
@Component({
  selector: 'app-root',
  templateUrl: './app.html',
  imports: [RouterOutlet, BookListComponent],      // added by hand
})
export class App { /* ... */ }

bootstrapApplication(App, {
  providers: [provideRouter(routes), provideBrowserGlobalErrorListeners()],   // replaces importProvidersFrom(...)
});
----

*Step 4 -- modernise the template.* `ng generate @angular/core:control-flow` rewrites the three structural directives and
deletes the `NgFor` / `NgIf` imports it made redundant:

[source,html]
----
<ul>
  @for (b of books; track byId($index, b)) {
    <li>
      {{ b.title | uppercase }}
      @if (b.price > 40) {
        <span>premium</span>
      } @else {
        budget
      }
    </li>
  }
</ul>
@if (books.length === 0) {
  <p>No books</p>
}
----

Note the two details a human should tidy up: the `trackBy` function became `track byId($index, b)` (simplify it to `track b.id`), and
the named `<ng-template #cheap>` became the `@else` block body.

*Step 5 -- modernise the class.* Three more schematics change the component's API without changing its behaviour; run them
one at a time and build in between:

[source,bash]
----
ng generate @angular/core:inject          # constructor parameters -> inject()
ng generate @angular/core:signal-inputs   # @Input -> input()
ng generate @angular/core:outputs         # @Output + EventEmitter -> output()
----

[source,typescript]
----
export class BookListComponent implements OnInit {
  private readonly service = inject(BookService);

  readonly title = input('');
  readonly pageSize = input.required<number>();
  readonly picked = output<{ title: string }>();
  books: { id: string; title: string; price: number }[] = [];

  ngOnInit(): void { this.books = this.service.list(); }
  byId(_: number, b: { id: string }): string { return b.id; }
}
----

Because inputs became signals, every *read* of `this.title` or `this.pageSize` elsewhere in the class is rewritten to
`this.title()` by the same schematic. The parent's template is unaffected (`[pageSize]="10"` binds the same way). The
service gets the same treatment with `ng generate @angular/core:service`, which rewrites
`+@Injectable({ providedIn: 'root' })+` to `@Service()`.

=== The schematics at a glance

[cols="2,3",options="header"]
|===
| Command (after `ng generate @angular/core:`) | What it rewrites

| `standalone` (three `--mode` values) | declarations, then module removal, then bootstrap
| `control-flow` | `+*ngIf+` / `+*ngFor+` / `+*ngSwitch+` to `@if` / `@for` / `@switch`
| `inject` | constructor injection to `inject()`
| `signal-inputs`, `signal-queries`, `outputs`, `signals` | decorators to signal-based `input()`, `viewChild()` and friends, `output()`; `signals` runs all of them
| `service` | `+@Injectable({ providedIn: 'root' })+` to `@Service()`
| `route-lazy-loading` | eagerly imported route components to `loadComponent`
| `common-to-standalone` | `CommonModule` to the individual pipes and directives
| `ngclass-to-class`, `ngstyle-to-style` | `[ngClass]` / `[ngStyle]` to `[class]` / `[style]` bindings
| `self-closing-tag` | `<app-x></app-x>` to `<app-x />`
| `cleanup-unused-imports` | unused entries in a standalone component's `imports`
|===

Commit between schematics, run the test suite after each, and review the diff: the rewrite is mechanical, so judgement
calls (a better `track` key, a store instead of a service) are still yours. `ng update` runs the version-specific
migrations for you when you move to a new major; these standalone commands are for modernising code at your own pace.

== Keeping up to date

Angular ships a major release roughly every *six months*. Each major gets about six months of active support and then
12 months of long-term support (LTS), 18 months in all -- so at any time the current major plus the previous two are
supported. Upgrade with `ng update`, which runs version-aware schematics that patch breaking changes for you:

[source,bash]
----
ng update @angular/core @angular/cli
----

https://angular.dev/update[The interactive update guide] generates the exact command list and manual steps for
any from/to version pair; https://angular.dev/reference/releases[the releases reference] lists the schedule and
support windows.

== State management

For most apps, *signals plus small services* -- a service that owns a `signal` (or a `computed` over several)
and exposes methods to update it -- is enough and needs no dependency. Reach for a library when many unrelated
components share complex, frequently-changing state.

* *NgRx Store + Effects* -- a Redux-style single store with actions, reducers, selectors, and `Effects` for
  side effects; the most established option. See https://ngrx.io/[ngrx.io].
* *NgRx SignalStore* -- the same team's lighter, signal-based store built from `signalStore()` and
  `withState` / `withComputed` / `withMethods` features. See https://ngrx.io/guide/signals[the SignalStore
  guide].
* *NGXS* -- a class-and-decorator store (`@State`, `@Action`, `@Selector`) that many find less boilerplate-heavy
  than classic NgRx. See https://www.ngxs.io/[ngxs.io].
* *Elf* -- a small, modular reactive store built on RxJS with composable feature functions and a rich set of
  entity helpers. See https://ngneat.github.io/elf/[the Elf docs].

[source,typescript]
----
import { Injectable, computed, signal } from '@angular/core';

@Injectable({ providedIn: 'root' })
export class CartStore {
  private readonly items = signal<string[]>([]);
  readonly count = computed(() => this.items().length);

  add(item: string): void {
    this.items.update((list) => [...list, item]);
  }
}
----

The same store written with NgRx SignalStore keeps the state, the derived values, and the updates in one declaration, and
adds `patchState` for typed, immutable updates:

[source,typescript]
----
import { computed } from '@angular/core';
import { patchState, signalStore, withComputed, withMethods, withState } from '@ngrx/signals';

interface CartState { items: { id: string; price: number }[]; }

export const CartStore = signalStore(
  { providedIn: 'root' },
  withState<CartState>({ items: [] }),
  withComputed(({ items }) => ({
    count: computed(() => items().length),
    total: computed(() => items().reduce((sum, i) => sum + i.price, 0)),
  })),
  withMethods((store) => ({
    add(item: { id: string; price: number }): void {
      patchState(store, (s) => ({ items: [...s.items, item] }));
    },
    clear(): void { patchState(store, { items: [] }); },
  })),
);
----

Both stores are tested the same way, by injecting them with `TestBed.inject` and asserting on the signals:

[source,typescript]
----
it('NgRx SignalStore', () => {
  const store = TestBed.inject(CartStore);
  store.add({ id: 'a', price: 10 });
  store.add({ id: 'b', price: 5 });
  expect(store.count()).toBe(2);
  expect(store.total()).toBe(15);
});
----

A practical rule: start with the signals-plus-service store; move to SignalStore when you want consistent structure,
plugins (entities, devtools, rxMethod for async work), or several stores that should look alike.

== Build, monorepo, and meta-framework tooling

* *Nx* -- an extensible monorepo build system with Angular generators, computation caching, and affected-only
  task running; a common choice for multi-app Angular workspaces. See https://nx.dev/[nx.dev].
* *AnalogJS* -- a Vite-powered meta-framework for Angular adding file-based routing, server routes, and
  Markdown content, aimed at full-stack and content sites. See https://analogjs.org/[analogjs.org].
* *Zoneless change detection* -- running without Zone.js, the default for new applications, where signals
  and explicit notifications drive updates; covered on
  xref:web/angular/lifecycle-and-change-detection.adoc[Lifecycle and Change Detection].
