= Signals
:description: Angular signals for reactive state -- signal() with set and update, computed() for derived values, effect() for side effects, linkedSignal() and resource() for writable-derived and async state, and when to use signals versus RxJS.
:keywords: Angular signals, signal(), set, update, computed(), effect(), untracked(), equality function, linkedSignal(), resource(), rxResource(), toSignal, toObservable, signals vs RxJS

include::partial$ai-disclaimer.adoc[]

A **signal** is a reactive value wrapper: reading it inside a reactive context (a template, a `computed()`, or
an `effect()`) records a dependency, so any consumer re-runs automatically when the value changes. Signals are
the default state primitive in modern Angular. See https://angular.dev/guide/signals[Signals].

== `signal()`

`signal(initialValue)` returns a `WritableSignal`. Call it with no arguments to **read**; use `.set(value)` to
replace it and `.update(fn)` to derive the next value from the current one.

[source,typescript]
----
import { signal } from '@angular/core';

const count = signal(0);

count();                      // read -> 0
count.set(10);                // replace
count.update((n) => n + 1);   // derive from current -> 11
----

[source,html]
----
<button (click)="count.set(count() + 1)">{{ count() }}</button>
----

By default a signal uses `Object.is` to decide whether the value changed; supply an **equality function** to
treat structurally equal values as unchanged and skip notifying consumers.

[source,typescript]
----
import _ from 'lodash-es';

const point = signal({ x: 0, y: 0 }, { equal: _.isEqual });
point.set({ x: 0, y: 0 });   // deep-equal -> consumers do NOT re-run
----

== `computed()`

`computed(fn)` creates a read-only signal derived from other signals. It is **lazy** (the body runs only when
read), **memoised** (re-runs only when a tracked dependency changes), and **glitch-free** (never exposes a
partially-updated intermediate value).

[source,typescript]
----
import { signal, computed } from '@angular/core';

const price = signal(100);
const qty = signal(3);
const total = computed(() => price() * qty());   // tracks price and qty

total();          // 300
qty.set(4);
total();          // 400 -- recomputed on read
----

== `effect()`

`effect(fn)` runs a side effect whenever any signal it reads changes. It runs once after creation, then again
(asynchronously, batched, after change detection) on each dependency change. Register it in an injection
context; it is cleaned up automatically on destroy. Return a cleanup callback via the `onCleanup` argument to
tear down the previous run.

[source,typescript]
----
import { Component, effect, signal, inject } from '@angular/core';
import { Analytics } from './analytics';

@Component({ selector: 'app-search', templateUrl: './search.html' })
export class Search {
  readonly query = signal('');
  private readonly analytics = inject(Analytics);

  constructor() {
    effect((onCleanup) => {
      const q = this.query();
      const handle = setTimeout(() => this.analytics.track('search', q), 300);
      onCleanup(() => clearTimeout(handle));   // cancel if query changes again
    });
  }
}
----

Use `untracked(fn)` to read a signal **without** creating a dependency -- so the effect reacts to some signals
but merely samples others.

[source,typescript]
----
import { untracked } from '@angular/core';

effect(() => {
  const q = this.query();                       // reactive: re-runs when query changes
  const user = untracked(() => this.userId());   // sampled: changes here do NOT re-run
  this.log(q, user);
});
----

Prefer `computed()` for deriving state and reserve `effect()` for genuine side effects (logging, DOM APIs,
syncing to `localStorage`); do not `set()` other signals from an effect. See
https://angular.dev/guide/signals/effect[Effects] and the note on
https://angular.dev/guide/signals#reading-without-tracking-dependencies[reading without tracking].

== `linkedSignal()` and `resource()`

`linkedSignal()` produces a **writable** signal that also derives from a source: it recomputes when the source
changes but can be overridden locally until the next source change -- ideal for a "selected item" that resets
when the list reloads.

[source,typescript]
----
import { signal, linkedSignal } from '@angular/core';

const options = signal<string[]>(['sm', 'md', 'lg']);
const choice = linkedSignal(() => options()[0]);   // follows options, but writable

choice.set('lg');       // local override
options.set(['xs', 's']);
choice();               // 'xs' -- reset to the new default
----

`resource()` wraps an async data source in signals, exposing `.value()`, `.status()`, `.error()`, and
`.reload()`, and cancels an in-flight request when its `params` change. `rxResource()` is the same backed by
an `Observable`. HTTP-specific fetching (`httpResource()`) is covered on
xref:web/angular/http-client.adoc[HTTP client].

[source,typescript]
----
import { resource, signal } from '@angular/core';

const userId = signal(1);
const user = resource({
  params: () => ({ id: userId() }),
  loader: ({ params, abortSignal }) =>
    fetch(`/api/users/${params.id}`, { signal: abortSignal }).then((r) => r.json()),
});

user.status();   // 'idle' | 'loading' | 'resolved' | 'error' | 'reloading'
----

References: https://angular.dev/guide/signals/linked-signal[`linkedSignal`] and
https://angular.dev/guide/signals/resource[`resource`].

== Worked example: a shopping cart

A cart is a good test of the mental model because it has source state (lines, tax rate), derived state (subtotal,
total), and a side effect (persisting). The code below was run in a test; the comments are the observed results.

[source,typescript]
----
import { computed, signal } from '@angular/core';

interface Line { title: string; price: number; qty: number }

let subtotalRuns = 0;
const lines = signal<Line[]>([{ title: 'Dune', price: 10, qty: 1 }]);
const taxRate = signal(0.21);

const subtotal = computed(() => { subtotalRuns++; return lines().reduce((s, l) => s + l.price * l.qty, 0); });
const total = computed(() => subtotal() * (1 + taxRate()));

// subtotalRuns === 0          computed() is lazy: nothing has been calculated yet
total();                    // 12.10  subtotalRuns === 1
total(); total();           // memoised: subtotalRuns is still 1
taxRate.set(0.1);
total();                    // 11.00  subtotalRuns is still 1: subtotal does not depend on taxRate
lines.update((ls) => [...ls, { title: 'Emma', price: 5, qty: 2 }]);
total();                    // 22.00  subtotalRuns === 2

lines()[0].qty = 100;       // mutate in place: no notification
total();                    // still 22.00 -- stale!
----

The last line is the usual way to break signals. A signal notifies when `set()` or `update()` stores a value that
is not equal (by `Object.is`) to the old one, so mutating the array's contents is invisible. Always produce a new
array or object, as `+update((ls) => [...ls, line])+` does.

Computed signals are also **glitch-free**: a value that depends on the same source through two paths (a "diamond")
is never observed half-updated.

[source,typescript]
----
const a = signal(1);
const b = computed(() => a() * 2);
const c = computed(() => a() * 3);
const seen: string[] = [];
const d = computed(() => { const r = `${b()}/${c()}`; seen.push(r); return r; });

d();          // '2/3'
a.set(2);
d();          // '4/6' -- never a mixed state such as '4/3'
seen;         // ['2/3', '4/6']
----

=== When effects run

An `effect()` is not a synchronous subscription. Writes only *mark* it dirty; the effect runs later, once, during the
next change-detection flush. Created with an `onCleanup` callback and a `untracked()` read, in a test where
`TestBed.tick()` forces the flush:

[source,typescript]
----
const log: string[] = [];
const query = signal('a');
const user = signal('u1');

// effect() needs an injection context: a component constructor, or runInInjectionContext in a test
const ref = TestBed.runInInjectionContext(() => effect((onCleanup) => {
  const q = query();                       // tracked
  const u = untracked(user);               // sampled, not tracked
  log.push(`run q=${q} u=${u}`);
  onCleanup(() => log.push(`cleanup after q=${q}`));
}));

TestBed.tick();                            // run q=a u=u1
query.set('b');
query.set('c');                            // two writes before the flush
TestBed.tick();                            // cleanup after q=a, run q=c u=u1   (b was never observed)
user.set('u2');
TestBed.tick();                            // nothing: user is untracked
ref.destroy();                             // cleanup after q=c
----

Three properties are visible: effects are **batched** (two writes, one run, and the intermediate value `b` is skipped),
the previous run's cleanup always runs **before** the next run, and a signal read inside `untracked()` does not
re-trigger the effect. Because an effect can only observe the latest value, never rely on one to see every change; use
RxJS when every emission matters.

== `linkedSignal` with the previous state

The one-argument form resets the choice to the first option whenever the options change. A "selected item" usually
wants something smarter: keep the selection if the item still exists. The object form receives the previous value:

[source,typescript]
----
import { linkedSignal, signal } from '@angular/core';

interface Opt { id: number; label: string }

const options = signal<Opt[]>([{ id: 1, label: 'A' }, { id: 2, label: 'B' }, { id: 3, label: 'C' }]);

const selected = linkedSignal<Opt[], Opt | undefined>({
  source: options,
  computation: (next, previous) => next.find((o) => o.id === previous?.value?.id) ?? next[0],
});

selected.set({ id: 2, label: 'B' });                          // the user picks B
options.set([{ id: 2, label: 'B*' }, { id: 9, label: 'Z' }]); // the list reloads
selected()?.label;   // 'B*' -- the selection followed its id to the refreshed object
options.set([{ id: 7, label: 'X' }]);                         // the selected item disappeared
selected()?.label;   // 'X'  -- fell back to the first option
----

== The life of a `resource()`

A resource runs its `loader` whenever the signals read in `params` change, aborts the previous run through
`abortSignal`, and exposes the outcome as signals. The statuses form a small state machine:

[mermaid]
....
stateDiagram-v2
    [*] --> loading: created with params
    loading --> resolved: loader returned
    loading --> error: loader threw
    loading --> loading: params changed (previous run aborted)
    resolved --> reloading: reload()
    reloading --> resolved: loader returned
    resolved --> loading: params changed
    error --> loading: params changed or reload()
....

In a test, a resource whose loader takes 30 ms for id 1 and 5 ms for the others, with `id` switched to 2 while the
first request is still running, ended like this: the first run was aborted (the loader saw `abortSignal.aborted`), the
second resolved with `+{ id: 2, title: 'Book 2' }+`, and the recorded loader calls were `1, 2`. After switching to 3 and
calling `reload()`, the status was `reloading` -- with the old value still readable, which lets a template keep showing
stale data while a spinner runs -- and then `resolved`, with the loader called twice for id 3.

[source,typescript]
----
@Component({
  selector: 'app-book-page',
  template: `
    @switch (book.status()) {
      @case ('loading') { <p>Loading...</p> }
      @case ('error') { <p>Could not load the book.</p> <button (click)="book.reload()">Retry</button> }
      @default { <h1>{{ book.value()?.title }}</h1> @if (book.isLoading()) { <small>refreshing</small> } }
    }
  `,
})
export class BookPage {
  readonly id = input.required<number>();
  readonly book = resource({
    params: () => ({ id: this.id() }),
    loader: async ({ params, abortSignal }) => {
      const r = await fetch(`/api/books/${params.id}`, { signal: abortSignal });
      if (!r.ok) throw new Error(`HTTP ${r.status}`);
      return (await r.json()) as { id: number; title: string };
    },
  });
}
----

Passing `abortSignal` to `fetch` is what turns "ignore the stale answer" into "cancel the stale request".

== Signals in components: a checklist

* Hold mutable component state in `signal()`, derived state in `computed()`, and call both with `()` in templates.
* Never `set()` a signal inside a `computed()` (it must be pure); avoid it inside `effect()` too -- prefer `linkedSignal()`.
* Replace, never mutate, arrays and objects held in signals; add an `equal` function only when a value is genuinely
  compared structurally.
* Keep effects for work that leaves the signal graph (storage, logging, third-party DOM libraries, analytics).
* Read an async value through `resource()`/`httpResource()` or `toSignal()`; avoid `subscribe()` into a signal by hand.

== Signals vs. RxJS

Both are reactive; they solve different problems.

[cols="1,1",options="header"]
|===
| Reach for a signal | Reach for RxJS (see xref:web/angular/rxjs-and-async.adoc[RxJS and async])

| Synchronous UI state that always has a current value | Streams of events over time (keystrokes, websocket messages)
| Derived values (`computed`) | Time-based combinators: `debounceTime`, `throttleTime`, `bufferTime`
| Template bindings, component state | Cancellation and switching between requests (`switchMap`)
| Inputs, model, and queries (all signal-based) | Complex multi-source orchestration and back-pressure
|===

Bridge between them with `toSignal(obs$)` and `toObservable(sig)` from `@angular/core/rxjs-interop`. Signal
**inputs** (`input()`), **model** (`model()`), and **queries** (`viewChild()` / `contentChildren()`) are all
covered on xref:web/angular/component-communication.adoc[Component communication]. See
https://angular.dev/ecosystem/rxjs-interop[RxJS interop].
