= TypeScript Essentials for Angular
:description: The subset of TypeScript that Angular relies on -- types, interfaces, readonly, unions, generics, and utility types -- plus decorators and the tsconfig settings Angular enables.

Angular is written in TypeScript and expects your application to be too. This page covers only the language
features that show up constantly in Angular code; for the language itself see the
xref:programming-languages/typescript/index.adoc[TypeScript Reference], and for the underlying runtime semantics see
xref:programming-languages/javascript/types.adoc[JavaScript / TypeScript types] and xref:programming-languages/javascript/classes.adoc[classes].

== The subset that matters

* *Type annotations* on parameters, fields, and return values give the compiler and the template type-checker
  something to verify.
* *Interfaces* describe the shape of data -- API responses, component inputs, configuration objects.
* *`readonly`* marks fields that must not be reassigned after construction; pair it with signals for state
  that is only replaced through `.set()` / `.update()`.
* *Union and literal types* model a value that is one of a fixed set -- a status, a variant, a mode.
* *Generics* let a service or a function work over a caller-chosen type without losing type safety
  (`+HttpClient.get<User>(...)+`, `signal<User | null>(null)`).
* *Utility types* transform existing types: `Partial<T>` (all properties optional), `Pick<T, K>` (a subset),
  `Record<K, V>` (a map type).

[source,typescript]
----
export interface User {
  readonly id: number;
  name: string;
  role: 'admin' | 'editor' | 'viewer';   // literal union
}

// generic service method
getUser(id: number) {
  return this.http.get<User>(`/api/users/${id}`);
}

// utility types
type UserPatch = Partial<User>;                 // { id?, name?, role? }
type UserSummary = Pick<User, 'id' | 'name'>;   // { id, name }
type UsersById = Record<number, User>;          // { [id: number]: User }
----

See https://www.typescriptlang.org/docs/[the TypeScript handbook] for the full language reference.

== Modeling data: a worked example

The examples below are one file, `essentials.ts`, that models the catalog's data and the places Angular code leans on the
type system. It was compiled with the generated workspace's settings, with `noUncheckedIndexedAccess` and
`exactOptionalPropertyTypes` added, and exercised in a test.

=== Interfaces, optional properties and utility types

[source,typescript]
----
export interface Book {
  readonly id: number;
  title: string;
  price: number;
  tags?: string[];                                  // optional: string[] | undefined
  author: { name: string; born?: number } | null;   // explicit "may be absent"
}

export type NewBook = Omit<Book, 'id'>;             // everything but the id: what a "create" form submits
export type BookPatch = Partial<Omit<Book, 'id'>>;  // any subset of the editable fields
export type BookSummary = Pick<Book, 'id' | 'title'>;
export type BooksById = Record<number, Book>;
----

An interface or type alias exists only at compile time: it disappears from the emitted JavaScript, so you cannot
check `x instanceof Book` or look a type up at runtime. Everything that must exist at runtime -- a validator, a
default, an injection token -- is a value, not a type.

=== Unions, narrowing and exhaustiveness

A **discriminated union** gives each variant a literal `status` field. After the check, the compiler knows which
variant it holds, and a `never` assignment turns a forgotten case into a compile error:

[source,typescript]
----
export type LoadState =
  | { status: 'idle' }
  | { status: 'loading' }
  | { status: 'loaded'; books: Book[] }
  | { status: 'failed'; error: string };

export function describe(state: LoadState): string {
  switch (state.status) {
    case 'idle': return 'Nothing yet';
    case 'loading': return 'Loading...';
    case 'loaded': return `${state.books.length} books`;   // narrowed: `books` exists only here
    case 'failed': return `Error: ${state.error}`;
    default: {
      const unreachable: never = state;                    // adding a variant without a case fails to compile
      return unreachable;
    }
  }
}
----

This shape works well for a component's view state: render with `@switch (state().status)`, and each `@case` branch
sees the right fields. For data of unknown shape -- parsed JSON, `postMessage`, `localStorage` -- type it as `unknown`
and narrow with a **type guard**, rather than casting with `as`:

[source,typescript]
----
export function isBook(value: unknown): value is Book {
  return typeof value === 'object' && value !== null && 'id' in value && 'title' in value && 'price' in value;
}

export function parseBooks(json: string): Book[] {
  const data: unknown = JSON.parse(json);
  return Array.isArray(data) ? data.filter(isBook) : [];
}
----

Given `+'[{"id":1,"title":"x","price":2},{"nope":1}]'+`, `parseBooks` returned one book: the guard rejected the second
element at runtime, which a type assertion would not have.

=== Optional chaining, nullish coalescing and `readonly`

`?.` short-circuits to `undefined` when the left side is `null` or `undefined`, and `??` supplies a default only for those
two values (unlike `||`, which also replaces `0` and the empty string):

[source,typescript]
----
export function authorName(b: Book): string {
  return b.author?.name ?? 'unknown author';
}
----

`+authorName({ ...book, author: null })+` returned `'unknown author'`. The same two operators work in templates, as the
xref:web/angular/templates-and-binding.adoc[Templates and Data Binding] page shows. `readonly` makes the
compiler reject reassignment: `book.id = 2` is an error for the interface above, and `readonly Book[]` rejects `push`.

=== Generics with constraints, `keyof`, `as const` and `satisfies`

[source,typescript]
----
export function indexBy<T, K extends keyof T>(items: readonly T[], key: K): Map<T[K], T> {
  return new Map(items.map((i) => [i[key], i] as const));
}

export function pluck<T, K extends keyof T>(items: readonly T[], key: K): T[K][] {
  return items.map((i) => i[key]);
}

indexBy(books, 'id');      // Map<number, Book>
pluck(books, 'title');     // string[]
pluck(books, 'cost');      // error: Argument of type '"cost"' is not assignable to parameter of type 'keyof Book'
----

`K extends keyof T` ties the second argument to the first: a typo in the key is a compile error, and the return type
follows the key. `as const` freezes a literal into its narrowest type, and `satisfies` checks a value against a type
*without widening it*:

[source,typescript]
----
export const SORTS = ['title', 'price'] as const;         // readonly ['title', 'price']
export type SortKey = (typeof SORTS)[number];              // 'title' | 'price'

export const routesConfig = {
  home: '/',
  book: (id: number) => `/books/${id}`,
} satisfies Record<string, string | ((id: number) => string)>;

routesConfig.book(3);   // '/books/3' -- still known to be a function; a wrong value type would be an error
----

`as const` plus `(typeof X)[number]` derives a union from one list, so the list and the type cannot drift apart.

=== Classes, parameter properties and private fields

[source,typescript]
----
export class PriceList {
  #cache = new Map<number, number>();                 // a runtime-private field
  constructor(private readonly books: readonly Book[]) {}   // parameter property: declares and assigns

  priceOf(id: number): number | undefined {
    const hit = this.#cache.get(id);
    if (hit !== undefined) return hit;
    const price = this.books.find((b) => b.id === id)?.price;
    if (price !== undefined) this.#cache.set(id, price);
    return price;
  }
}
----

`private` is a compile-time rule; `#name` is enforced by JavaScript at runtime. Services in Angular usually use
`private readonly dep = inject(Dep)` fields, which makes parameter properties rare in new code.

=== Typing signals, tokens, services and forms

[source,typescript]
----
export const PAGE_SIZE = new InjectionToken<number>('PAGE_SIZE', { providedIn: 'root', factory: () => 20 });

@Injectable({ providedIn: 'root' })
export class Library {
  private readonly http = inject(HttpClient);
  private readonly pageSize = inject(PAGE_SIZE);                       // number
  readonly books = signal<Book[]>([]);                                 // WritableSignal<Book[]>
  readonly selected = signal<Book | null>(null);                       // the union must be spelled out
  readonly titles = computed(() => this.books().map((b) => b.title));  // Signal<string[]>
  load() { return this.http.get<Book[]>('/api/books', { params: { limit: this.pageSize } }); }
}

export const form = new FormGroup({
  title: new FormControl('', { nonNullable: true }),
  price: new FormControl<number | null>(null),
});
export const value = form.getRawValue();    // { title: string; price: number | null }
----

`signal(null)` alone would be typed `WritableSignal<null>`, so write `signal<Book | null>(null)`; the same applies to
`new FormControl<number | null>(null)`. `HttpClient.get<Book[]>` does **not** validate the response -- the generic is a
promise to the compiler, which is where a runtime guard such as `isBook` earns its keep.

=== Compiler-checked expectations

`// @ts-expect-error` asserts that the next line **fails** to compile, and itself becomes an error if the line is
fixed -- a convenient way to pin type-level behavior in a test file. All four of these held in the project that
compiled this page's code:

[source,typescript]
----
// @ts-expect-error  a readonly property cannot be assigned
book.id = 2;
// @ts-expect-error  'cost' is not a key of Book
pluck([book], 'cost');
// @ts-expect-error  null is not assignable under strictNullChecks
const bad: string = authorName(book) === '' ? null : 'x';
// @ts-expect-error  the 'loaded' variant requires `books`
describe({ status: 'loaded' });
----

=== JavaScript features Angular code uses constantly

Arrow functions keep `this` lexical, which is why callbacks passed to `subscribe` and `map` inside a class can use
class members; `const` and `let` replace `var`; `import` / `export` define the module graph that `loadComponent` and the
bundler split on (`import('./x')` is the dynamic form, returning a promise); and destructuring plus the spread operator
(`+{ ...book, title }+`) express the "copy with a change" updates that signals and `OnPush` rely on. See
xref:programming-languages/javascript/types.adoc[JavaScript types] and
xref:programming-languages/javascript/classes.adoc[classes] for the language side of each.

== Decorators as Angular uses them

A *decorator* is a function prefixed with `@` that attaches metadata to a class (or, in legacy code, a class
member). Angular reads that metadata to know how to compile and wire the class. The class-level decorators are
still current: `@Component`, `@Injectable`, `@Directive`, `@Pipe`.

[source,typescript]
----
import { Injectable } from '@angular/core';

@Injectable({ providedIn: 'root' })
export class Logger {
  log(message: string): void {
    console.log(`[app] ${message}`);
  }
}
----

The legacy *property* decorators -- `@Input()`, `@Output()`, `@ViewChild()`, `@HostBinding()` -- still work but
are superseded by the signal-based functions `input()`, `output()`, `model()`, `viewChild()`, and `host`
metadata. New code uses the functions; see xref:web/angular/component-communication.adoc[component
communication]. The class decorators above are not going away.

== tsconfig essentials

A workspace from the current CLI is created with strict type-checking on, both for your TypeScript and for your
templates, so a fresh `tsconfig.json` does not even have to mention it: TypeScript 6 turns `strict` on by default, and
Angular's strict template checking is the default too. Older workspaces, and anyone who wants the intent written
down, spell the two settings out:

[source,json]
----
{
  "compilerOptions": {
    "strict": true
  },
  "angularCompilerOptions": {
    "strictTemplates": true
  }
}
----

* `strict` turns on the full strict family (`strictNullChecks`, `noImplicitAny`, and the rest) for your
  TypeScript.
* `strictTemplates` (under `angularCompilerOptions`) extends that checking into templates: binding
  expressions, `@for` loop variables, pipe argument types, and component input types are all verified at build
  time. It replaces the older, weaker `fullTemplateTypeCheck` flag.

Keep both on. What they catch is concrete. A file with an untyped parameter and a `null` assigned to a `string`, compiled
with the generated project's config, fails with:

[source,text]
----
src/app/bad.ts(1,19): error TS7006: Parameter 'x' implicitly has an 'any' type.
src/app/bad.ts(2,14): error TS2322: Type 'null' is not assignable to type 'string'.
----

and a template that passes a string to a `number` input and reads a property the class does not have fails the
`ng build` even though the template is "just HTML":

[source,typescript]
----
@Component({ selector: 'app-price', template: '{{ amount().toFixed(2) }}' })
export class Price { readonly amount = input.required<number>(); }

@Component({
  selector: 'app-bad',
  imports: [Price],
  template: `<app-price [amount]="'12'" /> {{ missing }}`,
})
export class Bad {}
----

[source,text]
----
✘ [ERROR] TS2322: Type 'string' is not assignable to type 'number'. [plugin angular-compiler]
✘ [ERROR] TS2339: Property 'missing' does not exist on type 'Bad'. [plugin angular-compiler]
----

The https://angular.dev/tools/language-service[Angular Language Service] surfaces the same
template diagnostics live in the editor. Two further options are worth enabling in a new project once the strict
baseline is clean: `noUncheckedIndexedAccess` (an index such as `items[0]` becomes `T | undefined`) and
`exactOptionalPropertyTypes` (an optional property cannot be set to `undefined` explicitly). The examples on this page
compile under both. For the compiler options in full see
https://www.typescriptlang.org/docs/[the TypeScript documentation].
