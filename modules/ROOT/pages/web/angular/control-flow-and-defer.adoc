= Control Flow and @defer
:description: The built-in @if, @for, and @switch template control flow, migrating from the structural directives, and @defer blocks for declarative lazy loading with placeholder, loading, and error states.
:keywords: Angular, control flow, if, for, switch, track, empty, ngIf migration, ngFor migration, control-flow schematic, defer, deferrable views, placeholder, loading, error, prefetch, triggers

include::partial$ai-disclaimer.adoc[]

Angular templates have keyword control-flow blocks -- `@if`, `@for`, `@switch` -- built into the compiler, plus
`@defer` for loading part of a template lazily. None of them needs an import.

== @if, @for, @switch

[source,html]
----
@if (user(); as u) {
  <p>Welcome, {{ u.name }}</p>
} @else if (loading()) {
  <app-spinner />
} @else {
  <a routerLink="/login">Sign in</a>
}

<ul>
  @for (item of items(); track item.id) {
    <li [class.first]="$first" [class.last]="$last">{{ $index + 1 }}. {{ item.label }}</li>
  } @empty {
    <li>No items ({{ $count }} total)</li>
  }
</ul>

@switch (status()) {
  @case ('active')  { <span class="ok">Active</span> }
  @case ('paused')  { <span class="warn">Paused</span> }
  @default          { <span>Unknown</span> }
}
----

Inside `@for`, the contextual variables are `$index`, `$first`, `$last`, `$even`, `$odd`, and `$count`. The
`track` expression is *required*: it tells Angular how to identify a row across renders so it can move DOM
nodes instead of destroying and recreating them. Use a stable unique key (`item.id`); use `track $index` only
for lists of primitives that never reorder. A bad `track` causes lost focus, restarted animations, and wasted
DOM work. See https://angular.dev/guide/templates/control-flow[control flow].

== How @for reconciles a list

`track` is a *key function*: Angular evaluates it for every item on every render and compares the keys with the previous
render to decide, per row, whether to keep, move, create, or destroy a view.

[mermaid]
....
flowchart TD
    A["New array arrives"] --> B["Compute track key for each item"]
    B --> C{"Key seen in the previous render?"}
    C -->|"yes"| D["Reuse the existing view and its DOM nodes, update the loop variable, move the view if its position changed"]
    C -->|"no"| E["Create a new embedded view and DOM nodes"]
    B --> F{"Previous key missing from the new array?"}
    F -->|"yes"| G["Destroy that view: listeners removed, inputs and local state lost"]
....

The key you choose therefore decides what survives a reorder. Reversing three rows rendered with `track r.id` moves the
existing `<li>` elements: the node that showed row `a` is now last, with its focus, scroll position, and any child
component state intact. The same reversal with `track $index` keeps the nodes where they are and only rewrites their
text, so a focused input, a running animation, or a child's internal state stays attached to the *position*, not the item.

[source,typescript]
----
@Component({
  selector: 'app-by-id',
  template: `<ul>@for (r of rows(); track r.id) { <li>{{ r.label }}</li> }</ul>`,
})
export class ById { readonly rows = signal<Row[]>([]); }

// rows set to [a, b, c], then reversed to [c, b, a]:
//   track r.id     -> after[0] === before[2]   (the same <li> element moved)
//   track $index   -> after[0] === before[0]   (the same <li> element, new text)
----

Rules of thumb: key by a stable identity from the data (a database id); use `track $index` only for read-only lists
of primitives; never key by a value that changes while the row is displayed (such as the label being edited), because
that destroys and recreates the row on every keystroke; and avoid `track` expressions that allocate (`+track {id: i.id}+`
creates a new object on each pass and defeats reuse). Keys must be unique within one array: two rows with the same key
cannot be told apart, so Angular cannot match them reliably across renders.

=== Everything else the control flow gives you

* `@if (expr; as alias)` stores the (narrowed) truthy value, so `@if (user(); as u)` makes `u` a non-null `User`
  inside the block. `@else if` chains work; there is no `@else` for `@for` -- use `@empty`.
* `@for (item of items(); track item.id; let i = $index, last = $last)` aliases a contextual variable to a shorter
  name, which helps in nested loops where `$index` would be ambiguous.
* `+@let total = items().length * 2;+` declares a read-only template variable that stays in sync with the signals it reads,
  visible in the rest of the current view and in nested blocks. It avoids repeating a long pipe or signal chain.
* `@switch` compares with strict equality, has no fall-through, and needs no `break`.
* A `@for` source can be an array or any other iterable, such as a `Set`; read a signal with `()` so the loop
  re-renders when it changes.

[source,html]
----
@let total = items().length * 2;
<p>{{ total }}</p>

@for (i of items(); track i; let idx = $index, last = $last, odd = $odd) {
  <span [class.last]="last" [class.odd]="odd">{{ idx }}:{{ i }}</span>
} @empty {
  <span>empty</span>
}
----

== Migrating from *ngIf / *ngFor / *ngSwitch

The old structural directives still work, but the schematic rewrites them automatically:

[source,bash]
----
ng generate @angular/core:control-flow
----

Before -- the structural directives:

[source,html]
----
<p *ngIf="user as u; else guest">
  Hi {{ u.name }}
</p>
<ng-template #guest><a>Sign in</a></ng-template>

<li *ngFor="let t of todos; trackBy: byId">
  {{ t.text }}
</li>

<div [ngSwitch]="status">
  <p *ngSwitchCase="'active'">Active</p>
  <p *ngSwitchDefault>Unknown</p>
</div>
----

After -- the built-in control flow:

[source,html]
----
@if (user(); as u) {
  <p>Hi {{ u.name }}</p>
} @else {
  <a>Sign in</a>
}

@for (t of todos(); track t.id) {
  <li>{{ t.text }}</li>
}

@switch (status()) {
  @case ('active') { <p>Active</p> }
  @default { <p>Unknown</p> }
}
----

The built-in blocks need no `CommonModule` import, give better type-narrowing, and make `track` mandatory
rather than optional. Run on a real project, the schematic also rewrote `trackBy: byId` as
`track byId($index, b)`, which preserves the behaviour but calls a function for every row: simplify it to `track b.id`
after the migration has run. The schematic also removed the `NgFor` / `NgIf` imports that became unused. See https://angular.dev/guide/templates/control-flow[control flow] and
https://angular.dev/reference/migrations/control-flow[the control-flow migration].

== @defer blocks

A `@defer` block does not render (and its dependencies are not bundled into the initial JavaScript) until a
trigger fires. Companion blocks cover the other states:

* `@placeholder` -- shown before the trigger; can declare a `minimum` display time.
* `@loading` -- shown while the deferred chunk downloads; supports `minimum` and `after`.
* `@error` -- shown if loading fails.

[source,html]
----
@defer (on viewport; prefetch on idle) {
  <app-comments [postId]="postId()" />
} @placeholder (minimum 500ms) {
  <p>Comments</p>
} @loading (after 100ms; minimum 1s) {
  <app-spinner />
} @error {
  <p>Could not load comments.</p>
}
----

Triggers: `on idle` (default), `on viewport`, `on interaction`, `on hover`, `on timer(2s)`, `on immediate`,
and `when <expression>`. `on viewport`, `interaction`, and `hover` may name a template reference variable to
watch a different element. `prefetch on <trigger>` downloads the chunk early without rendering it yet. See
https://angular.dev/guide/templates/defer[deferrable views].

== @defer in depth

`@defer` moves the dependencies used *only* inside the block into a separate JavaScript chunk that is fetched when a
trigger fires. Building a BookShelf page whose reviews panel sits in a block

[source,html]
----
<button #more type="button">Show reviews</button>
@defer (on interaction(more); prefetch on idle) {
  <app-reviews [bookId]="id()" />
} @placeholder {
  <p>Reviews load on demand.</p>
}
----

makes the build report the panel as a lazy chunk instead of part of `main`:

[source,text]
----
Initial chunk files | Names         |  Raw size
main-JGWTGGCN.js    | main          |  98.22 kB
...
Lazy chunk files    | Names         |  Raw size
chunk-KXJ2FROK.js   | reviews       | 430 bytes
----

Two conditions have to hold for a component to be split out. It must be *standalone* and listed in the host component's
`imports`; and it must be used only inside deferred blocks. A use outside any `@defer`, or a reference to the class from
other code in the same file (for example a `viewChild()` query for it), pulls it back into the main chunk. If the
compiler cannot split a dependency, the template still works -- it just does not shrink the bundle.

=== Triggers

[cols="1,3",options="header"]
|===
| Trigger | Fires when

| `on idle` (default) | the browser reports idle time (`requestIdleCallback`)
| `on immediate` | right after the surrounding view renders; useful with `prefetch` or for splitting only
| `on timer(2s)` | after the delay
| `on viewport` | the placeholder (or a referenced element) scrolls into view, via `IntersectionObserver`
| `on interaction` | a click or keydown on the placeholder or a referenced element
| `on hover` | mouse enters or an element receives focus
| `when expr` | the boolean expression becomes `true`; it is one-way, so the block stays rendered if the value later returns to `false`
|===

`on viewport`, `on interaction`, and `on hover` need something to watch: either a `@placeholder` with a single root
element, or an explicit template reference (`on interaction(more)`). Several triggers in one condition are alternatives;
the first to fire wins. `+prefetch on ...+` accepts the same triggers but only downloads the chunk, so the render is
instant when the main trigger finally fires. In server-rendered applications, `+hydrate on ...+` triggers keep a block as
inert server HTML until the trigger (see xref:web/angular/production-and-performance.adoc[Production and Performance]).

=== The block's states and what each guarantees

* `@placeholder (minimum 500ms)` renders first, and `minimum` keeps it on screen long enough to avoid a flash when the
  chunk is already cached.
* `@loading (after 100ms; minimum 1s)` is shown only if loading takes longer than `after`, and then at least `minimum`;
  both timers are there to prevent flicker.
* `@error` renders if the dynamic import fails, for example because the user went offline.
* A deferred block that reaches the main state never goes back, and its placeholder is destroyed.

=== Testing deferred blocks

The test harness lets you drive a block through its states without waiting for real triggers:

[source,typescript]
----
import { DeferBlockBehavior, DeferBlockState, TestBed } from '@angular/core/testing';

describe('reviews panel', () => {
  beforeEach(() =>
    TestBed.configureTestingModule({ deferBlockBehavior: DeferBlockBehavior.Manual }));

  it('walks placeholder, loading, complete', async () => {
    const fixture = TestBed.createComponent(BookPage);
    await fixture.whenStable();
    const [block] = await fixture.getDeferBlocks();
    const el = fixture.nativeElement as HTMLElement;

    expect(el.querySelector('#ph')).not.toBeNull();            // placeholder first
    await block.render(DeferBlockState.Loading);
    expect(el.querySelector('#ld')).not.toBeNull();
    await block.render(DeferBlockState.Complete);
    expect(el.querySelector('.reviews')?.textContent).toBe('Reviews for b1');
  });

  it('renders the error state', async () => {
    const fixture = TestBed.createComponent(BookPage);
    await fixture.whenStable();
    const [block] = await fixture.getDeferBlocks();
    await block.render(DeferBlockState.Error);
    expect((fixture.nativeElement as HTMLElement).querySelector('#er')).not.toBeNull();
  });
});
----

`DeferBlockBehavior.Playthrough` (the default) instead lets triggers fire as they would in the browser, which suits
end-to-end style component tests.
