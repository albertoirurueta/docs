Angular ships https://rxjs.dev/[RxJS] and uses observables for the HTTP client, router events, reactive form
value streams, and `@Output` events. This page covers the parts you need day to day; for signals, and when to
prefer them, see xref:web/angular/signals.adoc[Signals].

== From callbacks to observables

A callback delivers one result at some later point; a `Promise` does the same with chaining and a single
resolution. An *observable* generalises both: it is a *lazy*, *cancellable* producer of *zero or more* values
over time.

[source,typescript]
----
// callback: one result, no composition
getUser(id, (err, user) => { /* ... */ });

// promise: one result, then-able, not cancellable
const user = await getUser(id);

// observable: many values, lazy (nothing runs until subscribe), cancellable
const sub = interval(1000).subscribe((n) => console.log(n));
sub.unsubscribe(); // stops the producer
----

* *Lazy* -- the function passed to `+new Observable(...)+` (or wrapped by `of`, `from`, `fromEvent`) runs only
  when something subscribes, and re-runs for every subscriber.
* *Cancellable* -- `unsubscribe()` tears down timers, listeners, and in-flight HTTP requests.
* *Multi-value* -- a stream can emit repeatedly (key presses, WebSocket messages, form changes) before it
  completes, or never complete at all.

For the underlying JavaScript concurrency model (the event loop, microtasks, `async`/`await`) see
xref:programming-languages/javascript/async-javascript.adoc[Asynchronous JavaScript]. RxJS concepts are introduced at
https://rxjs.dev/guide/overview[the RxJS overview].

== Creating observables

[source,typescript]
----
import { of, from, fromEvent, interval, timer } from 'rxjs';

of(1, 2, 3);                       // emit each argument, then complete
from(fetch('/api/books'));         // from a Promise (or array, or iterable)
from([10, 20, 30]);
fromEvent(input, 'input');         // from a DOM event target
interval(1000);                    // 0, 1, 2, ... every second (never completes)
timer(2000);                       // emit 0 once after 2s
timer(2000, 1000);                 // first after 2s, then every 1s
----

A `Subject` is both an observable and an observer: you call `next()` on it to push values to every current
subscriber. A `BehaviorSubject` additionally stores the latest value and replays it to new subscribers, which
makes it a common building block for small shared state.

[source,typescript]
----
import { Subject, BehaviorSubject } from 'rxjs';

const clicks = new Subject<void>();
clicks.subscribe(() => console.log('clicked'));
clicks.next(); // -> "clicked"

@Injectable({ providedIn: 'root' })
export class ThemeService {
  private readonly theme$ = new BehaviorSubject<'light' | 'dark'>('light');
  readonly current$ = this.theme$.asObservable(); // expose read-only
  set(next: 'light' | 'dark') { this.theme$.next(next); }
}
----

== Operators

Operators are pure functions passed to `pipe()` that transform a stream into a new stream.

[cols="1,3"]
|===
| Operator | Purpose

| `map`, `filter`, `tap` | transform each value, drop values, run a side effect without changing the value
| `switchMap` | map to an inner observable, *cancelling* the previous inner one (searches, autocompletes)
| `mergeMap` | map to an inner observable, run them *concurrently* (independent writes)
| `concatMap` | map to an inner observable, run them *one after another* (ordered writes)
| `debounceTime` | wait for a quiet gap before emitting the latest value
| `distinctUntilChanged` | suppress consecutive duplicates
| `combineLatest` | combine the latest value of several streams whenever any of them emits
| `catchError` | handle an error, returning a fallback stream (`+of(...)+`, `EMPTY`) or re-throwing
| `retry` | re-subscribe on error, up to N times or per a delay strategy
| `takeUntil` | complete this stream when a *notifier* stream emits
|===

A typeahead search combines `debounceTime`, `distinctUntilChanged`, and `switchMap`:

[source,typescript]
----
import { Component, inject } from '@angular/core';
import { FormControl, ReactiveFormsModule } from '@angular/forms';
import { HttpClient } from '@angular/common/http';
import { debounceTime, distinctUntilChanged, switchMap, catchError } from 'rxjs/operators';
import { of } from 'rxjs';
import { toSignal } from '@angular/core/rxjs-interop';

@Component({
  selector: 'app-book-search',
  imports: [ReactiveFormsModule],
  template: `
    <input [formControl]="query" placeholder="Search books" />
    @for (book of results(); track book.id) { <li>{{ book.title }}</li> }
  `,
})
export class BookSearch {
  private readonly http = inject(HttpClient);
  readonly query = new FormControl('', { nonNullable: true });

  readonly results = toSignal(
    this.query.valueChanges.pipe(
      debounceTime(300),               // ignore rapid keystrokes
      distinctUntilChanged(),          // skip if the text did not actually change
      switchMap((q) =>                 // cancel the previous request
        this.http.get<Book[]>('/api/books', { params: { q } }).pipe(
          catchError(() => of([])),    // a failed search yields no results, not a broken stream
        ),
      ),
    ),
    { initialValue: [] as Book[] },
  );
}
----

Operators are documented individually at https://rxjs.dev/guide/operators[the RxJS operators guide].

== Choosing a flattening operator

`switchMap`, `mergeMap`, `concatMap`, and `exhaustMap` all map each outer value to an inner observable and flatten the
results; they differ only in what they do when a new outer value arrives while an inner observable is still running.
The catalog's "save" button makes the difference visible. Three clicks arrive at 0 ms, 10 ms, and 20 ms, and each save
takes 25 ms. Run on RxJS's virtual-time `TestScheduler`, the four operators emit:

[source,typescript]
----
import { TestScheduler } from 'rxjs/testing';
import { switchMap, mergeMap, concatMap, exhaustMap } from 'rxjs/operators';

const operators = { switchMap, mergeMap, concatMap, exhaustMap };

for (const [name, op] of Object.entries(operators)) {
  const seen: string[] = [];
  const scheduler = new TestScheduler(() => {});           // virtual time: no real waiting

  scheduler.run(({ cold, hot, flush }) => {
    const clicks = hot('a 9ms b 9ms c', { a: 'A', b: 'B', c: 'C' });   // clicks at 0, 10 and 20 ms
    const save = (book: string) => cold('25ms (x|)', { x: book });      // a save takes 25 ms

    clicks.pipe(op((book: string) => save(book))).subscribe((v) => seen.push(`${v}@${scheduler.now()}`));
    flush();
  });
  console.log(name.padEnd(10), seen.join(' '));
}
----

[cols="1,2,3,3",options="header"]
|===
| Operator | Emissions (value@ms) | Behaviour | Typical use

| `switchMap` | `C@45` | cancels the running save as each click arrives; only the last result survives | typeahead, route-parameter driven loads, "latest wins"
| `mergeMap` | `A@25 B@35 C@45` | starts every save immediately, results in completion order | independent writes that may overlap
| `concatMap` | `A@25 B@50 C@75` | queues the saves, one after another | ordered writes, where order matters
| `exhaustMap` | `A@25` | ignores clicks while a save is running | submit and login buttons, preventing double submission
|===

[mermaid]
....
flowchart LR
    A["New outer value<br/>while an inner one is running"] --> B{"Which operator?"}
    B -- "switchMap" --> C["Unsubscribe the old inner,<br/>start the new one"]
    B -- "mergeMap" --> D["Start the new one too,<br/>run both"]
    B -- "concatMap" --> E["Queue the new one<br/>until the old one completes"]
    B -- "exhaustMap" --> F["Drop the new one"]
....

The cancellation in `switchMap` is real: unsubscribing from an `HttpClient` observable aborts the underlying request,
which is why the typeahead above cannot display results for a query that was already superseded.

== Cold, hot, and sharing

An observable made by `HttpClient` or `+new Observable(...)+` is **cold**: every subscriber starts its own execution. A
subject is **hot**: it multicasts values to whoever is subscribed right now. When two parts of a template subscribe to
the same cold observable, the work is done twice:

[source,typescript]
----
import { Observable } from 'rxjs';
import { shareReplay } from 'rxjs/operators';

let requests = 0;
const books$ = new Observable<{ id: number }>((subscriber) => {
  requests++;                                   // stands in for an HTTP request
  subscriber.next({ id: requests });
  subscriber.complete();
});

books$.subscribe(); books$.subscribe();
console.log(requests);                          // 2 -- cold: one execution per subscriber

requests = 0;
const shared$ = books$.pipe(shareReplay({ bufferSize: 1, refCount: true }));
shared$.subscribe(); shared$.subscribe();
shared$.subscribe();                            // a late subscriber gets the replayed value
console.log(requests);                          // 1
----

`+shareReplay({ bufferSize: 1, refCount: true })+` runs the source once, replays the latest value to late subscribers,
and with `refCount: true` tears the source down when the last subscriber leaves. Prefer the object form: the bare
`shareReplay(1)` keeps the source subscription alive forever. In a service, the usual home for a shared request is
`shareReplay` on a property; in a component, `toSignal()` already subscribes only once.

The three subject flavors differ in what a late subscriber sees after `next('1')`, `next('2')`, `next('3')`:

[cols="1,2",options="header"]
|===
| Type | A subscriber that arrives after the three values receives

| `Subject` | nothing -- only values emitted after it subscribes
| `BehaviorSubject('init')` | `3` -- the current value, immediately (it must be created with an initial value)
| `ReplaySubject(2)` | `2` and `3` -- the last two values
|===

== Errors: where `catchError` goes

An error terminates an observable. Where you catch it decides whether the *outer* stream survives. In the typeahead,
`catchError` sits **inside** `switchMap`, so a failed request becomes an empty result and the search box keeps working;
placed after `switchMap`, the first failure would complete the whole search pipeline. Feeding the values `'a'`,
`'bad'`, `'c'` through both arrangements produced:

[cols="1,2",options="header"]
|===
| Placement | Emitted

| inside: `+switchMap(v => fetch(v).pipe(catchError(() => of('fallback'))))+` | `result:a`, `fallback`, `result:c`
| outside: `+switchMap(v => fetch(v)).pipe(catchError(() => of('fallback')))+` | `result:a`, `fallback`, then complete -- `'c'` is never processed
|===

For transient failures, `retry` accepts a count and a delay function that returns the notifier observable, which gives
exponential backoff in a few lines. A source that fails twice and then succeeds, with a delay of `+2 ** n * 100+` ms before
retry number `n`, ran like this on the virtual clock:

[source,typescript]
----
import { retry, timer } from 'rxjs';

flaky$.pipe(
  retry({
    count: 3,
    delay: (error, retryCount) => timer(2 ** retryCount * 100),   // 200 ms, 400 ms, 800 ms
  }),
).subscribe((v) => console.log(v));
----

[source,text]
----
retry#1 after "503 #1" at 0ms
retry#2 after "503 #2" at 200ms
ok after 3 at 600ms
----

Retrying a non-idempotent request (a `POST` that creates something) can duplicate the effect; retry reads, not writes.
The HTTP-specific version of this pattern is on xref:web/angular/http-client.adoc[HTTP client].

== Combining streams

`combineLatest([a$, b$])` emits an array each time any input emits, once every input has emitted at least once;
`+forkJoin({ ... })+` waits for every input to **complete** and emits their last values once. Use `forkJoin` for
"load these three things, then continue" (HTTP calls complete), and `combineLatest` for state that keeps changing
(a filter and a sort order):

[source,typescript]
----
import { combineLatest, forkJoin, of, timer, Subject } from 'rxjs';
import { map } from 'rxjs/operators';

forkJoin({ a: of(1), b: timer(5).pipe(map(() => 2)) })
  .subscribe((v) => console.log(v));                 // { a: 1, b: 2 }, then complete

const x = new Subject<number>(); const y = new Subject<string>();
combineLatest([x, y]).subscribe((v) => console.log(v));
x.next(1); x.next(2);                                // nothing yet: y has not emitted
y.next('a');                                         // [2, 'a']
x.next(3);                                           // [3, 'a']
----

== Teardown flows upstream

Unsubscribing at the end of a pipeline tears down every stage in turn: timers stop, listeners detach, and in-flight
requests abort. In a virtual-time run, a pipeline of `interval(10)`, `take(100)`, and `switchMap` into a 50 ms inner
observable was unsubscribed at 35 ms; a `+tap({ unsubscribe: ... })+` placed on the source reported
`source torn down at 35`, the same instant. This is also why forgetting to unsubscribe is a leak and not just
untidiness: the whole chain keeps running.

[mermaid]
....
sequenceDiagram
    participant C as Component
    participant P as pipe(...) chain
    participant S as Source (interval / HTTP)
    C->>P: subscribe()
    P->>S: subscribe upstream
    S-->>P: next(value)
    P-->>C: next(transformed)
    C->>P: unsubscribe() (or view destroyed)
    P->>S: unsubscribe upstream
    Note over S: timer cleared, request aborted
....

== Subscribing and unsubscribing

Every manual `subscribe()` that does not complete on its own must be torn down, or it leaks (and keeps
running after the component is destroyed). There are three good options, roughly in order of preference.

*1. The `async` pipe* subscribes in the template and unsubscribes automatically when the view is destroyed. It
also marks the component for check on each emission, so it works with `OnPush` and zoneless change detection.

[source,typescript]
----
@Component({
  selector: 'app-books',
  imports: [AsyncPipe],
  template: `
    @if (books$ | async; as books) {
      @for (b of books; track b.id) { <li>{{ b.title }}</li> }
    }
  `,
})
export class Books {
  readonly books$ = inject(BookService).list();
}
----

See https://angular.dev/api/common/AsyncPipe[`AsyncPipe`].

*2. `takeUntilDestroyed()`* completes the stream when the current injection context's `DestroyRef` fires.
Called in a field initializer or constructor it needs no argument; elsewhere pass a captured `DestroyRef`.

[source,typescript]
----
import { Component, inject } from '@angular/core';
import { takeUntilDestroyed } from '@angular/core/rxjs-interop';

@Component({ selector: 'app-ticker', template: '{{ tick }}' })
export class Ticker {
  tick = 0;
  constructor() {
    interval(1000)
      .pipe(takeUntilDestroyed())
      .subscribe(() => (this.tick += 1));
  }
}
----

*3. A manual `Subscription`* collected and unsubscribed in `ngOnDestroy` -- verbose, but explicit:

[source,typescript]
----
import { Subscription } from 'rxjs';

export class Ticker implements OnDestroy {
  private readonly sub = new Subscription();
  ngOnInit() {
    this.sub.add(interval(1000).subscribe(/* ... */));
  }
  ngOnDestroy() {
    this.sub.unsubscribe();
  }
}
----

=== Bridging to signals

`@angular/core/rxjs-interop` converts between the two reactive primitives. `toSignal()` subscribes to an
observable and exposes its latest value as a read-only signal (unsubscribing on destroy); `toObservable()`
emits whenever a signal changes.

[source,typescript]
----
import { toSignal, toObservable } from '@angular/core/rxjs-interop';

readonly user = toSignal(this.userService.current$, { initialValue: null });
readonly userId = signal(1);
readonly user$ = toObservable(this.userId).pipe(
  switchMap((id) => this.http.get<User>(`/api/users/${id}`)),
);
----

See https://angular.dev/ecosystem/rxjs-interop[the RxJS interop guide].

== A pipeline at a glance

[mermaid]
....
flowchart LR
    A["source$<br/>(valueChanges / fromEvent)"] --> B["debounceTime(300)"]
    B --> C["distinctUntilChanged()"]
    C --> D["switchMap(q => http.get(...))<br/>cancels the previous request"]
    D --> E["catchError(() => of([]))"]
    E --> F["subscribe() / async pipe / toSignal()"]
....

Each operator returns a new observable; nothing runs until step F subscribes, and `unsubscribe()` (or view
destruction) propagates back up the chain to cancel timers and the in-flight request.
