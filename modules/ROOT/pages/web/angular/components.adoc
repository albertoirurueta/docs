= Components
:description: The @Component decorator and its metadata, selectors and the render tree, view encapsulation and component styles, host elements, and rendering components programmatically.
:keywords: Angular, components, Component decorator, selector, templateUrl, styleUrl, standalone, imports, host, view encapsulation, Emulated, ShadowDom, host bindings, hostDirectives, NgComponentOutlet, ViewContainerRef

include::partial$ai-disclaimer.adoc[]

A component is a TypeScript class with an `@Component` decorator that pairs a template with the logic and state
that drive it. Components are the only building block you need to compose an Angular UI; every screen is a tree
of them.

== @Component metadata

The decorator's configuration object describes how Angular compiles and renders the class. The common fields:

* `selector` -- the CSS selector that marks where this component mounts in a template.
* `template` (inline) or `templateUrl` (a separate `.html` file).
* `styles` (inline) or `styleUrl` / `styleUrls` (separate stylesheet files).
* `standalone` -- defaults to `true`; a standalone component manages its own dependencies and does not belong
  to an `NgModule`.
* `imports` -- the other components, directives, and pipes this template uses.
* `host` -- bindings and listeners applied to the component's own host element.
* `changeDetection` -- `OnPush` (the default) or `Eager`; see <<_change_detection_and_the_component>>.
* `encapsulation` -- how component styles are scoped; see <<_styling_and_view_encapsulation>>.
* `providers` / `viewProviders` -- services scoped to this component and its subtree; see
  xref:web/angular/dependency-injection.adoc[Dependency Injection].
* `hostDirectives` -- directives applied to the host element; see <<_host_elements>>.

[source,typescript]
----
import { Component, signal } from '@angular/core';

@Component({
  selector: 'app-counter',
  imports: [],
  template: `
    <p>Count: {{ count() }}</p>
    <button (click)="increment()">+1</button>
  `,
  styles: `
    :host { display: inline-flex; gap: .5rem; }
    button { font: inherit; }
  `,
})
export class Counter {
  readonly count = signal(0);

  increment(): void {
    this.count.update((n) => n + 1);
  }
}
----

See https://angular.dev/guide/components[Components] for the full metadata reference.

== What Angular does with a component

The `@Component` decorator is metadata for the compiler, not runtime configuration. At build time the template is
compiled into a function with two modes, and the class is registered with a component definition that points at it:

[mermaid]
....
flowchart LR
    SRC["Class + @Component metadata + template"] --> AOT["Template compiler (ng build)"]
    AOT --> DEF["Component definition: template function, styles, inputs, outputs"]
    DEF --> CREATE["Create mode: run once per instance, builds DOM nodes and listeners"]
    CREATE --> UPDATE["Update mode: run on each change detection pass, refreshes changed bindings"]
    UPDATE -->|"a signal, input or event marks the view dirty"| UPDATE
    UPDATE --> DESTROY["Destroy: listeners removed, DestroyRef callbacks run"]
....

Creation runs once for each instance of the component and builds the static DOM. Update runs every time change
detection visits the component, compares each binding with its previous value, and touches the DOM only for those that
changed. That split is why a template expression must be cheap and free of side effects: Angular evaluates it
repeatedly and has no control over how often.

== Change detection and the component

Angular decides *whether* to run a component's update pass from its `changeDetection` setting. In the current release
every component is `OnPush` unless it says otherwise: it is refreshed only when

* a signal read by its template changes,
* one of its inputs receives a new value,
* an event listener declared in its own template fires, or
* code calls `markForCheck()` on its `ChangeDetectorRef`.

`ChangeDetectionStrategy.Eager` (the strategy that was called `Default`) checks the component on every pass that
reaches it. The difference is visible in a component that mutates a plain field:

[source,typescript]
----
import { ChangeDetectionStrategy, Component, signal } from '@angular/core';

@Component({
  selector: 'app-plain',
  // changeDetection: ChangeDetectionStrategy.Eager  // opt out of the OnPush default
  template: `<button (click)="bump()">{{ plain }}</button> <span>{{ sig() }}</span>`,
})
export class Plain {
  plain = 0;                      // an ordinary field: invisible to Angular
  readonly sig = signal(0);       // a signal: read in the template, so a write schedules a refresh

  bump(): void {
    this.plain++;                 // inside a template listener: the view is marked dirty, button shows 1
  }
}
----

Assigning `plain = 99` from a timer or a promise callback does not update the button, because nothing told Angular the
view is dirty; the stale value appears only when another trigger (here, `sig.set(1)`) refreshes the view. Keeping state
in signals removes the problem and is the reason signals are the default style throughout this section. See
xref:web/angular/lifecycle-and-change-detection.adoc[Lifecycle and Change Detection] for the full model.

== The component class and the render tree

Angular instantiates one object of the component class per place the selector appears. That instance owns the
template's state; the template reads it through bindings and calls its methods from event handlers. Nesting
components -- by putting one component's selector in another's template -- builds a *render tree* rooted at the
component passed to `bootstrapApplication`.

[mermaid]
....
flowchart TD
    App --> Header
    App --> ProductList
    ProductList --> ProductCard1["ProductCard"]
    ProductList --> ProductCard2["ProductCard"]
    ProductList --> ProductCard3["ProductCard"]
....

*Selectors* come in three forms:

[source,typescript]
----
@Component({ selector: 'app-card', /* ... */ })          // element:   <app-card>
@Component({ selector: '[appHighlight]', /* ... */ })     // attribute: <div appHighlight>
@Component({ selector: '.app-toolbar', /* ... */ })       // class:     <div class="app-toolbar">
----

Element selectors are the norm for components; attribute selectors are typical for directives. See
https://angular.dev/guide/components/selectors[component selectors].

== Styling and view encapsulation

Styles declared in `styles` / `styleUrl` are *scoped to the component* by default. Angular's
`ViewEncapsulation` setting controls how:

* `Emulated` (default) -- Angular rewrites selectors and adds per-component attributes so the styles do not
  leak out or in. No native Shadow DOM.
* `None` -- styles are added to the document `<head>` as-is and apply globally.
* `ShadowDom` -- the component renders into a real shadow root; browser-native style isolation.

[source,typescript]
----
import { Component, ViewEncapsulation } from '@angular/core';

@Component({
  selector: 'app-badge',
  template: `<span class="dot"></span><ng-content />`,
  styleUrl: './badge.scss',
  encapsulation: ViewEncapsulation.Emulated,
})
export class Badge {}
----

[source,scss]
----
:host {
  display: inline-block;
}

:host(.danger) .dot {          // host element that also has the .danger class
  background: red;
}

:host-context(.dark-theme) {   // an ancestor anywhere has .dark-theme
  color: #eee;
}

::ng-deep .legacy-child {       // deprecated: pierces into child components
  margin: 0;
}
----

`:host` targets the component's own element, `:host-context()` styles it based on an ancestor, and `::ng-deep`
forces a style through to descendants -- it is *deprecated*; prefer exposing a CSS custom property or moving the
rule to `src/styles.css`, the global stylesheet listed in `angular.json`. See
https://angular.dev/guide/components/styling[styling components].

== Host elements

Every component instance has a *host element* -- the DOM element its selector matched. Bind to it and listen on
it through `host` metadata, and compose behaviour onto it with `hostDirectives`:

[source,typescript]
----
import { Component } from '@angular/core';
import { Tooltip } from './tooltip';

@Component({
  selector: 'app-icon-button',
  template: `<ng-content />`,
  host: {
    'role': 'button',
    'tabindex': '0',
    '[class.is-active]': 'active()',
    '(keydown.enter)': 'activate()',
  },
  hostDirectives: [Tooltip],
})
export class IconButton {
  // active(), activate() defined here
}
----

`hostDirectives` applies `Tooltip` to every `<app-icon-button>` without the template opting in. See
https://angular.dev/guide/components/host-elements[host elements].

== Deep dive: a presentational component for BookShelf

BookShelf (introduced in xref:web/angular/getting-started.adoc[Getting Started]) renders each book in the list through
a small *presentational* component: it receives data through inputs, reports user intent through outputs, and owns
no state of its own. The list component (the *container*) injects the store and decides what happens.

[source,typescript]
----
import { Component, computed, input, output } from '@angular/core';
import { CurrencyPipe } from '@angular/common';
import { Book } from './book';

@Component({
  selector: 'app-book-card',
  imports: [CurrencyPipe],
  template: `
    <article>
      <h3>{{ book().title }}</h3>
      <p class="meta">{{ book().author }} - {{ book().price | currency: 'EUR' }}</p>
      <p class="stars" [attr.aria-label]="book().rating + ' out of 5'">{{ stars() }}</p>
      <button type="button" (click)="selected.emit(book())">Select</button>
    </article>
  `,
  styles: `
    :host { display: block; }
    article { border: 1px solid var(--card-border, #ccc); padding: .75rem; }
    .stars { color: goldenrod; }
  `,
})
export class BookCard {
  readonly book = input.required<Book>();
  readonly selected = output<Book>();
  protected readonly stars = computed(() => '\u2605'.repeat(this.book().rating));
}
----

Because `BookCard` is `OnPush` and reads only the `book` input, Angular skips it entirely while the parent hands it the
same `Book` object, however often the parent re-renders. Replace the object (an immutable update such as
`+{ ...book, rating: 5 }+`) and the card refreshes; mutate the same object in place and it does not.

=== What encapsulation does to the DOM

The styles above stay inside the card. With the default `Emulated` mode Angular adds a unique attribute to the host
element and to every element in the component's own template, and rewrites each selector to require it. Rendering a
component with `+.dot { color: red; }+` and `+:host { display: inline-block; }+` produces:

[source,html]
----
<!-- host element -->
<app-badge _nghost-a-c3143507194 ...>
  <span class="dot" _ngcontent-a-c3143507194></span>
</app-badge>
----

[source,css]
----
.dot[_ngcontent-a-c3143507194] { color: red; }
[_nghost-a-c3143507194]        { display: inline-block; }
----

The attribute suffix is generated per component (yours will differ). Projected content carries its *owner's*
attribute, not the card's, which is why a card's styles do not reach `<ng-content>` children. `ViewEncapsulation.None`
skips the rewrite and inserts the stylesheet verbatim, so its selectors are global. `ViewEncapsulation.ShadowDom` attaches
a real shadow root to the host and places the `<style>` element inside it, so even global stylesheets cannot reach in.

=== Choosing the render strategy

[cols="1,2,2",options="header"]
|===
| Need | Use | Why

| A fixed set of children known at compile time
| the child's selector in the template
| the compiler resolves it, tree-shakes it, and checks inputs

| One of several known components, picked at runtime
| `@switch` over a value, or `NgComponentOutlet`
| declarative, no injector plumbing

| Anything created in response to code (a dialog, a toast, a dropped widget)
| `ViewContainerRef.createComponent` or `createComponent()`
| you control placement and lifetime and must call `destroy()`
|===

== Rendering components programmatically

When the component to show is only known at runtime, render it from code rather than from a static selector.

`NgComponentOutlet` does it declaratively in a template:

[source,html]
----
<ng-container *ngComponentOutlet="currentWidget()" />
----

`ViewContainerRef.createComponent` does it imperatively:

[source,typescript]
----
import { Component, ViewContainerRef, inject } from '@angular/core';
import { ChartWidget } from './chart-widget';

@Component({ selector: 'app-dashboard', template: `` })
export class Dashboard {
  private readonly vcr = inject(ViewContainerRef);

  show(): void {
    const ref = this.vcr.createComponent(ChartWidget);
    ref.setInput('title', 'Sales');
    // ref.destroy() to remove it
  }
}
----

`NgComponentOutlet` passes inputs with its `inputs` field, and `createComponent` accepts *bindings* that stay reactive:
`inputBinding()` ties an input to a signal or function, `outputBinding()` subscribes to an output, and
`twoWayBinding()` connects a `model()` to a writable signal. Unlike `ref.setInput()`, a binding keeps updating the child
whenever the signal it reads changes.

[source,typescript]
----
import { Component, ViewContainerRef, inject, input, output, signal,
  inputBinding, outputBinding } from '@angular/core';

@Component({
  selector: 'app-chart-widget',
  template: `<h3>{{ title() }}</h3><button (click)="picked.emit(42)">pick</button>`,
})
export class ChartWidget {
  readonly title = input.required<string>();
  readonly picked = output<number>();
}

@Component({ selector: 'app-dashboard', template: `` })
export class Dashboard {
  private readonly vcr = inject(ViewContainerRef);
  private readonly title = signal('Sales');
  lastPick = 0;

  show(): void {
    const ref = this.vcr.createComponent(ChartWidget, {
      bindings: [
        inputBinding('title', this.title),                       // follows the signal
        outputBinding<number>('picked', (n) => (this.lastPick = n)),
      ],
    });
    // ref.destroy() removes it and runs its cleanup
  }
}
----

Calling `+this.title.set('Revenue')+` later re-renders the widget's heading with no further code. The same works
declaratively: `+<ng-container *ngComponentOutlet="widget(); inputs: { title: 'Sales' }" />+` swaps the component when
`widget()` changes and updates its inputs.

See https://angular.dev/guide/components/programmatic-rendering[programmatic rendering].
