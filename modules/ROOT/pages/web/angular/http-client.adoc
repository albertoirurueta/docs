= HTTP Client
:description: Configuring Angular's HttpClient with provideHttpClient, making typed requests with parameters and headers, handling errors and retrying with backoff, functional interceptors, httpResource, and testing HTTP code.
:keywords: Angular HttpClient, provideHttpClient, withXhr, withInterceptors, HttpParams, HttpHeaders, typed response, observe response, observe events, responseType, HttpErrorResponse, catchError, retry backoff, HttpInterceptorFn, functional interceptor, httpResource, provideHttpClientTesting, HttpTestingController, CORS

include::partial$ai-disclaimer.adoc[]

`HttpClient` is Angular's typed wrapper over the browser's networking APIs. It returns observables, integrates
with dependency injection, and supports a chain of interceptors. For the platform primitive it builds on, see
xref:programming-languages/javascript/browser-networking.adoc[Browser networking].

== Setup and requests

Register `HttpClient` once in the application config. In the current release the `fetch` API is the default backend,
so no feature is needed for it; `+withInterceptors([...])+` installs the functional interceptor chain.

[source,typescript]
----
// app.config.ts
import { ApplicationConfig } from '@angular/core';
import { provideHttpClient, withInterceptors } from '@angular/common/http';
import { authInterceptor, loggingInterceptor } from './http/interceptors';

export const appConfig: ApplicationConfig = {
  providers: [
    provideHttpClient(
      withInterceptors([authInterceptor, loggingInterceptor]),
    ),
  ],
};
----

The features you can pass to `provideHttpClient()`:

[cols="1,3",options="header"]
|===
| Feature | Effect

| `+withInterceptors([...])+` | installs functional interceptors, run in the listed order
| `withInterceptorsFromDi()` | keeps class-based `HttpInterceptor` classes registered through the `HTTP_INTERCEPTORS` token (migration aid)
| `withXhr()` | uses `XMLHttpRequest` instead of `fetch`; needed only for *upload* progress events, which `fetch` cannot report
| `+withXsrfConfiguration({ cookieName, headerName })+` / `withNoXsrfProtection()` | customises or disables the built-in XSRF header for mutating same-origin requests
| `withJsonpSupport()` | enables `HttpClient.jsonp()`
| `withRequestsMadeViaParent()` | forwards requests to the parent injector's `HttpClient`, so a lazy route can add interceptors on top of the root chain
| `withHttpTransferCache()` | reuses responses fetched during server rendering instead of repeating them in the browser
|===

The older `withFetch()` is deprecated: it is now a no-op because `fetch` is the default.

Inject `HttpClient` and call the verb methods. Each returns a cold `Observable` -- the request fires on
`subscribe()` (the `async` pipe, `toSignal`, or an explicit call) and is cancelled on `unsubscribe()`.

[source,typescript]
----
import { Injectable, inject } from '@angular/core';
import { HttpClient, HttpParams, HttpHeaders } from '@angular/common/http';

@Injectable({ providedIn: 'root' })
export class BookApi {
  private readonly http = inject(HttpClient);

  list(q: string, page: number) {
    const params = new HttpParams().set('q', q).set('page', page);
    return this.http.get<Book[]>('/api/books', { params }); // Observable<Book[]>
  }

  get(id: string) {
    return this.http.get<Book>(`/api/books/${id}`);
  }

  create(book: NewBook) {
    return this.http.post<Book>('/api/books', book);
  }

  replace(id: string, book: Book) {
    return this.http.put<Book>(`/api/books/${id}`, book);
  }

  patch(id: string, changes: Partial<Book>) {
    const headers = new HttpHeaders({ 'X-Reason': 'inline-edit' });
    return this.http.patch<Book>(`/api/books/${id}`, changes, { headers });
  }

  remove(id: string) {
    return this.http.delete<void>(`/api/books/${id}`);
  }
}
----

`HttpParams` and `HttpHeaders` are *immutable* -- every `set`/`append` returns a new instance, so chain them.
The type argument on `get<T>` / `post<T>` types the response body; Angular does not validate it at runtime.

By default the observable emits the parsed body. Change what you observe, and how the body is parsed, with the
options object:

[source,typescript]
----
// full HttpResponse<T> (status, headers, body)
this.http.get<Book>('/api/books/1', { observe: 'response' });

// the stream of HttpEvent<T> values; download progress works with fetch, upload progress needs withXhr()
this.http.post('/api/upload', form, { observe: 'events', reportProgress: true });

// non-JSON payloads
this.http.get('/report.csv', { responseType: 'text' });
this.http.get('/logo.png', { responseType: 'blob' });
----

See https://angular.dev/guide/http[HTTP client], https://angular.dev/guide/http/setup[Setting up HttpClient],
and https://angular.dev/guide/http/making-requests[Making requests].

== Error handling

A failed request produces an `HttpErrorResponse` in the observable's error channel -- either a network/CORS
failure (`error` is a `ProgressEvent`, `status` is `0`) or an HTTP error status (`status` is `4xx`/`5xx`,
`error` is the parsed error body). Handle it with `catchError`.

[source,typescript]
----
import { catchError, retry, timer } from 'rxjs';
import { throwError } from 'rxjs';
import { HttpErrorResponse } from '@angular/common/http';

list() {
  return this.http.get<Book[]>('/api/books').pipe(
    retry({ count: 3, delay: (_err, i) => timer(500 * 2 ** i) }), // backoff (i is 1-based): 1s, 2s, 4s
    catchError((err: HttpErrorResponse) => {
      const message = err.status === 0
        ? 'Network error -- check your connection.'
        : `Server returned ${err.status}: ${err.error?.detail ?? err.message}`;
      return throwError(() => new Error(message));
    }),
  );
}
----

Centralised handling (global `ErrorHandler`, an interceptor that catches every response, redirecting on `401`)
is covered on xref:web/angular/error-handling.adoc[Error handling].

== Functional interceptors

An interceptor is an `HttpInterceptorFn` -- a function that receives the outgoing request and a `next` handler,
and returns the response stream. It runs in the injection context, so it can `inject()` services. Interceptors
run in the order listed in `+withInterceptors([...])+`.

[source,typescript]
----
import { HttpInterceptorFn, HttpErrorResponse } from '@angular/common/http';
import { inject } from '@angular/core';
import { catchError, retry, tap, throwError, timer } from 'rxjs';

// 1. attach a bearer token to same-origin API calls
export const authInterceptor: HttpInterceptorFn = (req, next) => {
  const token = inject(AuthStore).token();
  if (!token || !req.url.startsWith('/api/')) return next(req);
  return next(req.clone({ setHeaders: { Authorization: `Bearer ${token}` } }));
};

// 2. log method, url, and outcome
export const loggingInterceptor: HttpInterceptorFn = (req, next) => {
  const started = performance.now();
  return next(req).pipe(
    tap({
      next: (event) => { /* inspect HttpResponse if event.type === HttpEventType.Response */ },
      error: (err: HttpErrorResponse) =>
        console.error(`${req.method} ${req.url} failed (${err.status})`),
      finalize: () => console.debug(`${req.method} ${req.url} ${Math.round(performance.now() - started)}ms`),
    }),
  );
};

// 3. retry idempotent requests with backoff
export const retryInterceptor: HttpInterceptorFn = (req, next) =>
  req.method === 'GET'
    ? next(req).pipe(retry({ count: 2, delay: (_e, i) => timer(300 * 2 ** i) }))
    : next(req);
----

`HttpRequest` is immutable; produce a modified copy with `+req.clone(...)+`. See
https://angular.dev/guide/http/interceptors[Interceptors].

== `httpResource()`

`httpResource()` wraps a GET in the signal-based `resource` API: pass a *reactive* request (a function reading
signals) and it re-fetches whenever a dependency changes, exposing `value`, `status`, `error`, and `isLoading`
as signals. It is for *reading* data into the view, not for mutations.

[source,typescript]
----
import { httpResource } from '@angular/common/http';
import { signal } from '@angular/core';

readonly bookId = signal('1');
readonly book = httpResource<Book>(() => `/api/books/${this.bookId()}`);

// template:
// @if (book.isLoading()) { <app-spinner /> }
// @else if (book.error()) { <p role="alert">Failed to load.</p> }
// @else { <h1>{{ book.value()?.title }}</h1> }
----

See https://angular.dev/guide/http/http-resource[`httpResource`] and xref:web/angular/signals.adoc[Signals].

== Testing

`provideHttpClientTesting` replaces the real backend with a controllable one. `HttpTestingController` lets a
test assert which requests were made and flush fake responses; `verify()` fails the test on unexpected or
outstanding requests. Full guidance is on xref:web/angular/testing.adoc[Testing].

[source,typescript]
----
import { provideHttpClient } from '@angular/common/http';
import { provideHttpClientTesting, HttpTestingController } from '@angular/common/http/testing';
import { TestBed } from '@angular/core/testing';

beforeEach(() => TestBed.configureTestingModule({
  providers: [provideHttpClient(), provideHttpClientTesting(), BookApi],
}));

it('requests the book list', () => {
  const api = TestBed.inject(BookApi);
  const http = TestBed.inject(HttpTestingController);

  api.list('ng', 1).subscribe((books) => expect(books.length).toBe(1));

  const req = http.expectOne('/api/books?q=ng&page=1');
  expect(req.request.method).toBe('GET');
  req.flush([{ id: '1', title: 'Learning Angular' }]);
  http.verify();
});
----

See https://angular.dev/guide/http/testing[Testing HTTP requests].

== Cross-origin requests

A request to a different origin is governed by the browser's *CORS* policy: the server must return
`Access-Control-Allow-Origin` (and, for non-simple requests, respond to a preflight `OPTIONS`), otherwise the
browser rejects the response and `HttpClient` reports an `HttpErrorResponse` with `status: 0`. Angular cannot
relax this -- it is enforced by the browser. See xref:web/cors.adoc[What is CORS?] and, for the request/response
model underneath, xref:programming-languages/javascript/browser-networking.adoc[Browser networking].

    S-->>I: 200 JSON body
    I-->>H: HttpResponse (Book array)
    H-->>C: parsed body, piped through map / catchError
    Note over C: unsubscribe() cancels an in-flight request

== Deep dive: BookShelf's API layer

The pieces above fit together as one small, testable layer: a typed `BookApi`, an `AuthStore` holding the access token, and
three interceptors. The sections below build it and test each behaviour against `HttpTestingController`.

=== The interceptor chain

Interceptors wrap each other like layers of an onion. A request passes through them in the order listed, and the response
travels back through them in reverse:

[mermaid]
....
flowchart LR
    CALL["http.get(...)"] --> AUTH["authInterceptor: add Authorization"]
    AUTH --> LOG["loggingInterceptor: log method and URL"]
    LOG --> REFRESH["refreshInterceptor: on 401, refresh and replay"]
    REFRESH --> BACKEND["HttpBackend (fetch)"]
    BACKEND -.->|"response or error flows back"| REFRESH
    REFRESH -.-> LOG
    LOG -.-> AUTH
    AUTH -.-> CALL
....

Each interceptor sees the *outgoing* request on the way in and the *response stream* on the way out. An interceptor that
only inspects (logging) passes `next(req)` through `tap`; one that changes the request (auth) calls `+next(req.clone(...))+`;
one that changes the outcome (refresh) transforms the response stream with `catchError`.

=== Skipping an interceptor with `HttpContext`

A request can carry typed, per-request flags in an `HttpContext`. The token below lets one call opt out of the auth
interceptor -- the refresh call itself must not carry the (expired) bearer token, and must not trigger another refresh:

[source,typescript]
----
import { HttpContext, HttpContextToken } from '@angular/common/http';

export const SKIP_AUTH = new HttpContextToken<boolean>(() => false);

export const authInterceptor: HttpInterceptorFn = (req, next) => {
  const token = inject(AuthStore).token();
  if (!token || req.context.get(SKIP_AUTH) || !req.url.startsWith('/api/')) return next(req);
  return next(req.clone({ setHeaders: { Authorization: `Bearer ${token}` } }));
};

// at the call site:
this.http.post('/auth/refresh', {}, { context: new HttpContext().set(SKIP_AUTH, true) });
----

=== Refreshing an expired token once

When several requests fail with `401` at the same moment, the app should refresh the token *once* and replay every failed
request with the new one. A `shareReplay` on the refresh observable gives all callers the same in-flight refresh:

[source,typescript]
----
@Injectable({ providedIn: 'root' })
export class AuthStore {
  private readonly http = inject(HttpClient);          // a field, not inject() inside refresh(): see below
  readonly token = signal<string | null>(null);
  private refreshing$?: Observable<string>;

  refresh(): Observable<string> {
    this.refreshing$ ??= this.http
      .post<{ token: string }>('/auth/refresh', {}, { context: new HttpContext().set(SKIP_AUTH, true) })
      .pipe(
        map((r) => r.token),
        tap((t) => this.token.set(t)),
        finalize(() => (this.refreshing$ = undefined)),
        shareReplay({ bufferSize: 1, refCount: false }),
      );
    return this.refreshing$;
  }
}

export const refreshInterceptor: HttpInterceptorFn = (req, next) => {
  const auth = inject(AuthStore);
  return next(req).pipe(
    catchError((err: HttpErrorResponse) => {
      if (err.status !== 401 || req.context.get(SKIP_AUTH)) return throwError(() => err);
      return auth.refresh().pipe(
        switchMap((token) => next(req.clone({ setHeaders: { Authorization: `Bearer ${token}` } }))),
      );
    }),
  );
};
----

....
sequenceDiagram

    participant B as Call B

The `inject(HttpClient)` is a *field initializer* on purpose. Calling `inject()` inside `refresh()` itself would run when the
interceptor's `catchError` fires -- long after construction -- and fail with `NG0203`. The test below confirms that exactly one
refresh request is sent for two concurrent `401` responses and that both replays carry the new token:

[source,typescript]
----
it('refreshes once on 401 and replays both requests', () => {
  const api = TestBed.inject(BookApi);
  const http = TestBed.inject(HttpTestingController);
  const results: string[] = [];
  api.get('b1').subscribe((b) => results.push(b.id));
  api.get('b2').subscribe((b) => results.push(b.id));

  http.expectOne('/api/books/b1').flush({}, { status: 401, statusText: 'Unauthorized' });
  http.expectOne('/api/books/b2').flush({}, { status: 401, statusText: 'Unauthorized' });

  const refresh = http.match('/auth/refresh');
  expect(refresh.length).toBe(1);                                    // one refresh, shared
  expect(refresh[0].request.headers.has('Authorization')).toBe(false);
  refresh[0].flush({ token: 't2' });

  const r1 = http.expectOne('/api/books/b1');
  const r2 = http.expectOne('/api/books/b2');
  expect(r1.request.headers.get('Authorization')).toBe('Bearer t2');
  r1.flush({ id: 'b1' });
  r2.flush({ id: 'b2' });
  expect(results).toEqual(['b1', 'b2']);
});
----

=== Testing retries with a controllable clock

`+retry({ count: 3, delay: (_err, i) => timer(500 * 2 ** i) })+` retries after 1 s, 2 s, and 4 s (the retry index `i` starts
at 1), for four requests in total. Vitest's fake timers let a test step through the schedule without waiting:

[source,typescript]
----
it('retries with exponential backoff, then maps the error', () => {
  vi.useFakeTimers();
  const api = TestBed.inject(BookApi);
  const http = TestBed.inject(HttpTestingController);
  let error: Error | undefined;
  api.listSafe().subscribe({ error: (e) => (error = e) });

  const fail = () => http.expectOne('/api/books').flush({ detail: 'boom' }, { status: 503, statusText: 'x' });
  fail();
  vi.advanceTimersByTime(999);  http.expectNone('/api/books');      // not yet
  vi.advanceTimersByTime(1);    fail();                              // 1 s: second attempt
  vi.advanceTimersByTime(2000); fail();                              // +2 s: third attempt
  vi.advanceTimersByTime(4000); fail();                              // +4 s: fourth and last
  expect(error?.message).toBe('Server returned 503: boom');
});
----

A transport failure (`status` 0) takes the same path and produces the `Network error` message; retrying every failure
blindly is only safe for idempotent requests, which is why the interceptor version earlier retries `GET` only.

=== Testing `httpResource`

A resource issues its request when change detection runs, not when it is created, and it stays pending until the request is
answered. Two details follow for tests. Call `TestBed.tick()` to run the effect that starts the request, and do *not*
`await fixture.whenStable()` before flushing: `whenStable()` waits for pending requests and would wait forever.

[source,typescript]
----
@Component({ selector: 'app-res', template: `{{ book.value()?.title ?? 'none' }}|{{ book.status() }}` })
class Res {
  readonly id = signal('b1');
  readonly book = httpResource<{ id: string; title: string }>(() => `/api/books/${this.id()}`);
}

it('refetches when the signal changes', async () => {
  TestBed.configureTestingModule({ providers: [provideHttpClient(), provideHttpClientTesting()] });
  const fixture = TestBed.createComponent(Res);
  const http = TestBed.inject(HttpTestingController);

  TestBed.tick();                                                       // starts the first request
  http.expectOne('/api/books/b1').flush({ id: 'b1', title: 'One' });
  await fixture.whenStable();
  expect((fixture.nativeElement as HTMLElement).textContent).toBe('One|resolved');

  fixture.componentInstance.id.set('b2');                               // the request function reads this signal
  TestBed.tick();
  http.expectOne('/api/books/b2').flush({ id: 'b2', title: 'Two' });
  await fixture.whenStable();
  expect((fixture.nativeElement as HTMLElement).textContent).toBe('Two|resolved');
});
----

A resource also accepts `parse` (to validate or reshape the raw response, a good place for a runtime schema check) and
`defaultValue` (so `value()` is never `undefined`), and exposes `reload()` to repeat the current request. Prefer a resource
for *reading* data that depends on signals, and a plain `HttpClient` call for commands (create, update, delete).
