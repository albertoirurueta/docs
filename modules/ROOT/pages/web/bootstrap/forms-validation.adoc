= Forms: Validation States & Feedback
:description: Covers styling valid and invalid Bootstrap 5 form controls with .is-valid/.is-invalid, showing feedback text with .valid-feedback/.invalid-feedback, and the difference between relying on browser tooltips and applying Bootstrap's own validation classes.
:keywords: bootstrap forms validation, is-valid, is-invalid, valid-feedback, invalid-feedback, was-validated, needs-validation, browser validation, custom validation

include::partial$ai-disclaimer.adoc[]

Bootstrap layers a set of validation-state classes and feedback elements on top of the native browser
validation described in
xref:web/html-css/forms-accessibility-validation.adoc[Form Accessibility & Validation] -- the `required`
attribute, `type="email"`, `pattern`, `:valid`/`:invalid`, and the JavaScript Constraint Validation API all
still work exactly as documented there. What Bootstrap adds is purely visual and structural: consistent
colors/icons for valid and invalid fields, and a standard place to put the feedback text explaining *why* a
field failed. This page covers `.is-valid`/`.is-invalid`, `.valid-feedback`/`.invalid-feedback`, and the two
ways of triggering them -- browser-native constraint validation and fully custom JavaScript validation -- as
well as xref:web/bootstrap/forms.adoc[Forms] for the controls being validated.

== The validation classes

Two pairs of classes drive Bootstrap's validation styling:

[cols="1,3", options="header"]
|===
| Class | Effect

| `.is-valid`
| Applied directly to a `.form-control`/`.form-select`/`.form-check-input`. Colors the border and, for text-like
  controls, adds a green checkmark icon.

| `.is-invalid`
| Same mechanism, red border and an exclamation-mark icon instead.

| `.valid-feedback`
| A block of text (typically a `<div>` right after the control) that is hidden by default and shown only when
  its *preceding sibling* carries `.is-valid`.

| `.invalid-feedback`
| Same mechanism as `.valid-feedback`, shown when the preceding sibling carries `.is-invalid`.
|===

Both feedback classes rely on being an *adjacent sibling* of the state-classed control in the DOM -- Bootstrap's
CSS uses a `+~+` sibling selector to reveal them, so moving the feedback `<div>` somewhere else in the markup (for
example, inside a wrapping `<div>` around only the control) silently breaks the reveal:

[source,html]
----
<div class="mb-3">
  <label for="username" class="form-label">Username</label>
  <input type="text" class="form-control is-invalid" id="username" value="a">
  <div class="invalid-feedback">
    Username must be at least 3 characters.
  </div>
</div>

<div class="mb-3">
  <label for="display-name" class="form-label">Display name</label>
  <input type="text" class="form-control is-valid" id="display-name" value="Jane">
  <div class="valid-feedback">
    Looks good!
  </div>
</div>
----

If a control sits inside an `.input-group`, the feedback `<div>` must stay *inside* the group, as a sibling of
the control that triggers it -- moving it after the group's closing tag breaks the very `+~+` sibling selector
this section opened with, since the feedback element would then be a sibling of `.input-group` rather than of
the state-classed control itself:

[source,html]
----
<div class="input-group has-validation">
  <span class="input-group-text" id="handle-addon">@</span>
  <input type="text" class="form-control is-invalid" aria-describedby="handle-addon">
  <div class="invalid-feedback">
    Please choose a username.
  </div>
</div>
----

`.has-validation` on the `.input-group` itself is required in this case -- without it, Bootstrap's own
input-group border-radius CSS overlaps the feedback text's position.

== Browser-native validation styling with `.was-validated`

Rather than hand-adding `.is-valid`/`.is-invalid` to every field, Bootstrap can drive the same visual states
straight off the browser's own `:valid`/`:invalid` pseudo-classes (see
xref:web/html-css/forms-accessibility-validation.adoc[Form Accessibility & Validation] for how those are
computed from `required`, `type`, `pattern`, and friends). The trigger is the `.was-validated` class on the
`<form>`, combined with disabling the browser's own bubble UI via `novalidate`:

[source,html]
----
<form class="row g-3 needs-validation" novalidate>
  <div class="col-md-6">
    <label for="first-name-v" class="form-label">First name</label>
    <input type="text" class="form-control" id="first-name-v" required>
    <div class="valid-feedback">Looks good!</div>
    <div class="invalid-feedback">First name is required.</div>
  </div>
  <div class="col-md-6">
    <label for="email-v" class="form-label">Email</label>
    <input type="email" class="form-control" id="email-v" required>
    <div class="valid-feedback">Looks good!</div>
    <div class="invalid-feedback">Please enter a valid email address.</div>
  </div>
  <div class="col-12">
    <button class="btn btn-primary" type="submit">Submit</button>
  </div>
</form>
----

[source,js]
----
// Bootstrap does not add this behavior automatically -- it must be wired up per form.
(() => {
  const forms = document.querySelectorAll(".needs-validation");

  Array.from(forms).forEach((form) => {
    form.addEventListener("submit", (event) => {
      if (!form.checkValidity()) {
        event.preventDefault();
        event.stopPropagation();
      }
      form.classList.add("was-validated");
    }, false);
  });
})();
----

`novalidate` on the `<form>` suppresses the browser's own validation bubbles so only Bootstrap's styling shows;
`form.checkValidity()` (from the Constraint Validation API) still runs the real native checks underneath, it is
only the *presentation* that is suppressed. Adding `.was-validated` to the form is what turns on the CSS rules
that map `:valid`/`:invalid` to `.is-valid`-/`.is-invalid`-equivalent styling -- before submission is attempted,
fields show no state at all, which avoids painting an untouched required field red before the user has had a
chance to fill it in.

== Fully custom validation

For rules the browser cannot express natively -- a password-confirmation match, an async username-availability
check, a business-specific format -- apply `.is-valid`/`.is-invalid` directly from JavaScript instead of relying
on `.was-validated`. This is the same pattern as `setCustomValidity` in plain HTML forms, just paired with
Bootstrap's own classes rather than the browser's native validation bubble:

[source,html]
----
<div class="mb-3">
  <label for="password-c" class="form-label">Password</label>
  <input type="password" class="form-control" id="password-c">
</div>
<div class="mb-3">
  <label for="confirm-c" class="form-label">Confirm password</label>
  <input type="password" class="form-control" id="confirm-c">
  <div class="invalid-feedback">Passwords do not match.</div>
</div>
----

[source,js]
----
const password = document.getElementById("password-c");
const confirm = document.getElementById("confirm-c");

function validateConfirm() {
  const matches = confirm.value === password.value;
  confirm.classList.toggle("is-invalid", !matches);
  confirm.classList.toggle("is-valid", matches && confirm.value !== "");
}

password.addEventListener("input", validateConfirm);
confirm.addEventListener("input", validateConfirm);
----

Because this approach never touches `required`/`pattern`/`setCustomValidity`, `form.checkValidity()` knows
nothing about it -- a submit handler relying purely on custom classes must check
`confirm.classList.contains("is-invalid")` itself (or block submission directly) rather than trusting native
constraint validation to catch the mismatch.

== Choosing between the two approaches

* Prefer the `.was-validated` / native-constraint route whenever `required`, `type`, `pattern`, `min`/`max`, or
  `minlength`/`maxlength` already express the rule -- it needs no per-field JavaScript and stays in sync with
  whatever the Constraint Validation API reports.
* Reach for manually toggled `.is-valid`/`.is-invalid` only for rules the browser genuinely cannot express, and
  combine it with `setCustomValidity` (see
  xref:web/html-css/forms-accessibility-validation.adoc[Form Accessibility & Validation]) if the field should
  also block a plain `form.checkValidity()`/`requestSubmit()` call, not just look wrong.
* Either way, always pair the color-coded border with real feedback text -- color alone is not perceivable to a
  colorblind user or a screen-reader user, both of whom rely on the `.invalid-feedback`/`.valid-feedback` text
  actually being present and shown.

== The validation flow end to end

The three ways of reaching a field's visual state (native constraints, custom rules, server responses) converge on the
same two things: the browser's validity state, and the `.is-valid`/`.is-invalid` classes that Bootstrap's CSS reads.

[mermaid]
....
flowchart TB
    SUBMIT["submit event"] --> SYNC["Run custom rules:<br/>setCustomValidity on each field"]
    SYNC --> MARK["form.classList.add was-validated"]
    MARK --> CHECK{"form.checkValidity()"}
    CHECK -->|"false"| STOP["preventDefault and stopPropagation<br/>focus the first :invalid field"]
    CHECK -->|"true"| SEND["Send the request"]
    SEND --> SERVER{"Server response"}
    SERVER -->|"errors"| SHOW["remove was-validated,<br/>add is-invalid and message per field"]
    SERVER -->|"ok"| DONE["Success feedback"]
    SHOW --> EDIT["User edits field:<br/>clear is-invalid"]
    EDIT --> SUBMIT
....

== Worked example: the Taskboard sign-up form

A sign-up form needs rules from all three sources: `required`, `type="email"` and `minlength` (native), "the two
passwords match" (custom: the browser cannot compare fields), and "this e-mail is already registered" (only the server
knows). The markup is ordinary Bootstrap; every field is a wrapper with a label, a control and feedback as the
control's next sibling:

[source,html]
----
<form id="signup" class="needs-validation" novalidate>
  <div class="mb-3">
    <label for="su-email" class="form-label">E-mail</label>
    <input type="email" class="form-control" id="su-email" name="email" required aria-describedby="su-email-fb">
    <div id="su-email-fb" class="invalid-feedback">Enter a valid e-mail address.</div>
  </div>
  <div class="mb-3">
    <label for="su-password" class="form-label">Password</label>
    <input type="password" class="form-control" id="su-password" name="password" minlength="8" required
           aria-describedby="su-password-fb">
    <div id="su-password-fb" class="invalid-feedback">Use at least 8 characters.</div>
  </div>
  <div class="mb-3">
    <label for="su-confirm" class="form-label">Confirm password</label>
    <input type="password" class="form-control" id="su-confirm" name="confirm" required aria-describedby="su-confirm-fb">
    <div id="su-confirm-fb" class="invalid-feedback">The passwords do not match.</div>
  </div>
  <button type="submit" class="btn btn-primary">Create account</button>
</form>
----

The script below puts the three kinds of rule behind the same classes. Its behavior was exercised in a DOM test with
the markup above (empty submit, mismatched passwords, corrected passwords, a valid submit, and a simulated server
error):

[source,javascript]
----
function initSignup(form) {
  const { password, confirm } = form.elements;

  // The browser cannot compare two fields, so express the rule as a custom validity message.
  function syncConfirm() {
    confirm.setCustomValidity(confirm.value === password.value ? "" : "Passwords do not match");
  }

  // Keep aria-invalid in step with the constraint state of a field.
  function reflect(field) {
    field.setAttribute("aria-invalid", String(!field.validity.valid));
  }

  for (const field of [password, confirm]) {
    field.addEventListener("input", () => {
      syncConfirm();
      reflect(confirm);
    });
  }

  form.addEventListener("submit", (event) => {
    syncConfirm();
    form.classList.add("was-validated");
    [...form.elements].filter((el) => el.willValidate).forEach(reflect);
    if (!form.checkValidity()) {
      event.preventDefault();
      event.stopPropagation();
      form.querySelector("input:invalid, select:invalid, textarea:invalid").focus();
    }
  });
}

// Show errors returned by the server using the same classes the browser-driven path uses.
function showServerErrors(form, errors) {
  form.classList.remove("was-validated");
  for (const [name, message] of Object.entries(errors)) {
    const field = form.elements[name];
    field.classList.add("is-invalid");
    field.setAttribute("aria-invalid", "true");
    field.parentElement.querySelector(".invalid-feedback").textContent = message;
    field.addEventListener("input", () => field.classList.remove("is-invalid"), { once: true });
  }
}

initSignup(document.getElementById("signup"));
----

The observed results were:

[cols="2,3", options="header"]
|===
| Scenario | Result

| Submit with every field empty
| `submit` is cancelled, `was-validated` is added, focus moves to the e-mail field.

| Valid e-mail and password, different confirmation
| `submit` is cancelled; the confirmation reports the validation message "Passwords do not match",
  `aria-invalid="true"`, and focus moves to it.

| Confirmation corrected (an `input` event)
| The custom message is cleared, the field becomes valid and `aria-invalid` becomes `false` immediately.

| Everything valid
| `submit` is *not* cancelled, so the request is sent.

| `+showServerErrors(form, { email: "That email is already registered." })+`
| `was-validated` is removed, the e-mail field has `is-invalid`, and its feedback element shows the server's text;
  editing the field removes `is-invalid`.
|===

Why the design looks like this:

* **`setCustomValidity` instead of only toggling classes.** Because the mismatch is registered with the browser,
  `form.checkValidity()` fails and the submit is blocked by the same code path as `required`. The alternative, only
  toggling `.is-invalid` (the technique shown earlier), looks right but lets the form submit.
* **`syncConfirm()` runs inside the submit handler as well as on input.** The `input` listeners cover typing, but a
  password-manager autofill or a script that sets `value` does not fire them; recomputing at submit time makes the
  check independent of how the values got there.
* **Static feedback text, one message per field.** `.invalid-feedback` is shown whichever rule failed. When different
  rules need different messages, set the element's text from the field's `validity` flags
  (`field.validity.valueMissing`, `field.validity.typeMismatch`, `field.validity.tooShort`) rather than showing the
  browser's own `validationMessage`, which is not controlled by the page and varies by language and browser.
* **`aria-describedby` on each control.** It links the feedback text to the field so a screen reader reads the
  explanation when the field gets focus. Note that an element referenced by `aria-describedby` still contributes to the
  description when it is hidden with `display: none`, so some screen readers read the message even when the field is
  valid. If that is a problem, leave the attribute out of the markup and add it from script when a field becomes invalid
  (and remove it when it becomes valid).
* **Focus moves to the first invalid field.** Without it a keyboard user must tab through the whole form to find what
  failed; the selector lists the control types explicitly because a `<fieldset>` containing an invalid control also matches
  `:invalid` and cannot take focus. It returns the first invalid control in DOM order.

== Behaviors worth knowing

* **Optional empty fields turn green too.** With `.was-validated`, any control that matches `:valid` gets the success
  styling, including an empty field that is not `required`. Forms with many optional fields often skip the
  success styling (leave out `.valid-feedback` and override the valid border) or apply `.is-invalid` only.
* **Tooltip-style feedback.** Using `.valid-tooltip`/`.invalid-tooltip` instead of the `-feedback` classes shows the
  message as a small floating bubble under the field. It is positioned absolutely, so the field's wrapper needs
  `.position-relative`. The bubble can overlap the next field, so it suits compact layouts only.
* **Checkboxes and radios.** `.is-invalid` on a `.form-check-input` colors the box and its label; put the feedback
  after the *last* check of a group so that one message covers the group.
* **Disabling the browser bubble.** `novalidate` hides the native message bubbles only for submit; calling
  `form.reportValidity()` (or `field.reportValidity()`) from script still shows them.
* **Theming.** `$form-feedback-valid-color`, `$form-feedback-invalid-color` and `$enable-validation-icons` control the
  colors and the icons at build time; see xref:web/bootstrap/forms.adoc[Forms] for the variables partial ordering.

See https://getbootstrap.com/docs/5.3/forms/validation/[the official Validation documentation] for the full set
of supported selectors and browser-compatibility notes.
