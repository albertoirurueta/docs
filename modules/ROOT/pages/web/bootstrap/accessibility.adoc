= Accessibility
:description: Covers accessibility support built into Bootstrap 5 components -- the ARIA attributes components manage automatically, keyboard navigation for interactive widgets, and color contrast guidance for the default theme.
:keywords: Bootstrap accessibility, ARIA attributes, aria-expanded, aria-hidden, keyboard navigation, focus trap, visually-hidden, color contrast, screen reader, Bootstrap a11y

include::partial$ai-disclaimer.adoc[]

Bootstrap's components are not accessible by default just because they are widely used -- but the library does
build a substantial amount of accessibility support directly into its markup patterns and JavaScript, so that
following the documented markup for a component (rather than reinventing it) gets most of the way there for
free. This page covers what that built-in support actually does: the ARIA attributes components manage
automatically, keyboard support for interactive widgets, and color contrast in the default theme. It does not
repeat general form-accessibility guidance -- labeling, fieldsets, the Constraint Validation API -- which is
covered in full on xref:web/html-css/forms-accessibility-validation.adoc[Form Accessibility & Validation] and
applies equally to a form built with Bootstrap's form classes. For WCAG conformance levels, legal accessibility
standards, and general page-level accessibility principles this page doesn't cover, see
xref:web/accessibility.adoc[Web Accessibility].

== ARIA attributes managed automatically

Several Bootstrap components toggle ARIA state attributes as part of their normal open/close JavaScript
lifecycle, so the accessibility tree stays in sync with the visual state without extra application code:

[source,html]
----
<!-- Collapse: aria-expanded flips between true/false as the JS toggles the panel -->
<button class="btn" data-bs-toggle="collapse" data-bs-target="#details" aria-expanded="false" aria-controls="details">
  Details
</button>
<div class="collapse" id="details">Collapsible content.</div>

<!-- Dropdown: aria-expanded on the toggle button, tracked the same way -->
<div class="dropdown">
  <button class="btn dropdown-toggle" data-bs-toggle="dropdown" aria-expanded="false">Menu</button>
  <ul class="dropdown-menu">
    <li><a class="dropdown-item" href="#">Action</a></li>
  </ul>
</div>
----

`aria-expanded` and `aria-controls` are written once in the markup, and Bootstrap's JavaScript keeps
`aria-expanded` current as the component opens and closes -- a screen reader announces "collapsed"/"expanded"
correctly even though nothing in the visible page text says so.

Modals rely on a similar pattern, plus `aria-hidden` and `aria-modal` to describe the modal's relationship to
the rest of the page while it's open:

[source,html]
----
<div class="modal" id="exampleModal" tabindex="-1" aria-labelledby="exampleModalLabel" aria-hidden="true">
  <div class="modal-dialog">
    <div class="modal-content">
      <div class="modal-header">
        <h5 class="modal-title" id="exampleModalLabel">Modal title</h5>
        <button type="button" class="btn-close" data-bs-dismiss="modal" aria-label="Close"></button>
      </div>
      <div class="modal-body">Modal body content.</div>
    </div>
  </div>
</div>
----

`aria-labelledby` points a screen reader at the modal's own heading, so opening it announces the modal's
title rather than "dialog" with no further context. `aria-hidden="true"` on the closed `.modal` keeps its hidden
content out of the accessibility tree; when Bootstrap's JavaScript shows the modal it *removes* that attribute
(rather than flipping it to `false`) and adds `aria-modal="true"` plus `role="dialog"` to the modal element
itself. Bootstrap does **not** apply `aria-hidden`/`inert` to the rest of the page behind the backdrop -- the
only thing stopping a user from reaching that content is the JavaScript focus trap, which keeps *keyboard* focus
inside the modal but does nothing to stop a screen reader's own virtual-cursor browsing from wandering into it.
A project that needs to actually hide background content from assistive technology has to apply
`aria-hidden="true"` (or `inert`) to its own top-level wrapper manually while the modal is open -- Bootstrap
does not do this automatically.

The close button's `aria-label="Close"` matters specifically because `.btn-close` renders as an empty,
icon-only button -- with no visible text for a screen reader to announce, the `aria-label` is the *only* thing
that identifies its purpose; omitting it leaves the button announced as just "button," with no indication of
what it does.

== `.visually-hidden`: screen-reader-only text

Not every accessibility need is solved by an ARIA attribute -- sometimes a component's visible label alone
isn't enough context for a non-sighted user, but adding visible text would be redundant or cluttered for a
sighted one. `.visually-hidden` (and `.visually-hidden-focusable` for content that should become visible again
once it receives keyboard focus, such as a skip link) hides content visually while keeping it in the
accessibility tree:

[source,html]
----
<div class="spinner-border" role="status">
  <span class="visually-hidden">Loading...</span>
</div>

<a class="visually-hidden-focusable" href="#main-content">Skip to main content</a>

<button type="button" class="btn-close" aria-label="Close"></button>
<!-- aria-label achieves the same announcement here without an extra hidden element,
     since btn-close has no visible text node to hide in the first place -->
----

The spinner example matters because `.spinner-border` on its own is a purely visual animation -- with no text
and no ARIA attribute, a screen-reader user gets no indication that anything is loading at all. The
`role="status"` plus the visually-hidden text together announce "Loading…" without adding a visible word next
to the spinner.

== Keyboard navigation

Bootstrap's interactive components implement the keyboard interaction patterns expected for their ARIA role,
not just mouse/touch activation:

[cols="1,2", options="header"]
|===
| Component | Keyboard support

| Dropdown
| *Enter*/*Space* opens the menu from the toggle button; *Arrow Down*/*Arrow Up* moves between menu items;
  *Esc* closes the menu and returns focus to the toggle.

| Modal
| *Esc* closes the modal (unless disabled via `data-bs-keyboard="false"`); focus is trapped inside the modal
  while open, so *Tab* cycles only through the modal's own focusable elements instead of leaking to page
  content behind the backdrop; focus returns to the element that opened the modal once it closes.

| Carousel
| *Arrow Left*/*Arrow Right* move to the previous/next slide when a carousel control has focus.

| Tabs (`.nav-tabs` / `.nav-pills` with `data-bs-toggle="tab"`)
| *Arrow Left*/*Arrow Right* (or *Up*/*Down* for a vertical list) move between tabs following the ARIA
  `tablist` pattern, rather than requiring a full *Tab* keypress per tab.

| Offcanvas
| *Esc* closes the panel; focus is trapped inside it while open, the same as a modal.
|===

The modal's focus trap is worth calling out specifically: without it, *Tab* would move focus behind a visually
closed-off backdrop into content a sighted user can't currently see or interact with, disorienting a keyboard
user in a way a mouse user would never encounter. This is exactly the kind of operability requirement described
generally in xref:web/html-css/forms-accessibility-validation.adoc[Form Accessibility & Validation]'s section
on keyboard navigation and focus -- Bootstrap's modal is one concrete component that implements it so an
application doesn't have to write its own focus-trap logic.

== Color contrast

Bootstrap's default theme colors were chosen to pass WCAG AA contrast requirements against their typical
pairing (e.g. white text on `$primary`), but this guarantee does *not* automatically survive customization.
Overriding `$theme-colors` (see xref:web/bootstrap/customization.adoc[Customization]) with a brand palette can
easily produce a color that looks fine to a sighted designer at full opacity but fails contrast for low-vision
users -- Bootstrap's build has no way to verify a project's overridden values, since contrast is a property of
the actual rendered pixels, not something the Sass compiler checks.

Two practical guidelines follow from this:

* After overriding any theme color, re-check contrast against both a light and dark background it's likely to
  appear on -- a button's text against its own background, and body text against `$body-bg` -- with a contrast
  checker, not by eye.
* The *subtle*/*emphasis* utility pairs introduced in Bootstrap 5.3 (`bg-primary-subtle` with
  `text-primary-emphasis`, covered on xref:web/bootstrap/utilities.adoc[Utilities]) are generated to maintain
  contrast automatically as color-mode changes, and are a safer default than hand-pairing an arbitrary
  background and text color when the exact color isn't otherwise constrained by brand requirements.

== Tabs: roving tabindex and `aria-selected`

The Tab plugin implements the ARIA `tablist` pattern, but only if the markup supplies the roles and the initial state.
Bootstrap then keeps `aria-selected` and `tabindex` in step with the active tab ("roving tabindex": only the selected
tab is in the page's *Tab* order, and the arrow keys move between tabs):

[source,html]
----
<ul class="nav nav-tabs" role="tablist">
  <li class="nav-item" role="presentation">
    <button class="nav-link active" id="tab-open" data-bs-toggle="tab" data-bs-target="#pane-open"
            type="button" role="tab" aria-controls="pane-open" aria-selected="true">Open</button>
  </li>
  <li class="nav-item" role="presentation">
    <button class="nav-link" id="tab-done" data-bs-toggle="tab" data-bs-target="#pane-done"
            type="button" role="tab" aria-controls="pane-done" aria-selected="false" tabindex="-1">Done</button>
  </li>
</ul>
<div class="tab-content">
  <div class="tab-pane fade show active" id="pane-open" role="tabpanel" aria-labelledby="tab-open" tabindex="0">...</div>
  <div class="tab-pane fade" id="pane-done" role="tabpanel" aria-labelledby="tab-done" tabindex="0">...</div>
</div>
----

In a DOM test of this markup, activating the second tab changed the first tab to `aria-selected="false"
tabindex="-1"` and the second to `aria-selected="true"` with its `tabindex` removed, and an *Arrow Left* keydown on
the second tab selected and focused the first. The author's part is the initial `tabindex="-1"` and
`aria-selected="false"` on the inactive tabs, `aria-labelledby` on each panel, and a `tabindex="0"` on panels whose
content has no focusable element, so that keyboard users can reach the panel after the tab.

== Modal lifecycle: what changes, and what does not

A DOM test of the modal markup earlier on this page (a trigger with `data-bs-toggle="modal"`, a `.modal` with
`aria-hidden="true"`) recorded the following state while it was shown and again after it was hidden:

[cols="2,2,2", options="header"]
|===
| Attribute or state | While shown | After hiding

| `aria-hidden` on `.modal`
| removed
| `true` again

| `aria-modal` and `role` on `.modal`
| `aria-modal="true"`, `role="dialog"`
| both removed

| `display` on `.modal`
| `block`
| `none`

| `class` on `<body>`
| `modal-open`
| removed

| Focus
| moves to the `.modal` element itself (`tabindex="-1"`), then Tab cycles inside it
| returned to the opener only for `data-bs-toggle` triggers; see below

| Content behind the backdrop
| not hidden and not `inert` (the test page's wrapper kept both unset)
| unchanged
|===

[mermaid]
....
sequenceDiagram
    participant U as User
    participant T as Trigger button
    participant M as Modal element
    participant P as Page content

    U->>T: Enter or click
    T->>M: show() via data-bs-toggle
    M->>M: remove aria-hidden, add aria-modal and role=dialog
    M->>M: body gets modal-open, focus trap starts, focus moves to dialog
    Note over P: still in the accessibility tree and not inert
    U->>M: Esc or close button
    M->>M: aria-hidden back to true, focus trap released
    M->>T: focus restored (data-api trigger only)
....

Focus is returned to the opener only when the modal was opened through the `data-bs-toggle="modal"` trigger: that
click handler registers a one-time `hidden.bs.modal` listener which refocuses the trigger if it is still visible.
A modal opened with `new bootstrap.Modal(el).show()` from a script gets no such listener, so the script has to restore
focus itself:

[source,javascript]
----
const dialog = document.getElementById("confirm-delete");
const modal = bootstrap.Modal.getOrCreateInstance(dialog);
let opener = null;

function openDialog(trigger) {
  opener = trigger;
  modal.show();
}

dialog.addEventListener("hidden.bs.modal", () => opener?.focus());
----

== Worked example: making the Taskboard page accessible

Starting from the Taskboard layout, these are the changes that turn a visually correct page into one a keyboard and
screen-reader user can operate, each taken from the guidance above:

[source,html]
----
<body>
  <a class="visually-hidden-focusable" href="#main">Skip to the task list</a>

  <header class="border-bottom">
    <nav class="navbar navbar-expand-md" aria-label="Main">...</nav>
  </header>

  <main id="main" tabindex="-1" class="container py-4">
    <h1 class="h3">Tasks</h1>

    <div id="status" class="visually-hidden" role="status"></div>

    <ul class="list-group" aria-label="Open tasks">
      <li class="list-group-item d-flex align-items-center gap-3">
        <input class="form-check-input mt-0" type="checkbox" id="task-1" aria-describedby="task-1-due">
        <label class="form-check-label flex-grow-1" for="task-1">Write documentation</label>
        <small id="task-1-due" class="text-body-secondary">Due Friday</small>
        <button type="button" class="btn btn-sm btn-outline-danger" data-bs-toggle="modal"
                data-bs-target="#confirm-delete">
          Delete<span class="visually-hidden"> "Write documentation"</span>
        </button>
      </li>
    </ul>
  </main>
</body>
----

* **Skip link.** `.visually-hidden-focusable` is hidden until it receives focus, so the first *Tab* press reveals it.
  The `href` target needs `tabindex="-1"` (as `<main>` has here) so that activating the link actually moves focus
  there in every browser.
* **Landmarks and labels.** `<header>`, `<nav aria-label="Main">`, `<main>` give screen-reader users shortcuts; two
  navigations on one page need distinct `aria-label` values.
* **Distinct button names.** A page with ten "Delete" buttons is ambiguous in a screen reader's list of controls. The
  `.visually-hidden` suffix makes each accessible name unique ("Delete "Write documentation"") without changing what
  sighted users see.
* **Status messages.** The empty `role="status"` element exists in the DOM from the start. Text written into it later
  (`status.textContent = "Task deleted"`) is announced politely. A live region that is inserted *together with* its
  text is frequently not announced at all, which is why the toast and alert examples on
  xref:web/bootstrap/feedback-components.adoc[Feedback Components] either exist before they are filled or are
  created before their content is added.
* **Delete confirmation.** The trigger uses `data-bs-toggle="modal"`, so focus returns to the Delete button when the
  dialog closes. The modal itself keeps `aria-labelledby` on its title, a close button with `aria-label`, and Cancel
  as the safest, first-focusable action.

== Motion, focus and preference media queries

* **Reduced motion.** Bootstrap's transitions (collapse, fade, carousel slide, spinner speed) are wrapped in
  `@media (prefers-reduced-motion: reduce)` rules that remove or shorten them, controlled at build time by the
  `$enable-reduced-motion` variable (true by default). Custom animations added to a Bootstrap page need the same
  guard.
* **Visible focus.** Buttons, form controls and component links (nav, pagination, list-group actions) show a focus ring
  built from a box-shadow in the theme color at 25% opacity. Buttons use `:focus-visible`, so the ring appears for
  keyboard focus and is usually suppressed for mouse clicks, while text inputs show it on `:focus`. Never remove it with
  `outline: none` without a replacement. The `.focus-ring` helper applies the same style to custom elements, and
  `+.focus-ring-{color}+` variants exist for each theme color.
* **Color mode.** `data-bs-theme="dark"` (see xref:web/bootstrap/colors.adoc[Colors]) recomputes the subtle and
  emphasis shades so that the pairs stay readable, but hand-picked hex colors inside custom CSS do not follow it.

== A review checklist for a Bootstrap page

[cols="2,3", options="header"]
|===
| Check | What to look for

| Document language and title
| `<html lang>` is set; every page has a distinct `<title>`.

| Interactive elements
| Real `<button>` and `<a>` elements, not styled `<div>` elements; icon-only buttons have an `aria-label`.

| Keyboard
| Every control reachable and operable with *Tab*, *Enter*, *Space*, *Esc* and the arrow keys; focus is visible; no
  keyboard trap outside open modals and offcanvas panels.

| Dynamic content
| Alerts, toasts and status text use live regions that exist before they are filled.

| Color
| Contrast checked for custom palettes; information never conveyed by color alone.

| Forms
| Each control has an associated `<label>`; error text is linked with `aria-describedby`
  (see xref:web/bootstrap/forms-validation.adoc[Forms: Validation]).

| Reordering
| Visual order produced by `+.order-*+` or `flex-row-reverse` matches the DOM order, or the mismatch is deliberate and
  harmless.
|===

== Summary: what Bootstrap gives you, and what it doesn't

Bootstrap's built-in ARIA management, keyboard support, and focus trapping remove a meaningful amount of the
accessibility work a component library needs -- but only for the interactive *widget* behavior (opening,
closing, navigating between items). None of it substitutes for the page-level accessibility fundamentals that
apply regardless of which CSS framework is used: meaningful heading structure, correctly labeled form fields,
sufficient contrast on custom content, and alt text on meaningful images. For form-specific guidance in
particular -- labels, `fieldset`/`legend` grouping, and validation messaging -- see
xref:web/html-css/forms-accessibility-validation.adoc[Form Accessibility & Validation], which applies whether a
form uses Bootstrap's `.form-control` classes or plain HTML.
