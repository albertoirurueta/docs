= Buttons
:description: Covers Bootstrap 5's button styles, contextual color and outline variants, sizes, states (active, disabled), and grouping buttons with .btn-group and .btn-toolbar.
:keywords: bootstrap buttons, btn-primary, btn-outline, btn-group, btn-toolbar, disabled button, active button

include::partial$ai-disclaimer.adoc[]

Bootstrap's button styling applies to any of three different elements -- `<button>`, `<a>`, and `<input
type="button|submit|reset">` -- so the same `.btn` classes render consistently regardless of which one is
semantically correct for a given action. Choosing the right element still matters: a `<button>` for an
in-page action, an `<a>` for navigation to a new URL, and `<input>` only inside a form being submitted the
old-fashioned way.

== Base class and color variants

`.btn` alone provides the base padding, border, and transition; a `+.btn-*+` modifier supplies the actual color,
drawn from the same semantic palette used throughout Bootstrap:

[source,html]
----
<button type="button" class="btn btn-primary">Primary</button>
<button type="button" class="btn btn-secondary">Secondary</button>
<button type="button" class="btn btn-success">Success</button>
<button type="button" class="btn btn-danger">Danger</button>
<button type="button" class="btn btn-warning">Warning</button>
<button type="button" class="btn btn-info">Info</button>
<button type="button" class="btn btn-light">Light</button>
<button type="button" class="btn btn-dark">Dark</button>
<button type="button" class="btn btn-link">Link</button>
----

A button is built from *multiple classes on one element*, each contributing independent declarations:
`.btn` supplies the base padding, border, and transition, `.btn-primary` the colors, and `.btn-lg` the larger
size:

[source,html]
----
<button type="button" class="btn btn-primary btn-lg">Large primary</button>
----

The classes depend on each other, so `+class="btn-primary"+` without `.btn` is not a button at all: in Bootstrap
5.3 a variant class only sets `+--bs-btn-*+` custom properties (`+--bs-btn-bg+`, `+--bs-btn-color+`, ...), and it is
the `.btn` rule that reads them, so the variant on its own has no visible effect. See xref:web/html-css/selectors-specificity.adoc#multiple-classes[Elements with multiple classes].

`.btn-link` renders with no background or border at all, styled to look like a plain hyperlink while keeping
the same padding/hover/focus behavior as every other button -- useful for a low-emphasis action that should not
visually compete with the primary action nearby.

An `<a>` styled as a button needs `role="button"` if its `href` doesn't actually navigate anywhere meaningful
(for example, `href="#"` paired with a JavaScript click handler), so assistive technology announces it as a
button rather than a link:

[source,html]
----
<a href="#" class="btn btn-primary" role="button">Link styled as a button</a>
----

== Outline buttons

Every solid color has a matching `+.btn-outline-*+` variant: transparent background, colored border and text,
filling in with the solid color only on hover/focus:

[source,html]
----
<button type="button" class="btn btn-outline-primary">Outline Primary</button>
<button type="button" class="btn btn-outline-danger">Outline Danger</button>
<button type="button" class="btn btn-outline-dark">Outline Dark</button>
----

Outline buttons are a common choice for a secondary action sitting next to a solid primary one -- "Cancel"
next to "Save", for instance -- since the pair reads as one primary and one lower-emphasis action without
needing a third, less standard color.

== Sizes

`.btn-lg` and `.btn-sm` scale a button up or down; the unmodified `.btn` is the default, medium size:

[source,html]
----
<button type="button" class="btn btn-primary btn-lg">Large button</button>
<button type="button" class="btn btn-primary">Default button</button>
<button type="button" class="btn btn-primary btn-sm">Small button</button>
----

Pairing `.btn-lg`/`.btn-sm` with `.w-100` (a width utility) produces a full-width button, common on mobile
forms and single-action cards:

[source,html]
----
<button type="button" class="btn btn-primary btn-lg w-100">Continue</button>
----

== States

=== Disabled

A `<button>` uses the native `disabled` attribute, which both blocks interaction and is announced correctly by
assistive technology. An `<a>` has no native `disabled` attribute, so the same visual effect there requires the
`.disabled` class *plus* `aria-disabled="true"` -- exactly the same pattern used for a disabled pagination link
(see xref:web/bootstrap/navigation-components.adoc[Navigation Components]):

[source,html]
----
<button type="button" class="btn btn-primary" disabled>Disabled button</button>

<a href="#" class="btn btn-primary disabled" aria-disabled="true" tabindex="-1">
  Disabled link
</a>
----

`tabindex="-1"` on the disabled link additionally removes it from the keyboard tab order -- without it, a
keyboard user could still focus a link that visually and functionally does nothing.

=== Active

`.active` forces a button to render in its pressed/active visual state regardless of actual interaction --
typically used to mark the currently selected button in a group of toggle-like buttons (see below), rather than
applied to an ordinary standalone button:

[source,html]
----
<button type="button" class="btn btn-primary active" aria-pressed="true">Active</button>
----

`aria-pressed="true"` communicates the same toggled state to assistive technology, since `.active` by itself is
purely a visual class with no accessibility semantics of its own.

=== Toggle buttons (checkbox/radio behavior)

A group of buttons can behave like a checkbox or radio group -- one or more pressed at a time -- by pairing
visually-hidden real `<input>` elements with `<label class="btn">` elements, so the underlying semantics stay
native even though the rendering is button-shaped:

[source,html]
----
<input type="checkbox" class="btn-check" id="option-1" autocomplete="off">
<label class="btn btn-outline-primary" for="option-1">Checkbox toggle</label>

<input type="radio" class="btn-check" name="options" id="option-a" autocomplete="off" checked>
<label class="btn btn-outline-primary" for="option-a">Radio A</label>
<input type="radio" class="btn-check" name="options" id="option-b" autocomplete="off">
<label class="btn btn-outline-primary" for="option-b">Radio B</label>
----

`.btn-check` visually hides the native input (rather than `display: none`, which would remove it from the tab
order) while keeping it fully operable by keyboard and screen reader -- the `<label>` only supplies the visual
button appearance.

== Grouping buttons

=== `.btn-group`

`.btn-group` visually joins a row of related buttons -- shared borders, no gap between them -- and wraps them
in a `role="group"` with a descriptive `aria-label` so assistive technology announces them as one coherent
control rather than a list of unrelated buttons:

[source,html]
----
<div class="btn-group" role="group" aria-label="Text alignment">
  <button type="button" class="btn btn-secondary">Left</button>
  <button type="button" class="btn btn-secondary">Center</button>
  <button type="button" class="btn btn-secondary">Right</button>
</div>
----

`.btn-group-lg`/`.btn-group-sm` on the wrapper size every button inside it at once, and `.btn-group-vertical`
stacks the group vertically instead of horizontally. Groups can also nest a dropdown (see
xref:web/bootstrap/interactive-components.adoc[Interactive Components]) as one of their members:

[source,html]
----
<div class="btn-group">
  <button type="button" class="btn btn-secondary">Save</button>
  <div class="btn-group">
    <button type="button" class="btn btn-secondary dropdown-toggle dropdown-toggle-split"
            data-bs-toggle="dropdown" aria-expanded="false">
      <span class="visually-hidden">Toggle Dropdown</span>
    </button>
    <ul class="dropdown-menu">
      <li><a class="dropdown-item" href="#">Save and continue</a></li>
      <li><a class="dropdown-item" href="#">Save as draft</a></li>
    </ul>
  </div>
</div>
----

=== `.btn-toolbar`

`.btn-toolbar` combines several separate `.btn-group` elements into one row -- a toolbar of distinct, unrelated
control clusters, each still announced individually by its own `role="group"`:

[source,html]
----
<div class="btn-toolbar" role="toolbar" aria-label="Toolbar with button groups">
  <div class="btn-group me-2" role="group" aria-label="First group">
    <button type="button" class="btn btn-secondary">1</button>
    <button type="button" class="btn btn-secondary">2</button>
  </div>
  <div class="btn-group me-2" role="group" aria-label="Second group">
    <button type="button" class="btn btn-secondary">3</button>
  </div>
  <div class="btn-group" role="group" aria-label="Third group">
    <button type="button" class="btn btn-secondary">4</button>
  </div>
</div>
----

`.me-2` between groups is an ordinary margin utility -- `.btn-toolbar` handles the flex layout of the groups
themselves, but spacing between them is applied the same way as anywhere else on the page.

== How a button is styled: the `+--bs-btn-*+` properties

In Bootstrap 5.3 a button is a bundle of CSS custom properties that one rule consumes. `.btn` declares the defaults
and the single rule that reads them; every variant, size and state only *reassigns* properties:

[mermaid]
....
flowchart TB
    BTN[".btn<br/>defaults: --bs-btn-padding-x, --bs-btn-bg,<br/>--bs-btn-color, --bs-btn-border-color, ..."]
    VARIANT[".btn-primary<br/>reassigns color, bg, border,<br/>hover, active and disabled values"]
    SIZE[".btn-lg or .btn-sm<br/>reassigns padding, font size, radius"]
    RULE["Rules for :hover, :focus-visible,<br/>:active, .active, :disabled"]
    RENDER["Rendered button"]

    BTN --> RENDER
    VARIANT --> RENDER
    SIZE --> RENDER
    RULE -->|"read the hover, active and<br/>disabled variants of each property"| RENDER

    classDef core fill:#3f51b5,stroke:#1a237e,color:#fff
    class BTN core
....

This design has a practical payoff: a single button can be restyled with an inline `style` or a project class and no
`!important`, because only the property values change, not the selector's specificity:

[source,html]
----
<button type="button" class="btn btn-primary"
        style="--bs-btn-padding-y: .25rem; --bs-btn-padding-x: .5rem; --bs-btn-font-size: .75rem">
  Extra small
</button>
----

== Worked example: the Taskboard action bar

The Taskboard task editor ends in an action bar: a primary Save button that shows progress while the request is in
flight, a secondary Cancel, a destructive Delete pushed to the far end, and a toggle for pinning the task. The markup
combines most of what this page has covered:

[source,html]
----
<div class="d-flex flex-wrap align-items-center gap-2">
  <button id="save" type="button" class="btn btn-primary">
    <span class="spinner-border spinner-border-sm d-none" aria-hidden="true"></span>
    <span class="btn-label">Save</span>
  </button>
  <button type="button" class="btn btn-outline-secondary">Cancel</button>

  <button type="button" class="btn btn-outline-primary" data-bs-toggle="button" aria-pressed="false">
    Pin task
  </button>

  <button type="button" class="btn btn-outline-danger ms-auto">Delete</button>
</div>
----

`.ms-auto` on the last button absorbs the free space in the flex row and pushes Delete to the end, which separates the
destructive action from the safe ones without any extra markup. `data-bs-toggle="button"` is Bootstrap's Button
plugin: each click toggles the `.active` class *and* flips `aria-pressed`, so a toggle button's state is exposed to
assistive technology without any project code. (A real `<input type="checkbox" class="btn-check">` is still the
better choice when the toggle is part of a form that is submitted.)

The Save button's progress behavior is project code. This version keeps the state changes in one function and
handles both outcomes of the request:

[source,javascript]
----
function setBusy(button, busy, label) {
  button.disabled = busy;
  button.setAttribute("aria-busy", String(busy));
  button.querySelector(".spinner-border").classList.toggle("d-none", !busy);
  button.querySelector(".btn-label").textContent = label;
}

async function save(button, request) {
  setBusy(button, true, "Saving…");
  try {
    await request();
    setBusy(button, false, "Saved");
  } catch (error) {
    setBusy(button, false, "Retry");
  }
}

document.querySelector("#save").addEventListener("click", (event) =>
  save(event.currentTarget, () => fetch("/api/tasks/42", { method: "PUT", body: JSON.stringify({ title: "..." }) })));
----

The three states were exercised in a DOM test (the `save` function with a request that resolves after a delay and
one that rejects): while the request runs the button is disabled with `aria-busy="true"` and the spinner is visible;
after success it is enabled again, labelled "Saved"; after a failure it is enabled again, labelled "Retry". The
`fetch` call itself was not run against a server.

[mermaid]
....
stateDiagram-v2
    [*] --> Idle
    Idle --> Busy : click
    Busy --> Saved : request resolves
    Busy --> Retry : request rejects
    Saved --> Busy : click
    Retry --> Busy : click
    Busy : disabled, spinner visible, aria-busy true
    Idle : label Save
    Saved : label Saved, enabled
    Retry : label Retry, enabled
....

Two accessibility cautions apply to this pattern. Setting `disabled` on the button that currently has keyboard focus
makes some browsers drop focus to the document, so a keyboard user loses their place; a common alternative is to keep
the button enabled, set `aria-disabled="true"`, and ignore clicks while busy. And because the spinner is
`aria-hidden`, the changing label is what carries the state: pair it with a visually hidden `role="status"` region if
the change must be announced to a screen reader.

== Full-width and stacked buttons

Bootstrap 4's `.btn-block` no longer exists. A stack of full-width buttons is a grid container instead:

[source,html]
----
<div class="d-grid gap-2">
  <button class="btn btn-primary" type="button">Create task</button>
  <button class="btn btn-outline-secondary" type="button">Import from file</button>
</div>
----

`.d-grid` stretches the children to the container's width and `.gap-2` spaces them, and a responsive form such as
`d-grid d-md-block` makes the buttons full width on phones and natural width from `md` upward. The earlier `.w-100`
example does the same for a single button.

== Creating your own button variant in Sass

Adding a color to `$theme-colors` creates `+.btn-{name}+` automatically (see
xref:web/bootstrap/colors.adoc[Colors]). A one-off variant that is not a theme color uses the same mixins Bootstrap
uses internally. This compiled with Bootstrap 5.3.3:

[source,scss]
----
@import "bootstrap/scss/functions";
@import "bootstrap/scss/variables";
@import "bootstrap/scss/variables-dark";
@import "bootstrap/scss/maps";
@import "bootstrap/scss/mixins";
@import "bootstrap/scss/root";
@import "bootstrap/scss/buttons";

$archive: #5f6b7a;
.btn-archive         { @include button-variant($archive, $archive); }
.btn-outline-archive { @include button-outline-variant($archive); }
.btn-xs              { @include button-size(.125rem, .5rem, .75rem, var(--bs-border-radius-sm)); }
----

`button-variant()` produces the whole property bundle for a solid button: `--bs-btn-color` is chosen with
`color-contrast()` (white here), the hover and active backgrounds are darkened automatically, and the disabled values
repeat the base colors. `button-size()` only reassigns the four size properties, which is why the compiled `.btn-xs`
is four lines long. The classes combine with `.btn` exactly like the built-in ones: `class="btn btn-archive btn-xs"`.

See https://getbootstrap.com/docs/5.3/components/buttons/[the official Buttons docs] and
https://getbootstrap.com/docs/5.3/components/button-group/[the official Button Group docs] for the complete
option reference.
