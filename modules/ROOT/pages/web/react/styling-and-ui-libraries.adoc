= Styling and UI Libraries
:description: Styling options for React from plain CSS and CSS Modules to Tailwind, CSS-in-JS and vanilla-extract, theming and dark mode with CSS variables, component libraries such as MUI, Ant Design, Chakra UI, PrimeReact, gluestack and Radix with a layout example, and accessibility of interactive components.

React does not have an opinion on styling -- any approach that produces class names or style rules works. This
page surveys the common options and the main component libraries.

== Styling options

* **Plain CSS / CSS Modules.** Import a stylesheet, or a `+*.module.css+` file whose class names are locally
  scoped and hashed:
+
[source,jsx]
----
import styles from './Card.module.css';
export function Card() {
  return <div className={styles.card}>…</div>;
}
----
+
Zero runtime, works everywhere including Server Components (see
xref:web/nextjs/styling.adoc[Next.js Styling] for the Server Component constraints). See xref:web/html-css/index.adoc[HTML & CSS
Reference] and, for a preprocessor, xref:web/sass/index.adoc[Sass Reference].

* **https://tailwindcss.com/[Tailwind CSS].** Utility classes in `className`; styling stays in the markup and
  the build strips unused classes.
+
[source,jsx]
----
<button className="rounded bg-blue-600 px-4 py-2 text-white hover:bg-blue-700">Save</button>
----

* **CSS-in-JS (https://styled-components.com/[styled-components],
  https://emotion.sh/[Emotion]).** Write styles as tagged template literals colocated with the component.
  Note the **runtime cost** (styles are generated in the browser) and that a styled component is a Client
  Component -- it needs `+'use client'+` and cannot be used directly in a Server Component
  (see xref:web/nextjs/styling.adoc[Next.js Styling]).

* **https://vanilla-extract.style/[vanilla-extract].** CSS-in-TypeScript that compiles to static `.css` files
  at build -- type safety with no runtime.

* **Inline `style`.** A camelCased object; fine for one-off dynamic values (`+style={{ width: pct + '%' }}+`),
  not for whole design systems (no media queries, no pseudo-classes).

== Choosing a styling approach

[cols="2,3,3",options="header"]
|===
| Approach | Scoping | Cost and constraints

| Plain CSS
| Global; you manage names (BEM and similar conventions)
| Zero runtime; collisions grow with the codebase.

| CSS Modules
| Class names hashed per file at build time
| Zero runtime; works with Server Components; dynamic values need CSS variables or inline `style`.

| Utility classes (Tailwind)
| No scoping needed: classes are single-purpose
| Zero runtime; styles live in the markup; build step scans files for class names.

| CSS-in-JS (styled-components, Emotion)
| Generated class per component
| Runtime cost; Client Components only; needs SSR style collection.

| Compile-time CSS-in-TS (vanilla-extract)
| Generated class per style
| Zero runtime, typed tokens; extra build integration.
|===

Most new apps pick one primary approach (often CSS Modules or Tailwind) and add a component library only when
the product needs ready-made complex widgets. The sections below build the same product card and the same
dark-mode support with each tool and show how it behaves.

== CSS Modules in practice

A file named `Something.module.css` is processed so that every class name is rewritten to a unique one, and the
import is an object mapping your names to the generated ones. Two components can both define `.title` without
colliding. `clsx` joins class names conditionally, which is how a modifier such as "sold out" is applied:

[source,css]
----
/* ProductCard.module.css */
.card {
  padding: var(--space-2);
  border-radius: var(--radius);
  border: 1px solid color-mix(in srgb, var(--color-text) 20%, transparent);
}
.soldOut { opacity: 0.6; }
.title { color: var(--color-accent); }
----

[source,tsx]
----
import clsx from 'clsx';
import styles from './ProductCard.module.css';

interface Props { name: string; soldOut?: boolean; className?: string }

export function ProductCard({ name, soldOut = false, className }: Props) {
  return (
    <article className={clsx(styles.card, soldOut && styles.soldOut, className)}>
      <h2 className={styles.title}>{name}</h2>
      {soldOut && <p>Sold out</p>}
    </article>
  );
}
----

Rendered with `soldOut` and an extra `className="extra"`, the element's class list contains generated names for
`card` and `soldOut` (they look like `+_card_1x2y3+`, with a hash) plus the literal `extra`, which is what a test
can assert. Accepting an optional `className` prop and merging it is the convention that lets a parent adjust
the margin or width of a component without reaching into its styles. In TypeScript, the
`vite/client` types declare `+*.module.css+` imports, so `styles.card` is typed. The `+var(--...)+` references
come from design tokens, covered next.

== Design tokens and theming with CSS variables

A theme is a set of named values (colors, spacing, radii) that components reference instead of hard-coding.
CSS custom properties are the simplest implementation, because the browser re-resolves them when the value
changes, with no React re-render:

[source,css]
----
/* tokens.css */
:root {
  --color-bg: #ffffff;
  --color-text: #1b1b1f;
  --color-accent: #0b5fff;
  --space-2: 0.5rem;
  --radius: 0.5rem;
}
:root[data-theme='dark'] {
  --color-bg: #121214;
  --color-text: #ececf1;
  --color-accent: #7aa2ff;
}
@media (prefers-color-scheme: dark) {
  :root:not([data-theme='light']) {
    --color-bg: #121214;
    --color-text: #ececf1;
    --color-accent: #7aa2ff;
  }
}
body { background: var(--color-bg); color: var(--color-text); }
----

The cascade gives three states for free: with no `data-theme` attribute the user's operating-system preference
decides (the media query); `data-theme="dark"` or `"light"` set explicitly override it. React's only job is to
set the attribute and remember the choice:

[source,tsx]
----
import { createContext, useContext, useEffect, useState, type ReactNode } from 'react';

type Theme = 'light' | 'dark' | 'system';
const ThemeContext = createContext<{ theme: Theme; setTheme: (t: Theme) => void } | null>(null);

function readStored(): Theme {
  try {
    const v = localStorage.getItem('theme');
    return v === 'light' || v === 'dark' ? v : 'system';
  } catch {
    return 'system';                 // storage can be blocked (private mode, sandboxed iframes)
  }
}

export function ThemeProvider({ children }: { children: ReactNode }) {
  const [theme, setTheme] = useState<Theme>(readStored);

  useEffect(() => {
    const root = document.documentElement;
    if (theme === 'system') root.removeAttribute('data-theme');   // let prefers-color-scheme decide
    else root.setAttribute('data-theme', theme);
    try { localStorage.setItem('theme', theme); } catch { /* ignore */ }
  }, [theme]);

  return <ThemeContext value={{ theme, setTheme }}>{children}</ThemeContext>;
}

export function useTheme() {
  const ctx = useContext(ThemeContext);
  if (!ctx) throw new Error('useTheme must be used inside <ThemeProvider>');
  return ctx;
}

export function ThemeSwitch() {
  const { theme, setTheme } = useTheme();
  return (
    <label>
      Theme
      <select value={theme} onChange={(e) => setTheme(e.target.value as Theme)}>
        <option value="system">System</option>
        <option value="light">Light</option>
        <option value="dark">Dark</option>
      </select>
    </label>
  );
}
----

[mermaid]
....
flowchart TD
    A["User picks a theme in ThemeSwitch"] --> B{"Which value?"}
    B -->|"light or dark"| C["Effect sets data-theme on html"]
    B -->|"system"| D["Effect removes data-theme"]
    C --> E["CSS variables for that theme apply"]
    D --> F{"prefers-color-scheme"}
    F -->|"dark"| E2["Dark variables apply via the media query"]
    F -->|"light"| E3["Default light variables apply"]
    C --> G["localStorage keeps the choice"]
    D --> G
....

Selecting "Dark" in the switch sets `data-theme="dark"` on `<html>` and stores `dark` in `localStorage`;
choosing "System" removes the attribute again. Both storage calls are wrapped in `try`/`catch` because
`localStorage` can throw (blocked storage, some embedded browsers). One limitation: an Effect runs after the
first paint, so a page that was rendered in light mode may flash before the stored dark theme is applied. Fix it
by setting the attribute before React starts, with a tiny inline script in `index.html` (or the server-rendered
document) that reads the stored value and sets `data-theme` synchronously, and keep the React code as the
source of truth afterwards.

== Tailwind CSS: utilities and a theme

Tailwind generates CSS from the class names it finds in your source files, so only used utilities are emitted.
With Tailwind 4 and Vite the setup is one plugin and one CSS import; design tokens are declared in an `@theme`
block and automatically become utilities:

[source,ts]
----
// vite.config.ts
import { defineConfig } from 'vite';
import react from '@vitejs/plugin-react';
import tailwindcss from '@tailwindcss/vite';

export default defineConfig({ plugins: [react(), tailwindcss()] });
----

[source,css]
----
/* src/index.css, imported once from main.tsx */
@import 'tailwindcss';

@theme {
  --color-brand: #0b5fff;
}
----

[source,tsx]
----
export const Btn = () => (
  <button className="rounded bg-brand px-4 py-2 text-white hover:bg-blue-700">Save</button>
);
----

Building this app produces a stylesheet that contains `+.bg-brand{background-color:var(--color-brand)}+` and the
`hover:` variant for `bg-blue-700`, and does not contain utilities nobody used (a search for `bg-red-500` finds
nothing). Two rules follow from "the scanner finds class names": write complete class names in the source
(`+'bg-red-500'+`), because a name assembled at run time such as `+bg-${color}-500+` is never found; and for a
value that really is dynamic, use a CSS variable or the inline `style` prop.

== Component libraries

Each ships ready-made, accessible components so you are not rebuilding dialogs, menus and data tables by hand.
Most provide a **theme** (design tokens for color, spacing, typography, dark mode) applied via a provider at
the app root, plus responsive-layout primitives. The usual flow is: install the package, wrap the app in the
library's provider (where it has one), then use its components.

* **https://mui.com/[MUI]** -- a large Material Design implementation with a powerful theming system
  (`ThemeProvider` + `createTheme`) and companion packages for icons, data grids and date pickers.
+
[source,jsx]
----
import { Button } from '@mui/material';

<Button variant="contained" onClick={save}>Save</Button>
----

* **https://ant.design/[Ant Design]** -- a comprehensive, enterprise-oriented set (rich `Form`, `Table`,
  `DatePicker`); theming via a `ConfigProvider` and design tokens.
+
[source,jsx]
----
import { Button } from 'antd';

<Button type="primary" onClick={save}>Save</Button>
----

* **https://chakra-ui.com/[Chakra UI]** -- a style-props API with accessible defaults: you pass style and
  layout as props rather than writing separate CSS.
+
[source,jsx]
----
import { Button } from '@chakra-ui/react';

<Button colorScheme="blue" px={4} onClick={save}>Save</Button>
----

* **https://primereact.org/[PrimeReact]** -- a very large suite (~90 components including `DataTable`,
  charts and pickers) with several ready-made themes switched via a CSS import or the `PrimeReactProvider`.
+
[source,jsx]
----
import { Button } from 'primereact/button';

<Button label="Save" icon="pi pi-check" onClick={save} />
----

* **https://gluestack.io/[gluestack UI]** -- a fully **open-source**, copy-in library (universal React and
  React Native) built on utility styling: `npx gluestack-ui add button` drops the component source into your
  project, so you own and can edit it. Wrap the app in `GluestackUIProvider`. For styling on the native side,
see xref:apps/react-native/styling.adoc[Styling] in the React Native section.
+
[source,jsx]
----
import { Button, ButtonText } from '@/components/ui/button';

<Button onPress={save}><ButtonText>Save</ButtonText></Button>
----

* **https://www.radix-ui.com/primitives[Radix Primitives]** -- unstyled, accessible behavior primitives
  (dialog, menu, popover, tabs) that ship the interaction and ARIA wiring and leave all styling to you.
  https://ui.shadcn.com/[shadcn/ui] is a popular set of Tailwind-styled components built on Radix that you
  copy into your project rather than install as a dependency.
+
[source,jsx]
----
import * as Dialog from '@radix-ui/react-dialog';

<Dialog.Root>
  <Dialog.Trigger>Open</Dialog.Trigger>
  <Dialog.Portal>
    <Dialog.Overlay className="overlay" />
    <Dialog.Content className="modal">
      <Dialog.Title>Confirm</Dialog.Title>
      <Dialog.Close>Cancel</Dialog.Close>
    </Dialog.Content>
  </Dialog.Portal>
</Dialog.Root>
----

=== A layout, navigation and input with MUI

A component library earns its place on layout, navigation and form controls. The sketch below builds a shop
page with an app bar, a responsive card grid and a search field, with theme-wide defaults declared once in
`createTheme`:

[source,tsx]
----
import { useState } from 'react';
import {
  AppBar, Box, Button, Card, CardContent, Container, CssBaseline, Stack, TextField,
  ThemeProvider, Toolbar, Typography, createTheme,
} from '@mui/material';

const theme = createTheme({
  palette: { primary: { main: '#0b5fff' } },
  shape: { borderRadius: 8 },
  components: { MuiButton: { defaultProps: { disableElevation: true } } },   // theme-wide defaults, no per-use props
});

export function MuiShop({ names }: { names: string[] }) {
  const [query, setQuery] = useState('');
  const shown = names.filter((n) => n.toLowerCase().includes(query.toLowerCase()));
  return (
    <ThemeProvider theme={theme}>
      <CssBaseline />
      <AppBar position="static">
        <Toolbar><Typography variant="h6" component="h1">Shop</Typography></Toolbar>
      </AppBar>
      <Container maxWidth="md" sx={{ py: 3 }}>
        <TextField label="Search" value={query} onChange={(e) => setQuery(e.target.value)} fullWidth />
        <Box sx={{ display: 'grid', gap: 2, mt: 2, gridTemplateColumns: { xs: '1fr', sm: 'repeat(2, 1fr)' } }}>
          {shown.map((n) => (
            <Card key={n}>
              <CardContent>
                <Stack direction="row" sx={{ justifyContent: 'space-between', alignItems: 'center' }}>
                  <Typography>{n}</Typography>
                  <Button variant="contained">Add</Button>
                </Stack>
              </CardContent>
            </Card>
          ))}
        </Box>
      </Container>
    </ThemeProvider>
  );
}
----

* **Layout and organization.** `Container` constrains the content width, `Box` with `sx` expresses a CSS grid
  whose column count changes at the `sm` breakpoint (one column on phones, two from tablets up), and `Stack`
  lays children out in a row or column with consistent spacing.
* **Navigation.** `AppBar` and `Toolbar` form the top bar; MUI also provides `Tabs`, `Drawer` and `Breadcrumbs`,
  which you connect to the router with `+component={Link}+` so that a click changes the URL rather than reloading
  the page (see xref:web/react/routing.adoc[Routing]).
* **Collecting input.** `TextField` renders a label, an input and helper text with the right ARIA wiring; passing
  `value` and `onChange` makes it a controlled input, as for a native element.
* **Styles and themes.** `ThemeProvider` makes the theme available to every MUI component below it, and the
  `sx` prop reads theme values (spacing units, breakpoints, palette) so one-off adjustments stay consistent.
  `CssBaseline` normalizes browser defaults. Per-component defaults in `createTheme` (the `Button` above)
  remove repeated props.

The test renders the page, finds both "Add" buttons by role, types `gad` into the field and asserts that only
one remains, which verifies the filtering through the library's real DOM.

== Accessibility

A component library gives you accessible primitives, but you still own the wiring: label every control,
manage focus in dialogs and menus, respect `prefers-reduced-motion`, and test with a keyboard and a screen
reader. `useId` generates stable ids to connect a label, a field, and its `aria-describedby` error text:

[source,jsx]
----
function Field({ label, error }) {
  const id = useId();
  return (
    <>
      <label htmlFor={id}>{label}</label>
      <input id={id} aria-invalid={!!error} aria-describedby={error ? `${id}-err` : undefined} />
      {error && <p id={`${id}-err`} role="alert">{error}</p>}
    </>
  );
}
----

=== Keyboard focus and motion

Whatever styling approach you choose, three rules keep an interface usable: never remove the focus outline
without replacing it with an equally visible one; keep text contrast at or above the WCAG minimum in every
theme; and honour the user's motion preference:

[source,css]
----
:focus-visible { outline: 2px solid var(--color-accent); outline-offset: 2px; }

@media (prefers-reduced-motion: reduce) {
  *, *::before, *::after { animation-duration: 0.01ms !important; transition-duration: 0.01ms !important; }
}
----

`:focus-visible` shows the ring for keyboard users but not for most mouse clicks, which removes the usual
reason for deleting outlines.

See xref:web/accessibility.adoc[Web Accessibility] for the conformance levels and validation tools.
