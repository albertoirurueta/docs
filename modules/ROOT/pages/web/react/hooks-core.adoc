= Core Hooks and the Rules of Hooks
:description: The Rules of Hooks and why they exist, useState versus useReducer, useRef and useId for non-rendering values and stable ids, and a reference table of every built-in React Hook.
:keywords: Rules of Hooks, eslint-plugin-react-hooks, useState, useReducer, reducer, dispatch, useRef, useId, useDebugValue, built-in Hooks table, React Hooks reference

include::partial$ai-disclaimer.adoc[]

Hooks are functions whose name starts with `use` that let a function component "hook into" React features --
state, context, refs, effects, and more. This page covers the rules that govern all Hooks and the core state
Hooks; the others have their own pages.

== The Rules of Hooks

. **Only call Hooks at the top level.** Not inside conditions, loops, nested functions, or after an early
  `return`. React identifies each Hook by its **call order**, which must be identical on every render.
. **Only call Hooks from React functions.** From a component body or from another custom Hook -- never from a
  plain function or an event handler.

[source,jsx]
----
function Profile({ id }) {
  const [user, setUser] = useState(null);   // OK: top level

  if (!id) return null;                      // early return AFTER all Hooks

  // const [x] = useState(0);                // BUG: Hook after a conditional return
}
----

The `eslint-plugin-react-hooks` plugin (in the default Vite React template) flags violations and checks Effect
dependency arrays. See https://react.dev/reference/rules/rules-of-hooks[Rules of Hooks].

== `useState` vs. `useReducer`

Reach for `useReducer` when state updates are complex, involve several sub-values, or the "next state" logic is
worth testing in isolation. A **reducer** is a pure function `+(state, action) => nextState+`.

[source,jsx]
----
import { useReducer } from 'react';

function reducer(state, action) {
  switch (action.type) {
    case 'increment': return { count: state.count + 1 };
    case 'set':       return { count: action.value };
    default:          throw new Error('unknown action: ' + action.type);
  }
}

function Counter() {
  const [state, dispatch] = useReducer(reducer, { count: 0 });
  return (
    <button onClick={() => dispatch({ type: 'increment' })}>{state.count}</button>
  );
}
----

References: https://react.dev/reference/react/useState[`useState`],
https://react.dev/reference/react/useReducer[`useReducer`],
https://react.dev/learn/extracting-state-logic-into-a-reducer[Extracting State Logic into a Reducer].

== `useRef` and `useId`

`useRef` holds a mutable value in `.current` that **persists across renders and does not trigger one** when it
changes -- a timer id, a previous value, or a DOM node (full DOM treatment on
xref:web/react/refs-and-the-dom.adoc[Refs and the DOM]).

[source,jsx]
----
function Timer() {
  const timerRef = useRef(null);          // { current: null }, survives re-renders

  function start() {
    timerRef.current = setInterval(tick, 1000);   // writing .current does NOT re-render
  }
  function stop() {
    clearInterval(timerRef.current);
  }
  // ...
}
----

Read or write `ref.current` only in event handlers or Effects, never during render -- doing it in the
component body makes render impure (see xref:web/react/rules-of-react.adoc[The Rules of React]).

`useId` generates a stable, unique string id for accessibility attributes, consistent between server and
client -- never use it for list keys.

[source,jsx]
----
function Field() {
  const id = useId();
  return (
    <>
      <label htmlFor={id}>Email</label>
      <input id={id} type="email" />
    </>
  );
}
----

`useDebugValue` labels a custom Hook in React DevTools. References:
https://react.dev/reference/react/useRef[`useRef`], https://react.dev/reference/react/useId[`useId`].

== Deep dive: why the order of Hooks matters

React does not know the *names* of your state variables. Each component instance keeps a list of "Hook slots", and the
n-th call to a Hook during a render reads the n-th slot. That is why the rules insist on an identical call order.

[mermaid]
....
flowchart LR
    subgraph first["First render"]
        a1["slot 1: useState (qty)"] --> a2["slot 2: useState (note)"] --> a3["slot 3: useEffect"]
    end
    subgraph second["Next render: same order"]
        b1["slot 1 reads qty"] --> b2["slot 2 reads note"] --> b3["slot 3 compares deps"]
    end
    a1 -.-> b1
    a2 -.-> b2
    a3 -.-> b3
....

If a Hook is skipped on one render, every later Hook would read the wrong slot. React detects the most obvious
form of this and throws:

[source,jsx]
----
function Bad({ show }) {
  if (show) { useState(0); }   // conditional Hook
  useState(1);
  return <p>x</p>;
}
// render <Bad show={false} />, then <Bad show={true} />:
// Error: Rendered more hooks than during the previous render.
----

When you need a condition, put it *inside* the Hook (`+useEffect(() => { if (cond) ... })+`) or move the conditional
part into a child component that always calls the same Hooks.

== Deep dive: a shopping cart with `useReducer`

The cart of the running example has several operations (add, remove, clear), and each must preserve the rest of the
state. A reducer centralizes that logic in one pure function.

[source,jsx]
----
import { useReducer } from 'react';

export function cartReducer(state, action) {
  switch (action.type) {
    case 'added': {
      const found = state.items.find((i) => i.id === action.product.id);
      const items = found
        ? state.items.map((i) => (i.id === found.id ? { ...i, qty: i.qty + 1 } : i))
        : [...state.items, { ...action.product, qty: 1 }];
      return { ...state, items };
    }
    case 'removed':
      return { ...state, items: state.items.filter((i) => i.id !== action.id) };
    case 'cleared':
      return { ...state, items: [] };
    default:
      throw new Error('Unknown action: ' + action.type);
  }
}

export const initialCart = { items: [] };

function CartView({ products }) {
  const [state, dispatch] = useReducer(cartReducer, initialCart);
  const total = state.items.reduce((sum, i) => sum + i.price * i.qty, 0);
  return (
    <div>
      {products.map((p) => (
        <button key={p.id} onClick={() => dispatch({ type: 'added', product: p })}>{p.name}</button>
      ))}
      <ul>{state.items.map((i) => <li key={i.id}>{i.name} x{i.qty}</li>)}</ul>
      <output>{total.toFixed(2)}</output>
      <button onClick={() => dispatch({ type: 'cleared' })}>clear</button>
    </div>
  );
}
----

The reducer is a plain function, so it needs no React to be tested:

[source,jsx]
----
import assert from 'node:assert/strict';

const kb = { id: 'kb', name: 'Keyboard', price: 49.9 };
let s = cartReducer(initialCart, { type: 'added', product: kb });
s = cartReducer(s, { type: 'added', product: kb });

assert.equal(s.items[0].qty, 2);                                    // quantity merged
assert.notEqual(s, initialCart);                                    // new object returned
assert.deepEqual(initialCart, { items: [] });                       // input not mutated
assert.deepEqual(cartReducer(s, { type: 'removed', id: 'kb' }).items, []);
assert.throws(() => cartReducer(s, { type: 'oops' }), /Unknown action/);
----

Rendering `CartView` with a keyboard (49.90) and a mouse (19.50), then clicking *Keyboard* twice and *Mouse* once,
shows `Keyboard x2`, `Mouse x1` and a total of `119.30`; *clear* returns an empty list and `0.00`.

=== `useState` or `useReducer`?

[cols="1,1,1",options="header"]
|===
| Criterion | `useState` | `useReducer`

| Number of related values | One or two independent values | Several values that change together
| Update logic | Inline in handlers | Named actions in one function
| Testing | Through the component | The reducer alone, without React
| Passing updates down | Pass setters (often several) | Pass a single stable `dispatch`
| Debugging | Inspect values | Log every action
|===

`dispatch` has a stable identity across renders, which makes it convenient to put in context
(see xref:web/react/state-management.adoc[State Management]). Reducers must be pure, so `<StrictMode>` calls them
twice in development: a reducer that mutates its input or reads the clock will show the problem immediately.

== Deep dive: `useRef`, `useId` and server rendering

A ref is the right place for a value that must survive renders but must not *cause* one, such as an interval id. If
changing the value should update the screen, it belongs in state instead. A quick test: "does anything displayed
depend on this?" -- if yes, state; if no, a ref.

`useId` returns an opaque string that is stable for a component instance and identical on the server and in the
browser, so hydration does not report an attribute mismatch the way `Math.random()` or a module-level counter would.
Rendering two `<Field />` components on the server produces two different ids, and each `<label for>` matches the
`<input id>` next to it. Call `useId` once per component and derive related ids by suffix (`pass:c[id + '-error']`); never
use the result as a list `key` or in a CSS selector, since it contains characters that need escaping.
