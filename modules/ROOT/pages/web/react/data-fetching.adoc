= Data Fetching
:description: Fetching data in React, from fetch in an Effect and its problems to axios, TanStack Query and SWR for caching and revalidation, GraphQL clients, and framework data loading.
:keywords: React data fetching, fetch in useEffect, request waterfall, race condition, axios, TanStack Query, useQuery, SWR, RTK Query, GraphQL, Apollo, Server Components data loading

include::partial$react-disclaimer.adoc[]

React does not prescribe how you fetch data. The options range from a bare `fetch` in an Effect to a
purpose-built caching library to framework-level loading. For a real app, use a library or a framework.

== `fetch` in an Effect: the baseline

[source,jsx]
----
function Product({ id }) {
  const [product, setProduct] = useState(null);
  const [error, setError] = useState(null);

  useEffect(() => {
    let ignore = false;
    fetch(`/api/products/${id}`)
      .then((r) => { if (!r.ok) throw new Error(r.status); return r.json(); })
      .then((data) => { if (!ignore) setProduct(data); })
      .catch((e) => { if (!ignore) setError(e); });
    return () => { ignore = true; };
  }, [id]);

  if (error) return <p role="alert">Failed to load.</p>;
  if (!product) return <Spinner />;
  return <ProductView product={product} />;
}
----

Its problems: **request waterfalls** (child fetches only start after the parent renders), **race conditions**
(handled here with the `ignore` flag or an `AbortController`), **no cache** (every mount refetches), and no
shared loading/error conventions. See xref:web/react/effects.adoc[Effects] for the Effect mechanics,
xref:web/javascript/browser-networking.adoc[Networking] for `fetch` itself, and -- for cross-origin requests
-- xref:web/cors.adoc[What is CORS?].

== axios and server-state libraries

https://axios-http.com/[axios] is a small HTTP client with interceptors, automatic JSON, and a terser API
than `fetch`; it does not solve caching or races.

**https://tanstack.com/query[TanStack Query]** (and https://swr.vercel.app/[SWR], and
https://redux-toolkit.js.org/rtk-query/overview[RTK Query]) treat server data as a **cache**: they
deduplicate concurrent requests, cache by key, revalidate in the background (on focus, on reconnect, on
interval), and expose mutations with cache invalidation.

[source,jsx]
----
import { useQuery } from '@tanstack/react-query';

function Product({ id }) {
  const { data, isPending, error } = useQuery({
    queryKey: ['product', id],
    queryFn: () => fetch(`/api/products/${id}`).then((r) => r.json()),
    staleTime: 60_000,
  });

  if (isPending) return <Spinner />;
  if (error) return <p role="alert">Failed to load.</p>;
  return <ProductView product={data} />;
}
----

== GraphQL and framework loading

For GraphQL APIs, a client such as https://www.apollographql.com/docs/react/[Apollo Client],
https://commerce.nearform.com/open-source/urql/[urql], or https://relay.dev/[Relay] provides the query cache
and normalized store equivalent to the above.

The modern answer for many apps is to fetch **on the server**: a framework route loader or a React
xref:web/react/server-rendering.adoc[Server Component] fetches data before render, eliminating the client
waterfall and shipping less JavaScript.
