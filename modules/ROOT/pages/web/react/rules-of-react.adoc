= The Rules of React
:description: The rules every React component and Hook must follow: purity and idempotency, no side effects in render, immutable props and state, letting React call your components and Hooks, and the Rules of Hooks.
:keywords: Rules of React, pure component, idempotent, side effects in render, immutable props, immutable state, React calls components, Rules of Hooks, component identity, key prop

include::partial$ai-disclaimer.adoc[]

React assumes your code follows a small set of rules. Break them and you get subtle bugs -- stale UI, lost
state, crashes -- that also defeat the xref:web/react/performance.adoc[React Compiler] and concurrent
features. The https://react.dev/reference/rules[Rules of React] are the contract.

== Components and Hooks must be pure

* **Idempotent** -- given the same props, state, and context, a component returns the same JSX every time.
* **No side effects in render** -- no network calls, no timers, no DOM mutation, no writing to external
  variables while rendering. Side effects go in event handlers or xref:web/react/effects.adoc[Effects].
* **Props and state are immutable** -- never mutate them. Create new objects/arrays and set state instead.
* **Do not mutate values after passing them to JSX** -- once you have used a value in returned JSX, treat it
  as frozen; mutating it afterward can produce inconsistent rendering.

[source,jsx]
----
function Cart({ items }) {
  items.sort((a, b) => a.price - b.price);   // BUG: mutates a prop during render
  const sorted = [...items].sort((a, b) => a.price - b.price);  // OK: a copy
  return <List items={sorted} />;
}
----

See https://react.dev/reference/rules/components-and-hooks-must-be-pure[Components and Hooks must be pure].

== React calls your components and Hooks

* **Never call a component as a plain function.** Render it as JSX (`<Row />`), not `Row()`. Calling it
  directly breaks Hook state, context, and the rules of the reconciler.
* **Never pass a Hook around as a value.** Call Hooks directly by name at the top level of a component or
  custom Hook; do not store one in a variable, pass it as a prop, or call it conditionally.

[source,jsx]
----
function Table({ rows }) {
  return <tbody>{rows.map((r) => <Row key={r.id} row={r} />)}</tbody>;  // JSX, not Row(r)
}
----

See https://react.dev/reference/rules/react-calls-components-and-hooks[React calls Components and Hooks].

== The Rules of Hooks

Call Hooks only at the **top level** of a React function -- not in conditions, loops, or nested functions --
and only from **React functions** (components or custom Hooks). React tracks Hooks by call order, so that
order must be identical on every render. Full detail on xref:web/react/hooks-core.adoc[Core Hooks and the
Rules of Hooks].

Related: a component's identity -- and therefore its state -- is tied to its **position in the render tree**.
The `key` prop overrides position-based identity so you can force React to treat an element as new (reset its
state) or preserve it across reorders. See https://react.dev/reference/rules/rules-of-hooks[Rules of Hooks] and
xref:web/react/state-management.adoc[State Management] for preserving and resetting state.

== Deep dive: why the rules exist

Every rule on this page protects one capability React relies on. React may call your component more than once, skip
it, pause it, throw the result away, or render it before it is needed. That is only safe if rendering is a pure
calculation.

[cols="2,3",options="header"]
|===
| React behavior | Rule it depends on

| Renders a component twice in `<StrictMode>` to detect impurity | Idempotent render, no side effects
| Interrupts and restarts a render for urgent updates (transitions, `Suspense`) | Render has no externally visible effects
| Skips re-rendering a subtree whose props did not change (`memo`, the React Compiler) | Props and state are never mutated
| Preserves state between renders by call order | Hooks at the top level, in the same order
| Decides *when* each component renders | Never call components as plain functions
|===

== Deep dive: breaking each rule, observed

The effects of a rule violation are easiest to understand by running one. All the results below come from rendering
the snippets with React 19.

*Impure render.* A component that takes the next id from a module-level counter looks harmless:

[source,jsx]
----
let nextId = 0;
function OrderNumber() {
  const id = ++nextId;                 // reads and writes state outside the component
  return <p>Order #{id}</p>;
}
----

Rendered once inside `<StrictMode>`, the counter reaches `2` and the page shows `Order #2`: React called the component twice and
the second call won. Server rendering, or any later re-render, produces yet another number. The fix is to move the
side effect to where it belongs (generate the id in the event handler that creates the order) or use `useId` when
only a unique DOM id is needed.

*Mutating a prop.* The `Cart` from the first section sorts `items` in place. Rendering it server-side prints the sorted
names, but the *caller's* array has changed order too (`ba` became `ab`), so unrelated components that read the same
array now behave differently, and re-rendering gives a different starting point than the first render. The copy
`+[...items].sort(...)+` leaves the original as `ba`.

*Local mutation is fine.* Mutating something you created during the same render cannot be observed by anyone else:

[source,jsx]
----
function Names({ users }) {
  const list = [];                      // created in this render
  for (const u of users) list.push(<li key={u.id}>{u.name}</li>);
  return <ul>{list}</ul>;
}
----

This renders `<ul><li>Ada</li><li>Bob</li></ul>` every time. The rule is about shared values, not about the `push`
call.

*Calling a component as a function.* `+{show && Counter()}+` runs `Counter` as part of the *caller's* render, so
`Counter`{apos}s Hooks become the caller's Hooks, with no component boundary, no separate state and no way for React to
skip or reorder it. The Rules of Hooks and the identity rules then apply to the wrong function. Always write
`<Counter />`.

*Position decides identity.* Two branches rendering the same component type at the same position share state. In a form
that shows a `Field` labelled "Name" or one labelled "Company", the text typed into the first remains in the second
(`"Ada"`), because React sees one `Field` whose prop changed. Give each variant a `key` (`+<Field key="c" ... />+`) and the
input starts empty (`""`). Use this deliberately to reset state, and avoid it by accident by never defining a
component inside another component's body (its identity would change on every render).

== Deep dive: how the tooling enforces the rules

* `eslint-plugin-react-hooks` enforces the Rules of Hooks and Effect dependencies; recent versions of its `recommended`
  configuration also include rules that flag impure renders, mutation of props and state, and refs read during render.
* The React Compiler assumes the rules hold. When it finds code that breaks them it **skips** that component (and
  reports a diagnostic) instead of risking wrong output, so a violation costs you the automatic optimization.
* `<StrictMode>` is the runtime check: double rendering, double Effects and double ref callbacks in development.

Treat a StrictMode double-run that changes the screen as a bug in the component, not in StrictMode.
