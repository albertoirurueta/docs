include::partial$ai-disclaimer.adoc[]

Test React components the way a user experiences them: render, interact, assert on what is visible. The
standard stack is a test runner (**Jest** or **Vitest**) plus **React Testing Library** (RTL) for component
tests, https://mswjs.io/[**Mock Service Worker**] (MSW) for the network, and
https://playwright.dev/[Playwright] or https://www.cypress.io/[Cypress] for a small end-to-end layer.

== Test types

* **Unit** -- a pure function or a small component in isolation. Fast, many.
* **Integration** -- several components together (a form, a page) with the network mocked. The sweet spot for
  RTL.
* **End-to-end (e2e)** -- the real app in a real browser. Slow, few.

The **test pyramid**: many unit and integration tests, few e2e.

== Test-runner setup

**Jest** is the long-standing default and is what most existing React projects use. **Vitest** is a drop-in
alternative with a near-identical API that reuses your Vite config; prefer it for new Vite projects. Both need
a DOM environment and the `@testing-library/jest-dom` matchers (`toBeInTheDocument`, `toHaveTextContent`, ...).

.Jest (`jest.config.js` + `jest.setup.js`)
[source,javascript]
----
// jest.config.js
module.exports = {
  testEnvironment: 'jsdom',
  setupFilesAfterEnv: ['<rootDir>/jest.setup.js'],
};

// jest.setup.js
import '@testing-library/jest-dom';
----

.Vitest (`vitest.config.ts` + `vitest.setup.ts`)
[source,ts]
----
// vitest.config.ts
import { defineConfig } from 'vitest/config';
export default defineConfig({
  test: { environment: 'jsdom', setupFiles: ['./vitest.setup.ts'], globals: true },
});

// vitest.setup.ts
import '@testing-library/jest-dom/vitest';
----

In the examples below, `+import ... from 'vitest'+` and `+vi.*+` map one-to-one to Jest globals and `+jest.*+`.

== React Testing Library

Query the way users find things -- by **role**, label, or text -- and drive interactions with `user-event`.

[source,jsx]
----
import { render, screen } from '@testing-library/react';
import userEvent from '@testing-library/user-event';
import { expect, test } from 'vitest';       // or: from '@jest/globals'
import Counter from './Counter';

test('increments on click', async () => {
  const user = userEvent.setup();
  render(<Counter />);

  const button = screen.getByRole('button', { name: /count: 0/i });
  await user.click(button);

  expect(screen.getByRole('button', { name: /count: 1/i })).toBeInTheDocument();
});
----

* `+getBy*+` throws if not found, `+queryBy*+` returns `null` (assert absence), `+findBy*+` is async (waits).
* RTL wraps state updates in **`act()`** for you; you rarely call it directly. An `act()` warning means a
  state update happened outside an awaited interaction -- usually a missing `+await user....+` or `+findBy*+`. See
  https://react.dev/reference/react/act[`act`].
* Mock **modules** with the runner (`+vi.mock('./api')+` / `+jest.mock('./api')+`); mock the **network** with MSW
  (next section) rather than stubbing `fetch` by hand.

== Mocking the network with MSW

https://mswjs.io/[Mock Service Worker] intercepts requests at the network layer, so the component under test
runs its real `fetch` / `axios` / query-client code against fake responses. One set of handlers works in unit
tests, in the browser, and in Playwright.

.`src/test/server.ts` -- shared handlers
[source,ts]
----
import { setupServer } from 'msw/node';
import { http, HttpResponse } from 'msw';

export const server = setupServer(
  http.get('/api/products/:id', ({ params }) =>
    HttpResponse.json({ id: params.id, name: 'Widget', price: 9.99 })),
);
----

.Setup file -- start once per test run
[source,ts]
----
import { server } from './src/test/server';

beforeAll(() => server.listen({ onUnhandledRequest: 'error' }));
afterEach(() => server.resetHandlers());   // undo per-test overrides
afterAll(() => server.close());
----

.A test using it -- happy path and a per-test error override
[source,jsx]
----
import { render, screen } from '@testing-library/react';
import { http, HttpResponse } from 'msw';
import { server } from './src/test/server';
import ProductPage from './ProductPage';

test('renders the product name from the API', async () => {
  render(<ProductPage id="42" />);
  expect(await screen.findByText('Widget')).toBeInTheDocument();
});

test('shows an error when the API fails', async () => {
  server.use(
    http.get('/api/products/:id', () => new HttpResponse(null, { status: 500 })),
  );
  render(<ProductPage id="42" />);
  expect(await screen.findByRole('alert')).toHaveTextContent(/could not load/i);
});
----

Cross-link xref:web/react/data-fetching.adoc[Data Fetching] for the component side.

== Testing custom Hooks

Use `renderHook` for logic that has no UI of its own:

[source,jsx]
----
import { renderHook, act } from '@testing-library/react';
import useToggle from './useToggle';

test('useToggle flips', () => {
  const { result } = renderHook(() => useToggle());
  act(() => result.current[1]());          // call toggle
  expect(result.current[0]).toBe(true);
});
----

See https://testing-library.com/docs/react-testing-library/intro/[the React Testing Library docs].

== What to test, and what not to

Tests should fail when behavior a user depends on breaks, and keep passing when you refactor internals. That is
the guiding principle behind React Testing Library: it gives you no way to reach a component's state or call
its methods, only the rendered DOM and user interactions. Test *what the user sees and does* (a heading appears,
a button becomes disabled, an error message is announced); do not test *how* it is done (that `setState` was
called, which Hook is used, the name of a CSS class).

[mermaid]
....
flowchart LR
    R["render(&lt;Component /&gt;)<br/>into jsdom"] --> Q["Query like a user<br/>getByRole, getByLabelText"]
    Q --> I["Interact<br/>userEvent.click, type"]
    I --> A["Assert on the DOM<br/>toBeInTheDocument, toHaveTextContent"]
    A -->|"async work"| W["findBy*, waitFor"]
    W --> A
....

The queries are ranked by how closely they match how people and assistive technology find things. Prefer them in
this order; a test that can only find an element by `data-testid` is often a sign of a missing label or role in
the markup.

[cols="2,3",options="header"]
|===
| Query | Use it for

| `+getByRole('button', { name: /save/i })+`
| Almost everything interactive; the `name` is the accessible name (text, label or `aria-label`).

| `+getByLabelText('Email')+`
| Form fields associated with a `<label>`.

| `getByText`, `getByDisplayValue`
| Non-interactive text, or the current value of an input.

| `getByAltText`, `getByTitle`
| Images, and elements with only a `title`.

| `getByTestId`
| Last resort, when nothing user-visible distinguishes the element.
|===

== The sample component under test

The examples below test the pieces of the shop built elsewhere in this section: the cart provider and its
buttons from xref:web/react/state-management.adoc[State Management], the product page from
xref:web/react/data-fetching.adoc[Data Fetching], and a debounced search box and a sign-up form defined here.
The test runner is Vitest with `jsdom`; the API base URL (`VITE_API_URL`, the same variable the app reads) is
supplied through the test environment, as it would be when the API lives on its own origin:

[source,ts]
----
// vitest.config.ts
import { defineConfig } from 'vitest/config';
import react from '@vitejs/plugin-react';

export default defineConfig({
  plugins: [react()],
  test: {
    environment: 'jsdom',
    setupFiles: ['./test/setup.ts'],
    globals: true,
    css: true,                                         // process CSS Modules so class names exist
    env: { VITE_API_URL: 'http://localhost:3000' },    // jsdom's default origin: no CORS surprises
  },
});
----

Handlers can match either an absolute URL such as `http://localhost:3000/api/products/:id` or, for `fetch`, a
relative path as in the MSW section above. Choosing the same origin as jsdom's own page URL
(`http://localhost:3000`) matters when the code under test uses axios: axios runs on `XMLHttpRequest` in jsdom,
which enforces CORS, so a mock on a different origin fails with a `Network Error` unless it also answers with
CORS headers.

[source,ts]
----
// test/setup.ts
import '@testing-library/jest-dom/vitest';
import { cleanup } from '@testing-library/react';
import { afterAll, afterEach, beforeAll } from 'vitest';
import { server } from './server';

beforeAll(() => server.listen({ onUnhandledRequest: 'error' }));
afterEach(() => { cleanup(); server.resetHandlers(); });
afterAll(() => server.close());
----

[NOTE]
====
These examples use MSW 2. In MSW 3 the `onUnhandledRequest` option of `server.listen` is named
`onUnhandledFrame`, and the `graphql` handlers are imported from `msw/graphql`; the handlers for `http` requests
are unchanged.
====

== A render helper with providers

Components that read context, the router or a query client cannot render on their own. Rather than repeating
the providers in every test, wrap `render` once. The helper creates a **fresh `QueryClient` per test** so cached
data cannot leak between tests, and turns retries off so a failing request fails the test immediately instead of
after three backoff retries:

[source,tsx]
----
// test/render-utils.tsx
import { render, type RenderOptions } from '@testing-library/react';
import userEvent from '@testing-library/user-event';
import { QueryClient, QueryClientProvider } from '@tanstack/react-query';
import { MemoryRouter } from 'react-router';
import type { ReactElement, ReactNode } from 'react';
import { CartProvider } from '../src/cart/CartContext';

export function renderWithProviders(
  ui: ReactElement,
  { route = '/', ...options }: { route?: string } & Omit<RenderOptions, 'wrapper'> = {},
) {
  const client = new QueryClient({ defaultOptions: { queries: { retry: false } } });
  function Wrapper({ children }: { children: ReactNode }) {
    return (
      <QueryClientProvider client={client}>
        <MemoryRouter initialEntries={[route]}>
          <CartProvider>{children}</CartProvider>
        </MemoryRouter>
      </QueryClientProvider>
    );
  }
  return { user: userEvent.setup(), client, ...render(ui, { wrapper: Wrapper, ...options }) };
}
----

A test of a component that needs the cart then reads like the user story:

[source,tsx]
----
test('a component that needs the cart provider', async () => {
  const { user } = renderWithProviders(<><AddButton product={widget} /><CartSummary /></>);
  await user.click(screen.getByRole('button', { name: 'Add Widget' }));
  expect(screen.getByLabelText('cart')).toHaveTextContent('1 items, total 9.99');
});
----

== Testing context and error paths

`renderHook` accepts the same `wrapper`, which is the way to test a Hook that reads context. A well written
Hook also fails clearly outside its provider, and that behavior deserves a test. React logs the thrown error to
the console even though the test expects it, so silence that one call:

[source,tsx]
----
test('a hook that reads context, with a wrapper', () => {
  const { result } = renderHook(() => useCart(), { wrapper: CartProvider });
  expect(result.current).toEqual({});
});

test('using a hook outside its provider throws a helpful error', () => {
  const spy = vi.spyOn(console, 'error').mockImplementation(() => {});   // React logs the thrown error
  expect(() => renderHook(() => useCart())).toThrow('inside <CartProvider>');
  spy.mockRestore();
});
----

An **error boundary** is tested by rendering a child that throws and asserting on the fallback; as above, the
console noise is silenced for that test only.

[source,tsx]
----
class Boundary extends Component<{ children: ReactNode }, { failed: boolean }> {
  state = { failed: false };
  static getDerivedStateFromError() { return { failed: true }; }
  render() { return this.state.failed ? <p role="alert">Oops</p> : this.props.children; }
}
function Bomb(): never { throw new Error('boom'); }

test('an error boundary renders its fallback', () => {
  const spy = vi.spyOn(console, 'error').mockImplementation(() => {});
  render(<Boundary><Bomb /></Boundary>);
  expect(screen.getByRole('alert')).toHaveTextContent('Oops');
  spy.mockRestore();
});
----

== Time: fake timers

Code that waits (a debounce, a timeout, polling) is tested with fake timers so the test does not really wait.
A debounced search box calls `onSearch` only after the user stops typing for 300 ms:

[source,tsx]
----
import { useEffect, useState } from 'react';

export function useDebounce<T>(value: T, ms: number): T {
  const [debounced, setDebounced] = useState(value);
  useEffect(() => {
    const id = setTimeout(() => setDebounced(value), ms);
    return () => clearTimeout(id);
  }, [value, ms]);
  return debounced;
}

export function DebouncedSearch({ onSearch }: { onSearch: (q: string) => void }) {
  const [text, setText] = useState('');
  const query = useDebounce(text, 300);
  useEffect(() => { if (query) onSearch(query); }, [query, onSearch]);
  return <input aria-label="Search" value={text} onChange={(e) => setText(e.target.value)} />;
}
----

[source,tsx]
----
test('debounce with fake timers', async () => {
  // shouldAdvanceTime lets Testing Library's own timeouts fire; user-event is told how to move the fake clock
  vi.useFakeTimers({ shouldAdvanceTime: true });
  const user = userEvent.setup({ advanceTimers: vi.advanceTimersByTime });
  const onSearch = vi.fn();
  render(<DebouncedSearch onSearch={onSearch} />);
  await user.type(screen.getByLabelText('Search'), 'wid');
  expect(onSearch).not.toHaveBeenCalled();               // still inside the 300 ms window
  await act(async () => { vi.advanceTimersByTime(300); });
  expect(onSearch).toHaveBeenCalledTimes(1);
  expect(onSearch).toHaveBeenCalledWith('wid');
  vi.useRealTimers();
});

afterEach(() => { vi.useRealTimers(); });   // a failing fake-timer test must not leak into the next one
----

Two details make this work under Vitest. `+userEvent.setup({ advanceTimers })+` is required so `user.type` can
move the fake clock between keystrokes. And plain `vi.useFakeTimers()` makes React Testing Library's
`asyncWrapper` wait forever (it only knows how to advance Jest's fake timers), which is why
`shouldAdvanceTime: true` is passed: the clock then also ticks in real time, and your own
`advanceTimersByTime` jumps it forward. Always restore real timers in `afterEach`; a test that fails before
`useRealTimers()` would otherwise freeze the clock for every test after it, producing unrelated timeouts.

== Forms and Actions

A form driven by `useActionState` (see xref:web/react/forms-and-actions.adoc[Forms and Actions]) is tested from
the outside: type, submit, observe the pending state, then the result. Controlling when the mocked server call
resolves lets the test look at the in-between state:

[source,tsx]
----
export function Signup({ signup }: { signup: (email: string) => Promise<{ error?: string; ok?: boolean }> }) {
  const [state, action, pending] = useActionState(
    async (_prev: { error?: string; ok?: boolean }, data: FormData) => signup(String(data.get('email'))),
    {},
  );
  return (
    <form action={action}>
      <label>Email <input name="email" type="email" /></label>
      <button disabled={pending}>{pending ? 'Sending…' : 'Sign up'}</button>
      {state.error && <p role="alert">{state.error}</p>}
      {state.ok && <p role="status">Welcome aboard</p>}
    </form>
  );
}
----

[source,tsx]
----
test('a form driven by an Action: pending, then error', async () => {
  const user = userEvent.setup();
  let finish!: (r: { error: string }) => void;
  const signup = vi.fn(() => new Promise<{ error: string }>((r) => (finish = r)));
  render(<Signup signup={signup} />);
  await user.type(screen.getByLabelText('Email'), 'a@b.co');
  await user.click(screen.getByRole('button', { name: 'Sign up' }));
  expect(screen.getByRole('button')).toBeDisabled();
  expect(screen.getByRole('button')).toHaveTextContent('Sending…');
  await act(async () => finish({ error: 'Already registered' }));
  expect(screen.getByRole('alert')).toHaveTextContent('Already registered');
  expect(signup).toHaveBeenCalledWith('a@b.co');
});
----

Wrapping the resolution in `+await act(async () => ...)+` is the explicit way to tell React that the promise
settling will cause updates; without it you get an `act()` warning and the assertion may run too early.

== Suspense, `use` and lazy components

A component that suspends has nothing to show until its promise resolves, and React retries it after the
promise settles. Render it inside an async `act`, which waits for that retry, and then assert on the final
content; a bare synchronous `render` followed by `+findBy*+` can miss the retry:

[source,tsx]
----
test('use(promise) with Suspense', async () => {
  await act(async () => { render(<ProductSuspense id="2" />); });
  expect(await screen.findByRole('heading', { name: 'Gadget' })).toBeInTheDocument();
});
----

Because the async `act` waits for the request, you do not observe the `Loading…` fallback in this form of test.
To assert on the fallback, give the promise a handle you resolve yourself (`+let resolve!: (v: T) => void;+` and `+const p = new Promise<T>((r) => (resolve = r))+`), render inside `act`, check the fallback text, then resolve
inside another `act`. The same technique tests nested Suspense boundaries and lazy components from
xref:web/react/code-splitting-and-suspense.adoc[Code Splitting and Suspense].

== Modules, routes and accessibility

* **Mocking a module.** `+vi.mock('../src/api', () => ({ getJson: vi.fn() }))+` replaces the module for the test
  file (Vitest hoists the call above the imports); configure it per test with
  `+vi.mocked(getJson).mockResolvedValue(...)+` and assert on the call with `toHaveBeenCalledWith`. Prefer
  mocking the network with MSW when you can, because a module mock bypasses code you would like to exercise.
* **Routes.** Build a router with `+createMemoryRouter(routes, { initialEntries: ['/products'] })+`, render
  `+<RouterProvider router={router} />+`, click links, and assert on headings and on `router.state.location`.
  This exercises loaders, actions and error elements for real; see xref:web/react/routing.adoc[Routing].
* **Accessibility.** The `vitest-axe` package runs the axe rules on rendered markup. It finds a subset of
  problems (missing labels, invalid ARIA, contrast cannot be checked in jsdom), so it complements, but does not
  replace, a keyboard and screen-reader check:
+
[source,tsx]
----
import { axe } from 'vitest-axe';
import * as axeMatchers from 'vitest-axe/matchers';

expect.extend(axeMatchers);   // once, in test/setup.ts

test('no detectable accessibility violations', async () => {
  const { container } = render(<ThemeProvider><ThemeSwitch /></ThemeProvider>);
  expect(await axe(container)).toHaveNoViolations();
});
----
+
For TypeScript, declare the matcher once with `+declare module 'vitest' { interface Assertion extends AxeMatchers {} }+`
(importing `AxeMatchers` from `vitest-axe/matchers`). See xref:web/accessibility.adoc[Web Accessibility].

== Snapshot tests and coverage

* **Snapshot tests** serialize rendered output and diff it on later runs. Use sparingly -- large snapshots
  churn and get rubber-stamped. Prefer explicit assertions.
* **Coverage** -- `jest --coverage` or `vitest --coverage`. Treat it as a gap finder, not a target.

== End-to-end tests

E2E tools drive a **real browser** against the running app. Reserve them for a handful of critical flows
(sign-up, checkout, search) and keep them stable. Point them at a dev/preview server, or reuse the MSW
handlers above so the backend is deterministic. For a deeper, tool-focused reference -- install, headless vs.
headed execution, evidence capture, CI/CD, and a full Selenium/Playwright/Cypress comparison -- see
xref:web/e2e-testing/index.adoc[E2E Testing in the Browser].

.Playwright (`tests/checkout.spec.ts`)
[source,ts]
----
import { test, expect } from '@playwright/test';

test('user can add a product to the cart', async ({ page }) => {
  await page.goto('/products/42');
  await page.getByRole('button', { name: /add to cart/i }).click();
  await expect(page.getByRole('status')).toHaveText(/1 item/i);
});
----

Run with `npx playwright test`; `npx playwright codegen` records a first draft, and traces (`--trace on`)
make failures debuggable in CI.

.Cypress (`cypress/e2e/checkout.cy.ts`)
[source,ts]
----
describe('checkout', () => {
  it('adds a product to the cart', () => {
    cy.visit('/products/42');
    cy.findByRole('button', { name: /add to cart/i }).click();
    cy.findByRole('status').should('contain.text', '1 item');
  });
});
----

Run with `npx cypress open` (interactive) or `npx cypress run` (headless in CI);
`@testing-library/cypress` adds the same `findByRole` queries used in RTL. See
https://playwright.dev/docs/intro[the Playwright docs] and https://docs.cypress.io/[the Cypress docs].
