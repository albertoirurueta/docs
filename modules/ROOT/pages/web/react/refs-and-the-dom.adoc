= Refs and the DOM
:description: Using useRef for mutable values that do not trigger re-renders, DOM refs for focus and scroll and measurement, ref as a prop in React 19, useImperativeHandle, and flushSync.
:keywords: useRef, mutable ref, DOM ref, ref attribute, ref callback, focus, scrollIntoView, ref as a prop, forwardRef, useImperativeHandle, flushSync

include::partial$ai-disclaimer.adoc[]

A **ref** is an escape hatch for values React should *not* re-render on: a mutable box (`ref.current`) that
persists across renders. Its two uses are holding an arbitrary mutable value and holding a DOM node.

== Refs for mutable values

[source,jsx]
----
function Stopwatch() {
  const [now, setNow] = useState(0);
  const intervalRef = useRef(null);           // survives re-renders, no re-render on change

  function start() {
    intervalRef.current = setInterval(() => setNow((n) => n + 1), 1000);
  }
  function stop() {
    clearInterval(intervalRef.current);
  }
  // ...
}
----

Reading or writing `ref.current` during render is not allowed (it makes render impure); do it in event
handlers or Effects. See
https://react.dev/learn/referencing-values-with-refs[Referencing Values with Refs].

== DOM refs

Pass a ref to a DOM element's `ref` attribute and React sets `ref.current` to the node after commit. Use it to
focus, scroll, or measure -- things with no declarative equivalent.

[source,jsx]
----
function SearchBox() {
  const inputRef = useRef(null);

  useEffect(() => {
    inputRef.current.focus();                 // focus on mount
  }, []);

  return (
    <>
      <input ref={inputRef} />
      <button onClick={() => inputRef.current.scrollIntoView()}>Reveal</button>
    </>
  );
}
----

A **ref callback** runs with the node on mount and `null` on unmount -- useful for a list of nodes:

[source,jsx]
----
<li ref={(node) => { if (node) map.set(id, node); else map.delete(id); }} />
----

See https://react.dev/learn/manipulating-the-dom-with-refs[Manipulating the DOM with Refs] and
xref:programming-languages/javascript/browser-dom-basics.adoc[Web Programming Basics] for the underlying node APIs.

== `ref` as a prop, `useImperativeHandle`, `flushSync`

* **React 19**: a function component can accept `ref` as an ordinary prop and forward it to a DOM element. The
  older `forwardRef` wrapper still works but is not needed for new code.
+
[source,jsx]
----
function TextInput({ ref, ...props }) {       // React 19: ref is just a prop
  return <input ref={ref} {...props} />;
}
----
* **`useImperativeHandle`** -- expose a *custom* object (not the raw node) as the ref handle, e.g. `{ focus,
  scrollToTop }`. Rare; prefer props.
* **`flushSync`** (from `react-dom`) -- force React to apply a state update and re-render synchronously so the
  DOM is up to date before your next line runs (e.g. scroll to a row you just added). Rare and a performance
  cost.

Avoid refs for anything you can express with state and props. References:
https://react.dev/reference/react/useImperativeHandle[`useImperativeHandle`],
https://react.dev/reference/react-dom/flushSync[`flushSync`].

== Deep dive: the life of a ref

A ref object starts as `+{ current: null }+` (or the value you gave `useRef`). For a DOM ref, React fills it in during the
commit phase and clears it again when the element goes away:

[mermaid]
....
sequenceDiagram
    participant C as Your component
    participant R as React
    participant D as DOM node
    C->>R: render returns element with ref
    R->>D: create or update the node (commit)
    R->>C: ref.current = node
    Note over C,D: Effects and event handlers can now use ref.current
    R->>D: element removed
    R->>C: ref.current = null
....

Two consequences. During the first render `ref.current` is still `null`, so DOM access belongs in an event handler or an
Effect. And a conditionally rendered element has a ref that is `null` whenever the element is absent, so guard
`ref.current?.focus()` where the element might not exist.

== Deep dive: focus management with `ref` as a prop

Moving focus is the most common legitimate use of a DOM ref. In the storefront's search field, focus the input on
mount and again after the "clear" button empties it, passing the ref through a reusable `TextInput`:

[source,jsx]
----
function TextInput({ ref, ...props }) {
  return <input ref={ref} {...props} />;
}

function Search() {
  const inputRef = useRef(null);

  useEffect(() => { inputRef.current.focus(); }, []);

  return (
    <>
      <TextInput ref={inputRef} aria-label="q" />
      <button onClick={() => { inputRef.current.value = ''; inputRef.current.focus(); }}>clear</button>
    </>
  );
}
----

After mounting, `document.activeElement` is the input. Changing `.value` directly is acceptable for an *uncontrolled*
input like this one; if the field were controlled, call the state setter instead.

== Deep dive: ref callbacks with cleanup

A ref callback receives the node on attach. Since React 19 it may also **return a cleanup function**, which is called
when the element is removed (instead of calling the callback with `null`). That makes registries and observers
symmetrical:

[source,jsx]
----
function Row({ id, registry }) {
  return (
    <li
      ref={(node) => {
        registry.set(id, node);
        return () => registry.delete(id);
      }}
    >
      {id}
    </li>
  );
}
----

Rendering a `Row` adds an entry to the map and unmounting it removes the entry again. The same pattern works for a
`ResizeObserver` or `IntersectionObserver`: observe in the callback, `disconnect` in the returned function. Note that an
inline arrow function is a *new* callback on every render, so React detaches and re-attaches on each render; wrap
the callback in `useCallback` if that matters. When a ref callback returns a function, React no longer calls it with
`null`, so do not rely on that call.

== Deep dive: `useImperativeHandle` and `flushSync`

A parent should not reach into a child's DOM node. If a child must offer a few operations (focus, reset), expose a narrow
handle instead of the node:

[source,jsx]
----
function QuantityInput({ ref }) {
  const inputRef = useRef(null);
  useImperativeHandle(ref, () => ({
    focus() { inputRef.current.focus(); },
    reset() { inputRef.current.value = '1'; },
  }), []);
  return <input ref={inputRef} defaultValue="1" aria-label="qty" />;
}

function Form() {
  const qty = useRef(null);
  return (
    <>
      <QuantityInput ref={qty} />
      <button onClick={() => { qty.current.reset(); qty.current.focus(); }}>Reset</button>
    </>
  );
}
----

After the button is clicked the input shows `1` and has focus, and `Object.keys(qty.current)` is only `+['focus', 'reset']+`
-- the parent cannot touch `style` or `value`.

State updates are batched, so the DOM does not change until the handler finishes. `flushSync` forces the update to
be applied immediately:

[source,jsx]
----
function add() {
  flushSync(() => setItems((l) => [...l, 'b']));
  // the DOM already contains the new <li> here
  listRef.current.lastElementChild.scrollIntoView();
}
----

In a test the list already contained two items, and one more was added with `flushSync`. Reading
`listRef.current.children.length` on the next line gave 3, whereas the same read after a plain `setItems` call still
returned the old count. Use
it for the rare "update, then measure or scroll" sequence; the usual alternative is an Effect.

=== A previous-value Hook

Because writing a ref does not re-render, a ref plus an Effect can remember the value from the previous render:

[source,jsx]
----
function usePrevious(value) {
  const ref = useRef(undefined);
  useEffect(() => { ref.current = value; });   // runs after the render that returned the old value
  return ref.current;
}
----

Rendering with `1` and then `2` shows `+1 -> 2+`. The Hook reads `ref.current` during render, which is a deliberate
exception that works because the value is only written in an Effect; for anything driving the UI, prefer storing
the previous value in state.
