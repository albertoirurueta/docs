**Code splitting** breaks the bundle into chunks loaded on demand, so the first screen ships less JavaScript.
React's tools for this are `lazy` and `<Suspense>`.

== `lazy` + `<Suspense>`

`lazy` turns a dynamic `import()` into a component. `<Suspense>` shows a `fallback` while that component (or
its data) is still loading.

[source,jsx]
----
import { lazy, Suspense } from 'react';

const Settings = lazy(() => import('./Settings.jsx'));

function App() {
  return (
    <Suspense fallback={<Spinner />}>
      <Settings />
    </Suspense>
  );
}
----

* Put a boundary where a **meaningful chunk** of UI can be replaced by a spinner without a jarring layout
  shift -- often at the route level, sometimes around a heavy widget (a chart, an editor).
* One `<Suspense>` can wrap several lazy children; they share the one fallback.
* Avoid `lazy` for tiny components or anything needed for the first paint -- the extra request costs more than
  it saves.

**Route-based splitting** is the highest-value case: each route's component is `lazy`, so visiting `/reports`
downloads only the reports chunk. Most routers (React Router, TanStack Router) build this in -- see
xref:web/react/routing.adoc[Routing].

References: https://react.dev/reference/react/lazy[`lazy`],
https://react.dev/reference/react/Suspense[`<Suspense>`].

=== What the bundler does with `import()`

A static `import` pulls a module into the chunk of the file that imports it. A dynamic `import()` is a split
point: the bundler puts the imported module and everything only it uses into a **separate chunk**, and the
call returns a promise that resolves when the browser has downloaded and evaluated that chunk. `lazy` wraps
that promise as a component. Building the sample shop with Vite shows the result: the route component loaded
with `lazy` becomes its own file next to the main bundle.

----

dist/assets/index-gp5Zc0wQ.js              96.26 kB

----

Splitting only pays when the chunk is large relative to the extra request and is not needed for the first
paint. The decision rule: split by **route** first, then by **heavy, rarely used widgets** (a charting library, a
rich-text editor, a map, a PDF viewer), and do not split small components (see "Avoiding lazy components"
below).

=== Named exports, preloading and transitions

`lazy` expects the module to have a `default` export that is the component. For a module with a named export,
map it in the factory. Combined with a **preload**, started when the user hovers or focuses the control that
will need the chunk, the download is usually finished by the time the click arrives:

[source,tsx]
----
import { lazy, startTransition, Suspense, useState } from 'react';

// 1. named export: lazy() wants a module whose `default` is the component
const loadChart = () => import('./Chart');
export const SalesChart = lazy(() => loadChart().then((m) => ({ default: m.SalesChart })));

// 2. preload: start the download before the user needs it (the module system caches the promise)
export function ChartToggle() {
  const [open, setOpen] = useState(false);
  return (
    <>
      <button
        onPointerEnter={() => void loadChart()}
        onFocus={() => void loadChart()}
        onClick={() => startTransition(() => setOpen(true))}   // keep the old UI instead of flashing a fallback
      >
        Show chart
      </button>
      <Suspense fallback={<p>Loading chart…</p>}>{open && <SalesChart points={[1, 2, 3]} />}</Suspense>
    </>
  );
}
----

Calling `loadChart()` twice does not download twice: the browser's module map returns the same promise for the
same specifier. Wrapping the state update in `startTransition` tells React the update is not urgent, so when
the new content suspends React keeps showing the *current* screen (already revealed content is never replaced
by a fallback during a transition) and swaps in the chart when it is ready. Without the transition the whole
`<Suspense>` region would first flash its fallback.

=== When a chunk fails to load

A chunk is a network request, and it can fail: the user went offline, or you deployed a new version and the old
hashed file the open tab asks for no longer exists. A rejected `import()` makes the lazy component throw, so the
failure is an *error* for the nearest error boundary, not an endless spinner. Because a `lazy` component
**remembers its rejection**, a "Retry" button that merely re-renders the same component fails again; retrying
needs a *new* lazy component so that `import()` runs again:

[source,tsx]
----
import { lazy, Suspense, useState, type ComponentType } from 'react';
import { ErrorBoundary } from 'react-error-boundary';

export function RetryableChart({ load }: { load: () => Promise<{ default: ComponentType<{ points: number[] }> }> }) {
  const [Chart, setChart] = useState(() => lazy(load));
  return (
    <ErrorBoundary
      onReset={() => setChart(() => lazy(load))}        // new lazy => the import() runs again
      fallbackRender={({ resetErrorBoundary }) => (
        <div role="alert">
          Could not load the chart. <button onClick={resetErrorBoundary}>Retry</button>
        </div>
      )}
    >
      <Suspense fallback={<p>Loading chart…</p>}>
        <Chart points={[1, 2, 3]} />
      </Suspense>
    </ErrorBoundary>
  );
}
----

The error boundary here is the `react-error-boundary` package (see below); `resetErrorBoundary` clears its
error state and calls `onReset`, where the new lazy component is created. For a transient failure it is also
common to retry automatically once inside the factory, and for the stale-deployment case to reload the page
when the error is a chunk-load error, since the new `index.html` references the new chunk names.

=== Avoiding lazy components

Lazy loading is a trade: fewer bytes up front, in exchange for a later request and a loading state that did not
exist before. It is a poor trade when:

* the component is small (the request overhead is larger than the code it saves);
* it is part of the first paint or "above the fold", so the user would see a fallback on every page load;
* it sits inside a list of many instances, each of which would show its own fallback;
* it is already inside a chunk that the same route always loads.

Measure before and after (the bundle sizes in the build output, and the Network panel for the chunk request
waterfall) rather than assuming a split helps.

== Suspense for data and the `use` API

`<Suspense>` also handles *data* loading when a Suspense-enabled source is read during render: a framework
loader, a Suspense-integrated library, or the **`use`** API reading a promise.

[source,jsx]
----
import { use, Suspense } from 'react';

function Message({ promise }) {
  const text = use(promise);      // suspends until the promise resolves
  return <p>{text}</p>;
}

// the promise must be STABLE across renders -- from a cache or a framework loader,
// created once (here at module scope), never `fetchGreeting()` inline in the JSX below
const greetingPromise = fetchGreeting();

function Greeting() {
  return (
    <Suspense fallback={<p>Loading…</p>}>
      <Message promise={greetingPromise} />
    </Suspense>
  );
}
----

Unlike Hooks, `use` may be called inside conditions and loops. Creating the promise fresh in `render` (e.g.
`+<Message promise={fetchGreeting()} />+`) makes a new promise every render and re-suspends forever -- it must
come from a cache or a framework. `use` can also read context. See
https://react.dev/reference/react/use[`use`].

== Nested boundaries and reveal order

Several `<Suspense>` boundaries can be nested. The nearest boundary above the suspended component shows its
fallback, so the placement of boundaries decides what the user sees while each part loads. An outer boundary
covers the whole page shell; inner boundaries let independent regions appear as soon as each is ready, instead
of the slowest part holding everything back:

[source,tsx]
----
import { Suspense, use } from 'react';

function Slow({ promise, label }: { promise: Promise<string>; label: string }) {
  return <p>{label}: {use(promise)}</p>;
}

// Outer boundary: the page shell. Inner boundaries: independent slow regions.
export function Dashboard({ fast, slow }: { fast: Promise<string>; slow: Promise<string> }) {
  return (
    <Suspense fallback={<p>Loading page…</p>}>
      <h1>Dashboard</h1>
      <Suspense fallback={<p>Loading summary…</p>}>
        <Slow promise={fast} label="Summary" />
      </Suspense>
      <Suspense fallback={<p>Loading activity…</p>}>
        <Slow promise={slow} label="Activity" />
      </Suspense>
    </Suspense>
  );
}
----

With an already-resolved `fast` promise and a pending `slow` one, the heading and the summary render
immediately and only "Loading activity…" remains; when `slow` resolves, the activity replaces its own fallback
without touching the rest. Without the inner boundaries the outer one would show "Loading page…" until *both*
were ready.

== Error boundaries

`<Suspense>` handles the *pending* state; an **error boundary** handles the *failed* state. An error boundary
is the one component that still must be a **class**, because it uses `static getDerivedStateFromError` and
`componentDidCatch`.

[source,jsx]
----
import { Component } from 'react';

class ErrorBoundary extends Component {
  state = { hasError: false };
  static getDerivedStateFromError() { return { hasError: true }; }
  componentDidCatch(error, info) { logError(error, info); }
  render() {
    return this.state.hasError ? this.props.fallback : this.props.children;
  }
}

<ErrorBoundary fallback={<p>Something went wrong.</p>}>
  <Suspense fallback={<Spinner />}>
    <Settings />
  </Suspense>
</ErrorBoundary>
----

The https://github.com/bvaughn/react-error-boundary[`react-error-boundary`] package provides a ready-made
component with retry support. See
https://react.dev/reference/react/Component#catching-rendering-errors-with-an-error-boundary[Catching rendering
errors with an error boundary].

In a framework, Suspense boundaries also decide what streams to the browser first; see
xref:web/nextjs/streaming-and-suspense.adoc[Next.js Streaming and Suspense].
