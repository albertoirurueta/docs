TypeScript catches whole classes of React bugs -- a missing prop, the wrong shape passed to a component, an
event field that does not exist. Use the `.tsx` extension and `[source,tsx]` for anything where types are the
point. See https://react.dev/learn/typescript[Using TypeScript]. This page covers the React-specific typing
patterns only; for the language itself -- the type system, generics, the utility types, and `tsconfig` -- see
the xref:programming-languages/typescript/index.adoc[TypeScript Reference].

== Typing props

Describe props with an `interface` or a `type` alias; either works, `interface` is conventional for object
props. Type `children` as `React.ReactNode`.

[source,tsx]
----
interface ButtonProps {
  label: string;
  onClick: () => void;
  variant?: 'primary' | 'ghost';   // optional
  children?: React.ReactNode;
}

function Button({ label, onClick, variant = 'primary', children }: ButtonProps) {
  return (
    <button className={variant} onClick={onClick}>
      {label}
      {children}
    </button>
  );
}
----

== Typing hooks and events

[source,tsx]
----
// useState — inferred from the initial value; annotate when it can be null
const [user, setUser] = useState<User | null>(null);
const [count, setCount] = useState(0);              // number, inferred

// useReducer — type the state and a discriminated-union action
type Action = { type: 'inc' } | { type: 'set'; value: number };
function reducer(state: number, action: Action): number { /* ... */ return state; }

// useRef — DOM ref starts as null
const inputRef = useRef<HTMLInputElement>(null);

// event handlers
function onChange(e: React.ChangeEvent<HTMLInputElement>) {
  setName(e.target.value);
}
function onSubmit(e: React.FormEvent<HTMLFormElement>) {
  e.preventDefault();
}

// context — give createContext a type; guard the null default
const ThemeContext = React.createContext<Theme | null>(null);
function useTheme(): Theme {
  const ctx = React.useContext(ThemeContext);
  if (!ctx) throw new Error('useTheme must be used within ThemeProvider');
  return ctx;
}
----

== Generics, utility types, `as const`

[source,tsx]
----
// a generic component
interface ListProps<T> {
  items: T[];
  renderItem: (item: T) => React.ReactNode;
}
function List<T>({ items, renderItem }: ListProps<T>) {
  return <ul>{items.map((it, i) => <li key={i}>{renderItem(it)}</li>)}</ul>;
}

// PropsWithChildren adds `children?: React.ReactNode`
type CardProps = React.PropsWithChildren<{ title: string }>;

// `as const` narrows a literal — useful for action creators and config
const ROUTES = ['home', 'about', 'contact'] as const;
type Route = (typeof ROUTES)[number];   // 'home' | 'about' | 'contact'
----

Other useful types: `+React.ComponentProps<'button'>+` (the props of a DOM element), `React.CSSProperties`,
`React.Dispatch<React.SetStateAction<T>>`.

== Making invalid states unrepresentable

The biggest payoff of typing components is not catching typos but encoding rules, so that a wrong combination of
props does not compile. All snippets in this section were compiled with `tsc --noEmit` under `strict`, with
`@types/react` 19, and the lines marked `@ts-expect-error` really are errors.

[mermaid]
....
flowchart LR
    S["Source .tsx"] --> TS["tsc / editor<br/>type-check only"]
    TS -->|"errors"| F["Fix before running"]
    TS -->|"ok"| B["Bundler strips types<br/>(Vite, esbuild, SWC)"]
    B --> J["Plain JavaScript<br/>no type information at run time"]
....

Types exist only at compile time. The bundler removes them without checking anything, so run `tsc --noEmit` (or
the editor's checker) in CI as a separate step; and anything that crosses a trust boundary at run time, such as
an API response or `JSON.parse` output, still needs validation, because the type annotation is a promise rather
than a check.

=== Discriminated unions for props

When one prop decides which other props make sense, model the props as a union with a literal "tag". Inside a
`switch` on the tag the compiler narrows to the matching member, so `percent` is only accessible, and required,
for the `+'sale'+` kind:

[source,tsx]
----
import type { ReactNode } from 'react';

type BadgeProps =
  | { kind: 'sale'; percent: number }
  | { kind: 'new' }
  | { kind: 'custom'; children: ReactNode };

export function Badge(props: BadgeProps) {
  switch (props.kind) {
    case 'sale': return <span>-{props.percent}%</span>;       // percent is known to exist here
    case 'new': return <span>New</span>;
    case 'custom': return <span>{props.children}</span>;
  }
}

// @ts-expect-error percent is required when kind is 'sale'
<Badge kind="sale" />;
----

Keep the `props` object and narrow on it. Splitting the tag from the other fields in the signature
(`+{ kind, ...rest }+`) breaks the link between them: `rest` is a union of the remaining fields and is not
narrowed by `kind`, so `rest.percent` is an error even inside `+if (kind === 'sale')+`.

=== Extending DOM elements and `ref` as a prop

`+ComponentProps<'button'>+` is the full set of props of a `<button>` including `onClick`, `disabled` and `+aria-*+`.
Intersect it with your own props and forward the rest, and the wrapper behaves like the native element.
In React 19 `ref` is an ordinary prop on function components (see
xref:web/react/refs-and-the-dom.adoc[Refs and the DOM]), so a wrapper no longer needs `forwardRef`; it just
declares `ref` in its props:

[source,tsx]
----
import { type ComponentProps, type Ref } from 'react';

type ButtonProps = ComponentProps<'button'> & { variant?: 'primary' | 'ghost' };

export function Button({ variant = 'primary', className, ...rest }: ButtonProps) {
  return <button className={`btn btn-${variant} ${className ?? ''}`} {...rest} />;
}

export function TextField({ ref, ...rest }: ComponentProps<'input'> & { ref?: Ref<HTMLInputElement> }) {
  return <input ref={ref} {...rest} />;
}

// @ts-expect-error unknown variant
<Button variant="danger" />;
----

=== Constrained generics and polymorphic components

A generic component takes its item type from the data it is given. A **constraint** (`extends`) states what the
component needs from every item, here an `id` to use as the key, so passing items without one is a compile
error rather than a runtime key warning:

[source,tsx]
----
import type { ReactNode } from 'react';

interface ListProps<T extends { id: string }> {
  items: T[];
  renderItem: (item: T) => ReactNode;
}
export function List<T extends { id: string }>({ items, renderItem }: ListProps<T>) {
  return <ul>{items.map((it) => <li key={it.id}>{renderItem(it)}</li>)}</ul>;
}

// @ts-expect-error items need an id
<List items={[{ name: 'x' }]} renderItem={() => null} />;
----

A **polymorphic** component renders a caller-chosen element through an `as` prop, and its props must follow the
chosen tag: `href` is valid for `as="a"` and not for the default `div`.

[source,tsx]
----
import type { ComponentProps, ElementType } from 'react';

type BoxProps<E extends ElementType> = { as?: E } & Omit<ComponentProps<E>, 'as'>;
export function Box<E extends ElementType = 'div'>({ as, ...rest }: BoxProps<E>) {
  const Tag: ElementType = as ?? 'div';
  return <Tag {...rest} />;
}

<Box as="a" href="/x">ok</Box>;
// @ts-expect-error href belongs to <a>, not <div>
<Box href="/x" />;
----

The assignment `const Tag: ElementType` widens the type inside the function body on purpose: the precise
checking happens at the call sites, which is where the guarantee matters.

=== Exhaustive reducers and typed hooks

The `never` type turns "I forgot a case" into a compile error. If a new action is added to the union and the
`switch` does not handle it, `action` is no longer `never` in the `default` branch and the assignment fails:

[source,ts]
----
type Action = { type: 'inc' } | { type: 'set'; value: number };

export function reducer(state: number, action: Action): number {
  switch (action.type) {
    case 'inc': return state + 1;
    case 'set': return action.value;
    default: {
      const unreachable: never = action;   // adding a new action without handling it becomes a compile error
      return unreachable;
    }
  }
}
----

A custom Hook that returns a pair should end with `as const`, otherwise the return type is the union array
`+(boolean | (() => void))[]+` and destructuring loses the positions:

[source,ts]
----
import { useState } from 'react';

export function useToggle(initial = false) {
  const [on, setOn] = useState(initial);
  return [on, () => setOn((v) => !v)] as const;   // readonly [boolean, () => void]
}
----

=== Typing Actions, refs and data libraries

`useActionState` infers its state type from the action and the initial state, so the component sees a typed
`state` with no annotation:

[source,tsx]
----
import { useActionState, useRef } from 'react';
import type { Product } from '../types';

interface FormState { error: string | null; saved: Product | null }

async function saveProduct(_prev: FormState, data: FormData): Promise<FormState> {
  const name = String(data.get('name') ?? '').trim();   // FormData values are string | File | null
  if (!name) return { error: 'Name is required', saved: null };
  return { error: null, saved: { id: '9', name, price: 1 } };
}

export function NewProduct() {
  const [state, action, pending] = useActionState(saveProduct, { error: null, saved: null });
  const input = useRef<HTMLInputElement>(null);
  return (
    <form action={action}>
      <TextField ref={input} name="name" aria-label="Name" />
      <Button disabled={pending}>Save</Button>
      {state.error && <p role="alert">{state.error}</p>}
    </form>
  );
}
----

Libraries that return data from the network carry types through generics: `useQuery(productQuery(id))` returns
`data` typed as `Product | undefined` when the query function is typed, React Router's
`useLoaderData<typeof loader>()` returns whatever the loader returns, and `useRef<HTMLInputElement>(null)`
yields a ref whose `current` is `HTMLInputElement | null`. See xref:web/react/data-fetching.adoc[Data Fetching]
and xref:web/react/routing.adoc[Routing] for those examples.

== Changes to the types in React 19

* The global `JSX` namespace is no longer provided: write `React.JSX.Element` or import `ReactElement`, and
  prefer not annotating component return types at all.
* `useRef` requires an argument: `useRef<number | null>(null)` compiles, `useRef<number>()` does not.
* `React.FC` is optional and often avoided: it adds nothing that a typed props parameter does not, and the
  explicit form generalizes to generic components, which `FC` cannot express.
* `PropTypes` and `defaultProps` for function components are gone; use default parameter values (as in
  `+variant = 'primary'+` above).

== Recommended compiler settings

[source,json]
----
{
  "compilerOptions": {
    "target": "ES2022",
    "module": "ESNext",
    "moduleResolution": "bundler",
    "jsx": "react-jsx",
    "strict": true,
    "noEmit": true,
    "skipLibCheck": true,
    "lib": ["ES2022", "DOM", "DOM.Iterable"]
  }
}
----

`"jsx": "react-jsx"` uses the automatic runtime, so files do not import `React` just to write JSX; `strict`
enables the null checks that make `useState<User | null>` meaningful; `"moduleResolution": "bundler"` matches how
Vite resolves imports; and `noEmit` makes `tsc` a pure checker because the bundler produces the output.

NOTE: `PropTypes` was **removed from React core in React 19**. Runtime prop validation is now the job of
TypeScript (compile time) or a schema library. See
https://react-typescript-cheatsheet.netlify.app/[the React TypeScript Cheatsheet] and
xref:programming-languages/javascript/index.adoc[JavaScript Development] for the language itself.
