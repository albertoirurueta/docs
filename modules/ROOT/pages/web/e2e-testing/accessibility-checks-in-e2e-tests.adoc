An automated accessibility check runs a rule engine against the page a browser test has just driven into some state, and
fails the test when a rule is broken. The engine nearly all tools share is https://github.com/dequelabs/axe-core[axe-core],
an open source JavaScript library from Deque Systems that runs inside the page, walks the DOM and the browser's computed
styles and reports violations of rules that map to the Web Content Accessibility Guidelines (WCAG). Playwright, Cypress
and Selenium do not ship an accessibility engine of their own; each one injects axe-core through a small integration
package, so the rules, the tags and the shape of the results are the same in every tool and only the calling code
differs. This page shows that code for all three, then covers the other side of the subject: what a rule engine cannot
decide, and the aria snapshot, a Playwright assertion that checks the structure and the accessible names of a region.

It was checked on 25 October 2026 against Playwright 1.64.1, Cypress 16.2.0 and Selenium 4.51.0, with axe-core 4.14.0
(`@axe-core/playwright` 4.14.0, `cypress-axe` 1.7.0, `com.deque.html.axe-core:selenium` 4.14.0 and `@axe-core/webdriverjs`
4.14.0) and the Python package `axe-selenium-python` 3.0.0, which bundles axe-core 4.10.2. Every example on this page was run
against the xref:web/e2e-testing/example-application-and-test-layout.adoc[Bookshelf] application, in both its light and its
dark theme, except where a sentence says that an example was not run. Because Bookshelf turned out to be almost clean, the
page also scans a small page that is broken on purpose, served from a separate static server, so that every tool can be
seen reporting real violations (see <<A deliberately broken page>>). The theory of accessibility itself (the POUR
principles, the conformance levels, the legal standards) lives in xref:web/accessibility.adoc[Web Accessibility]; this page
is about wiring checks into tests.

== What an automated check can tell you

axe-core evaluates a set of *rules*. Each rule has an identifier such as `color-contrast`, `image-alt` or `label`, an impact
(`minor`, `moderate`, `serious` or `critical`), a help URL on the Deque University site that explains the failure, and a list
of *tags*. The tags are how a test chooses which rules to run.

[cols="2,4",options="header"]
|===
|Tag |Meaning

|`wcag2a`, `wcag2aa`, `wcag2aaa`
|Rules required by WCAG 2.0 level A, AA or AAA.

|`wcag21a`, `wcag21aa`
|Rules added by WCAG 2.1 at level A and AA.

|`wcag22aa`
|Rules added by WCAG 2.2 at level AA.

|`wcag111`, `wcag143`, ...
|One tag per WCAG success criterion (`wcag111` is 1.1.1 Non-text Content, `wcag143` is 1.4.3 Contrast Minimum).

|`best-practice`
|Common recommendations that no WCAG criterion requires, for example `heading-order`. They run by default.

|`ACT`
|Rules that implement the W3C Accessibility Conformance Testing rules format.

|`section508`, `EN-301-549`, `RGAAv4`, `TTv5`
|Rules that map to the old US Section 508, the European standard EN 301 549, the French RGAA and the Trusted Tester process.

|`experimental`
|Cutting-edge rules, disabled by default.

|`cat.forms`, `cat.color`, `cat.aria`, ...
|The category a rule belongs to; every rule has one.
|===

Source: https://github.com/dequelabs/axe-core/blob/develop/doc/API.md#axe-core-tags[axe-core API documentation: Axe-core tags]

A scan returns four lists, and understanding the difference between them prevents most misreadings:

[cols="1,4",options="header"]
|===
|List |Meaning

|`violations`
|Rules that failed on at least one element. These are what a test normally asserts to be empty.

|`passes`
|Rules that applied and succeeded.

|`incomplete`
|Rules that applied but that axe could not decide automatically, such as the contrast of text over an image or an
`aria-label` on an element that has no role. Each of these needs a person to look at it.

|`inapplicable`
|Rules that had nothing to check on this page, for example a table rule on a page without tables.
|===

Source: https://github.com/dequelabs/axe-core/blob/develop/doc/API.md#results-object[axe-core API documentation: Results object]

Two consequences follow. An empty `violations` list means that no automatable rule failed in the state the test scanned,
not that the page is accessible. And a scan is a statement about one DOM state, so a modal, an error message or a dark
theme is only checked if the test brings the page into that state before it scans.

== Bookshelf as the subject

Bookshelf is a small server-rendered application written with accessibility in mind: every page has a `lang` attribute, a
title, a skip link, landmark regions, labelled form fields and an `aria-live` result counter. The test runs below showed
that it is nearly, but not entirely, clean:

* Scanned with the WCAG tags, every public page (`/`, `/books`, `/books/3`, `/signin`) and the signed-in pages had no
  violations in the light theme and in the dark theme, both when the dark theme came from the toggle button and when it came from
  the operating system preference.
* Scanned with the default rule set, `/books` has one `heading-order` violation (impact `moderate`, tag `best-practice`): the
  catalogue goes from a level 1 heading straight to the level 3 headings of the book cards. It does not show up in a scan
  restricted to WCAG tags.
* The error message of the review form (`#review-error`) failed `color-contrast` when the dark theme was selected through the
  operating system's `prefers-color-scheme` setting: red text `#b91c1c` on the dark background `#111827` has a contrast
  ratio of 2.74, below the required 4.5. Choosing the dark theme with the toggle button fixes it, because only the explicit
  `data-theme="dark"` selector overrides the colour. The sections below show the tests that found this.
* On the signed-in admin page and account page axe reported two rules as `incomplete`: the star ratings are `span` elements
  with an `aria-label` and no role, which axe flags for a human to review (<<What automated checks cannot find>>).

The page that is broken on purpose is a "Checkout" page served by a throwaway Node server on its own port. It is not part
of Bookshelf. Its markup has one example of each common mistake, and its colour palette fails contrast only in the dark

== Playwright

=== @axe-core/playwright

The package adds an `AxeBuilder` class to Playwright. It injects axe-core into the page (and into its frames), runs it and
returns the standard axe results object.

[source,bash]
----
npm install --save-dev @axe-core/playwright
----

Source: https://playwright.dev/docs/accessibility-testing[Playwright: Accessibility testing]

The simplest test navigates, scans and asserts on the violations. This one scans the catalogue twice: with the default
rule set, which contains one best-practice finding, and with the WCAG A and AA tags, which is clean.

[source,typescript]
----
test('the default rule set also runs best-practice rules', async ({ page }) => {
  await page.goto('/books');
  const results = await new AxeBuilder({ page }).analyze();
  expect(results.violations.map((v) => `${v.id}:${v.impact}`)).toEqual(['heading-order:moderate']);
  const wcagOnly = await new AxeBuilder({ page }).withTags(['wcag2a', 'wcag2aa']).analyze();
  expect(wcagOnly.violations).toEqual([]);
});
----

Source: https://playwright.dev/docs/accessibility-testing#scanning-an-entire-page[Playwright: Scanning an entire page]

`AxeBuilder` is a builder: each method returns the builder, and `analyze()` runs the scan and returns a promise.

[cols="2,4",options="header"]
|===
|Method |Effect

|`+new AxeBuilder({ page })+`
|Creates a builder for a Playwright `Page`. The page must come from `browser.newContext()` or from the `page` fixture; a page
created with `browser.newPage()` makes `analyze()` throw "Please use browser.newContext()", because the package needs to open a
helper page in the same context.

|`include(selector)`
|Limits the scan to the matching elements. Can be called several times. A frame is addressed with a nested array.

|`exclude(selector)`
|Removes the matching elements and all their descendants from the scan, for every rule.

|`withTags(tags)`
|Runs only the rules that carry at least one of the tags (a string or an array).

|`withRules(rules)`
|Runs only the listed rules, by id.

|`disableRules(rules)`
|Switches the listed rules off.

|`options(runOptions)`
|Passes any axe run option, for example `+resultTypes: ['violations']+`, which makes axe keep a single node for passes,
incomplete and inapplicable results instead of all of them.

|`setLegacyMode(true)`
|Runs the scan through a single page instead of a helper page, with limited iframe support. Not needed in normal use.

|`analyze()`
|Runs the scan and resolves to `+{ violations, passes, incomplete, inapplicable, ... }+`.
|===

Source: https://github.com/dequelabs/axe-core-npm/tree/develop/packages/playwright[axe-core-npm: @axe-core/playwright]

`analyze()` scans the page as it is at that moment. If the state under test appears after an interaction, wait for it with
a web-first assertion first, as the review-form example further down does.

=== Choosing the rules, and scoping the scan

A scan with no configuration runs the default rule set, best-practice rules included: on `/books` it reports `heading-order`,
while the same scan restricted to the WCAG tags is clean (the first test of this page checks both). Teams usually restrict
scans to the WCAG A and AA tags, because those are what the standards and the laws require, and keep best-practice findings
as a separate, lower-priority report. A fixture that returns a pre-configured builder keeps that choice in one place:

[source,typescript]
----
import { test as base } from '@playwright/test';
import AxeBuilder from '@axe-core/playwright';

type AxeFixture = {
  makeAxeBuilder: () => AxeBuilder;
};

// Every test gets a builder that already checks WCAG 2.0 to 2.2 A and AA rules.
export const test = base.extend<AxeFixture>({
  makeAxeBuilder: async ({ page }, use) => {
    await use(() =>
      new AxeBuilder({ page }).withTags(['wcag2a', 'wcag2aa', 'wcag21a', 'wcag21aa', 'wcag22aa']),
    );
  },
});

export { expect } from '@playwright/test';

// A stable summary of the violations: rule id and the selectors that failed.
export function violationFingerprints(results: { violations: { id: string; nodes: { target: unknown }[] }[] }) {
  return JSON.stringify(
    results.violations.map((v) => ({ rule: v.id, targets: v.nodes.map((n) => n.target) })),
    null,
    2,
  );
}
----

Source: https://playwright.dev/docs/accessibility-testing#using-a-test-fixture-for-common-axe-configuration[Playwright: Using a test fixture for common axe configuration]

The test files then use `makeAxeBuilder()` instead of `+new AxeBuilder({ page })+`. The fixture is built with
`test.extend`, which xref:web/e2e-testing/playwright/configuration-fixtures-and-projects.adoc[Configuration, Fixtures & Projects] explains.
The tests below show what `include`, `exclude`, `options`, `withRules` and `disableRules` do to a scan of Bookshelf's catalogue:

[source,typescript]
----
test('include and exclude narrow the scan', async ({ page }) => {
  await page.goto('/books');
  const whole = await new AxeBuilder({ page }).analyze();
  const nav = await new AxeBuilder({ page }).include('[data-testid=main-nav]').analyze();
  const noNav = await new AxeBuilder({ page }).exclude('[data-testid=main-nav]').analyze();
  console.log(`passes: whole=${whole.passes.length} nav=${nav.passes.length} withoutNav=${noNav.passes.length}`);
  expect(nav.passes.length).toBeLessThan(whole.passes.length);
});

test('options() passes axe run options such as resultTypes', async ({ page }) => {
  await page.goto('/books');
  const results = await new AxeBuilder({ page }).options({ resultTypes: ['violations'] }).analyze();
  expect(results.violations.map((v) => v.id)).toEqual(['heading-order']);
  // Only one node is kept for every result type that was not requested.
  expect(results.passes.every((rule) => rule.nodes.length <= 1)).toBe(true);
});

test('withRules runs one rule, disableRules switches rules off', async ({ page }) => {
  await page.goto('/');
  const one = await new AxeBuilder({ page }).withRules(['color-contrast']).analyze();
  expect(one.passes.map((r) => r.id)).toEqual(['color-contrast']);
  const without = await new AxeBuilder({ page }).disableRules(['color-contrast']).analyze();
  expect(without.passes.map((r) => r.id)).not.toContain('color-contrast');
});
----

Source: https://playwright.dev/docs/accessibility-testing#configuring-axe-to-scan-a-specific-part-of-a-page[Playwright: Configuring axe to scan a specific part of a page]

The first of these tests printed `passes: whole=42 nav=11 withoutNav=41`: scoping the scan to the navigation ran 11 passing rules
instead of 42, and excluding the navigation removed one.

=== Both themes, and states that need an interaction

Colour contrast is the rule most affected by the theme. Playwright can emulate the operating system preference with
`+page.emulateMedia({ colorScheme })+`, which switches `prefers-color-scheme` for that page, so a loop produces a scan per page
and per scheme. The toggle button is exercised separately because Bookshelf also stores an explicit choice in
`localStorage` and in `data-theme`:

[source,typescript]
----
for (const colorScheme of ['light', 'dark'] as const) {
  for (const path of ['/', '/books', '/books/3', '/signin']) {
    test(`${path} has no WCAG A/AA violations (${colorScheme})`, async ({ page, makeAxeBuilder }) => {
      await page.emulateMedia({ colorScheme });
      await page.goto(path);
      const results = await makeAxeBuilder().analyze();
      expect(results.violations, violationFingerprints(results)).toEqual([]);
    });
  }
}

test('the theme toggle switches the page to the dark theme and it still passes', async ({ page, makeAxeBuilder }) => {
  await page.emulateMedia({ colorScheme: 'light' });
  await page.goto('/books/3');
  await page.getByTestId('theme-toggle').click();
  await expect(page.locator('html')).toHaveAttribute('data-theme', 'dark');
  const results = await makeAxeBuilder().analyze();
  expect(results.violations).toEqual([]);
});
----

Source: https://playwright.dev/docs/api/class-page#page-emulate-media[Playwright: page.emulateMedia()]

The review form in its error state is a page state that only exists after an interaction. The helper below submits a
too-short review and waits for the alert, then the tests scan the `main` region. This is where the contrast problem of the
error message appeared:

[source,typescript]
----
async function submitShortReview(page: Page) {
  await signIn(page, 'reader', readerPassword);
  await expect(page.getByTestId('account-heading')).toBeVisible();
  await page.goto('/books/3');
  await page.getByLabel('Your review').fill('Short');
  await page.getByTestId('review-submit').click();
  await expect(page.getByRole('alert')).toBeVisible(); // wait for the state before scanning
}

test('the review form in its error state (light)', async ({ page, makeAxeBuilder }) => {
  await page.emulateMedia({ colorScheme: 'light' });
  await submitShortReview(page);
  const results = await makeAxeBuilder().include('main').analyze();
  expect(results.violations, violationFingerprints(results)).toEqual([]);
});

test('the error message fails colour contrast when dark comes from the OS preference', async ({ page, makeAxeBuilder }) => {
  await page.emulateMedia({ colorScheme: 'dark' });
  await submitShortReview(page);
  const results = await makeAxeBuilder().include('main').analyze();
  console.log(violationFingerprints(results));
  expect(results.violations.map((v) => v.id)).toEqual(['color-contrast']);
  expect(results.violations[0].nodes[0].target).toEqual(['#review-error']);
});

test('the same state passes once the dark theme is chosen with the toggle', async ({ page, makeAxeBuilder }) => {
  await page.emulateMedia({ colorScheme: 'light' });
  await submitShortReview(page);
  await page.getByTestId('theme-toggle').click();
  await expect(page.locator('html')).toHaveAttribute('data-theme', 'dark');
  const results = await makeAxeBuilder().include('main').analyze();
  expect(results.violations).toEqual([]);
});

test('a known issue can be excluded while it is being fixed', async ({ page, makeAxeBuilder }) => {
  await page.emulateMedia({ colorScheme: 'dark' });
  await submitShortReview(page);
  const results = await makeAxeBuilder().include('main').exclude('#review-error').analyze();
  expect(results.violations).toEqual([]);
});
----

=== Known issues, fingerprints and attachments

When a page has defects that cannot be fixed immediately, the scan must neither fail forever nor stop checking the rest of
the page. Playwright's guide lists three techniques:

. *`exclude(selector)`* removes an element and everything inside it from every rule. It is the simplest option, but a new
  defect inside that element will go unnoticed.
. *`+disableRules(['rule-id'])+`* switches one rule off for the whole scan. Use it only when many elements break the same
  rule, and re-enable it when they are fixed.
. *A fingerprint snapshot* compares only the rule id and the selectors of the violations against a stored value, so existing
  issues are accepted but a new one fails the test. The raw violations array must not be snapshotted, because it contains
  the HTML of each element and changes whenever a component is edited.

The fingerprint helper used on this page is `violationFingerprints()` in the fixture file shown above. With a stored
snapshot the assertion is `expect(violationFingerprints(results)).toMatchSnapshot()`.

For debugging, attach the whole result, including passes and incomplete items, to the test report. Reporters then embed or
link the JSON, and the HTML report shows it among the test's attachments:

[source,typescript]
----
test('attach the full scan results', async ({ page, makeAxeBuilder }, testInfo) => {
  await page.goto('/books');
  const results = await makeAxeBuilder().analyze();
  await testInfo.attach('accessibility-scan-results', {
    body: JSON.stringify(results, null, 2),
    contentType: 'application/json',
  });
  console.log(`violations=${results.violations.length} passes=${results.passes.length} incomplete=${results.incomplete.length} inapplicable=${results.inapplicable.length}`);
  expect(results.violations).toEqual([]);
});
----

Source: https://playwright.dev/docs/accessibility-testing#exporting-scan-results-as-a-test-attachment[Playwright: Exporting scan results as a test attachment]

=== Aria snapshots

An aria snapshot is not an axe rule. It compares the *accessibility tree* the browser builds for an element, a list of
roles, accessible names and a few states, with a YAML template, so a test can state what a screen reader should be able to
perceive and fail when the structure or a name changes. It therefore complements an axe scan: axe looks for known mistakes,
and a snapshot pins down what the page should contain. The syntax of the template, partial matching, file-based snapshots
and the `page.ariaSnapshot()` and `ariaSnapshotJSON()` APIs are explained in
xref:web/e2e-testing/playwright/assertions.adoc#_aria_snapshots[Playwright Assertions]; this section shows them used as an
accessibility check.

[source,typescript]
----
test('aria snapshot of the main navigation', async ({ page }) => {
  await page.goto('/books');
  await expect(page.getByRole('navigation', { name: 'Main' })).toMatchAriaSnapshot(`
    - navigation "Main":
      - link "Catalogue"
      - link /Sign in/
      - button "Toggle theme"
  `);
});

test('aria snapshot of the pagination', async ({ page }) => {
  await page.goto('/books');

== Cypress

=== What the Cypress guide recommends

Cypress's accessibility guide describes three layers: *accessibility scans* with an in-test plugin such as `cypress-axe`,
*explicit tests* for application-specific behaviour (keyboard navigation, accessible names, alternative text), and
*Cypress Accessibility*, a paid service in Cypress Cloud. It also warns about two things that are easy to miss. First, a
scan costs time on every call, so it should run on the states that matter and not on every test. Second, finding an element
with a role-based locator does not prove it is accessible: a `div` with `role="button"` can be located like a `button`
but has none of the keyboard behaviour of a real one. The Cypress 16 query `cy.getByRole()` therefore matches native elements
by default (a `div` with `role="button"` is not matched unless `native: false` is passed), which makes a refactor from a button
to a `div` fail a test that locates it by role. See
xref:web/e2e-testing/cypress/queries-assertions-and-custom-commands.adoc[Queries, Assertions & Custom Commands] for the query itself.

Source: https://docs.cypress.io/app/guides/accessibility-testing[Cypress: Accessibility testing]

=== The commands

Importing the plugin in the support file registers three commands. The Bookshelf project's support file already contains
`+import 'cypress-axe'+`.

[cols="2,4",options="header"]
|===
|Command |Effect

|`cy.injectAxe(options?)`
|Injects axe-core into the page under test. It must run after every `cy.visit()` or full page load, because a new document
has no `axe` object. The `axeCorePath` option points to a different copy of axe-core.

|`cy.configureAxe(configuration)`
|Calls `axe.configure()` for the checks that follow; for example it can disable a rule with
`+{ rules: [{ id: 'heading-order', enabled: false }] }+`.

|`cy.checkA11y(context?, options?, violationCallback?, skipFailures?)`
|Runs the scan and fails the test if it finds violations. `context` is a selector or an axe context object with `include` and
`exclude`; `options` are the axe run options plus `includedImpacts`, `interval` and `retries`; `violationCallback` receives the
violations (use it to log them); `skipFailures: true` reports violations through the callback without failing the test.
|===

Source: https://github.com/component-driven/cypress-axe#readme[cypress-axe README]

The first tests scan the same four pages as the Playwright suite, in both themes. Cypress has no command for emulating
`prefers-color-scheme`, so the first block sets the `theme` key in `localStorage` before the page loads;
the second block, further down, uses the Chrome DevTools Protocol:

import type { Result } from 'axe-core';

const wcag = { runOnly: { type: 'tag' as const, values: ['wcag2a', 'wcag2aa', 'wcag21a', 'wcag21aa', 'wcag22aa'] } };

// Prints one line per violation in the terminal of `cypress run`.
function logViolations(violations: Result[]) {
  cy.task('log', `${violations.length} accessibility violation(s)`);
  violations.forEach(({ id, impact, nodes }) => {
    cy.task('log', `${id} (${impact}): ${nodes.map((n) => n.target.join(' ')).join(', ')}`);
  });
}
----

The tests that scope the scan, as in the Playwright section, are shorter in Cypress because the options live in the
command's arguments:

[source,typescript]
----
  it('scans only the main region, and only serious or critical impacts', () => {
    cy.visit('/books');
    cy.injectAxe();
    cy.checkA11y('main', { includedImpacts: ['serious', 'critical'] });
  });

  it('excludes an element and disables one rule', () => {
    cy.visit('/books');
    cy.injectAxe();
    cy.checkA11y(
      { exclude: ['[data-testid=main-nav]'] },
      { rules: { 'heading-order': { enabled: false } } },
    );
  });

  it('configureAxe applies to every later check', () => {
    cy.visit('/books');
    cy.injectAxe();
    cy.configureAxe({ rules: [{ id: 'heading-order', enabled: false }] });
    cy.checkA11y();
  });

  it('the default rule set reports the best-practice heading-order rule', () => {
    cy.visit('/books');
    cy.injectAxe();
    cy.checkA11y(null, null, (violations) => {
      expect(violations.map((v) => v.id)).to.deep.equal(['heading-order']);
    }, true); // skipFailures: log the violations but do not fail
  });
----

Source: https://github.com/component-driven/cypress-axe#readme[cypress-axe README]

`includedImpacts` filters the violations *after* the scan, so a team can fail the build only on `serious` and `critical`
findings while the rest are reported. In the last test `skipFailures` (the fourth parameter) is `true`: the scan still runs, the callback still receives the
violations (it asserts that the only one is `heading-order`), and the test does not fail. Cypress exposes no equivalent of Playwright's results object, so the callback is the way to get at the
data, for example to write it to a file with `cy.writeFile()`.

// Emulates prefers-color-scheme through the Chrome DevTools Protocol (Chromium-based browsers only).
function emulateColorScheme(value: 'light' | 'dark') {

    command: 'Emulation.setEmulatedMedia',
    params: { features: [{ name: 'prefers-color-scheme', value }] },
  });
}

=== Cypress Accessibility in Cypress Cloud

Cypress Accessibility is a commercial feature of Cypress Cloud that does not use in-test scans at all. Runs recorded with Test Replay (Cypress 13 or
later) are analysed on the Cloud side with axe-core: no test code or configuration is needed, the checks add no time to the run, and every
distinct DOM state reached by a test, in end-to-end or component tests, is analysed. The Cloud then offers sortable and
filterable reports by page, component or run, an inspectable DOM snapshot for each violation, a comparison between two runs
that shows only the new issues, historical scores, Jira issue creation, and a Results API that a CI job can call to block a pull
request. Elements marked as ignored in configuration are left out of the score but stay visible for manual review.

This page's Cypress Cloud examples were not run: Cypress Accessibility is a paid product that needs a Cloud project, a
record key and a trial arranged with Cypress, none of which is available to this documentation. The description above comes from Cypress's own
documentation. See xref:web/e2e-testing/cypress/cypress-cloud.adoc[Cypress Cloud] for recording runs.

Source: https://docs.cypress.io/accessibility/get-started/introduction[Cypress Accessibility: Introduction]

== Selenium

Selenium has no accessibility engine either, and its documentation has no page about accessibility checks. The ecosystem
fills the gap with axe-core integrations published by Deque (Java, JavaScript, .NET) and by Mozilla's services team (Python).
All of them work with a plain `WebDriver`, and so also with a `RemoteWebDriver` against a Grid, because the engine runs inside the browser:
the binding injects `axe.min.js` with `executeScript`, calls `axe.run()` and reads the JSON that comes back.

`AxeBuilder` offers `withTags(List)`, `withRules(List)`, `withOnlyRules(List)`, `disableRules(List)`, `include(String)`,

The `Axe` class has four methods: `inject()` loads the bundled axe-core into the page, `run(context, options)` runs it and
returns the results dictionary, `report(violations)` formats the violations as readable text, and
`write_results(data, name)` saves the JSON. Version 3.0.0 bundles axe-core 4.10.2, which is older than the 4.14.0 used by the
Java, JavaScript and Playwright packages, so the same page can be judged by a slightly different rule set.

`run()` builds JavaScript source with string formatting, and this has one trap. The `options` are pasted with `%s`, so a Python
dictionary containing `False` or `True` arrives in the browser as the undefined identifier `False` and the call fails with
`JavascriptException: javascript error: False is not defined`. Pass the options as a JSON string made with
`json.dumps()`, as the tests do. The `context` is pasted with `%r`, which is valid JavaScript for dictionaries of lists and strings.

[source,python]
----

    options = webdriver.ChromeOptions()
    options.add_argument("--headless=new")
    d = webdriver.Chrome(options=options)
    yield d

from axe_selenium_python import Axe
from selenium.webdriver.common.by import By

WCAG = json.dumps({"runOnly": {"type": "tag", "values": ["wcag2a", "wcag2aa", "wcag21a", "wcag21aa", "wcag22aa"]}})


def scan(driver, context=None, options=None):
    """Inject axe-core into the current page and run it."""
    axe = Axe(driver)
    axe.inject()
    return axe, axe.run(context=context, options=options)

=== JavaScript and other languages

For Selenium's JavaScript binding Deque publishes `@axe-core/webdriverjs`, whose `AxeBuilder` takes the driver and offers the same builder
methods as the Playwright package (`include`, `exclude`, `withTags`, `withRules`, `disableRules`, `options`, `analyze`). The
two tests below ran with `node --test`, Selenium 4.51.0 and headless Chrome:

[source,javascript]

import assert from 'node:assert/strict';
import { test } from 'node:test';
import { Builder } from 'selenium-webdriver';
import chrome from 'selenium-webdriver/chrome.js';
import AxeBuilder from '@axe-core/webdriverjs';

const BASE_URL = process.env.BASE_URL ?? 'http://localhost:3000';
const BROKEN_URL = process.env.BROKEN_URL ?? 'http://localhost:39640/';

async function withDriver(run) {
  const driver = await new Builder()
    .forBrowser('chrome')
    .setChromeOptions(new chrome.Options().addArguments('--headless=new'))
    .build();
  try {
    await run(driver);
  } finally {
    await driver.quit();
  }
}

test('Bookshelf catalogue has no WCAG violations', () =>
  withDriver(async (driver) => {
    await driver.get(`${BASE_URL}/books`);
    const results = await new AxeBuilder(driver)
      .withTags(['wcag2a', 'wcag2aa', 'wcag21a', 'wcag21aa', 'wcag22aa'])
      .analyze();
    assert.deepEqual(results.violations, []);
  }));

test('the broken fixture is reported', () =>
  withDriver(async (driver) => {
    await driver.get(BROKEN_URL);
    const results = await new AxeBuilder(driver).analyze();
    const ids = results.violations.map((v) => v.id).sort();
    console.log(ids.join(', '));
    assert.deepEqual(ids, ['button-name', 'html-has-lang', 'image-alt', 'label', 'link-name']);
  }));

== Where to run the checks

Scans are slower than ordinary assertions, because axe evaluates every rule against every element, and the same page state
is often reached by many tests. Cypress's guide recommends to test accessibility at least once for a component, an area or a
workflow, and not to repeat it in every test. A practical arrangement is:

. A scan of each page and of each important state (open dialog, error message, empty state, both themes) in a dedicated
  accessibility suite, or in the end-to-end test that reaches the state, with the WCAG tags.
. Explicit assertions for behaviour that a scan cannot know: keyboard order, focus after a dialog closes, accessible names of
  icon buttons, the skip link.
. Component tests for reusable widgets (see
  xref:web/e2e-testing/playwright/component-testing.adoc[Playwright Component Testing] and
  xref:web/e2e-testing/cypress/component-testing.adoc[Cypress Component Testing]), which are faster and show the markup
  that is meant to be rendered.
. A CI step that keeps the JSON results as an artifact, so that a failing build can be diagnosed without re-running it. See
  xref:web/e2e-testing/running-in-ci-cd.adoc[Running in CI/CD].

The checks are normal tests. They are subject to the same timing problems as any other test, so wait for the state first
and see xref:web/e2e-testing/flaky-tests-and-reliability.adoc[Flaky Tests & Reliability] for the general remedies. Checks
that run headless and headed give the same answers for the rules used on this page, and the browser matters little because
the rules inspect the DOM and the computed styles.

== What automated checks cannot find

A clean report means that no *mechanically verifiable* rule failed. Playwright's own guide says that many accessibility
problems can only be found by manual testing, and recommends combining automated tests, manual assessments and user testing;
Cypress's guide says that no automated scan can prove that an interface works for people with disabilities. Typical gaps:

* *Meaning.* axe can tell that an image has an `alt` attribute, not that the text describes the image. It can tell that a
  label exists, not that it says what the field is for.
* *Reading and focus order.* Whether the order of the DOM matches the order of meaning, whether focus moves to a dialog when it
  opens and returns to the button when it closes, whether a keyboard user can escape a widget (a keyboard trap).
* *Screen reader output.* What NVDA, JAWS or VoiceOver actually announces for a live region, a custom widget or a route change in a
  single-page application.
* *Content and cognition.* Plain language, consistent navigation, error messages that explain how to fix the problem,
  time limits, motion and flashing.
* *Things axe reports as incomplete.* The star ratings of Bookshelf are the example from this page: axe cannot decide whether a
  `span` with an `aria-label` and no role is read at all, and cannot compute the contrast of text made of symbols.
* *Anything outside the scanned state.* Content that appears only after an interaction, other viewport sizes, zoom and text
  spacing, forced-colours mode and other themes are checked only if the test creates them. The dark-mode finding in this page
  appeared only because the tests scanned the error state under both colour schemes.

Manual checks fill the rest: tabbing through the page with the keyboard alone, using a screen reader, zooming to 200 percent,
and the guided assessment of https://accessibilityinsights.io/[Accessibility Insights for Web]. xref:web/accessibility.adoc[Web Accessibility] lists the success
criteria and the standards, and its section on automated checks makes the same point about the validation tools it describes.

Source: https://www.w3.org/WAI/test-evaluate/[W3C WAI: Evaluating Web Accessibility]
