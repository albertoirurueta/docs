Cypress is an end-to-end and component test runner for web applications that executes your tests inside the browser, next to
the application, and ships its own interactive app for writing and debugging them. This page takes you from an empty project to
a running suite and then through every day-to-day command, option and setting you need first. It was written against Cypress
16.2.0 (released 13 October 2026) and checked on 25 October 2026. Every example that tests an application was run against the
xref:web/e2e-testing/example-application-and-test-layout.adoc[Bookshelf] application, started on a local port, with Cypress
16.2.0 and Chrome 155 on macOS. The interactive parts of the product (the Launchpad and `cypress open`) need a display and a
person to click, so they are described from the official documentation and were not run. For why Cypress is built the way it is,
see xref:web/e2e-testing/how-browser-automation-works.adoc[How Browser Automation Works]; for choosing it over Playwright or
Selenium, see xref:web/e2e-testing/choosing-a-tool.adoc[Choosing a Tool]. The commands, ideas and files here come back in the
rest of the Cypress pages, starting with xref:web/e2e-testing/cypress/core-concepts.adoc[Core Concepts].

== System requirements

Cypress 16 documents these requirements:

[cols="1,3",options="header"]
|===
|Item |Requirement

|Node.js
|22.x, 24.x or 26.x and later. Node.js 20 and 25 were dropped in 16.0.0. Cypress itself bundles Node.js 24.15.0 for the code it
runs in `setupNodeEvents` and `cy.task()`, whatever Node.js you installed.

|macOS
|13.5 or later, on Intel or Apple Silicon.

|Linux
|x64 or arm64: Ubuntu 22.04 or later (arm64 needs 24.04 or later), Debian 12 or later (arm64 needs 13 or later), Fedora 43 or
later. The prebuilt binary needs a glibc-based distribution (glibc 2.31 or later since Cypress 15).

|Windows
|Windows 10 and 11 (x64); Windows 11 25H2 on arm64 runs in x64 emulation and is a preview; Windows Server 2019, 2022 and 2025.

|Package manager
|npm 10.1.0 or later, Yarn Classic 1.22.22 or later, Yarn 4 or later, pnpm 8 or later, or Bun 1.2.22 or later.

|Hardware
|Any modern development machine. In CI use at least 2 CPUs and 4 GB of RAM, and 8 GB or more for long runs or when recording
video. Abrupt exits, frozen video frames and slow runs are the usual signs of too little.
|===

Source: https://docs.cypress.io/app/get-started/install-cypress#System-requirements[Cypress -- Install Cypress: System requirements]

=== Supported browsers

Cypress supports the latest three major versions of Google Chrome, Microsoft Edge and Mozilla Firefox (Firefox 140 or later,
because Cypress automates Firefox through WebDriver BiDi only). It also finds Chrome for Testing, Chromium, the beta, canary and
developer channels of the Chrome and Edge families, Firefox Developer Edition and Nightly, and offers experimental WebKit
support. Every release also bundles an Electron-based Chromium browser. *Electron has been deprecated as a test browser since
Cypress 16.0.0* and will be removed in a future major version, so the examples on this page always name an installed browser.
The reasons the project gives are that Electron's Chromium trails the current Chrome by weeks or months and that its behaviour
diverges from the browser your users run.

When you pass no `--browser` flag and no `defaultBrowser` is set, Cypress still falls back to Electron, and prints a warning.
This is the real output of `cypress run` with no browser chosen:

[source,text]
----
  │ Browser:        Electron 146 (headless) (deprecated)                                           │

Warning: The Electron browser is deprecated as a test browser and will be removed in a future version of Cypress.

Switch to Chrome or another installed browser to avoid a breaking change when you upgrade.

Read more about supported browsers: https://on.cypress.io/launching-browsers
----

Source: https://docs.cypress.io/app/references/migration-guide#Migrating-away-from-the-Electron-browser[Cypress -- Migration guide: Migrating away from the Electron browser]

=== Linux libraries and Docker

On a bare Linux machine Cypress needs a few system libraries. For Ubuntu 22.04 and Debian the documented command is
`apt-get install libgtk-3-0 libgbm-dev libnotify-dev libnss3 libxss1 libasound2 libxtst6 xauth xvfb`; on Ubuntu 24.04 and
later the `libgtk-3-0t64` and `libasound2t64` package names replace two of them. The Cypress Docker images
(`cypress/base`, `cypress/browsers` and `cypress/included`) already contain everything, and the `cypress/factory` image builds
a custom combination of Node.js, browser and Cypress versions. Install `unzip` as well, so that the binary download does not fall
back to a slower unzip implemented in Node.js. Running in CI is covered in the continuous-integration pages of this section.

Source: https://docs.cypress.io/app/get-started/install-cypress#Linux-Prerequisites[Cypress -- Install Cypress: Linux prerequisites]

== Installing Cypress

Install Cypress as a development dependency of the project that holds your tests. The `cypress` npm package is a small command
line wrapper; its `postinstall` script downloads the real application, called the *binary*, into a per-user cache that every
project on the machine shares.

[source,bash]
----
mkdir bookshelf-e2e && cd bookshelf-e2e
npm init -y
npm install cypress --save-dev
npm install typescript @types/node --save-dev   # needed for TypeScript specs, see below
----

Source: https://docs.cypress.io/app/get-started/install-cypress[Cypress -- Install Cypress]

The first command printed (from an empty project, with the binary already in the cache, so no download happened):

[source,text]
----
added 171 packages, and audited 172 packages in 2s

found 0 vulnerabilities
npm warn install-scripts 1 package has install scripts not yet covered by allowScripts:
npm warn install-scripts   cypress@16.2.0 (postinstall: node dist/index.js --exec install)
npm warn install-scripts
npm warn install-scripts Run `npm install-scripts ls` to review, or `npm install-scripts approve <pkg>` to allow.
----

Source: https://docs.cypress.io/app/get-started/install-cypress[Cypress -- Install Cypress]

That last warning matters. Package managers are moving to block dependency lifecycle scripts by default, and Cypress depends on
one to fetch its binary: npm 11.16.0 and later warn (as above) and npm 12.0.0 will block, Yarn 4.14.0 and later block, pnpm
requires an allow-list entry, and Bun runs the script only for trusted dependencies. When the script is blocked the binary is
not downloaded and Cypress will not start. The fix differs per package manager:

[cols="1,3",options="header"]
|===
|Package manager |Allow the Cypress install script

|npm 11.16 or later
|`npm install-scripts approve cypress --no-allow-scripts-pin` followed by `npm rebuild cypress`, or add `+"allowScripts": { "cypress": true }+` to `package.json`.

|Yarn 4.14 or later
|In `.yarnrc.yml`: `enableScripts: true` and a `npmPreapprovedPackages` list that contains `cypress`. Use `nodeLinker: node-modules`,
because component testing does not work with Plug'n'Play.

|pnpm
|`pnpm --allow-build=cypress add --save-dev cypress`, and turn the side-effects cache off with
`pnpm config set side-effects-cache false --location project`.

|Bun
|`bun pm trust cypress`, or add `+"trustedDependencies": ["cypress"]+` to `package.json`; or run `bun install --ignore-scripts`
followed by `bunx cypress install`.

|Any
|Skip the script and install the binary explicitly: `npx cypress install`.
|===

Source: https://docs.cypress.io/app/get-started/install-cypress#Package-Manager[Cypress -- Install Cypress: Package manager]

== Opening the app: the Launchpad

Cypress has two ways to run tests, which are covered in detail under <<cypress-open-and-cypress-run>>. The first command you
type in a new project is the interactive one:

[source,bash]
----
npx cypress open
----

Source: https://docs.cypress.io/app/get-started/open-the-app[Cypress -- Open the app]

The Cypress *Launchpad* appears. It is the setup wizard for a project and it also decides which browser to start. The first time
it runs in a project it asks three things, in this order:

[mermaid]
....
flowchart LR
    A[npx cypress open] --> B[1. Choose a testing type]
    B --> C[2. Review generated configuration]
    C --> D[3. Pick a browser and click Start]
    D --> E[Specs page in the Cypress app]
....

. *Choose a testing type.* E2E Testing runs your whole application in the browser and visits pages the way a user would.
Component Testing mounts single components in isolation. The choice is not permanent; the other type can be set up later.
. *Review the generated configuration.* The Launchpad lists the files it will create for the chosen type and writes them when you
click Continue: `cypress.config.ts` (or `.js` for a JavaScript project), the support files, and an example fixture. If you chose
Component Testing there are two extra screens first, which detect your front-end framework and bundler and check that the
dependencies are installed.
. *Launch a browser.* The Launchpad shows the compatible browsers it found on the machine, including Electron. You can switch
browser at any time, even in the middle of a session.

Once the project is configured you can skip the wizard by choosing the testing type and the browser on the command line. The
Launchpad still opens briefly, because it handles configuration errors, and then lands directly on the Specs page:

[source,bash]
----
npx cypress open --e2e --browser chrome
----

Source: https://docs.cypress.io/app/core-concepts/open-mode#Launchpad[Cypress -- Open mode: Launchpad]

The Launchpad is the only thing that writes the initial configuration. `cypress run` in a folder without a configuration file does
not scaffold one; it stops. This is the real output:

[source,bash]
----
$ npx cypress run
Could not find a Cypress configuration file in this folder: /path/to/empty-project
----

Source: https://docs.cypress.io/app/references/command-line#cypress-run[Cypress -- Command line: cypress run]

If you prefer to create the files by hand, the section <<the-cypress-configuration-file>> and the folder layout under
<<folder-structure>> are all you need; the Launchpad adds nothing else.

You can use the Cypress app without an account. Signing in to Cypress Cloud from the profile menu adds run history, a Debug page
for CI failures and the AI features of Studio and `cy.prompt`; those are covered in
xref:web/e2e-testing/cypress/cypress-cloud.adoc[Cypress Cloud].

== Choosing a testing type

Cypress names four kinds of test and the Launchpad offers the first two:

[cols="1,3,3",options="header"]
|===
|Type |What it does |Reach for it when

|End-to-end (E2E)
|Visits URLs in a real browser and exercises the whole application, front end to back end and third-party services, the way a
user does.
|Authentication and purchase flows, data that has to survive several screens, smoke tests before a deployment. Slower and harder
to set up, because it needs a running back end.

|Component
|Mounts one component with `cy.mount()` and tests it on its own, in the same real browser. The test lives next to the component.
|Many states and props of a button, a form or a table. Fast and independent of any server, but passing component tests say
nothing about the application as a whole.

|API
|Sends requests with `cy.request()` and asserts on the responses, with no UI.
|The REST contract, and fast set-up of state for UI tests.

|Accessibility
|Checks pages or components against accessibility rules, with an axe-based plugin or the Cypress Accessibility product.
|Catching regressions in labels, roles and contrast early.
|===

A healthy suite combines them, the way the test pyramid recommends. This page and the next ones concentrate on end-to-end tests;
component testing has its own page, xref:web/e2e-testing/cypress/component-testing.adoc[Component Testing].

Source: https://docs.cypress.io/app/core-concepts/testing-types[Cypress -- Testing types]

== Your first end-to-end test

The official tutorial writes a spec against Cypress's own demo site. The same steps against Bookshelf are shown here, so that you
can compare them with the Playwright page in this section. Start Bookshelf in another terminal (the application is described in
xref:web/e2e-testing/example-application-and-test-layout.adoc[Example Application & Test Layout]):

[source,bash]
----
cd bookshelf
PORT=3921 BOOKSHELF_REVIEW_DELAY_MS=100 node server.js
----

Source: https://nodejs.org/docs/latest/api/cli.html[Node.js: Command-line API]

Every Cypress test follows three phases: put the application into a known state, take an action, and assert on the result. The
recommended shape of a chain is query, query, then an action or assertions. In the Cypress vocabulary that becomes four steps:
visit a page, query for an element, interact with it, and assert on the outcome. The spec below contains each step as its own
test. It uses `cy.task('resetBookshelf')` (defined in <<the-cypress-configuration-file>>) to restore the 24 seeded books before
each test, and a custom command `getByTestId` (defined under <<typescript>>):

[source,typescript]
----
// cypress/e2e/first-test.cy.ts
describe('My first Bookshelf test', () => {
  beforeEach(() => {
    cy.task('resetBookshelf');
  });

  it('does not do much', () => {
    expect(true).to.equal(true);
  });

  it('visits the catalogue', () => {
    cy.visit('/books');
    cy.title().should('include', 'Bookshelf');
  });

  it('finds a book, opens it and checks the address', () => {
    cy.visit('/');
    cy.contains('A Field Guide to Clouds').click();
    cy.url().should('include', '/books/3');
    cy.getByTestId('book-detail').should('contain', 'Nora Quill');
  });

  it('types into the search box and filters the catalogue', () => {
    cy.visit('/books');
    cy.getByTestId('search-input').type('quiet{enter}');
    cy.getByTestId('book-card').should('have.length', 1);
    cy.getByTestId('search-input').should('have.value', 'quiet');
  });
});
----

Source: https://docs.cypress.io/app/end-to-end-testing/writing-your-first-end-to-end-test[Cypress -- Write your first test]

The run (headless Chrome, `BASE_URL` pointing at the local server):

[source,bash]
----
BASE_URL=http://localhost:3921 npx cypress run --browser chrome --spec cypress/e2e/first-test.cy.ts
----

[source,text]
----
  │ Cypress:        16.2.0                                                                         │
  │ Browser:        Chrome 155 (headless)                                                          │
  │ Specs:          1 found (first-test.cy.ts)                                                     │

  My first Bookshelf test
    ✓ does not do much (46ms)
    ✓ visits the catalogue (88ms)
    ✓ finds a book, opens it and checks the address (126ms)
    ✓ types into the search box and filters the catalogue (154ms)

  4 passing (440ms)
----

Source: https://docs.cypress.io/app/references/command-line#cypress-run[Cypress -- Command line: cypress run]

A few things in these four tests are worth understanding before moving on:

* `describe`, `it` and the hooks (`before`, `beforeEach`, `afterEach`, `after`) come from *Mocha*, and `expect` and `should`
  assertions come from *Chai*, both bundled with Cypress. You do not install them.
* *Commands retry.* `cy.contains()`, `cy.get()` and the other queries keep looking for their element until it appears or the
  timeout passes. The default `defaultCommandTimeout` is 4000 ms, so a test that looks for something that never appears fails
  after about four seconds, not at once.
* *Many commands assert implicitly.* `cy.visit()` fails on a non-2xx response or an uncaught application exception;
  `cy.contains('text')` fails if the text is not found, even without a `.should()`. You do not need an assertion after every command.
* *Page transitions are handled for you.* After `.click()` navigates to a new page Cypress pauses the command queue until the
  next page has loaded, and raises the timeout to `pageLoadTimeout` (60 seconds by default) for that one page load. Commands never
  run against a stale or half-loaded page.
* *Do not chain after an action.* The shape query, query, action is deliberate: a command that follows an action is not retried
  together with it, so put the next query on a new `cy.` chain, as the search test does with its second `getByTestId`.
* `+type('quiet{enter}')+` types the characters and then presses Enter, which submits the search form. The `+{enter}+` is one of
  the special character sequences of `.type()`.

=== A failing test

The official tutorial makes a test fail on purpose so that you can see what Cypress shows. The spec below looks for text that
Bookshelf does not contain:

[source,typescript]
----
// cypress/e2e/failing-on-purpose.cy.ts
describe('A test that fails on purpose', () => {
  it('cannot find the text "hype"', () => {
    cy.visit('/');
    cy.contains('hype');
  });
});
----

Source: https://docs.cypress.io/app/end-to-end-testing/writing-your-first-end-to-end-test#Step-2-Query-for-an-element[Cypress -- Write your first test: Query for an element]

== Testing your own application

Cypress is built to run against an application you control, on a development server you start yourself. Three rules follow from
that, all from the official guide:

* *Start the server before Cypress, and not from inside a test.* Starting a web server from Cypress scripts is documented as an
  anti-pattern. Start it in a terminal or as a CI step, wait for it to answer, and then run Cypress.
* *Prefer a local server over production.* A local server is one you can control: reset state, seed data, expose routes that exist
  only in the test environment and relax security features that make automation hard. Many teams run most tests locally and keep a
  small set of smoke tests for the deployed site.
* *Do not test sites you do not control.* Third-party sites change without notice, run A/B tests and may block automation. The
  exceptions are sign-in providers and complementary services your application is designed to integrate with.

Set `baseUrl` so that a test never contains the host name, which is the first thing the guide asks you to configure:

[source,typescript]
----
// cypress/e2e/uses-base-url.cy.ts
describe('baseUrl', () => {
  it('prefixes cy.visit and cy.request', () => {
    cy.visit('/');
    cy.location('pathname').should('eq', '/');
    cy.request('/api/books').its('body.total').should('eq', 24);
    expect(Cypress.config('baseUrl')).to.match(/^http:\/\/localhost:\d+$/);
  });
});
----

Source: https://docs.cypress.io/app/end-to-end-testing/testing-your-app#Step-3-Configure-Cypress[Cypress -- Testing your app: Configure Cypress]

The test passed (1 passing). Cypress restarts itself and closes the browser whenever you edit the configuration file, which is
normal; click the spec again to relaunch.

To prepare data, the guide offers two tools: `cy.task()` to run Node.js code defined in `setupNodeEvents`, and `cy.request()` to
call your own HTTP endpoints. Bookshelf has `/api/test/reset` and `/api/test/seed` for this, and the `resetBookshelf` task below
uses the first. The other approach Cypress promotes, replacing server responses with `cy.intercept()`, is covered in
xref:web/e2e-testing/cypress/network-stubs-spies-and-clocks.adoc[Network, Stubs, Spies & Clocks], and signing in once per spec
with `cy.session()` in xref:web/e2e-testing/cypress/sessions-authentication-and-cross-origin.adoc[Sessions, Authentication & Cross-Origin].
Keeping tests independent of each other and of page markup is explained in
xref:web/e2e-testing/test-design-and-page-objects.adoc[Test Design & Page Objects].

== `cypress open` and `cypress run`

Cypress has two modes, and the choice is the main difference between writing a test and running it in a pipeline.

[cols="2,3,3",options="header"]
|===
|Aspect |`cypress open` (open mode) |`cypress run` (run mode)

|Purpose
|Writing and debugging. The Launchpad, the Specs page and the Command Log with time travel.
|Running to completion and exiting with a status. Pre-push checks and CI.
|Browser
|Visible (headed) always.
|Headless by default; `--headed` shows it.
|Specs
|You click a spec; Cypress re-runs it whenever you save the file.
|All specs matching `specPattern`, or the ones selected with `--spec`, one after another.
|Defaults that differ
|`watchForFileChanges` true, `numTestsKeptInMemory` 50, retries 0 (`openMode`).
|`watchForFileChanges` false, `numTestsKeptInMemory` 0, retries 0 (`runMode`), screenshots on failure.
|Output
|The app window.
|The terminal, plus screenshots, optional videos and any reporter.
|Testing type
|Chosen in the Launchpad or with `--e2e` / `--component`.
|E2E by default; `--component` for component tests.
|===

Source: https://docs.cypress.io/app/references/command-line[Cypress -- Command line], https://docs.cypress.io/app/references/configuration[Cypress -- Configuration]

=== Headed and headless

`cypress run` launches the browser headless: no window is drawn, which is what CI needs. Pass `--headed` to see the browser, or
`--headless` to make the default explicit. The header of the run output states what was used. These three commands were run:

[source,bash]
----
npx cypress run --browser chrome --spec cypress/e2e/uses-base-url.cy.ts
#  │ Browser:        Chrome 155 (headless)

npx cypress run --browser chrome --headless --spec cypress/e2e/uses-base-url.cy.ts
#  │ Browser:        Chrome 155 (headless)

npx cypress run --browser chrome --headed --spec cypress/e2e/uses-base-url.cy.ts
#  │ Browser:        Chrome 155
----

Source: https://docs.cypress.io/app/references/launching-browsers#Launching-headed-or-headless[Cypress -- Browser launch options: Launching headed or headless]

`cypress run --headed --no-exit` keeps the browser open after the last spec has finished, so that you can look at the Command
Log or open the browser's developer tools. Headless runs use the same browser engine, but the window size and display configuration can differ between a laptop and a
headless CI machine, so when a test passes headed and fails headless, compare the viewport first. The default viewport is 1000 by 660
(`viewportWidth` and `viewportHeight`); the failure screenshot above was 1280 by 633, so set the viewport explicitly when a
test depends on the layout.

Source: https://docs.cypress.io/app/references/launching-browsers[Cypress -- Browser launch options]

=== Choosing a browser

`--browser` accepts `chrome`, `chromium`, `edge`, `firefox`, `electron` (deprecated) and a `name:channel` form such as
`chrome:canary` or `firefox:nightly`. A file system path points at a browser Cypress did not detect (only Chrome-family browsers
and Firefox are supported). In open mode the Launchpad and a drop-down at the top right of the app select the browser. To make
the choice permanent, set `defaultBrowser` in the configuration file, as the example config below does; it only affects the first
launch of a project.

Source: https://docs.cypress.io/app/references/launching-browsers[Cypress -- Browser launch options]

=== The flags of `cypress run`

These are the options of `cypress run` in Cypress 16. Only the ones named under "Ran" were executed for this page; the others are
quoted from the reference.

[cols="3,5,1",options="header"]
|===
|Option |Effect |Ran

|`--browser`, `-b`
|Browser name or path. Without it, `defaultBrowser`, then Electron.
|yes

|`--e2e` / `--component`
|Testing type. E2E is the default.
|no

|`--spec`, `-s`
|Spec files to run: a path, a quoted glob such as `+"cypress/e2e/login/**/*"+`, or several separated by commas. It can only narrow what
`specPattern` already matches.
|yes

=== Exit codes

By default the exit code of `cypress run` is the number of failed tests, with some reserved values, which is not POSIX
compliant and can mislead: most shells apply modulo 256, so exactly 256 failures look like success. `--posix-exit-codes` makes
the code 1 for any failure and also reports Cypress Cloud network failures as 112. With one failing test both modes returned 1;
the difference only shows with two or more failures, which was not run.

[source,bash]
----
npx cypress run --browser chrome --spec cypress/e2e/failing-on-purpose.cy.ts; echo $?
# 1
npx cypress run --browser chrome --posix-exit-codes --spec cypress/e2e/failing-on-purpose.cy.ts; echo $?
# 1
npx cypress run --pass-with-no-tests --spec cypress/e2e/nothing.cy.ts; echo $?
# 0
npx cypress run --spec cypress/e2e/nothing.cy.ts; echo $?
# 1
----

Source: https://docs.cypress.io/app/references/command-line#Exit-code[Cypress -- Command line: Exit code]

[[the-cypress-configuration-file]]
== The Cypress configuration file

The Launchpad writes `cypress.config.ts` (or `.js`, `.mjs`, `.cjs`, `.mts`, `.cts`) in the project root. It is a normal module
that exports an object, which you should wrap in `defineConfig()` so that editors can complete and check it. The file below is
the one used for every example on this page, and the test project that ran them was a plain folder with the layout shown under
<<folder-structure>>:

[source,typescript]
----
// cypress.config.ts
import { defineConfig } from 'cypress';

const baseUrl = process.env.BASE_URL ?? 'http://localhost:3000';

export default defineConfig({
  // Electron is deprecated as a test browser: name an installed browser explicitly.
  defaultBrowser: 'chrome',
  video: false,
  e2e: {
    baseUrl,
    specPattern: 'cypress/e2e/**/*.cy.ts',
    supportFile: 'cypress/support/e2e.ts',
    setupNodeEvents(on, config) {
      on('task', {
        // Runs in Node, not in the browser: reset Bookshelf through its test API.
        async resetBookshelf() {
          const response = await fetch(`${baseUrl}/api/test/reset`, { method: 'POST' });
          return response.json();
        },
      });
      return config;
    },
  },
});
----

Source: https://docs.cypress.io/app/references/configuration[Cypress -- Configuration], https://docs.cypress.io/app/end-to-end-testing/testing-your-app#Seeding-data[Cypress -- Testing your app: Seeding data]

The file has three levels:

* *Top-level options* apply to both testing types: `defaultBrowser`, `video`, the timeouts, the viewport, `retries`,
  `screenshotsFolder`, `env`, `expose` and so on.
* *The `e2e` object* holds options for end-to-end tests only: `baseUrl`, `specPattern`, `excludeSpecPattern`, `supportFile`,
  `slowTestThreshold`, `testIsolation`, `setupNodeEvents`. A `component` object does the same for component tests, with
  `devServer` as its required option. An option in `e2e` or `component` overrides the same option at the top level for that type.
* *`setupNodeEvents(on, config)`* is a function that runs in Node.js, in the background process, before the project loads, before the
  browser launches and while tests run. It registers listeners with `on()` (such as `task`, `before:run`, `after:screenshot` and
  `before:browser:launch`) and may return a modified `config`. Tests reach it through `cy.task()`. The `resetBookshelf` task
  above is called as `cy.task('resetBookshelf')` and its return value, the JSON the server answers, comes back to the test.
  Tasks run in Node.js, so they can read files and call databases, which a spec running in the browser cannot. The plugin events
  have their own page: xref:web/e2e-testing/cypress/debugging-studio-plugins-and-reporters.adoc[Debugging, Studio, Plugins & Reporters].

=== Overriding configuration

The same option can be set in six places, from the weakest to the strongest: its default, the configuration file, a
`cypress.env.json` file (for `env`), a `CYPRESS_*` environment variable, a command line flag, and an override in the test. The
Project settings panel of the app shows where each resolved value came from.

[cols="2,4",options="header"]
|===
|Where |Example

|Command line
|`+cypress run --config viewportWidth=1280,viewportHeight=720+` or `cypress run --config-file tests/cypress.config.ts`

|Environment variable
|`CYPRESS_VIEWPORT_WIDTH=800` (the option name in upper snake case with the `CYPRESS_` prefix)

|Suite or test
|`+it('shows a warning outside Chrome', { browser: '!chrome' }, () => { ... })+` and `+describe('login', { retries: { runMode: 3, openMode: 2 } }, () => { ... })+`

|Inside a test
|`+Cypress.config('pageLoadTimeout', 100000)+` changes the setting for the rest of the current spec file only. `blockHosts`,
`viewportWidth` and `viewportHeight` can no longer be changed this way during a test (16.0.0); use the test configuration or
`cy.viewport()`.
|===

The following spec reads values that came from the command line and from the environment. It needs a secret and a public
value, and shows the split Cypress 16 enforces:

[source,typescript]
----
// cypress/e2e/config-and-env.cy.ts
describe('Configuration, secrets and public values', () => {
  it('uses the viewport passed with --config', () => {
    cy.log(`isInteractive = ${Cypress.config('isInteractive')}`);
    cy.window().its('innerWidth').should('eq', Cypress.config('viewportWidth'));
  });

  it('reads a secret with cy.env() and a public value with Cypress.expose()', () => {
    cy.env(['READER_PASSWORD']).then(({ READER_PASSWORD }) => {
      expect(READER_PASSWORD).to.be.a('string').and.not.be.empty;
    });
    expect(Cypress.expose('channel')).to.equal('smoke');
  });
});
----

[source,bash]
----
CYPRESS_READER_PASSWORD="$BOOKSHELF_READER_PASSWORD" npx cypress run --browser chrome \
  --spec cypress/e2e/config-and-env.cy.ts \
  --config viewportWidth=1280,viewportHeight=720 \
  --expose channel=smoke
----

[source,text]
----
  Configuration, secrets and public values
    ✓ uses the viewport passed with --config (26ms)
    ✓ reads a secret with cy.env() and a public value with Cypress.expose() (12ms)

  2 passing (52ms)
----

Source: https://docs.cypress.io/app/references/configuration#Overriding-Options[Cypress -- Configuration: Overriding options], https://docs.cypress.io/app/references/command-line#cypress-run-expose-expose[Cypress -- Command line: cypress run --expose]

`Cypress.env()` no longer exists in Cypress 16: a `CYPRESS_` variable is read with `cy.env()` (asynchronous, and only the keys
you ask for are exposed to the page) and public values with `Cypress.expose()`. The migration, `cy.origin()` behaviour and the
risks of the yielded value are covered in
xref:web/e2e-testing/cypress/sessions-authentication-and-cross-origin.adoc[Sessions, Authentication & Cross-Origin].

=== ESM or CommonJS

Since Cypress 15.17.0 the configuration and everything `setupNodeEvents` imports are loaded as ECMAScript modules or as
CommonJS using the same rules as Node.js, and there is no fallback to the other format when loading fails.

[cols="2,2,2",options="header"]
|===
|Config file |Nearest `package.json` `"type"` |Loaded as

|`.mjs` or `.mts`
|any
|ES module

|`.cjs` or `.cts`
|any
|CommonJS

|`.js` or `.ts`
|`"module"`
|ES module

|`.js` or `.ts`
|absent or `"commonjs"`
|CommonJS
|===

The project that ran these examples is CommonJS (`"type": "commonjs"`), so `import` and `export default` in the `.ts` file are
transpiled to `require` and `module.exports`. If you move to `"type": "module"`, remember that `__dirname` does not exist in an
ES module and `import.meta.dirname` takes its place.

Source: https://docs.cypress.io/app/references/configuration#ESM-vs-CommonJS[Cypress -- Configuration: ESM vs CommonJS]

=== Generated files are emptied before every run

With `trashAssetsBeforeRuns` on, `cypress run` removes the entire contents of the screenshots, videos and downloads folders at
the start of each run, subfolders included, so a download you keep there is lost. On macOS and Windows items go to the system
trash and on Linux they are deleted for good. On the Apple Silicon host used for this page the trash step failed on every run
with the message below and the old screenshots piled up as `(1)`, `(2)` copies; the run itself and its exit code were not
affected. Keep nothing you need in those folders, and ignore the warning if you see it on a similar host.

[source,text]
----
Warning: We failed to trash the existing run results.

This error will not affect or change the exit code.
----

Source: https://docs.cypress.io/app/references/configuration#trashAssetsBeforeRuns[Cypress -- Configuration: trashAssetsBeforeRuns]

[[typescript]]
== TypeScript

Cypress ships its own type declarations and understands TypeScript natively: specs, support files and the configuration file can
all be `.ts` with no build step. Cypress transpiles specs itself, and since Cypress 15.0.0 it runs the configuration file with
`tsx` (earlier versions used `ts-node`). It does not type-check; the editor and `tsc` do.

Install TypeScript 5, 6 or 7 (TypeScript 6.0 support arrived in 15.14.0 and TypeScript 7.0 in 15.19.0) together with the Node.js
types, and create a `tsconfig.json` that limits the global types to the ones Cypress needs. Limiting `types` also avoids clashes
when the project has Jest or another test runner that declares its own `describe`, `it` and `expect`:

[source,json]
----
{
  "compilerOptions": {
    "target": "es2022",
    "lib": ["es2022", "dom"],
    "sourceMap": true,
    "types": ["cypress", "node"]
  },
  "include": ["**/*.ts"]
}
----

Source: https://docs.cypress.io/app/tooling/typescript-support[Cypress -- TypeScript support]

The official page recommends `es6` as target and library; a newer target works equally well and was used here. Without
`@types/node` installed, TypeScript 7.0.2 stops with `error TS2688: Cannot find type definition file for 'node'` because
`"node"` is listed in `types`; installing `@types/node` fixes it, after which `npx tsc --noEmit` reported no errors for the whole
project (the specs, the configuration and the support files).

=== Custom commands need declarations

A command added with `Cypress.Commands.add()` is invisible to TypeScript until you declare it on the `Cypress.Chainable`
interface. Put both in `cypress/support/commands.ts`, which the support file imports. The file must be a module, so end it with an
empty `export {}`; otherwise `declare global` is an error. This is the command the first-test spec uses:

[source,typescript]
----
// cypress/support/commands.ts
declare global {
  namespace Cypress {
    interface Chainable {
      /** Select an element by its data-testid attribute. */
      getByTestId(id: string): Chainable<JQuery<HTMLElement>>;
    }
  }
}

Cypress.Commands.add('getByTestId', (id: string) => cy.get(`[data-testid="${id}"]`));

export {};
----

[source,typescript]
----
// cypress/support/e2e.ts
import './commands';
----

Source: https://docs.cypress.io/app/tooling/typescript-support#Types-for-Custom-Commands[Cypress -- TypeScript support: Types for custom commands]

Other declarations follow the same pattern and are covered with custom commands and queries in
xref:web/e2e-testing/cypress/queries-assertions-and-custom-commands.adoc[Queries, Assertions & Custom Commands]: child commands
need the `prevSubject` option, `Cypress.Commands.overwrite<'type', 'element'>()` needs generics, custom queries are declared
before `addQuery()`, properties your application adds to `window` extend `Cypress.ApplicationWindow`, and a standalone `.d.ts`
file may declare `namespace Cypress` directly if it has no imports (when it does, use `declare global`). Make sure every
`tsconfig.json` that should see a declaration file includes it.

If the editor does not pick up the types, restart its TypeScript server (in VS Code, the command "TypeScript: Restart TS Server").

For configuration files, `defineConfig()` infers the types of `setupNodeEvents(on, config)` automatically. For a function kept
in another file, annotate it with `Cypress.PluginConfig`. Align `compilerOptions.module` with how the file loads: `commonjs` for a
`cypress.config.cts` or a CommonJS project, `NodeNext` or `ES2022` for `cypress.config.mts` or `"type": "module"`.

Source: https://docs.cypress.io/app/tooling/typescript-support#Processing-your-Cypress-configuration-and-plugins[Cypress -- TypeScript support: Processing your Cypress configuration and plugins]

=== Specs and the `.cy.` rule

Cypress loads only files that match `specPattern`, and the default pattern needs the *`.cy.` infix*. A file called
`cypress/e2e/login.ts` is invisible; `cypress/e2e/login.cy.ts` is a spec. That convention lets helpers and specs live in the
same folder without Cypress trying to run helpers. If a spec does not appear, the file name is the first thing to check. Three
settings work together:

* `specPattern` is the master list of what counts as a spec.
* `excludeSpecPattern` subtracts files from that list.
* `--spec` picks which of the remaining specs run this time. It can never add a file outside `specPattern`: a spec at
  `tests/login.cy.ts` is not found by `--spec` until `specPattern` also includes `+tests/**+`.

If specs still do not show up, run Cypress with `DEBUG=cypress:cli,cypress:data-context:sources:FileDataSource,cypress:data-context:sources:ProjectDataSource`
to see how it searches.

As a rule of thumb use one spec for a feature or user flow, with `describe()` blocks for related scenarios. Cypress reloads the
browser, the support file and the application for every spec, so many tiny specs are slower, and it distributes whole specs when
you parallelize, so one very long spec delays the run.

Source: https://docs.cypress.io/app/core-concepts/writing-and-organizing-tests#How-Cypress-finds-your-specs[Cypress -- Writing and organizing tests: How Cypress finds your specs]

=== Support files, fixtures and node events

* The *support file* (`cypress/support/e2e.ts`) runs before every spec file. It is the place for custom commands, global
  `beforeEach` hooks and overrides. It is bundled together with everything it imports, so keep it lean and never import Node.js-only
  code such as `fs` into it.
* *Fixtures* (`cypress/fixtures`) are static data loaded with `cy.fixture()`, with `cy.intercept()` `+{ fixture: 'users.json' }+`, or
  attached to an upload with `.selectFile()`. Use `cy.readFile()` for files that change while the test runs and `cy.task()`
  for large files or work that needs Node.js.
* *Specs* may be `.js`, `.jsx`, `.ts` or `.tsx`, may use ES modules or CommonJS and may import local modules and npm packages.
  The bundle runs in the browser, so a module that needs `fs` must run inside a task.

Source: https://docs.cypress.io/app/core-concepts/writing-and-organizing-tests#Support-file[Cypress -- Writing and organizing tests: Support file]

== IDE integration

Cypress works with any editor that understands JavaScript or TypeScript. Five steps give a fully configured editor:

. *Turn on IntelliSense.* With a `tsconfig.json` that lists `"types": ["cypress"]` (as above) every `cy.` command completes in
  VS Code, Visual Studio and WebStorm, which have TypeScript support built in; other editors need an extra TypeScript plugin. In a
  JavaScript project add `/// <reference types="cypress" />` to the top of each spec, or a `jsconfig.json` with
  `+"include": ["./node_modules/cypress", "cypress/**/*.js"]+`. If completion fails, check that the right `tsconfig.json` covers
  the spec files, restart the TypeScript server, select the workspace TypeScript version and look for a clash with Jest types.
. *Lint.* The official `eslint-plugin-cypress` declares the Cypress and Mocha globals so that spec files do not report undefined
  variables, and has rules that flag anti-patterns while you type.
. *Choose your file opener.* The first time you click a file path or an error in the Command Log, Cypress asks where to open
  files: the file system, an IDE it found, or an application path. Change it later in the Settings tab of the app.
. *Install extensions where useful.* Community extensions add running specs from the editor and navigating to custom commands:
  Cypress Test Explorer, Cypress Helper and Test Utils for Visual Studio Code (and forks such as Cursor, which use the Open VSX
  registry, so some are missing there), the JetBrains "Test Automation" plugin (official) and Cypresso for JetBrains IDEs, and
  `vim-test` for Vim and Neovim. Commit a `.vscode/extensions.json` with the recommended extensions so that every teammate is
  offered them.
. *Add AI tooling if you use an assistant.* `npx skills add cypress-io/ai-toolkit` installs the Cypress AI Skills, and the Cloud
  MCP server connects an assistant to recorded runs. They are covered in
  xref:web/e2e-testing/ai-agents/ai-features-in-cypress-and-selenium.adoc[AI Features in Cypress & Selenium] and were not run
  for this page.

[source,json]
----
{
  "recommendations": [
    "dbaeumer.vscode-eslint",
    "dpanshug.cypress-test-explorer"
  ]
}
----

Source: https://docs.cypress.io/app/tooling/IDE-integration[Cypress -- IDE integration]

Debugging differs from what Playwright users may expect: a Cypress test runs in the browser, not in Node.js, so your editor's
Node debugger cannot attach to a test. Debug tests with the browser's developer tools together with `debugger`, `.debug()` and
`cy.pause()`. The editor's Node debugger does apply to `setupNodeEvents` and to `cy.task()` code, which do run in Node.js. These
tools are covered in xref:web/e2e-testing/cypress/debugging-studio-plugins-and-reporters.adoc[Debugging, Studio, Plugins & Reporters].
Cypress Studio also opens a code panel beside the running test, so you can edit a test while you watch it.

Source: https://docs.cypress.io/app/tooling/IDE-integration#Debugging-from-your-IDE[Cypress -- IDE integration: Debugging from your IDE]

== Common pitfalls

* *The binary is missing* because a package manager blocked the `postinstall` script. Allow the script or run `npx cypress install`.
* *Running on Electron without noticing.* Set `defaultBrowser` or pass `--browser`, and look at the `Browser:` line of the run
  output.
* *A spec that does not appear.* The file name lacks `.cy.`, or lives outside `specPattern`.
* *`baseUrl` not set.* Every test then repeats the host name, and relative paths such as `cy.visit('/')` cannot resolve.
* *The server was not running* when Cypress started. Cypress cannot start it for you; start it first and wait for it.
* *Chaining after an action.* Commands after `.click()` or `.type()` on the same chain are not retried together with the
  action; begin a new `cy.` chain.
* *Assuming `Cypress.env()` still works.* It was removed in 16.0.0; use `cy.env()` and `Cypress.expose()`.
* *Expecting a 10 ms keystroke delay.* Typing is instant since 16.0.0; set `keystrokeDelay: 10` if your application needs
  slower input.
* *Secrets on the command line.* `--env` values can appear in CI logs; use `CYPRESS_*` variables or the CI secret store.
* *TypeScript errors on custom commands.* The declaration is missing, the file has no `export {}`, or the `tsconfig.json` that
  covers it does not list the declaration file.
* *Keeping files in the generated folders.* They are emptied before every `cypress run`.
