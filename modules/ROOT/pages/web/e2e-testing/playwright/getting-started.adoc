Playwright Test is the end-to-end test runner that ships with Playwright: it bundles the runner, the assertions, test
isolation, parallelism and the tooling (HTML report, UI Mode, trace viewer, code generator) in one package. This page takes
you from an empty folder to a running suite and then through every day-to-day command. It was written against Playwright
1.64.1 for Node.js (the Python, Java and .NET examples elsewhere in this section were run at 1.63) and checked on 25 October
2026. Every example that tests an application was run against the
xref:web/e2e-testing/example-application-and-test-layout.adoc[Bookshelf] application, a small catalogue of books started on
a local port; the scaffolding commands were run in an empty folder. For why Playwright works the way it does, see
xref:web/e2e-testing/how-browser-automation-works.adoc[How Browser Automation Works]; for choosing it over Cypress or
Selenium, see xref:web/e2e-testing/choosing-a-tool.adoc[Choosing a Tool].

== System requirements

Playwright 1.64 documents these requirements:

[cols="1,3",options="header"]
|===
|Item |Requirement

|Node.js
|The latest 22.x, 24.x or 26.x release.

|Windows
|Windows 11 or later, Windows Server 2019 or later, or Windows Subsystem for Linux (WSL).

|macOS
|macOS 14 (Sonoma) or later.

|Linux
|Debian 12 or 13, Ubuntu 22.04, 24.04 or 26.04, on x86-64 or arm64.
|===

Playwright runs Chromium, WebKit and Firefox on Windows, Linux and macOS, locally or in CI, headless or headed. It also
offers native mobile emulation for Chrome on Android and Mobile Safari. The browsers are not the ones installed on your
machine: each Playwright version downloads the exact builds it was tested with, so a test behaves the same on a laptop and
in CI. 1.64 ships Chromium 156, Firefox 157 and WebKit 27.2.

Support for an operating system version is dropped from time to time: release 1.59 removed WebKit support for macOS 14 and
release 1.61 added Ubuntu 26.04, so re-check the requirements when you upgrade the operating system or Playwright.

Source: https://playwright.dev/docs/intro#system-requirements[Playwright -- Installation: System requirements]

== Installing Playwright

=== Scaffolding with `npm init playwright@latest`

The command below either initialises a new project or adds Playwright to an existing one. It is a thin wrapper around the
`create-playwright` package, so `yarn create playwright` and `pnpm create playwright` do the same.

[source,bash]
----
mkdir bookshelf-e2e && cd bookshelf-e2e
npm init playwright@latest
----

Source: https://playwright.dev/docs/intro#installing-playwright[Playwright -- Installation]

Run interactively, it asks four questions:

* TypeScript or JavaScript (the default is TypeScript).
* The name of the tests folder (`tests`, or `e2e` if `tests` already exists).
* Whether to add a GitHub Actions workflow (recommended when you run tests in CI).
* Whether to install the Playwright browsers (the default is yes).

You can re-run the command later; it does not overwrite existing tests. For scripts and CI the same choices are flags:

[cols="2,3",options="header"]
|===
|Flag |Effect

|`--quiet`
|Do not ask any question; use the defaults and the other flags.

|`--lang=TypeScript` or `--lang=js`
|Language of the generated config and example test.

|`--browser=chromium` (repeatable)
|Browsers to put in the default config. Without it the config lists `chromium`, `firefox` and `webkit`.

|`--no-browsers`
|Do not download browsers; run `npx playwright install` yourself later.

|`--no-examples`
|Do not create the example test files.

|`--install-deps`
|Also install the operating system packages the browsers need (Linux).

|`--gha`
|Add a GitHub Actions workflow.

|`--next`, `--beta`
|Install the `next` or `beta` npm tag of Playwright (see <<_canary_releases,Canary releases>>).

|`--ct`
|Install Playwright component testing (see xref:web/e2e-testing/playwright/component-testing.adoc[Component Testing]).
|===

This run, in an empty folder, created a TypeScript project with a single browser:

[source,bash]
----
npm init playwright@latest -- --quiet --lang=TypeScript --browser=chromium
----

....
Writing playwright.config.ts.
Writing tests/example.spec.ts.
Writing package.json.
Downloading browsers (npx playwright install chromium)…
✔ Success! Created a Playwright Test project at .../ex-getting-started-init

Inside that directory, you can run several commands:

  npx playwright test
    Runs the end-to-end tests.

  npx playwright test --ui
    Starts the interactive UI mode.

  npx playwright test --project=chromium
    Runs the tests only on Desktop Chrome.

  npx playwright test example
    Runs the tests in a specific file.

  npx playwright test --debug
    Runs the tests in debug mode.

  npx playwright codegen
    Auto generate tests with Codegen.
....

Source: https://playwright.dev/docs/intro#installing-playwright[Playwright -- Installation]

=== What is installed

The scaffold is small:

[source,text]
----
playwright.config.ts   # test configuration
package.json           # @playwright/test and @types/node as devDependencies
package-lock.json
.gitignore             # node_modules, test-results, playwright-report, blob-report, playwright/.auth
tests/
  example.spec.ts      # a minimal starter test
----

In an existing project Playwright adds its dependencies to the current `package.json`. The generated `package.json`
lists `@playwright/test` with a caret range (`+^1.64.1+` here) and `@types/node`. Pin the exact version
(`npm install -D --save-exact @playwright/test@1.64.1`) if you want builds that are reproducible between a laptop and CI
months apart, because every Playwright release changes the browser builds it expects.

The generated configuration, with its explanatory comments and commented-out examples removed, was:

[source,typescript]
----
import { defineConfig, devices } from '@playwright/test';

export default defineConfig({
  testDir: './tests',
  fullyParallel: true,
  forbidOnly: !!process.env.CI,
  retries: process.env.CI ? 2 : 0,
  workers: process.env.CI ? 1 : undefined,
  reporter: 'html',
  use: {
    trace: 'on-first-retry',
  },
  projects: [
    {
      name: 'chromium',
      use: { ...devices['Desktop Chrome'] },
    },
  ],
});
----

Source: https://playwright.dev/docs/intro#whats-installed[Playwright -- Installation: What's installed]

Each setting has a reason:

* `testDir` is where Playwright looks for `+*.spec.ts+` and `+*.test.ts+` files.
* `fullyParallel: true` runs the tests of one file in parallel too, not just different files.
* `forbidOnly` makes the run fail in CI if someone committed `test.only`.
* `retries` is 2 in CI and 0 locally, so a flaky test is reported as "flaky" instead of hiding.
* `workers` is left to the default locally (half of the logical CPU cores) and set to 1 in CI.
* `+reporter: 'html'+` writes the report described in <<_the_html_report,The HTML report>>.
* `+trace: 'on-first-retry'+` records a trace when a test is retried.
* `projects` is the list of browser configurations. Without `--browser` the scaffold lists Chromium, Firefox and WebKit.

All of these are explained in
xref:web/e2e-testing/playwright/configuration-fixtures-and-projects.adoc[Configuration, Fixtures & Projects]. The server that
the tests talk to is not part of the scaffold; for Bookshelf the layout in
xref:web/e2e-testing/example-application-and-test-layout.adoc[Example Application & Test Layout] adds `baseURL` and
`testIdAttribute` to the `use` block.

=== Installing browsers

`npm init playwright@latest` runs `npx playwright install` for you. You run it yourself when you skipped that step, when
you upgrade Playwright (each version needs its own browser builds) and in CI.

[source,bash]
----
npx playwright install                       # the default browsers
npx playwright install chromium              # only Chromium
npx playwright install chromium webkit       # a selection
npx playwright install --with-deps           # browsers plus operating system packages
npx playwright install --help                # all the browsers that can be installed
----

Source: https://playwright.dev/docs/browsers#install-browsers[Playwright -- Browsers: Install browsers]

The options of `playwright install`:

[cols="2,4",options="header"]
|===
|Option |Effect

|`--with-deps`
|Install the system dependencies of the browsers too (Linux packages through `apt`).

|`--dry-run`
|Do not install; print what would be installed and where.

|`--list`
|Print the browsers of every Playwright installation on the machine.

|`--force`
|Reinstall browsers that are already installed.

|`--only-shell`
|Install only `chromium-headless-shell` instead of full Chromium. Enough when tests only run headless with the default channel.

|`--no-shell`
|Do not install `chromium-headless-shell`. Use it when you run the "new headless mode" with full Chromium.

|`--no-progress`
|Hide the download progress bars (useful in CI logs).

|`--no-remove`
|Keep browsers that the current version no longer uses.
|===

`npx playwright uninstall` removes the browsers of the current installation, and `npx playwright clear-cache` clears
Playwright's caches. A dry run shows what Playwright 1.64.1 downloads for the platform:

----
npx playwright install --dry-run

Since release 1.57 Playwright uses Chrome for Testing builds instead of Chromium: headed mode runs `chrome` and headless
mode runs `chrome-headless-shell`, which is why both are downloaded. The browsers occupy a few hundred megabytes each;
`PLAYWRIGHT_BROWSERS_PATH` moves them to another folder (set it for both `install` and `test`). Behind a proxy, set
`HTTPS_PROXY`; with an internal artifact repository, set `PLAYWRIGHT_DOWNLOAD_HOST` (or the per-browser
`PLAYWRIGHT_CHROMIUM_DOWNLOAD_HOST`, `PLAYWRIGHT_FIREFOX_DOWNLOAD_HOST`, `PLAYWRIGHT_WEBKIT_DOWNLOAD_HOST`); and when a
download stalls, raise the idle timeout with `PLAYWRIGHT_DOWNLOAD_CONNECTION_TIMEOUT` (milliseconds, default 30 seconds).

Playwright can also drive an installed Google Chrome or Microsoft Edge through the `channel` option; `npx playwright install
msedge` installs Edge, and it overwrites an existing installation at the default system location.

=== System dependencies on Linux

A freshly installed Linux machine or container usually lacks the shared libraries the browsers need (fonts, GTK, audio and
so on). `install-deps` installs them with the system package manager and asks for `sudo`:

[source,bash]
----
npx playwright install-deps            # dependencies of all browsers
npx playwright install-deps chromium   # dependencies of one browser
npx playwright install --with-deps chromium   # browsers and dependencies in one command
npx playwright install-deps --dry-run  # simulate; on Linux exits non-zero if packages are missing
----

Source: https://playwright.dev/docs/browsers#install-system-dependencies[Playwright -- Browsers: Install system dependencies]

`install-deps --dry-run` does not change the system, which makes it usable in a verification script. On Windows it prints
the install command; on macOS and Windows the browsers bring what they need. Behind a proxy on Linux run the command as root
(`+sudo HTTPS_PROXY=... npx playwright install-deps+`), otherwise Playwright elevates itself and the variable does not reach
the package manager. The `install-deps` step was not run on this macOS host because it applies to Linux only.

== Your first test

The scaffold's `tests/example.spec.ts` tests the Playwright website, which is fine to see a green run but proves nothing
about your own application. This version of it tests Bookshelf. It needs no configuration beyond a `baseURL`, so `+page.goto('/')+`
resolves against the running server.

[source,typescript]
----
import { test, expect } from '@playwright/test';

test('home page has a title and a search form', async ({ page }) => {
  await page.goto('/');

  await expect(page).toHaveTitle(/Bookshelf/);
  await expect(page.getByTestId('search-input')).toBeVisible();
});

test('search narrows the catalogue to one book', async ({ page }) => {
  await page.goto('/books');

  await page.getByTestId('search-input').fill('quiet');
  await page.getByRole('button', { name: 'Search' }).click();

  await expect(page.getByTestId('book-card')).toHaveCount(1);
  await expect(page.getByRole('heading', { name: 'The Quiet Compiler' })).toBeVisible();
});
----

Source: https://playwright.dev/docs/writing-tests#first-test[Playwright -- Writing tests: First test]

The configuration used to run these examples:

[source,typescript]
----
import { defineConfig, devices } from '@playwright/test';

export default defineConfig({
  testDir: '.',
  outputDir: './test-results',
  reporter: [['list'], ['html', { outputFolder: './playwright-report', open: 'never' }]],
  use: {
    baseURL: process.env.BASE_URL,
    testIdAttribute: 'data-testid',
    trace: 'on-first-retry',
  },
  projects: [
    { name: 'chromium', use: { ...devices['Desktop Chrome'] } },
    { name: 'webkit', use: { ...devices['Desktop Safari'] } },
  ],
});
----

Source: https://playwright.dev/docs/test-configuration[Playwright -- Test configuration]

A test is a function passed to `test()`. Its argument is an object of *fixtures*: `page` is a new page in a new browser
context, created for this test and discarded afterwards. The body performs actions and asserts the state, and nothing in it
waits explicitly. Section <<_writing_tests,Writing tests>> explains the pieces.

== Writing tests

=== Navigation

Most tests start with `page.goto()`. A relative URL is resolved against `baseURL`; an absolute URL is used as is. Playwright
waits for the page to reach the `load` state before it continues. `goto` accepts `waitUntil` (`load`, `domcontentloaded`,
`networkidle`, `commit`), `timeout` and `referer` for the cases where `load` is the wrong signal, for example a page that
keeps a connection open.

[source,typescript]
----
await page.goto('/books?q=quiet');
await page.goto('/books/3', { waitUntil: 'domcontentloaded' });
----

Source: https://playwright.dev/docs/writing-tests#navigation[Playwright -- Writing tests: Navigation]

=== Actions

Actions start with a *locator*, a description of how to find an element that Playwright evaluates again each time it is
used. Before it acts, Playwright waits for the element to be actionable (attached, visible, stable, enabled and able to
receive events), so a test needs no sleeps and does not race the page. The most used actions:

[cols="2,3",options="header"]
|===
|Action |Description

|`locator.click()`
|Click the element.

|`locator.fill()`
|Fill a form field with text.

|`locator.check()` and `locator.uncheck()`
|Check or uncheck a checkbox or radio button.

|`locator.selectOption()`
|Select an option in a drop-down.

|`locator.press()`
|Press a single key.

|`locator.hover()` and `locator.focus()`
|Hover the mouse over the element or focus it.

|`locator.setInputFiles()`
|Pick files to upload.
|===

Source: https://playwright.dev/docs/writing-tests#basic-actions[Playwright -- Writing tests: Basic actions]

The complete list of locators and actions, with the actionability rules, is in
xref:web/e2e-testing/playwright/locators-actions-and-auto-waiting.adoc[Locators, Actions & Auto-Waiting].

=== Assertions

`expect(value)` plus a matcher states what must be true. Matchers that take a locator or a page are *web-first*: they retry
until the condition holds or the assertion timeout (5 seconds by default) expires. They need `await`. The popular ones:

[cols="2,3",options="header"]
|===
|Assertion |Description

|`expect(locator).toBeVisible()`
|The element is visible.

|`expect(locator).toBeEnabled()` and `toBeChecked()`
|The control is enabled or checked.

|`expect(locator).toHaveText()` and `toContainText()`
|The text matches exactly or contains the value.

|`expect(locator).toHaveAttribute()` and `toHaveValue()`
|The element has the attribute or the input has the value.

|`expect(locator).toHaveCount()`
|A list of elements has the given length.

|`expect(page).toHaveTitle()` and `toHaveURL()`
|The page has the given title or URL.
|===

Source: https://playwright.dev/docs/writing-tests#assertions[Playwright -- Writing tests: Assertions]

Generic matchers such as `toEqual`, `toContain` and `toBeTruthy` check a value that already exists, so they are synchronous
and take no `await`. Using `expect(await locator.isVisible()).toBe(true)` instead of a web-first matcher throws the retry
away and is the usual source of flaky tests. See xref:web/e2e-testing/playwright/assertions.adoc[Assertions].

=== Test isolation

Each test gets its own browser context, the equivalent of a brand new browser profile with its own cookies, local storage and
session storage, even when many tests share one browser process. The two tests below pass in any order because the second
starts with empty storage, whichever worker runs it.

[source,typescript]
----
import { test, expect } from '@playwright/test';

test('dark theme is stored in this test only', async ({ page }) => {
  await page.goto('/');
  await page.getByTestId('theme-toggle').click();
  const stored = await page.evaluate(() => localStorage.getItem('theme'));
  expect(stored).not.toBeNull();
});

test('a second test starts with empty local storage', async ({ page }) => {
  await page.goto('/');
  const stored = await page.evaluate(() => localStorage.getItem('theme'));
  expect(stored).toBeNull();
});
----

Source: https://playwright.dev/docs/writing-tests#test-isolation[Playwright -- Writing tests: Test isolation]

Isolation covers the browser, not the server. State on the server (the Bookshelf reviews, for example) is shared, which is
why the examples reset it through the test API; see
xref:web/e2e-testing/test-design-and-page-objects.adoc[Test Design & Page Objects] and
xref:web/e2e-testing/playwright/authentication-and-isolation.adoc[Authentication & Isolation].

=== Test hooks

`test.describe()` groups tests. `test.beforeEach()` and `test.afterEach()` run around every test of the group;
`test.beforeAll()` and `test.afterAll()` run once per worker. Hooks receive the same fixtures as tests, except that
`beforeAll` and `afterAll` cannot use `page` (it is per test) but can use `request` and `browser`.

[source,typescript]
----
import { test, expect } from '@playwright/test';

test.describe('catalogue', () => {
  test.beforeAll(async ({ request }) => {
    // Once per worker: restore the 24 seeded books.
    await request.post('/api/test/reset');
  });

  test.beforeEach(async ({ page }) => {
    // Before every test: start on the first page of the catalogue.
    await page.goto('/books');
  });

  test('shows six books per page', async ({ page }) => {
    await expect(page.getByTestId('book-card')).toHaveCount(6);
  });

  test('next page changes the indicator', async ({ page }) => {
    await page.getByTestId('page-next').click();

    await expect(page).toHaveURL(/page=2/);
    await expect(page.getByTestId('page-indicator')).toContainText('2');
  });

  test.afterEach(async ({ page }, testInfo) => {
    console.log(`${testInfo.title}: ${testInfo.status}`);
  });
});
----

Source: https://playwright.dev/docs/writing-tests#using-test-hooks[Playwright -- Writing tests: Using test hooks]

In a real suite prefer fixtures to `beforeEach` for shared set-up, because a fixture runs only for the tests that ask for it
and cleans up after itself; see
xref:web/e2e-testing/playwright/configuration-fixtures-and-projects.adoc[Configuration, Fixtures & Projects].

=== Tags in tests

A test can carry tags, either as `@name` in its title or in the `tag` option (a string or an array). The command line
selects them with `--grep`. The tag in the `tag` option is not part of the title, but `--grep` matches it.

[source,typescript]
----
import { test, expect } from '@playwright/test';

test('catalogue lists books @smoke', async ({ page }) => {
  await page.goto('/books');
  await expect(page.getByTestId('book-list')).toBeVisible();
});

test('book detail shows a cover', { tag: '@detail' }, async ({ page }) => {
  await page.goto('/books/1');
  await expect(page.getByTestId('book-cover')).toBeVisible();
});

test('add a review needs a session', async ({ page }) => {
  await page.goto('/books/1');
  await expect(page.getByTestId('review-form')).toHaveCount(0);
});
----

Source: https://playwright.dev/docs/test-annotations#tag-tests[Playwright -- Annotations: Tag tests]

=== Selecting what to run

Positional arguments are regular expressions matched against the full path of the test file. `file:line` selects the test
that starts at that line.

[source,bash]
----
npx playwright test tests/todo-page/ tests/landing-page/   # directories
npx playwright test landing login                          # files whose path contains landing or login
npx playwright test first-test.spec.ts:10                  # the test declared at line 10
npx playwright test --project=chromium                     # one project (repeat the flag for several)
npx playwright test --project webkit --project chromium
npx playwright test -g "add a review"                      # titles matching a regular expression
npx playwright test -g @smoke                              # tests tagged @smoke
npx playwright test --grep-invert "@smoke|@detail"         # everything else
npx playwright test --list                                 # collect and print, do not run
----

Source: https://playwright.dev/docs/running-tests#run-specific-tests[Playwright -- Running tests: Run specific tests]

=== Command line options

`npx playwright test --help` is the authoritative list. The ones used most:

[cols="3,5",options="header"]
|===
|Option |Effect

|`--headed`
|Run in headed browsers (the default is headless).

|`+--project <name...>+`
|Only run these projects; supports a `+*+` wildcard.

|`-g <regex>`, `--grep <regex>`
|Only run tests whose title (or tag) matches.

|`-G <regex>`, `--grep-invert <regex>`
|Only run tests that do not match.

|`-j <n>`, `--workers <n>`
|Number of concurrent workers, or a percentage of the logical CPU cores. `1` runs everything in one worker. The default is 50 percent.

|`--fully-parallel`
|Run all tests in parallel, including those in one file.

|`--ui`
|Open UI Mode. `--ui-host` and `--ui-port` serve it on a host and port and open it in a browser tab.

|`--debug [mode]`
|Run with the Playwright Inspector. A shortcut for `PWDEBUG=1` with `--timeout=0 --max-failures=1 --headed --workers=1`. The mode `cli` attaches over `playwright-cli` for coding agents.

|`--reporter <name>`
|Replace the configured reporters. Comma separated: `dot`, `line`, `list`, `html`, `json`, `junit`, `github`, `blob`, or a path to a custom reporter.

|`--add-reporter <name>`
|Add reporters on top of those in the config instead of replacing them.

|`--last-failed`
|Re-run only the tests that failed in the last run.

|`--last-failed-file <file>`
|Where the failed tests are stored (default `<outputDir>/.last-run.json`, or `PLAYWRIGHT_LAST_RUN_OUTPUT_FILE`).

|`--retries <n>`
|Maximum retries for failing tests.

|`--repeat-each <n>`
|Run each test `n` times, useful for hunting flaky tests.

|`-x`, `--max-failures <n>`
|Stop after the first (or `n`) failures.

|`--timeout <ms>`
|Test timeout (default 30 seconds; 0 for none).

|`--trace <mode>`
|Force a trace mode: `on`, `off`, `on-first-retry`, `on-all-retries`, `retain-on-failure`, `retain-on-first-failure`, `retain-on-failure-and-retries`.

|`--shard <current/all>`
|Run one slice of the suite, for example `3/5`.

|`--shuffle [seed]`
|Run in random order; the seed is printed so a failing order can be reproduced.

|`--only-changed [ref]`
|Run only test files changed since `ref` (Git only).

|`--test-list <file>`, `--test-list-invert <file>`
|Run (or skip) the tests listed in a file.

|`-u`, `--update-snapshots [mode]`
|Update screenshot and snapshot baselines.

|`--forbid-only`, `--fail-on-flaky-tests`
|Fail the run if `test.only` is present or if any test was flaky. Useful in CI.

|`--pass-with-no-tests`
|Succeed even when no tests are found.

|`--global-timeout <ms>`
|Maximum time for the whole run.

|`-c <file>`, `--config <file>`
|Configuration file, or a folder that contains `playwright.config.ts`.

|`--output <dir>`
|Folder for test artifacts (default `test-results`).

|`--tsconfig <path>`
|One tsconfig for all imported files.
|===

Source: https://playwright.dev/docs/test-cli#all-options[Playwright -- Command line: All options]

Parallelism, sharding and retries have their own page,

=== Re-running failures

After a failing run, `--last-failed` runs only what failed. A deliberate failing test was added for this demonstration:

[source,bash]
----
npx playwright test --project=chromium          # one test fails
cat test-results/.last-run.json
npx playwright test --project=chromium --last-failed
----

....
{
  "status": "failed",
  "failedTests": [
    "8cd190df4f1066666642-efdf0e18fe1dbbbd309b"
  ]
}

Running 1 test using 1 worker
[1/1] [chromium] › failing.spec.ts:2:5 › deliberate failure

In a sharded CI job give each shard its own file (`--last-failed-file=.cache/last-run-shard-1.json`) so the shards do not
overwrite each other's list.

=== Headless and headed

Headless is the default: no window opens and the results appear in the terminal. It is what CI uses, it is faster and it
works on machines without a display. Headed mode shows the browser window, which is the quickest way to see what a test does
while you are writing it.

[source,bash]
----
npx playwright test --headed
npx playwright test --headed --project=chromium --workers=1 first-test.spec.ts
----

Source: https://playwright.dev/docs/running-tests#run-tests-in-headed-mode[Playwright -- Running tests: Run tests in headed mode]

Headed can also be set in the configuration (`+use: { headless: false }+`) or per context, but the command line flag leaves the
configuration untouched. A few practical differences:

* Tests run in parallel, so several windows open at once; add `--workers=1` to watch one test at a time.
* Headless uses the `chrome-headless-shell` build and headed uses full Chrome for Testing (since 1.57); the behaviour is
  meant to be identical, and a difference is a Playwright bug worth reporting.
* In headless mode the clipboard is isolated from the operating system (release 1.62), so tests that use `navigator.clipboard`
  no longer read or overwrite the clipboard of the machine.
* For debugging, prefer UI Mode or the Inspector to a plain headed run, because they let you step.

The headed examples above were not run: they open browser windows on the desktop, and the other commands in this page ran
headless. Screenshots, videos and traces, which capture what headed mode shows, are covered in
xref:web/e2e-testing/screenshots-videos-and-traces.adoc[Screenshots, Videos & Traces].

=== UI Mode and the Inspector

`npx playwright test --ui` opens UI Mode, a window with the test tree, a watch mode, a timeline with "time travel" through
every step, DOM snapshots, the network log and a locator picker. `npx playwright test --debug` opens the Playwright Inspector
and a headed browser and lets you step through the API calls. Both are explained in
xref:web/e2e-testing/playwright/debugging-tracing-and-codegen.adoc[Debugging, Tracing & Codegen]. They need a display, so they
were not run for this page.

[source,bash]
----
npx playwright test --ui
npx playwright test --debug
npx playwright test first-test.spec.ts:10 --debug
----

Source: https://playwright.dev/docs/running-tests#debugging-tests[Playwright -- Running tests: Debugging tests]

== The HTML report

The HTML reporter writes a self-contained folder, `playwright-report`, that you open as a web page: filter by browser,
passed, failed, skipped or flaky, search by title, open a test to see its error, steps, attachments and (for the first
retry) its trace. Since 1.57 a Speedboard tab sorts the executed tests by duration.

The `html` reporter is the default in the scaffold, and you can ask for it from the command line:

[source,bash]
----
npx playwright test --reporter=html
npx playwright show-report                          # open the latest report
npx playwright show-report playwright-report/       # open a specific folder
npx playwright show-report --host 0.0.0.0 --port 8080
----

Source: https://playwright.dev/docs/test-reporters#html-reporter[Playwright -- Reporters: HTML reporter]

By default the report opens in the browser automatically only when a test failed (`+open: 'on-failure'+`). The option and
environment variables that control it:

[cols="2,2,3,2",options="header"]
|===
|Reporter option |Environment variable |Meaning |Default

|`open`
|`PLAYWRIGHT_HTML_OPEN`
|When to open the report: `always`, `never` or `on-failure`.
|`on-failure`

|`outputFolder`
|`PLAYWRIGHT_HTML_OUTPUT_DIR`
|Where the report is written.
|`playwright-report`

|`host`
|`PLAYWRIGHT_HTML_HOST`
|Host the report is served on when it opens.
|`localhost`

|`port`
|`PLAYWRIGHT_HTML_PORT`
|Port the report is served on.
|`9323`, or any free port if it is taken

|`title`
|`PLAYWRIGHT_HTML_TITLE`
|Title shown in the report.
|none

|`attachmentsBaseURL`
|`PLAYWRIGHT_HTML_ATTACHMENTS_BASE_URL`
|Where the `data` folder is uploaded, when the attachments are stored apart from the report.
|`data/`

|`doNotInlineAssets`
|`PLAYWRIGHT_HTML_DO_NOT_INLINE_ASSETS`
|Write JavaScript, CSS and data as separate files for sites with a strict Content Security Policy.
|`false`
|===

Source: https://playwright.dev/docs/test-reporters#html-reporter[Playwright -- Reporters: HTML reporter]

[source,typescript]
----
import { defineConfig } from '@playwright/test';

export default defineConfig({
  reporter: [['html', { open: 'never', outputFolder: 'my-report' }]],
});
----

Source: https://playwright.dev/docs/test-reporters#html-reporter[Playwright -- Reporters: HTML reporter]

Do not rely on the automatic opening in CI: with `+open: 'on-failure'+` a failing CI run waits for Ctrl+C because the report
server keeps running. Set `+open: 'never'+` there (or the environment variable) and upload the folder as an artifact.
`show-report` also accepts a `.zip` archive, for example one downloaded from CI, as long as it contains `index.html` at its
top level (release 1.60). Serving the report from this run on a chosen host and port:

[source,bash]
----
npx playwright show-report --host 127.0.0.1 --port 9411
----

....
  Serving HTML report at http://127.0.0.1:9411. Press Ctrl+C to quit.
....

The server answered with HTTP 200 on that address. Other reporters (`list`, `line`, `dot`, `json`, `junit`, `github`,
`blob`) and merging blob reports from shards are covered in
xref:web/e2e-testing/playwright/parallelism-sharding-and-retries.adoc[Parallelism, Sharding & Retries] and
xref:web/e2e-testing/running-in-ci-cd.adoc[Running in CI/CD].

== The VS Code extension

The official Playwright extension for Visual Studio Code (identifier `ms-playwright.playwright`) lets you create, run, debug
and record tests without leaving the editor. It needs Node.js and VS Code. This page documents it from the official guide;
it was not exercised here because it needs the VS Code graphical interface.

. Open the Extensions view (`Ctrl+Shift+X` or `Cmd+Shift+X`), search for "Playwright" and install the extension from Microsoft.
. Open the Command Palette (`Ctrl+Shift+P` or `Cmd+Shift+P`) and run *Test: Install Playwright*.
. Choose the browsers, and optionally add a GitHub Actions workflow. You can change this later in `playwright.config.ts`.
. Open the Testing icon in the Activity Bar to see the Test Explorer and the Playwright sidebar.

What it offers:

[cols="2,4",options="header"]
|===
|Task |How

|Run tests
|Click the green triangle next to a test, a file or the whole project. Results show beside the test and in the Test Results panel.

|Run on several browsers
|Check the projects in the Playwright sidebar. Each project is a browser configuration from the config file; the first one is selected by default.

|Watch the browser
|Enable *Show Browsers* in the sidebar. Disable it to run headless.

|Debug
|Set a breakpoint, right-click the test and choose *Debug Test*. With *Show Browsers* enabled, clicking a locator in the code highlights the element in the page.

|Trace Viewer
|Enable *Show Trace Viewer*; a trace opens when the test finishes.

|Fix a failure with AI
|Click the sparkle icon beside the error to ask Copilot for a suggested fix.

|Record a test
|*Record new* opens a browser and writes code as you click; *Record at cursor* inserts actions at the cursor; *Pick locator* copies the best locator for an element.

|Setup and global setup
|Project dependency tests appear in the Test Explorer and can run on their own; global setup and teardown can be triggered from the sidebar.

|Several configurations
|Switch between `playwright.config.ts` files with the gear icon in the sidebar.
|===

Source: https://playwright.dev/docs/getting-started-vscode[Playwright -- VS Code]

The extension runs the same runner as the command line, so anything that works in the terminal works there, and a
test that is flaky in one place is flaky in the other. The recording and locator-picking features are the same as
the `codegen` command described in
xref:web/e2e-testing/playwright/debugging-tracing-and-codegen.adoc[Debugging, Tracing & Codegen].

== Canary releases

Playwright for Node.js publishes a canary release every day under the `next` npm dist tag, for any code-related commit on the
main branch. It lets you try an unreleased feature, or confirm that a bug is fixed, before the next stable version, and it is
a good way to give feedback to the maintainers. The npm tags at the check date:

[source,bash]
----
npm view @playwright/test dist-tags --json
----

[source,json]
----
{
  "rc": "1.18.0-rc1",
  "latest": "1.64.1",
  "beta": "1.64.1-beta-1792067398000",
  "next": "1.65.0-alpha-2026-10-25"
}
----

* `latest` is the stable release.
* `next` is the daily canary.
* `beta` is published after a release branch is cut, usually a week before a stable release, for each commit.

[source,bash]
----
npm install -D @playwright/test@next
npm init playwright@latest -- --next    # scaffold a project on the next tag
npx playwright install                  # the canary may need newer browser builds
----

Source: https://playwright.dev/docs/canary-releases[Playwright -- Canary releases]

The Playwright maintainers state that a canary passes all automated tests and is used to test the HTML report, the trace
viewer and the Inspector, but it can still change from day to day, so do not rely on it for a production build; pin
`latest` there. The documentation for the `next` version is published on playwright.dev as well: press Shift five times on the
site to switch to it. The canary install was not run so that the shared test project kept its pinned 1.64.1.

== Common pitfalls

* *Forgetting to install browsers after an upgrade.* The error message says the executable does not exist and tells you to run
  `npx playwright install`.
* *Running as a different user than the one who installed the browsers.* Browsers are stored per user (for example
  `+~/Library/Caches/ms-playwright+`); set `PLAYWRIGHT_BROWSERS_PATH` to share them.
* *Missing Linux libraries.* Use `npx playwright install --with-deps` or the Playwright Docker image
  (`mcr.microsoft.com/playwright:v1.64.1-noble`), whose version tag must match the installed Playwright.
* *Using the system Chrome without a channel.* Tests use Playwright's own build unless you set `+channel: 'chrome'+`.
* *Waiting for the report in CI.* See the HTML report section above.
* *Quoting.* Regular expressions in `-g` and file filters need quotes in a shell, and `|` inside them is a pipe otherwise.
* *Local Firefox on a new operating system.* On the macOS 27 host used for these pages the Firefox build 1555 failed to
  launch ("Could not find profile folder"), while the same build worked in the Linux Docker image. If a browser fails to
  start locally, try the container before concluding the tests are wrong.

== What changed recently

* *1.64* (October 2026): browsers Chromium 156, Firefox 157, WebKit 27.2; new `--shuffle [seed]` command line option to
  run in random order and reproduce an order from its seed.
* *1.63*: `--add-reporter` appends reporters instead of replacing the configured ones; `omitTags` for the text reporters.
* *1.62*: the clipboard is isolated from the operating system in headless mode.
* *1.61*: Ubuntu 26.04 supported.
* *1.60*: `show-report` accepts `.zip` archives.
* *1.59*: `npx playwright test --debug=cli` lets coding agents attach and debug over `playwright-cli`; WebKit support for macOS 14 removed.
* *1.57*: Chrome for Testing builds replace Chromium (headed runs `chrome`, headless runs `chrome-headless-shell`); the HTML
  report gains a Speedboard tab. Docker images moved from Node.js 22 to 24.
* *1.44 and 1.46*: `--last-failed` and `--only-changed` were introduced.
