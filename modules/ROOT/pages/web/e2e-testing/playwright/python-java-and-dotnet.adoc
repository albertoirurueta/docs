Playwright is one implementation with four language bindings. The browser automation, the locators, auto-waiting and
web-first assertions behave the same in TypeScript, Python, Java and .NET, but the *test runner* around them does not:
Node.js has Playwright Test, which bundles a runner, a config file, projects, sharding and reporters, while the other
three languages plug Playwright into the runner their ecosystem already uses (pytest, JUnit or TestNG, NUnit, MSTest or
xUnit). This page writes the same Bookshelf scenario in all three languages, explains the library mode versus test-runner
mode split, and lists what you give up or do differently outside Node.js.

The pages of this section were written against Playwright 1.64.1 for Node.js and checked on 25 October 2026. The Python,
Java and .NET examples on this page were run with the 1.63.0 bindings (Python `playwright` 1.63.0 with `pytest-playwright`
0.10.0, Maven `com.microsoft.playwright:playwright` 1.63.0, NuGet `+Microsoft.Playwright.*+` 1.63.0), because the language
documentation at the check date still lists 1.63 as its newest release. Newer bindings were already published at that
date: PyPI `playwright` 1.64.1, Maven Central 1.64.0 and NuGet 1.64.1. Everything below applies to them as well, but it
was not re-run on 1.64. Every example ran against the
xref:web/e2e-testing/example-application-and-test-layout.adoc[Bookshelf] application on a local port, with the reader's
password read from the `BOOKSHELF_READER_PASSWORD` environment variable. The page-object and fixture ideas used here are
explained in xref:web/e2e-testing/test-design-and-page-objects.adoc[Test Design & Page Objects]; the Node.js
equivalent of every example is in xref:web/e2e-testing/playwright/getting-started.adoc[Playwright: Getting Started].

== The scenario every language runs

Two tests, the same in every binding:

. *Search finds a book.* Open `/books`, type `quiet` into the search box, press Search, and expect exactly one book card
  whose heading is "The Quiet Compiler".
. *A reader adds a review.* Sign in as `reader` (password from `BOOKSHELF_READER_PASSWORD`), expect to land on
  `/account`, open `/books/3`, choose a rating of 4, write a review, submit it, and expect the new review row to reach
  `data-state="saved"`.

Each test starts from known data by calling `POST /api/test/reset` through Playwright's own HTTP client before the test
runs, so no test depends on what the previous one left behind. In the reviews test this matters: without the reset, a
second run finds two matching review rows (the saved one and the optimistic pending one) and the locator violates
strict mode.

The official language overview states that all core features for automating the browser are supported in all languages,
while the testing ecosystem integration differs, and recommends choosing the language by your team's experience and
project constraints, with the runner recommended for that language.

== Library mode and test-runner mode

The same split exists in Node.js and is the key to reading the other languages' documentation. *Library mode* means you
call the automation API directly: you pick a browser type, launch it, create a context and a page, run your steps and
close everything yourself. *Test-runner mode* means a runner owns that lifecycle and hands your test a ready page.

[cols="1,2,2",options="header"]
|===
|Concern |Library (any language) |Test runner

|Installation
|`pip install playwright`, one Maven dependency, or `dotnet add package Microsoft.Playwright`; browsers installed
separately
|Runner package (`pytest-playwright`, `Microsoft.Playwright.NUnit`, ...) that depends on the library

|Browser, context, page
|You launch the browser, call `new_context` and `new_page` (or the Java and .NET equivalents) and pass context options
such as the base URL and device yourself
|The runner creates an isolated context and page for each test, lazily, and applies the options from flags,
configuration or overridable methods

|Assertions
|The language's own assertions, or the retrying web-first helpers that the Python, Java and .NET libraries also ship
(`expect`, `assertThat` and `Expect`); the plain Node.js library has no web-first assertions
|The same retrying web-first assertions, plus the runner's assertion reporting

|Timeouts
|Actions default to 30 s
|Actions follow the runner's settings and every test also has its own timeout (Playwright Test, 30 s by default)

|Cleanup
|You close contexts and browsers (in Python and Java with context managers or `try`-with-resources)
|The runner closes the fixtures

|Running
|You run a script (`python script.py`, a `main` method)
|You run the runner (`pytest`, `mvn test`, `dotnet test`)
|===

Source: https://playwright.dev/docs/library[Playwright -- Library]

Use test-runner mode for end-to-end testing. Library mode is the right tool for scripts that are not tests: scraping,
generating screenshots or PDFs, warming a cache, or a custom harness. The Python examples below include a library-mode
script in both the sync and the async flavor; the Java `TracingTest` and the Java plain-library test show that in Java
the line between the two is thin, because the Java documentation recommends building your own `@BeforeAll` and
`@BeforeEach` fixtures around the library when you do not use the experimental JUnit integration.

=== Installing

Python needs a supported interpreter. The Python documentation lists "Python 3.8 or higher", but the PyPI metadata of
the 1.6x releases requires Python 3.10 or later, and the macOS system Python 3.9 of the machine used here was too old.
The runs below used Python 3.13 in a virtual environment.

[source,bash]
----
python3 -m venv .venv
.venv/bin/pip install pytest-playwright==0.10.0 playwright==1.63.0
.venv/bin/playwright install chromium webkit   # download the browsers
.venv/bin/playwright --version
# Version 1.63.0
----

Source: https://playwright.dev/python/docs/intro[Playwright Python -- Installation]

`pip install pytest-playwright` pulls in `playwright` and `python-slugify`; the plugin then provides the
`--base-url` option itself in the 0.10 release. `playwright install` with no arguments downloads Chromium, Firefox and
WebKit; name the engines you need to save time and disk space, add `--with-deps` on a fresh Linux image to install the
operating-system libraries as well, and use `--dry-run` to print what would be downloaded and where. Browsers are cached
per user (`+~/Library/Caches/ms-playwright+` on macOS) and shared between projects that use the same Playwright version.
Environment variables change the behaviour: `PLAYWRIGHT_BROWSERS_PATH` moves the cache, `PLAYWRIGHT_DOWNLOAD_HOST`
downloads from an internal mirror, `HTTPS_PROXY` sends downloads through a proxy and `PLAYWRIGHT_SKIP_BROWSER_DOWNLOAD`
skips the download.

=== The Bookshelf test

The plugin needs no configuration to run: a test function that asks for the `page` fixture gets a new page in a new
context. The base URL is the only setting the tests need, and it goes in `pytest.ini` so that a plain `pytest` works
(the command line can override it with `--base-url`).

[source,ini]
----
# pytest.ini
[pytest]
addopts = --base-url=http://localhost:3920 --output=test-results
testpaths = tests
----

[source,python]
----
# tests/conftest.py
import pytest
from playwright.sync_api import APIRequestContext, Playwright, expect


@pytest.fixture(scope="session")
def browser_context_args(browser_context_args):
    # Extends the options the plugin builds from the CLI flags (--device, --base-url, ...).
    return {**browser_context_args, "locale": "en-GB"}


@pytest.fixture(autouse=True)
def reset_data(playwright: Playwright, base_url: str):
    # Arrange through the HTTP API instead of the UI, as in the other examples.
    request: APIRequestContext = playwright.request.new_context(base_url=base_url)
    request.post("/api/test/reset")
    request.dispose()


def pytest_configure():
    expect.set_options(timeout=5_000)
----

[source,python]
----
# tests/test_bookshelf.py
import os
import re

import pytest
from playwright.sync_api import Page, expect

READER_PASSWORD = os.environ["BOOKSHELF_READER_PASSWORD"]


def test_search_finds_a_book(page: Page):
    page.goto("/books")
    page.get_by_test_id("search-input").fill("quiet")
    page.get_by_role("button", name="Search").click()
    expect(page.get_by_test_id("book-card")).to_have_count(1)
    expect(page.get_by_role("heading", name="The Quiet Compiler")).to_be_visible()


def test_reader_adds_a_review(page: Page):
    page.goto("/signin")
    page.get_by_label("Username").fill("reader")
    page.get_by_label("Password").fill(READER_PASSWORD)
    page.get_by_test_id("signin-submit").click()
    expect(page).to_have_url(re.compile(r"/account$"))

    page.goto("/books/3")
    page.get_by_label("Rating").select_option("4")
    page.get_by_label("Your review").fill("A lovely, detailed field guide.")
    page.get_by_role("button", name="Submit review").click()

    review = page.get_by_test_id("review").filter(has_text="lovely")
    expect(review).to_have_attribute("data-state", "saved")


@pytest.mark.browser_context_args(timezone_id="Europe/Berlin", locale="de-DE")
def test_context_args_marker(page: Page):
    page.goto("/")
    assert page.evaluate("navigator.language") == "de-DE"
    assert page.evaluate("Intl.DateTimeFormat().resolvedOptions().timeZone") == "Europe/Berlin"


def test_two_users_with_new_context(page: Page, new_context):
    other = new_context()
    other_page = other.new_page()
    page.goto("/signin")
    other_page.goto("/signin")
    assert page.context is not other_page.context
----

Notes on the code:

* The `[chromium]` suffix is added by the plugin: the browser is a test parameter, so one test function becomes one test
  per `--browser` value.
* `browser_context_args` is a *session-scoped* fixture that returns the keyword arguments of `browser.new_context()`.
  Override it in `conftest.py` and extend the dictionary you receive (`+{**browser_context_args, ...}+`) so the options
  the plugin derived from the command line, such as the base URL or `--device`, survive.
* The `browser_context_args` *marker* overrides the same options for a single test. The official snippet for this
  marker asserts the time zone against `navigator.userAgent`; the test above checks `navigator.language` and the
  resolved time zone instead.
* `new_context` is a factory fixture for extra contexts (a second user, for example). Contexts it creates are closed by
  the plugin at the end of the test.
* `+playwright.request.new_context(...)+` is the API-testing client, used here to reset the data without a browser.
* `+expect.set_options(timeout=...)+` sets the default timeout of the retrying assertions for the whole run (5 s is the
  default). Hooking it into `pytest_configure` keeps it out of the individual tests.

=== Command line flags

The plugin adds these options to pytest. They configure the *built-in* `browser`, `context` and `page` fixtures only:
a browser or context you create yourself with `browser.new_context()` is not affected.

[cols="2,3,2",options="header"]
|===
|Flag |Effect |Default

|`--browser`
|Engine to run: `chromium`, `firefox` or `webkit`. Repeat the flag to run every test on several engines.
|`chromium`

|`--headed`
|Show the browser window.
|headless

|`--browser-channel`
|Branded browser to use, for example `chrome` or `msedge`.
|none (bundled engine)

|`--slowmo`
|Slow every Playwright operation down by this many milliseconds.
|`0`

|`--device`
|Emulate a device from Playwright's device list, for example `"iPhone 11 Pro"`.
|none

|`--output`
|Directory for artifacts produced by tests.
|`test-results`

|`--tracing`
|Record a trace per test: `on`, `off` or `retain-on-failure`.
|`off`

|`--video`
|Record a video per test: `on`, `off` or `retain-on-failure`.
|`off`

|`--screenshot`
|Take a screenshot after each test: `on`, `off` or `only-on-failure`.
|`off`

|`--full-page-screenshot`
|Capture the full page instead of the viewport; needs `--screenshot`.
|off

|`--base-url`
|Base URL of the application; relative `goto` calls resolve against it.
|none

|`--playwright-debug`

=== Fixtures

[cols="1,1,3",options="header"]
|===
|Fixture |Scope |What you get

|`page`
|function
|A new page in its own new context. The workhorse of almost every test.

|`context`
|function
|A new browser context; the `page` fixture belongs to this context.

|`new_context`
|function
|A factory returning more contexts, with the same arguments as `browser.new_context()`; useful for multi-user tests.

|`playwright`
|session
|The `Playwright` instance (here it also provides `playwright.request` for API calls and `playwright.devices`).

|`browser_type`, `browser`
|session
|The `BrowserType` of the current parameter and the browser launched from it, shared across tests.

|`browser_name`, `browser_channel`
|session
|The engine and channel as strings.

|`is_chromium`, `is_firefox`, `is_webkit`
|session
|Booleans for conditional logic in a test or fixture.

|`browser_type_launch_args`
|session
|Override to change the arguments of `browser_type.launch()`; return a dictionary.

|`browser_context_args`
|session
|Override to change the arguments of `browser.new_context()`.

|`connect_options`
|session
|Return the options of `browser_type.connect()` to run against a remote browser server (for example a `wsEndpoint`).
|===

Source: https://playwright.dev/python/docs/test-runners[Playwright Python -- Pytest Plugin Reference]

Two markers help with browser matrices: `@pytest.mark.skip_browser("firefox")` skips a test on one engine and
`@pytest.mark.only_browser("chromium")` restricts it to one. Plugin-supplied `--base-url` comes from the `base_url`
fixture, so other fixtures (like `reset_data` above) can depend on it.

=== Parallel runs, unittest and debugging

Tests run one after the other in a single process by default. Install `pytest-xdist` and pass `--numprocesses` (`-n`)
to run them in several processes; the Python documentation suggests a number between 2 and the number of CPUs, and half
the logical cores for the running-tests guide. Each worker launches its own browser:

[source,bash]
----
$ .venv/bin/pip install pytest-xdist
$ .venv/bin/pytest tests -n 2
2 workers [4 items]

....                                                                     [100%]
============================== 4 passed in 1.51s ===============================
----

Source: https://playwright.dev/python/docs/test-runners[Playwright Python -- Pytest Plugin Reference]

The data-reset fixture above runs once per test in every worker, so two workers that reset the same Bookshelf can
overwrite each other's data. For parallel runs, give each worker its own data (for example with different books,
users or a per-worker server) rather than one global reset; the isolation techniques are covered in
xref:web/e2e-testing/playwright/authentication-and-isolation.adoc[Authentication & Isolation] and
xref:web/e2e-testing/playwright/parallelism-sharding-and-retries.adoc[Parallelism, Sharding & Retries].

Further points from the plugin reference, documented but not run here: `unittest.TestCase` classes can use the fixtures
through an `autouse` pytest fixture that stores the page on the instance, with the limitation that only one browser can
be specified; `--browser-channel chrome` runs against an installed Chrome; `breakpoint()` in a test opens a `pdb` prompt;
and `PWDEBUG=1 pytest -s -k test_name` opens the Playwright Inspector.

=== Async tests

The default plugin uses the *sync* API (`playwright.sync_api`), which looks like ordinary blocking code. If your tests
already live in an `asyncio` application, use the async API (`playwright.async_api`), install `pytest-playwright-asyncio`
(which replaces the sync fixtures with async ones) and `pytest-asyncio` 0.26 or later, and set the session loop scope. The
sync API cannot run inside a running event loop, so keep the two flavors in separate test suites (the plugin documentation
shows `pytest-playwright-asyncio` as the way to get async fixtures). The async variant was run in its own virtual environment (`pytest-asyncio` 1.4.0):

[source,ini]
----
# async_tests/pytest.ini
[pytest]
asyncio_default_test_loop_scope = session
asyncio_default_fixture_loop_scope = session
addopts = --base-url=http://localhost:3920 --output=test-results
----

[source,python]
----
# async_tests/conftest.py
import pytest_asyncio
from playwright.async_api import Playwright


@pytest_asyncio.fixture(autouse=True, loop_scope="session")
async def reset_data(playwright: Playwright, base_url: str):
    request = await playwright.request.new_context(base_url=base_url)
    await request.post("/api/test/reset")
    await request.dispose()
----

=== Library mode in Python

Without pytest, use the sync context manager for scripts, or the async one inside an event loop. Both were run, and both
printed the same line:

[source,python]
----
# library_sync.py
from playwright.sync_api import sync_playwright

with sync_playwright() as p:
    browser = p.chromium.launch()
    context = browser.new_context(base_url="http://localhost:3920")
    page = context.new_page()
    page.goto("/books")
    page.get_by_test_id("search-input").fill("quiet")
    page.get_by_role("button", name="Search").click()
    page.wait_for_selector("[data-testid=book-card]")
    print(page.get_by_test_id("book-card").count(), "book found:", page.get_by_test_id("book-title").first.text_content())
    context.close()
    browser.close()
----

[source,python]
----
# library_async.py
import asyncio

from playwright.async_api import async_playwright


async def main():
    async with async_playwright() as p:
        browser = await p.chromium.launch()
        page = await browser.new_page(base_url="http://localhost:3920")
        await page.goto("/books")
        await page.get_by_test_id("search-input").fill("quiet")
        await page.get_by_role("button", name="Search").click()
        await page.get_by_test_id("book-card").first.wait_for()
        print(await page.get_by_test_id("book-card").count(), "book found:", await page.get_by_test_id("book-title").first.text_content())
        await browser.close()


asyncio.run(main())

=== Plain library with JUnit 5 lifecycle methods

The Java documentation does not ship a runner of its own; the recommended structure for JUnit 5 is one `Playwright` and
one `Browser` for the class, created in `@BeforeAll` and closed in `@AfterAll`, and one `BrowserContext` with its `Page` per
test, created in `@BeforeEach` and closed in `@AfterEach`. This is the Bookshelf test in that shape:

[source,java]
----
package demo;

import static com.microsoft.playwright.assertions.PlaywrightAssertions.assertThat;

import com.microsoft.playwright.*;
import com.microsoft.playwright.options.AriaRole;
import java.util.regex.Pattern;
import org.junit.jupiter.api.*;

class BookshelfPlainTest {
  static final String BASE_URL = System.getenv().getOrDefault("BASE_URL", "http://localhost:3000");
  static final String READER_PASSWORD = System.getenv("BOOKSHELF_READER_PASSWORD");

  // Shared by every test in the class.
  static Playwright playwright;
  static Browser browser;
  // One new instance per test.
  BrowserContext context;
  Page page;

  @BeforeAll
  static void launchBrowser() {
    playwright = Playwright.create();
    browser = playwright.chromium().launch();
    APIRequestContext request = playwright.request().newContext(new APIRequest.NewContextOptions().setBaseURL(BASE_URL));
    request.post("/api/test/reset");
    request.dispose();
  }

  @AfterAll
  static void closeBrowser() {
    playwright.close();
  }

  @BeforeEach
  void createContextAndPage() {
    context = browser.newContext(new Browser.NewContextOptions().setBaseURL(BASE_URL));
    page = context.newPage();
  }

  @AfterEach
  void closeContext() {
    context.close();
  }

  @Test
  void searchFindsABook() {
    page.navigate("/books");
    page.getByTestId("search-input").fill("quiet");
    page.getByRole(AriaRole.BUTTON, new Page.GetByRoleOptions().setName("Search")).click();
    assertThat(page.getByTestId("book-card")).hasCount(1);
    assertThat(page.getByRole(AriaRole.HEADING, new Page.GetByRoleOptions().setName("The Quiet Compiler"))).isVisible();
  }

  @Test
  void readerAddsAReview() {
    page.navigate("/signin");
    page.getByLabel("Username").fill("reader");
    page.getByLabel("Password").fill(READER_PASSWORD);
    page.getByTestId("signin-submit").click();
    assertThat(page).hasURL(Pattern.compile("/account$"));

    page.navigate("/books/3");
    page.getByLabel("Rating").selectOption("4");
    page.getByLabel("Your review").fill("A lovely, detailed field guide.");
    page.getByRole(AriaRole.BUTTON, new Page.GetByRoleOptions().setName("Submit review")).click();

    Locator review = page.getByTestId("review").filter(new Locator.FilterOptions().setHasText("lovely"));
    assertThat(review).hasAttribute("data-state", "saved");
  }
}
----

=== JUnit 5 with the experimental `@UsePlaywright` fixtures

Since Playwright for Java 1.42 an experimental JUnit extension injects the objects. Annotate the class with
`@UsePlaywright` and declare `Page`, `BrowserContext`, `Browser`, `Playwright` or `APIRequestContext` as test-method
parameters. The `page` and `browserContext` fixtures are isolated per test, the `browser` is shared across tests, and
the `playwright` instance is shared between tests that run on the same thread. To customize them, implement
`OptionsFactory` and pass the class to the annotation.

[source,java]
----
package demo;

import static com.microsoft.playwright.assertions.PlaywrightAssertions.assertThat;

import com.microsoft.playwright.*;
import com.microsoft.playwright.junit.Options;
import com.microsoft.playwright.junit.OptionsFactory;
import com.microsoft.playwright.junit.UsePlaywright;
import com.microsoft.playwright.options.AriaRole;
import java.nio.file.Paths;
import java.util.regex.Pattern;
import org.junit.jupiter.api.Test;

@UsePlaywright(BookshelfJUnitTest.BookshelfOptions.class)
class BookshelfJUnitTest {
  static final String BASE_URL = System.getenv().getOrDefault("BASE_URL", "http://localhost:3000");

  public static class BookshelfOptions implements OptionsFactory {
    @Override
    public Options getOptions() {
      return new Options()
          .setHeadless(true)
          .setBaseUrl(BASE_URL)
          .setApiRequestOptions(new APIRequest.NewContextOptions().setBaseURL(BASE_URL))
          .setTestIdAttribute("data-testid")
          .setTrace(Options.Trace.RETAIN_ON_FAILURE)
          .setOutputDir(Paths.get("target/playwright-output"));
    }
  }

  @Test
  void readerAddsAReview(Page page, APIRequestContext request) {
    request.post("/api/test/reset");

    page.navigate("/signin");
    page.getByLabel("Username").fill("reader");
    page.getByLabel("Password").fill(System.getenv("BOOKSHELF_READER_PASSWORD"));
    page.getByTestId("signin-submit").click();
    assertThat(page).hasURL(Pattern.compile("/account$"));

    page.navigate("/books/3");
    page.getByLabel("Rating").selectOption("4");
    page.getByLabel("Your review").fill("A lovely, detailed field guide.");
    page.getByRole(AriaRole.BUTTON, new Page.GetByRoleOptions().setName("Submit review")).click();
    assertThat(page.getByTestId("review").filter(new Locator.FilterOptions().setHasText("lovely")))
        .hasAttribute("data-state", "saved");
  }

  @Test
  void searchFindsABook(Page page) {
    page.navigate("/books");
    page.getByTestId("search-input").fill("quiet");
    page.getByRole(AriaRole.BUTTON, new Page.GetByRoleOptions().setName("Search")).click();
    assertThat(page.getByTestId("book-card")).hasCount(1);
  }
}
----

Source: https://playwright.dev/java/docs/junit[Playwright Java -- JUnit (experimental)]

The members of `Options` in the 1.63.0 jar, which were listed with `javap`:

[cols="2,3",options="header"]
|===
|Setter |Effect

|`setHeadless`, `setChannel`, `setBrowserName`
|Run headed or headless, pick a branded channel, pick `chromium`, `firefox` or `webkit`.

|`setBaseUrl`
|Base URL of the injected browser contexts (and so of `page.navigate("/path")`).

|`setApiRequestOptions`
|Options for the injected `APIRequestContext`; set its own `setBaseURL`.

|`setContextOptions`, `setLaunchOptions`
|Full `Browser.NewContextOptions` and `BrowserType.LaunchOptions` objects for anything not covered above.

|`setDeviceName`, `setIgnoreHTTPSErrors`, `setTestIdAttribute`
|Emulate a device, ignore certificate errors, change the attribute used by `getByTestId`.

|`setPlaywrightCreateOptions`, `setWsEndpoint`, `setConnectOptions`
|Options for `Playwright.create()`, and the remote-browser connection settings.

|`setTrace`, `setOutputDir`
|`Options.Trace.OFF`, `ON` or `RETAIN_ON_FAILURE`, and the directory that receives the traces.
|===

Source: https://playwright.dev/java/docs/junit[Playwright Java -- JUnit (experimental)]

Three differences from the published documentation showed up when running this against 1.63.0:

* The documentation example calls `+setContextOption(...)+`. The class has `+setContextOptions(...)+` (plural), so the
  documented snippet does not compile as written.
* `+setBaseUrl(...)+` applies to the injected browser contexts only. The injected `APIRequestContext` had no base URL
  until `+setApiRequestOptions(...)+` was added; `request.post("/api/test/reset")` otherwise failed with a
  `TypeError: Invalid URL` from the driver.
* With `Options.Trace.RETAIN_ON_FAILURE` a passing test leaves nothing behind; a failing one left
  `target/playwright-output/demo.BookshelfJUnitTest.readerAddsAReview-chromium/trace.zip`.

The extension is still labelled *experimental* in the documentation at the check date, as it has been since its
introduction in 1.42, so its API may change; the plain-library structure above does not have that risk.

=== Running tests in parallel with JUnit 5

JUnit runs tests sequentially on one thread by default. Playwright objects are not thread-safe, so the Java
documentation recommends one `Playwright` instance per thread, used only on that thread. With `@UsePlaywright` the
extension does this for you. With the plain structure, annotate the base class
`@TestInstance(TestInstance.Lifecycle.PER_CLASS)` and keep `Playwright` and `Browser` in instance fields so that every
test class has its own copy. Then let classes run concurrently but keep the methods of one class sequential:

[source,properties]
----
# src/test/resources/junit-platform.properties
junit.jupiter.execution.parallel.enabled = true
junit.jupiter.execution.parallel.mode.default = same_thread
junit.jupiter.execution.parallel.mode.classes.default = concurrent
junit.jupiter.execution.parallel.config.strategy=dynamic
junit.jupiter.execution.parallel.config.dynamic.factor=0.5
----

Source: https://playwright.dev/java/docs/test-runners[Playwright Java -- Test Runners]

This configuration was not run (the Bookshelf data-reset caveat from the Python section applies equally). TestNG is
documented with the same structure using `@BeforeClass`, `@AfterClass`, `@BeforeMethod` and `@AfterMethod`; it was not
run here.

=== Headed mode and debugging in Java

Pass `new BrowserType.LaunchOptions().setHeadless(false)` to `+launch(...)+` (or `setHeadless(false)` in the JUnit
`Options`), optionally with `.setSlowMo(50)`. `PWDEBUG=1 mvn test` opens the Inspector, and `PLAYWRIGHT_JAVA_SRC` lets
the Inspector show the Java sources. Neither was run, because they open windows.

namespace Bookshelf.Tests;

[Parallelizable(ParallelScope.Self)]
[TestFixture]
public class BookshelfTests : PageTest

        Environment.GetEnvironmentVariable("BASE_URL") ?? "http://localhost:3000";

        Locale = "en-GB",
    };

    [SetUp]
    public async Task ResetData()
    {

        var request = await Playwright.APIRequest.NewContextAsync(new() { BaseURL = BaseUrl });
        await request.PostAsync("/api/test/reset");
        await request.DisposeAsync();
    }

    [Test]
    public async Task SearchFindsABook()
    {
        await Page.GotoAsync("/books");
        await Page.GetByTestId("search-input").FillAsync("quiet");
        await Page.GetByRole(AriaRole.Button, new() { Name = "Search" }).ClickAsync();

        await Expect(Page.GetByRole(AriaRole.Heading, new() { Name = "The Quiet Compiler" })).ToBeVisibleAsync();

    [Test]
    public async Task ReaderAddsAReview()
    {

        await Page.GetByLabel("Username").FillAsync("reader");
        await Page.GetByLabel("Password").FillAsync(ReaderPassword);
        await Page.GetByTestId("signin-submit").ClickAsync();

        await Page.GotoAsync("/books/3");
        await Page.GetByLabel("Rating").SelectOptionAsync("4");
        await Page.GetByLabel("Your review").FillAsync("A lovely, detailed field guide.");
        await Page.GetByRole(AriaRole.Button, new() { Name = "Submit review" }).ClickAsync();

        var review = Page.GetByTestId("review").Filter(new() { HasText = "lovely" });
        await Expect(review).ToHaveAttributeAsync("data-state", "saved");
    }
}

=== dotnet test flags, environment variables and .runsettings

Playwright's .NET integration reads its configuration from environment variables, from `+Playwright.*+` parameters passed
after `--`, and from a `.runsettings` file (used by the `dotnet test --settings` option and by Visual Studio).

[cols="3,3",options="header"]
|===
|Command or variable |Effect

|`dotnet test`
|Run all tests on Chromium, headless.

|`BROWSER=webkit dotnet test`
|Choose `chromium`, `firefox` or `webkit` (any other value fails the tests with "Invalid browser name from 'BROWSER'
environment variable").

|`HEADED=1 dotnet test`
|Run headed (PowerShell: `$env:HEADED="1"`).

|`PWDEBUG=1 dotnet test`
|Open the Playwright Inspector.

|`dotnet test -- Playwright.BrowserName=webkit`
|Same as `BROWSER`, through the launch configuration.

|`dotnet test -- Playwright.LaunchOptions.Headless=false Playwright.LaunchOptions.Channel=msedge`
|Launch options from the command line.

|`dotnet test --settings:webkit.runsettings`
|Take every setting from a file; the documented way to run several browser configurations is one `dotnet test` per file.

|`+dotnet test --filter "Name~GetStartedLink"+`
|Run tests by name; `--filter "ExampleTest1\|ExampleTest2"` runs several classes.

|`dotnet test -- NUnit.NumberOfTestWorkers=5`
|Number of parallel workers (NUnit). Only `ParallelScope.Self` is supported.

|`dotnet test -- MSTest.Parallelize.Workers=4`
|Workers for MSTest; parallelism is at class level (`ExecutionScope.ClassLevel`), not method level.

|`dotnet test -- xUnit.MaxParallelThreads=5`
|Threads for xUnit and xUnit v3; the conservative algorithm is the default in xUnit 2.8 and later.

|`DEBUG=pw:api dotnet test`
|Verbose API log on standard error, shown in the test log of each test.
|===

=== Tracing in .NET

The .NET base classes do not have a tracing switch (the Python plugin has `--tracing`, and Java's `@UsePlaywright`
has `Options.setTrace`). Start and stop it in `[SetUp]` and `[TearDown]` and keep the file only for failing tests. This
class ran; the intentionally failing test is marked `[Explicit]` so a normal `dotnet test` skips it:

[source,csharp]
----
using Microsoft.Playwright;
using Microsoft.Playwright.NUnit;

namespace Bookshelf.Tests;

[Parallelizable(ParallelScope.Self)]
[TestFixture]
public class TracedTests : PageTest
{
    public override BrowserNewContextOptions ContextOptions() => new()
    {
        BaseURL = Environment.GetEnvironmentVariable("BASE_URL") ?? "http://localhost:3000",
    };

    [SetUp]
    public async Task StartTracing()
    {
        // The NUnit base classes have no tracing switch: start it per test.
        await Context.Tracing.StartAsync(new() { Screenshots = true, Snapshots = true, Sources = true });
    }

    [TearDown]
    public async Task StopTracing()
    {
        var failed = TestContext.CurrentContext.Result.Outcome.Status == NUnit.Framework.Interfaces.TestStatus.Failed;
        await Context.Tracing.StopAsync(new()
        {
            // Keep the trace only for failing tests.
            Path = failed ? Path.Combine(TestContext.CurrentContext.WorkDirectory, "traces",
                $"{TestContext.CurrentContext.Test.Name}.zip") : null,
        });
    }

    [Test]
    public async Task CatalogueShowsSixBooksPerPage()
    {
        await Page.GotoAsync("/books");
        await Expect(Page.GetByTestId("book-card")).ToHaveCountAsync(6);
    }

    [Test, Explicit("Fails on purpose to show the kept trace")]
    public async Task FailingTestKeepsItsTrace()
    {
        await Page.GotoAsync("/books");
        await Expect(Page.GetByTestId("book-card")).ToHaveCountAsync(7, new() { Timeout = 1000 });
    }
}
----

The browser engine, auto-waiting, actionability checks, locators and retrying assertions are shared. What differs is

Cells that say "none built in" or "no equivalent" mean that the language's Playwright documentation and API reference
list no such feature at the check date (for example, the Python, Java and .NET `PageAssertions` and `LocatorAssertions`
classes have no screenshot assertion). They do not claim that it is impossible: screenshots can be taken in every
language and compared with an image-diff library or a hosted service, as explained in
xref:web/e2e-testing/visual-regression-testing.adoc[Visual Regression Testing]. The rows about sharding and retries describe
what Playwright itself provides; each runner has its own rerun and splitting ecosystem.

Other differences that matter every day:

* *Naming.* The same API is `get_by_role`, `getByRole` and `GetByRole`; Python and C# add `async` flavors or the `Async`
  suffix, and Python options are keyword arguments where Java uses builders (`+new Page.GetByRoleOptions().setName(...)+`)
  and C# uses `+new() { Name = ... }+`.
* *Enums.* Roles are strings in Python (`"button"`), `AriaRole.BUTTON` in Java and `AriaRole.Button` in .NET.
* *Errors.* A failed assertion is a Python `AssertionError`, a JUnit `AssertionFailedError` or a .NET
  `PlaywrightException`; the call log is identical.
* *Default timeouts.* Actions wait up to 30 s everywhere, retrying assertions wait 5 s, and each runner has its own test
  timeout (pytest has none by default; Playwright Test has 30 s; NUnit, MSTest and xUnit have none unless configured).
* *Thread safety.* A Java `Playwright` instance and everything created from it must stay on one thread. Python's sync API
  runs a greenlet-based event loop of its own, so it cannot be used inside a running `asyncio` loop; use the async API
  there.
* *Version lag.* The Node.js package is the first to receive a release; the Python, Java and .NET release-notes pages
  at the check date list 1.63 as their newest entry, while the registries already carried 1.64.x.

== Choosing between them

[cols="1,3",options="header"]
|===
|Situation |Suggested choice

|A team that already writes Node.js or TypeScript, or wants the most complete tooling
|Playwright Test in Node.js: config, projects, sharding, UI Mode, reporters and visual comparisons come built in.

|A Python codebase (Django, FastAPI, data science)
|`pytest-playwright`: the closest experience to Playwright Test, with `--tracing`, `--video` and `--screenshot` flags and
pytest's fixtures and markers. See the stack sections for Django and FastAPI for the application side.

|A Java or Spring Boot team
|The plain library with JUnit 5 lifecycle methods, or `@UsePlaywright` when you accept its experimental status. Wire the
browser install into your CI image build, not into the first test run.

|A .NET team
|The NUnit, MSTest or xUnit base class matching your existing runner. `PageTest` covers most cases.

|Mixed teams
|Test the UI in one language and put API checks in each service's own runner. Playwright's `APIRequestContext` is
available in all four languages, as used in the data-reset fixtures above.
|===

== Running in CI

The official Docker images exist per language and release: `mcr.microsoft.com/playwright/python:v1.63.0-noble`,

== Common pitfalls

* *Forgetting the browser install.* The library does not download browsers at `pip install` time. In Python run
  `playwright install`; in .NET run the installation script after the first build; Java downloads on first
  `Playwright.create()`, which makes a first CI run slow and network-dependent.
* *Mismatched runner and package majors in .NET.* See the MSTest finding above.
* *`exec:java` with a test-scoped dependency.* Add `-D exec.classpathScope=test` or move the dependency to compile scope.
* *Baking the base URL into tests.* Use `--base-url`, `Options.setBaseUrl` or `ContextOptions()` so the same tests run
  against local, staging and CI hosts.
* *Sharing state across tests.* Contexts are cheap and isolated; browsers are shared. Do not reuse a page between tests,
  and do not run a global reset from every parallel worker.
* *Mixing the sync and async Python APIs.* The sync API fails inside a running event loop. Keep sync and async suites
  in separate directories, as in the example above where the async tests had their own environment.
* *Using one `Playwright` object from several Java threads.* Create one per thread.
* *Expecting runner flags to affect objects you create.* The `pytest-playwright` flags apply to the built-in fixtures
  only; contexts created with `browser.new_context()` need their own arguments.
