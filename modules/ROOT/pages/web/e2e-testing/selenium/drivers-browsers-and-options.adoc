A Selenium test never talks to a browser directly. It builds a few small objects -- *Options* that describe the browser
session, a *Service* that starts the driver executable, and optionally an *HTTP client configuration* -- and hands them to
a driver class, which starts the session. This page explains those objects, the options every browser shares, and then the
specifics of each browser Selenium drives: Chrome, Edge, Firefox, Safari and Internet Explorer mode. It was written against
Selenium 4.51.0 (released 9 October 2026) and checked on 25 October 2026. Every Java (JUnit 5.14.4, Java 17) and Python
(pytest, Python 3.13) example marked as run was executed against the xref:web/e2e-testing/example-application-and-test-layout.adoc[Bookshelf]
application with Selenium 4.51.0: Chrome 155 ran locally on macOS, and Chrome 155 and Firefox 158 ran inside the
`selenium/standalone-chrome:4.51.0` and `selenium/standalone-firefox:4.51.0` containers. Edge, Safari and Internet Explorer
could not be run on this host, and local Firefox did not start under Selenium on it, so those sections are written from the
official documentation and the Selenium API and say so where it matters. C#, Ruby and JavaScript snippets are shown where the official
documentation shows a binding-specific difference; they were not run. For installing Selenium and the first script, see
xref:web/e2e-testing/selenium/getting-started.adoc[Getting Started]; for Grid itself, see
xref:web/e2e-testing/selenium/selenium-grid.adoc[Selenium Grid].

== Anatomy of a session

Creating a driver object corresponds to the W3C WebDriver command
https://w3c.github.io/webdriver/#new-session[New Session]. The constructor does the whole job: it resolves the driver
executable, starts it, sends the capabilities and returns once the browser is open. Three kinds of argument shape that process:

[cols="1,2,2",options="header"]
|===
|Argument |What it controls |Applies to

|*Options* (`ChromeOptions`, `FirefoxOptions`, `EdgeOptions`, `SafariOptions`, `InternetExplorerOptions`)
|Which browser, which version and platform, how it behaves (page-load strategy, timeouts, prompts, proxy) and the vendor-specific settings (arguments, binary, preferences).
|Local and remote sessions. Required for a remote session, because the options decide which browser the remote end starts.

|*Service* (`ChromeDriverService`, `GeckoDriverService`, `EdgeDriverService`, `SafariDriverService`, `InternetExplorerDriverService`)
|The driver process: its executable, port, log file, log level and driver-specific switches.
|Local sessions only. A Service cannot be used with a Remote WebDriver session.

|*HTTP client configuration* (`ClientConfig` in Java and Python, an HTTP client object in Ruby)
|How the client talks to the driver or Grid: timeouts, retries, proxy, TLS trust, credentials.
|Remote sessions. Local drivers use a default client of the same kind.
|===

Source: https://www.selenium.dev/documentation/webdriver/drivers/[Selenium -- Driver Sessions]

A session ends with the W3C command https://w3c.github.io/webdriver/#delete-session[Delete Session], which is what
`quit()` sends. `quit()` closes every window, ends the session and stops the driver process. `close()` only closes the current window, and the session
and the driver process stay alive if it was the last window, so tests should always end with `quit()` (in a `finally` block, a JUnit `@AfterEach` or a pytest
fixture). A forgotten `quit()` leaves a browser and a driver process behind, which is the most common reason a CI machine slows down over time.

Source: https://www.selenium.dev/documentation/webdriver/drivers/[Selenium -- Driver Sessions: Quitting Sessions]

== Options and capabilities

A *capability* is a name-value pair in the JSON object the client sends with New Session; the W3C specification defines a
small set of standard ones, and every browser vendor adds its own, prefixed with a vendor name (`goog:chromeOptions`,
`ms:edgeOptions`, `moz:firefoxOptions`, `safari:` keys, and `se:` keys that Selenium Grid reads). An *Options class* is the typed
builder for that JSON object. You never write the JSON by hand: the setters of the Options class fill it in, and the
driver class sends it. The result the driver returns is also a set of capabilities, which you can read back to see what
the session really got. In Selenium 3 the same job was done by the capabilities helper classes; Selenium 4 requires Options
classes, and the old helpers are described on
xref:web/e2e-testing/selenium/selenium-ide-and-legacy.adoc[Selenium IDE & Legacy]. For a remote session an Options instance is mandatory, as it
determines the browser.

=== The shared options

These capabilities are defined by the W3C specification and are available on every Options class:

[cols="2,3,3,3",options="header"]
|===
|Capability |Java |Python |Meaning

|`browserName`
|set by the class (`ChromeOptions` is `chrome`)
|set by the class
|Read it back with `getBrowserName()`.

|`browserVersion`
|`options.setBrowserVersion("stable")`
|`options.browser_version = "stable"`
|Selects an installed or downloadable browser version. When the version is not found locally, Selenium Manager downloads it.

|`platformName`
|`+options.setPlatformName(...)+`
|`+options.platform_name = ...+`
|Identifies the operating system of the remote end. With cloud providers, setting it picks the operating system.

|`acceptInsecureCerts`
|`options.setAcceptInsecureCerts(true)`
|`options.accept_insecure_certs = True`
|Trust expired or self-signed TLS certificates for the whole session. With `false` an insecure-certificate error is returned.

|`pageLoadStrategy`
|`options.setPageLoadStrategy(PageLoadStrategy.EAGER)`
|`options.page_load_strategy = "eager"`
|When a navigation counts as finished, see the next section.

|`timeouts`
|`setScriptTimeout`, `setPageLoadTimeout`, `setImplicitWaitTimeout` (all take a `Duration`)
|`+options.timeouts = {"script": 5000, "pageLoad": 20000, "implicit": 0}+` (milliseconds)
|Session timeouts, see the table below.

|`unhandledPromptBehavior`
|`options.setUnhandledPromptBehaviour(UnexpectedAlertBehaviour.DISMISS_AND_NOTIFY)`
|`options.unhandled_prompt_behavior = "dismiss and notify"`
|What to do with an alert, confirm or prompt dialog nobody handled: `dismiss`, `accept`, `dismiss and notify` (the default), `accept and notify` or `ignore`.

|`strictFileInteractability`
|`options.setCapability(CapabilityType.STRICT_FILE_INTERACTABILITY, true)`
|`options.strict_file_interactability = True`
|Apply the strict interactability checks to `input type=file` elements. It is off by default, so `sendKeys` works on hidden file inputs.

|`proxy`
|`options.setCapability("proxy", proxy)` with a `Proxy`
|`+options.proxy = Proxy({...})+`
|Send the browser traffic through a proxy: useful to capture traffic, to mock backend calls or to reach a site from behind a corporate network.

|`setWindowRect`
|read only
|read only
|Reported by the driver: whether the resize and reposition commands are supported. ChromeDriver rejects it as an input capability.
|===

The three session timeouts have these W3C defaults:

[cols="1,1,3",options="header"]
|===
|Timeout |Default |Behaviour

|`script`
|30,000 ms
|How long an executing script may run before it is interrupted.

|`pageLoad`
|300,000 ms
|How long a navigation may take. When it is exceeded the command fails with a `TimeoutException`.

|`implicit`
|0 ms
|How long element lookups retry before failing. Leave it at 0 and use explicit waits (see xref:web/e2e-testing/selenium/waits-and-expected-conditions.adoc[Waits & Expected Conditions]); mixing the two produces unpredictable total waits.
|===

The next test builds Chrome options with several of these, prints the JSON the client would send, starts a headless session,
and checks what the driver returned:

[source,java]
----
import static org.junit.jupiter.api.Assertions.*;

import java.time.Duration;
import org.junit.jupiter.api.Test;
import org.openqa.selenium.PageLoadStrategy;
import org.openqa.selenium.Proxy;
import org.openqa.selenium.UnexpectedAlertBehaviour;
import org.openqa.selenium.WebDriver;
import org.openqa.selenium.chrome.ChromeDriver;
import org.openqa.selenium.chrome.ChromeOptions;
import org.openqa.selenium.remote.CapabilityType;

class OptionsTest {
  @Test
  void sharedOptionsBecomeSessionCapabilities() {
    ChromeOptions options = new ChromeOptions();
    options.addArguments("--headless=new");
    options.setPageLoadStrategy(PageLoadStrategy.EAGER);
    options.setAcceptInsecureCerts(true);
    options.setScriptTimeout(Duration.ofSeconds(5));
    options.setPageLoadTimeout(Duration.ofSeconds(20));
    options.setImplicitWaitTimeout(Duration.ZERO);
    options.setUnhandledPromptBehaviour(UnexpectedAlertBehaviour.DISMISS_AND_NOTIFY);
    options.setCapability(CapabilityType.STRICT_FILE_INTERACTABILITY, true);

    // What the client would send: the W3C capabilities plus the goog:chromeOptions extension.
    System.out.println("asMap: " + options.asMap());

    WebDriver driver = new ChromeDriver(options);
    try {
      var caps = ((ChromeDriver) driver).getCapabilities();
      System.out.println("browserName=" + caps.getBrowserName() + " platformName=" + caps.getPlatformName()
          + " pageLoadStrategy=" + caps.getCapability("pageLoadStrategy")
          + " timeouts=" + caps.getCapability("timeouts"));
      assertEquals("chrome", caps.getBrowserName());
      assertEquals("eager", caps.getCapability("pageLoadStrategy"));
      // setWindowRect is reported by the driver; it is not accepted as an input capability.
      assertEquals(true, caps.getCapability(CapabilityType.SET_WINDOW_RECT));
      assertEquals(true, caps.getCapability("acceptInsecureCerts"));
      assertEquals(Duration.ofSeconds(5), driver.manage().timeouts().getScriptTimeout());
      assertEquals(Duration.ofSeconds(20), driver.manage().timeouts().getPageLoadTimeout());
      assertEquals(Duration.ZERO, driver.manage().timeouts().getImplicitWaitTimeout());
    } finally {
      driver.quit();
    }
  }

  @Test
  void proxyIsAStandardCapability() {
    Proxy proxy = new Proxy();
    proxy.setHttpProxy("proxy.example.test:8080");
    proxy.setNoProxy("localhost");
    ChromeOptions options = new ChromeOptions();
    options.setCapability("proxy", proxy);
    System.out.println("proxy capability: " + options.asMap().get("proxy"));
    assertEquals("proxy.example.test:8080", ((Proxy) options.getCapability("proxy")).getHttpProxy());
  }
}

Three details are worth noting from this run. First, the official examples for `setWindowRect` only build an Options object and
read the capability back; if you send it to ChromeDriver the session fails with `unrecognized capability: setWindowRect`,
because it is a capability the driver *returns*. Second, the same timeout is a `Duration` in Java, plain milliseconds in the Python
`options.timeouts` dictionary, and seconds when read back through Python's `driver.timeouts` object (`driver.timeouts.script` was 5
for the 5000 ms set here). Third, the returned capabilities contain more than you sent: Chrome adds `chrome.chromedriverVersion`,
`goog:chromeOptions.debuggerAddress`, `networkConnectionEnabled`, WebAuthn extension flags and the process id, the Grid adds `se:` keys
(`se:cdp`, `se:vnc`, `se:downloadsEnabled`, `se:noVncPort` and others), and Firefox adds `moz:` keys (`moz:profile`, `moz:headless`,
`moz:geckodriverVersion`, `moz:debuggerAddress`).

=== Options versus capabilities

The two terms are not interchangeable. The *capabilities* are the data sent on the wire and returned by the driver; the *Options
object* is the per-browser class that builds the data safely. Every Options class is itself a capabilities object, so
`getCapability`, `setCapability` and `merge` work on it, and `options.setCapability("key", value)` (`options.set_capability("key", value)`
in Python) is the escape hatch for a capability the class has no setter for. When a feature is configured both through a typed setter
and through a raw capability, prefer the setter, which also validates the value. Capability names that contain a colon belong to a
vendor, and the Grid ignores or rejects keys it does not know.

The returned capabilities can differ from the requested ones. Selenium Manager and the driver can pick a different
browser version than you assumed, and a browser may ignore an option. Reading `driver.capabilities` (`driver.getCapabilities()` in Java) is the way to check what a
session actually got, which is what the example above does.

== Page-load strategies

`driver.get(url)` returns when the navigation is finished, and the page-load strategy decides what "finished" means. It queries
https://developer.mozilla.org/en-US/docs/Web/API/Document/readyState[document.readyState]:

[cols="1,1,2,3",options="header"]
|===
|Strategy |Ready state |Event waited for |Use

|`normal` (default)
|`complete`
|the `load` event, after every resource has downloaded
|The safe default; the page is as the user sees it.

|`eager`
|`interactive`
|`DOMContentLoaded`: the DOM is ready, but images, style sheets and frames may still be loading
|Faster tests when sub-resources do not matter to the test.

|`none`
|any
|only the initial HTML document is downloaded; WebDriver does not block at all
|You wait yourself, for example for a long-polling or streaming page, with explicit waits.
|===

The strategy applies to the whole session, so the waiting strategy of the test must be strong enough for the page (a single-page
application can report `complete` long before its JavaScript has drawn anything). It also only applies to navigation
commands such as `get`, `navigate().to` and `refresh`; a navigation that is the result of clicking an element or submitting a form is
not governed by it, and needs an explicit wait.

Bookshelf's pages load too quickly to show a difference, so this test starts a tiny HTTP server in the test process whose page contains an image that takes two seconds to arrive, and
measures how long `get` blocks under each strategy:

[source,java]
----
import static org.junit.jupiter.api.Assertions.*;

import com.sun.net.httpserver.HttpServer;
import java.io.IOException;
import java.net.InetSocketAddress;
import java.util.Base64;
import java.util.concurrent.Executors;
import org.junit.jupiter.api.AfterAll;
import org.junit.jupiter.api.BeforeAll;
import org.junit.jupiter.params.ParameterizedTest;
import org.junit.jupiter.params.provider.EnumSource;
import org.openqa.selenium.JavascriptExecutor;
import org.openqa.selenium.PageLoadStrategy;
import org.openqa.selenium.WebDriver;
import org.openqa.selenium.chrome.ChromeDriver;
import org.openqa.selenium.chrome.ChromeOptions;

class PageLoadStrategyTest {
  static final int SLOW_PORT = Integer.getInteger("slow.port", 4518);
  static final byte[] PIXEL = Base64.getDecoder().decode(
      "iVBORw0KGgoAAAANSUhEUgAAAAEAAAABCAYAAAAfFcSJAAAADUlEQVR4nGP4z8DwHwAFAAH/q842iQAAAABJRU5ErkJggg==");
  static HttpServer server;

  @BeforeAll
  static void startServer() throws IOException {
    server = HttpServer.create(new InetSocketAddress(SLOW_PORT), 0);
    server.createContext("/", ex -> {
      byte[] body = "<html><body><h1 id=title>Slow page</h1><img src='/slow.png'></body></html>".getBytes();
      ex.getResponseHeaders().add("Content-Type", "text/html");
      ex.sendResponseHeaders(200, body.length);
      ex.getResponseBody().write(body);
      ex.close();
    });
    server.createContext("/slow.png", ex -> {
      try { Thread.sleep(2000); } catch (InterruptedException ignored) { } // the slow sub-resource
      ex.getResponseHeaders().add("Content-Type", "image/png");
      ex.sendResponseHeaders(200, PIXEL.length);
      ex.getResponseBody().write(PIXEL);
      ex.close();
    });
    server.setExecutor(Executors.newCachedThreadPool()); // the slow image must not block other requests
    server.start();
  }

  @AfterAll
  static void stopServer() { server.stop(0); }

  @ParameterizedTest
  @EnumSource(value = PageLoadStrategy.class, names = {"NORMAL", "EAGER", "NONE"})
  void getReturnsAtTheStrategysReadyState(PageLoadStrategy strategy) {
    ChromeOptions options = new ChromeOptions();
    options.addArguments("--headless=new");
    options.setPageLoadStrategy(strategy);
    WebDriver driver = new ChromeDriver(options);
    try {
      long start = System.nanoTime();
      driver.get("http://localhost:" + SLOW_PORT + "/");
      long ms = (System.nanoTime() - start) / 1_000_000;
      Object state = ((JavascriptExecutor) driver).executeScript("return document.readyState");
      System.out.printf("%-6s get() took %4d ms, readyState=%s%n", strategy, ms, state);
      if (strategy == PageLoadStrategy.NORMAL) {
        assertTrue(ms >= 1800, "normal waits for the 2 s image");
        assertEquals("complete", state);
      } else {
        assertTrue(ms < 1500, strategy + " does not wait for the image");
      }
    } finally {
      driver.quit();
    }
  }
}

== The driver Service

The Service classes manage the starting and stopping of *local* driver executables. They let you choose the driver location and the
port, and they pass command-line arguments to the driver, most of which are about logging. Without a Service the driver class builds a default one.
The shape of the API differs by language: in Java a Service is built once through a `Builder` and is immutable afterwards; in Python the values are constructor
arguments; .NET services expose them as properties; and Ruby accepts either constructor arguments or attributes.

[cols="1,3",options="header"]
|===
|Setting |How

|Default service
|Java `new ChromeDriverService.Builder().build()`, Python `webdriver.ChromeService()` (Python Service constructors with values date from Selenium 4.11).

|Driver location
|Java `usingDriverExecutable(File)`, Python `+ChromeService(executable_path=...)+`. With Selenium 4.6 or later you should not need it, because
xref:web/e2e-testing/selenium/getting-started.adoc[Selenium Manager] finds or downloads the driver; set it only for an unusual setup.

|Port
|Java `usingPort(int)`, Python `+ChromeService(port=...)+`. By default a free port is chosen.

|Log output
|Java `withLogFile(File)` or `withLogOutput(OutputStream)`, Python `ChromeService(log_output=path_or_stream)`. Logging is ignored unless you direct it somewhere.

|Log level and driver switches
|Java builder methods (`withLogLevel`, `withAppendLog`, `withReadableTimestamp`, `withBuildCheckDisabled`), Python `+service_args=[...]+`.
|===

This test covers port, log file, log level and the two file-only log features, and then shows how to point at explicit driver and
browser executables found by `DriverFinder`, which asks Selenium Manager where they are:

@Test
void logFileLevelTimestampsAndPort() throws Exception {
  File log = File.createTempFile("chromedriver-", ".log");
  ChromeDriverService service = new ChromeDriverService.Builder()
      .usingPort(4513)
      .withLogFile(log)
      .withLogLevel(ChromiumDriverLogLevel.DEBUG)
      .withAppendLog(true)
      .withReadableTimestamp(true)
      .build();
  ChromeDriver driver = new ChromeDriver(service, headless());
  try {
    driver.get(Env.BASE_URL + "/books");
    assertEquals("http://localhost:4513", service.getUrl().toString());
  } finally {
    driver.quit();
  }
  String text = Files.readString(log.toPath());
  System.out.println(text.lines().limit(3).toList());
  assertTrue(text.contains("Starting ChromeDriver"));
  assertTrue(text.contains("[DEBUG]:"));
  assertTrue(text.matches("(?s)^\\[\\d\\d-\\d\\d-\\d\\d\\d\\d.*"), "readable timestamp");
}

@Test
void explicitDriverAndBrowserLocations() {
  ChromeOptions probe = headless();
  probe.setBrowserVersion("stable");
  // DriverFinder asks Selenium Manager where the driver and the browser are.
  DriverFinder finder = new DriverFinder(ChromeDriverService.createDefaultService(), probe);
  System.out.println("driver:  " + finder.getDriverPath());
  System.out.println("browser: " + finder.getBrowserPath());

  ChromeOptions options = headless();

    driver.quit();
  }

== HTTP client configuration

Underneath, every command is an HTTP request. The HTTP client configuration lets you set the parameters of that client: connection and read timeouts,
retries, an HTTP version, a proxy, a custom TLS trust store (or none), and credentials for a Grid protected with basic
authentication. The implementation varies by language. In Java you build a `ClientConfig` and pass it to the
`RemoteWebDriver` builder; in Python you pass a `ClientConfig` as `client_config`; in Ruby you create an HTTP client object and pass it as `http_client`.
The official documentation shows no example for .NET and JavaScript. The following test configures a Java and a Python client for the Chrome container: retries, timeouts, and (Java only) the
augmented driver the builder returns.

[source,java]
----
@Test
void clientConfigAndBuilderGiveYouBrowserSpecificFeatures() {
  ClientConfig config = ClientConfig.defaultConfig()
      .withRetries()
      .connectionTimeout(Duration.ofSeconds(30))
      .readTimeout(Duration.ofMinutes(5));
  ChromeOptions options = new ChromeOptions();
  options.addArguments("--headless=new");
  driver = RemoteWebDriver.builder()
      .address(Env.url(Env.CHROME_GRID))
      .oneOf(options)
      .config(config)
      .build();

  // The builder returns an augmented driver, so the Chromium interfaces are available remotely too.
  assertTrue(driver instanceof HasCasting);
  assertTrue(driver instanceof HasNetworkConditions);
  driver.get(Env.BASE_URL_FROM_DOCKER + "/books");
  assertEquals("Catalogue - Bookshelf", driver.getTitle());
}
----

== Remote WebDriver

Selenium can automate browsers on other computers when a Selenium Grid (or a Selenium Server in standalone mode) runs there. The machine that executes your test is the *client*;
the machine with the browser and the driver is the *remote end* or node. To direct a test to it, use the Remote WebDriver class with the URL (including the port)
of the Grid and an Options instance: both the address and the options are required, because the driver must know where to send commands and which browser the remote end should start.
For how to build and operate the Grid, see xref:web/e2e-testing/selenium/selenium-grid.adoc[Selenium Grid].

The Java tests of this section share a small base: a `Fixture` helper server (shown at the end of the section) started once per class, a `driver` field and an `@AfterEach` that quits it. The Python tests omit imports, use a small helper `chrome_options()` that returns a `ChromeOptions` with `--headless=new`, and take their
constants (`BASE_URL`, `CHROME_GRID` and so on) from `conftest.py`, which reads them from environment variables with the defaults of these runs.

The tests in this section talk to a `selenium/standalone-chrome:4.51.0` container started with `docker run -d --rm --name sel-drivers-chrome --shm-size=2g -p 4511:4444 selenium/standalone-chrome:4.51.0`.

=== Uploads

Uploading a file through a remote session is harder than locally, because the file lives on the computer running the test while the driver looks for the path on
*its own* file system. The solution is a *local file detector*: when one is set, Selenium bundles the file, sends it to the remote machine and rewrites the path the driver sees.
The bindings differ in what they set up for you:

[cols="1,3",options="header"]
|===
|Binding |Behaviour

|Java
|No file detector by default; always call `setFileDetector(new LocalFileDetector())` before `sendKeys`.

|Python
|Adds a `LocalFileDetector` to remote sessions by default; you can also write your own class.

|.NET
|Adds a local file detector by default; set `FileDetector` to replace it.

|Ruby
|Adds one by default; a custom detector is a lambda.

|JavaScript
|No file detector by default; call `driver.setFileDetector(new remote.FileDetector())`.
|===

Bookshelf has no upload form, so the tests serve one from the same small helper server used elsewhere on this page: a page with an `input type=file` that prints the chosen file name.

=== Downloads

Chrome, Edge and Firefox each let you set the download directory, but on a remote machine that directory is on the remote file system. *Managed downloads* bring the files back
to the client. Two switches are needed:

* the Grid (in node or standalone mode) must start with `--enable-managed-downloads true` (the docker-selenium images enable it by default through `SE_NODE_ENABLE_MANAGED_DOWNLOADS=true`), and
* the client sets the `se:downloadsEnabled` capability, which every binding exposes on its Options class (`setEnableDownloads(true)` in Java,
`options.enable_downloads = True` in Python, `EnableDownloads = true` in C#, `enable_downloads: true` in Ruby, `enableDownloads()` in JavaScript).

The client then lists, fetches and deletes the files of the session. Selenium does not wait for a download to finish, so the list is an immediate snapshot of the file names currently in the session's
download directory, which is why the tests wait for the name to appear. By default the directory is deleted when the session ends.

[source,java]
----
@Test
void managedDownloadsBringFilesBackToTheClient() throws Exception {
  ChromeOptions options = new ChromeOptions();
  options.addArguments("--headless=new");
  options.setEnableDownloads(true); // se:downloadsEnabled
  driver = new RemoteWebDriver(Env.url(Env.CHROME_GRID), options);

  driver.get(Fixture.FROM_DOCKER + "/download/hello.txt");
  new WebDriverWait(driver, Duration.ofSeconds(10))
      .until(d -> ((HasDownloads) d).getDownloadableFiles().contains("hello.txt"));

  List<String> names = ((HasDownloads) driver).getDownloadableFiles();
  System.out.println("downloadable files: " + names);

  Path target = Files.createTempDirectory("download");
  ((HasDownloads) driver).downloadFile("hello.txt", target);
  assertEquals("Hello, World!", Files.readString(target.resolve("hello.txt")));

  ((HasDownloads) driver).deleteDownloadableFiles();
  assertTrue(((HasDownloads) driver).getDownloadableFiles().isEmpty());
}
----

Source: https://www.selenium.dev/documentation/webdriver/drivers/remote_webdriver/#downloads[Selenium -- Remote WebDriver: Downloads]

=== Browser-specific features on a remote driver

Each browser has features available only to it (casting, network conditions, Firefox add-ons and so on), and the bindings expose them differently in a remote session:

* *Java* returns a plain `RemoteWebDriver` that lacks the browser interfaces. The `Augmenter` adds the implementations for every interface that matches the session's capabilities. `RemoteWebDriver.builder()` augments the driver automatically, so it is the easiest way to get everything.
* *.NET* uses a custom command executor for the commands valid for the browser.
* *Ruby* adds the browser methods to the remote driver through mixins; they just work.
* *JavaScript* returns the browser-specific class (such as `chrome.Driver`) directly, so no step is needed.
* *Python* did not expose them in this run: a `webdriver.Remote` session had no `set_network_conditions`, `get_sinks`, `set_permissions`, `install_addon` or full-page-screenshot methods
(the first Python test above asserts that). Use the BiDi modules (`driver.network`, `driver.webextension`) or a local driver for those features.

[source,java]
----
@Test
void augmenterAddsTheSameInterfacesToAPlainRemoteDriver() {
  ChromeOptions options = new ChromeOptions();
  options.addArguments("--headless=new");
  driver = new RemoteWebDriver(Env.url(Env.CHROME_GRID), options);
  assertFalse(driver instanceof HasCasting);

  driver = new Augmenter().augment(driver);
  assertTrue(driver instanceof HasCasting);
}
----

Source: https://www.selenium.dev/documentation/webdriver/drivers/remote_webdriver/#browser-specific-functionalities[Selenium -- Remote WebDriver: Browser specific functionalities]

=== Tracing client requests

The Java client can emit OpenTelemetry traces for every HTTP request to the Grid, so a request can be followed from the client through the router and distributor to the node. Tracing must be enabled on the server and
the client, and both need a trace exporter pointing at a visualisation tool such as Jaeger UI; the Java dependencies are an OpenTelemetry exporter and a gRPC transport, and the
exporter is configured with system properties (`otel.traces.exporter`, `otel.exporter.jaeger.endpoint` and `otel.resource.attributes`). This is a Java-only feature, and the official page it comes from was written for the Selenium 4.0 betas, so the
dependency versions it names are old; check the Grid observability page for current ones. It was not run here. The Java log line of the runs above, `Using OpenTelemetry for tracing`, shows that
the tracer is on by default.

== Headless and headed browsers

Headless means the browser runs without showing a window. It is the normal mode for CI and containers; headed is useful for debugging a failing test by watching it. Selenium has no
common "headless" switch since the per-browser setters were removed (see "What changed recently"), so you pass the browser's own flag as an argument:

[cols="1,2,3",options="header"]
|===
|Browser |Flag |Notes

|Chrome and Edge
|`--headless=new` (also plain `--headless`)
|The browser's real headless mode, with the same code as the headed browser. The old headless implementation was removed from the Chrome binary in Chrome 132 and lives on as the separate `chrome-headless-shell` binary.

|Firefox
|`-headless` (one dash)
|`moz:headless` is `true` in the returned capabilities.

|Safari
|none
|Safari has no headless mode. On a Mac it needs a logged-in desktop session.

|Internet Explorer
|none
|The driver needs a normal interactive Windows session.
|===

On this host Chrome 155 started and ran Bookshelf with `--headless=new` and with plain `--headless`; both reported a `HeadlessChrome/155.0.0.0` user agent. A run with `--headless=old` also started a session
with a `HeadlessChrome` user agent, although Chrome's own announcement says Chrome 132 and later print an error message for that flag instead of starting the old mode, so do not rely on it and migrate to
`--headless=new` or to `chrome-headless-shell`. Selenium Manager does not download `chrome-headless-shell` (its `--browser` choices are chrome, firefox, edge, iexplorer, safari, safaritp, webview2 and electron), so
you point `binary` at it yourself. Headless pages can differ from headed ones in default window size, in GPU-dependent rendering and in features that need a window (a headless browser has no real focus
or print preview), so set an explicit `--window-size`, as the Chrome examples below do, rather than relying on the default. Headed runs were not performed on this host, to avoid popping windows up on the desktop; Firefox ran headless in the container.

Source: https://www.selenium.dev/documentation/webdriver/browsers/chrome/#arguments[Selenium -- Chrome: Arguments]

Source: https://developer.chrome.com/blog/removing-headless-old-from-chrome[Chrome for Developers -- Removing --headless=old from Chrome]

*Network conditions* simulate latency, throughput and being offline for the whole browser session, through ChromeDriver's `chromium/network_conditions` command. Throughput is in bytes per second (the test converts
kilobits), and `-1` means no limit. `deleteNetworkConditions` / `delete_network_conditions` restores the defaults. Be careful: conditions persist for the session, so a test that sets them and fails before resetting them poisons later steps.

[source,java]
----
@Test
void networkConditionsSlowTheBrowserDown() {
  ChromiumNetworkConditions slow = new ChromiumNetworkConditions();
  slow.setOffline(false);
  slow.setLatency(Duration.ofMillis(400));
  slow.setDownloadThroughput(500 * 1024 / 8); // 500 kbps
  slow.setUploadThroughput(500 * 1024 / 8);
  driver.setNetworkConditions(slow);
  assertEquals(Duration.ofMillis(400), driver.getNetworkConditions().getLatency());

  long start = System.nanoTime();
  driver.get(Env.BASE_URL + "/books");
  long slowMs = (System.nanoTime() - start) / 1_000_000;

  driver.deleteNetworkConditions();
  start = System.nanoTime();
  driver.get(Env.BASE_URL + "/books");
  long fastMs = (System.nanoTime() - start) / 1_000_000;
  System.out.printf("with latency 400 ms: %d ms, without: %d ms%n", slowMs, fastMs);
  assertTrue(slowMs > fastMs + 300);
}

@Test

=== Firefox special features

*Add-ons.* Unlike Chrome extensions, Firefox add-ons are not part of the capabilities (see the geckodriver discussion in https://github.com/mozilla/geckodriver/issues/1476[issue 1476]); they are installed after the driver has started. A signed `.xpi` from the Mozilla add-ons site installs
permanently for the session. An unfinished extension is unsigned, and can only be installed as *temporary*, by passing a zip file or a directory (Selenium 4.5). Uninstalling needs the add-on id, which the install call returns. The example extension adds a banner
element, like the Chrome one. Its `manifest.json` carries a `browser_specific_settings.gecko.id` (`bookshelf-banner@example.test`) and lists the content script `banner.js`:

[source,java]
----
@Test
void temporaryUnsignedAddon() {
  driver = start();
  Path dir = Path.of("src/test/resources/extensions/bookshelf-banner");
  String id = ((HasExtensions) driver).installExtension(dir, true);
  System.out.println("add-on id: " + id);

  driver.get(Env.BASE_URL_FROM_DOCKER + "/books");
  String text = new WebDriverWait(driver, Duration.ofSeconds(10))
      .until(d -> d.findElement(By.id("bookshelf-banner"))).getText();
  assertEquals("Injected by the bookshelf-banner add-on", text);

  ((HasExtensions) driver).uninstallExtension(id);
  driver.navigate().refresh();
  assertTrue(driver.findElements(By.id("bookshelf-banner")).isEmpty());
}
----

*Context.* Firefox can run commands in the page (`content`, the default) or in the browser itself (`chrome`), where privileged scripts can touch the browser interface. Since Firefox 138, geckodriver must be started with `--allow-system-access` to switch to the
`chrome` context. Java uses `setContext(FirefoxCommandContext.CHROME)` and Python a context manager, `+with driver.context(driver.CONTEXT_CHROME): ...+`.

[source,java]
----
@Test
void contentContextIsTheDefaultAndChromeNeedsSystemAccess() {
  driver = start();
  HasContext withContext = (HasContext) driver;
  assertEquals(FirefoxCommandContext.CONTENT, withContext.getContext());

  // Firefox 138+ refuses the CHROME context unless geckodriver was started with --allow-system-access.
  var e = assertThrows(Exception.class, () -> withContext.setContext(FirefoxCommandContext.CHROME));
  System.out.println(e.getClass().getSimpleName() + ": " + e.getMessage().lines().findFirst().orElse(""));
}
----

Source: https://www.selenium.dev/documentation/webdriver/browsers/firefox/#context[Selenium -- Firefox: Context]

It passed. The container's geckodriver was not started with the flag, so the `chrome` switch was refused, which is the expected result here:

[source,text]
----
UnsupportedCommandException: System access is required. Start Firefox with "-remote-allow-system-access" to enable it.
----

Passing `-remote-allow-system-access` as a Firefox argument in the options did not help: the node answered `+Argument --remote-allow-system-access can't be set via capabilities+`. For a remote Firefox you therefore
have to start the node's geckodriver with `--allow-system-access` through the Grid's driver configuration (see xref:web/e2e-testing/selenium/selenium-grid.adoc[Selenium Grid]); that was not set up here, so a successful `chrome` context switch was not run.

== Safari

Unlike the Chromium and Firefox drivers, `safaridriver` is installed with the operating system (this host has the one shipped with Safari 27.0.1), so there is nothing for Selenium Manager to download. Automation must be enabled once, from a terminal:

[source,bash]
----
safaridriver --enable
----

Source: https://www.selenium.dev/documentation/webdriver/browsers/safari/[Selenium -- Safari specific functionality]

`--enable` applies configuration changes so that later sessions run without further authentication, and it asks for an administrator password; the same switch exists in Safari as the Develop menu item *Allow Remote Automation*. `safaridriver` also has `-p` (port), `-b`
(a port for WebDriver BiDi WebSocket connections), `--diagnose` (diagnostic logging) and, in this version, `--mcp` (run as an MCP server over standard input and output). Enabling remote automation is a system setting, which was
not changed on this host, so a Safari session was attempted but not completed: starting `webdriver.Safari()` fails with the message that "Allow remote automation" must be enabled in Safari's Developer settings. The code below follows the official examples and was not run.

[source,java]
----
SafariOptions options = new SafariOptions();
SafariDriverService service = new SafariDriverService.Builder().withLogging(true).build();
WebDriver driver = new SafariDriver(service, options);
----

Source: https://www.selenium.dev/documentation/webdriver/browsers/safari/[Selenium -- Safari specific functionality]

[source,python]
----
options = webdriver.SafariOptions()
service = webdriver.SafariService(enable_logging=True)
driver = webdriver.Safari(service=service, options=options)
----

Source: https://www.selenium.dev/documentation/webdriver/browsers/safari/[Selenium -- Safari specific functionality]

Key points:

* Capabilities specific to Safari are listed by Apple in https://developer.apple.com/documentation/webkit/about_webdriver_for_safari[About WebDriver for Safari]; the Java `SafariOptions` offers `setAutomaticInspection`, `setAutomaticProfiling`, `setUseTechnologyPreview` and `enableBiDi`.
* Safari on iOS is not automated with Selenium; the documentation points to the https://appium.io/[Appium] project.
* There is no headless mode, and logging is only on or off: you cannot choose the location or level. When on, the logs are written to `+~/Library/Logs/com.apple.WebDriver/+` (Java `withLogging(true)` or the system property `SafariDriverService.SAFARI_DRIVER_LOGGING`, Python `SafariService(enable_logging=True)`).

== Internet Explorer and IE mode

As of June 2022 Selenium no longer officially supports standalone Internet Explorer. What remains is the Internet Explorer driver's ability to run *Microsoft Edge in IE Compatibility Mode*, which is the way to test sites that still need Internet Explorer behaviour.
The IE driver is the only driver maintained by the Selenium project itself. Both 32-bit and 64-bit builds of `IEDriverServer.exe` exist, and the bitness of the driver decides the bitness of the browser it launches, but the 64-bit driver has
https://jimevansmusic.blogspot.co.uk/2014/09/screenshots-sendkeys-and-sixty-four.html[known limitations], so the 32-bit one is recommended. IE mode runs only on Windows, so none of this section was run on this macOS host; the code follows the official examples.

=== Starting IE mode

Since IE Driver 4.5.0 the options are simple. If Internet Explorer is not on the system (the default on Windows 11), you need no special options: the driver uses Edge and locates it. If both are present, you only need to ask to attach to Edge. On Windows 10 with an explicit location:

[source,java]
----
InternetExplorerOptions options = new InternetExplorerOptions();
options.attachToEdgeChrome();
options.withEdgeExecutablePath(System.getenv("EDGE_BIN"));
WebDriver driver = new InternetExplorerDriver(options);
----

Source: https://www.selenium.dev/documentation/webdriver/browsers/internet_explorer/#options[Selenium -- Internet Explorer: Options]

[source,python]
----
options = webdriver.IeOptions()
options.attach_to_edge_chrome = True
options.edge_executable_path = os.environ["EDGE_BIN"]
driver = webdriver.Ie(options=options)
----

Source: https://www.selenium.dev/documentation/webdriver/browsers/internet_explorer/#options[Selenium -- Internet Explorer: Options]

[source,csharp]
----
var options = new InternetExplorerOptions();   // Windows 11: nothing else is needed
var driver = new InternetExplorerDriver(options);
----

Source: https://www.selenium.dev/documentation/webdriver/browsers/internet_explorer/#options[Selenium -- Internet Explorer: Options]

Microsoft documents the Edge side of IE mode (enabling it and the site list) in https://learn.microsoft.com/en-us/microsoft-edge/webdriver-chromium/ie-mode[Use Internet Explorer mode in Microsoft Edge with WebDriver].

=== IE driver service

The Service for IE directs the log file and level and the place where supporting files are extracted. File output and console output have been available since Selenium 4.10; the log levels are `FATAL`, `ERROR`, `WARN`, `INFO`, `DEBUG` and `TRACE`, and
when logging output is specified the default level is `FATAL`. The Java builder methods are `withLogFile`, `withLogOutput`, `+withLogLevel(InternetExplorerDriverLogLevel...)+` and `withExtractPath`.

Source: https://www.selenium.dev/documentation/webdriver/browsers/internet_explorer/#service[Selenium -- Internet Explorer: Service]

=== The IE Driver Server

`IEDriverServer.exe` is a standalone server that implements the WebDriver protocol. It was tested with Internet Explorer 11 on Windows 10 and may work with older versions, which is not supported. You do not need an installer: download the
executable from the https://www.selenium.dev/downloads/[Selenium downloads page] and put it in the `PATH` (Selenium Manager can also find it since Selenium 4.7). Its command-line switches (`-`, `--` and `/` prefixes all work) are:

[cols="2,3",options="header"]
|===
|Switch |Meaning

|`--port=<portNumber>`
|The port of the driver's HTTP server. Default 5555.

|`--host=<hostAdapterIPAddress>`
|The IP address of the host adapter to listen on. Default 127.0.0.1.

|`--log-level=<logLevel>`
|`FATAL`, `ERROR`, `WARN`, `INFO`, `DEBUG` or `TRACE`. Default `FATAL`.

|`--log-file=<logFile>`
|Full path of the log file. Default is standard output.

|`--extract-path=<path>`
|Directory used to extract supporting files. Default is the TEMP directory.

|`--silent`
|Suppresses diagnostic output at start-up.
|===

In Java the same settings can be passed as the system properties `webdriver.ie.driver` (the binary location), `webdriver.ie.driver.host`, `webdriver.ie.driver.loglevel`, `webdriver.ie.driver.logfile`, `webdriver.ie.driver.silent` and `webdriver.ie.driver.extractpath`.

The driver needs this configuration on the target machine:

* The Protected Mode setting must be the same for every zone (on or off), and Enhanced Protected Mode must be off for IE 10 and later. Internet Explorer needs a new browser session when a navigation crosses a Protected Mode boundary, which orphans the COM object the driver controls; requiring identical settings avoids the transition. Current drivers check the settings and return an error if they differ.
* The browser zoom must be 100%, so that native mouse events get the right coordinates, and on Windows 10 "Change the size of text, apps, and other items" must also be 100%.
* For IE 11 only, a registry DWORD named `iexplore.exe` with value 0 must exist under `HKEY_LOCAL_MACHINE\SOFTWARE\Microsoft\Internet Explorer\Main\FeatureControl\FEATURE_BFCACHE` (under `Wow6432Node` on 64-bit Windows), so that the driver keeps its connection to the browser.

Other behaviour to know about:

* The driver uses *native events* (operating-system input) for the mouse and keyboard where it can, instead of simulated JavaScript events. Native events do not depend on the JavaScript sandbox and give proper event propagation, but the browser window needs focus, and the machine is effectively unavailable for other work while a test runs. Hovering fails while the real mouse pointer is inside the browser window.
* Clicking an `option` element and submitting a form with `submit()` use JavaScript instead of native events, so if the page's `onchange` or `onsubmit` handler calls `alert()`, `confirm()` or `prompt()`, the call blocks until the dialog is dismissed by hand, and there is no WebDriver-only workaround.
* Several instances of the driver are largely untested and may share cookies and window focus. The two documented workarounds are to start IE in private mode (`ie.forceCreateProcessApi` true plus `ie.browserCommandLineSwitches` `-private`, IE 8 and later, with `TabProcGrowth` 0) or to set `ie.ensureCleanSession`. Otherwise use Remote WebDriver and virtual machines.
* The server accepts connections only from the local machine, and this cannot be changed without modifying its source. To run IE on another machine, use the Java standalone server with the Remote WebDriver class of your binding.
* Running `IEDriverServer.exe` inside a Windows Service is explicitly unsupported.

Source: https://www.selenium.dev/documentation/ie_driver_server/[Selenium -- IE Driver Server]

The driver's internals page adds that the driver talks to a local HTTP server using the W3C protocol and keeps the native interop surface small, uses ATL smart pointers to manage COM objects, and synthesises keyboard and mouse input by posting window messages
to the browser instance (for typing, only key-down and key-up messages are posted, plus a "probe" event so key-press events are ordered correctly).

Source: https://www.selenium.dev/documentation/ie_driver_server/internals/[Selenium -- Internet Explorer Driver Internals]

== Pitfalls

* *Versions of browser and driver must match.* Let Selenium Manager choose; set a driver path only for a reason, and remember that a browser binary set through `binary` is the one the driver must match.
* *Units differ between bindings.* Timeouts are `Duration` in Java, milliseconds in Python's `options.timeouts` and seconds in Python's `driver.timeouts`.
* *Do not send return-only capabilities.* `setWindowRect` is reported by the driver and rejected as input.
* *Use the right headless flag.* `--headless=new` for Chrome and Edge, `-headless` for Firefox; Safari and IE have none.
* *The default page-load strategy waits for everything.* Use `eager` or `none` only with explicit waits, and not for pages whose scripts build the content after `DOMContentLoaded`.
* *`quit()`, not `close()`.* Leaked drivers and browsers are the usual CI slowdown.
* *Remote sessions do not see your files or `localhost`.* Set a file detector for uploads, enable managed downloads for downloads, and give the remote browser an address it can reach (`host.docker.internal` for a container, a service name in Compose or Kubernetes).
* *Browser-specific features need an augmented driver.* In Java use the builder or the `Augmenter`; in Python use a local driver or BiDi.
* *Conditions and permissions persist for the session.* Network conditions and permissions set through the driver stay until deleted or until `quit()`.
* *Never put credentials in code.* Read Grid and application passwords from the environment.
