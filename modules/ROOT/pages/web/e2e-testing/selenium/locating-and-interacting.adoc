Selenium WebDriver drives a real browser through the W3C WebDriver protocol: you ask the driver for a reference to a page element, then
tell the browser to do something with it, or you send the browser itself a command such as "go back", "accept this dialog" or "print this
page". This page covers both halves of that vocabulary: how to *find* things (locators, finders, relative locators, the shadow DOM) and
how to *act* on them and on the browser (element interactions, select lists, the Actions API, navigation, alerts, cookies, frames,
windows and tabs, the virtual authenticator and PDF printing). It was written against Selenium 4.51.0 (released 9 October 2026) and
checked on 25 October 2026. The Java examples use Java 17 and JUnit 5.14.4; the Python examples use pytest with Selenium 4.51.0
and Python 3.13. All of them were run against the xref:web/e2e-testing/example-application-and-test-layout.adoc[Bookshelf] application

docker-selenium container (the differences are listed near the end). The C#, Ruby and JavaScript snippets show where the official

== Locating elements

A *locator* is a way to identify one or more elements on the page; it is the argument you give to `findElement` / `find_element`.
Selenium supports eight traditional strategies, all built on the `By` class (Java, C#, Ruby and JavaScript spell it `+By.id(...)+`,
`+By.Id(...)+`, `+{id: ...}+` and `+By.id(...)+`; Python uses `By.ID` constants):

[cols="2,3,3",options="header"]
|===
|Strategy |Matches |Java / Python

|id
|The element whose `id` attribute equals the value.
|`By.id("q")` / `By.ID, "q"`

|name
|Elements whose `name` attribute equals the value.
|`By.name("q")` / `By.NAME, "q"`

|class name
|Elements whose class attribute contains the value. A compound class name (`"a b"`) is not permitted; use a CSS selector for that.
|`By.className("card")` / `By.CLASS_NAME, "card"`

|tag name
|Elements with that tag.
|`By.tagName("h1")` / `By.TAG_NAME, "h1"`

|link text
|Anchor elements whose visible text matches the value exactly.
|`By.linkText("Catalogue")` / `By.LINK_TEXT, "Catalogue"`

|partial link text
|Anchor elements whose visible text contains the value; with several matches `findElement` returns the first.
|`By.partialLinkText("Sign")` / `By.PARTIAL_LINK_TEXT, "Sign"`

|CSS selector
|Anything a CSS selector can express: attributes, structure, pseudo-classes.
|`By.cssSelector("[data-testid=book-author]")` / `By.CSS_SELECTOR, "[data-testid=book-author]"`

|XPath
|A path through the document tree, absolute or relative; also the only strategy that can match on text of any element or climb to a parent.
|`+By.xpath("//li[@data-testid='book-card']//h3")+` / `+By.XPATH, "//li[@data-testid='book-card']//h3"+`
|===

The id, name, class name and tag name strategies are, in the WebDriver protocol, shortcuts that the driver turns into CSS selectors, so
the CSS selector and XPath strategies are the two that carry real expressive power. All eight run against Bookshelf's catalogue
page like this:

[source,java]
----
@Test
void eightStrategies() {
  driver.get(BASE_URL + "/books?q=quiet");
  assertEquals("quiet", driver.findElement(By.id("q")).getDomProperty("value"));
  assertEquals("search", driver.findElement(By.name("q")).getDomAttribute("type"));
  assertEquals("1", driver.findElement(By.className("card")).getDomAttribute("data-book-id"));
  assertTrue(driver.findElement(By.linkText("Catalogue")).getDomProperty("href").endsWith("/books"));
  assertEquals("Sign in", driver.findElement(By.partialLinkText("Sign")).getText());
  assertEquals("Catalogue", driver.findElement(By.tagName("h1")).getText());
  assertEquals("The Quiet Compiler",
      driver.findElement(By.xpath("//li[@data-testid='book-card']//h3")).getText());
  assertEquals("Mara Velde", driver.findElement(By.cssSelector("[data-testid=book-author]")).getText());
}
----

=== Choosing a locator

Locators are the part of a Selenium suite that breaks most often, so choose them with the page's *contract* in mind rather than its
current markup. A practical order, which matches the guidance of the other tools:

. *A dedicated test attribute*, such as Bookshelf's `data-testid`, through a CSS selector: `+[data-testid=search-submit]+`. Selenium has
no built-in test-id locator (Playwright has `getByTestId`), so wrap the selector once in a helper or a page object.
. *An `id` or `name`* that is part of the page's behaviour (form fields, anchors targeted by labels): stable, fast and unambiguous when
unique. Ids are only unique by convention, so a page with duplicate ids returns the first match.
. *Link text or partial link text* for navigation links whose wording is part of the user-facing contract. They break on any copy
change or translation, and only match `a` elements.
. *CSS selectors on structure* (`+.card > a+`) when no attribute exists. Prefer short selectors tied to meaningful ancestors over long
chains copied from the browser's developer tools.
. *XPath* when you need what CSS cannot do: matching by text (`+//button[normalize-space()='Search']+`), selecting a parent or
ancestor, or position-based logic. Avoid absolute paths (`+/html/body/div[2]/...+`), which break on any layout change.
. *Relative locators* (below) when an element is hard to describe but easy to place next to one that is not.

Selenium has no role- or label-based locators like Playwright's `getByRole` and `getByLabel`. The accessibility information is
available after the fact (`getAriaRole()` and `getAccessibleName()`, in the element-information section), and the XPath-with-label
pattern `+//label[text()='Username']/following-sibling::input+` is the usual workaround.

=== ByChained and ByAll (Java)

The Java support package has two composite locators. `ByChained` applies several locators in sequence, each searching inside the
previous result, so one `findElement` replaces a parent lookup followed by a child lookup. `ByAll` returns elements that match *any* of
the locators, in document order, so one `findElements` finds, for example, the username and password fields together:

[source,java]
----
import org.openqa.selenium.support.pagefactory.ByAll;
import org.openqa.selenium.support.pagefactory.ByChained;

@Test
void chainedAndAllLocators() {
  driver.get(BASE_URL + "/books");
  WebElement title = driver.findElement(new ByChained(By.cssSelector("[data-testid=book-list]"), By.tagName("h3")));
  assertFalse(title.getText().isEmpty());
  driver.get(BASE_URL + "/signin");
  List<WebElement> fields = driver.findElements(new ByAll(By.id("username"), By.id("password")));
  assertEquals(2, fields.size());
}
----

Source: https://www.selenium.dev/documentation/webdriver/elements/locators/[Selenium: Locator strategies]

The Python bindings have no equivalent classes (a search in the 4.51.0 package finds none); chain `find_element` calls on the parent
element, or use a combined CSS selector, instead.

=== Relative locators

Relative locators (called friendly locators in Selenium 3 documentation) describe an element by where it is relative to another one.
Selenium asks the browser for the position and size of the candidate elements and picks those that satisfy the spatial relationship.
They are useful when an element has no good attribute but its neighbour does:

[cols="2,4",options="header"]
|===
|Method (Java / Python) |Meaning

|`above` / `above`
|The element's bottom edge is above the reference element's top edge.

|`below` / `below`
|The element is below the reference.

|`toLeftOf` / `to_left_of`
|The element is left of the reference.

|`toRightOf` / `to_right_of`
|The element is right of the reference.

|`near` / `near`
|The element is at most 50 pixels from the reference by default; Java accepts a different distance as a second argument.
|===

The reference can be a locator or a previously located element; the starting point is the tag, or any other locator, that
filters the candidates (`with(By.tagName("input"))`). Calls chain, which combines constraints (below the email field *and* right of
the cancel button). They run on Bookshelf's sign-in form:

[source,java]
----
import static org.openqa.selenium.support.locators.RelativeLocator.with;

@Test
void relativeLocators() {
  driver.get(BASE_URL + "/signin");
  WebElement above = driver.findElement(with(By.tagName("input")).above(By.id("password")));
  WebElement below = driver.findElement(with(By.tagName("input")).below(By.id("username")));
  WebElement near = driver.findElement(with(By.tagName("input")).near(By.cssSelector("label[for=username]")));
  assertEquals("username", above.getDomAttribute("id"));
  assertEquals("password", below.getDomAttribute("id"));
  assertEquals("username", near.getDomAttribute("id"));
  WebElement button = driver.findElement(with(By.tagName("button")).below(below).toLeftOf(By.id("theme-toggle")));
  assertEquals("Sign in", button.getText());
}
----

Source: https://www.selenium.dev/documentation/webdriver/elements/locators/[Selenium: Locator strategies]

def test_relative_locators(driver, base_url):
    driver.get(f"{base_url}/signin")
    above = driver.find_element(locate_with(By.TAG_NAME, "input").above({By.ID: "password"}))
    below = driver.find_element(locate_with(By.TAG_NAME, "input").below({By.ID: "username"}))
    near = driver.find_element(locate_with(By.TAG_NAME, "input").near({By.CSS_SELECTOR: "label[for=username]"}))

Relative locators are computed from the rendered geometry, so they depend on viewport size and layout: a responsive design that stacks a
row of buttons vertically at phone width changes what `toLeftOf` means. Use them as a fallback, check them at the viewport your
tests actually run in, and prefer `near` only when the relative positions vary.

== Finding elements

=== find_element and find_elements

`findElement` returns a reference to the *first* matching element in document order and throws `NoSuchElementException` when nothing
matches. `findElements` returns a list of every match and an *empty list* when there are none, which makes it the idiomatic existence
check. A reference is a handle to an element in the browser's current document; if the page replaces that element (a re-render, a
navigation) the handle becomes stale and any use throws `StaleElementReferenceException`, so look the element up again rather than
caching it across page changes.

=== Scoping a search

`WebDriver`, `WebElement` and `ShadowRoot` all implement the `SearchContext` interface, so a search can start from any of them. A
lookup from an element searches only its descendants; use it to find a field inside the right card when the page repeats the same
markup, instead of building one long locator:

[source,java]
----
@Test
void findersScopingAndActiveElement() {
  driver.get(BASE_URL + "/books");
  List<WebElement> cards = driver.findElements(By.cssSelector("[data-testid=book-card]"));
  assertEquals(6, cards.size());
  assertFalse(cards.get(0).findElement(By.tagName("h3")).getText().isEmpty());
  assertTrue(driver.findElements(By.id("does-not-exist")).isEmpty());
  assertThrows(NoSuchElementException.class, () -> driver.findElement(By.id("does-not-exist")));
  driver.findElement(By.id("q")).click();
  assertEquals("q", driver.switchTo().activeElement().getDomAttribute("id"));
}
----

Source: https://www.selenium.dev/documentation/webdriver/elements/finders/[Selenium: Finding web elements]

round trips; when speed matters, a single CSS selector or XPath that expresses the same path is cheaper.

=== The shadow DOM

A shadow DOM is an encapsulated DOM tree hidden inside an element (a *shadow host*): ordinary locators on the document do not see into it.
Selenium can reach an *open* shadow root with `getShadowRoot()` (Java) or `shadow_root` (Python), which returns a `SearchContext`
you can search from. Inside a shadow root use CSS selectors: when tried with Python on Chrome 155, `By.ID` and CSS selectors worked, while an XPath and a
tag-name lookup failed with `invalid argument: invalid locator`. A lookup stays inside that one root and does not cross into nested
shadow roots (a selector for an element two roots down raised `NoSuchElementException`), so nested components are searched one root at a
time. The examples use an open shadow root; closed roots were not tested.

[source,java]
----
@Test
void shadowDom() {
  driver.get(dataUrl("""
      <div id=host></div><script>
      const r = document.getElementById('host').attachShadow({mode: 'open'});
      r.innerHTML = '<button id=inner class=pill>Inside</button><input name=q>';
      </script>"""));
  SearchContext root = driver.findElement(By.id("host")).getShadowRoot();
  assertEquals("Inside", root.findElement(By.cssSelector("#inner")).getText());
  assertEquals(2, root.findElements(By.cssSelector("button, input")).size());
  // since 4.50 relative locators also work from a shadow root
  WebElement input = root.findElement(with(By.tagName("input")).near(By.id("inner")));
  assertEquals("q", input.getDomAttribute("name"));
}
----

Source: https://www.selenium.dev/documentation/webdriver/elements/finders/[Selenium: Finding web elements]

== Interacting with elements

The high-level element commands are `click`, `sendKeys` / `send_keys`, `clear` and `submit`, plus the `Select` helper covered below. They
are designed to emulate a user's experience, and unlike the Actions API they try to make the action possible first:

* If the element is outside the viewport, Selenium scrolls it into view (aligning the bottom of the element with the bottom of the
viewport) before acting. If that fails, or the element is not displayed for another reason, the command throws.
* Selenium decides whether an element is displayed by running a JavaScript atom that checks for things that would keep it from being
visible (`display: none`, zero size, hidden by an ancestor and so on). The W3C specification mentions the concept but does not define
it, which is why `isDisplayed()` is an approximation.
* If the centre of the element is covered by another element, `click` throws `ElementClickInterceptedException`. A sticky header, a cookie
banner or an overlay still animating away are the usual culprits; wait for the covering element to go (an explicit condition, see
xref:web/e2e-testing/selenium/waits-and-expected-conditions.adoc[Waits & Expected Conditions]) rather than forcing the click with
JavaScript, which would hide the bug a real user would hit.

`click` clicks the centre of the element. `sendKeys` types the keys into a *keyboard-interactable* element, typically a text input or an
element with `contenteditable`; otherwise it throws. The key constants (`Keys.ENTER`, `Keys.TAB`, `Keys.CONTROL` and so on) can be sent
too. `clear` resets the content of an editable element. `submit` was a separate endpoint in Selenium 3; in Selenium 4 it works by running a
script, so the documentation recommends clicking the page's submit button instead. The test below exercises all four on a small page:

[source,java]
----
@Test
void informationAndInteractions() {
  driver.get(dataUrl("""
      <style>#lnk{color:rgb(0,0,255);font-size:20px}</style>
      <input id=t value=start><input id=c type=checkbox checked><input id=d disabled>
      <a id=lnk href="#x">Link text</a><div id=hidden style="display:none">hidden</div>
      <button id=b onclick="this.textContent='clicked'">Press</button>
      <form id=f onsubmit="document.title='submitted';return false"><input id=s name=s><input type=submit></form>"""));
  WebElement t = driver.findElement(By.id("t"));
  t.clear();
  t.sendKeys("typed");
  // ... information checks, shown in the next section ...
  driver.findElement(By.id("b")).click();
  assertEquals("clicked", driver.findElement(By.id("b")).getText());
  driver.findElement(By.id("s")).sendKeys("x");
  driver.findElement(By.id("s")).submit();
  assertEquals("submitted", driver.getTitle());
}
----

Source: https://www.selenium.dev/documentation/webdriver/elements/interactions/[Selenium: Interacting with web elements]

== Information about elements

You can query a lot about an element once you have it:

[cols="2,2,4",options="header"]
|===
|Java / Python |Returns |Notes

|`isDisplayed()` / `is_displayed()`
|boolean
|Whether the element is displayed, by the approximation described above.

|`isEnabled()` / `is_enabled()`
|boolean
|False for disabled form controls.

|`isSelected()` / `is_selected()`
|boolean
|For checkboxes, radio buttons and `option` elements.

|`getTagName()` / `tag_name`
|string
|Lower-case tag name.

|`getRect()` / `rect`
|x, y, width, height
|Position from the top-left of the page and size of the element's bounding box.

|`getCssValue(name)` / `value_of_css_property(name)`
|string
|The computed style property.

|`getText()` / `text`
|string
|The rendered text, as a user sees it: hidden text is excluded and whitespace is normalised.

|`getDomAttribute(name)` / `get_dom_attribute(name)`
|string or null
|The value of the HTML *attribute* as written in the markup.

|`getDomProperty(name)` / `get_property(name)`
|object
|The JavaScript *property* of the element: the live state.

|`getAttribute(name)` / `get_attribute(name)`
|string or null
|The older helper: returns the property if there is one and otherwise the attribute, plus a few boolean-attribute conversions. It is what most older code uses.

|`getAriaRole()` / `aria_role`
|string
|The computed WAI-ARIA role (for example `link`, `button`).

|`getAccessibleName()` / `accessible_name`
|string
|The computed accessible name that assistive technology would announce.

|`+getScreenshotAs(...)+` / `screenshot(path)`
|file, bytes or base64
|A screenshot of just this element.
|===

== File upload

Selenium cannot drive the operating system's file chooser dialog, so it offers a shortcut: when the element is an

== Select lists

`select` elements have special behaviour (options, a selected state, a multiple mode), and the support package wraps them in a `Select`
class so tests say what they mean. It only works with the HTML `select` and `option` elements; a JavaScript drop-down built from `div` or
`li` elements is driven with ordinary clicks. A standard list allows exactly one selected option; a list with the `multiple` attribute
allows several, and only those can be deselected. Since Selenium 4.5, constructing a `Select` for a disabled `select` element throws.

[cols="2,3",options="header"]
|===
|Operation |Java / Python

|Create
|`new Select(element)` / `Select(element)`

|`selectByVisibleText`, `selectByValue`, `selectByIndex` / `select_by_visible_text`, `select_by_value`, `select_by_index`

|Inspect

== Colors

Colour definitions on the web are not constant: the same colour can be hex, `rgb`, `rgba`, `hsl` or `hsla`, and `getCssValue` returns
whatever format the browser chooses (see the Chrome and Firefox difference above). The `Color` class, in the support package, parses any
of the common formats into one object you can compare and convert. Java and Python provide it (the official page documents Java, Python
and Kotlin).

[source,java]
----
import org.openqa.selenium.support.Color;
import org.openqa.selenium.support.Colors;

@Test
void colors() {

  assertEquals(Color.fromString("#2f7ed8"), Color.fromString(p.getCssValue("color")));
  assertEquals("rgba(0, 0, 0, 0)", Color.fromString(p.getCssValue("background-color")).asRgba());
}

== The Actions API

The element commands above are high-level. The Actions API is the low-level interface: it sends *virtualised device input* to the browser,
exactly as the W3C specification describes it. Selenium provides three kinds of input source: a *key* input for keyboards, a *pointer*
input for a mouse, a pen or a touch device, and a *wheel* input for a scroll wheel (added in Selenium 4.2). You build a chain of actions
assigned to those inputs and run them with `perform()`; the browser executes them in order. Each pointer movement and wheel scroll can take
a duration, and `pause` adds a plain wait between actions.

You rarely need the raw building blocks: the `Actions` class (Java) and `ActionChains` (Python) combine them into convenience methods for the common
gestures, as shown below. Two things to remember:

* *The driver remembers the state of every input device for the whole session.* A key that was pressed and not released stays pressed, and the
pointer stays wherever the last action left it, even if you create a new `Actions` object. There is a special method to release everything:
`((RemoteWebDriver) driver).resetInputState()` in Java, `ActionChains(driver).reset_actions()` in Python. In a suite with a fresh browser per test
this rarely matters, but with a shared driver call it between tests.
* *Actions do not scroll for you*, unlike `click` and `sendKeys`. Moving the pointer to an element that is outside the viewport fails, and
the wheel input exists precisely to scroll first.

All the Actions examples share one fixture page: an input, a target `div`, a draggable box and a drop zone, with a log that records the events
the browser delivered, and a tall `div` so the page can scroll.

=== Keyboard actions

A keyboard can do exactly two things: press a key down and release a pressed key. Regular characters are keys; the non-character keys (Shift, Control,
Enter, arrows) have unicode values that Selenium exposes as the `Keys` class (the constants differ by language, and the full list is in
each binding's API documentation). `sendKeys` in the Actions API is a convenience that combines `keyDown` and `keyUp` for typing several
characters in the middle of other actions; given an element, it first moves to or focuses that element. The example types text, then
holds Shift for a capital letter, then does select-all and cut with the platform's shortcut key (Command on macOS, Control elsewhere):

[source,java]
----
@Test
void keyboard() {
  driver.get(dataUrl(PAGE));
  WebElement field = driver.findElement(By.id("field"));
  new Actions(driver).sendKeys(field, "selenium").keyDown(Keys.SHIFT).sendKeys("a").keyUp(Keys.SHIFT).perform();
  assertEquals("seleniumA", field.getDomProperty("value"));
  Keys cmd = System.getProperty("os.name").toLowerCase().contains("mac") ? Keys.COMMAND : Keys.CONTROL;
  new Actions(driver).keyDown(cmd).sendKeys("a").sendKeys("x").keyUp(cmd).perform(); // select all, cut
  assertEquals("", field.getDomProperty("value"));
}
----

=== Mouse actions

A mouse can do three things: press a button, release a pressed button and move. A mouse has five defined buttons: 0 left, 1 middle,
2 right, 3 back and 4 forward. The convenience methods combine the three primitives:

[cols="2,4",options="header"]
|===
|Java / Python |What it does

|`click(element)` / `click(element)`
|Moves to the in-view centre of the element, then presses and releases the left button. With no argument it clicks at the current pointer location.

|`clickAndHold(element)` / `click_and_hold(element)`
|Moves to the centre and presses the left button without releasing.

|`release()` / `release()`
|Releases the left button wherever the pointer is.

|`contextClick(element)` / `context_click(element)`
|Moves to the centre and presses and releases the right button (button 2).

|`doubleClick(element)` / `double_click(element)`
|Moves to the centre and presses and releases the left button twice.

|`moveToElement(element)` / `move_to_element(element)`
|Moves to the in-view centre of the element (hover). The element must be in the viewport, or the command errors. Java also has `moveToElement(element, x, y)`, and Python `move_to_element_with_offset(element, x, y)`: offsets are measured from the element's centre.

|`moveByOffset(x, y)` / `move_by_offset(x, y)`
|Moves the pointer from its *current* position (the top-left of the viewport if it has not moved yet). Positive x moves right and positive y moves down, so `moveByOffset(30, -10)` is 30 right and 10 up. The destination must be inside the viewport.

|`dragAndDrop(source, target)` / `drag_and_drop(source, target)`
|Click-and-hold on the source, move to the centre of the target, release.

|`dragAndDropBy(source, x, y)` / `drag_and_drop_by_offset(source, x, y)`
|Click-and-hold on the source, move by the given offset, release.
|===

The pointer position does not change when the page is scrolled, which matters when mixing scrolls and offsets. The mouse example clicks,

=== Pen actions

A pen is a pointer input with the same behaviour as a mouse plus event properties unique to a stylus (pressure, tilt, twist). Where a
mouse has five buttons, a pen has three button states: 0 touch contact (the default, equivalent to a left click), 2 barrel button
(equivalent to a right click) and 5 eraser (currently unsupported by the drivers). In Java you tell `Actions` to use a pen as the active
pointer; in Python you build the sequence with an `ActionBuilder` whose pointer is a `PointerInput` of kind `pen`.

@Test

=== Scroll wheel actions

Because `Actions` does not scroll by itself, the wheel input provides four ways to scroll:

* *Scroll to an element* (`scrollToElement` / `scroll_to_element`): scrolls so that the bottom of the element is at the bottom of the viewport,
whether the element was above or below. If the element is already inside the viewport nothing happens. The most common case.
* *Scroll by an amount* (`scrollByAmount(dx, dy)` / `scroll_by_amount(dx, dy)`): positive values go right and down, negative left and up.
* *Scroll from an origin* (`scrollFromOrigin` / `scroll_from_origin`), which takes a *scroll origin* and a delta. The origin is either the
viewport (an offset from its upper-left corner) or an element (an offset from its centre). Use it to scroll only part of the page, for
example a nested scrollable container or an iframe. If the element is out of view it is first scrolled to the bottom of the viewport, and
if the resulting origin falls outside the viewport the command errors.

Scrolling is asynchronous in a browser with smooth scrolling, so assert on the final scroll position with a wait, not immediately:

[source,java]
----
@Test
void wheel() {
  driver.get(dataUrl(PAGE));
  WebDriverWait wait = new WebDriverWait(driver, Duration.ofSeconds(5));
  new Actions(driver).scrollByAmount(0, 500).perform();
  wait.until(d -> scrollY() == 500);
  new Actions(driver).scrollFromOrigin(ScrollOrigin.fromViewport(10, 10), 0, -200).perform();
  wait.until(d -> scrollY() == 300);
  new Actions(driver).scrollToElement(driver.findElement(By.id("tall"))).perform();
}
----

Source: https://www.selenium.dev/documentation/webdriver/actions_api/wheel/[Selenium: Scroll wheel actions]

== Browser interactions

The remaining features act on the browser itself rather than on an element.

=== Title, URL and navigation

`getTitle()` / `title` and `getCurrentUrl()` / `current_url` read the title and the address bar. `get(url)` opens a page and, by default,
waits for the page load strategy to finish (see xref:web/e2e-testing/selenium/drivers-browsers-and-options.adoc[Drivers, Browsers & Options]
for `normal`, `eager` and `none`). The history commands are `navigate().to(url)` (the same as `get`), `navigate().back()`,
`navigate().forward()` and `navigate().refresh()` in Java, and `driver.back()`, `driver.forward()` and `driver.refresh()` in Python.

=== Alerts, prompts and confirmations

WebDriver can handle the three kinds of native JavaScript popups. An *alert* shows a message and an OK button; a *confirm* adds a
Cancel button; a *prompt* also has a text input. While one is open, the page is blocked, and any other WebDriver command fails with
`UnexpectedAlertOpenException` unless the session's unhandled-prompt behaviour says otherwise. Switch to it, read it and answer it:

[cols="2,4",options="header"]
|===
|Java / Python |What it does

|`driver.switchTo().alert()` / `driver.switch_to.alert`
|Returns the open alert, or throws `NoAlertPresentException` when there is none.

|`getText()` / `text`
|The message.

|`accept()`, `dismiss()` / `accept()`, `dismiss()`
|Press OK or Cancel (and OK or close on an alert).

|`sendKeys(text)` / `send_keys(text)`
|Types into a prompt, replacing its default text. Cancelling does not submit text.
|===

The popup appears asynchronously after the click, so wait for it with the `alertIsPresent` expected condition instead of switching immediately:

[source,java]
----
@Test
void alerts() {
  driver.get(dataUrl("""
      <button id=a onclick="alert('Hi')">alert</button>
      <button id=c onclick="document.title=confirm('Sure?')">confirm</button>
      <button id=p onclick="document.title=prompt('Name?','x')">prompt</button>"""));
  driver.findElement(By.id("a")).click();
  Alert alert = waitFor().until(ExpectedConditions.alertIsPresent());
  assertEquals("Hi", alert.getText());
  alert.accept();
  driver.findElement(By.id("c")).click();
  waitFor().until(ExpectedConditions.alertIsPresent()).dismiss();
  assertEquals("false", driver.getTitle());
  driver.findElement(By.id("p")).click();
  Alert prompt = waitFor().until(ExpectedConditions.alertIsPresent());
  prompt.sendKeys("Alberto");
  prompt.accept();
  assertEquals("Alberto", driver.getTitle());
  assertThrows(NoAlertPresentException.class, () -> driver.switchTo().alert());
}
----

=== Cookies

A cookie is a small piece of data a site stores in the browser to recognise the user. WebDriver can add, read and delete cookies of the
*current browsing context*:

[cols="2,4",options="header"]
|===
|Java / Python |What it does

|`manage().addCookie(cookie)` / `add_cookie(dict)`
|Adds a cookie. The cookie must be for the domain of the page you are on, so navigate to the site first. If the home page is slow, pick a
small page of the same site (a 404 page is typical) to set cookies before the real test. Java builds one with `+new Cookie.Builder(name, value)...build()+`; Python takes a dictionary with `name`, `value`, `path`, `domain`, `secure`, `httpOnly`, `expiry` and `sameSite`.

|`manage().getCookieNamed(name)` / `get_cookie(name)`
|The serialised cookie with that name, or null.

|`manage().getCookies()` / `get_cookies()`
|Every cookie visible to the current page.

|`manage().deleteCookieNamed(name)`, `deleteCookie(cookie)` / `delete_cookie(name)`
|Deletes one cookie.

|`manage().deleteAllCookies()` / `delete_all_cookies()`
|Deletes all cookies of the current browsing context.
|===

The `sameSite` attribute (`Strict` or `Lax`) controls whether the cookie is sent with requests that originate from third-party sites, and is a
defence against cross-site request forgery. It is supported by Chrome 80 and later and Firefox 79 and later with Selenium 4. `HttpOnly`
cookies, such as Bookshelf's `bookshelf_session`, are readable through WebDriver even though page JavaScript cannot see them. That
makes cookies the cheapest way to reuse a login: sign in once through the UI (or the API), keep the session cookie, and add it to later
browsers instead of repeating the form. This test does the whole cycle on Bookshelf:

[source,java]
----
@Test
void cookies() {
  driver.get(BASE_URL + "/signin");
  driver.manage().addCookie(new Cookie.Builder("theme-hint", "dark").sameSite("Strict").build());
  Cookie hint = driver.manage().getCookieNamed("theme-hint");
  assertEquals("dark", hint.getValue());
  assertEquals("Strict", hint.getSameSite());
  driver.findElement(By.id("username")).sendKeys("reader");
  driver.findElement(By.id("password")).sendKeys(READER_PASSWORD);
  driver.findElement(By.cssSelector("[data-testid=signin-submit]")).click();
  waitFor().until(ExpectedConditions.urlContains("/account"));
  Cookie session = driver.manage().getCookieNamed("bookshelf_session");
  assertTrue(session.isHttpOnly());
  assertEquals("Lax", session.getSameSite());
  Set<String> names = driver.manage().getCookies().stream().map(Cookie::getName).collect(Collectors.toSet());
  assertEquals(Set.of("theme-hint", "bookshelf_session"), names);
  driver.manage().deleteCookie(session);
  driver.get(BASE_URL + "/account");
  assertTrue(driver.getCurrentUrl().contains("/signin"));
  driver.manage().addCookie(new Cookie("bookshelf_session", session.getValue()));
  driver.get(BASE_URL + "/account");
  assertTrue(driver.getCurrentUrl().endsWith("/account"));
  driver.manage().deleteAllCookies();
  assertTrue(driver.manage().getCookies().isEmpty());
}
----

=== Frames and iframes

Frames (a deprecated way of building layouts from several documents) and iframes (a document embedded from the same or another
origin) are separate browsing contexts. Selenium only sees the elements of the *top-level document* until you switch into the frame,
so looking for a button that lives in an iframe fails with `NoSuchElementException` even though you can see it. There are three ways to switch:

* *By element* (the most flexible): find the `iframe` element with any locator and pass it to `switchTo().frame(element)`.
* *By name or id*: `switchTo().frame("inner-name")`; if the value is not unique, the first match wins.
* *By index*: `switchTo().frame(1)`, the position among the frames of the current document (zero-based).

To leave, `switchTo().defaultContent()` returns to the top-level document and `switchTo().parentFrame()` goes up one level. The tests use
two iframes created from `srcdoc` attributes:

[source,java]
----
@Test
void frames() {
  driver.get(dataUrl("""
      <h1 id=top>Top</h1><iframe id=inner name=inner-name srcdoc="<button id=b onclick=&quot;this.textContent='clicked'&quot;>Inside</button>"></iframe>
      <iframe srcdoc="<p id=second>Second</p>"></iframe>"""));
  assertThrows(NoSuchElementException.class, () -> driver.findElement(By.id("b")));
  driver.switchTo().frame(driver.findElement(By.id("inner")));   // by element
  driver.findElement(By.id("b")).click();
  assertEquals("clicked", driver.findElement(By.id("b")).getText());
  driver.switchTo().defaultContent();
  driver.switchTo().frame("inner-name");                         // by name or id
  driver.switchTo().parentFrame();
  driver.switchTo().frame(1);                                    // by index
  assertEquals("Second", driver.findElement(By.id("second")).getText());
  driver.switchTo().defaultContent();
  assertEquals("Top", driver.findElement(By.id("top")).getText());
}
----

Source: https://www.selenium.dev/documentation/webdriver/interactions/frames/[Selenium: Working with iframes and frames]

=== Windows and tabs

WebDriver makes no distinction between windows and tabs. If a site opens a new one, you work with it through its *window handle*, a
string that identifies it for the session. `getWindowHandle()` returns the handle of the current one and `getWindowHandles()` the handles of all of them
(in the order they were opened, though you should not depend on it for anything but the first). Opening a window with a link or
`window.open` focuses it on screen, but WebDriver does not know which window the operating system considers active, so you must switch to it:

[source,java]
----
@Test
void windowsAndTabs() {
  driver.get(BASE_URL + "/books");
  String original = driver.getWindowHandle();
  assertEquals(1, driver.getWindowHandles().size());
  ((JavascriptExecutor) driver).executeScript("window.open(arguments[0], '_blank')", BASE_URL + "/signin");
  waitFor().until(ExpectedConditions.numberOfWindowsToBe(2));
  for (String handle : driver.getWindowHandles()) {
    if (!handle.equals(original)) {
      driver.switchTo().window(handle);
    }
  }
  waitFor().until(ExpectedConditions.urlContains("/signin"));
  driver.close();
  driver.switchTo().window(original);   // forgetting this raises NoSuchWindowException
  assertTrue(driver.getCurrentUrl().endsWith("/books"));
  driver.switchTo().newWindow(WindowType.TAB);   // created and focused in one call
  driver.get(BASE_URL + "/");
  assertEquals(2, driver.getWindowHandles().size());
  driver.close();
  driver.switchTo().window(original);
  driver.switchTo().newWindow(WindowType.WINDOW);
  driver.close();
  driver.switchTo().window(original);
}
----

Source: https://www.selenium.dev/documentation/webdriver/interactions/windows/[Selenium: Working with windows and tabs]

`close()` closes the *current* window only and leaves the session on a window that no longer exists, so always switch to a valid handle
afterwards. `quit()` ends the whole session: it closes every window, notifies a Grid that the browser is free and ends the driver process.
Forgetting `quit()` leaves browser and driver processes and ports behind, which is why every example above calls it in a teardown
(`@AfterEach` or a pytest fixture); outside a test framework use `try`/`finally`, and in Python the driver also works as a context
manager (`with webdriver.Chrome() as driver:`). `switchTo().newWindow(WindowType.TAB)` (Selenium 4) creates a window or tab and
switches to it in one call.

==== Window size, position and states

Screen size changes how a page lays out, so tests often set it. The window commands are under `manage().window()` in Java and directly on the
driver in Python:

[cols="2,4",options="header"]
|===
|Java / Python |What it does

==== Screenshots and running JavaScript

Screenshots are part of the same interaction group. `((TakesScreenshot) driver).getScreenshotAs(OutputType.FILE)` (Java) and `driver.save_screenshot(path)`
(Python, also `get_screenshot_as_file`, `get_screenshot_as_png` and `get_screenshot_as_base64`) capture the visible viewport; every `WebElement` is also a
`TakesScreenshot`, and Python's `element.screenshot(path)` captures just that element. The `+executeScript(script, args...)+` / `+execute_script(script, *args)+` call runs
JavaScript in the current context; elements passed as arguments arrive as DOM nodes and can be read back as `arguments[0]`. Treat it as an escape hatch for
reading state and not as a way to click or type, since it bypasses the checks that make interactions realistic.

[source,java]
----
@Test
void windowManagementAndScreenshots(@TempDir Path tmp) throws Exception {

  assertEquals(900, driver.manage().window().getSize().getWidth());
  driver.manage().window().setPosition(new Point(10, 20));
  driver.manage().window().maximize();

  assertTrue(Files.size(tmp.resolve("page.png")) > 1000);
  assertTrue(brand.length() > 0 && brand.length() < shot.length());
  Object text = ((JavascriptExecutor) driver).executeScript("return arguments[0].innerText", driver.findElement(By.tagName("h1")));
  assertNotNull(text);
}

=== Printing a page to PDF

Selenium can ask the browser to print the current page and return the PDF. Configure the output with `PrintOptions`, then call
`print` through the `PrintsPage` interface (Java: `((PrintsPage) driver).print(options)` returning a `Pdf`) or `driver.print_page(options)` (Python). The result is a *base64-encoded*
string, which you decode and write to a file. The Selenium documentation says Chromium browsers must be in headless mode for the command (the examples here ran headless Chrome 155), and
the Python test also passed against Firefox in a container. The options mirror the print dialog and the W3C "Print" command:

[cols="2,2,4",options="header"]
|===
|Java / Python |Default |Meaning

|`setOrientation` / `orientation`
|portrait
|`PORTRAIT` or `LANDSCAPE`.

|`setScale` / `scale`
|1.0
|Scale factor from 0.1 to 2; 1.0 is 100 percent.

|`setBackground` / `background`
|false
|Whether background colours and images are printed.

|`setShrinkToFit` / `shrink_to_fit`
|true
|Shrink the page content to the page width.

|`setPageRanges` / `page_ranges`
|all pages
|Pages to print, such as `"2-4"` (Java) or a list of strings (Python). C# has `AddPageRangeToPrint` and `AddPageToPrint`.

|`setPageSize` / `page_width`, `page_height`
|21.59 by 27.94 cm (US Letter)
|Paper size in centimetres; Java also has named sizes.

|`setPageMargin` / `margin_top`, `margin_bottom`, `margin_left`, `margin_right`
|1 cm
|Page margins in centimetres.

=== Virtual authenticator

Web Authentication (WebAuthn) lets users sign in without passwords using public-key credentials held by an *authenticator*, which can be
a hardware key or software in the device. The *virtual authenticator* emulates one for testing, so a test can register and use a
passkey without touching a real device or answering a biometric prompt. In Selenium you create it from `VirtualAuthenticatorOptions` and add it
to the driver; credentials then live in that authenticator, and you can list, add and remove them. Support is a Chromium feature through the
DevTools WebAuthn domain; Firefox and Safari do not currently document it. The properties you can set:

[cols="2,4",options="header"]
|===
|Option |Meaning

|protocol
|`CTAP2` or `U2F`. U2F authenticators cannot hold resident (discoverable) credentials.

|transport
|`BLE`, `INTERNAL`, `NFC` or `USB`, the transport the authenticator pretends to use.

|hasResidentKey
|Whether the authenticator supports resident (discoverable) credentials.

|hasUserVerification
|Whether it supports user verification such as a PIN or biometric.

|isUserConsenting
|Whether it simulates the user consenting to the operation.

|isUserVerified
|Whether user verification succeeds or fails; flip it with `setUserVerified` on the authenticator to test the failure path.
|===

The authenticator exposes these methods: `addCredential` and `addResidentCredential` forms (`Credential.createResidentCredential` and `createNonResidentCredential`
build credentials from an id, relying-party id, a PKCS#8-encoded private key, a user handle for resident ones and a signature counter), `getCredentials`,
`removeCredential(id)`, `removeAllCredentials`, `setUserVerified(boolean)`, and finally removing the authenticator itself. The test registers a passkey on
Bookshelf's origin (`localhost` counts as a secure context, so WebAuthn is available), reads the credential back from the authenticator, removes
it, adds it again, and uses it to authenticate:

[source,java]
----
@Test
void virtualAuthenticator() {
  driver.get(BASE_URL + "/");   // localhost is a secure context, so WebAuthn is available
  VirtualAuthenticatorOptions options = new VirtualAuthenticatorOptions()
      .setProtocol(VirtualAuthenticatorOptions.Protocol.CTAP2)
      .setHasResidentKey(true)
      .setHasUserVerification(true)
      .setIsUserVerified(true);
  VirtualAuthenticator authenticator = ((HasVirtualAuthenticator) driver).addVirtualAuthenticator(options);
  Object result = ((JavascriptExecutor) driver).executeAsyncScript("""
      const done = arguments[arguments.length - 1];
      navigator.credentials.create({publicKey: {
        rp: {name: 'Bookshelf'}, user: {id: new Uint8Array([1]), name: 'reader', displayName: 'Reader'},
        challenge: new Uint8Array([1, 2, 3]), pubKeyCredParams: [{type: 'public-key', alg: -7}],
        authenticatorSelection: {residentKey: 'required', userVerification: 'required'}}})
        .then(c => done(c.id), e => done('error: ' + e.name));""");
  assertFalse(result.toString().startsWith("error"));
  List<Credential> credentials = authenticator.getCredentials();
  assertEquals(1, credentials.size());
  assertTrue(credentials.get(0).isResidentCredential());
  Credential stored = credentials.get(0);
  authenticator.removeAllCredentials();
  assertTrue(authenticator.getCredentials().isEmpty());
  authenticator.addCredential(stored);   // a Credential read from the authenticator can be added back
  Object login = ((JavascriptExecutor) driver).executeAsyncScript("""
      const done = arguments[arguments.length - 1];
      navigator.credentials.get({publicKey: {challenge: new Uint8Array([4, 5, 6]), userVerification: 'required'}})
        .then(c => done('ok'), e => done('error: ' + e.name));""");
  assertEquals("ok", login);
  authenticator.setUserVerified(false);   // simulate a failed biometric check
  ((HasVirtualAuthenticator) driver).removeVirtualAuthenticator(authenticator);
}
----

Source: https://www.selenium.dev/documentation/webdriver/interactions/virtual_authenticator/[Selenium: Virtual authenticator]

[source,python]
----
from selenium.webdriver.common.virtual_authenticator import Credential, VirtualAuthenticatorOptions

def test_virtual_authenticator(driver, base_url):
    driver.get(f"{base_url}/")   # localhost is a secure context, so WebAuthn is available
    options = VirtualAuthenticatorOptions()
    options.protocol = VirtualAuthenticatorOptions.Protocol.CTAP2
    options.has_resident_key = True
    options.has_user_verification = True
    options.is_user_verified = True
    driver.add_virtual_authenticator(options)
    result = driver.execute_async_script("""
      const done = arguments[arguments.length - 1];
      navigator.credentials.create({publicKey: {
        rp: {name: 'Bookshelf'}, user: {id: new Uint8Array([1]), name: 'reader', displayName: 'Reader'},
        challenge: new Uint8Array([1, 2, 3]), pubKeyCredParams: [{type: 'public-key', alg: -7}],
        authenticatorSelection: {residentKey: 'required', userVerification: 'required'}}})
        .then(c => done(c.id), e => done('error: ' + e.name));""")
    assert not result.startswith("error")
    credentials = driver.get_credentials()
    assert len(credentials) == 1 and credentials[0].is_resident_credential
    stored = credentials[0]
    driver.remove_all_credentials()
    assert driver.get_credentials() == []
    driver.add_credential(stored)   # a Credential read from the authenticator can be added back
    assert driver.get_credentials()[0].id == stored.id
    login = driver.execute_async_script("""
      const done = arguments[arguments.length - 1];
      navigator.credentials.get({publicKey: {challenge: new Uint8Array([4, 5, 6]), userVerification: 'required'}})
        .then(c => done('ok'), e => done('error: ' + e.name));""")
    assert login == "ok"
    assert driver.get_credentials()[0].sign_count >= 1   # the authenticator signed the assertion
    driver.remove_virtual_authenticator()
----

Source: https://www.selenium.dev/documentation/webdriver/interactions/virtual_authenticator/[Selenium: Virtual authenticator]

In Python the authenticator is attached to the driver itself (`add_virtual_authenticator`, `get_credentials`, `add_credential`,
`remove_credential`, `remove_all_credentials`, `set_user_verified`, `remove_virtual_authenticator`), while in Java the object returned by
`addVirtualAuthenticator` carries the credential methods. Bookshelf has no passkey sign-in, so the tests call the browser's WebAuthn API from the
page, which is exactly what a real site's JavaScript would do. The Selenium documentation also shows PKCS#8 RSA and EC private keys embedded
in the tests to build credentials from scratch; reading one back from the authenticator, as above, avoids committing key material to a repository.

== Pitfalls checklist

* *Stale elements.* Any action that rebuilds the DOM invalidates references; re-find after navigation, filters, tab switches and Single Page Application re-renders.
* *Click intercepted.* An overlay is covering the target; wait for it, do not click through with JavaScript.
* *Implicit waits and `findElements`.* A list lookup that should be empty can burn the whole implicit wait; see
xref:web/e2e-testing/selenium/waits-and-expected-conditions.adoc[Waits & Expected Conditions].
* *Frame state.* After `+switchTo().frame(...)+` every lookup runs inside it until you leave; reset with `defaultContent()` in teardown.
* *Window state.* After `close()` switch back; an unclosed extra window leaks into later tests unless `quit()` runs.
* *Prompt state.* A popup you did not handle makes the next command fail; handle it or choose an unhandled-prompt behaviour.
* *Action state.* Pressed keys and pointer position persist for the session; call `resetInputState()` / `reset_actions()` if a test may leave them dirty.
* *Colour and CSS strings.* Normalise through `Color` before comparing, and never compare computed font or colour strings across browsers.
* *Headless differences.* Headless Chrome (`--headless=new`) shares the real Chrome engine, so locators and interactions behave the same as headed
mode, but window size, fonts and popup behaviour can differ; print-to-PDF and some viewport-dependent relative locators are the likeliest to change.
* *Parallel tests.* Give each test its own driver; a `WebDriver` instance is not thread-safe, and the `ThreadGuard` wrapper (see
xref:web/e2e-testing/selenium/waits-and-expected-conditions.adoc[Waits & Expected Conditions]) makes misuse fail loudly.

== What changed recently

* *Selenium 4.51 (9 October 2026):* the Java client bindings dropped the Guava dependency, so `ExpectedCondition` no longer implements Guava's
`Function`; `+until(d -> ...)+` lambdas still work. The release also updates the CDP versions (v153 to v155) and adds the BiDi code generator.
* *Selenium 4.50:* relative locators can start from an element or a shadow root (the Java example above), and the removed deprecated HTTP client methods may affect custom
client factories.
* *October 2026 documentation:* runnable shadow DOM finder examples for all bindings (8 October) and tested C# and Kotlin alert examples (20 October). The
alert page notes that recent drivers dismiss `beforeunload` prompts automatically.
* *Selenium 4.5:* creating a `Select` for a disabled `select` element throws.
* *Selenium 4.2:* the wheel input and its scroll actions arrived in the Actions API.
* *Selenium 4.0 and the 4.x line:* the W3C-only protocol, `getDomAttribute` / `getDomProperty`, `switchTo().newWindow`, the print command and the virtual authenticator replaced or
extended Selenium 3 behaviour; Selenium 3 style capability objects and the JSON Wire Protocol commands are legacy (see
xref:web/e2e-testing/selenium/selenium-ide-and-legacy.adoc[Selenium IDE & Legacy]).
