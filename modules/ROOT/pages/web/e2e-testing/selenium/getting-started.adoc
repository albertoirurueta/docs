Selenium automates browsers through the W3C WebDriver protocol: your test code (the *language binding*) talks to a small *driver*
program such as `chromedriver`, and the driver controls the browser. This page takes you from nothing to a running suite: it installs
the library in each supported language, walks through the eight components that every Selenium script is made of, shows how to run
the script headless or headed, organises it with a test runner, and explains Selenium Manager, the tool that finds, downloads and
caches the drivers and browsers for you. It was written against Selenium 4.51.0 (released 9 October 2026) and checked on 25 October
2026. The Java, Python, JavaScript and C# examples were run against the xref:web/e2e-testing/example-application-and-test-layout.adoc[Bookshelf]
application on a local port with headless Chrome 155 on macOS (arm64); the Ruby examples were run on Linux arm64 in a Docker
container with Ruby 3.3.13 and the Debian build of Chromium 156 against the same application, because the macOS host ships Ruby 2.6,
which Selenium 4.51 no longer supports. Where something was not run, the text says so. For why WebDriver is built the way it is, see
xref:web/e2e-testing/how-browser-automation-works.adoc[How Browser Automation Works]; for the other tools see
xref:web/e2e-testing/choosing-a-tool.adoc[Choosing a Tool]. Later Selenium pages cover
xref:web/e2e-testing/selenium/drivers-browsers-and-options.adoc[drivers, browsers and options],

== What you need before the first script

Selenium setup differs from most commercial tools because three separate pieces have to fit together:

[cols="1,3",options="header"]
|===
|Piece |What it is

|Language binding
|The library you add to your project (`selenium-java`, `selenium`, `Selenium.WebDriver`, `selenium-webdriver`, the `selenium-webdriver` gem). It
contains the `WebDriver` API, the `By` locators, the browser Options classes and the code that speaks the protocol.

|Driver
|A program per browser that implements the WebDriver protocol for it: `chromedriver`, `geckodriver` (Firefox), `msedgedriver`,
`safaridriver` (shipped with macOS) and `IEDriverServer`. The driver is maintained by the browser vendor where possible; the Selenium
project maintains the Internet Explorer driver.

|Browser
|The real Chrome, Edge, Firefox or Safari that is driven. It must be compatible with the driver version, because browsers update
themselves and a driver only supports a narrow range of browser versions.
|===

Before Selenium 4.6 you downloaded the driver by hand and put it on the `PATH`. When Chrome silently updated, the script broke with
`session not created: This version of ChromeDriver only supports Chrome version 113`. Since Selenium 4.6 every binding ships
*Selenium Manager*, and since 4.11 it can also fetch the browser, so for the common case the only thing you install is the binding.
Selenium Manager is explained in detail <<Selenium Manager,below>>. Low-code recording is a separate product, covered in
xref:web/e2e-testing/selenium/selenium-ide-and-legacy.adoc[Selenium IDE & Legacy], and running browsers on other machines is covered in
xref:web/e2e-testing/selenium/selenium-grid.adoc[Selenium Grid].

Source: https://www.selenium.dev/documentation/webdriver/getting_started/[Selenium -- Getting started]

== Your first script: the eight basic components

Everything Selenium does is either a command to the browser or a request for information. Almost every script is a combination of eight
building blocks:

[cols="1,2,3",options="header"]
|===
|# |Component |What it does

|1
|Start the session
|Creates a driver object. This launches the driver process and the browser, and it is where Selenium Manager runs. The Options
object chooses the browser, the headless mode and other settings.

|2
|Take action on the browser
|Navigates to a page. The call returns once the page has loaded (see the page load strategy on the
xref:web/e2e-testing/selenium/drivers-browsers-and-options.adoc[options page]).

|3
|Request browser information
|Title, URL, window handles, window size and position, cookies, alerts and so on.

|4
|Establish a waiting strategy
|Make sure the element exists and is interactable before you use it. This is the hardest part of Selenium to get right.

|5
|Find an element
|Locate it with a `By` locator (or the equivalent in your language). Most commands in a session are about elements.

|6
|Take action on an element
|Click, type, clear, submit. There are only a handful of element actions.

|7
|Request element information
|Text, attributes, state (displayed, enabled, selected), size and CSS values.

|8
|End the session
|Quits the driver process and, by default, closes the browser. No more commands can be sent to that driver object.
|===

The same components in each binding (the official examples show them one by one):

[cols="2,2,2,2,2,2",options="header"]

=== Java

The script below tests the Bookshelf catalogue: it opens the catalogue, searches for "quiet" and reads the result count. The numbers in
the comments are the eight components. The locators use the `data-testid` attributes that
xref:web/e2e-testing/example-application-and-test-layout.adoc[Bookshelf] defines, and the browser is started headless so the example
also runs on a server with no display.

[source,java]
----
package demo;

import java.time.Duration;
import org.openqa.selenium.By;
import org.openqa.selenium.WebDriver;
import org.openqa.selenium.WebElement;
import org.openqa.selenium.chrome.ChromeDriver;
import org.openqa.selenium.chrome.ChromeOptions;
import org.openqa.selenium.support.ui.ExpectedConditions;
import org.openqa.selenium.support.ui.WebDriverWait;

public class FirstScript {
  public static void main(String[] args) {
    String baseUrl = System.getenv().getOrDefault("BASE_URL", "http://localhost:3000");

    // 1. Start the session (Selenium Manager finds or downloads chromedriver)
    ChromeOptions options = new ChromeOptions();
    options.addArguments("--headless=new");
    WebDriver driver = new ChromeDriver(options);

    try {
      // 2. Take action on the browser
      driver.get(baseUrl + "/books");

      // 3. Request browser information
      String title = driver.getTitle();
      System.out.println("title = " + title);

      // 4. Establish a waiting strategy: an explicit wait of at most five seconds
      WebDriverWait wait = new WebDriverWait(driver, Duration.ofSeconds(5));

      // 5. Find elements
      WebElement searchBox = driver.findElement(By.cssSelector("[data-testid=search-input]"));
      WebElement submitButton = driver.findElement(By.cssSelector("[data-testid=search-submit]"));

      // 6. Take action on the elements
      searchBox.sendKeys("quiet");
      submitButton.click();

      // 7. Request element information
      By resultCount = By.cssSelector("[data-testid=result-count]");
      wait.until(ExpectedConditions.textToBePresentInElementLocated(resultCount, "1 book found"));
      System.out.println("result count = " + driver.findElement(resultCount).getText());
    } finally {
      // 8. End the session
      driver.quit();
    }
  }
}
----

Source: https://www.selenium.dev/documentation/webdriver/getting_started/first_script/[Selenium -- Write your first Selenium script]

The output, with Bookshelf listening on port 3911 (the class reads the address from the `BASE_URL` environment variable):

[source,text]
----
title = Catalogue - Bookshelf
result count = 1 book found
----

Source: https://www.selenium.dev/documentation/webdriver/getting_started/first_script/[Selenium -- Write your first Selenium script]

The `try` and `finally` pair is not decoration. If an exception skips `driver.quit()`, the driver process and the browser keep running;
on a CI machine such orphans pile up and eventually exhaust memory. A test runner's teardown hook does the same job (see
<<Test runners>>).

=== Python

The Python script is the same eight components. `find_element` takes the strategy and the value as two arguments, and the explicit
wait comes from `selenium.webdriver.support`.

[source,python]
----
import os

from selenium import webdriver
from selenium.webdriver.common.by import By
from selenium.webdriver.support import expected_conditions as EC
from selenium.webdriver.support.ui import WebDriverWait

base_url = os.environ.get("BASE_URL", "http://localhost:3000")

# 1. Start the session (Selenium Manager finds or downloads chromedriver)
options = webdriver.ChromeOptions()
options.add_argument("--headless=new")
driver = webdriver.Chrome(options=options)

try:
    # 2. Take action on the browser
    driver.get(f"{base_url}/books")

    # 3. Request browser information
    title = driver.title
    print("title =", title)

    # 4. Establish a waiting strategy: an explicit wait of at most five seconds
    wait = WebDriverWait(driver, 5)

    # 5. Find elements
    search_box = driver.find_element(By.CSS_SELECTOR, "[data-testid=search-input]")
    submit_button = driver.find_element(By.CSS_SELECTOR, "[data-testid=search-submit]")

    # 6. Take action on the elements
    search_box.send_keys("quiet")
    submit_button.click()

    # 7. Request element information
    result_count = (By.CSS_SELECTOR, "[data-testid=result-count]")
    wait.until(EC.text_to_be_present_in_element(result_count, "1 book found"))
    print("result count =", driver.find_element(*result_count).text)
finally:
    # 8. End the session
    driver.quit()
----

=== Ruby

The Ruby script is run with `ruby spec/first_script.rb`. It ran in the Linux container described in the introduction, where Selenium
Manager found the `chromedriver` that the Debian `chromium-driver` package installs on the `PATH` and used it.

[source,ruby]
----
require 'selenium-webdriver'

base_url = ENV.fetch('BASE_URL', 'http://localhost:3000')

# 1. Start the session (Selenium Manager finds or downloads chromedriver)
options = Selenium::WebDriver::Chrome::Options.new
options.add_argument('--headless=new')
driver = Selenium::WebDriver.for :chrome, options: options

begin
  # 2. Take action on the browser
  driver.get("#{base_url}/books")

  # 3. Request browser information
  puts "title = #{driver.title}"

  # 4. Establish a waiting strategy: an explicit wait of at most five seconds
  wait = Selenium::WebDriver::Wait.new(
    timeout: 5,
    ignore: [Selenium::WebDriver::Error::NoSuchElementError,
             Selenium::WebDriver::Error::StaleElementReferenceError]
  )

  # 5. Find elements
  search_box = driver.find_element(css: '[data-testid=search-input]')
  submit_button = driver.find_element(css: '[data-testid=search-submit]')

  # 6. Take action on the elements
  search_box.send_keys('quiet')
  submit_button.click

  # 7. Request element information
  wait.until { driver.find_element(css: '[data-testid=result-count]').text == '1 book found' }
  puts "result count = #{driver.find_element(css: '[data-testid=result-count]').text}"
ensure
  # 8. End the session
  driver.quit
end
----

Source: https://www.selenium.dev/documentation/webdriver/getting_started/first_script/[Selenium -- Write your first Selenium script]

The `ignore:` list replaces Ruby's default, which is only `NoSuchElementError`, so it names both errors that can occur while the old
page is being replaced by the new one. The next section explains why that matters.

=== Why the example waits for the text

The official first script sets an implicit wait of 500 ms in component 4 and reads the element right after the click. That works against
the static demo page the official documentation uses, but not against a page that is replaced after a click, as Bookshelf's search form
does (it is a plain `GET` form). `click()` returns as soon as the click has been dispatched, and the old page is still in the browser for
a moment. Looking for `result-count` then finds the element of the *old* page. Running the official shape of the script against Bookshelf
(implicit wait of 0.5 s, no explicit wait) gave, in four consecutive Python runs:

[source,text]
----
result count = 24 books found
result count = 24 books found
selenium.common.exceptions.WebDriverException: Message: unknown error: unhandled inspector error: {"code":-32000,"message":"Node with given id does not belong to the document"}
result count = 24 books found
----

Source: https://www.selenium.dev/documentation/webdriver/waits/[Selenium -- Waits]

and the Java version printed `1 book found` in two of four runs and the stale `24 books found` in the other two. The JavaScript
version of the same pattern failed with `StaleElementReferenceError`, and the Ruby spec with the default wait failed intermittently for
the same reason. The fix is always the same: after an action that changes the page, wait for the *state* you expect (here, the text
`1 book found`), not for the element to exist. The scripts above do that with an explicit wait, and the Ruby and JavaScript versions
also treat a stale element as "not yet". Implicit and explicit waits are covered, with the rule against mixing them, in
xref:web/e2e-testing/selenium/waits-and-expected-conditions.adoc[Waits & Expected Conditions].

=== Headless and headed

Selenium starts a visible browser window by default. That is what you want while writing and debugging a script, and it needs a
desktop session. In CI, on servers and in containers there is no display, so you ask the browser to run without a window:

[cols="1,2,2",options="header"]
|===
|Browser |Option |Notes

|Chrome
|`options.addArguments("--headless=new")`
|`--headless=new` is the argument used on this page, and the Selenium Chrome page lists it among the commonly used arguments. It runs the full browser engine without a window.

|Edge
|`options.addArguments("--headless=new")` on `EdgeOptions`
|Same as Chrome; Edge is Chromium-based.

|Firefox
|`options.addArguments("-headless")` on `FirefoxOptions`
|A single dash. Firefox has no `new` variant.

|Safari
|Not available
|`safaridriver` drives the visible Safari application only.
|===

Every example on this page that creates a browser passes `--headless=new` through the Options class, and nothing changes in the rest of
the script. A headed run is the same code without that line. The headless runs on this page are real; a headed run opens a window on
the desktop, which was not exercised for this page. In headless mode the window size is not the one of your screen, so set it
explicitly (for example `--window-size=1280,800`) when a layout depends on it. The per-browser options, including `Service`, `Options`
and remote sessions, are the subject of
xref:web/e2e-testing/selenium/drivers-browsers-and-options.adoc[Drivers, Browsers & Options].

Source: https://www.selenium.dev/documentation/webdriver/browsers/chrome/[Selenium -- Chrome]

=== Browsers that need more than a binding

Chrome, Edge and Firefox are started the same way and Selenium Manager supplies the drivers. Two exceptions need action from you:

* *Safari.* `safaridriver` ships with macOS, but you must run `safaridriver --enable` once (it asks for an administrator password), or switch on "Allow remote automation" in the Developer section of the Safari settings. Without it, `webdriver.Safari()` fails with a message that tells you to enable that setting. This is a
  system setting, so it was not changed on the host used for this page and no Safari example was run.
* *Firefox on this host.* Local Firefox did not start on the macOS 27 host used for this page (the geckodriver session timed out), so
  Firefox runs in the Selenium Docker images. The Docker images are covered in
  xref:web/e2e-testing/selenium/selenium-grid.adoc[Selenium Grid].

== Test runners

A script is a program. To run tens or hundreds of checks, you put the same calls into tests managed by a *test runner*, which gives
you set-up and tear-down hooks, assertions, grouping, reports and parallel execution. Selenium itself ships no test framework; it works
with the standard runner of each language. The official documentation recommends these (the first in each list is the one its own
examples use):

[cols="1,3",options="header"]
|===
|Language |Runners

|Java
|JUnit 5 (this page), TestNG (adds parallel execution and parameterised tests of its own)

|Python
|pytest (this page), `unittest` from the standard library

|C#
|NUnit, MSTest (both below)

|Ruby
|RSpec (this page), Minitest

|JavaScript
|Mocha (this page), Jest

|Kotlin
|Kotest, JUnit 5
|===

Source: https://www.selenium.dev/documentation/webdriver/getting_started/using_selenium/[Selenium -- Organizing and executing Selenium code]

Whatever the runner, the same four rules apply, and the examples below follow them:

. *Start the driver in the set-up hook and quit it in the tear-down hook*, so a failing assertion cannot leak a browser. A fresh
  browser per test is the safest default; share a browser only when start-up time is a measured problem, and then reset cookies and
  storage between tests.
. *Assert with the runner's assertion library.* Selenium has no assertions of its own.
. *Take the base URL from configuration*, here the `BASE_URL` environment variable, so the same tests run against a local server,
  a container or a staging host.
. *Never share a `WebDriver` between threads.* A driver instance is not thread safe; give each parallel test its own (the Java
  `ThreadGuard` class exists to catch mistakes).

Selenium also fits non-test jobs: repetitive browser tasks that run on a schedule, and scraping of sites that do not offer an API
(check the site's terms of service first, because some forbid it and some block Selenium).

=== MSTest and NUnit (C#)

=== Mocha (JavaScript)

Mocha provides `describe`, `it`, `before` and `after`. Because Selenium's JavaScript API returns promises, the hooks and tests are
`async` functions.

[source,javascript]
----
const { Builder, By, Browser, error } = require('selenium-webdriver');
const chrome = require('selenium-webdriver/chrome');
const assert = require('assert');

const baseUrl = process.env.BASE_URL || 'http://localhost:3000';

describe('Bookshelf search', function () {
  let driver;

  before(async function () {
    const options = new chrome.Options().addArguments('--headless=new');
    driver = await new Builder().forBrowser(Browser.CHROME).setChromeOptions(options).build();
  });

  it('finds The Quiet Compiler', async function () {
    await driver.get(`${baseUrl}/books`);
    assert.equal(await driver.getTitle(), 'Catalogue - Bookshelf');

    await driver.findElement(By.css('[data-testid=search-input]')).sendKeys('quiet');
    await driver.findElement(By.css('[data-testid=search-submit]')).click();

    // Poll until the results page shows the new count. The old page can still
    // answer for a moment, so a stale element simply means "try again".
    await driver.wait(async () => {
      try {
        const count = await driver.findElement(By.css('[data-testid=result-count]'));
        return (await count.getText()) === '1 book found';
      } catch (e) {
        if (e instanceof error.StaleElementReferenceError) return false;
        throw e;
      }
    }, 5000);
  });

  after(async () => await driver.quit());
});

== Selenium Manager

Selenium Manager is the official driver manager of the Selenium project. It is a command line tool written in Rust, compiled for
Windows, Linux and macOS, and shipped inside every binding. It replaced the practice of downloading `chromedriver` yourself, and the
third-party managers (WebDriverManager for Java, `webdriver-manager` for Python and JavaScript, WebDriverManager.Net, `webdrivers` for Ruby),
which inspired it. Its version follows Selenium's with a leading `0`, so 4.51.0 ships Selenium Manager 0.4.51.

=== When it runs

The bindings call Selenium Manager only as a fallback, at the moment your script creates a driver object (`new ChromeDriver()`,
`webdriver.Chrome()`, and so on). If you provide a driver yourself, Selenium Manager is not used for it. The precedence is:

[mermaid]
....
flowchart TD
    A["Script creates a driver object"] --> B{"Driver location given by a Service, a SE_*DRIVER variable or the PATH?"}
    B -- yes --> C["Use that driver, no download"]
    B -- no --> D["Selenium Manager runs"]
    D --> E["1. Detect the installed browser and its version"]
    E --> F["2. Resolve the matching driver version from the vendor metadata"]
    F --> G{"Driver in the cache?"}
    G -- yes --> H["Use the cached driver"]
    G -- no --> I["3. Download and unpack it into the cache"]
    I --> H
    D --> J{"Browser not installed, or a version or channel requested?"}
    J -- yes --> K["Download the browser into the cache too"]
    J -- no --> L["Use the installed browser"]
    H --> M["Binding starts the driver, the driver starts the browser"]
    K --> M
    L --> M
....

Source: https://www.selenium.dev/documentation/selenium_manager/[Selenium -- Selenium Manager]

Using it needs no code at all. In older Selenium the same session needed a system property pointing at a driver you had downloaded:

[source,java]
----
// Before Selenium Manager: a driver downloaded by hand
System.setProperty("webdriver.chrome.driver", "/path/to/chromedriver");
WebDriver driver = new ChromeDriver();

// With Selenium Manager: nothing to set
WebDriver driver = new ChromeDriver();
----

Source: https://www.selenium.dev/documentation/selenium_manager/#using-selenium-manager-from-the-bindings[Selenium -- Selenium Manager: using it from the bindings]

This snippet only shows the difference and was not run on its own, but the Selenium Manager form is what every example on this page uses.

=== Automated driver management

The process has four steps, which the manager calls *management* rather than download because there is more to it:

. *Browser discovery.* It finds the installed browser and runs `--version` on it.
. *Driver version discovery.* It maps the browser version to a driver version using the metadata the browser vendors publish: Chrome for
  Testing (CfT) JSON endpoints for Chrome, the geckodriver releases for Firefox, Microsoft's endpoints for Edge.
. *Driver download.* It downloads and unpacks the driver from the resolved URL.
. *Driver cache.* It stores the unpacked driver under `+~/.cache/selenium+` and reuses it next time.

You can watch these steps by running the Selenium Manager binary directly. A copy is extracted to the cache by the Java binding (here
`+~/.cache/selenium/manager/4.51.0/selenium-manager+`) and the Python wheel contains one in
`selenium/webdriver/common/macos/`. With a new empty cache and `--debug`:

[source,bash]
----
selenium-manager --browser chrome --cache-path ./cache --debug
----

=== The cache

Everything Selenium Manager downloads lives in one folder, `+~/.cache/selenium+` by default (on Windows, the same path under the user
profile). After the runs above the folder looked like this:

[source,text]
----
cache/
  chromedriver/mac-arm64/155.0.8059.84/chromedriver
  chromedriver/mac-arm64/156.0.8078.47/chromedriver
  chrome/mac-arm64/156.0.8078.47/Google Chrome for Testing.app/...
  se-metadata.json
----

Source: https://www.selenium.dev/documentation/selenium_manager/#caching[Selenium -- Selenium Manager: caching]

Two files live at the root of the cache next to the downloaded assets:

* `se-config.toml`: optional, written by you, read by Selenium Manager (see the next section).
* `se-metadata.json`: written and maintained by Selenium Manager. It remembers the versions it discovered over the network, so a test
  suite that creates hundreds of drivers does not query the CfT endpoints hundreds of times. In the observed file the entries are
  `browsers`, `drivers`, `stats` and `cached_assets`, each driver entry with the browser major version, the driver version and an
  expiry timestamp (`driver_ttl`).

The *TTL* (time to live) is how long a discovered version stays valid. It defaults to 3600 seconds (one hour), is set with `--ttl` or
`SE_TTL`, and `0` disables the metadata cache. Within the TTL the version is read from the file; afterwards it is stale and Selenium
Manager asks the network again. A driver already unpacked in the cache is reused even then; the TTL only governs the *lookup*.

To keep the cache from growing for ever, Selenium Manager records a `last_used` timestamp each time it resolves an asset from the cache
and removes driver or browser version folders that have not been used for 30 days (pruning was added in Selenium Manager 0.4.45). `--clear-cache` (`SE_CLEAR_CACHE=true`) deletes the whole folder and `--clear-metadata`
(`SE_CLEAR_METADATA=true`) deletes only the metadata file.

In CI, restore the cache folder between runs, so jobs do not download the driver every time:

[source,yaml]
----
- uses: actions/cache@v6
  with:
    path: ~/.cache/selenium
    key: selenium-${{ runner.os }}-${{ hashFiles('**/pom.xml') }}
----

Source: https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching[GitHub Actions -- Dependency caching]

This workflow snippet was not run. Its key is only a suggestion: any stable key works, and a cache hit does not stop Selenium Manager
from refreshing a stale version. The CI pages of this section continue from here (see
xref:web/e2e-testing/running-in-ci-cd.adoc[Running in CI/CD]).

=== Configuration: flags, se-config.toml and environment variables

Selenium Manager takes its settings from three places. The documented order, which was confirmed by running it, is:

. *Command line arguments.* The bindings pass the options of your session this way.
. *The configuration file* `se-config.toml` in the cache folder.
. *Environment variables.* Each key becomes an environment variable by upper-casing it, replacing `-` with `+_+` and adding the prefix `+SE_+`
  (`cache-path` becomes `SE_CACHE_PATH`).

A file entry wins over an environment variable, and a flag wins over both. With `browser = "chrome"` in `se-config.toml`:

[source,bash]
----
SE_CACHE_PATH=./cache selenium-manager                          # the file chooses chrome
SE_CACHE_PATH=./cache SE_BROWSER=edge selenium-manager          # still chrome: the file beats the variable
SE_CACHE_PATH=./cache selenium-manager --browser edge           # edge: the flag beats the file
----

Source: https://www.selenium.dev/documentation/selenium_manager/#configuration[Selenium -- Selenium Manager: configuration]

The first two commands printed the cached chromedriver and the installed Chrome. The third downloaded Edge for Testing 156.0.4314.42 and
its `msedgedriver`. Without `SE_CACHE_PATH`, Selenium Manager looked for `se-config.toml` in `+~/.cache/selenium+` and printed
`You need to specify a browser or driver`, so the file belongs in whichever cache folder is in effect. All keys:

[cols="3,3,3,4",options="header"]

The table lists every key the official page documents. The 0.4.51 binary has several more flags: `--grid [version]`,
`--log-level`, `--license`, `--init-skills [file]` and `--init-rules [file]`, and `electron` is accepted as a browser name. `--init-skills` and `--init-rules` write a guidance file with Selenium best practices for AI coding assistants into
the current folder (`skills/skills.md` of 122 lines and `rules/selenium.md` of 475 lines when run on this host); they have no environment
variable listed in the documentation. They are covered with the other AI helpers in
xref:web/e2e-testing/ai-agents/ai-features-in-cypress-and-selenium.adoc[AI Features in Cypress & Selenium].

Per-browser variants of the keys exist as well: `chrome-version`, `firefox-version`, `edge-version` (and `SE_CHROME_VERSION` and so on),
`chromedriver-version`, `geckodriver-version`, `msedgedriver-version`, `chrome-path`, `firefox-path`, `edge-path`,
`chromedriver-mirror-url`, `chrome-mirror-url` and the matching names for Firefox and Edge. They let one file or one environment
configure several browsers at once.

A complete `se-config.toml`, as in the official page, shows the value of every key (do not use all of them together; for instance
`offline = true` with `cache-path` pointing at an empty folder leaves nothing to download):

[source,toml]
----
browser = "chrome"                 # --browser BROWSER
driver = "chromedriver"            # --driver DRIVER
browser-version = "106"            # --browser-version BROWSER_VERSION
driver-version = "106.0.5249.61"   # --driver-version DRIVER_VERSION
browser-path = "/usr/bin/google-chrome"  # --browser-path BROWSER_PATH
driver-mirror-url = "https://custom-driver-mirror.com"  # --driver-mirror-url
browser-mirror-url = "https://custom-browser-mirror.com"  # --browser-mirror-url
output = "LOGGER"                  # --output OUTPUT
os = "linux"                       # --os OS
arch = "x64"                       # --arch ARCH
proxy = "myproxy:8080"             # --proxy PROXY
timeout = 300                      # --timeout TIMEOUT
offline = true                     # --offline
force-browser-download = true      # --force-browser-download
avoid-browser-download = false     # --avoid-browser-download
debug = true                       # --debug
trace = true                       # --trace
cache-path = "/custom/cache/path"  # --cache-path CACHE_PATH
ttl = 3600                         # --ttl TTL
language-binding = "Python"        # --language-binding LANGUAGE
avoid-stats = true                 # --avoid-stats
----

Source: https://www.selenium.dev/documentation/selenium_manager/#se-configtoml-example[Selenium -- Selenium Manager: se-config.toml example]

Two differences from the documentation showed up in the 0.4.51 binary. First, with `debug = true` in `se-config.toml` no DEBUG lines were
printed, while `--debug` and `SE_DEBUG=true` did print them (a small file with `browser`, `avoid-stats` and `offline` keys behaved as
documented). Second, a boolean written as a string (`offline = "true"` or `debug = "true"`) made the binary stop with a Rust panic in
`src/config.rs` instead of an error message. Write booleans without quotes, and prefer a flag or an environment variable for `debug`.

=== What the bindings pass

The bindings do not read `se-config.toml` themselves; they run the Selenium Manager binary as a child process and give it arguments taken
from the session's options:

[cols="2,2",options="header"]
|===
|Session option |Argument

|`browserName`
|`--browser`

|`browserVersion`
|`--browser-version`

|Browser binary location (for example Chrome's `setBinary`)
|`--browser-path`

|`proxy` (HTTP or SSL)
|`--proxy`
|===

Source: https://www.selenium.dev/documentation/selenium_manager/#configuration-from-the-selenium-bindings[Selenium -- Selenium Manager: configuration from the Selenium bindings]

Anything else, such as `cache-path`, `ttl`, `offline` or the mirrors, cannot be set from the browser options; set it in the process
environment (the child process inherits it) or in `se-config.toml`. To see exactly what a binding sends, point `SE_MANAGER_PATH` at a
wrapper script that records its arguments and then runs the real binary:

[source,bash]
----
#!/bin/sh
echo "$@" >> sm-args.log
exec "$HOME/.cache/selenium/manager/4.51.0/selenium-manager" "$@"
----

Source: https://www.selenium.dev/documentation/selenium_manager/#building-a-custom-selenium-manager[Selenium -- Selenium Manager: building a custom Selenium Manager]

After `SE_MANAGER_PATH=$PWD/sm-wrapper.sh SE_DEBUG=true python first_script.py` and the Java first script, the log held:

[source,text]
----
--browser chrome --debug --language-binding python --output json
--browser chrome --language-binding java --output json
----

Source: https://www.selenium.dev/documentation/selenium_manager/#building-a-custom-selenium-manager[Selenium -- Selenium Manager: building a custom Selenium Manager]

So `SE_DEBUG` is turned into `--debug` by the binding, and the language binding is always reported. `SE_MANAGER_PATH` (supported since
Selenium 4.13.0) is the supported way to run your own build of Selenium Manager; see <<Building a custom Selenium Manager>>. In Python
the logging module shows the same lines: with `logging.basicConfig(level=logging.DEBUG)` the logger
`selenium.webdriver.common.selenium_manager` prints each line of the debug output shown earlier.

=== Offline mode

`--offline` or `SE_OFFLINE=true` disables every network request and download. Selenium Manager then can only reuse what is in the
cache. With a populated cache it behaves normally. With an empty one it warns and returns no driver:

[source,bash]
----
SE_CACHE_PATH=./empty SE_OFFLINE=true SE_AVOID_STATS=true selenium-manager --browser chrome --output json
----

Source: https://www.selenium.dev/documentation/selenium_manager/#configuration[Selenium -- Selenium Manager: configuration]

[source,json]
----
{
  "logs": [
    { "level": "WARN", "message": "Unable to discover proper chromedriver version in offline mode" },
    { "level": "INFO", "message": "Browser path: /Applications/Google Chrome.app/Contents/MacOS/Google Chrome" }
  ],
  "result": { "code": 0, "message": "", "driver_path": "", "browser_path": "/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" }
}
----

Source: https://www.selenium.dev/documentation/selenium_manager/#configuration[Selenium -- Selenium Manager: configuration]

(The `timestamp` fields and the path layout of the real output are omitted from this JSON; the `code` is `0` even though no driver was
found.) The exit status is 0, so a script cannot rely on it; the binding is what fails, with `NoSuchDriverException` in Python:

[source,text]
----
selenium.common.exceptions.NoSuchDriverException: Message: Unable to obtain driver for chrome; For documentation on this error, please visit: https://www.selenium.dev/documentation/webdriver/troubleshooting/errors/driver_location
----

Source: https://www.selenium.dev/documentation/webdriver/troubleshooting/errors/[Selenium -- Troubleshooting: errors]

Offline CI agents either pre-populate the cache (build it with one online run and ship the folder) or skip Selenium Manager by naming
the drivers, as the next section shows.

=== Skipping Selenium Manager: drivers you provide

Selenium Manager is a fallback, so any of these makes it unnecessary:

* *A `Service` with an explicit path* (`+ChromeDriverService.Builder().usingDriverExecutable(...)+` in Java, `+Service(executable_path=...)+` in
  Python). The Service classes are covered in
  xref:web/e2e-testing/selenium/drivers-browsers-and-options.adoc[Drivers, Browsers & Options].
* *A driver on the `PATH`.* Selenium Manager finds it and uses it (`chromedriver not found in PATH` appears in the debug output above when
  there is none). Add `--skip-driver-in-path` to ignore it.
* *The `SE_CHROMEDRIVER`, `SE_EDGEDRIVER`, `SE_GECKODRIVER` and `SE_IEDRIVER` environment variables*, which hold the path of the driver
  executable. They are supported in the Java, Python (from 4.26.0) and Ruby (from 4.25.0) bindings, but not in the others. With `SE_CHROMEDRIVER`
  set to the cached driver, `SE_OFFLINE=true` and an empty `SE_CACHE_PATH`, the Python first script ran and created nothing in the cache folder.

Source: https://www.selenium.dev/documentation/selenium_manager/#using-an-environment-variable-for-the-driver-path[Selenium -- Selenium Manager: using an environment variable for the driver path]

=== Proxies, mirrors and connectivity

Selenium Manager downloads from public endpoints: `googlechromelabs.github.io` and `storage.googleapis.com` for Chrome and
chromedriver, the geckodriver releases on GitHub, `ftp.mozilla.org`, and the Microsoft Edge endpoints. Behind a corporate proxy or firewall
you may see errors like these:

[source,text]
----
error sending request for url (https://googlechromelabs.github.io/chrome-for-testing/known-good-versions-with-downloads.json)
error trying to connect: dns error: failed to lookup address information
error trying to connect: An existing connection was forcibly closed by the remote host. (os error 10054)
----

Source: https://www.selenium.dev/documentation/selenium_manager/#connectivity-issues[Selenium -- Selenium Manager: connectivity issues]

The first message is what the 0.4.51 binary printed when run with `--proxy 127.0.0.1:9`, a proxy that is not listening. Fixes, in order:

. *Set the proxy for the session* with the Proxy option; the bindings pass it to Selenium Manager (`--proxy`), so the same proxy is used by the
  browser and by the downloads.
. *Use `SE_PROXY` or `+proxy = "..."+` in `se-config.toml`* when Selenium Manager needs a proxy that the browser must not use.
. *Allow the endpoints* in your firewall, or *mirror them* with `driver-mirror-url` and `browser-mirror-url` (or the per-browser variants).
  A mirror must repeat the layout and response format of the original: the Chrome for Testing JSON files for Chrome (the download URLs in
  them can point at your storage), the geckodriver release layout plus a `geckodriver-support.json` file for Firefox, and
  `msedgedriver.microsoft.com` and `edgeupdates.microsoft.com/api/products/` for Edge. Driver and browser mirrors are separate
  because, for Firefox and Edge, they come from different repositories. A mirror cannot point at a source with a different structure,
  such as a Linux distribution's package repository; install the browser and driver yourself in that case. The mirror setting was not
  exercised for this page because it needs a mirror server.

Source: https://www.selenium.dev/documentation/selenium_manager/#using-mirrors[Selenium -- Selenium Manager: using mirrors]

=== Usage statistics and SE_AVOID_STATS

Selenium Manager sends anonymised usage statistics to Plausible once a day (the same TTL mechanism). The data is the Selenium version,
the language binding, the operating system and architecture, the browser and its version, and a rough geolocation derived from the IP
address. It is *on by default*. Opt out with `SE_AVOID_STATS=true`, `--avoid-stats` or `avoid-stats = true` in `se-config.toml`. The
selenium-manager change log also lists support for the `DO_NOT_TRACK` environment variable since 0.4.48; this was not tested.

You can see the effect in `se-metadata.json`: the shared cache used by runs without an opt-out had `stats` entries (browser, OS,
architecture, language binding and Selenium version, each with a `stats_ttl`), and every cache created with `--avoid-stats` had an empty
`"stats": []` array. In an organisation that blocks outbound traffic, set `SE_AVOID_STATS=true` anyway, so no request is attempted.

Source: https://www.selenium.dev/documentation/selenium_manager/#data-collection[Selenium -- Selenium Manager: data collection]

=== Known limitations

* *Architectures.* Each Selenium release ships four Selenium Manager binaries: macOS (Intel and Apple silicon in one), Windows (x86 and
  x64, also used on Windows arm64), Linux x64, and, since Selenium 4.49.0, Linux arm64. On Linux arm64 it can manage Chrome and
  chromedriver from version 153 (the first Chrome for Testing build for that platform) and Firefox from version 136 plus geckodriver;
  Edge is not available there. Other platforms, such as 32-bit Linux on ARM, are not supported because the vendors publish nothing for them. Install
  the browser and driver with the system package manager and set the driver location in a `Service` or in a `+SE_*DRIVER+` variable. This is
  what happened in the Ruby container on this page: the container is Linux arm64 with Chromium 156 and the Debian `chromium-driver` on the `PATH`.
* *Linux libraries.* Browsers that Selenium Manager downloads are portable builds that still need system libraries. If Firefox fails with
  `libdbus-glib-1.so.2: cannot open shared object file`, install it (`sudo apt-get install libdbus-glib-1-2`); if Chrome for Testing
  fails with `libatk-1.0.so.0: cannot open shared object file`, install `libatk-bridge2.0-0`.
* *Custom package managers.* Anaconda or snap installs of browsers need a specific driver; set the driver location, the browser
  location, or both, because Selenium Manager cannot discover those.
* *Grid.* `--selenium-manager true` on a Grid node lets the node use Selenium Manager to find drivers (see
  xref:web/e2e-testing/selenium/selenium-grid.adoc[Selenium Grid]), and `selenium-manager --grid [version]` downloads the Selenium
  Server jar into the cache.

Source: https://www.selenium.dev/documentation/selenium_manager/#known-limitations[Selenium -- Selenium Manager: known limitations]

=== Building a custom Selenium Manager

The bindings use the Selenium Manager binary named in `SE_MANAGER_PATH` when it is set (since Selenium 4.13.0). The documented recipe for a
platform without a shipped binary is: install the Rust toolchain, clone `SeleniumHQ/selenium`, run `cargo build --release` in the `rust`
folder, set `SE_MANAGER_PATH` to `rust/target/release/selenium-manager`, and put the driver you want on the `PATH`. That last step is needed
because a custom build still cannot download what the vendors do not publish. The recipe was not run here; the wrapper script above
shows that `SE_MANAGER_PATH` works with a prebuilt binary. The Selenium Manager binaries can also be taken from the
`SeleniumHQ/selenium_manager_artifacts` repository or from the CI workflow; the Java binding extracts its copy into
`+~/.cache/selenium/manager/<version>+` (since 4.15.0).

Source: https://www.selenium.dev/documentation/selenium_manager/#building-a-custom-selenium-manager[Selenium -- Selenium Manager: building a custom Selenium Manager]

# Terminal 1: the application under test
cd bookshelf && PORT=3911 npm start

# Terminal 2: the tests
BASE_URL=http://localhost:3911 pytest -q
BASE_URL=http://localhost:3911 mvn -B test

== Troubleshooting the first run

[cols="2,3",options="header"]
|===
|Symptom |Likely cause and fix

|`session not created: This version of ChromeDriver only supports Chrome version N`
|A manually installed driver no longer matches the auto-updated browser. Remove the driver from the `PATH` (or pass
`--skip-driver-in-path`) so Selenium Manager resolves a matching one.

|`NoSuchDriverException: Unable to obtain driver for chrome`
|Selenium Manager could not find or download a driver. Run it by hand with `--debug`; check offline mode, the proxy and the firewall.

|`You need to specify a browser or driver` from the binary
|The binary was run without `--browser` or `--driver` and no `se-config.toml` supplied them from the cache in effect.

|`StaleElementReferenceError` after a click
|The page was replaced while you held an element. Wait for the new state and look the element up again.

|The script hangs or Chrome stays after a failure
|`quit()` was skipped. Use `try`/`finally` or the runner's teardown hook.

|Safari: "You must enable Allow remote automation"
|Run `safaridriver --enable` once, or enable remote automation in the Developer section of the Safari settings.

|Linux: `error while loading shared libraries`
|Install the missing library (see <<Known limitations>>).
|===

Source: https://www.selenium.dev/documentation/webdriver/troubleshooting/[Selenium -- Troubleshooting]

More error messages, logging and the listener classes are collected in
xref:web/e2e-testing/selenium/waits-and-expected-conditions.adoc[Waits & Expected Conditions].
