== Selenium IDE

Selenium IDE records what you do in a browser and plays it back. It is the quickest way to see the Selenium command
vocabulary (`open`, `click`, `type`, `assertText`), to produce a throwaway reproduction of a bug, or to let someone who does not
program capture a flow. It is not a replacement for a coded suite, and the project that maintains it has been quiet for a long
time, which matters for the decision of whether to invest in it.

=== What it is today

The official documentation page for the IDE (updated 9 October 2026) describes it as "a standalone application that records
and plays back a user's actions" for Windows, macOS and Linux, downloaded from the GitHub releases page of the
`SeleniumHQ/selenium-ide` repository. The downloads page adds that it can also be installed with `npm install -g selenium-ide`
and that the previous browser extension (version 3) is no longer maintained, is no longer in the Chrome Web Store and can still
be installed for Firefox or Edge. The IDE's own documentation site (last updated in 2019) still tells you to install the IDE
"from either the Chrome or Firefox web store" and to click its icon in the browser toolbar. That text describes the old
extension; follow the downloads page, not the 2019 instructions.

=== Recording, playback and the project structure

The workflow documented in the IDE's Getting Started page is unchanged between the extension and the application:

. Create a project: give it a name and a *base URL*, the address of the application under test, set once for all tests in the
project and overridable later.
. Record: a browser window opens on the base URL and every click and keystroke becomes a command row (command, target,
value). Stop recording from the IDE window.
. Organise: tests are grouped into *suites*; a "Default Suite" is created with the project and holds the first test.
. Save: saving writes the whole project to one `.side` file.
. Play back: select a test or suite and press play; the test runs in the window used for recording, or in a new one.
. Cross-browser: to run on other browsers, on a Grid and in parallel, use the command-line runner (below).

Each command has a *command* (the action, such as `click`), a *target* (usually a locator such as `id=q`, `+css=...+` or
`+xpath=...+`) and a *value* (text to type, an expected string or a variable name). The recorder stores several alternative
locators per step (`targets`) and falls back to them during playback when the primary locator fails. Hand-written steps need
only the primary `target`, which is how the example below was written.

=== Control flow

The IDE adds conditional logic and loops through opening and closing commands, with the condition written as a JavaScript
expression in the *target* field. Variables from `execute script` and `store` commands can be used in the expression.

[cols="2,3",options="header"]
|===
|Commands |Purpose

|`if`, `else if`, `else`, `end`
|Conditional branching. `if` and `else if` evaluate a JavaScript expression; `else` runs when none matched; `end` closes the block (a missing `end` is reported when you run the test).

|`times`, `end`
|Repeat the block a fixed number of times (the number goes in the target field).

|`do`, `repeat if`
|Run the block, then evaluate the expression in `repeat if`; loop while it is true.

|`while`, `end`
|Evaluate first, run the block while the expression is true.

|`forEach`, `end`
|Iterate a JavaScript array held in a variable; the target is the array variable and the value is the name of the loop variable.
|===

`+do ... repeat if+` and `while` carry infinite-loop protection: after 1000 iterations by default the test stops, and a number in
the *value* field of `repeat if` or `while` overrides the limit.

=== The command-line runner: selenium-side-runner

`selenium-side-runner` runs `.side` files outside the IDE, on any browser that has a WebDriver, in parallel and on a Grid, with
Jest underneath. Its documentation asks for Node.js 8 or 10 and global installation of the runner and a driver package; the
published package declares Node.js 16 or later, and the runner depends on `selenium-webdriver` 4.51.0, so Selenium Manager finds
the driver and no `chromedriver` package is needed. The commands below are the ones that were run.

[source,bash]
----
mkdir sel-ide-side && cd sel-ide-side
npm init -y
npm i selenium-side-runner@4.0.13
npx selenium-side-runner --version
----

Source: https://www.selenium.dev/selenium-ide/docs/en/introduction/command-line-runner[Selenium IDE -- Command-line Runner]

Real output of `npx selenium-side-runner --version`:

[source,text]
----
4.0.13
----

Running the project in headless Chrome against Bookshelf, with the capabilities written the way the runner documentation shows
for headless mode:

[source,bash]
----
npx selenium-side-runner -c "browserName=chrome goog:chromeOptions.args=[disable-infobars, headless]" \
  --base-url http://localhost:3917 --output-directory results bookshelf.side

=== Code export

The IDE can export a test or a suite to WebDriver code by right-clicking it, choosing *Export*, selecting a language and
ticking, if wanted, the origin-tracing comments option, which writes a comment in the generated code naming the IDE step that
produced each line. The code export page lists four supported targets: C# NUnit, Java JUnit, JavaScript Mocha and Python
pytest. The same page still contains sections for C# xUnit and Ruby RSpec that its "Supported Exports" list does not name,
and its dependency examples are from the Selenium 4 alpha era (Java 8 with JUnit 4.12 and `4.0.0-alpha-3`, pytest 4.6 with
`selenium == 4.0.0a1`, .NET Core 2.0). The exporter packages exist on npm (for example `@seleniumhq/code-export-python-pytest`
at `4.0.13`, published in November 2024). Code export was not run for this page: the exported files target old library
versions, so treat the output as a starting point that you port to current Selenium (Options classes, `Duration`, no driver
paths), using the rest of this page.

=== When to use it and when not to

Use the IDE to explore locators, show a team what a flow looks like, or capture a bug reproduction. Do not build a regression
suite on it: `.side` files cannot share page objects, the recorder's locators are brittle (`xpath=//div[3]/a`), the last
release is from July 2024 and its documentation describes an extension that no longer exists in the Chrome Web Store. For
suites that last, write code with the bindings and the practices in
xref:web/e2e-testing/test-design-and-page-objects.adoc[Test Design & Page Objects], or use a recorder in another tool
(`playwright codegen`, Cypress Studio; see xref:web/e2e-testing/playwright/debugging-tracing-and-codegen.adoc[Playwright:
Debugging, Tracing & Codegen]).

== Legacy components

The Selenium documentation keeps a *Legacy* section "purely for historical reasons and not as an incentive to use deprecated
components". This section summarises what is in it, what each generation was, and what replaced it.

=== The generations

[cols="1,3,3",options="header"]
|===
|Generation |What it was |What replaced it

|Selenium 1 (Selenium RC)
|A Java server (`+selenium-server-standalone-<version>.jar+`) that launched and killed browsers, acted as an HTTP proxy between the browser and the application and injected the *Selenium Core* JavaScript into the page. Client libraries sent Selenese commands to the server as HTTP GET/POST requests and the injected JavaScript executed them in the page. Not supported any more.
|WebDriver (Selenium 2)

|Selenium 2
|A rewrite built on WebDriver code, which drives the browser natively through a driver rather than by injecting JavaScript. It still shipped the RC server, a legacy Firefox driver implemented as a browser extension (no longer works after Firefox changed its security model; use geckodriver), the pure-Java HtmlUnit driver, Grid 2 (WebDriver and RC) and the Java page-object helpers `PageFactory` and `LoadableComponent`.
|Selenium 3

|Selenium 3
|WebDriver without the RC code. Grid 3, the JSON Wire Protocol and, from about version 3.11, the W3C protocol side by side (the clients negotiated whichever the driver supported). Language bindings such as Python and Ruby had their own Selenium 3 documentation, and JavaScript tests had to be moved off the WebDriverJS promise manager to async/await.
|Selenium 4

|Selenium 4
|Implements the W3C WebDriver specification only, a rewritten Grid, Selenium Manager and WebDriver BiDi.
|Current (4.51.0)
|===

Source: https://www.selenium.dev/documentation/legacy/[Selenium -- Legacy documentation]

The legacy tree also holds the original Firefox-extension IDE, a page on migrating from RC to WebDriver, notes about stealing
focus in Linux, untrusted certificates and WebDriver for mobile browsers (what Appium replaced), the Grid 2 and Grid 3 set-up
guides and the Selenium 2 developer notes. None of that is relevant to code you start today; it is useful for reading and
migrating old suites.

=== The JSON Wire Protocol and the W3C protocol

Before the W3C standard, every driver spoke the *JSON Wire Protocol*: a REST-like service where the client sent JSON over HTTP to
the driver or the Remote WebDriver server, with endpoints such as `POST /session` (carrying `desiredCapabilities`),
`POST /session/:sessionId/element` and a capabilities object with keys like `browserName`, `version`, `platform`,
`javascriptEnabled`, `takesScreenshot` and `acceptSslCerts`. Elements were returned as an object with the key `ELEMENT`.

The W3C WebDriver protocol keeps the same shape but standardises it: new sessions send `capabilities` with `alwaysMatch` and
`firstMatch`, standard capability names are `browserName`, `browserVersion`, `platformName`, `acceptInsecureCerts`,
`pageLoadStrategy`, `proxy`, `timeouts`, `unhandledPromptBehavior` (and others in the specification), every non-standard
capability needs a vendor prefix containing a colon, and elements are returned under the key
`element-6066-11e4-a52e-4f735466cecf`. Selenium 4 speaks the W3C protocol only. A Selenium 4.51.0 Grid, asked for a session in
the legacy format, answers:

[source,bash]
----
curl -s -X POST http://localhost:4551/wd/hub/session -H 'Content-Type: application/json' \
  -d '{"desiredCapabilities":{"browserName":"chrome"}}'
----

Source: https://www.selenium.dev/documentation/legacy/json_wire_protocol/[Selenium -- JSON Wire Protocol Specification]

[source,text]
----
session not created: Could not start a new session. No nodes support the capabilities in the request
----

The same request in the W3C shape starts a session, and finding an element returns the W3C element key:

[source,json]
----
{"value": {"element-6066-11e4-a52e-4f735466cecf": "f.F876D29C343D9E9C9D1503718415A27C.d.5721E3E66EF11A49B6ACE8F67019E8A8.e.16"}}
----

Source: https://www.w3.org/TR/webdriver2/[W3C WebDriver (Level 2)]

The first output above is the real answer of the `selenium/standalone-chrome:4.51.0` container to the legacy request; the
second is its real response to `POST /element` on a session created with the W3C request shape.

=== PageFactory

`PageFactory` is a Java helper in `selenium-support` (`org.openqa.selenium.support.PageFactory`) from the Selenium 2 era. You
declare `WebElement` or `+List<WebElement>+` fields in a page object, call `PageFactory.initElements(driver, page)` and the
fields become *lazy proxies*: each use of the field looks the element up again on the live page. The default lookup uses the
field name as an `id`, then as a `name`. Annotations change the strategy:

[cols="2,3",options="header"]
|===
|Feature |Behaviour

|`@FindBy(how = How.NAME, using = "q")` or `+@FindBy(css = "...")+`
|Chooses the locator; `id`, `name`, `className`, `css`, `tagName`, `linkText`, `partialLinkText` and `xpath` are accepted.

|`@FindAll`, `@FindBys`
|Match any of several locators (`@FindAll`) or chain them (`@FindBys`).

|`@CacheLookup`
|Looks the element up once and keeps the reference; it goes stale after navigation or a re-render.

|`AjaxElementLocatorFactory(driver, timeoutInSeconds)`
|Retries each lookup until the element is present and displayed or the timeout passes, which gives fields a basic wait.

|`PageFactory.initElements(driver, SomePage.class)`
|Creates the page object itself, using a constructor that takes a `WebDriver` if there is one.
|===

The official page now ends with "For current guidance, read about Page Object Models". `PageFactory` is still present and not
deprecated in 4.51.0, but it is rarely recommended: it hides when a lookup happens, `@CacheLookup` produces stale-element
errors, the Python binding has no equivalent at all, and
explicit page object methods with waits are easier to read and to debug. The example below is a page object using the
`PageFactory`, with the `q` field found by the id-then-name default, the other fields by `@FindBy`, and
`AjaxElementLocatorFactory` supplying a five-second retry; the test that uses it follows.

[source,java]
----
package demo;

import java.time.Duration;
import java.util.List;
import org.openqa.selenium.WebDriver;
import org.openqa.selenium.WebElement;
import org.openqa.selenium.support.FindBy;
import org.openqa.selenium.support.PageFactory;
import org.openqa.selenium.support.pagefactory.AjaxElementLocatorFactory;

/** Page Object initialised by the PageFactory (a Selenium 2 era pattern, still shipped in selenium-support). */
public class BooksPage {
  private final WebDriver driver;
  private final String baseUrl;

  // No annotation: the PageFactory falls back to the field name and looks for id="q", then name="q".
  private WebElement q;

  @FindBy(css = "[data-testid=search-submit]")
  private WebElement searchSubmit;

  @FindBy(css = "[data-testid=result-count]")
  private WebElement resultCount;

  @FindBy(css = "[data-testid=book-card]")
  private List<WebElement> cards;

  public BooksPage(WebDriver driver, String baseUrl) {
    this.driver = driver;
    this.baseUrl = baseUrl;
    // Every field access is lazily looked up (and retried for up to 5 seconds) by the AjaxElementLocator.
    PageFactory.initElements(new AjaxElementLocatorFactory(driver, (int) Duration.ofSeconds(5).toSeconds()), this);
  }

  public BooksPage open() {
    driver.get(baseUrl + "/books");
    return this;
  }

  public BooksPage search(String text) {
    q.sendKeys(text);
    searchSubmit.click();
    return this;
  }

  public String resultCountText() { return resultCount.getText(); }

  public int cardCount() { return cards.size(); }
}
----

Source: https://www.selenium.dev/documentation/legacy/selenium_2/page_factory/[Selenium -- The PageFactory (legacy)]

object whose attributes are descriptors that look the element up on every access, which is what the proxies do. The class

[source,python]

import pytest
from selenium import webdriver
from selenium.webdriver.common.by import By
from selenium.webdriver.common.desired_capabilities import DesiredCapabilities
from selenium.webdriver.support import expected_conditions as EC
from selenium.webdriver.support.ui import WebDriverWait

from conftest import APP_URL, GRID_URL


class LazyElement:
    """A tiny PageFactory equivalent: a descriptor that looks the element up on every access."""

    def __init__(self, by, value):
        self.locator = (by, value)

    def __get__(self, page, owner):
        return page.driver.find_element(*self.locator)


class BooksPage:
    search_input = LazyElement(By.ID, "q")
    search_submit = LazyElement(By.CSS_SELECTOR, "[data-testid=search-submit]")
    result_count = LazyElement(By.CSS_SELECTOR, "[data-testid=result-count]")

    def __init__(self, driver, base_url):
        self.driver = driver
        self.base_url = base_url

    def open(self):
        self.driver.get(f"{self.base_url}/books")
        return self

    def search(self, text):
        self.search_input.send_keys(text)
        self.search_submit.click()
        WebDriverWait(self.driver, 5).until(
            EC.text_to_be_present_in_element((By.CSS_SELECTOR, "[data-testid=result-count]"), "1 book found"))
        return self


def test_page_object_replaces_page_factory(driver, base_url):

=== DesiredCapabilities (legacy) and the Options replacement

In Selenium 2 and 3 you described the browser you wanted with a `DesiredCapabilities` object (a dictionary in Python, a
hash in Ruby, a plain object in JavaScript) and passed it to the driver or to `RemoteWebDriver`. Keys were free-form:
`platform`, `version`, and whatever your cloud vendor wanted (`build`, `name`) at the top level. Selenium 4 sends W3C
capabilities, which reject unknown keys without a vendor prefix. The Options classes (`ChromeOptions`, `FirefoxOptions`,
`EdgeOptions`, `Options` in each binding) are the typed replacement: standard capabilities are properties, browser
arguments are methods, and everything else goes in a vendor-prefixed capability.

The legacy shape below is what Selenium 3 projects used. It is shown only to explain the error; do not write new code like
this. In Selenium 4.51.0, Java still contains the class `org.openqa.selenium.remote.DesiredCapabilities` (without the old
static factories such as `chrome()` and `firefox()`) and Python still has `DesiredCapabilities.CHROME` (a plain dictionary,
`+{'browserName': 'chrome'}+`), but the clients no longer accept them in the same places.

[source,java]
----
  @Test void legacyDesiredCapabilities() throws Exception {
    // Selenium 3 style: free-form keys, no vendor prefix. Kept only to show what a W3C-only server does with them.
    DesiredCapabilities caps = new DesiredCapabilities();
    caps.setBrowserName("chrome");
    caps.setCapability("platform", "Linux");
    caps.setCapability("version", "92");
    caps.setCapability("build", "nightly-42");
    caps.setCapability("name", "legacy caps");
    WebDriver driver = null;
    try {
      driver = new RemoteWebDriver(new URL(GRID), caps);
      driver.get(APP + "/books");
      System.out.println("LEGACY accepted: " + ((RemoteWebDriver) driver).getCapabilities().getBrowserVersion());
    } catch (Exception e) {
      System.out.println("LEGACY rejected: " + e.getClass().getSimpleName() + ": " + e.getMessage().lines().limit(6).toList());
    } finally {
      if (driver != null) driver.quit();
    }
  }
----

== Upgrading to Selenium 4

The official guide says that upgrading is "a painless process" for the officially supported languages (Ruby, JavaScript, C#,
Python and Java) and walks through three steps: prepare the test code, upgrade the dependencies, then fix the errors and
deprecation messages. Note that the guide's own examples pin `4.4.0` and `4.4.3`, the release in which it was written; replace
those with the current version (4.51.0 on the check date). Selenium 3.x releases from about 3.11 already implemented the W3C
protocol, so W3C-compliant Selenium 3 code works unchanged in Selenium 4. Code that relied on the legacy protocol does not.

=== Step 1: prepare the code

Selenium 4 removes the legacy protocol and uses W3C WebDriver underneath. For most code that is invisible; the two exceptions
are *capabilities* and the *Actions* API.

*Capabilities.* A session fails to start if the requested capabilities are not W3C compliant. The standard ones are
`browserName`, `browserVersion` (replaces `version`), `platformName` (replaces `platform`), `acceptInsecureCerts`,
`pageLoadStrategy`, `proxy`, `timeouts` and `unhandledPromptBehavior`. Anything else, including browser-specific and cloud
vendor keys, needs a vendor prefix, usually in a block such as `goog:chromeOptions`, `moz:firefoxOptions`, `ms:edgeOptions` or
the vendor's own `cloud:options`-style key. Replace `DesiredCapabilities` with the Options class of the browser, as shown above.

*Actions.* The Actions API follows the W3C model: input sources (keyboard, pointer, wheel) with sequences of ticks. In the Java
bindings the old `Actions` calls still work, but `perform()` builds the sequence itself so `.build().perform()` can drop the
`build()`; the old `Mouse` and `Keyboard` interfaces and `HasInputDevices` are gone from the 4.51.0 jars. In every binding
the new pointer and wheel actions, such as `scrollToElement`, `scrollByAmount` and `clickAndHold`, are available. Details are
in xref:web/e2e-testing/selenium/locating-and-interacting.adoc[Locating & Interacting].

=== Step 3: fix the errors

The table lists the changes most projects meet. "Removed" means the 4.51.0 jar or package no longer has it (checked by
inspecting the jars, importing the Python package and compiling or running the examples on this page); "changed" means the
call exists but its signature or behaviour differs.

[cols="2,2,3",options="header"]
|===
|Selenium 3 code |Selenium 4.51 |Notes

|`driver.manage().timeouts().implicitlyWait(10, TimeUnit.SECONDS)`
|`implicitlyWait(Duration.ofSeconds(10))`
|Java. `pageLoadTimeout` takes a `Duration` too, and `setScriptTimeout(2, TimeUnit.MINUTES)` became `scriptTimeout(Duration.ofMinutes(2))`. The `long`/`TimeUnit` overloads are removed.

|`new WebDriverWait(driver, 3)`
|`new WebDriverWait(driver, Duration.ofSeconds(3))`
|Java. `FluentWait.withTimeout` and `pollingEvery` also take a `Duration`.

|Java. The `+FindsBy*+` interfaces were internal and are removed; use `By`.

|`options.merge(capabilities);`
|`options = options.merge(capabilities);`
|Java. `merge` no longer mutates the caller; assign the result.

|`FirefoxOptions.setHeadless(true)`, `ChromeOptions.setHeadless(true)`

|Java. The `setHeadless` methods are gone from both Options classes in 4.51.0.

|`FirefoxOptions.setLegacy(true)`

|`BrowserType.FIREFOX`

|Java. `BrowserType` is removed.

|C#.

=== Beyond the compiler: behaviour changes to check

* *Waits.* Selenium 4 does not change the semantics of implicit and explicit waits, but mixing them still gives unpredictable
delays; use explicit waits (see xref:web/e2e-testing/selenium/waits-and-expected-conditions.adoc[Waits & Expected Conditions]).
From 4.51 the Java `ExpectedCondition` no longer implements Guava's `Function`, so code that composed conditions with Guava
types needs to use `java.util.function.Function` instead, and the Java client drops its Guava dependency.
* *Window and tab handling.* `driver.switchTo().newWindow(WindowType.TAB)` creates and switches to a new tab or window; the
older "open a link with a keyboard shortcut" workarounds can go.
* *Locators.* Relative locators (`+RelativeLocator.with(By.tagName("input")).above(...)+`) were added in Selenium 4; they are a
convenience, not a replacement for stable test ids.
* *Timeouts of the commands.* Selenium 4 has an HTTP client timeout (`ClientConfig`) separate from the session timeouts.
* *Grid URLs.* If your suite points at a Selenium 3 Grid at `http://host:4444/wd/hub`, it can keep that URL against a Grid 4;
but the old `desiredCapabilities` request format is rejected, as shown above.
* *Cloud vendors.* Move vendor settings under the vendor's prefixed key (`sauce:options`, `bstack:options`, `LT:Options`,
`cloud:options` in the guide's example) and read their current documentation: the keys differ.

== What changed recently

* *4.51.0 (9 October 2026):* Java client no longer depends on Guava; `ExpectedCondition` stops implementing Guava's `Function`;
`RemoteWebDriver.getClientFactory()` added; CDP versions 153 to 155 bundled.
* *4.50.0:* deprecated `HttpClient` methods removed in Java; relative locators from elements and shadow roots.
* *September 2026:* the Selenium IDE page was rewritten to describe a standalone application, and the downloads page states
that the version 3 extension is unmaintained and no longer in the Chrome Web Store.
* *July 2024 / November 2024:* last Selenium IDE release (`v4.0.1-beta.14`) and last `selenium-side-runner` publication
(`4.0.13`).
* *Selenium 4.0 (October 2021):* W3C-only protocol, Options classes as the way to request a session, `Duration` in Java
timeouts and waits, Grid 4, relative locators, new window API, `EventFiringDecorator`.
* *Selenium 4.6 (late 2022):* Selenium Manager first shipped with the bindings, removing the need for manual driver handling (it is the default in 4.51.0).
