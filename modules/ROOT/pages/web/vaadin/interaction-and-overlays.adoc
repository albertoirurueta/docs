Beyond input fields and the Grid, an application UI is buttons, menus, transient messages and pop-ups. This
page follows the individual component pages under https://vaadin.com/docs/latest/components[Components],
starting with https://vaadin.com/docs/latest/components/button[Button]. Every component here is Flow Java;
overlays render into a top-level layer, not inside their parent's DOM.

== Buttons and shortcuts

[source,java]
----
Button save = new Button("Save", VaadinIcon.CHECK.create(), e -> save());
save.addThemeVariants(ButtonVariant.LUMO_PRIMARY);
save.setDisableOnClick(true);                 // guards against double-submit

// a keyboard shortcut bound to the click
save.addClickShortcut(Key.KEY_S, KeyModifier.CONTROL);

// a shortcut not tied to a component
Shortcuts.addShortcutListener(this, this::openSearch, Key.KEY_K, KeyModifier.META);
----

An `Anchor` is a real link -- use it for downloads and external URLs; use `RouterLink` (see
xref:web/vaadin/routing-and-navigation.adoc[]) for in-app navigation. See
https://vaadin.com/docs/latest/flow/create-ui/shortcut[Keyboard shortcuts].

== Menus

`MenuBar` is a horizontal bar of buttons with drop-down sub-menus; `ContextMenu` attaches a menu to any
component, opened on right-click (or left-click if you set `setOpenOnClick(true)`). `GridContextMenu<T>` is the
row-aware variant.

[source,java]
----
MenuBar bar = new MenuBar();
MenuItem file = bar.addItem("File");
SubMenu fileMenu = file.getSubMenu();
fileMenu.addItem("New", e -> newDocument());
fileMenu.addItem("Open…", e -> openDialog());

ContextMenu ctx = new ContextMenu(grid);
ctx.addItem("Refresh", e -> reload());
----

See https://vaadin.com/docs/latest/components/menu-bar[Menu Bar] and
https://vaadin.com/docs/latest/components/context-menu[Context Menu].

== Transient messages

A `Notification` is a self-dismissing toast; a `Dialog` is a modal (or modeless) window you build from
components; `ConfirmDialog` is a ready-made yes/no prompt.

[source,java]
----
Notification.show("Saved", 3000, Notification.Position.BOTTOM_START);

Dialog dialog = new Dialog();
dialog.setHeaderTitle("Edit customer");
dialog.add(form);
dialog.getFooter().add(new Button("Cancel", e -> dialog.close()), saveButton);
dialog.open();

ConfirmDialog confirm = new ConfirmDialog(
        "Delete customer?", "This cannot be undone.",
        "Delete", e -> delete(),
        "Cancel", e -> {});
confirm.setConfirmButtonTheme("error primary");
confirm.open();
----

`ConfirmDialog` ships in the open-source component set (the `vaadin-core` artifact).
See https://vaadin.com/docs/latest/components/dialog[Dialog] and
https://vaadin.com/docs/latest/components/confirm-dialog[Confirm Dialog].

== Popover and Tooltip

`Popover` is a lightweight, non-modal overlay anchored to a target -- for menus, forms or help content.
`Tooltip` shows a short string on hover or focus and is configured through `+setTooltipText(...)+` on any
component.

[source,java]
----
Button info = new Button(VaadinIcon.INFO.create());
Popover popover = new Popover();
popover.setTarget(info);
popover.setPosition(PopoverPosition.BOTTOM);
popover.add(new Paragraph("Detailed explanation…"));

save.setTooltipText("Persist your changes (Ctrl+S)");
----

See https://vaadin.com/docs/latest/components/popover[Popover] and
https://vaadin.com/docs/latest/components/tooltip[Tooltip].

== Grouping content

[cols="1,3",options="header"]
|===
| Component | Use

| `Tabs` / `TabSheet` | A row of tabs; `TabSheet` also owns and swaps the content per tab.
| `Accordion` | Vertically stacked panels, one open at a time.
| `Details` | A single collapsible panel (a summary plus content).
| `SideNav` | A hierarchical navigation list, usually in an `AppLayout` drawer.
|===

[source,java]
----
TabSheet tabs = new TabSheet();
tabs.add("Summary", new SummaryView());
tabs.add("History", new HistoryView());

Accordion accordion = new Accordion();
accordion.add("Shipping address", shippingForm);
accordion.add("Billing address", billingForm);
----

`Avatar`, `Badge` (a `Span` with `theme="badge"`), and `ProgressBar` round out the status indicators:

[source,java]
----
ProgressBar bar = new ProgressBar(0, 100, 0);
bar.setValue(progress);

Span status = new Span("Active");
status.getElement().getThemeList().add("badge success");
----

== Drag and drop

Mark a source draggable and a target as a drop zone; the drop event carries the dragged component or, for a
`GridDropTarget`, the row it landed on.

[source,java]
----
DragSource<Card> source = DragSource.create(card);
source.setDraggable(true);
source.setEffectAllowed(EffectAllowed.MOVE);

DropTarget<VerticalLayout> target = DropTarget.create(column);
target.addDropListener(e -> e.getDragSourceComponent()
        .ifPresent(dragged -> column.add(dragged)));

GridDropTarget<Person> gridDrop = new GridDropTarget<>(grid, DropMode.BETWEEN);
gridDrop.addGridDropListener(e -> reorder(e.getDropTargetItem().orElse(null)));
----

See https://vaadin.com/docs/latest/flow/create-ui/drag-and-drop[Drag and drop].

== How overlays work

`Dialog`, `ConfirmDialog`, `Notification`, `Popover`, `ContextMenu` and the drop-downs of `ComboBox` and `Select`
are all *overlays*: the browser renders their content in a dedicated layer at the end of the document, outside the
DOM subtree of the component that opened them. That is why a dialog is never clipped by a `Scroller` or an
`overflow: hidden` parent, and why page CSS written for the parent does not reach the overlay -- style it through
a theme variant or the overlay's `::part()` (see xref:web/vaadin/theming-and-styling.adoc[]).

On the server an overlay is still an ordinary component. If you call `open()` on a dialog that has not been added
to any parent, Flow attaches it to the current `UI` for you and detaches it again when it closes (an *auto-added*
overlay); a dialog you added yourself with `add(dialog)` stays where you put it. Overlays also close when the
user navigates to another view. Either way the lifecycle is short:

[mermaid]
....
stateDiagram-v2
    [*] --> Created: new Dialog()
    Created --> Opened: open()
    Opened --> Closed: close(), Esc, outside click, a button, or navigation
    Closed --> Opened: open() again (reuse)
    Closed --> [*]: auto-added dialogs are detached here
....

The common options are all properties of the overlay, not CSS:

[cols="2,3",options="header"]
|===
| Setting | Effect

| `setModal(false)` | Modeless: the page behind stays interactive and there is no backdrop. Modal is the default.
| `setCloseOnEsc(false)` / `setCloseOnOutsideClick(false)` | Make the user choose a button, for example in an edit dialog with unsaved input.
| `setDraggable(true)` / `setResizable(true)` | Let the user move or resize a dialog; position and size are not preserved between opens.
| `+addOpenedChangeListener(...)+` | Runs on every open and close, whatever the cause -- the place for cleanup.
| `Notification#setDuration(0)` | A toast that stays until it is closed; use for errors that need action.
| `+Notification#setPosition(...)+` | Where the toast appears; only one position per notification.
|===

Focus is managed for you: a modal dialog traps keyboard focus while it is open and returns focus to the element
that opened it. Give custom dialogs a header title or an
`aria-label` so a screen reader announces them (see xref:web/accessibility.adoc[]).

== Worked example: deleting a customer with undo

A destructive action deserves two safety nets: a confirmation before, and a way back afterwards. The example below
combines a `GridContextMenu`, a keyboard shortcut, a `ConfirmDialog`, and a `Notification` that carries an *Undo*
button. It builds on the `Customer` grid used throughout this section:

[source,java]
----
@Route("customers-actions")
@PermitAll
public class CustomerActionsView extends VerticalLayout {

    private final CustomerService service;
    private final Grid<Customer> grid = new Grid<>(Customer.class, false);

    public CustomerActionsView(CustomerService service) {
        this.service = service;
        grid.addColumn(Customer::getName).setHeader("Name");

        GridContextMenu<Customer> menu = new GridContextMenu<>(grid);
        menu.addItem("Edit", e -> e.getItem().ifPresent(this::edit));
        menu.addItem("Delete", e -> e.getItem().ifPresent(this::confirmDelete));

        // Delete key on the selected row, active only while the grid has focus
        Shortcuts.addShortcutListener(grid, () ->
                grid.asSingleSelect().getOptionalValue().ifPresent(this::confirmDelete),
                Key.DELETE).listenOn(grid);
        add(grid);
        refresh();
    }

    private void refresh() { grid.setItems(service.findAll()); }

    private void edit(Customer c) {
        Dialog dialog = new Dialog();
        dialog.setHeaderTitle("Edit " + c.getName());
        dialog.setDraggable(true);
        dialog.setResizable(true);
        dialog.setCloseOnEsc(false);
        dialog.setCloseOnOutsideClick(false);

        Button save = new Button("Save", e -> { service.save(c); dialog.close(); refresh(); });
        save.addThemeVariants(ButtonVariant.LUMO_PRIMARY);
        save.addClickShortcut(Key.ENTER);
        dialog.getFooter().add(new Button("Cancel", e -> dialog.close()), save);

        dialog.addOpenedChangeListener(e -> {
            if (!e.isOpened()) {
                grid.focus();                   // keep keyboard users in the grid
            }
        });
        dialog.open();                          // auto-added to the UI, detached again on close
    }

    private void confirmDelete(Customer c) {
        ConfirmDialog dialog = new ConfirmDialog();
        dialog.setHeader("Delete " + c.getName() + "?");
        dialog.setText("The customer and its orders will be removed.");
        dialog.setCancelable(true);
        dialog.setConfirmText("Delete");
        dialog.setConfirmButtonTheme("error primary");
        dialog.addConfirmListener(e -> {
            service.delete(c);
            refresh();
            showUndo(c);
        });
        dialog.open();
    }

    private void showUndo(Customer deleted) {
        Notification toast = new Notification();
        toast.addThemeVariants(NotificationVariant.LUMO_CONTRAST);
        toast.setPosition(Notification.Position.BOTTOM_START);
        toast.setDuration(8000);

        Button undo = new Button("Undo", e -> {
            Customer copy = new Customer();
            copy.setName(deleted.getName());
            copy.setEmail(deleted.getEmail());
            service.save(copy);
            refresh();
            toast.close();
        });
        undo.addThemeVariants(ButtonVariant.LUMO_TERTIARY_INLINE);

        HorizontalLayout content = new HorizontalLayout(new Span("Deleted " + deleted.getName()), undo);
        content.setAlignItems(FlexComponent.Alignment.CENTER);
        toast.add(content);
        toast.open();
    }
}
----

Several design choices in this code are worth copying:

* *The same action, three entry points.* The context menu, the `Delete` key and any toolbar button all call
  `confirmDelete`, so the confirmation can never be bypassed by one route.
* *`listenOn(grid)` scopes the shortcut.* Without it a `Key.DELETE` listener would be active on the whole page and
  fire while the user is typing in a text field.
* *Undo re-creates the record.* A real application would soft-delete (set a flag) and clear it on undo, so the
  id, audit trail and relations survive; copying the fields as above is the simplest stand-in.
* *Create the dialog per click and let `open()` attach it.* Because the dialog was never added to a parent, Flow
  detaches it on close, so repeated edits do not accumulate components in the `UI`. The opened-change listener
  fires for every cause of closing (Cancel, Save, navigation) and is the single place for cleanup.

The key shortcuts compose with the focus model of the page: a click shortcut such as `Key.ENTER` on `Save` fires
only while the dialog is open, because the dialog's content is the shortcut's scope. A shortcut registered with
`+Shortcuts.addShortcutListener(this, ...)+` on the view, by contrast, stays active under open modal dialogs unless
you scope it with `listenOn`.
