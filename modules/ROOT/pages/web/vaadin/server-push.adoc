:keywords: Vaadin, Flow, server push, Push, PushMode, AUTOMATIC, MANUAL, Transport, WEBSOCKET, LONG_POLLING, UI.access, VaadinSession lock, VaadinService.getExecutor(), ExecutorService, Async, broadcaster, UIDetachedException, getUI, access versus accessSynchronously, Poll, PollListener, setPollInterval

include::partial$ai-disclaimer.adoc[]

By default a Flow UI only changes in response to a user action. *Server push* keeps a channel open so the
server can send DOM updates at any time -- for progress bars, dashboards, chat, or notifying one user of
another's change. This page follows
https://vaadin.com/docs/latest/flow/advanced/server-push[Server Push] and
https://vaadin.com/docs/latest/building-apps/server-push[the Building Apps guide].

== Enabling push

Add `@Push` to the class that implements `AppShellConfigurator` (there is exactly one per application):

[source,java]
----
@Push
public class AppShell implements AppShellConfigurator { }
----

`@Push(transport = Transport.WEBSOCKET)` is the default; `Transport.LONG_POLLING` falls back to a series of
held-open HTTP requests where a WebSocket cannot be established (some proxies). `@Push(PushMode.MANUAL)` means
*you* decide when a batch of changes is flushed with `ui.push()`; the default `PushMode.AUTOMATIC` flushes
after every access block.

== The session lock

A `VaadinSession` and its UIs are *not* thread-safe. Every read or write of a component from a thread other
than the one handling the current request must run inside `UI.access(Command)`, which acquires the session
lock, runs the command, and (in automatic mode) pushes the result:

[mermaid]
....
sequenceDiagram
    participant W as Worker thread
    participant L as Session lock
    participant UI as UI / component tree
    participant B as Browser
    W->>W: long-running work (query, report, API call)
    W->>L: ui.access(() -> ...)
    L-->>W: lock acquired
    W->>UI: mutate components (progressBar.setValue(...))
    W->>L: command returns, lock released
    L->>B: push DOM diff over the open channel
    B->>B: apply update
....

[source,java]
----
UI ui = UI.getCurrent();     // capture on the request thread, before starting the work

executor.execute(() -> {
    String report = reportService.build();     // slow — off the UI thread
    ui.access(() -> {
        downloadLink.setHref(report);
        Notification.show("Report ready");
    });
});
----

`+ui.access(...)+` is asynchronous and safe to call from any thread; `+ui.accessSynchronously(...)+` blocks the
caller and must never be called from a request thread already holding the lock.

== Running background work

Flow owns a shared `java.util.concurrent.Executor`; `VaadinService.getExecutor()` returns it. It is created with
the service and shut down with it, so background tasks do not outlive the application. In a Spring Boot
application the same executor is available as a bean with the `@VaadinTaskExecutor` qualifier:

[source,java]
----
public ReportView(ReportService reports, @VaadinTaskExecutor Executor executor) {
    UI ui = UI.getCurrent();                 // capture on the request thread
    executor.execute(() -> {
        for (int i = 0; i <= 100; i += 10) {
            int pct = i;
            reports.buildChunk();
            ui.access(() -> progressBar.setValue(pct / 100.0));
        }
    });
}
----

It is a plain `Executor`: it does not carry the Spring `SecurityContext` or the Vaadin thread-locals into the
worker, and it does not cancel a task when the UI detaches. Pass the data the task needs as arguments, keep a
`Future` (or a Reactor `Disposable`) if you want to cancel on detach, and wrap the executor with
`DelegatingSecurityContextExecutor` when the task calls secured services. A plain `ExecutorService` or a Spring
`@Async` method works too; you are then responsible for capturing the `UI` and for not leaking threads when the
user closes the tab.

== Broadcasting to many UIs

For "notify everyone" features, keep a thread-safe registry of listeners and fan out to each UI through its own
`+access(...)+`:

[source,java]
----
public final class Broadcaster {
    private static final Set<Consumer<String>> LISTENERS = new CopyOnWriteArraySet<>();

    public static Registration register(Consumer<String> listener) {
        LISTENERS.add(listener);
        return () -> LISTENERS.remove(listener);
    }

    public static void broadcast(String message) {
        LISTENERS.forEach(l -> l.accept(message));
    }
}

// in a view
private Registration registration;

@Override
protected void onAttach(AttachEvent event) {
    UI ui = event.getUI();
    registration = Broadcaster.register(msg ->
            ui.access(() -> Notification.show(msg)));
}

@Override
protected void onDetach(DetachEvent event) {
    registration.remove();   // avoid leaking the listener and the UI
}
----

An `+ui.access(...)+` scheduled against a UI that has since detached throws `UIDetachedException`; unregistering
in `onDetach` (as above) prevents it, and wrapping the body in a `try`/`catch` handles the race.

== The no-push alternative

If push cannot be enabled, `ui.setPollInterval(millis)` makes the browser poll on a timer; a `PollListener`
runs on each poll and can refresh the UI. It costs a request per interval per open tab, so use push where you
can:

[source,java]
----
ui.setPollInterval(2000);
ui.addPollListener(e -> grid.getDataProvider().refreshAll());
----

== How push works underneath

Push replaces the usual "request, then response" rhythm with a connection that stays open. Flow uses Atmosphere on
the server and a small client library in the browser. The browser first tries a WebSocket; if the handshake fails
(an old proxy, a firewall that strips the `Upgrade` header) it falls back to long polling, so the application
still works, only with more requests. `Transport.WEBSOCKET_XHR` is a third option: server-to-client messages travel
over the WebSocket, while client-to-server messages are ordinary HTTP requests, which is more robust behind
proxies that mishandle upstream WebSocket frames.

[mermaid]
....
flowchart TD
    start(["UI attaches with @Push"]) --> try["open a WebSocket"]
    try -->|handshake ok| ws["server writes DOM diffs to the socket<br/>whenever access() completes"]
    try -->|blocked or fails| lp["fall back to long polling<br/>(a held-open HTTP request)"]
    lp --> reconnect["server answers when there is a change,<br/>client immediately re-opens the request"]
    ws --> drop{"connection lost?"}
    reconnect --> drop
    drop -->|yes| retry["client reconnects<br/>(events emitted meanwhile are not replayed)"]
    drop -->|no| ws
....

Choosing a push mode is a trade-off between simplicity and control:

[cols="1,2",options="header"]
|===
| Setting | Behaviour

| `PushMode.AUTOMATIC` (default) | Every `+ui.access(...)+` block is pushed when it returns. Simple, but ten small
  updates make ten messages.
| `PushMode.MANUAL` | Nothing is sent until you call `ui.push()` inside an access block, so a batch of changes is
  flushed once.
| `PushMode.DISABLED` | No push; updates arrive only with the next request.
|===

== Worked example: a live order board

The order board shows incoming orders on every open screen. It combines a source of events that is independent of
the UI (a Reactor `Sinks.Many` here, but a message listener or an application event bridge works the same), a
subscription tied to the *attach/detach* life cycle of the view, and `+ui.access(...)+` to cross into the UI thread.

*The feed.* It is a singleton that any thread may publish into. Emissions to a `Sinks.Many` must not overlap, so
`publish` is serialised:

[source,java]
----
public record OrderEvent(long orderId, String customer, Instant at) { }

@Component
public class OrderFeed {

    private final Sinks.Many<OrderEvent> sink = Sinks.many().multicast().directBestEffort();

    /** Emissions to a Sinks.Many must be serialised: publishers may run on any thread. */
    public synchronized void publish(OrderEvent event) {
        sink.tryEmitNext(event);
    }

    public Flux<OrderEvent> stream() {
        return sink.asFlux();
    }
}
----

*The view.* The subscription is created in `onAttach` and disposed in `onDetach`. Attach is the earliest moment
when the `UI` is known, and detach is the last moment before it goes away, so the subscription's lifetime matches
the screen's exactly:

[source,java]
----
@Route("orders-live")
@PermitAll
public class OrderBoardView extends VerticalLayout {

    private final OrderFeed feed;
    private final Grid<OrderEvent> grid = new Grid<>(OrderEvent.class, false);
    private final List<OrderEvent> rows = new ArrayList<>();
    private Disposable subscription;

    public OrderBoardView(OrderFeed feed) {
        this.feed = feed;
        grid.addColumn(OrderEvent::orderId).setHeader("Order");
        grid.addColumn(OrderEvent::customer).setHeader("Customer");
        grid.addColumn(OrderEvent::at).setHeader("Received");
        grid.setItems(rows);
        add(grid);
    }

    @Override
    protected void onAttach(AttachEvent event) {
        UI ui = event.getUI();
        subscription = feed.stream().subscribe(order -> ui.access(() -> {
            rows.add(0, order);
            grid.getDataProvider().refreshAll();
        }));
    }

    @Override
    protected void onDetach(DetachEvent event) {
        subscription.dispose();            // stop receiving before the UI goes away
    }
}
----

The class on the application shell enables push; `@Push(PushMode.MANUAL)` would be the choice for the batch import
shown next:

[source,java]
----
@Push
public class AppShell implements AppShellConfigurator { }
----

The fan-out logic is plain Java, so it can be tested without Vaadin. The test below publishes 1,000 events from
four threads to two subscribers, disposes one halfway (a closed tab) and checks that the live subscriber saw every
event while the disposed one saw nothing after disposal:

[source,java]
----
@Test
void fansOutToLiveSubscribersOnly() throws Exception {
    OrderFeed feed = new OrderFeed();
    AtomicInteger a = new AtomicInteger();
    AtomicInteger b = new AtomicInteger();
    Disposable subA = feed.stream().subscribe(e -> a.incrementAndGet());
    Disposable subB = feed.stream().subscribe(e -> b.incrementAndGet());

    ExecutorService pool = Executors.newFixedThreadPool(4);
    CountDownLatch half = new CountDownLatch(1);
    for (int t = 0; t < 4; t++) {
        int base = t * 1000;
        pool.execute(() -> {
            for (int i = 0; i < 250; i++) {
                feed.publish(new OrderEvent(base + i, "c", Instant.now()));
                if (i == 124) half.countDown();
            }
        });
    }
    half.await();
    subB.dispose();                                  // a "closed tab"
    int bAtDispose = b.get();
    pool.shutdown();
    pool.awaitTermination(10, TimeUnit.SECONDS);

    assertEquals(1000, a.get());                     // the attached subscriber saw every event
    assertEquals(bAtDispose, b.get());               // the disposed one saw nothing afterwards
    subA.dispose();
}
----

== Batching updates with manual push

When a background task produces many changes, `AUTOMATIC` mode sends a message per `access` block. In manual mode
the task changes as much as it likes and flushes once:

[source,java]
----
@Push(PushMode.MANUAL)
public class AppShell implements AppShellConfigurator { }

void batchImport(UI ui, List<OrderEvent> incoming) {
    Executor executor = VaadinService.getCurrent().getExecutor();
    executor.execute(() -> {
        for (OrderEvent e : incoming) {
            ui.access(() -> rows.add(e));             // no message is sent yet
        }
        ui.access(() -> {
            grid.getDataProvider().refreshAll();
            ui.push();                                // one message for the whole batch
        });
    });
}
----

== Push and the browser tab

A hidden or throttled tab still holds its WebSocket, so a UI whose view is still attached keeps receiving
updates. Consider these cases when designing a feed:

* *Many open tabs.* Every tab is a separate `UI` with its own subscription; a feed that emits 100 events per second
  produces 100 `access` calls per second *per tab*. Sample or buffer (`Flux#sample`, `Flux#buffer`) before
  the UI.
* *Reconnects.* After a network drop the client reconnects, but events emitted in the gap are not replayed. If the
  UI must be correct, re-read the current state on `onAttach` and use the stream only for increments.
* *Session expiry.* A UI that has expired is closed by the server; its next `access` throws
  `UIDetachedException`. Unsubscribing in `onDetach` prevents this; for stray cases catch it and dispose the
  subscription.
