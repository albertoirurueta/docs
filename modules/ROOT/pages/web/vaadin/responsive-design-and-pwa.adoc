Vaadin components carry responsive behaviour, and a few annotations turn a Vaadin app into an installable
Progressive Web App. This page follows
https://vaadin.com/docs/latest/styling/lumo/utility-classes/breakpoints[the Lumo breakpoint utilities],
https://vaadin.com/docs/latest/flow/configuration/pwa[the PWA guide], and
https://vaadin.com/docs/latest/designing-apps[Designing Apps].

== Responsive components

Several components adapt on their own once configured:

[source,java]
----
// FormLayout: one column on narrow screens, two from 30em up
form.setResponsiveSteps(
        new FormLayout.ResponsiveStep("0", 1),
        new FormLayout.ResponsiveStep("30em", 2),
        new FormLayout.ResponsiveStep("60em", 3));

// AppLayout: the drawer overlays instead of pushing below a breakpoint (its default),
// with a toggle in the navbar
appLayout.addToNavbar(new DrawerToggle());
appLayout.setPrimarySection(AppLayout.Section.DRAWER);

// Grid: let columns size to content, and one column absorb the slack
grid.getColumns().forEach(c -> c.setAutoWidth(true));
grid.getColumnByKey("description").setFlexGrow(1);
----

== Breakpoint utilities

Lumo ships responsive variants of its utility classes -- prefix a class with a breakpoint name and it only
applies at that width and up. Combined with `LumoUtility` they cover most layout shifts without media queries:

[source,java]
----
layout.addClassNames(
        LumoUtility.Display.FLEX,
        LumoUtility.FlexDirection.COLUMN,
        "md:flex-row",            // horizontal from the medium breakpoint up
        LumoUtility.Gap.MEDIUM);
----

The breakpoints (`sm`, `md`, `lg`, `xl`, `xxl`) are listed at
https://vaadin.com/docs/latest/styling/lumo/utility-classes/breakpoints[Responsive utility classes]. For a
hand-written media query, target the theme stylesheet.

== The viewport

Flow sets a sensible viewport tag by default. Override it with `@Viewport` on the shell class when you need a
different scale or zoom policy:

[source,java]
----
@Viewport("width=device-width, initial-scale=1, viewport-fit=cover")
public class AppShell implements AppShellConfigurator { }
----

== Progressive Web App

`@PWA` on the shell class generates the web app manifest, icons and a service worker, so the app is
installable and its shell loads offline:

[source,java]
----
@PWA(
    name = "Acme Field Service",
    shortName = "Acme FS",
    offlinePath = "offline.html",
    offlineResources = { "images/logo.png" })
public class AppShell implements AppShellConfigurator { }
----

The generated service worker caches the application shell; server-driven views still need a connection, so
provide an `offlinePath` fallback and, for genuinely offline flows, a Hilla view with client-side state (see
xref:web/vaadin/hilla-and-react-views.adoc[]). See
https://vaadin.com/docs/latest/flow/configuration/pwa[Creating a PWA].

== Web Push

Web Push delivers notifications when the app is closed. Register the subscription on the client, store it, and
send from the server through the `WebPush` API:

[source,java]
----
WebPush webPush = new WebPush(vapidPublicKey, vapidPrivateKey, "mailto:ops@example.com");

// after the user grants permission and the client posts its subscription
webPush.sendNotification(subscription,
        new WebPushMessage("Job assigned", "Ticket #4821 is now yours"));
----

See https://vaadin.com/docs/latest/flow/configuration/web-push[Web Push].

== Choosing a responsive strategy

A Vaadin view can adapt in three places, and the cheapest one that works is the right one:

[mermaid]
....
flowchart TD
    q1{"Can CSS alone express it?<br/>(columns, direction, spacing, hiding)"} -->|yes| css["Breakpoint utility classes or a media query<br/>runs in the browser, no round trip"]
    q1 -->|no| q2{"Does a component have a<br/>responsive setting?"}
    q2 -->|yes| comp["FormLayout steps, AppLayout drawer,<br/>Grid auto-width"]
    q2 -->|no| srv["Server side: resize listener<br/>changes the component tree"]
....

* *CSS first.* Direction, wrapping, column counts, visibility and spacing are all expressible with breakpoint
  utilities or a media query, and they react to a resize instantly with no server round trip.
* *Component settings next.* `FormLayout` steps, the `AppLayout` drawer and `Grid` column sizing already measure
  the browser for you.
* *Server-side adaptation last.* When the *structure* must differ -- a column removed, a different component
  shown -- ask the browser for the width and change the tree. Each resize then costs a round trip, so keep this
  for what CSS cannot do.

The Lumo breakpoints follow the usual min-width convention: `sm` 640px, `md` 768px, `lg` 1024px, `xl` 1280px and
`xxl` 1536px. `LumoUtility` offers them as typed constants, so there is no class-name string to mistype:

[source,java]
----
Div cards = new Div(grid);
cards.addClassNames(
        LumoUtility.Display.FLEX,
        LumoUtility.FlexDirection.COLUMN,                       // stacked on a phone
        LumoUtility.FlexDirection.Breakpoint.Medium.ROW,        // side by side from 768px up
        LumoUtility.Gap.MEDIUM);
----

== Worked example: a customer list that adapts

The customer list below shows email next to the name on a wide screen and drops the column on a phone. It combines
the `Grid` column features with a server-side width check, because removing a *column* is something CSS utilities
cannot do. It reads the width once on attach and then follows resizes:

[source,java]
----
@Route("customers-responsive")
@PermitAll
public class ResponsiveCustomerView extends VerticalLayout {

    private static final int WIDE = 768;       // the Lumo "md" breakpoint
    private final Grid.Column<Customer> emailColumn;
    private Registration resizeRegistration;

    public ResponsiveCustomerView(CustomerService service) {
        Grid<Customer> grid = new Grid<>(Customer.class, false);
        grid.addColumn(Customer::getName).setHeader("Name").setAutoWidth(true).setFlexGrow(1);
        emailColumn = grid.addColumn(Customer::getEmail).setHeader("Email");
        grid.setItems(service.findAll());
        setSizeFull();
        add(grid);
    }

    @Override
    protected void onAttach(AttachEvent event) {
        UI ui = event.getUI();
        ui.getPage().executeJs("return window.innerWidth;")
                .then(Integer.class, width -> emailColumn.setVisible(width >= WIDE));
        resizeRegistration = ui.getPage().addBrowserWindowResizeListener(
                e -> emailColumn.setVisible(e.getWidth() >= WIDE));
    }

    @Override
    protected void onDetach(DetachEvent event) {
        resizeRegistration.remove();           // do not leak the listener
    }
}
----

Three details matter. The initial width must be requested explicitly, because the resize listener fires only on
*changes*; without the `executeJs` call a phone would start with the wide layout. The listener is removed on
detach so a closed view does not keep receiving events. And the threshold is the same 768 that the CSS utilities
use, so the CSS-driven and server-driven parts of the screen flip at the same width.

== The PWA life cycle

`@PWA` generates three artefacts: a web app manifest, the icon set, and a service worker. The service worker is
what makes the app installable and gives it an offline fallback. Its life follows the browser's, not Vaadin's:

[mermaid]
....
sequenceDiagram
    participant B as Browser
    participant S as Service worker
    participant V as Vaadin server
    B->>V: first visit over HTTPS
    V-->>B: app shell + manifest + service worker script
    B->>S: register and install
    S->>S: precache offlinePath and offlineResources
    Note over B,S: later visit, no connection
    B->>S: request for the app
    S-->>B: cached offline.html
    Note over B,V: later visit, connected
    B->>V: normal server-driven session
....

The service worker caches the *shell* and the offline page, not the server-driven views: a Flow view needs the
server, so while offline the user sees `offline.html`, not a working form. Installability also requires HTTPS
(except on `localhost`) and a manifest with a name and icons, which `@PWA` supplies. A new deployment ships a new
service worker; the browser installs it in the background and activates it on the next visit, so a user can run an
older shell for one visit after an upgrade.

== Web Push: the subscription flow

Web Push is a three-party exchange. The browser asks the user for permission and subscribes with its push
service; the server stores that subscription; and later the server sends a message through the push service,
which wakes the service worker even when the app is closed. The server needs a VAPID key pair, generated once and
kept in configuration:

[mermaid]
....
sequenceDiagram
    participant U as User
    participant B as Browser
    participant S as Vaadin server
    participant P as Push service
    U->>B: grant notification permission
    B->>P: subscribe (VAPID public key)
    P-->>B: subscription endpoint and keys
    B->>S: WebPush.subscribe callback receives the subscription
    S->>S: store subscription per user
    Note over S,P: later, a ticket is assigned
    S->>P: sendNotification(subscription, message)
    P->>B: deliver to the service worker
    B->>U: show the notification
....

[source,java]
----
public class FieldNotifier {

    private final WebPush webPush =
            new WebPush(vapidPublicKey, vapidPrivateKey, "mailto:ops@example.com");
    private final Map<String, WebPushSubscription> subscriptions = new ConcurrentHashMap<>();

    /** Call from a click handler: browsers expect the permission prompt to follow a user gesture. */
    public void subscribe(UI ui, String userId) {
        webPush.subscribe(ui, subscription -> subscriptions.put(userId, subscription));
    }

    public void assign(String userId, String ticket) throws WebPushException {
        WebPushSubscription subscription = subscriptions.get(userId);
        if (subscription != null) {
            webPush.sendNotification(subscription,
                    new WebPushMessage("Job assigned", "Ticket " + ticket + " is now yours"));
        }
    }
}
----

Store subscriptions in a database in a real application (they have to survive a restart), delete the ones the push
service reports as gone, and remember that the feature needs the `flow-webpush` module on the classpath.
