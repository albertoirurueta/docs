Vaadin has two test layers: fast *browserless* UI unit tests that instantiate views in the JVM, and *end-to-end*
tests that drive a real browser. This page follows
https://vaadin.com/docs/latest/flow/testing[the Testing documentation].

== UI unit tests (browserless)

`vaadin-testbench-unit` renders a view and its components server-side -- no browser, no HTTP -- so tests run at
unit-test speed. Extend `UIUnitTest` and point `@ViewPackages` at the code under test:

[source,xml]
----
<dependency>
  <groupId>com.vaadin</groupId>
  <artifactId>vaadin-testbench-unit</artifactId>
  <scope>test</scope>
</dependency>
----

[source,java]
----
@ViewPackages(packages = "com.example.views")
class CustomerViewTest extends UIUnitTest {

    @Test
    void savingShowsANotification() {
        CustomerView view = navigate(CustomerView.class);

        test($(TextField.class).withCaption("Name").single()).setValue("Ada");
        test($(Button.class).withText("Save").single()).click();

        assertEquals("Saved", test($(Notification.class).last()).getText());
    }
}
----

`+navigate(...)+` performs a real navigation (running `BeforeEnter` observers and security checks); `$(Type.class)`
queries the component tree with filters like `withText`, `withCaption`, `withId`; `test(component)` wraps a
component in a tester that simulates user actions (`click()`, `setValue()`, `_click()` for the raw event). This
module is *not* commercial -- it ships under the same licence as the framework core. See
https://vaadin.com/docs/latest/flow/testing/ui-unit[UI unit testing].

== End-to-end tests with TestBench

*TestBench* is Vaadin's commercial Selenium-based tool (see xref:web/vaadin/ui-component-libraries.adoc[]). It
drives a real browser and adds a fluent, component-aware element query API and pixel screenshot comparison:

[source,java]
----
@BrowserTest
class CustomerViewIT extends TestBenchTestCase {

    @BeforeEach
    void open() { getDriver().get("http://localhost:8080/customers"); }

    @Test
    void filtersTheGrid() {
        TextFieldElement filter = $(TextFieldElement.class).id("filter");
        filter.setValue("Ada");

        GridElement grid = $(GridElement.class).first();
        assertEquals("Ada Lovelace", grid.getCell(0, 0).getText());
    }
}
----

`$(GridElement.class)`, `+.id(...)+`, `.waitForFirst()` and `compareScreen("customers")` are the core API. Run
these against a started application (for example in the Maven `verify` phase).

== Playwright and Selenium

You can also test a running Vaadin app with plain https://playwright.dev/java/[Playwright for Java] or raw
Selenium -- Vaadin exposes stable `id` and component structure for selectors. TestBench adds the
component-typed element classes and screenshot tooling on top; the plain tools are the free option. For a
deeper, tool-focused reference -- install, headless vs. headed execution, evidence capture, CI/CD, and a full
Selenium/Playwright/Cypress comparison -- see xref:web/e2e-testing/index.adoc[E2E Testing in the Browser] and xref:web/e2e-testing/choosing-a-tool.adoc[Choosing a Tool].

== Load testing

The client-server protocol replays well: record a session and drive it with a load tool
(https://gatling.io/[Gatling] is commonly used). See
https://vaadin.com/docs/latest/flow/testing/load-testing[Load testing] for capturing and parameterising the
sync messages.

== With Spring

Extend `SpringUIUnitTest` (a `UIUnitTest` that starts the Spring Boot context) to exercise the real services and repositories:

[source,java]
----
@SpringBootTest
@ViewPackages(packages = "com.example.views")
class CustomerViewSpringTest extends SpringUIUnitTest {
    // injected Spring beans are used by the view under test
}
----

== What to test where

The two layers answer different questions, and a healthy suite has many cheap tests and few expensive ones:

[mermaid]
....
flowchart TD
    e2e["End-to-end (TestBench, Playwright)<br/>real browser, real bundle, few tests<br/>login, one happy path per feature, rendering"]
    ui["Browserless UI tests (UIUnitTest)<br/>views, binders, navigation, security<br/>milliseconds each, hundreds of tests"]
    unit["Plain unit tests<br/>services, validators, converters, access rules<br/>no Vaadin at all"]
    unit --> ui --> e2e
....

[cols="2,3",options="header"]
|===
| Test | Best layer

| A `Converter`, a `Validator`, a service rule | Plain unit test -- no Vaadin required.
| Which roles may open a route | Plain unit test with `AccessAnnotationChecker`; see xref:web/vaadin/security.adoc[].
| A form: value in, `Binder` validation, save, notification | Browserless UI test.
| Navigation guards, redirects, leave confirmation | Browserless UI test (it runs the real router).
| Layout correctness, CSS, a web component's behaviour in a real browser | End-to-end test.
| A file download or upload, a drag and drop | End-to-end test.
|===

A browserless test does not run JavaScript, so it cannot catch a bundling error or a styling problem; the
end-to-end layer exists for those, and should stay thin.

== Worked example: testing the customer editor

The tests below exercise the guarded editor from xref:web/vaadin/routing-and-navigation.adoc[] against a real
Spring context and a database. `SpringUIUnitTest` is the Spring-aware base class: it starts the Boot context, so
the views receive real beans, and it honours `@WithMockUser` for the security rules. `+@ViewPackages(classes = ...)+`
limits route discovery to the views under test, which keeps startup fast:

[source,java]
----
@SpringBootTest
@ViewPackages(classes = { CustomerEditorView.class, CustomerListView.class, MainLayout.class })
class CustomerEditorTest extends SpringUIUnitTest {

    @Autowired CustomerRepository repo;
    Long id;

    @BeforeEach
    void seed() {
        repo.deleteAll();
        Customer c = new Customer();
        c.setName("Ada Lovelace");
        c.setEmail("ada@example.com");
        id = repo.save(c).getId();
    }

    @Test
    @WithMockUser(roles = "ADMIN")
    void savingPersistsTheChangeAndReturnsToTheList() {
        navigate(CustomerEditorView.class, Map.of("customerId", String.valueOf(id)));

        TextField name = $(TextField.class).withCaption("Name").single();
        assertEquals("Ada Lovelace", name.getValue());

        test(name).setValue("Ada King");
        test($(Button.class).withText("Save").single()).click();

        assertEquals("Ada King", repo.findById(id).orElseThrow().getName());
        assertInstanceOf(CustomerListView.class, getCurrentView());
    }

    @Test
    @WithMockUser(roles = "ADMIN")
    void leavingWithUnsavedChangesAsksFirst() {
        navigate(CustomerEditorView.class, Map.of("customerId", String.valueOf(id)));
        test($(TextField.class).withCaption("Name").single()).setValue("Changed");

        navigate(CustomerListView.class);                    // postponed by beforeLeave

        ConfirmDialog dialog = $(ConfirmDialog.class).single();
        assertEquals("Discard changes?", test(dialog).getHeader());
        assertInstanceOf(CustomerEditorView.class, getCurrentView());   // still on the editor

        test(dialog).confirm();
        assertInstanceOf(CustomerListView.class, getCurrentView());
    }

    @Test
    @WithMockUser(roles = "ADMIN")
    void unknownCustomerShowsTheErrorView() {
        navigate(CustomerEditorView.class, Map.of("customerId", "9999"));
        assertNotEquals(CustomerEditorView.class, getCurrentView().getClass());
    }
}
----

Reading the test against the API:

* `+navigate(View.class, Map.of(...))+` fills the route template parameters and runs the full navigation, including
  every `BeforeEnter` observer and the access check -- this is why an `@RolesAllowed` view can only be opened with
  the right `@WithMockUser`.
* `$(Type.class)` queries the component tree of the *current view*; `withCaption`, `withText` and `withId` narrow
  the match and `single()` fails if there is not exactly one, which catches an accidentally duplicated field.
* `test(component)` returns a *tester*: a small object that simulates what a user can do (`setValue`, `click`,
  `confirm`) and respects what a user cannot do -- clicking a disabled button or typing into a read-only field
  throws instead of silently succeeding. Calling `+component.setValue(...)+` directly bypasses that check.
* `getCurrentView()` is the routed component after the navigation, so `assertInstanceOf` verifies where the user
  ended up.
* Notifications are components too: `test($(Notification.class).last()).getText()` reads a toast, and
  `ConfirmDialog` has its own tester with `confirm()`, `cancel()`, `getHeader()` and `getText()`.

The UI test classes use the commercial component classes in their signatures, so they expect the full `vaadin`
artifact on the test classpath rather than only `vaadin-core`.

== Testing asynchronous and pushed updates

A browserless test has no browser, but it still runs the real `ui.access` machinery, so an update pushed by a
background thread is applied when the test thread next synchronises with the UI. Wait for it explicitly instead
of sleeping:

[source,java]
----
@Test
@WithMockUser
void newOrdersAppearOnTheBoard() {
    navigate(OrderBoardView.class);
    orderFeed.publish(new OrderEvent(7, "Ada", Instant.now()));

    Awaitility.await().atMost(Duration.ofSeconds(2)).untilAsserted(() -> {
        roundTrip();                                           // process pending UI.access commands
        assertEquals(1, test($(Grid.class).single()).size());
    });
}
----

`roundTrip()` is the base-class hook that runs queued `ui.access` commands, which is what a browser round trip
would do in a running application. Keep the timeout small: a failure here usually means the view never
subscribed, which is a bug worth seeing quickly.

== End-to-end tests that stay stable

* *Select by `id`.* Give the components a test needs an explicit id (`filter.setId("customer-filter")`) so
  selectors do not break when a label changes language.
* *Wait, do not sleep.* Server-side updates and web-component rendering are asynchronous; use `waitForFirst()`
  (TestBench) or Playwright's auto-waiting locators.
* *Start from a known state.* Reset the database in a `@BeforeEach` (a throw-away database container is a good fit), or log in through
  a seeded user so tests are independent.
* *Keep the suite thin.* One login test, one happy path per feature, plus screenshots for the visual regressions
  you care about. Everything else belongs in browserless tests.
