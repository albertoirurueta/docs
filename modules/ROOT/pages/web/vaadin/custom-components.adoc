= Building Custom Components
:description: Creating reusable Vaadin Flow components -- composing existing components with Composite, extending a component, building one from a raw element with @Tag, implementing a value-bearing field with AbstractField, AbstractCompositeField or CustomField, packaging a component as a Maven add-on for the Vaadin Directory, and wrapping a JavaScript library or a React component.

When a screen repeats a cluster of components with its own behaviour, promote it to a class. Flow gives four
levels of custom component, from "just group these" to "a brand-new element". This page follows
https://vaadin.com/docs/latest/building-apps/components[Build a Component] and
https://vaadin.com/docs/latest/flow/create-ui/creating-components[Creating components]. It replaces the
Vaadin 7 xref:web/gwt/index.adoc[GWT] widget / connector approach.

== Compose with `Composite`

`Composite<T>` builds a component from other components without exposing the wrapper's own layout API. The
content is created once in `initContent()`:

[source,java]
----
public class SearchBar extends Composite<HorizontalLayout> {

    private final TextField field = new TextField();
    private final Button button = new Button(VaadinIcon.SEARCH.create());

    public SearchBar() {
        field.setPlaceholder("Search…");
        field.setValueChangeMode(ValueChangeMode.LAZY);
        getContent().add(field, button);
        getContent().setAlignItems(FlexComponent.Alignment.END);
    }

    public void addSearchListener(Consumer<String> listener) {
        Runnable fire = () -> listener.accept(field.getValue());
        button.addClickListener(e -> fire.run());
        field.addValueChangeListener(e -> fire.run());
    }
}
----

Callers see `SearchBar` and `+addSearchListener(...)+`, not a `HorizontalLayout`. Extending a component directly
(`class PrimaryButton extends Button`) is fine when you genuinely want its whole API.

== Build from an element

For a component with no Flow counterpart, start from `@Tag` and the `Element` API (see
xref:web/vaadin/element-api-and-web-components.adoc[]):

[source,java]
----
@Tag("hr")
public class ThematicBreak extends Component {
    public ThematicBreak() {
        getElement().setAttribute("role", "separator");
    }
}
----

== A component with a value

A field participates in `Binder` by implementing `HasValue`. `AbstractField<C, T>` implements it over an
element property; `AbstractCompositeField<C, S, T>` does the same but backed by a composed component; and
`CustomField<T>` is the simplest -- add child fields, then implement `generateModelValue()` and
`setPresentationValue(t)`:

[source,java]
----
public record Money(Currency currency, BigDecimal amount) { }

public class MoneyField extends CustomField<Money> {

    private final BigDecimalField amount = new BigDecimalField();
    private final Select<Currency> currency = new Select<>();

    public MoneyField(String label) {
        setLabel(label);
        currency.setItems(Currency.getInstance("EUR"), Currency.getInstance("USD"));
        currency.setValue(Currency.getInstance("EUR"));
        amount.addValueChangeListener(e -> updateValue());     // recompute the model value ...
        currency.addValueChangeListener(e -> updateValue());   // ... whenever a child changes
        add(new HorizontalLayout(amount, currency));
    }

    @Override
    protected Money generateModelValue() {
        return amount.isEmpty() ? null : new Money(currency.getValue(), amount.getValue());
    }

    @Override
    protected void setPresentationValue(Money money) {
        amount.setValue(money == null ? null : money.amount());
        if (money != null) {
            currency.setValue(money.currency());
        }
    }
}

// then it binds like any field
binder.forField(new MoneyField("Price"))
        .asRequired("Price is required")
        .withValidator(m -> m.amount().signum() > 0, "Must be positive")
        .bind(Product::getPrice, Product::setPrice);
----

The two `updateValue()` calls are essential: a `CustomField` does not observe its children, it only asks
`generateModelValue()` for a fresh value when told to. Without them `setPresentationValue` would work (the form
would *display* a price) but `getValue()` would stay `null` and the binder would never see the user's input.
With them, typing `19.99` and choosing `USD` yields `Money[currency=USD, amount=19.99]`; `writeBeanIfValid`
stores it; a negative amount fails the positivity rule and nothing is written; and reading a `Product` with no
price clears the field.

See https://vaadin.com/docs/latest/components/custom-field[Custom Field] and
https://vaadin.com/docs/latest/flow/binding-data/components-binder[creating a field with a value].

== Choosing the base class

The four levels from the introduction are really a decision about *what the component is*:

[mermaid]
....
flowchart TD
    start["I need a reusable piece of UI"] --> value{"Does it hold a value for a Binder?"}
    value -->|"no"| shape{"Built from existing components?"}
    shape -->|"yes, hide their API"| composite["Composite"]
    shape -->|"yes, keep the whole API"| extend["Extend the component"]
    shape -->|"no, it is a new element"| tag["Component with @Tag"]
    value -->|"yes"| one{"One element property?"}
    one -->|"yes"| single["AbstractSinglePropertyField"]
    one -->|"no"| made{"Made of several fields?"}
    made -->|"yes"| custom["CustomField"]
    made -->|"no, a composed layout"| acf["AbstractCompositeField"]
....

== Worked example: a field over one property

When the browser element already has a `value` property and a change event, `AbstractSinglePropertyField` is all
that is needed -- there is no `generateModelValue` to write. This colour picker wraps the native
`<input type="color">`:

[source,java]
----
@Tag("input")
public class ColorPicker extends AbstractSinglePropertyField<ColorPicker, String> {

    public ColorPicker() {
        super("value", "#000000", false);            // property name, default value, null not allowed
        getElement().setAttribute("type", "color");
        setSynchronizedEvent("change");              // sync after the DOM "change" event
    }
}
----

`setValue("#ff8800")` makes `getElement().getProperty("value")` return `#ff8800` and fires a value-change event with
the old value `#000000`; the rendered element is `<input type="color">`, because the colour is a property, not an
attribute. The class is a complete `HasValue<ValueChangeEvent<String>, String>`, so
`binder.forField(new ColorPicker()).bind(Theme::getAccent, Theme::setAccent)` works as is. The same technique,
backed by a Lit element, appears in xref:web/vaadin/element-api-and-web-components.adoc[].

== Worked example: events from a custom component

A component that announces something should expose a typed event and a listener method that returns a
`Registration`. `ComponentEvent` and the protected `addListener` / `fireEvent` pair of `Component` are the whole
mechanism:

[source,java]
----
public class RatingField extends Composite<Div> implements HasSize {

    public static class RatedEvent extends ComponentEvent<RatingField> {
        private final int stars;

        public RatedEvent(RatingField source, boolean fromClient, int stars) {
            super(source, fromClient);
            this.stars = stars;
        }

        public int getStars() { return stars; }
    }

    public Registration addRatedListener(ComponentEventListener<RatedEvent> listener) {
        return addListener(RatedEvent.class, listener);
    }

    void rate(int stars) {                        // called from the component's own click handlers
        fireEvent(new RatedEvent(this, true, stars));
    }
}
----

A listener added with `addRatedListener` receives every `+rate(...)+` call until its `Registration.remove()` is
called; after that, later events are not delivered. Return the `Registration` rather than `void` so callers can
unregister in `onDetach`, as described in xref:web/vaadin/architecture.adoc[].

== Packaging an add-on

To share a component, build it as its own Maven artifact. The `vaadin-archetype-addon` archetype produces a
project with the right layout and an `addon` assembly. Publish the jar and list it on
https://vaadin.com/directory[the Vaadin Directory]; consumers add the `vaadin-addons` repository and your
dependency (see xref:web/vaadin/ui-component-libraries.adoc[]):

[source,bash]
----
mvn -B archetype:generate \
  -DarchetypeGroupId=com.vaadin \
  -DarchetypeArtifactId=vaadin-archetype-addon \
  -DarchetypeVersion=LATEST \
  -DgroupId=org.example -DartifactId=money-field
----

Keep the frontend files under `src/main/resources/META-INF/frontend` (or reference them with `@JsModule`) so
the consuming project's build bundles them.

== Wrapping client libraries

* *A JavaScript library* -- add it with `@NpmPackage` + `@JsModule`, then drive it from a
  `@Tag`-backed component with `+executeJs(...)+` and DOM event listeners (see
  xref:web/vaadin/element-api-and-web-components.adoc[]).
* *A React component* -- extend `ReactAdapterComponent`, ship a small `.tsx` adapter under the frontend
  folder, and pass props and events across with `+setState(...)+` / `+addStateChangeListener(...)+`. See
  https://vaadin.com/docs/latest/flow/integrations/react[Add a React component].
