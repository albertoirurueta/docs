This page is written against Laravel 13.x (13.34.0) on PHP 8.3 to 8.5, checked on 2026-10-05. The newest of the
books, *Laravel: Up & Running* (2nd ed., 2019), describes Laravel 5.8 on PHP 7.1. Since then there have been eight
major releases, and the framework's structure, defaults and recommended packages have changed more than its core
ideas. This page summarises the releases, shows what old code does on Laravel 13, and collects in one table the
outdated statements that the pages of this section correct one by one. The PHP language side, from PHP 7 to 8.5, is
on xref:programming-languages/php/whats-new-and-migration.adoc[What's New and Migration].

== Releases from 6 to 13

Laravel has used semantic versioning since 6.0 and ships one major version a year. Each release in one line:

[cols="1,1,6"]
|===
| Version | Year | Main changes

| 6 (LTS) | 2019 | Semantic versioning. `make:auth` moved to `laravel/ui`. The `+str_*+` and `+array_*+` helpers and the `Input` facade removed. Lazy collections, Ignition error page, job middleware.
| 7 | 2020 | Sanctum (as Airlock), the `Http` client, custom casts, Blade components as `<x-…>` tags, fluent `Str`, built-in CORS, several mailers (`MAIL_MAILER`).
| 8 | 2020 | `app/Models`, class-based factories, Jetstream and then Breeze, job batches, named rate limiters, controller namespace removed from route files, time travel in tests, `schema:dump`.
| 9 | 2022 | PHP 8.0. Symfony Mailer, Flysystem 3, `Attribute` accessors, enum casts, anonymous migrations, `lang/` at the root, Vite instead of Mix (9.19).
| 10 | 2023 | PHP 8.1. Native types in the skeleton, the `Process` facade, Pennant, Laravel Prompts, Precognition. `$dates` removed.
| 11 | 2024 | PHP 8.2. The slim skeleton: `bootstrap/app.php` instead of the HTTP and console kernels, SQLite and database queues by default, `install:api` and `install:broadcasting`, Reverb, `casts()` method, `/up` health route, `APP_PREVIOUS_KEYS`, `Concurrency`.
| 12 | 2025 | Minimal breaking changes. React, Vue, Svelte and Livewire starter kits replace Breeze and Jetstream. UUIDv7 for `HasUuids`.
| 13 | 2026 | PHP 8.3. The AI SDK, JSON:API resources, `PreventRequestForgery` with `Sec-Fetch-Site`, queue attributes and `Queue::route()`, `Cache::touch()`, vector search, cache `serializable_classes`.
|===

Source: https://laravel.com/framework/docs/13.x/releases[Laravel -- Release Notes]

== Support policy

Each release gets bug fixes for 18 months and security fixes for 2 years:

[cols="1,1,2,2,2"]
|===
| Version | PHP | Released | Bug fixes until | Security fixes until

| 10 | 8.1 to 8.3 | 2023-02-14 | 2024-08-06 | 2025-02-04
| 11 | 8.2 to 8.4 | 2024-03-12 | 2025-09-03 | 2026-03-12
| 12 | 8.2 to 8.5 | 2025-02-24 | 2026-08-13 | 2027-02-24
| 13 | 8.3 to 8.5 | 2026-03-17 | Q3 2027 | 2028-03-17
|===

Source: https://laravel.com/framework/docs/13.x/releases#support-policy[Laravel -- Support Policy]

On 2026-10-05, Laravel 11 and older receive no fixes, 12 receives security fixes only, and 13 is the release to be on.
There is no LTS release since 6. Every application upgrades once a year, or at least every second year. Laravel 14
is expected in the first quarter of 2027 and will require PHP 8.4 or later. An application on PHP 8.3 has to upgrade
PHP before it can move to Laravel 14. `composer prohibits php 8.2` shows what holds an application to a PHP version.
In Bookshelf, `laravel/laravel` itself, `laravel/ai`, Intervention Image, paratest and the local `bookshelf/isbn`
package require `+^8.3+`.

== Old code on Laravel 13

Code from the books and from Laravel 5-era tutorials, run in Bookshelf:

[source,php]
----
<?php
str_slug('Wild Seed');                                     // 5.7 helper
array_get(['x' => ['y' => 1]], 'x.y');                     // 5.7 helper
Input::get('q');                                           // facade removed in 6
Route::get('/legacy-string-route', 'BookController@index');   // controller strings without a namespace
new class extends Model { protected $dates = ['due_at']; };   // removed in 10
factory(App\Models\Book::class)->make();                   // 5.x factory helper
new App\User;                                              // 5.x model location
Request::create('/?q=')->has('q');                         // has() versus filled()
----

Source: https://laravel.com/framework/docs/13.x/upgrade[Laravel -- Upgrade Guide]

[source,text]
----
str_slug('Wild Seed') (5.7 helper)             -> Error: Call to undefined function str_slug()
array_get($a, 'x.y') (5.7 helper)              -> Error: Call to undefined function array_get()
Input::get('q') (facade removed in 6)          -> Error: Class "Input" not found
Route 'BookController@index' (no namespace)    -> 500, log: Target class [BookController] does not exist
$dates = ['due_at'] on a model (removed in 10) -> string
Carbon on a casts() datetime                   -> Illuminate\Support\Carbon
factory(App\Models\Book::class) (5.x helper)   -> Error: Call to undefined function factory()
App\User (5.x model location)                  -> Error: Class "App\User" not found
$request->has('q') on an empty value           -> true / filled: false
----

Source: https://laravel.com/framework/docs/13.x/eloquent-mutators#date-casting[Laravel -- Date Casting]

Most of this fails loudly, which is the easy case. The `$dates` line is the dangerous one: the property is silently
ignored, so `due_at` stays a string and code that calls `+->isPast()+` on it fails later and somewhere else. The `has()`
line has not changed, but tutorials often use it where `filled()` is meant. The fixes are on the pages for each
feature: `Str::slug()` and `Arr::get()` (xref:web/php-laravel/collections-and-pagination.adoc[Collections and
Pagination]), `[BookController::class, 'index']` (xref:web/php-laravel/routing.adoc[Routing]), the `casts()` method
(xref:web/php-laravel/eloquent-casts-accessors-and-serialization.adoc[Eloquent Casts, Accessors and Serialization]),
class factories (xref:web/php-laravel/migrations-seeders-and-factories.adoc[Migrations, Seeders and Factories]) and
`app/Models` (xref:web/php-laravel/eloquent-models.adoc[Eloquent Models]).

== The Laravel 11 skeleton

Laravel 11 removed `app/Http/Kernel.php`, `app/Console/Kernel.php`, `app/Exceptions/Handler.php` and most service
providers from new applications. Middleware, exception handling and routing moved into `bootstrap/app.php` (54
lines in Bookshelf), the schedule into `routes/console.php`, and the remaining providers into
`bootstrap/providers.php`. Bookshelf's `app/Http` holds only `Controllers`, `Middleware`, `Requests`, `Resources`
and `Responses`.

*Existing applications do not need to change their structure.* The upgrade guide for 11 says so explicitly: an
application upgraded from 10 keeps its kernels and providers, and they keep working. The new structure is the
default for new applications and what the documentation describes. Moving an old application to it is optional
cleanup, and Laravel Shift offers it as a separate step. The mapping is on
xref:web/php-laravel/directory-structure-and-configuration.adoc[Directory Structure and Configuration] and
xref:web/php-laravel/middleware.adoc[Middleware].

== Upgrading to 13

Laravel 13 has three high-impact items and two medium ones, and most applications upgrade without code changes:

* *Dependencies*: `laravel/framework` `+^13.0+`, `laravel/tinker` `+^3.0+`, `phpunit/phpunit` `+^12.0+`, `pestphp/pest`
  `+^4.0+` and `laravel/boost` `+^2.0+`, plus an updated installer.
* *Request forgery protection*: `VerifyCsrfToken` became `PreventRequestForgery`. References in
  `bootstrap/app.php`, tests (`withoutMiddleware(VerifyCsrfToken::class)`) and the `$except` list move to the new
  class and `preventRequestForgery(except: …)`
  (xref:web/php-laravel/security-csrf-encryption-and-hashing.adoc[Security: CSRF, Encryption and Hashing]).
* *Cache `serializable_classes`*: cached objects come back as `+__PHP_Incomplete_Class+` unless listed. In Bookshelf
  this broke a cached Eloquent model and a cached `Collection`
  (xref:web/php-laravel/cache-and-rate-limiting.adoc[Cache and Rate Limiting]).
* *`upsert` on MySQL and MariaDB* changed how the unique columns are passed.

The upgrade guide lists the low-impact items, such as cache prefixes, session cookie names and event property
renames, each with its likelihood of affecting an application.

Source: https://laravel.com/framework/docs/13.x/upgrade#upgrade-13.0[Laravel -- Upgrading To 13.0 From 12.x]

== Tools for upgrading

* *Laravel Shift* (laravelshift.com, commercial) opens a pull request per upgrade step. It covers the version bump,
  the renamed classes, the configuration files and, optionally, the new skeleton. Running one Shift per major version,
  in order, is the usual way to bring a 5.x application forward.
* *Rector* with `driftingly/rector-laravel` applies automated refactorings, such as helpers to facades, `$dates` to
  casts and string routes to callables, through level sets per version. `rector/rector` is published as a prebuilt
  package, and `composer require --dev rector/rector driftingly/rector-laravel` failed in this environment
  (`Could not authenticate against github.com` for the dist archive), so it was not run here.
* *Boost* gives a coding agent the `/upgrade-laravel-v13` command with the upgrade guide as context
  (xref:web/php-laravel/ai-sdk-mcp-and-boost.adoc[AI SDK, MCP and Boost]).

All three work best on a codebase with tests, because an upgrade is mostly verifying that nothing changed. The
suite on xref:web/php-laravel/testing.adoc[Testing] is what makes a yearly upgrade a day's work.

== Where older books and tutorials are outdated

* *"Laravel releases an LTS version every two years"* stopped after 6. Every release now has 18 months of bug fixes
  and two years of security fixes.
* *"Upgrade guides are long"* was true for 5.x. Laravel 12 and 13 were designed for minimal breaking changes.
* *Upgrading by copying the new skeleton over the old application* loses customisations. The upgrade guide, Shift or
  Rector change only what is needed.
