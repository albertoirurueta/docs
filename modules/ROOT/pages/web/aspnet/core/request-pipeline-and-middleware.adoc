= Request Pipeline and Middleware
:description: The ASP.NET Core middleware pipeline -- ordered RequestDelegates, Use/Run/Map, the recommended order, built-in middleware, writing custom middleware, and HttpContext.
:keywords: ASP.NET Core middleware, request pipeline, RequestDelegate, app.Use, app.Run, app.Map, UseRouting, UseAuthentication, HttpContext, IMiddleware, custom middleware

include::partial$ai-disclaimer.adoc[]

Every HTTP request flows through an ordered chain of *middleware* components. Each one can inspect and modify
the request, call the next component, and then inspect and modify the response on the way back out.

== The pipeline as a chain of delegates

A middleware is a function that takes the next middleware (`RequestDelegate`) and returns a `RequestDelegate`.
Calling `await next(context)` passes control down the chain; *not* calling it short-circuits, so nothing after
it runs.

[source,csharp]
----
var app = builder.Build();

app.Use(async (context, next) =>
{
    // runs on the way in
    var start = TimeProvider.System.GetTimestamp();
    await next(context);                 // invoke the rest of the pipeline
    // runs on the way out
    var ms = TimeProvider.System.GetElapsedTime(start).TotalMilliseconds;
    app.Logger.LogInformation("{Path} took {Elapsed} ms", context.Request.Path, ms);
});

app.Run();
----

See https://learn.microsoft.com/en-us/aspnet/core/fundamentals/middleware/[ASP.NET Core Middleware].

== `Use`, `Run`, `Map`

* `+app.Use(...)+` adds a middleware that may call `next`.
* `+app.Run(...)+` adds a *terminal* middleware -- it never calls `next`.
* `+app.Map("/admin", branch => ...)+` / `+app.MapWhen(predicate, branch => ...)+` fork the pipeline into a branch
  for matching requests.

[source,csharp]
----
app.Map("/health", branch => branch.Run(async ctx => await ctx.Response.WriteAsync("OK")));

app.MapWhen(ctx => ctx.Request.Query.ContainsKey("debug"),
    branch => branch.Use(async (ctx, next) => { /* extra logging */ await next(ctx); }));
----

**Recommended order** (register in this sequence):

[source,csharp]
----
app.UseExceptionHandler("/error");   // outermost: catches everything below
app.UseHsts();
app.UseHttpsRedirection();
app.UseStaticFiles();                // or app.MapStaticAssets()
app.UseRouting();
app.UseCors();
app.UseRateLimiter();
app.UseAuthentication();
app.UseAuthorization();
app.UseOutputCache();
app.MapControllers();                // endpoint execution
----

See https://learn.microsoft.com/en-us/aspnet/core/fundamentals/middleware/#middleware-order[Middleware order].

== Built-in middleware tour

[cols="1,3",options="header"]
|===
| Middleware | Purpose

| `UseExceptionHandler` | Convert unhandled exceptions into a clean error response. See
  xref:web/aspnet/core/error-handling-logging-and-observability.adoc[Error handling].
| `UseStaticFiles` / `MapStaticAssets` | Serve files from `wwwroot`; `MapStaticAssets` (.NET 9+) adds build-time
  fingerprinting and compression.
| `UseRouting` + endpoint execution | Match the request to an endpoint, then run it.
| `UseCors` | Apply cross-origin policies. See xref:web/cors.adoc[What is CORS?].
| `UseAuthentication` / `UseAuthorization` | Establish `HttpContext.User`, then enforce policies.
| `UseResponseCompression` | Gzip/Brotli-compress responses.
| `UseResponseCaching` / `UseOutputCache` | HTTP cache headers vs. server-side cached responses. See
  xref:web/aspnet/core/performance-and-caching.adoc[Performance and caching].
| `UseRateLimiter` | Reject or queue requests above a configured rate.
| `UseRequestLocalization` | Resolve culture from the request.
|===

== Writing custom middleware

**Inline lambda** -- for one-off logic (shown above with `app.Use`).

**Convention-based class** -- a class with a constructor taking `RequestDelegate` and an `InvokeAsync(HttpContext)`
method. It is instantiated once (singleton); inject scoped services as `InvokeAsync` parameters, not
constructor parameters.

[source,csharp]
----
public sealed class RequestIdMiddleware(RequestDelegate next)
{
    public async Task InvokeAsync(HttpContext context, ILogger<RequestIdMiddleware> logger)
    {
        context.Response.Headers["X-Request-Id"] = context.TraceIdentifier;
        using (logger.BeginScope("ReqId:{Id}", context.TraceIdentifier))
            await next(context);
    }
}

// a small helper extension keeps Program.cs readable:
public static class RequestIdMiddlewareExtensions
{
    public static IApplicationBuilder UseRequestId(this IApplicationBuilder app)
        => app.UseMiddleware<RequestIdMiddleware>();
}

// registration in Program.cs:
app.UseRequestId();          // or: app.UseMiddleware<RequestIdMiddleware>();
----

**Factory-based** -- implement `IMiddleware` and register it in DI (`AddTransient` / `AddScoped`); the framework
resolves a fresh instance per request, so constructor injection of scoped services is safe.

[source,csharp]
----
public sealed class AuditMiddleware(IAuditSink sink) : IMiddleware
{
    public async Task InvokeAsync(HttpContext context, RequestDelegate next)
    {
        await sink.RecordAsync(context.Request.Path);
        await next(context);
    }
}

builder.Services.AddScoped<AuditMiddleware>();
app.UseMiddleware<AuditMiddleware>();
----

See https://learn.microsoft.com/en-us/aspnet/core/fundamentals/middleware/write[Write custom middleware].

== `HttpContext`

`HttpContext` carries everything about the current request:

[source,csharp]
----
app.Use(async (context, next) =>
{
    var path   = context.Request.Path;                 // request line + headers + body
    context.Response.StatusCode = StatusCodes.Status202Accepted;
    var user   = context.User;                         // ClaimsPrincipal (after auth)
    context.Items["startedAt"] = DateTimeOffset.UtcNow; // per-request scratch dictionary
    var clock  = context.RequestServices.GetRequiredService<TimeProvider>(); // request-scoped DI
    var feature = context.Features.Get<IHttpConnectionFeature>();            // low-level server features
    await next(context);
});
----

Read the request body once (it is a forward-only stream); call `context.Request.EnableBuffering()` first if
you need to read it more than once. `IHttpContextAccessor` exposes the current `HttpContext` to non-request
types, but it uses an `AsyncLocal` and adds overhead -- prefer passing what you need explicitly. See
https://learn.microsoft.com/en-us/aspnet/core/fundamentals/httpcontext[Access HttpContext].

[mermaid]
....

    RT --> AUTH[UseAuthentication / UseAuthorization]

    HR --> EH
    EH --> RESP([Response])
    SF -. file found: short-circuit .-> RESP

Each component wraps the next; the response unwinds back through every component that called `next`. Static
files, when a file matches, write the response and never call routing.

== Deep dive: a timing middleware that survives the response

A middleware does work *before* calling `next` and *after* it returns. The trap is the response: once the first byte
is written, the status line and headers are on the wire and `+context.Response.Headers[...] = ...+` throws
`InvalidOperationException` ("Headers are read-only, response has already started"). A middleware that wants to add a
header based on work done by the rest of the pipeline therefore registers a callback with `Response.OnStarting`,
which the server invokes just before it flushes the headers.

The example measures how long the rest of the pipeline took and reports it as a `Server-Timing` header, skipping
health probes with `UseWhen` so they stay cheap and unlogged.

[source,csharp]
----
using System.Diagnostics;

public sealed class ServerTimingMiddleware(RequestDelegate next, ILogger<ServerTimingMiddleware> logger)
{
    public async Task InvokeAsync(HttpContext context)
    {
        var started = Stopwatch.GetTimestamp();

        context.Response.OnStarting(static state =>
        {
            var (ctx, start) = ((HttpContext, long))state;
            var elapsed = Stopwatch.GetElapsedTime(start);
            ctx.Response.Headers.Append("Server-Timing", $"app;dur={elapsed.TotalMilliseconds:F1}");
            return Task.CompletedTask;
        }, (context, started));

        await next(context);

        logger.LogInformation("{Method} {Path} -> {Status} in {Elapsed:F1} ms",
            context.Request.Method, context.Request.Path, context.Response.StatusCode,
            Stopwatch.GetElapsedTime(started).TotalMilliseconds);
    }
}
----

[source,csharp]
----
var app = WebApplication.CreateBuilder(args).Build();

app.UseWhen(
    ctx => !ctx.Request.Path.StartsWithSegments("/healthz"),
    branch => branch.UseMiddleware<ServerTimingMiddleware>());

app.MapGet("/healthz", () => "ok");
app.MapGet("/slow", async () => { await Task.Delay(120); return "done"; });
app.Run();
----

`UseWhen` forks the pipeline for requests matching the predicate and then *rejoins* the main branch, so routing and
the endpoints below it still run. `MapWhen` and `Map`, in contrast, fork for good: the branch never returns to the
main pipeline, which suits an isolated sub-application but not a cross-cutting concern like timing.

=== Testing the middleware without a server

Because a middleware is just a delegate over `HttpContext`, it can be unit-tested with `DefaultHttpContext`; no host is
needed. Supply a terminal `next` delegate that stands in for the rest of the pipeline.

[source,csharp]
----
public class ServerTimingMiddlewareTests
{
    [Fact]
    public async Task Next_is_invoked_and_status_is_preserved()
    {
        var context = new DefaultHttpContext();
        var called = false;
        var middleware = new ServerTimingMiddleware(
            ctx => { called = true; ctx.Response.StatusCode = 201; return Task.CompletedTask; },
            NullLogger<ServerTimingMiddleware>.Instance);

        await middleware.InvokeAsync(context);

        Assert.True(called);
        Assert.Equal(201, context.Response.StatusCode);
    }
}
----

`DefaultHttpContext` never starts a real response, so `OnStarting` callbacks do not fire in this test. To assert on
the `Server-Timing` header, use `WebApplicationFactory<Program>` as shown in
xref:web/aspnet/core/testing.adoc[Testing], where the full pipeline runs in memory.

=== Ordering mistakes worth recognising

* **Exception handler too late.** `UseExceptionHandler` only catches what is thrown by components *after* it, so it
  goes first.
* **Authorization before routing.** `UseAuthorization` reads endpoint metadata such as `[Authorize]`, which exists
  only once `UseRouting` has selected an endpoint.
* **Writing then calling `next`.** A middleware that writes to the body and then still calls `next` will usually
  cause the next component to fail when it tries to set headers or a status code.
* **Capturing the response body.** Replacing `Response.Body` with a `MemoryStream` to inspect output costs a copy of
  every response; prefer `OnStarting` or `IHttpResponseBodyFeature` wrappers for anything on a hot path.
