= Getting Started with ASP.NET Core
:description: What ASP.NET Core is, the .NET 10 LTS release cadence, the SDK and dotnet CLI, the project layout, the minimal hosting model, and how to choose an app model.
:keywords: ASP.NET Core, .NET 10, C# 14, dotnet CLI, dotnet new, WebApplication, minimal hosting model, Program.cs, LTS, Kestrel, Blazor, Minimal API

include::partial$ai-disclaimer.adoc[]

ASP.NET Core is a cross-platform, open-source framework for building web apps, HTTP APIs, and real-time
services on .NET. This page gets you from an installed SDK to a running app and explains how the pieces fit
together.

== What ASP.NET Core is

ASP.NET Core runs on Windows, Linux, and macOS, is developed in the open, and unifies MVC, Web API, Razor
Pages, Blazor, SignalR, and gRPC on one HTTP server and one dependency-injection container. It is a complete
rewrite of the older .NET Framework "ASP.NET" and shares almost no API with it.

* **.NET 10 is a Long-Term Support (LTS) release** -- C# 14, released November 2025, supported for three years.
  .NET ships a major version every November: even-numbered releases (8, 10, 12) are LTS (3 years), odd-numbered
  (9, 11) are Standard-Term Support (18 months).
* Every example in this section targets **.NET 10 / C# 14** and the minimal hosting model.

See https://learn.microsoft.com/en-us/aspnet/core/introduction-to-aspnet-core[Introduction to ASP.NET Core]
and the https://dotnet.microsoft.com/platform/support/policy/dotnet-core[.NET and .NET Core Support Policy].

== The SDK and the `dotnet` CLI

Install the .NET 10 SDK, then everything else is the `dotnet` command:

[source,bash]
----
dotnet --info                       # installed SDKs and runtimes
dotnet new list                     # available templates
dotnet new web      -o Api          # empty minimal app
dotnet new webapi   -o Api          # HTTP API (Minimal API by default; --use-controllers for MVC)
dotnet new webapp   -o Site         # Razor Pages
dotnet new mvc      -o Site         # MVC
dotnet new blazor   -o App          # Blazor Web App

dotnet run                          # build + run
dotnet watch                        # run with hot reload
dotnet build -c Release             # compile
dotnet publish -c Release           # produce a deployable folder
dotnet test                         # run the test project
dotnet add package Serilog.AspNetCore
----

See the https://learn.microsoft.com/en-us/dotnet/core/tools/[`dotnet` CLI reference].

== Project layout

A new web project is small:

[source,xml]
----
<!-- Api.csproj -->
<Project Sdk="Microsoft.NET.Sdk.Web">
  <PropertyGroup>
    <TargetFramework>net10.0</TargetFramework>
    <Nullable>enable</Nullable>
    <ImplicitUsings>enable</ImplicitUsings>
  </PropertyGroup>
</Project>
----

* `Program.cs` -- the entry point and app configuration (see below).
* `appsettings.json` + `+appsettings.\{Environment}.json+` -- configuration, layered by environment.
* `Properties/launchSettings.json` -- local run profiles (URLs, environment variables); not deployed.
* `wwwroot/` -- static files served at the site root.

[source,json]
----
// appsettings.json
{
  "Logging": { "LogLevel": { "Default": "Information" } },
  "AllowedHosts": "*"
}
----

== The minimal hosting model

Modern ASP.NET Core apps have no `Startup` class. `Program.cs` uses top-level statements: build a
`WebApplication`, register services, add middleware, run.

[source,csharp]
----
var builder = WebApplication.CreateBuilder(args);

// 1. Register services in the DI container.
builder.Services.AddOpenApi();
builder.Services.AddSingleton<IGreeter, Greeter>();

var app = builder.Build();

// 2. Configure the middleware pipeline (order matters).
if (app.Environment.IsDevelopment())
{
    app.MapOpenApi();
}
app.UseHttpsRedirection();

// 3. Map endpoints.
app.MapGet("/hello/{name}", (string name, IGreeter g) => g.Greet(name));

app.Run();

public interface IGreeter { string Greet(string name); }
public sealed class Greeter : IGreeter
{
    public string Greet(string name) => $"Hello, {name}!";
}
----

`WebApplication.CreateBuilder` wires up configuration, logging, DI, and Kestrel with sensible defaults. See
https://learn.microsoft.com/en-us/aspnet/core/fundamentals/minimal-apis/[Minimal APIs overview] and
xref:web/aspnet/core/request-pipeline-and-middleware.adoc[Request pipeline and middleware].

== Choosing an app model

[cols="1,3",options="header"]
|===
| Model | Use it for

| **Minimal APIs** | New JSON/HTTP APIs; the least ceremony. xref:web/aspnet/core/minimal-apis.adoc[Details].
| **Controller-based Web API** | Larger APIs wanting conventions, filters, and `ApiController` behavior.
  xref:web/aspnet/core/web-api-controllers.adoc[Details].
| **Razor Pages** | Page-focused server-rendered sites (forms, CRUD screens).
  xref:web/aspnet/core/razor-pages.adoc[Details].
| **MVC** | Server-rendered sites that benefit from separate controllers, views, and shared layouts.
  xref:web/aspnet/core/mvc-controllers-and-views.adoc[Details].
| **Blazor** | Interactive C# UI in the browser (SPA-like). xref:web/aspnet/core/blazor-overview-and-render-modes.adoc[Details].
| **SignalR** | Server-to-client push (chat, dashboards, notifications).
  xref:web/aspnet/core/signalr.adoc[Details].
| **gRPC** | High-performance service-to-service RPC with a `.proto` contract.
  xref:web/aspnet/core/grpc.adoc[Details].
|===

See https://learn.microsoft.com/en-us/aspnet/core/fundamentals/apis[Choose between controller-based APIs and
Minimal APIs].

== Tooling and dev setup

* **IDE**: Visual Studio, VS Code with the *C# Dev Kit*, or JetBrains Rider.
* **HTTPS**: trust the local development certificate once:
+
[source,bash]
----
dotnet dev-certs https --trust
----
* .NET 10 Kestrel resolves any `+*.localhost+` host name to the loopback address, so per-app host names such as
  `https://api.localhost:7010` work with no `hosts`-file edits.

For client-side integration, ASP.NET Core hosts SPA front-ends (React, Angular, Vue) via the SPA proxy
templates, ships `LibMan` for pulling client libraries into `wwwroot`, and works with any bundler. See
xref:web/react/index.adoc[the React Reference] and xref:web/angular/index.adoc[the Angular Reference] for those
frameworks, and
https://learn.microsoft.com/en-us/aspnet/core/client-side/spa/intro[the SPA integration guide].

== Deep dive: from `dotnet run` to the first response

Understanding what the host does between process start and the first byte of a response removes most of the
mystery of an ASP.NET Core app. The Orders API used throughout this section starts like this:

[mermaid]
....
sequenceDiagram
    participant CLI as dotnet run
    participant P as Program.cs
    participant B as WebApplicationBuilder
    participant H as Host and Kestrel
    participant C as Client
    CLI->>P: start process, apply launchSettings profile
    P->>B: CreateBuilder(args) loads configuration, logging, DI
    P->>B: Services.Add... register services
    P->>H: Build() freezes the service collection
    P->>H: UseXxx / MapXxx build the pipeline and endpoint table
    P->>H: Run() starts hosted services, binds the URLs
    C->>H: GET /orders/42
    H->>H: middleware chain, routing, endpoint handler
    H-->>C: 200 JSON
....

The line order in `Program.cs` therefore has two distinct phases. Before `Build()` you only *describe* the app
(services, configuration sources); after `Build()` you configure how requests flow (middleware order, endpoints).
Registering a service after `Build()` throws, because the container has already been compiled.

=== Worked example: a first Orders endpoint, run and tested

[source,csharp]
----
// Program.cs
var builder = WebApplication.CreateBuilder(args);
builder.Services.AddSingleton<IOrderStore, InMemoryOrderStore>();

var app = builder.Build();

app.MapGet("/orders/{id:int}", (int id, IOrderStore store) =>
    store.Find(id) is { } order ? Results.Ok(order) : Results.NotFound());

app.Run();

public sealed record Order(int Id, string Customer, decimal Total);

public interface IOrderStore { Order? Find(int id); }

public sealed class InMemoryOrderStore : IOrderStore
{
    private readonly Dictionary<int, Order> _orders = new() { [42] = new Order(42, "Ada", 19.90m) };
    public Order? Find(int id) => _orders.GetValueOrDefault(id);
}

public partial class Program { }   // makes the entry point visible to the test project
----

[source,bash]
----
dotnet new web -n OrdersApi && cd OrdersApi    # then replace Program.cs with the code above
dotnet run --launch-profile http
curl -i http://localhost:5000/orders/42      # 200 with the JSON order
curl -i http://localhost:5000/orders/7       # 404
----

The port comes from `Properties/launchSettings.json`, which is read only by `dotnet run` and the IDE; in production
the URLs come from `ASPNETCORE_URLS` or Kestrel configuration. A smoke test boots the same `Program` in memory:

[source,csharp]
----
// OrdersApi.Tests.csproj references Microsoft.AspNetCore.Mvc.Testing
public sealed class SmokeTests(WebApplicationFactory<Program> factory) : IClassFixture<WebApplicationFactory<Program>>
{
    [Fact]
    public async Task Known_order_is_returned()
    {
        var client = factory.CreateClient();
        var order = await client.GetFromJsonAsync<Order>("/orders/42");
        Assert.Equal("Ada", order!.Customer);
    }

    [Fact]
    public async Task Unknown_order_is_404()
    {
        var response = await factory.CreateClient().GetAsync("/orders/7");
        Assert.Equal(HttpStatusCode.NotFound, response.StatusCode);
    }
}
----

=== Reading the generated project

* `OrdersApi.csproj` uses `Microsoft.NET.Sdk.Web`, which implicitly references the whole ASP.NET Core shared
  framework -- there are no per-feature `PackageReference` entries for MVC, Kestrel or routing.
* `<Nullable>enable</Nullable>` and `<ImplicitUsings>enable</ImplicitUsings>` explain why the sample needs no
  `using` lines. The test project uses the plain SDK, whose implicit usings are smaller, so it adds
  `using System.Net;`, `using System.Net.Http.Json;`, `using Microsoft.AspNetCore.Mvc.Testing;` and `using Xunit;`.
* `appsettings.Development.json` is layered over `appsettings.json` only when `ASPNETCORE_ENVIRONMENT` is
  `Development`, which `dotnet run` sets from the launch profile.

See xref:web/aspnet/core/configuration-and-options.adoc[Configuration and the Options Pattern] for how those layers
combine and xref:web/aspnet/core/testing.adoc[Testing ASP.NET Core Applications] for `WebApplicationFactory` in depth.
