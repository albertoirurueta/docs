= Blazor Routing and Navigation
:description: Blazor routing and navigation -- @page route templates and constraints, the Router component, NavigationManager, SupplyParameterFromQuery, NavLink, navigation locks, NotFoundPage, enhanced navigation, and layouts.
:keywords: Blazor routing, @page, Router, AppAssembly, AdditionalAssemblies, NavigationManager, NavigateTo, LocationChanged, SupplyParameterFromQuery, NavLink, NavLinkMatch, NavigationLock, NotFoundPage, layouts

include::partial$ai-disclaimer.adoc[]

Blazor routes URLs to components with the same `@page` mechanism regardless of render mode, and layers
client-side navigation on top of it. See
xref:web/aspnet/core/blazor-overview-and-render-modes.adoc[Blazor Overview and Render Modes] for how a routed
component's render mode is chosen.

== `@page` and route templates

[source,razor]
----
@page "/products/{Id:int}"
@page "/products/{Id:int}/{Slug?}"

@code {
    [Parameter] public int Id { get; set; }
    [Parameter] public string? Slug { get; set; }
}
----

Constraints (`:int`, `:guid`, `:bool`, ...), optional segments (`+\{Slug?}+`), and catch-alls
(`+\{*rest}+`) work the same as MVC route templates -- see xref:web/aspnet/core/routing.adoc[Routing] for the
full constraint list. A component can declare more than one `@page` directive to be reachable at multiple
URLs.

== `Router`, `AppAssembly`, and `AdditionalAssemblies`

`Routes.razor` hosts the `Router` component, which scans assemblies for `@page`-annotated components at
startup:

[source,razor]
----
<Router AppAssembly="typeof(Program).Assembly" AdditionalAssemblies="new[] { typeof(Shared.Nav).Assembly }">
    <Found Context="routeData">
        <RouteView RouteData="routeData" DefaultLayout="typeof(MainLayout)" />
        <FocusOnNavigate RouteData="routeData" Selector="h1" />
    </Found>
    <NotFound>
        <LayoutView Layout="typeof(MainLayout)">
            <p>Sorry, there's nothing at this address.</p>
        </LayoutView>
    </NotFound>
</Router>
----

`AppAssembly` is scanned by default; `AdditionalAssemblies` adds routable components shipped in a referenced
Razor class library (see
xref:web/aspnet/core/blazor-webassembly-hybrid-and-deployment.adoc[Razor class libraries]).

== `NavigationManager`

[source,razor]
----
@inject NavigationManager Nav
@implements IDisposable

<button @onclick='() => Nav.NavigateTo("/products")'>Back</button>
<button @onclick='() => Nav.NavigateTo(Nav.GetUriWithQueryParameter("page", 2))'>Next page</button>

@code {
    protected override void OnInitialized() => Nav.LocationChanged += OnLocationChanged;

    private void OnLocationChanged(object? sender, LocationChangedEventArgs e)
        => Console.WriteLine($"Navigated to {e.Location}");

    public void Dispose() => Nav.LocationChanged -= OnLocationChanged;
}
----

`NavigateTo(uri, forceLoad: true)` bypasses client-side routing for a full page reload;
`NavigateTo(uri, replace: true)` replaces the current history entry instead of pushing a new one.
`GetUriWithQueryParameter` builds a new URL with one query parameter added/changed/removed, which is the
supported way to update the query string without hand-building strings.

== `[SupplyParameterFromQuery]`

Bind a component parameter straight from a query-string value instead of reading `NavigationManager.Uri`
manually:

[source,razor]
----
@page "/products"

@code {
    [SupplyParameterFromQuery] public string? Search { get; set; }
    [SupplyParameterFromQuery(Name = "p")] public int Page { get; set; } = 1;
}
----

See https://learn.microsoft.com/en-us/aspnet/core/blazor/fundamentals/routing[ASP.NET Core Blazor routing and
navigation].

== `NavLink`

[source,razor]
----
<NavLink href="/products" Match="NavLinkMatch.All">All products</NavLink>
<NavLink href="/products" Match="NavLinkMatch.Prefix">Products section</NavLink>
----

`NavLink` renders an `<a>` and adds the `active` CSS class when the current URL matches -- `Match.All` requires
an exact match, `Match.Prefix` (the default) matches any URL that starts with `href`.

== Navigation locks

`NavigationLock` intercepts an in-app navigation attempt (and, in supporting browsers, a tab close) to confirm
unsaved changes before leaving:

[source,razor]
----
<NavigationLock OnBeforeInternalNavigation="ConfirmLeave" ConfirmExternalNavigation="true" />

@code {
    private void ConfirmLeave(LocationChangingContext ctx)
    {
        if (hasUnsavedChanges) ctx.PreventNavigation();
    }
}
----

== `NotFoundPage` and `NavigationManager.NotFound()`

.NET 10 lets a component declare it has no result for the current request, and the framework renders a
dedicated not-found page instead of the component's own markup:

[source,razor]
----
@page "/products/{Id:int}"
@inject NavigationManager Nav

@code {
    [Parameter] public int Id { get; set; }
    private ProductDto? product;

    protected override async Task OnParametersSetAsync()
    {
        product = await Products.FindAsync(Id);
        if (product is null) Nav.NotFound();
    }
}
----

[source,razor]
----
@* Routes.razor *@
<Router AppAssembly="typeof(Program).Assembly" NotFoundPage="typeof(Pages.NotFound)">
    ...
</Router>
----

This replaces routing to a hand-rolled "not found" component via `<NotFound>` for the common case of "the route
matched, but the requested entity does not exist." See
https://learn.microsoft.com/en-us/aspnet/core/blazor/fundamentals/routing[ASP.NET Core Blazor routing and
navigation].

== Enhanced navigation and form handling

As covered in xref:web/aspnet/core/blazor-overview-and-render-modes.adoc[the overview page], enhanced
navigation intercepts same-origin link clicks and form posts with JavaScript and patches the DOM instead of a
full reload -- it applies across render modes, including Static SSR, and is what makes
xref:web/aspnet/core/blazor-data-binding-forms-and-validation.adoc[SSR form posts] feel like an SPA without any
client-side interactivity. Disable it per link/form with `data-enhance-nav="false"` when a specific navigation
genuinely needs a full page load.

== Layouts and nested layouts

[source,razor]
----
@* MainLayout.razor *@
@inherits LayoutComponentBase
<div class="page">
    <nav>...</nav>
    <main>@Body</main>
</div>
----

[source,razor]
----
@page "/admin/users"
@layout AdminLayout      @* nests inside whatever layout AdminLayout itself declares *@
----

A layout is a component implementing `LayoutComponentBase`, rendering `@Body` where the routed component goes;
`@layout` on a page (or `DefaultLayout` on `RouteView`) selects it, and layouts can nest by one layout's `@Body`
containing another `RouteView`-rendered layout. See
https://learn.microsoft.com/en-us/aspnet/core/blazor/components/layouts[ASP.NET Core Blazor layouts].

== Deep dive: a product list whose state lives in the URL

A filter, a sort order and a page number are navigation state: users expect Back to undo a filter change, a
reload to keep it, and a copied link to reproduce it. Making the URL the single source of truth gives all three for
free, and it simplifies the component because there is only one way state can change -- navigation.

[mermaid]
....
flowchart TD
    A[User picks category Tools] --> B[NavigationManager.NavigateTo with new query string]
    B --> C[Router matches the same page, URL changes]
    C --> D[SupplyParameterFromQuery sets Category and Page]
    D --> E[OnParametersSetAsync]
    E --> F[Load products for the URL state]
    F --> G[Render list and pager]
    H[Browser Back or a pasted link] --> C
....

[source,razor]
----
@page "/products"
@inject NavigationManager Nav
@inject IProductService Products

<label>
    Category
    <select value="@Category" @onchange="OnCategoryChanged">
        <option value="">All</option>
        <option value="tools">Tools</option>
        <option value="toys">Toys</option>
    </select>
</label>

@if (result is null)
{
    <p>Loading...</p>
}
else
{
    <ul>
        @foreach (var p in result.Items)
        {
            <li @key="p.Id">@p.Name</li>
        }
    </ul>

    <nav>
        @if (CurrentPage > 1)
        {
            <NavLink href="@PageUri(CurrentPage - 1)">Previous</NavLink>
        }
        @if (result.HasMore)
        {
            <NavLink href="@PageUri(CurrentPage + 1)">Next</NavLink>
        }
    </nav>
}

@code {
    [SupplyParameterFromQuery] public string? Category { get; set; }
    [SupplyParameterFromQuery] public int? Page { get; set; }

    private PagedResult<ProductDto>? result;
    private int CurrentPage => Page is > 0 ? Page.Value : 1;

    protected override async Task OnParametersSetAsync()
    {
        result = null;
        result = await Products.SearchAsync(Category, CurrentPage);   // runs again for every URL change
    }

    private void OnCategoryChanged(ChangeEventArgs e) =>
        Nav.NavigateTo(Nav.GetUriWithQueryParameters(new Dictionary<string, object?>
        {
            ["Category"] = string.IsNullOrEmpty((string?)e.Value) ? null : (string?)e.Value,
            ["Page"] = null                      // a new filter starts at page 1; null removes the parameter
        }));

    private string PageUri(int page) =>
        Nav.GetUriWithQueryParameters(new Dictionary<string, object?> { ["Page"] = page });
}

public sealed record PagedResult<T>(IReadOnlyList<T> Items, bool HasMore);
----

`GetUriWithQueryParameters` starts from the *current* URI, so unrelated parameters (such as `Category` while the pager
changes `Page`) are preserved, and a `null` value removes a parameter. Because the page component stays the same
while only the query string changes, the Router reuses the instance and calls `OnParametersSetAsync` again, not
`OnInitializedAsync`; loading in `OnInitializedAsync` would be the classic bug of a filter that changes the URL but
not the list.

=== Redirecting and replacing history

A filter change that is a refinement, like typing in a search box, should not add a history entry per keystroke.
`NavigateTo(uri, replace: true)` replaces the current entry instead of pushing a new one:

[source,csharp]
----
Nav.NavigateTo(Nav.GetUriWithQueryParameter("q", text), replace: true);
----

=== Route constraints and what a bad URL does

A template such as `+/products/{Id:int}+` matches only integer segments, so `/products/abc` falls through to the
router's not-found handling rather than reaching the component with a failed parse. Use constraints (`:int`, `:guid`,
`:datetime`, `:min(1)`) to keep invalid URLs out of component code, and give optional or catch-all segments an
explicit meaning:

[source,razor]
----
@page "/products/{Id:int}"
@page "/products/{Id:int}/{Slug?}"          @* the slug is cosmetic: /products/7 and /products/7/widget are the same page *@
@page "/docs/{*path}"                       @* catch-all: path receives the rest of the URL, slashes included *@
----

When the optional slug is present but wrong (the product was renamed), redirect to the canonical URL so search
engines and bookmarks converge on one address.

=== Testing navigation

bUnit provides a fake `NavigationManager` that records navigations, so the filter behavior is testable without a
browser:

[source,csharp]
----
var nav = Services.GetRequiredService<FakeNavigationManager>();
var cut = RenderComponent<ProductListPage>();

cut.Find("select").Change("tools");

Assert.EndsWith("/products?Category=tools", nav.Uri);
----
