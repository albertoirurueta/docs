= Globalization and Localization
:description: Localizing ASP.NET Core apps -- IStringLocalizer/IViewLocalizer, .resx conventions, RequestLocalizationMiddleware and culture providers, route/query/cookie culture selection, data annotations localization, and Blazor localization.
:keywords: IStringLocalizer, IViewLocalizer, resx, RequestLocalizationMiddleware, IRequestCultureProvider, culture, CultureInfo, DataAnnotations localization, Blazor localization

include::partial$ai-disclaimer.adoc[]

Globalization is formatting dates, numbers, and currency for a culture; localization is translating an app's
own text into that culture's language. ASP.NET Core supports both through `IStringLocalizer` and the request
localization middleware.

== `IStringLocalizer` and `IViewLocalizer`

[source,csharp]
----
builder.Services.AddLocalization(o => o.ResourcesPath = "Resources");
builder.Services.AddControllersWithViews().AddViewLocalization();
----

[source,csharp]
----
public sealed class ProductsController(IStringLocalizer<ProductsController> localizer) : Controller
{
    public IActionResult Index()
    {
        ViewData["Title"] = localizer["ProductsTitle"];
        return View();
    }
}
----

[source,cshtml]
----
@inject IViewLocalizer Localizer
<h1>@Localizer["Welcome"]</h1>
----

`IStringLocalizer<T>` resolves strings scoped to the resource file of type `T`; `IViewLocalizer` is the equivalent
for a Razor view, scoped by the view's own path. Both fall back to the requested key itself (in square brackets
during development, depending on configuration) when no translation exists, making a missing translation
visible rather than silently blank. See
https://learn.microsoft.com/en-us/aspnet/core/fundamentals/localization[Globalization and localization in
ASP.NET Core].

== `.resx` conventions

[source,text]
----
Resources/
  Controllers.ProductsController.es.resx     # matches IStringLocalizer<ProductsController>
  Views.Products.Index.es.resx                # matches a Razor view under Views/Products/Index.cshtml
----

A `.resx` file with no culture suffix (`ProductsController.resx`) is the fallback/neutral resource; one per
supported culture (`.es.resx`, `.fr.resx`, ...) overrides it. The file's path mirrors the type's or view's
namespace/folder path under the configured `ResourcesPath`, which is how `IStringLocalizer<T>` finds the right
file without explicit registration per type.

== `RequestLocalizationMiddleware` and culture providers

[source,csharp]
----
var supportedCultures = new[] { "en", "es", "fr" };
app.UseRequestLocalization(new RequestLocalizationOptions()
    .SetDefaultCulture(supportedCultures[0])
    .AddSupportedCultures(supportedCultures)
    .AddSupportedUICultures(supportedCultures));
----

The middleware determines the current request's culture by asking a chain of ``IRequestCultureProvider``s, in
order, and uses the first one that returns a supported culture:

[cols="1,3",options="header"]
|===
| Provider (default order) | Reads the culture from

| `QueryStringRequestCultureProvider` | `?culture=es&ui-culture=es` query parameters -- useful for testing,
  rarely for production.
| `CookieRequestCultureProvider` | A cookie (`.AspNetCore.Culture`) set once the user picks a language.
| `AcceptLanguageHeaderRequestCultureProvider` | The browser's `Accept-Language` header -- the usual default
  for a first-time visitor.
|===

Add a **route** provider (reading `/es/products` style URLs) by inserting a custom `IRequestCultureProvider`
ahead of the defaults when the app needs the culture visible in the URL itself, e.g. for SEO.

[source,csharp]
----
// persist the user's explicit choice as the cookie provider reads
Response.Cookies.Append(
    CookieRequestCultureProvider.DefaultCookieName,
    CookieRequestCultureProvider.MakeCookieValue(new RequestCulture("es")));
----

`UseRequestLocalization` must run early in the pipeline (before anything that reads the current culture) --
see xref:web/aspnet/core/request-pipeline-and-middleware.adoc[Request Pipeline and Middleware] for the general
ordering rules. See
https://learn.microsoft.com/en-us/aspnet/core/fundamentals/localization#localization-middleware[Localization
middleware].

== Data annotations localization

Validation messages from `DataAnnotations` (see
xref:web/aspnet/core/model-binding-and-validation.adoc[Model Binding and Validation]) are localized the same
way as any other string, through `IStringLocalizer<T>` resolved for the model's own type:

[source,csharp]
----
builder.Services.AddControllersWithViews()
    .AddDataAnnotationsLocalization();
----

[source,csharp]
----
public sealed class ProductInput
{
    [Required(ErrorMessage = "NameRequired")]   // looked up in ProductInput.{culture}.resx
    public string Name { get; set; } = "";
}
----

== Blazor localization

Blazor components inject `IStringLocalizer<T>` exactly like an MVC controller, but culture selection works
differently per xref:web/aspnet/core/blazor-overview-and-render-modes.adoc[render mode]:

[source,razor]
----
@inject IStringLocalizer<Counter> Localizer
<p>@Localizer["ClickedTimes", count]</p>
----

* **Static SSR / Interactive Server** -- the culture is resolved the same way as any other request, via
  `RequestLocalizationMiddleware`, and stays fixed for the circuit's lifetime once the interactive connection
  starts (changing it typically requires a full reload/redirect so a fresh circuit picks up the new cookie).
* **Interactive WebAssembly / standalone WASM** -- there is no server-side middleware pipeline per request;
  the app sets `CultureInfo.DefaultThreadCurrentCulture`/`CurrentUICulture` explicitly at startup, typically
  from a value persisted in browser storage (see xref:web/aspnet/core/blazor-state-management.adoc[Blazor
  State Management]) or the browser's own locale.

See https://learn.microsoft.com/en-us/aspnet/core/blazor/globalization-localization[ASP.NET Core Blazor
globalization and localization].

== Deep dive: a localized Orders confirmation

A localization setup has two independent questions. *Which culture does this request use?* is answered by the
request localization middleware. *What does that culture change?* is answered by two properties of the current
thread: `CurrentCulture` drives formatting (numbers, currency, dates) and `CurrentUICulture` drives which resource
file `IStringLocalizer` reads.

[mermaid]
....
sequenceDiagram
    participant B as Browser
    participant M as RequestLocalizationMiddleware
    participant P as Providers in order
    participant E as Endpoint
    B->>M: GET /orders/42/confirmation with Accept-Language es-ES
    M->>P: QueryString culture parameter?
    P-->>M: none
    M->>P: Cookie .AspNetCore.Culture?
    P-->>M: none
    M->>P: Accept-Language header?
    P-->>M: es-ES, supported
    M->>E: set CurrentCulture and CurrentUICulture to es-ES
    E-->>B: Spanish text, Spanish number and date formats
....

=== Worked example: configuring cultures and a switcher

[source,csharp]
----
using System.Globalization;
using Microsoft.AspNetCore.Localization;

string[] supported = ["en-US", "es-ES", "fr-FR"];

builder.Services.AddLocalization(o => o.ResourcesPath = "Resources");

var app = builder.Build();

app.UseRequestLocalization(o => o
    .SetDefaultCulture("en-US")
    .AddSupportedCultures(supported)         // formatting
    .AddSupportedUICultures(supported));     // resource lookup

// a "language switcher" endpoint: remember the choice in a cookie, then go back
app.MapGet("/culture/{name}", (string name, string? returnUrl, HttpContext http) =>
{
    if (!supported.Contains(name)) return Results.BadRequest();

    http.Response.Cookies.Append(
        CookieRequestCultureProvider.DefaultCookieName,
        CookieRequestCultureProvider.MakeCookieValue(new RequestCulture(name)),
        new CookieOptions { Expires = DateTimeOffset.UtcNow.AddYears(1), IsEssential = true });

    return Results.LocalRedirect(string.IsNullOrEmpty(returnUrl) ? "/" : returnUrl);   // local URLs only
});
----

The confirmation endpoint uses the localizer for text with a placeholder and the current culture for the amount and
date, so translators control word order and the runtime controls separators:

[source,csharp]
----
// Resources/SharedResource.es.resx, key "OrderPlaced" =
//   "Pedido {0} realizado el {1:d} por un total de {2:C}"
app.MapGet("/orders/{id:int}/confirmation", (int id, IStringLocalizer<SharedResource> loc) =>
{
    var total = 1234567.5m;
    var when = new DateOnly(2026, 3, 9);
    return Results.Text(loc["OrderPlaced", id, when, total]);
});

public sealed class SharedResource { }          // marker type for Resources/SharedResource.es.resx
----

`IStringLocalizer` passes the arguments to `string.Format` using the current culture, so for `en-US` the amount is
formatted as `$1,234,567.50`, while the Spanish and French cultures use `.` or a space for grouping, a comma for the
decimal separator and put the currency symbol after the number. Note that the `C` format uses the culture's own
currency symbol: the *culture* does not know what currency the order was actually placed in. Store the ISO currency
code with the order and format the number with a `NumberFormatInfo` you build for that currency, or show the code
explicitly, rather than trusting the viewer's culture.

=== Dates, time zones and `DateTime.Kind`

Culture changes how a date is written, not which instant it is. Store instants in UTC (`DateTimeOffset` or UTC
`DateTime`) and convert to the user's time zone only for display; the time zone is a user setting, not something the
culture implies.

=== Testing the culture selection

Because the providers read ordinary request data, a test needs only a header:

[source,csharp]
----
var client = factory.CreateClient();
using var request = new HttpRequestMessage(HttpMethod.Get, "/orders/42/confirmation");
request.Headers.AcceptLanguage.ParseAdd("es-ES");

var body = await (await client.SendAsync(request)).Content.ReadAsStringAsync();
Assert.StartsWith("Pedido 42", body);
----

=== Pitfalls in production

* *Invariant globalization* -- `InvariantGlobalization=true` (common in trimmed and chiseled container images that omit
  the ICU libraries) makes every culture behave like the invariant culture, so the code above would silently format in
  one style. Either ship ICU or test the container image, not only the local build.
* *Missing keys* -- `IStringLocalizer` returns the key itself with `ResourceNotFound` set, so a log check on
  `loc["OrderPlaced"].ResourceNotFound` finds untranslated keys before users do.
* *Neutral versus specific cultures* -- a resource file `.es.resx` serves `es-ES` and `es-MX`; a file for `es-MX` is only
  needed when the wording really differs.
