= Data Access with EF Core
:description: Using Entity Framework Core in ASP.NET Core -- registering a DbContext, querying and change tracking, saving and concurrency, modelling with the Fluent API, migrations, resiliency, and Dapper as an alternative.
:keywords: EF Core, DbContext, AddDbContext, AddDbContextPool, AddDbContextFactory, LINQ, AsNoTracking, Include, SaveChangesAsync, concurrency token, Fluent API, migrations, dotnet ef, Dapper

include::partial$ai-disclaimer.adoc[]

Entity Framework Core is the default object-relational mapper for .NET: you model tables as classes, query
with LINQ, and persist changes through a `DbContext`. This page covers using it from an ASP.NET Core app; for
SQL itself see xref:database/sql/index.adoc[the SQL Reference].

== Registering a context

[source,csharp]
----
builder.Services.AddDbContext<AppDbContext>(o =>
    o.UseSqlServer(builder.Configuration.GetConnectionString("Default")));
----

[cols="1,3",options="header"]
|===
| Registration | Use when

| `AddDbContext<T>` | Standard: one scoped context per request.
| `AddDbContextPool<T>` | High-throughput APIs -- contexts are reset and reused instead of re-created.
| `AddDbContextFactory<T>` | Blazor, background services, or anywhere you need to create contexts on demand
  outside a request scope.
|===

[source,json]
----
{ "ConnectionStrings": { "Default": "Server=localhost;Database=shop;Trusted_Connection=True;Encrypt=False" } }
----

Provider packages: `Microsoft.EntityFrameworkCore.SqlServer`, `.Sqlite`, and `Npgsql.EntityFrameworkCore.PostgreSQL`.
See https://learn.microsoft.com/en-us/ef/core/[Entity Framework Core] and
https://learn.microsoft.com/en-us/aspnet/core/data/ef-mvc/intro[EF Core with ASP.NET Core].

== Querying

[source,csharp]
----
public sealed class AppDbContext(DbContextOptions<AppDbContext> options) : DbContext(options)
{
    public DbSet<Product> Products => Set<Product>();
    public DbSet<Order> Orders => Set<Order>();
}

// read-only query: skip change tracking, project to a DTO
var results = await db.Products
    .AsNoTracking()
    .Where(p => p.Price < 100)
    .OrderBy(p => p.Name)
    .Select(p => new ProductListItem(p.Id, p.Name, p.Price))
    .ToListAsync(ct);

// related data
var order = await db.Orders
    .Include(o => o.Lines).ThenInclude(l => l.Product)
    .FirstOrDefaultAsync(o => o.Id == id, ct);
----

Tracked entities (the default) let EF detect changes on `SaveChanges`; `AsNoTracking` is faster for reads you
will not modify. Prefer `Include` (eager) or explicit loading; avoid lazy loading in web apps (it hides N+1
queries).

== Saving and concurrency

[source,csharp]
----
db.Products.Add(new Product { Name = "Widget", Price = 9.99m });
product.Price = 12.50m;                 // tracked change
db.Orders.Remove(order);
await db.SaveChangesAsync(ct);          // one transaction
----

The `DbContext` is the unit of work -- all pending changes flush together. Add a concurrency token so a stale
update fails instead of silently overwriting:

[source,csharp]
----
public sealed class Product
{
    public int Id { get; set; }
    public string Name { get; set; } = "";
    public decimal Price { get; set; }
    [Timestamp] public byte[]? RowVersion { get; set; }   // or .IsRowVersion() in the Fluent API
}

try { await db.SaveChangesAsync(ct); }
catch (DbUpdateConcurrencyException) { /* reload, merge, retry or surface a 409 */ }
----

== Modelling

Conventions cover most mappings; data annotations (`[Table]`, `[Column]`, `[MaxLength]`, `[Required]`) or the
Fluent API in `OnModelCreating` handle the rest:

[source,csharp]
----
protected override void OnModelCreating(ModelBuilder b)
{
    b.Entity<Order>(e =>
    {
        e.HasMany(o => o.Lines).WithOne(l => l.Order).OnDelete(DeleteBehavior.Cascade);
        e.Property(o => o.Status).HasConversion<string>();          // value converter
        e.OwnsOne(o => o.ShippingAddress);                          // owned type
        e.HasIndex(o => o.Customer);
    });
}
----

See https://learn.microsoft.com/en-us/ef/core/dbcontext-configuration/[DbContext configuration and
initialization].

== Migrations

[source,bash]
----
dotnet tool install --global dotnet-ef
dotnet ef migrations add AddOrders
dotnet ef database update                 # apply to the dev database
dotnet ef migrations script -o out.sql    # generate SQL for a release pipeline
dotnet ef dbcontext scaffold "Server=...;Database=..." Microsoft.EntityFrameworkCore.SqlServer  # database-first
----

Apply migrations from a pipeline or an idempotent script in production rather than calling
`db.Database.Migrate()` at startup (which races when several instances start together). See
https://learn.microsoft.com/en-us/ef/core/managing-schemas/migrations/[Migrations overview].

== Resiliency, the repository debate, and Dapper

* **Connection resiliency**: `+o.UseSqlServer(cs, sql => sql.EnableRetryOnFailure())+` retries transient
  failures.
* **See the SQL**: `o.LogTo(Console.WriteLine, LogLevel.Information)` or EF Core's built-in logging category.
* **Repository / unit-of-work**: `DbContext` already *is* both. A repository layer still helps when you want to
  hide LINQ from the domain, standardise queries, or swap persistence in tests -- otherwise it is indirection
  for its own sake.
* **Dapper** is a thin micro-ORM for hot paths or complex SQL:
+
[source,csharp]
----
using var conn = new SqlConnection(cs);
var rows = await conn.QueryAsync<ProductListItem>(
    "SELECT Id, Name, Price FROM Products WHERE Price < @max", new { max = 100 });
----

Cross-link: xref:database/sql/index.adoc[SQL Reference].

== Deep dive: the change tracker and placing an order safely

`SaveChangesAsync` does not diff your objects against the database; it consults the *change tracker*, which keeps
one entry per tracked entity with a state. Every operation moves entries between states, and `SaveChanges` turns the
non-`Unchanged` states into `INSERT`, `UPDATE` and `DELETE` statements.

[mermaid]
....
stateDiagram-v2
    [*] --> Detached
    Detached --> Added: Add
    Detached --> Unchanged: Attach or query with tracking
    Unchanged --> Modified: property changed
    Unchanged --> Deleted: Remove
    Added --> Unchanged: SaveChanges
    Modified --> Unchanged: SaveChanges
    Deleted --> Detached: SaveChanges
....

A query with `AsNoTracking()` never creates entries, which is why it is faster and why modifying its results has no
effect on the database. Tracking queries also give *identity resolution*: loading the same product twice in one
context returns the same instance.

=== Worked example: reserving stock when an order is placed

Placing an order must decrement stock without overselling when two customers buy the last item. Two techniques solve
this: optimistic concurrency (detect and retry) and an atomic conditional update (avoid the race entirely).

[source,csharp]
----
public sealed class Product
{
    public int Id { get; set; }
    public string Name { get; set; } = "";
    public int Stock { get; set; }
    [Timestamp] public byte[]? RowVersion { get; set; }
}

public sealed class OrderPlacement(AppDbContext db)
{
    // Option 1: atomic, one round trip, no tracking and no concurrency exception
    public async Task<bool> TryReserveAsync(int productId, int quantity, CancellationToken ct)
    {
        var affected = await db.Products
            .Where(p => p.Id == productId && p.Stock >= quantity)
            .ExecuteUpdateAsync(s => s.SetProperty(p => p.Stock, p => p.Stock - quantity), ct);
        return affected == 1;                       // 0 rows: product missing or not enough stock
    }

    // Option 2: load, change, save; the RowVersion check turns a lost update into an exception
    public async Task<bool> ReserveWithRetryAsync(int productId, int quantity, CancellationToken ct)
    {
        for (var attempt = 0; attempt < 3; attempt++)
        {
            var product = await db.Products.SingleAsync(p => p.Id == productId, ct);
            if (product.Stock < quantity) return false;
            product.Stock -= quantity;
            try
            {
                await db.SaveChangesAsync(ct);
                return true;
            }
            catch (DbUpdateConcurrencyException e)
            {
                e.Entries.Single().Reload();        // refresh with the winner's values, then retry
            }
        }
        return false;
    }
}
----

When the order and the stock change must commit together, wrap both in a transaction. With
`EnableRetryOnFailure` the provider's execution strategy re-runs the whole delegate on a transient error, so a
user-started transaction has to live *inside* it:

[source,csharp]
----
var strategy = db.Database.CreateExecutionStrategy();
await strategy.ExecuteAsync(async () =>
{
    await using var tx = await db.Database.BeginTransactionAsync(ct);
    if (!await placement.TryReserveAsync(productId, quantity, ct))
        throw new InvalidOperationException("Out of stock");
    db.Orders.Add(order);
    await db.SaveChangesAsync(ct);
    await tx.CommitAsync(ct);
});
----

=== Query shape: the N+1 trap and split queries

Looping over orders and touching `order.Lines` in each iteration issues one query per order when lazy loading is on.
Prefer an explicit `Include` or, better, a projection that selects only what the response needs. A collection
`Include` produces a join that repeats the parent columns for every child row; `AsSplitQuery()` sends one query per
collection instead, trading a round trip for less duplicated data:

[source,csharp]
----
var orders = await db.Orders
    .AsNoTracking()
    .AsSplitQuery()
    .Include(o => o.Lines)
    .Where(o => o.CustomerId == customerId)
    .ToListAsync(ct);
----

=== Testing with SQLite in memory

The EF Core in-memory provider does not enforce constraints or concurrency tokens. SQLite in memory is closer to a
relational database and still runs in milliseconds; the connection must stay open or the database vanishes:

[source,csharp]
----
await using var connection = new SqliteConnection("DataSource=:memory:");
await connection.OpenAsync();

var options = new DbContextOptionsBuilder<AppDbContext>().UseSqlite(connection).Options;
await using (var setup = new AppDbContext(options))
{
    await setup.Database.EnsureCreatedAsync();
    setup.Products.Add(new Product { Name = "Widget", Stock = 1 });
    await setup.SaveChangesAsync();
}

await using var db = new AppDbContext(options);
var placement = new OrderPlacement(db);
Assert.True(await placement.TryReserveAsync(1, 1, CancellationToken.None));
Assert.False(await placement.TryReserveAsync(1, 1, CancellationToken.None));   // the last unit is gone
----

SQLite does not generate row versions (a `[Timestamp]` property stays `null`), so the concurrency-token path of
`ReserveWithRetryAsync` cannot be exercised there. Keep a small set of integration tests against the real engine, for
example in a container, for concurrency-sensitive code.
