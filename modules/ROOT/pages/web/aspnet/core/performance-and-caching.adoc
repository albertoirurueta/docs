Most ASP.NET Core performance work is caching what is expensive to recompute, limiting abusive load, and being

== Response caching vs. output caching

[cols="1,3",options="header"]
|===
| | Where the copy lives

| **Response caching** (`[ResponseCache]`, `UseResponseCaching`) | The client and intermediary proxies, driven
  by HTTP `Cache-Control` / `Vary` headers. You do not control eviction.
| **Output caching** (`AddOutputCache`, `UseOutputCache`) | On your server, in memory or a distributed store.
  You control policies, tags, and eviction.
|===

[source,csharp]
----
builder.Services.AddOutputCache(o =>
{
    o.AddBasePolicy(b => b.Expire(TimeSpan.FromSeconds(30)));
    o.AddPolicy("ByTenant", b => b.SetVaryByQuery("tenant").Tag("catalog").Expire(TimeSpan.FromMinutes(5)));
});

app.UseOutputCache();

app.MapGet("/catalog", GetCatalog).CacheOutput("ByTenant");

// invalidate on write
app.MapPost("/catalog", async (IOutputCacheStore cache, CancellationToken ct) =>
{
    await cache.EvictByTagAsync("catalog", ct);
    return Results.Ok();
});
----

Output caching is auth-aware (it will not serve one user's response to another). The `<cache>` tag helper caches
view fragments. See
https://learn.microsoft.com/en-us/aspnet/core/performance/caching/output[Output caching middleware].

== In-process, distributed, and hybrid caches

`AddStackExchangeRedisCache` backs `IDistributedCache` with Redis; see the
xref:database/redis/use-cases-and-patterns.adoc[Redis Use Cases & Patterns] page for that caching pattern in
depth.

[source,csharp]
----
// IMemoryCache -- single server
var products = await memoryCache.GetOrCreateAsync("products", entry =>
{
    entry.AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(2);
    entry.Size = 1;
    return LoadProductsAsync();
});

// IDistributedCache -- shared across servers (Redis / SQL Server)
builder.Services.AddStackExchangeRedisCache(o => o.Configuration = redisConnString);

// HybridCache (.NET 9+) -- L1 in-memory + L2 distributed, stampede protection, tag invalidation
builder.Services.AddHybridCache();
var value = await hybridCache.GetOrCreateAsync($"product:{id}", ct => LoadAsync(id, ct),
    tags: ["product"]);
----

See https://learn.microsoft.com/en-us/aspnet/core/performance/caching/hybrid[HybridCache in ASP.NET Core].

== Rate limiting

[source,csharp]
----
builder.Services.AddRateLimiter(o =>
{
    o.RejectionStatusCode = StatusCodes.Status429TooManyRequests;
    o.AddFixedWindowLimiter("api", opt => { opt.Window = TimeSpan.FromSeconds(10); opt.PermitLimit = 100; });
    o.AddPolicy("per-user", ctx => RateLimitPartition.GetTokenBucketLimiter(
        ctx.User.Identity?.Name ?? "anon",
        _ => new TokenBucketRateLimiterOptions { TokenLimit = 50, TokensPerPeriod = 10,
            ReplenishmentPeriod = TimeSpan.FromSeconds(1) }));
    o.OnRejected = (ctx, _) => { ctx.HttpContext.Response.Headers.RetryAfter = "10"; return ValueTask.CompletedTask; };
});

app.UseRateLimiter();
app.MapGet("/search", Search).RequireRateLimiting("api");
----

Limiter algorithms: fixed window, sliding window, token bucket, and concurrency. See
https://learn.microsoft.com/en-us/aspnet/core/performance/rate-limit[Rate limiting middleware].

== Timeouts, compression, and pooling

[source,csharp]
----
builder.Services.AddRequestTimeouts(o => o.DefaultPolicy = new() { Timeout = TimeSpan.FromSeconds(30) });
app.UseRequestTimeouts();
app.MapGet("/report", SlowReport).WithRequestTimeout(TimeSpan.FromMinutes(2));

builder.Services.AddResponseCompression(o => o.EnableForHttps = true);
app.UseResponseCompression();
----

Reuse buffers with `ObjectPool<T>`, `ArrayPool<T>.Shared`, and `RecyclableMemoryStreamManager` to cut GC
pressure on hot paths.

== EF Core and runtime checklist

* EF Core: `AddDbContextPool`, `AsNoTracking` for reads, `AsSplitQuery` for wide ``Include``s, compiled queries
  for hot queries, and watch for N+1 (log the SQL).
* Be **async all the way** -- never block on `.Result` / `.Wait()`.
* Server GC (`<ServerGarbageCollection>true</ServerGarbageCollection>`) for throughput.
* Tune Kestrel limits for your workload.
* **ReadyToRun** and **trimming** cut startup and size; **Native AOT** (Minimal APIs) removes JIT and slashes
  memory and cold-start.

See
https://learn.microsoft.com/en-us/aspnet/core/fundamentals/best-practices[ASP.NET Core performance best
practices].

== Deep dive: protecting a hot catalog endpoint

The catalog endpoint is read thousands of times per minute and written a few times per hour, the textbook case for
caching. Done naively, two problems appear: a *cache stampede* when a popular entry expires and every concurrent
request recomputes it, and *unbounded clients* that bypass the cache's benefit by hammering unique URLs. The example
layers a `HybridCache` for the data with a rate limiter in front.

=== Stampede-safe reads with `HybridCache`

With a plain `IMemoryCache`, `GetOrCreateAsync` does not stop two concurrent callers from both running the factory
(the factory is not locked). `HybridCache` does: for a given key, concurrent callers on one process share a single
factory execution, and the result is stored in a fast in-process layer (L1) and, if configured, a distributed layer
(L2) so other servers can reuse it.

[source,csharp]
----
using Microsoft.Extensions.Caching.Hybrid;

public sealed class CatalogService(HybridCache cache, ICatalogRepository repo)
{
    private static readonly HybridCacheEntryOptions Options = new()
    {
        Expiration = TimeSpan.FromMinutes(5),               // L2 lifetime
        LocalCacheExpiration = TimeSpan.FromMinutes(1),     // L1 lifetime: bounds how stale one server can be
    };

    public ValueTask<ProductDto?> GetAsync(int id, CancellationToken ct = default)
        => cache.GetOrCreateAsync(
            $"product:{id}",
            async token => await repo.FindAsync(id, token),   // runs once per key, not once per request
            Options,
            tags: ["product", $"product:{id}"],
            cancellationToken: ct);

    public async Task UpdateAsync(int id, ProductDto dto, CancellationToken ct = default)
    {
        await repo.SaveAsync(id, dto, ct);
        await cache.RemoveByTagAsync($"product:{id}", ct);    // next read repopulates
    }
}

// Program.cs
builder.Services.AddHybridCache();
builder.Services.AddStackExchangeRedisCache(o => o.Configuration = builder.Configuration.GetConnectionString("redis"));
----

When an `IDistributedCache` implementation such as Redis is registered, `HybridCache` uses it automatically as L2;
without one it is an in-process cache with stampede protection. The two expirations are a staleness budget: a write
on server A evicts by tag in both layers, but server B's L1 entry survives until `LocalCacheExpiration`, so keep it
short when readers must see updates quickly.

    L2 -- no --> DB["Run factory: query database"]

=== A limiter per client, with an honest `Retry-After`

A global fixed window punishes everyone for one client's burst. Partitioning gives each client its own budget:

[source,csharp]
----
using System.Globalization;
using System.Threading.RateLimiting;

builder.Services.AddRateLimiter(o =>
{
    o.RejectionStatusCode = StatusCodes.Status429TooManyRequests;

    o.GlobalLimiter = PartitionedRateLimiter.Create<HttpContext, string>(ctx =>
        RateLimitPartition.GetSlidingWindowLimiter(
            partitionKey: ctx.User.Identity?.Name ?? ctx.Connection.RemoteIpAddress?.ToString() ?? "unknown",
            factory: _ => new SlidingWindowRateLimiterOptions
            {
                PermitLimit = 120,
                Window = TimeSpan.FromMinutes(1),
                SegmentsPerWindow = 6,                 // smooths the edge of a fixed window
                QueueLimit = 0,
            }));

    o.OnRejected = (context, _) =>
    {
        if (context.Lease.TryGetMetadata(MetadataName.RetryAfter, out var retryAfter))
            context.HttpContext.Response.Headers.RetryAfter =
                ((int)retryAfter.TotalSeconds).ToString(CultureInfo.InvariantCulture);
        return ValueTask.CompletedTask;
    };
});

app.UseRateLimiter();         // after UseRouting so endpoint-specific policies are visible
----

Behind a reverse proxy, `RemoteIpAddress` is the proxy unless forwarded-headers processing is enabled first (see
xref:web/aspnet/core/hosting-servers-and-environments.adoc[Hosting, Servers, and Environments]); otherwise all
clients share one partition. The partition table above lives in process memory, so with several instances each
enforces its own limit. A shared limit needs a gateway or a store-backed limiter.

=== Measure before tuning

Caching hides cost rather than removing it, so confirm the gain. A quick, repeatable check with `curl` shows the
`Age`/timing difference between a cold and warm request, and `dotnet-counters monitor` shows the hit effect on
allocation and request rate while a load tool runs:

[source,bash]
----
curl -s -o /dev/null -w "cold: %{time_total}s\n" http://localhost:5000/catalog/42
curl -s -o /dev/null -w "warm: %{time_total}s\n" http://localhost:5000/catalog/42
dotnet-counters monitor --process-id <pid> --counters Microsoft.AspNetCore.Hosting System.Runtime
----

Look for a sharp drop in time per request and in `gc-heap-size` growth once the cache is warm. If latency does not
change, the bottleneck is elsewhere (serialization, a downstream call) and caching the wrong layer will not help.
