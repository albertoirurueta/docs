This page covers how Interactive WebAssembly and standalone Blazor WebAssembly apps actually run in the
browser, how to host and deploy them, and how to reuse Blazor components outside a Blazor Web App entirely --
in a .NET MAUI shell (Blazor Hybrid) or embedded in a non-Blazor page.

== The WebAssembly runtime

A Blazor WebAssembly app downloads the .NET runtime itself (compiled to WebAssembly), the app's assemblies, and
any dependencies, then runs .NET IL in the browser with no plugin. First-load size and startup time are
dominated by how much of that gets downloaded and JIT/AOT-compiled, which is what the rest of this section
optimizes. For comparison, languages without a runtime to ship, such as Rust, compile straight to a small `.wasm`
module; see the Rust Reference's xref:programming-languages/rust/webassembly.adoc[WebAssembly].

== IL trimming and AOT compilation

**IL trimming** removes unused code from published assemblies (on by default for WebAssembly publish); **AOT
(ahead-of-time) compilation** compiles .NET IL directly to WebAssembly instead of interpreting it at runtime,
trading a larger download and slower build for substantially faster execution:

[source,xml]
----
<PropertyGroup>
  <RunAOTCompilation>true</RunAOTCompilation>   <!-- set at publish time -->
  <WasmEnableSIMD>true</WasmEnableSIMD>          <!-- vectorized instructions where the browser supports them -->
</PropertyGroup>
----

AOT roughly doubles publish time and increases download size, so it pays off for CPU-bound client-side work
more than for typical CRUD UI. **SIMD** lets AOT-compiled code use vectorized WebAssembly instructions on
supporting browsers for further speedups on numeric workloads. See
https://learn.microsoft.com/en-us/aspnet/core/blazor/host-and-deploy/webassembly/[ASP.NET Core Blazor
WebAssembly build tools and AOT] and
https://learn.microsoft.com/en-us/aspnet/core/blazor/tooling/webassembly[Ahead-of-time (AOT) compilation].

== Lazy loading of assemblies

Defer assemblies not needed for the initial page, loading them only when a route that needs them is reached:

[source,xml]
----
<ItemGroup>
  <BlazorWebAssemblyLazyLoad Include="AdminModule.wasm" />   <!-- .dll before .NET 8 -->
</ItemGroup>
----

[source,razor]
----
<Router AppAssembly="typeof(Program).Assembly" OnNavigateAsync="OnNavigateAsync">
    ...
</Router>

@code {
    private async Task OnNavigateAsync(NavigationContext ctx)
    {
        if (ctx.Path.StartsWith("admin"))
        {
            await LazyAssemblyLoader.LoadAssembliesAsync(["AdminModule.wasm"]);
        }
    }
}
----

See https://learn.microsoft.com/en-us/aspnet/core/blazor/webassembly-lazy-load-assemblies[Lazy load assemblies
in ASP.NET Core Blazor WebAssembly].

== Native dependencies

A WebAssembly app can reference native code compiled to WASM (a C/C++ library, or a .NET library with a native
component) via the .NET WebAssembly build tools' native-relinking step -- relevant mainly for
performance-critical or existing native libraries with no managed equivalent; most apps never need this.

== Fingerprinted static assets and preloaded framework assets (.NET 10)

.NET 10's static web assets pipeline (see
xref:web/aspnet/core/static-files-and-asset-delivery.adoc[Static Files and Asset Delivery]) fingerprints the
WebAssembly runtime and app assemblies themselves, not just `wwwroot` content, so a browser caches them
indefinitely and only re-downloads what actually changed between deployments. The generated `index.html`
preloads the framework assets it knows it will need, reducing the number of sequential round trips before the
app becomes interactive.

== Boot config

`blazor.boot.json` (generated at publish time) lists every assembly, its integrity hash, and load-time options
the WebAssembly bootstrapper reads before starting the runtime -- inspect it when diagnosing "an assembly
failed to load" issues, but it is not meant to be hand-edited.

== PWAs and service workers

`dotnet new blazorwasm --pwa` scaffolds a Progressive Web App: a manifest, a service worker
(`service-worker.published.js`) that caches the app shell for offline use, and installability on supporting
platforms. See
https://learn.microsoft.com/en-us/aspnet/core/blazor/progressive-web-app[ASP.NET Core Blazor Progressive Web
Application (PWA)].

== Hosting standalone WASM vs. hosted

[cols="1,3",options="header"]
|===
| Style | Notes

| Standalone, static host/CDN | `dotnet new blazorwasm`; publish output is static files (HTML/JS/WASM) with no
  server-side .NET at all -- host on any static file server or CDN.
| Hosted (ASP.NET Core-served) | The WebAssembly client is served by (and typically calls back into) an
  ASP.NET Core project -- the shape a Blazor Web App with WebAssembly/Auto interactivity takes.
|===

A static host needs to be configured to serve `.wasm` files with the `application/wasm` MIME type and to
rewrite unknown paths back to `index.html` for client-side routing to work on a hard refresh/deep link.

== IIS / Nginx configuration for WASM

[source,nginx]
----
location / {
    try_files $uri $uri/ /index.html;
}
location ~ \.wasm$ {
    types { application/wasm wasm; }
}
----

IIS needs the `web.config` generated at publish time (which sets the `application/wasm` MIME type and a
`web.config`-driven fallback route) deployed alongside the static output. See
xref:web/aspnet/core/deployment.adoc[Deployment] for the general IIS/Nginx hosting material this extends.

== Blazor Hybrid with .NET MAUI

**Blazor Hybrid** hosts Razor components in a native app shell instead of a browser, via the `BlazorWebView`
control, sharing the same component model and much of the same code as a web Blazor app:

[source,xml]
----
<!-- MainPage.xaml -->
<BlazorWebView HostPage="wwwroot/index.html" x:Name="blazorWebView">
    <BlazorWebView.RootComponents>
        <RootComponent Selector="#app" ComponentType="{x:Type local:Main}" />
    </BlazorWebView.RootComponents>
</BlazorWebView>
----

Components run with full trust and full .NET access (file system, native APIs via platform-specific code) --
there is no browser sandbox, so the "WebAssembly is not a trust boundary" caveat from
xref:web/aspnet/core/blazor-security.adoc[Blazor Security] does not apply the same way, but the app still runs
on the end user's device. **Native interop** goes through normal .NET MAUI platform APIs, not `IJSRuntime`,
though JS interop into the hosted web content still works for DOM-facing code. See
https://learn.microsoft.com/en-us/aspnet/core/blazor/hybrid/[ASP.NET Core Blazor Hybrid].
For the Windows desktop side (WPF, WinUI 3, MSIX packaging and distribution), see the
xref:apps/windows/index.adoc[Windows Apps] section.

== Razor class libraries

A **Razor class library (RCL)** packages components, static assets, and CSS-isolated stylesheets for reuse
across projects -- a web app, a Blazor Hybrid app, and another web app can all reference the same RCL:

[source,bash]
----
dotnet new razorclasslib -o SharedUi
dotnet add MyApp reference ../SharedUi
----

RCL components are just Razor components; an RCL exposing routable `@page` components needs its assembly added
to the host's `AdditionalAssemblies` (see
xref:web/aspnet/core/blazor-routing-and-navigation.adoc[Blazor Routing and Navigation]). See
https://learn.microsoft.com/en-us/aspnet/core/blazor/components/class-libraries[ASP.NET Core Razor class
library (RCL)].

== Adding Blazor to an existing MVC/Razor Pages/Angular/React app

Blazor components can be embedded into a page that is not itself a Blazor Web App by rendering them as
**custom elements** -- each acts as a normal HTML tag the host page's own framework (or plain HTML) can drop
in:

[source,csharp]
----
builder.RootComponents.RegisterCustomElement<Counter>("my-counter");
----

[source,html]
----
<my-counter increment="5"></my-counter>
<script src="_framework/blazor.webassembly.js"></script>
----

This is the supported path for incrementally adding an interactive island to an existing MVC, Razor Pages,
Angular, or React app without a full rewrite. See
https://learn.microsoft.com/en-us/aspnet/core/blazor/components/js-spa-frameworks[Use Blazor components in
JavaScript apps or SPA frameworks] and xref:web/react/index.adoc[the React Reference] /
xref:web/angular/index.adoc[the Angular Reference] for the host-side frameworks.

== Deep dive: measuring and shrinking the Orders client

Tuning without measuring tends to optimize the wrong thing. The cost of a WebAssembly app has three parts: bytes
downloaded, time to start the runtime and run the first render, and steady-state execution speed. Trimming and lazy
loading attack the first, caching removes it on return visits, and AOT attacks the third at the cost of the first.

[mermaid]
....
flowchart LR
    A[Browser requests the page] --> B[Static host serves HTML and boot config]
    B --> C[Download dotnet.native.wasm runtime]
    B --> D[Download framework and app assemblies]
    C --> E[Start the .NET runtime]
    D --> E
    E --> F[Run Program.cs, first render]
    F --> G[User can interact]
    D -. "lazy assemblies wait for their route" .-> H[Reports module loaded on demand]
    D -. "fingerprinted files cached by hash" .-> I[Return visit skips most of the download]
....

=== Measure the published size

[source,bash]
----
dotnet publish Orders.Client -c Release -o publish
du -sh publish/wwwroot/_framework                       # raw output
ls -lS publish/wwwroot/_framework | head -15            # the largest files, including *.br and *.gz copies
----

Compare the compressed sizes (`.br`), which are what the browser downloads, not the raw ones. The runtime and the base
class library dominate; app assemblies are usually a small share, so the biggest wins come from not pulling in
heavyweight dependencies and from trimming.

=== Keep the app trim-safe

The trimmer removes code it cannot prove is used. Reflection-based serialization is the usual casualty, producing a
runtime failure only in the published build. A source-generated JSON context removes the reflection and the warning:

[source,csharp]
----
using System.Text.Json.Serialization;

[JsonSourceGenerationOptions(PropertyNamingPolicy = JsonKnownNamingPolicy.CamelCase)]
[JsonSerializable(typeof(List<OrderSummary>))]
[JsonSerializable(typeof(OrderDto))]
internal partial class AppJsonContext : JsonSerializerContext
{
}

// usage with HttpClient
var orders = await http.GetFromJsonAsync("api/orders", AppJsonContext.Default.ListOrderSummary);
----

Treat trim warnings (`IL2026`, `IL3050`) in your own code as errors during development so they appear in the build,
not in production:

[source,xml]
----
<PropertyGroup>
  <EnableTrimAnalyzer>true</EnableTrimAnalyzer>
  <TreatWarningsAsErrors Condition="'$(Configuration)' == 'Release'">true</TreatWarningsAsErrors>
</PropertyGroup>
----

=== Lazy-load a rarely used feature

The order *reports* screen pulls in a charting library that most users never open. Moving it to its own assembly and
loading that assembly on first navigation removes it from the initial download. Since .NET 8 the assemblies are
published as WebAssembly (Webcil) files, so the item uses the `.wasm` extension:

[source,xml]
----
<ItemGroup>
  <BlazorWebAssemblyLazyLoad Include="Orders.Reports.wasm" />
</ItemGroup>
----

[source,razor]
----
@* App.razor *@
@using System.Reflection
@using Microsoft.AspNetCore.Components.WebAssembly.Services
@inject LazyAssemblyLoader AssemblyLoader

<Router AppAssembly="typeof(App).Assembly"
        AdditionalAssemblies="lazyLoaded"
        OnNavigateAsync="OnNavigateAsync">
    <Navigating><p>Loading...</p></Navigating>
    <Found Context="routeData"><RouteView RouteData="routeData" DefaultLayout="typeof(MainLayout)" /></Found>
    <NotFound><p>Page not found.</p></NotFound>
</Router>

@code {
    private readonly List<Assembly> lazyLoaded = [];

    private async Task OnNavigateAsync(NavigationContext context)
    {
        if (context.Path.StartsWith("reports", StringComparison.OrdinalIgnoreCase))
        {
            var assemblies = await AssemblyLoader.LoadAssembliesAsync(["Orders.Reports.wasm"]);
            lazyLoaded.AddRange(assemblies);          // lets the router discover the @page routes inside
        }
    }
}
----

Two details are easy to miss. The loaded assemblies must be passed to `AdditionalAssemblies`, or the router never
finds the `@page` components inside them. And a lazy assembly must not be referenced by code in the initial path
(including a type used in a field of a startup component), or the runtime loads it eagerly anyway.

=== Decide about AOT with a number

AOT-compiled code runs faster but is larger. Measure the *actual* hot path before paying for it: time the operation in
a Release build with and without `RunAOTCompilation`.

[source,csharp]
----
var sw = Stopwatch.StartNew();
var totals = RecalculateOrderTotals(orders);        // the CPU-bound work, e.g. 50,000 orders
Console.WriteLine($"Recalculation took {sw.ElapsedMilliseconds} ms");
----

If the work is 20 ms either way, keep the smaller interpreted build; if it is 2 seconds interpreted and 200 ms AOT,
the larger download is justified for that screen -- or the work belongs on the server, where it need not ship to the
browser at all.

=== Caching on return visits

Fingerprinted framework files (see the fingerprinting section above) can be cached for a year because a new build
changes their names; only the small HTML shell and boot configuration need revalidation. If the host serves them with
`Cache-Control: no-cache` or without compression, the runtime download repeats on every visit and no amount of
trimming compensates, so check the response headers in the browser's network panel before blaming the bundle size.
