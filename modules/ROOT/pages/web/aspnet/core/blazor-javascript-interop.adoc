= Blazor JavaScript Interop
:description: Calling JavaScript from Blazor and back -- IJSRuntime, IJSObjectReference and JS modules, collocated JS files, [JSInvokable], DotNetObjectReference, InvokeConstructorAsync, GetValue/SetValue, synchronous WebAssembly interop, ElementReference, and prerendering.
:keywords: Blazor JavaScript interop, IJSRuntime, InvokeAsync, InvokeVoidAsync, IJSObjectReference, JS module, JSInvokable, DotNetObjectReference, InvokeConstructorAsync, IJSInProcessRuntime, ElementReference, FocusAsync

include::partial$ai-disclaimer.adoc[]

Blazor calls JavaScript for anything the .NET runtime cannot do itself -- wrapping an existing JS library, DOM
APIs with no C# equivalent, browser-only features -- through `IJSRuntime`, and JavaScript calls back into .NET
through `[JSInvokable]`.

== `IJSRuntime`

[source,razor]
----
@inject IJSRuntime JS

@code {
    private async Task CopyAsync(string text)
        => await JS.InvokeVoidAsync("navigator.clipboard.writeText", text);

    private async Task<int> GetWidthAsync()
        => await JS.InvokeAsync<int>("eval", "document.body.clientWidth");
}
----

`InvokeAsync<T>` returns a value, `InvokeVoidAsync` does not. Both are asynchronous even under Interactive
Server, where the call is a round trip over the SignalR circuit. See
https://learn.microsoft.com/en-us/aspnet/core/blazor/javascript-interoperability/[JavaScript interoperability
(JS interop)].

== `IJSObjectReference` and JS modules

Load an ES module and keep a reference to it instead of calling `eval`/global functions -- the idiomatic way to
wrap a library or a page's own script:

[source,javascript]
----
// wwwroot/js/chart.js
export function render(element, data) { /* draw the chart */ }
export function destroy(element) { /* cleanup */ }
----

[source,csharp]
----
private IJSObjectReference? module;

protected override async Task OnAfterRenderAsync(bool firstRender)
{
    if (firstRender)
    {
        module = await JS.InvokeAsync<IJSObjectReference>("import", "./js/chart.js");
        await module.InvokeVoidAsync("render", chartElement, data);
    }
}

public async ValueTask DisposeAsync()
{
    if (module is not null)
    {
        await module.InvokeVoidAsync("destroy", chartElement);
        await module.DisposeAsync();
    }
}
----

== Collocated JS

A file named `Component.razor.js` next to `Component.razor` is a JS module scoped to that component, served
automatically and loaded the same way as any other module -- no manual `wwwroot` placement needed:

[source,javascript]
----
// Chart.razor.js
export function render(element, data) { /* ... */ }
----

[source,csharp]
----
module = await JS.InvokeAsync<IJSObjectReference>("import", "./Components/Chart.razor.js");
----

See https://learn.microsoft.com/en-us/aspnet/core/blazor/javascript-interoperability/import-export-interop[JavaScript
`import`/`export` interop].

== JS to .NET: `[JSInvokable]` and `DotNetObjectReference`

[source,csharp]
----
public sealed partial class NotificationBell : IAsyncDisposable
{
    private DotNetObjectReference<NotificationBell>? selfRef;

    protected override async Task OnAfterRenderAsync(bool firstRender)
    {
        if (firstRender)
        {
            selfRef = DotNetObjectReference.Create(this);
            await JS.InvokeVoidAsync("notifications.subscribe", selfRef);
        }
    }

    [JSInvokable]
    public void OnNotificationReceived(string message)
    {
        latest = message;
        StateHasChanged();
    }

    public ValueTask DisposeAsync()
    {
        selfRef?.Dispose();
        return ValueTask.CompletedTask;
    }
}
----

`[JSInvokable]` marks an **instance** method callable via a `DotNetObjectReference`, or a **static** method
callable globally via `+DotNet.invokeMethodAsync("AssemblyName", "MethodName", ...)+` from JS with no reference
needed. Always dispose a `DotNetObjectReference` -- it pins the .NET object alive for JS to call back into.

== `InvokeConstructorAsync`, `GetValue`/`SetValue` (.NET 10)

.NET 10 adds first-class support for constructing a JS object and reading/writing its members without a
hand-written wrapper function:

[source,csharp]
----
var mapRef = await JS.InvokeConstructorAsync<IJSObjectReference>("L.Map", containerElement);
await mapRef.SetValueAsync("zoom", 12);
var currentZoom = await mapRef.GetValueAsync<int>("zoom");
----

Previously this required a small JS shim (`+export function createMap(el) { return new L.Map(el); }+`) for every
constructor or property access; these APIs cover the common case directly.

== Synchronous interop in WebAssembly

Interactive WebAssembly runs in the same browser tab as the JS it calls, so it can skip the async round trip
where startup latency matters:

[source,csharp]
----
@inject IJSInProcessRuntime JS

private int GetWidth() => JS.Invoke<int>("eval", "document.body.clientWidth");
----

`IJSInProcessRuntime` is available only under Interactive WebAssembly -- injecting it under Interactive Server
throws, since there is no synchronous path over a network connection.

== `ElementReference` and `FocusAsync`

Capture a reference to a rendered DOM element with `@ref` to pass it into JS interop calls, or use the built-in
`FocusAsync` extension for the common case of moving keyboard focus without any custom JS:

[source,razor]
----
<input @ref="searchBox" />

@code {
    private ElementReference searchBox;
    protected override async Task OnAfterRenderAsync(bool firstRender)
    {
        if (firstRender) await searchBox.FocusAsync();
    }
}
----

== Wrapping an existing JS library

The pattern is consistent regardless of the library: write a small JS module exposing the operations the
component needs, `import` it once, keep the `IJSObjectReference`, and dispose it (and the underlying JS object,
if the library needs explicit teardown) in `DisposeAsync` -- exactly as shown for the chart example above.

== Interop and prerendering

JS interop calls fail during prerendering (see
xref:web/aspnet/core/blazor-overview-and-render-modes.adoc[the double-render trap]) because there is no browser
DOM yet to call into -- `document`, `window`, and any injected library are simply undefined. Guard interop calls
to run only in `OnAfterRender(Async)` (which never runs during prerendering) rather than in
`OnInitializedAsync`, or check `RendererInfo.IsInteractive` first. See
https://learn.microsoft.com/en-us/aspnet/core/blazor/components/prerender[Prerender ASP.NET Core Razor
components].

== Deep dive: infinite scrolling with an `IntersectionObserver`

Browser APIs without a .NET equivalent -- observers, clipboard, canvas, geolocation -- are reached through a small
JavaScript module. The Orders list loads the next page when a sentinel element at the bottom scrolls into view. It
exercises every interop direction and the disposal rules that most interop bugs violate.

[mermaid]
....
sequenceDiagram
    participant C as OrderList component
    participant M as OrderList.razor.js module
    participant O as IntersectionObserver
    C->>C: OnAfterRenderAsync(firstRender)
    C->>M: import module (IJSObjectReference)
    C->>M: observe(sentinel ElementReference, DotNetObjectReference)
    M->>O: new IntersectionObserver and observe(sentinel)
    M-->>C: handle object with dispose()
    O->>M: sentinel visible
    M->>C: invokeMethodAsync LoadMore (JSInvokable)
    C->>C: load next page, StateHasChanged
    C->>M: DisposeAsync: handle.dispose(), module.DisposeAsync()
    C->>C: DotNetObjectReference.Dispose()
....

=== The collocated module

Placing the module next to the component keeps the pair together and lets the build fingerprint and publish it:

[source,javascript]
----
// Components/Pages/OrderList.razor.js
export function observe(element, dotNetRef) {
  const observer = new IntersectionObserver(entries => {
    if (entries.some(e => e.isIntersecting)) {
      dotNetRef.invokeMethodAsync('LoadMore');
    }
  }, { rootMargin: '200px' });          // start loading a little before the sentinel is visible
  observer.observe(element);
  return { dispose: () => observer.disconnect() };
}
----

The function returns a plain object. A JavaScript object returned to .NET arrives as an `IJSObjectReference`, and
calling `InvokeVoidAsync("dispose")` on it calls that member, which gives the component a way to stop the observer
without a global registry.

=== The component

[source,razor]
----
@* Components/Pages/OrderList.razor *@
@page "/orders"
@implements IAsyncDisposable
@inject IJSRuntime JS
@inject IOrderApi Orders

<ul>
    @foreach (var o in orders)
    {
        <li @key="o.Id">Order @o.Id: @o.Total.ToString("C")</li>
    }
</ul>
<div @ref="sentinel" aria-hidden="true"></div>

@code {
    private readonly List<OrderSummary> orders = [];
    private ElementReference sentinel;
    private IJSObjectReference? module;
    private IJSObjectReference? observer;
    private DotNetObjectReference<OrderList>? self;
    private int nextPage = 1;
    private bool loading, finished;

    protected override async Task OnAfterRenderAsync(bool firstRender)
    {
        if (!firstRender) return;                      // JS runs only after the element exists
        module = await JS.InvokeAsync<IJSObjectReference>("import", "./Components/Pages/OrderList.razor.js");
        self = DotNetObjectReference.Create(this);
        observer = await module.InvokeAsync<IJSObjectReference>("observe", sentinel, self);
        await LoadMore();                              // the first page, once everything is wired
    }

    [JSInvokable]
    public async Task LoadMore()
    {
        if (loading || finished) return;               // observer callbacks can arrive while a load is running
        loading = true;
        try
        {
            var page = await Orders.GetPageAsync(nextPage++);
            orders.AddRange(page);
            finished = page.Count == 0;
        }
        finally
        {
            loading = false;
        }
        await InvokeAsync(StateHasChanged);            // JS calls arrive outside the render flow
    }

    public async ValueTask DisposeAsync()
    {
        try
        {
            if (observer is not null) await observer.InvokeVoidAsync("dispose");
            if (module is not null) await module.DisposeAsync();
        }
        catch (JSDisconnectedException)
        {
            // the circuit is already gone: the browser side disposed itself
        }
        self?.Dispose();                               // release the .NET object the JS side was holding
    }
}
----

[source,csharp]
----
public sealed record OrderSummary(int Id, decimal Total);

public interface IOrderApi
{
    Task<IReadOnlyList<OrderSummary>> GetPageAsync(int page);
}
----

=== The rules the example follows

* *Interop only after the first render.* The element reference is valid and, under Interactive Server, the circuit
  exists, only from `OnAfterRenderAsync`. During prerender there is no browser, so calling JS in
  `OnInitializedAsync` throws.
* *Anything created is disposed.* The module reference, the object returned by `observe`, and the
  `DotNetObjectReference` all pin resources: forgetting the last keeps the component alive on the server for the life
  of the circuit.
* *`JSDisconnectedException` is expected* during disposal when the connection dropped first, and is swallowed on
  purpose.
* *Re-entrancy guard.* A JS-triggered callback is not serialized with the component's own work, so `LoadMore` protects
  itself with a flag.

=== Calling a long browser operation with a timeout

Interactive Server interop calls wait for the browser to answer. Give a call that may never return a cancellation
token so a stuck call does not hang the component forever:

[source,csharp]
----
using var cts = new CancellationTokenSource(TimeSpan.FromSeconds(5));
try
{
    await module!.InvokeVoidAsync("exportCanvas", cts.Token, canvasRef);
}
catch (TaskCanceledException)
{
    // report to the user that the export took too long
}
----
