SignalR pushes messages from the server to connected clients in real time, over whichever transport the client
and server negotiate, and falls back automatically when a better one is unavailable.

== Hubs

A *hub* is the server-side endpoint clients connect to and call methods on. `Hub<T>` makes client calls
strongly typed -- the compiler catches a wrong method name or argument type instead of failing at runtime:

[source,csharp]
----
public interface IChatClient
{
    Task ReceiveMessage(string user, string text);
}

public sealed class ChatHub : Hub<IChatClient>
{
    public async Task SendMessage(string user, string text)
        => await Clients.All.ReceiveMessage(user, text);

    public async Task JoinRoom(string room, string user)
    {
        await Groups.AddToGroupAsync(Context.ConnectionId, room);
        await Clients.Group(room).ReceiveMessage("system", $"{user} joined");
    }

    public override async Task OnConnectedAsync()
    {
        await Clients.Caller.ReceiveMessage("system", "welcome");
        await base.OnConnectedAsync();
    }
}

// Program.cs
builder.Services.AddSignalR();
app.MapHub<ChatHub>("/hubs/chat");
----

See https://learn.microsoft.com/en-us/aspnet/core/signalr/introduction[Introduction to ASP.NET Core SignalR]
and https://learn.microsoft.com/en-us/aspnet/core/signalr/hubs[Use hubs].

== Clients and groups

[cols="1,3",options="header"]
|===
| Target | Sends to

| `Clients.All` | Every connected client.
| `Clients.Caller` | Only the connection that invoked the current hub method.
| `Clients.Others` | Every connection except the caller.
| `Clients.Group(name)` | Members of a named group.
| `Clients.User(id)` | All connections (e.g. multiple tabs/devices) for one user id.
| `Clients.Client(connectionId)` | One specific connection.
|===

`Groups.AddToGroupAsync` / `RemoveFromGroupAsync` manage group membership; groups are not persisted, so a
reconnecting client must rejoin (typically from `OnConnectedAsync`).

== Transports

SignalR negotiates the best available transport and falls back automatically:

. **WebSockets** -- full-duplex, lowest overhead (preferred)
. **Server-Sent Events** -- a server-to-client stream plus separate POSTs for client-to-server calls
. **Long polling** -- last resort

`MapHub<ChatHub>("/hubs/chat")` exposes the negotiate endpoint plus each transport. The underlying browser
mechanisms are covered in xref:programming-languages/javascript/browser-networking.adoc[Networking].

== Clients

[source,javascript]
----
import * as signalR from "@microsoft/signalr";

const conn = new signalR.HubConnectionBuilder()
    .withUrl("/hubs/chat")
    .withAutomaticReconnect()
    .build();

conn.on("ReceiveMessage", (user, text) => appendLine(user, text));
await conn.start();
await conn.invoke("SendMessage", "alice", "hello");
----

[source,csharp]
----
var conn = new HubConnectionBuilder()
    .WithUrl("https://example.com/hubs/chat")
    .WithAutomaticReconnect()
    .Build();

conn.On<string, string>("ReceiveMessage", (user, text) => Console.WriteLine($"{user}: {text}"));

Both a JavaScript/TypeScript client (`@microsoft/signalr`) and a .NET client (`Microsoft.AspNetCore.SignalR.Client`)
ship officially; Java and other community clients also exist. See
https://learn.microsoft.com/en-us/aspnet/core/signalr/javascript-client[Use the JavaScript client] and
https://learn.microsoft.com/en-us/aspnet/core/signalr/dotnet-client[Use the .NET client].

== Streaming

Return or accept `IAsyncEnumerable<T>` / `ChannelReader<T>` for long-running data flows in either direction:

[source,csharp]
----
public async IAsyncEnumerable<int> CounterAsync(
    int count, [EnumeratorCancellation] CancellationToken ct)
{
    for (var i = 0; i < count; i++)
    {
        await Task.Delay(500, ct);
        yield return i;
    }
}
----

See https://learn.microsoft.com/en-us/aspnet/core/signalr/streaming[Streaming in ASP.NET Core SignalR].

SignalR is also an alternative transport for streaming chat responses to a browser; the SSE, WebSocket and NDJSON options
are compared in xref:ai/conversational-channels/streaming-chat-apis.adoc[Streaming Chat APIs].

== Authentication

`[Authorize]` works on a hub class or an individual hub method, same as an MVC controller; the access token
rides the connection (typically as a query-string parameter on the negotiate/WebSocket handshake, since custom
headers aren't available to browser WebSocket APIs):

[source,csharp]
----
[Authorize]
public sealed class ChatHub : Hub<IChatClient>
{
    [Authorize(Policy = "AdminOnly")]
    public Task Broadcast(string text) => Clients.All.ReceiveMessage("admin", text);
}
----

See xref:web/aspnet/core/authorization.adoc[Authorization] for policies, and
https://learn.microsoft.com/en-us/aspnet/core/signalr/authn-and-authz[Authentication and authorization in
ASP.NET Core SignalR].

== Scale-out

A single server holds every open connection in memory; running more than one server needs a **backplane** so a
message sent on one server reaches clients connected to another:

[source,csharp]
----
// dotnet add package Microsoft.AspNetCore.SignalR.StackExchangeRedis
builder.Services.AddSignalR()
    .AddStackExchangeRedis("localhost:6379", o => o.Configuration.ChannelPrefix = "chat");
----

The fully managed **Azure SignalR Service** is the alternative: it offloads connection management entirely, so
app servers don't hold WebSocket connections at all. See
https://learn.microsoft.com/en-us/aspnet/core/signalr/scale[Host and scale ASP.NET Core SignalR].

== Beyond the hub

* **`IHubContext<ChatHub, IChatClient>`** -- inject it anywhere (a controller, a background service) to push
  messages without being inside a hub method.
* **`MessagePack`** -- `AddSignalR().AddMessagePackProtocol()` swaps the default JSON protocol for a compact
  binary format.
* **Hub filters** -- `IHubFilter` wraps every hub invocation for cross-cutting logic (logging, validation),
  the SignalR analog of xref:web/aspnet/core/filters-and-the-mvc-pipeline.adoc[MVC filters].

== Deep dive: pushing order status to the right user

The chat example sends to everyone in a room. A more common shape is *server-initiated push to one user*: an order
ships and only its owner's browser tabs should hear about it. The piece that triggers the push is not a hub method; it
is ordinary application code, a controller, a Minimal API endpoint or a background service, that holds an
`IHubContext`.

=== Hub, notifier and identity

[source,csharp]
----
using Microsoft.AspNetCore.Authorization;
using Microsoft.AspNetCore.SignalR;

public interface IOrderClient
{
    Task OrderStatusChanged(int orderId, string status);
}

[Authorize]
public sealed class OrderHub : Hub<IOrderClient> { }          // no client-callable methods: the server only pushes

public sealed class OrderNotifier(IHubContext<OrderHub, IOrderClient> hub)
{
    public Task NotifyAsync(string userId, int orderId, string status)
        => hub.Clients.User(userId).OrderStatusChanged(orderId, status);   // every connection of that user
}

public sealed class SubjectUserIdProvider : IUserIdProvider
{
    // Hub "User" ids default to the NameIdentifier claim. JWT handlers in current .NET keep the raw "sub" claim,
    // so say explicitly which claim identifies the user.
    public string? GetUserId(HubConnectionContext connection)
        => connection.User.FindFirst("sub")?.Value
           ?? connection.User.FindFirst(System.Security.Claims.ClaimTypes.NameIdentifier)?.Value;
}
----

[source,csharp]
----
builder.Services.AddSignalR();
builder.Services.AddSingleton<IUserIdProvider, SubjectUserIdProvider>();
builder.Services.AddSingleton<OrderNotifier>();

builder.Services.AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddJwtBearer(o =>
    {
        // Browsers cannot set an Authorization header on a WebSocket, so the client sends the token as
        // ?access_token=... on hub URLs only; copy it into the normal JWT pipeline.
        o.Events = new JwtBearerEvents
        {
            OnMessageReceived = context =>
            {
                var token = context.Request.Query["access_token"];
                if (!string.IsNullOrEmpty(token) && context.HttpContext.Request.Path.StartsWithSegments("/hubs"))
                    context.Token = token;
                return Task.CompletedTask;
            },
        };
    });
builder.Services.AddAuthorization();

app.UseAuthentication();
app.UseAuthorization();
app.MapHub<OrderHub>("/hubs/orders");

app.MapPost("/orders/{id:int}/ship", async (int id, IOrderRepository orders, OrderNotifier notifier) =>
{
    var order = await orders.MarkShippedAsync(id);
    if (order is null) return Results.NotFound();

    await notifier.NotifyAsync(order.OwnerId, id, "Shipped");        // push after the state change is saved
    return Results.NoContent();
});
----

Query-string tokens end up in server and proxy access logs, so restrict the `OnMessageReceived` rewrite to the hub
path, as above, and keep access tokens short-lived. Notify *after* persisting the change: a push for a state that then
fails to save tells the user something untrue.

=== Reconnection is a state machine

A long-lived connection will drop: a laptop sleeps, a server restarts, a proxy times out an idle socket. The client
library models this explicitly, and the UI should reflect it.

[mermaid]
....
stateDiagram-v2
    [*] --> Disconnected
    Disconnected --> Connecting: start()
    Connecting --> Connected: handshake ok
    Connecting --> Disconnected: start() fails
    Connected --> Reconnecting: transport lost
    Reconnecting --> Connected: automatic retry succeeds
    Reconnecting --> Disconnected: retries exhausted
    Connected --> Disconnected: stop()
....

[source,javascript]
----
import * as signalR from "@microsoft/signalr";

const connection = new signalR.HubConnectionBuilder()
    .withUrl("/hubs/orders", { accessTokenFactory: () => sessionStorage.getItem("access_token") ?? "" })
    .withAutomaticReconnect([0, 2000, 10000, 30000])     // delays in ms before each retry, then give up
    .build();

connection.on("OrderStatusChanged", (orderId, status) => updateRow(orderId, status));

connection.onreconnecting(() => showBanner("Reconnecting..."));
connection.onreconnected(async () => {
    hideBanner();
    await reloadOrders();            // messages sent while offline are NOT replayed: resynchronize from the API
});
connection.onclose(() => showBanner("Live updates stopped. Reload to retry."));

await connection.start();
----

The important line is `reloadOrders()`. SignalR delivers each message at most once to a connected client and does not
buffer for a disconnected one, and after a reconnect the connection has a *new* connection id and has lost its group
memberships. Treat the push as a hint that something changed, and treat the API as the source of truth: on reconnect,
fetch the current state, and rejoin any groups from `OnConnectedAsync`.

=== Testing the notifier

`IHubContext<THub, T>` is an interface, so the notifier is testable with a substitute library such as NSubstitute:

[source,csharp]
----
using NSubstitute;

[Fact]
public async Task Notifies_every_connection_of_the_owner()
{
    var proxy = Substitute.For<IOrderClient>();
    var clients = Substitute.For<IHubClients<IOrderClient>>();
    clients.User("user-1").Returns(proxy);
    var hub = Substitute.For<IHubContext<OrderHub, IOrderClient>>();
    hub.Clients.Returns(clients);

    await new OrderNotifier(hub).NotifyAsync("user-1", 7, "Shipped");

    await proxy.Received(1).OrderStatusChanged(7, "Shipped");
}
----

The transport, negotiation and authentication wiring need an integration test with a real `HubConnection` created from
`WebApplicationFactory` (the test server supports the long-polling and WebSocket transports through the factory's
`Server.CreateHandler()` / `CreateWebSocketClient()` hooks).
