== Unit tests

Instantiate the class under test directly and pass fakes:

[source,csharp]
----
[Fact]
public async Task Get_returns_404_when_missing()
{
    var svc = Substitute.For<IOrderService>();
    svc.FindAsync(7).Returns((Order?)null);
    var controller = new OrdersController(svc);

    var result = await controller.Get(7);

    Assert.IsType<NotFoundResult>(result.Result);
}

// custom middleware: feed it a DefaultHttpContext
[Fact]
public async Task RequestId_middleware_sets_header()
{
    var ctx = new DefaultHttpContext();
    var mw = new RequestIdMiddleware(_ => Task.CompletedTask);
    await mw.InvokeAsync(ctx, NullLogger<RequestIdMiddleware>.Instance);
    Assert.True(ctx.Response.Headers.ContainsKey("X-Request-Id"));
}
----

The same approach covers Razor Page models, minimal-endpoint handler methods (extract them as named methods),
validators, and `AuthorizationHandler` classes. See
https://learn.microsoft.com/en-us/aspnet/core/mvc/controllers/testing[Unit test controller logic].

== Integration tests

`WebApplicationFactory<TEntryPoint>` boots the real pipeline in memory and hands you an `HttpClient`:

[source,csharp]
----
public sealed class OrdersApiTests(WebApplicationFactory<Program> factory)
    : IClassFixture<WebApplicationFactory<Program>>
{
    [Fact]
    public async Task Post_then_get_roundtrips()
    {
        var client = factory.WithWebHostBuilder(b => b.ConfigureTestServices(services =>
        {
            services.RemoveAll<IPaymentGateway>();
            services.AddSingleton<IPaymentGateway, FakePaymentGateway>();
        })).CreateClient();

        var created = await client.PostAsJsonAsync("/orders", new { customerId = 1 });
        created.EnsureSuccessStatusCode();

        var url = created.Headers.Location!;
        var order = await client.GetFromJsonAsync<OrderDto>(url);
        Assert.Equal(1, order!.CustomerId);
    }
}
----

Requires `Program` to be reachable (top-level statements expose an implicit `public partial class Program`).
`TestServer` is the lower-level primitive underneath. See
https://learn.microsoft.com/en-us/aspnet/core/test/integration-tests[Integration tests in ASP.NET Core].

== Test infrastructure

* **Config overrides**: `+builder.UseSetting("ConnectionStrings:Default", ...)+` or an in-memory config source.
* **Test auth**: register an `AuthenticationHandler<AuthenticationSchemeOptions>` that always returns a known
  `ClaimsPrincipal`, so `[Authorize]` endpoints are reachable without a real identity provider.
* **Database**: point EF Core at **SQLite in-memory** (a kept-open connection) for a real relational store per
  test; seed it in the fixture.
* **Antiforgery**: parse the token from the returned HTML with **AngleSharp** and echo it on the POST.
* **Assertions**: deserialize `ProblemDetails` and assert on `Status` / `Title` / `Errors`.

[source,csharp]
----
public sealed class TestAuthHandler(IOptionsMonitor<AuthenticationSchemeOptions> o, ILoggerFactory l, UrlEncoder e)
    : AuthenticationHandler<AuthenticationSchemeOptions>(o, l, e)
{
    protected override Task<AuthenticateResult> HandleAuthenticateAsync()
    {
        var claims = new[] { new Claim(ClaimTypes.Name, "test"), new Claim(ClaimTypes.Role, "Admin") };
        var ticket = new AuthenticationTicket(
            new ClaimsPrincipal(new ClaimsIdentity(claims, "Test")), "Test");
        return Task.FromResult(AuthenticateResult.Success(ticket));
    }
}
----

See https://learn.microsoft.com/en-us/aspnet/core/test/middleware[Test ASP.NET Core middleware].

== End-to-end and load

* **Contract / snapshot** tests pin an API's JSON shape so a breaking change fails CI.
* **Playwright for .NET** drives a real browser for end-to-end flows.
* **`k6`** or **`bombardier`** generate load; assert on p95 latency and error rate.

See https://learn.microsoft.com/en-us/aspnet/core/test/load-tests[Load and stress testing].

== Deep dive: a test fixture with a real database, a fake identity, and a load gate

Slow, flaky integration tests are usually a fixture problem: each test builds its own host, shares a database, or
logs in through a real identity provider. A reusable `WebApplicationFactory` subclass fixes all three once.

[mermaid]
....
flowchart TD
    UT["Unit tests<br/>many, milliseconds, fakes"] --> IT["Integration tests<br/>WebApplicationFactory, in-memory host"]
    IT --> E2E["End-to-end tests<br/>Playwright, real browser"]
    E2E --> LOAD["Load tests<br/>k6 thresholds in CI"]
    UT -. "catch logic errors" .-> R1["fast feedback"]
    IT -. "catch wiring, routing, serialization" .-> R2["pipeline confidence"]
    E2E -. "catch UI and deployment issues" .-> R3["user-journey confidence"]
....

=== The factory

[source,csharp]
----
using Microsoft.AspNetCore.Authentication;
using Microsoft.Data.Sqlite;
using Microsoft.EntityFrameworkCore;

public sealed class ShopFactory : WebApplicationFactory<Program>
{
    // An in-memory SQLite database lives only as long as its connection, so keep one open for the factory's lifetime.
    private readonly SqliteConnection _connection = new("DataSource=:memory:");

    protected override void ConfigureWebHost(IWebHostBuilder builder)
    {
        _connection.Open();
        builder.UseEnvironment("Testing");

        builder.ConfigureTestServices(services =>
        {
            services.RemoveAll<DbContextOptions<ShopDbContext>>();
            services.AddDbContext<ShopDbContext>(o => o.UseSqlite(_connection));

            services.AddAuthentication(o =>
                {
                    o.DefaultAuthenticateScheme = "Test";
                    o.DefaultChallengeScheme = "Test";
                })
                .AddScheme<AuthenticationSchemeOptions, HeaderAuthHandler>("Test", _ => { });
        });
    }

    public async Task SeedAsync(Action<ShopDbContext> seed)
    {
        using var scope = Services.CreateScope();
        var db = scope.ServiceProvider.GetRequiredService<ShopDbContext>();
        await db.Database.EnsureCreatedAsync();
        seed(db);
        await db.SaveChangesAsync();
    }

    protected override void Dispose(bool disposing)
    {
        if (disposing) _connection.Dispose();
        base.Dispose(disposing);
    }
}

// Authenticates only when the test says so, so anonymous (401) and signed-in cases are both testable.
public sealed class HeaderAuthHandler(
    IOptionsMonitor<AuthenticationSchemeOptions> options, ILoggerFactory logger, UrlEncoder encoder)
    : AuthenticationHandler<AuthenticationSchemeOptions>(options, logger, encoder)
{
    protected override Task<AuthenticateResult> HandleAuthenticateAsync()
    {
        if (!Request.Headers.TryGetValue("X-Test-User", out var user))
            return Task.FromResult(AuthenticateResult.NoResult());

        var claims = new[] { new Claim(ClaimTypes.Name, user.ToString()), new Claim(ClaimTypes.Role, "Admin") };
        var ticket = new AuthenticationTicket(
            new ClaimsPrincipal(new ClaimsIdentity(claims, "Test")), "Test");
        return Task.FromResult(AuthenticateResult.Success(ticket));
    }
}
----

=== Tests that use it

Use one factory per test class (`IClassFixture<ShopFactory>`) so state does not leak between classes. Within a class,
give each test its own data instead of resetting the database.

[source,csharp]
----
public sealed class ProductAdminTests(ShopFactory factory) : IClassFixture<ShopFactory>
{
    [Fact]
    public async Task Anonymous_delete_is_rejected()
    {
        await factory.SeedAsync(db => db.Products.Add(new Product { Sku = "ANN-0001", Name = "Shelf" }));

        var response = await factory.CreateClient().DeleteAsync("/api/catalog/ANN-0001");

        Assert.Equal(HttpStatusCode.Unauthorized, response.StatusCode);
    }

    [Fact]
    public async Task Admin_delete_removes_the_product()
    {
        await factory.SeedAsync(db => db.Products.Add(new Product { Sku = "ADM-0001", Name = "Shelf" }));
        var client = factory.CreateClient();
        client.DefaultRequestHeaders.Add("X-Test-User", "alice");

        var response = await client.DeleteAsync("/api/catalog/ADM-0001");

        Assert.Equal(HttpStatusCode.NoContent, response.StatusCode);
    }
}
----

Each test seeds its own SKU, so the tests are independent and can run in any order against the class's shared
database. Sharing one factory (and its database) across a class keeps start-up cost low; sharing *rows* is what makes
suites flaky.

The pattern gives a real relational engine (constraints, transactions, SQL translation) without a server, which the
EF Core in-memory provider does not: that provider ignores foreign keys and cannot execute relational features, so a
test can pass against it and fail in production. For provider-specific behaviour such as JSON columns or full-text
search, run the same fixture against a Testcontainers-managed instance of the production engine instead.

=== A load test as a pipeline gate

A load test is useful when it can fail. k6 expresses the pass criteria as `thresholds`, so a regression in p95
latency or error rate returns a non-zero exit code that fails the CI job:

[source,javascript]
----
import http from "k6/http";
import { check, sleep } from "k6";

export const options = {
  stages: [
    { duration: "30s", target: 50 },   // ramp up to 50 virtual users
    { duration: "1m", target: 50 },    // hold
    { duration: "10s", target: 0 },    // ramp down
  ],
  thresholds: {
    http_req_failed: ["rate<0.01"],      // under 1 percent errors
    http_req_duration: ["p(95)<300"],    // 95th percentile under 300 ms
  },
};

export default function () {
  const response = http.get(`${__ENV.BASE_URL}/api/catalog/BKS-0042`);
  check(response, { "status is 200": (r) => r.status === 200 });
  sleep(1);
}
----

Run it against a deployed staging build, not the in-memory host, with
`k6 run -e BASE_URL=https://staging.example.com load.mjs`, and keep the ramp short enough for a pipeline stage.
