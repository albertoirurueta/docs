= Static Files and Asset Delivery
:description: Serving static content in ASP.NET Core -- UseStaticFiles vs. MapStaticAssets, static web assets, fingerprinting and compression, ImportMap, wwwroot conventions, Razor class library assets, and CDN/cache-control strategy.
:keywords: UseStaticFiles, MapStaticAssets, static web assets, fingerprinting, compression, ImportMap, wwwroot, Razor class library, CDN, Cache-Control

include::partial$ai-disclaimer.adoc[]

ASP.NET Core serves files from `wwwroot` through middleware, and, for build-time-known assets, through a
dedicated static web assets pipeline that adds fingerprinting and compression the classic middleware alone does
not.

== `UseStaticFiles` vs. `MapStaticAssets`

[source,csharp]
----
app.UseStaticFiles();     // serves wwwroot as-is; no fingerprinting, no build-time manifest
----

[source,csharp]
----
app.MapStaticAssets();    // .NET 10+: serves the build's static web assets with fingerprinting + compression
app.MapRazorComponents<App>()
   .AddInteractiveServerRenderMode()
   .MapStaticAssets();    // components also resolve <link>/<script> URLs through the fingerprinted map
----

`UseStaticFiles` is plain middleware: whatever is under `wwwroot` at runtime is served, unmodified, with a
default `Cache-Control` the app must configure itself. `MapStaticAssets` is endpoint-routed and backed by a
build-time manifest of every static web asset (including ones contributed by referenced projects and RCLs),
so it can rewrite each asset's referenced URL to a fingerprinted one and serve precompressed variants. Prefer
`MapStaticAssets` for anything produced at build time; fall back to `UseStaticFiles` (optionally pointed at a
different physical/`IFileProvider` location) for files that only exist at runtime -- user uploads, generated
reports. See https://learn.microsoft.com/en-us/aspnet/core/fundamentals/static-files[Static files in ASP.NET
Core].

== Static web assets

Any project (including a referenced Razor class library or NuGet package) can contribute static web assets --
files under its own `wwwroot` are automatically merged into the consuming app's static asset set at build time,
namespaced under `+_content/\{LibraryName}/...+` unless the asset pipeline rewrites the reference for you via
`MapStaticAssets`. This is what makes a UI component library (see
xref:web/aspnet/core/ui-component-libraries.adoc[UI Component Libraries]) able to ship its own CSS/JS without
the consuming app copying files manually.

== Fingerprinting and compression

`MapStaticAssets` renames each asset's served URL to embed a content hash (e.g.
`app.a1b2c3d4.css`), so a browser can cache it **indefinitely** -- a new deployment produces a new hash, and
old cached copies simply stop being referenced instead of needing cache invalidation. It also serves
precompressed `.br`/`.gz` variants generated at publish time when the client's `Accept-Encoding` allows it,
rather than compressing on every request.

[source,razor]
----
<link rel="stylesheet" href="~/css/app.css" />   @* rendered as .../app.{hash}.css by MapStaticAssets *@
----

== `ImportMap`

Blazor and other ES-module-based apps use an **import map** so JS module specifiers (`import "./chart.js"`)
resolve to the actual fingerprinted URLs without every source file needing to know the hash:

[source,razor]
----
<ImportMap />   @* emits a <script type="importmap"> built from the static asset manifest *@
----

This is generated automatically alongside `MapStaticAssets` and is what lets
xref:web/aspnet/core/blazor-javascript-interop.adoc[collocated component JS modules] keep plain, hash-free
import paths in source while still benefiting from fingerprinted URLs at runtime.

== `wwwroot` conventions

[source,text]
----
wwwroot/
  css/site.css
  js/site.js
  lib/                # third-party libraries (LibMan or npm-built output)
  favicon.ico
----

`wwwroot` is the default web root; anything outside it is not served by either `UseStaticFiles` or
`MapStaticAssets` unless explicitly configured with an additional `IFileProvider`. Bundler-built output
(Webpack/Vite/esbuild) is typically configured to emit straight into `wwwroot` so the .NET build treats it like
any other static asset.

== Razor class library static assets

An RCL's own `wwwroot` participates the same way an app's does -- see
xref:web/aspnet/core/blazor-webassembly-hybrid-and-deployment.adoc[Razor class libraries] for packaging
components together with their CSS/JS/images for reuse across projects.

== CDN and cache-control strategy

[cols="1,3",options="header"]
|===
| Strategy | Notes

| Fingerprinted assets, `Cache-Control: max-age=31536000, immutable` | The default with `MapStaticAssets` --
  safe because the URL itself changes on any content change.
| Non-fingerprinted assets (runtime-generated, user uploads) | Set an explicit, shorter `Cache-Control`
  (or `no-cache` plus an `ETag`/`Last-Modified` validator) via `StaticFileOptions.OnPrepareResponse`.
| CDN in front of the app | Point the CDN at fingerprinted asset URLs specifically -- they can be cached at
  the edge indefinitely without any purge/invalidation step on deploy.
|===

[source,csharp]
----
app.UseStaticFiles(new StaticFileOptions
{
    OnPrepareResponse = ctx =>
        ctx.Context.Response.Headers.CacheControl = "public,max-age=600"
});
----

See https://learn.microsoft.com/en-us/aspnet/core/fundamentals/map-static-files[Static files in ASP.NET Core]
for `MapStaticAssets`, fingerprinting, and compression details, and
xref:web/aspnet/core/performance-and-caching.adoc[Performance and Caching] for response/output caching of
dynamic content.

== Deep dive: serving build assets and user uploads side by side

Build-time assets and runtime files have opposite needs. A stylesheet is known at build time, can be fingerprinted and
cached forever. A product photo uploaded by a user appears at runtime, may be replaced under the same name, and is
*untrusted input*. Serving both well means using each mechanism for what it is good at.

[source,csharp]
----
using Microsoft.AspNetCore.StaticFiles;
using Microsoft.Extensions.FileProviders;

var builder = WebApplication.CreateBuilder(args);
builder.Services.AddRazorPages();

var app = builder.Build();

app.MapStaticAssets();                                          // build output: an endpoint, fingerprinted + precompressed

var uploads = Path.Combine(builder.Environment.ContentRootPath, "App_Data", "uploads");
Directory.CreateDirectory(uploads);

// An allow-list, not the default table: only these three extensions are ever served from /uploads.
var contentTypes = new FileExtensionContentTypeProvider(new Dictionary<string, string>
{
    [".jpg"] = "image/jpeg",
    [".png"] = "image/png",
    [".pdf"] = "application/pdf",
});

app.UseStaticFiles(new StaticFileOptions
{
    FileProvider = new PhysicalFileProvider(uploads),           // outside wwwroot: not reachable any other way
    RequestPath = "/uploads",
    ContentTypeProvider = contentTypes,
    ServeUnknownFileTypes = false,                              // unmapped extensions answer 404, not octet-stream
    OnPrepareResponse = ctx =>
    {
        var headers = ctx.Context.Response.Headers;
        headers.CacheControl = "public,max-age=300";            // short: the file may be replaced
        headers["X-Content-Type-Options"] = "nosniff";          // browsers must honour the declared type
        headers["Content-Security-Policy"] = "default-src 'none'; sandbox";   // an uploaded HTML file stays inert
    },
});

app.MapRazorPages();
app.Run();
----

Three decisions carry the security weight. The uploads folder is outside `wwwroot`, so nothing serves it unless this
explicit mapping does. The content-type table is an allow-list: with `ServeUnknownFileTypes` off, an upload whose
extension is not in it (`.html`, `.svg`, `.config`) is not served at all, which closes the classic "stored XSS
through an uploaded file" hole, since neither HTML nor SVG can carry script out of `/uploads`. The response headers turn a browser that is handed a file it should not run into one that
refuses to.

=== Validating caching with conditional requests

The static file middleware emits `ETag` and `Last-Modified` for every file, which lets a client revalidate cheaply.
Confirm that it works instead of assuming:

[source,bash]
----
curl -sI http://localhost:5000/uploads/shelf.jpg | grep -iE 'etag|cache-control|content-type|x-content'
# ETag: "1dbd0f1a2b3c4d5"   <- value differs per file version
curl -sI -H 'If-None-Match: "1dbd0f1a2b3c4d5"' http://localhost:5000/uploads/shelf.jpg | head -1
# HTTP/1.1 304 Not Modified
----

A `304` response has no body, so a revalidation costs one round trip and almost no bandwidth. The middleware also
honours `Range` requests for large files such as video, answering `206 Partial Content`, with no code from you.

=== Cache-busting for files that are not fingerprinted

Files served through `UseStaticFiles` have no hash in their name, so a changed `site.css` could be stale in
browsers that cached it. The `asp-append-version` Tag Helper appends a content-hash query string to the URL when
rendering, so the URL changes exactly when the file does:

[source,cshtml]
----
<link rel="stylesheet" href="~/css/site.css" asp-append-version="true" />
<!-- rendered: /css/site.css?v=Kl_dqr9NVtnMdsM2MUg4qthUnWZm5T1fCEimBPWDNgM -->
----

Combined with a long `max-age`, this gives the same "cache forever, invalidate by changing the URL" behaviour that
`MapStaticAssets` provides natively. With `MapStaticAssets` this tag helper is unnecessary, because the fingerprint
is already in the file name.

=== Directory browsing and default documents

`UseDirectoryBrowser` lists a folder's contents and should stay off in production. `UseDefaultFiles` rewrites `/` to
`/index.html` when that file exists, and must be registered before `UseStaticFiles` because it only rewrites the
path; the static file middleware then serves the result. `UseFileServer` bundles the three behaviours for a
single-page application's static host.
