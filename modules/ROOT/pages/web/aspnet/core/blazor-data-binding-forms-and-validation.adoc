Blazor binds C# state to markup with `@bind` and validates it with `EditForm`/`EditContext`. This page assumes
the xref:web/aspnet/core/blazor-components-and-lifecycle.adoc[component model] already covered.

== One-way and two-way binding

A plain `@expression` is one-way (state to markup); `@bind-Value` (or its shorthand `@bind`) is two-way,
listening for a change event and writing the new value back:

[source,razor]
----
<p>Hello, @name</p>                       @* one-way *@
<input @bind="name" />                    @* two-way: writes back on the element's default event (change) *@
----

== `@bind:event`, `@bind:after`, `@bind:get`/`@bind:set`

[source,razor]
----
<input @bind="name" @bind:event="oninput" />                       @* update on every keystroke *@
<input @bind="name" @bind:after="Search" />                        @* run Search() after the value commits *@
<input @bind:get="Query" @bind:set="OnQueryChanged" />             @* split read/write for custom logic *@
----

[source,csharp]
----
@code {
    private string name = "";
    private string Query { get; set; } = "";

    private void Search() => results = catalog.Search(name);
    private async Task OnQueryChanged(string value)
    {
        Query = value;
        await SaveDraftAsync(value);
    }
}
----

* `@bind:event` overrides the triggering DOM event (default is `onchange`; `oninput` fires per keystroke).
* `@bind:after` runs a method after the bound value is assigned -- convenient for "debounced search" or
  "recompute a derived value" without manually wiring an event handler.
* `@bind:get` / `@bind:set` split a two-way binding into an explicit getter and setter, useful when the setter
  needs to be `async` or must transform the incoming value.

Format strings work the same way as before: `<input @bind="startDate" @bind:format="yyyy-MM-dd" />`.

See https://learn.microsoft.com/en-us/aspnet/core/blazor/components/data-binding[Data binding in ASP.NET Core
Blazor].

== `EventCallback` vs. `Action`

Prefer `EventCallback` / `EventCallback<T>` over a plain `Action`/`Action<T>` delegate for parameters a
component invokes as an event: `EventCallback` integrates with Blazor's rendering so the *invoking* component
re-renders after the callback returns (including awaiting an async handler), which a raw delegate does not do
automatically.

[source,razor]
----
@code { [Parameter] public EventCallback<ProductDto> OnBuy { get; set; } }
----

[source,razor]
----
<button @onclick="() => OnBuy.InvokeAsync(Product)">Buy</button>
----

== `EditForm` and `EditContext`

`EditForm` builds an `EditContext` over a model and tracks field modification/validation state for its
descendants:

[source,razor]
----
<EditForm Model="Input" OnValidSubmit="Save">
    <DataAnnotationsValidator />
    <ValidationSummary />

    <InputText @bind-Value="Input.Name" />
    <ValidationMessage For="() => Input.Name" />

    <InputNumber @bind-Value="Input.Price" />
    <InputDate @bind-Value="Input.ReleaseOn" />
    <InputCheckbox @bind-Value="Input.InStock" />
    <InputSelect @bind-Value="Input.CategoryId">
        @foreach (var c in Categories) { <option value="@c.Id">@c.Name</option> }
    </InputSelect>

    <button type="submit">Save</button>
</EditForm>

@code {
    private ProductInput Input = new();
    private Task Save() => ProductApi.CreateAsync(Input);
}
----

`OnValidSubmit` (and `OnInvalidSubmit`) fire only after validation runs; use plain `OnSubmit` to control that
yourself. Injecting `EditContext` directly (instead of `Model`) is the way to share one context across nested
components or add custom validation logic. See
https://learn.microsoft.com/en-us/aspnet/core/blazor/forms/[ASP.NET Core Blazor forms overview].

== Built-in input components

`InputText`, `InputTextArea`, `InputNumber`, `InputSelect`, `InputCheckbox`, `InputDate`, `InputRadio` /
`InputRadioGroup`, `InputFile`, and, since .NET 10, `InputHidden` -- each binds a model field and participates
in `EditContext` validation:

[source,razor]
----
<InputRadioGroup @bind-Value="Input.Size">
    <InputRadio Value="'S'" /> Small
    <InputRadio Value="'M'" /> Medium
    <InputRadio Value="'L'" /> Large
</InputRadioGroup>

<InputFile OnChange="OnFileSelected" multiple />
<InputHidden @bind-Value="Input.CorrelationId" />
----

See https://learn.microsoft.com/en-us/aspnet/core/blazor/forms/input-components[ASP.NET Core Blazor forms and
input components].

== Validation

[source,csharp]
----
public sealed class ProductInput
{
    [Required, StringLength(100)] public string Name { get; set; } = "";
    [Range(0.01, 100000)] public decimal Price { get; set; }
}
----

`<DataAnnotationsValidator />` wires `System.ComponentModel.DataAnnotations` attributes into the `EditContext`;
`<ValidationSummary />` lists every error, `+<ValidationMessage For="...">+` shows one field's error. Add a
**custom validation attribute** (`class MustBeEvenAttribute : ValidationAttribute`) for reusable rules, or
subscribe to `EditContext.OnValidationRequested` for ad hoc cross-field logic.

.NET 10 adds `[ValidatableType]` for declarative validation of **nested objects and collections** -- previously
`DataAnnotationsValidator` only validated the top-level model's own properties:

[source,csharp]
----
[ValidatableType]
public sealed class OrderInput
{
    [Required] public string Customer { get; set; } = "";
    public List<OrderLineInput> Lines { get; set; } = [];
}

public sealed class OrderLineInput
{
    [Required] public string Sku { get; set; } = "";
    [Range(1, 100)] public int Quantity { get; set; }
}
----

Marking `OrderInput` (and transitively validated types) `[ValidatableType]` makes `DataAnnotationsValidator`
walk into `Lines` and validate each `OrderLineInput`, which previously required a hand-written
`IValidatableObject` implementation. See
https://learn.microsoft.com/en-us/aspnet/core/blazor/forms/validation[ASP.NET Core Blazor forms validation].

== SSR form handling

A Static SSR page has no interactive circuit to bind against, so its `EditForm` posts a normal HTTP form
submission; recover the values with `[SupplyParameterFromForm]` and protect the endpoint with antiforgery:

[source,razor]
----
@page "/products/create"
@attribute [RenderModeStatic]

<EditForm Model="Input" method="post" OnValidSubmit="Save" FormName="create-product">
    <AntiforgeryToken />
    <DataAnnotationsValidator />
    <InputText @bind-Value="Input.Name" />
    <button type="submit">Save</button>
</EditForm>

@code {
    [SupplyParameterFromForm] private ProductInput Input { get; set; } = new();

    private async Task Save()
    {
        await ProductApi.CreateAsync(Input);
        Nav.NavigateTo("/products");
    }
}
----

Antiforgery validation is enabled for Blazor Web App form posts by default via `AddAntiforgery` and
`UseAntiforgery`; `<AntiforgeryToken />` embeds the token in the rendered form. See
https://learn.microsoft.com/en-us/aspnet/core/blazor/forms/[ASP.NET Core Blazor forms overview] and
xref:web/aspnet/core/security-hardening.adoc[Security Hardening] for antiforgery/CSRF in general.

== Deep dive: validation you cannot do on the client

Data annotations cover rules a form can check alone: required, ranges, lengths. Some rules need the server -- "is
that product in stock", "is this coupon still valid" -- and their errors must appear next to the right field just
like annotation errors. The mechanism is a `ValidationMessageStore` attached to the form's `EditContext`.

[mermaid]
....
sequenceDiagram
    participant U as User
    participant F as EditForm and EditContext
    participant A as DataAnnotationsValidator
    participant M as ValidationMessageStore
    participant S as Order service
    U->>F: edit a field
    F->>A: OnFieldChanged, validate that field
    A->>M: add or clear messages for the field
    U->>F: submit
    F->>A: OnValidationRequested, validate whole model
    alt annotations fail
        A-->>F: invalid, OnInvalidSubmit
    else annotations pass
        F->>S: OnValidSubmit, place order
        S-->>F: rule violations for specific fields
        F->>M: Add(field, message), NotifyValidationStateChanged
        M-->>U: messages shown by ValidationMessage and ValidationSummary
    end
....

=== Worked example: the order form

[source,razor]
----
@page "/orders/new"
@inject IOrderApi Orders
@inject NavigationManager Nav

<EditForm EditContext="editContext" OnValidSubmit="SubmitAsync">
    <DataAnnotationsValidator />
    <ValidationSummary />

    <label>Product id <InputNumber @bind-Value="Input.ProductId" /></label>
    <ValidationMessage For="() => Input.ProductId" />

    <label>Quantity <InputNumber @bind-Value="Input.Quantity" /></label>
    <ValidationMessage For="() => Input.Quantity" />

    <label>Coupon <InputText @bind-Value="Input.Coupon" /></label>
    <ValidationMessage For="() => Input.Coupon" />

    <button type="submit" disabled="@submitting">Place order</button>
</EditForm>

@code {
    private OrderInput Input = new();
    private EditContext editContext = default!;
    private ValidationMessageStore serverMessages = default!;
    private bool submitting;

    protected override void OnInitialized()
    {
        editContext = new EditContext(Input);
        serverMessages = new ValidationMessageStore(editContext);

        // server messages describe the value that was submitted: drop them as soon as the user changes it
        editContext.OnFieldChanged += (_, e) => serverMessages.Clear(e.FieldIdentifier);
        editContext.OnValidationRequested += (_, _) => serverMessages.Clear();
    }

    private async Task SubmitAsync()
    {
        if (submitting) return;                    // a double click must not place two orders
        submitting = true;
        try
        {
            var result = await Orders.PlaceAsync(Input);
            if (result.Succeeded)
            {
                Nav.NavigateTo($"/orders/{result.OrderId}");
                return;
            }

            foreach (var problem in result.Problems)       // (field name, message) pairs from the server
            {
                serverMessages.Add(editContext.Field(problem.Field), problem.Message);
            }
            editContext.NotifyValidationStateChanged();
        }
        finally
        {
            submitting = false;
        }
    }
}
----

[source,csharp]
----
public sealed class OrderInput
{
    [Range(1, int.MaxValue, ErrorMessage = "Choose a product.")] public int ProductId { get; set; }
    [Range(1, 100)] public int Quantity { get; set; } = 1;
    [StringLength(12)] public string? Coupon { get; set; }
}

public sealed record OrderProblem(string Field, string Message);
public sealed record PlaceOrderResult(bool Succeeded, int OrderId, IReadOnlyList<OrderProblem> Problems);

public interface IOrderApi
{
    Task<PlaceOrderResult> PlaceAsync(OrderInput input);
}
----

Three behaviors are worth noticing. The `OnFieldChanged` handler clears only the field the user touched, so an
unrelated server message stays visible. `Field("Quantity")` creates a `FieldIdentifier` for a property of the form's
model by name, which is how a server response that only knows property names reaches the right `ValidationMessage`.
`NotifyValidationStateChanged` is required, because adding to a store does not itself notify the UI.

=== Binding with conversion and culture

`@bind` on an `InputNumber` or a plain `<input type="number">` parses the text with the current culture, and
`@bind:culture` overrides it. A text box that must accept both `1.5` and `1,5` should bind to a string and convert
explicitly:

[source,razor]
----
@using System.Globalization

<input @bind="priceText" @bind:event="oninput" />
<p>@(decimal.TryParse(priceText, NumberStyles.Number, CultureInfo.CurrentCulture, out var p) ? p.ToString("C") : "not a number")</p>

@code { private string priceText = ""; }
----

For an unparsable value an `InputNumber` keeps the model unchanged and reports the field as invalid with the
`ParsingErrorMessage` (which you can override per input), so the user sees an error and the model never
holds a half-parsed number.
