Blazor authorization builds on the same xref:web/aspnet/core/authentication-and-identity.adoc[authentication]
and xref:web/aspnet/core/authorization.adoc[authorization] primitives used everywhere else in ASP.NET Core, with
a component-model layer on top.

== `AuthenticationStateProvider` and `CascadingAuthenticationState`

`AuthenticationStateProvider` is the abstraction components query for the current user; `<CascadingAuthenticationState>`
(wired up automatically by `AddAuthorizationCore`/`AddCascadingAuthenticationState` in a Blazor Web App
template) makes an `AuthenticationState` available as a cascading value to the whole component tree:

[source,csharp]
----
builder.Services.AddCascadingAuthenticationState();
builder.Services.AddAuthorization();
----

[source,razor]
----
@inject AuthenticationStateProvider AuthState

@code {
    protected override async Task OnInitializedAsync()
    {
        var state = await AuthState.GetAuthenticationStateAsync();
        var user = state.User;   // ClaimsPrincipal
    }
}
----

See https://learn.microsoft.com/en-us/aspnet/core/blazor/security/[ASP.NET Core Blazor authentication and
authorization].

== `AuthorizeView`, `[Authorize]`, and `AuthorizeRouteView`

[source,razor]
----
<AuthorizeView Policy="AdminOnly">
    <Authorized><AdminPanel /></Authorized>
    <NotAuthorized><p>Access denied.</p></NotAuthorized>
</AuthorizeView>

<AuthorizeView Roles="Manager,Admin" Context="authState">
    <p>Welcome, @authState.User.Identity?.Name</p>
</AuthorizeView>
----

[source,razor]
----
@page "/admin"
@attribute [Authorize(Policy = "AdminOnly")]
----

`<AuthorizeView>` shows/hides UI fragments; `[Authorize]` on a routed `@page` component gates the whole page.
The two combine through `AuthorizeRouteView`, which `Routes.razor` uses in place of a plain `RouteView` so a
denied `[Authorize]` page renders a `NotAuthorized`/`NotAuthenticated` fragment instead of the page itself:

[source,razor]
----
<Router AppAssembly="typeof(Program).Assembly">
    <Found Context="routeData">
        <AuthorizeRouteView RouteData="routeData" DefaultLayout="typeof(MainLayout)">
            <NotAuthorized><p>Please sign in.</p></NotAuthorized>
        </AuthorizeRouteView>
    </Found>
</Router>
----

See https://learn.microsoft.com/en-us/aspnet/core/blazor/security/index[Authorization in ASP.NET Core Blazor
apps].

== Auth in Server vs. WebAssembly: why WASM auth is never a trust boundary

Under **Interactive Server**, `[Authorize]`/`<AuthorizeView>` checks run on the server, over the same
`ClaimsPrincipal` an MVC controller would see -- they are a real trust boundary, and hiding a component is
equivalent to never sending its markup or invoking its code at all.

Under **Interactive WebAssembly**, all component code -- including anything an `[Authorize]` attribute
"protects" -- runs in the user's own browser, downloaded and executable regardless of whether the check passes.
Hiding a button or a route with `<AuthorizeView>`/`[Authorize]` there is a **UX convenience, not a security
control**: it stops a legitimate user from seeing UI they shouldn't act on, but a motivated attacker can still
call the underlying API directly. **Every actual authorization decision must be re-enforced server-side**, on
the API the WebAssembly client calls -- exactly as if that client were untrusted, because it is. See
https://learn.microsoft.com/en-us/aspnet/core/blazor/security/webassembly/[Secure ASP.NET Core Blazor
WebAssembly].

== ASP.NET Core Identity in a Blazor Web App

The `dotnet new blazor -au Individual` template wires up ASP.NET Core Identity's cookie-based authentication
for a Blazor Web App directly (registration, login, external logins, two-factor, and the .NET 10 passkey flow
below), reusing the Identity pieces covered in
xref:web/aspnet/core/authentication-and-identity.adoc[Authentication and ASP.NET Core Identity]. Identity's own
account-management pages are still Razor Pages/MVC-rendered, since they run once, outside the interactive
circuit.

== OIDC with an external identity provider

For sign-in against Entra ID, Auth0, Duende IdentityServer, or another OpenID Connect provider, add the OIDC
handler at the server (Static SSR / Interactive Server sign-in still happens through a normal browser redirect
and cookie, not inside the WebAssembly runtime):

[source,csharp]
----
builder.Services.AddAuthentication(OpenIdConnectDefaults.AuthenticationScheme)
    .AddCookie()
    .AddOpenIdConnect(o =>
    {
        o.Authority = "https://login.microsoftonline.com/{tenant}/v2.0";
        o.ClientId = builder.Configuration["Oidc:ClientId"];
        o.ResponseType = "code";
    });
----

See xref:web/aspnet/core/authentication-and-identity.adoc[Authentication and ASP.NET Core Identity] for OAuth
2.0/OIDC handler details that apply identically here.

== Token handling and `AuthorizationMessageHandler`

A standalone or Interactive WebAssembly client calling a separate API attaches an access token via a
`DelegatingHandler` added to its `HttpClient`, rather than relying on the cookie used for the Blazor app itself:

[source,csharp]
----
builder.Services.AddHttpClient("OrdersApi", c => c.BaseAddress = new Uri("https://api.example.com"))
    .AddHttpMessageHandler<AuthorizationMessageHandler>();

builder.Services.AddScoped(sp => sp.GetRequiredService<IHttpClientFactory>().CreateClient("OrdersApi"));
----

`AuthorizationMessageHandler` (from `Microsoft.AspNetCore.Components.WebAssembly.Authentication`) attaches the
token acquired via the WebAssembly OIDC/MSAL sign-in flow and refreshes it as needed. See
xref:web/aspnet/core/http-client-and-resilience.adoc[HTTP Client and Resilience] for `IHttpClientFactory`
itself.

== Passkeys / WebAuthn (.NET 10)

The .NET 10 Identity-backed Blazor Web App template supports **passkey (WebAuthn) sign-in** out of the box --
users register a passkey (a platform authenticator or security key) as an alternative to a password, using the
browser's WebAuthn API under the hood with no extra client-side code required from the app.

== Antiforgery, CSP, and reconnection UI

* **Antiforgery** -- SSR form posts (see
  xref:web/aspnet/core/blazor-data-binding-forms-and-validation.adoc[Data Binding, Forms, and Validation])
  are protected the same way as any other ASP.NET Core form post; see
  xref:web/aspnet/core/security-hardening.adoc[Security Hardening].
* **Content Security Policy** -- Interactive WebAssembly needs `script-src` to allow the WASM runtime's own
  scripts (and, without further hardening, `+'unsafe-eval'+` in some hosting configurations); test a CSP against
  the actual render modes in use rather than assuming an MVC-app policy carries over unchanged.
* **Reconnection UI** -- an Interactive Server circuit that drops shows a built-in "Attempting to reconnect..."
  overlay (customizable via the `components-reconnect-modal` CSS classes/JS) while it tries to resume; if it
  cannot, the user is prompted to reload. Combine with .NET 10 circuit state persistence (see
  xref:web/aspnet/core/blazor-state-management.adoc[Blazor State Management]) so a successful reconnect does
  not also lose in-progress work.

== Deep dive: the UI hides, the server decides

In Blazor Server the component code runs on the server, so an `[Authorize]` attribute on a page is a real check. In
WebAssembly the component code runs in the browser, where the user can modify it, so authorization in a component only
shapes the interface. The real check must live on the server API that the component calls. The Orders cancel button
shows both layers:

[mermaid]
....
sequenceDiagram
    participant U as User
    participant C as OrderDetails component
    participant A as AuthorizeView with Resource
    participant API as POST /orders/id/cancel
    participant H as Authorization handler
    U->>C: opens order 42
    C->>A: evaluate policy CanCancel for this order
    A-->>U: show or hide the Cancel button (convenience only)
    U->>API: clicks Cancel (or crafts the request by hand)
    API->>H: AuthorizeAsync(user, order, Cancel)
    alt allowed
        H-->>API: succeeded
        API-->>U: 204
    else denied
        H-->>API: failed
        API-->>U: 403
    end
....

=== The component layer

`AuthorizeView` accepts a `Resource`, so the same policy and handler that protect the API can drive the interface. The
policy is the resource-based `CanCancel` policy built in
xref:web/aspnet/core/authorization.adoc[Authorization]:

[source,razor]
----
@page "/orders/{Id:int}"
@attribute [Authorize]
@inject IOrderApi Orders

@if (order is not null)
{
    <h1>Order @order.Id</h1>

    <AuthorizeView Policy="CanCancel" Resource="order">
        <Authorized>
            <button @onclick="CancelAsync">Cancel order</button>
        </Authorized>
        <NotAuthorized>
            <p>This order can no longer be cancelled.</p>
        </NotAuthorized>
    </AuthorizeView>
}

@code {
    [Parameter] public int Id { get; set; }
    private OrderDto? order;

    protected override async Task OnParametersSetAsync() => order = await Orders.GetAsync(Id);

    private async Task CancelAsync()
    {
        var response = await Orders.CancelAsync(Id);       // the server decides again
        order = response.IsSuccessStatusCode ? await Orders.GetAsync(Id) : order;
    }
}
----

[source,csharp]
----
// registration: the policy name used by AuthorizeView
builder.Services.AddAuthorizationBuilder()
    .AddPolicy("CanCancel", p => p.Requirements.Add(OrderOperations.Cancel));
----

In WebAssembly the policy and its handler execute in the browser, so the handler must be registered in the client
project too; under Interactive Server the single server registration is enough.

=== The server layer

The endpoint repeats the check with the same handler, so a request that never went through the component is held to
the same rule:

[source,csharp]
----
app.MapPost("/orders/{id:int}/cancel",
    async (int id, ClaimsPrincipal user, AppDbContext db, IAuthorizationService auth, CancellationToken ct) =>
    {
        var order = await db.Orders.FindAsync([id], ct);
        if (order is null) return Results.NotFound();
        if (!(await auth.AuthorizeAsync(user, order, OrderOperations.Cancel)).Succeeded) return Results.Forbid();

        order.Status = OrderStatus.Cancelled;
        await db.SaveChangesAsync(ct);
        return Results.NoContent();
    }).RequireAuthorization();
----

=== Calling the API from WebAssembly with a token

A standalone WebAssembly app that signs in with OpenID Connect attaches the access token to API calls through a
message handler. `BaseAddressAuthorizationMessageHandler` adds the token only to requests under the app's own base
address, so a token is never sent to a third-party host by accident:

[source,csharp]
----
builder.Services.AddHttpClient("OrdersApi", c => c.BaseAddress = new Uri(builder.HostEnvironment.BaseAddress))
    .AddHttpMessageHandler<BaseAddressAuthorizationMessageHandler>();

builder.Services.AddOidcAuthentication(o =>
{
    builder.Configuration.Bind("Oidc", o.ProviderOptions);
    o.ProviderOptions.DefaultScopes.Add("orders.write");
});
----

For an API on a *different* origin, derive a handler that names the allowed URLs and the scopes it needs:

[source,csharp]
----
public sealed class OrdersApiHandler : AuthorizationMessageHandler
{
    public OrdersApiHandler(IAccessTokenProvider provider, NavigationManager navigation)
        : base(provider, navigation)
    {
        ConfigureHandler(authorizedUrls: ["https://orders.example/"], scopes: ["orders.write"]);
    }
}

builder.Services.AddTransient<OrdersApiHandler>();
builder.Services.AddHttpClient("OrdersApi", c => c.BaseAddress = new Uri("https://orders.example/"))
    .AddHttpMessageHandler<OrdersApiHandler>();
----

=== Reading the user outside a component

A service that needs the current user injects `AuthenticationStateProvider` and awaits the state at the moment it is
needed, rather than caching it, because the state can change during a long-lived circuit:

[source,csharp]
----
public sealed class CurrentUser(AuthenticationStateProvider provider)
{
    public async Task<string?> GetIdAsync()
    {
        var state = await provider.GetAuthenticationStateAsync();
        return state.User.FindFirstValue(ClaimTypes.NameIdentifier);
    }
}
----
