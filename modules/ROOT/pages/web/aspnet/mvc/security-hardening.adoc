This page documents security hardening for ASP.NET MVC 5.3.x on .NET Framework 4.8.1 -- not ASP.NET Core (see
xref:web/aspnet/core/security-hardening.adoc[Security Hardening] under ASP.NET Core, which covers the Data
Protection API and the current antiforgery implementation).

== CSRF

[source,cshtml]
----
@using (Html.BeginForm())
{
    @Html.AntiForgeryToken()
}
----

[source,csharp]
----
[HttpPost]
[ValidateAntiForgeryToken]
public ActionResult Transfer(TransferViewModel model) { ... }
----

For AJAX POSTs, the token must be read from the DOM and sent explicitly (it is not part of a browser cookie the
server can read back automatically the way ASP.NET Core's double-submit cookie works by default):

[source,javascript]
----
var token = $('input[name="__RequestVerificationToken"]').val();
$.post('/Account/Transfer', { __RequestVerificationToken: token, amount: 50 });
----

See xref:web/aspnet/mvc/html-helpers-and-forms.adoc[HTML Helpers and Forms] for `Html.AntiForgeryToken()` and
xref:web/aspnet/mvc/filters.adoc[Filters] for where `[ValidateAntiForgeryToken]` runs as an authorization
filter.

== XSS and Razor's automatic encoding

Razor HTML-encodes every `@`-expression by default (see xref:web/aspnet/mvc/razor-syntax.adoc[Razor Syntax]);
`Html.Raw` is the deliberate, narrow opt-out and must never wrap unsanitized user input:

[source,cshtml]
----
<p>@Model.Comment</p>                     <!-- safe: automatically encoded -->
<p>@Html.Raw(_sanitizer.Sanitize(Model.Comment))</p>   <!-- only safe because it was sanitized first -->
----

`AntiXssEncoder` (`Microsoft.Security.Application.AntiXss` / `System.Web.Security.AntiXss`) was a
Microsoft-supplied, whitelist-based HTML encoder that some MVC 5 applications registered as the default
encoder (`HttpUtility`/`AntiXssEncoder.HtmlEncode`) in place of the framework's built-in encoder, for stricter
encoding behavior; it has since been folded into `System.Web`{apos}s own encoder in later Framework versions.

== Request validation and `[AllowHtml]`

`System.Web` rejects any posted value containing markup-like characters by default; `[AllowHtml]` narrows that
exception to one specific property, and that property must still be sanitized before ever being rendered with
`Html.Raw` (see xref:web/aspnet/mvc/model-binding-and-validation.adoc[Model Binding and Validation]).

== Open redirect

A redirect target taken directly from user input (a `returnUrl` query-string parameter after login, for
example) can be abused to send a victim to an attacker-controlled site while the URL still points at your own
trusted domain up to the redirect. `Url.IsLocalUrl` guards against this:

[source,csharp]
----
private ActionResult RedirectToLocal(string returnUrl)
    => Url.IsLocalUrl(returnUrl) ? (ActionResult)Redirect(returnUrl) : RedirectToAction("Index", "Home");
----

== Clickjacking and security headers via `web.config`

[source,xml]
----
<system.webServer>
  <httpProtocol>
    <customHeaders>
      <add name="X-Frame-Options" value="DENY" />
      <add name="X-Content-Type-Options" value="nosniff" />
      <add name="Content-Security-Policy" value="default-src 'self'" />
      <add name="Strict-Transport-Security" value="max-age=31536000; includeSubDomains" />
    </customHeaders>
  </httpProtocol>
</system.webServer>
----

Unlike ASP.NET Core, where security headers are typically added via middleware in `Program.cs`, MVC 5's
`System.Web` hosting model most commonly sets them declaratively in IIS/`web.config`, applying to every
response including static files IIS serves directly.

== SQL injection with EF6

Parameterization is the default and correct defense: LINQ-to-Entities queries and EF6's `SqlQuery`/`SqlCommand`
overloads that take FormattableString or explicit ``SqlParameter``s are safe; string-concatenated raw SQL is not:

[source,csharp]
----
// Safe -- LINQ translates to a parameterized query
var product = db.Products.SingleOrDefault(p => p.Name == name);

// Safe -- parameterized raw SQL
db.Database.SqlQuery<Product>("SELECT * FROM Products WHERE Name = @p0", name);

// NEVER: string concatenation into raw SQL
// db.Database.SqlQuery<Product>("SELECT * FROM Products WHERE Name = '" + name + "'");
----

See xref:web/aspnet/mvc/data-access-ef6.adoc[Data Access with EF6] for EF6 query patterns in general.

== `machineKey` in farms

`<machineKey>` derives the keys used to encrypt/validate Forms Authentication tickets, view state (where still
used), and by default the antiforgery token. In a web farm, every instance must share the **same**
`machineKey`, or a request handled by one server and validated by another (a token issued by server A, checked
by server B) fails -- either intermittently invalidating antiforgery tokens or, worse, silently falling back to
per-machine keys that make CSRF tokens issued by one server unusable elsewhere:

[source,xml]
----
<system.web>
  <machineKey validationKey="..." decryptionKey="..." validation="SHA1" decryption="AES" />
</system.web>
----

== `[RequireHttps]`, HSTS, cookie `secure`/`httpOnly`

[source,csharp]
----
[RequireHttps]                          // authorization filter -- 301-redirects HTTP to HTTPS
public class AccountController : Controller { }
----

[source,xml]
----
<system.web>
  <httpCookies httpOnlyCookies="true" requireSSL="true" />
</system.web>
----

HSTS itself is set via the `Strict-Transport-Security` custom header shown above -- MVC 5 has no first-class
HSTS middleware equivalent to ASP.NET Core's `UseHsts()`.

== The OWASP Top 10 mapped onto MVC 5

[cols="1,2"]
|===
| OWASP category | MVC 5 mitigation

| Broken Access Control | `[Authorize]`/`+[Authorize(Roles=...)]+` filters; `[ValidateAntiForgeryToken]`; see
  xref:web/aspnet/mvc/filters.adoc[Filters].
| Cryptographic Failures | `[RequireHttps]`, `requireSSL` cookies, a shared `machineKey` across a farm.
| Injection | LINQ-to-Entities / parameterized `SqlQuery` (see xref:web/aspnet/mvc/data-access-ef6.adoc[Data
  Access with EF6]); never string-concatenated SQL.
| Insecure Design | View models instead of binding directly to entities (see
  xref:web/aspnet/mvc/model-binding-and-validation.adoc[Model Binding and Validation]) to avoid over-posting.
| Security Misconfiguration | `debug="false"`, `customErrors mode="On"`, `httpOnlyCookies`, custom security
  headers.
| Vulnerable and Outdated Components | Keeping `Microsoft.AspNet.Mvc`/`WebApi`/Json.NET NuGet versions current
  -- MVC 5 receives security-only patches (see xref:web/aspnet/mvc/index.adoc[the section landing page]).
| Identification and Authentication Failures | ASP.NET Identity 2's lockout, password validators, two-factor
  support (see xref:web/aspnet/mvc/authentication-identity-and-owin.adoc[Authentication, Identity, and OWIN]).
| Software and Data Integrity Failures | Request validation, `[AllowHtml]` used narrowly and paired with
  sanitization.
| Security Logging and Monitoring Failures | ELMAH, `Application_Error`, `<system.diagnostics>` tracing (see
  xref:web/aspnet/mvc/testing-and-diagnostics.adoc[Testing and Diagnostics]).
| Server-Side Request Forgery | Validate and allow-list any server-side outbound URL built from user input
  (image proxies, webhooks) -- no framework-level mitigation exists.
|===

== Deep dive: defaults that fail closed, and the layers around one admin action

The most reliable MVC 5 hardening is to make the safe behavior the default, so that a forgotten attribute on a new action
cannot open a hole. The framework opts nothing in for you: `[Authorize]` and `[ValidateAntiForgeryToken]` are opt-in per
action, which means every new action is open and unprotected until somebody remembers. Two global filters invert that.

[mermaid]
....
flowchart TD
    A[POST /Admin/Products/Edit] --> B{HTTPS? RequireHttps}
    B -->|no| X1[Redirect to https]
    B --> C{Authenticated? global Authorize}
    C -->|no| X2[401 or redirect to login]
    C --> D{Anti-forgery token valid? global filter}
    D -->|no| X3[HttpAntiForgeryException]
    D --> E[Request validation: markup in form values rejected]
    E --> F[Model binding with a view model, not the entity]
    F --> G[DataAnnotations validation]
    G --> H[EF6 parameterized SQL]
    H --> I[Razor encodes on output]
....

=== Worked example: default-deny authorization and automatic CSRF validation

`[Authorize]` registered as a global filter protects every action; the few public ones (login, a public catalog page)
are marked `[AllowAnonymous]`. MVC 5 has no built-in equivalent of Core's automatic anti-forgery validation, but an
authorization filter that validates the token for every unsafe HTTP method is a few lines:

[source,csharp]
----
using System;
using System.Web.Helpers;
using System.Web.Mvc;

[AttributeUsage(AttributeTargets.Class | AttributeTargets.Method, AllowMultiple = false)]
public sealed class AutoValidateAntiForgeryAttribute : FilterAttribute, IAuthorizationFilter
{
    public void OnAuthorization(AuthorizationContext filterContext)
    {
        var request = filterContext.HttpContext.Request;
        var method = request.HttpMethod;
        if (method == "GET" || method == "HEAD" || method == "OPTIONS" || method == "TRACE") return;

        // Ajax calls may send the form token in a header instead of the body.
        var headerToken = request.Headers["X-CSRF-Token"];
        if (!string.IsNullOrEmpty(headerToken))
        {
            var cookie = request.Cookies[AntiForgeryConfig.CookieName];
            AntiForgery.Validate(cookie?.Value, headerToken);
        }
        else
        {
            AntiForgery.Validate();                                       // cookie token + __RequestVerificationToken field
        }
    }
}

public class FilterConfig
{
    public static void RegisterGlobalFilters(GlobalFilterCollection filters)
    {
        filters.Add(new RequireHttpsAttribute());
        filters.Add(new AuthorizeAttribute());                            // everything requires login ...
        filters.Add(new AutoValidateAntiForgeryAttribute());              // ... and every POST needs a token
        filters.Add(new HandleErrorAttribute());
    }
}
----

[source,javascript]
----
// Layout: every jQuery ajax call sends the token header automatically.
var token = $('form#antiforgery input[name="__RequestVerificationToken"]').val();
$.ajaxSetup({ headers: { "X-CSRF-Token": token } });
----

In `_Layout.cshtml`, `+@using (Html.BeginForm(null, null, FormMethod.Post, new { id = "antiforgery" })) { @Html.AntiForgeryToken() }+`
renders the hidden form the script reads. `AntiForgery.Validate` throws `HttpAntiForgeryException` on a missing or
mismatched token; map it to a 400 or 403 in a global exception filter rather than letting the default error page leak a
stack trace.

=== Where each attack is stopped

[cols="2,3"]
|===
| Attack on the product edit action | Layer that stops it

| A forged cross-site `POST` that changes a price | The anti-forgery token (global filter above); the attacker's
  page cannot read the victim's token.
| A posted `IsActive=false` or `Id=7` the form never offered (over-posting) | Binding to `ProductEditModel` that has
  no such property, or `[Bind(Include = "Name,Price")]`.
| `<script>` in the product description shown to other users | Razor encoding on output; `Html.Raw` only after
  sanitizing; request validation as a second line.
| `returnUrl=http://evil.example` after login | `Url.IsLocalUrl` check before redirecting.
| `+Name = "x'; DROP TABLE Products;--"+` | EF6 parameterized queries; with raw SQL, `SqlParameter` values and never string
  concatenation.
| Sniffing the session or authentication cookie | `RequireHttps`, `requireSSL="true"` on `httpCookies` and `forms`,
  `Secure` and `HttpOnly` flags.
| Embedding the admin page in a hostile frame | `X-Frame-Options: DENY` or CSP `frame-ancestors` from `web.config`.
|===

No single layer is enough, and each depends on a configuration detail that is easy to lose: the CSRF cookie is only
`Secure` when `AntiForgeryConfig.RequireSsl = true`, `HandleError` does nothing with `customErrors` off, and request
validation is bypassed by `[AllowHtml]` and by `[ValidateInput(false)]`. Review these three settings first in an audit.

See https://learn.microsoft.com/en-us/aspnet/mvc/overview/security/[ASP.NET MVC Security] and
https://owasp.org/www-project-top-ten/[the OWASP Top 10].

See also https://learn.microsoft.com/en-us/aspnet/mvc/overview/security/xsrfcsrf-prevention-in-aspnet-mvc-and-web-pages[XSRF/CSRF
Prevention in ASP.NET MVC and Web Pages] for the token mechanics, and
https://learn.microsoft.com/en-us/dotnet/api/system.web.helpers.antiforgery[AntiForgery] for the validation overloads.
