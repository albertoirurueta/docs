== `RouteCollection` and `RouteTable`

`RouteTable.Routes` is the single, process-wide `RouteCollection` that `UrlRoutingModule` matches every request
against (see xref:web/aspnet/mvc/mvc-pattern-and-request-lifecycle.adoc[The MVC Pattern and Request Life
Cycle]). Convention routes are registered with `MapRoute`, in order, from `RouteConfig.RegisterRoutes`:

[source,csharp]
----
public class RouteConfig
{
    public static void RegisterRoutes(RouteCollection routes)
    {
        routes.IgnoreRoute("{resource}.axd/{*pathInfo}");

        routes.MapRoute(
            name: "ProductDetails",
            url: "products/{id}",
            defaults: new { controller = "Products", action = "Details" },
            constraints: new { id = @"\d+" });                       // regex constraint

        routes.MapRoute(
            name: "Default",
            url: "{controller}/{action}/{id}",
            defaults: new { controller = "Home", action = "Index", id = UrlParameter.Optional });
    }
}
----

* **Defaults** (`UrlParameter.Optional`) make a segment optional; a URL missing that segment still matches.
* **Constraints** accept either a regex `string` per segment or a custom `IRouteConstraint`.
* **`IgnoreRoute`** marks URLs (e.g. `+*.axd+` handler paths) that routing should never intercept.
* **Order matters**: `RouteCollection` tries routes in registration order and stops at the first match -- a
  more specific route (like `ProductDetails` above) must be registered *before* a catch-all `Default` route or
  it is never reached.

image::aspnet-mvc-route-matching.svg["Route matching walks the route table in order and stops at the first match",width=780,role=text-center]

A custom constraint implements `IRouteConstraint.Match` for logic a regex cannot express (e.g. checking a
database):

[source,csharp]
----
public class ActiveProductConstraint : IRouteConstraint
{
    public bool Match(HttpContextBase httpContext, Route route, string parameterName,
        RouteValueDictionary values, RouteDirection routeDirection)
        => int.TryParse(values[parameterName]?.ToString(), out var id) && ProductStore.IsActive(id);
}
----

See https://learn.microsoft.com/en-us/aspnet/mvc/overview/older-versions-1/controllers-and-routing/asp-net-mvc-routing-overview-cs[ASP.NET
MVC Routing Overview].

== Attribute routing

`MapMvcAttributeRoutes()` (called once, typically before the convention routes) enables `[Route]`/`[RoutePrefix]`
on controllers and actions, matched *before* convention routes in the pipeline regardless of registration
position:

[source,csharp]
----
public static void RegisterRoutes(RouteCollection routes)
{
    routes.MapMvcAttributeRoutes();
    routes.MapRoute("Default", "{controller}/{action}/{id}",
        new { controller = "Home", action = "Index", id = UrlParameter.Optional });
}

[RoutePrefix("products")]
public class ProductsController : Controller
{
    [Route("")]
    [Route("~/catalog")]                          // "~/" overrides the prefix entirely
    public ActionResult Index() => View();

    [Route("{id:int:min(1)}", Name = "ProductDetails")]   // inline constraint + a named route
    public ActionResult Details(int id) => View();

    [Route("{category}/{page:int=1}")]             // optional segment with a default value
    public ActionResult Browse(string category, int page) => View();
}
----

Inline constraints (`:int`, `:min(1)`, `+:regex(...)+`, `:alpha`, ...) live directly in the route template; a
`Name` lets `Url.RouteUrl`/`Html.RouteLink` generate URLs from that specific route regardless of which one
would otherwise match first. See
https://learn.microsoft.com/en-us/aspnet/mvc/overview/older-versions-2/attribute-routing/attribute-routing-in-asp-net-mvc-5[Attribute
Routing in ASP.NET MVC 5].

== `UrlHelper`, `Html.ActionLink`, `Url.Action`

Generating URLs from route values (rather than hardcoding paths) keeps links in sync with routing changes:

[source,csharp]
----
string url = Url.Action("Details", "Products", new { id = 42 });     // "/products/42" or "/products/details/42"
----

[source,cshtml]
----
@Html.ActionLink("View product", "Details", "Products", new { id = 42 }, null)
<a href="@Url.Action("Details", "Products", new { id = 42 })">View product</a>
----

Both resolve through the same `RouteCollection.GetVirtualPath`, so a route change is reflected everywhere links
are generated this way instead of only where URLs happen to be typed literally.

== Areas

An **area** is a self-contained slice of an application -- its own `Controllers`, `Views`, and (usually) a
distinct route namespace -- registered through an `AreaRegistration`:

[source,csharp]
----
// Areas/Admin/AdminAreaRegistration.cs
public class AdminAreaRegistration : AreaRegistration
{
    public override string AreaName => "Admin";

    public override void RegisterArea(AreaRegistrationContext context)
    {
        context.MapRoute(
            "Admin_default",
            "Admin/{controller}/{action}/{id}",
            new { action = "Index", id = UrlParameter.Optional });
    }
}
----

[source,text]
----
/Areas/Admin/Controllers/UsersController.cs
/Areas/Admin/Views/Users/Index.cshtml
/Areas/Admin/Views/web.config
----

`AreaRegistration.RegisterAllAreas()`, called from `Application_Start` before `RouteConfig.RegisterRoutes`,
reflects over the assembly and invokes every `AreaRegistration`{apos}s `RegisterArea`. **Ambiguous-controller
pitfall**: if both `/Controllers/UsersController.cs` and `/Areas/Admin/Controllers/UsersController.cs` exist,
`DefaultControllerFactory` can throw "multiple types were found that match the controller named 'Users'"
unless the area route's `namespaces` constraint (or `DataTokens["Namespaces"]`) disambiguates which
`UsersController` it means:

[source,csharp]
----
context.MapRoute("Admin_default", "Admin/{controller}/{action}/{id}",
    new { action = "Index", id = UrlParameter.Optional },
    namespaces: new[] { "MyApp.Areas.Admin.Controllers" });
----

== Deep dive: URLs in both directions

Routing is bidirectional. The same `RouteCollection` that turns `/products/42` into `controller=Products`,
`action=Details`, `id=42` also turns `+Url.Action("Details", "Products", new { id = 42 })+` back into `/products/42`.
Inbound matching stops at the first route that matches; outbound generation does the equivalent and stops at the
first route that can *produce* a URL from the supplied values. That symmetry is why a slightly wrong route order
breaks links and not only incoming requests.

[mermaid]
....
sequenceDiagram
    participant V as View or controller
    participant U as UrlHelper
    participant R as RouteTable.Routes
    V->>U: Url.Action("Details", "Products", new id = 42)
    U->>U: merge explicit values with the ambient values of the current request
    U->>R: GetVirtualPath(requestContext, values)
    loop each route in registration order
        R->>R: does the route accept these values (constraints, required segments)?
    end
    R-->>U: first VirtualPathData - /products/42
    U-->>V: /products/42
....

=== Worked example: three catalog routes and what each link generates

[source,csharp]
----
public static void RegisterRoutes(RouteCollection routes)
{
    routes.IgnoreRoute("{resource}.axd/{*pathInfo}");
    routes.LowercaseUrls = true;                      // /products/42 instead of /Products/42

    routes.MapRoute("ProductDetails", "products/{id}",
        new { controller = "Products", action = "Details" }, new { id = @"\d+" });

    routes.MapRoute("ProductSearch", "products/search/{term}",
        new { controller = "Products", action = "Search", term = UrlParameter.Optional });

    routes.MapRoute("Default", "{controller}/{action}/{id}",
        new { controller = "Home", action = "Index", id = UrlParameter.Optional });
}
----

[cols="2,1,2"]
|===
| Call | Generated URL | Why

| `+Url.Action("Details", "Products", new { id = 42 })+` | `/products/42` | The first route needs `id` and accepts a
  number.
| `+Url.Action("Details", "Products", new { id = "abc" })+` | `/products/details/abc` | The regex constraint rejects
  `abc` for the first route, so generation falls through to `Default`.
| `+Url.Action("Search", "Products", new { term = "mouse" })+` | `/products/search/mouse` | `ProductDetails` supplies
  `action=Details` as a default, which conflicts with `Search`, so it is skipped.
| `Url.Action("Index", "Products")` from a page with no `id` | `/products` | Only `Default` has no required `id`; the optional `id` and the
  default `action=Index` are dropped from the URL.
|===

The incoming URL `/products/search` hides a trap that the table does not show: `ProductDetails` is registered
first, but its `pass:c[\d+]` constraint rejects `search`, which is the only reason `ProductSearch` is reachable. Remove the
constraint and `/products/search` would be matched by `ProductDetails` with `id=search`. Constraints, defaults and
order together decide which route owns a URL, so test every pattern with a route test (see
xref:web/aspnet/mvc/testing-and-diagnostics.adoc[Testing and Diagnostics]).

=== Ambient values: the surprise in outbound links

`Url.Action` merges the values you pass with the *ambient* values of the current request, but an ambient value is
reused only for segments to the left of the first segment whose value differs. On a page served by
`/Products/Details/42`, `Url.Action("Details")` produces `/Products/Details/42`: nothing to the left of `id` changed,
so `id` is carried over. `Url.Action("Edit")` produces `/Products/Edit` instead, because `action` changed and the
`id` to its right is discarded; write `+Url.Action("Edit", new { id = 42 })+` when the link needs it. When a generated
link has an unexpected `id`, or a missing one, ambient values are the first thing to check, and passing the value
explicitly removes the guesswork.

=== Attribute routes next to convention routes

[source,csharp]
----
// RouteConfig.RegisterRoutes -- attribute routes must be mapped BEFORE the convention routes
routes.MapMvcAttributeRoutes();
routes.MapRoute("Default", "{controller}/{action}/{id}",
    new { controller = "Home", action = "Index", id = UrlParameter.Optional });

[RoutePrefix("catalog")]
public class CatalogController : Controller
{
    [Route("")]                              // /catalog
    public ActionResult Index() => View();

    [Route("{sku:length(8)}")]               // /catalog/ABC-1234 -- inline constraint
    public ActionResult BySku(string sku) => View();

    [Route("~/legacy-products/{id:int}")]    // ~ ignores the prefix
    public ActionResult Legacy(int id) => RedirectToActionPermanent("BySku", new { sku = "ABC-" + id.ToString("0000") });
}
----

An action that has an attribute route is no longer reachable through the convention routes (the attribute route
replaces its convention URL), which is useful when moving a URL space incrementally. The built-in inline constraints
are `alpha`, `bool`, `datetime`, `decimal`, `double`, `float`, `guid`, `int`, `length`, `long`, `max`, `maxlength`,
`min`, `minlength`, `range` and `regex`.

See https://learn.microsoft.com/en-us/aspnet/mvc/overview/older-versions-1/areas/areas-in-aspnet-mvc[Areas in
ASP.NET MVC].

Routing in ASP.NET MVC 5] and
https://learn.microsoft.com/en-us/dotnet/api/system.web.routing.routecollection[RouteCollection] for the outbound
