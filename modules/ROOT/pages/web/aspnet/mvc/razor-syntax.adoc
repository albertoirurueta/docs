= Razor Syntax

This page documents the Razor view engine as it ships with ASP.NET MVC 5.3.x / Web Pages 3 on .NET Framework
4.8.1 -- not ASP.NET Core's Razor, which adds Tag Helpers and Blazor component syntax on top of the same
expression language (see xref:web/aspnet/core/razor-syntax-and-tag-helpers.adoc[Razor Syntax and Tag Helpers]).

== Where Razor came from

Razor shipped in **January 2011** as part of MVC 3, alongside **ASP.NET Web Pages 1** -- a lightweight,
non-MVC way to build `.cshtml` sites. It replaced the original MVC 1/2 **WebForms view engine**
(`.aspx`/`.ascx` views with `<%= %>`/`<%: %>` code-nuggets and a `ViewPage` base class inherited from Web
Forms), which was verbose, easy to mis-encode, and dragged in Web Forms concepts (the page directive, control
parsing) that MVC's action/view model did not need. Razor was designed from scratch for view templates: a
minimal-punctuation syntax the parser can distinguish from literal markup by context, HTML-encoding by default,
and no dependency on the Web Forms control tree.

== Implicit and explicit expressions

[source,cshtml]
----
<p>Hello, @Model.UserName!</p>              <!-- implicit expression: @ + a single identifier/member chain -->
<p>Total: @(Model.Price * Model.Quantity)</p>  <!-- explicit expression: @( ... ) for anything the parser can't disambiguate -->
----

== Code blocks

[source,cshtml]
----
@{
    var greeting = "Welcome back";
    ViewBag.Title = "Home";
}
<h1>@greeting, @Model.UserName</h1>
----

== `@:` and `<text>`

Inside a code block, a line of literal text needs an explicit marker so Razor doesn't try to parse it as C#:

[source,cshtml]
----
@foreach (var item in Model.Items)
{
    @:Item: @item.Name          <!-- single line of literal markup -->
    <text>Qty: @item.Quantity</text>   <!-- multi-token literal run without wrapping HTML -->
}
----

== Comments

[source,cshtml]
----
@* This comment never reaches the rendered output, unlike an HTML <!-- --> comment. *@
----

== Automatic HTML encoding and `Html.Raw`

Every `@`-expression is HTML-encoded by default, which is what makes Razor safe against reflected XSS by
default (see xref:web/aspnet/mvc/security-hardening.adoc[Security Hardening]):

[source,cshtml]
----
<p>@Model.Comment</p>              <!-- "<script>" is encoded to "&lt;script&gt;" -->
<div>@Html.Raw(Model.TrustedHtml)</div>   <!-- opt out ONLY for content you generated/sanitized yourself -->
----

`Html.Raw` must never be used on user-supplied input without sanitizing it first -- it is the single most common
source of stored/reflected XSS in MVC 5 codebases.

== `@model`, `@using`, `@inherits`, `@functions`, `@helper`

[source,cshtml]
----
@model MyApp.Models.ProductViewModel
@using MyApp.Helpers
@inherits System.Web.Mvc.WebViewPage<MyApp.Models.ProductViewModel>   <!-- rarely needed; @model implies this -->

<h1>@Model.Name</h1>

@helper Star(int filled)                <!-- an inline, reusable markup-producing helper, scoped to this view -->
{
    for (int i = 0; i < 5; i++) { <span class="@(i < filled ? "on" : "off")">*</span> }
}
@Star(Model.Rating)

@functions {
    // C# members (not markup-producing) usable elsewhere in the same view
    string FormatPrice(decimal p) => p.ToString("C");
}
<p>@FormatPrice(Model.Price)</p>
----

`@model` is sugar for `@inherits System.Web.Mvc.WebViewPage<T>`, giving the view a strongly typed `Model`.

== `_ViewStart.cshtml`

`Views/_ViewStart.cshtml` (and an area-local `+Views/\{Area}/_ViewStart.cshtml+`) runs before every view in its
folder and below, and conventionally sets the shared `Layout`:

[source,cshtml]
----
@{
    Layout = "~/Views/Shared/_Layout.cshtml";
}
----

== `Views/web.config` namespaces

Namespaces listed in `Views/web.config` under `<system.web.webPages.razor><pages><namespaces>` are available to
every view without an explicit `@using` (see
xref:web/aspnet/mvc/getting-started.adoc[Getting Started] for the full snippet) -- `System.Web.Mvc.Html` (the
HTML helpers, see xref:web/aspnet/mvc/html-helpers-and-forms.adoc[HTML Helpers and Forms]) is imported this way
by default.

== ASP.NET Web Pages 3: the third framework of this era

**ASP.NET Web Pages** is `.cshtml` Razor *without* MVC -- a page-per-file model closer to classic ASP or PHP
than to MVC's controller/action separation, aimed at simple sites. It shares the Razor parser and
`Microsoft.AspNet.WebPages` runtime with MVC (see
xref:web/aspnet/mvc/getting-started.adoc[Getting Started]) but has its own conventions:

[source,cshtml]
----
@{
    // default.cshtml -- the file itself is the "action"
    Page.Title = "Home";
}
<h1>@Page.Title</h1>
@RenderPage("~/_nav.cshtml")           <!-- Web Pages' equivalent of a partial -->
----

* An `App_Start/_AppStart.cshtml` runs once at startup, analogous to MVC's `Application_Start`.
* `WebSecurity` (`Microsoft.Web.WebPages.OAuth` / `WebMatrix.WebData`) provided Web Pages' own membership and
  OAuth login support, parallel to (and predating) ASP.NET Identity -- see
  xref:web/aspnet/mvc/authentication-identity-and-owin.adoc[Authentication, Identity, and OWIN].
* Web Pages is rarely chosen for new work even within the MVC 5 era; it is documented here because it explains
  why `Microsoft.AspNet.WebPages` appears as a dependency of every MVC 5 project even when no `.cshtml` file is
  ever rendered outside the `Views` folder.

== Deep dive: how a `.cshtml` file becomes HTML

A Razor view is not interpreted. The first time a view is requested, the Razor parser turns the file into a C# class
that derives from `System.Web.Mvc.WebViewPage<TModel>`, the class is compiled into a dynamic assembly (kept under
`Temporary ASP.NET Files`), and every later request simply instantiates that class and calls its `Execute` method.
Understanding the generated shape explains most Razor behavior: why a syntax error appears only when the page is
first requested, why `@Model` is strongly typed, and where encoding happens.

[mermaid]
....
flowchart LR
    A[Index.cshtml] --> B[Razor parser: markup and code blocks]
    B --> C[Generated C# class deriving WebViewPage of IEnumerable of Product]
    C --> D[CodeDom compiler: dynamic assembly]
    D --> E[Instance created per request]
    E --> F[Execute writes literals with WriteLiteral and expressions with Write]
    F --> G[HTML response]
    H[ViewStart and Layout files] --> E
....

=== Worked example: the generated code for a product row

Given this fragment from the catalog's `Details.cshtml`:

[source,html]
----
@model MyApp.Models.Product
@helper PriceTag(decimal price)
{
    <span class="@(price > 100 ? "price high" : "price")">@price.ToString("C")</span>
}

<h2>@Model.Name</h2>
<p>@PriceTag(Model.Price)</p>
<p>Total with tax: @(Model.Price * 1.21m)</p>
@Html.Raw("<em>trusted</em>")
----

the compiler produces, in essence (simplified; the real output also contains line pragmas and generated attribute
helpers), the following:

[source,csharp]
----
public class _Page_Views_Products_Details_cshtml : System.Web.Mvc.WebViewPage<MyApp.Models.Product>
{
    public static System.Web.WebPages.HelperResult PriceTag(decimal price) { /* WriteLiteralTo / WriteTo calls */ }

    public override void Execute()
    {
        WriteLiteral("\r\n<h2>");
        Write(Model.Name);                       // HTML-encoded: Write(object) encodes unless it is an IHtmlString
        WriteLiteral("</h2>\r\n<p>");
        Write(PriceTag(Model.Price));            // HelperResult is an IHtmlString, written as is
        WriteLiteral("</p>\r\n<p>Total with tax: ");
        Write(Model.Price * 1.21m);              // explicit expression, still encoded
        WriteLiteral("</p>\r\n");
        Write(Html.Raw("<em>trusted</em>"));     // IHtmlString: no encoding
    }
}
----

Three rules follow directly from this shape:

* **Everything between `@` and the end of the expression goes through `Write`**, which calls
  `HttpUtility.HtmlEncode` on strings and passes `IHtmlString` values (`MvcHtmlString`, `HelperResult`, the result of
  `Html.Raw`) through untouched. That is the whole mechanism behind Razor's automatic encoding.
* **Markup is `WriteLiteral`**: it is never encoded and never evaluated, so a literal `<script>` in a template is
  safe and a literal `@` must be written `@@` (an e-mail address such as `team@example.com` is recognized as an
  address and left alone, but `@` before an identifier starts code).
* **`@helper` becomes a static method on the page class** and so is visible to that page only. To share a helper
  between views, place it in `App_Code` (one file per helper set) or write an extension method on `HtmlHelper`
  instead; see xref:web/aspnet/mvc/html-helpers-and-forms.adoc[HTML Helpers and Forms].

=== `@functions` and compile-time errors

`+@functions { ... }+` injects members into the generated class, which is why it can declare fields and methods that
every expression of the page can use, and why it should stay small (a page class is created for every request):

[source,html]
----
@functions {
    static string Badge(Product p) => p.Price > 100m ? "premium" : "standard";
}
<span class="badge @Badge(Model)">@Badge(Model)</span>
----

An error such as an unbalanced brace or an undeclared name is reported as a compilation error the first time the
view is requested ("Compiler Error Message: CS0103") and cannot be found by building the web project. Precompile the
views at publish time (`MvcBuildViews` in the project file, or RazorGenerator; see
xref:web/aspnet/mvc/views-layouts-and-partials.adoc[Views, Layouts, and Partials]) to move those errors into the
build.
