= The MVC Pattern and Request Life Cycle
:description: How Model/View/Controller applies to ASP.NET MVC 5, and how a request travels from UrlRoutingModule through MvcRouteHandler, MvcHandler, IControllerFactory, IActionInvoker, an action, ActionResult.ExecuteResult, and the view engine -- plus MVC vs Web Forms.
:keywords: ASP.NET MVC 5, request life cycle, UrlRoutingModule, MvcRouteHandler, MvcHandler, IControllerFactory, IActionInvoker, ActionResult, ExecuteResult, RazorViewEngine, Model View Controller

include::partial$ai-disclaimer.adoc[]

This page documents ASP.NET MVC 5.3.x on .NET Framework 4.8.1 -- not ASP.NET Core MVC. It traces one request
end to end and explains where each extensibility point sits.

== Model, View, Controller as applied here

* **Model** -- plain C# classes (POCOs), commonly EF6 entities or dedicated view models -- see
  xref:web/aspnet/mvc/data-access-ef6.adoc[Data Access with EF6]. MVC imposes no base class on a model.
* **View** -- a `.cshtml` Razor template that renders a model to HTML (or another format). See
  xref:web/aspnet/mvc/razor-syntax.adoc[Razor Syntax].
* **Controller** -- a class deriving from `System.Web.Mvc.Controller`, grouping related action methods that
  handle requests, manipulate the model, and choose a view. See
  xref:web/aspnet/mvc/controllers-and-actions.adoc[Controllers and Actions].

Unlike Web Forms, where a page's markup and code-behind are tightly coupled to a `Control` tree and view state,
MVC deliberately separates these three concerns so each can be tested and replaced independently -- this is the
central architectural difference covered in the table below.

== The request pipeline, step by step

[mermaid]
....
sequenceDiagram
    participant C as Client
    participant URM as UrlRoutingModule
    participant MRH as MvcRouteHandler
    participant MH as MvcHandler
    participant CF as IControllerFactory
    participant Ctl as Controller
    participant AI as IActionInvoker
    participant AR as ActionResult
    participant VE as IViewEngine
    C->>URM: HTTP request
    URM->>URM: match RouteTable.Routes -> RouteData
    URM->>MRH: route's IRouteHandler
    MRH->>MH: GetHttpHandler() -> new MvcHandler(RequestContext)
    MH->>CF: CreateController(controllerName)
    CF->>Ctl: new HomeController(...)
    MH->>Ctl: Controller.Execute(RequestContext)
    Ctl->>AI: ActionInvoker.InvokeAction(...)
    AI->>AI: select action, bind parameters, run filters
    AI->>AR: invoke action -> ActionResult
    AR->>VE: ExecuteResult(ControllerContext)
    VE->>VE: FindView() -> RazorViewEngine renders .cshtml
    VE-->>C: HTTP response (HTML)
....

. **`UrlRoutingModule`** -- an `IHttpModule` registered in `web.config` that hooks `PostResolveRequestCache` and
  matches the incoming URL against `RouteTable.Routes` (populated by `RouteConfig.RegisterRoutes`; see
  xref:web/aspnet/mvc/routing-and-areas.adoc[Routing and Areas]). A match produces `RouteData` carrying the
  route's `IRouteHandler`.
. **`MvcRouteHandler`** -- the `IRouteHandler` that every `MapRoute` call implicitly wires up; its
  `GetHttpHandler` returns an `MvcHandler` for the matched `RequestContext`.
. **`MvcHandler`** -- the `IHttpHandler` (async, via `IHttpAsyncHandler`) that is MVC's actual entry point in the
  `System.Web` pipeline. It resolves an `IControllerFactory` (`ControllerBuilder.Current.GetControllerFactory`)
  and asks it to create the controller named in the route.
. **`IControllerFactory`**  -- `DefaultControllerFactory` locates a `Controller`-derived type by naming
  convention (`+\{name}Controller+`) and instantiates it, optionally through `IControllerActivator` so a DI
  container can supply constructor dependencies.
. **`IActionInvoker`** -- `ControllerActionInvoker` (via `Controller.ActionInvoker`) selects the action method
  using action selectors, binds its parameters via model binding (see
  xref:web/aspnet/mvc/model-binding-and-validation.adoc[Model Binding and Validation]), and runs the filter
  pipeline around the call (see xref:web/aspnet/mvc/filters.adoc[Filters]).
. **The action** returns an `ActionResult`; **`ActionResult.ExecuteResult`** is then called with the current
  `ControllerContext`. For `ViewResult` this locates and renders a view through the **view engine**
  (`RazorViewEngine`, resolved via the `ViewEngines.Engines` collection -- see
  xref:web/aspnet/mvc/views-layouts-and-partials.adoc[Views, Layouts, and Partials]).

See https://learn.microsoft.com/en-us/aspnet/mvc/overview/getting-started/lifecycle-of-an-aspnet-mvc-5-application[Lifecycle
of an ASP.NET MVC 5 Application] and
https://learn.microsoft.com/en-us/previous-versions/aspnet/ms178473(v=vs.100)[ASP.NET Application Life Cycle
Overview for IIS 7.0] for the underlying `System.Web` request pipeline that hosts all of this.

== Extensibility at each step

[cols="1,2"]
|===
| Step | Substitute by

| Route matching | A custom `RouteBase` (rarely needed; attribute routing and `MapRoute` cover almost every
  case).
| `IRouteHandler` | A custom `IRouteHandler` in place of `MvcRouteHandler` (uncommon).
| `IControllerFactory` | `+ControllerBuilder.Current.SetControllerFactory(...)+` -- the classic seam for wiring a
  DI container (Ninject, Autofac, Unity) into controller construction.
| `IActionInvoker` | `Controller.ActionInvoker` per controller, or a custom `IActionInvoker` for cross-cutting
  action-selection logic.
| `ActionResult` | Any custom `ActionResult` subclass overriding `ExecuteResult` (e.g. a CSV or PDF result).
| `IViewEngine` | `ViewEngines.Engines.Add(new MyViewEngine())` -- see
  xref:web/aspnet/mvc/views-layouts-and-partials.adoc[Views, Layouts, and Partials].
|===

== MVC vs. Web Forms

[cols="1,1,1"]
|===
| | ASP.NET MVC 5 | ASP.NET Web Forms

| Request entry point | `MvcHandler` via `UrlRoutingModule` | A `Page`-derived `IHttpHandler` per `.aspx` file
| UI unit | Action method returning an `ActionResult` | A `Page` with a server-side control tree
| State model | Stateless per request; explicit `TempData`/`Session` | `ViewState`, postbacks, control events
| Markup | Razor `.cshtml`, no code-behind coupling | `.aspx` + code-behind, `runat="server"` controls
| Testability | Controllers/actions unit-testable in isolation | Requires the ASP.NET runtime or heavy mocking
| HTML control | Full -- you own every tag | Partial -- server controls render their own markup
|===

== Deep dive: where MVC sits inside the `System.Web` pipeline

MVC does not own the request. It is one `IHttpHandler` that the ASP.NET pipeline selects, and before and after it the
same `HttpApplication` events fire that Web Forms and plain handlers see. Knowing the event order explains why
`Session` is unavailable in some modules, why `UrlRoutingModule` can remap the handler at all, and where a custom
`IHttpModule` can interfere with MVC.

[mermaid]
....
flowchart TD
    A[BeginRequest] --> B[AuthenticateRequest]
    B --> C[AuthorizeRequest]
    C --> D[ResolveRequestCache]
    D --> E[PostResolveRequestCache]
    E -->|UrlRoutingModule matches a route and remaps the handler| F[MapRequestHandler]
    F --> G[AcquireRequestState]
    G --> H[PreRequestHandlerExecute]
    H --> I[MvcHandler.ProcessRequest]
    I --> J[PostRequestHandlerExecute]
    J --> K[ReleaseRequestState]
    K --> L[UpdateRequestCache]
    L --> M[EndRequest]
    I -.-> N[Controller creation, filters, action, ActionResult.ExecuteResult, view rendering]
....

Authentication has already run (`AuthenticateRequest`, by `FormsAuthenticationModule` or an OWIN middleware stage) by
the time the controller is created, which is why `User` and `Request.IsAuthenticated` are populated inside an action.
Session state is acquired at `AcquireRequestState`, immediately before the handler runs. Everything inside the dotted
box is MVC; the dotted box is the part the rest of this page and the xref:web/aspnet/mvc/filters.adoc[Filters] page
dissect.

=== Worked example: tracing `GET /Products/Details/42`

The default route from `RouteConfig` is `+{controller}/{action}/{id}+` with `Home`/`Index` defaults. For the catalog URL
above the stages produce:

[cols="1,2"]
|===
| Stage | Result for `/Products/Details/42`

| `UrlRoutingModule` | `RouteData.Values` is `controller=Products`, `action=Details`, `id=42` (all strings).
| `MvcHandler` | Reads `controller` from the route values, asks the controller factory for `"Products"`.
| `DefaultControllerFactory` | Finds `ProductsController` in the build manager's list of controller types and
  creates it through its parameterless constructor or the registered `IControllerActivator`.
| `ControllerActionInvoker` | Finds `Details(int id)`, converts `"42"` to `42` through model binding, runs filters.
| `ViewResult.ExecuteResult` | Probes `+~/Views/Products/Details.cshtml+`, then `+~/Views/Shared/Details.cshtml+`,
  renders it inside `_Layout.cshtml`.
|===

A controller that takes constructor arguments fails with "No parameterless constructor defined for this object"
unless the factory is replaced. The smallest possible seam is a subclass of `DefaultControllerFactory`:

[source,csharp]
----
using System;
using System.Web.Mvc;
using System.Web.Routing;

public class CatalogControllerFactory : DefaultControllerFactory
{
    protected override IController GetControllerInstance(RequestContext requestContext, Type controllerType)
    {
        // controllerType is null when no controller matched the route; the base class turns that into a 404.
        if (controllerType == typeof(ProductsController))
        {
            return new ProductsController(new EfProductRepository());
        }

        return base.GetControllerInstance(requestContext, controllerType);
    }
}

public class MvcApplication : System.Web.HttpApplication
{
    protected void Application_Start()
    {
        ControllerBuilder.Current.SetControllerFactory(new CatalogControllerFactory());
        RouteConfig.RegisterRoutes(RouteTable.Routes);
    }
}
----

For anything beyond one or two controllers, register a DI container's `IDependencyResolver` with
`+DependencyResolver.SetResolver(...)+` instead: the default factory consults it through `IControllerActivator`, so no
factory subclass is needed.

=== Extending the end of the pipeline with a custom `ActionResult`

Because `ExecuteResult` is the last MVC step before bytes leave the process, a custom result is the cleanest way to
add a new response format. This one streams the catalog as CSV:

[source,csharp]
----
using System.Collections.Generic;
using System.Text;
using System.Web.Mvc;

public class CsvResult : ActionResult
{
    private readonly IEnumerable<Product> _rows;
    private readonly string _fileName;

    public CsvResult(IEnumerable<Product> rows, string fileName)
    {
        _rows = rows;
        _fileName = fileName;
    }

    public override void ExecuteResult(ControllerContext context)
    {
        var response = context.HttpContext.Response;
        response.ContentType = "text/csv";
        response.ContentEncoding = Encoding.UTF8;
        response.AddHeader("Content-Disposition", "attachment; filename=\"" + _fileName + "\"");

        response.Write("Id,Name,Price\r\n");
        foreach (var p in _rows)
        {
            response.Write(p.Id + ",\"" + p.Name.Replace("\"", "\"\"") + "\"," + p.Price.ToString("0.00",
                System.Globalization.CultureInfo.InvariantCulture) + "\r\n");
        }
    }
}

// In ProductsController:
public ActionResult Export() => new CsvResult(_repository.GetAll(), "products.csv");
----

The action stays unit-testable: a test calls `Export()` and asserts that the result is a `CsvResult`, without ever
touching `Response`.

authoritative event order and
https://learn.microsoft.com/en-us/aspnet/mvc/overview/older-versions/getting-started-with-ef-using-mvc/[the MVC 5 tutorials]
