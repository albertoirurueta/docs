== Layouts and `RenderBody`

A layout is a `.cshtml` file that wraps every view assigned to it, calling `@RenderBody()` exactly once where
the child view's content belongs:

[source,cshtml]
----
<!-- Views/Shared/_Layout.cshtml -->
<!DOCTYPE html>
<html>
<head><title>@ViewBag.Title</title></head>
<body>
    @Html.Partial("_Nav")
    <div class="container">@RenderBody()</div>
</body>
</html>
----

A view opts in with `+Layout = "~/Views/Shared/_Layout.cshtml";+` in a code block, or inherits it from
`_ViewStart.cshtml` (see xref:web/aspnet/mvc/razor-syntax.adoc[Razor Syntax]).

== Sections

`@section` defines a named block a layout can place anywhere with `RenderSection`; `required: false` (or
checking `IsSectionDefined`) makes a section optional:

[source,cshtml]
----
<!-- in the layout -->
<head>
    <title>@ViewBag.Title</title>
    @RenderSection("styles", required: false)
</head>
...
@RenderSection("scripts", required: false)
----

[source,cshtml]
----
<!-- in a view -->
@section scripts {
    <script src="~/Scripts/product-detail.js"></script>
}
@if (IsSectionDefined("styles")) { @RenderSection("styles") }
----

== Partial views: four ways to include one

[cols="1,2"]
|===
| Helper | Behavior

| `Html.Partial(name, model)` | Renders synchronously *into the current buffer* and returns an `MvcHtmlString`
  -- used as `+@Html.Partial(...)+`. Reuses the parent's `ViewData`/`ViewBag` unless overridden.
| `Html.RenderPartial(name, model)` | Writes *directly to the response stream* (`void`, no return value) --
  used as `+@{ Html.RenderPartial(...); }+`. Slightly cheaper for large partials since it skips buffering the
  result into a string first.
| `Html.Action(actionName, controllerName)` | Executes a **separate child action** (its own controller, its
  own model, its own filters) and returns its rendered output as a string, inserted into the current view.
| `Html.RenderAction(actionName, controllerName)` | The `RenderPartial` equivalent of `Html.Action` -- writes
  directly to the stream instead of returning a string.
|===

[source,cshtml]
----
@Html.Partial("_ProductSummary", Model.FeaturedProduct)
@{ Html.RenderPartial("_ProductSummary", Model.FeaturedProduct); }

@Html.Action("RecentOrders", "Orders")          <!-- runs OrdersController.RecentOrders() as a child request -->
----

`Html.Partial`/`Html.RenderPartial` share the *calling action's* model and view data -- no new controller
action runs. `Html.Action`/`Html.RenderAction` invoke a full child action, which is the right tool when a
fragment (a "recently viewed" widget, a shopping-cart summary) needs its own data access independent of the
page's main action -- see donut-hole caching in
xref:web/aspnet/mvc/caching-and-performance.adoc[Caching and Performance], and mark such actions
`[ChildActionOnly]` (see xref:web/aspnet/mvc/filters.adoc[Filters]) so they cannot be routed to directly.

== `_ViewStart.cshtml` chaining

`_ViewStart.cshtml` files run from the outermost applicable folder inward -- `Views/_ViewStart.cshtml` first,
then an area- or folder-specific one -- each able to override `Layout` set by the previous:

[source,text]
----
/Views/_ViewStart.cshtml            # sets the site-wide default layout
/Views/Admin/_ViewStart.cshtml      # overrides it for everything under Views/Admin
----

== Display and editor templates

`DisplayFor`/`EditorFor` render a strongly typed expression through a **template** resolved by type name (or
`[UIHint]`), searched first in `+~/Views/\{Controller}/DisplayTemplates+` (or `EditorTemplates`), then
`+~/Views/Shared/DisplayTemplates+`:

[source,cshtml]
----
@Html.DisplayFor(m => m.CreatedOn)         <!-- resolves ~/Views/Shared/DisplayTemplates/DateTime.cshtml if present -->
@Html.EditorFor(m => m.Price)
----

[source,csharp]
----
public class Product
{
    [DataType(DataType.Currency)]
    [UIHint("Currency")]                    // forces ~/Views/Shared/EditorTemplates/Currency.cshtml
    public decimal Price { get; set; }
}
----

[source,cshtml]
----
<!-- Views/Shared/EditorTemplates/Currency.cshtml -->
@model decimal
@Html.TextBox("", Model.ToString("F2"), new { @class = "currency-input" })
----

`[DataType]` picks a semantic template (`Currency`, `Date`, `MultilineText`, ...); `[UIHint]` names one
explicitly. See
https://learn.microsoft.com/en-us/aspnet/mvc/overview/older-versions-1/views/aspnet-mvc-templated-helpers-cs[ASP.NET
MVC Templated Helpers].

== The `ViewEngines` collection and custom view engines

`ViewEngines.Engines` is the ordered list `MvcHandler` searches (via `IViewEngine.FindView`) to locate a view
for a given controller/action/master-name; `RazorViewEngine` and the legacy `WebFormViewEngine` are registered
by default:

[source,csharp]
----
// Global.asax.cs, Application_Start
ViewEngines.Engines.Clear();
ViewEngines.Engines.Add(new RazorViewEngine());   // drop WebFormViewEngine entirely if no .aspx views remain
----

A custom `IViewEngine`/`VirtualPathProviderViewEngine` can change view-location conventions entirely (e.g.
feature-folder layouts) without touching controllers.

== View compilation and `RazorGenerator`

By default, `.cshtml` files are compiled **on first request** (or via `aspnet_compiler` at publish time), which
means a syntax error in a view surfaces only at runtime. **RazorGenerator** is a community tool (a custom tool
attached to `.cshtml` files in Visual Studio, or an MSBuild task) that precompiles views to `.cs` at build time,
producing compile-time errors for view syntax mistakes and slightly faster first-request latency, at the cost
of an extra build step. See
https://learn.microsoft.com/en-us/aspnet/mvc/overview/deployment/precompiling-your-mvc-application[Precompiling
Your MVC Application].

== Deep dive: view lookup, location formats and display modes

`View("Details")` does not name a file. `ViewResult.ExecuteResult` asks `+ViewEngines.Engines.FindView(...)+`, which
asks each registered engine in order; `RazorViewEngine` then expands its *location formats* by substituting `+{0}+`
(the view name), `+{1}+` (the controller name) and `+{2}+` (the area name) and checks whether a file exists. The first
hit wins, and the result is cached in `ViewLocationCache`, so the probing cost is paid once per view per process.

[mermaid]
....
flowchart TD
    A[View Details from ProductsController] --> B{ViewLocationCache hit?}
    B -->|yes| H[Use cached virtual path]
    B -->|no| C[Probe Views/Products/Details.cshtml]
    C -->|missing| D[Probe Views/Shared/Details.cshtml]
    D -->|missing| E[Probe the .vbhtml and .aspx variants]
    E -->|missing| F[InvalidOperationException listing every searched location]
    C -->|found| G[Cache the path]
    D -->|found| G
    G --> H
....

The exception message in the last branch is the most useful debugging aid in the view engine: it lists every path
that was tried, which is how a misplaced partial (a `_Rows.cshtml` created in `Views/Home` while called from
`ProductsController`) is found in seconds.

=== Worked example: a lean engine with feature folders

A default MVC 5 application probes `.aspx`, `.ascx` and `.vbhtml` paths that a C#-only Razor site never uses. Clearing
the engines and registering a Razor engine with project-specific locations removes that probing and lets the catalog
group its files by feature instead of by file type:

[source,csharp]
----
using System.Web.Mvc;

public class FeatureViewEngine : RazorViewEngine
{
    public FeatureViewEngine()
    {
        // {0} = view name, {1} = controller name
        ViewLocationFormats = new[]
        {
            "~/Features/{1}/{0}.cshtml",
            "~/Views/{1}/{0}.cshtml",
            "~/Views/Shared/{0}.cshtml",
        };
        PartialViewLocationFormats = ViewLocationFormats;
        MasterLocationFormats = new[] { "~/Views/Shared/{0}.cshtml" };
        FileExtensions = new[] { "cshtml" };
    }
}

// Global.asax.cs, Application_Start
ViewEngines.Engines.Clear();
ViewEngines.Engines.Add(new FeatureViewEngine());
----

Views under `+~/Features/Products/+` are now found before the conventional folder. An area-aware engine would also
need `AreaViewLocationFormats` (and the other two `+Area...+` arrays) with `+{2}+` for the area; if they are left at their
defaults, areas keep working through the conventional folders. Razor still needs a `web.config` in
`+~/Features+` (copy `Views/web.config`) so that the `@model` directive and the namespaces resolve in the new folder.

=== Display modes: mobile-specific views without a second site

`DisplayModeProvider` lets one action pick a different file by device. When a mode matches, MVC prefers
`Details.Mobile.cshtml` over `Details.cshtml` and falls back to the plain file when the suffixed one does not exist:

[source,csharp]
----
using System;
using System.Web.WebPages;

// Application_Start: a custom mode is evaluated before the built-in Mobile and Default modes.
DisplayModeProvider.Instance.Modes.Insert(0, new DefaultDisplayMode("Kiosk")
{
    ContextCondition = ctx => ctx.Request.Headers["X-Kiosk"] == "1"
});
----

With this registration, requests carrying the `X-Kiosk: 1` header render `Index.Kiosk.cshtml` when it exists. The same
suffix applies to layouts and partials, and `ViewContext.DisplayMode` tells a view which mode was selected. The
built-in `Mobile` mode relies on `HttpBrowserCapabilities.IsMobileDevice`, whose browser definitions are often stale;
prefer a responsive layout and keep display modes for the few views that genuinely need a different structure.

See also https://learn.microsoft.com/en-us/dotnet/api/system.web.mvc.razorviewengine[RazorViewEngine] for the full list
of location-format properties, and
https://learn.microsoft.com/en-us/aspnet/mvc/overview/older-versions/aspnet-mvc-4-mobile-features[ASP.NET MVC 4 Mobile
Features] for display modes.
