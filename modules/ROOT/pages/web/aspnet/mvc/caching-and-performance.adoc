== `[OutputCache]` and cache profiles

[source,csharp]
----
[OutputCache(Duration = 300, VaryByParam = "category;page", Location = OutputCacheLocation.Server)]
public ActionResult Index(string category, int page = 1) => View(_repository.Browse(category, page));
----

[source,xml]
----
<!-- web.config -->
<system.web>
  <caching>
    <outputCacheSettings>
      <outputCacheProfiles>
        <add name="ProductListing" duration="300" varyByParam="category;page" />
      </outputCacheProfiles>
    </outputCacheSettings>
  </caching>
</system.web>
----

[source,csharp]
----
[OutputCache(CacheProfile = "ProductListing")]
public ActionResult Index(string category, int page = 1) { ... }
----

A **cache profile** centralizes cache settings in `web.config` so they can be changed (or disabled entirely for
debugging) without recompiling, and reused across multiple actions.

== Donut caching and donut-hole caching

Caching an entire page is easy but breaks the moment part of that page is per-user (a "Welcome, Alice" header,
a cart count). Two patterns split the difference:

* **Donut caching** -- cache everything *except* a hole (the opposite naming convention some libraries use);
  effectively, cache the outer shell and leave a gap for personalized content, typically via a third-party
  library since `[OutputCache]` alone caches an entire action's output.
* **Donut-hole caching** -- the built-in MVC 5 approach: cache the *page* action normally, but render the
  personalized fragment through `Html.Action`/`Html.RenderAction` calling a **separate, `[ChildActionOnly]`**
  action that is *not* itself output-cached (or is cached with a much shorter, per-user duration):

[source,cshtml]
----
@{ Html.RenderAction("CartSummary", "Cart"); }   <!-- always executes fresh, even though the parent view is cached -->
----

[source,csharp]
----
[OutputCache(Duration = 300)]
public ActionResult Index() => View();            <!-- the whole page, cached -->

[ChildActionOnly]
public ActionResult CartSummary() => PartialView(_cart.GetSummary());   <!-- the "hole": never cached -->
----

See xref:web/aspnet/mvc/views-layouts-and-partials.adoc[Views, Layouts, and Partials] for `Html.Action`/
`Html.RenderAction`, and xref:web/aspnet/mvc/filters.adoc[Filters] for `[ChildActionOnly]` and `[OutputCache]`
as a result filter.

== `System.Runtime.Caching.MemoryCache` and the ASP.NET `Cache`

For caching values that aren't HTTP responses (a computed result, an external API call), MVC 5-era code
generally uses either the framework-agnostic `System.Runtime.Caching.MemoryCache` or the older, `System.Web`-
coupled `HttpContext.Cache`:

[source,csharp]
----
var cache = MemoryCache.Default;
var key = $"product:{id}";
if (!(cache.Get(key) is Product product))
{
    product = _repository.Find(id);
    cache.Set(key, product, DateTimeOffset.UtcNow.AddMinutes(10));
}
----

`MemoryCache` has no dependency on `System.Web`, making it usable from a service layer shared with, e.g.,
Web API self-hosting; `HttpContext.Cache` additionally supports cache-item dependencies tied to files or SQL
notifications.

== Response compression and static-content caching in IIS

[source,xml]
----
<system.webServer>
  <urlCompression doDynamicCompression="true" doStaticCompression="true" />
  <staticContent>
    <clientCache cacheControlMode="UseMaxAge" cacheControlMaxAge="365.00:00:00" />
  </staticContent>
</system.webServer>
----

Bundled scripts/styles already carry a cache-busting `v=` token (see
xref:web/aspnet/mvc/bundling-and-client-side-integration.adoc[Bundling and Client-Side Integration]), which is
what makes a far-future `clientCache` max-age safe for those URLs specifically.

== View precompilation

Compiling `.cshtml` on first request adds latency to that request and defers syntax errors to runtime;
`aspnet_compiler` (run at publish time, e.g. via a Web Deploy publish profile) or RazorGenerator (see
xref:web/aspnet/mvc/views-layouts-and-partials.adoc[Views, Layouts, and Partials]) both move that cost to build
time instead.

== Async all the way and thread-pool starvation

IIS serves each request from a limited thread-pool. A synchronous, blocking call inside an otherwise
`async`-looking chain (`.Result`, `.Wait()`, a genuinely synchronous EF6/`HttpClient` call) ties up a thread for
the full duration of that I/O instead of releasing it back to the pool -- under load, this exhausts the pool and
queues requests behind it (thread-pool starvation) even though the CPU itself is nearly idle:

[source,csharp]
----
// Starves a thread for the entire HTTP call
public ActionResult Bad() => Content(new HttpClient().GetStringAsync(url).Result);

// Releases the thread while awaiting
public async Task<ActionResult> Good() => Content(await new HttpClient().GetStringAsync(url));
----

"Async all the way" means every layer between the action and the actual I/O call is `async`/`await` -- see
xref:web/aspnet/mvc/controllers-and-actions.adoc[Controllers and Actions] for async action methods and
xref:web/aspnet/mvc/data-access-ef6.adoc[Data Access with EF6] for EF6's async query methods.

== `Server.MapPath` and synchronous I/O costs

`Server.MapPath` itself is cheap (a string translation), but the file I/O that often follows it
(`+File.ReadAllText(Server.MapPath("~/App_Data/config.json"))+`) is synchronous by default in `System.IO` unless
explicitly performed with `File.ReadAllTextAsync`/a `FileStream` opened with `useAsync: true` -- a common,
easy-to-miss source of the same thread-pool starvation described above when it happens inside a request.

== Deep dive: caching the product catalog, layer by layer

A catalog page can be cached at five places, each with a different scope and a different invalidation story. Picking
the layer is the design decision; the attributes and APIs are the easy part.

[mermaid]
....
flowchart LR
    A[Browser cache] -->|miss or expired| B[IIS kernel-mode and output cache]
    B -->|miss| C["OutputCache: whole ActionResult"]
    C -->|miss| D[Action runs]
    D --> E["MemoryCache: repository result"]
    E -->|miss| F[EF6 query against SQL Server]
....

[cols="1,1,2"]
|===
| Layer | Scope | Invalidation

| Browser (`Location = Client`) | One user | Only by expiry; the server cannot reach it, so avoid it for data that
  changes.
| `OutputCache` on the server | All users, per `VaryBy` key | Expiry, or `HttpResponse.RemoveOutputCacheItem(path)` from
  the code that writes the data.
| `MemoryCache` in a repository decorator | One process (one web-farm node) | Expiry or explicit `Remove`.
| EF6 first-level cache | One `DbContext`, one request | Disposed with the context -- not a cross-request cache.
|===

=== Worked example: output caching with explicit invalidation

The product list changes only when an administrator edits a product, so a short server-side cache with a *known*
invalidation point beats a long blind one:

[source,csharp]
----
public class ProductsController : Controller
{
    private readonly IProductRepository _repository;
    public ProductsController(IProductRepository repository) => _repository = repository;

    [OutputCache(Duration = 300, VaryByParam = "page;sort", Location = OutputCacheLocation.Server, NoStore = true)]
    public ActionResult Index(int page = 1, string sort = "name")
    {
        var all = _repository.GetAll();
        var ordered = sort == "price" ? all.OrderBy(p => p.Price) : all.OrderBy(p => p.Name);
        return View(ordered.Skip((page - 1) * 20).Take(20).ToList());
    }

    [HttpPost, ValidateAntiForgeryToken]
    public ActionResult Edit(ProductEditModel model)
    {
        if (!ModelState.IsValid) return View(model);
        _repository.Update(FromModel(model));

        // Drop every cached variant of /Products so the next request shows the change.
        Response.RemoveOutputCacheItem(Url.Action("Index", "Products"));
        return RedirectToAction("Index");
    }
}
----

`RemoveOutputCacheItem` removes entries by *path*; because `VaryByParam` created several entries under the same path,
all of them go together. `Location = Server` plus `NoStore = true` keeps proxies and browsers from holding on to a
stale list, and `VaryByParam` must list every parameter that changes the output, otherwise page 2 is served as page 1.
Never output-cache an action that renders `Html.AntiForgeryToken()` or any per-user content: the cached copy would be
served to everyone.

=== Worked example: a `MemoryCache` decorator for the repository

Caching below the controller keeps the cache testable and shared by every action that reads the same data. A
decorator wraps any `IProductRepository`:

[source,csharp]
----
using System;
using System.Collections.Generic;
using System.Linq;
using System.Runtime.Caching;

public class CachedProductRepository : IProductRepository
{
    private const string AllKey = "products:all";
    private readonly IProductRepository _inner;
    private readonly MemoryCache _cache;

    public CachedProductRepository(IProductRepository inner) : this(inner, MemoryCache.Default) { }
    public CachedProductRepository(IProductRepository inner, MemoryCache cache) { _inner = inner; _cache = cache; }

    public IEnumerable<Product> GetAll()
    {
        var cached = _cache.Get(AllKey) as IReadOnlyList<Product>;
        if (cached != null) return cached;

        var fresh = _inner.GetAll().ToList();                      // materialize BEFORE caching: never cache a query
        _cache.Set(AllKey, fresh, new CacheItemPolicy { AbsoluteExpiration = DateTimeOffset.UtcNow.AddMinutes(5) });
        return fresh;
    }

    public Product Find(int id) => GetAll().FirstOrDefault(p => p.Id == id);

    public void Add(Product product)    { _inner.Add(product);       _cache.Remove(AllKey); }
    public void Update(Product product) { _inner.Update(product);    _cache.Remove(AllKey); }
    public void Remove(int id)          { _inner.Remove(id);         _cache.Remove(AllKey); }
}
----

Two rules keep this safe: cache materialized objects (a cached `IQueryable` would run on a disposed `DbContext`, or
re-run on every enumeration), and treat cached objects as immutable (a controller that edits a cached `Product`
changes it for every user before the update is even saved). `MemoryCache` lives in one process, so on a web farm each
node holds its own copy; after a write the other nodes serve stale data until their entry expires. When that is not
acceptable, shorten the expiry, move the cache to a shared store such as Redis, or use `SqlDependency`.

== Profiling with MiniProfiler and Glimpse

* **MiniProfiler** -- a lightweight, always-on profiler that overlays timing for the request, nested custom
  steps, and (with the EF6 integration package) individual SQL queries directly in the rendered page.
* **Glimpse** -- a more heavyweight in-browser diagnostics panel (routes matched, model binding, SQL, session)
  installed as a set of NuGet packages per feature (`Glimpse.Mvc5`, `Glimpse.EF6`).

Both are development/staging tools and should not ship enabled to production by default. See
https://learn.microsoft.com/en-us/aspnet/mvc/overview/performance/[ASP.NET MVC Performance] and
https://learn.microsoft.com/en-us/aspnet/mvc/overview/performance/output-caching-for-asp-net-mvc[Improving
Performance with Output Caching].

See also https://learn.microsoft.com/en-us/dotnet/api/system.runtime.caching.memorycache[MemoryCache] and
https://learn.microsoft.com/en-us/dotnet/api/system.web.httpresponse.removeoutputcacheitem[HttpResponse.RemoveOutputCacheItem]
for the APIs used above.

Next: xref:web/aspnet/mvc/testing-and-diagnostics.adoc[Testing and Diagnostics] covers verifying these behaviors
with tests rather than by observation alone.
