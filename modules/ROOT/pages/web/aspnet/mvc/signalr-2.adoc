== Hubs and persistent connections

SignalR 2 offers two abstraction levels: the low-level **`PersistentConnection`** (raw message send/receive,
rarely used directly) and the high-level **`Hub`**, which exposes server methods clients call directly (an
RPC-like model) and lets the server call back into client-side JavaScript/.NET methods:

[source,csharp]
----
public class ChatHub : Hub
{
    public void Send(string user, string message)
        => Clients.All.receiveMessage(user, message);   // calls a client-side "receiveMessage" function
}
----

== `Startup.MapSignalR()`

SignalR 2 is OWIN-hosted (see xref:web/aspnet/mvc/authentication-identity-and-owin.adoc[Authentication,
Identity, and OWIN] for the shared OWIN pipeline) even inside an otherwise `System.Web`-hosted MVC 5
application:

[source,csharp]
----
[assembly: OwinStartup(typeof(MyApp.Startup))]
namespace MyApp
{
    public partial class Startup
    {
        public void Configuration(IAppBuilder app)
        {
            app.MapSignalR();                    // maps hubs at /signalr by default
        }
    }
}
----

== Hub methods, `Clients.All`/`Caller`/`Group`/`User`, groups

[source,csharp]
----
public class ChatHub : Hub
{
    public override Task OnConnected()
    {
        Clients.Caller.welcome("Connected!");
        return base.OnConnected();
    }

    public Task JoinRoom(string room)
        => Groups.Add(Context.ConnectionId, room);

    public Task SendToRoom(string room, string message)
        => Clients.Group(room).receiveMessage(Context.User.Identity.Name, message);

    public Task SendToUser(string userId, string message)
        => Clients.User(userId).receiveMessage(message);   // requires a configured IUserIdProvider
}
----

`Clients.All` broadcasts to every connected client; `Clients.Caller` targets only the invoking connection;
`Clients.Group(name)` targets connections added to a named group (`Groups.Add`/`Groups.Remove`, tracked
server-side, not persisted -- groups must be rejoined in `OnConnected` after a reconnect); `Clients.User(id)`
targets all of one user's connections (across tabs/devices) via `IUserIdProvider`.

== The JavaScript client and the .NET client

[source,javascript]
----
// generated hub proxies (/signalr/hubs, auto-generated from server-side Hub classes)
var chat = $.connection.chatHub;
chat.client.receiveMessage = function (user, message) { appendMessage(user, message); };

$.connection.hub.start().done(function () {
    chat.server.send("Alice", "Hello!");
});
----

[source,csharp]
----
// .NET client (Microsoft.AspNet.SignalR.Client) -- e.g. a WPF app or a service talking to a SignalR 2 server
var connection = new HubConnection("https://example.com/");
var chat = connection.CreateHubProxy("ChatHub");
chat.On<string, string>("receiveMessage", (user, message) => Console.WriteLine($"{user}: {message}"));
await connection.Start();
await chat.Invoke("Send", "Alice", "Hello!");
----

== Transports and fallback

SignalR 2 auto-negotiates the best available transport and falls back automatically: **WebSockets** ->
**Server-Sent Events** -> **Forever Frame** (IE-only, a hidden iframe kept perpetually loading) -> **long
polling** (the universal fallback -- repeated short-lived HTTP requests). This negotiation is what let
SignalR 2 target IIS/`System.Web` environments and older browsers where WebSockets might be unavailable
(Windows Server versions without WebSocket support, corporate proxies that block Upgrade headers), at the cost
of client code that must tolerate any of the four.

== Authorization on hubs

[source,csharp]
----
[Authorize]
public class ChatHub : Hub
{
    [Authorize(Roles = "Support")]
    public void BroadcastAlert(string message) => Clients.All.alert(message);
}
----

`Microsoft.AspNet.SignalR`{apos}s `[Authorize]` is a separate attribute from `System.Web.Mvc.AuthorizeAttribute`
(see xref:web/aspnet/mvc/filters.adoc[Filters]) but relies on the same `IPrincipal`/`ClaimsPrincipal`
established by the OWIN authentication middleware.

== Scale-out backplanes

A single SignalR 2 server holds connections in memory, so scaling to multiple servers (a web farm) requires a
**backplane** to fan messages out across instances -- `+Clients.All.someMethod(...)+` on one server must reach
clients connected to every other server:

[source,csharp]
----
// NuGet: Microsoft.AspNet.SignalR.SqlServer / .Redis / .ServiceBus
GlobalHost.DependencyResolver.UseSqlServer("Data Source=...;Initial Catalog=SignalR;Integrated Security=True");
// or: GlobalHost.DependencyResolver.UseRedis("server", 6379, "password", "signalr-app");
// or: GlobalHost.DependencyResolver.UseServiceBus(connectionString, "signalr-app");
----

SQL Server, Redis, and Azure Service Bus are the three officially supported backplanes; Redis is the most
common choice for throughput-sensitive deployments.

== How SignalR 2 differs from ASP.NET Core SignalR

[cols="1,1,1"]
|===
| | SignalR 2 | ASP.NET Core SignalR

| Hosting | OWIN, inside or alongside `System.Web` | ASP.NET Core middleware (`app.MapHub<T>()`)
| Wire protocol | SignalR 2's own JSON protocol | A newer protocol supporting JSON and MessagePack, with
  a documented spec
| Client generation | `/signalr/hubs` auto-generated JS proxy | No server-generated proxy; clients call
  `+connection.invoke("MethodName", ...)+` directly
| Strongly typed hubs | Not built in | `Hub<T>` gives compile-time-checked client calls
| Streaming | Not supported | `IAsyncEnumerable<T>`/`ChannelReader<T>` streaming methods
| Scale-out | SQL Server / Redis / Azure Service Bus backplanes | Redis backplane, or Azure SignalR Service
|===

== Deep dive: pushing price changes from an MVC action to the browsers watching a product

A hub is created per *call*, not per connection: SignalR instantiates a new `Hub` object for every client-to-server
invocation and disposes it afterwards, so a hub must not hold state in instance fields. Code outside a hub, such as an
MVC controller that has just saved a change, reaches connected clients through the hub *context* instead.

[mermaid]
....

    H->>H: Groups.Add(ConnectionId, product-42)
    Note over C: an administrator saves a new price
    C->>X: GetHubContext of CatalogHub
    C->>X: Clients.Group(product-42).priceChanged(42, 59.90)
    X-->>W: priceChanged(42, 59.90)
    W->>W: update the price on the page
....

=== Worked example

The hub only manages group membership. Product ids are the group names, so a browser receives updates for the products it
is showing and nothing else:

[source,csharp]
----
using System.Threading.Tasks;
using Microsoft.AspNet.SignalR;

public class CatalogHub : Hub
{
    public Task Watch(int productId)   => Groups.Add(Context.ConnectionId, GroupName(productId));
    public Task Unwatch(int productId) => Groups.Remove(Context.ConnectionId, GroupName(productId));

    public static string GroupName(int productId) => "product-" + productId;
}
----

The MVC action pushes after the change is saved. `GlobalHost.ConnectionManager.GetHubContext<T>()` returns an
`IHubContext` whose `Clients` property is the same dynamic proxy a hub uses, minus `Caller` and `Context` (there is no
calling connection):

[source,csharp]
----
using Microsoft.AspNet.SignalR;
using System.Web.Mvc;

public class ProductsController : Controller
{
    private readonly IProductRepository _repository;
    public ProductsController(IProductRepository repository) => _repository = repository;

    [HttpPost, ValidateAntiForgeryToken]
    public ActionResult ChangePrice(int id, decimal price)
    {
        var product = _repository.Find(id);
        if (product == null) return HttpNotFound();

        product.Price = price;
        _repository.Update(product);                                  // save first, then notify

        var hub = GlobalHost.ConnectionManager.GetHubContext<CatalogHub>();
        hub.Clients.Group(CatalogHub.GroupName(id)).priceChanged(id, price);

        return RedirectToAction("Details", new { id });
    }
}
----

On the page, the generated proxy exposes the hub as `$.connection.catalogHub` (the hub name is camel-cased). Handlers
must be registered *before* `start()`, otherwise the proxy does not subscribe to the event:

[source,html]
----
<span id="price-42">@Model.Price.ToString("C")</span>

@section scripts {
    <script src="~/Scripts/jquery.signalR-2.4.3.min.js"></script>
    <script src="~/signalr/hubs"></script>
    <script>
        $(function () {
            var catalog = $.connection.catalogHub;

            catalog.client.priceChanged = function (id, price) {
                $("#price-" + id).text(Number(price).toLocaleString(undefined, { style: "currency", currency: "USD" }));
            };

            $.connection.hub.start().done(function () {
                catalog.server.watch(@Model.Id);
            });

            // Group membership is kept across transient reconnects but not across a full restart of the
            // connection, so join again whenever a fresh connection is established.
            $.connection.hub.disconnected(function () {
                setTimeout(function () {
                    $.connection.hub.start().done(function () { catalog.server.watch(@Model.Id); });
                }, 5000);
            });
        });
    </script>
}
----

The number in the script file name must match the installed `Microsoft.AspNet.SignalR` package (`2.4.3` is the last
2.x release); the `/signalr/hubs` script is generated at runtime from the hub classes and is not a file on disk.

Three points explain most production problems:

* `Clients.All`, `Clients.Group` and the others return `dynamic`, so a typo in `priceChanged` compiles and silently
  does nothing. A strongly typed hub (`Hub<ICatalogClient>`) turns that mistake into a compile error; its context is
  obtained with `GetHubContext<CatalogHub, ICatalogClient>()`.
* The hub context only reaches connections on *this server*. With more than one web node, add a backplane (see the
  scale-out section above), or an update saved on node A never reaches a browser connected to node B.
* Do not call `SaveChanges` and notify inside one database transaction. Notify after commit; a client that receives
  the event and immediately reloads the product must see the new value.
