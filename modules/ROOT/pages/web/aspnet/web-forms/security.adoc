= Security

:keywords: ASP.NET Web Forms, FormsAuthentication, Windows authentication, MembershipProvider, RoleProvider, SqlMembershipProvider, Login control, trust levels, ValidateRequest, machineKey, ASP.NET Identity 2

include::partial$ai-disclaimer.adoc[]

Web Forms security predates ASP.NET Core Identity by roughly a decade and is built around configuration-driven
authentication modules and a swappable **provider model** rather than middleware and dependency injection --
the concepts map onto modern ASP.NET Core Identity (see the concept table in
xref:web/aspnet/choosing-a-framework.adoc[Choosing an ASP.NET Framework]) but the mechanics are distinctly
`System.Web`-era.

== Threat surface and the ASP.NET security context

A Web Forms request carries risk at several layers simultaneously: the transport (HTTPS), the authentication
module deciding *who* the caller is, URL/file authorization deciding *what* they may reach, ViewState/event
validation guarding against tampered postbacks (see
xref:web/aspnet/web-forms/view-state-and-control-state.adoc[ViewState and Control State]), and ordinary
web-application concerns (XSS, SQL injection, CSRF) that apply to any framework. This page covers the
Web-Forms-specific mechanisms; general web hardening is out of this section's scope.

== Forms authentication

`FormsAuthentication` issues a signed (and optionally encrypted) cookie -- the **ticket** -- after a successful
login, and a module checks it on every subsequent request:

[source,xml]
----
<system.web>
  <authentication mode="Forms">
    <forms loginUrl="~/Login.aspx" timeout="30" slidingExpiration="true"
           cookieless="UseCookies" protection="All" name=".ASPXAUTH" />
  </authentication>
</system.web>
----

[source,csharp]
----
protected void LoginButton_Click(object sender, EventArgs e)
{
    if (Membership.ValidateUser(UsernameBox.Text, PasswordBox.Text))
    {
        FormsAuthentication.SetAuthCookie(UsernameBox.Text, createPersistentCookie: RememberMeBox.Checked);
        Response.Redirect(FormsAuthentication.GetRedirectUrl(UsernameBox.Text, false));
    }
    else
    {
        StatusLabel.Text = "Invalid username or password.";
    }
}
----

`slidingExpiration="true"` reissues the ticket once more than half its timeout has elapsed on an active
request, keeping an active user logged in without extending a session indefinitely past inactivity;
`protection="All"` both validates (MAC) and encrypts the ticket using `machineKey`.

**Windows authentication** (`<authentication mode="Windows"/>`, paired with IIS-level Windows
Authentication/Negotiate) instead delegates identity entirely to the OS/domain -- typical for intranet
line-of-business apps where every user already has a domain account, with no login page at all.

== URL authorization and file authorization

`<authorization>` restricts access declaratively by user/role, and combines with `<location>` (see
xref:web/aspnet/web-forms/http-pipeline-handlers-and-configuration.adoc[HTTP Pipeline, Handlers, and
Configuration]) to scope rules to specific folders:

[source,xml]
----
<location path="Admin">
  <system.web>
    <authorization>
      <allow roles="Administrators" />
      <deny users="*" />
    </authorization>
  </system.web>
</location>
----

Rules are evaluated top-to-bottom, first match wins -- `<allow roles="Administrators"/>` before
`+<deny users="*"/>+` is required, not incidental. **File authorization**
(`FileAuthorizationModule`) additionally checks NTFS ACLs against the authenticated Windows identity, relevant
only under Windows authentication.

== The provider model

Membership, roles, and profile are each fronted by an abstract provider base class, swappable via
configuration without changing calling code:

[cols="1,2"]
|===
| Provider base | Built-in implementations

| `MembershipProvider` | `SqlMembershipProvider` (ASPNETDB schema), `ActiveDirectoryMembershipProvider`
| `RoleProvider` | `SqlRoleProvider`, `AuthorizationStoreRoleProvider` (Authorization Manager/`.xml`/AD store)
| `ProfileProvider` | `SqlProfileProvider`
|===

[source,xml]
----
<system.web>
  <membership defaultProvider="SqlMembership">
    <providers>
      <add name="SqlMembership" type="System.Web.Security.SqlMembershipProvider"
           connectionStringName="ASPNETDB" applicationName="/MyApp"
           minRequiredPasswordLength="8" requiresUniqueEmail="true" />
    </providers>
  </membership>
  <roleManager enabled="true" defaultProvider="SqlRole">
    <providers>
      <add name="SqlRole" type="System.Web.Security.SqlRoleProvider"
           connectionStringName="ASPNETDB" applicationName="/MyApp" />
    </providers>
  </roleManager>
</system.web>
----

[source,csharp]
----
if (Roles.IsUserInRole(User.Identity.Name, "Administrators")) { /* ... */ }
MembershipUser user = Membership.GetUser();
----

== Login controls and their events

A family of declarative controls wraps `Membership`/`FormsAuthentication` end to end, needing little or no
code-behind for the common cases:

[cols="1,2"]
|===
| Control | Purpose

| `Login` | Username/password form; `Authenticate` event for custom validation logic.
| `LoginView` | Shows different markup templates for anonymous vs. authenticated (optionally per-role) users.
| `LoginStatus` | A "Log in"/"Log out" link that swaps automatically based on auth state.
| `CreateUserWizard` | Self-service registration against the configured `MembershipProvider`.
| `PasswordRecovery` | Email-based password reset flow (requires `MembershipProvider.EnablePasswordRetrieval`
  or reset support and a configured SMTP `<mailSettings>`).
| `ChangePassword` | Authenticated password-change form.
|===

[source,aspx]
----
<asp:Login ID="LoginControl" runat="server" OnAuthenticate="LoginControl_Authenticate" />
<asp:LoginView runat="server">
    <AnonymousTemplate>Please <asp:LoginStatus runat="server" /></AnonymousTemplate>
    <LoggedInTemplate>Welcome, <asp:LoginName runat="server" />!</LoggedInTemplate>
</asp:LoginView>
----

== ASP.NET Universal Providers

The "Universal Providers" NuGet package (`Microsoft.AspNet.Providers`) reimplements
Membership/Role/Profile/SessionState providers against a plain SQL Server (including SQL Server Compact/LocalDB)
schema managed by Entity Framework migrations, avoiding the older `aspnet_regsql`-provisioned ASPNETDB schema --
useful when the hosting environment cannot run `aspnet_regsql` directly (e.g. many shared/Azure hosts of that
era).

== Trust levels

`+<trust level="...">+` constrained what a Web Forms application was permitted to do at the CLR level under
Code Access Security (CAS) -- `Full`, `High`, `Medium`, `Low`, `Minimal` -- historically used by shared hosts
to sandbox tenant applications from each other and from the filesystem/registry. **CAS-based trust levels are
obsolete**: .NET Framework 4 deprecated partial-trust ASP.NET hosting, and `<trust level="Full">` (the only
level guaranteed to work correctly with most modern libraries) is effectively mandatory. This is documented
here because older code and hosting guides still reference `<trust level="Medium">`; do not attempt to use
partial trust in a current application.

== Request validation and `ValidateRequest`

ASP.NET's built-in request validation rejects a request outright if any input contains markup that looks like
HTML/script, as a baseline XSS defense -- on by default since ASP.NET 1.1:

[source,xml]
----
<system.web>
  <httpRuntime requestValidationMode="4.5" /> <!-- lazy validation: only checked when the value is actually read -->
</system.web>
----

[source,aspx]
----
<%@ Page ValidateRequest="false" %> <%-- disable only for the specific page that legitimately needs raw HTML input --%>
----

Disabling `ValidateRequest` removes a real protection and shifts full responsibility for encoding/sanitizing
that input onto application code -- it should never be disabled site-wide, only on the specific page (e.g. a
rich-text editor submission) that needs it, paired with explicit output encoding and, ideally, a
allow-list-based HTML sanitizer on the way in.

== Antiforgery and CSRF

Web Forms has no first-class `AntiForgeryToken` helper the way MVC does; `ViewStateUserKey` (see
xref:web/aspnet/web-forms/view-state-and-control-state.adoc[ViewState and Control State]) is the standard
Web-Forms-era CSRF mitigation, binding a page's ViewState to the authenticated user so a replayed form from a
different user's session fails MAC-consistent processing. For non-ViewState-carrying endpoints (an `.ashx`
handler accepting a POST), a hand-rolled anti-CSRF token in a hidden field, validated server-side, is the
equivalent construct.

== `machineKey` and why it matters in a farm

`machineKey` (introduced in xref:web/aspnet/web-forms/view-state-and-control-state.adoc[ViewState and Control
State] for ViewState signing) also signs and encrypts the Forms authentication ticket and any other protected
data (`MachineKeySection`-based APIs). In a load-balanced farm, every server **must** share an explicitly
configured `machineKey` -- auto-generated (the default) keys are per-machine, so a user authenticated by one
server would fail validation on another, and ViewState generated by one server would be rejected by another:

[source,xml]
----
<machineKey validationKey="[64-hex-char shared key]" decryptionKey="[48-hex-char shared key]"
            validation="HMACSHA256" decryption="AES" />
----

== Claims-based identity and ASP.NET Identity 2.x on Web Forms

ASP.NET Identity 2.x (the same `Microsoft.AspNet.Identity.Core`/`.Owin` packages MVC 5 uses) can be hosted on
Web Forms via OWIN (`Microsoft.Owin.Host.SystemWeb`), replacing `FormsAuthentication`/`Membership` with a
`ClaimsPrincipal`-based model and EF-backed `UserManager`/`SignInManager`:

[source,csharp]
----
// Startup.cs (OWIN)
public class Startup
{
    public void Configuration(IAppBuilder app)
    {
        app.CreatePerOwinContext(ApplicationDbContext.Create);
        app.CreatePerOwinContext<ApplicationUserManager>(ApplicationUserManager.Create);
        app.UseCookieAuthentication(new CookieAuthenticationOptions
        {
            AuthenticationType = DefaultAuthenticationTypes.ApplicationCookie,
            LoginPath = new PathString("/Login")
        });
    }
}
----

[source,csharp]
----
var userManager = HttpContext.Current.GetOwinContext().GetUserManager<ApplicationUserManager>();
var user = await userManager.FindByNameAsync(UsernameBox.Text);
bool ok = await userManager.CheckPasswordAsync(user, PasswordBox.Text);
----

This is the same migration path xref:web/aspnet/mvc/index.adoc[ASP.NET MVC] applications typically take before
a full move to ASP.NET Core Identity, and is a reasonable intermediate step for a Web Forms application that
needs claims-based identity (e.g. to integrate with an external OAuth/OIDC provider) without a full rewrite.
See https://learn.microsoft.com/en-us/previous-versions/aspnet/hh377851(v=vs.108)[ASP.NET Security
Fundamentals] and https://learn.microsoft.com/en-us/aspnet/identity/overview/getting-started/introduction-to-aspnet-identity[Introduction
to ASP.NET Identity].

== One request through authentication and authorization

Authentication (who is calling) and authorization (what may they reach) are separate pipeline stages, performed by
separate modules, and both finish before the page's own code runs. Following one anonymous request to a protected
page, and the next request after login, shows where each decision happens:

[mermaid]
....
sequenceDiagram
    participant B as Browser
    participant F as FormsAuthenticationModule
    participant U as UrlAuthorizationModule
    participant L as Login.aspx
    participant P as Orders/Admin.aspx
    B->>F: GET /Orders/Admin.aspx (no cookie)
    F->>F: AuthenticateRequest: no ticket, User is anonymous
    F->>U: AuthorizeRequest
    U->>U: authorization rules: deny users="?"
    U-->>B: 302 to /Login.aspx?ReturnUrl=/Orders/Admin.aspx
    B->>L: GET /Login.aspx?ReturnUrl=...
    L->>L: validate credentials, issue the ticket cookie
    L-->>B: 302 back to ReturnUrl with Set-Cookie
    B->>F: GET /Orders/Admin.aspx with ticket cookie
    F->>F: decrypt and validate, build FormsIdentity, set User
    F->>U: AuthorizeRequest: user allowed
    U->>P: page runs, User.Identity.Name is set
....

The two modules work independently: `FormsAuthenticationModule` never denies access (it only establishes identity), and
`UrlAuthorizationModule` never establishes identity (it only checks it). A page with no `<authorization>` rule for it
is reachable by anyone, authenticated or not, which is why the secure default is a root-level `<deny users="?" />`
with `<location>` exceptions for the public pages, rather than the reverse.

== Worked example: a login that carries roles in the ticket

`Membership.ValidateUser` plus `FormsAuthentication.SetAuthCookie` is enough for many sites. When roles should be
available on every request without a database round trip, they can ride inside the encrypted ticket. The login page
validates the user, builds the ticket with the roles in `UserData`, and redirects only to a *local* return URL:

[source,csharp]
----
// Login.aspx.cs
using System;
using System.Web;
using System.Web.Security;
using System.Web.UI;

namespace WebFormsApp
{
    public partial class Login : Page
    {
        protected void LoginButton_Click(object sender, EventArgs e)
        {
            if (!Page.IsValid)
            {
                return;
            }

            if (!Membership.ValidateUser(UsernameBox.Text, PasswordBox.Text))
            {
                StatusLabel.Text = "Invalid username or password."; // the same message for unknown user and bad password
                return;
            }

            string[] roles = Roles.GetRolesForUser(UsernameBox.Text);
            var ticket = new FormsAuthenticationTicket(
                1,                                   // version
                UsernameBox.Text,
                DateTime.Now,
                DateTime.Now.AddMinutes(30),
                RememberMeBox.Checked,
                string.Join(",", roles),             // UserData
                FormsAuthentication.FormsCookiePath);

            var cookie = new HttpCookie(FormsAuthentication.FormsCookieName, FormsAuthentication.Encrypt(ticket))
            {
                HttpOnly = true,
                Secure = FormsAuthentication.RequireSSL,
                Expires = ticket.IsPersistent ? ticket.Expiration : DateTime.MinValue // MinValue = session cookie
            };
            Response.Cookies.Add(cookie);

            Response.Redirect(SafeReturnUrl(Request.QueryString["ReturnUrl"]), false);
            Context.ApplicationInstance.CompleteRequest();
        }

        // Only site-relative paths are accepted; "//host", "/\host" and absolute URLs are rejected.
        private static string SafeReturnUrl(string returnUrl)
        {
            bool local = !string.IsNullOrEmpty(returnUrl)
                && returnUrl.StartsWith("/")
                && !returnUrl.StartsWith("//")
                && !returnUrl.StartsWith("/\\");
            return local ? returnUrl : "~/Default.aspx";
        }
    }
}
----

[source,csharp]
----
// Global.asax.cs -- turn the roles stored in the ticket into a principal that IsInRole understands
using System;
using System.Security.Principal;
using System.Web.Security;

protected void Application_PostAuthenticateRequest(object sender, EventArgs e)
{
    var identity = Context.User != null ? Context.User.Identity as FormsIdentity : null;
    if (identity == null)
    {
        return; // anonymous request, or a different authentication mode
    }

    string[] roles = identity.Ticket.UserData
        .Split(new[] { ',' }, StringSplitOptions.RemoveEmptyEntries);
    Context.User = new GenericPrincipal(identity, roles);
}
----

With this in place, `<allow roles="Administrators" />` in `<authorization>`, `User.IsInRole("Administrators")` in
code, and `LoginView` role templates all see the roles, and none of them touches the database. The trade-off is
staleness: a role removed from a user stays effective until the ticket expires (30 minutes here), so use short
timeouts for sensitive roles, or skip this technique and let `RoleManager` look the roles up on each request. The
`FormsAuthentication.GetRedirectUrl` helper used earlier rejects absolute URLs outside the application when
`enableCrossAppRedirects` is `false` (its default), but a redirect built by hand from a raw query-string value has
no such check, which is the reason for `SafeReturnUrl`. Redirecting with `Response.Redirect(url, false)` followed by
`CompleteRequest` avoids the `ThreadAbortException` described in the
xref:web/aspnet/web-forms/page-lifecycle-and-postback.adoc[page life cycle] page.

== Hashing passwords for a custom user store

If the application does not use `Membership` (for example a hand-written `Users` table), passwords must still be
stored as salted, deliberately slow hashes, never in reversible form. PBKDF2 is available in the framework itself:

[source,csharp]
----
using System;
using System.Security.Cryptography;

namespace WebFormsApp.Services
{
    public static class PasswordHasher
    {
        private const int Iterations = 100000;
        private const int SaltSize = 16;
        private const int HashSize = 32;

        public static string Hash(string password)
        {
            var salt = new byte[SaltSize];
            using (var rng = RandomNumberGenerator.Create())
            {
                rng.GetBytes(salt);
            }

            byte[] hash = Derive(password, salt, Iterations);
            return Iterations + "." + Convert.ToBase64String(salt) + "." + Convert.ToBase64String(hash);
        }

        public static bool Verify(string password, string stored)
        {
            string[] parts = stored.Split('.');
            if (parts.Length != 3)
            {
                return false;
            }

            byte[] expected = Convert.FromBase64String(parts[2]);
            byte[] actual = Derive(password, Convert.FromBase64String(parts[1]), int.Parse(parts[0]));

            // Compare every byte regardless of where they first differ, so timing does not leak the match length.
            int difference = expected.Length ^ actual.Length;
            for (int i = 0; i < expected.Length && i < actual.Length; i++)
            {
                difference |= expected[i] ^ actual[i];
            }

            return difference == 0;
        }

        private static byte[] Derive(string password, byte[] salt, int iterations)
        {
            using (var kdf = new Rfc2898DeriveBytes(password, salt, iterations, HashAlgorithmName.SHA256))
            {
                return kdf.GetBytes(HashSize);
            }
        }
    }
}
----

The iteration count is stored with each hash, so it can be raised later without invalidating existing passwords:
`Verify` honors the stored value, and a successful login can re-hash with the current default. (The
`HashAlgorithmName` overload of `Rfc2898DeriveBytes` requires .NET Framework 4.7.2 or later, which any 4.8.1 project
satisfies.)

== Output encoding: which controls encode and which do not

Cross-site scripting in Web Forms is almost always a stored value written to the page without encoding, and the
controls differ in what they do by default:

[cols="2,1,3"]
|===
| Output path | Encodes? | Note

| `<%: expr %>`, `<%#: expr %>` | Yes | The safe default for markup.
| `<%= expr %>`, `<%# expr %>` | No | Fine for trusted, already-encoded values only.
| `Label.Text`, `Literal.Text` (default `Mode`) | No | The text is written as HTML; use `Literal.Mode="Encode"` or
  encode before assigning.
| `TextBox.Text` | Yes (attribute-encoded) | Safe as a value, but not in a `Label` that echoes it.
| `BoundField` | Yes (`HtmlEncode="true"`) | Disabling it for a column makes that column an injection point.
| `TemplateField` with `+<%# Eval(...) %>+` | No | Use `+<%#: Eval(...) %>+`.
| `HyperLink.NavigateUrl` | No | A `javascript:` URL from user data runs; validate the scheme.
|===

[source,aspx]
----
<%-- vulnerable: a name like <script>...</script> is written as markup --%>
<asp:Label ID="WelcomeLabel" runat="server" />
<%-- safe --%>
<asp:Literal ID="WelcomeLiteral" runat="server" Mode="Encode" />
<script>
    // values placed inside JavaScript need JavaScript encoding, not HTML encoding
    var customer = "<%= HttpUtility.JavaScriptStringEncode(CustomerName) %>";
</script>
----

The same discipline applies to SQL: concatenating input into the command text is the injection, and parameters are the
fix, whatever the data-access layer:

[source,csharp]
----
using (var connection = new SqlConnection(ConfigurationManager.ConnectionStrings["CatalogDb"].ConnectionString))
using (var command = new SqlCommand("SELECT Id, Name, Price FROM Products WHERE Name LIKE @pattern", connection))
{
    // never: "... WHERE Name LIKE '%" + SearchBox.Text + "%'"
    command.Parameters.AddWithValue("@pattern", "%" + SearchBox.Text + "%");
    connection.Open();
    // ... read the results
}
----

`SqlDataSource` parameters and `ObjectDataSource` method parameters are parameterized automatically; the risk
returns the moment a `SelectCommand` is built from a string in code-behind.

== Worked example: anti-forgery for a Web Forms site

The standard Web Forms template protects postbacks with a per-browser token that is both a cookie and the page's
`ViewStateUserKey`, plus a copy inside ViewState. A request forged from another site cannot read the cookie, so its
ViewState fails validation. The code lives in the master page, which makes every page on the site protected:

[source,csharp]
----
// Site.master.cs
private const string AntiXsrfTokenKey = "__AntiXsrfToken";
private const string AntiXsrfUserNameKey = "__AntiXsrfUserName";
private string _antiXsrfTokenValue;

protected void Page_Init(object sender, EventArgs e)
{
    HttpCookie requestCookie = Request.Cookies[AntiXsrfTokenKey];
    Guid requestCookieGuidValue;
    if (requestCookie != null && Guid.TryParse(requestCookie.Value, out requestCookieGuidValue))
    {
        _antiXsrfTokenValue = requestCookie.Value;
        Page.ViewStateUserKey = _antiXsrfTokenValue;
    }
    else
    {
        _antiXsrfTokenValue = Guid.NewGuid().ToString("N");
        Page.ViewStateUserKey = _antiXsrfTokenValue;

        var responseCookie = new HttpCookie(AntiXsrfTokenKey) { HttpOnly = true, Value = _antiXsrfTokenValue };
        if (FormsAuthentication.RequireSSL && Request.IsSecureConnection)
        {
            responseCookie.Secure = true;
        }

        Response.Cookies.Set(responseCookie);
    }

    Page.PreLoad += master_Page_PreLoad;
}

protected void master_Page_PreLoad(object sender, EventArgs e)
{
    if (!IsPostBack)
    {
        ViewState[AntiXsrfTokenKey] = Page.ViewStateUserKey;
        ViewState[AntiXsrfUserNameKey] = Context.User.Identity.Name ?? string.Empty;
    }
    else if ((string)ViewState[AntiXsrfTokenKey] != _antiXsrfTokenValue
        || (string)ViewState[AntiXsrfUserNameKey] != (Context.User.Identity.Name ?? string.Empty))
    {
        throw new InvalidOperationException("Validation of Anti-XSRF token failed.");
    }
}
----

It protects only requests that carry ViewState. A hand-posted form or an `.ashx` that accepts POST needs its own
token check, and the cookie itself should opt in to `SameSite` (`<httpCookies sameSite="Lax" />`, available from
.NET Framework 4.7.2). The check also depends on the master page's ViewState being saved: a page that follows the
`ViewStateMode="Disabled"` advice from the ViewState page disables the master's copy of the token too, and every
postback then fails validation, so set `ViewStateMode = ViewStateMode.Enabled` on the master page itself. The
Visual Studio Web Forms project templates ship exactly this code in `Site.Master`, so existing sites often have it
already -- check before adding a second copy.

See the https://learn.microsoft.com/en-us/aspnet/web-forms/[ASP.NET Web Forms documentation] and the https://learn.microsoft.com/en-us/previous-versions/aspnet/[ASP.NET 4 documentation archive]
for the security guidance on threats, countermeasures, and cross-site scripting prevention.
