= Server Controls
:description: runat="server" and the control tree, HTML server controls, the Web server control families, common properties and styling, ClientScriptManager script registration, and client callbacks vs. postback.
:keywords: ASP.NET Web Forms, runat=server, HtmlControl, HtmlContainerControl, HtmlGenericControl, Label, TextBox, GridView, ClientScriptManager, RegisterClientScriptBlock, ICallbackEventHandler

include::partial$ai-disclaimer.adoc[]

Every visible or logical element on a Web Forms page that the server needs to inspect, modify, or re-render is
a **server control** -- an object in a tree rooted at the `Page`, each node implementing
`System.Web.UI.Control` and participating fully in the
xref:web/aspnet/web-forms/page-lifecycle-and-postback.adoc[page life cycle].

== `runat="server"` and the control tree

Adding `runat="server"` to an HTML element (or using an `+<asp:...>+` tag, which is always server-side) tells
the ASP.NET page parser to create a corresponding server-side object instead of emitting the tag verbatim:

[source,aspx]
----
<div id="MessagePanel" runat="server" class="alert">
    <span id="MessageText" runat="server">Default text</span>
</div>
----

[source,csharp]
----
MessagePanel.Visible = true;
MessageText.InnerText = "Saved.";
----

Every server control the parser creates becomes a child of its containing control (the page, a master page
content area, a user control, another control acting as a naming container), forming the control tree that
`Init`/`Load`/`PreRender`/`Render` walk.

image::aspnet-web-forms-control-tree.svg["The Web Forms control tree: Page at the root, a master page, an HtmlForm and a user control as children, with GridView and TextBox/Button as leaf controls",width=700,role=text-center]

See
https://learn.microsoft.com/en-us/previous-versions/aspnet/ms178472(v=vs.100)[ASP.NET Page Life Cycle
Overview] for how the tree relates to the life cycle, and
https://learn.microsoft.com/en-us/aspnet/web-forms/[the ASP.NET Web Forms documentation index] for the control
reference.

== HTML server controls

HTML server controls map almost 1:1 to an HTML tag and expose it as an object without changing its rendered
markup shape -- useful when close control over the exact HTML is needed while still wanting server-side
access:

[cols="1,2"]
|===
| Base class | Purpose

| `HtmlControl` | Abstract base for all HTML server controls; exposes `Style`, `Attributes` (a generic bag for
  any HTML attribute not otherwise wrapped).
| `HtmlContainerControl` | HTML elements with a closing tag and inner content (`HtmlGenericControl`,
  `HtmlAnchor`, `HtmlTable`); exposes `InnerText`/`InnerHtml`.
| `HtmlGenericControl` | Any element with no dedicated wrapper class (`<div>`, `<span>`, `<ul>`, ...) --
  `runat="server"` on such a tag produces this type.
|===

[source,csharp]
----
HtmlGenericControl div = (HtmlGenericControl)MessagePanel; // typed as HtmlGenericControl
div.Attributes["data-status"] = "saved";
----

== Web server controls

The `System.Web.UI.WebControls` namespace is the much larger, richer family used for the majority of Web
Forms UI, rendered from `WebControl` and offering a consistent property set (`CssClass`, `Font`, `BackColor`,
`Enabled`, `Visible`, `TabIndex`) regardless of the underlying HTML.

[cols="1,2"]
|===
| Category | Controls

| Basic input/output | `Label`, `TextBox`, `Button`, `LinkButton`, `ImageButton`, `HiddenField`, `Literal`
| Selection | `DropDownList`, `ListBox`, `CheckBox`, `CheckBoxList`, `RadioButton`, `RadioButtonList`
| Layout/grouping | `Panel`, `PlaceHolder`, `Table`
|===

[source,aspx]
----
<asp:Label ID="TotalLabel" runat="server" Text="Total:" CssClass="form-label" />
<asp:TextBox ID="QuantityBox" runat="server" TextMode="Number" CssClass="form-control" />
<asp:DropDownList ID="CountryList" runat="server" AppendDataBoundItems="true">
    <asp:ListItem Text="-- choose --" Value="" />
</asp:DropDownList>
<asp:Button ID="AddButton" runat="server" Text="Add" OnClick="AddButton_Click" CssClass="btn btn-primary" />
----

== Rich controls

Beyond basic input, Web Forms ships several purpose-built rich controls:

[cols="1,2"]
|===
| Control | Purpose

| `Calendar` | A full month-view date picker, `SelectedDate`/`SelectionChanged`.
| `AdRotator` | Rotates banner ads driven by an XML advertisement file or a data source.
| `MultiView` / `View` | Multiple mutually exclusive content panels, switched via `ActiveViewIndex` -- a
  lightweight tab/wizard-step primitive.
| `Wizard` | A built-in multi-step form flow with navigation, `WizardStep` pages, and `FinishButtonClick`.
| `FileUpload` | A file `<input>` wrapper exposing `PostedFile`/`SaveAs`; requires `enctype="multipart/form-data"`
  on the `<form>` (applied automatically once a `FileUpload` is present).
| `Table` | Programmatically buildable `<table>` via `TableRow`/`TableCell` objects.
|===

== Common properties and styling

`CssClass` (not `class`, which ASP.NET does not special-case on Web controls), `Style` (an `IDictionary` of
inline CSS, `Style["display"] = "none"`), `Enabled`, `Visible` (suppresses rendering entirely -- an invisible
control emits no markup at all, unlike CSS `display:none`), and the `Font`/`ForeColor`/`BackColor`
presentation properties that render as inline styles unless a theme/skin (see
xref:web/aspnet/web-forms/master-pages-themes-and-localization.adoc[Master Pages, Themes, and Localization])
overrides them.

== Registering client script from the server

`Page.ClientScript` (`ClientScriptManager`) is the standard way for server-side code to inject JavaScript into
the rendered page without hand-writing `<script>` blocks in markup:

[source,csharp]
----
protected void SaveButton_Click(object sender, EventArgs e)
{
    // A one-time <script> block emitted once, wherever RegisterClientScriptBlock outputs it (top of form).
    ClientScript.RegisterClientScriptBlock(GetType(), "confirmSave",
        "function confirmSave(){ return confirm('Save changes?'); }", true);

    // A statement that runs once the page has finished loading in the browser (near the closing </form>).
    ClientScript.RegisterStartupScript(GetType(), "focusFirstField",
        "document.getElementById('" + FirstNameBox.ClientID + "').focus();", true);

    // A reference to an external .js file, de-duplicated by key even if called from multiple controls.
    ClientScript.RegisterClientScriptInclude("validation-lib", ResolveUrl("~/Scripts/validation.js"));
}
----

`RegisterClientScriptBlock` and `RegisterStartupScript` differ only in *where* in the rendered HTML the block
is placed (top vs. bottom of the form); both de-duplicate by their `key` argument, so calling the same
registration twice in one request (e.g. from a control used more than once) emits the script only once.

== Client callbacks vs. postback

`ICallbackEventHandler` lets a control make an asynchronous round trip to the server that runs the page life
cycle but skips full-page rendering -- a lighter-weight precursor to `UpdatePanel`
(xref:web/aspnet/web-forms/ajax-and-client-side.adoc[AJAX and Client-Side Integration]):

[source,csharp]
----
public partial class Lookup : System.Web.UI.Page, ICallbackEventHandler
{
    private string _result;

    protected void Page_Load(object sender, EventArgs e)
    {
        string reference = ClientScript.GetCallbackEventReference(
            this, "arg", "onLookupComplete", null);
        ClientScript.RegisterClientScriptBlock(GetType(), "callback",
            "function doLookup(arg){ " + reference + "; }", true);
    }

    public string GetCallbackResult() => _result;

    public void RaiseCallbackEvent(string eventArgument)
    {
        _result = LookupService.Find(eventArgument); // runs server-side, full life cycle, no full render
    }
}
----

A callback still executes `PreInit` through `PreRender` (so `Page_Load` runs on every callback exactly as on a
postback) but produces only the string returned by `GetCallbackResult`, not a rendered page -- useful for
type-ahead search boxes and similar small server round trips that predate any AJAX framework.

== Control identity: `ID`, `UniqueID`, `ClientID`, and naming containers

Every control has three names, and mixing them up is behind most `FindControl` returning `null` problems:

* `ID` -- the name chosen in markup, unique only within its *naming container*.
* `UniqueID` -- the path of `ID` values from the page down to the control, joined with `$`; this is the `name`
  attribute that appears in the posted form, and it is how postback data is routed back to the right control.
* `ClientID` -- the same path joined with `_` (under the default `ClientIDMode`); this is the `id` attribute
  JavaScript sees.

A *naming container* (a control implementing `INamingContainer`: the page, a master page, a user control, each
row of a `Repeater` or `GridView`) starts a new scope, which is why two rows can both contain a control with the ID
`AddButton`:

[mermaid]
....
flowchart TD
    P["Page"] --> M["Master page (naming container)\nUniqueID prefix: ctl00"]
    M --> C["ContentPlaceHolder MainContent\n(naming container)"]
    C --> R["Repeater ProductsRepeater\n(naming container)"]
    R --> I1["RepeaterItem 0 (naming container)\nctl01"]
    R --> I2["RepeaterItem 1 (naming container)\nctl02"]
    I1 --> B1["Button AddButton\nUniqueID ctl00$MainContent$ProductsRepeater$ctl01$AddButton\nClientID ctl00_MainContent_ProductsRepeater_ctl01_AddButton"]
    I2 --> B2["Button AddButton\nUniqueID ctl00$MainContent$ProductsRepeater$ctl02$AddButton"]
....

`FindControl(id)` searches only the *current* naming container and does not look inside nested ones, which is why
`Page.FindControl("AddButton")` fails for a button inside a repeater item and the call has to start from the item
(`e.Item.FindControl("AddButton")`). When a control really must be located from the outside, a recursive helper
walks the whole tree:

[source,csharp]
----
public static T FindControlRecursive<T>(Control root, string id) where T : Control
{
    if (root.ID == id)
    {
        var match = root as T;
        if (match != null)
        {
            return match;
        }
    }

    foreach (Control child in root.Controls)
    {
        T found = FindControlRecursive<T>(child, id);
        if (found != null)
        {
            return found;
        }
    }

    return null;
}
----

A recursive search is a diagnostic or last-resort tool: prefer exposing the control through a public property of
the user control that owns it, so the page depends on a property rather than on an ID string.

== Event bubbling: handling clicks from inside a templated control

A `Button` inside a `Repeater` item cannot be given its own `OnClick` handler per row. Instead, the button
carries a `CommandName` and `CommandArgument`, raises a *bubbled* event, and the repeater re-raises it as a single
`ItemCommand` that the page handles. This is how every list control (`Repeater`, `DataList`, `GridView`,
`ListView`) reports its row-level buttons:

[source,aspx]
----
<%-- Orders/Catalog.aspx (excerpt) --%>
<asp:Repeater ID="ProductsRepeater" runat="server" OnItemCommand="ProductsRepeater_ItemCommand">
    <ItemTemplate>
        <div>
            <%# Eval("Name") %> -- <%# Eval("Price", "{0:C}") %>
            <asp:Button ID="AddButton" runat="server" Text="Add" CommandName="Add"
                CommandArgument='<%# Eval("Id") %>' />
        </div>
    </ItemTemplate>
</asp:Repeater>
<asp:Label ID="CartLabel" runat="server" />
----

[source,csharp]
----
// Orders/Catalog.aspx.cs
using System;
using System.Web.UI.WebControls;
using WebFormsApp.Services;

namespace WebFormsApp.Orders
{
    public partial class Catalog : System.Web.UI.Page
    {
        protected void Page_Load(object sender, EventArgs e)
        {
            if (!IsPostBack)
            {
                ProductsRepeater.DataSource = ProductCatalog.All();
                ProductsRepeater.DataBind();
            }
        }

        protected void ProductsRepeater_ItemCommand(object source, RepeaterCommandEventArgs e)
        {
            if (e.CommandName != "Add")
            {
                return;
            }

            Product product = ProductCatalog.Find(int.Parse((string)e.CommandArgument));
            CartLabel.Text = "Added " + product.Name + " (item index " + e.Item.ItemIndex + ").";
        }
    }
}
----

[mermaid]
....
sequenceDiagram
    participant U as Browser
    participant B as AddButton (in row 1)
    participant I as RepeaterItem
    participant R as ProductsRepeater
    participant P as Page
    U->>B: POST, __EVENTTARGET = ...ctl02$AddButton
    B->>B: OnClick, then OnCommand (CommandName = Add)
    B->>I: RaiseBubbleEvent(CommandEventArgs)
    I->>R: OnBubbleEvent wraps it as RepeaterCommandEventArgs
    R->>P: ItemCommand event
    P->>P: ProductsRepeater_ItemCommand runs
....

The item rows are rebuilt from ViewState on the postback, which is what lets the page bind only when
`!IsPostBack` and still receive the event: the bubbled event needs the row's control tree to exist when the
click is processed. A custom control can take part in the same mechanism by overriding `OnBubbleEvent`
(return `true` to stop the event) and calling `RaiseBubbleEvent` to push its own.

== Page usability helpers

Several small page and form properties remove the need for hand-written script on every form:

[source,aspx]
----
<%@ Page Language="C#" MaintainScrollPositionOnPostBack="true"
    MetaDescription="Order entry" MetaKeywords="orders, catalog"
    CodeBehind="NewOrder.aspx.cs" Inherits="WebFormsApp.Orders.NewOrder" %>
...
<form id="form1" runat="server" defaultfocus="QuantityBox" defaultbutton="AddButton">
    <asp:Panel ID="SearchPanel" runat="server" DefaultButton="SearchButton">
        <asp:TextBox ID="SearchBox" runat="server" />
        <asp:Button ID="SearchButton" runat="server" Text="Search" />
    </asp:Panel>
    ...
</form>
----

* `MaintainScrollPositionOnPostBack` restores the scroll offset after a postback, so a postback from the bottom
  of a long grid does not jump back to the top.
* `DefaultFocus` on the `<form>` (or `Page.SetFocus(control)` from code) puts the cursor in the right field on
  load; `DefaultButton` on the form or on a `Panel` decides which button the Enter key presses, so a search box
  and the main form can have different Enter behavior.
* `MetaDescription`, `MetaKeywords` and `Page.Title` fill the matching `<head>` elements from the `@Page`
  directive or from code, which matters for pages that otherwise have no markup control over `<head>` (pages that
  use a master page).

== Worked example: the order-entry `Wizard`

`Wizard` turns a multi-step form into a single control with a built-in navigation bar. Each `WizardStep` holds
ordinary child controls; `StepType` decides which navigation buttons appear (`Start`, `Step`, `Finish`) and
`Complete` marks the final confirmation, which has no navigation at all:

[source,aspx]
----
<asp:Wizard ID="OrderWizard" runat="server" ActiveStepIndex="0"
    OnNextButtonClick="OrderWizard_NextButtonClick"
    OnFinishButtonClick="OrderWizard_FinishButtonClick">
    <WizardSteps>
        <asp:WizardStep ID="ProductStep" runat="server" Title="Product" StepType="Start">
            <asp:DropDownList ID="ProductList" runat="server" />
        </asp:WizardStep>
        <asp:WizardStep ID="QuantityStep" runat="server" Title="Quantity" StepType="Step">
            <asp:TextBox ID="QuantityBox" runat="server" Text="1" />
        </asp:WizardStep>
        <asp:WizardStep ID="ConfirmStep" runat="server" Title="Confirm" StepType="Finish">
            <asp:Label ID="SummaryLabel" runat="server" />
        </asp:WizardStep>
        <asp:WizardStep ID="DoneStep" runat="server" Title="Done" StepType="Complete">
            <asp:Label ID="DoneLabel" runat="server" />
        </asp:WizardStep>
    </WizardSteps>
</asp:Wizard>
----

[source,csharp]
----
protected void OrderWizard_NextButtonClick(object sender, WizardNavigationEventArgs e)
{
    int quantity;
    if (e.CurrentStepIndex == 1 && !int.TryParse(QuantityBox.Text, out quantity))
    {
        e.Cancel = true; // stay on the quantity step
        QuantityBox.BackColor = System.Drawing.Color.MistyRose;
        return;
    }

    if (e.NextStepIndex == 2)
    {
        Product product = ProductCatalog.Find(int.Parse(ProductList.SelectedValue));
        SummaryLabel.Text = QuantityBox.Text + " x " + product.Name;
    }
}

protected void OrderWizard_FinishButtonClick(object sender, WizardNavigationEventArgs e)
{
    DoneLabel.Text = "Order placed: " + SummaryLabel.Text;
}
----

The wizard keeps its current step in *control state* (see the ViewState page), so navigation still works with
`EnableViewState="false"`. The values typed in earlier steps are held in the controls of the steps that are not
displayed, which are kept in ViewState; a wizard with large steps therefore carries them on every request, and a
long flow with big grids is better built from separate pages with the order carried in `Session`.

See the https://learn.microsoft.com/en-us/aspnet/web-forms/[ASP.NET Web Forms documentation] and the https://learn.microsoft.com/en-us/previous-versions/aspnet/[ASP.NET 4 documentation archive]
for the web server controls event model and the `Wizard` control overview.
