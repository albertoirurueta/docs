= State Management and Caching
:description: Client-side state (ViewState, control state, hidden fields, cookies, query string) vs. server-side (Application, Session, Cache, Profile); session modes; the Cache API, dependencies, and callbacks; SQL cache dependency; and output/fragment caching.
:keywords: ASP.NET Web Forms, Session, Application, Cache, Profile, InProc, StateServer, SQLServer session state, SqlCacheDependency, OutputCache, VaryByParam, Substitution control

include::partial$ai-disclaimer.adoc[]

Web Forms offers several distinct ways to keep data alive across requests, each with a different lifetime,
scope, and cost -- picking the wrong one is a common source of both bugs (data that should have persisted did
not) and performance problems (data that did not need to persist was carried anyway).

== Client-side vs. server-side state

[cols="1,1,2"]
|===
| Mechanism | Scope | Notes

| ViewState / control state | One page, one user, round-trips every postback | See
  xref:web/aspnet/web-forms/view-state-and-control-state.adoc[ViewState and Control State] -- opaque to the
  client, carried in the response/request body.
| Hidden fields | One page, one user | Like ViewState but explicit and app-defined; no automatic
  serialization/tree-matching.
| Cookies | One user (or session), across pages, size-limited (~4KB) | Sent on every request to the matching
  domain/path regardless of whether the page needs them.
| Query string | One user, one URL, visible/bookmarkable | No server storage; easily tampered with, so never a
  substitute for authorization.
| `Application` | Whole app, all users, in-process only | See below.
| `Session` | One user, across pages, server- or out-of-process | See below.
| `Cache` | Whole app, expiration/eviction-aware | See below.
| `Profile` | One (typically authenticated) user, persisted to storage | Strongly typed, configured in
  `web.config`; see xref:web/aspnet/web-forms/user-and-custom-controls.adoc[User and Custom Controls].
|===

See https://learn.microsoft.com/en-us/previous-versions/aspnet/bb386448(v=vs.100)[ASP.NET State Management
Overview].

== `Application`, `Session`, `Cache`, and `Profile`

`Application` is a single, process-wide `IDictionary` shared by every user and every request -- rarely the
right choice today (no expiration, no locking safety by default, lost on app-pool recycle) but still seen as a
crude read-mostly cache:

[source,csharp]
----
protected void Application_Start(object sender, EventArgs e)
{
    Application["StartedAtUtc"] = DateTime.UtcNow;
}

protected void Page_Load(object sender, EventArgs e)
{
    Application.Lock();
    Application["HitCount"] = (int)(Application["HitCount"] ?? 0) + 1;
    Application.UnLock();
}
----

`Session` is per-user and is where the great majority of "remember this across pages" state actually belongs
(shopping cart contents, wizard-in-progress data, small caches of the current user's own data).

== Session modes

`sessionState` mode determines where session data physically lives:

[cols="1,3"]
|===
| Mode | Behavior

| `InProc` (default) | Stored in the worker process's memory. Fastest; lost on app-pool recycle/restart and
  does not work across a farm without sticky sessions.
| `StateServer` | Stored by a separate Windows service (`ASP.NET State Service`), survives app-pool recycles,
  works across a farm; objects must be serializable.
| `SQLServer` | Stored in a SQL Server database (`aspnet_regsql`-provisioned); survives process and even
  server restarts, works across a farm without sticky sessions; slowest of the three.
| `Custom` | A custom `SessionStateStoreProviderBase` implementation (e.g. a Redis- or NoSQL-backed provider).
|===

[source,xml]
----
<system.web>
  <sessionState mode="SQLServer"
      sqlConnectionString="Data Source=sqlserver;Initial Catalog=ASPState;Integrated Security=true"
      cookieless="false" timeout="20" />
</system.web>
----

**Session-less pages** (`<%@ Page EnableSessionState="false" %>` or `"ReadOnly"`) skip the session-state
locking overhead entirely (`EnableSessionState="True"` serializes concurrent requests from the same session
against each other) or read-only access, which is worth setting explicitly on any page that does not touch
`Session`. **Cookieless sessions** (`cookieless="true"` or `"AutoDetect"`) embed the session ID in the URL
instead of a cookie, at the cost of session-fixation risk and unwieldy URLs -- generally avoided in favor of
requiring cookies.

== The `Cache` API

`System.Web.Caching.Cache` (`HttpContext.Cache`/`Page.Cache`) is an application-wide, expiration- and
memory-pressure-aware store distinct from `Application` -- entries can expire on a timer, on a dependency
(file, another cache key, a SQL change), or be evicted under memory pressure, and can notify code when removed:

[source,csharp]
----
public Product GetProduct(int id)
{
    string key = "Product_" + id;
    if (Cache[key] is Product cached) return cached;

    var product = _repository.Find(id);
    Cache.Insert(key, product,
        dependencies: null,
        absoluteExpiration: DateTime.UtcNow.AddMinutes(10),
        slidingExpiration: Cache.NoSlidingExpiration,
        priority: CacheItemPriority.Normal,
        onRemoveCallback: (k, value, reason) => Trace.WriteLine($"Evicted {k}: {reason}"));
    return product;
}
----

**Dependencies** (`CacheDependency`) invalidate an entry when a file changes on disk, or when another cache key
is removed (chained invalidation); **priority** (`CacheItemPriority`) influences which entries are evicted
first under memory pressure; the **callback** lets code react to eviction (e.g. to re-warm the entry).

=== SQL cache dependency

`SqlCacheDependency` invalidates a cache entry when the underlying database rows actually change, using either
polling (SQL Server 7/2000-compatible, a background poll of a tracked table) or the newer query-notification
mechanism (`SqlDependency`, SQL Server 2005+):

[source,xml]
----
<system.web>
  <caching>
    <sqlCacheDependency enabled="true" pollTime="60000">
      <databases>
        <add name="CatalogDb" connectionStringName="CatalogDb" />
      </databases>
    </sqlCacheDependency>
  </caching>
</system.web>
----

[source,csharp]
----
var dependency = new SqlCacheDependency("CatalogDb", "Products");
Cache.Insert("AllProducts", products, dependency);
----

== Output caching

`@OutputCache` caches an entire page's (or user control's -- "fragment caching") rendered response, keyed by
its `+VaryBy*+` attributes:

[source,aspx]
----
<%@ OutputCache Duration="120" VaryByParam="category;page" VaryByHeader="Accept-Language" %>
----

* `VaryByParam` -- a separate cached entry per distinct query-string/form value combination (`"none"` for a
  single shared entry, `+"*"+` for every parameter).
* `VaryByControl` -- vary by a named control's value (typically on a user control being fragment-cached).
* `VaryByCustom` -- a free-form string resolved by overriding `HttpApplication.GetVaryByCustomString` (e.g.
  vary by device type or by authenticated-vs-anonymous).
* `VaryByHeader` -- vary by one or more request header values.

**Fragment caching** applies `@OutputCache` to a `.ascx` user control instead of the whole page, so a mostly
static sidebar can be cached independently of a dynamic main content area on the same page.

=== Post-cache substitution

`<asp:Substitution>` punches a hole in an otherwise output-cached page for content that must always be
per-request fresh (e.g. a greeting that names the signed-in user on an otherwise static page):

[source,aspx]
----
<%@ OutputCache Duration="300" VaryByParam="none" %>
...
<asp:Substitution ID="Greeting" runat="server" MethodName="GetGreeting" />
----

[source,csharp]
----
public static string GetGreeting(HttpContext context)
{
    // Static method; runs on every request even while the rest of the page is served from cache.
    return "Welcome, " + (context.User.Identity.Name ?? "Guest");
}
----

**Distributed output-cache providers** (`System.Web.Caching.OutputCacheProvider`, pluggable since ASP.NET 4)
let output-cache entries live outside a single worker process -- e.g. backed by a distributed cache such as
Redis -- so a farm shares one cache instead of each server caching independently.

See https://learn.microsoft.com/en-us/previous-versions/aspnet/xsbfdd8c(v=vs.100)[Caching Application Data]
and https://learn.microsoft.com/en-us/previous-versions/aspnet/06bh14hg(v=vs.100)[ASP.NET Output Caching].

== Worked example: the order cart in `Session`

The order-entry application keeps the in-progress order in `Session`. Wrapping the key in one typed accessor
removes magic strings from the pages and gives a single place to make the stored type serializable, which is
mandatory the day the session mode moves from `InProc` to `StateServer` or `SQLServer`:

[source,csharp]
----
// Services/CartSession.cs
using System;
using System.Collections.Generic;
using System.Linq;
using System.Web.SessionState;

namespace WebFormsApp.Services
{
    [Serializable]
    public class CartLine
    {
        public int ProductId { get; set; }
        public int Quantity { get; set; }
    }

    public static class CartSession
    {
        private const string Key = "Cart";

        public static List<CartLine> Current(HttpSessionState session)
        {
            var cart = session[Key] as List<CartLine>;
            if (cart == null)
            {
                cart = new List<CartLine>();
                session[Key] = cart;
            }

            return cart;
        }

        public static void Add(HttpSessionState session, int productId, int quantity)
        {
            List<CartLine> cart = Current(session);
            CartLine line = cart.FirstOrDefault(l => l.ProductId == productId);
            if (line == null)
            {
                cart.Add(new CartLine { ProductId = productId, Quantity = quantity });
            }
            else
            {
                line.Quantity += quantity;
            }
        }

        public static decimal Total(HttpSessionState session)
        {
            return Current(session).Sum(l => ProductCatalog.Find(l.ProductId).Price * l.Quantity);
        }
    }
}
----

[source,csharp]
----
// in a page's code-behind
protected void AddButton_Click(object sender, EventArgs e)
{
    CartSession.Add(Session, int.Parse(ProductList.SelectedValue), int.Parse(QuantityBox.Text));
    TotalLabel.Text = CartSession.Total(Session).ToString("C");
}
----

Two behaviors matter once more than one user, or more than one server, is involved. In an out-of-process mode the
whole session is serialized at the end of each request and deserialized at the start of the next, so a class that is
not `[Serializable]` (or holds, say, an open `SqlConnection`) fails at the *end of the request that stored it*, not at
the line that assigned it. And mutating the list after reading it from `Session` is saved only because reading a
mutable object through the indexer marks it dirty; a design that relied on a private static reference to the list
instead would silently lose changes.

== Session locking and why a long page blocks the next click

By default a request holds an exclusive lock on the session for its entire duration, which keeps the data
consistent but serializes every request from the same browser session: a slow report page makes the next click
wait for it to finish.

[mermaid]
....
sequenceDiagram
    participant A as Request A (report page, EnableSessionState = true)
    participant S as Session store
    participant B as Request B (next click)
    A->>S: acquire session, exclusive lock
    B->>S: acquire session
    Note over B,S: blocked until A finishes
    A->>A: long-running work
    A->>S: write back and release the lock
    S-->>B: lock granted
    B->>B: runs
....

The remedy is to declare per page what it needs: `EnableSessionState="ReadOnly"` takes a shared (non-exclusive) lock
and cannot write; `EnableSessionState="False"` takes no lock at all, which is right for `.ashx` handlers that serve
images or JSON (a handler gets no session at all unless its class implements `IRequiresSessionState` or
`IReadOnlySessionState`). Pages that only
read the cart should be `ReadOnly`; only the page that modifies it needs the default.

== `Session_End`, abandoning, and session fixation

`Session_End` in `global.asax` fires only in `InProc` mode; with `StateServer`, `SQLServer`, and custom providers it is
never raised, so cleanup logic must not depend on it. `Session.Abandon()` ends the session, but the browser still
holds the old session ID cookie and a *new* session starts on the next request under the same ID unless the cookie
is cleared, which matters at logout and, more importantly, at login: a session ID that was valid before
authentication must not remain valid after it, otherwise an attacker who planted that ID before the victim logged in
shares the victim's session (*session fixation*):

[source,csharp]
----
protected void LogoutButton_Click(object sender, EventArgs e)
{
    FormsAuthentication.SignOut();
    Session.Clear();
    Session.Abandon();
    Response.Cookies.Add(new HttpCookie("ASP.NET_SessionId", "") { Expires = DateTime.UtcNow.AddYears(-1) });
    Response.Redirect("~/Login.aspx");
}
----

== Worked example: a stampede-safe product cache

The usual use of the `Cache` API is *cache-aside*: look in the cache, load and store on a miss. The naive version has a
flaw under load: when a popular entry expires, every concurrent request misses at once and each one queries the
database. A double-checked lock around the load closes that gap:

[source,csharp]
----
// Services/ProductCache.cs
using System;
using System.Collections.Generic;
using System.Web;
using System.Web.Caching;

namespace WebFormsApp.Services
{
    public static class ProductCache
    {
        private const string Key = "products:all";
        private static readonly object Gate = new object();

        public static IReadOnlyList<Product> GetAll()
        {
            Cache cache = HttpRuntime.Cache;

            var items = cache[Key] as IReadOnlyList<Product>;
            if (items != null)
            {
                return items;
            }

            lock (Gate)
            {
                items = cache[Key] as IReadOnlyList<Product>; // another request may have loaded it while we waited
                if (items == null)
                {
                    items = ProductCatalog.All(); // stands in for a database query
                    cache.Insert(Key, items, null,
                        DateTime.UtcNow.AddMinutes(5), Cache.NoSlidingExpiration,
                        CacheItemPriority.Normal, null);
                }

                return items;
            }
        }

        public static void Invalidate()
        {
            HttpRuntime.Cache.Remove(Key);
        }
    }
}
----

[mermaid]
....
flowchart TD
    A["GetAll()"] --> B{"Entry in Cache?"}
    B -- yes --> R["Return cached list"]
    B -- no --> L["Take the lock"]
    L --> C{"Entry now in Cache?\n(another request loaded it)"}
    C -- yes --> R
    C -- no --> D["Load from the database,\nCache.Insert with 5-minute absolute expiration"]
    D --> R
    E["Admin edits a product"] --> F["ProductCache.Invalidate()"]
    F --> G["Next GetAll() misses and reloads"]
....

`HttpRuntime.Cache` is the same object as `Page.Cache`, but reachable from any class, including one with no
`HttpContext`; this is why a cache helper is a static class rather than something a page owns. Absolute expiration
bounds staleness (a sliding expiration would keep a hot entry alive forever); explicit `Invalidate` makes edits visible
at once; and the cache is per application domain, so on a farm each server has its own copy and invalidation reaches
only the server that handled the edit -- the situation `SqlCacheDependency` or a distributed cache exists for.

== Worked example: output caching with profiles and `VaryByCustom`

Output caching is configured per page, but repeating `Duration` and `+VaryBy*+` attributes across many pages
invites drift. A *cache profile* names the settings once in `web.config`:

[source,xml]
----
<system.web>
  <caching>
    <outputCacheSettings>
      <outputCacheProfiles>
        <add name="Catalog" duration="60" varyByParam="category;page" varyByCustom="user" />
      </outputCacheProfiles>
    </outputCacheSettings>
  </caching>
</system.web>
----

[source,aspx]
----
<%@ OutputCache CacheProfile="Catalog" %>
----

`varyByCustom="user"` is a key the application must interpret by overriding `GetVaryByCustomString` in
`global.asax`; the version below keeps one cached copy for anonymous visitors and one for authenticated ones, so
a "Welcome back" banner cannot leak into the anonymous copy:

[source,csharp]
----
// Global.asax.cs
public override string GetVaryByCustomString(HttpContext context, string custom)
{
    if (custom == "user")
    {
        return context.Request.IsAuthenticated ? "authenticated" : "anonymous";
    }

    return base.GetVaryByCustomString(context, custom);
}
----

[mermaid]
....
sequenceDiagram
    participant B as Browser
    participant M as OutputCacheModule
    participant P as Page
    B->>M: GET /Catalog?category=2
    M->>M: build key from path, category, page, user
    alt entry exists and not expired
        M-->>B: cached HTML (page code does not run)
    else miss
        M->>P: run the full page life cycle
        P-->>M: rendered HTML
        M->>M: store under the key
        M-->>B: HTML
    end
....

The same behavior can be set from code, which is the tool for decisions made at request time:

[source,csharp]
----
protected void Page_Load(object sender, EventArgs e)
{
    Response.Cache.SetCacheability(HttpCacheability.Public);
    Response.Cache.SetExpires(DateTime.UtcNow.AddSeconds(60));
    Response.Cache.VaryByParams["category"] = true;
    Response.Cache.AddValidationCallback(ValidateCachedCopy, null);
}

private static void ValidateCachedCopy(HttpContext context, object data, ref HttpValidationStatus status)
{
    // Called before each cache hit is served: mark the entry invalid to force a re-run of the page.
    status = ProductCache.IsStale() ? HttpValidationStatus.Invalid : HttpValidationStatus.Valid;
}
----

(`ProductCache.IsStale` is an application-defined check, for example a version counter bumped by `Invalidate`.)
Three rules prevent the common failures. Never output-cache a page whose markup contains per-user data without
varying on it. Be careful with postback pages: a cached response contains one user's `+__VIEWSTATE+` and
`+__EVENTVALIDATION+`, so output caching suits read-only pages and fragments, not forms. And `HttpCacheability.Public`
also allows proxies and the browser to cache the response, which is what you want for a public catalog and a leak
for anything authenticated; use `Server` or `ServerAndPrivate` for pages that vary by user.

See the https://learn.microsoft.com/en-us/aspnet/web-forms/[ASP.NET Web Forms documentation] and the https://learn.microsoft.com/en-us/previous-versions/aspnet/[ASP.NET 4 documentation archive]
for the session state and caching overviews.
