= User and Custom Controls
:description: .ascx user controls with properties and events; building custom server controls deriving from Control vs. WebControl, composite and templated controls, designer attributes; building a data-bound control; and Web Parts and personalization.
:keywords: ASP.NET Web Forms, ascx user control, custom server control, WebControl, INamingContainer, ITemplate, templated control, WebPartManager, personalization, Profile

include::partial$ai-disclaimer.adoc[]

Web Forms offers two ways to build a reusable piece of UI: a **user control** (markup-based, fast to author)
and a **custom server control** (code-based, compiled, distributable as a standalone assembly). This page
covers both, plus Web Parts, the framework built on top of custom controls for end-user page personalization.

== `.ascx` user controls

A user control is authored exactly like a page -- markup plus code-behind -- but has no `<html>`/`<form>` of
its own and is embedded into a hosting page via `@Register`:

[source,aspx]
----
<%-- Controls/AddressEditor.ascx --%>
<%@ Control Language="C#" CodeBehind="AddressEditor.ascx.cs" Inherits="WebFormsApp.Controls.AddressEditor" %>
<div class="address-editor">
    <asp:TextBox ID="StreetBox" runat="server" />
    <asp:TextBox ID="CityBox" runat="server" />
</div>
----

[source,csharp]
----
// Controls/AddressEditor.ascx.cs
public partial class AddressEditor : System.Web.UI.UserControl
{
    public event EventHandler AddressChanged;

    public string Street
    {
        get => StreetBox.Text;
        set => StreetBox.Text = value;
    }

    protected void StreetBox_TextChanged(object sender, EventArgs e)
        => AddressChanged?.Invoke(this, EventArgs.Empty);
}
----

[source,aspx]
----
<%@ Register TagPrefix="uc" TagName="AddressEditor" Src="~/Controls/AddressEditor.ascx" %>
<uc:AddressEditor ID="ShippingAddress" runat="server" OnAddressChanged="ShippingAddress_AddressChanged" />
----

Public properties (`Street` above) and events (`AddressChanged`) are exactly how the host page communicates
with the control; `@Reference` on the host page (or `Src=` on `@Register`, as above) is what makes the
control's strongly typed members visible at design time and compile time.

== Custom server controls

A custom server control is a compiled class, not markup, and lives in an ordinary class library assembly
referenced by any number of applications.

=== `Control` vs. `WebControl`

Deriving from `System.Web.UI.Control` gives the bare life-cycle/tree participation with no rendering
assumptions -- appropriate for a control with no visual output of its own, or one whose output shape does not
fit the single-root-tag model of `WebControl`. Deriving from `System.Web.UI.WebControl` (itself a `Control`) adds
the common styling API (`CssClass`, `Font`, `BackColor`, `Style`, ...) and a default single-tag rendering
model (`TagKey`, defaulting to `<span>`).

=== `Render`/`RenderContents` and `CreateChildControls`

[source,csharp]
----
[ToolboxData("<{0}:RatingStars runat=server></{0}:RatingStars>")]
public class RatingStars : WebControl
{
    public int Value { get; set; }
    public int MaxStars { get; set; } = 5;

    protected override HtmlTextWriterTag TagKey => HtmlTextWriterTag.Span;

    protected override void RenderContents(HtmlTextWriter writer)
    {
        for (int i = 1; i <= MaxStars; i++)
        {
            writer.AddAttribute(HtmlTextWriterAttribute.Class, i <= Value ? "star filled" : "star");
            writer.RenderBeginTag(HtmlTextWriterTag.Span);
            writer.Write(i <= Value ? "&#9733;" : "&#9734;");
            writer.RenderEndTag();
        }
    }
}
----

`Render` controls the entire output including the wrapping tag; overriding `RenderContents` instead (as
above) keeps the tag and attribute rendering of `WebControl` and only customizes what goes inside it.
`CreateChildControls` is where a **composite** control builds its own internal control tree (rather than
writing raw HTML), and is called lazily via `EnsureChildControls()` -- typically overridden instead of
`OnInit` so the tree is (re)built consistently across the life cycle, including after ViewState is restored.

=== `INamingContainer`

Implementing the marker interface `INamingContainer` makes a control's own `ClientID`/`UniqueID` become a
prefix for all of its children's IDs, guaranteeing uniqueness when the control (and therefore its children) is
repeated multiple times on one page -- essential for any composite or data-bound control that generates
children in a loop (a `Repeater` row, for instance, is itself a naming container).

=== Composite and templated controls

A **templated** control lets the *page author* supply the inner markup, rather than the control author baking
it in -- the pattern every data-bound list control (`Repeater`, `GridView` via `TemplateField`) is built on:

[source,csharp]
----
[ParseChildren(true)]
public class Callout : Control, INamingContainer
{
    private ITemplate _contentTemplate;

    [TemplateContainer(typeof(Control)), PersistenceMode(PersistenceMode.InnerProperty)]
    public ITemplate ContentTemplate
    {
        get => _contentTemplate;
        set => _contentTemplate = value;
    }

    protected override void CreateChildControls()
    {
        Controls.Clear();
        var container = new Control();
        _contentTemplate?.InstantiateIn(container);
        Controls.Add(container);
    }
}
----

[source,aspx]
----
<cc:Callout runat="server">
    <ContentTemplate>
        <p>Anything the page author wants, including <asp:Label runat="server" Text="other controls" />.</p>
    </ContentTemplate>
</cc:Callout>
----

`ITemplate.InstantiateIn(Control container)` is called during `CreateChildControls` to build whatever markup
the page author supplied into the control's own tree.

=== Designer attributes

`[ToolboxData]`, `[DefaultProperty]`, `[Bindable]`, `[Category]`, and `[Description]` (from
`System.ComponentModel`) drive how a control appears in the Visual Studio Toolbox and Properties window; none
affect runtime behavior.

=== Building a data-bound control

A minimal data-bound custom control implements `IPostBackDataHandler`/relies on `WebControl` plus a
`DataSource` property and overrides `DataBind`/`PerformDataBinding` to build its child controls from the bound
data during `CreateChildControls`, following the same `DataBinding`/bound-item events documented in
xref:web/aspnet/web-forms/data-binding-and-data-controls.adoc[Data Binding and Data Controls].

See https://learn.microsoft.com/en-us/previous-versions/aspnet/24tc38tf(v=vs.100)[Developing Custom ASP.NET
Server Controls].

== Web Parts and personalization

The Web Parts framework (`System.Web.UI.WebControls.WebParts`) turns custom controls into end-user
reconfigurable page regions -- Zones the user can drag parts between, minimize, close, and (per-user)
remember, which is the layer Vogel's *Professional Web Parts and Custom Controls with ASP.NET 2.0* is written
against:

[source,aspx]
----
<asp:WebPartManager ID="Manager1" runat="server" />
<asp:WebPartZone ID="LeftZone" runat="server">
    <ZoneTemplate>
        <uc:WeatherPart ID="Weather1" runat="server" Title="Weather" />
    </ZoneTemplate>
</asp:WebPartZone>
<asp:WebPartZone ID="RightZone" runat="server" />
----

[source,csharp]
----
public class WeatherPart : UserControl, IWebPart
{
    public string CatalogIconImageUrl { get; set; }
    public string Description { get; set; }
    public string Subtitle { get; set; }
    public string Title { get; set; }
    public string TitleUrl { get; set; }
    public bool AllowClose { get; set; } = true;
    public bool AllowHide { get; set; } = true;
    public bool AllowMinimize { get; set; } = true;
    public bool AllowZoneChange { get; set; } = true;
    public string AuthorizationFilter { get; set; }
}
----

`WebPartManager` orchestrates zones, drag-and-drop layout, and mode switching (`Browse`/`Design`/`Edit`);
**connections** let two parts exchange data declared through `[ConnectionProvider]`/`[ConnectionConsumer]`
methods; **personalization providers** (the default `SqlPersonalizationProvider`, backed by the ASPNETDB
schema) persist the per-page layout of each user; and `Profile` properties (configured in the `<profile>` section
of `web.config`) give strongly typed, per-user settings storage (`Profile.FavoriteColor`) available
anywhere in the application, independent of Web Parts specifically. See
https://learn.microsoft.com/en-us/previous-versions/aspnet/aa478965(v=msdn.10)[ASP.NET Web Parts Overview] and
https://learn.microsoft.com/en-us/previous-versions/aspnet/tx28h29t(v=vs.100)[ASP.NET Profile Properties
Overview].

== Choosing between a user control and a custom control

[mermaid]
....
flowchart TD
    A{"Reusable inside\none application only?"}
    A -->|yes| B{"Mostly layout of\nexisting controls?"}
    A -->|"no, shared across applications"| C["Custom server control\n(class library, NuGet package)"]
    B -->|yes| D["User control (.ascx)\nmarkup + code-behind"]
    B -->|"no, needs exact HTML, own rendering or templates"| C
    C --> E{"What does it render?"}
    E -->|"existing controls"| F["CompositeControl:\nCreateChildControls"]
    E -->|"its own HTML"| G["WebControl or Control:\nRenderContents or Render"]
    E -->|"rows from a data source"| H["CompositeDataBoundControl\nor DataBoundControl"]
....

A user control is the quickest way to extract repeated markup from a page, but it is copied by deployment (the
`.ascx` file travels with the site) and cannot be used from a second application without copying it. A custom
server control is compiled into an assembly, versioned, and usable from any project that references it, at the cost
of writing rendering and state handling in code.

== Worked example: a `ProductPicker` user control

The picker wraps a `DropDownList` over `ProductCatalog` (see
xref:web/aspnet/web-forms/getting-started.adoc[Getting Started]), shows the selected product's price, and tells its
host page when the selection changes, through a typed event rather than by exposing the inner list:

[source,aspx]
----
<%-- Controls/ProductPicker.ascx --%>
<%@ Control Language="C#" AutoEventWireup="true"
    CodeBehind="ProductPicker.ascx.cs" Inherits="WebFormsApp.Controls.ProductPicker" %>
<asp:DropDownList ID="ProductList" runat="server" AutoPostBack="true"
    OnSelectedIndexChanged="ProductList_SelectedIndexChanged" />
<asp:Label ID="PriceLabel" runat="server" />
----

[source,csharp]
----
// Controls/ProductPicker.ascx.cs
using System;
using System.Web.UI;
using WebFormsApp.Services;

namespace WebFormsApp.Controls
{
    public class ProductSelectedEventArgs : EventArgs
    {
        public ProductSelectedEventArgs(Product product)
        {
            Product = product;
        }

        public Product Product { get; private set; }
    }

    public partial class ProductPicker : UserControl
    {
        public event EventHandler<ProductSelectedEventArgs> ProductSelected;

        public int? SelectedProductId
        {
            get
            {
                int id;
                return int.TryParse(ProductList.SelectedValue, out id) ? id : (int?)null;
            }
        }

        protected void Page_Load(object sender, EventArgs e)
        {
            if (!IsPostBack)
            {
                ProductList.DataSource = ProductCatalog.All();
                ProductList.DataTextField = "Name";
                ProductList.DataValueField = "Id";
                ProductList.DataBind();
            }
        }

        protected void ProductList_SelectedIndexChanged(object sender, EventArgs e)
        {
            Product product = ProductCatalog.Find(int.Parse(ProductList.SelectedValue));
            PriceLabel.Text = product.Price.ToString("C");

            EventHandler<ProductSelectedEventArgs> handler = ProductSelected;
            if (handler != null)
            {
                handler(this, new ProductSelectedEventArgs(product));
            }
        }
    }
}
----

[source,aspx]
----
<%@ Register TagPrefix="uc" TagName="ProductPicker" Src="~/Controls/ProductPicker.ascx" %>
<uc:ProductPicker ID="Picker" runat="server" OnProductSelected="Picker_ProductSelected" />
<asp:Label ID="ChosenLabel" runat="server" />
----

[source,csharp]
----
protected void Picker_ProductSelected(object sender, ProductSelectedEventArgs e)
{
    ChosenLabel.Text = "Selected: " + e.Product.Name;
}
----

The same control can be created from code with `LoadControl`. Dynamically loaded user controls obey the rules from
the page life cycle: create them on *every* request, in `Init`, and give them an explicit `ID`, or their
ViewState and the events they raise cannot be matched on the postback:

[source,csharp]
----
protected override void OnInit(EventArgs e)
{
    base.OnInit(e);
    var picker = (ProductPicker)LoadControl("~/Controls/ProductPicker.ascx");
    picker.ID = "Picker";
    picker.ProductSelected += Picker_ProductSelected;
    PickerHolder.Controls.Add(picker); // PickerHolder is a PlaceHolder in the page
}
----

== Worked example: a composite `QuantityStepper`

Where a user control assembles controls in markup, a *composite* custom control assembles them in code, so it can be
compiled into a library. `CompositeControl` already implements `INamingContainer`, calls `EnsureChildControls` whenever its `Controls`
collection is read, and wraps the output in a `<span>`:

[source,csharp]
----
// Controls/QuantityStepper.cs
using System;
using System.Web.UI;
using System.Web.UI.WebControls;

[assembly: TagPrefix("WebFormsApp.Controls", "cc")]

namespace WebFormsApp.Controls
{
    public class QuantityStepper : CompositeControl
    {
        private TextBox _box;
        private Button _down;
        private Button _up;

        public event EventHandler ValueChanged;

        public int Minimum
        {
            get { return (int)(ViewState["Minimum"] ?? 0); }
            set { ViewState["Minimum"] = value; }
        }

        public int Maximum
        {
            get { return (int)(ViewState["Maximum"] ?? 100); }
            set { ViewState["Maximum"] = value; }
        }

        public int Value
        {
            get
            {
                EnsureChildControls();
                int parsed;
                return int.TryParse(_box.Text, out parsed) ? parsed : Minimum;
            }
            set
            {
                EnsureChildControls();
                _box.Text = value.ToString();
            }
        }

        protected override void CreateChildControls()
        {
            Controls.Clear();

            _down = new Button { ID = "Down", Text = "-", CausesValidation = false };
            _box = new TextBox { ID = "Box", Columns = 3, Text = Minimum.ToString() };
            _up = new Button { ID = "Up", Text = "+", CausesValidation = false };

            _down.Click += Step;
            _up.Click += Step;

            Controls.Add(_down);
            Controls.Add(_box);
            Controls.Add(_up);
        }

        private void Step(object sender, EventArgs e)
        {
            int delta = ReferenceEquals(sender, _up) ? 1 : -1;
            Value = Math.Max(Minimum, Math.Min(Maximum, Value + delta));

            EventHandler handler = ValueChanged;
            if (handler != null)
            {
                handler(this, EventArgs.Empty);
            }
        }
    }
}
----

[source,aspx]
----
<%@ Register TagPrefix="cc" Namespace="WebFormsApp.Controls" Assembly="WebFormsApp" %>
<cc:QuantityStepper ID="Stepper" runat="server" Minimum="1" Maximum="50"
    OnValueChanged="Stepper_ValueChanged" />
----

Four things in this class generalize. The properties are stored in `ViewState` so they survive postbacks; the child
controls are created in `CreateChildControls`, not in the constructor, so they are built at the point where the
framework is ready to apply ViewState and postback data to them; the clicks of the inner buttons are consumed
inside the control and surfaced as one meaningful event (`ValueChanged`) instead of leaking the buttons; and
because the stepper is a naming container, two steppers on one page produce distinct unique IDs
(`Stepper$Up` and `Stepper2$Up`), which the page-level
xref:web/aspnet/web-forms/server-controls.adoc[control identity rules] require.

[mermaid]
....
sequenceDiagram
    participant B as Browser
    participant S as QuantityStepper
    participant U as Up button (child)
    participant P as Page
    B->>S: POST with __EVENTTARGET = Stepper$Up
    S->>S: CreateChildControls (during Init or EnsureChildControls)
    S->>U: restore posted text into Box, route the click to Up
    U->>S: Click event, handled by Step
    S->>S: clamp Value to Minimum and Maximum
    S->>P: ValueChanged event
    P->>P: Stepper_ValueChanged runs
....

== Worked example: a data-bound control

A data-bound control gets its rows from `DataSource` or `DataSourceID` just like `Repeater`. The simplest correct
base class is `CompositeDataBoundControl`, which solves the hard part -- re-creating the child controls from
ViewState on a postback -- by calling the same method twice: once with real data (`dataBinding` is `true`), and
on later requests with a placeholder list of `null` items of the same length (`dataBinding` is `false`), so the
control tree has the same shape and ViewState can fill in the values:

[source,csharp]
----
// Controls/ProductBullets.cs -- renders one list item element per bound item
using System;
using System.Collections;
using System.Web.UI;
using System.Web.UI.HtmlControls;
using System.Web.UI.WebControls;

namespace WebFormsApp.Controls
{
    public class ProductBullets : CompositeDataBoundControl
    {
        public string DataTextField
        {
            get { return (string)(ViewState["DataTextField"] ?? ""); }
            set { ViewState["DataTextField"] = value; }
        }

        protected override HtmlTextWriterTag TagKey
        {
            get { return HtmlTextWriterTag.Ul; }
        }

        protected override int CreateChildControls(IEnumerable dataSource, bool dataBinding)
        {
            int count = 0;
            foreach (object item in dataSource)
            {
                var li = new HtmlGenericControl("li");
                if (dataBinding)
                {
                    li.InnerText = Convert.ToString(DataBinder.Eval(item, DataTextField));
                }

                Controls.Add(li);
                count++;
            }

            return count;
        }
    }
}
----

[source,aspx]
----
<asp:ObjectDataSource ID="CatalogSource" runat="server"
    TypeName="WebFormsApp.Services.ProductCatalog" SelectMethod="All" />
<cc:ProductBullets ID="Bullets" runat="server" DataSourceID="CatalogSource" DataTextField="Name" />
----

The rule to remember is the `dataBinding` flag: reading `item` when it is `false` hits a `null`, and anything
assigned in the bound branch must be a value that ViewState can restore (`InnerText` of an `HtmlGenericControl`
is; a field of the control is not). `ProductCatalog.All` is a static method returning `IReadOnlyList<Product>`, which
`ObjectDataSource` accepts as an `IEnumerable`. For richer controls the same shape extends with templates: the
`ItemTemplate` is instantiated into a container per row in the `dataBinding` branch, as `Repeater` does.

See https://learn.microsoft.com/en-us/dotnet/api/system.web.ui.webcontrols.compositedataboundcontrol[CompositeDataBoundControl
Class] and the https://learn.microsoft.com/en-us/previous-versions/aspnet/[ASP.NET 4 documentation archive] for the server control development topics.
