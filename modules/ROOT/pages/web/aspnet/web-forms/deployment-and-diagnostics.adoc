= Deployment and Diagnostics
:description: IIS application pools and CLR/bitness settings, Web Deploy and Visual Studio publish profiles, precompiled vs. updatable deployment, customErrors and error pages, tracing, health monitoring, ELMAH, performance counters, and web.config environment differences.
:keywords: ASP.NET Web Forms, IIS application pool, Web Deploy, MSDeploy, publish profile, customErrors, Page.Trace, healthMonitoring, ELMAH, performance counters

include::partial$ai-disclaimer.adoc[]

Running a Web Forms application in production is inseparable from IIS -- this page covers the deployment and
operational-diagnostics concerns specific to that combination, on top of the ordinary "watch the logs" practices
that apply to any web application.

== IIS application pools

Each IIS **application pool** is an isolated worker process (`w3wp.exe`) hosting one or more applications, with
its own recycling schedule, identity, and CLR settings:

[cols="1,2"]
|===
| Setting | Why it matters for Web Forms

| **Integrated pipeline** | The default and effectively only mode used today -- see
  xref:web/aspnet/web-forms/http-pipeline-handlers-and-configuration.adoc[HTTP Pipeline, Handlers, and
  Configuration] for classic-vs-integrated behavior.
| **32-bit vs. 64-bit** | "Enable 32-Bit Applications" must match what any native-dependency assemblies were
  built for; a mismatch throws a `BadImageFormatException` at load time, not at compile time.
| **.NET CLR version** | `.NET Framework 4.x` (Web Forms always uses "v4.0" here regardless of the specific
  4.x version targeted -- 4.0 through 4.8.1 share one CLR) vs. the legacy "v2.0" pool setting, relevant only
  for ancient ASP.NET 1.1/2.0-3.5 applications still needing the old CLR.
| **Recycling** | Scheduled/idle-timeout/memory-threshold recycling drops all in-process state --
  `InProc` session, `Application`, in-memory `Cache` -- which is exactly why
  xref:web/aspnet/web-forms/state-management-and-caching.adoc[out-of-process session state] matters for any
  application that cannot tolerate that.
|===

== Web Deploy (MSDeploy) and Visual Studio publishing profiles

**Web Deploy** (`msdeploy.exe`) synchronizes a built application, IIS site/app-pool settings, and optionally
databases, from a build machine (or CI agent) to a target server, either directly over the Web Management
Service or by producing a portable package:

[source,batch]
----
msdeploy.exe -verb:sync -source:contentPath="C:\src\MyApp\obj\Release\Package\PackageTmp" ^
    -dest:contentPath="MyApp",computerName="https://webserver:8172/msdeploy.axd",userName=deploy,password=%DEPLOY_PW%,authType=basic
----

A **publish profile** (`.pubxml`, created and edited through Visual Studio's Publish dialog, or hand-edited)
captures a named deployment target's settings -- destination, credentials reference, whether to precompile,
which `web.config` transform to apply -- so a repeatable `msbuild /p:DeployOnBuild=true
/p:PublishProfile=Production` can run from CI without Visual Studio installed.

== Precompiled vs. updatable deployment

As introduced in
xref:web/aspnet/web-forms/http-pipeline-handlers-and-configuration.adoc[HTTP Pipeline, Handlers, and
Configuration], `aspnet_compiler` (invoked automatically by a Web Deploy publish, or run standalone) produces
either an **updatable** precompiled site (markup `.aspx`/`.ascx` files still deployed, tweakable in place
without recompiling; code-behind is precompiled into assemblies) or a fully **non-updatable** precompiled site
(everything, including markup, compiled to assemblies -- nothing readable/editable remains on disk). Fully
precompiled is the safer default for anything beyond a small internal tool: it removes first-request
compilation latency, avoids leaking source-adjacent markup on the server, and prevents an accidental
production hotfix made by editing a file directly on the server (a workflow the Web Site Project model, see
xref:web/aspnet/web-forms/getting-started.adoc[Getting Started], made easy but which bypasses source control
entirely).

== `<customErrors>` and error pages

[source,xml]
----
<system.web>
  <customErrors mode="RemoteOnly" defaultRedirect="~/Errors/Generic.aspx">
    <error statusCode="404" redirect="~/Errors/NotFound.aspx" />
    <error statusCode="500" redirect="~/Errors/ServerError.aspx" />
  </customErrors>
</system.web>
----

`mode="RemoteOnly"` (the default) shows the detailed ASP.NET error/stack-trace page to requests from the local
machine only, and the friendly `customErrors` page to everyone else -- `mode="On"` forces friendly pages
everywhere (including locally, useful when testing the error pages themselves), `mode="Off"` disables the
feature entirely and should never be set in production, since it leaks stack traces (and potentially
connection strings, in an unhandled exception message) to end users.

== Page and application `Trace`

`Page.Trace`/`<trace>` in `web.config` gives per-request diagnostic output -- request/response details,
control-tree size and ViewState contribution per control (relevant to
xref:web/aspnet/web-forms/view-state-and-control-state.adoc[measuring ViewState weight]), session/application
state dumps, and custom timed messages -- either inline at the bottom of the page or collected centrally:

[source,xml]
----
<system.web>
  <trace enabled="true" requestLimit="40" pageOutput="false" localOnly="true" />
</system.web>
----

[source,csharp]
----
protected void Page_Load(object sender, EventArgs e)
{
    Trace.Write("OrderPage", "Loading order " + Request.QueryString["id"]);
}
----

With `pageOutput="false"`, trace output is collected application-wide and viewed at `+~/Trace.axd+` instead of
appended to every page -- the practical choice for anything beyond debugging a single page locally, since it
does not alter the page's own rendered output.

== Health monitoring

`<healthMonitoring>` is ASP.NET's built-in event-based monitoring system -- application lifecycle events,
unhandled exceptions, Membership/Forms-authentication failures, and custom `WebBaseEvent`-derived events -- are
routed to one or more configured providers (SQL Server, email, the Windows event log, or a custom provider):

[source,xml]
----
<system.web>
  <healthMonitoring enabled="true">
    <providers>
      <add name="SqlWebEventProvider" type="System.Web.Management.SqlWebEventProvider"
           connectionStringName="HealthMonitoring" buffer="false" />
    </providers>
    <rules>
      <add name="All Errors Default" eventName="All Errors" provider="SqlWebEventProvider" />
    </rules>
  </healthMonitoring>
</system.web>
----

This predates, and covers roughly the same ground as, structured application logging in later frameworks --
most current Web Forms applications either lean on this built-in system for baseline coverage or replace it
outright with a conventional logging library (log4net, NLog, Serilog) called directly from
`Application_Error` and other code.

== ELMAH

**ELMAH** (Error Logging Modules and Handlers) is the de facto standard third-party error-logging package for
`System.Web` applications -- a drop-in `HttpModule` (NuGet: `elmah`) that captures every unhandled exception
automatically, with zero code changes, and exposes a browsable log (`+~/elmah.axd+`) plus pluggable storage
(SQL Server, SQLite, Azure Table Storage, XML files, ...):

[source,xml]
----
<system.webServer>
  <modules>
    <add name="ErrorLog" type="Elmah.ErrorLogModule, Elmah" preCondition="managedHandler" />
  </modules>
</system.webServer>
----

ELMAH and `<healthMonitoring>` are not mutually exclusive but overlap significantly in the "log unhandled
exceptions somewhere reviewable" use case -- most teams pick one rather than running both.

== Performance counters

ASP.NET registers a set of Windows Performance Counters under the `ASP.NET Apps v4.0.30319` and `ASP.NET
v4.0.30319` categories -- `Requests/Sec`, `Requests Queued`, `Requests Timed Out`, `% Managed Processor Time`,
`Errors Total/Sec`, `Sessions Active`, `Cache Total Hit Ratio` -- viewable live via Performance Monitor
(`perfmon.exe`) or captured for trend analysis by any monitoring agent that reads Windows performance counters.
`Requests Queued` climbing under load is the classic early signal of thread-pool starvation, frequently caused
by blocking synchronous I/O in code that should have been made asynchronous.

== The classic "works on my machine" `web.config` differences

The most common source of "it worked in dev, broke in production" for Web Forms specifically: a `web.config`
`<compilation debug="true">` left on in production (major performance cost -- disables batch compilation, turns off
request timeouts, and keeps compiled debug artifacts and extra symbol information around), a `machineKey` that is
auto-generated per-server rather than explicitly shared across a farm (breaking ViewState/Forms-auth validation
intermittently depending on which server handles a given request -- see
xref:web/aspnet/web-forms/security.adoc[Security]), and connection strings or `<appSettings>` pointing at a
developer's local database because a `Web.Release.config` transform was never actually wired up or tested.
Verifying the *deployed*, post-transform `web.config` on the target server -- not just the source-controlled
one -- after every release catches most of these before they become an incident.

See https://learn.microsoft.com/en-us/previous-versions/aspnet/dd394698(v=vs.100)[ASP.NET Web Deployment
Overview for Visual Studio and IIS] and
https://learn.microsoft.com/en-us/previous-versions/aspnet/bb763046(v=vs.100)[ASP.NET Health Monitoring
Overview].

== Worked example: provisioning the IIS site and pool from a script

Click-built IIS configuration is the usual reason a staging server and the production server behave differently. The
settings that matter for a Web Forms application can be applied by an idempotent PowerShell script from the
`WebAdministration` module, run by the deployment pipeline on every release:

[source,powershell]
----
# provision-iis.ps1 -- safe to run repeatedly
Import-Module WebAdministration

$pool = 'OrderDesk'
$site = 'OrderDesk'
$path = 'D:\sites\OrderDesk'

if (-not (Test-Path "IIS:\AppPools\$pool")) { New-WebAppPool -Name $pool | Out-Null }
$poolPath = "IIS:\AppPools\$pool"
Set-ItemProperty $poolPath -Name managedRuntimeVersion -Value 'v4.0'      # one CLR for every 4.x
Set-ItemProperty $poolPath -Name managedPipelineMode   -Value 'Integrated'
Set-ItemProperty $poolPath -Name startMode             -Value 'AlwaysRunning'   # start at boot, not at first request
Set-ItemProperty $poolPath -Name processModel.idleTimeout -Value ([TimeSpan]::Zero) # never unload an idle app
Set-ItemProperty $poolPath -Name recycling.periodicRestart.time -Value ([TimeSpan]::Zero) # no fixed-interval restart

if (-not (Test-Path "IIS:\Sites\$site")) {
    New-Website -Name $site -PhysicalPath $path -ApplicationPool $pool -Port 80 | Out-Null
}
Set-ItemProperty "IIS:\Sites\$site" -Name applicationDefaults.preloadEnabled -Value $true # warm up after (re)start
----

`startMode=AlwaysRunning` together with `preloadEnabled` means the worker process starts when the machine boots and
IIS sends it a synthetic request (the *application initialization* feature) before the first user arrives, so the
compilation cost described under
xref:web/aspnet/web-forms/getting-started.adoc[Getting Started] is paid before traffic, not by the first visitor. A
Windows feature, *Application Initialization*, must be installed for the preload to take effect.

[mermaid]
....
sequenceDiagram
    participant LB as Load balancer
    participant A as Worker process A (old)
    participant B as Worker process B (new)
    Note over A: recycle triggered (deployment, schedule, memory limit)
    A->>B: overlapped recycle: start the new process
    B->>B: Application_Start, compile pages, preload
    LB->>A: requests still served by A while B warms up
    B-->>LB: warm, begins accepting requests
    A->>A: finish in-flight requests, then shut down
    Note over A,B: InProc Session, Application and Cache of A are lost
....

Overlapped recycling (the default) keeps the site available during a recycle, but it does not carry state across:
in-memory session and cache entries vanish with the old process, which is the operational reason for the
out-of-process session modes in
xref:web/aspnet/web-forms/state-management-and-caching.adoc[State Management and Caching]. For a deployment that
replaces files, dropping an `app_offline.htm` file in the application root makes ASP.NET unload the application and
answer every request with that page until the file is removed, which is the safe way to copy files that must not be
served half-updated.

== Worked example: a release pipeline

Putting the build, transform, publish, and verification steps in a fixed order makes releases repeatable, and gives a
single place to add the post-deployment check recommended at the end of this page:

[mermaid]
....
flowchart LR
    A["Build\nmsbuild Release,\nrestore NuGet packages"] --> B["Package\nWeb Deploy package with\nWeb.Release.config transform applied"]
    B --> C["Deploy to staging\nmsdeploy sync with SetParameters\nfor connection strings"]
    C --> D{"Smoke test\n/health.ashx returns 200?"}
    D -- no --> E["Stop: keep production on\nthe previous package"]
    D -- yes --> F["Deploy to production\napp_offline.htm, sync, remove it"]
    F --> G{"Smoke test"}
    G -- no --> H["Roll back:\nredeploy previous package"]
    G -- yes --> I["Done"]
....

The package step is where secrets stay out of source control. A Web Deploy package ships a `parameters.xml` that
declares which values vary per environment, and each target supplies them in a `SetParameters.xml` held by the
pipeline, not by the repository:

[source,batch]
----
msbuild WebFormsApp.csproj /p:Configuration=Release /p:DeployOnBuild=true /p:WebPublishMethod=Package ^
    /p:PackageLocation=C:\out\WebFormsApp.zip

C:\out\WebFormsApp.deploy.cmd /Y /M:https://webserver:8172/msdeploy.axd -setParamFile:C:\secrets\production.SetParameters.xml
----

[source,xml]
----
<!-- parameters.xml (in the project): declares the value that differs per environment -->
<parameters>
  <parameter name="CatalogDb connection string" defaultValue="Data Source=.;Initial Catalog=Catalog;Integrated Security=true">
    <parameterEntry kind="XmlFile" scope="Web\.config$"
                    match="/configuration/connectionStrings/add[@name='CatalogDb']/@connectionString" />
  </parameter>
</parameters>
----

The `.deploy.cmd` produced by the package build calls `msdeploy` with the package and the parameter file, so the same
artifact that passed staging is the one promoted to production, differing only in injected values.

== Worked example: logging every unhandled error, with a health endpoint

Error pages tell the visitor something went wrong; the log tells the team why. `Application_Error` is the one place
every unhandled exception from a page, handler, or module passes through, so it is where logging belongs. The version
below uses the correlation ID from the `RequestDecorationModule` of
xref:web/aspnet/web-forms/http-pipeline-handlers-and-configuration.adoc[HTTP Pipeline, Handlers, and Configuration]
and writes through `System.Diagnostics.Trace`, so the destination is chosen in configuration, not code:

[source,csharp]
----
// Global.asax.cs
using System;
using System.Web;

protected void Application_Error(object sender, EventArgs e)
{
    Exception exception = Server.GetLastError();
    if (exception == null)
    {
        return;
    }

    var http = exception as HttpException;
    if (http != null && http.GetHttpCode() == 404)
    {
        return; // missing pages are not application errors; the 404 page handles them
    }

    string correlationId = Context.Items["CorrelationId"] as string ?? "n/a";
    System.Diagnostics.Trace.TraceError("[{0}] {1} {2}: {3}",
        correlationId, Request.HttpMethod, Request.RawUrl, exception.GetBaseException());
}
----

[source,xml]
----
<system.diagnostics>
  <trace autoflush="true">
    <listeners>
      <add name="file" type="System.Diagnostics.TextWriterTraceListener" initializeData="D:\logs\orderdesk.log" />
    </listeners>
  </trace>
</system.diagnostics>
----

The pool identity needs write permission on the log folder, or the listener fails silently, which is the usual
reason "the log is empty". The error page then needs to report the failure honestly, because a `customErrors`
redirect by default answers `200 OK` (a "soft error" that monitors and crawlers read as success):

[source,xml]
----
<system.web>
  <customErrors mode="RemoteOnly" defaultRedirect="~/Errors/Generic.aspx" redirectMode="ResponseRewrite" />
</system.web>
----

[source,csharp]
----
// Errors/Generic.aspx.cs
protected void Page_Load(object sender, EventArgs e)
{
    Response.StatusCode = 500;
    Response.TrySkipIisCustomErrors = true; // keep this body instead of IIS substituting its own error page
}
----

Finally, a load balancer and the release pipeline both need a cheap answer to "is this instance working?". A handler that
touches the dependencies the application cannot live without, and answers with a status code, serves both:

[source,csharp]
----
// Handlers/Health.ashx.cs
using System.Configuration;
using System.Data.SqlClient;
using System.Web;

namespace WebFormsApp.Handlers
{
    public class Health : IHttpHandler
    {
        public bool IsReusable { get { return true; } }

        public void ProcessRequest(HttpContext context)
        {
            context.Response.ContentType = "text/plain";
            context.Response.Cache.SetCacheability(HttpCacheability.NoCache);
            try
            {
                string connectionString = ConfigurationManager.ConnectionStrings["CatalogDb"].ConnectionString;
                using (var connection = new SqlConnection(connectionString))
                {
                    connection.Open();
                }

                context.Response.Write("OK");
            }
            catch (SqlException)
            {
                context.Response.StatusCode = 503;
                context.Response.Write("database unavailable");
            }
        }
    }
}
----

The endpoint deliberately returns no connection details, only a status word, and it should be reachable without
authentication only if the load balancer cannot authenticate; otherwise restrict it to the balancer's address range with IIS IP address
restrictions (`system.webServer/security/ipSecurity` under a `<location>`).

See the https://learn.microsoft.com/en-us/aspnet/web-forms/[ASP.NET Web Forms documentation] and the
https://learn.microsoft.com/en-us/previous-versions/aspnet/[ASP.NET 4 documentation archive] for the Web Deploy
packaging and IIS application-pool topics.
