= Migrating to Modern ASP.NET
:description: The honest support picture for Web Forms, the incremental System.Web.Adapters + YARP migration path, the .NET Upgrade Assistant, Blazor Server as the closest conceptual target with a concept-mapping table, DotVVM as an in-place alternative, what must be rewritten outright, and realistic effort framing.
:keywords: ASP.NET Web Forms, migration, System.Web.Adapters, YARP, .NET Upgrade Assistant, Blazor Server, DotVVM, incremental migration, strangler fig

include::partial$ai-disclaimer.adoc[]

This page is the practical follow-up to xref:web/aspnet/web-forms/index.adoc[the section landing page]'s
support-status summary: given that a Web Forms application exists and needs to move forward, what are the
actual options, and what does each one really cost.

== The honest support picture

Repeated once more because it drives every decision on this page: **there is no automatic upgrade path from
Web Forms to any current ASP.NET.** .NET Framework 4.8.1 receives security fixes only and has no successor;
Web Forms itself never ran on .NET Core/.NET 5+ and Microsoft has not indicated it ever will. Moving off Web
Forms means re-platforming to a different UI framework, full stop -- the choice is *which* framework and *how
much at once*, not whether a mechanical conversion tool can do it for you the way `dotnet` tooling can bump a
.NET 8 project to .NET 10. See
https://learn.microsoft.com/en-us/aspnet/web-forms/[the ASP.NET Web Forms documentation] and
https://learn.microsoft.com/en-us/lifecycle/products/microsoft-net-framework[the .NET Framework support
lifecycle] for the current, authoritative statement of this.

== The incremental migration path: `System.Web.Adapters` + YARP

For an application under active development -- too large or too risky to rewrite in one release -- the
practical strategy is the *strangler fig* pattern: run the legacy .NET Framework application and a new
ASP.NET Core application side by side behind a reverse proxy, and move functionality across page by page.

[mermaid]
....
flowchart LR
    Client[Browser] --> Proxy[YARP reverse proxy]
    Proxy -->|"/legacy/*, not-yet-migrated pages"| WF["ASP.NET Web Forms\n(.NET Framework 4.8.1)"]
    Proxy -->|"migrated pages"| Core["ASP.NET Core\n(current LTS)"]
    WF <-->|shared Session / auth ticket\nvia System.Web.Adapters| Core
....

* **YARP** (Yet Another Reverse Proxy, a Microsoft-built .NET library) sits in front of both applications and
  routes each request to whichever one currently owns that URL -- as pages are migrated, routes move from the
  Web Forms backend to the ASP.NET Core backend, with no visible change to the end user.
* **`System.Web.Adapters`** (the `Microsoft.AspNetCore.SystemWebAdapters` / matching `System.Web`-side package)
  is what makes the two halves usable *together* during the transition rather than as two unrelated
  applications -- it lets the ASP.NET Core side read and write `HttpContext`-shaped state
  (`Session`, in particular) in a way that round-trips correctly with the still-running Web Forms side's
  session store, and shares the Forms authentication ticket/cookie so a user does not have to re-log-in when a
  request happens to land on the other backend.
* Each release moves a self-contained slice of pages from the Web Forms side to the ASP.NET Core side,
  re-implemented as Razor Pages/MVC/Blazor; YARP's routing config is updated to match; the Web Forms
  application shrinks release over release until nothing routes to it and it can be retired.

This is materially more engineering effort up front than a rewrite-in-place would look like on paper, but it
is what makes migrating a large, continuously-shipping application tractable without a multi-month feature
freeze. See https://learn.microsoft.com/en-us/aspnet/core/migration/inc/overview[Incremental ASP.NET to
ASP.NET Core migration] and https://microsoft.github.io/reverse-proxy/[the YARP documentation]. For the same
strangler strategy treated technology-neutrally, see
xref:backend/architecture/decisions-and-migrations/migration-path-legacy-to-modern-stack.adoc[Migration Path: From a Legacy Stack to a
Modern One].

== The .NET Upgrade Assistant

The `dotnet-upgrade-assistant` global tool automates the *mechanical* parts of any .NET Framework -> .NET
migration -- project file conversion (old-style `.csproj` to SDK-style), NuGet `packages.config` to
`PackageReference`, and known API substitutions. For **Web Forms specifically it does not, and cannot,
convert `.aspx`/code-behind into Razor/Blazor** -- there is no mechanical equivalent for the page/control
model. It is genuinely useful preparation work (getting the project file and package references into a shape
that will build under a modern SDK) but does not replace the actual UI rewrite described in the rest of this
page. It is considerably more effective on an MVC 5 codebase -- see
xref:web/aspnet/mvc/index.adoc[ASP.NET MVC]'s own migration coverage -- because MVC's controller/view split
maps far more directly onto ASP.NET Core than Web Forms' control tree does.

== Blazor Server as the closest conceptual target

Of the current ASP.NET Core UI models, **Blazor Server** is the closest conceptual match to Web Forms: both
are server-rendered, stateful, event-driven UI models where a persistent server-side connection (a SignalR
circuit, in Blazor's case, vs. postback-per-interaction in Web Forms) carries UI events to the server and
patches the client DOM in response, rather than requiring the client to manage its own application state the
way a SPA or Blazor WebAssembly app does.

[cols="1,2"]
|===
| Web Forms concept | Blazor Server equivalent

| Control tree (`Page`, `Control`) | Component tree (`ComponentBase`, `.razor` files)
| `Page_Load` | `OnInitializedAsync` / `OnParametersSetAsync`
| Postback (`+__doPostBack+`, full round trip) | Server event over a persistent SignalR circuit (no full-page
  round trip)
| ViewState | No equivalent needed -- component state lives server-side in the circuit for its lifetime;
  see xref:web/aspnet/core/blazor-state-management.adoc[Blazor State Management] for what *does* need
  explicit handling (state that must survive a circuit reconnect)
| User control (`.ascx`) | Razor component (`.razor`), parameterized via `[Parameter]`
| `EnableViewState`/`ViewStateMode` | Not applicable -- state is simply server-side C# fields for the
  component's lifetime
| `UpdatePanel` partial rendering | The default and only rendering model -- every component update is
  already incremental
| Server control library (`GridView`, `Wizard`, ...) | A Blazor component library
  (xref:web/aspnet/core/ui-component-libraries.adoc[UI Component Libraries] catalogs the main options)
|===

The migration is still a rewrite -- `.aspx` markup and code-behind do not mechanically become `.razor` files --
but the *mental model* transfers more directly than to Razor Pages/MVC, which is why teams coming from Web
Forms often find Blazor Server the most comfortable landing spot conceptually, even though the actual
component code is new. Microsoft's free e-book,
https://dotnet.microsoft.com/en-us/learn/aspnet/blazor-for-web-forms-devs-ebook[*Blazor for ASP.NET Web Forms
Developers*], is written specifically for this audience and walks the same conceptual mapping in much greater
depth than fits here.

== In-place modernization with DotVVM as an alternative

**DotVVM** (open-source, https://www.dotvvm.com/[dotvvm.com]) is a third-party MVVM-based web framework for
.NET that deliberately targets teams coming from Web Forms: it runs on both .NET Framework and current .NET,
supports a more gradual in-place adoption (new pages written in DotVVM's own markup/viewmodel model,
coexisting with remaining `.aspx` pages in the same application, without the two-application YARP setup above),
and offers server-side rendering with two-way data binding conceptually closer to Web Forms' postback model
than a component-per-request Razor approach. It is a smaller ecosystem than Blazor/MVC and not a Microsoft
product, which is the trade-off against its gentler migration curve -- worth evaluating specifically when a
full side-by-side YARP migration is judged too heavyweight for the application's size, but not a default
recommendation over Blazor Server/MVC for a green-field rewrite.

== What has to be rewritten outright

Some Web Forms-era investments have no automated or even semi-automated path forward and must be redesigned:

[cols="1,2"]
|===
| No forward path | Why

| ViewState-dependent logic | Any code relying on ViewState to implicitly persist state across postbacks has
  to be redesigned around explicit state (component fields in Blazor, `TempData`/session in MVC).
| `HttpModule`/`HttpHandler` | Rewritten as ASP.NET Core middleware/endpoints -- the extension points exist but
  the API surface is unrelated (see
  xref:web/aspnet/core/request-pipeline-and-middleware.adoc[Request Pipeline and Middleware]).
| Web Parts | No successor in any current framework; personalization/composable-zone UI has to be
  purpose-built from Razor components or a third-party dashboard library.
| ASMX web services | Replaced by ASP.NET Core Web API controllers/Minimal APIs or gRPC -- SOAP itself has no
  first-class story in ASP.NET Core.
| Membership/Role/Profile password hashes | The legacy hashing of `SqlMembershipProvider` (and, in older
  applications, unsalted or weakly salted schemes) does not map onto ASP.NET Core Identity's password hasher --
  migrating users typically means either a one-time re-hash-on-next-login shim or a forced password reset.
|===

== Realistic effort framing

Treat a Web Forms -> modern ASP.NET migration as a genuine rewrite of the presentation layer, not a
recompilation: the business/data-access layers, *if* they were kept reasonably separate from `Page` code-behind
(see xref:web/aspnet/web-forms/architecture-and-testing.adoc[Architecture and Testing] and its
Model-View-Presenter discussion), are the part most likely to be reusable close to as-is; every `.aspx` page
and its server controls are not. Sizing a migration by page count alone under-estimates it if a meaningful
fraction of those pages hide business logic in code-behind rather than a presenter/service layer -- that logic
has to be found and extracted before it can be reused in the new UI, and that discovery work is frequently the
larger, less predictable part of the effort compared to writing the new markup itself.

== A phased plan for the order-entry application

A migration is easier to manage as a fixed sequence of phases than as a single "rewrite". The sequence below is the one
the rest of this page assumes; each phase leaves the application shippable.

[mermaid]
....
flowchart TD
    A["1. Inventory\nlist pages, controls, modules, handlers,\nwhat each page does and who uses it"] --> B["2. Create seams\nextract logic from code-behind into\nservices and presenters (no System.Web)"]
    B --> C["3. Share the code\nmove services into a class library\nmulti-targeted net48 and net8.0"]
    C --> D["4. Put the proxy in front\nYARP forwards everything\nto Web Forms, no behavior change"]
    D --> E["5. Migrate one slice\nre-implement a set of pages in ASP.NET Core,\nmove its route to the new app"]
    E --> F{"Pages left in\nWeb Forms?"}
    F -- yes --> E
    F -- no --> G["6. Retire Web Forms\nremove the legacy cluster and the adapters"]
....

Phases 2 and 3 are the ones that decide the cost. They are also the only ones that are useful *even if the migration
is never finished*: code that has left `Page` code-behind is testable (see
xref:web/aspnet/web-forms/architecture-and-testing.adoc[Architecture and Testing]) and reusable by the new application.
A page triage shortens phase 1:

[cols="1,2,2"]
|===
| Page category | Typical content | Migration effort

| Read-only views | A `Repeater` or `GridView` over a query, no editing | Low: a Razor page or component over the same
  service.
| Forms over data | `FormView`, validators, a save button | Medium: a form component with model validation; the
  validators become DataAnnotations.
| Stateful flows | `Wizard`, `MultiView`, session-backed carts, dynamic controls | High: the implicit state has to be
  made explicit before it can be moved.
| Page-model extensions | Web Parts, custom server controls, `UpdatePanel`-heavy pages | Highest: no equivalent;
  redesign with the page's job (not its controls) as the specification.
|===

== Worked example: routing one slice with YARP

Phase 4 puts a thin ASP.NET Core application in front of the legacy site. All it does at first is forward requests; as
slices are migrated, individual routes are pointed at the new application. This is the whole proxy application:

[source,csharp]
----
// Program.cs of the proxy project (requires the Yarp.ReverseProxy package)
var builder = WebApplication.CreateBuilder(args);

builder.Services.AddReverseProxy()
    .LoadFromConfig(builder.Configuration.GetSection("ReverseProxy"));

var app = builder.Build();
app.MapReverseProxy();
app.Run();
----

[source,json]
----
{
  "ReverseProxy": {
    "Routes": {
      "orders": {
        "ClusterId": "core",
        "Order": 1,
        "Match": { "Path": "/orders/{**catch-all}" }
      },
      "legacy": {
        "ClusterId": "legacy",
        "Order": 100,
        "Match": { "Path": "{**catch-all}" }
      }
    },
    "Clusters": {
      "core": {
        "Destinations": { "primary": { "Address": "http://localhost:5100/" } }
      },
      "legacy": {
        "Destinations": { "primary": { "Address": "http://localhost:8080/" } }
      }
    }
  }
}
----

The routes are matched in `Order` (lowest first), so `+/orders/...+` goes to the new application and everything else
falls through to the catch-all that points at the Web Forms site. Migrating the next slice is a configuration change
(a new route above the catch-all), and rolling it back is the same change reversed, which is what makes the strangler
approach low-risk. Two practical details: the proxy must preserve the `Host` header and forwarded headers if the legacy
site generates absolute URLs, and the Forms authentication cookie must be readable by both applications (same
`machineKey` and cookie name on the legacy side, and the `System.Web.Adapters` authentication support on the new
side), or users are asked to log in again at every boundary. Session works the same way: every session key shared
across the boundary has to be declared with a type on both sides, which in practice means moving shared values to
simple serializable types such as `int` or `string` first.

== Worked example: the same page, in Blazor Server

The order-entry page from xref:web/aspnet/web-forms/getting-started.adoc[Getting Started] -- a product list, a quantity
with validation, a button, a result label -- is about thirty lines in Blazor Server, and the mapping from each Web Forms
piece to its replacement is direct. The business code does not change at all: `ProductCatalog` comes from the shared
class library of phase 3.

[source,razor]
----
@* Pages/Orders/NewOrder.razor *@
@page "/orders/new"
@using System.ComponentModel.DataAnnotations
@using WebFormsApp.Services

<PageTitle>New order</PageTitle>

<EditForm Model="line" OnValidSubmit="Add">
    <DataAnnotationsValidator />
    <ValidationSummary />

    <InputSelect @bind-Value="line.ProductId">
        @foreach (var product in products)
        {
            <option value="@product.Id">@product.Name</option>
        }
    </InputSelect>
    <InputNumber @bind-Value="line.Quantity" />
    <button type="submit">Add to order</button>
</EditForm>

<p>@total</p>

@code {
    private readonly OrderLine line = new();
    private IReadOnlyList<Product> products = Array.Empty<Product>();
    private string total = "";

    protected override void OnInitialized()
    {
        products = ProductCatalog.All();
        line.ProductId = products[0].Id;
    }

    private void Add()
    {
        var product = ProductCatalog.Find(line.ProductId)!;
        total = $"{line.Quantity} x {product.Name} = {line.Quantity * product.Price:C}";
    }

    public class OrderLine
    {
        public int ProductId { get; set; }

        [Range(1, 100, ErrorMessage = "Enter a quantity between 1 and 100.")]
        public int Quantity { get; set; } = 1;
    }
}
----

[cols="1,1"]
|===
| Web Forms version | Blazor Server version

| `ProductList.DataSource` and `DataBind()` in `Page_Load` under `!IsPostBack` | `OnInitialized`, which runs once per
  component instance (there is no postback to guard against)
| `RequiredFieldValidator` and `RangeValidator` | `[Range]` on the model plus `DataAnnotationsValidator`
| `AddButton_Click` with an `IsValid` check | `OnValidSubmit`, which only fires when validation passed
| `+TotalLabel.Text = ...+` | A field that the markup renders; Blazor re-renders when the handler returns
| ViewState carrying the list items | Nothing: `products` is an ordinary field kept in the circuit
|===

The two versions can run side by side during the migration: the legacy `/Orders/NewOrder.aspx` keeps working, the new
`/orders/new` is reachable through the proxy route above, and users can be switched over by changing links or by a
redirect rule once the new page has been validated.

== Handling the parts with no equivalent

Three Web Forms habits need a decision rather than a translation. *Postback-driven state*: pages that rely on
`IsPostBack` branches to remember a mode (view versus edit, which step is open) become explicit component fields or
route parameters. *Code that talks to `HttpContext.Current`*: wrapping it behind the abstractions shown in
xref:web/aspnet/web-forms/architecture-and-testing.adoc[Architecture and Testing] (`ILastOrderStore` and similar) turns
a rewrite into swapping one implementation. *Custom server controls*: re-derive the requirement from what the control
does for the user, and build a Razor component against that, instead of porting `Render` and `ViewState` code line
by line; a control such as the `QuantityStepper` in
xref:web/aspnet/web-forms/user-and-custom-controls.adoc[User and Custom Controls] is a twenty-line component with
a `[Parameter]` for the value and an `EventCallback` for the change.

See https://learn.microsoft.com/en-us/aspnet/core/migration/inc/overview[Incremental ASP.NET to ASP.NET Core migration]
and https://microsoft.github.io/reverse-proxy/[the YARP documentation] for the configuration reference of the proxy
shown above.
