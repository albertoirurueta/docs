= Model Binding and Modern Web Forms
:description: The Web Forms 4.5+ story -- ItemType and strongly typed data controls, model binding with SelectMethod/UpdateMethod/InsertMethod/DeleteMethod, value providers, DataAnnotations validation, friendly URLs, bundling/minification, and async page methods.
:keywords: ASP.NET Web Forms, ItemType, SelectMethod, model binding, QueryStringAttribute, DataAnnotations, friendly URLs, System.Web.Optimization, RegisterAsyncTask, PageAsyncTask

include::partial$ai-disclaimer.adoc[]

ASP.NET 4.5 (2012) added a set of features that brought Web Forms conceptually closer to MVC without changing
its underlying page/control model -- strongly typed, method-based model binding in place of
`SqlDataSource`/`ObjectDataSource` markup, DataAnnotations validation, cleaner URLs, and async page
processing. These are the last substantial additions Web Forms received.

== `ItemType` and strongly typed data controls

Setting `ItemType` on a data-bound control gives its templates a strongly typed `Item` instead of an untyped
`Eval("Name")` lookup, with full IntelliSense and compile-time checking:

[source,aspx]
----
<asp:ListView ID="ProductsList" runat="server" ItemType="WebFormsApp.Models.Product"
    SelectMethod="GetProducts">
    <ItemTemplate>
        <%-- Item is a Product, not object -- Item.Name is checked at compile time --%>
        <li><%#: Item.Name %> -- <%#: Item.Price.ToString("C") %></li>
    </ItemTemplate>
</asp:ListView>
----

`<%#: %>` combines strongly typed binding with automatic HTML encoding, the data-binding analogue of `<%: %>`.

== Model binding: `SelectMethod`/`UpdateMethod`/`InsertMethod`/`DeleteMethod`

Instead of a `SqlDataSource`/`ObjectDataSource` control, a data-bound control can point directly at plain
methods on the page (or a referenced class), each following simple parameter-binding conventions:

[source,aspx]
----
<asp:GridView ID="ProductsGrid" runat="server" ItemType="WebFormsApp.Models.Product"
    SelectMethod="GetProducts" UpdateMethod="UpdateProduct" DeleteMethod="DeleteProduct"
    DataKeyNames="Id" AllowPaging="true" PageSize="20">
    <Columns>
        <asp:BoundField DataField="Name" HeaderText="Name" />
        <asp:BoundField DataField="Price" HeaderText="Price" />
        <asp:CommandField ShowEditButton="true" ShowDeleteButton="true" />
    </Columns>
</asp:GridView>
----

[source,csharp]
----
public partial class Products : System.Web.UI.Page
{
    private readonly ProductRepository _repository = new ProductRepository();

    public IQueryable<Product> GetProducts()
    {
        return _repository.All(); // paging/sorting are applied by the framework against the IQueryable
    }

    public void UpdateProduct(int id, Product product)
    {
        _repository.Update(id, product);
    }

    public void DeleteProduct(int id) => _repository.Delete(id);
}
----

This is a direct, no-markup-configuration substitute for the method-name conventions of `ObjectDataSource` -- the
method itself *is* the data source, resolved and invoked by the model-binding infrastructure per request.

== Value providers

Method parameters are populated from named sources using attributes, mirroring MVC's model-binding attributes
of the same era:

[cols="1,2"]
|===
| Attribute | Binds from

| `[QueryString]` | `Request.QueryString`
| `[Control]` | Another control's value on the page (e.g. a filter `DropDownList`)
| `[Cookie]` | `Request.Cookies`
| `[Form]` | `Request.Form`
| `[Session]` | `Session`
| `[Profile]` | The current user's `Profile` properties
| `[RouteData]` | Values from a matched route (see "Friendly URLs" below)
|===

[source,csharp]
----
public IQueryable<Product> GetProducts([QueryString("cat")] int? categoryId,
    [Control("MinPriceBox")] decimal? minPrice)
{
    var query = _repository.All();
    if (categoryId.HasValue) query = query.Where(p => p.CategoryId == categoryId);
    if (minPrice.HasValue) query = query.Where(p => p.Price >= minPrice);
    return query;
}
----

== DataAnnotations validation on Web Forms

Model classes decorated with `System.ComponentModel.DataAnnotations` attributes are validated automatically
when bound through `UpdateMethod`/`InsertMethod`, surfaced via `Page.ModelState` (Web Forms' equivalent of
MVC's `ModelState`) alongside, not instead of, the
xref:web/aspnet/web-forms/validation-controls.adoc[validator controls]:

[source,csharp]
----
public class Product
{
    [Required, StringLength(100)]
    public string Name { get; set; }

    [Range(0, 100000)]
    public decimal Price { get; set; }
}
----

[source,csharp]
----
public void UpdateProduct(int id, Product product)
{
    if (!ModelState.IsValid) { return; } // DataAnnotations failures land here
    _repository.Update(id, product);
}
----

== Friendly URLs

The `Microsoft.AspNet.FriendlyUrls` NuGet package (installed by default in the ASP.NET 4.5 Web Forms project
template) layers extension-less, parameterized URLs on top of `System.Web.Routing` with almost no manual route
registration:

[source,csharp]
----
// RouteConfig.cs
public static class RouteConfig
{
    public static void RegisterRoutes(RouteCollection routes)
    {
        var settings = new FriendlyUrlSettings { AutoRedirectMode = RedirectMode.Permanent };
        routes.EnableFriendlyUrls(settings);
    }
}
----

`/Products.aspx` becomes reachable as `/Products`; segment-style parameters (`/Products/5`) map onto
`PageRouteData` on the target page, read the same way as the `RouteTable.Routes.MapPageRoute` approach in
xref:web/aspnet/web-forms/master-pages-themes-and-localization.adoc[Master Pages, Themes, and Localization],
but without hand-writing each route.

== Bundling and minification

`System.Web.Optimization` (the `Microsoft.AspNet.Web.Optimization` NuGet package) combines and minifies
script/CSS files into a small number of cacheable requests:

[source,csharp]
----
// BundleConfig.cs
public static class BundleConfig
{
    public static void RegisterBundles(BundleCollection bundles)
    {
        bundles.Add(new ScriptBundle("~/bundles/jquery").Include("~/Scripts/jquery-{version}.js"));
        bundles.Add(new StyleBundle("~/Content/css").Include("~/Content/site.css"));
    }
}
----

[source,aspx]
----
<%: Scripts.Render("~/bundles/jquery") %>
<%: Styles.Render("~/Content/css") %>
----

This is the same bundling infrastructure ASP.NET MVC 5 uses, since `System.Web.Optimization` is a
`System.Web`-level library shared by both.

== Async page methods

`RegisterAsyncTask` lets a page await I/O-bound work without blocking a thread-pool thread for the whole
request, provided the page opts in with `Async="true"`:

[source,aspx]
----
<%@ Page Async="true" Language="C#" CodeBehind="ProductReport.aspx.cs" Inherits="WebFormsApp.ProductReport" %>
----

[source,csharp]
----
protected void Page_Load(object sender, EventArgs e)
{
    RegisterAsyncTask(new PageAsyncTask(LoadReportAsync));
}

private async Task LoadReportAsync()
{
    ReportData = await _reportService.GenerateAsync(); // runs during the page's async point, before PreRender
}
----

`PageAsyncTask` also accepts the older Begin/End APM delegate pair for legacy async patterns; the `Task`-based
overload above is the practical choice for any code written against modern `async`/`await`. See
https://learn.microsoft.com/en-us/previous-versions/aspnet/hh975440(v=vs.118)[ASP.NET 4.5 Model Binding for
Web Forms] and https://learn.microsoft.com/en-us/previous-versions/aspnet/hh975440(v=vs.118)#async-support[Async
support for Web Forms].

== How model binding resolves a method call

The select, update, insert, and delete methods are looked up and called by the framework, not by the page. The
control hands its data-source operation to a *model data source* that finds the named method, builds each argument
from the declared value provider (or from the control's own values for update and insert), calls the method, and
then post-processes the result:

[mermaid]
....
sequenceDiagram
    participant G as GridView
    participant M as Model data source
    participant V as Value providers
    participant P as Page method GetProducts
    G->>M: Select (sort expression, paging window)
    M->>V: resolve each parameter (QueryString, Control, Cookie, RouteData)
    V-->>M: converted values (null for missing nullable ones)
    M->>P: invoke with the resolved arguments
    P-->>M: IQueryable of Product
    M->>M: apply sorting and paging to the IQueryable
    M-->>G: rows for the current page
    G->>G: RowCreated and RowDataBound per row
....

Because the framework composes sorting and paging onto the returned `IQueryable`, the method should return the
query *unexecuted* (no `ToList()`): with Entity Framework the paging then turns into SQL `OFFSET`/`FETCH`, whereas
a materialized list makes every request load the whole table. A method that cannot return a query takes over
paging itself by declaring the `maximumRows`, `startRowIndex`, `sortByExpression`, and `out int totalRowCount`
parameters, as in the example below.

== Worked example: a filterable, editable product page with validation

The model type carries its own validation rules, so they apply on every page that edits a `Product`, and the page
contains no validator markup at all for them:

[source,csharp]
----
// Models/Product.cs
using System.ComponentModel.DataAnnotations;

namespace WebFormsApp.Models
{
    public class Product
    {
        public int Id { get; set; }

        [Required(ErrorMessage = "Name is required.")]
        [StringLength(100, ErrorMessage = "Name must be 100 characters or fewer.")]
        public string Name { get; set; }

        [Range(0.01, 100000, ErrorMessage = "Price must be between 0.01 and 100000.")]
        public decimal Price { get; set; }

        public int CategoryId { get; set; }
    }
}
----

[source,csharp]
----
// Models/ProductRepository.cs -- in-memory stand-in for a database-backed repository
using System.Collections.Generic;
using System.Linq;

namespace WebFormsApp.Models
{
    public class ProductRepository
    {
        private static readonly List<Product> Store = new List<Product>
        {
            new Product { Id = 1, Name = "Keyboard", Price = 49.90m, CategoryId = 1 },
            new Product { Id = 2, Name = "Monitor", Price = 219.00m, CategoryId = 2 },
            new Product { Id = 3, Name = "Webcam", Price = 79.50m, CategoryId = 2 },
        };

        public IQueryable<Product> All() { return Store.AsQueryable(); }

        public Product Find(int id) { return Store.FirstOrDefault(p => p.Id == id); }

        public void Delete(int id) { Store.RemoveAll(p => p.Id == id); }
    }
}
----

[source,aspx]
----
<%-- Products.aspx --%>
<asp:ValidationSummary ID="Summary" runat="server" ShowModelStateErrors="true"
    HeaderText="Please fix the following:" />

<asp:DropDownList ID="CategoryFilter" runat="server" AutoPostBack="true">
    <asp:ListItem Text="All categories" Value="" />
    <asp:ListItem Text="Input devices" Value="1" />
    <asp:ListItem Text="Video" Value="2" />
</asp:DropDownList>

<asp:GridView ID="ProductsGrid" runat="server" ItemType="WebFormsApp.Models.Product"
    SelectMethod="GetProducts" UpdateMethod="UpdateProduct" DeleteMethod="DeleteProduct"
    DataKeyNames="Id" AutoGenerateColumns="false" AllowPaging="true" PageSize="10" AllowSorting="true">
    <Columns>
        <asp:BoundField DataField="Name" HeaderText="Name" SortExpression="Name" />
        <asp:BoundField DataField="Price" HeaderText="Price" SortExpression="Price" />
        <asp:CommandField ShowEditButton="true" ShowDeleteButton="true" />
    </Columns>
</asp:GridView>
----

[source,csharp]
----
// Products.aspx.cs
using System;
using System.Linq;
using System.Web.ModelBinding;
using System.Web.UI;
using WebFormsApp.Models;

namespace WebFormsApp
{
    public partial class Products : Page
    {
        private readonly ProductRepository _repository = new ProductRepository();

        public IQueryable<Product> GetProducts([Control("CategoryFilter")] int? categoryId)
        {
            IQueryable<Product> query = _repository.All();
            if (categoryId.HasValue)
            {
                query = query.Where(p => p.CategoryId == categoryId.Value);
            }

            return query; // sorting and paging are added by the framework
        }

        public void UpdateProduct(int id)
        {
            Product item = _repository.Find(id);
            if (item == null)
            {
                ModelState.AddModelError("", "Product " + id + " was not found.");
                return;
            }

            TryUpdateModel(item); // copies the edited cells onto the item and runs the DataAnnotations rules
            if (!ModelState.IsValid)
            {
                return; // the ValidationSummary shows the messages; the row stays in edit mode
            }

            // item is a live object from the store, so the change is already applied here;
            // with a database-backed repository this is where the unit of work is saved.
        }

        public void DeleteProduct(int id)
        {
            _repository.Delete(id);
        }
    }
}
----

Reading the page from the top: the `[Control("CategoryFilter")]` attribute supplies `categoryId` from the drop-down,
and an empty `ListItem` value converts to `null`, so "All categories" needs no special case. The `GridView` rebinds
whenever the filter posts back because a model-bound control re-runs its select method on every request that needs
data. `UpdateProduct(int id)` loads the *existing* entity and uses `TryUpdateModel` to apply only the submitted
fields, which preserves properties that were never on the form (`CategoryId`); declaring `Product product` as a
parameter instead would give a new, partially filled object and is the classic cause of "my update blanked a
column". The DataAnnotations errors flow into `ModelState`, and `ShowModelStateErrors` on the summary displays them
with no validator controls.

== Friendly URLs: reading segments with model binding

With `EnableFriendlyUrls` in place, a page named `ProductDetails.aspx` answers `/ProductDetails/3`, and the
trailing segment can be bound straight into the select method, together with a link helper that builds such URLs:

[source,aspx]
----
<asp:FormView ID="DetailsView" runat="server" ItemType="WebFormsApp.Models.Product"
    SelectMethod="GetProduct">
    <ItemTemplate>
        <h2><%#: Item.Name %></h2>
        <p><%#: Item.Price.ToString("C") %></p>
    </ItemTemplate>
    <EmptyDataTemplate><p>No such product.</p></EmptyDataTemplate>
</asp:FormView>

<a href="<%: FriendlyUrl.Href("~/ProductDetails", 3) %>">Open product 3</a>
----

[source,csharp]
----
using Microsoft.AspNet.FriendlyUrls.ModelBinding;

public WebFormsApp.Models.Product GetProduct([FriendlyUrlSegments(0)] int? id)
{
    return id.HasValue ? new ProductRepository().Find(id.Value) : null;
}
----

The `FriendlyUrl` helper lives in the `Microsoft.AspNet.FriendlyUrls` namespace, which the project template registers
under `<system.web><pages><namespaces>` so markup can use it without an `@Import`. `FriendlyUrlSegments(0)` binds the
first path segment after the page name; the ordinary `[QueryString]` and
`[RouteData]` providers keep working next to it. With `AutoRedirectMode = RedirectMode.Permanent`, requests for
the old `/ProductDetails.aspx?id=3` style are redirected with a 301, which preserves search-engine rankings when
turning on friendly URLs for an existing site. The package also adds a *mobile view* convention: a
`Site.Mobile.Master` or `ProductDetails.Mobile.aspx` is picked automatically for mobile browsers, and
`ViewSwitcher` lets users override the choice.

== Async pages in practice

Async pages exist for one reason: to give the request thread back to the thread pool while the page waits on I/O. The
request keeps its page life cycle; only the thread underneath it changes.

[mermaid]
....
sequenceDiagram
    participant IIS as ASP.NET worker pool
    participant T1 as Thread A
    participant X as Remote service
    participant T2 as Thread B
    IIS->>T1: start request, Init, Load
    T1->>T1: RegisterAsyncTask in Page_Load
    T1->>X: HttpClient.GetStringAsync (task started after PreRender)
    T1-->>IIS: thread released while waiting
    X-->>T2: response arrives
    T2->>T2: task completes, PreRenderComplete and Render run
    T2-->>IIS: response sent
....

A complete page using the task-based overload and `HttpClient`:

[source,aspx]
----
<%@ Page Async="true" AsyncTimeout="10" Language="C#"
    CodeBehind="RatesReport.aspx.cs" Inherits="WebFormsApp.RatesReport" %>
<asp:Literal ID="RatesLiteral" runat="server" />
<asp:Label ID="StatusLabel" runat="server" />
----

[source,csharp]
----
// RatesReport.aspx.cs
using System;
using System.Net.Http;
using System.Threading.Tasks;
using System.Web.UI;

namespace WebFormsApp
{
    public partial class RatesReport : Page
    {
        // One shared instance: creating an HttpClient per request exhausts sockets under load.
        private static readonly HttpClient Client = new HttpClient { Timeout = TimeSpan.FromSeconds(5) };

        protected void Page_Load(object sender, EventArgs e)
        {
            RegisterAsyncTask(new PageAsyncTask(LoadRatesAsync));
        }

        private async Task LoadRatesAsync()
        {
            try
            {
                string json = await Client.GetStringAsync("https://example.org/api/rates");
                RatesLiteral.Text = Server.HtmlEncode(json);
            }
            catch (HttpRequestException ex)
            {
                StatusLabel.Text = "Rates are unavailable: " + ex.Message;
            }
        }
    }
}
----

Notes that decide whether this works. The page must opt in with `Async="true"`, and the application must target 4.5
or later (`<httpRuntime targetFramework="4.5" />` or higher, see
xref:web/aspnet/web-forms/getting-started.adoc[Getting Started]), because only then does ASP.NET install the
synchronization context that lets an `await` resume on the request's context with `HttpContext.Current` intact;
without it, `async` handlers fail with "An asynchronous operation cannot be started at this time". Registered
tasks start after `PreRender` and are awaited before `PreRenderComplete`, so controls set inside them still render.
`AsyncTimeout` (default 45 seconds) bounds how long the page waits for registered tasks. Finally, async helps only
when the awaited work is genuinely I/O: wrapping CPU-bound work in `Task.Run` simply moves it to another pool thread
and gains nothing.

See https://learn.microsoft.com/en-us/aspnet/web-forms/overview/presenting-and-managing-data/model-binding/[Model
Binding and Web Forms] and https://learn.microsoft.com/en-us/aspnet/web-forms/overview/performance-and-caching/using-asynchronous-methods-in-aspnet-45[Using
Asynchronous Methods in ASP.NET 4.5].
