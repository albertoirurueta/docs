= HTTP Pipeline, Handlers, and Configuration
:description: HttpApplication and global.asax events, HttpContext/HttpRequest/HttpResponse/Server, writing IHttpHandler/IHttpHandlerFactory and .ashx, writing IHttpModule, IIS classic vs. integrated pipeline, the web.config hierarchy, config transforms and encryption, and compilation/precompilation.
:keywords: ASP.NET Web Forms, HttpApplication, global.asax, IHttpHandler, ashx, IHttpModule, IIS integrated pipeline, web.config, machine.config, aspnet_regiis, aspnet_compiler

include::partial$ai-disclaimer.adoc[]

Every ASP.NET Web Forms request, before it ever reaches a `Page`, passes through the same
`HttpApplication`-driven pipeline that also serves `.ashx` handlers and any custom module -- the same pipeline
xref:web/aspnet/web-forms/page-lifecycle-and-postback.adoc[the page life cycle] sits inside as one particular
kind of handler.

== `HttpApplication` and `global.asax`

`global.asax` (compiled into a class deriving from `HttpApplication`) is where application- and request-wide
events are handled, by naming convention exactly like `AutoEventWireup` on a page:

[source,csharp]
----
// Global.asax.cs
public class Global : System.Web.HttpApplication
{
    protected void Application_Start(object sender, EventArgs e)
    {
        RouteConfig.RegisterRoutes(RouteTable.Routes);
        BundleConfig.RegisterBundles(BundleTable.Bundles);
    }

    protected void Application_BeginRequest(object sender, EventArgs e) { /* runs for every request, incl. .ashx/.axd */ }

    protected void Application_AuthenticateRequest(object sender, EventArgs e) { /* after auth module runs */ }

    protected void Application_Error(object sender, EventArgs e)
    {
        Exception ex = Server.GetLastError();
        Server.ClearError(); // suppress the default yellow-screen-of-death if handled here
        LogError(ex);
    }

    protected void Application_End(object sender, EventArgs e) { /* app domain shutting down */ }
}
----

`Application_Start`/`Application_End` fire once per application-domain lifetime (recycles count as a new
lifetime); the `+*Request+` events fire on every request, in the fixed order documented at
https://learn.microsoft.com/en-us/previous-versions/aspnet/bb470252(v=vs.100)[ASP.NET Application Life Cycle
Overview for IIS].

== `HttpContext`, `HttpRequest`, `HttpResponse`, `Server`

`HttpContext.Current` (or `Page.Context` inside a page) is the ambient, per-request object graph:

[source,csharp]
----
HttpRequest request = HttpContext.Current.Request;
string userAgent = request.UserAgent;
string queryValue = request.QueryString["id"];

HttpResponse response = HttpContext.Current.Response;
response.ContentType = "application/json";
response.Write("{\"ok\":true}");

HttpServerUtility server = HttpContext.Current.Server;
string safe = server.HtmlEncode(userInput);
server.Transfer("~/Error.aspx"); // server-side redirect, no round trip; Response.Redirect is client-side
----

`HttpContext.Current` is thread-static-like ambient state tied to the request thread, which is exactly why it
does not survive naively across `async`/`await` continuations scheduled on a different thread in older code --
a common source of null-reference surprises when retrofitting `async` onto legacy handlers.

== Writing `IHttpHandler`/`IHttpHandlerFactory` and `.ashx`

A `.ashx` **generic handler** is the lightest way to answer an HTTP request with no page life cycle at all --
appropriate for a raw image, JSON, or file-download endpoint:

[source,csharp]
----
// Thumbnail.ashx.cs
public class Thumbnail : IHttpHandler
{
    public bool IsReusable => true;

    public void ProcessRequest(HttpContext context)
    {
        int id = int.Parse(context.Request.QueryString["id"]);
        byte[] bytes = _imageService.GetThumbnail(id);
        context.Response.ContentType = "image/jpeg";
        context.Response.BinaryWrite(bytes);
    }
}
----

[source]
----
<%-- Thumbnail.ashx --%>
<%@ WebHandler Language="C#" CodeBehind="Thumbnail.ashx.cs" Class="WebFormsApp.Thumbnail" %>
----

An `IHttpHandlerFactory` sits one level above -- it decides *which* handler instance to hand back for a given
request, useful for routing a whole extension (or a custom-registered path) to different handler types based
on request content:

[source,csharp]
----
public class ReportHandlerFactory : IHttpHandlerFactory
{
    public IHttpHandler GetHandler(HttpContext context, string requestType, string url, string pathTranslated)
        => context.Request.QueryString["format"] == "csv" ? new CsvReportHandler() : new PdfReportHandler();

    public void ReleaseHandler(IHttpHandler handler) { }
}
----

Both are registered in `web.config` under `<httpHandlers>` (IIS 6/classic pipeline) or `<handlers>` (IIS 7+
integrated pipeline, see below).

== Writing `IHttpModule`

A module runs on **every** request through the pipeline, regardless of handler, by subscribing to
`HttpApplication` events -- the mechanism `FormsAuthenticationModule`, `SessionStateModule`, and similar
built-in features are themselves implemented with:

[source,csharp]
----
public class RequestTimingModule : IHttpModule
{
    public void Init(HttpApplication app)
    {
        app.BeginRequest += (s, e) => ((HttpApplication)s).Context.Items["StartedAt"] = DateTime.UtcNow;
        app.EndRequest += (s, e) =>
        {
            var started = (DateTime)((HttpApplication)s).Context.Items["StartedAt"];
            Trace.WriteLine("Request took " + (DateTime.UtcNow - started).TotalMilliseconds + "ms");
        };
    }

    public void Dispose() { }
}
----

[source,xml]
----
<system.webServer>
  <modules>
    <add name="RequestTimingModule" type="WebFormsApp.RequestTimingModule" />
  </modules>
</system.webServer>
----

== IIS classic vs. integrated pipeline

[mermaid]
....
flowchart LR
    subgraph Classic["IIS 6 classic mode"]
        direction TB
        C1[IIS native pipeline\nhandles static files, auth, logging] --> C2{Extension mapped\nto aspnet_isapi.dll?}
        C2 -->|.aspx/.ashx/.asmx| C3[ASP.NET pipeline\nmodules + handler run]
        C2 -->|.html/.css/.jpg| C4[Served by IIS directly\nASP.NET modules never run]
    end
    subgraph Integrated["IIS 7+ integrated mode"]
        direction TB
        I1[Unified IIS + ASP.NET pipeline] --> I2[ASP.NET modules can\nrun for EVERY request,\nany extension]
        I2 --> I3[Handler selected by\nconfigured mapping]
    end
....

Classic mode only ran the ASP.NET pipeline (and therefore custom `IHttpModule` classes) for requests IIS had mapped to
the ASP.NET ISAPI extension -- typically `.aspx`/`.ashx`/`.asmx` only, so a module could not, for example,
inspect a static `.html` request. Integrated mode (the default and effectively the only mode still used since
IIS 7) merges the two pipelines so ASP.NET modules participate in every request IIS handles, static files
included, which is what enables things like Forms-authentication-protecting static content. See
https://learn.microsoft.com/en-us/previous-versions/iis/6.0-sdk/ms525145(v=vs.90)[IIS 6.0 vs. IIS 7 Integrated
Pipeline] (previous-versions archive) and
https://learn.microsoft.com/en-us/previous-versions/aspnet/bb470252(v=vs.100)[ASP.NET Application Life Cycle
Overview for IIS].

== `web.config` hierarchy and `machine.config`

Configuration is hierarchical and inherited: `machine.config` (one per .NET Framework install) is the
outermost layer, then the site-root `web.config`, then a `web.config` in each subfolder, each layer able to
add to or override the one above it -- exactly like nested CSS cascade:

[source,xml]
----
<!-- web.config at the application root -->
<configuration>
  <system.web>
    <authorization>
      <deny users="?" /> <!-- deny anonymous site-wide by default -->
    </authorization>
  </system.web>
  <location path="Public">
    <system.web>
      <authorization>
        <allow users="*" /> <!-- override: this one subfolder is public -->
      </authorization>
    </system.web>
  </location>
</configuration>
----

`<location>` (used inline above, or as a `path=` targeting a specific file/folder from the root `web.config`)
applies settings to a specific path without needing a physical nested `web.config` file -- the two approaches
are equivalent; `<location>` is preferred when the settings for many paths need to live in one reviewable
place.

=== `web.config` transforms

Web Application Projects support per-configuration transform files (`Web.Release.config`,
`Web.Debug.config`) applied during publish via XDT (XML Document Transform) syntax:

[source,xml]
----
<!-- Web.Release.config -->
<configuration xmlns:xdt="http://schemas.microsoft.com/XML-Document-Transform">
  <system.web>
    <compilation xdt:Transform="RemoveAttributes(debug)" />
    <customErrors xdt:Transform="Replace" mode="On" />
  </system.web>
</configuration>
----

=== Encrypting configuration sections

Connection strings and other secrets in `web.config` can be encrypted at rest on a given machine using
`aspnet_regiis`:

[source,batch]
----
%windir%\Microsoft.NET\Framework64\v4.0.30319\aspnet_regiis.exe -pe "connectionStrings" -app "/MyApp"
----

`-pe` ("protect element") encrypts the named section in place; ASP.NET decrypts it transparently at runtime
using the configured provider (`RSA` machine key container by default, so the encrypted file is only readable
on the machine/key container that encrypted it -- relevant when planning to sync `web.config` across a farm).

== Compilation models and precompilation

By default, Web Forms compiles each page/control on first request (or eagerly if pre-JIT-warmed) into
per-page assemblies under the ASP.NET temporary files folder. `aspnet_compiler` precompiles the whole site
ahead of deployment:

[source,batch]
----
aspnet_compiler.exe -v /MyApp -p C:\src\MyApp C:\out\MyApp -u
----

`-u` produces an **updatable** precompiled site (markup files are still deployed and can be tweaked without a
full recompile; code-behind is precompiled); omitting it produces a fully precompiled, non-updatable site
where even markup changes require recompilation. See
xref:web/aspnet/web-forms/deployment-and-diagnostics.adoc[Deployment and Diagnostics] for the deployment-time
trade-offs between the two, and
https://learn.microsoft.com/en-us/previous-versions/aspnet/ms228048(v=vs.100)[ASP.NET Compilation Overview].

== The request pipeline event by event

In integrated mode every request travels through the same ordered series of `HttpApplication` events, and each
`IHttpModule` and each `+Application_*+` method in `global.asax` is simply a subscriber to one of them. Knowing the order
is what lets a module be placed at the right point (before authentication to read a header, after authorization to log
the identity, at the end to measure time):

[mermaid]
....
flowchart TD
    A[BeginRequest] --> B[AuthenticateRequest]
    B --> C[PostAuthenticateRequest]
    C --> D[AuthorizeRequest]
    D --> E[ResolveRequestCache]
    E -->|output cache hit| X[skip to UpdateRequestCache]
    E -->|miss| F[MapRequestHandler]
    F --> G[AcquireRequestState]
    G --> H[PreRequestHandlerExecute]
    H --> I["Handler runs: Page life cycle, .ashx, .asmx"]
    I --> J[PostRequestHandlerExecute]
    J --> K[ReleaseRequestState]
    K --> L[UpdateRequestCache]
    X --> L
    L --> M[LogRequest]
    M --> N[EndRequest]
    N --> O[PreSendRequestHeaders]
    O --> P[PreSendRequestContent]
....

The built-in modules are placed on this line: `FormsAuthenticationModule` on `AuthenticateRequest`,
`UrlAuthorizationModule` on `AuthorizeRequest`, `OutputCacheModule` on `ResolveRequestCache` and
`UpdateRequestCache`, `SessionStateModule` on `AcquireRequestState` and `ReleaseRequestState`. Two consequences
follow. `Session` is not available in `BeginRequest` or `AuthenticateRequest` (the state is acquired later), and
`context.User` is not yet set in `BeginRequest`. And an output-cache hit short-circuits everything between
`ResolveRequestCache` and `UpdateRequestCache`, so a module that must run for every response (to add a header, say)
has to subscribe to an event that fires on both paths, such as `PreSendRequestHeaders` or `EndRequest`.

== Worked example: a module that stamps every response

A module can add behavior to the whole application without touching a single page. This one assigns a correlation
ID to each request (taking it from the incoming `X-Correlation-Id` header when a caller supplied one), makes it
available to the rest of the pipeline through `HttpContext.Items`, and adds it and two security headers to every
response, including cached ones:

[source,csharp]
----
// Infrastructure/RequestDecorationModule.cs
using System;
using System.Web;

namespace WebFormsApp.Infrastructure
{
    public class RequestDecorationModule : IHttpModule
    {
        public const string CorrelationKey = "CorrelationId";

        public void Init(HttpApplication application)
        {
            application.BeginRequest += OnBeginRequest;
            application.PreSendRequestHeaders += OnPreSendRequestHeaders;
        }

        private static void OnBeginRequest(object sender, EventArgs e)
        {
            HttpContext context = ((HttpApplication)sender).Context;
            string incoming = context.Request.Headers["X-Correlation-Id"];
            context.Items[CorrelationKey] = string.IsNullOrWhiteSpace(incoming) || incoming.Length > 64
                ? Guid.NewGuid().ToString("N")
                : incoming;
        }

        private static void OnPreSendRequestHeaders(object sender, EventArgs e)
        {
            HttpContext context = ((HttpApplication)sender).Context;
            HttpResponse response = context.Response;

            response.Headers["X-Correlation-Id"] = (string)context.Items[CorrelationKey];
            response.Headers["X-Content-Type-Options"] = "nosniff";
            response.Headers["X-Frame-Options"] = "SAMEORIGIN";
        }

        public void Dispose()
        {
        }
    }
}
----

[source,xml]
----
<system.webServer>
  <modules>
    <add name="RequestDecoration" type="WebFormsApp.Infrastructure.RequestDecorationModule" />
  </modules>
</system.webServer>
<system.web>
  <httpRuntime enableVersionHeader="false" />
</system.web>
----

Because the correlation ID lives in `Context.Items`, any later code -- `Application_Error`, a page, a handler -- can
include it in a log line, so one failed request can be traced across the layers. Modifying `Response.Headers`
requires the integrated pipeline (in classic mode it throws `PlatformNotSupportedException`), which is why the
registration is under `system.webServer` rather than `system.web/httpModules`.

== Worked example: an asynchronous JSON handler

The `.ashx` shown earlier blocks a thread for the whole request. For I/O-bound work, derive from
`HttpTaskAsyncHandler` instead, so the thread is released while awaiting, exactly as for async pages
(see xref:web/aspnet/web-forms/model-binding-and-modern-web-forms.adoc[Model Binding and Modern Web Forms]):

[source,csharp]
----
// Handlers/ProductHandler.ashx.cs
using System.Threading.Tasks;
using System.Web;
using System.Web.Script.Serialization;
using WebFormsApp.Services;

namespace WebFormsApp.Handlers
{
    public class ProductService
    {
        public Task<Product> FindAsync(int id)
        {
            return Task.FromResult(ProductCatalog.Find(id)); // stands in for an awaited database call
        }
    }

    public class ProductHandler : HttpTaskAsyncHandler
    {
        private readonly ProductService _products = new ProductService();

        public override async Task ProcessRequestAsync(HttpContext context)
        {
            int id;
            if (!int.TryParse(context.Request.QueryString["id"], out id))
            {
                context.Response.StatusCode = 400;
                return;
            }

            Product product = await _products.FindAsync(id);
            if (product == null)
            {
                context.Response.StatusCode = 404;
                return;
            }

            context.Response.ContentType = "application/json";
            context.Response.Write(new JavaScriptSerializer().Serialize(product));
        }
    }
}
----

[source,aspx]
----
<%-- Handlers/ProductHandler.ashx --%>
<%@ WebHandler Language="C#" CodeBehind="ProductHandler.ashx.cs" Class="WebFormsApp.Handlers.ProductHandler" %>
----

Notes: the handler parses the identifier as an `int`, which rejects any malformed input before it reaches a query or a
file path; it returns real status codes (`400`, `404`) so that clients, caches, and monitoring can tell failure from
success (the default for an unhandled exception is a `500` HTML error page, not JSON); and `HttpTaskAsyncHandler` returns `false`
from `IsReusable` by default, so a new instance serves each request; if you override it to return `true`, every field
(such as `_products`) must be thread-safe, which a stateless service is.

== Sending files: `Response` and the redirect family

[cols="1,3"]
|===
| Call | Behavior

| `Response.Redirect(url)` | Sends a 302 to the browser, which requests the new URL (a round trip, URL in the address
  bar changes). Ends the request with a `ThreadAbortException` unless called with `endResponse` set to `false`.
| `Response.RedirectPermanent(url)` | The same with a 301, for moved pages that search engines should re-index.
| `Server.Transfer(path)` | Restarts the page pipeline for a different page on the server, with no round trip; the
  URL does not change, and the new page can read the old form values (`preserveForm`).
| `Server.Execute(path)` | Runs another page and merges its output into the current response, then continues.
|===

Sending a file is where `Response` is easiest to misuse. `TransmitFile` streams from disk without loading the file into
managed memory, unlike `BinaryWrite(File.ReadAllBytes(path))`:

[source,csharp]
----
// Handlers/InvoiceDownload.ashx.cs
using System.IO;
using System.Web;

namespace WebFormsApp.Handlers
{
    public class InvoiceDownload : IHttpHandler
    {
        public bool IsReusable { get { return true; } }

        public void ProcessRequest(HttpContext context)
        {
            int id;
            if (!int.TryParse(context.Request.QueryString["id"], out id))
            {
                context.Response.StatusCode = 400;
                return;
            }

            // The path is built from an integer only, so "..\\" tricks cannot escape the invoices folder.
            string path = context.Server.MapPath("~/App_Data/invoices/" + id + ".pdf");
            if (!File.Exists(path))
            {
                context.Response.StatusCode = 404;
                return;
            }

            context.Response.ContentType = "application/pdf";
            context.Response.AddHeader("Content-Disposition", "attachment; filename=invoice-" + id + ".pdf");
            context.Response.TransmitFile(path);
        }
    }
}
----

Serving from `App_Data` is deliberate: that folder is blocked from direct HTTP access, so the handler is the only
way in, and it is the natural place to add an authorization check before sending. `Response.End()` and the
`endResponse` default of `Redirect` both rely on aborting the thread and should be avoided in new code; finish a handler
by returning from it.

== A custom configuration section

Application settings that have structure, defaults, and validation belong in a custom section rather than in a pile
of `appSettings` keys, because the configuration system then validates them at startup and gives typed access:

[source,csharp]
----
// Configuration/OrderDeskSection.cs
using System.Configuration;

namespace WebFormsApp.Configuration
{
    public class OrderDeskSection : ConfigurationSection
    {
        [ConfigurationProperty("maxLines", DefaultValue = 50)]
        [IntegerValidator(MinValue = 1, MaxValue = 500)]
        public int MaxLines
        {
            get { return (int)this["maxLines"]; }
            set { this["maxLines"] = value; }
        }

        [ConfigurationProperty("currency", DefaultValue = "EUR")]
        public string Currency
        {
            get { return (string)this["currency"]; }
            set { this["currency"] = value; }
        }
    }
}
----

[source,xml]
----
<configuration>
  <configSections>
    <section name="orderDesk" type="WebFormsApp.Configuration.OrderDeskSection, WebFormsApp" />
  </configSections>
  <orderDesk maxLines="100" currency="USD" />
</configuration>
----

[source,csharp]
----
var settings = (OrderDeskSection)System.Configuration.ConfigurationManager.GetSection("orderDesk");
int limit = settings.MaxLines; // 100 here; an out-of-range value fails at first access with a ConfigurationErrorsException
----

The `<location>` mechanism from earlier can also freeze sections: `<location path="." allowOverride="false">` on a
parent configuration prevents child `web.config` files from changing the enclosed settings, which hosting providers
and security-conscious teams use to keep a subfolder from re-enabling `ValidateRequest` or switching off authorization.

See the https://learn.microsoft.com/en-us/aspnet/web-forms/[ASP.NET Web Forms documentation] and the https://learn.microsoft.com/en-us/previous-versions/aspnet/[ASP.NET 4 documentation archive]
for the HTTP modules and handlers overview and the configuration reference.
