= Customization and Configuration
:description: Tailwind CSS v4's CSS-first configuration -- @import, @theme, @utility, @custom-variant, @plugin and @source; automatic class detection and safelisting; using a legacy JavaScript config via @config; the prefix option; and the --spacing() / --alpha() functions.
:keywords: Tailwind CSS-first config, @import tailwindcss, @theme, @utility, @custom-variant, @plugin, @source, @source inline, safelist, detecting classes, @config tailwind.config.js, prefix, --spacing function, --alpha function, cascade layers

include::partial$ai-disclaimer.adoc[]

In v4 there is no `tailwind.config.js` by default -- the whole framework is configured *in CSS*. You
`@import "tailwindcss"` and then use a handful of at-rules (`@theme`, `@utility`, `@custom-variant`,
`@plugin`, `@source`) in the same stylesheet. See
https://tailwindcss.com/docs/functions-and-directives[Functions and Directives] and
https://tailwindcss.com/docs/theme[Theme Variables].

== The build and scan pipeline

Tailwind never ships a giant stylesheet you trim down. It reads your source files as plain text, extracts
anything that looks like a class name, generates CSS only for the ones it recognises, and (in a production
build) minifies the result.

[mermaid]
....
flowchart LR
  A["Source files<br/>HTML / JS / JSX / Vue"] --> B["Scan for<br/>class-name tokens"]
  C["@import tailwindcss<br/>@theme / @utility / @source"] --> D["Tailwind engine"]
  B --> D
  D --> E["Generate CSS for<br/>matched utilities + variants"]
  E --> F["Minified stylesheet<br/>for the browser"]
....

== Detecting classes in source files

Detection is automatic and `.gitignore`-aware; `node_modules`, binary files, CSS files, and lock files are
skipped. The one hard rule: *a class must appear as a complete, unbroken string* -- Tailwind does not evaluate
a constructed name like `+text-$\{color}-500+`. Map props to whole class names instead. This also applies to
multi-class strings: each class in `+class="px-4 py-2 bg-sky-500"+` is detected individually and must appear
complete in the source, never as concatenated fragments.

[source,css]
----
@import "tailwindcss";

/* scan an external package that ships Tailwind classes */
@source "../node_modules/@acme/ui";

/* exclude a folder */
@source not "../src/legacy";

/* force-generate classes that never appear literally in source */
@source inline("underline");
@source inline("{hover:,focus:,}bg-sky-{500,600,700}");
----

To turn *off* automatic detection and register every path yourself (monorepos):

[source,css]
----
@import "tailwindcss" source(none);
@source "../app";
@source "../../packages/ui/src";
----

See https://tailwindcss.com/docs/detecting-classes-in-source-files[Detecting classes in source files].

== Plugins

[source,css]
----
@import "tailwindcss";
@plugin "@tailwindcss/typography";
@plugin "@tailwindcss/forms";
@plugin "./plugins/my-plugin.js";   /* a JS plugin still works */
----

== Using a legacy JavaScript config

An existing v3 config can be loaded explicitly:

[source,css]
----
@import "tailwindcss";
@config "../tailwind.config.js";
----

[source,javascript]
----
// tailwind.config.js -- still read via @config
module.exports = {
  theme: { extend: { colors: { brand: "#3f3cbb" } } },
  plugins: [require("@tailwindcss/typography")],
};
----

v4 does not support the `corePlugins`, `safelist`, or `separator` keys, and `content` is replaced by
`@source`. Prefer moving the theme into `@theme` over time.

== The prefix option

[source,css]
----
@import "tailwindcss" prefix(tw);
----

[source,html]
----
<div class="tw:flex tw:items-center tw:hover:bg-black tw:md:p-4">&#8230;</div>
----

The prefix is written once, at the very front of the class, followed by any variants: `tw:hover:bg-black`, not
`tw:hover:tw:bg-black` (that form generates nothing). The theme variables are emitted with the prefix as well -- for
example `--tw-spacing` instead of `--spacing` -- so hand-written CSS that reads a theme variable must use the prefixed
name.

== Functions in custom CSS

[source,css]
----
.card {
  padding: --spacing(6);                              /* calc(var(--spacing) * 6) */
  background: --alpha(var(--color-slate-900) / 10%);  /* color-mix(&#8230; 10%, transparent) */
}

@media (width >= theme(--breakpoint-xl)) { /* &#8230; */ }
----

The old `theme(spacing.6)` dot-notation still works but is deprecated -- reference the CSS variable
(`var(--color-slate-900)`) or, for media queries, `theme(--breakpoint-xl)`.

== Deep dive: configuring the Acme project

A small project needs very little configuration, and it helps to know *where each decision lives*. The Acme page
from xref:web/tailwind/worked-example.adoc[Building a Page with Utilities] ends up with one stylesheet that answers
five questions, each with its own at-rule:

[mermaid]
....
flowchart TD
    Q1["What does my design look like?"] --> A1["@theme: tokens that also make utilities"]
    Q2["Which files contain classes?"] --> A2["@source: add, exclude or force classes"]
    Q3["Which behaviour is missing?"] --> A3["@utility, @custom-variant or @plugin"]
    Q4["How should plain elements look?"] --> A4["@layer base"]
    Q5["Which values must be reusable CSS?"] --> A5["@layer components or a framework component"]
    A1 --> S["app.css"]
    A2 --> S
    A3 --> S
    A4 --> S
    A5 --> S
....

[source,css]
----
@import "tailwindcss";

/* what the design looks like */
@theme {
  --color-brand: oklch(0.55 0.2 264);
  --font-display: "Satoshi", ui-sans-serif, sans-serif;
}

/* which files contain classes: the build output of the CMS, plus two always-on states */
@source "../cms-export";
@source inline("{hover:,}bg-sky-{500,600}");

/* how plain elements look */
@layer base {
  a { color: var(--color-sky-700); }
  h1, h2 { text-wrap: balance; }
}

/* a reusable class for markup that cannot carry utilities */
@layer components {
  .card { @apply rounded-xl border border-gray-200 p-6; }
}
----

Compiling this with a template that uses `hover:bg-sky-500` and `hover:bg-sky-600` confirms the brace expansion: the
`@source inline()` line forces `bg-sky-500`, `bg-sky-600`, `hover:bg-sky-500` and `hover:bg-sky-600` into the output
even when no file mentions them, which is what you want for colours chosen by an editor at runtime.

=== Writing a plugin

When the same behaviour is needed in several projects, package it as a plugin and load it with `@plugin`. A plugin
is a JavaScript function that receives helpers for adding base styles, components, utilities and variants; it is the
only place in v4 where JavaScript participates in configuration.

[source,javascript]
----
// acme-plugin.js
const plugin = require("tailwindcss/plugin");

module.exports = plugin(function ({ addBase, addComponents, matchUtilities, addVariant }) {
  // base styles, emitted in @layer base
  addBase({ "h1, h2": { textWrap: "balance" } });

  // a component class, emitted in @layer components
  addComponents({ ".btn-acme": { borderRadius: "0.375rem", fontWeight: "600" } });

  // a functional utility: glow-soft, glow-strong
  matchUtilities(
    { glow: (value) => ({ textShadow: `0 1px 2px ${value}` }) },
    { values: { soft: "rgb(0 0 0 / 0.2)", strong: "rgb(0 0 0 / 0.6)" } },
  );

  // a variant: hocus:underline
  addVariant("hocus", ["&:hover", "&:focus-visible"]);
});
----

[source,css]
----
@import "tailwindcss";
@plugin "./acme-plugin.js";
----

A template using `glow-soft hocus:underline btn-acme` compiles to `text-shadow: 0 1px 2px rgb(0 0 0 / 0.2)`, a
`.hocus\:underline:hover, .hocus\:underline:focus-visible` rule, and the component rule. Most things a v3 plugin did can
now be written in CSS (`@utility`, `@custom-variant`, `@theme`), so reach for `@plugin` only when you need logic that
CSS cannot express, or when you are using a published plugin such as `@tailwindcss/typography`.

=== Choosing where a customization lives

[cols="2,2,3",options="header"]
|===
| You want | Use | Because

| A new colour, font, radius, breakpoint | `@theme` | it also becomes utilities and a CSS variable
| A one-off class with variants support | `@utility` | `hover:`, `md:` and `dark:` work on it automatically
| A new state or media condition | `@custom-variant` | it composes with every other variant
| Styles for elements you do not control | `@layer base` or a `@layer components` class with `@apply` | the markup cannot carry utilities
| A repeated card or button in your own markup | a framework component | the class list stays visible and the pieces stay overridable
| Behaviour that needs JavaScript at build time | `@plugin` | CSS alone cannot express it
|===

== The cascade-layer model

image::tailwind-cascade-layers.svg["Tailwind emits four CSS @layer blocks -- theme, base, components, utilities -- and a later layer wins over an earlier one regardless of selector specificity",width=700,role=text-center]

Because `utilities` is the last layer, a single utility class overrides a more specific rule you wrote in
`@layer components` -- which is exactly why component classes stay overridable by utilities. Anything outside a
layer still beats everything inside one, so unlayered custom CSS always wins.
