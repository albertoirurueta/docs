= Build and Production
:description: How the Tailwind CSS v4 build works -- source scanning and on-demand utility generation, minification, the three integration shapes (Vite plugin, PostCSS, standalone CLI), the Play CDN, and CI.
:keywords: Tailwind CSS build, tailwindcss v4 production, minify, tree-shaking, @tailwindcss/vite, @tailwindcss/postcss, standalone CLI, Play CDN, deterministic CSS artifact

include::partial$ai-disclaimer.adoc[]

Tailwind v4 has no separate "purge" phase: the engine reads your source files, works out which utility classes
you actually use, and emits exactly the CSS for those -- and nothing else -- in one stylesheet.

== How the build works end to end

The pipeline is: **scan the source files -> generate only the utilities that appear -> write one small
stylesheet**.

. Your CSS entry point is a single import. Everything else -- the reset, the theme variables, every utility and
  variant -- is pulled in and generated by that line. See
  https://tailwindcss.com/docs/installation/using-postcss[Using PostCSS] and
  https://tailwindcss.com/blog/tailwindcss-v4[the v4 release notes].
+
[source,css]
----
/* app.css -- the whole Tailwind entry point in v4 */
@import "tailwindcss";
----
. The engine automatically discovers template files to scan, starting from the current directory, honouring
  your `.gitignore`, and skipping binary and generated files. It scans them as **plain text**, extracts
  candidate class names, and generates CSS only for the ones it finds. Nothing else ends up in the output, so
  there is nothing to strip afterwards. See
  https://tailwindcss.com/docs/detecting-classes-in-source-files[Detecting classes in source files].
. When automatic detection is not enough -- a component library in `node_modules`, a path that is gitignored,
  classes that only exist in a database -- you register extra sources explicitly in CSS. There is no `content`
  array and no `tailwind.config.js` required in v4.
+
[source,css]
----
@import "tailwindcss";

/* pull in classes from a dependency that ships pre-built markup */
@source "../node_modules/@acme/ui/dist";

/* opt a path back out of scanning */
@source not "../src/legacy";

/* keep specific classes that never appear literally in source */
@source inline("bg-red-500 bg-green-500 bg-blue-500");
----

Because the CSS is *generated on demand* rather than *generated in full and then trimmed*, v4 needs no
`purge` option, no `content` glob, and no separate https://purgecss.com/[PurgeCSS] step. Removing a component
from your templates removes its utilities from the next build automatically.

== Minification

The generated stylesheet is already minimal in *rules*; `--minify` also strips whitespace and comments for the
smallest possible file. Add it to a standalone CLI build:

[source,bash]
----
# one-off production build with the npm CLI
npx @tailwindcss/cli -i src/app.css -o dist/app.css --minify

# or watch during development (no --minify)
npx @tailwindcss/cli -i src/app.css -o dist/app.css --watch
----

When Tailwind runs inside a bundler, the framework's own production build minifies the CSS for you -- for
example `vite build` (or `npm run build` in a Vite, Next.js, or SvelteKit project) emits minified, hashed
assets with no extra flags. A real application's Tailwind stylesheet is typically well under 10 kB
compressed, and it grows with the number of *distinct* utilities used, not with the size of the codebase.

== The three integration shapes

Pick whichever matches your toolchain; the CSS output is the same.

. **Bundler plugin** -- `@tailwindcss/vite`, the fastest path for any Vite-based project (React, Vue, Svelte,
  SolidJS, Astro, SvelteKit).
+
[source,javascript]
----
// vite.config.js
import { defineConfig } from "vite";
import tailwindcss from "@tailwindcss/vite";

export default defineConfig({
  plugins: [tailwindcss()],
});
----
. **PostCSS plugin** -- `@tailwindcss/postcss`, for build setups that already run PostCSS (Next.js, Angular,
  webpack, Parcel). See https://tailwindcss.com/docs/installation/using-postcss[Using PostCSS].
+
[source,javascript]
----
// postcss.config.mjs
export default {
  plugins: {
    "@tailwindcss/postcss": {},
  },
};
----
. **Standalone CLI** -- a single self-contained executable with **no Node.js required**, ideal for Ruby on
  Rails, Laravel, Go, and Phoenix projects that would otherwise not need a JavaScript toolchain. (A new Laravel
  application already ships Vite with `@tailwindcss/vite`; see
  xref:web/php-laravel/vite-and-frontend-assets.adoc[Vite and Frontend Assets].)
+
[source,bash]
----
# download the binary for your platform, then run it like the npm CLI
curl -sLO https://github.com/tailwindlabs/tailwindcss/releases/latest/download/tailwindcss-macos-arm64
chmod +x tailwindcss-macos-arm64
mv tailwindcss-macos-arm64 tailwindcss

./tailwindcss -i app/assets/stylesheets/app.css -o public/assets/app.css --minify
----

For framework-specific wiring -- where the entry CSS lives, which command to run -- follow
https://tailwindcss.com/docs/installation/framework-guides[the official framework guides].

== Deep dive: building the Acme page

The page from xref:web/tailwind/worked-example.adoc[Building a Page with Utilities] makes a good test project:
a single HTML file, a stylesheet that imports Tailwind and declares the brand token, and a small script for the menu.

[source,text]
----
acme/
  src/
    app.css      -- @import "tailwindcss"; @source "./index.html"; @theme { ... }
    index.html
    menu.js
  package.json
----

[source,json]
----
{
  "private": true,
  "scripts": {
    "dev": "tailwindcss -i src/app.css -o dist/app.css --watch",
    "build": "tailwindcss -i src/app.css -o dist/app.css --minify"
  },
  "devDependencies": {
    "@tailwindcss/cli": "^4.0.0",
    "tailwindcss": "^4.0.0"
  }
}
----

`npm run dev` rebuilds the stylesheet whenever a template or `app.css` changes; `npm run build` writes the minified
production file. The `tailwindcss` binary is provided by the `@tailwindcss/cli` package.

[mermaid]
....
sequenceDiagram
    participant D as Developer
    participant W as tailwindcss --watch
    participant F as Template files
    participant O as dist/app.css
    D->>W: npm run dev
    W->>F: scan for class names
    W->>O: write the first stylesheet
    D->>F: add hover:bg-brand/90 to a link
    F-->>W: file change event
    W->>F: re-scan the changed file
    W->>O: rewrite the stylesheet
    D->>W: npm run build
    W->>O: same engine with --minify
....

=== What a build costs

Building the finished Acme page and measuring the result gives concrete numbers:

[cols="2,1,1",options="header"]
|===
| Output | Bytes | Gzip -9

| Page with no utilities at all (reset, theme and `@property` rules only) | 12,013 | 3,374
| Acme page, unminified | 15,670 | 3,771
| Acme page, `--minify` | 13,024 | 3,496
|===

Two lessons come out of the table. Most of a small build is a fixed cost -- Preflight, the cascade-layer scaffolding
and the registered custom properties -- and every utility the page actually uses adds only a few hundred bytes on
top. And minification matters less than people expect once gzip or Brotli is in play, which is why the server's
compression setting is part of the same decision. The page's utilities are a tiny fraction of the total, so
`@source` discipline (do not scan folders you do not need) improves build time far more than it improves size.

=== Using a bundler instead

The same page built with Vite needs only the plugin; Vite then scans, generates, minifies and hashes the file as part
of `vite build`:

[source,javascript]
----
// vite.config.js
import { defineConfig } from "vite";
import tailwindcss from "@tailwindcss/vite";

export default defineConfig({ plugins: [tailwindcss()] });
----

[source,javascript]
----
// src/main.js
import "./app.css";
----

[source,text]
----
$ npx vite build
dist/index.html                  2.44 kB | gzip: 1.08 kB
dist/assets/index-IqGjBJvV.css  13.04 kB | gzip: 3.51 kB
dist/assets/index-Dbz7Q2II.js    0.67 kB | gzip: 0.38 kB
----

The CSS asset is within a few dozen bytes of the CLI's minified output, because both run the same engine; the hash in
the file name changes only when the content does, which is what lets a CDN cache it forever.

=== A size budget in CI

A pull request that accidentally scans `node_modules` or turns on `@source inline()` for a whole palette can double
the stylesheet without anyone noticing. A short script turns the size into a failing check:

[source,sh]
----
#!/bin/sh
# usage: check-size.sh dist/app.css 6000   (limit in bytes, gzip -9)
size=$(gzip -9 -c "$1" | wc -c | tr -d ' ')
echo "$1: $size bytes gzipped (limit $2)"
[ "$size" -le "$2" ] || { echo "CSS budget exceeded" >&2; exit 1; }
----

[source,yaml]
----
# .github/workflows/build.yml
name: build
on: [pull_request]
jobs:
  css:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: npm
      - run: npm ci
      - run: npm run build
      - run: sh check-size.sh dist/app.css 6000
----

Run against the Acme build above, the script reports `3513 bytes gzipped` and passes a 6000-byte budget, and exits
non-zero for a 3000-byte one. Because the build is deterministic, two consecutive builds of the same sources produce
identical files, so a budget failure is always caused by a source change and never by flakiness.

=== Troubleshooting a missing class

When a class works in development and disappears in production, the scanner is the cause nearly every time:

[cols="2,3",options="header"]
|===
| Cause | Fix

| The class is built from fragments (`pass:c["bg-" + color]`) | Write the complete class name in the source, or map values to full names
| The file lives in a gitignored folder or in `node_modules` | Add it with `@source "../path"`
| The class only exists in a database or CMS | List it with `+@source inline("...")+`
| The CSS entry file is not the one the page loads | Check the output path in the build command or bundler
| Production serves an older cached file | Use hashed file names so the cache key changes with the content
|===

== Play CDN and CI

The https://tailwindcss.com/docs/installation/play-cdn[Play CDN] (`<script
src="https://unpkg.com/@tailwindcss/browser@4"></script>`) compiles Tailwind in the browser at page load. It is
for prototyping and reduced test cases only -- never production, where it costs a full compile on every visit
and ships the entire engine to the client.

In **CI**, run the same build command you run locally -- `+npx @tailwindcss/cli ... --minify+`, or your
framework's `build` script. Given the same source files and the same Tailwind version, the output stylesheet is
a **deterministic artifact**: byte-for-byte reproducible, safe to cache between runs, and meaningful to diff in
a pull request. Treat it like any other compiled asset.

See also xref:web/html-css/performance-build-optimization.adoc[] for the general CSS delivery picture --
minification, compression, hashing, and critical CSS -- into which the Tailwind output slots unchanged, and
xref:web/tailwind/upgrading-v3-to-v4.adoc[] if you are moving a v3 `tailwind.config.js` project onto this
pipeline.
