= Building a Page with Utilities
:description: A worked Tailwind CSS v4 example -- a responsive header with a collapsing nav, a hero, and a card grid, built with utilities only, then layered with responsive variants, states, and dark mode, and finished by extracting the card into a component and adding one @theme customization.
:keywords: Tailwind worked example, responsive header, card grid, sm:grid-cols-2 lg:grid-cols-3, hover focus-visible, dark mode, extract component, @theme brand colour, Tailwind Play

include::partial$ai-disclaimer.adoc[]

This page assembles utilities from the rest of the section into one small responsive layout, showing the
usual order of work: structure first, then breakpoints, then states, then theme -- the workflow described in
https://tailwindcss.com/docs/styling-with-utility-classes[Styling with utility classes]. Paste any step into
https://play.tailwindcss.com/[Tailwind Play] to see it live.

== 4. Extract the repeated card

Once a class list repeats, move it into a component of whatever framework you use -- not `@apply`.

[source,jsx]
----
function Feature({ title, children }) {
  return (
    <article className="rounded-xl border border-gray-200 p-6 hover:shadow-md
                        dark:border-slate-800 dark:bg-slate-800/50">
      <h3 className="font-semibold">{title}</h3>
      <p className="mt-2 text-sm text-gray-600 dark:text-slate-400">{children}</p>
    </article>
  );
}
----

== 5. One theme customization

Add a brand colour and display font once; every `+*-brand+` / `font-display` utility now exists.

[source,css]
----
@import "tailwindcss";

@theme {
  --color-brand: oklch(0.55 0.2 264);
  --font-display: "Satoshi", ui-sans-serif, sans-serif;
}
----

== 6. A mobile menu that is state-driven

Step 2 hid the navigation on phones and showed a menu button, but the button did nothing. The state that matters --
whether the menu is open -- already has a standard home in the markup, the `aria-expanded` attribute, so the button
carries the state and the stylesheet reacts to it. The button becomes a `peer` and the navigation, which follows it,
uses `peer-aria-expanded:`.

[source,html]
----
<header class="flex flex-wrap items-center justify-between border-b border-gray-200 px-6 py-4">
  <a href="/" class="text-lg font-bold">Acme</a>

  <button class="peer rounded-md px-2 py-1 sm:hidden"
          aria-expanded="false" aria-controls="menu" aria-label="Menu">&#9776;</button>

  <nav id="menu"
       class="hidden w-full flex-col gap-2 pt-4 text-sm font-medium
              peer-aria-expanded:flex sm:flex sm:w-auto sm:flex-row sm:gap-6 sm:pt-0">
    <a href="/features">Features</a>
    <a href="/pricing">Pricing</a>
    <a href="/docs" aria-current="page" class="aria-[current=page]:text-brand">Docs</a>
  </nav>
</header>
----

[source,javascript]
----
const button = document.querySelector('button[aria-controls="menu"]');

button.addEventListener("click", () => {
  const open = button.getAttribute("aria-expanded") === "true";
  button.setAttribute("aria-expanded", String(!open));
});
----

Read the `nav` classes in layers. Unprefixed, it is a hidden full-width column. `peer-aria-expanded:flex` shows it
while the button reports `aria-expanded="true"`. From `sm` up, `sm:flex sm:w-auto sm:flex-row` makes it the inline
row from step 2 regardless of the button, and the button itself is `sm:hidden`. The current page link is styled from
`aria-current`, so the visual and the accessibility state cannot disagree.

[mermaid]
....
stateDiagram-v2
    [*] --> Closed
    Closed --> Open: click button, aria-expanded true
    Open --> Closed: click button, aria-expanded false
    Closed --> Inline: window reaches sm
    Open --> Inline: window reaches sm
    Inline --> Closed: window shrinks below sm
....

The script has one job -- flip an attribute -- and nothing in it knows about classes, so restyling the menu never
touches JavaScript. A DOM test (for example with jsdom) can load the page, click the button twice and assert that the
attribute alternates between `"true"` and `"false"`.

== 7. Make the card ask its container

The card in step 1 is placed in a three-column grid on desktop, but the same component may later move into a sidebar or
a wider layout. Wrap each card in a query container and let the card respond to the width it actually has:

[source,html]
----
<ul class="mx-auto grid max-w-5xl gap-6 px-6 pb-16 sm:grid-cols-2 lg:grid-cols-3">
  <li class="@container">
    <article class="group flex flex-col gap-2 rounded-xl border border-gray-200 p-6
                    @md:flex-row @md:items-center @md:gap-6
                    hover:shadow-md has-[a:focus-visible]:ring-2 has-[a:focus-visible]:ring-brand
                    dark:border-slate-800 dark:bg-slate-800/50">
      <h3 class="font-semibold group-hover:text-brand"><a href="/fast" class="outline-none">Fast</a></h3>
      <p class="text-sm text-gray-600 dark:text-slate-400">Only the CSS you use is generated.</p>
    </article>
  </li>
</ul>
----

Three changes from step 3, each from a different part of this section: the `@container` wrapper and `@md:` variants
(xref:web/tailwind/responsive-design.adoc[Responsive Design]); `group-hover:` plus `has-[a:focus-visible]:` so the
whole card reacts to the pointer and to keyboard focus
(xref:web/tailwind/states-and-variants.adoc[Hover, Focus, and Other States]); and the brand colour from the theme.

== 8. Put it together and build

The finished page needs only three files. The stylesheet below also wires the `dark:` variant to a `data-theme`
attribute so a toggle can drive it (xref:web/tailwind/dark-mode.adoc[Dark Mode]).

[source,css]
----
/* src/app.css */
@import "tailwindcss";
@source "./index.html";

@custom-variant dark (&:where([data-theme=dark], [data-theme=dark] *));

@theme {
  --color-brand: oklch(0.55 0.2 264);
  --font-display: "Satoshi", ui-sans-serif, sans-serif;
}
----

[source,bash]
----
npm install tailwindcss @tailwindcss/cli
npx @tailwindcss/cli -i src/app.css -o app.css --minify
----

The result of building exactly the page assembled in steps 1 to 7 -- header with the state-driven menu, hero, a
container-aware feature card, hover, focus and dark variants, and the brand token -- is a single stylesheet of about
13 kB (3.5 kB gzipped), of which roughly 12 kB is the fixed Preflight and theme scaffolding every Tailwind build
includes. Adding the other two feature cards adds nothing, because they reuse the same classes: the stylesheet grows
with the number of *distinct* utilities, not with the number of elements.

Doing them in reverse makes every later change a layout change.
