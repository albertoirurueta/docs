= Custom Styles and Arbitrary Values
:description: Tailwind CSS v4 escape hatches -- arbitrary values, properties and variants in square brackets, the CSS-variable shorthand, data-type hints, custom utilities with @utility (including functional utilities and --value()), @custom-variant, @variant, and @apply / @reference in component styles.
:keywords: Tailwind arbitrary values, arbitrary properties, arbitrary variants, bg-(--var) shorthand, data-type hint, @utility, functional utility, --value(), --modifier(), @custom-variant, @variant, @apply, @reference, custom CSS

include::partial$ai-disclaimer.adoc[]

When no built-in utility fits, Tailwind gives you graduated escape hatches -- from a one-off value in square
brackets, through your own reusable `@utility`, to plain CSS in a `@layer`. See
https://tailwindcss.com/docs/adding-custom-styles[Adding Custom Styles].

== Arbitrary values

Put any CSS value in square brackets and Tailwind generates the utility on demand. Use `+_+` for spaces (it is
converted to a space; keep literal underscores in `url()` and escape one you need as `\_`).

[source,html]
----
<div class="top-[117px] lg:top-[344px]"></div>
<div class="bg-[#bada55] text-[22px]"></div>
<div class="grid grid-cols-[1fr_500px_2fr]"></div>
<div class="max-h-[calc(100dvh-4rem)]"></div>
<span class="before:content-['Hello_world']"></span>
----

== Arbitrary properties and variants

[source,html]
----
<!-- a property with no utility at all -->
<div class="[mask-type:luminance] hover:[mask-type:alpha]"></div>

<!-- set a CSS variable inline, responsively -->
<div class="[--gutter:1rem] lg:[--gutter:2rem]"></div>

<!-- a selector Tailwind has no variant for -->
<div class="[&_p]:mt-4 [&.is-open]:block [&::-webkit-scrollbar]:hidden
            [@supports(display:grid)]:grid"></div>
----

== The CSS-variable shorthand

For values that are genuinely dynamic (a colour from a CMS, a user setting), set a CSS variable with an inline
`style` and reference it with the `(--var)` shorthand -- shorter than `[var(--var)]`:

[source,html]
----
<button style="--btn: #7c3aed; --btn-hover: #6d28d9"
        class="bg-(--btn) hover:bg-(--btn-hover) text-white px-4 py-2 rounded">
  Themed button
</button>
----

When the utility could take more than one CSS data type, add a hint:

[source,html]
----
<p class="text-(length:--fluid-size)">font-size from a variable</p>
<p class="text-(color:--brand)">colour from a variable</p>
----

== Custom utilities with `@utility`

`@utility` registers a class that works with every variant (`hover:`, `md:`, `dark:`) -- the v4 replacement
for a v3 `@layer utilities` block.

[source,css]
----
@import "tailwindcss";

/* static utility */
@utility content-auto { content-visibility: auto; }

/* nested selectors */
@utility scrollbar-none {
  &::-webkit-scrollbar { display: none; }
  scrollbar-width: none;
}

/* functional utility: `tab-*` accepts a number, a named value, or a bare integer */
@theme { --tab-size-github: 8; }

@utility tab-* {
  tab-size: --value(--tab-size-*, integer, [integer]);
}
----

[source,html]
----
<pre class="tab-4 md:tab-github">&#8230;</pre>
----

`--value()` resolves the part after the dash and `--modifier()` resolves a `/` modifier. To give the bare class a
default, register a static utility of the same name next to the functional one (`+@utility tab { tab-size: 4; }+`). See
https://tailwindcss.com/docs/adding-custom-styles#functional-utilities[Functional utilities].

== Custom variants

[source,css]
----
@import "tailwindcss";

/* selector form */
@custom-variant theme-midnight (&:where([data-theme="midnight"] *));

/* at-rule form */
@custom-variant pointer-coarse (@media (pointer: coarse));
----

[source,css]
----
/* apply a Tailwind variant inside your own rule */
.panel {
  background: white;
  @variant dark { background: #0f172a; }
  @variant hover, focus { background: #f1f5f9; }
}
----

== Deep dive: building the Acme utilities

The Acme page from xref:web/tailwind/worked-example.adoc[Building a Page with Utilities] needs four things the
framework does not ship: a coloured bar on the start edge of a card, a tinted background whose strength is chosen in
the markup, a vertical stack with a spacing step, and a wide horizontal gutter. Each is a small `@utility`.

[source,css]
----
@import "tailwindcss";

@theme {
  --color-brand: oklch(0.55 0.2 264);
  --gutter-wide: 3rem;
}

/* accent-bar-sky-500, accent-bar-brand, accent-bar-[#ff0] */
@utility accent-bar-* {
  border-inline-start: 4px solid --value(--color-*, [color]);
}

/* tint-sky-500/40, tint-brand/15 : the modifier is the strength in percent */
@utility tint-* {
  background-color: color-mix(in oklab, --value(--color-*, [color]) calc(--modifier(integer) * 1%), transparent);
}

/* stack-4, stack-6 : a column with a spacing-scale gap */
@utility stack-* {
  display: flex;
  flex-direction: column;
  gap: --spacing(--value(integer));
}

/* pad-wide : horizontal padding from a theme token in its own namespace */
@utility pad-* {
  padding-inline: --value(--gutter-*, [length]);
}
----

[source,html]
----
<article class="accent-bar-brand tint-sky-500/10 stack-4 pad-wide hocus:stack-6 md:accent-bar-sky-500">
  &#8230;
</article>
----

Compiling that markup shows how each argument is resolved:

[cols="2,3",options="header"]
|===
| Class | Result

| `accent-bar-sky-500` | `+border-inline-start: 4px solid var(--color-sky-500);+` -- the first `--value()` argument, a theme namespace, matched
| `accent-bar-[#ff0]` | `+border-inline-start: 4px solid #ff0;+` -- the bracket form matched the `[color]` argument
| `tint-sky-500/40` | `+color-mix(in oklab, var(--color-sky-500) calc(40 * 1%), transparent)+`
| `tint-sky-500` (no modifier) | *nothing is generated*: a declaration that needs `--modifier()` is dropped when the class has none
| `stack-4` | `+gap: calc(var(--spacing) * 4);+`
| `pad-wide` | `+padding-inline: var(--gutter-wide);+`
| `hocus:stack-6` | the whole utility, wrapped by the variant
|===

[mermaid]
....
flowchart LR
    C["class accent-bar-sky-500"] --> P["split at the pattern accent-bar-*"]
    P --> V["value = sky-500"]
    V --> T1{"matches --color-* ?"}
    T1 -->|yes| R1["var of --color-sky-500"]
    T1 -->|no| T2{"is a color in brackets?"}
    T2 -->|yes| R2["use the bracket value"]
    T2 -->|no| R3["no CSS generated"]
....

`--value()` tries its arguments in order and uses the first that matches, so the order is a priority list: a theme
namespace (`+--color-*+`), a bare data type (`integer`, `number`, `percentage`, `ratio`), or an arbitrary value with a
type (`[color]`, `[length]`, `[integer]`). A class that matches nothing is silently ignored, exactly as a built-in
utility with an unknown value would be.

=== A static utility with a variant inside

`@variant` lets a custom utility describe its own dark-mode or state rule, so the class works anywhere and does not
need a `dark:` prefix at the call site:

[source,css]
----
@utility surface-panel {
  background: white;
  border-radius: var(--radius-xl);

  @variant dark {
    background: var(--color-slate-800);
  }
}
----

With the default media-query strategy this compiles to the declarations plus a nested
`@media (prefers-color-scheme: dark)` block; with a `@custom-variant dark` it follows whatever you redefined.

NOTE: `dark:surface-panel` on such a utility is redundant, because the rule ends up wrapped in a dark condition twice
(once for the prefix and once for the inner `@variant`). Pick one place for the variant: inside the utility, or at the
call site.

=== Choosing the right escape hatch

[cols="2,3",options="header"]
|===
| Situation | Reach for

| One element needs one odd value | An arbitrary value: `top-[117px]`
| A value comes from data at runtime | A CSS variable set in `style`, read with `bg-(--btn)`
| The same odd value appears in several places | A theme token, so it becomes `bg-brand` instead of `bg-[#3f3cbb]`
| A new family of classes (`+accent-bar-*+`) | A functional `@utility`
| A new state (`hocus:`) | `@custom-variant`
| Third-party markup you cannot class | `@layer base` / `@layer components` with `@apply`
|===

The order is deliberate: each step moves the decision further from the markup, so use the earliest one that fits.

== `@apply` and `@reference`

`@apply` inlines existing utilities into a custom rule. Reach for it sparingly -- mainly to style third-party
markup you cannot add classes to; prefer a framework component for your own repeated patterns.

[source,css]
----
@layer components {
  .select2-dropdown { @apply rounded-b-md border border-gray-200 shadow-md; }
}
----

`@apply` can also target a combination of classes, which keeps a compound selector's specificity:

[source,css]
----
@layer components {
  .tarjeta.activo { @apply border-sky-500 bg-sky-50 shadow-md; }
}
----

The trade-off: the styling now lives in a stylesheet and the markup (`+class="tarjeta activo"+`) no longer shows
what it looks like, whereas utilities in the markup keep each element's styling visible in one place.

In a scoped stylesheet that is compiled separately (a Vue / Svelte `<style>` block, CSS Modules), the theme
and utilities are not in scope, so `@apply` and `@variant` fail. Pull them in with `@reference` -- it imports
the definitions without duplicating any CSS into that file:

[source,css]
----
/* Component.vue <style> */
@reference "../app.css";

h1 { @apply text-2xl font-bold text-sky-600; }
----
