= Dark Mode
:description: How Tailwind CSS v4's dark: variant works -- the default prefers-color-scheme behaviour, switching to a manual class or data-attribute strategy with @custom-variant, and a flash-free three-state light/dark/system toggle.
:keywords: Tailwind CSS dark mode, dark variant, prefers-color-scheme, custom-variant, class strategy, data-theme, theme toggle, matchMedia, localStorage, flash of wrong theme, FOUC

include::partial$ai-disclaimer.adoc[]

Tailwind styles dark mode through the `dark:` variant, which is on by default and driven by the operating
system. You opt into a manual toggle by redefining that variant with `@custom-variant`.

== The `dark:` variant

Prefix any utility with `dark:` and it applies only when dark mode is active. Out of the box that means the
https://developer.mozilla.org/en-US/docs/Web/CSS/@media/prefers-color-scheme[`prefers-color-scheme: dark`]
media query -- no configuration, no JavaScript.

[source,html]
----
<div class="bg-white text-gray-900 dark:bg-gray-900 dark:text-gray-50">
  <h1 class="text-2xl font-bold">Adaptive card</h1>
  <p class="text-gray-600 dark:text-gray-400">
    This block flips automatically when the OS is set to dark mode.
  </p>
  <button class="bg-sky-600 text-white hover:bg-sky-700
                 dark:bg-sky-500 dark:hover:bg-sky-400">
    Action
  </button>
</div>
----

See https://tailwindcss.com/docs/dark-mode[Dark mode].

== Switching to a manual (class) strategy

To let users choose a theme regardless of their OS setting, redefine the `dark` variant with
https://tailwindcss.com/docs/functions-and-directives#custom-variant-directive[`@custom-variant`] so it keys
off a `.dark` class on an ancestor instead of the media query.

[source,css]
----
@import "tailwindcss";

/* dark: now matches when a .dark class is on the element or any ancestor */
@custom-variant dark (&:where(.dark, .dark *));
----

Then add or remove that class on `<html>`:

[source,javascript]
----
const root = document.documentElement;

document.querySelector("#toggle").addEventListener("click", () => {
  root.classList.toggle("dark");
});
----

Every existing `dark:` utility keeps working unchanged; only the trigger moved from the media query to the
class.

== The data-attribute strategy

If you prefer an attribute over a class -- for example to expose more than two themes, or to keep class lists
clean -- point the variant at a `data-theme` attribute instead.

[source,css]
----
@import "tailwindcss";

@custom-variant dark (&:where([data-theme=dark], [data-theme=dark] *));
----

[source,html]
----
<!-- server-rendered, or set by the inline script below -->
<html data-theme="dark">
  <!-- dark: utilities are active for the whole document -->
</html>
----

== A three-state toggle: light / dark / system

A good toggle has three states: force light, force dark, or follow the OS ("system"). Persist the explicit
choices in
https://developer.mozilla.org/en-US/docs/Web/API/Window/localStorage[`localStorage`] and resolve "system" at
runtime with
https://developer.mozilla.org/en-US/docs/Web/API/Window/matchMedia[`matchMedia`].

[source,javascript]
----
// theme.js -- states: "light" | "dark" | "system"
const STORAGE_KEY = "theme";
const media = window.matchMedia("(prefers-color-scheme: dark)");

const resolve = (choice) =>
  choice === "system" ? (media.matches ? "dark" : "light") : choice;

export function applyTheme(choice) {
  document.documentElement.classList.toggle("dark", resolve(choice) === "dark");
  if (choice === "system") localStorage.removeItem(STORAGE_KEY);
  else localStorage.setItem(STORAGE_KEY, choice);
}

export const currentChoice = () => localStorage.getItem(STORAGE_KEY) ?? "system";

// keep "system" live when the OS setting changes
media.addEventListener("change", () => {
  if (currentChoice() === "system") applyTheme("system");
});

// wire up a <select id="theme-picker"> with light / dark / system options
// (guarded, so this module is safe to import on pages without the picker)
const picker = document.querySelector("#theme-picker");
if (picker) {
  picker.value = currentChoice();
  picker.addEventListener("change", () => applyTheme(picker.value));
}
----

To avoid a flash of the wrong theme, resolve it *before the first paint* with a tiny synchronous script at the
top of `<head>`, ahead of any stylesheet. This version matches the **class** strategy above:

[source,html]
----
<head>
  <script>
    (function () {
      var stored = localStorage.getItem("theme");
      var dark = stored === "dark" ||
        (!stored && window.matchMedia("(prefers-color-scheme: dark)").matches);
      document.documentElement.classList.toggle("dark", dark);
    })();
  </script>
  <link rel="stylesheet" href="/app.css" />
</head>
----

If you chose the **data-attribute** strategy instead, set `data-theme` rather than the class in that same
script:

[source,html]
----
<script>
  (function () {
    var stored = localStorage.getItem("theme");
    var dark = stored === "dark" ||
      (!stored && window.matchMedia("(prefers-color-scheme: dark)").matches);
    document.documentElement.dataset.theme = dark ? "dark" : "light";
  })();
</script>
----

`applyTheme()` in the module above must set the same thing (`+classList.toggle("dark", ...)+` for the class
strategy, `+dataset.theme = ...+` for the attribute strategy) so the pre-paint script and the runtime toggle
stay in agreement.

== What the strategies compile to

Switching strategy changes only the wrapper Tailwind puts around each `dark:` rule; the declarations inside are
identical. Compiling `dark:bg-slate-900` shows both shapes.

[cols="1,3",options="header"]
|===
| Strategy | Generated rule for `dark:bg-slate-900`

| Default (media query) | `+@media (prefers-color-scheme: dark) { .dark\:bg-slate-900 { background-color: var(--color-slate-900); } }+`
| `+@custom-variant dark (&:where([data-theme=dark], [data-theme=dark] *))+` | `+.dark\:bg-slate-900:where([data-theme=dark], [data-theme=dark] *) { background-color: var(--color-slate-900); }+`
|===

The `:where()` keeps the added selector at zero specificity, so a `dark:` utility has the same strength as any other
single-class utility and the usual stylesheet order decides conflicts.

== Deep dive: semantic tokens for the Acme page

Writing `bg-white dark:bg-slate-900` on every element works, but it repeats the colour decision everywhere and makes
a third theme expensive. A common refinement is to name the *roles* (surface, ink, line) once, give each role a value
per theme in plain CSS, and expose the roles as utilities. Elements then need no `dark:` prefix at all.

[source,css]
----
@import "tailwindcss";

@custom-variant dark (&:where([data-theme=dark], [data-theme=dark] *));

:root {
  color-scheme: light;
  --surface: oklch(1 0 0);
  --ink: oklch(0.21 0.03 265);
  --line: oklch(0.92 0.01 265);
}

[data-theme="dark"] {
  color-scheme: dark;
  --surface: oklch(0.21 0.03 265);
  --ink: oklch(0.96 0.01 265);
  --line: oklch(0.32 0.03 265);
}

@theme inline {
  --color-surface: var(--surface);
  --color-ink: var(--ink);
  --color-line: var(--line);
}

@theme {
  --color-brand: oklch(0.55 0.2 264);
}
----

[source,html]
----
<body class="bg-surface text-ink">
  <header class="border-b border-line">&#8230;</header>
  <article class="rounded-xl border border-line p-6">&#8230;</article>
</body>
----

Three details matter here:

* `@theme inline` makes `bg-surface` compile to `background-color: var(--surface)`. Without `inline`, Tailwind would
  emit `var(--color-surface)`, a variable defined once on `:root` whose value is resolved there, so a nested scope that
  overrides `--surface` (a dark panel inside a light page) would not take effect. Use `inline` whenever a theme token
  points at another variable that changes at runtime.
* `color-scheme` tells the browser to draw form controls, scrollbars and the default canvas for the active theme, so
  an unstyled `<input>` is not a white box on a dark page.
* The `dark:` variant is still available for the exceptions: a brand-coloured link that needs a lighter shade in
  dark mode is `text-brand dark:text-sky-400`.

The brand colour (`bg-brand`, `bg-brand/90`) stays an ordinary `@theme` token, because it is the same in both themes.

NOTE: The role variables are written in unlayered CSS, so they beat any rule inside a Tailwind layer. That is what
you want for variables, but remember it when you debug a colour that "will not change".

== The toggle end to end

The pre-paint script, the runtime module and the stylesheet cooperate in a fixed order. Following one visit shows why
the script has to be synchronous and sit in `<head>`.

[mermaid]
....
sequenceDiagram
    participant B as Browser
    participant S as Inline head script
    participant C as app.css
    participant M as theme.js
    B->>S: parse head, run synchronously
    S->>S: read localStorage theme, else matchMedia
    S->>B: set data-theme on html
    B->>C: load stylesheet, first paint uses the right theme
    B->>M: load module
    M->>B: picker shows the stored choice
    Note over M,B: the user picks system
    M->>M: remove stored key, resolve with matchMedia
    M->>B: set data-theme and color-scheme
    Note over M,B: the OS setting changes
    M->>B: change event, re-resolve only if the choice is system
....

Here is a version of the runtime module for the data-attribute strategy that also sets `color-scheme`, so the
semantic tokens above and the native controls change together:

[source,javascript]
----
// theme.js
const STORAGE_KEY = "theme";
const media = window.matchMedia("(prefers-color-scheme: dark)");

const resolve = (choice) =>
  choice === "system" ? (media.matches ? "dark" : "light") : choice;

export function applyTheme(choice) {
  const theme = resolve(choice);
  document.documentElement.dataset.theme = theme;
  document.documentElement.style.colorScheme = theme;
  if (choice === "system") localStorage.removeItem(STORAGE_KEY);
  else localStorage.setItem(STORAGE_KEY, choice);
}

export const currentChoice = () => localStorage.getItem(STORAGE_KEY) ?? "system";

media.addEventListener("change", () => {
  if (currentChoice() === "system") applyTheme("system");
});

const picker = document.querySelector("#theme-picker");
if (picker) {
  picker.value = currentChoice();
  picker.addEventListener("change", () => applyTheme(picker.value));
}
----

=== Testing the toggle

The logic has four behaviours worth pinning down: "system" follows the OS, an explicit choice ignores the OS, the
choice is persisted, and choosing "system" clears the stored value. A test runs in a plain DOM implementation such as
https://github.com/jsdom/jsdom[jsdom], with a stub for `matchMedia` that you can flip:

[source,javascript]
----
import { JSDOM } from "jsdom";
import fs from "node:fs";
import assert from "node:assert";

const source = fs.readFileSync("theme.js", "utf8").replace(/export /g, "") +
  "\nwindow.__theme = { applyTheme, currentChoice };";

const dom = new JSDOM(
  `<select id="theme-picker"><option>light</option><option>dark</option><option>system</option></select>`,
  { runScripts: "outside-only", url: "http://localhost/" },
);
const { window } = dom;

const listeners = [];
const osDark = { matches: false, addEventListener: (_event, fn) => listeners.push(fn) };
window.matchMedia = () => osDark;
window.eval(source);

const { applyTheme } = window.__theme;
const root = window.document.documentElement;
const setOsDark = (value) => { osDark.matches = value; listeners.forEach((fn) => fn()); };

applyTheme("system");
assert.equal(root.dataset.theme, "light");

setOsDark(true);                                   // system follows the OS
assert.equal(root.dataset.theme, "dark");

applyTheme("light");                               // explicit choice persists and beats the OS
assert.equal(window.localStorage.getItem("theme"), "light");
setOsDark(true);
assert.equal(root.dataset.theme, "light");

const picker = window.document.querySelector("#theme-picker");
picker.value = "system";                           // choosing system clears the stored value
picker.dispatchEvent(new window.Event("change"));
assert.equal(window.localStorage.getItem("theme"), null);
console.log("theme toggle: ok");
----

== Accessibility and dark mode

* Check contrast in *both* themes. A `text-gray-400` that is fine on a dark surface can fail on white; semantic roles
  make this a two-value review instead of a per-element one.
* Do not rely on colour alone to signal state. The `+aria-*+` variants from
  xref:web/tailwind/states-and-variants.adoc[Hover, Focus, and Other States] work identically in both themes.
* Respect users who ask for less: `contrast-more:` and `forced-colors:` variants are independent of the theme
  strategy, so a high-contrast user keeps the system colours even when `data-theme` is set.
