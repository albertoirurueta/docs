Tailwind CSS is a utility-first framework: you style elements by composing small single-purpose classes directly
in your markup. This page covers what that means, how to install Tailwind v4, how to set up your editor, and
which browsers it supports.

== Utility-first vs. component frameworks

A component framework such as xref:web/bootstrap/index.adoc[Bootstrap] ships ready-made semantic classes -- you
write `<button class="btn btn-primary">` and inherit a designed component, then override its CSS wherever the
design diverges. Tailwind instead gives you low-level *utilities* -- roughly one class per declaration -- that
you compose into the exact component you want (`inline-flex rounded-md bg-sky-600 px-4 py-2 text-sm
font-semibold text-white hover:bg-sky-500`); there is no `btn` rule to fight, custom values come from your theme
rather than from a growing override stylesheet, and because every state (`hover:`, `focus:`, `md:`, `dark:`) is
expressible as a prefixed utility you "rapidly build modern websites without ever leaving your HTML" -- the
styling decisions happen in the template you are already editing, not in a separate CSS file you switch to.

[source,html]
----
<!-- component framework: one semantic class, styling hidden in a stylesheet -->
<button class="btn btn-primary">Save changes</button>

<!-- utility-first: the same button composed from utilities, styling visible inline -->
<button class="inline-flex items-center rounded-md bg-sky-600 px-4 py-2
               text-sm font-semibold text-white shadow-sm
               hover:bg-sky-500 focus-visible:outline focus-visible:outline-2">
  Save changes
</button>
----

== Installation

Tailwind v4 has one build engine with several entry points. Pick by how your project already builds CSS.

=== Vite plugin (recommended)

If you use Vite, add `@tailwindcss/vite`. It is the fastest path and needs no PostCSS configuration.

[source,bash]
----
npm install tailwindcss @tailwindcss/vite
----

[source,javascript]
----
// vite.config.js
import { defineConfig } from 'vite'
import tailwindcss from '@tailwindcss/vite'

export default defineConfig({
  plugins: [
    tailwindcss(),
  ],
})
----

See https://tailwindcss.com/docs/installation/using-vite[Installing Tailwind CSS with Vite].

=== PostCSS

For toolchains built on PostCSS (Webpack, Next.js, the Angular CLI, and similar), use `@tailwindcss/postcss`.

[source,bash]
----
npm install tailwindcss @tailwindcss/postcss postcss
----

[source,javascript]
----
// postcss.config.mjs
export default {
  plugins: {
    "@tailwindcss/postcss": {},
  },
}
----

See https://tailwindcss.com/docs/installation/using-postcss[Installing Tailwind CSS as a PostCSS plugin].

=== Tailwind CLI

The CLI compiles CSS with no bundler at all -- good for a simple site, an email template, or a one-step build.

[source,bash]
----
npx @tailwindcss/cli -i input.css -o output.css --watch
----

A standalone executable is also published for each platform, so Tailwind can run on a machine with no Node.js
installed:

[source,bash]
----
# download the tailwindcss binary for your platform, then:
./tailwindcss -i input.css -o output.css --watch
----

See https://tailwindcss.com/docs/installation/tailwind-cli[Installing the Tailwind CSS CLI].

=== Framework guides

The docs carry step-by-step guides for Next.js, Nuxt, SvelteKit, Angular, Laravel, Rails, Astro, and more, each
wiring Tailwind into that framework's own build. See
https://tailwindcss.com/docs/installation/framework-guides[Framework guides]. For Next.js, see also
xref:web/nextjs/styling.adoc[Next.js Styling]; for Laravel, see
xref:web/php-laravel/vite-and-frontend-assets.adoc[Vite and Frontend Assets]; for Thymeleaf, see
xref:web/thymeleaf/styling-and-front-end-assets.adoc[Styling & Front-end Assets].

=== Play CDN

For a prototype with no build step, pull the engine straight from a `<script>` tag. It compiles in the browser
-- fine for a pen or a bug repro, but **not for production**. In v4 the Play CDN ships as the
`@tailwindcss/browser` package (the v3 `cdn.tailwindcss.com` host does not serve v4):

[source,html]
----
<script src="https://unpkg.com/@tailwindcss/browser@4"></script>
----

See https://tailwindcss.com/docs/installation/play-cdn[Play CDN].

=== Choosing an install path

The paths above differ only in *where the engine runs*; the stylesheet (`@import "tailwindcss";`) and the class
vocabulary are identical in all of them. The decision usually takes one look at what already builds your CSS:

[mermaid]
....
flowchart TD
    A["Starting a Tailwind project"] --> B{"Already using a bundler?"}
    B -->|"Vite or a Vite-based framework"| V["@tailwindcss/vite"]
    B -->|"Webpack, Next.js, Angular CLI"| P["@tailwindcss/postcss"]
    B -->|"No bundler"| C{"Node.js available?"}
    C -->|"Yes"| L["@tailwindcss/cli"]
    C -->|"No"| S["standalone tailwindcss binary"]
    A --> D{"Only a throwaway prototype?"}
    D -->|"Yes"| PL["Play CDN (@tailwindcss/browser)"]
....

Whichever entry point you pick, it reads the same CSS entry file, so switching later (for example from the CLI to
the Vite plugin when a site grows a bundler) changes one config file and nothing in the markup.

== The stylesheet and HTML starter

In v4 the whole framework is pulled in with a single CSS `@import`. This replaces v3's three `@tailwind`
directives.

[source,css]
----
/* app.css -- Tailwind v4 */
@import "tailwindcss";

/* v3 equivalent, no longer used:
   @tailwind base;
   @tailwind components;
   @tailwind utilities; */
----

Load the compiled stylesheet and start writing utilities:

[source,html]
----
<!doctype html>
<html lang="en">
  <head>
    <meta charset="utf-8">
    <meta name="viewport" content="width=device-width, initial-scale=1">
    <link href="/dist/app.css" rel="stylesheet">
  </head>
  <body>
    <h1 class="text-3xl font-bold underline">Hello Tailwind</h1>
  </body>
</html>
----

== Editor setup

* **Tailwind CSS IntelliSense** -- the official VS Code extension: class-name autocomplete, hover previews of the
  generated CSS, linting, and colour swatches. It is powered by a **Language Server**
  (`@tailwindcss/language-server`), so the same features work in Neovim, Zed, and other LSP-capable editors.
* **prettier-plugin-tailwindcss** -- a Prettier plugin that sorts utility classes into Tailwind's recommended
  order automatically on format.

[source,bash]
----
npm install -D prettier prettier-plugin-tailwindcss
----

[source,json]
----
{
  "plugins": ["prettier-plugin-tailwindcss"]
}
----

See https://tailwindcss.com/docs/editor-setup[Editor setup].

== Compatibility

Tailwind v4 targets modern browsers and leans on recent CSS features -- notably `@property` and `color-mix()` --
for things like the `/` opacity modifier and the theme variables. The support baseline is:

[cols="1,1",options="header"]
|===
| Browser | Minimum version

| Safari | 16.4+
| Chrome | 111+
| Firefox | 128+
|===

On an older browser a Tailwind stylesheet still loads, but effects that depend on those features (opacity
modifiers, some colour and gradient handling) degrade or drop out; there is no build-time transpile-to-old-CSS
path, so a project that must support older engines should stay on Tailwind v3. The generated CSS is otherwise
standard cascade layers and custom properties -- see xref:web/html-css/index.adoc[HTML & CSS] for the underlying
platform features.

[source,css]
----
/* the kind of modern CSS Tailwind v4 emits */
@property --tw-bg-opacity {
  syntax: "<number>";
  inherits: false;
  initial-value: 1;
}

.bg-sky-500\/75 {
  background-color: color-mix(in oklab, var(--color-sky-500) 75%, transparent);
}
----

See https://tailwindcss.com/docs/compatibility[Compatibility].

== Worked example: the Acme page, end to end

The rest of this section builds one running example, the *Acme* landing page (a header, a hero and a card grid; see
xref:web/tailwind/worked-example.adoc[]). This is the smallest complete project that produces the first step of
it with the CLI, no bundler and no framework. The directory holds three files you write by hand and one that is
generated:

[source,text]
----
acme-site/
  package.json      <- scripts and the two dev dependencies
  index.html        <- the markup, with utility classes
  src/input.css     <- the Tailwind entry point (one line)
  dist/app.css      <- generated; do not edit, usually git-ignored
----

[source,json]
----
{
  "name": "acme-site",
  "private": true,
  "scripts": {
    "build:css": "tailwindcss -i src/input.css -o dist/app.css --minify",
    "watch:css": "tailwindcss -i src/input.css -o dist/app.css --watch"
  },
  "devDependencies": {
    "@tailwindcss/cli": "^4.0.0",
    "tailwindcss": "^4.0.0"
  }
}
----

[source,css]
----
/* src/input.css */
@import "tailwindcss";
----

[source,html]
----
<!-- index.html: the body of the page (the head is the starter shown above, linking /dist/app.css) -->
<header class="flex items-center justify-between border-b border-gray-200 px-6 py-4">
  <a href="/" class="text-lg font-bold">Acme</a>
  <nav class="flex gap-6 text-sm font-medium">
    <a href="/features">Features</a>
    <a href="/pricing">Pricing</a>
    <a href="/docs">Docs</a>
  </nav>
</header>
<section class="mx-auto max-w-3xl px-6 py-16 text-center">
  <h1 class="text-4xl font-extrabold tracking-tight">Ship your site faster</h1>
  <p class="mt-4 text-gray-600">Utility-first CSS, no context switching.</p>
</section>
----

Run `npm install`, then `npm run build:css` (or `npm run watch:css` while you edit). The build finishes in a few
tens of milliseconds and writes `dist/app.css`. With Tailwind 4.3 the minified stylesheet for this page is about
6 KB: the theme variables, Preflight, and exactly the dozen or so utilities the markup uses. Add a class such as
`bg-sky-600` to the HTML while `watch:css` is running and the rule appears in `dist/app.css` on the next
save; remove the class and the rule disappears again. Nothing is generated for a class that no file mentions.

=== How the build turns markup into CSS

The engine never parses your HTML as HTML. It scans every non-ignored source file as plain text, collects each
token that *could* be a class name, asks the theme whether each candidate is a real utility or variant, and emits
CSS only for the ones that are. This is why a class assembled from string fragments (`pass:c['bg-' + color]`) is never
found: the complete name has to appear somewhere in the source.

[mermaid]
....
flowchart LR
    SRC["source files: HTML, JSX, templates"] --> SCAN["scan as plain text"]
    SCAN --> CAND["candidate tokens"]
    CAND --> MATCH{"matches a utility or variant?"}
    THEME["@theme variables"] --> MATCH
    MATCH -->|"yes"| GEN["generate the rule"]
    MATCH -->|"no"| DROP["discard silently"]
    GEN --> OUT["app.css in the layers: theme, base, utilities"]
....

Files that Git ignores, `node_modules` and binary files are skipped automatically. The same page explains how to
add a source directory or safelist a class: see xref:web/tailwind/build-and-production.adoc[] and
xref:web/tailwind/customization-and-configuration.adoc[].

=== Checking that it works

Three quick checks tell you whether the toolchain is wired correctly, in the order failures usually appear:

. *The stylesheet is empty or unstyled.* The `<link>` points at a path the server does not serve, or the build
  was never run; open `dist/app.css` and confirm it exists and starts with the `tailwindcss v4` banner.
. *Preflight applied but a utility did nothing.* The class is not in a scanned file (a path outside the project
  root, a dynamically built name). Write the full class name somewhere the scanner reads.
. *Everything is unstyled but the build log is clean.* The entry file lacks `@import "tailwindcss";`, or an old
  v3 `@tailwind base;` block is still there.

Once the page renders, follow the Acme example into xref:web/tailwind/utility-first-fundamentals.adoc[], which
takes the same markup apart class by class.
