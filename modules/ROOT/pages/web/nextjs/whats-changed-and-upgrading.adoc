[#v13]
=== Next.js 13 and 13.4: the App Router Arrives

Next.js 13 is the version the Pages Router books stop at. It introduced the `app` directory in beta with layouts,
React Server Components and streaming, and the App Router was declared stable in 13.4 (May 2023). The release notes
list the first set of breaking changes that tutorials from 2021 and 2022 trip over:

* the minimum React version became 18.2 and the minimum Node.js version 14.6;
* `next/image` was renamed `next/legacy/image` and the new image component took the name `next/image`;
* a `next/link` child can no longer be an `<a>` (the temporary `legacyBehavior` prop keeps the old form);
* the `target` option of `next.config.js` was removed, Internet Explorer was dropped as a target, and `swcMinify`
became `true`;
* `@next/font` replaced the CSS font loading recipes (13.2 made it built in as `next/font`).

The Pages Router was not removed. Both routers coexist in one application, and the Pages Router remains supported;
it is simply no longer where the new features land. The pages of this section that touch it say so where it differs.

Source: https://nextjs.org/blog/next-13[Next.js 13] and https://nextjs.org/blog/next-13-4[Next.js 13.4]

[#v14]
=== Next.js 14: Server Actions and `next export`

Next.js 14 (2023-10-26) is a small upgrade guide. Its summary is four lines:

* the minimum Node.js version moved from 16.14 to 18.17;
* the `next export` command was removed in favour of `output: 'export'` in `next.config`;
* `ImageResponse` moved from `next/server` to `next/og`;
* the `@next/font` package was removed in favour of the built-in `next/font`.

Server Actions became stable, and Partial Prerendering appeared as a preview. Version 14.2 added the first `staleTimes`
experiment for the client router cache, which Next.js 15 used to change a default (see below).

Running `next export` in a current project shows what the removal looks like.

.`next export` in Next.js 16.3.8
[source,text]
----
$ npx next export
⨯
    `next export` has been removed in favor of 'output: export' in next.config.js.
Learn more: https://nextjs.org/docs/app/building-your-application/deploying/static-exports
----

Source: https://nextjs.org/docs/app/guides/upgrading/version-14[Upgrading from 13 to 14] and https://nextjs.org/docs/app/guides/static-exports[Static Exports]

[#v15]
=== Next.js 15: Async Request APIs and Caching Off by Default

Version 15 (2024-10-21) made the two changes that break the most old code. Both are described in the
https://nextjs.org/docs/app/guides/upgrading/version-15[version 15 upgrade guide].

*Request-time APIs became asynchronous.* `cookies`, `headers`, `draftMode`, the `params` prop of `layout`, `page`,
`route`, `default` and the metadata image files, and the `searchParams` prop of `page` are Promises. Version 15 kept a
temporary synchronous compatibility mode that logged a warning in development; Next.js 16 removed it. The reason is
rendering: a Promise lets Next.js prerender everything before the first access to request data, which is what Partial
Prerendering and Cache Components build on.

.Version 15 and later: awaiting the request APIs
[source,tsx]
----
import { cookies } from 'next/headers'

// Before (13 and 14)
const cookieStore = cookies()
const token = cookieStore.get('token')

// After (15, required in 16)
const cookieStore = await cookies()
const token = cookieStore.get('token')
----

Source: https://nextjs.org/docs/app/guides/upgrading/version-15#async-request-apis-breaking-change[Upgrading from 14 to 15: Async Request APIs] and https://nextjs.org/blog/next-15#async-request-apis-breaking-change[Next.js 15: why the APIs became asynchronous]

The page-level form is the one tutorials get wrong most often, because the destructured argument is now a Promise
object:

.A page before and after (the output of the codemod shown in a later section)
[source,tsx]
----
// Before
type Props = { params: { id: string }; searchParams: { lang?: string } }

export default function Page({ params, searchParams }: Props) {
  const theme = cookies().get('theme')?.value ?? 'light'
  /* ... */
}

// After
type Props = {
  params: Promise<{ id: string }>
  searchParams: Promise<{ lang?: string }>
}

export default async function Page(props: Props) {
  const searchParams = await props.searchParams
  const params = await props.params
  const theme = (await cookies()).get('theme')?.value ?? 'light'
  /* ... */
}
----

Source: https://nextjs.org/docs/app/guides/upgrading/version-15#params--searchparams[Upgrading from 14 to 15: params and searchParams]

A synchronous Client Component page cannot `await`; it reads the Promise with React's `use` hook instead
(`const params = use(props.params)`). Next.js 15.5 added `npx next typegen`, which generates the global `PageProps`,
`LayoutProps` and `RouteContext` helpers so that these types need not be written by hand; they are used throughout this
section as `PageProps<'/[locale]/books/[id]'>`.

.`next typegen` in the scratch _Bookshelf_ app
[source,text]
----
$ npx next typegen
Generating route types...
✓ Types generated successfully
----

Source: https://nextjs.org/docs/app/guides/upgrading/version-16#migrating-types-for-async-request-time-apis[Upgrading to version 16: migrating types for async Request-time APIs]

*Caching defaults moved to "uncached".* In versions 13 and 14 a `fetch` was cached by default, a `GET` Route Handler was
cached unless it used a dynamic function, and the client router cache reused page segments for about 30 seconds.
Version 15 reversed all three: `fetch` requests and `GET` handlers are not cached unless asked to be (`cache:
'force-cache'`, `export const dynamic = 'force-static'`), and the client router cache no longer reuses page segments on
navigation (`staleTimes.dynamic` is 0), although it still reuses them for back and forward navigation and for shared
layouts. The full account of the layers, in both models, is on the xref:web/nextjs/caching.adoc[Caching] page; the
shape of the change is this:

.Caching defaults across versions (previous model)
[cols="3,2,2",options="header"]
|===
| Behaviour | Next.js 13 and 14 | Next.js 15 and later

| `fetch` without options
| Cached (`force-cache`)
| Not cached

| `GET` Route Handler
| Cached when it uses no dynamic function
| Not cached; opt in with `dynamic = 'force-static'`

| Client router cache for page segments
| About 30 seconds for dynamic pages
| Not reused (`staleTimes.dynamic: 0`); opt in with `experimental.staleTimes`
|===

Source: https://nextjs.org/docs/app/guides/upgrading/version-15#fetch-requests[Upgrading from 14 to 15: fetch requests, Route Handlers and Client Cache]

Other breaking changes in 15: the minimum Node.js version became 18.18; React 19 became the minimum for the App Router
(the Pages Router accepts React 18 or 19); `useFormState` was replaced by `useActionState`; `next/dynamic` with
`ssr: false` is disallowed in Server Components; the `runtime` value `experimental-edge` is an error (use `edge`);
`revalidateTag` and `revalidatePath` throw if called during render; `geo` and `ip` were removed from `NextRequest`;
Speed Insights auto-instrumentation was removed; `experimental.bundlePagesExternals` became
`bundlePagesRouterDependencies` and `experimental.serverComponentsExternalPackages` became `serverExternalPackages`.
Version 15 also made `next.config.ts` a supported file, shipped `<Form>`, stabilised `instrumentation.js`, and improved
hydration error messages. Version 15.1 added `after` (stable) and `forbidden`/`unauthorized` (experimental).

Source: https://nextjs.org/blog/next-15[Next.js 15] and https://nextjs.org/blog/next-15-1[Next.js 15.1]

[#v16]
=== Next.js 16.0: Turbopack, Proxy and the End of the Compatibility Period

Version 16 (2025-10-21) is the largest cleanup since 13. Its
https://nextjs.org/docs/app/guides/upgrading/version-16[upgrade guide] is long, but the changes group into five themes.

*Turbopack by default.* `next dev` and `next build` use Turbopack; the `--turbopack` flag in `package.json` scripts is
no longer needed. A project with a custom `webpack` function and no `turbopack` key fails `next build` on purpose, so
that nobody ships a build that silently ignores their webpack configuration. The three ways out are `--webpack` to opt
out, `--turbopack` to build anyway, or an (empty or real) `turbopack` key. The `turbopack` configuration also moved out
of `experimental`.

.A webpack function without a turbopack key, built with Next.js 16.3.8
[source,text]
----
$ npx next build
▲ Next.js 16.3.8 (Turbopack)

  Creating an optimized production build ...
⨯ ERROR: This build is using Turbopack, with a `webpack` config and no `turbopack` config.
   This may be a mistake.

   As of Next.js 16 Turbopack is enabled by default and
   custom webpack configurations may need to be migrated to Turbopack.
   [...]
   `--turbopack` or `--webpack` flag explicitly or simply setting an
   empty turbopack config in your Next config file (e.g. `turbopack: {}`).
----

Source: https://nextjs.org/docs/app/guides/upgrading/version-16#turbopack-by-default[Upgrading to version 16: Turbopack by default]

The moved key is detected by the configuration validator. This is the project that the `upgrade` codemod (below) had
just processed, whose `next.config.mjs` still had the Next.js 15 shape.

.`experimental.turbopack` after the upgrade, built with Next.js 16.3.8

----
▲ Next.js 16.3.8 (Turbopack)

⚠     Unrecognized key(s) in object: 'turbopack' at "experimental"
⚠ See more info here: https://nextjs.org/docs/messages/invalid-next-config

.The fix: `turbopack` at the top level
[source,js]
----

  turbopack: {}, // was: experimental: { turbopack: {} }
}
----

Source: https://nextjs.org/docs/app/guides/upgrading/version-16#turbopack-configuration-location[Upgrading to version 16: Turbopack configuration location]

*Synchronous request APIs removed.* The version 15 compatibility mode is gone, so code that still reads `params`,
`searchParams`, `cookies()`, `headers()` or `draftMode()` synchronously fails to type-check and fails at runtime. In
Next.js 16 the props of `opengraph-image`, `twitter-image`, `icon`, `apple-icon` and `sitemap` (the `id`) became Promises
as well.

.A synchronous page and a one-argument `revalidateTag`, after the upgrade, built with Next.js 16.3.8
[source,text]
----
  Running TypeScript ...
app/books/[id]/page.tsx(6,27): error TS2339: Property 'get' does not exist on type 'Promise<ReadonlyRequestCookies>'.
lib/cache.ts(15,3): error TS2554: Expected 2 arguments, but got 1.
Failed to type check.
----

Source: https://nextjs.org/docs/app/guides/upgrading/version-16#async-request-apis-breaking-change[Upgrading to version 16: Async Request APIs]

*Caching APIs.* `revalidateTag` takes a second argument, a `cacheLife` profile, and the single-argument form is
deprecated (a TypeScript error, as above); `updateTag` is new, for Server Actions only, and gives read-your-writes
semantics; `refresh` refreshes the client router from a Server Action; `cacheLife` and `cacheTag` are stable, so the
`unstable_` prefix and the aliased imports go away. `experimental.ppr`, the `experimental_ppr` segment export,
`experimental.dynamicIO` and `experimental.useCache` were removed in favour of the top-level `cacheComponents` flag.
Enabling `cacheComponents` is not a rename: it can surface build errors for uncached data outside `<Suspense>`, and
the migration path is the https://nextjs.org/docs/app/guides/migrating-to-cache-components[Migrating to Cache Components]
guide. The mechanics are on the xref:web/nextjs/caching.adoc[Caching] and
xref:web/nextjs/partial-prerendering-and-cache-components.adoc[Partial Prerendering & Cache Components] pages.

.The three caching changes in code
[source,ts]
----
// Before
import {
  unstable_cacheLife as cacheLife,
  unstable_cacheTag as cacheTag,
} from 'next/cache'
revalidateTag('posts')

// After (16): stable names, a profile on revalidateTag
import { cacheLife, cacheTag, revalidateTag } from 'next/cache'
revalidateTag('posts', 'max') // stale-while-revalidate

// For read-your-writes inside a Server Action
import { updateTag } from 'next/cache'
updateTag(`user-${userId}`)
----

A `'use server'` file that calls `updateTag`, `refresh` and the two-argument `revalidateTag` compiled and type-checked
with `next build` in the scratch project.

Source: https://nextjs.org/docs/app/guides/upgrading/version-16#caching-apis[Upgrading to version 16: Caching APIs]

cannot be changed; the Edge runtime is not supported in the Proxy, so projects that need it keep `middleware.ts`. The
flags that contained the word "middleware" were renamed (`skipMiddlewareUrlNormalize` is now `skipProxyUrlNormalize`).

*Removals.* These were deprecated earlier and are gone:

* *AMP*: the `amp` configuration, `next/amp` and `useAmp`, and `export const config = { amp: true }`;
* *`next lint`* and the `eslint` option of `next.config`; `next build` no longer lints;
* *`serverRuntimeConfig` and `publicRuntimeConfig`* (use environment variables);
* the `devIndicators` options `appIsrStatus`, `buildActivity` and `buildActivityPosition`;
* `experimental.dynamicIO`, `experimental.useCache`, `experimental.ppr` and `experimental_ppr`;
* `unstable_rootParams` (replaced by `next/root-params`, which shipped in 16.3);
* the size and First Load JS columns of the `next build` output, which were inaccurate with Server Components.

Each removal has a visible failure mode. Importing `next/amp`, setting a removed key, or running the old command gives
these messages in 16.3.8.

The replacement for `serverRuntimeConfig` and `publicRuntimeConfig` is plain environment variables: read secrets on
the server, prefix only genuinely public values with `NEXT_PUBLIC_`, and call `connection()` before reading
`process.env` when a value must be read at request time rather than inlined at build time (see
xref:web/nextjs/configuration-typescript-and-environment-variables.adoc[Configuration, TypeScript & Environment Variables]).

Source: https://nextjs.org/docs/app/guides/upgrading/version-16#removals[Upgrading to version 16: Removals]

*Behaviour changes and defaults.* These do not break compilation but change output:

* *Parallel routes need `default.js`.* Every parallel route slot needs a `default.js` (return `null` or call
`notFound()`). In the scratch test a slot without one built successfully, and the request that did not match the slot
answered 404; adding `default.tsx` returning `null` made the same request answer 200. The upgrade guide says builds fail
without it, so treat the file as required (see xref:web/nextjs/parallel-and-intercepting-routes.adoc[Parallel &
Intercepting Routes]).
* *`next/image` defaults.* `minimumCacheTTL` went from 60 seconds to 4 hours; `16` left the default `imageSizes`;
`qualities` defaults to `[75]`; local IPs are blocked unless `dangerouslyAllowLocalIP` is set; `maximumRedirects`
defaults to 3; local images with a query string need `localPatterns` with a `search` entry. `next/legacy/image` and
`images.domains` are deprecated; use `next/image` and `remotePatterns`. See
xref:web/nextjs/images-fonts-and-scripts.adoc[Images, Fonts & Scripts].
* *Dev and build directories.* `next dev` writes to `.next/dev`, so `dev` and `build` can run at the same time, and a
lockfile prevents two `next dev` or two `next build` processes on one project.
* *ESLint flat config.* `@next/eslint-plugin-next` defaults to the flat config format.
* *Scroll behaviour.* Next.js no longer overrides a global `scroll-behavior: smooth` during navigation; add
`data-scroll-behavior="smooth"` to `<html>` to get the old override.
* *Navigation.* The prefetch and navigation layer was rewritten (layout deduplication, incremental prefetching): more,
smaller prefetch requests with no code changes.
* *`next dev` config load.* The config file is no longer loaded by the `next dev` launcher, so a check such as
`process.argv.includes('dev')` in `next.config.js` returns `false`; check `NODE_ENV` or the config `phase` instead.
* *Sass.* `sass-loader` 16 and the modern Sass API; Turbopack does not support the legacy `~` prefix in Sass imports.

*Also in 16.0.* React 19.2 features arrive through the bundled canary (`Activity`, `useEffectEvent`,

server lets coding agents inspect a running app; `unstable_` prefixes were dropped from stabilised APIs; and the first
alpha of the Build Adapters API appeared (stable in 16.2). `Link` with `legacyBehavior` was announced for removal in 16
by the 15.5 deprecation notices, but a page using `<Link passHref legacyBehavior><a>…</a></Link>` still built without an
error on Next.js 16.3.8 in the scratch project. It is deprecated, not working-by-design: remove it with the `new-link`
codemod. The tools for all of this are in the next sections; the details of Turbopack and the compiler are on
xref:web/nextjs/turbopack-and-the-compiler.adoc[Turbopack & the Compiler].

Source: https://nextjs.org/blog/next-16[Next.js 16] and https://nextjs.org/blog/next-15-5[Next.js 15.5]

[#v16-minors]
=== Next.js 16.1, 16.2 and 16.3: The Minors

The minor releases of 16 carry no breaking change for a project already on 16.0, but several of them change behaviour
by default, and several are experiments whose names changed between minors. Anyone reading a post or a prompt from one
month may find the name different in the next.

.What each 16.x minor added, and what was still experimental or opt-in
[cols="1,3,2",options="header"]
|===
| Version | Added | Status to check

| 16.1 (2025-12-18)
| Turbopack file-system caching for `next dev` is stable and on by default; the `next upgrade` command; `next
experimental-analyze` (an interactive bundle analyzer for Turbopack); `next dev --inspect`; Turbopack externalises
transitive `serverExternalPackages`; the DevTools MCP gains a `get_routes` tool.

| 16.2 (2026-03-18)

| 16.3 (2026-08-03)

Source: https://nextjs.org/blog/next-16-1[Next.js 16.1], https://nextjs.org/blog/next-16-2[Next.js 16.2] and https://nextjs.org/blog/next-16-3[Next.js 16.3]

A few of these renamed or moved between minors, and the names matter when following older material:

* *`catchError`.* In 16.2 it shipped as `unstable_catchError()` with an `unstable_retry()` callback (and an
`unstable_retry` prop for `error.tsx`). In 16.3 the stable names are `catchError` and `retry`, imported from
`next/error`. The `remove-unstable-prefix` codemod (checked in its source) renames only `unstable_cacheLife` and
`unstable_cacheTag`, so rename this one by hand.
* *`next/root-params`.* Version 16.0 removed `unstable_rootParams` and promised an alternative in a minor release;
that alternative is `next/root-params`, which arrived in 16.3. It works in Server Components (and inside `use cache`
scopes) but not yet in Route Handlers or Server Actions.
* *Adapters.* The alpha of 16.0 read `experimental.adapterPath`; 16.2 made `adapterPath` a stable top-level option.
* *Bundle analysis.* `next experimental-analyze` (16.1) replaces `@next/bundle-analyzer` for Turbopack projects, and it
is experimental by name and by status.
* *File-system caching.* Dev caching was stable in 16.1; the build cache and memory eviction became defaults in 16.3
(see xref:web/nextjs/turbopack-and-the-compiler.adoc[Turbopack & the Compiler]).
* *Agents.* The DevTools MCP is from 16.0 and `get_routes` from 16.1; bundled docs are from 16.2 and the `AGENTS.md`
block that `next dev` maintains is from 16.3.

[#workflow]
=== A safe order for an upgrade

The commands above combine into a routine that works for one major at a time. Skipping versions is possible (the 16
guide is written for 15), but each guide assumes the previous one was applied, and the two compatibility periods of
Next.js (synchronous request APIs in 15, `middleware` in 16) are easiest to leave one at a time.

. Commit everything and create a branch; the codemods refuse to run on a dirty tree.
. Upgrade to the latest patch of the *current* major first (`npx @next/codemod upgrade patch`), so that the deprecation
warnings of the current version are visible.
. Read the upgrade guide of the next major from top to bottom once; most steps are one paragraph.
. Run `npx next upgrade` (16.1+) or `npx @next/codemod@canary upgrade latest`, answer the prompts, and review the diff
of `package.json` and the lockfile on its own.
. Run `npx @next/codemod@latest next-async-request-api .` when the project still reads request APIs synchronously, then
`npx next typegen` and replace hand-written `params` types by `PageProps`, `LayoutProps` and `RouteContext`.
. Fix `next.config` by hand: `turbopack` at the top level, removed keys, `images` defaults, and the
`cacheComponents` decision. Keep `cacheComponents` off until the rest builds.
. Run `next build`. Type errors and the validator messages shown in this page are the checklist; fix, rebuild, repeat.
. Run the test suite and a production-mode smoke test (`next start`, then `curl` or the end-to-end suite), because
caching defaults changed silently between 14 and 15: code that relied on a cached `fetch` is now slower, not broken.
. Only then adopt the new features (Cache Components, Partial Prefetching, the React Compiler) one at a time.

The same upgrade can be handed to a coding agent: the version 16 guide ships a prompt that asks the agent to set up
version-matched docs first (`npx @next/codemod@canary agents-md`, or the bundled docs and `AGENTS.md` block that
Next.js 16.2 and 16.3 maintain), run the codemod, explain the plan, and verify the result with the dev tools.

Source: https://nextjs.org/docs/app/guides/upgrading/version-16#use-an-ai-agent-recommended[Upgrading to version 16: use an AI agent] and https://nextjs.org/docs/app/guides/ai-agents[AI coding agents]

[#migrate-spa]
== Migrating from Create React App and Vite

Both official guides use the same incremental strategy: first make the existing single-page app run inside Next.js as
a client-only application, unchanged, then adopt Next.js features route by route. The motivation the guides give is the
usual list (a client-only app downloads all its code before it can fetch data, which causes waterfalls; Next.js adds
automatic code splitting, streaming, server-side data fetching, the Proxy and the built-in optimisations). Nothing
about the first step needs React Server Components. The two guides are at
https://nextjs.org/docs/app/guides/migrating/from-create-react-app[Create React App] and
https://nextjs.org/docs/app/guides/migrating/from-vite[Vite]; Create React App is no longer maintained, so that guide
is the one most older projects need.

[#cra]
=== From Create React App

The steps of the guide, applied to a small Create React App style project (a `src/App.tsx` with state, an image import
and a `REACT_APP_` variable), were:

. Install Next.js (`npm install next@latest`).
. Create `next.config.ts` with `output: 'export'` and `distDir: 'build'`.
. Create `app/layout.tsx`: the `<html>`, `<head>` and `<body>` of `public/index.html` become the root layout, and the
`div#root` becomes `<div id="root">\{children}</div>`.
. Move the title and description into the Metadata API, and drop the `charset` and `viewport` tags (Next.js adds them).
. Import global CSS from the layout.
. Create the entry page as an optional catch-all route, `app/[[...slug]]/page.tsx`, with `generateStaticParams`
returning `[{ slug: [''] }]`.
. Add a client-only entrypoint, `app/[[...slug]]/client.tsx`, that loads the old `App` with `next/dynamic` and
`ssr: false`.
. Change image imports (they return an object; use `logo.src` or the `Image` component).
. Rename `REACT_APP_` variables to `NEXT_PUBLIC_`.
. Update the `package.json` scripts and `.gitignore`, then clean up `public/index.html`, `src/index.tsx`,
`react-scripts` and the `reportWebVitals` setup.

the `proxy` field of `package.json` becomes a `rewrites` entry in `next.config.ts`, a custom webpack or Babel
configuration needs `--webpack` (or a Turbopack equivalent), and `next-env.d.ts` must be in `tsconfig.json`'s `include`.
Next.js uses Turbopack by default, whereas Create React App used webpack; `next dev --webpack` is the closest match.

[#vite]
=== From Vite

The Vite guide has the same shape (steps 1 to 9) with these differences from the Create React App one:

* `next.config.mjs` uses `distDir: './dist'`;
* `tsconfig.json` needs nine specific changes (remove the project reference to `tsconfig.node.json`, add
`./dist/types/**/*.ts` and `./next-env.d.ts` to `include`, the `next` plugin, `esModuleInterop`, `jsx: react-jsx`,
`allowJs`, `forceConsistentCasingInFileNames`, `incremental`);
* the layout replaces `index.html`, the entry page replaces `main.tsx`;
* environment variables change prefix from `VITE_` to `NEXT_PUBLIC_`;
* Turbopack supports `import.meta.env.MODE`, `DEV`, `PROD`, `BASE_URL` and `SSR` without changes (`BASE_URL` follows
`basePath` and has a trailing slash), but not custom `VITE_*` variables, Vite modes, `envPrefix` or `envDir`;
* Turbopack supports `import.meta.glob` (16.3) with no changes, except that the Vite 5 `as` option (deprecated) is
replaced by `query`, and `import.meta.globEager` is not supported (use `{ eager: true }`).

The two Vite APIs were exercised in the migrated SPA of the previous section by replacing `App.tsx` with a component that
globs three TypeScript modules and prints `import.meta.env.MODE`.

.import.meta.glob and import.meta.env in a client-only Next.js SPA
[source,tsx]
----
// src/App.tsx
const notes = import.meta.glob('./notes/*.ts', { eager: true })

export default function App() {
  return (
    <ul>
      {Object.entries(notes).map(([path, mod]) => (
        <li key={path}>
          {path}: {(mod as { default: string }).default}
        </li>
      ))}
      <li>mode: {import.meta.env.MODE}</li>
    </ul>
  )
}
----

Built with `next build` (Turbopack) and opened from the same static server, the page listed `./notes/a.ts: first note`,
`./notes/b.ts: second note` and `mode: production`. A `.txt` glob failed with "Unknown module type" because Turbopack
needs a registered loader for file types it does not know (the 16.3 post makes the same point for `.md`); and the
eager result is typed `Record<string, unknown>`, so the cast above is needed.

Source: https://nextjs.org/docs/app/guides/migrating/from-vite[Vite guide] and https://nextjs.org/docs/app/api-reference/turbopack#importmetaglob[Turbopack: import.meta.glob]

After either migration the guides' "next steps" are the same: move from React Router to the App Router (see
xref:web/nextjs/routing-fundamentals.adoc[Routing Fundamentals] and
xref:web/nextjs/client-side-rendering.adoc[Client-Side Rendering] for the single-page-app mode this leaves you in),
then adopt `next/image`, `next/font`, `next/script` and the ESLint config
(xref:web/nextjs/images-fonts-and-scripts.adoc[Images, Fonts & Scripts]). The migration that starts from an existing
Pages Router application, as opposed to a single-page app, is the incremental

[#errata]
== Errata and Bad Practices Not to Reproduce

The books also contain faults that are not a matter of age. They are collected here with the correct form of each, so
that nobody copies them; the pages that teach the topic (data security, authentication, Route Handlers) repeat the
relevant one in context. The correct forms below follow the official documentation, and the ones that
could be shown as a short program were built and run in the scratch _Bookshelf_ app with `next build` and `next start
-p 3903`.

.Errata of the two books, and the correct form
[cols="1,3,4",options="header"]
|===
| # | Fault | Correct form

| 1
| *Secret exposed to the browser (Libby ch. 3 to 4, 7).* A Sanity *write* token stored as `NEXT_PUBLIC_SANITY_TOKEN`
with the build warning silenced, and the claim that `.env` keeps it private.
| Everything prefixed `NEXT_PUBLIC_` is inlined into the client JavaScript, wherever it is defined. Use an un-prefixed
variable read in server-only code, rotate any token that was ever shipped, and use a read-only token or none for
public reads. See xref:web/nextjs/data-security-and-csp.adoc[Data Security & CSP].

| 2
| *Secret exposed to the browser.* A Stripe secret key named `NEXT_PUBLIC_STRIPE_SECRET_KEY`.
| Only the publishable key may use the prefix. The secret key stays in a server-only variable and a `server-only` module.

| 3
| *Price tampering (Libby ch. 4, 7).* Checkout `line_items` are built from the cart posted by the client and its prices;
quantities are not validated (missing in both books).
| The client sends product ids and quantities only. The server looks the price up by id and validates the quantity. The
Route Handler below was run.

| 4
| *Payment fulfilment (both books).* The success redirect is treated as proof of payment.
| The redirect proves nothing. Fulfil an order from the payment provider's signed webhook, verified on the raw body,
answered quickly and idempotent. See xref:web/nextjs/route-handlers-and-backend-for-frontend.adoc[Route Handlers & Backend for Frontend].

| 5
| *Injection.* The slug is interpolated into a GROQ query (Libby ch. 3).
| Pass the slug as a query parameter of the CMS client (a GROQ query uses `$slug` and the client takes the value
separately) instead of concatenating it into the query string, and validate it first, as in item 6.

| 6
| *Injection and open proxy (Riva ch. 4).* An unvalidated path segment is interpolated into an upstream URL, and the API
route forwards whatever it is given.
| Validate the segment against a strict pattern, build the upstream URL from a fixed host, and look the resource up by
id. Run below.

| 7
| *Auth (Riva ch. 12, Libby ch. 12).* A hard-coded JWT secret and hard-coded credentials.
| Secrets come from environment variables (placeholders in the repository, real values in the hosting provider);
credentials come from a user store with hashed passwords, or from an identity provider.

| 8
| *Auth.* No token expiry, and a cookie without `secure` or `sameSite`.
| Set `httpOnly`, `secure`, `sameSite` and an expiry (`maxAge`). Run below.

| 9
| *Auth.* An uncaught `jwt.verify` error, so a tampered cookie produces a 500.
| Treat a failed verification as "not signed in": catch the error and return a 401 or a redirect to sign-in.

| 10
| *Auth.* Pages protected only by client-side hooks (`useAuth`, `useSession`).
| A client hook hides UI; it protects nothing. Authorise on the server, in the Server Component, Route Handler or
Server Action that reads the data, and use the Proxy only as an optimistic first check. See
xref:web/nextjs/authentication-and-authorization.adoc#errata[Authentication & Authorization].

| 11
| *Auth.* `NEXTAUTH_SECRET` omitted from the initial setup.
| Auth.js v5 needs `AUTH_SECRET` (and `AUTH_TRUST_HOST` behind a proxy, or on localhost with `next start`), and the
NextAuth v4 setup of the books needed `NEXTAUTH_SECRET`. Generate a random value, keep it in the environment, and set
it before the first sign-in.

| 12
| *Other.* `useEffect(async () => ...)` with no abort (Riva ch. 4).
| An effect callback must be synchronous (it may return only a cleanup function). Put the async work in an inner function and abort the request in the cleanup. Built below.

| 13
| *Other.* A root-run, single-stage Dockerfile without a `.dockerignore` that copies `.env*` (Riva ch. 11).
| A multi-stage build, a non-root user, and a `.dockerignore` that excludes `.env*`, `.git` and `node_modules`. The
deployment pages of this section show the Next.js specific parts.

| 14
| *Other.* `req.headers.origin` used to build redirect URLs (Libby ch. 4).
| The header is controlled by the caller. Build the redirect from a fixed base URL in configuration, a relative path, or
an allow-list. Run below.

| 15
| *Other.* The claims that `generateMetadata` needs TypeScript and that the App Router is unsuitable (Libby ch. 8).
| Neither is true. `generateMetadata` works in plain JavaScript files (run below), and the App Router is the default for
new Next.js applications.
|===

.Errata 3: prices read on the server by id, quantities validated (`app/api/quote/route.ts`)
[source,ts]
----
import { z } from "zod";
import { getBook } from "@/lib/books";

// The client sends ids and quantities only; prices never come from the request.
const Cart = z.object({
  items: z.array(z.object({ id: z.string(), quantity: z.number().int().min(1).max(10) })).min(1),
});

export async function POST(request: Request) {
  const parsed = Cart.safeParse(await request.json().catch(() => null));
  if (!parsed.success) {
    return Response.json({ error: "invalid cart" }, { status: 400 });
  }
  const lines = [];
  for (const { id, quantity } of parsed.data.items) {
    const book = await getBook(id);
    if (!book) return Response.json({ error: `unknown book ${id}` }, { status: 400 });
    lines.push({ id, quantity, unitCents: book.priceCents });
  }
  const totalCents = lines.reduce((sum, l) => sum + l.unitCents * l.quantity, 0);
  return Response.json({ lines, totalCents });
}
----

    const controller = new AbortController();
    // The effect callback itself stays synchronous; the async work lives inside it.
    async function load() {
      try {
        const res = await fetch("/api/books", { signal: controller.signal });
        setCount((await res.json()).length);
      } catch (error) {
        if ((error as Error).name !== "AbortError") throw error;
      }
    }
    load();
    return () => controller.abort();
  }, []);

  return <p>{count === null ? "Loading…" : `${count} books`}</p>;
}
----

The component was compiled and type-checked by `next build`, and the server-rendered HTML contained `Loading…`; the
effect itself runs only in the browser. The React side of the rule is on the
xref:web/react/effects.adoc[Effects] page.

Source: https://react.dev/reference/react/useEffect#fetching-data-with-effects[useEffect: fetching data with Effects]

[#pitfalls]
== Upgrade Pitfalls

.Symptoms after an upgrade, and the usual cause
[cols="3,4",options="header"]
|===
| Symptom | Usual cause

| `Property 'get' does not exist on type 'Promise<ReadonlyRequestCookies>'`
| A synchronous `cookies()` or `headers()` call from before 15. Run `next-async-request-api`.

| `Expected 2 arguments, but got 1` on `revalidateTag`
| The 16 signature; add a profile such as `'max'`, or use `updateTag` in a Server Action.

| `next build` fails with "This build is using Turbopack, with a `webpack` config"
| A `webpack` function, often added by a plugin. Add `turbopack: {}`, migrate the config, or pass `--webpack`.

| `Unrecognized key(s) in object: 'turbopack' at "experimental"`
| The key moved to the top level in 16.

| `Route segment config "instant" requires nextConfig.cacheComponents`
| The `cache-components-instant-false` codemod ran while `cacheComponents` is off.

| `Module not found: Can't resolve 'next/amp'`
| AMP was removed in 16.

| `ssr: false is not allowed with next/dynamic in Server Components`
| Move the `dynamic()` call into a Client Component.

| A parallel route slot returns 404 on a hard refresh
| The slot has no `default.js` (required in 16).

| `next lint` prints "Invalid project directory ... lint"
| The command was removed in 16; use `eslint .` (codemod `next-lint-to-eslint-cli`).

| Slower pages after upgrading from 14 to 15
| `fetch` and GET handlers are no longer cached; add `cache: 'force-cache'`, `dynamic = 'force-static'` or `use cache`.

| More, smaller prefetch requests after upgrading to 16
| The routing and prefetching rewrite (layout deduplication, incremental prefetching), expected by design.
|===

Source: https://nextjs.org/docs/messages/invalid-next-config[invalid-next-config] and the upgrade guides in the references

[#summary]
== Summary

* The big changes by version: 13 (the App Router), 14 (Server Actions stable, `next export` removed), 15 (async request
APIs, uncached by default, React 19), 16 (Turbopack default, `proxy.ts`, Cache Components, synchronous APIs and several
features removed) and 16.1 to 16.3 (stable dev cache, Adapters, `catchError`, `next/root-params`, Instant Navigations
opt-in).
* `npx next upgrade` (16.1 and later) or `npx @next/codemod@canary upgrade latest` upgrades the packages and runs the
recommended codemods, but not all of them: run `next-async-request-api` by hand, fix `next.config` and `revalidateTag`
manually, and accept `cache-components-instant-false` only when adopting Cache Components.
* Create React App and Vite apps move to Next.js as a client-only catch-all page with `output: 'export'`, and then
adopt features route by route.
* `cacheComponents` and `partialPrefetching` remain opt-in in 16.3; the section teaches both caching models.
* Thirteen areas of the books are outdated and fifteen items are errata; the tables above list each with the correct
form and the page that teaches it.
