that the rest of this section grows; each example is followed by the official page it derives from, and every number,
header and log line quoted below is a real measurement from those runs.

"Caching" is not one thing in Next.js; it is a stack of independent layers, each with its own key, lifetime and way to
invalidate it. Most caching bugs come from invalidating one layer and forgetting the others.
xref:web/nextjs/incremental-static-regeneration.adoc[Incremental Static Regeneration] explains the
stale-while-revalidate loop and every revalidation API in depth, and
xref:web/nextjs/partial-prerendering-and-cache-components.adoc[Partial Prerendering and Cache Components] explains the
static shell and the prerender rules. This page is the map of all the layers: where each one lives, what it stores, how
it is keyed, when it expires, what clears it, and how to see what it is doing. The sibling pages on data fetching, on
Server Actions and mutations, and on Route Handlers and the backend for frontend of this section use these layers from
the calling side.

[#layers]
== The Layers at a Glance

A request for a page can be answered by up to five layers, from the closest to the user to the closest to the data. It
stops at the first layer that holds a fresh answer:

.The cache layers of Next.js in the previous model and with Cache Components
image::nextjs-cache-layers.svg["A diagram with two stacks of layers between the browser and the data source. The previous model stack, top to bottom: the browser HTTP cache and CDN; the client router cache (dynamic page segments 0 seconds since 15, static 300 seconds, tuned with staleTimes); the Full Route Cache (HTML and RSC payload of prerendered routes, controlled by the dynamic, revalidate and fetchCache segment config); the Data Cache (fetch with force-cache, next.revalidate and next.tags, and unstable_cache, surviving deployments); request memoization (one render pass). The Cache Components stack: the browser HTTP cache and CDN; the client cache (cacheLife stale, minimum 30 seconds, and the only home of use cache private results); prerendered shells and route entries; use cache entries in a cache handler (in-memory LRU by default, a shared store for use cache remote, not kept across deployments); the unchanged fetch Data Cache as a separate layer; request memoization. Both stacks end at the data source.",width=1000,role=text-center]

[cols="2,3,3,3,2",options="header"]
|===
| Layer | Where it lives and what it stores | Key and lifetime | Cleared or refreshed by | Survives a deploy

| Request memoization (both models)
| The memory of one server render pass: the results of identical `GET` `fetch` calls and of `React.cache` functions.
| The URL and options of the call, or the arguments of the cached function. Lasts until the response is sent.
| Nothing: it is gone when the render ends.
| No

| Data Cache (previous model; still present with Cache Components)
| The server: `fetch` responses cached with `cache: 'force-cache'` or `next.revalidate`, and `unstable_cache` results.
| URL, method, headers and body for `fetch`; key parts plus arguments for `unstable_cache`. `next.revalidate` or `revalidate`, otherwise indefinite.
| `revalidateTag`, `updateTag`, `revalidatePath`, time.
| Yes

| Full Route Cache (previous model)
| The server: the HTML and the RSC payload of every prerendered route (built or generated on demand).
| The route. The `revalidate` segment config, the lowest value across the layouts and the page; otherwise one year.
| `revalidatePath`, tags of the data the route read, time.
| No: every build seeds its own

| Client router cache (previous model)
| The browser tab's memory: RSC payloads of layouts, loading boundaries and page segments.
| The route segment. `staleTimes.static` 300 s, `staleTimes.dynamic` 0 s (15 and later).
| Reload, `router.refresh()`, a Server Action that revalidates or sets cookies, time.
| Not applicable (per tab)

| Prerendered shells and route entries (Cache Components)
| The server or a CDN: the static shell (HTML and RSC payload) of each route, and the concrete pages ISR adds later.
| The route, including the known params. `revalidate` and `expire` of the `cacheLife` profiles used inside it.
| `revalidatePath`, `revalidateTag`, `updateTag` for the tags used in the shell, time.
| No

| `'use cache'` entries (Cache Components)
| The cache handler: an in-memory LRU per server instance by default, or the store you register for `'use cache: remote'`.
| Build id (or `deploymentId`), function id and the serialized arguments and captured variables. The `cacheLife` profile.
| `cacheTag` with `revalidateTag` or `updateTag`, time.
| No (the key contains the build id)

| Client cache (Cache Components)
| The browser tab's memory: the cached content of the RSC payloads of visited and prefetched routes, including `'use cache: private'` results.
| The route and its cached scopes. The `stale` time of the `cacheLife` profiles involved, at least 30 s.
| A Server Action that revalidates, `refresh()`, reload, time.
| Not applicable (per tab)

| Browser HTTP cache and CDN (both models)
| Outside Next.js: whatever the response headers allow a shared cache to keep.
| The URL (and the `rsc`-related headers and `_rsc` parameter). `s-maxage`, `stale-while-revalidate`.
| A purge call to the CDN; Next.js does not do it for you.
| Depends on the CDN
|===

Which model a project uses is one line in the config. Everything on this page that is not marked otherwise is true in
both:

[source,ts]
----
// next.config.ts
import type { NextConfig } from 'next'

const nextConfig: NextConfig = {
  cacheComponents: true, // omit (or false) for the previous model
}

export default nextConfig
----

`cacheComponents` and `partialPrefetching` are still opt-in in 16.3; the 16.3 release post says their behaviours
"will become the default in a future major version", so new projects can adopt Cache Components now and existing ones
can move route by route (see xref:web/nextjs/partial-prerendering-and-cache-components.adoc[Partial Prerendering and Cache Components]
for the migration).

[#lab]
== How the Examples Were Measured

A cache is invisible until the thing behind it is counted. The experiments of this page use a *lab* inside the scratch
app: a stand-in for the Bookshelf API (the "origin") that counts how often it is really called and returns the count with
a timestamp. Whenever a layer answers instead of the origin, the number stays the same.

.The origin: a Route Handler that counts its real calls (lib/source.ts and app/api/source/route.ts)
[source,ts]
----
// lib/source.ts
import "server-only";

// Stands in for a slow upstream (CMS, database, REST API): counts how often it is really hit.
const g = globalThis as unknown as { __origin?: Record<string, number> };

export function originHit(label: string) {
  g.__origin ??= {};
  const n = (g.__origin[label] = (g.__origin[label] ?? 0) + 1);
  console.log(`[origin] ${label} hit #${n}`);
  return { label, n, at: new Date().toISOString().slice(11, 23) };
}

export const ORIGIN = "http://localhost:3603/api/source";

export async function readOrigin(label: string, init?: RequestInit) {
  const res = await fetch(`${ORIGIN}?label=${encodeURIComponent(label)}`, init);
  return (await res.json()) as { label: string; n: number; at: string };
}
----

[source,ts]
----
// app/api/source/route.ts
import { connection } from "next/server";
import { originHit } from "@/lib/source";

// The "upstream": every real call increments a counter and returns it with a timestamp.
export async function GET(request: Request) {
  await connection();
  const label = new URL(request.url).searchParams.get("label") ?? "api";
  return Response.json(originHit(`api:${label}`));
}
----

Pages that prerender at build time have no running server to call, so for `next build` a short Node script stands in
for the origin on the same port (it prints `[origin] stub:... hit #1` for every build-time call). Each model has its own
folder of lab routes (`app/lab/...`), built and started with the same two commands:

[source,bash]
----
# previous model                                 # Cache Components
npm run build                                    CACHE_COMPONENTS=1 npm run build
PORT=3603 npm start                              CACHE_COMPONENTS=1 PORT=3603 npm start
----

where `next.config.ts` reads `CACHE_COMPONENTS` to set `cacheComponents`. The lab was always observed on a production
build (`next build` and `next start`), because `next dev` caches differently (<<debugging>>).

Source: https://nextjs.org/docs/app/api-reference/config/next-config-js/cacheComponents[cacheComponents],
https://nextjs.org/docs/app/api-reference/file-conventions/route[Route Handlers]

[#memoization]
== Request Memoization (Both Models)

The cheapest layer is the one you rarely configure. During one server render, identical `GET` `fetch` calls are
*memoized*: the layout, the page and `generateMetadata` can all ask for the same URL, and the request leaves the server
once. This is separate from persistent caching: the memo lives for one render pass and is gone when the response is
sent. For data that does not come from `fetch` (an ORM, a database driver, an SDK), React's `cache` function gives the
same per-render deduplication. Both are shown below with two components that need the same data.

.Two components, one origin call per render (app/lab/memo/page.tsx, previous model)
[source,tsx]
----
// app/lab/memo/page.tsx
import { cache } from "react";
import { connection } from "next/server";
import { originHit, readOrigin } from "@/lib/source";

// Not a fetch: React cache() deduplicates it for the duration of one render pass.
const countOnce = cache(async () => originHit("react-cache"));

async function Header() {
  const book = await readOrigin("memo", { cache: "no-store" }); // same URL and options ...
  const again = await countOnce();
  return <p>header: fetch n={book.n}, cache() n={again.n}</p>;
}

async function Footer() {
  const book = await readOrigin("memo", { cache: "no-store" }); // ... so this reuses the answer
  const again = await countOnce();
  return <p>footer: fetch n={book.n}, cache() n={again.n}</p>;
}

export default async function Page() {
  await connection();
  return (
    <>
      <Header />
      <Footer />
    </>
  );
}
----

Each request to `/lab/memo` prints one `api:memo` and one `react-cache` line in the server log, although `fetch` and
`countOnce()` are called twice:

[source,text]
----
$ curl localhost:3603/lab/memo        # header and footer render the same numbers
header: fetch n=1, cache() n=1 | footer: fetch n=1, cache() n=1
$ curl localhost:3603/lab/memo        # a second request is a new render pass
header: fetch n=2, cache() n=2 | footer: fetch n=2, cache() n=2
----

The same page under `cacheComponents` (the `connection()` call moves into a component under `<Suspense>`, as the
prerender rules require) printed the same numbers, so memoization does not depend on the model. Four rules:

* Memoization applies to `GET` requests with the same URL and options in the same render pass. It also covers
  `generateStaticParams`, `generateMetadata` and `generateViewport`.
* It does not apply in Route Handlers, which are not part of the React tree.
* Passing an `AbortController` `signal` to `fetch` opts that call out.
* Inside `'use cache'`, `React.cache` has its own isolated scope: a value stored by `React.cache` outside a cached
  function is not visible inside it, and calls from two separate cached functions do not share one result.

Because memoization lives for a single render, it is the layer that makes "fetch where you need it" cheap: put the data
call in the component that uses it instead of passing props down.

Source: https://nextjs.org/docs/app/api-reference/functions/fetch#memoization[fetch: Memoization],
https://nextjs.org/docs/app/guides/caching-without-cache-components#deduplicating-requests[Deduplicating requests],
https://react.dev/reference/react/cache[React: cache]

[#previous-model]
== The Previous Model

This is what runs when `cacheComponents` is not set. The mental model is a *default of "dynamic where the code needs
it, static where it can"*: a route is prerendered at build time unless something in it needs the request (`cookies()`,
`headers()`, `searchParams`, an uncached `fetch` after one of them, `connection()`), and data is cached only where you say so.

[#fetch-cache]
=== `fetch` and the Data Cache

Next.js extends `fetch` so that each call on the server can set its own persistent cache and revalidation. The `cache`
option decides whether the server-side Data Cache is used:

[cols="2,5",options="header"]
|===
| Option | Behaviour (16.3)

| none (the default, called `auto no cache`)
| Not cached. Fetched on every request in development, once during `next build` if the route is prerendered, and on every request if a request-time API is used on the route.

| `cache: 'no-store'`
| Fetched on every request, even without a request-time API; the route becomes dynamic.

| `cache: 'force-cache'`
| Looked up in the Data Cache. A request matches on URL, method, headers and body. A fresh match is returned; a missing or stale match fetches again and stores the response. Only `200` responses are stored.

| `next: { revalidate: false \| 0 \| n }`
| Cache lifetime in seconds. `false` means indefinitely, `0` means do not cache, `n` means at most `n` seconds. If two calls in one route differ, the lower value wins, and a value lower than the route's `revalidate` lowers the route's interval.

| `next: { tags: ['books'] }`
| Labels for on-demand invalidation with `revalidateTag`. At most 128 tags of 256 characters.
|===

Combining options that contradict each other, such as `{ revalidate: 3600, cache: 'no-store' }`, is not allowed: both are
ignored and development prints a warning. The next example reads the origin four ways in one render; the page calls
`connection()` first so it renders per request, which lets us watch the Data Cache without a Full Route Cache in front:

.Four ways to call the origin (app/lab/fetch/page.tsx, previous model)
[source,tsx]
----
// app/lab/fetch/page.tsx
import { connection } from "next/server";
import { readOrigin } from "@/lib/source";

export default async function Page() {
  await connection(); // render per request, so we can watch the data cache on its own
  const [plain, forced, timed, tagged] = await Promise.all([
    readOrigin("plain"), // no option: not cached in Next.js 15 and 16
    readOrigin("force-cache", { cache: "force-cache" }),
    readOrigin("revalidate-5", { next: { revalidate: 5 } }),
    readOrigin("tagged", { cache: "force-cache", next: { tags: ["books"] } }),
  ]);
  return <pre>{JSON.stringify({ plain, forced, timed, tagged }, null, 2)}</pre>;
}
----

Time-based revalidation and tag-based revalidation are both stale-while-revalidate: the first caller after the
invalidation gets the old answer, never a wait. The exception is `{ expire: 0 }` (<<invalidation>>).

A plain `fetch` in a page with no request-time API behaves differently: the route is prerendered, so the fetch runs once
at build time (the build log shows `[origin] stub:... hit #1`) and its result is frozen into the Full Route Cache
(<<full-route-cache>>). That is why the same code can look "cached" in production and "fresh" in development.

Two further notes on the Data Cache. First, caching is strictly opt-in and includes `POST` requests and requests with
`authorization` or `cookie` headers; because a match includes the headers a per-user token gives per-user entries, but
the personalized response still sits in a *server-wide* store, so do not `force-cache` credentialed responses unless you
meant to. Draft Mode bypasses the cache entirely. Second, in development the HMR cache keeps `fetch` responses across hot
reloads (`serverComponentsHmrCache`), which is why an edit can seem not to refetch.

[#unstable-cache]
=== `unstable_cache` for Everything That Is Not a `fetch`

Database queries, ORM calls and SDK calls do not go through `fetch`, so they miss the Data Cache.
`unstable_cache(fn, keyParts, { tags, revalidate })` wraps such a function so that its result is stored in the same Data
Cache, with the same tags and the same stale-while-revalidate behaviour. The arguments and the stringified function are
already part of the key; `keyParts` is only needed when the function reads outside variables that are not passed as
arguments.

.Caching a non-fetch function (app/lab/unstable/page.tsx, previous model)
[source,tsx]
----
// app/lab/unstable/page.tsx
import { unstable_cache } from "next/cache";
import { connection } from "next/server";
import { originHit } from "@/lib/source";

// Persists across requests (and deployments) in the data cache, like a tagged fetch.
const getBookRow = unstable_cache(
  async (id: string) => originHit(`unstable-cache:${id}`),
  ["book-row"], // key prefix; the arguments are added to the key automatically
  { tags: ["books"], revalidate: 5 },
);

export default async function Page() {
  await connection();
  const [one, two] = await Promise.all([getBookRow("1"), getBookRow("2")]);
  return <pre>{JSON.stringify({ one, two })}</pre>;
}
----

The two arguments make two entries. Observed: request 1 returned `one=1 two=1` (both computed); a second request the
same second returned the same numbers; after `revalidateTag('books', 'max')` the next request still showed `1` and the one
after showed `2`, as for `fetch`; and six seconds later (the `revalidate: 5` had passed) a request showed the old
value and the next showed the refreshed one (`3`). Because it shares the tag `books` with the tagged `fetch` of the
previous example, one `revalidateTag('books', ...)` call refreshed both.

Cookies, headers and other request data cannot be read inside the wrapped function; read them outside and pass the
values in. The name is historical: `unstable_cache` was introduced in 14.0 and, as of 16, the official docs mark it as
*replaced* by `'use cache'`. It remains the way to cache a non-`fetch` function in the previous model, and it is also the
one that survives deployments (see <<cc-and-data-cache>>).

Source: https://nextjs.org/docs/app/api-reference/functions/unstable_cache[unstable_cache],
https://nextjs.org/docs/app/guides/caching-without-cache-components#unstable_cache-for-non-fetch-functions[unstable_cache for non-fetch functions]

[#full-route-cache]
=== The Full Route Cache and the Segment Config

The Full Route Cache is the server-side store of prerendered routes: for every route that has no request-time
dependency, `next build` stores the HTML and the RSC payload, and ISR regenerates them later (see
xref:web/nextjs/static-site-generation.adoc[Static Site Generation] and
xref:web/nextjs/incremental-static-regeneration.adoc[Incremental Static Regeneration]). You steer it with three
route segment config exports from a page, layout or Route Handler:

[cols="2,5",options="header"]
|===
| Export | Values and effect

| `dynamic`
| `'auto'` (default: cache as much as possible without blocking dynamic behaviour); `'force-dynamic'` (render per request, like every `fetch` being `{ cache: 'no-store', next: { revalidate: 0 } }`); `'error'` (fail the build if anything is dynamic, like `getStaticProps`); `'force-static'` (prerender and make `cookies()`, `headers()` and `useSearchParams()` return empty values).

| `revalidate`
| `false` (default, cache indefinitely), `0` (always dynamic), or a number of seconds. It must be statically analyzable (`600`, not `60 * 10`). The lowest value across the layouts and the page of a route wins, and it does not override `next.revalidate` of individual fetches.

| `fetchCache`
| An advanced override of the default `cache` of every fetch in a segment: `'auto'`, `'default-cache'`, `'only-cache'`, `'force-cache'`, `'force-no-store'`, `'default-no-store'`, `'only-no-store'`. The `only-*` values throw when a fetch contradicts them; `force-*` wins over `only-*` across the segments of one route; a parent cannot use `'default-no-store'` if a child uses `'auto'` or a `*-cache` value.
|===

Seven small pages show what each one does. Each reads the origin once with `fetch`:

.A page with no request-time dependency (app/lab/frc-static/page.tsx)
[source,tsx]
----
// app/lab/frc-static/page.tsx
import { readOrigin } from "@/lib/source";

// No request-time API anywhere: prerendered at build time into the Full Route Cache.
export default async function Page() {
  const book = await readOrigin("frc-static");
  return <p>static: origin n={book.n} at {book.at}</p>;
}
----

[source,tsx]

route stayed prerendered and served the build-time value on 16.3.8, although the docs say `force-no-store` makes every
fetch re-fetch "even if they provide a `'force-cache'` option". Treat the combination as unreliable and do not mix
`fetchCache` with per-call `cache` options; use one mechanism per route. A `fetchCache = 'only-cache'` segment that
contains `cache: 'no-store'` fails the build with `Error: cache: 'no-store' used on fetch for ... with 'export const
fetchCache = 'only-cache'`.

request regenerates *both* the HTML and the RSC payload together, so a page load and a client navigation never disagree.

[#stale-times]
=== The Client Router Cache and `staleTimes`

The browser keeps its own cache of RSC payloads, so that moving between pages sends only the segments that changed and
back and forward buttons are instant (xref:web/nextjs/linking-and-navigation.adoc[Linking and Navigation] shows how
`<Link>` prefetching feeds it). Its lifetime is the one cache setting most people have never touched. In the previous
model the defaults since 15 are:

* *Dynamic* pages (not statically generated and not fully prefetched): `staleTimes.dynamic` = 0 seconds, so every click on a
  link requests the page again. In 14 the value was 30 seconds.
* *Static* pages, or links with `+prefetch={true}+`: `staleTimes.static` = 5 minutes.
* Layouts and `loading` boundaries are still reused, because only the segment that changes is requested.
* Back and forward navigation restores the entry regardless, to keep scroll position and avoid layout shift.

`staleTimes` is the option to change them. The docs still label it *experimental*, so it sits under `experimental` in 16.3:

[source,ts]
----
// next.config.ts (previous model)
import type { NextConfig } from 'next'

const nextConfig: NextConfig = {
  experimental: {
    staleTimes: {
      dynamic: 30, // seconds
      static: 180,
    },
  },
}

export default nextConfig
----

Observed with a headless Chrome (Playwright) clicking a `<Link>` to a dynamic page three times, going back in between,
and counting the RSC requests each click sent:

[cols="3,1,1,1",options="header"]
|===
| Build | Click 1 | Click 2 | Click 3

| defaults (`dynamic: 0`)
| 1 request
| 1 request
| 1 request

| `staleTimes: { dynamic: 30, static: 180 }`
| 1 request
| 0 requests
| 0 requests

The same link with `+prefetch={false}+` was requested on every click in both builds in my runs, so do not rely on
`staleTimes.dynamic` for links that opt out of prefetching. A Server Action that calls `revalidatePath`, `revalidateTag`,
`updateTag` or `refresh`, and any change of cookies in a Server Action, clears the *whole* client cache regardless
of the stale time, and `router.refresh()` clears the current route.

[#cache-components]
== Cache Components

This is what runs when `cacheComponents: true`. The default flips: *everything that needs data at request time is dynamic,
and you choose what to cache*, at the level of a function, a component or a whole file, with the `'use cache'` directive.
Next.js prerenders a static shell (HTML plus RSC payload) from everything that can finish at build time, including the
results of cached functions, and streams the rest behind `<Suspense>` boundaries (Partial Prerendering, the subject of
xref:web/nextjs/partial-prerendering-and-cache-components.adoc[Partial Prerendering and Cache Components]). The route
segment config of the previous model is replaced: a route that exports `dynamic`, `revalidate` or `fetchCache` fails the
build (the exact message is in <<use-cache>>); `cacheLife` and `cacheTag` take over the lifetime and invalidation roles.

.A static shell, a cached part and a live part on one page (app/lab/shell/page.tsx, Cache Components)
[source,tsx]
----
// app/lab/shell/page.tsx
import { Suspense } from "react";
import { connection } from "next/server";
import { cacheLife, cacheTag } from "next/cache";
import { readOrigin } from "@/lib/source";

async function Catalogue() {
  "use cache";
  cacheLife("hours"); // stale 5 min, revalidate 1 h, expire 1 day
  cacheTag("catalogue");
  const book = await readOrigin("shell-cached");
  return <p>cached catalogue: origin n={book.n} at {book.at}</p>;
}

async function Live() {
  await connection(); // request time: never cached, never in the shell
  const book = await readOrigin("shell-live");
  return <p>live: origin n={book.n} at {book.at}</p>;
}

export default function Page() {
  return (
    <>
      <h1>Shelf</h1>
      <Catalogue />
      <Suspense fallback={<p>loading live data</p>}>
        <Live />
      </Suspense>
    </>
  );
}

[#use-cache]
=== `'use cache'`: Forms, Keys and Restrictions

The directive caches the return value of an `async` function or component. It can sit at the top of a function body
(function or component level), or at the top of a file, where every export becomes a cached async function (including
`generateMetadata` and `generateStaticParams`, which must then be async). A `page` or `layout` file is a module like any
other, so a file-level directive caches that whole segment, and a cached layout does not cache the `children` it
renders, because slots pass through unread. A file with the directive at its top can have its exports imported into a
Client Component and called there, running on the server like a Server Function; prefer calling them on the server and
passing results down.

[#cache-keys]
==== What Makes Up the Key

The entry of a cached function is stored under a key built from:

. the *build id* (or the `deploymentId` when one is configured, which overrides it), so a new build invalidates everything
. the *function id*, a secure hash of the function's location and signature
. the *serialized arguments*: props of a component, parameters of a function
. in development only, an *HMR refresh hash*

A variable captured from an enclosing scope is bound as an argument automatically, so it becomes part of the key too.
Different inputs mean different entries; the same inputs mean one entry shared by every user and every request.

.Arguments and captured values are the key (app/lab/keys/page.tsx, Cache Components)
[source,tsx]
----
// app/lab/keys/page.tsx
import { Suspense } from "react";
import { cacheLife } from "next/cache";
import { readOrigin } from "@/lib/source";

async function getBook(id: string) {
  "use cache";
  cacheLife("lab"); // custom profile from next.config.ts: stale 30, revalidate 5, expire 60
  return readOrigin(`keys-book-${id}`); // the id argument is part of the cache key
}

async function Books({ searchParams }: { searchParams: Promise<{ id?: string; lang?: string }> }) {
  const { id = "1", lang = "en" } = await searchParams;

  // A value captured from the enclosing scope becomes part of the key as well.
  const getTitle = async () => {
    "use cache";
    cacheLife("lab");
    return readOrigin(`keys-title-${id}-${lang}`);
  };

  const [a, b, title] = await Promise.all([getBook(id), getBook(id), getTitle()]);
  return <pre>{JSON.stringify({ first: a, second: b, title })}</pre>;
}

export default function Page(props: PageProps<"/lab/keys">) {
  return (
    <Suspense fallback={<p>loading</p>}>
      <Books searchParams={props.searchParams} />
    </Suspense>
  );
}
----

to watch):

| Request | Origin calls | What it shows

| `/lab/keys?id=1`
| `keys-book-1` 1, `keys-title-1-en` 1
| `first` and `second` of the same render share one call: the arguments are equal.

| `/lab/keys?id=1` again
| unchanged
| Served from the cache: same `n` and the same timestamp.

| `/lab/keys?id=2`
| `keys-book-2` 1, `keys-title-2-en` 1

| `/lab/keys?id=1&lang=es`

(<<http-caching>>), but I measured the entries of *runtime* `'use cache'` functions behaving like a time-to-live: once
`revalidate` had passed the call recomputed synchronously. Plan for a short pause at the first call after each
revalidate, not for an instant stale answer.

With `NEXT_PRIVATE_DEBUG_CACHE=1` the key is visible (<<debugging>>): it is a JSON array of the build id, the function
id and the list of arguments, for example `["BUILD_ID","8048...",[]]`.

==== Serialization

Arguments and return values must be serializable, with two different rules: arguments use the Server Components
serialization (stricter), return values the Client Components one. Supported arguments are primitives, plain objects,
arrays, `Date`, `Map`, `Set`, typed arrays and `ArrayBuffer`, and React elements *as pass-through only*; return values
add JSX. Class instances, functions (except pass-through), symbols, `WeakMap`, `WeakSet` and `URL` instances are not
supported. *Pass-through* means the cached function accepts a value it never reads: `children`, other slots and Server
Actions can flow through a cached component without becoming part of its key, which keeps a cached wrapper around dynamic
content valid:

.A cached wrapper around a dynamic child (app/lab/wrapper/page.tsx, Cache Components)
[source,tsx]
----
// app/lab/wrapper/page.tsx
import { Suspense, type ReactNode } from "react";
import { connection } from "next/server";
import { cacheLife } from "next/cache";
import { readOrigin } from "@/lib/source";

// children is passed through, never read: it does not become part of the cache key
async function CachedWrapper({ children }: { children: ReactNode }) {
  "use cache";
  cacheLife("hours");
  const book = await readOrigin("wrapper-cached");
  return (
    <section>
      <p>cached header: origin n={book.n} at {book.at}</p>
      {children}
    </section>
  );
}

async function Live() {
  await connection();
  const book = await readOrigin("wrapper-live");
  return <p>live child: origin n={book.n} at {book.at}</p>;
}

export default function Page() {
  return (
    <CachedWrapper>
      <Suspense fallback={<p>loading</p>}>
        <Live />
      </Suspense>
    </CachedWrapper>
  );
}

==== Restrictions and the Errors They Produce

A cached function runs in an isolated environment. Each restriction below was provoked in a scratch route and the error
copied from `next build`:

[cols="3,3",options="header"]
|===
| Mistake | Where it fails

| Reading `cookies()`, `headers()` or `searchParams` inside the cached scope, directly or through a helper
| `next build` for a prerendered route; at request time on a dynamic one, so it can pass the build and fail under `next start` (`next-request-in-use-cache`).

| A function marked `'use cache'` that is not `async`
| Compile time, in the bundler.

| A class instance as an argument
| When the cached function reads the object.

| `dynamic`, `revalidate` or `fetchCache` exported from a route
| Compile time, in the bundler.

| A short-lived cached function (`cacheLife('seconds')`) inside a cached function with no `cacheLife` of its own
| Prerendering (`nested-use-cache-no-explicit-cachelife`).

| A Promise of runtime data (for example `cookies()` without `await`) passed into a cached scope
| The build hangs for about 50 seconds and then fails with a cache-fill timeout (documented, see below).

| `connection()` inside a cached scope
| Not allowed in `'use cache'` or `'use cache: private'`: it provides connection-specific information that cannot be cached.
|===

The cache-fill timeout is described in the docs under the same heading as the others but was not reproduced in the lab: it
happens when a Promise created outside the scope (from `cookies()`, `params` or an uncached fetch) is passed in and
awaited inside it, because that Promise cannot resolve while the cache is being filled. Await the runtime value outside
and pass the plain value in.

In every case the cure is the same: read the request outside, pass a small plain value in. A cached function that
needs the signed-in user takes `userId` as an argument; the argument then *is* the cache key, which is also what keeps
one user's data out of another user's entry. Two more rules: when Draft Mode is on, every cached function re-executes
on every request and nothing is stored (reading `draftMode().isEnabled` inside is allowed, toggling it is not), and
`React.cache` inside a cached function is isolated from the outside (<<memoization>>).

The correct shape is the one of `recommendationsShared` in <<use-cache-private>>: the component reads the cookie, the cached
function receives its value as an argument, and the argument becomes part of the key.

[#cache-life]
=== `cacheLife`: Stale, Revalidate and Expire

Every cached scope has a lifetime with three numbers, in seconds. `stale` is how long the *client* may use the content
without asking the server. `revalidate` is how long the *server* serves it before a refresh is due (after that the next
request triggers a regeneration; for a route entry the old copy is served meanwhile). `expire` is the age after which
the server must regenerate synchronously. When both are set, `expire` must be longer than `revalidate`. Call
`cacheLife` inside the cached scope, once per call and never at module scope. The docs recommend setting it in every
`'use cache'` scope so that the lifetime is visible at the call site; without it the `default` profile applies.

[cols="2,3,2,2,2",options="header"]
|===
| Profile | Use case | `stale` | `revalidate` | `expire`

| `default`
| Standard content
| 5 minutes
| 15 minutes
| never

| `seconds`
| Real-time data
| 30 seconds
| 1 second
| 1 minute

| `minutes`
| Frequently updated content
| 5 minutes
| 1 minute
| 1 hour

| `hours`
| Several updates a day
| 5 minutes
| 1 hour
| 1 day

| `days`
| Daily updates
| 5 minutes
| 1 day
| 1 week

| `weeks`
| Weekly updates
| 5 minutes
| 1 week
| 30 days

| `max`
| Stable content that rarely changes
| 5 minutes
| 30 days
| 1 year
|===

I checked the values against the defaults compiled into `next@16.3.8` (`defaultConfig.cacheLife`); `default` has no
`stale` of its own and takes the 300 seconds of `staleTimes.static`. A profile can be used by name, as an inline object
(applies to that function only) or defined once in `next.config.ts`, where redefining a built-in name, `default`
included, is supported but surprising (`days` reads as 24 hours), so prefer your own names. Omitted properties of a
custom or inline profile inherit from `default`:

[source,ts]
----
// next.config.ts (Cache Components)
import type { NextConfig } from 'next'

const nextConfig: NextConfig = {
  cacheComponents: true,
  cacheLife: {
    // used above as cacheLife("lab")
    lab: { stale: 30, revalidate: 5, expire: 60 },
    editorial: { stale: 600, revalidate: 3600, expire: 86400 },
  },
}

export default nextConfig
----

[source,tsx]
----

  return readOrigin("profile-editorial");
}

  await connection();

      <Data />

for the second (`n=1` for all three), and `next build` accepted the mix of a built-in, an inline and a custom profile.

*Short lifetimes change where the result lives.* During prerendering, a cached scope with `revalidate: 0` or an `expire`
under 5 minutes is excluded from the shell and becomes a "dynamic hole" resolved at request time; a `stale` under 30 seconds
is excluded too, because a prefetch would expire before the user could click; a `stale` between 30 seconds and 5
minutes is included in the prerender but excluded from the route's App Shell. Of the presets only `seconds` crosses these
thresholds (its `expire` is 1 minute). Wrap holes in `<Suspense>`; the pages
xref:web/nextjs/partial-prerendering-and-cache-components.adoc[Partial Prerendering and Cache Components] and
xref:web/nextjs/streaming-and-suspense.adoc[Streaming & Suspense] cover how.

*Nested scopes.* An outer scope with an explicit `cacheLife` always keeps its own lifetime, longer or shorter than the
inner ones. An outer scope without one uses `default` (15 minutes) and a shorter inner lifetime lowers it, while a longer
one cannot extend it; a short-lived inner scope with no explicit outer `cacheLife` fails the prerender (the error above).
Set `cacheLife` explicitly everywhere.

[#cache-tag]
=== `cacheTag` and Invalidation by Tag

`cacheTag('a', 'b')` labels the entry of the enclosing cached scope; a single call accepts up to 128 tags of at most 256
characters (extra or longer tags are dropped or skipped with a console warning). Tags are idempotent and
case-sensitive, and may be computed from the data (`cacheTag('book', data.id)` after the fetch). The labels are what
`revalidateTag` and `updateTag` act on. Next.js also attaches *soft tags* to every entry, derived from the route
(`_N_T_/layout`, `_N_T_/books/layout`, `_N_T_/books/1`...), which is how `revalidatePath` reaches entries through the
same mechanism and what a custom cache handler receives as `softTags` in `get()`.

The invalidation API is small and the difference between its members is a choice about *who waits*:

[cols="2,3,3",options="header"]
|===
| Call | Where | Behaviour

| `updateTag(tag)`
| Server Actions only
| Expires the tag now: the next read waits for fresh data. Read-your-own-writes after a mutation.

| `revalidateTag(tag, 'max')`
| Server Actions and Route Handlers
| Marks the tag stale; the next request is served stale content while a refresh runs. The profile (`'max'` = one-year window, any `cacheLife` profile, or `{ expire: seconds }`) says how long stale content may still be served.

| `revalidateTag(tag, { expire: 0 })`
| Server Actions and Route Handlers
| Never serves stale: the next request blocks on fresh data. The one-argument form `revalidateTag(tag)` is deprecated and behaves like this.

| `revalidatePath(path, type?)`
| Server Actions and Route Handlers
| Invalidates the entries of a route (or a layout and below) through the soft tags.

| `refresh()`
| Server Actions only
| Refreshes the client router for the current page; does not touch the server caches.
|===

None of them can be called from a Client Component or from Proxy. A revalidation is triggered by the next *request*, not
by the call. The full treatment, including `revalidatePath` types and webhooks, is in
xref:web/nextjs/incremental-static-regeneration.adoc[Incremental Static Regeneration]; below are the two ways to call
them that every project needs. A Route Handler that a CMS webhook or a script can call, protected by a secret header:

.Revalidating by tag from a Route Handler (app/api/revalidate/route.ts, both models)
[source,ts]
----
// app/api/revalidate/route.ts
import { revalidateTag } from "next/cache";
import type { NextRequest } from "next/server";

export async function POST(request: NextRequest) {
  if (request.headers.get("x-revalidate-secret") !== process.env.REVALIDATE_SECRET) {
    return Response.json({ ok: false }, { status: 401 });
  }
  const tag = request.nextUrl.searchParams.get("tag");
  if (!tag) return Response.json({ ok: false }, { status: 400 });
  const expire = request.nextUrl.searchParams.get("expire");
  revalidateTag(tag, expire === "0" ? { expire: 0 } : "max");
  return Response.json({ ok: true, tag, expire: expire === "0" ? 0 : "max" });
}

[#use-cache-private]
=== `'use cache: private'`: Per-Browser Caching of Request-Dependent Work

The default directive is for content that every user shares. `'use cache: private'` is for the rare function that must
read `cookies()`, `headers()` or `searchParams` itself and still wants a lifetime. Nothing is stored on the server
across requests: Next.js may reuse a matching call *within one request*, and the client router keeps the rendered output
in browser memory for the `stale` time of its `cacheLife`. Private functions run at request time and are excluded from
the static shell, they cannot be configured with a custom cache handler, and `connection()` is still forbidden.

[cols="3,2,2,2",options="header"]
|===
| | `'use cache'` | `'use cache: remote'` | `'use cache: private'`

| Server-side storage
| In-memory or the cache handler
| The `remote` cache handler
| None

| Scope
| Shared by all users
| Shared by all users
| Per browser

| Reads `cookies()`, `headers()`, `searchParams` directly
| No
| No
| Yes

| Extra cost
| None
| Storage and a network round trip
| None

| Survives a deploy
| No
| No
| Not applicable
|===

.A shared function and a private one side by side (app/lab/private/page.tsx, Cache Components)
[source,tsx]
----
// app/lab/private/page.tsx
import { Suspense } from "react";
import { cookies } from "next/headers";
import { cacheLife } from "next/cache";
import { readOrigin } from "@/lib/source";

// Reads the cookie itself: allowed only with 'use cache: private'.
async function recommendationsPrivate() {
  "use cache: private";
  cacheLife({ stale: 60 }); // browser keeps it for 60 s; nothing is shared on the server
  const session = (await cookies()).get("session")?.value ?? "guest";
  return readOrigin(`private-${session}`);
}

// Shared alternative: read the cookie outside, pass the value in.
async function recommendationsShared(session: string) {
  "use cache";
  cacheLife("lab");
  return readOrigin(`shared-${session}`);
}

async function Recs() {
  const session = (await cookies()).get("session")?.value ?? "guest";
  const [priv, shared] = await Promise.all([recommendationsPrivate(), recommendationsShared(session)]);
  return <pre>{JSON.stringify({ priv, shared })}</pre>;
}

export default function Page() {
  return (
    <Suspense fallback={<p>loading</p>}>
      <Recs />
    </Suspense>
  );
}

[#use-cache-remote]
=== `'use cache: remote'` and `cacheHandlers`

The default `'use cache'` stores entries in memory, which has limits: entries are evicted, memory is finite, and on
serverless platforms each instance is short-lived with its own memory, so a runtime entry is rarely reused. `'use cache:
remote'` stores the output in a *remote* cache handler instead, shared by every instance and surviving restarts, at the
price of a network lookup and storage cost. It pays off for content that is deferred to request time (read behind
`cookies()`, `headers()` or `searchParams` inside `<Suspense>`) and expensive or fragile to compute: rate-limited APIs,
slow databases, costly aggregations, flaky services. Avoid it when operations already take under about 50 ms, when keys
are mostly unique per request (search filters, per-user ids: near-zero hit rate), or when the data changes every few
seconds. Cache on the dimension with few values (category, language) and filter the rest in memory.

Nesting rules: a remote cache may sit inside a remote or a regular cache; it cannot sit inside a private one, and a
private cache cannot sit inside a remote one.

.A remote cache keyed by language (app/lab/remote/page.tsx, Cache Components)
[source,tsx]
----
// app/lab/remote/page.tsx
import { Suspense } from "react";
import { connection } from "next/server";
import { cacheLife, cacheTag } from "next/cache";
import { readOrigin } from "@/lib/source";

async function getCatalogue(language: string) {
  "use cache: remote";
  cacheLife({ stale: 30, revalidate: 5, expire: 60 });
  cacheTag("catalogue-remote");
  return readOrigin(`remote-${language}`);
}

async function Remote() {
  await connection();
  const [en, es] = await Promise.all([getCatalogue("en"), getCatalogue("es")]);
  return <pre>{JSON.stringify({ en, es })}</pre>;
}

export default function Page() {
  return (
    <Suspense fallback={<p>loading</p>}>
      <Remote />
    </Suspense>
  );
}
----

The handler that stores it is configured with `cacheHandlers` (plural; see below for the singular one). Two names are
built in: `default` serves `'use cache'` and `remote` serves `'use cache: remote'`; extra names can be used as `'use
cache: <name>'`. Without configuration both use an in-memory LRU. A handler implements five methods: `get(cacheKey,
softTags)` (return `undefined` for a missing or expired entry), `set(cacheKey, pendingEntry)` (await the pending entry,
whose `value` is a `ReadableStream`), `refreshTags()` (called before a request, to sync tag state in a cluster),
`getExpiration(tags)` (the most recent revalidation timestamp for those tags, `0` for none, `Infinity` to check soft
tags in `get`) and `updateTags(tags, durations)` (invalidate entries with those tags). A `CacheEntry` has `value`,
`tags`, `stale`, `timestamp`, `expire` and `revalidate`. This minimal handler keeps entries in a `Map` and logs every call;
it is not for production (a real one talks to Redis, DynamoDB or similar and must catch its own errors, since an
exception thrown from `refreshTags()` or `get()` fails the request):

.A logging in-memory handler (cache-handlers/remote.cjs)
[source,js]
----
// A minimal in-process "remote" handler that logs every call. A production handler
// would talk to Redis, DynamoDB or another store shared by all instances.
const cache = new Map();
const pending = new Map();
const log = (...a) => console.log("[handler:remote]", ...a);

module.exports = {
  async get(cacheKey, softTags) {
    const p = pending.get(cacheKey);
    if (p) await p;
    const entry = cache.get(cacheKey);
    log("get", cacheKey.slice(0, 40), entry ? "HIT" : "MISS", "softTags=" + softTags.length);
    if (!entry) return undefined;
    if (Date.now() > entry.timestamp + entry.revalidate * 1000) return undefined;
    // the stored stream can be read once: hand out a copy
    const [a, b] = entry.value.tee();
    entry.value = b;
    return { ...entry, value: a };
  },
  async set(cacheKey, pendingEntry) {
    let done;
    pending.set(cacheKey, new Promise((r) => (done = r)));
    try {
      const entry = await pendingEntry;
      log("set", cacheKey.slice(0, 40), "tags=" + entry.tags.join(","));
      cache.set(cacheKey, entry);
    } finally {
      done();
      pending.delete(cacheKey);
    }
  },
  async refreshTags() {},
  async getExpiration() {
    return 0;
  },
  async updateTags(tags) {
    log("updateTags", tags.join(","));
    for (const [key, entry] of cache) {
      if (entry.tags.some((t) => tags.includes(t))) cache.delete(key);
    }
  },
};
----

There are two handler options with similar names, and mixing them up is a common mistake:

[cols="2,3,3",options="header"]
|===
| Option | Used for | Notes

| `cacheHandlers` (plural, 16.0)
| `'use cache'`, `'use cache: remote'` and named variants. Not `'use cache: private'`.
| Entries are scoped to one deployment.

| `cacheHandler` (singular, stable since 14.1; config path `incrementalCacheHandlerPath` before)

[#shells]
=== Prerendered Shells, App Shell and ISR

The layer that most users see without configuring anything is the prerendered shell: at build time Next.js renders the
component tree, completes everything that can finish (cached functions whose lifetime is long enough, module imports,
pure computation) and stores the result as static HTML and an RSC payload; the holes (`<Suspense>` boundaries around
request-time work) are filled when the request arrives, by resuming the render. When the params of a dynamic route are not
known at build time, the reusable, URL-independent shell is the *App Shell*, served instantly and upgraded in the
background with the concrete params (ISR with Cache Components, 16.3). Where the shell lives, how it is resumed and how
a CDN can serve it are in xref:web/nextjs/partial-prerendering-and-cache-components.adoc[Partial Prerendering and Cache Components] and
xref:web/nextjs/incremental-static-regeneration.adoc[Incremental Static Regeneration]; for caching purposes remember two
points. The shell is a cache like any other: its lifetime comes from the cached scopes it contains (the single `hours` scope of
`◐ /lab/shell 1h 1d` above), and `updateTag`/`revalidateTag` of a tag used in it regenerates it. And bots and crawlers
are detected by user agent and get a complete document rendered at request time instead of the shell, so everything
the shell used at build time must also be reachable at request time.

Source: https://nextjs.org/docs/app/getting-started/caching#prerendering[Caching: prerendering],
https://nextjs.org/docs/app/guides/incremental-static-regeneration-cache-components[ISR with Cache Components]

[#client-cache]
=== The Client Cache

With Cache Components the browser keeps the cached content of visited and prefetched routes in memory, and its freshness
is the `stale` of the `cacheLife` profiles involved. The server communicates it with the `x-nextjs-stale-time` response
header, the router enforces a *minimum of 30 seconds* so that prefetched links stay usable until clicked, and the
lifetime applies only to time-based expiry: any Server Action that calls `revalidateTag`, `revalidatePath`, `updateTag`
or `refresh` clears the whole client cache immediately. This `stale` is per function or per route; `staleTimes` of the
previous model is a global setting (and updating `staleTimes.static` also updates the `stale` of the `default` profile).
`'use cache: private'` results live only here. 16.3 adds `partialPrefetching`, which prefetches each route's App Shell by
default and, with `+<Link prefetch={true}>+`, the cached content that depends on the link's URL data (see
xref:web/nextjs/linking-and-navigation.adoc[Linking and Navigation]).

`curl` shows the header; on the lab's fully cached page (`stale: 120`) it was `x-nextjs-stale-time: 120`, on a route whose
scopes use the default profile `300`. A headless browser confirmed the effect: a `<Link>` to `/lab/cached-page` sent
no RSC request on the click (0 requests on three clicks), because its content had already been prefetched and was fresh
for 120 seconds.

Source: https://nextjs.org/docs/app/api-reference/functions/cacheLife#client-cache-behavior[cacheLife: client cache behavior],
https://nextjs.org/docs/app/getting-started/caching#prefetching[Caching: prefetching]

Reading the diagram:

* Time works on the two server layers by itself. In both models an entry is *fresh*, then *stale* (served while a
  regeneration runs, except in the cases noted above), then *expired* (the next request waits).
* A tag call reaches the Data Cache and the `'use cache'` entries that carry the tag; the routes whose render read those
  entries are rebuilt on the next visit. `revalidatePath` goes through the route's soft tags and reaches the route entry.
* Any of the Server Action calls clears the *whole* client cache at once, ignoring `stale`/`staleTimes`; `refresh()`
  touches only the client side and leaves every server cache alone.
* The CDN is outside the picture. Purge it yourself right after the Next.js call, for the HTML *and* the RSC variants
  of the URL (<<http-caching>>).
* With several server instances the call only reaches the instance that received it unless a shared cache handler
  coordinates them through `updateTags()` and `refreshTags()` (<<use-cache-remote>>).

| An editor publishes in the CMS and a visitor may see the old page once
| `revalidateTag(tag, 'max')` in a Route Handler called by the webhook

| A background job deleted data and no stale copy may ever be served
| `revalidateTag(tag, { expire: 0 })`

| A whole section of the site changed shape
| `revalidatePath('/books', 'layout')`

| Only the browser's copy is wrong (a count in a header)
| `refresh()` in a Server Action

| Everything, once, because the code changed
| Deploy: the build id is part of every key
|===

[#http-caching]
== CDN Caching and `Cache-Control`

Next.js sets standard `Cache-Control` headers from the rendering strategy of each route, and a CDN in front of it can
use them. All the values below were read with `curl -I` against `next start`, in each model:

[cols="3,3,3",options="header"]
|===
| Route (model) | `Cache-Control` | Other headers

| Static page, no lifetime (`/lab/frc-static`, previous model; `/lab/static`, Cache Components)
| `s-maxage=31536000` (one year)
| `x-nextjs-cache: HIT`, `x-nextjs-prerender: 1`, `x-nextjs-stale-time: 300`, `ETag`

| Time-revalidated page (`revalidate = 5`, previous model)
| `s-maxage=5, stale-while-revalidate=31535995`
| `x-nextjs-cache: STALE` then `HIT`

| Whole page cached with `cacheLife({ stale: 120, revalidate: 5, expire: 3600 })` (Cache Components)
| `s-maxage=5, stale-while-revalidate=3595` (revalidate, and expire minus revalidate)
| `x-nextjs-cache: HIT`, `x-nextjs-stale-time: 120`

| Dynamic page (`force-dynamic`, a `no-store` fetch, request-time API)
| `private, no-cache, no-store, max-age=0, must-revalidate`
| no `x-nextjs-cache`

| Partial prerender (`/lab/shell`, `/lab/tags`, Cache Components)
| `private, no-cache, no-store, max-age=0, must-revalidate` on the streamed response
| `x-nextjs-prerender: 1`, `x-nextjs-stale-time: 300`

| A Route Handler that reads the request (`/api/source`)
| none set by Next.js
| `vary: rsc, next-router-state-tree, ...`

| `/_next/static/*` (hashed files)
| `public, max-age=31536000, immutable`
| `ETag`

| `getStaticProps` with `revalidate` (Pages Router)
| `s-maxage=5, stale-while-revalidate=31535995`
| `x-nextjs-cache: STALE`, then `HIT`

| `next dev` (any page)
| `no-cache, must-revalidate`
| nothing is cached
|===

[source,text]
----
$ curl -sI localhost:3603/lab/cached-page            # Cache Components, one page = one cache entry
HTTP/1.1 200 OK
Vary: rsc, next-router-state-tree, next-router-prefetch, next-router-segment-prefetch, Accept-Encoding
x-nextjs-cache: HIT
x-nextjs-prerender: 1
x-nextjs-stale-time: 120
Cache-Control: s-maxage=5, stale-while-revalidate=3595
ETag: "q5qlhymj6z4pq"
Content-Type: text/html; charset=utf-8

$ curl -sI localhost:3603/lab/frc-dynamic            # previous model, force-dynamic
HTTP/1.1 200 OK
Vary: rsc, next-router-state-tree, next-router-prefetch, next-router-segment-prefetch, Accept-Encoding
Cache-Control: private, no-cache, no-store, max-age=0, must-revalidate
Content-Type: text/html; charset=utf-8
----

Note the asymmetry of a *partial prerender*. The static shell is stored as a prerender, but the response of a route that
also streams holes is a live, per-request response, so Next.js itself marks it non-cacheable; a CDN that wants to serve
the shell from the edge must be able to resume the postponed holes (see
xref:web/nextjs/partial-prerendering-and-cache-components.adoc[Partial Prerendering and Cache Components]). A fully
prerendered route is the one a plain CDN can cache with the headers above.

What a CDN must get right, per the official CDN guide:

* *Honour `s-maxage` and `stale-while-revalidate`* and cache the HTML and the RSC payload of a route together, with the
  same lifetime and invalidation, otherwise client navigation can show different content from a page load.
* *Respect `Vary`.* App Router responses vary on `rsc`, `next-router-state-tree`, `next-router-prefetch`,
  `next-router-segment-prefetch` and, for interception routes, `next-url`. For CDNs that ignore `Vary`, Next.js adds an
  `_rsc` query parameter, a hash of those header values, that must stay in the cache key. A request with `rsc: 1` but
  without the right `_rsc` value gets a `307` to the URL with the correct hash (observed), which the CDN must follow.
* *Never strip the `rsc` request header*: the server would answer with HTML where the client router expects an RSC
  payload and navigation would fall back to full page loads.
* *Purge on demand revalidation.* `revalidateTag` and `revalidatePath` invalidate the Next.js server cache only. The CDN
  keeps its copy until `s-maxage` ends, so call the CDN purge API for the affected URLs (both variants) right after
  the Next.js call.
* *Run Proxy before the CDN cache*, or bypass the CDN for routes whose behaviour depends on `proxy.ts` decisions
  (see xref:web/nextjs/redirects-rewrites-and-proxy.adoc[Redirects, Rewrites and Proxy]).
* Static assets under `/_next/static/` are immutable and can be cached for a year; `assetPrefix` serves them from another
  origin. The official guide also describes a direction of travel: moving every cache-affecting input into the URL
  pathname so that `Vary` and `_rsc` are no longer needed. It is still design work in 16.3.

The `stale-while-revalidate` and `s-maxage` directives are the standard ones of HTTP caching (RFC 9111 and RFC 5861);
`expireTime` in `next.config` lowers the one-year default of the second number for every ISR page of the previous model
(see xref:web/nextjs/incremental-static-regeneration.adoc[Incremental Static Regeneration]).

Source: https://nextjs.org/docs/app/guides/cdn-caching[CDN caching],
https://nextjs.org/docs/app/guides/how-revalidation-works#what-gets-revalidated[How revalidation works]

[#pages-router]
== The Pages Router

The Pages Router has a much shorter list of caches, none of which is controlled by `cacheComponents` (Cache Components,
`'use cache'` and the segment config belong to the App Router): a page is statically generated with `getStaticProps`
(optionally with `revalidate`, which is ISR), rendered per request with `getServerSideProps`, or neither. The server
cache behind ISR is the one that `cacheHandler` (singular) replaces, and `res.revalidate()` is the on-demand call.
`getServerSideProps` has no cache of its own, so the only way to cache its responses is a `Cache-Control` header,
which is set by the page and honoured by a CDN:

.The two caching modes of a Pages Router page (pages/lab-pages/ssr-cached.tsx and static-isr.tsx)
[source,tsx]
----
// pages/lab-pages/ssr-cached.tsx
import type { GetServerSideProps } from "next";

type Props = { renderedAt: string };

export const getServerSideProps: GetServerSideProps<Props> = async ({ res }) => {
  // Fresh for 10 s at a shared cache, then stale-while-revalidate for 59 s.
  res.setHeader("Cache-Control", "public, s-maxage=10, stale-while-revalidate=59");
  return { props: { renderedAt: new Date().toISOString() } };
};

export default function Page({ renderedAt }: Props) {
  return <p>getServerSideProps rendered at {renderedAt}</p>;
}
----

[source,tsx]
----
// pages/lab-pages/static-isr.tsx
import type { GetStaticProps } from "next";

type Props = { builtAt: string };

export const getStaticProps: GetStaticProps<Props> = async () => ({
  props: { builtAt: new Date().toISOString() },
  revalidate: 5, // ISR: regenerate at most once every 5 seconds
});

export default function Page({ builtAt }: Props) {
  return <p>getStaticProps generated at {builtAt}</p>;
}
----

Observed: `/lab-pages/ssr-cached` answered with `Cache-Control: public, s-maxage=10, stale-while-revalidate=59` and
rendered anew on every request that reached the server (the timestamp changed between two requests); `/lab-pages/static-isr`
answered `Cache-Control: s-maxage=5, stale-while-revalidate=31535995` with `x-nextjs-cache: STALE` once the 5 seconds
had passed and the regenerated page on the next request (the generation timestamp moved from `15:06:01` to `15:06:24`
and then `15:06:30`). The build table lists it as `● /lab-pages/static-isr 5s 1y` under `Route (pages)`. For
`getServerSideProps` the official advice is to consider `getStaticProps` with ISR first and use the header only when the
response is genuinely per-request but safe to share for seconds.

Source: https://nextjs.org/docs/pages/building-your-application/data-fetching/get-server-side-props#caching-with-server-side-rendering-ssr[getServerSideProps: caching with SSR],
https://nextjs.org/docs/pages/guides/incremental-static-regeneration[Pages Router: ISR]

[#self-hosting]
== Self-Hosting, Instances and Deployments

Three facts decide how caching behaves outside a managed platform:

* *One instance, one cache.* The default `'use cache'` handler is an in-memory LRU per Node.js process and the
  server cache of ISR is a file-system cache of that machine. Several instances behind a load balancer each have their
  own, and a revalidation call reaches only the instance that received it. A shared `cacheHandler` and a shared
  `cacheHandlers` store, coordinated through `updateTags()` and `refreshTags()`, are the answer;
  xref:web/nextjs/incremental-static-regeneration.adoc[Incremental Static Regeneration] works through a multi-instance
  setup.
* *Serverless instances are short-lived,* so runtime `'use cache'` entries are rarely reused. Build-time caching
  works normally. Use `'use cache: remote'` for the expensive ones, and measure with `cacheMaxMemorySize: 0` first.
* *A deployment starts clean.* The build id (or `deploymentId`) is part of every `'use cache'` key and the Full Route Cache
  is rebuilt, so the first visits after a deploy recompute. Only the `fetch` Data Cache and `unstable_cache`
  persist. During a rolling deploy, set `deploymentId` so that a client of deploy A that meets a server of deploy B
  does a hard navigation instead of mixing payloads.

Source: https://nextjs.org/docs/app/guides/self-hosting#caching-and-isr[Self-hosting: Caching and ISR],
https://nextjs.org/docs/app/guides/how-revalidation-works#multi-instance-considerations[How revalidation works: multi-instance considerations]

[#debugging]
== Debugging Caches

A cache bug always has the same shape: a value that is older, or newer, than you expect. Work from the outside in.

. *Build output.* The route table tells you what was prerendered: `○` static, `●` generateStaticParams, `ƒ` dynamic,
  `◐` partial prerender, plus *Revalidate* and *Expire* columns. A route you thought was cached and shows `ƒ` has a
  request-time API or a `no-store` fetch somewhere below it.
. *Response headers.* `curl -I` shows `Cache-Control` (what a CDN will do), `x-nextjs-cache` (`HIT`, `STALE`, `MISS`,
  `REVALIDATED`; self-hosted only), `x-nextjs-prerender` and `x-nextjs-stale-time` (what the client will do).
. *Count the origin.* Put a counter, a log line or a timestamp on the data source, as the lab does. "Is it the Next.js
  cache or my own?" is answered by whether the counter moved.
. *Verbose cache logs.* `NEXT_PRIVATE_DEBUG_CACHE=1 npm run start` (or `dev`) logs every cache operation, including
  ISR, the file-system cache and `use cache`. A shortened excerpt from the log while the lab's fully cached page was requested
  after its 5 second `revalidate` had passed:
+
[source,text]
----
use-cache: initializing cache handlers
use-cache: setting "default" cache handler from default
use-cache: setting "remote" cache handler from default
FileSystemCache: get /route-cache/APP_PAGE/dc2530ec.../$/lab/cached-page APP_PAGE true
use-cache: Resume Data Cache entry not found ["BUILD_ID","80480...",[]]
use-cache: registering as cross-request invocation leader ["BUILD_ID","80480...",[]]
DefaultCacheHandler: get ["BUILD_ID","80480...",[]] not found
[origin] api:cached-page hit #1
use-cache: Resume Data Cache entry saved ["BUILD_ID","80480...",[]]
DefaultCacheHandler: set ["BUILD_ID","80480...",[]] done
use-cache: delaying entry ["BUILD_ID","80480...",[]] until after the shell stage due to short stale value: 120
pending revalidates promise finished for: /lab/cached-page
----
+
Each `use-cache:` line carries the key (<<cache-keys>>): the build id, the function id and the arguments. The two
messages "leader" and "delaying entry" are exactly the rules of this page at work (one computation shared by concurrent
requests, a `stale` under 5 minutes kept out of the shell).
. *Development behaves differently.* In `next dev` pages are never cached for the Full Route Cache, `Cache-Control` is
  `no-cache, must-revalidate`, and `console.log` calls inside cached functions are replayed with a `Cache` prefix.
  `logging: { fetches: { fullUrl: true } }` in `next.config` prints every `fetch` with its cache outcome, and in the
  lab the second request showed:
+
[source,text]
----
 │ GET http://localhost:3603/api/source?label=force-cache 200 in 1ms (cache hit)
 │ GET http://localhost:3603/api/source?label=revalidate-5 200 in 1ms (cache hit)
 │ GET http://localhost:3603/api/source?label=tagged 200 in 1ms (cache hit)
 │ GET http://localhost:3603/api/source?label=plain 200 in 5ms (cache skip)
 │ │ Cache skipped reason: (auto no cache)
----
+
A hard refresh (browser sends `cache-control: no-cache`) makes development ignore the `fetch` options and read from the
source, and the HMR cache can serve a response across hot reloads; always confirm a caching change on a production
build.
. *The dev overlay.* With Cache Components it names the problem: `blocking-route`, `blocking-prerender-dynamic`,
  `blocking-prerender-random`, `blocking-prerender-current-time`, each with fix suggestions, and `next-request-in-use-cache`
  for a request API inside a cached scope.
. *Mimic production serverless.* `cacheMaxMemorySize: 0` turns the in-memory caches off.
. *Log the handler.* A logging `cacheHandlers` handler (above) shows `get` hits, misses, `set` and `updateTags` calls, and
  is the quickest way to see whether `revalidateTag` reached a shared store.
. *A build that hangs for about 50 seconds* and fails is a cache fill waiting on a Promise of runtime data created outside
  the scope (<<use-cache>>).

Source: https://nextjs.org/docs/app/api-reference/directives/use-cache#troubleshooting[use cache: troubleshooting],
https://nextjs.org/docs/app/api-reference/functions/fetch#troubleshooting[fetch: troubleshooting],
https://nextjs.org/docs/app/api-reference/config/next-config-js/serverComponentsHmrCache[serverComponentsHmrCache]

[#choosing]
== Choosing a Layer

[cols="3,3,3",options="header"]
|===
| I want to | Previous model | Cache Components

| Deduplicate the same read within one render
| `fetch` (automatic) or `React.cache`
| The same

| Cache one API call for everyone
| `fetch(url, { cache: 'force-cache', next: { revalidate, tags } })`
| A `'use cache'` function with `cacheLife` and `cacheTag`

| Cache a database query for everyone
| `unstable_cache(fn, keyParts, { tags, revalidate })`
| A `'use cache'` function

| Prerender a page and refresh it over time
| `export const revalidate = n`
| `'use cache'` with `cacheLife`; unknown params get the App Shell and ISR

| Make a page always dynamic
| `export const dynamic = 'force-dynamic'` or a `no-store` fetch
| Read the request (`connection()`, `cookies()`) under `<Suspense>`

| Cache per-user data
| Do not use the shared Data Cache; render per request
| Pass the user id into a `'use cache'` function, or `'use cache: private'`

| Share the cache between instances
| A shared `cacheHandler`
| `'use cache: remote'` with a shared `cacheHandlers` store (and `cacheHandler` for ISR)

| Make navigation reuse pages in the browser
| `staleTimes` (and prefetching)
| `stale` of the `cacheLife` profiles
|===

== Common Pitfalls

* *Invalidating one layer and forgetting the next.* A tag call updates the server; the CDN keeps its copy until you
  purge it, and an open browser tab keeps its own until a Server Action clears it or the `stale` time passes.
* *Assuming `fetch` is cached.* It was in 13 and 14; it is not in 15 and 16. The same page can feel fast in one
  version and slow in the next.
* *One `cache: 'no-store'` fetch deep in the tree makes the whole route dynamic* in the previous model; it shows as `ƒ`
  in the build table.
* *Mixing `fetchCache` with per-call `cache` options.* The measured result contradicted the docs on 16.3.8 (see above);
  use one mechanism.
* *`unstable_cache` and captured variables.* Variables read from outside are not part of the key unless you pass them
  in the arguments or in `keyParts`; two different closures can then share one entry.
* *Per-user data in a shared cache.* `'use cache'` and `'use cache: remote'` are shared by all users. The user id (or
  its absence) must be part of the key; with `fetch`, `force-cache` on a credentialed request stores a personal
  response server-wide.
* *Over-keying.* A cache keyed by a search string, a price range or a user id has a near-zero hit rate and fills memory.
  Cache the shared slice and filter in memory, especially for `'use cache: remote'`.
* *No `cacheLife`.* The `default` profile (15 minutes) is applied silently and a short inner lifetime can shorten an outer
  one; name a profile in every `'use cache'` scope.
* *Reading `cookies()` inside `'use cache'`.* It fails; read it outside and pass the value.
* *Expecting entries to survive a deploy.* `'use cache'` keys contain the build id; `fetch` and `unstable_cache` data
  survive.
* *Expecting a shared cache on serverless.* The in-memory handler is per instance; use `'use cache: remote'` or accept
  that runtime entries are rarely reused.
* *Treating `x-nextjs-cache` as an API.* It is a diagnostic of a self-hosted server and may change.
* *Revalidation endpoints with secrets in the URL, or on `GET`.* Use `POST`, a header secret or a verified signature, and
  never put the secret in the query string.
* *Single-argument `revalidateTag(tag)`.* Deprecated since 16; use `'max'`, a profile or `{ expire: 0 }`, or `updateTag`
  in a Server Action.
* *Trusting `next dev`.* Development does not cache pages and behaves differently for `fetch`; confirm with `next build`
  and `next start`.
* *Bots and crawlers* skip the static shell and render everything at request time; data the shell used at build time
  must be reachable then too.

[#changes]
== What Changed Recently

[cols="1,4",options="header"]
|===
| Version | Change for caching

| 13.0, 13.4
| App Router (13.4 stable) with the four caches: request memoization, Data Cache, Full Route Cache, client router cache; `fetch` cached by default.

| 14.0, 14.1, 14.2
| `unstable_cache` (14.0); `cacheHandler` stable (14.1, the former `incrementalCacheHandlerPath`); experimental `staleTimes` (14.2).

| 15.0
| `fetch`, `GET` Route Handlers and the client router cache for page segments are no longer cached by default (`staleTimes.dynamic` 30 s to 0 s); `'use cache'` introduced as experimental.

| 16.0
| Cache Components (`cacheComponents`), `'use cache'` and the `private` and `remote` variants, `cacheHandlers`, stable `cacheLife` and `cacheTag`, `updateTag`, `refresh`, two-argument `revalidateTag`; `experimental.ppr`, `dynamicIO` and `useCache` removed; `unstable_cache` documented as replaced; layout deduplication and incremental prefetching in the router.

| 16.2
| `cacheHandler` can also cache optimized images (`images.customCacheHandler`).

| 16.3
| App Shell ISR for unknown params, `partialPrefetching` and Instant Navigations next to `cacheComponents`, prefetch inlining; `cacheComponents` and `partialPrefetching` stay opt-in.
|===

Two statuses to keep in mind in October 2026: `staleTimes` is still documented as *experimental*, and `unstable_cache`
keeps its name although the docs call it replaced.

[#books]
== Where the Books Are Outdated

The two reference books were written for the Pages Router, before any of the App Router caches existed. Their
caching material is correct for the Pages Router and incomplete for everything else:

[cols="2,3",options="header"]
|===
| The books say | Today

| Pages are cached through `getStaticProps` with `revalidate` (ISR), and a response is cached by setting `Cache-Control` with `s-maxage` and `stale-while-revalidate` in `getServerSideProps`
| Still valid in the Pages Router (and shown above). In the App Router the same ideas are `revalidate`/`cacheLife`, `fetch` options and `'use cache'`, and Next.js writes the `Cache-Control` header itself.

| There is one cache to think about: the server's
| There are up to five layers (<<layers>>), and most surprises come from the client router cache, the CDN or the Data Cache.

| Client libraries (an Apollo `InMemoryCache`, SWR, TanStack Query) are *the* data cache of the page
| Those are client-side caches of another layer (see xref:web/nextjs/client-side-rendering.adoc[Client-Side Rendering]). With Server Components the data layer is on the server (Data Cache, `'use cache'`), and the client libraries are for data that must be fetched in the browser.

| Data is fetched in `getStaticProps` and `getServerSideProps` and frozen into JSON props
| Data is fetched in async Server Components, and the cache is a property of the function (`'use cache'`, `unstable_cache`) or the call (`fetch`), not of the page type.

| `res.revalidate()` from an API route called with a secret in the URL
| Valid for the Pages Router. In the App Router use `revalidateTag(tag, 'max')` or `updateTag` from a Route Handler or Server Action, with a header secret or signature, never a secret in a URL.

| Pages are static or dynamic as a whole
| A route can mix static, cached and dynamic parts with Cache Components, each with its own lifetime.

| Performance advice about cache policy of static assets (Lighthouse)
| `/_next/static/*` is already `public, max-age=31536000, immutable`; third-party assets are outside Next.js' control.
|===
