[#overview]
== Where Configuration Lives

A Next.js project is configured by a small, fixed set of files in the project root. Each is read by a different tool at
a different moment, which is what decides whether a change needs a restart, a rebuild or nothing at all.

.The configuration surfaces of a Next.js 16 project
[cols="2,3,3",options="header"]
|===
| File | Owns | Read by

| `next.config.ts` (or `.js`, `.mjs`, `.mts`)
| Framework behaviour: routing rules, caching model, images, headers, bundler options, build output, TypeScript and build flags, experimental flags.
| The Next.js CLI at `next dev`, `next build`, `next start` and `next typegen`, at start-up and again in some build sub-processes. It runs in Node.js, is not bundled and is never sent to the browser. A change needs a restart of the dev server.

| `tsconfig.json`
| TypeScript compiler options, the `next` editor plugin, the `paths` aliases for absolute imports, and which generated type files are included.
| `tsc`, the editor and the build's type-check step. The bundler also reads `paths` to resolve aliases.

| `next-env.d.ts`
| References to Next.js's own ambient types, regenerated for you.
| TypeScript only. Never edit it.

| `eslint.config.mjs`
| Lint rules, through the `eslint-config-next` package and the ESLint CLI.
| The `eslint` command that you run yourself, never `next build` (see <<eslint,ESLint With the Flat Config CLI>>).

| `.env`, `.env.local`, `.env.development`, `.env.production`, `.env.test` and their `.local` variants
| Values that differ between machines and environments: URLs, feature flags, secrets, and `NEXT_PUBLIC_` values that are baked into client code.
| Next.js loads them into `process.env` before it loads `next.config.ts`; `loadEnvConfig` from `@next/env` does the same for other tools.

| `package.json`
| Scripts, dependencies, the `engines` range and the `"type"` field that decides whether `.js` files are ESM.
| Node.js and the package manager.

| `proxy.ts`, `instrumentation.ts`
| Request interception and start-up hooks. They are code rather than configuration and have their own pages.
| At request time, and once on server start.
|===

Source: https://nextjs.org/docs/app/api-reference/config/next-config-js[next.config.js], https://nextjs.org/docs/app/api-reference/config/typescript[TypeScript], https://nextjs.org/docs/app/api-reference/config/eslint[ESLint] and https://nextjs.org/docs/app/guides/environment-variables[Environment Variables]

The pieces interact. `next.config.ts` sets `typedRoutes`, which makes Next.js generate types that `tsconfig.json` must
include, which `tsc` and the editor then check. A `.env` value feeds `next.config.ts` through `process.env` because the
config file runs in Node.js with the environment already loaded. The sections below follow that order.

[#next-config]
== next.config.ts

The configuration file lives in the project root (next to `package.json`, not inside `app/` or `src/`). Next.js
accepts four spellings: `next.config.ts`, `next.config.js` (CommonJS, with `module.exports`), `next.config.mjs` and
`next.config.mts`. The official reference states that `.cjs` and `.cts` are not supported; in the scratch app a
`next.config.cjs` stops `next typegen` and `next build` with "Configuring Next.js via 'next.config.cjs' is not supported. Please replace the file with 'next.config.js', 'next.config.mjs', or 'next.config.ts'". TypeScript
configuration (`next.config.ts`) arrived in Next.js 15.0 and is what `create-next-app` generates. The file is a
regular Node.js module that runs when the CLI starts, so it can read `process.env`, compute values and import other
modules, but it is not processed by Turbopack, webpack or Babel: avoid JavaScript syntax your Node.js version lacks.

.The extensions Next.js accepts for the configuration file, checked on 16.3.8
[cols="2,3,4",options="header"]
|===
| File name | Module system | Result in the scratch app

| `next.config.ts`
| ES module syntax in TypeScript. Documented since Next.js 15.0.
| Loads. Use the `NextConfig` type.

| `next.config.js`
| CommonJS (`module.exports`) unless `package.json` sets `"type": "module"`.
| Loads. Use a JSDoc `@type` comment for editor checking.

| `next.config.mjs`
| ES module (`export default`).
| Loads.

| `next.config.mts`
| ES module in TypeScript.
| Loads (the TypeScript reference recommends it when you need top-level `await` in a CommonJS project).

| `next.config.cjs`, `next.config.cts`
| CommonJS.
| Rejected. The build stops with `Configuring Next.js via 'next.config.cjs' is not supported`.
|===

Source: https://nextjs.org/docs/app/api-reference/config/next-config-js[next.config.js] and https://nextjs.org/docs/app/api-reference/config/typescript#type-checking-nextjs-configuration-files[TypeScript: type checking Next.js configuration files]

The smallest useful file exports an object typed with `NextConfig`. The Bookshelf's version below turns on the checks
and hardening that every project should have and adds one redirect, one header rule and one remote image host.

.next.config.ts for the Bookshelf (previous caching model)
[source,ts]
----
import type { NextConfig } from "next";

const nextConfig: NextConfig = {
  reactStrictMode: true,
  poweredByHeader: false,
  typedRoutes: true,
  images: {
    remotePatterns: [
      { protocol: "https", hostname: "covers.example.com", pathname: "/covers/**" },
    ],
  },
  async redirects() {
    return [{ source: "/catalogue", destination: "/en", permanent: true }];
  },
  async headers() {
    return [
      {
        source: "/:path*",
        headers: [
          { key: "X-Content-Type-Options", value: "nosniff" },
          { key: "Referrer-Policy", value: "strict-origin-when-cross-origin" },
        ],
      },
    ];
  },
};

export default nextConfig;
----

Source: https://nextjs.org/docs/app/api-reference/config/next-config-js[next.config.js]

The same configuration was built and started on port 3214 of the scratch app. The route table comes from `next build`,
and `curl` confirms the effect of each key: `poweredByHeader: false` removes the `x-powered-by` header, `headers()`
adds the security headers, and `redirects()` answers `/catalogue` with a permanent redirect before the Proxy runs.

If a project contains both `next.config.js` and `next.config.ts`, 16.3.8 loaded the `.js` file and ignored the `.ts` one
(in a re-check, `next typegen` printed the `console.log` of the `.js` file and then failed on its `module.exports`
because the package had `"type": "module"`). The documentation does not promise an order, so keep exactly one config
file.

=== A function instead of an object

The default export may also be a function (sync or `async`) that receives the current *phase* and returns the
configuration. Phases are string constants exported by `next/constants`; the function form is how you make a setting
depend on whether Next.js is running the dev server, a production build or the production server. Async functions have
been supported since Next.js 12.1.

.next.config.ts as an async function of the phase
[source,ts]
----
import type { NextConfig } from "next";
import { PHASE_DEVELOPMENT_SERVER, PHASE_PRODUCTION_BUILD } from "next/constants";

export default async function config(phase: string): Promise<NextConfig> {
  const isDev = phase === PHASE_DEVELOPMENT_SERVER;
  console.log(`[next.config] phase=${phase}`);
  return {
    reactStrictMode: true,
    poweredByHeader: false,
    typedRoutes: true,
    // Serve static assets from a CDN only in production builds.
    assetPrefix: phase === PHASE_PRODUCTION_BUILD ? "https://cdn.example.com" : undefined,
    allowedDevOrigins: isDev ? ["bookshelf.local"] : undefined,
    env: { BUILD_LABEL: "bookshelf-2026-10" },
  };
}
----

Running it shows when the file is evaluated. The log line appeared three or four times during one `next build`, so Next.js evaluates the file more than once; a
configuration function must be free of side effects. In the scratch app `next build` printed
`[next.config] phase=phase-production-build` and `next dev` printed `[next.config] phase=phase-development-server`;
after a production build the HTML referenced `https://cdn.example.com/_next/static/chunks/...` for every script.

Source: https://nextjs.org/docs/app/api-reference/config/next-config-js#configuration-as-a-function[Configuration as a Function] and https://nextjs.org/docs/app/api-reference/config/next-config-js/assetPrefix[assetPrefix]

`next/constants` exports `PHASE_DEVELOPMENT_SERVER`, `PHASE_PRODUCTION_BUILD`, `PHASE_PRODUCTION_SERVER`, `PHASE_EXPORT`,
`PHASE_TEST`, `PHASE_INFO` and `PHASE_ANALYZE` (the seven names were listed from the installed package); their values
are strings such as `phase-development-server`. The function also receives a second argument, an object holding the
`defaultConfig`. `next typegen` loads the config with the production build phase, so it needs the same environment
variables as a build. In the scratch app each command printed its own phase value, and a single `next build` printed the
phase line three times, because the configuration is evaluated in more than one process.

.Phase values printed by each command
[source,bash]
----
$ npx next dev
[next.config] phase=phase-development-server

$ npx next build
[next.config] phase=phase-production-build      # printed three or four times in one build

$ npx next start
[next.config] phase=phase-production-server
----

Source: https://nextjs.org/docs/app/api-reference/config/next-config-js#phase[Phase]

=== Native ESM, top-level await and next.config.mts

Module resolution inside `next.config.ts` is limited to CommonJS semantics. On Node.js 22.10 or later, Next.js detects
Node's native TypeScript support through `process.features.typescript`, and the file can then use native ESM, including
top-level `await` and dynamic `import()`. The feature is on by default from Node.js 22.18; on 22.10 to 22.17 you start
the CLI with `NODE_OPTIONS=--experimental-transform-types`. In a CommonJS project the documentation recommends the
`.mts` spelling so that Node.js knows the file is ESM from the start.

.next.config.mts using a dynamic import (Node.js 22.10 or later)
[source,ts]
----
import type { NextConfig } from "next";

// Top-level await and dynamic import() work in next.config.mts (Node.js 22.10+).
const flags = await import("./flags.mjs").then((m) => m.default);

const nextConfig: NextConfig = {
  typedRoutes: Boolean(flags.typedRoutes),
  poweredByHeader: false,
};

export default nextConfig;
----

With a one-line `flags.mjs` (`export default { typedRoutes: true };`) next to it, `npx next typegen` and
`npx next build` both reported `Running next.config.mts` and loaded the flag on Node.js 24.16. A `flags.js` in a
project without `"type": "module"` also works, but Node.js prints a `MODULE_TYPELESS_PACKAGE_JSON` warning because it
has to reparse the file; naming it `.mjs` avoids that.

Source: https://nextjs.org/docs/app/api-reference/config/typescript#using-nodejs-native-typescript-resolver-for-nextconfigts[Using Node.js Native TypeScript Resolver for next.config.ts]


=== The caching-model switch used by the Bookshelf

`cacheComponents` is the one option that changes how the rest of the application is rendered, which is why the scratch
app drives it from an environment variable (`CACHE_COMPONENTS=1`) read in the configuration function. Everything else in
this page works in both models. When the option is on, `next build` prints `Cache Components enabled` before the route
table, and the table uses the `◐` (Partial Prerender) symbol for routes that mix a static shell with streamed dynamic
content. Later pages explain the model; here you only need to know where it is switched on.

.Reading the switch from the environment (excerpt of the configuration function)
[source,ts]
----
export default async function bookshelfConfig(phase: string): Promise<NextConfig> {
  return {
    // CACHE_COMPONENTS=1 -> Cache Components; unset -> the previous caching model
    cacheComponents: process.env.CACHE_COMPONENTS === "1",
    typedRoutes: true,
  };
}
----

Source: https://nextjs.org/docs/app/api-reference/config/next-config-js/cacheComponents[cacheComponents]

.The same build in both models (excerpt of the route table)
[source,bash]
----
$ npx next build                       # previous model
├   /[locale]/env-demo/frozen
│ ├ ● /en/env-demo/frozen
│ └ ● /es/env-demo/frozen
├ ƒ /[locale]/env-demo/runtime
└ ƒ /api/env

$ CACHE_COMPONENTS=1 npx next build    # Cache Components

[#invalid-keys]
=== What Next.js does with unknown and removed keys

The configuration is validated when it loads. An unknown key does not stop the build: it prints a warning that links to
`https://nextjs.org/docs/messages/invalid-next-config`, which is easy to miss in CI logs. A few keys that were removed in
earlier majors are fatal, with a message that names the replacement. This configuration, deliberately wrong, was built on
Next.js 16.3.8 to show the output.

.A config with typos and removed keys (deliberately wrong)
[source,ts]
----
import type { NextConfig } from "next";

const nextConfig = {
  typedRoutes: true,
  reactStrictModee: true, // typo
  serverRuntimeConfig: { authSecret: process.env.AUTH_SECRET }, // removed in 16
  publicRuntimeConfig: { apiUrl: "/api" }, // removed in 16
  eslint: { ignoreDuringBuilds: true }, // removed in 16
  experimental: { notARealFlag: true },
} as unknown as NextConfig;

export default nextConfig;
----

Source: https://nextjs.org/docs/messages/invalid-next-config[Invalid next.config.js options detected]

.next build output for that config
[source,bash]
----
▲ Next.js 16.3.8 (Turbopack)
- Environments: .env.local
⚠ `eslint` configuration in next.config.ts is no longer supported. See more info here: https://nextjs.org/docs/app/api-reference/cli/next#next-lint-options
⚠ Invalid next.config.ts options detected:
⚠     Unrecognized key(s) in object: 'notARealFlag' at "experimental"
⚠     Unrecognized key(s) in object: 'reactStrictModee', 'serverRuntimeConfig', 'publicRuntimeConfig', 'eslint'
⚠ See more info here: https://nextjs.org/docs/messages/invalid-next-config
✓ Running next.config.ts took 52ms

  ? notARealFlag (invalid experimental key)
----

Two things to take from the output. The `Environments` line lists the `.env` files that were loaded, which is the
quickest way to confirm which file a value came from. The `Experiments` list prints the `experimental` flags that are
set, so it is also a record of what your build opted into (an invalid key shows up there with a `?`). Removed flags are
fatal rather than silent: `experimental.ppr` stops the build with the message that it "has been merged into
`cacheComponents`", and `experimental.dynamicIO` with "has been replaced by `cacheComponents`". Treat any warning as a
failure in CI.

Source: https://nextjs.org/docs/messages/invalid-next-config[Invalid next.config.js options detected]

[#catalogue]
== The Option Catalogue

The official `next.config.js` reference has one page per option, 72 of them at `@doc-version` 16.3.8 (one of them,
`incrementalCacheHandlerPath`, documents the `cacheHandler` key, and `turbopackIgnoreIssue` documents
`turbopack.ignoreIssue`). This catalogue lists every one of them, grouped by purpose, with its status, the version where
it appeared or changed where the documentation gives one, and a link to its page. Read it as an index: the option pages
carry the full detail, and most options are expanded on the later page that uses them.

Three rules decide where a key goes in `NextConfig`, and putting a key in the wrong object is the most common reason an
option is silently ignored.

* *Top level:* stable options such as `basePath`, `images` or `typedRoutes`.
* *Under `experimental`:* options marked experimental, for example `experimental.staleTimes`. Their names and behaviour
  may change in a minor release. The same rule holds for several options that have long been in use, such as
  `experimental.serverActions` for its `allowedOrigins` and `bodySizeLimit` settings. The tables write the full path of
  these keys.
* *A key that is not in the schema at all:* a warning (<<invalid-keys,see above>>), or an error for removed flags.

The status column uses four words. *Stable* means a documented top-level option. *Experimental* means the documentation
page carries the experimental banner and the key lives under `experimental`. *Legacy* or *deprecated* means the page
says so. *Removed* means the key is no longer in the schema.

=== Routing, URLs and Output

.Options that shape URLs, routing rules and the build output
[cols="3,2,6",options="header"]
|===
| Option | Status and version | What it does

| https://nextjs.org/docs/app/api-reference/config/next-config-js/basePath[`basePath`]
| Stable
| Serves the app under a sub-path such as `/docs`. Set at build time: the value is inlined into client bundles. `next/link` applies it automatically; a static `src` passed to `next/image` needs it added by hand.

| https://nextjs.org/docs/app/api-reference/config/next-config-js/assetPrefix[`assetPrefix`]
| Stable
| Serves `/_next/` assets from a CDN origin. Combine with the phase argument so development keeps local assets. Not needed on Vercel.

| https://nextjs.org/docs/app/api-reference/config/next-config-js/trailingSlash[`trailingSlash`]
| Stable (9.5)
| Redirects `/about` to `/about/` when `true` (the default is the reverse). Files with extensions and `.well-known` paths are exempt.

| https://nextjs.org/docs/app/api-reference/config/next-config-js/skipTrailingSlashRedirect[`skipTrailingSlashRedirect`]
| Stable (13.1)
| Turns off the automatic trailing-slash redirects so that Proxy can decide. An advanced Proxy flag.

| https://nextjs.org/docs/app/api-reference/config/next-config-js/skipProxyUrlNormalize[`skipProxyUrlNormalize`]
| Stable. Renamed in 16.0 from `skipMiddlewareUrlNormalize` (13.1)
| Lets Proxy see the original request URL instead of the normalised one. An advanced Proxy flag.

| https://nextjs.org/docs/app/api-reference/config/next-config-js/pageExtensions[`pageExtensions`]
| Stable
| Extensions treated as page files. The default is `tsx`, `ts`, `jsx`, `js`; add `md` and `mdx` for MDX pages.

| https://nextjs.org/docs/app/api-reference/config/next-config-js/redirects[`redirects`]
| Stable (9.5; `has` 10.2, `missing` 13.3)
| An array of `source`, `destination`, `permanent` rules; 308 when permanent, 307 otherwise. Sync or async function.

| https://nextjs.org/docs/app/api-reference/config/next-config-js/rewrites[`rewrites`]
| Stable (9.5; `has` 10.2, `missing` 13.3)
| Maps a request path to another destination while keeping the URL, acting as a URL proxy. Also applied to client-side navigation.

| https://nextjs.org/docs/app/api-reference/config/next-config-js/headers[`headers`]
| Stable (9.5; `has` 10.2, `missing` 13.3)
| Adds response headers for matching paths. A function returning `source` plus a list of `key` and `value` pairs.

| https://nextjs.org/docs/app/api-reference/config/next-config-js/output[`output`]
| Stable
| `'standalone'` traces the files each page needs and writes a self-contained `.next/standalone` folder with a minimal `server.js` (used by Docker deployments). Static HTML export is the other documented mode.

| https://nextjs.org/docs/app/api-reference/config/next-config-js/distDir[`distDir`]
| Stable
| Replaces the `.next` build folder. It must stay inside the project. Since 16, `next dev` writes to `.next/dev` so dev and build can run at the same time.

| https://nextjs.org/docs/app/api-reference/config/next-config-js/exportPathMap[`exportPathMap`]
| Legacy, deprecated
| Belonged to the removed `next export` command. Use `generateStaticParams` (App Router) or `getStaticPaths` (Pages Router).

| https://nextjs.org/docs/app/api-reference/config/next-config-js/appDir[`appDir`]
| Legacy. Unnecessary since 13.4
| Once enabled the App Router. In 16.3.8 the key is no longer in the schema and logs `Unrecognized key(s)`.
|===

=== Rendering, Caching and Deployment

.Options for the caching model, revalidation, deployments and server behaviour
[cols="3,2,6",options="header"]
|===
| Option | Status and version | What it does

| https://nextjs.org/docs/app/api-reference/config/next-config-js/cacheComponents[`cacheComponents`]
| Stable flag, opt-in (16.0)
| Turns on Cache Components and the `use cache` directive. One flag that replaces `experimental.ppr`, `useCache` and `dynamicIO`. Requires the Node.js runtime.

| https://nextjs.org/docs/app/api-reference/config/next-config-js/partialPrefetching[`partialPrefetching`]
| Stable flag, opt-in (16.3)
| Prefetches only the static parts of each route by default (Instant Navigations). Requires `cacheComponents`; without it, `next dev` and `next build` throw at config validation.

| https://nextjs.org/docs/app/api-reference/config/next-config-js/cacheLife[`cacheLife`]
| Stable, needs `cacheComponents`
| Defines named cache profiles (`stale`, `revalidate`, `expire`, in seconds) used by the `cacheLife` function inside `use cache`.

| https://nextjs.org/docs/app/api-reference/config/next-config-js/cacheHandlers[`cacheHandlers`]
| Stable (16.0)

The documented order of evaluation of the routing options is: `headers`, `redirects`, the Proxy, `beforeFiles` rewrites,
static files and non-dynamic pages, `afterFiles` rewrites, dynamic routes, and finally `fallback` rewrites. `rewrites()`
returns either a plain array (treated as `afterFiles`) or an object with those three keys. That order is why `/catalogue`
in the first example of this page is redirected before the Proxy's locale logic can touch it.

=== Unit-testing the routing rules

Since 15.1 the experimental `next/experimental/testing/server` package contains `unstable_getResponseFromNextConfig`,
which runs only the `headers`, `redirects` and `rewrites` of a configuration against a request. It ignores the Proxy and
file-system routes, so use it for configuration regressions rather than end-to-end routing. The test below uses the
built-in Node.js test runner; the `.js` suffix on the import is needed only because plain Node.js ESM does not resolve
extensionless subpath imports (Vitest and Jest resolve `next/experimental/testing/server` as written in the reference).

.Testing a redirect rule without starting the server
[source,js]
----
import assert from "node:assert/strict";
import { test } from "node:test";
import { getRedirectUrl, unstable_getResponseFromNextConfig } from "next/experimental/testing/server.js";

test("/catalogue redirects permanently to /en", async () => {
  const response = await unstable_getResponseFromNextConfig({
    url: "https://bookshelf.example.com/catalogue",
    nextConfig: {
      async redirects() {
        return [{ source: "/catalogue", destination: "/en", permanent: true }];
      },
    },
  });
  assert.equal(response.status, 308);
  assert.equal(getRedirectUrl(response), "https://bookshelf.example.com/en");
});
----

Running `node --test scripts/config-rules.test.mjs` printed `pass 1`, and the response status was 308 because the rule
is permanent.

== TypeScript

TypeScript is first-class in Next.js. A project made with `create-next-app` is already TypeScript; to add it to an
existing project, rename a file to `.ts` or `.tsx` and run `next dev` or `next build`, which installs the missing
packages and writes a `tsconfig.json` with the recommended options. If a `jsconfig.json` exists, copy its `paths` into
the new `tsconfig.json` and delete it. The required levels are TypeScript 5.1 or later (an `async` Server Component
returns a `Promise`, which only type-checks from TypeScript 5.1.3 with `@types/react` 18.2.8 or later; otherwise you see

=== The editor plugin

Next.js ships a TypeScript language-service plugin (the `"plugins": [{ "name": "next" }]` entry above). In VS Code you

=== Generated types and next-env.d.ts

Next.js generates two kinds of type files. `next-env.d.ts` sits in the project root and pulls in the Next.js ambient

`next typegen`. The file is rewritten by those commands, so put your own ambient declarations in a file of your own and
list it in `include`; anything you add to `next-env.d.ts` is overwritten.

=== The typescript key and the build

`next build` fails when the project has type errors. Two keys of the `typescript` object adjust that:
`tsconfigPath` selects a different file (for example `tsconfig.build.json` that extends the main one and relaxes a
check for the production build), and `ignoreBuildErrors` skips the type-checking step entirely, which the reference
calls dangerous unless a separate type-check runs in CI. The configured path is used by `next dev`, `next build` and
`next typegen`; in development only `tsconfig.json` is watched, so restart the dev server after editing a different file.

.Switching the tsconfig for production builds
[source,ts]
----
import type { NextConfig } from "next";

const isProd = process.env.NODE_ENV === "production";

const nextConfig: NextConfig = {
  typescript: {
    tsconfigPath: isProd ? "tsconfig.build.json" : "tsconfig.json",
  },
};

export default nextConfig;
----

In 16.3.8 the production build runs the project-local `tsc` CLI by default. That makes TypeScript 7, which does not
provide the JavaScript compiler API, usable for `next build` after `npm install -D typescript@^7`; the trade-off is that
the output is the native `tsc` diagnostics without Next.js-specific code frames. Set `experimental.useTypeScriptCli`
to `false` to return to the compiler-API checker. Incremental type checking (`"incremental": true`, already in the
generated file) has been supported since 10.2.1.

[#typed-routes]
== Typed Routes, Route Helpers and next typegen

Three features make the file-system router visible to the compiler. They all rest on one generated artefact: a
declaration file produced from the `app/` tree (and from the `redirects()` of the configuration).

=== typedRoutes

With `typedRoutes: true` (stable since 15.5; it used to be `experimental.typedRoutes`), the `href` of `next/link` and the
arguments of `push`, `replace` and `prefetch` from `next/navigation` are checked against the real route list. Literal
strings and template literals with dynamic segments are validated; a string built at run time needs a cast to `Route`.
In the Pages Router the feature types `next/link`'s `href` only, not `next/router`.

=== PageProps, LayoutProps and RouteContext

Next.js declares three global helper types, so they need no import. Each takes the route as a string literal and
derives the shape from the folder tree: `PageProps<'/blog/[slug]'>` gives `params` (a `Promise`, since the sync access
was removed in 16) and `searchParams`; `LayoutProps<'/dashboard'>` gives `children`, `params` and one prop per parallel
route slot (`@modal` becomes `modal`); `RouteContext<'/users/[id]'>` gives the `params` of a Route Handler. A
`PageProps` for a static route has `params` equal to `{}`. They are available once types have been generated.

.PageProps in the book detail page of the Bookshelf
[source,tsx]
----

  const { locale, id } = await params;
  if (!isLocale(locale)) notFound();
  return (
    <Suspense fallback={<p>…</p>}>
      <BookDetail id={id} label={dict[locale].send} />
    </Suspense>
  );
}
----

Types used to exist only while `next dev` or `next build` ran, so a bare `tsc --noEmit` in CI could not see

[#env]
== Environment Variables

Next.js loads `.env*` files into `process.env` before it evaluates `next.config.ts`, so the configuration file itself
can read them. Files are plain `KEY=value` lines. Multi-line values are allowed inside double quotes, and a `$OTHER`
reference is expanded from another variable (escape a literal dollar as `\$`). Three rules decide what code can see a
variable: the load order, the `NEXT_PUBLIC_` prefix, and whether the code runs at build time or per request.

=== Files and load order

For each variable Next.js looks, in order, in: the real process environment, `.env.$(NODE_ENV).local`, `.env.local`
(skipped when `NODE_ENV` is `test`), `.env.$(NODE_ENV)` and `.env`, and stops at the first place that defines it.
`NODE_ENV` is `development` for `next dev` and `production` for every other command (`build`, `start`), and `test`
only if a test runner sets it. The files are looked up in the project root, also when you use a `src/` folder.

The order is easier to follow as a decision for one variable, as the next diagram shows. The reason for the test exception is reproducibility: tests should give the same result for everyone, so `.env.local`, the personal overrides, is ignored when `NODE_ENV` is `test`.

[mermaid]
....
flowchart TD

=== NEXT_PUBLIC_ inlining versus runtime reads

Variables without a prefix exist only in the Node.js process. To make a value available to browser code, prefix it with
`NEXT_PUBLIC_`; at `next build` Next.js then **replaces** each `process.env.NEXT_PUBLIC_*` expression with the literal
value from the environment of the build. The consequences follow from that: the value is public, it is frozen in the
bundle, and changing the variable after the build has no effect. A single Docker image promoted from staging to
production therefore keeps the staging value of every `NEXT_PUBLIC_` variable.

[mermaid]
....
flowchart LR
    F[".env files and shell<br/>loaded into process.env"] --> B{"next build"}
    B -->|"NEXT_PUBLIC_ prefix"| I["Literal inlined into client<br/>and server bundles"]
    B -->|"no prefix"| S["Stays a process.env read"]
    S -->|"route prerendered at build"| P["Value frozen into the HTML<br/>and RSC payload"]
    S -->|"read after connection(), cookies(),<br/>headers() or other request-time API"| R["Read again on every request<br/>by next start"]
....


The substitution is a text replacement made at build time, and it has three consequences.

* The value becomes part of a public JavaScript file, so every visitor can read it.
* It is frozen at build time: changing the variable on a running server changes nothing.
* The replacement is static. The guide says that `process.env[name]` and `const env = process.env; env.NEXT_PUBLIC_X`
  are not inlined; the table below shows what Turbopack in 16.3.8 really does, and the safe rule is to write the full
  `process.env.NEXT_PUBLIC_X` expression.

.What gets inlined and what does not
[cols="2,3,3",options="header"]
|===
| Expression in a Client Component | Result in the 16.3.8 build | Why

| `process.env.NEXT_PUBLIC_API_BASE`
| The literal from build time.
| Static property access with the prefix: the documented case.

| `process.env[key]` where `key` is a function parameter
| Compiled to a lookup on the browser's `process.env` shim: not inlined.
| The name is unknown at build time. Nothing from your `.env` files is in the browser's `process.env`.

| `const name = "NEXT_PUBLIC_API_BASE"; process.env[name]`
| Also the literal: Turbopack folded the constant.
| The guide says dynamic lookups are not inlined; with Turbopack a lookup whose key is a compile-time constant is. Do not rely on either.

| `const env = process.env; env.NEXT_PUBLIC_API_BASE`
| Also the literal in the same build.
| Same: the guide says it is not inlined; Turbopack resolved it. Write the full expression.

| `process.env.DB_HOST` (no prefix)
| Not available in the browser.
| Server-only; reading it in a Client Component gives `undefined`.
|===

The last two rows are behaviour of Turbopack in 16.3.8 that differs from what the guide states, and the safe rule is the
guide's: write `process.env.NEXT_PUBLIC_NAME` literally wherever you need it. Never put a secret behind a `NEXT_PUBLIC_`
name, and read secrets only in server-only modules (`import 'server-only'`), a Data Access Layer, Route Handlers and Server Actions.

environments with different values.

=== Runtime environment variables

By default variables are only available on the server, and a `NEXT_PUBLIC_` variable is a build-time constant. To read a
value at runtime, read it on the server during dynamic rendering (after `await connection()` or another request-time API
such as `cookies()` or `headers()`), in a Route Handler for a client that must discover its configuration, or in code that
runs at startup through the `register` function of `instrumentation.ts`. A client that needs a runtime value fetches
it from an endpoint or receives it as a prop from a Server Component; the guide states that you have to set up your own API
for this. That is the pattern that lets one Docker image run in several environments.

Source: https://nextjs.org/docs/app/guides/environment-variables#runtime-environment-variables[Runtime Environment Variables] and https://nextjs.org/docs/app/guides/instrumentation[Instrumentation]

=== The env key of next.config.ts

The `env` key in the configuration defines build-time constants that **always** go into the bundle; the `NEXT_PUBLIC_` prefix
has no effect on them. The reference marks the key as legacy since 9.4. In the experiment,
`env: { BUILD_LABEL: "bookshelf-2026-10" }` made `process.env.BUILD_LABEL` appear as the literal `"bookshelf-2026-10"`
in the client chunk. Because destructuring `process.env` cannot be replaced, write `process.env.BUILD_LABEL` in full.
Prefer `.env` files unless you need a value computed in `next.config.ts`, such as a Git hash.

Source: https://nextjs.org/docs/app/api-reference/config/next-config-js/env[env]

=== Pages Router differences

The Pages Router reads `.env*` files with the same rules and the same `NEXT_PUBLIC_` inlining. For runtime values the
guide recommends `getServerSideProps` (or adopting the App Router incrementally); `getStaticProps` runs at build
time, so what it reads is frozen into the generated HTML and JSON.


=== Secrets and the NEXT_PUBLIC_ prefix

The prefix is a publication switch, not a naming style. `NEXT_PUBLIC_` is correct only for values that are safe to
show every visitor: a publishable payment key, an analytics identifier, a public site URL. Credentials of any kind
(API secret keys, database URLs, CMS write tokens, signing secrets such as `AUTH_SECRET`) must carry *no* prefix and
must be read only in server code: Server Components, Route Handlers, Server Actions and `proxy.ts`. A variable that is
unprefixed stays out of the client bundle by construction, which is the protection to rely on. Keeping a `.env` file out
of git protects the repository, not the browser: the file's contents still reach the page if the name starts with the
prefix.

Concrete rules for the _Bookshelf_ code:

* Keep every secret unprefixed, for example `STRIPE_SECRET_KEY`, `SANITY_API_WRITE_TOKEN` or `DATABASE_URL`, and import the
  module that reads it through `import "server-only"` so that a Client Component importing it fails the build.
* Use the prefix only for values you would put in HTML anyway, such as `NEXT_PUBLIC_SITE_URL`.
* After a build, search the client output for the secret's value. A secret that appears under `.next/static` has leaked
  and must be rotated.
* Never rely on the "frozen at build time" behaviour to hide a value: build artefacts and Docker layers are readable.
* Values that differ per environment (an API host, a feature flag) are better as unprefixed variables read at request
  time than as `NEXT_PUBLIC_` values, which would force a rebuild per environment. When a Docker image is built once and
  promoted, pass genuinely public values as build arguments, because setting them on the running container does nothing.

The data-security page of this section (_Data Security & CSP_) covers the Data Access Layer, `server-only` and the
taint APIs in depth.

[#runtime-config]
== The Removed Runtime Config

Older Pages Router projects configured values with `serverRuntimeConfig` and `publicRuntimeConfig` in `next.config.js`
and read them with `getConfig()` from `next/config`. Both keys were removed in Next.js 16.0 and the `next/config` module
is no longer in the package (no `node_modules/next/config.js` in 16.3.8). The scratch build confirms it: the keys are
reported under "Unrecognized key(s) in object" (see the warning block above) and are ignored. The replacement is
environment variables, with the split described above.

.Replacing runtime config
[cols="2,3",options="header"]
|===
| Before (up to 15) | Now (16)

| `serverRuntimeConfig: { dbUrl: process.env.DATABASE_URL }` and `getConfig().serverRuntimeConfig.dbUrl`
| Read `process.env.DATABASE_URL` directly in server code, in a server-only module.

| `publicRuntimeConfig: { apiUrl: '/api' }` and `getConfig().publicRuntimeConfig.apiUrl`
| `NEXT_PUBLIC_API_URL` in `.env`, read as `process.env.NEXT_PUBLIC_API_URL` (build-time constant).

| `publicRuntimeConfig` used to change a value without rebuilding
| Read a variable on the server after `await connection()` and pass it down as a prop, or serve it from a Route Handler.
|===

The upgrade guide shows the three replacements in code: a server-only value read from `process.env` in a Server Component, a client-visible value with the `NEXT_PUBLIC_` prefix set at build time, and a value that must be read at runtime rather than bundled, which calls `connection()` first.

.app/page.tsx -- a server-only value: read process.env in a Server Component
[source,tsx]
----
async function fetchData() {
  const dbUrl = process.env.DATABASE_URL;
  // use for server-side operations only
}
----

Source: https://nextjs.org/docs/app/guides/upgrading/version-16#runtime-configuration[Upgrading to 16: runtime configuration]

.A client-visible value: NEXT_PUBLIC_ prefix, set at build time (.env.local holds NEXT_PUBLIC_API_URL="/api")
[source,tsx]
----
"use client";

export default function ClientComponent() {
  return <p>API URL: {process.env.NEXT_PUBLIC_API_URL}</p>;
}
----

Source: https://nextjs.org/docs/app/guides/upgrading/version-16#runtime-configuration[Upgrading to 16: runtime configuration]

.app/page.tsx -- a value that must be read at runtime, not bundled: call connection() first
[source,tsx]
----
import { connection } from "next/server";

export default async function Page() {
  await connection();
  return <p>{process.env.RUNTIME_CONFIG}</p>;
}
----

Source: https://nextjs.org/docs/app/guides/upgrading/version-16#runtime-configuration[Upgrading to 16: runtime configuration]

The Bookshelf's replacement is the example of the previous section: the public API base URL is a `NEXT_PUBLIC_` constant
that is correct for the environment where the image was built, and the value that must change at deploy time is read in a
Server Component after `connection()` inside `<Suspense>`. The Next.js guide also suggests the `taint` API
(`experimental.taint`) to prevent sensitive server values from reaching Client Components by accident.

Source: https://nextjs.org/docs/app/guides/upgrading/version-16#runtime-configuration[Runtime Configuration (upgrading to version 16)] and https://nextjs.org/docs/app/api-reference/config/next-config-js/taint[taint]

[#absolute-imports]
== Absolute Imports and Module Path Aliases

Next.js reads the `baseUrl` and `paths` compiler options of `tsconfig.json` (or `jsconfig.json`), so `import { Button }
from '@/components/button'` replaces `'../../../components/button'`. The generated file already contains
`"paths": { "@/*": ["./*"] }`. A `baseUrl` makes every top-level folder importable by name, and `paths` adds named
aliases whose targets are relative to `baseUrl` (or to the `tsconfig.json` when there is none). Turbopack, webpack, the
type checker and the editor plugin all use the same mapping, so there is no second place to configure; test runners do
need their own alias configuration.

.tsconfig.json compilerOptions with a baseUrl and an extra alias
[source,json]
----
{
  "compilerOptions": {
    "baseUrl": ".",
    "paths": {
      "@/*": ["./*"],
      "@ui/*": ["components/*"]
    }
  }
}
----

Source: https://nextjs.org/docs/app/getting-started/installation#set-up-absolute-imports-and-module-path-aliases[Set up Absolute Imports and Module Path Aliases]

.A page that uses all three forms
[source,tsx]
----
import { dict } from "lib/i18n"; // resolved through baseUrl
import { Nav } from "@ui/nav"; // resolved through paths
import { listBooks } from "@/lib/books";

export default async function Page() {
  const books = await listBooks();
  return (
    <main>
      <Nav locale="en" genre="sf" />
      <p>{dict.en.send}</p>
      <p>{books.length} books</p>
    </main>
  );
}
----

This built with `next build` (the page appeared as `/en/abs` and `/es/abs` in the route table), and `tsc --noEmit`
accepted it. Without `paths` entries that match, an import such as `@/app/...` fails with Turbopack's "Module not found:
Can't resolve '@/app/[locale]/books/[id]/book-detail'", which is what happened when the `@/*` alias was left out
of the first attempt; aliases are not additive between `extends` files, so repeat the ones you need. When a project
uses a `src/` folder, `.env*` files and `next.config.ts` stay in the root, and the usual alias becomes `"@/*": ["./src/*"]`.

Source: https://nextjs.org/docs/app/getting-started/installation#set-up-absolute-imports-and-module-path-aliases[Set up Absolute Imports and Module Path Aliases] and https://nextjs.org/docs/app/glossary[Glossary]


`create-next-app` asks `Would you like to customize the import alias (@/* by default)?`, and with the `src/` option the
default alias points at `src/*`. A `baseUrl` also lets bare specifiers such as `components/nav` resolve from a folder: the
scratch app built and passed `tsc` on TypeScript 5.9 with `"baseUrl": "."` and an import of `components/nav` next to one
of `@/components/nav`. Under TypeScript 7, however, `baseUrl` no longer exists (error `TS5102`, shown in the
<<typescript,TypeScript section>>), so new code should use `paths` only, with entries resolved relative to the
`tsconfig.json` when there is no `baseUrl`.

.paths-only aliases that work without baseUrl
[source,json]
----
{
  "compilerOptions": {
    "paths": {
      "@/components/*": ["./components/*"],
      "@/lib/*": ["./lib/*"]
    }
  }
}
----

Source: https://nextjs.org/docs/app/getting-started/installation#set-up-absolute-imports-and-module-path-aliases[Set up Absolute Imports and Module Path Aliases]

[#pitfalls]
== Pitfalls

.Common mistakes with configuration, types and environment variables
[cols="2,3,3",options="header"]
|===
| Symptom | Cause | Fix

| A config option seems to do nothing
| Misspelt key, removed key, or a key in the wrong object (top-level versus `experimental`). Next.js only warns.
| Read the `Invalid next.config.ts options detected` warning; fail CI on warnings; check the catalogue above.

| Both `next.config.js` and `next.config.ts` exist
| 16.3.8 loaded the `.js` file and ignored the `.ts` one; `.cjs` and `.cts` are rejected.
| Keep exactly one configuration file.

| The configuration function logs or does work several times
| The config is evaluated in several processes and phases (three phase lines in one build).
| Keep it pure and fast.

| `partialPrefetching` throws at startup
| It requires `cacheComponents`.
| Enable both, or neither.

| Build fails with "This build is using Turbopack, with a `webpack` config and no `turbopack` config"
| A `webpack` function (possibly added by a plugin) while Turbopack is the default bundler.
| Migrate to the `turbopack` key, or run `next build --webpack`.

| `reactCompiler: true` fails with "Failed to resolve package babel-plugin-react-compiler"
| The compiler package is not installed.
| Install `babel-plugin-react-compiler`.

| The Turbopack build fails with a conflict error naming a package
| The same package is listed in `transpilePackages` and `serverExternalPackages`.
| List it in one only.

| A `Link` whose `href` is a variable does not compile under `typedRoutes`
| The value is a plain `string`, not a literal.
| Build the string from literals, or cast with `as Route`.

| `PageProps`, `LayoutProps` or `RouteContext` are "not found" (`Cannot find name 'PageProps'`)
| Types are not generated yet.
| Run `next typegen` (or `next dev`, `next build`) before `tsc`, and include `.next/types/**/*.ts`.

| `tsc --noEmit` passes locally and fails in CI
| `next-env.d.ts` and `.next/types` are git-ignored and not present on a clean checkout.
| Run `next typegen && tsc --noEmit` in CI.

| `TS5102: Option 'baseUrl' has been removed`
| TypeScript 7 dropped `baseUrl`.
| Use `paths` only.

| `ignoreBuildErrors: true` ships type errors
| The type-check step is skipped entirely.
| Only acceptable when CI type-checks separately.

| `npm run lint` is missing, `next lint` does nothing, or `next build` never lints
| `next lint` was removed in 16.0 and the build has no lint step.
| Use `eslint` with `eslint.config.mjs` in CI.

| A `NEXT_PUBLIC_` value is stale after changing the environment
| It was inlined at build time.
| Rebuild, or read the value at runtime on the server and pass it down.

| A dynamic lookup of a public variable is `undefined` in the browser
| `process.env[key]` with a key known only at run time is not inlined. (A constant key or an alias of `process.env` was inlined by Turbopack in 16.3.8, but the guide says it is not.)
| Write the full literal expression `process.env.NEXT_PUBLIC_NAME`.

| A non-public variable is `undefined` after hydration and React reports error 418
| A Client Component read an unprefixed variable: the server-rendered HTML had the real value, the browser has none.
| Read it in a Server Component, Server Action or Route Handler and pass the result down.

| A secret appears in the browser bundle
| It was given a `NEXT_PUBLIC_` prefix, or put in the `env` key.
| Remove the prefix, rotate the secret, and keep it in server-only modules.

| A server variable is frozen at build time
| It was read in a prerendered route without a request-time API.
| Call `await connection()` first (inside `<Suspense>` with Cache Components).

| A `GET` Route Handler returns the build-time value
| Under Cache Components a handler without a dynamic API is prerendered (`○ /api/env`).
| Add `await connection()`.

| The build fails with "Next.js encountered uncached or runtime data during prerendering"
| `connection()`, `cookies()`, `params` or `searchParams` read outside `<Suspense>` under Cache Components.
| Wrap the reading component in `<Suspense>`.

| Variables in `.env` are not found in a monorepo or `src/` layout
| Files are read from the project root only.
| Keep `.env*` next to `package.json`, or load them with `@next/env`.

| Tests do not see `.env.local`
| It is not loaded when `NODE_ENV` is `test`, so tests do not depend on a developer's machine.
| Put test values in `.env.test`.
|===

Source: https://nextjs.org/docs/messages/invalid-next-config[Invalid next.config.js options detected], https://nextjs.org/docs/messages/blocking-prerender-dynamic[blocking-prerender-dynamic] and https://nextjs.org/docs/app/guides/environment-variables[Environment Variables]

| Turbopack file-system cache on by default for `next dev`.

| 16.2
| `logging.browserToTerminal`; `cacheHandler` also caches optimised images; `turbopack.ignoreIssue`; `prefetchInlining` added; `adapterPath` stable and top level.

| 16.3
| `partialPrefetching`, `outputHashSalt`, `supportsImmutableAssets`, `instrumentationClientInject`, `turbopackLocalPostcssConfig`, `turbopackMemoryEviction`, `turbopackRustReactCompiler`; Turbopack file-system cache on by default for builds; `prefetchInlining` on by default; project-local `tsc` for type checking (TypeScript 7 works).
|===

[#books]
== Where the Books Are Outdated

Real-World Next.js (Riva, Packt, 2022) targets Next.js 12 and the Pages Router, and Practical Next.js for E-Commerce
(Libby, Apress, 2023) targets 13.2, when the App Router was still in beta; both of those majors are out of support. Their
configuration, TypeScript and environment chapters stay correct about the principles (a root configuration file, `.env`
files, the per-environment load order, `$VAR` expansion, `NEXT_PUBLIC_` inlining, path aliases) but the details have moved
on.

.Material in Next.js 12 and 13.2 era tutorials versus the 16.3 behaviour
[cols="2,3",options="header"]
|===
| If a tutorial from that era shows | Today

| `next.config.js` with `module.exports`
| Still works, but `next.config.ts` (15.0) with `import type { NextConfig }` is the default, and `.mjs` or `.mts` allow ESM; `.cjs` is rejected.

| `experimental: { appDir: true }`
| Not needed since 13.4; the key is now unrecognised.

| A custom `.babelrc` and a `webpack(config)` function as the standard way to customise the build
| SWC compiles by default and Turbopack is the default bundler, so a `webpack` function without a `turbopack` key fails `next build` unless you pass `--webpack`. The React Compiler is a config option (`reactCompiler`).

| `.eslintrc.json` with `"extends": "next/core-web-vitals"`, and `next lint`
| Removed in 16.0: `eslint.config.mjs` with `eslint-config-next/core-web-vitals` and the `eslint` CLI.

| `serverRuntimeConfig`, `publicRuntimeConfig` and `getConfig()`
| Removed in 16.0: environment variables, with `connection()` for per-request reads. Credentials never get the `NEXT_PUBLIC_` prefix.

| The `i18n` key in `next.config.js` (sub-path routing, `next-i18next`)
| Pages Router only; an App Router project gets the warning `i18n configuration in next.config.ts is unsupported in App Router`. Use an `app/[locale]` segment and Proxy.

| `next export` and `exportPathMap`
| `next export` is removed; use `output: 'export'` and `generateStaticParams`.

| `images: { domains: [...] }`
| Deprecated; use `images.remotePatterns` (and `localPatterns` for local images with query strings).

| Typing routes by hand, hand-typed props for `getServerSideProps` pages, or `experimental: { typedRoutes: true }`
| `typedRoutes: true` is stable (15.5); `PageProps`, `LayoutProps`, `RouteContext` and `next typegen` generate the types.

| Synchronous `params` and `searchParams` objects in pages
| `params` and `searchParams` are Promises in 15 and 16; use `await` and the `PageProps` helper.

| `@next/font`
| Removed in 15.0; `next/font`.

| `middleware.ts` and `skipMiddlewareUrlNormalize`
| `proxy.ts` and `skipProxyUrlNormalize` since 16.0.

| Config examples for the Pages Router only (`pages/`, `getStaticProps` typing)
| Still supported; new work targets the App Router. This page's typing helpers are App Router only.
|===
