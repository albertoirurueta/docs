section hangs from the answer, because in Next.js the route is also the unit of rendering, of code splitting, of

does it by hand, and then shows how Next.js moves the same decision into the folder structure and into the server.
It does not re-teach React; for components, props and state read
xref:web/react/getting-started.adoc[React Getting Started]; for the library-level view of client routing read

the advanced route types (parallel and intercepting routes, Route Handlers) are covered by later pages in this

[#spa-routing]
== How Routing Works in a React Single-Page App

React renders a tree of components from state. It has no notion of a URL. A single-page app (SPA) therefore adds
three things on top of React, and every client-side router is a variation of them:

. *The browser's History API* to change the address bar without asking the server for a new document.
. *A route table* that matches the current URL (`location.pathname`) against patterns such as `/books/:id`.
. *React state* that holds the current location, so that a change re-renders the matching components.

Here is the whole mechanism without any library. It is not production code (no nested routes, no scroll handling,
no data loading), but it is exactly what a router does:

.A router in a few lines of plain TypeScript (the same code without types ran in a browser console)
[source,ts]
----
const routes: Record<string, string> = { "/": "Home", "/books": "Books" };

function match(pathname: string): string {
  const m = pathname.match(/^\/books\/([^/]+)$/); // "/books/:id"
  return m ? `Book ${m[1]}` : (routes[pathname] ?? "Not found");
}

function render() {
  console.log("render:", match(location.pathname)); // React would set state here
}

// 1. Our own navigation: change the URL, then render. No request is made.
function navigate(to: string) {
  history.pushState(null, "", to);
  render();
}

// 2. The browser's back and forward buttons: popstate fires, we render again.
window.addEventListener("popstate", render);

navigate("/books/7"); // render: Book 7
navigate("/books");   // render: Books
history.back();       // render: Book 7  (popstate)
----

Running this in a page returned `Book 7`, `Books` and `Book 7` again after `history.back()`. Two details matter later.
`history.pushState()` does *not* fire `popstate`; only the back and forward buttons do, so a router must render
itself after its own `pushState`. And the server is out of the loop: the first visit loaded one HTML document,
the app's JavaScript bundle, and from then on every "page" is a component switch. A SPA host therefore has to answer
*every* path with the same `index.html` (a "fallback"), because `/books/7` is not a file, and the browser asks for
it when the user reloads or opens a shared link.

Source: https://developer.mozilla.org/en-US/docs/Web/API/History_API[MDN: History API]

React Router packages the three pieces. This is the same Bookshelf shape as a declarative route object with a
nested layout:

.React Router: the route table is data, nesting is `children` and `Outlet`
[source,tsx]
----
import { StrictMode } from "react";
import { createRoot } from "react-dom/client";
import {
  createBrowserRouter,
  Link,
  Outlet,
  RouterProvider,
  useParams,
} from "react-router";

function BooksLayout() {
  return (
    <section>
      <nav>
        <Link to="/books/1">Dune</Link>
      </nav>
      <Outlet /> {/* the matching child route renders here */}
    </section>
  );
}

function Book() {
  const { id } = useParams(); // string | undefined
  return <h1>Book {id}</h1>;
}

const router = createBrowserRouter([
  { path: "/", element: <h1>Bookshelf</h1> },
  {
    path: "/books",
    element: <BooksLayout />,
    children: [
      { index: true, element: <h1>All books</h1> },
      { path: ":id", element: <Book /> },
    ],
  },
]);

createRoot(document.getElementById("root")!).render(
  <StrictMode>
    <RouterProvider router={router} />
  </StrictMode>,
);
----

This file type-checks with `tsc --strict` against `react-router` 8.4.0 (the version on npm on 2026-10-03; the older
`react-router-dom` package, which xref:web/react/routing.adoc[React Routing] imports from, is a separate package that
re-exports the same API, at 7.18.4 on the same date). Source: https://reactrouter.com/start/data/routing[React Router: Routing]

A SPA router has real strengths: instant transitions once the bundle is loaded, full control in JavaScript, and a
static host is enough. It also has the weaknesses that motivate a framework router:

* *Nothing is rendered until the bundle runs.* The first HTML is an empty shell; the content appears after the
  JavaScript has downloaded, executed and (usually) fetched data. Search engines and slow devices feel it.
* *The route table is code you maintain by hand*, in a place that is not obviously connected to the files that
  implement each screen.
* *Code splitting is opt-in.* Without `lazy()` per route the bundle contains every screen.
* *Data loading is a separate problem*, solved per library (loaders in React Router, `useEffect`, a query library)
  and usually serial: route, then component, then request.

[#framework-router]
== What a Framework Router Changes

A framework router keeps the client half (History API, `Link`, nested layouts) and adds three decisions that a
library cannot make, because it does not own the server and the build:

[cols="1,2,2",options="header"]
.A React SPA router versus the Next.js App Router
|===
| Question | React SPA with a router library | Next.js App Router

| Where is the route table?
| In code: an array of route objects or JSX `<Route>` elements.
| In the file system: folders are URL segments, `page` files make them reachable. The build derives the table.

| Who matches the URL first?
| The browser, after the bundle has loaded.
| The server, on every request. The matching route's layouts and page render on the server as Server Components.

| What does a navigation fetch?
| Possibly a lazy chunk, then whatever data the component asks for.
| The RSC payload of the next route (the serialised UI tree), requested with a `?_rsc=` parameter, plus Client
Component chunks that are not loaded yet.

| What does the first visit return?
| An empty HTML shell plus the bundle.
| Complete HTML of the page, plus the RSC payload for hydration. See the SSR, SSG and hydration pages of this
section.

| Code splitting
| Manual (`React.lazy` per route).
| Automatic per route segment, and Server Components add no client JavaScript at all.

| Layouts
| Hand-written nesting with `Outlet`.
| The `layout` file of each folder; nesting follows the folders and the layout is kept alive across navigations.
|===

Source: https://nextjs.org/docs/app/getting-started/layouts-and-pages[Layouts and Pages] and
https://nextjs.org/docs/app/getting-started/linking-and-navigating[Linking and Navigating]

The consequence worth internalising is that Next.js routing is *server-centric with client-side navigation*. The
server decides what a URL renders, in every case; the client just avoids reloading the document while it asks. The
rest of the page follows that idea.

[#file-system-routing]
== File-System Routing in the App Router

Next.js uses *file-system based routing*: the folders and files under `app/` define the routes. Two kinds of names
are involved.

* *Folders* define *route segments*. A segment is one part of the URL path between slashes, so `app/books/[id]`
  contributes the two segments `books` and `[id]`.
* *Files* with reserved names define *the UI shown for a segment*. `page` is the one that makes a segment reachable,
  `layout` wraps the segment and its descendants, and `route` (a Route Handler, covered on its own page) answers
  with data instead of UI.

[cols="1,1,3",options="header"]
.The file conventions of this page
|===
| File | Extensions | Purpose

| `page`
| `.js` `.jsx` `.tsx`
| The UI of a route. Default-export a React component. A segment is publicly accessible only if it contains a `page`
(or a `route`).

| `layout`
| `.js` `.jsx` `.tsx`
| UI shared by a segment and all segments below it. Receives `children`. The *root layout* in `app/` is required and
must render `<html>` and `<body>`.

| `loading`, `error`, `not-found`, `template`, `default`, `route`
| `.js` `.jsx` `.tsx` (`route`: `.js` `.ts`)
| Other special files. Introduced in later pages of this section.
|===

Source: https://nextjs.org/docs/app/getting-started/project-structure#routing-files[Project structure: routing files]

A route is made of segments, and the segment kinds are:

[cols="2,2,3",options="header"]
.Segment kinds and what they match
|===
| Folder | Matches | `params`

| `app/books/page.tsx`
| `/books` (a static segment)
| none

| `app/books/[id]/page.tsx`
| `/books/1`, `/books/2`, ... (one dynamic segment)
| `{ id: '1' }`

| `app/shop/[...slug]/page.tsx`
| `/shop/a`, `/shop/a/b`, `/shop/a/b/c`, but *not* `/shop` (catch-all)
| `{ slug: ['a'] }`, `{ slug: ['a', 'b'] }`

| `app/shop/[[...slug]]/page.tsx`
| the same, *and* `/shop` (optional catch-all)
| `{ slug: undefined }` for `/shop`

| `app/(marketing)/about/page.tsx`
| `/about` (the folder name in parentheses is a *route group*: organisation only, not part of the URL)
| none

| `app/books/_components/`
| nothing (a leading underscore makes a *private folder*: opted out of routing)
| none
|===

Source: https://nextjs.org/docs/app/api-reference/file-conventions/dynamic-routes[Dynamic Routes],
https://nextjs.org/docs/app/api-reference/file-conventions/route-groups[Route Groups] and
https://nextjs.org/docs/app/getting-started/project-structure#colocation[Project structure: colocation]

Three consequences are easy to miss:

* *Only `page` and `route` make a segment public.* Any other file in a route folder (a helper, a test, a component)
  is *colocated* safely: it can never be reached by URL, and only what `page` returns is sent to the client. A build
  with `app/books/format.ts` and `app/books/_components/helper.ts` added produced exactly the same route table as one
  without them. Private folders are therefore optional; they are useful to group files and to avoid clashes with
  future file conventions, which the project-structure page of this section discusses.
* *Route groups do not change the URL, but they do change the tree.* `(marketing)/about` is `/about`. Two groups that
  resolve to the same URL (`(marketing)/about` and `(shop)/about`) are a build error.
* *Dynamic segments return strings (or arrays of strings).* `params.id` is `'2'`, never `2`, and unknown params are
  not an error by themselves: whether `/books/99` is a 404 is decided by your code (`notFound()`) or by
  `dynamicParams` for statically generated params.

== Worked Example: the Bookshelf Route Tree

The Bookshelf uses four kinds of route: the home page, a static page in a route group, a layout with a list of
books, and a nested dynamic route. The folder tree below is the whole application's routing; the file contents
follow.

.The Bookshelf routing, as a folder tree
[source,text]
----
app/
├── layout.tsx                 # root layout: <html>, <body>, main navigation
├── page.tsx                   # /
├── (marketing)/
│   └── about/page.tsx         # /about   (the group is not in the URL)
└── books/

The root layout holds what every page shares: the document and the navigation.

.app/layout.tsx
[source,tsx]
----
import Link from "next/link";

export default function RootLayout({ children }: LayoutProps<"/">) {
  return (
    <html lang="en">
      <body>
        <header>
          <nav>
            <Link href="/">Home</Link> | <Link href="/books">Books</Link> |{" "}
            <Link href="/about">About</Link>
          </nav>
        </header>
        {children}
      </body>
    </html>
  );
}
----

`LayoutProps<"/">` (and `PageProps<"/books/[id]">` below) are *global type helpers*: Next.js generates them (during
`next dev`, `next build` or `next typegen`) from the route table, so `params` is typed from the folder names. They
need no import. The configuration page of this section covers `next typegen`.

Source: https://nextjs.org/docs/app/getting-started/layouts-and-pages#creating-a-layout[Layouts and Pages: creating a layout]
and https://nextjs.org/docs/app/api-reference/file-conventions/layout[layout.js]

The `books` layout lists the books, and the two leaf pages are the dynamic part. `params` is a Promise in current
Next.js (see <<changed-since-13-14>>), so the page awaits it.

.app/books/layout.tsx
[source,tsx]
----
import { Suspense } from "react";
import { MountedAt } from "@/components/mounted-at";
import { BookNav } from "@/components/book-nav";
import { listBooks } from "@/lib/books";

export default async function BooksLayout({ children }: LayoutProps<"/books">) {
  const books = await listBooks();
  return (
    <section>
      <aside>
        <MountedAt label="books-layout" />
        <Suspense fallback={<p>Loading books...</p>}>
          <BookNav books={books} />
        </Suspense>
      </aside>
      <div>{children}</div>
    </section>
  );
}
----

.app/books/[id]/page.tsx
[source,tsx]
----
import Link from "next/link";
import { notFound } from "next/navigation";
import { getBook, listBooks } from "@/lib/books";

export async function generateStaticParams() {
  return (await listBooks()).map((b) => ({ id: b.id }));
}

export default async function BookPage({ params }: PageProps<"/books/[id]">) {
  const { id } = await params;
  const book = await getBook(id);
  if (!book) notFound();
  return (
    <article>
      <h1>{book.title}</h1>
      <p>{book.author}</p>
      <Link href={`/books/${book.id}/reviews`}>Reviews</Link>
    </article>
  );
}
----

.app/books/[id]/reviews/page.tsx
[source,tsx]
----
import { listBooks, listReviews } from "@/lib/books";

export async function generateStaticParams() {
  return (await listBooks()).map((b) => ({ id: b.id }));
}

export default async function ReviewsPage({
  params,
}: PageProps<"/books/[id]/reviews">) {
  const { id } = await params;
  const reviews = await listReviews(id);
  return <h2>{reviews.length} reviews for book {id}</h2>;
}
----

Two small Client Components finish the example. `MountedAt` is a probe, used in the navigation section below: it
records the moment it was mounted. `BookNav` is the usual "highlight the active link" component, and the reason a
layout can know which child is active even though layouts do not receive the URL.

.components/mounted-at.tsx
[source,tsx]
----
"use client";

import { useEffect, useState } from "react";

// The effect runs once per mount: if the timestamp does not change during
// navigation, the component was kept alive (it was not remounted).
export function MountedAt({ label }: { label: string }) {
  const [at, setAt] = useState<string | null>(null);
  useEffect(() => setAt(new Date().toISOString()), []);
  return (
    <p data-testid={label}>
      {label} mounted at {at ?? "..."}
    </p>
  );
}
----

.components/book-nav.tsx
[source,tsx]
----
"use client";

import Link from "next/link";
import { useSelectedLayoutSegment } from "next/navigation";

export function BookNav({ books }: { books: { id: string; title: string }[] }) {
  const active = useSelectedLayoutSegment(); // "2" on /books/2/reviews, null on /books
  return (
    <ul>
      {books.map((b) => (
        <li key={b.id}>
          <Link
            href={`/books/${b.id}`}
            aria-current={active === b.id ? "page" : undefined}
          >
            {b.title}
          </Link>
        </li>
      ))}
    </ul>
  );
}
----

== URL to Component Tree

The diagram maps one request through the three views of the Bookshelf: the folders, the URL segments they stand for,
and the component tree React renders.

The mapping has a few rules that explain every behaviour in this page:

. *Segments are matched left to right, one per folder.* `/books/2/reviews` matches `app`, `books`, `[id]` and
  `reviews`.
. *Each segment on the path contributes at most one layout, and the last segment contributes the page.* Layouts nest
  from the root down; each receives the next level as `children`. The tree for `/books/2/reviews` is `RootLayout`,
  containing `BooksLayout`, containing `ReviewsPage`. There is no layout in `[id]` or `reviews`, so those segments
  add only a param and a page.
. *A page is a leaf.* `books/[id]/page.tsx` is the leaf of `/books/2`; it is *not* an ancestor of
  `/books/2/reviews`, even though its folder is. The two pages are siblings below the same layout.
. *Params flow down.* `params` is `{ id: '2' }` for the page and, if it declared them, for layouts below the
  `[id]` segment. A layout above a dynamic segment does not see it.
. *Layouts do not receive the URL.* A layout is shared by many URLs, so it has no `searchParams` and no pathname.
  To react to the URL from a layout, use a Client Component with `usePathname()`, `useSelectedLayoutSegment()` or
  `useSelectedLayoutSegments()`, as `BookNav` does.

[#navigation]
== Navigation: Soft versus Hard

Two things can change the URL: a *hard navigation*, in which the browser requests a new HTML document and throws the
old one away, and a *soft navigation* (the docs call it a *client-side transition*), in which Next.js fetches the
RSC payload of the next route and swaps it into the running page.

[#navigation-apis]
=== The APIs that navigate

[cols="2,2,3",options="header"]
.Ways to go to another route
|===
| API | Kind | Use it for

| `<Link href="/books">` from `next/link`
| Soft
| The default for every in-app link. Renders an `<a>`, so it is accessible, crawlable and works with Ctrl/Cmd+click.
Prefetches the route when it enters the viewport.

| `router.push(href)`, `router.replace(href)` from `useRouter()` in `next/navigation`
| Soft
| Navigation from event handlers and effects in Client Components (after a form, on a timer). `replace` does not add
a history entry. Never use for plain links: it is not an `<a>`.

| `redirect(url)` and `permanentRedirect(url)` from `next/navigation`
| Soft on the client; a 307 (`redirect`) or 308 (`permanentRedirect`) response on the server
| Redirecting from Server Components, Server Actions and Route Handlers.

| `window.history.pushState` / `replaceState`
| Soft, URL only
| Changing the query string or path without any server work. They integrate with `usePathname` and
`useSearchParams`.

| A plain `<a href="/books">`, `window.location.assign()`, typing a URL, reload, a link to another origin
| *Hard*
| External links, downloads, and routes that must reload the document.
|===

Source: https://nextjs.org/docs/app/api-reference/components/link[Link],
https://nextjs.org/docs/app/api-reference/functions/use-router[useRouter] and
https://nextjs.org/docs/app/getting-started/linking-and-navigating#native-history-api[Linking and Navigating: native History API]

Two small hooks answer "where am I?": `usePathname()` returns the pathname (`/books/2/reviews`) and
`useParams()` returns the dynamic params; both are in `next/navigation` and work only in Client Components. They are
not interchangeable with the Pages Router's `next/router`, as the comparison later shows.

[#soft-vs-hard]
=== What happens on a click

The sequence below follows a click on a `Link` to `/books/2` while the user is on `/books` (soft), and a click on a
plain `<a>` to the same URL (hard). It was checked in a real browser; see the evidence after the diagram.

[mermaid]
....
sequenceDiagram
  autonumber
  actor U as User
  participant B as Browser, running page
  participant R as Next.js client router
  participant S as Next.js server
  Note over B,S: Soft navigation (Link, router.push)
  U->>R: click on Link to /books/2
  R->>R: prefetched? use the cached RSC payload
  R->>S: GET /books/2?_rsc=hash (only if not cached)
  S-->>R: RSC payload of the changed segments
  R->>B: React transition: swap the page, keep the layouts
  R->>B: history.pushState, scroll to the new page
  Note over B,S: Hard navigation (plain a, reload, typed URL)
  U->>B: click on a plain a href
  B->>S: GET /books/2 (new HTML document)
  S-->>B: HTML plus RSC payload plus script tags
  B->>B: discard the old page, new document, hydrate everything
....

The second diagram shows the decision the router takes for every link, including the cases that turn a soft
navigation into a hard one.

Evidence from the Bookshelf, in Chromium against `next start`. The layout of `books` records its mount time in
`MountedAt`. Clicking `Link`s from `/books/1` to `/books/2` and then to `/books/2/reviews`:

* the URL changed to `/books/2` and `/books/2/reviews`, the `<h1>` changed, and the active link in `BookNav` followed
  (`useSelectedLayoutSegment()` returned `2`);
* the layout's timestamp text did *not* change, and a marker property set on `window` before the first click was
  still there afterwards, so no new document was loaded;
* the browser requested URLs such as `/books/2?_rsc=<hash>` -- the RSC payload, not HTML;
* navigating on to `/about`, which is outside the `books` layout, removed the layout entirely, and going back to
  `/books` mounted it again with a new timestamp.

A hard navigation does exactly the opposite: `MountedAt` shows a new time, `window` state is gone and the browser
asks for a full document.

Source: https://nextjs.org/docs/app/getting-started/linking-and-navigating#client-side-transitions[Linking and Navigating: client-side transitions]

Four things turn out to be hard navigations in practice:

* *Using `<a>` instead of `Link`.* It works, but it reloads the document and gets no prefetching.
* *Crossing root layouts.* If a route group defines its own root layout (`app/(shop)/layout.tsx` with `<html>` and
  `<body>`), moving between two root layouts is a full page load, because the document itself differs.
* *Links to files and other origins*, and links with a `download` attribute.
* *The first request of every visit*, by definition: HTML is generated for the initial visit.

[#partial-rendering]
== Partial Rendering of Shared Layouts

A soft navigation does not re-render the page: it re-renders *what differs*. When you go from `/books/2` to
`/books/2/reviews`, the root layout and the books layout are the same, so React keeps them: their client state, their
DOM, their focus, and any scroll position inside them survive, and their server-rendered output is not requested
again. Only the `[id]` page is replaced by the `reviews` page. The docs state it in one sentence: *on navigation,
layouts preserve state, remain interactive, and do not rerender*.

Three mechanisms cooperate:

. *Prefetching.* A `Link` that enters the viewport prefetches its route in the background. For a static route the whole
  route is prefetched; for a dynamic route, down to the nearest `loading` file, so the shared layouts and the loading
  fallback are ready before the click. `+prefetch={false}+` turns it off for long lists of links. Prefetching is enabled in
  production only (not in `next dev`), and it only starts after `Link` has hydrated.
. *Layout deduplication and incremental prefetching* (Next.js 16). When many prefetched URLs share a layout, the
  layout payload is downloaded once, and only the parts not already in the client cache are requested. You may see
  more, smaller prefetch requests than in Next.js 15; the total transfer is lower.
. *Streaming and `loading`.* If the target page is dynamic, the server streams the changed part. A `loading` file
  (or a `<Suspense>` boundary) lets the router show a fallback immediately and keep the shared layouts interactive and
  the navigation interruptible.

The corollary is a design rule: *put state and expensive UI in the layout, and the things that change in the page.*
The reverse also holds, and is the most common surprise: *a layout does not re-run when the URL changes within it*.
Code that must run on every navigation (a page-view counter, a form that resets, a `useEffect` with a per-page
effect) does not belong in a layout; it belongs in the page or in a `template`, which remounts on every navigation
and has its own page in this section.

Source: https://nextjs.org/docs/app/getting-started/linking-and-navigating#prefetching[Prefetching],
https://nextjs.org/docs/app/guides/prefetching[Prefetching guide] and
https://nextjs.org/docs/app/guides/upgrading/version-16[Upgrading to version 16: incremental prefetching]

[#pages-router]
== The Pages Router Equivalent

The Pages Router is still supported and is what the two books in this section's bibliography teach. Its idea is
the same (file-system routing, `Link`, client-side transitions) but the mapping is *file to route*, not *folder to
segment*, and there is no built-in nesting of layouts.

[cols="2,2",options="header"]
.The Bookshelf in the `pages/` directory
|===
| File | URL

| `pages/index.tsx`
| `/`

| `pages/legacy/books/index.tsx`
| `/legacy/books`

| `pages/legacy/books/[id].tsx`
| `/legacy/books/2`

| `pages/_app.tsx`
| Not a route: the wrapper around every page. A "layout for everyone" is written here.
|===

Source: https://nextjs.org/docs/pages/building-your-application/routing/pages-and-layouts[Pages Router: Pages and Layouts]
and https://nextjs.org/docs/pages/building-your-application/routing/dynamic-routes[Pages Router: Dynamic Routes]

Layouts are a pattern, not a convention: you write a layout component, and a page can export a `getLayout`
function. `_app` applies it. Because the same React component sits at the same place before and after the
transition, React keeps its state, which is the Pages Router's version of "layouts persist".

.pages/_app.tsx: the layout pattern from the official docs, typed
[source,tsx]
----
import type { AppProps } from "next/app";
import type { NextPage } from "next";
import type { ReactElement, ReactNode } from "react";

type PageWithLayout = NextPage & {
  getLayout?: (page: ReactElement) => ReactNode;
};

export default function MyApp({
  Component,
  pageProps,
}: AppProps & { Component: PageWithLayout }) {
  const getLayout = Component.getLayout ?? ((page: ReactElement) => page);
  return getLayout(<Component {...pageProps} />);
}
----

.pages/legacy/books/[id].tsx: a dynamic page with `next/router`
[source,tsx]
----
import Link from "next/link";
import { useRouter } from "next/router";
import type { ReactElement } from "react";
import { LegacyShelfLayout } from "@/components/legacy-shelf-layout";

export default function LegacyBookPage() {
  const router = useRouter();
  const { id } = router.query; // string | string[] | undefined
  return (
    <main>
      <h1>Legacy book {id}</h1>
      <Link href="/legacy/books/1">Book 1</Link>{" "}
      <Link href="/legacy/books/2">Book 2</Link>
    </main>
  );
}

LegacyBookPage.getLayout = function getLayout(page: ReactElement) {
  return <LegacyShelfLayout>{page}</LegacyShelfLayout>;
};
----

Run in the same scratch app, `next build` listed the page under `Route (pages)` as static (`○ /legacy/books/[id]`),
and clicking from `Book 1` to `Book 2` kept `LegacyShelfLayout` mounted (its mount timestamp did not change), as in
the App Router. Two differences show in the raw HTML. First, the HTML of `/legacy/books/2` contained
`<h1>Legacy book </h1>` with no id and `"query":{}` in the embedded `__NEXT_DATA__` JSON: a page without
`getServerSideProps` is statically optimised, so `router.query` is empty on the server and during hydration, and the
real value appears only after the router is ready on the client. That is the Pages Router's well-known `isReady`
gotcha; the App Router has no equivalent, because `params` is passed to the page on the server. Second, the page is a
Client Component by nature (it uses a Hook), while an App Router page is a Server Component by default.

Source: https://nextjs.org/docs/pages/api-reference/functions/use-router[Pages Router: useRouter] and
https://nextjs.org/docs/pages/building-your-application/routing/pages-and-layouts#per-page-layouts[Per-page layouts]

*Both routers can coexist in one project*, which is how an incremental migration works: `app/` and `pages/` side by
side, `Link` navigating between them (a hard navigation between the two routers). They must not define the same URL.
Adding `pages/about.tsx` next to the Bookshelf's `app/(marketing)/about/page.tsx` fails `next build` with:

[source,text]
----
Error: App Router and Pages Router both match path: /about
Next.js does not support having both App Router and Pages Router routes matching the same path. Please remove one of the conflicting routes.
----

Source: https://nextjs.org/docs/app/guides/migrating/app-router-migration[Migrating to the App Router]

[#cache-components]
== Under Cache Components

Routing does not change with `cacheComponents: true`, but two reads that the previous model tolerates are rejected
at build time if they are not inside `<Suspense>`: *runtime data* (`params` of a segment that has no
`generateStaticParams`, `searchParams`, `cookies()`, `headers()`) and *routing hooks* such as `usePathname()` and
`useSelectedLayoutSegment()`. The first build of this page's example without the final changes failed under Cache
Components with `blocking-prerender-client-hook` (a hook read outside `<Suspense>`) and
`blocking-prerender-dynamic` (`params` awaited outside `<Suspense>`). Both are fixed in the code above:
`BookNav` is wrapped in a `Suspense` boundary in the layout, and both pages declare `generateStaticParams`, so the
params are known at build time. With those two changes the same files build in both models; with
`CACHE_COMPONENTS=1` the build succeeded and the route table marked the `/books/[id]` and
`/books/[id]/reviews` entries `◐ Partial Prerender`, next to the prerendered `○` paths for ids 1 to 3. The caching and Partial Prerendering pages of this section explain the model; the two errors
are documented at https://nextjs.org/docs/messages/blocking-prerender-client-hook[blocking-prerender-client-hook]
and https://nextjs.org/docs/messages/blocking-prerender-dynamic[blocking-prerender-dynamic].

The probe `MountedAt` itself needs care: a first version computed `new Date()` in the `useState` initialiser and was
rejected by Cache Components (`blocking-prerender-current-time-client`), because the value would be frozen at build
time. Reading the clock in an effect, as above, is the fix. The *Instant Navigations* of Next.js 16.3 (`cacheComponents`
plus `partialPrefetching`) go one step further: the per-route app shell is prefetched so that a click shows the
static and cached part of the next route at once. They are opt-in in 16.3.8 and are covered in the navigation page
of this section.

Source: https://nextjs.org/docs/app/guides/instant-navigation[Instant navigation]

[#pitfalls]
== Pitfalls

[cols="3,3,3",options="header"]
.Common routing mistakes and their fixes
|===
| Symptom | Cause | Fix

| A route returns 404 although the folder exists
| The folder has no `page` (or `route`) file, or the file is named `Page.tsx` or `index.tsx`. Reserved names are
lower-case: `page`, `layout`, `route`.
| Add `page.tsx`. In the App Router `index.tsx` has no special meaning.

| A new file next to a `page` suddenly shows up as a URL
| It was named `page`, or `route`, or a metadata convention such as `icon`, by accident.
| Rename it. Other names are safe to colocate; use a `_private` folder to be explicit.

| `Error: App Router and Pages Router both match path`
| The same URL is defined in `app/` and `pages/`, or two route groups resolve to the same path.
| Remove one definition; migrate a route at a time.

| `params.id` is `undefined`, or `Property 'id' does not exist on type 'Promise'`
| Since Next.js 15 `params` is a Promise; Next.js 16 removed synchronous access.
| `const { id } = await params;` in an `async` function. In a Client Component, `use(params)`.

| The layout does not update when I navigate
| By design: a layout is kept alive within its segment. It receives neither the URL nor new `searchParams`.
| Read the URL in a Client Component (`usePathname`, `useSelectedLayoutSegment`), or move the code to the page or to a
`template`.

| The whole page reloads, the layout state is lost and links are not prefetched
| A plain `<a>` was used, or navigation crossed two root layouts, or `window.location` was assigned.
| Use `Link` or `router.push`; keep one root layout unless the groups really are different documents.

| `useRouter` imported from `next/router` in `app/`: `NextRouter was not mounted`
| The Pages Router's router is not available in the App Router.
| Import from `next/navigation`; use `usePathname`, `useSearchParams` and `useParams` instead of `router.query`. In
`pages/`, `next/compat/router` is the variant that does not throw.

| `router.query` is empty on first render (Pages Router)
| Automatic static optimisation: the router is not ready until the client has hydrated.
| Wait for `router.isReady` in an effect, or read the value in `getServerSideProps` or `getStaticProps`.

| Active-link highlighting is wrong or the build says "outside of Suspense"
| `usePathname()`, `useSelectedLayoutSegment()` or `params` read in a layout that is prerendered under Cache
Components.
| Wrap the Client Component in `<Suspense>` and give dynamic segments `generateStaticParams`.

| Search crawlers or users see `/books/99` as 200 with an empty page
| `notFound()` was thrown inside a streamed `<Suspense>` boundary after the response status was already sent.
| Decide existence outside any `<Suspense>` boundary (as `BookPage` does), or accept a 200 and add `noindex`. The
streaming page of this section covers the details.

| Many tiny prefetch requests after upgrading to 16
| Layout deduplication and incremental prefetching split prefetches into smaller requests.
| Expected; the total bytes are lower. Use `+prefetch={false}+` on very long lists of links.

| `<Link>` inside `<Link>`, or a button wrapped in a link
| Invalid HTML: it renders nested `<a>` or an `<a>` containing interactive content, which breaks keyboard and
screen-reader behaviour.
| Style the `Link` as a button, or use `router.push` in a `button`'s handler.
|===

[#changed-since-13-14]
== What Changed Since Next.js 13 and 14

The App Router reached *stable* in Next.js 13.4; most tutorials and both books in the bibliography were written before
13.4, or with the Pages Router. This is the routing-relevant history, with the version where each change landed.
Dates come from the version-history tables of the official pages and the release posts.

[cols="1,4",options="header"]
.Routing-relevant changes
|===
| Version | Change

| 13.0
| `app/` introduced, with `page` and `layout`. `<Link>` no longer needs a child `<a>`. The `useRouter` hook in
`next/navigation` is introduced next to the Pages Router's `next/router`.

| 15.0 (2024-10-21)
| `params` and `searchParams` of pages (and `params` of layouts) become *Promises*. A codemod exists. Client router cache: `staleTimes.dynamic` defaults to 0 (pages are not reused from the
cache for 30 seconds any more).

| 15.3
| `onNavigate` on `Link`.

| 15.4
| `prefetch="auto"` is an alias of the default `Link` prefetch behaviour; `router.prefetch` accepts `onInvalidate`.

| 16.0 (2025-10-21)
| Synchronous access to `params` and `searchParams` is *removed*. Prefetch cache rewritten: layout deduplication and
incremental prefetching. Parallel route slots require an explicit `default` file. Turbopack is the default
bundler. `middleware.ts` is renamed to `proxy.ts`.

| 16.2 (2026-03-18)
| `Link` accepts `transitionTypes` for the View Transition API (the `router.push` and `router.replace` options take
it too in the 16.3.8 docs).

| 16.3 (2026-08-03)
| *Instant Navigations* (opt-in, needs `cacheComponents` and `partialPrefetching`): the per-route app shell is
prefetched so a click shows static and cached UI immediately. `next/root-params` gives Server Components access to
the root-level params (such as a locale). Both are covered by later pages of this section.
|===

[#books-outdated]
== Where the Books Are Outdated

The two books that this section consulted (published in 2022 and 2023) teach routing with the Pages Router, `pages/`,
`getStaticProps` and `getServerSideProps`; the second one also touches the first App Router files of 13.x, such as
`head.js`, which no longer exist. What to take, and what to replace:

[cols="2,3",options="header"]
.Outdated routing advice and the current approach
|===
| In the books | Current approach

| Routing means files under `pages/`, with `getStaticProps`/`getServerSideProps` next to each page.
| The App Router is the recommended router: folders and `page` files, async Server Components, `generateStaticParams`.
The Pages Router is supported, and both can coexist while you migrate.

| Dynamic routes read `router.query.slug` with `useRouter` from `next/router`.
| In `app/`, `params` is a prop of `page` and `layout` (a Promise since 15, awaited), and the hooks are in
`next/navigation`. `router.query` still applies in `pages/`.

| `<Link href="..."><a>text</a></Link>` and `passHref` on a child.
| `Link` renders its own `<a>`; the child `<a>` stopped being required in 13. The `legacyBehavior` prop of older
versions is not part of the current `Link` documentation.

| A persistent layout needs `getLayout` in `_app`.
| A `layout` file per folder gives nested layouts that persist without extra code.

| A custom Express or Fastify server for routing rules.
| Next.js routes by file system; redirects, rewrites and headers go in `next.config.ts` and request-time logic goes in
`proxy.ts`. Custom servers are rarely justified.

| Locale routing with the `i18n` key of `next.config.js` (Pages Router only).
| `app/[locale]` segments with locale detection in `proxy.ts`; the i18n page of this section shows it.
|===

== Summary

* Routing is the function from URL to component tree. A SPA computes it in the browser from a route table you
  write; Next.js computes it on the server from the folder structure, and the client router avoids document reloads.
* Folders are segments, `page` makes them public, `layout` wraps the segment and everything below, and anything else
  is colocated and private. `[id]`, `[...slug]`, `[[...slug]]` and `(group)` shape params and URLs.
* The tree for a URL is root layout, nested layouts, then one page; the page is a leaf, not an ancestor of its
  child routes.
* Soft navigation (`Link`, `router.push`) fetches an RSC payload and keeps shared layouts alive; hard navigation
  (`<a>`, reload, crossing root layouts) is a new document.
* The Pages Router does the same by files and by `_app`; coexistence is allowed but URLs must not overlap.
