[#what-conventions-are]
== Conventions, Not Configuration

Next.js discovers your application from the file system. A folder inside `app` is a *route segment*; a small set of
reserved file names inside it gives the segment a UI, a boundary or an endpoint; everything else is yours. The
official page is explicit that Next.js is unopinionated about how you organise and colocate the rest of your
project, and gives you tools (colocation, private folders, route groups, `src`) rather than a mandatory layout.

Three rules explain almost everything that follows:

* *Folders define URL segments.* Nesting folders nests segments, and a layout at any level wraps all of its child
segments.
* *Only special file names do anything.* A route becomes publicly reachable only when it contains a `page` or a
`route` file (or a metadata route such as `sitemap.ts`). Any other file next to them is just a module.
* *Names in brackets or parentheses are syntax*, not folder names: `[id]` is a dynamic segment, `(group)` is
invisible in the URL, `_folder` is invisible to routing, `@slot` is a named slot and `(.)folder` intercepts a route.

Source: https://nextjs.org/docs/app/getting-started/project-structure[Project structure and organization]

[#top-level-folders]
== Top-Level Folders

[cols="1,2,3",options="header"]
.Top-level folders of a Next.js project
|===
| Folder | Purpose | Notes

| `app`
| The App Router: file-system routes, layouts, Server Components and Route Handlers.
| The recommended router for new projects. A root layout (with `<html>` and `<body>`) is required.

| `pages`
| The Pages Router: one file per route, `getStaticProps`/`getServerSideProps`, `pages/api`.
| Still supported; both routers can live in the same project, which is how incremental migration works.

| `public`
| Static assets served from the base URL: `public/avatars/me.png` is served at `/avatars/me.png`.
| Next.js cannot safely cache these files, so it sends `Cache-Control: public, max-age=0`. For `robots.txt`,
favicons and similar files use the metadata file conventions inside `app` instead.

| `src`
| Optional folder that holds `app` or `pages` (and usually `components`, `lib`, `proxy.ts`) so that application code is
separated from configuration files at the root.
| `public`, `package.json`, `next.config.*`, `tsconfig.json` and `.env*` files stay in the project root. See
<<src-folder,the src folder>> below.
|===

A freshly generated project and the final _Bookshelf_ both contain a top-level `public` folder. This is the
behaviour of a file in `public`, as served by the scratch project:

[source,bash]
.A file in public/ is served from the root, with the default caching header
----
$ curl -sI localhost:3203/file.svg | grep -i -E "^(HTTP|content-type|cache-control)"
HTTP/1.1 200 OK
Cache-Control: public, max-age=0
Content-Type: image/svg+xml
----

[#top-level-files]
== Top-Level Files

Top-level files configure the application, manage dependencies, run the Proxy, integrate monitoring and define
environment variables.

[cols="2,3,3",options="header"]
.Top-level files (project root, or inside `src` where noted)
|===
| File | Purpose | Notes

| `next.config.ts` (also `.js`, `.mjs`)
| Configuration of Next.js itself.
| `next.config.ts` is supported for TypeScript projects. Always in the project root.

| `package.json`
| Dependencies and scripts (`dev`, `build`, `start`).
| Minimum manual install: `next`, `react`, `react-dom`.

| `proxy.ts` (also `.js`)
| The Proxy: code that runs on the server before a request is completed (rewrite, redirect, header changes).
| Same level as `app` or `pages`, so inside `src` when you use `src`. Renamed from `middleware.ts` in Next.js 16.

| `instrumentation.ts` (also `.js`)
| Server-side observability hook: `register()` once per server instance and optional `onRequestError()`.
| Root, or inside `src`. Stable since Next.js 15.

| `instrumentation-client.ts` (also `.js`)
| Client-side code that runs after the HTML is loaded and before React hydration starts; may export
`onRouterTransitionStart`.
| Root, or inside `src`. Introduced in Next.js 15.3.

| `mdx-components.tsx` (also `.js`)
| Required to use `@next/mdx` with the App Router; defines the components MDX content uses.
| Root, or inside `src`, at the same level as `app` or `pages`.

| `.env`, `.env.local`, `.env.development`, `.env.production`
| Environment variables.
| Should not be tracked by version control (at least `.env.local`). The load order and the `NEXT_PUBLIC_` rules are
covered on the configuration page.

| `eslint.config.mjs`
| ESLint flat configuration.
| Linting runs through the ESLint CLI; `next lint` was removed in Next.js 16.

| `tsconfig.json` / `jsconfig.json`
| TypeScript or JavaScript configuration, including `paths` aliases.
| Next.js adds the `next` TypeScript plugin and its generated type folders.

| `next-env.d.ts`
| Generated TypeScript declarations for Next.js.
| Generated; should not be tracked by version control.

| `.gitignore`
| Files and folders Git ignores.
| Must cover `.next/`, `node_modules/` and `.env*` files.

| `AGENTS.md`, `CLAUDE.md`
| Instructions for AI coding agents. The Next.js block points agents at the version-matched documentation bundled in
`node_modules/next/dist/docs/`.
| Generated by `create-next-app` (opt out with `--no-agents-md`); `CLAUDE.md` contains the single line `@AGENTS.md`.
|===

Two of these files are worth showing because they run in places a component never does. `instrumentation.ts`

The Proxy file follows the same placement rule. The _Bookshelf_ one redirects every request that has no locale
prefix; its `matcher` leaves API routes, `_next` assets and files with an extension (such as `/file.svg` or
`/favicon.ico`) alone, which matters because without a matcher the Proxy runs on every request, including static
files.

[source,ts]
.proxy.ts - the exported function is named proxy
----
import { NextResponse, type NextRequest } from "next/server";
import { locales, defaultLocale } from "@/lib/i18n";

export function proxy(request: NextRequest) {
  const { pathname } = request.nextUrl;
  if (locales.some((l) => pathname === `/${l}` || pathname.startsWith(`/${l}/`))) {
    return NextResponse.next();
  }
  return NextResponse.redirect(new URL(`/${defaultLocale}${pathname}`, request.url));
}

export const config = {
  matcher: ["/((?!api|_next|.*\\..*).*)"],
};
----

Source: https://nextjs.org/docs/app/api-reference/file-conventions/proxy[proxy.js]

[#file-convention-table]
== The File-Convention Table

The next four tables list every file convention of the App Router, derived from the project-structure page and the
File-system conventions reference of the 16.3.8 documentation. Where a file has a JavaScript and a TypeScript form,
the table gives the accepted extensions.

[#routing-files]
=== Routing Files

[cols="2,2,5",options="header"]
.Routing files of the App Router (every one lives inside a route segment folder)
|===
| File | Extensions | What it does

| `layout`
| `.js` `.jsx` `.tsx`
| Shared UI that wraps the segment and its children. Preserves state and does not re-render on navigation between
child routes. The root layout (`app/layout`) must define `<html>` and `<body>`.

| `page`
| `.js` `.jsx` `.tsx`
| The UI unique to a route and what makes the segment publicly accessible. Always the leaf of the route subtree; a
Server Component by default. Receives `params` and `searchParams` as promises.

| `loading`
| `.js` `.jsx` `.tsx`
| An instant loading state: Next.js wraps the segment's `page` and children in a React Suspense boundary and uses
this file as the fallback while content streams in.

| `not-found`
| `.js` `.jsx` `.tsx`
| UI rendered when `notFound()` is thrown inside the segment; the root `app/not-found` also handles unmatched URLs.

| `global-not-found`
| `.js` `.jsx` `.tsx`
| Experimental (since 15.4, behind `experimental.globalNotFound`). One 404 page for the whole app that bypasses
rendering of any layout, so it must define its own `<html>` and `<body>`. Useful with multiple root layouts.

| `error`
| `.js` `.jsx` `.tsx`
| A React error boundary (a Client Component) for the segment's `page` and children, with a `retry` function.
Does not catch errors of the layout or template of the same segment.

| `global-error`
| `.js` `.jsx` `.tsx`
| Replaces the root layout when an error escapes it; must define its own `<html>` and `<body>`. Lives in the root
`app` folder.

| `route`
| `.js` `.ts`
| A Route Handler: an endpoint exporting `GET`, `POST` and the other HTTP method functions. A segment cannot have both
`route` and `page`.

| `template`
| `.js` `.jsx` `.tsx`
| Like a layout, but a new instance is mounted for each child on navigation, so state is reset and effects re-run.

| `default`
| `.js` `.jsx` `.tsx`
| Fallback for a parallel-route slot (and the implicit `children` slot) when Next.js cannot recover the slot's active
state after a full page load.

| `forbidden`
| `.js` `.jsx` `.tsx`
| UI for the `forbidden()` function (HTTP 403). Experimental, needs `experimental.authInterrupts`; introduced in 15.1.

| `unauthorized`
| `.js` `.jsx` `.tsx`
| UI for the `unauthorized()` function (HTTP 401). Experimental, needs `experimental.authInterrupts`; introduced in
Next.js 15.1.
|===

Sources: https://nextjs.org/docs/app/api-reference/file-conventions/layout[layout.js], https://nextjs.org/docs/app/api-reference/file-conventions/page[page.js], https://nextjs.org/docs/app/api-reference/file-conventions/loading[loading.js], https://nextjs.org/docs/app/api-reference/file-conventions/not-found[not-found.js], https://nextjs.org/docs/app/api-reference/file-conventions/error[error.js], https://nextjs.org/docs/app/api-reference/file-conventions/route[route.js], https://nextjs.org/docs/app/api-reference/file-conventions/template[template.js], https://nextjs.org/docs/app/api-reference/file-conventions/default[default.js], https://nextjs.org/docs/app/api-reference/file-conventions/forbidden[forbidden.js], https://nextjs.org/docs/app/api-reference/file-conventions/unauthorized[unauthorized.js]

Several of these are one-file examples. The error boundary and the 401/403 files are the ones people most often get
wrong, so here they are as built in the scratch project. `error.tsx` must be a Client Component and receives `retry`
(stable in 16.3.0; `unstable_retry` in 16.2). The `forbidden.tsx` and `unauthorized.tsx` files sit in the root of `app`
and only render once `experimental.authInterrupts` is on and a page calls `forbidden()` or `unauthorized()`.

[source,tsx]
.error.tsx, forbidden.tsx and the page that triggers it
----
// app/[locale]/(shop)/books/[id]/error.tsx
"use client";

export default function BookError({ retry }: { error: Error; retry: () => void }) {
  return <button onClick={() => retry()}>Try again</button>;
}

// app/forbidden.tsx
export default function Forbidden() {
  return <h1>403 - you may not see this</h1>;
}

// app/[locale]/(account)/admin/page.tsx
import { forbidden } from "next/navigation";
import { getUser } from "@/lib/dal";

export default async function AdminPage() {
  const user = await getUser();
  if (user?.id !== "admin") forbidden();
  return <h1>Admin</h1>;
}
----

[source,ts]
.next.config.ts - the flag that enables forbidden() and unauthorized()
----
import type { NextConfig } from "next";

const nextConfig: NextConfig = {
  experimental: { authInterrupts: true },
};

export default nextConfig;
----

anyone without a cookie is redirected by the account layout (the scratch session cookie only stands in for a real
session; real authentication belongs to the Data Access Layer, as the authentication page shows):

[#folder-conventions]
=== Folder Conventions

Folder names carry the rest of the routing syntax.

[cols="2,3,4",options="header"]
.Folder name conventions
|===
| Pattern | Example | Meaning

| `folder`
| `app/blog/authors/page.tsx` is `/blog/authors`
| A route segment.

| `[segment]`
| `app/blog/[slug]/page.tsx` is `/blog/my-first-post`
| A dynamic segment; the value arrives in `params`.

| `[...segment]`
| `app/shop/[...slug]/page.tsx` is `/shop/clothing/shirts`
| Catch-all segment.

| `[[...segment]]`
| `app/docs/[[...slug]]/page.tsx` is `/docs` and `/docs/layouts-and-pages`
| Optional catch-all segment.

| `(group)`
| `app/(shop)/cart/page.tsx` is `/cart`
| Route group: organisation only, omitted from the URL.

| `_folder`
| `app/blog/_components/Post.tsx` is not routable
| Private folder: the folder and all its subfolders are opted out of routing. Use `%5Ffolder` for a URL segment that
starts with an underscore.

| `@slot`
| `app/@team/page.tsx`
| Named slot, rendered by the parent layout as a prop.

| `(.)folder`
| `app/[locale]/@modal/(.)books/[id]`
| Intercept a route at the same level.

| `(..)folder`
| `app/feed/(..)photo/[id]`
| Intercept a route one level up (segments, not folders: groups and slots do not count).

| `(..)(..)folder`
| two levels up
| Intercept two levels up.

| `(...)folder`
| from the root `app`
| Intercept from the root.
|===

Sources: https://nextjs.org/docs/app/api-reference/file-conventions/dynamic-routes[Dynamic Segments], https://nextjs.org/docs/app/api-reference/file-conventions/parallel-routes[Parallel Routes], https://nextjs.org/docs/app/api-reference/file-conventions/intercepting-routes[Intercepting Routes]

[#metadata-files]
=== Metadata Files

File-based metadata is defined by adding special files to route segments. Each convention has a static form (an
image or text file) and a generated form (a `.js`, `.ts` or `.tsx` file that exports a function); Next.js serves the
file (with hashes in production for caching) and adds the matching tags to the page head. When you use a Proxy, the
metadata files must be excluded in its `matcher`.

[cols="2,3,3,3",options="header"]
.Metadata file conventions
|===
| File | Static extensions | Generated extensions | Valid location

| `favicon`
| `.ico`
| (none)
| Root of `app` only.

| `icon`
| `.ico` `.jpg` `.jpeg` `.png` `.svg`
| `.js` `.ts` `.tsx`
| Any segment of `app`.

| `apple-icon`
| `.jpg` `.jpeg` `.png`
| `.js` `.ts` `.tsx`
| Any segment of `app`.

| `opengraph-image`
| `.jpg` `.jpeg` `.png` `.gif`
| `.js` `.ts` `.tsx`
| Any route segment (alt text in an `opengraph-image.alt.txt` beside it).

| `twitter-image`
| `.jpg` `.jpeg` `.png` `.gif`
| `.js` `.ts` `.tsx`
| Any route segment.

| `sitemap`
| `.xml`
| `.js` `.ts`
| Root of `app`, or nested in segments to split a sitemap.

| `robots`
| `.txt`
| `.js` `.ts`
| Root of `app`.

| `manifest`
| `.json` `.webmanifest`
| `.js` `.ts`
| Root of `app`.
|===

The _Bookshelf_ uses the generated form of four of them, plus a static `icon.svg`. Building them produced route-table
entries (they are special Route Handlers) and the tags shown below:

[source,ts]
.app/robots.ts, app/sitemap.ts and app/manifest.ts (three files, shown together)
----
// app/robots.ts
import type { MetadataRoute } from "next";

export default function robots(): MetadataRoute.Robots {
  return { rules: { userAgent: "*", allow: "/" } };
}

// app/sitemap.ts
import type { MetadataRoute } from "next";

export default function sitemap(): MetadataRoute.Sitemap {
  return [{ url: "https://bookshelf.example/en" }];
}

// app/manifest.ts
import type { MetadataRoute } from "next";

export default function manifest(): MetadataRoute.Manifest {
  return { name: "Bookshelf", short_name: "Bookshelf", start_url: "/en" };
}
----

[source,tsx]
.app/[locale]/(shop)/books/[id]/opengraph-image.tsx - a generated image for one segment
----
import { ImageResponse } from "next/og";
import { getBook } from "@/lib/books";

export const size = { width: 1200, height: 630 };
export const contentType = "image/png";

export default async function Image({
  params,
}: {
  params: Promise<{ locale: string; id: string }>;
}) {
  const { id } = await params;
  const book = await getBook(id);
  return new ImageResponse(
    <div style={{ display: "flex", fontSize: 72 }}>{book?.title ?? "Bookshelf"}</div>,
    size,
  );
}
----

The `og:image` URL uses the default `http://localhost:3000` base because no `metadataBase` was configured; a real
project sets `metadataBase` in its root metadata. The segment's image file gets a hashed name in the URL, as the
route table below shows.

[#component-hierarchy]
== Component Hierarchy

The components defined in special files are rendered in a fixed hierarchy, from the outside in: `layout.js`, then
`template.js`, then `error.js` (a React error boundary), then `loading.js` (a React Suspense boundary), then
`not-found.js` (a React error boundary for the "not found" UI) and finally `page.js` or a nested `layout.js`. In nested
routes the components of a segment are nested inside the components of its parent segment.

[mermaid]
....
flowchart TB
  subgraph L["layout.js - persists across navigations"]
    subgraph T["template.js - new instance for each navigation"]
      subgraph E["error.js - React error boundary"]
        subgraph S["loading.js - Suspense boundary"]
          subgraph N["not-found.js - boundary for notFound()"]
            P["page.js, or the nested layout.js of the child segment"]
          end
        end
      end
    end
  end
....

Two consequences follow from the nesting, and both are easy to get wrong:

* `error.js` sits *inside* the layout and template of its own segment, so it cannot catch their errors. An error in
the root layout needs `global-error.js`, which replaces the root layout while active.
* `loading.js` wraps the page and children but not the layout, so it never shows while the layout itself is slow;
a slow layout therefore blocks the segment's loading UI.

To see the order in the rendered output, the scratch project has a segment `app/[locale]/(shop)/demo` that contains all
of `layout`, `template`, `error`, `loading` and `page`, with a `data-file` attribute on each wrapper. The page calls
`connection()` so it is rendered at request time and the fallback is streamed first:

[source,tsx]
.The demo segment: one file per convention (error.tsx is a Client Component boundary and leaves no DOM)
----
// layout.tsx
export default function Layout({ children }: LayoutProps<"/[locale]/demo">) {
  return <div data-file="layout">{children}</div>;
}

// template.tsx
export default function Template({ children }: { children: React.ReactNode }) {
  return <div data-file="template">{children}</div>;
}

// loading.tsx
export default function Loading() {
  return <p data-file="loading">loading...</p>;
}

// page.tsx
import { connection } from "next/server";

export default async function Page() {
  await connection(); // request-time rendering, so loading.tsx is streamed first
  await new Promise((r) => setTimeout(r, 200));
  return <p data-file="page">page</p>;
}
----

[source,html]
.The initial HTML of /en/demo: layout contains template contains the Suspense fallback; the page arrives later
----
<div data-file="layout"><div data-file="template"><!--$?--><template id="B:0"></template><p data-file="loading">loading...</p><!--/$--></div></div>
...
<div hidden id="S:0">...</div>
<div hidden id="S:1"><p data-file="page">page</p></div>
----

The streamed `<div hidden>` chunks hold the page content that React swaps into the fallback's place, which is the
loading UI doing its job. The full hierarchy for a nested route repeats the box, with the child segment's `layout.js`
taking the place of `page.js` at each level until the leaf `page.js`.

Source: https://nextjs.org/docs/app/getting-started/project-structure#component-hierarchy[Component hierarchy]

[#colocation]
== Colocation

Because only `page` and `route` files make a segment public, and only their *returned content* is sent to the client,
project files can be safely colocated inside route segments without becoming routable. The decision tree is short:

[mermaid]
....
flowchart TD
  F["File inside app/"] --> Q1{"Inside a _private folder?"}
  Q1 -->|yes| NR1["Never routable, nor its subfolders"]
  Q1 -->|no| Q2{"File name is page, route or a metadata route?"}
  Q2 -->|no| NR2["Plain module - not routable, can be imported"]
  Q2 -->|yes| Q3{"Another page or route at the same URL?"}
  Q3 -->|yes| ERR["Build error: conflicting paths"]
  Q3 -->|no| R["Public route"]
....

The _Bookshelf_ book page keeps a helper and a test next to `page.tsx`:

[source,text]
.A segment with colocated files
----
app/[locale]/(shop)/books/[id]/
├── page.tsx           # routable: exports the page
├── format-title.ts    # colocated helper, imported by page.tsx
├── page.test.tsx      # colocated test
├── error.tsx
├── loading.tsx
└── opengraph-image.tsx
----

[source,ts]
.Colocated helper (format-title.ts) used by page.tsx
----
// A colocated helper: sits next to page.tsx but is not routable
export const formatTitle = (t: string) => t.toUpperCase();
----

[source,bash]
.Only the page is reachable; colocated files are 404
----
$ curl -s -o /dev/null -w "%{http_code}\n" localhost:3203/en/books/1
200
$ curl -s -o /dev/null -w "%{http_code}\n" localhost:3203/en/books/1/format-title
404
$ curl -s -o /dev/null -w "%{http_code}\n" localhost:3203/en/books/1/page.test
404
$ curl -s -o /dev/null -w "%{http_code}\n" localhost:3203/en/books/1/page
404
----

The two rules that look like the opposite of colocation are conflicts. A segment with both a `page` and a `route`, and two
route groups that resolve to the same URL, fail the build instead of picking a winner (messages from the scratch builds):

[source,text]
.Build errors for conflicting routes
----
Error: Conflicting route and page at /: route at /(shop)/route and page at /(shop)/page

Error: You cannot have two parallel pages that resolve to the same path. Please check /(account)/books and /(shop).
----

Colocation is optional. You can also keep project files outside `app`, in top-level folders such as `components` and
`lib` (the strategy the final _Bookshelf_ layout uses), or put top-level folders inside `app`, or split files by feature
under the route segments that use them; see <<organisation-strategies,Organisation strategies>>.

Source: https://nextjs.org/docs/app/getting-started/project-structure#colocation[Colocation]

[#private-folders]
== Private Folders

A folder prefixed with an underscore, `_folderName`, is a private implementation detail: it and every subfolder are
opted out of routing. Colocation already makes private folders unnecessary for safety, but they help to separate UI
logic from routing logic, to organise internal files consistently, to sort and group files in editors and to avoid
clashes with future Next.js file conventions. The _Bookshelf_ uses `_components` next to the pages that use the
components. To prove the opt-out, the scratch project also has a `page.tsx` inside a private `_internal` folder:

[source,text]
.A page.tsx inside a private folder, and the %5F escape for a real underscore segment
----
app/[locale]/(shop)/
├── _components/book-card.tsx   # imported by page.tsx
├── _internal/page.tsx          # a page, but inside a private folder
└── %5Fstatus/page.tsx          # URL segment that starts with an underscore
----

[source,bash]
.A private folder is invisible to routing; %5F produces an underscore URL
----
$ curl -s -o /dev/null -w "%{http_code}\n" localhost:3203/en/_internal
404
$ curl -s -o /dev/null -w "%{http_code}\n" localhost:3203/en/internal
404
$ curl -s -o /dev/null -w "%{http_code}\n" localhost:3203/en/_status
200
----

The route table (shown in full later) lists `/[locale]/_status` and has no entry for `_internal`.

Source: https://nextjs.org/docs/app/getting-started/project-structure#private-folders[Private folders]

[#route-groups]
== Route Groups

A route group is a folder wrapped in parentheses, `(folderName)`. It exists for organisation and is not part of the
URL. Typical uses are to organise routes by site section, intent or team, to share a layout between a subset of
routes of the same segment level, and to create multiple root layouts. In the _Bookshelf_, `(shop)` and `(account)`
share the `[locale]` segment and the URL space, yet have different layouts: the account layout requires a session and
the shop layout does not.

[source,tsx]
.app/[locale]/(account)/layout.tsx - a layout that applies to the account routes only
----
import { requireUser } from "@/lib/dal";
import { SiteHeader } from "@/components/ui/site-header";

export default async function AccountLayout({
  children,
  params,
}: LayoutProps<"/[locale]">) {
  const { locale } = await params;
  await requireUser(locale);
  return (
    <>
      <SiteHeader locale={locale} />
      {children}
    </>
  );
}
----

Everything the group does is invisible in the URL and in the route table:

[source,text]
.Folders and the URLs they produce
----
app/[locale]/(shop)/page.tsx                  /en
app/[locale]/(shop)/books/[id]/page.tsx       /en/books/1
app/[locale]/(account)/my-reviews/page.tsx    /en/my-reviews
app/[locale]/(account)/admin/page.tsx         /en/admin
----

The documentation shows three further uses of groups. To opt only some routes into a layout, move them into a group
with its own `layout.js`. To give one page a loading skeleton without affecting its siblings, put `loading.tsx` and
the page inside a group such as `(overview)`. And to partition an app into sections with completely different UI,
create multiple root layouts.

[#multiple-root-layouts]
=== Multiple Root Layouts

To create multiple root layouts, remove the top-level `layout.js` and add a `layout.js` with `<html>` and `<body>`
inside each route group. This was built in a second scratch project (a `(shop)` and an `(account)` group, no
`app/layout.tsx`):

[source,tsx]
.Two root layouts, one per route group
----
// app/(shop)/layout.tsx
export default function ShopRootLayout({ children }: LayoutProps<"/">) {
  return (
    <html lang="en">
      <body className="shop">{children}</body>
    </html>
  );
}

// app/(account)/layout.tsx
export default function AccountRootLayout({ children }: LayoutProps<"/">) {
  return (
    <html lang="en">
      <body className="account">{children}</body>
    </html>
  );
}
----

[source,bash]
.Each route gets the body of its own root layout
----
$ for u in / /books /my-reviews; do echo $u; curl -s localhost:3203$u | grep -o '<body[^>]*>'; done
/
<body class="shop">
/books
<body class="shop">
/my-reviews
<body class="account">
----

The caveats from the Route Groups reference are real constraints, not style advice. Navigating between routes that
use different root layouts triggers a *full page load* instead of a client-side navigation. Routes in different
groups must not resolve to the same URL (the second build error above). And if you use multiple root layouts with no
top-level `layout.js`, the home route `/` has to be defined inside one of the groups.

A root layout can also sit under a dynamic segment. The _Bookshelf_ does this: its root layout is
`app/[locale]/layout.tsx`, there is no `app/layout.tsx`, and the dynamic segments before the root layout are *root
parameters*, which any Server Component can read with `next/root-params`.

[source,tsx]
.app/[locale]/layout.tsx - the root layout of the Bookshelf, under a dynamic segment
----
import { notFound } from "next/navigation";
import { locales, isLocale } from "@/lib/i18n";

export function generateStaticParams() {
  return locales.map((locale) => ({ locale }));
}

export default async function RootLayout({
  children,
  modal,
  params,
}: LayoutProps<"/[locale]">) {
  const { locale } = await params;
  if (!isLocale(locale)) notFound();
  return (
    <html lang={locale}>
      <body>
        {children}
        {modal}
      </body>
    </html>
  );
}
----

Sources: https://nextjs.org/docs/app/api-reference/file-conventions/route-groups[Route Groups], https://nextjs.org/docs/app/api-reference/file-conventions/layout#root-layout[Root layout], https://nextjs.org/docs/app/api-reference/functions/next-root-params[next/root-params]

[#src-folder]
== The src Folder

Application code can live in an optional `src` folder, which separates it from the configuration files at the root.
Move `app` (or `pages`) to `src/app` (or `src/pages`). The reference lists what has to stay put and what must follow:

* `public`, `package.json`, `next.config.*`, `tsconfig.json` and `.env*` files stay in the project root.
* `src/app` or `src/pages` is ignored if `app` or `pages` exists in the root.
* The Proxy (`proxy.ts`) goes inside `src`; so do `instrumentation.ts` and `instrumentation-client.ts`.
* You will probably also move `components` and `lib` into `src`.
* If a `@/*` path alias exists, update its target in `tsconfig.json` so that it includes `src/`.
* If a `tailwind.config.js` file is used, add the `/src` prefix to its `content` paths.

The scratch _Bookshelf_ was converted in a copy, moving `app`, `components`, `lib`, `proxy.ts`, `instrumentation.ts`
and `instrumentation-client.ts` under `src/` and pointing the alias at `./src/*`. The build produced the identical
route table, and the server printed the same `register()` line:

[source,json]
.tsconfig.json when everything lives in src
----
{
  "compilerOptions": {
    "paths": {
      "@/*": ["./src/*"]
    }
  }
}
----

[#module-path-aliases]
== Module Path Aliases

Next.js has built-in support for the `paths` and `baseUrl` options of `tsconfig.json` and `jsconfig.json`, so imports
read `@/components/button` instead of `../../../components/button`. `create-next-app` offers an import alias (default
`@/*`), and with `--yes` it is set up for you. The configuration that the scratch project uses, and that the
generator writes, maps `@/*` to the project root with `paths` alone:

[source,json]
.tsconfig.json - the default alias
----
{
  "compilerOptions": {
    "plugins": [{ "name": "next" }],
    "paths": {
      "@/*": ["./*"]
    }
  }
}
----

[source,tsx]
.Using the alias from any depth
----
import { SiteHeader } from "@/components/ui/site-header";
import { getUser } from "@/lib/dal";
----

The reference also documents `baseUrl` (absolute imports relative to a folder) and several aliases whose targets are
relative to `baseUrl`. This was built in the `src` copy: with `baseUrl` set to `src/`, a second alias and a bare absolute
import both resolved, and the build passed.

[source,json]
.tsconfig.json - baseUrl plus several aliases
----
{
  "compilerOptions": {
    "baseUrl": "src/",
    "paths": {
      "@/*": ["./*"],
      "@ui/*": ["components/ui/*"]
    }
  }
}
----

[source,tsx]
.Imports that resolve with that configuration
----
import { SiteHeader } from "@ui/site-header"; // alias
import { requireUser } from "lib/dal";        // absolute import from baseUrl (src/)
----

Aliases are a TypeScript and bundler feature: they exist at compile time only, so they work in `app`, `pages`,
`proxy.ts` and route files alike. The TypeScript plugin, `typedRoutes` and the `PageProps`, `LayoutProps` and
`RouteContext` helpers are covered on the configuration and TypeScript page of this section.

Source: https://nextjs.org/docs/app/getting-started/installation#set-up-absolute-imports-and-module-path-aliases[Set up Absolute Imports and Module Path Aliases]

[#organisation-strategies]
== Organisation Strategies

The official examples are a high-level overview of common strategies; the stated takeaway is to choose one that works
for you and your team and to be consistent. `components` and `lib` are placeholders with no framework meaning; your
project might use `ui`, `utils`, `hooks` or `styles`.

[cols="2,4,3",options="header"]
.Common strategies for project files
|===
| Strategy | Layout | Good when

| Store project files outside `app`
| Shared code in folders at the project root; `app` contains only routing files.
| You want routing and implementation fully separate (the final _Bookshelf_ layout).

| Store project files in top-level folders inside `app`
| Shared code in folders in the root of `app`.
| You want everything under one folder.

| Split project files by feature or route
| Globally shared code in the root `app` folder, route-specific code in the segments that use it.
| Features are owned by different people or move independently (colocation and private folders).
|===

Whichever you pick, the rest of the structure is the same: private folders keep helpers away from the router, route
groups divide the URL space into sections without changing it, and aliases make deep imports readable.

Source: https://nextjs.org/docs/app/getting-started/project-structure#examples[Project structure examples]

The data access layer and the Server Actions are the two files with an architectural role; both are plain modules
that only Server Components and actions import. `lib/dal.ts` reads the session cookie through `cookies()` and is the
single place that decides who the user is (the scratch version only checks that a cookie exists; the authentication
page replaces it with a real session check):

[source,ts]
.lib/dal.ts - a server-only module
----
import "server-only";
import { cache } from "react";
import { cookies } from "next/headers";
import { redirect } from "next/navigation";

// Data Access Layer: the only place that reads the session
export const getUser = cache(async () => {
  const jar = await cookies();
  const id = jar.get("session")?.value;
  return id ? { id } : null;
});

export async function requireUser(locale: string) {
  const user = await getUser();
  if (!user) redirect(`/${locale}/sign-in`);
  return user;
}
----

.lib/actions/reviews.ts - a file of Server Actions

"use server";

import { revalidatePath } from "next/cache";

  const text = String(formData.get("text")).slice(0, 500);

}

Always create `default.tsx` for every slot. The routing pages show how soft navigation keeps the slot's active state
and why a full page load needs this fallback.

Sources: https://nextjs.org/docs/app/api-reference/file-conventions/default[default.js], https://nextjs.org/docs/app/api-reference/file-conventions/parallel-routes[Parallel Routes], https://nextjs.org/docs/app/guides/upgrading/version-16#parallel-routes-defaultjs-requirement[Next.js 16 upgrade guide: default.js requirement]

[#pages-router-structure]
== The Pages Router Structure, for Comparison

In the Pages Router the file name in `pages` is the route, and every file there is a route. There are no layout files,
no colocation and no private folders; special behaviour comes from reserved names with an underscore.

[cols="2,3,3",options="header"]
.The same ideas in both routers
|===
| Concern | App Router | Pages Router

| Route files
| `page.tsx` inside a folder
| Any file in `pages/`; `index.tsx` for the folder's own route

| Document shell (`<html>`, `<body>`)
| Root layout `app/layout.tsx`
| `pages/_document.tsx` (server-only; `Html`, `Head`, `Main`, `NextScript`)

| Shared wrapper around every page
| Nested `layout.tsx` files
| `pages/_app.tsx` (`Component`, `pageProps`)

| Error and not-found UI
| `error`, `global-error`, `not-found`
| `pages/_error.tsx`, `pages/404.tsx`, `pages/500.tsx`

| API endpoints
| `route.ts` in `app/` (Route Handlers)
| Files in `pages/api/`

| Head metadata
| Metadata API and metadata files
| `next/head` per page

| Helper files next to routes
| Safe (colocation, `_private` folders)
| Not safe: any file in `pages/` with a page extension is a route (`pageExtensions` can restrict which extensions count)

| Data
| Async Server Components and `fetch`
| `getStaticProps`, `getServerSideProps`, `getStaticPaths`
|===

A minimal Pages Router project was built to confirm the last point. It has `_app`, `_document`, an index page, a dynamic
page with `getStaticProps` and `getStaticPaths`, an API route and a custom 404, plus a file `pages/helper.tsx` that was
meant as a helper:

[source,text]
.A Pages Router project
----
pages/
├── _app.tsx
├── _document.tsx
├── 404.tsx
├── index.tsx
├── helper.tsx           # a helper that nobody told Next.js is not a page
├── books/[id].tsx
└── api/books.ts
components/helper.tsx    # keep real helpers outside pages/
----

[source,tsx]
.pages/_app.tsx and pages/_document.tsx
----
// pages/_app.tsx
import type { AppProps } from "next/app";

export default function MyApp({ Component, pageProps }: AppProps) {
  return <Component {...pageProps} />;
}

// pages/_document.tsx
import { Html, Head, Main, NextScript } from "next/document";

export default function Document() {
  return (
    <Html lang="en">
      <Head />
      <body>
        <Main />
        <NextScript />
      </body>
    </Html>
  );
}
----

[source,ts]
.pages/api/books.ts - the Pages Router counterpart of a Route Handler
----
import type { NextApiRequest, NextApiResponse } from "next";

export default function handler(_req: NextApiRequest, res: NextApiResponse) {
  res.status(200).json([{ id: "1", title: "Dune" }]);
}
----

[source,bash]
.Pages Router route table and requests (next build, next start)
----
Route (pages)
┌ ○ /
├   /_app
├ ○ /404
├ ƒ /api/books
├   /books/[id]
│ └ ● /books/1
└ ○ /helper

○  (Static)   prerendered as static content
●  (SSG)      prerendered as static HTML (uses getStaticProps)
ƒ  (Dynamic)  server-rendered on demand

$ for u in / /books/1 /api/books /helper /nope; do curl -s -o /dev/null -w "$u %{http_code}\n" localhost:3203$u; done
/ 200
/books/1 200
/api/books 200
/helper 200
/nope 404
----

The helper became the public route `/helper`. A project can use both routers at once, which is how incremental
adoption works, and the same shared folders (`components`, `lib`, `public`) serve both. The root layout replaces
`_app` and `_document` when a page is moved to `app`.

[#what-changed]
== What Changed Recently

[cols="1,5",options="header"]
.Changes to project structure, by Next.js version
|===
| Version | Change

| 13.0
| The `app` directory and the layout, page, loading, error and template conventions were introduced.

| 13.2
| The Metadata API in `app` replaced the experimental `head.js` special file.

| 13.4
| The App Router became stable.

| 15.0
| `instrumentation` became stable and `onRequestError` was added; `params` and `searchParams` became promises.

| 15.1
| `forbidden.js` and `unauthorized.js` introduced (experimental).

| 15.3
| `instrumentation-client` introduced.

| 15.4
| `global-not-found.js` introduced (experimental).

| 15.5
| Middleware can use the Node.js runtime (stable).

| 16.0
| `middleware` is deprecated and renamed `proxy`; the Proxy runs on Node.js and its function is named `proxy`.
`next lint` was removed, so the project carries an `eslint.config.mjs` and runs the ESLint CLI. Parallel-route slots
require a `default.js`. Turbopack is the default bundler. `next dev` writes to `.next/dev`.

| 16.2
| `create-next-app` generates `AGENTS.md`, and version-matched documentation is bundled in the `next` package.

| 16.3
| `retry` became stable in `error.js` (it was `unstable_retry` in 16.2). `next dev` maintains the `AGENTS.md` block
(and `CLAUDE.md`) when an AI coding agent is detected. An experimental router-transition event can be enabled for
`instrumentation-client`.
|===

[#books-outdated]
== Where the Books Are Outdated

The two books consulted for this section, _Real-World Next.js_ (Packt, 2022) and _Practical Next.js for E-Commerce_
(Apress, 2023), describe the Pages Router with Next.js 12 and 13.2. Their project layouts are therefore the Pages
Router ones. Nothing in them is wrong for that router, but several things have moved:

[cols="2,3,3",options="header"]
.Project-structure topics where the books are behind
|===
| Topic | In the books (Pages Router, Next.js 12 / 13.2) | Today (Next.js 16.3)

| Route files and layout
| `pages/`, `pages/_app`, `pages/_document` and `pages/api`; every file in `pages` is a route.
| `app/` with a root layout, nested layouts, `route.ts`; colocation is safe. The Pages Router is still supported.

| Head and SEO files
| `next/head`, the experimental `head.js` file (13.x) and a third-party SEO package.
| The Metadata API plus the metadata file conventions (`robots`, `sitemap`, `manifest`, `icon`, `opengraph-image`).

| Request interception
| `middleware.ts`.
| `proxy.ts` with an exported function named `proxy` (Node.js runtime).

| Code organisation
| Atomic-design style `components` and `lib`/`utils` folders at the root, away from `pages/`.
| Still valid and now one of three official strategies. `components` and `lib` have no special meaning; colocation and
private folders are the alternative.

| `src` folder and alias
| `src/` with an `@/*` alias for imports.
| Unchanged and still offered by `create-next-app`; just update `paths` when moving into `src`.

| Build tooling files
| Custom `.babelrc` and webpack configuration.
| SWC and Turbopack (default in 16); a custom `webpack` config fails `next build` unless you pass a flag.

| Linting
| `next lint` and `.eslintrc`.
| ESLint CLI with `eslint.config.mjs` (flat config).

| New top-level files
| (not covered)
| `instrumentation.ts`, `instrumentation-client.ts`, `mdx-components.tsx`, `AGENTS.md`.
|===

Source for the book editions: https://www.packtpub.com/en-us/product/real-world-nextjs-9781801073493[Real-World Next.js (Packt)] and https://link.springer.com/book/10.1007/978-1-4842-9612-7[Practical Next.js for E-Commerce (Springer)]
